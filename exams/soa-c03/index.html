D1 · Monitoring, Logging, and Remediation 22%

Monitoring and remediation items ask an operator to make the right signal visible or to explain why one is missing: container metrics that never appear, volumes that need more performance but not more space, costs that rose without warning, alarms that fire on a normal daily pattern, or many accounts with no shared view. Each tool answers a different kind of question, so the work is matching the question to the tool.

What to watch for

  • When only part of the expected telemetry shows up, check whether the collector itself runs where the data comes from, not only whether the right permissions exist.
  • For metrics that rise and fall on a daily or weekly rhythm, a single fixed threshold fits badly. Look for a CloudWatch alarm type that learns the expected band.
  • To see many accounts in one dashboard, link them to a central monitoring account instead of copying data around. Questions about cost by service and date belong to a cost tool.

D2 · Reliability and Business Continuity 22%

Reliability questions mix definitions with design choices. Some test vocabulary, such as recovery point versus recovery time, or how an RDS standby differs from a read replica; others ask how to absorb spikes, protect objects from deletion, or prove that backups really restore. Strong answers use the feature that keeps history, buffers load or actually performs a restore, rather than one that only reports.

What to watch for

  • Pin down the terms first: one objective measures acceptable data loss and the other acceptable downtime. Many reliability items depend on reading that number correctly.
  • To handle sudden traffic, separate the tiers with a queue and scale the workers on the backlog. A bigger fixed fleet only moves the breaking point.
  • A backup is proven only by restoring it. Prefer AWS Backup features that test restores on a schedule over ones that lock, log or report on backups.

D3 · Deployment, Provisioning, and Automation 22%

Deployment and automation questions describe an operational job: a stack that hangs during creation, settings that must stay applied on a fleet, a large file copy followed by nightly syncs, a stack update that failed to roll back, or a risky production update. The choice is the AWS tool built for that job at that moment. Several options are related tools that act once, act later or work at a different layer.

What to watch for

  • If a CloudFormation resource waits a long time and then fails, think about a signal the template expects from the instance, not about launch errors, which tend to fail quickly.
  • Separate one-time actions from continuous enforcement. Configuration that must correct itself over time needs a Systems Manager feature built for ongoing state.
  • Before a risky stack update, preview it. Tools that preview changes, find manual drift or protect resources from updates serve three different purposes.

D4 · Security and Compliance 16%

Security operations questions name a goal and a scope: stop even administrators from turning off logging, find card numbers in S3, list resources shared outside the organization, give an application credentials, serve traffic over HTTPS, or let a VPC function reach an AWS API. The task is to pick the control type that fits (preventive, detective or corrective) and confirm that every layer which must allow access does so.

What to watch for

  • Constraints that must bind administrators in member accounts come from organization policies, not from IAM policies inside those accounts or from alarms after the fact.
  • Know what each finding service looks at: data content in S3 buckets, threats seen in activity, or resource policies that grant external or unused access.
  • For cross-account reads of SSE-KMS objects, count every policy that must allow the request, and remember that a VPC function with no internet path still needs a route to the AWS APIs it calls.

D5 · Networking and Content Delivery 18%

Networking items often start from a symptom: a forwarding rule that never takes effect, intermittent 502 errors behind healthy targets, rejected entries in flow logs. Others ask for a capability, such as deep packet inspection or sending users to the fastest Region. Answers depend on knowing which component makes each decision, so a fix aimed at the application rarely solves a network filter problem.

What to watch for

  • When a Route 53 Resolver rule seems to be ignored, check its scope before its target. Rules only affect the VPCs they are associated with.
  • Intermittent errors from a load balancer with healthy targets often come from mismatched connection timeouts between the two sides, not from a lack of capacity.
  • Match the inspection need to the service: inline packet inspection with intrusion prevention, HTTP-layer filtering and threat detection are three different jobs.
