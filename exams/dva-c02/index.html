D1 · Development with AWS Services 32%

Most items put a developer in front of a concrete coding or integration task (expose a function over HTTPS, write an item, read a date range, reject a bad request) and ask which feature or API call does it. Several options name real features of the same service, so the deciding factor is what each feature is actually for: routing traffic, managing versions, metering clients or shaping data.

What to watch for

  • For DynamoDB reads, start from what the key schema already gives you. A known partition key plus a range on the sort key calls for a different operation than reading the whole table.
  • Know how the two kinds of DynamoDB secondary index differ: when each one can be created, which keys it may use, and what read consistency it offers.
  • When an API must refuse bad input, look for an API Gateway feature that inspects the request itself. Features that split, route or meter traffic never check what a request contains.

D2 · Security 26%

Security for developers mixes identity with data protection. A scenario names a caller (a browser app, a microservice, a role in another account) or a piece of data (a key, a sensitive field, a tenant's records) and asks which mechanism lets the right party in and keeps others out. Wrong options often use a real security service for a job it was not built to do.

What to watch for

  • Classify the client first. Code that runs in a browser or on a phone cannot keep a secret, and that fact shapes which Cognito sign-in flow and app client settings fit.
  • For any cross-account KMS question, check both sides: the key policy in the owning account and the IAM policy of the calling identity must both permit the action.
  • Separate protecting stored data from controlling what a user sees on screen. Hiding part of a field by role is an application concern, while encryption context binds ciphertext to metadata such as a tenant ID.
