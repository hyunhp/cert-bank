D1 · Terraform configuration 14.3%

Expect short HCL snippets and team requirements rather than definitions. Some items ask you to predict what an expression returns, others ask which construct enforces a rule, reads an outside fact or configures a provider. The wrong answers tend to be constructs that look close but behave differently, such as a warning where a hard stop was asked for, or a function that treats null and errors alike.

What to watch for

  • Decide first whether the rule must stop the run or only report a problem. Validation and preconditions block; a check block only warns.
  • When a function result is asked, trace null, missing attributes and errors separately. try, coalesce and merge each treat these cases in their own way.
  • For assistant and registry questions, remember that the Terraform MCP server supplies current documentation and workspace data as tools; it does not retrain the model.

D2 · State management and upgrades 14.3%

Most items start from a symptom: a version error on plan, a lock table to retire, a rename across many workspaces, or a need to inspect a large state. The task is to choose the backend setting, block or command that fixes it without losing or rewriting state. Options that edit state by hand or skip a migration step are the usual distractors.

What to watch for

  • Treat state format as one-way. When an older CLI cannot read a state, the fix moves the lagging tool forward and tightens required_version.
  • Match each inspection need to its command: addresses only, one instance, full machine-readable output, or the dependency graph. The scope of the output usually decides it.
  • For renames and refactors in shared modules, prefer a moved block placed inside the module, so every caller picks up the new address on its own next plan.

D3 · Infrastructure workflow and lifecycle 14.3%

This domain follows a change from adoption to apply: importing existing objects, protecting critical ones, splitting projects and loading variables. Scenarios usually include a constraint such as "reviewed before anything changes" or "must not be destroyed", and the right option respects it. Distractors often trade safety for speed, like skipping refresh or editing state directly.

What to watch for

  • When a reviewer must see adopted objects first, favour the declarative import path that appears in plan over commands that change state at once.
  • In split projects, check run order before blaming code. A consumer reading remote outputs fails if the producer has not applied in that environment.
  • Read lifecycle questions carefully: prevent_destroy also blocks replacement, and create_before_destroy is the one rule that Terraform carries over to the resources it depends on.

D4 · CI/CD and deployment 14.3%

Pipeline questions describe a delivery setup (approval gates, preview environments, variable sets, cloud credentials) and something that went wrong or must be designed. You decide which mechanism keeps the reviewed change identical to the applied one and which identity or variable source wins. Answers that re-plan at apply time or rely on long-lived keys are typical traps.

What to watch for

  • An approval only means something when the approved plan file is the one applied. Look for options that save the plan and apply that exact file.
  • For variable conflicts in HCP Terraform, check whether a variable set is marked priority; that flag changes which value a workspace run receives.
  • Dynamic provider credentials rest on a per-run OIDC token that the cloud verifies before handing out temporary credentials. Trust settings should match the subject, not only the audience.

D5 · Security, secrets and compliance 14.3%

Security items mix three themes: who may do what in HCP Terraform, how secrets stay out of state and plans, and how policies gate or merely flag risky changes. The scenario names a control goal, and you pick the setting that reaches it with the least exposure. Close options often differ in whether they block, warn, or still store the secret.

What to watch for

  • Add up permissions from organization, project and workspace scope before deciding what a team can do. A narrow workspace role does not cancel a broad organization grant.
  • Ephemeral values may only flow into a short list of places, such as write-only arguments and provider blocks. Check each usage against that list.
  • For policy enforcement, separate the levels: one blocks with an override path, one blocks fully, and an advisory policy or a check block only warns.

D6 · Modules and the registry 14.3%

Module questions test design and lifecycle: what a reusable module may contain, how refactors keep existing objects, how registry sources and versions are written, and how terraform test runs and cleans up. Many stems include a code fragment and ask for the plan or the outcome. Wrong options usually assume behavior from plain configuration that does not hold inside modules or tests.

What to watch for

  • If a module call fails with count or for_each, look for a provider block inside the module. A reusable module states what it needs and leaves provider configuration to the calling code.
  • For a moved block with an instance key, follow the existing objects to that key and expect only the remaining instances to be created.
  • Inside terraform test, variables set in the test file take priority over ones passed on the command line, and run blocks are cleaned up in the reverse of their order.

D7 · HCP Terraform operations 14.3%

Here the scenarios come from running HCP Terraform for many teams: workspace triggers in a monorepo, project layout, cost estimates, external review gates and version upgrades. You choose the feature or run option that fits the operating need. The distractors are real features placed at the wrong layer, for example a policy where an external service call is needed.

What to watch for

  • When a change starts no run, compare the edited path with the workspace working directory and its trigger patterns or prefixes.
  • Map each gate to its tool: an external service reviewing plan data is a run task, while rules expressible in code belong in a Sentinel or OPA policy set.
  • Group workspaces by team with projects, so access and credentials are set once per team while environments stay separate workspaces.
