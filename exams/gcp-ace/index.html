D1 · Setting up a cloud solution environment 20%

Expect short setup stories: a startup creating its first organization, finance asking for invoices or cost data, a security team preparing a new guardrail. Each one asks for the action or command that fits how Google Cloud is already structured. Wrong options often skip something the platform requires, such as testing a policy first, holding the right billing role, or picking the right dataset location.

What to watch for

  • When a stem asks to see the effect of a guardrail before anyone is blocked, look for a dry-run option rather than a staged rollout across folders.
  • For billing changes, ask which billing role can make the change and whether it is something to apply for rather than a setting to switch on alone.
  • Treat dataset location as a real decision, not a default: for the billing export, multi-region and regional datasets differ in how much cost history they receive.

D2 · Planning and implementing a cloud solution 30%

This is the widest domain. A workload arrives with a few hard constraints (lowest cost, no code rewrite, no servers to run, automatic recovery) and you choose the compute, data, network or deployment product that fits. Several options are usually real Google Cloud services, so the deciding detail is often operational, such as who manages the cluster or whether a network mode supports peering.

What to watch for

  • If existing clients and tools must stay unchanged, prefer the managed version of the same technology over a Google-native service that would need a rewrite.
  • For cheap batch workers that can be interrupted, think about what recreates a lost VM: the provisioning model and the managed instance group work as a pair.
  • Before choosing a networking fix, check the network mode and IP ranges; auto mode VPC networks have limits that custom mode networks with planned, non-overlapping ranges avoid.

D3 · Ensuring the successful operation of a cloud solution 30%

Here the solution already runs and something needs care: a slow database, a bucket whose costs grow, a VM about to be rebuilt, a notebook that must run while its instance is off. Answers are judged on whether they use the built-in operational feature for the job. Distractors tend to capture too little (one disk instead of a whole VM) or rely on manual work the platform already automates.

What to watch for

  • Sort backup options by what they capture: one disk, a bootable image, configuration only, or the entire VM with every disk at one point in time.
  • When nobody can predict which objects will be read, favour a storage feature that moves objects between classes on its own over hand-written lifecycle rules.
  • Anything that must survive deleting a resource, such as an internal IP address, has to be made permanent before the delete, not after it.

D4 · Configuring access and security 20%

Access questions put a principal in front of a task (a pipeline outside Google Cloud, a team lead creating a role, a service calling another service) and ask for the narrowest grant or mechanism that works. The right option usually removes stored keys or picks a role made for exactly one action. Broad roles such as Editor, or a general token role, tend to be the trap.

What to watch for

  • Separate granting roles from defining them: being able to set IAM policy on a project does not let someone create custom roles there.
  • For CI/CD systems outside Google Cloud, look for federation with an attribute condition that limits which workflows can act, instead of any option that stores a key.
  • When cutting back broad grants, rely on evidence of actual permission use from IAM role recommendations, and check which permissions a custom role may contain before drafting it.
