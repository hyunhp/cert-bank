D1 · Design Secure Architectures 30%

Questions in this domain rarely ask you to define a service. They describe a requirement (a new policy, a group of users, a kind of data) and ask which control meets it with the least exposure. Three threads come up again and again: who gets access and how, what traffic may reach or leave the workload, and how the data itself is protected.

What to watch for

  • Find the constraint that decides the answer, such as "without embedding credentials" or "never more than an approved ceiling". It usually rules out options before the service names matter.
  • Keep detection and enforcement apart: a service that finds a problem is not the one that blocks it.
  • Check whether a setting can be changed later. Some protections, such as encryption at rest on an EFS file system, are fixed when the resource is created.

D2 · Design Resilient Architectures 26%

Resilience questions describe something that can fail or change size (a Region, instances that scale in, a database read path, a backup routine) and ask how the design keeps working or recovers. The choice usually turns on how fast recovery must be and how much the business will pay for it. Weak answers keep state on a single instance or pick a service that copies data without managing backup policy.

What to watch for

  • Read the recovery target and the budget together. Accepting hours of downtime allows a much cheaper disaster recovery pattern than one that keeps resources running in a second Region.
  • Anything that must survive scale-in, such as user sessions, has to live outside the instances. Pinning users to one instance only delays the problem.
  • Match routing needs to the layer: rules on path, host or header need an HTTP-aware load balancer, while the other Elastic Load Balancing types work below that level.
Tasks in the official exam guide (2)

  • 2.2 Highly available, fault-tolerant architectures

D3 · Design High-Performing Architectures 24%

This domain hands you a workload with a performance target (a latency budget, a throughput figure, an access pattern) and asks which storage, database, network or analytics service meets it. The wrong options are usually real services that would work, only slower, costlier or built for a different pattern.

What to watch for

  • Read the access pattern before the service names: large sequential reads, a shared POSIX file system and per-request edge logic each point to a different family.
  • When a table throttles while its total capacity looks fine, suspect how the keys spread the load rather than the capacity setting.
  • Prefer the lightest option that meets the target. If no extra capability is asked for, the simpler and cheaper service is often the intended answer.

D4 · Design Cost-Optimized Architectures 20%

Cost questions set a workload pattern (low and spiky traffic, a short event that needs guaranteed capacity, data with unknown access, shared costs across business units) and ask for the option that meets it for the least money. Watch for answers that give a discount without the capacity, or a report without the alert. The cheapest choice still has to satisfy every stated requirement.

What to watch for

  • Separate discounts from guarantees. A pricing commitment such as a Savings Plan lowers the rate but does not hold instances for you in a specific Availability Zone.
  • Per-project chargeback and alerts both start with tags activated for cost allocation. After that, pick the tool that fits the need: a report to attribute cost, a budget to send alerts.
  • When access to stored objects is unpredictable, prefer a storage class that moves data between tiers automatically over hand-written lifecycle rules that guess the pattern.
