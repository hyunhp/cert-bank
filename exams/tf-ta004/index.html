D1 · Infrastructure as Code (IaC) with Terraform 12.5%

As the entry point of the exam, this domain checks the ideas behind infrastructure as code more than syntax. Items ask what Terraform is for, how it works across platforms, and which of its parts (providers, modules, HCL, state) plays which role. Distractors often stretch Terraform into jobs it does not do, such as managing software inside servers.

What to watch for

  • Keep the roles apart: providers translate resources into API calls, modules package reusable configuration, and state records what Terraform manages.
  • When a stem talks about many clouds, the shared part is the workflow and language. Resource types still belong to each provider.
  • Watch for in-guest tasks like installing packages or editing config files. Those point to configuration management tools rather than to Terraform.
Tasks in the official exam guide (3)
  • 1.1 Explain what IaC is
  • 1.2 Describe the advantages of IaC patterns
  • 1.3 Explain how Terraform manages multi-cloud, hybrid cloud, and service-agnostic workflows

D2 · Terraform fundamentals 12.5%

Fundamentals covers providers and state at a practical level. You read a short configuration and say which provider configuration a resource uses, which version a constraint selects, what a lock file error means, or what state adds beyond the code. Correct answers follow Terraform's documented rules exactly, while wrong ones rely on intuition about "latest" or "default".

What to watch for

  • For version constraints, apply every condition together and then take the newest version that passes all of them, unless a lock file already fixes the choice.
  • A resource without a provider argument uses the default configuration; only an explicit alias reference selects another one.
  • State holds what configuration cannot: the link from each instance to its real object ID, plus metadata such as recorded dependencies.
Tasks in the official exam guide (4)
  • 2.1 Install and version Terraform providers
  • 2.2 Describe how Terraform uses providers
  • 2.3 Write Terraform configuration using multiple providers
  • 2.4 Explain how Terraform uses and manages state

D3 · Core Terraform workflow 12.5%

Questions walk through write, plan and apply, then ask about the flags that change each step: init upgrades, formatting gates in CI, saved plans, targets and refresh options. Each scenario has a goal such as "do not change files" or "apply exactly what was reviewed". The right flag meets that goal, and close alternatives either do too much or quietly skip a safety check.

What to watch for

  • Planning options belong on the plan command. A saved plan file already holds its decisions, so apply rejects added planning flags.
  • A formatting gate in CI should report problems without rewriting files and should cover subfolders, which takes two separate options.
  • Skipping refresh makes plans faster but blind to changes made outside Terraform. Refresh-only does the opposite: it updates state and changes nothing real.

D4 · Terraform configuration 12.5%

Configuration items are the most hands-on in this exam. They show resource, data, variable and local blocks, and ask how to reference an instance, what an expression evaluates to, when a data source is read, or when a validation runs. Precise reading of the snippet matters, because the distractors are usually near-miss syntax or a wrong step in the run order.

What to watch for

  • Address for_each instances by key and count instances by index. The brackets look similar, but the value inside them differs.
  • When a data source depends on a value not known yet, expect its read to move to the apply phase and its attributes to show as known after apply.
  • Compare secret handling options by where the value ends up. Ephemeral resources keep it out of state and plans, while ordinary data sources store their results.

D5 · Terraform modules 12.5%

Module scenarios focus on boundaries and sources. You decide how values cross into and out of a child module, how to order a module after a resource it does not reference, where init places downloaded code, and how tightly a source is pinned. Options that assume a module can see the caller's variables or resources directly are common traps.

What to watch for

  • Only arguments in the module block go in, and only outputs come out. Anything else inside another module is out of reach.
  • If ordering matters but no attribute links the two, an explicit depends_on on the module block is the tool to consider.
  • Judge module proposals by the abstraction they add. A thin wrapper that passes every argument through unchanged adds a layer without real value.

  • 5.2 Describe variable scope within modules

  • 5.4 Manage module versions

D6 · Terraform state management 12.5%

State management is tested through operational situations: locking without extra services, objects deleted outside Terraform, stuck locks, local backend behavior and saved plans that fail later. You pick the setting or command that keeps state consistent with reality without risking corruption. Unsafe shortcuts, such as unlocking another person's live run, appear often as attractive wrong answers.

What to watch for

  • Know what each refresh option touches: refresh-only rewrites state to match reality and leaves real objects alone, so a later normal plan may recreate missing ones.
  • Force-unlock is a recovery tool for a stale lock you own. Using it to bypass a running operation risks several writers on one state.
  • A saved plan carries backend settings with it. Short-lived backend credentials are safer passed through environment variables.
Tasks in the official exam guide (4)
  • 6.1 Describe the local backend
  • 6.2 Describe state locking
  • 6.3 Configure remote state with the backend block
  • 6.4 Manage resource drift and Terraform state

D7 · Maintain infrastructure with Terraform 12.5%

Maintenance items check that you can import, inspect and debug without causing damage. Scenarios include binding existing objects, reading state with scripts, changing log levels and sharing command output. The correct option is usually the read-only or narrowly scoped one; distractors either change more than needed or overlook that some outputs reveal sensitive values in plain text.

What to watch for

  • Bind every real object to one resource address only. Two addresses for one object leads to conflicting actions later.
  • Separate state subcommands that read from those that modify; only the modifying ones write backups, and none of them change real infrastructure.
  • Treat machine-readable state output as secret material. Sensitive values that are hidden in normal CLI output can appear there unmasked.
Tasks in the official exam guide (3)
  • 7.1 Import existing infrastructure
  • 7.2 Use the CLI to inspect state
  • 7.3 Describe when and how to use verbose logging

D8 · HCP Terraform 12.5%

This domain describes everyday use of HCP Terraform: VCS-driven runs, workspace variables, team permissions, cloud block settings and policy enforcement. Each stem names an action, such as opening a pull request or failing a policy, and asks what the platform does next. Knowing the default behavior of each workflow separates the right option from plausible guesses.

What to watch for

  • Link the event to the run type: a pull request gives a plan that cannot be applied, while a merge to the tracked branch starts a normal run.
  • Sensitive workspace variables can be replaced but never read back. They can still leak if the configuration exposes them in state or logs.
  • Team access adds up across organization, project and workspace levels, so the broadest grant decides what a team can actually do.
