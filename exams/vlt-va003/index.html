D1 · Authentication methods 11.1%

Auth method items pair a type of client with an identity source and ask which method fits, or why a login fails. People with directory accounts, Kubernetes workloads and shared logins all appear. The right answer follows how Vault turns verified credentials into a token with identity and policies; wrong options often pick a method built for a different kind of client.

What to watch for

  • Start with who is logging in. Humans with existing accounts and machine workloads lead to different method families.
  • When a Kubernetes login fails in one namespace only, compare the namespaces and service accounts bound to the role with the ones in use.
  • Shared credentials hide who did what in audit logs. Give each person a login and share permissions through groups instead.

D2 · Vault policies 11.1%

Policy questions are mostly about reading HCL path stanzas correctly. A stem shows a path, a capability list or a template and asks what a request is allowed to do, or which policy grants just enough. Because Vault denies by default, the details decide the answer: exact versus glob paths, the KV v2 data/ segment, and how deny interacts with everything else.

What to watch for

  • Check whether the path is exact or uses a glob before thinking about capabilities. An exact path matches one location only.
  • For KV v2, write policies against the real API paths, which include data/ for values and metadata/ for key names.
  • Remember that deny overrides every other capability, and that list results are not filtered, so key names should never carry secrets.

D3 · Vault tokens 11.1%

Token scenarios ask which token type or setting matches a workload, why a token request is refused, or how long a token can survive. Root token handling, accessors, periods and maximum TTLs come up often. The distractors usually treat renewal as unlimited or ignore which actions need extra privileges on the token create path.

What to watch for

  • Look for the hard limit before trusting renewal. An explicit max TTL caps total life no matter how often the token is renewed.
  • Child tokens and on-demand revocation point to service tokens; batch tokens give up those features in exchange for being lightweight.
  • If creating a token works until a flag like period or orphan is added, the missing piece is extra privilege on the create path, best delegated through a token role.

D4 · Vault leases 11.1%

Lease questions check what each lease operation does and who may run it. Some ask for the matching CLI or HTTP call, others ask why bulk revocation is denied or why leases exist at all. Right answers separate inspecting a lease from changing it, and recognise which endpoints are privileged.

What to watch for

  • Separate reading from acting: lookup only reports timing and renewability, while renew and revoke change the lease.
  • Bulk operations such as prefix revocation need the sudo capability on their sys paths, unlike revoking a single lease.
  • Use tidy with care. It cleans up leases left without a valid token, but it can put a heavy load on storage.

D5 · Secrets engines 11.1%

Secrets engine items ask which engine matches a need and how to use it correctly. Typical needs are encrypting data an application stores itself, issuing short-lived certificates, creating database users on demand, or reading KV v2 data with generic commands. The distractors are often real engines used for the wrong pattern, or commands that ignore the real API path.

What to watch for

  • Sort engines into those that only return what was written and those that create the secret on request. The scenario usually signals which one is needed.
  • With the generic read command on KV v2, the path must include the data/ segment that the kv subcommands hide.
  • For PKI, prefer short-lived, unique certificates per instance; they keep revocation rare and revocation lists small.

D6 · Encryption as a Service 11.1%

Encryption as a Service centres on the transit engine. Stems show encrypt, decrypt or key configuration commands and ask what is wrong, what the output means, or what a key setting allows. Small details carry the answer: base64 encoding on the way in and out, which named key produced a ciphertext, and the difference between encryption and decryption version limits.

What to watch for

  • Transit works with base64 on both sides, and encoding the plaintext is your job, not the CLI's. Check the encoding before suspecting the key.
  • A ciphertext can be decrypted only with the named key that produced it. The version prefix identifies the key version, not the key name.
  • Keep the two minimum version settings apart: one limits which versions encrypt, the other limits which can decrypt.

D7 · Vault architecture fundamentals 11.1%

Architecture fundamentals cover what happens from first start to sealed data at rest. Questions ask about the initialize and unseal steps, the default behavior of operator init, what the security barrier does, how the key chain fits together, and which client settings are safe. Wrong options tend to mix up the order of keys or treat test shortcuts as production practice.

What to watch for

  • Trace the key chain in order: unseal key, then root key, then encryption key, then data. Most wrong options reverse or skip a link.
  • A new server must be initialized once before any unseal step makes sense. Read the status flags in the stem before choosing.
  • For TLS problems with a private CA, trust the CA explicitly rather than disabling certificate verification, which suits only testing.

D8 · Vault deployment architecture 11.1%

Deployment questions weigh cluster design choices: seal types, rekeying, replication effects, storage layout and node counts. Most present a proposal or operational pain point and ask what the change really achieves. Answers that sound safer, such as adding a node or a standby for throughput, are often wrong once quorum and HA behavior are taken into account.

What to watch for

  • Work out failure tolerance from quorum, not from node count alone. An even node count can add cost without adding resilience.
  • Auto-unseal removes human share holders at start-up but adds a dependency on a trusted external service. Rekeying replaces shares when holders change.
  • When storage and ha_storage differ, one stores the encrypted data and the other holds the lock that chooses the active node.

D9 · Access management architecture 11.1%

Access management architecture is about getting secrets to applications. Scenarios involve Kubernetes pods, VSO resources, Vault Agent caching and applications that cannot reload secrets. You decide which delivery pattern or setting fits, or why secrets come back stale. Distractors usually mix up Kubernetes-only tools with host-based ones, or miss how Agent settings and environment variables interact.

What to watch for

  • Match the delivery tool to the platform: the Injector and VSO run in Kubernetes, while Vault Agent templates also serve applications on virtual machines.
  • For VSO, separate where Vault is from how the operator logs in; each lives in its own resource kind.
  • If Agent keeps serving revoked credentials or dials itself, look at its cache and its environment before changing the Vault server.
