D1 · Data Connectivity and Ingestion 12.5%

Ingestion scenarios describe a source (where it sits on the network, how it delivers data, whether it has a reliable change column) and ask for the connection and sync pattern that fits. Some also concern virtual tables or a standard way to onboard many sources. Wrong options force a source into a pattern it does not support, such as an incremental sync with nothing reliable to key on.

What to watch for

  • Check network reach first: a direct connection when Foundry can reach the source, and an agent inside the network when it cannot.
  • Look at how the source signals change. A trustworthy update column supports incremental syncs, ideally with periodic reconciliation; without one, snapshots are safer.
  • Batch files are landed as raw files first and parsed in a transform, instead of being treated like a database or a stream.
Tasks in the official exam guide (4)
  • 1.1 Connectors and connection architecture
  • 1.2 Snapshot, append, update and CDC ingestion
  • 1.3 Agents, egress, virtual tables and exports
  • 1.4 Diagnosing stale or failing ingestion

D2 · Data Transformation and Pipeline Authoring 12.5%

Transform questions focus on correctness and maintainability more than syntax. Situations include business definitions that must not drift, missing values in aggregates, cleanup rules that change over time, and small jobs on a heavy engine. The best options make the logic testable and visible (unit tests, expectations, branch comparisons, reference datasets) and keep the engine sized to the data.

What to watch for

  • Validate a change by comparing the branch output with production on counts, keys and metrics. A successful build alone proves very little.
  • Missing values need an agreed meaning. Decide with the business how nulls are treated in an aggregate and make their count visible.
  • For small inputs where startup time dominates, a lightweight engine is a better fit than Spark; data that outgrows one node points back to Spark.
Tasks in the official exam guide (4)
  • 2.1 Pipeline Builder, Code Workspaces or Code Repositories
  • 2.2 Joins, aggregations, expressions and enrichment
  • 2.3 Choosing a compute engine
  • 2.4 Testing, debugging and refactoring transforms

D3 · Pipeline Processing Modes 12.5%

This domain turns on how data moves through a pipeline: batch, incremental or streaming, and what each transaction type does to a dataset. Scenarios mix freshness needs, unexpected full recomputes and streaming jobs that stall while still running. You choose the mode, explain the behaviour or pick what to check first, and precise knowledge of the transaction types often decides the answer.

What to watch for

  • Learn the four transaction types well. Incremental transforms stay incremental only on appended inputs, so other types in the history explain a sudden full rebuild.
  • One source can feed outputs with different freshness needs. A live view and a daily report may need streaming and batch side by side.
  • When a streaming job looks healthy but produces nothing, its lag, backlog and error metrics are the first evidence to read.
Tasks in the official exam guide (4)
  • 3.1 Batch, incremental, streaming or lightweight
  • 3.2 SNAPSHOT, APPEND, UPDATE and DELETE semantics
  • 3.3 Incremental fallback to snapshot
  • 3.4 State, backlogs, small files, replay and schema evolution

D4 · Pipeline Operations and Scheduling 12.5%

Running pipelines day to day is the subject: schedules, slow builds, chains of failures and compute cost. Scenarios give symptoms (a doubled runtime, many red builds, a high bill, a source that skips holidays) and ask for the likely cause or the next step. Answers that use evidence such as Job Comparison and lineage, and that remove unneeded work first, beat simply adding resources.

What to watch for

  • When many builds fail at once, look for one shared upstream input. Fixing that first and rebuilding in order avoids chasing each error.
  • Compare a slow run with a recent normal one before changing anything. Memory pressure and garbage collection usually point to data or code, not to too few resources.
  • Builds should follow data arrival and real consumption. An input-update trigger and a frequency matched to the readers cut both waste and early starts.
Tasks in the official exam guide (4)
  • 4.1 Schedules and event-based triggers
  • 4.2 Diagnostic evidence: builds, logs, lineage, Spark details
  • 4.3 Classifying slowdowns and failures
  • 4.4 Branches, releases, resources and cost

D5 · Data Quality and Health Monitoring 12.5%

Data quality scenarios ask which control fits a risk and what to do when an alert fires. You weigh build-blocking expectations against health checks, isolate bad input files, trace schema changes and define what a new dataset needs before it ships. The key distinction is between a rule that must never be broken and a shift that might be genuine business change.

What to watch for

  • Expectations stop invalid data at build time and health checks watch published data over time. Critical datasets usually need both.
  • On a schema alert with no code change, trace the column upstream with Data Lineage and decide whether it is breaking before editing anything.
  • A single bad file should not stop good data. Validating each file as it is parsed lets non-conforming ones go to quarantine with an alert.
Tasks in the official exam guide (3)
  • 5.1 Expectations versus health checks
  • 5.2 Blocking invalid transactions
  • 5.3 Monitoring, alerts and investigation

D6 · Security, Projects, and Governance 12.5%

Most security scenarios here are puzzles about why one person sees less than expected, or how to grant exactly the right access. You reason across project roles, markings, organizations, restricted views and Ontology policies. The trap is assuming a higher role fixes everything; correct answers find the specific missing control and enforce restrictions in the data layer so they hold on every path.

What to watch for

  • Roles and markings are separate. No project role, however high, replaces holding a marking, so look for the marking when a role seems sufficient.
  • If a user can read an object type but a link returns nothing, check access on the linked side, using Check Access on that object type's data.
  • External or temporary access should be narrow and expire: a dedicated group, a project with only the needed data, and an end date.
Tasks in the official exam guide (4)
  • 6.1 Organizations, markings and project roles
  • 6.2 Project structure and boundaries
  • 6.3 Restricted views for row-level access
  • 6.4 Diagnosing access failures

D7 · Ontology Data Modeling 12.5%

Ontology modeling questions ask how real-world things and relationships become object types, links and keys, and how to change a live model safely. Scenarios cover cardinality, relationships that change over time, attributes in the wrong place and retiring old types. Wrong options often store entity facts on pair or summary objects, or skip the migration of user edits.

What to watch for

  • Put each attribute on the entity it describes. A customer's address belongs on Customer, not on an object that pairs customers with products.
  • A relationship with its own dates or attributes deserves its own object type linked to both sides, and the current state can be derived from it.
  • Decide where values are computed: filterable, widely used values south in the pipeline, and on-demand explanations or user-driven values north.
Tasks in the official exam guide (5)
  • 7.1 Object types, properties, links and interfaces
  • 7.2 Primary keys and link cardinality
  • 7.3 Normalization and modeling anti-patterns
  • 7.4 Evolving live Ontology resources
  • 7.5 Computation north or south of the Ontology

D8 · AI-Assisted Data Engineering 12.5%

AI shows up here in two roles: as a helper for engineers and as a step that enriches data. Scenarios ask which AI capability fits, where it should run, how to keep repeated runs affordable, and how to review AI-written transforms. Sound answers keep deterministic logic first, verify AI output and code against lineage and contracts, and record versions so results can be traced and refreshed.

What to watch for

  • Use AI where rules run out. Structured problems such as parsing are solved with rules and reference data first, and the model handles what remains.
  • Treat code assistant output as a draft. Verify summaries against lineage, and replace hard-coded values in generated code with governed reference datasets.
  • For large enrichment jobs, process only changed rows and key the cache by input and prompt version, so prompt changes can be backfilled gradually.
Tasks in the official exam guide (4)
  • 8.1 AI FDE, AIP Assist, Continue and LLM transforms
  • 8.2 Structured outputs, caching and quality checks
  • 8.3 Pipeline-layer versus Ontology-layer AI
  • 8.4 Reviewing AI-generated code and outputs
