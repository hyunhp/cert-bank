D1 · Data Ingestion and Transformation 34%

Ingestion and transformation questions describe a data source, a latency need and the tools a team already uses, then ask which AWS service or feature moves and processes the data. Keywords like real-time, existing Kafka or serverless often decide the answer. Wrong options tend to be capable services that would mean rewriting clients, managing more infrastructure or reprocessing data already handled.

What to watch for

  • Keep existing tools in mind. Teams already using Kafka clients or Airflow DAGs are usually best served by the managed version of that tool.
  • On EMR, put Spot capacity only on nodes whose loss is harmless, and keep the nodes that control the cluster or hold HDFS data On-Demand.
  • When a scheduled job keeps reprocessing old files, the fix is tracking state between runs, not changing crawlers or schemas.

D2 · Data Store Management 26%

Data store questions describe an access pattern, a growth problem or a governance need and ask which store, table format or feature fits. The common pairs become clear once the pattern is named: key-value lookups versus large analytical joins, loading versus exporting, Athena versus Redshift Spectrum. Distractors often add metadata or capacity when the real fix is a different feature.

What to watch for

  • Classify the access pattern before reading the service names: single-key lookup, heavy analytics, full-text search and time series point to different stores.
  • When storage fills up but compute sits idle, look for options that scale the two separately rather than buying more of both.
  • For tables with huge numbers of predictably named partitions, computing partitions beats registering them; more crawling only adds metadata.

D3 · Data Operations and Support 22%

Operations items start with a symptom: one task that runs for hours, a pipeline that finishes late, duplicate rows, a slow dashboard query or failures linked to Spot interruptions. You diagnose the cause and pick a targeted fix. Answers that simply add resources are usually wrong, because the intended cause is often key design, data skew or missing state.

What to watch for

  • Think symptom, then cause, then fix. A single slow task on a join with one dominant key is a data distribution problem, not a capacity one.
  • To catch a job that never finishes, alarm on the absence of its completion signal instead of waiting for someone to notice.
  • When small errors are acceptable, an approximate aggregate can be far cheaper and faster than an exact distinct count over a huge table.

D4 · Data Security and Governance 18%

Security and governance scenarios cover IAM delegation, KMS keys, central audit logging, PII in free text and data catalogs for business users. The question usually asks for a control that is both least privilege and auditable. Options that fail either test are the distractors, even when they look simpler or cover more ground.

What to watch for

  • Keep finding and fixing apart: a service that discovers PII is not the one that removes it from free text.
  • Pointing an alias at a new KMS key changes only future encryptions. Older ciphertext still needs the key that encrypted it.
  • When IAM and Lake Formation both appear, work out which layer is blocking access, because access can be allowed by one layer and refused by the other.
