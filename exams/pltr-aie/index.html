D1 · AIP Logic Development 12.5%

Each scenario describes a job for an AIP Logic function, such as pulling related Ontology objects, ranking work items or writing new objects, and asks how to build or change it safely. The better options split the work cleanly: tools fetch the data, the model handles only the language part, and code applies fixed rules. Weak options hand everything to the model or push changes straight to live consumers.

What to watch for

  • Look for the part of the task that follows a fixed rule. If a rule can be computed, it belongs in deterministic logic, and the model should only interpret text.
  • Be careful with any function that writes Ontology edits. A safe answer limits the first runs to a small sample and keeps writes off or on a branch until someone reviews the result.
  • When a function has many callers, think in versions. A new input that starts optional with a default lets consumers move over one by one.
Tasks in the official exam guide (3)
  • 1.1 Typed inputs/outputs, prompts, tools and blocks
  • 1.2 Ontology edits and Logic versus code
  • 1.3 Debugging traces, tuning and publishing versions

D2 · AIP Agent Design and Deployment 12.5%

Here the setting is an agent about to be built or released: who uses it, on what device, with which data, and what it must never do. The task is to pick the configuration, environment or test that fits that context. Correct choices rely on hard limits (scoped retrieval, withheld tools, typed outputs, tests per identity); wrong ones usually rely on politer wording in the instructions.

What to watch for

  • Note where the agent runs and who reads its answers. A mobile or wearable user changes the right scope, answer length and model speed.
  • If content or an operation is off-limits, remove it from what the agent can reach, then prove the refusal with adversarial test cases.
  • Permission behaviour is only verified by testing as several different users, including one with no access, and checking what each one sees.
Tasks in the official exam guide (3)
  • 2.1 Agent types and deployment channels
  • 2.2 Tools, retrieval context and guardrails
  • 2.3 Testing agents before release

D3 · RAG Architecture and Semantic Search 12.5%

Retrieval questions start from a corpus problem: answers cite nothing, old documents slip in, short entries get buried, or quality is unknown. You decide how chunks are built, tagged, filtered and measured. Strong answers solve the problem in the data and the pipeline (metadata, filters, chunk identifiers, labelled evaluation sets) instead of asking the model to judge freshness or remember its sources.

What to watch for

  • Treat metadata as the main control. Status, dates and document type let retrieval filter or prefer the right chunks before the model ever sees them.
  • Citations must travel with the data. An identifier attached to each chunk can come back in a structured output; a request to the model to name sources cannot be trusted.
  • Measure retrieval on its own, against chunks that people have labelled as relevant, so a weak index is not hidden behind a good generator.
Tasks in the official exam guide (3)
  • 3.1 Chunking, metadata and embeddings
  • 3.2 Precision, recall, freshness and token limits
  • 3.3 Diagnosing poorly grounded answers

D4 · AI-Powered Data Processing 12.5%

Batch enrichment is the theme: large record sets, nightly runs, unstable provider APIs and auditors who ask where a value came from. You choose the build layer (Pipeline Builder, Code Repositories or an on-demand Logic function) and the records and controls that make each AI-produced row reliable and traceable. Options that ignore scale, failures or provenance are the usual distractors.

What to watch for

  • Match the tool to the amount of control required. Custom retries, rate limits and per-row audit point to code, while simpler batch jobs can stay in Pipeline Builder.
  • Let the model extract and let deterministic code clean up. Matching name variants to one canonical key is a rules job, not a prompt job.
  • Think about what an auditor will ask later. Storing the prompt version, model id and injected inputs on each row turns provenance into a query.
Tasks in the official exam guide (4)
  • 4.1 Batch LLM/VLM processing and structured output
  • 4.2 Preserving prompts and raw responses
  • 4.3 Processing layer: south or north of the Ontology
  • 4.4 Code Repositories for scheduled, programmatic work

D5 · Evaluation, Testing, and Quality Assurance 12.5%

Expect situations where an evaluation result needs reading, not just running: a score that moved, a suite that engineers learned to game, free text that needs grading, or corrections arriving from downstream. The questions ask what the numbers really mean and how to build cases and evaluators that stay honest. Distractors often treat a single score as proof of a regression or of quality.

What to watch for

  • Before calling a drop a regression, check whether the test cases changed too. Old and new cases should be scored apart so a shift in the suite is not blamed on the function.
  • Pick the evaluator by output type: exact checks in code for single correct values, and model graders for free text only with clear criteria and human calibration.
  • Good edge cases come from the hard spots of the business domain, and real failures from users or downstream fixes should become new cases.
Tasks in the official exam guide (4)
  • 5.1 Evaluation suites, evaluators and metrics
  • 5.2 Edge, adversarial and high-consequence cases
  • 5.3 Regression versus non-deterministic variance
  • 5.4 Feedback loops into evaluation

D6 · Automation, Orchestration, and Integration 12.5%

These scenarios join AI steps to automations and Actions, and then something goes wrong: silent empty results, wasted runs, races between processes, or two writers fighting over a value. You decide where to validate, what should trigger a run and how writes are guarded. The right answers make failures loud and writes controlled, rather than adding delays or turning retries off.

What to watch for

  • An AI result should pass validation before anything is written. A function-backed Action is the usual place where checked output becomes an Ontology change.
  • When an automation runs far too often, narrow its trigger to the properties or state changes that actually feed the AI step.
  • Concurrent writers need explicit rules: a version check at write time, or a single owner for each property, prevents stale or flipping values.
Tasks in the official exam guide (3)
  • 6.1 Automate triggers, effects and execution modes
  • 6.2 Chaining Functions, Actions and AI outputs
  • 6.3 Retries, duplicates and safe changes to live workflows

D7 · Model Selection, Observability, and Performance 12.5%

Choosing a model and keeping it healthy in production are the two halves of this domain. Situations include language coverage, context size, rising cost, slower answers and a product owner asking for proof. Correct options tie each choice to a stated requirement and confirm it with evaluation or AIP Observability data, while weaker ones pick the biggest model or guess without evidence.

What to watch for

  • Let the requirement pick the model. If quality must hold for every language or input type, the evaluation suite should be split the same way.
  • When a live system drifts with no change on the team's side, traces and telemetry over time show which stage moved, so start there.
  • Caching only fits answers that do not depend on the user or context. The cache key needs the content version so stale answers can be cleared.
Tasks in the official exam guide (4)
  • 7.1 Model selection from requirements
  • 7.2 Multi-provider resilience, BYOM and custom endpoints
  • 7.3 Observability: traces, logs and token telemetry
  • 7.4 Latency and cost optimization

D8 · Security, Governance, and Responsible AI 12.5%

Risk drives this domain: sensitive data in tools and traces, prompt injection, decisions about people, and audits of what an AI recommendation was based on. The questions ask which control, record or review step addresses the risk. Reliable answers lean on identity, permissions, stored evidence and human decisions; prompt warnings and the model's own explanation are rarely enough.

What to watch for

  • When the tools act with the identity of whoever is asking, Ontology permissions filter each answer per person, without a separate copy of the agent per group.
  • Traces and logs hold the same data the model saw. They need the same markings, access limits and auditing as the source data.
  • For high-consequence outcomes, look for AI that explains and flags while a person decides, with bias checks and evidence stored outside the model.
Tasks in the official exam guide (4)
  • 8.1 Permissions, execution security and georestrictions
  • 8.2 Audit, lineage and sensitive data
  • 8.3 Human review for high-consequence actions
  • 8.4 Prompt injection, exfiltration and unsafe tool use
