AZ-104 Study Guide: The Azure Administrator Exam Is a Troubleshooting Exam, So Study It by Symptom

AZ-104 (Microsoft Azure Administrator) is usually described by its five skill areas. That is how Microsoft lists it, but it is not how the questions feel. Half of the 250 AZ-104 questions we wrote for this site start with something that does not work: a VM no one can reach, a user who cannot read a blob, a deployment that fails. So this guide is organised by symptom: what you see, where to look, and what usually fixes it.

Study guide · Microsoft Azure Administrator (AZ-104)

The exam

100 minutes; Microsoft does not publish the number of questions. Passing score 700 on a scale of 1–1,000. Besides multiple choice, expect interactive items such as case studies. Skill areas: Manage Azure identities and governance (20–25%), Implement and manage storage (15–20%), Deploy and manage Azure compute resources (20–25%), Implement and manage virtual networking (15–20%), Monitor and maintain Azure resources (10–15%). On associate exams such as AZ-104 you can open Microsoft Learn during the exam. It is meant for looking up one detail, not for every question, and the clock keeps running, so do not count on having time to search.

Symptom: "nobody can connect to the VM"

  • Check the effective security rules on the network interface. A VM can have an NSG on its NIC and another on its subnet; inbound traffic must pass the subnet NSG first and then the NIC NSG, and both must allow it.
  • Use Network Watcher IP flow verify to test one specific packet; it names the rule that allowed or denied it.
  • Remember rule order: lower priority numbers win, and the default rules (including DenyAllInBound at 65500) sit at the bottom.
  • No public IP and no Bastion? The VM is only reachable from inside the network, through peering, VPN or ExpressRoute.
Going deeper: why a deny at the subnet cannot be fixed at the NIC

For inbound traffic, Azure evaluates the subnet's NSG first. If a rule there denies the packet, it is dropped before the NIC's NSG is ever consulted, so adding an allow rule on the NIC changes nothing. For outbound traffic the order is reversed: NIC first, then subnet. The rules are also stateful: once an inbound connection is allowed, its return traffic is allowed automatically, which is why you rarely need outbound rules for replies. Questions that show two NSGs and ask why traffic still fails are testing exactly this order.

Symptom: "the VNets are peered, but traffic does not get through"

Peering is not transitive: if A is peered with B and B with C, A cannot reach C through B. Either peer A and C directly, or route through a network virtual appliance or Azure Virtual WAN in a hub. To let spokes use a VPN gateway in the hub, enable gateway transit on the hub side and use remote gateways on the spoke side. Overlapping address spaces cannot be peered at all.

Symptom: "the user has Contributor but cannot read the blob"

Azure separates the control plane (managing resources) from the data plane (the data inside them). Owner and Contributor manage the storage account; to read or write blobs with Microsoft Entra authentication a user needs a data role such as Storage Blob Data Reader or Storage Blob Data Contributor. Other causes to rule out: the storage account firewall does not allow the user's network, a SAS has expired or lacks the needed permission, or a stored access policy was changed.

Going deeper: the account key loophole

Contributor cannot read data through Entra authentication, but it can list the storage account's access keys, and an account key opens all data in the account. That is why "Contributor can still get at the data" is true in practice, and why hardened environments disable shared key authorisation on the storage account so that only Entra roles (and user delegation SAS) work. If a question asks how to make sure access is controlled only through RBAC, disabling shared key access is the step people forget.

Symptom: "the deployment failed" or "the change is not allowed"

  • Azure Policy with a deny effect blocks resources that break a rule (wrong region, missing tag). The error names the policy assignment.
  • A resource lock blocks deletion (CanNotDelete) or every change (ReadOnly), even for an Owner, until the lock is removed.
  • A quota (for example vCPUs per VM family per region) blocks a VM size; request an increase.
  • Moving a resource to another resource group or subscription fails if the resource type does not support the move or if dependent resources are left behind.

Beginner tip: make every failure on purpose once. In a free or pay-as-you-go subscription, put a CanNotDelete lock on a resource group and try to delete a resource in it; add a deny NSG rule and run IP flow verify; give a test user Contributor and try to open a blob in the portal with "Microsoft Entra user account" selected. Each takes minutes, costs almost nothing if you delete the resources afterwards, and turns a troubleshooting question into something you remember seeing.

Symptom: "we need it back" (backup and recovery)

Azure Backup with a Recovery Services vault covers VMs, Azure Files and SQL in VMs; know backup policies, soft delete, and file-level versus full VM restore. Azure Site Recovery replicates VMs to another region for disaster recovery. For storage, know blob versioning, soft delete, and the redundancy options (LRS, ZRS, GRS, GZRS) and what each one survives.

Symptom: "we need to know before it breaks" (monitoring)

Azure Monitor metrics and alerts, Log Analytics workspaces and basic KQL, action groups for notifications, VM insights and Network Watcher (connection monitor and virtual network flow logs; NSG flow logs can no longer be created and retire on September 30, 2027). Expect to recognise a simple KQL query rather than write one.

Study order

  1. Identities and governance: Entra users and groups, RBAC scopes, Azure Policy, locks, tags, management groups.
  2. Networking: VNets, subnets, NSGs, peering, Azure DNS and private DNS zones, load balancers.
  3. Compute: VMs, availability sets and zones, scale sets, App Service plans, containers, ARM templates and Bicep.
  4. Storage, then backup and monitoring, then mixed practice sets with the clock running.
