DBX-DEP Study Guide: The Professional Exam Rewards the Smallest Action That Fixes the Problem

At associate level, a Databricks question usually has one working answer and three that do not work. At professional level, often two or three options would work, and the exam wants the one that does the least: reprocesses the least data, grants the least access, rewrites the least code, costs the least compute. Learning to rank working options by how narrow they are is the skill this guide is built around, domain by domain.

Study guide · Databricks Certified Data Engineer Professional (DBX-DEP)

The narrowest recovery

When something fails, the options usually form a ladder from "redo one step" to "redo everything". The professional answer is the lowest rung that restores a correct state.

SituationNarrow fixToo wide
Two tasks of a job failedRepair run: only unsuccessful tasks and their dependants, with current settings and optional parameter overrides.Run the whole job again.
One or two pipeline tables failed after a transient errorRefresh failed tables.Full refresh of the pipeline.
A new source must feed an existing streaming tableAdd an append flow, with a one-time ONCE flow for the backfill.Rewrite the query as a UNION and fully refresh.
Change one setting of a job via the CLIjobs update with the changed fields.jobs reset, which replaces all settings with what you send.

The "too wide" option is not just slower. A full refresh clears streaming tables and their checkpoints and replays what the source still holds. If a Kafka topic keeps seven days and the table holds two years, history is gone. Setting pipelines.reset.allowed to false on such a table blocks full refreshes.

Going deeper: why foreachBatch needs its own idempotency

Structured Streaming writes the planned batch to the checkpoint's offset log before it runs, and to the commit log after it finishes. If the query dies between the two, the restart replays the same batch with the same batchId. A built-in Delta sink handles that for you. Inside foreachBatch you write to arbitrary places, so Spark only promises at-least-once. For Delta writes inside the function, pass txnAppId and txnVersion bound to batchId; Delta then skips a write it has already committed for that pair. Without it, a replayed batch appends its rows twice, and the "duplicates after a restart" stem is about exactly this.

The narrowest permission

Security questions list four grants that would all let the person do the job. Pick the lowest rung that covers every duty in the stem.

  • Someone who must start, cancel and read logs of a job: CAN MANAGE RUN, not CAN MANAGE.
  • A service principal that only refreshes one materialized view: USE CATALOG, USE SCHEMA and REFRESH on that view, not SELECT or MODIFY on the schema.
  • ALL PRIVILEGES does not include MANAGE.
  • Many tables with a pii tag: one ABAC policy on governed tags at the catalog or schema, not a mask on every table. Keep the mask and filter functions small SQL functions, because they run for every row.

Compliance has the same shape. A plain sha2 of a phone number is pseudonymisation, not anonymisation, because a small value space can be hashed in full. A DELETE with deletion vectors only hides rows; physically removing them needs REORG TABLE ... APPLY (PURGE) to rewrite the files, then VACUUM to remove the older files that still hold the data. A change data feed keeps deleted values too, for as long as its table versions are retained.

The narrowest code change

The biggest section, at 23%, is about code. The options often differ by one line, so read for the line that changes behaviour:

  • A Series-to-Series pandas UDF that loads a large model in its body loads it once per batch. The Iterator-of-Series form can load it once and reuse it for every batch in the iterator.
  • A window with ORDER BY and no frame defaults to RANGE up to the current row, so ties share a running total.
  • VARIANT paths are case-sensitive; JSON string paths are not, unless you use brackets. try_parse_json returns NULL where parse_json fails the batch.
  • In a declarative pipeline, pivot() is not supported because it must read the data eagerly to work out its output schema; use conditional aggregation.
  • AUTO CDC (formerly APPLY CHANGES) orders changes by sequence_by; a column added with current_timestamp() records processing time and lets old values win.

Beginner tip: before your first practice set, open a notebook and run SELECT * FROM system.lakeflow.job_run_timeline LIMIT 20 and SELECT * FROM system.billing.usage LIMIT 20 (an admin may need to grant access). Find one long run that spans several rows, and one usage row with a job_id. Monitoring questions assume you know these tables have hourly slices and that the final result_state sits only on the row that ends a run. Seeing it once is faster than memorising it.

The narrowest cost fix

Cost and performance questions reward evidence before action. Find where the time goes, then change only that:

  • Spark UI for a classic cluster stage: skew when the maximum task time is far above the 75th percentile, spill statistics when memory ran out, timeline gaps with a busy driver when non-Spark code is the bottleneck.
  • Query profile for SQL on a warehouse: insights such as DATA_SPILL or EXCESSIVE_QUEUE_TIME say whether to change the query, the layout or the warehouse.
  • System tables for many runs over time. Remember that usage_metadata.job_id is empty when a job runs on all-purpose compute, and that the jobs table keeps a row for every edit, so join to the latest row only.

Layout: Liquid Clustering for new tables (it cannot be combined with partitioning or ZORDER), CLUSTER BY AUTO and predictive optimization for managed tables, deletion vectors for MERGE jobs that touch few rows in many files.

Going deeper: why a materialized view sometimes recomputes everything

A materialized view promises that its content equals the batch query over the current inputs. Incremental refresh is an optimisation on top of that promise, available only on serverless pipelines, and even there it is cost-based: if the engine estimates that a full recompute is cheaper or the query shape cannot be maintained incrementally, it recomputes. The result is the same either way. Summing FLOAT or DOUBLE columns gives order-dependent results, so such a view is planned as a full refresh; casting to a decimal type makes incremental planning possible. The pipeline event log shows why a refresh was full. When a stem asks why a refresh did a full recompute on a classic pipeline, the answer is the compute type, not the query.

A study order

  1. Lakeflow Spark Declarative Pipelines in depth: streaming tables versus materialized views, flows, AUTO CDC, expectations, refresh options.
  2. Structured Streaming: watermarks, output modes, foreachBatch, Kafka and Auto Loader recovery.
  3. Python and SQL: UDF types, window frames, VARIANT, testing with assertDataFrameEqual.
  4. Monitoring and cost: system tables, event log, Jobs API paging, query profile, Spark UI.
  5. Declarative Automation Bundles (formerly Databricks Asset Bundles) and Git folders, permissions and ABAC, then timed mixed sets of 60.
