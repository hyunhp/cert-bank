Terraform Associate (004) 학습 가이드: 구성, 상태, 실제 인프라와 명령어별로 바뀌는 대상

Terraform Associate 문제는 대부분 모습만 다를 뿐 같은 질문입니다. 이 명령어나 블록은 세 가지 중 무엇을 바꾸는가? 세 가지란 직접 작성하는 구성(configuration), Terraform이 보관하는 상태(state), 클라우드에 있는 실제 인프라입니다. 명령어마다 세 가지 중 무엇을 읽고 무엇을 쓰는지 말할 수 있게 되면 시험의 상당 부분을 예측할 수 있습니다. 이 가이드는 이 생각을 중심으로 구성했고, 이어서 004 버전에서 달라진 점과 학습 시간을 나누는 방법을 다룹니다.

학습 가이드 · HashiCorp Certified: Terraform Associate (004) (TF-TA004)

시험 개요

시험 시간은 1시간이며, 온라인 감독 방식으로 영어로 치릅니다. Terraform 1.12를 기준으로 출제하고 HCP Terraform도 포함합니다. 문제 유형은 참/거짓, 객관식, 복수 정답이며, 복수 정답 문제는 몇 개를 골라야 하는지 알려 줍니다. HashiCorp는 문항 수, 합격 점수, 8개 목표(objective)별 비중을 공개하지 않습니다. 최신 정보는 공식 시험 페이지에서 확인하고, 준비는 고르게 나누어 하십시오.

이 문제은행의 TF-TA004 문제 266개 가운데 47개(18%)가 둘 이상의 답을 요구합니다. 가장 큰 비중(40%)은 활용 사례 문제입니다. "팀이 X를 하려고 한다. 어떤 명령어나 블록을 써야 하는가?" 같은 형식입니다. 약 다섯 문제 중 하나는 무언가 잘못된 상황을 다룹니다. 구성 목표의 문제가 가장 많은 이유는 세부 목표가 8개(4a-4h)로 범위가 가장 넓기 때문입니다. 변수, 표현식, lifecycle 규칙, 사용자 지정 조건(custom condition)이 모두 여기에 속합니다.

세 가지를 구분하기

  • 구성은 원하는 모습입니다. 즉 .tf 파일입니다.
  • 상태는 Terraform이 마지막으로 기록한 모습입니다. 어떤 블록이 어떤 실제 객체와 연결되어 있는지, 그리고 속성과 의존 관계를 담습니다.
  • 실제 인프라는 누가 만들고 바꿨든 지금 존재하는 것입니다.

일반적인 plan은 세 가지를 모두 읽습니다. 상태에 있는 실제 객체 정보를 새로 고치고(refresh), 구성과 비교한 다음, 작업을 제안합니다. 상태 항목이 없는 블록은 생성 대상이 됩니다. 블록이 없는 상태 항목은 삭제 대상이 됩니다. 누군가 직접 만들고 import하지 않은 객체는 Terraform에 보이지 않습니다.

일반적인 plan과 apply가 읽고 쓰는 것
1
Refresh
상태가 추적하는 실제 객체를 읽고, 그 객체에 대한 Terraform의 정보를 갱신합니다
2
비교
구성을 그 정보와 비교합니다. import하지 않은 객체는 계속 보이지 않습니다
3
Plan
상태 항목이 없는 블록은 생성, 블록이 없는 상태 항목은 삭제. 아직 아무것도 바뀌지 않습니다.
4
Apply
실제 인프라를 구성에 맞게 바꾸고, 그 결과를 상태에 기록합니다
카드를 따라가며 각 단계가 구성, 상태, 실제 인프라 중 무엇을 읽거나 바꾸는지 확인하십시오.

명령어별로 바뀌는 대상

명령어 또는 블록바뀌는 것
init, validate, fmt상태와 실제 인프라는 바뀌지 않습니다. init은 provider와 모듈을 설치하고 backend를 설정합니다. validate는 API를 호출하지 않고 문법, 타입, 참조를 검사합니다. fmt는 파일 서식만 다시 씁니다.
plan아무것도 바뀌지 않습니다. 미리 보기입니다.
apply (일반)실제 인프라를 구성에 맞게 바꾸고, 이어서 상태를 바꿉니다.
apply -refresh-only상태만 실제에 맞게 바꿉니다. 객체를 생성, 변경, 삭제하지 않습니다.
apply -replace=ADDR구성이 바뀌지 않았어도 실제 객체 하나를 다시 만듭니다.
import 블록plan에서 검토하고 apply한 뒤 상태가 바뀝니다. 실제 객체는 그대로입니다.
terraform import 명령어검토할 plan 없이 상태가 즉시 바뀝니다.
moved 블록 / state mv객체를 추적하는 주소가 바뀝니다. 블록은 검토를 거치고 공유 코드와 함께 전달됩니다. 명령어는 상태 하나를 한 번 수정합니다.
destroy = false를 둔 removed 블록 / state rm상태가 객체를 잊고, 객체는 계속 실행됩니다. destroy = false가 없으면 removed 블록은 객체를 삭제합니다.
destroy상태가 추적하는 모든 실제 객체가 삭제되고, 그 항목도 상태에서 빠집니다.
force-unlock잠금(lock)만 바뀝니다. 리소스도 상태 내용도 바뀌지 않습니다.

오답 선택지 상당수는 이 표에서 걸러집니다. "terraform validate로 AMI가 존재하는지 확인한다"는 틀렸습니다. validate는 provider를 호출하지 않기 때문입니다. "state rm을 실행하고 블록은 그대로 둔다"도 틀렸습니다. 다음 plan이 객체를 하나 더 만들기 때문입니다.

더 깊이: Terraform이 구성만으로 동작할 수 없는 이유

상태에는 코드가 제공할 수 없는 세 가지가 들어 있습니다. 첫째, aws_instance.web 같은 주소와 실제 객체 ID의 연결입니다. 이 연결이 없으면 빈 상태로 plan을 실행할 때 객체가 이미 있어도 전부 다시 만들자고 제안합니다. 둘째, 의존 관계 정보입니다. 한 번의 변경에서 서브넷 블록과 그 서브넷을 쓰던 인스턴스 블록을 함께 지우면, 코드에는 무엇을 먼저 지워야 하는지 나와 있지 않습니다. 하지만 상태에는 인스턴스가 서브넷에 의존한다는 기록이 남아 있으므로 삭제 순서가 올바르게 정해집니다. 셋째, 속성 캐시입니다. 이 덕분에 아주 큰 구성도 모든 객체를 조회하지 않고 plan할 수 있습니다(-refresh=false가 이 캐시를 쓰며, 대신 외부 변경을 놓칩니다). 그래서 상태를 잃으면 대가가 큽니다. 모든 객체를 다시 import해야 합니다.

세 가지가 어긋날 때: 드리프트(drift)

누군가 콘솔에서 인스턴스 크기를 바꿨다고 가정해 봅시다. 다음 일반 plan은 refresh를 거쳐 차이를 발견하고, 인스턴스를 원래대로 되돌리자고 제안합니다. 이제 어느 쪽이 맞는지 결정해야 합니다.

  • 콘솔 변경이 실수였다면 일반 apply를 실행합니다. 구성이 이깁니다.
  • 콘솔 변경을 유지해야 한다면 구성을 그에 맞게 고칩니다. 먼저 상태에만 기록하고 싶다면 apply -refresh-only를 씁니다. 다만 이것만으로는 다음 일반 plan이 변경을 되돌리는 것을 막지 못합니다.
  • 콘솔에서 객체를 삭제했다면 plan이 객체를 다시 만들자고 제안합니다.

예전 terraform refresh 명령어는 검토 없이 refresh-only 갱신을 수행했습니다. 그래서 지원 중단(deprecated)되었습니다.

초보자 팁: 드리프트를 보려고 클라우드 계정이 있을 필요는 없습니다. 텍스트 파일을 만드는 local_file 리소스(hashicorp/local provider) 하나를 작성해 apply한 뒤, 파일을 직접 수정하고 terraform plan을 실행해 보십시오. 이어서 plan -refresh-only, apply -replace, 리소스 이름을 바꾼 뒤의 moved 블록, state rm 뒤의 plan을 차례로 해 보십시오. 10분만 투자하면 위 표의 대부분을 외우지 않고도 채울 수 있습니다.

004에서 새로 다루는 내용

예전 학습 자료가 다루지 않는 네 가지 주제는 특히 신경 써야 합니다.

  1. depends_on과 create_before_destroy가 구성 목표에 명시되어 있습니다. 앞의 것은 Terraform이 참조로는 알 수 없는 순서를 추가합니다. 뒤의 것은 기존 객체를 지우기 전에 대체 객체를 먼저 만듭니다.
  2. 사용자 지정 조건: precondition은 리소스를 처리하기 전에 입력을 검사하고, postcondition은 처리한 뒤 결과를 검사합니다. check 블록은 실행을 멈추지 않고 문제를 경고로 알립니다.
  3. Ephemeral 값과 write-only 인수: 비밀 값이 상태와 plan 파일에 남지 않게 합니다.
  4. HCP Terraform 워크스페이스와 프로젝트, 그리고 HCP 워크스페이스가 CLI 워크스페이스와 어떻게 다른지(Terraform 상태와 워크스페이스 비교 글에서 자세히 다룹니다).

예전 습관을 대신하는 현재 방식도 알아 두십시오. terraform refresh 대신 apply -refresh-only, taint 대신 apply -replace, S3 backend 잠금에 DynamoDB 테이블 대신 use_lockfile = true, import 명령어보다 import 블록입니다. 문서는 refresh, taint, DynamoDB 잠금을 지원 중단(deprecated)으로 표시하므로, 두 선택지가 모두 동작한다면 현재 문서가 권장하는 쪽을 고르십시오.

더 깊이: sensitive는 숨기고, ephemeral은 남기지 않는다

변수나 출력에 sensitive = true를 지정하면 Terraform이 값을 보여 주는 방식만 바뀝니다. plan과 apply 출력에서 값이 가려집니다. 그러나 값은 여전히 상태와 저장된 plan 파일에 평문으로 기록되므로, 그 파일을 읽을 수 있는 사람은 비밀 값도 읽을 수 있습니다. Ephemeral 변수와 ephemeral 리소스는 성격이 다릅니다. 현재 작업 동안에만 존재하고 상태나 plan에 기록되지 않습니다. Write-only 인수(예: aws_db_instance의 password_wo)는 작업할 때마다 provider에 전달된 뒤 버려지며, 상태나 plan에 저장되지 않습니다. 비밀번호를 상태에 남기지 않는 방법을 묻는 문제에서 "sensitive로 지정한다"는 전형적인 오답입니다.

HCP Terraform 한 번에 정리

목표 8은 호스팅 서비스를 다룹니다. 다음 사실을 알아 두십시오.

  • 워크스페이스는 자체 상태 버전, 변수, 자격 증명, 실행 기록, 권한을 가집니다. 프로젝트는 워크스페이스를 묶어 접근 권한을 한꺼번에 부여할 수 있게 합니다.
  • 워크플로는 세 가지입니다. CLI 기반(cloud 블록과 terraform login), VCS 기반(pull request에 대해 apply할 수 없는 speculative plan이 실행됨), API 기반입니다.
  • 실행 모드는 remote, agent, local 중 하나입니다. local 모드에서는 워크스페이스 변수와 정책 검사를 쓰지 않습니다.
  • 정적 provider 자격 증명은 보통 환경 변수로 넣고(동적 자격 증명을 쓰면 저장하지 않아도 됩니다), Terraform 변수는 var. 입력에 값을 넣습니다. 변수 세트(variable set)는 여러 워크스페이스에서 값을 공유합니다.
  • Run trigger는 상위 워크스페이스의 apply 뒤에 하위 워크스페이스의 실행을 대기열에 넣습니다. 정책 세트(Sentinel 또는 OPA)는 plan을 검사합니다. Health assessment는 드리프트와 실패한 사용자 지정 조건을 알려 줄 뿐, 인프라를 바꾸지 않습니다.

학습 순서

  1. IaC 개념과 핵심 워크플로: init, validate, plan, apply, destroy, fmt와 주요 플래그.
  2. provider, lock 파일, 버전 제약. 이어서 상태, backend, 잠금.
  3. 구성: 변수와 우선순위, count와 for_each의 차이, 표현식, lifecycle, 사용자 지정 조건, 비밀 값.
  4. 모듈, 이어서 import와 state 명령어, 그다음 HCP Terraform.
  5. 1시간 제한을 두고 여러 주제를 섞은 연습 세트 풀기.
