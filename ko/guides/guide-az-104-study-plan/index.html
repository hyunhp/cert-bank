AZ-104 학습 가이드: Azure Administrator는 문제 해결 시험이므로 증상별로 공부하십시오

AZ-104(Microsoft Azure Administrator)는 보통 다섯 개의 평가 영역으로 소개됩니다. Microsoft가 그렇게 정리하기 때문이지만, 실제 문제는 그런 느낌이 아닙니다. 저희가 이 사이트를 위해 만든 AZ-104 문제 250개 중 절반은 무언가가 동작하지 않는 상황으로 시작합니다. 아무도 접속할 수 없는 VM, Blob을 읽지 못하는 사용자, 실패한 배포 같은 것입니다. 그래서 이 가이드는 증상별로 구성했습니다. 무엇이 보이는지, 어디를 확인해야 하는지, 보통 무엇으로 해결되는지를 정리합니다.

학습 가이드 · Microsoft Azure Administrator (AZ-104)

시험 개요

시험 시간은 100분이며, Microsoft는 문항 수를 공개하지 않습니다. 합격 점수는 1–1,000점 척도에서 700점입니다. 객관식 외에 사례 연구 같은 대화형 문항도 나옵니다. 평가 영역은 Manage Azure identities and governance(Azure ID 및 거버넌스 관리, 20–25%), Implement and manage storage(스토리지 구현 및 관리, 15–20%), Deploy and manage Azure compute resources(Azure 컴퓨팅 리소스 배포 및 관리, 20–25%), Implement and manage virtual networking(가상 네트워킹 구현 및 관리, 15–20%), Monitor and maintain Azure resources(Azure 리소스 모니터링 및 유지 관리, 10–15%)입니다. AZ-104 같은 어소시에이트 시험에서는 시험 중에 Microsoft Learn을 열어 볼 수 있습니다. 세부 사항 하나를 찾아보라는 기능이지 모든 문제에 쓰라는 것이 아니고, 그동안에도 시험 시간은 흐르므로 검색할 시간이 있으리라고 기대하지는 마십시오.

증상: "아무도 VM에 접속할 수 없다"

  • 네트워크 인터페이스의 유효 보안 규칙(effective security rules)을 확인하십시오. VM은 NIC에 NSG 하나, 서브넷에 또 다른 NSG를 둘 수 있습니다. 인바운드 트래픽은 서브넷 NSG를 먼저 통과한 뒤 NIC NSG를 통과해야 하며, 둘 다 허용해야 합니다.
  • Network Watcher의 IP 흐름 확인(IP flow verify)으로 특정 패킷 하나를 테스트하십시오. 패킷을 허용하거나 거부한 규칙의 이름을 알려 줍니다.
  • 규칙 순서를 기억하십시오. 우선순위 숫자가 낮은 규칙이 이기며, 기본 규칙(65500의 DenyAllInBound 포함)은 맨 아래에 있습니다.
  • 공용 IP도 Bastion도 없나요? 그렇다면 VM에는 네트워크 내부에서 피어링, VPN, ExpressRoute를 통해서만 접근할 수 있습니다.
더 깊이: 서브넷의 거부를 NIC에서 고칠 수 없는 이유

인바운드 트래픽의 경우 Azure는 서브넷의 NSG를 먼저 평가합니다. 거기서 규칙이 패킷을 거부하면 NIC의 NSG를 확인하기도 전에 패킷이 버려지므로, NIC에 허용 규칙을 추가해도 아무것도 바뀌지 않습니다. 아웃바운드 트래픽은 순서가 반대로, NIC가 먼저이고 서브넷이 다음입니다. 규칙은 상태 저장(stateful) 방식이기도 합니다. 인바운드 연결이 한 번 허용되면 응답 트래픽은 자동으로 허용되므로, 응답을 위한 아웃바운드 규칙은 거의 필요 없습니다. NSG 두 개를 보여 주고 트래픽이 왜 여전히 실패하는지 묻는 문제는 바로 이 순서를 확인하는 문제입니다.

인바운드 패킷이 NSG 두 개를 지나 VM에 도달하는 경로
1
서브넷 NSG
인바운드 트래픽은 여기서 먼저 확인합니다. 우선순위 숫자가 낮은 규칙이 이기며, 거부되면 패킷은 여기서 버려집니다.
2
NIC NSG
여기서도 패킷을 허용해야 합니다. 여기의 허용 규칙으로 서브넷의 거부를 되돌릴 수 없습니다.
3
VM
규칙이 상태 저장 방식이라 응답은 자동으로 허용됩니다. 아웃바운드는 NIC가 먼저, 서브넷이 다음입니다.
4
그래도 막힌다면?
Network Watcher IP 흐름 확인을 실행하십시오. 패킷을 허용하거나 거부한 규칙을 알려 줍니다.
인바운드 패킷을 카드 순서대로 따라가십시오. 두 NSG가 모두 허용해야 하며, 서브넷 NSG가 먼저 판단합니다.

증상: "VNet은 피어링되어 있는데 트래픽이 통과하지 않는다"

피어링은 전이되지 않습니다. A가 B와, B가 C와 피어링되어 있어도 A는 B를 거쳐 C에 도달할 수 없습니다. A와 C를 직접 피어링하거나, 허브에 둔 네트워크 가상 어플라이언스(NVA)나 Azure Virtual WAN을 통해 라우팅해야 합니다. 스포크가 허브의 VPN 게이트웨이를 쓰게 하려면 허브 쪽에서 게이트웨이 전송(gateway transit)을, 스포크 쪽에서 원격 게이트웨이 사용(use remote gateways)을 활성화하십시오. 주소 공간이 겹치는 VNet은 아예 피어링할 수 없습니다.

증상: "사용자에게 Contributor 역할이 있는데 Blob을 읽지 못한다"

Azure는 컨트롤 플레인(control plane)(리소스 관리)과 데이터 플레인(data plane)(리소스 안의 데이터)을 구분합니다. Owner와 Contributor는 스토리지 계정을 관리합니다. Microsoft Entra 인증으로 Blob을 읽거나 쓰려면 Storage Blob Data Reader나 Storage Blob Data Contributor 같은 데이터 역할이 필요합니다. 그 밖에 확인해야 할 원인은 스토리지 계정 방화벽이 사용자의 네트워크를 허용하지 않는 경우, SAS가 만료되었거나 필요한 권한이 없는 경우, 저장된 액세스 정책(stored access policy)이 변경된 경우입니다.

더 깊이: 계정 키라는 허점

Contributor는 Entra 인증으로 데이터를 읽을 수 없지만, 스토리지 계정의 액세스 키를 조회할 수는 있습니다. 그리고 계정 키 하나면 계정 안의 모든 데이터에 접근할 수 있습니다. 그래서 실제로는 "Contributor도 데이터에 접근할 수 있다"가 사실이고, 보안을 강화한 환경에서는 스토리지 계정의 공유 키 인증(shared key authorisation)을 비활성화해 Entra 역할(과 사용자 위임 SAS)만 동작하게 합니다. 액세스가 RBAC로만 통제되도록 하는 방법을 묻는 문제라면, 사람들이 잊는 단계가 바로 공유 키 액세스 비활성화입니다.

증상: "배포가 실패했다" 또는 "변경이 허용되지 않는다"

  • 거부(deny) 효과가 있는 Azure Policy는 규칙을 어기는 리소스(잘못된 지역, 누락된 태그)를 막습니다. 오류 메시지에 정책 할당 이름이 나옵니다.
  • 리소스 잠금은 해제되기 전까지 소유자(Owner)에게도 삭제(CanNotDelete) 또는 모든 변경(ReadOnly)을 막습니다.
  • 할당량(quota)(예: 지역별 VM 제품군당 vCPU 수) 때문에 특정 VM 크기를 쓸 수 없다면 할당량 증가를 요청하십시오.
  • 리소스를 다른 리소스 그룹이나 구독으로 옮길 때, 해당 리소스 유형이 이동을 지원하지 않거나 종속 리소스가 남아 있으면 실패합니다.

초보자 팁: 모든 장애를 한 번씩 일부러 만들어 보십시오. 무료 또는 종량제(pay-as-you-go) 구독에서 리소스 그룹에 CanNotDelete 잠금을 걸고 그 안의 리소스를 삭제해 보십시오. 거부 NSG 규칙을 추가하고 IP 흐름 확인을 실행해 보십시오. 테스트 사용자에게 Contributor를 주고, "Microsoft Entra 사용자 계정"을 선택한 상태로 포털에서 Blob을 열어 보십시오. 각각 몇 분이면 되고, 끝난 뒤 리소스를 삭제하면 비용도 거의 들지 않습니다. 그러면 문제 해결 문제가 직접 본 기억이 있는 장면이 됩니다.

증상: "되살려야 한다"(백업과 복구)

Recovery Services 자격 증명 모음(vault)을 사용하는 Azure Backup은 VM, Azure Files, VM 내 SQL을 다룹니다. 백업 정책, 일시 삭제(soft delete), 파일 수준 복원과 전체 VM 복원의 차이를 알아 두십시오. Azure Site Recovery는 재해 복구를 위해 VM을 다른 지역으로 복제합니다. 스토리지에서는 Blob 버전 관리, 일시 삭제, 중복 옵션(LRS, ZRS, GRS, GZRS)과 각 옵션이 어떤 장애를 견디는지 알아 두십시오.

증상: "고장 나기 전에 알아야 한다"(모니터링)

Azure Monitor 메트릭과 경고, Log Analytics 작업 영역과 기본 KQL, 알림을 위한 작업 그룹(action group), VM insights, Network Watcher(연결 모니터와 가상 네트워크 흐름 로그. NSG 흐름 로그는 더 이상 새로 만들 수 없고 2027년 9월 30일에 종료됩니다)를 공부합니다. KQL은 직접 작성하기보다 간단한 쿼리를 알아보는 수준을 기대하십시오.

학습 순서

  1. ID와 거버넌스: Entra 사용자와 그룹, RBAC 범위, Azure Policy, 잠금, 태그, 관리 그룹.
  2. 네트워킹: VNet, 서브넷, NSG, 피어링, Azure DNS와 프라이빗 DNS 영역, 부하 분산 장치.
  3. 컴퓨팅: VM, 가용성 집합과 가용성 영역, 확장 집합(scale set), App Service 플랜, 컨테이너, ARM 템플릿과 Bicep.
  4. 스토리지, 그다음 백업과 모니터링, 마지막으로 시간을 재며 혼합 연습 세트.
