SAA-C03에서 자주 틀리는 문제 유형 8가지와 유형별 해결 규칙

AWS Solutions Architect – Associate 시험의 오답 대부분은 지식이 부족해서 생기지 않습니다. 두 보기가 똑같이 좋아 보이고 지문의 작은 단서 하나가 정답을 가르는 몇 가지 유형에서 생깁니다. 저희는 이 사이트를 위해 만든 SAA-C03 문제 395개를 살펴보고, 이런 함정을 중심으로 만든 문제를 유형별로 묶었습니다. 가장 자주 나오는 여덟 가지 유형과, 각 유형을 해결하는 규칙을 소개합니다.

자주 틀리는 유형 · AWS Solutions Architect – Associate (SAA-C03)

1. 읽기 부하 문제에 Multi-AZ를 고르는 경우(또는 장애 조치 문제에 읽기 복제본을 고르는 경우)

출제 형태: "운영 데이터베이스에서 리포트를 실행해 애플리케이션이 느려진다"는 지문 옆에 Multi-AZ를 활성화하는 보기가 있습니다. 또는 "데이터베이스는 데이터 손실 없이 가용 영역(Availability Zone) 하나의 손실을 견뎌야 한다"는 지문 옆에 다른 AZ에 읽기 복제본(read replica)을 추가하는 보기가 있습니다.

규칙: Multi-AZ는 가용성을 위한 것입니다. 전통적인 Multi-AZ 대기 인스턴스(standby)는 장애 시 역할을 넘겨받을 뿐 읽기 요청을 처리하지 않습니다. 읽기 복제본은 읽기 확장을 위한 것이며, 복제가 비동기이므로 복제본을 승격하면 마지막 쓰기가 유실될 수 있습니다. 읽기 부하 → 복제본. 데이터 손실 없는 AZ 장애 대응 → Multi-AZ. 저희 문제은행에도 이 구분에 달린 문제가 적지 않습니다.

2. 보안 그룹과 네트워크 ACL을 같은 종류의 필터로 보는 경우

출제 형태: 트래픽은 들어오는데 응답이 돌아오지 않습니다. 또는 보안 그룹으로 IP 주소 하나를 차단하려는 보기가 있습니다.

규칙: 보안 그룹은 상태 저장(stateful) 방식이며 허용 규칙만 있습니다. 응답 트래픽은 자동으로 허용됩니다. 네트워크 ACL은 상태 비저장(stateless) 방식이며 허용과 거부 규칙이 모두 있고, 임시 포트(ephemeral port)로 돌아오는 응답 트래픽에 명시적인 규칙이 필요합니다. "이 주소를 차단하라" → 네트워크 ACL(HTTP라면 AWS WAF). "응답이 버려진다" → 네트워크 ACL에 아웃바운드 규칙이 빠져 있는지 확인하십시오.

3. 여러 인스턴스가 파일을 공유해야 하는데 EBS를 고르는 경우

출제 형태: 여러 AZ에 걸친 Linux 인스턴스 Auto Scaling 그룹이 같은 업로드 파일을 써야 하는데, 한 보기가 EBS 볼륨을 연결합니다.

규칙: EBS 볼륨은 한 AZ에 존재하며 보통 인스턴스 하나에 연결됩니다(Multi-Attach는 한 AZ 안의 특정 볼륨 유형으로 제한되며 클러스터 인식 파일 시스템이 필요합니다). 여러 인스턴스와 AZ가 공유하는 POSIX 파일 → Amazon EFS. Windows 파일 공유 → FSx for Windows File Server. HTTP로 접근하는 객체 → S3.

4. 서비스 제어 정책(SCP)이 권한을 부여한다고 기대하는 경우

출제 형태: 멤버 계정의 액세스 거부(access-denied) 오류를 해결하려고 "S3 액세스를 허용하는 SCP를 연결하는" 보기가 있습니다.

규칙: SCP는 조직 내 계정의 최대 권한을 정할 뿐입니다. 아무것도 부여하지 않으며, 작업을 허용하는 IAM 정책(또는 리소스 정책)이 여전히 필요합니다. 지문에 "어떤 계정도 …하지 못하게 하라"고 나오면 SCP가 정답입니다. "사용자가 …할 수 없다"고 나오면 먼저 IAM을 보십시오. 또한 SCP는 관리 계정에는 적용되지 않습니다.

더 깊이: AWS가 정책을 결합하는 방식과 SCP가 권한을 빼기만 할 수 있는 이유

멤버 계정에서 요청이 오면 AWS는 여러 유형의 정책을 확인하며, 요청은 그 모두를 통과해야 합니다. 어디서든 명시적 거부가 있으면 평가는 그 자리에서 끝납니다. 그렇지 않으면 적용되는 모든 경계(SCP, 권한 경계(permissions boundary), 세션 정책)가 작업을 허용해야 하고, 자격 증명 기반 정책이나 리소스 기반 정책도 그 작업을 허용해야 합니다. 실제 권한은 경계와 부여된 권한의 교집합입니다.

SCP는 이 경계 중 하나입니다. 걸러낼 뿐 더하지 않습니다. 그래서 "허용하는 SCP를 연결한다"로는 액세스 거부 오류가 절대 해결되지 않습니다. 위임된 관리(delegated administration) 문제에서 자주 나오는 IAM 역할의 권한 경계도 같은 논리로 설명됩니다.

AWS가 멤버 계정의 요청을 평가하는 방식
명시적 거부
어느 정책에든 거부가 있으면 평가 종료
경계
SCP · 권한 경계 · 세션 정책 · 적용되는 모든 경계가 허용해야 함
권한 부여
자격 증명 기반 또는 리소스 기반 정책 · 이 정책도 작업을 허용해야 함
실제 권한
경계와 부여된 권한의 교집합
요청은 위에서 아래로 모든 단계를 통과해야 합니다. SCP는 부여된 권한을 걸러낼 뿐, 더하지 않습니다.

5. KMS 권한을 IAM에서만 확인하는 경우

출제 형태: 다른 계정의 역할에 kms:Decrypt를 허용하는 IAM 정책이 있는데도 복호화가 계속 실패합니다.

규칙: 고객 관리형 KMS 키에는 자체 키 정책이 있습니다. 교차 계정으로 사용하려면 키가 있는 계정의 키 정책과 호출하는 계정의 IAM 정책이 모두 작업을 허용해야 합니다. AWS 관리형 키는 계정 간에 아예 공유할 수 없습니다. 그래서 "고객 관리형 키를 사용한다"가 정답의 앞부분인 경우가 많습니다.

6. CloudFront와 Global Accelerator를 트래픽 유형이 아니라 이름으로 고르는 경우

출제 형태: UDP를 쓰는 글로벌 멀티플레이어 게임이나 고정 IP 주소가 필요한 애플리케이션이 나오고, 보기에 CloudFront가 섞여 있습니다.

규칙: CloudFront는 HTTP(S)용 콘텐츠 전송 네트워크(CDN)이며 엣지에서 콘텐츠를 캐시합니다. Global Accelerator는 TCP와 UDP 트래픽을 AWS 네트워크를 통해 가장 가까운 정상 엔드포인트로 보내고, 고정 애니캐스트(anycast) IP 주소 두 개를 제공합니다. 캐시는 하지 않습니다. 캐시 가능한 웹 콘텐츠 → CloudFront. HTTP가 아닌 트래픽, 고정 IP, 빠른 리전 간 장애 조치 → Global Accelerator.

7. 중단되면 안 되는 작업에 스팟 인스턴스를 고르는 경우

출제 형태: "가장 비용 효율적인(most cost-effective)"이라는 조건 옆에 상태 저장 데이터베이스나, 재시작 없이 마감 전에 끝나야 하는 작업 같은 워크로드가 나옵니다.

규칙: 스팟 용량은 2분 전 경고와 함께 회수될 수 있습니다. 작업이 장애를 견딜 수 있을 때만 가장 저렴한 답이 됩니다. 체크포인트를 남기는 배치 작업, 로드 밸런서 뒤의 상태 비저장 웹 계층, CI 러너가 그렇습니다. 꾸준히 상시 실행되는 워크로드 → Savings Plans 또는 예약 인스턴스. 섞여 있다면 → 온디맨드나 예약 용량을 기반으로 두고 그 위에 스팟을 더하는 Auto Scaling.

8. 순서나 정확히 한 번 처리가 중요한데 표준 SQS 대기열을 고르는 경우

출제 형태: 같은 고객의 주문을 순서대로 처리해야 하거나 결제가 두 번 청구되면 안 되는데, 보기는 표준 대기열에 소비자를 더 붙이는 방법을 제시합니다.

규칙: 표준 대기열은 최소 한 번 전달(at-least-once)과 최선의 순서(best-effort ordering)를 제공합니다. FIFO 대기열은 메시지 그룹 안에서 순서를 지키고 5분 구간 안의 중복을 제거하는 대신, 최대 처리량이 더 낮습니다. "순서대로" 또는 "정확히 한 번" → 고객이나 주문마다 메시지 그룹 ID를 둔 FIFO. "최대한 빠르게, 순서는 상관없음" → 표준.

초보자 팁: 세 칸짜리 오답 노트를 만드십시오. 이 목록의 유형 번호(또는 "새 유형"), 내가 고른 보기, 지문에서 놓친 단어를 적습니다. 오답이 스무 개에서 서른 개쯤 쌓이면 나에게 해당하는 유형 두세 개가 보이고, 전부가 아니라 그 유형만 복습하면 됩니다.
