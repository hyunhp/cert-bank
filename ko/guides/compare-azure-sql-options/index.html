Azure SQL Database, SQL Managed Instance, Azure VM의 SQL Server 비교: 정답을 가르는 기능 단서

Azure에서 SQL Server 워크로드를 실행하는 방법은 세 가지입니다. Azure SQL Database, Azure SQL Managed Instance, 그리고 Azure Virtual Machines의 SQL Server입니다. 셋 다 같은 엔진 계열이라, 시험 보기에 모두 나오면 하나같이 그럴듯해 보입니다. 차이는 하나뿐입니다. SQL Server를 내가 얼마나 직접 관리하느냐입니다. 그리고 문제 지문은 거의 언제나 이를 결정짓는 기능 하나를 언급합니다. 이 글에서는 그 사다리 구조와 단계별 단서, 그리고 정답이 아예 SQL이 아닌 경우를 살펴봅니다.

개념 비교 · AZ-305, DP-900 및 기타 Azure 시험

질문은 하나: 워크로드가 무엇을 직접 제어해야 하는가?

세 칸짜리 사다리를 떠올려 보세요. 맨 위 칸은 Azure SQL Database로, 데이터베이스 단위의 PaaS(platform as a service)입니다. 엔진, 패치, 백업, 고가용성은 Microsoft가 맡고, 사용자는 데이터베이스만 관리합니다. 가운데 칸은 Azure SQL Managed Instance로, 인스턴스 단위의 PaaS입니다. 플랫폼은 여전히 Microsoft가 운영하지만, 사용자는 SQL Server 인스턴스 전체를 받으며 호환성도 거의 완벽합니다. 맨 아래 칸은 Azure VM의 SQL Server로, IaaS(infrastructure as a service)입니다. Windows나 Linux VM에 SQL Server를 설치하는 방식이라 엔진과 운영체제를 모두 직접 제어합니다. 한 칸 내려갈 때마다 제어권도, 할 일도 늘어납니다. 시험은 모든 요구사항을 만족하는 칸 중 가장 높은 칸을 정답으로 봅니다.

이 문제은행에서는 Azure 문제 32개가 지문이나 보기에 Azure SQL Managed Instance 또는 Azure VM의 SQL Server를 언급합니다(DP-900 18개, AZ-305 10개, AZ-104와 AZ-900 각 2개). 그리고 이 중 옵션끼리 고르게 하는 문제는 일반론으로 묻지 않고 거의 언제나 특정 기능을 콕 집어 언급합니다.

기능 단서

  • SQL Database에 머무르세요. 지문이 새 클라우드 앱, 가끔씩만 쓰는 데이터베이스 하나(서버리스), 피크 시간대가 서로 다른 여러 데이터베이스(탄력적 풀), 약 100 TB까지 커지면서 빠른 스냅샷 백업이 필요한 단일 데이터베이스(Hyperscale)를 설명할 때입니다. 이 가운데 어느 것도 Managed Instance에는 없습니다.
  • Managed Instance로 내려가세요. 지문에 SQL Server Agent 작업, 세 부분 이름(three-part name)을 쓰는 데이터베이스 간 쿼리, CLR 어셈블리, Database Mail, Service Broker, 연결된 서버(linked server), MS DTC가 나오면서 "패치할 운영체제 없음"이나 "PaaS 서비스"라는 조건도 함께 붙을 때입니다.
  • VM으로 내려가세요. 서버 자체만 제공할 수 있는 무언가가 필요할 때입니다. FILESTREAM 파일 그룹, 데이터베이스 서버 운영체제에 설치하는 벤더 에이전트, 같은 서버에 올리는 다른 소프트웨어, 특정 구버전 SQL Server, 업데이트 설치 시점 제어가 여기에 해당합니다.

초보자 팁: 지문에 나온 기능마다 소리 내어 한 가지만 물어보세요. "이건 데이터베이스에 있나, 인스턴스에 있나, 서버 운영체제에 있나?" 그리고 옆에 D, I, S 중 하나를 적습니다. 가장 아래 단계의 글자가 서비스를 결정합니다. D만 있으면 SQL Database, I가 하나라도 있으면 Managed Instance, S가 하나라도 있으면 VM입니다. 문제 세트를 풀기 전에 위 목록으로 먼저 연습해 보세요. 그러면 정답이 두 개인 문제("VM만 충족할 수 있는 요구사항 두 가지는?")도 금방 풀립니다.

누가 계속 돌아가게 하는가

두 PaaS 옵션에서는 데이터베이스 고가용성이 서비스에 포함되어 있습니다. VM은 그렇지 않으며, 여기서 단골 트러블슈팅 문제가 나옵니다.

더 깊이: VM은 살아 있는데 데이터베이스가 죽었다

IaaS에서 Microsoft의 SLA는 가상 머신을 보장할 뿐, 그 위에서 도는 SQL Server 프로세스는 보장하지 않습니다. VM은 계속 실행 중인데 SQL Server 서비스가 멈추면, 플랫폼은 VM이 정상이라고 보고 아무것도 하지 않습니다. 따라서 데이터베이스 가용성은 고객이 설계해야 합니다. 가용성 집합이나 여러 가용성 영역에 VM을 두 대 이상 배치하고, SQL Server 자체의 고가용성 기능을 쓰는 방식입니다. 영역 장애에서 데이터 손실 없이 자동으로 장애 조치하려면, 서로 다른 영역에 동기 커밋 복제본을 둔 Always On 가용성 그룹이 정답입니다. 다른 영역으로의 Azure Site Recovery는 RPO가 0이 아닌 재해 복구 도구이므로 대안이 되지 못합니다. SQL IaaS Agent 확장은 백업과 패치를 도와주지만, 데이터베이스를 고가용성으로 만들어 주지는 않습니다.

PaaS 쪽에서는 Managed Instance를 영역 중복으로 구성하고, 다른 리전의 보조 인스턴스와 함께 장애 조치 그룹(failover group)에 넣을 수 있습니다. 장애 조치 그룹의 리스너 덕분에 리전 장애 조치 후에도 애플리케이션의 연결 문자열을 바꿀 필요가 없습니다.

마이그레이션하기

마이그레이션 전에 데이터베이스가 어떤 기능을 쓰는지 파악하세요. Azure Migrate(또는 SQL Server enabled by Azure Arc)의 Azure SQL 평가가 SQL Database나 Managed Instance에서 지원되지 않는 항목을 알려 줍니다. 다운타임을 몇 분으로 줄여 Managed Instance로 옮기는 경우, 이 문제은행의 문제는 온라인 모드의 Azure Database Migration Service나 연속 모드의 Log Replay Service를 정답으로 봅니다. 전환하기 전 몇 달 동안 Azure에 읽기 가능한 사본을 두고 싶다면, Managed Instance link가 분산 가용성 그룹을 통해 복제합니다. 앱을 멈춘 뒤 BACPAC으로 내보내는 방법도 되긴 하지만, 다운타임을 최소화하는 방법은 아닙니다.

더 깊이: "예전 동작이 필요하다"와 "예전 버전이 필요하다"는 다르다

Azure SQL Database는 evergreen입니다. Azure가 엔진을 알아서 업데이트하므로 지원 종료에 따른 업그레이드 프로젝트가 없고, 대신 예전 엔진을 고를 수도 없습니다. 애플리케이션이 이전 릴리스의 동작에 의존한다면 데이터베이스 호환성 수준(compatibility level)을 설정합니다. 그러면 현재 엔진에서도 쿼리 처리가 해당 릴리스처럼 동작합니다. 특정 SQL Server 버전을 설치해 계속 쓸 수 있는 곳은 VM뿐이며, 그 대가로 업그레이드 계획을 직접 세워야 합니다. 따라서 "업그레이드 작업 없이 최신 기능"을 요구하는 지문은 사다리 위쪽을, "정확히 SQL Server 2019, 업데이트는 우리 일정대로"를 요구하는 지문은 아래쪽을 가리킵니다.

정답이 아예 SQL Server가 아닐 때

같은 주제의 문제 중 일부는 Azure Cosmos DB가 정답입니다. 단서는 데이터의 형태와 사용자가 있는 위치입니다. 네 대륙의 쇼핑객, 구조가 자주 바뀌는 JSON, 가까운 리전에서의 빠른 읽기와 쓰기가 나오면, 한 리전에 있는 단일 Azure SQL 데이터베이스가 아니라 여러 리전과 다중 리전 쓰기를 쓰는 Cosmos DB가 정답입니다. 기존 Cassandra 애플리케이션이 드라이버를 그대로 써야 한다면 Azure Cosmos DB for Apache Cassandra입니다. Table storage 데이터에 이제 전역 복제와 모든 속성에 대한 인덱스가 필요하다면 Azure Cosmos DB for Table입니다. 반대로 조인과 트랜잭션이 있는 고정된 관계형 스키마라면 Azure SQL에 남습니다. 그리고 Azure Cosmos DB for PostgreSQL은 사용 중지(retirement) 수순에 있으므로, 새로운 분산 관계형 앱의 정답이 아닙니다.
