SAA-C03 학습 가이드: 출제 범위, 도메인별 비중, 효과적인 학습 순서

AWS Certified Solutions Architect – Associate(SAA-C03) 시험은 서비스 이름을 외우는 시험이 아닙니다. 시나리오가 제약 조건을 두세 개씩 한꺼번에 제시할 때 알맞은 설계를 고르는 능력을 봅니다. 이 가이드에서는 출제 범위, 네 도메인의 비중, 권장 학습 순서, 그리고 가장 많은 점수를 잃게 만드는 함정을 정리합니다.

학습 가이드 · AWS Solutions Architect – Associate (SAA-C03)

시험 한눈에 보기

문항 수65문항(채점 50문항, 표시 없이 섞여 있는 비채점 15문항)

문항당 2분이면 넉넉해 보입니다. 하지만 요구 사항 표가 붙은 6~7줄짜리 지문을 만나면 생각이 달라집니다. 짧은 정의 문제는 1분 안에 풀고, 아낀 시간을 긴 시나리오 문제에 쓰도록 계획하십시오.

네 개 도메인과 각 도메인이 실제로 묻는 것

도메인비중실제로 묻는 것
Design Secure Architectures(보안 아키텍처 설계)30%누가 무엇에 접근할 수 있는가: IAM 정책과 역할, 멀티 계정 가드레일, 네트워크 경계, 암호화와 키 소유권.
Design Resilient Architectures(복원력 있는 아키텍처 설계)26%구성 요소가 장애를 일으키면 어떻게 되는가: Multi-AZ, 큐를 이용한 분리(decoupling), 복구 목표(RPO와 RTO), 재해 복구 패턴.
Design High-Performing Architectures(고성능 아키텍처 설계)24%스토리지, 컴퓨팅, 데이터베이스, 네트워크 선택을 접근 패턴에 맞추기: 캐싱, 읽기 복제본(read replica), 알맞은 스토리지 유형.
Design Cost-Optimized Architectures(비용 최적화 아키텍처 설계)20%요구 사항에 필요한 만큼만 비용 지불하기: 구매 옵션, 스토리지 클래스와 수명 주기 규칙, 데이터 전송 경로.

도메인별 비중이 서로 비슷하므로 건너뛸 수 있는 도메인은 없습니다. 보안은 비중이 가장 클 뿐 아니라 나머지 세 도메인 안에도 등장합니다. "복원력"이나 "비용" 문제에도 보안 요구 사항을 슬그머니 어기는 보기가 하나쯤 섞여 있는 경우가 많습니다.

문제는 어떤 모습인가

저희는 공개된 시험 가이드를 바탕으로 이 사이트에 SAA-C03 문제 395개를 직접 만들었습니다. 이 문제들을 전체로 놓고 보면 문제 하나를 볼 때보다 시험의 모습이 훨씬 잘 드러납니다.

  • 약 3문항 중 2문항은 시나리오 문제입니다("한 회사가 …을 운영한다. …이 필요하다. 어떤 솔루션이…"). 단순 정의를 묻는 문제는 10문항 중 1문항 정도입니다.
  • 약 12문항 중 1문항은 답을 두 개 고르는 문제입니다. 둘 다 맞아야 하며, 부분 점수는 없습니다.
  • Amazon S3가 어떤 서비스보다 자주 나옵니다. 그다음은 RDS, IAM, VPC, EC2, DynamoDB 순입니다. 한 서비스에 시간을 더 쓴다면 S3입니다. 스토리지 클래스, 수명 주기 규칙, 버킷 정책, 암호화 옵션, 복제, 액세스 포인트를 익혀 두십시오.

효과적인 학습 순서

도메인들은 서로 기대고 있어서, 시험 가이드 순서대로 공부하는 것이 가장 빠른 길은 아닙니다. 아래 순서는 앞 단계 위에 다음 단계를 쌓아 올립니다.

  1. 네트워크와 자격 증명 먼저(1–2주). VPC, 서브넷, 라우팅 테이블, 보안 그룹과 네트워크 ACL의 차이, VPC 엔드포인트, 그리고 IAM 사용자, 역할, 정책과 정책 평가 로직. 거의 모든 시나리오가 이 위에서 펼쳐집니다.
  2. 스토리지와 데이터베이스(1–2주). S3 심화, EBS·EFS·FSx 비교, RDS와 Aurora(Multi-AZ, 읽기 복제본, 글로벌 데이터베이스), DynamoDB(용량 모드, 글로벌 테이블, DAX), ElastiCache.
  3. 컴퓨팅과 분리(1주). EC2 구매 옵션, Auto Scaling, 로드 밸런서, Lambda, ECS와 Fargate 기반 컨테이너, SQS, SNS, EventBridge.
  4. 복원력과 성능 패턴(1주). 백업 및 복원, 파일럿 라이트(pilot light), 웜 스탠바이(warm standby), 다중 사이트(multi-site), 그리고 CloudFront, Global Accelerator, Route 53 라우팅 정책.
  5. 비용은 마지막에(며칠). 서비스를 알고 나면 비용 문제는 요구 사항을 꼼꼼히 읽는 문제가 됩니다. Savings Plans, 예약 인스턴스(Reserved Instances), 스팟(Spot) 비교, S3 Intelligent-Tiering, 데이터 전송 경로를 다룹니다.

초보자 팁: VPC 용어가 헷갈린다면 한 번 직접 만들어 보십시오. 퍼블릭 서브넷과 프라이빗 서브넷을 하나씩 둔 VPC에 인터넷 게이트웨이, NAT 게이트웨이, 라우팅 테이블 두 개를 구성합니다. 각 서브넷에 인스턴스를 하나씩 띄우고 양쪽에서 인터넷에 접속해 보십시오. 20분만 클릭해 보면 라우팅 테이블이 하는 일을 어떤 다이어그램보다 잘 알 수 있습니다. 네트워크 문제의 절반이 바로 이 구성을 글로 설명합니다. 실습이 끝나면 NAT 게이트웨이를 삭제하십시오. 시간 단위로 요금이 나옵니다.

각 단계를 마칠 때마다 방금 공부한 도메인의 연습 세트를 몇 개 풀고, 혼합 세트를 하나 푸십시오. 일찍부터 섞어서 풀어야 문제를 읽는 대신 도메인을 알아맞히는 습관이 생기지 않습니다.

가장 많은 점수를 잃게 만드는 함정

1. 지문 끝의 조건어를 놓치는 실수

"가장 비용 효율적인(most cost-effective)", "운영 오버헤드가 가장 적은(least operational overhead)", "가장 안전한(most secure)", "애플리케이션 변경을 최소화하는(with minimal changes to the application)"은 같은 아키텍처에서도 각각 다른 정답을 가리킵니다. 대개 여러 보기가 동작하지만, 조건어에 맞는 보기는 하나뿐입니다. 지문의 마지막 문장을 먼저 읽고 나서 시나리오를 읽으십시오.

초보자 팁: 연습하는 동안 두 칸짜리 작은 목록을 만들어 두십시오. 왼쪽에는 조건어("least operational overhead")를, 오른쪽에는 복습한 문제에서 그 조건어가 가리킨 답("관리형 또는 서버리스 서비스")을 적습니다. 세트를 서너 개 풀고 나면 목록이 더 늘지 않고, 보기를 다 읽기도 전에 패턴이 보이기 시작합니다.

2. 고가용성과 확장을 같은 것으로 보는 실수

RDS Multi-AZ 배포는 장애 조치(failover)를 위해 대기 인스턴스(standby)를 둡니다. 이 대기 인스턴스는 읽기 요청을 처리하지 않습니다(전통적인 단일 대기 인스턴스 구성 기준). 읽기 복제본은 읽기 용량을 늘리고 승격할 수도 있지만, 복제는 비동기로 이루어집니다. 지문에 "가용 영역(Availability Zone) 하나를 잃어도 버텨야 한다"고 나오면 Multi-AZ를, "리포팅 쿼리 때문에 기본 인스턴스가 느려진다"고 나오면 읽기 복제본을 떠올리십시오.

더 깊이: 대기 인스턴스가 읽기를 처리하지 못하는 이유와 처리할 수 있는 경우

전통적인 RDS Multi-AZ DB 인스턴스에서는 모든 쓰기가 다른 가용 영역의 대기 인스턴스로 동기 복제된 뒤에야 확인 응답이 나갑니다. 대기 인스턴스는 오직 장애 시 역할을 넘겨받기 위해 존재합니다. 쿼리할 수 있는 엔드포인트가 없고, 장애 조치(보통 1~2분)가 일어나면 DNS 이름이 대기 인스턴스로 옮겨 갑니다. 그래서 읽기 용량은 늘지 않지만, 커밋된 데이터도 잃지 않습니다.

최근의 두 가지 설계는 이 경계를 흐립니다. Multi-AZ DB 클러스터(MySQL과 PostgreSQL)는 라이터(writer) 하나와 서로 다른 AZ에 있는 대기 인스턴스 둘로 구성되며, 이 대기 인스턴스는 읽기를 처리합니다. 장애 조치도 더 빠릅니다. Aurora는 컴퓨팅과 스토리지를 분리합니다. 클러스터 볼륨은 세 AZ에 걸쳐 사본 여섯 개를 유지하고, 쓰기를 확정하려면 그중 네 개의 확인이 필요합니다. Aurora Replica는 같은 볼륨에서 읽으므로, 복제본 하나가 읽기 용량이자 장애 조치 대상이 됩니다. 문제에 "Aurora"와 "고가용성"이 함께 나오면 별도의 대기 인스턴스가 아니라 다른 AZ의 Aurora Replica가 정답인 경우가 많습니다.

3. 동작은 하지만 손이 더 많이 가는 답을 고르는 실수

EC2에서 Kafka를 직접 운영하거나, 인스턴스에 cron 작업을 만들거나, 복제 스크립트를 직접 작성해도 동작은 하는 경우가 많습니다. 하지만 같은 일을 하는 관리형 서비스(MSK, EventBridge Scheduler, S3 Replication)가 있다면 거의 언제나 관리형 서비스가 기대하는 정답입니다. "least operational overhead"가 붙으면 더욱 그렇습니다.

4. 최소 저장 기간을 잊는 실수

객체를 S3 Standard-IA, Glacier Flexible Retrieval, Glacier Deep Archive로 옮기면 저렴해 보입니다. 하지만 이 클래스들은 최소 저장 기간(각각 30일, 90일, 180일)과 검색 요금을 부과합니다. 자주 읽거나 곧 삭제할 데이터라면 "더 저렴한" 클래스가 오히려 더 비쌀 수 있습니다.

5. 게이트웨이 엔드포인트와 인터페이스 엔드포인트를 혼동하는 실수

NAT 게이트웨이 없이 VPC에서 S3나 DynamoDB에 비공개로 접근하는 것은 게이트웨이 엔드포인트의 교과서적인 사례이며, 시간당 요금이 없습니다. 인터페이스 엔드포인트(PrivateLink)는 그 밖의 대부분 서비스에 쓰이며 시간당, GB당 요금이 부과됩니다.

마지막 한 주

  • 시간 제한을 두고 전체 혼합 세트를 최소 두 번 풀고, 맞힌 문제를 포함해 모든 문제의 모든 보기를 검토하십시오.
  • 틀린 문제는 한 문제에 대한 사실이 아니라 규칙("Multi-AZ는 읽기 확장 기능이 아니다")으로 적어 두십시오.
  • 틀린 답의 조건어를 다시 읽으십시오. 실수 대부분이 지문의 마지막 문장에서 나온다면, 모든 곳이 아니라 그 부분에서만 속도를 늦추면 됩니다.
