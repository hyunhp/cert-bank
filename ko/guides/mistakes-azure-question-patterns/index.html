AZ-900부터 AI-103까지, Azure 시험마다 반복되는 일곱 가지 실수

저희는 Microsoft Azure 시험 일곱 개(AZ-900, AZ-104, AZ-305, SC-900, DP-900, AI-901, AI-103)를 위한 연습 문제 1,644개를 만들었습니다. 문제마다 오답 선택지가 왜 틀렸는지 해설을 달았습니다. 해설을 나란히 놓고 읽어 보면 시험마다 주제는 달라도 실수는 같습니다. 거버넌스, 데이터베이스, AI 에이전트 문제에서 똑같은 일곱 가지 혼동이 나타납니다. 이 글은 각 실수를 설명하고, 어디에 나오는지 보여 주고, 그 실수를 드러내는 지문 속 단서를 알려 드립니다.

자주 틀리는 유형 · Microsoft Azure 자격증 (AZ-900, AZ-104, AZ-305, SC-900, DP-900, AI-901, AI-103)

실수: 바뀐 이름이나 끝난 기능을 믿는다

Microsoft는 제품 이름을 자주 바꾸고 제품을 자주 사용 중지합니다. 시험은 현재 이름을 쓰며, 모든 학습 가이드에 대부분의 문제가 정식 출시(GA)된 기능을 다룬다고 적혀 있습니다. 저희 해설에서 사용 중지를 다루는 문제는 61개, 미리 보기(preview) 상태를 다루는 문제는 70개이며, 미리 보기 70개 중 44개가 AI-103입니다. 오답 선택지가 매력적으로 보이는 이유는 바로 1~2년 전에는 그것이 정답이었기 때문입니다.

단서: 두 선택지가 모두 작동하는데, 그중 하나가 예전 자료에서 본 서비스를 쓰는 경우입니다. 요구 사항에 "프로덕션"이나 "새 솔루션"이 있으면 미리 보기이거나 사용 중지 예정인 선택지는 대개 오답입니다.

실수: "무엇이 존재해도 되는가"를 묻는데 "누가 해도 되는가"로 답한다

Azure에는 서로 다른 세 가지 질문에 답하는 거버넌스 도구 세 가지가 있습니다. Azure RBAC는 누가 작업할 수 있는지 정합니다. Azure Policy는 누가 만들든 리소스가 어떤 모습이어야 하는지 정합니다. 허용 리전, 허용 크기, 필수 태그 같은 것입니다. 리소스 잠금(resource lock)은 Owner를 포함한 모든 사람의 삭제나 변경을 막습니다. 저희 해설 중 21개가 Policy와 RBAC를 대비시키고, 그중 13개가 AZ-900입니다. 잠금은 AZ-900부터 AZ-305까지 단골 오답 선택지입니다. 태그는 네 번째 함정입니다. 리소스는 리소스 그룹의 태그를 상속하지 않으며, 정책으로 복사해야 합니다.

단서: 요구 사항이 리소스의 속성(리전, SKU, 태그)에 관한 것이면, 선택지에 범위를 좁게 잡은 역할이 있더라도 답은 Policy입니다.

더 깊이: 잠금은 리소스를 보호할 뿐, 그 안의 데이터는 보호하지 않습니다

Azure는 컨트롤 플레인과 데이터 플레인을 구분합니다. 컨트롤 플레인은 리소스를 만들고, 바꾸고, 삭제하는 Azure Resource Manager 요청이고, 데이터 플레인은 데이터베이스에 SQL을 실행하거나 Blob을 업로드하는 것처럼 서비스 자체에 보내는 요청입니다. 잠금은 컨트롤 플레인에만 적용됩니다. 논리 SQL 서버에 ReadOnly 잠금을 걸면 아무도 서버를 삭제할 수 없지만, 그 데이터베이스의 행은 여전히 넣고 지울 수 있습니다. 스토리지 계정에 잠금을 걸어도 Blob 삭제는 막지 못합니다. 읽기처럼 보이지만 실제로는 컨트롤 플레인 POST 요청인 호출도 있어서, ReadOnly 잠금은 이것들도 막습니다. 스토리지 계정 키 나열이나 VM 시작이 그렇습니다. 이 한 가지 사실로 잘 알려진 수수께끼 하나가 풀립니다. ReadOnly 잠금이 걸려 있으면 포털이 계정 키를 가져오지 못해 사용자의 Entra ID로 전환하고, 데이터 역할이 없는 Owner는 갑자기 Blob을 볼 수 없게 됩니다. 데이터를 보호하려면 권한, 일시 삭제(soft delete), 백업, 변경 불가(immutability) 같은 데이터 기능을 쓰세요.

실수: 역할 체계 하나가 모든 것을 다룬다고 생각한다

역할 체계는 두 가지이고 플레인은 여러 개입니다. Microsoft Entra 역할(Global Administrator, User Administrator)은 디렉터리를 관리합니다. 사용자, 그룹, 암호, 앱 등록이 그 대상입니다. Azure RBAC 역할(Owner, Contributor, Reader)은 Azure 리소스를 관리합니다. 그리고 Azure RBAC 안에서도 관리 역할은 데이터 접근 권한을 주지 않습니다. 스토리지 계정의 Contributor는 Entra 인증으로 Blob을 읽을 수 없고, 그러려면 Storage Blob Data Reader 같은 데이터 역할이 필요합니다. AI-103에도 같은 구분이 나옵니다. 개발자가 프로젝트에서 빌드하고 호출할 수 있게 해 주는 것은 Foundry User 역할이고, Reader는 에이전트를 호출할 수 없습니다.

단서: "Contributor인데 액세스가 거부된다"거나 "Global Administrator인데 VM을 관리할 수 없다"는 거의 항상 올바른 체계 안에서 권한 하나가 빠진 것이 아니라, 체계나 플레인 자체가 틀린 것입니다.

초보자 팁: Azure 포털에서 스토리지 계정의 Access control (IAM) 블레이드를 열고 "Add role assignment"를 선택한 다음, 검색 상자에 "Storage Blob"을 입력해 보세요. 그다음 구독에서 같은 작업을 하고 "Global Administrator"를 검색해 보세요. 나오지 않습니다. Azure RBAC 역할이 아니기 때문입니다. 어떤 역할이 어디에 있는지 직접 보는 데 2분이면 충분하고, AZ-900, AZ-104, SC-900, AZ-305에 걸친 문제 한 묶음이 해결됩니다.

실수: 강제가 필요한 일에 탐지 도구를 고른다

Microsoft Entra ID Protection은 로그인 위험과 사용자 위험을 계산합니다. 그 위험을 바탕으로 차단하거나 MFA를 요구하는 엔진은 Conditional Access입니다(SC-900 해설에서 12개 문제가 이 경계를 다룹니다). Defender for Cloud는 구성 수정 사항을 권장하고, Policy의 deny 효과는 잘못된 리소스를 차단합니다. 감사(Audit)는 누가 무엇을 했는지 기록할 뿐, 아무것도 막지 않습니다. AI 시험에서는 같은 실수가 다른 모습으로 나옵니다. 시스템 메시지에 "절대 개인 데이터를 공개하지 마라"라고 적어도 모델을 유도할 뿐이고, 입력과 출력에 대한 강제는 가드레일이 합니다. "이 사용자의 문서만 사용하라"는 지침이 아니라 검색 쿼리의 필터로 강제합니다.

단서: "절대 ~하면 안 된다", "차단", "방지", "보장" 같은 단어에는 강제하는 통제가 필요합니다. "식별", "보고", "알림 받기" 같은 단어는 탐지 도구를 가리킵니다.

실수: 사본을 서비스를 계속 돌리는 수단으로 착각한다

Azure Backup은 복원할 수 있도록 복구 지점을 보관하며, VM의 RPO는 시간 단위입니다(백업은 가장 자주 해도 4시간마다). Azure Site Recovery는 장애 조치(failover)할 수 있도록 VM을 복제하며, RPO는 분 단위입니다. Azure SQL에서 지역 복원(geo-restore)은 백업에서 데이터베이스를 다시 만듭니다(느리고, 엔드포인트가 새로 생깁니다). 활성 지역 복제(active geo-replication)는 데이터베이스마다 읽기 가능한 보조 복제본을 유지합니다. 장애 조치 그룹(failover group)은 이름이 바뀌지 않는 수신기(listener) 뒤에서 데이터베이스를 함께 옮깁니다. 저희 AZ-104와 AZ-305 해설 중 14개 문제가 Backup과 Site Recovery를 대비시킵니다. 반대 방향의 실수도 나옵니다. 복제는 삭제와 손상까지 충실하게 복사하므로 결코 백업을 대신하지 못합니다.

단서: 두 숫자를 먼저 읽으세요. RPO가 시간 단위이고 하루 정도의 중단이 허용되면 백업 문제입니다. 분 단위면 복제 문제입니다. "연결 문자열이 바뀌면 안 된다"는 장애 조치 그룹입니다.

실수: "프라이빗"을 너무 느슨하게 읽는다

서비스 엔드포인트(service endpoint)는 서브넷이 Storage나 SQL 같은 서비스에 Microsoft 백본망으로 닿게 해 주지만, 리소스의 공용 엔드포인트는 그대로 남고 온프레미스 클라이언트는 이를 쓸 수 없습니다. 프라이빗 엔드포인트(private endpoint)는 특정 리소스 하나에 가상 네트워크 안의 사설 IP 주소를 주며, 피어링, VPN, ExpressRoute로 접근할 수 있고 공용 엔드포인트를 끌 수 있습니다. AZ-104와 AZ-305의 같은 문제에 두 가지가 모두 선택지로 나옵니다.

단서: "온프레미스에서", "공용 액세스 비활성화", "다른 계정으로의 데이터 유출 방지"는 모두 프라이빗 엔드포인트를 가리킵니다.

실수: 눈에 보이는 이름이 코드가 쓰는 이름은 아니다

Microsoft Foundry에서 카탈로그의 모델은 배포하기 전까지 아무 일도 하지 않으며, 배포에는 별도의 이름을 붙일 수 있습니다. 코드에서 model 매개 변수에는 모델의 카탈로그 이름이 아니라 배포 이름이 들어갑니다. 저희 AI-901과 AI-103 해설 중 23개 문제가 이 점을 근거로 하며, 대개 권한 문제처럼 보이는 "model not found"나 404 오류로 나옵니다. AI-103에는 가까운 친척도 있습니다. 리소스의 openai.azure.com/openai/v1 엔드포인트와 services.ai.azure.com 아래의 프로젝트 엔드포인트는 서로 다른 API를 제공하므로, 자격 증명이 맞아도 엔드포인트가 틀리면 실패합니다.

단서: 인증은 잘 된다는 것이 확인된 상태에서 모델이나 경로를 지목하는 오류가 나면, 역할이 아니라 이름과 엔드포인트의 문제입니다.

더 깊이: 같은 혼동이 여러 시험에 걸쳐 나오는 이유

이 일곱 가지 실수는 일곱 개의 사실이 아니라, Azure가 어디에나 긋는 네 가지 경계입니다. 컨트롤 플레인 대 데이터 플레인(잠금, RBAC 데이터 역할, Foundry 역할). 탐지 대 강제(ID Protection과 Conditional Access, Defender for Cloud와 Policy, 시스템 메시지와 가드레일). 사본 대 실행 중인 복제본(Backup과 Site Recovery, 지역 복원과 장애 조치 그룹). 이름이나 주소 대 그것이 가리키는 대상(배포 이름, 엔드포인트, 프라이빗 엔드포인트). 선택지가 경계의 어느 쪽에 있는지 말할 수 있으면, 잘 모르는 주제에서도 오답을 지워 나갈 수 있는 경우가 많습니다.
