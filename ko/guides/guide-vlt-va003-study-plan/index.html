Vault Associate (003) 학습 가이드: 로그인부터 폐기까지 요청 하나를 따라가 보기

Vault Associate 시험에는 목표(objective)가 아홉 개 있습니다. 하나씩 공부하면 서로 다른 과목 아홉 개처럼 느껴집니다. 하지만 실제로는 요청 하나가 거치는 정거장들을 설명합니다. 클라이언트가 자신이 누구인지 증명하고, 토큰을 받고, 토큰의 정책이 경로와 대조되고, 시크릿 엔진이 응답하고, 그 응답에는 리스(lease)가 붙고, 언젠가는 토큰과 리스가 끝납니다. 그 모든 것 아래에 암호화된 스토리지와 봉인(seal)이 있습니다. 이 가이드는 이 요청을 처음부터 끝까지 따라갑니다. 시험 문제 대부분이 한 정거장에서 무슨 일이 일어나는지, 또는 앞단이 바뀌었을 때 뒷단에서 무슨 일이 일어나는지를 묻기 때문입니다.

학습 가이드 · HashiCorp Certified: Vault Associate (003) (VLT-VA003)

시험 요약

시험 시간은 1시간이고, 온라인 감독 방식으로 영어로 치르며, Vault 1.19를 기준으로 합니다. 문제 유형은 참/거짓, 단일 선택, 복수 선택이며, 복수 선택 문제는 몇 개를 골라야 하는지 알려 줍니다. HashiCorp는 문제 수, 합격 점수, 목표별 비중을 공개하지 않습니다. 공식 시험 페이지를 확인하고 아홉 개 목표를 모두 공부하십시오. 이 문제은행의 VLT-VA003 문제 253개 중 17%는 답을 여러 개 고르는 문제이고, 다섯 문제 중 하나 이상이 "이것이 갑자기 안 된다"는 상황을 다룹니다. 문제 본문에 "token"이라는 단어가 나오는 문제는 56개로, "policy"(30개)나 "lease"(28개)보다 훨씬 많습니다.

정거장 1: 당신은 누구입니까? (인증 방식)

인증 방식(auth method)은 신원을 확인하고, 성공하면 토큰을 반환합니다. 시크릿을 반환하는 일은 없습니다. 인증 방식을 고른다는 것은 신원의 출처를 고른다는 뜻입니다. 그러니 먼저 클라이언트가 사람인지 워크로드인지 판단하십시오.

문제 속 단서인증 방식
직원이 회사 SSO로 UI에 로그인함OIDC 역할을 사용하는 JWT/OIDC(브라우저 리디렉션)
기존 Active Directory 비밀번호를 사용하고 싶음LDAP
CI 플랫폼이 이미 잡마다 서명된 JWT를 발급함JWT 역할(브라우저 없음)
파드가 사전 공유 시크릿 없이 토큰을 받아야 함Kubernetes
AWS의 워크로드가 신원을 증명함AWS, iam 유형(권장)
앱이나 배치 잡이며, 오케스트레이터가 일회용 시크릿을 전달할 수 있음AppRole, 응답 래핑된 SecretID와 함께

대표적인 함정은 헤드리스 파이프라인에서 쓰는 OIDC 역할입니다. 그곳에서는 브라우저 리디렉션이 일어날 수 없습니다. 또 로그인 하나를 여러 사람이 함께 쓰면 모두가 엔터티 하나로 보이므로 감사 추적이 무너진다는 점도 기억하십시오.

정거장 2: 토큰

서비스 토큰(service token)은 저장되고 추적됩니다. 그래서 갱신과 폐기가 가능하고, 하위 토큰, 접근자(accessor), cubbyhole을 가질 수 있습니다. 배치 토큰(batch token)은 아무것도 저장하지 않는 암호화된 블롭입니다. 갱신하거나 직접 폐기할 수 없고, 접근자나 하위 토큰도 없습니다. 짧고 단순한 잡이 매우 많을 때는 배치 토큰을, 그 밖의 모든 경우에는 서비스 토큰을 고르십시오. TTL이 짧다고 해서 서비스 토큰이 상태 없는(stateless) 토큰이 되지는 않습니다.

수명 규칙에서 많은 점수가 나옵니다.

  • 갱신하면 TTL 구간이 지금부터 다시 시작됩니다. 원래 만료 시점에 시간을 더하는 것이 아닙니다.
  • max TTL에 이르면 갱신이 더 이상 되지 않습니다. 몇 주 동안 제대로 갱신하던 토큰이 갑자기 죽었다면 max TTL에 도달한 것입니다.
  • 주기적 토큰(periodic token)에는 (명시적으로 설정하지 않는 한) max TTL이 없으며, 주기마다 갱신하는 한 계속 살아 있습니다. 오래 실행되는 서비스에 알맞습니다.
  • 부모 토큰을 폐기하면 모든 하위 토큰과 그 리스도 폐기됩니다. 고아 토큰(orphan token)에는 부모가 없습니다. token 방식 이외의 로그인으로 받은 토큰은 모두 고아 토큰입니다.

정거장 3: 정책 검사

Vault는 기본적으로 거부합니다. 토큰에 붙은 정책 중 하나에 경로가 일치하는 스탠자가 있고, 그 스탠자가 HTTP 메서드에 필요한 권한(capability)을 줄 때만 요청이 성공합니다. GET은 read, POST나 PUT은 create 또는 update, LIST는 list입니다. 데이터베이스 자격 증명 생성은 GET이므로 read면 충분합니다.

  • *는 접두사 일치이며 끝에만 쓸 수 있습니다. +는 정확히 한 세그먼트를 뜻하며 어디에나 쓸 수 있습니다.
  • KV 버전 2에서 값은 data/ 아래에, 키 목록은 metadata/ 아래에 있습니다. secret/app/db에 대한 정책은 vault kv get이 보내는 어떤 요청과도 일치하지 않습니다.
  • deny는 sudo를 포함한 모든 것보다 우선합니다. sudo는 감사 장치(audit device), 봉인, 접두사 폐기처럼 루트로 보호되는 경로에만 필요합니다.
더 깊이: 더 좁은 스탠자가 권한을 빼앗을 수 있는 이유

토큰에 붙은 여러 정책이 완전히 같은 경로 패턴을 가지면 권한이 합쳐집니다. 하지만 서로 다른 패턴이 같은 요청에 일치하면 Vault는 합치지 않습니다. 우선순위가 가장 높은 패턴 하나만 적용됩니다. 패턴의 첫 와일드카드가 더 앞에 나올수록, 한쪽만 *로 끝날 때 그쪽이, + 세그먼트가 더 많을수록, 길이가 더 짧을수록 우선순위가 낮습니다. 그래서 secret/data/*에 read와 update를, secret/data/app/*에 read만 가진 토큰은 secret/data/app/x를 수정할 수 없습니다. 더 구체적인 스탠자가 이기고, 그 스탠자는 읽기만 허용하기 때문입니다. 정책 두 개를 보여 주고 토큰이 무엇을 할 수 있는지 묻는 문제는 이 규칙을 시험합니다.

초보자 팁: vault server -dev로 버려도 되는 개발 서버를 띄우고, KV 버전 2를 활성화한 뒤, 아무 명령에나 -output-policy를 붙여 실행해 보십시오. CLI가 명령을 실행하는 대신 그 요청에 필요한 정책을 정확히 출력합니다. 그다음 작은 정책을 작성하고, 그 정책으로 토큰을 만들고, vault token capabilities TOKEN PATH로 경로를 시험해 보십시오. 출력된 정책에 data/가 나타나는 것을 한 번 보면 KV v2 경로 규칙을 잊지 않게 됩니다.

정거장 4: 시크릿 엔진

정적 엔진은 입력받은 것을 저장합니다(KV). 동적 엔진은 요청이 오면 자격 증명을 만들고 나중에 폐기합니다(database, AWS). PKI는 인증서를 발급하고, SSH는 키에 서명하거나 자격 증명을 발급하고, cubbyhole은 토큰 하나만 쓰는 개인 공간이며, transit은 데이터를 저장하지 않고 암호화합니다. 응답 래핑(response wrapping)은 일회용 래핑 토큰으로 값을 전달하므로 중간자가 그 값을 볼 수 없습니다.

transit은 별도의 목표로 다룹니다. 평문은 base64로 인코딩해야 합니다. vault:v2:... 같은 암호문은 키가 아니라 키 버전을 나타냅니다. 키를 교체(rotate)하면 버전이 하나 늘고, 기존 암호문은 여전히 복호화됩니다. rewrap은 평문을 드러내지 않고 암호문을 최신 버전으로 옮기며, 그 결과는 애플리케이션이 직접 저장해야 합니다. min_decryption_version은 오래된 버전으로 복호화하지 못하게 막습니다.

정거장 5: 리스, 그리고 종착점

모든 동적 시크릿과 모든 서비스 토큰에는 리스가 있습니다. KV 데이터에는 없습니다. 리스 ID는 시크릿이 나온 경로로 시작하므로, vault lease revoke -prefix aws/로 모든 AWS 자격 증명을 한 번에 폐기할 수 있습니다(sudo 필요). 갱신해도 시크릿과 리스 ID는 그대로이며, 늘어나는 시간은 지금부터 셉니다. 리스가 만료되거나 그 리스를 만든 토큰이 폐기되면, Vault는 원천에서 시크릿을 폐기합니다. 엔진을 비활성화하면 그 엔진이 발급한 모든 것이 폐기되고 데이터도 삭제되므로, 접두사 폐기보다 훨씬 무거운 조치입니다.

요청은 왼쪽에서 오른쪽으로 흐릅니다. 한 정거장의 변화는 그 뒤 정거장들에 나타납니다.

그 아래: 배리어, 봉인, 클러스터

Vault가 쓰는 모든 것은 배리어(barrier)를 거치며 암호화됩니다. 그래서 스토리지는 신뢰할 수 없는 곳으로 취급합니다. 이를 키 체인이 보호합니다. 봉인 해제 키(unseal key)가 루트 키(root key)를, 루트 키가 암호화 키(encryption key)를 보호합니다. vault operator init는 클러스터마다 한 번 실행하며, 키 조각(기본값 5개, 임계값 3)과 초기 루트 토큰을 출력합니다. 봉인된 노드는 상태를 보고하고 키 조각을 받는 일만 할 수 있습니다.

더 깊이: 복구 키로 할 수 있는 일과 없는 일

자동 봉인 해제(auto-unseal)를 쓰면 클라우드 KMS 같은 신뢰할 수 있는 외부 서비스가 시작 시 루트 키를 복호화합니다. 그래서 재시작한 노드가 사람 없이 봉인 해제된 상태로 올라옵니다. 이때 초기화는 봉인 해제 키 대신 복구 키(recovery key)를 반환합니다. 복구 키로는 아무것도 봉인 해제할 수 없습니다. 새 루트 토큰 생성이나 키 재생성(rekey) 같은 정족수 작업을 승인할 뿐입니다. 그래서 "KMS 키가 삭제된 뒤 복구 키로 봉인을 해제한다"는 오답입니다. KMS 키가 없으면 루트 키를 복호화할 수 없고 데이터에 접근할 수 없습니다. Shamir에서 자동 봉인 해제로 옮기는 것은 봉인 마이그레이션(seal migration)이며, vault operator unseal -migrate로 수행합니다. 기존 Shamir 키는 복구 키가 됩니다.

배포 문제는 노드 정족수(quorum)를 갖춘 Integrated Storage, 활성 노드 하나와 대기 노드들로 이루어진 HA, 직접 관리하는 Vault와 HCP Vault Dedicated의 차이를 묻습니다(HCP Vault Dedicated에서는 HashiCorp가 스토리지, 봉인 해제, 업그레이드, 백업을 맡고, 인증, 정책, 엔진 구성은 여전히 사용자가 합니다). DR이든 성능(performance)이든 복제(replication)는 Vault Enterprise 기능입니다.

애플리케이션에 시크릿 전달하기

마지막 목표는 누가 Vault를 알아야 하는지 묻습니다. Vault Agent는 수정하지 않은 애플리케이션 옆에서 실행되며, 스스로 로그인하고(auto-auth), 토큰을 갱신하고, 템플릿으로 시크릿을 파일에 렌더링합니다. 가상 머신에서도 동작합니다. Vault Secrets Operator는 시크릿을 네이티브 Kubernetes Secret으로 동기화하며 Kubernetes 전용입니다. API를 직접 호출하면 모든 레코드에 transit을 쓰는 식으로 가장 세밀하게 제어할 수 있지만, 애플리케이션이 Vault를 알아야 합니다.

학습 순서

  1. 정책과 토큰을 먼저 공부하십시오. 다른 모든 목표의 문제 안에 등장합니다.
  2. 인증 방식, 그다음 리스.
  3. 시크릿 엔진과 transit.
  4. 아키텍처: 배리어, 초기화, 봉인과 봉인 해제. 그다음 클러스터, 자동 봉인 해제, HCP Vault Dedicated.
  5. Agent와 Secrets Operator, 그다음 시간을 재며 여러 목표를 섞은 세트.
