SCS-C03 학습 가이드: AWS가 요청 하나를 판정하는 방식부터, 누가 지켜보는지까지

AWS Certified Security – Specialty 시험(SCS-C03)은 도메인이 여섯 개지만, 모든 도메인을 관통하는 질문은 두 가지입니다. 이 요청은 허용될까? 그리고 문제가 생기면 어떤 서비스가 알아차리고, 그다음엔 무슨 일이 일어날까? 이 가이드는 이 두 질문을 뼈대로 삼습니다. 먼저 접근 판정을 계층별로 살펴봅니다. 어떤 단일 서비스보다 더 많은 점수를 좌우하기 때문입니다. 다음으로 탐지 서비스와 각 서비스가 실제로 볼 수 있는 것을 다룹니다. 마지막으로 이 둘에서 이어지는 대응 규칙과 데이터 보호 규칙을 정리합니다.

학습 가이드 · AWS Certified Security – Specialty (SCS-C03)

시험 개요

170분 동안 65문항을 풉니다(채점 50문항, 표시되지 않는 비채점 15문항). 점수는 100~1,000점 척도이며 합격 점수는 750점입니다. 도메인은 여섯 개입니다. Detection(16%), Incident Response(14%), Infrastructure Security(18%), Identity and Access Management(20%), Data Protection(18%), Security Foundations and Governance(14%)입니다. 건너뛰어도 될 만큼 작은 도메인은 없습니다.

이 문제은행의 SCS-C03 문제 395개에서 가장 자주 나오는 서비스는 단연 IAM입니다. 23%의 문제에 태그가 붙어 있고, 그 뒤로 Amazon S3(16%), AWS Organizations(11%), CloudTrail과 KMS(각 10%), GuardDuty(9%)가 이어집니다. 다섯 문제 중 하나(20%)는 트러블슈팅 시나리오로, 대개 "이건 동작해야 하는데 왜 안 될까?"를 묻습니다. 약 12%는 정답을 두 개 고르는 문제입니다.

1부: 접근 판정

모든 API 호출은 여러 종류의 정책에 동시에 검사를 받습니다. 어떤 정책은 접근을 부여할 수 있고, 어떤 정책은 상한선만 정할 수 있습니다. IAM 트러블슈팅 문제 대부분은 "어느 계층이 거부하고 있는가?"를 물으면 풀립니다.

정책 유형권한 부여 가능?역할
서비스 제어 정책(SCP)아니요멤버 계정의 보안 주체가 할 수 있는 일에 상한선을 둡니다. 예: aws:RequestedRegion으로 "승인된 리전만" 허용.
리소스 제어 정책(RCP)아니요외부 보안 주체를 포함해 누구든 멤버 계정의 리소스에 할 수 있는 일에 상한선을 둡니다(RCP를 지원하는 서비스 한정). 리소스 정책이 지나치게 열려 있어도 적용됩니다.
권한 경계(permissions boundary)아니요사용자나 역할 하나에 상한선을 둡니다. 작업이 자격 증명 정책과 경계 양쪽에 모두 있어야 합니다.
자격 증명 정책(identity policy)예사용자나 역할이 할 수 있는 일.
리소스 정책예이 버킷, 키, 큐, 시크릿을 누가 쓸 수 있는지. aws:PrincipalOrgID로 내 조직에만 한정할 수 있습니다.
세션 정책아니요역할을 맡은(assume) 세션 하나의 권한을 좁힙니다.

이 표 위에 두 가지 규칙이 있습니다. 이 정책들 중 어디에든 명시적 거부(explicit deny)가 있으면 판정은 거기서 끝납니다. 허용은 아무것도 거부하지 않을 때만 의미가 있습니다. 그리고 상한선은 겹쳐서 적용됩니다. 작업은 해당하는 모든 상한선을 통과해야 비로소 허용이 효력을 가집니다.

더 깊이: 교차 계정 접근에 양쪽 허용이 필요하고, KMS에는 세 번째가 필요한 이유

한 계정 안에서는 자격 증명 정책이나 리소스 정책 중 하나만 허용해도 대개 충분합니다. 계정을 넘나들면 그렇지 않습니다. 호출하는 쪽 계정이 자격 증명 정책에서 작업을 허용해야 하고, 리소스 쪽 계정이 리소스 정책에서(호출자가 그쪽 역할을 맡는다면 역할의 신뢰 정책에서) 그 호출자를 허용해야 합니다. 각 계정이 자기 쪽을 통제합니다. AWS KMS는 규칙이 하나 더 있습니다. 키 정책이 1차 통제 수단이며, 키가 있는 계정의 IAM 정책은 키 정책이 그 계정에 위임을 허용할 때만 효력이 생깁니다. 그래서 "버킷 정책은 다른 계정을 허용하는데 SSE-KMS 객체 읽기가 여전히 실패한다"는 단골 문제의 답은 키 정책에 그 계정의 kms:Decrypt를 추가하는 것입니다(호출자의 IAM 정책도 이를 허용해야 합니다). 같은 이유로 aws/secretsmanager나 aws/rds처럼 키 정책을 수정할 수 없는 AWS 관리형 키는 교차 계정에서 쓸 수 없습니다. 고객 관리형 키를 쓰세요.

초보자 팁: 샌드박스 계정에서 AdministratorAccess를 가진 역할을 만들고, s3:ListBucket과 s3:GetObject만 허용하는 권한 경계를 붙여 보세요. 그 역할을 맡아 파일을 업로드해 봅니다. 그다음 같은 역할과 s3:PutObject 작업으로 IAM 정책 시뮬레이터를 열어 보세요. 거부의 원인이 자격 증명 정책이 아니라 경계라는 것을 보여 줍니다. 한 번만 해 보면 "자격 증명 정책이 허용하는 것만으로는 부족하다"가 문장이 아니라 직접 본 사실이 됩니다.

위에서부터 읽으세요. 요청은 해당하는 모든 상한선을 통과해야 비로소 허용이 효력을 가집니다.

2부: 누가 지켜보고, 각자 무엇을 보는가

탐지 문제에는 하나같이 관련 있어 보이는 모니터링 서비스가 여럿 나옵니다. 각 서비스가 보는 대상은 다릅니다. 입력 데이터가 문제와 맞는 서비스를 고르세요.

서비스답해 주는 질문
AWS CloudTrail누가 어떤 API를 언제, 어디서 호출했는가. Insights는 비정상적인 호출량이나 오류율을 표시합니다.
AWS Config리소스가 시간에 따라 어떤 상태였고, 내 규칙을 준수하는가.
Amazon GuardDuty악의적인 일이 벌어지고 있는가? 로그와 활동에서 위협 결과(finding)를 냅니다. 탐지만 할 뿐 차단하지는 않습니다.
Amazon Detective결과 주변에서 무슨 일이 있었는가. 관련 엔터티와 시간에 따른 활동.
AWS Security Hub CSPMAWS Foundational Security Best Practices, CIS 같은 표준에 대한 제어 점검과 GuardDuty, Inspector, Macie의 결과를 여러 계정에 걸쳐 한곳에서. (예전 이름은 AWS Security Hub였고, 이 이름은 이제 이 결과들을 노출(exposure)로 연관 분석하는 새 서비스가 씁니다.)
Amazon InspectorEC2 인스턴스, 컨테이너 이미지, Lambda 함수의 알려진 취약점. 리소스 유형별로 따로 활성화합니다.
Amazon MacieS3의 어디에 민감한 데이터가 있는가.
IAM Access Analyzer어떤 리소스가 신뢰 영역(zone of trust) 밖에서 접근 가능한가. 별도로, 선택한 리소스에 대한 내부 접근과 사용되지 않는 접근 권한.

멀티 계정 환경에서 시험이 기대하는 구성은 이렇습니다. GuardDuty와 Security Hub의 위임된 관리자(delegated administrator)로 전용 보안 도구 계정을 두고, 멤버 계정이 멈출 수 없는 조직 트레일을 만들고, EventBridge 규칙으로 심각도 높은 결과를 자동화나 채팅 채널로 보냅니다. 변경되면 안 되는 로그는 별도의 로그 아카이브 계정으로 보내고, 변조를 탐지하려면 CloudTrail 로그 파일 무결성 검증을, 변조를 막으려면 S3 Object Lock을 씁니다.

3부: 문제가 생겼을 때

Incident Response 문제는 순서와 완결성을 시험합니다. 유출된 액세스 키는 가장 먼저 비활성화합니다. 코드 저장소를 정리해도 아무것도 취소되지 않습니다. 키를 비활성화해도 그 키로 이미 만든 세션은 끝나지 않으므로, aws:TokenIssueTime을 조건으로 하는 거부를 추가합니다(역할의 "활성 세션 취소(revoke active sessions)"가 하는 일입니다). 같은 서브넷의 이웃으로부터도 인스턴스를 격리하려면, 인스턴스의 모든 네트워크 인터페이스에서 보안 그룹을 바꿉니다. 네트워크 ACL과 라우팅은 서브넷 전체에 작용합니다. 정리하기 전에 증거부터 보존하고, 루트 사용자조차 지울 수 없어야 한다면 Object Lock을 규정 준수 모드(compliance mode)로 쓰세요. 거버넌스 모드(governance mode)는 권한 있는 사용자가 우회할 수 있습니다.

4부: 사람들을 놀라게 하는 데이터 보호 규칙

  • 기존 RDS 인스턴스나 EBS 볼륨은 그 자리에서 암호화할 수 없습니다. 스냅샷을 암호화하며 복사한 뒤, 그 사본에서 복원하거나 새로 만드세요.
  • SSE-S3는 이미 기본으로 객체를 암호화합니다. 자체 키 정책으로 누가 키를 쓸 수 있는지 통제해야 하면 고객 관리형 키를 쓰는 SSE-KMS를 고르세요. KMS 호출은 CloudTrail에도 기록됩니다.
  • KMS 키는 한 리전에 속합니다. 다른 리전으로 복사한 암호화 데이터에는 그 리전의 키(또는 다중 리전 키)가 필요합니다.
  • 내부 전용 프라이빗 TLS 인증서는 공개 ACM 인증서가 아니라 AWS Private CA에서 발급합니다.
더 깊이: KMS가 파일이 아니라 키를 암호화하는 이유

KMS Encrypt 작업은 적은 양의 데이터(최대 4,096바이트)만 받습니다. KMS 키는 서비스 밖으로 나가지 않으므로, 모든 바이트가 KMS까지 이동해야 하기 때문입니다. 실제 데이터에는 서비스들이 봉투 암호화(envelope encryption)를 씁니다. GenerateDataKey를 호출해 평문 데이터 키와, 같은 키를 KMS 키로 암호화한 사본을 받습니다. 평문 키로 데이터를 로컬에서 암호화한 뒤 평문 키는 버리고, 암호화된 데이터 키를 데이터 옆에 저장합니다. 복호화할 때는 작은 암호화 데이터 키만 KMS로 보냅니다. 그래서 큰 파일을 "KMS로" 암호화하는 문제에서 파일에 Encrypt를 호출하는 보기는 오답이고, 키에 대해 kms:Decrypt를 거부하면 객체가 몇 개든 그 키로 암호화된 모든 것에 접근할 수 없게 됩니다.

학습 순서

  1. IAM 정책 평가, 교차 계정 역할, STS, Identity Center, Organizations 정책(SCP, RCP, 태그 정책).
  2. KMS 키 정책, 그랜트(grant), 봉투 암호화, S3 암호화 옵션, Secrets Manager.
  3. 네트워크 통제: 보안 그룹, 네트워크 ACL, VPC 엔드포인트와 그 정책, WAF, Firewall Manager, Shield.
  4. 탐지 서비스, 이어서 인시던트 대응 런북, 그다음 거버넌스(Control Tower, Config 적합성 팩, 위임된 관리자).
