@ DBX-DEA D1 T1.1 applied definition
S: A security architect asks where the web application, job scheduler and notebook service of a Databricks workspace run, compared with the place where Spark processes the data of a classic compute cluster. Which description is correct?
A: The web application and scheduling services run in the control plane managed by Databricks; classic compute runs in the compute plane inside the customer's own cloud account
B: The web application and scheduling services run in the customer's cloud account; classic compute runs in a compute plane that Databricks operates in its own account
C: Both the web application and classic compute run in the control plane, and the customer's cloud account only stores the cloud audit logs of the workspace
D: Both the web application and classic compute run in the customer's cloud account, and Databricks supplies only the Spark runtime images used by the clusters
K: A
G: ## Two planes
A Databricks workspace is split into a control plane and a compute plane.
- The **control plane** holds the backend services that Databricks manages in the Databricks account: the web application, the notebook and job services, cluster management and workspace metadata.
- The **compute plane** is where data is actually processed. With **classic compute** the plane lives in the customer's own cloud account, so clusters read data in the customer's network and storage. With **serverless compute** the resources run in a serverless compute plane in the Databricks account.
## Why it matters
Data engineers choose compute partly by this split: classic compute gives control over networking and instance types in the customer account, while serverless removes the infrastructure work.
Example: submitting a job in the Jobs UI sends the request to the control plane, which launches VMs in the compute plane to run the Spark tasks.
W: Control plane versus compute plane: Databricks hosts the web application and scheduling services, and classic clusters are started as VMs in the customer's own cloud account, which is where Spark processes the data.
X: B=Reversed planes: the web application is a Databricks-managed service in the control plane, not something running in the customer account, and classic compute is the part that runs in the customer account.
C=Everything in the control plane: classic compute resources are created in the customer's cloud account, so data processing does not happen in the Databricks-managed control plane.
D=Everything in the customer account: the web application, job service and workspace metadata are backend services that Databricks manages itself, so they are not deployed into the customer's account.
T: Control plane = Databricks-managed services; compute plane = where data is processed (customer account for classic, Databricks account for serverless).
V: Databricks workspace architecture

@ DBX-DEA D1 T1.1 applied use-case
S: A nightly job runs `INSERT INTO sales_silver SELECT * FROM staging_sales` on a Delta table. The cluster is terminated by an out-of-memory error after the write has produced some data files but before the job finished. What does a reader querying `sales_silver` see afterwards?
A: The partial rows from the files written before the failure, because Delta appends each data file to the table as soon as it is written
B: The table in its state before the failed job, because the files are added to the table only when the transaction log commit succeeds
C: An error on every query until someone runs `VACUUM`, since the orphaned files make the table state inconsistent for readers
D: Only the rows from the first half of the job, since Delta rolls back the failed commit but keeps the files that were completed
K: B
G: ## How Delta Lake provides atomicity
A Delta table is a set of Parquet data files plus a **transaction log** (the `_delta_log` folder). The log records each commit as an ordered list of actions, such as "add this file" or "remove that file". Readers build the table from the log, not by listing files in the folder.
- A write first creates new data files, which at that point belong to no table version.
- The write becomes visible only when the commit entry is atomically added to the log.
- If the job dies before the commit, the files stay orphaned and no reader ever sees them.
This is the **A** (atomicity) of ACID: a transaction either fully applies or not at all. The orphaned files are removed later by `VACUUM`.
W: Readers see the previous table state: the data files from the failed job are not referenced by any commit in the transaction log, so the table behaves as if the job never ran.
X: A=Partial rows: Delta never appends files to the table as they are written. Files count only after the log commit, which is why readers cannot see half-finished writes.
C=Errors until VACUUM: orphaned files are invisible to readers and cause no query errors. VACUUM only reclaims their storage space later.
D=Partial rollback: there is no half-commit; a failed transaction leaves no rows visible at all, not the ones finished before the failure.
T: Delta data files become part of a table only when the transaction log commit succeeds, so failed writes are invisible.
V: Delta Lake

@ DBX-DEA D1 T1.1 applied troubleshooting
S: A data engineer ran `DELETE FROM orders WHERE region = 'EU'` on a Delta table by mistake. Yesterday's table state is needed for a report, and no `VACUUM` has been run. Which statement lets the engineer find the version before the delete and read it?
A: `SELECT * FROM orders VERSION AS OF 0`, because version 0 is always the state of the table before the latest operation
B: `DESCRIBE DETAIL orders`, which lists every earlier table version and can be queried directly for the rows of each version
C: `DESCRIBE HISTORY orders`, then `SELECT * FROM orders VERSION AS OF <version before the DELETE>` with the number found in the history
D: `SELECT * FROM orders@v-1`, because the table name suffix always returns the previous version regardless of later changes
K: C
G: ## Table history and time travel
Every commit to a Delta table adds a numbered **version** to the transaction log. Two features use that log:
- `DESCRIBE HISTORY <table>` lists the versions with timestamp, user, operation (`WRITE`, `DELETE`, `MERGE`...) and operation metrics.
- **Time travel** reads an earlier version: `SELECT * FROM t VERSION AS OF 12` or `TIMESTAMP AS OF '2026-10-30'`.
Time travel works only while the old data files still exist; `VACUUM` removes files older than the retention threshold, which is 7 days by default.
Example: history shows version 15 is the `DELETE`, so `VERSION AS OF 14` returns the rows as they were just before it.
W: History then VERSION AS OF: the history identifies which version is the DELETE, and querying the version just before returns the data from before the mistake because the files are still present.
X: A=Version 0: version 0 is the table's first commit, not the one before the latest change, so it would show the table as it was created.
B=DESCRIBE DETAIL: it shows the current metadata of the table (location, file count, size, properties), not a list of versions, and it cannot be queried by version.
D=Suffix v-1: the `@v` syntax needs an explicit version number such as `orders@v14`; a relative `v-1` is not valid.
T: Find the version with DESCRIBE HISTORY, then read it with VERSION AS OF or TIMESTAMP AS OF while the files still exist.
V: Delta Lake

@ DBX-DEA D1 T1.1 applied troubleshooting
S: A pipeline run replaced the contents of a Delta table with bad data. The table history shows the last good state as version 41, and the files for that version are still within the retention period. The engineer wants the table itself, not just a query, to return to that state. Which command does that?
A: `RESTORE TABLE customers TO VERSION AS OF 41`, which requires MODIFY permission and creates a new commit that reverts the table's contents
B: `CREATE OR REPLACE TABLE customers SHALLOW CLONE customers`, which rolls back the table by cloning the current version again
C: `VACUUM customers RETAIN 0 HOURS`, which deletes data files from versions newer than the one named by the retention setting
D: `DELETE FROM customers VERSION AS OF 41`, which removes every row that was added to the table after that version
K: A
G: ## Reading an old version versus restoring it
`VERSION AS OF` only reads an old snapshot; the table keeps its current content. `RESTORE` goes further: it makes the table's current state equal to a previous version or timestamp.
- Syntax: `RESTORE TABLE t TO VERSION AS OF 41` (or `TO TIMESTAMP AS OF ...`).
- It needs `MODIFY` permission on the table.
- The restore is itself a new commit, so history stays intact and you can restore again.
- It works only if the data files of that version still exist. After `VACUUM` removed them, restoring to that version is not possible.
W: RESTORE: it rewrites the table's current state to match version 41 as a new commit, and it is allowed because the old files are still within retention.
X: B=Shallow clone of itself: a clone of the current version just copies the bad current state, so it does not go back in time.
C=VACUUM RETAIN 0 HOURS: vacuum deletes unreferenced old files and cannot revert anything. It would destroy the files needed for time travel and restore.
D=DELETE ... VERSION AS OF: DELETE has no version clause, and deleting rows does not bring back updated or overwritten data either.
T: VERSION AS OF reads history; RESTORE makes the table itself return to an earlier version while the files exist.
V: Delta Lake

@ DBX-DEA D1 T1.1 applied tradeoff
S: Last month a table was changed several times. Today `SELECT * FROM events TIMESTAMP AS OF '2026-10-01'` fails because the files are gone, although the table history still lists that date. A weekly `VACUUM` runs with default settings and the table properties were never changed. What explains this?
A: Table history and time travel use different thresholds: the history is kept longer, while data files are removed by `VACUUM` once they pass the file retention
B: Time travel is limited to the last 24 hours, so any older timestamp always fails regardless of the table properties and of the maintenance that runs
C: `OPTIMIZE` rewrote the table into larger files, which deletes the older versions of the table from the transaction log at the same moment
D: Time travel needs the table to be a managed table, and the older versions of an external table are never readable after thirty days
K: A
G: ## Two retention settings
Delta keeps two separate things:
- The **log** (`logRetentionDuration`, 30 days by default) is what `DESCRIBE HISTORY` shows.
- The **data files** that old versions reference are kept for `deletedFileRetentionDuration` (7 days by default). `VACUUM` deletes unreferenced files older than that threshold.
Time travel therefore works for roughly the past 7 days unless both settings were increased. A version can appear in the history while its files are already deleted.
## What to do
If the business needs longer time travel, raise both retention properties on the table (this raises storage cost), or keep a separate backup copy; table history is not an archive.
W: Different thresholds: the history entry survives with the log retention, but the data files were deleted by the weekly VACUUM after the shorter file retention, so the version cannot be read any more.
X: B=24-hour limit: there is no fixed 24-hour limit. The window follows the file retention property, 7 days by default, and can be configured.
C=OPTIMIZE: compaction writes new files and marks the old ones as removed in a new commit, but older versions stay readable until VACUUM deletes the files.
D=Managed vs external: time travel works on both types as long as the files exist. There is no 30-day rule tied to the table type.
T: History (30 days) and time travel files (7 days) have different retention; VACUUM removes files, so extend both properties if you need longer time travel.
V: Delta Lake

S: A team creates a table with `CREATE TABLE main.sales.orders (id BIGINT, amount DECIMAL(10,2))` and no `USING` clause in a Unity Catalog enabled workspace. In which storage format is the table created?
A: Parquet, because it is the open file format that Spark uses when a table definition does not name any other format
B: Delta Lake, because it is the default table format on Databricks when the format is not specified
C: CSV, because the schema contains only simple types and Spark writes a delimited text file when no format is named

Delta Lake is the optimized storage layer under tables on Databricks. It extends Parquet data files with a file-based transaction log, which adds ACID transactions, time travel and scalable metadata handling. It is open source and is the default format for all operations on Databricks: unless you name another format, tables are Delta tables.

@ DBX-DEA D1 T1.1 applied definition
S: In a workspace that uses Unity Catalog, an engineer wants to query the table `customers` that belongs to the schema `crm` of the catalog `prod`. Which reference follows the Unity Catalog object model?
A: `SELECT * FROM crm.prod.customers`, since the schema is always named first and the catalog second
B: `SELECT * FROM prod.customers.crm`, since the table name sits between the catalog and the schema
C: `SELECT * FROM prod.crm.customers`, using the three-level namespace catalog, schema and table
D: `SELECT * FROM metastore.prod.crm.customers`, using the metastore name as an extra prefix before the catalog
K: C
G: ## The Unity Catalog hierarchy
Unity Catalog is the governance layer for data and AI. Its securable objects follow a three-level namespace: `catalog.schema.object`.
- The **catalog** is the top container, often one per environment or domain (`prod`, `dev`).
- The **schema** (database) groups tables, views, volumes and functions.
- The **object** is the table, view, volume or function.
Permissions are granted on these objects and inherit downward: a privilege granted on a catalog applies to the schemas and tables inside it. The metastore sits above the catalogs and is attached to workspaces, but it is not part of the name you type.
W: Three-level namespace: `prod.crm.customers` lists the catalog first, then the schema, then the table, which is how Unity Catalog resolves object names.
X: A=Schema first: the order is the reverse; the catalog is the outermost container, so `crm.prod.customers` would look for a catalog named `crm`.
B=Table in the middle: the table is the last part of the name. This order would look for a schema named `customers`.
D=Metastore prefix: a table name has three parts. The metastore is attached to the workspace and is never written in the name.
T: Unity Catalog names are catalog.schema.object, and privileges inherit from catalog down to the table.
V: Unity Catalog

@ DBX-DEA D1 T1.1 applied comparison
S: A company runs five Databricks workspaces for different teams and needs one place to define who can read which tables, to see lineage and to audit access, regardless of the workspace used. Which platform component provides this?
A: Unity Catalog, the governance layer that provides centralized access control, lineage, auditing and data discovery across workspaces
B: The Hive metastore of each workspace, which stores table definitions locally and is shared automatically with every other workspace
C: Delta Lake's transaction log, which records the grants of every user together with the data files of each table
D: Cluster access modes set on the compute of each team, which apply one common permission model to every workspace
K: A
G: ## What each component does
- **Delta Lake** is the storage layer: Parquet files plus a transaction log for ACID and time travel. It defines how a table stores data, not who may read it.
- **Unity Catalog** is the governance layer. It provides centralized access control, lineage, auditing and data discovery across the workspaces attached to a metastore. Admins grant privileges once (`GRANT SELECT ON TABLE prod.crm.customers TO analysts`) and every attached workspace enforces them.
- **Compute** (clusters, SQL warehouses, serverless) executes queries and enforces the governance defined in Unity Catalog.
Per-workspace stores cannot give a single view: each keeps its own definitions and permissions.
W: Unity Catalog: it is attached to several workspaces, so access rules, lineage and audit records are defined and viewed in one place.
X: B=Workspace Hive metastore: this legacy store is local to one workspace and is not shared automatically, so governance would be duplicated five times.
C=Transaction log: it records table commits (adds and removes of files), not user privileges, and it has no lineage or audit view across tables.
D=Cluster access modes: they control how a cluster isolates users, but they do not hold grants, lineage or audit data shared across workspaces.
T: Delta Lake stores and versions table data; Unity Catalog governs it centrally across workspaces.
V: Unity Catalog

@ DBX-DEA D1 T1.2 applied tradeoff
S: A nightly ETL notebook runs on an all-purpose cluster that three engineers also use for ad hoc work. The cluster is idle most of the day, and the team wants to lower cost without changing the code. Which change fits best?
A: Run the notebook as a Lakeflow Jobs task on job compute, or serverless compute for jobs, so resources exist only while the run lasts
B: Keep the all-purpose cluster running all day with a larger node type, so the nightly run finishes sooner and ends before the day begins
C: Move the notebook to a SQL warehouse, which is the compute that Databricks designed for scheduled Python data engineering code

D=Fixed workers: removing autoscaling does not stop idle charges, because the fixed-size cluster keeps all workers running until it is terminated.
T: Scheduled, non-interactive pipelines belong on job compute or serverless jobs, not on a shared all-purpose cluster.

S: Two engineers use the same shared Git folder. After one of them switched the folder to a different branch, the other found notebooks suddenly showing different code. How should the team avoid this?
A: Give each engineer their own Git folder cloned from the remote, with Git operations done only by its owner
B: Lock the shared folder so that only workspace admins may edit it, and ask engineers to send code in a ticket

G: ## Why one Git folder has one working branch
A Git folder is a local checkout, and it has one current branch. If other users have access to the folder, changing the branch changes it for everyone who shares it in the same workspace. That is why the guidance is that only one user performs Git operations on each Git folder; multiple users doing so can cause branch management problems like this one.
## The fix

X: B=Admin-only lock: it blocks collaboration instead of fixing the cause, and engineers would no longer be able to develop in the workspace.

D=Disabling pull: this stops engineers from getting teammates' commits and does not prevent branch switches from changing the shared files.

G: ## Production Git folders
User-level Git folders under `/Workspace/Users/` are local checkouts for development. A **production Git folder** is different:
- Created by an admin outside user folders, on a deployment branch (for example `release`).
- Users get run-only access (`Can Run`); only admins and a service principal that automation uses may update it.

@ DBX-DEA D5 T5.2 applied use-case
S: A bundle deploys a job that writes to a schema. The schema must be `etl_dev` for the `dev` target and `etl_prod` for `prod`, with `dev` as the default. The team wants one job definition, not two. Which approach follows the bundle configuration model?
A: Declare a variable `schema_name` with a default, reference it as `${var.schema_name}`, and set `variables` for the `prod` target
B: Copy the bundle folder into two projects, one per environment, and replace the schema name in the job file of each copy

G: ## Variables and target overrides

@ DBX-DEA D5 T5.2 applied comparison
S: A bundle declares `variables: {warehouse_size: {default: Small}}` and the `prod` target sets `warehouse_size: Large` under its `variables`. A CI pipeline runs `databricks bundle validate -t prod --var="warehouse_size=Medium"` with `BUNDLE_VAR_warehouse_size=XL` also set. Which value does the CLI use?

C: Small, because the default is the only value that can pass validation
D: Medium, because the `--var` option is checked first, before environment variables and target values

G: ## Precedence of variable values
The CLI looks for a variable's value in this order and stops at the first value it finds:
- The `--var` option of the `bundle` command.
- Environment variables starting with `BUNDLE_VAR_`.
- The `.databricks/bundle/<target>/variable-overrides.json` file, if it exists.
- The `variables` mapping within `targets` in the configuration files.
- The `default` in the top-level variable definition.
So command-line input beats environment variables, which beat files, target values and defaults. This lets CI pass a one-time value without editing YAML. If a variable has no default and no source provides a value, you must supply one.

C=Default: the default is the last fallback and is used only when nothing else provides a value.
T: Variable precedence: --var, then BUNDLE_VAR_ environment, then variable-overrides.json, then target variables, then default.

@ DBX-DEA D5 T5.2 applied tradeoff
S: A job defined at the top level of a bundle has a job cluster with `job_cluster_key: main` and 2 workers. The `prod` target should use 8 workers on the same cluster, keeping every other setting. How is this expressed?
A: Declare a second job named like the first in the `prod` target, which then runs next to the original job after deployment
B: Redefine the whole `resources` block under `prod`, since a target replaces the top-level resources and nothing is merged
C: Put `num_workers: 8` under a job_clusters entry with `job_cluster_key: main` in the `prod` target's job resource, which overrides that setting
D: Set `num_workers` in the top-level `variables` mapping, which automatically changes the job cluster for the last-deployed target
K: C
G: ## Overriding with target settings
Settings in a target are merged with the top-level settings, and where the same setting appears in both, the target wins. Items in lists are matched by key so only the changed fields need repeating:
- Job clusters are matched by `job_cluster_key`.
- Job tasks are matched by `task_key`.
- Pipeline clusters are matched by `label`.
```
targets:
  prod:
    resources:
      jobs:
        my_job:
          job_clusters:
            - job_cluster_key: main
              new_cluster:
                num_workers: 8
```
Everything else about the cluster, such as `spark_version`, comes from the top-level definition.
W: Matching key under the target: the `main` job cluster is joined with the top-level one and `num_workers` from the target takes precedence, leaving other settings unchanged.
X: A=Second job: this would create another job instead of changing the cluster of the existing one.
B=Replace all resources: target settings are merged with top-level settings, so repeating everything is unnecessary and duplicates the definition.
D=Top-level variable alone: a variable changes a value only where it is referenced with `${var.name}`; it does not rewrite the cluster by itself.
T: Join by job_cluster_key (or task_key) in the target to override only the differing settings.
