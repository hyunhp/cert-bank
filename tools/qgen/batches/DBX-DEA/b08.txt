@ DBX-DEA D6 T6.3 applied troubleshooting
S: A nightly join-and-aggregate job has one stage that runs for 40 minutes while the rest finish in minutes. On the stage page in the Spark UI, the Summary Metrics table shows a median task duration of 20 seconds, a 75th percentile of 25 seconds and a maximum of 38 minutes. The cluster has 64 cores and most of them sit idle during the last minutes of the stage. What does this pattern indicate?
A: Data skew: a few tasks process far more data than the others, so the cores that finish early wait for the long tasks
B: Disk spill: every task ran out of execution memory and wrote its data to local disk before the stage could finish
C: Too many shuffle partitions: the tiny median task time proves that Spark created more tasks than the stage needed
D: A cold disk cache: the first reads of the stage were slow, which lifts the maximum duration without affecting the 75th percentile
K: A
G: ## Reading the stage page
Spark splits every stage into tasks, one per partition, and a stage is finished only when its slowest task is finished. The Summary Metrics table of the stage page shows the distribution of task durations: minimum, 25th percentile, median, 75th percentile and maximum.
## Skew
Skew means a few partitions hold much more data than the rest, for example because a few key values dominate a join or group-by. Those tasks run long while the other cores sit idle, which wastes cluster capacity and stretches the job. Databricks suggests comparing the maximum with the 75th percentile: a maximum that exceeds the 75th percentile by about 50% or more indicates possible skew. In a healthy stage the two are close.
Typical fixes are adaptive query execution (AQE) skew handling for sort merge joins, salting the hot keys or pre-aggregating, clustering the source table, or a `REBALANCE` hint when the stage writes a table.
W: Data skew: a maximum of 38 minutes against a 75th percentile of 25 seconds is far beyond the 50% rule of thumb, and the idle cores at the end of the stage show that only a few long tasks were left running.
X: B=Disk spill: spill would show up as spill statistics in the stage details and would slow many tasks, not leave a median of 20 seconds with a single extreme maximum.
C=Too many shuffle partitions: small tasks are not harmful by themselves, and a tiny median would not create a 38-minute outlier; the outlier is a partition that holds far too much data.
D=Cold disk cache: a cold cache slows the first reads of many tasks evenly, and it would not leave most cores idle while a handful of tasks keep running for tens of minutes.
T: A maximum task duration far above the 75th percentile (about 50% or more) on the stage page means skew; look for hot keys or uneven partitions.

@ DBX-DEA D6 T6.3 applied troubleshooting
S: A join-heavy batch ETL job is slow. The stage page of the longest stage shows spill statistics (data written from memory to disk), and task durations are similar across the stage, so there is no skew. The workers are many small instances. Which change addresses the cause most directly?
A: Use fewer, larger worker instances with more memory, so more shuffle data fits in execution memory before it must be written to disk
B: Increase the number of workers while keeping the same small instance type, so more tasks run in parallel on identical memory
C: Enable the disk cache on the workers, because a cache holds shuffle data in memory and removes the need to spill
D: Cast every column to STRING before the join, so Spark can use a simpler row format with a smaller memory footprint
K: A
G: ## What spill is
Spark uses execution memory for shuffles, joins, sorts and aggregations. When a task needs more than it has, Spark writes intermediate data from memory to local disk and reads it back later. This is called spill. It works, but it is expensive, and it is most common during shuffles. The stage details at the top of the stage page show spill statistics only when the stage spilled; if none appear, there was no spill.
## Typical remedies
- Use auto-optimized shuffle (`spark.sql.shuffle.partitions=auto`) so Spark sizes the shuffle partitions from the plan and input size.
- Reduce the data held in memory: fewer rows or columns, and avoid very large string, array, map or struct columns.
- Increase executor memory. For complex batch ETL with joins over several tables, use fewer, larger workers: this also reduces the amount of data shuffled between machines.
- For streaming queries, limit the batch size so micro-batches do not cause spill.
W: Fewer, larger workers: each task gets more execution memory, so less data spills to disk, and a larger share of the join happens inside a single machine instead of being shuffled over the network.
X: B=More small workers: parallelism rises, but each executor keeps the same memory and more of the join data is shuffled between machines, so spill is not removed.
C=Disk cache: the disk cache speeds up repeated reads of remote files on local SSDs; it does not hold shuffle data and does not give execution more memory.
D=Casting to STRING: strings usually need more memory than numeric or date types, so this raises memory use and can make spill worse.
T: Spill means execution memory ran short: give tasks more memory per core (fewer, larger workers), shrink the data in memory, or let Spark choose shuffle partitions with `auto`.

The longest stage in the Spark UI shows a very large Input column and almost no shuffle or output, there is no skew or spill, and throughput per core is around 3 MB per second. The table has no clustering. What should the engineer do to cut the stage time?
A: Cluster the table on `store_id` with liquid clustering so that data skipping lets the stage read far fewer files
B: Raise `spark.sql.shuffle.partitions` to 2000 so that the large input is divided among more shuffle tasks
C: Add a `REBALANCE` hint to the query so that Spark splits oversized output partitions evenly
D: Increase the executor memory so that the input data stays in memory instead of spilling to disk

The I/O columns of the stage table (Input, Output, Shuffle Read, Shuffle Write) show where the stage spends its time. A rough rule from the Databricks guide: take the largest value, divide by the total number of cores and by the stage duration; if the result is about 3 MB per second per core, the stage is probably I/O bound.
- High input: the stage reads a lot of data. Store data in Delta, use liquid clustering for better data skipping, make the query more selective, use Photon, use the disk cache for repeated reads, or add compute.
- High output: reduce rewrites (optimize merges, use deletion vectors), use Photon, or add compute.
- High shuffle: set `spark.sql.shuffle.partitions` to `auto`.

Liquid clustering organizes files by the clustering keys, so a filter on `store_id` can skip files whose min/max statistics rule them out.
W: Liquid clustering on `store_id`: the stage is limited by input, and clustering lets the selective filter skip most files so that much less data is read.
X: B=More shuffle partitions: the stage has almost no shuffle, so this setting is not the bottleneck and would only create more, smaller tasks.
C=REBALANCE hint: it splits skewed output partitions when a stage writes a table; this stage is dominated by input and shows no skew or large output.
D=More executor memory: that fights spill, but the stage shows no spill, so extra memory would not make the file reads any smaller.
T: Read the I/O columns first: large Input points to data layout (clustering, selective filters, Photon), large Shuffle to `spark.sql.shuffle.partitions=auto`, large Output to fewer rewrites.

@ DBX-DEA D6 T6.3 applied use-case
S: A shuffle-heavy aggregation stage reads 900 GB of shuffle data, and the stage page shows the Shuffle Read column as the largest I/O value. Task times are even and there is no spill. The team set `spark.sql.shuffle.partitions` to 200 years ago and never revisited it, and input sizes now change a lot from run to run. Which setting does Databricks recommend to reduce the shuffle time?
A: Set `spark.sql.shuffle.partitions` to `auto` so that Spark picks the number of shuffle partitions from the query plan and input data size
B: Set `spark.sql.shuffle.partitions` to 1 so that no data has to be exchanged between executors during the aggregation
C: Set `spark.sql.autoBroadcastJoinThreshold` to -1 so that every aggregation avoids the shuffle by broadcasting its input
D: Set `spark.sql.adaptive.enabled` to false so that the plan is fixed and the same number of partitions is used on every run
K: A
G: ## High shuffle on the stage page
A stage with large Shuffle Read or Shuffle Write values spends much of its time moving data between executors for joins and aggregations. A fixed shuffle partition count is a poor fit when input size varies: too few partitions give huge tasks (and spill), too many give lots of tiny tasks.
## What Databricks recommends
Set `spark.sql.shuffle.partitions` to `auto` (auto-optimized shuffle). Spark then chooses the number of shuffle partitions based on the query plan and the input data size, together with adaptive query execution (AQE), which can coalesce small shuffle partitions at runtime.
W: `auto` for shuffle partitions: Spark sizes the partitions from the plan and the data volume of each run, so a changing input no longer runs against a stale fixed number.
X: B=A single partition: a shuffle still happens, and the whole 900 GB would be handled by one task on one core, which makes the stage slower and causes spill.
C=Broadcast threshold of -1: this turns automatic broadcast joins off; it does not remove the shuffle of an aggregation and makes joins shuffle more, not less.
D=Disabling AQE: AQE is what adapts partition counts and handles skew at runtime; turning it off removes that help, and a fixed plan is exactly the problem here.
T: For high shuffle read/write, use `spark.sql.shuffle.partitions=auto` instead of a hand-tuned constant.

@ DBX-DEA D6 T6.3 advanced troubleshooting
S: A sort merge join stage shows skew: the maximum task duration is many times the 75th percentile. Adaptive query execution is on, yet the skewed partitions, about 150 MB each, are not being split. A colleague notes the skewed partitions are smaller than the AQE skew thresholds. Which action fits?
A: Lower `spark.sql.adaptive.skewJoin.skewedPartitionThresholdInBytes` (and the factor if needed) so AQE treats these partitions as skewed
B: Add a broadcast hint on the large side of the join, because AQE splits skewed partitions of broadcast joins first
C: Turn AQE off and set the shuffle partitions to 1, because Spark then no longer compares partition sizes with thresholds
D: Increase `spark.sql.adaptive.skewJoin.skewedPartitionThresholdInBytes` so that more partitions qualify as skewed
K: A
G: ## How AQE handles skew
For sort merge joins and shuffle hash joins, adaptive query execution can split a skewed shuffle partition into smaller ones at runtime. It does this only when a partition exceeds both of its size thresholds: a factor over the median partition size (`spark.sql.adaptive.skewJoin.skewedPartitionFactor`) and an absolute size (`spark.sql.adaptive.skewJoin.skewedPartitionThresholdInBytes`).
- If the skewed partitions are below the thresholds, lower the thresholds so that they qualify.
- Broadcast joins are never skew-optimized, and the join type determines which side AQE can optimize.
- If a few key values hold most of the data, salting the keys or pre-aggregating in two stages also works, and liquid clustering helps when the skew comes from the layout of a stored table.
W: Lowering the threshold: a partition is split only if it is larger than the threshold, so a lower value lets the 150 MB partitions qualify as skewed.
X: B=Broadcast hint on the large side: broadcast joins are never skew-optimized by AQE, and broadcasting a large table would overload memory.
C=AQE off and one partition: without AQE no skew split happens at all, and a single shuffle partition concentrates everything on one task.
D=Raising the threshold: the threshold is a minimum size a partition must exceed; raising it makes fewer partitions qualify, which is the opposite of what is needed.
T: AQE splits a skewed partition only when it exceeds both skew thresholds, so lower the thresholds when the skewed partitions are smaller than the defaults.

@ DBX-DEA D6 T6.4 applied use-case
S: A 5 TB events table is clustered with `CLUSTER BY (customer_id)`. Analysts now filter mostly on `event_date` and `country`, so the team runs `ALTER TABLE events CLUSTER BY (event_date, country)`. The command finishes immediately, but queries on the new keys are still slow for old data. What explains this and what is the next step?
A: Changing keys only affects newly written data; run `OPTIMIZE events FULL` to recluster the existing files with the new keys
B: The table must be dropped and recreated, because clustering keys of a Delta table cannot be changed after creation
C: Clustering keys are applied by `VACUUM`, so run `VACUUM events` to rewrite the old files with the new layout
D: Old data is reclustered by the next `OPTIMIZE events ZORDER BY (event_date, country)`, which replaces the clustering keys
K: A
G: ## Liquid clustering and changing keys
Liquid clustering replaces Hive-style partitioning and `ZORDER`. A table is clustered by keys set with `CLUSTER BY`, and unlike partitioning you can redefine the keys later with `ALTER TABLE ... CLUSTER BY (...)` without rewriting the existing data.
## Why old data stays slow
The `ALTER` only changes the table metadata. Existing files keep their old layout, and a normal `OPTIMIZE` is incremental: it rewrites only what is needed to cluster new data. To recluster everything under the new keys, run:
```
OPTIMIZE events FULL;
```
On a large table that has not been clustered on the new keys, this can take hours, so plan it. Clustering is not compatible with `ZORDER`.
W: `OPTIMIZE ... FULL`: it reclusters existing files that were clustered with other keys or not at all, so data skipping on `event_date` and `country` works for old data too.
X: B=Drop and recreate: keys can be changed with `ALTER TABLE ... CLUSTER BY` on the live table; a rewrite is not required.
C=VACUUM: it deletes data files that are no longer referenced; it never reorganizes the layout of live files.
D=ZORDER: liquid clustering is not compatible with `ZORDER`, and a `ZORDER BY` does not define the clustering keys of the table.
T: After changing clustering keys, run `OPTIMIZE ... FULL` to recluster existing data; a plain OPTIMIZE only clusters data that is not yet clustered.

Predictive optimization automatically runs `OPTIMIZE` (including incremental clustering), `VACUUM` and `ANALYZE` on Unity Catalog managed tables, using serverless compute for jobs. @ DBX-DEA D6 T6.4 applied use-case
S: Predictive optimization is enabled for the catalog `prod`. The schema `prod.scratch` holds short-lived tables that are rewritten every hour, and the team does not want any maintenance compute spent on them, while all other schemas should stay enabled. Which statement fits?
A: `ALTER SCHEMA prod.scratch DISABLE PREDICTIVE OPTIMIZATION`

G: ## Inheritance of predictive optimization
Predictive optimization can be enabled for an account, catalog, schema or table. Managed tables inherit the account value by default, a catalog's setting flows to its schemas, and a schema's setting flows to its tables. You can override the inherited value at a lower level with `ENABLE`, `DISABLE` or `INHERIT`:

```
ALTER CATALOG c { ENABLE | DISABLE | INHERIT } PREDICTIVE OPTIMIZATION;

```
To change it you need to be the owner or have `MANAGE` on that object (account admin for the account).
W: Schema-level `DISABLE`: it overrides the inherited catalog value for `prod.scratch` and every table in it, and leaves other schemas enabled.
X: B=Catalog-level `DISABLE`: it turns the feature off for the entire catalog, which also removes it from the schemas that should stay enabled.
C=`INHERIT`: it resets the schema to the catalog value, which is enabled, so the scratch tables would still be maintained.
D=Wildcard table syntax: `ALTER TABLE` names one table; there is no wildcard form, and a schema-level setting is the right scope.
T: Override predictive optimization at the narrowest level that fits: `ALTER SCHEMA ... DISABLE PREDICTIVE OPTIMIZATION` for one schema.

@ DBX-DEA D6 T6.5 applied troubleshooting
S: After a Delta pipeline team added a cluster-scoped init script that installs an OS package, every start of their classic cluster fails during launch. The script ends with a failing command, and the cluster event log shows an init script failure. What is the most effective way to find the cause?
A: Configure cluster log delivery and read the init script log, because a non-zero exit code of the script fails the launch
B: Increase the driver node size, because init scripts that exceed driver memory terminate the cluster launch
C: Move the script to a global init script, because global scripts ignore non-zero exit codes during startup

G: ## Init scripts run before Spark
An init script is a shell script that runs on every cluster node during startup, before the Spark driver or executor JVM starts. Cluster-scoped init scripts are defined in the cluster configuration and apply to clusters you create and those created for jobs. Scripts run in order.
## Failure behaviour
If a cluster-scoped init script returns a non-zero exit code, the cluster launch fails. To troubleshoot it, configure cluster log delivery and examine the init script log. Databricks also recommends using compute policies or built-in features instead of init scripts where possible, and installing libraries via policies and not via init scripts. Serverless compute does not support init scripts.
W: Log delivery plus init script log: it shows the script output and exit code, which is the evidence needed to fix the failing command.
X: B=Larger driver: the failure is the exit status of the script, not a memory limit of the driver, so resizing it does not help.
C=Global script: switching the script type does not stop a failing command from being a failure, and Databricks recommends cluster-scoped or policy-managed scripts over global ones.
D=Serverless: serverless compute does not support init scripts, so the script would not run at all, which changes the setup rather than finding the cause.
T: A cluster-scoped init script with a non-zero exit code fails the launch; use cluster log delivery and the init script log to debug it.

@ DBX-DEA D6 T6.5 applied troubleshooting
S: Right after a new AWS-based workspace was deployed into the customer's own VPC, the first classic cluster never becomes ready. After roughly 30 minutes the event log reports that the compute plane network is misconfigured and that the node daemon ping timed out. What should the engineer check first?
A: Routing and firewall rules, to confirm the instances can reach the Databricks control plane, for example with `nc -zv` tests

X: B=Shuffle partitions: this is a Spark runtime setting evaluated while queries run; it has no effect on whether instances can connect to the control plane.
C=Delta table properties: tables are read only after the cluster is running, so they cannot cause a startup ping timeout.

@ DBX-DEA D6 T6.5 applied troubleshooting
S: A notebook on a classic cluster upgrades a library with `%pip install --upgrade pandas` in cell 1. In cell 2, `pandas.__version__` still prints the old version, although the install log reports success. What is the cause and the fix?
A: `%pip` does not restart the Python process; call `dbutils.library.restartPython()` so the notebook imports the new version
B: The install only applies to the next cluster start, so the cluster must be terminated and started again
C: `%pip` installs only on the driver of another cluster, so the library must be added through the Jobs API
D: Libraries from PyPI always lose to the copy in Databricks Runtime, so the only option is to upload the wheel file to DBFS
K: A
G: ## Notebook-scoped libraries
`%pip install` creates a Python environment scoped to the notebook session. Other notebooks on the same compute are not affected, and the libraries do not persist: they must be installed again for every session. Place the `%pip` commands at the top of the notebook.
## Why the old version appears
`%pip` commands do not restart the Python process automatically. A package that was already imported in the running process stays in memory, so the new version is not seen. After installing or updating a package, call `dbutils.library.restartPython()` to restart the Python process (this resets Python state, so run it before the rest of the code). Upgrading core packages such as IPython with `%pip` may break features; in that case restart the cluster or start a new session.
W: Restart the Python process: the new package files are installed, but the running interpreter still holds the old module, so a restart makes the notebook import the new one.
X: B=Cluster restart: notebook-scoped installs take effect in the session, so a full restart is not needed.

`ALL PRIVILEGES` grants all privileges applicable to the object at the time access is checked, and also the privileges inherited by child objects. It does not include `EXTERNAL USE SCHEMA`, `EXTERNAL USE LOCATION`, `MANAGE` or `READ METADATA`, to avoid data exfiltration or privilege escalation.
## Managing privileges
- `MANAGE` lets a principal manage privileges, transfer ownership, rename and drop the object.
- Owners can always grant. Make the group the owner or grant `MANAGE` if it should hand out access.
- Revoking `ALL PRIVILEGES` revokes the grant and the privileges implied by it, but leaves `MANAGE` and the other excluded privileges in place.
- A group is a valid grantee and can own objects.
