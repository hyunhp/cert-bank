@ DBX-DEA D1 T1.1 expert troubleshooting
S: On Monday a faulty job overwrote rows in the managed Delta table `silver.orders`, and an engineer ran `RESTORE TABLE silver.orders TO VERSION AS OF 812`, which reported success. A separate Structured Streaming job reads `silver.orders` as a stream with `skipChangeCommits` disabled and appends every new file's rows to `gold.order_events`, which feeds billing. After the restore, `gold.order_events` contains about 3 million duplicate rows, all from files that had been part of versions up to 812. The source table history shows only the bad write and the RESTORE since Friday, and billing must not see duplicates again during future restores. Which explanation and change fit the evidence?
A: The restore commit re-adds old files with `dataChange` set to true, so the stream reads them as new data; write gold with an insert-only MERGE by key
B: The restore commit re-adds old files with `dataChange` set to false, so the stream skipped them and gold lost rows; replay the stream from version 812
C: The restore rewrote every file of the table into new files, so the stream read the whole table again; run VACUUM after each restore to remove the copies
D: The restore reset the table's streaming checkpoint to version 812, so the stream read every later version again; keep checkpoints outside the table location
K: A
G: ## What RESTORE writes
`RESTORE` returns a Delta table to an earlier version by committing a **new version** that removes the files added since then and adds back the files of the old version. The history docs warn that restore is a data-changing operation: its log entries have `dataChange` set to `true`.
## Effect on streaming readers
A Structured Streaming query that reads the table processes new commits as new data. The re-added files arrive in a commit with `dataChange = true`, so the stream treats them as **newly added data and processes them again**, which can create duplicates downstream. The checkpoint of the reader is unaffected; it lives with the stream, not in the table.
## Protecting the downstream table
Because a restore can replay rows, the downstream write must be idempotent: for example an insert-only MERGE on the event key (deduplicating the micro-batch first) instead of a blind append.
W: dataChange true on restore: the stream sees the re-added files as new data and appends them again; an idempotent write by key in gold absorbs future restores.
X: B=dataChange false: restore commits are documented with dataChange true, and the evidence is duplicates, not missing rows.
C=Full rewrite plus VACUUM: restore re-adds existing files rather than rewriting the table, and VACUUM removes unreferenced files, not duplicate rows already in gold.
D=Checkpoint reset: a stream's checkpoint belongs to the stream, not the source table, and RESTORE does not touch it.
T: RESTORE commits re-added files as data changes, so streaming readers reprocess them; make downstream writes idempotent.

S: A nightly job upserts customer changes into `silver.customers` with `MERGE INTO silver.customers t USING staging.customer_changes s ON t.customer_id = s.customer_id WHEN MATCHED THEN UPDATE SET * WHEN NOT MATCHED THEN INSERT *`. Tonight it failed with: "Cannot perform Merge as multiple source rows matched and attempted to modify the same target row". `staging.customer_changes` is rebuilt every night from a CRM export, and the export now contains several change rows per customer when a customer was edited more than once in a day; each row has `changed_at`. Silver must hold the latest state per customer, the MERGE must stay one statement, and the CRM export cannot be changed. Which fix fits?
A: Add `WHEN MATCHED AND s.changed_at > t.changed_at` to the MERGE, so that only the newer source rows update a target row
B: Use as the MERGE source a subquery that keeps one row per `customer_id` with the latest `changed_at`, using `row_number()` and `QUALIFY`
C: Run the MERGE once for each distinct `changed_at` value of the night, in ascending order, so that each run sees at most one row per customer

G: ## The MERGE rule behind the error
Only **one source row may match a given target row**. If several source rows match and the merge tries to update the same target row, the operation is ambiguous (which row should win?) and MERGE fails. The docs recommend preprocessing the source to remove the possibility of multiple matches.
In recent runtimes, MERGE evaluates both the ON clause and the WHEN MATCHED conditions to detect duplicate matches. A condition such as `s.changed_at > t.changed_at` can still let **two** newer source rows qualify for the same target row, so it does not remove the ambiguity.

`SELECT * FROM staging.customer_changes QUALIFY row_number() OVER (PARTITION BY customer_id ORDER BY changed_at DESC) = 1` keeps the latest change per customer. Used as the MERGE source, it gives exactly one candidate per target row, in one statement.
W: Latest row per key as the source: each customer has one source row, so the ambiguity is gone and silver gets the latest state in a single MERGE.
X: A=Newer-than condition: two edits on the same day can both be newer than the target, so the same target row is still matched by several source rows.
C=One MERGE per timestamp: it works only if timestamps align across customers, multiplies the runs, and is no longer one statement.
D=INSERT OVERWRITE with DISTINCT: it replaces silver with only tonight's changes, and DISTINCT does not collapse rows that differ in `changed_at`.
T: When MERGE reports multiple source rows for one target row, deduplicate the source to one row per key before merging.

B: Add `seq_no DESC` after `event_ts DESC` in the window ORDER BY, so that ties on the timestamp are broken by the carrier's sequence
C: Add `ORDER BY shipment_id` to the outer query, so that Spark processes the rows in a fixed order and row_number assigns the same numbers

G: ## Ties and row_number
`row_number()` assigns a unique sequential number in the order of the window. The docs say: unlike `rank` and `dense_rank`, row_number **breaks ties**, and **if the order is not unique, the result is non-deterministic**. Add a column that orders rows within the tie. A monotonically increasing `seq_no` per shipment is ideal: `ORDER BY event_ts DESC, seq_no DESC`. Now exactly one row is first, every time.

- `rank()` gives tied rows the same rank, so `= 1` returns **two** rows per shipment, which breaks the one-row-per-shipment rule.
- Sorting the outer result or caching does not change the order within each window partition.
W: Tie-breaker in the window: the order becomes unique, so the same event is numbered 1 every run and the status stops flipping.
X: A=rank(): tied events both get 1, so silver would hold two rows per affected shipment.
C=Outer ORDER BY: it sorts the final output; the numbering inside each partition is still undefined for ties.
D=Cache the source: the data is already unchanged; the non-determinism comes from the tie, not from different files.
T: `row_number()` over a non-unique order is non-deterministic; add a tie-breaker column.
