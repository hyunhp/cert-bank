@ DBX-DEA D3 T3.4 applied use-case
S: A silver table `customer_updates` receives several rows per `customer_id` because the source emits every change. Each row has an `updated_at` timestamp. The team needs exactly one row per customer, always the one with the latest `updated_at`. The current code is `df.dropDuplicates(["customer_id"])`, and the kept row changes from run to run. Which approach fixes this in SQL?
A: Rank rows with `row_number() OVER (PARTITION BY customer_id ORDER BY updated_at DESC)` and keep rank 1 with a `QUALIFY` clause
B: Run `SELECT DISTINCT customer_id, updated_at` so that only the newest timestamp for each customer remains in the output
C: Add `ORDER BY updated_at DESC` before the deduplication step so the first row seen by Spark is always the latest one
D: Replace the duplicate removal with `GROUP BY customer_id` and select the remaining columns without any aggregate functions
K: A
G: ## Removing duplicates by key
`dropDuplicates(["customer_id"])` and `SELECT DISTINCT` remove rows that repeat on the listed columns, but when two rows share the key and differ in other columns, Spark keeps whichever one it meets first. After a shuffle that order is not guaranteed, so the surviving row can change between runs.
## Deterministic "latest row per key"
Use a window function to number the rows inside each key and keep the first:
```
SELECT * FROM customer_updates
QUALIFY row_number() OVER (PARTITION BY customer_id ORDER BY updated_at DESC) = 1
```
`row_number()` gives each row a unique sequence number inside its partition, following the `ORDER BY`. `QUALIFY` filters on a window function result without a subquery.
W: row_number with QUALIFY: the window orders each customer's rows by `updated_at` descending and numbers them, so keeping number 1 always returns the most recent row, and ties are the only remaining ambiguity.
X: B=SELECT DISTINCT on two columns: it keeps every distinct pair of `customer_id` and `updated_at`, so a customer with several timestamps still has several rows, and the other columns are not even selected.
C=ORDER BY before deduplication: a sort earlier in the plan does not control which row `dropDuplicates` keeps, because the shuffle that follows reorders rows; Spark documents no ordering guarantee for the kept row.
D=GROUP BY without aggregates: columns that are neither grouped nor aggregated cannot be selected, so the query fails or loses the other columns, and nothing in it picks the latest row.
T: To keep a specific duplicate (such as the latest), rank with row_number over a partition and filter on rank 1; plain dropDuplicates and DISTINCT keep an arbitrary row.

@ DBX-DEA D3 T3.4 applied comparison
S: A silver table `contacts` has 1,000 rows. The `email` column is NULL in 200 of them, and the remaining 800 rows hold 600 different addresses. A data quality report must show how many contacts have an e-mail address on file. Which expression returns 800?
A: `count(email)`, which counts only the rows where the column is not NULL
B: `count(*)`, which counts the rows after removing the ones where any column is NULL
C: `count(DISTINCT email)`, which counts every non-NULL value including the repeated ones
D: `approx_count_distinct(email)`, which counts all non-NULL values using a faster algorithm
K: A
G: ## What each count form counts
- `count(*)` and `count(1)` count every row, NULLs included. Here that is 1,000.
- `count(expr)` counts the rows where `expr` is not NULL. Here that is 800.
- `count(DISTINCT expr)` counts the different non-NULL values. Here that is 600.
- `approx_count_distinct(expr)` estimates the number of different values, so it is close to 600, not 800.
A missing value is ignored by `count(expr)` and by most other aggregates; only `count(*)` counts rows regardless of content.
W: count(email): it skips the 200 NULL values and counts the other 800 rows, including the repeated addresses, which is exactly "contacts with an e-mail on file".
X: B=count(*): it counts all 1,000 rows and does not drop rows that contain NULLs; the description of removing rows is wrong.
C=count(DISTINCT email): it removes repeated addresses as well as NULLs, so it returns the 600 unique values rather than the 800 non-NULL rows.
D=approx_count_distinct: it estimates distinct values (about 600), not a total of non-NULL rows, and it is only approximate.
T: count(*) counts rows, count(col) counts non-NULL values, count(DISTINCT col) counts unique non-NULL values.

@ DBX-DEA D3 T3.4 advanced use-case
S: A dashboard shows daily unique visitors computed from a 4-billion-row `page_views` table. `count(DISTINCT visitor_id)` over several days takes long and uses a lot of memory. Product owners accept an error of about 2% in the displayed number. Which change reduces the cost most directly while meeting that requirement?
A: Use `approx_count_distinct(visitor_id, 0.02)` and group by day, which estimates distinct values with a bounded relative error
B: Use `count(visitor_id)` instead, which gives the number of unique visitors after the engine removes duplicates by itself
C: Use `count(DISTINCT visitor_id)` on a 2% random sample of the rows and display the sample result unchanged
D: Use `avg(visitor_id)` per day, because the average of the identifiers approximates the number of unique visitors
K: A
G: ## Exact versus approximate distinct counts
An exact `count(DISTINCT x)` must keep or shuffle every distinct value, which grows with cardinality. `approx_count_distinct(expr[, relativeSD])` uses the HyperLogLog++ algorithm: it keeps a small fixed-size sketch and returns an estimate. The default maximum relative standard deviation is 5%, and the optional second argument lowers it (a smaller value gives a more accurate but larger sketch).
## When to use it
Dashboards, monitoring and exploration can tolerate a known small error. Billing, reconciliation and compliance counts must stay exact.
W: approx_count_distinct with a relativeSD of 0.02: it replaces the memory-heavy exact distinct with a fixed-size HyperLogLog++ sketch, and the second argument sets the accepted error to the stated 2%.
X: B=count(visitor_id): it counts non-NULL rows, so a visitor with ten page views is counted ten times; no deduplication happens.
C=Distinct count on a sample: the result of a sample counts only the visitors who appear in the sample, so the figure is far below the real number and would have to be scaled with an unreliable estimate.
D=avg of identifiers: the mean of identifier values says nothing about how many different identifiers exist.
T: When a small known error is acceptable, approx_count_distinct(col, relativeSD) replaces exact count(DISTINCT) at much lower cost.

@ DBX-DEA D3 T3.4 applied troubleshooting
S: A gold report shows the average rating per product with `SELECT product_id, avg(rating) FROM reviews GROUP BY product_id`. Many reviews have `rating` NULL because the customer only left a text comment. A new analyst rewrites the metric as `avg(coalesce(rating, 0))` and the averages drop sharply. Which statement explains the difference?
A: `avg(rating)` ignores NULL values, while `coalesce(rating, 0)` turns unrated reviews into zeros that are included in the average
B: `avg(rating)` treats NULL as zero already, so the extra `coalesce` should not change results unless the data changed
C: `avg(rating)` raises an error whenever a group contains NULL, so the original query could not have returned results
D: `coalesce(rating, 0)` removes the rows with NULL from the group, so the denominator becomes smaller and the averages drop
K: A
G: ## Aggregates and NULL
Most aggregate functions skip NULL inputs. `avg(col)` sums the non-NULL values and divides by the number of non-NULL values; a group with only NULLs returns NULL. This is why a missing value is not the same as zero.
## Replacing NULL changes the meaning
`coalesce(rating, 0)` returns 0 when `rating` is NULL. Those rows now count as real ratings of 0, so the sum stays the same but the count grows, and the average falls. Only fill NULLs with a default when the business meaning really is "zero".
W: NULL is ignored by avg: the original query divides by the number of rated reviews, while the rewrite adds a zero rating for each comment-only review, which raises the denominator and lowers every average.
X: B=NULL treated as zero: avg does not do that; it skips NULLs, which is exactly why the two queries differ.
C=Error on NULL: avg handles NULL inputs without any error; it skips them, so the original query returns results.
D=coalesce removes rows: coalesce never removes rows; it substitutes a value, so the rows stay in the group and the count of values goes up, not down.
T: Aggregates such as avg and sum skip NULLs; filling NULL with 0 before aggregating changes the result.

@ DBX-DEA D3 T3.4 applied definition
S: During profiling of a silver DataFrame `df` in a notebook, an engineer needs count, mean, standard deviation, minimum, the 25th, 50th and 75th percentiles and maximum for the numeric columns, returned as a DataFrame. Which call does that?
A: `df.summary()`
B: `df.describe()`
C: `df.agg(F.count("*"))`
D: `df.dropDuplicates()`
K: A
G: ## Two profiling methods
- `DataFrame.describe()` returns count, mean, stddev, min and max.
- `DataFrame.summary()` returns the same statistics plus approximate percentiles; by default 25%, 50% and 75%. You can also pass the statistics you want, for example `df.summary("count", "min", "75%", "max")`.
Both return a DataFrame, so the result can be filtered or written like any other. The percentiles of `summary()` are approximate to keep the computation cheap on large data.
W: summary(): it produces count, mean, stddev, min, the three quartile percentiles and max for the numeric columns, in one result.
X: B=describe(): it computes count, mean, stddev, min and max but not the 25th, 50th and 75th percentiles, so the quartiles are missing.
C=agg with count: it returns a single number, the row count, and not the other statistics unless each one is written explicitly.
D=dropDuplicates(): it returns a DataFrame with duplicate rows removed, not statistics.
T: describe() gives count, mean, stddev, min, max; summary() adds approximate quartiles and lets you choose the statistics.

@ DBX-DEA D3 T3.4 advanced use-case
S: A Structured Streaming job reads events from a source that sometimes delivers the same event twice, up to 30 minutes apart. Every event has a unique `event_id` and an `event_time`. The job must drop duplicates without keeping unbounded state, and the two copies may carry slightly different `event_time` values. Which approach fits?
A: Apply `withWatermark("event_time", "1 hour")` and `dropDuplicatesWithinWatermark(["event_id"])`
B: Use `dropDuplicates(["event_id", "event_time"])` and no watermark, because the key then identifies every copy
C: Use `distinct()` after the read, because distinct deduplicates streams exactly the same way it does batch tables
D: Run `dropDuplicates(["event_id"])` in the batch pipeline only, because streams cannot be deduplicated
K: A
G: ## Duplicates in a stream
Structured Streaming provides exactly-once processing, but it does not remove duplicates that are already in the source. Deduplication needs state: the engine must remember the keys it has seen. Without a bound, that state grows forever.
## Bounding state with a watermark
A watermark (`withWatermark(column, delay)`) tells Spark how late data can be, so it can drop old state. `dropDuplicatesWithinWatermark(["event_id"])` removes duplicates on a unique identifier even when other fields such as the event time differ between copies, and it needs a watermark. Choose a delay greater than the largest gap between copies (here 30 minutes) to guarantee all duplicates are removed.
W: Watermark plus dropDuplicatesWithinWatermark: it deduplicates on `event_id` even though `event_time` differs, and the one-hour watermark exceeds the 30-minute gap while letting Spark discard old keys.
X: B=dropDuplicates on both columns: the copies have different event times, so the pair is different each time and no copy is removed; without a watermark the state would also grow without bound.
C=distinct() on a stream: distinct on a stream also needs state and a watermark, and deduplicating every column fails for copies whose columns differ.
D=Batch only: streams can be deduplicated with dropDuplicates and dropDuplicatesWithinWatermark; the statement is wrong.
T: Streaming deduplication needs state: use a watermark with dropDuplicatesWithinWatermark on a unique id, and set the delay above the maximum duplicate gap.

@ DBX-DEA D3 T3.5 applied troubleshooting
S: A batch job aggregates about 600 GB of data. In the Spark UI the shuffle stage of the `groupBy` has 200 tasks, each processing several GB, and the tasks spill heavily to disk. The cluster has enough cores to run many more tasks. The job uses DataFrame APIs only. Which setting is the most direct fix?
A: Increase `spark.sql.shuffle.partitions` (or set it to `auto`) so the shuffle creates more, smaller partitions
B: Increase `spark.default.parallelism` so the DataFrame shuffle uses more partitions
C: Lower `spark.sql.autoBroadcastJoinThreshold` so that the aggregation stage broadcasts less data to every executor
D: Decrease `spark.sql.shuffle.partitions` to 20 so fewer, larger tasks avoid scheduling overhead
K: A
G: ## Shuffle partitions
A shuffle (for `groupBy`, joins, `distinct`) redistributes rows into a fixed number of partitions, and each partition becomes one task. `spark.sql.shuffle.partitions` sets that number for DataFrame and SQL queries; the documented default is 200, and the value `auto` lets Databricks pick a number from the query plan and input size.
- Too few partitions: each task is large, memory runs out and tasks spill to disk.
- Too many partitions: many tiny tasks, with scheduling overhead and small output files.
Adaptive query execution (enabled by default) can coalesce small shuffle partitions after the shuffle, but the configured starting number still limits how finely the data is split here.
W: More shuffle partitions: raising `spark.sql.shuffle.partitions` (or using `auto`) cuts the data per task so each fits in memory and spill decreases.
X: B=spark.default.parallelism: it sets the default partition count for RDD operations such as `parallelize` and `reduceByKey`; DataFrame and SQL shuffles use the SQL setting, so the stage stays at 200 tasks.
C=Lower autoBroadcastJoinThreshold: that threshold only decides whether a join side is broadcast; this is an aggregation without a join and the setting does not touch the number of shuffle partitions.
D=Decrease to 20: that would put even more data in each task, so the spill gets worse.
T: spark.sql.shuffle.partitions controls the number of tasks after a DataFrame shuffle; too few gives spill, too many gives small tasks.

@ DBX-DEA D3 T3.5 advanced use-case
S: A classic-compute job joins a 20 GB fact table with a 150 MB dimension table. The query plan shows a sort merge join with a full shuffle of the 20 GB table, and the table statistics are accurate. The workers have plenty of memory, and the team does not want to change the SQL text. Which change makes Spark broadcast the dimension table automatically?
A: Set `spark.sql.autoBroadcastJoinThreshold` above 150 MB so the dimension qualifies for a broadcast
B: Set `spark.sql.autoBroadcastJoinThreshold` to `-1`, because that value forces every join to use a broadcast
C: Increase `spark.default.parallelism` to 150, so that the dimension table is split into many small broadcast pieces
D: Reduce `spark.sql.shuffle.partitions` to 1, so the single remaining partition can be broadcast to all workers
K: A
G: ## Automatic broadcast joins
In a broadcast hash join, Spark sends a copy of the small side to every executor and joins the large side in place, with no shuffle of the large table. Spark chooses it automatically when the estimated size of one side is below `spark.sql.autoBroadcastJoinThreshold`. A join hint such as `BROADCAST(table)` forces the choice regardless of that threshold, but it changes the query text.
## Risks of a high threshold
The broadcast table is collected on the driver and held in executor memory, so a threshold that is too high can cause out-of-memory errors. Raise it only to a size that the driver and executors can hold, and check the plan afterward. Adaptive query execution can also switch a sort merge join to a broadcast at runtime using its own adaptive threshold.
W: Raise autoBroadcastJoinThreshold: with accurate statistics showing 150 MB, a threshold above that size lets the planner pick a broadcast hash join and skip the shuffle of the 20 GB table, with no change to the SQL.
X: B=Threshold -1: that value disables automatic broadcast joins, which is the opposite of the goal.
C=Raise default parallelism: it is an RDD setting that has nothing to do with join strategy, and tables are not split into broadcast pieces.
D=Shuffle partitions of 1: that would move all shuffled data into one partition and does not make the planner broadcast anything.
T: A table is broadcast automatically when its size is under spark.sql.autoBroadcastJoinThreshold; raise it carefully, or use a hint, and set -1 only to disable.

@ DBX-DEA D3 T3.5 advanced tradeoff
S: A transformation on a classic job cluster spills a lot of shuffle data to local disk because each executor has too little memory per core. K: A
G: ## Where executor memory comes from
On Databricks, executor memory is determined by the worker instance type. Total executor memory decides how much data can sit in memory before it spills to disk; the ratio of memory to cores per worker also matters, because each running task shares the executor memory.
## Fix spill through compute choice
Databricks guidance says not to hardcode properties such as `spark.executor.memory` or `spark.dynamicAllocation.*` in compute or job definitions, because hardcoded values override built-in optimizations and often waste money or reduce performance. To give tasks more memory, pick a memory-optimized instance family or an instance with fewer cores per GB of memory, or reduce data per task with more shuffle partitions.
W: Memory-optimized workers: a different instance type raises memory per core within supported sizing, which is the recommended way to reduce spill without hardcoding executor settings.
X: B=Hardcode everywhere: the best practices page says the opposite; hardcoded Spark settings override Databricks optimizations.
C=Driver memory: spill during shuffles happens on executors using their local disks; the driver heap does not affect it.
D=Disable AQE: AQE re-optimizes plans from runtime statistics and typically reduces shuffle cost; it is not the cause of spill.
T: Fix executor memory pressure by choosing the instance type (memory per core) and adding shuffle partitions, not by hardcoding spark.executor.memory.

@ DBX-DEA D3 T3.6 applied use-case
S: A gold layer must offer a regional sales summary built from a join and an aggregation over silver tables with hundreds of millions of rows. B: A streaming table over the join, because it re-reads previous rows whenever the dimension changes

K: A
G: ## Streaming tables and changing dimensions
A streaming table reads each source row once. When it joins a stream with a dimension table, the join result is fixed at the time the row is processed; later changes in the dimension do not update rows already written. That can be useful for point-in-time history, and is described in the docs as potentially "fast but wrong" if you need current values.
## Materialized views recompute
A materialized view is always correct as of its last refresh: when the dimension changes, Databricks recomputes the affected parts of the result (incrementally when it can) so past orders reflect the new segment.
W: Materialized view: it keeps joins correct when the dimension changes, since refresh recomputes results for the affected rows.
X: B=Streaming table re-reading: a streaming table does not revisit processed rows when the dimension changes; only a full refresh would reprocess them.
C=Stream joins always correct: the docs state that joins in streaming tables do not recompute when dimensions change, so they can be stale.
D=Standard view stores results: a view stores no results at all; it recomputes each time and is not the object that precomputes.
T: Choose a materialized view when joins must stay correct as dimensions change; streaming tables freeze the join result at processing time.

S: A gold table `customer_360` is maintained by a Lakeflow Jobs task that must apply updates from several upstream systems with custom `MERGE INTO` logic, delete rows on request, and be written by more than one job. BI tools only read it. Which gold object is appropriate?

@ DBX-DEA D3 T3.7 applied use-case
S: A Lakeflow Declarative Pipelines silver streaming table `clean_orders` must not contain rows where `order_id` is NULL. The team wants those rows removed from the target automatically, and the number of dropped rows visible as a data quality metric. The pipeline must keep running. Which declaration fits?
A: `CONSTRAINT valid_order_id EXPECT (order_id IS NOT NULL) ON VIOLATION DROP ROW`
B: `CONSTRAINT valid_order_id EXPECT (order_id IS NOT NULL)` with no violation action
C: `CONSTRAINT valid_order_id EXPECT (order_id IS NOT NULL) ON VIOLATION FAIL UPDATE`
D: `CONSTRAINT valid_order_id CHECK (order_id IS NOT NULL)` added with `ALTER TABLE` after the pipeline run
K: A
G: ## Expectations in pipelines
An expectation is a named SQL boolean condition on a dataset in a pipeline (streaming table, materialized view or view). It has three parts: a name, a constraint and an action when a record violates it.
- Default (`EXPECT`, Python `expect`): warn. Invalid records are written to the target, and metrics count them.
- `ON VIOLATION DROP ROW` (Python `expect_or_drop`): invalid records are dropped before the write, and the count of dropped records is logged with the dataset metrics.
- `ON VIOLATION FAIL UPDATE` (Python `expect_or_fail`): an invalid record makes the update fail, and the run needs manual intervention.
W: DROP ROW: rows with a NULL id are removed before they reach the table, the dropped count is recorded as a metric, and the pipeline continues.
X: B=No action: that is the default warn behavior; invalid records are still written to the target, so NULL ids stay in the silver table.
C=FAIL UPDATE: the update stops on the first invalid record, which conflicts with the requirement that the pipeline keeps running.
D=CHECK constraint after the run: a Delta `CHECK` makes a write transaction fail when violated, and it is not a drop-and-count expectation; adding it later does not remove existing rows.
T: Use EXPECT for warn, ON VIOLATION DROP ROW to remove bad rows and count them, and FAIL UPDATE to stop the update.

- Fail: use when invalid data is unacceptable. The update fails, and for table updates the transaction is rolled back atomically, so the previous result remains. A person must fix the code or data before rerunning.

G: ## Enforced Delta constraints
Delta tables support two enforced constraint types:
- `NOT NULL` on a column.

When a write violates an enforced constraint the transaction fails with an error. `ALTER TABLE ... ADD CONSTRAINT` first verifies that all existing rows satisfy the new CHECK; if any row violates it, the statement fails and nothing is added.
