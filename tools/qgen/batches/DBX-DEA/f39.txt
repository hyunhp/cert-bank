@ DBX-DEA D6 T6.5 applied troubleshooting
S: A notebook on a classic cluster has already run `import pandas` in an earlier cell. Cell 1 then upgrades the library with `%pip install --upgrade pandas`, and in cell 2 `pandas.__version__` still prints the old version, although the install log reports success. What is the cause and the fix?
A: `%pip` placed the package on a different compute resource, so the library has to be attached through the Jobs API instead
B: The Databricks Runtime copy of pandas takes precedence over PyPI installs, so the wheel file has to be uploaded to DBFS
C: `%pip` leaves the running Python process in place; call `dbutils.library.restartPython()` so the new version is imported
D: Notebook-scoped installs take effect at the next cluster start, so the cluster has to be terminated and started again
K: C
G: ## Notebook-scoped libraries
`%pip install` creates a Python environment scoped to the notebook session. Other notebooks on the same compute are not affected, and the libraries do not persist: they must be installed again for every session. Place the `%pip` commands at the top of the notebook.
## Why the old version appears
`%pip` commands do not restart the Python process automatically. A package that was already imported in the running process stays in memory, so the new version is not seen. After installing or updating a package, call `dbutils.library.restartPython()` to restart the Python process (this resets Python state, so run it before the rest of the code). Upgrading core packages such as IPython with `%pip` may break features; in that case restart the cluster or start a new session.
W: Restart the Python process: the new package files are installed, but the running interpreter still holds the old module in memory, so `dbutils.library.restartPython()` makes the notebook import the new one.
X: A=Different compute and Jobs API: `%pip` installs into the notebook's own environment on the attached compute; no other cluster is involved and the Jobs API is not needed.
B=Runtime copy takes precedence: a notebook-scoped install can supply a newer version than the one in Databricks Runtime, and storing libraries in the DBFS root is deprecated and disabled by default in current runtimes.
D=Next cluster start: notebook-scoped installs take effect in the current session, so a full cluster restart is not needed; only the Python process has to restart.
T: After `%pip install` or upgrade, restart the Python process with `dbutils.library.restartPython()` to use the new version.

@ DBX-DEA D4 T4.4 applied use-case
S: A job is started by a file arrival trigger on `/Volumes/main/landing/events/`. The notebook task should ingest exactly the files that arrived since the previous run, even when runs are skipped or delayed, and must not reread files. What should the notebook do?
A: List the volume with dbutils.fs.ls and process the files whose modification time falls within the last hour
B: Read with Auto Loader and write with trigger availableNow, using a checkpoint outside the monitored path
C: Read the folder with spark.read on each run and drop duplicates from the target table with a final DISTINCT step
D: Delete processed files from the volume after the write so the next run lists just the unprocessed ones
K: B
G: ## Trigger plus Auto Loader
The file arrival trigger only says that something new exists; it does not remember what was processed. Databricks documents using Auto Loader in the triggered job: it discovers new files incrementally with exactly-once processing, tracked in a checkpoint.
```
spark.readStream.format("cloudFiles")
.option("cloudFiles.format", "json")
.option("cloudFiles.schemaLocation", checkpoint)
.load(file_location)
.writeStream.option("checkpointLocation", checkpoint)
.trigger(availableNow=True).toTable(sink_table)
```
The checkpoint must be outside the monitored location, so its own files do not start new runs.
W: Auto Loader with availableNow: the checkpoint tracks processed files, so each run ingests exactly the new files and stops, whatever the number or timing of runs.
X: A=Modification time window: a run delayed or skipped for more than one hour would lose files, and a rerun inside the hour would read some files twice.
C=Full read plus DISTINCT: it rereads the whole history on every run, grows more expensive over time, and DISTINCT on the target does not guard against every duplicate case.
D=Deleting processed files: it needs delete rights and loses the source copy for replay; a failure between the write and the deletion leads to duplicates or loss.
T: Pair a file arrival trigger with Auto Loader and trigger availableNow; the checkpoint, not the trigger, tracks what is processed.
V: Lakeflow Jobs, Auto Loader

@ DBX-DEA D4 T4.3 applied troubleshooting
S: A job has a table update trigger on a Unity Catalog view that filters `main.sales.orders` to `region = 'EU'`. Rows for the US region are added to the table, and the job starts although no EU row changed. Why?
A: The trigger watches the view's source tables, so a change that the view filter hides still counts as an update of the view
B: The run-as principal lacks SELECT on the view, which makes the trigger fall back to firing at each evaluation of the job
C: The trigger watches storage files, and a view has no files of its own, so file changes elsewhere in the account fire it
D: A trigger on a view runs once per evaluation interval, whether or not the underlying tables have received new data
K: A
G: ## Triggers on views
Table update triggers can monitor Unity Catalog views and metric views that depend on supported tables. The trigger does not evaluate the view's query result; it monitors changes to the dependent tables and considers the view updated if any dependent table is updated. A run can therefore be triggered by data changes that the view's filter hides.
## Notes
- Source tables of a view count toward the table limit of the trigger.
- Views that use `read_files`, depend on non-Unity-Catalog tables or on federated tables are not supported: the trigger can be created but never starts runs.
W: Dependent table change: the view counts as updated when its source table changes, so US inserts into the shared table start the run even though the view result is unchanged.
X: B=Missing SELECT: with a missing privilege the trigger would fail to evaluate and no run would start; it does not switch to firing on every evaluation.
C=Storage file watching: this is a table update trigger; it tracks changes of the view's dependent tables and has no account-wide file watching behavior.
D=Interval firing: the trigger fires on changes, not on a timer; with no updated dependent table, no run starts.
T: A table update trigger on a view fires when any underlying table changes, even if the view's filter would exclude the changed rows.
V: Lakeflow Jobs, Unity Catalog

S: A bundle's dev target uses mode: development. A developer deploys it and finds that the scheduled job is not running and that resources have a "[dev username]" prefix. Which statement describes development mode?

B: It deploys notebooks and files but skips job definitions, so that production schedules are not duplicated
C: It renames the target after the deploying user and keeps the deployment state in a shared workspace folder

G: ## Development mode
Setting `mode: development` on a target applies defaults for pre-production work:
- Resources that are not files or notebooks get the prefix `[dev <short_name>]` and jobs and pipelines get a `dev` tag.
- Lakeflow pipelines are marked `development: true`.
- Schedules and triggers are paused (set `pause_status: UNPAUSED` on a specific schedule to run it).
- Concurrent runs are enabled for faster iteration, and the deployment lock is disabled.
- `--cluster-id` can override compute definitions on deploy.

W: Development mode: the prefix, the `dev` tag and the paused schedules are its documented defaults, so a developer cannot accidentally schedule a personal copy of a production job.
X: B=Skips job definitions: jobs and pipelines are deployed in development mode, carrying the dev prefix; only their schedules are paused.
C=Renamed target and shared state: the prefix goes on resources, not on the target, and the state is stored under the deployer's own workspace path by default.
D=Single node and no retries: development mode does not change cluster types or retry settings; it can only let `--cluster-id` override compute on deploy.
T: mode: development prefixes resources, tags them and pauses schedules; mode: production validates settings.

@ DBX-DEA D4 T4.1 applied use-case
S: A pipeline job has four parallel load tasks feeding a notification task. The team wants a Slack-style alert task to run only when at least one load task fails and to be skipped when all loads succeed. Which setting on the alert task fits?
A: Run if "All done" with the four load tasks as its dependencies
B: Run if "At least one succeeded" with the four load tasks as its dependencies
C: Run if "At least one failed" with all four load tasks as its dependencies
D: Run if "None failed" with the four load tasks as its dependencies
K: C
G: ## Choosing the right Run if option
Run if looks at the outcomes of the tasks listed in Depends on.
- **At least one failed**: runs if one or more dependencies failed; if none failed the task is Excluded and skipped.
- **All failed**: runs only when every dependency failed.
- **At least one succeeded**: runs when one or more dependencies succeeded; otherwise the task is marked Upstream failed.
- **None failed**: runs when nothing failed and at least one dependency ran.
- **All done**: always runs after the dependencies finish, whatever their status.
An alert for partial failure needs the first option, because a single failing load among four must trigger it.
W: At least one failed: a single failing load task is enough to start the alert, and when all four succeed the alert task is marked Excluded and does not run.
X: A=All done: the alert runs after every run, successful or not, so it would notify even when all four loads succeed.
B=At least one succeeded: it runs whenever any load succeeds, which includes the all-success case, and it is skipped when all four loads fail, the opposite of an alert.
D=None failed: this is the success path; the alert would run when everything is fine and be skipped on failures, the reverse of the requirement.
T: For failure-only alerting, depend on the tasks with Run if "At least one failed"; "All done" and the success conditions also run when nothing failed.
V: Lakeflow Jobs

@ DBX-DEA D2 T2.3 applied troubleshooting
S: After a refactor an engineer points checkpointLocation of a running Auto Loader job to a new directory. The next run loads every historic file again and duplicates rows in the target. Why?
A: The schema location was reset with it, and a fresh schema inference reloads files seen before
B: The new directory switched the stream to file notification mode, which replays past events
C: Auto Loader records discovered files in the checkpoint, so a new location starts from zero
D: Auto Loader keeps its progress in the target Delta table history, which the refactor reset
K: C
G: ## What the checkpoint stores
The checkpoint holds offsets, commits, state and the query ID. For Auto Loader, metadata for discovered files is persisted in a RocksDB key-value store in the checkpoint location; this is what gives exactly-once file processing and lets a failed stream resume where it stopped. If you delete the checkpoint files or point to a new location, the next run begins fresh. `cloudFiles.includeExistingFiles` (default true) is evaluated when a stream starts for the first time, so the new run processes all existing files again.
Treat the checkpoint as part of the table's state: keep it stable, and only create a new one on purpose (for example, a full backfill with target truncation).
W: Checkpoint holds the file record: a new checkpoint has no record of processed files, and `cloudFiles.includeExistingFiles` applies to the new stream, so everything existing is picked up again.
X: A=Schema location reset: the schema location affects the stored and inferred schema, not which files count as processed.
B=Notification mode: the file detection mode is independent of the checkpoint path and does not replay old events.
D=Progress in the table history: Auto Loader progress lives in the checkpoint, not in the target table, and the table history was not changed.
T: A new or deleted checkpoint means full reprocessing; keep the checkpoint location stable.
V: Auto Loader, Structured Streaming

@ DBX-DEA D7 T7.4 applied tradeoff
S: A security architect worries that a data engineer who can edit tags on a column could remove the `pii` tag and so unmask the column under an ABAC policy. Which design choice addresses this concern directly?
A: Grant engineers MANAGE on the catalog so they can re-create the policies whenever a tag is changed
B: Replace ABAC with table-level masks, which do not use tags and leave masking to each table owner
C: Limit assigning the governed tag to stewards and review tag changes in the audit log system table
D: Write the masking function as a Python UDF so that removing the tag makes the function raise errors
K: C
G: ## Tagging is a security boundary
In ABAC, the tags decide which policies apply. If a user may change tags on an asset, they can change which policies cover it. Databricks best practices therefore say:
- Restrict tag creation and modification to authorized data stewards or governance admins, using governed tag permissions.
- Audit tag assignments and deletions regularly with the audit log system table (`system.access.audit`).
- Apply a default restrictive tag to new objects until a steward has classified them, with a policy that restricts access to the default tag.
Permissions: assigning a governed tag value needs `ASSIGN` on the tag and `APPLY TAG` on the object.
W: Control and audit tagging: limiting `ASSIGN` on the governed tag to stewards prevents engineers from removing it, and the audit log records tag assignment events for review.
X: A=MANAGE for engineers: this widens their power over policies and does not stop the tag from being removed in the first place.
B=Table-level masks: they are not tag based, but they pass control to each table owner, which loses central governance, and table owners can change or drop their own masks.
D=Python UDF: the function runs only after a policy matched; it cannot detect or restore a removed tag, and Python UDFs are also less performant.
T: Tags are the security boundary of ABAC: limit who can assign governed tags and audit tag changes.
V: Unity Catalog, ABAC

@ DBX-DEA D2 T2.5 applied use-case
S: Every night a partner REST API must be queried page by page (about 300 pages), and the raw responses must be stored for later parsing. The API token must not appear in code. Which design fits the Databricks toolset best?
A: A Lakeflow Connect managed database connector that uses the API endpoint as its source database
B: A nightly COPY INTO statement that uses the API URL as its file location, with the token in the SQL
C: An Auto Loader stream whose `load()` path is the REST API URL, run continuously on a small cluster
D: A scheduled Lakeflow Jobs notebook that gets the token from a secret scope and lands raw JSON in bronze

G: ## REST sources
Auto Loader, COPY INTO and the managed database connectors do not call arbitrary REST endpoints, so the usual pattern is code orchestrated by **Lakeflow Jobs**: a Python or notebook task calls the API with an HTTP client (for example `requests`), handles pagination and retries, and writes the responses to a Delta table. Keeping the **raw JSON string** in a bronze table preserves the source exactly and lets you parse and fix types later.
Credentials belong in a **secret scope** and are read with `dbutils.secrets.get("scope", "key")`; the value is redacted in notebook output.
## Example
Nightly job schedule -> task `pull_api` (notebook) -> task `parse_to_silver`.
W: Scheduled notebook with secrets: it can paginate, store raw responses and keep the token out of code, and the job gives scheduling, retries and monitoring.
X: A=Managed database connector: these connectors read databases (for example with CDC); a REST endpoint is not a database source.
B=COPY INTO from the API URL: COPY INTO loads files from a cloud storage or volume location, and a token in the SQL text would be exposed in code and query history.
C=Auto Loader on a URL: Auto Loader discovers files in cloud object storage or volumes; it cannot call an HTTP API.
T: For REST sources run code in a Lakeflow Jobs task, keep tokens in secret scopes and land the raw responses in bronze.

@ DBX-DEA D7 T7.1 applied troubleshooting
S: A data engineer who has `USE CATALOG`, `USE SCHEMA` and `CREATE TABLE` on `main.finance` runs `CREATE TABLE main.finance.audit_ext (id BIGINT) LOCATION 's3://acme-finance/audit/'`. The statement fails with a permission error. Which missing privilege explains it?
A: `SELECT` on the metastore, which allows queries of any table registered in it
B: `CREATE MANAGED STORAGE` on the external location, which lets a catalog or schema keep managed tables there
C: `MODIFY` on the schema `main.finance`, which covers data changes in the schema's tables
D: `CREATE EXTERNAL TABLE` on the external location defined over that bucket prefix
K: D
G: ## Creating an external table
An external table must point at a path inside a Unity Catalog external location, which links a cloud path to a storage credential. To create one you need:
- `CREATE EXTERNAL TABLE` on the external location that grants access to the path,
- `USE CATALOG` on the parent catalog,
- `USE SCHEMA` and `CREATE TABLE` on the parent schema.
```
CREATE TABLE c.s.t (id BIGINT) LOCATION 's3://bucket/dir/';
```
Managed tables need only the schema-level rights, since Databricks decides the location.
External locations carry other privileges too, such as `READ FILES`, `WRITE FILES` and `CREATE MANAGED STORAGE`; each authorizes a different action.
W: `CREATE EXTERNAL TABLE` on the external location: the engineer already has the schema-side rights, and this missing privilege is the one that governs creating tables over that storage path.
X: A=`SELECT` on the metastore: reading rights are irrelevant to creating a table, and `SELECT` is granted on tables and views, not used to authorize a storage path.
B=`CREATE MANAGED STORAGE`: it lets a catalog or schema use the location as storage for managed tables; it does not authorize creating an external table there.
C=`MODIFY` on the schema: `MODIFY` is a data-change privilege for tables; it is not what authorizes new tables at a storage path.
T: Creating an external table needs `CREATE EXTERNAL TABLE` on the external location, plus `USE CATALOG`, `USE SCHEMA` and `CREATE TABLE` on the parents.

S: A table owner in the `prod.sales` schema sees no row filter or column mask in the table definition, yet analysts report that some values in the table come back masked. The team suspects a policy defined at a higher level. Which command lists the policies that apply to this table, including those inherited from the schema and catalog?

G: ## Seeing ABAC policies
ABAC policies are dynamic: unlike table-level filters and masks they are not shown in the table definition, because they live on the catalog, schema or table scope and are matched by tags at query time.

W: SHOW EFFECTIVE POLICIES: it returns policies defined on the table plus those inherited from its schema and catalog, which exposes the hidden higher-level mask.
X: B=SHOW GRANTS: it lists the privileges the analysts group holds on the table; masks and filters are not privileges, so the policy does not appear.
C=DESCRIBE HISTORY: it lists Delta transactions of the table, not policies from higher scopes.
D=SHOW POLICIES: valid, but it lists only policies defined directly on the table, so the catalog- or schema-level policy behind the masked values is missing.
T: Use `SHOW EFFECTIVE POLICIES ON TABLE` to see every ABAC policy that affects a table, including inherited ones.
