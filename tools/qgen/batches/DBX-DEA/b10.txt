@ DBX-DEA D1 T1.1 advanced use-case
S: A team must move the Delta table `legacy.sales.events` (40 TB) into the new catalog `prod` as `prod.sales.events`. A Structured Streaming job appends to the old table around the clock, and after the cut-over it must keep writing to the new table from where it stopped, without reprocessing its Kafka offsets. The old table will be dropped a week later, and the copy must not depend on its files. Which approach meets these requirements?
A: Create the new table with SHALLOW CLONE, stop the stream, and restart it with its existing checkpoint pointed at the shallow clone as the new target
B: Create the new table with DEEP CLONE, stop the stream, run DEEP CLONE again to catch up, and restart the stream against the new table
C: Create the new table with CREATE TABLE AS SELECT from the old one, stop the stream, and restart it with a fresh checkpoint and startingOffsets set to latest
D: Create the new table with CREATE TABLE LIKE, copy the data with INSERT INTO SELECT, and restart the stream with its old checkpoint against the new table
K: B
G: ## Two kinds of clone
`CLONE` creates a copy of a Delta table at a specific version.
- **Deep clone** (`CLONE` or `DEEP CLONE`) copies the data files and the metadata. It is fully independent of the source.
- **Shallow clone** (`SHALLOW CLONE`) copies only metadata; the clone keeps pointing at the source's data files. It is cheap to create, but if the source is vacuumed or dropped, reads of the clone fail.
## What travels with a deep clone
Besides schema, table properties and partitioning, a deep clone also copies **stream metadata and COPY INTO metadata**. The docs state that a stream writing to the source table can be stopped and continued on the deep clone target from where it left off. Running the deep clone again after stopping the stream copies only the files added since the last clone, so the final catch-up is fast.
## Why the other copies fall short
CTAS and INSERT copy rows, but they create a brand new table with none of the source's streaming metadata, so the writer cannot simply resume.
W: Deep clone: it copies the data files, so the copy survives the drop of the old table, and it carries the stream metadata that lets the writer continue on the new table where it stopped.
X: A=Shallow clone: it references the old table's files, so the copy breaks when the old table is dropped next week, and stream metadata is cloned only for deep clones.
C=CTAS with a fresh checkpoint: starting at the latest offsets skips every record produced while the stream was stopped, which loses data instead of resuming.
D=CREATE TABLE LIKE plus INSERT: the rows arrive, but the new table has no streaming metadata, so the old checkpoint does not describe it and resuming cleanly is not supported.
T: To move a table and resume its streaming writer on the copy, use DEEP CLONE; shallow clones depend on source files and do not carry stream metadata.
V: Delta Lake, Structured Streaming

@ DBX-DEA D1 T1.2 advanced tradeoff
S: A nightly batch job runs a Python notebook that calls a vendor library shipped only inside a custom Docker image built with Databricks Container Services. The job runs for 50 minutes once a day, nobody uses it interactively, and the platform team wants the lowest compute cost that still runs the job unchanged. The workspace already uses serverless compute for most other jobs. Which compute should the job use?
A: Serverless compute for jobs, with the vendor library added to the task's environment as a dependency taken from the custom Docker image
B: An all-purpose cluster with the custom container image, kept running between runs so that the image does not have to be pulled each night
C: A classic jobs compute cluster defined in the job with the custom container image, created for each run and terminated when the run ends
D: A serverless SQL warehouse that runs the notebook through a SQL task, so that the platform team does not have to manage the container image
K: C
G: ## Choosing compute for a scheduled job
- **Serverless compute for jobs** starts quickly and needs no cluster management, but it has documented limits: no Databricks Container Services, no compute-scoped init scripts or compute policies, only Spark Connect APIs. Dependencies go into the task's environment (Python packages from requirements-style specifications, wheels or projects in workspace files or volumes).
- **Classic jobs compute** is a cluster that the job creates for its run and terminates at the end. It supports custom container images, init scripts and any cluster configuration, and it bills at the jobs rate only while the run lasts.
- **All-purpose compute** is meant for interactive work; it costs more per unit and keeps billing while idle.
## The deciding constraint
The library exists only inside a custom Docker image. Serverless does not support Databricks Container Services, so the cheapest compute that can run the image unchanged is classic jobs compute.
W: Classic jobs compute: it supports custom container images and exists only for the duration of each run, which is the cheapest option that runs the job unchanged.
X: A=Serverless jobs: serverless compute does not support Databricks Container Services, so the library inside the image cannot be used there as is.
B=Always-on all-purpose cluster: it can run the image, but it bills all day for a 50-minute job and at the higher all-purpose rate.
D=SQL warehouse: a SQL task runs SQL queries or files on a warehouse; it cannot run a Python notebook or a container image.
T: Serverless compute cannot use custom container images or init scripts; when a job needs them, use classic jobs compute rather than an all-purpose cluster.
V: Serverless compute, Lakeflow Jobs

@ DBX-DEA D2 T2.1 advanced use-case
S: A legacy process has already loaded three years of order files from `/Volumes/main/raw/orders/` into the bronze table, and it will be switched off tonight. A new Auto Loader stream must take over and load only files that arrive after its first start, because reloading the 2 million existing files would create duplicates and take days. The folder must stay as it is for audits. Which configuration meets these requirements?
A: Start the new stream with `cloudFiles.includeExistingFiles` set to false, so that its first run skips the files already present and loads only later arrivals
B: Start the new stream with `cloudFiles.maxFilesPerTrigger` set to 1000, so the existing files are loaded in small batches that the bronze table can absorb without long-running micro-batches
C: Start the new stream with the default options and add `cloudFiles.maxFileAge` of 1 day later, after the first run has already listed the existing files
D: Start the new stream with the default options, then set `cloudFiles.includeExistingFiles` to false on the second run once the stream has caught up
K: A
G: ## How Auto Loader decides what to load first
Auto Loader tracks every discovered file in its checkpoint, so each file is processed exactly once. On the **first start** of a stream (a new checkpoint), it must decide what to do with files already in the input path:
- `cloudFiles.includeExistingFiles` = `true` (default): existing files are processed too.
- `cloudFiles.includeExistingFiles` = `false`: only files arriving after the initial setup are processed.
The docs add an important detail: the option is **evaluated only when the stream starts for the first time**. Changing it on a later restart has no effect, because the checkpoint already contains the state.
## Rate limits are not filters
`cloudFiles.maxFilesPerTrigger` and `cloudFiles.maxBytesPerTrigger` only split the backlog into smaller micro-batches; every file is still loaded eventually.
W: includeExistingFiles false at first start: the existing files are skipped from the start, and only new arrivals are loaded, without moving or deleting anything in the audited folder.
X: B=maxFilesPerTrigger: it limits files per micro-batch but still loads all 2 million existing files, creating the duplicates the team wants to avoid.
C=maxFileAge added later: by then the first run has already taken the existing files into processing, so the duplicates are already written.
D=Change the option on the second run: the option is read only at the first start of a stream; changing it after the checkpoint exists does nothing.
T: Set `cloudFiles.includeExistingFiles` to false before the first start of a stream; it cannot be changed effectively afterwards.
V: Auto Loader

@ DBX-DEA D2 T2.2 advanced use-case
S: A SQL-only team loads partner CSV files into `main.bronze.claims` with a scheduled COPY INTO. Auditors now require a column with the full source file path on every row, and `amount` must be stored as `DECIMAL(12,2)` instead of the inferred string. Reruns must stay idempotent, and the team does not want to add Python code or a second load step. Which statement fits?
A: `COPY INTO main.bronze.claims FROM 's3://partner/claims/' FILEFORMAT = CSV FORMAT_OPTIONS ('header'='true', 'includeFilePath'='true', 'amount'='DECIMAL(12,2)')`, which sets lineage and type through format options alone
B: `COPY INTO main.bronze.claims FROM (SELECT *, CAST(amount AS DECIMAL(12,2)) AS amount, input_file_name() AS src FROM 's3://partner/claims/') FILEFORMAT = CSV COPY_OPTIONS ('force'='true')`, scheduled as before
C: `COPY INTO main.bronze.claims FROM (SELECT claim_id, CAST(amount AS DECIMAL(12,2)) AS amount, _metadata.file_path AS src FROM 's3://partner/claims/') FILEFORMAT = CSV FORMAT_OPTIONS ('header'='true')`
D: `INSERT INTO main.bronze.claims SELECT claim_id, CAST(amount AS DECIMAL(12,2)), _metadata.file_path FROM read_files('s3://partner/claims/', format => 'csv')` run every hour from a SQL task
K: C
G: ## COPY INTO with a transformation
`COPY INTO` can read from a subquery: `FROM (SELECT expression_list FROM 'path')`. The expressions can cast, rename or derive columns before the rows are written, so typing and lineage happen in the same idempotent load.
## The file metadata column
Every file-based source exposes a hidden `_metadata` column with fields such as `file_path`, `file_name`, `file_size` and `file_modification_time`. It must be selected explicitly, and Databricks recommends selecting specific fields (for example `_metadata.file_path`) rather than the whole struct so that new metadata fields do not cause schema evolution errors.
## Idempotency
COPY INTO skips files it has already loaded. Setting `COPY_OPTIONS ('force' = 'true')` turns that off and reloads every file on each run.
W: Subquery with _metadata.file_path: the cast and the lineage column are applied inside the load, and the default COPY INTO file tracking keeps reruns idempotent.
X: A=Format options for path and type: `includeFilePath` and a column type are not COPY INTO format options; types and derived columns belong in the SELECT list of the source subquery.
B=force plus input_file_name: `force` disables idempotency, so every scheduled run reloads all files, and the documented way to get the file path is the `_metadata` column.
D=INSERT from read_files hourly: a plain INSERT has no memory of loaded files, so each run appends every file again; it is not idempotent.
T: Use `COPY INTO ... FROM (SELECT ..., _metadata.file_path ... FROM 'path')` to cast and add lineage in one idempotent load.
V: COPY INTO

@ DBX-DEA D2 T2.3 advanced troubleshooting
S: An Auto Loader stream with a schema location ingests JSON from `/Volumes/main/raw/clicks/` laid out as `event=<type>/date=<yyyy-mm-dd>/`. The bronze table has `event` and `date` columns from the paths. Last week the producer added a third level, `hour=<hh>/`, and analysts report that bronze has no `hour` column although the files load normally. The stream must keep its checkpoint. What should the engineer change?
A: Set `cloudFiles.schemaEvolutionMode` to `addNewColumns`, so that the next file in a new directory level makes the stream add the `hour` column
B: Set `cloudFiles.partitionColumns` to `event,date,hour`, so that Auto Loader parses the new directory level as a column for the files it reads
C: Set `cloudFiles.inferColumnTypes` to true, so that Auto Loader re-samples the files and infers `hour` as an integer column from the paths
D: Add `hour INT` to `cloudFiles.schemaHints`, so that the inferred schema gains the column and Auto Loader reads its value from the JSON body
K: B
G: ## Partition columns in Auto Loader
When files are laid out in Hive style (`key=value/` directories), Auto Loader infers those keys as columns when it first infers the schema. Two documented details matter here:
- Auto Loader **does not consider partition columns for schema evolution**. A new directory level that appears later (such as `hour=01/`) is ignored.
- To capture new partition levels, set `cloudFiles.partitionColumns` to a comma-separated list, for example `event,date,hour`. Auto Loader then parses those columns from the path when they exist in it.
## Why schema evolution does not help
Schema evolution modes such as `addNewColumns` react to new fields **inside the data files**. The `hour` value exists only in the directory path, not in the JSON records, so evolution never sees it.
W: cloudFiles.partitionColumns: listing the new level tells Auto Loader to parse `hour` from the path, which is the documented fix for partition levels added after the schema was inferred.
X: A=addNewColumns: this mode evolves the schema for new fields in the files; partition columns are excluded from schema evolution, so the path level is still ignored.
C=inferColumnTypes: it controls whether JSON values are typed or kept as strings; it does not add path levels that appeared after inference.
D=Schema hint for hour: a hint adds or types a column, but the JSON records have no `hour` field, so the column would be NULL; the value lives only in the path.
T: Auto Loader ignores partition directories added later; list them in `cloudFiles.partitionColumns`.
V: Auto Loader

@ DBX-DEA D2 T2.4 advanced use-case
S: A managed Lakeflow Connect pipeline ingests a CRM `accounts` table. Finance now needs to see which sales region an account belonged to on any past date, starting from today, while other teams keep reading the current state. The team wants no custom MERGE code and no second copy of the source extract. Which change meets these requirements with the LEAST effort?
A: Keep history tracking off and add a Lakeflow Jobs task after each run that copies changed rows into a separate history table with a MERGE statement
B: Run a full refresh of the destination table every night, because a full refresh keeps the previous rows as older versions of the destination table
C: Turn history tracking on (SCD type 2) for the table in the pipeline, with a sequence column, so that changed rows are kept as inactive versions
D: Enable Delta time travel on the destination table with a long log retention, so that finance can query earlier versions by date for any account
K: C
G: ## History tracking in Lakeflow Connect
Managed ingestion pipelines have a **history tracking** setting, also called the slowly changing dimension (SCD) setting:
- **Off (SCD type 1, default)**: an update in the source overwrites the row in the destination.
- **On (SCD type 2)**: the pipeline keeps the old row, marks it inactive, and adds the update as a new row. A sequence column (such as `last_updated`) determines when each version was active, recorded in `__START_AT` and `__END_AT`.
Not every connector supports SCD type 2; the connector's feature table says which do. History starts when the setting is turned on.
## Full refresh warning
A full refresh **replaces the entire table and removes all previous row versions**; history is tracked again from the refresh point.
W: History tracking on: the connector itself keeps every earlier version with validity columns, so finance can ask for any past date and nobody writes MERGE code.
X: A=Custom MERGE task: it works, but it is the custom code and extra job the team wants to avoid, while the connector offers SCD type 2 as a setting.
B=Nightly full refresh: a full refresh replaces the table and discards previous versions, the opposite of keeping history.
D=Long time travel: time travel serves recovery and short audits, not as a long-term history; table versions are also tied to retention settings and pipeline writes, not to business dates.
T: For point-in-time history from a managed connector, turn on history tracking (SCD type 2); a full refresh resets that history.
V: Lakeflow Connect

@ DBX-DEA D2 T2.5 advanced use-case
S: A nightly Lakeflow Jobs task must copy changed rows from a 900-million-row `orders` table in an in-house database that has a JDBC driver but no managed connector and no change log. The DBA forbids full table scans during business hours, and the table has an indexed `updated_at` column. Silver must contain exactly one current row per `order_id`. Which design fits?
A: Read with `spark.read.format("jdbc")` and the whole table as `dbtable` every night, then overwrite the silver table so that it always matches the source exactly
B: Create a Lakehouse Federation foreign catalog for the database and point all silver queries at the foreign table, so no copy is ever needed
C: Read with `spark.read.format("jdbc")` using a `query` filtered on `updated_at` above the stored watermark, then MERGE the rows into silver by `order_id`
D: Export the table to CSV files with a nightly database script and load them with Auto Loader, appending each export to the silver table by default
K: C
G: ## Incremental pulls over JDBC
Without a change log or connector, the usual pattern is a **watermark**: remember the highest `updated_at` already loaded, and ask the source only for rows changed after it.
- The JDBC reader accepts either `dbtable` (a table or subquery) or `query`. A filter in the query runs **in the source database**, so with an index on `updated_at` the source reads only the changed rows.
- Changed rows must update existing rows rather than be appended, so the load ends with `MERGE INTO silver USING changes ON order_id`.
- The job stores the new watermark (for example in a control table) after a successful MERGE.
## Federation is for querying, not copying
Lakehouse Federation lets Unity Catalog query the external database in place. Every silver query would then run against the source, which is the load the DBA wants to avoid.
W: Filtered JDBC query plus MERGE: the source reads only changed rows through its index, and MERGE keeps exactly one current row per order in silver.
X: A=Full read and overwrite: it scans all 900 million rows every night, which the DBA forbids, and moves far more data than needed.
B=Federated foreign table: no copy is made, but every downstream query hits the source database, and silver no longer exists as a governed Delta table.
D=CSV export plus append: a full export still scans the table, and appending each export creates many rows per `order_id` instead of one current row.
T: For a JDBC source without a change log, pull rows above a watermark with a filtered `query` and MERGE them by key.
V: JDBC, Delta Lake

@ DBX-DEA D2 T2.6 advanced use-case
S: Click events from the web shop are published to a Kafka topic with seven days of retention. Product analysts, who write only SQL, need them in a bronze Delta table within about five minutes, each event loaded exactly once, and they want Databricks to manage the checkpoint and the refresh compute. The platform team will not run notebooks or Python jobs for this. Which approach meets these requirements?
A: A streaming table created in Databricks SQL with `SELECT * FROM STREAM read_kafka(...)` and a refresh schedule of a few minutes
B: A materialized view created in Databricks SQL over `read_kafka(...)`, refreshed every few minutes, which reprocesses the topic and stores the latest result
C: A Lakeflow Connect managed database connector pointed at the Kafka brokers, with an ingestion gateway and staging storage for change capture
D: A COPY INTO statement that reads the Kafka topic directly, scheduled in a SQL task every five minutes, which skips offsets already loaded
K: A
G: ## Streaming from Kafka with SQL only
Databricks provides the `read_kafka` table-valued function. The Kafka docs state that **streaming with SQL is supported only in Lakeflow pipelines or with streaming tables in Databricks SQL**. A streaming table defined as
`CREATE STREAMING TABLE bronze_clicks SCHEDULE EVERY 5 MINUTES AS SELECT * FROM STREAM read_kafka(bootstrapServers => '...', subscribe => 'clicks')`
reads only new offsets on each refresh, processes every record once, and keeps its own checkpoint. A serverless pipeline that Databricks creates runs the refresh, so the team manages no compute or checkpoint.
## Why the others do not fit
- Materialized views recompute results from their sources; they are not designed to track Kafka offsets.
- COPY INTO loads files from object storage, not message buses.
- Managed database connectors use an ingestion gateway and staging storage to capture changes from relational databases such as SQL Server or PostgreSQL; a message bus is not a database.
W: Streaming table over read_kafka: SQL-only, incremental with exactly-once processing, and Databricks manages the checkpoint and the refresh pipeline.
X: B=Materialized view: it is meant for results that can be recomputed from sources, not for consuming new Kafka offsets once each.
C=Database connector with gateway: the gateway captures changes from relational database logs; Kafka is a message bus, read with the Kafka source or `read_kafka`.
D=COPY INTO from Kafka: COPY INTO reads files in cloud storage; it cannot consume a Kafka topic.
T: SQL users stream Kafka into Delta with a streaming table over `STREAM read_kafka(...)`.
V: Streaming tables, Kafka

@ DBX-DEA D2 T2.7 advanced troubleshooting
S: A partner now exports each order as a pretty-printed JSON document that spans many lines per file, instead of one JSON object per line. Since the switch, the Auto Loader stream into bronze loads rows where every business column is NULL and only a corrupt-record column is filled. The schema is unchanged, files are complete, and the team must keep using Auto Loader. Which change fixes the parsing?
A: Set `cloudFiles.format` to `text` and parse each line with `from_json`, because Auto Loader cannot read JSON that spans more than one line
B: Set `cloudFiles.schemaEvolutionMode` to `rescue`, so that fields that fail to parse are moved into the rescued data column for later use
C: Set the `mode` option to `DROPMALFORMED`, so that the broken records are dropped and only the valid JSON lines are written to bronze
D: Set the JSON option `multiLine` to true, so that each file is parsed as whole JSON documents rather than as one record per line
K: D
G: ## JSON Lines versus multi-line JSON
By default, the JSON reader (also inside Auto Loader) expects **JSON Lines**: one complete JSON object per line. When a document is pretty-printed over many lines, each physical line is an incomplete fragment, so every line fails to parse. In `PERMISSIVE` mode the fields become NULL and the raw text lands in the corrupt-record column.
The JSON option `multiLine` (default `false`) says whether JSON records span multiple lines. With `multiLine` set to `true`, the reader parses whole documents instead of single lines.
## Rescue is for mismatches, not for broken framing
The rescued data column catches values that do not match the schema (type or case mismatches, unknown fields). It cannot repair records that were split at every newline.
W: multiLine true: the reader treats each file as complete JSON documents spanning lines, so the fields parse again with the same schema and the same stream.
X: A=Text plus from_json: reading line by line still splits each document into fragments, and Auto Loader can read multi-line JSON with the right option.
B=Rescue mode: rescue handles fields that do not match the schema; a record split into fragments is malformed, not mismatched.
C=DROPMALFORMED: it would drop every fragment, so bronze would receive nothing instead of the orders.
T: Pretty-printed JSON documents need `multiLine` = true; the default reader expects one object per line.
V: Auto Loader

@ DBX-DEA D2 T2.3 advanced use-case
S: A governance board requires that the bronze schema of a regulated feed changes only after a data steward has reviewed it. If a producer adds a column, ingestion must stop instead of silently continuing, and it must not resume until the schema has been updated. The stream uses Auto Loader with schema inference and a schema location, and a Lakeflow Jobs task with retries runs it. Which `cloudFiles.schemaEvolutionMode` meets these requirements?
A: `addNewColumns`, because the stream stops on the new column and the job retries then pick up the evolved schema without anyone reviewing it
B: `failOnNewColumns`, because the stream fails on a new column and does not restart until the schema is updated or the file is removed
C: `rescue`, because the stream never fails and records new columns in the rescued data column for the stewards to review later
D: `none`, because the stream ignores new columns without failing, so the bronze schema never changes unless someone edits it manually
K: B
G: ## Auto Loader schema evolution modes
With an inferred schema, `cloudFiles.schemaEvolutionMode` decides what happens when files contain a new column:
- `addNewColumns` (default): the stream fails once, updates the schema in the schema location, and works again after a restart (for example a job retry). No human review is needed.
- `rescue`: the schema never evolves and the stream never fails; new columns go to the rescued data column.
- `failOnNewColumns`: the stream fails and **does not restart** unless the provided schema is updated or the offending data file is removed.
- `none`: new columns are ignored and the stream does not fail.
## Mapping to the requirement
The board wants ingestion to stop and stay stopped until the schema is changed on purpose. Only `failOnNewColumns` blocks the stream until a person acts; job retries cannot get past it.
W: failOnNewColumns: the new column stops the stream, and retries keep failing until a steward updates the schema, so no change slips through unreviewed.
X: A=addNewColumns: the job retry restarts the stream with the evolved schema automatically, which is exactly the unreviewed change the board forbids.
C=rescue: ingestion silently continues; the board requires that it stops.
D=none: new columns are dropped and ingestion continues, so data is lost and nobody is forced to review.
T: To make schema changes wait for a human, use `failOnNewColumns`; `addNewColumns` recovers on the next restart by itself.
V: Auto Loader

@ DBX-DEA D3 T3.1 advanced use-case
S: A silver table `main.silver.app_logs` receives log events from a stream. The source sometimes resends the same event, with the same `event_id`, up to three days later, and duplicates must never reach silver. The table holds two years of data, and the team wants the deduplication to scan as little of the target as possible on each micro-batch. Which write logic meets these requirements?
A: An insert-only MERGE on `event_id` whose ON clause also limits the target to the last three days of `event_date`, after deduplicating the batch itself
B: An insert-only MERGE on `event_id` over the whole target table, without deduplicating the batch, so that every resent event is matched against two years
C: A plain append of each micro-batch, followed by a nightly `INSERT OVERWRITE` of silver with `SELECT DISTINCT *` that removes the duplicates
D: A MERGE with WHEN MATCHED THEN UPDATE SET * on `event_id`, so that a resent event replaces the stored row instead of being inserted again
K: A
G: ## Insert-only merge for deduplication
A MERGE with only a `WHEN NOT MATCHED THEN INSERT *` clause adds new events and ignores events already present. Two documented details make it correct and cheap:
- **Deduplicate the new batch first.** MERGE matches new rows against the table, but duplicates inside the new data itself would both be inserted.
- **Limit the target range in the ON clause.** If duplicates can only appear within a few days, add a predicate such as `t.event_date > current_date() - INTERVAL 3 DAYS` to the ON condition. The engine then looks for matches only in that slice instead of the whole table.
Because an insert-only MERGE only appends rows, another stream can keep reading the silver table incrementally.

@ DBX-DEA D7 T7.4 advanced troubleshooting
S: The account uses the governed tag `pii` with allowed values, and ABAC policies on the `prod` catalog mask columns tagged `pii = email`. A data engineer who owns several new tables in `prod.crm` tries to tag their email columns with the governed tag, and the operation is denied. The engineer can add ordinary tags elsewhere. Security wants engineers to apply this tag only to their own tables. What is missing?
A: The ASSIGN permission on the governed tag `pii`, granted in the account; ownership of the tables already provides APPLY TAG on them
B: The MANAGE permission on the governed tag `pii`, which is required to edit the tag's allowed values before any engineer can assign it
C: MANAGE on the catalog `prod`, because only principals who can manage privileges on the catalog may set governed tags on its columns
D: Membership in the account admins group, because governed tags can be assigned only by account admins and never by table owners
K: A
G: ## Two permissions to tag with a governed tag
Governed tags are account-level tags with controlled keys and allowed values, often used by ABAC policies. Assigning one needs two separate things:
- **ASSIGN** on the governed tag (account level, or on that specific tag): controls who may use the tag at all.
- **APPLY TAG** on the Unity Catalog object: controls who may add or edit tags on that object. Owners have all privileges on their objects.
The docs stress that ASSIGN is distinct from the object-level privilege: APPLY TAG on an object is also required.
## Other governed tag permissions
- **MANAGE** on a governed tag lets a principal edit or delete the tag and manage its permissions; it is broader than needed to use it.
W: ASSIGN on the governed tag: the engineer already controls tags on owned tables; what is missing is the right to use this governed tag, granted per tag.
X: B=MANAGE on the tag: it allows editing the tag definition and permissions, more than security wants to hand out.
C=MANAGE on the catalog: object privileges do not replace the tag-level ASSIGN permission, and it would cover all of `prod`.
D=Account admins only: table owners can assign governed tags once they have ASSIGN; admin rights are not required.
T: Using a governed tag needs ASSIGN on the tag plus APPLY TAG (or ownership) on the object.
V: Unity Catalog, Governed tags

@ DBX-DEA D7 T7.3 advanced troubleshooting
S: A data engineer uses a dedicated (single user) access mode cluster for a nightly notebook that reads `main.sales.orders`, which has a row filter. The workspace admin confirms that serverless compute is not enabled there. Which explanation fits?

B: The row filter function lives in another workspace, and dedicated clusters can call functions only from their own workspace catalog
C: Dedicated access mode cannot read tables with row filters in any configuration, so the first workspace must be using a standard access mode cluster
D: On dedicated compute, Databricks enforces row filters and masks through serverless compute, so the workspace must be enabled for serverless
K: D
G: ## Fine-grained access control on dedicated compute
Row filters and column masks are fine-grained access controls (FGAC). On **standard** access mode compute and SQL warehouses they are evaluated directly. For **dedicated** access mode compute, the docs state:
- dedicated access compute can access tables with row filters or column masks (on supported runtime versions) **if the workspace is enabled for serverless compute**;
- when such a table is queried from dedicated compute, Databricks **uses serverless compute to enforce the FGAC**, and all FGAC limitations apply.
## Applying it
The same notebook works in one workspace and fails in the other, and the only difference named is serverless enablement, which is the documented requirement.
W: Serverless enforcement: dedicated compute hands the filtered read to serverless compute, so it fails in a workspace where serverless is not enabled.
X: A=SQL warehouses only: standard access mode clusters and, with serverless, dedicated clusters can read filtered tables too.
B=Function in another workspace: Unity Catalog functions are metastore objects, available in every attached workspace with the right grants.
C=Never on dedicated: the docs describe how dedicated access works with filters; the first workspace shows it does.
T: Dedicated access mode reads tables with row filters or masks through serverless compute, so serverless must be enabled in the workspace.
V: Unity Catalog, Compute
