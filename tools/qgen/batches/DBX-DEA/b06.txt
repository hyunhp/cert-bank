@ DBX-DEA D4 T4.1 applied use-case
S: A Lakeflow Jobs task reads a table from an external REST API and occasionally fails with a connection reset that disappears a minute later. The team wants the task to try again automatically a few times before the whole run is marked failed, without changing the notebook code. What should the engineer configure?
A: A retry policy on that task with a maximum number of retries and a minimum interval between attempts
B: A second copy of the task with a Run if condition of "At least one failed" that points at the same notebook
C: A For each task that loops over a list of three attempt numbers and runs the notebook for each one
D: A job-level schedule that fires again every minute until a run finishes successfully
K: A
G: ## Retries are a per-task setting
In Lakeflow Jobs (formerly Workflows) each task has advanced settings with a **retry policy**: how many times a failed task run is retried and how long to wait between attempts. For most configurations the default is no retry, so a transient error fails the run at once.
- The retry applies to that task only, so the rest of the job graph is untouched.
- The interval is measured in milliseconds from the start of the failed attempt to the start of the next one.
- If a timeout is also set, it applies to each attempt separately.
Retries are the right tool for transient problems such as network resets or a briefly unavailable source. They are not a way to fix logic errors, because the same code fails the same way each time.
W: Retry policy: it re-runs only the failed task up to the configured count after the configured wait, so a connection reset that clears within a minute is absorbed and the run only fails if every attempt fails.
X: B=Duplicate task with At least one failed: a Run if condition decides whether a downstream task starts after an upstream result, so this would build a manual second attempt that runs even on unrelated failures and adds a node to maintain. The built-in retry setting does the same thing on the original task.
C=For each over attempt numbers: a For each task runs every iteration regardless of success, so the notebook would execute three times even when the first attempt works, which duplicates the API load and the writes.
D=Schedule every minute: a schedule starts new runs of the whole job on a clock, not retries of one task, and it would keep launching runs even after a success.
T: For transient task failures, set a retry policy (count and interval) on the task; use Run if and branching tasks for logic that depends on outcomes.

@ DBX-DEA D4 T4.1 applied troubleshooting
S: A task is configured with a timeout of 30 minutes and 2 retries. The source system hangs, so every attempt stalls. An engineer expects the job to fail after at most 30 minutes in total but it keeps running for about 90 minutes before ending in Timed Out. What explains this?
A: The timeout covers the whole task including retries, but the cluster start time was added on top of it
B: The timeout applies to each attempt, so two retries allow up to three attempts of 30 minutes each
C: Each retry replaces the timeout with the configured retry interval, so the interval becomes the new limit
D: Timeouts are ignored while a retry policy is set, so the task ended only when the source released the connection
K: B
G: ## Timeout and retries together
A **timeout** sets the maximum duration of a task run. If the run exceeds it, its status becomes Timed Out. A **retry policy** starts new attempts after a failure.
When both are configured, the documentation states that the timeout applies to each retry. With 2 retries the task can run as the original attempt plus two retries, so three attempts, and each is cut off at its own timeout.
## Planning a worst case
Worst case runtime = attempts x timeout + waiting intervals. If a hard overall limit matters, lower the timeout or the retry count rather than expecting the timeout to span attempts.
W: Timeout per attempt: each of the three attempts (the first run plus two retries) may use the full 30 minutes, which matches roughly 90 minutes before the final Timed Out status.
X: A=Timeout covers all retries: that is the opposite of the documented behavior, and cluster start time would not explain a full hour of extra runtime.
C=Retries reset timeout to the interval: the retry interval is only the wait between attempts and does not replace the timeout value.
D=Timeouts ignored with retries: timeouts still apply when a retry policy exists; the task did end as Timed Out, which proves the timeout was enforced.
T: With both settings, the timeout applies to every attempt, so total worst-case time is about (retries + 1) x timeout plus waits.

@ DBX-DEA D4 T4.1 applied use-case
S: A job has tasks ingest, transform and report. After the run ends, whether it succeeded or failed, a final task must always release a lock row in a control table. Which configuration on the cleanup task does this?
A: Depend on report only and keep the default Run if setting of "All succeeded"
B: Depend on report and set Run if to "At least one failed" so it starts when something goes wrong
C: Depend on all three tasks with Run if "All done", so it runs after they finish whatever their status
D: Depend on ingest and set Run if to "None failed" so it only runs when the start of the job is healthy
K: C
G: ## Run if conditions
By default a task runs only when all its upstream dependencies succeeded (**All succeeded**). If a dependency fails, the task is marked **Upstream failed** and does not run.
The Run if setting changes this:
- **All succeeded** (default), **At least one succeeded**, **None failed** (none failed and at least one ran).
- **All done**: run after every dependency has finished, whatever the outcome.
- **At least one failed** and **All failed**: run only for failure cases; otherwise the task is Excluded (skipped).
Cleanup logic that must always happen therefore uses All done and depends on every task that could leave the lock behind.
W: All done: the cleanup task starts once ingest, transform and report have all finished, independent of success or failure, so the lock is released in both cases.
X: A=All succeeded on report: if ingest or transform fails, report is marked Upstream failed, so the cleanup task is also Upstream failed and never runs; the lock stays held.
B=At least one failed: the task would be skipped (Excluded) on a successful run, so the lock would be released only on failures.
D=None failed on ingest: it ignores transform and report, is marked Upstream failed when ingest fails, so it neither covers all outcomes nor waits for the later tasks to end.
T: Use Run if "All done" for cleanup that must run regardless of upstream results; "At least one failed" is for failure-only handling.

@ DBX-DEA D4 T4.1 applied use-case
S: A pipeline job has four parallel load tasks feeding a notification task. The team wants a Slack-style alert task to run only when at least one load task fails and to be skipped when all loads succeed. Which setting on the alert task fits?
A: Run if "At least one failed" with the four load tasks as dependencies
B: Run if "All failed" with the four load tasks as dependencies
C: Run if "None failed" with the four load tasks as dependencies, so it runs only on a clean pass
D: Run if "All done" with the four load tasks as dependencies
K: A
G: ## Choosing the right Run if option
Run if looks at the outcomes of the tasks listed in Depends on.
- **At least one failed**: runs if one or more dependencies failed; if none failed the task is Excluded and skipped.
- **All failed**: runs only when every dependency failed.
- **None failed**: runs when nothing failed and at least one dependency ran.
- **All done**: always runs after the dependencies finish.
An alert for partial failure needs the first option, because a single failing load among four must trigger it.
W: At least one failed: a single failing load task is enough to start the alert, and when all four succeed the alert task is marked Excluded and does not run.
X: B=All failed: the alert would fire only when all four loads fail, so a partial failure of one or two loads would go unreported.
C=None failed: this is the success path; the alert would run when everything is fine and be skipped on failures, the reverse of the requirement.
D=All done: the alert runs after every run, successful or not, so it would notify even when all four loads succeed.
T: For failure-only alerting, depend on the tasks with Run if "At least one failed"; "All done" always runs and "All failed" waits for a total failure.

@ DBX-DEA D4 T4.1 applied use-case
S: A notebook task named count_rows sets a task value with dbutils.jobs.taskValues.set(key="bad_records", value=n). The job must run a quarantine task when n is greater than 0 and a publish task otherwise. Which design implements this branching?
A: Two notebook tasks that both depend on count_rows and read the task value in code, and each one exits early when its branch does not apply
B: One For each task whose input is the bad_records value, with a nested publish task that is repeated once per bad record found
C: An If/else task testing {{tasks.count_rows.values.bad_records}} > 0, with quarantine on true and publish on false
D: A Run Job task that starts a separate job, which then decides from its own result whether quarantine or publish should run
K: C
G: ## Branching in the job graph
The **If/else condition** task evaluates a boolean expression made of two operands and an operator. Operands can be job parameters, task parameters or **task values** set by earlier tasks with `dbutils.jobs.taskValues.set`, referenced as `{{tasks.<task>.values.<key>}}`.
Downstream tasks pick a branch in Depends on: `<condition task> (true)` or `<condition task> (false)`. The unused branch is not run, and the Jobs UI shows the evaluated expression.
- Comparison operators `>`, `>=`, `<`, `<=` compare numerically.
- Only numeric, string and boolean values can be referenced.
W: If/else condition task: the expression checks the task value, the quarantine task depends on the true branch and publish on the false branch, so exactly one runs and the decision is visible in the task graph.
X: A=Two tasks checking in code: both tasks still start and take compute, and the branching is hidden inside notebooks where the DAG and run history cannot show it. The If/else task keeps the logic in the job graph.
B=For each over bad_records: a For each loops over an array of inputs; a single integer is not a branch, and it would not choose between two different tasks.
D=Run Job task: it triggers another job but does not by itself select between two tasks of this job based on a value.
T: Use an If/else condition task with a task value expression to branch, and attach tasks to its true or false outcome.

@ DBX-DEA D4 T4.1 applied troubleshooting
S: An If/else condition task compares {{tasks.profile.values.avg_amount}} == 12 and the upstream task sets the value 12.0. The engineer expected the true branch but the false branch runs. What is the cause and the fix?
A: The == operator compares strings, so 12.0 differs from 12; use a numeric operator such as >= 12 instead
B: The task value was stored as a decimal, which makes the whole condition task fail instead of choosing a branch
C: If/else tasks can only compare job parameters, so the task value is read as empty and the false branch is the default result
D: The false branch runs whenever the upstream task needs more than one retry, so the retry count must be reset to zero
K: A
G: ## String versus numeric comparison
In an If/else condition the operators behave differently:
- `==` and `!=` compare operands as **strings**. So `12.0 == 12` is false.
- `>`, `>=`, `<`, `<=` compare **numerically**. So `12.0 >= 12` is true and `10.0 >= 12` is false.
This matters when a value can have a trailing decimal or format difference. Use a numeric operator (or normalize the value upstream) when comparing numbers.
W: String comparison with ==: the text "12.0" is not equal to "12", so the false branch runs; a numeric operator or an integer value gives the intended result.
X: B=Decimal makes the task fail: numeric values, including decimals, are allowed in operands; only other types (such as arrays) cause the expression to fail.
C=Only job parameters allowed: operands may reference job parameters, task parameters and task values, so the value is read correctly.
D=Retries decide the branch: the branch comes from the boolean result of the expression, not from retry counts.
T: == and != in If/else tasks are string comparisons; use >, >=, <, <= for numeric logic.

@ DBX-DEA D4 T4.1 applied use-case
S: A job must run the same transformation notebook for 40 tables, each with its own table name. The list is stored in a control table, and several tables should be processed at the same time. Which approach follows Lakeflow Jobs practice?
A: Create 40 notebook tasks by hand, each with a hard-coded table name and all depending on one start task
B: Wrap the notebook in a loop in a single task that processes the tables one after another on a single driver thread
C: Create 40 separate jobs and trigger them from an external scheduler that reads the control table
D: A For each task over the table list, with the notebook as nested task and a concurrency above the default
K: D
G: ## Looping with For each
A **For each** task runs one nested task once per element of an input array, passing each element as a parameter. The nested task can be any standard task type except another For each.
- Inputs can be a JSON array typed in the task, a task value from an earlier task (`{{tasks.<name>.values.<key>}}`), or a job parameter (`{{job.parameters.<name>}}`).
- Inside the nested task, `{{input}}` is the element, or `{{input.table}}` for an object field.
- **Concurrency** sets how many iterations run in parallel; the default is 1, so iterations run one at a time unless you raise it.
A SQL task that reads a control table can set a task value that feeds the loop, which keeps the table list as data.
W: For each with concurrency: one task definition covers all 40 tables, the list can come from the control table, and a higher concurrency value runs several tables at once.
X: A=Forty hand-made tasks: it works but clutters the graph, needs a code change for each new table, and does not read the control table.
B=Loop inside one task: tables run sequentially in one task, with no per-table status in the Jobs UI and no parallel iterations or per-iteration retries.
C=Forty jobs plus an external scheduler: this adds a second orchestrator and loses the single run view; For each exists to keep this inside one job.
T: To run one task for many inputs, use a For each task with the list as input and raise concurrency for parallel iterations.

@ DBX-DEA D4 T4.1 applied troubleshooting
S: A three-task job (extract -> transform -> load) failed in transform after extract finished writing a large staging table. Fixing the transform bug takes five minutes, and the team wants to avoid re-running extract. What should they do?
A: Use Run now, which skips tasks that finished in an earlier run of the same job
B: Delete the extract task from the job, then run the job again
C: Create a new job containing only transform and load, copying the parameters and cluster settings across by hand
D: Fix the cause and use Repair run, which re-runs only the failed task and its dependents
K: D
G: ## Repair run
A **repair run** re-runs only the unsuccessful tasks of a multi-task job run and the tasks that depend on them. Tasks that succeeded are not run again, which saves time and compute. Unsuccessful tasks use the **current** job and task settings, so you can fix a notebook path or cluster setting first.
- Repair works for jobs with two or more tasks.
- A repair starts failed tasks from the beginning. Lakeflow Jobs does not make tasks idempotent, so output written before the failure can be duplicated if the task appends.
After the repair, the matrix view in the Runs tab gets a new column for the repaired run.
W: Repair run: only transform and the dependent load task run again, extract's results stay, and the fixed settings are used.
X: A=Run now: it starts a fresh run of the whole job, so extract runs again; Run now does not reuse earlier results.
B=Delete extract: removes the ingestion step from the job and would leave transform without its dependency, changing the job rather than recovering the run.
C=New job with copied parameters: manual, error-prone, and the run history of the original job is split.
T: Repair run re-executes failed and dependent tasks only; make sure re-run tasks are idempotent.

@ DBX-DEA D4 T4.2 applied use-case
S: In a job, tasks b and c both depend on task a, and task d depends on b and c with the default settings. Task b fails after a succeeds. What happens to c and d in this run?
A: c is skipped because b failed, and d runs because one of its parents succeeded
B: Both c and d run, since the default is to run every task regardless of failures
C: c runs, since it depends only on a, but d is marked Upstream failed and does not run

Dependencies create a directed acyclic graph. A task starts when its own dependencies are met, and as many tasks as possible run in parallel.
- b and c are siblings: each depends on a only, so a failure in b does not affect c.
- d uses the default **All succeeded** Run if. If any dependency fails, d is marked **Upstream failed** and does not run.

W: c runs and d is upstream failed: c only needs a, which succeeded, while d needs both b and c to succeed and b did not.
X: A=c skipped and d runs: c does not depend on b, and d with All succeeded does not start when one parent fails.
B=Run every task: the default is All succeeded, not run regardless of failures.
D=c cancelled: failures of a sibling do not cancel unrelated tasks, and d would not run with a failed parent.
T: Siblings are independent; a downstream task with All succeeded runs only if every parent succeeded.

@ DBX-DEA D4 T4.1 applied comparison
S: A continuous job that streams data fails several times in a row because a source is down. An engineer wants to know how Lakeflow Jobs handles the repeated failures without manual restarts. What is the behavior?
A: It stops permanently after the first failure and sends an email that must be acknowledged
B: It retries immediately in a tight loop until the run succeeds, with a fixed interval of one second
C: It retries the failed task with the task's retry count and then marks the job paused until someone resumes it
D: It backs off exponentially once consecutive failures pass a threshold, showing the failure count and next retry time
K: D
G: ## Continuous jobs
A **continuous job** starts a new run as soon as the previous one ends or fails, so the job is always running. If consecutive failures exceed a threshold, Lakeflow Jobs applies **exponential backoff** between retries. A **Restart run** action cancels the active run, resets the retry period and starts a new run.
Task-level retries are separate; continuous jobs use this backoff policy as their failure handling.

X: A=Permanent stop: continuous jobs keep retrying with backoff instead of stopping on the first failure.
B=Tight loop: a fixed one-second interval would be the opposite of backoff.
C=Task retry then pause: the documented handling is exponential backoff, not a pause waiting for a person.
T: Continuous jobs back off exponentially after repeated consecutive failures; Restart run resets it.
