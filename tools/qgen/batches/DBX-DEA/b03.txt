@ DBX-DEA D2 T2.4 applied definition
S: A team sets up a Lakeflow Connect managed database connector that uses change data capture. Besides the ingestion pipeline and the destination tables, the architecture contains a component that runs in its own job as a continuous task and captures changes using staging storage. Which component is it?
A: The ingestion gateway
B: The Unity Catalog connection
C: The destination streaming table
D: The pipeline update schedule
K: A
G: ## Parts of a managed connector
Lakeflow Connect managed connectors (built and run by Databricks) are made of a few Unity Catalog governed pieces:
- A **connection**: a Unity Catalog securable object that stores the authentication details for the source.
- An **ingestion pipeline**: a Lakeflow pipeline that runs on serverless compute and writes to the destination.
- **Destination tables**: streaming tables that hold the ingested data.
Database connectors that use change data capture (CDC) add two more parts: an **ingestion gateway** and **staging storage**. The gateway extracts the change data continuously and stages it, so it runs in its own job as a continuous task, separate from the scheduled pipeline.
## Example
A SQL Server table receives updates all day. The gateway keeps reading the change feed into staging storage, while a scheduled pipeline run applies the staged changes to the streaming table.
W: The ingestion gateway: it is the extra component of database (CDC) connectors, it runs as a continuous task in its own job and uses staging storage to support continuous change capture.
X: B=The Unity Catalog connection: it only stores authentication details for the source database and is not a running component, so it has no job and does not capture changes.
C=The destination streaming table: it is where the ingested data is stored; it receives rows but does not read from the source or run in a job.
D=The pipeline update schedule: a schedule defines when the ingestion pipeline runs and Lakeflow Connect turns it into a job, but it is not the component that continuously captures changes.
T: CDC-based managed database connectors add a continuously running ingestion gateway with staging storage to the connection, pipeline and destination tables.
V: Lakeflow Connect, Unity Catalog

@ DBX-DEA D2 T2.4 applied use-case
S: A managed SaaS connector pipeline for Salesforce data runs on a daily schedule. After each successful ingestion run, a notebook must refresh a silver table from the new data. What is the recommended way to chain the notebook to the ingestion?
A: Add the notebook as a task, depending on the pipeline task, in the job created for the schedule
B: Schedule a separate job one hour after the ingestion and assume the pipeline has finished by then
C: Edit the connector code to call the notebook when the source API returns its last page of data
D: Replace the managed pipeline with a custom notebook that calls the Salesforce API directly and loops
K: A
G: ## Orchestration of managed connectors
You can run a Lakeflow Connect ingestion pipeline on one or more custom schedules. For every schedule you add, Lakeflow Connect automatically creates a **Lakeflow Jobs** job in which the ingestion pipeline is a task. You can optionally add more tasks to that job, which makes ordinary job features available: task dependencies, retries, notifications.
## Example
Job `salesforce_daily`: task 1 = ingestion pipeline, task 2 = notebook `refresh_silver` with a dependency on task 1. The notebook starts only after the pipeline task succeeds.
W: Add a task to the job created for the schedule: the pipeline is already a task of that job, so a dependent notebook task runs exactly after ingestion succeeds, with no timing guess.
X: B=Separate job one hour later: this is time-based coupling; if ingestion runs long or fails, the notebook reads incomplete or stale data and nothing stops it.
C=Editing the connector code: managed connectors are a Databricks service and do not expose connector code to edit; dependency handling belongs to job orchestration.
D=Replacing the managed pipeline: this gives up the source authentication, incremental ingestion and retry handling that the managed connector provides, only to get something a job task already offers.
T: Each schedule of a Lakeflow Connect pipeline becomes a Lakeflow Jobs job, so add downstream work as extra tasks that depend on the pipeline task.
V: Lakeflow Connect, Lakeflow Jobs

@ DBX-DEA D2 T2.4 applied definition
S: A managed connector pipeline ingests a large table for the first time and is then scheduled every hour. What does Lakeflow Connect do on the later runs, when the source supports it?
A: It re-reads the whole selected table and replaces the destination tables on every run
B: It ingests only the data that changed since the previous run, using change tracking
C: It ingests only rows whose ingestion timestamp column is newer than the last run date set by the engineer
D: It pauses the pipeline until an engineer confirms that the first load is complete
K: B
G: ## Incremental ingestion in Lakeflow Connect
On the first run a managed connector ingests all of the selected data from the source and, in parallel, tracks changes. On each following run it uses that change tracking to ingest only what changed since the prior run, when possible. The mechanism depends on the source: for SQL Server both change tracking and CDC are available, while the Salesforce connector selects a cursor column from a set list of options. Some sources or tables do not support incremental ingestion yet, and those are read in full.
This is why managed ingestion scales better than a full reload for large tables refreshed often.
W: Only changed data is ingested: after the initial full load the connector relies on source change tracking, which keeps hourly runs small and cheap.
X: A=Full reload on every run: this is the behavior of a naive replace-all job, not of an incremental connector, and it would make cost grow with the table size.
C=Engineer-set timestamp: the connector chooses and manages its change tracking (change tracking, CDC or a cursor column); nobody maintains a last run date by hand.
D=Waiting for confirmation: pipeline runs follow the schedule; there is no manual approval step between the first load and later runs.
T: Managed connectors load everything once, then read only changes on later runs wherever the source supports incremental ingestion.
V: Lakeflow Connect

@ DBX-DEA D2 T2.4 applied troubleshooting
S: A managed connector pipeline fails overnight because the credentials stored for the source database expired. An administrator updates the credentials the next morning. What does Lakeflow Connect do on the next pipeline run?
A: It must delete the destination tables and run a full initial load again from the source system
B: It skips every change that occurred during the outage and continues from the current position
C: It continues from its last stored cursor position, so changes made during the outage are not missed
D: It stays failed until the pipeline is recreated with a new connection
K: C
G: ## Failure recovery
Lakeflow Connect is a managed service that tries to recover on its own. When a connector fails it retries automatically with exponential backoff. Some errors need a person, for example expired credentials. In that case the connector avoids missing data by **storing the last position of the cursor**, and picks up from that position on the next run when possible.
Monitoring helps: event logs, pipeline health and data quality metrics are available for the pipeline.
## Example
Credentials expire at 01:00 and are rotated at 08:00. The next run starts from the cursor stored at 01:00 and reads the seven hours of changes.
W: Continue from the stored cursor: this is the documented behavior for errors that need intervention, so no changes are lost and no full reload is required.
X: A=Delete and reload: nothing in the recovery model requires a full reload after a credential fix; that would be slow and costly for large tables.
B=Skipping the changes: the connector stores its position precisely to avoid missing data, so outage changes are ingested, not dropped.
D=Recreate the pipeline: a failed run with fixed credentials resumes on the next run; the pipeline definition is not the problem.
T: When a managed connector needs human help, it keeps its last cursor position and resumes from it, so fix the cause and run again.
V: Lakeflow Connect

@ DBX-DEA D2 T2.4 applied use-case
S: The security team forbids database passwords in pipeline definitions, notebooks and Git. A team plans to ingest an on-premises PostgreSQL database with a Lakeflow Connect managed connector. Where is the source authentication supposed to live?
A: In a Unity Catalog connection that the ingestion pipeline references
B: In widget parameters of the pipeline that operators type before each run
C: In a CSV file in the workspace root that only the pipeline owner can open
D: In an environment variable that is exported inside the ingestion gateway notebook
K: A
G: ## Connections hold the credentials
A managed connector uses a **Unity Catalog connection**: a securable object that stores the authentication details for the source. The ingestion pipeline refers to the connection, so credentials do not appear in pipeline configuration. Access to the connection is governed with Unity Catalog privileges, and the credentials are hidden from the people who use the pipeline.
This also works for the other layers of the stack: with plain Spark code you would instead keep secrets in a **secret scope** and read them with `dbutils.secrets.get`, never in the notebook text.
W: Unity Catalog connection: it is the designed place for source authentication, is reusable, governed by privileges and keeps credentials out of code and Git.
X: B=Widget parameters: typing passwords before runs would expose them in run parameters and history and cannot support unattended scheduled runs.
C=CSV file in the workspace: credentials in a file are unmanaged, easy to copy and not integrated with Unity Catalog access control.
D=Environment variable in a notebook: managed connectors have no gateway notebook to edit, and plain-text variables in code are the pattern the security team wants to avoid.
T: Managed connectors authenticate through a governed Unity Catalog connection; never place source passwords in code, parameters or files.
V: Lakeflow Connect, Unity Catalog

@ DBX-DEA D2 T2.5 applied use-case
S: A notebook loads a 500-million-row `orders` table from PostgreSQL with `spark.read.format("jdbc")` and only `url`, `dbtable` and credentials. It runs for hours on a cluster with many idle cores. Which change speeds up the read the most?
A: Add workers to the cluster so that the single JDBC query runs on more executors
B: Call `repartition(200)` on the DataFrame right after the read to spread the rows
C: Set `partitionColumn` to the indexed numeric key, with `lowerBound`, `upperBound` and `numPartitions`
D: Set `fetchSize` to a very large value so that the driver sends every row in one round trip
K: C
G: ## Parallel JDBC reads
By default the Spark JDBC source reads a table with **one query on one task**, however large the cluster. To read in parallel you set four options together:
- `partitionColumn`: a numeric, date or timestamp column, ideally indexed in the source and evenly distributed
- `lowerBound` and `upperBound`: used only to compute the stride between partitions
- `numPartitions`: the number of parallel queries
Spark then issues one range query per partition, for example `WHERE order_id >= 0 AND order_id < 62500000`. Keep `numPartitions` modest (around the core count for small clusters): too many simultaneous queries can overwhelm an application database.
## Example
```
df = (spark.read.format("jdbc")
  .option("url", url).option("dbtable", "public.orders")
  .option("partitionColumn", "order_id")
  .option("lowerBound", 1).option("upperBound", 500000000)
  .option("numPartitions", 8).load())
```
W: Partitioned read: the four options turn one long query into several range queries that run at the same time on different tasks, so the idle cores are used.
X: A=More workers: the read is still a single query on a single task, so extra executors stay idle.
B=Repartition after the read: the whole table has already been pulled through one connection into one partition; repartitioning only reshuffles afterwards.
D=Larger fetchSize: this changes how many rows come per network round trip and can cause memory errors when too large; it does not add parallel queries.
T: JDBC reads are single-threaded until you set partitionColumn, lowerBound, upperBound and numPartitions.
V: Spark JDBC, Lakeflow Jobs

@ DBX-DEA D2 T2.5 applied troubleshooting
S: An engineer sets `partitionColumn=id`, `lowerBound=1000`, `upperBound=2000` and `numPartitions=4`, expecting to load only rows with ids from 1000 to 2000. The result holds every row of the source table. What explains this?
A: The bounds only set the partition stride, so the first and last partitions also take ids outside the range
B: The JDBC source ignores the bounds whenever the source table has an index on the partition column
C: Spark applies the bounds only when `fetchSize` has also been set to a value above 1000 rows
D: The cluster uses a Unity Catalog connection, and that connection type disables all partitioning options
K: A
G: ## What lowerBound and upperBound do
With a partitioned JDBC read, Spark splits the range between `lowerBound` and `upperBound` into `numPartitions` strides. The first partition gets all rows below the first stride boundary and the last partition all rows above the last one, so **no rows are filtered out**. The bounds only decide how evenly the work is divided.
To load a subset, filter explicitly: a `WHERE` condition in a `query` or in a subquery given as `dbtable`, or a DataFrame filter that Spark can push down.
## Example
`dbtable = "(SELECT * FROM orders WHERE id BETWEEN 1000 AND 2000) AS o"` reads only that range, and the partition bounds can then match it.
W: Stride only: the bounds shape the partitions and the edge partitions are open ended, so rows outside the range are still read; filtering needs its own condition.
X: B=Index ignored: an index on the partition column helps the source answer range queries quickly but has no effect on how Spark treats the bounds.
C=fetchSize dependence: `fetchSize` only controls rows per round trip and is unrelated to bounds.
D=Connection disables options: a Unity Catalog JDBC connection allows `partitionColumn`, `lowerBound`, `upperBound` and `numPartitions` among its default option allowlist, and this behavior is not about connections.
T: lowerBound and upperBound split the work and do not filter; add a WHERE condition to limit the rows read.
V: Spark JDBC

@ DBX-DEA D2 T2.5 applied tradeoff
S: A daily job must load the result of a join between two large tables in a source Oracle database plus a GROUP BY that reduces 2 billion rows to 3 million. Which JDBC read design moves the least data over the network?
A: Read both tables in full with two JDBC reads and run the join and aggregation in Spark
B: Read the first table in full and join the second one inside a Spark UDF row by row
C: Read both tables with a high `numPartitions` and `fetchSize`, then cache the result in memory
D: Use the `query` option with the join and aggregation SQL so that the source database computes it
K: D
G: ## Pushing work down to the source
The JDBC source can send a complete SQL statement to the database: use the `query` option (or a parenthesized subquery with an alias in `dbtable`). The database then runs the join and the aggregation and returns only the 3 million result rows. Pushing down is attractive when the source is well indexed and the result is much smaller than the input.
Trade-offs: the work runs on the source system, which may also serve an application, and the SQL is written in the source dialect. For very large results you can still combine it with partitioned reads.
## Example
```
spark.read.format("jdbc").option("url", url)
  .option("query", "SELECT region, SUM(amt) AS amt FROM o JOIN c USING (cid) GROUP BY region")
  .load()
```
W: Query pushdown: the database executes the join and aggregation, and only the small aggregated result crosses the network.
X: A=Two full reads: all 2 billion rows (plus the second table) are transferred before Spark reduces them, which is the opposite of the goal.
B=Row-by-row UDF join: it still reads one table in full and makes the join slow and non-distributed in the worst way; the source never helps.
C=High parallelism and caching: more partitions and fetch speed make the full transfer faster but do not reduce the amount transferred, and caching billions of rows is costly.
T: When the source can shrink the data, push the SQL down with the query option and move only the result.
V: Spark JDBC

@ DBX-DEA D2 T2.5 applied use-case
S: Every night a partner REST API must be queried page by page (about 300 pages), and the raw responses must be stored for later parsing. The API token must not appear in code. Which design fits the Databricks toolset best?
A: A scheduled Lakeflow Jobs notebook task that reads the token from a secret scope and appends raw JSON pages to bronze
B: An Auto Loader stream whose `load()` path is the REST API URL, run continuously on a small cluster
C: A COPY INTO statement with the API URL as file location and the token written in the SQL text
D: A managed database connector configured with the API endpoint as the source database to read

G: ## REST sources
Databricks has no connector that reads arbitrary REST endpoints for you, so the usual pattern is code orchestrated by **Lakeflow Jobs**: a Python or notebook task calls the API with an HTTP client (for example `requests`), handles pagination and retries, and writes the responses to a Delta table. Keeping the **raw JSON string** in a bronze table preserves the source exactly and lets you parse and fix types later.
Credentials belong in a **secret scope** and are read with `dbutils.secrets.get("scope", "key")`; the value is redacted in notebook output.
## Example
Nightly job schedule -> task `pull_api` (notebook) -> task `parse_to_silver`.
W: Scheduled notebook with secrets: it can paginate, store raw responses and keep the token out of code, and the job gives scheduling, retries and monitoring.
X: B=Auto Loader on a URL: Auto Loader discovers files in cloud object storage or volumes; it cannot call an HTTP API.
C=COPY INTO from the API URL: COPY INTO loads files from a cloud storage or volume location, and a token in the SQL text would be exposed in code and history.
D=Managed database connector: these connectors read databases (for example with CDC); a REST endpoint is not a database source.
T: For REST sources run code in a Lakeflow Jobs task, keep tokens in secret scopes and land the raw responses in bronze.
V: Lakeflow Jobs, Databricks secrets

@ DBX-DEA D2 T2.6 applied tradeoff
S: Analysts need an occasional look at a few operational PostgreSQL tables from Databricks, in read-only mode, to prove whether the data is useful. Copying the data is not wanted yet and table-level access control in Unity Catalog is required. What should the team use?
A: Lakehouse Federation (query federation) with a foreign catalog for the PostgreSQL database
B: A Lakeflow Connect managed database connector with CDC and a continuous ingestion gateway
C: A nightly custom JDBC notebook that overwrites a copy of every table in Delta
D: Partner Connect to purchase a third-party replication tool for the proof of concept
K: A
G: ## Ingest or query in place
Databricks recommends **ingestion** for most use cases because it scales to high data volumes, supports low-latency queries and respects third-party API limits. The cost is a copy that can become stale.
If you do not want to copy data, **Lakehouse Federation** (query federation) runs queries against an external relational database through a Unity Catalog **foreign catalog**. Queries are pushed down to the source, access is read-only and governed per table. It fits ad hoc reporting, BI and proof-of-concept access. Ingest when the workload is repeated, heavy, needs history or must not load the operational system.
W: Query federation: read-only, no copy, pushdown to the source and table-level governance through a foreign catalog, which is right for a short proof of concept.
X: B=CDC managed connector: it copies all changes continuously into Databricks, which is the opposite of the no-copy requirement and is more setup than a trial needs.
C=Nightly overwrite notebook: this makes a stale copy and needs custom code and credentials handling that federation avoids.
D=Third-party replication tool: it also copies the data and adds cost and tooling for something that only needs read access.
T: For occasional read-only access without copying, use Lakehouse Federation; ingest when the workload is heavy, repeated or needs history.
V: Lakehouse Federation, Unity Catalog

@ DBX-DEA D2 T2.7 applied comparison
S: Event payloads from many producers arrive as JSON. Producers often add fields and sometimes change a field type. The table has hundreds of distinct fields, and analysts frequently query a few of them. The team wants flexible schema handling without pre-processing and good read performance. Which storage type does Databricks recommend?
A: One STRING column holding the raw JSON text
B: A STRUCT column with a fixed definition of all hundreds of fields
C: A MAP<STRING, STRING> column with every value cast to text
D: A VARIANT column filled with parse_json
K: D
G: ## Choosing a semi-structured pattern
- **JSON strings**: no type information and no pre-processing, perfect for keeping a complete raw copy. Worst read performance, because the whole string is parsed for every query.
- **VARIANT**: semi-structured JSON stored in an optimized binary encoding that outperforms JSON strings on read and write. Flexible to new fields and type changes. Databricks recommends VARIANT over JSON strings for semi-structured data.
- **STRUCT**: best read performance for well-known schemas, but types are enforced on write, so it needs pre-processing and is less flexible for schema evolution, and degrades past hundreds of columns.
- **MAP and ARRAY**: typed keys and values; no statistics; balanced for around 500 fields.
## Example
```
SELECT parse_json(payload) AS v FROM raw_events;
SELECT v:user.id::int FROM events;
```
W: VARIANT: it tolerates changing fields and types without pre-processing, and its optimized encoding reads faster than parsing a JSON string each time.
X: A=Raw STRING column: it is flexible but the worst for reads, since the full string is parsed on every query.
B=Fixed STRUCT: producers change types and add fields, so writes would fail or drop data, and hundreds of fields hurts performance.
C=MAP of strings: it throws away type information and does not collect statistics, so it is flexible but not better for reads.
T: For evolving JSON with frequent reads choose VARIANT; keep STRING for raw archives and STRUCT for stable, known schemas.
V: VARIANT, Delta Lake

@ DBX-DEA D2 T2.7 applied troubleshooting
S: A bronze table keeps order JSON in a STRING column `raw`. A query `SELECT AVG(raw:store.bicycle.price) FROM store_data` returns results, but a later `ORDER BY` on the extracted value sorts "19.95" after "100". What is the reason, and the fix?
A: The extracted value is a string, so cast it, for example `raw:store.bicycle.price::double`
B: The colon operator returns numbers only for arrays, so convert the column to ARRAY first
C: JSON strings cannot hold decimals, so the price must be stored as an INT
D: The table needs `OPTIMIZE` so that numbers are sorted in numeric order
K: A
G: ## Querying JSON strings
For a STRING column that holds JSON, use `column:path` to extract a field, with dot or bracket notation for nested fields (`raw:store.bicycle`, `raw:store.fruit[0].type`). The result is **always a string**. Use `::` to cast to a basic type (`::double`, `::int`, `::date`). For complex types use `from_json(raw:store.basket[*], 'array<array<string>>')`.
Databricks recommends extracting nested fields into typed columns for best read performance, since the whole JSON string is parsed on each query.
## Example
```
SELECT raw:owner, raw:store.bicycle.price::double FROM store_data
```
W: Cast the extracted string: the colon path returns STRING, so a text sort puts "100" before "19.95"; casting with `::double` gives numeric ordering and arithmetic.
X: B=Array conversion: extraction returns strings for scalar fields as well; converting to an array does not fix types.
C=INT only: JSON can hold decimal numbers; casting to double or decimal handles them.
D=OPTIMIZE: it compacts files and does not change data types or how strings sort.
T: The colon operator on a JSON string returns STRING, so cast with :: (or from_json for complex types) before numeric work.
V: Databricks SQL, JSON

@ DBX-DEA D2 T2.7 applied use-case
S: A bronze column `payload` is a STRING holding an object such as `{"id": 7, "tags": ["a","b"], "geo": {"lat": 1.5, "lon": 2.5}}`. Silver needs a column with typed nested fields that can be queried as `payload_s.geo.lat`. Which expression does this?
A: `cast(payload AS STRUCT<id: INT, tags: ARRAY<STRING>, geo: STRUCT<lat: DOUBLE, lon: DOUBLE>>)`
B: `from_json(payload, 'id INT, tags ARRAY<STRING>, geo STRUCT<lat: DOUBLE, lon: DOUBLE>')`
C: `explode(payload)` followed by a select of `col.geo.lat` and `col.geo.lon`
D: `payload:geo` extracted with the colon operator and cast to a struct without a schema
K: B
G: ## From JSON string to struct
`from_json(string_col, schema)` parses a JSON string into a STRUCT (or array or map) according to a schema given as a DDL string or a schema object. Nested fields are then reached with dot notation, and the struct has typed fields that can be used for data skipping. If you do not know the schema, `schema_of_json` can derive a DDL string from a sample record.
Because it applies a schema, fields not in the schema are not kept in the result and a mismatching value becomes NULL, so keep the raw string in bronze.
## Example
```
SELECT from_json(payload, 'id INT, geo STRUCT<lat: DOUBLE, lon: DOUBLE>') AS payload_s FROM bronze_events
```
W: from_json with a schema: it parses the string into a typed STRUCT so nested fields are reachable by dot notation.
X: A=Cast to STRUCT: casting a string to a struct type does not parse JSON text; the string would have to be parsed with from_json instead.
C=explode: it turns the elements of an array or map into rows; applied to a plain string it does not parse the JSON and fails.
D=Colon path: it extracts a value from the string as a STRING, and casting without a schema does not build a typed struct for `payload_s.geo.lat`.
T: Use from_json with a schema to turn a JSON string into a typed struct; use the colon operator only to extract individual string values.
V: Databricks SQL, JSON

@ DBX-DEA D2 T2.7 applied troubleshooting
S: A silver job extracts a price from a VARIANT column with `variant_get(v, '$.price', 'double')`. One producer starts sending `"price": "n/a"` and the whole job fails on the cast. The team wants a NULL for such values and a running job. Which change handles it?
A: Use `try_variant_get` so that a failed cast returns NULL

G: ## Safe casting of variant fields
`variant_get(col, path, type)` extracts a field and casts it to the type; if the value cannot be cast, the query fails. `try_variant_get` has the same arguments but returns **NULL** when the cast fails, which fits dirty or mixed-type data. T: Use try_variant_get to turn cast failures into NULLs on VARIANT data instead of failing the job.

@ DBX-DEA D2 T2.7 applied tradeoff
S: Queries on a Delta table with a VARIANT column `v` always filter by the field `v:customer_id`. The team wants to use that field as a clustering key to skip data. What is the correct approach?
A: Declare `CLUSTER BY (v)` on the whole variant column
B: Extract `customer_id` into a regular typed column and cluster by that column
C: Partition the table by `v:customer_id` so that every customer gets a folder
D: Add the variant column to ZORDER because Z-order supports all types
K: B
G: ## Limits of VARIANT
VARIANT columns cannot be used as clustering keys, partition columns or Z-order keys, and cannot be used for comparisons, grouping, ordering or set operations. When a field of semi-structured data is used often for filtering, joining or clustering, **promote it to a typed top-level column** (derived at write time), and keep the VARIANT column for the long tail of fields.
Structs are different: struct fields can be used as clustering keys and collect statistics.
## Example
```
CREATE TABLE events (customer_id BIGINT, v VARIANT) CLUSTER BY (customer_id);
```
W: Extracted typed column: a plain BIGINT column can be a clustering key and gets statistics, while the rest of the payload stays flexible in VARIANT.
X: A=Cluster by variant: VARIANT is not allowed as a clustering key.
C=Partition by field: VARIANT cannot be a partition column, and one folder per customer produces too many small partitions.
D=Z-order on variant: VARIANT cannot be used as a Z-order key either, and the claim that it supports all types is wrong.
T: VARIANT is great for flexible payloads but cannot be a clustering, partition or Z-order key; pull hot fields into typed columns.
V: VARIANT, Liquid Clustering
