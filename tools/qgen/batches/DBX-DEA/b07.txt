@ DBX-DEA D4 T4.3 applied troubleshooting
S: An hourly job uses a scheduled trigger with the time zone America/New_York. On the night the clocks change, the run for one hour is missing and, in the spring, later runs appear shifted by an hour in the run history. The team wants a job that fires at every absolute hour all year. What should they change?
A: Replace the cron expression with a simple schedule of every 60 minutes, which the scheduler corrects automatically when daylight saving time begins or ends
B: Raise the maximum concurrent runs of the job to 2 so that the run missed during the clock change is queued and started later
C: Set the schedule time zone to UTC, which does not observe daylight saving time, so every hour is an absolute hour
D: Move the schedule to the minute 30 of each hour, because the scheduler only skips runs that are due exactly at the top of the hour
K: C
G: ## Scheduled trigger and time zones
The scheduled trigger fires a job on a time-based schedule. An advanced schedule lets you pick the period, the start time and a time zone, and shows the Quartz cron expression behind it. The time zone matters: if you choose a zone that observes daylight saving time (DST), wall-clock hours repeat or disappear twice a year.
## What happens at the clock change
Databricks documents that, with a DST time zone, an hourly job is skipped or appears delayed by an hour or two when DST begins or ends. To run at every hour in absolute time, choose UTC.
```
Quartz cron, UTC:  0 0 * * * ?     (every hour on the hour)
```
W: UTC time zone: UTC has no daylight saving shifts, so the cron expression fires at every real hour, which is the documented way to avoid skipped or delayed hourly runs.
X: A=Simple schedule: a simple schedule is an interval and unit of time, but it does not remove the DST effect of a wall-clock zone, and you cannot choose its first run time; the scheduler does not "correct" skipped hours.
B=Concurrent runs: maximum concurrent runs only limits runs that overlap; it does not recreate a run that the schedule never produced because the local hour did not exist.
D=Minute 30: the DST shift moves the whole wall clock by an hour, so a run at minute 30 is skipped or delayed in the same way; the problem is the zone, not the minute.
T: For jobs that must run at absolute intervals, configure the schedule in UTC; DST time zones skip or shift hourly runs at clock changes.

@ DBX-DEA D4 T4.3 applied use-case
S: A data engineer adds a scheduled trigger to a job so that it starts every day at exactly 02:15. With the simple schedule type the editor does not let the engineer choose the minute of the first run. Which choice meets the requirement?
A: Use the advanced schedule, which lets the engineer set the period, the starting time and the time zone, or edit the Quartz cron expression
B: Keep the simple schedule of 24 hours and start the job manually at 02:15 once, so that every later run follows 24 hours after it
C: Use the simple schedule of every 1 day, because the scheduler always aligns the first run with the minute at which the job was saved
D: Add a file arrival trigger on an empty volume and place a marker file there at 02:15 each day to start the run
K: A
G: ## Simple and advanced schedules
A scheduled trigger has two modes. A simple schedule runs the job periodically at a chosen unit and interval (for example every twelve hours) starting when the job first runs. You cannot specify the time of the first run; the scheduler chooses it.
An advanced schedule gives control over the period, the start time and the time zone, and exposes Quartz cron syntax for fine control (`0 15 2 * * ?` means 02:15:00 every day).
W: Advanced schedule: it is the mode where you pick the exact time and time zone, so a run at 02:15 every day is expressed directly, without manual steps.
X: B=Manual first run: a manual run does not set the schedule of a simple trigger, and the scheduler picks the first run time itself, so the 24-hour cadence would not be anchored at 02:15.
C=Simple every 1 day: the documentation states the time of the first run of a simple schedule cannot be specified, so there is no guarantee it matches the minute of saving.
D=Marker file trigger: it needs an external process to write a file every day, which only rebuilds a clock with extra moving parts; a scheduled trigger exists for time-based starts.
T: Choose the advanced schedule (or cron) when the exact time of day or the time zone matters; a simple schedule only sets an interval.

@ DBX-DEA D4 T4.3 applied troubleshooting
S: A job with a scheduled trigger runs every 15 minutes and keeps the default maximum of one concurrent run. One day a run takes 40 minutes because of a slow source. The team notices that two scheduled runs in that window appear in the run list with the status Skipped. What explains this?
A: Lakeflow Jobs cancels the running attempt after 15 minutes and replaces it with a new one, marking the replaced runs as Skipped
B: The scheduler pauses the trigger after the first overrun and shows each due slot as Skipped until someone presses Resume
C: Skipped marks the two due runs as retries of the long run, which reuses its cluster and shows no work of its own
D: Scheduled runs that come due while the job is already at its maximum concurrent runs are skipped instead of started
K: D
G: ## Concurrency and triggered runs
A job has a maximum number of concurrent runs, by default 1. When a trigger fires while that limit is reached, the new run does not start. For most trigger types the run is recorded with the status Skipped. (Queueing of runs is a separate job setting that can be enabled.)
## Impact on schedules
A slow run therefore leaves holes in the schedule rather than a pile-up. To see them, check the run history: skipped runs appear in the runs list and the matrix view (pink bars).
W: Maximum concurrent runs: with one allowed run, due scheduled runs that overlap the 40-minute run are skipped, which the run list reports as Skipped.
X: A=Replacement of the running attempt: Lakeflow Jobs does not cancel a healthy running run because a new trigger is due; the long run continues to its end.
B=Pausing the trigger: a trigger is paused only by a user or an explicit setting; overlap alone does not pause it, and the next slot after the long run starts normally.
C=Retries: a retry is a repeated attempt of a failed task and is shown on that task; a skipped run is a separate job run that never started and does not share any cluster.
T: A scheduled run that comes due while the job is at its concurrent-run limit is skipped, so long runs show up as Skipped entries in the history.

@ DBX-DEA D4 T4.3 applied troubleshooting
S: A team configures a file arrival trigger with the storage location `/Volumes/main/landing/raw/region=*/` so that the job fires when files land in any region folder. The trigger cannot be saved. What is the correct way to monitor all regions?
A: Replace the asterisk with a question mark, because only that wildcard is accepted in file arrival trigger paths
B: Point the trigger at the parent path `/Volumes/main/landing/raw/`, which is checked recursively; wildcards are not accepted
C: Create one file arrival trigger per region folder, because a trigger only monitors the files directly in its folder
D: Use the cloud storage URL of the volume instead of the volume path, which unlocks wildcard patterns for the trigger
K: B
G: ## File arrival triggers
A file arrival trigger starts a run when new files land in a Unity Catalog volume or external location. It can monitor the root or a subpath, and it checks recursively: for `/Volumes/main/landing/raw/` it also checks `region=eu/`, `region=us/` and any deeper folder.
## Path rules
- The path cannot contain wildcards such as `*` or `?`.
- The path must not include external tables or managed locations of catalogs and schemas.
- Only new files trigger runs.
W: Parent path: since subdirectories are checked recursively, monitoring the parent folder covers every region folder without needing a wildcard.
X: A=Question mark wildcard: neither `*` nor `?` is allowed in the path, so swapping one for the other does not help.
C=One trigger per region: a trigger already looks into all subfolders, so splitting it adds triggers and maintenance without gaining coverage (a job also has one trigger in the general case).
D=Cloud storage URL: the storage location may be given as a volume path or an external location URL, but neither form accepts wildcards.
T: File arrival triggers monitor a path and everything under it; do not use wildcards, point the trigger at the parent folder.

@ DBX-DEA D4 T4.3 applied troubleshooting
S: A file arrival trigger monitors `/Volumes/main/landing/orders/`. A producer corrects a bad file by uploading a new version under the same name, overwriting the original. Nobody is notified and no run starts. What is the reason?
A: Only new files trigger runs, so overwriting an existing file with the same name does not start a job run
B: The trigger is evaluated once per hour and the correction arrived within an hour of the original file
C: Corrected files are processed by the trigger only when the job has the run-as principal set to the file owner
D: A file arrival trigger starts a run only when at least ten files arrive together within the evaluation window
K: A
G: ## What a file arrival trigger detects
The trigger watches for new files. It makes a best-effort check roughly every minute. A file replaced under the same name is not a new file, so it does not start a run. (If the replaced file's metadata falls outside the rolling retention period of file events, the change may be treated as a new arrival, which is why immutable files are recommended.)
## Design consequence
Producers feeding a file arrival trigger should write new, uniquely named files (for example with a timestamp in the name) instead of overwriting.
W: New files only: an overwrite with an identical name is not a new file, so the trigger does not fire; writing a new file name would.
X: B=Hourly evaluation: the trigger checks for new files about every minute, not hourly, so timing is not the issue.
C=Run-as principal: the run-as identity needs read access to the location, but it has no relation to who owns the file or to whether a change is treated as new.
D=Ten files: there is no minimum file count; a single new file can start a run (the advanced options only add a cooldown or a wait for quiet time).
T: File arrival triggers react to new files only; overwriting a file with the same name does not start a run, so write uniquely named files.

@ DBX-DEA D4 T4.3 applied use-case
S: A partner delivers a batch of roughly 300 files to a volume every hour. The files land over about 40 seconds, and the next batch is at least 50 minutes away. The job should start once per batch, after the last file of the batch is there, not in the middle. Which file arrival trigger setting fits?
A: Minimum time between triggers of 30 seconds, so the job can only run once the batch is complete
B: Minimum time between triggers of 3000 seconds, which keeps each run waiting until all files of the previous run are processed
C: Wait after last change of 60 seconds, which restarts its timer on every new file and starts the run after a quiet minute
D: Maximum concurrent runs of 300, so that each file gets its own run and all runs finish at about the same time
K: C
G: ## Two advanced options
File arrival triggers (and table update triggers) have two rate-control options:
- **Minimum time between triggers**: a cooldown. At most one run per interval; after a run completes the trigger waits that long before starting another.
- **Wait after last change**: a debounce. The trigger waits this long after the most recent arrival before it starts a run, and each new file resets the timer.
## Choosing the value
For batches, pick a value longer than the gap between files in a batch and shorter than the gap between batches. Files here arrive within 40 seconds, batches are 50 minutes apart, so 60 seconds works: the run starts after 60 quiet seconds.
W: Wait after last change: every new file resets the 60-second timer, so the run starts only after the batch is complete and quiet, giving one run per batch.
X: A=30-second cooldown: a cooldown limits the frequency of runs but does not wait for the batch to finish; the first file can still start a run in the middle of the batch.
B=3000-second cooldown: it spaces runs 50 minutes apart but still starts a run as soon as the first file lands after the cooldown, so the run may begin mid-batch.
D=300 concurrent runs: concurrency controls how many runs may overlap, not how many files start a run; this would create duplicate work on partial batches.
T: Use Wait after last change to debounce batch arrivals into one run, and Minimum time between triggers to cap run frequency.

@ DBX-DEA D4 T4.3 applied use-case
S: Small event files arrive in a volume every few seconds all day. A file arrival trigger starts a job run that takes about 3 minutes, and the team sees back-to-back runs that keep the compute busy while each run handles only a few files. They want at most one run every 15 minutes and are fine with processing in larger groups. What should they configure?
A: Wait after last change of 900 seconds, so that the run starts 15 minutes after the final file, which never happens on a continuous stream
B: Switch to a table update trigger on the folder, because it can only fire a maximum of one run per quarter hour
C: A simple schedule of 15 minutes added in addition to the file arrival trigger, so that the trigger itself is limited
D: Minimum time between triggers of 900 seconds, so a new run is not started earlier than 15 minutes after the previous run completes
K: D
G: ## Cooldown versus debounce
When files arrive continuously, a debounce (Wait after last change) never fires because the timer is reset by every new file. A cooldown is the right rate control: **Minimum time between triggers** limits the job to at most one run per interval. After a run completes, files that arrive during the cooldown do not start a new run until the interval has elapsed, and the following run handles everything accumulated.
## Auto Loader pairing
A job triggered this way commonly reads the location with Auto Loader, which keeps a checkpoint and picks up all files that arrived since the last run.
W: Minimum time between triggers: a value of 900 seconds caps the job at one run per 15 minutes and lets each run process the files accumulated meanwhile.
X: A=900-second debounce: with a file every few seconds the timer restarts constantly, so the run would be delayed indefinitely and never start under a steady stream.
B=Table update trigger: it watches tables, not a folder of files, and it has the same kind of cooldown option; changing the trigger type does not give the limit by itself.
C=Extra schedule: a second schedule would add runs rather than limit those of the file arrival trigger, and a job configured with only one standard trigger does not combine them (multiple triggers are a separate beta feature).
T: For a constant stream of small arrivals use the cooldown (Minimum time between triggers); use the debounce only for bursts with quiet gaps.

@ DBX-DEA D4 T4.3 applied troubleshooting
S: A job with a table update trigger on `main.sales.orders` was working for weeks. After the job's run-as principal was changed to a new service principal, the job stops starting although the table is updated every hour. The team receives a failure notification about the trigger. What is the most likely cause?
A: Table update triggers can only watch tables owned by the run-as principal, and the table has a different owner
B: The new principal lacks SELECT on the monitored table, so the trigger fails to evaluate and no run starts
C: A table update trigger is cancelled automatically whenever the run-as principal changes, and has to be recreated from scratch
D: The service principal must have the CAN MANAGE permission on the table because triggers need to modify its change history
K: B
G: ## Permissions of a table update trigger
A table update trigger reads the metadata and change history of each monitored object. It does this as the job's **Run as** principal, which therefore needs `SELECT` on every monitored table, plus `USE CATALOG` and `USE SCHEMA` on its catalog and schema. For a Unity Catalog view it needs SELECT on the underlying tables.
## Failure mode
Without SELECT the trigger cannot evaluate and the job does not run. To be told about it, configure email or system destination notifications on job failure; they also fire when a table update trigger fails to evaluate.
W: Missing SELECT: the new run-as principal has no access to the monitored table, so the trigger fails to evaluate, which matches the trigger failure notification.
X: A=Table ownership: the trigger needs read access (SELECT), not ownership by the run-as principal.
C=Automatic cancellation: changing the run-as principal does not delete or cancel the trigger; its configuration stays, but it is evaluated with the new identity.
D=CAN MANAGE on the table: Unity Catalog tables do not use that permission, and the trigger only reads; it never modifies the change history.
T: A table update trigger evaluates as the Run as principal, which needs SELECT (plus USE CATALOG and USE SCHEMA) on every monitored table.

@ DBX-DEA D4 T4.3 applied use-case
S: A reporting job joins `main.sales.orders` and `main.sales.customers`, which are refreshed by two separate pipelines at different times each morning. The report must be built only after both tables have new data, and not twice. Which table update trigger configuration is right?
A: Monitor both tables and set Trigger when to All tables are updated, so the run waits until each monitored table has changed
B: Monitor both tables and set Trigger when to Any table is updated, so the run starts at the first change and waits for the second one
C: Create two jobs, each monitoring one table, and let the second start the first with a Run Job task
D: Monitor only the orders table, since an update of one table always implies that all tables joined with it are refreshed
K: A
G: ## Several tables, one trigger
A table update trigger can monitor one or more tables (Delta and Iceberg managed tables, external Delta tables, materialized views, streaming tables, views that depend on them). With several tables you decide how they combine:
- **Any table is updated**: the first change in any monitored table starts a run.
- **All tables are updated**: the run starts once each monitored table has changed.
Updates include inserts, updates, merges and deletes.
W: All tables are updated: the run starts when both tables have changed, so the report uses fresh data from both pipelines and runs once.
X: B=Any table: the run would start at the first refreshed table, with stale data in the other, and could run again when the second one is updated.
C=Two jobs: this chains two jobs with extra orchestration and still needs one of them to know when both tables are fresh; a single trigger already encodes the AND condition.
D=Monitor one table: tables are refreshed by independent pipelines, so a change in one table does not imply that the other has been refreshed.
T: With several monitored tables, All tables are updated gives an AND of the updates, Any table is updated an OR.

@ DBX-DEA D4 T4.3 applied use-case
S: A platform team wants one job to start when any table in a group of 14 Unity Catalog tables is updated. When saving the trigger they get an error although each table is readable by the run-as principal. Which requirement applies to a table update trigger monitoring more than 10 tables?
A: File events must be enabled for every monitored table, because without them a trigger is limited to 10 tables
B: All monitored tables must be located in the same schema, because a trigger can only watch one schema
C: The tables must be Delta streaming tables, since batch tables cannot be monitored in groups of more than ten
D: The job must run on a dedicated all-purpose cluster, which is needed to list change history for many tables
K: A
G: ## Limits of table update triggers
A trigger can monitor up to 25 tables. Up to 10 tables work with any supported location. Monitoring more than 10 requires file events to be enabled on the external location of every monitored table; if one of them has no file events, the trigger cannot be saved or fails to evaluate. Views count as the number of source tables they depend on.
## Why file events
With file events Databricks tracks ingestion metadata from cloud provider notifications, which makes table update detection faster and more scalable (the same feature improves Auto Loader and file arrival triggers). Tables in metastore root storage must first move to an external location.
W: File events: for more than 10 tables, every monitored table must have file events enabled, which lifts the limit from 10 to 25.
X: B=Same schema: tables from different catalogs and schemas can be monitored by one trigger, as long as the principal can read them.
C=Streaming tables only: managed tables, external Delta tables, materialized views and streaming tables are all supported sources, so the type is not the restriction.
D=Dedicated cluster: the trigger is evaluated by the Jobs service, not on a compute resource of the job, so no cluster type applies.
T: Table update triggers cap at 25 tables, and more than 10 requires file events on every monitored table.

@ DBX-DEA D4 T4.4 applied use-case
S: A vendor drops CSV files into a Unity Catalog volume at unpredictable times, between zero and eight times per day, and the data should be ingested soon after arrival. An hourly scheduled job mostly starts compute and finds nothing to do. Which change lowers cost while keeping latency low?
A: Replace the scheduled trigger with a file arrival trigger on the volume path and let the job ingest the new files with Auto Loader
B: Keep the hourly schedule and add a cron expression that runs every minute, so that any file is found as early as possible
C: Convert the job to continuous mode, so it keeps running and polls the volume for new files without any trigger
D: Replace the scheduled trigger with a table update trigger on the volume, which fires whenever any file is added
K: A
G: ## Time-based or data-driven
A scheduled trigger runs whether or not there is new data. When arrivals are irregular, the file arrival trigger is the documented fit: Databricks says it is useful when a scheduled job's efficiency is compromised by irregular new data arrivals. It makes a best-effort check about every minute and costs only the cloud listing calls, and runs start only when a new file exists.
## Pattern
Combine the trigger with Auto Loader (using `availableNow`) so that each run ingests exactly the files that arrived since the previous run.
W: File arrival trigger: runs happen only when a file lands, so there are no empty runs, and the latency is about a minute plus job start time.
X: B=Every-minute cron: this would start compute 1,440 times a day for the same few files, which maximizes the cost the team wants to cut.
C=Continuous mode: a continuously running job keeps compute allocated all day and is meant for always-on streaming; it would be far costlier than eight short runs.
D=Table update trigger: it watches tables, not a volume of files, so it cannot be pointed at a storage location.
T: For irregular file arrivals prefer a file arrival trigger over a frequent schedule: data-driven starts avoid empty runs.

@ DBX-DEA D4 T4.4 applied tradeoff
S: Each morning an executive dashboard must be refreshed by 06:00 for a compliance review. The source tables are loaded by upstream teams at different times between 01:00 and 04:30, and the job only needs to run once a day. Which trigger is the most suitable?
A: A table update trigger with All tables are updated, because it always starts the job before 06:00 at the latest
B: A file arrival trigger on the pipeline's output volume, as it is the only data-driven trigger type that supports a deadline
C: A scheduled trigger at 05:00 in a fixed time zone, since the deadline is a time of day and the data is always there by 04:30
D: A continuous trigger, so the job picks up the data as soon as it exists and also meets the deadline
K: C
G: ## Choosing between time and data
Use a **scheduled** trigger when the requirement is defined by the clock (a report due at a fixed time, a daily cut-off) and the inputs are reliably ready earlier. Use a **data-driven** trigger (file arrival, table update) when the start should follow the data, or when arrival times vary and are not known.
## Applying it
Here the business constraint is a time of day, and the upstream window ends at 04:30, so a schedule at 05:00 leaves a safety margin. A data trigger would start whenever the last table changes, but would give no assurance about the deadline if the data never arrives, and the job would not run at all.
W: Scheduled at 05:00: it is anchored to the compliance time, and all data is there by 04:30, so one run per day is simple and predictable.
X: A=Table update with All: it starts only when each table changed; if one upstream team is late or skips a day, the job does not run, so no deadline is guaranteed.
B=File arrival trigger: it is data-driven and has no deadline feature, and the source here is tables, not a folder of files.
D=Continuous trigger: it keeps the job running over and over, which does not fit a once-a-day report and wastes compute.
T: When the requirement is a clock deadline and inputs are ready earlier, use a scheduled trigger; data-driven triggers follow data, not deadlines.

@ DBX-DEA D4 T4.4 applied use-case
S: A job scheduled at 03:00 transforms a table that a separate ingestion pipeline refreshes between 01:30 and 04:00 depending on source delays. On late days the transformation reads yesterday's data and publishes stale results. Which trigger change fixes this without guessing a safer hour?
A: Use a simple schedule every 30 minutes so that one of the runs is certain to land after the refresh
B: Replace the schedule with a table update trigger on the refreshed table so the job starts after the table has been updated
C: Add a file arrival trigger on the source system's landing path, because it also reports when the table is complete
D: Move the schedule to 04:30 and rely on the ingestion pipeline never to finish later than 04:00
K: B
G: ## Pipeline dependency without a shared orchestrator
When two processes are owned separately and the finishing time varies, a clock-based schedule is a guess. A **table update trigger** starts the downstream job when the monitored table changes, so the dependency is on the data and not on the clock. It needs no knowledge of the process that updates the table and no always-running cluster. With advanced options, Wait after last change can hold the run until a multi-step update has settled.
## When it does not apply
If the producing and consuming steps belong to one job, use task dependencies; table update triggers are for separate jobs or external writers.
W: Table update trigger: the transformation starts after the table commits, on early and late days alike, so stale reads from the timing guess are gone.
X: A=Every 30 minutes: it creates up to 48 runs a day and still can read stale data on runs before the refresh, so correctness is not guaranteed.
C=File arrival trigger: it watches files in a Unity Catalog location, but the dependency here is on a table refresh, and the files landing say nothing about the table being completed.
D=Later fixed time: this is still a guess; the next slow day will break it again, and results are delayed on all fast days.
T: When a downstream job depends on a table refreshed by another process at varying times, trigger on the table update instead of guessing a time.

@ DBX-DEA D4 T4.4 applied tradeoff
S: A job pulls a daily snapshot from a third-party REST API every night. The API has no change notification, writes nothing to a Unity Catalog volume or table beforehand, and the data of a day is available after midnight UTC. Which trigger fits?
A: A file arrival trigger on the volume where the job writes its output, which fires when the job has written the snapshot
B: A table update trigger on the target table, which fires when the table is updated by the job itself
C: A continuous trigger, which calls the API in a loop and starts a new run every time one completes
D: A scheduled trigger shortly after midnight UTC, because there is no table or file in Databricks whose change can start the run
K: D
G: ## Data-driven triggers need something in Databricks to watch
File arrival triggers watch a Unity Catalog volume or external location; table update triggers watch Unity Catalog tables (and shared or system tables). If the source is an external system that exposes only an API, nothing observable exists before the job runs, so the start of the job must be time-based (or started by an external orchestrator calling the Jobs API).
## Anti-pattern
Triggering on the job's own output is circular: the trigger would fire after the data was already loaded.
W: Scheduled trigger: the data is available after a known time of day and no Databricks object signals it, so a schedule shortly after midnight UTC is the right start.
X: A=File arrival on output: the output only exists after the job ran, so the trigger could never start the first run.
B=Table update on the target: the same circle; the target changes only when the job has already loaded it.
C=Continuous: it would call the API in a loop all day, wasting compute and API quota, for a snapshot that changes once per day.
T: Choose a scheduled trigger when the source is an API or other system with nothing in Unity Catalog to observe; data-driven triggers require a watchable table or location.

@ DBX-DEA D4 T4.4 applied tradeoff
S: Sensor events must be processed within seconds of arrival, around the clock, and the job reads from a streaming source with a stateful query. The team considers file arrival triggers, scheduled triggers and continuous jobs. Which option matches the requirement?
A: A job in continuous mode, which keeps one run active and restarts it with exponential backoff when it fails
B: A scheduled trigger of every 10 seconds, since the scheduler guarantees low-latency starts at exactly that interval
C: A file arrival trigger, as it evaluates on every file creation event with a latency of milliseconds
D: A table update trigger with a wait after last change of 600 seconds to batch the sensor events
K: A
G: ## Continuous jobs
Continuous mode is the recommended trigger for always-on streaming workloads. There is only one active run; when it ends or fails, the scheduler starts a new run, normally within about a minute. Failures are handled with exponential backoff and no limit on retries, and the backoff resets once the job is healthy.
## Why not the others
The scheduler is not intended for low-latency jobs (runs may be delayed by several minutes) and enforces a minimum of 10 seconds between runs. File arrival triggers check about every minute on a best-effort basis, which is micro-batch speed at best.
W: Continuous mode: one run stays active for the stateful stream, and a failed run is restarted automatically with exponential backoff, which fits second-level latency around the clock.
X: B=10-second schedule: the minimum interval is 10 seconds, but the job start time itself takes much longer, and the scheduler is not intended for low-latency work.
C=File arrival trigger: it is a best-effort check about every minute and then must start a run, so it cannot reach second-level latency or keep stream state.
D=Table update trigger with a 600-second wait: it delays runs by ten minutes, the opposite of the latency requirement.
T: Always-on, low-latency streaming belongs in a continuous job; schedules and file arrival triggers are for batch-style runs.

@ DBX-DEA D4 T4.4 applied use-case
S: A job is started by a file arrival trigger on `/Volumes/main/landing/events/`. The notebook task should ingest exactly the files that arrived since the previous run, even when runs are skipped or delayed, and must not reread files. What should the notebook do?

B: Read the whole folder with spark.read on every run and remove duplicates from the target table with a final DISTINCT step
C: Read with Auto Loader and write with trigger availableNow, using a checkpoint outside the monitored path
D: Delete each processed file from the volume so the next run sees only unprocessed files
K: C
G: ## Trigger plus Auto Loader
The file arrival trigger only says that something new exists; it does not remember what was processed. Databricks documents using Auto Loader in the triggered job: it discovers new files incrementally with exactly-once processing, tracked in a checkpoint.
```

  .option("cloudFiles.format", "json")
  .option("cloudFiles.schemaLocation", checkpoint)
  .load(file_location)
  .writeStream.option("checkpointLocation", checkpoint)
  .trigger(availableNow=True).toTable(sink_table)
```
The checkpoint must be outside the monitored location, so its own files do not start new runs.
W: Auto Loader with availableNow: the checkpoint tracks processed files, so each run ingests exactly the new files and stops, whatever the number or timing of runs.

D=Deleting processed files: it needs delete rights and loses the source copy for replay; a failure between processing and deletion leads to duplicates or loss.
T: Pair a file arrival trigger with Auto Loader and trigger availableNow; the checkpoint, not the trigger, tracks what is processed.

G: ## Jobs system tables
If you can read the `system.lakeflow` schema you can query runs and tasks across the account: `jobs`, `job_tasks`, `job_run_timeline`, `job_task_run_timeline` (plus pipeline tables).   count_if(result_state = 'FAILED') / count(*) AS failure_rate

G: ## How the run status is determined
Databricks decides whether a run was successful from the outcome of its **leaf tasks**, which are tasks with no downstream dependency. The outcomes are:
- **Succeeded**: all tasks were successful.
- **Succeeded with failures**: some tasks failed, but all leaf tasks were successful.
- **Failed**: one or more leaf tasks failed.
- **Skipped**, **Timed Out**, **Canceled** for runs not started, exceeding time, or stopped.
## This scenario

D=Skipped: a skipped run is one that was never started, for example for exceeding maximum concurrent runs; here the run started and had a failing task.
T: Run status is decided by leaf tasks: any failed or unrun leaf makes the run Failed, and Succeeded with failures needs all leaves to succeed.
