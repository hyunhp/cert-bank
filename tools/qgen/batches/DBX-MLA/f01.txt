S: Which TWO benefits do data scientists get from running AutoML at the start of a project? (Select TWO)
A: It produces a model that beats hand-built ones on most datasets, which makes manual modeling work unnecessary
B: It builds baseline models fast and generates a data exploration notebook with summary statistics of the dataset
C: It logs each trial as an MLflow run with its parameters, metrics and model, so trials can be compared and registered

K: B,C
G: ## What AutoML is good for
AutoML accelerates the early part of the lifecycle:
- It **cleans and prepares data** and builds baselines across algorithms, with a data exploration notebook that has summary statistics. Baselines tell you whether the data can solve the problem and set a bar to beat.
- Each trial is recorded in **MLflow** (parameters, metrics, artifacts, model), so you can sort runs, compare them and register one model.
- It generates trial notebooks, so you can start from working code.
It does not replace judgement: you still evaluate on held-out data, choose the business metric, and decide whether to deploy.
W: B=Baselines and exploration: AutoML builds baseline models quickly and summarizes the dataset, which shortens EDA.
C=MLflow tracking: every trial is an MLflow run, so comparison and registration are straightforward.
X: A=Beats hand-built models: no tool can promise this; AutoML is a baseline and starting point, and domain features can beat it, so manual modeling stays useful.
D=Deployment at the end of the experiment: AutoML presents results. Registration and deployment are separate decisions, typically with validation first.
E=Replaces held-out evaluation: AutoML evaluates on validation and test splits, and you still check results against your requirements; trial metrics are not production accuracy.
T: AutoML gives fast baselines, an exploration notebook and MLflow-tracked trials to build on.

@ DBX-MLA D1 T1.5 applied use-case
S: A compliance officer asks which models were trained with a customer feature table before a column in it is changed. Which capability of Unity Catalog feature tables answers this?
A: Lineage captured when models are logged with Feature Engineering, shown in Catalog Explorer
B: The AutoML data exploration notebook, which lists the models that trained on the feature table
C: The registered model's alias, which stores the feature tables used to train that version
D: The cluster event log, which records the feature tables read by notebooks on the cluster
K: A
G: ## Feature governance and lineage
When you train and log a model with a training set built from Unity Catalog feature tables, Databricks stores the feature specification with the model and tracks **lineage** across the feature tables, functions and models. In Catalog Explorer you can open a feature table and see the models (and notebooks and jobs) that use it, which is the impact analysis needed before changing a column.
The legacy Workspace Feature Store had lineage as well, but at workspace level. In Unity Catalog the lineage sits with the other governance metadata.
W: Feature lineage: models trained and logged with Feature Engineering in Unity Catalog are linked to their feature tables, so Catalog Explorer lists the models affected by a change.
X: B=AutoML exploration notebook: it summarizes the input dataset and does not track downstream consumers.
C=Alias: an alias is a pointer to a model version and does not store training tables.
D=Cluster event log: it records cluster events like start and resize, not table-level lineage.
T: UC feature tables plus models trained from them give lineage you can inspect before changing a table.

@ DBX-MLA D1 T1.15 applied definition
S: A team starts a new project in a recently created Databricks account whose workspace has a Unity Catalog default catalog. A teammate suggests using the Workspace Model Registry because it is familiar. What does Databricks documentation say about this plan?
A: It is a legacy registry that is disabled for such accounts, and Models in Unity Catalog are the recommended choice
B: It works as in older accounts, since both registries are supported side by side and the choice is a matter of habit
C: It has to be enabled per user in the Unity Catalog metastore admin console before the team can register models
D: It is required, because Unity Catalog stores models as Delta tables rather than as registered model versions
K: A
G: ## Status of the Workspace Model Registry
The docs label the Workspace Model Registry as legacy. Key points:
- Starting in April 2024, Databricks disabled it for workspaces in new accounts where the workspace's default catalog is in Unity Catalog.
- It is still supported where it already exists, including with MLflow 3, but to use it from MLflow 3 you must call `mlflow.set_registry_uri("databricks")` because the default registry URI in MLflow 3 is `databricks-uc`.
- Databricks recommends Models in Unity Catalog for governing and deploying models and documents a migration path for model versions.
Older names in the exam outline that refer to "workspace registry" and "stages" describe this legacy registry.
W: Legacy and disabled: starting in April 2024 Databricks disabled the Workspace Model Registry for new accounts whose default catalog is in Unity Catalog, so the project should use Models in Unity Catalog, as Databricks recommends.
X: B=Both supported side by side: the registry is labeled legacy and disabled for these new accounts, so the plan would not work.
C=Per-user enablement: there is no such per-user opt-in switch. The point is that the registry is disabled for these workspaces.
D=Models as Delta tables: Unity Catalog has a registered-model securable type with model versions; models are not stored as tables.
T: Workspace Model Registry = legacy (disabled for new accounts with UC default catalog); use Models in Unity Catalog.
