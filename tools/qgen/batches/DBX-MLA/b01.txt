@ DBX-MLA D1 T1.1 applied use-case
S: A retail company is setting up MLOps on Databricks with Unity Catalog. Data scientists experiment freely, an ML engineering team runs automated tests, and only a locked-down process may touch production. Which design follows the Databricks recommendation for isolating these stages?
A: Keep one shared catalog for all ML assets and tell the stages apart with "dev_", "test_" and "prod_" prefixes on table and model names
B: Create a separate execution environment per stage (development, staging, production) with its own compute and jobs, and a matching catalog for its data and models
C: Use a single development workspace for everything and mark the stage of each model version by moving it between the legacy registry stages "Staging" and "Production"
D: Separate only the production environment, and let development and staging share one catalog so that test results are visible to the data scientists immediately
K: B
G: ## Why ML assets move through stages
MLOps manages three kinds of assets: code, data and models. Early in development the assets change often and are not rigorously tested, so access can be wide. In the middle stage they are tested automatically. In production they are tightly controlled. Mixing these in one place means an experiment can break a production job or read data it should not.
## The recommended layout
Databricks recommends a separate **execution environment** per stage, with clearly defined transitions between them. An execution environment is the place where code creates or consumes models and data: compute instances, runtimes, libraries and automated jobs. The common names are development, staging and production. In Unity Catalog this is usually expressed as a `dev`, `staging` and `prod` catalog (three-level names such as `prod.ml.churn_features`), so privileges can differ per stage. Models created in development are registered to the `dev` catalog.
Note the legacy workspace model registry used fixed stages (Staging, Production) on one model; Unity Catalog models use catalogs for environments and aliases for roles such as Champion.
W: Separate environments per stage, each with its own compute and a matching catalog, give each stage its own access control and clear promotion points. This is the layout the Databricks MLOps guidance describes.
X: A=Prefixes in one catalog: prefixes are only a naming convention. They give no separate privileges, compute or jobs, so a mistake in development can still touch production assets.
C=One workspace with legacy stages: moving versions between stage labels does not isolate compute, data or access, and registry stages belong to the legacy workspace registry rather than the Unity Catalog approach.
D=Isolate only production: development and staging have different purposes (free experiments versus automated, repeatable tests). Merging them removes the clean testing step that gates a release.
T: One environment per stage (dev, staging, prod), each with its own compute and catalog, and defined transitions between them.
V: Unity Catalog, MLflow

@ DBX-MLA D1 T1.1 applied definition
S: In most situations, which approach does Databricks recommend for moving an ML solution from development to staging and production?
A: Promote the trained model artifact from environment to environment, so that the exact binary tested in staging is the one served in production
B: Promote the evaluation metrics only and re-train the model by hand in production when the numbers look good
C: Promote the training code, so the production model is trained by production code that passed review and integration tests
D: Promote the data from the development catalog and let each environment generate its own pipeline code on the fly
K: C
G: ## Deploy code or deploy models
There are two deployment patterns:
- **Deploy models**: train once in development and copy the model artifact to production.
- **Deploy code**: move the ML pipeline code (feature computation, training, validation, inference) from the development branch to staging and then the release branch, and let each environment run it.
## Which Databricks recommends
In most situations Databricks recommends deploying code. All code in the ML development process then goes through the same review and integration testing as any software, and the production model is trained on production code with access to production data. Deploying models can be right when training is very expensive or production data cannot be used for training in the target environment, but it is the exception.
W: Code promotion makes every change pass code review and integration tests, and the production model is trained by production code, so the training process itself is what gets promoted.
X: A=Promote the artifact: this is the "deploy models" pattern. It skips review of the training code and does not prove the model can be retrained in the target environment, so it is not the default recommendation.
B=Metrics only: metrics are evidence, not a deployable asset. Manual re-training in production is not repeatable and bypasses version control and automated tests.
D=Promote data and generate code: data is not the unit of promotion, and code created on the fly has no review or version history. Code belongs in Git.
T: Default MLOps pattern: promote code, not models, so production models are trained by reviewed and tested production code.

@ DBX-MLA D1 T1.1 applied use-case
S: A validation job loads a newly trained model from Unity Catalog and runs format checks, required-metadata checks and performance checks on selected data slices. The model passes every check. What does the recommended Databricks workflow do next?
A: The model is assigned the "Challenger" alias so a deployment step can promote it to "Champion" or compare it with the current Champion
B: The model is deleted from the catalog and re-registered under the name of the production model, replacing its earlier versions entirely
C: The AutoML data exploration notebook is regenerated so that reviewers can approve the model
D: The model stage is moved to "Production" in the legacy registry, which immediately starts serving traffic
K: A
G: ## Validation then deployment
After training, the model is registered to Unity Catalog in the catalog of the environment that ran the pipeline. A **model validation** task takes the model URI from the training task (passed with task values in a multitask job), loads the model, and runs checks. The checks depend on context: basic format and metadata checks, and for regulated industries compliance checks and performance on data slices.
If the checks pass, the model gets the **Challenger** alias. If they fail, the process ends and can notify users. A **model deployment** task then either promotes the Challenger directly by moving the **Champion** alias to the new version, or compares Challenger and Champion first. Aliases are named pointers to model versions, so promotion is an alias update, not a copy.
W: Passing validation earns the Challenger alias, which marks the version as a candidate for the deployment step and lets it be compared with the current Champion.
X: B=Delete and re-register: replacing versions destroys lineage and history. Versions are kept and an alias moves between them.
C=Regenerate AutoML notebook: AutoML notebooks come from the exploration and baseline step and are not an approval mechanism.
D=Legacy stage change: stages belong to the legacy workspace registry and moving one does not itself serve traffic. Serving is configured separately by the deployment step.
T: Pass validation, get the Challenger alias; the deployment step then moves Champion by an alias update.
V: Unity Catalog, MLflow, Lakeflow Jobs

@ DBX-MLA D1 T1.1 applied definition
S: What is the main purpose of the staging stage in the recommended Databricks MLOps workflow?
A: To let data scientists explore data interactively in notebooks and decide which features may be useful
B: To run unit and integration tests in CI over all ML pipeline code, then cut a release branch that starts production
C: To serve the model to real users for the first time and gather business feedback before any tests run

G: ## Three stages, three goals
- **Development**: experimentation. Data scientists run EDA, build features and models, and the output is ML pipeline code.
- **Staging**: test the pipeline code to confirm it is ready for production. @ DBX-MLA D1 T1.2 advanced troubleshooting
S: A team enables Photon on compute running Databricks Runtime ML and sees no speed-up when training a scikit-learn RandomForest and an XGBoost model on a pandas DataFrame, though their Spark SQL feature engineering became faster. What explains this?
A: Photon only works with tables stored outside Unity Catalog, so the training data must be moved out of it
B: Photon speeds up Spark SQL and DataFrame work, but not Python packages such as XGBoost
C: Photon is disabled on Dedicated access mode, so every query ran on the standard engine
D: Photon requires GPU instance types for model training, so CPU training never benefits from it
K: B
G: ## What Photon accelerates
Photon is a native vectorized engine. On Runtime ML (when enabled) it improves performance for Spark SQL, Spark DataFrames, feature engineering, GraphFrames and `xgboost4j` (the JVM XGBoost). It is not expected to help Spark RDDs, Pandas UDFs and non-JVM languages such as Python. So the Python XGBoost package, PyTorch and TensorFlow see no gain, and scikit-learn training is also Python.
Also, Spark RDD APIs and Spark MLlib have limited compatibility with Photon, and with large data they can hit Spark memory issues.
## Practical rule
Use Photon for the data-preparation steps, and look elsewhere (bigger or GPU instances, distributed libraries, parallel tuning) to speed up single-node Python training.
W: Photon is a SQL and DataFrame engine on the JVM side; scikit-learn and Python XGBoost training run in Python processes it does not touch, which matches the observed split.
X: A=Outside Unity Catalog: Photon works with Unity Catalog tables. The location of the data does not explain this.
C=Dedicated mode disables Photon: the ML compute default is Dedicated and Photon can be enabled on it. The Spark SQL speed-up proves it runs.
D=Requires GPU: Photon targets CPU query processing and does not depend on GPUs.
T: Photon speeds up Spark SQL/DataFrame work, not Python ML libraries such as scikit-learn, XGBoost or PyTorch.

@ DBX-MLA D1 T1.4 advanced troubleshooting

G: ## AutoML library requirements
AutoML relies on the `databricks-automl-runtime` package and on the library versions preinstalled in Runtime ML. The documented requirement is that **no additional libraries other than those preinstalled** should be installed on the cluster, and any modification (removal, upgrade or downgrade) to existing library versions makes runs fail because of incompatibility.
Fix: run AutoML on a clean Runtime ML cluster (or revert the change). Use a separate cluster, or notebook-scoped installs, for projects that need other versions.
