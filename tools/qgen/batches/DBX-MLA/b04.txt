@ DBX-MLA D1 T1.16 applied use-case
S: A bank retrains its fraud model every week. Security policy forbids reading production transactions from the development workspace, and the team uses Git and CI/CD. Which promotion approach fits best?
A: Train once in development on a sample, then copy the model artifact to staging and production each week
B: Promote the training code through staging to production and train the model in the production environment
C: Train in staging on exported production extracts, then register the resulting model for production use
D: Train in development on synthetic data and let production serve that model until the next release
K: B
G: ## Two things you can promote
Models are produced by code, but the code and the model artifact can change at different times. Databricks describes two patterns.
- **Deploy code**: the training code is written in development and moves to staging and then production. The model is trained in each environment: in development during exploration, in staging on a limited subset of data as an integration test, and in production on the full production data to create the final model.
- **Deploy models**: the artifact is trained once in development, tested in staging and then deployed to production.
Databricks recommends deploy code in most situations and builds its recommended MLOps workflow around it.
## When production data cannot leave production
If access to production data is restricted, a model can only be trained on that data inside the production environment. The deploy code pattern allows exactly that, and because the training code is reviewed and tested before it reaches production, automated weekly retraining is safer.
W: Promoting the code means the weekly retraining job runs in production, where the transactions may be read. The code was reviewed and integration tested in staging, so automatic retraining is low risk, and no production data ever has to move to development.
X: A=Copying a development artifact: a model trained in development never saw production transactions, and the weekly retraining would depend on a hand-off from development, which is the tricky part of the deploy models pattern.
C=Staging with exported extracts: copying production data out to staging breaks the stated policy and creates another copy of sensitive data to govern. The model should be trained where the data may be read.
D=Synthetic data in development: a fraud model trained on synthetic data will not reflect real transaction patterns, and it would not be retrained weekly as the policy of the bank requires.
T: When production data is restricted or retraining is frequent and automated, promote the code and train in production (deploy code).

@ DBX-MLA D1 T1.16 applied use-case
S: A team trains one very large deep learning model that takes days on a GPU cluster and is retrained only a few times a year. All work happens in a single Databricks workspace, and the team has no external Git repository or CI/CD process. Which promotion approach fits best?
A: Deploy code, so that the full training run is repeated in staging and again in production
B: Deploy code, but with training scheduled nightly in production to keep the model fresh
C: Hybrid, with code deployed to staging, retrained there and the data copied to production
D: Deploy models, so the artifact is trained once, tested in staging and then promoted
K: D
G: ## Choosing the artifact to promote
The deploy models pattern is described in the documentation as a good fit when one or more of these apply:
- model training is very expensive or hard to reproduce;
- all work is done in a single Databricks workspace;
- the team is not working with external repositories or a CI/CD process.
Its advantages are a simpler hand-off for data scientists and training only once. Its disadvantages are that production data may not be reachable from development, that automatic retraining is tricky, and that supporting code (feature engineering, inference, monitoring) must be deployed to production separately.
## What this scenario shows
Every condition for deploy models is present: days-long training, one workspace and no CI/CD. Repeating the training in every environment would multiply a very expensive job by three for no benefit.
W: Training once and promoting the artifact avoids paying for the multi-day GPU run in staging and production. With one workspace and no CI/CD, a simple hand-off of the validated model is the lowest-friction path.
X: A=Full training in every environment: this repeats the multi-day GPU run in staging and production, which is the cost that the deploy models pattern is meant to avoid when training is expensive.
B=Nightly production training: the model is retrained only a few times a year, so nightly retraining would spend a large amount of compute for no business reason.
C=Hybrid with copied data: the hybrid approach trains in staging and then deploys the model to production, but it is about moving the model, not the data. It also adds operating cost in staging for a team without CI/CD.
T: Expensive-to-train models in a single workspace without CI/CD favor deploy models; otherwise default to deploy code.

@ DBX-MLA D1 T1.16 advanced tradeoff

A: A hybrid: deploy code to staging, train there on the full data, then deploy the model to production
B: Deploy code only, running the full training twice, in staging and in production

G: ## A middle path
Deploy code and deploy models are the two main patterns, but the documentation also mentions a hybrid. If the situation requires that the model be trained in staging over the full production dataset, you can deploy code to staging, train the model there, and then deploy the model to production.
- It saves the cost of training again in production, because the production environment receives a finished model.
- It adds an extra operational cost in staging, because staging now needs access to the full data and enough compute.
## When it is useful
Use it when integration testing needs a full-size training run and a second full run in production would be wasteful. The model is promoted (as a copy of a model version, see the Unity Catalog promotion example), while the code was promoted into staging.
W: Training in staging on the full data lets the team test with production-sized data, and promoting the resulting model avoids a second expensive run in production. The cost is extra work in staging.
X: B=Two full training runs: this repeats the expensive run in production, which is the cost the team wants to avoid.
C=Development on production data: restricted production data usually is not reachable from development, which is a disadvantage of deploy models, so it cannot be assumed here.
D=Skipping staging: removing the integration test environment discards the validation the team asked for, and unit tests alone do not exercise training on full-size data.
T: Hybrid = deploy code to staging, train there on full data, deploy the model to production.

G: ## Environments are catalogs
In Unity Catalog the environment of a model is expressed in its three-level name `catalog.schema.model`. A model named `staging.ml_team.fraud_detection` lives in the staging environment and `prod.ml_team.fraud_detection` in production. Using the `prod` catalog does not by itself mean the version serves traffic: the catalog gives the environment and its governance rules, and aliases give the deployment status.
## Copying a version
Where retraining across environments is too expensive, you copy a model version from one registered model to another with the MLflow Client API `copy_model_version(src_model_uri, dst_name)`. The caller needs `EXECUTE` on the source model, `USE CATALOG` and `USE SCHEMA` on both locations, and either ownership of the destination model or `CREATE MODEL VERSION` on it. No other promotion rules are needed, since access control on each environment already decides who can promote. After the copy and any validation, an alias such as `Champion` marks the version for deployment.
W: `copy_model_version` creates a new version of the production registered model from the staging version, with governance enforced by the privileges on both models.
X: B=Stage transition: stages are not supported for models in Unity Catalog, and a stage change would not move the model to another catalog anyway.
C=An alias on the staging model: setting an alias on the destination name only points to a version that already exists in that model. The version is not in the production model, and the alias is about deployment status, not environment.
D=Registering onto itself: this registers a version under the same staging name, so nothing reaches the production registered model.
T: In Unity Catalog, promote a model across environments with `copy_model_version` between catalog-scoped models, then mark it with an alias.

S: Before deployment, each new model version in Unity Catalog is validated. The team wants to label version 4 of `prod.ml_team.fraud_detection` with `validation_status = approved` so reviewers can see it in Catalog Explorer. Which call does this?

G: ## Tags on registered models and model versions
Tags are key-value pairs that you attach to registered models and model versions to label them by function or status. A registered model might carry `task:question-answering`, while versions can carry `validation_status:pending` or `validation_status:approved`.
## The Client API
- `set_registered_model_tag(name, key, value)` and `delete_registered_model_tag(name, key)` work on the whole model.
- `set_model_version_tag(name, version, key, value)` and `delete_model_version_tag(name, version, key)` work on one version.
Tags can also be set in the UI. The tool you need depends on the level you want to label. A status that applies to version 4 only has to be a version tag, because a registered-model tag would apply to every version.
W: `set_model_version_tag` takes the model name, the version number, the key and the value, so the tag is attached to version 4 only and shows up on that version.
X: A=Registered model tag: this labels the whole registered model, so the approval would appear to cover all versions, including ones that have not been validated.
B=`mlflow.set_tag`: this sets a tag on the active experiment run, not on a model version in Unity Catalog.
C=Alias named `approved`: an alias is a mutable pointer used for deployment, such as Champion. It is not a key-value label, so no value `approved` is stored, and the reviewers would see an alias rather than a validation status.
T: Version-level status goes in a model version tag; model-wide labels use a registered model tag.

@ DBX-MLA D1 T1.18 applied use-case
S: Version 7 of `prod.ml_team.churn` (the challenger) passed validation, and version 5 is the current champion. A scheduled batch job loads `models:/prod.ml_team.churn@Champion`. Which single action makes the next batch run score with version 7 and requires no change to the job?

G: ## Aliases as movable pointers
A model alias is a mutable, named reference to one version of a registered model. It indicates the deployment status of the version: the version that serves production carries `Champion` and the candidate under test can carry `Challenger`. Workloads target the alias, not a number.
- `client.set_registered_model_alias(name, "Champion", version)` creates or moves the alias.
- `models:/<catalog>.<schema>.<model>@Champion` is the URI that resolves the alias.
## What happens at promotion
Reassigning `Champion` from version 5 to version 7 is the whole promotion. A batch inference workload that resolves the alias picks the new version on its next execution, which decouples deployments from the jobs. Model serving endpoints can also be updated by looking up the version behind the alias.
W: Setting the alias to version 7 moves the pointer. The job resolves `@Champion` at run time, so the next run loads version 7 without any code change.
X: A=Deleting version 5: that destroys the previous champion and removes the rollback option. Without an alias on version 7, the URI would not resolve to it either.
B=Renaming the model: the job loads by name and alias, so renaming breaks the URI instead of promoting. Ordering of versions has no meaning for alias resolution.
D=Hard-coded version in the job: this works only until the next promotion, and it defeats the purpose of aliases because every promotion needs a job edit.
T: Promote a challenger to champion by reassigning the `Champion` alias to its version; consumers that load `@Champion` follow.

G: ## Rollback with aliases
Moving an alias does not delete anything. Version 5 is still a version of the registered model with its artifacts and metadata; it simply no longer carries `Champion`. Because consumers resolve `models:/<model>@Champion` at load time, pointing the alias back at version 5 reverts them on their next load or run.
- No retraining, copying or redeploying is needed.
- The alias change is a single call, `set_registered_model_alias(name, "Champion", 5)`, and requires ownership of the registered model plus `USE SCHEMA` and `USE CATALOG`.
## Why this is a design advantage
Using version numbers in consumers makes a rollback a code change in every consumer. Using an alias makes it a metadata change in one place.
W: Version 5 is intact, so setting `Champion` back to it reverts all alias-based consumers in a single call without retraining or touching job code.
X: B=Retraining: promotion does not delete the previous champion. Retraining would take longer and may not give the same model.
C=Copy to a new model: this creates a duplicate and forces every consumer to change its model name, which is the opposite of a quick, central rollback.
D=Deleting the alias: with no `Champion` alias the URI `models:/<model>@Champion` does not resolve to any version. It does not fall back to the previous one, so consumers would fail.
T: Roll back by pointing the alias at the previous version; versions are not deleted when the alias moves.

The mean and standard deviation are sensitive to extreme values: a few huge orders raise the mean and inflate the standard deviation.
