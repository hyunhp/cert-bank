@ DBX-MLA D1 T1.11 applied use-case
S: A team ran 60 hyperparameter trials that each logged a metric named `rmse` to the experiment with ID `1234`. A notebook cell must return only the single run with the lowest `rmse` as a pandas DataFrame. Which call does this?
A: `mlflow.search_runs(experiment_ids=["1234"], order_by=["metrics.rmse DESC"], max_results=1)`
B: `mlflow.get_run("1234")` followed by a sort of its `data.metrics` dictionary by value
C: `mlflow.search_runs(experiment_ids=["1234"], order_by=["metrics.rmse ASC"], max_results=1)`
D: `mlflow.search_runs(experiment_ids=["1234"], filter_string="metrics.rmse = MIN")`
K: C
G: ## Finding runs programmatically
Every MLflow run records its parameters and metrics on the tracking server that Databricks hosts. To analyze them in code you query the experiment instead of opening runs one by one. The MLflow Python `mlflow.search_runs` function returns a pandas DataFrame with one row per run; the Spark data source for experiments returns a Spark DataFrame instead.
## The arguments that matter
- `experiment_ids` limits the search to one or more experiments (note that `1234` here is an experiment ID, not a run ID).
- `filter_string` keeps only matching runs, for example `metrics.rmse < 1.0`.
- `order_by` sorts runs by a key with `ASC` or `DESC`, for example `metrics.rmse ASC`.
- `max_results` caps the number of rows returned.
Sorting by the metric in the direction where "better" comes first and keeping one row is the standard way to get the best run. For an error metric such as RMSE, smaller is better, so the order is ascending.
W: Sorting ascending by `metrics.rmse` puts the smallest error first, and `max_results=1` keeps only that row, so the DataFrame holds exactly the best run.
X: A=Descending order: `DESC` puts the largest RMSE first, so this returns the worst run of the 60, not the best.
B=`mlflow.get_run`: it takes a run ID, not an experiment ID, and returns one run object. It cannot rank 60 runs, and sorting the metrics of a single run says nothing about the other trials.
D=MIN in the filter: `filter_string` compares a metric with a literal number; it has no aggregate such as `MIN` to pick the lowest value among runs. Ranking is done with `order_by`.
T: Best run = `search_runs` ordered by the metric (ASC for error, DESC for score) with `max_results=1`.

@ DBX-MLA D1 T1.11 applied use-case
S: Several training runs in one experiment log `val_accuracy`. The team wants the run with the highest `val_accuracy` programmatically with MLflow. Which TWO approaches return that run? (Select TWO)
A: Call `mlflow.last_active_run()` after the final trial, because it returns the run with the best metric in the current session
B: Read `mlflow.get_experiment(exp_id).best_run` after the trials finish, because the experiment object tracks its top run
C: Call `mlflow.search_runs([exp_id])` with default ordering and take the first row, because the default order ranks runs by metric quality
D: Call `mlflow.search_runs([exp_id], order_by=["metrics.val_accuracy DESC"], max_results=1)` and read the single row of the returned DataFrame
E: Call `MlflowClient().search_runs([exp_id], order_by=["metrics.val_accuracy DESC"], max_results=1)` and take the first element of the returned list
K: D,E
G: ## Two entry points for the same query
MLflow offers the search in two forms. The fluent function `mlflow.search_runs` returns a pandas DataFrame, which is convenient for analysis in a notebook. The `MlflowClient().search_runs` method of the Client API returns a list of `Run` objects (with `run.info.run_id`, `run.data.metrics`, `run.data.params`), which is convenient when you only need IDs and values to pass on to the next step, such as model registration.
Both accept `order_by` and `max_results`, so "best run" is the same recipe with either: order by the metric in the better direction and keep one result.
## What is not available
There is no "best run" property on an experiment, and the search does not rank by quality unless you ask it to. The default ordering is by run start time, newest first.
W: D=DataFrame search: ordering by `metrics.val_accuracy DESC` puts the highest accuracy first and `max_results=1` keeps it, giving a one-row pandas DataFrame.
E=Client API search: `MlflowClient().search_runs` takes the same `order_by` and `max_results`, so the first element of the returned list is the run with the highest accuracy.
X: A=Last active run: `mlflow.last_active_run()` returns the most recently active run of the current process. Recency has nothing to do with the metric, so it may well be a poor trial.
B=Experiment `best_run`: the experiment object has no such attribute. MLflow does not pick a winner on its own; you query for it.
C=Default ordering: unless `order_by` is given, results are ordered by start time, so the first row is the newest run, not the most accurate.
T: MLflow never ranks runs for you: use `order_by` on the metric plus `max_results=1`, with `mlflow.search_runs` (DataFrame) or `MlflowClient().search_runs` (list of Run objects).

S: A notebook runs `best = mlflow.search_runs(["1234"], order_by=["metrics.rmse ASC"], max_results=1)`. The next cell must pass the best run's ID and its logged `max_depth` hyperparameter to the registration step. Which code reads them?
A: `best[0].info.run_id` and `best[0].data.params["max_depth"]`
B: `best.loc[0, "run_id"]` and `best.loc[0, "params.max_depth"]`
C: `best["run_id"]` and `best["max_depth"]`
D: `best.info.run_id` and `best.data.params.max_depth`
K: B
G: ## Which object do you hold?
The return type decides the syntax, and the two search APIs differ.
- `mlflow.search_runs` returns a pandas DataFrame. Each run is a row, with a `run_id` column and one column per logged value named `metrics.<name>`, `params.<name>` and `tags.<name>`.
- `MlflowClient().search_runs` returns a list of `Run` objects, read with attribute access such as `run.info.run_id` and `run.data.params["max_depth"]`.
Parameters are stored as strings, so the `params.max_depth` cell holds text such as `"8"` and needs a cast (`int(...)`) before it is used as a number.
W: The call returns a DataFrame, so the run ID is the `run_id` column and the hyperparameter sits in the column `params.max_depth`, both read from row 0.
X: A=List-of-Run syntax: indexing `best[0]` and reading `.info` / `.data` works for the Client API, which returns Run objects. On a DataFrame, `best[0]` looks for a column named 0 and raises a KeyError.
C=Missing prefix: the column is called `params.max_depth`, not `max_depth`, and `best["run_id"]` returns a whole column (a Series), not the single value.
D=Attribute access on the DataFrame: a DataFrame has no `info` or `data` attributes. Those belong to `Run` objects returned by the Client API.
T: `mlflow.search_runs` gives a DataFrame (columns `run_id`, `metrics.x`, `params.x`); `MlflowClient().search_runs` gives Run objects (`run.info`, `run.data`).

@ DBX-MLA D1 T1.11 applied troubleshooting
S: A data scientist runs `mlflow.search_runs(["1234"], filter_string="rmse < 1.0 AND team = 'fraud'")`. The call fails with a parse error although runs with `rmse` metrics and a `team` tag exist. What is the fix?
A: Add a leading `WHERE` keyword, because the filter string is parsed as the condition of a SQL query
B: Pass the conditions as a dictionary such as `{"rmse": "<1.0", "team": "fraud"}` instead of a string
C: Move the `rmse` condition into `order_by`, because metrics cannot appear in a filter string
D: Prefix each key by its kind: `metrics.rmse < 1.0 AND tags.team = 'fraud'`
K: D
G: ## Run search syntax
`filter_string` uses a small SQL-like grammar over the data stored in a run. Because metrics, parameters, tags and run attributes live in different namespaces, each key must say which one it comes from.
- `metrics.rmse < 1.0` compares a logged metric with a number.
- `tags.team = 'fraud'` compares a tag with a string (string values are quoted).
- `attributes.status = 'FINISHED'` or the short form `attribute.status` filters on run attributes.
- Conditions are joined with `AND`; there is no `WHERE` keyword and no dictionary form.
The same expressions work in the search field of the experiment page in the Databricks UI, for example `metrics.r2 > 0.3`.
W: A bare name such as `rmse` is not a valid identifier in the grammar. With the `metrics.` and `tags.` prefixes the expression parses and filters correctly.
X: A=`WHERE` keyword: the filter string is only the condition, so adding `WHERE` itself causes another parse error.
B=Dictionary filter: `filter_string` is a string. There is no dictionary form for the comparison operators.
C=Using `order_by`: `order_by` only sorts. Metrics can be filtered, so moving the condition would also drop the `team` condition and the threshold would no longer apply.
T: In run searches name the namespace: `metrics.`, `params.`, `tags.`; combine with `AND`; no `WHERE`.

@ DBX-MLA D1 T1.11 applied definition
S: A deep learning run logged `val_loss` once per epoch for 50 epochs. The engineer wants the epoch at which `val_loss` was lowest, to pick the best checkpoint. Which Client API call provides the data needed?
A: `client.get_metric_history(run_id, "val_loss")`, which returns every logged value of the metric with its step
B: `client.get_run(run_id).data.metrics["val_loss"]`, which returns every epoch value as a list
C: `client.get_run(run_id).data.params["val_loss"]`, because per-epoch values are stored as parameters
D: `client.list_artifacts(run_id)`, because epoch values are stored as files under the run's artifact root
K: A
G: ## Metrics are time series, parameters are not
`mlflow.log_metric("val_loss", value, step=epoch)` can be called many times with the same key. MLflow stores every value with its step and timestamp, so a metric is a series.
- `client.get_metric_history(run_id, key)` returns that whole series (a list of `Metric` objects with `value`, `step`, `timestamp`).
- `run.data.metrics` is a dictionary with one number per key: the latest value that was logged for the key, not the history.
- Parameters are logged once per run and are fixed after that; they hold configuration such as `max_depth`, not training curves.
In the Databricks UI the run page draws the same series as a chart per metric.
W: `get_metric_history` returns each step and value of `val_loss`, so taking the entry with the smallest value gives the best epoch.
X: B=`data.metrics`: the dictionary holds only one value per key, the last logged one, so it loses the other 49 epochs.
C=`data.params`: parameters are single, immutable configuration values. A metric name is not stored there.
D=Artifacts: artifacts are files such as plots or models that you log explicitly. Metric values are kept in the tracking store, not as files.
T: One value per metric key in `run.data.metrics`; the full per-step series comes from `get_metric_history`.

@ DBX-MLA D1 T1.12 applied use-case
S: A team uses `mlflow.sklearn.autolog()` for scikit-learn training. Autologging records parameters, training metrics and the model, but the team also needs a confusion matrix plot and a business metric `expected_revenue_lift` in each run. What should they do?
A: Disable autologging and recreate everything by hand, because autologging blocks custom logging calls inside the same run
B: Keep autologging and add `mlflow.log_metric("expected_revenue_lift", v)` plus `mlflow.log_figure(fig, "cm.png")` in the run
C: Wrap the extra values in model hyperparameters, because autologging accepts custom values only through estimator parameters of the model
D: Write the plot and the value to a Delta table instead, because runs accept only values produced by the library itself
K: B
G: ## Autolog and manual logging together
Autologging patches supported libraries (scikit-learn, Spark ML, XGBoost, TensorFlow and others) so that `fit` records parameters, metrics and the model with no extra code. It is the quickest way to start tracking.
Manual logging gives control over what is recorded. The calls work on the active run and can be mixed with autologging:
- `mlflow.log_param` / `mlflow.log_params` for configuration values
- `mlflow.log_metric` / `mlflow.log_metrics` for numbers, optionally with `step`
- `mlflow.log_artifact`, `mlflow.log_figure`, `mlflow.log_dict`, `mlflow.log_text` for files and plots
- `mlflow.set_tag` for searchable labels
A common pattern is autolog for the standard training information plus a few manual calls for domain metrics and custom plots.
W: Manual calls attach to the run that autologging opened (or to one you start with `mlflow.start_run()`), so the plot and the custom metric appear next to the automatically logged values.
X: A=Disabling autologging: nothing in MLflow makes the two approaches exclusive. Dropping autologging would only add work.
C=Hyperparameters trick: only estimator parameters are logged as parameters, and a metric belongs in the metric store where it can be sorted and charted. A plot cannot be stored as a parameter at all.
D=Delta table: you can store results in a table, but then they are not attached to the run. MLflow accepts arbitrary metrics and artifacts through its logging API.
T: Autolog for the defaults, manual `log_metric` / `log_figure` / `log_artifact` calls for anything else, in the same run.

@ DBX-MLA D1 T1.12 applied definition
S: A training loop logs `mlflow.log_param("learning_rate", 0.1)` once and `mlflow.log_metric("loss", loss, step=epoch)` after each of 20 epochs inside one run. Which TWO statements describe how MLflow stores these values? (Select TWO)
A: Each of the 20 loss values is kept together with its step, so the run can show a loss curve
B: Calling `log_metric` with an existing key replaces the earlier value, so only the final loss is kept
C: The parameter is stored as a string, and logging the same key again with a different value in that run raises an error
D: The parameter is a numeric time series that MLflow updates automatically whenever the optimizer changes the learning rate
E: Metric values must be strings so that MLflow can compare them across runs with `filter_string`
K: A,C
G: ## Parameters versus metrics
MLflow separates two kinds of key-value data on a run.
- **Parameters** describe the configuration of the run: hyperparameters, dataset version, feature list. They are written once, stored as strings and cannot be overwritten with a different value in the same run. They are used to filter and group runs.
- **Metrics** describe results: loss, accuracy, RMSE. They are numeric and can be logged many times with the same key. Each call adds a point with a `step` (and timestamp), so the run keeps a history that the UI plots as a chart.
Because the optimizer's changing learning rate is not reported to MLflow unless you log it, a value that changes over time belongs in a metric, with a step, rather than a parameter.
W: A=Metric history: repeated `log_metric` calls with `step` append points, so all 20 loss values remain available for charts and `get_metric_history`.
C=Immutable string parameter: a parameter is saved as text, and MLflow rejects a second `log_param` with a different value for the same key in the same run.
X: B=Overwrite behavior: metrics append rather than replace. The run page and the history API show every logged step, while `run.data.metrics` shows only the latest one.
D=Automatic update: MLflow records only what you log; it does not observe the optimizer, and parameters are not time series.
E=String metrics: metrics are numbers. That is what lets the search compare them with `<`, `>` and sort by them.
T: Parameters are write-once strings for configuration; metrics are numeric and can be logged repeatedly with a step to form a history.

@ DBX-MLA D1 T1.12 applied comparison
S: A training script finishes with `mlflow.log_artifact("model.pkl")` for a pickled scikit-learn estimator. A colleague asks why the team should use `mlflow.sklearn.log_model(model, name="model", input_example=X.head(5))` instead. Which is the best reason?
A: `log_artifact` cannot store files bigger than a few megabytes, while `log_model` has no such restriction
B: `log_model` stores the model only inside the Databricks control plane, while `log_artifact` copies the file into the customer's cloud storage account
C: `log_model` saves the MLflow Model format with flavors, dependency files and a signature, so it can be loaded, registered and served
D: `log_artifact` stores the file in Unity Catalog automatically, while `log_model` leaves the file unversioned in the run
K: C
G: ## A file versus an MLflow Model
`mlflow.log_artifact` copies any local file into the run's artifact location. MLflow treats it as an opaque file: it does not know what is inside.
`mlflow.<flavor>.log_model` writes a directory in the MLflow Model format:
- an `MLmodel` file that lists the flavors (for example `sklearn` and the generic `python_function`) and the model signature
- the serialized model
- `requirements.txt` and `conda.yaml` so the environment can be rebuilt
- an input example when you pass one
With this structure, `mlflow.pyfunc.load_model`, batch inference with a Spark UDF, registration with `mlflow.register_model` and Model Serving all work without custom code. A bare pickle supports none of them.
In MLflow 3 the call uses `name=` for the logged model (MLflow 2 called this argument `artifact_path`).
W: Logging the model with its flavor, signature and dependency files is what makes it loadable with one call, registrable in Unity Catalog and deployable on Model Serving.
X: A=Size limit: there is no small size cap on `log_artifact` that `log_model` avoids; both write to the same artifact storage for the run.
B=Storage location: both use the experiment's artifact location (MLflow-managed storage by default, or a Unity Catalog volume you choose). Neither writes to a different place by default.
D=Automatic Unity Catalog storage: `log_artifact` does not register anything in Unity Catalog. Registration requires `register_model` or `registered_model_name` for a logged model.
T: Use `log_model` (flavor, signature, requirements) for models; use `log_artifact` for plain files such as reports and CSVs.

@ DBX-MLA D1 T1.12 applied comparison
S: A notebook defines `params = {"max_depth": 8, "n_estimators": 200, "min_samples_leaf": 5}` and `scores = {"rmse": 0.41, "r2": 0.88}`. Which pair of calls records each dictionary in the active run as parameters and metrics, in one call each?
A: `mlflow.log_params(params)` and `mlflow.log_metrics(scores)`
B: `mlflow.log_dict(params, "p.json")` and `mlflow.log_dict(scores, "s.json")`
C: `mlflow.set_tags(params)` and `mlflow.set_tags(scores)`
D: `mlflow.log_artifacts(params)` and `mlflow.log_artifacts(scores)`
K: A
G: ## Same data, four different places
A run holds several kinds of information, and each logging call writes to one of them.
- Parameters go to the parameter table (`log_param`, `log_params` for a dict).
- Metrics go to the metric table (`log_metric`, `log_metrics` for a dict of numbers).
- Tags are free labels (`set_tag`, `set_tags`), meant for metadata such as owner or data source.
- Artifacts are files (`log_artifact`, `log_artifacts` for a local directory, `log_dict` for a JSON/YAML file generated from a dict).
Only parameters and metrics can be compared across runs in the experiment table, sorted, and used in `metrics.rmse < 0.5` style filters. If the values land in an artifact or a tag, those features do not see them as metrics.
W: `log_params` writes a dictionary of hyperparameters in one call and `log_metrics` does the same for numeric results, so both land in the tables the experiment page compares and filters on.
X: B=`log_dict`: it stores each dictionary as a JSON file in the artifacts. The values are not parameters or metrics, so they do not appear as columns in the runs table.
C=`set_tags`: tags are metadata labels stored as strings. Numeric results saved as tags cannot be charted or ordered as metrics.
D=`log_artifacts`: it expects a path to a local directory, not a dictionary, and it would copy files rather than record values.
T: Dict of hyperparameters -> `log_params`; dict of numbers -> `log_metrics`; `log_dict` and `log_artifacts` store files.

@ DBX-MLA D1 T1.12 applied troubleshooting
S: A hyperparameter search wraps each trial as `with mlflow.start_run():` inside a function that is itself called inside another `with mlflow.start_run():` block. The first trial raises "Run with UUID ... is already active". The team wants each trial to appear as its own run grouped under the outer run. What is the correct change?
A: Call `mlflow.end_run()` after the outer `start_run`, so that trials never have an active parent
B: Pass `mlflow.start_run(run_name=...)` with a unique name for each trial, which lets MLflow open several active runs

The fluent API keeps one active run at a time. Calling `mlflow.start_run()` while a run is active raises an exception, because MLflow cannot tell which run later `log_metric` calls belong to.

X: A=Ending the outer run: this closes the parent so nothing groups the trials, and any later parent-level logging would silently create yet another run. The goal was a parent-child structure.
B=Run names: a name is just a label. It does not lift the one-active-run rule, so the error remains.
C=Changing the experiment: the active run is still open and `start_run` still raises. Moving trials to other experiments would also scatter them instead of grouping.
T: Need runs inside an active run (tuning trials) -> `mlflow.start_run(nested=True)`.

@ DBX-MLA D1 T1.13 applied use-case
S: Three data scientists each train in their own notebook and call `mlflow.start_run()` without setting an experiment. The team lead wants all their runs to land in one experiment so the runs can be compared side by side. What is the best approach?
A: Have each notebook call `mlflow.set_experiment("/Shared/churn-model")` first, so every run goes to one shared workspace experiment
B: Merge the three notebooks into one notebook, because only runs started in the same notebook can be compared
C: Rely on the defaults, because Databricks groups the runs of notebooks in the same folder into one experiment
D: Copy the runs between the notebook experiments by exporting CSV files and re-importing them as new runs
K: A
G: ## Notebook and workspace experiments
An experiment is the collection of runs that you compare. Databricks has two kinds.
- A **notebook experiment** exists for one notebook. If no experiment is active when `mlflow.start_run()` is called in a notebook, Databricks creates it automatically (it shares the notebook's name and ID), and runs from that notebook go there.
- A **workspace experiment** is not tied to a notebook. Any notebook, job or API call can log to it by name or ID, for example with `mlflow.set_experiment("/Shared/name_of_experiment")`.
So, to share one experiment between several authors, use a workspace experiment in a shared location and set it explicitly. The permissions on the experiment decide who can see and edit runs.
W: A shared workspace experiment is the supported way to collect runs from several notebooks; each notebook only needs `set_experiment` with the same path.
X: B=Merging notebooks: any notebook can log to a workspace experiment, so merging only removes the independence of the three scientists.
C=Default grouping: each notebook's default is its own notebook experiment. Databricks does not merge notebooks by folder.
D=Exporting and re-importing: this is manual, creates duplicate runs without the original lineage and is unnecessary because runs can be logged to the shared experiment directly.
