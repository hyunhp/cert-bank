@ DBX-MLA D1 T1.1 advanced use-case
S: A bank sets up MLOps on Databricks with Unity Catalog and separate dev, staging and prod catalogs. Security forbids data scientists from writing anything to the prod catalog, yet product owners want them to study how the live model behaves. Auditors require the production model to come from reviewed code trained on production data, and the platform team wants no extra copy of production data unless read access cannot be granted. Which TWO practices follow Databricks recommendations? (Select TWO)
A: Grant data scientists read-only access to the prod catalog, including inference and metric tables, to analyze live predictions from dev
B: Promote the training code through dev, staging and release branches, and let the production job retrain the model on production data in production
C: Copy a nightly snapshot of all production tables into the dev catalog, so data scientists can study live behavior without any grant on the prod catalog
D: Train the final model in the development workspace on production data, then copy that model version into the prod catalog with copy_model_version
E: Give data scientists write access to one schema inside the prod catalog, so their experiment models are registered next to the production model
K: A,B
G: ## The recommended Databricks MLOps workflow
Databricks maps each stage (development, staging, production) to its own execution environment and, in Unity Catalog, usually to its own catalog (`dev`, `staging`, `prod`).
- **Data access**: data scientists have read-write access to the dev catalog. Ideally they also get **read-only** access to the prod catalog (production data, inference tables, metric tables) so they can analyze current production predictions and load production models for comparison. Only when read-only access is impossible should a snapshot of production data be written to the dev catalog.
- **Deploy code, not models**: in most situations the training code, not the model artifact, moves from dev to staging to production through Git branches. The production job then trains the model on production data with reviewed, tested code.
## Example
A pull request to `main` runs unit tests; a release branch triggers the production job, which trains on `prod` tables and registers the version in `prod.ml_team.<model>`.
W: A=Read-only prod access: it gives data scientists the production view the product owners want, without any write path into the prod catalog.
B=Deploy code: reviewed training code runs in production on production data, which is exactly what the auditors ask for.
X: C=Nightly snapshot: the docs keep the snapshot as the fallback when read-only access is not possible; here access can be granted, and the platform team wants no extra copy.
D=Train in development: this is the deploy models pattern; the production model would be produced in development, not by the reviewed production job, and dev would need production data.
E=Write schema in prod: security forbids any writes to the prod catalog; development models belong in the dev catalog.
T: Read-only prod access for data scientists + deploy code so production trains on production data.

Creating one compute resource per person is rejected for cost reasons. Which compute configuration fits all of these constraints?

To read Unity Catalog data on compute that runs Databricks Runtime ML, the access mode must be **Dedicated** (formerly single user). Selecting the *Machine learning* checkbox sets Dedicated automatically, assigned to your own account.
- A Dedicated resource can be assigned to **one user or one group**.
- When it is assigned to a group, each user's permissions are automatically **down-scoped to the group's permissions**, so members can share the resource safely.

@ DBX-MLA D1 T1.5 advanced use-case
S: A retailer keeps customer features in `ml.features.customer_activity`, a feature table in Unity Catalog. A subsidiary's data science team works in a workspace attached to a different Unity Catalog metastore in another cloud region and must train models on these features. The platform team refuses to build a copy pipeline, and the owning team must keep governing the table. What should the owning team do to give the subsidiary access?
A: Share the feature table through OpenSharing in the Databricks-to-Databricks flow, so the subsidiary reads it from a catalog created from the share
B: Attach the subsidiary's workspace to the retailer's metastore as a second metastore, so the feature table becomes readable there without other changes
C: Grant SELECT on the feature table to the subsidiary's group, because Unity Catalog grants apply in every workspace of the whole Databricks account
D: Re-create the features in the legacy Workspace Feature Store of the subsidiary's workspace and schedule a job that keeps writing the same values
K: A
G: ## Where a Unity Catalog feature table is visible
A feature table in Unity Catalog is a Delta table with a primary key. Like any Unity Catalog table it is accessible from **every workspace assigned to the same metastore**, subject to grants. A workspace is attached to one metastore, and metastores are regional.
## Crossing metastores
To reach workspaces that are **not** on the same metastore (another region or another account), Databricks documents **OpenSharing** (formerly Delta Sharing): the provider adds the table to a share, and the recipient creates a catalog from the share and reads the table in place. The provider keeps ownership and can revoke access.
## Example
Provider: share `features_share` contains `ml.features.customer_activity`. Recipient: `CREATE CATALOG retail_features USING SHARE ...`, then `FeatureLookup`s or reads point at `retail_features...`.
W: OpenSharing: it is the documented path for feature tables across metastores, reads the data in place without a copy pipeline, and leaves governance with the provider.
X: B=Second metastore: a workspace can be attached to only one metastore, and metastores are regional, so this is not possible.
C=Account-wide grant: grants are scoped to a metastore; the subsidiary's workspace does not see objects from another metastore at all.
D=Legacy Workspace Feature Store copy: this is the copy pipeline the platform team refused, and it moves the data into a legacy, workspace-scoped store outside the owner's governance.
T: Same metastore = direct access with grants; different metastore = OpenSharing.

Which approach meets both needs?

A **simple SELECT view** over a single Unity Catalog Delta table (only SELECT, FROM, WHERE, ORDER BY, LIMIT, OFFSET, with the primary keys selected) can act as a feature table. It is handy for offline subsets because nothing is copied.

@ DBX-MLA D1 T1.8 advanced troubleshooting
S: A churn model is trained with `fe.create_training_set(df=labels_df, feature_lookups=lookups, label="churned")`, where `labels_df` holds the integer key `customer_id` and the label `churned`. The data scientist converts `training_set.load_df()` to pandas, drops only the label column and fits a gradient-boosting model. Feature importance ranks `customer_id` near the top, and accuracy on newer customers is poor. Which change fixes training while keeping automatic feature lookup at scoring?
A: Pass exclude_columns=["customer_id"] to create_training_set, so the key still drives the lookup but is not returned as a model input
B: Drop customer_id from labels_df before calling create_training_set, so the DataFrame holds only the label and the looked-up feature columns
C: Rename customer_id in labels_df to cust_key and pass it as lookup_key, so the model treats it as a categorical identifier instead of a number
D: Keep customer_id in the training data but cast it to a string first, so the model can no longer rank customers by the numeric key value
K: A
G: ## What load_df returns
`TrainingSet.load_df()` returns every column of the DataFrame passed to `create_training_set` **plus** the looked-up features, except the columns named in `exclude_columns`. Lookup keys are needed for the join, but if they stay in the output, a model trained on that DataFrame uses them as inputs.
## Why an ID is a bad feature
A sequential customer ID mostly encodes when the customer signed up. The model can learn patterns tied to old IDs that do not hold for new customers, which looks fine on a random split and fails on newer customers.
## The documented pattern
```
fe.create_training_set(df=labels_df, feature_lookups=lookups,
    label="churned", exclude_columns=["customer_id"])
```
At scoring, `fe.score_batch` still needs `customer_id` in the batch DataFrame to look the features up.
W: exclude_columns: the key is used for the join but removed from the training columns, so the model learns only real features and lookup at scoring is unchanged.
X: B=Drop the key first: `create_training_set` needs every lookup key in the DataFrame; without `customer_id` the lookup fails.
C=Rename the key: the column is still returned by `load_df` and still used as an input, whatever its name.
D=Cast to string: the ID remains in the training data, and a tree model can still memorize its values; the leakage stays.
T: Lookup keys go in the DataFrame for the join and in exclude_columns so they are not model inputs.

@ DBX-MLA D1 T1.8 advanced troubleshooting
S: A feature lookup renames a column and should give new customers, who have no feature row yet, a default tier. The team forbids writing placeholder rows into the shared table, and batch scoring must apply the same default:
```
FeatureLookup(table_name="ml.crm.cust", feature_names=["tier"],
  lookup_key="customer_id", rename_outputs={"tier": "cust_tier"},
  default_values={"tier": "bronze"})
```
New customers still get null `cust_tier` in the training set. What should change?
A: Key the defaults by the renamed output, as default_values={"cust_tier": "bronze"}, because defaults must use the renamed feature names
B: Remove rename_outputs and rename the column after load_df, so that default_values can keep the original feature name tier as its key
C: Call fillna("bronze") on the DataFrame returned by load_df, so that training and later batch scoring both see bronze for new customers
D: Set default_values={"tier": "bronze"} on a second FeatureLookup without rename_outputs, and drop its duplicate tier column after load_df
K: A
G: ## Default values in a FeatureLookup
`FeatureLookup(default_values={...})` fills a feature when the feature table has no value for a key, for example a brand-new customer. Because the defaults are part of the lookup definition, they are packaged with the model by `fe.log_model` and applied again in `score_batch`.
## Interaction with renaming
When `rename_outputs` renames a feature, **`default_values` must use the renamed names**. A default keyed by the original name does not match the output column, so nothing is filled.
## Why not fix it afterwards
Changes made to the `load_df()` DataFrame before training are **not** applied at inference: the model only knows its lookups. A fill or rename done on the DataFrame works in training and silently disappears in batch scoring.
W: Renamed key: `default_values={"cust_tier": "bronze"}` matches the output column, and the default travels with the model into batch scoring.
X: B=Rename after load_df: a rename on the DataFrame is not part of the packaged lookup, so scoring would produce a column the model does not expect.
C=fillna after load_df: training sees bronze, but `score_batch` does not repeat DataFrame edits, so new customers would be scored with nulls.
D=Second lookup: the same feature is looked up twice to work around the naming rule, and dropping a column after `load_df` is again an edit that scoring does not repeat.
T: With rename_outputs, default_values use the new names; never patch the load_df output.

@ DBX-MLA D1 T1.9 advanced use-case
S: A demand model was trained with a point-in-time lookup (`timestamp_lookup_key="order_ts"`) on the time series feature table `ml.ops.store_daily` and logged with `fe.log_model`. To reuse a generic scoring job, an engineer plans to load it with `mlflow.pyfunc.spark_udf` and pass `store_id` and `order_ts`. The nightly job must keep automatic, point-in-time-correct feature lookup, and the team prefers a documented scoring path over custom joins. Which approach produces correct batch predictions?
A: Call fe.score_batch with a DataFrame holding store_id and an order_ts column with the same name and data type as in training
B: Keep the generic MLflow pyfunc scoring job, because models logged with fe.log_model look up time series features through pyfunc too
C: Call fe.score_batch with a DataFrame holding only store_id, because the packaged model looks up the latest feature value for each key
D: Join ml.ops.store_daily to the batch on store_id yourself and pass every feature column to the pyfunc model, so that lookups are skipped
K: A
G: ## Two ways to batch score a feature-aware model
A model logged with `fe.log_model(..., training_set=...)` carries its feature lookups.
- `fe.score_batch(model_uri, df)` looks the features up and returns `df` plus the features and a `prediction` column.
- MLflow pyfunc batch inference can also look features up, but the docs state that **models that use time series feature tables are not supported** there; use `score_batch` for them.
## Point-in-time scoring
For a time series lookup, the scoring DataFrame must contain a timestamp column with the **same name and DataType** as the `timestamp_lookup_key` used in training. Feature Store then takes the latest feature value at or before each row's timestamp.
W: score_batch with order_ts: it is the documented path for time series lookups and repeats the point-in-time join with the timestamp column the model expects.
X: B=pyfunc scoring: MLflow pyfunc batch inference with feature lookup does not support models that use time series feature tables.
C=Keys only: a time series lookup needs the timestamp lookup column; without it the point-in-time join cannot run.
D=Manual join on store_id: the table holds one row per store and day, so a key-only join duplicates rows and ignores point-in-time correctness.
T: Time series feature tables = fe.score_batch with the same timestamp lookup column, not pyfunc lookup.

@ DBX-MLA D1 T1.10 advanced use-case
S: Ten data scientists each created their own Databricks Online Feature Store with `fe.create_online_store` to test real-time feature serving, and these stores sit idle on nights and weekends. Finance asks the team to cut the cost of this development work. The single production online store, read by a Model Serving endpoint with automatic feature lookup, must not change. Which TWO actions follow Databricks guidance? (Select TWO)
A: Publish the development feature tables of all ten users into one shared development online store instead of keeping one store per person
B: Delete the development online stores that are no longer needed, because an online store keeps incurring cost for as long as it exists
C: Enable Lakebase scale-to-zero on each development online store, so that compute stops automatically during idle nights and weekends
D: Lower the production online store to the smallest capacity each night, and raise it again every morning before business hours start
E: Replace the development online stores with offline feature tables, and let test endpoints look up features directly from the Delta tables
K: A,B
G: ## What an online store is
A Databricks Online Feature Store is a managed, highly available **Lakebase** instance created with `fe.create_online_store(name=..., capacity=...)`. Feature tables are synced into it with `publish_table`, and Feature Serving or Model Serving endpoints read it for low-latency lookups.
## Cost guidance from the docs
- **Reuse online stores**: many feature tables can be published to one store; for development, testing and training, share one store across projects or users.
- **Right-size capacity**: start small for testing and scale only on evidence.
- **Delete stores that are not in use**: online stores incur cost continuously.
## Limitation to remember
Lakebase **scale-to-zero is not supported** for online feature stores.
W: A=One shared development store: the docs recommend sharing a store across users and projects for development and testing.
B=Delete unused stores: an online store costs money continuously, so stores nobody uses should be removed.
X: C=Scale-to-zero: the online feature store limitations list Lakebase scale-to-zero as not supported.
D=Resize production nightly: the production store must not change, and capacity flips add risk to the live endpoint.
E=Offline tables for endpoints: real-time endpoints look features up from online stores; offline Delta tables are for training and batch scoring.
T: Cut online store cost by sharing one development store and deleting idle ones; scale-to-zero is not available.

@ DBX-MLA D1 T1.11 advanced use-case
S: Sixty runs in experiment `4471` compare XGBoost and random forest models. Each run logs the parameter `model_type` and the metric `val_auc`, but some runs crashed after logging a partial `val_auc`. A job must return the best finished XGBoost run in one `mlflow.search_runs` call, with no extra filtering in pandas afterwards, because the run ID feeds a registration step. Which arguments should the call use?
A: Filter "params.model_type = 'xgboost' and attributes.status = 'FINISHED'", order by "metrics.val_auc DESC", and set max_results to 1

C: Filter "params.model_type = 'xgboost' and attributes.status = 'FINISHED'", order by "metrics.val_auc", and set max_results to 1

G: ## Anatomy of a search
`mlflow.search_runs(experiment_ids=["4471"], filter_string=..., order_by=[...], max_results=...)` returns a pandas DataFrame by default, one row per run.
- **Filter prefixes**: `params.<name>` for parameters (string values in quotes), `metrics.<name>` for metrics (numbers), `tags.<name>` for tags, and `attributes.<name>` for run attributes such as `status`.

X: B=No status filter: a crashed run with a high partial `val_auc` could be returned as the best run.
C=Default order: ascending order returns the finished XGBoost run with the lowest AUC, the worst one.
D=metrics prefix for a parameter: `model_type` was logged as a parameter, so it must be filtered with `params.`, not `metrics.`.
T: Best run = right prefixes (params./metrics./attributes.) + DESC for higher-is-better + max_results=1.

@ DBX-MLA D1 T1.12 advanced use-case
S: A credit team trains a scikit-learn model on the Unity Catalog table `prod.risk.applications`, reading it with `spark.table(...).toPandas()`, then logs and registers the model in Unity Catalog. Auditors open the model version in Catalog Explorer and find no upstream table on the Lineage tab. The team does not use feature tables and wants the next registered version to show its training table. What should the training code add?
A: Load the table with mlflow.data.load_delta and call mlflow.log_input with that dataset inside the run that logs and registers the model
B: Log the table name as a run parameter with mlflow.log_param("training_table", ...) so that the registered version links back to the table
C: Save a CSV extract of the table as a run artifact with mlflow.log_artifact, so that the lineage graph records the extract as its input
D: Add the model version tag source_table = prod.risk.applications, which Catalog Explorer reads to draw the upstream table on the Lineage tab
K: A
G: ## Table-to-model lineage in Unity Catalog
When a model trains on a Unity Catalog table, Databricks can record the link from the table to the model version. The docs give two ways:
- Models logged with **feature store APIs** capture lineage automatically.
- Otherwise, record the dataset with **`mlflow.log_input`**: load the table as an MLflow dataset (`mlflow.data.load_delta(table_name=..., version=...)`) and log it in the run. When the model is registered to Unity Catalog, lineage is saved and shown on the Lineage tab of the model version.
## Example
```
dataset = mlflow.data.load_delta(table_name="prod.risk.applications")
with mlflow.start_run():
    mlflow.log_input(dataset, "training")
    mlflow.sklearn.log_model(clf, name="model", input_example=X.iloc[[0]],
        registered_model_name="prod.ml.credit_risk")
```
W: log_input with load_delta: it records the Unity Catalog table as the run's training dataset, and registration turns that into table-to-model lineage.
X: B=Parameter: a parameter is just a string in the run; Unity Catalog does not build lineage from it.
C=CSV artifact: an artifact file is not a Unity Catalog table input, so no table lineage is recorded, and it duplicates sensitive data.
D=Version tag: tags are labels for search and status; Catalog Explorer does not draw lineage from tag values.
T: Table-to-model lineage without feature tables = mlflow.data.load_delta + mlflow.log_input in the training run.

@ DBX-MLA D1 T1.13 advanced use-case
S: Forty runs each log `val_loss` once per epoch for 30 epochs, and several runs overfit so that `val_loss` rises again late. On the experiment page, a reviewer searches `metrics.val_loss < 0.25` and gets only runs whose last epoch is below 0.25, missing runs that reached 0.21 earlier. The reviewer must find runs by their best epoch, without changing training code and with the least manual work. What should the reviewer do?
A: Search on the minimum value of the metric instead, because by default the run search filters each metric on its last logged value
B: Sort the runs table by val_loss ascending, because the sort uses the lowest value that each run logged instead of its final value
C: Filter on the validation dataset in the Datasets drop-down, so that the search compares the value of every epoch instead of the last one
D: Add a best_val_loss tag to every run by hand in the run page, and then search the experiment for runs whose tag is lower than 0.25
K: A
G: ## How the run search reads metrics
A metric logged with steps has many values per run. On the experiment page, **metric filters use the last logged value by default**. The search also supports **MIN** and **MAX** forms of a metric, which filter on the lowest or highest value each run logged (available for runs logged after August 2024).
## Other filters on the page
Besides metric and parameter filters, the page filters runs by state (Active or Deleted), creation time and the datasets used. None of these change how a metric is compared.
## Example
A run with `val_loss` 0.21 at epoch 12 and 0.31 at epoch 30 fails `val_loss < 0.25` (last value) but passes the MIN form of the same filter.
W: MIN of the metric: it compares each run's lowest logged `val_loss`, so overfitting runs that reached 0.21 earlier are found without code changes.
X: B=Sort ascending: the runs table shows and sorts the last logged value, so the late, higher values decide the order.
C=Datasets drop-down: it selects runs by the datasets they used; it does not make the search look at earlier epochs.
D=Manual tags: forty runs edited by hand is the most manual option, and tag values are strings, which makes numeric comparison unreliable.
T: Run search uses the last metric value by default; use MIN/MAX to search on the best value.

@ DBX-MLA D1 T1.14 advanced use-case
S: A CI service principal must register a new version of the existing model `prod.ml_team.fraud`, owned by the `ml-admins` group, after each training run. Policy says the principal must not be able to delete the model or move its aliases, so it cannot become the owner. Its first attempt failed during registration in a workspace whose default catalog is in Unity Catalog. Which THREE items does it need? (Select THREE)

G: ## Privileges for models in Unity Catalog

G: ## How endpoint configuration updates work
Updating a serving endpoint's configuration (served entities, traffic split) starts an update.
- **Until the new configuration is ready, the old configuration keeps serving prediction traffic**, so there is no downtime.
- **While an update is in progress, another update cannot be made** (it can be cancelled from the Serving UI).
## Scripting a staged rollout
Send the 90/10 update, poll the endpoint state until the update has finished, observe metrics, then send the 50/50 update the same way.
