@ DBX-MLA D4 T4.4 advanced troubleshooting
S: A pipeline's streaming table adds a `score` column by applying model version 1 to each new event. The team swaps the query to use version 2 and runs a normal (non-full) update. What does the table contain afterwards?
A: The update fails, since a streaming table's query is locked after its first run
B: Old rows are dropped, and the table holds just the rows that arrive after the change
C: Old rows keep version 1 scores and new rows get version 2 scores, until a full refresh
D: Version 2 scores on old and new rows, since each update re-reads the source with the new query
K: C
G: ## Streaming tables process each row once
In a pipeline, a **streaming table** processes each record exactly once, assuming an append-only source. A row already appended is not re-read on later updates. The Databricks streaming table docs give an example: changing `SELECT LOWER(name)` to `SELECT UPPER(name)` leaves old rows lowercase while new rows are uppercase, and a **full refresh** requeries all earlier data from the source to update every row.
## Consequence for scoring
Applying the same reasoning to a model-scoring column, changing the model changes only rows processed after the change. To make every row use the new model, run a full refresh. Teams must also remember that different query versions have processed different rows.
W: C=Mixed versions until full refresh: a streaming table sees each row once, so earlier rows keep the old logic and a full refresh is what reprocesses them.
X: A=Query locked: the docs say you can change the query without recomputing the entire dataset, so the update runs.
B=Old rows dropped: a changed query does not remove rows already appended; they stay unless a full refresh rebuilds the table.
D=Re-read everything: a normal update does not re-query rows already appended to a streaming table; recomputing results as needed describes a materialized view, and here only a full refresh re-reads the source.
T: Streaming table = each row processed once; changing the logic needs a full refresh to rescore old rows.

@ DBX-MLA D4 T4.1 applied use-case
S: A checkout service must return a fraud score to the payment page while the customer waits, using the values in that single request. Which approach meets the requirement?
A: A nightly batch job that scores the previous day's transactions and writes the results to a Delta table
B: A weekly retraining job that recomputes fraud scores for the known customers before its next scheduled run
C: A triggered pipeline that rescores the transactions table on an hourly schedule and refreshes a materialized view
D: A model serving endpoint that the application calls over REST, returning the prediction in the HTTP response body
K: D
G: ## Per-request predictions need an online endpoint
Real-time inference means a caller sends input and waits for the prediction. On Databricks, Mosaic AI Model Serving exposes a registered model as a REST API. The service is described as highly available and low-latency, with automatic scale-up and scale-down as demand changes, so the application only needs an HTTP client.
## Why stored scores do not work here
A table of precomputed scores can only contain customers and transactions that existed at the last run. A brand-new transaction has no row yet, so the page would have nothing to read. Per-request input that only exists at checkout time forces online scoring.
W: D=Model serving endpoint: it scores the new transaction at the moment it is sent, returns the prediction in the HTTP response, and scales with checkout traffic.
X: A=Nightly batch: the new transaction does not exist when the job runs, so the page would show yesterday's data or nothing, with up to a day of delay.
B=Weekly retraining: retraining changes the model, not when predictions are produced, and weekly recomputation is far too slow for a checkout.
C=Hourly triggered pipeline: triggered mode refreshes the available data and stops, so the score would arrive up to an hour late and never inside the customer's request.
T: When the input exists only at request time and a person waits, use a real-time serving endpoint.

@ DBX-MLA D1 T1.10 applied tradeoff
S: A marketing team scores 40 million customers once every night to produce next-day campaign lists. They ask for an online feature store "to be safe". What is the best recommendation?
A: Create the online store and read the 40 million feature rows through its Postgres interface during each nightly scoring run
B: Skip the online store and run `score_batch` on the offline tables, since an online store adds a billed service with no latency need
C: Export the features to CSV files on cloud storage first, because `score_batch` is meant to read plain files rather than Delta tables
D: Create a large-capacity online store and publish continuously, because online stores serve big nightly scans faster than Delta
K: B
G: ## Choosing offline or online
Choose by the access pattern:
- **Batch** (nightly or hourly, large volumes, no per-request deadline): read the offline Delta tables. `score_batch` joins the features by key and scores in Spark, scaling with the cluster.

C=CSV export: `score_batch` looks up features from the feature tables directly, so converting them to unmanaged files adds a copy with no benefit.
D=Large online store: online stores are built for point reads by key, not large scans, and a larger capacity only raises the running cost.

@ DBX-MLA D1 T1.6 applied use-case
S: A churn team must retrain monthly on what each customer's features looked like on every past day, for audit. The feature job runs daily, and overwriting yesterday's rows with today's values would lose that history. How should the feature table be designed?
A: Keep `customer_id` as the primary key and write each day's DataFrame in append mode so that the daily rows accumulate in the table
B: Use a composite primary key of `date` and `customer_id`, with liquid clustering (or partitioning on `date`) for window reads
C: Keep `customer_id` as the primary key and read older Delta versions with time travel whenever training needs past values
D: Create a new feature table each day with the date in its name, and add a `FeatureLookup` for each daily table
K: B
G: ## Storing past values of daily features
A feature table has one row per primary key value. If the key is only `customer_id`, a daily job that merges new values replaces the old row, and the table shows only the latest state. To keep history, put the date in a **composite primary key**, for example `PRIMARY KEY (date, customer_id)`. Each day then adds one row per customer.
For efficient reads of a window, Databricks recommends liquid clustering on the table; without it, partition by the date column. A training job filters `date` to the period of interest.
If lookups must also return the latest value as of the label time, declare the time column with `TIMESERIES` so `create_training_set` can do a point-in-time join.
W: B=Composite key with the date: one row per customer per day keeps the history, and clustering or partitioning on the date makes window reads cheap.
X: A=Append with a single-column key: a primary key is not enforced as a duplicate check, but lookups require exactly one row per key; duplicate customers make joins ambiguous and break the feature table contract.
C=Time travel: Delta versions are kept only for the retention period and are not addressable by `FeatureLookup`, so they are not a dependable history for audits.
D=A table per day: it explodes the number of tables, and each `FeatureLookup` names one table; a model cannot reference an open-ended, growing list of daily tables.
T: To keep history in a feature table, put the date (or a `TIMESERIES` timestamp) into a composite primary key instead of overwriting rows.

@ DBX-MLA D1 T1.12 applied comparison
S: A training script finishes with `mlflow.log_artifact("model.pkl")` for a pickled scikit-learn estimator. A colleague asks why the team should use `mlflow.sklearn.log_model(model, name="model", input_example=X.head(5))` instead. Which is the best reason?
A: `log_artifact` is limited to small files of a few megabytes, while `log_model` accepts large serialized models of any common size
B: `log_artifact` registers the file in Unity Catalog as a model version, while `log_model` keeps the file unversioned in the run
C: `log_model` saves the MLflow Model format with flavors, dependency files and a signature, so it can be loaded, registered and served
D: `log_model` keeps the model inside the Databricks control plane, while `log_artifact` writes the file to the customer's cloud storage
K: C
G: ## A file versus an MLflow Model
`mlflow.log_artifact` copies any local file into the run's artifact location. MLflow treats it as an opaque file: it does not know what is inside.
`mlflow.<flavor>.log_model` writes a directory in the MLflow Model format:
- an `MLmodel` file that lists the flavors (for example `sklearn` and the generic `python_function`) and the model signature
- the serialized model
- `requirements.txt` and `conda.yaml` so the environment can be rebuilt
- an input example when you pass one

W: C=MLflow Model format: logging the model with its flavor, signature and dependency files is what makes it loadable with one call, registrable in Unity Catalog and deployable on Model Serving.

B=Unity Catalog registration: `log_artifact` does not register anything in Unity Catalog. Registration requires `register_model` or `registered_model_name` for a logged model.
D=Storage location: both use the experiment's artifact location (MLflow-managed storage by default, or a Unity Catalog volume you choose). Neither writes to a different place by default.
T: Use `log_model` (flavor, signature, requirements) for models; use `log_artifact` for plain files such as reports and CSVs.

@ DBX-MLA D3 T3.9 advanced use-case
S: A pipeline chains `StandardScaler` and `LogisticRegression`. A data scientist first fits the scaler on the full training DataFrame, transforms it, then runs `CrossValidator` on the scaled data. Validation scores are slightly optimistic. What is the better design?
A: Fit the scaler on each validation fold, so that the scaling reflects the data being scored in that fold
B: Pass a `Pipeline` of scaler and classifier as the estimator, so the scaler is refit on each fold's training part
C: Fit the scaler on the full dataset including the test set, so the folds share identical scaling statistics
D: Remove the scaler from the pipeline, since logistic regression gives the same model on unscaled features
K: B
G: ## Leakage through preprocessing
If the scaler is fit on all training rows, the mean and standard deviation of each validation fold have influenced the scaling that the model receives. The effect is usually small, but with imputers, target encoders, feature selection or PCA the leak can be large.
## The fix
An `Estimator` handed to `CrossValidator` can be a `Pipeline`. The tuner then fits the whole pipeline on the training folds of each split, so every fitted stage (scaler, imputer, indexer) learns only from training rows and is applied to the held-out fold. The same idea in scikit-learn is passing a `Pipeline` to `GridSearchCV` or `cross_val_score`.
W: B=Pipeline as the estimator: all stages are refit inside each fold using only that fold's training rows, which removes preprocessing leakage and also lets pipeline stage parameters join the grid.
X: A=Fit on validation fold: a transformer must learn only from training data, otherwise the held-out rows influence the transformation they are evaluated with.
C=Fit on everything: including the test set leaks even more information and makes the final estimate unreliable.
D=Drop the scaler: scaling affects how regularized logistic regression penalizes features and speeds up convergence, so the model changes; removing it is not a fix for leakage.
T: Put preprocessing and model in one Pipeline and give it to the CrossValidator so each fold fits its own transformers.
