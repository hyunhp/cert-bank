@ DBX-MLA D2 T2.8 applied use-case
S: A team trains a gradient-boosted tree model in scikit-learn on a table where the feature `merchant_id` has about 60,000 distinct values. A colleague proposes one-hot encoding `merchant_id` before training. Which is the best assessment?
A: It is required, because tree models cannot split on any column that holds integer codes
B: It is a poor fit, since it creates 60,000 sparse columns, and a compact encoding such as frequency or target encoding suits trees better
C: It is ideal, because each new column gives the trees exactly one extra split to test
D: It is harmless, because one-hot encoding always reduces the number of distinct values
K: B
G: ## When one-hot encoding is the wrong tool
One-hot encoding turns a categorical feature with k values into k (or k-1) binary columns. This is a generally accepted feature-engineering technique and works well for low-cardinality nominal features. Its cost grows with the number of distinct values: a feature with 60,000 values becomes 60,000 mostly-zero columns, which increases memory, training time and the risk of overfitting on rare levels.
## Trees and high cardinality
Tree-based models split on one feature at a time and can already use an integer-coded or otherwise compact numeric representation. For very high-cardinality features, practitioners usually prefer frequency encoding, target (mean) encoding computed with care to avoid label leakage, hashing, or grouping rare levels into an "other" bucket.
W: Poor fit with a compact alternative: 60,000 sparse columns are expensive and each rare level gets almost no training signal, so frequency, target or hashed encodings are generally better for trees.
X: A=Required: trees split on numeric thresholds, so an integer code is a usable input; one-hot encoding is not required for tree models.
C=Ideal: extra columns do not give useful splits; each indicator isolates a single merchant, which mostly fits noise for rare merchants.
D=Harmless: one-hot encoding does not reduce distinct values, it spreads each value across its own column and increases the feature count.
T: High-cardinality features make one-hot encoding wide and sparse; trees do better with frequency, target or hashed encodings.

@ DBX-MLA D2 T2.8 applied use-case
S: A dataset has a feature `shirt_size` with the ordered values S, M, L and XL, and a linear regression predicts return rate. Which encoding is most appropriate for `shirt_size`?
A: One-hot encoding, because ordered categories must always be expanded to separate columns
B: A StringIndexer with random ordering, so that no size is favoured over another
C: An ordinal encoding that maps S, M, L, XL to 0, 1, 2, 3 to keep the natural order
D: Dropping the feature, because categorical values cannot be used by linear models
K: C
G: ## Nominal versus ordinal categories
A nominal feature (colour, country) has no order, so assigning it integer codes would invent a false ranking and one-hot encoding is the usual fix. An ordinal feature (shirt size, rating level) has a genuine order, and an integer code that preserves that order carries real information that a linear model can use. These definitions are generally accepted in machine learning.
## Trade-off
One-hot encoding an ordinal feature is not wrong, but it discards the ordering and adds columns. If the steps between levels are roughly even, an ordinal code is compact and keeps the order; if the effect of each step is very different, one-hot encoding lets the model learn a separate weight for each level.
W: Ordinal encoding: S, M, L, XL have a natural order, so 0 to 3 preserves it in a single numeric column that a linear model can use.
X: A=One-hot always: it is not a rule that ordered categories must be expanded; doing so throws away the order and adds three columns.
B=Random-order index: a random mapping invents an arbitrary ranking and hides the real one, which is worse than either alternative.
D=Dropping the feature: linear models work with categorical data once it is encoded as numbers, so the feature does not need to be dropped.
T: Ordered categories can use an order-preserving integer code; unordered ones need one-hot (or another encoding) for linear models.

@ DBX-MLA D2 T2.8 applied use-case
S: A data scientist is deciding where one-hot encoding of the categorical inputs is appropriate. Which TWO situations suit one-hot encoding? (Select TWO)
A: A logistic regression with a `region` feature that has five unordered values
B: A random forest with a `user_id` feature of 8 million distinct values
C: A k-nearest-neighbours model using Euclidean distance with a `colour` feature of four unordered values
D: A model whose categorical feature has already been converted to its numeric target-mean value
E: A linear model where the single categorical feature has 2 million distinct values
K: A,C
G: ## Where one-hot encoding fits
One-hot encoding suits models that treat numeric inputs as magnitudes or distances (linear and logistic regression, neural networks, k-nearest neighbours) when the categorical feature is nominal and has a modest number of values. It avoids inventing an order between categories. This is a generally accepted guideline, not a Databricks-specific rule.
## Where it does not
It is a poor choice when cardinality is very high (identifier-like columns), and unnecessary when the feature is already numeric-encoded.
W: A=Logistic regression with five regions: a nominal feature with few values becomes five clean binary inputs, and the model gets one weight per region without an invented order.
C=k-NN with four colours: distance calculations need numeric inputs, and one-hot columns make every pair of different colours equally far apart instead of implying that some colours are closer.
X: B=Random forest with user_id: 8 million values would create 8 million sparse columns, and an identifier-like column is better dropped or encoded compactly.
D=Target-mean column: the feature is already numeric, so expanding it would add nothing and the numeric column is the intended input.
E=Linear model with 2 million values: the matrix would be extremely wide and sparse, so hashing or target encoding is the better choice.
T: One-hot encoding suits nominal, low-cardinality features in linear or distance-based models; avoid it for identifier-like columns.

The Spark ML guide explains that feature transformers such as `StringIndexer` and `VectorIndexer` index categories and add metadata to the DataFrame, which tree-based algorithms can recognize. @ DBX-MLA D2 T2.8 advanced use-case
S: A logistic regression in Spark ML must use a `zip_code` string column with about 30,000 values. A one-hot vector of that size is too wide for the team's memory budget. Which transformer produces a feature vector of fixed, smaller width from the string column?
A: `FeatureHasher`, which maps the categorical values into a vector of a chosen dimension
B: `Imputer`, which replaces each rare zip code with the most frequent one
C: `VectorAssembler`, which compresses the string column into a single index
D: `StandardScaler`, which shrinks the number of categories to its standard deviation
K: A
G: ## Feature hashing
`FeatureHasher` projects categorical or numeric features into a vector of a specified dimension (typically much smaller than the original feature space) using the hashing trick. For string columns it hashes `column_name=value` to an index and sets an indicator of 1.0, so it behaves like one-hot encoding with a bounded width. Different values can collide into the same index, which is the price for the fixed size. This is described on spark.apache.org.
## Alternatives
Grouping rare zip codes into an "other" level or using aggregate features such as region are generally accepted ways to cut cardinality before encoding.
W: FeatureHasher: it maps categorical strings into a vector of a chosen dimension, so the width is fixed whatever the number of zip codes, at the cost of occasional collisions.
X: B=Imputer: it fills missing numeric values with mean, median or mode; it does not shrink cardinality.
C=VectorAssembler: it concatenates columns into one vector and does not encode strings; it accepts numeric, boolean and vector columns.
D=StandardScaler: it rescales numeric vector features to unit variance or zero mean and has nothing to do with categories.
T: To bound the width of a high-cardinality categorical feature in Spark ML, use FeatureHasher (accepting some collisions).

@ DBX-MLA D2 T2.9 applied use-case
S: A regression model predicts `house_price` from `lot_area`. `lot_area` is strictly positive, has a long right tail with a few very large lots, and the relationship with price is roughly multiplicative. The model is a linear regression. Which preprocessing step is most appropriate?
A: Standardise `lot_area` to zero mean and unit variance and keep the skew
B: One-hot encode `lot_area` into ten equal buckets of rows
C: Apply a log transform to `lot_area`, which compresses the tail and makes the relationship closer to linear
D: Replace `lot_area` with its minimum value for every row
K: C
G: ## What a log transform does
Taking the logarithm compresses large values much more than small ones. For a positive, right-skewed feature (area, income, counts of events), the result is closer to symmetric, and a multiplicative relationship (a percent change in the input gives a percent change in the output) becomes additive and therefore a better match for linear models. These are generally accepted statistical definitions.
## What it does not do
Standardising changes the scale and the centre but not the shape, so a skewed feature stays skewed. Log transforms need positive inputs; when zeros occur, `log1p(x)` is the usual variant.
W: Log transform: it pulls in the long right tail and linearises the multiplicative relationship, which helps a linear regression fit.
X: A=Standardise only: scaling keeps the same skew and the same extreme values relative to the others, so the problem for a linear fit remains.
B=Ten equal buckets: this is a binning choice, and one-hot encoding the buckets would discard the numeric information; it does not address the tail.
D=Minimum value: a constant column carries no information, so the feature would be useless.
T: Right-skewed positive features with multiplicative effects are good candidates for a log transform before a linear model.

@ DBX-MLA D2 T2.9 applied use-case
S: Which TWO scenarios call for a log transform of a numeric column? (Select TWO)
A: A bounded `completion_rate` that is evenly spread between 0 and 1
B: Daily `transaction_amount` values that span from 1 to 10,000,000 and are strongly right-skewed
C: A binary `is_active` flag with values 0 and 1
D: A strictly positive `response_time_ms` column in which a few outliers are 1,000 times the median
E: A `temperature_change` column with many negative values and a symmetric spread
K: B,D
G: ## Recognising candidates
A log transform helps with strictly positive data that spans several orders of magnitude or has a long right tail. After the transform the distribution is closer to symmetric, extreme values lose leverage, and ratios become differences. A histogram or a skewness statistic is the usual check. This is a generally accepted exploratory-analysis practice.
## When it is not appropriate
Bounded, symmetric or binary columns have no tail to compress, and the logarithm is undefined for zero and negative values.
W: B=Transaction amounts across seven orders of magnitude: the strong right skew makes a few large values dominate, and the log compresses the range.
D=Response times with extreme outliers: a positive, long-tailed column is the classic case, and outliers lose influence after the transform.
X: A=Completion rate between 0 and 1: an evenly spread bounded column has no tail to compress, so the log would only distort it.
C=Binary flag: log of 0 is undefined and log of 1 is 0, so the transform destroys the information.
E=Negative symmetric column: the logarithm of negative values is undefined, and a symmetric distribution does not need it.
T: Use a log transform for positive, long-tailed, multi-order-of-magnitude columns, not for bounded, binary or negative ones.

@ DBX-MLA D2 T2.9 applied use-case
S: A practitioner plans to log-transform the heavily skewed feature `revenue` before training a random forest, hoping to improve accuracy. What should the practitioner expect?
A: Little or no change, because tree splits depend only on the order of values and a log transform preserves that order
B: A large gain, because random forests assume normally distributed features
C: A failure, because tree models cannot read transformed columns
D: A large gain, because log transforms increase the number of rows available for splits
K: A
G: ## Monotonic transforms and trees
A decision tree chooses thresholds on a feature, and a split asks only whether a value is above or below a threshold. A strictly increasing transform such as log keeps the order of all values, so it produces the same partitions of the data and, for the same training run, essentially the same tree structure. The transform therefore rarely helps tree ensembles such as random forests or gradient-boosted trees. This is a generally accepted property of tree models.
## Where it still matters
Log transforms help models that depend on magnitude and distance (linear and logistic regression, k-NN, neural networks), and they can help when the transformed column is also the target variable.
W: Little or no change: log is a monotonic transform, so the ordering of values, and with it the possible splits, stays the same.
X: B=Normality assumption: random forests make no distributional assumption about features; that is a feature of some classical statistical models.
C=Failure: the model takes any numeric column; there is no incompatibility.
D=More rows: a column transform does not add rows or split candidates.
T: Tree models are invariant to monotonic feature transforms, so log-transforming features rarely helps them.

@ DBX-MLA D2 T2.9 applied troubleshooting
S: A Spark job computes `df.withColumn("log_visits", F.log("visits"))` for a count column that contains many zeros. Rows with zero visits give unusable results. Which change keeps those rows meaningful?
A: Drop all rows whose visits equal zero before the transform
B: Replace zeros with the mean of `visits`, then take the log
C: Use the base-10 logarithm instead of the natural logarithm
D: Use `F.log1p("visits")`, which computes the log of 1 plus the value and is defined at zero
K: D
G: ## Zeros and the logarithm
The logarithm is not defined at zero. For count data that includes zeros, the usual fix is `log1p(x) = log(1 + x)`, which maps 0 to 0 and behaves like a log for large values. `pyspark.sql.functions.log1p` is available for this purpose. This is a generally accepted practice.
## Why the other fixes cost information
A zero-visit row is information (inactive users). Deleting it, or replacing it by an average, changes what the model sees.
W: log1p: it is defined for zero, keeps zero-visit rows in the data, and still compresses large counts.
X: A=Dropping zero rows: the model would never see the inactive users, which biases training and fails at scoring time when zeros appear.
B=Replacing with the mean: this invents a value for inactive users and mixes them with active ones.
C=Base-10 logarithm: changing the base only rescales the result; the log of zero is still undefined.
T: For non-negative counts with zeros, use log1p instead of log; changing base or dropping zeros does not fix it.

@ DBX-MLA D2 T2.9 advanced use-case
S: After fitting a linear regression to `sales`, a practitioner plots residuals against fitted values and sees a funnel: small residuals for small predictions, much larger residuals for large predictions. The target `sales` is strictly positive. Which step is most likely to help?
A: Add more polynomial terms of the label to the feature set
B: Fit the model to `log(sales)` so errors become more even across the range
C: Remove the intercept from the model to flatten the residuals
D: Standardise the label to zero mean and unit variance
K: B
G: ## Non-constant variance
Linear regression works best when the residual spread is roughly constant across the fitted range. A funnel shape means the variance grows with the level of the target, which is typical of positive quantities where errors are proportional (a 10% error is large on a big number, small on a small one). Transforming the target with a log often stabilises the variance and turns proportional errors into additive ones. This is a generally accepted diagnostic practice.
## Reading predictions
A model fitted on the log scale predicts log values; its predictions must be converted back to the original unit before they are reported (a topic for the metrics section).
W: Fit to log(sales): proportional errors become roughly constant additive errors, which removes the funnel in the residual plot.
X: A=Polynomial terms of the label: the label is the output and cannot be an input feature; using it as one would be target leakage.
C=Removing the intercept: this forces the line through the origin and generally worsens the fit without addressing the changing variance.
D=Standardising the label: a linear rescaling keeps the same funnel shape, so residuals remain just as uneven in relative terms.
T: A residual funnel on a positive target suggests a log transform of the target to stabilise variance.

@ DBX-MLA D3 T3.2 applied use-case
S: A fraud model trains on 20 million transactions of which 0.2% are fraud. A baseline logistic regression predicts "not fraud" for almost everything. In Spark ML, which training-time change addresses the imbalance without removing any rows?
A: Increase `maxIter` so the optimiser runs longer on the majority class

C: Remove the label column from the feature vector
D: Replace the label with its log so that the classes become closer
K: B
G: ## Class weights
With a rare positive class, a model can reach high accuracy by always predicting the majority class. Class weights make errors on the minority class cost more: each row gets a weight (for example inversely proportional to its class frequency) and the loss function sums weighted errors. No rows are removed or duplicated. This is a generally accepted technique.
## In Spark ML
`LogisticRegression` has a `weightCol` parameter naming a column of instance weights; scikit-learn's equivalent is `class_weight="balanced"`.
W: Weight column with `weightCol`: fraud rows count for more in the loss, so the minority class influences the fit without dropping data.
X: A=More iterations: this refines the same unweighted objective and the majority class still dominates.
C=Removing the label from features: the label should already be separate; this does not change class importance.
D=Log of the label: labels are classes; transforming them breaks the classification target.
T: Class weights (weightCol in Spark ML, class_weight in scikit-learn) counter imbalance without discarding rows.

@ DBX-MLA D3 T3.2 applied use-case
S: A 100 million-row Spark training DataFrame has 99% negatives (label 0) and 1% positives (label 1). The team wants to undersample the majority class to about 10%, keeping every positive. Which expression does this?
A: `train.dropDuplicates(["label"])`
B: `train.limit(1000000)`
C: `train.orderBy("label").limit(1000000)`
D: `train.sampleBy("label", fractions={0: 0.1, 1: 1.0}, seed=42)`
K: D
G: ## Stratified undersampling
Random undersampling keeps only a fraction of the majority class so the classes are closer in size. In Spark, `DataFrame.sampleBy(col, fractions, seed)` returns a stratified sample without replacement, where `fractions` gives the keep fraction for each value of the column. Here, 10% of label 0 and 100% of label 1 are kept. This is a generally accepted technique; its cost is the information lost by dropping majority rows.
## Why the others fail
`limit` takes the first rows, not a random or stratified sample, and `dropDuplicates` on the label keeps one row per class.
W: `sampleBy` with fractions: it samples each label value at its own fraction, giving about 10% of negatives and all positives.
X: A=dropDuplicates on label: it keeps one row per distinct label, leaving only two rows.
B=limit: it returns an arbitrary first 1,000,000 rows, which can be almost all negatives and is not stratified.
C=orderBy then limit: sorted by label this returns only label-0 rows, which removes every positive.
T: Use DataFrame.sampleBy with per-class fractions to undersample the majority class in Spark.

@ DBX-MLA D3 T3.2 advanced use-case
S: A team balances a training set by oversampling the minority class. Which TWO practices keep the evaluation honest? (Select TWO)
A: Resample the full dataset first, then split into training and test sets
B: Split first and resample only the training set
C: Evaluate on a test set that keeps the natural class ratio, using metrics such as recall or precision-recall AUC
D: Evaluate on the oversampled training set because it has more positives
E: Use accuracy as the only metric, because balanced training makes it reliable
K: B,C
G: ## Resampling belongs inside training
Resampling changes the class distribution to help the learner. The data used to judge the model, however, should look like the data the model will see in production, which still has the natural imbalance. So the split is made first, only the training portion is resampled, and the test portion is left untouched. Under imbalance, accuracy is misleading, so recall, precision, F1 or precision-recall AUC are used. These are generally accepted evaluation practices.
## Leakage
If duplicated minority rows end up on both sides of a split, the model is scored on rows it has memorised.
W: B=Split first, resample the training set only: the test rows stay independent, so there is no duplicated record on both sides.
C=Natural-ratio test set with imbalance-aware metrics: it estimates production performance, which recall or PR AUC measure properly.
X: A=Resample then split: copies of the same minority rows appear in both sets and inflate the scores.
D=Scoring on the oversampled training set: that measures memorisation, not generalisation.
E=Accuracy only: with a 1% positive rate a model that never flags a positive still scores about 99%.
T: Split first, resample only the training data, and judge on a natural-ratio test set with recall or PR AUC.

S: A data scientist duplicates minority-class rows until the classes are balanced, then makes a random 80/20 split. Validation recall is 0.97, but the model performs far worse in production. What is the most likely cause?
A: Copies of the same minority rows landed in both training and validation, so the model was scored on rows it had already seen
B: Random splits always reduce recall by about 80%
C: Oversampling converts minority rows into majority rows
D: The validation set was too balanced, which raises recall by definition
K: A
G: ## Leakage through duplicates
Random oversampling copies minority rows. If that copying happens before the split, an identical row can be in both the training set and the validation set. The model memorises it in training and is rewarded for recognising it in validation, so the validation recall (0.97) is optimistic. In production there are only new, unseen rows and the recall falls. This is a generally accepted pitfall.
## Fix
Split first, then oversample only the training portion (or use class weights), and validate on untouched data with the natural class ratio.
W: Duplicates on both sides: identical minority rows in training and validation inflate recall, which then does not carry over to unseen production data.
X: B=Random splits reduce recall: there is no such effect; a random split keeps the class mix of the data.
C=Conversion to majority: oversampling duplicates rows with the same label and does not change any label.
D=Balanced validation set: the set is optimistic mostly because of leakage, and a balanced mix is not what raises recall.
T: Oversampling before the split leaks duplicated rows into validation; split first, then resample only the training data.

@ DBX-MLA D3 T3.2 advanced use-case
S: A practitioner replaces random duplication of minority rows with SMOTE from the imbalanced-learn library. How does SMOTE differ from random oversampling?
A: It deletes majority rows until both classes have the same size
B: It assigns larger weights to the minority class without creating rows
C: It creates new synthetic minority rows by interpolating between a minority row and its nearest minority neighbours
D: It copies the whole dataset several times and then shuffles it
K: C
G: ## Synthetic oversampling
Random oversampling repeats existing minority rows, which can lead to overfitting on those exact points. SMOTE (Synthetic Minority Over-sampling Technique) builds new rows: it picks a minority row, finds its k nearest minority neighbours in feature space and creates a point on the line segment between them. This is a generally accepted definition. It is applied to numeric features, and as with other resampling it should be applied only to the training split.
## On Databricks
SMOTE comes from the single-node imbalanced-learn library (it is not part of Spark ML), so it is typically run on a pandas DataFrame, for example after sampling or on a single-node training set.
W: Interpolation between neighbours: SMOTE generates synthetic minority points, which reduces the exact-duplicate problem of random oversampling.
X: A=Deleting majority rows: that is undersampling, a different technique.
B=Class weights: weighting changes the loss and creates no rows, so it is not SMOTE.
D=Copying the whole dataset: this keeps the original class ratio and does not balance anything.
T: SMOTE synthesises new minority rows by interpolating between neighbours; random oversampling just repeats existing rows.

@ DBX-MLA D3 T3.3 applied definition
S: In a Spark ML pipeline, which of the following stages is an `Estimator` that learns from the data when `fit()` is called and produces a model?
A: `VectorAssembler`, which combines columns into one vector
B: `Bucketizer`, which maps values to buckets using fixed split points
C: `SQLTransformer`, which applies a SQL statement to the DataFrame
D: `StandardScaler`, which computes the mean and standard deviation of each feature
K: D
G: ## Estimators versus transformers
In Spark ML, a `Transformer` implements `transform()`, which turns one DataFrame into another, usually by appending columns. An `Estimator` implements `fit()`, which takes a DataFrame and produces a `Model`, and that model is itself a `Transformer`. The distinction is whether anything has to be learned from the data first.
## Examples from the Spark docs
`StandardScaler` is described as an Estimator that is fit on a dataset to produce a `StandardScalerModel` by computing summary statistics. `VectorAssembler` is a transformer that concatenates columns; `Bucketizer` uses split points you provide; `SQLTransformer` runs a SQL statement.
W: StandardScaler: it must compute summary statistics from the training data before it can scale, so it is an Estimator whose `fit()` returns a model.
X: A=VectorAssembler: it concatenates columns by rule and needs no learned state, so it is a Transformer.
B=Bucketizer: its split points are supplied by the user, so nothing is learned from the data.
C=SQLTransformer: it applies a fixed SQL statement and learns nothing.
T: If a stage must learn something from data (statistics, vocabulary, weights) it is an Estimator; fit() returns a Transformer model.

G: ## The two contracts
Spark ML defines two abstractions. A `Transformer` has a `transform()` method that maps a DataFrame to a new DataFrame, generally adding one or more columns; feature transformers and fitted models both qualify. An `Estimator` has a `fit()` method that learns from a DataFrame and returns a `Model`, which is a `Transformer`.

G: ## How Pipeline.fit() works
Stages run in order. For a Transformer stage (`Tokenizer`, `HashingTF`), `transform()` is called and its output DataFrame feeds the next stage. For an Estimator stage (`LogisticRegression`), `fit()` is called on the DataFrame it receives and the resulting model becomes part of the `PipelineModel`. If an Estimator is not the last stage, the pipeline also calls the fitted model's `transform()` to produce the input of the next stage. This is the walk-through in the Spark ML guide.
## Why order matters
Each stage reads columns written by the stage before it, so the stages must be listed in dependency order.
W: transform on Transformers, fit on the Estimator: the tokenizer and hashing stages add columns, and logistic regression is trained on the resulting feature vectors.

B=transform on all, then train separately: the Estimator stage is fit inside the same call as part of the pipeline.
C=Parallel averaging: stages are sequential because each depends on the previous output.
T: Pipeline.fit() applies transform() to Transformer stages and fit() to Estimator stages, in order.
