@ DBX-MLA D4 T4.1 applied use-case
S: A retailer scores all 40 million customers every night with a churn model. Marketing opens the scores the next morning from a Delta table, and nobody needs a prediction at the moment a customer acts. Which deployment mode fits?
A: Real-time serving: one REST request per customer from a scheduler, so each score comes back within milliseconds
B: Batch inference: a scheduled job scores the whole table and writes the predictions to a Delta table
C: Streaming inference: a continuously running pipeline that waits for events and scores each one on arrival
D: Real-time serving with a route-optimized endpoint, so that 40 million calls finish at the highest possible rate
K: B
G: ## Three ways to serve a model
- **Batch inference** runs the model over a large, bounded set of rows on a schedule (hourly, nightly) and stores the predictions, usually in a table. Consumers read the stored results later. Latency per prediction does not matter; throughput and cost do.
- **Real-time (online) inference** keeps a model behind a REST endpoint. A client sends a request and gets a prediction back right away. On Databricks this is Mosaic AI Model Serving, which uses serverless compute and scales with demand.
- **Streaming inference** scores events continuously as they arrive in a stream and writes results to a table or sink, with freshness measured in seconds to minutes.
## How to choose
Ask when the prediction is needed. If it is needed inside a user request, use real-time. If it is needed shortly after an event but not in the request, use streaming. If it is consumed later from a table, batch is the simplest and cheapest.
W: Batch inference: the input is a bounded table, the output is read the next day, and no caller waits, so a scheduled scoring job that writes to Delta needs no always-on endpoint.
X: A=Real-time per customer: it works technically but pays for an always-on endpoint and 40 million round trips to produce results that are only read the next morning.
C=Streaming inference: the input is a finite table scored once a night, not an unbounded event stream, so a continuously running pipeline adds cost for no freshness benefit.
D=Route-optimized endpoint: route optimization targets high-QPS, low-latency online traffic; the mode is still real-time, which is the wrong fit for a nightly bulk job.
T: Prediction needed in the request = real-time; needed seconds after an event = streaming; read later from a table = batch.

@ DBX-MLA D4 T4.1 applied use-case
S: A checkout service must return a fraud score to the payment page while the customer waits, using the values in that single request. Which approach meets the requirement?
A: A nightly batch job that scores all transactions of the previous day and writes the results to a Delta table
B: A triggered pipeline that rescores the transactions table every hour and refreshes a materialized view
C: A weekly retraining job that recomputes the fraud scores for every known customer before the next run
D: A model serving endpoint that the service calls over REST for each request and gets the score in the response
K: D
G: ## Per-request predictions need an online endpoint
Real-time inference means a caller sends input and waits for the prediction. On Databricks, Mosaic AI Model Serving exposes a registered model as a REST API. The service is described as highly available and low-latency, with automatic scale-up and scale-down as demand changes, so the application only needs an HTTP client.
## Why stored scores do not work here
A table of precomputed scores can only contain customers and transactions that existed at the last run. A brand-new transaction has no row yet, so the page would have nothing to read. Per-request input that only exists at checkout time forces online scoring.
W: Model serving endpoint: it scores the new transaction at the moment it is sent, returns the prediction in the HTTP response, and scales with checkout traffic.
X: A=Nightly batch: the new transaction does not exist when the job runs, so the page would show yesterday's data or nothing, with up to a day of delay.
B=Hourly triggered pipeline: triggered mode refreshes the available data and stops, so the score would arrive up to an hour late and never inside the customer's request.
C=Weekly retraining: retraining changes the model, not when predictions are produced, and weekly recomputation is far too slow for a checkout.
T: When the input exists only at request time and a person waits, use a real-time serving endpoint.

@ DBX-MLA D4 T4.1 advanced comparison
S: Clickstream events arrive continuously from a message bus. The business wants each event scored within seconds to minutes and appended to a table that dashboards read, but no caller waits for a response. Which mode fits best?
A: Real-time serving, with every dashboard refresh calling a REST endpoint once per displayed event row
B: Batch inference, with a nightly job that scores the whole event history again and overwrites the table
C: Streaming inference, with a pipeline running in continuous mode that scores new events and appends to a table
D: Batch inference, with a job started by hand each morning that scores only the events of the previous day
K: C
G: ## Streaming sits between batch and real-time
Streaming inference reads a growing source incrementally and scores rows as they arrive, so freshness is seconds to minutes. Nobody waits on a response, which separates it from real-time serving, and the data is unbounded, which separates it from batch.
## Pipeline modes
In Lakeflow Spark Declarative Pipelines (formerly Delta Live Tables), triggered mode refreshes the data available at the start and stops; continuous mode keeps tables fresh as new data arrives. The docs match continuous mode with freshness needs from every 10 seconds to a few minutes, and triggered mode with updates every 10 minutes, hourly or daily.
W: Streaming inference: continuous processing handles the unbounded feed, delivers freshness in seconds to minutes, and writes results to a table with no request-response loop.
X: B=Nightly overwrite: results would be up to a day old, and rescoring all history every night wastes compute on events that were already scored.
A=REST call per row: this turns a table-producing workload into thousands of online calls and puts scoring on the dashboard's critical path, though no caller needs a synchronous answer.
D=Manual morning job: scores arrive a day late and depend on a person, which fails the seconds-to-minutes freshness requirement.
T: Unbounded events + seconds-to-minutes freshness + no waiting caller = streaming inference.

@ DBX-MLA D4 T4.1 applied use-case
S: Which TWO workloads are best served by batch inference rather than a real-time endpoint? (Select TWO)
A: Precomputing next-week demand forecasts for every store and SKU, which planners read in a dashboard on Monday
B: Ranking products for a shopper while the product page loads, using the items viewed in the current session
C: Scoring a freshly typed support message so that an agent sees a suggested category before the reply is sent
D: Scoring a 200-million-row customer table once a month to pick the audience of a marketing campaign
E: Returning a credit decision to a loan applicant who is waiting on the web form after submitting it
K: A,D
G: ## Choosing by consumption pattern
Batch inference suits workloads where the input set is known in advance, the output is stored, and the consumer reads it later. The model runs over the whole table on a schedule, so there is no always-on endpoint and no per-request latency target.
Real-time inference suits workloads where the input only exists at request time (a session, a message just typed) and a person or service waits for the answer.
## Test for each scenario
Ask: does the input exist before the request, and will the result be read later? If both are yes, precompute in batch.
W: A=Demand forecasts: stores and SKUs are a known, finite set, the forecasts are read later in a dashboard, so a weekly scheduled job that writes a table is enough.
D=Monthly campaign audience: the whole customer table exists in advance, and the output is a stored list used later, which is the textbook bulk scoring case.
X: B=Session ranking: the session items exist only while the page loads and the shopper waits, so only an online endpoint can use them.
C=Typed message: the message does not exist until the agent has it open, and the suggestion is needed before replying, which requires an online call.
E=Loan applicant waiting: the decision is needed while the applicant waits on the form, using the submitted input, so it needs an online call.
T: Known, finite input read later = batch; input that appears at request time with someone waiting = real-time.

@ DBX-MLA D4 T4.1 advanced tradeoff
S: A team serves a recommendation model with a scheduled batch job that writes scores to a table. Which downside must the team accept compared with real-time serving?
A: Predictions cannot be written to a Delta table, so consumers must use a REST API to read them
B: The model must be trained again for every run, which makes the scoring job slower than an endpoint
C: Scores are only as fresh as the last run, so new users or changed inputs wait for the next job
D: Only one consumer can read the stored scores at a time, which limits the number of dashboards
K: C
G: ## The staleness trade-off
Batch inference trades freshness for simplicity and cost. Predictions are computed at schedule time and stored, so a row that appears or changes after the run has no score (or an old score) until the next run. Real-time serving computes the prediction from the input in the request, so it always reflects the current input, at the price of an always-available endpoint.
## What batch does not cost you
Stored predictions sit in an ordinary Delta table: many consumers read them in parallel with SQL, dashboards or jobs, and scoring uses an already trained model, loaded from the registry.
W: Staleness: the score reflects the data at the last run, so anything new or changed waits for the next scheduled execution, the main limit of batch.
X: A=Delta output: batch jobs write predictions to Delta tables directly, and consumers read them with SQL, so no REST API is needed to read results.
B=Retraining per run: scoring loads an already trained model and applies it. Training is a separate job on its own schedule.
D=Single reader: Delta tables support many concurrent readers, so any number of dashboards can use the stored scores.
T: Batch = cheap and simple but only as fresh as the last run.

@ DBX-MLA D4 T4.2 applied definition
S: A data scientist has a trained scikit-learn model and wants it available behind a Databricks Model Serving endpoint as a custom model. What is the correct sequence?
A: Package the model in a Docker image, push it to a registry, then point a serving endpoint at the image
B: Create a serving endpoint first, then upload the model file to it and log the model after creation
C: Export the model to ONNX, copy the file to a volume, then start a cluster that exposes it as a REST API
D: Log the model in MLflow format, register it in Unity Catalog, then create an endpoint that serves the version
K: D
G: ## What a custom model is
Databricks calls traditional ML models or Python models packaged in the MLflow format "custom models". Examples are scikit-learn, XGBoost, PyTorch and Hugging Face transformer models. Anything with arbitrary Python code can be wrapped with the `pyfunc` flavor.
## Deployment steps
1. **Log** the model with MLflow (autologging on Databricks Runtime ML, a built-in flavor such as `mlflow.sklearn.log_model`, or custom `pyfunc`). Adding a signature and input example is recommended; a signature is required for Unity Catalog.
2. **Register** it in Unity Catalog (recommended) or the legacy workspace model registry.
3. **Create the endpoint** (Serving UI, REST API or MLflow Deployments SDK) and choose the model and version as the served entity.
Databricks builds the serving container for you, so no image, cluster or ONNX conversion is needed.
W: Log, register, serve: the MLflow format and the registered model version are what the endpoint creation form and API take as the served entity.
X: A=Docker image: custom model serving builds the container from the registered MLflow model, so users do not build or push images.
B=Endpoint first: the endpoint needs an existing registered model version as a served entity, so the model must be logged and registered before creation.
C=ONNX plus cluster: ONNX is not required and a cluster is not the serving mechanism; Model Serving runs on serverless compute managed by Databricks.
T: Custom model serving = log in MLflow format, register (Unity Catalog), create endpoint.

@ DBX-MLA D4 T4.2 applied use-case
S: Which TWO actions prepare a model so that it can be served from a Unity Catalog endpoint? (Select TWO)
A: Log it with MLflow, using a built-in flavor or pyfunc, and include a signature so the input and output schema are known
B: Convert the model to a PySpark ML pipeline, because only Spark ML models can be served from Model Serving
C: Register the logged model in Unity Catalog, so that a versioned model exists that an endpoint can reference
D: Attach the model to a running all-purpose cluster so that the endpoint can borrow that cluster's compute
E: Export the model weights to a CSV file, because serving endpoints load tables and not MLflow models
K: A,C
G: ## What the endpoint needs
A serving endpoint references a **registered model version** as its served entity. Two things must exist first.
- A model **logged in MLflow format**. Built-in flavors (`mlflow.sklearn`, and so on) or `pyfunc` for custom code both work. The Databricks docs recommend a signature and input example, and a signature is necessary for logging models to Unity Catalog.
- A **registered** version in Unity Catalog (recommended) or the workspace registry.
Model Serving supports many frameworks, not only Spark ML, and it runs on its own serverless compute.
W: A=Log with signature: MLflow format is the packaging that Model Serving deploys, and the signature is required for Unity Catalog and documents the schema of requests.
C=Register in Unity Catalog: the endpoint takes a registered model name and version, so registration creates what can be served and governed with `EXECUTE` grants.
X: B=Spark ML only: custom model serving explicitly covers scikit-learn, XGBoost, PyTorch and Hugging Face models, so no conversion to Spark ML is needed.
D=Attach to a cluster: endpoints use serverless Model Serving compute sized by the endpoint settings, not an all-purpose cluster.
E=CSV of weights: endpoints serve MLflow-format models, not exported tables, and a CSV loses the model code and its signature.
T: Log (MLflow format, signature) then register (Unity Catalog); the endpoint serves a registered version.

@ DBX-MLA D4 T4.2 applied troubleshooting
S: An endpoint was created by a data scientist's personal account. After that person left the company and was removed from the workspace, a teammate with full permissions tries to update the endpoint's served model version and gets `PERMISSION_DENIED`. What is the cause and the lasting fix?
A: The endpoint name starts with a reserved prefix; rename it and apply the update again afterwards
B: The new model version has a signature mismatch; relog the model with the previous input example
C: The endpoint scaled to zero while idle; wait for the cold start to finish and then repeat the same update request
D: The recorded creator is no longer a workspace member; recreate the endpoint under a long-lived service principal
K: D
G: ## Creator identity
When an endpoint is created, Databricks records the calling identity as its creator. That identity is used to access Unity Catalog resources on behalf of the endpoint and cannot be changed afterwards.
Configuration and served-entity updates re-check that the recorded creator is still a workspace member and still holds the required grants (`USE CATALOG`, `USE SCHEMA`, `EXECUTE` on the model). If not, the update fails with `PERMISSION_DENIED` even when the person making the call has valid permissions.
## Fix and prevention
Delete the endpoint and recreate it under a service principal that is a current member with the grants. Databricks recommends a long-lived service principal owned by the team, not a personal account that may be removed.
W: Recorded creator removed: the update re-validates the creator's membership, which fails, and the identity cannot be changed, so recreating under a service principal is the lasting fix.
X: B=Signature mismatch: a bad model version would fail with a schema or validation error, not a permission error tied to workspace membership.
C=Scale to zero: a scaled-to-zero endpoint adds cold-start latency to queries, but it does not block configuration updates or raise `PERMISSION_DENIED`.
A=Reserved prefix: the `databricks-` prefix is blocked at creation, and a name that was already accepted cannot cause permission errors later.
T: Use a team-owned service principal as endpoint creator; a removed personal creator breaks every update.

@ DBX-MLA D4 T4.2 advanced tradeoff
S: A team enables scale to zero on the endpoint for an internal demand-forecast API that is called only a few times per day. A second team asks to reuse the same setting on the endpoint behind a payment checkout. What should be said?
A: Scale to zero never adds latency, so it is safe for checkout and always cheaper for any endpoint
B: Scale to zero is not advised for production, since capacity is not guaranteed and idle endpoints pay a cold start
C: Scale to zero is unsupported for custom model endpoints, so the first team must recreate its endpoint without it
D: Scale to zero is only a Unity Catalog permission setting and has no effect on compute or latency
K: B
G: ## What scale to zero does
With scale to zero enabled, a serving endpoint releases its compute when it is idle. This saves cost on endpoints that are rarely called. The cost is that the next request needs compute to start again, a **cold start**, which adds latency, and the docs say capacity is not guaranteed when the endpoint is scaled to zero.
## Decision
- Rarely used, latency-tolerant endpoint (internal tool): scale to zero is reasonable.
- Latency-sensitive production endpoint (checkout): keep minimum capacity running. Databricks does not recommend scale to zero for production endpoints.
W: Not recommended for production: idle endpoints need a cold start and capacity is not guaranteed, which is unacceptable on a payment path but acceptable for an occasional internal call.
X: A=Never adds latency: the docs state the opposite, a scaled-up-again endpoint has extra latency (cold start), and capacity is not guaranteed.
C=Unsupported for custom models: the custom model creation settings include a scale-to-zero option, so the first team's setup is valid and needs no recreation.
D=Permission setting: scale to zero is a compute scaling option of the served entity, unrelated to Unity Catalog grants.
T: Scale to zero saves cost but adds cold-start latency and no capacity guarantee: fine for rare internal calls, not for production paths.

@ DBX-MLA D4 T4.2 applied use-case
S: A model needs to clean the request first (map unseen category values, rename columns) and then call a trained estimator, and the same code must run at serving time. How should the team package it for a custom model endpoint?
A: Wrap the preprocessing and estimator in a custom `mlflow.pyfunc.PythonModel` and log that, so the code is served with the model
B: Keep the preprocessing in a notebook that clients run before calling the endpoint, and log only the bare estimator
C: Log the bare estimator and ask the endpoint to run a separate notebook before each prediction request it receives
D: Log only the preprocessing code as a pyfunc and store the trained estimator in a separate registered model served on its own second endpoint
K: A
G: ## Custom pyfunc models
Besides built-in flavors, MLflow supports **custom logging with `pyfunc`**, which the Databricks docs describe as the method for deploying arbitrary Python code or "additional code alongside your model". You subclass `mlflow.pyfunc.PythonModel`, implement `predict(self, context, model_input)`, and log it. Preprocessing, the estimator and post-processing then travel as one versioned artifact that Model Serving builds into the endpoint.
## Why this beats client-side preprocessing
If every client repeats the cleaning, versions drift and requests differ from training. One packaged model guarantees the same transformation at training-time test and serving time.
W: Custom pyfunc: it bundles the cleaning code and the estimator in one logged, registered artifact, so the endpoint applies the same logic to every request.
X: B=Client notebook: this moves logic out of the model, so each client must reproduce it exactly, and an endpoint cannot call a notebook.
C=Separate notebook per request: endpoints serve the logged MLflow model; they do not execute a notebook before each request.
D=Two models: splitting code and estimator across endpoints doubles network hops and still leaves the caller to chain them.
T: Need custom code with the model at serving time = log a pyfunc `PythonModel` that includes it.

@ DBX-MLA D4 T4.3 applied use-case
S: A data scientist must score 80,000 rows that already fit in memory as a pandas DataFrame, using a registered MLflow model, in a one-off notebook. What is the simplest correct approach?
A: Load the model with `mlflow.pyfunc.load_model` and call `predict` on the pandas DataFrame
B: Convert the rows to a Spark DataFrame and register a new pandas UDF with a separate cluster for each batch
C: Create a model serving endpoint and loop over all rows with one REST call per row, then merge results
D: Retrain the model on the 80,000 rows and use the training predictions as the final output
K: A
G: ## Single-node batch inference with pandas
For a dataset that fits in the memory of one node, load the registered model and call `predict` on a pandas DataFrame:
```
model = mlflow.pyfunc.load_model(model_uri)
preds = model.predict(pdf)
```
`mlflow.pyfunc.load_model` returns a generic Python-function wrapper that works for any flavor, so the same code scores a scikit-learn, XGBoost or custom model. No Spark is needed.
## When to scale out
When the data no longer fits on one node, move to Spark with `mlflow.pyfunc.spark_udf` (see the other scoring questions in this set).
W: Load and predict: the data fits in memory, so one node and one `predict` call on the pandas DataFrame is the least complex route and uses the registered model as is.
X: B=Extra UDF and clusters: this adds distributed machinery that 80,000 rows do not need, and a cluster per batch is not how a UDF is run.
C=Row-by-row REST calls: 80,000 sequential network calls are slow and costly compared with one in-memory prediction, and they need an endpoint that does not exist.
D=Retrain and reuse: training predictions are not scores from the registered model, and they are biased because the model saw those rows.
T: Fits in memory = `load_model` + `predict` on pandas; too large = Spark UDF.

@ DBX-MLA D4 T4.3 applied use-case
S: A registered model must score a 600-million-row Delta table, and the result is written to another table. The data cannot be collected to the driver. What should the team do?
A: Call `toPandas()` on the table, run `predict` on the driver, then write the pandas result back to Delta
B: Load the model as a pandas object inside a loop on the driver and read 10,000 rows at a time
C: Wrap the model with `mlflow.pyfunc.spark_udf` and add the prediction column with `withColumn`
D: Move the table to a CSV file and have each analyst run the notebook on a laptop with the model
K: C
G: ## Distributed batch inference with a Spark UDF
MLflow can export a logged model as an Apache Spark UDF so scoring runs on the executors, in parallel, on a Spark DataFrame:
```
udf = mlflow.pyfunc.spark_udf(spark, model_uri)
df = spark.table(t).withColumn("prediction", udf())
```
The Databricks docs show this pattern for batch jobs (and for Spark Streaming jobs). The data stays distributed, so the table size is limited by the cluster, not by driver memory.
## Why not the driver
`toPandas()` pulls every row to the driver. For hundreds of millions of rows this exhausts memory or runs serially even if it fits.
W: Spark UDF: scoring is parallelized across the cluster, the data never needs to fit on the driver, and the output is a DataFrame that can be saved as a Delta table.
X: A=`toPandas()`: it collects all 600 million rows onto the driver, which runs out of memory and wastes the cluster.
B=Driver loop: this scores serially on one node in many small reads, so most of the cluster sits idle and the job takes far longer.
D=Laptops: moving production data out of the platform creates governance problems and cannot handle the volume.
T: Large table = `mlflow.pyfunc.spark_udf` and `withColumn`; small data = pandas `predict`.

@ DBX-MLA D4 T4.3 applied use-case
S: A nightly scoring job must always use whichever model version is currently marked Champion in Unity Catalog, without editing the job when a new version is promoted. How should the job load the model?
A: Use the URI `models:/prod.ml_team.iris_model/latest`, so the job always gets the newest uploaded version
B: Copy the version number into the job code, then edit and redeploy the job after every promotion
C: Use the URI `models:/prod.ml_team.iris_model@Champion`, so each run resolves the alias to its current version
D: Download the model artifacts once into a volume folder and have the job read the files from there
K: C
G: ## Alias-based loading
A Unity Catalog **alias** is a mutable name that points to one model version, such as `Champion`. A model URI of the form `models:/<catalog>.<schema>.<model>@<alias>` resolves to whatever version the alias points to when the code runs.
The Databricks docs show exactly this for batch inference: loading `models:/prod.ml_team.iris_model@Champion` with `mlflow.pyfunc.load_model`. If the Champion alias is reassigned to a new version, the inference workload picks it up on its next execution, which decouples model deployment from the batch job. The job needs `EXECUTE` on the model plus `USE SCHEMA` and `USE CATALOG`.
W: Alias URI: the alias is resolved at load time on every run, so promoting a new Champion changes what the next batch uses with no job edit.
X: B=Hard-coded version: it works until the next promotion, then it silently keeps scoring with the old model unless somebody edits the job.
A=`latest`: Unity Catalog models are addressed by version number or alias, and "newest uploaded" is not the same as the approved Champion, so an untested version could be scored.
D=Downloaded copy: the files never change after the download, so promotions are ignored and registry governance and lineage are bypassed.
T: Load `models:/<name>@<alias>` in batch jobs so alias moves change the model with no code change.

@ DBX-MLA D4 T4.3 applied troubleshooting
S: A model trained with specific library versions is scored on a different cluster with `mlflow.pyfunc.spark_udf`. Predictions fail or differ because installed packages do not match the model's logged dependencies. What does Databricks suggest for the UDF?
A: Set `env_manager="virtualenv"` in `spark_udf`, so the model's dependencies are restored for the UDF only
B: Downgrade the cluster runtime to the oldest version available and retry the same notebook there
C: Convert the model to a CSV of coefficients and rebuild the prediction formula in SQL on the new cluster
D: Install the model's packages on the driver only and keep the UDF on the executors unchanged
K: A
G: ## Model dependencies and UDFs
MLflow logs the Python packages a model needs. When the scoring environment differs, MLflow warns about the mismatch. For `pyfunc` models you can fetch the requirements with `mlflow.pyfunc.get_model_dependencies` and `%pip install` them in the notebook.
For Spark UDF scoring, the Databricks docs add a better option: pass `env_manager="virtualenv"` to `mlflow.pyfunc.spark_udf`. This restores the model's dependencies in the context of the UDF and does not affect the outside environment, so the notebook's own libraries stay untouched.
W: `env_manager="virtualenv"`: it rebuilds the logged dependency set just for the UDF, keeping exact versions without changing the notebook environment.
X: B=Oldest runtime: guessing a runtime does not guarantee the model's versions and loses other fixes on the cluster.
C=SQL formula: rebuilding a model by hand is error-prone, impossible for non-linear models and skips the logged artifact.
D=Driver only: the UDF runs on the executors, so fixing the driver leaves the executors with the mismatched libraries.
T: Mismatched dependencies in `spark_udf` = `env_manager="virtualenv"`; for pandas scoring use `get_model_dependencies` and `%pip install`.

@ DBX-MLA D4 T4.3 applied definition
S: Which TWO code patterns score a logged MLflow model in batch on Databricks? (Select TWO)
A: `mlflow.pyfunc.load_model(uri).predict(pdf)` on a pandas DataFrame that fits on one node
B: `spark.table(t).predict(model)` which adds a prediction column to a Spark DataFrame using the registered model
C: `mlflow.pyfunc.load_model(uri).fit(pdf)` which scores the rows after refreshing the model's weights
D: `df.withColumn("prediction", mlflow.pyfunc.spark_udf(spark, uri)())` on a Spark DataFrame
E: `spark.read.format("mlflow").load(uri)` which returns the predictions of the model for the whole table
K: A,D
G: ## Two supported scoring patterns
- **pandas**: `mlflow.pyfunc.load_model(model_uri)` returns a model object whose `predict` takes a pandas DataFrame (or NumPy array) and returns predictions. Good for data in memory on one node.
- **Spark UDF**: `mlflow.pyfunc.spark_udf(spark, model_uri)` returns a UDF applied with `withColumn` for a distributed Spark DataFrame. Calling the UDF without arguments uses the columns from the model signature.
## What does not exist
- A Spark DataFrame has no `predict(model)` method.
- A pyfunc model is for scoring and exposes `predict`, not `fit`; scoring does not retrain.
W: A=pandas predict: loading the pyfunc model and calling `predict` on a pandas DataFrame is the documented single-node batch scoring path.
D=Spark UDF: `spark_udf` plus `withColumn` is the documented distributed batch path, and the same UDF also works in Spark streaming jobs.
X: B=`DataFrame.predict`: Spark DataFrames have no such method, so the call raises an `AttributeError`; scoring requires a UDF or a model's `predict`.
C=`fit` on pyfunc: the loaded pyfunc wrapper is for inference; it has no `fit`, and retraining is not scoring anyway.
E=`spark.read.format("mlflow")`: MLflow models are loaded with pyfunc APIs, and no such Spark data source exists for scoring a table.

@ DBX-MLA D4 T4.4 applied use-case

@ DBX-MLA D4 T4.4 advanced troubleshooting

G: ## Streaming tables process each row once
In a pipeline, a **streaming table** processes each record exactly once, assuming an append-only source. A row already appended is not re-read on later updates. @ DBX-MLA D4 T4.4 advanced comparison
S: Raw events are appended to a table continuously and never updated. A team wants a pipeline dataset that holds the scored events, adding each new event once, at low latency. Which dataset type fits?
A: A materialized view, because it always recomputes the full table on each update
B: A streaming table, because it processes each appended record once with incremental, low-latency handling
C: A view, because views are persisted to the catalog and can be queried by other pipelines
D: A materialized view, because it is the only dataset type that is able to read from a streaming source such as Kafka
K: B
G: ## Choosing a pipeline dataset type
- **Streaming table**: each record is processed exactly once for an append-only, growing source; suited to ingestion and incremental processing, high throughput and low latency.
- **Materialized view**: results are recomputed as needed to match the current state of the data; suited to aggregations, joins and sources that can change by updates and deletes.
- **View**: evaluated on demand and not persisted; usable only inside the same pipeline.
## Applying it
Append-only events with a "score each once" requirement is the streaming table pattern. If the source could be updated or deleted, or the query needs joins that must stay correct when a dimension changes, a materialized view is safer because streaming-table joins do not recompute when dimensions change.
W: Streaming table: it reads new rows from the growing source on every update and appends the result once, which matches append-only, low-latency scoring.
X: A=Full recompute: a materialized view recomputes as needed (incrementally when possible); it is meant for changing data and joins, not for append-once low-latency ingestion.
C=View: views are not persisted and can be used only within the same pipeline, so nothing would be stored for others to read.
D=Only MV supports streaming: the claim is reversed, since streaming tables are always defined against streaming sources.
T: Append-only growing source, score once = streaming table; changing source or joins that must stay correct = materialized view.

@ DBX-MLA D4 T4.4 advanced use-case
S: A streaming table in a pipeline computes windowed features before scoring. The stream has no end, and the pipeline fails from memory pressure. Which TWO measures keep the stream's state bounded? (Select TWO)

B: Run a full refresh of the streaming table at every update, so that no state is retained between updates

G: ## Bounded state
Streaming tables are built for low-latency streaming over **bounded state** and use checkpoints. They expect streams that are naturally bounded or bounded with a watermark. An unbounded stream without a watermark can cause a pipeline to fail due to memory pressure.
- A **naturally bounded** stream has a defined start and end, for example a directory of files where no new files are added after the initial batch.
- A **watermark** in Structured Streaming tells the engine how long to wait for delayed events before treating a window as complete, so old state can be dropped.
## Not a fix
Repeating a full refresh or changing the dataset type does not bound the state of a windowed streaming query.
W: A=Naturally bounded source: a finite source ends, so the amount of state is limited by its size.

D=View: views are evaluated on demand and are not persisted; they do not cache windows or release state, and a view of the same unbounded query has the same problem.
E=More shuffle partitions: this changes how state is distributed, not how much of it is kept, so an unbounded stream still grows without limit.
T: Streaming tables need naturally bounded streams or a watermark; otherwise state grows until memory fails.
