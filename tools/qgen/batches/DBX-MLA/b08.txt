@ DBX-MLA D3 T3.10 applied use-case
S: A Spark ML `ParamGridBuilder` defines 3 values of `regParam` and 4 values of `maxIter`. The grid is passed to a `CrossValidator` with `numFolds=5`. How many model fits does the search itself run, not counting the final refit on the full dataset?
A: 12, one fit for each combination of `regParam` and `maxIter`
B: 60, one fit for each combination in each of the five folds
C: 61, the search fits plus one fit for the final best model
D: 20, one fit for each fold and each `maxIter` value
K: B
G: ## Counting fits
A parameter grid is the Cartesian product of the value lists, so 3 values of `regParam` and 4 values of `maxIter` give 3 x 4 = 12 `ParamMap`s (combinations). This arithmetic is a generally accepted definition, and the Spark ML tuning guide describes the same procedure.
- `CrossValidator` splits the data into `numFolds` pairs of training and validation sets and evaluates every `ParamMap` on every pair.
- Search fits = combinations x folds = 12 x 5 = 60.
- After the best `ParamMap` is chosen, `CrossValidator` re-fits the estimator on the entire dataset, which is one more fit (61 in total).
W: 60 fits: each of the 12 combinations is trained once per fold, and the question excludes the refit.
X: A=12: this counts combinations only and forgets that every combination is repeated in each of the five folds.
C=61: it adds the final refit on the full dataset, which the question explicitly leaves out.
D=20: it multiplies folds by only one parameter's values and ignores the other parameter, so it does not match the product of the grid.
T: Fits in a search = grid combinations x folds; the refit adds one more.

@ DBX-MLA D3 T3.10 applied use-case
S: A data scientist builds a grid of 3 values for `numTrees` and 2 values for `maxDepth` and tunes a Spark ML `RandomForestRegressor` with `TrainValidationSplit`. How many models are fitted in total, including the final model trained with the best parameters on the whole dataset?
A: 6, one fit for each of the parameter combinations
B: 3, one fit for each value of `numTrees`
C: 12, each combination is fitted twice, once for training and once for validation
D: 7, six combination fits plus the final fit on the entire dataset
K: D
G: ## Single split versus folds
The Spark ML tuning guide states that `TrainValidationSplit` evaluates each parameter combination once, in contrast to k times for `CrossValidator`. It creates one (training, validation) pair, for example 75% and 25% with `trainRatio=0.75`.
- Combinations: 3 x 2 = 6, so 6 fits during the search.
- Like `CrossValidator`, it finally fits the estimator with the best `ParamMap` on the entire dataset: 1 more fit.
- Total: 6 + 1 = 7.
The arithmetic is a generally accepted counting definition.
W: 7 models: six combinations are each fitted once on the training part, and the best one is refitted on the whole dataset.
X: A=6: this is correct for the search alone, but the question counts the final model trained on the whole dataset too.
B=3: it counts only one parameter's values, but a grid tries every combination of both parameters.
C=12: a fit happens only on the training part; the validation part is used to score the model, so it never doubles the number of fits.
T: TrainValidationSplit = combinations fits + 1 refit; CrossValidator = combinations x folds + 1.

@ DBX-MLA D3 T3.10 applied use-case
S: A team's grid had 4 values of `maxDepth` and 3 values of `minInstancesPerNode`, evaluated with 3 folds. They now add two more `minInstancesPerNode` values (5 in total) and move to 5 folds. How many fits does the search run now, not counting the refit?
A: 100, since 4 x 5 combinations are each fitted in 5 folds
B: 60, since 4 x 3 combinations are each fitted in 5 folds
C: 36, since 4 x 3 combinations are each fitted in 3 folds
D: 20, since only the 4 x 5 combinations are counted once each
K: A
G: ## Both factors grow
The number of fits is combinations x folds. The earlier setup gave 4 x 3 x 3 = 36 fits. Changing both the grid and the folds multiplies the effect:
- New combinations: 4 x 5 = 20.
- New fits: 20 x 5 = 100.
Cost grows roughly 2.8 times for a change that sounds small. With Spark ML you can set `parallelism` on the `CrossValidator` to evaluate several `ParamMap`s at once, but the count of fits stays the same.
W: 100 fits: the new grid has 4 x 5 = 20 combinations, and each of them is trained once in each of the five folds.
X: B=60: it uses the five folds but keeps the old grid of 3 values for `minInstancesPerNode`.
C=36: it is the old configuration before the grid and the number of folds were changed.
D=20: it counts the combinations once and ignores that cross-validation repeats each combination in every fold.
T: Grid size and fold count multiply; widening both changes cost quickly.

@ DBX-MLA D3 T3.10 advanced tradeoff
S: A grid search over three hyperparameters with 4 values each runs with `CrossValidator(numFolds=5)`, which is too slow. Which TWO changes bring the number of search fits below 100? (Select TWO)
A: Switch to `TrainValidationSplit` and keep the same grid
B: Set `parallelism=8` and keep the same grid and folds
C: Cut each hyperparameter to 3 values and use 3 folds
D: Set `collectSubModels=True` and keep the same grid and folds
E: Keep the grid and folds and add a second evaluator metric

G: ## Where the count comes from
4 x 4 x 4 = 64 combinations, times 5 folds = 320 fits. Only changes to the grid size or to the number of evaluations per combination change this number. These counts are generally accepted arithmetic.
- `TrainValidationSplit` evaluates each combination once: 64 fits.
- 3 values per parameter and 3 folds: 27 x 3 = 81 fits.
- `parallelism` (in Spark ML, the number of `ParamMap`s evaluated at the same time) shortens wall-clock time but not the count.
- `collectSubModels` keeps the fitted sub-models for later inspection, which adds memory use and not fewer fits.
W: A=TrainValidationSplit: one validation pair per combination, so 64 fits, below 100.
C=Smaller grid and fewer folds: 3 x 3 x 3 = 27 combinations times 3 folds = 81 fits, below 100.

D=collectSubModels: it only stores the fitted models, so the number of fits stays at 320 and memory use grows.

@ DBX-MLA D3 T3.11 applied definition
S: A team scores a binary classifier with Spark ML `BinaryClassificationEvaluator` and wants the area under the precision-recall curve instead of the default metric. Which `metricName` do they set?
A: `f1`, the harmonic mean of precision and recall
B: `prAUC`, a short name for the area under the precision-recall curve
C: `areaUnderPR`, the area under the precision-recall curve
D: `areaUnderRecall`, the area under the recall curve
K: C
G: ## Metrics in the binary evaluator
According to the PySpark documentation, `BinaryClassificationEvaluator` supports exactly two metric names: `areaUnderROC` (the default) and `areaUnderPR`. It reads a `rawPrediction` column (a length-2 vector or a numeric score) and a `label` column.
- `areaUnderROC`: area under the receiver operating characteristic curve (true positive rate against false positive rate across thresholds).
- `areaUnderPR`: area under the precision-recall curve; often more informative when positives are rare.
Metrics such as `f1`, `accuracy` and `logLoss` belong to `MulticlassClassificationEvaluator`. The definitions of the curves are generally accepted.
W: areaUnderPR: this is the documented name for the area under the precision-recall curve in the binary evaluator.
X: A=f1: valid for the multiclass evaluator, but the binary evaluator rejects it because only the two area metrics are supported.
B=prAUC: this name does not exist in Spark ML; the area metric is named `areaUnderPR`.
D=areaUnderRecall: there is no such metric; recall is a point on a curve and not an area metric in the evaluator.
T: BinaryClassificationEvaluator = areaUnderROC (default) or areaUnderPR.

@ DBX-MLA D3 T3.11 applied use-case
S: A multiclass model outputs class probabilities, and the team wants its log loss with Spark ML. Which setup computes it?
A: `MulticlassClassificationEvaluator(metricName="logLoss")` on `label` and `probability` columns
B: `BinaryClassificationEvaluator(metricName="logLoss")` on `label` and `rawPrediction` columns
C: `MulticlassClassificationEvaluator(metricName="logLoss")` on `label` and `prediction` columns
D: `RegressionEvaluator(metricName="mse")` on the label and predicted class index columns
K: A
G: ## Log loss in Spark ML
Log loss (cross-entropy) averages the negative log of the probability the model assigned to the true class. It punishes confident wrong answers heavily and is lower for better models; this is the generally accepted definition.
- The PySpark docs list `logLoss` among the `MulticlassClassificationEvaluator` metrics (with `f1`, `accuracy`, `hammingLoss`, `weightedPrecision` and others) and state that the `probabilityCol` is only used for `logLoss`.
- Hard class predictions (`prediction`) alone carry no probability, so log loss cannot be computed from them.
W: Multiclass evaluator with a probability column: it is the documented place for `logLoss`, which reads the class probabilities.
X: B=Binary evaluator: it supports only `areaUnderROC` and `areaUnderPR`, so `logLoss` is not a valid name.
C=Only prediction: the label and hard prediction hold no confidence, and the evaluator needs `probabilityCol` for log loss.
D=Regression mse: this measures squared distance between class indexes, which have no numeric meaning for classes, and it is not log loss.
T: logLoss lives in MulticlassClassificationEvaluator and needs the probability column.

@ DBX-MLA D3 T3.11 applied use-case
S: A classifier reaches precision 0.90 and recall 0.30 for the positive class. What is its F1 score for that class?
A: 0.60, the arithmetic mean of precision and recall
B: 0.27, the product of precision and recall
C: 0.90, the precision, because F1 follows the higher value
D: 0.45, the harmonic mean of precision and recall
K: D
G: ## F1
F1 = 2 x precision x recall / (precision + recall), the harmonic mean (generally accepted definition). Here 2 x 0.90 x 0.30 / 1.20 = 0.45.
- The harmonic mean is pulled toward the smaller value, so a model cannot hide poor recall behind high precision.
- In Spark ML, `MulticlassClassificationEvaluator` uses `f1` as its default metric name (a weighted F1 across classes) and offers `fMeasureByLabel` for one class.
W: 0.45: the harmonic mean 2 x 0.90 x 0.30 / (0.90 + 0.30) equals 0.45, well below the mean of the two inputs.
X: A=0.60: the arithmetic mean is not F1 and hides the weak recall that F1 is meant to expose.
B=0.27: the plain product of precision and recall is not scaled by the sum, so it is not F1.
C=0.90: F1 is limited by the lower of the two values and never follows the higher one.
T: F1 is the harmonic mean of precision and recall, pulled toward the smaller one.

@ DBX-MLA D3 T3.11 applied use-case
S: A team passes the hard 0/1 `prediction` column of a classifier as the `rawPredictionCol` of `BinaryClassificationEvaluator` with the default metric. On the validation set the true positive rate is 0.80 and the true negative rate is 0.90. What does the evaluator return?
A: 0.72, the product of the two rates
B: 0.85, the average of the two rates
C: 0.90, the larger of the two rates
D: An error, because the column must hold a vector of scores
K: B
G: ## ROC AUC from hard predictions
The PySpark documentation says the `rawPrediction` column can be a double (a binary 0/1 prediction or the probability of label 1) or a length-2 vector. A 0/1 column is therefore accepted, but it holds only one threshold.
- The ROC curve then has three points: (0, 0), (FPR, TPR) and (1, 1), with FPR = 1 - 0.90 = 0.10 and TPR = 0.80.
- The area under those two line segments is (1 + TPR - FPR) / 2 = (1 + 0.80 - 0.10) / 2 = 0.85, which equals the average of the true positive and true negative rates (balanced accuracy).
- With real scores or probabilities the curve has many points and measures ranking quality, so scores are the better input.
W: 0.85: a 0/1 column gives a ROC curve with one interior point, and its area is the mean of TPR and TNR, (0.80 + 0.90) / 2.
X: A=0.72: the product 0.80 x 0.90 is not an area under any ROC curve.
C=0.90: the area depends on both rates and is not simply the larger one.
D=Error: the documentation lists a double column of 0/1 predictions as valid input, so no error is raised.
T: AUC on hard predictions equals balanced accuracy; feed scores to measure ranking.

@ DBX-MLA D3 T3.11 advanced comparison
S: Two binary classifiers both reach 90% accuracy at a 0.5 threshold. Model X's wrong predictions have probabilities near 0.5. Model Y's wrong predictions have probabilities near 0.99 for the wrong class. Which metric separates the models, and which model does it favor?
A: F1 at the 0.5 threshold, which favors model Y because its errors are more confident
B: `areaUnderROC`, which scores model Y higher because its errors are more extreme
C: Log loss, which favors model X because it is less confident when it is wrong
D: `hammingLoss`, which favors model Y because its wrong predictions are further away
K: C
G: ## Why accuracy is not enough
Accuracy and F1 at a fixed threshold only look at the hard class, so the two models look alike. Log loss (generally accepted definition) uses the probability of the true class, so a prediction of 0.01 for the true class costs far more than one of 0.45.
- Lower log loss is better, so model X (mild errors) beats model Y (confident errors).
- Spark ML computes `logLoss` in `MulticlassClassificationEvaluator`, which needs the probability column.
- `hammingLoss` is the fraction of wrong labels, the same for both models here.
W: Log loss: confident mistakes add a large penalty, so the model with milder errors has the lower loss and wins.
X: A=F1 at 0.5: both models make the same number of errors at that threshold, so F1 cannot tell them apart and does not reward confident errors.
B=areaUnderROC: it measures ranking, never favors "more extreme" mistakes, and there is no reason for it to prefer the confidently wrong model.
D=hammingLoss: it is the share of wrong labels, which is 10% for both models, so it does not separate them.
T: Log loss rewards honest uncertainty; threshold metrics ignore it.

@ DBX-MLA D3 T3.12 applied definition
S: A Spark ML `RegressionEvaluator` is created without setting `metricName`. Which metric does `evaluate` return?

B: `r2`, the coefficient of determination
C: `mae`, the mean absolute error
D: `mse`, the mean squared error

G: ## Regression metric names
The PySpark documentation lists the `RegressionEvaluator` metric names:
- `rmse`: root mean squared error (the default)
- `mse`: mean squared error
- `r2`: the R-squared metric
- `mae`: mean absolute error
- `var`: explained variance

@ DBX-MLA D3 T3.12 applied use-case
S: A delivery-time model makes five errors of 1, 1, 1, 1 and 16 minutes (absolute values) on a validation set. Which statement about its MAE and RMSE is correct?
A: MAE is about 7.2 and RMSE is 4, because MAE weights the 16-minute miss more heavily
B: MAE and RMSE are both 4, because both average the errors the same way
C: MAE is 20 and RMSE is about 7.2, because MAE sums the five errors
D: MAE is 4 and RMSE is about 7.2, because squaring gives the 16-minute miss a large weight
K: D
G: ## Outliers and the two averages
- MAE = mean of absolute errors = (1+1+1+1+16)/5 = 4.0 minutes.
- RMSE = square root of mean squared error = sqrt((1+1+1+1+256)/5) = sqrt(52) = about 7.2 minutes.
Both are in the label's units (these are generally accepted definitions, and Spark ML names them `mae` and `rmse`). RMSE is never smaller than MAE, and the gap grows when a few errors are large, because squaring makes them dominate.
W: MAE 4 and RMSE about 7.2: the squared 16-minute error dominates the mean of squares, while MAE treats every minute alike.
X: A=Swapped values: it assigns the large-error weighting to MAE, but MAE is the metric that treats all errors linearly.
B=Both 4: RMSE squares before averaging, so it gives a different, larger value whenever errors are uneven.
C=MAE of 20: MAE is a mean, so it divides the sum of 20 by five and gives 4.
T: RMSE punishes large errors more than MAE; RMSE >= MAE.

@ DBX-MLA D3 T3.12 applied use-case
S: A regression model evaluated on a validation set returns an `r2` of -0.3. What does the value say?
A: The model explains 30% of the variance with the opposite sign of the relation
B: The model fits worse than always predicting the mean of the validation labels
C: The evaluation is invalid because R-squared must be between 0 and 1
D: The model's average error is 30% of the mean label value
K: B
G: ## What R-squared compares
R-squared = 1 - (sum of squared residuals of the model) / (sum of squared deviations from the mean of the labels); this is the generally accepted definition.
- 1.0: perfect predictions. 0.0: no better than predicting the mean label for every row.
- Negative: worse than that baseline, which is possible on held-out data (and even in training for models without an intercept). It usually signals a poor model or a mismatch between the training and validation data.
Spark ML returns this value with `RegressionEvaluator(metricName="r2")`.
W: Worse than the mean: the sum of squared residuals is larger than that of the constant mean predictor, so the ratio exceeds 1 and R-squared falls below 0.
X: A=Opposite relation: R-squared does not measure the sign or direction of a relationship, so -0.3 is not "30% explained in reverse".
C=Invalid result: the 0-to-1 range holds only for training fits with an intercept; on new data it can be negative.
D=30% average error: R-squared is a unitless variance ratio and not a percentage error.
T: R-squared 0 = the mean baseline; negative = worse than the baseline.

@ DBX-MLA D3 T3.12 applied comparison
S: Which statement correctly compares RMSE and MAE for the same predictions?
A: MAE is measured in squared units of the label and punishes outliers more
B: RMSE is unitless and always lies between 0 and 1
C: Both are in the label's units, and RMSE is never smaller than MAE
D: RMSE is robust to outliers because it averages the squared residuals
K: C
G: ## Properties
- MAE = mean(|y - y_hat|) and RMSE = sqrt(mean((y - y_hat)^2)), generally accepted definitions.
- Both have the same units as the label (dollars, minutes), unlike MSE, which is in squared units.
- By the power-mean inequality RMSE >= MAE, with equality only if all absolute errors are equal.
- RMSE grows faster when a few errors are large, so it is the more outlier-sensitive of the two.
In Spark ML they are `rmse` and `mae` in `RegressionEvaluator`.
W: Same units, RMSE >= MAE: both take a root or an absolute value so they stay in the label's units, and the squaring step can only raise the average.
X: A=Squared units: MAE has no squaring, so it keeps the label's units and is less sensitive to outliers than RMSE.
B=Unitless 0-to-1: RMSE is in label units and can be any non-negative number.
D=Robust RMSE: squaring makes large residuals count more, so RMSE is less robust to outliers than MAE.
T: RMSE and MAE share the label's units; RMSE >= MAE and reacts more to large errors.

@ DBX-MLA D3 T3.12 applied use-case
S: A `CrossValidator` uses `RegressionEvaluator(metricName="rmse")`. How does it pick the best `ParamMap`?
A: The one with the highest RMSE averaged across folds
B: The one with the lowest RMSE in the first fold only
C: The one with the highest R-squared, because `r2` is the metric of every evaluator
D: The one with the lowest RMSE averaged over folds, as smaller is better here

G: ## How the evaluator steers selection
`CrossValidator` computes the evaluator's metric for each `ParamMap` on each fold and averages over the folds. The default metric used to choose the best `ParamMap` can be overridden with `setMetricName` on the evaluator (Spark ML tuning guide). The evaluator also exposes `isLargerBetter`: for `rmse`, `mse` and `mae` it is false, for `r2` it is true.
- Selection takes the lowest average error for error metrics and the highest average score for `r2`.
- Using `r2` with the same grid can pick a different model only if the rankings differ, but each choice is based on the metric you set.
W: Lowest average RMSE: the evaluator reports that smaller is better, so the combination with the smallest mean across the folds wins.
X: A=Highest RMSE: it would choose the least accurate setting, which contradicts the direction the evaluator reports.
B=First fold only: cross-validation averages over all folds so that the choice does not depend on a single split.
C=Highest R-squared: the metric is whatever `metricName` says; with `rmse` set, no R-squared is computed.
T: CrossValidator averages the chosen metric over folds and respects its direction (smaller RMSE is better).

@ DBX-MLA D3 T3.13 applied use-case

@ DBX-MLA D3 T3.13 applied use-case
S: A screening model flags patients for a follow-up test. Missing a sick patient is far more costly than a false alarm, which only triggers an extra test. Which metric should the team prioritize?
A: Recall of the positive class
B: Precision of the positive class
C: True negative rate (specificity)
D: Weighted precision across the classes
K: A
G: ## Match the metric to the cost
- Recall = TP / (TP + FN): the share of sick patients found. It falls with each missed case (false negative).
- Precision = TP / (TP + FP): the share of flagged patients who are sick. It falls with false alarms.
- Specificity = TN / (TN + FP): the share of healthy patients correctly cleared.
When false negatives are the costly error, maximize recall (usually by lowering the decision threshold) and accept lower precision. These are generally accepted definitions; Spark ML exposes them as `recallByLabel` and `precisionByLabel` in `MulticlassClassificationEvaluator`.
W: Recall: it measures how many real positives are found, which is exactly the cost of missing sick patients.
X: B=Precision: it penalizes false alarms, which the scenario treats as cheap.
C=Specificity: it counts healthy patients cleared correctly, and says nothing about sick patients who were missed.
D=Weighted precision: it averages precision over classes by support, so it is again about false alarms.
T: Costly false negatives -> recall; costly false positives -> precision.

@ DBX-MLA D3 T3.13 applied use-case
S: A spam filter moves flagged mail into a folder that users rarely open. Losing a legitimate message is much worse than letting some spam through. Which metric should be optimized?
A: Recall of the spam class
B: Overall accuracy across the legitimate and spam classes
C: Precision of the spam class
D: Mean absolute error of the spam score
K: C
G: ## Which error hurts
Here a false positive (legitimate mail marked as spam) is the expensive error. Precision for the spam class = TP / (TP + FP) drops with every legitimate message flagged, so a high-precision filter rarely hides good mail. Recall would rise when more is flagged, which pushes in the opposite direction. These are generally accepted definitions.
- Typical approach: raise the decision threshold until precision reaches the target, then check how much recall is lost.
- Report the choice with a precision-recall curve, so the trade-off is visible.
W: Precision of the spam class: it falls whenever legitimate mail is flagged, so maximizing it avoids the costly mistake.
X: A=Recall of spam: it rewards catching every spam message and so encourages flagging more, which puts good mail at risk.
B=Overall accuracy: it mixes both errors and is dominated by the larger class, so it does not focus on false positives.
D=MAE of the score: this is a regression metric for numeric targets and does not measure classification mistakes.
T: Costly false positives -> precision.

@ DBX-MLA D3 T3.13 applied comparison
S: A team forecasts delivery times in minutes. A handful of records have wrong timestamps that create extreme values, and the team does not want them to dominate the choice among models. They also want the score in minutes. Which `RegressionEvaluator` metric fits?
A: `rmse`, because squaring emphasizes the extreme errors
B: `mse`, because it is in minutes squared
C: `r2`, because it is unitless
D: `mae`, because it weighs every error linearly

G: ## Choosing among regression metrics
- `rmse` and `mse` square the residuals, so a few large errors dominate the score. Use them when large misses are especially costly.
- `mae` averages absolute errors: each minute of error counts the same, and the result is in minutes.
- `r2` is relative to the variance of the labels and not in minutes; it is also affected by outliers.
Generally accepted guidance is to match the metric to the business cost of an error. Here extreme records are noise, so a linear penalty is the better choice. Fixing the timestamps is still the best remedy.
W: mae: it grows linearly with each error, so a few extreme rows do not decide the ranking, and it stays in minutes.
X: A=rmse: it is in minutes but amplifies exactly the extreme errors the team wants to damp down.
B=mse: it is in squared minutes, so it fails the requirement for minutes, and it amplifies outliers even more.
C=r2: it is unitless, so the requirement for minutes is not met, and squared errors still drive it.
T: Outlier-heavy noise and a unit-based score -> MAE; costly big misses -> RMSE.

G: ## Metrics that look at the minority class
With 1% positives, a model that never predicts the positive class reaches 99% accuracy. The generally accepted remedy is to use metrics computed for the positive class.

- F-measure for one label (`fMeasureByLabel`, with `metricLabel=1.0`, in the multiclass evaluator) combines precision and recall of that class at the model's threshold.

C=hammingLoss: it is the fraction of wrongly predicted labels, so an always-negative model gets about 1%, which looks excellent.

Training on `log(y)` makes the model predict `log(y)`. Its outputs, and any error computed from them, are on the log scale.

@ DBX-MLA D3 T3.14 applied definition
S: A target with many zero values was transformed with `np.log1p(y)` before training. Which function converts the model's predictions back to the original scale?

D: `np.exp(x) + 1`, which adds back the shift
K: C
G: ## Why log1p
`log1p(y)` = log(1 + y) works when `y` can be zero, where `log(0)` is undefined. Its exact inverse is `expm1(x)` = exp(x) - 1, because exp(log(1 + y)) - 1 = y. These are generally accepted math facts (NumPy provides both functions).
- `exp(x)` alone returns 1 + y, so every prediction would be off by one.
- Applying `log1p` again would shrink values further, not undo anything.
- Adding 1 goes the wrong way: the shift has to be subtracted.
W: expm1: exp(log(1 + y)) - 1 gives back y exactly, including for y = 0, so it is the exact inverse of `log1p`.
X: A=exp: the plain inverse of log, but with log1p it returns 1 + y, so each prediction is too high by one.
B=log1p again: it is another logarithm, which shrinks the values further.
D=exp plus one: it adds the shift again and is off by two from the original value.
T: log1p is undone by expm1; log by exp.

@ DBX-MLA D3 T3.15 advanced tradeoff
