@ DBX-MLA D1 T1.6 applied use-case
S: An ML engineer must create a feature table of customer activity metrics. Each row holds values as of a timestamp, and training must join each label to the latest feature values known before the label's event time. Which table definition does this?
A: A Delta table with `CONSTRAINT pk PRIMARY KEY (customer_id)` and a plain `ts timestamp` column that holds the date of each computation
B: A Delta table with `CONSTRAINT pk PRIMARY KEY (customer_id, ts TIMESERIES)` where `ts` is a `NOT NULL` timestamp column
C: A Delta table with `CONSTRAINT pk PRIMARY KEY (customer_id, ts)` and no further keyword, so the engine detects the timestamp type
D: A Delta table with `CONSTRAINT pk PRIMARY KEY (customer_id)` and `PARTITIONED BY (ts)`, so each partition holds one snapshot
K: B
G: ## What a feature table is
In Unity Catalog a feature table is simply a Delta table that has a primary key constraint; the key identifies the entity (a customer, a product) whose features the row holds. You can create it with Databricks SQL, the Python `FeatureEngineeringClient`, or a pipeline. The exam guide still says "feature store" and the older workspace-level version (Workspace Feature Store, now legacy, with a `timestamp_keys` argument). Databricks now recommends Feature Views for new work, where Databricks manages the feature pipelines; feature tables, which you populate yourself, remain fully supported and are what this question tests.
## Time series feature tables
Feature values change over time. If a model is trained on feature values measured after the label's timestamp, the training data leaks the future. A **time series feature table** marks one primary key column with the `TIMESERIES` keyword (`PRIMARY KEY (customer_id, ts TIMESERIES)`). With that marking, `create_training_set` and `score_batch` perform an as-of join: for each label row they pick the latest feature row at or before the lookup timestamp. In Python the same marking is the `timeseries_columns` argument.
If a timestamp column is a key but not marked `TIMESERIES`, Feature Store applies no point-in-time logic and matches only rows with exactly equal times.
W: Declaring the timestamp as a `TIMESERIES` key column makes the table a time series feature table, so training and scoring use an as-of join that returns the latest value at or before each label's timestamp.
X: A=Key on customer only: with one row per customer the table keeps just one set of values, and a plain timestamp column is ordinary data that the join never uses for point-in-time matching.
C=Timestamp key without the keyword: the column is part of the key, but without `TIMESERIES` the lookup matches only rows with an exactly equal timestamp, so most labels find no values instead of the latest earlier ones.
D=Partition by timestamp: partitioning only organizes files for faster reads. It does not change the key, and the key still holds one row per customer, so history is not queryable as of a time.
T: Mark the time column of the key `TIMESERIES` to get point-in-time (as-of) lookups; a plain timestamp key only matches exact times.
V: Unity Catalog, Feature Store

@ DBX-MLA D1 T1.6 applied use-case
S: A Unity Catalog Delta table `main.crm.customer_attrs` has one row per `customer_id` and no constraints. A data scientist (not the table owner) is told the table must become a feature table. The owner agrees to help. Which sequence makes it usable as a feature table?
A: Add `PRIMARY KEY (customer_id)` straight away and rely on Unity Catalog to skip the rows whose key value is NULL during lookups
B: Convert the data to Parquet files, then call `create_table` with the files as the source so that the client writes a new managed table
C: The owner sets `customer_id` to `NOT NULL`, then adds a primary key constraint on `customer_id`, and the table appears as a feature table
D: Call `create_training_set` once with the table; the client adds a primary key constraint on its first use and marks the table
K: C
G: ## Turning an existing table into a feature table
Any Delta table in Unity Catalog with a primary key constraint can be a feature table, so you do not have to copy data into a special structure. If the table has no key yet, you add one with DDL:
1. For every key column run `ALTER TABLE <table> ALTER COLUMN <col> SET NOT NULL`. Key columns cannot be nullable.
2. Run `ALTER TABLE <table> ADD CONSTRAINT <name> PRIMARY KEY (<col>, ...)`. By convention the name is the table name with a `_pk` suffix.
Only the **table owner** can declare a primary key constraint. After that the table shows up in the Features UI and can be used in `FeatureLookup`.
The error `Feature tables must have a primary key` is what you see when you reference a table that still lacks the constraint.
W: Setting the key column to `NOT NULL` first and then adding the primary key constraint (as the owner) is the documented procedure; afterwards the existing Delta table is a feature table with no data copy.
X: A=Skip the NOT NULL step: a key column must be non-nullable before the constraint can be added, and Unity Catalog does not ignore NULL keys; the statement is rejected.
B=Convert to Parquet: feature tables are Delta tables, and copying data into new files is not needed; adding the constraint to the existing table is enough.
D=Constraint added by `create_training_set`: reading APIs never alter table definitions. The call fails with `Feature tables must have a primary key` until someone with ownership adds the constraint.
T: Existing Delta table to feature table: key columns NOT NULL, then ADD CONSTRAINT PRIMARY KEY, done by the owner.

T: Feature table = Delta table with a primary key, created by SQL DDL or `FeatureEngineeringClient.create_table`.

@ DBX-MLA D1 T1.6 applied use-case
S: A churn team must retrain monthly on what each customer's features looked like on every past day, for audit. The feature job runs daily, and overwriting yesterday's rows with today's values would lose that history. How should the feature table be designed?
A: Use a composite primary key of `date` and `customer_id`, with liquid clustering (or partitioning on `date`) for window reads
B: Keep `customer_id` as the only key, and write each day's DataFrame in append mode so that daily duplicates per customer pile up
C: Create one new feature table per day with the date in its name, and list all of them in every `FeatureLookup`
D: Keep `customer_id` as the only key and rely on Delta time travel to read old versions at training time
K: A
G: ## Storing past values of daily features
A feature table has one row per primary key value. If the key is only `customer_id`, a daily job that merges new values replaces the old row, and the table shows only the latest state. To keep history, put the date in a **composite primary key**, for example `PRIMARY KEY (date, customer_id)`. Each day then adds one row per customer.
For efficient reads of a window, Databricks recommends liquid clustering on the table; without it, partition by the date column. A training job filters `date` to the period of interest.
If lookups must also return the latest value as of the label time, declare the time column with `TIMESERIES` so `create_training_set` can do a point-in-time join.
W: A composite key with the date keeps one row per customer per day, so history is retained, and clustering or partitioning on the date makes window reads cheap.
X: B=Append with a single-column key: a primary key is not enforced as a duplicate check, but lookups require exactly one row per key; duplicate customers make joins ambiguous and break the feature table contract.
C=A table per day: it explodes the number of tables, and each `FeatureLookup` names one table; a model cannot reference an open-ended list of daily tables.
D=Time travel: Delta versions are kept only for the retention period and are not addressable by `FeatureLookup`, so they are not a dependable history for audits.
T: To keep history in a feature table, put the date (or a `TIMESERIES` timestamp) into a composite primary key instead of overwriting rows.
V: Unity Catalog, Delta Lake

S: Several teams need a subset of an existing feature table (only customers aged 18 to 35) for offline training, without copying data. The table has primary key `customer_id`. What does Unity Catalog allow?
A: Create a `SELECT ... WHERE` view over that single table that keeps the key columns, and use it as a feature table for offline training

A **simple SELECT view** can be used as a feature table. @ DBX-MLA D1 T1.7 applied use-case
S: A nightly job recomputes features for only the customers that were active that day, about 5% of the table. Rows of all other customers must stay as they are. Which write call fits?
A: `fe.write_table(name=..., df=active_df, mode="overwrite")` so the table always reflects exactly the latest computation run
B: `fe.write_table(name=..., df=active_df, mode="append")` so that new rows are added next to the old ones
C: `fe.write_table(name=..., df=active_df, mode="merge")` so that rows are matched on the primary key and other keys stay unchanged
D: `fe.read_table(...)` of the old rows, a union with the new rows, and a drop and recreate of the table
K: C
G: ## Writing to a feature table
A feature table is a Delta table, and `FeatureEngineeringClient.write_table(name, df, mode)` writes a DataFrame into it. Two modes matter:
- `mode="merge"` upserts by primary key: rows whose key exists are updated, new keys are inserted, and rows whose key is missing from the DataFrame are **left unchanged**. This is the mode Databricks shows for scheduled feature updates.
- `mode="overwrite"` replaces the whole table content with the DataFrame.
Because lookups assume one row per key, appending rows for existing keys is not a way to update.
W: Merge matches on the primary key, updates the 5% of active customers and keeps everyone else untouched, which is exactly the nightly requirement.
X: A=Overwrite: the table would contain only the 5% of customers in the DataFrame, so 95% of the features would disappear for training and scoring.
B=Append: existing customers would get a second row with the same key, which breaks the one-row-per-key assumption of lookups.
D=Read, union, drop and recreate: it rewrites the entire table nightly, loses table history and metadata, and breaks consumers while the table does not exist. `merge` does the update in place.
T: Use `write_table(..., mode="merge")` to update some rows by key; `overwrite` replaces everything.
V: Feature Store, Delta Lake

@ DBX-MLA D1 T1.7 applied use-case
S: Which TWO changes to an existing feature table can break downstream training and serving pipelines, according to Databricks guidance? (Select TWO)
A: Merging fresh values for existing customers with `write_table` in merge mode
B: Changing the data type of an existing feature column
C: Changing the primary key of the table
D: Adding a new feature column with `write_table`
E: Scheduling a job to refresh the table every day

G: ## What not to change
Models trained with feature lookups keep references to the feature table, the lookup keys and the feature names and types. Databricks says three kinds of metadata must not be updated on a feature table: the **primary key**, the **partition key**, and the **name or data type of an existing feature**. Changing them breaks downstream pipelines that use the table for training and serving.
Safe changes are changes of content or additions: merging new values by key, adding new feature columns, and scheduling regular refreshes (Databricks recommends a scheduled job using `mode="merge"`).
If a feature really must change, create a new feature (or table) under a new name and move consumers over.
W: B=Data type change: models and endpoints expect the type that existed when they were trained, so changing it breaks the lookup contract.
C=Primary key change: lookups join on the key, so altering it makes saved lookups and published online tables no longer match the table.
X: A=Merge of fresh values: this is the normal way to refresh content and keeps the schema as is.
D=New feature column: adding columns is documented as safe; existing models ignore columns they did not request.
E=Scheduled refresh: Databricks recommends regular jobs so that feature values stay up to date.
T: Update values and add columns freely; never change the primary key, partition key, or an existing feature's name or type.

G: ## Point-in-time lookups
For a time series feature table, the `FeatureLookup` gets two kinds of keys:
- `lookup_key`: the DataFrame columns that match the non-timestamp primary keys (here `account_id`).
- `timestamp_lookup_key`: the DataFrame column holding the observation time of each label row (here `txn_ts`).
`create_training_set` then performs an as-of join: for each row it picks the latest feature value whose timestamp is at or before the lookup timestamp, so no future information leaks into training. A timestamp column must not be given in `lookup_key`.
A `DATE` or `TIMESTAMP` primary key column that is not declared as a timeseries key makes `create_training_set` return an error; either declare the column with `timeseries_columns` or change it to `STRING` if it is a plain key.
W: `lookup_key` covers the account and `timestamp_lookup_key` names the transaction time column, so each row gets the latest feature values from at or before its own transaction time.
X: A=Timestamp as a normal lookup key: timestamp columns are not used as `lookup_key`, and an exact match on time would find almost no rows.
B=Filter to yesterday: a single cut-off date gives every transaction the same values and discards the history, instead of a per-row as-of value.
C=Table column as lookup timestamp: `timestamp_lookup_key` names a column of the training DataFrame (`txn_ts`), not the table's `ts`, and excluding `txn_ts` would not make the join as-of.
T: Time series tables: `lookup_key` for the entity, `timestamp_lookup_key` for the DataFrame's event-time column.
V: Feature Store

@ DBX-MLA D1 T1.8 applied use-case
S: Some training rows refer to new customers that have no row yet in `customer_features`. The team wants the model to use an age of 18 and tier `"bronze"` for them instead of nulls. What do they set?
A: `default_values={"age": 18, "membership_tier": "bronze"}` in the `FeatureLookup`
B: A `fillna` call on the DataFrame after `load_df`, which they repeat in the scoring notebook
C: `exclude_columns=["age", "membership_tier"]` so those features are skipped for the missing customers
D: `label=None` in `create_training_set` so the training set tolerates rows without features
K: A
G: ## Left joins and missing keys
`create_training_set` performs a **left join** from the training DataFrame to the feature tables. A row whose key is absent in the feature table is kept, with nulls in the feature columns. To control this, the `FeatureLookup` has a `default_values` parameter: a dictionary from feature name to the value to use when the feature store has no value for an ID. If the feature columns are renamed with `rename_outputs`, the dictionary must use the renamed names.
Because the defaults are part of the lookup stored with the model, they are also applied when the model looks up features at inference. A `fillna` after `load_df` would not be: changes after `load_df` are not part of the model's feature metadata.
W: `default_values` on the `FeatureLookup` fills in the stated values where no feature row exists and is stored with the model's lookup definition.
X: B=`fillna` after `load_df`: modifications to that DataFrame are not applied at inference through the lookup, so training and scoring would disagree for new customers.
C=`exclude_columns`: it removes columns from the output DataFrame, such as the join keys, rather than filling the missing values.
D=`label=None`: it declares an unsupervised training set (no label column) and has no effect on missing feature rows.
T: Use `default_values` in the `FeatureLookup` to fill features for keys the feature table does not have.

@ DBX-MLA D1 T1.10 applied definition
S: Which statement correctly contrasts the offline and the online feature store in Databricks?
A: The offline store holds the Delta feature tables for discovery, training and batch scoring; the Lakebase-based online store serves real-time apps
B: The offline store keeps the full history for batch scoring on cheap object storage, and the online store is a read-only cache that keeps its own schema with different key columns
C: The offline store is the place where models are served from, and the online store holds only the model artifacts and their versions
D: The offline store is for notebooks only; the online store is any Delta table that has a primary key, so both can be written by streaming jobs
K: A
G: ## Offline versus online
Feature tables in Unity Catalog are Delta tables: this is the **offline store**. It is used for feature discovery, model training and batch inference, where throughput matters more than latency.
The **online feature store** is a low-latency, high-scale store for real-time applications and for automatic feature lookup in model serving endpoints. It is powered by Databricks Lakebase and you populate it by publishing offline tables (`publish_table`). Lineage and governance stay tied to the source table, and Databricks keeps the online table in sync according to the publish mode.
Feature tables and Feature Views can both publish to the Online Feature Store; feature tables can also use a third-party online store. The legacy Workspace Feature Store (the older name in the exam guide) is not the current path.
W: The offline tables are the Delta tables for discovery, training and batch scoring; the Lakebase-powered online store gives the millisecond lookups real-time applications need.
X: B=Cache with its own schema: the online table mirrors the published offline table and the entity key; it is populated from the offline table and is not a separate dataset.
C=Serving and model artifacts: the offline store is not where models are served; models live in Unity Catalog and serve from endpoints, while the online store holds feature values.
D=Notebook-only offline store: the offline store is the main source for training and batch jobs, and an ordinary keyed Delta table is a feature table, not an online store.
T: Offline = Delta tables for training and batch; online = low-latency Lakebase-backed store for real-time lookups, filled by publishing.

S: A time series feature table `ml.shop.user_features` has key `(user_id, ts TIMESERIES)` with many rows per user. A real-time recommender endpoint should get each user's most recent values.
