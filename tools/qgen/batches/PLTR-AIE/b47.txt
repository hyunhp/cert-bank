# PLTR-AIE batch 47: Domain 6 round 6 (Automation, Orchestration, and Integration), 8 questions

@ PLTR-AIE D6 T6.1 applied use-case
S: A workflow must send a weekly digest to each account manager summarizing AI-flagged risks on their accounts, generated from objects updated during the week. Which automation design fits?
A: An object-update trigger that sends a digest email to the responsible manager every time any one of their accounts changes during the week
B: A weekly scheduled automation that gathers each manager's flagged accounts, runs the summary once, and sends one digest, with send markers
C: A manual process in which each account manager remembers to ask an agent for a summary of their accounts on Friday afternoon
D: A daily scheduled automation that sends each manager a partial digest every morning, adding up to seven messages per week
K: B
G: ## Periodic aggregate automations
The exam guide asks for triggers and execution modes matched to the workload. A weekly digest is a scheduled aggregate per recipient.
## Design
- Trigger: weekly schedule.
- Batch: group flagged accounts by manager; one summary call each; one email each.
- Idempotency: a sent-marker per manager per week.
Example: 40 managers receive one digest each Monday morning; a re-run after a failure sends only to those not yet marked.
W: Weekly batch per manager with idempotent sending: the right cadence, one message each, safe to re-run.
X: A=Per update: dozens of emails a week per manager; the opposite of a digest.
C=Manual: depends on forty people remembering every Friday; some will not, and the result is not a consistent digest.
D=Daily partials: seven messages a week per manager instead of the single weekly digest that was asked for.
T: Build periodic digests as scheduled per-recipient batches with send markers.
V: Automate, AIP Logic

@ PLTR-AIE D6 T6.2 applied troubleshooting
S: A function-backed Action that applies an AI-generated field occasionally times out because the AI call takes too long, leaving the user's click apparently ignored. What is the right integration change?
A: Increase the Action's timeout setting to ten minutes so that the AI call always finishes before the platform gives up on it
B: Separate request from execution: the Action records a request and returns; an automation runs the AI call and writes result and status
C: Ask users in a help note to click the button again if nothing appears after a while, since the second attempt usually succeeds
D: Remove the AI call from the Action entirely and have users type the field value by hand, since the AI step is too slow to be reliable
K: B
G: ## Long work behind Actions
The exam guide recommends asynchronous execution for long work with visible status. Synchronous Actions must return quickly.
## Design
- Action: write `request = pending`, return.
- Automation on the request: run the AI function, write the field, set `complete` (or `failed` with reason).
- Interface: status indicator; result appears when ready.
Example: the click confirms instantly; the generated field appears 40 seconds later with a "completed" badge.
W: Request/response via Action and automation: the click never times out and the result arrives reliably with status.
X: A=Ten-minute timeout: the user still waits with a frozen interface, and long Actions are fragile.
C=Click again: repeated clicks create duplicate requests and writes, and users are left guessing whether anything happened.
D=Remove AI: the generated field is the feature users want; removing it solves the timeout by removing the value.
T: Keep Actions fast; run long AI work asynchronously with status on the object.
V: Actions, Automate, Workshop

@ PLTR-AIE D6 T6.3 applied use-case
S: An automation processes objects from several sources, and one source began sending malformed objects that cause the AI step to fail. What design prevents one source from blocking the others?
A: Stopping the whole automation until the source team has fixed their system, so that no malformed object is ever processed
B: Per-object fault isolation with failures recorded, per-source quarantine for malformed objects, and per-source failure alerts
C: Dropping all objects from that source silently in the automation so that the failures disappear from the execution history
D: Retrying each malformed object indefinitely until it succeeds, since the source might fix the data at some point
K: B
G: ## Isolation in multi-source automations
The exam guide asks for workflows that stay safe under partial failure. One bad source should degrade only its own slice.
## Design
- Each object processed independently; failures recorded.
- Quarantine: malformed objects set aside with reason; the source team alerted.
- Metrics per source so the problem is visible.
Example: 2% of objects (one source) are quarantined; the other sources' objects process normally.
W: Per-object isolation with source-level quarantine and alerts: the failing source cannot block the rest.
X: A=Stop everything: objects from the healthy sources sit unprocessed for as long as one source misbehaves.
C=Silent drop: that source's valid objects are lost too, and nobody is told that anything is being discarded.
D=Infinite retries: a malformed object fails the same way every time; the retries burn compute and the backlog grows.
T: Isolate failures per object and per source in automations; quarantine and alert rather than block.
V: Automate

@ PLTR-AIE D6 T6.1 applied comparison
S: Which trigger configuration correctly implements "run the AI check when a Document's status changes from draft to submitted, but not on any other transition"?
A: A trigger on any change of the status property with no condition, relying on the AI function to ignore irrelevant transitions
B: A trigger on the status property with a condition that the previous value was draft and the new value is submitted, scoped per object
C: A trigger on object creation, since every document is created before it is submitted and the check can run at that point
D: A daily scheduled automation that runs the AI check over every document in the system regardless of status
K: B
G: ## Transition-specific triggers
The exam guide asks for precise triggers. A transition condition names both the previous and the new value.
## Configuration
- Property-change trigger on `status`.
- Condition: old = draft, new = submitted.
- Per-object scope; idempotent effect.
Example: a document moving to submitted runs the check once; a later move to approved runs nothing.
W: A transition-conditioned trigger: the condition names both the old and the new value, so the check runs on exactly the draft-to-submitted change and on no other transition, once per object.
X: A=Any status change: the function runs on every transition (approved, archived) and must waste a call to decide it was irrelevant.
C=On creation: documents are created as drafts; the transition happens later.
D=Daily check: a submission waits up to a day, and thousands of unchanged documents are checked needlessly.
T: Implement "on this transition" with property-change triggers conditioned on old and new values.
V: Automate

@ PLTR-AIE D6 T6.3 applied troubleshooting
S: An AI automation that enriches Customer objects was found to have been overwriting a property that another process also writes, causing the two to flip the value back and forth. What is the right resolution?
A: Make the AI automation run more often than the other process so that its value is the one that ends up winning most of the time
B: Define ownership: one writer per property, or split into AI-suggested and confirmed properties, with conditions ignoring the other writer
C: Let both processes continue writing the property and tell users that the value may change from time to time without warning
D: Delete the property from the object type entirely so that neither process can write it and the conflict goes away
K: B
G: ## Write ownership
The exam guide asks for safe modification and clear contracts in orchestration. Two writers on one property is a conflict, not a race to be won.
## Resolution
- Ownership: a single writer per property.
- Separation: `segment_ai_suggested` versus `segment_confirmed`, with a documented relationship.
- Trigger conditions that ignore the other writer's changes; lineage shows writers.
Example: the AI writes the suggested property; a human or rule confirms into the confirmed one; the flip-flop ends.
W: Single ownership or separated properties with conditioned triggers: the conflict is designed away.
X: A=Run more often: two writers fighting faster produce more flip-flops, more writes and more confusion.
C=Let it continue: users see a value that changes depending on which process ran last; the data is unreliable by design.
D=Delete: both processes write it because consumers need it; deleting it removes the data, not the design problem.
T: Give every written property a single owner or split it into distinct properties.
V: Automate, Ontology

@ PLTR-AIE D6 T6.2 applied use-case
S: A Workshop app has a button that calls an AI function and shows the result. Users want the result saved and visible to colleagues, with an audit of who generated it and when. What change is needed?
A: Nothing; the button already shows the result to whoever clicks it, and colleagues can click it themselves to see their own
B: Route the button through a function-backed Action that stores the result on the object with generator, timestamp and version
C: Ask users to copy the generated result into a free-text notes field on the object by hand so that colleagues can read it
D: Have the button email the generated result to a distribution list of colleagues so that everyone receives a copy
K: B
G: ## From display to governed write
The exam guide places writes behind Actions and asks for audit evidence. Display-only results are ephemeral; shared results are object data.
## Change
- Action: calls the function; writes result, `generated_by`, `generated_at`, `function_version`.
- Permissions: who may generate; validation of the result.
- Colleagues see the stored result; audit is built in.
Example: a colleague opens the object and sees the summary generated by a teammate yesterday, with the version noted.
W: A function-backed Action storing the result with provenance: shared, audited and governed.
X: A=Display only: each click produces a new, possibly different result that vanishes; nothing is shared or audited.
C=Manual copy: pasted text drifts from the original, and nothing records who generated it, when or with which version.
D=Email: copies scatter into inboxes; there is no single stored result on the object and no audit trail.
T: Persist AI results that others rely on through Actions that record provenance.
V: Workshop, Actions

@ PLTR-AIE D6 T6.1 applied tradeoff
S: An automation triggers an AI classification on object creation, but objects are often created with incomplete data that is filled in over the next few minutes. Classifications are frequently wrong because they run too early. What should change?
A: Run the classification twice, once at creation and once an hour later, keeping whichever result was produced on more complete data
B: Trigger on the condition that marks the object complete (a status transition or required fields present), with a fallback sweep
C: Ask the model to guess the values of the missing fields from the fields that are present before classifying the object
D: Slow down object creation in the source system so that objects arrive only once all of their fields have been filled in
K: B
G: ## Trigger on readiness, not existence
The exam guide asks for trigger conditions matched to the data's lifecycle. Creation is not readiness.
## Change
- Condition: `status = complete` or required properties non-null.
- Trigger on that transition.
- Fallback: a scheduled sweep for objects stuck incomplete, with a flag.
Example: classifications run a few minutes after creation, on complete data, and accuracy returns to the suite's level.
W: Trigger on completeness with a fallback sweep: the classification runs once, on finished inputs, and objects that never complete are still caught and flagged.
X: A=Twice: double cost and a wrong first result that may be acted on.
C=Guess fields: the model invents inputs and then classifies its own inventions; errors compound.
D=Slow creation: the source's behaviour is not the team's to change; the trigger condition is.
T: Trigger AI steps on data readiness conditions rather than on object creation.
V: Automate

@ PLTR-AIE D6 T6.3 advanced use-case
S: A regulated process requires that every AI-assisted decision in a workflow be reproducible: given the same inputs, the team must be able to show what the workflow did. Which orchestration practices support this?
A: Running the workflow faster so that any decision can be regenerated quickly whenever an auditor asks to see it
B: Versioned functions and prompts, per-run versions and inputs on a linked run record, deterministic steps where possible, trace retention
C: Deleting traces after a week to save storage space, since the final decisions themselves are kept on the objects
D: Letting the model choose which steps to run freely on each execution so that it can adapt to each case as it sees fit
K: B
G: ## Reproducible workflows
The exam guide asks for versioned, observable orchestration and audit evidence. Reproducibility comes from recorded versions and inputs plus deterministic design where feasible.
## Practices
- Versions: functions, prompts, models pinned and recorded per run.
- Run records: inputs, outputs, decisions, timestamps, linked to the object.
- Determinism: low temperature, structured outputs, deterministic rules for decisions.
- Retention: traces kept for the regulatory window.
Example: an auditor replays run R-5512 against version 7 and sees the same decision with the same cited inputs.
W: Versioning, run records, deterministic steps and retention: the workflow's behaviour is recorded and reproducible.
X: A=Faster: speed does not make a non-deterministic, unrecorded run reproducible; regenerating may give a different answer.
C=Delete traces: the record of what the workflow did is exactly what the regulator wants; deleting it after a week destroys the evidence.
D=Free step choice: a workflow whose steps vary at the model's discretion cannot be shown to do the same thing twice.
T: Make AI workflows reproducible with recorded versions, inputs and deterministic design.
V: Automate, AIP Observability
