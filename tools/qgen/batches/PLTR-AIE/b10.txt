# PLTR-AIE batch 10: Domain 1 round 2 (AIP Logic Development), 8 questions

@ PLTR-AIE D1 T1.1 applied use-case
S: An AIP Logic function must look up a customer's open invoices before drafting a reminder email. The invoices live as objects linked to the customer. Which block configuration retrieves them?
A: Inject the customer's name into the prompt and ask the model to recall that customer's open invoices from what it learned during training
B: Add an Ontology query tool over Invoice objects linked to the customer input, and inject the results into the drafting prompt
C: Paste the full invoices dataset into the system prompt so the model can find the relevant rows itself
D: Ask the user to type the invoice numbers into the function's input each time it runs
K: B
G: ## Tools in AIP Logic
A Logic function can call tools: Ontology queries over object types and links, other functions, and Logic functions. The exam guide lists tools among the things to configure. When the data needed is in the Ontology, a query tool is how the function gets it, scoped to the input object.
## Pattern
- Input: a Customer object reference.
- Block: query Invoice objects linked to that customer with status = open.
- Block: single completion with the invoice list injected as a variable.
- Output: the drafted email text (typed string).
Example: customer C-114 has three open invoices; the prompt receives their numbers, amounts and due dates, and the email lists them accurately.
W: Ontology query tool linked to the input: the function reads real, current invoices under the right permissions and feeds them into the prompt.
X: A=Model recall: a model knows nothing about a company's invoices; it would invent them.
C=Whole dataset in prompt: the prompt would be enormous, expensive and still unreliable; retrieval is what tools are for.
D=User types invoice numbers: this defeats the purpose and introduces manual error.
T: Fetch Ontology data inside a Logic function with a query tool scoped to the input, then inject it into the prompt.
V: AIP Logic, Ontology

@ PLTR-AIE D1 T1.1 applied tradeoff
S: A Logic function receives a long contract and must answer a specific question about termination terms. The engineer wonders whether to put the whole contract into the prompt or to add a semantic search tool over contract chunks. Contracts are up to 150 pages. Which is the better default?
A: Always put the whole contract in the prompt, since the model can read it all and nothing is missed
B: Use semantic search over the contract's chunks to retrieve the termination clauses and inject those, keeping the prompt small
C: Summarize the contract first with another completion and answer from the summary
D: Split the contract into 150 single-page completions, ask the same question of every page, and concatenate all the answers into one response
K: B
G: ## Prompt size versus retrieval
The exam guide covers choosing between single completion and tool-using approaches, and RAG principles apply inside Logic too. A 150-page contract is tens of thousands of tokens: expensive, slow, and the relevant clause can be lost in the middle.
## Retrieval inside Logic
- Chunks of the contract are embedded (a pipeline step or a prepared index).
- The function's search tool retrieves the chunks most relevant to "termination".
- The completion answers from those chunks, with citations to the clauses.
Example: three termination-related clauses (12 paragraphs) go into the prompt instead of 150 pages, and the answer cites clause 14.2.
W: Semantic search over chunks: it provides the relevant clauses, keeps the prompt small and makes the answer traceable to specific text.
X: A=Whole contract: cost and latency scale with size, and very long contexts degrade accuracy on specific questions.
C=Summary first: a summary may omit the termination detail the question needs; the original clause text is what matters.
D=Page-by-page: 150 calls per question, with contradictory partial answers to merge; retrieval is designed to avoid this.
T: For long documents, retrieve the relevant chunks into the prompt rather than sending the whole document.
V: AIP Logic, semantic search

@ PLTR-AIE D1 T1.2 applied troubleshooting
S: A Logic function creates a new Task object for every support email it processes. During a test run on last month's emails, it created 4,000 Tasks in the production Ontology that nobody wanted. What practice would have prevented this?
A: Running the test with a smaller model, which creates fewer objects
B: Testing on a few sample inputs with edits disabled or on a branch, and reviewing the proposed edits before enabling writes
C: Deleting the Task object type before testing so that no objects could be created
D: Running the test only once instead of twice, so that the number of Task objects created in production during testing is at least halved
K: B
G: ## Safe testing of edit-producing functions
A Logic function that applies Ontology edits changes production data on every run, including test runs. The exam guide asks you to apply Ontology edits safely and to test on representative objects before enabling live use.
## Practices
- Test with a handful of representative inputs, not a month of history.
- Inspect the proposed edits (what would be created or changed) before enabling the edit for real; with Global Branching, run on an Ontology branch so production is untouched.
- Enable edits only after the output is confirmed, and bound the scope of the first live run.
Example: five sample emails produce five proposed Tasks for review; after approval, the function is enabled on live traffic.
W: Sample inputs, edits disabled or on a branch, review before enabling: the test produces evidence without producing 4,000 unwanted production objects.
X: A=Smaller model: the model's size does not change how many inputs were processed or whether edits were applied.
C=Delete the object type: destroying a production object type to test a function is far worse than the problem.
D=Run once: 4,000 objects came from one run over a month of emails; the volume of inputs and the live edit are the issues.
T: Test edit-producing functions on small samples with edits disabled or on a branch, and review before enabling.
V: AIP Logic, Global Branching

@ PLTR-AIE D1 T1.3 applied troubleshooting
S: A Logic function sometimes returns an empty output. The trace shows that the model's answer was present, but a later block that parses the answer into the typed output failed when the model included extra commentary. What is the right fix?
A: Tell the model in the prompt to never add commentary and rely on that instruction
B: Use structured output so the answer is produced in the typed shape, and make any conversion failure loud with the raw answer attached
C: Increase the maximum output tokens so the commentary and the answer both fit, then change the parser to read only the last line of the model's text
D: Retry the function up to five times until an answer parses
K: B
G: ## Reading the trace to the failing block
The trace shows the failure is in the parsing block, not the model. The exam guide asks you to identify whether a problem is prompt design, block wiring, tool configuration, model behaviour or execution logic: here it is execution logic (a brittle parser) plus output design.
## Fix
- Structured output: the model fills the typed fields directly, so there is nothing fragile to parse.
- Loud failures: if conversion still fails, the function should surface an error with the raw answer, so a consumer never sees a silent empty value.
- Add the failing cases to the evaluation suite.
Example: output type {decision: enum, reason: string}; the model's extra sentence lands in `reason` or is excluded, and empty outputs disappear.
W: Structured output and loud failure: the brittle parse is removed and any residual failure is visible, which fixes the cause rather than the symptom.
X: A=Prompt instruction only: it reduces commentary but does not guarantee it; the parser stays brittle.
C=Parse the last line: a different fragile heuristic; the next variation breaks it.
D=Retry blindly: it burns cost and latency and still returns empty when all five fail.
T: Replace fragile parsing of model text with structured output, and never let a failed conversion return a silent empty result.
V: AIP Logic

@ PLTR-AIE D1 T1.2 applied comparison
S: A requirement is to rank support tickets by urgency using a mix of hard rules (SLA breaches first) and judgement from the ticket text. Which design is appropriate?
A: Let the model do everything, including the SLA calculation, in one prompt
B: Compute the SLA breach flag deterministically, use the model only for urgency from the text, and combine both in deterministic ranking
C: Compute everything in code and drop the text judgement, since rules are more reliable
D: Ask the model at run time to decide for each ticket which parts should be handled as rules and which parts need its judgement
K: B
G: ## Combining deterministic logic and AI
The exam guide's first decision area says to use deterministic logic for explicit rules, AI for bounded interpretation, and to combine them where useful. SLA breach is a rule (timestamp arithmetic); urgency from text is interpretation.
## Design
- Code or conditional: SLA breached? (yes/no, exact).
- Completion: urgency score from text with an enumerated output and a short reason.
- Deterministic ranking: breached first, then by model urgency.
Each part is testable on its own; the rule part never varies.
Example: ticket 88 is breached and gets rank 1 regardless of text; two unbreached tickets are ordered by the model's score.
W: Rules in code, judgement in the model, combined deterministically: each component does what it is good at and the ranking is reproducible where it must be.
X: A=Model does everything: timestamp arithmetic in a model is unreliable; SLA ordering would vary between runs.
C=Rules only: the requirement includes judgement from text, which rules cannot express well.
D=Model decides the split: the split is a design decision, not a run-time guess; it should be fixed and tested.
T: Put rules in deterministic logic and let the model handle bounded interpretation; combine them in code.
V: AIP Logic

@ PLTR-AIE D1 T1.3 applied use-case
S: Before publishing a new version of a widely used Logic function, which check sequence is appropriate?
A: Evaluate the draft against the current version, review traces for a sample of cases, then publish and migrate consumers deliberately
B: Publish immediately and let the consuming teams report any problems they find, since production traffic is the only realistic test of a prompt
C: Ask the model whether the new version is better and publish if it says yes
D: Compare the two prompts side by side by eye and publish if the new one reads better
K: A
G: ## Release discipline for Logic functions
The exam guide asks you to debug traces, tune parameters, publish versions and preserve behaviour for existing consumers. The checks before publishing are the same ones that protect any shared component.
## Sequence
- Evaluate the draft on the fixed suite; compare with the current version (repeated runs if variance is material).
- Inspect traces of a sample, especially cases that changed, to confirm the change is for the right reason.
- Publish the new version; existing consumers stay on their version until migrated.
- Migrate consumers one at a time, with rollback available.
Example: version 6 improves accuracy on multilingual tickets by 8 points with no regression elsewhere; the Workshop app moves first.
W: Evaluate, compare, inspect traces, publish, migrate: it produces evidence of improvement and protects consumers during the change.
X: B=Publish and wait: consumers become the test; failures reach users first.
C=Ask the model: a model's opinion of itself is not an evaluation.
D=Eyeball the prompt: reading cannot predict behaviour on real inputs; the suite can.
T: Evaluate against the suite and inspect traces before publishing; then migrate consumers deliberately.
V: AIP Logic, AIP Evals

@ PLTR-AIE D1 T1.1 applied troubleshooting
S: A Logic function uses a tool-using reasoning block with a "search knowledge base" tool. On some inputs the model calls the tool repeatedly with slightly different queries and never produces an answer before the step limit. What change helps most?
A: Remove the step limit entirely so the model can keep searching with new queries until it finally finds the evidence it is looking for
B: Give the tool a clear description, instruct the model when to stop (answer or report nothing found), and cap iterations with a fallback output
C: Add more tools so the model has alternatives when the search returns nothing
D: Lower the temperature to zero, which prevents the model from repeating tool calls
K: B
G: ## Tool-using reasoning needs boundaries
In tool-using reasoning the model decides when to call tools and when to stop. Without clear stopping criteria, "nothing found" can turn into endless re-querying. The exam guide asks you to configure tools, blocks, conditionals and loops and to choose single completion or tool-using reasoning appropriately.
## Fixes
- Tool description: what it searches and what an empty result means.
- Stop rule: answer when evidence is sufficient; if two searches return nothing relevant, return a "not found" output.
- Iteration cap with a defined fallback, so the function always returns a typed result.
- Evaluation cases with unanswerable inputs to verify the behaviour.
Example: after the change, an unanswerable question ends in two searches and a typed "no answer found" output in a few seconds.
W: Clear tool semantics, stop rule, cap and fallback: this bounds the loop and defines the result for the no-evidence case, which is what was missing.
X: A=No step limit: the loop would run until some external timeout; cost and latency become unbounded.
C=More tools: more options to call do not teach the model when to stop.
D=Temperature zero: determinism can make the model repeat the same unproductive call even more consistently.
T: Give tool-using loops explicit stop rules, iteration caps and a defined fallback output.
V: AIP Logic

@ PLTR-AIE D1 T1.3 applied tradeoff
S: Two engineers debate how to document a Logic function used by other teams. Which practice best preserves behaviour for consumers over time?
A: Keep the prompt in a shared chat thread so the team can discuss changes
B: Record the input/output contract, each published version with what changed, and the evaluation results per version
C: Rely on the prompt text as the documentation, since it describes what the function does
D: Publish every change under the same version number so that all consumers automatically receive the latest behaviour without any migration
K: B
G: ## Contracts and versions
The exam guide asks engineers to publish versions and preserve behaviour for existing consumers. For a shared function that means consumers must know what each version does and how well it does it.
## What to record
- Contract: typed inputs and outputs, and what each field means.
- Version history: what changed (prompt, tools, model) and why.
- Evaluation results per version on the fixed suite.
- Migration notes: what a consumer must check when moving.
Example: version 4's notes say "added `confidence` output; model changed to X; suite 93% vs 91%"; the automation team moves when they are ready to use `confidence`.
W: Documented contract, versions and evaluations: consumers can rely on a specific version and understand the cost of moving, which is how behaviour is preserved for them.
X: A=Chat thread: not discoverable, not tied to versions, and lost over time.
C=Prompt as docs: a prompt is an implementation detail; it does not state the contract or the measured quality.
D=Same version number: this silently changes behaviour for every consumer, the opposite of preserving it.
T: Document a shared Logic function by its contract, version history and evaluation results.
V: AIP Logic
