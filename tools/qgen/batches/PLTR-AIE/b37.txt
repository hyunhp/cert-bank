@ PLTR-AIE D4 T4.1 applied use-case
S: A pipeline must extract the parties and effective date from 100,000 contracts and also flag contracts that contain a non-compete clause. Which output schema is appropriate for the LLM step?
A: A single free-text field in which the model writes everything it found in the contract, to be parsed later by whichever team needs the values
B: A typed struct: parties as a list, effective_date as a date, has_non_compete as a boolean, plus an evidence field quoting the clause, validated
C: Three separate pipelines, one per field, each with its own prompt and model call for every contract
D: A single score from 0 to 100 representing how important the contract is, from which the other fields can be inferred by downstream users
K: B
G: ## One structured extraction
The exam guide asks for structured outputs with validation for batch extraction. Multiple fields from one document are one call with one schema.
## Schema
- `parties: list<string>`, `effective_date: date`, `has_non_compete: boolean`, `non_compete_evidence: string?`.
- Validation: dates parse; parties non-empty; evidence present when the flag is true.
- Raw response and prompt version retained.
Example: 100,000 contracts yield four typed columns; the evidence field lets reviewers verify the flag quickly.
W: A typed multi-field struct with evidence and validation: all required values from one call, checkable and auditable.
X: A=Free text: every consumer must parse; values are inconsistent and unvalidated.
C=Three pipelines: triple cost and possibly inconsistent extractions from the same document.
D=Importance score: a score does not contain parties, a date or a non-compete flag; none of the required values can be inferred from it.
T: Extract several fields per document with one validated structured schema.
V: Pipeline Builder, AIP

@ PLTR-AIE D4 T4.2 applied tradeoff
S: A compliance officer asks whether LLM-processed records can be "re-derived" if the model provider changes. What design makes that possible?
A: Storing nothing beyond the results, since the model provider guarantees continuity of behaviour across versions in its service terms
B: Storing the input reference, prompt version, parameters and raw response per record, so processing can be re-run and compared
C: Keeping a screenshot of the model's configuration page in the platform, taken whenever the configuration is changed by the team
D: Exporting all processed records to a spreadsheet each month and archiving the files so that past results are always available
K: B
G: ## Re-derivability
The exam guide asks for prompts and raw responses retained for auditability and for versioned, observable change. Re-deriving on a new model needs the inputs and the recipe.
## Design
- Per record: input reference, prompt version, parameters, model id, raw response.
- Migration: re-run the prompt on the new model; compare outputs; record the new version.
Example: 2 million records are re-derived over a week on the new model; 3% differ and are reviewed.
W: Inputs, prompt version and parameters stored with each record: the processing recipe is reproducible on another model.
X: A=Nothing extra: providers change models; nothing could be re-derived.
C=Screenshot: a picture of settings is not machine-readable and says nothing about which prompt and parameters produced any particular record.
D=Spreadsheet export: it preserves outputs but not the inputs, prompts or parameters needed to re-derive them on another model.
T: Store the inputs and the prompt recipe per record so AI processing can be re-run on a different model.
V: Pipeline Builder

@ PLTR-AIE D4 T4.3 applied comparison
S: A team is unsure whether a daily "customer churn risk narrative" should be computed south or north of the Ontology. The narrative uses only stored customer features and is read in a dashboard by many managers. Which placement is right and why?
A: North, because narratives are generated text and text outputs should always be generated at read time so they reflect the latest model
B: South, as a scheduled pipeline step: the inputs are stored features, many consumers read the same narrative, and daily freshness suffices
C: North, because dashboards are interactive surfaces and anything shown on an interactive surface belongs in the interactive layer
D: Neither; churn narratives should be written by analysts who know the customers, since generated text cannot be trusted for managers
K: B
G: ## Placement by reuse and inputs
The exam guide's criteria: consumer breadth, freshness, reusability, scale and cost. Stored inputs, many readers and daily cadence point south.
## Design
- Pipeline step: generate the narrative from features with structured guardrails (length, no invented numbers; features injected).
- Stored as a property; dashboards read it.
- Audit: prompt version and raw response retained.
Example: 50,000 narratives generated nightly; every manager sees the same text for a customer.
W: South, as a scheduled enrichment: inputs are stored, consumers are many, freshness is daily.
X: A=Text means north: the data type does not decide the layer; reuse and inputs do.
C=Dashboard interactivity: reading a stored narrative in a dashboard is not interactive generation.
D=Analysts write: 50,000 narratives a day cannot be written by hand.
T: Generated text with stored inputs and many readers is pipeline-layer enrichment.
V: Pipeline Builder, Ontology

@ PLTR-AIE D4 T4.4 applied use-case
S: An AI enrichment transform must run nightly but the provider's API has a 2-hour maintenance window at a varying time. What should the Code Repositories implementation include?
A: A schedule chosen so that the window hopefully does not overlap the run, with the on-call engineer rerunning the job by hand if it does
B: Detection of maintenance errors with backoff and bounded retries, checkpointing so the job resumes after the window, and deadline alerting
C: Cancelling the whole run whenever any error occurs and leaving the dataset unbuilt for that night so nothing partial is published
D: Running the job twice each night at different times so that at least one of the two runs is likely to miss the maintenance window
K: B
G: ## Resilient batch AI jobs
The exam guide lists retries, rate limiting and programmatic control among reasons to use Code Repositories. A known outage window is handled by resilience, not luck.
## Implementation
- Error classification: maintenance responses trigger backoff rather than failure.
- Checkpointing per batch of rows; resume where it stopped.
- Deadline awareness: alert if the remaining work cannot finish by the morning cutoff.
Example: the job pauses for 90 minutes during maintenance, resumes, and finishes 20 minutes before the deadline.
W: Backoff, checkpointing and deadline alerting: the job tolerates the window and signals when it cannot.
X: A=Hope: a varying window will eventually overlap any schedule; relying on luck and manual reruns is not an operational design.
C=Cancel on error: a maintenance window would fail the nightly job every time it overlaps.
D=Run twice: doubles the model cost every night, and both runs can still hit the window on a bad day; it handles nothing.
T: Build batch AI jobs to pause, resume and alert around known provider outages.
V: Code Repositories

@ PLTR-AIE D4 T4.1 applied troubleshooting
S: A translation transform occasionally returns the source text unchanged instead of a translation. The output passes schema validation because it is a non-empty string. What should be added?
A: Nothing; occasional untranslated rows are an acceptable imperfection in a large translated dataset and readers can skip them
B: A content validation: detect the output language or compare with the source, flag rows not in the target language, retry or review
C: A longer prompt that asks the model to try harder and reminds it several times that the output must be in the target language
D: A deterministic rule that marks any output shorter than its input as a failure, since untranslated text tends to be returned verbatim
K: B
G: ## Validation beyond schema
The exam guide pairs structured outputs with deterministic post-processing and quality checks. A schema check cannot see that the content is wrong.
## Fix
- Language detection on the output; must equal the target language.
- Similarity check against the source to catch unchanged text.
- Flagged rows retried with an adjusted prompt or sent to review; rate alerted.
Example: 0.8% of rows are flagged as untranslated and fixed on retry; the dashboard never shows source-language text.
W: Content-level validation (language detection and source comparison): the specific failure is caught and handled.
X: A=Accept: untranslated text in a translated column is wrong data.
C=Try harder: a longer instruction does not guarantee the behaviour and adds no way to detect when it still fails.
D=Length rule: translations are often shorter or longer; length is not the signal.
T: Validate AI outputs for content correctness, not only for shape.
V: Pipeline Builder, Code Repositories

@ PLTR-AIE D4 T4.2 applied use-case
S: Which stored artefact most directly lets an auditor verify that an AI-extracted value was supported by the source document?
A: The model's confidence score alone, stored next to the value, since a high confidence indicates that the value was well supported
B: An evidence field capturing the source span (quote and location) the model used, stored with the value and validated against the document
C: The timestamp of the extraction run, which lets the auditor find the version of the document that was current at that time
D: The name of the engineer who configured the extraction, so that the auditor can ask them how the value was obtained
K: B
G: ## Evidence spans
The exam guide asks for auditability and provenance. A quoted, located span ties the value to the document and can be checked mechanically.
## Design
- Output: value plus evidence span and location.
- Validation: the span must occur in the document text (for scanned documents, a page reference).
- Stored with the row.
Example: "effective_date: 2026-03-04; evidence: 'effective as of March 4, 2026' (page 1)".
W: A validated evidence span: the auditor sees exactly what supported the value and can confirm it in the document.
X: A=Confidence alone: a number says how sure the model was, not where in the document the value came from; it cannot be verified.
C=Timestamp: it tells the auditor when the extraction ran, not what in the document supported the value.
D=Engineer's name: the engineer did not extract the value and cannot recall the evidence for one row among thousands.
T: Capture and validate evidence spans for extracted values so audits can verify support directly.
V: Pipeline Builder

@ PLTR-AIE D4 T4.3 applied tradeoff
S: A pipeline currently generates an AI summary for every ticket, but analysis shows only 15% of summaries are ever read, and reads happen within an hour of ticket creation. What adjustment balances cost and usefulness?
A: Keep generating a summary for every ticket in the nightly batch as now, since the cost is already in the budget and the output is consistent
B: Generate on ticket creation via an automation, or on first open with a short cache, keeping batch generation only for reporting needs
C: Stop generating summaries entirely, since a feature that only 15% of readers use is not worth maintaining at any cost
D: Generate summaries only at weekends when compute is cheaper, so that the cost of the batch is reduced without changing the design
K: B
G: ## Matching generation to consumption
The exam guide's layer criteria include consumer breadth and cost. If most summaries are unread and reads are near creation, event-driven or on-demand generation fits better than full batch.
## Options
- Event-driven at creation: fresh and available at the time of reading, no backlog processing.
- On first open with caching: cost scales with reads.
- Batch retained only where every ticket needs a summary (reporting).
Example: generation volume drops by 70% with no change in what readers experience.
W: Event-driven or on-demand generation aligned with reading patterns: cost follows use.
X: A=Keep all: 85% of the generated summaries are never read; the budget is paying for outputs with no consumer.
C=Stop: the 15% who read summaries find them useful at exactly the moment a ticket is created; removing them loses that value.
D=Weekends: reads happen within an hour of ticket creation on any day; weekend-only generation misses almost every reader.
T: Generate AI outputs when and where they are consumed; use batch only for universal needs.
V: Automate, Pipeline Builder

@ PLTR-AIE D4 T4.1 advanced tradeoff
S: An extraction pipeline's accuracy is 97% on the evaluation set, but the 3% errors concentrate in a document type that represents 40% of production volume. What should the team conclude?
A: 97% on the evaluation set is excellent and above the agreed threshold, so no further action is needed on the pipeline
B: The suite under-represents that type; re-weight it to production mix, measure per type, and improve prompt or routing for the weak type
C: Remove the problematic document type from production processing so that the pipeline's accuracy figure is not dragged down by it
D: Accept that production accuracy is unknowable, since the evaluation set is the only measurement available and it says 97%
K: B
G: ## Evaluation sets must mirror production
The exam guide asks for representative suites and per-case analysis. If the suite's mix differs from production, its average misleads.
## Steps
- Compute accuracy per document type; estimate production accuracy using production shares.
- Rebalance the suite to production proportions.
- Target the weak type: examples, routing to a different model or prompt.
Example: the weak type scores 85%; production-weighted accuracy is 92%, not 97%; a targeted prompt raises it to 95%.
W: Re-weighting the suite and fixing the weak type: the measurement becomes honest and the real problem is addressed.
X: A=97% is fine: the suite's mix differs from production; weighted by real volume the accuracy is far lower than the headline.
C=Remove the type: it is 40% of production volume; excluding it means the pipeline no longer does most of its job.
D=Unknowable: per-type accuracy weighted by production shares gives a sound estimate; it is measurable.
T: Weight evaluation by production mix and fix the segments where errors concentrate.
V: AIP Evals, Pipeline Builder
