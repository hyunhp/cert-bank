@ PLTR-AIE D3 T3.1 applied tradeoff
S: A team is indexing 20,000 engineering procedures for a retrieval-augmented assistant. Each procedure is 10 to 40 pages, and users ask precise questions such as the torque value for a specific bolt. The first attempt embedded each whole document as one vector and retrieval returns the right document but the model misses the detail. What should change?
A: Keep one vector per document but raise the number of documents retrieved, so the model receives several complete procedures and can search within them
B: Split each procedure into smaller chunks that keep section headings and the procedure's metadata, embed the chunks, and retrieve at chunk level
C: Replace the embedding model with a larger one, since a stronger model produces vectors that capture the fine detail inside a long document
D: Add the exact question to the system prompt and ask the model to quote the torque value, since the right document is already being retrieved
K: B
G: ## Chunking
An embedding represents the meaning of a whole text. A 40-page procedure embedded as one vector captures its general topic, not the torque value on page 23. Retrieval then finds the right document, and the model receives tens of pages where the detail is buried.
## Chunk design
The exam guide lists chunking, metadata, embedding and vector-property strategies. Practical rules:
- Chunk by logical units (sections, steps) so a chunk is self-contained; keep the heading so "Bolt M12 torque: 45 Nm" stays attached to its component.
- Attach metadata (procedure id, equipment, revision) to filter and to cite.
- Store chunk vectors (for example as a vector property on a chunk object) and retrieve chunks, then pass only those to the model.
Example: the torque question now retrieves the "Rear axle: fastener torques" chunk and the answer is in a few hundred tokens of context.
W: Section-level chunks with headings and metadata: retrieval becomes precise enough to return the passage that holds the detail, and the model's context is small and relevant.
X: A=More whole documents: this multiplies the irrelevant text; the detail is still buried, now in several documents instead of one.
C=Larger embedding model: a better model still has to compress 40 pages into one vector; the granularity problem is in the chunking, not the model.
D=Prompt instruction: the model cannot quote what it cannot find in a long context reliably; the fix belongs in retrieval, not in a request to look harder.
T: Chunk long documents into self-contained sections with metadata so retrieval returns the passage that holds the answer.

@ PLTR-AIE D3 T3.2 applied tradeoff
S: A retrieval-grounded assistant for product specifications was tuned to retrieve 40 chunks per question to maximize recall. Answer quality is now worse than with 8 chunks: the model mixes details from similar products. What is the best adjustment?
A: Keep 40 chunks but ask the model in the prompt to use only the chunks about the exact product mentioned in the question
B: Reduce the retrieved set and filter by product metadata so only that product's chunks are ranked
C: Increase to 80 chunks so that the correct product's chunks are certain to be included among the retrieved results
D: Switch to a model with a larger context window so that 40 chunks fit comfortably and nothing is truncated
K: B
G: ## Precision, recall and context budget
Recall asks whether the right chunk is in the retrieved set; precision asks how much of the set is relevant. Retrieving 40 chunks raises recall but fills the context with near-duplicates from similar products. The exam guide warns that more context can add noise, conflict, staleness or unauthorized data, and asks you to balance precision, recall, freshness, token limits and latency.
## Better levers than "more"
- Metadata filters: restrict the candidate set to the product named in the question before ranking by similarity.
- Smaller top-k with a relevance threshold.
- Reranking the candidates so the most specific chunks come first.
Example: "maximum load of model X200" filtered to product = X200 returns five chunks, none about the X210, and the mixing disappears.
W: Fewer chunks plus a product metadata filter: precision rises because other products' chunks are excluded before ranking, and recall for the right product stays high within a small, relevant set.
X: A=Prompt-level filtering: the conflicting chunks are still in the context; asking the model to ignore them is unreliable and wastes the token budget.
C=80 chunks: this makes the noise and the product mixing worse and raises latency and cost; the issue is precision, not recall.
D=Bigger context window: fitting more noise is not the goal; the model still has to disambiguate similar products from conflicting chunks.
T: Improve retrieval with filters and ranking, not by retrieving more; more context often means more noise.
V: semantic search, Ontology

@ PLTR-AIE D3 T3.3 advanced troubleshooting
S: Users of a policy assistant report answers that quote a rule that was replaced three months ago. The documents were re-uploaded with the new version, and the pipeline that builds the chunk objects runs nightly. Which diagnosis is most likely, and what should be checked?
A: The model has memorized the old policy from training; switch to a newer model whose training data includes the replacement rule
B: Old chunks were never removed, so stale chunks still match; check the chunk pipeline and version metadata for the superseded document
C: The retrieval returns too few chunks; raise the number retrieved so the new rule's chunk appears alongside the old one in the context
D: Users are asking the question ambiguously; add an instruction telling the model to prefer the most recent policy whenever two rules conflict
K: B
G: ## Freshness in retrieval
A retrieval corpus is only as current as its index. If a document is replaced but the chunk objects and their vectors from the old version remain, both versions are retrievable and the old one may rank first because it matches older phrasing. The exam guide lists freshness among retrieval criteria and asks you to diagnose whether poor answers come from chunking, embeddings, ranking, thresholds, context selection or generation.
## What to check
- Does the chunk pipeline delete or supersede chunks of replaced documents, or only append?
- Do chunks carry a version or effective-date property that retrieval can filter on?
- Is there a transaction or build that shows the new chunks exist and are embedded?
Example: the lineage shows chunks for policy v3 and v4 both present; adding a "current version" filter and removing superseded chunks fixes the answers.
W: Stale chunks still indexed: a replaced document whose old chunks remain is the direct cause of answers citing the old rule; inspecting the chunk pipeline and version metadata confirms and fixes it.
X: A=Model memory: the assistant quotes the rule from retrieved context, not from training; changing models leaves the stale chunks in place.
C=More chunks: both versions would appear and the model would have to guess; the fix is to stop retrieving superseded content.
D=Prompt preference rule: the model cannot reliably tell which chunk is newer without version metadata, and the superseded text should not be in the corpus at all.
T: When answers cite outdated content, check whether superseded chunks are still indexed; freshness is a retrieval problem before it is a prompt problem.
V: Ontology, Pipeline Builder, Data Lineage

@ PLTR-AIE D3 T3.3 applied troubleshooting
S: A retrieval evaluation shows that the correct chunk is in the top five results for 95% of test questions, yet the final answers are wrong for 30% of them. Where should the engineer look next?
A: In the embedding model, since wrong answers after retrieval usually mean the vectors are not capturing the meaning of the questions well enough
B: In the context assembly and generation stages, checking how the retrieved chunks are presented to the model and whether the prompt makes it use them
C: In the chunking strategy, since a 95% hit rate suggests that the chunks are too large and should be split further before re-indexing
D: In the relevance threshold, since lowering it will admit more chunks and give the model more chances to find the correct one
K: B
G: ## Separating retrieval from generation
A RAG workflow has stages: chunking, embedding, ranking, thresholds, context selection and generation. The exam guide asks you to identify which stage to change and how to measure the improvement. Measuring retrieval separately is exactly what this team did: 95% of questions have the right chunk in the top five.
## Reading the two numbers together
High retrieval hit rate with low answer accuracy points downstream:
- Context assembly: is the correct chunk actually included in the prompt, in a readable order, or cut off by a token limit?
- Prompt: does it tell the model to answer from the context and cite it?
- Generation: is the model ignoring the evidence, or is the question type (calculations, comparisons) beyond what the prompt supports?
Example: the trace shows the correct chunk at position five was dropped when the top three were passed to the model; passing all five fixes most failures.
W: Context assembly and generation: retrieval is measured and healthy, so the failure sits between "chunk retrieved" and "answer produced", which the trace of the prompt and the model's output reveals.
X: A=Embedding model: the embeddings already find the right chunk 95% of the time; changing them risks the part that works.
C=Smaller chunks: a high hit rate does not indicate chunks are too large; re-chunking changes a working stage without evidence.
D=Lower threshold: admitting more chunks adds noise to a context that already contains the right one; it does not fix how that chunk is used.
T: Measure retrieval and generation separately; when retrieval is good and answers are bad, fix context assembly and the prompt.

@ PLTR-AIE D3 T3.1 applied use-case
S: A manufacturer wants its maintenance assistant to answer questions about machines by combining free-text manuals with structured data such as each machine's model, location and last service date, which already exist as object properties. How should the retrieval context be designed?
A: Convert all the structured properties into sentences, embed them together with the manual text, and rely on semantic search for everything
B: Use semantic search over the manual chunks for the free-text part, and read the machine's structured properties directly from its object for the factual part
C: Embed only the manuals and ask the model to infer the machine's model, location and service date from the manual text that is retrieved
D: Drop the manuals and answer from the structured properties alone, since object data is exact while manual text is ambiguous and expensive to embed
K: B
G: ## Two kinds of evidence
Not everything should go through a vector search. The exam guide's context-injection strategy covers how evidence reaches the model, and the Ontology already holds exact facts as properties.
- Unstructured: manual text has no fixed schema; semantic search over chunks finds the relevant passage.
- Structured: model, location and last service date are properties of the Machine object; reading them directly is exact, cheap and permission-aware, with no similarity ranking involved.
## Assembling context
The workflow looks up the machine object, injects its properties, retrieves manual chunks for that machine's model (a metadata filter), and passes both. Provenance stays clear: facts come from the object, procedures from the manual.
Example: "When was pump P-17 last serviced and how do I replace its seal?" uses the property for the date and the seal-replacement chunk for the procedure.
W: Semantic search for text, direct property reads for facts: each kind of evidence is fetched by the method that is exact and efficient for it, and the context carries clear provenance.
X: A=Embed everything: turning exact properties into sentences and searching them semantically makes precise facts fuzzy, and a similarity search may return another machine's date.
C=Infer facts from manuals: manuals do not contain a specific machine's service date; the model would guess.
D=Properties only: procedures live in the manuals; without them the assistant cannot explain how to do anything.
T: Retrieve unstructured text with semantic search and read structured facts straight from the object; combine both in the context.
V: Ontology, semantic search

@ PLTR-AIE D3 T3.2 applied tradeoff
S: A legal assistant must answer within three seconds. Its retrieval currently embeds the query, searches 2 million chunks, reranks the top 200 with a second model and passes 30 chunks to the generator. Latency is seven seconds, dominated by the rerank and the long prompt. Which change gives the best trade-off?
A: Remove the reranker and pass the top 30 by vector similarity, accepting some precision loss, and measure answer quality on the evaluation set
B: Rerank the top 50 instead of 200 and pass the top 10 chunks, then measure answer quality and latency on the evaluation set before and after
C: Search only the 100,000 most recent chunks to make the vector search faster, since older legal documents are rarely needed for answers
D: Cache the final answer for every question so that repeated questions return instantly, which brings the average latency under three seconds
K: B
G: ## Trading precision, recall and latency
The exam guide asks you to balance precision, recall, freshness, token limits and latency. Two costs stand out here: reranking 200 candidates with a second model, and a 30-chunk prompt. Both scale linearly with their counts.
## A measured reduction
- Reranking fewer candidates (50) keeps most of the benefit, because the right chunk is usually well inside the top 50 by similarity.
- Passing fewer chunks (10) shortens the prompt and often improves answers by removing noise.
- The evaluation set tells you whether recall dropped; if it did, adjust the numbers rather than guess.
Example: rerank 50, pass 10 brings latency to about 2.5 seconds with no measurable loss on the evaluation set; the team keeps the reranker, which protects precision.
W: Smaller rerank set and fewer passed chunks, verified by evaluation: both bottlenecks shrink and the reranker's precision benefit is kept; the measurement shows whether recall survived.
X: A=Drop the reranker: this removes the stage that most improves precision in legal search and still passes a 30-chunk prompt; quality loss is likely and the prompt stays slow.
C=Search only recent chunks: legal answers often depend on older documents; silently excluding them trades correctness for speed.
D=Answer cache: legal questions rarely repeat exactly, so most requests miss the cache and the seven-second path remains for them; caching also risks stale answers.
T: Reduce rerank candidates and passed chunks in measured steps rather than removing stages or restricting the corpus.
V: semantic search, AIP Evals

@ PLTR-AIE D3 T3.1 applied troubleshooting
S: After adding 5,000 new technical bulletins to a retrieval corpus, questions about older manuals started returning bulletin chunks instead of manual chunks, even when the manual is clearly more relevant. Each bulletin was chunked at 100 tokens while manuals were chunked at 800 tokens. What is the likely cause and the fix?
A: The bulletins are more recent, so the search prefers them; add a date penalty to the ranking so that older manual chunks regain priority
B: Inconsistent chunk sizes skew similarity, since short chunks match queries more tightly; re-chunk to one consistent strategy and re-evaluate
C: The corpus is now too large for a single vector index; split bulletins and manuals into two indexes and query only one of them per question
D: The embedding model is biased towards short text; switch to an embedding model that is trained on long documents and re-embed only the manuals
K: B
G: ## Chunk size and similarity
A short chunk about one topic produces a vector very close to a short query on that topic. A long chunk averages many topics, so its vector sits further from any single query. Mixing 100-token and 800-token chunks therefore biases ranking towards the short ones, regardless of which document is actually best.
## Fixing it
The exam guide lists chunking strategy as the first thing to design and to suspect when retrieval misbehaves.
- Choose one chunking strategy (size, overlap, by section) and apply it to the whole corpus, or make sizes comparable.
- Re-embed after re-chunking, then run the retrieval evaluation set to confirm manual questions retrieve manual chunks again.
- Use metadata (document type) in filters if some question types should prefer one source.
Example: re-chunking manuals to around 150-200 tokens by step restores the expected ranking without touching the model.
W: Inconsistent chunk sizes: the symptom appeared exactly when a very differently chunked set was added, and short chunks win on similarity; a consistent strategy plus re-evaluation fixes it.
X: A=Date penalty: recency is not what the vector search ranks on; a date penalty would be a workaround that also harms genuinely recent, relevant bulletins.
C=Two indexes: splitting the corpus forces a routing decision per question and still leaves the size skew inside each index.
D=Long-document embedding model: the bias comes from chunk length, not the model; re-embedding only one part of the corpus with a different model breaks comparability entirely.
T: Keep chunking consistent across a corpus; mixed chunk sizes distort similarity ranking.
V: semantic search

@ PLTR-AIE D3 T3.3 advanced troubleshooting
S: A grounded assistant answers correctly but users complain that it cites no source. Audit requires that every answer show which document chunk supported it. What should be changed?
A: Ask the model in the prompt to mention the document name it remembers using, since it has seen the chunks and can name them
B: Pass each chunk with its identifier and require the structured output to list the chunk identifiers that support the answer
C: Append the full list of all retrieved chunk titles under every answer, so that any of them could be the source the user needs
D: Store the final answer in the Ontology with a link to the question, which gives auditors a record of what was answered
K: B
G: ## Provenance in context injection
The exam guide asks that retrieved evidence expose its provenance to the workflow and that AI systems provide audit and lineage evidence. Provenance has to be carried, not reconstructed: if the chunks go into the prompt as anonymous text, nothing downstream can say which one mattered.
## Design
- Inject each chunk with a stable identifier (chunk object id, document, section, version).
- Make the output typed: answer text plus a list of supporting chunk ids.
- Validate that the cited ids are among the retrieved ones, so the model cannot invent a citation.
- Show the citations to the user and store them with the answer for audit.
Example: "Replace the seal every 2,000 hours [chunk 8812: Pump P-series manual, section 4.3, rev 7]".
W: Identified chunks and structured citations: the supporting evidence is named by the workflow at the point where it is known, validated against what was retrieved, and recorded for audit.
X: A=Model recall of names: without identifiers in the context the model would guess document names; invented citations are worse than none.
C=List everything retrieved: this does not say which chunk supported the answer and buries the real source among irrelevant ones.
D=Store the answer only: a record of answers without their sources does not meet the requirement to show what supported each one.
T: Carry chunk identifiers through the context and return them as structured citations; provenance must be tracked, not remembered.
V: AIP Logic, Ontology
