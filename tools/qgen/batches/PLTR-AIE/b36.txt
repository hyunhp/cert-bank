# PLTR-AIE batch 36: Domain 3 round 5 (RAG Architecture and Semantic Search), 8 questions

@ PLTR-AIE D3 T3.1 applied use-case
S: A corpus of engineering drawings has very little text; the useful information is in the images and their short captions. How should it be made retrievable?
A: Embedding only the short captions as text and hoping that they describe the drawings well enough to answer every question users ask
B: Generating structured descriptions of each drawing with a vision model in the pipeline, stored with captions and metadata, and embedding them
C: Skipping the drawings entirely from the retrieval corpus, since semantic search only works on documents that consist of text
D: Asking users to search for drawings by file name, since engineers usually know the naming conventions for the drawings they need
K: B
G: ## Making visual content searchable
The exam guide covers VLMs in data processing and chunking and embedding strategies. Images become searchable through text descriptions produced in the pipeline.
## Design
- Vision model step: structured description (components, dimensions mentioned, type of drawing) per image.
- Combine with captions and metadata (project, revision).
- Embed the combined text; store on the Drawing object with a vector property.
Example: "pump assembly with dual inlet" retrieves the drawing whose generated description mentions a dual-inlet pump.
W: Generated descriptions embedded alongside captions and metadata: the visual content becomes retrievable by meaning.
X: A=Captions only: too sparse; most questions are about content the caption does not mention.
C=Skip: the content is the point; vision models make it indexable.
D=File names: a name like DWG-4471-rev3 says nothing about what the drawing shows; users cannot find a drawing by its content.
T: Index visual content by generating structured descriptions with a vision model and embedding them.
V: Pipeline Builder, AIP, Ontology vector properties

@ PLTR-AIE D3 T3.2 applied troubleshooting
S: A RAG assistant's answers about recent policy updates are correct, but answers about older, still-valid policies have become worse since the corpus started receiving daily updates. What is likely wrong?
A: Older policies are inherently harder to retrieve than new ones because their language is more dated and matches queries less well
B: Recency boosting or chunk churn crowding out older valid content: check ranking weights, re-indexing effects and duplicates
C: The embedding model has gradually forgotten the older documents as newer ones were added to the index over the past weeks
D: Users have stopped asking about the older policies in the right way now that the newer ones are the main topic of conversation
K: B
G: ## Balancing recency and validity
The exam guide asks you to diagnose retrieval and to balance freshness against other criteria. Freshness is a filter for superseded content, not a ranking boost for everything.
## Checks
- Ranking: a recency factor that pushes valid older chunks down.
- Re-indexing side effects: older chunks re-chunked differently or dropped.
- Duplicates: daily updates adding near-identical chunks that fill the top-k.
Example: removing a recency weight and deduplicating update chunks restores retrieval for older policies with no loss for new ones.
W: Over-weighted recency or churn in the index crowding out valid content: the pattern matches, and the checks confirm the cause.
X: A=Inherently harder: older documents retrieved fine before the updates.
C=Model forgot: embeddings are computed per chunk; the model does not forget.
D=Users changed: the regression is visible on the fixed evaluation set, whose questions did not change; the system did.
T: Use recency to exclude superseded content, not to boost ranking; watch for churn and duplicates from frequent updates.
V: semantic search, AIP Evals

@ PLTR-AIE D3 T3.3 applied use-case
S: A team wants to measure retrieval quality independently of the generation model. Which evaluation design is right?
A: Scoring the final generated answers only, since the quality of retrieval is reflected in whether the answers come out correct
B: A retrieval evaluation set with labelled relevant chunks, measuring hit rate at k, reciprocal rank and precision against the index directly
C: Asking the generation model at the end of each answer whether it found the retrieved context helpful, and counting the yes answers
D: Counting how many chunks are retrieved per question and treating a higher average count as evidence of better retrieval
K: B
G: ## Stage-level evaluation
The exam guide asks you to measure improvement at each stage. Retrieval has its own metrics that do not involve the generator.
## Design
- Labelled set: question → relevant chunk ids.
- Metrics: hit@k, mean reciprocal rank, precision at k.
- Run on index changes (chunking, embeddings, filters, reranking).
Example: a chunking change raises hit@5 from 81% to 93% before any generation test is run.
W: A labelled retrieval set with rank-based metrics evaluated directly on the index: retrieval is measured on its own.
X: A=Answers only: conflates retrieval and generation; a good generator can hide retrieval misses and vice versa.
C=Model's opinion: a model's self-report about helpfulness is subjective and uncalibrated; it is not a retrieval metric.
D=Chunk count: ten irrelevant chunks score the same as ten relevant ones; count without relevance labels measures nothing.
T: Evaluate retrieval with labelled relevant chunks and rank metrics, separate from generation.
V: AIP Evals, semantic search

@ PLTR-AIE D3 T3.1 applied tradeoff
S: A compliance team insists that the assistant only use the official policy wording and never paraphrase it. How should retrieval and generation be configured?
A: Lower the temperature to zero and hope that the paraphrasing stops once the model's output becomes fully deterministic
B: Configure generation to quote retrieved passages verbatim with citations and only connective text, validated by exact span matching
C: Increase the retrieved chunk count substantially so that the model has more of the official wording to choose from when it answers
D: Fine-tune a model on the policy documents so that it memorizes the official wording and reproduces it from memory in its answers
K: B
G: ## Verbatim grounding
Some use cases forbid paraphrase. The exam guide asks for context-injection strategies and evaluation that fits the requirement.
## Configuration
- Instructions: answer by quoting the relevant passage; add only minimal connective text.
- Output: quoted span plus citation; a check that the span is a substring of the retrieved chunk.
- Evaluation: exact-match on quoted spans.
Example: the answer presents the policy clause in quotation marks with its section reference; the validator confirms the quote is exact.
W: Quote-based generation with exact-match validation: the official wording is preserved and verified.
X: A=Temperature: paraphrase is a behaviour to constrain, not a randomness issue.
C=More chunks: the model receives more official text but is still free to paraphrase it; nothing constrains the output.
D=Fine-tuning: outside the role and does not guarantee verbatim output.
T: When wording must be exact, configure quoting with citations and validate spans against the source.
V: AIP Logic, AIP Evals

@ PLTR-AIE D3 T3.2 applied use-case
S: Users of a retrieval assistant work in two divisions whose documents use the same terms with different meanings ("ticket" means a support case in one and a trading order in the other). Answers mix the two. What fixes this?
A: Instructing the model to guess which division the user means from the wording of their question and to answer accordingly
B: Division metadata on chunks and a retrieval filter set from the user's division, with a clarifying question for cross-division users
C: Removing the ambiguous terms from the documents in both divisions and replacing them with unique words that nobody actually uses
D: Merging the two divisions' corpora into a single index without any tagging, so that the model sees all the context at once
K: B
G: ## Context-dependent vocabulary
The exam guide asks for metadata filtering and context-injection strategies. Ambiguity resolved by user context is a filter, not a guess.
## Design
- Chunk metadata: division.
- Filter from the user's division (state or profile); cross-division users get a clarifying question or both sets labelled.
- Evaluation per division.
Example: a trading analyst asking about "ticket status" retrieves only trading documents.
W: Division metadata filtered by user context: the ambiguity is removed at retrieval.
X: A=Model guesses: "ticket status" gives no clue; the model would guess wrong often when the user's division is already known.
C=Remove terms: each division uses its terms correctly; rewriting documents to avoid them is disruptive and still ambiguous in speech.
D=Untagged merge: an untagged shared index is exactly the configuration producing the mixed answers.
T: Resolve vocabulary ambiguity with metadata filters driven by the user's context.
V: semantic search, Ontology

@ PLTR-AIE D3 T3.3 applied troubleshooting
S: After moving to a new embedding model, retrieval quality is better on average but a few document types (tables of parts) got worse. What should be done?
A: Revert to the old embedding model entirely and re-index everything, giving up the average improvement to protect the parts tables
B: Analyze retrieval by document type and fix the degraded type's representation (row-level chunks with headers, exact lookup for identifiers)
C: Ignore the degraded document type since the average retrieval quality across the whole corpus improved after the change
D: Add more retrieved chunks per question to compensate, so that parts-table chunks are more likely to be included somewhere
K: B
G: ## Segmented retrieval diagnosis
The exam guide asks for per-case analysis and stage-specific fixes. A global average can hide a type-specific regression.
## Response
- Break retrieval metrics down by document type.
- For tables: chunk per row with header context, or route identifier queries to exact lookup.
- Re-evaluate per type.
Example: table rows chunked with their column headers recover the parts-table hit rate while the new model keeps its gains elsewhere.
W: Type-specific diagnosis and representation fixes: the global improvement is kept and the regression repaired where it occurs.
X: A=Revert: the new model improved most document types; reverting sacrifices all of that for one type that can be fixed separately.
C=Ignore: the engineers who look up parts tables experience a real regression; an average does not help them.
D=More chunks: the tables rank poorly because of how they are chunked; retrieving more of everything adds noise without fixing that.
T: Analyze retrieval by segment and fix representation for the segments that regress.
V: semantic search, AIP Evals

@ PLTR-AIE D3 T3.1 applied comparison
S: Which chunk design best supports answering "what changed between version 6 and version 7 of the procedure"?
A: Chunks without any version metadata, relying on the model to notice version numbers mentioned somewhere in the chunk text
B: Chunks tagged with document id and version, retrieved for both versions and injected with labels for comparison
C: A single chunk per document containing only the latest version of the procedure, since that is what users normally need
D: A random sample of chunks from across the corpus injected on every question, so that some version is always present
K: B
G: ## Version-aware retrieval
The exam guide asks for metadata and context-injection strategies. Comparing versions requires retrieving both deliberately and labelling them.
## Design
- Metadata: document id, version.
- Workflow: retrieve the relevant section for v6 and for v7; inject with labels.
- Output: a labelled comparison with citations to both.
Example: "In v7, the inspection interval changed from 30 to 14 days (v6 §4.2 vs v7 §4.2)."
W: Version metadata with explicit dual retrieval and labelled injection: the comparison is grounded in both versions.
X: A=No metadata: version numbers rarely appear in every chunk, so the model cannot tell which version a passage belongs to.
C=Latest only: version 6 is not in the index, so there is nothing to compare version 7 against.
D=Random: random chunks are unrelated to the question; this is not retrieval and cannot support a comparison.
T: Support version comparisons with version metadata and explicit retrieval of each version.
V: semantic search, Ontology

@ PLTR-AIE D3 T3.2 advanced tradeoff
S: An organization wants one retrieval index shared by many assistants, but each assistant needs different filters and ranking. What architecture is appropriate?
A: A separate full index per assistant, each built by its own pipeline from a duplicate copy of the corpus
B: One governed index of chunk objects with metadata and permissions, with per-assistant filters, thresholds and rerankers at query time
C: One index with one fixed retrieval configuration applied identically to all assistants, regardless of their purpose
D: No index at all; each assistant reads the raw documents directly from storage whenever it needs to answer a question
K: B
G: ## Shared corpus, per-use retrieval
The exam guide covers metadata, thresholds and ranking as retrieval design. These are query-time choices; the index can be shared.
## Architecture
- Index: chunk objects with metadata (type, division, version, status) and inherited permissions, built once by the pipeline.
- Per assistant: filter predicates, k, thresholds, reranking, embedding of the query with the shared model.
- Evaluation per assistant.
Example: the HR assistant filters to HR documents with a high threshold; the engineering assistant filters to manuals and reranks.
W: One governed index with per-assistant query-time configuration: no duplication, consistent governance, tailored retrieval.
X: A=Index per assistant: duplicated storage and pipelines; drift in freshness and permissions.
C=One fixed configuration: assistants with different needs get the same, mismatched retrieval.
D=No index: without embeddings and chunk objects there is no semantic search; assistants would scan raw documents on every question.
T: Share a governed index and tailor retrieval per assistant at query time.
V: Ontology, semantic search
