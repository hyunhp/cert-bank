# PLTR-AIE batch 28: Domain 3 round 4 (RAG Architecture and Semantic Search), 8 questions

@ PLTR-AIE D3 T3.1 applied use-case
S: A retrieval corpus contains both long narrative reports and short FAQ entries. Users complain that FAQ answers are drowned out by report chunks. Which indexing design helps?
A: Removing the reports from the index so that only the FAQ entries can ever be retrieved for any question
B: Indexing both with a document-type metadata field, preferring FAQ entries for question-shaped queries, and keeping chunk sizes comparable
C: Merging each FAQ entry into the nearest report so that the corpus has a single uniform document type
D: Increasing the number of retrieved chunks so that the FAQ entries are statistically more likely to appear somewhere in the context
K: B
G: ## Heterogeneous corpora
Different document types compete in one vector space. The exam guide asks you to use metadata and consistent chunking in retrieval design.
## Design
- Metadata `doc_type`: faq, report.
- Query handling: question-shaped queries prefer or require faq first, with reports as backup.
- Comparable chunk sizes so neither type dominates by length effects.
- Evaluation per type.
Example: "how do I reset my badge" returns the FAQ entry first; "what happened in the Q3 audit" returns report chunks.
W: Document-type metadata with type-aware ranking and consistent chunking: both types are retrievable where they fit.
X: A=Remove reports: every question whose answer lives in a report becomes unanswerable; the corpus loses most of its content.
C=Merge FAQs into reports: destroys the concise answers that made FAQs useful.
D=More chunks: more report noise in context; the FAQ still ranks low.
T: Tag document types as metadata and rank by query type instead of letting one type drown the other.
V: semantic search, Ontology

@ PLTR-AIE D3 T3.2 applied tradeoff
S: A legal assistant must never cite a document the user is not entitled to see, even in a passing reference. Where in the retrieval pipeline must the permission filter run, and why not later?
A: After generation, scanning the finished answer for the titles of documents the user cannot see and removing any sentences that mention them
B: Before ranking, by executing the search as the user so unauthorized chunks are never candidates and cannot influence the answer
C: At display time, hiding links the user cannot open while leaving the answer text intact
D: Nowhere, since legal documents are internal and all employees are trusted
K: B
G: ## Authorization before ranking
The exam guide asks that retrieval return only authorized evidence. A chunk that enters the context can shape the answer even if its title is later hidden.
## Design
- Semantic search executed with the user's permissions (Ontology enforcement on chunk objects).
- Unauthorized chunks are not candidates, so they cannot be ranked, injected or cited.
- Test: a user without access asks a question whose answer exists only in a restricted document; the correct result is "no information found".
Example: an associate asks about a sealed matter and receives nothing; a partner receives the cited memo.
W: User-scoped retrieval before ranking: unauthorized content never exists in the workflow, which is the only way to guarantee no citation or influence.
X: A=Post-generation scan: the content already influenced the answer; title matching misses paraphrase.
C=Hide links: the answer text still carries the restricted content.
D=All trusted: legal matters are restricted by design even internally.
T: Enforce document permissions at retrieval, under the user's identity, before anything reaches the context.
V: Ontology, semantic search

@ PLTR-AIE D3 T3.3 applied troubleshooting
S: Retrieval quality dropped after the corpus grew from 100,000 to 5 million chunks, although the embedding model and chunking are unchanged. What is the most likely cause and remedy?
A: The embedding model cannot handle large corpora and must be replaced with a bigger one
B: Many more near-neighbours crowd the top results; add metadata filters, reranking over a larger candidate set, and deduplication
C: The index is corrupted and must be rebuilt from an empty state before it works again
D: Users are simply asking harder questions now that the corpus is bigger, and nothing in the retrieval system itself has changed
K: B
G: ## Scale effects in vector search
A larger corpus means more chunks close to any query. The exam guide asks you to diagnose retrieval and to balance precision and recall with filters and ranking.
## Remedies
- Filters: product, date, type, applied before similarity.
- Reranking: re-score the top 100 with a stronger relevance model.
- Deduplication: collapse near-identical chunks (versions, boilerplate).
- Evaluate on the fixed retrieval set before and after.
Example: filtering by product and reranking restores top-5 hit rate from 72% to 93% without touching embeddings.
W: Crowding at scale, remedied by filters, reranking and deduplication: the retrieval stages absorb the growth.
X: A=Model cannot scale: embedding quality is per chunk; corpus size does not degrade the model.
C=Corruption: a working index with a quality drop at scale is a ranking problem, not a corruption.
D=Harder questions: the evaluation set is fixed; the drop is in the system.
T: As corpora grow, add filtering, reranking and deduplication to keep precision.
V: semantic search

@ PLTR-AIE D3 T3.1 applied use-case
S: A workflow must answer questions that require combining facts from several documents (for example, comparing two suppliers' contract terms). Which retrieval approach supports this?
A: A single top-1 retrieval for the whole question, since the single best chunk will contain the comparison if one exists anywhere
B: Multi-query retrieval: decompose into sub-questions per supplier and aspect, retrieve for each, deduplicate, and inject labelled evidence
C: Retrieving the entire contracts of both suppliers into the context regardless of length
D: Asking the user to compare the suppliers themselves after the assistant returns one representative chunk per supplier for them to read
K: B
G: ## Compositional questions
A comparison needs evidence from multiple places; a single similarity search for the whole question returns a blurred middle. The exam guide covers context-injection strategy and evaluation of multi-part questions.
## Approach
- Decompose: supplier A payment terms; supplier B payment terms; termination clauses for each.
- Retrieve per sub-question; deduplicate; label by supplier and aspect.
- Generate with instructions to compare explicitly and cite each side.
Example: the answer presents a side-by-side of payment terms with citations to clause 7 in each contract.
W: Decomposed, labelled multi-retrieval: the model receives the right evidence for each side of the comparison.
X: A=Top-1: a comparison across two contracts almost never lives in one chunk; the single result covers one side at best.
C=Whole contracts: huge context, slow, and the relevant clauses are buried.
D=User compares: the assistant exists to do the comparison; handing the user two chunks is the manual process it was meant to replace.
T: Decompose compositional questions into sub-queries and inject labelled, grouped evidence.
V: AIP Logic, semantic search

@ PLTR-AIE D3 T3.2 applied troubleshooting
S: A retrieval-grounded assistant occasionally returns chunks from a draft version of a document that was never approved. How should drafts be handled?
A: Index drafts and approved versions alike, trusting the model to prefer the approved one when both are retrieved for a question
B: Exclude unapproved drafts from the corpus, or filter on an approval-status metadata field, with the pipeline enforcing the rule
C: Keep drafts but add "DRAFT" to the chunk text so the model notices
D: Delete all drafts from the source system to be safe
K: B
G: ## Content governance for retrieval
The exam guide lists freshness and authorized evidence among retrieval criteria; approval status is part of that governance. A draft can contradict the approved version.
## Design
- Metadata `status` on chunks; retrieval filters `status = approved` by default.
- The chunk pipeline reads status from the source and updates when documents are approved or withdrawn.
- Tests: a question whose only answer is in a draft should return nothing (or an explicit "no approved guidance").
Example: a draft policy proposing a new limit is invisible to the assistant until it is approved.
W: Status-based exclusion enforced by the pipeline: unapproved content cannot be retrieved, by construction.
X: A=Trust the model: it cannot know which is approved and may cite the draft.
C="DRAFT" in text: the draft still ranks and may still be quoted.
D=Delete drafts: drafts are legitimate work in the source; the corpus should filter, not the source.
T: Filter retrieval corpora by approval status in the pipeline; never rely on the model to tell drafts apart.
V: Pipeline Builder, semantic search

@ PLTR-AIE D3 T3.3 applied use-case
S: A team wants an early-warning signal that retrieval quality is degrading in production before users complain. What should they monitor?
A: Nothing automated; wait for user complaints, which are the only reliable signal of quality problems in a system that answers questions
B: Retrieval metrics over time: top-score distributions, no-hit rates, sampled groundedness, and the retrieval evaluation re-run on changes
C: Only the number of queries per day, since lower usage indicates lower quality
D: The size of the index, since a growing index always means degrading quality
K: B
G: ## Monitoring retrieval
The exam guide asks for monitoring of real behaviour and for measuring improvements at each stage. Retrieval has its own observable signals.
## Signals
- Top similarity score distribution shifting down: queries drifting from the corpus.
- Share of "no relevant chunk" responses rising.
- Groundedness on sampled production answers.
- Scheduled re-run of the retrieval evaluation set after corpus or model changes.
Example: the share of queries with no chunk above threshold doubles after a new document family is indexed; the alert prompts a chunking fix.
W: Score distributions, no-hit rates, sampled groundedness and scheduled evaluation: retrieval degradation becomes visible early.
X: A=Complaints: a late and biased signal; most users who get a poor answer simply stop using the assistant without saying anything.
C=Query count: usage changes for many reasons unrelated to quality.
D=Index size: a growing index means more content was added; it says nothing about retrieval quality on its own.
T: Monitor retrieval with score distributions, no-hit rates and sampled groundedness, plus scheduled evaluation.
V: AIP Observability, AIP Evals

@ PLTR-AIE D3 T3.1 applied comparison
S: Which retrieval design choice most directly affects whether citations in answers are verifiable by users?
A: The temperature setting used by the generation model when it writes the final answer, since lower values produce more careful citations
B: Whether each chunk carries a stable identifier and location (title, section, version) injected with it and returned in the answer
C: The number of executors allocated to the pipeline that builds the index
D: The length of the system prompt, since longer prompts produce more citations
K: B
G: ## Verifiability comes from provenance
The exam guide asks that retrieved evidence expose its provenance. A citation is only useful if a user can open the cited place.
## Design
- Chunk metadata: document id, title, section, page or anchor, version.
- Injected with the chunk; required in the structured output.
- The interface links citations to the document location.
Example: "[Policy 14 v7, §3.2]" opens the exact section; "[document]" opens nothing useful.
W: Stable identifiers and locations carried through retrieval into the answer: the basis of verifiable citations.
X: A=Temperature: affects randomness, not whether sources are identifiable.
C=Executors: pipeline performance, unrelated to citation content.
D=Prompt length: does not create provenance that was never captured.
T: Verifiable citations require chunk-level provenance captured at indexing and carried into the answer.
V: Ontology, semantic search

@ PLTR-AIE D3 T3.2 advanced tradeoff
S: A product team wants to inject the user's last 20 conversation turns plus 15 retrieved chunks plus a long system prompt into every request. Latency and cost are now unacceptable. What is the principled way to budget context?
A: Keep everything and ask the provider for a higher rate limit
B: Set a per-request token budget and allocate it: compact prompt, summarized or windowed history, thresholded reranked chunks, validated by evaluation
C: Remove the retrieved chunks entirely and rely on the conversation history and the model's general knowledge for every answer
D: Remove the conversation history entirely and rely on retrieval alone, treating every message as a fresh question
K: B
G: ## Context budgeting
The exam guide asks you to balance token limits, latency and cost with quality. Context is a budget to be allocated, not a bucket to be filled.
## Allocation
- System prompt: compact; move long rules into retrieval or code.
- History: sliding window plus a running summary instead of 20 raw turns.
- Chunks: threshold and rerank; typically 5-8 relevant chunks beat 15.
- Validate: evaluation on multi-turn and retrieval cases before and after.
Example: 14,000 tokens per request become 4,500 with no evaluation loss; latency halves.
W: Explicit per-request budget allocated across prompt, history and chunks, validated by evaluation: cost and latency fall while quality is protected.
X: A=Higher rate limit: does not reduce per-request cost or latency.
C=No chunks: the assistant loses its grounding in the corpus and answers from general knowledge; accuracy collapses.
D=No history: follow-ups like "and for last year?" lose their referent; multi-turn conversations stop working.
T: Treat context as a budget: compact prompt, summarized history, thresholded chunks, validated by evaluation.
V: AIP Agent Studio, AIP Evals
