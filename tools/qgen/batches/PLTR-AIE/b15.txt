# PLTR-AIE batch 15: Domain 6 round 2 (Automation, Orchestration, and Integration), 8 questions

@ PLTR-AIE D6 T6.1 applied comparison
S: An AI workflow should process orders in batches overnight when a daily feed lands, not one by one as they arrive. Which Automate configuration matches this?
A: An object-created trigger that fires per order, since every order must eventually be processed and per-object execution is the default
B: A schedule-based or input-update trigger that runs once when the daily feed has landed and processes the day's orders as a set
C: A property-change trigger on each order's status, which runs the workflow whenever any status changes during the day
D: A manual trigger that an operator presses each morning after checking that the feed arrived
K: B
G: ## Execution modes and trigger types
The exam guide lists triggers, effects and execution modes among Automate configuration. Per-object triggers fit event-driven, real-time needs; batch execution fits periodic processing of a set.
## Matching
- Daily feed lands once: trigger on that event (input update) or on a schedule after the expected landing.
- Process the day's orders together: batch execution mode, one run, one summary.
- Avoid: per-object triggers that produce thousands of runs for a batch requirement.
Example: the feed lands at 02:30; the automation runs once at 02:35, processes 8,000 orders in one job, and posts a summary.
W: Once-per-feed trigger with batch processing: it matches the daily batch requirement and avoids thousands of per-object executions.
X: A=Per-order trigger: thousands of separate runs for a batch requirement, with higher cost and no batch summary.
C=Status-change trigger: it runs at unpredictable times on individual orders, the opposite of a nightly batch.
D=Manual trigger: unreliable and unnecessary when the feed's arrival can trigger the run.
T: Match the trigger and execution mode to the workload: batch triggers for batch work, per-object triggers for event-driven work.
V: Automate

@ PLTR-AIE D6 T6.2 applied use-case
S: An AI function returns a recommended discount for a quote. The business requires that any discount above 15% is applied only after a manager approves. How should the function's output reach the quote object?
A: The function applies the discount directly through an Ontology edit, and a separate report lists discounts above 15% for managers to review afterwards
B: The function returns a recommendation; an Action applies it, and discounts above 15% create an approval task applied only on approval
C: The function is told in its prompt never to recommend more than 15%, which removes the need for approval
D: The function writes the discount to a notes field, and sales staff copy it to the quote manually
K: B
G: ## Separate recommend, prepare and execute
The exam guide's tool-use decision area says to separate recommend, prepare and execute when appropriate, and to add human review for high-consequence actions. The function recommends; the Action executes with rules; approval gates the high-consequence path.
## Flow
- Function output: recommended discount (typed number) and rationale.
- Action: validates the value; if ≤ 15%, applies; if > 15%, creates an approval task with the rationale attached.
- Manager approves in Workshop; the Action completes.
Example: a 22% recommendation becomes an approval task; the manager approves 20%; the quote is updated with an audit trail.
W: Recommendation plus a rule-bearing Action with approval: the business rule is enforced where the write happens, with the AI providing input rather than authority.
X: A=Apply then review: discounts above 15% would already be applied before any manager sees them.
C=Cap in the prompt: it removes legitimate large discounts rather than governing them, and a prompt cannot guarantee the cap.
D=Manual copying: error-prone, unaudited and still without an approval rule.
T: AI recommends; Actions execute under business rules; approval gates the high-consequence path.
V: AIP Logic, Actions, Workshop

@ PLTR-AIE D6 T6.3 applied troubleshooting
S: An automation that sends AI-generated notifications ran twice for the same event after a platform restart, and recipients received duplicate messages. What design change prevents a repeat?
A: Reduce the number of recipients so duplicates affect fewer people
B: Make the send idempotent with a per-event delivery marker, skipping sends when the marker exists
C: Disable the automation during every planned platform maintenance window and re-enable it afterwards by hand once the restart is confirmed
D: Add a delay of ten minutes before every send so that duplicates are spaced out
K: B
G: ## Duplicate execution after interruption
Automations can be re-run after a failure or restart; the exam guide asks for designs that stay safe under duplicate execution and partial failure. A notification is an external side effect that cannot be undone, so it must be guarded.
## Idempotent send
- Before sending, check for a delivery marker keyed on the event (and recipient).
- Send, then write the marker atomically with the outcome.
- A re-run finds the marker and skips.
This same pattern applies to emails, API calls and payments.
Example: event 7781 has a marker after the first run; the post-restart run finds it and sends nothing.
W: Delivery marker and skip: it makes the side effect idempotent, so duplicates cannot occur however many times the run repeats.
X: A=Fewer recipients: duplicates still happen for everyone who remains; this only shrinks the audience of the defect instead of fixing it.
C=Manual disable: restarts are not always planned; human procedures do not make the workflow safe.
D=Delay: spacing the sends apart does not prevent the second send; recipients would still receive the same message twice, ten minutes later.
T: Guard external side effects with per-event markers so re-runs are harmless.
V: Automate

@ PLTR-AIE D6 T6.2 applied use-case
S: A multi-step workflow extracts data with an AI function, validates it, writes an object via an Action, and then calls an external system. The external call sometimes fails after the object is written. What should the design ensure?
A: That the external call happens before the object is written, so a failed call leaves nothing behind
B: That the object records the external call's status, retries resume from that step only, and the call carries an idempotency key
C: That the whole workflow is re-run from the beginning on any failure, including the AI extraction
D: That failures are ignored for now, since the object is already written and the external system can be reconciled against it by a monthly report
K: B
G: ## Partial failure in chained workflows
The exam guide asks you to account for retries, duplicate execution and partial failure. When a late step fails, the earlier steps have already produced effects; the design must resume, not restart.
## Design
- Status on the object: extracted → validated → written → external_pending → external_done.
- A retry picks up objects in `external_pending` and performs only the external call.
- The external call carries an idempotency key so that a repeat after a timeout does not duplicate on the other side.
- Alerts if an object stays pending beyond a threshold.
Example: 40 objects were left pending after an outage; the retry pass completes them with no duplicate records in the external system.
W: Status-tracked resumption with idempotent external calls: the workflow completes correctly after partial failure without repeating work or creating duplicates.
X: A=Reorder steps: the external call may succeed and the object write may then fail, which is the same problem in reverse.
C=Full re-run: it repeats the AI extraction (cost) and risks creating a second object before the external call.
D=Ignore: data diverges between systems for a month; silent inconsistency is the worst outcome.
T: Track step state on the object and resume from the failed step with idempotent external calls.
V: Automate, Actions

@ PLTR-AIE D6 T6.1 applied tradeoff
S: An automation should run an AI function for every new ticket but must not run while a related nightly data migration is in progress, which would give the function inconsistent data. What is the appropriate control?
A: Tell the AI function in its prompt to be careful during migrations
B: Add a condition that checks the migration status before processing and defers tickets until the migration completes
C: Schedule the automation to run only during business hours, on the assumption that data migrations always happen overnight and finish before morning
D: Delete tickets that arrive during the migration and ask users to resubmit
K: B
G: ## Conditions and preconditions
Automate rules can carry conditions; functions can check preconditions. The exam guide asks for workflows that remain safe when dependencies are unavailable. A migration in progress is an unavailable dependency.
## Design
- A migration status object or flag that the migration sets and clears.
- The automation's condition: process only when the flag is clear; otherwise leave the ticket queued.
- When the flag clears, queued tickets are processed.
- Alert if the flag stays set unusually long.
Example: 50 tickets arrive during a two-hour migration; they are processed in order when it ends, with consistent data.
W: A status-based precondition that defers processing: the automation avoids the inconsistent window deterministically and catches up afterwards.
X: A=Prompt caution: the model cannot detect a migration or avoid inconsistent inputs by being "careful".
C=Business hours only: migrations can overrun; a time assumption is not a check, and daytime tickets would be delayed.
D=Delete tickets: destroying user requests to avoid a timing issue is unacceptable.
T: Gate automations on explicit dependency status rather than on time assumptions or prompt instructions.
V: Automate

@ PLTR-AIE D6 T6.3 applied use-case
S: A team must change a live automation so that it also writes a second property. The change is approved. Which rollout minimizes risk?
A: Edit the live automation directly, since adding a property cannot break anything
B: Make the change in a new version or branch, test on representative objects, deploy at low traffic with monitoring and rollback ready
C: Pause the automation for a week while the change is developed, then resume with the new behaviour
D: Deploy the change and immediately reprocess all historical objects in one run so that every object has the new property populated from the start
K: B
G: ## Safe change to live orchestration
The exam guide asks for safe modification of live workflows. Even an "additive" change can break consumers (a property expected to be null, an Action's validation, a downstream automation triggered by the new write).
## Rollout
- Develop on a version or branch; test on representative objects; check downstream consumers of the new property.
- Deploy at a quiet time; watch traces and error rates.
- Rollback ready: previous version available.
- Backfill historical objects separately and deliberately, if needed, as a bounded batch.
Example: the new property write triggers another automation nobody remembered; the branch test reveals it before production.
W: Versioned change, tested, deployed with monitoring and rollback: it handles the hidden risks that "just adding a property" conceals.
X: A=Edit live: untested changes reach every new object immediately, including any side effects on downstream automations.
C=Pause a week: a week of unprocessed objects is a business failure, not a risk reduction.
D=Immediate full reprocess: a large uncontrolled backfill right after a change is the moment of maximum risk.
T: Roll out automation changes through tested versions with monitoring and rollback; backfill separately.
V: Automate, AIP Logic

@ PLTR-AIE D6 T6.2 applied comparison
S: A Workshop user needs to trigger an AI analysis of a selected object and see the result immediately, while an operations process needs the same analysis run automatically for every new object. Which integration serves both without duplicating logic?
A: Two separate implementations of the analysis, one for the Workshop button and one for the automation, so each can be tuned and released independently
B: One published function, called by a function-backed Action from Workshop and as an effect by the Automate rule, sharing one version
C: The Workshop path only, with operations staff clicking the button for every new object
D: The automation path only, with Workshop users waiting for the nightly run to see results
K: B
G: ## Reuse across channels
The exam guide covers chaining Functions, Actions and AI outputs, and Workshop integration. A published function is callable from several places; sharing it keeps behaviour consistent and evaluation meaningful.
## Design
- Function: the analysis with typed inputs and outputs, versioned and evaluated.
- Workshop: a button bound to a function-backed Action that calls the function and stores the result on the object.
- Automate: a rule on object creation whose effect runs the same function (or the same Action).
- One suite, one version, two channels.
Example: an interactive user and the nightly automation both produce the same result for the same object, with the same audit trail.
W: One function behind an Action and an automation effect: both needs are met and the logic, version and evaluation are shared.
X: A=Two implementations: they drift apart; the same object gets different results depending on the channel.
C=Manual clicks: operations cannot scale to every new object by hand.
D=Automation only: the interactive user needs the result now, not tonight.
T: Implement AI logic once as a published function and expose it through Actions for users and effects for automations.
V: AIP Logic, Actions, Automate, Workshop

@ PLTR-AIE D6 T6.3 advanced troubleshooting
S: An automation applies AI-recommended price updates through an Action. One night the AI function began returning prices ten times too high due to a unit confusion, and 300 products were updated before anyone noticed. Which safeguards should have been in place?
A: A larger model, which would not have confused the units
B: Action validation (price band, maximum change), volume limits on the automation, and an anomaly alert, so the bad batch is blocked and surfaced
C: A nightly email listing all price changes for review the next morning
D: Manual approval of every single price change by a pricing manager before it is applied, regardless of the size of the change or the product
K: B
G: ## Validation strictness proportional to consequence
The exam guide asks you to add human review for high-consequence actions and to match validation strictness to consequence, and to design workflows that stay safe when an AI call misbehaves. Price updates are consequential; an unguarded Action turned one model error into 300 bad prices.
## Safeguards
- Action validation: price within a plausible band; change per product limited (for example ±20%); larger changes routed to approval.
- Volume guard: the automation stops after N changes or when the aggregate change is abnormal.
- Anomaly alert: output distribution checked before applying.
- Rollback: the Action's audit trail allows reverting the batch.
Example: the ten-times prices fail the band check; 0 products are updated; an alert fires at 02:05.
W: Action-level validation, volume limits and anomaly alerts: these catch an AI error at the boundary where it would become a business change, regardless of its cause.
X: A=Larger model: it may still confuse units; a model change is not a control.
C=Morning email: the damage is done overnight; review must precede the change for consequential actions.
D=Approve everything: it blocks the routine 95% and buries reviewers; validation plus approval only for outliers is proportional.
T: Protect consequential automated changes with Action validation, volume limits and anomaly alerts, not with better models or later reviews.
V: Actions, Automate
