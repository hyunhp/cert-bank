# PLTR-AIE batch 32: Domain 7 round 4 (Model Selection, Observability, and Performance), 8 questions

@ PLTR-AIE D7 T7.1 applied use-case
S: A team must pick a model for a real-time chat assistant where users expect the first words of a reply within a second. The reference sheet shows a high-capability model with high latency and a mid-capability model with low latency. Which is right and what else should be checked?
A: The high-capability model, since quality always matters more than responsiveness for chat assistants that employees use for their work
B: The low-latency model, verified against the quality threshold on the suite, with streaming enabled and p95 latency monitored
C: The high-capability model with a loading animation that keeps users patient while the model works on the reply
D: Both models run in parallel on every message, with whichever finishes first shown to the user
K: B
G: ## Latency as a requirement
The exam guide includes latency among selection criteria and asks for performance optimized without sacrificing quality beyond requirements. Chat has a responsiveness bar; models that miss it fail the use case.
## Selection
- Filter by latency requirement (time to first token, p95).
- Verify the fast model meets the quality threshold on the evaluation suite.
- Streaming so users see output early; tail latency monitored.
Example: the fast model scores 90% versus 93% for the slow one, above the 85% threshold, and responds in 600 ms.
W: The fast model meeting the quality bar, with streaming and p95 monitoring: the requirement is met and quality is verified.
X: A=Quality always: a reply that arrives too late fails the chat requirement regardless of quality.
C=Animation: a spinner does not shorten the wait users have rejected.
D=Both in parallel: doubles cost on every message and the slow one rarely wins.
T: Treat latency as a hard requirement for interactive use; pick the fastest model that passes the quality threshold.

@ PLTR-AIE D7 T7.3 applied use-case
S: A workflow intermittently produces a wrong answer that cannot be reproduced on demand. Which observability practice makes the next occurrence diagnosable?
A: Asking users to write down exactly what they typed and what they saw whenever it happens again, and to send the notes to the team
B: Capturing full traces for every run with retention, so a reported case can be pulled by request id and replayed
C: Increasing the log level to debug for one day and hoping that the issue recurs during that window so the logs capture it
D: Re-running the evaluation suite repeatedly, since the suite will eventually hit the same input that triggered the wrong answer
K: B
G: ## Always-on tracing
The exam guide lists session and distributed traces among observability evidence. Intermittent failures are diagnosed from the trace of the actual failing run.
## Practice
- Trace every run with a request id surfaced to the user interface.
- Retention of traces for a reasonable window.
- Replay: the trace's inputs and context can be re-run against the function to reproduce.
Example: a user reports request R-7781; the trace shows an unusual retrieved chunk; the chunk becomes an evaluation case.
W: Full traces per run with ids and retention: the next report is diagnosable from what actually happened.
X: A=User notes: incomplete and often wrong; the system should capture it.
C=Debug for a day: the issue may not recur then; coverage is partial.
D=Suite re-runs: the suite does not contain the unknown input.
T: Trace every production run with a surfaced id so intermittent failures can be pulled and replayed.

@ PLTR-AIE D7 T7.4 applied troubleshooting
S: A document workflow's cost per document doubled after the team added "think step by step" reasoning to the prompt. Quality improved by one point on the suite. What is the right decision process?
A: Keep it as it is, since any measurable quality improvement justifies any increase in cost for a document workflow
B: Quantify it: measure tokens and the quality delta with repeated runs, test cheaper alternatives, decide against the threshold
C: Remove it immediately without further measurement, since cost per document is the only metric the business tracks for this workflow
D: Apply the reasoning instruction only on weekends when document volume is low, so the doubled cost affects fewer documents
K: B
G: ## Prompt techniques have costs
The exam guide asks you to optimize prompts and execution structure with quality maintained and costs understood. Reasoning instructions can help but multiply output tokens.
## Process
- Measure: tokens before and after; quality delta with variance.
- Alternatives: concise reasoning, reasoning routed only to low-confidence cases, a different model.
- Decide: is one point worth doubling cost for this workload?
Example: reasoning only on documents flagged as complex keeps most of the gain at 15% extra cost.
W: Quantified trade-off with targeted alternatives: the decision is based on measured value against measured cost.
X: A=Any gain justifies any cost: unbounded spending for marginal improvement.
C=Remove blindly: the gain may be worth it for some cases; measure first.
D=Weekend only: documents processed on a Tuesday deserve the same quality as those on a Saturday; the calendar is not a routing criterion.
T: Evaluate prompt techniques by their quality delta against their cost, and apply them where they pay off.

@ PLTR-AIE D7 T7.2 applied troubleshooting
S: A fallback model is configured for provider outages but has never been exercised. During a real outage it failed because its prompt format differed. What practice prevents this?
A: Removing the fallback configuration entirely, since an untested fallback that fails during an outage is worse than having none
B: Regularly exercising the fallback path (drills or a small share of traffic), keeping its prompts and evaluations current, alerting on drift
C: Writing a detailed document describing how the fallback should work and which prompts it needs, stored with the workflow
D: Choosing a fallback model from the same provider, which guarantees the same prompt format and removes the need for separate testing
K: B
G: ## Fallbacks must be exercised
The exam guide covers multi-provider resilience. A fallback that is never run is a hypothesis, not a safeguard.
## Practice
- Periodic drill: force the fallback path and run the suite.
- Canary traffic: a small percentage routed to the fallback continuously.
- Prompt variants per model kept in step; evaluation results tracked for both.
Example: a monthly drill reveals the fallback's output schema drifted; it is fixed long before the next outage.
W: Exercised and evaluated fallback with drift alerts: it works when needed because it has been working all along.
X: A=Remove: the next outage then takes the workflow down completely; the fix is to maintain the fallback, not to abandon resilience.
C=Document: a description of how it should work does not prove it does; the prompt drift would still be discovered during an outage.
D=Same provider: a provider outage affects all of that provider's models, so the fallback is unavailable exactly when it is needed.
T: Test fallback paths regularly with drills or canary traffic and keep their prompts and evaluations current.

@ PLTR-AIE D7 T7.3 applied use-case
S: An engineer wants to detect that an AI feature's error rate rose from 1% to 6% within an hour of a release, not a day later. What should be configured?
A: A weekly report of error counts generated from the execution history and reviewed by the team lead at the Monday meeting
B: Real-time outcome metrics with alerts on error-rate thresholds and deviation from the pre-release baseline, with release markers
C: A note in the feature's interface asking users to report any errors they encounter by email to the engineering team
D: Doubling the retry count on every model call so that transient errors are absorbed and the visible error rate stays low
K: B
G: ## Release-aware monitoring
The exam guide asks for monitoring of real behaviour and regressions. Fast detection needs streaming metrics and thresholds anchored to the release.
## Configuration
- Error rate, latency and quality proxies computed in near real time.
- Alert on absolute thresholds and on change versus the pre-release baseline.
- Release markers on dashboards so a jump lines up with a deployment.
- Rollback path ready.
Example: the alert fires 20 minutes after release; the team rolls back and the trace shows a prompt variable rename.
W: Real-time metrics with baseline-relative alerts and release markers: regressions are detected within minutes and attributed.
X: A=Weekly report: a regression released on Tuesday runs at 6% errors until the following Monday's meeting.
C=Email reports: few users write in, and those who do write hours later; the signal is slow and unrepresentative.
D=Hide with retries: a real regression is not transient; retries mask it in the metrics while multiplying cost and latency.
T: Monitor AI features in near real time with alerts relative to the pre-release baseline.

@ PLTR-AIE D7 T7.1 applied comparison
S: Which factor most justifies choosing a smaller model for a high-volume classification workload?
A: The smaller model's more recent release date, since newer models are generally assumed to be better than older ones
B: Evaluation showing the smaller model meets the accuracy requirement, plus its cost and latency advantage at this volume
C: The engineer's familiarity with the smaller model from a previous project, which makes it quicker to configure
D: The larger model's higher benchmark scores on public tests that cover unrelated tasks such as coding and mathematics
K: B
G: ## Fit for purpose at volume
The exam guide asks for model selection by capability, latency, cost and task requirements. For high volume, per-call cost multiplies.
## Reasoning
- Requirement first: accuracy threshold on the suite.
- If the smaller model passes, its cost and latency advantage dominates at scale.
- Record the evaluation so the decision is defensible.
Example: 2 million classifications a day at a tenth of the cost with accuracy within the threshold.
W: Evaluated adequacy plus the volume-multiplied cost and latency benefit: the principled justification.
X: A=Release date: a newer model is not necessarily better for this task; only evaluation on the task shows fitness.
C=Familiarity: an engineer's comfort with a model says nothing about its accuracy, cost or latency for the workload.
D=Public benchmarks: scores on coding or math tests do not predict classification accuracy on the team's own data.
T: Choose smaller models when evaluation shows they meet the requirement and volume makes their efficiency valuable.

@ PLTR-AIE D7 T7.4 applied use-case
S: An assistant's retrieval step and model call are both fast, but the end-to-end response is slow because a pre-processing step calls a slow external service for every request. The external data changes hourly. What is the fix?
A: Removing the pre-processing step entirely so that the assistant answers from retrieval and the model alone
B: Caching the external service's result with an hourly refresh into the Ontology so requests read a fresh local copy
C: Calling the external service in parallel with the retrieval step for every request so that the two waits overlap
D: Asking the external service provider to improve their response time, since the slowness originates on their side
K: B
G: ## Decouple slow dependencies
The exam guide lists caching and execution structure among optimizations. Data that changes hourly does not need fetching per request.
## Design
- Scheduled sync or automation refreshes the external data into the Ontology hourly.
- Requests read the local copy; freshness is within an hour by design.
- Monitor sync freshness.
Example: response time drops from 6 seconds to 1.2 seconds; the data is at most 60 minutes old, matching its change rate.
W: Hourly refreshed local copy: the slow call leaves the request path while freshness matches the data's cadence.
X: A=Remove the step: the external data feeds the answer; without it the assistant is incomplete or wrong.
C=Parallel calls: overlapping the wait helps a little, but every request still pays the slow call; the dependency stays in the path.
D=Ask the provider: their performance is outside the team's control; the architecture should not depend on it per request.
T: Move slowly changing external data out of the request path with scheduled refresh.

@ PLTR-AIE D7 T7.3 advanced tradeoff
S: Leadership asks whether an AI feature is "worth its cost". Which combination of observability and evaluation data answers the question properly?
A: Only the monthly cost broken down by model, since that is the number leadership asked about and value is hard to quantify
B: Cost per request and total, alongside outcome metrics (completion, time saved, overturns) and suite quality, trended together
C: The number of users who tried the feature at least once since launch, which shows how much interest there is in it
D: A written statement from the engineering team explaining that the feature is important and should continue to be funded
K: B
G: ## Value versus cost
The exam guide lists cost signals among observability evidence and expects engineers to operate features with measurable outcomes. "Worth it" compares value to cost.
## Data
- Cost: per request, per outcome, total trend.
- Value: completion rates, time saved per task, reduction in manual work, overturn rate, feedback.
- Quality: suite score over the period.
Example: the feature costs 4,000 a month and saves 600 analyst hours; the overturn rate is 3%: a clear case.
W: Cost and value metrics on one timeline: the question is answered with evidence rather than opinion.
X: A=Cost only: cost without the value it buys cannot answer "worth it"; it is half the equation.
C=Trial users: trying something once measures curiosity, not whether it saves time or improves outcomes.
D=Team's statement: an opinion from the people who built it, with no measurement behind it.
T: Judge AI features by cost against measured outcomes and quality, trended together.
