@ PLTR-AIE D5 T5.1 applied use-case
S: A team wants to evaluate an agent that must choose the right tool among four for each request. Which metric design measures this?
A: Overall answer accuracy only, since a correct final answer implies that the right tool must have been chosen somewhere along the way
B: Tool-selection accuracy per test case, comparing the tools called with the expected calls, alongside answer accuracy
C: The total number of tool calls per session, where fewer calls always indicates better tool selection
D: Latency per request, since choosing the wrong tool usually makes the request slower
K: B
G: ## Measuring tool selection
The exam guide lists tool selection among the behaviours to measure, separate from correctness. A correct answer reached through the wrong tool (or an expensive detour) is a hidden defect that will fail on the next similar input.
## Design
- Each case specifies expected tool calls (which tool, sometimes the order, sometimes "none").
- The evaluator compares the trace's calls with the expectation.
- Report tool accuracy and answer accuracy separately; both must pass.
Example: "What is the status of order 118?" expects one call to the order lookup tool; a case that calls the knowledge-base tool first fails tool selection even if the answer is right.
W: Per-case tool-selection accuracy from the trace: it measures the behaviour directly and catches right answers reached the wrong way.
X: A=Answer accuracy only: it cannot see detours, unnecessary calls or lucky answers; the next input exposes them.
C=Fewer calls always better: a request that needs two tools should use two; the count alone is not the measure.
D=Latency: a proxy at best; a wrong but fast tool choice passes.
T: Evaluate tool selection explicitly against expected calls per case, not only the final answer.

@ PLTR-AIE D5 T5.2 applied use-case
S: An evaluation suite for a grounded assistant has 300 answerable questions. A reviewer asks for cases that test what the assistant does when the corpus has no answer. How should these be constructed?
A: Reuse the existing answerable questions but delete their expected answers from the suite, so that any response the assistant gives counts as a failure
B: Write questions whose answers are genuinely absent from the corpus, expecting an explicit "not found", scored for refusal and no invented content
C: Ask questions in a foreign language, since the assistant will not be able to answer them
D: Ask extremely vague questions, since vagueness guarantees an unanswerable case
K: B
G: ## Testing the refusal path
The exam guide asks for cases where the correct behaviour is refusal or stating uncertainty, and lists refusal behaviour as a metric. Unanswerable cases must be truly unanswerable, with the refusal itself defined as the correct outcome.
## Construction
- Verify the corpus does not contain the answer (search it).
- Expected behaviour: "no supporting information found", possibly with a suggested next step.
- Evaluator: checks that the response states this and contains no fabricated specifics.
- Mix near-miss questions (a topic that exists but the specific detail does not) to catch confident guessing.
Example: "What is the maximum reimbursement for home office chairs?" where the policy mentions home office equipment but no amount; the correct answer says the amount is not specified.
W: Genuinely absent answers with refusal as the expected outcome and an evaluator for fabrication: this measures the behaviour that matters when evidence is missing.
X: A=Delete expected answers: the questions are still answerable from the corpus; a correct answer would be scored as a failure.
C=Foreign language: this tests language handling, not the absence of evidence.
D=Vague questions: vagueness tests clarification behaviour; the evidence may still exist.
T: Build unanswerable cases from verified gaps in the corpus and score the explicit refusal as correct.

@ PLTR-AIE D5 T5.3 applied troubleshooting
S: A team runs its evaluation suite nightly. Scores fluctuate between 86% and 92% with no changes to the function. A manager wants to set a pass threshold at 90%. What should the engineer advise?
A: Set the threshold at 90% as requested and treat any nightly run that scores below it as a regression requiring an immediate rollback of the function
B: Measure run-to-run variance first, set the threshold relative to that distribution, and reduce variance (temperature, suite size) where possible
C: Set the threshold at 86% so the suite never fails
D: Stop running the suite nightly, since fluctuating scores are not informative
K: B
G: ## Thresholds must respect variance
The exam guide asks you to distinguish signal from non-deterministic variance. A 6-point nightly spread with no changes means a fixed 90% threshold fires on noise about half the time.
## Better practice
- Characterize variance: multiple runs, distribution of scores.
- Alert on departures from the distribution, not on a single number crossing a line.
- Reduce variance: deterministic settings where appropriate, larger suites (more cases reduce per-case noise), more stable evaluators.
- Pair the score with per-case diffs so a drop can be explained.
Example: after increasing the suite to 400 cases and fixing the grader's criteria, the spread narrows to 89-91%, and a threshold at 87% becomes meaningful.
W: Variance-aware thresholds and variance reduction: alerts then mean something, and the suite becomes a reliable regression signal.
X: A=Fixed 90% with rollbacks: half the nights would trigger rollbacks of a function that did not change.
C=Threshold at the floor: a real regression to 85% would be hidden inside "never fails" territory only slightly; the threshold is arbitrary either way without variance analysis.
D=Stop running: the suite is informative once variance is understood; abandoning it loses regression detection.
T: Set evaluation thresholds relative to measured variance and work to reduce that variance.

@ PLTR-AIE D5 T5.1 applied tradeoff
S: Which evaluator is appropriate for checking that a function's extracted invoice total matches the expected value?
A: A model-graded rubric asking whether the total "seems reasonable" given the invoice
B: A deterministic numeric comparison with exact match, or a tolerance only where rounding is legitimate
C: A string similarity score between the extracted and expected totals formatted as text, passing when the similarity is above 90%
D: Human review of every case, since numbers are too important to automate
K: B
G: ## Match the evaluator to the output type
The exam guide asks you to create evaluators and metrics. For deterministic outputs, deterministic evaluators are more accurate, cheaper and reproducible than model grading.
## Numeric fields
- Exact match on the parsed number; a tolerance only if the source legitimately rounds.
- Normalize formatting first (currency symbols, thousands separators).
- Reserve model-graded rubrics for free text where exactness is undefined.
Example: expected 1,234.50; extracted "1234.5" normalizes to the same number and passes; "1,234.05" fails.
W: Deterministic numeric comparison: it is exact, reproducible and cheap, which is what a numeric field needs.
X: A=Model "seems reasonable": a wrong total can seem reasonable; model grading adds noise to a question that has an exact answer.
C=String similarity: "1,234.50" and "1,234.05" are very similar strings and very different amounts.
D=Human review of everything: humans spot-check and calibrate, but the comparison itself is trivially automated.
T: Use deterministic evaluators for deterministic outputs; save model grading for free text.

@ PLTR-AIE D5 T5.4 applied use-case
S: An automated workflow approves or rejects document submissions. Downstream, human reviewers sometimes overturn its decisions. How should these overturns be used?
A: Ignore them, since reviewers and the workflow apply different standards and the workflow's metrics are already tracked
B: Capture each overturn with input and both decisions, turn confirmed cases into evaluation cases, analyze by failure type, and prioritize fixes
C: Retrain the model on overturned cases every week so that the workflow aligns with the reviewers automatically
D: Reduce the workflow's authority so that every submission goes to human review from now on, since the overturns prove the workflow cannot be trusted
K: B
G: ## Downstream outcomes as feedback
The exam guide asks for feedback loops that capture user corrections or downstream outcomes and turn them into new evaluation cases or improvement priorities. Overturns are the most valuable signal: a labelled disagreement with ground truth from a human.
## Process
- Capture: structured record per overturn.
- Confirm: not every overturn is a workflow error; some are reviewer inconsistency.
- Convert: evaluation cases with the reviewer's decision as expected.
- Analyze: group by cause (missing document type, ambiguous rule, retrieval miss).
- Improve and re-measure.
Example: 70% of overturns involve a new submission format; the prompt and validation are updated and the suite gains 40 cases.
W: Capture, confirm, convert, analyze, prioritize: the overturns drive measured improvements and protect against the same failures later.
X: A=Ignore: the workflow keeps making the same mistakes, reviewers keep correcting them, and nobody learns why.
C=Weekly retraining: training models is outside the role; the levers are prompts, retrieval, rules and evaluation.
D=Remove authority: some overturns are expected; the right response is to measure and improve, not to abandon automation.
T: Turn human overturns of automated decisions into evaluation cases and prioritized fixes.

@ PLTR-AIE D5 T5.2 advanced use-case
S: An agent can execute an Action that changes a customer's contract terms. Which evaluation cases are essential before release?
A: Cases where the request is clear and the user is authorized, to confirm that the Action works end to end and the contract object is updated
B: Authorized requests (execute), unauthorized users (no change), ambiguous evidence (escalate) and injected instructions (ignore), checked on the objects
C: Cases that measure how quickly the Action executes under load
D: Cases that check the politeness of the agent's responses to customers
K: B
G: ## High-consequence actions need all four classes
The exam guide requires testing normal, edge, adversarial, unauthorized and high-consequence cases, and emphasizes that high-consequence actions deserve the strictest validation. For a contract-changing Action, each class corresponds to a way of causing real harm.
## Checking outcomes
- Assertions on the Ontology: did the contract object change, or not, as expected?
- Not just the chat transcript: an agent that says "done" without changing anything, or changes something while saying "I can't", must be caught.
Example: an unauthorized request produces no change and a clear message; an ambiguous request produces a review task, not a change.
W: The four classes with object-level outcome checks: this is the complete pre-release evidence for an agent that can change contracts.
X: A=Happy path only: it says nothing about refusals and escalations, which are the safety-critical behaviours.
C=Load: performance matters later; correctness of execution decisions comes first.
D=Politeness: a tone metric does not address whether contracts are changed correctly.
T: For agents with consequential Actions, test execute, refuse, escalate and ignore-injection cases against the actual object state.

@ PLTR-AIE D5 T5.3 applied troubleshooting
S: After switching the grading model used by an evaluation suite, every function's score rose by about 5 points overnight with no changes to the functions. What happened and what should be done?
A: The functions improved because the new grader gives the model better feedback during evaluation; the higher scores should be reported as progress
B: The grader changed, so scores are no longer comparable; calibrate the new grader against human ratings and re-baseline all functions
C: The old grader was broken; the new scores are the true ones and history should be deleted
D: Nothing happened; a 5-point rise across all functions is normal variance
K: B
G: ## The measuring instrument changed
A model-based evaluator is part of the measurement. Changing it changes scores independently of the thing measured. The exam guide asks you to separate genuine regression (or improvement) from variance and distribution change; a grader change is a measurement change.
## Response
- Calibrate: compare the new grader's verdicts with human ratings on a sample; check for leniency.
- Re-baseline: run all functions under the new grader to establish new reference scores.
- Keep grader version as metadata on every result so history can be interpreted.
Example: the new grader agrees with humans 90% but is systematically more lenient on partial answers; the rubric is tightened and the baseline reset.
W: Calibrate and re-baseline: scores regain meaning only after the new grader is validated and references are reset.
X: A=Functions improved: nothing about the functions changed; the uniform rise is the grader.
C=Delete history: history under the old grader remains useful once the offset is understood; destroying it loses trend information.
D=Normal variance: a simultaneous, uniform shift across all functions coinciding with a grader change is not noise.
T: Changing the evaluator changes the scale; calibrate and re-baseline before comparing.

@ PLTR-AIE D5 T5.1 applied use-case
S: A team wants to compare three prompt variants for a summarization function fairly. Which experiment design is correct?
A: Run each variant on different random samples of documents and compare average scores
B: Run all three on the same fixed suite with the same model, settings and evaluators, repeated to estimate variance, and compare per case
C: Let each engineer test their own variant on documents they choose themselves and present the best examples to the team for a vote
D: Run the variants in production on alternate days and compare user complaints
K: B
G: ## Controlled experiments
The exam guide lists experiments among evaluation tools. A fair comparison changes one thing (the prompt) and holds everything else fixed: inputs, model, parameters, evaluators.
## Design
- Same fixed suite for all variants.
- Same model and settings, same evaluators and rubric.
- Repeated runs to estimate variance.
- Per-case analysis: which variant wins on which kinds of documents.
- Record everything (prompt versions, model, grader) so the experiment is reproducible.
Example: variant B wins overall by 3 points but loses on technical documents; the team adopts B and adds a technical-document rule.
W: Same inputs, model and evaluators, repeated, with per-case comparison: the only difference is the prompt, so the result is attributable to it.
X: A=Different samples: differences in documents confound differences in prompts.
C=Engineer-chosen examples: cherry-picking produces no comparable measurement.
D=Alternate days in production: uncontrolled inputs, user populations and days; complaints are a weak, noisy signal.
T: Compare variants on the same fixed suite with the same model and evaluators, repeated, and look at per-case results.
