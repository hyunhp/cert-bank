# PLTR-AIE batch 42: Domain 1 round 6 (AIP Logic Development), 8 questions

@ PLTR-AIE D1 T1.1 applied use-case
S: A Logic function must return a list of up to five recommended knowledge articles for a support ticket, each with an article id and a one-line reason. Downstream, an app renders them as links. How should the output be typed?
A: A single string containing the five article titles separated by commas, which the app splits on commas before rendering the links
B: A list of structs, each with a validated article id and a reason string, capped at five items, so the app renders from typed fields
C: Five separate string outputs named article1 to article5 with the reasons embedded inside each string after a dash character
D: A free-text paragraph in which the model mentions the articles it thinks are relevant, with the app searching the paragraph for article ids
K: B
G: ## Lists of typed records
AIP Logic outputs can be lists of structured records. The exam guide asks for typed outputs; a list of references with reasons is a natural typed shape.
## Design
- Output: `recommendations: list<{article_id: reference, reason: string}>` with a maximum length.
- Validation: each id must exist (a lookup); reasons non-empty.
- The app iterates the list; no parsing.
Example: three recommendations returned for a printer issue, each linking to a real article with a reason.
W: A capped list of typed records: the app renders from fields and ids are validated, with no parsing or fixed slots.
X: A=Comma-separated string: titles with commas break the split, and no ids means no reliable links.
C=Fixed string slots: brittle, cannot represent fewer than five, and still needs parsing for the reason.
D=Paragraph to search: the app would mine prose for identifiers that may be misspelt or absent; fragile and unvalidated.
T: Return collections as typed lists of records with validated references rather than delimited strings.
V: AIP Logic, Ontology

@ PLTR-AIE D1 T1.2 applied tradeoff
S: A function must decide whether a contract clause is "standard" or "non-standard" against a library of approved clauses. What combination of deterministic and AI steps is appropriate?
A: Ask the model to judge whether the clause looks standard from its general knowledge of commercial contracts, with no reference to the library
B: Match exactly or after normalization against the library in code, and only for misses use a completion comparing with the closest approved clauses
C: Use the model for everything, including deciding what the approved library contains
D: Use exact matching only, treating any clause not identical to an approved one as non-standard with no explanation
K: B
G: ## Deterministic first, AI for the residual
The exam guide's first decision area: explicit rules in code, interpretation by the model, combined where useful. Exact and normalized matching is deterministic; comparing near-matches needs interpretation.
## Design
- Code: normalize whitespace and punctuation; match against the library; standard on hit.
- Completion for misses: retrieve the closest approved clauses; the model explains deviations with a typed output (verdict, differences).
- Evaluation cases for both paths.
Example: 70% of clauses match exactly in milliseconds; the rest get a reasoned comparison.
W: Code for exact matches and the model for near-matches with explanations: cheap where possible, interpretive where needed.
X: A=General knowledge: the library defines "standard"; the model cannot know it without reference.
C=Model decides the library: the library is a governed artefact, not a guess.
D=Exact only: trivial rewording becomes non-standard with no explanation; unhelpful.
T: Match deterministically against references and apply the model only to the unmatched residual.
V: AIP Logic, Code Repositories

@ PLTR-AIE D1 T1.3 applied troubleshooting
S: A Logic function's trace shows the resolved prompt contains the literal text "{customer_name}" instead of the customer's name. What is wrong and how is it fixed?
A: The model is refusing to read the customer's name for privacy reasons; a stronger model will substitute it into the prompt correctly
B: The variable was not bound (a typo or renamed variable), so injection did not occur; fix the binding and add a check for unresolved placeholders
C: The customer object has no name property value, which the platform displays as the raw placeholder in the resolved prompt by design
D: The trace viewer is showing the prompt template instead of the resolved prompt, so nothing is actually wrong with the function
K: B
G: ## Unresolved placeholders
Variable injection substitutes declared variables into the prompt. A literal placeholder in the resolved prompt means the name did not match any variable. The exam guide asks you to debug from traces and classify as prompt design or wiring.
## Fix
- Match the placeholder to the declared input or block output name; correct the typo or rename.
- Add a check: fail the run if the resolved prompt still contains `{...}` patterns.
- Evaluation case for the input.
Example: the input was renamed `customer_display_name` last week; the prompt still referenced the old name.
W: A binding mismatch found in the trace and fixed with a placeholder check: the injection works and the failure cannot recur silently.
X: A=Model refusing: the model received the placeholder text; substitution happens before the model.
C=Missing name shows placeholder: a missing value would inject empty or null, not the placeholder.
D=Viewer artefact: the trace shows the resolved prompt; the placeholder is really there.
T: Literal placeholders in a resolved prompt mean a variable binding failed; fix the name and guard against unresolved placeholders.
V: AIP Logic, AIP Observability

@ PLTR-AIE D1 T1.1 applied use-case
S: A Logic function must process an input text that is sometimes in Korean and sometimes in English, with instructions written in English. Which design keeps behaviour consistent?
A: Translate the input to English with a second model call before the main prompt on every single run, regardless of its language
B: Keep English instructions, state that input may be in any language and fix the output language, and evaluate with cases in both languages
C: Reject any non-English input with an error message asking the submitter to resubmit the text in English
D: Maintain two separate Logic functions, one per language, and ask every caller to detect the input language and pick the right one
K: B
G: ## Multilingual inputs in one function
Models handle mixed-language prompts; the design must state expectations and verify them. The exam guide asks for typed outputs and evaluation across input variety.
## Design
- Instruction: input language may vary; output language fixed (or mirror the input).
- Output includes a detected-language field for validation.
- Evaluation cases in Korean and English with the same expected structure.
Example: a Korean complaint yields a Korean (or English, as specified) classification with identical fields to an English one.
W: Explicit language expectations in the prompt with per-language evaluation: one function, consistent output.
X: A=Always translate first: extra cost and translation errors on every run, even English ones.
C=Reject Korean: half of the inputs are rejected and their submitters are turned away; the function fails its purpose.
D=Two functions: duplicated logic and detection burden on callers.
T: Handle multilingual inputs in one function by specifying output language and testing per language.
V: AIP Logic, AIP Evals

@ PLTR-AIE D1 T1.2 applied troubleshooting
S: A Logic function applies an edit that increments a counter property on an object. When the function is retried after a timeout, the counter is sometimes incremented twice. What design fixes this?
A: Asking the model in the prompt to remember whether it already incremented the counter in a previous attempt and to skip it if so
B: Making the edit idempotent: set the value from a stable source (count of linked records) or guard the increment with a per-run marker
C: Disabling retries on the function so that a timed-out run is never attempted again and the counter cannot be touched twice
D: Incrementing by 0.5 on each run so that two increments from a retry add up to exactly one, while a single run adds half
K: B
G: ## Idempotent edits
The exam guide asks for safe Ontology edits that tolerate retries. An increment is inherently non-idempotent; the edit must be re-expressed.
## Design
- Prefer absolute values: set `count = number of linked X` rather than `count = count + 1`.
- Or record a run id on the object; skip the increment if the run id was already applied.
Example: after the change, a retried run recomputes the same count and the object is correct.
W: Absolute or marker-guarded edits: retries become harmless because the edit no longer depends on how many times it ran.
X: A=Model memory: the model has no memory across runs; the state lives on the object.
C=Disable retries: transient failures then leave the counter un-incremented.
D=Half increments: a run that is not retried would increment by half, so the counter is wrong in the normal case; absurd.
T: Express edits as absolute, idempotent state changes rather than relative increments.
V: AIP Logic, Actions

@ PLTR-AIE D1 T1.3 applied use-case
S: A team wants to roll out a new Logic function version to 10% of traffic first. How can this be done safely?
A: Editing the published version in place for 10% of the time by switching the prompt back and forth on a timer throughout the day
B: Publishing the new version alongside the old, routing a share of calls to it by configuration or flag, and comparing per-version metrics
C: Asking users to opt into the new version by typing a special command at the start of their request if they want to try it
D: Replacing the old version entirely with the new one and rolling back if enough complaints arrive from users during the first week
K: B
G: ## Staged rollout of versions
The exam guide asks for versioned, observable change. Versions can coexist; routing decides which serves a request.
## Practice
- Both versions published.
- A consumer-level or automation-level condition routes a percentage (for example by object id hash) to the new version.
- Observability: compare quality proxies, latency, error rate per version; increase the share stepwise; rollback is a routing change.
Example: 10% for two days shows equal error rates and better latency; the share goes to 50%, then 100%.
W: Parallel versions with controlled routing and per-version metrics: a measured rollout with instant rollback.
X: A=Edit in place: there is no "10% of the time" for an in-place edit; everyone gets it.
C=User opt-in: only curious users opt in, so the sample is unrepresentative, and the burden is pushed onto them.
D=Replace and wait for complaints: 100% exposure to any defect.
T: Roll out new function versions gradually by routing a share of traffic and comparing per-version metrics.
V: AIP Logic, AIP Observability

@ PLTR-AIE D1 T1.1 applied comparison
S: Which Logic function design is appropriate for "given a ticket, find similar past tickets and summarize how they were resolved"?
A: A single completion with the ticket text, asking the model to recall similar tickets it has seen during training and how they were resolved
B: A semantic search tool over past tickets (scoped by product and permissions), then a completion summarizing the resolutions with citations
C: A loop block that reads every past ticket in the system into the prompt one by one so that the model can compare them all
D: A conditional block that returns a canned "see knowledge base" message whenever the ticket text is longer than a few sentences
K: B
G: ## Retrieval then summarization
The exam guide asks you to combine tools and completions appropriately. Similar past tickets live in the Ontology; they are retrieved, not recalled.
## Design
- Tool: semantic search over Ticket objects (vector property), filtered by product and the user's permissions.
- Completion: summarize resolutions; output typed with cited ticket ids.
- Evaluation: retrieval hit rate and summary groundedness.
Example: five similar tickets retrieved; the summary says three were fixed by a firmware update, citing them.
W: Semantic search tool plus a grounded summary: real past tickets, cited, in one function.
X: A=Recall from training: the model has never seen the company's tickets.
C=Every ticket in the prompt: hundreds of thousands of tickets cannot fit in a prompt; cost and context limits make this impossible.
D=Canned message: a fixed message does not find similar tickets or summarize resolutions; it is not the task at all.
T: Retrieve relevant Ontology objects with a search tool and summarize them with citations.
V: AIP Logic, semantic search

@ PLTR-AIE D1 T1.3 advanced tradeoff
S: Two Logic function designs achieve the same accuracy: one uses three chained completions, the other a single completion with structured output. Which should be preferred and why?
A: The three-step version, because more steps are always more robust and each intermediate result can be inspected separately
B: The single completion: with equal accuracy it has lower latency and cost and fewer failure points; chaining is justified only by measured gains
C: The three-step version, because it produces more trace data for observability and that makes the function easier to monitor
D: Neither on its own; both versions should be published and alternated between runs so that the team benefits from each design
K: B
G: ## Simplicity when quality is equal
The exam guide asks you to optimize execution structure without losing quality. Each extra model call adds latency, cost and a failure point.
## Reasoning
- Equal accuracy on the suite (verified with repeated runs).
- Single call: lower cost and latency; one place to fail; simpler debugging.
- Chaining earns its place when intermediate validation, tool use or measurable gains require it.
Example: the single-call version cuts latency by 60% and cost by 65% with identical scores.
W: The single completion: with accuracy equal on the suite, the single call wins on latency, cost, failure points and debuggability, and nothing in the task requires intermediate tools or validation.
X: A=More steps more robust: more steps means more things that can fail.
C=More traces: trace volume is a cost of complexity, not a benefit; a simpler function is easier to observe, not harder.
D=Alternate: two behaviours in production with no benefit; consumers see inconsistent latency and cost for identical results.
T: Prefer the simplest function structure that meets the quality bar; add steps only for measured benefit.
V: AIP Logic
