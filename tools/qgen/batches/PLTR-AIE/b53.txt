@ PLTR-AIE D7 T7.2 applied troubleshooting
S: Every weekday at 09:00 a workflow built on one catalog model starts failing with rate-limit errors, while other teams' workflows on a different catalog model run normally. The workflow's prompts and volumes have not changed. What is the most appropriate first remedy?
A: Rewrite the prompts to be shorter, since rate limits are caused by the wording of a prompt rather than by how many tokens are sent each minute
B: Disable retries in the workflow so the failed requests stop competing with other teams for the same shared model capacity
C: Move the workflow to a model that is enabled for the enrollment but lightly used, after checking it against the evaluation suite
D: Wait for the model provider to recover, because the rate-limit errors prove that the provider itself is down for the whole enrollment
K: C
G: ## Capacity is per model
AIP follows the limits that model providers impose, measured in tokens per minute (TPM) and requests per minute (RPM). Enrollment capacity is tracked for each model separately, so heavy use of one model does not reduce the capacity of another.
## What that means for resilience
- A rate-limit pattern that repeats at the same time each day points to contention for one model's capacity, not to an outage.
- The capacity documentation lists switching to a different model that the enrollment is not currently using, and so has spare capacity, among the actions for hitting limits.
- A different model is a behaviour change, so it is checked against the evaluation suite before it replaces the original.
Example: a morning surge from several teams saturates one model; the workflow moves to a sibling model with headroom and still meets its quality threshold.
W: C=Move to a lightly used model: independent per-model capacity gives headroom, and the evaluation gate protects quality.
X: A=Shorter prompts: token volume matters, but a daily collision with other teams is a capacity-sharing problem and rewording does not remove the contention.
B=Disable retries: failed requests are not the cause, and removing retries only turns temporary throttling into permanent failures.
D=Wait for the provider: other workflows on a different model work fine, so the evidence shows model-level capacity contention rather than a total outage.
T: Capacity is per model, so a model with spare headroom (validated by evaluation) is the first resilience lever.

@ PLTR-AIE D7 T7.2 applied comparison
S: A customer-facing production application already has its project limit raised to 100 percent of the enrollment capacity for its model, yet it is still throttled when other projects run heavy jobs on that same model. Which measure guarantees the application a share of capacity?
A: Reserve part of the model's tokens and requests per minute and allocate that reserved share to the application's project
B: Raise the project limit above 100 percent of the enrollment capacity so that the application outranks every other project
C: Ask the other teams to stop using the model, because a project limit at 100 percent already reserves the capacity for it
D: Move the application to a project with a lower limit, since smaller projects are served before larger ones on a shared model
K: A
G: ## A limit is a ceiling, not a guarantee
A project limit caps how much of a model's per-minute capacity a project may use. It does not stop other projects drawing on the same pool, so a project at 100 percent still competes for shared capacity.
## Reserved capacity
- Reserved capacity sets aside a share of a model's TPM and RPM (up to 50 percent of the model's total) and lets an administrator allocate it to critical projects.
- The application uses its reserved share first and then falls back to the shared pool.
- Rescheduling competing jobs and moving them to other models reduce contention, and reserved capacity covers what remains.
Example: 250 thousand of 1 million TPM is reserved for the production application and the other 750 thousand stays shared.
W: A=Reserved capacity: a guaranteed share of tokens and requests per minute allocated to the project, used before the shared pool.
X: B=Limit above 100 percent: a limit is a percentage of the enrollment capacity, so it cannot exceed the ceiling and never confers priority.
C=Ask others to stop: a 100 percent limit is only a ceiling, so it reserves nothing and the contention continues.
D=Lower-limit project: a smaller limit only restricts the application further and gives no precedence on a shared model.
T: A project limit caps usage; reserved capacity is what guarantees it.
