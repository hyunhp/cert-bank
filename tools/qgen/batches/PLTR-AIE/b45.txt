# PLTR-AIE batch 45: Domain 4 round 6 (AI-Powered Data Processing), 8 questions

@ PLTR-AIE D4 T4.1 applied use-case
S: A pipeline must extract the signatory names and their roles from scanned contract signature pages, where the names are handwritten and the roles are printed. Which approach is most reliable?
A: A text-only model over the OCR output alone, since modern OCR handles both printed and handwritten text equally well on scanned pages
B: A vision model over the page image with a structured {name, role} list, roles validated against a list, and review of low-confidence names
C: Asking a text model to guess the likely signatories from the names and roles mentioned on the contract's first page
D: Skipping the signature pages entirely since handwriting recognition is unreliable, and recording the signatories as unknown
K: B
G: ## Mixed printed and handwritten content
The exam guide names VLMs and visual document processing with structured outputs and validation. Handwriting needs the image; roles can be validated against a list; uncertainty goes to review.
## Design
- Vision model on the image; schema: `signatories: list<{name, role, confidence}>`.
- Validation: role in allowed set; name non-empty.
- Low-confidence names to a review queue; raw response retained.
Example: 85% of pages are extracted automatically; 15% have a name reviewed by a person.
W: Vision extraction with structured output, validation and confidence-routed review: handwriting handled with appropriate control.
X: A=OCR plus text model: OCR of handwriting is poor; the text model never sees the image.
C=Guess from page one: signatories are on the signature page, not inferable.
D=Skip: the signatories are the information the business asked for; recording them as unknown fails the requirement.
T: Use vision models with structured output and confidence-based review for handwritten content.
V: Pipeline Builder, AIP

@ PLTR-AIE D4 T4.2 applied use-case
S: An AI enrichment pipeline changes its prompt monthly. The business asks how they can tell which rows were produced under which prompt. What is the right design?
A: Keep a changelog document describing each prompt change by date, which analysts cross-reference with the timestamps on the enriched rows
B: Write the prompt version and model id as columns on every enriched row, so provenance is queryable and backfills can target versions
C: Rely on differences in the model's output style and wording to infer which prompt version produced any given row
D: Reset the enriched dataset every month and regenerate everything, so that only one prompt version ever exists at a time
K: B
G: ## Version columns
The exam guide asks for auditability of AI outputs. A version column makes provenance a first-class, queryable attribute of each row.
## Design
- Columns: `prompt_version`, `model_id`, `generated_at`.
- Queries: counts by version; targeted backfill of rows on old versions.
- Cache keys include the version so changes regenerate deliberately.
Example: a dashboard shows 72% of rows on v9 and 28% still on v8 awaiting backfill.
W: Per-row version columns: provenance that can be queried, audited and used to drive backfills.
X: A=Changelog by date: ambiguous around change times and useless for targeted reprocessing.
C=Output style: wording varies run to run within one version; inferring the version from style is guesswork.
D=Monthly reset: destroys history and costs a full regeneration.
T: Record prompt and model versions on every AI-produced row.
V: Pipeline Builder

@ PLTR-AIE D4 T4.3 applied tradeoff
S: An LLM step that classifies incoming emails is implemented north of the Ontology, in a function called when an agent opens an email. Reports now need the classification for every email. What should change?
A: Nothing; the reports can call the same function for each email at report time, so there is no need to change the architecture
B: Move the classification south into an event-driven or batch step that classifies every email on arrival and stores the class as a property
C: Have an agent open every incoming email in the application so that the function runs and the classification is produced for all of them
D: Compute the classification twice, once north in the function and once south in a pipeline, each independently with its own prompt
K: B
G: ## When a north computation becomes a shared need
The exam guide's layer criteria: a result needed by many consumers for every item is south. The original placement served one interactive use; the requirement changed.
## Change
- Pipeline or Automate on email creation: classify, validate, store `category`.
- The agent's view reads the stored class; reports aggregate it.
- Same function logic, different placement; evaluation unchanged.
Example: 10,000 emails a day are classified on arrival; reports run in seconds and agents see the same class.
W: Move the classification south and store it: one computation serving both the interactive view and the reports.
X: A=Reports call the function: thousands of model calls per report run and inconsistent results.
C=Agent opens every email: a person clicking through 10,000 emails a day to trigger a function is absurd and still leaves gaps.
D=Twice independently: two sources of truth that can disagree.
T: When a per-item AI result becomes a shared need, move it to the pipeline and store it.
V: Automate, Pipeline Builder, Ontology

@ PLTR-AIE D4 T4.4 applied troubleshooting
S: A Code Repositories LLM transform fails after three hours because a single malformed row causes an exception that aborts the whole job. What should be changed?
A: Remove the malformed row from the input by hand before each run, after finding it in the error message of the failed job
B: Handle errors per row: catch exceptions, record the row with a failure status and message, continue, and threshold the failure rate
C: Increase the job's overall timeout so that it has more time to get past the malformed row before the platform stops it
D: Run the job on a bigger cluster with more executors so that the malformed row is processed by a worker with more memory
K: B
G: ## Row-level fault isolation
The exam guide asks for programmatic control in Code Repositories including error handling. A batch should degrade per row, not fail per job.
## Implementation
- try/except around the model call and parsing per row.
- Output includes `status` and `error`; good rows proceed.
- Expectation: failure rate below a threshold; alert otherwise.
Example: one row with invalid encoding is recorded as failed; the other 2 million complete.
W: Per-row error handling with recorded failures and a rate threshold: resilience without hiding problems.
X: A=Manual removal: unscalable and the next malformed row aborts the job again.
C=Longer timeout: the job did not run out of time; it crashed on an exception, which a longer timeout does nothing about.
D=Bigger cluster: a malformed row throws the same exception on any executor; more resources cannot catch it.
T: Isolate failures per row in batch AI transforms and monitor the failure rate.
V: Code Repositories

@ PLTR-AIE D4 T4.1 applied use-case
S: A pipeline classifies product reviews for sentiment, but the business now also wants the specific product feature each review mentions (battery, screen, price). How should the extraction be extended?
A: Run a second, separate LLM pass over all 5 million reviews just for features, doubling the number of model calls permanently
B: Extend the structured schema with features as a validated list alongside sentiment, so one call yields both, with a versioned backfill
C: Ask the model to describe in free text which features each review mentions, and store the description as a string column
D: Infer the mentioned features from the sentiment score with a rule, since reviews with similar sentiment tend to mention similar things
K: B
G: ## Extending a structured extraction
The exam guide asks for structured outputs and efficient processing. Adding a field is a schema extension and a version bump, not a second pipeline.
## Design
- Schema: `{sentiment: enum, features: list<enum>}`.
- Validation: features within the allowed list.
- Prompt version bump; backfill incrementally; new reviews get both fields in one call.
Example: 5 million reviews gain a features column over a week's rolling backfill; new reviews are complete on arrival.
W: Schema extension with a versioned backfill: both fields from one call, with the regeneration bounded.
X: A=Second pass: every future review costs two calls instead of one, when a single structured call produces both fields.
C=Free text: "mentions the battery and screen" cannot be filtered or counted; the business wants a categorical list.
D=Infer from sentiment: a score carries no feature information.
T: Extend AI extraction schemas rather than adding passes, and backfill by version.
V: Pipeline Builder, Code Repositories

@ PLTR-AIE D4 T4.2 applied use-case
S: Auditors ask whether an AI-generated field could have been influenced by data the model should not have seen. What stored artefact answers this directly?
A: The output value itself, since a correct-looking value is evidence that the model used only appropriate inputs to produce it
B: The resolved prompt (template version plus injected variables) and the list of retrieved or injected inputs per row
C: The name and version of the model that produced the field, since the provider documents what data each model was trained on
D: The pipeline's schedule and the timestamp of the run, since they show when the field was generated relative to data changes
K: B
G: ## What the model saw
The exam guide asks to preserve prompts for auditability. The resolved prompt and the inputs per row are the record of what the model received.
## Stored
- Template version plus variable values (reconstructible resolved prompt).
- References to injected context (chunk ids, object ids).
- Model and parameters.
Example: for row 4421 the record shows two injected objects, both authorized; no restricted data was in the prompt.
W: The reconstructible resolved prompt and the per-row inputs: direct evidence of what influenced the output.
X: A=Output alone: a value says nothing about which data the model received; a correct value can still come from an improper input.
C=Model name: identifies the model, not the prompt and context this pipeline sent to it for this row.
D=Schedule: timing says nothing about the content injected into the prompt.
T: Store what the model received per row so influence questions can be answered from records.
V: Pipeline Builder

@ PLTR-AIE D4 T4.3 applied comparison
S: A team is sorting four proposed AI workloads into pipeline-layer and interaction-time placements. Which of the following most clearly belongs in a scheduled pipeline rather than at interaction time?
A: Rewriting a single email draft in a different tone at the moment the user clicks a "make it formal" button in the application
B: Translating all 200,000 product descriptions into four languages for the catalogue, refreshed whenever a description changes
C: Answering an analyst's ad hoc question about a specific customer's recent history while they are looking at that customer
D: Summarizing the document that a user has just uploaded, on their request, before they decide whether to read it in full
K: B
G: ## Batch at scale
The exam guide's criteria: breadth, reusability, scale and freshness decide the layer.
- Catalogue translation: every item, reusable, large scale, change-driven refresh: pipeline.
- Tone rewrite, ad hoc question, on-request summary: single-user, on-demand: interaction time.
Example: translations are produced once per description change and served to millions of page views.
W: Catalogue-wide translation: every item, reused by millions of views, refreshed on change; the reusable, large-scale, scheduled case that defines pipeline-layer work.
X: A=Tone rewrite: one user's one draft, transformed on demand; nothing to precompute or share.
C=Ad hoc question: unknown in advance and specific to the analyst's context; it can only run at interaction time.
D=Upload summary: produced once for one user on request; there is no catalogue of items to process in batch.
T: Whole-catalogue, reusable AI work is pipeline work; per-user requests are interactive.
V: Pipeline Builder, AIP Logic

@ PLTR-AIE D4 T4.1 advanced tradeoff
S: A batch extraction achieves 99% field accuracy, but the remaining 1% of errors are concentrated in a field that triggers financial actions downstream. What should the pipeline do with that field?
A: Accept 99% as excellent overall accuracy and let the downstream financial action proceed automatically for all extracted rows
B: Stricter controls on the financial field: cross-checks against another source, a review threshold, and a hold on actions for unverified rows
C: Remove the financial field from the extraction entirely so that the pipeline's accuracy figure is not affected by its errors
D: Lower the model's temperature for the extraction, which should make the financial field more accurate without any other change
K: B
G: ## Field-level consequence
The exam guide asks to match validation strictness to consequence. One field drives money; it deserves more control than the others.
## Design
- Cross-check: the extracted amount against a second source (totals, line sums).
- Confidence threshold; below it, review.
- Downstream gate: financial action only on verified rows.
Example: 0.6% of rows are reviewed before any payment; the rest flow automatically.
W: Stricter validation, cross-checks and a downstream hold for the consequential field: proportionate control where errors cost money.
X: A=Accept: 1% of rows with a wrong financial value means thousands of wrong payments at scale; the aggregate loss is large.
C=Remove: the financial field is the one the downstream process needs; dropping it does not make the process work.
D=Temperature: lower randomness does not correct misreads in a hard field; the errors are systematic, not sampling noise.
T: Apply field-level validation strictness according to the consequence of each field's errors.
V: Pipeline Builder, Actions
