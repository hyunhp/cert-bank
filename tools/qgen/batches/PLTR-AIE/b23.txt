# PLTR-AIE batch 23: Domain 6 round 3 (Automation, Orchestration, and Integration), 8 questions

@ PLTR-AIE D6 T6.1 applied use-case
S: An automation should send an AI-drafted reminder to customers whose invoices become overdue, but only once per invoice and never to customers flagged as "do not contact". Which configuration expresses this?
A: A trigger on the overdue status with no further conditions, relying on the AI draft to mention that the customer should ignore the message if they have opted out of contact
B: A trigger on the overdue transition with conditions (not do-not-contact, no reminder sent yet) and an effect that records the reminder after sending
C: A daily schedule that drafts reminders for every overdue invoice and sends them all, since customers who do not want contact can reply to say so
D: A manual list that an accounts clerk reviews each morning before copying the AI draft into an email for each customer by hand
K: B
G: ## Conditions and state in Automate
The exam guide asks you to configure triggers, effects and conditions correctly. "Once per invoice" and "never to opted-out customers" are conditions on state; the state must be recorded so the condition can be evaluated next time.
## Configuration
- Trigger: invoice status becomes overdue.
- Conditions: `customer.do_not_contact = false` and `invoice.reminder_sent_at is null`.
- Effects: generate draft, send, then set `reminder_sent_at` (idempotent marker).
Example: an invoice that flips to overdue twice after a partial payment gets one reminder; an opted-out customer gets none.
W: Trigger plus state conditions plus a recorded marker: both rules are enforced by the automation, not by the message text.
X: A=No conditions: opted-out customers are contacted; repeated triggers send repeatedly.
C=Daily blast: violates both rules and is a compliance problem.
D=Manual: unnecessary when the rules are expressible, and slow.
T: Enforce business rules in automation conditions and record state so "once" can be checked.

@ PLTR-AIE D6 T6.2 applied troubleshooting
S: A workflow chains three functions: extract → score → decide. The decide step sometimes receives a null score because the score step silently returned nothing on model errors. What should be changed?
A: Make the decide step treat a null score as zero, so the workflow never stalls and every item receives a decision one way or the other
B: Make the score step return a typed error state on model errors, and route errored items to retry or review instead of passing nulls on
C: Add a fourth function that guesses a score whenever the previous step returned a null value, so downstream always has a number to work with
D: Remove the score step and let the decide step work from the raw extraction alone, which avoids the null problem entirely
K: B
G: ## Explicit failures between steps
Silent nulls propagate wrong decisions. The exam guide asks for workflows that remain safe when an AI call fails: failures must be visible and handled.
## Design
- Typed outputs include a status; a model error yields `status = error` rather than a null score.
- Orchestration branches on status: retry with backoff, or route to review.
- Metrics: error rate per step.
Example: a provider timeout now produces an "error" status; the item is retried ten minutes later and decided correctly.
W: Explicit error states and routing: decisions are made only on real scores, and failures are visible and recoverable.
X: A=Null as zero: a model outage would silently mark everything low-priority.
C=Guessing function: it fabricates a score to paper over a failure, so decisions are made on invented data without anyone knowing.
D=Remove the step: the score exists because the decision needs it.
T: Never pass silent nulls between workflow steps; make failures explicit and route them.
V: AIP Logic, Automate

@ PLTR-AIE D6 T6.3 applied use-case
S: A team must run a one-time backfill of an AI enrichment over 2 million historical objects through the same Action used by the live automation. What precautions apply?
A: Run it at full speed during business hours so it finishes quickly and the live automation can resume afterwards without any lag
B: Run it as a bounded, rate-limited, resumable batch off-peak with idempotent writes and monitoring so live operation is not disrupted
C: Disable all Action validation for the backfill to avoid rejections, since historical data is known to be reliable and does not need checking
D: Run it as 2 million separate automation triggers, one per object, so that each object is processed exactly like a live one
K: B
G: ## Safe backfills
The exam guide asks you to account for in-flight work, retries and duplicate execution when changing live workflows; a backfill is a large planned change.
## Precautions
- Bounded batches with rate limits (provider and platform capacity).
- Progress state so the job can pause and resume without repeating work.
- Idempotent writes keyed on object and enrichment version.
- Off-peak scheduling and monitoring of live automation latency.
- Validation stays on; rejected items are queued for review.
Example: 2 million objects processed over four nights in batches of 50,000, with the live automation unaffected.
W: Bounded, resumable, idempotent, monitored and validated: the backfill completes without disrupting live operation or corrupting data.
X: A=Full speed in business hours: rate limits and capacity starve the live automation.
C=Disable validation: historical data has the same errors; bad values would land.
D=Per-object triggers: millions of trigger events overwhelm the automation system and lose batch control.
T: Backfills run as bounded, resumable, idempotent batches with validation on and live traffic protected.

@ PLTR-AIE D6 T6.1 applied comparison
S: Which situation is best served by a function-backed Action rather than a plain Action with static rules?
A: Changing a status field from Open to Closed with no computation involved, where a simple rule can validate the transition and no function is needed
B: Applying a change whose values are computed at execution time, such as generating a summary with an AI function and writing it with validation
C: Deleting an object, since deletion is irreversible and therefore always requires custom function logic before it can be allowed
D: Any Action at all, since function-backed Actions are strictly more capable and should be the default for every edit in the Ontology
K: B
G: ## Function-backed Actions
A plain Action applies edits defined declaratively with rules. A function-backed Action runs code (which may call AI functions) to compute the edits. The exam guide lists function-backed Actions among orchestration tools.
## When to use
- Edits depend on computation or external calls at execution time.
- Conditional logic across several objects.
- Integration with AI outputs under validation.
Example: "Generate and attach summary" computes the summary and writes it; "Close ticket" is a static rule.
W: Computed edits at execution time: that is what the function behind the Action provides.
X: A=Simple status change: declarative rules suffice; a function adds complexity.
C=Deletion: a plain Action with validation handles deletion; irreversibility is a permission and confirmation matter.
D=Always: unnecessary code for simple edits; use the simplest Action that works.
T: Use function-backed Actions when the edit must be computed; keep simple edits declarative.
V: Actions, AIP Logic

@ PLTR-AIE D6 T6.3 applied troubleshooting
S: An automation's AI step was updated to a new function version last night. This morning, half of the objects processed overnight have the old output shape and half have the new one, and a downstream dashboard broke. What should have been done, and what now?
A: Nothing could have prevented this, since version changes always cause temporary inconsistency and the dashboard team should have expected it
B: Coordinate with consumers and cut over cleanly with a compatible shape or transition; now find affected objects by version, map them to one shape, fix the dashboard
C: Roll back to the old version permanently so the dashboard works again and never upgrade the function in the future
D: Delete the objects processed overnight and let the automation reprocess them, which will restore consistency on its own
K: B
G: ## Output-shape changes are breaking changes
The exam guide asks for safe modification of live workflows and for preserving behaviour for consumers. An output-shape change is a contract change; it needs a plan.
## Should have
- Compatible output (additive) or versioned output field with a transition.
- Coordination with the dashboard owner.
- Cut-over at a quiet point; in-flight objects finished on the old version.
## Now
- Use the recorded version on each object to find the mixed set.
- Reprocess or map to one shape; validate; repair the dashboard.
Example: 4,100 objects are mapped to the new shape in one run; the dashboard's query is updated to the new field.
W: Planned contract change with transition, then a version-based repair: both the prevention and the recovery.
X: A=Unavoidable: an additive output shape or a versioned field with a short transition would have avoided the mixed state entirely.
C=Permanent rollback: it fixes today by freezing the function forever.
D=Delete and reprocess: destroys data and loses edits; the version column makes a targeted repair possible.
T: Treat AI output-shape changes as contract changes with a transition; repair mixed states using recorded versions.
V: Automate, AIP Logic

@ PLTR-AIE D6 T6.2 applied use-case
S: A Workshop user clicks "Analyze" and the AI analysis takes 40 seconds. The team wants the button to return immediately and the result to appear when ready. Which integration supports this?
A: A synchronous function call from the button that blocks the interface until the analysis finishes, since Workshop buttons must wait for results
B: The button triggers an Action that records a request; an automation runs the analysis and writes the result to the object; the module shows status
C: The button opens a dialog asking the user to wait and refreshes the page every five seconds until the analysis completes
D: The analysis is run in the user's browser using a lightweight model so it finishes in under a second
K: B
G: ## Asynchronous patterns in Workshop
The exam guide recommends asynchronous execution for long work with visible status. In Workshop this is achieved by separating the request from the result.
## Design
- Action: creates an "analysis request" (status = pending) on the object.
- Automation: triggers on the request, runs the AI function, writes the result and status = done.
- Module: shows status; updates when the result lands.
Example: the user clicks, keeps working, and the analysis panel fills in 40 seconds later with a "completed" badge.
W: Request/response via Action and automation with status on the object: the interface stays responsive and the result arrives reliably.
X: A=Synchronous block: 40 seconds of frozen interface, the problem being solved.
C=Polling dialog: still blocks the user and hammers the server.
D=Browser model: the analysis needs the real model; quality would collapse.
T: For long AI work from Workshop, record a request, process it asynchronously, and show status on the object.
V: Workshop, Actions, Automate

@ PLTR-AIE D6 T6.1 applied tradeoff
S: An automation must process objects in a strict order (older first) because each decision depends on the previous one. Per-object parallel execution is producing out-of-order decisions. What should change?
A: Keep parallel execution and accept occasional out-of-order decisions, since the automation will eventually process every object and small ordering errors even out
B: Switch to batch execution that processes objects sequentially in order within one run, or chain per-object runs so each waits for the previous
C: Increase the parallelism so that all objects are processed at once and the ordering problem is no longer visible to anyone
D: Randomize the processing order so that no particular object is consistently disadvantaged by being processed later than another
K: B
G: ## Ordering and execution modes
The exam guide lists execution modes among automation configuration. When decisions depend on earlier ones, the execution model must respect order.
## Options
- Batch run: collect pending objects, sort by timestamp, process sequentially.
- Chained execution: each run reads the latest state and processes one object, so the next sees the updated state.
- Guard: a precondition that the previous object's decision exists.
Example: ten orders arriving in a minute are decided oldest first, each with the correct running context.
W: Sequential batch or chained execution: order is guaranteed by the execution mode, which is the only way the dependency is respected.
X: A=Accept disorder: decisions dependent on order become wrong, not "evened out".
C=More parallelism: even more objects decided simultaneously without context from earlier ones; the ordering problem gets worse, not invisible.
D=Random order: fairness between objects is not the issue; the decisions depend on chronological order, which randomization destroys completely.
T: When decisions depend on order, use sequential or chained execution, not per-object parallelism.
V: Automate

@ PLTR-AIE D6 T6.3 advanced use-case
S: Before enabling a complex multi-step AI automation in production, the team wants a rehearsal that proves the full chain works end to end without real effects. What is the best approach?
A: Enable it in production for one hour and watch the first effects closely, reverting any that look wrong before anyone outside the team notices
B: Run it on a branch or test objects with effects pointed at non-production targets, inspect every step's output and object state, then enable with limited scope
C: Review the configuration on screen with the whole team and enable it if nobody can think of a problem with any of the steps
D: Run only the AI step on sample inputs, since the rest of the chain is just plumbing that cannot fail in interesting ways
K: B
G: ## Rehearsing automations
The exam guide asks you to test manually with representative objects before enabling live triggers and to account for in-flight work. For a multi-step chain, every step and its side effects must be exercised.
## Approach
- Isolated run: branch (Global Branching) or dedicated test objects; effects to non-production targets or dry-run markers.
- Inspect: each step's output, the Action results, object state, notifications captured.
- Staged enablement: one segment of objects first, with monitoring, then widen.
Example: the rehearsal reveals that the notification step uses a production address; it is fixed before go-live.
W: Isolated end-to-end rehearsal with inspection and staged go-live: the chain is proven, including its side effects, before real effects happen.
X: A=Production trial: real effects, real consequences; "revert" is not always possible (sent emails).
C=Review only: reading configuration cannot reveal runtime behaviour.
D=AI step only: integration failures live in the plumbing (Actions, permissions, notifications).
T: Rehearse automations end to end in isolation, inspect every step, then enable with limited scope.
V: Automate, Global Branching
