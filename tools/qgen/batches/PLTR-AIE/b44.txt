# PLTR-AIE batch 44: Domain 3 round 6 (RAG Architecture and Semantic Search), 8 questions

@ PLTR-AIE D3 T3.1 applied use-case
S: A knowledge base contains many near-identical documents (templates with small variations per region). Retrieval returns five almost identical chunks and the answer never mentions the one regional difference the user asked about. What chunking or retrieval change helps?
A: Increase the number of retrieved chunks to twenty so that the regional variant is more likely to be included somewhere in the context
B: Deduplicate near-identical chunks at retrieval, tag chunks with region metadata, and filter or boost by the user's region
C: Remove all but one template from the corpus so there is no duplication at all
D: Ask the model to notice regional differences on its own from whatever chunks it receives
K: B
G: ## Near-duplicates crowd out variants
The exam guide asks for metadata and context selection that balance precision and recall. Five copies of the same text consume the context budget and hide the one that differs.
## Design
- Near-duplicate collapse: cluster by similarity; keep one per cluster.
- Region metadata on chunks; filter to the user's region (from state or profile) or boost it.
- Diversity in ranking so variants, not copies, fill the slots.
Example: the user in region B gets region B's variant and one representative base chunk, and the answer names the difference.
W: Deduplication plus region metadata filtering: the context carries the variant that matters instead of five copies.
X: A=Twenty chunks: more copies, more noise, more cost; the variant may still be crowded out.
C=Delete templates: the regional variants are legitimate content.
D=Model notices: it cannot notice a variant it never received.
T: Collapse near-duplicates and use metadata to retrieve the variant relevant to the user.
V: semantic search, Ontology

@ PLTR-AIE D3 T3.2 applied tradeoff
S: A retrieval workflow must support both short keyword-like queries ("SKU 4471 warranty") and long natural-language questions. Pure semantic search handles the long ones well but misses exact codes. What design fits?
A: Use semantic search only and ask users to write longer, more descriptive questions so that their queries embed well
B: Hybrid retrieval: combine keyword matching for codes with semantic search, merge and rerank, with evaluation sets for both styles
C: Use keyword search only, since exact codes and identifiers are the most important thing for users to be able to find
D: Run semantic search twice with two different embedding models and merge the results, so that more varied matches are found
K: B
G: ## Hybrid retrieval
The exam guide asks you to design retrieval for the questions users actually ask and to measure each stage. Identifiers need lexical matching; meaning needs embeddings.
## Design
- Lexical index on codes, SKUs, titles.
- Semantic index on chunk text.
- Merge candidates; rerank; inject.
- Evaluation sets: code-style and natural-language queries, measured separately.
Example: "SKU 4471 warranty" hits the exact SKU chunk lexically and the warranty policy semantically; both are injected.
W: Lexical plus semantic retrieval with reranking: each query style is served by the method that fits it.
X: A=Semantic only with longer questions: users will not comply, and codes still embed poorly.
C=Keyword only: long questions with no shared terms miss entirely.
D=Two embedding models: both are semantic; neither matches "SKU 4471" exactly, so codes remain weak and cost doubles.
T: Combine lexical and semantic retrieval when queries mix identifiers and natural language.
V: semantic search

@ PLTR-AIE D3 T3.3 applied troubleshooting
S: Groundedness evaluation shows the model frequently cites the correct chunk but states a number that differs from the chunk (for example 30 days instead of 14). What is the likely cause and fix?
A: The embedding model returned the wrong chunk and the citation is misleading, so the embedding model should be replaced
B: Generation is blending prior knowledge or other chunks with the cited one; instruct verbatim figures, cut competing chunks, verify
C: The cited chunk is too long for the model to read accurately, so the chunk size should be reduced across the corpus
D: The generation temperature is too low, which makes the model fall back on memorized figures rather than reading the passage
K: B
G: ## Right chunk, wrong fact
The exam guide separates retrieval from generation diagnosis. The citation shows retrieval worked; the number shows generation strayed.
## Fix
- Instruction: quote figures exactly from the cited passage; do not infer.
- Context: fewer competing chunks with similar numbers.
- Validation: numeric values in the answer must occur in the cited chunk; otherwise flag.
- Evaluation: numeric-fidelity cases.
Example: after the change, every "days" figure in answers matches the cited text, verified automatically.
W: Generation-stage tightening with numeric verification: the fact is tied to the cited source and checked.
X: A=Wrong chunk: the citation points to the correct chunk containing the right figure; retrieval did its job.
C=Too long: a long chunk may bury a figure but does not turn 14 into 30; the number came from elsewhere.
D=Temperature too low: lower randomness does not cause fabricated numbers.
T: When citations are right but facts are wrong, fix generation with verbatim instructions and value checks.
V: AIP Evals, AIP Logic

@ PLTR-AIE D3 T3.1 applied use-case
S: A retrieval corpus must include spreadsheets with hundreds of rows each. Embedding each sheet as one chunk loses row-level detail; embedding each row loses the header context. What is the right chunking?
A: Embed only the first data row of each sheet as a representative summary of the whole spreadsheet
B: Chunk by row or small row groups with the header row and sheet title prepended, plus sheet and row-range metadata
C: Convert each spreadsheet to a paragraph of prose with a language model and embed that paragraph instead of the table
D: Exclude spreadsheets from the retrieval corpus entirely, since tabular data does not suit semantic search
K: B
G: ## Tabular chunking
The exam guide asks for chunking strategies that keep chunks self-contained. Tables need the header to make a row meaningful.
## Design
- Chunk: header + N rows (small N), with sheet title and row range metadata.
- Retrieval returns rows with their column meanings.
- Identifier queries can also route to exact lookups if the sheet becomes an object type.
Example: "price of part 88-1204" retrieves the chunk whose rows include that part, with the header "part, description, price".
W: Header-prepended row chunks with metadata: row-level retrieval with preserved meaning.
X: A=First row only: one row cannot represent hundreds; every other row's data becomes unretrievable.
C=Prose conversion: a model's paragraph drops or alters exact values; retrieval would return descriptions rather than data.
D=Exclude: the spreadsheets hold the prices and parts users ask about; excluding them makes those questions unanswerable.
T: Chunk tables by rows with headers attached so each chunk is self-describing.
V: semantic search, Pipeline Builder

@ PLTR-AIE D3 T3.2 applied use-case
S: An assistant must answer only from documents published in the last 12 months unless the user explicitly asks for historical material. How should retrieval be configured?
A: Delete every document older than 12 months from the corpus so that nothing historical can ever be retrieved by mistake
B: A default publication-date filter (last 12 months) at retrieval, with an explicit mode that relaxes it for historical requests
C: Ask the model in its instructions to ignore any document older than 12 months unless the user asks for history
D: Boost recent documents slightly in the ranking so that they usually appear above older ones in the retrieved set
K: B
G: ## Default filters with explicit overrides
The exam guide lists freshness among retrieval criteria and asks for metadata filtering. The requirement is a default scope with a user-controlled exception.
## Configuration
- Chunk metadata: publication date.
- Default filter: date ≥ now − 12 months.
- Override: detected request for historical content (or a toggle) removes the filter.
- Evaluation: default and historical cases.
Example: "what is the current travel policy" uses the filter; "what did the 2021 policy say" relaxes it.
W: Date filter by default with an explicit historical mode: the requirement is enforced and the exception is deliberate.
X: A=Delete old documents: historical questions become unanswerable.
C=Ask the model: a soft request; old chunks still enter the context.
D=Slight boost: a highly similar old chunk can still outrank the new policy; a boost is not a scope rule.
T: Enforce default retrieval scope with metadata filters and provide an explicit override mode.
V: semantic search, Ontology

@ PLTR-AIE D3 T3.3 applied troubleshooting
S: A team notices that retrieval latency doubled after they added a reranker. Quality improved. Users complain about speed. What is a balanced response?
A: Remove the reranker entirely and go back to similarity ranking, accepting the quality loss to restore the old speed
B: Tune the reranker's cost: rescore fewer candidates, use a lighter model or cache repeated queries, measuring latency and quality
C: Double the candidate set the reranker rescores to improve quality even further, and address the latency later
D: Tell users that answer quality matters more than speed and that they should accept the longer wait for better results
K: B
G: ## Reranker cost management
The exam guide asks you to balance precision and latency. Rerankers help quality but scale with the number of candidates they rescore.
## Tuning
- Candidates: rerank the top 30 instead of 200.
- Model: a lighter cross-encoder.
- Caching for repeated queries.
- Measure: quality and latency per configuration; pick the balanced point.
Example: reranking 30 candidates keeps 95% of the quality gain at 20% of the added latency.
W: Reduce reranker cost by candidate count, model size and caching, measured against quality: both goals are met.
X: A=Remove: the measured quality improvement disappears entirely when a tuned reranker could keep most of it.
C=Double candidates: reranking cost scales with candidates; latency gets worse while users are already complaining.
D=Dismiss users: speed is part of quality for interactive use.
T: Keep rerankers affordable by limiting candidates and model size, measured on both quality and latency.
V: semantic search, AIP Evals

@ PLTR-AIE D3 T3.1 applied comparison
S: A team is selecting an embedding model for a new retrieval corpus and asks what constraints the choice carries. Which statement about embedding model choice is correct?
A: Any embedding model can be mixed with any other at query time without re-indexing, since the vectors are just numbers of the same length
B: The embedding model is part of the index: queries must use the same model, changing it means re-embedding, and the choice is evaluated on retrieval
C: The largest available embedding model is always the best choice for retrieval regardless of the corpus domain or the cost of embedding it
D: Embedding models do not need to be evaluated on the retrieval set because they do not generate any text that could be wrong
K: B
G: ## The embedding model as an index component
The exam guide asks for embedding strategy decisions and consistency between indexing and query time.
- Same model for both sides.
- A change means re-embedding everything and re-evaluating.
- Choice by evaluation: hit rate on the retrieval set, language coverage, cost and latency.
Example: a domain-tuned model raises hit@5 by 9 points on technical manuals; the corpus is re-embedded once.
W: Index-bound, consistent between indexing and query, re-embedded on change, and chosen by retrieval evaluation on the actual corpus: the correct view of embedding model choice.
X: A=Mix freely: vectors from different models are not comparable.
C=Largest always: domain fit and cost matter; size is not fitness.
D=No evaluation: the model decides which chunks are found; hit rate on the retrieval set is exactly how its fitness is measured.
T: Treat the embedding model as part of the index: consistent, re-embedded on change, chosen by retrieval evaluation.
V: semantic search

@ PLTR-AIE D3 T3.2 advanced tradeoff
S: An assistant's retrieval must respect three constraints at once: user permissions, document approval status and a maximum context budget. In what order should these be applied?
A: Budget first to pick a small set of chunks, then approval status, then permissions, since the budget is the tightest constraint
B: Permissions and approval as filters before ranking, then similarity ranking and reranking, then the token budget on the result
C: Permissions last, applied to the answer after the model has read everything, since the model can then explain what it withheld
D: In any order the implementation finds convenient, since the same set of chunks ends up in the context whichever order is used
K: B
G: ## Order of constraints
The exam guide asks for authorized evidence and bounded context. Hard constraints (authorization, status) filter candidates; soft constraints (budget) trim the ranked eligible set.
## Order
- Filter: user permissions (executed as the user) and status = approved.
- Rank: similarity, then reranking.
- Budget: fill the token allocation from the top of the eligible ranking.
Example: 2 million chunks → 40,000 eligible → top 30 reranked → 8 injected within budget.
W: Hard filters, then ranking, then budget: unauthorized content never competes for space and the budget holds the best eligible evidence.
X: A=Budget first: it might fill with chunks that later get filtered, leaving gaps.
C=Permissions last: the model has already seen unauthorized content.
D=Any order: the orders produce different, sometimes unsafe, results.
T: Apply authorization and status filters before ranking, and the context budget after.
V: semantic search, Ontology
