@ PLTR-AIE D1 T1.2 advanced use-case
S: A Logic function must set an object's `priority` property based on an explicit matrix of (customer tier, issue severity) that the business maintains, and also write a short justification that references the customer's recent history. Which split of work is correct?
A: Let the model read the matrix from the prompt and decide the priority, then write the justification, so that one completion produces both outputs
B: Compute the priority deterministically from the governed matrix in code, and use the completion only to write the justification from injected history
C: Ask the model to infer both the priority and the matrix from past tickets
D: Compute the justification in code with a template and let the model set the priority
K: B
G: ## The guide's first decision, applied to one function
The exam guide separates explicit rules (code) from interpretation (model). The priority is a lookup; the justification is language.
## Split
- Code: priority = matrix[tier][severity] from a reference dataset; deterministic and auditable.
- Completion: justification text from injected recent history; typed string output.
- Edit: priority from code, justification from the model; validated.
Example: tier gold plus severity high yields priority 1 by rule every time; the justification varies in wording but not in the priority it accompanies.
W: Deterministic priority with a model-written justification: each part done by the right mechanism and the consequential value never left to the model.
X: A=Model decides from the prompt: a lookup becomes a judgement that can vary or err.
C=Infer the matrix: the matrix is a governed business artefact, not a guess.
D=Reversed: a template cannot write a history-aware justification, and the model should not set the rule-driven value.
T: Within one function, compute rule-driven values in code and reserve the model for language.
V: AIP Logic, Code Repositories

@ PLTR-AIE D2 T2.3 advanced tradeoff
S: An agent passed its evaluation suite, pilot and security review. On release day, a stakeholder asks to add a new Action "to make the launch more impressive". What is the right response?
A: Add it quickly before the launch, since it is only one more tool and the rest of the agent has already been thoroughly tested
B: Decline the untested addition: ship the evaluated agent and add the Action in the next release with its own cases, permission review and pilot
C: Add the Action and remove the evaluation gate for this one release only, so that the launch date can still be met with the new feature
D: Cancel the launch entirely until the new Action has been built, evaluated and piloted, however long that takes
K: B
G: ## Scope discipline at release
The exam guide asks for controlled, evaluated change. A last-minute tool invalidates the testing that justified the release.
## Response
- The validated scope ships.
- The new Action enters the next cycle: cases, permissions, consequence review, pilot.
- Communicate the plan; the stakeholder's request is honoured safely.
Example: the agent launches on schedule; the Action ships three weeks later with its own evidence.
W: Ship what was validated; add new capability through the normal evaluated process: the release stays trustworthy.
X: A=Quick add: an untested tool in production with Action consequences.
C=Skip the gate: suspending evaluation precisely when an untested capability is added is the worst possible moment to do it.
D=Cancel: punishes users for a late request; the validated agent has value now.
T: Never add untested capabilities to a validated release; schedule them with their own evaluation.
V: AIP Agent Studio, AIP Evals

@ PLTR-AIE D3 T3.3 advanced troubleshooting
S: A retrieval-grounded assistant's groundedness is high, its retrieval hit rate is high, yet users rate answers as unhelpful. What is the most likely remaining problem and how is it found?
A: The embedding model must be wrong and should be replaced with a different one, since poor user ratings on a retrieval assistant point at retrieval
B: The answers are faithful but do not address what users wanted (intent, synthesis, level of detail); review feedback and traces, add a helpfulness rubric
C: The evaluation suite should be deleted since it disagrees with the users, and user ratings should become the only measure of quality
D: Users should be trained to ask better, more specific questions so that the assistant's faithful answers become more useful to them
K: B
G: ## Grounded but unhelpful
The exam guide separates correctness, groundedness and usefulness. High groundedness and hit rate mean the system is faithful; unhelpfulness means it is answering the wrong question or at the wrong level.
## Diagnosis
- Feedback clusters: "too generic", "did not answer my actual question", "too long".
- Trace review: retrieved chunks relevant but the answer restates them without synthesis.
- Fix: question-intent handling, synthesis instructions, length calibration; helpfulness rubric in the suite.
Example: users ask "which option should I choose"; the assistant lists options faithfully but never compares; a comparison instruction fixes it.
W: A usefulness gap found through feedback and traces, fixed in instructions and measured with a helpfulness rubric: the metrics now cover what users care about.
X: A=Embedding model: the retrieval hit rate is already high; the right chunks are being found, so the embedding model is not the problem.
C=Delete the suite: it measures what it measures; it needs a usefulness dimension added.
D=Train users: the assistant exists to serve the questions users actually ask; blaming the questions avoids fixing the assistant.
T: When grounded answers are unhelpful, measure and fix usefulness, not retrieval.
V: AIP Evals, AIP Agent Studio

@ PLTR-AIE D4 T4.3 advanced tradeoff
S: An AI engineer is asked to decide, for a new workload, between an LLM transform in Pipeline Builder, a Code Repositories transform, and an on-demand Logic function. The workload: enrich 3 million records nightly with a classification, requiring custom retry logic, strict rate limiting and per-row audit, consumed by dashboards. Which choice and why?
A: An on-demand Logic function invoked for each record, since classification is an AI task and AIP Logic is the platform's AI authoring tool
B: A Code Repositories transform: the scale is pipeline-layer, and custom retry, rate limiting and audit need programmatic control
C: An LLM transform node in Pipeline Builder, since it is the quickest to set up for any batch AI job and needs no code
D: Manual classification by a team of analysts working through the records in a Workshop queue, with the dashboards reading their labels
K: B
G: ## Choosing among batch AI implementations
The exam guide distinguishes LLM transforms in Pipeline Builder from Code Repositories, which suit custom logic, retries, rate limiting and programmatic control. Scale and consumption place the work south.
## Reasoning
- South: nightly, millions of rows, dashboards.
- Code: custom retry and rate limiting, per-row audit records, checkpointing.
- Pipeline Builder would fit a simpler job without those control requirements.
Example: the transform paces calls at the provider limit, records prompt version and raw response per row, and resumes after interruptions.
W: Code Repositories: the batch placement plus the control requirements that a configured node cannot express.
X: A=On-demand Logic: 3 million nightly rows for dashboards is not on-demand work.
C=Pipeline Builder LLM node: fine for simple batch jobs; lacks custom retry, pacing and audit control.
D=Manual: 3 million records a night cannot be classified by people; the dashboards would never be current.
T: Use Code Repositories for batch AI that needs custom control; Pipeline Builder LLM nodes for simpler batch jobs; Logic for on-demand.
V: Code Repositories, Pipeline Builder, AIP Logic

@ PLTR-AIE D5 T5.4 advanced use-case
S: Six months after launch, an AI feature's suite score is unchanged, but production overturn rates have doubled. What does this combination indicate and what should the team do?
A: The suite must be fundamentally wrong and should be rewritten from scratch, discarding all of the existing cases and expected answers
B: Production inputs have drifted from what the suite represents; refresh it with recent production cases and re-evaluate
C: Users have simply become more critical of the feature over time for no particular reason, as people do with any tool they use daily
D: Nothing, since the suite score is stable and the suite is the authoritative measure of the feature's quality
K: B
G: ## Suite stable, production worse
The exam guide asks for production feedback loops and representative suites. A stable suite with worsening production means the suite no longer represents production.
## Action
- Compare the production mix (segments, document types) now versus at launch.
- Sample recent production cases with overturns; add to the suite.
- Re-evaluate: the score will drop, revealing the real regression; fix.
Example: a new product line's documents now make up 30% of traffic and were absent from the suite; 60 cases are added and the fixes follow.
W: Distribution drift detected through the overturn signal and repaired by refreshing the suite: the measurement realigns with reality.
X: A=Rewrite everything: the existing cases still cover real behaviours; the suite needs new cases from production, not a blank page.
C=Users more critical: a doubled overturn rate is a measured change in outcomes, not a mood; the inputs changed and the suite did not.
D=Nothing: the doubled overturn rate is what users experience; a stable suite score that misses it is a measurement gap, not reassurance.
T: Treat stable suite scores with worsening production metrics as distribution drift and refresh the suite from production.
V: AIP Evals, AIP Observability

@ PLTR-AIE D6 T6.3 advanced use-case
S: A multi-step AI workflow (classify → enrich → route → notify) runs on object creation. The team must guarantee each object is notified exactly once even if the automation is retried, the function times out mid-chain, or two creations arrive for the same object. What combination of practices is required?
A: Faster execution of every step so that timeouts and failures become rare enough that duplicate notifications almost never happen
B: Per-step idempotency, step state on the object so retries resume, a notification marker checked before sending, and trigger dedupe
C: Disabling retries on the automation entirely and accepting that some objects will never be notified when a step fails
D: Sending the notification as the very first step of the chain so that it is never missed, and running the other steps afterwards
K: B
G: ## Exactly-once effects in chains
The exam guide asks for idempotent, resumable orchestration with safe handling of retries and duplicates. "Exactly once" is achieved through markers and resumable state.
## Practices
- Step state on the object: classified, enriched, routed, notified.
- Each step idempotent; a retry skips completed steps.
- Notification guarded by a marker set atomically with the send.
- Trigger dedupe by object id.
Example: a timeout after enrichment leads to a retry that resumes at routing and sends one notification; a duplicate creation event is ignored.
W: Per-step state, idempotency, a send marker and trigger deduplication: every failure mode leaves exactly one notification.
X: A=Faster: faster steps still time out and get retried sometimes; speed reduces frequency, it does not guarantee exactly once.
C=No retries: every transient failure becomes a permanently unnotified object; "exactly once" becomes "at most once".
D=Notify first: a later step failing leaves a notified but unprocessed object, and retries resend.
T: Achieve exactly-once effects with per-step state, idempotent steps, send markers and event deduplication.
V: Automate, Actions

@ PLTR-AIE D7 T7.4 advanced tradeoff
S: An AI engineer must cut a workflow's cost by 40% without reducing its evaluation score. Which sequence of optimizations is most likely to achieve this with the least risk?
A: Switch the whole workflow to the cheapest model available in the catalog and check the evaluation score afterwards to see what was lost
B: Measure the cost breakdown, then remove waste, cache, route easy cases to a cheaper model, and change the main model last, re-evaluating
C: Halve the evaluation suite so that fewer model calls are made during testing, which reduces the overall monthly cost of the workflow
D: Reduce the number of requests by rate-limiting users to a daily quota, which cuts the total cost in proportion
K: B
G: ## Optimization in order of risk
The exam guide asks for cost and performance optimization without losing quality, using observability to guide it. Waste removal and caching are risk-free; model changes carry quality risk and come last, gated by evaluation.
## Sequence
- Measure: cost breakdown per component.
- Waste: trim prompts, bound context, structured outputs, fix retry storms.
- Cache: identical inputs.
- Route: a cheaper model for cases the suite shows it handles.
- Main model change last, if still needed.
Example: waste removal saves 25%, caching 10%, routing 8%; the main model is untouched and the score unchanged.
W: Measured, risk-ordered optimization gated by evaluation: the target is met without gambling quality on a model swap.
X: A=Cheapest model first: the riskiest change to quality, made before the risk-free savings have even been measured.
C=Halve the suite: evaluation runs are a small fraction of a production workflow's cost, and halving coverage weakens the gate that protects quality.
D=Rate-limit users: capping usage reduces the value delivered along with the cost; the waste per request is untouched.
T: Cut AI cost by measuring, removing waste, caching and routing before changing the main model, re-evaluating at each step.
V: AIP Observability, AIP Evals

@ PLTR-AIE D8 T8.4 advanced use-case
S: A newly hired AI engineer is handed an existing agent and asked to confirm it is "secure". Which review covers the layered model the guide describes?
A: Reading the agent's system prompt carefully for safety instructions and confirming that it tells the model to behave responsibly
B: Reviewing each boundary: retrieval permissions, tool scoping, execution identity, prompt and output checks, human review, adversarial tests
C: Asking the previous owner in a handover meeting whether the agent was tested for security before it was released
D: Running a single prompt-injection attempt against the agent and declaring it secure if that one attempt fails to change its behaviour
K: B
G: ## The security review as a boundary walk
The exam guide's security domain and its self-check describe controls at each boundary. A review walks them in order and records what is enforced where.
## Review
- Data: retrieval as the user; markings on sources and chunks.
- Tools: least privilege; validation; confirmations; caps.
- Execution: identity, mode, residency.
- Prompts and outputs: hardening, checks.
- Human review points; adversarial suite; monitoring and alerts.
- Gap list with owners.
Example: the review finds retrieval runs as a service identity rather than the user, exposing restricted documents; it is fixed before the sign-off.
W: A boundary-by-boundary review with a documented gap list: the only way to confirm the layered controls are actually in place.
X: A=Prompt only: the prompt is the layer most easily bypassed; reviewing it alone says nothing about permissions, tools or execution.
C=Ask the previous owner: a recollection is not evidence; the controls must be inspected as they exist now.
D=One injection attempt: a single test proves nothing about the other boundaries.
T: Review agent security by walking every boundary and documenting the enforced controls and the gaps.
V: AIP Agent Studio, Actions, AIP Evals
