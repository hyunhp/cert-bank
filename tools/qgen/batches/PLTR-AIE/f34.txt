@ PLTR-AIE D8 T8.3 applied tradeoff
S: An AIP Chatbot Studio assistant has an Action tool that closes customer accounts. The business wants speed, so a developer proposes configuring it to run automatically. What is the better design?
A: Run it automatically but add a sentence to the instructions telling the model to be careful before it closes a customer's account
B: Remove the Action tool and make the assistant refuse requests about accounts, so that no closure can be triggered by mistake
C: Let it run without confirmation and review a weekly sample, on the assumption that support staff can reopen accounts closed by mistake
D: Configure the Action to run after the user's confirmation, so a person sees and approves the proposed edit before it is applied
K: D
G: ## Confirm consequential edits
The AIP Chatbot Studio (formerly AIP Agent Studio) tools page says an Action tool gives the chatbot the ability to execute an ontology edit and can be configured to run automatically or after confirmation from the user. Closing an account is hard to undo and affects a customer, so the confirmation step puts a human decision before the write.
## Why not the rest
- Prompt wording is not a control.
- After-the-fact sampling finds errors only once harm occurred.
- Removing all account capability throws away value that a gated design preserves.
W: Confirmation before execution: the Action tool supports running after confirmation from the user, so a person sees and approves exactly what will change before the edit is applied, while the assistant still does the work of preparing it.
X: A=Be-careful sentence: guidance the model may ignore or be talked out of, so it is not an enforceable control on a hard-to-undo edit.
B=Remove and refuse: over-corrects by discarding useful account help that a gated design would keep safely.
C=Weekly sample: a detective check that finds wrong closures only after customers were affected, and the premise that every closure is easy to reverse is unproven.
T: Gate consequential edits behind explicit human confirmation instead of prompt wording, removal or after-the-fact review.

@ PLTR-AIE D3 T3.3 applied troubleshooting
S: A retrieval assistant gives a wrong answer. In the trace, the correct passage was never among the retrieved chunks, though it exists in the corpus. Which action targets the failure?
A: Switch to a larger model, because a larger model can recall corpus passages from its training even when retrieval misses them
B: Rewrite the answer instructions to say "be more accurate", since the wrong answer was produced in the generation step
C: Investigate retrieval: chunking, embedding, metadata, query wording and K for that passage, then re-test the case
D: Remove the retrieval step and let the model answer from its training data, which avoids the problem of missed passages
K: C
G: ## Locate the failing stage
In retrieval-augmented generation the relevant content is fetched and passed to the LLM with the message. If the passage is absent from the retrieved set, generation cannot use it; the fault is upstream.
## Check
- Chunking: was the passage split or buried in a huge chunk?
- Embedding and metadata: is it embedded and not filtered out?
- Query and K: does the query resemble the passage; is K too small?
Example: a table row separated from its header never matches the question.
W: Investigate retrieval: the trace shows the passage missing from the retrieved set, so the retrieval settings (chunking, embedding, filters, query, K) are the lever, and re-testing the case shows whether the fix worked.
X: A=Larger model: a model is not trained on the organization's private corpus, so it cannot supply a passage that never reached it, and it adds cost without evidence.
B=Accuracy instruction: a generation instruction cannot make the model use text that was never provided to it; the failure happened before generation.
D=Remove retrieval: answering from training data alone removes grounding in the corpus and makes the answers unverifiable.
T: If the right passage is not retrieved, fix retrieval, not generation.

S: An automation creates a payment request through an Action. After a failed run was retried, finance finds two requests for one invoice. How should the AI engineer prevent duplicates, given that a retry may repeat an effect that already partly succeeded?

Retries exist because effects can fail transiently, but a retried effect may repeat work that took effect before the failure was reported. @ PLTR-AIE D6 T6.3 advanced use-case
S: A multi-step AI workflow (classify → enrich → route → notify) runs on object creation. The team must guarantee each object is notified exactly once even if the automation is retried, the function times out mid-chain, or two creations arrive for the same object. What combination of practices is required?
A: Faster execution of each step, so that timeouts and failures become rare enough that duplicate notifications seldom happen
B: Per-step idempotency, step state on the object so retries resume, a notification marker checked before sending, and trigger dedupe
C: Disabling retries on the automation and accepting that some objects stay unnotified when one of the steps fails
D: Sending the notification as the first step of the chain so that it goes out early, and running the other steps afterwards
K: B
G: ## Exactly-once effects in chains
The exam guide asks for idempotent, resumable orchestration with safe handling of retries and duplicates. "Exactly once" is achieved through markers and resumable state.
## Practices
- Step state on the object: classified, enriched, routed, notified.
- Each step idempotent; a retry skips completed steps.
- Notification guarded by a marker set atomically with the send.
- Trigger dedupe by object id.
Example: a timeout after enrichment leads to a retry that resumes at routing and sends one notification; a duplicate creation event is ignored.
W: Per-step state, idempotency, a send marker and trigger deduplication: a retry resumes after the last completed step, the marker blocks a second send, and a duplicate creation event is ignored, so each failure mode leaves exactly one notification.
X: A=Faster steps: faster steps still time out and get retried sometimes; speed reduces how often duplicates happen, it does not prevent them.
C=No retries: each transient failure becomes a permanently unnotified object, so "exactly once" becomes "at most once".
D=Notify first: a later step failing leaves a notified but unprocessed object, and a retry of the chain sends the notification again.
T: Achieve exactly-once effects with per-step state, idempotent steps, send markers and event deduplication.
