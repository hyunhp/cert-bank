# PLTR-AIE batch 19: Domain 2 round 3 (AIP Agent Design and Deployment), 8 questions

@ PLTR-AIE D2 T2.2 applied tradeoff
S: An agent helps analysts explore a large Ontology. Its retrieval context currently includes every object type's documentation, making each turn slow and the answers unfocused. What should be changed about its context?
A: Keep all of the documentation in the standing context, since the agent might need any part of it on any turn and omitting something risks wrong answers
B: Replace the static dump with retrieval of only the object types and documentation relevant to the question, plus a short overview
C: Remove all documentation from the context and let the model infer the Ontology's structure from object and property names as it goes
D: Ask the analysts to type the relevant object type names at the start of every message
K: B
G: ## Retrieval context design for agents
The exam guide asks you to configure tools, retrieval context and conversation behaviour. "Everything in context" is simple but scales badly: latency, cost and noise all grow with the Ontology.
## Better
- A compact overview always present (what the Ontology covers, naming conventions).
- Retrieval over documentation chunks keyed by object type and topic; the question selects what is injected.
- Tools that let the agent inspect a specific object type's schema when needed.
Example: a question about shipments injects the Shipment and Carrier documentation only, and the turn takes two seconds.
W: Targeted retrieval with a small standing overview: context fits the question, which fixes both speed and focus.
X: A=Keep everything: the cost and noise grow with every new object type.
C=No documentation: the agent would misunderstand properties and links.
D=Users type names: it pushes the retrieval problem onto users and breaks for those who do not know the names.
T: Agents over large knowledge bases use retrieval to assemble per-turn context rather than a static dump.
V: AIP Agent Studio, semantic search

@ PLTR-AIE D2 T2.1 applied use-case
S: A company has an agent in AIP Agent Studio and wants Workshop users to interact with it inside a specific module, with the agent aware of the object the user has selected on screen. How is this achieved?
A: By telling users to copy the selected object's id from the module and paste it into the chat at the start of every conversation with the agent
B: By embedding the agent in the module and passing the selected object as application state, so its tools and prompts use the selection
C: By giving the agent a tool that lists all objects and asking it to guess which one the user means
D: By running the agent as a standalone page in another browser tab beside the Workshop module, where users can describe what they are looking at
K: B
G: ## Embedding with application state
The exam guide lists Workshop embedding and application state among deployment configuration. An embedded agent can receive the module's state (the selected object, filters) so its behaviour is anchored to what the user sees.
## Configuration
- Embed the agent widget in the module.
- Map module variables (selected object) to the agent's context or inputs.
- Tools scoped to that object where appropriate.
Example: the user selects supplier S-14; the agent's answers and Actions concern S-14 without the user naming it.
W: Embedded agent with the selection passed as application state: the agent is context-aware by design.
X: A=Copy ids: manual and error-prone, and unnecessary when the module already knows the selection and can pass it along.
C=Guess from a list: unreliable and slow; the selection is already known.
D=Separate tab: a standalone agent has no access to the module's state, so the user must describe the selection in words every time.
T: Embed agents in Workshop and pass the module's state so the agent knows the user's current selection.
V: AIP Agent Studio, Workshop

@ PLTR-AIE D2 T2.2 applied troubleshooting
S: An agent's guardrail is meant to stop it from giving legal advice. Testers find that asking "what would a lawyer say about this contract clause" bypasses it. What should the engineer do?
A: Add that exact phrase and a few obvious variants to a blocklist that rejects the message before the agent sees it
B: Define the boundary in instructions, add an output check for advice-like legal content, and add paraphrased adversarial cases to the suite
C: Remove the guardrail since it cannot be perfect
D: Lower the temperature so the agent is less creative and therefore less likely to drift into giving advice when asked indirect questions
K: B
G: ## Guardrails are behaviours, not keywords
The exam guide lists guardrails among agent configuration and asks for adversarial testing. A single phrase bypass shows the guardrail is matching surface form rather than intent.
## Approach
- Define the boundary: general information about contract terms (allowed) versus a recommendation for the user's situation (not allowed), with examples.
- Output check: a classifier or rubric that flags advice-like legal content, triggering a safe response.
- Adversarial suite: many paraphrases, hypotheticals and role-play attempts; expected behaviour defined.
Example: after the change, "what would a lawyer say" yields general information plus a pointer to counsel, consistently across 30 phrasings.
W: Defined behaviour, output check and paraphrased adversarial tests: the guardrail becomes robust to wording.
X: A=Blocklist: the next paraphrase bypasses it; there are endless ways to ask the same thing and a list cannot cover them.
C=Remove: the requirement remains; imperfection is addressed with layers, not abandonment.
D=Temperature: determinism does not change what counts as advice.
T: Implement guardrails as defined, tested behaviours with output checks, not as phrase lists.
V: AIP Agent Studio, AIP Evals

@ PLTR-AIE D2 T2.3 applied use-case
S: An agent will be used by external customers, not employees. What additional pre-release considerations apply compared with an internal agent?
A: None; the same pre-release test plan applies to any agent regardless of who its users are, since the agent's logic is the same
B: Stricter adversarial testing, data scoped to the authenticated customer, rate and cost controls, refusal and escalation paths, and compliance review
C: Only additional load testing, since the main difference with external users is that the traffic volume will be far higher than internal use
D: Removing all tools so the agent can only chat
K: B
G: ## Audience changes the risk
The exam guide asks you to design agents for the right audience and context. External users are untrusted by default: they will probe, misuse and share outputs.
## Considerations
- Data scoping: each customer sees only their own data; verified by tests.
- Adversarial coverage: injection, jailbreak, extraction of other customers' data.
- Controls: rate limits, cost caps, abuse monitoring.
- Behaviour: refusal and escalation to humans; compliant, consistent tone.
Example: a test as customer A asking about customer B's order returns nothing; abusive input is declined politely and logged.
W: Untrusted-audience controls and testing: these address the risks that an internal deployment does not carry to the same degree.
X: A=Same plan: it ignores that external users are untrusted and that mistakes are seen publicly, which changes the risk profile entirely.
C=Load only: volume is one concern; abuse and data scoping are larger.
D=No tools: some tools (order status) are the value; the answer is scoping, not removal.
T: External-facing agents need stricter scoping, adversarial testing, cost controls and escalation paths.
V: AIP Agent Studio

@ PLTR-AIE D2 T2.2 applied use-case
S: A support agent should hand a conversation to a human when it cannot help. Which design makes this work well?
A: Ending the conversation with a generic "please call us" message and the support phone number whenever the agent cannot answer
B: A defined escalation path: recognized triggers, a summary of the conversation, a ticket or queue handoff with that summary, and clear next steps
C: Continuing to try different answers in a loop until the user either gets what they need or gives up and leaves the conversation
D: Escalating every conversation to a human agent after the first exchange, so that no customer is ever left with an unresolved question
K: B
G: ## Escalation as a designed behaviour
The exam guide asks what an agent should do when evidence is insufficient and emphasizes escalation for high-consequence or ambiguous cases. Escalation should carry context so the human does not start from zero.
## Design
- Triggers: no supporting evidence, repeated failure, sentiment, specific request types.
- Handoff: structured summary (issue, what was tried, customer details) into a ticket or queue via an Action.
- Communication: tell the user the next step and expected time.
- Measure: escalation rate and resolution after handoff.
Example: after two failed answers the agent says it is passing the case to a specialist and creates a ticket with the transcript summary.
W: Triggered, context-carrying handoff with clear communication: the user is helped and the human is prepared.
X: A=Call us: the customer has to start over on the phone; nothing from the conversation is transferred and the experience is poor.
C=Loop: repeated failed attempts waste the user's time and erode trust; a defined stopping point is needed.
D=Escalate everything: removes the agent's value and floods humans.
T: Design escalation with explicit triggers and a context-rich handoff to humans.
V: AIP Agent Studio, Actions

@ PLTR-AIE D2 T2.1 applied comparison
S: Which statement about AIP Assist and a custom standard agent is accurate?
A: AIP Assist can be configured with a company's custom tools and Ontology Actions just like a standard agent, so a separate agent is rarely needed
B: AIP Assist is the built-in helper for using the platform; standard agents are custom-built in Agent Studio with their own instructions, context and tools
C: Standard agents cannot be embedded in Workshop; only AIP Assist can
D: AIP Assist replaces the need for any custom agents
K: B
G: ## Two different things
The exam guide asks you to distinguish standard agents and AIP Assist based on deployment context and capabilities.
- AIP Assist: platform-wide helper, answers "how do I do X in Foundry", available across the platform.
- Standard agent: built in Agent Studio for a business purpose, with custom instructions, retrieval over business data, tools and Actions; deployed embedded in Workshop or standalone.
Example: "how do I create a schedule?" is for AIP Assist; "which of my shipments are at risk?" is for a custom agent.
W: Platform helper versus custom business agent: the accurate distinction in purpose, configuration and deployment.
X: A=Configure Assist with custom tools: that is what Agent Studio agents are for.
C=Embedding: standard agents are embeddable in Workshop; that is one of their deployment channels.
D=Replaces custom agents: Assist does not know a company's business data or tools.
T: AIP Assist helps with the platform; standard agents are built for business tasks.
V: AIP Assist, AIP Agent Studio

@ PLTR-AIE D2 T2.3 applied troubleshooting
S: An agent passes all evaluation cases but, in production, users often rephrase questions two or three times before getting a useful answer. What does this indicate and what should be done?
A: Users are asking poorly and need training on how to phrase questions, since the agent passes every case in the evaluation suite
B: The suite lacks real phrasings; sample production conversations, add messy and partial questions to the suite, and improve clarification behaviour
C: The model should be replaced with a larger one, since a stronger model would understand the users' first phrasing without rephrasing
D: The agent should refuse rephrased questions and ask users to submit each question only once, which keeps conversations short
K: B
G: ## Representative evaluation
A suite written by engineers often contains clean questions. The exam guide asks for representative suites and for feedback loops from production into evaluation.
## Steps
- Sample real conversations; identify patterns that fail on the first try.
- Add them as cases with the expected outcome (an answer or a specific clarifying question).
- Improve instructions: when a question is ambiguous, ask one targeted clarifying question.
- Track first-turn success rate as a metric.
Example: "status of my thing from last week" becomes a case expecting "Do you mean order 1182 from 7 March?".
W: Realistic phrasings in the suite plus better clarification behaviour: the measurement and the agent both align with real use.
X: A=Blame users: the agent exists to serve how users actually ask.
C=Replace the model: the gap is in test coverage and clarification design, not model capability.
D=Refuse rephrasings: hostile to users and useless for the business; rephrasing is a signal of the agent's failure, not the user's.
T: Keep evaluation suites representative of real phrasing and design clarification behaviour for ambiguity.
V: AIP Evals, AIP Agent Studio

@ PLTR-AIE D2 T2.2 advanced tradeoff
S: Two agents are being designed. Agent A answers questions from a knowledge base. Agent B can submit refund requests up to a limit. How should their tool and permission configurations differ?
A: Both should have the same tools and permissions for consistency, so that users get the same capabilities whichever agent they happen to use
B: Agent A gets read-only retrieval and no Actions; Agent B gets the refund Action with validation, limits, idempotency, audit and restricted invocation
C: Agent B should have fewer safeguards than Agent A since it is more useful to customers and safeguards would slow down legitimate refunds
D: Agent A should also have the refund Action in case users ask about refunds while reading the knowledge base, to avoid sending them elsewhere
K: B
G: ## Capability proportional to consequence
The exam guide asks why an agent needs each tool and to match controls to consequence. Reading knowledge is low-consequence; issuing refunds changes money.
## Configurations
- A: retrieval tools only; refusal path; no write capability.
- B: one Action with limits, validation, idempotency and audit; restricted invocation; approval above a threshold; adversarial cases for manipulation attempts.
Example: an injected instruction in a document cannot make Agent A do anything harmful; the same attack on Agent B is blocked by the Action's validation and limits.
W: Read-only for A, tightly controlled single Action for B: each agent's capabilities and safeguards match what it can affect.
X: A=Same tools: gives the knowledge agent a money-moving capability it does not need.
C=Fewer safeguards: higher consequence demands more control, not less.
D=Refund tool on A: unnecessary capability is unnecessary risk.
T: Scale an agent's tools and safeguards to the consequence of its actions.
V: AIP Agent Studio, Actions
