# PLTR-AIE batch 30: Domain 5 round 4 (Evaluation, Testing, and Quality Assurance), 8 questions

@ PLTR-AIE D5 T5.1 applied use-case
S: A function produces a structured summary with five fields. The team wants a single evaluation score per case but also needs to know which field fails. How should the evaluator be designed?
A: One evaluator that returns pass or fail for the whole record at once, since a single number per case is what the quality dashboard shows
B: Field-level evaluators (exact match for identifiers and dates, rubrics for text) aggregated into a case score, with per-field results retained
C: A model-graded evaluator that reads the whole record and returns one holistic score without field detail
D: Human review of all five fields for every case in the suite, with the reviewer entering a single overall score for the record
K: B
G: ## Granular evaluators with aggregation
The exam guide asks you to create evaluators and metrics; for multi-field outputs, per-field evaluators give both the aggregate and the diagnosis.
## Design
- Identifier and date fields: exact match after normalization.
- Text fields: rubric-based or similarity with a threshold.
- Case score: weighted aggregate; per-field scores stored.
- Reports: overall trend plus "which field regressed".
Example: overall score fell from 90 to 85; the breakdown shows only `relief_sought` dropped, pointing to a prompt change in that section.
W: Per-field evaluators aggregated into a case score: one number for tracking and the detail for fixing.
X: A=Whole-record pass/fail: a single wrong field fails the case with no indication which.
C=Holistic model score: hides which field is wrong and adds grader noise to exact fields.
D=Human for everything: reviewing every field of every case by hand cannot be repeated on each change; regression testing needs automation.
T: Evaluate structured outputs per field and aggregate, keeping the per-field detail.

@ PLTR-AIE D5 T5.2 applied use-case
S: Which evaluation case is the best example of a "high-consequence" test for an agent that can reschedule customer deliveries?
A: A request to reschedule a single delivery by one day where the customer has no special constraints and the slot is available
B: A request to reschedule all deliveries for a region during a storm warning, where the correct behaviour is to escalate for confirmation
C: A request for the agent to explain the company's rescheduling policy in general terms without referring to any specific delivery
D: A request to look up the current status of a single delivery and report it, without changing anything about the delivery
K: B
G: ## Identifying high-consequence cases
The exam guide asks for evaluation of normal, edge, adversarial, unauthorized and high-consequence cases, and for escalation on high-consequence, ambiguous requests. Consequence scales with scope and reversibility.
## The case
- Mass change (a whole region) with external uncertainty (storm) is high-consequence and ambiguous.
- Expected behaviour: prepare the change, surface the scope and risk, require confirmation.
- Evaluator: no deliveries changed; an escalation created with the right summary.
Example: the agent replies "this affects 1,200 deliveries; I've prepared the change for a dispatcher's approval."
W: A mass, uncertain, hard-to-reverse request expecting escalation: the archetypal high-consequence case.
X: A=One delivery, no constraints: a routine, reversible change that the agent should simply perform; it is the normal case.
C=Policy explanation: an informational answer with no state change; its risk is a wrong explanation, not a consequential action.
D=Status lookup: a read-only question with no consequence beyond a possibly wrong status; nothing is changed.
T: High-consequence cases involve broad, hard-to-reverse actions under uncertainty, with escalation as the expected outcome.

@ PLTR-AIE D5 T5.3 applied troubleshooting
S: A regression suite shows a 4-point drop after a prompt change. Per-case analysis shows the drop is entirely in cases that were added last week from production feedback, all of one type. What should the engineer conclude?
A: The prompt change is bad for everything and must be reverted immediately
B: The change regressed on one case type while the rest held; targeted work on that type is needed, and the new cases did their job
C: The new cases must be wrong because they lowered the score, and they should be removed from the suite to restore the baseline
D: Nothing can be concluded from a 4-point change on a suite of this size, so the prompt change should ship as planned
K: B
G: ## Reading per-case results
The exam guide asks for per-case analysis and for feedback loops that add production cases. A localized drop tells you where the change hurt.
## Action
- Isolate the case type; inspect traces for those cases.
- Fix narrowly: a rule, an example or a retrieval adjustment for that type.
- Re-run: the type recovers without disturbing the rest.
Example: the new cases are multilingual tickets; the prompt change removed a language instruction; restoring it fixes them.
W: A type-specific regression identified by the new cases: the suite worked, and the fix is targeted.
X: A=Revert everything: the change is fine for 95% of cases; targeted repair keeps the benefit.
C=Remove cases: deleting the evidence does not fix the behaviour.
D=Nothing: the per-case analysis shows the entire drop concentrated in one case type, which is a clear, actionable finding.
T: Localize regressions by case type with per-case analysis and fix narrowly.

@ PLTR-AIE D5 T5.4 applied use-case
S: A workflow's outputs are reviewed by a human team who approve or edit them before release. The team wants to use the edits to improve the workflow. What should be recorded to make that possible?
A: Only whether each output was approved or edited, since the edits themselves are too varied to analyze in any systematic way
B: Original output, edited output, diff, reviewer, reason category and input reference, so edits become evaluation cases
C: A weekly count of how many outputs were edited, which indicates whether the workflow's quality is improving over time
D: The reviewers' general impressions of the workflow's quality, gathered in a monthly meeting and written up as notes
K: B
G: ## Edits as labelled corrections
The exam guide asks for feedback loops that capture user corrections. An edit is a before/after pair with ground truth.
## Record
- Original and edited output; the diff.
- Reviewer and optional reason category (tone, factual, missing field).
- Input reference for reproduction.
- Pipeline: cluster diffs by pattern; convert recurring patterns into evaluation cases and instruction changes.
Example: 40% of edits shorten the opening sentence; an instruction and 30 cases fix it; edit rate halves.
W: Full before/after records with context: edits become analyzable, reproducible improvements.
X: A=Approval only: a flag says an output needed changing but nothing about what was wrong or how to fix it.
C=Edit count: a trend line without any indication of what the edits were, so nothing can be targeted.
D=Impressions: unstructured recollections cannot be reproduced as test cases or linked to specific inputs.
T: Record original, edited output and context so human edits drive evaluation and improvement.

@ PLTR-AIE D5 T5.1 applied tradeoff
S: An evaluation suite's groundedness evaluator is a model that reads the answer and the retrieved context. The team notices it marks answers grounded when the context merely mentions the topic. What should change?
A: Accept it, since topic overlap is a reasonable proxy for groundedness
B: Tighten it: require claim-level support traced to passages, calibrate against human judgements, track agreement
C: Replace the model-based evaluator with exact string matching between the answer and the retrieved context passages
D: Remove groundedness from the suite since it is hard to measure
K: B
G: ## Evaluator rigour
The exam guide asks for calibrated evaluators and measures groundedness distinctly from correctness. A lax grader produces false confidence.
## Improvement
- Claim decomposition: split the answer into claims; each needs a supporting passage.
- Explicit criteria and examples of unsupported-but-related answers.
- Calibration: human-labelled sample; agreement target; periodic re-check.
Example: the tightened evaluator drops groundedness from 95% to 81%, revealing that many answers added facts beyond the context.
W: Claim-level support with calibration: groundedness measures what it should, and the number becomes trustworthy.
X: A=Accept proxy: unsupported answers pass; the metric is meaningless.
C=Exact matching: correct paraphrases fail; too strict in the wrong way.
D=Remove: groundedness is central for a retrieval-grounded system.
T: Make groundedness evaluators claim-level and calibrate them against humans.

@ PLTR-AIE D5 T5.2 applied use-case
S: A team builds an evaluation suite for an agent with three tools. Which case design verifies tool use properly?
A: Cases that only check the final answer text, since a correct answer implies that the agent must have used its tools correctly
B: Cases with expected tool-call sequences (including no-tool cases), asserting on tools, arguments and resulting state
C: Cases that count the number of tool calls and pass if the count is below three
D: Cases that check latency, since tool misuse makes the agent slower
K: B
G: ## Testing tool use explicitly
The exam guide lists tool selection among behaviours to measure and asks for checks on resulting object state for Actions.
## Case design
- Expected calls: tool names, order where it matters, key arguments.
- Negative cases: questions that must not trigger a tool.
- Write tools: assert on the object after the run.
- Answer check as well.
Example: "cancel order 118" expects one call to the cancel Action with id 118 and the order's status changed; "what is your return policy" expects no tool call.
W: Expected call sequences, no-tool cases and state assertions: tool behaviour is verified directly.
X: A=Answer only: a right answer via wrong or unnecessary tools goes undetected.
C=Call count: a crude proxy that says nothing about which tools or arguments.
D=Latency: a fast run can call the wrong tool and a slow one the right tool; timing does not verify behaviour.
T: Assert on tool calls, arguments and resulting state, not just on the final answer.

@ PLTR-AIE D5 T5.3 applied use-case
S: A function's suite is run before every release, but regressions still reach production in areas the suite does not cover. What practice closes the gap?
A: Running the suite more often, such as on every commit, since higher frequency catches more regressions before release
B: Expand coverage systematically: map production traffic by category, add cases for uncovered categories and incidents, track coverage
C: Replacing the evaluation suite with a bigger model that makes fewer mistakes, so that regressions become rare enough to ignore
D: Asking users to test the function before each release
K: B
G: ## Coverage, not frequency
A suite only catches what it contains. The exam guide asks for representative suites and production feedback loops.
## Practice
- Traffic analysis: categories of real requests and their shares.
- Coverage map: which categories have cases, which do not.
- Fill gaps; add incident cases as they occur.
- Coverage metric reported with the score.
Example: 30% of traffic is "multi-document comparison" with zero cases; 40 cases are added and the next regression in that area is caught pre-release.
W: Coverage mapping against production traffic plus incident cases: the suite grows where regressions were escaping.
X: A=More often: the suite has the same blind spots however often it runs; frequency does not add coverage.
C=Bigger model: a different model still needs testing, and the suite's gaps would hide its regressions just as well.
D=Users as testers: production exposure is the problem, not a solution.
T: Measure and expand evaluation coverage against real traffic and incidents.

@ PLTR-AIE D5 T5.4 advanced tradeoff
S: Stakeholders want a single quality score published weekly. The engineer worries it will hide important trade-offs. What is a sound reporting design?
A: Publish only the single score, since stakeholders asked for simplicity
B: Publish a headline score with its components visible beneath it and release gates per component, so no single number masks a regression
C: Refuse to publish any score, since all metrics are misleading
D: Publish the single score but adjust its definition whenever a component regresses, so that the headline remains stable over time
K: B
G: ## Headline plus components
The exam guide lists multiple metrics and warns against conflating them. A headline number is fine if it is transparent and gated.
## Design
- Weighted headline with a published formula.
- Components displayed with trends.
- Gates: safety and groundedness must not fall below thresholds regardless of headline.
Example: the headline rises 2 points while groundedness falls below its gate; the release is held and the report shows why.
W: Transparent headline with components and per-component gates: simple for stakeholders, honest for engineering.
X: A=Single score only: a safety regression can hide behind an accuracy gain.
C=Refuse: stakeholders need signal; the answer is transparency.
D=Moving definition: changing the formula to keep the number flat destroys comparability across weeks and the trust of everyone reading it.
T: Report a headline score with visible components and per-component release gates.
