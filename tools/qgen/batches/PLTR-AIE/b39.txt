# PLTR-AIE batch 39: Domain 6 round 5 (Automation, Orchestration, and Integration), 8 questions

@ PLTR-AIE D6 T6.1 applied use-case
S: A compliance process requires that every new Contract object be screened by an AI function within an hour of creation, and that a screening record be stored even when the screening finds nothing. Which automation design meets both requirements?
A: A weekly schedule that screens all contracts created during the week and writes records only for the ones that were flagged by the screening function
B: An object-creation trigger that runs the screening and always writes a ScreeningResult via an Action, with an alert if any contract lacks a result after an hour
C: A manual screening by the compliance officer whenever they have time during the week, with a note added only to the contracts they decided to flag
D: A nightly batch that screens the day's contracts and emails the officer a list of flagged ones without creating any records
K: B
G: ## Event-driven screening with a complete record
The exam guide asks for triggers matched to latency and for auditable workflows. A one-hour requirement means an event trigger; "record even when nothing is found" means the Action always writes.
## Configuration
- Trigger: Contract created.
- Effects: screening function → Action creating ScreeningResult (outcome, flags, version, time), unconditionally.
- Monitoring: contracts older than an hour without a result raise an alert.
Example: 120 contracts created today each have a ScreeningResult, 117 clear and 3 flagged, all within minutes.
W: Object-creation trigger with an unconditional result write and a freshness alert: the time and completeness requirements are both met and monitored.
X: A=Weekly, flagged only: misses the hour requirement and leaves no record for cleared contracts.
C=Manual: screening depends on the officer's availability, so the hour requirement is unmet, and cleared contracts get no record.
D=Nightly email: misses the hour requirement and creates no stored records at all.
T: Use event triggers for time-bound per-object processing and always write an auditable result object.

@ PLTR-AIE D6 T6.2 applied troubleshooting
S: A chained workflow (extract → validate → write) occasionally writes stale values because the validate step reads an object property that another automation updates concurrently. What design change prevents the race?
A: Adding a random delay of a few seconds before the write step so that the other automation usually finishes first and the race rarely occurs
B: Making the write conditional on the version read at validation time (an optimistic check in the Action), re-validating if the object changed
C: Disabling the other automation that updates the property, so that this workflow is the only process ever writing to the object
D: Running the workflow only at night when the other automation is less active, so the two rarely touch the same object at the same time
K: B
G: ## Concurrency between automations
The exam guide asks for workflows that stay safe under concurrent and in-flight changes. A race is resolved with a consistency check at the write, not with timing tricks.
## Design
- Capture the object's version (or relevant properties) during validation.
- The Action's precondition compares the current version with the captured one; mismatch → reject and re-validate.
- Alternatively serialize the two automations on the same object.
Example: the write is rejected once in a hundred runs because the status changed meanwhile; the workflow re-validates and writes correctly.
W: Optimistic version checks in the Action with re-validation: stale writes cannot happen, and the workflow self-corrects.
X: A=Random delay: reduces the frequency of the race; does not prevent it.
C=Disable the other automation: it maintains the property for its own business reason; removing it trades one problem for another.
D=Night only: the other automation may run at night too, and latency suffers.
T: Prevent races between automations with version checks at the write and re-validation on conflict.

@ PLTR-AIE D6 T6.3 applied use-case
S: A team must temporarily pause an AI automation during a data migration and resume it afterwards without losing or duplicating any objects created during the pause. What should be in place?
A: Deleting the automation before the migration and recreating it from scratch afterwards with the same configuration
B: A pause with backlog identifiable by object state, idempotent processing, and a resume that processes the backlog once and verifies
C: Nothing special; objects created during the pause are simply skipped, since the migration is short and a small gap is acceptable
D: Asking all users by email not to create any objects during the migration window, so that there is no backlog to process afterwards
K: B
G: ## Pausing safely
The exam guide asks for safe modification of live workflows with attention to in-flight work and duplicates. A pause must be resumable without gaps or repeats.
## Design
- Pause: disable the trigger; objects keep arriving.
- Backlog: identified by state (for example, objects without a result record).
- Resume: process the backlog with idempotent writes; then re-enable the live trigger.
- Verify: no object without a result.
Example: 340 objects created during a 3-hour migration are processed in one backlog run; counts reconcile.
W: Resumable pause with state-based backlog, idempotent processing and verification: nothing is lost or duplicated.
X: A=Delete and recreate: loses configuration and history; the backlog is still unprocessed.
C=Skip: a compliance or business process that must cover every object cannot have a gap; those objects would never be processed.
D=Ask users: some users will not see the email and integrations keep creating objects; a request is not a control.
T: Pause automations with a plan to process the backlog idempotently on resume.

@ PLTR-AIE D6 T6.1 applied comparison
S: Which Automate configuration is most appropriate for "re-run the risk assessment whenever a Supplier's financial rating property changes, but not when other properties change"?
A: A trigger on any Supplier property change at all, with the function re-assessing every supplier in the Ontology on every single edit
B: A trigger scoped to changes of the financial rating property, running the assessment for the changed supplier only, with a loop guard
C: A daily schedule that re-assesses all suppliers regardless of whether any rating changed, so nothing is ever missed
D: A manual button in the supplier application that an analyst clicks after noticing that a supplier's rating has changed
K: B
G: ## Property-scoped triggers
The exam guide asks for triggers that avoid unnecessary executions and loops. The condition names the property explicitly.
## Configuration
- Trigger: `financial_rating` changed on a Supplier.
- Scope: that supplier only.
- Guard: the assessment writes to different properties, or skips when the change came from itself.
Example: a rating downgrade on one supplier re-runs one assessment; an address edit on another runs nothing.
W: Trigger on the specific property with per-object scope and a loop guard: exactly the requirement, nothing more.
X: A=Any change, all suppliers: massive unnecessary work and a loop risk.
C=Daily for all: a rating downgrade waits up to a day, and thousands of unchanged suppliers are re-assessed needlessly.
D=Manual: rating changes are noticed late or not at all; the re-assessment depends on an analyst's attention.
T: Scope automation triggers to the property that matters and guard against self-triggering.

@ PLTR-AIE D6 T6.3 applied troubleshooting
S: An automation's AI step started failing after a prompt variable was renamed in the function, but the automation kept "succeeding" because the function returned an empty default. Which safeguards were missing?
A: None; returning an empty default when a variable is missing is a reasonable, defensive way to keep an automation from failing
B: A failure (not a default) on a missing required variable, output validation rejecting empties, evaluation before publishing, consumer notice
C: A longer timeout on the automation's AI step, so that the function has more time to find the renamed variable before giving up
D: A bigger model for the AI step, which would be more tolerant of a missing or renamed variable in its prompt
K: B
G: ## Fail loudly on contract breaks
The exam guide asks for versioned, evaluated changes and workflows that remain safe when a step misbehaves. A renamed variable is a contract change; silent defaults hide it.
## Safeguards
- Function: missing required input → error, not default.
- Automation: validate non-empty, well-formed results; route failures.
- Release: evaluation suite on the change; version bump; consumers informed.
Example: the renamed variable would have failed the suite and the automation's validation on the first run, instead of three days of empty outputs.
W: Loud failures, output validation and evaluated, communicated changes: the silent breakage becomes impossible.
X: A=Defaults are fine: a default for a required input converts a bug into bad data.
C=Timeout: the function returned quickly with an empty default; time was never the issue, and a longer wait changes nothing.
D=Bigger model: the variable was never injected; no model can produce the right output from a prompt that lacks the input.
T: Required inputs fail when missing; validate outputs; evaluate and announce contract changes.

@ PLTR-AIE D6 T6.2 applied use-case
S: A Workshop form lets users request an AI-generated report that takes about two minutes and must be stored on the request object. Users should not have to keep the form open. What is the right integration?
A: A synchronous function call from the submit button that holds the form open and shows a spinner until the two-minute report is ready
B: A submit Action creating a pending ReportRequest; an automation generates the report, writes it with status complete, and notifies the user
C: Emailing the user a link so that they can run the generation function themselves later, at a time when they can wait for it
D: Generating the report in the user's browser with a client-side model so that the server is never involved and the page stays responsive
K: B
G: ## Request objects and asynchronous completion
The exam guide recommends asynchronous execution for long work with status visibility, and integration through Actions and automations.
## Design
- Action: create the request (inputs captured, status pending).
- Automation: generate, write, update status; failures set status failed with reason.
- Notification on completion; the form can be closed meanwhile.
Example: the user submits and goes to lunch; the report is on the request object when they return, with a notification.
W: Request object plus automation with status and notification: long work completes reliably without holding the user.
X: A=Synchronous: a two-minute frozen form, lost if the user navigates away.
C=User runs it later: the user still has to wait two minutes somewhere; the system should do the work and tell them when it is done.
D=Browser: the model, the data and the write to the request object all live server-side; a client-side model cannot do this.
T: Model long AI requests as objects processed by automations with status and notification.

@ PLTR-AIE D6 T6.1 applied tradeoff
S: An automation processes 50,000 objects every morning with an AI function, and the model provider's rate limit causes a third of runs to fail with throttling. What should change?
A: Nothing; the runs that fail with throttling are simply retried the next morning along with that day's objects
B: Batch execution with controlled concurrency and rate limiting (a paced code step), with failed items retried in the same window
C: Triple the number of parallel executions so that the morning run finishes faster and the throttled calls are retried sooner
D: Switch to a different model provider every morning, rotating between three so that no single provider's limit is reached
K: B
G: ## Rate-aware orchestration
The exam guide lists execution modes and rate limiting among orchestration concerns. Per-object parallel execution ignores provider limits.
## Design
- Batch mode or a paced code step: calls per second bounded below the limit.
- Backoff on throttling; failed items recorded and retried in-window.
- Monitoring: throughput and failure rate.
Example: 50,000 calls paced at 90% of the limit complete in 2.5 hours with zero throttling failures.
W: Paced batch execution with retries: the limit is respected and the morning run completes.
X: A=Next-day retries: a third of objects wait a day, then throttle again.
C=More parallelism: the provider's limit is fixed; tripling concurrency triples the throttling and fails even more runs.
D=Provider roulette: daily switching gives inconsistent outputs and still ignores each provider's limit; it is not a design.
T: Pace high-volume AI automations against provider limits with batched, rate-limited execution.

@ PLTR-AIE D6 T6.3 advanced use-case
S: A critical automation chain spans three teams' functions. A change in any one of them could break the chain. What operating practice reduces this risk?
A: Freezing all three functions permanently so that none of the teams can change anything that might affect the chain
B: Contract tests at each boundary, versioned functions with pinned consumers, a shared end-to-end regression, and clear ownership
C: Reorganizing so that a single team owns all three functions and the chain, removing the need for coordination
D: Relying on the three teams to coordinate informally in chat before they make changes, as they mostly do today
K: B
G: ## Cross-team orchestration discipline
The exam guide asks for versioning, evaluation and clear ownership in orchestration. A multi-team chain needs explicit contracts and shared tests.
## Practice
- Typed contracts at each boundary; contract test cases.
- Version pinning; upgrades are deliberate.
- End-to-end regression run of the chain pre-release.
- Ownership and alert routing per step; runbooks.
Example: team B's change fails the contract test with team C's cases before release, and the fix is made before anything ships.
W: Boundary contracts, version pinning, end-to-end regression and clear ownership: changes in one team cannot silently break the chain.
X: A=Freeze forever: the functions serve changing business needs; a permanent freeze blocks every improvement to avoid coordination.
C=One team: organizational fantasy; the contract discipline is what matters.
D=Informal hope: a chat message before a change is easily missed; it is not a practice that catches a broken contract.
T: Operate multi-team AI chains with contract tests, version pinning and end-to-end regression.
V: AIP Logic, Automate, AIP Evals
