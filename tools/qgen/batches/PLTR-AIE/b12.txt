# PLTR-AIE batch 12: Domain 3 round 2 (RAG Architecture and Semantic Search), 8 questions

@ PLTR-AIE D3 T3.1 applied use-case
S: A team is choosing metadata to store with each chunk of its HR policy documents. Which set of metadata most improves retrieval and answer quality for policy questions?
A: Only the chunk text, since the embedding already captures everything the retriever needs to rank chunks correctly
B: Section heading, effective date and version, the country or entity the policy applies to, and a document identifier for citations
C: The name of the engineer who uploaded the document and the upload timestamp, which help trace who added each chunk and when it entered the index
D: A model-generated summary of the whole document attached to every chunk, so each chunk carries the document's overall meaning
K: B
G: ## Metadata makes retrieval precise and traceable
The exam guide lists metadata among chunking and retrieval design choices. Embeddings rank by similarity; metadata lets the workflow filter, prefer and cite.
## Useful fields
- Section heading: keeps a chunk's meaning attached ("Parental leave: eligibility").
- Effective date and version: filter superseded policies; answer "as of" questions.
- Applicability (country, entity): avoid answering with another jurisdiction's rule.
- Document id and section: citations the user can check.
Example: "maternity leave in Germany" filters to country = DE and current version, then ranks by similarity within that set.
W: Headings, dates and versions, applicability and identifiers: each field solves a retrieval or citation problem that similarity alone cannot.
X: A=Text only: no way to filter by jurisdiction or currency or to cite; stale and foreign chunks compete on similarity.
C=Uploader and timestamp: operational provenance, but it does not help choose the right policy chunk for a question.
D=Document summary on every chunk: it dilutes each chunk's specific meaning and adds tokens without enabling filters.
T: Store metadata that enables filtering (applicability, version), freshness and citations alongside each chunk.
V: Ontology, semantic search

@ PLTR-AIE D3 T3.2 applied tradeoff
S: A retrieval workflow returns the top 10 chunks by similarity. For some questions the tenth chunk has a similarity far below the first, yet it is still injected and sometimes misleads the answer. What is the appropriate refinement?
A: Always inject exactly 10 chunks, since a fixed number keeps the prompt size predictable for cost planning
B: Apply a relevance threshold or drop-off rule to exclude weak chunks, and measure answer quality with and without it
C: Inject only the single best-scoring chunk for every question, since the top result is nearly always the correct one and the rest add cost
D: Replace similarity scores with document recency so the most recently updated chunks are injected first
K: B
G: ## Thresholds in context selection
The exam guide names thresholds and context selection among the stages to tune and asks you to balance precision, recall and token limits. A fixed top-k ignores how relevant the k-th chunk actually is.
## Options
- Absolute threshold: exclude chunks below a similarity score.
- Relative drop-off: stop when the score falls far below the best.
- Cap plus threshold: at most 10, and only above the bar.
- Validate on the evaluation set: ensure recall does not fall for questions that genuinely need many chunks.
Example: a question answered by one strong chunk now gets one or two chunks; a multi-part question still gets eight.
W: Threshold or drop-off with measured impact: it removes misleading weak chunks while the evaluation confirms recall is preserved.
X: A=Always 10: predictable cost is not worth injecting chunks known to be irrelevant.
C=Top-1 only: multi-part and comparative questions need several chunks; recall collapses.
D=Recency instead of similarity: recency is a useful filter, not a replacement for relevance ranking.
T: Select context by relevance threshold, not by a fixed count alone, and verify recall on the evaluation set.
V: semantic search, AIP Evals

@ PLTR-AIE D3 T3.3 applied troubleshooting
S: Users of a technical assistant report that answers to questions phrased with product code names ("XR-7 throughput") are poor, while the same questions phrased in plain words ("throughput of the 7th generation router") work well. What is the likely cause and the fix?
A: Codes embed poorly because the documents use plain names; add a code-to-name mapping (query expansion or metadata filter) for code queries
B: The users are asking badly formed questions; add instructions telling the model to ask users to rephrase in plain words whenever a code appears
C: The documents are chunked too finely; merge chunks so that each contains both the code and the plain name
D: The model is too small to understand codes; switch to a larger generation model
K: A
G: ## Vocabulary mismatch in retrieval
Embeddings capture meaning from text; an opaque code like "XR-7" carries little semantic signal unless the documents use it. If documents say "7th generation router", a query with the code lands far from them in vector space. This is a retrieval-stage failure, which the exam guide asks you to diagnose and fix at the right stage.
## Fixes
- Query expansion: map codes to names before embedding the query.
- Metadata: tag chunks with product codes and filter on them.
- Hybrid search: combine keyword matching for codes with semantic ranking.
Example: "XR-7 throughput" becomes "XR-7 (7th generation router) throughput" plus a product filter; retrieval hit rate on code queries rises to match plain queries.
W: Code-to-name mapping or metadata filter: it bridges the vocabulary gap at retrieval, which is where the failure occurs.
X: B=Blame the users: product codes are how engineers talk; the system must handle them.
C=Merge chunks: chunk size is not the issue; the code is absent from the text entirely.
D=Larger generator: the model never receives the right chunks; generation cannot fix retrieval.
T: When queries use vocabulary the documents do not, fix retrieval with expansion, metadata or hybrid search.
V: semantic search

@ PLTR-AIE D3 T3.1 applied use-case
S: A company has 50,000 PDF manuals. The team must build the chunk objects for semantic search. Which pipeline design is appropriate?
A: A pipeline that extracts text, chunks by section with metadata, embeds, writes chunk objects with vector properties, and reruns incrementally
B: A manual process where an engineer pastes each manual into the assistant once and asks it to remember the content for all future conversations
C: A single embedding per manual produced in a notebook and uploaded as a dataset when someone remembers
D: An agent that reads a manual on demand when a user asks about it, so no index is needed
K: A
G: ## Building the retrieval corpus as a pipeline
Retrieval needs a maintained index. The exam guide places reusable enrichment (text extraction, chunking, embedding) in the pipeline layer, with chunk objects carrying vector properties.
## Stages
- Extract text (OCR for scanned pages).
- Chunk by sections with metadata (manual, product, revision).
- Embed with the model that queries will use.
- Write chunk objects; vector property for semantic search.
- Incremental: changed or new manuals re-chunk and re-embed; superseded chunks removed.
Example: 50,000 manuals become about two million chunk objects, refreshed nightly for the handful of manuals that changed.
W: Extract, chunk, embed, write objects, incrementally: this produces a governed, current index that the assistant can search.
X: B=Paste and remember: agents have no persistent memory of pasted documents, and 50,000 manuals cannot be pasted.
C=One embedding per manual: too coarse for specific questions and not maintained.
D=Read on demand: a 300-page manual per question is slow and costly, and users must know which manual to ask about.
T: Build and maintain the retrieval corpus with a pipeline that chunks, embeds and writes vector-bearing objects incrementally.
V: Pipeline Builder, Ontology vector properties

@ PLTR-AIE D3 T3.2 applied tradeoff
S: A compliance assistant must only cite documents that are currently in force. The corpus contains current and archived versions because auditors sometimes ask about past rules. How should retrieval be designed?
A: Remove archived versions from the corpus entirely so that only current documents can ever be retrieved, and refer auditors to the archive team
B: Keep both with status and effective-date metadata; default retrieval filters to current, and an "as of date" mode filters to that date
C: Keep both and let the model decide which version is current based on the text of the chunks
D: Keep both and rank current documents slightly higher so they usually win
K: B
G: ## Freshness as a filter, not a hope
The exam guide lists freshness among retrieval criteria and asks you to balance it against other needs. Two audiences need different time scopes; metadata lets one corpus serve both.
## Design
- Metadata: `status` (current/archived), `effective_from`, `effective_to`.
- Default mode: filter status = current.
- Historical mode: filter effective range containing the requested date.
- Citations include the version, so answers are auditable.
Example: "what is the retention rule?" uses current only; "what was the retention rule in 2024?" filters to versions in force then.
W: Metadata-driven filters with a default on current: compliance answers cite only in-force rules while auditors can still ask about the past.
X: A=Delete archives: the auditors' requirement to ask about past rules is lost, and a question about a 2024 rule gets today's rule or nothing.
C=Model decides: the model cannot reliably tell which chunk is current from text alone; outdated rules will be cited.
D=Rank slightly higher: "usually" is not acceptable for compliance; an archived chunk can still win on similarity.
T: Enforce freshness with metadata filters and explicit modes, not with ranking tweaks or model judgement.
V: semantic search, Ontology

@ PLTR-AIE D3 T3.3 applied troubleshooting
S: After a retrieval change, the retrieval evaluation shows recall improved from 85% to 95%, but end-to-end answer accuracy dropped from 88% to 80%. What is the most likely explanation?
A: The evaluation suite is broken and must be rebuilt from scratch before any conclusion can be drawn
B: Higher recall came with more chunks, adding noise or conflict the generator handles worse; check precision and context size and adjust ranking
C: The generation model was silently downgraded by the provider at the same time, so the retrieval change is unrelated to the accuracy drop
D: Higher recall always reduces accuracy, so the retrieval change should be fully reverted
K: B
G: ## Recall is not the whole story
More retrieved chunks raise the chance the right one is included (recall) and also the chance that wrong, duplicate or conflicting chunks are included (lower precision). The exam guide warns that more context can add noise and conflict, and asks you to measure each stage.
## Investigation
- Compare the number and relevance distribution of injected chunks before and after.
- Inspect failing cases: does the context contain contradictory chunks?
- Adjust: keep the recall gain but rerank or threshold so the generator sees fewer, better chunks; re-measure end to end.
Example: recall stays at 94% with 6 chunks instead of 15 after reranking, and answer accuracy returns to 90%.
W: Noise from higher recall harming generation: it explains both numbers, and the fix is to restore precision in context selection while keeping the recall gain.
X: A=Suite broken: the two metrics moved in a consistent, explainable way; nothing suggests the suite is wrong.
C=Provider downgrade: possible, but the simpler explanation is the change that was made; verify the model version in traces before assuming coincidence.
D=Always reduces accuracy: recall gains are good when precision is maintained; full reversion throws away the improvement.
T: When recall rises but answers get worse, the context got noisier; fix precision and context size rather than reverting.
V: AIP Evals, semantic search

@ PLTR-AIE D3 T3.1 applied use-case
S: An assistant must answer questions about customer contracts, and each customer's contracts are confidential to the account team. The corpus contains contracts for all customers. How must the index and retrieval be structured?
A: One shared index with a note in the system prompt that the model must not disclose other customers' contracts
B: Chunk objects that inherit their source contract's permissions, with retrieval executed as the user so only authorized chunks return
C: A separate assistant deployment per customer, each with its own hand-maintained document set
D: A shared index with the customer name stripped from every chunk before embedding so that retrieved chunks cannot be attributed to a customer
K: B
G: ## Authorization at the chunk level
Retrieval must only return authorized evidence. When chunks are Ontology objects, they can inherit the permissions of the source document (via the backing dataset's markings and restricted views), and queries run as the user. The exam guide's security scenario is exactly this: fix access at the retrieval and data boundary.
## Design
- Chunk objects reference their contract and inherit its access controls.
- Semantic search runs as the user; unauthorized chunks are not returned.
- Verify with tests: a user from account team A asks about customer B's contract and gets nothing.
Example: two account managers ask the same question and receive chunks only from their own customers' contracts.
W: Permission-carrying chunks with user-scoped retrieval: confidentiality is enforced structurally and tested, in one corpus.
X: A=Prompt note: the model has already received the other customer's chunk; prompts do not enforce access.
C=Per-customer deployments: unmaintainable at scale and still requires correct per-user access to each deployment.
D=Strip names: chunks remain attributable from their content, and the real control (permissions) is absent.
T: Carry source permissions on chunk objects and retrieve as the user; never rely on prompts or anonymization for confidentiality.
V: Ontology, restricted views

@ PLTR-AIE D3 T3.2 advanced tradeoff
S: An assistant answers from both a semantic index of manuals and exact lookups of part numbers. Users complain that part-number questions ("What is part 88-1204?") sometimes return parts with similar numbers. Which retrieval design fixes this?
A: Increase the number of semantic results returned for part-number questions so the exact part is more likely to be somewhere among them
B: Route questions with a part-number pattern to an exact Ontology lookup on the identifier, and use semantic search for descriptive questions
C: Re-embed the part catalogue with a larger embedding model so that similar numbers become more distinguishable
D: Ask users to describe the part in words instead of using numbers
K: B
G: ## Exact lookups versus semantic search
Semantic search ranks by meaning; "88-1204" and "88-1240" are nearly identical to an embedding model. For identifiers, exact matching on a property is both faster and correct. The exam guide includes context-injection strategy and metadata in retrieval design; routing by query type is part of that.
## Design
- Detect identifier patterns in the query.
- Exact query: Part object where `part_number = '88-1204'`.
- Otherwise: semantic search over manual chunks.
- Both results can be injected when a question mixes the two.
Example: "What is part 88-1204 and how do I replace it?" fetches the exact Part object and the replacement procedure chunk.
W: Route identifiers to exact Ontology lookups: identifiers are not semantic, so the right tool is an exact query, and descriptive questions keep semantic search.
X: A=More semantic results: similar numbers still rank together; the error does not go away with volume.
C=Bigger embedding model: embeddings are not designed to distinguish near-identical codes; the approach is wrong, not the size.
D=Describe instead: users know the number; forcing descriptions is worse for them and for accuracy.
T: Use exact property lookups for identifiers and semantic search for meaning; route queries accordingly.
V: Ontology, semantic search
