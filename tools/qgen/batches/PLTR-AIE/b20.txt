@ PLTR-AIE D3 T3.1 applied tradeoff
S: A team debates chunk overlap for a manual corpus. One engineer wants zero overlap to save storage; another wants 50% overlap "to be safe". What is the sound position?
A: Zero overlap is always correct because duplicated text confuses the retriever and doubles the cost of every search over the index
B: A modest overlap helps when answers span a boundary, while large overlaps add near-duplicates; pick the value by measuring retrieval quality
C: Maximum overlap is always correct because it guarantees that every answer will be found inside at least one chunk regardless of boundaries
D: Overlap is irrelevant to retrieval quality, so the choice should be made purely on storage cost and the engineer's personal preference
K: B
G: ## Overlap as a tunable
Chunk boundaries can split a sentence or a step; a small overlap keeps context intact at the edges. Large overlaps create many near-identical chunks that crowd the top results. The exam guide asks you to design chunking strategies and measure improvement.
## Practice
- Start with section-aware chunking so boundaries fall at natural breaks.
- Add a small overlap; evaluate retrieval hit rate and answer quality; adjust.
- Deduplicate near-identical chunks in results if overlap is used.
Example: a 10% overlap raised boundary-case recall from 78% to 90% with negligible storage growth; 50% overlap produced duplicate-heavy result lists.
W: Modest overlap chosen by measurement: it captures the benefit at boundaries without flooding results with duplicates.
X: A=Zero always: boundary-spanning answers are lost; "always" ignores the measurable trade-off.
C=Maximum always: near-duplicate chunks dominate results and waste context tokens.
D=Irrelevant: overlap affects recall at boundaries and result diversity; it is a retrieval parameter.
T: Use small overlaps chosen by evaluation, with section-aware boundaries.
V: semantic search

@ PLTR-AIE D3 T3.2 applied troubleshooting
S: A retrieval workflow has a latency budget of 500 ms. Vector search over 50 million chunks takes 400 ms, leaving no room for reranking. Which design addresses this without discarding reranking?
A: Remove reranking entirely and accept whatever order the vector search returns, since there is no time left in the latency budget for it
B: Narrow the search space with metadata filters first so the vector search covers far fewer candidates, leaving time to rerank
C: Increase the latency budget to two seconds so that the full search and reranking both fit comfortably
D: Rerank before the vector search so the expensive step happens on a smaller input set
K: B
G: ## Filter, then search, then rerank
Searching the whole corpus is the most expensive design. The exam guide asks you to balance precision, recall and latency and to use metadata in retrieval design.
## Approach
- Metadata filters applied before similarity search cut the candidate set by orders of magnitude.
- Vector search over the filtered set is fast.
- Reranking the top 30 fits easily in the remaining budget.
Example: filtering to the product named in the question reduces 50 million chunks to 200,000; search takes 40 ms and reranking 60 ms.
W: Pre-filtering by metadata: it makes both search and reranking affordable within the budget while keeping precision.
X: A=Drop reranking: precision suffers; the budget problem has a structural fix.
C=Raise the budget: the requirement is 500 ms; changing requirements is not engineering.
D=Rerank first: reranking needs candidates; it cannot run before retrieval.
T: Apply metadata filters before similarity search to make retrieval fast enough to afford reranking.
V: semantic search, Ontology

@ PLTR-AIE D3 T3.3 applied troubleshooting
S: Answers from a RAG assistant are usually right but occasionally contain a fact from a different, unrelated document that was retrieved with a low score. What change reduces this?
A: Remove the retrieval stage entirely and rely on the model's training knowledge, so that unrelated documents can never be retrieved and leak
B: Add a relevance threshold, label injected chunks with source and score, instruct the model to cite, and verify with groundedness evaluation
C: Retrieve twice as many chunks so that the relevant ones outnumber the unrelated ones in the context
D: Lower the model's temperature to zero so that it only uses the first chunk in the context
K: B
G: ## Low-relevance leakage
A weak chunk in the context is still text the model may use. The exam guide asks you to diagnose whether poor answers come from thresholds, context selection or generation, and to inspect retrieved context.
## Fixes
- Threshold: exclude chunks below a relevance score.
- Attribution in context: source and score per chunk; instructions to rely on strong evidence and cite.
- Groundedness evaluation: catches answers that use unsupported chunks.
Example: after thresholding, the unrelated manual's chunk is no longer injected, and the cited answers point to the right document.
W: Threshold plus attributed context and groundedness checks: weak chunks are excluded, and remaining use of evidence is visible and measured.
X: A=No retrieval: the assistant loses its grounding; hallucinations rise.
C=More chunks: more weak chunks enter the context; leakage gets worse.
D=Temperature zero: determinism does not stop the model from using a chunk that is present.
T: Keep weak chunks out of context with thresholds and make evidence use visible and measurable.
V: semantic search, AIP Evals

@ PLTR-AIE D3 T3.1 applied use-case
S: A multilingual company has manuals in English, German and Japanese. Users ask questions in any of the three languages and expect answers from any manual. How should the retrieval index be designed?
A: Three separate indexes, one per language, with users required to pick the language of the manual they want to search before asking
B: A multilingual embedding model so queries and chunks share one vector space across languages, with language as metadata
C: Translate every manual into English with a model and index only the English versions so a single-language setup can be used
D: Index only the English manuals, since most users can read English and this keeps the corpus small and consistent
K: B
G: ## Cross-lingual retrieval
If the embedding model is multilingual, a German question can retrieve a Japanese chunk about the same topic. The exam guide asks you to design embedding strategies and metadata.
## Design
- Multilingual embedding model for both indexing and queries (same model, as always).
- Language metadata to filter or prefer when a user wants a specific language.
- Generation can answer in the user's language from chunks in another.
- Evaluate per language pair.
Example: a Japanese question about torque values retrieves the German manual's chunk and the answer is given in Japanese.
W: Multilingual embeddings with language metadata: one index serves all languages and cross-lingual questions work.
X: A=Separate indexes with manual choice: users may not know which manual holds the answer; cross-lingual retrieval is lost.
C=Translate everything: expensive, lossy for technical terms, and still needs query translation.
D=English only: German and Japanese manuals contain unique content; excluding them loses answers.
T: Use a multilingual embedding model with language metadata for mixed-language corpora.
V: semantic search

@ PLTR-AIE D3 T3.2 applied tradeoff
S: An assistant must answer questions over both a knowledge base and the user's own recent uploads (not yet in the main index). Which context strategy fits?
A: Ignore the uploads until the nightly pipeline indexes them, so that all retrieval comes from one consistent index
B: Chunk and embed the uploads into a session-scoped index on the fly, merge its results with the main index, and keep provenance
C: Inject the full text of every upload into every prompt for the rest of the session, since uploads are small compared with the knowledge base
D: Replace the main index with the uploads for the session, since the user's own documents are what they care about most
K: B
G: ## Session-scoped retrieval
Not all evidence is in the main index yet. The exam guide covers context-injection strategy and freshness; a session-scoped index handles fresh, user-specific documents without waiting for the pipeline.
## Design
- Uploads chunked and embedded at upload time (same model), stored per session or per user with the user's permissions.
- Retrieval merges main-index and session-index results, with source labels.
- Session data expires or is promoted to the main index through the governed pipeline.
Example: the user uploads a new supplier contract and asks about its payment terms; the answer cites the upload, not the older contract in the main index.
W: Session-scoped index merged with the main index, with provenance: fresh user documents are searchable immediately and attribution stays clear.
X: A=Wait for nightly: the user needs answers about the upload now.
C=Full text every prompt: uploads grow, and the prompt becomes bloated and expensive.
D=Replace the main index: knowledge base questions would go unanswered.
T: Handle fresh user documents with a session-scoped index merged with the main index, keeping provenance.
V: semantic search, AIP Agent Studio

@ PLTR-AIE D3 T3.3 applied troubleshooting
S: A retrieval evaluation shows that for 20% of questions the correct chunk ranks between positions 6 and 15, just outside the top 5 that are injected. What is the most efficient improvement?
A: Inject the top 15 chunks for every question so the correct one is always included regardless of its position
B: Add a reranking stage over the top 30 candidates so the correct chunk is promoted into the top 5
C: Re-chunk the entire corpus with smaller chunks and rebuild the index from scratch
D: Switch to a model with a larger context window and inject the top 50 chunks for every question
K: B
G: ## Reranking fixes near misses
First-stage vector retrieval is approximate; a reranker (cross-encoder or model-based) re-scores a candidate set with the query for higher precision. The exam guide lists ranking among the stages to tune.
## Why reranking here
- The correct chunk is already retrieved, just ranked low: a ranking problem, not a recall problem.
- Reranking 30 candidates is cheap compared with tripling the injected context.
- Measure: top-5 hit rate before and after.
Example: top-5 hit rate rises from 80% to 94% with the same five injected chunks.
W: Reranking the candidate set: it addresses the exact failure (right chunk, wrong rank) without enlarging the context.
X: A=Inject 15: triples context cost and noise for every question to fix a ranking issue.
C=Re-chunk everything: a large, uncertain change for a problem that reranking solves directly.
D=Larger window with 50 chunks: even more noise and cost per question, and the ranking problem that put the right chunk low is untouched.
T: When the right chunk is retrieved but ranked low, add reranking rather than injecting more.
V: semantic search, AIP Evals

@ PLTR-AIE D3 T3.1 applied use-case
S: An assistant must answer questions about tabular reference data (a 5,000-row parts price list) alongside free-text manuals. How should the price list be handled for retrieval?
A: Convert each row into a natural sentence, embed all 5,000 sentences and rely on semantic search alone to find the right price for any part
B: Keep the price list as structured objects with exact lookup by part number, use semantic search only for manuals, and route by question type
C: Embed the whole price list as one chunk so the model receives the full table whenever any part is mentioned
D: Exclude the price list from the assistant since tables cannot be used in retrieval systems
K: B
G: ## Structured data is not for semantic search
The exam guide distinguishes structured facts read from objects from unstructured text retrieved semantically. A price list is a table with keys; exact lookup is correct, fast and exact.
## Design
- Part objects with price properties; lookup by part number, filter by category.
- Manuals chunked and embedded for semantic search.
- Routing: identifier patterns and price intent go to the lookup; descriptive questions go to the manuals; mixed questions use both.
Example: "price of part 88-1204" returns the exact price property; "how do I fit part 88-1204" retrieves the manual chunk.
W: Exact lookup for the table, semantic search for manuals, with routing: each data type is accessed the right way.
X: A=Sentence per row: similar part numbers and prices blur in vector space; exact questions get approximate answers.
C=Whole table as one chunk: huge context on every mention and no exactness.
D=Exclude: tables are usable; they simply need exact access rather than embeddings.
T: Serve tabular reference data through exact lookups; reserve semantic search for text.
V: Ontology, semantic search

@ PLTR-AIE D3 T3.3 advanced tradeoff
S: An assistant retrieves from a corpus that is updated continuously. Users sometimes get an answer and, minutes later, a different answer to the same question because a new document arrived. Stakeholders ask for "stable answers". What is the appropriate response?
A: Freeze the corpus and stop indexing new documents so that answers never change for any question
B: Explain that answers reflect the current corpus; add version and timestamp to citations, and offer an "as of" mode for reproducibility
C: Cache every answer permanently so that the first answer given to a question is always returned afterwards, even after the corpus changes
D: Delay all new documents by a month so that answers change less often during normal use
K: B
G: ## Freshness versus stability
Freshness is a feature: a corrected procedure should change the answer. The exam guide lists freshness and provenance among retrieval criteria. Stability is achieved with transparency and explicit snapshots, not by stale data.
## Design
- Citations with document version and effective time explain why an answer changed.
- "As of" mode: retrieval filtered to documents as of a timestamp, for audits or reproducibility.
- Monitor change frequency; alert users when a cited document is superseded.
Example: the second answer cites manual revision 8 issued ten minutes earlier; the user sees why it differs and can request the revision 7 answer.
W: Transparent, versioned citations with an optional "as of" mode: answers stay current and changes are explainable and reproducible when needed.
X: A=Freeze: users receive outdated and possibly unsafe procedures.
C=Permanent cache: stale answers forever, with no way to get corrections.
D=Delay a month: arbitrary staleness; critical updates are hidden.
T: Keep retrieval fresh and make changes explainable with versioned citations and "as of" queries.
V: semantic search, Ontology
