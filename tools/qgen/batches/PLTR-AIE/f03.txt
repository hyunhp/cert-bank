@ PLTR-AIE D4 T4.3 advanced tradeoff
S: An AI engineer is asked to decide, for a new workload, between an LLM transform in Pipeline Builder, a Code Repositories transform, and an on-demand Logic function. The workload: enrich 3 million records nightly with a classification, requiring custom retry logic, strict rate limiting and per-row audit, consumed by dashboards. Which choice and why?
A: An LLM transform node in Pipeline Builder, since it is the quickest to set up for any batch AI job and needs no code
B: A Code Repositories transform, since batch scale belongs in the pipeline layer and the control needs call for hand-written code
C: An on-demand Logic function invoked for each record, since classification is an AI task and AIP Logic is the platform's AI authoring tool
D: Manual classification by a team of analysts working through the records in a Workshop queue, with the dashboards reading their labels
K: B
G: ## Choosing among batch AI implementations
The exam guide distinguishes LLM transforms in Pipeline Builder from Code Repositories, which suit custom logic, retries, rate limiting and programmatic control. Scale and consumption place the work south.
## Reasoning
- South: nightly, millions of rows, dashboards.
- Code: custom retry and rate limiting, per-row audit records, checkpointing.
- Pipeline Builder would fit a simpler job without those control requirements.
Example: the transform paces calls at the provider limit, records prompt version and raw response per row, and resumes after interruptions.
W: Code Repositories transform: nightly bulk enrichment for dashboards is pipeline-layer work, and custom retries, strict rate limiting and per-row audit records need programmatic control that a configured node cannot express.
X: A=Pipeline Builder LLM node: fine for simple batch jobs; lacks custom retry, pacing and audit control.
C=On-demand Logic: 3 million nightly rows for dashboards is not on-demand work.
D=Manual: 3 million records a night cannot be classified by people; the dashboards would never be current.
T: Use Code Repositories for batch AI that needs custom control; Pipeline Builder LLM nodes for simpler batch jobs; Logic for on-demand.
V: Code Repositories, Pipeline Builder, AIP Logic

@ PLTR-AIE D3 T3.1 applied use-case
S: A knowledge base contains many near-identical documents (templates with small variations per region). Retrieval returns five almost identical chunks and the answer never mentions the one regional difference the user asked about. What chunking or retrieval change helps?
A: Increase the number of retrieved chunks to twenty so that the regional variant is more likely to be included somewhere in the context
B: Collapse look-alike results during ranking and attach location metadata so retrieval prefers the variant that applies
C: Remove all but one template from the corpus so the index never holds duplicate passages
D: Ask the model in the prompt to notice and mention any regional differences among the chunks it receives
K: B
G: ## Near-duplicates crowd out variants
The exam guide asks for metadata and context selection that balance precision and recall. Five copies of the same text consume the context budget and hide the one that differs.
## Design
- Near-duplicate collapse: cluster by similarity; keep one per cluster.
- Region metadata on chunks; filter to the user's region (from state or profile) or boost it.
- Diversity in ranking so variants, not copies, fill the slots.
Example: the user in region B gets region B's variant and one representative base chunk, and the answer names the difference.
W: Deduplication plus region metadata: collapsing near-identical chunks frees the context slots, and region metadata lets retrieval filter or boost the user's region, so the context carries the variant that matters instead of five copies.
X: A=Twenty chunks: more copies, more noise, more cost; the variant may still be crowded out.
C=Delete templates: the regional variants are legitimate content, so removing them deletes the very difference users ask about.
D=Prompt the model to notice: it cannot mention a variant it never received, and retrieval still fills the context with copies.
T: Collapse near-duplicates and use metadata to retrieve the variant relevant to the user.
V: semantic search, Ontology

@ PLTR-AIE D1 T1.1 applied use-case
S: A Logic function must return a list of up to five recommended knowledge articles for a support ticket, each with an article id and a one-line reason. Downstream, an app renders them as links. How should the output be typed?
A: A single string containing the five article titles separated by commas, which the app splits on commas before rendering the links
B: A bounded list of typed records holding an object reference and a short text field, which the app iterates without parsing
C: A free-text paragraph in which the model mentions the articles it thinks are relevant, with the app searching the paragraph for article ids
D: Five separate string outputs named article1 to article5 with the reasons embedded inside each string after a dash character
K: B
G: ## Lists of typed records
AIP Logic outputs can be lists of structured records. The exam guide asks for typed outputs; a list of references with reasons is a natural typed shape.
## Design
- Output: `recommendations: list<{article_id: reference, reason: string}>` with a maximum length.
- Validation: each id must exist (a lookup); reasons non-empty.
- The app iterates the list; no parsing.
Example: three recommendations returned for a printer issue, each linking to a real article with a reason.
W: Capped list of typed records: each item carries a validated article reference and a reason string, the list holds at most five items, and the app renders links from fields with no parsing or fixed slots.
X: A=Comma-separated string: titles with commas break the split, and no ids means no reliable links.
C=Paragraph to search: the app would mine prose for identifiers that may be misspelt or absent; fragile and unvalidated.
D=Fixed string slots: brittle, cannot represent fewer than five, and still needs parsing for the reason.
T: Return collections as typed lists of records with validated references rather than delimited strings.
V: AIP Logic, Ontology

@ PLTR-AIE D6 T6.1 applied comparison
S: Which Automate configuration is most appropriate for "re-run the risk assessment whenever a Supplier's financial rating property changes, but not when other properties change"?
A: A property-scoped object trigger that runs one assessment per edited object and ignores edits the assessment itself makes
B: A manual button in the supplier application that an analyst clicks after noticing that a supplier's rating has changed
C: A daily schedule that re-assesses all suppliers regardless of whether any rating changed, so nothing is ever missed
D: A trigger on any Supplier property change at all, with the function re-assessing every supplier in the Ontology on every single edit
K: A
G: ## Property-scoped triggers
The exam guide asks for triggers that avoid unnecessary executions and loops. The condition names the property explicitly.
## Configuration
- Trigger: `financial_rating` changed on a Supplier.
- Scope: that supplier only.
- Guard: the assessment writes to different properties, or skips when the change came from itself.
Example: a rating downgrade on one supplier re-runs one assessment; an address edit on another runs nothing.
W: Property-scoped trigger: it fires only when the financial rating property changes, runs the assessment for that supplier alone and has a loop guard so the assessment's own writes do not trigger it again, which is exactly the requirement and nothing more.
X: B=Manual: rating changes are noticed late or not at all; the re-assessment depends on an analyst's attention.
C=Daily for all: a rating downgrade waits up to a day, and thousands of unchanged suppliers are re-assessed needlessly.
D=Any change, all suppliers: massive unnecessary work and a loop risk.
T: Scope automation triggers to the property that matters and guard against self-triggering.
V: Automate

@ PLTR-AIE D1 T1.1 applied use-case
S: A Logic function must return a decision of "approve", "reject" or "escalate" together with a short reason and a confidence between 0 and 1. The consuming automation branches on the decision. How should the output be declared?
A: A free-text paragraph in which the model explains its decision in detail for a human to read before the automation acts
B: A struct output with an enum field for the outcome plus text and number fields, so the consumer compares a typed value
C: Three separate outputs on three different functions that the automation calls one after another and then combines
D: A single string output such as "approve: looks fine (0.8)" that the automation parses with a regular expression on every run it processes
K: B
G: ## Typed struct outputs for branching consumers
AIP Logic outputs can be structured records with typed fields. The exam guide asks for typed inputs and outputs; a consumer that branches needs a field it can compare, not prose.
## Declaration
- `decision: enum(approve, reject, escalate)`, `reason: string`, `confidence: number`.
- The automation's condition reads `decision` directly; `confidence` can gate escalation.
Example: `{decision: escalate, reason: "amount above approver limit", confidence: 0.91}`; the automation routes to the approver queue.
W: Enumerated decision in a typed struct: the automation gets a decision field limited to approve, reject or escalate that it branches on directly, plus a reason string and a numeric confidence, with no parsing.
X: A=Paragraph for a human: the consumer is an automation; prose cannot drive a branch without a person in between.
C=Three functions: triple the cost and no guarantee that the three outputs describe one consistent decision.
D=String with regex: fragile parsing that breaks on any variation of wording or punctuation in the model's answer.
T: Declare decision-type outputs as enumerations inside a typed struct so consumers branch without parsing.
V: AIP Logic, Automate
