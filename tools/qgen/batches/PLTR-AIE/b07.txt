@ PLTR-AIE D6 T6.1 applied use-case
S: A team wants every newly created Complaint object to be classified by an AIP Logic function and, if the function marks it as urgent, to have a notification sent to the duty manager. Which configuration achieves this without manual steps?
A: An Automate rule triggered on Complaint creation, with a function effect and a conditional notification effect for urgent results
B: A Workshop button on the complaint list that a dispatcher presses each morning to classify the complaints created since yesterday
C: A nightly pipeline build that classifies all complaints created during the day and writes an "urgent" column for the manager to filter
D: An AIP agent that the duty manager asks for new urgent complaints whenever they have time to check in
K: A
G: ## Automate: triggers and effects
Automate watches the Ontology for conditions and runs effects when they occur. A **trigger** can be an object creation, a property change or a schedule; **effects** include running functions, applying Actions and sending notifications. The exam guide lists triggers, effects, execution modes and function-backed Actions as the pieces to configure.
## Mapping the requirement
- Trigger: a Complaint object is created.
- Effect 1: run the classification function on that object.
- Effect 2 (conditional): notify the duty manager when the result is urgent.
Because it is event-driven, each complaint is handled as it appears, with no polling and no person in the loop for the routine case.
Example: a complaint created at 02:14 is classified within minutes and the manager is paged only if it is urgent.
W: Automate with an object-creation trigger, a function effect and a conditional notification: it runs per event, unattended, and sends the notification only when the classification says urgent.
X: B=Manual button: classification would wait until a person remembers; an urgent complaint at night would sit until morning.
C=Nightly pipeline: a batch classifies in bulk once a day, so the notification requirement for urgent complaints is not met in time.
D=Agent on request: an agent answers when asked; it does not watch for new objects or notify anyone proactively.
T: For "when X happens, do Y" over Ontology objects, use an Automate trigger with function and notification effects.

@ PLTR-AIE D6 T6.2 applied use-case
S: A workflow must take a new supplier onboarding request, extract company details from the attached documents with an AIP Logic function, create a Supplier object, and then submit it to compliance review. The creation must only happen if extraction succeeds and the details pass validation. How should the pieces be chained?
A: Let the Logic function create the Supplier object directly inside its extraction step, so the whole workflow lives in one function and needs no orchestration
B: Have the function return the extracted details as typed output, validate them, then call a function-backed Action that creates the Supplier and triggers the review step
C: Create the Supplier object first from the request's basic fields, then let the function fill in details afterwards whenever extraction eventually finishes
D: Send the documents to an agent that creates the Supplier when it is satisfied with its own extraction, then forwards the result to compliance by email
K: B
G: ## Chaining Functions, Actions and AI outputs
The exam guide asks you to chain Functions, Actions and AI outputs into multi-step workflows. The reliable pattern separates stages:
1. AI step produces typed output (the extracted details).
2. Deterministic validation checks required fields, formats and duplicates.
3. A function-backed Action performs the write (create Supplier) with the Action's own validation and permissions.
4. The Action's effect, or an Automate rule, starts the review step.
## Why separate
Each stage can fail on its own and be retried or rejected without half-created objects. Validation sits between the model and the write, so a bad extraction never becomes a Supplier.
Example: extraction returns a tax id in the wrong format; validation fails, the request goes to a queue, and no Supplier is created.
W: Typed output, validation, then a function-backed Action: the write happens only after the AI result has been checked, and the Action carries the create-and-review logic in a controlled place.
X: A=Write inside extraction: the model's output would become an object before any validation; failures leave partial Suppliers and nothing can be retried cleanly.
C=Create first, fill later: incomplete Supplier objects would exist and could reach review or other consumers before details are known.
D=Agent decides and emails: an agent judging its own extraction and writing directly bypasses validation, and email is not an auditable workflow step.
T: Chain AI output through validation into a function-backed Action; never let the model write before its output is checked.
V: AIP Logic, Actions, Automate

@ PLTR-AIE D6 T6.3 applied use-case
S: An engineer has built an automation that, for each Order marked as disputed, runs an AI analysis and applies an Action that issues a refund up to a limit. Nothing has run yet. What is the right next step before enabling the live trigger?
A: Enable the trigger on all orders and watch the first few runs closely, pausing the automation if any refund looks wrong
B: Run the workflow manually on representative disputed orders, including edge cases, and check the refunds before enabling the trigger
C: Enable the trigger with the refund limit set to zero for a week, so the automation runs end to end on real disputes without any effect on money
D: Enable the trigger only at night, when few orders are disputed, so that any problems affect a small number of customers
K: B
G: ## Test manually with representative objects first
The exam guide says to test manually with representative objects before enabling live triggers. An automation that issues refunds changes money on every run; the cheapest place to find a defect is a manual run on chosen objects, where the engineer can inspect each result.
## What to run
- Normal disputed orders of different sizes.
- Edge cases: an order already refunded, a dispute with missing evidence, an amount right at the limit.
- Confirm the Action's validation blocks what it should, and that the AI analysis's output lands correctly in the Action's inputs.
Then enable the trigger, ideally scoped at first (one region or order type) with monitoring.
Example: the manual run shows the analysis recommends a refund on an already-refunded order; the Action's precondition is fixed before any customer is affected.
W: Manual runs on representative and edge-case objects: defects are found on a few chosen orders with no customer impact, which is the step the guide prescribes before a live trigger.
X: A=Enable and watch: the first wrong refund is already issued before anyone can pause; watching is not testing.
C=Zero limit: with the limit at zero nothing meaningful runs, so the test does not exercise the real refund path or its edge cases.
D=Night only: fewer affected customers is still affected customers; it limits blast radius but does not verify behaviour.
T: Before turning on a live automation, run it by hand on representative objects, including edge cases, and inspect every result.

@ PLTR-AIE D6 T6.3 advanced troubleshooting
S: A live automation enriches new Shipment objects by calling an external carrier API through a function, then applies an Action that sets the delivery estimate. The carrier API is down for an hour. Afterwards, some shipments have no estimate and others have two conflicting ones. Which redesign fixes both symptoms?
A: Remove the external call and let the model estimate delivery from the shipment's own fields and history, so the automation never depends on an outside system again
B: Return an explicit failure when the API is down, record those shipments for retry, and make the Action idempotent so a repeat replaces the estimate
C: Increase the API timeout to ten minutes and disable retries, so each shipment is attempted exactly once and no duplicates can occur
D: Run the automation every five minutes in batch over all shipments without an estimate, which guarantees that every shipment is eventually covered
K: B
G: ## Partial failure and duplicate execution
The exam guide asks for workflows that remain safe when an external dependency fails or is retried. Two things went wrong here:
- Some runs failed silently or were not retried, leaving shipments without an estimate.
- Some runs were retried after the Action had already written, producing a second estimate.
## The fix pattern
- Explicit failure: the function returns an error state instead of a blank; the automation records the shipment as pending.
- Retry: pending shipments are retried once the API recovers, with backoff.
- Idempotent Action: setting the estimate replaces the value (or checks for an existing one) so a retry after a partial success cannot create a duplicate.
- In-flight safety: changes to the automation account for runs that were mid-way when the outage started.
Example: 300 shipments marked pending during the outage, all processed once afterwards, each with exactly one estimate.
W: Explicit failures with retry plus an idempotent Action: the first handles the missing estimates, the second the duplicates, which together cover partial failure and repeated execution.
X: A=Model-estimated delivery: inventing a delivery estimate replaces the carrier's data with a guess; the dependency problem is solved by removing the truth.
C=Long timeout, no retries: a shipment that fails once stays without an estimate forever, and a ten-minute timeout blocks the workflow.
D=Five-minute batch sweep: without an idempotent Action the sweep can still produce duplicates when a previous run is in flight, and it replaces an event-driven design with polling.
T: Design automations for failure: explicit error states, retries for pending work, and idempotent Actions so repeats are harmless.
V: Automate, Actions

@ PLTR-AIE D6 T6.1 applied tradeoff
S: An automation drafts a reply to each incoming customer email with an AI function. For most emails the draft is sent automatically; for emails that mention legal action or a regulator, a person must approve the draft before it is sent. How should execution be configured?
A: Configure the automation to send every draft automatically and ask the AI function to be especially careful with legal emails
B: Branch on the classification: automatic send for routine emails, and a human review task that sends only after approval for sensitive ones
C: Require a person to approve every draft, since separating routine from sensitive emails is not something an automation can do reliably
D: Send all drafts automatically but delay sensitive ones by 24 hours, giving staff a window in which they can cancel the send
K: B
G: ## Match control to consequence
The exam guide asks to add human review for high-consequence actions and to match validation strictness to consequence. A routine reply and a reply in a legal dispute carry very different risk; the workflow should treat them differently rather than treating all emails alike.
## Execution design
- Classification step (AI or rules) tags the email as routine or sensitive.
- Routine: automatic send, with monitoring.
- Sensitive: the draft is stored, a review task is created for a person, and the send Action runs only on approval; the classification itself can be over-inclusive, since the cost of an extra review is low.
- Evaluate the classifier on adversarial cases (a legal threat phrased casually) because a missed sensitive email is the real risk.
Example: "I will contact the regulator" is classified sensitive; the draft waits for a legal reviewer.
W: Branched execution with human approval for the sensitive path: control is applied where the consequence is high and routine work stays automatic.
X: A=Ask the model to be careful: a prompt instruction is not a control; sensitive replies would still go out without a person seeing them.
C=Approve everything: this removes the value of automation for routine emails and buries reviewers so the sensitive ones get less attention.
D=Delay and cancel window: nobody is required to look, so sensitive replies go out unless someone happens to notice in time.
T: Branch workflows by consequence: automate the routine path and require human approval on the high-consequence path.

@ PLTR-AIE D6 T6.3 applied use-case
S: A team must change the prompt used by a live automation that processes about 500 objects per hour. Some objects are always mid-processing. What is the safe way to make the change?
A: Edit the function in place during business hours, since the automation picks up the change on the next object and objects already processed are unaffected by it
B: Publish a new function version, test it on representative objects, then switch the automation at a quiet moment while in-flight runs finish on the old one
C: Pause the automation, delete the objects currently being processed, deploy the change and resume so that nothing is in a mixed state
D: Deploy the change and reprocess the last hour of objects with the new prompt to make sure every object was handled by the same version
K: B
G: ## Modifying live workflows safely
The exam guide asks you to modify live workflows accounting for retries, duplicate execution, partial failure and in-flight work. A running automation has objects somewhere between trigger and effect at any moment.
## The procedure
- Version: publish the new prompt as a new function version; the live automation keeps using the old one.
- Test: run the new version on representative objects, compare with the old.
- Switch: point the automation at the new version at a low-traffic moment; runs already started complete on the version they began with.
- Watch: monitor the first runs and keep the old version available for rollback.
Example: the switch happens at 03:00; 12 in-flight objects finish under version 7, every object after that uses version 8, and nothing is processed twice.
W: New version, tested, switched at a quiet moment with in-flight runs finishing: this changes behaviour without mixed states, duplicates or an untested prompt reaching live objects.
X: A=Edit in place: the change goes live untested, and runs that started on the old prompt may continue with the new one mid-way.
C=Delete in-flight objects: destroying business objects to avoid a mixed state is unacceptable; those objects represent real work.
D=Reprocess the last hour: reprocessing already-handled objects risks duplicate effects and is unnecessary if the switch is clean.
T: Change live automations through a new tested version and a clean switch that lets in-flight work complete.
V: Automate, AIP Logic

@ PLTR-AIE D6 T6.2 applied use-case
S: A Workshop app lets analysts click "Generate summary" on a case. The summary comes from an AIP Logic function and should be saved on the case object so colleagues can see it. Which integration is correct?
A: Have the Workshop button call the function and show the result on screen only, since saving it would require a separate pipeline
B: Bind the button to a function-backed Action that calls the function and writes the summary to the case property under the Action's permissions
C: Have the function write directly into the Workshop module's variables, which the module keeps and shows to every user who later opens the same case
D: Schedule the function to summarize every case nightly so that the button is unnecessary and the summary is always present
K: B
G: ## Workshop, Functions and Actions
Workshop shows and edits Ontology objects. Reading a function's result for display is one thing; **writing** to an object is an edit, and edits in Foundry go through Actions, which carry permissions, validation and audit. The exam guide lists function-backed Actions and Workshop integration among the orchestration tools.
## The pattern
- The button triggers an Action.
- The Action is backed by a function that calls the AIP Logic summarizer and sets the `summary` property.
- The Action's rules decide who may run it and validate the result (length, non-empty).
- The object changes once, with an audit record of who triggered it.
Example: an analyst clicks the button; the Action runs, the property updates, and a colleague opening the case sees the summary with its timestamp.
W: Function-backed Action bound to the button: the write to the object happens through the governed path, so permissions, validation and audit apply, and the summary is visible to everyone.
X: A=Display only: the requirement is a saved summary; showing it on one screen does not share it with colleagues.
C=Module variables: Workshop variables are UI state, not Ontology data; they are not a durable, governed store for object properties.
D=Nightly schedule: analysts asked for an on-demand summary of a specific case; nightly batches summarize cases nobody needs and lag the current state.
T: Writes from a Workshop button go through a function-backed Action, not directly from a function into UI state.

@ PLTR-AIE D6 T6.1 applied troubleshooting
S: An Automate rule triggers whenever a Ticket's status property changes and runs an AI function that writes a status note back onto the same Ticket. Shortly after launch, runs multiplied and the team saw thousands of executions on a single ticket. What is the cause and the fix?
A: The model is generating very long notes; shorten the output so each execution finishes before the next change is detected
B: The automation's own write re-triggers the rule in a loop; narrow the trigger to specific status transitions and keep the function's write outside the trigger condition
C: Too many users edit tickets at the same time; add a rate limit so the automation can run at most once per minute across the whole Ontology until load falls
D: The function is failing and being retried; disable retries so each change triggers at most one execution
K: B
G: ## Trigger loops
An automation that reacts to a change on an object and then changes that object can trigger itself. If the trigger is "any change to status" and the effect modifies the ticket in a way that counts as such a change, every run causes the next one.
## Breaking the loop
The exam guide asks you to configure triggers without creating unnecessary builds or executions.
- Narrow the trigger: specific transitions (for example, Open → Resolved), not any change.
- Make the effect's write distinguishable: write to a different property, or include a condition that skips objects the automation already handled.
- Add a guard: do not run if the last note was written by the automation itself within a short window.
- Test on representative objects before enabling, which would have revealed the loop.
Example: the trigger becomes "status changed to Resolved" and the function writes to `resolution_note`; one change, one run.
W: Self-triggering loop fixed by narrowing the trigger and decoupling the write: the automation's own effect no longer satisfies its trigger, so each real change runs once.
X: A=Shorter notes: output length has nothing to do with the loop; shorter runs would simply loop faster.
C=Global rate limit: it throttles the symptom for every ticket while the loop keeps consuming the budget; the cause remains.
D=Disable retries: the executions are new triggers, not retries; removing retries would also drop genuine transient failures.
T: An automation must not satisfy its own trigger; narrow the condition and separate what it writes from what it watches.
V: Automate
