@ PLTR-AIE D4 T4.1 applied use-case
S: A team must extract the supplier name, invoice date and total from 300,000 scanned PDF invoices into dataset columns. Some scans are photographs of paper invoices. Which approach fits?
A: A visual document processing step that sends each page image to a vision-capable model with a structured output schema, then validates the fields
B: A text-only LLM transform over the PDF file names and metadata, since the supplier, date and total can usually be inferred from how the files are named
C: An agent that opens each invoice in a conversation and asks the user to confirm the three fields before writing them to the dataset
D: A regular-expression transform over the PDF bytes, since invoice totals follow a fixed pattern that does not require a model to detect
K: A
G: ## Processing documents with LLMs and VLMs
The exam guide lists batch LLM processing, entity extraction, visual document processing and structured output among the data-processing capabilities. Scanned and photographed invoices have no reliable text layer, so a **vision-capable model** reads the page image directly.
## Making extraction trustworthy
- Structured output: define the three fields and their types so the model's answer is parsed into columns, not prose.
- Validation: dates must parse, totals must be numeric and plausible, suppliers can be matched against a known list; failures go to a review queue.
- Auditability: keep the prompt and the raw model response next to the parsed values (see the auditability task), so a wrong total can be traced.
Example: 300,000 pages run as a scheduled batch; 2% fail validation and are routed to a reviewer rather than silently written.
W: Visual document processing with structured output and validation: it reads images directly, produces typed columns, and catches bad extractions before they reach consumers.
X: B=File names only: names rarely hold the total or the correct date; the real values are on the page image, which this approach never reads.
C=Conversational confirmation: 300,000 invoices cannot be confirmed one by one in chat; this is a batch workload for the pipeline.
D=Regex on bytes: scanned PDFs contain image data, not text; regular expressions have nothing to match, and even text invoices vary too much for fixed patterns.
T: For scanned documents, use vision-capable extraction with structured output and validation in a batch pipeline step.
V: Pipeline Builder, AIP

@ PLTR-AIE D4 T4.2 applied tradeoff
S: A pipeline uses an LLM to classify 50,000 customer complaints per week. An auditor asks how a particular complaint received its label two months ago. The pipeline stores only the final label. What should the team change?
A: Re-run the current prompt on that complaint when an auditor asks, since the same prompt and model will reproduce the label that was assigned
B: Store, alongside each label, the prompt version, model identifier and the raw model response that produced it, so any label can be traced later
C: Add a free-text "reason" column generated by a second LLM call after classification, which explains why the label is appropriate
D: Keep a copy of the whole weekly input dataset so that auditors can re-classify any complaint themselves with a model of their choice
K: B
G: ## Auditability of AI outputs
The exam guide asks to preserve prompts and raw responses where auditability and debugging require them. An LLM label is the result of three things: the input, the prompt (and its version) and the model. If only the label survives, nobody can explain or reproduce it later.
## What to keep
- Prompt version or hash, model identifier, and parameters.
- The raw response before parsing, which shows what the model actually said.
- A timestamp and the pipeline build that produced the row.
Storage is cheap relative to a compliance finding, and the same data makes debugging possible when quality drifts.
Example: the auditor sees the raw response "Category: billing (customer disputes a double charge)" produced by prompt v12 on model X, which explains the label without re-running anything.
W: Stored prompt, model and raw response per label: this reconstructs how the label came to be, exactly as it happened, without relying on reproduction.
X: A=Re-run on request: models are non-deterministic and the prompt and model have changed in two months; a re-run shows today's behaviour, not what happened then.
C=Post-hoc reason: a second model explaining a label it did not produce is a rationalization, not evidence of the original decision.
D=Keep inputs only: inputs without the prompt, model and response do not explain the label; re-classification by auditors produces a different result.
T: Preserve the prompt version, model and raw response next to every AI-generated value that may need to be explained later.
V: Pipeline Builder, Code Repositories

@ PLTR-AIE D4 T4.3 applied tradeoff
S: Analysts want an "ask a question about this customer" feature that reasons over the customer's recent orders, open tickets and the analyst's own question, which differs every time. Where should the LLM call happen?
A: In the nightly pipeline, generating a stored answer for a fixed set of likely questions per customer so that the feature can read from a property
B: North of the Ontology, in a function or agent invoked at interaction time with the customer's current objects and the analyst's question as context
C: In the ingestion sync, so that every order and ticket is annotated with an answer as soon as it arrives from the source system
D: In a batch step that runs hourly over all customers, writing one general summary per customer that the feature returns for any question
K: B
G: ## North and south again
The exam guide's layering rule: south of the Ontology for reusable batch enrichment, north for interactive, context-dependent reasoning. The deciding factors are consumer breadth, freshness, reusability, scale and cost.
## Why this is north
- The question is different each time and unknown in advance, so there is no reusable result to compute ahead.
- The context must be current: the orders and tickets as they are at that moment.
- One analyst asks, and the answer is used once.
A function (AIP Logic or code) or an agent is invoked when the analyst asks, fetches the customer's objects under the analyst's permissions and reasons over them.
Example: "Why has this customer's ticket volume doubled since the last order?" cannot be precomputed; a batch summary would not address it.
W: Interaction-time function north of the Ontology: the reasoning depends on the live question and current objects, which is the case the guide reserves for the north layer.
X: A=Precomputed likely questions: the analyst's question is not in a fixed set; stored answers would be stale and usually off-topic.
C=Annotate at ingestion: annotating each record with an answer to an unknown future question is impossible and would bloat every sync.
D=Hourly general summary: a generic summary is not an answer to a specific question and goes stale within the hour.
T: Context-dependent, one-off reasoning over current objects runs north of the Ontology at interaction time.
V: AIP Logic, Ontology

@ PLTR-AIE D4 T4.4 applied comparison
S: A team currently runs LLM summarization of incident reports from a notebook they trigger by hand. They now need it to run every night, respect the model provider's rate limit, retry failed calls and use a custom text-cleaning library. What should they do?
A: Keep the notebook and add a calendar reminder for the on-call engineer to run it each night and watch for rate-limit errors
B: Move the workflow into a Code Repositories transform with scheduled builds, rate-limited batched calls, retries and the library as a dependency
C: Rebuild it as an AIP agent that an engineer messages each evening with "summarize today's incidents" and that handles the calls itself
D: Rebuild it as a single AIP Logic function that loops over all incident reports in one run, since Logic handles retries automatically
K: B
G: ## When to codify a workflow
The exam guide names the triggers for moving AI processing into Code Repositories: scheduled batch execution, programmatic control, rate limiting, or libraries beyond what no-code tools offer. This case has all four.
## What the repository gives
- Scheduling as part of the pipeline, with builds and lineage.
- Code-level control over batching, concurrency and backoff, so the provider's rate limit is respected.
- Explicit retry and failure handling, with failed items recorded rather than lost.
- Declared dependencies, so the custom cleaning library is versioned with the transform.
Example: the transform processes reports in batches of 20, sleeps on rate-limit responses, writes summaries and a status column, and runs at 01:00 nightly.
W: Code Repositories transform: it provides scheduling, rate limiting, retries and custom libraries in one governed place, which is exactly the list of needs.
X: A=Manual notebook: a reminder is not scheduling; failures depend on someone watching, and nothing is versioned or reproducible.
C=Agent on request: an agent is an interactive tool; it is the wrong shape for an unattended nightly batch with rate-limit control.
D=Single Logic loop: a Logic function is not designed for scheduled large batches with custom libraries and provider-level rate control; one huge run is fragile.
T: Scheduled, rate-limited, retried or library-dependent AI processing belongs in a Code Repositories transform.
V: Code Repositories

@ PLTR-AIE D4 T4.1 advanced troubleshooting
S: An LLM transform classifies product descriptions into 40 categories with structured output. About 6% of rows receive a category that does not exist in the list, such as "Sportswear" instead of "Apparel". Which fix is most robust?
A: Accept the new categories as they appear, since the model is discovering useful categories that the original list did not include
B: Constrain the output to an enumeration of the 40 categories and add validation that routes any non-matching result to review
C: Add the sentence "only use categories from the list" to the prompt and rerun the transform, checking that the rate of invalid categories drops
D: Post-process the output with fuzzy string matching to map any unknown category to the nearest valid one before writing the dataset
K: B
G: ## Structured output needs constraints and validation
Structured output tells the model the shape of the answer. For a categorical field, the shape should include the allowed values: an **enumeration**. The exam guide pairs structured outputs with deterministic post-processing and quality checks.
## Defence in depth
- Enumeration: the model is asked for one of 40 values, not free text.
- Validation: anything that still does not match is rejected by code, not written; the row goes to a review queue or gets a null plus a status.
- Monitoring: the invalid rate is a quality metric; a jump signals a prompt, model or data change.
Example: "Sportswear" fails validation; the row is flagged, reviewed, and the reviewer's choice becomes a new evaluation case.
W: Enumeration plus validation and review: the constraint prevents most invalid labels and the validation guarantees that none reach the dataset unchecked.
X: A=Accept new categories: downstream filters and dashboards depend on the 40 categories; unplanned values break them and the taxonomy drifts without governance.
C=Prompt sentence only: it lowers the rate but gives no guarantee, and without validation the remaining invalid labels still get written.
D=Fuzzy mapping: "Sportswear" might map to "Apparel" or to "Sports equipment"; silently guessing hides errors in the data.
T: Constrain categorical AI output with an enumeration and validate in code; route failures to review rather than guessing.
V: Pipeline Builder, Code Repositories

@ PLTR-AIE D4 T4.2 applied tradeoff
S: A pipeline enriches 2 million product records with an LLM-generated marketing summary. The product data changes for about 1% of records per day, but the full job re-generates every summary nightly and costs more than the rest of the pipeline combined. What should change?
A: Generate summaries only for records whose inputs changed, caching existing ones by input content, with a full run only for refreshes
B: Switch to a cheaper model for the nightly run and accept lower summary quality in exchange for the reduced cost
C: Run the full job weekly instead of nightly, so the cost falls by about 85% at the price of summaries that are up to a week old
D: Ask the model to produce shorter summaries so each call uses fewer output tokens and the nightly cost drops proportionally
K: A
G: ## Caching in AI pipelines
The exam guide lists caching among the controls for AI data processing. An LLM call is deterministic enough in purpose, if not in wording, that regenerating a summary for unchanged input is pure waste.
## Incremental generation
- Key the cache on a hash of the input fields that the prompt uses (plus prompt version and model). Same key, same summary, no call.
- Process only new or changed records each night; 1% of 2 million is 20,000 calls instead of 2 million.
- Keep a periodic full regeneration or a prompt-version bump to refresh everything when the prompt or model changes.
This is also a data-engineering pattern: an incremental transform over the changed rows.
Example: a prompt change increments the version in the cache key, so every record regenerates once, then nightly runs return to 1%.
W: Cache keyed on input content and prompt version with incremental runs: cost drops to roughly 1% of today's with no loss of freshness or quality.
X: B=Cheaper model: the waste remains, since 99% of calls are still unnecessary; quality drops for no structural gain.
C=Weekly run: this trades freshness for cost and still regenerates unchanged records every week.
D=Shorter summaries: output tokens are a fraction of the cost per call, and the two million unnecessary calls remain.
T: Cache AI outputs by input content and prompt version, and regenerate only what changed.
V: Code Repositories, Pipeline Builder

@ PLTR-AIE D4 T4.3 applied comparison
S: A bank wants to detect the sentiment of every customer chat transcript so that a dashboard can show daily sentiment trends per branch, and also wants a relationship manager to be able to ask "what is this specific customer unhappy about today?" Which split of processing layers is correct?
A: Both south of the Ontology: compute the sentiment and a per-customer answer for the question nightly, and show the stored results in the dashboard and to the manager
B: Sentiment per transcript south of the Ontology as a stored property; the manager's question answered north at interaction time over current transcripts
C: Both north of the Ontology: compute sentiment on demand when the dashboard opens and answer the manager's question on demand in the same function
D: Sentiment north and the manager's question south: calculate sentiment live when the dashboard is viewed and precompute the manager's answer every night
K: B
G: ## Two workloads, two layers
The exam guide's rule is to justify each AI task's layer by consumer breadth, freshness, reusability, scale and cost.
- **Sentiment per transcript**: every transcript, needed by a dashboard for aggregation, the same value for every viewer, nightly freshness is fine. That is reusable batch enrichment: south, stored as a property.
- **"What is this customer unhappy about today?"**: a specific question, about current transcripts, for one user. That is interactive, context-dependent reasoning: north, computed when asked, and it can read the stored sentiment too.
Example: the dashboard aggregates `sentiment` over 80,000 transcripts in a query; the manager's question runs a function over the 6 transcripts from today for that customer.
W: Batch sentiment south, on-demand question north: each workload lands where its breadth, freshness and scale point, and the north function can reuse the south result.
X: A=Both south: the manager's question cannot be precomputed because it is not known in advance; stored answers would be stale and generic.
C=Both north: computing sentiment for 80,000 transcripts every time the dashboard opens is slow and costly, and yields inconsistent values between views.
D=Reversed: this puts the aggregate workload on the interactive path and the one-off question in the batch, which is backwards on every criterion.
T: Aggregate, reusable scores go south as properties; specific, current questions are answered north on demand.
V: Pipeline Builder, AIP Logic, Ontology

@ PLTR-AIE D4 T4.1 applied troubleshooting
S: An LLM entity-extraction transform pulls people and organizations from news articles into an Ontology. Reviewers find that the same organization appears under several spellings ("ACME Corp", "Acme Corporation", "ACME") as separate objects. What is the right fix?
A: Ask the model to always use the official name, since a language model knows the canonical name of most organizations
B: Add a deterministic normalization and entity-resolution step after extraction that maps variants to a canonical identifier
C: Create a link type between the variant objects so that applications can traverse from one spelling to the others when needed
D: Lower the temperature of the extraction model so that it returns the same spelling for an organization every time it sees it
K: B
G: ## Deterministic post-processing
The exam guide pairs AI processing with deterministic post-processing and quality checks. Extraction is the AI step; deciding that three spellings are one entity is a resolution step that should be rule-based and reproducible.
## Entity resolution in the pipeline
- Normalize: case, punctuation, legal suffixes ("Corp", "Corporation").
- Resolve against a reference list of known organizations, assigning the canonical id.
- Unresolved names go to a review queue; confirmed matches extend the reference list.
- The object's primary key is the canonical id, so a fourth spelling tomorrow lands on the same object.
Example: "ACME Corp" and "Acme Corporation" both resolve to `org-00417`; "Acme Holdings" stays unresolved for review.
W: Normalization and entity resolution before object creation: the mapping is explicit, repeatable and governed, and the Ontology receives one object per organization.
X: A=Ask for the official name: the model's idea of a canonical name is unreliable and unverifiable, and the article text drives what it returns.
C=Link the duplicates: this preserves the duplicates and pushes the problem onto every application and query that counts organizations.
D=Lower temperature: the spelling variation comes from the source articles, not from randomness; the model would still return the text it sees.
T: Keep extraction in the model and entity resolution in deterministic code with a canonical key.
V: Pipeline Builder, Ontology
