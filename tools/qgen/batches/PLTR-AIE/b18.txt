@ PLTR-AIE D1 T1.1 applied use-case
S: A Logic function must produce a customer-facing message in the customer's preferred language, which is stored as a property on the Customer object passed as input. How should the prompt be built?
A: Write one prompt per supported language as separate Logic functions and ask every caller to pick the right function for each customer it processes
B: Inject the language property into the task prompt as a variable, instruct the model to write in it, and return the language in the typed output
C: Ask the model to guess the customer's language from their name and write accordingly
D: Always write in English and translate afterwards with a second function
K: B
G: ## Variable injection from object properties
AIP Logic prompts can reference properties of input objects as variables. The exam guide lists variable injection among the basics of building Logic functions. The language preference is already data; it should drive the prompt.
## Design
- Input: Customer object; variables: `{customer.preferred_language}`, `{customer.first_name}`.
- Task prompt: "Write the message in {preferred_language}."
- Typed output: `{message: string, language: enum}` so a validator can confirm the language matches.
Example: a customer with preferred_language = "de" receives a German message; the output's language field is checked against the property.
W: Inject the property as a prompt variable with verification in the output: the data decides the language and the result is checkable.
X: A=One function per language: duplicated logic and a routing burden on every caller; a property can drive one function.
C=Guess from name: unreliable and potentially offensive; the preference is already known.
D=Translate afterwards: two calls, extra cost and translation artifacts, when the model can write directly in the target language.
T: Drive prompt behaviour from object properties through variable injection, and verify in the typed output.

@ PLTR-AIE D1 T1.1 applied comparison
S: Which of the following is the best reason to use a tool-using reasoning block instead of a single completion in AIP Logic?
A: The task needs a long and detailed answer that would not fit comfortably in the output of a single completion block
B: The task requires the model to decide from the input which lookups or functions to call and to use their results
C: The task requires a lower temperature than usual, and temperature can only be configured on tool-using reasoning blocks
D: The task's output must be a structured object with several typed fields rather than a plain string of text
K: B
G: ## When reasoning with tools is warranted
The exam guide asks you to choose single completion or tool-using reasoning appropriately. The distinguishing factor is whether the model must gather information or perform intermediate steps that depend on the input.
- Single completion: all needed information is in the inputs; one call produces the answer.
- Tool-using reasoning: the model needs to look things up (Ontology queries, functions) and the choice of lookup depends on the input.
Length, temperature and output structure are available in both modes.
Example: "Resolve this customer's complaint" may need order history, shipment status and policy lookup depending on the complaint: reasoning with tools.
W: Input-dependent decisions about which tools to call: that is the capability a reasoning block adds over a single completion.
X: A=Long answer: a single completion can produce long output; output length is a token setting, not a reason for tool use.
C=Low temperature: a model parameter available in both block types; it has nothing to do with choosing reasoning over completion.
D=Structured output: typed, structured outputs are available with single completions as well; structure does not require tools.
T: Use tool-using reasoning only when the model must decide which lookups to perform and use their results.

@ PLTR-AIE D1 T1.2 applied troubleshooting
S: A Logic function with an Ontology edit block works in testing but, in production, some edits are rejected with validation errors from the Action it uses. What is the right response?
A: Remove the Action's validation rules so that the function's edits always succeed in production the way they did during testing
B: Treat the rejections as the Action doing its job: inspect them, fix the function's output to satisfy the constraints, and add the cases to the suite
C: Bypass the Action and write directly to the dataset
D: Retry the rejected edits until they pass
K: B
G: ## Actions enforce the contract
Edits from a Logic function go through Actions whose validation rules protect the Ontology. The exam guide asks you to apply edits safely and to tune functions from traces. A rejection means the function produced something the business rules forbid.
## Response
- Trace the rejected runs: what values violated which rule (an invalid status transition, a value out of range)?
- Fix the function: constrain outputs, add a conditional, or route edge cases to a review task.
- Evaluation: the failing inputs become regression cases.
Example: the function set `priority = "critical"` on tickets of a type where only three priorities are allowed; an enumeration per ticket type fixes it.
W: Fix the function and add the cases to the suite: the Action's validation is the safety net, and the function must respect it.
X: A=Remove validation: it disables the protection for every caller of the Action, not just this function.
C=Write to the dataset: bypasses the Ontology's governance entirely and is not how edits are made.
D=Retry: the same invalid edit fails every time it is submitted; retrying only adds load and delays the real fix.
T: Action validation failures are signals to fix the function's output, never a reason to weaken the Action.

@ PLTR-AIE D1 T1.3 applied use-case
S: An engineer wants to test a Logic function change against the same inputs that caused a production incident last week. What should they use?
A: The current production objects that were involved in the incident, even though some of them may have been edited since the incident happened
B: The stored inputs from the incident runs' traces, replayed against the draft as evaluation cases, so the test uses exactly what failed
C: New synthetic inputs invented to resemble the incident
D: The function's system prompt, read carefully
K: B
G: ## Reproducing incidents from traces
Execution traces store the inputs and intermediate results of a run. The exam guide asks you to debug traces and use evaluation cases; incident inputs are the most valuable cases of all.
## Practice
- Export the incident runs' inputs (and retrieved context where relevant) into evaluation cases with the corrected expected output.
- Run the draft against them; compare with the production version's results.
- Keep the cases permanently as regression tests.
Example: the 14 tickets misclassified last Tuesday become 14 evaluation cases; the fix passes all 14 and the suite guards against the same failure.
W: Incident inputs from traces as evaluation cases: the fix is proven on the exact failures, and the cases prevent recurrence.
X: A=Current objects: they may no longer reproduce the condition; the test would be inconclusive.
C=Synthetic lookalikes: guesses at what failed; the real inputs exist.
D=Read the prompt: reading cannot demonstrate behaviour on the failing inputs.
T: Turn incident runs into evaluation cases from their traces and test fixes against them.

@ PLTR-AIE D1 T1.1 applied tradeoff
S: A Logic function sometimes receives inputs with missing optional fields (no phone number, no account manager). How should the prompt and blocks handle this?
A: Fail the function whenever any field is missing
B: Make the fields optional in the typed input, handle absence with conditionals or explicit "not provided" injection, and test with and without them
C: Fill missing fields with made-up default values inside the function so that the prompt template is always complete and the model never sees a gap
D: Ignore the issue since models handle missing text fine
K: B
G: ## Designing for absent inputs
Typed inputs can be optional; the function should behave well either way. The exam guide asks you to configure typed inputs and conditionals and to test edge cases.
## Design
- Optional types for the fields.
- Conditional: if `account_manager` is absent, skip the "copy the account manager" instruction or inject "no account manager assigned".
- Never inject empty strings that the model may interpret as a value.
- Evaluation cases with and without each optional field.
Example: without a phone number, the output omits the callback suggestion rather than inventing a number.
W: Optional typing, explicit handling of absence and tests both ways: the function is correct for every input shape.
X: A=Fail on missing: the fields are legitimately optional; failing blocks valid cases.
C=Fabricated defaults: the model may treat the fake value as real and act on it.
D=Ignore: an empty placeholder like "Phone: " invites hallucinated numbers.
T: Model optional inputs explicitly and handle their absence with conditionals and clear injection.

@ PLTR-AIE D1 T1.3 applied troubleshooting
S: Users report that a Logic function has become slower over the past month. Traces show the function's prompt now includes the full text of every linked document because a loop was added to inject them all. What should the engineer change?
A: Remove the loop entirely and stop injecting any linked documents into the prompt, so the function answers from the object's own properties only
B: Bound the context: inject only relevant documents or sections (metadata or semantic search), cap count and size, and verify with the suite
C: Increase the model's context window
D: Ask users to link fewer documents
K: B
G: ## Context growth in Logic functions
A loop that injects everything scales the prompt with the data. The exam guide asks you to optimize prompts and context and to debug from traces. The trace shows the cause precisely.
## Fix
- Relevance: select documents by metadata (type, date) or semantic search for the task.
- Caps: at most N documents or M tokens; summarize overflow.
- Measure: latency and quality before and after on the suite.
Example: injecting the three most relevant sections instead of twelve full documents restores a 4-second response and keeps accuracy.
W: Bound and target the injected context with verification: it removes the unbounded growth without losing the information the task needs.
X: A=Remove documents: the function needed context; the problem is injecting all of it unfiltered.
C=Bigger window: cost and latency keep growing with the data; it postpones the limit.
D=Fewer links: users link what they need; the function should select what it uses.
T: Never inject unbounded content into prompts; select relevant pieces and cap size.

@ PLTR-AIE D1 T1.2 applied use-case
S: A team wants a Logic function to summarize a meeting and then create follow-up Task objects for each action item. Which structure is safest?
A: One completion that writes the summary and creates all the Tasks in a single Ontology edit block without any validation checks in between
B: A completion producing a typed list of action items, a validation block (owners exist, dates valid), then an edit per validated item with invalid ones reported
C: Create Tasks first and summarize afterwards
D: Ask the model to create as many Tasks as it thinks are appropriate
K: B
G: ## Extraction, validation, then edits
The exam guide's safe-edit guidance and the orchestration principle of validating AI output before writes apply here. The model extracts; code validates; edits are applied only to validated items.
## Structure
- Completion: structured output list of action items.
- Validation: owner resolves to a user, due date parses and is in the future, description non-empty.
- Edit/Action per valid item; invalid items listed in the output for a person.
Example: five action items extracted, four valid; one with an unknown owner is returned for manual assignment.
W: Typed extraction, validation, then per-item edits: nothing invalid becomes a Task, and failures are visible.
X: A=Unchecked single edit: an invented owner or a malformed date becomes a broken Task.
C=Tasks first: there are no items to create before extraction.
D=Model decides freely: an unbounded number of unvalidated Task objects, including ones with invented owners or dates, would be created.
T: Validate AI-extracted items before creating objects from them.

@ PLTR-AIE D1 T1.3 advanced tradeoff
S: Two versions of a Logic function differ only in temperature (0.2 versus 0.8). The evaluation suite scores them equally on accuracy, but the 0.8 version has twice the variance across runs. The function feeds an automation. Which version should be published?
A: The 0.8 version, since variety in a model's outputs is generally desirable and prevents the automation from becoming too predictable
B: The 0.2 version, since an automation benefits from consistent outputs and lower variance makes regressions easier to detect
C: Alternate between the two versions on successive runs so that the automation gets the average of their behaviour over time
D: Neither, until the variance of both is zero
K: B
G: ## Choosing parameters for consumers
The exam guide asks you to tune parameters and to distinguish signal from variance. For an automated consumer, consistency is a feature: the same input should yield the same decision, and evaluation changes should reflect real changes.
## Reasoning
- Equal accuracy: no quality argument for 0.8.
- Lower variance: more predictable automation, clearer regression signals.
- Higher temperature belongs to creative tasks where variety matters.
Example: with 0.2, the nightly suite's score moves within one point; drift becomes visible immediately.
W: The lower-temperature version: equal accuracy with half the variance is strictly better for an automation.
X: A=Variety: not a goal for an automation that must make the same decision for the same input; variety here is just inconsistency.
C=Alternate: the automation would behave differently from run to run by design, combining the unpredictability of both versions.
D=Zero variance: unattainable with language models; the goal is low, measured variance.
T: For automated consumers, prefer the lower-variance configuration when accuracy is equal.
V: AIP Logic, AIP Evals
