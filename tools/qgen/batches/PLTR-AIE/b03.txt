# PLTR-AIE batch 03: Domain 2 (AIP Agent Design and Deployment), 8 questions

@ PLTR-AIE D2 T2.1 applied comparison
S: A logistics company wants an assistant that helps dispatchers inside their existing Workshop dispatch board: it should answer questions about the shipments shown on screen and propose reassignments using the board's own Actions. Which deployment fits best?
A: A standard agent built in AIP Agent Studio and embedded in the Workshop module, with tools scoped to the shipment objects and the board's Actions
B: AIP Assist, since it is already available across the platform and can answer general questions about how Foundry and Workshop work
C: A standalone agent page shared by link, so that dispatchers open it in a second browser tab beside the dispatch board when they need help
D: A scheduled AIP Logic function that writes a daily list of suggested reassignments to a dataset that the dispatch board displays
K: A
G: ## Standard agents versus AIP Assist
AIP Agent Studio builds **standard agents**: purpose-built assistants with their own instructions, retrieval context and tools, which can be embedded in Workshop, exposed standalone or used in AIP Studio. **AIP Assist** is the platform-wide helper for questions about using Foundry itself; it is not a place to wire custom business tools into a specific app.
## Choosing the channel
The exam guide asks you to distinguish the two by deployment context and capabilities, and to use Workshop embedding, standalone access and AIP Studio appropriately.
- Embedded in Workshop: the agent can use the module's state (what is on screen) and its Actions, so dispatchers stay in one place.
- Standalone: good for general assistants that do not depend on an app's context.
Example: "why is shipment 4471 late and who can take it?" needs the board's objects and its reassignment Action, which the embedded agent can call.
W: Embedded standard agent: it lives where the dispatchers work, sees the board's shipments and can propose reassignments through the same Actions, with tools scoped to that domain.
X: B=AIP Assist: it answers questions about the platform, not about a company's shipments, and it cannot be given the dispatch board's Actions.
C=Standalone page: a separate tab loses the application state and forces dispatchers to describe what they are looking at; integration with the board's Actions is weaker.
D=Scheduled Logic function: a daily list is not an assistant; it cannot answer questions in the moment or react to the current board.
T: For an assistant that works with an app's objects and Actions, build a standard agent and embed it in that Workshop module.
V: AIP Agent Studio, Workshop

@ PLTR-AIE D2 T2.2 applied tradeoff
S: An HR agent answers employee questions about leave policy. The team gave it fifteen tools, including ones that can create, edit and delete employee records, so that it can "handle anything". Reviewers worry about safety and about the agent choosing tools poorly. What should change?
A: Keep all fifteen tools but add a sentence to the instructions saying that the agent should only use the record-editing tools when the employee explicitly asks for a change
B: Remove the tools and let the agent answer from the policy documents alone, since any agent that holds a tool will eventually misuse it
C: Reduce the tools to the few the policy task needs, keep them read-only, and route any record change through a separate controlled Action with review
D: Keep the tools but switch the agent to a larger model, since tool selection quality depends mostly on the model's reasoning ability
K: C
G: ## Tools define what an agent can do
An agent's tools are its capabilities: every tool is a thing the model can decide to call. The exam guide asks why the agent needs these tools, and says to give a system only the tools, data and Actions the task requires.
## Why fewer, narrower tools are safer and better
- Safety: a policy question answerer with a delete-record tool can be manipulated into deleting a record; without that tool the worst outcome is a wrong answer.
- Quality: the model chooses among tools on every turn; fifteen overlapping tools make wrong choices more likely and slow each turn.
- Separation: reading policy and changing a record are different consequences; the change belongs in an Action with validation and a human in the loop.
Example: tools become "search leave policy", "look up my remaining balance"; "request a leave record change" opens an Action that HR approves.
W: Narrow, read-only tool set with a reviewed Action for changes: the agent keeps what the task needs, loses the capabilities that make misuse dangerous, and chooses tools more reliably.
X: A=Instruction only: an instruction does not remove a capability; the model can still call a delete tool when confused or manipulated, and tool choice stays cluttered.
B=No tools at all: some tools are useful and safe (reading a balance); the principle is least privilege, not zero capability.
D=Larger model: a better model still has fifteen tools and a delete capability it should never have had; it reduces one symptom without fixing the design.
T: Give an agent only the narrow, mostly read-only tools its task needs; put changes behind controlled Actions.
V: AIP Agent Studio, Actions

@ PLTR-AIE D2 T2.2 applied troubleshooting
S: A customer-support agent answers questions using retrieved knowledge-base articles. When a question is outside the knowledge base, the agent confidently invents an answer. Which configuration change addresses this best?
A: Instruct the agent to say it cannot answer when the retrieved context gives no support, and test that path with out-of-scope questions
B: Raise the number of retrieved articles for every question, so that there is always enough context for the agent to find some relevant answer
C: Add a disclaimer to every response stating that answers may be inaccurate, so customers know to verify what the agent tells them
D: Lower the model's temperature, since a less random model is less likely to make up facts that are not present in the retrieved articles
K: A
G: ## Grounding and the refusal path
A retrieval-grounded agent should answer from the evidence it retrieved. The exam guide's self-check asks what the agent should do when the evidence is insufficient: it needs an explicit behaviour, such as saying the knowledge base does not cover the question and offering escalation. Without that, the model fills the gap with a plausible guess.
## Making it reliable
- Instructions: answer only from retrieved context; when nothing supports an answer, say so and suggest the next step.
- Context handling: include enough relevance signal (scores or thresholds) that "nothing relevant" is detectable.
- Testing: the exam guide calls for representative, edge and adversarial cases; unanswerable questions are an edge case that must be in the test set, and the evaluation should check refusal behaviour.
Example: "Can I pay with cryptocurrency?" with no article on payment methods should produce "I don't have information on that; I can connect you to an agent", not an invented policy.
W: Explicit uncertainty path, tested: this gives the agent a correct behaviour for insufficient evidence and verifies it, instead of hoping the model stays quiet.
X: B=More articles: retrieving more for an out-of-scope question adds unrelated context, which gives the model more material to confabulate from.
C=Blanket disclaimer: it shifts the burden to customers and does nothing about the invented content; the agent keeps hallucinating with a warning attached.
D=Lower temperature: randomness is not the cause; a deterministic model will still produce its most likely guess when it has no evidence and no instruction to refuse.
T: Give every grounded agent a tested path for "the evidence does not answer this" instead of letting it guess.
V: AIP Agent Studio

@ PLTR-AIE D2 T2.3 advanced use-case
S: Before releasing an agent that can submit purchase requests, a team drafts a test plan. Which set of test interactions is the most complete?
A: Fifty typical purchase conversations covering the most common items, with the requests checked against the expected amounts and suppliers
B: Typical purchases, incomplete requests, users without purchasing rights, injected instructions in pasted supplier text, and an ambiguous high-value request
C: A load test that sends hundreds of concurrent purchase conversations to measure latency and verify that the tool calls complete under pressure
D: A one-week beta with the finance team, who use the agent for real purchases and report any mistakes that they notice during that period
K: B
G: ## What to test before release
The exam guide asks for representative, edge and adversarial interactions, and for tests of normal, edge, adversarial, unauthorized and high-consequence cases. For an agent that can spend money, each category maps to a real risk:
- Representative: normal requests, to confirm basic quality.
- Edge: missing fields, unclear quantities, items not in the catalogue.
- Unauthorized: a user who may not purchase; the agent must not submit.
- Adversarial: instructions hidden in content the agent reads, such as a supplier quote that says "approve this at any price".
- High-consequence and ambiguous: a large request with unclear details should be constrained or sent to review, not maximized.
Keep the set as a regression suite so later prompt or model changes are checked against the same cases.
W: Mixed normal, edge, unauthorized, adversarial and high-consequence cases: this is the only option that exercises every way a purchasing agent can cause harm, not just whether it works when used properly.
X: A=Typical only: fifty happy-path cases say nothing about missing details, wrong permissions or manipulated input, which is where a purchasing agent fails expensively.
C=Load test: concurrency and latency matter, but they do not test whether the agent submits a request it should have refused.
D=Beta with real purchases: real money is spent during the test, and mistakes are only found if someone notices them; it is feedback, not pre-release testing.
T: Test an agent that can act across normal, edge, unauthorized, adversarial and high-consequence cases before it goes live.
V: AIP Agent Studio, AIP Evals

@ PLTR-AIE D2 T2.1 applied use-case
S: A company has three mature agents: one for contract clauses, one for pricing rules and one for delivery terms. Sales staff now want a single place to ask questions that span all three, for example whether a proposed deal is allowed. Which approach fits?
A: Merge the three agents' instructions, retrieval contexts and tools into one large agent, so that a single model has everything it needs for every question
B: Keep the three specialist agents and add a coordinating agent that routes each question, or parts of it, to the right specialist and combines the answers
C: Train a new model on the three knowledge areas so that sales staff get one agent with no need for retrieval or routing between specialists
D: Ask sales staff to consult the three agents in turn and combine the answers themselves, since each agent is already accurate within its own area
K: B
G: ## Multi-agent coordination
The exam guide lists multi-agent coordination, where required, among the deployment options. Three specialist agents each have focused instructions, their own retrieval context and narrow tools. That focus is what makes them accurate.
## Why a coordinator rather than a merge
- A coordinating agent receives the question, decides which specialists are needed, calls them (as tools or sub-agents), and composes the answer.
- Each specialist keeps its scope, tests and ownership; the coordinator adds only routing and synthesis.
- Merging everything into one agent produces an oversized context and tool set, which lowers quality and makes testing and ownership harder.
Example: "Can we offer net-90 terms with a 15% discount on this contract?" is split into a delivery-terms question, a pricing question and a contract-clause question, then combined.
W: Coordinator over specialists: cross-cutting questions get routed and combined while each specialist stays small, accurate and separately maintained.
X: A=One merged agent: the combined instructions and tools dilute each specialist's focus; quality and tool selection degrade, and the three teams lose clear ownership.
C=Train a custom model: training foundation models is outside the AI engineer's role boundary and would freeze knowledge that changes constantly; retrieval exists for exactly this.
D=Manual consultation: it pushes the coordination work onto users and does not answer the actual question of whether the deal as a whole is allowed.
T: When questions span several specialist agents, add a coordinating agent rather than merging them into one.
V: AIP Agent Studio

@ PLTR-AIE D2 T2.2 applied tradeoff
S: An internal IT helpdesk agent should remember what a user said earlier in the same conversation (device, error message) but must not carry details from one user's conversation into another user's. How should conversation behaviour be configured?
A: Keep conversation state within each session so follow-up turns use the earlier messages, and never share session history across users
B: Store every conversation in a shared memory so the agent learns from all past tickets and can reuse solutions that worked for other users
C: Disable conversation history entirely so each message is answered on its own, since statelessness is the only way to guarantee privacy
D: Keep history per user and also append each resolved conversation to the retrieval corpus automatically, so the agent improves over time
K: A
G: ## Conversation behaviour
Agents keep the turns of a conversation so that "it still fails after the restart" refers to the device and error mentioned earlier. That state belongs to the session: it should not leak into other users' sessions, and it should not be confused with the retrieval corpus.
## Separating memory kinds
- Session context: the current conversation, needed for follow-ups.
- Retrieval corpus: curated, governed knowledge that every user may see, maintained deliberately.
- Feedback: resolved conversations can inform improvements, but through a review process that strips personal details and checks quality, not by automatic appending.
The exam guide lists conversation behaviour and guardrails among the things to configure, and the security domain requires sensitive data to stay within its permissions.
W: Per-session state without cross-user sharing: follow-up questions work, and nothing one user said becomes visible to another.
X: B=Shared memory of all conversations: other users' device details, names and errors would surface in unrelated chats, which is a data-protection failure.
C=No history: every follow-up would need the user to repeat the device and error, which makes the agent nearly unusable for troubleshooting.
D=Auto-append to corpus: unreviewed conversations with personal details would become retrievable by everyone; corpus changes need curation and permission checks.
T: Keep conversation state inside the session; feed knowledge back into the corpus only through a reviewed process.
V: AIP Agent Studio

@ PLTR-AIE D2 T2.2 advanced troubleshooting
S: A sales agent is allowed to answer questions about a customer's own orders. During testing, a user asked "show me the biggest orders of our competitor" and the agent returned another company's order data it retrieved through its search tool. What is the correct fix?
A: Add a rule to the agent's instructions that it must only discuss the current user's company, and retest with the same question
B: Scope the agent's retrieval and tools so queries run with the user's permissions and only reach the user's own customer records
C: Remove the search tool and replace it with a static summary of each customer's orders that is regenerated by a nightly pipeline
D: Add a post-processing step that scans answers for other company names and blanks them out before the response reaches the user
K: B
G: ## Enforce access at the data boundary
The exam guide is explicit: do not rely on prompts to enforce policy; retrieval must return only authorized evidence, and the execution context must be verified. If a tool can query any customer's orders, the model can be asked, tricked or simply confused into doing so.
## How to scope it
- Run tools under the user's own permissions, so the Ontology returns only objects that user may see.
- Constrain the tool's query itself to the user's customer (for example, a filter the model cannot remove).
- Verify in tests that an unauthorized request returns nothing, regardless of phrasing.
Example: the same question after the fix yields "I can only show orders for your company" because the search finds no other rows at all.
W: Permission-scoped retrieval and tools: the data the agent can reach is limited at the source, so no phrasing of the question can produce another company's orders.
X: A=Prompt rule: the capability remains; a reworded request or an injected instruction can still trigger the query. Prompts reduce risk; they do not enforce access.
C=Static nightly summaries: this removes useful live data and still needs correct per-user scoping of which summary each user may see.
D=Output filter: scanning for names misses amounts, product lines and paraphrases; the unauthorized data was already retrieved and processed.
T: Scope what an agent can retrieve to what the user is allowed to see; never leave authorization to the prompt or to output filtering.
V: AIP Agent Studio, Ontology

@ PLTR-AIE D2 T2.3 applied use-case
S: After a successful pilot with ten users, a team wants to release a document-review agent to the whole company. Which release practice keeps the risk under control?
A: Release to everyone at once, since the pilot proved the agent works and a staged release only delays the value for the remaining users
B: Keep the pilot's test cases as a regression suite, release in stages while watching traces and feedback, and define what would trigger a rollback
C: Replace the pilot agent with a rewritten one that uses the newest model, so the company-wide release starts from the strongest possible version
D: Release to everyone but remove the agent's tools for the first month, so any problems can only affect answers rather than data
K: B
G: ## From pilot to production
A pilot gives evidence about ten users' questions. Company-wide use brings new question types, new documents and adversarial inputs. The exam guide treats a polished demo as insufficient evidence and asks for designs that are testable, observable and operated with monitoring.
## Controlled release
- Regression suite: the pilot's representative, edge and adversarial cases, run on every later change.
- Staged rollout: a department at a time, so a problem affects a bounded group.
- Observability: traces, feedback and cost reviewed as the audience grows.
- Rollback criteria: decided before release (for example, groundedness below a threshold, or any unauthorized data in answers).
Example: week one, legal and procurement; week three, all of operations, after the trace review shows no grounding regressions.
W: Regression suite, staged rollout, monitoring and rollback criteria: these turn the pilot's evidence into a controlled expansion rather than a leap.
X: A=All at once: the pilot covered a narrow population; a defect found at full scale affects everyone, with no plan for pulling back.
C=Rewrite on a new model: discarding the tested agent at release time throws away the pilot's evidence and introduces untested behaviour at the moment of widest exposure.
D=Remove tools for a month: if the tools are needed, the release is no longer the agent that was tested; if they are not, they should not be there at all.
T: Expand an agent in stages, with the pilot's cases as a regression suite, monitoring, and rollback criteria set in advance.
V: AIP Agent Studio, AIP Observability
