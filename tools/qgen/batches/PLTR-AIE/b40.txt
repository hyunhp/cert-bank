# PLTR-AIE batch 40: Domain 7 round 5 (Model Selection, Observability, and Performance), 8 questions

@ PLTR-AIE D7 T7.1 applied use-case
S: A workflow must extract structured fields from images of handwritten forms. The reference sheet lists a text-only model with top benchmark scores and a vision-capable model with lower text benchmarks. Which selection is right?
A: The text-only model, since its benchmark scores are higher and published benchmarks are the most objective way to compare any two models
B: The vision-capable model, since the task requires reading images; verify it on real forms with per-field accuracy
C: The text-only model, with a note on the upload screen asking users to type the form contents into a text box before uploading the image
D: Both models in sequence, with the text-only model reviewing and correcting the vision model's output before it is written to the dataset
K: B
G: ## Capability is a hard filter
The exam guide asks you to select models from task requirements first. A task over images requires image understanding; a text-only model cannot do it at all, whatever its benchmarks.
## Selection
- Filter by modality: vision-capable.
- Evaluate on real forms: per-field accuracy, handling of poor handwriting.
- Then compare cost and latency among capable models.
Example: the vision model reaches 91% field accuracy on the suite; the text model cannot process the input.
W: The vision-capable model, verified on real forms: the only model that can perform the task, measured for how well.
X: A=Benchmarks: a text model cannot process an image at all, so its text benchmark scores are irrelevant to a form-reading task.
C=Users type contents: the workflow exists to avoid manual transcription; asking users to type the form first removes its value.
D=Sequence with text correction: the text model has no access to the image; "correction" would be guesswork.
T: Filter models by required capability (modality) before comparing scores.
V: model catalog, AIP Evals

@ PLTR-AIE D7 T7.3 applied troubleshooting
S: An engineer sees a sudden rise in "context length exceeded" errors in a workflow's execution history. What is the most likely cause and the right fix?
A: The provider silently shortened the model's context window overnight, and nothing can be done except waiting for them to restore it
B: Some input (retrieved context, history or a document) grew beyond budget; find which in the traces, bound it, add a pre-flight check
C: The model has become defective and should be swapped for a different one from the catalog as soon as possible
D: The errors are random noise from the provider's infrastructure and should be ignored until they go away on their own
K: B
G: ## Context overflows have a source
The exam guide asks you to diagnose from execution history and traces and to bound context. Overflow means something grew.
## Steps
- Traces of failing runs: token counts per component.
- Cause: a longer document family, unbounded history, more chunks.
- Fix: budget per component; summarize or truncate; pre-flight check that falls back (fewer chunks, summarized history) instead of failing.
Example: a new 300-page document type overflowed; chunked extraction replaces whole-document injection.
W: Trace-based identification of the growing component and a bounded, pre-checked context: the overflow is fixed and prevented.
X: A=Provider shrank the window: implausible and verifiable; the inputs grew.
C=Defective model: a context-length error is the model correctly refusing an input that is too large; the input is the problem.
D=Random: the errors correlate with inputs; they are not noise.
T: Context-length errors mean an input grew; find it in traces and bound it.
V: AIP Observability, AIP Logic

@ PLTR-AIE D7 T7.4 applied use-case
S: An agent's latency is dominated by a 3-second semantic search over a 20 million chunk index on every turn, even for follow-up questions on the same topic. What optimization is appropriate?
A: Removing semantic search from the agent entirely and relying on the model's general knowledge to answer every question
B: Caching retrieval results within a session for related queries, pre-filtering with metadata, and re-retrieving only when the topic changes
C: Switching to a much smaller index containing only the 1,000 most frequently retrieved chunks, so that every search is fast
D: Increasing the model's temperature so that it relies more on its own knowledge and needs retrieval less often on follow-up turns
K: B
G: ## Retrieval reuse within sessions
The exam guide lists caching and execution structure among optimizations. Follow-up turns often need the same evidence.
## Design
- Session cache keyed on query embedding similarity; reuse when the follow-up is close.
- Metadata filters from the conversation's topic to narrow the search.
- Re-retrieve on topic change.
Example: a five-turn conversation about one policy performs one full search; latency per turn drops from 3.5 to 0.8 seconds.
W: Session-level caching with topic-aware re-retrieval and pre-filtering: the expensive search runs only when needed.
X: A=Remove search: the agent loses its grounding in the corpus and starts answering from general knowledge; accuracy collapses.
C=Tiny index: questions about anything outside the 1,000 chunks become unanswerable; speed is bought with coverage.
D=Temperature: it changes how the model samples tokens; it has no effect on whether or how fast retrieval runs.
T: Cache and reuse retrieval within a session; re-retrieve only when the topic changes.
V: AIP Agent Studio, semantic search

@ PLTR-AIE D7 T7.2 applied use-case
S: An organization's policy allows only models whose providers have signed a specific data-processing agreement. How should model selection enforce this?
A: Engineers consult a shared list of approved providers from memory whenever they configure a new workflow or change a model
B: Enrollment-level enablement of only the approved models, so workflows can select only compliant ones, with observability per request
C: A disclaimer in each workflow's system prompt stating that only approved providers may process the organization's data
D: Periodic quarterly audits of workflow configurations that catch non-compliant model usage after it has been in production
K: B
G: ## Compliance by configuration
The exam guide lists enrollment and capability permissions among controls. Policy is enforced by making non-compliant models unavailable, not by memory or audits.
## Implementation
- Administrators enable only approved models in the enrollment.
- Workflows choose among them; non-approved models cannot be selected.
- Observability: model id per request for proof.
Example: a new provider is added to the approved list after signing; the model appears in the catalog the next day.
W: Enrollment-level enablement of approved models with observability: compliance is structural and provable.
X: A=Memory: a list people are supposed to remember is forgotten by someone eventually, and a non-compliant model gets configured.
C=Disclaimer: a sentence in a prompt does not stop the workflow from sending data to whichever model it is configured with.
D=Audits after the fact: by the time a quarterly audit finds the non-compliant model, data has been processed by it for months.
T: Enforce provider policy by enabling only approved models at the enrollment level.
V: model catalog, AIP Observability

@ PLTR-AIE D7 T7.3 applied use-case
S: A product owner wants to know, for each AI feature, how often the model's output was overridden by a human and how long each run took. Where should this data come from?
A: From quarterly user surveys asking people how often they changed the AI's output and how long they think it took
B: From execution traces (duration per run) joined with Action and edit records showing overrides, aggregated per feature
C: From the model provider's usage dashboard, which shows call volumes and latencies for the organization's API key
D: From the engineers' own estimates of override rates and run times, based on their experience building each feature
K: B
G: ## Joining observability with outcomes
The exam guide lists traces and execution history and asks for feedback loops from downstream outcomes. Overrides are recorded as Actions or edits in the Ontology.
## Design
- Traces: run id, feature, duration, model.
- Outcomes: override records keyed to the run or object.
- Join and aggregate per feature; trend over time.
Example: feature A has p50 latency 2.1 s and a 6% override rate; feature B 0.9 s and 14%, which prompts a quality investigation.
W: Traces joined with override records: both questions answered from recorded data.
X: A=Surveys: recollections are subjective and sparse; the system already records every run and every override.
C=Provider dashboard: it sees API calls, not which feature made them or whether a human later overrode the result.
D=Estimates: guesses from the builders are not measurements and cannot be trended or compared across features.
T: Measure AI feature performance by joining run traces with recorded human outcomes.
V: AIP Observability, Ontology

@ PLTR-AIE D7 T7.1 applied tradeoff
S: Two models meet the quality threshold for a workflow. Model A costs twice as much and is 10% faster. The workflow is a nightly batch with no latency requirement. Which should be chosen?
A: Model A, because a faster model is always the better choice and the extra cost is justified by finishing the batch sooner
B: Model B: both meet quality, latency is irrelevant for a nightly batch, and cost is the remaining differentiator; record and revisit
C: Both models, alternating nightly between them so that the team benefits from the strengths of each over the course of a week
D: Neither; keep evaluating further models until one is found that is both the cheapest and the fastest available
K: B
G: ## Selection on the criteria that matter
The exam guide asks for selection by capability, latency, cost and task requirements. When quality is equal and latency is irrelevant, cost decides.
## Reasoning
- Quality: both pass.
- Latency: no requirement for a batch.
- Cost: half.
Example: the nightly job runs in 50 minutes instead of 45 at half the cost; nobody notices the five minutes.
W: The cheaper model: both pass the quality threshold, a 10% speed difference has no value in a nightly batch with no deadline pressure, and halving the cost is the only remaining advantage.
X: A=Faster always: five minutes saved on an unattended overnight job is worth nothing; paying double for it is waste.
C=Alternate: outputs would differ night to night for no reason, and the average cost is still higher than using B.
D=Perfect model: a model that is cheapest and fastest and best rarely exists; the decision is made on the criteria that matter.
T: When quality is met and latency does not matter, choose by cost.
V: model catalog

@ PLTR-AIE D7 T7.4 applied troubleshooting
S: After enabling detailed tracing on every request, an AI workflow's own latency rose by 15%. What is the right response?
A: Disable tracing entirely and rely on user reports to find out when something goes wrong with the workflow
B: Keep tracing but tune it: sample full traces (a share plus all errors), keep cheap metrics on every request, write traces asynchronously
C: Accept the 15% latency increase permanently as the unavoidable price of having full observability on every request
D: Enable detailed tracing only at weekends when traffic is low, and run without any tracing during the working week
K: B
G: ## Observability overhead
Observability has a cost; the exam guide asks for performance optimization without losing observability. Sampling and asynchronous writes keep both.
## Design
- Metrics (latency, tokens, status) on every request; cheap.
- Full traces sampled (for example 10%) plus all errors and flagged sessions.
- Trace emission off the critical path.
Example: overhead falls to 2% while every error still has a full trace.
W: Sampled detailed traces with asynchronous writes and universal lightweight metrics: observability retained at negligible cost.
X: A=Disable: the team loses the ability to diagnose anything; user reports are late and incomplete.
C=Accept: sampling and asynchronous writes recover almost all of the latency with no loss of diagnostic value; the cost is avoidable.
D=Weekends: the problems worth diagnosing happen during the working week when traffic is highest; weekend-only tracing misses them.
T: Sample full traces and emit them asynchronously; keep cheap metrics on everything.
V: AIP Observability

@ PLTR-AIE D7 T7.2 advanced tradeoff
S: A company considers standardizing on a single model for every AI workflow to simplify operations. What should the AI engineer point out?
A: Agree; one model for everything is always best because it removes all of the complexity of comparing and maintaining several
B: Standardize on a small approved set with per-workflow selection and fallbacks, since one model misfits some tasks and risks outages
C: Refuse any standardization at all, since every workflow should be free to use whichever model its engineers happen to prefer
D: Pick the most expensive, most capable model for everything, since it will handle every task at least as well as any other
K: B
G: ## Portfolio, not monoculture
The exam guide asks for selection by requirements and for multi-provider resilience. One model cannot be optimal for extraction, chat, vision and batch classification alike, and it concentrates availability risk.
## Recommendation
- An approved, evaluated set (few models) covering modalities and tiers.
- Selection per workflow by evaluation and constraints.
- Fallbacks across providers.
Example: three approved models cover 95% of workflows; a vision model and a small classifier model serve the rest.
W: A small approved set with per-workflow selection and fallbacks: operational simplicity without forcing poor fits or single points of failure.
X: A=One model always: a text model cannot read images and a single provider outage stops every workflow at once.
C=Refuse standardization: an unbounded zoo of models multiplies evaluation, cost management and compliance work with no benefit.
D=Most expensive for all: high-volume simple tasks pay premium prices for capability they do not use.
T: Standardize on a small evaluated model portfolio, not a single model.
V: model catalog
