@ PLTR-AIE D2 T2.1 applied comparison
S: A logistics company wants an assistant that helps dispatchers inside their existing Workshop dispatch board: it should answer questions about the shipments shown on screen and propose reassignments using the board's own Actions. Which deployment fits best?
A: A standalone agent page shared by link, so that dispatchers open it in a second browser tab beside the dispatch board when they need help
B: A standard agent built in AIP Chatbot Studio and embedded in the Workshop module, with tools scoped to the shipment objects and the board's Actions
C: A scheduled AIP Logic function that writes a daily list of suggested reassignments to a dataset that the dispatch board displays
D: AIP Assist, since it is already available across the platform and can answer general questions about how Foundry and Workshop work
K: B
G: ## Standard agents versus AIP Assist
AIP Chatbot Studio (formerly AIP Agent Studio) builds **standard agents**: purpose-built assistants with their own instructions, retrieval context and tools, which can be embedded in Workshop, exposed standalone or used in AIP Studio. **AIP Assist** is the platform-wide helper for questions about using Foundry itself; it is not a place to wire custom business tools into a specific app.
## Choosing the channel
The exam guide asks you to distinguish the two by deployment context and capabilities, and to use Workshop embedding, standalone access and AIP Studio appropriately.
- Embedded in Workshop: the agent can use the module's state (what is on screen) and its Actions, so dispatchers stay in one place.
- Standalone: good for general assistants that do not depend on an app's context.
Example: "why is shipment 4471 late and who can take it?" needs the board's objects and its reassignment Action, which the embedded agent can call.
W: Embedded standard agent: it lives where the dispatchers work, sees the board's shipments and can propose reassignments through the same Actions, with tools scoped to that domain.
X: A=Standalone page: a separate tab loses the application state and forces dispatchers to describe what they are looking at; integration with the board's Actions is weaker.
C=Scheduled Logic function: a daily list is not an assistant; it cannot answer questions in the moment or react to the current board.
D=AIP Assist: it answers questions about the platform, not about a company's shipments, and it cannot be given the dispatch board's Actions.
T: For an assistant that works with an app's objects and Actions, build a standard agent and embed it in that Workshop module.
V: AIP Chatbot Studio, Workshop

@ PLTR-AIE D7 T7.4 applied troubleshooting
S: An AIP Chatbot Studio assistant in prompted tool-calling mode answers complex questions slowly. Traces show it calls its four lookup tools strictly one after another although the lookups are independent. The model in use supports native tool calling. What change addresses the cause?
A: Remove two of the tools so the model has fewer choices, even though users need all four lookups for complete answers
B: Switch the tool mode to native tool calling, which can call multiple tools in parallel and is more token efficient
C: Add a sentence to the instructions asking the model to call tools faster, which will make the prompted mode run them together
D: Increase the retrieval context so the model has all answers before using tools, and then tools are no longer needed
K: B
G: ## Two tool-calling modes
The tools page of AIP Chatbot Studio (formerly AIP Agent Studio) describes prompted tool calling, which inserts tool instructions into the prompt and allows only one tool at a time, and native tool calling, which uses the model's built-in capability, is more token efficient and can call several tools in parallel. Prompted mode is supported for all models; native mode needs a supporting model.
## Reading the trace
Sequential, independent calls at one tool per step match the single-tool limitation of prompted mode. The fix is in the mode, not the wording.
W: Native tool calling: allows parallel calls and saves tokens, removing the serial delay.
X: A=Remove tools: cuts capability to save time and users lose needed answers.
C=Ask for speed: the mode itself allows one tool per step, so no instruction can parallelise it.
D=Bigger retrieval context: adds tokens and latency and does not replace live lookups.
T: When independent tool calls run serially in prompted mode, move to native tool calling if the model supports it.
V: AIP Chatbot Studio

@ PLTR-AIE D7 T7.4 applied tradeoff
S: An AIP Chatbot Studio assistant has an object query tool on a customer object type with 60 properties; it answers questions about order status and delivery date only. Token usage per question is high. Which optimisation keeps behaviour intact?
A: Make the tool accessible to all properties so the model can choose what it needs and no information is ever missing
B: Limit the tool to the few properties needed for status and delivery questions, which is more token efficient
C: Remove the object query tool and ask users to paste the order details into every question they send themselves
D: Lower the model's output limit so that responses are cut short, before they reach their usual length for users
K: B
G: ## Smaller tool results, same answers
The AIP Chatbot Studio (formerly AIP Agent Studio) tools page says an object query tool lets you specify the accessible properties and that doing so makes queries more token efficient. Every property returned is input the model must read on each call.
## Tradeoff
- Expose what the use case needs; the model loses nothing it would use.
- Properties are added later if a new question type appears and is evaluated.
W: Restrict to needed properties: fewer tokens per call with the same answer quality, and less data exposed.
X: A=All properties: every property returned is extra input on each call, so token use and data exposure both go up for no gain.
C=Remove the tool: shifts work to users and loses the grounded lookup.
D=Lower output limit: truncates answers and does not address the large input from the tool.
T: Narrow tool results to the fields the task needs.

@ PLTR-AIE D8 T8.3 applied tradeoff
S: An AIP Chatbot Studio assistant has an Action tool that closes customer accounts. The business wants speed, so a developer proposes configuring it to run automatically. What is the better design?
A: Run it automatically but add a sentence to the instructions telling the model to be careful before closing any account
B: Remove the Action tool and make the assistant refuse every request about accounts, to avoid risk completely for everyone
C: Run it automatically and review a weekly sample, because closing mistakes can always be reversed by ordinary support staff
D: Configure the Action to run after the user's confirmation, so a person sees and approves the proposed edit first
K: D
G: ## Confirm consequential edits
The AIP Chatbot Studio (formerly AIP Agent Studio) tools page says an Action tool gives the chatbot the ability to execute an ontology edit and can be configured to run automatically or after confirmation from the user. Closing an account is hard to undo and affects a customer, so the confirmation step puts a human decision before the write.
## Why not the rest
- Prompt wording is not a control.
- After-the-fact sampling finds errors only once harm occurred.
- Removing all account capability throws away value that a gated design preserves.
W: Confirmation before execution: a person sees and approves exactly what will change before the edit is applied.
X: A=Be-careful sentence: guidance the model may ignore or be talked out of, so it is not an enforceable control.
B=Remove and refuse: over-corrects by discarding useful account help that a gated design would keep safely.
C=Weekly sample: detective, and the premise of easy reversal is unproven.
T: Gate consequential edits behind explicit human confirmation.
V: AIP Chatbot Studio, Actions

@ PLTR-AIE D8 T8.4 advanced tradeoff
S: Security worries that a manipulated AIP Chatbot Studio assistant could misuse its Action tool, which edits customer records, to change fields it never needs for its job. Which design limits the damage most directly?
A: Expose a narrow Action that edits only the few fields the use case needs, with its own submission rules, and keep user confirmation on it
B: Ask the model in the instructions to edit only the fields mentioned by the user, which holds whenever the model understands the instruction
C: Rename the sensitive fields so the model cannot recognise them, since a model that cannot recognise a field will not choose to edit it
D: Keep one broad Action that edits every field, and log each edit for later review so that mistakes are noticed by the team afterwards
K: A
G: ## Bound what a manipulated model can do
The exam guide's layered-control principle: assume the model can be manipulated and limit what it can do when it is. The product documentation reviewed does not describe an injection setting, so this answer rests on that principle and not on a product setting.
## Layers
- An Action tool runs an ontology edit and can be set to run after user confirmation, so a person sees the proposed change first.
- A narrow Action (few parameters, its own validation rules) caps the possible damage whatever the model asks for.
- Instructions, renaming and after-the-fact logs do not stop an edit.
Note: AIP Chatbot Studio was formerly called AIP Agent Studio.
W: Narrow Action with confirmation: the edit surface is small and a person approves it, whatever the model is persuaded to request.
X: B=Instruction only: a soft layer that injected text can persuade the model to override.
C=Renaming: the model still reads the field names and values it is given and can still pass them to the Action.
D=Broad Action plus logs: detective only, so the edit has already happened and the surface stays wide.
T: Limit the blast radius of a manipulated agent with narrow, confirmed Actions.
V: AIP Chatbot Studio, Actions
