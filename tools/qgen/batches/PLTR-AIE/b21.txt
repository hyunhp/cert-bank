@ PLTR-AIE D4 T4.1 applied use-case
S: A pipeline must detect which of 20 compliance topics each internal memo touches; a memo can cover several topics at once. How should the LLM step's output be designed?
A: A single enumerated field holding the one most important topic per memo, since a memo should be filed under exactly one heading
B: A typed list output restricted to the 20 topic values, allowing zero or more per memo, with validation that every value is in the list
C: A free-text paragraph describing the topics in the memo, which analysts read when they need the classification
D: A score from 1 to 10 for how compliant the memo is, since that is what compliance reviewers care about
K: B
G: ## Multi-label classification with structured output
Some classifications are multi-valued. The exam guide asks for structured outputs with validation; the schema should match the problem: a list of allowed values, possibly empty.
## Design
- Output: `topics: list<enum(20 values)>`.
- Validation: each value in the list; dedupe; empty allowed.
- Downstream: an array property or a link to Topic objects per memo, so filters like "memos touching data retention" work.
Example: a memo about vendor onboarding and data retention gets two topics, both valid.
W: A validated list of allowed topics, zero or more: it fits the multi-label requirement and keeps values governed.
X: A=One topic: memos covering several topics are misfiled, and filters miss them.
C=Free text: not filterable; the classification requirement is not met.
D=Compliance score: a different question; it does not say which topics the memo touches.
T: When items can carry multiple labels, design the output as a validated list of allowed values.

@ PLTR-AIE D4 T4.2 applied use-case
S: A pipeline uses an LLM to anonymize free-text notes before they are shared with a wider audience. What verification should accompany this step?
A: None beyond the prompt, since the model was instructed to remove all personal information and modern models follow such instructions reliably
B: Deterministic post-checks (identifier patterns, name lists), sampled human review, restricted retention of originals, and a block on rows that fail
C: A second LLM asked whether the first one did a good job, with its answer trusted
D: Publishing the output and relying on readers to report any personal information they notice
K: B
G: ## Verifying AI redaction
Anonymization is a safety-critical transformation. The exam guide pairs AI steps with deterministic post-processing and quality checks, and treats sensitive data handling as a governance matter.
## Controls
- Deterministic scanners on the output: phone, email, id patterns, known name lists.
- Fail closed: rows that trip a scanner are not published.
- Sampled human review with a measured miss rate.
- Originals and raw responses kept under the original restrictions for audit.
Example: the scanner catches a surname the model left in 0.3% of notes; those are routed to review rather than released.
W: Deterministic checks, human sampling, fail-closed publishing and restricted originals: layered assurance for a step where misses are harmful.
X: A=Trust instructions: models miss cases; an untested redaction leaks personal data.
C=Second LLM only: model judging model is still unverified; it can be one signal, not the control.
D=Readers report: by the time a reader notices, the personal data has already been exposed to the wider audience; detection after release is not protection.
T: Verify AI redaction with deterministic checks and human sampling, and fail closed.
V: Pipeline Builder, markings

@ PLTR-AIE D4 T4.3 applied comparison
S: Which processing placement correctly serves this requirement: "a Workshop list must sort 500,000 cases by an AI-generated urgency score"?
A: North of the Ontology: compute the score with a function each time the list is sorted, so that the urgency the user sees is always freshly computed
B: South of the Ontology: compute the score in the pipeline and store it as a property, since sorting needs a value on every object
C: In the Workshop module itself, using a client-side script that calls the model for the visible rows
D: In an agent that the user asks to sort the cases for them
K: B
G: ## Sorting and filtering require materialized properties
The exam guide's layer criteria include consumer breadth and scale. Sorting 500,000 objects by a value means the value must exist on every object before the sort; it cannot be computed per view.
## Design
- Pipeline LLM step scores each case; validation; stored as `urgency_score`.
- Incremental: score new or changed cases only.
- Workshop sorts and filters on the property natively.
Example: the list sorts instantly by urgency; new cases get a score within the hour.
W: Pipeline-computed property: sorting across the whole set needs a stored value, which is the south-of-Ontology case.
X: A=Compute on sort: every sort would require 500,000 model calls before the first row could be shown; it is impossible in practice.
C=Client-side for visible rows: the sort needs all rows, not the visible ones.
D=Agent: a conversation cannot produce a sorted list of 500,000 objects that a Workshop widget can display and filter.
T: Anything used to sort or filter across many objects must be materialized by the pipeline.
V: Pipeline Builder, Workshop

@ PLTR-AIE D4 T4.4 applied troubleshooting
S: An LLM transform in a Code Repository runs nightly and occasionally fails entirely when the model provider has a brief outage, leaving the dataset unbuilt for a day. What change improves resilience?
A: Remove the transform from the nightly schedule and run it by hand on days when the provider's status page shows that the service is stable
B: Add per-row error handling with retries, write processed rows plus a status column for failures, and reprocess only failed rows in a follow-up run
C: Switch providers every night to whichever one is up at the time
D: Catch all errors and write nulls for every row so the build always succeeds
K: B
G: ## Partial failure handling in AI transforms
The exam guide lists retries, rate limiting and programmatic control among reasons to codify in Code Repositories. A whole-build failure on a transient outage is a design choice, not a necessity.
## Design
- Row-level try/except with retries and backoff.
- Output: processed rows with results; failed rows with `status = retry` and the error.
- Follow-up run (or next incremental run) reprocesses `retry` rows.
- Alert if the failure rate exceeds a threshold.
Example: a 10-minute outage leaves 2% of rows pending; they are completed at the next run; consumers see the rest on time.
W: Row-level error handling with recorded retries: the build degrades gracefully and completes the remainder later.
X: A=Manual runs: unreliable and dependent on someone checking a status page; the nightly schedule exists so the data arrives without that.
C=Provider roulette: inconsistent quality and configuration; a fallback model is fine, but nightly switching is not a design.
D=Nulls for all: it hides failures as missing data for every row, including ones that succeeded.
T: Make AI transforms fail per row with recorded retries, not per build.
V: Code Repositories

@ PLTR-AIE D4 T4.1 applied use-case
S: A team wants an LLM to extract line items (description, quantity, unit price) from 200,000 purchase orders, which have widely varying layouts. Which prompt and output design is most robust?
A: A prompt asking for a plain-text list of what the model finds, since the layouts vary far too much for any fixed structure to capture them
B: A structured list schema, few-shot examples across layouts, arithmetic validation (quantity × price vs total), and review routing for failures
C: One prompt per known layout, with a manual step to classify each order's layout first
D: Extracting only the order total, since line items are too hard
K: B
G: ## Robust extraction design
The exam guide pairs entity extraction with structured output and validation. Layout variety is handled by instructions and examples, not by abandoning structure.
## Design
- Schema: `items: list<{description, quantity, unit_price, line_total?}>`.
- Prompt: few-shot examples spanning layouts (tables, free text, multi-page).
- Validation: arithmetic consistency, non-negative numbers, item count sanity.
- Review queue for failures; raw responses kept.
Example: a handwritten-style order yields three items; the arithmetic check flags one misread price for review.
W: Structured list schema, layout-diverse examples, arithmetic validation and review routing: robust to variety and safe on errors.
X: A=Plain text: unparseable at scale; the requirement is structured line items.
C=Per-layout prompts: a manual classification step for 200,000 orders is impractical.
D=Totals only: the requirement is line items with quantities and prices; extracting the total alone does not meet it and gives up too early.
T: Handle layout variety with examples and validation inside a structured-output design.
V: Pipeline Builder, AIP

@ PLTR-AIE D4 T4.2 applied tradeoff
S: An AI enrichment pipeline's audit requirements say that any output must be reproducible "to the extent possible". The team notes that LLM outputs are non-deterministic. What should the pipeline record and state?
A: Nothing, since reproducibility is impossible with non-deterministic models and the requirement therefore cannot be met in any meaningful way
B: The input, prompt version, model and parameters, and the raw response, with a documented note that re-runs may differ and the stored response is the record
C: Only the final output, since that is what auditors look at
D: A hash of the output so auditors can verify it has not changed
K: B
G: ## Reproducibility with non-deterministic models
The exam guide asks to preserve prompts and raw responses where auditability requires. Full reproduction is not guaranteed, but explanation and re-execution under identical configuration are.
## Record
- Input reference, prompt version, model id, parameters (temperature), timestamp.
- Raw response: the authoritative evidence of what the model produced.
- Policy statement: re-runs may vary; the stored response is the record.
Example: an auditor sees that row 4421 was produced by prompt v9 on model X at temperature 0.1, with the raw response attached.
W: Configuration plus raw response, with the limitation documented: this is "to the extent possible" done properly.
X: A=Give up: explanation and configuration capture are possible and expected.
C=Output only: there is no way to explain how the value arose, which prompt produced it or whether the model has since changed.
D=Hash: a hash proves the stored output has not been altered; it says nothing about how the output was produced or by what configuration.
T: Record configuration and raw responses for AI outputs and document the limits of reproducibility.
V: Pipeline Builder

@ PLTR-AIE D4 T4.3 applied use-case
S: A service desk wants each new ticket enriched with a suggested resolution drawn from past tickets, visible to agents when they open it, and refreshed if the knowledge base changes. Where should the retrieval-and-suggest step run?
A: Entirely north: generate a fresh suggestion from retrieval every time an agent opens the ticket, so it always reflects the latest knowledge base
B: Index south in the pipeline; compute and store an initial suggestion on ticket creation; allow an on-demand refresh north when the agent asks
C: In a nightly batch only, so suggestions appear the day after a ticket is created
D: Nowhere; agents should search manually
K: B
G: ## Hybrid placement
The exam guide allows combining layers: reusable batch work south, interactive refinement north. A suggestion needed at ticket creation and sometimes refreshed is a hybrid.
## Design
- Pipeline: embeddings for knowledge and past tickets (index maintenance).
- On creation: an automation runs the suggest function once and stores the result (south-ish, event-driven).
- On demand: a Workshop button triggers a fresh suggestion with the agent's added notes (north).
Example: the ticket opens with a stored suggestion; after the agent adds a note, a refresh produces a better one.
W: Index south, initial suggestion on creation, optional refresh north: each part placed by reuse and interactivity.
X: A=Every open: repeated cost for the same ticket and no stored value for reporting.
C=Nightly only: a service desk needs the suggestion when the ticket arrives; a next-day suggestion is useless for most tickets.
D=Manual: agents searching by hand is the status quo the team wants to replace; it does not meet the requirement.
T: Combine layers: maintain indexes and initial results in the pipeline/automation, refine interactively when asked.
V: Pipeline Builder, Automate, AIP Logic

@ PLTR-AIE D4 T4.1 advanced troubleshooting
S: An LLM classification transform's accuracy on the evaluation set is 95%, but production outputs show a category assigned to 40% of rows that the evaluation set rated at 5%. What is the likely issue?
A: The model has become biased and should be retrained
B: Production inputs differ from the suite or the prompt misfires on real inputs; sample the over-assigned rows, compare input traits, update suite and prompt
C: The evaluation set was clearly too easy and should be deleted so that the team is no longer misled by its 95% accuracy figure
D: Nothing; 40% is the true rate
K: B
G: ## Distribution shift between evaluation and production
A suite measures performance on its own inputs. The exam guide asks you to distinguish distribution changes from regressions and to monitor real behaviour.
## Investigation
- Sample rows assigned the suspicious category; are they correct? If yes, the input mix changed; if no, the prompt misfires on a new input style.
- Compare input features (length, source, language) between production and the suite.
- Fix: add representative production samples to the suite; adjust the prompt for the new style; re-measure.
Example: a new ticket source submits short, vague descriptions that the prompt defaults to "other"; adding guidance and 50 such cases fixes both the output and the suite.
W: Distribution shift or prompt behaviour on real inputs, diagnosed by sampling and comparison: the suite and the prompt are then updated together.
X: A=Retrain: not the role, and the likely cause is input shift, not model drift.
C=Delete the suite: the suite is still valid for what it covers; it should be extended with production-like cases, not discarded.
D=Accept: a tenfold jump needs verification before trusting it.
T: Large gaps between evaluation and production rates mean the inputs differ; sample, compare and update the suite.
V: AIP Evals, Pipeline Builder
