# PLTR-AIE batch 25: Domain 8 round 3 (Security, Governance, and Responsible AI), 8 questions

@ PLTR-AIE D8 T8.1 applied use-case
S: An agent is available to the whole company, but one of its tools queries a dataset that only the finance group may read. How should the configuration handle this so that permissions are respected without breaking the agent for everyone else?
A: Give every user the finance marking so the tool works for all of them, since an agent that fails for most users is a poor experience
B: Run the tool under each user's own permissions, so finance users get results and others get an empty result the agent explains
C: Run the tool under a privileged service identity so that all users receive finance results regardless of their own permissions
D: Remove the tool from the agent entirely, since any tool with restricted data cannot be offered in a company-wide agent
K: B
G: ## Per-user execution for mixed audiences
The exam guide asks you to apply execution security modes and enforce least privilege at retrieval and tool boundaries. Executing a tool as the calling user lets the Ontology's own permissions decide what each person sees.
## Behaviour
- Finance users: the tool returns data.
- Others: the tool returns nothing (authorized empty), and the agent says the information is not available to them.
- No data leaks; no one is over-provisioned.
Example: a finance analyst gets budget figures; an engineer asking the same question is told the data is restricted.
W: User-scoped tool execution with an explanatory behaviour: permissions are respected automatically and the agent remains useful for everyone.
X: A=Grant everyone: over-provisioning hundreds of users to make a tool work.
C=Privileged identity: leaks finance data to every user; a classic execution-mode mistake.
D=Remove the tool: finance users lose a legitimate capability.
T: Execute agent tools as the user so Ontology permissions decide what each person can see.
V: AIP Agent Studio, Ontology

@ PLTR-AIE D8 T8.2 applied use-case
S: A customer asks a company to delete their personal data. The company's AI workflows have stored chunk embeddings, raw model responses and generated summaries containing that customer's data. What must the AI engineer's design support?
A: Nothing, since derived artefacts such as embeddings and summaries are not personal data and are exempt from deletion requests
B: Traceability from the customer to every derived artefact (chunks, vectors, raw responses, outputs) so deletion can be executed and verified
C: Deletion of the source record only, since downstream artefacts will be rebuilt automatically from scratch by the next pipeline run
D: Deletion only of artefacts that are visible to users, since internal artefacts cannot cause harm to the customer
K: B
G: ## Data protection across AI artefacts
The exam guide asks for understanding of data-protection architecture, audit and lineage. Derived artefacts that carry personal data are still personal data.
## Design
- Every chunk, vector, response and output references its source record (customer id).
- Lineage shows where the source flowed.
- Deletion: remove or re-derive all artefacts for that id; verify with a query that nothing remains.
- Retention policies that bound how long raw responses live.
Example: a deletion request removes the customer's 40 chunks, their vectors, 12 raw responses and 3 summaries, confirmed by lineage-based search.
W: Identifier-based traceability through lineage: deletion can be complete and provable across every artefact.
X: A=Exempt: derived data containing personal information is personal data.
C=Source only: artefacts persist until rebuilt, and some (raw responses) are never rebuilt.
D=Visible only: internal copies are still retained personal data.
T: Design AI pipelines so every derived artefact traces to its source record and can be deleted and verified.
V: Data Lineage, Ontology

@ PLTR-AIE D8 T8.3 applied use-case
S: An AI function flags transactions as potential fraud for an investigations team. Which design respects the consequence of a wrong flag for the customer?
A: Automatically freeze the customer's account on any flag, since speed matters more than accuracy when fraud is suspected
B: Treat the flag as a recommendation with reasons; an investigator decides any customer-impacting action; monitor false positives; allow appeals
C: Notify the customer directly by email that they are suspected of fraud, so they can defend themselves before any internal investigation starts
D: Ignore flags below a confidence of 99% so that only near-certain cases are ever reviewed by the investigations team
K: B
G: ## Consequential decisions about people
A fraud flag can lead to frozen funds and reputational harm. The exam guide asks for human review of high-consequence actions, validation proportional to consequence, and attention to fairness.
## Design
- Output: flag, confidence, reasons (explainable).
- Human decision for any customer-impacting action.
- Fairness monitoring: false-positive rates by segment; adversarial and edge cases in the suite.
- Appeals and audit trail.
Example: a flagged transaction is reviewed within an hour; the investigator clears it after seeing the reason was a merchant category mismatch.
W: Recommendation with reasons, human decision, fairness monitoring and appeals: proportionate to the consequence.
X: A=Auto-freeze: a false positive harms an innocent customer immediately.
C=Notify the customer first: alerts actual fraudsters and distresses innocent customers unnecessarily.
D=99% threshold only: most real fraud would be missed; thresholds should be set by measured trade-offs with humans in the loop.
T: AI flags about people are inputs to human decisions, with explainability, fairness monitoring and appeal.
V: AIP Logic, AIP Evals

@ PLTR-AIE D8 T8.4 applied troubleshooting
S: Security review finds that an agent's tool can accept an arbitrary query string that the model composes. A crafted conversation made the model compose a query that returned records outside the intended scope. What is the right fix?
A: Add a prompt instruction telling the model to compose only safe queries that stay strictly within the current user's own records and nothing else
B: Constrain the tool: replace free-form query strings with typed parameters bound to the user's scope, and run it under the user's permissions
C: Log all queries the model composes and review them weekly for scope violations
D: Limit the tool to returning at most ten records, which bounds how much data a crafted query can expose
K: B
G: ## Tool interfaces as a security boundary
A free-form query parameter turns the model into a query author under attacker influence. The exam guide asks you to enforce controls at the tool boundary and to recognize unsafe tool-use risks.
## Fix
- Typed parameters: the tool takes a customer id (from context, not the model) and a small set of filters.
- Scope binding: the tool itself adds the user's scope; the model cannot remove it.
- Permission execution: as the user, so the Ontology also enforces.
- Adversarial tests for scope escape.
Example: the tool signature becomes `search_orders(status, date_range)` with the customer fixed from the session; no query string exists to craft.
W: Typed, scope-bound tool interface with permission-scoped execution: the model cannot compose an out-of-scope query at all.
X: A=Prompt instruction: the model is the thing being manipulated; instructions do not bound the tool.
C=Weekly log review: the out-of-scope records have already been exposed by the time anyone reads the logs; detection is not prevention.
D=Ten-record cap: ten unauthorized records per query is still a breach, and repeated crafted queries can page through much more.
T: Design tool interfaces with typed, scope-bound parameters so the model cannot author unsafe queries.
V: AIP Agent Studio, Ontology

@ PLTR-AIE D8 T8.1 applied tradeoff
S: A department wants to turn off the organization's capacity limits for AI usage because their workflow was throttled during a busy week. What should the AI engineer recommend?
A: Turn off the limits for everyone, since throttling legitimate work is worse than any risk from unlimited usage
B: Keep the limits; analyze and optimize the throttled workflow, then request a justified, monitored capacity increase for it
C: Turn off the limits for that department only, since they have demonstrated a real need and will manage their own usage
D: Advise the department to split their workflow across several accounts to stay under each account's limit
K: B
G: ## Capacity controls are governance
The exam guide lists capacity controls among the controls to apply. Limits protect budgets, provider quotas and other workflows from runaway consumption, including loops and attacks.
## Response
- Diagnose the throttling: was the usage efficient? Often caching or batching removes the need.
- Request a specific, monitored increase for the workflow with a justification.
- Keep the control in place for everyone.
Example: the busy week's usage came from re-embedding unchanged documents; a cache fixes it and the limit is never hit again.
W: Keep the control, optimize, and raise capacity by justified exception: the need is met without removing protection.
X: A=Remove for all: a loop or an attack could then consume unbounded budget.
C=Remove for one department: the same risk, scoped; self-management is not a control.
D=Account splitting: circumventing limits violates policy and hides usage.
T: Capacity limits stay; meet real needs through optimization and justified, monitored increases.
V: AIP

@ PLTR-AIE D8 T8.2 applied use-case
S: A company must be able to answer, for any AI-generated recommendation, "which version of which policy document did the model rely on". What does the retrieval design need?
A: A note in the system prompt listing the policy documents the model is allowed to use for its recommendations
B: Chunks carrying document id and version metadata, injected with those ids, and outputs recording the cited chunk ids
C: A copy of the entire policy library attached to every recommendation so that any version can be found later if needed
D: The model's own statement of which policy it used, included in its answer text for auditors to read
K: B
G: ## Provenance to the version
The exam guide asks for audit and lineage evidence and for provenance exposed to the workflow. "Which version" requires version metadata at chunk level and citation at output level.
## Design
- Chunk metadata: document id, version, effective dates.
- Injection with identifiers.
- Output: cited chunk ids; validation that cited ids were actually retrieved.
- Stored with the recommendation.
Example: recommendation R-2211 cites policy P-14 v7, section 3.2; a later question about why it differs from today's advice is answered by the version change.
W: Versioned chunk metadata carried into citations: the question becomes a lookup rather than an investigation.
X: A=Prompt note: it lists what may be used, not what was used, and never the version.
C=Whole library copy: enormous and still does not say which part was relied on.
D=Model's self-report: a model's statement of which policy it used is unverifiable and may be invented; auditors need recorded identifiers.
T: Carry document version metadata through retrieval into validated citations.
V: Ontology, semantic search

@ PLTR-AIE D8 T8.3 applied tradeoff
S: Which design correctly applies "match validation strictness to consequence" for an AI workflow that both answers product questions and can issue store credit?
A: Apply the same strict human approval to every output, including product answers, so that the workflow is uniformly safe
B: Light validation (groundedness, refusal path) for product answers; strict validation, limits and approval for store credit, with audit
C: No validation for either, since the workflow is customer-facing and validation would slow down responses for customers
D: Strict validation for product answers because they are frequent and errors add up, and light validation for store credit because it is rare
K: B
G: ## Strictness follows consequence, not frequency
The exam guide asks for validation strictness matched to consequence and human review for high-consequence actions. Product answers carry informational risk; store credit changes money.
## Design
- Answers: grounded, cited, with refusal when evidence is missing; monitored.
- Credit: validated amount, per-customer limits, idempotent execution, approval above a threshold, audit.
Example: a question about return windows is answered instantly; a 200-credit request becomes an approval task.
W: Light for informational, strict for monetary: this applies the proportionality rule exactly, keeping answers fast while every credit is validated, bounded and approved where it matters.
X: A=Strict everywhere: product answers would be delayed for no benefit, and reviewers overwhelmed.
C=None: the workflow could issue credit on a manipulated conversation with nothing to stop it; speed is not a reason to drop controls on money.
D=By frequency: backwards; rare but costly actions need the most control.
T: Validation strictness follows the consequence of the action, not how often it happens.
V: Actions, AIP Agent Studio

@ PLTR-AIE D8 T8.4 advanced tradeoff
S: A company deploys an AI agent that reads incoming documents from external parties. Which combination best reflects defence in depth against prompt injection for this agent?
A: A single strong system prompt instruction to ignore any instructions found within documents, reviewed quarterly by the security team
B: Content isolation, least-privilege tools, no consequential Actions on document content alone, input/output checks, approval, monitoring, tests
C: Blocking all external documents from being processed by the agent, which removes the possibility of injection altogether at the cost of the use case
D: Relying on the model provider's built-in safety features, since modern models are trained to recognize and ignore injected instructions
K: B
G: ## Layers against injection
The exam guide names prompt injection among risks and asks for defensive controls at multiple boundaries. No single layer is sufficient; together they reduce likelihood and impact.
## Layers
- Isolation: content is data, clearly delimited.
- Capability: no consequential Action can be triggered by document content alone; human approval for state changes.
- Detection: input scanning, output checks, flagged-session monitoring.
- Assurance: adversarial cases in the regression suite.
Example: an injected "approve this invoice" in a PDF is detected on input, cannot trigger the approve Action without human review, and the session is logged.
W: Isolation, least privilege, detection, human approval, monitoring and tests: defence in depth as the guide intends.
X: A=One instruction: a prompt line is the layer most easily defeated by a crafted document, and alone it leaves nothing behind it.
C=Block the use case: removing all external documents abandons the business purpose; it is a last resort when controls truly cannot manage the risk.
D=Provider only: provider training helps but does not know the application's tools and risks.
T: Defend against injection with layered controls spanning isolation, capability, detection, approval and testing.
V: AIP Agent Studio, Actions, AIP Evals
