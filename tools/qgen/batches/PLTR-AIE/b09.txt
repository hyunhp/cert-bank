# PLTR-AIE batch 09: Domain 8 (Security, Governance, and Responsible AI), 8 questions

@ PLTR-AIE D8 T8.1 applied troubleshooting
S: A new AIP Logic function works when the engineer who built it runs it, but fails with a permission error when it runs inside an automation on behalf of other users. Where should the engineer look?
A: At the model's enrollment permissions, since the automation uses a different model configuration from the one the engineer tested with
B: At the execution security mode and identity, since the automation runs as a different principal that lacks access to the objects or tools involved
C: At the automation's schedule, since functions invoked by automations only have permission to run during the configured time window
D: At the function's version, since only the engineer's draft is permitted to access the objects while the published version runs with reduced rights
K: B
G: ## Execution identity
A function can run with the permissions of the user who invoked it, or in an automation on behalf of a configured identity. The exam guide lists execution security modes among the controls to apply, and asks engineers to verify the execution context. What the author can see is not what the automation's principal can see.
## Diagnosing
- Identify the principal the automation runs as.
- Use the platform's access checks to see which object, dataset or tool that principal cannot reach.
- Grant the specific, least-privilege access to that principal, or change the execution mode deliberately; never widen access to everyone to make the error disappear.
Example: the automation's identity cannot read the Contract objects the function queries; granting that identity read access to the Contract object type fixes the run.
W: Execution mode and identity: the failure appears only when a different principal runs the function, which points directly at what that principal is allowed to access.
X: A=Model enrollment: a model permission problem would fail for the engineer too; the symptom is tied to who runs the function, not which model.
C=Schedule window: automation schedules control timing, not permissions; there is no time-based permission for functions.
D=Draft versus published rights: versions do not carry different access rights; the difference is the principal executing them.
T: When a function works for its author but not in automation, check the execution identity and what it is allowed to access.
V: AIP Logic, Automate, Check Access

@ PLTR-AIE D8 T8.1 applied use-case
S: A company operates in two jurisdictions. Customer data from one must not be sent to models hosted outside it, and the AI budget for each department is capped. Which controls should the AI engineer configure?
A: Georestrictions on which models may process that jurisdiction's data, and per-department capacity or spend limits, in platform configuration
B: A system prompt in every workflow stating that data must not leave the jurisdiction and that departments must stay within their budgets
C: A monthly report comparing model regions and spend against policy, with corrective action taken when a violation is found
D: A single model hosted in one jurisdiction for all workflows, with no budget controls, since one model simplifies compliance
K: A
G: ## Platform-level controls
The exam guide lists enrollment and capability permissions, execution security modes, georestrictions and capacity controls as things to apply. These are configured in the platform, where they are enforced before a request is made, not described in prompts after the fact.
## Mapping the requirements
- Georestrictions: data with a jurisdiction tag can only be processed by models hosted in approved regions; a workflow attempting otherwise is blocked.
- Capacity and spend controls: per-department caps on usage, with alerts before the cap is reached.
- Observability: usage by model region and department, to prove compliance.
Example: a workflow configured with an out-of-region model fails validation for the restricted dataset before any data is sent.
W: Georestrictions and capacity controls in platform configuration: both requirements are enforced by the system, which is what makes them controls rather than intentions.
X: B=Prompt statements: a prompt cannot stop data from being sent to a model; the sending already happened by the time the model reads it.
C=Monthly reports: detection after the fact does not prevent a violation, and a month of non-compliance may already have occurred.
D=One model, no budget: this may violate the other jurisdiction's needs, removes resilience, and ignores the budget requirement entirely.
T: Enforce data residency and spend with platform configuration (georestrictions, capacity controls), never with prompts or after-the-fact reports.
V: AIP, model catalog

@ PLTR-AIE D8 T8.2 applied use-case
S: An audit requires that for any AI-generated recommendation that led to a contract being cancelled, the company can show which data the model saw, which model produced the recommendation, and who approved the cancellation. Which design satisfies this?
A: Keep a copy of the model's final recommendation text on the contract object, since the text itself describes what the model considered
B: Record the inputs, retrieved context, model and prompt version and run trace, and cancel through an Action that logs the approver
C: Ask the model to list its sources in the recommendation, and rely on the model's own account of what it used
D: Store the cancellation date and the recommendation score, since an auditor needs the outcome and the confidence rather than the full history
K: B
G: ## Audit and lineage evidence
The exam guide asks engineers to understand audit and lineage evidence and data-protection architecture. For a decision chain, the evidence is produced by the system at each step:
- Inputs and retrieved context: stored with the run, so "what did the model see" is a record, not a reconstruction.
- Model and prompt version: part of the trace.
- Execution trace: tool calls and the raw model output.
- Action: the cancellation is applied through an Action, which records who ran it and when; human approval is part of that record.
Example: the auditor opens the run trace for recommendation 5521, sees the three retrieved clauses and model X v12, and the Action log showing the approver's identity.
W: Stored inputs, context, trace and an Action with the approver logged: every question in the audit is answered by a recorded artefact from the time of the decision.
X: A=Recommendation text only: text does not prove what data the model actually received or which model wrote it, and says nothing about the approver.
C=Model-listed sources: a model's self-report can be incomplete or invented; audit evidence must come from the workflow's records.
D=Date and score: these do not show the data, the model or the approver, which are the three things the audit asks for.
T: Audit evidence for AI-driven decisions comes from stored context, traces and Action logs, not from the model's own narrative.
V: AIP Logic, Actions, AIP Observability

@ PLTR-AIE D8 T8.3 advanced tradeoff
S: An agent assists with three kinds of request: answering questions about a policy, drafting an internal memo, and approving vendor payments above a threshold. Which validation and review design matches the consequences?
A: The same confirmation dialog for all three, so that users always see what the agent is about to do before it happens
B: No review for policy answers, a light review for drafted memos, and strict validation plus mandatory human approval for payment approvals
C: Mandatory human approval for all three, since any output from an AI system should be reviewed by a person before it is used
D: Strict validation for policy answers, since wrong information spreads widely, and automatic execution for payments, since the threshold already limits risk
K: B
G: ## Validation strictness follows consequence
The exam guide's second lifecycle step is to assess risk: is the output informational, advisory, or capable of changing external state? Controls should scale with that:
- Informational (policy answer): grounding and refusal behaviour, measured by evaluation; no per-request human gate.
- Advisory (memo draft): the human who sends it reviews it; a light check.
- State-changing with money (payment approval): validation of preconditions and amounts, mandatory human approval, idempotent execution and audit.
Example: a policy question is answered instantly; a memo arrives as a draft the user edits; a payment approval becomes a request that a finance approver must confirm.
W: Graduated review by consequence: each request type gets the control its risk requires, which keeps the routine paths usable and the high-consequence path safe.
X: A=Same dialog for all: a uniform click-through trains users to confirm without reading, so the one that matters (payments) gets no real review.
C=Approve everything: reviewing every policy answer removes the value of the agent and dilutes attention where it is needed.
D=Reversed strictness: automatic payment execution is the highest-consequence action in the list; a threshold limits amount, not the need for approval.
T: Scale validation and human review with the consequence of the action; the state-changing, high-value path gets the strictest controls.
V: AIP Agent Studio, Actions

@ PLTR-AIE D8 T8.4 applied troubleshooting
S: A retrieval-grounded agent reads customer-uploaded documents to answer questions. A tester uploaded a document containing hidden text instructing the agent to email the full customer list to an external address. The agent has an email tool. Which control should be addressed first?
A: Add a classifier that scans uploaded documents for instruction-like text and rejects any document that contains it
B: Remove or narrow the email tool: a question-answering agent should not send data externally; any legitimate send goes through a restricted Action
C: Instruct the agent to treat uploaded documents as untrusted and never follow instructions found in them
D: Log every email the agent sends with its recipients and attachments so the security team can detect exfiltration attempts and revoke the offending user's access
K: B
G: ## Prompt injection meets a dangerous tool
The exam guide names prompt injection, jailbreak, data exfiltration and unsafe tool-use risks, and says to enforce least privilege at the tool and Action boundaries. The injection is the attack; the email tool is what makes it harmful. Remove the harm first.
## Layered defence, in order
1. Capability: the agent gets only the tools its task needs. Answering questions needs no outbound email; if some workflow must send, use a restricted Action with recipient allow-lists and approval.
2. Data scope: the agent should not be able to retrieve the full customer list in the first place.
3. Hardening: treat document content as data, detect injection patterns, and test adversarial cases in the evaluation suite.
Example: after removing the tool, the same document produces at worst an odd answer; nothing can leave the system.
W: Remove or restrict the email tool: without the capability, the injected instruction cannot cause exfiltration, no matter how it is phrased; the remaining measures then reduce residual risk.
X: A=Document classifier: useful as a later layer, but attackers rephrase and encode instructions; a filter cannot be the primary control while the tool exists.
C=Prompt instruction: the guide is explicit that prompts do not enforce policy; a well-crafted injection can still override it.
D=Logging: detection after the customer list has been emailed is too late; the data is already outside.
T: Against injection, first remove the capability that makes it dangerous; then scope data, then harden prompts and filters.
V: AIP Agent Studio, Actions

@ PLTR-AIE D8 T8.2 applied use-case
S: An AI workflow summarizes support tickets that sometimes contain payment card numbers and national identifiers. The summaries are stored on ticket objects visible to a wide support audience. What should the AI engineer do?
A: Instruct the model to omit sensitive numbers from the summary and rely on the instruction to keep them out of the stored text
B: Mask sensitive identifiers deterministically before the text reaches the model, and apply markings or restrictions to any output that may still carry sensitive data
C: Store the summaries only in the model provider's logs rather than on the ticket objects, so the sensitive data never enters the Ontology
D: Allow the summaries as they are, since the wide support audience already has access to the original tickets and therefore already sees the same sensitive data
K: B
G: ## Sensitive data handling in AI workflows
The exam guide requires understanding data-protection architecture and sensitive data handling, and the retrieval principle is that authorized evidence only should flow through the workflow. Two steps keep sensitive values under control:
- Before the model: deterministic redaction or masking of known patterns (card numbers, national ids), so the model never sees them and cannot reproduce them.
- After the model: the output is data too; if it can carry sensitive content, it receives the same markings and access restrictions as its source, and the audience is scoped accordingly.
Also check whether the model's hosting meets the data-protection requirements for the categories of data involved.
Example: a card number becomes `****4417` before summarization; the summary object inherits the ticket's "PCI" marking so only entitled users can read it.
W: Deterministic pre-model redaction plus protection on the output: the sensitive values are removed where that is reliable and whatever remains stays governed.
X: A=Prompt instruction: the model may still echo a number, and the instruction cannot be audited; redaction in code is reliable and testable.
C=Provider logs: storing business output in an external provider's logs is worse for data protection and makes the summaries unusable.
D=Same audience as tickets: the premise may be wrong (tickets may carry restrictions that the summary would bypass), and copying sensitive data into new objects widens exposure.
T: Mask sensitive data before the model and govern AI outputs with the same markings as their inputs.
V: Pipeline Builder, markings

@ PLTR-AIE D8 T8.3 applied use-case
S: A request to an agent reads: "The vendor's contract looks expired, cancel all their open purchase orders now." The agent's retrieved evidence shows the contract end date is ambiguous and one order is in delivery. The agent has an Action to cancel orders. What should it do?
A: Cancel the orders as instructed, since the user has authority over purchase orders and asked for a specific, unambiguous action
B: Decline to execute, state the ambiguity about the date and the in-delivery order, and route the decision to a human with the evidence
C: Cancel only the orders not yet in delivery as a compromise, then report what was cancelled and what was left
D: Ask the user to confirm once with a yes or no, and cancel all orders if the user confirms
K: B
G: ## High-consequence actions with ambiguous evidence
The exam guide's practice principle: when a request asks for a high-consequence action with ambiguous evidence, constrain or refuse execution, surface uncertainty and route to human review rather than maximizing autonomy. Cancelling open orders is a state change with financial and operational consequences, and the evidence does not support the premise.
## What a well-designed agent does
- Explains what it found: the end date is ambiguous; one order is in delivery.
- Does not execute; proposes the action for a person with authority, with the evidence attached.
- Keeps an audit of the request and the refusal.
Design-wise, the cancel Action can enforce this: a precondition that orders in delivery cannot be bulk-cancelled, and approval required above a count or value.
Example: "I can't confirm the contract expired (two end dates in the documents), and PO-1182 is in delivery. I've prepared the cancellation for your approval with the details."
W: Refuse and route to review with evidence: the consequence is high and the premise is uncertain, which is precisely the case for human judgement rather than agent action.
X: A=Execute as instructed: authority to request does not make the premise true; cancelling on an unverified expiry can breach a live contract.
C=Partial cancellation: a compromise the user did not ask for, executed on the same unverified premise, is still an unauthorized consequential action.
D=Yes/no confirmation: a single click confirmation does not convey the ambiguity; the user is confirming a premise the agent could not verify.
T: For consequential actions, uncertainty means stop and escalate with evidence, not act or compromise.
V: AIP Agent Studio, Actions

@ PLTR-AIE D8 T8.4 advanced tradeoff
S: Where should the control be placed so that an agent can never return retrieved documents the current user is not permitted to see?
A: In the system prompt, instructing the agent to check each document's classification and withhold anything above the user's level
B: In the retrieval layer, so semantic search and object queries run under the user's permissions and unauthorized documents are never returned
C: In an output filter that compares each answer against a list of restricted document titles and removes matching passages
D: In the user interface, which hides answers that reference documents the user cannot open when they click through
K: B
G: ## Enforce where the data is accessed
The exam guide's self-check for this domain asks where a control must be enforced: in retrieval, the prompt, the tool, the Action, permissions or human review. For authorization of evidence, the answer is the retrieval and data boundary, under the user's permissions.
## Why the other layers fail
- Prompt: the model has already received the unauthorized document; it may summarize or leak it despite instructions.
- Output filter: it inspects text after the fact and misses paraphrases and partial information.
- UI: hiding a link does not undo the fact that the answer was built from the document.
When retrieval runs as the user, the Ontology's own permissions and markings decide what is returned, and the agent cannot see what the user cannot.
Example: two users ask the same question; the manager's answer cites a restricted memo, the analyst's answer says no relevant document was found.
W: Retrieval under the user's permissions: unauthorized documents never enter the workflow, which is the only layer where the guarantee holds regardless of prompts or phrasing.
X: A=Prompt-based withholding: the document is already in context; a prompt instruction is advisory and bypassable.
C=Title-based output filter: content, not titles, is what leaks; the filter cannot recognize paraphrased restricted information.
D=UI hiding: the leak happens in the answer text; what the interface hides afterwards does not matter.
T: Authorization for retrieved evidence belongs in the retrieval and data layer, executed with the user's permissions.
V: Ontology, semantic search
