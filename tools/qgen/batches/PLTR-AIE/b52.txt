@ PLTR-AIE D4 T4.4 applied tradeoff
S: A nightly Code Repositories transform sends every row of a 2-million-row support-ticket dataset to a model for sentiment scoring. Only about 4,000 tickets change each day, yet the run is slow and the model bill is large. What is the best change?
A: Process only the rows that are new or changed since the last successful run, and keep earlier scores in the output
B: Switch the model to a smaller tier and keep scoring all 2 million rows every night so the output stays fully refreshed
C: Run the same job twice a day on separate schedules so that each run has fewer rows left to finish before the deadline
D: Cache the scores in the transform's memory between runs so that repeated rows are not scored a second time
K: A
G: ## Do the model work only once per row
The exam guide places scheduled, programmatic LLM work in Code Repositories and asks for cost and rate awareness. A nightly job that rescored unchanged rows pays for answers it already has.
## Approach
- Read the new or changed rows (incremental processing), score only those, and append or merge them into the output.
- Keep the earlier scores as-is; a full rebuild remains available when the prompt or model version changes.
Example: 4,000 changed tickets are scored tonight; the other 1,996,000 keep their stored sentiment.
The docs pages available to this batch did not cover Code Repositories incremental settings, so the exact configuration is not described here.
W: A=Incremental scoring: model calls fall roughly in proportion to the share of rows that changed, and old results stay intact.
X: B=Smaller tier: it lowers the unit price but still pays for 2 million calls nightly, and it changes score behaviour for every row.
C=Two runs: the same unchanged rows are still scored, and a second schedule adds more calls rather than fewer.
D=In-memory cache: a transform's memory does not persist between scheduled runs, so nothing is reused.
T: Score only what changed; do not pay the model to re-answer unchanged rows.

@ PLTR-AIE D4 T4.4 applied troubleshooting
S: A scheduled Code Repositories transform summarizes documents with a model each morning at 06:00. On some days it runs against the previous day's data because the upstream ingestion finishes at about 06:20. What is the most robust fix?
A: Move the summarization schedule to 07:00 so that the ingestion has always finished well before it starts
B: Trigger the summarization build when the upstream dataset updates, instead of at a fixed clock time
C: Add a loop at the start of the transform that sleeps until new rows appear, retrying for up to an hour
D: Have the summarization transform read directly from the ingestion source so it no longer depends on the dataset
K: B
G: ## Schedule on the dependency, not on the clock
A fixed time works only while upstream timing never moves. Foundry build schedules can also be driven by upstream updates, so the build starts when its input is ready. The Automate overview likewise lists dataset conditions (trigger when a dataset is updated) as a condition type; the same dependency idea applies. The docs pages read here did not describe build-schedule triggers in detail.
## Why it matters for LLM jobs
A stale run wastes model calls on old data and can overwrite good output with a duplicate.
Example: ingestion finishes at 06:55 on a heavy day; the summarization starts at 06:55, not at 06:00.
W: B=Update-driven trigger: the build begins when the input actually changes, whatever time that happens.
X: A=Later fixed time: it shortens the odds of a clash but fails again on the first slow ingestion day.
C=Sleeping loop: the job holds compute while idle and still gives up after an hour, so a long delay breaks it again.
D=Read the source directly: it bypasses the governed ingested dataset and couples the job to the source's availability and format.
T: Start dependent builds from the upstream update, not from an assumed finish time.

@ PLTR-AIE D4 T4.2 applied troubleshooting
S: About 2% of rows in a batch LLM job fail JSON parsing because the model wrapped the answer in extra text. The job stored only parsed output, so the team must call the model again for those rows each night. What change would have avoided the repeated cost?
A: Persist the raw response for every row, so failed parses can be fixed in the parser and re-run without new model calls
B: Lower the temperature to zero and call again, because that guarantees the model never adds extra text in any answer

G: ## The raw response is an asset
Parsing is a deterministic step downstream of a paid, non-deterministic one. If the raw text is kept, a parser fix is a cheap re-run over stored text. If it is not kept, every parser bug costs new model calls and may give different answers.

- Store raw response, parsed value and a parse-status column.
- Fix the parser, then reprocess rows with a failed status.
- Where the platform offers structured output, use it so malformed JSON is rarer.
W: A=Persist raw responses: the parser is fixed once and re-applied to saved text, with no new calls and no changed answers.

C=Drop the rows: silent loss of data in the output, with no trace of which records are missing.
D=Longer prompt: more instructions and tokens cost more per row and still give no guarantee about the format.
