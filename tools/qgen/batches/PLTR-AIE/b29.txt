@ PLTR-AIE D4 T4.1 applied use-case
S: A pipeline must summarize 50,000 lengthy legal filings into a fixed set of fields (parties, court, filing date, relief sought). Filings can exceed the model's context window. Which processing design is appropriate?
A: Truncating each filing to its first page before extraction, since the key facts usually appear at the beginning of a legal document anyway
B: Chunk each filing, extract candidate fields per chunk with structured output, merge per filing with deterministic rules, flag conflicts
C: Sending each filing to the model repeatedly until it fits, by asking the model to compress its own input
D: Processing only filings that fit the context window and skipping the rest
K: B
G: ## Long documents in batch extraction
The exam guide covers batch LLM processing, entity extraction and structured output. When documents exceed the window, extraction becomes map-and-merge.
## Design
- Chunk by section; extract typed candidates per chunk.
- Merge per filing: deterministic precedence (first non-null, majority, or a confidence rule); conflicts flagged.
- Validation: date parses, court in a reference list.
- Audit: raw responses per chunk retained.
Example: a 300-page filing yields parties from the caption chunk and relief from the prayer section; a conflicting court name is flagged.
W: Chunk-level structured extraction with deterministic merge and validation: complete coverage of long filings with controlled conflict handling.
X: A=First page only: relief sought and other fields often appear late; truncation loses them.
C=Self-compression: the model cannot read what does not fit in order to compress it.
D=Skip large filings: the longest filings are often the most important; incomplete coverage.
T: Process documents larger than the context window by chunked extraction and deterministic merging.
V: Pipeline Builder, AIP

@ PLTR-AIE D4 T4.2 applied tradeoff
S: An LLM enrichment's audit log stores the full prompt for every row. Prompts include a 3,000-token system section that is identical for every row. What is a better recording design?
A: Stop recording prompts altogether, since the large system section is identical for every row and is therefore uninteresting for any audit
B: Record the template version and the per-row injected variables, with the template stored once per version, so each prompt is reconstructible
C: Compress each prompt with a general-purpose compression algorithm before storing it per row
D: Store the prompt only for rows where the output was later found to be wrong
K: B
G: ## Reconstructible provenance
The exam guide asks to preserve prompts where auditability requires, which does not mean storing identical text millions of times. Template plus variables reconstructs exactly.
## Design
- Template versioned and stored once.
- Per row: template version, variable values, model, parameters, raw response.
- Reconstruction: template(version) + variables = the exact prompt.
Example: storage per row drops from 3,200 tokens to 200, and an auditor can still see the full prompt for row 4421.
W: Template version plus per-row variables: exact reconstruction at a fraction of the storage.
X: A=Stop recording: audits lose the ability to see what the model was asked.
C=Generic compression: still stores redundant data per row, and the structure is lost.
D=Only wrong rows: you do not know which rows are wrong until later.
T: Store prompt templates once per version and only the per-row variables alongside each output.
V: Pipeline Builder

@ PLTR-AIE D4 T4.3 applied comparison
S: A team wants to decide the layer for "detect whether an uploaded image shows the required safety equipment, for every image uploaded by field crews, and show the result in the inspection app". Which placement is right?
A: North of the Ontology only, running the vision model at the moment an inspector opens the image in the inspection app on their device
B: South of the Ontology: an event-driven or batch step classifies each image on arrival and stores the result as a property
C: In the mobile app itself, with a small on-device model, since connectivity is unreliable
D: Nowhere; inspectors should judge images manually
K: B
G: ## Reusable classification on arrival
The exam guide asks you to place AI by consumer breadth, freshness, reusability and scale. Every image needs the result (for reporting and compliance), not only the ones an inspector opens.
## Design
- Event-driven or batch step on upload: vision model with structured output, confidence, review routing.
- Property on the Inspection or Image object.
- App displays; reports aggregate compliance rates.
Example: 10,000 images a week are classified within minutes of upload; the compliance dashboard counts every one.
W: Classify on arrival in the pipeline/event layer and store the result: complete coverage, reusable by app and reports.
X: A=On open only: images never opened are never classified; reports are incomplete.
C=On-device model: outside the governed platform and inconsistent across devices.
D=Manual: the requirement is automated detection for every image; manual judgement is the process being replaced and does not scale.
T: Per-item results needed by apps and reports are produced on arrival and stored, not computed on view.
V: Automate, Pipeline Builder, Ontology

@ PLTR-AIE D4 T4.4 applied use-case
S: A Code Repositories transform calls an LLM for 5 million rows. The team wants to run it in parallel but safely. Which implementation practices matter?
A: Launching as many concurrent requests as the cluster allows across all executors, since the provider will queue whatever it cannot handle
B: Bounded concurrency with a shared rate limit, batching where supported, backoff on throttling, per-row status and checkpointing to resume
C: Running everything on the driver in a single thread to avoid any concurrency problems
D: Splitting the dataset into five jobs run by five different engineers
K: B
G: ## Parallel AI calls done safely
The exam guide lists rate limiting and programmatic control among reasons to codify in Code Repositories. Parallelism must respect provider limits and survive interruptions.
## Practices
- Concurrency bound and rate limiting coordinated across executors.
- Batching requests where possible.
- Backoff with jitter; failed rows recorded with status.
- Checkpointing so a job that stops at row 3 million resumes there.
Example: the job runs at 95% of the rate limit for 9 hours, survives two throttling episodes, and completes with 0.1% rows flagged for retry.
W: Bounded, rate-limited, batched, checkpointed parallelism: throughput without violating limits or losing progress.
X: A=Unbounded: throttling storms, failed rows and possible provider blocks.
C=Single thread on the driver: 5 million sequential calls take weeks.
D=Five engineers: manual sharding with no coordination or checkpointing.
T: Parallelize AI calls with shared rate limits, batching, backoff and checkpoints.
V: Code Repositories

@ PLTR-AIE D4 T4.1 applied troubleshooting
S: A sentiment model's output distribution in production shows 60% "neutral" while the evaluation set shows 20%. Sampling reveals many production texts are short, template-like system messages. What should change?
A: Nothing; neutral is a valid label and the pipeline is working
B: Pre-filter by text type: exclude or separately handle template and system messages so sentiment covers customer text, and extend the suite
C: Remove "neutral" from the allowed labels entirely so that the model is forced to choose either positive or negative for every text
D: Increase the temperature so the model varies its labels more
K: B
G: ## Input quality before model quality
The exam guide asks you to inspect inputs and to keep evaluation representative. The model is right that templates are neutral; the pipeline is wrong to score them at all.
## Fix
- Deterministic pre-filter: detect templates and system-generated text (patterns, source flags).
- Route: skip or label as "not applicable".
- Evaluation: add template cases with the expected "not applicable".
- Dashboard: sentiment computed over customer text only.
Example: after filtering, neutral falls to 22% on customer text and the dashboard reflects real sentiment.
W: Filter non-customer text before the model and reflect it in the suite: the metric measures what it is meant to measure.
X: A=Working: the dashboard is diluted by system messages; the business metric is wrong.
C=Remove neutral: forces false polarity on genuinely neutral text.
D=Temperature: randomizing label choice does not change the fact that 60% of the inputs are system templates with no sentiment.
T: Validate and filter inputs to AI steps; a correct model on the wrong inputs still produces a wrong metric.
V: Pipeline Builder, AIP Evals

@ PLTR-AIE D4 T4.2 applied use-case
S: A regulator may ask why a specific customer was assigned a specific risk category by an LLM step months ago. The team wants the explanation to be available in seconds. What should the pipeline store alongside the category?
A: Only the category and the date it was assigned, since regulators care about the outcome and not about how the pipeline reached it
B: The category with the model's structured reason, prompt version, model id, input snapshot reference and raw response, linked to the customer
C: A cryptographic hash of the input, which proves the input existed at the time the category was assigned and has not been altered since
D: The engineer's name, so the regulator can interview them
K: B
G: ## Explanations as data
The exam guide asks for auditability of AI outputs. "Why" in seconds means the explanation was stored at the time, not reconstructed later.
## Stored per decision
- Structured reason field from the model (explainable output).
- Prompt version, model id, parameters.
- Input snapshot reference (which data the model saw).
- Raw response.
- Linked to the customer object; retrievable by query.
Example: the regulator's question is answered with a screen showing the reason, the inputs and the version that produced it.
W: Reason, versions, input reference and raw response linked to the object: a complete, instant explanation.
X: A=Outcome only: the regulator asked why; a category and a date cannot explain what the model saw or how it reasoned.
C=Hash: it proves the input was not altered; it explains nothing about the reasoning or which prompt and model were used.
D=Engineer's name: people forget and leave; the record must stand alone.
T: Store the model's reason, versions and input reference with every consequential AI decision.
V: Ontology, Pipeline Builder

@ PLTR-AIE D4 T4.3 applied tradeoff
S: A pipeline computes an LLM-generated "next best action" for each of 2 million customers nightly, but the action depends on the customer's live cart contents at the moment an agent speaks to them. What is the better design?
A: Keep the nightly batch as it is, since it is far cheaper, and accept that the recommended action may be stale by the time of the call
B: Split: precompute stable features and candidate actions nightly (south), then generate the final recommendation on demand with the live cart
C: Run the full LLM step for all 2 million customers every five minutes so the actions are nearly live
D: Ask agents to ignore the cart and follow the nightly action
K: B
G: ## Hybrid for stale-sensitive outputs
The exam guide allows combining layers: reusable parts south, context-dependent parts north. The cart is live context; the customer's history is stable.
## Design
- Nightly: features, segments, candidate action list per customer stored as properties.
- On demand: a function uses the candidates plus the live cart to produce the final recommendation for that conversation.
Example: the night's candidates for customer C-4 are three offers; with a cart containing a printer, the on-demand step picks the ink bundle.
W: Precompute the stable part, personalize on demand with live context: correct recommendations at reasonable cost.
X: A=Stale action: the recommendation ignores the reason the agent is talking to the customer.
C=Every five minutes for all: 2 million LLM calls every five minutes is absurdly expensive.
D=Ignore the cart: the cart is the strongest signal of what the customer wants right now; ignoring it defeats the purpose of the recommendation.
T: Precompute what is stable south; finish what depends on live context north.
V: Pipeline Builder, AIP Logic, Ontology

@ PLTR-AIE D4 T4.1 advanced troubleshooting
S: After switching an extraction step from a text model to a vision-capable model for scanned documents, accuracy improved for scans but dropped for clean digital PDFs. How should the pipeline handle both?
A: Use the vision model for every document, since scans are the harder case and the accuracy drop on digital PDFs is an acceptable trade-off
B: Route by document type: PDFs with a reliable text layer go to the text model, scans and poor-text PDFs to the vision model, evaluated per type
C: Run both models on every document and average their outputs
D: Convert all digital PDFs to images so that they are processed like scans
K: B
G: ## Routing by input type
The exam guide asks for structured outputs with deterministic handling and evaluation by case type. Different inputs suit different models; a deterministic router picks the right one.
## Design
- Detection: text-layer presence and quality (character count, garbage ratio).
- Route: text model for clean text; vision model for scans.
- Evaluation: stratified by type so each path's accuracy is measured.
- Fallback: if the text path fails validation, retry via vision.
Example: 70% of documents are digital and go to the cheaper, more accurate text path; 30% are scans handled by vision.
W: Deterministic routing by document characteristics with per-type evaluation: each document gets the model that is best for it.
X: A=Vision for all: accepts a known accuracy loss on the majority of documents.
C=Average both: doubles cost and averaging structured fields is meaningless.
D=Rasterize everything: degrades clean text into images and increases cost.
T: Route inputs to the model that suits them, and evaluate each path separately.
V: Pipeline Builder, AIP Evals
