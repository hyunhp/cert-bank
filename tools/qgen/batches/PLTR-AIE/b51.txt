@ PLTR-AIE D1 T1.2 applied troubleshooting
S: A Logic function contains an Apply action block that sets a ticket's `status`. Testing in the debugger shows the block ran and returned the expected edit, yet no ticket changes in the Ontology afterwards. What is the most likely explanation?
A: The model inside the function ignored the block and produced a different output, so the edit was silently discarded before it reached the Ontology
B: The Apply action block can only run inside a Loop, so the standalone block returned a preview value and skipped the real edit entirely
C: The function was only run as a function; the edit is written only when the Logic function is executed from an Action, which the workflow has not wired up
D: The ticket object type must first be converted into a dataset, because Logic functions can read Ontology objects but never edit them
K: C
G: ## Edits are staged by the function, applied by an Action
An Apply action block calls an Action deterministically, with the parameters you set and without going through a model. The Logic function produces the Ontology edit, but the docs state that the Ontology is not edited unless the Logic function is executed from an Action, even when the function contains an Apply action block.
## Troubleshooting order
- Confirm the block output in the debugger (done here: the edit is correct).
- Check how the function is invoked: a bare function run or a Workshop widget that calls it as a function does not write edits.
- Wire the function into an Action (function-backed Action) and invoke that.
Example: a button calls the function directly and shows the proposed status; the same function behind a function-backed Action actually updates the ticket.
W: Executing from an Action: the debugger shows the edit that would be made, but only a function-backed Action run commits it, so the missing wiring explains the symptom.
X: A=Model ignored the block: an Apply action block is deterministic and does not go through the model, and the debugger already showed the expected edit.
B=Only inside a Loop: the block works standalone; loops are for iterating over lists and are not a requirement for writing an edit.
D=Convert to dataset: Logic functions do edit Ontology objects through Actions; no dataset conversion is involved.
T: A Logic function proposes Ontology edits; they are written only when the function runs from an Action.

@ PLTR-AIE D1 T1.2 applied use-case
S: A Logic function receives a free-text complaint and must call an existing Action that sets the `category` of the complaint from a fixed list. The categorisation itself is an interpretation, but filling the Action's other parameters (case id, timestamp, author) is mechanical. Which design is most appropriate?
A: Use a Use LLM block to classify the complaint, then pass its typed output into an Apply action block that fills the other parameters from inputs
B: Give the model the Action as a tool and let it choose all parameter values itself, including the case id and the timestamp, in one prompt
C: Skip the model, and match keywords in code against the fixed list because any classification of language is better done by string matching
D: Ask the model to write out the Action's parameters as free text, then have an administrator copy them into the Action by hand each day
K: A
G: ## Interpretation first, deterministic write second
The exam guide asks you to use the model where judgement is needed and deterministic blocks where values are known. The Apply action block calls an Action without going through an LLM and gives precise control over how parameters are filled.
## Design
- Use LLM block: input the complaint, output a typed value limited to the allowed categories.
- Apply action block: category from the block output; case id, timestamp and author mapped from inputs and variables.
Example: the model returns "billing"; the Action receives billing plus the case id from the function input, not from the model.
W: Typed classification followed by an Apply action block: the interpretation is the only model step, and mechanical parameters cannot be mis-filled by the model.
X: B=Model fills everything: the case id and timestamp are known values; letting the model write them adds avoidable error risk.
C=Keyword matching only: free-text complaints need interpretation, and brittle string rules miss paraphrases.
D=Manual copying: it removes the automation and adds a human transcription step with no benefit.
T: Let the model interpret, then pass its typed output into a deterministic Apply action block.

@ PLTR-AIE D1 T1.2 applied troubleshooting
S: A Logic function uses a Conditional block. The "then" branch returns an Ontology edit through an Apply action; the "else" branch is left empty because nothing should happen in that case. The function fails validation. What is the correct fix?
A: Replace the Conditional with a Loop over a one-element list so that the empty branch is no longer evaluated by the function
B: Make the "else" branch return a text string explaining why nothing happened, so that both branches produce some output of any type at all
C: Remove the "else" branch entirely, since Conditional blocks only support a "then" path and an empty path is the default behaviour
D: Set the "else" branch to explicitly take no action, since branches returning Ontology edits must all run an action or take no action
K: D
G: ## Consistent branch outputs
Conditional blocks work like if-then-else. Each branch defines what it returns: a path of blocks, a variable, or take no action (available when another branch returns Ontology edits). All branches must return consistent output types.
## Applying it
- Output is Ontology edits in one branch, so every other branch must run an action or explicitly take no action.
- A string in the other branch would mismatch the edit type.
Example: "if refund approved, apply the refund Action; else take no action" validates, while "else return a message" does not.
W: Explicit take no action: this is the documented way to give a no-op branch a compatible output when another branch returns edits.
X: A=Loop over one element: a loop is for iterating a collection, not a workaround for validation, and it does not change the branch contract.
B=Return a string: a string in one branch and edits in the other is exactly the inconsistent output the validation rejects.
C=Remove the else branch: the docs describe branches that must each be defined; an unset branch is not the default no-op.
T: When one Conditional branch returns Ontology edits, every other branch must run an action or explicitly take no action.

@ PLTR-AIE D1 T1.2 advanced tradeoff
S: A team must update 300 objects per run from the model's recommendations. One engineer wants a single Use LLM block that returns the whole list of 300 updates in one completion; another wants a Loop that handles one object per iteration. The updates are independent of each other. What is the stronger design?
A: One completion for all 300, because a single call is always cheaper and the model keeps a consistent tone across all objects
B: One completion for all 300 plus a manual review of the full list, since reading the list is faster than reviewing per-object traces
C: A Loop with one small, typed model call per object, so that each update is isolated, testable and a failure affects one object
D: A Loop that runs the model once and reuses the same answer for every object, which minimises cost and keeps the outputs identical
K: C
G: ## Granularity of model work
Loops let a Logic function iterate over a list and run a transformation or an action for each element, with `element` and `index` available. Independent items favour small, isolated calls.
## Tradeoff
- One huge completion: long prompt and output, harder to validate, one malformed item can spoil the response, and the context window may be exceeded.
- Per-item calls: each typed output is checkable; failures are localised; loops without actions run iterations in parallel.
Example: an invalid answer for object 117 is rejected alone while the other 299 proceed.
W: A per-object Loop with typed output: independent items stay isolated, validated and traceable, which beats an all-in-one completion for reliability.
X: A=Single completion: the prompt and output grow with 300 items, which strains the context window and couples every item to one failure.
B=Single completion plus manual review: it keeps the coupling and adds a human burden that per-object typed checks avoid.
D=One answer reused for all: the objects differ, so identical outputs are wrong by construction.
T: For independent items, iterate with small typed calls rather than one giant completion.

The context window is the amount of text an LLM can process at once. - Start a new conversation for the symptom.
- Reduce what is injected: fewer returned properties, smaller retrieval K, shorter descriptions.
Example: lowering the number of retrieved items per message leaves room for a longer conversation.

X: A=Ontology corruption: nothing suggests data damage, and short sessions work.
B=Expired model: not indicated, and rebuilding is far more than needed.
