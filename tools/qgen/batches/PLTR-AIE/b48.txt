@ PLTR-AIE D7 T7.1 applied use-case
S: A workflow must classify documents written in twelve languages, several of them low-resource. The reference sheet lists a model with top English benchmarks and another with explicit multilingual coverage and slightly lower English scores. How should the choice be made?
A: Choose the model with the top English benchmarks, since English performance is the standard measure of a model's overall quality
B: Evaluate both on a suite with cases in all twelve languages, weight by the language mix, and choose the model that clears the threshold
C: Choose whichever model is cheaper per token without evaluating language coverage
D: Translate everything to English first with a third model and then use the top English model
K: B
G: ## Requirement-driven selection
The exam guide asks for model selection by task requirements and evaluation. Language coverage is a capability requirement that English benchmarks do not measure.
## Selection
- Suite: cases per language, including the low-resource ones.
- Metric: accuracy per language and weighted by production mix.
- Decision: the model that clears the threshold everywhere; cost compared among qualifying models.
Example: the English-strong model scores 60% on two low-resource languages; the multilingual model scores 88% there and 90% in English; it is chosen.
W: Per-language evaluation weighted by the production mix: the model is chosen for the languages it must actually handle.
X: A=English benchmark: says nothing about the eleven other languages.
C=Cheapest without evaluation: may fail the low-resource languages entirely.
D=Translate first: adds cost and translation errors on every document; low-resource translation is itself weak.
T: Select models by evaluating on the task's actual language and input mix, not on headline benchmarks.

@ PLTR-AIE D7 T7.3 applied troubleshooting
S: A dashboard shows an AI feature's average latency is stable at 1.8 seconds, yet users report frequent multi-second waits. What is the engineer missing?
A: Users are exaggerating their experience; a stable 1.8-second average proves that the system is fast and nothing needs investigating
B: The average hides the tail: inspect p95 and p99, break down slow requests by step and input size, and alert on tail latency
C: The dashboard must be broken if it disagrees with users, and it should be rebuilt from scratch before anything else is done
D: The model should be replaced immediately with a faster one, since latency complaints about an AI feature always come from the model
K: B
G: ## Tail latency
The exam guide lists latency among observability signals; a mean can mask a heavy tail. Users experience the tail.
## Analysis
- Percentiles: p95 of 6 seconds explains the complaints.
- Breakdown: which component dominates on slow requests (a tool timeout, a large retrieval).
- Alerting on p95, not mean.
Example: 8% of requests with long documents spend 5 seconds in a tool call; a cache fixes the tail.
W: Percentiles and component breakdown: the tail that users feel becomes visible and fixable.
X: A=Users exaggerating: a 1.8-second mean is perfectly consistent with 8% of requests taking six seconds; the users are right.
C=Rebuild the dashboard: it shows a true but incomplete metric.
D=Replace the model: without a breakdown, the slow component may be a tool call or retrieval; swapping the model could change nothing.
T: Monitor latency by percentile and component; averages hide the tail users experience.

@ PLTR-AIE D7 T7.4 applied use-case
S: A function makes four independent tool calls (lookup customer, lookup orders, lookup tickets, lookup contracts) before composing a prompt. Each takes 400 ms and they run sequentially. What is the right optimization?
A: Remove three of the four lookups to save time, keeping only the customer lookup and letting the model work without the rest
B: Run the four independent lookups in parallel, reducing pre-prompt time to the longest single call, with timeouts and fallbacks
C: Cache the results of all four lookups permanently so that they never run again for a customer once they have been fetched
D: Ask the model to recall the customer's orders, tickets and contracts from its own memory instead of looking them up
K: B
G: ## Parallelizing independent work
The exam guide lists execution structure (parallelization) among optimizations. Independent tool calls need not wait for each other.
## Design
- Parallel execution of the four lookups.
- Timeout per lookup; fallback (partial context with a note) if one is slow.
- Measure: pre-prompt time drops from 1.6 s to about 0.45 s.
Example: the function's p50 latency falls by more than a second with no change in output.
W: Parallel lookups with per-call timeouts: latency falls to the slowest single call while results stay complete.
X: A=Remove lookups: orders, tickets and contracts are the context the prompt needs; dropping them makes the answer wrong.
C=Permanent cache: orders and tickets change daily; a permanent cache serves stale data forever.
D=Model memory: the model has never seen this customer's records; it would fabricate them.
T: Run independent tool calls in parallel with timeouts and fallbacks.
V: AIP Logic

@ PLTR-AIE D7 T7.2 applied use-case
S: An organization wants to use a new model that just appeared in the catalog. What should happen before it is used in a production workflow?
A: Switch production to it immediately to benefit from the improvement
B: Confirm enablement and compliance, evaluate it on the suite against the incumbent, test the prompt for differences, roll out gradually
C: Use it first on the most critical production workflow, since that is where any improvement delivers the most business benefit
D: Wait until other companies have reported using it successfully for a few months before considering it at all
K: B
G: ## Adopting a new model
The exam guide asks for selection by evaluation and for monitored, reversible change. A new model is a candidate, not an upgrade until evaluated.
## Steps
- Compliance and enablement check.
- Suite evaluation versus the incumbent; prompt adjustments for format or behaviour differences.
- Gradual rollout with metrics and rollback.
Example: the new model is 20% cheaper with equal quality on the suite; a two-week staged rollout confirms no production regressions.
W: Compliance check, evaluation, prompt testing and staged rollout: the new model earns its place with evidence.
X: A=Switch immediately: unevaluated behaviour changes in production.
C=Most critical first: the highest-risk place to try something unproven.
D=Wait for others: other companies' tasks are not yours; evaluate on your own.
T: Adopt new models through evaluation and staged rollout, never by direct switch.

@ PLTR-AIE D7 T7.3 applied use-case
S: An AI feature's usage grew tenfold in a month. Which observability signals should be reviewed to decide whether the system is still healthy?
A: Only the number of requests per day, since the growth itself is the main thing that matters for capacity planning
B: Error rate, latency percentiles, token usage and cost, quota headroom and throttling, quality proxies and backlog, before and after
C: The number of engineers on the team maintaining the feature, since more usage usually requires more people to support it
D: The model provider's latest release notes, in case a model update coincided with the growth and explains any changes
K: B
G: ## Scaling review
The exam guide lists the observability signals and asks for monitoring of capacity and cost. Growth stresses every dimension.
## Signals
- Reliability: error rate, throttling, timeouts.
- Performance: p95 latency, backlog.
- Cost: tokens and spend versus budget; quota headroom.
- Quality: sampled groundedness and feedback (growth may bring new user types).
Example: p95 latency rose from 2 to 5 seconds and throttling events appeared; capacity and caching are adjusted.
W: Reliability, performance, cost and quality signals compared across the growth: a complete health picture.
X: A=Request count: the growth is already known; the question is whether reliability, latency, cost and quality held up under it.
C=Team size: headcount is not an operational signal of the system's health under load.
D=Release notes: documentation about the model; they say nothing about how this feature is behaving under tenfold load.
T: After usage growth, review error, latency, cost, quota and quality signals together.
V: AIP Observability

@ PLTR-AIE D7 T7.1 applied comparison
S: Which selection criterion most directly justifies choosing a model with a larger context window for a workflow?
A: The model's name sounds newer and more advanced than the current one, which suggests it will perform better on everything
B: The workflow must reason over long inputs that cannot be chunked without losing cross-references, and evaluation confirms the gain
C: Larger context windows are always better for every task, so the model with the largest window should be chosen by default
D: Engineers prefer not to implement chunking, and a larger window lets them inject whole documents without any extra work
K: B
G: ## Context window as a requirement
The exam guide lists context limits among selection criteria. A larger window is justified by inputs that genuinely need it, confirmed by evaluation.
## Reasoning
- Task: cross-document reasoning where chunking breaks references.
- Evaluation: accuracy gain on long-input cases.
- Cost: longer contexts cost more; accept if the gain warrants.
Example: contract comparison accuracy rises from 71% to 90% with the larger window; the extra cost is accepted for that workflow only.
W: Long-input tasks where chunking loses meaning, validated by evaluation: the direct justification.
X: A=Newer name: a name is not a capability; selection rests on requirements and evaluation.
C=Always better: longer contexts cost more and can dilute attention.
D=Developer convenience: avoiding chunking work is not a task requirement, and longer contexts cost more on every call.
T: Choose larger context windows for tasks that need them, confirmed by evaluation, not by default.

@ PLTR-AIE D7 T7.4 applied troubleshooting
S: A batch AI job's cost doubled although the number of rows and the prompt are unchanged. Traces show output lengths grew sharply. What should be checked and done?
A: Nothing; output length is up to the model and cannot be controlled, so the doubled cost simply has to be accepted
B: Whether a model version change or instruction drift made outputs verbose; constrain with schemas and max tokens, alert on length
C: Reduce the number of rows processed each night by half so that the total cost returns to its previous level
D: Switch to a more capable model with a higher per-token price, since it will produce more concise and accurate outputs
K: B
G: ## Output-driven cost
The exam guide asks for cost optimization and monitoring of real behaviour. Output tokens are often the larger cost; verbosity growth doubles cost without changing inputs.
## Response
- Trace comparison: output tokens per row before and after; model version.
- Constrain: structured output; max tokens; instruction on brevity.
- Monitor: output-length metric with alert on drift.
Example: a provider version change made the model explain its reasoning; a structured schema restores 200-token outputs.
W: Diagnose the verbosity source and constrain outputs with schemas and limits: cost returns to baseline and drift is monitored.
X: A=Up to the model: output length is controllable through schemas, instructions and token limits; accepting a doubled cost is a choice.
C=Fewer rows: half the data processed, with every row still twice as expensive as it should be.
D=Pricier model: a higher price per token on verbose outputs raises cost further; nothing constrains length.
T: Monitor and constrain output tokens; verbosity drift doubles cost silently.

@ PLTR-AIE D7 T7.2 advanced tradeoff
S: A team wants to pin a specific model version for stability, but the provider will retire that version in six months. How should the team plan?
A: Pin the version for stability and deal with the retirement when it happens, since six months is a long time and priorities may change
B: Pin now, record the retirement date, evaluate the successor well before it with the suite, and migrate in stages with rollback
C: Never pin model versions at all, so that retirements never matter because the workflow always uses whatever is current
D: Switch to the successor version today without evaluation, since the migration has to happen eventually anyway
K: B
G: ## Version lifecycle management
The exam guide asks for versioned, evaluated, reversible change and awareness of provider dependencies. Pinning gives stability; retirement dates require planning.
## Plan
- Pin; track the retirement date as a milestone.
- Three months out: evaluate the successor; adjust prompts; fix regressions.
- Staged migration with per-version metrics; rollback possible while both exist.
Example: the successor is evaluated in month three, migrated in month four, and the old version is retired with no incident.
W: Pin now, evaluate and migrate early, keep rollback while both versions exist: stability without a cliff.
X: A=Deal with it later: a forced, unevaluated migration at the deadline.
C=Never pin: uncontrolled behaviour changes whenever the provider updates.
D=Switch today: an unevaluated behaviour change in production with no urgency; the evaluation is cheap and the risk is not.
T: Pin model versions for stability and plan evaluated migrations ahead of retirements.
