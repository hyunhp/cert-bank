# PLTR-AIE batch 41: Domain 8 round 5 (Security, Governance, and Responsible AI), 8 questions

@ PLTR-AIE D8 T8.1 applied use-case
S: A function must read a highly restricted dataset to compute an aggregate that is safe to show widely. How should execution security be configured so that the restricted rows are never exposed?
A: Run the function as each calling user and grant every user in the audience the dataset's marking so the function can read the rows for them
B: Run it under a configured identity that holds the marking, return only the aggregate with a validated shape, restrict invocation, audit runs
C: Copy the restricted dataset to an unrestricted project so that the function can read it when running as any ordinary user
D: Have users request the underlying rows directly from the data owner instead of computing the aggregate through a function
K: B
G: ## Controlled elevation for aggregates
The exam guide lists execution security modes and asks for least privilege. A configured identity can read what users cannot, provided the function exposes only what is safe.
## Design
- Identity: holds the marking; nothing else.
- Output: aggregate only, with a typed contract; row-level data cannot leave.
- Invocation restricted; every run audited with the caller.
- Disclosure review: aggregates over small groups can leak; apply thresholds.
Example: the function returns "average salary by department (n ≥ 10)"; the identity reads salaries, users never see them.
W: Configured identity with an aggregate-only contract, restricted invocation and audit: elevated read without exposing rows.
X: A=Grant everyone the marking: over-provisions the whole audience with restricted data.
C=Copy to unrestricted: the restricted rows become readable by anyone with access to the copy; the marking's protection is gone.
D=Users request rows: the restriction exists precisely so users do not see rows; handing out rows defeats it, and the aggregate was all they needed.
T: Use a configured execution identity for controlled elevated reads, and expose only safe aggregates.
V: AIP Logic, markings

@ PLTR-AIE D8 T8.2 applied use-case
S: A regulator asks for evidence that a specific AI agent never accessed a particular restricted dataset. What records support the answer?
A: A written statement from the engineering team confirming that, to their knowledge, the agent was never configured to use the dataset
B: The agent's configuration history, permission records for its execution identities, and the dataset's access logs
C: A screenshot of the agent's current tool and retrieval settings showing that the restricted dataset is not among its sources
D: The agent's own statement when asked in a conversation whether it has ever accessed the restricted dataset, recorded as a transcript
K: B
G: ## Proving non-access
The exam guide asks for audit and lineage evidence and understanding of permissions. "Never accessed" is shown by configuration history, permission history and access logs together.
## Evidence
- Configuration history: sources and tools over time.
- Permissions: the execution identities' memberships over time; the marking was never held.
- Dataset access logs: no reads by those identities.
Example: the three records together show the dataset was neither configured, permitted nor read.
W: Configuration, permission and access-log history: independent records that together demonstrate non-access.
X: A=Team statement: an assertion from the people being audited, with no records behind it; a regulator needs evidence.
C=Current screenshot: it shows today's configuration, not what the agent used across the whole period the regulator asks about.
D=Agent's own statement: a model's self-report is not evidence.
T: Demonstrate non-access with configuration history, permission history and access logs.
V: Check Access, AIP Observability

@ PLTR-AIE D8 T8.3 applied tradeoff
S: An AI workflow proposes which patients should be contacted first for follow-up care. What design responsibilities apply beyond ordinary accuracy?
A: None beyond accuracy; a ranking is just an ordered list and the clinic would have contacted all of these patients anyway
B: Fairness evaluation across groups, explainable reasons, clinician review before action, feature governance and monitoring
C: Faster models so that more patients can be ranked each day, since throughput is the main constraint on follow-up care
D: Letting the workflow contact the top-ranked patients automatically by text message to save clinic staff time
K: B
G: ## Healthcare prioritization is high-consequence
The exam guide asks for human review of high-consequence actions, fairness attention and documented limits. Rankings that affect care access carry fairness and safety obligations.
## Responsibilities
- Feature review: exclude proxies for protected attributes where inappropriate.
- Fairness metrics: outcomes and rankings by group.
- Explainability: reasons a clinician can assess.
- Human decision: clinicians act, the workflow suggests.
- Monitoring and documentation.
Example: the workflow shows "elevated risk: two missed appointments, recent lab change"; a nurse decides the call order.
W: Fairness, explainability, clinical review, feature governance and monitoring: proportionate to the consequence for patients.
X: A=Just a list: the order determines who receives follow-up first; a biased or wrong ranking directly affects patients' health.
C=Faster: ranking more patients more quickly does nothing about fairness, explainability or clinical oversight.
D=Auto-contact: removes the human from a consequential care decision.
T: AI that prioritizes people for consequential outcomes needs fairness evaluation, explainability and human decision.
V: AIP Logic, AIP Evals

@ PLTR-AIE D8 T8.4 applied troubleshooting
S: An agent that summarizes web pages was found to have followed a link embedded in a page and fetched content from an unapproved site. Which control was missing?
A: A prompt instruction telling the agent never to follow links it finds inside the pages it is asked to summarize
B: A tool-level allow-list restricting fetches to approved domains, enforced in the tool regardless of what the page or model requests, with logging
C: A faster, cheaper model for the workflow, so that even a runaway night costs less than it otherwise would that completes the summary before it has time to follow any of the links on the page
D: A longer system prompt that explains in detail which sites are approved and asks the agent to check each link against the list
K: B
G: ## Allow-lists at the tool boundary
The exam guide asks for controls at the tool boundary against unsafe tool use. A fetch tool decides what it will fetch; the model only asks.
## Control
- Allow-list of domains in the tool's code; everything else refused.
- Logging of refused requests for monitoring.
- Adversarial tests with pages containing links to unapproved sites.
Example: the page's link to an external site is refused by the tool and logged; the summary notes the link was not followed.
W: A tool-enforced domain allow-list with logging: the agent cannot reach unapproved sites, whatever it is asked.
X: A=Prompt instruction: the model can be persuaded; the tool cannot.
C=Faster model: speed has nothing to do with whether the fetch tool will retrieve an unapproved URL when asked.
D=Longer prompt: a list of approved sites in the prompt still leaves the decision to the model, which the page can influence.
T: Enforce resource restrictions inside tools, not in prompts.
V: AIP Agent Studio

@ PLTR-AIE D8 T8.1 applied comparison
S: Which control prevents an AI workflow from consuming the organization's entire monthly model budget in a single runaway night?
A: A prompt asking the model to be economical with its answers so that each call uses as few tokens as possible
B: Capacity and spend controls at the enrollment or workflow level (quotas, rate limits, budget alerts), failing safe when the quota is hit
C: A faster, cheaper model for the workflow, so that even a runaway night costs less than it otherwise would that completes the summary before it has time to follow any of the links on the page
D: A note in the runbook reminding the on-call engineer to check the spend dashboard whenever a workflow behaves oddly
K: B
G: ## Budget guardrails
The exam guide lists capacity controls among governance controls. A loop or an unexpected input surge can consume budget rapidly; the guardrail is configured, not requested.
## Controls
- Quotas per workflow and per enrollment.
- Rate limits and concurrency bounds.
- Alerts at thresholds; hard stop at the cap with a clear failure.
Example: a retry loop hits the workflow's nightly quota after 20 minutes and stops; the alert wakes the on-call engineer; the budget is intact.
W: Configured quotas, rate limits and alerts with fail-safe behaviour: runaway consumption is bounded by the platform.
X: A=Economical prompt: a runaway loop makes thousands of calls; how long each answer is barely matters and the prompt cannot stop the loop.
C=Faster model: a cheaper call in an unbounded loop still drains the budget, possibly faster because more calls fit in the night.
D=Runbook note: by the time someone reads the note and checks the dashboard, the budget is gone; nothing enforces a limit.
T: Bound AI spend with enforced quotas and alerts, not with prompts or notes.
V: AIP

@ PLTR-AIE D8 T8.2 applied use-case
S: An organization must retain AI interaction records for seven years for regulatory reasons but must also delete personal data on request. How can both be satisfied?
A: Keep every record intact forever and refuse all deletion requests on the grounds that the retention obligation takes precedence
B: Store interactions pseudonymized and keep the identity mapping separately, so deletion severs the mapping while the record is kept
C: Delete all AI interaction records after one year so that no personal data is held long enough for anyone to request its deletion
D: Store the records only in the model provider's logs, so that the organization itself holds no personal data from AI interactions
K: B
G: ## Retention and deletion together
The exam guide asks for data-protection architecture. Conflicting obligations are reconciled by separating identifying data from the retained record.
## Design
- Interaction record: pseudonymous id, content with identifiers redacted or tokenized, versions, timestamps.
- Identity mapping: separate, access-controlled, deletable.
- Deletion: remove the mapping (and any residual direct identifiers); the record stays but is no longer attributable.
Example: a deletion request severs the mapping for one customer; auditors still see the seven-year record without a name.
W: Pseudonymized records with a separable identity mapping: retention and deletion obligations both hold.
X: A=Refuse deletion: the obligation to delete personal data on request is not waived by a retention rule; refusing breaches it.
C=Delete after a year: the seven-year retention obligation is breached for six years of records.
D=Provider logs: outside the organization's control for either obligation.
T: Separate identity from retained AI records so deletion requests can be honoured without breaking retention.
V: Ontology, markings

@ PLTR-AIE D8 T8.3 applied use-case
S: A manager wants an AI agent to automatically approve employee expense reports under 50 to speed things up. What safeguards make this acceptable?
A: None; 50 is a small enough amount that a wrong approval costs the company almost nothing and controls would cost more
B: Validation rules, per-employee spend caps, sampled human audit, anomaly alerts, idempotent approval Actions and logging
C: A larger threshold of 500 instead of 50, so that even more reports are approved automatically and managers save even more time
D: A prompt instruction asking the agent to be careful and to approve only reports that look legitimate to it
K: B
G: ## Small-amount automation still needs controls
The exam guide asks to match validation to consequence; low per-item consequence can still aggregate (fraud at scale) and needs bounds and audit.
## Safeguards
- Deterministic validation before approval.
- Per-employee caps; duplicate detection.
- Sampled human audit and anomaly alerts (sudden bursts).
- Idempotent Action; logs.
Example: an employee submitting 40 reports of 49 each in a week trips the cap and the anomaly alert.
W: Validation, caps, sampled audit, anomaly alerts and logged idempotent Actions: automation at low per-item risk with aggregate risk controlled.
X: A=None: fifty small approvals a week per employee add up; with no caps or audit the aggregate exposure is unbounded.
C=Larger threshold: tenfold the exposure per report with none of the controls that would make any threshold safe.
D=Prompt: asking the model to be careful enforces nothing; a crafted report description can still produce an approval.
T: Automate low-consequence approvals with validation, caps, sampling and anomaly detection.
V: Actions, Automate

@ PLTR-AIE D8 T8.4 advanced tradeoff
S: A team wants to measure how resistant its agent is to prompt injection over time. What is a sound approach?
A: Assume resistance is constant after the initial pre-release tests, since the agent's instructions have not changed since then
B: Maintain a growing adversarial set, run it on every change and on a schedule, gate releases on the pass rate, add flagged sessions
C: Rely on the model provider's published claims about injection resistance, since they test their models far more thoroughly
D: Test injection resistance once a year as part of the annual security review, using whatever attack patterns are known at that time
K: B
G: ## Injection resistance as a tracked metric
The exam guide asks for adversarial testing and monitoring of real behaviour. Resistance is a property that regresses with changes and erodes as attacks evolve.
## Approach
- Adversarial set: direct, indirect (in documents), multi-turn, encoded attempts.
- Run on every change and periodically; pass rate with a gate.
- Production: flagged sessions reviewed; new patterns become cases.
Example: a prompt tweak drops the injection pass rate from 98% to 90%; the release is held and the tweak revised.
W: A growing adversarial set with a gated pass rate and production feedback: resistance is measured continuously and regressions are caught.
X: A=Assume constant: prompt tweaks, tool changes and new attack techniques all erode resistance; an untested assumption hides regressions.
C=Provider claims: not specific to the application's tools and data.
D=Yearly: a regression introduced in February is exploited until the next review; the cadence is far too slow.
T: Track injection resistance with a maintained adversarial suite and release gates.
V: AIP Evals, AIP Agent Studio
