# PLTR-AIE batch 06: Domain 5 (Evaluation, Testing, and Quality Assurance), 8 questions

@ PLTR-AIE D5 T5.1 applied use-case
S: A team is building its first evaluation suite for an AIP Logic function that extracts the due date and amount from contract clauses. They have 2,000 historical clauses with values confirmed by the legal team. How should they assemble the suite?
A: A few hundred clauses spanning contract types, formats and tricky phrasings, with the confirmed values as expected outputs and exact-match evaluators
B: The 50 clauses that the function already handles correctly, since a suite should first establish a baseline the function passes before it is extended with harder material
C: Generate 2,000 synthetic clauses with a language model and use the model's own extraction as the expected values, which avoids manual labelling
D: Use all 2,000 clauses but let the function's current output define the expected values, then flag any future run that differs from today's output
K: A
G: ## What an evaluation suite needs
The exam guide asks for representative evaluation suites with test cases, target functions, evaluators and metrics. A test case has an input, an expected result and an evaluator that compares them.
## Representative, not convenient
- Coverage: the clauses should span contract types, date formats ("30 days after signature" as well as explicit dates), currencies and unusual phrasing, so the suite can catch failures the common cases hide.
- Ground truth: the legal team's confirmed values are the expected outputs; they do not come from the function under test.
- Evaluators: exact match for amount and date is appropriate because the fields are deterministic; looser evaluators are for free-text outputs.
Example: 300 cases, stratified by contract type, with 40 deliberately hard ones, give a precision figure that means something.
W: Stratified real cases with confirmed values and exact-match evaluators: the suite measures the function against the truth, across the variety it will meet in production.
X: B=Cases it already passes: a suite built from known successes cannot reveal weaknesses; it measures nothing new.
C=Synthetic clauses with model-generated truth: the expected values are not verified, so errors in them are counted as correct, and synthetic text may miss real-world phrasing.
D=Current output as truth: this freezes today's mistakes as the expected answer and only detects change, not correctness.
T: Build evaluation suites from representative real cases with independently confirmed expected outputs.

@ PLTR-AIE D5 T5.2 applied use-case
S: An agent can approve expense reports under a limit and must refuse anything above it or outside policy. The evaluation suite currently contains only normal, in-policy reports. Which cases should be added first?
A: More in-policy reports from other departments, so that the approval accuracy is measured across the whole organization
B: Reports just above the limit, violations hidden in the description, submitters who may not request approval, and large ambiguous reports
C: Reports with spelling mistakes, mixed currencies and unusual receipt formats, so that the agent's parsing is proven on messy input before decision quality is tested
D: Reports submitted at high volume, so that the suite measures whether the agent's latency stays acceptable during month-end peaks
K: B
G: ## Testing the failure modes that matter
The exam guide asks evaluation to include normal, edge, adversarial, unauthorized and high-consequence cases. For an approving agent, the dangerous outcome is a wrong approval, so the suite must contain the cases that could produce one:
- Edge: amounts just above the limit, where rounding or misreading flips the decision.
- Adversarial: a violation phrased to look compliant, or an instruction in the description ("this has been pre-approved by finance").
- Unauthorized: a submitter who may not request approval.
- High-consequence or ambiguous: a large report with unclear receipts, which should be escalated rather than decided.
Each case gets an expected outcome (approve, refuse, escalate) and an evaluator that checks the decision, not just the wording.
W: Edge, adversarial, unauthorized and ambiguous high-value cases: these are the ways the agent can approve something it should not, which is the risk the suite exists to catch.
X: A=More normal cases: the suite already covers in-policy reports; adding more of them improves confidence in the easy case only.
C=Parsing variations: useful later, but a parsing error on a normal report is less consequential than a wrong approval on an adversarial one.
D=Load cases: latency under load is an operational metric, not an evaluation of decision quality, and belongs in a separate performance test.
T: Prioritize evaluation cases that could produce the worst outcome: edge, adversarial, unauthorized and high-consequence inputs.

@ PLTR-AIE D5 T5.1 applied tradeoff
S: A function generates a short customer-facing explanation of a declined transaction. The team wants to evaluate it automatically. Which evaluator design is appropriate?
A: Exact string match against a reference explanation written by a human for each test case
B: A per-criterion rubric for required facts, forbidden content and tone, plus a deterministic check that the decline reason matches the record
C: A single pass/fail judgement by a second model asked whether the explanation looks good to a customer, applied to every test case in the suite
D: Human review of every output, since free-text quality cannot be measured by any automated method
K: B
G: ## Evaluators for free text
Deterministic outputs (an amount, a category) suit exact-match evaluators. Free text does not: two correct explanations can differ in every word. The exam guide lists evaluators and metrics as things to design, and the design should fit the output.
## A rubric with a deterministic anchor
- Rubric criteria: mentions the correct reason, suggests the next step, avoids internal jargon, no promises about outcomes, polite tone. Each is scored separately, so a failure tells you what to fix.
- Deterministic anchor: the decline reason in the text must match the reason code on the transaction; this is checked in code, not by judgement.
- Model-based grading can score rubric items, but it needs explicit criteria and should be spot-checked against human ratings.
Example: a case fails "correct reason" when the text says "insufficient funds" but the record says "card expired", regardless of how well written it is.
W: Rubric per criterion plus a deterministic factual check: this measures the qualities that matter, points to the failing criterion, and anchors correctness to the record.
X: A=Exact match: a different but correct wording would fail; the metric would measure phrasing, not quality.
C=Single "looks good" judgement: an unstructured verdict is inconsistent and cannot say what is wrong; it also misses factual mismatches that a model may not notice.
D=Human review of everything: humans calibrate the automated evaluator and review samples, but reviewing every output does not scale to continuous regression testing.
T: Evaluate free text with criterion-level rubrics and anchor factual claims with deterministic checks.

@ PLTR-AIE D5 T5.3 advanced troubleshooting
S: A classification function's evaluation score fell from 94% to 85% after a prompt change. Looking closer, 40 new test cases were added to the suite in the same week, and the old 200 cases still score 94%. How should this be interpreted?
A: The prompt change caused a regression that only shows on recent data, so the prompt should be reverted and the new cases set aside until the regression is fixed
B: The suite's distribution changed: the original cases are unchanged at 94%, so the new cases and the prompt change must be measured separately
C: The 40 new cases are mislabelled, since a function that scores 94% on 200 cases cannot genuinely score far lower on a new sample
D: The drop is normal variance, because adding cases always lowers scores at first, and the function should be left as it is
K: B
G: ## Three causes of a score change
The exam guide asks you to distinguish a genuine regression, expected variance and a change in the test distribution. Changing the prompt and the suite in the same week mixes two of them.
## Separating the effects
- Hold the suite fixed: on the original 200 cases, old and new prompts both score 94%, so the prompt did not regress on that distribution.
- Look at the new 40 cases alone: both prompts should be run on them. If both score low, the cases are a harder or different distribution (or need label review); if only the new prompt scores low, there is a regression specific to that kind of input.
- Report the two numbers separately rather than one blended score.
Example: both prompts score 50% on the 40 new multilingual cases; the suite now covers something the function never handled, which is a gap to work on, not a regression.
W: Distribution change to be separated from the prompt change: the unchanged 94% on the original cases shows the drop comes from the new cases, so each effect must be measured on its own before deciding anything.
X: A=Revert and remove cases: the evidence does not show a regression on the original data, and removing hard cases hides a real gap.
C=Assume mislabelling: new cases can be mislabelled, but a lower score on a different sample is also what a genuine coverage gap looks like; check, do not assume.
D=Normal variance: a nine-point drop concentrated entirely in the new cases is not run-to-run noise; it is a signal about those cases.
T: Never change the suite and the function in the same comparison; measure old and new cases separately to tell distribution shift from regression.

@ PLTR-AIE D5 T5.4 applied use-case
S: A deployed agent lets users give a thumbs-down and a comment on each answer. The team wants this feedback to improve the agent over time. Which process is right?
A: Automatically append every thumbs-down answer and its comment to the system prompt as an example of what to avoid, so the agent adjusts immediately
B: Review the thumbs-down cases, turn confirmed failures into evaluation cases with corrected expected results, and prioritize fixes by frequency
C: Retrain the underlying model each week on the comments, since direct feedback is the most effective training signal for an agent
D: Count the thumbs-down rate as a KPI and reduce the agent's scope whenever the rate rises, until the rate stays below a target
K: B
G: ## Closing the loop
The exam guide asks for feedback loops that capture user corrections or downstream outcomes and turn them into new evaluation cases or improvement priorities. Feedback is raw signal; it becomes useful when it is reviewed, turned into a reproducible test, and ranked.
## The process
- Review: some thumbs-down are wrong (user disagreement with a correct answer); confirm each failure.
- Convert: each confirmed failure becomes an evaluation case with the input, the retrieved context if relevant, and the corrected expected output.
- Prioritize: group failures by type (retrieval miss, refusal where an answer existed, wrong tool); fix the most frequent or most harmful first.
- Verify: every fix is checked against the growing suite, so old failures cannot return unnoticed.
Example: 60% of confirmed failures are retrieval misses on one document family; that becomes the first improvement, and its 25 new cases guard the fix.
W: Review, convert to evaluation cases, prioritize by frequency: feedback drives measurable improvement and the suite grows to protect against regressions.
X: A=Auto-append to prompt: unreviewed feedback (including wrong feedback) would change behaviour immediately, bloat the prompt and bypass any testing.
C=Weekly retraining: training foundation models is outside the AI engineer's role; the practical levers are prompts, retrieval, tools and evaluation.
D=Shrink scope on KPI: a thumbs-down rate without diagnosis does not say what to fix; cutting scope removes value instead of correcting failures.
T: Turn user feedback into reviewed evaluation cases and prioritized fixes; it is signal to test against, not a control to react to blindly.

@ PLTR-AIE D5 T5.3 applied troubleshooting
S: An engineer wants to decide whether a new model is better for a summarization function. On one evaluation run the candidate scores 82% and the current model 80%. Rubric scoring is done by a grading model. What is the sound way to decide?
A: Adopt the candidate, since 82% is higher than 80% and the grading model applies the same rubric to both
B: Run each model several times, compare score distributions and per-case differences, and check a sample of grader verdicts against humans
C: Keep the current model, since a two-point gain is within the margin that a grading model can be wrong by, so the candidate has not proved itself
D: Run the candidate once more and adopt it if it scores above 80% again, since two wins out of two shows that the result is reliable
K: B
G: ## Comparing models on non-deterministic outputs
Both the function and the grading model are non-deterministic, so a single run of each is two noisy measurements. The exam guide asks you to tell signal from variance and to detect regressions across models.
## A fair comparison
- Repeat runs: several runs per model on the same fixed suite give a distribution; compare the spread, not one number.
- Per-case view: see which cases the candidate wins and loses; a model that is better on average but fails a critical case type may still be the wrong choice.
- Calibrate the grader: sample verdicts and compare with human ratings; if the grader is inconsistent, both scores are unreliable.
- Decide against a threshold set in advance, including cost and latency.
Example: candidate 80-84% across five runs, current 78-82%, grader agrees with humans 92% of the time, and the candidate loses no high-consequence case: adopt.
W: Repeated runs, per-case comparison and grader calibration: this is how to know whether two points is a real difference and whether the measurement itself can be trusted.
X: A=Adopt on one run: a two-point gap on single runs of two noisy processes is not evidence; the next run could invert it.
C=Reject on principle: a small gain can be real; the right response is to measure enough to know, not to assume it is noise.
D=Best of two: two single runs are still too few, and "above 80%" does not compare the models against each other under the same conditions.
T: Compare models with repeated runs on a fixed suite, per-case analysis and a calibrated grader before adopting a change.

@ PLTR-AIE D5 T5.2 advanced use-case
S: A workflow drafts responses to regulatory inquiries. Its evaluation suite measures factual accuracy against a reference. A reviewer notes that the suite never checks whether the workflow refuses when the inquiry asks for information it is not allowed to disclose. What should be added?
A: Nothing, since the factual accuracy metric already covers the quality of the responses and refusals would lower the accuracy score
B: Cases where refusing or escalating is the right answer, scored as such by the evaluator, plus cases where a refusal would be wrong
C: A rule in the prompt forbidding disclosure of restricted information, since the evaluation suite should measure answer quality while policy is enforced by the instructions
D: A separate monthly audit by the compliance team, since refusal behaviour is a compliance matter rather than an engineering metric
K: B
G: ## Refusal is a measured behaviour
The exam guide lists refusal behaviour among the things to measure, along with correctness, groundedness, tool selection, safety, latency and cost. A workflow that answers everything accurately but discloses restricted information is failing in its most important dimension, and a suite that only rewards answers cannot see it.
## Designing the cases
- Positive refusal cases: inquiries that must be refused or escalated; the expected outcome is the refusal, scored as correct.
- Negative cases: legitimate inquiries where refusing would be a failure, so the workflow cannot pass by refusing everything.
- Evaluator: checks the decision (answer, refuse, escalate) and that no restricted content appears in the output.
Example: 30 restricted-information inquiries expect refusal with a pointer to the compliance contact; 30 near-miss inquiries expect a full answer.
W: Refusal and non-refusal cases with a decision-level evaluator: the suite then measures both over-disclosure and over-refusal, which is what the workflow must get right.
X: A=Accuracy is enough: accuracy against a reference answer does not detect a correct-looking answer that should never have been given.
C=Prompt rule only: a rule is a control, not a measurement; without test cases nobody knows whether it works or regresses after a change.
D=Monthly audit: audits are too slow and too sparse to catch a regression introduced by a prompt change on Tuesday.
T: Measure refusal behaviour explicitly, with cases that expect refusal and cases that forbid it.

@ PLTR-AIE D5 T5.1 applied troubleshooting
S: A team's evaluation suite for a retrieval-grounded assistant reports 90% answer correctness, yet production users report many unsupported claims. Investigation shows the suite's expected answers were accepted whenever the answer "sounded right". What is missing?
A: A larger suite, since 90% on a small suite is not statistically meaningful and more cases would reveal the unsupported claims
B: A groundedness evaluator that checks each answer's claims against the retrieved context, so that a fluent but unsupported answer fails
C: A latency metric, since users who wait too long tend to judge answers more harshly and report problems that are not real
D: A stricter correctness threshold, raising the passing score from 90% to 95% so that the team is forced to improve the answers
K: B
G: ## Groundedness is its own metric
The exam guide separates correctness from groundedness: an answer can match the reference and still not be supported by the retrieved evidence, or sound plausible and be wrong. A grader that accepts answers because they sound right measures fluency.
## Adding the evaluator
- For each case, keep the retrieved context with the answer.
- The groundedness evaluator checks that each claim in the answer is supported by that context (model-based grading with explicit criteria, calibrated against human judgement).
- Unsupported claims fail even when the final answer happens to be right.
- Add adversarial cases where the context does not contain the answer; the expected behaviour is to say so.
Example: "The warranty is 3 years" matches the reference, but the retrieved chunk said 2 years; groundedness fails and reveals the model relied on prior knowledge.
W: Groundedness evaluator against retrieved context: it makes the suite detect exactly the failure users see, fluent claims that the evidence does not support.
X: A=Bigger suite: more cases graded the same lenient way give the same blind spot with more confidence.
C=Latency metric: user complaints are about content, and latency does not explain unsupported claims.
D=Higher threshold: a stricter bar on a metric that cannot see the problem changes nothing about what is measured.
T: Measure groundedness separately from correctness; an answer must be supported by the retrieved evidence, not just sound right.
