@ PLTR-AIE D4 T4.1 applied use-case
S: A pipeline must summarize 80,000 customer call transcripts into three fields: main issue, resolution status and follow-up needed (yes/no). Which output design is right for the LLM step?
A: A single free-text summary paragraph per transcript, since the model writes natural summaries best when it is not constrained by a schema
B: A structured output schema with three typed fields (short text, enumerated status, boolean), validated before the values are written to columns
C: Three separate LLM calls per transcript, one per field, each returning free text that is later combined
D: A single call that returns a markdown table that a regular expression later splits into the three columns
K: B
G: ## Structured output for pipelines
The exam guide lists structured output and validation among AI-powered data processing techniques. Fields that feed columns, filters and dashboards need defined types: a status enumeration cannot be a paragraph.
## Design
- Schema: `main_issue` (short string), `resolution_status` (enum: resolved, pending, escalated), `follow_up_needed` (boolean).
- One call per transcript producing the structure.
- Validation: enum and boolean checked in code; failures flagged.
- Keep prompt and raw response for audit.
Example: 80,000 rows gain three clean columns; a dashboard filters `follow_up_needed = true` directly.
W: Typed three-field schema with validation: it produces exactly the columns needed and makes bad outputs detectable.
X: A=Free paragraph: status and the boolean would have to be parsed from prose; dashboards cannot use it.
C=Three calls: triple the cost for the same information, and still free text.
D=Markdown table with regex: a fragile parse of free-form text; the schema does the job directly.
T: When AI output feeds columns, ask for a typed structure and validate it.
V: Pipeline Builder, AIP

@ PLTR-AIE D4 T4.3 applied tradeoff
S: An AI step classifies incoming documents. Classification depends only on the document content and is used by five downstream pipelines and three applications. A colleague proposes doing it in a Workshop function so that users always see the latest model's output. What is the better choice and why?
A: The Workshop function, since users benefit from the latest model output on every view
B: A pipeline LLM transform, since the result depends only on the document and is reused by many pipelines and apps
C: An agent, since classification is a conversational task that benefits from the model asking clarifying questions about ambiguous documents
D: Both, so that the pipeline value can be compared with the on-view value each time
K: B
G: ## Reuse decides the layer
The exam guide asks you to justify the layer by consumer breadth, freshness, reusability, scale and cost. Classification that depends only on the content, consumed by eight consumers, is reusable enrichment: compute once in the pipeline.
## Consequences
- Downstream pipelines can read the class as a column; a Workshop function cannot feed pipelines.
- One consistent value for every consumer, with the model and prompt version recorded.
- Model upgrades are applied by re-running the transform (with a version bump), not by changing behaviour per view.
Example: the class is a property; a Workshop list filters on it; two pipelines route documents by it; an agent uses it as metadata.
W: Pipeline transform: the computation is content-only and widely reused, so storing it once serves every consumer, including the pipelines that a Workshop function could never serve.
X: A=Workshop function: pipelines cannot consume it, values differ per view, and the same document is classified repeatedly.
C=Agent: classification needs no conversation; an agent adds cost and inconsistency.
D=Both: two sources of truth for the same fact invite disagreement and double cost.
T: Content-only results needed by many consumers belong in the pipeline as stored properties.
V: Pipeline Builder, Ontology

@ PLTR-AIE D4 T4.2 applied troubleshooting
S: A quality reviewer finds that an LLM extraction step produced a wrong date for a contract. The pipeline stored the prompt version, model and raw response. How does this stored information help, and what should the engineer do?
A: It is not useful, because the model's reasoning cannot be inspected from a response; the engineer should simply re-run the extraction and hope the new value is right
B: The raw response and prompt version reveal whether the error was in the prompt, the model or the parsing; fix that stage, add the case to the suite, reprocess affected rows
C: It helps only for compliance reporting; the engineer should not change anything based on a single error
D: It allows blaming the model provider for the error and requesting a refund
K: B
G: ## Using audit artefacts for debugging
The exam guide asks to preserve prompts and raw responses where auditability and debugging require them. Debugging is the second use: a wrong value becomes a reproducible case.
## Steps
- Read the raw response: did the model return the wrong date, or was the right date mangled by parsing (dd/mm vs mm/dd)?
- Read the prompt version: did the instructions cover this date format?
- Fix the right stage (prompt, parser or model), add the contract as an evaluation case, and reprocess the rows produced under the faulty version (the version column tells you which).
Example: the raw response had "03/04/2025"; the parser read it as 4 March; the prompt is changed to require ISO dates and 2,000 rows are reprocessed.
W: Stored response and version localize the error and bound the reprocessing: this is the practical payoff of auditability.
X: A=Not useful: the raw response is exactly what reveals the failing stage; blind re-running may repeat the error.
C=Compliance only: a single error can reveal a systematic parsing bug affecting thousands of rows.
D=Blame the provider: the goal is a correct dataset, and the error may well be in the prompt or parser.
T: Use stored prompts, versions and raw responses to find the failing stage, fix it, and reprocess exactly the affected rows.

@ PLTR-AIE D4 T4.4 applied use-case
S: A team runs an LLM enrichment over 10 million rows. The provider allows 100 requests per second. The transform currently fires requests as fast as Spark executors can, causing throttling errors and failed rows. What should the engineer implement in the Code Repositories transform?
A: Retry every failed row immediately in a tight loop until it succeeds
B: Client-side rate limiting under the provider's limit, backoff on throttling, and recorded failed rows for a later retry pass
C: More Spark executors, so that the rows that failed with throttling errors are retried faster and in parallel across the cluster
D: Splitting the dataset across three provider accounts to triple the limit
K: B
G: ## Programmatic control of AI calls
The exam guide lists rate limiting among the reasons to codify workflows in Code Repositories. A provider limit is a contract; exceeding it produces failures, not throughput.
## Implementation
- Limit concurrency and request rate across executors (token bucket or bounded parallelism) to stay under 100/s.
- Batch where the API allows.
- Exponential backoff with jitter on throttling responses.
- Persist failed rows with the error and retry them in a later bounded pass, never silently dropping them.
Example: at 90 requests per second the 10 million rows take about 31 hours spread over nightly windows, with zero dropped rows.
W: Rate limiting, backoff and recorded retries: the transform respects the provider's limit and guarantees completeness.
X: A=Tight retry loop: hammering a throttled API keeps it throttled and can get the client blocked.
C=More executors: more parallelism increases the request rate, which is the problem.
D=Multiple accounts: circumventing limits violates provider terms and is not an engineering solution.
T: Control AI call rates in code with limits, backoff and recorded retries; never fire as fast as the cluster can.
V: Code Repositories

@ PLTR-AIE D4 T4.1 applied use-case
S: A pipeline must detect whether product photos show visible damage, for 200,000 images per week. Which approach fits?
A: A text LLM step over the image file names and sizes, which correlate with damage reports
B: A vision-capable model step that classifies each image with a structured output (damaged / not damaged / unclear) and routes unclear results to review
C: An agent that opens each image in conversation and asks a warehouse employee to confirm the damage
D: A deterministic rule that flags any image larger than 2 MB, since damaged items are usually photographed in more detail and produce larger files
K: B
G: ## Visual processing at scale
The exam guide names visual document processing and VLMs (vision language models) among AI-powered data processing. Image classification for 200,000 photos a week is a batch pipeline task for a vision-capable model.
## Design
- Structured output: an enumeration plus a confidence.
- Routing: unclear or low-confidence images go to human review; the rest are written as properties.
- Evaluation: a labelled set of damaged and undamaged photos measures precision and recall before the pipeline goes live.
- Keep the raw response and model version per image.
Example: 92% classified automatically, 8% reviewed; damaged items trigger a workflow via an automation.
W: Vision model with structured output and review routing: it reads the images themselves and handles uncertainty explicitly at pipeline scale.
X: A=File names and sizes: these do not show damage; any correlation is accidental and unreliable.
C=Conversational confirmation: 200,000 images cannot be confirmed one by one in chat.
D=Size rule: file size depends on resolution and compression, not on whether the item is damaged; it would flag crisp photos of perfect items and miss small photos of broken ones.
T: For image content questions at scale, use a vision-capable model in the pipeline with structured output and a review path.
V: Pipeline Builder, AIP

@ PLTR-AIE D4 T4.3 applied comparison
S: Which of the following is a workload that belongs north of the Ontology rather than in the pipeline?
A: Translating every product description in the catalogue into three languages, refreshed automatically whenever a description changes
B: Drafting a reply to the specific email an agent is currently reading, using that customer's open tickets and the agent's selected tone
C: Computing an embedding for every support article so that semantic search works
D: Extracting the invoice total from every scanned invoice as it arrives
K: B
G: ## Recognizing interactive, context-dependent work
The exam guide distinguishes south (reusable batch enrichment) from north (interactive, context-dependent reasoning). The test: does the result depend on who is asking, what they selected, and the moment?
- Catalogue translation, article embeddings, invoice totals: depend only on the data, reused by many, computed in batch: south.
- A reply to this email with this customer's current tickets and this agent's chosen tone: depends on the user's context and the moment: north.
Example: the reply draft is generated when the agent clicks "draft", with the selected tone and the live ticket list; nothing about it can be precomputed.
W: Drafting a reply with the current context: it is interactive and context-dependent, which is the definition of north-of-Ontology work.
X: A=Catalogue translation: content-only, reused, refreshed on change: pipeline.
C=Article embeddings: index building for every article: pipeline.
D=Invoice totals: per-document extraction as data arrives: pipeline.
T: Work that depends on the current user, selection and moment runs north; content-only, reusable work runs south.
V: AIP Logic, Pipeline Builder

@ PLTR-AIE D4 T4.2 applied tradeoff
S: Storing raw LLM responses for 50 million rows is expensive. The compliance team requires auditability for the extracted fields. What is a sound compromise?
A: Store nothing beyond the extracted values themselves, since the storage cost of 50 million responses outweighs the compliance team's need
B: Keep prompt version, model id and input reference per row; keep raw responses for a retention window plus sampled rows; document it
C: Store the raw responses in a spreadsheet maintained by the compliance team
D: Store everything forever, regardless of cost, since compliance always takes priority
K: B
G: ## Auditability with proportion
The exam guide asks to preserve prompts and raw responses where auditability and debugging require them, which leaves room for judgement about scope and retention.
## A proportionate design
- Always: prompt version, model id, input reference, timestamp per row (small).
- Raw responses: kept for a retention window agreed with compliance, plus indefinitely for flagged, reviewed or sampled rows.
- Policy: documented, so an auditor knows which rows can be fully reconstructed and which have metadata only.
- Reprocessing: with the input reference and version, a row can be regenerated, acknowledging non-determinism.
Example: 90 days of full responses, 1% random sample kept permanently, all metadata permanent.
W: Metadata always, raw responses by retention and sampling, with a documented policy: this satisfies audit needs at a sustainable cost.
X: A=Nothing extra: the audit requirement is unmet; a wrong value cannot be explained.
C=Spreadsheet: 50 million responses cannot live in a spreadsheet, and it is outside governance.
D=Everything forever: a policy with no proportion; compliance teams accept retention windows.
T: Keep cheap audit metadata for every row and raw responses under a documented retention and sampling policy.
V: Pipeline Builder

@ PLTR-AIE D4 T4.1 advanced troubleshooting
S: An LLM extraction over supplier PDFs works well for English documents but produces empty or wrong fields for the 15% of documents in Japanese. What should be done?
A: Exclude the Japanese documents from the pipeline and handle them manually, since the model evidently does not support that language well enough
B: Check the extracted text (OCR, encoding), the prompt's language assumptions and the model's multilingual capability; fix that stage and add Japanese cases
C: Translate every incoming document to English with a second model call before the extraction step, regardless of the additional cost and latency
D: Ask the supplier to send documents in English only
K: B
G: ## Language failures have several possible causes
Empty or wrong fields for one language can come from: text extraction (OCR not configured for Japanese, encoding errors), the prompt (examples and field names assume English date and number formats), or the model (weak multilingual support). The exam guide asks you to diagnose the stage before changing anything.
## Investigation
- Inspect the extracted text for Japanese PDFs: garbled text means the extraction stage.
- Inspect raw responses: a correct Japanese answer mangled by parsing means post-processing.
- If the model struggles, choose a model with stronger Japanese capability from the reference characteristics.
- Add Japanese documents to the evaluation suite so the fix is measured.
Example: OCR was configured for Latin scripts only; enabling Japanese OCR fixes 90% of the failures, and a date-format note in the prompt fixes the rest.
W: Stage-by-stage diagnosis with evaluation cases: it finds the actual cause for the Japanese documents and prevents regressions.
X: A=Exclude: 15% of suppliers unprocessed is a failed requirement, and the assumption about support is untested.
C=Translate everything: costly and lossy, and if extraction is garbled the translation is garbled too.
D=English only: not within the engineer's control and not a technical fix.
T: When one language fails, check extraction, prompt assumptions and model capability in turn, and add that language to the evaluation suite.
V: Pipeline Builder, AIP Evals
