# PLTR-AIE batch 31: Domain 6 round 4 (Automation, Orchestration, and Integration), 8 questions

@ PLTR-AIE D6 T6.1 applied use-case
S: A workflow must run an AI classification on every new support email and, separately, a nightly summary of the day's emails for managers. Which trigger configuration serves both?
A: One schedule at midnight that classifies all of the day's emails and produces the summary in the same run
B: An object-creation trigger for per-email classification, plus a separate nightly trigger for the day's summary
C: An object-creation trigger that both classifies the email and regenerates the full daily summary every time an email arrives
D: A manual run by a manager each evening that performs both tasks together
K: B
G: ## Two workloads, two triggers
The exam guide asks you to configure triggers and execution modes to fit the workload. Per-item, event-driven work and periodic aggregate work are different.
## Configuration
- Event trigger per email: classify within minutes of arrival.
- Nightly trigger: summarize the day's classified emails in one batch run.
- The summary reads the stored classifications rather than recomputing them.
Example: 3,000 emails are classified during the day as they arrive; at 23:00 one run produces the managers' summary.
W: Per-item event trigger plus a nightly batch trigger: each workload runs at the cadence it needs.
X: A=Midnight for both: emails sit unclassified all day; the per-email need is not met.
C=Regenerate the summary per email: thousands of full summary runs a day for a report read once.
D=Manual: a manager running both tasks by hand each evening is unreliable, delays classification all day, and is unnecessary when triggers exist.
T: Use event triggers for per-item work and scheduled triggers for periodic aggregates.
V: Automate

@ PLTR-AIE D6 T6.2 applied troubleshooting
S: A function-backed Action that applies an AI-generated field to an object occasionally fails validation because the AI output contains a value slightly outside the allowed range. Which design handles this best?
A: Widen the Action's allowed range enough that the AI output always passes validation, which removes the failures entirely
B: Keep the Action's validation, clamp or reject out-of-range values in the function with a logged flag, and add the cases to the suite
C: Retry the AI call until it produces a value inside the range
D: Apply the value without validation whenever it is only slightly outside the allowed range, since small deviations are harmless
K: B
G: ## Validation stays authoritative
The exam guide treats Action validation as the boundary that protects the Ontology. The function must produce values the Action accepts, with explicit handling of the rest.
## Design
- Function: validate the AI output against the same range; clamp where a documented rule allows, otherwise reject and flag.
- Action: unchanged; its validation catches anything that slips through.
- Evaluation: cases that produce boundary values.
Example: a confidence of 1.02 is clamped to 1.0 with a flag; a category outside the list is rejected and routed to review.
W: Function-side handling with the Action's validation intact: bad values never reach the object and the behaviour is explicit and tested.
X: A=Widen the range: it weakens the rule for every caller of the Action, not just this function.
C=Retry until it fits: wasteful, and the model may never comply.
D=Skip validation: "slightly outside" today is "far outside" tomorrow.
T: Enforce ranges in the function before the Action and keep the Action's validation as the final guard.
V: Actions, AIP Logic

@ PLTR-AIE D6 T6.3 applied use-case
S: An automation runs an AI step that takes about a minute per object, and objects can arrive in bursts of hundreds. Users complain that during bursts, urgent objects wait behind routine ones. What orchestration change helps?
A: Removing the AI step from the automation so that nothing waits
B: Prioritized execution: route objects by priority to separate paths or queues with their own concurrency limits, and monitor queue depth
C: Increasing the model's speed by switching to a smaller, faster model for every object regardless of its priority or complexity
D: Telling users that bursts are rare and that a delay of an hour for urgent objects during a burst is acceptable for the business
K: B
G: ## Prioritization in orchestration
The exam guide asks you to design execution modes and to monitor queues and latency. A single first-in-first-out path cannot honour priority.
## Design
- Priority property on the object (from a cheap classifier or rules).
- Separate automation paths or queues per priority with their own concurrency.
- Queue-depth and wait-time monitoring; alerts on backlog.
Example: during a 400-object burst, the 12 urgent objects complete within three minutes while routine ones drain over the next hour.
W: Priority-routed paths with concurrency limits and monitoring: urgent work is not blocked by routine volume.
X: A=Remove the AI step: the step is the purpose of the automation.
C=Smaller model: may reduce quality and still does not prioritize.
D=Accept: the complaint is legitimate and the fix is structural.
T: Separate automation paths by priority so urgent objects are not queued behind routine ones.
V: Automate

@ PLTR-AIE D6 T6.1 applied comparison
S: Which Automate effect is appropriate for "when an invoice object is flagged as disputed, create a review task for the account manager with an AI-drafted summary attached"?
A: A notification effect alone, since the account manager will create the review task themselves after reading the notification message
B: A function effect that drafts the summary, then an Action effect that creates the review task with the summary and assigns it
C: A schedule effect that runs once a week to find all disputed invoices and list them in a report for managers to work through
D: An Ontology edit effect that sets a "needs review" flag on the invoice object, with no task created and no summary drafted
K: B
G: ## Composing effects
The exam guide lists effects (functions, Actions, notifications) among automation configuration. Creating a task with AI content is a function (draft) followed by an Action (create and assign).
## Configuration
- Trigger: invoice.disputed becomes true.
- Effect 1: Logic function drafts the summary (typed output).
- Effect 2: Action creates ReviewTask with summary, invoice link and assignee; validation ensures required fields.
- Optional: notification to the manager.
Example: a dispute flagged at 10:02 produces a task with a summary in the manager's queue at 10:03.
W: Function effect then Action effect: the summary is produced and the task created and assigned in one chained automation.
X: A=Notification only: the task and summary are the requirement; a message is not a task.
C=Weekly schedule: a dispute could wait a week, and a list is not a task assigned to the manager with a summary.
D=Flag only: a flag on the invoice creates no task, drafts no summary and assigns nobody; the requirement is unmet.
T: Chain a function effect for AI content with an Action effect for the object change.
V: Automate, AIP Logic, Actions

@ PLTR-AIE D6 T6.3 applied troubleshooting
S: After a dependency (an external API used by an automation's function) was replaced with a new version, the automation began writing empty values. Nobody noticed for three days. What should have been in place?
A: Nothing could have detected this in advance, since the automation reported success on every run and the function did not throw an error
B: Output validation in the function, a failure path instead of silent writes, and monitoring of the written property (empty-rate alert)
C: A policy forbidding any upgrade of external dependencies used by automations, so that their behaviour can never change unexpectedly
D: A weekly manual check of a few randomly chosen objects by the team to confirm that the written values still look reasonable
K: B
G: ## Silent failures are design failures
The exam guide asks for workflows that remain safe when dependencies fail and for observability of real behaviour. A succeeded run that writes empties is a failure the system should have detected.
## Controls
- Validation: empty or malformed values fail the step.
- Failure path: route to retry or review; never write a null as if it were a result.
- Monitoring: empty-rate and distribution on the written property with alerts.
Example: the first run after the upgrade produces 100% empties; the alert fires within minutes and the dependency is rolled back.
W: Validation, explicit failure path and property monitoring: the silent failure becomes a loud one on day one.
X: A=Undetectable: validation and monitoring detect exactly this.
C=Forbid upgrades: dependencies must evolve; the answer is detection.
D=Weekly manual check: three days of empties would still pass unnoticed until the check.
T: Validate outputs, fail explicitly and monitor written properties so dependency changes cannot silently corrupt data.
V: Automate, AIP Observability

@ PLTR-AIE D6 T6.2 applied use-case
S: A multi-step workflow must be auditable: for each processed object, which steps ran, with which versions, and what each produced. Which design provides this?
A: A single log line per workflow run saying "completed" with the timestamp, written to the automation's execution history
B: Step-level records on a linked run record: step, function version, input/output references, status and timestamp
C: Screenshots of the automation's configuration page saved monthly to a shared folder as a record of how it was set up
D: The responsible engineer's memory of how the workflow was configured at the time, to be recounted if an auditor asks
K: B
G: ## Auditable orchestration
The exam guide asks for audit and lineage evidence for AI workflows. A chain of steps needs per-step records linked to the object.
## Design
- Run record object per workflow execution, linked to the processed object.
- Step records with version, status, references to inputs and outputs.
- Queryable: "show the chain for object X" or "which objects were processed by step v3".
Example: an auditor sees that object O-77 went through extract v4, validate v2 and apply v6, with the summary it produced.
W: Per-step linked records with versions and references: the complete, queryable audit trail.
X: A=One "completed" line: no detail of steps, versions or outputs.
C=Screenshots: configuration at a point in time, not what happened to each object.
D=Memory: an engineer's recollection is not evidence; people forget, leave, and cannot reconstruct per-object details.
T: Record each workflow step's version, status and references on a linked run record.
V: Automate, Ontology

@ PLTR-AIE D6 T6.1 applied tradeoff
S: An automation currently triggers on every property change of an object, running an AI step each time. Most changes are irrelevant to the AI's purpose. What should change?
A: Nothing; running on every change guarantees the AI output is always current
B: Narrow the trigger to the properties or transitions that affect the AI's inputs, and verify with run counts before and after
C: Switch the automation to a nightly schedule that processes every object regardless of whether anything about it changed
D: Add a prompt instruction asking the model to return early without output whenever nothing relevant appears to have changed
K: B
G: ## Precise triggers
The exam guide asks for triggers that avoid unnecessary executions. A trigger on "any change" wastes model calls and risks loops.
## Configuration
- Trigger on the properties the AI reads (for example, description or status), not on every field.
- Condition: skip if the relevant properties are unchanged since the last run.
- Metrics: runs per object per day.
Example: runs drop from 40,000 to 3,000 per day with identical AI outputs for consumers.
W: Property-scoped trigger with a change condition: runs happen only when the inputs the AI uses actually change.
X: A=Every change: cost without benefit; the output does not change when irrelevant fields change.
C=Nightly: relevant changes made in the morning are not reflected until the next day, losing the timeliness the event trigger provided.
D=Prompt early return: the model call has already happened; the cost is paid.
T: Trigger automations on the properties that matter, not on any change.
V: Automate

@ PLTR-AIE D6 T6.3 advanced use-case
S: A team must decommission an automation that other automations depend on (they trigger on the objects it writes). What is the safe approach?
A: Disable it and see what breaks downstream, since that is the quickest way to find out which automations really depended on it
B: Map dependents, communicate, migrate them to a replacement, disable at an agreed time with monitoring, keep it re-enable-able
C: Delete the automation together with the properties it wrote, so that no orphaned data is left behind in the Ontology
D: Keep it running forever, since something somewhere might depend on it and the cost of running it is lower than the risk of breaking things
K: B
G: ## Decommissioning with dependents
The exam guide asks for safe modification of live workflows and assessment of consumers. An automation's outputs are inputs to others.
## Approach
- Discover dependents: what triggers on or reads the properties it writes.
- Communicate; migrate dependents to the replacement source of those properties.
- Disable (not delete) at an agreed time; monitor dependents; rollback possible.
- Remove after a stable period.
Example: two downstream automations are repointed to the new enrichment pipeline before the old automation is disabled; nothing breaks.
W: Dependency mapping, migration, reversible disablement and monitoring: decommissioning without surprises.
X: A=Disable and watch: dependent automations stop silently and the breakage is discovered by users, not by the team.
C=Delete with properties: the properties are read by other automations and applications; deleting them breaks every dependent at once.
D=Forever: the platform fills with unmaintained automations whose purpose nobody remembers, each costing compute and model calls.
T: Decommission automations by mapping dependents, migrating them, and disabling reversibly with monitoring.
V: Automate, Data Lineage
