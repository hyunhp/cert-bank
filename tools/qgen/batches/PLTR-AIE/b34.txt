@ PLTR-AIE D1 T1.1 applied use-case
S: A Logic function receives an Order object and must include the names of all products on the order in its prompt. Products are linked objects. How is this done in the function?
A: Ask the caller to type the product names into a separate string input every time the function is invoked from the application
B: Traverse the Order's product link inside the function and inject the product names as a list variable
C: Hard-code the most common product names in the system prompt so the model recognizes them from memory
D: Ask the model to infer the products from the order number pattern, since orders in the same range share products
K: B
G: ## Link traversal for prompt context
AIP Logic can traverse links from an input object to related objects and inject their properties. The exam guide lists tools and variable injection among the building blocks.
## Pattern
- Input: Order object.
- Block: traverse `order → products`, collect `name` into a list.
- Prompt: "Products on this order: {product_names}".
Example: order O-77 with three linked products produces a prompt listing exactly those three.
W: Link traversal inside the function with list injection: the prompt is built from the actual related objects without caller effort.
X: A=Caller types names: manual, error-prone and unnecessary when the link exists.
C=Hard-coded names: the model cannot know which products are on this order from a general list.
D=Infer from number: order numbers carry no product information; the model would guess.
T: Build prompt context from linked objects by traversing links inside the Logic function.
V: AIP Logic, Ontology

@ PLTR-AIE D1 T1.2 applied troubleshooting
S: A Logic function applies an Ontology edit that sets `reviewed_by` to the model's suggested reviewer. Occasionally the model outputs a name that does not match any user. The edit then fails or writes an invalid value. What is the right fix?
A: Lower the temperature so that the model produces reviewer names more consistently from one run to the next and stops varying them
B: Type the output as a User object reference selected from a tool lookup of eligible reviewers, so the edit references only real users
C: Append "(unverified)" to any name the model produces and write that string into the property so readers know it may be wrong
D: Instruct the model in the prompt to only suggest reviewers it is certain exist in the organization and to avoid guessing names
K: B
G: ## Typed references instead of free text
The exam guide asks for typed outputs and safe Ontology edits. A property that references a user should be an object reference chosen from real candidates, not a string the model composes.
## Design
- Tool: query eligible reviewers (active users with the right role).
- Output: a reference selected from that list (an enumeration of ids or an object reference).
- Edit: writes the reference; impossible to produce a non-existent user.
Example: the model picks reviewer U-204 from five candidates; the edit links the object to that user.
W: Object-reference output from a looked-up candidate list: the edit can only point to users that exist.
X: A=Lower temperature: the model still invents names; consistency is not existence.
C="(unverified)": the property is still wrong and now has noise in it.
D=Instruct certainty: the model cannot verify existence; instructions do not replace lookups.
T: When a model must select an entity, present real candidates and output a typed reference, never a free-text name.
V: AIP Logic, Ontology

@ PLTR-AIE D1 T1.3 applied use-case
S: An engineer wants to compare two prompt versions of a Logic function on 200 real past inputs without affecting production. What is the right approach?
A: Publish both versions to production side by side and let users pick whichever prompt they prefer for each request they make
B: Run both drafts against the 200 inputs as evaluation cases, compare per case and in aggregate, then publish the winner
C: Replace the production version with the new prompt for a day and compare the number of support tickets with the previous day
D: Ask the model itself to read both prompts and state which one is better written for the task, and publish the one it prefers
K: B
G: ## Offline comparison before publishing
The exam guide asks you to evaluate before publishing and to preserve consumer behaviour. Drafts can be run against evaluation cases without touching the published version.
## Approach
- Cases: the 200 inputs with expected or reference outputs.
- Run each draft; compare per-case and aggregate; repeat for variance.
- Publish the better one as a new version; migrate consumers.
Example: version B wins on 170 of 200 cases and loses on none of the critical ones; it is published.
W: Evaluation of both drafts on the same cases, then publication: evidence-based choice with production untouched.
X: A=Both in production: users become the experiment with no measurement.
C=Day-long swap: users affected and support tickets are a poor, delayed signal.
D=Ask the model: the model's opinion of prompts is not an evaluation.
T: Compare prompt versions offline on real cases before publishing.

@ PLTR-AIE D1 T1.1 applied tradeoff
S: A Logic function needs the current exchange rate for a currency pair to compute an amount in the prompt. Rates change hourly. How should it get the rate?
A: Ask the model for the current exchange rate inside the prompt, since large models have seen exchange rates in their training data
B: Look up the current rate from a function or Ontology object maintained by a sync, inject it, and do the arithmetic in code
C: Hard-code last month's published rate in the system prompt and update it manually whenever someone remembers to check
D: Let the user type the current rate into an input field each time they run the function, so the value is always what they intended
K: B
G: ## Live facts and arithmetic belong outside the model
The exam guide says deterministic rules and lookups are code; the model interprets. A rate is a fact to fetch; multiplication is arithmetic to compute.
## Design
- Rate object or function (fed by a scheduled sync).
- Code block computes the converted amount.
- The prompt receives the computed figure for the language task.
Example: rate 1.0842 fetched; amount 1,200 EUR becomes 1,301.04 USD in code; the model writes the sentence around the figure.
W: Fetch the rate from a maintained source and compute in code: current, exact, auditable.
X: A=Model knows rates: it knows stale, approximate values and will present them confidently.
C=Hard-coded: a rate that changes hourly is wrong within hours of being typed in, and nobody will keep it current.
D=User types: manual entry of a value a system already holds invites typos and stale figures for no benefit.
T: Fetch live facts via tools and do arithmetic in code; give the model only the result to phrase.
V: AIP Logic, Functions

@ PLTR-AIE D1 T1.2 applied use-case
S: A team is deciding which parts of a new document-intake workflow belong in code and which in AIP Logic. Which step is a clear case for implementing in code rather than AIP Logic?
A: Classifying the free-text complaints found in the uploaded documents into a fixed set of themes for reporting
B: Validating that an uploaded CSV has the required columns, correct types and no duplicate ids before anything else runs
C: Drafting a polite, context-aware reply to the customer's question that accompanied the uploaded documents
D: Summarizing the long meeting transcript that was included among the uploaded documents into a one-page brief
K: B
G: ## Rules versus interpretation
The exam guide's decision area: explicit rules are code; interpretation is AI.
- CSV schema and duplicate validation: exact rules with exact answers: code.
- Theme classification, polite drafting, summarization: language understanding: AI.
Example: a code function rejects a file missing `customer_id` in milliseconds with a precise error.
W: Schema and duplicate validation: the rules are explicit and the answers exact, so code is deterministic, cheap, testable and far more reliable than a model for this step.
X: A=Theme classification: interpreting free text into themes needs language understanding, which is what AIP Logic is for.
C=Polite reply: generating a context-aware, well-phrased reply is a language task for the model.
D=Summarization: condensing a transcript faithfully is a language task that code cannot perform.
T: Validation and other exact rules go in code; language tasks go to the model.
V: Code Repositories, AIP Logic

@ PLTR-AIE D1 T1.3 applied troubleshooting
S: A Logic function's cost per run has tripled after an engineer added three few-shot examples to the prompt. Quality rose by half a point on the suite. What should the team consider?
A: Keep all three examples as they are, since few-shot examples always improve quality and cost is secondary to accuracy
B: Measure whether the half point is within variance, test fewer or shorter examples, or retrieve examples only for hard cases
C: Remove all three examples immediately and accept whatever quality loss results, since the cost increase is unacceptable
D: Add three more examples to the prompt to see whether quality rises further, since the first three produced an improvement
K: B
G: ## Examples cost tokens
Few-shot examples are powerful but expensive at volume. The exam guide asks you to optimize prompts without losing quality and to distinguish signal from variance.
## Process
- Variance: repeated runs; is half a point real?
- Alternatives: one example instead of three; shorter examples; retrieved examples for the input's type only.
- Decide on quality per token.
Example: one well-chosen example recovers most of the gain at a third of the added cost.
W: Measure the gain, test cheaper variants, choose by quality per token: the examples earn their place or are trimmed.
X: A=Keep regardless: tripled cost for a possibly noisy half point.
C=Remove blindly: the examples may help on hard cases; measure first.
D=Add more: each example adds tokens to every run; returns diminish while cost climbs further past an already tripled baseline.
T: Treat few-shot examples as a cost to justify with measured quality gains.
V: AIP Logic, AIP Evals

@ PLTR-AIE D1 T1.1 applied use-case
S: A Logic function should answer a question only from a specific document attached to the input object and must refuse if the document does not contain the answer. How should the prompt and output be designed?
A: Inject the document, instruct the model to answer only from it, and type the output as {answer, found: boolean, citation}
B: Inject the document and let the model answer freely in prose, since it will naturally say so when the document does not contain the answer
C: Do not inject the document at all; ask the model to answer from its general knowledge, which covers most common questions
D: Inject the document and set the temperature to zero, which guarantees that the model's answer is grounded in the document
K: A
G: ## Grounded answering with an explicit found flag
The exam guide asks for typed outputs and refusal behaviour when evidence is insufficient. A boolean makes the refusal machine-readable.
## Design
- Prompt: answer only from the document; if absent, set found=false and leave answer empty.
- Output struct: answer, found, citation (a quoted span or section).
- Consumers branch on found; evaluation includes unanswerable cases.
Example: "What is the warranty period?" on a document without that clause returns found=false, and the app shows "not specified in the document".
W: Grounding instruction plus a typed found flag and citation: refusal is explicit and consumers can act on it.
X: B=Free answer: models fill gaps with plausible text; "naturally saying" is unreliable.
C=General knowledge: the requirement is to answer from this document; general knowledge is ungrounded by design and may contradict it.
D=Temperature zero: a deterministic model still fabricates when the answer is absent; it just fabricates the same thing every time.
T: Make "not found" a typed output field so grounded refusals are explicit and testable.
V: AIP Logic

@ PLTR-AIE D1 T1.3 advanced tradeoff
S: A widely used Logic function needs a change to its input signature (a new required input). Fifteen consumers call it. What is the safest way to introduce the change?
A: Change the signature in place on the published version and let the consumers that fail find out from their own error logs
B: Publish a new version with the input optional and defaulted at first, migrate consumers in sequence, keep the old version meanwhile
C: Create a differently named function with the new signature and never touch the old one again, leaving both in production
D: Add the new required input to the signature but ignore it inside the function's logic so that existing behaviour does not change
K: B
G: ## Signature changes are breaking changes
The exam guide asks you to publish versions and preserve behaviour for consumers. A new required input breaks every existing call.
## Practice
- Prefer an optional input with a default first, so existing calls keep working.
- Publish as a new version; consumers migrate one by one; old version retained until then.
- Deprecate with notice; remove after confirmation.
Example: the input is optional for a month; by then all fifteen consumers pass it; it becomes required in the next version.
W: Versioned, backward-compatible introduction with planned migration: no consumer breaks and the change still lands.
X: A=In place: all fifteen consumers start failing at once with no warning and no version to fall back to.
C=New name forever: duplication and the old function stays unmaintained.
D=Ignore the input: consumers must still be changed to pass it, yet the function gains nothing; the worst of both.
T: Introduce required inputs through versions and optional defaults, migrating consumers deliberately.
V: AIP Logic
