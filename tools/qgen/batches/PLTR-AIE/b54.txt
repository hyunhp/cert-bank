@ PLTR-AIE D1 T1.1 advanced use-case
S: A warranty team's AIP Logic function reads a claim and must give a Workshop module three values: a category, a numeric confidence and a one-line rationale. AIP Evals will score each value with its own evaluator. Finance has capped the function at one LLM call per claim, and the Workshop builder refuses to parse free text. Which output design meets every constraint with the least extra logic?
A: Use three Use LLM blocks in a row, each prompted for one of the values, and return their three outputs from the function
B: Configure the single Use LLM block with a Struct output type whose named fields hold the category, confidence and rationale
C: Ask the single block for one string with the three values separated by pipes and split that string inside the Workshop module
D: Return a JSON string from the single block and let one LLM-as-a-judge evaluator check all three values inside that one string
K: B
G: ## One block, several typed values
A Use LLM block in AIP Logic declares an output type. The Logic FAQ answers "Can one LLM block return multiple values?" with yes: the **Struct** output type returns multiple named values from one block.
## Why the type matters downstream
- A typed struct lets consumers such as Workshop read each field directly, with no string parsing.
- In AIP Evals, each target-function output can be mapped to an evaluator's actual value, so a struct's fields can be scored separately (for example exact string match on the category and a floating-point range on the confidence).
- Every extra Use LLM block is another model call with its own tokens.
Example: `{category: "Water damage", confidence: 0.82, rationale: "Photo shows corrosion at the seal"}` comes back from one call.
W: B=Struct output on one block: one LLM call returns three named, typed fields that Workshop reads directly and that evaluators can score one by one.
X: A=Three blocks: each value is clean, but three model calls per claim break the one-call cost cap.
C=Pipe-separated string: it stays within one call, but the Workshop builder would have to parse free text, which is the constraint the team ruled out.
D=JSON string with one judge: one call is kept, but the output is still an untyped string and one judge cannot give each value its own evaluator and metric.
T: When one LLM step must return several values, use a Struct output type instead of extra blocks or hand-parsed strings.
V: AIP Logic, AIP Evals, Workshop

@ PLTR-AIE D1 T1.1 advanced troubleshooting
S: A Use LLM block in an AIP Logic function uses the Query objects tool on a Shipment object type to find the few late shipments a planner should chase. The Debugger shows one tool call returning about 400 Shipment objects, after which the block becomes slow and unreliable. The tool must stay flexible for other questions, and the model may not change because of an approved cost plan. What should the engineer change?
A: Move the block to a model with a much larger context window so that all 400 returned Shipment objects fit in a single prompt
B: Replace the Query objects tool with a block input that passes every Shipment object to the prompt together with all of its properties
C: Configure object return limits on the Query objects tool so that each tool call hands only a small number of objects to the LLM
D: Split the block into two Use LLM blocks so that the 400 objects are read by the first block and summarized for the second block
K: C
G: ## Tool responses count toward the block's tokens
The Logic FAQ states that all activity in AIP Logic counts toward token limits, **including tool responses**, and that token limits reset per block. A Query objects call that returns hundreds of objects floods the block's context.
## Controls on the tool itself
- The FAQ says that when an Object Query tool is added to an LLM block, you can configure object return limits to choose how many objects any tool use returns.
- The Query objects tool also lets you choose which properties the LLM can access, to make queries more token-efficient.
- These settings keep the tool available for open questions while capping what each call can return.
Example: a return limit of 20 lets the LLM still filter and sort Shipments, but no single call injects 400 objects.
W: C=Object return limits: the cap applies to every tool use, so the LLM keeps its flexible querying while each response stays small enough for a reliable block.
X: A=Larger context model: the approved cost plan fixes the model, and a bigger window still pays for 400 objects of tokens on every call.
B=Pass every object as input: it removes the tool's flexibility and puts even more data into the prompt than the failing tool call did.
D=Split into two blocks: the first block still receives the full 400-object tool response, so its context is flooded exactly as before.
T: Tool responses consume the block's tokens, so cap what a Query objects tool returns rather than enlarging the model.

@ PLTR-AIE D1 T1.2 advanced tradeoff
S: An AIP Logic function prepares refund decisions. It must compute the refund as the sum of an order's line items minus a fixed 7 percent fee, and then ask an LLM to draft a short explanation for the customer. Audits found the LLM sometimes miscalculates the amount. The amount must be exact on every run, and the team wants to spend no extra tokens on the arithmetic. Which design should the engineer choose?
A: Add the Calculator tool to the Use LLM block and instruct the model to call it whenever it needs to work out a refund amount
B: Compute the amount with deterministic blocks, such as an Execute function block, and pass the result into the drafting prompt
C: Add five worked refund examples to the prompt as few-shot examples so that the model learns the exact fee calculation pattern
D: Keep the arithmetic in the prompt and set the block's temperature to 0 so that the model returns the same amount on every run
K: B
G: ## Deterministic blocks versus LLM steps
AIP Logic functions combine LLM blocks with deterministic blocks. The Logic FAQ recommends using deterministic blocks (transform, execute and apply action blocks) whenever possible: they give more predictable outcomes and **do not use any tokens**.
## Where each choice lands
- An Execute function block can call an existing TypeScript or Python function that sums line items and applies the fee exactly.
- The Calculator tool gives accurate maths, but only when the LLM decides to call it, and every tool call is part of the block's token use.
- Temperature 0 is already the default in a Use LLM block; it reduces randomness but does not make a model's arithmetic correct.
Example: `refund = sum(lines) * 0.93` is computed first; the prompt receives `refund = 186.00` and only writes the explanation.
W: B=Deterministic computation first: code computes the exact amount on every run without tokens, and the LLM only drafts the text around a fixed number.
X: A=Calculator tool: the maths is accurate when used, but the model must still choose to call it and the tool calls add tokens to every run.
C=Few-shot examples: examples improve the pattern but cannot guarantee an exact figure, and they lengthen every prompt.
D=Temperature 0: it is already the default and only makes the output less random; a consistent answer can still be a wrong amount.
T: Put exact business arithmetic in deterministic blocks and keep the LLM for the language around it.

@ PLTR-AIE D1 T1.3 advanced troubleshooting
S: A published AIP Logic function that routes maintenance requests started sending most requests to the wrong team this morning. A colleague edited and republished it yesterday but cannot remember exactly what changed, and no one wrote release notes. Operations need correct routing again within the hour, and the change review board wants evidence of what caused the problem. What should the AI engineer do first?
A: Rebuild the function from scratch in a new Logic file, following the original design notes, and point every consumer at the new function
B: Raise the block's temperature and rerun yesterday's requests until the routing matches what operations expect from the function
C: Switch the Use LLM block to a larger model and republish, because a stronger model will route correctly even with the edited prompt
D: Compare yesterday's version with the last good one in version history, roll back to the good version, and record the difference
K: D
G: ## Versions are the first tool after a bad change
AIP Logic keeps saved versions. The Logic FAQ says you can see and **roll back** to previously saved versions in the version history sidebar, and the getting-started guide adds that version history can compare two versions to show which blocks were edited, added or removed.
## Restore, then learn
- Rolling back restores known-good behaviour quickly, which meets the one-hour window.
- The version comparison is the evidence the review board asks for.
- The failing requests then belong in the evaluation suite so the next edit is tested before it is published.
Example: the comparison shows that a routing rule was deleted from the prompt; the team rolls back, then adds ten affected requests as test cases.
W: D=Compare and roll back: the version comparison shows exactly what changed, and restoring the last good version fixes routing within the hour.
X: A=Rebuild from scratch: it takes far longer than an hour, risks new defects, and gives no evidence of what the edit broke.
B=Raise temperature: more randomness cannot restore a rule that was edited away, and rerunning until it looks right is not evidence.
C=Larger model: it changes cost and behaviour without fixing the edited prompt, and it hides rather than explains the root cause.
T: After a bad Logic change, compare versions and roll back first; redesign comes later, with evaluation.

@ PLTR-AIE D1 T1.3 advanced use-case
S: An AIP Logic function does three jobs in one Use LLM block: it extracts fields from a supplier email, classifies the request and drafts a reply. The Debugger shows the model skipping extraction steps on long emails, and results vary between runs. The team wants each step to be inspected and tested on its own, and wants to stay on the current model. Which change best addresses this?
A: Write a longer prompt that repeats every step twice and lists all three tasks in capital letters at the top of the block
B: Move the block to the largest available model so that it can follow all three steps inside the single block more reliably
C: Raise the block's temperature so that the model explores more reasoning paths and is less likely to skip extraction
D: Split the work into three chained Use LLM blocks, passing each block only the output that the next step needs to use
K: D
G: ## When to split a Logic block
The Logic FAQ lists reasons to split one large block into several: the LLM takes multiple steps and gives inconsistent results, the block approaches its context limit, or runs take too long.
## What splitting buys
- Each block gets its **own context window**, so the model only sees what is passed in rather than irrelevant intermediate text.
- Block outputs can be chained, so extraction feeds classification and classification feeds drafting.
- Each block's output can be checked in the Debugger and, with AIP Evals intermediate parameters, scored on its own.
Example: block 1 returns a struct of extracted fields; block 2 classifies using only that struct; block 3 drafts from the class and fields.
W: D=Three chained blocks: each step runs in its own context with only the input it needs, which makes it more consistent and testable on the current model.
X: A=Longer repeated prompt: it adds tokens to an already overloaded block and does not let the steps be inspected or tested separately.
B=Largest model: it breaks the stay-on-model constraint and still leaves three steps hidden in one block that cannot be tested on its own.
C=Higher temperature: more randomness increases run-to-run variation, which is already part of the problem.
T: Split multi-step Logic work into chained blocks when one block gives inconsistent results or nears its context limit.

The business wants agents to keep the speed of letting the chatbot prepare cancellations, but legal requires a human to approve each individual cancellation before it is written. @ PLTR-AIE D3 T3.1 advanced troubleshooting
S: An engineer configures Ontology context for an AIP Chatbot on a Maintenance Note object type with 2 million objects, and plans to retrieve the 10 notes most similar to each question. The configuration only offers to supply a fixed set of objects, not a semantic search. The answers must stay grounded in the most relevant notes, and the full note set is far too large for the context window. What is the cause and fix?

B: Semantic search is limited to document context, so the notes must be exported as documents and added through document context
C: The fixed set must be the whole object type first, and semantic ranking is then applied to it automatically after the first message

## How embeddings fit
- Embeddings are numerical representations of text that capture semantic meaning, used to compare and retrieve similar text.
- Without an embedding property there is nothing to compare a question against, so only the fixed-set option remains.
- Code can produce embeddings with a Palantir-provided embedding model, for example `createEmbeddings` in a function.

W: D=Missing vector embedding property: semantic search depends on one, and once it is added the chatbot can pull the 10 closest notes per question.

B=Document context only: Ontology context supports semantic search itself, so converting the notes into documents is unnecessary.

T: Ontology context semantic search needs a vector embedding property on the object type.

@ PLTR-AIE D3 T3.2 advanced troubleshooting
S: A product-support AIP Chatbot uses Ontology context with semantic search, K set to 2, over manual chunk objects that already print only their text and title. Evaluation shows that answers needing steps spread across several sections are often incomplete, while single-fact questions are fine. Token use per message has headroom, and the team must not lose citations. What change should the engineer evaluate first?
A: Replace Ontology context with the Object query tool so that the LLM can fetch as many chunks as it decides it needs on each turn
B: Raise K moderately and rerun the evaluation suite, checking that multi-section answers improve while token use stays acceptable
C: Switch to a fixed set of all manual chunks so that every possible section is available to the model with each new user message
D: Add an instruction telling the model to answer completely and to list every step it knows, even when only two chunks were retrieved
K: B
G: ## K trades recall against context size
Ontology context semantic search returns the **K most relevant** objects to the user query. When K is small, an answer that needs several chunks has its evidence cut off: a recall problem, not a precision problem.
## Making the change safely
- The context window includes the system prompt, conversation history and injected retrieval context, and exceeding it causes an error, so K should grow only as far as needed.
- Ontology context outputs citations; switching away from it can lose them.
- AIP Evals compares runs, so the K change is judged on the same test cases.
Example: K from 2 to 6 lifts multi-section completeness from 55 to 85 percent with average tokens still under budget.
W: B=Raise K and re-evaluate: more relevant chunks restore the missing steps, and the suite confirms the gain while tokens have headroom.
X: A=Object query tool: the LLM decides what to fetch, so retrieval stops being deterministic per message, and the built-in citations of Ontology context are lost.
C=Fixed set of all chunks: it maximises recall but floods the context window and invites the context-window error.
D=Answer completely instruction: the model cannot use steps it never received, so it may invent them instead.
T: Incomplete answers on multi-part questions point to recall; raise K carefully and confirm with evaluation.

B: Lower the Logic effect's parallelization to one so that the functions run one at a time and can no longer create the same task twice

D: Make the edit idempotent, for example by deriving the task's primary key from the invoice and trigger so a rerun cannot add a second

G: ## At-least-once execution
Automate effects follow **at-least-once** semantics, not exactly-once. In rare cases the same effect runs more than once for the same trigger event, and Automate cannot fully remove this because of its distributed design and its retries for transient failures.
## Designing for reruns
The effect-settings docs list the strategies:
- Idempotent operations, for example creating a resource with a consistent ID so it is created only once.
- Conditional checks that confirm whether the operation already happened.
- Data models that tolerate duplicate submissions.
Example: task key `FT-<invoiceId>-<dueDate>`; a second run finds the key already used and makes no new task.
W: D=Idempotent edit: a deterministic key makes a rerun produce the same single task, which removes duplicates while retries stay on.
X: A=Turn off retries: the team needs them for rate limits, and duplicates can still occur without them because delivery is at-least-once.
B=Parallelization of one: it reduces conflicts between different objects but does not stop the same effect from running twice.
C=Scheduled monitoring: it merges rapid edits into one trigger but does not change at-least-once delivery of each effect.
T: Automate is at-least-once, so make effects idempotent instead of hoping duplicates never happen.
