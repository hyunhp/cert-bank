@ PLTR-AIE D6 T6.3 applied troubleshooting
S: An automation must process objects in a strict order (older first) because each decision depends on the previous one. Per-object parallel execution is producing out-of-order decisions. What should change?
A: Increase the parallelism so that all objects are processed at once and the ordering problem is no longer visible to anyone
B: Stop relying on execution order: one function step sorts the objects oldest-first and decides them in sequence, or each run waits for the previous
C: Keep parallel execution and accept occasional out-of-order decisions, since the automation will eventually process every object and small ordering errors even out
D: Randomize the processing order so that no particular object is consistently disadvantaged by being processed later than another
K: B
G: ## Make ordering explicit
Foundry's Automate documentation notes that when multiple actions are configured, their execution order is not guaranteed. Parallel per-object runs therefore cannot be trusted to respect a business order.
## Design
- A single function (or Logic) step receives the set, sorts it oldest-first and decides each item in sequence, carrying forward the state each decision needs.
- Or chain the work so that each decision is triggered by the previous one completing.
- Test with objects arriving out of order.
Example: ten claims processed in one ordered step always produce the same decisions, whatever order the triggers fired in.
W: Ordering is enforced in logic the team controls, not assumed from the execution engine: dependent decisions are always made in the required sequence.
X: A=More parallelism: running even more objects at once makes out-of-order decisions more frequent, not less.
C=Accept errors: each decision depends on the previous one, so errors compound rather than even out.
D=Randomize: deliberately destroys the order the decisions depend on.
T: When decisions depend on order, enforce the order in your own logic rather than relying on automation execution order.
