# PLTR-AIE batch 26: Domain 1 round 4 (AIP Logic Development), 8 questions

@ PLTR-AIE D1 T1.1 applied use-case
S: A Logic function must return a decision of "approve", "reject" or "escalate" together with a short reason and a confidence between 0 and 1. The consuming automation branches on the decision. How should the output be declared?
A: A single string output such as "approve: looks fine (0.8)" that the automation parses with a regular expression on every run it processes
B: A struct output with an enumerated decision, a string reason and a numeric confidence, so the automation branches on a typed field
C: Three separate outputs on three different functions that the automation calls one after another and then combines
D: A free-text paragraph in which the model explains its decision in detail for a human to read before the automation acts
K: B
G: ## Typed struct outputs for branching consumers
AIP Logic outputs can be structured records with typed fields. The exam guide asks for typed inputs and outputs; a consumer that branches needs a field it can compare, not prose.
## Declaration
- `decision: enum(approve, reject, escalate)`, `reason: string`, `confidence: number`.
- The automation's condition reads `decision` directly; `confidence` can gate escalation.
Example: `{decision: escalate, reason: "amount above approver limit", confidence: 0.91}`; the automation routes to the approver queue.
W: An enumerated decision in a typed struct: the automation gets exactly the field it branches on, with no parsing.
X: A=String with regex: fragile parsing that breaks on any variation of wording or punctuation in the model's answer.
C=Three functions: triple the cost and no guarantee that the three outputs describe one consistent decision.
D=Paragraph for a human: the consumer is an automation; prose cannot drive a branch without a person in between.
T: Declare decision-type outputs as enumerations inside a typed struct so consumers branch without parsing.
V: AIP Logic, Automate

@ PLTR-AIE D1 T1.2 applied tradeoff
S: An engineer must decide whether a text-normalization step (trimming whitespace, standardizing date formats, mapping country codes) should be a Logic completion or deterministic code inside the function. What is the right call?
A: A Logic completion, because language models are good at text and will handle unusual cases that code would miss
B: Deterministic code (a code function or expression block), since the rules are explicit and must give identical results every run
C: A Logic completion with temperature set to zero, which makes the model as reliable as code for formatting tasks
D: A tool-using reasoning block that looks up each country code in a reference table before the model normalizes the rest of the text itself
K: B
G: ## Explicit rules are code
The exam guide's first decision area asks whether a task is a fixed rule or needs interpretation. Trimming, date formatting and code mapping are fixed rules with exact answers.
## Why code
- Deterministic and testable: the same input always produces the same output.
- Cheap and fast: no model call.
- Auditable: a rule is readable; a model's behaviour is not.
Example: "US" → "United States" via a lookup; "03/04/2026" normalized by a documented date rule, not by model guesswork.
W: Deterministic code: rules with exact answers belong in code, where they are reproducible, cheap and testable.
X: A=Model handles edge cases: the model also introduces variation and errors into cases that have one right answer.
C=Temperature zero: lower randomness, not guaranteed correctness; a model can still misformat a date consistently.
D=Reasoning block: an expensive loop for a lookup that a deterministic mapping performs in microseconds.
T: Put fixed transformation rules in deterministic code; use the model only where interpretation is needed.
V: AIP Logic, Code Repositories

@ PLTR-AIE D1 T1.3 applied troubleshooting
S: A Logic function started returning answers in a different language for some inputs after a model version change by the provider. The prompt was unchanged. How should the engineer respond?
A: Assume the provider will fix it and wait, since the prompt did not change and nothing on the function's side needs adjustment
B: Confirm the version change in traces, add a language instruction and output validation, extend the suite, manage the version
C: Switch the function to a completely different provider immediately, since any provider that changes models cannot be relied on
D: Add a post-processing translation step that translates every answer to the expected language regardless of what the model returned
K: B
G: ## Model drift from the provider side
The exam guide asks you to debug from traces and to monitor regressions across models. A provider's version change can alter behaviour under an unchanged prompt.
## Response
- Traces: confirm which model version served the bad outputs.
- Harden: explicit language instruction; validate the output language; reject or retry on mismatch.
- Evaluation: the failing inputs become regression cases; run the suite on the new version.
- Version control: pin a model version where the platform allows, or make version changes a deliberate, evaluated event.
Example: the suite gains 20 multilingual cases and the output validator catches any future language drift at once.
W: Confirm via traces, harden the prompt and output validation, extend the suite, manage the model version: the drift is fixed and future drift is detected.
X: A=Wait: users receive wrong-language answers meanwhile, and the provider may consider the new behaviour correct.
C=Switch provider blindly: an unevaluated model may regress elsewhere; the fix is control, not flight.
D=Translate everything: adds cost and translation artifacts to answers that were correct, without fixing the cause.
T: When the model changes under you, confirm with traces, harden instructions and validation, and manage model versions deliberately.
V: AIP Logic, AIP Observability, AIP Evals

@ PLTR-AIE D1 T1.1 applied use-case
S: A function must call a legacy calculation that exists only as a published TypeScript function in the Ontology. The result feeds the prompt. How is this integrated in AIP Logic?
A: Re-implement the calculation inside the prompt by describing the formula in words and asking the model to compute it
B: Add the published function as a tool in the Logic function and inject its typed result into the prompt as a variable
C: Export the legacy function's results to a spreadsheet each night and paste the relevant row into the function's input
D: Ask the model to guess the calculation's result from similar past outputs that are included as examples in the prompt
K: B
G: ## Functions as tools
AIP Logic can call published functions (TypeScript or Python) as tools. The exam guide lists tools among the blocks to configure.
## Pattern
- Tool: the legacy function with its typed inputs and outputs.
- Block: call it with values from the input object.
- Inject the result into the completion's prompt.
Example: the legacy pricing function returns 1,250.00; the prompt receives `{price}` and the model drafts the quote text around the exact figure.
W: The published function as a tool with its result injected: exact computation reused, model used only for the language.
X: A=Formula in prose: the model performs arithmetic unreliably, and the legacy logic is duplicated by hand.
C=Spreadsheet export: manual, stale and disconnected from the function's inputs.
D=Guess from examples: fabricated numbers where an exact function exists.
T: Reuse existing published functions as Logic tools instead of re-implementing or approximating them in prompts.
V: AIP Logic, Functions

@ PLTR-AIE D1 T1.3 applied use-case
S: A Logic function's evaluation suite passes, but an engineer wants to understand the single worst-scoring case before publishing. Which trace elements are most informative?
A: Only the final output, since the score is computed from it alone and nothing else in the run matters for understanding the failure
B: The resolved prompt, each tool call with its result, the raw model response and the parsed output, read in order to find the failing stage
C: The function's overall latency, since slow runs tend to be the wrong ones
D: The temperature setting, since variance explains most low-scoring cases
K: B
G: ## Reading a trace end to end
The exam guide asks you to debug traces and classify failures by stage. A trace contains the resolved prompt, tool calls and results, the raw response and the typed output; the failing stage is wherever the data first went wrong.
## Reading order
- Resolved prompt: was the injected data correct and complete?
- Tool results: did a lookup return the wrong object or nothing?
- Raw response: did the model misread, or was it fed bad context?
- Parsed output: did conversion lose or distort anything?
Example: the resolved prompt shows an empty `{customer_tier}` because the input object lacked the property; the error entered at injection, not at the model.
W: Prompt, tool calls, raw response, parsed output in order: this locates the stage that introduced the error rather than guessing.
X: A=Final output only: it shows that the answer is wrong, not why.
C=Latency: a run can be slow and correct or fast and wrong; duration says nothing about where the error entered.
D=Temperature: a parameter, not an explanation for a specific case.
T: Debug a failing case by walking the trace from resolved prompt to parsed output.
V: AIP Logic, AIP Observability

@ PLTR-AIE D1 T1.2 applied troubleshooting
S: A Logic function applies an edit that sets `owner` on a Case object. In production, some cases were assigned to users who had left the company. What safeguard belongs in the function?
A: A prompt instruction asking the model to choose only owners who are current employees, with a list of departed employees to avoid
B: A lookup that checks the proposed owner against active users before the edit, routing invalid ones to review
C: A weekly report listing cases assigned to inactive users for manual correction
D: A larger model that is less likely to suggest former employees
K: B
G: ## Validate before edits
The exam guide asks for safe Ontology edits: the edit should depend on verified state, not on the model's belief. Whether a user is active is a fact in the Ontology.
## Design
- The model proposes an owner (typed reference).
- A lookup tool checks `is_active`; a conditional routes invalid proposals to a default queue or review.
- Only validated assignments reach the edit block.
Example: the model suggests a former employee; validation fails; the case goes to the team queue with a note.
W: Lookup-based validation before the edit: the Ontology's facts decide, and no case is assigned to an inactive user.
X: A=Prompt instruction: the model does not know who is current; instructions cannot replace a lookup.
C=Weekly report: a week of misassigned cases before correction.
D=Larger model: a stronger model still has no knowledge of who left the company; it guesses more fluently.
T: Validate model-proposed references against Ontology state before applying edits.
V: AIP Logic, Ontology

@ PLTR-AIE D1 T1.1 applied comparison
S: Which block arrangement in AIP Logic best handles "if the input document is longer than 20 pages, summarize it first; otherwise answer the question directly"?
A: A single completion that receives the whole document and is told to summarize it first if it seems long
B: A conditional on a measured page or token count that routes long documents through a summarization completion before answering
C: Two separate functions, one for long and one for short documents, with every caller expected to measure the length and pick the right one
D: A loop that summarizes every document regardless of length to keep the flow simple
K: B
G: ## Deterministic routing in Logic
The exam guide asks you to use conditionals for explicit rules. Page or token count is measurable; routing on it is deterministic and testable.
## Arrangement
- Input: document plus computed length (from a code block or property).
- Conditional: length > threshold → summarize block → answer block; else → answer block.
- Evaluation: cases on both sides of the threshold.
Example: a 45-page contract is summarized to 2 pages and then answered; a 3-page memo is answered directly in one call.
W: Conditional on a measured length: the rule is applied exactly and the expensive step runs only when needed.
X: A=Model decides "if it seems long": the rule becomes a judgement and the long document is already in the prompt.
C=Two functions: pushes the measurement and routing onto every caller.
D=Summarize everything: wastes a call on short documents and may lose detail the direct answer needed.
T: Implement length- or value-based routing with a conditional on a measured input, not a model judgement.
V: AIP Logic

@ PLTR-AIE D1 T1.3 advanced tradeoff
S: Two engineers disagree about a Logic function's prompt: one wants a long prompt with twenty rules and examples; the other wants a short prompt. The function's suite scores 92% with the long prompt and 91% with the short one, at half the tokens. The function runs 50,000 times a day. Which should be published?
A: The long prompt, because a higher evaluation score always wins regardless of the token cost or the daily volume of calls
B: The short prompt, since one point is within variance and the saving is substantial; confirm with repeated runs first
C: Neither, until a prompt reaches 100% on the suite
D: Alternate daily between the two to average the cost and the score
K: B
G: ## Prompt length as a cost lever
The exam guide asks you to optimize prompts and context without sacrificing quality, and to distinguish signal from variance. One point on a suite is usually noise; 50,000 daily calls at half the tokens is real money.
## Decision
- Repeat runs: is the 92 vs 91 gap stable?
- Per-case: does the long prompt win on any critical category?
- If no material difference, publish the short prompt and record the comparison.
Example: five runs each give 90-93% for both; the short prompt ships and the monthly cost drops by 45%.
W: The short prompt after confirming the gap is noise: equal quality at half the cost is the better engineering choice.
X: A=Score always wins: ignores cost and variance; one point is not a difference.
C=100% or nothing: no language-model function reaches a perfect score on a realistic suite; it is not a decision rule.
D=Alternate: users and the suite would see two behaviours on alternate days, with no benefit over simply choosing the better one.
T: When prompt variants are statistically equivalent, choose the cheaper one and record the evidence.
V: AIP Logic, AIP Evals
