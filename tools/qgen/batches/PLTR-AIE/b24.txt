@ PLTR-AIE D7 T7.1 applied tradeoff
S: A workflow needs to process documents in Japanese, Korean and English with equal quality. The reference sheet lists one model with strong multilingual capability at medium cost and another with top English quality but weak support for Asian languages at lower cost. Which should be chosen and how verified?
A: The cheaper English-focused model, since English is the most common language in the corpus and the cost saving is significant over a year
B: The multilingual model, verified with a language-stratified evaluation suite so quality per language is measured against the requirement
C: Both models, with the English one used for all documents and the multilingual one used only when the English model's output looks wrong to a reviewer
D: Whichever model the provider recommends for document processing, since providers understand their own models' strengths better than any customer
K: B
G: ## Capability must match the task's languages
The exam guide asks you to select models from reference characteristics against task requirements. "Equal quality in three languages" is a capability requirement that the cheaper model does not meet.
## Verification
- Stratified evaluation: cases per language with per-language metrics.
- Compare each language's score with the threshold; the model must pass all three.
- Cost is compared only among models that meet the requirement.
Example: the multilingual model scores 92/90/91 across the three; the English model scores 94/71/68, failing two.
W: The multilingual model with per-language evaluation: it meets the stated requirement and the verification proves it.
X: A=Cheaper model: fails the Japanese and Korean requirement; cost does not override capability.
C=Reviewer-triggered fallback: manual, inconsistent, and the weak model still produces first drafts in two languages.
D=Provider recommendation: generic advice is not an evaluation on this corpus.
T: Choose the model that meets every language's requirement, verified with a language-stratified suite.

@ PLTR-AIE D7 T7.3 applied use-case
S: An engineer wants to compare how two versions of a workflow behave on the same production request. Which observability capability makes this straightforward?
A: Reading both versions' prompts side by side, since the prompt is the main difference between the two versions and fully determines the behaviour
B: Session and distributed traces recording each stage's inputs, outputs, tool calls and timing, so the two runs compare step by step
C: The monthly cost report, which shows which version consumed more tokens and is therefore the more thorough one
D: A user survey asking which version produced the more helpful answer for the request in question
K: B
G: ## Traces as the unit of comparison
The exam guide lists session traces and distributed traces among observability evidence. A trace is the complete record of a run; two traces on the same input show exactly where behaviour diverged.
## Comparison
- Same input through both versions (or replay).
- Compare retrieved context, tool calls, intermediate outputs, final answer, latency and tokens.
- Attribute the difference to a stage.
Example: version 8 retrieved two extra chunks that changed the answer; the trace shows it in the retrieval stage.
W: Per-stage traces: they record everything that happened in each run, so a difference in answers can be traced to the exact stage where the two versions diverged.
X: A=Prompts side by side: behaviour depends on retrieval, tools and the model, not just prompt text.
C=Cost report: token totals say nothing about where behaviour differed.
D=Survey: a single opinion about which answer felt better says nothing about why the versions behaved differently.
T: Compare workflow versions through their traces, stage by stage, on the same inputs.
V: AIP Observability

@ PLTR-AIE D7 T7.4 applied troubleshooting
S: An agent's average latency is acceptable, but p99 latency is 30 seconds and those slow requests cluster around questions that trigger four or more tool calls. What is the best improvement?
A: Cap tool calls at one per conversation turn so that no request can take more than a single call's time regardless of complexity
B: Analyze slow traces: parallelize independent tool calls, cut redundant calls, cache lookups, and set a per-turn budget
C: Switch to a faster model for all requests, since the model is the only part of the pipeline the team controls directly
D: Remove the slowest tool from the agent entirely, since any tool that contributes to p99 latency is not worth keeping
K: B
G: ## Tail latency
Averages hide the tail; p99 is what some users experience. The exam guide asks you to profile traces and apply targeted optimizations.
## Levers
- Parallelize tool calls that do not depend on each other.
- Reduce call count: clearer tool descriptions and instructions on when a lookup is needed.
- Cache: repeated lookups within a session.
- Budget: after N calls or T seconds, answer with what is available and offer to continue.
Example: p99 falls from 30 to 9 seconds after parallelizing two lookups and caching the customer record for the session.
W: Trace-driven parallelization, call reduction, caching and a turn budget: targeted at the exact cause of the tail.
X: A=One call per turn: questions that genuinely need several lookups can no longer be answered; the cap trades correctness for latency.
C=Faster model: the traces show the time is spent in four sequential tool calls, not in model generation; a faster model barely moves p99.
D=Remove a tool: the tool may be essential; the problem is how many calls and how they are sequenced.
T: Fix tail latency by analyzing slow traces and restructuring tool calls, not by blanket restrictions.

@ PLTR-AIE D7 T7.2 applied use-case
S: A team wants to evaluate a new third-party model that is not yet in the platform's catalog before deciding whether to request its enablement. What is the appropriate path?
A: Call the model's public API directly from a Workshop widget using a developer's personal key so users can try it on real data right away
B: Request governed enablement in a test scope, run the suite on non-sensitive data, and decide with the results and a policy review
C: Ask the vendor for benchmark numbers and decide based on those, since vendor benchmarks are standardized and comparable across providers
D: Use the model only through an external notebook outside the platform, copying production data into it for a realistic test
K: B
G: ## Governed evaluation of new models
The exam guide lists enrollment and capability permissions among controls. Evaluating an outside model is legitimate; doing it outside governance is not.
## Path
- Administrator-controlled enablement in a test scope.
- Evaluation on non-sensitive data; policy review (residency, terms, cost).
- Decision recorded; production enablement if justified.
Example: the model scores 4 points higher on the suite and meets residency rules; it is enabled for the workflow with a cost cap.
W: Governed test enablement with evaluation and policy review: an informed decision without bypassing controls.
X: A=Personal key in Workshop: bypasses governance and exposes real data.
C=Vendor benchmarks: not the application's task; evaluation must be on the suite.
D=External notebook with production data: a data-protection violation.
T: Evaluate new models through governed test scopes, never through personal keys or exported data.

@ PLTR-AIE D7 T7.3 applied troubleshooting
S: Cost alerts show an AI workflow spending far more at 02:00-03:00 than at any other time, though user traffic is lowest then. What should the engineer look for?
A: A pricing change by the provider that applies only at night, which would explain why the same traffic costs more during those hours
B: Automated runs in that window: a nightly automation, backfill or retry loop, visible in execution history and telemetry by caller
C: Users in other time zones, since 02:00 locally is daytime elsewhere and their requests are naturally longer and more expensive
D: Nothing unusual, since AI costs fluctuate randomly and a nightly spike is within normal variation for any workflow
K: B
G: ## Attributing cost by caller and time
The exam guide lists token telemetry and cost signals; attributing them by caller reveals non-user consumers.
## Investigation
- Execution history filtered to the window: which automation or job ran?
- Token telemetry by caller: a backfill or a retry loop stands out.
- Decide: expected (a scheduled batch, to be budgeted) or a defect (retries without backoff, a loop).
Example: a nightly enrichment reprocesses all objects because its cache key omitted the prompt version; fixing the key cuts the window's cost by 95%.
W: Scheduled or automated callers in that window: the pattern (high cost, no users) points to machine traffic, which telemetry attributes.
X: A=Night pricing: providers do not price by hour; the cause is volume.
C=Other time zones: user traffic is measured as lowest; the spike is not users.
D=Random: a spike that recurs at the same hour every night is a pattern with a cause, not random fluctuation to be ignored.
T: Attribute cost spikes by caller and time; non-user windows point to automations and backfills.

@ PLTR-AIE D7 T7.1 applied comparison
S: A workflow must run in a jurisdiction that requires data to stay in-region. The reference sheet shows the best-performing model hosted out of region, and an in-region model with slightly lower scores. Which choice is correct?
A: The out-of-region model, since quality is the primary selection criterion and the residency rule can be satisfied by encrypting the data in transit
B: The in-region model, since geography is a hard constraint; verify it meets the quality threshold on the suite and document the decision
C: The out-of-region model with a prompt instruction telling it not to store the data, which satisfies the regulation's intent
D: Neither; the workflow should be cancelled because no single model is both the best performing and hosted in the required region
K: B
G: ## Hard constraints first
The exam guide includes geography among selection criteria and georestrictions among controls. A residency rule is not a preference to trade against quality; it narrows the candidate set.
## Process
- Filter candidates by hard constraints (region, terms).
- Among the remainder, choose by evaluation, latency and cost.
- If no candidate meets the quality bar, that is a different conversation (BYOM, prompt improvements), not a reason to break the rule.
Example: the in-region model scores 2 points lower but passes the threshold; it is selected and the choice recorded.
W: The in-region model, verified against the quality threshold: constraints filter, then quality decides.
X: A=Encrypt and go: transit encryption does not change where the data is processed.
C=Prompt promise: the data has already left the region when the model reads the prompt.
D=Cancel: a compliant model exists; "best performing" is not the requirement.
T: Apply residency and policy constraints before comparing models on quality.
V: model catalog

@ PLTR-AIE D7 T7.4 applied use-case
S: An AI workflow's token usage per request has crept up 60% over three months without any deliberate change. Which observability practice would have caught this earlier, and what is the fix?
A: Reviewing the monthly invoice line by line, which would have shown the gradual increase early and prompted the team to shorten the system prompt
B: Trending tokens per request with a drift alert, then diagnosing with traces which component grew and bounding it
C: Capping the model's maximum output tokens, which limits the cost of every request regardless of what caused the growth
D: Switching to a cheaper model each quarter so that gradual growth in tokens is offset by a lower price per token
K: B
G: ## Trend monitoring
The exam guide asks for monitoring of real behaviour, regressions and cost signals. Slow drift is invisible in point-in-time checks and in blended invoices; a per-request trend with an alert is the instrument.
## Diagnosis and fix
- Traces across the period: which part of the prompt grew? Retrieved chunks (corpus growth), conversation history (no truncation), or an ever-expanding system prompt.
- Bound it: top-k and thresholds, history windows or summaries, prompt hygiene.
Example: conversation history was never truncated; a sliding window with summarization returns tokens per request to baseline.
W: Trended per-request token metric with drift alerts, then trace-based bounding of the growing component: detection and cure.
X: A=Invoice: too coarse and too late; it cannot say which component grew.
C=Output cap: input tokens are what grew; the cap does nothing.
D=Cheaper model each quarter: masks the drift with quality loss.
T: Trend tokens per request and alert on drift; bound whatever component is growing.

@ PLTR-AIE D7 T7.2 advanced tradeoff
S: A production workflow uses a provider model that the provider announces will be deprecated in 60 days. What should the AI engineer do?
A: Wait until the deprecation date and switch to whatever replacement the provider offers at that time, since there is no way to prepare in advance
B: Select a replacement now, run the evaluation suite, adjust prompts, roll it out as a versioned change with rollback, and make the model change visible
C: Pin the deprecated model indefinitely by contract with the provider so that nothing in the workflow has to change
D: Switch immediately to a different provider's model without evaluation, since any model is better than one that is about to be deprecated
K: B
G: ## Planned model transitions
Model lifecycles are an operational reality. The exam guide covers model selection, multi-provider resilience and versioned, observable change.
## Plan
- Candidate selection against requirements; evaluation suite run; prompt adjustments (models differ in formatting and instruction following).
- Versioned rollout with monitoring and rollback.
- Observability: model id on every request so the transition is auditable.
- Consider a fallback on another provider while at it.
Example: the replacement passes the suite after two prompt tweaks; rollout happens in week three with no user-visible change.
W: Evaluated, versioned, observable migration ahead of the deadline: the transition is controlled rather than forced.
X: A=Wait: a forced switch with no evaluation on the deadline day.
C=Pin indefinitely: usually impossible and leaves the workflow on unsupported infrastructure.
D=Switch blind: an unevaluated model can regress quality or safety.
T: Treat model deprecations as planned migrations with evaluation, versioning and observability.
