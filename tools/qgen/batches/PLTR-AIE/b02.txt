# PLTR-AIE batch 02: Domain 1 (AIP Logic Development), 8 questions

@ PLTR-AIE D1 T1.1 applied troubleshooting
S: An AIP Logic function reads a support ticket and is expected to return a priority (low, medium, high) and a confidence between 0 and 1. The function's output is a free-text string, and the automation that consumes it fails about one run in ten because the text is formatted differently. What is the best fix?
A: Lower the temperature so that the model produces the same sentence format every time, and keep parsing the text in the automation as it does today
B: Define a typed output, an enumerated priority plus a number, so the answer is validated into that structure before it leaves the function
C: Add a regular expression in the automation that searches the text for the three priority words and the first decimal number it can find
D: Ask the model in the prompt to write its answer inside a JSON block, and let the automation strip the surrounding explanation before it parses it
K: B
G: ## Typed inputs and outputs in AIP Logic
AIP Logic functions declare their inputs and outputs with types: strings, numbers, booleans, enumerations, lists, object references and structs. The output type is part of the function's contract: whatever consumes the function receives that shape, not whatever the model happened to write.
## Why this matters for automations
An automation or a Workshop app cannot negotiate with prose. When the output is typed, a priority that is not one of the three allowed values fails inside the function, where it can be retried or surfaced, rather than breaking the consumer later.
- Enumerated output: the priority can only be low, medium or high.
- Numeric output: the confidence is a number, not "about 80%".
- The consumer reads fields, so a wording change in the model's reasoning cannot break it.
Example: output `{priority: high, confidence: 0.82}` works for every consumer; the sentence "I would rate this as High (82%)" works only until the model phrases it differently.
W: Typed structured output: the contract moves from "parse whatever the model says" to "the function returns this structure", which removes the format drift that causes the failures.
X: A=Lower temperature: less randomness makes the format more consistent but does not guarantee it; the consumer still parses prose and still breaks on any variation.
C=Regular expression: pattern matching on free text is brittle; a sentence such as "not high priority, confidence low" produces the wrong priority and the wrong number.
D=JSON in the prompt: asking for JSON in prose still leaves the model free to add text or malformed JSON, and the consumer still carries the parsing and validation burden.
T: Give an AIP Logic function a typed output; consumers should receive a structure, not text to parse.

@ PLTR-AIE D1 T1.1 applied tradeoff
S: An AIP Logic function summarizes a meeting transcript that arrives as a typed string input. It was built with a tool-using reasoning block connected to five Ontology search tools. Runs take over a minute and the model sometimes calls irrelevant tools and includes unrelated objects in the summary. What should the engineer change?
A: Increase the number of reasoning iterations allowed, so the model has enough steps to finish its tool calls and still produce the summary
B: Add two more tools that return the attendees and the project, so the model has every object it could possibly need for the summary
C: Replace the reasoning block with a single completion that receives the transcript and no tools, since the task needs no external data
D: Switch to a larger model, because a stronger model will choose the right tools and ignore the objects that are not relevant to the transcript
K: C
G: ## Single completion versus tool-using reasoning
AIP Logic offers two ways to use the model:
- A **single completion** sends one prompt with the injected inputs and takes the answer. It is fast, cheap and predictable.
- A **tool-using reasoning** block lets the model decide, over several steps, which tools to call (Ontology queries, functions, other Logic) before answering. It is for tasks where the needed information is not in the inputs.
## Matching the block to the task
The exam guide asks you to choose single completion or tool-using reasoning appropriately. Summarizing text that is already an input needs no lookup. Giving the model tools anyway adds latency per step, cost per call, and a new failure mode: calling tools it does not need and pulling unrelated data into the answer.
Example: "summarize this transcript" is a completion; "summarize this transcript and link each action item to the owner's open tasks" would justify tools.
W: Single completion without tools: the transcript is already an input, so the model has everything it needs. Removing the tools removes the slow steps and the irrelevant lookups at the same time.
X: A=More iterations: this lets the model make even more tool calls, so runs get longer and the chance of unrelated data in the summary rises.
B=More tools: the function would gain more ways to fetch data the task does not need; the problem is that tools are present at all, not that two are missing.
D=Larger model: a stronger model may pick tools more sensibly but is slower and dearer, and it still cannot make an unnecessary lookup useful.
T: Use tool-using reasoning only when the answer needs data that is not in the inputs; otherwise a single completion is faster, cheaper and more predictable.

@ PLTR-AIE D1 T1.1 applied use-case
S: An AIP Logic function drafts a reply to an expense claim. Claims above 10,000 must be answered with a formal escalation template, all others with a short approval note. The team currently puts both templates in one prompt and asks the model to pick the right one, and about 5% of large claims get the short note. How should the function be structured?
A: Keep one prompt but move the threshold rule to the top of the system prompt in capital letters, so that the model gives it priority over everything else
B: Use a conditional block on the typed amount input to route claims above 10,000 to the escalation prompt and the rest to the approval prompt
C: Run the prompt twice and keep the answer that mentions the correct amount, since two attempts make it unlikely that both pick the wrong template
D: Add a tool that returns the threshold from a configuration object, so the model can look up the rule before it chooses the template
K: B
G: ## Deterministic logic or AI
The exam guide's first decision area is whether a task is a fixed, reproducible rule or needs interpretation. "Amount greater than 10,000" is a rule. Letting a language model apply it means accepting a small error rate on something that never needed judgement.
## Blocks in AIP Logic
A Logic function is a sequence of blocks: completions, tool calls, conditionals, loops and edits. A **conditional** branches on a typed input or on an earlier block's output. Here the amount is a typed number, so the branch is evaluated exactly, and the model only does the part that needs language: writing the note in the chosen template.
This also makes the function easier to test: each branch can be checked with a claim on either side of the threshold.
W: Conditional block on the amount: the threshold becomes deterministic code inside the function, and the model is only asked to write text within the template that the branch selected.
X: A=Emphasize the rule in the prompt: the rule stays a request to the model, so it can still be missed; prompt emphasis reduces errors but does not remove them.
C=Run twice: this doubles cost and latency and still relies on the model to apply the rule; two guesses are not a guarantee.
D=Threshold tool: fetching the rule from a tool makes it configurable, but the comparison is still performed by the model rather than by code.
T: Put fixed rules in conditional blocks; reserve the model for the parts that need language or interpretation.
V: AIP Logic

@ PLTR-AIE D1 T1.2 advanced troubleshooting
S: An AIP Logic function reads carrier emails and sets an order's status to "Shipped" through an Ontology edit. Occasionally a carrier email arrives for an order that was cancelled days earlier, and the function overwrites "Cancelled" with "Shipped", which confuses customer service. Which change best fixes this?
A: Add a condition that reads the current status and applies the edit only for an allowed transition to "Shipped", flagging the order for review otherwise
B: Tell the model in the task prompt that cancelled orders must never be marked as shipped, so it decides for each email whether the status change is appropriate
C: Change the edit so that it appends "Shipped" to a notes property instead of replacing the status, so no existing status is ever overwritten by the function
D: Run the function only once a day in a batch, so that a cancelled order has time to settle before any carrier email about it can be processed
K: A
G: ## Applying Ontology edits safely
An Ontology edit from a Logic function changes real objects that people and automations rely on. The exam guide asks you to apply Ontology edits safely: an edit should depend on the object's current state, not only on the incoming evidence.
## Allowed transitions
Order statuses usually form a state machine: New → Shipped → Delivered, with Cancelled as a terminal state. "Cancelled → Shipped" is not a valid transition no matter what an email says. A conditional block can read the current status before the edit block runs:
- allowed transition: apply the edit;
- not allowed: skip the edit and flag the order so a person can check whether the cancellation or the shipment is wrong.
Example: an email for order 1182 (status Cancelled) is logged as "shipment reported for cancelled order", not written as Shipped.
W: Precondition on current status: the edit is only applied for valid transitions and conflicting evidence is routed to review, which is exactly the "edit safely" pattern.
X: B=Prompt instruction: the model does not see the current status unless the function provides it, and a prompt rule can be misapplied; the guard belongs in logic that reads the object.
C=Append to notes: this avoids the overwrite but stops the function from doing its job for the normal case, so every shipment would need a manual status update.
D=Daily batch: a cancellation can still happen after the daily run, and delaying every status update by a day harms the normal case without fixing the conflict.
T: Before an Ontology edit, read the object's current state and only apply transitions that are allowed; send conflicts to review.
V: AIP Logic, Ontology

@ PLTR-AIE D1 T1.2 applied comparison
S: A team needs a function that converts invoice amounts between currencies using the day's exchange rate, applies the finance team's exact rounding rules and runs over two million invoices every night. Which implementation fits?
A: An AIP Logic function with the rounding rules written in the prompt and the temperature set to zero, so the model produces the same arithmetic result on every run
B: Code in a repository, as a transform or function, because the task is fully deterministic, needs exact arithmetic and runs as a large scheduled batch
C: An AIP agent with a calculator tool, so that the model can perform each conversion step by step and explain its rounding decisions when asked
D: An AIP Logic function with a loop block over the invoices, so that each invoice is converted by its own completion within one nightly run
K: B
G: ## When code is more suitable than AIP Logic
The exam guide asks you to understand when code is more suitable than AIP Logic. AIP Logic is for tasks that need language understanding or flexible interpretation. Three signals point to code here:
- **Determinism**: currency conversion with fixed rounding rules has exactly one correct answer per input.
- **Scale**: two million rows per night is a pipeline-scale batch, where per-row model calls would be slow and expensive.
- **Scheduling and control**: a nightly job with rate limits and programmatic control is what Code Repositories are for.
A language model is not a calculator: even at temperature zero it can produce wrong arithmetic, and it cannot be audited the way a rounding function can.
W: Code in a repository: deterministic arithmetic at batch scale on a schedule is the textbook case for a transform or function, giving exact results, testability and low cost.
X: A=Logic with temperature zero: zero temperature makes output more repeatable, not correct; model arithmetic and rounding errors remain, and two million completions a night are costly.
C=Agent with calculator: an agent adds reasoning, latency and cost to a task with no judgement in it, and the calculator tool does the only part that matters.
D=Loop block: looping two million completions through a Logic function is slow and expensive and still trusts the model with exact arithmetic.
T: Deterministic, large-scale, scheduled computation belongs in code; AIP Logic is for tasks that need language or interpretation.
V: Code Repositories, AIP Logic

@ PLTR-AIE D1 T1.3 applied troubleshooting
S: An AIP Logic function classifies product reviews into one of six categories. Running the same review several times returns different categories, and the evaluation suite's score moves by several points between runs with no change to the function. Which adjustment addresses this first?
A: Lower the temperature and define the output as an enumeration of the six categories, so the model varies less and can only return a valid category
B: Raise the maximum output tokens so the model can explain its reasoning fully before it states the category, which makes the choice more deliberate
C: Add a loop block that runs the classification three times and returns the last answer, since the final attempt is usually the most refined one
D: Increase the size of the retrieved context so that the model sees similar reviews from the past and copies their categories when it is unsure
K: A
G: ## Tuning parameters
AIP Logic exposes model parameters such as temperature and maximum output tokens. **Temperature** controls randomness: higher values let the model pick less likely tokens, which helps creative writing and hurts classification. A classifier should be as deterministic as possible, so a low temperature is the first setting to change.
## Constrain the output type
A typed enumerated output removes a second source of variation: the model cannot answer "mostly shipping, maybe billing" when the contract is one of six values. Together, low temperature and an enumeration make repeated runs far more consistent.
After tuning, rerun the evaluation suite several times; the remaining spread tells you how much variance is still inherent to the model, which matters when you judge future changes.
W: Low temperature plus enumerated output: the two settings target the two causes of run-to-run variation, randomness in generation and freedom in the output format.
X: B=More output tokens: longer explanations do not make the final label more stable; they add cost and give the model more room to wander.
C=Three runs, keep the last: the last answer is no more reliable than the first, and three completions triple the cost without reducing randomness.
D=More retrieved context: a classifier of review text needs no retrieval; extra context adds noise and makes behaviour depend on which neighbours were returned.
T: For classification, lower the temperature and constrain the output to the allowed values before changing anything else.
V: AIP Logic, AIP Evals

@ PLTR-AIE D1 T1.3 applied use-case
S: An AIP Logic function is called by a Workshop app and two automations. The team wants to add a new output field and reword the system prompt. The change must not disturb current consumers while it is being evaluated. What is the right release process?
A: Edit the current published version directly, because consumers already reference the function by name and will receive the improvement automatically
B: Publish the change as a new version, evaluate it, then move each consumer over deliberately while the previous version stays available
C: Create a second function with a different name for the new behaviour and delete the old function once the new one has been published
D: Make the change in the editor without publishing and point the automations at the draft, since drafts are the right place to test with real consumers
K: B
G: ## Versions in AIP Logic
A Logic function is edited as a draft and released by **publishing** a version. Consumers (Workshop, Automate, other functions) use a published version, so editing and publishing are separate steps. The exam guide asks engineers to publish versions and preserve behaviour for existing consumers.
## A safe release
- Make the change in the draft and run the evaluation suite against it.
- Publish it as a new version; the earlier version keeps serving current consumers.
- Update the consumers one by one, checking each; if something breaks, that consumer goes back to the earlier version.
This is the same discipline as software releases: new behaviour ships behind a version boundary, and rollback is a configuration change, not an emergency edit.
Example: the new output field is added in version 4; the Workshop app moves first, the two automations the following week after their owners confirm the new field.
W: New version, evaluate, migrate consumers: the previous version keeps working while the change is tested, and each consumer is switched only when its owner is ready.
X: A=Edit in place: every consumer would receive untested behaviour at once, and there is no version to fall back to if the reworded prompt changes results.
C=New function and delete the old: this duplicates the function's identity, breaks every reference to the old name on deletion and loses the version history.
D=Point consumers at a draft: drafts change while being edited; consumers would follow every keystroke, which is the opposite of preserving behaviour.
T: Publish changes as a new version, evaluate, then migrate consumers deliberately while the old version stays available.
V: AIP Logic, Workshop, Automate

@ PLTR-AIE D1 T1.1 applied use-case
S: An AIP Logic function receives a purchase order as an object with a list of line items, between 1 and 400 per order. For each line item it must produce a short risk note. The first design pasted every line item into one prompt and failed on large orders. How should the function handle the list?
A: Use a loop block over the typed list of line items, running the risk-note completion once per item and collecting a list output
B: Split large orders into several smaller orders before they reach the function, so no single prompt ever has to contain more than a few line items
C: Keep one prompt but raise the model's context limit to the maximum available, so that even the largest orders fit into a single completion
D: Call the function recursively on the second half of the list whenever the first attempt fails, until every order has been processed successfully
K: A
G: ## Loops over typed lists
AIP Logic blocks include **loops**, which run a set of blocks once for each element of a list input or of an earlier block's output. Each iteration gets its own completion with just that element injected into the prompt, and the results are collected.
## Why one giant prompt fails
Putting hundreds of items into one prompt hits token limits, raises cost, and makes quality drop as the model's attention is spread across the whole list. Per-item completions are bounded in size regardless of the order, and a single bad item does not spoil the notes for the others.
Example: an order with 380 lines becomes 380 short completions, each with the same template and one item injected, returning a list of 380 notes in the same order.
W: Loop block per item: it fits the data shape (a list of independent items), keeps every prompt small and produces a typed list output the consumer can use.
X: B=Split orders upstream: changing the data model to work around a function design corrupts the order's identity and still does not bound the prompt for a mid-sized order.
C=Maximum context: larger context raises cost and latency and only postpones the limit; quality on very long prompts still degrades.
D=Recursion on failure: retrying halves after failures is unpredictable, wastes the failed attempts and is not a supported design for a Logic function.
T: Process a list of independent items with a loop block, one bounded completion per item.
V: AIP Logic
