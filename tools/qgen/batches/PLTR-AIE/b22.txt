@ PLTR-AIE D5 T5.1 applied use-case
S: A team is defining metrics for a retrieval-grounded assistant. Which set gives a complete picture of quality for release decisions?
A: Answer correctness alone, measured against reference answers written by the team, since a correct answer is the only thing that matters to users
B: Correctness, groundedness, retrieval hit rate, refusal behaviour, latency and cost, each reported separately
C: User satisfaction from a survey sent after the release, since real users are the only valid judges of an assistant's quality
D: The number of evaluation cases that run without errors, since a case that throws an error cannot be scored and signals a broken assistant
K: B
G: ## A metric per failure mode
The exam guide lists correctness, groundedness, retrieval quality, refusal behaviour, tool use, safety, latency and cost as things to measure. Each catches a different way to fail: an answer can be correct but ungrounded, or grounded but slow, or right but given when it should have refused.
## Reporting
- Separate numbers, not a blended score, so a regression is attributable.
- Thresholds per metric for release.
Example: a release candidate improves correctness by 2 points but drops groundedness by 6 and doubles cost; separate metrics make that trade visible.
W: Correctness, groundedness, retrieval, refusal, latency and cost reported separately: the full picture the guide prescribes.
X: A=Correctness only: unsupported, slow or inappropriate answers would pass.
C=Post-release survey: too late for a release decision and too coarse to locate problems.
D=Cases without errors: execution success says nothing about answer quality.
T: Evaluate across correctness, groundedness, retrieval, refusal, latency and cost, each separately.

@ PLTR-AIE D5 T5.2 applied use-case
S: An evaluation suite for a document-processing function is built entirely from clean, well-formatted sample documents. Which additions make it representative?
A: More clean documents of the same kind, since a larger suite always produces a more reliable accuracy estimate for the function
B: Messy real cases: scanned pages, missing fields, unusual layouts, other languages, size extremes, and known-tricky production examples
C: Documents from a different domain entirely, since testing on unrelated material proves that the function generalizes beyond its training
D: Synthetic documents generated by the same model that performs the extraction, since the model knows what inputs it handles well
K: B
G: ## Representativeness
The exam guide asks for representative suites that include edge cases. A suite of clean samples overestimates production accuracy and misses the inputs that fail.
## What to add
- Edge formats: scans, rotation, low resolution.
- Missing or malformed fields.
- Layout and language variety.
- Size extremes.
- Production failures from feedback, with corrected expected outputs.
Example: adding 60 production-style documents drops the measured accuracy from 98% to 89%, which is the real number to improve.
W: Messy, varied, production-derived cases: these make the suite predict real performance and expose the failures that matter.
X: A=More of the same: a bigger clean suite is still unrepresentative.
C=Unrelated domain: tests the wrong thing; production inputs are in-domain but messy.
D=Model-generated inputs: biased toward what the model handles; the hard cases come from reality.
T: Make evaluation suites representative by adding real-world edge cases, not more clean samples.

@ PLTR-AIE D5 T5.3 applied troubleshooting
S: Two engineers get different evaluation scores for the same function version on the same day: 90% and 84%. What should be checked before concluding anything?
A: Whether suite version, grader, model configuration or parameters differ between them, and how much the suite varies run to run
B: Which engineer is more experienced, since the more experienced engineer's measurement should be treated as the correct one
C: Whether the function was changed between the two runs, since nothing else could explain different scores on the same version
D: Nothing; the difference is small enough to ignore, and the team should proceed with the higher of the two scores
K: A
G: ## Reproducible measurement
A score is a function of the suite, the evaluators, the model configuration and the randomness of the run. The exam guide asks you to separate signal from variance; that starts with controlling the setup.
## Checks
- Same suite version and case count.
- Same grader (version, rubric) and same model and parameters.
- Variance: repeat runs under one setup to see the spread.
- Record all of these with every result so comparisons are valid.
Example: one engineer ran against the suite before 40 new hard cases were added; with the same suite both get 84-86%.
W: Setup differences and variance: these explain divergent scores far more often than anything about the function.
X: B=Experience: measurement validity does not depend on who runs it.
C=Only a function change: suites, graders, settings and randomness also change scores.
D=Ignore and pick the higher: cherry-picking a number without knowing why they differ.
T: Make evaluation runs reproducible: same suite, grader, model and parameters, with variance known.

@ PLTR-AIE D5 T5.4 applied use-case
S: An evaluation suite has grown to 2,000 cases and takes four hours to run, so engineers stop running it before small changes. What is a sound approach?
A: Delete most of the cases so the suite is small again, keeping only the hundred that the team finds most interesting
B: Tier the suite: a fast representative subset for every change, the full suite nightly and before releases
C: Run the full suite only once a quarter, since four hours is too long to run more often than that for a team of this size
D: Stop maintaining the suite and rely on production feedback, which is faster and reflects what users actually ask
K: B
G: ## Keeping evaluation practical
A suite nobody runs protects nothing. The exam guide asks for regression detection across changes; the suite must fit the workflow.
## Tiering
- Fast tier (a few minutes): stratified sample across case types, plus all recently failed and recently added cases.
- Full tier: nightly and pre-release.
- Rotate the fast tier periodically so coverage spreads.
- Parallelize where possible to shorten the full run.
Example: a 150-case fast tier runs in 8 minutes on every change; the full 2,000 run overnight catches anything the sample missed.
W: Tiered suites: frequent fast feedback plus complete coverage at the right moments, so the suite stays in use.
X: A=Delete cases: coverage is lost; "interesting" is not a sampling strategy.
C=Quarterly: a regression introduced in week one would go undetected for up to three months while every change builds on it.
D=Production feedback instead: users become the test; the suite exists to prevent that.
T: Tier large evaluation suites into a fast subset for every change and a full run for releases.

@ PLTR-AIE D5 T5.2 applied tradeoff
S: Which approach to adversarial evaluation cases keeps them useful over time?
A: Write a fixed set once at launch and never change it, so results remain comparable across every future version of the workflow
B: Maintain a living set: add new attack patterns from production and research, record the expected safe behaviour, re-run on every change
C: Rely on the model provider's safety testing, since they test their models against attacks more thoroughly than any application team could
D: Remove adversarial cases once the workflow passes them, so the suite stays focused on the cases that still fail
K: B
G: ## Adversarial cases evolve
Attack techniques change. The exam guide asks for adversarial testing and for feedback loops that turn observations into cases.
## Practice
- Source new patterns from production monitoring (flagged sessions) and public research.
- Each case: input, expected safe behaviour, evaluator.
- Keep passing cases as regression protection.
- Version the set so comparisons remain possible.
Example: a new injection style found in a flagged session becomes three cases; the next prompt change is checked against them.
W: A living, versioned adversarial set re-run on every change: it tracks the threat landscape and guards against regressions.
X: A=Fixed forever: attack techniques discovered after launch are never tested, so the suite's "pass" slowly stops meaning anything.
C=Provider only: the provider does not test an application's specific tools, data and prompts.
D=Remove passing cases: a later change can reintroduce the vulnerability unnoticed.
T: Treat adversarial cases as a maintained, growing regression set.

@ PLTR-AIE D5 T5.3 applied use-case
S: A team wants to know whether a change improved the function for the cases that matter most to the business, not just on average. How should results be analyzed?
A: Report the overall average score only, since an average is the standard way to summarize any evaluation and is easy for stakeholders to read
B: Segment results by category and consequence, compare per segment before and after, and weight the decision by the segments that matter
C: Report the best-performing segment, since highlighting the strongest result shows stakeholders the value of the change most clearly
D: Report only the worst case, since a single failure is enough to block any release regardless of the other results
K: B
G: ## Segmented evaluation
An average hides trade-offs. The exam guide asks for per-case analysis and for matching rigor to consequence; segments connect the two.
## Method
- Tag cases with category and consequence.
- Per-segment metrics before and after the change.
- Decision rules: no regression allowed in high-consequence segments; average improvement elsewhere is a bonus.
Example: overall +3 points, but regulatory cases drop from 96% to 90%; the change is held until that segment recovers.
W: Per-segment comparison weighted by consequence: the decision reflects where quality matters most.
X: A=Average only: a gain on common cases can hide a regression in a small, critical segment such as regulatory cases.
C=Best segment only: cherry-picking the strongest result misleads stakeholders and hides where the change hurt.
D=Worst case only: blocks everything on one outlier without context; segments give proportion.
T: Analyze evaluation results by segment and consequence, not just on average.

@ PLTR-AIE D5 T5.1 applied comparison
S: A team wants to use a model-graded evaluator to score the quality of free-text summaries produced by a function. Which statement about model-graded evaluators is accurate?
A: They are always as reliable as human raters, so calibration against humans is unnecessary once the rubric has been written clearly
B: They scale free-text evaluation but need explicit criteria, calibration against human ratings, and handling of their own non-determinism
C: They should never be used, because any model-based judgement is circular and cannot be trusted for evaluation purposes
D: They can replace deterministic checks for numeric and categorical outputs, since a model can compare values just as well as code
K: B
G: ## Using model graders well
Model-based grading scales rubric evaluation of free text. The exam guide lists evaluators among the things to design and asks you to distinguish signal from variance.
## Conditions
- Explicit rubric criteria, scored separately.
- Calibration: agreement with human ratings on a sample; adjust the rubric until agreement is acceptable.
- Variance: graders are non-deterministic too; repeat or use low temperature.
- Deterministic checks for anything deterministic.
Example: after calibration the grader agrees with humans 92% on groundedness; numeric fields are still checked by code.
W: Scalable but calibrated, with explicit criteria and variance handled: the accurate description.
X: A=Always reliable: graders have biases and noise; calibration is required.
C=Never use: they are the practical way to evaluate free text at scale, with safeguards.
D=Replace deterministic checks: exact comparisons are cheaper and more reliable in code.
T: Use model graders for free text with explicit criteria and human calibration; keep deterministic checks in code.

@ PLTR-AIE D5 T5.4 advanced use-case
S: An AI workflow's outputs are later corrected by downstream systems (for example, finance adjusts amounts the workflow extracted). How can these corrections improve the workflow systematically?
A: They cannot, since downstream systems are separate and the workflow has no way to learn from what happens after it runs
B: Join corrections to outputs by key, measure correction rates by field and input type, turn recurring patterns into evaluation cases, prioritize fixes
C: Replace the workflow with the downstream system's manual process, since the corrections show that humans do the job better anyway
D: Ask finance to stop correcting values so the workflow's outputs remain consistent with what it originally produced
K: B
G: ## Downstream outcomes as feedback
The exam guide asks for feedback loops that capture downstream outcomes and turn them into evaluation cases or improvement priorities. Corrections are labelled errors with ground truth.
## Loop
- Join: workflow output ↔ corrected value by document id.
- Measure: correction rate by field, document type, source.
- Convert: recurring patterns into evaluation cases with the corrected value as expected.
- Prioritize: fix the highest-impact pattern first; re-measure.
Example: 70% of corrections are on invoices from one supplier whose totals include tax; a prompt rule and a validation fix it, and the correction rate halves.
W: Join, measure, convert, prioritize: corrections become a measurable improvement engine.
X: A=Cannot learn: the data to learn from exists in the downstream system; joining it is straightforward.
C=Abandon automation: corrections on a minority of rows do not negate the value on the rest.
D=Stop correcting: it hides errors instead of fixing their source.
T: Feed downstream corrections back into evaluation and prioritized improvements.
