@ SAP-C03 D1 T1.4 expert troubleshooting
S: A retailer attached an application VPC and a database VPC in us-east-1 to one transit gateway and enabled security group referencing on the transit gateway and on both attachments. For PCI scope, traffic from the application VPC to the database VPC is routed through an inspection VPC with AWS Network Firewall, attached to the same transit gateway. A reporting VPC in us-west-2 reaches the database VPC through transit gateway peering. The database security group has inbound rules that reference the application security group and the reporting security group. Flow logs show both flows arriving at the database ENIs and being rejected. Which change restores both flows while keeping inspection and least privilege?
A: Enable appliance mode on the inspection VPC attachment so that the database security group can match the application security group on both directions of each flow
B: Enable security group referencing on the inspection VPC attachment and on the peering attachment, so that both referenced groups resolve across the transit gateway
C: Replace both referenced-group rules with an inbound rule that uses a customer managed prefix list holding only the application and reporting subnet CIDRs
D: Add outbound rules to the application and reporting security groups that reference the database security group, so that the return path is matched by reference
K: C
G: ## Security group referencing through a transit gateway
A transit gateway can let a security group in one attached VPC reference a security group in another attached VPC. It works only when:
- It is enabled on the **transit gateway and on both VPC attachments**.
- Both VPCs are attached to the **same** transit gateway; it is **not supported across transit gateway peering**.
- The traffic does **not** pass through an inspection VPC with **Gateway Load Balancer or AWS Network Firewall**.
- The rule is an **inbound** rule; outbound rules cannot reference groups across the transit gateway.
## Reading the evidence
Both flows reach the database ENIs (routing works) and are rejected by the security group: the application flow passes through Network Firewall, and the reporting flow crosses a peering attachment, so neither source group can be matched by reference.
## Least-privilege fix
Use IP-based rules. A customer managed prefix list such as `pl-db-clients` with `10.1.8.0/22` (application subnets) and `10.40.2.0/24` (reporting subnets) keeps the rule narrow and reusable.
W: Prefix list of the source subnet CIDRs: CIDR-based rules work regardless of inspection or peering, and listing only the client subnets keeps access as narrow as the old references.
X: A=Appliance mode: it keeps flows symmetric through the firewall but does not make referenced security groups work through Network Firewall.
B=Referencing on more attachments: referencing is unsupported across peering and through Network Firewall inspection, so enabling it elsewhere changes nothing.
D=Outbound references: security groups are stateful, so return traffic is already allowed, and outbound rules cannot reference groups across a transit gateway.
T: Security group referencing over a transit gateway fails through Network Firewall or GWLB inspection and across peering; use CIDR or prefix list rules there.

@ SAP-C03 D1 T1.5 expert use-case
S: A bank keeps customer balances in a 2 TB DynamoDB table in eu-west-1. The application uses TTL to expire hold records and TransactWriteItems to move money between two items. A new rule requires an RPO of zero for a Regional outage and strongly consistent reads in a second Region, eu-central-1, where an active copy of the application will run. A data residency clause in the bank's licence states that no customer data, in any form, may be stored outside EU Regions. The bank wants full replicas only in eu-west-1 and eu-central-1. Which TWO actions are required? (Select TWO)
A: Add an eu-central-1 replica to the existing table and select multi-Region strong consistency mode for the global table during the replica creation
B: Create a new empty table as an MRSC global table with replicas in eu-west-1 and eu-central-1 and a witness in eu-west-3, then load the data and cut over
C: Place the witness for the new MRSC global table in us-east-1, because a witness stores only metadata and no customer data is kept in that Region
D: Remove the use of TTL and TransactWriteItems from the application, replacing them with scheduled cleanup and conditional single-item writes, before moving to MRSC
E: Keep the default multi-Region eventual consistency mode and alarm when ReplicationLatency exceeds 1 second, so that the RPO stays effectively at zero
K: B,D
G: ## Two consistency modes for global tables
- **MREC** (default): asynchronous replication, usually under a second. RPO equals the replication delay, so it is not zero. It publishes `ReplicationLatency`.
- **MRSC**: a write is synchronously replicated to at least one other Region before it succeeds; strongly consistent reads in any replica return the latest item. **RPO is zero.**
## MRSC rules that change the plan
- Exactly **three Regions**: three replicas, or **two replicas plus a witness**.
- A **witness contains data written to the replicas** (it cannot be read or written), so it counts as storing data in its Region.
- The mode is chosen at creation and cannot be changed; a single-Region table can be converted only when it is **empty**.
- **TTL is not supported**, and **transaction operations return an error**.
## Applying it
eu-west-3 (Paris) is an MRSC Region in the EU, so replicas in eu-west-1 and eu-central-1 plus a witness in eu-west-3 keep all data in the EU. The 2 TB table must be loaded into a new empty MRSC table.
W: B=New empty MRSC table with an EU witness: MRSC gives RPO zero and strongly consistent reads, the existing table cannot be converted because it holds data, and an EU witness respects residency.
D=Remove TTL and transactions: MRSC tables do not support TTL and reject transaction operations, so the application must change before the move.
X: A=Convert the existing table: the consistency mode is set at creation, and a table that already contains data cannot become an MRSC global table.
C=Witness in us-east-1: the witness holds data written to the replicas, so placing it outside the EU breaks the residency clause.
E=MREC with a latency alarm: an alarm only reports lag; asynchronous replication can still lose the last writes, so the RPO is not zero.
T: MRSC gives zero RPO but needs an empty table, three Regions (witness included), and no TTL or transactions.
V: Amazon DynamoDB

@ SAP-C03 D1 T1.1 expert troubleshooting
S: One Lambda function processes two standard SQS queues, orders and returns, through two event source mappings, each with maximum concurrency 40. The function writes to a database that accepts at most 50 connections, so its reserved concurrency is set to 50 and must not be raised. The function timeout is 50 seconds, both queues have a visibility timeout of 60 seconds, and the redrive policy sends messages to a DLQ after maxReceiveCount 2. During peaks the Throttles metric rises, and the DLQ fills with valid messages that succeed when redriven. Which change removes the root cause while protecting the database?
A: Raise the function's reserved concurrency to 80, matching the combined maximum concurrency of both mappings, and keep the queue settings as they are
B: Set maximum concurrency to 25 on each mapping, raise both queue visibility timeouts to 300 seconds, and raise maxReceiveCount to at least 5
C: Remove maximum concurrency from both mappings so Lambda scales pollers only up to the reserved concurrency of 50, and keep the queue settings unchanged
D: Keep both mappings at 40, raise maxReceiveCount to 10 on both queues, and add a retry with backoff inside the function code for database errors
K: B
G: ## Two concurrency controls that must agree
- **Reserved concurrency** caps how many instances of the function can run at once (here 50, set by the database limit).
- **Maximum concurrency** on an SQS event source mapping caps how many concurrent invocations that mapping makes. It is a separate setting.
AWS guidance: reserved concurrency must be **greater than or equal to the sum of maximum concurrency** of all SQS mappings on the function; otherwise Lambda throttles invocations.
## What throttling does to SQS messages
When an invocation is throttled, the batch is not processed and the messages become visible again after the visibility timeout. Each receive counts toward `maxReceiveCount`. With a limit of 2, valid messages reach the DLQ after a couple of throttles.
## Recommended queue settings
- Visibility timeout at least **6x the function timeout** (6 x 50 s = 300 s).
- `maxReceiveCount` of **at least 5**.
## Working the numbers
40 + 40 = 80 > 50, so up to 30 invocations can be throttled at peak. 25 + 25 = 50 matches the reserved concurrency exactly.
W: Split the reserved concurrency across mappings and fix queue settings: 25 + 25 stops throttling within the 50-connection limit, 300-second visibility follows the 6x rule, and a maxReceiveCount of 5 gives retries room before the DLQ.
X: A=Reserved concurrency 80: it removes throttling but lets 80 instances open connections against a database that accepts 50.
C=No maximum concurrency: each mapping can still scale to the reserved limit on its own, so together they keep hitting the cap of 50 and throttling continues.
D=More retries and backoff: it hides the symptom and slows the DLQ, but the mappings still request 80 concurrent invocations against a cap of 50.
T: Keep the sum of SQS mapping maximum concurrency at or below reserved concurrency, and size visibility timeout and maxReceiveCount for retries.
V: AWS Lambda, Amazon SQS

@ SAP-C03 D1 T1.3 expert use-case

B: Attach a new VPN connection to a transit gateway with Large Bandwidth Tunnels on both tunnels, dynamic routing, and acceleration disabled, using one tunnel at a time

D: Attach four standard VPN connections to a transit gateway with dynamic routing and enable ECMP, spreading the backup traffic evenly over eight tunnels

- A **standard** VPN tunnel carries up to **1.25 Gbps** (and 140,000 packets per second), which matches the 1.2 Gbps seen in the test.
- A **Large Bandwidth Tunnel (LBT)** carries up to **5 Gbps** (400,000 pps).

- Only for VPN connections attached to a **transit gateway or Cloud WAN**; **not** for virtual private gateways.

X: A=LBT on a virtual private gateway: Large Bandwidth Tunnels are not supported on virtual private gateway attachments, and they cannot be combined with acceleration.
C=LBT with acceleration: accelerated VPN is not supported for Large Bandwidth Tunnels, so this configuration cannot be built.
D=Four standard connections with ECMP: it reaches the bandwidth only by spreading flows across many equal-cost tunnels, which the firewall cluster cannot handle.
T: For more than 1.25 Gbps on one VPN tunnel, use Large Bandwidth Tunnels on a transit gateway or Cloud WAN, without acceleration.

@ SAP-C03 D1 T1.1 expert tradeoff
S: A payments company processes 30 million orders a month. Each order is validated and enriched in about 4 seconds by idempotent Lambda steps. For about 2% of orders, a non-idempotent capture-payment step must wait up to 20 minutes for a bank callback that returns a task token. A cost review showed that running every order in a Standard workflow, billed per state transition, exceeds the budget, while execution-duration billing fits it. Payment capture must never run twice for an order. Orders arrive through Amazon API Gateway at peaks of about 2,000 per second. Which design meets these requirements?
A: Run every order in an Express workflow, and for payment orders use a Task state with the waitForTaskToken pattern so the workflow waits for the bank callback
B: Run every order in an Express workflow that starts a Standard child workflow with the .sync pattern for payment orders, and waits for its result
C: Run every order in a Standard workflow and set each Lambda task's Retry block to zero attempts so the capture step can never execute more than once
D: Run every order in an Express workflow that, for payment orders, starts a Standard child workflow with StartExecution and ends without waiting for it
K: D
G: ## Standard versus Express
- **Standard**: up to 1 year, exactly-once execution (unless you add Retry), billed per state transition, supports Request Response, Run a Job (`.sync`) and Wait for callback (`.waitForTaskToken`).
- **Express**: up to 5 minutes, at-least-once execution, billed per execution, duration and memory, supports **Request Response only**.
## Splitting the work
High-volume, short, idempotent steps fit **Express**. A long wait for a callback and a non-idempotent action fit **Standard**. An Express workflow can still start a Standard workflow with a plain `StartExecution` call (Request Response), which returns as soon as the child starts.
## Working the numbers
30 million orders x a few transitions each in Standard is what broke the budget. Only 2% (600,000 a month) need the Standard child, so most executions are billed by duration in Express.
W: Express parent with a fire-and-forget Standard child: high-volume idempotent steps run cheaply in Express, and the 2% of payment orders get a Standard workflow that can wait 20 minutes for the callback with exactly-once execution.
X: A=Express with waitForTaskToken: Express workflows support only Request Response integrations and stop after five minutes, so they cannot wait 20 minutes for a callback.
B=Express starting the child with .sync: the Run a Job (.sync) pattern is not available in Express workflows, and waiting 20 minutes would exceed the five-minute limit anyway.
C=All Standard with no retries: it keeps exactly-once behavior, but per-transition billing for 30 million orders is the cost the review rejected.
T: Use Express for high-volume idempotent steps and hand long or non-idempotent work to a Standard workflow started with a Request Response call.
V: AWS Step Functions, AWS Lambda

@ SAP-C03 D2 T2.3 expert troubleshooting
S: A company attaches an SCP to its Workloads OU that denies all actions when aws:RequestedRegion is not eu-west-1 or eu-central-1, with a NotAction list of cloudfront:*, iam:*, route53:*, and support:*. A team in a workload account now deploys a CloudFront distribution with a custom domain. The pipeline role fails on acm:RequestCertificate in us-east-1 and later on wafv2:CreateWebACL with the CLOUDFRONT scope. Compliance insists that no other workload resources are created outside the two EU Regions. The security team reviews every SCP change against the residency policy before release. Which SCP change fixes the deployment while meeting the compliance rule?
A: Add us-east-1 to the list of allowed Regions in the existing deny statement, so that the pipeline role can call ACM and AWS WAF in that Region
B: Add acm:* and wafv2:* to the NotAction list of the existing statement, so that certificate and web ACL calls are never denied in any Region
C: Add an exception to the existing statement for the CloudFront service-linked role ARN, so that CloudFront can request the certificate and web ACL itself
D: Add acm:* and wafv2:* to NotAction, plus a second deny for those actions when aws:RequestedRegion is not eu-west-1, eu-central-1, or us-east-1
K: D
G: ## Region-deny SCPs and global services
A Region-deny SCP uses `Deny` with `NotAction` and a `StringNotEquals` condition on `aws:RequestedRegion`. Global services such as CloudFront, IAM, Route 53 and Support have a single endpoint in **us-east-1**, so they go into `NotAction` or every call would be denied.
## The CloudFront seams
Some regional services must be called in us-east-1 for CloudFront:
- A certificate for a CloudFront custom domain must be requested in **ACM in us-east-1**.
- An AWS WAF web ACL with the **CLOUDFRONT** scope is created through the us-east-1 endpoint.
Both are regional APIs (`acm:*`, `wafv2:*`), so the Region-deny statement blocks them.
## Narrow exception
Exempt the two services from the general statement and add a second deny that still blocks them outside the two EU Regions **and** us-east-1:
`{"Effect": "Deny", "Action": ["acm:*", "wafv2:*"], "Resource": "*", "Condition": {"StringNotEquals": {"aws:RequestedRegion": ["eu-west-1", "eu-central-1", "us-east-1"]}}}`
W: Exempt and re-restrict ACM and WAF: removing them from the general deny lets the pipeline call them in us-east-1, while the second deny keeps them out of every other Region and nothing else gains us-east-1.
X: A=Allow us-east-1 for everything: every service, such as EC2 and S3, could then create resources in us-east-1, which breaks the compliance rule.
B=NotAction only: ACM certificates and web ACLs could then be created in any Region in the world, wider than the CloudFront need.
C=Exception for the CloudFront service-linked role: the calls are made by the pipeline role, not by CloudFront, and SCPs never apply to service-linked roles anyway.
T: When a Region-deny SCP blocks CloudFront prerequisites, exempt ACM and WAF from the general deny and restrict them with a second deny that adds only us-east-1.

A: SCPs do not affect users or roles in the management account, so the management account's IAM user could launch the instance in us-east-1
B: SCPs do not restrict service-linked roles, so AWS Config's role can call APIs in Regions that the SCP otherwise denies to principals in the account

G: ## Who SCPs apply to
- **Member accounts only.** Users and roles in the **management account** are not affected.
- **Including the root user** of member accounts.
- **Including delegated administrator accounts**, which are member accounts.
- **Not service-linked roles**: AWS services that act through service-linked roles are never restricted by SCPs.
- SCPs never grant permissions, and an explicit deny in any applicable policy beats any allow.
## Reading the four events
1. Management account IAM user in us-east-1: expected, SCPs do not reach the management account.
2. Config service-linked role in ap-southeast-2: expected, service-linked roles are exempt.
3. Member root user denied: expected, the SCP applies to member root users.
4. Delegated administrator role created a table in us-west-2: **not** explained by SCP behavior; it should have been denied. The likely causes are an SCP that is not attached where the team thinks (for example, the account sits in an OU whose effective policy lacks the deny) or a statement mismatch, which the team must investigate.
W: A=Management account exemption: SCPs affect only member accounts, so the management account's IAM user was not restricted.
B=Service-linked role exemption: AWS Config acts through its service-linked role, which SCPs cannot restrict.
C=Member root user is covered: SCPs restrict member accounts' root users too, so the denial was correct.
X: D=Delegated administrators exempt: delegated administrator accounts are member accounts and SCPs apply to them; this event points to a gap in the policy attachment, not an exemption.
E=Identity Allow overrides SCP: an explicit deny in an SCP always wins over any allow in identity policies.
F=Read-only actions exempt: SCP conditions apply to read-only actions like any others; only the service-linked role made those calls succeed.
T: SCPs bind member accounts and their root users, including delegated administrators, but never the management account or service-linked roles.

@ SAP-C03 D2 T2.1 expert troubleshooting
S: A data platform account (A) owns an S3 bucket with Object Ownership set to bucket owner enforced. Objects are encrypted with SSE-KMS using a customer managed key in account A. An analytics role in account B reads the bucket through an S3 gateway endpoint in account B. The bucket policy allows the role s3:GetObject, the role's IAM policy allows s3:GetObject on the bucket, and the endpoint policy allows the bucket. HeadObject calls from the role succeed, but GetObject calls return AccessDenied, and account A's CloudTrail shows kms:Decrypt denied for the role. Which TWO changes are required? (Select TWO)
A: In account A, add a statement to the KMS key policy that allows account B, or the analytics role, to call kms:Decrypt on the key
B: In account A, create a KMS grant for account B's root principal on the key, because cross-account use of a key requires a grant instead of a key policy statement
C: In account B, add kms:Decrypt on the full key ARN of account A's key to the analytics role's IAM policy, not on an alias ARN
D: In account A, change Object Ownership to bucket owner preferred, so that ACLs can give account B permission to decrypt each object's data key
E: In account B, add kms:Decrypt for account A's key to the gateway endpoint policy, because S3 calls KMS through the endpoint used by the caller

G: ## Two permission checks for SSE-KMS objects
Reading an SSE-KMS object needs **S3 permission** for `s3:GetObject` and **KMS permission** for `kms:Decrypt` on the key, because S3 asks KMS to decrypt the object's data key on behalf of the caller.
## Cross-account KMS access
Cross-account use of a KMS key requires **both**:
1. The **key policy** in the key's account allows the external account (or a specific role).
2. An **IAM policy** in the external account allows its principal to use the key, naming the key by its **key ARN** (aliases cannot be used to grant access to a key in another account).
Grants are an alternative way to delegate, but they are not required when the key policy and IAM policy both allow the action.

W: A=Key policy in account A: KMS checks the key policy first, and it must allow account B or the role to decrypt.
C=IAM permission in account B: the role also needs kms:Decrypt on the key ARN in its own identity policy, because cross-account key use needs both sides.
X: B=Grant required: grants are optional for this case; a key policy statement plus an IAM policy is the documented method.
D=Object Ownership change: ACLs control S3 access, not KMS permissions, and S3 access already works.
E=KMS in the S3 endpoint policy: the gateway endpoint governs S3 requests only; S3's call to KMS is not authorized by that endpoint policy.
T: Cross-account SSE-KMS reads need the key policy to allow the other account and the caller's IAM policy to allow kms:Decrypt on the key ARN.

@ SAP-C03 D2 T2.2 expert troubleshooting
S: A company uses client-side encryption with the AWS Encryption SDK for documents stored in DynamoDB global tables in us-east-1 and eu-west-1. It created a multi-Region primary key in us-east-1, replicated it to eu-west-1, and configured each Regional application to use the key ARN in its own Region. A security rule says application traffic must not make cross-Region KMS calls. After a failover drill, the eu-west-1 application gets AccessDeniedException on kms:Decrypt for the replica key, although the same role name decrypts in us-east-1 and its IAM policy allows both key ARNs. Which change fixes this?
A: Point the eu-west-1 application at the us-east-1 primary key ARN, because the primary key policy already allows the role and multi-Region keys share key material
B: Run ReplicateKey again from the primary key, because replica keys inherit the primary key policy only when they are re-created after a policy change
C: Update the primary key policy to name the eu-west-1 role, because KMS synchronizes key policies from the primary key to every replica as a shared property
D: Add a statement to the eu-west-1 replica key's own key policy that allows the eu-west-1 application role to call kms:Decrypt and GenerateDataKey
K: D
G: ## What multi-Region keys share and what they do not
Related multi-Region keys share **key ID** and **key material** (plus a few other shared properties that KMS synchronizes from the primary). That is why ciphertext from one Region decrypts in another without a cross-Region call.
Each replica is still a **fully independent KMS key** with its **own key policy, grants, aliases and tags**. KMS never copies a primary's key policy changes to replicas.
## Reading the evidence
The role's IAM policy allows both key ARNs, and the call fails only on the replica key, so the replica's key policy does not allow the role. When the replica was created, it got whatever policy was supplied then (often the default).
## Fix

K: A
G: ## Backlog per instance
Scaling on raw queue length ignores how many instances are working. AWS recommends a **backlog per instance** metric:
- Backlog per instance = `ApproximateNumberOfMessagesVisible` / number of **InService** instances, computed with **metric math** in the target tracking policy (no custom metric needed).
- Target value = **acceptable latency / processing time per message**.
## Working the numbers
- Target: 60 s / 0.25 s = **240 messages per instance**.
- At peak: 36,000 / 240 = **150 instances** needed, so the maximum size of 100 caps the group below the target and latency grows.
- With raw queue length and a target of 240, the policy tries to hold the whole queue at 240 messages, so it pushes to the maximum during peaks and keeps too many instances while the queue drains.
W: Backlog per instance with target 240 and a higher maximum: each instance then holds 60 seconds of work, and allowing 150 instances lets the group reach the capacity the peak needs.
X: B=Target of 4: 4 is the processing rate per instance per second, not the acceptable backlog, so the group would scale to 9,000 instances' worth of demand and hit any maximum.
C=Keep maximum 100: the metric is right, but 36,000 / 100 = 360 messages per instance, which is 90 seconds of latency, above the limit.
D=Raw queue target of 60: the latency limit in seconds is not a queue length, and a raw queue target still ignores how many instances share the work.
T: Scale SQS workers on backlog per instance with target = acceptable latency / processing time, and size the maximum for peak backlog.
