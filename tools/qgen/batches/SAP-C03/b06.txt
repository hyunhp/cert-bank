@ SAP-C03 D3 T3.2 advanced tradeoff
S: A company connects 35 VPCs in one Region through a transit gateway. Each VPC route table sends 10.0.0.0/8 to the transit gateway. A data lake VPC (10.20.0.0/16) and an analytics VPC (10.30.0.0/16) exchange about 400 TB per month, mostly between subnets in the same Availability Zones, which is now the largest line on the network bill. All other VPC pairs exchange little data and must keep using the transit gateway. Which change reduces cost the most with the least redesign?
A: Create a VPC peering connection between the two VPCs and add routes for each other's /16 CIDR pointing to the peering connection, leaving the 10.0.0.0/8 route to the transit gateway in place
B: Enable appliance mode on both transit gateway VPC attachments so that the traffic between the two VPCs stays in the same Availability Zone and avoids the transit gateway processing charge
C: Move both VPCs into a separate transit gateway route table with only each other's routes so that their traffic is isolated and billed as attachment hours instead of per gigabyte
D: Publish the data lake as an endpoint service behind a Network Load Balancer and consume it from the analytics VPC through an interface endpoint powered by AWS PrivateLink
K: A
G: ## How the three VPC-to-VPC options are billed
- **Transit gateway**: an hourly charge per attachment plus a **data processing charge per GB** sent into the transit gateway. Every byte between two attached VPCs pays this charge.
- **VPC peering**: no hourly charge and no processing charge. Traffic that stays within one Availability Zone over a peering connection is free; traffic that crosses Availability Zones pays the normal inter-AZ data transfer rate.
- **AWS PrivateLink**: an hourly charge per interface endpoint per Availability Zone plus a per-GB processing charge, and the provider runs a Network Load Balancer.
## Mixing peering and a transit gateway
VPC route tables use the most specific matching route. If a route table has `10.0.0.0/8 -> tgw-...` and `10.30.0.0/16 -> pcx-...`, traffic to the analytics VPC uses the peering connection, while every other destination still uses the transit gateway. This lets you offload one heavy pair without touching the hub.
## Example
400 TB a month through the transit gateway pays 400 TB of processing charges. The same traffic over peering, mostly within the same AZ, pays little or nothing for the same-AZ part.
W: Peering for the heavy pair: peering has no per-GB processing charge and same-AZ traffic over it is free, and the more specific /16 routes override the 10.0.0.0/8 route only for this pair, so the rest of the network stays on the transit gateway unchanged.
X: B=Appliance mode: appliance mode keeps both directions of a flow on the same attachment network interface for stateful appliances; it does not remove or reduce the per-GB data processing charge.
C=Separate route table: transit gateway route tables control which attachments can reach each other, but every GB sent into the transit gateway is still billed for data processing no matter which route table it uses.
D=PrivateLink endpoint service: PrivateLink also charges per GB processed plus endpoint hours and adds a load balancer, so moving 400 TB a month through it does not avoid a per-GB charge the way peering does.
T: For a few VPC pairs that move very large volumes, add VPC peering with more specific routes beside the transit gateway; peering has no processing charge, while transit gateway and PrivateLink bill per GB.
V: AWS Transit Gateway, Amazon VPC, AWS PrivateLink

@ SAP-C03 D3 T3.2 advanced use-case
S: A company has 50 spoke VPCs in one Region connected through a transit gateway. Every spoke VPC has its own interface endpoints for 12 AWS services in three Availability Zones, and the endpoint hourly charges have become significant even though API traffic to those services is light. The same spokes also read several terabytes per day from Amazon S3 in the same Region. Which TWO changes lower the network cost while keeping traffic off the internet? (Select TWO)
A: Create the interface endpoints once in a shared services VPC, disable private DNS on them, and associate Route 53 private hosted zones for the service names with every spoke VPC
B: Create one S3 gateway endpoint in the shared services VPC and add a route in each spoke VPC that sends S3 prefix list traffic to that VPC through the transit gateway
C: Create an S3 gateway endpoint in each spoke VPC and add it to the spoke route tables, so S3 traffic goes directly to S3 without using the transit gateway
D: Delete the interface endpoints and send AWS API traffic through centralized NAT gateways in an egress VPC, which already serves internet-bound traffic from the spokes
E: Keep interface endpoints in every spoke but deploy them in a single Availability Zone, so each service needs one endpoint network interface per VPC instead of three
K: A,C
G: ## What each endpoint type costs
- **Interface endpoints** (AWS PrivateLink) are billed per endpoint per Availability Zone per hour, plus a per-GB processing charge. 50 VPCs x 12 services x 3 AZs = 1,800 endpoint-AZ hours every hour.
- **Gateway endpoints** for S3 and DynamoDB have **no charge** at all. They are a route table target, so they only serve the VPC whose route tables reference them; they cannot be reached from another VPC through peering, a transit gateway or a VPN.
## Centralizing interface endpoints
A common hub pattern puts the interface endpoints in a shared services VPC. Private DNS is turned off there, and a Route 53 private hosted zone such as `ssm.us-east-1.amazonaws.com` with an alias to the endpoint is associated with every spoke VPC. Spokes then resolve the service name to the central endpoint IPs and reach them through the transit gateway.
The trade-off: spoke traffic now pays transit gateway data processing per GB, which is cheap when the API traffic is light but expensive for heavy flows. That is why bulk S3 traffic should not take this path.
W: A=Centralized interface endpoints: 12 services x 3 AZs in one VPC replaces 1,800 endpoint-AZ hours with 36, and the light API traffic adds only a small transit gateway processing charge.
C=Gateway endpoint per spoke: S3 gateway endpoints are free and keep the terabytes of S3 traffic on a direct private path, so that traffic pays neither transit gateway nor endpoint processing charges.
X: B=Central S3 gateway endpoint: a gateway endpoint is a route table target that works only for traffic originating in its own VPC; traffic arriving from spokes through the transit gateway cannot use it.
D=Centralized NAT gateways: NAT gateways charge per GB processed and the traffic also pays transit gateway processing, and API calls then leave through public service endpoints instead of a private endpoint path.
E=Single-AZ endpoints: it cuts endpoint hours by two thirds but still leaves 600 endpoints, adds cross-AZ data transfer for two thirds of clients, and makes every service unreachable privately if that one AZ fails.
T: Centralize lightly used interface endpoints behind the transit gateway with shared private hosted zones, but keep free gateway endpoints for S3 and DynamoDB in every VPC that moves bulk data.
V: AWS PrivateLink, Amazon S3, AWS Transit Gateway, Amazon Route 53

@ SAP-C03 D3 T3.2 applied troubleshooting
S: A company replaced a full mesh of VPC peering connections between 12 VPCs with a single transit gateway to simplify routing. Traffic volumes and Availability Zone placement did not change, but the monthly networking bill rose sharply. Cost Explorer shows a large new line item for the transit gateway in the same Region. What is the most likely cause of the increase?
A: The transit gateway charges inter-Region data transfer rates for traffic between attachments, because each attachment is treated as a separate network even within one Region
B: The transit gateway bills an hourly charge for every attachment and a per-GB data processing charge for traffic sent into it, neither of which applies to VPC peering
C: The transit gateway enables appliance mode on every attachment by default, which sends each flow through an extra Availability Zone and doubles the data transfer charge
D: The transit gateway bills a charge for every propagated route in its route tables, and the 12 VPCs propagate many more routes than the peering connections did
K: B
G: ## Transit gateway pricing in one sentence
A transit gateway charges **per attachment per hour** and **per GB of data processed** (the data sent from an attachment into the transit gateway). Inter-Region data transfer charges apply on top when traffic crosses a transit gateway peering to another Region.
## VPC peering pricing
VPC peering has no hourly charge and no processing charge. Data that crosses Availability Zones over peering pays the normal inter-AZ rate; data within one Availability Zone over peering is free.
## What this means for a migration
Moving the same traffic from peering to a transit gateway adds two new costs: 12 attachments running every hour, and a processing charge on every GB exchanged between the VPCs. The bigger the east-west traffic, the bigger the jump. Many designs keep peering for the few heaviest pairs and use the transit gateway for everything else.
W: Attachment hours plus data processing: these two charges exist only on the transit gateway, so the same traffic that used to cost nothing extra over peering now pays per GB processed plus hourly attachment fees.
X: A=Inter-Region rates: traffic between attachments of one transit gateway in one Region is not billed as inter-Region transfer; inter-Region rates apply only when traffic crosses a transit gateway peering to another Region.
C=Appliance mode by default: appliance mode is off by default and is enabled per VPC attachment for stateful appliances; it controls flow symmetry and does not double data transfer.
D=Per-route charge: transit gateways have route quotas, not a per-route fee; the bill is driven by attachment hours and gigabytes processed.
T: A transit gateway adds per-attachment hourly fees and per-GB processing that VPC peering does not have, so high east-west traffic can cost much more after consolidating onto it.
V: AWS Transit Gateway, Amazon VPC, AWS Cost Explorer

@ SAP-C03 D3 T3.3 applied troubleshooting

Two months ago, platform teams began tagging all resources in member accounts with a CostCenter key, and the tags are visible on the resources in the console. The finance team, which works in the management account, still cannot group or filter by CostCenter in AWS Cost Explorer or see it as a column in the Cost and Usage Report. What should the company do?
A: Enable AWS Config in every member account and add the required-tags managed rule for CostCenter, so that billing can read the recorded tag values from the configuration items
B: Attach a tag policy for CostCenter to the organization root with enforcement turned on, which publishes the tag key to the billing data of every member account
C: Activate CostCenter as a user-defined cost allocation tag on the cost allocation tags page of the management account and wait for the activation to take effect
D: Create a Cost and Usage Report in each member account with resource IDs included, and join the reports with the tag values exported from the Resource Groups Tagging API
K: C
G: ## Resource tags versus cost allocation tags
A tag on a resource is metadata. It does not appear in billing data until its key is **activated as a cost allocation tag**.
- **User-defined tags** (such as `CostCenter`, `Project`, `Environment`) are activated on the cost allocation tags page of Billing and Cost Management.
- **AWS-generated tags** (such as `aws:createdBy`) also need activation.
- In an organization, activation is done from the **management account**, and it applies to the consolidated billing data for all member accounts.
- A newly used tag key can take up to 24 hours to show up on that page, and activation takes up to 24 hours more before it is usable in Cost Explorer and the Cost and Usage Report.
## Example
After `CostCenter` is activated, Cost Explorer can group by `CostCenter` and the Cost and Usage Report gains a column for it, so costs can be split by cost center without any extra joins.
W: Activate the cost allocation tag: billing tools only use tag keys that have been activated for cost allocation, and the management account is where that activation is done for the whole organization.
X: A=AWS Config required-tags rule: Config evaluates whether resources carry the tag and reports compliance; it does not feed tag keys into billing data.
B=Tag policy: tag policies standardize tag keys and allowed values and can prevent noncompliant tagging operations, but they do not activate the key for cost allocation.
D=Per-account reports with joins: it rebuilds by hand what activation gives for free, needs custom processing in every account, and still leaves Cost Explorer unable to group by the tag.
T: Tags reach Cost Explorer and the Cost and Usage Report only after their keys are activated as cost allocation tags in the management account.

@ SAP-C03 D3 T3.3 advanced use-case

Finance wants every dollar assigned to a business unit and environment, including charges that cannot be tagged, such as some data transfer and support fees. A: Put all business units in one shared account per environment and depend on BusinessUnit, Project and Environment tags on every resource for each allocation dimension

C: Use one large account for the whole company and assign costs to business units and environments each month by splitting the bill in proportion to vCPU hours

- **Account structure**: every charge on the bill belongs to a linked account, including charges that cannot carry a tag. If accounts map to business units and environments, those dimensions are always complete.
- **Tags**: tags give finer splits inside an account (for example `Project`), but only for taggable resources and only when people remember to apply them.

A robust strategy puts the dimensions that must be 100% complete into the account and OU structure (for example `BU-Retail/prod`), and uses a small, mandatory set of tags such as `Project` and `Owner` for the finer split. C=Single account with vCPU split: a proportional formula is an estimate, not an allocation of actual charges, and it ignores storage, data transfer and managed services that have no vCPU hours.
D=aws:createdBy inference: that tag identifies the creating principal, not the business unit or environment, and it is not added to all resource types, so the mapping would be incomplete and fragile.

Snapshots are created by an Amazon Data Lifecycle Manager policy. Which change fixes the allocation with the least ongoing effort?
A: Add volume tag specifications to the launch template, and enable the copy-tags option in the Data Lifecycle Manager policy so snapshots inherit the volume tags
B: Activate the AWS-generated aws:createdBy cost allocation tag, which links each volume and snapshot to the Auto Scaling group that created the instance

@ SAP-C03 D3 T3.4 advanced use-case
S: A company protects Amazon EFS file systems and Amazon DynamoDB tables with AWS Backup (advanced DynamoDB backup features are enabled). Requirements: daily backups kept 35 days for operational restores, and monthly backups kept 7 years for compliance; monthly backups are restored less than once a year. The company wants the lowest storage cost that still meets the retention rules. Which TWO backup plan settings should the solutions architect configure? (Select TWO)
A: A daily rule that keeps recovery points for 35 days in warm storage with no transition to cold storage
B: A daily rule that moves recovery points to cold storage after 7 days and deletes them after 35 days
C: A monthly rule that moves recovery points to cold storage after 30 days and keeps them for 7 years
D: A monthly rule that keeps recovery points for 90 days in a vault with AWS Backup Vault Lock in compliance mode set to 7 years
E: A monthly rule that keeps recovery points in warm storage and a vault lifecycle rule that exports them to S3 Glacier Deep Archive
K: A,C
G: ## AWS Backup lifecycle
Each backup rule has a lifecycle: an optional **transition to cold storage** after N days and a **retention** (delete after M days).
- Cold storage is much cheaper per GB, but a recovery point must stay in cold storage for **at least 90 days**. AWS Backup therefore requires retention to be at least 90 days longer than the transition day.
- Cold storage is supported for some resource types only, including EFS, DynamoDB with advanced features, and EBS; check the feature availability table for others.
## Matching rules to retention
- Short operational backups (here 35 days) cannot use cold storage at all: 35 is less than any transition day plus 90.
- Long compliance backups are the ideal case: keep them warm for a short time in case of a recent restore, then move them to cold storage for the rest of the 7 years (about 2,555 days).
W: A=Daily rule kept warm: 35-day backups cannot meet the 90-day cold storage minimum, so warm storage with 35-day retention is the cheapest valid setting.
C=Monthly rule to cold after 30 days: rarely restored recovery points spend almost 7 years at the cold storage price, and retention far exceeds transition plus 90 days.
X: B=Daily cold after 7 days: deleting at day 35 breaks the rule that retention must be at least 90 days after the cold transition, so AWS Backup rejects that lifecycle.
D=Vault Lock for retention: Vault Lock stops anyone from deleting recovery points early, but it does not extend retention; the rule still deletes them at 90 days.
E=Export to Glacier Deep Archive: backup vaults are not S3 buckets you can attach lifecycle rules to, and AWS Backup has no vault rule that exports recovery points to S3 storage classes.
T: In AWS Backup, use cold storage only for long retention (retention at least transition + 90 days); keep short operational backups warm.
V: AWS Backup, Amazon EFS, Amazon DynamoDB

@ SAP-C03 D3 T3.4 applied tradeoff
S: A company runs 400 EC2 instances with EBS volumes. Policy requires daily snapshots kept 14 days and quarterly snapshots kept 3 years for audits. Quarterly snapshots are almost never restored, and an audit restore that takes up to three days is acceptable. The company wants automation with no custom code and the lowest snapshot storage cost. Which solution meets these requirements?
A: Create an Amazon Data Lifecycle Manager policy with a daily schedule that archives every snapshot to the EBS Snapshots Archive tier one day after creation and retains it for 3 years
B: Create an Amazon Data Lifecycle Manager policy with a daily schedule kept 14 days and a quarterly schedule that moves snapshots to the EBS Snapshots Archive tier for 3 years
C: Create an Amazon Data Lifecycle Manager policy with daily snapshots kept 14 days and a Recycle Bin retention rule that keeps deleted snapshots for 3 years as an audit copy
D: Create an Amazon Data Lifecycle Manager policy with daily and quarterly schedules in the standard tier, and enable fast snapshot restore on the quarterly snapshots for audits
K: B
G: ## Standard tier versus archive tier
- **Standard tier** snapshots are incremental: each one stores only the blocks changed since the previous snapshot of the volume, so daily snapshots are cheap.
- **EBS Snapshots Archive** stores a **full** copy of the snapshot at a much lower price per GB. Archived snapshots have a **90-day minimum**, and restoring one to the standard tier takes **24 to 72 hours** before it can be used.
Archive pays off for snapshots kept a long time and rarely restored, such as monthly, quarterly or yearly copies. It is a bad fit for frequent snapshots, because each archived copy is full size instead of incremental.
## Data Lifecycle Manager
Amazon Data Lifecycle Manager (DLM) creates, retains and deletes EBS snapshots and EBS-backed AMIs on schedules. A snapshot policy can have several schedules, and a schedule can include an archive rule that moves its snapshots to the archive tier for a set retention.
W: Two DLM schedules with quarterly archiving: daily snapshots stay incremental in the standard tier for 14 days, and the long-lived quarterly snapshots move to the cheaper archive tier, where a 24 to 72 hour restore fits the three-day audit window.
X: A=Archive every daily snapshot: archived snapshots are full copies, so 1,000+ full-size copies per volume cost far more than incremental standard snapshots, and the 3-year retention ignores the 14-day policy.
C=Recycle Bin as long-term retention: Recycle Bin protects snapshots from accidental deletion for a set period; deleted snapshots in it are billed at the standard rate and it is not a scheduled retention or archive mechanism.
D=Standard tier with fast snapshot restore: fast snapshot restore is billed per snapshot per Availability Zone per hour and speeds up restores the audit does not need, so it raises cost instead of lowering it.
T: Keep frequent snapshots incremental in the standard tier and use DLM archive rules for long-retention, rarely restored snapshots.
V: Amazon Data Lifecycle Manager, Amazon EBS, Amazon EC2

A backup plan rule can include a **copy action** that copies each recovery point it creates to a vault in another Region or account. The copy has its own lifecycle (retention, optional cold storage) independent of the source.

- The in-Region daily rule serves operational restores (24-hour RPO).

W: Weekly rule with a copy action: one cross-Region copy per week meets the 7-day RPO and the four-restore-point requirement at a quarter of the transfer and storage of daily copies.

B=S3 replication on the vault: a backup vault is not an S3 bucket, so S3 Cross-Region Replication and S3 lifecycle rules cannot be configured on it.
C=DLM cross-Region copy: Data Lifecycle Manager manages EBS snapshots and EBS-backed AMIs only; it cannot copy RDS or DynamoDB backups.

@ SAP-C03 D4 T4.2 advanced use-case
S: A company runs 30 stateless microservices on one Amazon EKS cluster in us-east-1, deployed by Argo CD from a Git repository, with images in Amazon ECR and data in an Aurora global database. A new requirement sets an RTO of 15 minutes for a Regional outage. Rebuilding a cluster and its add-ons during a test took over two hours. Which design meets the RTO with the least operational effort?
A: Add a managed node group in us-west-2 subnets to the existing cluster, so pods can be scheduled in the second Region when us-east-1 nodes become unavailable
B: Take scheduled Velero backups of the cluster to S3 with Cross-Region Replication, and restore them into a new EKS cluster created in us-west-2 during a disaster
C: Run a second EKS cluster in us-west-2 synced by Argo CD from the same repository, replicate images with ECR replication, and fail over DNS with Route 53 health checks
D: Use EKS Pod Identity associations in both Regions so the pods can authenticate in us-west-2, and redeploy the manifests there when the primary Region fails
K: C
G: ## What a Regional EKS failure needs
An EKS cluster's control plane runs in one Region (spread across Availability Zones). A cluster cannot span Regions, so Regional DR means a **second cluster** in another Region.
How fast that cluster can serve traffic decides the RTO:
- **Backup and restore** (for example Velero): cheap, but cluster creation, add-ons, node scaling and restore all happen during the outage, which takes hours.
- **Warm standby / active-passive**: a running cluster in the DR Region with the same workloads, perhaps scaled down, ready to receive traffic.
## Keeping two clusters identical
GitOps tools such as Argo CD or Flux apply the same manifests to both clusters from one repository, so configuration does not drift. **ECR replication** copies images to the DR Region, so the DR cluster does not pull from the failed Region. **Route 53** failover records with health checks (or Application Recovery Controller) move users.
W: Second cluster kept in sync by GitOps: the DR cluster is already running with identical workloads and local images, so failover is a DNS change that fits within 15 minutes.
X: A=Node group in another Region: EKS node groups must use subnets of the cluster's VPC in the cluster's Region, and the control plane would still fail with us-east-1.
B=Velero backup and restore: it is a valid backup method, but creating the cluster, installing add-ons and restoring during the outage repeats the two-hour rebuild that already missed the RTO.
D=Pod Identity plus redeploy: Pod Identity handles IAM credentials for pods, not cluster availability; a cluster must still exist in us-west-2 and be built during the outage.
T: For EKS Regional DR with a short RTO, keep a second cluster running in the DR Region, synced by GitOps, with replicated images and DNS failover.
V: Amazon EKS, Amazon ECR, Amazon Route 53, Amazon Aurora

@ SAP-C03 D4 T4.2 advanced tradeoff
S: A platform team runs all production workloads on a single large Amazon EKS cluster in one Region. Last quarter, a faulty cluster-wide add-on update and a misconfigured admission webhook each caused a full outage for every service. The team wants to limit the impact of cluster-level failures and upgrade clusters without risking all traffic at once, while staying in one Region for data residency. Which approach best meets these goals?
A: Split workloads across separate managed node groups for each team inside the existing cluster, and apply add-on updates to one node group at a time
B: Enroll the cluster in EKS extended support so that Kubernetes version upgrades can be postponed until the team has more time for testing

D: Run two or more identical clusters in the Region behind Route 53 weighted records, and shift traffic away from one cluster before changing it

G: ## Blast radius of a cluster
Some failures affect a whole cluster regardless of how many nodes or Availability Zones it uses: a broken admission webhook, a bad cluster-wide add-on (CNI, DNS, ingress controller), an API server overload or a failed version upgrade. Spreading nodes across AZs does not help, because the shared layer is the cluster itself.
## Multi-cluster within one Region
Running several identical clusters ("cells") and spreading traffic across them limits a cluster-level failure to that cluster's share of traffic.
- Traffic is split with Route 53 weighted records, or weighted target groups on a load balancer.
- For an upgrade, set one cluster's weight to zero, upgrade and test it, then shift traffic back and repeat for the next cluster (a blue/green cluster upgrade).
- GitOps keeps all clusters identical.
W: Multiple clusters with weighted routing: a cluster-wide fault or a failed upgrade affects only the cluster that has it, and traffic can be drained from a cluster before any change, all within the same Region.
X: A=Node groups per team: node groups separate compute, but webhooks, cluster-wide add-ons and the control plane are still shared, so the same faults would again break every service.
B=Extended support: it postpones version upgrades at extra cost but does nothing about add-on or webhook failures and still upgrades everything at once later.
C=Control plane logging and alarms: faster detection shortens an outage but does not limit it; every service still fails while the faulty change is rolled back.
T: To contain cluster-level failures, run multiple identical clusters and shift traffic between them, rather than adding node groups to one cluster.
V: Amazon EKS, Amazon Route 53

Which design meets these requirements?
A: Create one ECS cluster with a capacity provider in each Region, pull images from the eu-west-1 ECR repository, and use Route 53 latency records for the two load balancers
B: Run an ECS cluster, service and ALB in each Region, replicate images with ECR replication, and add both ALBs as endpoint groups of an AWS Global Accelerator
C: Run the ECS service only in eu-west-1 with the deployment circuit breaker enabled, so failed tasks are automatically relaunched in eu-central-1 during an outage
D: Run an ECS service in each Region that pulls images from the eu-west-1 ECR repository, and put both ALBs behind one CloudFront distribution with an origin group
K: B
G: ## ECS is Regional
An ECS cluster, its services and capacity providers all live in one Region. Multi-Region ECS means a separate cluster and service in each Region, deployed by the same pipeline or infrastructure as code.
## Removing cross-Region dependencies
- **Images**: ECR replication copies images to a repository in each Region, so task launches do not depend on the other Region's registry.
- **Data**: DynamoDB global tables replicate writes between Regions for active-active use.
## Fast failover without DNS
AWS Global Accelerator gives static anycast IPs. Each Region's ALB is an endpoint in a Regional endpoint group. Health checks stop sending traffic to an unhealthy Region within seconds, and clients keep the same IPs, so cached DNS answers do not slow failover. Traffic dials can also drain a Region on purpose.
W: Per-Region ECS stacks with Global Accelerator: both Regions serve traffic, images come from a local ECR replica, and Global Accelerator health checks move traffic quickly without waiting for DNS caches to expire.
X: A=One cluster across Regions: ECS clusters and capacity providers are Regional, and pulling images from eu-west-1 keeps a dependency on the failed Region; latency records also rely on DNS TTLs.
C=Circuit breaker relaunch: the deployment circuit breaker rolls back failed deployments within a service; it never moves tasks to another Region, and the design is not active-active.
D=Shared eu-west-1 repository with CloudFront: new tasks in eu-central-1 cannot pull images when eu-west-1 fails, and CloudFront origin failover applies only to GET, HEAD and OPTIONS requests, not to API writes.
T: Multi-Region ECS means a full stack per Region with replicated images and data, and Global Accelerator for fast, DNS-independent failover.

@ SAP-C03 D4 T4.3 advanced use-case
S: A company plans its first AWS Fault Injection Service experiment in production: a network disruption on the EC2 instances of a checkout service that runs across three Availability Zones. Leadership requires that the experiment affects only a small share of capacity at first and stops automatically if customers are affected. Which experiment template configuration meets these requirements?
A: Target instances by tag with a selection mode of ALL, and assign an on-call engineer to watch dashboards and stop the experiment manually if errors appear
B: Target instances by tag with a selection mode of PERCENT(10), and set a stop condition on a CloudWatch alarm for checkout error rate and p99 latency
C: Target instances by tag with a selection mode of COUNT(1), and set a stop condition on a CloudWatch alarm for CPU utilization of the targeted instances
D: Target instances by tag with a selection mode of PERCENT(10), and add an EventBridge rule that deletes the experiment template when an error alarm fires
K: B
G: ## Parts of an FIS experiment template
- **Actions**: what to do (for example `aws:network:disrupt-connectivity`, `aws:ec2:stop-instances`), with duration and order.
- **Targets**: which resources, chosen by ARN, tags or filters, plus a **selection mode**: `ALL`, `COUNT(n)` or `PERCENT(n)`. A small count or percentage limits the blast radius.
- **Stop conditions**: CloudWatch alarms. If an alarm goes into the ALARM state while the experiment runs, FIS stops the experiment.
- **IAM role**: the permissions FIS uses to act on targets.
## Choosing the stop condition
The alarm should measure **customer impact** (error rate, latency, failed orders), the same metrics that define the steady state. An alarm on the direct effect of the fault (for example CPU of a stressed instance) either fires immediately or says nothing about customers.
W: PERCENT(10) with a customer-impact stop condition: only a tenth of the matching instances are disrupted, and FIS halts the experiment by itself as soon as the error-rate or latency alarm enters ALARM.
X: A=ALL with manual stop: every tagged instance is disrupted at once, and a human watching dashboards reacts more slowly and less reliably than an automatic stop condition.
C=CPU alarm as stop condition: a network disruption need not change CPU on the targets, and CPU says nothing about whether customers see errors, so the stop condition protects nothing.
D=Delete the template on alarm: deleting a template does not stop an experiment that is already running; FIS stop conditions are the built-in way to halt it.
T: Limit blast radius with tag-based targets and COUNT or PERCENT selection, and use CloudWatch alarms on customer-facing metrics as FIS stop conditions.
V: AWS Fault Injection Service, Amazon CloudWatch, Amazon EC2

@ SAP-C03 D4 T4.3 advanced troubleshooting
S: A team ran the AWS Fault Injection Service "AZ Availability: Power Interruption" scenario against a staging copy of an order platform. After the run, engineers disagreed whether it passed: some pointed to instance replacements, others to a short error spike, and nobody knew how much impact was acceptable. Which TWO changes make the next experiment produce a clear pass or fail result? (Select TWO)
A: Before the run, write a steady-state hypothesis with measurable customer metrics and limits, such as order success rate above 99.5 percent and p99 latency under 400 ms during the disruption
B: Measure success by whether all EC2 instances in the impaired Availability Zone are replaced within the scenario duration, because replacement proves that self-healing works
C: Express the hypothesis limits as CloudWatch alarms, use them as the experiment's stop conditions, and compare the metrics during the run with the baseline period before it
D: Expand the experiment to impair all three Availability Zones at once so that any weakness produces a larger, unmistakable error spike that every engineer can recognize
E: Use the AWS Config compliance status of the affected resources at the end of the experiment as the pass or fail signal, because Config records every configuration change
K: A,C
G: ## The steady-state hypothesis
Chaos engineering starts with a **steady state**: the normal, measurable output of the system that customers care about (orders per minute, success rate, latency). The **hypothesis** states that this steady state will hold, within stated limits, while a specific fault is injected.
- Written before the run, with numbers, so the result is objective.
- Based on business or customer metrics, not infrastructure events.
## Turning the hypothesis into the experiment
- Create CloudWatch alarms at the hypothesis limits and attach them to the FIS template as **stop conditions**. If the steady state is broken, the experiment stops and the result is a fail.
- Compare metrics during the fault with a baseline period before it to see how much the system degraded.
## Example
Hypothesis: "During an AZ power interruption, order success stays at or above 99.5% and p99 latency below 400 ms." A short spike to 98% success breaks it, which is a clear fail and a finding to fix.
W: A=Measurable steady-state hypothesis: agreeing on customer metrics and limits before the run turns "did it pass" into a comparison against numbers rather than opinions.
C=Hypothesis as alarms and stop conditions: the same limits become CloudWatch alarms, so FIS stops when they are breached and the baseline comparison shows exactly how far the metrics moved.
X: B=Instance replacement as success: replacement is an infrastructure event; customers can still see errors while instances are replaced, so it does not prove the business kept working.
D=Impair all AZs: it makes the experiment unsafe and unrealistic for the scenario, and a bigger spike still gives no agreed threshold for pass or fail.
E=Config compliance as the signal: AWS Config tracks resource configuration, not request success or latency, so it cannot tell whether the steady state held.
T: Define a numeric steady-state hypothesis on customer metrics before injecting faults, and encode its limits as CloudWatch alarms used as FIS stop conditions.
V: AWS Fault Injection Service, Amazon CloudWatch

@ SAP-C03 D4 T4.3 advanced use-case
S: A payments application spans three AWS accounts: one for the API tier on Amazon EKS, one for Amazon RDS databases and one for shared networking. A central resilience team in a fourth account wants to run one AWS Fault Injection Service experiment that disrupts resources in all three accounts at the same time, with one set of stop conditions and one experiment record. Which solution meets these requirements?
A: Create a multi-account experiment template in the resilience account with target account configurations, using roles in each target account that trust the resilience account's FIS role
B: Create an experiment template in each of the three accounts and start them together from an AWS Step Functions state machine in the resilience account at the same timestamp
C: Deploy the same experiment template to all three accounts with CloudFormation StackSets and give each account its own stop condition alarm on its local metrics
D: Share the target resources from the three accounts with the resilience account through AWS RAM, so a single-account experiment template there can select them as targets
K: A
G: ## Multi-account FIS experiments
AWS Fault Injection Service supports experiments that act on resources in several accounts from one **orchestrator account**.
- The template's account targeting is set to multi-account.
- A **target account configuration** is added for each target account, naming an IAM role in that account.
- The experiment role in the orchestrator account assumes those roles to run actions; each target account role must trust it and allow the needed actions.
- Stop conditions, logging and the experiment record live in the orchestrator account, so the whole experiment is started, watched and stopped as one unit.
## Why one experiment matters
A real incident hits all tiers at once. Separate experiments started in parallel each have their own stop conditions, so one may keep running after another has stopped, and their results must be stitched together by hand.
W: Multi-account template with target account configurations: one experiment in the resilience account acts on resources in all three accounts through their roles, under a single set of stop conditions and one experiment record.
X: B=Step Functions starting three experiments: they run as three separate experiments with separate stop conditions and records, so a breach in one account does not stop the others.
C=StackSets copies per account: StackSets only distributes templates; each account still runs its own experiment with its own local stop condition and result.
D=RAM-shared targets: FIS selects targets in the accounts named by the template, and sharing resources through RAM does not make them FIS targets of another account.
T: To inject faults across accounts as one controlled experiment, use an FIS multi-account template with target account configurations from an orchestrator account.

@ SAP-C03 D5 T5.3 advanced tradeoff
S: A media company added CloudWatch RUM to a website that serves about 60 million sessions a month. The first bill was far above budget. Product managers need trend data on page load performance and error rates, not every session, and privacy rules forbid collecting more user data than needed. Which change best reduces cost while keeping useful real-user insight?
A: Shorten the retention of the RUM app monitor's data in CloudWatch Logs to one day so that the stored telemetry is deleted before it can be billed
B: Replace RUM with a Synthetics canary that loads the home page every minute, because canaries represent the average experience of all real users
C: Lower the app monitor's session sample rate to a small percentage and collect only the telemetry types needed, such as performance and errors
D: Keep every session but disable the X-Ray integration of the app monitor, because RUM bills each event according to its number of trace segments
K: C
G: ## How CloudWatch RUM is billed and tuned
CloudWatch RUM is billed by the number of **RUM events** collected (page views, performance entries, errors, HTTP requests and so on). Two app monitor settings control volume:
- **Session sample rate**: the share of user sessions that send data. For trend analysis on high-traffic sites, a few percent of sessions already gives statistically useful numbers.
- **Telemetry types**: performance, errors and HTTP can be enabled separately, so only needed data is collected.
Collecting fewer sessions and fewer event types also limits how much user data is gathered, which supports privacy requirements. Cookies, which link events into sessions, are optional as well.
## Example
At a 5% sample rate, 60 million sessions become about 3 million sampled sessions, still plenty for load time and error-rate trends per page, browser and country.
W: Sample rate and telemetry types: billing scales with collected events, so sampling a small share of sessions and limiting event types cuts cost roughly in proportion while preserving trends and collecting less user data.
X: A=Shorter log retention: RUM charges for events as they are collected; deleting stored data later does not remove the ingestion charge.
B=Replace RUM with a canary: a canary measures one scripted session from AWS, not real users on their own browsers, devices and networks, so it cannot show differences across real users.
D=Disable X-Ray: RUM billing is per RUM event, not per trace segment, so disabling the X-Ray integration does not address the volume of events from 60 million sessions.
T: Control CloudWatch RUM cost with the session sample rate and selected telemetry types; sampling keeps trends while collecting less data.
V: Amazon CloudWatch RUM
