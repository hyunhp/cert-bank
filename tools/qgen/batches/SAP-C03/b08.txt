@ SAP-C03 D1 T1.1 advanced use-case
S: A media company keeps 2 million image files in an S3 bucket in a shared data account. Once a month every file must pass through two existing Lambda functions in sequence, resize and then watermark, each with retries on throttling. The run must finish overnight under the account's concurrency quota of 1,000, a few hundred corrupt files must not stop it, and the team needs a list of failed files. Which solution needs the LEAST custom orchestration code?
A: Use a Standard workflow whose Distributed Map reads an S3 inventory manifest, runs both functions per item, sets a tolerated failure percentage, and writes results
B: Use a Step Functions Express workflow with an inline Map state that lists the bucket prefix, runs both functions for each object, and catches errors in a Catch block
C: Create an S3 Batch Operations job on an S3 inventory manifest that invokes a new wrapper function per object, which calls both functions and writes a completion report
D: Run an AWS Glue Python shell job that lists the objects, calls both functions for each key from a thread pool, and writes failed keys to a DynamoDB table
K: A
G: ## Two ways to fan out over millions of S3 objects
Step Functions has two Map modes:
- **Inline Map** runs iterations inside the parent execution and shares its history, so it suits small arrays.
- **Distributed Map** runs each iteration (or batch) as a **child workflow execution** with its own history. Its `ItemReader` reads large S3 sources such as a CSV/JSON file, an S3 inventory manifest or an object listing, and it runs up to 10,000 child executions in parallel by default.
Distributed mode is supported only in **Standard** parent workflows. `ToleratedFailurePercentage` lets the Map Run continue until the failed share exceeds a set value, and `ResultWriter` writes succeeded and failed item results to S3.
## Working the numbers
2 million files x two steps of a few seconds each, capped by 1,000 concurrent Lambda invocations, is a few hours, so it fits overnight. Set the Map's maximum concurrency to stay below the quota and add `Retry` on `Lambda.TooManyRequestsException` in each task.
## Example
Child workflow: `Resize` task -> `Watermark` task, each with a Retry block. The parent Distributed Map reads the inventory manifest, tolerates 1% failures and writes the failed keys to `s3://ops/results/`.
W: Distributed Map: child workflows give each file its own two-step sequence with per-step retries, the S3 inventory reader handles millions of items, the failure threshold keeps corrupt files from stopping the run, and ResultWriter produces the failure list without custom code.
X: B=Express with inline Map: Express workflows run for at most five minutes, far shorter than an overnight run, and an inline Map cannot read millions of S3 objects as its input.
C=S3 Batch Operations: Batch Operations invokes one function per object, so the two-step sequence and per-step retries must be coded in a new wrapper function, which is the custom orchestration the team wants to avoid.
D=Glue Python shell: listing, threading, retries and failure tracking are all hand-written code, and a single job process becomes the bottleneck and the failure point for the whole run.
T: For multi-step processing of millions of S3 objects, use a Standard workflow with a Distributed Map, a failure threshold and ResultWriter.
V: AWS Step Functions, AWS Lambda, Amazon S3

@ SAP-C03 D1 T1.1 advanced use-case
S: A company has 70 workload accounts in AWS Organizations, and each account sends order events from its applications to its default event bus. A fraud team in a central account needs every order event from all current and future accounts in its own EventBridge rules in near real time. Security forbids resource policies that list individual account IDs, and the fraud team will not change application code. Which solution meets these requirements with the LEAST operational overhead?
A: Create a custom bus in the central account with a policy that lists every workload account ID, and update it from a Lambda function triggered when new accounts are created
B: Create a custom bus in the central account whose policy allows PutEvents for the organization ID, and deploy a forwarding rule to every account with StackSets automatic deployment
C: Create an organization trail in CloudTrail and build rules in the central account that match the order events recorded for API calls in every workload account
D: Have every workload application publish its order events to an SNS topic in the central account, and subscribe the fraud team's queue with filter policies per event type
K: B
G: ## Cross-account event delivery in EventBridge
An event bus in a receiving account accepts events from other accounts only when its **resource-based policy** allows `events:PutEvents`. The policy can name accounts or a whole organization with the `aws:PrincipalOrgID` condition, so accounts that join later are allowed automatically.
On the sending side, a rule on the source bus targets the receiver's bus ARN and uses an IAM role that may call `PutEvents` on it. The fraud team then writes its own rules on its own bus.
## Rolling out the sender rules
CloudFormation StackSets with service-managed permissions and automatic deployment create the forwarding rule and role in every account of the target OUs, including accounts added later. This is configuration, not application code.
## Example
Bus policy condition: `"StringEquals": {"aws:PrincipalOrgID": "o-a1b2c3d4"}`. Each account rule pattern: `{"source": ["com.shop.orders"]}` with target `arn:aws:events:us-east-1:111122223333:event-bus/fraud`.
W: Organization-wide bus policy with StackSets: the PrincipalOrgID condition admits current and future accounts without listing IDs, StackSets automatic deployment adds the forwarding rule to new accounts, and applications keep sending to their default bus unchanged.
X: A=Account-ID list kept by Lambda: it breaks the explicit rule against listing individual account IDs and adds a custom function that must handle every account event correctly.
C=CloudTrail organization trail: CloudTrail records AWS API calls, not the custom order events applications send to EventBridge, so the fraud team would never see the order content.
D=SNS topic per event: publishing to SNS means changing every application's code, and the fraud team would lose EventBridge rule matching on its own bus.
T: Forward events org-wide with a receiving bus policy keyed on aws:PrincipalOrgID and sender rules deployed by StackSets automatic deployment.
V: Amazon EventBridge, AWS Organizations, AWS CloudFormation

@ SAP-C03 D1 T1.2 advanced use-case
S: A retailer's finance analysts want to ask questions such as "Which stores missed their margin target last quarter?" in plain language over 40 well-documented tables in an Amazon Redshift Serverless data warehouse. Answers must reflect data loaded within the last hour, the data must not be copied into another store, and the platform team does not want to write or maintain its own text-to-SQL prompts. Which solution meets these requirements?
A: Export the 40 tables to S3 as CSV files every night, build a vector knowledge base over the files with semantic chunking, and answer questions with RetrieveAndGenerate
B: Build a Bedrock agent with a Lambda action group whose code sends schema prompts to a model, runs the generated SQL through the Redshift Data API, and summarizes the rows
C: Connect an Amazon Bedrock knowledge base to the Redshift Serverless workgroup as a structured data store, so it turns each question into SQL and answers from live results
D: Fine-tune a foundation model on a year of historical query results so that it answers margin questions directly without sending queries to the warehouse at runtime
K: C
G: ## Structured retrieval for RAG
Amazon Bedrock Knowledge Bases can use two kinds of sources:
- **Unstructured** documents that are chunked, embedded and stored in a vector index.
- **Structured data stores** such as Amazon Redshift. The knowledge base converts the user's question into a SQL query for the store, runs it, and uses the returned rows to generate the answer.
With a structured store nothing is copied or embedded: every answer comes from the current warehouse data, and AWS manages the natural-language-to-SQL step. Good table and column descriptions improve the generated queries.
## When each fits
- Narrative content such as manuals or policies: vector knowledge base.
- Facts that live in tables, aggregations, filters by date or store: structured knowledge base on the warehouse.
W: Structured data store knowledge base: the knowledge base generates and runs SQL against the warehouse for every question, so answers include data loaded minutes ago, no copy is made, and the text-to-SQL logic is managed by Bedrock.
X: A=Nightly CSV export to a vector store: it copies the data, answers are up to a day old, and vector similarity over CSV rows cannot compute aggregates such as margin by store.
B=Agent with custom text-to-SQL: it works, but the team must write and maintain the schema prompts, the SQL generation and the error handling, which is exactly what it wants to avoid.
D=Fine-tuned model: a model trained on old results has no access to data loaded in the last hour and cannot produce exact current figures.
T: For natural-language questions over warehouse tables, connect a Bedrock knowledge base to the structured store instead of copying data into a vector index.
V: Amazon Bedrock, Amazon Redshift

@ SAP-C03 D1 T1.2 advanced tradeoff
S: A travel company's support assistant uses a large Amazon Bedrock model for one narrow task: classifying and summarizing booking-change requests. Model invocation logging to S3 has captured six months of prompts and the large model's good responses. Token cost and latency are now too high at current volume. The company wants a smaller, faster model with similar quality on this task, and nobody has time to label new training data. Which approach meets these requirements?
A: Run a continued pre-training job for a smaller model on the raw booking documents in S3, so that the model learns the travel vocabulary without any labeled examples
B: Run an Amazon Bedrock Model Distillation job with the large model as teacher and a smaller supported model as student, using the invocation logs as training data
C: Switch to a smaller model and add the best 50 logged responses as few-shot examples in every prompt, keeping the large model as a fallback for low-confidence answers
D: Buy Provisioned Throughput for the large model to lower the price per token, and call it through cross-Region inference to cut latency at peak booking periods
K: B
G: ## Distillation in one sentence
Model distillation transfers knowledge from a large **teacher** model to a smaller **student** model for one use case: Bedrock generates responses from the teacher (or reuses existing ones) and fine-tunes the student on them.
## Data options
- Provide prompts in `.jsonl` files and let Bedrock generate teacher responses, optionally with labeled golden examples.
- Use **model invocation logs** stored in S3: existing teacher responses become training data, so no new labeling is needed.
The result is a custom model that is smaller, faster and cheaper per request, tuned for the task the logs describe.
## Why the other levers fall short
Prompt engineering adds input tokens to every call, continued pre-training teaches vocabulary but not the task's output format, and Provisioned Throughput keeps the same large model.
W: Model Distillation from invocation logs: the logged teacher responses already show the desired behavior, so Bedrock can fine-tune a smaller student for this narrow task without manual labels, cutting both cost and latency.
X: A=Continued pre-training: it adapts a model to domain text, but unlabeled documents do not teach the classification and summary format the teacher produces, so quality on the task is not preserved.
C=Few-shot prompting a small model: 50 examples in every prompt add thousands of input tokens to each call, which eats much of the saving, and the student never learns the teacher's behavior beyond those examples.
D=Provisioned Throughput for the large model: it reserves capacity for the same large model, so latency per request stays high and the cost only drops if utilization is constant.
T: When a large model already produces good answers for a narrow task, distill it into a smaller model using its invocation logs.
V: Amazon Bedrock

@ SAP-C03 D1 T1.3 advanced use-case
S: On-premises analytics servers upload about 30 TB per month to Amazon S3 in us-east-1 over the internet. The company has a Direct Connect private VIF into a shared-services VPC. Security now requires that on-premises S3 traffic uses private IP addresses over Direct Connect without changing the S3 endpoint names in hundreds of scripts. EC2 instances in that VPC use an S3 gateway endpoint, which must remain their path. Which solution meets these requirements?
A: Keep only the gateway endpoint and advertise the S3 prefix list ranges to the on-premises router over the private VIF, so that on-premises traffic is routed through the gateway endpoint
B: Create an S3 interface endpoint with standard private DNS, so that every client resolves S3 to the endpoint, and forward on-premises S3 queries to a Resolver inbound endpoint
C: Create an S3 interface endpoint without private DNS and update the on-premises scripts to use the endpoint-specific DNS names that start with bucket.vpce in each request
D: Create an S3 interface endpoint with private DNS only for inbound endpoints, add a Route 53 Resolver inbound endpoint, and forward on-premises S3 DNS queries to it
K: D
G: ## Gateway and interface endpoints for S3
- A **gateway endpoint** is a route-table target. It is free, but only traffic that originates in the VPC can use it; on-premises networks cannot reach S3 through it.
- An **interface endpoint** (PrivateLink) places ENIs with private IPs in your subnets, so on-premises clients can reach it over Direct Connect or VPN. It has hourly and per-GB charges.
## Private DNS options
With private DNS enabled, the regional names such as `s3.us-east-1.amazonaws.com` resolve to the interface endpoint's private IPs, so scripts keep their endpoint names. The option **Enable private DNS only for inbound endpoints** applies that private resolution only to queries arriving through a **Route 53 Resolver inbound endpoint** (on-premises), while in-VPC clients keep resolving to the public S3 addresses that the gateway endpoint carries. The option requires a gateway endpoint in the VPC.
## Example
On-premises DNS forwards `s3.us-east-1.amazonaws.com` to the inbound endpoint IPs `10.20.1.10` and `10.20.2.10`; EC2 traffic keeps using the free gateway endpoint.
W: Inbound-only private DNS: on-premises queries through the inbound Resolver endpoint resolve S3 to the interface endpoint's private IPs over Direct Connect, scripts keep their names, and in-VPC traffic stays on the gateway endpoint.
X: A=Advertising prefixes to a gateway endpoint: gateway endpoints cannot be reached from outside the VPC, so routing on-premises traffic toward them does not work.
B=Standard private DNS: in-VPC instances would also resolve S3 to the interface endpoint, moving their traffic off the free gateway endpoint onto per-GB interface endpoint charges.
C=Endpoint-specific names: it reaches S3 privately but forces edits to hundreds of scripts, which the requirement rules out.
T: Use an S3 interface endpoint with private DNS only for inbound endpoints to serve on-premises clients while VPC traffic keeps the gateway endpoint.
V: Amazon S3, AWS PrivateLink, Amazon Route 53, AWS Direct Connect

@ SAP-C03 D1 T1.4 advanced use-case
S: A platform team runs 25 application VPCs in several accounts. Each VPC has a zonal NAT gateway and public subnet per Availability Zone, and teams that expand into a new AZ often forget the NAT gateway and routes. A new baseline forbids public subnets in application VPCs and forbids new per-GB charges on egress. One VPC also needs private NAT to an on-premises network with overlapping CIDRs. Which design needs the LEAST ongoing effort?
A: Create a regional NAT gateway in every VPC, including the overlapping-CIDR VPC, and configure it in manual mode with private connectivity for the on-premises network
B: Centralize egress in a shared VPC with zonal NAT gateways per AZ, route all application VPCs through a transit gateway, and remove their NAT gateways
C: Replace the zonal NAT gateways in application VPCs with one regional NAT gateway each in automatic mode, and keep a zonal private NAT gateway in the overlapping VPC
D: Keep zonal NAT gateways and add a Lambda function, triggered by subnet creation events, that adds a public subnet, NAT gateway, and routes in each new AZ
K: C
G: ## Zonal versus regional NAT gateways
A **zonal** NAT gateway lives in one AZ and one public subnet. High availability means one NAT gateway per AZ plus per-AZ routes, repeated every time workloads enter a new AZ.
A **regional** NAT gateway (availability mode `regional`):
- Needs **no public subnet**; it has its own route table with a route to the internet gateway.
- Uses **one NAT ID** in the route tables of every AZ and expands automatically to AZs where workloads have ENIs (expansion can take up to 60 minutes; until then traffic is processed in another AZ).
- Supports up to 32 IP addresses per AZ in automatic or manual mode.
- Does **not support private NAT**; private connectivity still needs a zonal NAT gateway.
## Example
`aws ec2 create-nat-gateway --vpc-id vpc-1234 --availability-mode regional` replaces three zonal gateways and three routes with one gateway and one route entry.
W: Regional NAT plus one zonal private NAT: regional gateways remove public subnets and follow workloads into new AZs automatically, and the overlapping-CIDR VPC keeps a zonal private NAT gateway because regional mode cannot do private NAT.
X: A=Regional NAT for private connectivity: regional NAT gateways do not support private NAT, so the overlapping-CIDR VPC could not reach the on-premises network this way.
B=Centralized egress through a transit gateway: it removes public subnets from application VPCs, but every egress gigabyte now also pays transit gateway data processing, which the baseline forbids.
D=Lambda that adds zonal NAT gateways: it keeps public subnets in every application VPC, breaking the new baseline, and adds custom automation to maintain.
T: Regional NAT gateways give multi-AZ egress without public subnets; keep zonal NAT gateways only where private NAT is needed.
V: Amazon VPC

@ SAP-C03 D1 T1.4 advanced use-case
S: A company runs 120 VPCs across 40 accounts in four Regions. Production and development VPCs must never route to each other, both must reach shared services, and a new VPC must land in the right network automatically from its Environment tag, without an engineer editing route tables. The network team wants one central policy document that defines the network in all four Regions. Which solution meets these requirements?
A: Deploy a transit gateway in each Region with separate route tables per environment, peer the transit gateways across Regions, and add static routes on each peering attachment
B: Use AWS Cloud WAN with one segment for all VPCs, and enforce the separation with security groups that reference the Environment tag values of the peer VPCs
C: Share subnets from one large VPC per Region through AWS RAM, and separate the environments with network ACLs that a StackSet maintains in every account
D: Use AWS Cloud WAN with production, development, and shared services segments, attachment policies that map the Environment tag, and route sharing from the shared segment only
K: D
G: ## Cloud WAN building blocks
AWS Cloud WAN builds a global **core network** from one JSON **core network policy**:
- **Segments** are isolated routing domains (like VRFs) that span the Regions you choose. Attachments in one segment cannot reach another segment unless the policy shares routes between them.
- **Attachment policies** map new VPC attachments to a segment by rules such as tag values, so a VPC tagged `Environment=prod` joins the production segment automatically (with optional acceptance).
- **Segment actions** such as `share` let both production and development reach a shared services segment while staying separated from each other.
## Compared with transit gateways
Multiple transit gateways need per-Region route tables, peering attachments and static routes that engineers maintain by hand; Cloud WAN derives all of that from the single policy.
W: Cloud WAN segments with tag-based attachment policies: one policy defines segments in all four Regions, the Environment tag places each new VPC automatically, and sharing only the shared services segment keeps production and development apart.
X: A=Per-Region transit gateways: peering attachments need static routes and per-Region route tables that engineers keep editing, and nothing places a new VPC by its tag.
B=One segment with security groups: a single segment routes all VPCs to each other, and security groups cannot reference tags, so the routing separation is not met.
C=Shared subnets with network ACLs: environments share one routed VPC, separation depends on large NACL sets in every account, and it is not a central multi-Region policy.
T: For multi-Region segmentation driven by tags from one policy, use Cloud WAN segments, attachment policies and segment sharing.
V: AWS Cloud WAN, AWS Transit Gateway

@ SAP-C03 D1 T1.4 advanced troubleshooting
S: A company sends all traffic between 30 spoke VPCs through an inspection VPC that has AWS Network Firewall endpoints in two Availability Zones and is attached to a transit gateway. After go-live, some long-lived TCP sessions between spokes in different AZs drop intermittently. The design must keep stateful inspection, keep both AZs active, and avoid scripts. Which TWO actions should a solutions architect take? (Select TWO)
A: Enable appliance mode on the inspection VPC's transit gateway attachment, so both directions of each flow use the same Availability Zone and firewall endpoint
B: Convert the firewall rule groups to stateless rules with forward actions, so that return traffic seen in a different zone is no longer checked against session state
C: Give each AZ's transit gateway attachment subnet in the inspection VPC its own route table that sends traffic to the firewall endpoint in that same AZ
D: Turn on security group referencing for the transit gateway, so that the spoke security groups track session state in place of the firewall endpoints
E: Remove the second Availability Zone from the inspection VPC, so that every flow passes one firewall endpoint, and rely on its built-in endpoint redundancy
K: A,C
G: ## Why stateful appliances break with a transit gateway
By default a transit gateway keeps traffic in the source AZ when it forwards into an attached VPC. A flow from a spoke in AZ a goes to the firewall endpoint in AZ a, but the reply from a spoke in AZ b enters the inspection VPC in AZ b and hits the other endpoint, which has never seen the session and drops it. The result is intermittent drops of cross-AZ flows.
## The fix
- **Appliance mode** on the inspection VPC attachment makes the transit gateway pick one AZ for the life of a flow (by a flow hash), so both directions reach the same firewall endpoint.
- Inside the inspection VPC, each AZ's TGW attachment subnet uses a route table whose default route points to the **firewall endpoint in the same AZ**, so the traffic is not sent to an endpoint in another zone.
## Example
`tgw-attach-insp`: `ApplianceModeSupport=enable`; route table `rt-tgw-a`: `0.0.0.0/0 -> vpce-fw-a`; `rt-tgw-b`: `0.0.0.0/0 -> vpce-fw-b`.
W: A=Appliance mode: the transit gateway keeps both directions of a flow in one AZ of the inspection VPC, so the same stateful endpoint sees the request and the reply.
C=Per-AZ route tables to the local endpoint: traffic that the transit gateway delivers into an AZ is inspected by that AZ's endpoint, keeping the path symmetric and both AZs active.
X: B=Stateless rules: it hides the symptom by dropping stateful inspection, which the design must keep.
D=Security group referencing: it lets spoke security groups reference each other across attachments, but does not change which firewall endpoint sees each direction, and it does not work across Network Firewall in an inspection VPC.
E=Single-AZ inspection: it breaks the requirement to keep both AZs active and makes one AZ a single point of failure for all east-west traffic.
T: For stateful inspection behind a transit gateway, enable appliance mode and route each AZ to its own firewall endpoint.
V: AWS Transit Gateway, AWS Network Firewall

@ SAP-C03 D1 T1.5 advanced use-case
S: A payments startup needs a relational database for a new ledger service that runs active-active in us-east-1 and us-east-2. Both Regions must accept writes, reads in either Region must see every committed transaction, and losing one Region must not lose committed data. Developers use PostgreSQL drivers, the company has no DBAs, and it does not want to manage instances, failover, or replication. Which solution meets these requirements?
A: Create an Aurora PostgreSQL global database with write forwarding on the secondary cluster, and use managed failover if the primary Region becomes unavailable
B: Create a DynamoDB global table in multi-Region strong consistency mode and use its PartiQL interface, so that developers keep writing SQL-like statements
C: Run PostgreSQL on EC2 in both Regions with bidirectional logical replication and a conflict-resolution trigger on every ledger table, managed by the platform team
D: Create an Aurora DSQL multi-Region cluster with peered clusters in us-east-1 and us-east-2 and a witness Region, and connect through each Region's endpoint

@ SAP-C03 D5 T5.1 advanced use-case
S: A production CloudFormation stack contains an RDS for PostgreSQL instance, an S3 bucket with audit data, and application resources. Last month a template change renamed the DB instance identifier, and CloudFormation replaced the database, losing data. The company wants stack updates that would replace or delete the database to be blocked, a final snapshot kept if the database is ever removed or replaced anyway, and the audit bucket kept if the stack is deleted. Which THREE actions meet these requirements? (Select THREE)
A: Apply a stack policy that denies Update:Replace and Update:Delete on the database's logical ID, while allowing updates on all other resources in the stack
B: Enable termination protection on the stack, which also blocks any stack update that would replace the database or delete the audit bucket
C: Set both DeletionPolicy and UpdateReplacePolicy to Snapshot on the DB instance, so that a snapshot is taken if the instance is deleted or replaced

F: Set DeletionPolicy to Snapshot on the audit bucket, so that CloudFormation saves its objects to a snapshot before it deletes the bucket

G: ## Three different protections
- **Stack policy**: a JSON policy evaluated during stack **updates**. `Deny` on `Update:Replace` and `Update:Delete` for a logical ID makes any update that would replace or delete that resource fail, while an `Allow` covers the rest. Deny always wins.

E=Retain on the bucket: deleting the stack leaves the audit bucket and its data in place.
X: B=Termination protection: it only blocks deleting the whole stack; updates that replace resources still run.
D=Drift detection: it compares live resources with the template; it does not inspect or block change sets.
F=Snapshot on an S3 bucket: S3 buckets do not support the Snapshot deletion policy, so it gives no protection.

S: A company patches a 400-instance Auto Scaling group each month by building a new AMI. The company wants the refresh to pause after 20% of instances for validation, revert automatically if an error-rate alarm fires, and keep at least 90% healthy capacity. K: C
G: ## Instance refresh with rollback
An instance refresh replaces instances in batches, keeping a **minimum healthy percentage** in service, and can stop at **checkpoints** (for example after 20%) for a set time so you can validate.
**Rollback** reverts instances already replaced to the configuration the group had before the refresh:
- **Auto rollback** runs if the refresh fails or if a CloudWatch **alarm** you list goes into ALARM.
- Rollback is available only when you start the refresh with a **desired configuration**.
- It works only if the group uses a **specific numbered launch template version**; it is not available with `$Latest` or `$Default`, because there would be no fixed previous version to return to.
## Example

X: A=Keeping $Latest: rollback is not available when the group uses $Latest or $Default, so auto rollback cannot be enabled in this setup.
B=Lambda that starts a second refresh: it is custom code and a full forward refresh to the old AMI, slower than built-in rollback.
D=Separate groups with manual traffic moves: it relies on people to move traffic and revert, so nothing reverts automatically when the alarm fires.
T: For automatic rollback of an instance refresh, use a desired configuration with a numbered launch template version, checkpoints and alarms.
