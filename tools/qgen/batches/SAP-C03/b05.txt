@ SAP-C03 D2 T2.4 advanced use-case
S: A national bank is moving its core analytics platform to Amazon S3, Amazon EBS and Amazon RDS. The banking regulator requires that the root key material protecting customer data is never stored in, or recoverable from, the cloud provider's infrastructure, and that the bank can cut off the cloud services' ability to decrypt the data by acting only on infrastructure it controls. The bank also wants to keep native SSE-KMS integration with these services and avoid changing application code. Which solution meets these requirements?
A: Create AWS KMS keys in a custom key store backed by an AWS CloudHSM cluster in the bank's VPC, and delete the CloudHSM cluster if access must be cut off
B: Create AWS KMS keys with imported key material generated in the bank's on-premises HSM, and delete the imported key material from KMS if access must be cut off
C: Create AWS KMS keys in an external key store that uses an XKS proxy in front of the bank's on-premises HSMs, and disconnect the proxy if access must be cut off
D: Encrypt all data on the client side with keys from the bank's on-premises HSMs before upload, and revoke the HSM credentials if access must be cut off
K: C
G: ## Where the key material lives
AWS KMS gives three places for the key material behind a KMS key, and the AWS services that integrate with KMS (S3, EBS, RDS and many more) work the same way with all of them:
- **AWS-managed HSMs (default)**: key material is generated and kept inside the FIPS-validated HSMs that KMS operates. It never leaves them in plaintext, but it does live in AWS infrastructure.
- **Imported key material (BYOK)**: you generate the material yourself and import it. KMS then holds a copy in its HSMs; you can set an expiry or delete it, but while the key is usable the copy is inside AWS.
- **Custom key stores**: either an **AWS CloudHSM key store** (material in a single-tenant CloudHSM cluster that you own, but still in an AWS data center) or an **external key store (XKS)** (material in an HSM or key manager that you run outside AWS).
## How an external key store works
With XKS, every encrypt or decrypt with that KMS key is sent by KMS to an **XKS proxy** you operate, which asks your external key manager to do the cryptographic operation. The root key never enters AWS. If you shut down or disconnect the proxy, or disable the key in your own HSM, KMS can no longer encrypt or decrypt data keys, so new reads of data protected by those keys fail. Services that already hold a plaintext data key in memory (for example an EBS volume that is attached to a running instance) can keep using it until the volume is detached or the instance stops, so plan the cut-off procedure with that in mind.
The trade-off: you own the availability and latency of the proxy and external HSMs. If they fail, every service using those keys fails too, which is why AWS recommends XKS only when a regulation or contract demands it.
W: External key store (XKS): the root key material stays in the bank's own HSMs outside AWS, S3, EBS and RDS keep using normal SSE-KMS integration with no code change, and the bank can cut off all decryption by disconnecting the proxy or disabling the external key.
X: A=CloudHSM key store: the cluster is single-tenant and controlled by the bank, but it runs in an AWS data center, so the key material is stored in the provider's infrastructure and the regulator's first condition fails.
B=Imported key material: KMS keeps a copy of the imported material in its own HSMs for as long as the key is usable, so root key material is stored inside AWS even though the bank can delete it later.
D=Client-side encryption: keys do stay on premises and access can be revoked, but every application must change to encrypt and decrypt data itself, and the services no longer use native SSE-KMS, which breaks the no-code-change requirement.
T: When a regulation says key material must stay outside the cloud provider yet services must keep native KMS integration, use a KMS external key store (XKS) and accept that you now own its availability.
V: AWS KMS, Amazon S3, Amazon EBS, Amazon RDS

@ SAP-C03 D2 T2.4 advanced troubleshooting
S: A healthcare provider in a country with no AWS Region runs its patient platform on an AWS Outposts rack in an in-country data center: EC2 instances with EBS volumes, Amazon RDS for PostgreSQL on Outposts, and S3 on Outposts for documents. A sovereignty audit finds copies of patient data in the parent Region in a neighboring country. Amazon Data Lifecycle Manager takes daily EBS snapshots, and RDS automated backups use default settings. Which change keeps every copy of patient data inside the country?
A: Encrypt the EBS snapshots and RDS backups with a customer managed KMS key that only in-country administrators may use, and keep the current snapshot and backup locations
B: Set the Data Lifecycle Manager policies to create EBS local snapshots on the Outpost, and set the RDS backup target to the Outpost for the database instance's backups
C: Attach an SCP to the platform accounts that denies all actions in the parent Region, so that no snapshot or backup can be written there after the policy takes effect
D: Run a nightly Lambda function that copies each new snapshot and backup from the parent Region to S3 on Outposts and then deletes the copies held in the Region
K: B
G: ## Outposts keep primary data local, but not every copy
An Outposts rack is AWS-owned and AWS-managed hardware in your own data center. It runs a subset of AWS services locally (EC2, EBS, ECS, EKS, RDS on Outposts, S3 on Outposts and others) with the same APIs. Each Outpost is anchored to a **parent Region** over a service link, which carries the control plane, so every API call for Outpost resources is made to the parent Region's endpoints.
Several data-protection features copy data to the parent Region **by default**:
- **EBS snapshots** of volumes on an Outpost are stored in the parent Region. **EBS local snapshots on Outposts** store them in S3 on Outposts instead. Data Lifecycle Manager policies can target the Outpost as the snapshot location, and an IAM policy can deny creating snapshots in the Region.
- **RDS on Outposts** automated backups and manual snapshots go to the parent Region unless you set the **backup target** of the DB instance to the Outpost (`--backup-target outposts`), which keeps them in S3 on Outposts.
- Objects in regular S3 buckets live in the Region; **S3 on Outposts** keeps object data on the rack.
## What still leaves the country
Some metadata and service telemetry go to the parent Region by design. The legal team should confirm that the rule covers data content, not management metadata.
W: Local snapshots and local RDS backups: both features write the copies to S3 on Outposts on the rack, so snapshots and backups stay in the country together with the primary data.
X: A=Customer managed key on Region copies: encryption controls who can read the copies, but the snapshots and backups are still stored in another country, which is exactly what the audit found.
C=SCP denying the parent Region: Outpost resources are managed through the parent Region's API endpoints, so this deny would also stop the team from managing the instances, volumes and databases on the rack.
D=Nightly copy and delete: the data still lands in the parent Region every day before it is removed, so the law is broken each night, and the custom job adds a failure point.
T: On Outposts, keep backups in the country with EBS local snapshots and an RDS on Outposts backup target of the Outpost; the defaults write these copies to the parent Region.
V: AWS Outposts, Amazon EBS, Amazon RDS, Amazon S3, Amazon Data Lifecycle Manager

@ SAP-C03 D2 T2.4 advanced use-case
S: A payments company processes national identity numbers on Amazon EC2. A regulator requires that plaintext identity numbers be accessible only to a specific, audited tokenization program, and not to operating system administrators of the instances, other processes on the host, or the company's cloud engineers with broad IAM permissions. The decryption key is in AWS KMS. Which design meets these requirements?
A: Run the tokenization program on a dedicated host, restrict SSH with Session Manager and IAM conditions, and allow kms:Decrypt only for the instance role of that host
B: Run the tokenization program in an AWS Nitro Enclave and add a KMS key policy condition that allows kms:Decrypt only when the enclave attestation matches the signed image
C: Store the identity numbers in AWS Secrets Manager with a resource policy that allows only the tokenization role, and rotate the secret every hour with a Lambda function
D: Run the tokenization program on a Nitro-based instance with encrypted EBS volumes and enable KMS key rotation, so administrators cannot read data at rest on the disk
K: B
G: ## The problem: who can see data while it is in use
Encryption at rest and in transit does not help once a program decrypts data in memory. Anyone with root on that instance, or anyone who can use the instance role, can call KMS or read process memory.
## Nitro Enclaves
A Nitro Enclave is an isolated virtual machine carved out of an EC2 instance's CPU and memory. It has no persistent storage, no interactive access and no external networking; the parent instance talks to it only through a local vsock channel. Even root on the parent instance cannot read enclave memory.
## Cryptographic attestation with KMS
When the enclave starts, the Nitro Hypervisor produces a signed attestation document containing measurements (PCRs) of the enclave image, such as `PCR0` (image hash) and `PCR8` (signing certificate). A KMS key policy can allow `kms:Decrypt` only when the request carries a matching attestation, for example with the condition key `kms:RecipientAttestation:ImageSha384` or `kms:RecipientAttestation:PCR0`. KMS then encrypts the response to a key that only the enclave holds, so the parent instance never sees the plaintext.
W: Nitro Enclave with attestation-based key policy: only the measured, signed tokenization image can obtain the plaintext key, the parent instance's administrators and processes cannot read enclave memory, and a broad IAM role alone is not enough to decrypt.
X: A=Dedicated host with role-scoped decrypt: anyone with root on that host can use the instance role credentials or dump process memory, so administrators can still reach the plaintext.
C=Secrets Manager with a tight policy: the program must still retrieve and hold the data in normal process memory, where OS administrators can read it, and engineers who can change the resource policy can grant themselves access.
D=Encrypted EBS with key rotation: this protects data at rest on the volume, but the running instance sees the decrypted volume, so administrators can read data in use, which is exactly what the regulator forbids.
T: To keep plaintext away from even the instance's own administrators, process it in a Nitro Enclave and tie KMS decryption to the enclave's attestation measurements.
V: AWS Nitro Enclaves, AWS KMS, Amazon EC2

@ SAP-C03 D2 T2.4 applied use-case
S: A health-tech company with 40 accounts in AWS Organizations is preparing for an external audit and for onboarding a hospital customer. The auditor asks for independent evidence of the controls that AWS operates for the underlying infrastructure, and the hospital requires that a HIPAA Business Associate Addendum covers every current and future account in the organization. Which actions meet these requirements? (Select TWO)
A: Download the AWS SOC 2 Type II report and the PCI DSS Attestation of Compliance from AWS Artifact and share them with the auditor under the Artifact terms
B: From the management account, accept the AWS BAA in AWS Artifact as an organization agreement so that it applies to all member accounts automatically
C: Open an AWS Support case asking AWS to email the SOC 2 report and a countersigned BAA, because AWS Artifact only provides ISO certificates
D: Enable the PCI DSS standard in Security Hub CSPM, which generates a signed AWS Attestation of Compliance for each member account
E: Deploy the HIPAA operational best practices conformance pack in AWS Config, which activates the BAA once all rules report compliant
K: A,B
G: ## Two halves of shared responsibility evidence
An auditor needs evidence for both sides of the shared responsibility model:
- **AWS's side** (data centers, hardware, hypervisor, managed service operations) is attested by third-party auditors. AWS publishes these reports, such as SOC 1/2/3, PCI DSS Attestation of Compliance, ISO certificates and others, in **AWS Artifact**. Many are confidential, so you accept the Artifact terms before downloading and sharing them with your auditors.
- **Your side** (configuration of your accounts and workloads) needs your own evidence, typically from AWS Config, Security Hub CSPM and CloudTrail.
## Agreements in AWS Artifact
AWS Artifact also holds legal agreements such as the HIPAA Business Associate Addendum (BAA). You can accept an agreement for a single account, or, from the management account of an organization with all features enabled, accept it as an **organization agreement**. An organization agreement covers all member accounts, including accounts added later.
W: A=Artifact reports: SOC 2 and the PCI DSS AOC are the third-party attestations of the controls AWS operates, which is exactly the independent evidence the auditor asked for.
B=Organization BAA in Artifact: accepting the agreement from the management account covers every current and future member account, so the hospital's requirement is met without per-account steps.
X: C=Support case for reports: AWS Artifact is the self-service source for SOC reports, PCI attestations and agreements such as the BAA; it is not limited to ISO certificates, and no email process is needed.
D=Security Hub CSPM PCI DSS standard: it checks your own resource configuration against PCI DSS controls; it produces findings and scores, not an attestation of AWS's infrastructure controls.
E=HIPAA conformance pack: it helps you monitor your own configuration against HIPAA-related rules, but it has no legal effect; the BAA is accepted only in AWS Artifact.
T: AWS Artifact supplies AWS's own audit reports and lets the management account accept agreements such as the BAA for the whole organization; your own configuration evidence comes from Config and Security Hub CSPM.
V: AWS Artifact, AWS Organizations

@ SAP-C03 D2 T2.4 advanced use-case
S: A financial company runs 300 accounts in AWS Organizations across four Regions. Every quarter, auditors select a date and ask for proof of whether any security group allowed inbound SSH from 0.0.0.0/0 on that date, which resource it was, and when it was fixed. Teams currently answer with screenshots, and evidence older than 90 days is often missing. Which solution provides this evidence with the LEAST ongoing manual effort?
A: Record security groups and rule compliance with AWS Config in all accounts and Regions, deploy a restricted-SSH organization Config rule, and query the central history files with Athena
B: Enable Security Hub CSPM with central configuration in all accounts and Regions, and export the current failed control findings to a spreadsheet at the end of each quarter
C: Enable VPC Flow Logs for every VPC, deliver them to a central S3 bucket, and use Amazon Athena to find accepted connections on port 22 from public IP addresses for each date
D: Use CloudTrail event history in each account to search for AuthorizeSecurityGroupIngress calls, and record the results in a central evidence register every quarter
K: A
G: ## Point-in-time configuration evidence
Audit questions like "was this resource non-compliant on date X?" need two things: a record of what each resource looked like over time, and an evaluation of that state against a rule.
- **AWS Config recording** stores a configuration item for each recorded resource whenever it changes, giving a configuration timeline. Config keeps this history for a retention period you choose, from 30 days up to 7 years (the default).
- **AWS Config rules** evaluate those configuration items. The managed rule `restricted-ssh` flags security groups that allow `0.0.0.0/0` on port 22. If the recorder also records the resource type `AWS::Config::ResourceCompliance`, Config keeps **compliance history**, so you can see when a resource became non-compliant and when it returned to compliant.
- The **delivery channel** of every account and Region can write configuration history files to one **central S3 bucket** (for example in a log archive account, as AWS Control Tower does). Amazon Athena can then query those files across all accounts, Regions and dates.
- An **aggregator** gives a central view of the *current* configuration and compliance of all accounts; its advanced queries search current state, not history, so point-in-time questions are answered from the history files (or per account from the resource timeline).
Organization Config rules and conformance packs can be deployed from a delegated administrator account, so new accounts are covered automatically.
W: Config recording, organization rule and central history: each security group's configuration and compliance changes are recorded with timestamps and delivered to one bucket, so the team can answer any date the auditor picks with an Athena query, with no screenshots.
X: B=Security Hub CSPM quarterly export: an end-of-quarter export only captures findings that exist on that day, and Security Hub CSPM removes findings about 90 days after their last update, so a resource that was fixed earlier in the quarter may leave no trace.
C=VPC Flow Logs on port 22: flow logs show traffic, not configuration. A security group can be wide open with no SSH traffic that day, so the absence of flows proves nothing about the rule.
D=CloudTrail event history: event history covers only the last 90 days of management events per Region and account, and reconstructing rule state from API calls by hand is the manual effort the company wants to avoid.
T: For "what did this resource look like and was it compliant on date X" across accounts, record resources and rule compliance with AWS Config, deliver the history to a central bucket and query it; aggregators show current state.
V: AWS Config, AWS Organizations, Amazon S3, Amazon Athena

@ SAP-C03 D2 T2.4 advanced troubleshooting
S: A retailer uses Security Hub CSPM with central configuration and a delegated administrator to run the PCI DSS standard in 90 accounts, with findings aggregated to one Region. For its annual assessment, the Qualified Security Assessor asks for control status evidence covering the full 12-month period, stored where application teams cannot alter it. The security team discovers that findings older than about three months are not available. Which solution fixes this for future assessments?
A: Increase the finding retention period in the Security Hub CSPM delegated administrator settings to 13 months, and restrict who can update findings with an SCP
B: Enable Amazon Security Lake from a delegated administrator in the log archive account, add Security Hub CSPM findings as a source for all accounts and Regions, and set 13-month retention
C: Enable the AWS Config aggregator in the audit account so that Security Hub CSPM findings are copied into Config compliance history, and keep that history for seven years
D: Schedule a monthly AWS Lambda function that takes a CSV export of the Security Hub CSPM summary dashboard and stores it in a versioned S3 bucket in each member account
K: B
G: ## How long Security Hub CSPM keeps findings
Security Hub CSPM is a working view of current posture, not an archive. It deletes findings about 90 days after they were last updated (or created, if never updated), and this period is not configurable. Control findings for resources that stay in the same state are refreshed by later checks, but findings that were resolved earlier disappear.
## Building an evidence archive
Every new or updated finding is also published to Amazon EventBridge. Two common ways to keep them:
- **Amazon Security Lake** collects security data, including **Security Hub CSPM findings** as a native source, from all accounts and Regions of an organization into S3 buckets in the delegated administrator account, normalized to the OCSF schema. You set the retention per Region (with optional transitions to cheaper storage classes), and you query it with **Amazon Athena** or share it with subscribers.
- A self-built pipeline: an EventBridge rule for `Security Hub Findings - Imported` events in the aggregation Region, Amazon Data Firehose and an S3 bucket, which you build and operate yourself.
Placing the archive in a **log archive** account that application teams cannot access keeps them from altering it; S3 Object Lock or tight bucket policies can harden it further.
W: Security Lake with Security Hub CSPM as a source: findings from all 90 accounts are collected continuously into a central account that application teams do not control, kept for the 13 months the assessor needs, and queried with Athena for any date range.
X: A=Longer retention setting: Security Hub CSPM has no setting to keep findings longer; the roughly 90-day retention is fixed, so the evidence gap would remain.
C=Config aggregator copy: a Config aggregator collects Config data, not Security Hub CSPM findings; Security Hub CSPM controls use Config rules, but the finding history is not copied into Config compliance history this way.
D=Monthly dashboard CSV in member accounts: a monthly snapshot misses changes between runs, and storing it in the member accounts lets the same application teams alter or delete the evidence.
T: Security Hub CSPM is not an evidence archive; collect its findings with Amazon Security Lake (or an EventBridge pipeline) into a separate account with the retention you need, and report with Athena.
V: AWS Security Hub CSPM, Amazon Security Lake, Amazon S3, Amazon Athena

@ SAP-C03 D2 T2.4 applied use-case
S: An insurance company is designing a claims platform that uses Amazon API Gateway, AWS Lambda, Amazon DynamoDB and Amazon Bedrock. Its risk committee wants a repeatable threat modeling practice that starts before code is written, identifies threats at every trust boundary, links each threat to a mitigation and an owner, and stays current as the design evolves. Which approach meets these goals?
A: Commission an annual third-party penetration test of the production platform and record its findings in the risk register as the platform's threat model
B: Enable Amazon GuardDuty and Amazon Inspector in every account at launch and treat their findings as the threat model, reviewing them each quarter with the committee
C: Model data flows and trust boundaries at design time, apply STRIDE to each element, record threats and mitigations in Threat Composer stored with the code, and revisit on change
D: Adopt the AWS Foundational Security Best Practices standard in Security Hub CSPM and accept the platform's design once all of its controls show as passed
K: C
G: ## What threat modeling is
Threat modeling is a design activity: you ask "what are we building, what can go wrong, what will we do about it, and did we do a good job?" before and while you build, not after deployment.
## A practical method
- **Diagram the system**: components, data stores, external actors, and the data flows between them. Mark **trust boundaries**, such as internet to API Gateway, Lambda to DynamoDB, or the application to a foundation model.
- **Find threats systematically**, for example with **STRIDE**: Spoofing, Tampering, Repudiation, Information disclosure, Denial of service, Elevation of privilege. Generative AI adds threats such as prompt injection and sensitive data in prompts.
- **Record mitigations and owners**, and turn them into requirements, tests and controls.
- **Revisit** whenever the architecture changes.
AWS publishes **Threat Composer**, an open-source tool that captures threat statements, assumptions and mitigations in a structured format that can be stored and versioned with the code.
## Why scanners are not threat models
Detective services (GuardDuty, Inspector, Security Hub CSPM) find known misconfigurations, vulnerabilities and active threats in deployed resources. They are valuable mitigations, but they do not reason about your design's trust boundaries before it exists.
W: Design-time model with STRIDE and Threat Composer: it starts before code, covers every trust boundary systematically, ties each threat to a mitigation and owner, and stays current because the model is versioned with the code and revisited on change.
X: A=Annual penetration test: it runs after the system is built and only once a year, so design flaws are found late and the model is stale between tests.
B=GuardDuty and Inspector findings: these detect active threats and software vulnerabilities in running resources; they do not analyze trust boundaries or design decisions and cannot start before code exists.
D=Foundational Security Best Practices standard: it checks deployed resources against generic configuration controls; passing them says nothing about threats specific to this platform's data flows, such as prompt injection.
T: Threat modeling is a design-time, iterative practice (diagram, STRIDE per trust boundary, mitigations with owners, revisit on change); detective services are mitigations, not the model.
V: Threat Composer, Amazon API Gateway, AWS Lambda, Amazon DynamoDB, Amazon Bedrock

@ SAP-C03 D2 T2.4 advanced use-case
S: A threat model of a bank's production operations flags a high-risk repudiation threat. Thirty operators federate from the corporate SAML identity provider into one shared OpsAdmin role, then chain into roles in 50 workload accounts. CloudTrail shows only role session names, which operators choose freely, so a harmful change cannot be tied to a person. Which mitigation addresses this risk?
A: Require each operator to pass their corporate user name as the role session name, and publish a runbook that tells operators to reuse the same session name when they chain into workload roles
B: Enable CloudTrail log file integrity validation on the organization trail and store the digest files in the log archive account, so every recorded role session can be proven authentic
C: Tag the OpsAdmin role and every workload role with the names of the operators allowed to use it, and add a condition to each trust policy that checks those tags before allowing the session
D: Have the identity provider set the SAML SourceIdentity attribute to the operator's user name, and require sts:SourceIdentity in the trust policies of the OpsAdmin role and every chained role
K: D
G: ## Repudiation in a threat model
In STRIDE, **repudiation** means a user can deny having performed an action because the records cannot prove who did it. Shared roles are a common cause: CloudTrail records the role and the session name, and the session name is a free-text value that the caller picks when assuming the role.
## Source identity
AWS STS supports a **source identity** for role sessions:
- A SAML or OIDC identity provider can pass it as an attribute (for SAML, `https://aws.amazon.com/SAML/Attributes/SourceIdentity`), or a principal can set it when calling `AssumeRole`.
- Once set, it **cannot be changed** for that session, and it **persists through role chaining**: every role assumed from that session carries the same value.
- CloudTrail records it in the `sourceIdentity` field of every event made with the session, in every account.
- Trust policies can require it with the `sts:SourceIdentity` condition key and must allow `sts:SetSourceIdentity`, so a session without a source identity cannot assume the role.
## Mapping threat to mitigation
Log file integrity validation answers a different threat (tampering with logs). It proves that the records are unchanged, but if the records do not name a person, there is still nothing to attribute.
W: SAML SourceIdentity required in trust policies: the identity provider stamps each session with the operator's user name, the value cannot be changed and follows every chained role, and CloudTrail records it on every action, so each change is tied to a person.
X: A=Session name convention: the role session name is chosen by the caller, so an operator can set any value, and a runbook cannot enforce what is used when chaining into the next role.
B=Log file integrity validation: it proves that log files were not modified or deleted, which counters tampering, but the logs still show only the shared role and a self-chosen session name.
C=Operator names as role tags: tags on a role describe the role, not the person in the session; every session of the shared role still looks the same in CloudTrail.
T: To counter repudiation with shared or chained roles, require an STS source identity set by the identity provider; it is immutable, survives role chaining and appears in every CloudTrail event.
V: AWS IAM, AWS STS, AWS CloudTrail

@ SAP-C03 D2 T2.4 advanced use-case
S: A threat modeling session for a public customer login API, which runs behind Amazon CloudFront and an Application Load Balancer, identifies two high-severity threats: credential stuffing with stolen username and password lists, and application-layer floods that could exhaust the backend. The company needs preventive mitigations at the edge rather than alerts after the fact. Which actions should the solutions architect take? (Select TWO)
A: Add the AWS WAF account takeover prevention managed rule group to the web ACL on the CloudFront distribution, scoped to the login request path
B: Enable Amazon GuardDuty Runtime Monitoring on the backend and configure it to block source IP addresses that produce repeated failed sign-in attempts
C: Subscribe to AWS Shield Advanced with automatic application layer DDoS mitigation, and add AWS WAF rate-based rules for the login path to the web ACL
D: Run Amazon Inspector network reachability scans on the load balancer and automatically close any listener port that a scan reports as reachable
E: Enable Amazon Macie on the S3 bucket that stores application logs so that leaked credentials in failed requests are found and the affected accounts are locked
K: A,C
G: ## From threat to mitigation
A threat model is only useful when each threat maps to a control. For a login endpoint, two classic STRIDE threats are:
- **Spoofing through credential stuffing**: attackers replay large lists of stolen credentials, often from many IP addresses at low rates per IP.
- **Denial of service at layer 7**: HTTP floods that look like normal requests but exhaust the application.
## Edge controls on AWS
- **AWS WAF Fraud Control account takeover prevention (ATP)** is a managed rule group that inspects login requests on a path you specify, checks submitted credentials against a stolen-credential database, and tracks failed login patterns, so it can block or challenge credential stuffing.
- **AWS WAF rate-based rules** cap the request rate per client key (such as IP) for a scope like the login path.
- **AWS Shield Advanced** adds DDoS response team support, cost protection and, with **automatic application layer DDoS mitigation**, creates and applies AWS WAF rules during an attack on protected resources such as CloudFront distributions.
Attaching these to the CloudFront web ACL stops bad traffic at the edge before it reaches the ALB.
W: A=WAF account takeover prevention: it is purpose-built for credential stuffing on login paths, comparing submitted credentials against known-compromised ones and blocking abusive login patterns at the edge.
C=Shield Advanced with rate-based rules: rate limits on the login path plus automatic layer 7 mitigation stop HTTP floods at CloudFront before they exhaust the backend.
X: B=GuardDuty Runtime Monitoring blocking IPs: GuardDuty is a detective service that produces findings about workloads; it does not block traffic itself, and it does not inspect application sign-in attempts.
D=Inspector network reachability: it reports which ports are reachable, which is intended for a public login API; closing the listener would take the service down and does nothing against credential stuffing.
E=Macie on log buckets: Macie finds sensitive data in S3 objects after it is written; it neither stops login attempts nor locks accounts, so it is not a preventive edge control.
T: Map credential stuffing to AWS WAF account takeover prevention and layer 7 floods to rate-based rules with Shield Advanced, all on the CloudFront web ACL.
V: AWS WAF, AWS Shield Advanced, Amazon CloudFront, Elastic Load Balancing

@ SAP-C03 D2 T2.4 advanced use-case
S: A bank uses Amazon Bedrock in two Regions for a customer-facing assistant. Regulators require that the bank retain, for seven years and in tamper-resistant storage, the full text of every prompt sent to a model and every response returned, encrypted with a bank-managed key, along with who invoked the model. The bank already has an organization trail in AWS CloudTrail. What additional configuration meets the requirement?
A: Add CloudTrail data event selectors for Amazon Bedrock to the organization trail so that the request and response payloads of InvokeModel calls are written to the trail
B: Enable Amazon Bedrock Guardrails with trace enabled on every request, and forward the guardrail traces to Amazon CloudWatch Logs with a seven-year retention policy
C: Enable Amazon Bedrock model invocation logging in both Regions, each to an S3 bucket with SSE-KMS using a customer managed key and S3 Object Lock retention of seven years
D: Turn on CloudWatch Logs data protection for the assistant's application log group, and configure the application to log the prompts and responses with a seven-year retention
K: C
G: ## Two different audit records for generative AI
- **AWS CloudTrail** records API activity: who called `InvokeModel` or `Converse`, when, from where, and with which model ID. These calls are logged as **management events**, so the existing trail already has them; CloudTrail data events exist for some other Bedrock resources (such as agents and knowledge bases), but no CloudTrail event contains the body of the request (the prompt) or the model's response.
- **Amazon Bedrock model invocation logging** records the invocation itself, including input and output data (text, and optionally image and embedding data) plus metadata such as the model and the caller's identity. It is off by default and is configured **per account and per Region**, with Amazon S3 and/or Amazon CloudWatch Logs as destinations.

An AWS KMS key is normally **single-Region**: it can be used only in the Region where it was created, so ciphertext copied to another Region cannot be decrypted by any key there. G: ## Revocation in IAM Roles Anywhere
IAM Roles Anywhere validates the certificate chain against the trust anchor on every `CreateSession` call. It does not fetch CRLs or query OCSP on its own. G: ## High availability inside a Region
A CloudHSM **cluster** can contain HSMs in several Availability Zones of one Region. When you add an HSM, it is created from a backup of the cluster and the cluster keeps keys and users **synchronized** across all HSMs. The CloudHSM client load-balances requests and fails over between HSMs, so a single HSM or a single AZ can fail without an outage. AWS recommends at least two HSMs in different AZs for production.
## Disaster recovery to another Region
CloudHSM takes encrypted **backups** of the cluster automatically (at least once every 24 hours and when HSMs are added). Backups are encrypted so that they can only be restored into CloudHSM hardware, and key material never leaves the HSMs in plaintext. You can **copy a backup to another Region** and **create a new cluster from that backup** there, then add HSMs. This is the standard way to rebuild a cluster with the same keys in another Region. Copying is not automatic, so schedule it (for example with an EventBridge rule and a Lambda function that calls `CopyBackupToRegion` after each new backup) to keep the remote copy recent.
There is no built-in synchronous cross-Region replication of a CloudHSM cluster.

E=KMS multi-Region keys in a custom key store: multi-Region keys are not supported in custom key stores, and the application signs directly with CloudHSM keys, not through KMS.
