@ SAP-C03 D1 T1.1 advanced use-case
S: A retailer captures website clickstream events (about 40,000 JSON records per second) in an Amazon Kinesis Data Streams stream that other consumers already read. Analysts query the history with Amazon Athena and complain that queries scan terabytes of JSON and cost too much. The company wants the stored data in a columnar format, partitioned by event date and country, available to Athena within 15 minutes, and wants no servers or custom code to manage. Which solution meets these requirements?
A: Add an Amazon Data Firehose stream that reads from the Kinesis stream, converts records to Parquet by using a Glue Data Catalog table schema, and uses dynamic partitioning
B: Add a Lambda consumer on the Kinesis stream that writes each batch as a JSON object to S3 under date and country prefixes, and run a Glue crawler every 15 minutes
C: Keep the raw JSON in S3 and run an Athena CTAS query every 15 minutes that rewrites the full history into Parquet partitioned by event date and country
D: Launch a long-running Amazon EMR cluster with Spark Structured Streaming that reads the stream and writes Parquet partitions to S3 for Athena queries
K: A
G: ## Why the storage format drives Athena cost
Athena charges by the amount of data scanned. Two things cut that amount sharply:
- **Columnar formats** such as Apache Parquet or ORC store each column separately and compress well, so a query that reads 3 of 60 fields reads only those 3 columns.
- **Partitioning** puts data in prefixes such as `s3://lake/clicks/dt=2026-10-27/country=DE/`. A query with `WHERE dt = '2026-10-27'` skips every other prefix.
## Amazon Data Firehose as the serverless loader
Firehose can use a Kinesis data stream as its source, so it becomes one more consumer next to the existing ones. It buffers records by size or time (up to 900 seconds) and can:
- **Convert record format**: JSON in, Parquet or ORC out, using the schema of a table in the AWS Glue Data Catalog.
- **Partition dynamically**: extract keys such as `event_date` and `country` from each record and write them into the S3 prefix.
Nothing is provisioned or patched; Firehose scales with the stream.
W: Firehose with format conversion and dynamic partitioning: it reads the existing stream as another consumer, writes compressed Parquet into date and country prefixes within the buffer interval, and needs no code or servers, so Athena scans far less data.
X: B=Lambda writing JSON with a crawler: the data stays in JSON, so Athena still scans whole records, and the team now owns consumer code, error handling and many small files that slow queries down.
C=Repeated CTAS over the full history: each run rescans and rewrites all the raw JSON, so cost grows with every day of history; it reduces query cost only by spending more on the conversion itself.
D=Long-running EMR streaming cluster: it can produce the same Parquet layout, but the company must size, patch and pay for a cluster around the clock, which breaks the no-servers requirement.
T: To land a Kinesis stream in S3 as partitioned Parquet without code, add a Firehose consumer with record format conversion (Glue schema) and dynamic partitioning.
V: Amazon Kinesis Data Streams, Amazon Data Firehose, AWS Glue, Amazon Athena

@ SAP-C03 D1 T1.1 advanced troubleshooting
S: An AWS Lambda function processes an Amazon Kinesis Data Streams stream through an event source mapping with default settings. Order must be preserved per partition key (customer ID). Twice this month a single malformed record caused the function to fail repeatedly, and its shard stopped making progress until the record expired. During daily peaks the iterator age also climbs for an hour, although each invocation takes only 2 seconds and the stream has enough shards for the write rate. Which TWO changes fix both problems? (Select TWO)
A: Set BisectBatchOnFunctionError, a low MaximumRetryAttempts, and an on-failure destination so failing records are isolated, recorded, and skipped
B: Raise ParallelizationFactor on the event source mapping so several batches from each shard are processed concurrently while keeping order per partition key
C: Raise the reserved concurrency of the function so that Lambda can run more invocations against each shard at the same time during daily peaks
D: Increase the stream retention period to 7 days so that a blocked shard keeps its records until the operations team can fix the malformed record
E: Register the function as an enhanced fan-out consumer so it receives a dedicated read throughput per shard that removes processing delays at peak
K: A,B
G: ## How Lambda reads a Kinesis shard
An event source mapping polls each shard and, by default, runs **one batch per shard at a time**. Records of a shard are processed in order, and a failing batch is retried until it succeeds or the records expire from the stream. That is why one bad record can block a whole shard: everything behind it waits.
## Settings that control failure handling
- `BisectBatchOnFunctionError` splits a failing batch in two and retries each half, narrowing down to the bad record.
- `MaximumRetryAttempts` and `MaximumRecordAgeInSeconds` bound how long Lambda keeps retrying.
- An **on-failure destination** (for example an SQS queue or SNS topic) receives details of the discarded records so they can be inspected and replayed.
## Settings that control throughput
`ParallelizationFactor` (1 to 10) lets Lambda process up to 10 batches from one shard at the same time. Lambda still sends all records with the same partition key to the same batch sequence, so ordering per key is kept. Example: 20 shards with a factor of 5 allow up to 100 concurrent invocations.
W: A=Bisect, bounded retries and on-failure destination: the poison record is isolated and sent to the destination after a few attempts, so the shard moves on instead of stalling until the record ages out.
B=ParallelizationFactor: the bottleneck is one batch per shard, not the stream or the function duration; processing several batches per shard in parallel raises throughput while keeping per-customer order.
X: C=More reserved concurrency: concurrency is capped by the event source mapping at one batch per shard by default, so extra reserved concurrency is never used and iterator age does not improve.
D=Longer retention: records would stay in the stream longer, which only extends how long a poison record blocks its shard; it fixes neither the stall nor the lag.
E=Enhanced fan-out: it gives the consumer its own 2 MB per second read pipe per shard and lower read latency, but the delay here comes from serial processing, and failures still block the shard.
T: Kinesis plus Lambda: contain poison records with bisect, bounded retries and an on-failure destination; add throughput per shard with ParallelizationFactor, which keeps per-key order.
V: AWS Lambda, Amazon Kinesis Data Streams, Amazon SQS

@ SAP-C03 D1 T1.1 applied troubleshooting
S: A logistics company stores IoT telemetry in S3 under prefixes such as device_type=X/year=2026/month=10/day=27/hour=14/. The Glue Data Catalog table now has more than 2 million partitions. Athena queries that filter on a single day spend most of their run time in query planning, and data written in the last hour is not visible until a scheduled Glue crawler finishes adding the new partitions. The company wants faster planning and immediate visibility with the least operational effort. What should a solutions architect do?
A: Run MSCK REPAIR TABLE after every hourly upload so that Athena loads all new partitions into the Glue Data Catalog before analysts query
B: Enable partition projection on the table and define the ranges and the S3 location template for the partition keys in the table properties
C: Increase the Glue crawler frequency to every 5 minutes and enable incremental crawls that add only new folders to the existing table
D: Create an Athena workgroup with a higher data scan limit and enable query result reuse so repeated queries return cached results faster
K: B
G: ## How Athena finds partitions
For a partitioned table, Athena normally asks the AWS Glue Data Catalog for the partitions that match the query filter. With millions of partitions, that lookup alone can dominate planning time. New partitions also have to be registered (by a crawler, `ALTER TABLE ADD PARTITION` or `MSCK REPAIR TABLE`) before Athena sees them.
## Partition projection
With partition projection, Athena computes partition values and locations from rules in the table properties instead of reading them from the catalog:
- `projection.enabled = true`
- a type and range per key, for example `projection.day.type = integer`, `projection.day.range = 1,31`, or an `enum` list for `device_type`
- `storage.location.template = s3://telemetry/device_type=${device_type}/year=${year}/...`
Because the partitions are calculated, there is no catalog lookup for them and nothing to register: data under a new prefix is queryable as soon as it is written.
W: Partition projection: Athena derives the matching prefixes from the query filter and the projection rules, which removes the large catalog lookup and makes new hourly prefixes visible immediately, with no crawler or repair job to run.
X: A=MSCK REPAIR after each upload: it scans the whole table location and gets slower as prefixes grow, and the catalog still holds millions of partitions that Athena must look up during planning.
C=Faster incremental crawls: new data still waits up to the crawler interval, crawler runs cost more, and the partition count that slows planning keeps growing.
D=Workgroup limits and result reuse: scan limits only cap cost, and result reuse helps only identical repeated queries; neither changes how partitions are found or when new data appears.
T: Athena tables with huge or predictable partition sets: use partition projection so partitions are calculated, not looked up or registered.
V: Amazon Athena, AWS Glue, Amazon S3

@ SAP-C03 D1 T1.1 advanced use-case
S: A company has 150 accounts in AWS Organizations across us-east-1, eu-west-1 and ap-southeast-2, and adds new accounts every month. Each workload publishes custom order events to the default event bus in its own account and Region. The integration team needs every event whose detail-type is OrderPlaced delivered to a single custom event bus in a central account in us-east-1, including events from accounts created later, without running any forwarding code. Which TWO actions should a solutions architect take? (Select TWO)
A: Add a resource-based policy on the central event bus that allows events:PutEvents from any principal whose aws:PrincipalOrgID matches the organization
B: Use a service-managed CloudFormation StackSet with automatic deployment to create a rule in each account and Region that targets the central bus ARN
C: Create an EventBridge global endpoint in each workload account that names the central account's event bus in us-east-1 as its primary event bus
D: Share the central event bus with the organization through AWS Resource Access Manager so that member accounts can publish to it as a local bus
E: Create an archive on each default event bus and schedule a daily replay that sends the archived OrderPlaced events to the central bus in us-east-1
K: A,B
G: ## Moving events between buses
In Amazon EventBridge, a **rule** on one event bus can use another event bus as its target, including a bus in a different account and a different Region. The event is delivered as is, and rules on the receiving bus process it like any other event. This is the native forwarding mechanism; no Lambda function is needed.
## Two permissions are involved
- The **receiving bus** must allow the sender. Its resource-based policy can allow `events:PutEvents` for a list of accounts or, more simply, for the whole organization with the `aws:PrincipalOrgID` condition, so new accounts are covered automatically.
- The **sending rule** uses an IAM role that is allowed to call `events:PutEvents` on the target bus ARN.
## Deploying the rule everywhere
A service-managed CloudFormation StackSet targeted at the organization (or OUs) with automatic deployment creates the rule and role in every listed Region of every account, including accounts that join later.
W: A=Organization-wide bus policy: one statement with aws:PrincipalOrgID authorizes every current and future member account to put events on the central bus.
B=StackSet-deployed forwarding rules: each account and Region gets a rule that matches detail-type OrderPlaced and targets the central bus ARN directly, and automatic deployment covers new accounts with no forwarding code.
X: C=Global endpoint to a central bus: global endpoints provide Regional failover between two event buses of the same account for the publisher; they are not a way to aggregate many accounts into one central bus.
D=RAM share of the event bus: event buses are not shared through AWS Resource Access Manager; cross-account delivery is authorized by the bus resource policy.
E=Archive and daily replay: replay sends archived events back to the bus they were archived from, not to another account's bus, and a daily batch is not continuous delivery.
T: Cross-account and cross-Region event aggregation: allow the organization on the central bus policy and deploy rules that target that bus ARN from every account and Region with StackSets.
V: Amazon EventBridge, AWS CloudFormation, AWS Organizations

@ SAP-C03 D1 T1.1 advanced tradeoff
S: A payments platform publishes events from its producers to a custom EventBridge event bus in us-east-1, where rules invoke consumers. A Regional disruption last year stopped event ingestion for 40 minutes. The company now runs consumers in both us-east-1 and us-west-2 and wants producers to keep publishing during a Regional event-ingestion problem, with automatic failover, without changing which endpoint producers call during an incident and without building custom health-check logic. Which solution best meets these requirements?
A: Add a rule on the us-east-1 bus that forwards every event to a custom bus in us-west-2, and run identical consumer rules on both event buses
B: Create a Route 53 failover record that points to the two Regional EventBridge service endpoints and configure the producer SDKs to use that DNS name
C: Create an EventBridge global endpoint with the us-east-1 bus as primary and a us-west-2 bus as secondary, a Route 53 health check, and event replication
D: Archive all events on the us-east-1 bus and, after a failure, replay the archive into a us-west-2 bus while producers are reconfigured to publish there
K: C
G: ## EventBridge global endpoints
A **global endpoint** sits in front of two custom event buses with the same name in two Regions, a primary and a secondary.
- Producers call `PutEvents` with the endpoint ID instead of a Regional bus.
- A **Route 53 health check** (usually driven by a CloudWatch alarm on the primary Region's EventBridge metrics) decides where events go. When it fails, EventBridge sends new events to the secondary Region automatically.
- **Event replication** additionally copies events to the secondary bus while the primary is healthy, so consumers there stay warm and can be processed idempotently.
Rules and targets must exist in both Regions; the endpoint only routes the ingestion.
## Why forwarding alone is not failover
A rule that forwards events from Region A to Region B helps only after events have reached Region A. If ingestion in Region A fails, producers that call Region A cannot publish at all.
W: Global endpoint with health check and replication: producers keep one endpoint ID, and EventBridge shifts ingestion to us-west-2 when the health check fails, using a managed Route 53 health check rather than custom logic.
X: A=Forwarding rule to us-west-2: events already in us-east-1 get copied, but when us-east-1 ingestion fails the producers still call us-east-1 and their PutEvents calls fail, so nothing reaches the forwarding rule.
B=Route 53 record over service endpoints: AWS service endpoints rely on TLS certificates for their own hostnames, so a custom DNS name in front of them breaks the request, and the company would be maintaining the health logic itself.
D=Archive and replay after failure: replay sends events back to the bus that archived them, it needs a person to act during the incident, and producers must be reconfigured, which the company wants to avoid.
T: Publisher-side Regional failover for EventBridge is a global endpoint (two same-named buses, a Route 53 health check, optional replication); forwarding rules only copy events that already arrived.
V: Amazon EventBridge, Amazon Route 53, Amazon CloudWatch

@ SAP-C03 D1 T1.1 advanced use-case
S: A company runs 35 HTTP microservices on an Amazon EKS cluster with pods on both EC2 nodes and AWS Fargate. Each service is currently exposed through its own Kubernetes Service of type LoadBalancer, which created 35 load balancers. The company wants to cut that cost by routing by host and path behind as few load balancers as possible, attach an AWS WAF web ACL, terminate TLS with ACM certificates, and keep each team managing its own Kubernetes manifests. Which solution meets these requirements?
A: Install the AWS Load Balancer Controller and let each team create Ingress resources with the same group.name annotation, target-type ip, and a WAF ACL annotation
B: Deploy an NGINX ingress controller behind a single Network Load Balancer and associate the WAF web ACL and the ACM certificates with that Network Load Balancer
C: Keep the per-service load balancers but switch them to Network Load Balancers with TLS listeners, and protect each one with a security group allowing only proxy IPs
D: Put an Amazon API Gateway HTTP API in front of the cluster with one route per service and a VPC link that points directly at each pod IP address
K: A
G: ## Ingress on Amazon EKS
The **AWS Load Balancer Controller** watches Kubernetes objects and creates AWS load balancers for them:
- A Service of type `LoadBalancer` gets a **Network Load Balancer**.
- An `Ingress` gets an **Application Load Balancer** with host- and path-based rules.
## Sharing one ALB across teams
By default each Ingress gets its own ALB. The `alb.ingress.kubernetes.io/group.name` annotation creates an **IngressGroup**: all Ingresses with the same group name are merged into one ALB, while each team still owns its own Ingress manifest. Other annotations add features:
- `alb.ingress.kubernetes.io/target-type: ip` registers pod IPs directly, which is required for pods on Fargate (there is no node to forward to).
- `alb.ingress.kubernetes.io/wafv2-acl-arn` associates a WAF web ACL, and ACM certificates are attached to the HTTPS listener.
W: Load Balancer Controller with an IngressGroup: all teams' Ingresses merge into one ALB with host and path rules, target-type ip reaches pods on EC2 and Fargate alike, and the ALB supports both AWS WAF and ACM certificates.
X: B=NGINX behind a Network Load Balancer: AWS WAF cannot be associated with a Network Load Balancer, so the web ACL requirement fails, and the company now operates the NGINX proxy fleet itself.
C=Per-service Network Load Balancers: the number of load balancers and their cost stay the same, and NLBs do not support WAF or host and path routing.
D=HTTP API with pod-IP integrations: pod IPs change on every reschedule, and HTTP API VPC links target load balancers or Cloud Map services, not individual pod addresses, so routes would break constantly.
T: Many HTTP services on EKS behind one ALB with WAF: AWS Load Balancer Controller Ingresses sharing an IngressGroup, with target-type ip for Fargate pods.
V: Amazon EKS, AWS Load Balancer Controller, Elastic Load Balancing, AWS WAF

@ SAP-C03 D1 T1.1 applied comparison
S: A company is moving an MQTT broker fleet for 2 million industrial sensors to EC2 instances in an Auto Scaling group. Sensors connect over TCP port 8883 with mutual TLS that the broker software itself must terminate, because the broker reads the client certificate. Customer firewalls allow outbound traffic only to a fixed list of IP addresses, connections stay open for days, and the brokers must see the sensors' source IP addresses. Which ingress option fits best?
A: An Application Load Balancer with an HTTPS listener in mutual TLS verify mode, forwarding the client certificate to the brokers in an HTTP header
B: An Amazon API Gateway WebSocket API with a VPC link integration that forwards each sensor message to the broker fleet through the private network
C: A Gateway Load Balancer with GENEVE encapsulation that distributes sensor connections across the brokers registered as virtual appliance targets
D: An internet-facing Network Load Balancer with an Elastic IP per Availability Zone and a TCP listener on port 8883 that passes TLS to the brokers
K: D
G: ## Layer 4 versus layer 7 ingress
- A **Network Load Balancer (NLB)** works at layer 4. A TCP listener forwards the byte stream unchanged, so TLS (including client certificates) is negotiated end to end with the target. It supports long-lived connections (the TCP idle timeout is 350 seconds by default and configurable, and MQTT keep-alive packets keep a flow active), millions of requests per second, client source IP preservation (always on for instance targets), and one static IP per Availability Zone; internet-facing NLBs can use your own **Elastic IP addresses**.
- An **Application Load Balancer (ALB)** works at layer 7 for HTTP, HTTPS and gRPC. It terminates TLS itself, and its IP addresses change over time, so it cannot be allowlisted by IP on its own.
- A **Gateway Load Balancer** inserts third-party virtual appliances (firewalls, IDS) into a traffic path using GENEVE; it is not an application front door.
## Example
Sensor connects to `203.0.113.10:8883` (an Elastic IP on the NLB in one AZ), the TCP listener passes the TLS handshake to a broker, and the broker validates the client certificate.
W: NLB with Elastic IPs and a TCP listener: it passes the TLS session untouched so the broker terminates mutual TLS, keeps long-lived connections, preserves source IPs, and gives fixed addresses for customer firewall rules.
X: A=ALB with mutual TLS: the ALB, not the broker, would terminate TLS, it accepts only HTTP-based protocols rather than raw MQTT over TCP, and its IP addresses are not fixed for allowlisting.
B=WebSocket API with VPC link: API Gateway speaks HTTP and WebSocket, not raw MQTT over TCP, it terminates TLS itself, and a WebSocket connection is limited to 2 hours, not days.
C=Gateway Load Balancer: it is designed to insert inspection appliances transparently into routed traffic, not to accept client connections on a listener port for an application fleet.
T: Raw TCP, end-to-end TLS, static IPs and source IP preservation point to a Network Load Balancer; HTTP routing and WAF point to an ALB.
V: Elastic Load Balancing, Amazon EC2

@ SAP-C03 D1 T1.1 advanced use-case
S: A trading company is building a browser dashboard that must push order status changes to the specific trader who placed each order within one second. Order events are produced by backend services into an SQS queue. Traders connect from browsers that cannot accept inbound connections, about 30,000 traders are online at peak, and the company wants a serverless design with no servers that hold connections. Which design meets these requirements?
A: Expose a REST API that browsers poll every second, with a Lambda function that reads pending updates for the caller from a DynamoDB table keyed by trader ID
B: Use an API Gateway WebSocket API that stores connection IDs by trader in DynamoDB on $connect, and a Lambda consumer that posts updates via the @connections API
C: Create one Amazon SNS topic per trader with an HTTPS subscription to each trader's browser, and publish each order update to the topic of its trader
D: Run an Application Load Balancer with sticky sessions in front of a Lambda function that keeps WebSocket connections open and streams updates to each trader
K: B
G: ## How API Gateway WebSocket APIs work
A WebSocket API keeps a persistent two-way connection between the client and API Gateway. API Gateway holds the connection; your backend stays stateless.
- Route `$connect` runs when a client connects. A Lambda function can authenticate the user and store the **connection ID** with the user identity, for example in DynamoDB (`traderId -> connectionId`).
- Route `$disconnect` runs when the connection closes (best effort), so the mapping can be cleaned up.
- Any backend with IAM permission can send a message to one client by calling the **@connections** management API: `POST https://{api-id}.execute-api.{region}.amazonaws.com/{stage}/@connections/{connectionId}`. A `410 Gone` response means the client is no longer connected.
## Example flow
Order service writes to SQS, a Lambda function reads the event, looks up the trader's connection IDs in DynamoDB, and posts the update to each of them. The browser receives it within milliseconds without polling.
W: WebSocket API with a connection table and @connections: API Gateway holds the 30,000 open connections, and a stateless Lambda consumer pushes each update to only the right trader within the latency target, with no servers.
X: A=One-second polling: 30,000 browsers calling every second produce constant requests and cost even when nothing changes, and updates can still arrive up to a full polling interval late.
C=SNS topic per trader with HTTPS subscriptions: SNS HTTPS subscriptions need a reachable, confirmed web endpoint, and browsers cannot accept inbound connections, so messages cannot be delivered.
D=ALB with a WebSocket-holding Lambda: Lambda targets behind an ALB handle request and response invocations; a function cannot keep WebSocket connections open for clients, so the push channel does not exist.
T: Server-to-client push to specific users without servers: API Gateway WebSocket API, a connection-ID store such as DynamoDB, and backend calls to the @connections API.
V: Amazon API Gateway, AWS Lambda, Amazon DynamoDB, Amazon SQS

@ SAP-C03 D1 T1.1 applied troubleshooting
S: A live auction site uses an Amazon API Gateway WebSocket API to push bid updates to browsers. Users report two problems: some lose updates after sitting on a quiet auction page for a while, and everyone watching long auctions is disconnected at exactly the same session age even while bids are flowing. Server logs show no errors and the service quotas for connections are not reached. Which TWO changes should a solutions architect recommend? (Select TWO)
A: Have the client send a small heartbeat message on a route at an interval shorter than the 10-minute idle timeout so quiet connections stay open
B: Raise the API Gateway idle connection timeout setting on the WebSocket stage from 10 minutes to 8 hours in the stage settings for long auctions
C: Add client logic that detects a closed connection and reconnects automatically, since connections end at the 2-hour maximum duration regardless of traffic
D: Enable API Gateway stage caching with a long TTL so that browsers reconnecting after a drop receive the bids they missed from the cache
E: Switch the WebSocket API to an edge-optimized endpoint type so CloudFront keeps connections alive past the API Gateway connection limits
K: A,C
G: ## WebSocket connection limits in API Gateway
API Gateway WebSocket APIs have two fixed connection limits:
- **Idle timeout: 10 minutes.** A connection with no messages in either direction for 10 minutes is closed.
- **Maximum connection duration: 2 hours.** Every connection is closed after 2 hours, even when it is busy.
These are not stage settings you can raise.
## Designing around them
- **Heartbeats**: the client sends a tiny message (for example `{"action":"ping"}` on a custom route) every few minutes, which resets the idle timer.
- **Reconnect logic**: the client listens for the close event, reconnects with back-off, and asks the backend for the state it missed (for example, the latest bid from DynamoDB), because messages sent while disconnected are not queued.
W: A=Client heartbeat: a message every few minutes counts as activity and prevents the 10-minute idle timeout on quiet auction pages.
C=Automatic reconnect: the simultaneous drops happen at the 2-hour maximum connection duration, which cannot be raised, so clients must reconnect and resync their state.
X: B=Raise the idle timeout: the 10-minute idle timeout and 2-hour duration are fixed limits of WebSocket APIs, and there is no stage setting that extends them to hours.
D=Stage caching for missed bids: caching applies to REST API responses, not WebSocket messages, and a cache would not replay pushes that a disconnected client never received.
E=Edge-optimized endpoint: WebSocket APIs are Regional, and moving traffic through CloudFront would not change the API Gateway idle and duration limits on the connection.
T: API Gateway WebSocket connections close after 10 idle minutes and after 2 hours in any case: send heartbeats and build reconnect-and-resync into the client.
V: Amazon API Gateway

@ SAP-C03 D1 T1.3 advanced use-case

New mobile and partner apps need a JSON REST API with request validation, per-partner API keys and throttling. The SOAP service cannot change and the company wants to avoid writing and running transformation code where configuration can do the job. Which solution meets these requirements?
A: Create an API Gateway HTTP API with parameter mapping to rewrite JSON bodies into SOAP envelopes, and use a VPC link to reach the on-premises service

API Gateway has two API types for HTTP clients, and they differ in how much they can change a request:

@ SAP-C03 D1 T1.3 advanced use-case
S: A manufacturer runs dozens of legacy Java applications that exchange fixed-width text messages through a self-managed Apache ActiveMQ broker using JMS over OpenWire. The company wants to retire the broker hardware and let new cloud microservices react to these messages as JSON events routed by EventBridge rules. The legacy applications may change only their broker connection URL. Which solution meets these requirements with the least custom infrastructure?
A: Migrate the broker to Amazon MQ for ActiveMQ and add a Lambda event source mapping on the queue that parses each message into JSON and calls PutEvents
B: Replace the broker with Amazon SQS FIFO queues and modify the legacy applications to use the AWS SDK so that EventBridge rules can read the queues directly
C: Migrate to Amazon MSK and use a Kafka Connect connector to translate OpenWire traffic from the applications into Kafka records that feed EventBridge
D: Point the applications at an Amazon SNS topic with raw message delivery and use an EventBridge input transformer to parse the fixed-width text into JSON
K: A
G: ## Amazon MQ as a migration path
**Amazon MQ** is a managed broker for **Apache ActiveMQ** and **RabbitMQ**. It speaks the same wire protocols (OpenWire, AMQP, STOMP, MQTT, WebSocket) and APIs such as JMS, so existing clients usually need only a new broker URL and credentials. That is why it fits lift-and-shift of messaging, while SQS and SNS fit new cloud-native code.
## Bridging to event-driven services
AWS Lambda supports Amazon MQ queues as an **event source mapping**: Lambda polls the queue and invokes the function with batches of messages. The function can parse the fixed-width layout (for example columns 1-10 = order ID, 11-18 = date) into JSON and publish it with `PutEvents` to an event bus, where rules route each event type to the right microservice.

W: Amazon MQ plus a Lambda event source mapping: the legacy applications keep JMS over OpenWire and change only the URL, and a small function translates each message into a JSON event for EventBridge, with no broker hardware to run.
X: B=SQS FIFO with SDK changes: SQS does not speak OpenWire, so every legacy application would need code changes, which the constraint forbids, and EventBridge rules do not read from SQS queues.
C=MSK with Kafka Connect: Kafka brokers do not accept OpenWire clients, and Kafka Connect does not translate a JMS client protocol, so the applications would have to be rewritten as Kafka producers.
D=SNS with an input transformer: SNS has no JMS or OpenWire endpoint, and an input transformer only rearranges JSON fields; it cannot parse fixed-width text.

@ SAP-C03 D1 T1.5 advanced use-case
S: A media company keeps 400 TB of viewing data in S3 as Hive-style partitioned Parquet tables. A privacy law now requires deleting a viewer's rows within 72 hours of a request, auditors want to query tables as they were on a past date, and engineers want to add columns without rewriting data. Data engineers use Spark on Amazon EMR, and analysts use Amazon Athena and Amazon Redshift. Which approach meets these requirements with the least custom code?
A: Keep the Parquet layout and run a nightly EMR job that rewrites every partition containing requested viewers, keeping a dated copy of each table for audits
B: Load all viewing data into Amazon Redshift tables, delete rows there, and use Redshift snapshots restored to new clusters for the auditors' historic queries
C: Convert the tables to Apache Iceberg tables registered in the Glue Data Catalog, use DELETE statements for requests and time travel queries for audits
D: Store each viewer's events as separate S3 objects under a viewer ID prefix and use S3 Lifecycle rules to expire the prefixes named in deletion requests
K: C
G: ## From data lake to lakehouse
Plain Parquet files in S3 are immutable: to delete one viewer's rows you must rewrite whole files or partitions yourself, and there is no record of what the table looked like before.
**Open table formats** such as **Apache Iceberg** add a metadata layer over Parquet files:
- **Row-level changes**: `DELETE`, `UPDATE` and `MERGE INTO` write new data or delete files and a new snapshot, with ACID guarantees.
- **Time travel**: each commit is a snapshot, so in Athena `SELECT ... FOR TIMESTAMP AS OF TIMESTAMP '2026-06-30 00:00:00 UTC'` returns the table as it was (Spark has an equivalent `TIMESTAMP AS OF` clause).
- **Schema and partition evolution**: columns can be added or renamed without rewriting data.
## Engines on one copy of data
Iceberg tables registered in the **AWS Glue Data Catalog** can be read and written by Spark on EMR and Athena, and queried from Amazon Redshift, all on the same S3 data. Old snapshots must later be expired so deleted rows are physically removed.
W: Iceberg tables in the Glue Data Catalog: engines run standard DELETE statements for privacy requests, auditors use time travel, columns are added through schema evolution, and EMR, Athena and Redshift share one copy without custom rewrite jobs.
X: A=Nightly partition rewrites with dated copies: it is custom code, and keeping a full dated copy of 400 TB for audits multiplies storage while still lacking real point-in-time queries.
B=Move everything into Redshift: deletes work, but EMR Spark users lose the open S3 data, and restoring snapshots to new clusters for each audit question is slow and costly.
D=One object prefix per viewer: billions of tiny objects make every analytic query slow and expensive, and Lifecycle rules act on age, not on a list of requested viewers within 72 hours.
T: Row-level deletes, time travel and schema evolution on S3 data shared by several engines call for an open table format such as Apache Iceberg in the Glue Data Catalog.
V: Amazon S3, Apache Iceberg, AWS Glue, Amazon Athena, Amazon EMR, Amazon Redshift

S: A healthcare company's data lake has 900 tables in S3 cataloged in the Glue Data Catalog, and analysts query it with Amazon Athena. G: ## Why S3 permissions are too coarse
S3 bucket policies and IAM decide whether a principal can read an **object**. A Parquet object holds many rows and columns, so S3 cannot hide one column or some rows inside it.

Lake Formation adds table, column, row and cell permissions on top of the Glue Data Catalog. After you **register** an S3 location, integrated engines such as Athena get temporary credentials from Lake Formation and enforce what it allows.

D=Athena views per region: Athena runs a view with the caller's own permissions on the base tables and their S3 data, so analysts who can use the views can also query the base tables directly, and every new table needs new views.
T: Column, row and tag-based permissions for a data lake belong in Lake Formation (LF-Tags plus data filters), not in S3 or IAM policies.
