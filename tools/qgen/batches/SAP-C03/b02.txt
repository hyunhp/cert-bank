# SAP-C03 batch 02: security and responsible AI controls (T2.5: 2.5.1 guardrails, 2.5.2 agent access, 2.5.3 human oversight) and post-quantum cryptography (T2.2 skill 2.2.4)

@ SAP-C03 D2 T2.5 advanced use-case
S: A retail bank is launching three generative AI assistants on Amazon Bedrock. Each assistant uses a different foundation model. Compliance requires that no assistant gives personalized investment recommendations, that account numbers never appear in a response although the assistant must still answer the rest of the question, and that jailbreak attempts in user prompts are stopped. The security team wants one centrally owned control that all three assistants reuse and that does not depend on how each model follows instructions. Which solution meets these requirements?
A: Add a shared system prompt that forbids investment advice and account numbers, and enable model invocation logging so that a compliance analyst can review samples of each assistant's conversations every day
B: Create one guardrail with a denied topic for investment advice, a regex sensitive-information filter that masks account numbers, and a prompt attack filter, and pass its version on every call
C: Fine-tune each of the three foundation models on curated conversations that refuse investment questions and omit account numbers, and run Amazon Comprehend PII detection on every response before display
D: Create one guardrail with a word filter that lists investment terms such as stock and fund, and a sensitive-information filter that blocks any response containing an account number pattern
K: B
G: ## What Amazon Bedrock Guardrails evaluates
A guardrail is a reusable policy object that Bedrock applies to the user input and to the model output, independent of which model produced the text. Its policies include:
- **Denied topics**: subjects you describe in natural language (with sample phrases), such as "personalized investment advice". The guardrail blocks prompts or responses that fall into the topic even when no specific keyword appears.
- **Content filters**: categories such as hate, insults, sexual, violence and misconduct, plus a **prompt attack** filter for jailbreaks and prompt injection, each with a strength setting.
- **Sensitive information filters**: built-in PII entity types and custom regular expressions, each with an action: **Block** (return the blocked message instead of the response) or **Mask/Anonymize** (replace the match with a placeholder tag, such as `{NAME}` for a name or the filter's name for a custom regex, and return the rest).
- **Word filters**: exact words and phrases, plus a managed profanity list.
## Reuse and versioning
You publish an immutable guardrail version and pass the guardrail ID and version on `InvokeModel` or `Converse` calls. Every application that references that version gets identical behavior, and the security team changes policy by publishing a new version.
W: One guardrail with topic, regex masking and prompt attack filters: the denied topic catches investment advice by meaning, masking removes account numbers while still returning the rest of the answer, and the prompt attack filter screens user input. Because the guardrail runs outside the model, it behaves the same for all three foundation models.
X: A=System prompt plus invocation logging: a system prompt depends on each model obeying it, which jailbreaks are designed to defeat, and log review only finds violations after customers have already seen them.
C=Fine-tuning plus Comprehend: fine-tuning shifts model behavior but gives no guarantee, must be repeated for three models, and does nothing against new jailbreak techniques. It is costly and still model-dependent.
D=Word filter and blocking PII action: a word list misses advice phrased without those words and blocks harmless mentions of "fund". The block action replaces the whole response, which breaks the requirement to keep answering the rest of the question.
T: Use one versioned guardrail for model-independent controls: denied topics for subjects, masking for data that must be removed but not block the answer, and the prompt attack filter for jailbreaks.
V: Amazon Bedrock, Amazon Bedrock Guardrails

@ SAP-C03 D2 T2.5 advanced troubleshooting
S: An insurance company runs a retrieval-augmented generation (RAG) assistant on Amazon Bedrock that answers questions about policy documents retrieved from a knowledge base. A guardrail with content filters set to High is attached. Auditors found answers that cite coverage limits that appear nowhere in the retrieved passages, and answers that drift to unrelated subjects when users ask narrow questions. The company wants such responses blocked automatically before users see them. What should a solutions architect do?
A: Add a denied topic to the guardrail named fabricated coverage information with sample phrases of invented limits, and raise the prompt attack filter to High so that misleading prompts are rejected at input
B: Set the model temperature to 0 and top-p to a low value for every request, and add a word filter that lists the coverage limit values that the policy documents contain
C: Enable the contextual grounding check with grounding and relevance thresholds, and pass the retrieved passages as the grounding source and the user question as the query
D: Raise the misconduct and violence content filters on model outputs from High to the maximum setting, and attach a second guardrail version to the knowledge base retrieval call
K: C
G: ## Harmful content versus unsupported content
Content filters judge whether text is harmful (hate, violence, misconduct and similar). A made-up coverage limit is not harmful in that sense, so content filters, however strict, let it through.
## Contextual grounding check
The contextual grounding check in Bedrock Guardrails compares a model response with two inputs you supply:
- the **grounding source**: the reference text, such as the passages the retriever returned;
- the **query**: the user's question.
It produces two scores between 0 and 1:
- **Grounding**: is the response factually supported by the source? Invented numbers score low.
- **Relevance**: does the response answer the query? An answer that drifts to another subject scores low.
You set a threshold for each. A response that scores below either threshold is blocked and replaced with your blocked message, for example "I could not find that in your policy documents".
W: Contextual grounding check: it measures exactly the two failures the auditors found, unsupported facts (grounding) and off-topic answers (relevance), against the passages actually retrieved, and blocks the response before it reaches the user.
X: A=Denied topic for fabricated information: denied topics describe a subject, not whether a statement is true. A response about coverage limits is on an allowed subject, and the prompt attack filter targets jailbreaks, not hallucinations.
B=Low temperature plus word filter: lower temperature makes output more deterministic but the model can still state an unsupported number, and a word list of real values cannot recognize an invented one.
D=Stricter content filters: content filters score harmful categories. A wrong coverage limit contains no hate or violence, so raising strength changes nothing for this problem.
T: Hallucinations and off-topic answers in RAG are caught by the contextual grounding check (grounding plus relevance thresholds), not by content filters or denied topics.
V: Amazon Bedrock Guardrails, Amazon Bedrock Knowledge Bases

@ SAP-C03 D2 T2.5 advanced use-case
S: A company runs two assistants on Amazon Bedrock: an internal HR assistant that may discuss salary bands with employees, and a public careers chatbot that must never discuss compensation. Both must mask email addresses and phone numbers in responses. Compliance requires that every guardrail policy change is tested before it reaches production, that production behavior never changes without an approved release, and that auditors can tell exactly which policy configuration each application used on a given date. Which combination of steps meets these requirements? (Select TWO)
A: Create a separate guardrail for each assistant from one shared infrastructure-as-code template, with the common PII masking in both and the compensation denied topic only in the chatbot guardrail
B: Create one shared guardrail that contains the compensation denied topic, and have the HR assistant switch that topic off on each request by passing a policy override in the guardrail configuration
C: Change and test the guardrail's working draft in a staging environment, then publish a numbered guardrail version and point production at that version only after the release is approved
D: Point both production assistants at the guardrail's working draft so that an approved edit takes effect at once in every application, without any separate code or configuration release
E: Keep the compensation and PII rules as versioned system prompt text in AWS Systems Manager Parameter Store, and log which parameter version each assistant loaded at startup
K: A,C
G: ## One guardrail is one policy
A Bedrock guardrail is a set of policies (content filters, denied topics, word filters, sensitive-information filters, contextual grounding) that is applied as a whole. A request names the guardrail and a version in its guardrail configuration (`guardrailIdentifier`, `guardrailVersion`, optional `trace`); there is no per-request switch that turns one policy of a guardrail on or off. Applications that need different rules therefore use different guardrails. Shared parts, such as the PII masking settings, stay consistent when every guardrail is built from the same CloudFormation or Terraform template.
## Working draft and versions
- Every guardrail has a mutable **working draft** (`DRAFT`). `UpdateGuardrail` changes it, and anything that references `DRAFT` sees the change immediately.
- `CreateGuardrailVersion` publishes an **immutable numbered version**, a snapshot of the draft at that moment. Version 3 always behaves like version 3.
A controlled release looks like this: change the draft, test it in staging (for example against a set of known good and bad prompts), publish a version, and after approval change production's configuration from version 2 to version 3. Rolling back means pointing at version 2 again.
## Audit evidence
CloudTrail records `UpdateGuardrail` and `CreateGuardrailVersion` calls, `GetGuardrail` returns the configuration of any version, and the application's deployment history shows which version it referenced on each date.
W: A=One guardrail per assistant from a shared template: the chatbot gets the compensation topic and the HR assistant does not, while the template keeps the email and phone masking identical in both.
C=Test the draft, release a numbered version: production only changes when its configuration is moved to a new immutable version after approval, and the version number identifies the exact policy in force on any date.
X: B=Per-request policy override: the guardrail configuration on a request names only the guardrail, its version and trace settings; a caller cannot disable one policy of a guardrail, so the HR assistant would be blocked from salary questions.
D=Production on the working draft: every edit, tested or not, reaches both assistants immediately, and because the draft keeps changing nobody can show which configuration was active on a past date.
E=Rules as system prompt text: prompt instructions depend on the model obeying them and do not mask data deterministically, so versioning the text gives change history for a control that is not reliable.
T: Use separate guardrails when applications need different policies, and release guardrail changes as immutable numbered versions after testing the working draft, never by pointing production at the draft.
V: Amazon Bedrock Guardrails, AWS CloudFormation, AWS CloudTrail

@ SAP-C03 D2 T2.5 advanced use-case
S: A media company uses Amazon Bedrock with a guardrail for its chat products. It also runs a fine-tuned open-weight model on an Amazon SageMaker AI endpoint and calls a third-party model provider's API for translation. The trust and safety team requires that prompts and responses for all three paths pass through exactly the same content, denied-topic and PII policies, maintained in one place, with no change of model providers. Which approach meets these requirements with the least operational effort?
A: Import the fine-tuned model with Amazon Bedrock Custom Model Import, move the translation workload to a Bedrock model, and attach the existing guardrail to every model invocation
B: Put Amazon API Gateway in front of the SageMaker endpoint and the third-party API, and attach AWS WAF with AWS managed rule groups and custom string-match rules for blocked topics
C: Add a guardrail configuration to the SageMaker endpoint configuration, and ask the third-party provider to call the company's guardrail from its side through a cross-account IAM role
D: Call the ApplyGuardrail API with the existing guardrail on each prompt before it is sent to the SageMaker endpoint or third-party API, and again on each response before returning it
K: D
G: ## Guardrails without a Bedrock model invocation
Guardrails are usually attached to a Bedrock `InvokeModel` or `Converse` call, but the **ApplyGuardrail** API evaluates any text against a guardrail on its own. You send the text and say whether it is an input (a prompt) or an output (a model response); the API returns whether the guardrail intervened, which policies matched, and the masked text when sensitive information was anonymized.
This lets one guardrail protect:
- models hosted on SageMaker AI or on your own infrastructure;
- third-party model APIs;
- any stage of a pipeline, for example checking retrieved documents or tool results.
## Typical pattern
1. The application calls `ApplyGuardrail` with the user prompt as input. If it intervenes, return the blocked message.
2. It calls the model (anywhere).
3. It calls `ApplyGuardrail` with the response as output, and returns the (possibly masked) text.
The same guardrail version used for Bedrock chat products can be referenced, so policies stay in one place.
W: ApplyGuardrail around each call: it applies the identical guardrail to prompts and responses for any model, so the SageMaker and third-party paths gain the same protections with a small code change and no change of provider.
X: A=Move everything onto Bedrock: it would work for content policy but it changes model providers and requires migrating the translation workload, which the requirement rules out, and it is far more effort than wrapping calls.
B=AWS WAF on API Gateway: WAF inspects HTTP requests with patterns and managed rule groups for web attacks. It cannot judge denied topics by meaning or mask PII in model responses.
C=Guardrail on the endpoint config: SageMaker endpoint configurations have no guardrail setting, and relying on an outside provider to call your guardrail removes the control from the company's hands.
T: For models outside Bedrock, call ApplyGuardrail on inputs and outputs so one guardrail governs every model path.
V: Amazon Bedrock Guardrails, Amazon SageMaker AI

@ SAP-C03 D2 T2.5 applied tradeoff
S: A healthcare provider uses Amazon Bedrock to summarize clinician notes for a care-coordination portal. Patient names and phone numbers must never appear in the summaries, but every note must still produce a usable summary. The compliance team also needs ongoing evidence of how often the guardrail acts on outputs. The current guardrail uses a sensitive-information filter with the Block action for names and phone numbers, and many summaries are being replaced by the blocked message. What change best meets the requirements?
A: Keep the Block action and add an Amazon Macie job that scans the portal's S3 export bucket each day, with findings sent to Security Hub CSPM as compliance evidence of guardrail activity
B: Change the name and phone entity actions to mask (anonymize) so matches become placeholders, and use the guardrail trace and its CloudWatch metrics on interventions as evidence
C: Replace the sensitive-information filter with a denied topic named patient identity, and log every blocked response to CloudWatch Logs for the compliance team to review each week
D: Remove the guardrail and instruct the model in the prompt to replace names and phone numbers with placeholders, then sample summaries manually each week for compliance evidence
K: B
G: ## Block versus mask for sensitive information
Each PII entity type or custom regex in a Bedrock guardrail has an action:
- **Block**: if the entity is found, the whole input or response is replaced by the configured blocked message. Use it when the request itself must not proceed, for example a prompt that contains a credit card number in a chat that must never handle card data.
- **Mask (anonymize)**: the matched text is replaced with a tag such as `{NAME}` or `{PHONE}`, and the rest of the text is returned. Use it when the content is useful but specific values must be removed.
Clinical notes almost always contain names, so Block on outputs throws away nearly every summary.
## Evidence that the guardrail works
When tracing is enabled, the response includes a guardrail trace that lists which policies matched and what action was taken. Bedrock Guardrails also publishes CloudWatch metrics, including counts of invocations where the guardrail intervened, which give the compliance team ongoing, aggregate evidence; model invocation logging can keep the full records.
W: Mask instead of block, with trace and metrics: masking removes names and phone numbers from every summary while keeping the summary usable, and the trace and intervention metrics document how often the guardrail acted.
X: A=Block plus Macie scans: Block keeps destroying summaries, which is the actual problem, and Macie scans S3 objects after the fact. It does not measure guardrail activity.
C=Denied topic for patient identity: a denied topic blocks the entire response just like the Block action, and summaries of patient notes would match it constantly.
D=Prompt instructions only: the model may miss or ignore the instruction, so names can leak, and manual sampling is weak evidence for a "never appear" requirement.
T: Block when the request must not proceed; mask when the content is needed but specific values must be removed. Use the guardrail trace and metrics as evidence.
V: Amazon Bedrock Guardrails, Amazon CloudWatch

@ SAP-C03 D2 T2.5 advanced use-case
S: A company runs a nightly reconciliation agent on Amazon Bedrock AgentCore Runtime. No user is signed in while it runs. The agent calls a payment partner's API, which accepts only OAuth 2.0 access tokens that the partner's authorization server issues through the client credentials grant with narrow scopes. Security requires that the client secret never appears in agent code, container images or environment variables, that the agent receives short-lived tokens only for its own workload identity, and that future agents can reuse the same managed pattern. Which design meets these requirements?
A: Configure an AgentCore Identity OAuth credential provider for the partner with the authorization code flow, have an operations engineer consent once, and let the token vault refresh that engineer's token every night
B: Configure an AgentCore Identity OAuth credential provider for the partner with the client credentials (machine-to-machine) flow, and have the agent request scoped access tokens at run time
C: Grant the runtime execution role permission to a private API Gateway API that forwards each request to the partner, and sign every agent call with SigV4 by using the runtime's temporary credentials
D: Have the build pipeline read the client secret from AWS Secrets Manager and write it into the container image as a KMS-encrypted file that the agent decrypts with its execution role at startup
K: B
G: ## Outbound credentials for an agent with no user
AgentCore Identity gives each agent a **workload identity** and manages the credentials the agent uses to call other systems through **credential providers**:
- **OAuth client credentials** (two-legged, machine-to-machine): the agent acts as itself. AgentCore Identity holds the client ID and secret, calls the partner's token endpoint, and returns an access token with the requested scopes.
- **OAuth authorization code** (three-legged, user-delegated): a user consents and the agent acts with that user's permissions. Tokens are stored in the **token vault** per agent and per user.
- **API key** providers for services that only accept keys.
The agent code asks for a token at run time (for example with the AgentCore SDK's `@requires_access_token` decorator and `auth_flow="M2M"`); it never reads the client secret itself. Because the secret and the token exchange live in the managed provider, a new agent only needs permission to use the same provider.
## Choosing the flow
Use client credentials when the work is done by the system, such as a scheduled batch job. Use the user-delegated flow only when actions must carry a specific person's permissions and that person is present to consent.
W: Client credentials provider in AgentCore Identity: it matches the grant the partner accepts, keeps the client secret inside the managed provider instead of the code, image or environment, and hands the agent short-lived scoped tokens tied to its workload identity.
X: A=User-delegated flow with one engineer's consent: the nightly job would act with a named employee's permissions, the partner accepts only client credentials tokens, and access breaks when that engineer leaves or revokes consent.
C=SigV4 through API Gateway: SigV4 proves an AWS identity to API Gateway, but the partner still requires its own OAuth token, so the forwarding layer would need the client secret anyway.
D=Secret baked into the image: encryption does not change the fact that the secret is shipped inside the container image, which the policy forbids, and rotating the secret requires a rebuild of every image.
T: For agent-to-API calls with no user present, use an AgentCore Identity OAuth provider with the client credentials (M2M) flow; reserve user-delegated OAuth for acting as a specific person.
V: Amazon Bedrock AgentCore, AgentCore Identity

@ SAP-C03 D2 T2.5 advanced use-case
S: A company hosts five AI agents on Amazon Bedrock AgentCore Runtime in a central AI platform account. The agents call tools implemented as AWS Lambda functions that are owned by business-unit accounts in the same organization. Each business unit must decide which agents may invoke its functions, each agent may call only the functions approved for it, a compromised agent must not be able to call another agent's tools, and no long-term credentials may be used. Which design meets these requirements?
A: Give each agent runtime its own execution role that allows lambda:InvokeFunction only on its approved function ARNs, and add a resource-based policy to each function that allows only the approved agents' role ARNs
B: Use one shared execution role for all five agents that allows lambda:InvokeFunction on every function in the organization, and list in each agent's system prompt the tools that it is allowed to call
C: Have each business unit add a resource-based policy to its functions that names the central platform account as the principal, and grant every agent execution role lambda:InvokeFunction on all resources
D: Create an IAM user with invoke rights in each business-unit account, store its access keys in AWS Secrets Manager in the platform account, and let each agent read the keys of the business units it uses
K: A
G: ## Cross-account invocation needs two allows
When a principal in one account invokes a Lambda function in another account, AWS evaluates both sides:
- the caller's **identity policy** in the platform account must allow `lambda:InvokeFunction` on the function ARN;
- the function's **resource-based policy** in the owning account must allow that principal.
If either is missing, the call is denied. This gives each side its own control.
## Making the principal specific
- Each AgentCore Runtime agent has its own **execution role**, so give every agent a separate role instead of a shared one. Its identity policy lists only the approved function ARNs, for example `arn:aws:lambda:us-east-1:111122223333:function:orders-status`.
- In the function policy, name the role ARN, for example `arn:aws:iam::444455556666:role/agent-support`. Naming the whole account (`arn:aws:iam::444455556666:root`) instead delegates the decision to the platform account: any role there whose identity policy allows the call can invoke the function.
Execution roles provide temporary credentials, so no access keys exist.
W: Per-agent role plus function policy naming that role: the platform account limits each agent to its approved ARNs, each business unit names exactly which agent roles may call it, and a compromised agent's credentials cannot reach another agent's tools.
X: B=Shared role with prompt-listed tools: every agent holds the union of all permissions, and a manipulated model can ignore the list in its prompt, so one compromised agent reaches every tool.
C=Account principal and wildcard grants: trusting the whole platform account plus wildcard identity policies lets any agent role invoke any function, so business units lose control over which agent calls them.
D=IAM user keys in Secrets Manager: long-term access keys break the no-long-term-credentials rule, and the agents share user identities, so the business unit cannot tell which agent made a call.
T: For cross-account agent tools, use one execution role per agent with ARN-scoped identity policies, and name those exact role ARNs in each Lambda function's resource-based policy.
V: Amazon Bedrock AgentCore, AWS Lambda, AWS IAM

@ SAP-C03 D2 T2.5 advanced use-case
S: An ecommerce company is building a customer support agent with Amazon Bedrock AgentCore. The agent has two tools: one returns order status and one issues refunds. A threat model highlights that a prompt injection in a customer message or a product review could make the agent refund another customer's order or exceed the 200 USD refund limit. Which combination of controls most effectively limits the impact of such an attack? (Select TWO)
A: Expose each tool as a separate AgentCore Gateway target backed by its own Lambda function, each with an execution role limited to the tables and actions that one tool needs
B: Add instructions to the agent's system prompt stating that refunds above 200 USD are forbidden and that the agent must refuse requests concerning orders of other customers
C: Enforce the refund limit and order ownership inside the refund tool's backend, checking each order against the authenticated customer of the session rather than fields the model supplies
D: Give the agent a single execution role with full read and write access to the orders and payments tables so that both tools can run efficiently from one shared code path
E: Add a denied topic for refunds to the guardrail used by the agent so that any message about refunds is blocked at input before the agent can consider calling the refund tool
K: A,C
G: ## Treat the model as untrusted
A large language model decides which tool to call and with what arguments, and prompt injection can steer that choice. Agent security therefore assumes the model may be manipulated and puts hard limits outside it:
- **Least privilege per tool**: each tool runs with only the permissions it needs. A read-only status tool that is tricked still cannot write anything. With AgentCore Gateway, each API or Lambda function becomes a separate target, and each Lambda function has its own execution role.
- **Deterministic authorization in the tool**: the tool code checks business rules (amount limits, ownership) using trusted inputs, such as the customer ID that the application established when the user signed in and bound to the session, not values the model wrote into the arguments.
- **Human approval** for high-impact actions and logging of every tool call complete the picture.
Prompt instructions and content filters still help, but they reduce probability; they do not bound the damage.
W: A=Separate gateway targets with minimal roles: a compromised call to the status tool cannot issue refunds, and the refund function can touch only the data it needs, which caps the blast radius.
C=Authorization in the refund backend: the limit and ownership checks run in deterministic code against the authenticated customer identity, so no injected instruction can push a refund past 200 USD or onto another customer's order.
X: B=System prompt rules: injection attacks exist precisely to override such instructions, so prompt rules lower the chance of misuse but cannot enforce a limit.
D=One broad shared role: it gives every tool the union of all permissions, so any successful injection can reach payment data. It is the opposite of least privilege.
E=Denied topic for refunds: it would block legitimate refund requests as well, breaking the use case, and an injection could still reach the tool through wording the topic does not catch.
T: Bound agent actions outside the model: least-privilege role per tool and deterministic authorization in the tool backend using the authenticated user identity.
V: Amazon Bedrock AgentCore, AWS Lambda, AWS IAM

@ SAP-C03 D2 T2.5 advanced use-case
S: A SaaS company runs one AI agent for several hundred tenants. The agent's tools read and write tenant data in a shared Amazon DynamoDB table whose partition key starts with the tenant ID. Tenants authenticate with Amazon Cognito, and the tenant ID is a claim in the access token. The company must guarantee that a tool call made for one tenant can never read another tenant's items, even if the model is manipulated into supplying another tenant's ID, and it wants to avoid per-tenant infrastructure. Which approach meets these requirements?
A: Deploy a separate agent runtime, tool set and DynamoDB table for each tenant in its own AWS account through an account vending pipeline, and route requests to the right account by subdomain
B: Add the tenant ID to the agent's system prompt for each session and instruct the model to always pass that ID to the tools, then enable a guardrail denied topic for other tenants' data
C: Have the tool code filter the query results by comparing each item's tenant attribute with the tenant ID argument the model supplies to the tool, and log any mismatches for review
D: Have tools assume a role with a session tag set from the validated token's tenant claim, under a policy using dynamodb:LeadingKeys matched to the aws:PrincipalTag tenant value
K: D
G: ## Tenant isolation with ABAC
Attribute-based access control (ABAC) lets one IAM policy serve every tenant by comparing attributes at request time:
- When the tool backend calls `sts:AssumeRole`, it passes a **session tag** such as `TenantId=t-123`, taken from the claim in the validated Cognito token (not from anything the model produced).
- The role's policy allows DynamoDB actions only when `dynamodb:LeadingKeys` matches `${aws:PrincipalTag/TenantId}`, so the session can touch only items whose partition key is that tenant's ID.
- The role's trust policy must allow `sts:TagSession` for the backend that tags the session.
Even if the model asks for another tenant's ID, DynamoDB rejects the request because the credentials themselves are scoped to one tenant. One role and one policy serve all tenants.
W: Session tags plus dynamodb:LeadingKeys: isolation is enforced by IAM on every DynamoDB request using the tenant from the verified token, so a manipulated model cannot widen access, and no per-tenant infrastructure is needed.
X: A=Account per tenant: it gives strong isolation but creates hundreds of accounts, runtimes and tables to operate, which the company explicitly wants to avoid.
B=Tenant ID in the prompt: the model is the component that might be manipulated, so trusting it to pass the right ID offers no guarantee, and a denied topic cannot recognize which tenant an item belongs to.
C=Filter on the model-supplied ID: the filter compares against an argument the model controls, so an injected ID passes the check, and the credentials can still read every tenant's items.
T: Scope agent tool credentials per tenant with session tags from the verified token and conditions like `dynamodb:LeadingKeys`, never with IDs the model supplies.
V: AWS IAM, AWS STS, Amazon DynamoDB, Amazon Cognito

@ SAP-C03 D2 T2.5 applied use-case
S: A company with 200 accounts in AWS Organizations allows Amazon Bedrock for experimentation. After a legal review, only four foundation models are approved for use. Platform teams must be able to keep using Bedrock management APIs such as guardrail and knowledge base operations. Security wants a preventive control that member account administrators cannot override and that requires no per-account work when new accounts are created. What should a solutions architect implement?
A: An AWS Config organization rule that detects invocations of unapproved models in AWS CloudTrail data and invokes an SSM Automation runbook to detach the calling role's Bedrock permissions
B: A guardrail in every account with denied topics that describe the unapproved models' names, so that prompts which mention those models are blocked before inference starts
C: An SCP on the root that denies Bedrock inference actions unless the resource is one of the approved foundation model or inference profile ARNs, leaving other Bedrock actions alone
D: A permissions boundary in every account that allows only the approved model ARNs, with an AWS Lambda function that attaches the boundary to every new role created in member accounts
K: C
G: ## Organization-wide model allow lists
Access to a specific Bedrock model is authorized with IAM on the inference actions `bedrock:InvokeModel` and `bedrock:InvokeModelWithResponseStream` (they also cover the Converse and ConverseStream APIs), using the model or inference profile ARN as the resource, for example `arn:aws:bedrock:*::foundation-model/<model-id>`.
A **service control policy** can cap these actions across an organization:
- A `Deny` statement on the inference actions with `NotResource` set to the approved model and inference profile ARNs blocks every other model.
- Because only the inference actions are listed, management actions such as creating guardrails or knowledge bases keep working.
- SCPs apply to all principals in member accounts, including account administrators, and new accounts inherit them automatically when they join the OU or root.
Remember that inference profiles also need the underlying model ARNs in their destination Regions to be allowed.
W: SCP allow-list on inference actions: it is preventive, account administrators cannot override it, it applies automatically to new accounts, and limiting it to inference actions leaves management APIs untouched.
X: A=Config rule with remediation: it reacts after an unapproved model has already been invoked, and removing the role's Bedrock permissions also breaks approved use.
B=Denied topics naming models: guardrails filter the text of prompts and responses, not which model serves the request. A prompt never needs to mention the model it is sent to.
D=Permissions boundary plus Lambda: it relies on custom automation per account and per role, administrators can remove or bypass boundaries, and any role created before the function runs is uncovered.
T: Restrict which foundation models can be used with an SCP on the inference actions scoped to approved model and inference profile ARNs.
V: Amazon Bedrock, AWS Organizations, AWS IAM

G: ## Pausing a workflow for a human
AWS Step Functions **Standard** workflows can run for up to one year and keep a full execution history, which makes them a good fit for approvals.
The **callback pattern** works like this:
1. A task state uses the `.waitForTaskToken` integration (for example with Lambda, SNS or SQS) and passes the task token from the context object (`$$.Task.Token`) in the payload.
2. The integration delivers the request to the approver, for example a message with approve and reject links that call an API.
3. The execution pauses without consuming compute.
4. The approval backend calls `SendTaskSuccess` (with the decision as output) or `SendTaskFailure` with the token, and the workflow continues to the apply step or a rejection branch.
A `TimeoutSeconds` value on the task defines how long to wait, and a `Catch` can route a timeout to escalation. Execution history and CloudTrail record each step and API call.
## Limits that rule out the alternatives
- Express workflows run for at most 5 minutes and do not support the `.waitForTaskToken` pattern.
- Lambda functions run for at most 15 minutes.
- Amazon SQS delivery delay is at most 15 minutes.

X: A=SQS delivery delay: the maximum delay is 15 minutes, and a delay only postpones the message; the plan would be applied without anyone approving it.
B=Express workflow with a Wait state: Express workflows end after 5 minutes, so a 3-day wait is impossible, and polling a table is not an approval mechanism.
C=Lambda polling loop: a Lambda invocation is limited to 15 minutes, and holding compute while waiting is wasteful and loses the state if it times out.

G: ## Task tokens and timeouts
In the callback pattern, a task token is valid only while its task is waiting. Two settings control how long:
- `TimeoutSeconds`: the maximum time the task waits for `SendTaskSuccess` or `SendTaskFailure`. When it passes, the task fails with `States.Timeout`.
- `HeartbeatSeconds`: if set, the worker must call `SendTaskHeartbeat` at least this often, or the task fails with `States.Timeout`. Heartbeats prove a worker is still alive; they do not extend `TimeoutSeconds`.
After a timeout, any later call with that token is rejected (`TaskTimedOut`). Tokens cannot be regenerated for a task that has already ended.

@ SAP-C03 D2 T2.2 advanced tradeoff
S: A government contractor stores engineering data in Amazon S3 encrypted with AWS KMS symmetric keys and sends the same data between on-premises sites and AWS over TLS connections that use classical elliptic-curve key exchange. The data must stay confidential for at least 25 years. A security review warns that an adversary may be recording traffic today. The company has a limited budget for its first post-quantum project. Which action addresses the most urgent risk?
A: Re-encrypt all S3 objects with new KMS keys and shorten key rotation to 90 days, because the symmetric keys that protect data at rest are the first targets of a quantum computer
B: Increase every RSA and ECDSA key used for TLS certificates to the largest available size, because larger classical keys keep recorded sessions secure against quantum attacks
C: Replace all code-signing and document-signing keys with ML-DSA keys first, because forged signatures are the main risk of traffic that adversaries record today
D: Move connections carrying this data to TLS 1.3 with hybrid post-quantum key exchange (classical ECDHE combined with ML-KEM) on clients and endpoints that support it
K: D
G: ## Harvest now, decrypt later
A large quantum computer running Shor's algorithm would break the public-key algorithms used today for key exchange and signatures (RSA, Diffie-Hellman, elliptic curves). Such a computer does not exist yet, but an adversary can **record encrypted traffic now** and decrypt it once one does. Data that must stay secret for decades is therefore already at risk if its session keys were agreed with classical key exchange.
## What is and is not affected
- **Symmetric encryption** such as AES-256 (used by KMS symmetric keys and S3 encryption) is only weakened by Grover's algorithm, which roughly halves the effective key strength; AES-256 is considered quantum-resistant.
- **Key exchange** in TLS is the urgent target, because recorded handshakes can be broken later.
- **Signatures** matter when a quantum computer exists to forge them; past signatures cannot be used to decrypt anything.
## The fix: ML-KEM in hybrid mode
ML-KEM (FIPS 203) is the NIST-standardized post-quantum key encapsulation mechanism. In TLS 1.3, a **hybrid** key exchange such as X25519 combined with ML-KEM-768 derives the session key from both, so traffic stays protected unless both are broken. AWS service endpoints such as AWS KMS, AWS Certificate Manager and AWS Secrets Manager support hybrid post-quantum TLS for clients that offer it.
W: Hybrid post-quantum key exchange: it protects new sessions against record-now-decrypt-later attacks, which is the threat the review named, while keeping classical ECDHE as a safety net.
X: A=Re-encrypt at rest: data at rest uses AES-256, which is not the weak point, so re-encryption spends the budget without reducing the main risk to recorded traffic.
B=Larger classical keys: Shor's algorithm breaks RSA and elliptic-curve schemes regardless of size, so bigger keys only add cost.
C=ML-DSA signing first: post-quantum signatures are needed eventually, but recorded traffic is threatened through key exchange, not through signatures, so this does not address the most urgent risk.
T: Long-lived secrets in transit face harvest-now-decrypt-later: prioritize hybrid ML-KEM key exchange in TLS; AES-256 at rest is already quantum-resistant.

@ SAP-C03 D2 T2.2 applied comparison
S: Security architects are deciding how to configure TLS between an internal client fleet and AWS service endpoints for traffic that must resist future quantum attacks. D: The session key is derived from both shared secrets, so it stays secure unless both algorithms are broken, which hedges against undiscovered flaws in the newer ML-KEM
K: D
G: ## How hybrid key exchange works
In a TLS 1.3 handshake, client and server agree on a shared secret through a key share. With a hybrid group such as `X25519MLKEM768`:
- The client sends an X25519 public key and an ML-KEM-768 encapsulation key in one key share.
- The server returns its X25519 share and an ML-KEM ciphertext.
- Both sides compute two shared secrets and feed both into the TLS key schedule to derive the session keys.
Records are then encrypted once, with a normal AEAD cipher such as AES-GCM.
## Why hybrid during the transition
- **Hedging**: ML-KEM is new compared with elliptic-curve Diffie-Hellman. If a flaw is found in ML-KEM or its implementation, X25519 still protects the session against classical attackers; if a quantum computer appears, ML-KEM still protects it. An attacker must break both.
- **Maturity**: X25519 has years of deployment and analysis behind it, while ML-KEM implementations are still new, so keeping both reduces the risk of an early implementation bug.
- **Cost**: hybrid adds roughly a kilobyte in each direction of the handshake (the ML-KEM-768 key and ciphertext) and a little computation, but nothing per record.
W: Both secrets feed the session key: security holds as long as either component remains unbroken, which protects against both future quantum attacks and possible weaknesses in the newer algorithm.
X: A=Smaller handshakes: hybrid messages are larger, because ML-KEM keys and ciphertexts are added to the classical share; the extra size is the cost, not a benefit.
B=ML-KEM only works with TLS 1.2: the post-quantum key exchange groups are defined for TLS 1.3 key shares; TLS 1.3 is required for them, not a reason to add a classical algorithm.
C=Double encryption of records: hybrid affects only key establishment. The derived session key encrypts each record once with a single AEAD cipher.
T: Hybrid TLS key exchange (X25519 + ML-KEM-768) combines two secrets into one session key, so a session is safe unless both algorithms fall.
