# PLTR-DE batch 20: Domain 3 round 3 (Pipeline Processing Modes), 8 questions

@ PLTR-DE D3 T3.1 applied use-case
S: A regulatory report is produced from a 3-year transaction history every month-end. Inputs are final by the 2nd of the month. Which processing mode is appropriate for the report transform?
A: Streaming, so that the report is continuously up to date and ready the moment the month ends
B: A scheduled monthly batch that runs after the inputs are final, recomputing the report from the full history
C: Hourly incremental processing throughout the month, so that the report is already complete and waiting on the 1st before inputs are final
D: A lightweight single-node transform run by hand whenever someone remembers that the report is due
K: B
G: ## Batch for periodic, authoritative outputs
The exam guide places batch processing with periodic or historical work. A monthly regulatory report needs a complete, reproducible computation over finalized inputs; freshness during the month has no value.
## Design
- Trigger: after the 2nd, once the inputs' finality is confirmed (event or date condition).
- Full recompute from history, which makes the report reproducible and auditable.
- Expectations on totals and completeness; the output is versioned per period.
Example: the March report builds on April 3rd from the full history and matches the finance ledger.
W: Monthly full batch after finality: it produces an authoritative, reproducible report with no unnecessary processing.
X: A=Streaming: continuous computation of a report that only matters once a month.
C=Hourly incremental: produces intermediate states nobody uses and complicates reproducibility.
D=Manual lightweight: unscheduled and risky for a regulatory obligation; also likely too large for one node.
T: Periodic authoritative outputs are full batch runs after inputs are final.
V: schedules, Code Repositories

@ PLTR-DE D3 T3.2 applied troubleshooting
S: A dataset consumer complains that a row they deleted from the source still appears in Foundry a week later. The sync is append-only. What is happening?
A: The agent is caching rows and must be restarted to clear the deleted row from Foundry
B: An append-only sync never removes rows; deletions need CDC with deletes, periodic snapshots, or a soft-delete flag
C: The deletion will appear automatically in Foundry after the dataset's default retention period of 30 days expires and the row ages out
D: The Ontology keeps deleted rows for audit and they cannot be removed from the dataset
K: B
G: ## Append semantics do not carry deletes
The exam guide asks you to understand transaction semantics and sync patterns. An APPEND transaction only adds files; nothing in the pattern expresses "this row no longer exists".
## Options
- CDC: delete events replicated and applied downstream.
- Periodic snapshot: the source's current state replaces the dataset; deletions disappear.
- Soft deletes: the source marks rows deleted; a transform filters them.
Example: a weekly snapshot reconciliation removes deleted rows; CDC would remove them within minutes.
W: Append cannot represent deletions: the pattern must change or deletions must be signalled another way.
X: A=Agent cache: agents transport data; they do not hold rows that keep a dataset populated.
C=Retention expiry: datasets do not automatically drop rows after a period.
D=Audit retention: the dataset is a copy of the source; it can and should reflect deletions if the pattern supports them.
T: Append-only ingestion never deletes; use CDC, snapshots or soft-delete flags when deletions matter.
V: Data Connection, transactions

@ PLTR-DE D3 T3.4 applied use-case
S: A streaming pipeline must guarantee that each sensor event affects the aggregate exactly once, even though the source may redeliver messages after network errors. Which design provides this?
A: Trusting the source, since message brokers never deliver a message more than once
B: Deduplication on a unique event id within a bounded window, with idempotent updates to the aggregate keyed on that id
C: Counting every message as received, since duplicates are rare and cancel out over time
D: Restarting the streaming pipeline whenever a duplicate is suspected so that its state is rebuilt from scratch and any duplicate is forgotten
K: B
G: ## Exactly-once effect through idempotency
Many sources deliver at least once; duplicates are normal. The exam guide asks you to handle state and replay safely in streaming.
## Design
- Each event carries a unique id (or a deterministic hash of its content).
- The pipeline keeps a bounded window of seen ids (TTL) and drops repeats.
- Aggregate updates are idempotent per event id.
Example: a redelivered event from a retry is recognized within the 10-minute window and discarded; the hourly count stays correct.
W: Windowed deduplication plus idempotent updates: the aggregate reflects each event once despite redelivery.
X: A=Trust the broker: at-least-once delivery is the norm; duplicates will arrive.
C=Count everything: duplicates inflate counts; they do not cancel out.
D=Restart on suspicion: destructive and does not prevent duplicates on the next replay.
T: Achieve exactly-once effects in streaming with event ids, bounded deduplication and idempotent state updates.
V: streaming

@ PLTR-DE D3 T3.3 applied tradeoff
S: An upstream team wants to switch their dataset from daily APPEND transactions to a daily SNAPSHOT because it is "simpler". Three incremental transforms depend on it. What should the data engineer explain?
A: Nothing changes for consumers, since the data content is the same either way and the transaction type is an internal detail of the upstream team
B: All three consumers would fall back to full recompute daily; if snapshots are truly needed, consumers must redesign, so the change must be coordinated
C: The switch is fine as long as the snapshot is taken at night when the consumers are not running
D: Snapshots are illegal for datasets that have incremental consumers, so the request must be refused
K: B
G: ## Transaction type is part of the contract
The exam guide asks you to understand incremental fallback and to assess consumers before changing semantics. A daily SNAPSHOT upstream means daily fallback downstream.
## Explanation
- Fallback consequences: runtime and cost for all three consumers.
- Alternatives: keep APPEND (often not harder), or add a diffing transform that converts snapshots into change records consumers can process incrementally.
- Coordination: consumers must agree and adapt before the change.
Example: the upstream team learns that writing a new file per day is as simple as replacing the dataset and keeps APPEND.
W: Daily fallback for all consumers, requiring coordination or a diffing stage: the real impact of a transaction-type change.
X: A=Internal detail: transaction type directly controls incremental behaviour downstream.
C=Timing: fallback happens whenever consumers next run, regardless of when the snapshot lands.
D=Illegal: snapshots are allowed; the point is informed coordination, not refusal.
T: Upstream transaction types are part of the contract with incremental consumers; change them only with coordination.
V: transactions, incremental transforms

@ PLTR-DE D3 T3.1 applied comparison
S: A team wants metrics on website events with a 5-minute freshness requirement during business hours and no requirement overnight. Events arrive as a stream. What is a cost-aware design?
A: A full batch transform every 5 minutes around the clock over the entire event history
B: A streaming or micro-batch pipeline for live metrics in business hours, with overnight batch consolidation for historical aggregates
C: Nightly batch only, telling the business that 5-minute freshness is not achievable on a stream of this volume without unreasonable cost
D: A lightweight transform every minute over all history, since lightweight engines are cheap
K: B
G: ## Hybrid modes for mixed requirements
The exam guide asks you to choose modes by latency, volume and cost, and allows different modes for different parts of a pipeline. Live metrics need continuous processing; historical aggregates do not.
## Design
- Streaming or short micro-batches during the day for recent-window metrics (bounded state).
- Overnight batch over the persisted stream for daily and historical aggregates, compaction and reconciliation.
- Cost follows the requirement: continuous compute only when freshness matters.
Example: live dashboards update within minutes; the overnight batch produces the daily rollup used by reports.
W: Streaming for the live window, batch for history: freshness where it is needed and efficient computation elsewhere.
X: A=Full batch every 5 minutes: recomputing all history 288 times a day is wildly inefficient.
C=Nightly only: ignores the business-hours requirement that streaming can meet.
D=Lightweight every minute over history: history outgrows a single node, and the overnight period needs no processing.
T: Combine streaming for live windows with batch for history when requirements differ by time or scope.
V: streaming, Pipeline Builder

@ PLTR-DE D3 T3.4 applied troubleshooting
S: After a streaming pipeline was changed to add a new field, records from before the change lack the field and downstream code fails on them. How should schema evolution have been handled?
A: By clearing the stream and its retained history and starting over, so that only records carrying the new field ever exist in the pipeline
B: By making the new field optional in the schema and downstream code so old and new records coexist, with a backfill or default where needed
C: By rejecting any record that lacks the field, since the schema now requires it
D: By converting the pipeline to batch, which handles schema changes automatically
K: B
G: ## Schema evolution in streams
The exam guide names schema evolution among streaming concerns to handle safely. Streams carry history; a schema change must be compatible with records already in flight or retained.
## Practice
- Additive, optional fields; consumers tolerate absence.
- Defaults or backfill for logic that depends on the field.
- Version the schema; test downstream with both old and new records.
Example: `region` is added as nullable; the aggregation treats null as "unknown" until the backfill assigns regions to old records.
W: Optional field with tolerant consumers and backfill: old and new records coexist without failures.
X: A=Clear the stream: destroys retained data and replay ability.
C=Reject old records: drops legitimate data that arrived before the change.
D=Batch conversion: batch pipelines need the same compatibility discipline; mode does not solve schema evolution.
T: Evolve stream schemas additively with optional fields and tolerant consumers.
V: streaming

@ PLTR-DE D3 T3.3 applied use-case
S: An incremental transform should process late corrections to already-processed days without reprocessing the entire history. The source delivers corrections as APPEND files tagged with the day they correct. Which design works?
A: Ignore the day tags and append corrections as new rows, letting consumers figure out for themselves which rows are corrections of which
B: Keyed, idempotent processing: output partitioned by day and key, with a correction's day tag directing the merge to that day's partition
C: Switch to a full snapshot transform so every correction triggers a complete recompute
D: Reject corrections older than the previous run, since incremental transforms cannot modify past output
K: B
G: ## Targeted reprocessing
The exam guide asks you to handle replay, state and corrections safely and to prefer bounded reruns over full recompute. Day-tagged corrections make targeted updates possible.
## Design
- Output keyed by (day, entity key).
- A correction file for day D updates D's partition for the affected keys (merge semantics).
- Idempotent: reapplying the same correction yields the same output.
- Reconciliation check per day against the source.
Example: a correction for the 3rd updates only that day's rows; the other 364 days are untouched.
W: Day-partitioned, key-merged, idempotent updates: corrections land exactly where they belong without full recompute.
X: A=Append and hope: consumers get duplicate and conflicting rows.
C=Full snapshot per correction: throws away incremental efficiency entirely.
D=Reject: corrections are legitimate; the output must be allowed to change for past days.
T: Design incremental outputs so tagged corrections can update specific partitions and keys idempotently.
V: incremental transforms

@ PLTR-DE D3 T3.2 advanced tradeoff
S: A dataset receives a DELETE transaction removing last month's files for data-retention reasons. A downstream incremental transform keeps a running total. What is the correct consequence and handling?
A: The running total should remain unchanged because retention deletions are administrative and should not affect any computed values downstream
B: The transform falls back to a full recompute over retained files; totals that must include deleted periods need a rollup materialized before deletion
C: The transform will crash and must be deleted and rebuilt from scratch
D: The DELETE will be ignored by the transform because incremental transforms only read APPEND transactions
K: B
G: ## Deletions and derived values
A DELETE changes the input view; an incremental transform cannot know what to subtract and falls back to full recompute, which is correct for "the data that exists". The exam guide asks you to understand DELETE semantics and plan for retention.
## Planning
- Before deleting raw data, materialize any aggregates that must survive (monthly rollups) in a separate retained dataset.
- Expect the fallback run and its cost.
- Document that totals over deleted periods come from the rollup, not the raw data.
Example: the monthly rollup dataset retains last month's total; the running total over raw data now starts from this month.
W: Fallback recompute over retained data with pre-materialized rollups for history: the correct behaviour and the right preparation.
X: A=Unchanged: the transform cannot keep values for data it no longer sees; the fallback recomputes without it.
C=Crash and rebuild: fallback is a normal, handled mode; nothing needs deleting.
D=Ignored: a DELETE changes the input view, so the incremental transform cannot continue from its state; it triggers fallback rather than being skipped.
T: Before retention deletions, materialize the aggregates that must outlive the raw data; expect fallback recompute afterwards.
V: transactions, incremental transforms
