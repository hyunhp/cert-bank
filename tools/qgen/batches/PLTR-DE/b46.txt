@ PLTR-DE D5 T5.1 applied use-case
S: An orders dataset must satisfy: every order has exactly one customer, the order total equals the sum of its line items within one cent, and order dates are not in the future. Where should these rules be enforced?
A: As health checks on the published dataset that alert the owner after consumers have already received the data for the day
B: As build-blocking expectations on the curated dataset, with the line sum computed in the transform and asserted
C: As a weekly manual review by an analyst who samples a few orders and compares them against the source system by hand
D: As notes in the dataset description so that consumers know which rules the data is supposed to satisfy
K: B
G: ## Invariants are expectations
The exam guide asks you to block invalid transactions when correctness matters. All three rules are always true for valid data, so they belong at build time.
## Implementation
- Expectation: customer id non-null and unique per order.
- Transform computes `line_sum`; expectation asserts |total − line_sum| ≤ 0.01.
- Expectation: order date ≤ build date.
Example: a source bug that doubles one line item fails the build at 02:10; consumers keep yesterday's correct data.
W: Build-blocking expectations for all three invariants: invalid orders are stopped before publication, and the computed line sum makes the cross-row rule checkable.
X: A=Health checks after publication: consumers have already seen the invalid orders by the time the alert fires.
C=Weekly manual sampling: catches a fraction of violations a week late, if at all.
D=Description notes: describe the rules without enforcing any of them.
T: Enforce data invariants with build-blocking expectations, computing derived checks in the transform where needed.
V: expectations

@ PLTR-DE D5 T5.2 applied troubleshooting
S: An expectation began failing every night after a source started sending a small number of legitimately negative quantities (returns). The expectation requires quantity > 0. What should be done?
A: Remove the expectation entirely so that the nightly builds stop failing on the returns
B: Update the contract: allow negative quantities for return rows only, keep the rule for sales, and add a test case
C: Filter out all negative quantities in the transform before the expectation runs so that the nightly build passes again
D: Ask the on-call engineer to override the expectation manually every night
K: B
G: ## When the contract changes
The exam guide asks for expectations that encode the real contract. A new legitimate business case means the contract changed; the rule should change deliberately.
## Update
- Agree with the business: returns are negative, sales are positive.
- Expectation: `quantity > 0 OR order_type = 'return'` (and the converse for returns).
- Test case covering returns.
Example: returns pass; a negative sale caused by a bug still fails the build.
W: A deliberate contract update that distinguishes returns from sales: legitimate data passes and genuine errors are still caught.
X: A=Remove the expectation: negative sales from real bugs would then publish unchecked.
C=Filter negatives: silently drops legitimate returns, making totals wrong.
D=Nightly override: a person manually bypassing a correctness control every single night, with no review of what slips through.
T: When legitimate data violates a rule, update the contract precisely instead of removing or bypassing the check.
V: expectations

@ PLTR-DE D5 T5.3 applied use-case
S: A dataset should receive roughly 50,000 rows per weekday and 5,000 on weekends. A team wants to be alerted when a day's volume is abnormal. Which configuration is appropriate?
A: A fixed alert whenever the row count is below 50,000, which will fire every weekend but is simple to configure
B: A size check with day-of-week expected ranges or same-weekday history, alerting beyond a tolerance
C: No volume monitoring, since row counts naturally vary and alerts would be noisy
D: An alert whenever the row count differs from yesterday's count by any amount at all
K: B
G: ## Seasonality-aware volume checks
The exam guide asks for health checks that reflect the data's real patterns. A weekly cycle needs expected ranges per day type.
## Configuration
- Expected range per weekday and weekend, or comparison with the same weekday over recent weeks.
- Tolerance such as ±30%.
- Alert routing to the owner.
Example: Saturday's 4,800 rows pass; a Tuesday with 18,000 rows alerts within minutes of the build.
W: Day-aware expected ranges with tolerance: real anomalies alert while normal weekly patterns stay quiet.
X: A=Fixed threshold: fires every weekend, teaching the team to ignore the check.
C=No monitoring: a half-delivered weekday goes unnoticed until consumers complain.
D=Any difference from yesterday: Monday versus Sunday always differs; the alert is pure noise.
T: Configure volume checks with expected ranges that follow the data's known cycles.

@ PLTR-DE D5 T5.1 applied comparison
S: Which statement best describes when to choose a build-blocking expectation over an alert-only check?
A: Always choose blocking, because any data problem should stop the pipeline until a person has reviewed it
B: Block when a violation would harm consumers and has no legitimate exceptions; alert when it may be legitimate
C: Always choose alert-only, because blocking builds causes outages that are worse than bad data
D: Choose randomly, since both mechanisms provide the same protection in practice
K: B
G: ## The decision rule
The exam guide's self-check asks whether a requirement needs blocking, alerting, or both. The deciding factors are consequence and the existence of legitimate exceptions.
- Block: invariants with harmful consequences (null keys, invalid currency).
- Alert: signals that may be legitimate (volume shifts, distribution changes).
Example: a null primary key blocks; a 25% drop in order count alerts while the build publishes.
W: Block invariants whose violation would harm consumers; alert on conditions that may be legitimate: the rule that keeps pipelines both safe and available.
X: A=Always block: legitimate changes would halt correct pipelines constantly.
C=Always alert: harmful invalid data would be published before anyone reacts.
D=Random: the mechanisms protect differently; the choice matters.
T: Choose blocking or alerting by consequence and by whether legitimate exceptions exist.

@ PLTR-DE D5 T5.3 applied troubleshooting
S: A health check on the number of distinct customers per day dropped by 40% overnight, but total rows are unchanged. What does this suggest and how should it be investigated?
A: Customer behaviour changed overnight and nothing technical needs to be checked
B: Customer ids were likely collapsed (a placeholder or overwriting join); check the id distribution and upstream changes
C: The health check is broken and should be deleted because totals did not change
D: The number of distinct customers per day is not a meaningful quality metric and should never have been monitored at all
K: B
G: ## Same rows, fewer distinct keys
The exam guide asks for content checks and investigation of anomalies. Unchanged row counts with far fewer distinct ids points to identifiers being overwritten or collapsed.
## Investigation
- Distribution: is one id now very frequent (a default such as 0 or "UNKNOWN")?
- Upstream: a source change, a join that replaced ids, a mapping table issue.
- Fix the cause; add an expectation on the placeholder value.
Example: a source started sending "UNKNOWN" for guest checkouts; 40% of orders now share that id.
W: Collapsed identifiers revealed by the distinct-count drop: the distribution and upstream changes locate the cause.
X: A=Behaviour change: 40% fewer distinct customers overnight with the same order volume is implausible behaviour.
C=Delete the check: it detected a real defect that totals alone could not show.
D=Not meaningful: distinct-key counts are a standard identity-quality signal.
T: Distinct-count drops with stable volume usually mean identifiers were collapsed; inspect the distribution.

@ PLTR-DE D5 T5.2 applied use-case
S: A pipeline needs to publish a dataset daily even when a small fraction of rows fail validation, but consumers must never see invalid rows. What design meets both requirements?
A: Publish everything and flag invalid rows with a column that consumers are asked to filter on
B: Route valid rows to the curated output and invalid rows to a rejects dataset with reasons, capping the reject rate
C: Fail the whole build whenever any single row fails validation, regardless of how many of the other rows are perfectly valid
D: Fix invalid rows automatically by replacing bad values with defaults so that every row passes
K: B
G: ## Quarantine at row level
The exam guide asks for expectations that block invalid data and for quarantine patterns. Row-level splitting keeps good data flowing while making bad data visible.
## Design
- Validation in the transform: valid → curated; invalid → rejects with reason.
- Expectations on curated output (no invalid rows).
- Expectation on reject rate (e.g., < 1%) so a systemic problem still blocks.
Example: 120 of 80,000 rows are rejected with reasons; the curated dataset publishes on time.
W: Row-level quarantine with a reject-rate cap: consumers get only valid rows, the pipeline publishes daily, and a surge of rejects still stops it.
X: A=Flag and ask consumers to filter: relies on every consumer remembering to filter; invalid rows leak.
C=Fail on any row: one bad row stops all valid data every day.
D=Default replacement: fabricates values and hides source problems.
T: Quarantine invalid rows with reasons and cap the reject rate, publishing only valid rows.

@ PLTR-DE D5 T5.3 applied use-case
S: Which monitoring combination most quickly detects that a curated dataset is complete in rows but wrong in a key business total?
A: A schema check and a build-status check on the curated dataset, which together cover structure and success
B: Reconciliation of the dataset's total against an independent source control total, plus amount distribution checks
C: A row-count check with a tight tolerance on the curated dataset, since completeness implies correctness
D: A freshness check on the curated dataset that alerts if the data is older than one day
K: B
G: ## Correctness beyond completeness
The exam guide asks for reconciliation and content checks because complete, fresh, well-formed data can still be wrong.
## Combination
- Reconciliation: dataset total versus the source's control total.
- Distribution: mean and percentiles of the amount column against history.
- Alert on mismatch beyond tolerance.
Example: a currency conversion applied twice leaves row counts intact but the total 8% low; reconciliation fires on the first build.
W: Reconciliation against an independent control total with distribution checks: the only combination that sees wrong values in complete data.
X: A=Schema and build status: a build that writes well-formed but wrong amounts passes both checks without any signal.
C=Row count: every row can be present while its amount is wrong; completeness says nothing about the values.
D=Freshness: the wrong total is published on time; a freshness check confirms only that it is recent.
T: Detect wrong totals with reconciliation against independent figures and distribution checks.

@ PLTR-DE D5 T5.1 advanced tradeoff
S: A critical dataset has 25 expectations, and the team finds that builds fail several times a week on expectations that turn out to be too strict, delaying consumers. What is a balanced response?
A: Remove all expectations so that the builds never fail again
B: Review each failing rule against the contract: keep true invariants, relax or convert wrong ones to alerts, document
C: Ignore failures by configuring the pipeline to publish even when expectations fail
D: Add more expectations so that real problems are more likely to be caught among the false ones
K: B
G: ## Expectation hygiene
The exam guide asks for expectations that reflect the real contract. Overly strict rules cause outages; the fix is per-rule review, not abolition.
## Review
- For each failing rule: is it a true invariant? Keep.
- Wrong assumption: relax the rule or convert to a health check.
- Document decisions; track how often each rule fails falsely.
Example: 6 of 25 rules are relaxed or converted; false failures drop from four a week to one a month.
W: Per-rule review against the contract with documentation and tracking: false failures fall while real protection remains.
X: A=Remove all: the real invariants among the 25 lose their protection along with the over-strict ones.
C=Publish on failure: an expectation that never blocks is just a log line; invalid data publishes anyway.
D=More rules: adding untuned rules increases false failures and delays; it does not separate real problems from noise.
T: Review overly strict expectations individually against the real contract instead of removing them all.
V: expectations
