# PLTR-DE batch 09: Domain 8 (AI-Assisted Data Engineering), 8 questions

@ PLTR-DE D8 T8.1 applied comparison
S: A data engineer wants to understand which AI capability to use for each of three needs: getting help writing a PySpark transform in the code editor, asking how a platform feature works, and adding a column that summarizes a free-text field for every row of a dataset. Which mapping is correct?
A: A data-producing LLM transform for all three, since every need involves a language model
B: A code assistant for writing the transform, AIP Assist for the platform question, and an LLM transform for the per-row column
C: AIP Assist for all three, since it is the platform's general assistant
D: An LLM transform for writing the transform code, AIP Assist for producing the summary column, and a code assistant for the platform question
K: B
G: ## Different AI aids for different jobs
The exam guide asks you to distinguish AI FDE, AIP Assist, Continue and data-producing LLM or embedding transforms:
- **Code assistants** (Continue in code environments, AI FDE as an engineering assistant) help write and change code and pipelines.
- **AIP Assist** answers questions about using the platform.
- **LLM transforms** run a model over data inside a pipeline, producing columns (classifications, summaries, embeddings) at scale.
## Mapping
Writing a transform is a code task; "how does feature X work" is a platform question; a summary column for every row is data processing in the pipeline.
Example: the engineer drafts the transform with the code assistant, checks a schedule setting with AIP Assist, and adds the summary via an LLM transform with structured output.
W: Code assistant, AIP Assist, LLM transform: each need is matched to the capability designed for it.
X: A=LLM transform for everything: a transform produces data; it does not help write code or answer platform questions.
C=AIP Assist for everything: it answers platform questions; it neither writes production transforms for you nor processes dataset rows.
D=Scrambled mapping: using an LLM transform to write code or a code assistant to answer platform questions misuses each tool.
T: Code assistants help write pipelines, AIP Assist explains the platform, LLM transforms process data in pipelines.
V: AIP Assist, Continue, Pipeline Builder

@ PLTR-DE D8 T8.2 applied use-case
S: An LLM transform extracts a structured "incident type" from maintenance logs. The team wants the results to be reliable enough to back an Ontology property. Which configuration is appropriate?
A: Free-text output from the model written directly to the column, since the model's own wording is more informative than any fixed list of types
B: Enumerated structured output, code validation of the value, caching by input text, and a quality check flagging invalid results
C: A second model call that rewrites the first model's free-text answer into one of the allowed types
D: A prompt instruction asking the model to be accurate, with the output written to the column as is
K: B
G: ## Making LLM output pipeline-grade
The exam guide asks you to configure structured outputs, deterministic post-processing, caching and quality checks for AI steps in pipelines.
- **Structured output** with an enumeration: the model's answer is one of the allowed types.
- **Deterministic post-processing**: validation in code; invalid values are rejected or nulled with a status flag, never silently written.
- **Caching** by input (plus prompt version): unchanged logs are not reprocessed, saving cost and keeping results stable.
- **Quality checks**: invalid rate, distribution of types over time, sampled review; expectations can enforce that the column only contains allowed values.
Example: 1,000 logs per night; 12 fail validation and are flagged for review; the property is populated for the rest with the prompt version recorded.
W: Enumeration, validation, caching and quality checks: these are the four controls that make an AI-produced column dependable for the Ontology.
X: A=Free text to the column: unbounded values cannot back a categorical property or be filtered reliably.
C=Second model call: a model normalizing another model's text adds cost and still produces unvalidated output; an enumeration achieves the constraint directly.
D=Prompt plea: "be accurate" is not a control; nothing validates what gets written.
T: AI-produced columns need constrained structured output, code validation, caching and ongoing quality checks.
V: Pipeline Builder, expectations

@ PLTR-DE D8 T8.3 applied tradeoff
S: Two requests arrive: (1) tag every one of 3 million documents with a topic, used by filters in several apps and refreshed weekly; (2) let an analyst ask free-form questions about one document while reading it. Where should the AI processing for each run?
A: Both in the pipeline: tag the documents weekly and also pre-generate answers to a list of likely questions for each document in the same run
B: Tagging as a batch LLM transform in the pipeline; free-form questions answered interactively at the application layer with the document as context
C: Both at the application layer: tag documents when a user opens them and answer questions on demand
D: Tagging at the application layer and questions in the pipeline, since questions are more predictable than tags
K: B
G: ## Pipeline-layer versus Ontology-layer AI
The exam guide asks you to choose pipeline-layer AI for reusable batch enrichment and Ontology-layer AI for interactive, context-dependent reasoning.
- **Tags for 3 million documents**: the same value for every consumer, needed by filters, weekly freshness: a batch LLM transform.
- **Free-form questions on one document**: unknown in advance, depends on the user's question and the current document: an interactive function or agent at the Ontology/application layer, which can also use the tags.
Example: the topic becomes a property used in list filters; the question "does this contract allow early termination?" runs a function with that document as context when asked.
W: Batch tagging in the pipeline and interactive questions at the application layer: each workload is placed where its breadth, freshness and interactivity point.
X: A=Pre-generate answers: the questions are not known in advance; precomputed answers would be stale and mostly irrelevant.
C=Tag on open: documents nobody opens never get tagged, so filters are incomplete, and the same document gets retagged per user.
D=Reversed: tags are the batch workload; free-form questions cannot be batched.
T: Reusable, large-scale enrichment runs in the pipeline; per-user, context-dependent reasoning runs at the Ontology/application layer.
V: Pipeline Builder, AIP Logic

@ PLTR-DE D8 T8.4 applied troubleshooting
S: A code assistant generated a transform that reads a large dataset, collects it to the driver, and loops over rows in Python to compute a running total. The build succeeds on a sample but fails with out-of-memory on the full input. What should the engineer conclude?
A: The assistant's code is correct and the cluster needs more driver memory
B: The generated code collects a distributed dataset to one node, an unsupported pattern at this size; rewrite it with distributed operations
C: The dataset is too large for Foundry and should be sampled permanently
D: The sample build already proves the logic is correct; the full build should simply be retried with more executors until it passes
K: B
G: ## Reviewing AI-generated code
The exam guide asks data engineers to review AI-generated code for incorrect assumptions, unsupported patterns and regressions. Collecting a distributed dataset to the driver and iterating in Python is a classic unsupported pattern: it works on small samples and fails at scale.
## The right fix
- Express the computation with distributed operations (window functions for running totals, aggregations).
- Validate on a branch against the full input, comparing results with a known baseline.
- Treat the assistant's output as a draft: useful, but accountable to the same review as human code.
Example: the loop is replaced by a window function partitioned by account and ordered by date; the full build completes in minutes.
W: Unsupported pattern identified by review and rewritten distributedly: the failure is in the code's approach, not in the cluster, and review is the control that catches it.
X: A=More driver memory: collecting a large dataset to one node will fail again as data grows; the design is wrong.
C=Sample permanently: a running total over a sample is not the running total; the requirement needs all rows.
D=Retry with more executors: executors do not help when the code forces everything onto the driver.
T: AI-generated code can hide scale-unsafe patterns; review it and rewrite with distributed operations.
V: Code Repositories, Continue

@ PLTR-DE D8 T8.2 applied use-case
S: A pipeline enriches 5 million customer reviews with an LLM-generated sentiment score. The prompt is being improved every week, and the team wants to avoid reprocessing every review on each change while still updating old results eventually. Which design is appropriate?
A: Reprocess all 5 million reviews whenever the prompt changes, since consistency requires every row to have been scored with the same prompt
B: Cache results by review text and prompt version; process new reviews with the current prompt and backfill older ones gradually
C: Never reprocess old reviews, since the sentiment of a review does not change
D: Reprocess only reviews from the last week, since older reviews are rarely viewed
K: B
G: ## Caching with prompt versions
The exam guide lists caching among the controls for AI data processing. A cache key of (input text, prompt version, model) means:
- Unchanged review and unchanged prompt: no call.
- New prompt: the key changes, so the row is eligible for recomputation.
## Controlling the cost of change
- New reviews use the current prompt immediately.
- A rolling backfill reprocesses older reviews in bounded daily batches, so the full dataset converges without one giant run.
- Record the prompt version on each row so consumers know which version produced the score and mixed states are visible.
Example: 50,000 reviews per night: 20,000 new and 30,000 from the backfill; after about six months all rows are on the latest prompt, with cost spread evenly.
W: Versioned cache plus rolling backfill: new data is current, old data converges, and no prompt change triggers a 5-million-row run.
X: A=Full reprocess per change: weekly prompt changes would cost 5 million calls a week; consistency can be achieved gradually.
C=Never reprocess: the score's definition changed with the prompt; old rows would carry a different definition forever.
D=Last week only: older reviews still feed aggregates and dashboards; leaving them on an old definition skews the results.
T: Key AI caches by input and prompt version, and backfill old rows gradually rather than all at once.
V: Code Repositories, Pipeline Builder

@ PLTR-DE D8 T8.3 applied use-case
S: A data engineer is asked to add embeddings for product descriptions so that a semantic search over products can be built. Where does this work belong?
A: In the pipeline, as an embedding transform writing a vector column, exposed as a vector property on the Product object type
B: In the application, computing embeddings for the products when a user searches, so that the vectors are always current at query time
C: In a notebook run once by hand and uploaded as a dataset, since embeddings only need to be created once
D: In an agent that embeds products during conversations and stores the vectors in its memory
K: A
G: ## Embedding transforms as pipeline enrichment
The exam guide lists embedding transforms among data-producing AI steps and places reusable batch enrichment in the pipeline layer. Embeddings for a product catalogue are exactly that: computed once per description (and recomputed when the description changes), stored as a vector property, used by every semantic search.
## Design points
- Same embedding model for indexing and later queries.
- Cache by description so unchanged products are not re-embedded.
- Schedule with the catalogue pipeline, so new and changed products are embedded automatically.
- The vector property on the Product object is what AI workflows and applications search.
Example: 200,000 products embedded nightly; a changed description re-embeds only that row; semantic search returns products by meaning.
W: Pipeline embedding transform with a vector property: reusable, scheduled, consistent enrichment, which is the pipeline layer's job.
X: B=Embed at search time: embedding the whole catalogue per search is impossibly slow; only the query should be embedded at search time.
C=One-off notebook: products change; an unscheduled upload goes stale and is not reproducible.
D=Agent memory: an agent's conversation state is not a data store for a product index.
T: Index-building AI work (embeddings, tags) is pipeline enrichment materialized on the Ontology; queries are embedded at search time.
V: Pipeline Builder, Ontology vector properties

@ PLTR-DE D8 T8.4 applied troubleshooting
S: An AI assistant suggested replacing a transform's inner join with a left join "to avoid losing rows". The engineer applied it, the build passed, and the row count rose by 3%. Downstream, a revenue dashboard now shows null customer segments for some orders. How should this have been handled?
A: Keep the change, since more rows is better and the dashboard team can filter out nulls
B: Review the suggestion against the data contract first: the join type changes semantics; validate on a branch and check consumers, then decide
C: Revert to the inner join and ask the assistant for a different suggestion, since assistants should never propose changes to join types in production transforms
D: Apply the left join but add a filter that removes rows with null segments, which restores the previous count
K: B
G: ## Semantics hidden in a suggestion
Changing a join type changes meaning: an inner join drops orders without a matching customer (enforcing a contract or hiding a data problem); a left join keeps them with nulls. The exam guide asks you to review AI-generated changes for incorrect assumptions and regressions and to assess existing consumers before changing semantics.
## What should have happened
- Ask why rows were being "lost": missing customers is a source-quality issue worth surfacing, not silently keeping or dropping.
- Decide the contract: either orders must always have a customer (keep inner join plus an expectation that flags the orphans), or orphans are allowed and downstream must handle nulls.
- Validate on a branch, compare counts, run downstream consumers, then release with communication.
Example: the 3% are orders from a new channel whose customers are not yet synced; the real fix is in ingestion, with an expectation on the orphan rate.
W: Review the semantic change against the contract and validate with consumers: the suggestion was not wrong in itself, but applying it without analysis changed meaning for the dashboard.
X: A=More rows is better: the extra rows have no segment; the dashboard is now wrong, and "filter nulls" just reintroduces the inner join downstream inconsistently.
C=Blanket rejection: assistants can propose useful changes; the discipline is review, not refusal.
D=Filter null segments: this hides the orphans again and makes the pipeline more complicated than the original inner join.
T: AI suggestions that touch join types or filters change semantics; review them against the data contract and consumers before applying.
V: Code Repositories, AIP Assist

@ PLTR-DE D8 T8.2 advanced tradeoff
S: An LLM transform classifies 100,000 documents nightly. The team notices the invalid-output rate jumped from 1% to 9% last night with no prompt change. What should the data engineer do?
A: Nothing, since the pipeline still succeeded and 9% is a small fraction of the documents
B: Treat it as a quality incident: sample the invalid outputs, compare model and prompt versions and inputs with the previous night, and hold affected rows
C: Lower the validation strictness so that more of the outputs pass, which returns the invalid rate to its normal level without touching the pipeline
D: Rerun the transform with a higher temperature to get more varied outputs that may fit the categories
K: B
G: ## Quality checks on AI steps need a response
The exam guide pairs AI processing with quality checks; a metric is only useful if a change in it triggers action. A ninefold jump in invalid outputs with no prompt change signals something moved: the model version at the provider, the input distribution (a new document type), or an upstream formatting change.
## Investigation
- Sample invalid outputs: are they a new category, malformed JSON, a language change?
- Compare model and prompt versions recorded on the rows against the previous night.
- Check the input: new source, new template, encoding issue.
- Keep invalid rows flagged and out of consumer-facing properties until resolved; fix the cause (prompt update for a new document type, pin the model version) and backfill.
Example: a new document template with embedded tables confused the model; adding a preprocessing step and a prompt note restores the 1% rate, and the 9,000 rows are reprocessed.
W: Investigate as a quality incident with the recorded evidence and quarantine the affected rows: this treats the metric as the control it is meant to be.
X: A=Ignore: 9,000 documents with bad or missing labels corrupt filters and dashboards; the jump is a symptom of a change that will persist.
C=Loosen validation: this hides the problem by accepting wrong values into the Ontology.
D=Raise temperature: more randomness in a classification task makes outputs less consistent, not more valid.
T: A sudden change in an AI step's quality metric is an incident: investigate with recorded versions and inputs, quarantine affected rows, fix and backfill.
V: Pipeline Builder, Data Health
