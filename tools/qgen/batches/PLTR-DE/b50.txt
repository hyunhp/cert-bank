# PLTR-DE batch 50: capstone, one question per domain (D1-D8), 8 questions

@ PLTR-DE D1 T1.4 advanced use-case
S: A new source must be onboarded: an on-premises database behind a firewall, a table of 400 million rows with a reliable update timestamp and soft deletes, needed daily by finance. Which end-to-end ingestion design is appropriate?
A: A direct connection from the platform through a temporary firewall opening, running a full snapshot of the whole table every night with no checks
B: An agent, an initial snapshot then a daily update sync with lookback, soft deletes applied, and freshness checks
C: A weekly manual export by the database team to a shared drive, uploaded by an analyst to the platform on Monday mornings
D: A streaming CDC pipeline with second-level latency, since streaming is always preferable for large tables
K: B
G: ## Putting ingestion decisions together
The exam guide's ingestion domain asks you to choose architecture (agent versus direct), pattern (snapshot, append, update, CDC) and monitoring together.
## Design
- Agent: the source is behind a firewall.
- Initial snapshot, then update sync on the timestamp with a lookback window.
- Soft deletes carried and applied in the current-state transform.
- Freshness against the finance deadline, size checks, alert routing, runbook.
Example: the first load takes a weekend; daily syncs transfer about 1% of rows in minutes.
W: Agent, initial snapshot, incremental update sync with lookback, soft-delete handling and monitoring: every choice follows from the source's constraints and the daily requirement.
X: A=Firewall opening with nightly full snapshots: weakens network security and moves 400 million rows nightly with nothing to detect failures.
C=Weekly manual export: misses the daily requirement and depends on two people every week.
D=Streaming CDC: second-level latency the business does not need, at much higher cost and complexity.
T: Design ingestion end to end: connection architecture, sync pattern and monitoring chosen from the source and the requirement.
V: Data Connection, Data Health

@ PLTR-DE D2 T2.4 advanced use-case
S: A critical transform computes revenue recognition. A new engineer must change one rule. Which combination of safeguards should already be in place so the change cannot silently corrupt revenue?
A: A comment at the top of the transform asking engineers to be careful when they edit revenue logic
B: Unit tests on the rules, reconciliation expectations, branch comparison with production, and required review
C: A lock that prevents anyone from ever editing the transform again after its first release
D: A monthly check by finance of whether the revenue numbers look roughly right compared with last month
K: B
G: ## Defence in depth for critical logic
The exam guide asks for tested, validated and reviewed transformations with expectations. Each safeguard catches a different kind of mistake.
## Layers
- Unit tests: rule-level correctness on known cases.
- Expectations: totals reconcile to an independent control figure.
- Branch comparison: real-data differences visible before merge.
- Review: a second engineer and a finance-aware approver.
Example: the change passes unit tests, but the branch comparison shows a 2% shift in one product line; review finds the misapplied rule.
W: Tests, reconciliation expectations, branch comparison and review together: a change to critical logic is checked at the rule, data and human level before it can publish.
X: A=Comment: a request for care at the top of the file checks nothing; a careless edit still publishes wrong revenue.
C=Permanent lock: rules legitimately change; the answer is safe change, not no change.
D=Monthly look: a wrong rule can stand for weeks and "roughly right" misses subtle shifts.
T: Protect critical transforms with tests, reconciliation, branch comparison and review together.
V: Code Repositories, expectations, branches

@ PLTR-DE D3 T3.3 advanced tradeoff
S: A team must choose a processing design for an append-only event dataset of 50 billion rows that grows daily, with consumers needing daily aggregates and occasional late events up to 7 days old. Which design fits?
A: A full nightly batch over all 50 billion rows, since full recomputation always handles late events correctly
B: Incremental over new appends, partitioned by event date, recomputing the last 7 days, with periodic reconciliation
C: A streaming pipeline with no persistence, since streaming always handles late data automatically without any configuration
D: An incremental transform that ignores late events entirely, since they are only a small fraction of all events
K: B
G: ## Incremental with a late-data window
The exam guide asks for processing modes chosen by volume and change patterns, with correct handling of late data.
## Design
- Incremental over APPEND transactions.
- Outputs partitioned by event date; each run recomputes the last 7 days' partitions.
- Monthly full reconciliation to catch anything outside the window.
Example: each night processes one day of new events and refreshes seven partitions, in minutes rather than the hours a full run would take.
W: Incremental processing with a bounded late-data recompute window and periodic reconciliation: scales with daily growth while keeping aggregates correct.
X: A=Full nightly over 50 billion rows: correct but enormously wasteful as the history grows.
C=Streaming without persistence: daily aggregates are not a streaming requirement, and late data still needs explicit handling.
D=Ignore late events: aggregates become permanently wrong for the affected days.
T: Combine incremental processing with a bounded recompute window for late data.
V: incremental transforms

@ PLTR-DE D4 T4.3 advanced use-case
S: A critical dataset failed at 03:00. The on-call engineer must restore service by 07:00 and prevent recurrence. Which sequence reflects the full operational playbook?
A: Force-rebuild everything upstream repeatedly until something succeeds, then go back to sleep without recording anything
B: Locate the first failing stage, classify it, repair minimally, verify, inform consumers, then add a guarding check
C: Wait for the next scheduled run, since most failures resolve themselves overnight without intervention
D: Roll back every dataset in the pipeline to last week's version so that consumers see consistent data
K: B
G: ## The complete playbook
The exam guide's troubleshooting playbook runs from symptom to prevention: first bad stage, classification, smallest safe repair, verification, communication and follow-up.
## Sequence
- Logs and lineage locate the first failure.
- Classify: data, code, resource, permission.
- Repair minimally; rebuild; verify counts and key metrics.
- Notify consumers; write the incident note; add a check or expectation.
Example: an upstream sync failed on an expired credential; it is rotated, the pipeline rebuilt by 05:30, and a credential-expiry alert added.
W: Locate, classify, repair minimally, verify, communicate and prevent: service is restored on time and the same failure is less likely next time.
X: A=Repeated force rebuilds: no diagnosis, wasted compute, and nothing learned.
C=Wait for the next run: the deadline passes and the same failure recurs.
D=Roll back everything: discards a week of valid data to fix one failure.
T: Follow the full playbook through repair, verification, communication and a preventive control.
V: builds, Data Lineage, Data Health

@ PLTR-DE D5 T5.2 advanced tradeoff
S: A curated dataset feeds both a regulatory report and an exploratory dashboard. The regulatory report needs strict correctness; the dashboard tolerates small gaps but wants daily freshness. How should quality controls be arranged?
A: One strict expectation set on a single dataset, accepting that the dashboard goes stale whenever the regulatory checks fail
B: A shared validated base, a strictly gated regulatory output, and a dashboard output that publishes daily with alerts
C: No expectations at all, so that the dashboard is always fresh and the regulatory team checks the report by hand
D: Separate pipelines from raw data for each consumer with independent logic and no shared base
K: B
G: ## Controls by consumer contract
The exam guide asks you to match blocking versus alerting to consequence and to publish datasets with clear contracts. Two consumers with different contracts need different gates on a shared base.
## Arrangement
- Base: shared parsing and key validation.
- Regulatory output: strict expectations; a failure holds the last good version.
- Dashboard output: publishes daily; health checks alert on anomalies.
Example: a reconciliation mismatch blocks the regulatory dataset on Tuesday while the dashboard updates with a warning banner.
W: A shared base with consumer-specific gates: strictness where consequences demand it and freshness where tolerance allows.
X: A=One strict set: the dashboard loses freshness whenever a regulatory rule fails.
C=No expectations: the regulatory report loses its automatic protection.
D=Separate pipelines: duplicated logic that drifts, giving consumers different numbers.
T: Share the base pipeline and apply blocking or alerting per consumer according to its contract.
V: expectations, Data Health

@ PLTR-DE D6 T6.4 advanced use-case
S: A dataset containing personal data feeds an Ontology object type used by a customer-service app, an analytics dataset for marketing, and an export to a partner. A review must confirm protection along every path. What should the review cover?
A: Only the source dataset's marking, since everything downstream is protected automatically by that one control
B: Every lineage path: markings on derived data and objects, view policies, roles, export policy and identity scopes
C: A survey asking each consuming team whether they believe they handle the data correctly
D: Only the partner export, since external sharing is the only path that can expose personal data
K: B
G: ## End-to-end governance review
The exam guide asks for security applied through the lifecycle and traced with lineage, across markings, roles, views and exports.
## Review per path
- Object type: backing data marked; view policies for service agents.
- Marketing analytics: marking or reviewed de-identification.
- Partner export: minimized extract, approved destination, egress policy, logs.
- Identities: least privilege on each pipeline.
Example: the review finds the marketing dataset carried names without a marking; it is marked and a de-identified version is built.
W: A lineage-driven review of every path's markings, policies, roles, exports and identities: protection is confirmed or fixed wherever the data flows.
X: A=Source marking only: derived paths can lose or bypass protection, especially exports and reviewed de-identifications.
C=Survey: what teams believe about their handling is not evidence of markings, policies or export controls actually in place.
D=Export only: the marketing dataset and the object type can expose personal data internally just as an export can externally.
T: Review data protection along every lineage path, not only at the source or at external exports.
V: Data Lineage, markings, exports

@ PLTR-DE D7 T7.2 advanced use-case
S: A team is designing the backing dataset for a new "Shipment" object type fed by three carriers with overlapping tracking numbers. Applications need stable objects, links to Orders, and user edits that survive daily rebuilds. Which design decisions are essential?
A: Use the tracking number alone as the key, since carriers promise their numbers are unique within their own systems
B: A carrier-namespaced key with a uniqueness expectation, one row per key, a validated Order link, and churn monitoring
C: Rebuild the object type from scratch daily with new random keys so that no stale objects ever remain
D: Store all three carriers' data in three separate Shipment object types so that keys never collide
K: B
G: ## Identity, cardinality and stability together
The exam guide's modelling domain asks for stable unique keys, correct links and preserved edits.
## Decisions
- Key: carrier + tracking number, constructed unambiguously; uniqueness expectation.
- One current row per key from the event history via keyed merge.
- Link to Order through a validated foreign key.
- Churn monitoring between builds.
Example: two carriers both use tracking number 77812; the namespaced keys keep them distinct and each keeps its edits.
W: Namespaced unique keys, one row per key, validated links and churn monitoring: stable shipment objects that survive rebuilds.
X: A=Tracking number alone: overlaps across carriers merge different shipments.
C=Random keys daily: every object is recreated each night, so every user edit and every link detaches every single day.
D=Three object types: the same entity split three ways; applications must query all three.
T: Combine namespaced keys, one row per key, validated links and churn monitoring for multi-source object types.
V: Ontology Manager, expectations

@ PLTR-DE D8 T8.3 advanced tradeoff
S: Leadership asks the data engineering team to add AI-generated summaries to every record in a 10-million-row dataset nightly. Only about 2% of records change daily, and summaries are read mostly in one application. What is the most responsible design?
A: Generate summaries for all 10 million rows every night so that they are always perfectly consistent with each other
B: Generate incrementally for changed rows with caching, validated output and version columns, reviewing on-demand placement
C: Generate summaries only for a random 1% sample to control cost and leave the rest empty
D: Refuse the request because AI summaries cannot be made reliable for production data
K: B
G: ## Responsible pipeline-layer AI
The exam guide's AI-assisted domain asks for AI where it adds value, with incremental processing, caching, structured outputs, validation and audit.
## Design
- Incremental over changed rows; cache keyed on content plus prompt version.
- Structured output with validation; prompt and model versions per row.
- Placement review: if reads stay in one app, on-demand generation may be cheaper.
Example: 200,000 summaries a night instead of 10 million; quality checks pass; cost falls 98%.
W: Incremental, cached, validated and versioned generation with a placement review: the requested value is delivered at a cost matched to how the data changes and is used.
X: A=All rows nightly: regenerates 9.8 million unchanged summaries every night.
C=Random 1%: ninety-nine in a hundred records never receive a summary, so the request is not actually met.
D=Refuse: well-controlled AI summaries can be reliable; refusing forgoes the value.
T: Deliver AI enrichment incrementally with caching, validation and versioning, and revisit placement based on usage.
V: Pipeline Builder, Code Repositories
