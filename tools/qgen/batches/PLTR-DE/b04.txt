# PLTR-DE batch 04: Domain 3 (Pipeline Processing Modes), 8 questions

@ PLTR-DE D3 T3.1 applied tradeoff
S: A pipeline computes daily sales totals from an orders dataset that receives about 100,000 new rows per day and whose history is 5 years. Results are needed by 06:00 each morning. The team is considering batch, incremental or streaming. Which choice is appropriate?
A: Streaming, so that the totals are always up to date and the 06:00 deadline is met by definition
B: Incremental processing of the new rows each night, since the input grows by appends and a nightly refresh meets the freshness need
C: Full batch over the entire 5-year history every night, since recomputing everything is the only way to be sure the totals are right
D: Lightweight single-node processing of the whole history, since daily totals are a simple aggregation
K: B
G: ## Choosing a processing mode
The exam guide asks you to choose a mode from latency, volume, growth, complexity, source behaviour and cost, and warns against streaming when incremental meets the freshness need.
- **Batch**: recompute all; simple, correct, cost grows with history.
- **Incremental**: process only new transactions; needs append-style inputs and careful state handling; cost proportional to the delta.
- **Streaming**: continuous processing; only for genuinely continuous requirements.
- **Lightweight**: single-node engines for small inputs.
## Here
Freshness: once a day. Growth: appends only. Volume: history is large, delta is small. Incremental fits precisely; a periodic full recompute can serve as a reconciliation.
Example: the nightly build reads 100,000 new rows, adds them to the running daily totals, and finishes in minutes.
W: Incremental: the input appends daily, the freshness need is daily, and the delta is tiny compared with the history, which is the case incremental processing exists for.
X: A=Streaming: continuous processing for a once-a-day requirement adds complexity and cost without improving the outcome.
C=Full batch nightly: reprocessing five years every night wastes compute that grows every day; it is the pattern incremental replaces.
D=Lightweight over all history: five years of orders is not a small input for a single node, and it still recomputes everything.
T: Appending inputs with a daily freshness need are the textbook case for incremental processing, not streaming or full recompute.
V: Code Repositories, Pipeline Builder

@ PLTR-DE D3 T3.2 applied definition
S: A data engineer sees four transaction types in a dataset's history: SNAPSHOT, APPEND, UPDATE and DELETE. Which statement describes them correctly?
A: SNAPSHOT replaces the contents entirely, APPEND adds files, UPDATE modifies or adds files while keeping the rest, DELETE removes files
B: SNAPSHOT and APPEND both add files, while UPDATE and DELETE are only used by streaming datasets and never appear in batch pipelines
C: SNAPSHOT is the only transaction type that can be used as an input to an incremental transform; the other three always force a full rebuild
D: APPEND replaces the dataset's contents with new files, while SNAPSHOT adds files to the existing contents
K: A
G: ## Transaction semantics
A Foundry dataset is a sequence of transactions, each of which changes the set of files in the dataset's view. The exam guide asks you to understand SNAPSHOT, APPEND, UPDATE and DELETE separately from the processing mode:
- **SNAPSHOT**: the new files replace everything; the dataset's view is only the files in this transaction.
- **APPEND**: new files are added; existing files stay.
- **UPDATE**: some files are added or replaced; files not mentioned stay.
- **DELETE**: files are removed.
## Why it matters
Incremental transforms rely on APPEND inputs: "what is new" is well defined. SNAPSHOT, UPDATE and DELETE change or remove earlier data, which is why they can trigger incremental fallback (see the next question).
Example: a daily sync writing APPEND transactions lets a downstream incremental transform process one day's files per run.
W: Replace, add, modify-or-add, remove: this is the correct meaning of the four transaction types.
X: B=Streaming only: UPDATE and DELETE are ordinary batch transaction types; they are not restricted to streaming datasets.
C=Snapshot as incremental input: the opposite is true; APPEND is the input incremental transforms process efficiently, and SNAPSHOT inputs trigger fallback.
D=Swapped definitions: SNAPSHOT replaces and APPEND adds, not the other way round.
T: SNAPSHOT replaces, APPEND adds, UPDATE modifies or adds, DELETE removes; incremental processing relies on APPEND inputs.
V: datasets, transactions

@ PLTR-DE D3 T3.3 applied troubleshooting
S: A data engineer has been asked to make a transform incremental. A colleague warns that the upstream sync "sometimes rewrites the whole table". What does this mean for the incremental design?
A: Incremental processing is impossible on this input, and the transform must stay a full batch
B: A SNAPSHOT upstream makes the incremental transform recompute fully for that run; tolerate it and move the sync to append where possible
C: The incremental transform will silently skip the snapshot runs, so nothing changes in the output and the design can ignore the warning
D: The incremental transform will process the snapshot as if it were new rows, doubling the output, so a deduplication step must be added
K: B
G: ## Incremental fallback
The exam guide asks why an incremental transform can fall back to a snapshot and how to investigate it. When an input receives a SNAPSHOT (or UPDATE or DELETE) transaction, the transform cannot determine "what is new", so it recomputes from the full input for that run. The output is correct; the run is slow.
## Designing for it
- Accept occasional fallbacks if they are rare and the full recompute is affordable.
- Write the transform so both modes produce the same output (idempotent logic, no reliance on state that a full run would not rebuild).
- Monitor: a fallback should be visible (build duration, transaction history) and investigated.
- Better: fix the source pattern so the sync appends, making fallbacks rare.
Example: the sync rewrites the table once a month; the incremental transform runs in 3 minutes normally and 2 hours on that day, which is acceptable.
W: Fallback tolerated and the sync improved: this is the accurate consequence and the right engineering response, rather than giving up or ignoring it.
X: A=Impossible: incremental works on the append runs; the snapshot runs just fall back, which is usually acceptable.
C=Silently skip: the transform does not skip; it recomputes fully. Ignoring the warning leaves unexpected long runs unexplained.
D=Double the output: fallback replaces the output with a full recompute; it does not append the snapshot as new rows.
T: SNAPSHOT inputs make incremental transforms recompute fully for that run; design for it and move sources to append where you can.
V: Code Repositories, incremental transforms

@ PLTR-DE D3 T3.4 advanced troubleshooting
S: An incremental pipeline ingests events every five minutes. After three months, downstream reads have become slow and the dataset has hundreds of thousands of tiny files. What should the data engineer do?
A: Switch the sync to hourly, which reduces the number of files created from now on but leaves the hundreds of thousands of existing files untouched
B: Add periodic compaction that rewrites the small files into fewer, larger ones, while keeping the frequent incremental ingestion
C: Delete the dataset and re-ingest the three months of history in one transaction, which removes all the small files
D: Increase the executor count on every downstream transform so that the many files are read in parallel
K: B
G: ## Small-file accumulation
Every incremental run writes at least one file. At five-minute intervals that is almost 300 files a day, and readers must open each one; after months, listing and opening files dominates read time. The exam guide names small-file accumulation among the things to handle safely.
## Compaction
- A scheduled compaction rewrites the data into larger files, typically as a snapshot transaction of the same dataset or a downstream compacted copy.
- Frequency: daily or weekly, depending on write rate.
- Downstream incremental transforms of the compacted dataset will see a SNAPSHOT and fall back for that run; schedule accordingly.
- Prevention: write fewer, larger files per run where the processing mode allows.
Example: a nightly compaction turns the day's 288 files into 4; reads downstream return to seconds.
W: Periodic compaction: it removes the accumulated small files and keeps the ingestion cadence, which is the standard remedy for this failure mode.
X: A=Hourly sync only: future growth slows but the existing problem remains, and freshness drops from five minutes to an hour.
C=Delete and re-ingest: destructive, loses history and lineage, and the small files start accumulating again immediately.
D=More executors: parallel reads reduce the symptom at a cost on every consumer; the file count keeps growing.
T: Frequent incremental writes need periodic compaction; do not let small files accumulate indefinitely.
V: datasets, incremental transforms

@ PLTR-DE D3 T3.1 applied tradeoff
S: A fraud team wants alerts on suspicious card transactions within seconds of the transaction occurring. The source is a message stream. Which processing mode is required, and what should the engineer be careful about?
A: Streaming, accepting the operational complexity of state, backlogs and replay because the requirement is continuous
B: Incremental batch every minute, since one-minute latency is close enough and avoids the complexity of streaming
C: Full batch every hour, since fraud patterns are only visible over an hour of data anyway
D: Streaming, but only for a one-week trial, after which the pipeline should be converted to a nightly batch to reduce cost
K: A
G: ## When streaming is justified
The exam guide reserves streaming for genuinely continuous requirements and asks you to recognize when it would add complexity without improving the outcome. "Within seconds" of a continuous source is that requirement.
## What streaming brings
- A streaming dataset and a streaming pipeline process each event as it arrives.
- Operational concerns: state management for windows, backlog monitoring when consumers lag, replay after a failure, schema evolution of the stream.
- Cost: always-on compute, justified here by the business value.
Compare: a dashboard that is refreshed hourly from the same stream could be served by batch; the alerting requirement is what demands streaming.
Example: a rule evaluated per transaction in the stream raises an alert object within a few seconds; batch of any cadence would miss the window.
W: Streaming with its operational complexity accepted: the latency requirement is seconds on a continuous source, which batch and incremental cannot meet.
X: B=One-minute incremental: a minute is not seconds, and very frequent incremental batches create small-file and scheduling overhead without reaching the target.
C=Hourly batch: it ignores the stated requirement; the team asked for seconds.
D=Temporary streaming: converting to nightly batch afterwards abandons the requirement; the mode follows the need, not a trial period.
T: Use streaming only when latency must be continuous; then plan for state, backlogs and replay.
V: streaming, Pipeline Builder

@ PLTR-DE D3 T3.4 applied troubleshooting
S: A streaming pipeline that aggregates sensor readings stopped producing output two hours ago. Readings still arrive in the input stream and the pipeline reports as running. What should be checked first?
A: Whether the input stream's schema changed, since streaming pipelines generally fail silently on new fields
B: The pipeline's backlog and lag metrics: whether it is behind the input, stuck on a failed record or blocked on state
C: The downstream Ontology indexing, since object views are the usual reason that streaming output appears to stop
D: Whether the sensors have been reassigned to a different topic, since that would stop the input
K: B
G: ## Backlogs and lag
A streaming job that is "running" can still be unhealthy: it may be processing far behind the input (backlog growing), repeatedly failing on one bad record, or waiting for state that never arrives. The exam guide lists state, transaction backlogs and replay among streaming concerns.
## Evidence to read
- Lag: the gap between the latest input offset and the latest processed offset.
- Error logs: a record that fails deserialization or a window computation.
- Resource usage: a stalled job may be out of memory for its state.
Then decide: fix the bad record handling, scale the job, or replay from a checkpoint.
Example: lag has grown steadily for two hours; one malformed message is retried endlessly; after skipping it with a dead-letter rule, the backlog drains.
W: Backlog and lag metrics: they distinguish "behind", "stuck" and "blocked", which are the streaming-specific causes of a running job with no output.
X: A=Schema change: possible, but it would normally show as errors in the job's logs, which the backlog investigation includes; assuming it skips the evidence.
C=Ontology indexing: the question is about pipeline output, which is upstream of any object indexing.
D=Sensors reassigned: the input stream still receives readings, which rules this out.
T: For a streaming job that runs but produces nothing, read its lag and backlog metrics and error logs first.
V: streaming, Data Health

@ PLTR-DE D3 T3.4 applied use-case
S: An append-only source will add two new columns next month. Several downstream incremental transforms read the dataset. How should the schema change be handled?
A: Let the new columns arrive and do nothing, since incremental transforms that do not reference the columns are unaffected and those that need them can be updated when they fail
B: Treat it as an additive change: update the schema deliberately, verify downstream transforms on a branch against the new schema, and roll out so that consumers are not broken
C: Create a brand-new dataset for the post-change data and ask consumers to switch, since schema changes cannot be applied to an existing dataset
D: Convert the incremental transforms to full batch for the month of the change, since incremental processing cannot handle any schema evolution
K: B
G: ## Schema evolution
The exam guide asks you to handle schema evolution safely and to classify changes as additive, breaking, semantic or source-quality before editing. Two new columns on an append-only source is **additive**: existing columns and their meaning stay the same.
## Safe rollout
- Confirm the change is additive (types and names of existing columns unchanged).
- On a branch, build the ingestion and the downstream incremental transforms against sample data with the new schema; check that select-all logic, schema expectations and Ontology mappings tolerate the new columns.
- Communicate to consumers; add the columns to the Ontology if they are needed.
- Watch the first builds after the change.
Example: a transform with a strict schema expectation would fail on the extra columns; the expectation is updated before the change lands.
W: Deliberate additive change validated on a branch: it keeps consumers working and handles the incremental transforms' expectations before the first build with the new columns.
X: A=Do nothing: some transforms have schema expectations or explicit column lists; discovering failures in production is avoidable.
C=New dataset: an additive change does not require a new dataset; forcing every consumer to switch is disproportionate.
D=Switch to full batch: incremental transforms can handle additive schema changes; converting them for a month adds cost and risk for no reason.
T: Classify schema changes first; roll out additive changes deliberately with branch validation and consumer communication.
V: Code Repositories, branches

@ PLTR-DE D3 T3.3 applied troubleshooting
S: A team wants an incremental transform to also handle corrections: the source occasionally sends a corrected version of a record from last week. The transform currently appends everything it receives, so corrected records appear twice. What is the correct design?
A: Keep appending and ask consumers to take the latest record per key when they query, since the dataset should preserve every version received
B: Produce a current-state output by merging corrections by key, optionally alongside an append history, with a documented contract
C: Switch the whole transform to a daily full snapshot of the source so that corrections overwrite the originals in the source before processing
D: Reject corrected records at ingestion, since incremental pipelines are only valid for data that never changes
K: B
G: ## State and corrections in incremental pipelines
The exam guide asks you to handle state, replay and schema evolution safely. A source that sends corrections has update semantics, even if it delivers them as appends. The pipeline must decide what the output's contract is:
- A **history** dataset that keeps every version (append) is useful for audit.
- A **current** dataset with one row per key, where later versions replace earlier ones, is what most consumers need.
Both can exist, with the contract documented. The merge step may need state (the last version per key) or a periodic recompute of the current view from the history.
Example: order 1182's corrected amount arrives on Tuesday; the history keeps both rows, the current view shows the corrected amount only.
W: Explicit current-state output with a documented contract: corrections are applied where the pipeline owns the logic, and consumers get one row per key without each inventing their own deduplication.
X: A=Leave it to consumers: every consumer must know the rule and implement it correctly; dashboards that forget will double-count.
C=Daily snapshot: this throws away incremental efficiency and only works if the source itself overwrites corrections, which was not stated.
D=Reject corrections: the corrections are real business data; rejecting them makes the output wrong.
T: When sources send corrections, publish a documented current-state view (and optionally a history) rather than raw appends.
V: Code Repositories, incremental transforms
