@ PLTR-DE D7 T7.4 applied use-case
S: A backing dataset's refresh must change from nightly to hourly for an object type used by a live operations app. What should be verified before making the change?
A: Nothing specific; a faster refresh gives newer data, and the operations app will pick up the hourly updates on its own
B: On a branch, confirm that hourly builds and indexing finish in time, keys stay stable, edits persist and the app copes
C: That the operations app has been rewritten to expect hourly data instead of nightly data before the cadence changes
D: That the app's users have been told by email to reload their browsers each hour so that they see the latest data
K: B
G: ## Refresh cadence and Ontology stability
The exam guide asks for safe evolution of live Ontology resources and attention to key stability and edits. More frequent backing updates stress indexing and identity.
## Verify
- Runtime and indexing: the hourly cycle completes within the hour.
- Key stability: the key set does not churn between builds.
- Edits: user edits survive frequent re-syncs.
- App behaviour: lists and selections handle refreshes.
Example: branch testing shows indexing takes 25 minutes; hourly is feasible; keys are stable; edits persist.
W: Capacity, key stability, edit preservation and app behaviour validated on a branch: the cadence change is safe.
X: A=No checks needed: if indexing cannot keep up or keys churn between builds, the app shows stale or detached objects; faster is not free.
C=App rewrite: unnecessary if the app handles refreshes; the verification decides.
D=Browser reloads: how often users reload has nothing to do with whether the backing data and index are correct and current.
T: Before increasing an object type's refresh cadence, verify indexing capacity, key stability and edit preservation.

@ PLTR-DE D6 T6.2 applied use-case
S: Ten pipeline engineers have Editor on a project that holds raw synced data and transforms. Only three of them maintain the syncs; seven only write transforms and merely read the raw data. How should access be restructured?
A: Keep the current Editor grants, since the ten engineers work in the same pipeline and trust each other
B: Make the ten engineers Owners so that a raw dataset can be fixed quickly by whoever is available
C: Move the synced data into its own project, editable by the sync maintainers and readable by the rest
D: Remove the editing rights and have a platform administrator apply each change on request instead
K: C
G: ## Least privilege by stage
Roles describe what a person may do in a project. People who only read a stage should not be able to change it.
## Design
- Raw project: three sync maintainers as Editor, others as Viewer.
- Transform project: the transform engineers as Editor.
- Grants given to groups, not to individuals.
Example: an accidental deletion of a raw dataset is only possible for the three people who maintain syncs.
W: Separate projects and roles by stage: the three sync maintainers edit the raw project, the seven transform engineers only view it, and each engineer holds the rights their job needs and no more.
X: A=Everyone stays Editor: any of the seven readers can change or delete raw data.
B=Everyone Owner: maximises rights and the ability to change permissions.
D=Administrator-only changes: creates a bottleneck and does not match how the team works.
T: Split projects by stage and give editing rights only to the people who maintain that stage.
V: Projects, roles
