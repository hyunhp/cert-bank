# PLTR-DE batch 40: Domain 7 round 5 (Ontology Data Modeling), 8 questions

@ PLTR-DE D7 T7.1 applied use-case
S: A company has Vehicles and Drivers. A driver can be assigned to several vehicles over time, a vehicle has many drivers over time, and at any moment a vehicle has at most one current driver. Which model captures both history and the current assignment efficiently?
A: A single many-to-many link between Vehicle and Driver with no properties, since that expresses that drivers and vehicles are related in both directions
B: An Assignment object type with vehicle, driver, start and end, linked to both, plus a derived current-driver link on Vehicle
C: A current_driver property on Vehicle only, overwritten on every change, since the assignment history is not usually needed by anyone
D: A list of driver names stored on each Vehicle object in chronological order, with the last entry treated as the current driver
K: B
G: ## Temporal many-to-many with a current view
The exam guide asks for normalized modeling that stays useful to applications. History lives in dated assignment objects; the current state is derived for fast access.
## Model
- Assignment: key (vehicle, driver, start), properties start, end.
- Links: Assignment → Vehicle, Assignment → Driver.
- Derived: Vehicle.current_driver from the assignment with null end.
Example: vehicle V-7's history shows four drivers; its current-driver link points to the one assigned since Tuesday.
W: Dated assignment objects plus a derived current link: history is complete and the current assignment is a direct lookup.
X: A=Bare many-to-many: cannot express when, nor which assignment is current.
C=Overwritten property: every reassignment erases the previous driver, so the history the business also needs is gone.
D=Name list: a list of strings cannot be queried by driver, has no dates, and is not linked to Driver objects; it breaks the first time a name changes.
T: Model time-varying relationships with dated association objects and derive the current state.
V: Ontology Manager

@ PLTR-DE D7 T7.2 applied troubleshooting
S: An Order object type's primary key comes from a source column that is unique per source system, but orders now arrive from two source systems whose ids overlap. What should the key become?
A: The same source column as before, accepting that overlapping ids will occasionally merge orders from the two systems into one object
B: A namespaced key combining the source system and the source order id, with a uniqueness expectation and a migration mapping existing objects
C: A random UUID generated at build time for every row, which guarantees that no two orders ever share a primary key
D: The order's row number in the combined dataset after the two sources are unioned, which is unique within each build
K: B
G: ## Keys across source systems
The exam guide asks for stable, unique primary keys. Uniqueness must hold across all sources feeding the object type; a namespace makes overlapping ids distinct.
## Design
- Key: `{system}:{order_id}` with an unambiguous separator, or a hash of (system, order_id).
- Expectation: uniqueness on the composite.
- Migration: existing objects mapped from old to new keys; edits and links carried over.
Example: ERP order 1001 and web order 1001 become `erp:1001` and `web:1001` and no longer collide.
W: A namespaced composite key with uniqueness enforcement and a migration: identity is unique across systems and existing objects are preserved.
X: A=Accept merges: two different orders become one object; data corruption.
C=Random UUID: a new key every build means every object is recreated and every edit and link detaches each night.
D=Row number: positions shift whenever rows are added or reordered, so the same order gets a different key on different builds.
T: When multiple sources feed one object type, namespace the key by source system.
V: Ontology Manager, expectations

@ PLTR-DE D7 T7.3 applied tradeoff
S: Two teams want to model "Customer" independently for their own applications, with different properties and keys. What should the data engineer recommend?
A: Let each team create its own Customer object type with its own key and properties, since independence avoids coordination costs
B: One shared Customer object type with a governed key and core properties, extended by team-specific properties or linked satellite types
C: Pick one team's model as the only Customer object type and force the other team to abandon the properties their application needs
D: Model customers as free-text name and address fields on each team's Order objects instead of creating any Customer object type
K: B
G: ## One entity, one object type
The exam guide warns against duplicated object types and asks for normalization. Two Customer types would diverge, break links and confuse every consumer.
## Recommendation
- Shared core: key, name, identifiers; owned by a steward.
- Extensions: team-specific properties on the same type (if broadly harmless) or satellite object types linked one-to-one.
- Governance: changes to the core go through review.
Example: team A adds a `loyalty_tier` property; team B adds a `CreditProfile` satellite object linked to Customer; both apps use the same Customer.
W: A single governed Customer type with extensions: one identity, no divergence, both teams served.
X: A=Two types: duplicated, divergent customers; links and AI workflows cannot tell which is real.
C=Force one model: the other team's needs can be met by extension; no need to discard them.
D=Free text: a name on an order is not an entity; customers cannot be linked, counted, edited or reasoned about.
T: Model each real-world entity once and extend it, rather than letting teams create duplicates.
V: Ontology Manager

@ PLTR-DE D7 T7.4 applied use-case
S: A backing dataset's refresh must change from nightly to hourly for an object type used by a live operations app. What should be verified before making the change?
A: Nothing in particular; a faster refresh is always better and the operations app will simply show newer data every hour
B: That hourly builds and indexing keep up, that keys stay stable between builds, that user edits are preserved, and that the app handles refreshes, on a branch
C: That the operations app has been completely rewritten to expect hourly data instead of nightly data before the change is made
D: That all users of the app have been told by email to refresh their browsers every hour so that they see the latest data
K: B
G: ## Refresh cadence and Ontology stability
The exam guide asks for safe evolution of live Ontology resources and attention to key stability and edits. More frequent backing updates stress indexing and identity.
## Verify
- Runtime and indexing: the hourly cycle completes within the hour.
- Key stability: the key set does not churn between builds.
- Edits: user edits survive frequent re-syncs.
- App behaviour: lists and selections handle refreshes.
Example: branch testing shows indexing takes 25 minutes; hourly is feasible; keys are stable; edits persist.
W: Capacity, key stability, edit preservation and app behaviour validated on a branch: the cadence change is safe.
X: A=Always better: if indexing cannot keep up or keys churn between builds, the app shows stale or detached objects; faster is not free.
C=App rewrite: unnecessary if the app handles refreshes; the verification decides.
D=Browser refresh: how often users reload has nothing to do with whether the backing data and index are correct and current.
T: Before increasing an object type's refresh cadence, verify indexing capacity, key stability and edit preservation.
V: Ontology Manager, Global Branching

@ PLTR-DE D7 T7.1 applied use-case
S: An application must show, for each Product, its current price and the full price history. Prices change weekly. How should this be modeled?
A: A single price property on Product overwritten weekly, with the history reconstructed from the dataset's transactions whenever anyone needs it
B: A PriceVersion object type (product, price, effective range) linked to Product, plus a derived current_price property on Product
C: A list of all historical prices stored as an array property on Product, with the most recent one at the end of the list
D: A separate Product object created for every price change, so that each object carries exactly one price and its date
K: B
G: ## Versioned attributes
The exam guide asks for modeling that serves both current-state and historical questions without duplication.
## Model
- PriceVersion: key (product, effective_from); properties price, effective range.
- Link: PriceVersion → Product.
- Derived: Product.current_price from the version with no end date.
Example: the app shows 19.99 now and a chart of 30 historical prices from the linked versions.
W: Versioned price objects with a derived current price: history is first-class and the current value is a direct property.
X: A=Overwrite with transaction archaeology: history is not queryable from objects; transactions are not an application interface.
C=List of prices: an array of numbers with no effective dates cannot answer when a price applied, and it is unqueryable.
D=Product per price: duplicates the product and breaks its identity.
T: Model changing attributes as versioned linked objects and derive the current value onto the entity.
V: Ontology Manager

@ PLTR-DE D7 T7.2 applied comparison
S: Which key choice is most likely to remain stable across rebuilds, source migrations and corrections?
A: A hash of all columns in the row, so that any change to the row produces a new key and nothing is ever silently overwritten
B: A business identifier assigned once by the system of record, or a deterministic hash of only the columns that identify the entity
C: The row's position in the dataset, which is guaranteed unique within a build and requires no knowledge of the business
D: The timestamp of the build concatenated with a per-build counter, which is unique across all builds and all datasets
K: B
G: ## What makes a key stable
The exam guide asks for stable primary keys. Stability means the key depends only on what identifies the entity.
- Business identifier: assigned once, never changes.
- Hash of identifying columns: deterministic; changes only if identity changes.
- Not: position, time, or non-identifying attributes.
Example: a customer's address change does not alter a key based on customer number; it would alter a hash of all columns.
W: An identifier from the system of record or a hash of identifying columns only: stable by construction.
X: A=Hash of all columns: any correction re-keys the object and detaches its edits.
C=Row position: any insert, delete or reorder shifts positions, so objects are re-keyed on every rebuild.
D=Build timestamp: the key changes on every single build by construction, so no object ever keeps its identity.
T: Base keys only on the entity's identifying attributes, never on position, time or mutable attributes.
V: Ontology Manager

@ PLTR-DE D7 T7.5 applied use-case
S: A quality score for each Supplier is computed from a complex model over the supplier's delivery history. Procurement wants to filter suppliers by score in lists and also wants an explanation of the score on demand. Where does each part go?
A: Both north: compute the score and the explanation with a function at the moment the user opens a supplier in the application
B: The score south as a materialized property for filtering, and the explanation north, generated on demand from the stored components
C: Both south, pre-generating a text explanation for every supplier nightly in the pipeline alongside the score
D: Neither; procurement should compute the scores and write the explanations in a spreadsheet that they maintain themselves
K: B
G: ## Splitting by use
The exam guide asks you to place computation by whether it is filtered, reused and consistent (south) or interactive and on-demand (north).
## Split
- Score and its components: pipeline; properties for filtering and consistency.
- Explanation: a function invoked when a user asks, composing the stored components into text.
Example: the list filters suppliers with score < 60; clicking one generates "score driven by 3 late deliveries in 90 days".
W: Score south for filtering, explanation north on demand: each part placed by its use.
X: A=Both north: lists cannot filter on a score computed per view.
C=Both south: explanations for every supplier nightly are mostly never read.
D=Spreadsheet: scores maintained by hand have no lineage, cannot drive list filters in the application, and go stale immediately.
T: Materialize filterable scores in the pipeline; generate on-demand explanations north.
V: Pipeline Builder, AIP Logic

@ PLTR-DE D7 T7.4 advanced troubleshooting
S: After a backing dataset switched to an incremental build, some objects now show properties from older rows (the latest value is not reflected). What is the likely modeling or pipeline issue?
A: Incremental builds cannot back object types at all, so the backing dataset must return to a full nightly batch immediately
B: The incremental output has multiple rows per key because corrections were appended, not merged; produce one current row per key and add a uniqueness expectation
C: The object type's primary key must be changed to a different column, since the current key no longer works with incremental data
D: The Ontology ignores datasets built incrementally and keeps serving the last full-batch version until a full build runs again
K: B
G: ## One row per key for object types
The exam guide asks for stable keys and correct current-state outputs. Object types expect one row per key; an append-only incremental output with updates produces duplicates, and the resolved object may be stale.
## Fix
- Incremental transform with a keyed merge producing a current-state view.
- Uniqueness expectation on the key of the backing dataset.
- Validate on a branch before switching the object type.
Example: 2% of suppliers had two rows; after the merge each has one, and properties reflect the latest values.
W: Duplicate rows per key from append-style incremental output, fixed by a keyed merge and a uniqueness expectation: objects reflect current values again.
X: A=Incremental cannot back objects: it can, provided the output has one row per key.
C=Change the key: the key is fine; the duplicates are the issue.
D=Ontology ignores incremental: false; it indexes the dataset's current view.
T: Backing datasets must have one current row per key; incremental outputs with updates need a keyed merge.
V: Ontology Manager, incremental transforms, expectations
