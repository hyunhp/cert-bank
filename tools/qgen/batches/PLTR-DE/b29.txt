# PLTR-DE batch 29: Domain 4 round 4 (Pipeline Operations and Scheduling), 8 questions

@ PLTR-DE D4 T4.2 applied troubleshooting
S: A transform that ran in 20 minutes yesterday now runs in 3 hours. Job Comparison shows the same stages, but one stage's shuffle read grew from 2 GB to 400 GB. The input row count grew only 5%. What happened and what should be checked?
A: The cluster was simply slower today because of other jobs; the build should be rerun at a quieter time when more resources are available
B: A join's output multiplied because a duplicate key appeared in one input; check key uniqueness in the join inputs for today's data
C: The transform's code was modified to add a new column, which explains the growth and requires no action beyond accepting it
D: The dataset has too many small files, which the Linter would have flagged before the build ran
K: B
G: ## Shuffle growth with stable input size
The exam guide asks you to use Job Comparison and Spark details to classify slowdowns. Input rows +5% with shuffle ×200 means the data multiplied inside the transform: a join whose cardinality changed.
## Checks
- Distinct key counts on each join input for today versus yesterday.
- A new duplicate (a source bug, a many-to-many relationship that was assumed one-to-one).
- Fix at the source or in the contract; add a uniqueness expectation on the join input.
Example: the customer dimension gained duplicate rows from a sync change; 200,000 orders joined to two rows each.
W: Join explosion from duplicate keys: the only thing that turns a 5% input change into a 200× shuffle, and key-count checks confirm it.
X: A=Slower cluster: the shuffle volume itself grew; the cluster is doing 200× the work.
C=New column: the code did not change, and one column does not multiply shuffle by 200.
D=Small files: file count affects read time, not shuffle volume.
T: When shuffle volume explodes with stable inputs, suspect a join cardinality change and check key uniqueness.
V: Job Comparison, Spark Details

@ PLTR-DE D4 T4.1 applied use-case
S: A pipeline's final dataset must be ready by 07:00 for a daily report. Its upstream sync lands between 03:00 and 05:30. The transforms take about 50 minutes. How should the schedule be designed to minimize risk of missing the deadline?
A: A fixed 06:10 start, which leaves exactly enough time if the sync lands by 05:30 and the transforms take their usual 50 minutes
B: An input-update trigger that starts the pipeline when the sync lands, plus a freshness alert at 06:30 if the output is not yet built
C: A fixed 03:00 start every day, since starting the pipeline earlier is always safer when there is a hard morning deadline
D: A trigger at 07:00 that builds the report dataset exactly at the deadline so that the report contains the freshest possible data
K: B
G: ## Deadline-aware scheduling
The exam guide asks for event-based triggers and alerts that give time to act. Reacting to the input landing uses the available slack instead of guessing.
## Design
- Trigger on sync completion: a 03:10 landing produces a 04:00 output; a 05:30 landing produces 06:20.
- Alert at 06:30 if not built: the on-call engineer has 30 minutes to intervene.
- Track lateness trends to renegotiate if the window tightens.
Example: on a night the sync lands at 05:50, the alert fires at 06:30 and the engineer confirms the build will finish by 06:40.
W: Input-triggered build with an early-warning alert: the deadline is met whenever possible and missed deadlines are foreseen, not discovered.
X: A=06:10 fixed: no margin; any slowness misses the deadline, and early syncs waste hours of slack.
C=03:00 fixed: the sync may not have landed; the build runs on stale data.
D=07:00 trigger: the build starts at the deadline and finishes 50 minutes after it; the report is late every single day.
T: Trigger on input arrival and alert before the deadline rather than scheduling against a guess.
V: schedules, Data Health

@ PLTR-DE D4 T4.3 applied troubleshooting
S: A build fails with "disk space exhausted" on executors during a wide aggregation. What is the likely cause and the right fix?
A: The dataset is simply too large to process in Foundry in one job; split it across two separate pipelines that each handle half of the data
B: Shuffle spill exceeded local disk; reduce shuffle size by pre-aggregating or repartitioning, fix skew, or adjust resources, per Spark details
C: The output dataset's storage quota was exceeded during the write; request more storage quota from the platform administrators
D: A permission problem writing temporary files to executor disks; grant the build identity broader access to the storage layer
K: B
G: ## Resource limits during shuffles
The exam guide asks you to distinguish resource limits from other failure classes using Spark details. Executor disk exhaustion comes from shuffle spill.
## Fix
- Reduce shuffle volume: pre-aggregate, filter early, select fewer columns.
- Skew: salt hot keys so one executor does not spill everything.
- Resources: more partitions or executor disk where justified.
- Verify spill metrics in Spark details after the change.
Example: pre-aggregating per partition before the global aggregation cuts shuffle by 90% and the spill disappears.
W: Shuffle spill handled by reducing shuffle volume, fixing skew or adjusting resources: the cause matches the symptom and the fix is targeted.
X: A=Too large: Foundry handles far larger data; the issue is how the aggregation shuffles.
C=Output quota: executor disk during computation is unrelated to output storage.
D=Permissions: a permission error is explicit; disk exhaustion is capacity.
T: Executor disk exhaustion means shuffle spill; reduce shuffle, fix skew, then tune resources.
V: Spark Details, Code Repositories

@ PLTR-DE D4 T4.4 applied use-case
S: A team needs an environment to test pipeline changes against production-like data without affecting production datasets or consumers. What should they use?
A: A complete copy of all production datasets duplicated into a separate testing project every week by a scheduled job
B: Branches: develop on a branch whose builds read production inputs and write isolated branch outputs, with consumers unaffected until merge
C: A separate Foundry instance purchased solely for testing, with production data copied across to it periodically
D: Testing changes directly on the production datasets during an announced maintenance window when consumers are told not to rely on them
K: B
G: ## Branches as test environments
The exam guide lists branch management as an operational responsibility and treats branch builds as the validation mechanism. Branches provide isolation without copying data.
## Use
- Branch from main; edit transforms.
- Branch builds use real inputs and produce branch-scoped outputs.
- Compare with production outputs; run expectations; review; merge.
Example: a schema change is validated on a branch against last night's real data; production consumers see nothing until the merge.
W: Branches: isolated builds on real inputs with no effect on production, which is exactly the test environment needed.
X: A=Weekly copies: stale, expensive and still not isolated for the logic under test.
C=Separate instance: heavy, costly and disconnected from production data and lineage.
D=Maintenance window: testing on production is the risk being avoided.
T: Use branches for isolated testing of pipeline changes on production-like data.
V: branches, Code Repositories

@ PLTR-DE D4 T4.3 applied use-case
S: An engineer is handling a failed build where the error message is unfamiliar. What is the most useful first evidence to gather?
A: The number of rows in the output dataset from the last successful build, as a baseline for what the failed build should have produced
B: The build logs and failing stage's error, the input transactions since the last good build, and the lineage of the failing dataset
C: The opinions of colleagues who have worked on this pipeline about what usually goes wrong with it and how they fixed it before
D: The dataset's description field in the platform, which may mention known issues or contacts for the pipeline
K: B
G: ## Evidence first
The exam guide's playbook starts with the symptom and the first bad stage. The build log and input changes locate the failure; lineage shows what depends on it.
## Gather
- Logs: exact error and the stage.
- Inputs: new transactions, schema changes.
- Lineage: upstream failures, downstream blast radius.
Then classify (data, code, resource, permission) and repair.
Example: the log points to a parsing error in the stage reading a new file; the input transactions show a file with a different encoding.
W: Logs, input changes and lineage: the evidence that turns an unfamiliar error into a classified, fixable failure.
X: A=Last output row count: says nothing about why this build failed.
C=Opinions: colleagues' recollections of past failures are guesses about this one; the evidence is in the logs and inputs.
D=Description field: rarely current and not specific to this failure.
T: Diagnose failed builds from logs, input changes and lineage before forming theories.
V: builds, Data Lineage

@ PLTR-DE D4 T4.1 applied tradeoff
S: A pipeline has 30 datasets. Each dataset has its own schedule, and the team struggles to understand why some build out of order. What scheduling change helps?
A: Removing all 30 schedules and having an engineer build everything manually in the correct order each morning
B: Replacing per-dataset schedules with one pipeline schedule that builds the dependency graph in order, triggered by the root inputs
C: Setting all 30 schedules to exactly the same time so that the datasets build together and finish at roughly the same moment
D: Adding ten-minute offsets between consecutive datasets' schedules so that each one has time to finish before the next starts
K: B
G: ## Scheduling the graph, not the nodes
The exam guide asks for schedules that avoid races and unnecessary builds. A schedule can target a set of datasets and build them in dependency order.
## Design
- One schedule covering the pipeline's outputs; the build resolves and orders the 30 datasets.
- Trigger: input updates at the root.
- Each dataset builds exactly once per run, after its inputs.
Example: the pipeline builds as one graph in 40 minutes with no out-of-order builds and no redundant runs.
W: A graph-aware pipeline schedule: ordering becomes automatic and the 30 timers disappear.
X: A=Manual: 30 datasets built by hand every day is slow, error-prone and the first thing to fail when the engineer is away.
C=Same time: every dataset starts before its inputs have been rebuilt; this maximizes out-of-order builds rather than fixing them.
D=Offsets: guesses at durations; one slow build breaks the sequence.
T: Schedule pipelines as dependency graphs, not as independent timers per dataset.
V: schedules

@ PLTR-DE D4 T4.4 applied troubleshooting
S: A dataset's cost report shows its builds consuming far more compute than similar datasets. Spark details show 2,000 tasks for a 500 MB input and most tasks finishing in under a second. What is wrong?
A: Over-partitioning: far too many tiny tasks for a small input; coalesce or set an appropriate partition count so tasks do real work
B: The dataset is too small to be worth running on Spark at all and should be deleted from the pipeline to save the compute
C: The executors must be faulty hardware if tasks finish that quickly, and they should be replaced by the platform team
D: Nothing; many short tasks indicate excellent parallelism and the cost report must be misattributing another pipeline's usage
K: A
G: ## Partition sizing
The exam guide asks for right-sized compute. Thousands of sub-second tasks on a small input mean the data is split too finely; each task's overhead exceeds its work.
## Fix
- Coalesce to a sensible number of partitions (tens, not thousands, for 500 MB).
- Or consider a lightweight engine for an input this size.
- Verify task durations and total runtime in Spark details.
Example: 2,000 tasks become 20; runtime and cost drop by 80%.
W: Over-partitioning identified from task counts and durations, fixed by coalescing: a classic right-sizing win.
X: B=Delete: the dataset serves consumers; the problem is how it is partitioned for processing, not whether it should exist.
C=Faulty executors: sub-second tasks are not a hardware fault.
D=Good parallelism: parallelism that does no work per task is overhead.
T: Match partition counts to data size; thousands of tiny tasks waste compute.
V: Spark Details

@ PLTR-DE D4 T4.3 advanced troubleshooting
S: A pipeline intermittently fails on a transient network error reading from object storage, roughly one run in thirty. What is the proportionate operational response?
A: Rewrite the pipeline so that it no longer reads from object storage at all, replacing the source with a database sync
B: Configure bounded automatic retries with backoff, alert only when retries are exhausted, and track the transient-failure rate for trends
C: Have the on-call engineer manually rerun every failed build as soon as the failure alert arrives, at any hour
D: Disable failure alerts for this pipeline entirely, since the failures are usually harmless and the next scheduled run fixes them
K: B
G: ## Transient failures
The exam guide asks for operational handling that distinguishes transient from persistent failures. Retries address the former; alerting and trend tracking catch the latter.
## Response
- Build retry policy: for example two retries with backoff.
- Alert only when retries are exhausted.
- Metric: transient failure rate; a rise indicates a real infrastructure problem.
Example: the 3% transient rate is absorbed silently; a jump to 20% the next month triggers an infrastructure investigation.
W: Bounded retries plus alerting on exhaustion and trend tracking: transient noise is absorbed without hiding real problems.
X: A=Rewrite: replacing the source to avoid a 3% transient error is a large, risky project for a problem retries solve.
C=Manual reruns: wastes on-call time on something automatable.
D=Disable alerts: hides the day the transient becomes persistent.
T: Absorb transient failures with bounded retries; alert when retries are exhausted; watch the rate.
V: builds, schedules
