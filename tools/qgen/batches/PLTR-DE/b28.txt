# PLTR-DE batch 28: Domain 3 round 4 (Pipeline Processing Modes), 8 questions

@ PLTR-DE D3 T3.1 applied use-case
S: A marketing team needs campaign metrics refreshed every 15 minutes during a campaign week and daily otherwise. The source is an append-only event dataset. Which processing design balances freshness and cost?
A: Full batch every 15 minutes all year round, since campaign weeks cannot be predicted reliably enough to change the schedule
B: An incremental transform over new events, scheduled every 15 minutes in campaign weeks and daily otherwise
C: A streaming pipeline running permanently, since 15-minute freshness is only achievable with continuous processing
D: A daily batch at all times, with the marketing team told that intra-day metrics are not possible
K: B
G: ## Adjustable cadence on incremental processing
The exam guide asks you to choose modes by freshness, volume and cost. Incremental processing makes frequent runs cheap, and schedules can change with business periods.
## Design
- Incremental over the append-only events: each run processes only new rows.
- Schedule: 15 minutes during campaign weeks, daily otherwise; or trigger on input updates with a minimum interval.
- Freshness health check adjusted per period.
Example: during the campaign, 96 small runs a day cost less than one full daily batch did before.
W: Incremental processing with a period-dependent schedule: 15-minute freshness when needed, minimal cost otherwise.
X: A=Full batch every 15 minutes always: recomputes history 96 times a day for a need that exists one week in ten.
C=Permanent streaming: continuous infrastructure for a 15-minute requirement that is itself occasional.
D=Daily always: refuses a requirement that incremental processing meets cheaply.
T: Combine incremental processing with schedules that follow business cadence.
V: incremental transforms, schedules

@ PLTR-DE D3 T3.2 applied troubleshooting
S: A dataset's transaction history shows an APPEND transaction every hour, but the dataset's total size never grows beyond one hour of data. What is happening?
A: APPEND transactions in Foundry automatically expire after one hour to keep datasets small, so only the latest hour is ever visible
B: The transform overwrites the same output file each run despite the label, or a retention job removes files; inspect transactions and write mode
C: The dataset has reached a storage quota on the platform and older files are being evicted automatically to make room for new ones
D: Datasets built on an hourly schedule always contain only the latest hour of data by design, regardless of the transaction type used
K: B
G: ## Reading transactions against reality
The exam guide asks you to understand SNAPSHOT, APPEND, UPDATE and DELETE semantics and to use transaction history as evidence. An APPEND adds files; if size does not grow, something else is removing or replacing them.
## Investigation
- Inspect each transaction's file list: are previous files present in the view?
- Check the transform's write configuration: overwrite versus append; a transform may overwrite the same file name, producing an UPDATE-like effect.
- Check for a compaction or retention job deleting files.
Example: the transform writes `output.parquet` every hour, replacing the file; switching to unique file names makes the appends accumulate.
W: Inspect transaction contents and the write mode: the mismatch between the label and the size reveals a replace behaviour that must be corrected.
X: A=Auto-expiry: transactions never expire on their own; files added by an APPEND remain in the view until a later transaction removes them.
C=Quota eviction: datasets do not silently evict files on a quota; writes would fail instead.
D=By design: an hourly schedule does not imply a one-hour window; the view depends on transactions.
T: When transaction labels and dataset size disagree, inspect the transaction file lists and the transform's write mode.
V: transactions

@ PLTR-DE D3 T3.4 applied use-case
S: A streaming pipeline is about to receive a 24-hour replay of historical messages after a source migration. What should the team prepare?
A: Nothing special, since a streaming pipeline simply processes whatever arrives in the order it arrives and the replay is just more messages
B: Capacity for the burst, idempotent processing against duplicates, event-time handling for old timestamps, and lag monitoring until it drains
C: A pause of all downstream consumers for a week until the replay is finished and the aggregates have been checked by hand
D: A temporary switch of the whole pipeline to batch mode for the replay, and a switch back to streaming afterwards once it is done
K: B
G: ## Planned replays
The exam guide names replay, state and backlogs among streaming concerns. A replay is a controlled burst with old timestamps.
## Preparation
- Scale the job for the burst; expect lag to rise then fall.
- Idempotency keyed on event id so messages already processed are not double-counted.
- Event-time handling: windows keyed on event time; watermark configuration tolerant of late data during the replay.
- Monitor lag and output counts; reconcile afterwards.
Example: the replay drains in 40 minutes; hourly aggregates for the replayed day match the source totals.
W: Capacity, idempotency, event-time awareness and lag monitoring: the replay completes correctly without corrupting state or output.
X: A=Nothing: duplicates and window misbehaviour are likely without preparation.
C=Pause consumers for a week: unnecessary disruption; the replay takes an hour with preparation.
D=Mode switch: unnecessary and risky; streaming can replay with the right configuration.
T: Prepare streaming replays with capacity, idempotency, event-time handling and lag monitoring.
V: streaming

@ PLTR-DE D3 T3.3 applied comparison
S: A data engineer is explaining incremental transforms to a colleague who is about to convert a nightly batch pipeline. Which statement about incremental transforms is correct?
A: It always processes only the single newest file in the input, regardless of how many transactions have arrived since its last successful run
B: It processes the input transactions added since its last successful run (typically APPENDs) and falls back when the increment is unsafe
C: It never needs a full recompute once it has run successfully for the first time, because its state is kept forever from then on
D: It is only available in Pipeline Builder pipelines and cannot be implemented in Python or SQL code transforms in a repository
K: B
G: ## Incremental semantics
The exam guide expects understanding of incremental processing and fallback.
- Processes all unprocessed input transactions since the last successful run, not just one file.
- Requires APPEND-style inputs to know what is new.
- Falls back to full computation on SNAPSHOT, UPDATE, DELETE or other conditions that invalidate the increment.
- Available in code transforms (and in Pipeline Builder where supported).
Example: three append transactions arrived overnight; the morning run processes all three; a snapshot upstream next week triggers one full run.
W: Processes the unprocessed appends and falls back when the increment is unsafe: the correct description.
X: A=Only the newest file: it processes everything since the last run, which may be several transactions.
C=Never recomputes: a SNAPSHOT, UPDATE or DELETE upstream forces a full recompute; fallback is a normal, expected mode.
D=Pipeline Builder only: incremental transforms are a core feature of code transforms.
T: Incremental transforms process everything since the last successful run and fall back when they cannot do so safely.
V: incremental transforms

@ PLTR-DE D3 T3.1 applied tradeoff
S: A pipeline runs a heavy machine-learning feature computation nightly over the whole customer base, but only 3% of customers have any new activity each day. What should change?
A: Nothing, since a nightly full batch is the standard approach for feature computation and the runtime is still acceptable
B: Make it incremental by key: recompute features only for customers with new activity and merge them in, with a periodic full recompute
C: Switch the feature computation to a streaming pipeline so that features update in real time for every customer as events arrive
D: Reduce the customer base processed each night to a random 3% sample, which matches the share of customers that actually changed
K: B
G: ## Targeted recomputation
The exam guide asks you to prefer bounded reruns over full recompute where the input supports it. Activity is append-only, so the affected customers are identifiable.
## Design
- Identify customers with new events since the last run.
- Recompute features for that set; merge into the current feature dataset (keyed by customer).
- Periodic full recompute (monthly) to absorb definitional changes.
Example: nightly runtime falls from 3 hours to 8 minutes with identical features.
W: Incremental by affected key with periodic full recompute: the heavy work is done only where inputs changed.
X: A=Nightly full: 97% of the customers have no new activity, so 97% of the three-hour computation is redundant every night.
C=Streaming: real-time features were not required; the batch cadence is fine.
D=Random sample: recomputes the wrong customers; features for active customers stay stale.
T: When only a subset of keys changed, recompute only those keys and merge.
V: incremental transforms

@ PLTR-DE D3 T3.4 applied troubleshooting
S: A streaming job's checkpoint became corrupted after a storage incident, and the job cannot resume. What is the correct recovery?
A: Delete the job and its output dataset and start again from an empty stream, accepting the permanent loss of all historical output
B: Reset the checkpoint to a known-good point or the earliest retained offset, replay idempotently, and reconcile the affected window
C: Restart the job from the latest available offset and ignore the gap between the corrupted checkpoint and now
D: Switch the pipeline to batch permanently, since the incident shows that streaming is unreliable for this data
K: B
G: ## Checkpoint recovery
The exam guide lists replay among streaming concerns. A corrupted checkpoint is recovered by replaying from retained messages, provided processing is idempotent.
## Recovery
- Determine the last good checkpoint or the earliest offset still retained.
- Reset and replay; dedupe on event id so re-processed messages do not duplicate.
- Reconcile the affected window; alert consumers if any gap is unrecoverable.
Example: replay from 6 hours earlier completes in 30 minutes; aggregates for the window match the source.
W: Reset to a known-good point and replay idempotently with reconciliation: the output is restored without duplicates or gaps.
X: A=Start empty: the retained messages make the history recoverable; deleting the output throws away what can be rebuilt.
C=Latest offset: every message between the corruption and the restart is skipped, leaving a permanent gap in aggregates.
D=Abandon streaming: an incident is a reason for recovery discipline, not a change of mode.
T: Recover streaming jobs by resetting to a good checkpoint and replaying with idempotent processing.
V: streaming

@ PLTR-DE D3 T3.2 applied use-case
S: A dataset must retain a full history of every version of each record for audit, while consumers need only the current version. Which transaction and dataset design serves both?
A: A single dataset written as a SNAPSHOT on each run, holding only the current version of every record and nothing older
B: An append-only history dataset plus a derived current-state dataset built from it: audit reads history, consumers read current
C: A single dataset in which DELETE transactions remove each old version as the new version of the record arrives
D: A spreadsheet export of each day's dataset kept in a shared folder, so that auditors can open the file for any past date
K: B
G: ## History and current state as two datasets
The exam guide asks you to use transaction types deliberately and to publish datasets with clear contracts. Two consumers, two contracts.
## Design
- History: APPEND only; never modified; the audit record.
- Current: derived by a transform (latest version per key); consumers read this.
- Lineage ties them; the current view can be rebuilt from history at any time.
Example: an auditor asks what a record looked like in March; the history dataset answers; the application shows today's version from the current dataset.
W: Append-only history plus derived current state: both requirements are met with clear, rebuildable contracts.
X: A=Snapshot only: every run replaces the previous versions, so the audit history is gone the moment a record changes.
C=Deletes: deleting old versions removes exactly the records the audit requirement says must be kept.
D=Spreadsheet folder: ungoverned, unqueryable and unreliable as an audit record.
T: Keep an append-only history and derive the current view from it when both audit and current state are required.
V: transactions, Code Repositories

@ PLTR-DE D3 T3.3 advanced tradeoff
S: A team is choosing between making a complex transform incremental (significant engineering, subtle state handling) or keeping it as a full nightly batch that currently takes 40 minutes on a 1 TB input growing 2% a month. What is a reasonable decision?
A: Make it incremental immediately, since incremental processing is always superior to full batch regardless of the engineering cost
B: Keep the batch since it meets the window and incremental state is costly and risky, monitoring runtime with a revisit trigger
C: Switch the transform to a streaming pipeline, which avoids the batch-versus-incremental question entirely
D: Reduce the input to the last month of data only so that the nightly batch stays fast forever as the dataset grows
K: B
G: ## Complexity has a cost
The exam guide asks you to weigh complexity and cost, not only latency and volume. Incremental processing adds state, fallback handling and testing burden; it pays off when batch becomes too slow or expensive.
## Decision
- Current: 40 minutes nightly is well within the window; cost is modest.
- Growth: 2% a month means years before the window is threatened.
- Monitor runtime; revisit when it crosses a defined threshold.
Example: the decision is recorded with a trigger at 90 minutes; the team spends its effort elsewhere.
W: Keep the simple batch with a monitored revisit trigger: proportionate engineering with a plan for when conditions change.
X: A=Always incremental: ignores the real cost and risk of incremental state for a pipeline that is fine.
C=Streaming: a mode change far more complex than the question.
D=Last month only: changes the output semantics; the business needs the full history.
T: Choose processing mode by current needs and growth; do not add incremental complexity before it pays off.
V: incremental transforms, schedules
