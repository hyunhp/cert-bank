@ PLTR-DE D5 T5.2 applied use-case
S: An orders dataset must satisfy: order id unique, customer id present, amount non-negative except for refunds, and order date not in the future. A build that violates any rule must not publish. Which expectations should be defined?
A: None in the build; a reviewer checks a sample of each new transaction against the four rules every morning
B: None that block; instead a health check per rule, set to alert the data team after each build has published
C: One expectation that the row count is above zero, since source problems usually shrink the delivered data
D: One blocking expectation per rule: unique order id, non-null customer id, amount by order type, no future date
K: D
G: ## Expressing a data contract as expectations
The exam guide asks you to use expectations to stop invalid transactions when correctness matters. Each contract rule maps to one expectation, which makes failures specific and the contract readable.
## Rules
- Uniqueness of `order_id`.
- Non-null `customer_id`.
- `amount >= 0 OR order_type = 'refund'`.
- `order_date <= current_date`.
Each fails the build on violation; the failure message names the rule, so the fix is targeted.
Example: a source bug ships 12 orders dated next year; the date expectation fails and the previous good transaction stays published.
W: One build-blocking expectation per rule: each contract rule is checked during the build, a violation stops publication, and the failure names the rule that broke, so the fix is targeted.
X: A=Morning reviewer: a person sampling data is not a check in the build; nothing evaluates the rules during the build and nothing blocks publication.
B=Health checks that alert: they report after publishing; the requirement is to block a violating build before it publishes.
C=Row count above zero: none of the four rules affects the row count; invalid rows would pass.
T: Encode each contract rule as its own build-blocking expectation.
V: expectations

@ PLTR-DE D6 T6.3 applied use-case
S: A restricted view must hide rows for customers who opted out of analytics from everyone except the privacy team. The opt-out flag is in a separate consent dataset. How should this be built?
A: Add a do_not_use column to the dataset and document that analysts must exclude the flagged rows
B: Delete opted-out customers from the source system so that their records never reach the platform
C: Publish a saved filter that drops opted-out customers and ask analysts to apply it in every query
D: Join consent into the backing dataset and let the view's policy limit opted-out rows to one group
K: D
G: ## Policies driven by consent data
The exam guide covers restricted views and governed data preparation. A policy can only act on attributes present in the dataset it governs.
## Design
- Pipeline: join consent into the backing dataset; expectation that every row has a consent status.
- Policy: rows with `opted_out = true` visible only to the privacy group.
- Refresh with consent changes.
Example: a customer opts out on Monday; by Tuesday's build their rows are invisible to analysts.
W: Consent joined into the backing data with a policy enforcing it: the policy can only act on attributes in the dataset it governs, so joining consent in lets it show opted-out rows to the privacy group alone, and opt-outs are honoured for every reader automatically.
X: A=Advisory column: the rows remain readable by everyone; a column name and a note ask for care but enforce nothing.
B=Delete at source: the privacy team still needs the records; deletion is a different obligation.
C=Saved filter analysts apply: one query without the filter exposes opted-out customers; nothing enforces the requirement.
T: Bring consent attributes into governed data so restricted view policies can enforce them.
V: restricted views, Pipeline Builder

@ PLTR-DE D6 T6.2 applied troubleshooting
S: A project contains raw syncs, transforms, curated outputs and three Workshop apps. Adding a new consumer team as Viewers exposed the raw source data to them. What is the structural fix?
A: Mark every raw dataset so the consumer team cannot read it, keeping all layers in the one project
B: Split by layer: raw syncs and transforms in a restricted project, curated outputs in a viewable one
C: Remove the consumer team from the project and send them scheduled exports of the curated datasets
D: Keep the single project and ask the consumer team to open only the curated outputs and the apps
K: B
G: ## Projects as permission boundaries
The exam guide asks you to structure projects to create boundaries between sources, transforms, Ontology outputs and workflows. A role grant applies to a whole project; mixing layers in one project makes it impossible to expose one layer and not another.
## Fix
- Datasource and pipeline project: engineers only.
- Curated project: consumer teams as Viewers.
- Application project: end users.
Lineage still links the layers; permissions no longer leak.
Example: after the split, the consumer team sees four curated datasets and nothing else.
W: Split by layer into projects: the role grant then exposes only the curated layer, which is the intended boundary, while lineage still links the layers.
X: A=Markings as a workaround: markings are for sensitivity classes, not for patching a project layout; new raw datasets would need marking every time, and the structure stays wrong.
C=Scheduled exports: it removes governed access and replaces it with ungoverned copies.
D=Ask them to stay in the curated layer: not a control; the data is readable with their role, and a mistake or a departing employee makes the request meaningless.
T: Separate layers into projects so role grants expose only the intended layer.
V: projects

@ PLTR-DE D6 T6.3 applied use-case
S: A restricted view must show each sales rep their own accounts, their manager all accounts of their team, and the sales operations group everything. How should the policy be structured?
A: Three restricted views, one each for reps, managers and sales operations, each on its own filtered copy
B: A marking per sales team on the dataset, managers holding their team's marking, sales operations all
C: One restricted view whose policy ORs three conditions: owner match, managed-team match, group check
D: A Workshop module that filters accounts to the logged-in rep, with a toggle managers use to see their team
K: C
G: ## Composite policies
The exam guide covers restricted views for row-level access and their policy capabilities. Hierarchical access is expressed as a disjunction of attribute matches and group membership in one policy.
## Policy
- `row.rep_id == user.id`
- OR `row.team_id IN user.managed_teams` (from a user attribute or a mapping dataset).
- OR `user IN group:sales_ops`.
Example: a rep sees 40 accounts; her manager sees 300; sales operations see 12,000, all from one dataset and one view.
W: One composite policy: matching the row's rep to the user, or the row's team to a team the user manages, or the user to the sales operations group serves all three audiences from one dataset without copies or dataset-level workarounds.
X: A=Three views on copies: triple the maintenance, and the copies drift.
B=Markings per team: markings apply to the whole dataset; a manager would see nothing or everything, not their team's rows.
D=Workshop filter and toggle: a module filter can be changed by the user, and the data is readable through other tools; it is not access control.
T: Express hierarchical row access as one restricted view policy combining attribute matches and group membership.
V: restricted views

@ PLTR-DE D4 T4.2 advanced troubleshooting
S: A dataset's build succeeds but takes twice as long every Monday. Spark details show the Monday runs read many more input files. What is the cause and the fix?
A: Monday input is simply larger after the weekend, so the longer build is expected and needs no change
B: Weekend incremental syncs leave many small files for Monday's build; compact them into larger ones
C: A code path that only runs on Mondays is slow; add a day-of-week condition so the transform skips it
D: The cluster is busy catching up after the weekend; move the Monday build to Tuesday morning instead
K: B
G: ## File count as a performance driver
Reading many small files costs more than reading few large ones with the same total size. The exam guide names small-file accumulation and asks you to use Spark details as evidence.
## Fix
- Compaction: a scheduled step that rewrites accumulated small files into larger ones (for example, Sunday night).
- Sync configuration: fewer, larger files per run where possible.
- Monitor input file counts as a metric.
Example: after a Sunday compaction, the Monday build reads 40 files instead of 4,000 and runs as fast as any other day.
W: Small-file accumulation over the weekend, fixed by compaction: it matches the evidence (more files, same logic) exactly, and rewriting the small files into larger ones removes the Monday penalty.
X: A=Accept larger input: the file count is a controllable property of the input; compaction removes the Monday penalty entirely.
C=Monday-only code path: the logic is the same every day; the input shape differs.
D=Busy cluster: Spark details show the Monday runs reading far more input files, not waiting for resources; the evidence points at file count.
T: When builds slow with file count, compact inputs; file count is a performance variable.
V: Spark Details, datasets
