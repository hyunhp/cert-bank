# PLTR-DE batch 45: Domain 4 round 6 (Pipeline Operations and Scheduling), 8 questions

@ PLTR-DE D4 T4.1 applied use-case
S: A pipeline must build only on business days and only after the upstream finance sync has landed, because finance does not deliver on weekends or public holidays. How should the schedule be configured?
A: A fixed daily timer at 06:00 including weekends, with weekend builds simply failing when the finance data is missing
B: An input-update trigger on the finance sync, so builds happen when data lands, with freshness checks aware of business days
C: A manual build started by an engineer each business morning after checking whether finance has delivered
D: A schedule every fifteen minutes around the clock that force-builds the pipeline regardless of whether the input changed
K: B
G: ## Event-driven schedules for irregular sources
The exam guide asks for schedules that avoid unnecessary builds and fit the source's real cadence. A trigger on the upstream landing adapts automatically to weekends and holidays.
## Configuration
- Trigger: finance sync dataset updated.
- Freshness check with a business-day calendar so weekends do not alert.
- Alert if a business day passes with no landing.
Example: on a public holiday nothing lands, nothing builds and nothing alerts; the next morning's landing builds at 05:40.
W: Input-triggered builds with a business-day freshness check: builds follow the data and silence on non-delivery days is expected rather than alarming.
X: A=Daily timer with failures: produces predictable failures every weekend and trains people to ignore them.
C=Manual builds: depend on an engineer remembering each morning, with no build when they are away.
D=Fifteen-minute force builds: nearly a hundred unnecessary builds a day on unchanged inputs.
T: Trigger builds on upstream arrival and make freshness checks calendar-aware for irregular sources.
V: schedules, Data Health

@ PLTR-DE D4 T4.2 applied troubleshooting
S: A transform's runtime suddenly doubled. Job Comparison shows identical stages, but one stage now spends most of its time in garbage collection, and executor memory usage is near its limit. Input size is unchanged. What is likely and what should be done?
A: The cluster is busier than usual today, so the build should simply be rerun later without any investigation
B: A memory-heavy change (wider rows, a large cached object) is causing GC pressure; find it and reduce memory use
C: The input dataset has too many files and should be compacted before the next build runs
D: The build identity's permissions changed and the platform is retrying reads in the background
K: B
G: ## Memory pressure signatures
The exam guide asks you to classify slowdowns with Spark details. Heavy garbage collection near the memory limit with unchanged input size points to memory-hungry rows or objects.
## Investigation
- Row width: a new wide column (large JSON, arrays).
- Code: a cached or collected object grew.
- Fix: select fewer columns, avoid caching large intermediates, then adjust memory if still needed.
Example: an upstream team added a 50 KB JSON column; selecting only needed fields restores the normal runtime.
W: GC pressure from wider rows or large objects, found in Spark details and fixed by reducing memory use: the evidence matches and the fix targets it.
X: A=Busier cluster: contention shows as waiting, not as garbage collection inside the stage near the memory limit.
C=Compact inputs: file count affects read overhead, not in-stage memory pressure.
D=Permission retries: permission problems fail visibly; they do not appear as garbage collection.
T: Heavy GC near memory limits means memory-hungry data or code; reduce memory use before adding resources.
V: Spark Details, Job Comparison

@ PLTR-DE D4 T4.3 applied use-case
S: An engineer discovers that a scheduled pipeline has been failing silently for a week because its failure alerts were routed to a person who left the company. What should be fixed?
A: Re-route the alerts to the engineer who discovered the issue, since they now know about the pipeline
B: Route alerts to a team rotation instead of a person, record ownership, and review routing periodically
C: Disable alerts for the pipeline, since nobody noticed the failures for a week and they must not matter
D: Add more people individually to the alert list so that at least one of them is likely to still work at the company
K: B
G: ## Ownership and alert routing
The exam guide treats alert routing and ownership as operational responsibilities. Alerts sent to an individual fail when that person leaves.
## Fix
- Route to a group or on-call rotation.
- Ownership recorded on the pipeline.
- Periodic review of routing and owners; offboarding checklist includes alert reassignment.
Example: the alert now reaches the data on-call rotation; the next failure is acknowledged within 15 minutes.
W: Group-based routing with recorded ownership and periodic review: alerts survive staff changes.
X: A=Re-route to the discoverer: repeats the single-person failure with a different name.
C=Disable alerts: a week of silent failure is the problem, not proof the alerts are unnecessary.
D=More individuals: still individuals; the list decays as people move on.
T: Route alerts to teams or rotations, not individuals, and review routing as staff change.
V: Data Health, schedules

@ PLTR-DE D4 T4.4 applied troubleshooting
S: After a pipeline was moved to a new project, its scheduled builds stopped running, although the code and datasets are intact. What should be checked?
A: Whether the transform code needs to be rewritten for the new project, since code written in one project cannot run in another
B: Whether the schedule and its build identity survived the move and still have access to inputs and outputs
C: Whether the datasets need to be deleted and recreated in the new project for the schedule to recognize them
D: Whether the platform pauses all schedules for a week after any project move as a safety measure
K: B
G: ## Moves and operational configuration
The exam guide asks you to diagnose builds and permissions. Schedules and build identities are operational configuration that must survive a move and still have access.
## Checks
- Schedule exists and targets the moved datasets.
- Build identity: permissions on inputs and outputs in their new locations.
- A test build confirms.
Example: the schedule's owner lost access after the move; transferring the schedule to the team's service identity restores the builds.
W: Schedule and identity verification after the move: the code is fine, but what runs it and its access must be re-established.
X: A=Rewrite code: transform code is not tied to a project; nothing in it needs to change.
C=Delete and recreate datasets: destroys history and lineage for a scheduling problem.
D=Automatic pause: no such rule exists; something concrete about the schedule or permissions broke.
T: After moving pipelines, verify schedules and build identities still exist and have access.
V: schedules, projects

@ PLTR-DE D4 T4.1 applied tradeoff
S: A heavy pipeline and an urgent ad hoc analysis compete for the same compute every morning. The pipeline must finish by 08:00; the analysis is needed by noon. How should this be handled?
A: Run both at 06:00 with maximum resources so that both finish as early as possible regardless of contention
B: Run the deadline-bound pipeline first or on reserved capacity, then the analysis, verifying both deadlines
C: Cancel the analysis permanently because pipelines always take precedence over analysts
D: Run the analysis first since it is urgent, and let the pipeline finish whenever it can
K: B
G: ## Scheduling by deadline
The exam guide asks for scheduling that respects deadlines and resources. The pipeline's deadline is earlier and harder; the analysis has slack.
## Plan
- Pipeline first or with reserved capacity; finishes by 07:30.
- Analysis starts after; finishes well before noon.
- Monitor durations so a growing pipeline does not squeeze the analysis.
Example: the pipeline finishes at 07:20 and the analysis at 09:10; both deadlines are met.
W: Order or reserve by deadline: the earlier hard deadline is protected and the flexible work still finishes in time.
X: A=Both at once with maximum resources: they contend and both slow down, risking the 08:00 deadline.
C=Cancel the analysis: the business needs it; it simply has more slack.
D=Analysis first: risks the pipeline's earlier, harder deadline for work that could wait.
T: Sequence or reserve compute according to deadlines when workloads compete.
V: schedules

@ PLTR-DE D4 T4.2 applied use-case
S: A data engineer wants to understand why a dataset built today is slower than the same build last week. Which tool directly compares the two runs?
A: The dataset's description field, which records performance notes added by previous engineers over time
B: Job Comparison, which compares the two builds' stages, durations, volumes and resources side by side
C: The Ontology Manager, which shows how each object type was indexed after the build finished
D: The user access audit log, which lists who opened the dataset during the week
K: B
G: ## Comparing builds
The exam guide names Job Comparison and Spark details for diagnosing performance changes. A side-by-side comparison localizes the difference.
## Use
- Compare stages: which got slower?
- Compare volumes: did input or shuffle grow?
- Compare resources: executors, memory.
Example: the comparison shows the join stage reading 4× more data because an upstream filter was removed.
W: Job Comparison: the tool built for exactly this question, showing which stage and which metric changed between the two runs.
X: A=Description field: free text, rarely updated, and not a measurement of either run.
C=Ontology Manager: concerns object types and indexing, not the transform's build performance.
D=Access audit log: records who viewed data, not how the build executed.
T: Use Job Comparison to locate what changed between a slow build and a normal one.
V: Job Comparison, Spark Details

@ PLTR-DE D4 T4.4 applied use-case
S: A team wants to release pipeline changes weekly with minimal risk. Which release practice fits?
A: Merge every change directly into main as soon as it is written, since small changes cannot cause problems
B: Branch per change with branch builds and output comparison, reviewed merges, release notes and rollback
C: Collect all changes for three months and release them together in one large merge to minimize the number of releases
D: Release changes only on Friday evenings so that problems surface over the weekend when fewer people use the data
K: B
G: ## Routine, safe releases
The exam guide lists branch and release management among operational responsibilities. Small, validated, reviewed changes with rollback make frequent releases safe.
## Practice
- Branch per change; branch builds; output comparison.
- Review and merge; release note listing changes.
- Rollback: revert the merge or restore previous transactions.
Example: a weekly release with four changes; one regression found in comparison is fixed before merge.
W: Branch-validated, reviewed releases with notes and rollback: frequent change with controlled risk.
X: A=Direct to main: unvalidated changes reach consumers immediately, however small.
C=Quarterly big bang: many changes at once make failures hard to diagnose and roll back.
D=Friday evenings: problems surface when nobody is watching, delaying response.
T: Release pipeline changes through branches, comparison, review and a rollback path.
V: branches, Code Repositories

@ PLTR-DE D4 T4.3 advanced troubleshooting
S: An on-call engineer finds that a critical dataset failed to build because one of twelve inputs is stale; the other eleven are fresh. Consumers need today's data by 09:00. What is the best response?
A: Rebuild the dataset ignoring the stale input entirely, without telling consumers that one source is missing from today's figures
B: Diagnose the stale input; if unfixable in time, let the owner choose a caveated publish or the last good version
C: Delete the stale input dataset so that the build stops depending on it and succeeds every day from now on
D: Wait silently until the stale input recovers on its own, however long that takes, without informing anyone
K: B
G: ## Partial inputs under a deadline
The exam guide's playbook asks for diagnosis, smallest safe repair, and communication of impact. Publishing incomplete data silently is not safe; neither is silence.
## Response
- Find why the input is stale (failed sync, source outage).
- Repair if possible within the window.
- Otherwise: owner decides between a caveated partial publish or the last good version; consumers informed.
Example: the source is down until noon; the owner holds yesterday's version with a banner and republishes at 12:30.
W: Diagnose, attempt repair, and make an informed, communicated decision: consumers are never misled about completeness.
X: A=Silent partial publish: consumers act on figures missing a twelfth of the data without knowing.
C=Delete the input: removes a needed source permanently to avoid one day's problem.
D=Silent waiting: the deadline passes with consumers uninformed.
T: When an input is stale near a deadline, diagnose, repair if possible, and communicate an explicit decision.
V: Data Lineage, Data Health
