# PLTR-DE batch 47: Domain 6 round 6 (Security, Projects, and Governance), 8 questions

@ PLTR-DE D6 T6.1 applied use-case
S: A dataset contains salary data. Only HR and payroll may read it. A derived dataset aggregates average salary by department with at least 20 employees per group, intended for all managers. How should markings be handled?
A: Apply the salary marking to both datasets so that only HR and payroll can read the aggregate as well
B: Keep the source marked; after a documented review that the aggregate cannot reveal individuals, publish it unmarked
C: Remove the marking from the salary dataset so that the aggregation pipeline can run under any identity
D: Publish the aggregate with no review, since aggregates are never sensitive in any circumstance
K: B
G: ## Deliberate de-identification
The exam guide asks for least privilege and sensitivity that follows data unless deliberately removed. An aggregate can be unmarked after a documented review that it no longer reveals individuals.
## Practice
- Source: marked; pipeline identity holds the marking.
- Aggregate: minimum group size enforced; review documented.
- Published to managers without the marking.
Example: departments under 20 employees are suppressed; the review is recorded with the dataset.
W: Marked source, reviewed and documented unmarked aggregate: managers get the insight without access to individual salaries.
X: A=Mark the aggregate: managers lose access to data that was designed and reviewed to be safe for them.
C=Remove the source marking: exposes individual salaries to anyone with project access.
D=No review: small groups can reveal individuals; aggregation alone is not a guarantee.
T: Unmark derived aggregates only after a documented review that they cannot reveal individuals.
V: markings

@ PLTR-DE D6 T6.2 applied use-case
S: A new analyst joins the marketing team and needs read access to the team's curated datasets but nothing else. What is the cleanest way to grant it?
A: Grant the analyst Owner on every project in the organization so that they never encounter a permission error
B: Add the analyst to the marketing consumers group that already holds Viewer on the marketing curated project
C: Grant Viewer on each marketing dataset individually to the analyst's personal account, one dataset at a time
D: Share an existing team member's credentials with the analyst until permanent access is arranged
K: B
G: ## Group-based access
The exam guide asks for least privilege managed through roles and groups. Group membership grants exactly the team's access and is removed in one step later.
## Practice
- Group: marketing consumers with Viewer on the curated project.
- New analyst: added to the group.
- Offboarding: removed from the group.
Example: the analyst sees the 14 curated datasets on day one and nothing in the raw datasource project.
W: Group membership with the team's existing Viewer grant: exactly the needed access, managed in one place.
X: A=Owner everywhere: extreme over-provisioning, including delete rights on unrelated data.
C=Per-dataset grants: tedious, error-prone and easy to forget at offboarding.
D=Shared credentials: the analyst's actions are attributed to someone else, and identity and audit controls are broken.
T: Grant access through groups that hold project roles, not through individual or shared accounts.
V: projects

@ PLTR-DE D6 T6.3 applied troubleshooting
S: After a restricted view's policy was updated to add a new region, users from an existing region report seeing no rows at all. What is the likely cause?
A: The underlying dataset was deleted at the same time the policy was updated
B: The edit introduced a logic error (AND instead of OR, a mistyped attribute); test the policy with users from each region
C: The users' browsers need to be restarted after any policy change
D: Restricted views can only support one region condition at a time, so adding a second region automatically breaks the first
K: B
G: ## Testing policy changes
The exam guide asks you to diagnose access with evidence and to validate changes. A policy edit that removes access for an unrelated group is almost always a logic error.
## Fix
- Review the edited policy: boolean structure and attribute names.
- Test with users from each region (or Check Access per identity).
- Add a policy test step to the change process.
Example: the edit wrapped both regions in an AND; changing to OR restores the existing users' rows.
W: A logic error in the edited policy, found by testing with representative users: the symptom follows directly from the change.
X: A=Dataset deleted: other users can still see rows, so the data exists.
C=Restart browsers: policies are evaluated on each query, not cached in the browser.
D=One-region limit: policies can express any number of conditions.
T: Test restricted view policies with users from every audience after each change.
V: restricted views, Check Access

@ PLTR-DE D6 T6.4 applied use-case
S: An auditor asks which identities could read a sensitive dataset at any time during the last quarter. What evidence should the data engineer provide?
A: The current list of users who can read the dataset today, which should reflect the last quarter's access closely enough
B: Role, group and marking membership history for the quarter, with access logs showing actual reads
C: A statement from the project owner that only the right people had access throughout the quarter
D: A screenshot of the project's sharing settings taken at the end of the quarter
K: B
G: ## Point-in-time access evidence
The exam guide asks for governance with audit evidence. "Who could read it during the quarter" requires history, not today's state.
## Evidence
- Membership history: roles, groups, markings over the quarter.
- Access logs: who actually read the dataset.
- Combined into a timeline for the auditor.
Example: two users had access for three weeks through a group later removed; logs show one of them read the dataset twice.
W: Membership change history plus access logs: the auditor sees who could and who did read the dataset across the quarter.
X: A=Today's list: anyone added and removed during the quarter is invisible in today's state, which is exactly what the auditor asks about.
C=Owner's statement: an assertion from the person accountable for the access, with no records to support it.
D=End-of-quarter screenshot: a single moment, not the quarter.
T: Answer point-in-time access questions with membership history and access logs.
V: Check Access, projects

@ PLTR-DE D6 T6.1 applied comparison
S: A data engineer is explaining to a new team member what happens to sensitivity when marked data flows through pipelines into other projects. Which statement about how markings propagate is correct?
A: Markings apply only to the dataset they are placed on and never to any dataset derived from it by a transform
B: Markings follow data through lineage into derived datasets, unless deliberately removed after review
C: Markings propagate only to datasets in the same project as the marked source
D: Markings propagate only when a user manually copies them to each derived dataset
K: B
G: ## Inheritance through lineage
The exam guide describes markings as mandatory controls that follow data. Derived outputs inherit markings unless intentionally de-identified and unmarked.
- Propagation via lineage, regardless of project.
- Removal is a deliberate, reviewed act.
Example: a marked customer dataset feeds a curated orders dataset in another project; the curated dataset carries the marking.
W: Lineage-based propagation with deliberate removal: the accurate description of how markings travel.
X: A=Source only: if derived datasets did not inherit markings, any transform would be a way to strip sensitivity from data.
C=Same project only: lineage crosses projects; so do markings.
D=Manual copying: propagation happens automatically through lineage; relying on manual copying would leave gaps.
T: Markings follow data through lineage into derived datasets across projects.
V: markings, Data Lineage

@ PLTR-DE D6 T6.2 applied tradeoff
S: A team wants to give a third-party vendor access to one curated dataset for a six-week integration project. Which approach balances need and risk?
A: Add the vendor's users to the organization permanently with Viewer on all curated projects so future projects are easier
B: Time-bound Viewer access through a dedicated group on a project holding only the needed dataset, with expiry
C: Copy the dataset to the vendor's systems without any record of the transfer
D: Refuse any access, since vendors should never see company data
K: B
G: ## Scoped, time-bound access
The exam guide asks for least privilege and governed sharing. External access should be as narrow and as short as the need.
## Design
- Dedicated project or scoped extract containing only the dataset.
- Vendor group with Viewer; expiry date set.
- Review and removal at the end; audit retained.
Example: access ends automatically after six weeks; the review confirms removal.
W: A narrow, expiring grant to a dedicated scope: the vendor can work and the exposure ends with the project.
X: A=Permanent broad access: far beyond the need and never revoked.
C=Unrecorded copy: data leaves the platform with no egress policy, no record and no way to know what the vendor holds.
D=Refuse all: blocks a legitimate business need that can be met safely.
T: Give external parties narrow, time-bound access to only the data they need.
V: projects, exports

@ PLTR-DE D6 T6.3 applied use-case
S: A restricted view must hide rows for customers who opted out of analytics from everyone except the privacy team. The opt-out flag is in a separate consent dataset. How should this be built?
A: Ask analysts to remember to filter out opted-out customers in every query they run
B: Join consent into the view's backing dataset and write a policy showing opted-out rows only to the privacy team
C: Delete opted-out customers from the source system entirely so that their records never reach the platform at all
D: Add a column named "do_not_use" and trust that analysts will respect it
K: B
G: ## Policies driven by consent data
The exam guide covers restricted views and governed data preparation. A policy can only act on attributes present in the dataset it governs.
## Design
- Pipeline: join consent into the backing dataset; expectation that every row has a consent status.
- Policy: rows with `opted_out = true` visible only to the privacy group.
- Refresh with consent changes.
Example: a customer opts out on Monday; by Tuesday's build their rows are invisible to analysts.
W: Consent joined into the backing data with a policy enforcing it: opt-outs are honoured for every reader automatically.
X: A=Analysts remember: one forgotten filter exposes opted-out customers; nothing enforces the requirement.
C=Delete at source: the privacy team still needs the records; deletion is a different obligation.
D=Advisory column: the rows remain readable by everyone; a column name asks for care but enforces nothing.
T: Bring consent attributes into governed data so restricted view policies can enforce them.
V: restricted views, Pipeline Builder

@ PLTR-DE D6 T6.4 advanced troubleshooting
S: A build identity has accumulated access to 300 datasets over two years, although the pipeline now reads only 12. What risk does this create and what should be done?
A: No risk; extra access is harmless as long as the pipeline's code does not read the other datasets
B: Excess privilege widens the blast radius; trim grants to the 12 inputs and outputs, verify on a branch, review regularly
C: Delete the build identity and create a new one with administrator rights so permission problems never occur
D: Rename the identity so that it is less likely to be misused
K: B
G: ## Least privilege for pipelines
The exam guide asks for least privilege at every layer, including build identities. Accumulated grants enlarge the blast radius of any defect or compromise.
## Remediation
- Lineage: list actual inputs and outputs.
- Remove all other grants.
- Branch build to confirm nothing needed was removed.
- Quarterly review of identity grants.
Example: 288 grants removed; the pipeline builds normally; a later bug that pointed at a wrong dataset fails instead of reading it.
W: Trim the identity to its real inputs and outputs and review periodically: the blast radius shrinks without breaking the pipeline.
X: A=Harmless: a code change or compromise could use any of the 300 grants.
C=Administrator identity: grants the pipeline access to everything, the exact opposite of what least privilege requires.
D=Rename: the identity's 300 grants are unchanged by its name; obscurity does nothing to reduce what it can read.
T: Keep build identities scoped to their actual inputs and outputs and review grants regularly.
V: Check Access, Data Lineage
