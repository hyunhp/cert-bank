# PLTR-DE batch 10: Domain 1 round 2 (Data Connectivity and Ingestion), 8 questions

@ PLTR-DE D1 T1.1 applied comparison
S: A team needs to ingest files that a partner drops onto an SFTP server every night, each file named with the date. Which sync configuration fits?
A: A JDBC sync pointed at the SFTP host, since all network sources are reached through the same database driver
B: A file-based sync on an SFTP source that picks up new files matching the naming pattern and appends them to the raw dataset
C: A streaming sync that watches the SFTP server for changes and emits each line as a message in real time
D: A manual download of each file by the on-call engineer every morning, followed by an upload through the browser into the raw dataset
K: B
G: ## Connector follows the source protocol
The exam guide asks you to select connectors based on source protocol, network reachability and required capabilities. SFTP is a file transfer protocol; the matching connector is a file-based source, not a database driver or a stream consumer.
## Configuration
- Source: SFTP with credentials stored in the connection.
- Sync: file pattern (for example `report_YYYY-MM-DD.csv`), new files only, append transactions.
- Downstream: a transform parses the raw files into a typed dataset with expectations.
Example: each night the sync finds one new file, appends it, and the parsing transform runs on the appended file only.
W: File-based SFTP sync with a pattern and append: it matches the protocol and the nightly-file behaviour, and feeds incremental processing downstream.
X: A=JDBC: a database driver cannot talk to a file server; the protocol does not match.
C=Streaming: files landing once a night are a batch source; treating them as a stream adds complexity without a continuous requirement.
D=Manual download: unreliable, unscheduled, and a person becomes the ingestion system.
T: Choose the connector by protocol: file sources get file syncs, databases get JDBC, streams get streaming syncs.
V: Data Connection

@ PLTR-DE D1 T1.2 applied troubleshooting
S: A CDC sync replicates a customer table including deletes. Analysts report that customers deleted in the source still appear in a downstream curated dataset. Where is the problem likely to be?
A: In the CDC sync, which by design captures only inserts and updates and never deletes, so the source team must stop deleting rows entirely
B: In the downstream transform, which treats the change records as appends and never applies the delete markers to its output
C: In the agent, which drops delete events when the network is slow
D: In the Ontology, which caches deleted objects for 30 days before removing them
K: B
G: ## CDC produces change records
Change-data-capture delivers inserts, updates and deletes as change events. The exam guide expects you to distinguish CDC from other patterns and to understand transaction semantics. The replicated dataset holds those events; producing a current-state table is a transform's job, and it must honour delete markers.
## Check
- Inspect the raw CDC dataset: are delete events present for the deleted customers? If yes, the sync is fine.
- Inspect the transform: does it apply inserts and updates but ignore deletes (or filter them out)?
- Fix: a merge that removes keys with a delete marker (or marks them deleted) in the current-state output.
Example: 120 delete events exist in the raw dataset; the transform's merge logic adds a delete branch and the customers disappear from the curated view.
W: Transform ignoring delete markers: CDC captured the deletes; the current-state logic failed to apply them, which exactly produces lingering deleted rows.
X: A=CDC never captures deletes: CDC is precisely the pattern that captures deletes; this is backwards.
C=Agent drops events: agents transport data; dropping specific event types is not a known behaviour, and the raw dataset would show the gap.
D=Ontology cache: the issue is in the curated dataset, upstream of any object indexing.
T: With CDC, the raw dataset holds change events; make sure the current-state transform applies deletes as well as inserts and updates.
V: Data Connection, incremental transforms

@ PLTR-DE D1 T1.3 applied use-case
S: A data engineer notices that a sync's source credentials are written in a transform's code so that the transform can query the source directly as well. What should be done?
A: Nothing, since credentials in code are acceptable when the repository is private
B: Remove them from the code; keep them in the Data Connection source configuration and have the transform read the synced dataset instead
C: Encrypt the credentials inside the code with a symmetric key that is also stored in the same repository, so they are no longer readable in plain text
D: Move the credentials into the dataset's description so they are easier to find
K: B
G: ## Credentials belong to the connection
Data Connection stores source credentials securely and uses them for syncs; transforms do not need them. The exam guide covers credentials and egress policies as ingestion concerns and least privilege throughout the lifecycle.
## Why it matters
- Credentials in code are visible to everyone with repository access and leak into history and branches.
- A transform that connects directly bypasses the sync's governance, lineage and egress controls.
- The correct flow is source → sync → dataset → transform; if a transform genuinely needs live access, use the platform's governed mechanisms, not raw credentials.
Example: the credentials are rotated, removed from the code, and the transform reads `customers_raw` produced by the sync.
W: Credentials only in the source configuration, transform reads the synced dataset: secure storage and governed data flow are restored.
X: A=Private repo is fine: private is not secure; history, forks and everyone with access can read them.
C=Encrypt with a stored key: a key next to the ciphertext is no protection.
D=Dataset description: metadata is even more widely visible than code.
T: Never put source credentials in transforms; store them in the connection and let syncs move the data.
V: Data Connection, Code Repositories

@ PLTR-DE D1 T1.4 applied troubleshooting
S: An agent-based sync has started failing intermittently: some runs succeed, others fail with connection timeouts to the source. The agent host is shared with other software. What is the right investigation?
A: Reinstall the agent on the same host, since intermittent failures of this kind usually mean the installation has become corrupted over time
B: Correlate failure times with the agent's health and host resource usage, the source database's load, and network stability
C: Increase the sync frequency so that successful runs outnumber failures
D: Switch to a direct connection, which does not need an agent and therefore cannot time out
K: B
G: ## Intermittent failures and the agent host
The exam guide names agent health among the evidence for ingestion diagnosis. An agent on a shared host competes for CPU, memory and network; a busy neighbouring job at 02:00 can starve it and produce timeouts that look random.
## Investigation
- Agent health metrics and logs around failure times.
- Host resource usage: other processes running then.
- Source database load (backup window, maintenance).
- Network: packet loss or firewall idle timeouts.
Then fix the actual cause: move the agent to a dedicated host, reschedule competing jobs, or adjust timeouts to match the source's behaviour.
Example: failures coincide with a nightly backup on the same host saturating disk and network; the agent is moved to its own VM.
W: Correlated diagnosis across agent, host, source and network: intermittent timeouts come from contention or instability, which these checks locate.
X: A=Reinstall: a corrupted install fails consistently, not intermittently; reinstalling destroys evidence.
C=More frequent syncs: more attempts on a contended host add load and more failures.
D=Direct connection: the source is behind the agent for a reason (network reachability); a direct connection is not possible and would still time out on a slow source.
T: For intermittent agent sync failures, correlate agent health, host contention, source load and network at the failure times.
V: Data Connection, agents

@ PLTR-DE D1 T1.2 applied tradeoff
S: A source table has 2 million rows, no reliable timestamp or increasing key, and about 5% of rows change each day in place. Which sync pattern should be used?
A: An append sync keyed on the primary key, which will capture the changed rows automatically because their keys already exist in the dataset
B: A daily snapshot sync, since without a change signal there is no safe way to identify changed rows, and the copy is affordable
C: A streaming sync, since in-place changes are best captured continuously
D: An update sync on a `last_modified` column that the source does not have
K: B
G: ## When there is no change signal
Incremental patterns (append, update, CDC) each need something to identify what changed: an increasing key, a modification timestamp, or a change log. The exam guide asks you to choose the sync pattern from source behaviour.
## Here
- Rows change in place, so append cannot see them.
- No timestamp, so update cannot select them.
- No CDC available (not stated), so no change log.
A daily snapshot is the correct, simple choice at this size; a downstream transform can diff snapshots to produce change records if consumers need them. Revisit if the table grows or if CDC becomes available.
Example: the nightly snapshot of 2 million rows takes a few minutes; a transform compares it with yesterday's to produce a `changed_rows` dataset.
W: Daily snapshot: with no change signal it is the only safe pattern, and the volume makes it cheap enough.
X: A=Append on primary key: append adds new rows; it does not detect modified values of existing keys.
C=Streaming: the source is a table with in-place updates and no stream; there is nothing to stream from.
D=Update on a missing column: the signal does not exist; the sync would select nothing.
T: Without a reliable change signal, snapshot the source; incremental patterns need something to key on.
V: Data Connection

@ PLTR-DE D1 T1.3 applied use-case
S: Analysts want to run ad hoc SQL against a large external data warehouse table from Foundry, but the warehouse team forbids copying the data out. Which approach respects the constraint?
A: A snapshot sync run once at night into Foundry, since a nightly copy for analytics is not really "copying the data out" of the warehouse
B: A virtual table registered over the warehouse table, so queries are pushed to the warehouse and the data stays there
C: An agent that caches the table on its host so analysts can query the cache
D: Exporting the table to CSV and emailing it to analysts
K: B
G: ## Querying in place
A virtual table registers an external table in Foundry without ingesting it; queries execute against the source. The exam guide lists virtual tables among ingestion options and asks you to choose based on required capabilities and constraints.
## Fit
- The data never leaves the warehouse, satisfying the policy.
- Analysts query it from Foundry with their permissions.
- Compute happens on the warehouse side; monitor cost and performance there.
If a pipeline later needs the data inside Foundry, that becomes a separate governance conversation.
Example: the virtual table appears alongside Foundry datasets; a query joins it with a small Foundry dataset for an analysis.
W: Virtual table: it provides the access analysts need while the data remains in the warehouse, which is exactly the constraint.
X: A=Nightly copy: a copy is a copy regardless of schedule; a dataset in Foundry holding the warehouse data violates the policy.
C=Agent cache: a cache on the agent host is an ungoverned copy outside both systems, and agents are not designed to serve queries.
D=CSV export by email: the least governed copy of all; it leaves both systems entirely and spreads to every inbox it is forwarded to.
T: When data must stay at the source, use a virtual table rather than any form of copy.
V: virtual tables

@ PLTR-DE D1 T1.4 applied use-case
S: A newly configured REST API sync returns only the first 1,000 records on every run although the source has 80,000. What is the most likely configuration problem?
A: The agent's memory limit on its host, which caps the number of records a single sync run can hold before writing them to the dataset
B: Pagination is not configured, so the sync reads only the first page of the response and never requests the next pages
C: The dataset's schema has a 1,000-row limit set in the Ontology
D: The API requires a streaming sync to return more than one page
K: B
G: ## Paginated APIs
REST APIs typically return results in pages with a cursor, offset or next-link. A sync configured without pagination fetches one page and stops; the round number (1,000) is the tell-tale sign of a page size. The exam guide expects you to configure connectors according to source capabilities and to diagnose ingestion with execution history and schema evidence.
## Fix
- Configure the sync's pagination (cursor or offset parameters, "next" link handling).
- Verify with execution history that the run fetched 80 pages.
- Add a size health check so a future regression to 1,000 rows is noticed.
Example: after enabling cursor pagination, the run reports 80,000 records and takes a few minutes.
W: Missing pagination: a fixed first page of records is the classic symptom, and configuring pagination resolves it.
X: A=Agent memory: a memory limit would fail the run, not cleanly return a round 1,000 records every time.
C=Ontology row limit: datasets have no such schema-level row cap.
D=Streaming requirement: REST pagination is a batch concern; streaming syncs are for message streams.
T: Exactly one page of records from an API sync means pagination is not configured.
V: Data Connection

@ PLTR-DE D1 T1.1 advanced tradeoff
S: A company must ingest data from 40 similar on-premises sites, each with its own database behind its own firewall. Which connection architecture scales best while keeping each site's network closed to inbound traffic?
A: One central agent in the head office that opens VPN tunnels into each site
B: An agent at each site connecting outbound and running that site's syncs, managed centrally with health monitoring and standard configuration
C: Direct connections from Foundry to each of the 40 site databases after every site's firewall has been opened for inbound traffic from the platform
D: A nightly email from each site containing a database dump
K: B
G: ## Agents per network boundary
Agents connect outbound from inside the network they serve. The exam guide asks you to select connection architectures from network reachability; 40 closed networks mean 40 (or more) agents, standardized and monitored.
## Operating at scale
- Standard agent configuration and credentials per site.
- Central monitoring of agent health; alerts when a site's agent is down.
- Syncs templated per site so a new site is onboarded consistently.
Example: site 23's agent goes offline; the health alert names it and the site's IT team restarts the host.
W: Per-site outbound agents with central management: it respects every site's closed network and scales through standardization and monitoring.
X: A=Central agent with VPNs: 40 VPN tunnels into closed sites is complex, often not permitted, and a single point of failure.
C=Open 40 firewalls: it violates the inbound constraint everywhere.
D=Email dumps: not an ingestion architecture; unreliable and ungoverned.
T: For many closed networks, deploy an agent per network with centralized monitoring and standard configuration.
V: Data Connection, agents
