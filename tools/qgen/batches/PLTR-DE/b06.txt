# PLTR-DE batch 06: Domain 5 (Data Quality and Health Monitoring), 8 questions

@ PLTR-DE D5 T5.1 applied comparison
S: A data engineer is asked to explain the difference between expectations and health checks to a new team member. Which description is accurate?
A: Expectations run inside a build and can block the transaction when a condition fails; health checks run over time and raise alerts
B: Expectations and health checks are the same mechanism; expectations are simply health checks that are defined in transform code instead of in the user interface
C: Health checks run inside the build and block it, while expectations run on a schedule afterwards and send notifications
D: Expectations apply only to Pipeline Builder pipelines and health checks only to code repositories, so the choice is made by authoring tool
K: A
G: ## Two layers of quality
The exam guide draws a line between proactive expectations and reactive health checks:
- **Expectations** are assertions evaluated during a build (row counts, nulls, uniqueness, allowed values, schema). A failing expectation can fail the build so the output transaction is never committed. They prevent bad data from being published.
- **Health checks** monitor a dataset over time (freshness, schema changes, size, build status, content). They detect problems and alert, but they operate on data that already exists.
Both apply to pipelines from either authoring tool.
Example: an expectation `customer_id is not null` fails the build at 02:10 and the dashboard keeps yesterday's good data; a freshness health check alerts at 06:00 that no new data arrived.
W: Build-time blocking versus over-time alerting: this is the accurate distinction and the reason the two tools serve different requirements.
X: B=Same mechanism: they differ in when they run and whether they can block; the difference is not just where they are defined.
C=Reversed: health checks do not block builds; expectations are the build-time checks.
D=By authoring tool: both tools work with both Pipeline Builder and code transforms.
T: Expectations block invalid transactions during the build; health checks watch datasets afterwards and alert.
V: Data Health, expectations

@ PLTR-DE D5 T5.2 applied use-case
S: An Ontology object type for Patients is backed by a dataset. The patient id must be unique and non-null, and the date of birth must fall within a plausible range. Any violation must prevent the data from reaching the Ontology. What should be configured?
A: Health checks on the dataset for null ids, duplicate ids and out-of-range dates, with alerts to the data owner
B: Build-blocking expectations for id uniqueness, id non-null and date-of-birth range, so a violating build fails before the Ontology is updated
C: A transform that drops rows violating any of the rules, so the Ontology only ever receives valid rows
D: A Workshop validation rule that hides patients with invalid data from end users in the application while keeping the rows in the Ontology
K: B
G: ## When correctness must be guaranteed
The exam guide asks you to use expectations to stop invalid transactions when correctness matters. Patient identity is such a case: a duplicate id would merge two people's records in the Ontology; a null id would break the primary key.
## Configuring expectations
- Uniqueness of `patient_id`, non-null `patient_id`, `date_of_birth` between plausible bounds.
- A violation fails the build; the previous good transaction remains the published one; the Ontology sync does not run on bad data.
- Alert the owner on the failure so the source issue is fixed.
Dropping rows silently is tempting but hides real problems (a source bug producing nulls) and loses patients.
Example: a source change makes 300 ids null; the build fails, the Ontology keeps yesterday's complete data, and the source team is contacted.
W: Build-blocking expectations: they guarantee that no violating data is ever published to the Ontology, which "must prevent" requires.
X: A=Health checks: they alert after the bad data is published, so the Ontology would have already received duplicates or nulls.
C=Drop violating rows: silently losing patients is a correctness failure of a different kind and hides the source problem.
D=Hide in Workshop: the invalid data is still in the Ontology, affecting other consumers, links and analyses.
T: Where invalid data must never be published, use build-blocking expectations, not alerts or silent filters.
V: expectations, Ontology

@ PLTR-DE D5 T5.3 applied use-case
S: A dataset's daily build succeeded, but a consumer notices that the dataset has only 3 rows today instead of the usual 2 million. Which monitoring would have caught this automatically, and what does it show about relying on build status?
A: A build-status health check, which fails whenever the build produces fewer rows than the previous day
B: A row-count health check with a threshold, which alerts on a sudden drop; build success says nothing about completeness
C: The Linter, which would have flagged the transform as producing an unexpectedly small output
D: Nothing could have caught it automatically; only a consumer looking at the actual data can notice that the row count is wrong for the day
K: B
G: ## Successful run, wrong result
The exam guide stresses that a successful run can still produce stale, empty, duplicated or incorrect data, and asks you to check source, run status, counts, schema and lineage. Build status is binary; completeness is a content property.
## Monitoring content
- Size / row-count checks: alert when the count falls outside a range or deviates sharply from history.
- Freshness checks: alert when no new transaction arrives.
- Content checks: null rates, distinct counts of key columns.
- Schema checks: unexpected column changes.
Together with build-blocking expectations (a minimum row count can also be an expectation), they cover both "did it run" and "is it right".
Example: a row-count check with a 50% drop threshold fires at 02:15; the on-call engineer finds the source delivered an empty file.
W: Row-count or size health check: it detects the drop automatically, and the case shows that build success and data completeness are different things.
X: A=Build-status check: the build succeeded; a status check sees nothing wrong, and build status checks do not compare row counts.
C=Linter: it inspects pipeline patterns, not daily output content.
D=Nothing automatic: content checks exist precisely for this; manual discovery is the failure mode to avoid.
T: Monitor content (row counts, sizes, nulls), not just build status; a green build can carry an empty dataset.
V: Data Health

@ PLTR-DE D5 T5.1 applied tradeoff
S: A team wants to be warned when the distribution of a numeric column shifts (for example, the average order value doubling), but they do not want to block builds, since a shift may be a legitimate business change. Which control fits?
A: A build-blocking expectation on the column's mean, which fails the build when the mean moves beyond a tolerance
B: A health check on the column's statistics with an alert, so the team investigates shifts without stopping the pipeline
C: No automated control, since statistical shifts are business questions rather than data engineering concerns
D: A transform that clips values to the historical range so that the average can never move much
K: B
G: ## Detect versus prevent
The exam guide's self-check asks whether a requirement needs a build-blocking expectation, a health alert, or both. Here the team has stated they do not want to block: a doubled average may be a real promotion week. That rules out expectations and points to monitoring.
## Content monitoring
- Column statistics (mean, nulls, distinct values) tracked over time.
- An alert when the statistic leaves a band or changes sharply.
- The alert triggers investigation: source issue (duplicated rows, wrong currency) or real change.
If investigation finds that certain shifts are always errors (negative amounts), those become expectations later.
Example: the alert fires on a doubled mean; investigation shows a currency column switched from EUR to cents; the fix goes upstream and an expectation is added for the unit.
W: Health check with alert on column statistics: it warns the team as requested without blocking a build that might be correct.
X: A=Blocking expectation: this blocks legitimate business changes, which the team explicitly did not want.
C=No control: shifts caused by data errors (duplicates, units) are data engineering problems; detection is the minimum.
D=Clipping values: altering the data to suppress a signal corrupts the dataset and hides both errors and real changes.
T: When a condition may be legitimate, monitor and alert; reserve build-blocking for conditions that are always wrong.
V: Data Health

@ PLTR-DE D5 T5.3 applied troubleshooting
S: A freshness health check on a curated dataset fires every morning, but the data is actually fine and the consumers are happy. The team has started ignoring the alerts. What should be done?
A: Delete the health check, since an alert that is ignored provides no value
B: Recalibrate the threshold to the dataset's real cadence so it alerts only on genuine lateness, and route it to owners who act
C: Leave it as it is, since a noisy alert is safer than no alert at all
D: Change the check from freshness to build status, since a build-status check only fires on real failures and never produces false alerts for the team
K: B
G: ## Alert design
The exam guide asks you to design alerts and investigate failures. An alert that fires when nothing is wrong teaches people to ignore it, and the day it matters it will be ignored too. The check is miscalibrated, not useless.
## Fixing the check
- Compare the threshold with the real cadence: a daily dataset that lands at 05:30 should not have a 4-hour freshness window checked at 06:00 against a 01:00 schedule.
- Allow for known delays (weekends, monthly closes).
- Route the alert to the people who own the fix, with enough context to act.
- Review alert volume regularly; every alert should lead to an action.
Example: the window changes from 4 hours to 26 hours; the check stays silent on normal days and fires on the day the sync fails.
W: Recalibrate and route the alert: this keeps the protection and removes the noise that caused it to be ignored.
X: A=Delete the check: the dataset would then be unmonitored for the real failure the check exists for.
C=Keep the noise: an ignored alert is equivalent to no alert, with the added cost of eroding trust in all alerts.
D=Build status instead: status checks miss lateness entirely (a build that never starts is not a failed build), which is the condition the team needs to see.
T: Noisy alerts get ignored; calibrate thresholds to real cadence and route alerts to owners who act.
V: Data Health

@ PLTR-DE D5 T5.2 advanced tradeoff
S: An expectation that checks `order_total >= 0` has been failing the build for three nights because a small number of legitimate refund rows have negative totals. The dashboard has been stale for three days. What is the right resolution?
A: Remove the expectation entirely so that the builds succeed again and the dashboard refreshes
B: Correct the expectation to the real rule (negatives allowed only for refund rows), fix any dashboard logic that assumed non-negatives, and rebuild
C: Keep the expectation and ask the source team to stop sending refunds as negative totals
D: Change the expectation to a non-blocking warning so builds always succeed, and add a note in the dataset description telling consumers about negative values
K: B
G: ## Expectations encode contracts
An expectation is a statement of the data contract. When it fails, either the data is wrong or the contract was stated wrongly. Here refunds are legitimate, so the expectation was too strict; the fix is to state the contract correctly, not to abandon it.
## Resolving properly
- Refine: `order_total >= 0 OR order_type = 'refund'` (or an equivalent rule).
- Check consumers: a dashboard that summed totals assuming all were positive may need a refund treatment.
- Rebuild; confirm the dashboard is correct, including refunds.
- Record the decision so the next engineer knows negatives are expected for refunds.
The exam guide warns against silently coercing or dropping data and against masking incorrect output; the same spirit applies to the checks themselves.
W: Fix the rule and the consumers: the contract becomes accurate, legitimate data flows, and the protection against truly invalid negatives remains.
X: A=Remove the expectation: a genuinely wrong negative total (a sign error in the source) would now pass unnoticed.
C=Change the source: refunds as negatives are a reasonable representation; forcing the source to change for a miswritten check is backwards.
D=Downgrade to warning: a warning does not protect against invalid data; the contract would be enforced by nobody.
T: When an expectation fails on legitimate data, correct the rule to the real contract rather than removing or weakening the check.
V: expectations

@ PLTR-DE D5 T5.3 applied use-case
S: A data engineer is designing monitoring for a dataset that backs a safety-critical application. Which combination gives the best coverage?
A: Freshness and build-status health checks only, since those are the two failure modes that matter for an application
B: Build-blocking expectations for key correctness rules, plus freshness, schema, size and status health checks with alerts to the owner
C: A single row-count expectation, since any problem in the data will show up as a change in the number of rows
D: Daily manual inspection of the dataset by the application team before each release, since automated checks cannot capture safety-critical requirements
K: B
G: ## Layered coverage
The exam guide describes a monitoring design that distinguishes prevention from detection and investigates failures without letting known-bad data reach consumers. A safety-critical consumer needs both layers:
- **Prevent**: expectations on primary keys, required fields, allowed values and ranges; a violation fails the build.
- **Detect**: freshness (data not arriving), schema (columns changed), size (drops or spikes), status (build failures), with alerts.
- **Respond**: alerts go to an owner who can act; the investigation follows the troubleshooting playbook.
Example: the expectation catches a null sensor id at build time; the freshness check catches a silent sync failure; the schema check catches a renamed column before the application breaks.
W: Expectations plus a full set of health checks with alerts: prevention of invalid data and detection of operational drift, which together cover the ways a safety-critical dataset can go wrong.
X: A=Freshness and status only: content problems (duplicates, nulls, bad values) pass undetected into a safety-critical application.
C=One row-count rule: many defects (wrong values, nulls, schema changes) leave the row count unchanged.
D=Manual inspection: slow, inconsistent and not continuous; automation exists for exactly this.
T: For critical consumers, combine build-blocking expectations with freshness, schema, size and status monitoring and routed alerts.
V: Data Health, expectations

@ PLTR-DE D5 T5.3 applied troubleshooting
S: A schema health check alerts that a column `customer_segment` changed type from string to integer in the curated dataset. No pipeline code changed. What should the engineer do first?
A: Change the downstream transforms to cast the column back to string, so consumers keep working
B: Trace the change upstream with Data Lineage to where the type first changed, and classify it as breaking or not before altering anything
C: Accept the new type as an improvement, since integer segments are more efficient to store and compare than strings, and update the dataset documentation
D: Rerun the build, since a type change without a code change is most likely a transient inference error
K: B
G: ## Schema changes are contract changes
A type change on a published column is potentially breaking: joins, filters and Ontology mappings that expect a string may fail or behave differently. The exam guide asks you to assess lineage before changing schemas and to classify a change as additive, breaking, semantic or a source-quality issue.
## Investigating
- Lineage: find the first dataset in the chain where the type is integer; the change originates there (likely the source or an inferred schema at ingestion).
- Source: did the system start sending codes instead of names? That is a semantic change too.
- Decide: restore the contract (map codes back to names) or roll out a planned breaking change with consumer updates.
Example: the source migrated segments to numeric codes; the pipeline maps codes to names so consumers keep the string contract, and the mapping table is governed.
W: Trace with lineage and classify the change: it finds the origin and decides the right response, instead of patching symptoms downstream.
X: A=Cast downstream: casting integer codes to strings produces "3" instead of "Premium"; the semantics are still broken and the cause stays upstream.
C=Accept silently: a changed type and meaning breaks consumers; "more efficient" is not the question.
D=Rerun: the data changed type because the input did; a rerun reproduces it.
T: On a schema alert, trace the change to its origin with lineage and classify it before touching downstream code.
V: Data Health, Data Lineage
