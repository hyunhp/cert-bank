@ PLTR-DE D2 T2.2 applied use-case
S: Three regional sales datasets have the same columns but different column orders and one region uses a different name for the amount column. The team wants one combined dataset. What is the correct approach?
A: A join of the three datasets on the sales id, which brings all the rows into one output
B: A union after aligning schemas: rename the odd column, select columns in one order with consistent types, and add a region column
C: Three separate outputs kept as they are, since datasets with different column orders and names cannot be combined safely into one dataset
D: Copying all three into a spreadsheet and pasting them together before uploading
K: B
G: ## Union versus join
The exam guide lists joins, unions and aggregations among transformations to apply appropriately. A **union** stacks rows from datasets with the same structure; a **join** combines columns of related rows by key. Three regional extracts of the same table need a union.
## Aligning schemas first
- Rename `amt` to `amount` in the odd region.
- Select columns explicitly in one order with consistent types.
- Add a `region` column for provenance.
- Add an expectation that the combined schema matches the contract.
Example: 300,000 + 250,000 + 180,000 rows become one 730,000-row dataset with a region column.
W: Schema-aligned union with a region column: it stacks the rows correctly and keeps provenance.
X: A=Join on sales id: joining three regions' different sales produces no matches (or wrong ones); joins combine columns, not stack rows.
C=Keep separate: column order and a rename are trivial to align; one dataset is what consumers need.
D=Spreadsheet: manual, unrepeatable and outside the pipeline; next month's extracts would need the same hand work and nothing would be governed.
T: Same structure, more rows: union after aligning schemas; related rows, more columns: join.

@ PLTR-DE D2 T2.3 applied tradeoff
S: A transform needs a Python library for a specialized statistical computation that has no Spark equivalent, on an input of about 500 MB that fits in memory. Which engine and approach fit?
A: Spark with the library called inside a user-defined function on every executor, which is the only way to use Python libraries in a Foundry transform
B: A lightweight single-node Python transform that imports the library and processes the dataframe in memory, since the data fits
C: Rewriting the statistical computation in SQL so that no library is needed
D: Running the library in a notebook by hand each week and uploading the result
K: B
G: ## Engine choice by API needs
The exam guide asks you to choose a compute engine based on scale, memory, API needs, startup cost and feature compatibility. A library that expects a single-node dataframe and an input that fits in memory point to a lightweight engine.
## Why not Spark here
- Spark UDFs can wrap Python code, but a library that needs the whole dataset in one process does not fit the distributed model.
- Startup overhead and complexity for a 500 MB input bring no benefit.
Declare the library as a dependency in the repository so the transform is reproducible and scheduled like any other.
Example: the transform loads 500 MB into pandas, runs the library, and writes the result in two minutes.
W: Lightweight Python transform with the library as a dependency: it matches the API need and the data size while staying a governed, scheduled transform.
X: A=Spark UDF: possible for row-wise functions, but a whole-dataset statistical routine does not decompose into per-executor calls; it is forced and slow.
C=Rewrite in SQL: specialized statistics are not SQL expressions; the rewrite is impractical.
D=Manual notebook: not scheduled, not versioned, not a pipeline.
T: Library needs single-node APIs and the data fits: use a lightweight engine with the library declared as a dependency.
V: Code Repositories

@ PLTR-DE D2 T2.4 applied troubleshooting
S: A transform computes a monthly rollup. For February the output has 31 days of data, including three days that belong to March. What is the right debugging approach?
A: Delete the three March rows from the February output by hand using a dataset edit so that the monthly rollup looks right for the report
B: Reproduce on a branch, inspect the date logic (time zone, inclusive end), fix it, add a test and a date-range expectation, rebuild
C: Change the rollup to cover six weeks so that the boundary never matters
D: Ask consumers to filter the extra rows themselves since the data is otherwise correct
K: B
G: ## Boundary bugs are logic bugs
Dates at month boundaries are classic defects: a UTC timestamp converted to local time, an inclusive `<=` where `<` was intended, or a period computed from the wrong column. The exam guide asks you to debug and refactor rather than mask incorrect output.
## Approach
- Reproduce on a branch with the same input.
- Trace the three March rows: what timestamp and what period assignment did they get?
- Fix the logic; add a unit test for the boundary; add an expectation that `period_month` matches the row's date.
- Rebuild and verify February has 28 days (or 29).
Example: the transform compared `event_date <= '2026-02-28 23:59:59'` on a timestamp column in a different time zone; the fix uses a half-open interval in one time zone.
W: Reproduce, fix the boundary logic, test and guard: the defect is removed at its source and prevented from returning.
X: A=Delete rows by hand: the next build recreates them; manual edits to outputs are never a fix.
C=Widen the window: this hides the boundary bug and makes every rollup wrong by design.
D=Push to consumers: a monthly rollup with the wrong month is incorrect data; consumers should not need to repair it.
T: Fix period and date boundary logic in the transform, with tests and expectations, rather than patching outputs.
V: Code Repositories, expectations

@ PLTR-DE D2 T2.2 applied use-case
S: A team must compute, for each customer, the number of orders in the last 90 days, the total value, and the date of the most recent order, refreshed daily for an Ontology property set. Which transformation pattern is correct?
A: A row-level expression on the orders dataset that writes the customer's count, total and latest date onto every one of that customer's order rows
B: An aggregation by customer over orders from the last 90 days giving count, sum and max date, joined to the customer dataset
C: A join of orders to customers without aggregation, leaving the counting to the application
D: A manual pivot table built by an analyst every morning and uploaded as the customer dataset
K: B
G: ## Aggregations for per-entity metrics
The exam guide lists aggregations among core transformations. Per-customer metrics are a group-by: one output row per customer, with aggregate functions over that customer's filtered orders.
## Pattern
- Filter: `order_date >= today - 90 days`.
- Group by `customer_id`: count, sum(amount), max(order_date).
- Left join to customers so customers with no recent orders get zeros/nulls explicitly.
- Expose as properties on the Customer object; schedule daily.
Example: customer C-7 has 4 orders in 90 days totalling 2,300 with the latest on the 12th; the Customer object shows those three properties.
W: Filtered group-by aggregation joined to customers: it produces exactly the per-customer values at the right grain, daily.
X: A=Row-level expression: it cannot count across rows; a per-row expression sees one order at a time.
C=Join without aggregation: the application would recompute counts on every view; the metrics should be materialized properties.
D=Manual pivot: unscheduled, unrepeatable and unversioned; the Ontology property set would depend on an analyst remembering every morning.
T: Per-entity metrics are group-by aggregations at the entity's grain, joined back to the entity dataset.
V: Pipeline Builder

@ PLTR-DE D2 T2.1 applied tradeoff
S: A Pipeline Builder pipeline has grown to 60 nodes with repeated logic in several branches, and the team struggles to review changes. What should the data engineer do?
A: Keep adding nodes, since Pipeline Builder is designed for pipelines of any size
B: Refactor: extract shared logic, split into stages with intermediate datasets, and move complex branches to tested code transforms where useful
C: Rewrite the entire pipeline in code transforms immediately, since visual pipelines cannot be maintained once they pass a few dozen nodes
D: Freeze the pipeline and forbid further changes to avoid breaking it
K: B
G: ## Maintainability as a design concern
The exam guide asks you to build correct, maintainable transformations and to refactor rather than accumulate. A 60-node pipeline with duplicated logic is hard to review and easy to break.
## Refactoring options
- Reuse: factor repeated logic into shared components where the tool supports it.
- Stage boundaries: intermediate datasets with contracts, so each pipeline is small and reviewable.
- Hybrid: keep standard joins and filters visual; move complex, testable logic to code transforms.
- Validate on a branch by comparing outputs before and after.
Example: three branches that each cleaned addresses become one shared cleaning stage feeding three small pipelines.
W: Refactor into reusable pieces and clear stages, with code where it helps: this restores reviewability without discarding what works.
X: A=Keep growing: size is not the problem; duplication and lack of structure are, and they get worse.
C=Rewrite everything in code: a wholesale rewrite is risky and unnecessary; much of the pipeline is fine as visual logic.
D=Freeze: pipelines must evolve; freezing postpones the problem and blocks the business.
T: Refactor large pipelines into reusable components and staged datasets; mix visual and code transforms by what each does best.
V: Pipeline Builder, Code Repositories

@ PLTR-DE D2 T2.2 applied troubleshooting
S: A transform deduplicates customer records by email address. Reviewers find that two different customers who share a family email were merged into one. What should change?
A: Nothing, since customers who share an email address are rare and merging a few of them is an acceptable loss for a cleaner dataset
B: Revise the key: use the business identity (customer id, or name plus date of birth plus email) and route ambiguous matches to review
C: Deduplicate by name instead of email
D: Stop deduplicating entirely so that no customer can be lost
K: B
G: ## Identity is a contract decision
Deduplication merges rows believed to be the same entity. The exam guide asks for stable keys and warns that a successful match is not necessarily a meaningful relationship. Email is not identity; it is a contact attribute that can be shared.
## Fix
- Use the entity's identifier where one exists.
- Where fuzzy matching is needed, combine multiple attributes and set a confidence threshold.
- Below the threshold: do not merge; create a review task.
- Add a test with the family-email case.
Example: the two family members have different dates of birth; the revised rule keeps them separate and flags the shared email for review.
W: Identity-based key with review for ambiguous matches: it stops incorrect merges while still removing true duplicates.
X: A=Accept the loss: merging two people corrupts their records, orders and communications; it is not acceptable.
C=Name instead: names collide far more often than emails; this is worse.
D=Stop deduplicating: true duplicates then persist and inflate counts; the fix is a better rule, not no rule.
T: Deduplicate on identity, not on shared attributes; send uncertain matches to review.
V: Pipeline Builder, Code Repositories

@ PLTR-DE D2 T2.4 applied use-case
S: A code transform has a function that normalizes phone numbers into an international format. Which testing approach is appropriate?
A: No tests, since the function is small and obviously correct
B: Unit tests for typical, edge (missing country code, extensions, empty) and bad inputs in CI, plus an output-format expectation
C: Manual spot checks of a few dozen rows in a preview of the output dataset after each build, done by whoever is on call that day
D: A test that only checks that the transform builds without error
K: B
G: ## Testing transforms
The exam guide asks you to test, debug and refactor transformations. Code Repositories support unit tests that run in CI; expectations guard the output in the build.
## For a normalizer
- Typical: "+1 415 555 0100" → "+14155550100".
- Edge: "415-555-0100" (no country code), "ext. 12", letters, empty, nulls.
- Known-bad: too few digits → null with a flag, not a fabricated number.
- Expectation: every non-null output matches `^\+\d{8,15}$`.
Example: a test reveals the function dropped leading zeros for one country; it is fixed before any data is affected.
W: Unit tests on typical, edge and bad inputs in CI plus an output expectation: the function is verified before merge and guarded in production.
X: A=No tests: phone normalization has many edge cases; "obviously correct" is how bad data gets published.
C=Manual spot checks: inconsistent, after the fact, and they miss rare cases.
D=Builds without error: a transform can build and produce wrong numbers.
T: Test transformation functions with unit tests in CI and guard outputs with expectations.
V: Code Repositories, expectations

@ PLTR-DE D2 T2.2 advanced use-case
S: A dataset of 10 million product images must be processed to produce a thumbnail and the image dimensions for each. Which transformation approach is appropriate?
A: A row-level expression in Pipeline Builder that reads each image's bytes as a string column and extracts the dimensions from the header text
B: A media processing step over the image files producing thumbnails and a dimensions dataset, run as a distributed batch
C: A manual batch where an analyst opens each image and records its size
D: An LLM transform that describes each image in words
K: B
G: ## Media processing
The exam guide lists media processing among transformation operations. Images are unstructured files; processing them (resizing, extracting metadata) uses media-aware transforms operating on files rather than on tabular rows.
## Design
- Input: a media set or dataset of image files.
- Transform: distributed over files; each produces a thumbnail and metadata (width, height, format).
- Output: thumbnails as media, metadata as a dataset joined to products.
- Incremental: process only new or changed images.
Example: 10 million images processed across executors in a few hours; the dimensions dataset backs a property on Product objects.
W: Media processing transform over files as a distributed batch: it matches the data type and the scale.
X: A=Expression on bytes: tabular expressions cannot decode and resize images.
C=Manual: 10 million images cannot be opened and measured by hand in any realistic time, and the result would still not be a pipeline.
D=LLM description: a text description is not a thumbnail or exact dimensions; it is the wrong tool and far more expensive.
T: Process unstructured media with media-aware transforms in a distributed batch, not with tabular expressions.
V: Pipeline Builder, media sets
