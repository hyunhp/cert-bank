@ PLTR-DE D1 T1.1 applied comparison
S: A team must ingest from a SaaS application that offers only a REST API with OAuth authentication and a daily rate limit. Which setup is appropriate?
A: A JDBC connection to the SaaS vendor's internal database, obtained by asking the vendor for direct database credentials and a firewall exception
B: A REST source with OAuth stored in the connection, a sync with pagination and incremental parameters, scheduled within the rate limit
C: A streaming sync that polls the API continuously, so the data is always current regardless of the vendor's rate limit
D: A manual export from the SaaS interface each week by an analyst, uploaded to Foundry as a spreadsheet for the pipeline to read
K: B
G: ## Matching the connector to the API
The exam guide asks you to select connectors by protocol and required capabilities. A REST API with OAuth is served by a REST source with the credential flow handled in the connection, not by database access the vendor does not offer.
## Configuration
- OAuth client stored securely in the source; tokens refreshed by the connection.
- Pagination and incremental parameters (updated-since) so each run fetches only new records.
- Schedule sized to the rate limit; execution history shows request counts.
Example: a nightly sync fetches 20,000 updated records in 40 pages, well under the daily limit.
W: REST source with OAuth, pagination and rate-aware scheduling: the connector fits the protocol and the vendor's constraints.
X: A=Vendor database: vendors do not expose internal databases; the API is the supported interface.
C=Continuous polling: it burns the rate limit and treats a batch API as a stream.
D=Weekly manual export: unreliable, stale and ungoverned when an API sync is available.
T: Use the connector that matches the source's interface, with credentials in the connection and scheduling that respects limits.

@ PLTR-DE D1 T1.2 applied troubleshooting
S: An append sync keyed on a timestamp column occasionally misses rows that arrived at the source with a timestamp slightly earlier than the previous run's watermark, because the source commits out of order. What is the right mitigation?
A: Switch to a full snapshot every run, since the only way to guarantee completeness is to copy the whole table every time
B: Use a lookback window: re-read rows from a little before the last watermark and deduplicate on the primary key
C: Ask the source team to stop committing rows out of order, since the sync cannot be expected to handle it
D: Ignore the missing rows, since they are a small fraction and will not affect most downstream reports
K: B
G: ## Late-arriving data in incremental syncs
Watermark-based syncs assume monotonic timestamps. The exam guide asks you to understand sync patterns and their failure modes; out-of-order commits are a common one.
## Mitigation
- Lookback: fetch rows with timestamp ≥ (watermark − window), where the window exceeds the source's commit delay.
- Deduplicate overlapping rows on the primary key downstream (or in the sync's merge).
- Periodic reconciliation snapshot to catch anything beyond the window.
Example: a 30-minute lookback with key-based dedupe recovers the late rows at negligible extra cost.
W: Lookback window with deduplication: late rows are captured while the sync stays incremental.
X: A=Full snapshot: correct but discards the efficiency that the lookback preserves.
C=Change the source: often impossible; the sync should be robust to normal source behaviour.
D=Ignore: missing rows corrupt totals and may be the important ones.
T: Handle late-arriving rows in incremental syncs with a lookback window and key-based deduplication.
V: Data Connection, incremental transforms

@ PLTR-DE D1 T1.3 applied use-case
S: An auditor asks which external destinations data can be exported to from the platform and who approved them. What should the data engineer be able to show?
A: A list compiled from memory by the engineers who have set up exports in the past year
B: The configured egress policies and export destinations with approval records, plus the execution history of exports
C: The outbound firewall logs of the company network, which show every connection made by the platform
D: Nothing, since exports are configured by individual users for their own purposes and the platform does not track or approve them centrally
K: B
G: ## Egress as governed configuration
The exam guide lists egress policies and exports among ingestion-domain concepts. Egress is centrally configured and approved, so the answer to the auditor is a record, not a recollection.
## Evidence
- Egress policies: allowed destinations and who may use them.
- Export configurations: dataset, destination, schedule, owner.
- Approval records and change history.
- Execution history: what left, when, how much.
Example: three approved destinations, each with an approver and date; 90 days of export runs listed.
W: Policies, export configurations, approvals and execution history: the governed record the auditor needs.
X: A=Memory: a list reconstructed from engineers' recollection is incomplete and unverifiable, and it omits approvals and run history entirely.
C=Firewall logs: show connections, not datasets, approvals or policy.
D=Untracked: egress is centrally governed precisely so it is tracked.
T: Data egress is governed by policies and export configurations with approval and execution records.
V: exports, egress policies

@ PLTR-DE D1 T1.4 applied troubleshooting
S: A sync's execution history shows every run succeeding with zero records for the past week, while the source team confirms thousands of new rows. What is the most likely cause?
A: The agent has silently stopped forwarding data while still reporting success for every run
B: The sync's incremental condition or filter no longer matches new rows (a watermark reset, a status value the source stopped using)
C: The dataset has reached a storage limit on the platform and silently rejects new transactions without reporting an error to the sync
D: The source team is mistaken, and no new rows actually exist in the table
K: B
G: ## Successful but empty runs
A run that selects zero rows succeeds. The exam guide asks you to diagnose with execution history and schema evidence; "success with zero" points to the selection logic.
## Checks
- The sync's incremental condition: watermark value versus the source's current values (a reset or time-zone change makes the condition select nothing).
- Filters: a status or type filter whose values changed at the source.
- Query the source with the sync's own condition to confirm.
Example: the source migrated to a new `updated_at` in UTC; the stored watermark in local time is "in the future", so nothing qualifies.
W: Selection logic no longer matching: it produces exactly "success, zero records" and is confirmed by running the sync's condition against the source.
X: A=Agent silently failing: a transport failure errors; it does not report success with zero rows consistently.
C=Storage limit: a dataset that could not accept data would fail the transaction with an error, not report a successful run with zero records.
D=Source mistaken: the source team has confirmed the rows; the engineer should verify, but the sync's own logic is the first suspect.
T: Successful runs with zero records mean the incremental condition or filter selects nothing; check it against the source.
V: Data Connection

@ PLTR-DE D1 T1.1 applied use-case
S: Sensor data arrives as thousands of small JSON files per hour landing in a cloud object storage bucket. Analysts need the data within about 15 minutes. Which ingestion fits?
A: A nightly file sync that copies the day's files in one transaction, since object storage sources are batch sources
B: A frequent file sync (every 10 minutes) that picks up new files and appends them, with downstream compaction
C: A streaming sync from the bucket, since the files arrive continuously and only streaming can meet the latency
D: A virtual table over the bucket so that analysts query the JSON files in place without ingestion
K: B
G: ## Near-real-time from object storage
The exam guide asks you to choose the pattern from source behaviour and freshness. Files landing in a bucket are a batch-style source; a frequent file sync meets a 15-minute need without streaming machinery.
## Design
- Sync every 10 minutes: new files only, append transactions.
- Downstream: parse JSON, then periodic compaction to prevent small-file accumulation.
- Freshness health check at 15 minutes.
Example: files landing at 10:03 are in the curated dataset by 10:14.
W: Frequent file sync with compaction: it meets the latency with the right pattern for file-based sources.
X: A=Nightly: analysts would wait up to a day for data that they need within 15 minutes; the freshness requirement is simply not met.
C=Streaming from a bucket: files in a bucket are not a message stream; a file sync at short intervals is the fit.
D=Virtual table over JSON files: not designed for querying raw sensor JSON at this rate, and it skips the parsing and governance.
T: File-based sources with tight freshness needs use frequent file syncs, not streaming, plus compaction.
V: Data Connection

@ PLTR-DE D1 T1.2 applied comparison
S: Which statement about change-data-capture (CDC) ingestion is correct?
A: CDC reads the source's change log to replicate inserts, updates and deletes, capturing changes without needing a timestamp column
B: CDC is the simplest sync pattern and should be used by default for every table because it requires no configuration on the source side
C: CDC can only capture inserts, so deletes and updates still require a periodic snapshot to be reflected downstream
D: CDC produces a current-state table directly, so no downstream transform is needed to apply the changes
K: A
G: ## What CDC provides
The exam guide asks you to distinguish snapshot, append, update and CDC patterns.
- CDC reads the database's transaction log, capturing inserts, updates and deletes, including rows without a reliable timestamp.
- It needs source-side enablement (log access) and is the most capable and most complex pattern.
- The raw output is a stream or dataset of change events; a transform applies them to produce current state.
Example: a table whose rows are updated in place and deleted without any timestamp column is replicated faithfully through CDC.
W: Log-based capture of inserts, updates and deletes: the defining property of CDC.
X: B=Simplest default: CDC is the most involved pattern and needs source configuration.
C=Inserts only: CDC captures inserts, updates and deletes alike from the log; capturing deletes is one of its main advantages over timestamp syncs.
D=Current state directly: change events must be applied by a transform.
T: CDC replicates all change types from the source log; a transform turns the events into current state.
V: Data Connection

@ PLTR-DE D1 T1.3 applied troubleshooting
S: A virtual table over an external warehouse has become slow for analysts, and the warehouse team reports high query costs from Foundry. What should be done?
A: Switch all analysts to querying the warehouse directly with their own credentials instead of through Foundry
B: Review the queries (pushdown, columns, joins), add filters, and materialize a curated subset in Foundry for common analyses if policy allows
C: Delete the virtual table, since virtual tables are only meant for one-off exploration and should never be used by multiple analysts at the same time
D: Increase the warehouse's compute size so that the queries complete faster regardless of their shape
K: B
G: ## Operating virtual tables
A virtual table pushes compute to the source; inefficient queries cost the source. The exam guide expects awareness of virtual tables' trade-offs.
## Response
- Inspect query patterns: unfiltered scans, wide selects, repeated joins.
- Improve: filters that push down, narrower column selection.
- If the same subset is analyzed repeatedly, materialize a curated extract in Foundry (with the warehouse team's agreement) so the warehouse is not hit for every query.
Example: a daily materialized extract of the last 90 days serves 90% of the analyses; warehouse cost drops sharply.
W: Query review plus selective materialization: it fixes the cost and speed while respecting the data's governance.
X: A=Direct warehouse access: loses Foundry's governance and does not reduce the query cost.
C=Delete: virtual tables are valid for shared use; the problem is query shape.
D=Bigger warehouse: it pays more to run the same inefficient queries faster, and the cost complaint from the warehouse team gets worse.
T: Manage virtual table cost by shaping queries and materializing frequently used subsets.
V: virtual tables

@ PLTR-DE D1 T1.4 advanced use-case
S: A data engineer is designing ingestion for a new source and wants to avoid the problems seen on earlier syncs: silent empty runs, stale data unnoticed, and agent outages. What should be built in from the start?
A: Nothing extra; the earlier problems were specific to those particular sources and their agents, and they are unlikely to recur with a new one
B: Status, freshness and size health checks, a minimum-row expectation where appropriate, agent health monitoring, alert routing and runbooks
C: A daily email to the whole team listing every sync's record counts so that someone can notice problems
D: A second redundant sync of the same source so that if one fails the other provides the data
K: B
G: ## Ingestion observability by design
The exam guide asks you to diagnose with execution history, agent health, credentials and Data Health; building these in from the start turns past incidents into standard practice.
## Checklist
- Status and freshness health checks with thresholds matching the cadence.
- Size or row-count checks (and a build-blocking minimum where correctness matters).
- Agent health monitoring with alerts.
- Alert routing to the owner; runbook per failure type.
Example: the new sync's first silent-empty run triggers the size check within minutes.
W: Checks, monitoring, routing and runbooks from day one: the earlier failure modes are detected automatically.
X: A=Nothing: silent empty runs, staleness and agent outages are generic ingestion failure modes; a new source is just as exposed to them.
C=Daily email: a long list of counts is noise that depends on someone reading it carefully every day; automated checks alert only when something is wrong.
D=Redundant sync: doubles cost and still does not detect staleness or empty runs.
T: Build ingestion monitoring (status, freshness, size, agent health, alerts, runbooks) into every new sync.
V: Data Health, Data Connection
