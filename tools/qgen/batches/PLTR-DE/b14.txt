@ PLTR-DE D5 T5.2 applied use-case
S: An orders dataset must satisfy: order id unique, customer id present, amount non-negative except for refunds, and order date not in the future. A build that violates any rule must not publish. Which expectations should be defined?
A: One expectation that the row count is above zero on every build, since any real data problem in the source will reduce the number of rows delivered
B: Separate build-blocking expectations: order id unique, customer id not null, amount rule conditional on order type, order date not in the future
C: Health checks for each rule, since health checks are easier to configure than expectations
D: A single expectation that the dataset "looks correct" evaluated by a reviewer each morning
K: B
G: ## Expressing a data contract as expectations
The exam guide asks you to use expectations to stop invalid transactions when correctness matters. Each contract rule maps to one expectation, which makes failures specific and the contract readable.
## Rules
- Uniqueness of `order_id`.
- Non-null `customer_id`.
- `amount >= 0 OR order_type = 'refund'`.
- `order_date <= current_date`.
Each fails the build on violation; the failure message names the rule, so the fix is targeted.
Example: a source bug ships 12 orders dated next year; the date expectation fails and the previous good transaction stays published.
W: One expectation per rule, build-blocking: the contract is enforced precisely and violations are named.
X: A=Row count only: none of the four rules affects the row count; invalid rows would pass.
C=Health checks instead: they alert after publishing; the requirement is to block.
D=Manual look: a reviewer's impression is not a check; nothing evaluates the rules during the build and nothing blocks publication.
T: Encode each contract rule as its own build-blocking expectation.
V: expectations

@ PLTR-DE D5 T5.3 applied troubleshooting
S: A dataset's freshness check has not fired, yet the data is stale: the last transaction is three days old. What is a likely cause?
A: Freshness checks cannot detect staleness longer than 24 hours
B: The check is misconfigured or not running (window too wide, wrong dataset or branch, failed execution, broken routing); verify and correct it
C: The dataset is too small for health checks to apply
D: Freshness checks only alert when a scheduled build fails with an error, not when no build runs at all, so a silently skipped schedule is invisible to them
K: B
G: ## Monitoring the monitors
A check that does not fire on a real problem is as dangerous as no check. The exam guide asks you to detect freshness problems and investigate failures; part of that is verifying that checks are configured correctly and are running.
## Causes to verify
- Window too wide (for example, seven days on a daily dataset).
- Pointed at the wrong resource (a different dataset, a branch, a view).
- The check's own schedule or execution failed.
- Alert routing broken (fired, but nobody received it).
Example: the check was created on the master branch of a dataset that is now built on a release branch; repointing it restores alerts.
W: Misconfigured or non-running check: a three-day gap with no alert on a daily dataset means the check's window, target, execution or routing is wrong, each verifiable.
X: A=24-hour limit: freshness checks can use any threshold; there is no such limit.
C=Too small: dataset size does not disable health checks; freshness is about transaction timing, which exists for datasets of any size.
D=Only on failed builds: freshness checks exist precisely to detect that no build ran.
T: When a health check stays silent on a real problem, audit the check's window, target, execution and routing.
V: Data Health

@ PLTR-DE D5 T5.1 applied tradeoff
S: A pipeline publishes a dataset used by both an Ontology object type (where correctness is critical) and an exploratory analytics team (who tolerate imperfections). A new rule would block builds on any null in a secondary column. What is the right approach?
A: Block on the rule for everyone, since stricter is always safer
B: Decide by consequence: block only if the null breaks the critical consumer; otherwise monitor it and handle nulls in the Ontology's backing transform
C: Remove all expectations so the analytics team never waits for data
D: Create two completely separate pipelines from the same source, each with its own rules, one for the Ontology and one for the analytics team
K: B
G: ## Proportional quality controls
The exam guide's self-check asks whether a requirement needs a blocking expectation, a health alert, or both. Over-blocking delays all consumers for problems that matter to none; under-blocking lets critical consumers receive bad data.
## Approach
- Ask: does a null in this column break the object type (key, required property)? If yes, block.
- If it only degrades analytics, monitor (health check on null rate) and handle in the Ontology backing transform (filter or flag).
- Document the contract so both consumers know what is guaranteed.
Example: `secondary_note` nulls do not affect the object type; a null-rate health check is added and builds keep flowing.
W: Blocking only where the null breaks a critical consumer, monitoring otherwise: proportional to consequence, with both consumers served.
X: A=Block everything: the analytics team and the object type wait for a problem that may not matter.
C=Remove expectations: the Ontology object type then receives whatever the source sends, including nulls in required properties and duplicate keys.
D=Two pipelines: duplicated logic and divergent data for one source; the layered approach achieves the same without duplication.
T: Match blocking to consequence; monitor what does not break critical consumers.
V: expectations, Data Health

@ PLTR-DE D5 T5.3 applied use-case
S: A team wants to detect when the distinct count of `country` in a dataset suddenly drops (for example from 40 to 3), which has happened once due to a broken join. Which health check should they configure?
A: A freshness check, since a broken join delays the build
B: A content check on the distinct count of `country` with an alert when it falls below a threshold or deviates from history
C: A build-status check, since a broken join fails the build
D: A schema check on the dataset, since a broken join usually changes the column types or drops the country column from the output entirely
K: B
G: ## Content checks
A build can succeed with a logically broken result; the exam guide warns that a successful run can still produce incorrect data. Content checks look at the values: distinct counts, null rates, value distributions.
## Configuration
- Metric: distinct count of `country`.
- Rule: below 30, or a drop of more than 50% from the previous build.
- Alert: owner, with the metric history.
Example: the next time a join key mismatch collapses the data to three countries, the alert fires minutes after the build.
W: Distinct-count content check with threshold or deviation alert: it watches the exact symptom of the earlier failure.
X: A=Freshness: the broken join produced fresh data; freshness would be fine.
C=Build status: the build succeeded with a logically wrong join, so a status check saw a green build and nothing else.
D=Schema: the column type was unchanged; only the values collapsed.
T: Guard against logical failures with content checks on value statistics.
V: Data Health

@ PLTR-DE D5 T5.2 applied troubleshooting
S: An expectation on a large dataset adds 20 minutes to each build because it checks uniqueness over 3 billion rows. The team wants to keep the protection but reduce the cost. What are reasonable options?
A: Remove the expectation, since 20 minutes is too expensive for a check
B: Keep the guarantee but make it cheaper: incremental slice check plus an anti-join on existing keys, a less frequent full check, or an upstream guarantee
C: Convert it to a health check that runs after publishing, accepting that duplicate keys may reach the Ontology and its consumers for a while before anyone reacts
D: Check uniqueness on a 1% sample, which is representative
K: B
G: ## Cost-aware quality
Expectations run inside the build and cost compute. The exam guide asks for right-sized compute and for expectations where correctness matters. The goal is to keep the guarantee while paying less.
## Options
- Incremental check: the new rows must be unique among themselves and absent from the existing key set (an anti-join), far cheaper than a full distinct count.
- Tiered schedule: lightweight check every build; full check weekly.
- Upstream guarantee: if the key is generated deterministically upstream with its own expectation, the downstream check can be lighter.
Example: the incremental anti-join check takes 40 seconds; the full check runs on Sundays.
W: Cheaper enforcement strategies that keep the guarantee: the protection remains and the cost drops.
X: A=Remove: duplicates would reach the Ontology, which the expectation existed to prevent.
C=Health check after publishing: this changes "prevent" to "detect"; duplicates reach consumers.
D=1% sample: uniqueness cannot be proven on a sample; a duplicate pair is unlikely to both be sampled.
T: Keep critical expectations and make them cheaper with incremental checks, tiered schedules or upstream guarantees.
V: expectations, incremental transforms

@ PLTR-DE D5 T5.3 applied use-case
S: Alerts from health checks across 200 datasets go to one shared channel, and the team is overwhelmed. What should be changed?
A: Turn off the alerts, since nobody can read them anyway
B: Route by ownership and severity: critical datasets page on-call, others go to the owning team, with deduplication and context
C: Send all alerts by email instead of chat
D: Keep the single shared channel but ask the whole team to check it more often and to acknowledge each alert with a reaction so nothing is missed
K: B
G: ## Alert routing and prioritization
The exam guide asks you to design alerts so failures are investigated. An alert nobody can act on is noise. Routing turns a firehose into actionable signals.
## Design
- Ownership: each dataset has an owner team; alerts go to them.
- Severity: critical consumers (Ontology-backing, SLAs) page on-call; exploratory datasets post to a low-priority channel.
- Deduplication: one alert per incident, not one per build.
- Context: dataset, check, metric, link to lineage and runbook.
Example: 200 datasets produce 10 well-routed alerts a day instead of 300 messages in one channel.
W: Ownership- and severity-based routing with deduplication and context: alerts become actionable and the overwhelm disappears.
X: A=Turn off: real failures then go unnoticed entirely; the problem is routing and volume, not the existence of alerts.
C=Email instead: the same 300 messages a day land in a different inbox; changing the channel does not reduce or prioritize them.
D=Check more often: the volume and lack of prioritization are the problem; more attention to an unfiltered feed does not make alerts actionable.
T: Route alerts by owner and severity, deduplicate, and include context.
V: Data Health

@ PLTR-DE D5 T5.1 applied comparison
S: Which statement about expectations and incremental transforms is correct?
A: Expectations cannot be used on incremental transforms at all, since every check would need to scan the entire dataset history on every single run
B: Expectations apply to incremental transforms; slice-level checks run on new rows, while global checks like uniqueness need a full or incremental-aware strategy
C: Expectations on incremental transforms only run during fallback snapshot builds
D: Expectations automatically convert an incremental transform into a full batch transform
K: B
G: ## Expectations and processing mode
Expectations are independent of processing mode; what differs is the scope they evaluate. The exam guide's incremental guidance and its expectations guidance combine here.
- Slice-level checks (nulls in new rows, value ranges, schema): cheap on the incremental output.
- Global checks (uniqueness across all rows, referential integrity): need the full dataset or an incremental-aware design (anti-join against existing keys).
Example: an incremental transform checks nulls on the new slice every run and uniqueness via an anti-join; a weekly full check validates the whole dataset.
W: Expectations apply to incremental transforms, with scope chosen per check: the accurate description of how the two work together.
X: A=Cannot be used: they can; the design of global checks just needs care.
C=Only during fallback: expectations run on every build, not only on snapshot runs.
D=Convert to batch: an expectation does not change the transform's processing mode.
T: Use expectations with incremental transforms; choose slice-level or global strategies per check.
V: expectations, incremental transforms

@ PLTR-DE D5 T5.3 advanced troubleshooting
S: A health check on a dataset's row count has been failing for a week because the dataset legitimately shrank after a business change. The team has been ignoring it. What should happen?
A: Nothing for now; the check's anomaly baseline will eventually adjust itself to the new dataset size as more builds accumulate at the smaller volume
B: Re-baseline the check to the new expected size and record the business change, because an ignored failing check hides any future real problem
C: Delete the check permanently
D: Double the dataset artificially so the check passes
K: B
G: ## Maintaining checks over time
Checks encode expectations about data that change with the business. The exam guide asks you to keep monitoring meaningful and to investigate failures; a permanently red check is equivalent to no check.
## Action
- Confirm the shrink is legitimate (the business change) and not a defect.
- Re-baseline the check: new expected range or anomaly baseline.
- Note the change in the dataset's documentation.
- Review other checks that may have assumed the old size.
Example: the check's floor moves from 2 million to 1.2 million rows; it turns green and will fire again if the dataset halves unexpectedly.
W: Re-baseline and document: the check regains meaning and the team stops being trained to ignore red.
X: A=Self-adjust: thresholds do not change themselves; the check stays red.
C=Delete: the dataset loses size monitoring entirely, so the next unexpected shrink, a real defect, goes undetected.
D=Pad the data: inventing rows to satisfy a monitor corrupts the dataset for every consumer; checks serve the data, not the other way round.
T: Re-baseline checks after legitimate changes; never let a check stay red.
V: Data Health
