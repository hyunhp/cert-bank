# PLTR-DE batch 08: Domain 7 (Ontology Data Modeling), 8 questions

@ PLTR-DE D7 T7.1 applied use-case
S: A curated dataset has one row per order line with columns for the order, the customer, the product and the quantity. The business wants to ask questions such as "which customers bought this product" and "what did this order contain". How should this be modeled in the Ontology?
A: One object type OrderLine with all the columns as properties, since the dataset already has the shape that the business questions need
B: Object types Order, Customer, Product and OrderLine, with links from OrderLine to Order and Product and from Order to Customer
C: Object types Customer and Product only, with the quantity stored as a property on a link between them
D: One object type Customer with a list property containing every product the customer ever bought
K: B
G: ## Modeling entities and relationships
The exam guide asks you to model real-world entities, properties, links, and to avoid dashboard-shaped or overly broad object types. The row-per-order-line dataset is a fact table; the business questions are about entities (customers, products, orders) and their relationships.
## A normalized model
- **Customer**, **Product**, **Order** are entities with stable keys and their own properties.
- **OrderLine** captures the many-to-many between orders and products with quantity.
- **Links**: OrderLine → Order (many-to-one), OrderLine → Product (many-to-one), Order → Customer (many-to-one).
Each object type is backed by a curated dataset with one row per entity. Questions traverse links: Product → OrderLines → Orders → Customers.
Example: "which customers bought product P" is Product P → its OrderLines → their Orders → Customers, with no duplicated customer data.
W: Separate entity object types with links through OrderLine: it models the real relationships, supports both questions by traversal, and avoids duplicating customer and product data on every line.
X: A=One OrderLine type: customer and product attributes repeat on every line; there is no Customer object to link to, and "what did this order contain" has no Order object.
C=Customer and Product with a link: orders disappear from the model, and a single link cannot represent repeated purchases over time with quantities.
D=List on Customer: this is a denormalized blob; products cannot be queried as entities, and orders are lost.
T: Model entities as object types and relationships as link types; use an association object (OrderLine) for many-to-many with attributes.
V: Ontology Manager

@ PLTR-DE D7 T7.2 applied use-case
S: An Employee object type is being created from an HR dataset. The candidates for primary key are the email address, the employee number assigned by HR, and the row's position in the dataset. Which should be the primary key?
A: The email address, since it is human-readable and unique in the company directory
B: The employee number, since it is assigned once, never changes, and is unique for each person
C: The row position, since it is guaranteed unique within any dataset and requires no business knowledge
D: A new UUID generated on each build, since UUIDs are globally unique by construction
K: B
G: ## Stable primary keys
The exam guide asks you to select stable primary keys. The key identifies the entity across rebuilds; edits, links and application references attach to it. A good key is unique, never null and never changes for the same entity.
## Evaluating candidates
- Employee number: assigned by HR once, immutable, unique: ideal.
- Email: changes on name change, department move or rehire; reused addresses collide.
- Row position: changes with any reorder, insert or delete; it is not a property of the person.
- Per-build UUID: new on every build, so every object is recreated and all edits and links detach.
Example: an employee marries and changes email; with the employee number as key, her object, its links and history are untouched.
W: The employee number: immutable and unique by design, so the object's identity survives data changes and rebuilds.
X: A=Email: it changes and can be reused, so the object's identity would change and edits would detach or collide.
C=Row position: it is positional, not an attribute of the employee; any reorder re-keys every object.
D=Per-build UUID: regenerating keys on every build destroys object identity each time.
T: Choose primary keys that are unique and immutable for the entity; never positional or regenerated values.
V: Ontology Manager

@ PLTR-DE D7 T7.2 applied troubleshooting
S: A link type between Shipment and Carrier is configured as one-to-one. Operations report that some shipments show no carrier even though the dataset has carrier assignments, and that a carrier's shipment list only ever shows one shipment. What is wrong?
A: The dataset's carrier column has nulls that must be filled before the link can be created
B: The cardinality is wrong: a carrier handles many shipments, so the link must be many-to-one from Shipment to Carrier
C: The link type is backed by the wrong dataset and needs to be re-pointed to the shipments dataset
D: Link types cannot connect object types that are backed by different datasets, so a join dataset combining shipments and carriers must be created first
K: B
G: ## Link cardinality
The exam guide asks you to select appropriate link cardinality. Cardinality states how many objects on each side can be linked: one-to-one, one-to-many (many-to-one), many-to-many. It must match the real relationship, and the data must support it.
## The symptom
- A one-to-one link allows one shipment per carrier; when several shipments reference the same carrier, only one link is valid and the others are dropped or conflict.
- That matches "a carrier shows only one shipment" and "some shipments show no carrier".
Fix: many-to-one from Shipment to Carrier (each shipment has one carrier; a carrier has many shipments), backed by the carrier id on the shipment.
Example: Carrier C-12 handles 400 shipments; with many-to-one, its shipment list shows all 400 and every shipment shows its carrier.
W: Wrong cardinality: the real relationship is many shipments to one carrier, and a one-to-one link cannot express it, which produces exactly the missing and single-link symptoms.
X: A=Nulls in the column: nulls would leave only those shipments without a carrier; they would not limit a carrier to one shipment.
C=Wrong backing dataset: a mis-pointed link would fail more broadly or show no links at all, not a pattern of one per carrier.
D=Different datasets: link types routinely connect object types from different datasets via a foreign key.
T: Set link cardinality to match the real relationship; one-to-one cannot represent one-to-many data.
V: Ontology Manager

@ PLTR-DE D7 T7.3 applied tradeoff
S: A dashboard team asks for an object type "SalesSummary" with properties such as total revenue this month, top product, and number of open tickets per region, so that their dashboard can read everything from one object. What should the data engineer recommend?
A: Create SalesSummary as requested, since object types should be shaped around how the consuming applications need to display the data
B: Model the entities (Sale, Product, Ticket, Region) and let the dashboard aggregate over links or a derived aggregate dataset
C: Create SalesSummary but rename it to make it clear that it is for the dashboard only
D: Create one SalesSummary object per region per month so that the dashboard can filter it by both dimensions
K: B
G: ## Avoiding dashboard-shaped object types
The exam guide explicitly warns against dashboard-shaped, duplicated or overly broad object types and asks you to apply normalization principles. A "SalesSummary" with unrelated aggregates is not an entity; it is a report row. It serves one consumer, goes stale as soon as the real objects change, and is useless to applications and AI workflows that reason about real things.
## What to do instead
- Model the entities; aggregates are computed by queries over links or by functions.
- If performance requires precomputed aggregates, produce an aggregate dataset with a clear grain (region × month) and expose it as its own object type whose identity is that grain, documented as derived.
- The dashboard then reads entities or the derived aggregate, both with a defined contract.
Example: revenue per region per month comes from a derived "RegionMonthRevenue" object with key (region, month), while Sales remain the source of truth.
W: Model entities and derive aggregates deliberately: the Ontology stays a semantic layer other consumers can trust, and the dashboard still gets efficient, well-defined data.
X: A=Build the report object: a one-consumer object with mixed aggregates is the anti-pattern the guide names; it pollutes the Ontology.
C=Rename only: a warning label does not make a report row an entity.
D=Per region per month: this is closer to a proper aggregate grain, but as described it still mixes unrelated measures (top product, open tickets) into one object with no entity meaning.
T: The Ontology models entities, not dashboards; derive aggregates with a defined grain if needed.
V: Ontology Manager

@ PLTR-DE D7 T7.4 applied use-case
S: A live object type used by three production applications needs a new property and a renamed link type. The team must not disrupt the applications while developing the change. How should this be done?
A: Make the changes directly on the live object type during off-hours, since Ontology edits apply instantly
B: Use Global Branching to develop the changes on a branch, validate them with the applications there, and merge once they pass
C: Create a copy of the object type with the new structure, migrate the applications to the copy one by one, and delete the original
D: Freeze the applications for a day while the changes are made and tested on the live object type
K: B
G: ## Evolving live Ontology resources
The exam guide names Global Branching as the way to evolve live Ontology resources safely. Just as pipelines are developed on branches, Ontology changes (new properties, link changes, new object types, together with their backing datasets) can be made on a branch and tested with applications before merging into the live Ontology.
## The workflow
- Create a branch covering the datasets and Ontology resources involved.
- Add the property and rename the link on the branch; applications pointed at the branch validate the change.
- Merge; production applications see a tested change.
Example: a Workshop module tested on the branch shows the new property; the renamed link breaks one filter, which is fixed before the merge.
W: Global Branching: it provides exactly the isolated, testable development of Ontology changes that the requirement demands.
X: A=Edit live: a mistaken rename breaks the applications immediately, with executives and users as the testers.
C=Copy and migrate: duplicating object types fragments the Ontology and forces every application through a migration for a routine change.
D=Freeze applications: downtime is a cost the branch avoids entirely.
T: Use Global Branching to develop and validate Ontology changes before they reach live applications.
V: Ontology Manager, Global Branching

@ PLTR-DE D7 T7.5 applied tradeoff
S: Applications need each Customer's "lifetime value" (sum of all order totals). It is needed by dashboards, filters and an AI workflow, and it only needs to be refreshed daily. Where should it be computed?
A: South of the Ontology, in the pipeline that builds the Customer dataset, exposed as a property
B: North of the Ontology, in a function that sums orders over links each time an application displays a customer
C: In every application separately, so each team controls its own definition
D: In the AI workflow, which can compute it on demand and share the result with the dashboards
K: A
G: ## North or south of the Ontology
The exam guide asks you to decide whether computation belongs north or south of the Ontology. Lifetime value is deterministic, needed by many consumers (dashboards, filters, AI), and daily freshness is enough: that is the profile of pipeline computation (south) materialized as a property.
## Why
- Filters and sorting need a property; a value computed at display time cannot be filtered on across all customers efficiently.
- One definition in one place; every consumer gets the same number.
- Computed once a day, not on every view.
Interactive, context-dependent reasoning (a question only the current user asked) is what belongs north.
Example: `lifetime_value` is a column in `customers_curated`, exposed as a property; the dashboard sorts customers by it in one query.
W: South, as a materialized property: deterministic, widely consumed, daily freshness, which is the case for pipeline computation exposed on the object.
X: B=Function at display time: recomputing sums per view is slow, cannot support filtering across customers, and repeats work.
C=Per application: multiple definitions drift and disagree; the Ontology exists to avoid that.
D=AI workflow: a deterministic aggregate is not an AI task, and the workflow is not a shared computation layer for dashboards.
T: Deterministic, widely used, periodically refreshed values are computed south and materialized as properties.
V: Ontology Manager, Pipeline Builder

@ PLTR-DE D7 T7.1 applied use-case
S: Several object types (Truck, Forklift, Crane) share properties like asset id, location and maintenance status, and applications want to show "all assets needing maintenance" regardless of type. Which Ontology feature fits?
A: Merge the three object types into one Asset type with a type column, dropping the type-specific properties
B: Define an Asset interface with shared properties implemented by all three types, so applications query the interface
C: Create a fourth object type AssetSummary that copies the shared properties from the three types each night
D: Add links from each type to a central Asset object that holds the shared properties, keeping them in two places that the pipeline updates nightly
K: B
G: ## Interfaces and shared properties
The exam guide lists interfaces and shared properties among the modeling constructs. An **interface** defines a set of properties (and possibly links) that several object types implement; applications and functions can query the interface and receive objects of all implementing types.
## Why it fits
- Each type keeps its own specific properties (crane reach, forklift capacity).
- Shared properties (asset id, location, maintenance status) are declared once on the interface.
- "All assets needing maintenance" becomes one query over the interface.
Example: a Workshop list bound to the Asset interface shows trucks, forklifts and cranes together, filtered on maintenance status.
W: An interface with shared properties: it gives the cross-type query the applications want while preserving each type's own model.
X: A=Merge into one type: type-specific properties are lost or become sparse columns, and the entities are genuinely different.
C=Nightly summary copy: duplicated data that goes stale and requires a pipeline just to approximate what an interface gives directly.
D=Central Asset object with duplicates: properties stored twice drift apart; the model should declare sharing, not copy values.
T: Use interfaces and shared properties to query across related object types without merging or duplicating them.
V: Ontology Manager, interfaces

@ PLTR-DE D7 T7.4 advanced troubleshooting
S: A product team wants to change the primary key of a live Order object type from an internal row id to the business order number. Users have made edits and created links on the existing objects. What must the data engineer plan for?
A: Nothing special; changing the primary key in the object type configuration remaps all the existing edits and links to the new key automatically
B: A migration: map old keys to new keys, migrate existing edits and links, update consumers that reference the old key, validated on a branch
C: Deleting all existing edits and links, since they belong to the old key and cannot be preserved in any way
D: Keeping both keys as primary keys so that old and new references continue to work side by side
K: B
G: ## Changing identity is a migration
A primary key change means that, from the Ontology's point of view, the old objects disappear and new ones appear. The exam guide asks you to plan migrations when requirements change and to assess existing consumers before changing semantics.
## Planning the migration
- Build a mapping from old key to new key from the backing data.
- Migrate user edits (edited properties) and links to the new objects using that mapping.
- Update applications, functions and automations that reference order ids.
- Do it on a branch with Global Branching; validate with the applications; release with a rollback plan.
Example: 12,000 orders with user edits are mapped by (old_id → order_number); after the migration, the comments made by users appear on the correctly keyed objects.
W: A planned, validated migration of edits, links and consumers: a key change re-identifies objects, so the data attached to them must be carried over deliberately.
X: A=Automatic remap: object identity is the key; nothing can know that old object 4411 is new object ORD-2026-9001 without an explicit mapping.
C=Delete everything: user edits and links are business data; discarding them is unacceptable when a mapping is possible.
D=Two primary keys: an object type has one primary key; references cannot be kept valid by declaring both.
T: Changing a primary key is a migration of identity; map and migrate edits, links and consumers on a branch.
V: Ontology Manager, Global Branching
