# PLTR-DE batch 27: Domain 2 round 4 (Data Transformation and Pipeline Authoring), 8 questions

@ PLTR-DE D2 T2.2 applied use-case
S: A dataset has a column of free-text addresses. The business wants structured city, postal code and country columns. Which transformation approach is appropriate?
A: A single regular expression applied in an expression node, since addresses worldwide follow one consistent pattern that a pattern can capture
B: Reference-backed address parsing with an LLM step for the residual, postal codes validated against reference lists, and flags for unparseable rows
C: Splitting the string on commas and assuming the parts are always city, postal code and country in that order
D: Asking each consuming team to parse the addresses themselves in their own pipelines
K: B
G: ## Structuring messy text
The exam guide lists expressions and enrichment among transformation operations and pairs AI with deterministic validation. Address parsing is a known problem with reference data and libraries.
## Design
- Deterministic parser plus postal-code and country reference lists for the bulk.
- Residual: LLM with structured output, validated against the same references.
- Flags for rows that cannot be parsed; never silently guess.
Example: 94% of addresses parse deterministically; 4% via the LLM step; 2% flagged for review.
W: Reference-backed parsing with validation and a controlled AI residual: structured columns with explicit handling of uncertainty.
X: A=One regex: address formats vary by country and source; a single pattern fails on most of them.
C=Split on commas: order and separators differ; the assumption is wrong for a large share of rows.
D=Per consumer: duplicated, inconsistent parsing in every pipeline.
T: Parse messy text with reference-backed logic, validate, and flag what cannot be parsed.
V: Pipeline Builder, Code Repositories

@ PLTR-DE D2 T2.1 applied tradeoff
S: A team maintains the same cleaning logic in a Pipeline Builder pipeline and in a code transform for different projects, and the two have drifted apart. What should be done?
A: Keep both implementations and add a comment in each pointing to the other, so that future changes are remembered to be made in both places
B: Consolidate: implement the cleaning once as a shared stage (a published dataset or a code library) and have both projects consume it
C: Delete the code transform and tell the second project to copy the Pipeline Builder pipeline manually into their own project whenever it changes
D: Accept the drift, since each project's needs are slightly different anyway
K: B
G: ## Single source of truth for logic
The exam guide asks for maintainable transformations and clear contracts. Duplicated logic drifts; the fix is one implementation consumed by both.
## Options
- Shared curated dataset: the cleaning stage runs once and both projects read its output.
- Shared library: a code package used by multiple transforms.
- Branch-validate that consumers get identical results after consolidation.
Example: `addresses_clean` becomes one dataset referenced by both projects; a cleaning rule change applies everywhere at once.
W: Consolidation into a shared stage or library: the drift ends because there is nothing left to drift.
X: A=Comments pointing both ways: still two copies to keep in sync by hand.
C=Manual copying: the drift returns the first time someone forgets.
D=Accept: inconsistent cleaning produces inconsistent results across the business.
T: Implement shared logic once as a shared dataset or library and consume it everywhere.
V: Pipeline Builder, Code Repositories

@ PLTR-DE D2 T2.3 applied troubleshooting
S: A Spark transform works on a sample but fails with out-of-memory on the full data during a `collect()` used to build a Python dictionary for lookups. What is the right change?
A: Increase the driver memory in the transform's configuration until the collected lookup data fits, and raise it again as the data grows
B: Replace the collect-and-dictionary pattern with a distributed join (or a broadcast join if the lookup side is small), keeping data in the engine
C: Reduce the full dataset to a sample permanently so the collect succeeds
D: Run the transform on a lightweight single-node engine instead, which has no separate driver limit to run out of during the collect
K: B
G: ## Scale-unsafe patterns
Collecting a large dataset to the driver is a classic unsupported pattern. The exam guide asks you to recognize code-level inefficiency and scale-unsafe code.
## Fix
- Express the lookup as a join between dataframes.
- If the lookup table is small (a few MB), a broadcast join is efficient.
- Validate output equivalence on a branch.
Example: a 20 GB lookup joined distributedly completes in minutes; the collect that failed is gone.
W: Distributed (or broadcast) join: the data stays in the engine and the pattern scales.
X: A=More driver memory: a temporary ceiling that the data will exceed again.
C=Permanent sample: the lookup and therefore the output become incomplete; rows whose key fell outside the sample are silently wrong.
D=Lightweight engine: single-node memory limits are even tighter than the driver's.
T: Replace collect-to-driver lookups with joins; keep large data distributed.
V: Code Repositories, Spark

@ PLTR-DE D2 T2.4 applied use-case
S: A transform computes a financial measure whose definition is agreed with finance. How should the definition be protected against accidental change?
A: A verbal agreement with the engineer who wrote the transform that they will not change the measure's logic without asking finance first
B: Unit tests encoding the definition, an expectation reconciling the output to a control figure, and required review on changes to the transform
C: A lock on the repository that prevents anyone from ever editing the transform again, so that the agreed definition cannot drift
D: A quarterly check by the finance team of whether the published number still looks right compared with their own ledger
K: B
G: ## Protecting agreed definitions
The exam guide asks for tested, reviewed transforms and expectations on correctness. A definition is protected when a change that alters it fails tests, fails expectations, or is caught in review.
## Controls
- Unit tests: representative inputs with finance-approved expected outputs.
- Expectation: the output total reconciles to an independent control figure within tolerance.
- Review: changes to this transform require a finance-aware reviewer.
Example: a refactor that mishandles refunds fails the unit test before merge.
W: Tests, reconciliation expectation and review: accidental definition changes are caught at three points.
X: A=Verbal agreement: not a control; engineers change and forget.
C=Lock forever: definitions legitimately evolve; the control is review, not prohibition.
D=Quarterly look: a definition broken in January would feed wrong figures into reports until the April check.
T: Encode agreed definitions in tests and reconciliation expectations, and require review.
V: Code Repositories, expectations

@ PLTR-DE D2 T2.2 applied use-case
S: Two datasets must be joined on customer name because no shared identifier exists, and names have inconsistent casing, punctuation and spacing. What should the transform do?
A: Join on the raw names as they appear in each dataset and accept that rows whose names do not match exactly are lost from the output
B: Normalize both sides into a join key (case, punctuation, whitespace, abbreviations), join, measure the match rate, and route the unmatched to review
C: Use a fuzzy match on the raw names with no similarity threshold, so that every row in the first dataset finds some partner in the second
D: Ask both source teams to add a shared customer identifier to their systems before any join is attempted in the pipeline
K: B
G: ## Joining without a shared key
The exam guide asks for correct joins with attention to cardinality and meaning. A name join needs a normalized key, measured matching and explicit handling of the residual.
## Design
- Normalization function (tested) applied to both sides.
- Deterministic join on the normalized key; match rate as a metric.
- Residual: fuzzy matching with a threshold and review; never silent.
Example: match rate rises from 61% to 93% after normalization; the remaining 7% are reviewed.
W: Normalized key, measured join, controlled residual: the join is as correct as the data allows, and the gaps are visible.
X: A=Raw names: "ACME Corp." and "acme corp" do not match; most rows fail silently and the output is badly incomplete.
C=Fuzzy without threshold: forces wrong matches; a "match" to anything is worthless.
D=Wait for identifiers: often impossible; the pipeline must work with what exists while the identifier is pursued.
T: Join on normalized keys, measure the match rate, and handle unmatched rows explicitly.
V: Pipeline Builder, Code Repositories

@ PLTR-DE D2 T2.3 applied comparison
S: Which workload is best served by a lightweight (single-node) transform rather than Spark?
A: A nightly join of two tables of about 500 GB each on a customer key, producing a wide output consumed by several teams
B: A daily transform that reads a 30 MB configuration file, applies validation rules and writes a small lookup table for other pipelines
C: A streaming aggregation over millions of sensor events per hour, producing per-device windows with sub-minute latency
D: A one-off backfill over five years of clickstream data to recompute session metrics with a corrected definition
K: B
G: ## The lightweight case
The exam guide includes lightweight engines for suitable smaller workloads among engine choices. Small inputs where distributed startup dominates are the fit.
- 30 MB with validation rules: seconds on one node; Spark would spend minutes starting.
- 500 GB joins, streaming at scale, multi-year backfills: distributed workloads.
Example: the lookup table builds in 15 seconds on a lightweight engine versus 4 minutes on Spark.
W: The small daily configuration transform: tiny input, simple logic, startup-dominated: the lightweight case.
X: A=500 GB join: two tables of that size cannot be held or joined on a single node; this is a distributed workload.
C=Streaming millions per hour: a streaming engine, not a single node.
D=Five-year backfill: years of clickstream is large-scale batch that needs partitioned, distributed processing.
T: Lightweight engines for small inputs; distributed engines for scale.
V: Code Repositories

@ PLTR-DE D2 T2.4 applied troubleshooting
S: A transform's output is correct, but reviewers cannot tell why certain rows were filtered out because the filtering logic is spread across several nested expressions. What refactoring helps?
A: Removing the filters entirely so that all rows pass through to the output and reviewers have nothing left to question about exclusions
B: Restructuring the logic into named steps, or a reason column recording why each row was excluded, so exclusions are explicit and testable
C: Adding a long comment at the end of the transform explaining the filters in prose
D: Moving all the filters into a single very long expression at the end of the transform so that they are at least gathered in one place
K: B
G: ## Explainable transformations
The exam guide asks for maintainable, reviewable transformations. Reviewers must be able to see which rule applied to which row.
## Refactoring
- Named intermediate steps: `valid_rows`, `excluded_missing_key`, `excluded_out_of_range`.
- Or an `exclusion_reason` column computed before the final filter, with counts per reason monitored.
- Unit tests per rule.
Example: the review shows 1,200 rows excluded for missing keys and 40 for out-of-range dates, each traceable.
W: Named steps or a reason column: exclusions become explicit, countable and testable.
X: A=Remove filters: the filters exist for a reason; removing them makes the output wrong rather than making it explainable.
C=Prose comment: documentation that drifts from the code and still cannot show per-row reasons.
D=One giant expression: gathering the logic in one place does not make it readable; a single long expression is harder to review, not easier.
T: Make exclusion logic explicit with named steps or reason columns.
V: Pipeline Builder, Code Repositories

@ PLTR-DE D2 T2.1 advanced tradeoff
S: A team wants to migrate a critical Pipeline Builder pipeline to code to add unit tests and custom logic. How should the migration be done safely?
A: Rewrite it in code directly on the main branch over a weekend and switch all consumers to the new implementation on Monday morning
B: Rebuild it in code on a branch, compare both implementations' outputs on the same inputs, add tests, then switch consumers with rollback
C: Rewrite it in code but skip the output comparison with the original, since the code version has unit tests and those are sufficient
D: Keep both the Pipeline Builder and the code implementation running forever and let each consuming team choose which output to use
K: B
G: ## Migrating implementations
The exam guide asks you to refactor with validation and manage branches and releases. An implementation change must prove equivalence before it replaces the original.
## Process
- Branch: the code implementation alongside the existing pipeline.
- Equivalence: identical inputs; compare counts, keys, values; investigate differences.
- Tests added; expectations carried over.
- Cutover with rollback; retire the original later.
Example: the comparison finds a rounding difference in one column; it is resolved before cutover and consumers never notice the migration.
W: Branch rebuild, equivalence comparison, tested cutover with rollback: the migration is safe for consumers.
X: A=Weekend rewrite on main: untested replacement of a critical pipeline.
C=Skip comparison: tests check the new code's intent, not equivalence with the old behaviour consumers rely on.
D=Both forever: two implementations of one critical pipeline drift apart and consumers end up with different numbers for the same thing.
T: Migrate implementations on a branch with output equivalence checks before cutting consumers over.
V: Code Repositories, Pipeline Builder, branches
