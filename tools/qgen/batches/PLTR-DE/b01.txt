# PLTR-DE batch 01: pilot, one question per domain (source: Data Engineer Associate exam guide, checked 2026-10-14)

@ PLTR-DE D1 T1.4 applied troubleshooting
S: A dataset synced every night from an on-premises database through a Data Connection agent has not received new data for two days. The downstream transforms build successfully on schedule, but their outputs are stale. What should the data engineer check first?
A: The sync's execution history together with the agent's health and the source credentials, to find whether the ingestion step itself is failing
B: The Spark details of the downstream transforms, since slow or skewed jobs are the usual reason why pipeline outputs stop reflecting new data
C: The permissions of the analysts who use the outputs, since stale results usually mean that consumers can no longer read the newest transactions
D: The schedule of the downstream transforms, then force a full rebuild of every downstream dataset so that all outputs are refreshed together
K: A
G: ## Following the data to the first bad stage
The exam guide's troubleshooting playbook says to state the symptom precisely, then find the **first bad stage** before changing anything. Here the symptom is stale output, and the downstream builds are succeeding: a successful build on unchanged input simply reproduces yesterday's result.
## Where ingestion can break
A sync from an on-premises system typically depends on:
- an **agent** installed inside the customer network, which must be running and able to reach both the source and Foundry;
- **credentials** for the source, which can expire or be rotated;
- the source itself (schema, availability).
The sync's execution history shows whether recent runs failed, were skipped or wrote empty transactions, and agent health shows whether the agent is online. Data Health checks on the synced dataset can alert on this sooner next time.
Example: a database password rotated on Monday makes every sync fail from that night on while downstream jobs keep "succeeding".
W: Sync history, agent health and credentials: the outputs are stale while downstream builds succeed, which points upstream to ingestion. These three pieces of evidence show whether the sync is failing and why.
X: B=Spark details downstream: those jobs succeed on schedule. Performance details explain slow or failing builds, not builds that finish correctly on unchanged input.
C=Consumer permissions: a permission problem shows up as access errors for those users, not as data that stopped changing two days ago for everyone.
D=Force a full rebuild: rebuilding downstream on the same stale input produces the same stale output, uses compute and hides the real failure.
T: Stale output with successful builds means look upstream: check the sync, the agent and the credentials before touching transforms.
V: Data Connection, Data Health

@ PLTR-DE D2 T2.3 applied tradeoff
S: A transform reads two reference files of a few megabytes each, joins them and writes a small lookup table every hour. Its Spark job spends most of its run time starting up, and the team wants lower cost and faster runs without changing the output. Which change fits best?
A: Raise the number of Spark executors and the driver memory, since more resources let the job finish its startup phase more quickly on every run
B: Convert the transform to a streaming pipeline, so that it stays running continuously and never has to pay the job startup cost again
C: Run the transform on a lightweight single-node compute engine, which suits small inputs and avoids most of the distributed startup overhead
D: Make the transform incremental, so each hourly run only processes the rows that changed in the two reference files since the previous run
K: C
G: ## Choosing a compute engine
The exam guide asks you to choose a compute engine based on scale, memory, API needs, startup cost and feature compatibility, and lists lightweight engines for suitable smaller workloads.
- **Spark** distributes work across executors. That pays off for large data, but every run first has to start the distributed job, which can dominate small jobs.
- A **lightweight** engine runs on one node, typically with libraries such as pandas or Polars. For inputs of a few megabytes it starts faster and uses fewer resources.
## Check before switching
Confirm the logic does not depend on Spark-only features, compare the output with the current version on a branch, and keep an eye on input growth: if the files grow to many gigabytes, Spark may become the right choice again.
Example: an hourly job that spends 3 minutes starting Spark and 5 seconds joining 4 MB of data is a classic candidate.
W: Lightweight engine: the cost is distributed startup on a tiny input. A single-node engine removes most of that overhead and produces the same table, which is what the team asked for.
X: A=More Spark resources: adding executors does not shorten the fixed startup and adds cost; a few megabytes of data never needed more parallelism.
B=Streaming: a continuously running pipeline costs more for an hourly lookup table and adds operational complexity, with no freshness requirement that needs it.
D=Incremental: incremental processing saves work on large, growing inputs. Here processing time is already tiny, and the startup overhead would remain on every run.
T: For small inputs where startup dominates, choose a lightweight engine; keep Spark for data that needs distribution.
V: Code Repositories, Python transforms

@ PLTR-DE D3 T3.3 advanced troubleshooting
S: An incremental transform normally processes a few thousand new rows per run in about two minutes. Yesterday one run took six hours and reprocessed the entire input history, although no code changed. Where should the data engineer look first?
A: The executor memory settings of the transform, since a memory shortage makes incremental jobs fall back to reading the full input on every run
B: The input datasets' transaction history, for a SNAPSHOT, UPDATE or DELETE transaction that made the build fall back to full computation
C: The build schedule, since a changed schedule makes an incremental transform run against every transaction that has accumulated in the input
D: The downstream health checks, since a failing check forces the upstream transform to recompute its full history to repair the bad output
K: B
G: ## How incremental transforms stay incremental
An incremental transform processes only what was added since its last run. That works when the input grows by **APPEND** transactions: new files added, nothing changed.
## Why it falls back to a snapshot
The exam guide notes that SNAPSHOT, UPDATE and DELETE transactions can trigger incremental fallback:
- **SNAPSHOT** replaces the whole input, so "what was added" is no longer defined.
- **UPDATE** and **DELETE** modify or remove existing data, so earlier results may be wrong.
In those cases the transform recomputes from the full input, which is correct but slow. The guide advises inspecting transaction history when an incremental build runs as a snapshot.
Example: an upstream team re-ran their sync in snapshot mode to fix a bad file, and every downstream incremental transform reprocessed full history the next day.
W: Input transaction history: a full reprocess without a code change is the signature of incremental fallback, and the transaction history shows which non-append transaction caused it and who wrote it.
X: A=Memory settings: memory pressure makes a job slow or fail; it does not change which rows an incremental transform decides to process.
C=Schedule change: a schedule controls when builds run, not whether the transform reads only new transactions. A late run still processes only the unprocessed appends.
D=Downstream health checks: health checks observe and alert; they do not make upstream transforms recompute their history.
T: When an incremental build suddenly runs as a snapshot, check the input transaction history for SNAPSHOT, UPDATE or DELETE transactions.
V: Code Repositories, incremental transforms

@ PLTR-DE D4 T4.1 applied use-case
S: A pipeline has five dependent datasets. Each one is scheduled to build every hour on its own timer, so builds often run when nothing upstream has changed, and the last dataset sometimes builds before its inputs finish. How should the schedule be redesigned?
A: Keep separate timers but stagger them ten minutes apart, so each dataset has time to finish before the next one in the chain starts building
B: Replace the timers with one schedule that force-builds all five datasets every hour, so they always refresh together in a single run
C: Build all five datasets every fifteen minutes, so that any upstream change is picked up quickly even if some runs find nothing new
D: Trigger the pipeline when the source updates and build the datasets in dependency order, skipping work when inputs are unchanged
K: D
G: ## Time-based versus event-based triggers
A schedule decides when builds run. Two kinds of trigger matter here:
- **Time-based**: run at fixed times, whether or not anything changed.
- **Event-based**: run when an input dataset receives new data.
## Problems with independent timers
Five timers know nothing about each other. They cause unnecessary builds when no new data arrived and race conditions when a downstream dataset starts before its upstream finishes. The exam guide asks you to configure schedules and event-based triggers without creating unnecessary builds.
A better design triggers on the source update and builds the chain as one unit in dependency order, so each dataset runs once per real change, after its inputs.
Example: the source sync lands at 02:10 on most nights and 04:30 on some; an event trigger follows it automatically, while a timer would build stale data on the late nights.
W: Event trigger with dependency order: the pipeline runs only when new data arrives, and building the chain in order removes the race where the last dataset reads unfinished inputs.
X: A=Staggered timers: offsets guess at run times. When a build runs long, the race returns, and every timer still fires when no data changed.
B=Force-build hourly: forcing builds removes the unnecessary-build problem only by doing all the work every hour, whether or not anything changed.
C=Every fifteen minutes: this multiplies unnecessary builds and cost, and independent timers still cannot guarantee inputs finished first.
T: Trigger pipelines on input updates and build in dependency order instead of running independent timers.
V: Data Lineage, schedules

@ PLTR-DE D5 T5.1 advanced tradeoff
S: An invoices dataset backs an Invoice object type. Two requirements: no invoice row with a null customer ID may ever reach the Ontology, and the team must be alerted if the dataset has not been updated for more than 26 hours. Which combination of controls meets both?
A: A build-blocking expectation that rejects null customer IDs, plus a freshness health check with an alert on the published dataset
B: A health check that alerts on null customer IDs, plus a build-blocking expectation that fails when the data is older than 26 hours
C: A filter in the transform that silently drops null customer IDs, plus a daily manual review of the dataset's last-updated time
D: Health checks for both conditions, since a health alert prevents bad rows from reaching consumers as well as reporting stale data
K: A
G: ## Proactive and reactive controls
The exam guide separates two tools:
- **Expectations** are checks that run as part of a build. A failing expectation can stop the transaction from being committed, so invalid data never becomes the published version. They are proactive.
- **Health checks** monitor a dataset over time: freshness, schema, size, status, content. They raise alerts but do not stop data that is already published. They are reactive.
## Matching each requirement
- "Must never reach the Ontology" needs prevention, so it is an expectation that blocks the build.
- "Alert if not updated for 26 hours" concerns a build that may never run at all. Only a monitor watching the dataset over time can detect that.
The guide's self-check asks exactly this: does a requirement need a build-blocking expectation, a health alert, or both?
W: Expectation plus freshness check: the expectation blocks invalid rows before they are published, and the freshness health check notices when no build happens at all, which a build-time check could never detect.
X: B=Swapped controls: a health alert fires after null rows are already published, and an expectation only runs when a build runs, so it cannot notice a build that never happened.
C=Silent filter: dropping rows hides a source-quality problem and loses invoices without anyone knowing. Manual review is unreliable for a 26-hour alert.
D=Health checks only: health checks report problems; they do not stop a transaction, so null customer IDs would still reach the Ontology.
T: Use expectations to prevent bad data from being published and health checks to detect drift and staleness; many requirements need both.
V: Data Health, expectations

@ PLTR-DE D6 T6.4 applied troubleshooting
S: An analyst can see a curated dataset in a project and open its details page, but gets an access error when trying to preview its rows. Colleagues on the same team can read it. The project lead suggests making the analyst a project Owner to fix it. What should the data engineer do instead?
A: Make the analyst a project Owner as suggested, since the highest project role always grants every permission that the data inside the project requires
B: Copy the dataset into a new project without restrictions and share it with the analyst, so that the analyst works on an equivalent dataset
C: Use Check Access to find the specific missing requirement, such as a marking or role, and request only that access through the proper approval path
D: Rebuild the dataset on the analyst's behalf, because access errors on a preview usually mean the latest transaction has not finished committing
K: C
G: ## Opening a resource versus reading its data
The exam guide asks you to explain separately why a user can open a resource, why they can read its data, and why a pipeline can or cannot execute. In Foundry these depend on different controls:
- **Project roles** grant discretionary access to resources in a project.
- **Markings** are mandatory controls for sensitive data: a user must hold the required marking in addition to a role, and a role alone cannot override a missing marking.
- **Organizations** limit who can see resources at all.
## Diagnosing instead of widening
Check Access shows which requirement the user does not meet. Requesting exactly that keeps least privilege intact.
Example: colleagues hold the "PII" marking and the analyst does not; Owner would not help, and getting the marking through its approval process would.
W: Check Access and targeted request: seeing the dataset but not its rows suggests a missing data-level requirement. Identifying it and requesting only that access fixes the problem without granting broader permissions.
X: A=Make Owner: a broad role does not satisfy a missing marking, so it may not even work, and it gives the analyst far more control than needed.
B=Unrestricted copy: copying sensitive data to bypass its controls defeats the governance that the restriction exists for.
D=Rebuild: colleagues already read the same data, so the transaction is committed. The difference is the analyst's access, not the build.
T: Diagnose the exact failing access layer with Check Access before granting anything; never widen roles or copy data to work around a control.
V: Check Access, markings, projects

@ PLTR-DE D7 T7.2 advanced troubleshooting
S: A Shipment object type uses as its primary key a row number generated in the backing transform. After a rebuild that changed the row order, users report that status edits and links now appear on the wrong shipments. What is the correct fix?
A: Generate the row number after sorting by load time, so the same order is produced on every rebuild and the numbering stays the same
B: Use a stable key from the business data, such as the shipment number, or a deterministic value derived from columns that identify the shipment
C: Generate a new random unique ID for each row on every build, which guarantees that no two shipments can ever share the same primary key
D: Use the build timestamp combined with the row number, so every key records when it was created and stays unique across rebuilds
K: B
G: ## What a primary key does for an object
A primary key identifies one real-world entity. User edits, link types and references from applications attach to that key. If the same shipment gets a different key after a rebuild, everything attached to the old key now points at whichever shipment received it.
## Stable keys
The exam guide asks you to select stable primary keys. A good key:
- comes from the entity itself (a shipment number, an order line ID), or is a deterministic hash of the columns that identify it;
- stays the same across rebuilds, backfills and reprocessing;
- is unique; if the source has duplicates, fix the data contract rather than inventing positional keys.
Row numbers, random IDs and build timestamps all depend on how or when a build ran, not on which shipment the row describes.
Example: `SHP-2026-004211` stays attached to the same shipment forever; row 4211 may be any shipment next week.
W: Stable business key: tying the key to the shipment's identity means edits and links follow the right object through every rebuild.
X: A=Sorted row number: sorting only makes the numbering stable until a late, corrected or deleted row shifts every number after it.
C=Random ID per build: every rebuild gives every shipment a new key, so all edits and links detach on each build.
D=Timestamp plus row number: the key changes on every build because the timestamp changes, which is the same problem in a different form.
T: Primary keys must come from the entity's identity and survive rebuilds; positional, random or time-based keys break edits and links.
V: Ontology Manager, object types

@ PLTR-DE D8 T8.4 applied use-case
S: A data engineer used an AI assistant to write a new PySpark transform that joins orders to customers. The code builds successfully on a branch. Before merging, what is the most important next step?
A: Merge it right away, since a successful build confirms that the generated join logic and its output are correct for downstream consumers
B: Ask the assistant to rewrite the code several more times and keep the version that builds fastest, since speed is the main risk in generated code
C: Merge it to the main branch first and review it afterwards, since branches only add delay when the assistant has already tested the code
D: Review it like a teammate's change: compare counts, key uniqueness and nulls with the current output and check the join's assumptions
K: D
G: ## Treat AI-generated code as untrusted until reviewed
The exam guide asks data engineers to review AI-generated code and outputs for incorrect assumptions, unsupported patterns and regressions. A successful build proves only that the code ran, not that it produced correct data.
## What to check for a join
- **Cardinality**: if customers can appear twice in the customer table, the join multiplies orders.
- **Keys and nulls**: orders with no matching customer may be dropped by an inner join or produce nulls.
- **Counts versus the current output**: run on the branch and compare row counts and key uniqueness with the production version.
- **Assumptions**: column names, types and filters the assistant guessed.
Branches exist for this: changes are validated in isolation before consumers see them.
Example: an assistant used an inner join; 3% of orders whose customer arrives a day late disappeared, yet the build was green.
W: Review with evidence: comparing counts, keys and nulls with the current output, on a branch, catches wrong assumptions that a green build cannot reveal.
X: A=Build success is enough: builds succeed on wrong logic all the time; duplicated or dropped rows do not cause errors.
B=Fastest rewrite: speed is not the main risk. Several unreviewed versions only multiply unverified assumptions.
C=Merge first: merging unreviewed code exposes consumers to possible bad data; branches are the place to validate first.
T: A green build is not a correct result: review AI-generated transforms against the current output before merging.
V: Code Repositories, AIP Assist
