@ PLTR-DE D1 T1.2 advanced use-case
S: A logistics company lands carrier manifests in an S3 bucket: each night the carrier adds about 40,000 new CSV files and never edits an old one, and the folder already holds six years of history. Downstream Python transforms are incremental and must stay that way. Last month a nightly SNAPSHOT sync ran for nine hours and then lost all of its work to a single network timeout. Which sync configuration best meets these constraints with the LEAST risk of repeated full reloads?
A: SNAPSHOT transaction type with the Exclude files already synced filter, so each run commits only the files that arrived since the previous run
B: UPDATE transaction type with Exclude files already synced and its Last modified date option, so that new and changed files are both picked up
C: APPEND transaction type with Exclude files already synced and Limit number of files filters, scheduled often enough to keep up with new arrivals
D: APPEND transaction type with only the Exclude files already synced filter, so each run ingests the whole nightly delivery in a single transaction
K: C
G: ## File-based ingestion modes
A file batch sync is defined by its transaction type plus its filters, and a few combinations give the well-known modes:
- Batch mirror: `SNAPSHOT`, no filters. Every run re-reads every file and replaces the view.
- Incremental mirror: `APPEND` + `Exclude files already synced`. Each run ingests only files not ingested before, keyed by file path, and adds them to the view.
- Incremental mirror with updates: `UPDATE` + `Exclude files already synced` with the `Last modified date` or `File size` option. Use it only when the source really modifies files, because the output is no longer append-only.
- Trailing window: `SNAPSHOT` + `Exclude files already synced`. The view holds only the files of the latest run.
## Why big runs are fragile
Batch syncs are transactional: if a run fails at any point, the whole transaction is aborted and nothing from that run is committed. The docs therefore recommend incremental `APPEND` syncs with a `Limit number of files` filter, so each run is a small checkpoint and a failure only repeats the current batch.
Example: 40,000 files a night with a limit of 5,000 per run and an hourly schedule commits eight small transactions instead of one huge one.
W: APPEND with a file limit: new files are added keyed by path, the output stays append-only for the incremental transforms, and each capped run is a small checkpoint, so a timeout repeats only one batch.
X: A=SNAPSHOT plus exclude: this is the trailing-window mode; each run replaces the view with only the newest files, and the SNAPSHOT transactions break incrementality downstream.
B=UPDATE with modified date: UPDATE is only for sources that modify files, and its output is not append-only, so the downstream transforms could no longer run incrementally.
D=APPEND without a limit: this keeps incrementality, but a whole night's 40,000 files still form one transaction, so one network error aborts the entire delivery again.
T: For append-only file drops, use APPEND with Exclude files already synced and cap each run with Limit number of files.
V: Data Connection

@ PLTR-DE D1 T1.3 advanced use-case
S: A retailer keeps a 60 TB sales table as an external Delta table in Databricks, reached from Foundry through a Foundry worker source with a direct egress policy. Finance wants a daily Foundry pipeline built on this table, but the storage budget rules out copying the raw table into Foundry, and builds should start only when the Delta table has actually changed rather than on a fixed clock. Which approach meets these requirements?
A: Create a daily table batch sync of the Delta table into a Foundry dataset and trigger the pipeline whenever that synced dataset gets a new transaction
B: Register the table as a virtual table, use it as the pipeline input, and enable update detection with a polling schedule so it can act as the trigger
C: Register the table as a virtual table, use it as the pipeline input, and run the pipeline on a fixed daily time trigger whether or not the source changed
D: Register the table as a virtual table and rely on Foundry's own pipeline build tracking to notice external changes, leaving update detection turned off
K: B
G: ## Virtual tables
A virtual table is a pointer to a table in an external system: Foundry stores the connection and a locator, not the data. Benefits include no duplicate storage for the raw table and querying data directly on use. They require a Foundry worker source with direct egress policies.
## Update detection
Foundry automatically tracks updates for virtual table *outputs* that its own pipelines write. For virtual table *inputs* managed outside Foundry, you enable update detection: Foundry polls the source on a schedule you choose (for example hourly or daily).
- If the table format supports versioning, such as Delta or Iceberg, Foundry detects real changes and triggers downstream builds only when needed.
- Once enabled, the virtual table input can be used as a schedule trigger for downstream datasets.
- Update detection is available only after the virtual table has been used to create downstream resources.
W: Virtual table with update detection: no raw copy is stored, and polling a versioned Delta table lets the schedule fire only when the table really changed.
X: A=Daily batch sync: the sync writes the full table into a Foundry dataset, which is exactly the duplicate storage the budget forbids.
C=Fixed daily trigger: this avoids the copy but builds every day even when nothing changed, missing the change-driven trigger requirement.
D=Build tracking only: automatic tracking covers virtual table outputs written by Foundry pipelines; an externally managed input needs update detection for changes to be seen.
T: Use a virtual table to avoid copying, and enable update detection to trigger builds from real source changes.
V: Virtual tables, Data Connection

@ PLTR-DE D1 T1.1 advanced use-case
S: A bank's on-premises Oracle database sits in a private network that allows no inbound connections from the internet. Its Foundry enrollment is cloud-hosted, and the existing source runs on a legacy agent worker whose host the team must patch and resize every month. The team now wants to call the source from Python external transforms and cut agent maintenance, while every connection keeps being initiated outbound from inside the bank's network. What should the data engineer configure?
A: Move the source to a Foundry worker with an agent proxy egress policy, so jobs run in Foundry and the agent only relays outbound traffic
B: Keep the source on the agent worker and enable code imports on it, so the external transforms can reuse the agent's existing connection and secrets
C: Move the source to a Foundry worker with a direct connection egress policy, and open the bank firewall to inbound traffic from Foundry's addresses
D: Keep the agent worker but give the agent host more JVM heap and a second host, so that syncs and external transform calls stop competing
K: A
G: ## Worker and networking are separate choices
A source has a **worker**, which decides where compute runs, and **networking**, which decides how the target system is reached.
- Foundry worker: capabilities run in Foundry's containerized job environment. It is the recommended option, and all Foundry worker sources can be used in code (external transforms, external functions, compute modules).
- Agent worker: legacy. Capabilities run on a customer-managed agent host. Agent worker connections cannot be used in code.
## Egress policies for Foundry worker sources
- Direct connection policies reach systems directly accessible from Foundry; for cloud-hosted Foundry that means the public internet.
- Agent proxy policies reach systems in a different network, such as on-premises. An agent inside the network initiates an outbound WebSocket to Foundry, so no new inbound paths are opened.
Agent proxy is a networking mode for a Foundry worker, not a worker type, and the agent then only acts as a network proxy, a much smaller operational footprint.
W: Foundry worker with agent proxy: compute moves into Foundry, the source becomes usable from external transforms, and the agent keeps all traffic outbound from the bank's network.
X: B=Agent worker with code imports: agent worker connections cannot be used in code, so the external transforms still could not use this source.
C=Direct connection with inbound rule: a direct policy needs the database reachable from Foundry, which means opening an inbound path the bank forbids.
D=Bigger agent host: more heap and hosts add maintenance instead of cutting it, and an agent worker source still cannot be called from code.
T: For on-premises systems, a Foundry worker with an agent proxy policy gives code access with outbound-only networking.
V: Data Connection

@ PLTR-DE D1 T1.3 advanced tradeoff
S: A Foundry dataset of shipment events is built incrementally with APPEND transactions and exported every hour to a PostgreSQL table. A billing system reads that table and keeps its own history, so the table must never be truncated, and any duplicate row causes a double invoice. Last quarter an upstream fix triggered an accidental SNAPSHOT, and the team now wants such an event to stop the export rather than resend data. Which table export mode fits BEST?
A: Efficiently mirror dataset to external table, which sends only unexported transactions and keeps the external table matching the Foundry view
B: Export incrementally and fail if not APPEND, which sends unexported transactions and stops on any non-APPEND change after the first run
C: Export incrementally, which sends only unexported transactions from the current view and never truncates the external PostgreSQL table
D: Full dataset without truncation, which sends the complete current view on every run and leaves existing rows in the external table untouched
K: B
G: ## Table export modes
A table export inserts rows from a Foundry dataset into an existing external table. The mode decides what happens when the dataset's transactions are not simple appends:
- Efficiently mirror dataset to external table (recommended default): exports unexported transactions incrementally and **truncates the external table when the dataset gets a SNAPSHOT**, so the external table always matches the Foundry view.
- Export incrementally: exports only unexported transactions without truncating; it **may produce duplicates** if the upstream dataset has a SNAPSHOT.
- Export incrementally and fail if not APPEND: exports unexported transactions and **fails if there is a SNAPSHOT, UPDATE or DELETE** after the first run. It guarantees no duplicate data is ever exported.
- Full dataset without truncation: exports the whole view every run and almost always creates duplicates.
- Full dataset with truncation and Export incrementally with truncation both truncate the target.
Example: an accidental SNAPSHOT with the fail-if-not-APPEND mode stops the export, and the team investigates before anything is resent.
W: Fail if not APPEND: it never truncates, never resends old rows, and turns an accidental SNAPSHOT into a failed export the team can investigate.
X: A=Efficiently mirror: on a SNAPSHOT it truncates the external table, which would wipe the history the billing system depends on.
C=Export incrementally: no truncation, but an upstream SNAPSHOT makes it export the new view's rows again, creating the duplicate invoices the team must avoid.
D=Full dataset without truncation: it resends the whole view every hour on top of existing rows, which produces duplicates on every run.
T: When the target must never be truncated or duplicated, use Export incrementally and fail if not APPEND.
V: Data Connection

@ PLTR-DE D1 T1.4 advanced troubleshooting
S: After an agent-worker PostgreSQL source is migrated to a Foundry worker, its nightly sync fails within seconds with `UnknownHostException`, and the source preview fails the same way. Nobody changed the credentials, the database team confirms the server is up, and syncs on other sources run normally. The on-call engineer must restore the sync tonight without reverting the migration. What should the engineer check first?
A: The egress policies attached to the source, confirming the host and port they allow match the database, then testing it from the source terminal
B: The stored credentials, re-entering the database password because migrated secrets are often stale and an expired password surfaces as a lookup failure
C: The source certificates, adding the database server's certificate chain because a missing certificate stops the connection before the handshake starts
D: The JDBC driver configured on the source, uploading the driver from the old agent because a missing driver class prevents host name resolution
K: A
G: ## Read the error before changing anything
Data Connection errors point to different layers, and the migration guide maps the common ones:
- `UnknownHostException`: make sure the correct egress policies are assigned to the source and that Foundry can reach the endpoint.
- `PKIX path building failed` or `SSLHandshakeException`: the certificates for the source are missing or wrong.
- `Driver class not found`: the JDBC driver is not uploaded to the source.
- `HTTP 401` with an outbound application: authorization or scopes, not networking.
## Egress after a migration
Agent worker sources were networked on the agent host. A Foundry worker source reaches systems only through the egress policies attached to it, which allowlist hosts, ports and protocols. A connection that fails before authentication is usually an egress problem. The source terminal (`dig`, `curl`, `openssl s_client`) and the network egress logs show what is being blocked.
W: Egress policies first: a host lookup failure right after moving to a Foundry worker, with the server up, points at missing or mismatched egress policies, which the terminal and egress logs confirm.
X: B=Re-enter credentials: the failure happens before authentication, and a wrong password produces an authentication error, not an unknown host.
C=Add certificates: certificate problems surface as PKIX or SSL handshake errors once a connection is made, not as an unresolved host name.
D=Upload the driver: a missing driver produces a driver class not found error, and the driver has nothing to do with resolving the host.
T: UnknownHostException on a Foundry worker source means checking its egress policies before credentials, certificates or drivers.
V: Data Connection

@ PLTR-DE D2 T2.3 advanced use-case
S: A support team ingests about 4 GB of new chat transcripts per day into an append-only dataset whose history is already 3 TB. A Python transform must call a Palantir-provided LLM to tag each transcript, and to control token cost it must process only the rows added since its last build. The team prefers code over a visual tool and wants a production pipeline with version control. Which implementation fits these constraints?
A: An incremental PySpark transform that reads only the added rows and calls the Palantir-provided LLM API inside the Spark job for each new transcript
B: A snapshot PySpark transform that tags the whole 3 TB transcript history each day, so every row is always labeled with the current prompt
C: A JupyterLab notebook in Code Workspaces that an engineer runs every morning to tag the new transcripts and write the results to a dataset
D: An incremental single-node Python transform using Polars that reads only added rows and calls the Palantir-provided LLM API per new transcript
K: D
G: ## Choosing a Python compute engine
Python transforms run either single-node (lightweight: Polars, pandas, DuckDB) or distributed (Spark). The docs recommend Polars as the default for production and Spark only when data scale demands it, roughly above 50 GB uncompressed per run.
## Feature support differs
The feature table for Python transforms shows, among others:
- Incremental transforms: supported in both.
- Palantir-provided LLMs API, snapshot: both.
- Palantir-provided LLMs API, **incremental: single-node only, not Spark**.
## Why size per run matters
An incremental build reads only the added rows, so the relevant size is the daily 4 GB, not the 3 TB history.
Example: a lightweight incremental transform reads `added` rows, calls the model per transcript and appends the tags.
W: Incremental Polars transform: single-node transforms support incremental use of the Palantir-provided LLM API, and 4 GB per run fits a single node comfortably.
X: A=Incremental PySpark: the Palantir-provided LLM API in incremental mode is not supported for Spark transforms.
B=Snapshot PySpark: tagging the full history daily pays for millions of repeat LLM calls, breaking the cost constraint.
C=Code Workspaces notebook: a manually run notebook is not a versioned, scheduled production pipeline, which the docs reserve for Code Repositories or Pipeline Builder.
T: For incremental LLM calls in Python transforms, use a single-node engine; Spark does not support the incremental LLM API.
V: Python transforms, AIP

@ PLTR-DE D2 T2.1 advanced comparison
S: An operations analytics team of five analysts, none of whom write Python, must own a production pipeline that cleans maintenance logs and outputs both a dataset and an object type. Their governance lead requires that nobody can change the production version directly and that every change is approved by someone who did not make it. Which authoring setup BEST fits the team and the governance rule?
A: Code Repositories Python transforms with a locked master branch, so every change goes through a pull request reviewed by a second engineer
B: A Contour analysis saved as a dataset, with edit rights limited to the governance lead so that only one person can change the production logic
C: Code Workspaces with VS Code and Git branches, so analysts experiment on branches and the lead merges the approved notebooks into production
D: Pipeline Builder with the main branch protected so changes need a proposal, plus one approval from an editor who did not contribute

- Pipeline Builder is Foundry's primary data integration application. Users who code and users who do not code build pipelines with graph and form interfaces, and outputs can be datasets or Ontology components such as object types and link types.

C=Code Workspaces: it is discouraged for production pipelines and still expects the analysts to write code.
T: For a non-coding team with review rules, use Pipeline Builder with protected branches that require proposals and approvals.

@ PLTR-DE D2 T2.4 advanced troubleshooting
S: An engineer adds `@incremental(require_incremental=True)` to a Python transform that appends deduplicated orders and filters them against its previous output. Preview in Code Repositories showed correct rows, yet the first incremental build on master wrote rows that should have been filtered out. Before any future build, the team wants a fast check that actually exercises the incremental code path. What should the engineer use?
A: Preview the transform again in Code Repositories with require_incremental=True kept on, which forces the preview to run in incremental mode
B: Preview the transform in Code Repositories after bumping semantic_version, so that the preview reads the previous output from the last build
C: Preview the transform in Code Repositories with a much larger input sample, so the deduplication against earlier rows shows up in the output
D: Preview the transform in a VS Code workspace, which respects incremental behaviour and reads previous output and added rows as a build does
K: D
G: ## Two previews, two behaviours
- Code Repositories Preview runs code on a sample without committing anything, and it **always runs transforms non-incrementally**, even when `require_incremental=True` is set. In a non-incremental run, reading the output in `previous` mode returns an empty DataFrame and inputs are presented in full.
- VS Code preview **respects incremental behaviour** and supports v1 and v2 incremental semantics for Spark and lightweight transforms; the docs recommend it for experimenting with the incremental API.
## Why the bug slipped through
Logic that filters against `previous` output can never be tested by a non-incremental preview, because `previous` is empty there. The first real incremental build was the first time that branch of the code ran.
W: VS Code preview: it runs the transform the way an incremental build would, so the filter against the previous output is actually exercised.
X: A=Preview with require_incremental: Code Repositories Preview ignores that argument and still runs non-incrementally.
B=Bump semantic_version: changing the semantic version forces the next run to be non-incremental, the opposite of what the check needs.
C=Larger sample: more rows do not change the mode; the preview is still non-incremental and the previous output is still empty.
T: Code Repositories Preview is always non-incremental; use VS Code preview to test incremental logic.
V: Code Repositories, Code Workspaces, Python transforms

@ PLTR-DE D2 T2.2 advanced use-case
S: An incremental Python transform maintains running totals of spend per customer from an append-only payments dataset of 900 million rows. With the default read and write modes, each build appends a new partial total, so customers end up with several rows. A nightly snapshot rebuild is too expensive, and the output must hold exactly one row per customer. What change fixes the logic while keeping the transform incremental?
A: Keep the default modes but switch the decorator to transform_df, so the platform merges each new partial total into the existing customer row
B: Aggregate the input read in current mode on each build and keep the output in modify mode, so each build writes the latest full totals
C: Bump semantic_version on every deploy so that each build recomputes the totals from scratch and replaces the existing customer rows
D: Aggregate the added payments, union them with the output read in previous mode with a schema, re-aggregate, and write in replace mode
K: D
G: ## Default modes suit row-level logic only
With `@incremental()`, inputs default to the `added` read mode and the output defaults to the `modify` write mode, which appends. That is correct when output rows depend only on new input rows, such as a filter. Aggregations break it: each build appends a fresh partial total.
## The merge pattern
- Read the new rows: `payments.dataframe('added')`.
- Read the existing output: `out.dataframe('previous', schema)`. The schema is required so a non-incremental run gets an empty DataFrame of the right shape.
- Union, re-aggregate per customer, then `out.set_mode('replace')` and write.
`set_mode()` is available with `transform()` or `transform.using()`; `transform_df()` and `transform_pandas()` only give the default modes.
Example: yesterday's total 120 plus today's added 30 is written as one row of 150, replacing the old row.
W: Merge with previous output: combining added rows with the previous output and writing in replace mode keeps one row per customer while reading only new payments.
X: A=Switch to transform_df: transform_df only offers the default added and modify modes, and the platform never merges rows for you.
B=Current mode with modify: current reads the full input every build, losing the incremental saving, and modify appends the totals again as new duplicate rows.
C=Bump semantic_version: each bump forces a full non-incremental run, which is the expensive rebuild the team ruled out.
T: For incremental aggregations, union added rows with the previous output and write in replace mode.
V: Python transforms

@ PLTR-DE D2 T2.2 advanced tradeoff
S: Two append-only datasets, a 2-billion-row sensor log and a 400-million-row calibration table, are joined every hour on the exact column pair `device_id` and `site_id` to produce a quality dashboard that operators read each morning. Spark details show shuffle write dominating each job, the join logic itself must stay unchanged, and both datasets are only ever extended with APPEND transactions. Which change should most reduce the shuffle?
A: Add a join-optimized projection on device_id alone to both datasets, since a projection on one join column also serves the two-column join
B: Add a join-optimized projection on the column set device_id and site_id to both datasets, with the same bucket count on each
C: Add a filter-optimized projection on the ordered list device_id then site_id to both datasets, so the join reads fewer files each hour
D: Add join-optimized projections on device_id and site_id to both datasets, with a different bucket count for each based on its size
K: B
G: ## What a projection is
A dataset projection is an extra copy of a dataset's data, stored and updated separately and laid out for one query pattern: either filters on an ordered list of columns, or joins on a set of columns. Projections can only be added to append-only datasets.
## Join-optimized projections
A join projection is defined by an unordered set of columns and a bucket count, and it optimizes joins on **exactly** that set.
- Large joins normally sort-merge: both sides are shuffled and sorted on the key.
- If one side has a matching join projection, that side is not shuffled or sorted.
- If both sides have matching join projections **with the same number of buckets**, neither side is shuffled or sorted.
Example: both datasets projected on `{device_id, site_id}` with 512 buckets each.
W: Matching join projections: the same column set and the same bucket count on both sides let the join skip shuffling and sorting entirely.
X: A=Projection on device_id only: a join projection only optimizes joins on its exact column set, so a one-column projection does not serve a two-column join.
C=Filter-optimized projection: filter projections speed up comparisons with constants on a column prefix; they do not lay out data for a join.
D=Different bucket counts: the no-shuffle case needs both projections to use the same number of buckets.
T: To remove join shuffles, give both datasets join projections on the exact join columns with the same bucket count.
V: Dataset projections, Spark

@ PLTR-DE D3 T3.1 advanced comparison
S: A utility receives smart meter readings that land in Foundry every few minutes as APPEND transactions. Dashboards may lag by up to 30 minutes, the compute budget is tight, and the only engineers available write Python. The current snapshot transform recomputes two years of readings on every run and is getting more expensive each month. Which processing mode should the team adopt?
A: A streaming pipeline written as a Python transform, so readings are processed continuously as soon as each one arrives
B: An incremental Python transform scheduled on input updates, which processes only the newly appended readings on each build
C: A streaming pipeline in Pipeline Builder that runs continuously, so the dashboards update within seconds of every reading
D: The existing snapshot Python transform on a 30-minute schedule, accepting the full recompute because the logic stays simplest
K: B
G: ## Streaming, incremental or batch
The docs frame the choice around latency, cost and supported languages:
- Streaming is for workflows that need low end-to-end latency. For use cases that can tolerate **more than ten minutes** of latency, incremental or standard batch datasets may be suitable.
- The average cost of a streaming pipeline is often higher than batch, because of its continuous, high-throughput computation.
- Python transforms are supported for batch but **not for streaming**; streaming supports Java transforms and Pipeline Builder.
## Incremental batch
An incremental transform reads only rows appended since its last run and appends results, so cost tracks the new data rather than the whole history.
Example: readings arriving every few minutes, built every 10 to 15 minutes incrementally, comfortably meet a 30-minute lag.
W: Incremental Python transform: a 30-minute tolerance does not need streaming, Python is supported for batch, and processing only new readings controls cost.
X: A=Python streaming: Python transforms are not supported for streaming pipelines.
C=Pipeline Builder streaming: it would work technically, but continuous streaming costs more and the 30-minute tolerance does not need it.

AI FDE proposes changes on branches, as a Global Branch proposal or a Code Repositories pull request, and acts with the user's own identity and permissions. It can validate its own work with previews and CI checks. Those checks prove the code compiles and runs on a sample; they do not prove the incremental semantics are right.
## The semantic trap
- `@incremental()` can wrap `transform_df`, but then only the **default** modes apply: inputs read `added` rows and the output is written in `modify` mode, which appends.
- That is fine when output rows depend only on new input rows. Joins, aggregations and distinct need explicit modes with `transform()` or `transform.using()`, such as reading the `previous` output and writing in `replace` mode.
- Code Repositories preview always runs non-incrementally, so a correct-looking preview cannot reveal the problem.
W: Default-mode aggregation: each incremental build would append a new partial distinct count per day instead of correcting the existing totals.
X: B=Cannot wrap transform_df: the decorator can wrap transform_df; the issue is that only default modes are available, not a runtime failure.
C=Bypassing protection: AI FDE proposes changes through branches and pull requests for review, so protection still applies.
D=Service account: AI FDE has no separate service account; it acts in the user's own session with the user's permissions.
T: When reviewing incremental code, check that aggregations do not rely on transform_df's default added and modify modes.
