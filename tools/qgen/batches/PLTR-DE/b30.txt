# PLTR-DE batch 30: Domain 5 round 4 (Data Quality and Health Monitoring), 8 questions

@ PLTR-DE D5 T5.1 applied use-case
S: A dataset feeds a pricing engine where a wrong currency code would cause incorrect charges. The currency column must always be one of 12 ISO codes. Which control is appropriate?
A: A health check on the distribution of currency codes that alerts the owner when an unusual code appears in the published dataset
B: A build-blocking expectation that every currency value is in the allowed set of 12 codes, so any other value blocks publication
C: A transform that maps any unknown code to USD so the pricing engine never sees an unexpected value
D: A note in the pipeline documentation listing the 12 allowed codes for consumers to verify
K: B
G: ## Allowed-value expectations
The exam guide asks you to use expectations to stop invalid transactions when correctness matters. An allowed-value set is a classic build-time assertion, and the consequence (wrong charges) demands prevention.
## Configuration
- Expectation: `currency IN (12 codes)`; failure blocks the build.
- Alert on failure to the owner; the source is corrected and the build rerun.
- Previous good data stays published meanwhile.
Example: a source sends "EU" instead of "EUR"; the build fails at 02:05 and no customer is charged in a wrong currency.
W: Build-blocking allowed-value expectation: invalid codes never reach the pricing engine, which is what the consequence requires.
X: A=Distribution alert: the bad code is already published and may already have charged customers.
C=Map unknown to USD: silently converts an error into a wrong currency; the charges would be wrong by design.
D=Documentation: consumers cannot verify every row; nothing enforces the set.
T: Enforce allowed-value sets with build-blocking expectations when consumers act on the values.
V: expectations

@ PLTR-DE D5 T5.3 applied troubleshooting
S: A freshness check on a dataset is green, but consumers report the data is weeks old. Investigation shows the pipeline rebuilds nightly and writes a transaction each time even though the source stopped delivering. What is the monitoring gap?
A: There is no gap; a green freshness check means the data is fresh by definition and the consumers must be looking at the wrong dataset
B: Freshness was measured on transaction time, not content; add a content-freshness check (maximum event date) plus a check on the upstream source
C: The freshness threshold is too strict for a nightly pipeline and should be lengthened to several days to avoid false alarms
D: The check should be deleted since it gave a wrong answer and a check that can be wrong is worse than no check
K: B
G: ## Transaction freshness versus content freshness
A successful nightly build writes a new transaction with old content. The exam guide warns that a successful run can still produce stale data and asks for checks on counts, dates and sources.
## Fix
- Content check: maximum `event_date` must be within the expected window.
- Upstream check: freshness on the source sync's dataset, which is where delivery stopped.
- Keep the transaction-freshness check as a build-ran signal, not a data-fresh signal.
Example: the content check fires the first night after the source stops, three weeks earlier than the consumers' complaint.
W: Content-based and upstream freshness checks: they measure what consumers care about, the age of the data itself.
X: A=Green means fresh: the check measured the wrong thing; the data was old.
C=Loosen threshold: makes the wrong measurement even less sensitive.
D=Delete: the check still detects a stopped pipeline; it needs complementing, not removing.
T: Measure freshness on data content and on upstream sources, not only on the latest transaction time.
V: Data Health

@ PLTR-DE D5 T5.2 applied tradeoff
S: A pipeline's expectation on a `country` column fails when the source legitimately starts sending a new country code after the company expands. What process keeps expectations useful without blocking legitimate business change?
A: Remove allowed-value expectations from the pipeline entirely so that new country codes never cause build failures again
B: Keep the allowed set as governed reference data the business updates through review, with the expectation reading it
C: Hard-code a very long list of every country code in the world into the expectation so that nothing new can ever appear
D: Let the on-call engineer edit the expectation's allowed list at night whenever a failure occurs, to keep the pipeline running
K: B
G: ## Expectations against reference data
The exam guide asks for expectations that encode the real contract and for governed change. Allowed sets that evolve should live in reference data, not in hard-coded lists.
## Design
- Reference dataset `countries_active`, owned by the business, updated via a reviewed Action or process.
- Expectation: values must exist in the reference dataset.
- Expansion to a new country: the reference is updated first; the build passes; a typo still fails.
Example: "BR" is added to the reference on Monday; Tuesday's build with Brazilian rows passes; "BZ" (a typo) is still caught.
W: Reference-backed expectation with governed updates: business change flows through data while invalid values stay blocked.
X: A=Remove: typos and corrupt codes reach consumers unchecked; the control that catches real errors is gone with the inconvenience.
C=Every possible code: loses the ability to catch codes the company does not actually operate in.
D=Night edits: unreviewed changes to a correctness control at 3 a.m.
T: Keep evolving allowed sets as governed reference data and validate against it.
V: expectations, Ontology

@ PLTR-DE D5 T5.3 applied use-case
S: A team wants to detect duplicate rows that appear occasionally after upstream retries. Duplicates are identical across all columns. Which check and placement are right?
A: A health check that counts total rows in the curated dataset and alerts the owner whenever the count grows faster than the expected rate
B: Idempotent deduplication in the transform, a uniqueness expectation on the curated output, and an upstream duplicate-rate check
C: A manual weekly query for duplicate rows run by an analyst, with any duplicates found reported to the pipeline team
D: A Linter rule configured to detect duplicate rows, since the Linter is the tool that checks pipeline data content
K: B
G: ## Detecting and preventing duplicates
The exam guide pairs expectations with the stage they protect and asks for idempotent handling of retries. Duplicates from retries are expected upstream and must not reach curated data.
## Design
- Transform: deduplicate by key (idempotent), since the cause is known.
- Expectation: key uniqueness on the curated output; blocks if the dedupe ever fails.
- Health check: duplicate rate on the raw input, to see if retries are getting worse.
Example: 0.4% duplicates in the raw sync are removed; the curated dataset's uniqueness expectation has never failed.
W: Idempotent deduplication plus a uniqueness expectation and an upstream rate check: prevention, enforcement and visibility.
X: A=Row growth: duplicates may be a tiny fraction; growth is dominated by real data.
C=Weekly manual query: duplicates sit in the curated data for up to a week and the check depends on someone remembering.
D=Linter: the Linter analyses pipeline structure and anti-patterns; it does not inspect rows in a dataset.
T: Deduplicate idempotently where duplicates originate and enforce uniqueness with an expectation on the curated output.
V: expectations, Data Health

@ PLTR-DE D5 T5.1 applied comparison
S: A data engineer is deciding, for each requirement on an orders dataset, whether to implement it as a build-blocking expectation or as a health check. Which requirement is best met by a health check?
A: No order in the curated dataset may ever have a null customer id, since every order must belong to a known customer
B: The team should be told if the average order value shifts by more than 30% week over week, which may be a legitimate change
C: The primary key must be unique in the dataset backing the Order object type, since duplicate keys would corrupt objects
D: Order dates must never be in the future relative to the build date, since such rows indicate a source clock or entry error
K: B
G: ## Detect versus prevent, again
The exam guide's self-check asks which requirements need blocking and which need alerting. Rules that are always true get expectations; signals that may be legitimate get health checks.
- Null customer id, unique key, future dates: always invalid: expectations.
- A 30% shift in average order value: possibly a real change: health check with investigation.
Example: the shift alert fires during a promotion week; investigation confirms it is real and the build was right not to block.
W: The average-value shift: a possibly legitimate signal to investigate, which is the health-check case.
X: A=Null customer id: never legitimate; a violating row must not be published, which is an expectation.
C=Unique key: a duplicate key breaks the object type's identity; always invalid, so it is enforced by an expectation.
D=Future dates: an order cannot legitimately be dated in the future; it is an invariant enforced at build time.
T: Use health checks for signals that may be legitimate and expectations for rules that are never legitimately violated.
V: Data Health, expectations

@ PLTR-DE D5 T5.3 applied troubleshooting
S: A data quality alert fires at 03:00 and the on-call engineer cannot tell from the message which dataset, which check or what threshold was breached. What should be improved?
A: Nothing; the on-call engineer can look through all of the team's datasets in the morning to find which one triggered the alert
B: The alert content: dataset, check, observed value versus threshold, links to the dataset and lineage, and the runbook
C: The alert should be sent to more people across the organization so that someone will recognize which dataset it refers to
D: The alert should be downgraded to a weekly summary email so that it does not wake anyone up at night
K: B
G: ## Actionable alerts
The exam guide asks for alert design that enables investigation. An alert without context wastes the responder's first hour.
## Content
- What: dataset, check name, metric value, threshold.
- Where: links to the dataset, its lineage and the failing build.
- How: runbook link with first steps.
- Who: owner and escalation.
Example: "orders_curated: freshness 31h > 26h; last transaction 02:10 yesterday; upstream sync failed; runbook: ..."
W: Context-rich alert content: the responder knows what, where and how within seconds.
X: A=Look in the morning: hours of delay on a quality problem, and the engineer still has to search every dataset for it.
C=More recipients: a vague alert sent widely confuses more people.
D=Weekly summary: removes the timeliness that alerting exists for.
T: Alerts must name the dataset, check, values and runbook so responders can act at once.
V: Data Health

@ PLTR-DE D5 T5.2 applied use-case
S: Which practice ensures that a newly created curated dataset has appropriate quality controls from day one?
A: Adding quality checks later, once the consuming teams have used the dataset for a while and complained about specific problems they found
B: A definition-of-done: documented contract, key expectations, freshness and size checks, alert routing and runbook, before publishing
C: Copying the checks from a random existing dataset into the new one regardless of whether they fit its contract
D: Asking the consuming teams to write whatever checks they want on the dataset themselves after it is published
K: B
G: ## Quality as part of publishing
The exam guide expects pipelines to be built with validation, publication contracts and monitoring. A checklist makes this routine.
## Definition of done
- Contract documented on the dataset.
- Expectations: keys, required fields, allowed values where applicable.
- Health checks: freshness, size, schema.
- Alert routing and runbook.
Example: the new dataset's first silent-empty input is caught by its size check on day two.
W: A definition-of-done applied before publication: every curated dataset starts with controls instead of acquiring them after incidents.
X: A=After complaints: consumers become the detection system, and the first problems reach them before any check exists.
C=Random copy: checks that do not match the dataset's contract either block wrongly or miss real problems.
D=Consumers write checks: the producer owns the contract and its enforcement.
T: Publish curated datasets only with their contract, expectations, health checks and alerts in place.

@ PLTR-DE D5 T5.3 advanced tradeoff
S: A platform-wide review finds 1,200 health checks, a third of which have fired continuously for months without action. What should the data engineering team do?
A: Delete all 1,200 health checks and start over from nothing, adding new checks one by one only when a specific need has been demonstrated
B: Triage each failing check as a real problem (fix) or a wrong assumption (re-baseline or retire), assign owners, forbid permanent red
C: Silence the failing third of the checks permanently so that the monitoring dashboard shows green for the platform
D: Lower every check's threshold across the platform until all 1,200 checks pass, so that the alert volume drops to zero
K: B
G: ## Alert hygiene
The exam guide asks for meaningful monitoring and investigation of failures. Checks that stay red are either ignored real problems or broken checks; both are harmful.
## Triage
- Classify each red check: real issue (open a fix), stale assumption (re-baseline), obsolete (retire with a note).
- Owner per check; a weekly review of anything red.
- Policy: red requires a decision within a defined time.
Example: of 400 red checks, 60 reveal real stale datasets, 250 are re-baselined, 90 are retired; the remaining signal is trusted again.
W: Triage with ownership and a no-permanent-red policy: the monitoring estate becomes credible and actionable.
X: A=Delete everything: throws away the 800 checks that work and leaves the platform unmonitored while they are rebuilt.
C=Silence: among the 400 red checks are real stale datasets; silencing hides those along with the broken checks.
D=Lower thresholds: a check tuned to never fire detects nothing; the whole estate becomes decorative.
T: Audit persistently failing checks, fix or re-baseline each, and never allow a check to stay red without a decision.
V: Data Health
