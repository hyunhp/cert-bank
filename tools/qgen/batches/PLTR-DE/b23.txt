# PLTR-DE batch 23: Domain 6 round 3 (Security, Projects, and Governance), 8 questions

@ PLTR-DE D6 T6.1 applied comparison
S: Which of the following correctly describes the difference between a marking and a project role?
A: A marking is a project-scoped permission such as Viewer or Editor, while a role is an organization-wide label that restricts access to sensitive data
B: A marking is a mandatory, data-following control required in addition to any role; a project role is a discretionary permission within a project
C: Markings and roles are interchangeable ways to grant access, and either one alone is sufficient for a user to read a dataset
D: A marking applies only to Ontology objects, while roles apply only to datasets and transforms within projects
K: B
G: ## Mandatory versus discretionary control
The exam guide asks you to understand how organizations, markings and project roles combine.
- Markings: mandatory access control. Applied to resources, they follow the data into derived resources; every reader must hold them regardless of role.
- Project roles: discretionary permissions (viewer, editor, owner) granted on a project to users and groups.
Both must be satisfied; neither replaces the other.
Example: a Viewer of the Finance project who lacks the Payroll marking cannot read the payroll dataset in it.
W: Mandatory data-following control versus discretionary project permission: the accurate distinction.
X: A=Swapped: roles are the project-scoped permissions; markings restrict sensitive data.
C=Interchangeable: both apply; a role never bypasses a marking.
D=Objects versus datasets: markings apply to datasets, objects and other resources alike.
T: Markings are mandatory and follow the data; roles are discretionary and project-scoped; access needs both.
V: markings, projects

@ PLTR-DE D6 T6.2 applied use-case
S: A data engineering team supports five business domains. Each domain has its own data sources, curated outputs and consumers. How should projects be organized to keep ownership and permissions manageable?
A: One project per engineer, so that each engineer has full control over the resources they personally created
B: Per-domain project sets (datasource, pipeline, curated) with the domain's owners and consumers as roles, plus a shared reference project
C: A single platform-wide project containing all five domains, with every dataset's permissions set individually by the engineer who created it
D: One project per dataset across all domains, which provides the finest-grained control possible
K: B
G: ## Projects by domain and layer
The exam guide asks for project structures that create appropriate boundaries. Two dimensions matter: domain (who owns it) and layer (who may see it).
## Organization
- Per domain: datasource (restricted), pipeline (engineers), curated (consumers).
- Shared reference data (calendars, currencies) in a common project with broad read.
- Roles assigned to groups by domain; lineage crosses projects via references.
Example: a consumer in the Logistics domain reads the Logistics curated project and the shared reference project, nothing else.
W: Domain-and-layer project sets with a shared reference project: ownership and audience are expressed by structure.
X: A=Per engineer: ownership should follow the business domain, not individuals who may leave.
C=One project, per-dataset permissions: unmanageable and error-prone at scale.
D=Per dataset: hundreds of projects with no structure; roles would have to be repeated on each one and nothing expresses domain or layer.
T: Organize projects by domain and layer, with shared reference data in a common project.
V: projects

@ PLTR-DE D6 T6.3 applied use-case
S: A dataset of employee records must be readable row-by-row only by each employee's own manager, and HR must see all rows. Which control expresses this?
A: Separate datasets per manager produced by the pipeline, plus a full dataset for HR, each in its own project
B: A restricted view with a policy granting a row when the viewer is the row's manager or a member of the HR group
C: A marking per manager applied to the whole dataset, so each manager must hold their own marking to open it
D: A Workshop filter defaulting to the manager's own team, with HR removing the filter when they need all rows
K: B
G: ## Attribute-based row policies
The exam guide covers restricted views for row-level access. A policy can compare row values with user attributes and combine with group membership.
## Policy
- `row.manager_id == user.id OR user in group:HR`.
- One dataset, one view, many audiences.
- Tested with a manager, a non-manager, and an HR user.
Example: a manager sees her 12 reports; an HR analyst sees all 4,000 rows; an engineer sees none.
W: Restricted view with manager-match-or-HR policy: row-level visibility for managers and full visibility for HR from one dataset.
X: A=Per-manager datasets: hundreds of datasets and projects to maintain; the view does this in one policy.
C=Marking per manager: markings are dataset-level; a manager would see all rows or none.
D=Workshop filter: a default filter is not access control; anyone can remove it.
T: Express per-user row visibility with restricted view policies that match row attributes to user attributes.
V: restricted views

@ PLTR-DE D6 T6.4 applied troubleshooting
S: A pipeline's build identity was granted a marking last month to read a sensitive source. A review asks whether the derived curated dataset is also marked. What should the data engineer verify and why?
A: Nothing; markings apply only to the original source dataset and never to datasets derived from it by transforms in other projects
B: That the curated dataset carries the marking, or was deliberately de-identified and reviewed, traced with lineage
C: That the build identity still holds the marking, which is all the review is concerned with
D: That the curated dataset is in the same project as the source, which makes marking unnecessary
K: B
G: ## Reviewing propagated sensitivity
The exam guide asks you to apply security throughout the lifecycle and to trace with lineage. A derived dataset containing the sensitive columns must be protected the same way; one that removes them can be unmarked after review.
## Verification
- Lineage from the source to the curated dataset.
- Does the curated dataset still contain the sensitive data? If yes, it must carry the marking.
- If de-identified, document the review that approved removing the marking.
Example: the curated dataset drops the national id but keeps the name and salary; the review concludes the marking still applies.
W: Verify marking on derived data via lineage, or a documented de-identification: sensitivity follows the data, and the review needs evidence either way.
X: A=Source only: derived data with the same columns is equally sensitive.
C=Identity only: the identity's access is one layer; the derived data's protection is another.
D=Same project: project membership does not substitute for a mandatory marking.
T: Derived datasets keep the sensitivity of their inputs unless deliberately de-identified and reviewed.
V: markings, Data Lineage

@ PLTR-DE D6 T6.1 applied use-case
S: A new user cannot see a project at all in the platform, although they have been added as a Viewer on it. Colleagues in the same team can see it. What is a likely cause?
A: The user has not refreshed their browser session since being added, and project visibility only updates after a full restart of the client
B: The user belongs to a different organization than the project, so the organization boundary blocks visibility regardless of role
C: Viewers cannot see projects; only Editors and Owners can
D: The project is too large to be displayed for new users until it is indexed
K: B
G: ## Organization boundaries
The exam guide lists organizations among the controls that combine with markings and roles. Organizations partition the platform: a project in one organization is not visible to users of another unless explicitly allowed, whatever role was assigned.
## Check
- Confirm the user's organization versus the project's.
- Check Access shows the organization requirement failing.
- Resolve through the organization's cross-organization sharing rules or by onboarding the user correctly.
Example: a contractor account created in a partner organization cannot see the internal project until the proper sharing is configured.
W: Organization mismatch: it makes a project invisible regardless of role, matching the symptom exactly.
X: A=Browser refresh: role grants take effect on the next request; a page that still shows nothing after a reload points to a real access condition.
C=Viewers cannot see: Viewer is precisely the role that grants read visibility.
D=Indexing size: project visibility is decided by organization and roles at request time; there is no indexing delay based on project size.
T: When a role is granted but the project is invisible, check the organization boundary.
V: organizations, Check Access

@ PLTR-DE D6 T6.2 applied tradeoff
S: A team proposes granting the "Everyone" group Viewer access to their curated project "to reduce access requests". What should the data engineer consider?
A: Agree without conditions, since curated data is by definition safe to share with the whole company
B: Evaluate sensitivity: broad read may suit non-sensitive curated data, markings and restricted views keep their controls, and the owner approves
C: Refuse, since no project should ever be readable by more than one team
D: Agree but remove all markings from the project's datasets first so that the broad Viewer access actually works for every dataset in it
K: B
G: ## Proportionate sharing
Least privilege does not mean maximal restriction; it means access matched to sensitivity and need. The exam guide asks for least privilege separately at each layer and for governed decisions.
## Considerations
- Classify the datasets: some curated data (reference tables, aggregates) is intended for broad use.
- Mandatory controls remain: markings and restricted views still apply to broad viewers.
- Owner approval and documentation of the decision.
Example: broad read is granted; the two marked datasets in the project remain readable only by marking holders.
W: Sensitivity-based decision with controls intact and owner approval: broad access where appropriate, nothing weakened.
X: A=Unconditional: curated describes how the data was prepared, not whether it is sensitive; salaries can be perfectly curated.
C=Never: reference tables and company-wide aggregates are meant for broad use; a blanket refusal blocks legitimate sharing.
D=Strip markings: removing mandatory controls to make sharing "work" is the exact failure the controls prevent.
T: Grant broad read only for data classified as non-sensitive, keeping markings and views in force.
V: projects, markings

@ PLTR-DE D6 T6.4 applied troubleshooting
S: After a dataset was moved from one project to another, a downstream team's scheduled build began failing with an access error. What happened?
A: Moving a dataset between projects deletes its transaction history, so the downstream build has no committed transaction to read from
B: The dataset now inherits the new project's roles; the build identity had access via the old project and needs a grant in the new one
C: Dataset moves are not supported and the dataset must be recreated in the original project
D: The downstream transform's code references the old project path and must be rewritten
K: B
G: ## Project moves change permissions
Roles are granted per project; a resource that moves takes on the destination's roles. The exam guide asks you to reason about which layer denies access.
## Fix
- Check Access for the build identity on the dataset in its new project: the role requirement fails.
- Grant the identity (or its group) Viewer on the new project, or move the dataset back if the move was wrong.
- Review other consumers of the moved dataset.
Example: the identity is added to the new project's viewer group and the build succeeds on rerun.
W: Role inheritance from the new project: the move changed the discretionary permissions, which the build identity no longer satisfies.
X: A=History deleted: moving a dataset changes its location and the roles that apply; its transactions and files are untouched.
C=Unsupported: moves are supported; permissions need attention.
D=Path in code: datasets are referenced by identity, not by project path.
T: Moving a dataset changes which project's roles apply; re-check consumer access after moves.
V: projects, Check Access

@ PLTR-DE D6 T6.3 advanced tradeoff
S: A restricted view is used for row-level access, but the team also needs a downstream transform to compute totals across all rows for an unrestricted aggregate dataset that everyone may see. How should this be designed?
A: Have the transform read the restricted view under the build identity and hope that the identity's policy row set happens to cover every row
B: Read the underlying dataset with a properly granted build identity, compute aggregates, and publish them unrestricted after a disclosure review
C: Have every user compute the totals themselves from the rows they can see
D: Remove the restricted view so the transform can read all rows, accepting that users will then see all rows too
K: B
G: ## Reading the full dataset for aggregates
The exam guide notes restricted views' limitations: they filter per reader. Aggregates over everything must come from the underlying data.
## Design
- Transform reads the full dataset with a properly granted build identity.
- Output: aggregates with no row-level data (checked for small-group disclosure risks).
- Publish without restriction if the aggregate is non-sensitive; otherwise with appropriate controls.
Example: the company-wide headcount per department is computed from the full dataset and shared broadly; individual rows stay behind the view.
W: Full-dataset read for aggregation with disclosure review: correct totals for everyone, row protection intact.
X: A=Read the view: the build identity's policy decides what it sees; totals would be partial or empty.
C=Users compute: each gets a subtotal of their own rows, not the org-wide total.
D=Remove the view: every user would then see every row, which breaks the row-level protection the view was created to provide.
T: Compute org-wide aggregates from the underlying dataset with a granted build identity, not from a restricted view.
V: restricted views, projects
