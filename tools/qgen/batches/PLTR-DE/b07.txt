# PLTR-DE batch 07: Domain 6 (Security, Projects, and Governance), 8 questions

@ PLTR-DE D6 T6.1 applied definition
S: A new data engineer asks how organizations, markings and project roles combine to decide whether a user can read a dataset. Which explanation is correct?
A: Any one of the three is sufficient: a user who holds a project role, or who holds the right marking, or who belongs to the organization can read the dataset
B: All controls must be satisfied: the organization boundary, every marking on the data, and a project role that grants read
C: Project roles override markings: an Owner of the project can read any dataset in it regardless of markings
D: Markings replace project roles: once a dataset carries a marking, roles no longer matter and only marking membership is checked
K: B
G: ## Three controls, all enforced
The exam guide asks you to understand how organizations, markings and project roles combine.
- **Organizations** partition the platform: resources and users belong to organizations, and cross-organization access is limited by design.
- **Markings** are mandatory access controls for sensitive data; a user must hold every marking on a resource to access it, whatever role they have.
- **Project roles** (viewer, editor, owner, and so on) are discretionary permissions granted within a project.
A user reads a dataset only if none of the controls denies them. That is why "give them Owner" does not fix a missing marking.
Example: an Owner of the Finance project who lacks the "Payroll" marking cannot open the payroll dataset in that project.
W: All controls must be satisfied: organization boundary, every marking, and a sufficient role; this is how the layers combine.
X: A=Any one suffices: markings and organizations are mandatory controls; a role alone never bypasses them.
C=Owner overrides markings: project roles are discretionary; they cannot override the mandatory marking control.
D=Markings replace roles: both apply; a user needs the marking and a role.
T: Organizations, markings and roles are layered; access requires passing all of them.
V: markings, projects, organizations

@ PLTR-DE D6 T6.2 applied use-case
S: A team is setting up Foundry resources for a new domain: raw source syncs, cleaning transforms, curated datasets backing object types, and Workshop applications. Several other teams will consume the curated data but must not see the raw sources. How should projects be structured?
A: One project for everything, with all datasets and apps together, so that lineage stays easy to follow and permissions are managed in one place
B: Separate projects for sources, transforms, Ontology outputs and applications, referenced across, so each layer has its own audience
C: One project per dataset, so that each resource has fully independent permissions
D: A project per consuming team, each containing a copy of the raw sources and the curated outputs that team needs
K: B
G: ## Projects as boundaries
The exam guide asks you to structure projects to create appropriate boundaries between sources, transforms, Ontology outputs and workflows. A project is the unit of role-based permissions, so layers with different audiences belong in different projects.
## A common layout
- Datasource project: syncs and raw data; access limited to the pipeline team.
- Transform project: cleaning and curation; pipeline team.
- Ontology / curated project: published datasets backing object types; readable by consuming teams.
- Application project: Workshop modules; end users.
Resources reference across projects so lineage is intact, and consumers see only the curated layer.
Example: a consuming analyst has viewer access to the curated project and none to the datasource project; lineage still shows where the data came from.
W: Layered projects with references: each layer gets its own audience and the raw sources are restricted, exactly the requirement.
X: A=One project: a single permission scope cannot restrict raw sources while exposing curated data to other teams.
C=Project per dataset: hundreds of projects with no shared structure; permissions become unmanageable and the layers are not expressed.
D=Project per consumer with copies: copies of raw data in consumer projects expose the sources and duplicate pipelines.
T: Separate projects by layer (sources, transforms, curated outputs, apps) so each has the right audience.
V: projects

@ PLTR-DE D6 T6.3 applied use-case
S: A sales dataset contains rows for all regions. Regional managers must each see only their own region's rows in the same dataset-backed object type, without maintaining separate datasets per region. What should be used?
A: A restricted view with a policy that filters rows by the user's region, used as the object type's backing
B: A marking per region applied to the whole dataset, so only managers holding the matching regional marking can open the dataset at all
C: A separate project per region containing a filtered copy of the dataset, maintained by the pipeline
D: A Workshop filter that defaults to the manager's region, which they can change if they need other regions
K: A
G: ## Row-level access with restricted views
The exam guide names restricted views for row-level access and asks you to understand their limitations. A **restricted view** sits on top of a dataset and applies policies that decide which rows each user can see, based on user attributes (group membership, organization) and row values.
## Using it
- Define the policy: a row is visible when its `region` matches the user's region group.
- Back the object type with the restricted view, so applications and queries inherit the filtering.
- One pipeline, one dataset, many audiences.
Limitations to remember: policies are evaluated on the view, not on the raw dataset; derived datasets built from the raw data are not filtered unless they also use the view; and some operations on restricted views have constraints.
Example: a manager in the EMEA group opens the same object type as a manager in APAC and sees only EMEA rows.
W: Restricted view with a region policy: it provides row-level access in a single dataset, which is the stated requirement.
X: B=Markings on the whole dataset: markings are dataset-level; a manager would see all rows or none.
C=Copies per region: this is the "separate datasets" approach the team wants to avoid, and raw data copies multiply maintenance.
D=Workshop default filter: a UI default is not access control; the manager can remove the filter and see all regions.
T: For row-level visibility within one dataset, use a restricted view with a user-attribute policy.
V: restricted views, Ontology

@ PLTR-DE D6 T6.4 applied troubleshooting
S: A pipeline build fails to read a source dataset. The data engineer confirms the executing identity has the Viewer role on the datasource project. What is the most likely remaining cause, and how should it be found?
A: The Viewer role is insufficient for builds; the identity must be made an Owner of the datasource project
B: A marking the executing identity lacks, or an organization boundary; Check Access on the dataset shows which requirement is unmet
C: The dataset is corrupted; it should be rebuilt by its owner
D: The build is running on an old version of the transform that still points at a previous dataset; stamping a new version will fix the access error
K: B
G: ## Diagnosing the exact layer
The exam guide asks you to diagnose access failures with Check Access and lineage rather than granting broad permissions, and to reason about each layer separately. A sufficient role but a failed read points to a mandatory control: a marking or an organization boundary.
## Check Access
- Shows, for a user or identity and a resource, which conditions pass and which fail (role, each marking, organization).
- The fix is specific: request the missing marking for the identity, or correct the organization setup.
Example: Check Access shows "Marking: Customer PII — not satisfied" for the build identity; the identity is added to that marking's membership and the build succeeds.
W: Marking or organization requirement unmet, found with Check Access: it is the remaining layer after a sufficient role, and Check Access names it.
X: A=Make it Owner: the role is not the problem, and Owner would not satisfy a marking anyway.
C=Corrupted dataset: an access failure is not a data integrity failure; other readers would see the same corruption.
D=Stamp a new version: versioning has nothing to do with access to inputs.
T: When the role is sufficient but access fails, check markings and organization boundaries with Check Access and request only what is missing.
V: Check Access, markings

@ PLTR-DE D6 T6.1 applied tradeoff
S: A dataset containing personal data must be processed by a pipeline and then published for analysts who are not allowed to see the personal columns. What is the correct governance pattern?
A: Mark the raw dataset and every derived dataset that still holds personal columns as PII, and publish an unmarked curated dataset without those columns
B: Apply the PII marking to the raw dataset only, since derived datasets are new resources whose sensitivity is decided independently of their inputs
C: Give analysts the PII marking so they can read the curated dataset, since the curated dataset is what they need
D: Publish the raw dataset to analysts with the personal columns hidden by a Workshop view that does not display them
K: A
G: ## Security through the data lifecycle
The exam guide asks you to apply security controls throughout the data lifecycle and least privilege separately to sources, pipeline execution, datasets, Ontology objects and consumers. Sensitivity follows the data: a derived dataset that still contains personal columns is as sensitive as its input.
## The pattern
- Raw and intermediate datasets with personal data carry the PII marking; only the pipeline identity and authorized engineers hold it.
- A curated output drops or de-identifies the personal columns; it carries no PII marking and lives in a project analysts can read.
- Lineage shows the relationship; Check Access confirms analysts cannot reach the marked datasets.
Example: `customers_raw` (marked PII) → `customers_curated` with hashed ids and no names (unmarked) → analysts.
W: Marking on every dataset that still holds personal data and a de-identified output for analysts: least privilege at each layer, with the sensitive data never exposed.
X: B=Mark the raw only: an intermediate dataset with the same personal columns would be unprotected.
C=Give analysts the marking: this grants access to personal data they are not allowed to see, defeating the control.
D=Hide columns in Workshop: the columns are still in the dataset; any other tool or query exposes them.
T: Sensitivity follows the data through derived datasets; publish a de-identified output for audiences that must not see personal data.
V: markings, projects

@ PLTR-DE D6 T6.4 applied troubleshooting
S: An application user can open a dataset-backed object type and see objects, but a particular property is always empty for them while colleagues see values. The pipeline and dataset are healthy. What should the data engineer check?
A: Whether a column- or row-level policy on the backing dataset or restricted view hides that column for this user, via Check Access
B: Whether the user's browser is caching an older version of the application module, since empty properties are usually a display problem on the client side
C: Whether the pipeline dropped the column for some rows, since a healthy build can still produce nulls
D: Whether the object type needs to be re-indexed, since indexing lag shows up as missing property values
K: A
G: ## Reading permission at the property level
The exam guide's practice scenario family includes a user who cannot see a field the pipeline can read, with the direction to check consumer-facing permissions separately from pipeline permissions. When one user sees an empty property and colleagues do not, the difference is in that user's access, not in the data.
## Where to look
- Restricted view policies: column or row restrictions keyed on user attributes.
- Property-level permissions configured on the Ontology.
- Check Access for the user on the backing dataset or view.
Example: the backing restricted view hides the `salary` column for users outside the HR group; the user is not in the group, so the property shows empty.
W: Column- or row-level policy for that user: the symptom is user-specific while the data is fine, which is exactly what a consumer-side restriction looks like.
X: B=Browser cache: a cache would not selectively blank one property for one user while colleagues see it.
C=Pipeline nulls: colleagues see values for the same rows, so the column is populated.
D=Indexing lag: lag affects all users equally; it does not vary by who is looking.
T: A property empty for one user but visible to others is a consumer-side permission, found through policies and Check Access.
V: restricted views, Check Access

@ PLTR-DE D6 T6.2 applied use-case
S: An engineer needs to debug a transform that reads a marked dataset, but holds neither the marking nor access to the datasource project. The engineer proposes to export the data to a personal folder to work on it. What should happen instead?
A: Approve the export to the personal folder, since the engineer genuinely needs the data to fix the bug and a personal folder is private to its owner
B: Request the marking through its approval process, or debug with a reviewed de-identified sample, keeping the data governed
C: Ask a colleague who holds the marking to copy the dataset into an unmarked project for the engineer
D: Remove the marking temporarily for the duration of the debugging and restore it afterwards
K: B
G: ## Access requests, not workarounds
Markings exist to keep sensitive data within an approved audience. Moving the data to a personal folder, copying it to an unmarked project or removing the marking all defeat the control; they are the "grant broad access" and "copy data" anti-patterns the exam guide warns against.
## The right path
- Request the marking (with justification) through its approval process.
- If access is not appropriate, work with someone who holds it, on a branch, or with a de-identified sample dataset produced and reviewed deliberately.
- Keep everything inside governed projects so lineage and audit remain intact.
Example: the marking is approved for two weeks for the engineer; the bug is fixed on a branch; the access expires.
W: Governed access request or de-identified sample: the engineer can do the work without taking sensitive data out of its controls.
X: A=Personal export: it moves protected data out of governance; "private folder" is not a security control.
C=Colleague's copy: a copy into an unmarked project is the same violation done by someone else.
D=Remove the marking: every other user without the marking would gain access during that window.
T: Never move or unmark sensitive data to make work easier; request the access or use a governed sample.
V: markings, projects

@ PLTR-DE D6 T6.3 applied troubleshooting
S: After introducing a restricted view to filter rows by region, a downstream transform that reads the view returns far fewer rows than expected when it runs, and a different count when a developer previews it. What explains this?
A: Restricted views filter by the reading identity, so the build identity and the developer see different rows; the transform should read the right source
B: The restricted view is corrupted and must be recreated before the transform can read all rows
C: The transform's cache is stale; clearing the developer's preview cache will align the counts
D: Restricted views always return a random sample of the rows to protect privacy, which is why the counts vary from one read to the next
K: A
G: ## Policies follow the reader
A restricted view returns the rows its policy allows for the identity that reads it. The exam guide asks you to understand restricted views' limitations; one is that they are not a filtered copy with fixed contents: a build reads them as the build's identity, a developer as themselves.
## Consequences for pipelines
- A transform that needs all rows should read the underlying dataset (with the appropriate permissions), not the view.
- A transform that intentionally produces a per-audience output must be designed with the identity in mind.
- Previews run as the developer; builds run as the build identity; counts differ by design.
Example: the developer in the EMEA group previews 40,000 rows; the build identity with no region groups reads 0; the transform is repointed to the full dataset.
W: Identity-dependent policy evaluation: it explains both the small build result and the different preview count, and points to the correct design choice.
X: B=Corrupted view: the behaviour is by design, not a defect; recreating the view would produce exactly the same identity-dependent counts.
C=Preview cache: the counts differ because the identities differ; clearing a cache cannot change what a policy allows an identity to read.
D=Random sampling: restricted views filter deterministically by policy; the same identity always gets the same rows, so sampling is not involved.
T: Restricted views filter per reader; pipelines that need the full data must read the underlying dataset with proper permissions.
V: restricted views
