@ PLTR-DE D2 T2.2 applied use-case
S: A dataset has one row per sensor reading with a timestamp. The business wants, per sensor, the difference between each reading and the previous reading. Which transformation construct is appropriate?
A: A self-join of the dataset to itself on sensor id, which pairs every reading with every other reading of the same sensor for comparison
B: A window function partitioned by sensor and ordered by timestamp that provides the previous reading (lag) so the difference is computed per row
C: A group-by aggregation on sensor id that returns the minimum and maximum readings, from which the differences can be inferred
D: A Python loop over the rows collected to the driver that keeps the previous reading in a variable and writes the difference out
K: B
G: ## Window functions for ordered, per-group computations
The exam guide lists expressions and aggregations among transformation operations; "previous row within a group" is the classic window case.
## Pattern
- Partition by `sensor_id`, order by `timestamp`.
- `lag(reading)` gives the previous reading; subtract.
- Runs distributed; no cross-product; no driver collection.
Example: 400 million readings processed in minutes; each row carries `delta = reading − previous_reading`.
W: Partitioned, ordered window with lag: the exact construct for per-group sequential differences at scale.
X: A=Self-join: pairs each reading with all others of the sensor, an enormous cross-product, and still needs filtering to the previous one.
C=Group-by min/max: loses the per-row sequence; the difference between consecutive readings cannot be derived from extremes.
D=Driver loop: collects the whole dataset to one node and fails at scale.
T: Use window functions for computations that depend on row order within a group.
V: Pipeline Builder, Code Repositories

@ PLTR-DE D2 T2.1 applied tradeoff
S: An analyst built a working transformation in a Contour analysis and wants it to become a scheduled production dataset consumed by other teams. What should the data engineer do?
A: Schedule the Contour analysis to refresh nightly and point the consuming teams at its result, since the logic is already proven correct
B: Re-implement it as a governed pipeline with expectations, lineage and a schedule, using the Contour analysis as the specification
C: Export the analysis result to a spreadsheet each night and upload it as the production dataset
D: Tell the consumers to rerun the Contour analysis themselves whenever they need fresh data
K: B
G: ## From exploration to production
Analysis tools are for exploration; production datasets need governed pipelines. The exam guide asks you to choose authoring tools by purpose and to build maintainable, tested transformations.
## Steps
- Treat the analysis as the specification: logic, filters, joins.
- Implement in Pipeline Builder or code with expectations.
- Validate: compare the pipeline output with the analysis result on the same input.
- Schedule; register lineage; hand to consumers with a contract.
Example: the pipeline reproduces the analyst's numbers exactly on last month's data and runs nightly thereafter.
W: Re-implementation as a governed pipeline validated against the analysis: production quality with the analyst's logic preserved.
X: A=Schedule the analysis: exploration tools lack the testing, lineage and operational controls of pipelines.
C=Spreadsheet export: a manual nightly export is fragile, breaks the first time someone is away, and has no lineage or expectations.
D=Rerun themselves: each consumer re-running an analysis by hand produces inconsistent results and is not a production dataset at all.
T: Promote exploratory logic to production by re-implementing it as a tested, scheduled pipeline.
V: Pipeline Builder, Contour

@ PLTR-DE D2 T2.3 applied troubleshooting
S: A Spark transform processes a 2 TB input, but one stage spends most of its time on a single task while the others finish quickly. What is the likely cause and remedy?
A: Insufficient executors overall; the fix is to double the executor count so that every stage, including the slow one, finishes sooner
B: Data skew on a join or group key; repartition or salt the hot key, or broadcast a small side, confirmed in Spark details
C: A slow disk on one node; the fix is to request new hardware from the platform team
D: Too many input files; the fix is to delete the smallest files from the input dataset
K: B
G: ## Recognizing skew
The exam guide asks you to distinguish data skew from resource limits and code inefficiency using Spark details. One long task among many short ones is the signature of skew: one partition carries far more data.
## Remedy
- Identify the hot key (a null id, a default value, one huge customer).
- Salt the key to spread it, or handle the hot key separately.
- Broadcast join if the other side is small.
- Verify in Spark details that task durations even out.
Example: 60% of rows have `customer_id = null`; filtering nulls into a separate branch and salting the remainder balances the stage.
W: Skew on a hot key with repartition or salting: the evidence matches skew exactly, and the fix targets the distribution.
X: A=More executors: the long task still runs on one executor; adding others does not split it.
C=Slow disk: one consistently slow task across runs is data, not hardware.
D=Delete files: destroys data and does not touch the key distribution.
T: One straggler task means skew; fix the key distribution, not the cluster size.
V: Spark Details, Code Repositories

@ PLTR-DE D2 T2.2 applied use-case
S: A pipeline must enrich each customer with the latest known address from a change-history table that holds every address a customer has ever had, with effective dates. Which transformation produces the correct "current address"?
A: An inner join of customers to the history table on customer id, which attaches the address
B: A window ranking addresses per customer by effective date, keeping the latest, then a left join of customers to that dataset
C: A group-by on customer id selecting the maximum address string, which returns the latest alphabetically
D: A join on customer id and the current date, which matches the address row whose effective date equals today
K: B
G: ## Deriving current state from history
The exam guide expects correct join and aggregation choices and awareness of cardinality. A history table has many rows per customer; joining it directly multiplies rows.
## Pattern
- Rank history rows per customer by effective date (and a tie-breaker).
- Keep the latest; this dataset has one row per customer.
- Left join customers to it so customers with no address still appear.
Example: a customer with five historical addresses gets exactly the one effective since March.
W: Latest-per-customer via window ranking, then left join: the correct current-state derivation with one row per customer.
X: A=Direct inner join: duplicates customers per address and drops customers without any address row.
C=Max of the string: alphabetical maximum has nothing to do with recency.
D=Join on today's date: effective dates rarely equal today; most customers would match nothing.
T: Turn history into current state with a per-key ranking by effective date before joining.
V: Pipeline Builder, Code Repositories

@ PLTR-DE D2 T2.4 applied use-case
S: A code transform's output must satisfy a contract that downstream teams rely on: specific columns, types and no nulls in keys. How should the contract be enforced in the pipeline?
A: A detailed comment at the top of the transform describing the contract for other engineers to read before they change anything
B: Schema expectations (columns, types) and non-null key expectations on the output that fail the build, with the contract documented
C: A monthly review meeting where downstream teams confirm the output still looks right
D: A unit test that checks the transform's code compiles, which guarantees the output shape
K: B
G: ## Contracts as enforced expectations
The exam guide asks you to publish datasets with clear contracts and to use expectations to block invalid data. A contract that is only written down is a wish; one that is checked at build time is a guarantee.
## Implementation
- Schema expectation: exact columns and types.
- Key expectations: non-null, unique.
- Documentation: the dataset description states the contract and its guarantees.
- Change management: contract changes go through branches and consumer communication.
Example: a refactor accidentally renames `order_id`; the schema expectation fails the build before any consumer sees it.
W: Build-time schema and key expectations with documentation: the contract is enforced, not merely described.
X: A=Comment: a comment informs whoever reads it; nothing checks the output, so a careless change still breaks consumers.
C=Monthly meeting: a contract violation introduced on day one is discovered up to a month later, after consumers have been affected.
D=Compiles: compilation says nothing about output columns or nulls.
T: Enforce data contracts with schema and key expectations that fail the build.
V: expectations

@ PLTR-DE D2 T2.3 applied tradeoff
S: A transform's input is 200 GB today and expected to reach 5 TB within a year. It currently runs on a lightweight single-node engine and is close to its memory limit. What should be planned?
A: Keep the lightweight engine and request progressively larger single nodes as the data grows, since single-node processing is simpler to maintain
B: Migrate the transform to a distributed engine (Spark) now, validating output equivalence on a branch, so the pipeline scales with the projected growth
C: Sample the input to 10% permanently so that the lightweight engine always has enough memory
D: Split the input into 25 separate datasets of 200 GB each and run 25 copies of the lightweight transform
K: B
G: ## Planning for scale
The exam guide asks you to choose engines by scale and growth. A workload at the edge of single-node memory with 25× growth ahead needs distribution; waiting for failure is not a plan.
## Migration
- Re-express the logic for Spark (often minor for dataframe code).
- Branch validation: identical output on today's input.
- Partitioning and resource settings tuned with Spark details.
Example: the migrated transform processes today's 200 GB in 8 minutes and scales linearly as data grows.
W: Proactive migration to a distributed engine with equivalence validation: the pipeline is ready for the growth instead of failing into it.
X: A=Bigger nodes: vertical scaling hits a ceiling well before 5 TB.
C=Permanent sampling: the output becomes an estimate; most requirements cannot accept that.
D=25 copies: a manual sharding scheme that reinvents distribution badly and breaks any cross-partition logic.
T: When growth will exceed a single node, migrate to a distributed engine before it fails.
V: Code Repositories, Spark

@ PLTR-DE D2 T2.4 applied troubleshooting
S: A transform occasionally produces slightly different outputs on identical inputs: row order varies and a "first value per group" column changes. Downstream equality checks fail intermittently. What is the cause and fix?
A: A platform bug; open a support ticket and wait for a fix before running the transform again
B: Non-deterministic logic: "first" without explicit ordering depends on partitioning; add a sort key with a tie-breaker to ordered selections
C: Insufficient executor memory causing some rows to be dropped at random during the shuffle, fixed by increasing memory per executor
D: The input changing between runs, fixed by snapshotting the input before each run
K: B
G: ## Determinism in distributed transforms
In a distributed engine, row order within a partition is not guaranteed between runs. "First", "last" or "head" without an explicit order are non-deterministic. The exam guide asks for correct, testable transforms; non-determinism breaks both equality tests and consumer trust.
## Fix
- Define "first" by an ordering: window ordered by timestamp with a tie-breaker (id).
- Never depend on output row order; consumers should sort if they need order.
- Add a test that runs the transform twice and compares outputs.
Example: "first status per order" becomes "status at the earliest timestamp, ties broken by event id"; outputs are identical across runs.
W: Explicit ordering for every ordered selection: determinism is restored and the equality checks pass.
X: A=Platform bug: unordered "first" is expected behaviour in distributed processing, not a defect.
C=Memory: dropped rows would change counts, not just the chosen first value.
D=Input changing: the inputs are stated to be identical; the variance is in the logic.
T: Make distributed transforms deterministic by giving every ordered operation an explicit sort key.
V: Code Repositories

@ PLTR-DE D2 T2.1 advanced tradeoff
S: A pipeline mixes three concerns in one transform: parsing a messy source, applying business rules, and producing an Ontology-ready dataset. Changes are risky and reviews are slow. How should it be restructured?
A: Keep one transform but add many comments so that reviewers can follow the three concerns within it
B: Split into staged transforms with contracts: parsing to a typed dataset, business rules to curated data, Ontology shaping, each with expectations
C: Move all three concerns into a single Pipeline Builder pipeline with no intermediate datasets so that there is only one place to look
D: Duplicate the transform per consuming team so each team can edit its own copy without affecting the others
K: B
G: ## Staging and separation of concerns
The exam guide asks for maintainable transformations and clear contracts between stages (Ingest → Validate → Transform → Publish → Expose). One transform doing everything hides the contracts and couples unrelated changes.
## Structure
- Stage 1: parse and type; expectations on schema and nulls.
- Stage 2: business rules; expectations on rule outcomes.
- Stage 3: Ontology shaping (keys, links); key expectations.
- Each stage is reviewable and testable on its own; lineage shows the chain.
Example: a parsing change no longer risks the business rules; the rules stage is reviewed by the domain owner alone.
W: Staged transforms with contracts and expectations: changes become local, reviews become focused, and failures are caught at the stage that caused them.
X: A=Comments: readability improves slightly but the three concerns stay coupled in one build, so a change to any of them still risks all three.
C=One pipeline, no intermediates: removes the boundaries that make the pipeline reviewable.
D=Per-team copies: divergent logic and duplicated maintenance.
T: Separate parsing, rules and Ontology shaping into staged transforms with their own contracts.
V: Pipeline Builder, Code Repositories, expectations
