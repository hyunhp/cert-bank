# PLTR-DE batch 49: Domain 8 round 6 (AI-Assisted Data Engineering), 8 questions

@ PLTR-DE D8 T8.1 applied use-case
S: A data engineer wants help writing a complex window-function transform but needs the result to be correct on real data. Which workflow uses AI assistance appropriately?
A: Ask a code assistant for the transform and merge it directly, since assistants are trained on large amounts of correct window-function code
B: Use a code assistant to draft the transform, then review it, add unit tests on edge cases, and compare a branch build against expectations
C: Avoid AI assistance entirely, since generated code can never be trusted for data transformations of any kind
D: Ask an LLM transform inside the pipeline to compute the window values for each row at runtime instead of writing code
K: B
G: ## Assistants draft; engineers verify
The exam guide asks engineers to use code assistants and review their output for incorrect assumptions. Window logic is easy to get subtly wrong (frame boundaries, ordering ties).
## Workflow
- Assistant drafts the transform.
- Review: partitioning, ordering, frame, tie-breaking.
- Unit tests on edge cases; branch build compared with expected results.
Example: the draft used a rows frame where a range frame was needed; a unit test with missing days catches it.
W: Assistant-drafted, engineer-verified code with tests and branch comparison: faster authoring with correctness established on real data.
X: A=Merge directly: subtle frame or ordering errors go straight to production.
C=Avoid entirely: forgoes a real productivity gain in drafting when review and tests already manage the risk of generated code.
D=LLM per row at runtime: nondeterministic, expensive and the wrong tool for deterministic arithmetic.
T: Use code assistants to draft transforms and verify them with review, tests and branch comparison.

@ PLTR-DE D8 T8.2 applied troubleshooting
S: An LLM extraction transform shows a slowly rising share of rows with empty outputs over several weeks, while schema checks pass. What should the engineer investigate?
A: Nothing, since empty outputs are valid strings and therefore pass every check in the pipeline
B: Whether inputs or the model changed; sample empty rows, read traces and raw responses, and add an empty-rate check
C: Whether the dataset's storage is running out, since empty outputs indicate the platform could not write values
D: Whether the prompt is too short, and if so make it much longer without examining any failing rows
K: B
G: ## Silent degradation in AI steps
The exam guide pairs AI processing with quality checks and traces. A rising empty rate is a content-quality signal that schema checks cannot see.
## Investigation
- Sample empty rows; read raw responses and inputs.
- Causes: new input formats, truncation at context limits, model version changes.
- Add a health check on empty-output rate with an alert.
Example: a new supplier's invoices are scanned images; the text step returns nothing; routing them to a vision step fixes it.
W: Sample, trace and monitor the empty rate: the cause of the degradation is found and future drift becomes visible.
X: A=Valid strings: an empty extraction is a failure to extract, whatever its type.
C=Storage: storage problems fail writes; they do not produce empty strings.
D=Longer prompt blindly: guesses at a fix without understanding which inputs fail.
T: Monitor AI output content rates such as emptiness, and investigate drift with traces and samples.
V: Pipeline Builder, Data Health

@ PLTR-DE D8 T8.3 applied use-case
S: A team wants to classify incoming support tickets into categories for routing. Volume is 20,000 tickets a day and categories must be available within minutes of a ticket's creation. Which placement and design fit?
A: An agent that classifies each ticket only when a support worker opens it, so the classification is always as current as possible
B: An event-driven step classifying each new ticket into validated categories, stored as a property for routing
C: A nightly batch classifying the day's tickets, so routing happens the next morning
D: A manual classification queue where support staff categorize each ticket before routing
K: B
G: ## Pipeline-layer AI for routing
The exam guide places reusable, per-item enrichment in the pipeline layer. Routing needs the category on every ticket within minutes, not on view.
## Design
- Trigger on new tickets (or incremental runs every few minutes).
- Structured output limited to allowed categories; validation; low-confidence routed to a general queue.
- Property used by routing rules and reports.
Example: a ticket created at 10:02 is categorized and routed by 10:04.
W: Event-driven classification with validated categories stored as a property: every ticket is routed promptly and the category is reusable.
X: A=Classify on open: routing needs the category before anyone opens the ticket.
C=Nightly batch: misses the minutes-level requirement by hours.
D=Manual queue: categorizing 20,000 tickets a day by hand is the workload the AI step was meant to remove, and far too slow for minutes-level routing.
T: Put per-item AI classification needed for routing in event-driven pipeline steps.
V: Automate, Pipeline Builder

@ PLTR-DE D8 T8.4 applied use-case
S: A code assistant proposes replacing a well-tested deduplication transform with a "simpler" version. What should the engineer require before accepting it?
A: Nothing, because simpler code is always better, and the assistant has already reviewed the original logic and its tests in detail
B: Proof of equivalence: existing tests pass, branch output matches production by key, and edge cases agree
C: A promise from the assistant that the new version is equivalent
D: Approval from a stakeholder who does not read code but likes simpler solutions
K: B
G: ## Refactoring requires equivalence evidence
The exam guide asks for review of AI-generated changes and validation against regressions. "Simpler" must also mean "same output".
## Evidence
- Existing tests pass.
- Branch output identical to production by key and count.
- Edge cases (ties on timestamp, null keys) explicitly checked.
Example: the simpler version picks a different row on ties; the comparison catches it and a tie-breaker is added.
W: Tests plus branch comparison and edge-case checks: the refactor is accepted only when it provably produces the same output.
X: A=Simpler is better: simplicity that changes results is a regression.
C=Assistant's promise: a model's assurance that two versions are equivalent is not evidence; only tests and output comparison are.
D=Non-technical approval: a stakeholder who does not read code cannot judge whether the new version produces the same output.
T: Accept AI-proposed refactors only with evidence of output equivalence.
V: Code Repositories, branches

@ PLTR-DE D8 T8.2 applied comparison
S: Which output configuration for an LLM transform best supports downstream joins on the extracted field?
A: Free-text output that downstream transforms parse with string matching before joining
B: A typed field normalized to the join key format and validated against the reference dataset it joins to
C: An output that includes the field inside a natural sentence such as "The supplier mentioned here is ACME Corp." for readability
D: A numeric confidence score only, from which the field can be inferred later
K: B
G: ## Join-ready AI outputs
The exam guide asks for structured outputs and deterministic post-processing. A field used as a join key must match the key format exactly.
## Configuration
- Schema: typed field; normalization rules (case, punctuation, id format).
- Validation: the value exists in the reference dataset; otherwise flagged.
- Unmatched rows routed to review.
Example: extracted supplier ids join to the supplier dataset with a 98% match rate; the rest are reviewed.
W: Typed, normalized, reference-validated output: the extracted field can be joined reliably and mismatches are visible.
X: A=Free text parsed downstream: fragile and inconsistent across consumers.
C=Field inside a sentence: requires parsing and invites errors.
D=Confidence only: a score says how sure the model was but carries no supplier value, so there is nothing to join on.
T: Make AI-extracted join keys typed, normalized and validated against their reference.
V: Pipeline Builder, expectations

@ PLTR-DE D8 T8.3 applied tradeoff
S: An LLM enrichment step is accurate but costly. The team notices that 60% of inputs are near-identical boilerplate texts. What optimization preserves quality while reducing cost?
A: Switch to the cheapest available model for all rows without evaluating whether quality is still acceptable
B: Normalize inputs, cache results by normalized content and prompt version, and call the model only on misses
C: Process only a random 40% of rows each night and leave the others without an enrichment value
D: Remove the enrichment entirely because the cost cannot be justified for any of the rows
K: B
G: ## Caching repeated inputs
The exam guide lists caching among AI processing controls. Near-identical boilerplate is the ideal cache candidate once normalized.
## Design
- Normalize text (whitespace, dates, ids masked) to a canonical form.
- Cache key: hash of canonical text plus prompt version and model.
- Model calls only for cache misses; cache invalidated on version change.
Example: calls fall by 58% with identical outputs on the evaluation set.
W: Normalized-content caching with version-aware keys: repeated boilerplate is enriched once and reused, with no loss of quality.
X: A=Cheapest model blindly: may degrade quality without measuring it.
C=Random 40%: three in five rows never receive the enrichment, so consumers get incomplete data every night.
D=Remove: throws away an accurate, valuable enrichment when the cost problem has a direct, lossless fix.
T: Cache AI results on normalized inputs to avoid paying repeatedly for identical work.

@ PLTR-DE D8 T8.4 applied troubleshooting
S: A code assistant generated a transform that reads an entire upstream dataset every run, although the upstream is append-only and the transform only needs new rows. The pipeline is slow and expensive. What should the engineer change?
A: Accept the full read, since code generated by an assistant can be assumed to be optimal for the platform it targets
B: Rewrite it as incremental over the append-only input, validated on a branch for identical results
C: Increase the number of executors so the full read finishes faster each night
D: Reduce the upstream dataset by deleting old rows so that the full read is smaller
K: B
G: ## Reviewing generated code for efficiency
The exam guide asks engineers to review AI-generated code for inefficient patterns. A full read of an append-only input is a classic missed optimization.
## Change
- Incremental transform over APPEND transactions.
- Branch validation: same results on the new data; fallback behaviour understood.
- Runtime and cost compared before and after.
Example: nightly runtime falls from 50 minutes to 3 with identical outputs.
W: Incremental processing over the append-only input: the generated inefficiency is removed and correctness is confirmed on a branch.
X: A=Generated is optimal: generated code often ignores platform-specific optimizations.
C=More executors: pays more to repeat unnecessary work faster.
D=Delete old rows: destroys history to compensate for inefficient code.
T: Review generated transforms for missed incremental opportunities and other platform-specific optimizations.
V: Code Repositories, incremental transforms

@ PLTR-DE D8 T8.1 advanced tradeoff
S: A manager proposes that an AI agent should automatically create new pipelines whenever a business user asks for a dataset in chat. What should the data engineer advise?
A: Agree, since automatically generated pipelines will reduce the backlog of data requests immediately
B: Let the AI draft a proposal for engineering review, with branch validation, ownership and governance before publishing
C: Refuse to use AI anywhere in the data request process
D: Agree but only for requests that involve sensitive data, since those are the most urgent
K: B
G: ## AI-assisted, human-governed pipelines
The exam guide asks for AI to assist data engineering while engineers own correctness, governance and operations. Unreviewed auto-created pipelines bypass every control.
## Process
- AI drafts: proposed sources, transform logic, expectations, schedule.
- Engineer reviews: permissions, sensitivity, contracts, cost.
- Branch validation; ownership and monitoring before publication.
Example: request-to-draft time drops from days to minutes; a review catches a draft that would have exposed marked data.
W: AI drafts with engineering review and governance before publication: faster delivery without uncontrolled pipelines.
X: A=Auto-create: unreviewed pipelines with unknown correctness, permissions and cost.
C=Refuse AI: rejects a real speed-up in drafting pipelines when review and governance already control the risk.
D=Sensitive data first: removes review precisely where a mistake would expose protected data; the riskiest possible choice.
T: Use AI to draft pipelines for engineering review, never to publish them unreviewed.
