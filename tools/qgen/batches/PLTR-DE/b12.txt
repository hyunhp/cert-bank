# PLTR-DE batch 12: Domain 3 round 2 (Pipeline Processing Modes), 8 questions

@ PLTR-DE D3 T3.1 applied tradeoff
S: A dashboard needs hourly refresh of metrics computed over a 10 TB event history that grows by 50 GB a day. Which processing mode keeps cost reasonable while meeting the hourly need?
A: Full batch every hour, recomputing the entire 10 TB history on each run, since the dashboard must be refreshed hourly and batch is simplest
B: Incremental processing of each hour's new events into running aggregates, with a periodic full recompute to reconcile
C: Streaming, since the only way to refresh hourly is to process events as they arrive
D: Daily batch, telling the business that hourly refresh is not possible at this scale
K: B
G: ## Incremental for large, growing inputs
The exam guide asks you to choose from latency, volume, growth, complexity and cost. Hourly freshness on a 10 TB history with append-only growth is the case for incremental: each run touches 2 GB of new events, not 10 TB.
## Design
- Running aggregates updated per hour; stored state per metric key.
- Periodic full recompute (weekly) to correct any drift and absorb late or corrected events.
- Monitoring on transaction types to catch fallback runs.
Example: hourly runs finish in minutes at a fraction of the full-batch cost; the dashboard is at most an hour stale.
W: Hourly incremental with periodic reconciliation: it meets the latency at proportional cost, which is the purpose of incremental processing.
X: A=Hourly full batch: 24 full passes over 10 TB a day is enormously expensive for an hourly refresh.
C=Streaming: the requirement is hourly, not seconds; streaming adds state and operational complexity for no benefit.
D=Daily batch: it declines a requirement that incremental can meet.
T: Large, append-only inputs with sub-daily freshness needs are handled incrementally, with periodic full reconciliation.
V: incremental transforms

@ PLTR-DE D3 T3.2 applied troubleshooting
S: A transform's output dataset shows a history of UPDATE transactions rather than APPEND, although the transform is meant to add new daily files. Downstream incremental transforms are falling back to full recompute every day. What should be checked?
A: Whether the downstream transforms have enough executor memory, since a fallback to full recompute is usually caused by a resource shortage
B: How the transform writes its output: UPDATE (replacing files) instead of APPEND; change it to write new files only
C: Whether the dataset's schema has changed, since schema changes always produce UPDATE transactions
D: Whether the schedule runs too often, since frequent runs generate UPDATE transactions
K: B
G: ## Output transaction type matters downstream
The exam guide asks you to understand SNAPSHOT, APPEND, UPDATE and DELETE and why incremental transforms fall back. A transform that rewrites or replaces files writes UPDATE (or SNAPSHOT); downstream incremental consumers cannot know what is new and recompute fully.
## Fix
- Inspect the transform's write configuration: does it overwrite an existing file name, or write a new file per run?
- Change to append-only output: new, uniquely named files per run, no modification of previous files.
- Verify the transaction history shows APPEND afterwards and downstream runs incrementally.
Example: the transform wrote `latest.parquet` every day (UPDATE); switching to `part-YYYYMMDD.parquet` produces APPEND and downstream fallbacks stop.
W: Output written as UPDATE instead of APPEND: this is why downstream falls back daily; writing new files only fixes it.
X: A=Memory: fallback is about transaction semantics, not resources.
C=Schema change: a schema change is not what produces a daily UPDATE; the write pattern is.
D=Schedule frequency: frequency changes how often transactions occur, not their type.
T: An incremental pipeline is only as incremental as its weakest link; make each transform write APPEND transactions.
V: transactions, incremental transforms

@ PLTR-DE D3 T3.4 applied use-case
S: A streaming pipeline failed for three hours overnight and the input stream retained the messages. After the fix, how should the gap be handled?
A: Ignore the three hours, since streaming data is only valuable in real time
B: Replay the retained messages from the last processed offset, with idempotent processing so twice-processed messages do not duplicate
C: Restart the pipeline from the latest message and backfill the three-hour gap manually from a spreadsheet exported by the source team
D: Convert the pipeline to batch to avoid gaps in future
K: B
G: ## Replay after failure
The exam guide lists replay among streaming concerns. Streams retain messages for a period; a consumer can resume from its last committed offset, processing what it missed.
## Safe replay
- Resume from the checkpoint; the pipeline processes the backlog, then catches up to real time.
- Idempotency: output keyed so that reprocessed messages (around the checkpoint) do not create duplicates.
- Monitor lag until it returns to zero.
- Verify completeness against source counts for the window.
Example: 1.2 million retained messages are replayed in 20 minutes; the aggregated output for the gap matches the expected totals.
W: Replay from the last offset with idempotent processing: the gap is filled correctly and without duplicates.
X: A=Ignore: three hours of missing data corrupt aggregates and downstream objects.
C=Manual backfill: the stream already has the data; a spreadsheet is slower, error-prone and ungoverned.
D=Convert to batch: failures happen in batch too; the answer to a failure is recovery, not changing modes.
T: After a streaming outage, replay from the checkpoint with idempotent processing.
V: streaming

@ PLTR-DE D3 T3.1 applied comparison
S: Which description correctly pairs a requirement with the appropriate processing mode?
A: Nightly report on yesterday's sales: streaming; alert within seconds on a sensor threshold: nightly batch; small lookup table: full Spark batch
B: Nightly sales report: batch or incremental; seconds-level sensor alert: streaming; small daily lookup from two 5 MB files: lightweight
C: Every requirement: streaming, since it is the most capable mode
D: Every requirement: full batch, since it is the simplest mode
K: B
G: ## Mode per requirement
The exam guide's core decision is batch, incremental, streaming or lightweight, chosen by freshness, volume, growth, source behaviour, complexity and cost.
- Nightly report: daily freshness, so batch (or incremental if the input appends and history is large).
- Alert in seconds: continuous requirement, so streaming.
- Tiny daily lookup: small input where startup dominates, so lightweight.
Example: a company runs all three side by side; each pipeline uses the mode its requirement needs.
W: Batch/incremental for nightly, streaming for seconds, lightweight for tiny: each pairing follows the decision criteria.
X: A=Swapped: a nightly report does not need streaming, and a seconds-level alert cannot be served by nightly batch.
C=Everything streaming: streaming for a nightly report adds complexity and cost with no benefit.
D=Everything full batch: batch cannot deliver seconds-level alerts and wastes compute on large histories.
T: Match the mode to each requirement; no single mode fits all.
V: Pipeline Builder, streaming

@ PLTR-DE D3 T3.4 applied troubleshooting
S: An incremental transform maintains a running total per account. After an upstream correction was delivered as an UPDATE transaction, the totals for some accounts are now wrong even though the transform ran successfully. Why, and what should be done?
A: The transform is bugged in its arithmetic; rewrite the sum logic
B: The fallback recompute was combined with the old running-total state, double counting; make state fallback-aware and recompute the totals
C: The UPDATE should have been rejected by a build-blocking expectation on the input; add one now and ignore the totals that are already wrong
D: Running totals cannot be computed incrementally; switch to daily full batch forever
K: B
G: ## State and fallback must agree
Incremental transforms that keep state (running totals) must handle fallback correctly: a full recompute replaces the history, so prior state must not be added again. The exam guide asks you to handle state and fallback safely.
## Fix
- Detect fallback mode in the transform and compute totals from the full input, discarding prior state.
- Or store state in a way that the full recompute rebuilds entirely.
- Recompute the affected accounts (or run a full recompute once) to repair current values.
- Add a reconciliation check comparing incremental totals with a periodic full computation.
Example: after the fix, the next UPDATE upstream triggers a clean full recompute and totals match the reconciliation.
W: Inconsistent state across fallback caused double counting: making state handling fallback-aware and repairing the totals addresses both cause and effect.
X: A=Arithmetic bug: the sums are correct on append runs; the defect is in state handling across modes.
C=Reject the UPDATE: corrections are legitimate business data; blocking them leaves the totals wrong differently.
D=Give up on incremental: running totals can be incremental with correct state handling; abandoning it is unnecessary.
T: Incremental state must be reset or rebuilt on fallback; verify with periodic reconciliation.
V: incremental transforms

@ PLTR-DE D3 T3.3 applied use-case
S: A data engineer wants to confirm, before enabling an incremental transform in production, that it produces the same result as the full batch version. Which validation is appropriate?
A: Trust the incremental logic, since the code was reviewed
B: Run batch and incremental versions on a branch over the same inputs across several runs, including one after an upstream UPDATE, and compare
C: Run the incremental version once and check that it finishes faster
D: Enable the incremental version in production now and compare its results with a batch run in a month, when there is enough history to judge
K: B
G: ## Proving equivalence
Incremental correctness is subtle: state, late data, fallback and transaction types all affect results. The exam guide asks you to test and verify rather than assume.
## Method
- Branch: both implementations on identical inputs.
- Multiple runs: simulate several append runs and at least one fallback (an upstream snapshot or update).
- Compare: row counts, key sets, column values; investigate any difference.
- Keep the comparison as a periodic reconciliation after go-live.
Example: the comparison reveals that the incremental version misses rows arriving with timestamps earlier than the watermark; late-data handling is added before launch.
W: Side-by-side comparison on a branch across append and fallback runs: it proves equivalence under the conditions that matter before production depends on it.
X: A=Code review only: review cannot exercise state and fallback behaviour.
C=Faster is not correct: speed says nothing about equality of results.
D=Compare in a month: a month of possibly wrong data reaching consumers is the risk being avoided.
T: Validate incremental transforms against the batch result on a branch, including a fallback run, before go-live.
V: Code Repositories, branches

@ PLTR-DE D3 T3.2 applied definition
S: A dataset's transaction history shows: SNAPSHOT (Monday), APPEND (Tuesday), APPEND (Wednesday), DELETE (Thursday, removing Tuesday's file). What is the dataset's current view?
A: All files from Monday, Tuesday and Wednesday, since DELETE only marks files as hidden
B: Monday's files plus Wednesday's file; Tuesday's file was removed by the DELETE
C: Only Wednesday's file, since the latest transaction defines the view
D: Nothing, since a DELETE transaction empties the dataset
K: B
G: ## Computing a dataset view from transactions
A dataset's view is the result of applying its transactions in order. The exam guide asks you to understand the four transaction types separately from processing modes.
- SNAPSHOT (Mon): view = Monday files.
- APPEND (Tue): view = Monday + Tuesday files.
- APPEND (Wed): view = Monday + Tuesday + Wednesday.
- DELETE (Thu, Tuesday's file): view = Monday + Wednesday.
An incremental consumer would have processed Tuesday's and Wednesday's files as new and must now handle the DELETE (typically a fallback).
W: Monday plus Wednesday: the DELETE removed exactly Tuesday's file from the view, and nothing else changed.
X: A=Hidden not removed: a DELETE transaction removes files from the view; they are not part of the dataset's current contents.
C=Latest only: only a SNAPSHOT replaces the view; APPEND and DELETE modify it.
D=Empties the dataset: a DELETE removes the files it names, not everything.
T: Apply transactions in order: SNAPSHOT replaces, APPEND adds, DELETE removes the named files.
V: transactions

@ PLTR-DE D3 T3.4 advanced tradeoff
S: A streaming pipeline's state (per-key windows) has grown to the point that the job restarts often with memory errors, and the key space keeps growing. What should the data engineer change?
A: Give the job unlimited memory on a larger machine, since per-key state must be kept for every key forever to keep the windows correct
B: Bound the state with windows and time-to-live so inactive keys are evicted, and move long-horizon aggregates to batch over the persisted stream
C: Convert the pipeline to batch and give up on streaming
D: Reduce the input rate by sampling messages
K: B
G: ## Managing streaming state
Streaming state lives in memory (and checkpoints); unbounded state eventually fails. The exam guide names state among streaming concerns to handle safely.
## Options
- Windowing and TTL: keep state only for the active window per key; evict keys that stop arriving.
- Reduce the state's scope: aggregate at a coarser key where acceptable.
- Split responsibilities: streaming for recent, low-latency results; batch over the persisted stream for long-horizon aggregates.
Example: a 24-hour TTL per device key keeps state at a stable size; weekly aggregates come from a batch over the streaming dataset.
W: Bounded state through windows and TTL with batch for long horizons: it makes the job stable without losing the required results.
X: A=Unlimited memory: memory is finite; a growing key space will exhaust any limit.
C=Abandon streaming: the latency requirement that justified streaming still exists.
D=Sampling: dropping messages corrupts the results; the problem is state growth, not throughput.
T: Keep streaming state bounded with windows and TTLs; compute long-horizon aggregates in batch.
V: streaming
