# PLTR-DE batch 39: Domain 6 round 5 (Security, Projects, and Governance), 8 questions

@ PLTR-DE D6 T6.1 applied use-case
S: A dataset must be readable by the whole company except for a single highly sensitive column that only the legal team may see. Which design achieves this cleanly?
A: Applying a legal marking to the entire dataset so that only the legal team can open it, and asking everyone else to request the data from legal
B: Publishing a curated dataset without the column for the company, and a separate dataset or column-restricted view with it, protected by a legal marking
C: Leaving the dataset unmarked and relying on a Workshop module to hide the sensitive column from non-legal users
D: Encrypting the sensitive column's values with a key that only legal staff know, inside the same dataset
K: B
G: ## Column-level separation
The exam guide asks for least privilege per consumer and for markings on sensitive data. One sensitive column among many public ones is handled by separating it, not by locking everything.
## Design
- Company dataset: all columns except the sensitive one; broad read.
- Legal dataset or column-restricted view: includes the column; legal marking or policy.
- Lineage shows both derive from the same source.
Example: analysts query 20 columns freely; legal sees the 21st in their own view.
W: Split by sensitivity with the sensitive column behind a marking or policy: broad access to the public columns and strict control of the one that matters.
X: A=Mark everything: the whole company loses access to 20 public columns.
C=Workshop hiding: not access control; the column is readable elsewhere.
D=Encrypt in place: unmanageable key handling and the column still travels everywhere.
T: Separate sensitive columns into their own protected dataset or view rather than locking the whole dataset.
V: markings, restricted views

@ PLTR-DE D6 T6.2 applied troubleshooting
S: A data engineer discovers that a project's Owner role was granted to a broad "all-employees" group years ago, so anyone can delete datasets in it. What is the right remediation?
A: Leaving the grant as it is, since nobody has deleted anything in the project so far and changing roles might disrupt users
B: Replacing the broad Owner grant with least-privilege roles (Viewer, Editor, a small Owner group), auditing changes, adding reviews
C: Deleting the whole project and recreating it from scratch with the right permissions, then re-adding the datasets to it
D: Renaming the project to something obscure so that fewer of the employees in the group ever find it in search
K: B
G: ## Over-provisioned projects
The exam guide asks for least privilege on projects and governed access. Owner for everyone is an accident waiting to happen.
## Remediation
- Roles: Viewer broadly if appropriate; Editor to the team; Owner to a few named people.
- Audit: changes made under the broad grant.
- Process: periodic access reviews so grants do not drift again.
Example: 2,000 users drop from Owner to Viewer; three engineers keep Editor; two leads are Owners.
W: Least-privilege role replacement with an audit and recurring review: the risk is removed and prevented from returning.
X: A=Leave it: any of 2,000 people can delete production datasets by accident; the risk is real regardless of past luck.
C=Recreate: destroys history and lineage; roles can be changed in place.
D=Rename: everyone in the group still holds Owner; an obscure name changes nothing about what they can do.
T: Fix over-broad project roles by assigning least-privilege roles and instituting access reviews.
V: projects

@ PLTR-DE D6 T6.3 applied use-case
S: A restricted view policy must grant rows based on a user attribute (region) that is stored in an HR system, not in the platform. How should this be set up?
A: Hard-coding each user's region directly into the restricted view's policy, updated by hand whenever someone moves to a new region
B: Syncing the user-to-region mapping from HR into a governed dataset or user attributes the policy references, so HR changes flow through
C: Asking each user to declare their own region in a prompt when they open the dataset, and filtering rows on what they declared
D: Granting every user access to every region's rows, which avoids the mapping problem by removing the restriction altogether
K: B
G: ## Attribute sources for policies
The exam guide covers restricted views and user attributes. Policies need a reliable, current attribute source; HR is the system of record for region.
## Setup
- Sync HR's user-region mapping into the platform (dataset or group memberships) on a schedule.
- Policy: row.region matches the user's region via that mapping.
- Monitoring: freshness of the mapping sync; audit of changes.
Example: an employee transfers regions in HR; the next sync updates the mapping and their rows change accordingly.
W: A synced, governed mapping from the system of record: policies stay correct as people move, with an audit trail.
X: A=Hand-coded: a policy edited by hand for every transfer is stale within weeks and offers no audit trail of who could see what.
C=Self-declared: a user could declare any region they like; the restriction becomes voluntary.
D=Everyone everything: the whole point was that users see only their region; granting all regions abandons the requirement.
T: Drive row-level policies from attributes synced from the system of record.
V: restricted views, Data Connection

@ PLTR-DE D6 T6.4 applied troubleshooting
S: A dataset's lineage shows it is derived from a marked source, but the dataset itself carries no marking and is readable by a broad audience. What should the data engineer do?
A: Nothing, since the marking only applies to the source dataset
B: Investigate: if sensitive content propagated, apply the marking and assess exposure; if de-identified, document the review
C: Delete the dataset to be safe
D: Add a note in the dataset's description warning readers that the data may be sensitive and should be handled carefully
K: B
G: ## Lineage as a security audit tool
The exam guide asks you to apply security throughout the lifecycle and to trace with lineage. Marked source → unmarked derived dataset is either a documented de-identification or a leak.
## Response
- Inspect the dataset: are the sensitive columns present?
- If yes: apply the marking now; determine who read it; report as an incident.
- If no: record the de-identification review so the question does not recur.
Example: the derived dataset still carries national ids; it is marked immediately and the 40 users who read it are identified.
W: Immediate investigation with marking or documented de-identification: sensitivity follows data, and gaps must be closed or justified.
X: A=Source only: derived data with the same content is equally sensitive.
C=Delete: destroys possibly legitimate data; marking it is the proportionate control.
D=Warning note: a description does not restrict anyone; the broad audience can still read the sensitive content.
T: An unmarked derivative of marked data is a finding to investigate and resolve, not to ignore.
V: markings, Data Lineage

@ PLTR-DE D6 T6.1 applied comparison
S: A data engineer is onboarding a partner company's analysts and needs to explain why they cannot see internal projects. Which statement correctly describes organizations in the access model?
A: Organizations are optional labels used for reporting with no effect on access, since only markings and project roles decide what a user can see
B: Organizations partition the platform: cross-organization visibility is restricted by default, and markings and roles apply within
C: Organizations are simply another name for projects, so a partner's analysts need only be added to the right project to see it
D: Organizations replace markings for sensitive data, so a dataset in the right organization needs no marking to be protected
K: B
G: ## The organization boundary
The exam guide lists organizations alongside markings and project roles as combining controls.
- Organization: the outermost boundary; cross-organization access is limited unless explicitly shared.
- Markings: mandatory data-level controls within.
- Roles: discretionary project permissions within.
Example: a partner organization's users cannot see internal projects at all, whatever roles exist on them.
W: A partitioning boundary within which markings and roles apply: the accurate description.
X: A=No effect: a partner organization's users cannot see internal projects regardless of roles; the boundary is real and enforced.
C=Same as projects: projects live inside organizations; adding a partner user to a project does not cross the organization boundary.
D=Replace markings: an organization is a boundary around everyone in it; a marking restricts a subset within it; they are different layers.
T: Organizations partition the platform; markings and roles control access within that boundary.
V: organizations

@ PLTR-DE D6 T6.2 applied use-case
S: Two business units must share a curated reference dataset while keeping all their other data separate. How should this be structured?
A: Giving each unit full access to the other's projects so the reference data is visible
B: Placing the shared reference dataset in a dedicated shared project readable by both units and referenced from their own projects
C: Duplicating the reference dataset into each unit's project and having the two teams keep the copies in sync by hand whenever it changes
D: Merging both business units' projects into a single project so that everything is visible to everyone and nothing needs sharing
K: B
G: ## Shared projects for shared assets
The exam guide asks for project boundaries that match ownership and audience. A shared asset gets a shared project; everything else stays separate.
## Structure
- Shared project: the reference dataset, with Viewer for both units; owned by a steward.
- Unit projects: reference the shared dataset; roles per unit.
- Lineage across projects.
Example: both units read `currencies_reference` from the shared project; neither sees the other's sales data.
W: A dedicated shared project with cross-unit read: sharing exactly what is shared, nothing more.
X: A=Full mutual access: exposes everything to share one dataset.
C=Manual copies: the two copies drift apart the first time someone forgets to sync them, and maintenance is doubled for no benefit.
D=Merge projects: each unit's other data becomes visible to the other, which is exactly what they must prevent.
T: Share specific assets through dedicated shared projects referenced by consumers.
V: projects

@ PLTR-DE D6 T6.4 applied troubleshooting
S: An Ontology object type is readable by a user, but one of its link types to another object type returns nothing for them while colleagues can traverse it. What is the likely cause?
A: Links are randomly hidden from some users for performance reasons when the linked object type is large
B: The user lacks access to the linked object type's backing data (a marking, role or view on that side); use Check Access there
C: The link type's configuration is broken for this user and must be deleted and recreated by the Ontology owner
D: The user's browser is caching an old version of the Ontology from before the link type was created, and a hard refresh will fix it
K: B
G: ## Links respect the other side's permissions
The exam guide asks you to reason about consumer-facing permissions per object type. Traversing a link shows only objects the user may see on the target type.
## Check
- Check Access for the user on the target object type's backing dataset or view.
- A marking or policy on the target side explains the empty link.
- Grant the specific requirement if appropriate.
Example: the Contract object type is marked "Legal"; the user lacks it; the Customer → Contracts link shows nothing for them.
W: Missing access to the target object type's data: links reveal only what the user may see on both ends.
X: A=Random hiding: link traversal is deterministic and governed by permissions; the platform does not hide links at random.
C=Broken link: colleagues traverse the same link successfully, so its configuration is intact; the difference is the user.
D=Browser cache: a cache would not selectively hide one link type for one user while colleagues see it; permissions do.
T: An empty link for one user means they lack access to the target object type's backing data; check that side.
V: Check Access, Ontology

@ PLTR-DE D6 T6.3 advanced tradeoff
S: A team debates whether to implement row-level security with a restricted view or by baking the filter into a Workshop module's queries. Which argument correctly favours the restricted view?
A: Workshop queries with filters are slower than restricted views, so query performance alone decides the question in favour of the view
B: A restricted view enforces the restriction at the data layer for every access path; a module filter protects one module only
C: Restricted views are easier and quicker for a data engineer to build than configuring filters inside a Workshop module
D: Workshop modules cannot filter data at all
K: B
G: ## Enforce at the data layer
The exam guide asks for least privilege at the data layer and warns that UI-level filtering is not access control. A module filter is a convenience; a restricted view is a control.
## Reasoning
- Every path: a function, an export or another module reads the same protected rows.
- Tamper-proof: users cannot remove a view policy; they can change a module filter.
- Consistent: one policy for all consumers.
Example: an analyst opens the dataset in a different tool; the restricted view still applies, the module filter would not.
W: Data-layer enforcement across every access path: the decisive argument for the restricted view.
X: A=Performance: the question is enforcement, not speed; and a view is not guaranteed to be faster than a filtered query.
C=Easier: ease of building is irrelevant; the criterion is whether the restriction holds on every path, which only the view guarantees.
D=Cannot filter: modules can filter; they just do not enforce.
T: Implement row-level security at the data layer so it applies to every tool, not inside one application's filters.
V: restricted views, Workshop
