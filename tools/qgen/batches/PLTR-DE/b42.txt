# PLTR-DE batch 42: Domain 1 round 6 (Data Connectivity and Ingestion), 8 questions

@ PLTR-DE D1 T1.1 applied use-case
S: A partner delivers data by pushing JSON events to an HTTPS endpoint whenever records change, at a rate of a few hundred events per minute. The business wants the data available within a couple of minutes. Which ingestion pattern fits?
A: A nightly file sync that asks the partner to write the day's events into a single file in a bucket, so that the data arrives in one daily batch
B: A push-based streaming ingestion endpoint receiving the events, with a payload schema and a transform to current state
C: A JDBC sync against the partner's database, since every partner exposes a database that can be queried directly over the internet
D: A manual process in which an analyst downloads the partner's events each morning from a web portal and uploads them as a spreadsheet
K: B
G: ## Push sources need push ingestion
The exam guide asks you to choose ingestion patterns from source behaviour and freshness. A partner that pushes events continuously with minute-level freshness needs an endpoint that receives a stream, not a batch pull.
## Design
- Streaming ingestion endpoint receiving the JSON events.
- Schema on the payload; malformed events routed aside.
- Downstream: current-state dataset or object updates from the stream.
Example: an event pushed at 10:01 is visible in the current-state dataset by 10:02.
W: A push-based streaming endpoint with a payload schema: it matches how the partner delivers data and meets the two-minute freshness requirement without inventing a batch interface.
X: A=Nightly file: the partner already pushes in real time; forcing a daily file misses the freshness requirement by a day.
C=JDBC to the partner: partners rarely expose their databases, and pulling would not match a push-based integration.
D=Manual daily download: unreliable, a day stale, and outside any governed pipeline or schema enforcement.
T: Match ingestion to how the source delivers: push sources with tight freshness need streaming ingestion.
V: streaming, Data Connection

@ PLTR-DE D1 T1.2 applied troubleshooting
S: A snapshot sync of a large table takes six hours and occasionally overlaps with the next run. The table has a reliable `updated_at` column and deletions are rare and soft-flagged. What should change?
A: Keep the snapshot and run it less often, accepting that the dataset is stale for most of the week between runs
B: An update sync on `updated_at` with a lookback, the soft-delete flag carrying deletions, and periodic reconciliation
C: Increase the agent host's memory so that the snapshot finishes faster, since snapshot duration depends mostly on agent resources
D: Split the table into ten copies at the source and snapshot each one separately in parallel every night
K: B
G: ## Incremental when the source supports it
The exam guide asks you to choose sync patterns by volume and change signals. A reliable timestamp and soft-deletes make incremental sync correct and far cheaper than repeated full copies.
## Design
- Update sync on `updated_at` with a lookback window and key deduplication.
- Deletions carried by the soft-delete flag.
- Weekly or monthly reconciliation snapshot to catch drift.
Example: the nightly run transfers 2% of the table in 15 minutes instead of 6 hours.
W: Update sync with lookback and soft-delete handling plus periodic reconciliation: correct results at a fraction of the transfer, and no more overlapping runs.
X: A=Less frequent snapshots: trades the overlap for staleness and still moves the whole table every time it runs.
C=More agent memory: transfer time is dominated by moving the full table, not by agent memory.
D=Ten source copies: asks the source team to duplicate data and still transfers everything every night.
T: When a reliable change signal exists, replace repeated full snapshots with incremental syncs and periodic reconciliation.
V: Data Connection

@ PLTR-DE D1 T1.3 applied use-case
S: An external auditor needs read-only, time-limited access to a curated dataset. The organization prefers not to create platform accounts for auditors. What is the appropriate approach?
A: Share the platform credentials of an internal employee with the auditor for the duration of the audit, then reset the password
B: Produce the agreed extract as a dataset and deliver it through a governed, logged export to an approved destination
C: Email the full curated dataset to the auditor's personal address as a compressed attachment
D: Make the curated dataset publicly accessible on the internet for the duration of the audit
K: B
G: ## Governed delivery to external parties
The exam guide covers exports and egress policies for sending data outside. Without platform accounts, the governed route is a controlled export of exactly what the audit needs.
## Design
- Extract dataset with the agreed scope.
- Export to an approved destination (the auditor's secure transfer location) under policy.
- Execution history as the delivery record.
Example: the auditor receives three extracts over the audit period, each logged with dataset version and time.
W: A scoped extract delivered through a governed, logged export: the auditor gets what is needed without accounts or uncontrolled copies.
X: A=Shared credentials: violates identity controls and attributes the auditor's actions to an employee.
C=Personal email: unapproved destination, unlogged, and the whole dataset rather than the agreed scope.
D=Public access: exposes the data to everyone on the internet, not just the auditor.
T: Deliver data to external parties through scoped extracts and governed, logged exports.
V: exports, egress policies

@ PLTR-DE D1 T1.4 applied troubleshooting
S: A file sync reports success, but downstream parsing fails because some landed files are truncated. The source writes large files slowly over several minutes. What is the likely cause and fix?
A: The parsing transform is buggy and should be rewritten to tolerate truncated JSON by guessing the missing closing characters
B: The sync reads files still being written; use a completion signal (marker file, rename after write, minimum age)
C: The bucket is losing data and the storage provider should be changed
D: The agent is corrupting files in transit and should be reinstalled on a new host
K: B
G: ## Reading files before they are finished
The exam guide asks you to diagnose ingestion with evidence. Truncated files from a slow writer point to a race between the writer and the sync.
## Fix
- Writer: write to a temporary name and rename on completion, or drop a marker file.
- Sync: match only completed names or require a minimum age.
- Validation: parse check on landing; quarantine anything incomplete.
Example: after switching to rename-on-complete, no truncated file is ingested again.
W: A completion signal so only finished files are picked up: the race between the slow writer and the sync disappears at its source.
X: A=Guess missing characters: fabricates data and hides an ingestion defect behind a parser hack.
C=Change storage provider: the files are complete in the bucket later; storage is not losing data.
D=Reinstall the agent: the agent copied what it saw; the file was incomplete at that moment.
T: Ingest only completed files by using rename-on-write, marker files or minimum file age.
V: Data Connection

@ PLTR-DE D1 T1.1 applied comparison
S: A team is deciding how to bring in data from a SaaS tool that offers both a REST API and a nightly CSV export to a bucket. The business needs daily freshness and the full history. Which statement best guides the choice?
A: The REST API is always the better choice because APIs are more modern than files, regardless of limits or completeness
B: Either can work; choose by completeness, rate limits, schema stability and operational cost for the requirement
C: The CSV export is always worse because files cannot be governed in the platform
D: Both should be ingested in parallel into the same dataset to be safe
K: B
G: ## Choosing among available interfaces
The exam guide asks you to select connectors by protocol, capability and requirements. When two interfaces exist, the requirement decides.
## Criteria
- Completeness: does the export include everything the API does?
- Rate limits: can the API deliver the full history nightly?
- Stability: schema changes in files versus API versions.
- Operations: a file sync is often simpler to run.
Example: the export is complete and stable; a daily file sync meets the need with less code than paginated API calls.
W: Choose by completeness, limits, stability and operational cost: the decision follows the requirement rather than a preference for one interface type.
X: A=API always better: rate limits or incomplete endpoints can make the API the worse choice for full daily history.
C=Files cannot be governed: landed files are governed like any dataset, with lineage and expectations.
D=Both into one dataset: duplicate rows and conflicting versions of the same records.
T: When multiple source interfaces exist, select by completeness, limits, stability and operations.
V: Data Connection

@ PLTR-DE D1 T1.2 applied use-case
S: A source table with 2 billion rows needs to be replicated with deletions and updates reflected within minutes, and the database supports change data capture. Which design fits?
A: An hourly full snapshot of all 2 billion rows, since full snapshots are the only pattern that always captures deletions correctly
B: An initial bulk load plus a CDC sync of the change log, with a keyed transform applying all changes to current state
C: An append sync on the primary key, since higher keys always mean newer rows
D: A daily export to CSV from the database followed by a file sync
K: B
G: ## CDC for large, fast-changing tables
The exam guide lists CDC among sync patterns for capturing all change types with low latency. At this size and freshness, only log-based capture is practical.
## Design
- Initial bulk load for the baseline.
- CDC stream of inserts, updates and deletes.
- Keyed merge transform maintaining current state; lag monitored.
Example: a deletion in the source disappears from the current-state dataset within three minutes.
W: CDC with an initial load and a keyed apply transform: every change type arrives within minutes without copying 2 billion rows repeatedly.
X: A=Hourly snapshot: moving 2 billion rows every hour is impractical and still not minute-level.
C=Append on key: misses updates and deletions entirely and assumes monotonic keys.
D=Daily CSV: a day stale and loses deletions unless handled separately.
T: Use CDC with a keyed apply for large tables that need all change types at low latency.
V: Data Connection, streaming

@ PLTR-DE D1 T1.3 applied troubleshooting
S: A virtual table's queries started returning fewer rows than the external system contains, only for some users. Nothing changed in the external system. What should be investigated first?
A: Whether the external system is randomly dropping rows for certain query patterns at busy times of day
B: Whether a row-level policy on the virtual table now filters rows for those users, checked with Check Access
C: Whether those users' browsers are caching old query results from before the change
D: Whether the virtual table should be converted to a full copy to make the counts match
K: B
G: ## User-specific differences point to policy
The exam guide asks you to reason about permission layers. When results differ by user and the source is unchanged, a platform-side policy is the first suspect.
## Investigation
- Policy on the virtual table or a view built on it.
- Check Access for an affected user.
- Recent changes to user attributes or groups that the policy reads.
Example: a new regional policy was attached last week; the affected users only see their own region, as intended.
W: A row-level policy filtering per user: the only explanation consistent with user-specific results and an unchanged source.
X: A=Random drops: a source dropping rows would affect all users, not specific ones.
C=Browser cache: query results are not cached per browser in a way that changes row counts by user.
D=Full copy: copies the data without explaining or respecting the policy that is causing the difference.
T: When results differ by user, check row-level policies and access before suspecting the source.
V: virtual tables, restricted views

@ PLTR-DE D1 T1.4 advanced tradeoff
S: Leadership wants every new data source onboarded within a week. The data engineering team wants a repeatable process that does not sacrifice quality. What should the onboarding standard include?
A: Only the sync itself, with quality checks, alerts and documentation added later whenever consumers find problems in the data
B: A standard template: owner and credentials, landing dataset, documented keys, expectations, health checks, alerts and a runbook
C: A rule that every source must be streaming so that freshness is always maximal
D: A separate custom design for each source by whichever engineer is free that week
K: B
G: ## Repeatable onboarding
The exam guide treats monitoring, expectations and ownership as part of ingestion. A template makes them routine and fast rather than optional and late.
## Template
- Registration: owner, credentials in the source, contact.
- Landing and documentation: schema, keys, cadence.
- Controls: expectations, freshness and size checks, alert routing.
- Runbook entry.
Example: twelve sources onboarded in a quarter, each with the same controls from day one.
W: A standard onboarding template with controls built in: speed comes from repetition, and quality is not deferred until consumers complain.
X: A=Checks later: consumers become the detection system and problems arrive before controls.
C=Streaming everywhere: most sources are batch; forcing streaming adds cost and complexity without benefit.
D=Custom each time: inconsistent controls and slow, engineer-dependent onboarding.
T: Onboard sources through a standard template that includes controls, ownership and runbooks.
V: Data Connection, Data Health
