# PLTR-DE batch 15: Domain 6 round 2 (Security, Projects, and Governance), 8 questions

@ PLTR-DE D6 T6.1 applied use-case
S: A dataset must be readable only by members of the finance department, and the requirement must hold wherever the data flows, including derived datasets built by other teams. Which control enforces this?
A: Grant the finance group the Viewer role on the dataset's project, since project roles are what govern who can read the data held in a project
B: Apply a "Finance" marking, so every reader, including readers of derived datasets, must hold it regardless of project roles
C: Put the dataset in a folder named "finance only" and tell other teams not to use it
D: Hide the dataset from search so that only people who know its path can find it
K: B
G: ## Markings for mandatory, data-following control
The exam guide asks you to understand how organizations, markings and project roles combine. Roles are discretionary and project-scoped; a marking is a mandatory control that travels with the data: a user needs it to access the marked resource whatever their role, and derived data carries the same obligation.
## Fit
- "Only finance, wherever it flows" is exactly what a marking expresses.
- Membership managed by the marking's stewards with an approval process.
- Check Access shows whether a user holds it.
Example: an analytics team builds a derived dataset; analysts without the Finance marking cannot read it either.
W: Finance marking: a mandatory control that applies to every reader and follows the data into derived datasets, matching the requirement.
X: A=Viewer role: a derived dataset in another project has different roles; the restriction would not follow the data.
C=Folder name and requests: not a control; anyone with project access reads the data.
D=Hide from search: obscurity is not access control; links and lineage reveal the path.
T: Use markings when a restriction must follow the data; roles only govern access within a project.
V: markings, projects

@ PLTR-DE D6 T6.2 applied troubleshooting
S: A project contains raw syncs, transforms, curated outputs and three Workshop apps. Adding a new consumer team as Viewers exposed the raw source data to them. What is the structural fix?
A: Remove the consumer team again and give them exports of the curated data by email
B: Split the project: raw syncs and transforms into a restricted pipeline project, curated outputs in a project the consumer team can view
C: Apply a marking to every raw dataset so the consumer team cannot read them, while keeping all layers together in the single existing project
D: Ask the consumer team to promise not to open the raw datasets
K: B
G: ## Projects as permission boundaries
The exam guide asks you to structure projects to create boundaries between sources, transforms, Ontology outputs and workflows. A role grant applies to a whole project; mixing layers in one project makes it impossible to expose one layer and not another.
## Fix
- Datasource and pipeline project: engineers only.
- Curated project: consumer teams as Viewers.
- Application project: end users.
Lineage still links the layers; permissions no longer leak.
Example: after the split, the consumer team sees four curated datasets and nothing else.
W: Split by layer into projects: the role grant then exposes only the curated layer, which is the intended boundary.
X: A=Email exports: it removes governed access and replaces it with ungoverned copies.
C=Markings as a workaround: markings are for sensitivity classes, not for patching a project layout; new raw datasets would need marking every time, and the structure stays wrong.
D=A promise: not a control; the data is readable with their role, and a mistake or a departing employee makes the promise meaningless.
T: Separate layers into projects so role grants expose only the intended layer.
V: projects

@ PLTR-DE D6 T6.3 applied use-case
S: A restricted view filters rows by the user's region. A new requirement: certain managers should see all regions. How should this be handled?
A: Give the managers the Owner role on the project that holds the view, since Owners have full rights and therefore bypass restricted view policies
B: Extend the restricted view's policy so members of an "all regions" group see every row while others stay filtered
C: Create a copy of the full dataset for managers in a separate project
D: Remove the restricted view entirely and rely on managers to filter appropriately
K: B
G: ## Policies support multiple audiences
A restricted view's policy evaluates user attributes; it can express "see your region's rows, or all rows if you are in the privileged group". The exam guide asks you to understand restricted views and their limitations; one strength is exactly this flexible, attribute-based policy.
## Design
- Policy: `user.region == row.region OR user in group:all_regions`.
- Membership of `all_regions` governed with approval.
- Test with a regional user and a manager.
Example: a regional manager sees EMEA rows; a global manager in the group sees all 40 regions in the same object type.
W: Policy extension with a privileged group: it meets the new requirement in the same governed view without copies or role changes.
X: A=Owner role: roles do not bypass restricted view policies, and Owner grants far more than reading rows.
C=Copy for managers: duplicates the data and governance; the view already supports the case.
D=Remove the view: regional users would then see every region's rows, which breaks the original requirement for everyone else.
T: Express multi-audience row access in the restricted view's policy using user attributes and groups.
V: restricted views

@ PLTR-DE D6 T6.4 applied troubleshooting
S: A transform's build identity can read all inputs and writes its output, but a Workshop app reading the Ontology object backed by that output shows "no access" for some users who can open the app. Where should the engineer look?
A: In the transform code, since access errors usually originate in the pipeline
B: In consumer-side permissions: the backing dataset or restricted view, its markings, and Ontology permissions, checked as those users
C: In the schedule, since builds that run overnight produce objects whose permissions are evaluated against the night-time build identity rather than the users
D: In the Workshop module's layout settings
K: B
G: ## Consumer access is separate from pipeline access
The exam guide asks you to diagnose consumer-facing permissions separately from pipeline execution permissions. The pipeline runs fine; the users' problem is at the Ontology or dataset layer.
## Checks
- Check Access for one affected user on the backing dataset and on the object type.
- Markings on the output the users lack.
- Restricted view policies that exclude them.
- Ontology-level permissions for the object type.
Example: the curated dataset carries a marking inherited from an input; app users lack it; the fix is a de-identified backing dataset or marking membership.
W: Consumer-side permissions checked as the affected users: the build is healthy, so the failure is in what those users may read of the backing data and object type.
X: A=Transform code: the transform executes successfully; code is not where a per-user read failure lives.
C=Night-time permissions: no such concept; build time does not affect permissions.
D=Workshop layout: layout settings decide where widgets appear; they cannot grant or deny access to object data for particular users.
T: When a healthy pipeline's objects are unreadable for some users, diagnose their access to the backing data and object type with Check Access.
V: Check Access, Ontology

@ PLTR-DE D6 T6.1 applied tradeoff
S: A data engineer is asked to make a pipeline's build identity an administrator "so that builds never fail on permissions again". What should they say?
A: Agree, since an administrator build identity reduces operational interruptions and the pipeline team is trusted with the data anyway
B: Decline: scope the build identity to the reads and writes its inputs and outputs need, and treat permission failures as specific grants to fix
C: Agree but only during business hours
D: Agree if the pipeline is important enough
K: B
G: ## Least privilege for execution identities
The exam guide asks you to apply least privilege separately to sources, pipeline execution, datasets, Ontology objects and consumers, and to diagnose access failures rather than grant broad permissions. An administrative build identity means a single transform (or a mistake in one) can read sensitive data or overwrite anything.
## Practice
- Grant per-input read and per-output write.
- When a build fails on access, add the one missing grant.
- Review build identity permissions periodically.
Example: a new input is added; the build fails once; the identity gets read on that dataset; nothing else changes.
W: Decline and scope access precisely: it keeps the blast radius of any transform small, and permission failures become quick, targeted fixes.
X: A=Agree: every transform could then exfiltrate or corrupt any dataset.
C=Business hours: time-limited administration is still administration.
D=Importance: importance argues for more care, not fewer controls.
T: Build identities get only the access their transforms need; never make them administrators for convenience.
V: projects, markings

@ PLTR-DE D6 T6.2 applied use-case
S: Two teams share a project and keep overwriting each other's datasets by accident. Each needs to build their own pipelines independently. What should be done?
A: Keep the one shared project but ask each team to use its own naming prefix on datasets so that it is obvious which team owns which resource
B: Give each team its own project for its pipelines and outputs, referencing shared inputs across projects, so ownership is clear
C: Make one team read-only in the shared project
D: Merge the two teams' pipelines into one shared pipeline
K: B
G: ## Ownership boundaries
Projects define who may edit what. The exam guide asks you to structure projects so boundaries are appropriate. Two teams writing in one project have no boundary.
## Design
- Project per team (or per domain) with Editor roles for that team only.
- Shared inputs referenced across projects, read-only for consumers.
- Lineage across projects remains visible.
Example: team A's project holds A's transforms; team B references A's curated output and cannot write to it.
W: Separate projects with cross-project references: ownership and permissions are explicit and overwrites become impossible.
X: A=Naming prefixes: a convention does not stop an edit to the wrong dataset.
C=Read-only team: that team can no longer build its own pipelines in the project, so the requirement that both work independently is not met.
D=Merge pipelines: it couples two teams' work further, the opposite of independence.
T: Give independent teams their own projects and share data through references.
V: projects

@ PLTR-DE D6 T6.3 applied troubleshooting
S: A restricted view backs an object type. Users report that counts shown in a Workshop aggregation differ from counts in a report built directly on the underlying dataset by the data team. Is this a defect?
A: Yes: a restricted view must always return the same row counts as the underlying dataset, so a mismatch means the view's policy is broken
B: Not necessarily: the view returns only each viewer's permitted rows, so their aggregate covers a subset; the difference is expected and should be explained
C: Yes: Workshop aggregations are known to be inaccurate on restricted views
D: Yes: the dataset must be rebuilt so that the view matches
K: B
G: ## Expected consequences of row-level security
The exam guide asks you to understand restricted views' limitations. A view returns a per-user subset; any aggregate over it is an aggregate over that subset. This is by design, and it should be communicated so users do not mistake it for an error.
## Handling
- Explain: "totals reflect the rows you are permitted to see".
- If org-wide totals must be shown to everyone, compute them in the pipeline as an aggregate dataset without row-level restriction (if policy allows) and expose that separately.
Example: a regional manager's dashboard shows 1,200 orders; the full report shows 9,800; both are correct.
W: Expected behaviour of a permission-filtered view, to be explained and designed around: there is no defect in the data or the aggregation.
X: A=Must match: the whole point of the view is that it does not return everything to everyone.
C=Workshop inaccurate: the aggregation is accurate over the rows it receives.
D=Rebuild: rebuilding changes nothing about per-user filtering.
T: Aggregates over restricted views reflect each user's permitted rows; design org-wide totals separately if needed.
V: restricted views, Workshop

@ PLTR-DE D6 T6.4 advanced use-case
S: A regulator asks the team to demonstrate that only authorized users could access a sensitive dataset over the past year. Which evidence can the data engineer assemble?
A: A verbal assurance from the project owner
B: Access configuration history (markings, roles), Check Access results, lineage with controls on derived datasets, and the platform's audit logs
C: A screenshot of the current permissions page only
D: A list of all users in the organization who, when asked, said that they never opened the dataset during the past year
K: B
G: ## Evidence for governance
The exam guide expects security controls applied through the lifecycle and diagnosed with Check Access and lineage. Demonstrating control to a regulator uses the same tools as evidence:
- Configuration: which markings and roles applied, and how membership changed over the year.
- Check Access: concrete per-user evaluations.
- Lineage: every derived dataset and the controls it inherited or added.
- Audit logs: who actually accessed what and when.
Example: the evidence shows the Finance marking in place all year, 14 members, 2 derived datasets both marked, and access logs listing only those members.
W: Configuration history, Check Access, lineage and audit logs: together they show both the controls and the actual access, which is what "demonstrate" requires.
X: A=Verbal assurance: an owner's word is not evidence of controls or of actual access; a regulator needs records.
C=Current screenshot: it shows now, not the year, and nothing about derived data or actual access.
D=User self-reports: not verifiable and incomplete; people forget, and the question is what the system allowed and recorded.
T: Prove access control with configuration history, Check Access, lineage and audit logs.
V: markings, Check Access, Data Lineage
