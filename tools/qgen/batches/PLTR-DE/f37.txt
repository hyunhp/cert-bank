S: An incremental Python transform with `require_incremental=True` used to run nightly. Last night, after the upstream dataset was rebuilt as a new SNAPSHOT, the run failed instead of running. The team lead is surprised. What should the engineer conclude?
A: The decorator is misconfigured; removing it lets the transform fall back to a full recompute whenever the input is replaced
B: The setting turns an unplanned full recompute into a failure; bump the semantic version if a full run is intended
C: The upstream SNAPSHOT corrupted the transform's stored incremental state, so the output must be deleted and rebuilt
D: The run hit a driver out-of-memory error while reading the rebuilt input, so the driver memory needs to be raised
K: B
G: ## Failing loudly versus silently recomputing
Per the incremental reference, `require_incremental=True` makes the transform fail if it cannot run incrementally. It is allowed to run as a snapshot only when an output has never been built, or the semantic version changed.
## What to do
- Check the driver logs for the warning that the transform is not running incrementally and read why.
- If the full recompute is acceptable, raise `semantic_version` to request it explicitly.
- If not, fix the upstream so the input is appended again.
Example: the engineer bumps the version from 1 to 2 and the next run rebuilds the output in full once, then resumes incrementally.
W: B=Deliberate failure, explicit full run: with the setting, an unexpected fallback to a snapshot run is a failure by design; a deliberate full run is requested by changing the semantic version.
X: A=Remove the decorator: the decorator is working as intended. Removing it loses the protection that exposed the problem and lets a costly full recompute happen silently next time.
C=Corrupted state: a SNAPSHOT upstream does not corrupt anything; it only means the new input cannot be processed as an increment, and the setting refuses the fallback.
D=Driver memory: the failure is a deliberate refusal to run non-incrementally, not a crash, so more memory changes nothing.
T: `require_incremental` fails rather than silently recomputes; request a full run by changing the semantic version.

S: A curated dataset has one row per order line with columns for the order, the customer, the product and the quantity. The business wants to ask questions such as "which customers bought this product" and "what did this order contain". How should this be modeled in the Ontology?
A: One object type Customer with a list property holding the products and order numbers of that customer's purchases
B: Object types Customer and Product, with a link between them that stores the quantity of each purchase as a property
C: One object type OrderLine with the order, customer, product and quantity columns as its properties, matching the dataset shape
D: Object types Order, Customer, Product and OrderLine, with links from OrderLine to Order and Product and from Order to Customer
K: D
G: ## Modeling entities and relationships
The exam guide asks you to model real-world entities, properties, links, and to avoid dashboard-shaped or overly broad object types. The row-per-order-line dataset is a fact table; the business questions are about entities (customers, products, orders) and their relationships.
## A normalized model
- **Customer**, **Product**, **Order** are entities with stable keys and their own properties.
- **OrderLine** captures the many-to-many between orders and products with quantity.
- **Links**: OrderLine → Order (many-to-one), OrderLine → Product (many-to-one), Order → Customer (many-to-one).
Each object type is backed by a curated dataset with one row per entity. Questions traverse links: Product → OrderLines → Orders → Customers.
Example: "which customers bought product P" is Product P → its OrderLines → their Orders → Customers, with no duplicated customer data.
W: D=Separate entity object types with links through OrderLine: it models the real relationships, supports both questions by traversal, and avoids duplicating customer and product data on every line.
X: A=List on Customer: this is a denormalized blob; products and orders cannot be queried as entities.
B=Customer and Product with a link: orders disappear from the model, and a single link cannot represent repeated purchases over time with quantities.
C=One OrderLine type: customer and product attributes repeat on every line; there is no Customer object to link to, and "what did this order contain" has no Order object.
T: Model entities as object types and relationships as link types; use an association object (OrderLine) for many-to-many with attributes.

A: Streaming, accepting the operational complexity of state, backlogs and replay because the requirement is continuous

G: ## When streaming is justified
The exam guide reserves streaming for genuinely continuous requirements and asks you to recognize when it would add complexity without improving the outcome. "Within seconds" of a continuous source is that requirement.
## What streaming brings
- A streaming dataset and a streaming pipeline process each event as it arrives.
- Operational concerns: state management for windows, backlog monitoring when consumers lag, replay after a failure, schema evolution of the stream.
- Cost: always-on compute, justified here by the business value.
Compare: a dashboard that is refreshed hourly from the same stream could be served by batch; the alerting requirement is what demands streaming.
Example: a rule evaluated per transaction in the stream raises an alert object within a few seconds; batch of any cadence would miss the window.
W: A=Streaming with its operational complexity accepted: the latency requirement is seconds on a continuous source, which batch and incremental cannot meet.
X: B=Hourly batch: it ignores the stated requirement; the team asked for seconds.
C=One-minute incremental: a minute is not seconds, and very frequent incremental batches create small-file and scheduling overhead without reaching the target.
D=Temporary streaming: converting to nightly batch afterwards abandons the requirement; the mode follows the need, not a trial period.
T: Use streaming only when latency must be continuous; then plan for state, backlogs and replay.

S: A transform reads two reference files of a few megabytes each, joins them and writes a small lookup table every hour. Its Spark job spends most of its run time starting up, and the team wants lower cost and faster runs without changing the output. Which change fits best?
A: Raise the number of Spark executors and the driver memory, since more resources let the job get through its startup phase faster on each run
B: Run the transform on a lightweight single-node compute engine, which suits small inputs and avoids most of the distributed startup overhead
C: Make the transform incremental, so each hourly run processes just the rows that changed in the two reference files since the previous run
D: Convert the transform to a streaming pipeline, so that it keeps running between updates and does not pay the job startup cost again
K: B
G: ## Choosing a compute engine
The exam guide asks you to choose a compute engine based on scale, memory, API needs, startup cost and feature compatibility, and lists lightweight engines for suitable smaller workloads.
- **Spark** distributes work across executors. That pays off for large data, but every run first has to start the distributed job, which can dominate small jobs.
- A **lightweight** engine runs on one node, typically with libraries such as pandas or Polars. For inputs of a few megabytes it starts faster and uses fewer resources.
## Check before switching
Confirm the logic does not depend on Spark-only features, compare the output with the current version on a branch, and keep an eye on input growth: if the files grow to many gigabytes, Spark may become the right choice again.
Example: an hourly job that spends 3 minutes starting Spark and 5 seconds joining 4 MB of data is a classic candidate.
W: B=Lightweight engine: the cost is distributed startup on a tiny input. A single-node engine removes most of that overhead and produces the same table, which is what the team asked for.
X: A=More Spark resources: adding executors does not shorten the fixed startup and adds cost; a few megabytes of data never needed more parallelism.
C=Incremental: incremental processing saves work on large, growing inputs. Here processing time is already tiny, and the startup overhead would remain on each run.
D=Streaming: a continuously running pipeline costs more for an hourly lookup table and adds operational complexity, with no freshness requirement that needs it.
T: For small inputs where startup dominates, choose a lightweight engine; keep Spark for data that needs distribution.

G: ## Deriving current state from history
The exam guide expects correct join and aggregation choices and awareness of cardinality. A history table has many rows per customer; joining it directly multiplies rows.
## Pattern
- Rank history rows per customer by effective date (and a tie-breaker).
- Keep the latest; this dataset has one row per customer.
- Left join customers to it so customers with no address still appear.
Example: a customer with five historical addresses gets exactly the one effective since March.
W: C=Latest-per-customer via window ranking, then left join: the correct current-state derivation with one row per customer.
X: A=Join on today's date: effective dates rarely equal today; most customers would match nothing.
B=Direct inner join: duplicates customers per address and drops customers without any address row.
D=Max of the string: alphabetical maximum has nothing to do with recency.
T: Turn history into current state with a per-key ranking by effective date before joining.
