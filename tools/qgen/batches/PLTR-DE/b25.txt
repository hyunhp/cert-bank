# PLTR-DE batch 25: Domain 8 round 3 (AI-Assisted Data Engineering), 8 questions

@ PLTR-DE D8 T8.1 applied use-case
S: A data engineer needs embeddings for product descriptions to power semantic search, and also wants to generate short marketing tags for each product. Which capabilities apply?
A: AIP Assist for both, since it can produce vectors and tags when asked in the chat interface
B: An embedding transform in the pipeline for the vectors and an LLM transform for the tags, both producing columns at build time
C: A code assistant for both, which computes the vectors and tags and writes them into the dataset during the engineer's coding session
D: An agent that users ask for each product's embedding and tags whenever they need them
K: B
G: ## Data-producing AI transforms
The exam guide distinguishes AI FDE, AIP Assist, Continue and data-producing LLM or embedding transforms. Vectors and tags are data for every row, produced in the pipeline.
## Design
- Embedding transform: same model as the search query side; vector property on Product.
- LLM transform: structured output for tags (validated list of allowed terms or short strings), with caching and quality checks.
- Both scheduled with the catalogue pipeline.
Example: 200,000 products gain vectors and three tags each nightly; search and filters use them.
W: Embedding and LLM transforms in the pipeline: the right capability for producing columns at scale.
X: A=AIP Assist: it answers questions about using the platform in a chat; it does not produce vector columns or tags for 200,000 rows.
C=Code assistant: it helps write the transforms; it does not generate dataset contents.
D=Agent on demand: products need their vectors and tags before anyone asks.
T: Produce AI-derived columns with embedding and LLM transforms in the pipeline.
V: Pipeline Builder, Ontology vector properties

@ PLTR-DE D8 T8.2 applied troubleshooting
S: An LLM transform that extracts dates from documents returns them in mixed formats ("3/4/2026", "4 March 2026", "2026-03-04"). The downstream column is a date type. What should the pipeline do?
A: Store the strings exactly as the model returned them and let each consumer interpret the dates in whichever way suits their own use
B: Ask for ISO-8601 in the schema, parse deterministically, validate the date and range, and flag ambiguous forms like 3/4/2026 for review
C: Guess day-first for all ambiguous dates, since most of the documents come from Europe
D: Drop any row whose date is not already in ISO format
K: B
G: ## Deterministic handling of ambiguous output
The exam guide pairs AI processing with structured outputs and deterministic post-processing. Dates are a classic ambiguity; "3/4/2026" is March 4 or April 3 depending on convention.
## Design
- Schema: `date` as ISO-8601 string; the model is instructed to normalize.
- Post-processing: strict parse; anything non-ISO parsed with explicit rules; ambiguous patterns flagged.
- Validation: valid calendar date within a plausible window; failures to review.
- Raw response kept for audit.
Example: "4 March 2026" normalizes cleanly; "3/4/2026" is flagged with the raw response for a reviewer.
W: ISO schema, deterministic parsing, validation and review for ambiguity: dates become reliable without guessing.
X: A=Raw strings: the column is a date type; consumers would parse inconsistently.
C=Guess day-first: wrong for a portion of documents, silently.
D=Drop non-ISO: most documents express dates in prose or local formats; dropping them discards a large share of legitimate data.
T: Normalize AI-extracted dates through schema and deterministic parsing; route ambiguity to review.
V: Pipeline Builder, Code Repositories

@ PLTR-DE D8 T8.3 applied comparison
S: Which of the following is an example of AI that belongs at the Ontology/application layer rather than in the pipeline?
A: Translating every product description into four languages in a nightly build so the catalogue is always available in each language
B: A support agent asking "summarize this customer's complaints this month" while viewing the customer, answered on demand from current tickets
C: Computing an embedding for every support ticket as it arrives
D: Classifying every incoming document into a document type for routing
K: B
G: ## Interactive versus batch AI
The exam guide places reusable batch enrichment in the pipeline and interactive, context-dependent reasoning at the Ontology layer.
- Translation, embeddings, document classification: every row, reusable, scheduled: pipeline.
- An on-demand summary for one customer, asked by one user, about this month: interactive and context-dependent: Ontology/application layer (a function or agent).
Example: the summary is generated when the agent clicks, from the tickets as they are now; nothing could have been precomputed for that question.
W: The on-demand customer summary: user-triggered, context-dependent, single-use: the Ontology-layer case.
X: A=Nightly translation: the same work for every row on a schedule, reused by every consumer; that is pipeline-layer batch enrichment.
C=Ticket embeddings: building the vector index for every ticket as it arrives is reusable pipeline work, not an interactive request.
D=Document classification: a per-document routing label computed once and reused by downstream pipelines belongs in the pipeline.
T: On-demand, user-contextual AI runs at the application layer; row-wise reusable AI runs in the pipeline.
V: AIP Logic, Pipeline Builder

@ PLTR-DE D8 T8.4 applied use-case
S: A team adopts a code assistant for writing transforms. Which practice keeps quality high?
A: Accept generated code whenever it builds successfully, since the assistant has been trained on far more code than the whole team has ever written
B: Treat generated code as a draft: review assumptions and scale-safety, run tests and branch builds, compare outputs, and keep the engineer accountable
C: Ban the assistant for production code and allow it only for notebooks
D: Let the assistant also review its own code, which replaces human review
K: B
G: ## Assistants as drafters, engineers as owners
The exam guide asks data engineers to review AI-generated code and outputs for incorrect assumptions, unsupported patterns and regressions. The assistant accelerates; the engineer validates.
## Practice
- Review checklist: assumptions about data, join cardinality, null handling, collect-to-driver patterns, redundant reads.
- Tests and branch builds; compare counts and keys with expectations.
- Accountability: the merging engineer owns the change.
Example: the assistant's join defaults to inner; the reviewer spots dropped rows in the branch comparison and switches to left with a flag.
W: Draft, review, test, own: the assistant's speed is kept while the engineer's judgement catches wrong assumptions, unsafe patterns and regressions before anything merges.
X: A=Builds means merge: a build succeeds on wrong joins, dropped rows and scale-unsafe patterns alike; compilation is not correctness.
C=Ban: forgoes real productivity; the risk is managed by review, not prohibition.
D=Self-review: the same model's blind spots review its own output.
T: Use code assistants for drafts and keep human review, tests and accountability.
V: Continue, Code Repositories

@ PLTR-DE D8 T8.2 applied use-case
S: An LLM enrichment runs over sensitive customer notes. Which measures address data protection in the pipeline step itself?
A: None, since the model provider is responsible for protecting any data sent to it
B: Confirm model enablement for the data class, minimize and redact what is sent, keep prompts and responses under the source's markings, record versions
C: Send the full notes to the model as they are but delete the raw responses immediately after parsing so that nothing sensitive is retained
D: Use the cheapest available model to reduce the exposure window
K: B
G: ## Data protection inside AI transforms
The exam guide places AI processing under the same governance as any data handling and asks for security through the lifecycle. The model call is a data flow.
## Measures
- Model enablement for the data class (residency, contractual terms).
- Minimization: only necessary fields; redaction where possible.
- Outputs and stored prompts/responses carry the source's markings.
- Audit: model and prompt version per row.
Example: names and ids are masked before summarization; the summary dataset inherits the "Customer PII" marking.
W: Enablement check, minimization, redaction, inherited markings and audit: the pipeline step handles the data responsibly end to end.
X: A=Provider responsible: the organization remains responsible for what it sends and stores.
C=Delete responses: auditability lost, and the sending itself was unminimized.
D=Cheapest model: price has nothing to do with where data is processed or how it is retained; a cheap model can be the least compliant one.
T: Treat the model call as a governed data flow: enablement, minimization, inherited controls, audit.
V: markings, Pipeline Builder

@ PLTR-DE D8 T8.3 applied tradeoff
S: A pipeline enrichment with an LLM costs more than the rest of the platform usage combined. Most of the input rows are unchanged day to day, and the prompt changes rarely. What is the first optimization?
A: Switch to a much smaller model and accept whatever quality results from it
B: Cache results keyed by input content and prompt version so unchanged rows are skipped, and process only new or changed rows
C: Run the enrichment weekly instead of daily so the cost is spread over more days
D: Remove the enrichment from the pipeline entirely, since AI steps are inherently too expensive to run in production pipelines at this scale
K: B
G: ## Incremental AI enrichment
The exam guide lists caching among AI processing controls, and incremental processing is the data engineer's core tool. Reprocessing unchanged rows is waste.
## Design
- Cache key: hash(input fields) + prompt version + model.
- Incremental run over new or changed rows; cache hits skip the call.
- Full regeneration only on prompt or model change, as a bounded backfill.
Example: daily calls drop from 2 million to 30,000; quality and freshness unchanged.
W: Content-keyed cache with incremental processing: the cost falls by the share of unchanged rows, with no loss.
X: A=Smaller model: quality may drop, and the two million unnecessary daily calls on unchanged rows are still being made.
C=Weekly: freshness drops and unchanged rows are still reprocessed weekly.
D=Remove: the enrichment delivers value; the cost comes from reprocessing unchanged rows, which is a design issue with a direct fix.
T: Make AI enrichment incremental with content-keyed caching before touching model choice.
V: Code Repositories, Pipeline Builder

@ PLTR-DE D8 T8.4 applied troubleshooting
S: A code assistant generated a transform with a hard-coded list of 50 category names copied from the prompt. The categories change monthly. What should the engineer do before merging?
A: Merge it and update the list by hand each month when the categories change
B: Replace the hard-coded list with a reference dataset the transform reads, so changes flow through data, and add a test for unknown categories
C: Ask the assistant to regenerate the code each month with the new list
D: Keep the hard-coded list in the transform but add a comment recording the date it was last updated and who is responsible for refreshing it
K: B
G: ## Data belongs in datasets, not code
The exam guide asks engineers to review generated code for incorrect assumptions. A changing reference list embedded in code is a maintenance trap and a correctness risk.
## Fix
- Reference dataset `categories` maintained by the business, with expectations.
- Transform joins or looks up against it.
- Unknown categories flagged rather than silently dropped.
Example: a new category added to the reference dataset appears in the pipeline the next day with no code change.
W: Reference data instead of a hard-coded list: changes flow through governed data and unknowns are detected.
X: A=Monthly hand edits: a code change and release every month for a data change is fragile and will be forgotten or delayed.
C=Regenerate monthly: the same fragility with extra risk from regenerated code.
D=Dated comment: it documents when the list went stale; it does nothing to keep the categories current or to catch unknown ones.
T: Replace generated hard-coded reference values with governed reference datasets.
V: Code Repositories, expectations

@ PLTR-DE D8 T8.1 advanced tradeoff
S: A manager proposes using an AI assistant to "automatically fix" pipeline failures by letting it edit and redeploy transforms whenever a build fails. What is the sound response?
A: Agree, since faster fixes are always better for the business and the assistant can read error messages and stack traces more quickly than people
B: Decline automatic production edits: let the assistant diagnose and propose fixes on a branch, with human review, tests and branch validation before release
C: Agree, but only for failures that happen at night when no engineer is available
D: Agree, provided the assistant is told to be careful in its system prompt
K: B
G: ## Assistants propose; engineers release
The exam guide asks for review of AI-generated code and for safe change management through branches. Automated edits straight to production bypass every control that keeps pipelines trustworthy.
## Sound use
- Assistant: reads errors, suggests root cause and a fix, drafts the change on a branch.
- Engineer: reviews, runs tests and branch builds, merges.
- Operations: alerts and runbooks reduce time to fix without removing review.
Example: the assistant's proposed fix for a schema change is correct; the engineer validates it on a branch and merges in ten minutes.
W: Assisted diagnosis and proposals with human-reviewed release: speed without removing the controls.
X: A=Agree: an automated edit can turn a failed build into a successful build of wrong data.
C=Night only: the risk is the same at night; absence of engineers is an argument for alerts, not for unreviewed edits.
D=Be careful: a prompt is not a control over production changes.
T: Let assistants diagnose and propose; keep human review and branch validation for any production change.
V: Continue, Code Repositories, branches
