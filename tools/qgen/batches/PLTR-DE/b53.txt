@ PLTR-DE D7 T7.3 applied troubleshooting
S: A Ticket object type stores its labels in one string property holding comma-separated label ids such as "L12,L40,L7". Workshop filters by label miss tickets, and nobody can open a label object from a ticket. What is the right fix?
A: Keep the string property and ask app builders to write a custom text-contains filter in every application that needs to filter by label
B: Model Label as its own object type, add a many-to-many link to Ticket backed by a join dataset, and drop the packed string
C: Add a second string property that holds the labels in alphabetical order so that the filters match more predictably
D: Split the string into ten fixed properties named label 1 to label 10 so that each one holds a single label id
K: B
G: ## Repeating values do not belong in one property
The ontology is a model of things and their relationships. A list packed into a string hides both the items and the relationship from the platform.
## What goes wrong
- Filters see one opaque string, so partial matches, ordering and typos all break results.
- A label is a real entity with its own attributes; packed ids cannot be traversed as links.
## Better shape
- A Label object type with its own primary key.
- A many-to-many link type, which needs a backing join dataset with one row per ticket-label pair.
Example: ticket T1 and labels L12, L40 become two rows in the join dataset, and each label is one click away.
W: Label object type with a many-to-many link: each label becomes a first-class object, filters use real link or property values, and the string hack disappears.
X: A=Custom text-contains filters: every app repeats fragile string logic, and "L1" matches "L12", so errors stay.
C=Alphabetical copy: sorting a packed list does not make it queryable and adds a second property to keep in step.
D=Ten fixed label properties: caps the label count, leaves mostly empty columns and still gives no traversal to label objects.
T: Model repeating or shared values as linked objects, not as delimited strings.

@ PLTR-DE D7 T7.3 applied comparison
S: A team creates a separate object type for every month of orders (Orders2026_01, Orders2026_02 and so on), each with the same properties. Every new month needs a new type and dozens of application edits. What is the better design?
A: One Order object type with an order date property, partitioned or filtered by date range in the backing data and in applications
B: Keep the monthly types but add a naming convention document so developers know which type to select for each report
C: One Order object type per year instead of per month, which divides the maintenance effort by twelve without further changes
D: A single object type that stores only the current month and deletes the previous month's objects when a new month starts
K: A
G: ## Data values are not schema
Object types describe kinds of things. A time period is a value of a thing, so it belongs in a property. Creating a type per period multiplies schema, permissions and application bindings.
## Cost of per-period types
- Every report must union types and every new period needs a release.
- Cross-period questions need links or code that treats the types as one.
## Better shape
- One Order type with an order date property; applications filter by range.
Example: a year view is a date-range filter on one type, not a union of twelve.
W: One Order type with an order date property: the schema stays stable, and new months are just new rows in the backing data.
X: B=Naming convention document: documents the duplication without removing it, and each month still needs new types and app edits.
C=One type per year: still creates a type for each period and still needs yearly schema work.
D=Current month only: destroys history that the business needs for comparison and audit.
T: Put time periods in properties and filters, never in additional object types.

@ PLTR-DE D7 T7.3 applied troubleshooting
S: A Customer object type has properties phone 1, phone 2, phone 3, email 1 and email 2, most of which are empty. Search by phone number must check three properties, and a customer with four phones cannot be stored. What is the better design?
A: Add phone 4 and phone 5, and email 3, so that nearly every customer fits within the existing columns

@ PLTR-DE D7 T7.3 advanced tradeoff
S: To save effort, an architect proposes one generic object type "Record" with a record type property and twenty text properties named field 1 to field 20, reused for invoices, shipments and contracts. What is the main problem with this design?
A: Generic types always load much more slowly than specific ones because the platform scans all twenty properties for every query
B: The platform forbids more than one object type from being backed by the same kind of source dataset in the ontology
C: Property names with numbers in them cannot be used as filters in Workshop or referenced in function code
D: Meaning, types, validation and permissions are lost, so nobody can tell what field 7 is and every application must decode it
K: D
G: ## One type per kind of thing
An object type gives a kind of thing a name, typed properties and a meaning that applications and people can rely on. Reusing one generic shape for many kinds moves that meaning into tribal knowledge.
## Costs
- Numbers, dates and text all become strings, so filtering and sorting break.
- Links, actions and security need to be per kind, which a catch-all type cannot express.
Example: "field 7" is a due date on contracts and a weight on shipments.
W: Loss of meaning and types: each application must know the hidden convention for every record type, which is what the ontology exists to avoid.
X: A=Slower queries: this is not the core issue; the structural cost is semantics and types, not scanning twenty properties.
B=Platform restriction: the ontology does not forbid several object types from sharing a similar source pattern.
C=Numbered names unusable: such properties can be filtered and referenced; the problem is that their meaning is undefined.
T: Model each kind of thing as its own type with named, typed properties instead of a generic catch-all.

@ PLTR-DE D7 T7.5 advanced tradeoff
S: Dispatchers use a Workshop what-if panel where they type a hypothetical fuel price and instantly see the projected cost of each route. The price is different for every dispatcher and every try. Where should this calculation run?
A: North of the Ontology, in a function that takes the typed price as input and returns costs without writing anything back
B: South of the Ontology, in a nightly transform that precomputes the cost for every possible fuel price to materialize each as a property
C: In a scheduled build triggered by each keystroke so that the result is saved into a backing dataset for the route object
D: In the source system, by asking its administrators to add one cost column per dispatcher so everyone sees the same value
K: A
G: ## North versus south
South logic runs in the pipeline and materializes a column. North logic runs on demand in functions or applications at read time.
## When north wins
- The input is known only at use time (a typed value, a selection).
- The result is ephemeral and personal, not something to store.
Example: the cost for a price of 1.87 exists only while the dispatcher looks at it.
W: A function with the price as input: it computes on demand from stored route attributes, and nothing is written back for a transient what-if.
X: B=Precompute for every price: the input space is unbounded, so the pipeline would be huge and still incomplete.
C=Build per keystroke: builds take far longer than interactive use, and a stored result for a hypothetical value is meaningless data.
D=Per-dispatcher columns in the source: pushes a user-interface concern into the system of record and does not scale.
T: Inputs known only at use time call for north-of-Ontology computation.
V: Functions, Workshop

@ PLTR-DE D7 T7.5 applied use-case
S: Two object types, Shipment and Customs Broker, must be linked. The link key is the shipment's reference after trimming whitespace, uppercasing and removing a legacy prefix, and it must exist as a column in the dataset for the link to work. Where does this normalization belong?
A: In a Workshop variable, so the key is calculated in the browser for every shipment shown on the page
B: In the transform that builds the backing dataset, so the normalized key is a stored column used by the link
C: In a function that applications call whenever they need to traverse the link from a shipment to its broker
D: In the training material for brokers, who are told to type the references the normalized way when they create records
K: B
G: ## Keys and links are south logic
A link is a join over stored columns. Anything that determines which objects are connected must exist as data before the ontology reads it, so cleaning logic for keys belongs in the pipeline.
## Why not north
- Application-side logic cannot create a link that other apps, searches and actions rely on.
- Every consumer would need to repeat the same rule, and rules would drift.
Example: a transform writes the normalized column once, and the link type uses it.
W: Transform producing a stored normalized key: the link joins on real data, all consumers see the same connections and the rule is tested in one place.
X: A=Workshop variable: only one page would see it; links, searches and other apps could not use it.
C=Function at traversal time: traversal itself needs the column, and each app would pay the cost and might differ.
D=Training brokers: relies on manual consistency for a deterministic cleaning rule that code does exactly.
T: Keys and link columns are computed in the pipeline, south of the Ontology.

@ PLTR-DE D7 T7.5 applied troubleshooting
S: A "distance to nearest depot" value for 3 million parcels was added as a function-backed property computed live. List views are now slow when users sort by it, and several saved filters time out. The distance changes only when a parcel's coordinates are updated, once or twice a day. What is the best correction?
A: Increase the page size of the list views so that more objects are computed and shown at once to users
B: Remove the filters and sorts on the property, and tell users to compare distances by reading values one by one
C: Wrap each list in a fixed row limit so that it never computes more than ten parcels at any time
D: Materialize the distance in the pipeline as a stored property, refreshed when coordinates change
K: D
G: ## Sort and filter need stored values
Computing a value at read time is fine for a few visible objects. Sorting or filtering across millions of objects is far cheaper when the value is already stored with the object (general design reasoning, not a documented limit).
## Decision rule
- Values slow to compute, changing rarely and needed for filtering or sorting belong south of the Ontology.
- Values depending on input at use time stay north.
Example: coordinates update twice a day, so a daily refreshed column is always fresh enough.
W: Materialized stored property: sorting and filtering read a stored value, and the compute cost moves to a pipeline run that happens when the data changes.
X: A=Bigger pages: asks the live computation to do more work per view, which makes the slowness worse.
B=Remove sort and filter: gives up the user need rather than meeting it with a better placement.
C=Hard row limit: hides most parcels and makes sorting incorrect, since only ten are ever evaluated.
T: Rarely changing values used for sort and filter belong in the pipeline as stored properties.

@ PLTR-DE D7 T7.5 applied comparison
S: A team debates two derived values: (1) the number of open orders per customer, used in dashboards, filters and alerts across many apps; (2) a one-off ranking that one analyst builds in a single exploratory workbook to compare scenarios. How should the placement differ?
A: Both are calculated in the analyst's workbook, so there is a single approach to explain to everyone in the organization
B: The count is materialized south of the Ontology; the ranking stays in the workbook or an application, north of the Ontology

D: Both are computed live in functions every time, so that no pipeline logic needs to exist for either of them

Shared, widely filtered values deserve one governed definition that every consumer reads. Personal, exploratory values should not become permanent schema.
## Rule of thumb
- Reused across apps, filtered or alerted on: south, materialized once.
- Single-use, exploratory or input-driven: north, near the person who needs it.
Example: the open-order count feeds an alert, so it must be an indexed, consistent property.
W: Count in the pipeline, ranking in the workbook: the shared metric gets one definition, and the throwaway analysis does not clutter the Ontology.
X: A=Both in the workbook: other apps and alerts could not read the count, and definitions would diverge.
C=Reversed placement: promotes a personal analysis to permanent schema and leaves the shared metric inconsistent.
D=Both live in functions: alerts and filters on a live count over many customers are slow, and the logic is still duplicated per use.
T: Materialize shared, filtered metrics south; keep exploratory ones north.

@ PLTR-DE D7 T7.1 applied troubleshooting
S: Users of a Workshop app see employee names shown as numeric ids such as "100482" in object lists and link chips, although the objects load correctly. What most likely needs to be corrected on the Employee object type?
A: The title key should be set to the property holding the employee's full name instead of the identifier
B: The primary key should be changed to the full name so that the lists show readable text from now on
C: The backing dataset must be rebuilt so that the Workshop lists regenerate their labels for every employee
D: The link type should be deleted and recreated, because link chips take their text from the link's API name
K: A
G: ## Primary key versus title key
Two different properties play two different roles on an object type.
- Primary key: the unique identifier for each object; every row in the backing datasource must have a different value.
- Title key: the property used as the display name of the object.
Example: the employee ID identifies "Melissa Chang" uniquely, while the full name property is what users should see.
## Why it matters
Changing the display never needs a key change. Edits and links attach to the primary key value, so changing a key is risky.
W: Title key set to the full name: the display name comes from the title key, while the primary key can stay a stable identifier.
X: B=Full name as primary key: names are not guaranteed unique or stable, and edits and links attach to the primary key value, so changing it risks them.
C=Rebuild the dataset: the data is fine; the display is controlled by object type configuration, not by a rebuild.
D=Recreate the link type: the display name of an object comes from its title key, not from the link, so recreating the link fixes nothing and risks the links.
T: Readable names in the UI come from the title key, not from the primary key.

@ PLTR-DE D7 T7.1 applied use-case
S: A developer plans two link types between Flight and Aircraft: one named "Flight to Aircraft" and another "Aircraft to Flight", to allow navigation both ways for the same assigned-aircraft relationship. What should the architect advise?
A: Create both, because each link type supports traversal in only one direction and the reverse requires its own definition
B: Create the first and delete it again later, since the platform adds the reverse automatically only after a full rebuild
C: Create a single link type; it has two sides, so traversal works in both directions without a second definition
D: Replace the links with a shared property holding the aircraft id, since object types cannot reference each other directly

A link type is the schema definition of a relationship between two object types. It is bidirectional: each side can be traversed on its own and has its own display name and API name.

- One link type from Flight to Aircraft already gives Flight a way to its aircraft and Aircraft a way to its flights.
- A second link type between the same two types is for a different real-world relationship, such as a maintenance record.

B=Reverse added after a rebuild: no such automatic step exists, and nothing about a rebuild is needed for the second side.
D=Shared property instead: object types are related with link types, which also give traversal and application support.
T: One link type gives both directions; add another only for a different relationship.

@ PLTR-DE D7 T7.4 applied troubleshooting
S: An object type backed by a daily dataset begins failing its nightly indexing after an upstream change introduced two rows with the same primary key value. Dashboards still show yesterday's objects. What is the best response?
A: Change the primary key to a randomly generated value per row so the failing duplicates stop colliding in the index
B: Disable the object type so that applications fall back to reading the raw dataset, which has no uniqueness requirement
C: Repair the upstream logic so each key appears once in the backing dataset, then let the next build re-index
D: Delete all user edits on the object type so that the build starts from a clean state that avoids the collision
K: C
G: ## Primary keys must be unique and deterministic
The primary key must be unique for every record in the datasource. With Object Storage v2, a duplicate primary key causes Funnel batch pipeline errors that lead to a build failure, so the object type keeps showing the last good state.
## Right fix
- Find where the duplicates enter, usually a join or a changed source feed.
- Fix or deduplicate upstream so the key is unique again.
## What not to do
A non-deterministic key makes edits vanish and links disappear, because both attach to the key value.
W: Fix the duplicates upstream: the key stays stable, edits and links remain attached, and the next build indexes cleanly.
X: A=Random per-row key: non-deterministic keys change on each build, so edits are lost and links can disappear.
B=Disable the type: breaks every application built on the Ontology and bypasses governance instead of fixing the data.
D=Delete user edits: removes legitimate business data and does nothing about the duplicate rows that cause the failure.
T: A duplicate primary key breaks indexing; fix uniqueness at the source and keep keys deterministic.

@ PLTR-DE D8 T8.2 advanced tradeoff
S: A nightly job sends all 2 million product descriptions to an LLM to extract a material type, though fewer than 1% of descriptions change from one day to the next. Cost is high and the results for unchanged rows are identical each time. What is the best design?
A: Process only new or changed descriptions incrementally, and keep previous results for the descriptions that did not change

LLM calls cost per input. If the input has not changed, the earlier output is still valid, so reuse it (general cost-design reasoning, not a documented Foundry rule).
## Approaches
- Incremental processing of new and changed rows only.
- Reusing stored results (caching) for repeated or unchanged inputs.
- Keep a full recompute for deliberate events such as a prompt or model change.
Example: 20,000 changed descriptions per night instead of 2,000,000.
W: Incremental processing with stored results: only changed descriptions pay for a call, and unchanged ones keep their valid output.
X: B=Full nightly resend: repeated identical inputs give no accuracy gain and multiply cost 100 times.
C=Monthly refresh: new products wait up to a month for their material type, failing freshness needs.
D=Regex without checking: swaps a tested capability for rules whose coverage is unknown; compare on a sample first.
T: Avoid repeat LLM calls for unchanged inputs by processing incrementally and reusing results.

@ PLTR-DE D8 T8.2 applied use-case
S: The team wants to replace the prompt of a production LLM classification step with a new version that should be more accurate. What should happen before the new prompt replaces the old one?

@ PLTR-DE D8 T8.3 advanced tradeoff
S: Analysts need an AI-generated "root cause category" on 800,000 historical incident records. The category will feed aggregations, joins to a cost table and long-term reports. Where should the LLM be applied?
A: In the pipeline, once per record, writing the category to a dataset that downstream joins and aggregations read
B: In a Workshop widget that calls the model every time a user opens an incident, with nothing saved afterwards
C: In a function that asks the model during each aggregation, so categories are recomputed whenever a report loads
D: Nowhere, because aggregations cannot be built on top of any column that an LLM produced for the records
K: A
G: ## Batch enrichment belongs in the pipeline
A value that many consumers join and aggregate must exist as stored data. Computing it once per record in the pipeline gives a consistent, auditable column.
## Why not in the app layer
- On-demand calls recompute per view, cost more and may return different categories each time.
- Aggregations over 800,000 rows cannot wait for 800,000 model calls on every report.
Example: the pipeline writes the category once; a later prompt change triggers a deliberate re-run.
W: Pipeline enrichment writing a stored column: joins and aggregates read stable values, and cost is paid once per record.
X: B=Per-open widget calls: not stored, so reports cannot aggregate them and each opening may produce a different category.
C=Model per aggregation: repeats the cost on each report load, with varying results that make totals inconsistent.
D=Never use LLM columns: stored LLM outputs are ordinary data once written; the quality is handled by checks.
T: Bulk enrichments used for joins and reports run in the pipeline and are stored.
V: LLM transforms

@ PLTR-DE D8 T8.3 applied troubleshooting
S: A team asked an LLM to produce a "case id" for each incoming document and made that value the primary key of a Case object type. After a rebuild, the same documents received different ids, user edits vanished and links disappeared. What was the design mistake?
A: The model was too small, and a larger model would have produced identical identifiers on every rebuild
B: A non-deterministic LLM output was used as the primary key; keys must be unique and deterministic, derived from source data
C: Case objects should never have a primary key, because keys are only required for backing datasets that use transforms
D: The rebuild should have been scheduled less often, since frequent builds are the only cause of changing identifiers
K: B
G: ## Never key an object on model output
A primary key identifies an object. Edits and links attach to the key value, so a key that changes on build loses edits and breaks links.
## Rules
- Primary keys must be unique and deterministic.
- Derive them from stable source data (a source id or a hash of stable fields).
- Use LLMs for attributes that can be recomputed or corrected, never for identity.
Example: the case id comes from the document's source reference; the LLM adds a category property.
W: LLM output as the key: it is not deterministic, so each build can assign new ids and detach edits and links.
X: A=Larger model: even a bigger model is not guaranteed to be deterministic, and identity should not depend on generation at all.
C=No key: every object type requires a primary key to uniquely identify its objects.
D=Fewer builds: hides the symptom; any rebuild can still reassign ids, and the fault remains.
T: Keys come from deterministic source data; LLMs enrich properties, never identity.
V: LLM transforms, Ontology Manager

@ PLTR-DE D8 T8.3 applied use-case
S: Case workers upload a scanned form in an application and need the key fields extracted and shown on screen within seconds so they can correct them before saving. Where does the AI step belong?
A: In the nightly pipeline, so the extracted fields appear the following morning after the next build has finished
B: In the application layer, as an on-demand AI-backed function invoked at upload, with the worker confirming the values
C: In the source system's database, as a trigger that rewrites every uploaded file into a text column unseen
D: In a monthly batch, since AI extraction is cheaper when many forms are processed together in a single run
K: B
G: ## Interactive work belongs in the application layer
When a person needs an answer in the moment and will confirm or edit it, the AI step runs on demand where the person works.
## Fit
- The input exists only at upload time.
- A human in the loop reviews the result before it is saved.
- Result: an editable draft, not a bulk column.
Example: the function returns the fields; the worker corrects one and saves an action.
W: On-demand function at upload with human confirmation: latency fits the task and the person validates the output before it becomes data.
X: A=Nightly pipeline: the worker would wait until the next day for a result needed within seconds.
C=Database trigger: unseen rewriting without a person validating it, and it moves AI into a system of record.
D=Monthly batch: efficiency does not justify a delay that makes the feature useless for the worker.
T: Interactive, human-confirmed AI belongs in the application layer, bulk enrichment in the pipeline.
V: AIP Logic, Functions, Workshop
