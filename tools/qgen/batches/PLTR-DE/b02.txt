# PLTR-DE batch 02: Domain 1 (Data Connectivity and Ingestion), 8 questions

@ PLTR-DE D1 T1.1 applied comparison
S: A company needs to ingest tables from an Oracle database that sits inside its corporate network with no inbound internet access, and the database team will not open the firewall. Which connection architecture fits?
A: A direct connection from Foundry to the database over the internet, using the database's public endpoint and TLS for security
B: An agent installed on a host inside the corporate network that makes outbound connections and runs the syncs on Foundry's behalf
C: A nightly export from the database to CSV files that an employee uploads to Foundry by hand through the browser
D: A virtual table that queries the Oracle database live from Foundry, which needs no connection to be configured
K: B
G: ## Direct connections and agents
Data Connection supports two broad architectures. A **direct connection** is made from Foundry to a source that Foundry can reach over the network. An **agent** runs on a host inside the customer's network: it connects to the source locally and talks outbound to Foundry, so no inbound firewall rule is needed.
## Choosing by network reachability
The exam guide asks you to select connectors and connection architectures based on source protocol, network reachability and required capabilities. "No inbound access, firewall stays closed" is the agent case by definition.
- Agent health becomes part of operations: if the host is down, syncs fail.
- Credentials are configured in the source, not shared with people.
Example: the agent on a server in the data centre runs a JDBC sync against Oracle every hour and pushes the data outbound to Foundry.
W: Agent-based connection: it satisfies the network constraint because all traffic is outbound from inside the network, and the syncs run as managed Data Connection syncs.
X: A=Direct over the internet: the database has no public endpoint and the firewall will not be opened, so a direct connection cannot reach it.
C=Manual CSV uploads: this is not an ingestion architecture; it is unreliable, unscheduled and loses lineage and freshness tracking.
D=Virtual table without a connection: a virtual table still needs a configured source that Foundry can reach; it does not bypass the network problem.
T: When a source is not reachable from Foundry and the network cannot be opened, use an agent that connects outbound.
V: Data Connection, agents

@ PLTR-DE D1 T1.2 applied tradeoff
S: A transactions table with 400 million rows receives new rows continuously and existing rows are never updated. The current sync copies the whole table every night and takes seven hours. Which sync pattern should replace it?
A: A snapshot sync run twice a day, so each copy is fresher even though every run still copies the full table
B: An append sync keyed on an increasing column such as the transaction id, fetching only rows added since the last run
C: A change-data-capture sync that reads the database's transaction log to replicate inserts, updates and deletes in near real time
D: An update sync that compares every row with the previous copy and writes only the rows whose values differ
K: B
G: ## Ingestion patterns
The exam guide asks you to distinguish snapshot, append, update and change-data-capture patterns:
- **Snapshot**: copy everything; simple, correct, expensive for large tables.
- **Append (incremental)**: fetch only new rows using a column that grows (id, timestamp); cheap when rows are never changed.
- **Update**: handle rows that change in place; needs a reliable "last modified" signal.
- **CDC**: read the database log for inserts, updates and deletes; most capable and most complex.
## Matching the source
Rows are only ever added, and there is an increasing key. An append sync reads a sliver per run and the full-table copy disappears. Keep a periodic snapshot or reconciliation to catch any rows added out of order.
Example: nightly run fetches rows with `transaction_id > last_seen_id`, about 1.2 million rows in minutes.
W: Append sync on an increasing column: it matches an insert-only source exactly, cutting the seven-hour copy to the new rows only.
X: A=Snapshot twice daily: this doubles the cost of the full copy rather than removing it.
C=CDC: capable but complex to set up and operate; it is unnecessary for a source with no updates or deletes.
D=Update sync by comparison: comparing 400 million rows each run is as expensive as the snapshot and solves a problem (updates) the source does not have.
T: For insert-only sources with an increasing key, use an append sync; reserve CDC for sources with updates and deletes that need low latency.
V: Data Connection

@ PLTR-DE D1 T1.3 applied use-case
S: A data science team wants to explore a 2 TB table in an external cloud warehouse before deciding whether to build a pipeline on it. Copying the table into Foundry would take a day and duplicate storage. What should the data engineer offer?
A: A virtual table that registers the warehouse table in Foundry and queries it in place, so the team can explore without first copying the data
B: A snapshot sync of a 1% sample of the table, so the team can explore a small copy and then request the full copy later
C: A streaming sync from the warehouse so that the data arrives continuously and the team can start exploring the first rows immediately
D: A manual export of the table to Parquet files that the team places in a Foundry dataset using the upload feature
K: A
G: ## Virtual tables
The exam guide lists agents, egress policies, virtual tables, exports and sync health among the concepts to know. A **virtual table** registers a table that lives in an external system (a cloud warehouse, a lakehouse) so that Foundry can read it in place, without ingesting a copy. Compute and storage stay on the source for the read.
## When it fits
- Exploration and evaluation before committing to a pipeline.
- Data that must remain in the source system of record.
- Cases where a copy would be large, slow or duplicate storage.
If the team later needs transforms, lineage within Foundry and Ontology backing at scale, a materialized ingestion may follow.
Example: the virtual table appears as a dataset-like resource; the team queries it, finds the columns they need, and the pipeline is designed on evidence.
W: Virtual table: the team explores the real table in place today, with no day-long copy and no duplicated storage, which is exactly the need described.
X: B=1% sample copy: a sample misses rare values and still requires a pipeline just to produce it; it delays the full question rather than answering it.
C=Streaming sync: a batch table in a warehouse is not a stream; streaming adds complexity and still copies all the data.
D=Manual Parquet upload: 2 TB through manual upload is impractical and produces an ungoverned, stale copy.
T: To explore or use external data without copying it, register a virtual table.
V: Data Connection, virtual tables

@ PLTR-DE D1 T1.4 applied troubleshooting
S: A sync from a REST API that ran reliably for months began failing yesterday. The agent is healthy and the credentials have not changed. The execution history shows every run ending with an error shortly after it starts. What is the most useful next check?
A: Replace the API connection with a new one configured from scratch, since a connection that fails after months is usually corrupted
B: Read the error in the sync's execution history and compare the API's current response and schema with the last successful run
C: Rerun the downstream pipeline with a forced snapshot build, since the error may come from stale derived datasets rather than the sync
D: Increase the sync frequency so that one of the runs succeeds between the API's intermittent failures
K: B
G: ## Diagnosing ingestion with evidence
The exam guide asks you to diagnose stale or failing ingestion using execution history, agent health, credentials, schema evidence and Data Health. Two of those are already ruled out (agent, credentials), so the remaining evidence is the run's own error and the source's behaviour.
## What usually changed
- The API changed: a renamed field, a removed endpoint, a new required parameter, a stricter rate limit, a different pagination format.
- The error message in execution history normally says which (HTTP 404, 429, schema mismatch).
- Comparing the response with the last known-good run shows the difference precisely, and the fix is targeted (update the sync configuration or the schema).
Example: the error is "unexpected field type for `amount`"; the API started returning amounts as strings, and the sync's schema is updated.
W: Execution-history error plus comparison with the last good run: it identifies the actual change at the source, which is the only thing left that could have broken a stable sync.
X: A=Recreate the connection: connections do not corrupt with age; rebuilding without a diagnosis usually recreates the same failure.
C=Rebuild downstream: the sync itself fails, so downstream datasets are not the problem and a forced rebuild would run on stale input.
D=Run more often: the failures are consistent, not intermittent; more attempts produce more identical errors and may trigger rate limits.
T: When a stable sync starts failing, read the run's error and compare the source's current response with the last successful one.
V: Data Connection, Data Health

@ PLTR-DE D1 T1.3 applied use-case
S: A finance team needs a curated dataset exported every night from Foundry to a partner's SFTP server. Security asks that only this one dataset can leave the platform through that route. How should it be set up?
A: Give the pipeline's service user the SFTP server credentials and let the transform write the files there directly from its own code each night
B: Configure an export to the SFTP destination under an egress policy that allows only the approved dataset through it
C: Share the dataset with the partner as a Foundry user account, so they log in and download the file themselves each night
D: Email the file to the partner from a scheduled function, since email is already approved for external communication
K: B
G: ## Exports and egress policies
Data leaving the platform is governed. The exam guide lists egress policies and exports among the concepts for this domain. An **export** sends dataset contents to an external destination (SFTP, cloud storage, another system) on a schedule; an **egress policy** defines which destinations may receive data and which data may go, so that exfiltration cannot happen through an arbitrary code path.
## Why it matters
- Allow-listing: only the approved dataset, only to the approved destination.
- Audit: each export run is recorded.
- Separation: the transform writes datasets; the export moves them; the policy constrains it.
Example: the export job runs at 02:00, pushes the curated file to the partner's SFTP, and any attempt to export another dataset through the same route is blocked by policy.
W: Governed export with an egress policy: it meets the requirement that exactly one dataset can leave through this route, with the transfer scheduled and audited.
X: A=Credentials in code: a transform writing to external servers bypasses egress governance; any dataset could be sent the same way.
C=Partner account: granting platform access to a partner for a nightly file is excessive and relies on them remembering to download.
D=Email: email attachments are not a governed data transfer, size-limited and unauditable as an export.
T: Move data out of the platform through governed exports under egress policies, never through ad hoc code or email.
V: Data Connection, exports

@ PLTR-DE D1 T1.2 advanced troubleshooting
S: A customer table is ingested with an update sync keyed on a `last_modified` timestamp. Analysts notice that some customers whose addresses changed in the source still show the old address in Foundry. Which cause should be investigated first?
A: The source sometimes updates the address without advancing `last_modified`, so those rows are never selected
B: The agent is too slow for the sync window, so the newest rows are cut off before the sync completes each night
C: The downstream Ontology object type caches old property values, so the dataset is correct but the object view is stale
D: The sync is incorrectly set to append mode, which would explain why updated rows are added rather than replaced
K: A
G: ## The watermark assumption
An update sync depends on a reliable signal that a row changed, usually a `last_modified` column (the watermark). If the source changes a row without advancing the watermark, the row looks unchanged and is skipped. The exam guide stresses understanding sync patterns and their failure modes.
## Checking it
- Query the source for the affected customers: is `last_modified` older than the address change? If so, the source is the problem (a batch job, a direct SQL fix, or a trigger that bypasses the column).
- Compare with the sync's last watermark value.
- Mitigations: a periodic full snapshot to reconcile, a different change signal (CDC), or a fix in the source.
Example: a nightly job in the source corrects addresses with a bulk update that does not touch `last_modified`; a weekly snapshot reconciliation catches these rows.
W: Watermark not advanced in the source: it exactly produces "changed in source, unchanged in Foundry" for a subset of rows, and it is verified by querying the source rows.
X: B=Slow agent: a cut-off run would miss the newest rows across the board and show in execution history as failures or timeouts, not a subset of silent misses.
C=Object cache: the question concerns the dataset; if the dataset were correct, the object would refresh on the next indexing. Check the dataset first.
D=Append mode: append would add duplicate rows with new addresses, so the new address would be visible (twice), not missing.
T: An update sync is only as good as its change signal; when rows are missed, check whether the source actually advances the watermark.
V: Data Connection

@ PLTR-DE D1 T1.1 applied use-case
S: A manufacturer wants to ingest sensor readings from 2,000 machines that publish messages to a Kafka topic at about 50,000 messages per second. Analysts need dashboards that lag the sensors by no more than a minute. Which ingestion should be set up?
A: A batch sync that polls the topic every hour and writes the messages to a dataset, which is far simpler to operate than a streaming setup
B: A streaming sync from the Kafka topic into a streaming dataset, with a streaming pipeline aggregating for the dashboards
C: An agent that writes the Kafka messages to CSV files and uploads them once a day
D: A virtual table over the Kafka topic so that dashboards query the live stream directly
K: B
G: ## Streaming ingestion
The exam guide expects you to choose the connection and sync pattern from the source and the freshness requirement. A Kafka topic at high volume with a one-minute freshness need is a streaming source with a streaming requirement.
## The streaming path
- A streaming sync consumes the topic continuously into a streaming dataset.
- A streaming pipeline (Pipeline Builder streaming) can window and aggregate.
- Downstream, the aggregated output feeds the dashboards, and the Ontology can expose live values if needed.
Streaming adds operational complexity (state, backlogs, replay), so it is reserved for genuinely continuous requirements, which this is.
Example: a per-machine one-minute average is produced continuously; the dashboard shows readings within seconds of the sensor.
W: Streaming sync and pipeline: the source is a stream and the freshness requirement is sub-minute, which batch patterns cannot meet.
X: A=Hourly batch: it violates the one-minute freshness requirement by an hour.
C=Daily CSV via agent: this loses the stream's continuity and lags by a day.
D=Virtual table over Kafka: virtual tables register tables in external systems; a message stream is not a table to be queried in place.
T: Continuous, high-volume sources with tight freshness needs use streaming syncs and streaming pipelines.
V: Data Connection, streaming

@ PLTR-DE D1 T1.4 applied use-case
S: A team has twenty syncs from different sources. They want to be notified when any sync fails or when a dataset has not received new data within its expected window, without checking each sync by hand. What should they configure?
A: A daily manual review of the execution history of all twenty syncs by the on-call engineer
B: Data Health checks on the synced datasets, such as sync status and time-since-last-update, with alerts routed to the team
C: A downstream transform that fails its build whenever its input dataset is older than expected, which serves as the alert
D: A spreadsheet listing each sync's expected cadence, updated by whoever notices a problem
K: B
G: ## Monitoring ingestion
The exam guide names Data Health among the evidence for diagnosing stale or failing ingestion. Health checks run against datasets on a schedule and evaluate conditions: build or sync status, time since last update, size changes, schema changes. Failing checks raise alerts to subscribed users or channels.
## For twenty syncs
- Status check: notifies on any failed sync.
- Freshness check: each dataset has its own expected window (hourly, daily).
- Alerts go to a channel or on-call rotation, so the team acts on problems rather than looking for them.
Example: the Oracle customer sync fails at 02:00; the status check alerts at 02:05; a freshness check on the weekly supplier feed only fires if eight days pass.
W: Data Health checks with alerts: they monitor status and freshness per dataset automatically, which is exactly "notified when any sync fails or data is late".
X: A=Daily manual review: slow, error-prone and the opposite of the requirement to avoid checking by hand.
C=Failing transforms as alerts: this breaks downstream builds to signal a problem, mixing data quality with ingestion monitoring, and alerts only when that transform happens to run.
D=Spreadsheet: it records expectations without monitoring anything; nobody is notified.
T: Monitor sync status and dataset freshness with Data Health checks and alerts rather than manual inspection.
V: Data Health, Data Connection
