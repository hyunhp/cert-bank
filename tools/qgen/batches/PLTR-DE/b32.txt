# PLTR-DE batch 32: Domain 7 round 4 (Ontology Data Modeling), 8 questions

@ PLTR-DE D7 T7.1 applied use-case
S: A company models Suppliers and Contracts. A contract can involve several suppliers (consortia), and a supplier has many contracts. Each supplier's share of a contract must be recorded. Which model is correct?
A: A many-to-many link between Supplier and Contract with no properties, with the share stored as a list on the Contract object in the same order as the linked suppliers
B: A ContractParticipation object type keyed by contract and supplier, holding the share, linked many-to-one to both Contract and Supplier
C: A share property on Supplier, since each supplier has one share
D: A Contract object per supplier, duplicating the contract for each participant
K: B
G: ## Many-to-many with attributes
The exam guide asks for normalized modeling of links and properties. A share belongs to the pair (contract, supplier), so the pair must be an object.
## Model
- ContractParticipation: key (contract_id, supplier_id), property `share`.
- Links: Participation → Contract, Participation → Supplier.
- Queries: a contract's participants with shares; a supplier's contracts with shares.
Example: contract C-9 has three participations: 50%, 30%, 20%.
W: A participation object keyed by the pair with the share as its property: the attribute lives where it belongs and both directions are queryable.
X: A=Ordered lists: fragile, unqueryable and unlinked; order desynchronizes easily.
C=Share on Supplier: a supplier has a different share in every contract.
D=Contract per supplier: duplicates the contract and breaks its identity.
T: When a many-to-many relationship carries attributes, model it as an object type keyed by the pair.
V: Ontology Manager

@ PLTR-DE D7 T7.2 applied troubleshooting
S: An object type's primary key is a composite of three source columns concatenated with a hyphen. Occasionally two different source rows produce the same key because one of the columns itself contains hyphens. What should change?
A: Nothing; collisions are rare enough that the affected objects can be split and fixed by hand whenever someone notices a merge
B: Build the key unambiguously (an absent delimiter, escaping, or a hash of the typed components) and add a uniqueness expectation
C: Drop the column that contains hyphens from the key so that only two clean columns remain and the delimiter scheme is unambiguous
D: Use the dataset row number as the primary key instead, which is guaranteed unique within any single build of the dataset
K: B
G: ## Composite keys done safely
The exam guide asks for stable, unique primary keys. Concatenation with a delimiter that can appear inside the parts is ambiguous: "A-B" + "C" equals "A" + "B-C".
## Fix
- Unambiguous composition: a delimiter guaranteed absent, escaping, or a hash of the typed tuple.
- Uniqueness expectation on the backing dataset to catch any future collision.
- Migrate existing keys with a mapping for edits and links.
Example: hashing (region, site, asset_no) produces distinct keys where the hyphen scheme collided.
W: Unambiguous key construction with a uniqueness expectation: collisions are eliminated and guarded against.
X: A=Rare and manual: merged objects corrupt data each time; "rare" is still wrong.
C=Drop a column: the remaining two may not be unique; the key loses meaning.
D=Row number: unstable across rebuilds; edits and links detach.
T: Construct composite keys unambiguously (escaped or hashed) and enforce uniqueness with an expectation.
V: Ontology Manager, expectations

@ PLTR-DE D7 T7.3 applied tradeoff
S: Applications need to filter Orders by the customer's country, which lives on the Customer object. Traversing the link for every filter is slow. What is the appropriate modeling response?
A: Copy every Customer property onto each Order object so that applications never need to traverse a link for any customer attribute
B: Denormalize minimally: add a derived `customer_country` property to Order, computed in the pipeline and documented, keeping the link
C: Remove the Customer object type entirely and store all customer data only on the Orders that reference each customer
D: Ask the application teams to stop offering a country filter on order lists, since the traversal cost makes it too expensive
K: B
G: ## Selective denormalization
The exam guide asks for normalization principles while keeping the Ontology useful to applications. Copying one frequently filtered attribute, documented as derived, is a legitimate performance choice; copying everything is the anti-pattern.
## Practice
- Add `customer_country` on Order, computed in the pipeline.
- Keep the link; the Customer object remains authoritative.
- Document derivation and refresh cadence; expectation that it matches the linked customer.
Example: order lists filter by country instantly; a customer's country change propagates on the next build.
W: One derived property, documented and kept consistent, with the link preserved: performance without abandoning normalization.
X: A=Copy everything: the broad, duplicated object type the guide warns against.
C=Remove Customer: destroys the entity model and every other use of customers.
D=Stop filtering: the filter is a legitimate business need; the Ontology should support it rather than remove it.
T: Denormalize only the attributes applications filter on, computed in the pipeline and documented as derived.
V: Ontology Manager, Pipeline Builder

@ PLTR-DE D7 T7.4 applied use-case
S: A team must add a new required property to a live object type whose backing dataset currently lacks the column. Applications display the object type today. What sequence avoids breaking them?
A: Add the property as required in the Ontology first, then update the pipeline afterwards, accepting a short period in which objects fail validation
B: On a branch, produce the column with values for all rows, add the property to the object type, validate the applications, then merge together
C: Add the property directly in production as optional for now and tell application teams to expect blank values until the pipeline catches up
D: Create a brand-new object type that includes the property and ask all application teams to switch their modules over to it
K: B
G: ## Coordinated schema evolution
The exam guide names Global Branching for evolving live Ontology resources and asks for coordination of data and Ontology changes.
## Sequence
- Branch: pipeline produces the column with a value for every row (backfill or default).
- Branch: object type gains the property; applications tested against branch data.
- Merge together; objects never exist without the required value.
Example: `priority` is backfilled from a rule for historical orders, and the property goes live with no nulls.
W: Pipeline and Ontology change developed and merged together on a branch: no window of invalid objects and no broken applications.
X: A=Ontology first: objects without the required value break validation and applications.
C=Blank values in production: a required property with blanks contradicts itself.
D=New object type: a duplicate entity and a migration for every application, all to add one property to an existing type.
T: Evolve object types together with their backing data on a branch and merge as one change.
V: Global Branching, Ontology Manager

@ PLTR-DE D7 T7.1 applied use-case
S: A field "status" exists on five object types with slightly different allowed values and spellings in each. Applications want a consistent status filter. What should the data engineer propose?
A: Leave each object type's status values as they are and let every application map the different spellings to a common set itself
B: Define a shared property with a controlled status vocabulary, map each type's values to it in the pipelines, expose it on all five
C: Merge the five object types into a single generic object type so that the status property is automatically shared among them
D: Store the status as free text on every type and ask users to search carefully with wildcards when they filter by status
K: B
G: ## Shared vocabulary across types
The exam guide lists shared properties and value types. Consistency across object types comes from a shared definition and pipeline mapping, not from each application reconciling spellings.
## Proposal
- Value type `WorkStatus`: open, in_progress, blocked, done.
- Shared property applied to the five types.
- Pipelines map source values to the vocabulary; an expectation enforces it.
Example: a cross-type "blocked" filter returns tickets, tasks and orders consistently.
W: Shared property with a controlled vocabulary and pipeline mapping: one filter works across all five types.
X: A=Applications map: five mappings maintained in every application.
C=Merge types: the entities are different; merging them for one field is wrong.
D=Free text: every spelling variant remains, so a status filter returns different results depending on which type and source wrote it.
T: Standardize cross-type attributes with shared properties and value types mapped in the pipeline.
V: Ontology Manager

@ PLTR-DE D7 T7.2 applied comparison
S: A data engineer is configuring the link between Invoice and Customer object types. Each Invoice belongs to exactly one Customer, and a Customer may have many Invoices. Which link cardinality is correct?
A: One-to-one from Invoice to Customer, since each invoice has exactly one customer and that is what one-to-one expresses
B: Many-to-one from Invoice to Customer, equivalently one-to-many from Customer to Invoice, backed by the customer id on the invoice
C: Many-to-many between Invoice and Customer backed by a join dataset, since a customer has many invoices and that implies many-to-many
D: No link at all; a customer name property on each Invoice is enough for applications to show who the invoice belongs to
K: B
G: ## Reading cardinality
The exam guide asks for correct link cardinality. "Each invoice has one customer; a customer has many invoices" is many invoices to one customer.
- Backing: `customer_id` on the invoice row.
- Traversal: Customer → invoices; Invoice → customer.
Example: customer C-1 has 230 invoices; invoice I-5 belongs to C-1.
W: Many-to-one from Invoice to Customer: many invoices point to one customer through the foreign key, which is exactly the relationship described and supports traversal both ways.
X: A=One-to-one: it constrains each customer to a single invoice, so the second invoice for a customer could not be linked.
C=Many-to-many: would allow an invoice to have several customers.
D=Name property: a copied name is not a link; traversal to the Customer object is impossible and the name duplicates and drifts.
T: "Many of these belong to one of those" is a many-to-one link via a foreign key.
V: Ontology Manager

@ PLTR-DE D7 T7.5 applied tradeoff
S: An application needs "days until contract expiry" for every contract in a list. The value changes daily. Where should it come from?
A: A property materialized nightly in the pipeline regardless of how it is used, which will be at most a day stale for every consumer
B: A nightly materialized property if filtering is needed and a day's staleness is fine, or a value computed at display time if exactness matters
C: A manual update of the value by the contract team each morning before the application's users start their day
D: A value typed in by application users whenever they open a contract and notice that the number is out of date
K: B
G: ## Choosing by use
The exam guide asks you to decide north or south by use: filtering and consistency favour south; simple derived display values can be computed north.
## Reasoning
- If lists must filter or sort by it: materialize south (nightly is usually fine).
- If only displayed and must be exact: a derived property or function computed from `expiry_date` at read time.
- Both can coexist: materialized for filtering, derived for exact display.
Example: a "expiring within 30 days" filter uses the nightly property; the card shows the exact day count computed live.
W: The decision depends on filtering and freshness needs; both placements are legitimate for different uses.
X: A=Nightly only: right when the value drives filters, but if it is only displayed and must be exact, a live computation from the expiry date is better; the use decides.
C=Manual: a trivially computable value should never be typed daily.
D=User input: asking users to maintain a value derivable from a date is pointless and produces stale, inconsistent numbers.
T: Place computed values by how they are used: materialize for filtering, compute north for exact display.
V: Ontology, AIP Logic

@ PLTR-DE D7 T7.4 advanced troubleshooting
S: After a backing dataset was rebuilt with a different sort order and a subtle change in how a key column was trimmed, 2% of objects lost their user edits. What happened and what should be done?
A: The Ontology randomly discards a small share of user edits during any large rebuild, and nothing in the pipeline can prevent that
B: The trimming change altered those rows' keys, re-identifying the objects and detaching edits; map old to new keys, re-attach, add tests
C: The new sort order changed the keys of the affected rows, so sorting the dataset the old way in the transform will restore the edits
D: The lost edits were not important since only 2% of objects were affected, and users can re-enter them if they notice
K: B
G: ## Key stability is a contract
The exam guide asks for stable primary keys and warns that identity changes detach edits and links. Any transformation of the key column (trimming, casing) is part of identity and must not change silently.
## Response
- Diagnose: compare old and new keys for the affected rows; the trimming change is the cause.
- Repair: map old → new keys; re-attach edits and links through a migration.
- Prevent: unit tests on the key derivation; an expectation comparing the key set with the previous build (no unexpected churn).
Example: keys with trailing spaces were previously kept; the new trim removed them; the mapping restores 2% of edits.
W: Key churn from a transformation change, repaired by mapping and prevented by tests and churn expectations: the correct diagnosis and the systemic fix.
X: A=Random discard: edits detach only when identity changes; this was caused, not random.
C=Sort order: ordering does not affect key values; the trim did.
D=Only 2%: user edits are business data; losing any is a defect.
T: Treat key derivation as part of the identity contract; test it and monitor key churn between builds.
V: Ontology Manager, expectations
