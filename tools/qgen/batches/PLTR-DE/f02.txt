# Restricted views provide row-level policies and do not support column-level policies (object-edits/materializations,
# platform-security-management/manage-restricted-views). Column- and cell-level control on objects comes from property

@ PLTR-DE D6 T6.3 applied troubleshooting
S: An application user can open a dataset-backed object type and see objects, but a particular property is always empty for them while colleagues see values. The pipeline and dataset are healthy. What should the data engineer check?
A: Whether a property security policy (or a separately permissioned datasource backing that property) hides it for this user
B: Whether the user's browser is caching an older version of the application module, since empty properties are usually a display problem on the client side
C: Whether the pipeline dropped the column for some rows, since a healthy build can still produce nulls for some users
D: Whether the object type needs to be re-indexed, since indexing lag shows up as missing property values for individual users
K: A
G: ## Property-level visibility
Foundry documentation describes **property security policies**: when a property is covered by one, a user must pass both the object security policy and the property security policy to see its value, which gives column- and cell-level control. Restricted views, by contrast, filter **rows** and do not support column-level policies; column-level separation with them is done by backing the sensitive properties with a separate, more restricted datasource (a multi-datasource object type).
## Where to look
- Property security policies on the object type.
- A separate datasource backing that property and the user's access to it.
- Check Access for the user on the relevant resources.
Example: `salary` is covered by a property security policy limited to HR; the user is not in HR, so the property shows empty while the rest of the object is visible.
W: A property-level control for that user: the symptom is user-specific and limited to one property while the data is fine, which is what a property security policy or separately permissioned datasource produces.
X: B=Browser cache: a cache would not selectively blank one property for one user while colleagues see it.
C=Pipeline nulls: colleagues see values for the same rows, so the column is populated.
D=Indexing lag: lag affects all users equally; it does not vary by who is looking.
T: A property empty for one user but visible to others points to property-level security, not to the pipeline.
V: object security policies, Check Access

@ PLTR-DE D6 T6.1 applied use-case
S: A dataset must be readable by the whole company except for a single highly sensitive column that only the legal team may see. Which design achieves this cleanly?
A: Applying a legal marking to the entire dataset so that only the legal team can open it, and asking everyone else to request the data from legal
B: A curated dataset without the column for the company, plus a separate keyed dataset holding the column under a legal marking
C: Leaving the dataset unmarked and relying on a Workshop module to hide the sensitive column from non-legal users
D: Encrypting the sensitive column's values with a personal key that only a few legal staff know, inside the same dataset
K: B
G: ## Column-level separation
The exam guide asks for least privilege per consumer and for markings on sensitive data. Markings apply to a whole resource and restricted views filter rows, not columns, so one sensitive column is handled by separating it into its own resource.
## Design
- Company dataset: all columns except the sensitive one; broad read.
- Legal dataset: primary key plus the sensitive column; legal marking.
- For the Ontology, the sensitive property can be backed by the legal dataset or protected with a property security policy.
Example: analysts query 20 columns freely; legal joins the 21st by key from their own dataset.
W: Split by sensitivity with the sensitive column in its own marked resource: broad access to the public columns and strict control of the one that matters.
X: A=Mark everything: the whole company loses access to 20 public columns.
C=Workshop hiding: not access control; the column is readable through every other tool.
D=Personal key in place: ad hoc keys held by individuals are unmanageable and the column still travels everywhere; governed obfuscation is a different, platform-managed approach.
T: Separate a sensitive column into its own protected resource rather than locking the whole dataset.
V: markings, object security policies

@ PLTR-DE D1 T1.3 applied troubleshooting
S: An object type is backed by a virtual table over an external warehouse. Users see fewer objects than the warehouse table contains, and the difference depends on the user. The warehouse connection uses one service credential and nothing changed in the warehouse. What should be investigated first?
A: Whether the warehouse is applying each Foundry user's own warehouse permissions, since virtual tables pass every user's identity to the source
B: Foundry-side controls on the object type (object security policies) for those users, using Check Access, since the source sees one credential
C: Whether those users' browsers are caching an older copy of the objects from before the latest sync of the table
D: Whether the virtual table should be replaced with a full copy so that every user sees the same row count
K: B
G: ## Where user-specific filtering can come from
The connection to the warehouse uses one configured credential, so the warehouse cannot distinguish Foundry users. A difference that depends on the user must come from controls applied on the Foundry side, such as object security policies on the object type.
## Investigation
- Object security policies on the object type and the attributes they compare.
- Recent changes to user attributes or groups.
- Check Access for an affected user.
Example: a new regional object security policy limits each user to their region's rows, as intended.
W: Foundry-side object security policies: the only layer consistent with user-specific results when the source sees a single credential and did not change.
X: A=Per-user warehouse permissions: the connection uses one service credential, so the warehouse cannot apply different permissions per Foundry user.
C=Browser cache: object data is served by the platform per request; caching does not produce user-specific row counts.
D=Full copy: copies the data without explaining or respecting the policy that is causing the difference.
T: When virtual-table-backed objects differ by user, look at Foundry-side policies, since the source sees one credential.
V: virtual tables, object security policies
