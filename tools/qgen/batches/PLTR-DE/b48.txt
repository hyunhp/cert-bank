# PLTR-DE batch 48: Domain 7 round 6 (Ontology Data Modeling), 8 questions

@ PLTR-DE D7 T7.1 applied use-case
S: A hospital system models Patients, Doctors and Appointments. An appointment involves one patient and one doctor at a specific time, and applications must list a doctor's appointments and a patient's history. Which model is correct?
A: A many-to-many link between Patient and Doctor with no properties, with appointment times stored as a list on the Patient object
B: An Appointment object type with time and status, linked many-to-one to Patient and to Doctor
C: Appointment times stored as a list property on each Doctor object, with patient names in a parallel list in the same order
D: A single Patient object per appointment, so that each visit creates a new patient record holding the doctor and time
K: B
G: ## Events as object types
The exam guide asks for entities, links and properties modelled with normalization. An appointment is an entity with its own attributes and two relationships.
## Model
- Appointment: key, time, status, type.
- Links: Appointment → Patient (many-to-one), Appointment → Doctor (many-to-one).
- Queries: a doctor's schedule, a patient's history, both through links.
Example: Dr. Kim's Tuesday shows eight Appointment objects; patient P-12's history shows 14 across three doctors.
W: An Appointment object with links to both participants: each visit has a home for its attributes and both application views traverse links naturally.
X: A=Bare many-to-many with a time list: the times cannot be tied to the right doctor and the list is unqueryable.
C=Parallel lists on Doctor: fragile ordering, no link to Patient objects, and no place for status or type.
D=Patient per appointment: duplicates the patient's identity for every visit and breaks history.
T: Model events that relate several entities as their own object type linked to each participant.
V: Ontology Manager

@ PLTR-DE D7 T7.2 applied troubleshooting
S: An object type uses an email address as its primary key. Customers sometimes change their email, and when they do, their history disappears from the application. What is the cause and the fix?
A: The application caches old objects; clearing the cache will restore each customer's history after an email change
B: Email is mutable, so a change re-keys the object and detaches history and edits; switch to a stable id and migrate
C: The pipeline is dropping rows with new emails; adding a filter on email format will prevent the loss
D: Customers should be told never to change their email address in the source system
K: B
G: ## Mutable keys break identity
The exam guide asks for stable primary keys. An attribute that can change is a property, not an identifier.
## Fix
- New key: the customer id from the system of record.
- Migration: map old email-keyed objects to the new keys; carry edits and links.
- Email becomes an ordinary property; uniqueness expectation on the new key.
Example: a customer updates their email; the object keeps its key C-4471 and its history.
W: A stable identifier as the key with the email demoted to a property: identity survives attribute changes and history stays attached.
X: A=Cache: the object really was re-keyed; nothing cached is hiding the history.
C=Email format filter: the rows are present; their key changed, which a format filter cannot fix.
D=Forbid email changes: the business cannot freeze a customer attribute to work around a modelling error.
T: Never key objects on attributes that can change; use the system of record's stable identifier.
V: Ontology Manager, expectations

@ PLTR-DE D7 T7.3 applied use-case
S: Analysts want a "Top 10 products this week" list in a dashboard. A colleague proposes a TopProduct object type rebuilt weekly with ranks 1–10. What is the better modeling approach?
A: Create the TopProduct object type as proposed, since it is the fastest way to make the dashboard work for analysts this week
B: Keep Product as the entity with a weekly sales metric (or a ProductWeek type) and rank in the dashboard
C: Store the top-10 list as a text property on a single global object that the dashboard reads and parses
D: Create ten separate object types, one for each rank position, each holding one product reference
K: B
G: ## Avoid dashboard-shaped object types
The exam guide warns against object types shaped by one view. A top-10 list is a query over products, not an entity.
## Approach
- Product holds weekly sales (or a ProductWeek aggregate keyed by product and week).
- Dashboard sorts and takes the top ten.
- Other views reuse the same metric for other questions.
Example: the dashboard shows the top ten; another app shows the bottom ten from the same property.
W: Model the entity and its metric and rank at query time: the dashboard works and the Ontology stays reusable for other questions.
X: A=TopProduct type: a view-shaped object type that duplicates products and must be rebuilt for every new list variant.
C=Text on a global object: unlinked, unqueryable and parsed by the dashboard.
D=Ten object types: an absurd structure that encodes ranking as schema.
T: Model entities and metrics; compute rankings and lists at query time rather than as object types.
V: Ontology Manager

@ PLTR-DE D7 T7.4 applied use-case
S: A team needs to split an existing object type "Asset" into two types, "Vehicle" and "Building", because their properties diverge. Applications and edits exist on Asset. How should the change be made?
A: Delete the Asset type and create the two new types from scratch, accepting the loss of user edits and links
B: On a branch, create both types, migrate edits and links, update the applications, then merge together
C: Keep a single Asset type and add every property of both, leaving most of them empty on each object
D: Create the new types in production immediately and tell application owners to switch whenever they can
K: B
G: ## Splitting a live object type
The exam guide asks for safe evolution of live Ontology resources with Global Branching and consumer coordination.
## Approach
- Branch: new types and backing datasets; key mapping from Asset.
- Migrate user edits and links to the new types.
- Update applications on the branch; validate.
- Merge together; deprecate Asset after confirmation.
Example: 4,000 assets become 3,100 vehicles and 900 buildings with every edit and link preserved.
W: Branch-based split with migration of edits and links and coordinated application updates: the model improves without breaking consumers or losing data.
X: A=Delete and recreate: destroys user edits and links that the business depends on.
C=One wide type: the divergence remains as a mass of empty properties.
D=Production first: applications break or diverge during an uncontrolled transition.
T: Split live object types on a branch with edit and link migration, then merge with application updates.
V: Global Branching, Ontology Manager

@ PLTR-DE D7 T7.1 applied comparison
S: Which property design is most appropriate for a "status" field that applications filter on and that must take one of five values?
A: A free-text string property where each pipeline writes whatever wording its source system uses for the status
B: A string property constrained to an enumerated set (or a value type), validated by an expectation in the pipeline
C: A numeric property where each status is encoded as an arbitrary number known only to the engineers
D: Five separate boolean properties, one per status, with applications checking which one is true
K: B
G: ## Controlled vocabularies
The exam guide lists value types and properties designed for consistent use. A small fixed set of statuses is an enumeration.
## Design
- Allowed values: open, in_progress, blocked, done, cancelled.
- Expectation: values must be in the set.
- Applications filter on consistent values.
Example: a new source writing "In Progress" is mapped to `in_progress` in the pipeline; an unmapped value fails the build.
W: An enumerated, validated property: consistent filtering for applications and immediate detection of unexpected values.
X: A=Free text: inconsistent spellings across sources break filters.
C=Opaque numbers: unreadable for users and error-prone for applications.
D=Five booleans: allows contradictory states and complicates every filter.
T: Model fixed-choice attributes as enumerated, validated properties.
V: Ontology Manager, expectations

@ PLTR-DE D7 T7.5 applied tradeoff
S: An application shows each customer's lifetime revenue. Recomputing it from all orders on every page view is slow. The value only needs to be current to the previous day. Where should it be computed?
A: North of the Ontology in a function on every page view, accepting the slowness so the value is always perfectly current
B: South, as a property materialized by the daily pipeline from the orders data, so pages read a stored value
C: In the browser by downloading all of the customer's orders and summing them on the user's device
D: By the customer service team, who update the value manually when a customer asks about it
K: B
G: ## Materialize what is read often and changes slowly
The exam guide's placement criteria: consistency, reuse and freshness. Daily freshness and heavy read traffic point south.
## Design
- Pipeline: lifetime revenue per customer, daily.
- Property on Customer; documented as "as of previous day".
- Same value reused in lists, filters and other apps.
Example: the page loads in 200 ms instead of 6 seconds, and the list view can sort customers by revenue.
W: A daily materialized property: fast reads, consistent values everywhere, and freshness that matches the requirement.
X: A=Function per view: slow for a freshness the requirement does not need, and unusable for sorting lists.
C=Browser summing: downloads entire order histories to every device, slow and wasteful.
D=Manual updates: the value is stale until someone asks, inconsistent between customers, and costs staff time for something a pipeline computes.
T: Materialize slowly changing, frequently read values in the pipeline.
V: Pipeline Builder, Ontology

@ PLTR-DE D7 T7.2 applied use-case
S: Two source systems describe the same physical Warehouse with different ids. Applications need one Warehouse object. How should the backing data be modeled?
A: Create two Warehouse objects, one per source, and let users figure out which one to use in each case
B: Map each source id to one canonical id through a crosswalk, key the object on it, keep source ids as properties
C: Concatenate both source ids into one string key so that both are represented in the single object
D: Use the warehouse name as the key, since both systems spell the names similarly most of the time
K: B
G: ## Entity resolution across sources
The exam guide asks for stable keys and one object per real-world entity. A crosswalk maps source ids to a canonical identity.
## Design
- Crosswalk dataset: (source, source_id) → canonical_id, maintained and validated.
- Object keyed by canonical_id; source ids stored as properties.
- Expectation: every source id maps to exactly one canonical id.
Example: ERP W-17 and WMS 5502 both map to WH-0042, the single Warehouse object.
W: A canonical id via a maintained crosswalk: one object per warehouse, with traceability back to each source.
X: A=Two objects: duplicates the entity and confuses every consumer.
C=Concatenated key: changes whenever either source changes and still does not express that they are the same entity.
D=Name as key: the two systems spell names differently and different warehouses can share a name, so identity would merge or split wrongly.
T: Resolve entities across sources with a crosswalk to a canonical key.
V: Ontology Manager, Pipeline Builder

@ PLTR-DE D7 T7.4 advanced troubleshooting
S: After a backing dataset was rebuilt with a corrected join, the number of objects of a type dropped by 5%, and some users report missing objects they had edited. What should the engineer do?
A: Accept the change, since the corrected join is more accurate and the missing objects were probably wrong
B: Diff the key sets, classify removed keys, restore legitimate objects and their edits, and add a key-churn check
C: Restore the old, incorrect join permanently so that no objects ever disappear again
D: Ask users to recreate the missing objects and their edits by hand
K: B
G: ## Key churn after logic changes
The exam guide asks for stable identities and preserved edits. A logic change that removes keys must be examined, not assumed correct.
## Investigation
- Diff key sets between versions.
- Classify removed keys: genuinely invalid versus wrongly excluded (for example, an inner join dropping valid rows).
- Restore legitimate objects; re-attach edits.
- Expectation or health check on key churn between builds.
Example: 3% were true duplicates; 2% were valid assets lost to an inner join; switching to a left join restores them and their edits.
W: Key-set diff, classification and restoration with a churn check: legitimate objects and their edits come back, and future rebuilds are guarded.
X: A=Accept: some removed objects were valid and carried user edits.
C=Restore the wrong join: reintroduces the duplicates and inaccuracies the correction was made to remove.
D=Users recreate: the original edit history and links are lost, and users waste time redoing work the system should preserve.
T: After logic changes, diff key sets, restore wrongly removed objects and monitor key churn.
V: Ontology Manager, expectations
