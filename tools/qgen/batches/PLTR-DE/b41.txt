# PLTR-DE batch 41: Domain 8 round 5 (AI-Assisted Data Engineering), 8 questions

@ PLTR-DE D8 T8.1 applied comparison
S: A data engineer wants to quickly understand an unfamiliar pipeline with forty transforms before modifying it. Which AI capability helps most, and how should its output be treated?
A: An LLM transform run over the repository's source files, producing a dataset of explanations that is then trusted as the pipeline's documentation
B: A code assistant that summarizes the transforms, their inputs, outputs and likely intent, verified against lineage and the code before changes
C: AIP Assist, which will automatically refactor the forty transforms into a cleaner structure that is easier to understand before the change
D: An embedding transform over the code files so that transforms similar to the one being modified can be found by semantic search
K: B
G: ## Assistants for comprehension
The exam guide places understanding and authoring with code assistants and asks for review of their output. A summary of unfamiliar code accelerates orientation but is not ground truth.
## Use
- Ask the assistant for a map: transforms, dependencies, what each seems to do.
- Verify against lineage (actual dependencies) and the code itself.
- Note discrepancies; the assistant can be wrong about intent.
Example: the assistant's map says transform 12 deduplicates orders; lineage and code show it also filters cancelled ones, which matters for the planned change.
W: A code assistant's summary verified against lineage and code: faster orientation without trusting a guess.
X: A=LLM transform over files: a batch step producing text to be trusted as documentation; the wrong tool and the wrong trust level.
C=AIP Assist refactoring: the platform helper does not refactor pipelines autonomously.
D=Embedding transforms: similarity search over code does not explain what the pipeline does.
T: Use code assistants to orient in unfamiliar pipelines, then verify with lineage and the code.
V: Continue, Data Lineage

@ PLTR-DE D8 T8.2 applied use-case
S: An LLM transform must produce a numeric "urgency" from 1 to 5 for support tickets, and downstream logic sorts by it. The model sometimes returns 0, 6 or "high". What configuration prevents bad values from reaching the sort?
A: Casting whatever the model returns to an integer in the transform and defaulting any cast failure to a middle value of 3
B: A range-constrained integer in the schema, validation rejecting values outside 1 to 5, a status column for rejects, and a range expectation
C: Asking the model politely in the prompt to stay between 1 and 5 and to never answer with words, which it usually respects
D: Sorting the tickets by the raw text of the model's answer so that unusual values such as "high" simply sort to the end of the list
K: B
G: ## Constrained numeric outputs
The exam guide pairs structured outputs with deterministic post-processing and quality checks. A bounded integer is a constraint to enforce in schema and code.
## Configuration
- Schema: integer 1 to 5 (enumeration of allowed values).
- Validation: reject anything else; status `invalid`; raw response kept.
- Expectation: published `urgency` within range; invalid rows excluded or reviewed.
Example: 0.4% of rows are rejected and reviewed; the sort never sees a 6 or a word.
W: Schema constraint, code validation, status and a range expectation: bad values are impossible in the published column.
X: A=Cast and default: a 6 becomes 6; "high" becomes 3 silently; wrong urgencies drive the sort.
C=Polite request: the model usually complies, but "usually" is not a guarantee, and nothing catches the times it does not.
D=Sort raw text: text sorting of numbers is wrong ("10" before "2") and words are meaningless.
T: Constrain AI numeric outputs in the schema and validate in code; never default invalid values silently.
V: Pipeline Builder, expectations

@ PLTR-DE D8 T8.3 applied tradeoff
S: A company wants customer-facing chat to answer questions about order status using an LLM. The data engineering team is asked what they own in this design. Which answer reflects the role boundary?
A: Everything in the design, including the chat agent's prompts, tools and conversation behaviour, since the data engineering team knows the data best
B: The curated, timely order data in the Ontology (object types, links, freshness, quality) and pipeline-layer AI enrichment; not the agent
C: Nothing at all, since AI projects are outside data engineering and the AI team can read whatever data it needs directly
D: Only the raw ingestion of order data from the source systems; everything after that, including the Ontology model, belongs to the AI team
K: B
G: ## The data engineer's AI boundary
The exam guide's role boundary places pipelines, curated data, Ontology data modeling and pipeline-layer AI with the data engineer, and agents, prompts and interactive AI with the AI engineer.
## Ownership
- Data engineer: Order object type and links, freshness and quality, any batch enrichment (for example, delivery-status normalization).
- AI engineer: agent instructions, tools, retrieval configuration, evaluation of conversations.
- Shared contract: what properties the agent may rely on.
Example: the data engineer guarantees `order.status` is current within 10 minutes; the AI engineer builds the agent that reads it.
W: Curated Ontology data and pipeline-layer AI for the data engineer; agent design for the AI engineer: the guide's boundary.
X: A=Everything: prompts, tools and conversation design are the AI engineer's role; the data engineer owns what the agent reads, not how it talks.
C=Nothing: the agent is only as good as the data; that is the data engineer's job.
D=Raw ingestion only: the Ontology model and quality controls are also theirs.
T: Data engineers own the curated data and pipeline-layer AI that agents depend on; agents themselves belong to AI engineering.
V: Ontology, Pipeline Builder

@ PLTR-DE D8 T8.4 applied troubleshooting
S: A code assistant generated a transform whose unit tests all pass, but the branch build shows the output has 12% fewer rows than the production version. What should the engineer conclude?
A: The passing tests prove the generated code is correct, so the production version must have been wrong all along and can be replaced
B: The tests cover only the cases the assistant imagined; the branch comparison reveals a real difference to investigate before merge
C: A 12% difference in row count is within the normal variation that any transform shows from build to build and needs no investigation
D: The branch build must be broken in some way and should be ignored, since the unit tests are the authoritative check for correctness
K: B
G: ## Tests and real data
The exam guide asks for both unit tests and branch validation on real inputs, and for review of AI-generated assumptions. Passing tests say nothing about rows the tests never considered.
## Investigation
- Diff the outputs by key: which rows are missing?
- Trace to the logic: a stricter filter, an inner join, a null-handling assumption.
- Decide: a bug (fix) or a correction of a known production defect (justify, document, communicate).
Example: the assistant's join dropped orders whose customer id was null; production kept them; the business wants them kept.
W: Investigate the real-data difference before merging: tests are necessary but the branch comparison is the evidence that matters.
X: A=Tests prove correctness: they prove the tested cases; the missing 12% were not tested.
C=Normal variation: a deterministic transform on the same input should match exactly.
D=Ignore the branch: the branch build is the real-data check; ignoring it defeats validation.
T: Passing unit tests do not replace branch comparison on real data; investigate any difference before merging generated code.
V: Code Repositories, branches

@ PLTR-DE D8 T8.2 applied use-case
S: An LLM transform is used to extract a product category from descriptions, and the category feeds a restricted view policy (some categories are confidential). What additional care applies?
A: None; the category is just another column in the dataset and the restricted view treats it like any other value
B: Stricter validation (enumeration, confidence thresholds, review of uncertain rows), monitoring, and a documented decision with a safe default
C: Lowering the confidence threshold so that more rows receive a category and fewer end up unclassified in the view's policy
D: Using the model's output directly in the restricted view policy without any validation, since validation would slow the pipeline
K: B
G: ## AI outputs that feed security decisions
The exam guide asks for quality checks proportional to consequence. A category used in an access policy is a security-relevant value; a misclassification can expose or hide rows.
## Care
- Validation: enumeration; confidence threshold; low-confidence rows to review before they drive policy.
- Monitoring: rates of movement into and out of confidential categories.
- Governance: an explicit, documented decision by the data owner that an AI-derived field may drive access, with a fallback (default to confidential when unsure).
Example: an ambiguous description defaults to the confidential category until reviewed; nothing leaks by misclassification.
W: Stricter validation, review for uncertainty, monitoring and a documented governance decision with a safe default: proportionate to a security-affecting output.
X: A=Just a column: this column decides which rows each user can see; a wrong value is an access-control failure, not a data blemish.
C=Lower threshold: more low-confidence classifications drive the policy, so more rows are exposed or hidden on a guess.
D=No validation: an unverified model output as an access control.
T: When AI-derived values drive access control, validate strictly, default to the safe side and document the decision.
V: restricted views, Pipeline Builder

@ PLTR-DE D8 T8.3 applied use-case
S: A data engineering team is listing which AI-related work items in a new programme fall within their role. Which is the best example of pipeline-layer AI that a data engineer would own?
A: An agent in Agent Studio that answers analysts' ad hoc questions about the sales data in natural language with retrieval and tools
B: A nightly LLM transform normalizing free-text supplier names into canonical identifiers, validated against the reference, feeding Supplier
C: A chat interface embedded in the executive dashboards that lets executives explore the figures conversationally
D: The model-selection decision for a customer-facing assistant, weighing capability, latency and cost across the catalog
K: B
G: ## Pipeline-layer AI
The exam guide places batch, reusable enrichment in the pipeline layer under the data engineer, and interactive agents under AI engineering.
- Supplier-name normalization nightly, validated, feeding an object type: data engineering.
- Agents, chat interfaces, assistant model choices: AI engineering.
Example: 50,000 supplier mentions map to 3,200 canonical suppliers each night; unmatched ones are flagged.
W: A scheduled, validated batch enrichment that feeds the Supplier object type: reusable, governed, pipeline-layer AI that sits squarely in the data engineer's role.
X: A=Ad hoc agent: an interactive agent with retrieval and tools is Ontology-layer AI owned by AI engineering.
C=Chat for executives: a conversational interface is interactive AI, designed and evaluated by AI engineering.
D=Assistant model selection: choosing models for an assistant is the AI engineer's selection and observability domain.
T: Pipeline-layer AI means scheduled, validated enrichment feeding curated data and the Ontology.
V: Pipeline Builder, Ontology

@ PLTR-DE D8 T8.4 applied tradeoff
S: An assistant offers to generate the entire data model (object types, links, keys) for a new domain from a description. How should the data engineer use this?
A: Accept the generated model as it is and publish the object types immediately, since it was produced quickly and looks reasonable
B: Treat it as a draft: verify keys and cardinalities against the real data and business needs, correct the assumptions, validate on a branch first
C: Reject the generated model entirely and start from a blank page, since AI assistants cannot contribute anything useful to data modeling
D: Publish the generated model and fix any modeling problems later as application users report them in production
K: B
G: ## Generated models need the same scrutiny
The exam guide asks for stable keys, correct cardinality and normalization, and for review of AI-generated outputs. A generated model encodes guesses about the data.
## Review
- Keys: verify uniqueness and stability in the actual data.
- Cardinality: check with counts (one-to-many versus many-to-many).
- Normalization: dashboard-shaped or duplicated types removed.
- Branch validation with real data before publishing.
Example: the draft proposed email as the Customer key; the uniqueness check finds shared emails and the key is changed before anything is live.
W: Draft reviewed against real data and business needs, validated on a branch: speed from the assistant, correctness from the engineer.
X: A=Accept as is: wrong keys and cardinalities become live defects.
C=Reject entirely: a draft that already lists entities and relationships is a useful head start; discarding it wastes real work.
D=Fix later: users suffer modeling errors that are expensive to migrate once edits exist.
T: Use AI-generated data models as drafts verified against real data before anything goes live.
V: Ontology Manager, Continue

@ PLTR-DE D8 T8.1 advanced tradeoff
S: A team wants to measure whether their use of AI assistants for pipeline development is actually improving outcomes. What should they track?
A: The number of prompts each engineer sends to the assistant per week, as a measure of how much the team has adopted the tool
B: Delivery and quality outcomes: lead time, defects caught in validation and production, review findings, incidents, before and after
C: How much the engineers say they like working with the assistant in a monthly satisfaction survey run by the team lead
D: Nothing, since AI assistants are obviously beneficial for development work and measuring it would waste the time it saves
K: B
G: ## Measuring assistant impact
The exam guide expects engineering judgement about AI tools, including their value. Usage is not value; outcomes are.
## Track
- Speed: lead time from change request to release.
- Quality: defects caught in validation, defects reaching production, incidents.
- Review signal: how often generated code needed correction and why.
- Qualitative: engineer feedback on where it helps and where it misleads.
Example: lead time falls 30%; defects caught in branch validation rise (more caught early); production incidents unchanged: a clear net benefit with a note on review discipline.
W: Outcome metrics before and after, plus review findings and feedback: a real measure of value rather than activity.
X: A=Prompt counts: heavy usage can coexist with worse code; activity measures adoption, not whether outcomes improved.
C=Liking it: engineers may enjoy a tool that introduces subtle defects; sentiment is not a quality or delivery result.
D=Obviously beneficial: an assumption to test, not a conclusion.
T: Evaluate AI assistants by delivery and quality outcomes, not by usage or sentiment.
V: Code Repositories, branches
