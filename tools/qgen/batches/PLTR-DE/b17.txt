# PLTR-DE batch 17: Domain 8 round 2 (AI-Assisted Data Engineering), 8 questions

@ PLTR-DE D8 T8.1 applied use-case
S: A data engineer wants help designing a pipeline's structure and generating boilerplate transforms from a description of the sources and targets. Which AI capability is intended for this?
A: An LLM transform, which produces data columns from a prompt
B: AI FDE or a code assistant such as Continue, which help engineers author pipelines interactively
C: AIP Assist, the platform-wide helper, which can generate a complete pipeline from a description if asked in the right way
D: An embedding transform, which converts descriptions into vectors
K: B
G: ## Engineering assistants versus data transforms
The exam guide asks you to distinguish AI FDE, AIP Assist, Continue and data-producing transforms. Helping an engineer build is an assistant's job; producing columns is a transform's job.
## Fit
- AI FDE / Continue: understand the engineer's intent, propose pipeline structure, generate transform code, explain errors; the engineer reviews and commits.
- The output is code and configuration in a repository or Pipeline Builder, subject to normal review and tests.
Example: from "join orders to customers, filter cancelled, aggregate monthly", the assistant drafts three transforms the engineer then reviews.
W: AI FDE or a code assistant: they assist authoring, which is exactly what designing structure and generating boilerplate is.
X: A=LLM transform: it runs over dataset rows at build time; it does not write pipelines.
C=AIP Assist: it answers platform questions and is not the pipeline-authoring assistant.
D=Embedding transform: it produces vectors from text, unrelated to authoring.
T: Use engineering assistants to author pipelines; use transforms to process data.
V: Continue, AIP Assist

@ PLTR-DE D8 T8.2 applied use-case
S: An LLM transform extracts a numeric "contract value" from documents. Sometimes the model returns "approximately 1.2M" or "1,200,000 USD". The downstream column is numeric. What should the pipeline do?
A: Write whatever text the model returns into a string column as is, and let each downstream consumer parse the number in the way that suits it
B: Constrain the schema to a number plus a currency field, normalize residual formatting in code, validate ranges, and flag unparseable rows
C: Ask the model to try harder to return a number
D: Convert "approximately" to zero
K: B
G: ## Deterministic post-processing
The exam guide pairs AI processing with structured outputs and deterministic post-processing. A numeric column needs a number, produced by schema and code, not by hoping the model formats consistently.
## Pipeline
- Schema: `{value: number, currency: enum}`.
- Post-processing: strip residual symbols, handle thousands separators, reject "approximately" into a flag.
- Validation: plausible range; null plus a reason when unparseable.
- Keep the raw response for audit.
Example: "1,200,000 USD" → 1200000 / USD; "approximately 1.2M" → parsed 1200000 with `approximate = true` or flagged for review per policy.
W: Typed schema plus deterministic normalization and validation: the column is reliably numeric and the ambiguous cases are explicit.
X: A=String column: every consumer re-implements parsing differently; the "numeric" requirement is unmet.
C=Try harder: an instruction does not guarantee numeric output; code does.
D=Zero: a contract worth roughly 1.2 million recorded as zero is silently wrong data, and it corrupts every total built on the column.
T: Shape AI output with typed schemas and clean it with deterministic code; never push parsing to consumers.
V: Pipeline Builder, Code Repositories

@ PLTR-DE D8 T8.3 applied tradeoff
S: A legal team wants two things: a risk category on every one of 400,000 historical contracts for reporting, and the ability to ask a specific contract "does this clause allow assignment to a subsidiary?" Which layering is correct?
A: Both at the Ontology/application layer, computing the risk category only when a user opens a contract and answering questions in the same function
B: Risk category as a pipeline LLM enrichment stored as a property; the clause question answered interactively at the application layer
C: Both in the pipeline, including pre-answering every possible clause question
D: Neither; legal work cannot use AI
K: B
G: ## Pipeline layer versus Ontology layer
The exam guide asks you to choose pipeline-layer AI for reusable batch enrichment and Ontology-layer AI for interactive, context-dependent reasoning.
- Category for 400,000 contracts, used in reporting: reusable, batch, stored: pipeline.
- A specific question about a specific clause: interactive, context-dependent: Ontology layer, a function or agent over that contract.
The interactive function can use the stored category as context.
Example: reports group contracts by risk category; a lawyer asks the assignment question on contract C-118 and gets an answer citing clause 14.
W: Batch category in the pipeline, interactive question at the application layer: each placed by reuse and interactivity.
X: A=Both on open: categories would be missing for reporting and recomputed per user.
C=Pre-answer every question: questions are unbounded; they cannot be precomputed.
D=No AI: assistive use with review is legitimate; the guide expects engineers to place AI appropriately, not to refuse it.
T: Reusable enrichment in the pipeline; specific questions at the Ontology layer.
V: Pipeline Builder, AIP Logic

@ PLTR-DE D8 T8.4 applied troubleshooting
S: A code assistant generated a transform that works but reads the same large input three times because it recomputes an intermediate result in three places. What should the engineer do?
A: Ship it, since correctness is what matters
B: Review it like any code: compute the intermediate once (or persist it), verify identical output on a branch, and merge
C: Ask the assistant to make the transform faster and merge whatever it returns without reading it, since the assistant understands the code best
D: Add more executors so the triple read is faster
K: B
G: ## Reviewing generated code for inefficiency
The exam guide asks data engineers to review AI-generated code for incorrect assumptions, unsupported patterns and regressions; inefficiency is a pattern to catch. Reading a large input three times multiplies cost and runtime.
## Fix
- Compute the intermediate once; reuse it (or materialize it as its own dataset if it is useful elsewhere).
- Compare output on a branch to confirm the refactor is equivalent.
- Merge; measure the runtime improvement.
Example: runtime falls from 45 minutes to 16 with identical output.
W: Refactor to compute once and verify equivalence: generated code gets the same scrutiny as human code, and the cost is removed.
X: A=Ship as is: it runs three times the necessary cost every day.
C=Blind re-prompting: the assistant's new version is also unreviewed; the engineer stays accountable for what merges.
D=More executors: paying more to do redundant work faster is the wrong fix.
T: Review generated transforms for redundant computation and refactor before merging.
V: Code Repositories, Continue

@ PLTR-DE D8 T8.2 applied use-case
S: A pipeline runs an LLM step over new documents nightly. The team wants to measure its ongoing quality without re-labelling everything. What is a practical quality-check design?
A: Trust the model since it was tested once at launch
B: Validation failure rates, output distribution monitoring, a weekly human-reviewed random sample, and a fixed evaluation set re-run on changes
C: Re-label every document every night
D: Ask the model to rate its own confidence on every document and trust that score as the quality measurement, reviewing nothing else
K: B
G: ## Quality checks for AI steps in production
The exam guide lists quality checks among AI processing controls. Full re-labelling is impossible; layered, cheap signals plus periodic human review give sustainable assurance.
## Design
- Automatic: invalid-output rate, null rate, category distribution drift, with alerts.
- Human: weekly review of a random sample; disagreements become evaluation cases.
- Regression: a fixed labelled set re-run on changes; version recorded on each row.
Example: a drift alert shows "other" rising from 5% to 20%; the sample review confirms a new document template; the prompt is updated.
W: Validation rates, drift monitoring, sampled human review and a regression set: cheap continuous signals plus periodic ground truth.
X: A=Tested once: inputs, models and prompts change; quality drifts unnoticed.
C=Re-label everything: human labelling of every document every night is unaffordable, and sampling plus drift metrics gives the same assurance.
D=Self-rated confidence: useful as one signal for routing, but a model's self-assessment is not a quality measurement.
T: Monitor AI steps with validation and drift metrics, sampled human review and a regression set on changes.
V: Data Health, AIP Evals

@ PLTR-DE D8 T8.3 applied use-case
S: A data engineer is asked to add "semantic search over support tickets" to a Workshop app. Which part of the work belongs to the data engineer's pipeline, and which to the application layer?
A: Everything belongs to the application team; the data engineer only provides the raw dataset
B: The data engineer builds the embedding pipeline and exposes a vector property on Ticket; the application embeds queries and searches it
C: The data engineer should also embed the users' search queries inside the nightly pipeline, since all embedding work is a pipeline concern
D: Semantic search should be done by re-embedding all tickets at query time in the app
K: B
G: ## Division of responsibility
The exam guide places data-producing embedding transforms with the data engineer and interactive search at the Ontology/application layer, and the Data Engineer role boundary excludes specialized retrieval systems' end-user behaviour.
## Split
- Pipeline: text preparation, embedding transform (consistent model), vector property on Ticket, incremental refresh.
- Application: embed the user's query with the same model, run semantic search over the vector property, display results.
Example: nightly embeddings for new tickets; the app's search box returns related tickets by meaning.
W: Index-building in the pipeline, query-time search in the application: each side does what it is responsible for, with the vector property as the contract.
X: A=Raw dataset only: embeddings at scale are pipeline work; the app cannot build the index.
C=Queries in the pipeline: queries arrive at interaction time; they cannot be batch-processed in advance.
D=Re-embed everything per query: hopelessly slow; only the query is embedded at search time.
T: Data engineers build the embedding index in the pipeline; applications embed queries and search it.
V: Pipeline Builder, Ontology vector properties, Workshop

@ PLTR-DE D8 T8.4 applied troubleshooting
S: An AI assistant proposed a transform that fills missing values in a revenue column with the column's mean "to avoid nulls downstream". The engineer notices this. What should happen?
A: Accept the suggestion, since nulls cause problems in downstream aggregations and the mean is a reasonable estimate of the missing revenue
B: Reject it: mean imputation fabricates financial data; preserve and flag the nulls, fix the source, and document the contract
C: Use the median instead of the mean
D: Fill with zero instead
K: B
G: ## Incorrect assumptions in generated code
The exam guide asks data engineers to review AI-generated code for incorrect assumptions and warns against silently coercing data. Mean imputation is a modeling technique for some analyses; in a curated revenue dataset it invents money that was never recorded.
## Correct handling
- Preserve nulls; add an `is_missing` flag or a status column if helpful.
- Investigate why revenue is missing (source gap, timing).
- Document the contract; downstream aggregations decide how to treat nulls explicitly.
Example: 300 orders with missing revenue are flagged; finance excludes them pending correction rather than booking a fabricated average.
W: Reject the imputation and preserve/flag nulls: curated data must not contain invented values, and the contract makes missingness explicit.
X: A=Accept: it corrupts financial data in a way that is invisible to consumers.
C=Median: a different statistic is still a fabricated revenue figure for an order whose revenue was never recorded.
D=Zero: it understates total revenue and is just as fabricated as the mean; a missing value is not the same as no revenue.
T: Never let generated code fill curated business values with statistical guesses; preserve and flag missing data.
V: Code Repositories

@ PLTR-DE D8 T8.1 advanced tradeoff
S: A pipeline team is deciding whether to use an LLM transform or a deterministic rule set to standardize 50,000 address records with varied formats. What is the sound reasoning?
A: Always use the LLM, since it handles variety better than rules
B: Deterministic parsing and reference data as the primary method, with an LLM only for the residual records rules cannot parse, validated and audited
C: Always use rules, since LLMs are never appropriate in pipelines
D: Use the LLM for every record and skip validation against reference data, since occasional address errors are low risk and easy to correct later
K: B
G: ## Deterministic first, AI for the residual
The exam guide's decision area says to use deterministic logic for explicit rules and AI for bounded interpretation, combining them where useful. Address standardization has standards and reference data; most records can be parsed exactly, and exactness matters for delivery.
## Design
- Rules and reference data handle the bulk, deterministically and cheaply.
- Residual unparsable records go to an LLM step with structured output, then validation against reference data; failures go to review.
- Audit: prompt and raw response kept for the LLM-handled subset.
Example: rules standardize 94%; the LLM resolves half of the remaining 6%; the rest are reviewed by hand.
W: Rules as primary with AI for the residual, validated: it is exact where exactness is possible and uses AI where interpretation is needed, under controls.
X: A=Always LLM: more expensive, less exact and harder to audit for a task that mostly has deterministic answers.
C=Never LLM: the residual messy records are precisely where bounded interpretation helps.
D=No validation: address errors cause failed deliveries; validation is essential.
T: Solve structured problems with deterministic logic first; apply AI, validated, to the residual.
V: Pipeline Builder, Code Repositories
