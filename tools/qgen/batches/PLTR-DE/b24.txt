# PLTR-DE batch 24: Domain 7 round 3 (Ontology Data Modeling), 8 questions

@ PLTR-DE D7 T7.1 applied use-case
S: A logistics company needs to model that a Shipment passes through several Hubs in a specific order, with the arrival time at each hub. Which model captures this correctly?
A: A many-to-many link between Shipment and Hub with no properties, since the order can be inferred from the hubs' locations on a map
B: A ShipmentHubVisit object type with sequence number and arrival time, linked to both Shipment and Hub
C: A list property on Shipment containing the hub names in order, with another list property holding the arrival times in the same order
D: A property on Hub recording the most recent shipment that passed through, updated by the pipeline as shipments move
K: B
G: ## Relationships with attributes become object types
The exam guide asks you to model entities, links and properties with normalization principles. A relationship that carries data (sequence, arrival time) is an entity in its own right: the visit.
## Model
- ShipmentHubVisit: key (shipment id, hub id, sequence), properties sequence and arrival time.
- Links: Visit → Shipment (many-to-one), Visit → Hub (many-to-one).
- Queries: a shipment's route in order; a hub's visits over time.
Example: shipment S-9 has visits 1 (Hub A, 08:10), 2 (Hub C, 14:40), 3 (Hub F, 21:05).
W: A visit object type with sequence and time, linked to both: the relationship's attributes have a home and queries work in both directions.
X: A=Plain many-to-many: cannot hold sequence or arrival time; map geometry does not define route order.
C=Parallel lists: unqueryable, fragile (lists can desynchronize) and impossible to link to Hub objects.
D=Latest shipment on Hub: loses all history and all other shipments.
T: Model relationships that carry attributes as their own object type linked to both sides.
V: Ontology Manager

@ PLTR-DE D7 T7.2 applied troubleshooting
S: A Product object type uses the product name as its primary key. Two different products were given the same name by marketing, and now their objects have merged, mixing their orders. What is the lesson and fix?
A: Rename one product so that the names are unique again, which separates the objects without any model change
B: Names are not stable identifiers; migrate the key to the SKU or catalogue id with a mapping of edits and links, and add a uniqueness expectation
C: Add the product's colour and size to the name so that the combined string is unique for every product currently in the catalogue
D: Delete both products and recreate them under new names chosen to be distinct
K: B
G: ## Natural keys must be unique and stable
The exam guide asks for stable primary keys and warns against duplicated or ambiguous identity. Names collide and change; catalogue identifiers do neither.
## Fix
- New key: SKU or catalogue id.
- Migration: map existing objects (and the merged one, split by the underlying rows) to the new keys; carry edits and links.
- Expectation: key uniqueness and non-null on the backing dataset.
Example: the two products become P-1182 and P-1190; their orders link correctly after the migration.
W: Migrate to a true identifier with key expectations: it fixes the collision and prevents the next one.
X: A=Rename: the next name collision or rename re-breaks identity; names are the wrong key.
C=Append colour: the key is still a mutable, human-chosen string that can collide or change; it postpones the next failure rather than preventing it.
D=Delete and recreate: destroys edits and links; identity remains name-based.
T: Use stable catalogue identifiers, never names, as primary keys; guard uniqueness with an expectation.
V: Ontology Manager, expectations

@ PLTR-DE D7 T7.3 applied tradeoff
S: Analysts want an object type "MonthlyRegionSales" with properties for revenue, units and top product per region per month. Is this acceptable, and under what conditions?
A: No; aggregates must never be object types, since the Ontology only models real-world entities
B: Yes, as a derived object type keyed by its grain (region × month), documented as computed from Sales and kept alongside Sale
C: Yes, but only if the aggregate replaces the Sale object type entirely, to avoid any duplication of sales data inside the Ontology
D: No; the analysts should recompute the aggregates in each dashboard from the Sale objects every time
K: B
G: ## Derived object types done properly
The exam guide warns against dashboard-shaped types yet accepts materializations with defined grain. The difference is discipline: a key that is the grain, documentation that it is derived, and the source entities kept.
## Conditions
- Key: (region, month); properties are aggregates over Sale.
- Lineage: computed by the pipeline from Sales; refreshed on schedule.
- Purpose: efficient reporting; Sale objects remain the source of truth.
Example: dashboards read MonthlyRegionSales instantly; drill-down goes to Sale objects.
W: A derived type with a defined grain, documented and refreshed, alongside the source entities: acceptable and useful.
X: A=Never: materialized aggregates with proper grain are legitimate.
C=Replace Sales: the aggregate cannot answer order-level questions; the source entities must stay.
D=Recompute everywhere: slow and inconsistent across dashboards.
T: Materialize aggregates as derived object types with a clear grain, documented and kept alongside the source entities.
V: Ontology Manager, Pipeline Builder

@ PLTR-DE D7 T7.4 applied use-case
S: An Ontology change needs both a new object type and a change to the pipeline that produces its backing dataset. How should the two be developed and released together?
A: Release the pipeline change first to production, then create the object type a week later once the dataset looks right
B: Use Global Branching spanning the pipeline and the Ontology resources, develop both on the branch, validate, and merge together
C: Create the object type first against an empty dataset, then change the pipeline on main and let the object type populate when the build runs
D: Develop both directly on main during a maintenance window announced to users
K: B
G: ## Coordinated data and Ontology changes
The exam guide names Global Branching for evolving live Ontology resources safely, and it covers backing datasets as well. Developing both sides on one branch keeps them consistent.
## Workflow
- Branch includes the pipeline and the new object type.
- Build the dataset on the branch; configure and test the object type against it.
- Review; merge both at once; the object type goes live with data.
Example: the object type's primary key mapping is validated against branch data before anything reaches production.
W: Global Branching spanning pipeline and Ontology, merged together: consistency and validation before release.
X: A=Pipeline first, type later: a week of a dataset nobody consumes and a type developed blind.
C=Type on empty data: cannot validate keys or links without data.
D=Main during a window: untested changes on production resources.
T: Develop dependent pipeline and Ontology changes on one branch and merge them together.
V: Global Branching, Ontology Manager

@ PLTR-DE D7 T7.1 applied use-case
S: Two object types, Invoice and Payment, each have an "amount" property with different currencies and rounding conventions in their sources, causing confusion in applications. What modeling improvement helps?
A: Rename the properties to amount_invoice and amount_payment so users can tell them apart
B: Define a shared monetary value type (currency code plus normalized decimal) for both properties, with pipelines normalizing to it
C: Convert all amounts to a single reporting currency in the pipeline and store them as plain integers without any currency information
D: Store the amount as a free-text string that includes the currency symbol as it appears in the source
K: B
G: ## Value types for consistent semantics
The exam guide lists value types and shared properties among modeling constructs. A monetary value type defines what an amount means (currency, scale) so every object type that uses it is consistent.
## Design
- Value type: `Money` = decimal amount with scale 2 plus ISO currency code.
- Pipelines normalize sources into it (rounding rule applied once, documented).
- Applications format and compare amounts uniformly.
Example: an invoice of 1,200.50 EUR and a payment of 1,200.50 EUR compare equal and display identically.
W: A shared monetary value type with pipeline normalization: consistent meaning and handling across object types.
X: A=Renaming: the two amounts still carry different currencies and rounding; a clearer name does not make them comparable.
C=Single currency, no code: loses information needed for reporting and reconciliation.
D=Free text: a string with a symbol cannot be summed, compared or converted; every consumer would have to parse it differently.
T: Define value types for cross-cutting attributes like money so semantics are consistent across the Ontology.
V: Ontology Manager

@ PLTR-DE D7 T7.2 applied use-case
S: A link between Employee and Department must support the fact that an employee can move between departments over time, and applications need to know the current department and the history. How should this be modeled?
A: A single many-to-one link from Employee to Department, overwritten each time the employee moves
B: An EmployeeDepartmentAssignment object type with start and end dates linked to both, plus a derived current-department link on Employee
C: A many-to-many link between Employee and Department with no dates, since the history is implied by the set of linked departments
D: A list of department names on the Employee object in chronological order
K: B
G: ## Temporal relationships
The exam guide asks for modeling that remains useful to applications and AI workflows; history and current state are different questions.
## Model
- Assignment object: employee, department, start, end (null for current).
- Links: Assignment → Employee, Assignment → Department.
- Current department: a derived link or property on Employee computed in the pipeline from the open assignment.
Example: an employee's three assignments show the career path; the current link answers "where are they now" instantly.
W: Assignment objects with dates plus a derived current link: both history and current state are modeled and fast.
X: A=Overwritten link: every move erases the previous department, so the history the applications need is gone.
C=Dateless many-to-many: the set of departments says nothing about order or which one is current; the two questions cannot be answered.
D=List on Employee: unqueryable and unlinked to Department objects.
T: Model time-varying relationships as dated assignment objects with a derived current link.
V: Ontology Manager

@ PLTR-DE D7 T7.5 applied tradeoff
S: A property "risk score" is computed from an object's own attributes by a formula that changes weekly as the risk team tunes it, and must be applied consistently in reports. Where should it be computed?
A: North of the Ontology, in a function called by each application when it displays the object, so the latest formula always applies
B: South of the Ontology, in the pipeline, with the formula version recorded, so every consumer sees the same score
C: In each report separately, so that report owners can apply the formula they prefer
D: Nowhere; the risk team should calculate scores in a spreadsheet
K: B
G: ## Consistency favours materialization
The exam guide asks where computation belongs; a value used in reports across consumers that must be consistent is a pipeline value, even if the formula changes often.
## Design
- Pipeline computes `risk_score` and `risk_formula_version`.
- Weekly formula changes are released through the pipeline (branch, validate, merge); the version column makes mixed states visible.
- Reports read the property.
Example: two reports on the same day show the same score; last week's reports show the old version, labelled.
W: Pipeline-computed, versioned score: consistent across consumers and auditable as the formula evolves.
X: A=Per-display function: reports from the same day can differ if the formula changes mid-day, and filters cannot use it.
C=Per report: each report applies its own formula, so the same object shows different scores depending on where you look; inconsistency by design.
D=Spreadsheet: scores maintained by hand outside the platform have no lineage, no schedule and no connection to the objects they describe.
T: Values that must be consistent across consumers are computed south, with the formula version recorded.
V: Pipeline Builder, Ontology

@ PLTR-DE D7 T7.4 advanced troubleshooting
S: After changing a property's type from string to integer on a live object type, several Workshop filters and a function broke. What should the engineer have done, and what now?
A: Nothing could have prevented it; property type changes always break consumers in some way and must simply be done quickly to limit the damage
B: Treated it as breaking: found consumers, changed type and consumers together on a branch; now revert or hot-fix, then redo properly
C: Changed the type only at night when fewer users were affected
D: Kept the type as string forever, since type changes are never worth the risk
K: B
G: ## Type changes are breaking
The exam guide asks you to evolve live resources via Global Branching and to assess consumers before changing semantics. A type change breaks filters, comparisons and function signatures.
## Should have
- Consumer discovery via lineage and usage.
- Branch: type change plus consumer updates; validate; merge together.
- Alternatively add a new typed property and migrate consumers, then retire the old one.
## Now
- Revert on production or hot-fix the consumers, then redo the change properly.
Example: a new `quantity_int` property is added, consumers migrated over two weeks, then the old string property is removed.
W: Branch-coordinated change with consumer updates, and a revert or hot-fix now: the right process and the right recovery.
X: A=Unavoidable: branching and consumer coordination prevent exactly this.
C=Night: the filters and the function break just the same; fewer users at the moment of breakage does not make the change safe.
D=Never change: types can and should evolve when needed; the discipline is coordination.
T: Treat property type changes as breaking; coordinate consumers on a branch and merge together.
V: Global Branching, Ontology Manager
