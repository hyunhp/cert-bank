# PLTR-DE batch 16: Domain 7 round 2 (Ontology Data Modeling), 8 questions

@ PLTR-DE D7 T7.1 applied use-case
S: An "Order" object type has 120 properties, including the customer's address fields, the product's specifications and the warehouse's contact details, all copied onto each order. Applications are slow and the data is often inconsistent. What is the modeling problem and fix?
A: There is no modeling problem; wide object types with everything copied on are faster for applications because no link traversals are needed
B: It is overly broad and duplicates other entities; model Customer, Product and Warehouse as object types linked from Order
C: Delete the extra properties and keep only the order id
D: Split Order into 12 object types of 10 properties each by column position
K: B
G: ## Normalization in the Ontology
The exam guide asks you to apply normalization principles and avoid duplicated or overly broad object types. Copying another entity's attributes onto every order means a customer address change requires updating thousands of orders, and the "same" customer differs across orders.
## Fix
- Customer, Product, Warehouse as object types with stable keys.
- Order keeps order-level properties (date, status, totals) and links to the three.
- Applications traverse links for related attributes.
Example: an address change updates one Customer object and every order shows it correctly through the link.
W: Normalize into entity object types with links: it removes duplication, fixes inconsistency and keeps Order focused on order facts.
X: A=Wide is fine: duplication is the cause of the inconsistency; width also slows indexing and queries.
C=Keep only the id: order-level properties are needed; the problem is the foreign attributes, not all properties.
D=Split by column position: arbitrary fragments are not entities; it fixes nothing semantically.
T: Model each real entity once and link to it; do not copy its attributes onto related objects.
V: Ontology Manager

@ PLTR-DE D7 T7.2 applied use-case
S: A Patient object type must be linked to Hospital. Each patient is registered at exactly one hospital; each hospital has many patients. The patients dataset has a `hospital_id` column. Which link configuration is correct?
A: A many-to-many link backed by a separate join dataset of patient and hospital ids maintained by the pipeline
B: A many-to-one link from Patient to Hospital using `hospital_id` on the patient dataset
C: A one-to-one link, since each patient has one hospital
D: No link; store the hospital name on the patient as a property
K: B
G: ## Cardinality from the real relationship
The exam guide asks for appropriate link cardinality. "Each patient at one hospital, each hospital many patients" is many-to-one from Patient to Hospital, and the foreign key on the patient row is exactly what backs it.
## Configuration
- Patient.hospital_id references Hospital's primary key.
- Link: many Patients → one Hospital.
- Traversals: Hospital → its patients; Patient → its hospital.
Example: Hospital H-3 lists 4,200 patients; patient P-9 shows hospital H-3 with its properties via the link.
W: Many-to-one via the foreign key: it mirrors the relationship and needs no extra dataset.
X: A=Many-to-many: a patient has one hospital; a join dataset models a relationship that does not exist and allows invalid multiple registrations.
C=One-to-one: a hospital has many patients; one-to-one would allow only one patient per hospital.
D=Name as property: copying the name denormalizes and loses the ability to traverse to the Hospital object.
T: Many rows pointing to one entity via a foreign key is a many-to-one link.
V: Ontology Manager

@ PLTR-DE D7 T7.3 applied troubleshooting
S: An analyst created an object type "CustomerProduct" with one object per customer-product pair holding the customer's name, the product's name and the number of purchases. Applications now need customer addresses too, and the analyst proposes adding them to CustomerProduct. What should the data engineer advise?
A: Add the address columns to CustomerProduct, since that is the object type the applications already read and it avoids a model change
B: Model Customer and Product as object types with a Purchase relationship holding the count, and put the address on Customer
C: Create a new object type CustomerProductAddress
D: Store the address as a JSON string on CustomerProduct
K: B
G: ## Recognizing an aggregate masquerading as an entity
The exam guide warns against dashboard-shaped and duplicated object types and asks for normalization. CustomerProduct is a pair-level aggregate; customer attributes belong to Customer.
## Fix
- Customer (with address), Product.
- The purchase count: a Purchase object per customer-product with count, or a many-to-many link with properties if supported in the model.
- Applications read the address via Customer.
Example: a customer moves; one Customer object changes rather than 300 CustomerProduct rows.
W: Entity object types with the aggregate kept as a relationship: attributes live with their entity and duplication is avoided.
X: A=Add to the aggregate: the address would be duplicated per product and drift.
C=Another aggregate type: a third place holding customer attributes multiplies the duplication instead of removing it.
D=JSON string: the address becomes unqueryable and unfilterable, and it is still duplicated on every customer-product row.
T: Entity attributes belong on the entity's object type, never on an aggregate or pair object.
V: Ontology Manager

@ PLTR-DE D7 T7.4 applied use-case
S: An object type's property must be renamed, and three Workshop apps and two functions reference it. How should this be approached?
A: Rename it in place during the day, since renames are instant
B: Rename on a Global Branching branch, update the apps and functions there, validate, and merge together
C: Add a second property with the new name alongside the old one and leave both in place forever so that nothing ever needs to be updated
D: Delete the property and recreate it with the new name
K: B
G: ## Coordinated Ontology and consumer changes
The exam guide names Global Branching as the mechanism for safely evolving live Ontology resources. A rename breaks every reference; the change and the references must move together.
## Process
- Branch covering the Ontology and the consuming resources.
- Rename on the branch; fix the apps and functions on the branch; test.
- Merge once, so production flips consistently.
- Where a transition is needed, keep an alias or both properties briefly, then remove the old one.
Example: all five consumers are validated on the branch; the merge happens at a quiet hour with no user-visible breakage.
W: Branch-based coordinated rename: references and the property change atomically after validation.
X: A=Rename live: the three apps and two functions reference the old name and break immediately, in front of users.
C=Permanent duplicate: confusion and double maintenance; a transition should end.
D=Delete and recreate: destroys edits and links attached to the property's object and still breaks references.
T: Make Ontology renames on a branch together with their consumers, and merge once.
V: Global Branching, Ontology Manager

@ PLTR-DE D7 T7.1 applied use-case
S: The business wants to attach "country" values with a fixed list and consistent display across many object types. Which Ontology construct helps?
A: A free-text string property on each object type, trusting pipelines to spell countries consistently
B: A value type or shared property that defines the allowed values and formatting once and is reused
C: A separate Country object type linked from every other object type in the Ontology, even where only the label is needed for display
D: A JSON property holding the country name and code together
K: B
G: ## Shared properties and value types
The exam guide lists shared properties and value types among modeling constructs. A value type defines constraints and semantics (allowed values, format) once; a shared property reuses a property definition across object types so applications treat it uniformly.
## Fit
- Consistency: one allowed-value list; the pipeline validates against it (an expectation).
- Reuse: filters and displays work the same on every object type.
Example: `country` as a shared property with a value type of ISO codes appears on Customer, Supplier and Site identically.
W: Value type or shared property: it enforces the fixed list and consistent display across types without duplicating definitions.
X: A=Free text everywhere: spellings diverge ("USA", "U.S.", "United States"); nothing enforces the list.
C=Country object type: valid when country has its own attributes and links; for a label with a fixed list, a value type is lighter, and the question says only the label is needed.
D=JSON: a combined name-and-code string is unstructured, cannot be constrained to a list, and is not uniformly filterable.
T: Use value types and shared properties for consistent, constrained attributes across object types.
V: Ontology Manager

@ PLTR-DE D7 T7.2 applied troubleshooting
S: An object type's primary key column has 2% null values in the backing dataset, and those rows do not appear as objects. The analyst wants them included. What is the correct response?
A: Replace the null ids with the string "UNKNOWN" in the transform so that every row has a key value and appears as an object
B: Investigate why those rows lack ids, fix identity upstream or derive a deterministic key, and add a non-null expectation
C: Use the row number as the key for those rows only
D: Ask the Ontology to accept null keys
K: B
G: ## Keys must be present and stable
The exam guide asks for stable primary keys and for not silently coercing data. Rows without a key are not identifiable entities; they must get an identity deliberately, not a placeholder.
## Response
- Investigate: why do 2% lack an id? Source bug, a different entity type, test data?
- Fix upstream when possible.
- If the rows are real and have identifying columns, a deterministic hash of those columns can serve as a key, documented.
- Expectation: key non-null and unique, so the problem is caught at build time in future.
Example: the null-id rows were records from a legacy system; a migration assigns them proper ids and the expectation prevents a recurrence.
W: Investigate and fix identity upstream or derive a deterministic key, with an expectation: the rows become real objects without inventing identity.
X: A="UNKNOWN": all such rows collide on one key; at most one object results and it is meaningless.
C=Row number: positional keys change on every rebuild; edits and links detach.
D=Null keys: an object must have a key; the Ontology cannot index or link a null identity.
T: Never fill a primary key with placeholders; fix identity at the source or derive it deterministically, and guard with an expectation.
V: Ontology Manager, expectations

@ PLTR-DE D7 T7.5 applied tradeoff
S: Which of the following computations is best placed north of the Ontology rather than materialized in the pipeline?
A: Each customer's total spend over the last year, used in list filters and in several dashboards across the company
B: A what-if delivery date for an order if the user moves it to another warehouse, computed while they edit it in Workshop
C: The number of open tickets per customer, refreshed hourly
D: A product's average rating from all reviews, refreshed daily
K: B
G: ## North of the Ontology: interactive, context-dependent
The exam guide asks you to decide whether computation belongs north or south of the Ontology. South: deterministic, reusable, periodically refreshed, used in filters. North: depends on the user's current input and happens at interaction time.
- Total spend, open ticket count, average rating: reusable, filterable, periodic: south (materialized properties).
- "What if I move this order to warehouse B?": depends on a hypothetical input the user is typing now; cannot be precomputed for every possibility: north (a function called from Workshop).
Example: the function computes the hypothetical date from the order and the chosen warehouse's lead time when the user changes the selection.
W: The what-if delivery date: it is interactive and depends on unsaved user input, which is the north-of-Ontology case.
X: A=Total spend: reusable, filterable and refreshed periodically; it is materialized south as a property.
C=Open ticket count: an hourly aggregate that many consumers share; computed south in the pipeline.
D=Average rating: a daily aggregate over reviews, identical for every viewer; computed south in the pipeline.
T: Precompute reusable aggregates south; compute hypothetical, user-input-dependent values north at interaction time.
V: Ontology, AIP Logic

@ PLTR-DE D7 T7.4 advanced tradeoff
S: A team wants to retire an old object type that applications no longer use and replace it with a redesigned one backed by a new dataset. Some users made edits on the old objects. What migration plan is appropriate?
A: Delete the old object type immediately, since no application uses it
B: Verify consumers with lineage, map old to new by stable key, migrate edits and links, overlap briefly, then deprecate and remove
C: Keep both object types forever to be safe
D: Rename the old object type to the new name and point the new dataset at it as its backing, without migrating any of the user edits
K: B
G: ## Planned migrations
The exam guide asks you to plan migrations when requirements change and to assess existing consumers before changing semantics. "No application uses it" must be verified, and user edits are data that must be carried over.
## Plan
- Verify: lineage, object usage, functions and automations referencing the type.
- Map: old key → new key.
- Migrate: edited property values and links to the new objects; validate.
- Overlap: both available briefly for comparison; then deprecate with notice and remove.
Example: 1,100 user edits are migrated; a forgotten automation referencing the old type is found by the usage check and updated.
W: Verified, key-mapped migration of edits and links with a short overlap and planned removal: nothing is lost and nothing breaks unexpectedly.
X: A=Delete now: user edits are lost and any unverified consumer breaks.
C=Keep forever: two versions of the same entity confuse users and double maintenance.
D=Rename and repoint: a different backing dataset under the old type does not migrate edits and may mismatch keys.
T: Retire object types through a verified, key-mapped migration of edits and links, with overlap and planned removal.
V: Ontology Manager, Data Lineage
