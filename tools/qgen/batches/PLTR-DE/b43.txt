@ PLTR-DE D2 T2.2 applied use-case
S: Two datasets must be combined: one lists every customer, the other lists only customers who placed orders this month with their totals. The output must include all customers, with a zero total for those without orders. Which join and handling are correct?
A: An inner join on customer id, since only matched customers have meaningful totals for the month
B: A left join from customers to the totals on customer id, with the total coalesced to zero when unmatched
C: A right join from customers to the totals, which keeps every customer whether or not they ordered
D: A cross join followed by a filter on matching ids, which produces the same result as any other join
K: B
G: ## Preserving the full population
The exam guide asks for correct joins and cardinality reasoning. "All customers" means the customer side must be preserved; missing totals become zero by explicit rule.
## Pattern
- Left join customers → totals on id.
- `coalesce(total, 0)` for unmatched rows.
- Expectation: output row count equals the customer count.
Example: 120,000 customers in, 120,000 rows out; 95,000 with zero.
W: Left join from the full population with an explicit zero default: every customer appears and the absence of orders is represented correctly.
X: A=Inner join: drops every customer without orders, which contradicts the requirement.
C=Right join from customers to totals: preserves the totals side, dropping customers without orders.
D=Cross join then filter: produces a huge intermediate result and, after the filter, behaves like an inner join.
T: Use a left join from the full population and default missing values explicitly.

@ PLTR-DE D2 T2.3 applied troubleshooting
S: A Spark transform runs fine but its output dataset consists of 20,000 tiny files, which slows every downstream read. What should the engineer change?
A: Ask downstream consumers to read the files in smaller batches so that the number of files matters less to them
B: Repartition the output to a sensible partition count before writing, then confirm file count and read time
C: Increase the executor count on the downstream transforms so that they can open the 20,000 files faster
D: Convert the output to CSV so that the files are easier to read for any tool that needs them
K: B
G: ## Output file sizing
The exam guide names small-file accumulation as a performance problem and asks for Spark-level fixes. Too many output partitions produce too many small files.
## Fix
- Repartition to a count that yields reasonably sized files for the data volume.
- Or partition by a meaningful key with controlled file counts per key.
- Verify file count and downstream read time.
Example: 20,000 files become 40; downstream builds start reading in seconds instead of minutes.
W: Right-size output partitions before writing: the file count drops and every downstream read gets faster.
X: A=Consumers read in batches: pushes the problem onto every consumer instead of fixing the producer.
C=More downstream executors: file-open overhead remains; more executors only spread the waste.
D=CSV: larger, untyped and slower to read; the file count is unchanged.
T: Control output file counts by repartitioning before writing.
V: Spark Details, Code Repositories

@ PLTR-DE D2 T2.4 applied use-case
S: A pipeline produces a dataset used for financial reporting. The finance team wants to know, for any month, exactly which version of the transformation logic produced the numbers. What should the engineering practice provide?
A: A spreadsheet maintained by hand by the team lead that lists the dates on which the transform code was changed and by whom
B: Reviewed, versioned code, builds tied to the commit that produced each transaction, and lineage to inputs
C: A promise from the engineer that the logic has not changed since the last audit
D: A screenshot of the transform code taken at each month end
K: B
G: ## Reproducible provenance
The exam guide asks for versioned, reviewed transformations and lineage. Provenance comes from the build system, not from records kept on the side.
## Practice
- Code in a repository; changes merged through review.
- Each dataset transaction tied to the build and code version.
- Lineage shows inputs and logic for any version.
Example: the March report traces to transaction T-882, built from commit 4f2a on 2 April, reviewed by two engineers.
W: Versioned code, build-to-commit linkage and lineage: any month's numbers trace to the exact logic and inputs that produced them.
X: A=Manual spreadsheet: drifts from reality and cannot prove which code built a given transaction.
C=Engineer's promise: an auditor needs evidence tied to each transaction; a personal assurance proves nothing about any particular month.
D=Screenshots: images of code are not linked to the dataset transactions and could show code that never ran for that month.
T: Make transformation provenance automatic through versioned code, build linkage and lineage.

@ PLTR-DE D2 T2.2 applied troubleshooting
S: A transform that computes average order value per region produces a value that is far too low for one region. Investigation shows many orders in that region have a null amount. How should the computation handle this?
A: Treat null amounts as zero in the average, since a missing value most likely means the order was free of charge
B: Agree null semantics with the business, usually excluding nulls and reporting their count, and monitor the null rate
C: Drop the region from the output until the nulls disappear on their own
D: Replace null amounts with the global average so the region's figure looks normal
K: B
G: ## Nulls in aggregates
The exam guide asks for correct aggregations and data contracts. Treating nulls as zero silently changes the meaning of an average.
## Handling
- Agree semantics: null means unknown, not zero.
- Exclude from the average; report the count of excluded orders.
- Health check on the null rate; investigate the source.
Example: the region's average rises to a plausible value and the dashboard shows "1,240 orders with missing amount".
W: An explicit, agreed null policy with visible counts and monitoring: the average is correct and the data gap is surfaced rather than buried.
X: A=Null as zero: drags the average down and misrepresents unknown amounts as free orders.
C=Drop the region: hides the region's data entirely and solves nothing upstream.
D=Global average imputation: fabricates values and masks the source problem.
T: Define null semantics explicitly in aggregates and make missing data visible.
V: Pipeline Builder, Data Health

@ PLTR-DE D2 T2.1 applied tradeoff
S: An analyst-friendly Pipeline Builder pipeline has grown to 150 nodes with deeply nested logic, and changes now take days to review. What is a sensible next step?
A: Keep adding nodes to the same pipeline, since visual pipelines can grow without limit
B: Refactor into stages with intermediate datasets and contracts, moving complex reusable logic into tested code
C: Rewrite the whole pipeline in code over a weekend and replace the original on Monday without comparing the outputs
D: Freeze the pipeline and prohibit further changes
K: B
G: ## Keeping pipelines maintainable
The exam guide asks for maintainable transformations and the right authoring tool per need. Size and nesting are signals to stage and, where warranted, codify.
## Refactor
- Stages with intermediate datasets and expectations at each boundary.
- Complex reusable logic into tested code transforms.
- Simple mappings remain visual for analyst access.
- Branch comparison of outputs before switching.
Example: the pipeline becomes four stages; reviews shrink to the stage that changed.
W: Staging with contracts and selective codification: reviews become local and testable logic gets tests without abandoning the visual tool where it fits.
X: A=Keep growing: review time and risk keep rising with every node.
C=Weekend rewrite without comparison: an unvalidated replacement of a critical pipeline.
D=Freeze: the business keeps needing changes; prohibiting them pushes work into unofficial copies of the pipeline.
T: Stage large visual pipelines and move complex logic into tested code where it helps.
V: Pipeline Builder, Code Repositories

@ PLTR-DE D2 T2.3 applied use-case
S: A transform joins a 2 TB events table to a 300 GB sessions table on session id. Both are large. Which optimization is appropriate when the join is the bottleneck?
A: Broadcast the 300 GB sessions table to every executor so that the much larger events table never needs to be shuffled
B: Prune both sides early, co-partition or bucket them on session id, and check for skew in Spark details
C: Collect the sessions table to the driver and look up sessions in a Python dictionary
D: Convert both tables to CSV before joining to make them easier to read
K: B
G: ## Large-to-large joins
The exam guide asks for efficient join strategies. Broadcasting only works for small sides; large-to-large joins benefit from co-partitioning, early pruning and skew handling.
## Practice
- Filter early: only the needed dates and columns.
- Co-partition or bucket on the join key so matching rows meet with less shuffle.
- Spark details: check for a skewed session id.
Example: pruning to 30 days and two dozen columns plus bucketing cuts the join stage from 90 to 15 minutes.
W: Co-partitioning on the key with early pruning and skew checks: the standard approach when neither side is small.
X: A=Broadcast 300 GB: far too large for executor memory; the job fails.
C=Collect to driver: a 300 GB table cannot fit in a single driver's memory; the job fails before any lookup happens.
D=CSV: text files are larger and slower to parse than columnar data, and the format has no effect on the join's shuffle.
T: For large-to-large joins, prune early and co-partition on the key instead of broadcasting.
V: Spark Details, Code Repositories

@ PLTR-DE D2 T2.4 applied comparison
S: Which practice best prevents a transform change from silently altering a published dataset's output?
A: Reading the code diff carefully during review, which is enough for an experienced reviewer to see any change in the output
B: A branch build compared with production output (counts, keys, metrics), plus expectations and unit tests
C: Running the transform locally on ten handwritten rows
D: Merging quickly and checking the dashboard the next morning
K: B
G: ## Output comparison as the safety net
The exam guide asks for validation on branches before release. Code review sees intent; output comparison sees effect.
## Practice
- Branch build on real inputs.
- Compare with production: counts, key sets, sums, distributions.
- Expectations and unit tests for known rules.
Example: a harmless-looking refactor changes 0.3% of rows because of null handling; the comparison catches it.
W: Branch build with output comparison plus tests and expectations: changes in effect are seen before they reach consumers.
X: A=Diff review alone: subtle data effects are invisible in code.
C=Ten handwritten rows: the rows the author imagines rarely include the nulls, duplicates and odd values that real data contains.
D=Check the dashboard later: by the next morning consumers have already seen and possibly acted on the changed numbers.
T: Compare branch outputs with production before merging any transform change.
V: Code Repositories, branches

@ PLTR-DE D2 T2.1 advanced use-case
S: A team must implement a transformation that standardizes company names across several sources (removing suffixes like "Inc." or "GmbH", fixing case, handling known aliases). Which implementation is most maintainable?
A: A single long expression in one visual node with dozens of nested replace calls written inline for every rule and alias
B: A tested code function with ordered rules and a governed alias reference dataset the business can update
C: A manual cleaning step in a spreadsheet each week before the data is uploaded
D: An LLM call for every name on every run with no validation or caching
K: B
G: ## Rules plus reference data
The exam guide asks for maintainable, tested transformations and governed reference data. Name standardization has stable rules and a changing alias list.
## Implementation
- Code function: ordered rules (case, punctuation, suffix removal), documented.
- Alias mapping as reference data maintained by the business.
- Unit tests on tricky cases; expectations on output uniqueness.
Example: adding "IBM Corp" → "IBM" to the alias dataset fixes the next build without a code change.
W: Tested rule function plus governed alias data: logic is reviewable and testable, and the changing part is maintained as data.
X: A=Nested inline replaces: unreadable, untested and hard to change safely.
C=Weekly spreadsheet: a manual cleaning step outside the pipeline is unscheduled, unversioned and breaks the first week someone is away.
D=Unvalidated LLM per run: pays for the same names every run, can change a name between runs, and nothing checks the result.
T: Implement standardization as tested rules with a governed reference for the parts that change.
V: Code Repositories, expectations
