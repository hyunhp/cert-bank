# PLTR-DE batch 33: Domain 8 round 4 (AI-Assisted Data Engineering), 8 questions

@ PLTR-DE D8 T8.1 applied use-case
S: A data engineer is debugging a failing PySpark transform and wants help interpreting a long stack trace. Which capability is designed for this?
A: An LLM transform run over the stack trace stored as a single dataset row, producing an explanation column the engineer can read
B: A code assistant (Continue or AI FDE) in the development environment that reads the error and the code and suggests a diagnosis to review
C: AIP Assist, the platform helper, which fixes failing transforms automatically and redeploys them when given an error message
D: An embedding transform that compares the stack trace with previous traces in a dataset to find the most similar past failure
K: B
G: ## Assistants in the development loop
The exam guide distinguishes code assistants from data-producing transforms. Interpreting an error during development is interactive assistance in the editor.
## Use
- The assistant reads the trace and the transform, explains the likely cause and proposes a change.
- The engineer validates on a branch; nothing is applied automatically.
Example: the assistant points out that a column name in the join was renamed upstream; the engineer confirms via lineage and fixes it.
W: A code assistant in the editor: interactive help with errors and code, reviewed by the engineer.
X: A=LLM transform: a pipeline step for data rows, not an interactive debugging aid.
C=AIP Assist auto-fix: the platform helper does not edit and redeploy transforms on its own.
D=Embedding comparison: finding similar past traces is a stretch; the engineer needs a diagnosis now.
T: Use code assistants for interactive debugging; keep the engineer in control of the fix.
V: Continue, Code Repositories

@ PLTR-DE D8 T8.2 applied use-case
S: An LLM transform classifies supplier invoices by spend category. The finance team requires that every classification can be explained and traced. Which configuration satisfies this?
A: Store only the category value per invoice, since storing explanations alongside it would roughly double the storage for the dataset
B: Structured output with category and reason, retention of prompt version, model and raw response per row, and a link to the source invoice
C: A monthly sample of ten classifications reviewed by the finance team, with the review notes stored in a shared document
D: An instruction in the prompt telling the model to be transparent about its reasoning when it assigns a category
K: B
G: ## Explainability as data
The exam guide asks for structured outputs and retention of prompts and raw responses for auditability. Explanation is a field; provenance is metadata.
## Configuration
- Output: `{category: enum, reason: string}`.
- Per row: prompt version, model, raw response, source invoice reference.
- Query: finance can pull any invoice's classification with its reason and provenance.
Example: invoice INV-8812 was classified "IT services" with the reason "line items reference software licences" by prompt v6.
W: Reason field plus provenance and source links: every classification is explainable and traceable on demand.
X: A=Category only: when finance asks why an invoice was classified a certain way, there is nothing stored to answer with.
C=Monthly sample: does not cover any specific invoice finance asks about.
D=Transparency instruction: an instruction produces nothing stored or traceable.
T: Capture a reason field and provenance for each AI classification that must be explainable.

@ PLTR-DE D8 T8.3 applied tradeoff
S: A team proposes running an LLM on every row of a 50 million row dataset nightly to compute a field that only 0.5% of rows (those with a non-empty free-text note) can actually have. What should the data engineer advise?
A: Run it on all 50 million rows every night, since consistency of treatment across the dataset matters more than the compute cost
B: Filter deterministically to rows with a non-empty note that changed since the last run, run the LLM on those, null elsewhere
C: Run it on a random 10% sample of rows each night to save cost, accepting that most rows will never receive a value
D: Replace the LLM step with a deterministic rule that sets the field to "unknown" for all rows, removing the cost entirely
K: B
G: ## Target the model at the rows that need it
The exam guide pairs AI processing with deterministic filtering and incremental processing. Rows without the input the model needs should never be sent to it.
## Design
- Deterministic filter: `note IS NOT NULL AND note != ''`.
- Incremental: only changed rows among those.
- Null semantics: a defined "not applicable" for the rest.
Example: 250,000 eligible rows instead of 50 million; nightly calls fall by 99.5% and the result is identical.
W: Deterministic pre-filtering and incremental processing: the model runs only where it can produce a value.
X: A=All rows: 49.75 million calls on rows with no note can only return nothing, at enormous cost for zero information.
C=Random sample: misses most eligible rows and processes ineligible ones.
D=Rule to "unknown": the field exists to capture what the notes say; a constant value abandons the requirement entirely.
T: Pre-filter AI steps to eligible rows and process incrementally; never send rows the model cannot use.

@ PLTR-DE D8 T8.4 applied troubleshooting
S: A code assistant generated a SQL transform that uses a `SELECT *` from a wide input followed by downstream logic. Reviewers are concerned. Why, and what should change?
A: There is no concern; `SELECT *` is the simplest and most maintainable way to get all of the input's columns into the output
B: `SELECT *` couples the output to the input's full schema, so new columns flow through; select columns explicitly and add a schema expectation
C: The assistant should have used `SELECT ALL` instead of `SELECT *`, which is the recommended form for wide inputs
D: The transform should be converted to a Python transform, since SQL transforms cannot express column selection safely
K: B
G: ## Reviewing generated SQL
The exam guide asks data engineers to review AI-generated code for unsupported patterns and regressions. Implicit column selection is a maintainability and contract risk.
## Fix
- Explicit column list: the transform's output contract is stable.
- Schema expectation on the output.
- Narrower reads: less data scanned, cheaper builds.
Example: an upstream team adds a PII column; the explicit select keeps it out of the curated output automatically.
W: Explicit column selection with a schema expectation: stable contract, protected output, cheaper reads.
X: A=No concern: schema drift and accidental propagation of new columns are real risks.
C=`SELECT ALL`: not a real alternative; it still selects every column implicitly and carries the same drift risk.
D=Convert to Python: an implicit `select(*)` in Python has the same problem; the language is not the issue, the explicit column list is.
T: Replace implicit column selection in generated code with explicit, contracted selects.
V: Code Repositories

@ PLTR-DE D8 T8.2 applied use-case
S: An LLM transform occasionally returns responses that cannot be parsed into the expected structure. What should happen to those rows?
A: They should be silently dropped from the output so that the dataset contains only well-formed rows and consumers see no errors
B: Keep them with a failure status and raw response, exclude them from consumer-facing properties, count them, retry or review
C: They should be filled with the most common category observed across the dataset so that the output has no gaps for consumers
D: They should cause the entire build to fail every time one occurs, so that no transaction with any parse failure is ever published
K: B
G: ## Handling parse failures explicitly
The exam guide asks for deterministic post-processing and quality checks with explicit handling. A parse failure is information, not something to hide or to fabricate over.
## Handling
- Status column: `parsed`, `parse_failed`; raw response retained.
- Consumers read only parsed rows; failed rows are visible in the metric.
- Retry with backoff for transient causes; review for systematic ones; an expectation on the failure rate.
Example: 0.3% parse failures tonight, within tolerance; a jump to 8% would fail the rate expectation.
W: Explicit failure status with retention, exclusion from consumers and a rate metric: nothing is hidden or invented.
X: A=Silent drop: rows disappear from the output and nobody knows which or why; completeness is silently broken.
C=Fill with the common category: a fabricated classification presented as real, indistinguishable from a genuine result.
D=Fail the whole build: a few transient failures should not block all rows; a rate threshold should.
T: Record AI parse failures explicitly, keep them out of consumer data, and monitor their rate.
V: Pipeline Builder, expectations

@ PLTR-DE D8 T8.3 applied comparison
S: A pipeline enriches customer records with an LLM-generated summary. Applications also offer a "regenerate summary now" button. How do the two relate?
A: They are redundant ways of producing the same summary, so one of the two mechanisms should be removed to avoid confusion
B: The pipeline provides the baseline summary for every record; the button regenerates one record on demand via a versioned Action
C: The button should trigger a full run of the enrichment pipeline so that every record's summary is regenerated at once
D: The pipeline should be replaced by the button entirely, since on-demand regeneration is always fresher than a scheduled batch
K: B
G: ## Complementary layers
The exam guide allows pipeline-layer and Ontology-layer AI to coexist: batch for coverage, interactive for currency and user intent.
## Relationship
- Pipeline: every record has a summary; refreshed on schedule.
- Button: an Action calls the same (versioned) function for one record and writes the result with a version and timestamp.
- The pipeline's next run respects user-triggered versions (does not overwrite newer ones unless inputs changed).
Example: a sales rep regenerates one customer's summary after a big meeting; the nightly run leaves it until the record's inputs change.
W: Pipeline for coverage, Action for on-demand refresh, sharing one versioned function: complementary, not redundant.
X: A=Redundant: one gives every record a summary at scale, the other refreshes a single record when a user needs it now; different needs.
C=Button runs the pipeline: regenerating millions to refresh one.
D=Replace the pipeline: records nobody clicks on never get a summary.
T: Combine batch enrichment for coverage with on-demand regeneration through an Action for currency.
V: Pipeline Builder, Actions, AIP Logic

@ PLTR-DE D8 T8.4 applied use-case
S: A team relies on an AI assistant to write expectations for new datasets. What should the engineer verify in the generated expectations?
A: That they compile and run without errors on the current dataset, which is sufficient proof that the quality rules are correct
B: That each reflects the real contract rather than column-name guesses, thresholds are justified, and severity matches consequence
C: That there are as many expectations as possible on the dataset, since more rules always mean better data quality
D: That the assistant added a comment above each expectation explaining its purpose, so reviewers can read the intent
K: B
G: ## Reviewing generated quality rules
The exam guide asks for review of AI-generated outputs for incorrect assumptions. Expectations encode contracts; a wrong one blocks good data or passes bad data.
## Review
- Contract fidelity: does the business really require this? (A column named `email` may legitimately be null.)
- Thresholds: based on data profiling, not guesses.
- Blocking versus alerting: by consequence.
- Coverage: keys, required fields, allowed values; no gratuitous rules.
Example: the assistant proposed "amount > 0"; the reviewer knows refunds are negative and corrects it before it blocks the first refund.
W: Contract fidelity, justified thresholds, right severity, sensible coverage: the review that makes generated expectations trustworthy.
X: A=Compiles: a rule can compile, pass today's data and still encode a wrong assumption that blocks tomorrow's legitimate rows.
C=As many as possible: over-constraint blocks legitimate data.
D=Comments: an explanation of a wrong rule is still a wrong rule; review must check the contract, not the prose.
T: Review generated expectations against the real contract and consequence, not just for syntax.
V: expectations, Continue

@ PLTR-DE D8 T8.1 advanced tradeoff
S: Leadership asks the data engineering team to "put AI in every pipeline". What is a sound engineering response?
A: Comply fully by adding an LLM step to every transform in every pipeline regardless of what the transform does or whether it needs one
B: Apply AI where it fits: rules stay deterministic, AI handles bounded interpretation of unstructured data under validation and checks
C: Refuse to use AI in any pipeline on the grounds that non-deterministic steps are too risky for governed data
D: Add AI only to pipelines that are already failing regularly, on the theory that they are the ones that most need improvement
K: B
G: ## Principled adoption
The exam guide's AI-assisted domain is explicit: use deterministic logic for explicit rules, AI for bounded interpretation, and choose the layer by reuse and interactivity, with controls. "Everywhere" is not a criterion.
## Response
- Inventory candidate tasks: free text, documents, images that rules cannot handle.
- For each, design with structured output, validation, caching, audit and quality checks.
- Decline where rules suffice; measure value and cost.
Example: 6 of 40 pipelines gain a well-controlled AI step; 34 remain deterministic and cheaper.
W: Fit-based adoption with controls, and the discipline to decline where it does not fit: the engineering answer to a blanket mandate.
X: A=AI everywhere: cost, non-determinism and audit burden added to pipelines that need none.
C=Refuse entirely: free text, documents and images that rules cannot process stay unused; real value is forgone out of blanket caution.
D=Failing pipelines only: failure is not a criterion for AI; a failing pipeline needs diagnosis.
T: Adopt AI in pipelines where interpretation is needed and controls are in place; keep rules deterministic.
V: Pipeline Builder, Code Repositories
