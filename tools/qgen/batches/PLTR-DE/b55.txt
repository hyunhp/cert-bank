@ PLTR-DE D1 T1.2 expert troubleshooting
S: A supplier drops daily price files into an S3 prefix that Foundry ingests with a file batch sync set to APPEND, using the Exclude files already synced filter with its Last modified date option enabled. Occasionally the supplier re-uploads a corrected file under the same path. Since the first correction, every sync run fails while committing, and the dataset has not updated for four days. Downstream transforms are incremental and must stay incremental. The supplier's contract, renegotiated last month, already allows corrected files to be published under a new versioned file name, and downstream logic can keep the newest version per price list. Which configuration change resolves the failures while meeting these constraints?
A: Keep APPEND with Exclude files already synced, turn off its Last modified date option, and have corrections published under new versioned names
B: Keep APPEND with Exclude files already synced and its Last modified date option, and add a Limit number of files filter so each run commits fewer files
C: Switch to UPDATE with Exclude files already synced and its Last modified date option, so that corrected files overwrite the earlier versions in place
D: Switch to SNAPSHOT with Exclude files already synced and no date option, so that each run commits only the newly arrived files as a fresh view
K: A
G: ## Files are keyed by path
File-based syncs track files by **path name**. In the incremental APPEND mode, `Exclude files already synced` ingests files whose path has not been ingested before.
## The contradictory setting
The docs list `Exclude files already synced` with the `Last modified date` or `File size` option as **contradictory** for APPEND: those options try to re-ingest an existing path when its date or size changes. An APPEND transaction cannot modify existing files, and committing an APPEND that overwrote a file fails. That is the failure on every run since the first correction.
## The options for changed files
- UPDATE mode with the date option ingests new and changed files, but its output is not append-only, so downstream pipelines cannot run incrementally.
- Keeping APPEND and giving every correction a new path keeps the dataset append-only; downstream logic then picks the newest version.
- SNAPSHOT with exclude is the trailing-window mode: only the latest run's files stay in the view.
W: APPEND without the date option plus versioned names: corrections arrive as new paths, so no existing file is overwritten and the dataset stays append-only for the incremental transforms.
X: B=Add a file limit: smaller runs still try to re-ingest corrected paths into an APPEND transaction, so commits keep failing.
C=Switch to UPDATE: the sync would succeed, but its output stops being append-only and the downstream transforms could no longer run incrementally.
D=Trailing-window SNAPSHOT: each run replaces the view with only the newest files, which breaks incrementality downstream and drops earlier prices from the view.
T: In APPEND syncs, never combine Exclude files already synced with its date or size options; publish changed files under new paths instead.

G: ## Virtual table prerequisites
Virtual tables require a **Foundry worker source with direct egress policies**. The documented limitations include:
- connections using **agent proxy** policies are not supported;
- connections using an **agent worker** are not supported;
- self-service private link egress policies are generally not supported, but private links set up by a Palantir representative are;

A direct connection policy reaches systems directly accessible from Foundry; for a cloud-hosted enrollment, that means the public internet. A workspace with no public endpoint is not reachable that way.

@ PLTR-DE D2 T2.2 expert troubleshooting
S: To speed up an hourly join, an engineer added join-optimized projections on the set `{order_id, line_no}` to two append-only datasets, sizing each to its data: 512 buckets on a 3-billion-row order lines dataset and 64 buckets on a 200-million-row returns table. After both projections finished building, Spark details for the join job still show a large shuffle write and a sort on both sides. The join condition is exactly `order_id` and `line_no`, the transform code must not change, and both datasets keep receiving only APPEND transactions. Storage is not a concern. Which change should remove the shuffle on both sides?
A: Rebuild the returns projection with 512 buckets on the same column set, so that both join projections share one bucket count
B: Rebuild both projections as filter-optimized on the ordered list order_id then line_no, so that the join reads pre-sorted files
C: Rebuild the returns projection on order_id alone with 64 buckets, so that it matches the leading join column of the other side
D: Drop the returns projection and keep the 512-bucket order lines projection, so only the larger side is laid out for the join
K: A
G: ## How join projections remove shuffles
Large joins in Foundry typically sort-merge: each side is partitioned on the join key, sorted and merged, which normally means shuffling and sorting both datasets.
A join-optimized projection is defined by an **unordered set of columns and a bucket count**, and it optimizes joins on exactly that set and bucket count.
- One side with a matching projection: that side is not shuffled or sorted, but the other side still is.
- **Both sides with matching projections using the same number of buckets**: neither side is shuffled or sorted.
## Diagnosing the evidence
Both projections cover the exact join columns, so the column set is right. What differs is the bucket count, 512 versus 64, which is what prevents the bucketed layouts from lining up.
W: Same bucket count: with matching column sets and 512 buckets on both, the projections line up and neither side needs a shuffle or sort.
X: B=Filter-optimized projections: filter projections speed up comparisons with constants on a column prefix; they do not lay out data for joins.
C=Projection on order_id only: a join projection only optimizes joins on its exact column set, so a one-column projection cannot serve this two-column join.
D=One-sided projection: with a projection on one side only, that side skips the shuffle but the other side is still shuffled and sorted.
T: Join projections remove shuffles on both sides only when the column sets and bucket counts match.

@ PLTR-DE D2 T2.4 expert troubleshooting
S: A nightly PySpark job that joins 1.5 billion payment rows to a merchant table now takes nine hours. Spark details show a total runtime across all tasks of about 10 hours against a job duration of 9 hours, and one stage has a task concurrency close to 1. In that stage a single task processed 90 million rows, spilled about 200 GB to disk and peaked at 5 GB of executor memory, while the other tasks processed between 20,000 and 800,000 rows each with no spill. The merchant table is too large to broadcast, and last week's merchant onboarding added one very large marketplace merchant. Which diagnosis is best supported by this evidence?
A: The join key is heavily skewed, so one merchant's rows land in a single task and the stage cannot spread its work across executors
B: The job has too few executors, so the stage runs most tasks one after another and needs a larger executor count to reach concurrency
C: The driver is collecting the joined result into a single process, so the final write stage runs on the driver rather than on executors
D: The executors have too little memory, so every task spills to disk and a profile with more executor memory would restore parallelism
K: A
G: ## Reading Spark details
- **Parallelism ratio** = total runtime across all tasks divided by job duration. A ratio close to 1 means poor parallelism: here 10 / 9.
- **Task concurrency** per stage = total task runtime in the stage divided by stage duration. A value near 1 means almost all the work in the stage happens in one long task.
- **Stage details** show per-task rows, spill and peak memory.
## The skew signature
The docs describe exactly this pattern: one task processing tens of millions of rows while others process thousands, with **high disk spillage and high executor peak memory on that task only**. That is data skew: one key value holds a large share of rows, and all rows of a key are processed by one task in a shuffle join.
Here the onboarding of one very large merchant explains where the hot key came from.
W: Skewed join key: one task with 90 million rows, huge spill and peak memory, while the rest are small and spill-free, is the documented skew signature.
X: B=Too few executors: with too few executors many tasks would queue, but here the other tasks are tiny and finish; one task dominates the stage.
C=Driver collect: a collect moves work to the driver, while the evidence shows one executor task in a shuffle stage carrying the rows.
D=Too little memory: only the skewed task spills; more memory per executor would not split one key's rows across tasks.
T: One task with far more rows, spill and peak memory than its peers means skew, not a lack of executors or memory.

@ PLTR-DE D3 T3.2 expert troubleshooting
S: An incremental PySpark transform merges new customer records into its own previous output. It reads the output with `out.dataframe('previous', schema)`, unions the added input rows, deduplicates per customer and writes in replace mode. The `schema` is a StructType in which `customer_id` is declared with `nullable=False`, because that column can never be null in practice, and the field order matches the output exactly. The first incremental build after deployment fails with `SchemaMismatchError`, although the initial non-incremental run succeeded and no column types changed. The transform must stay incremental and keep working if it ever has to fall back to a snapshot. What should the engineer change?
A: Declare every field in the previous-mode schema nullable, including customer_id, since Foundry saves all output columns as nullable
B: Move customer_id to the last position in the previous-mode schema, because previous reads expect key columns at the end of the schema
C: Remove the schema argument from the previous read, because a schema is only needed when the transform runs non-incrementally anyway
D: Set require_incremental=True on the decorator, because the schema comparison only happens when a run may fall back to a snapshot
K: A
G: ## The schema argument of a previous read
Reading an incremental output in `previous` mode takes a schema:
- In a **non-incremental** run, the schema is used to generate an empty DataFrame, and it is required.
- In an **incremental** run, the schema is compared with the actual schema of the last output, and an exception is raised if column types, **nullability** or column order do not match.
## Why the first incremental build failed
Foundry saves all columns as nullable, whatever schema the transform used. A previous-mode schema with a non-nullable field therefore never matches the stored output, and the docs say the build will fail with a `SchemaMismatchError`. The initial run passed because it was non-incremental and only used the schema to build an empty DataFrame.
## Keeping order stable
To keep the column order aligned, write the output with `df.select(schema.fieldNames())`.
W: All fields nullable: the stored output is always nullable, so a schema that declares every field nullable matches it in incremental runs and still serves snapshot fallbacks.
X: B=Reorder fields: column order must match the output, and moving customer_id would create a new mismatch rather than fix the nullability one.
C=Drop the schema: without it, a non-incremental fallback cannot build the empty previous DataFrame, so the transform breaks on the next snapshot.
D=require_incremental: it makes fallbacks fail instead of snapshot; the schema comparison happens in incremental runs and would still fail.
T: Schemas for previous-mode reads must declare every field nullable, because Foundry stores all columns as nullable.

@ PLTR-DE D3 T3.3 expert troubleshooting
S: A multi-output incremental transform with v2 semantics writes `valid_orders` and `rejected_orders` from one append-only input every hour. To avoid empty transactions, an engineer added code that calls `abort()` on `rejected_orders` whenever a batch has no rejects, while `valid_orders` is written normally. Since then, every build after such a batch runs as a snapshot, the logs report the failed incremental check `Provenance records for the previous build are inconsistent`, and compute costs have tripled. The team's real goal is to skip downstream work only when an hourly batch brings no new rows at all; an empty `rejected_orders` write in a batch that has valid rows is acceptable. What should the transform do?
A: Call ctx.abort_job() only when the added input is empty, and otherwise write both outputs even if rejected_orders receives no rows
B: Keep calling abort() on rejected_orders when it has no rows, and also call abort() on valid_orders in the same build to keep them aligned
C: Keep calling abort() on rejected_orders when it has no rows, and set require_incremental=True so the next build cannot fall back to a snapshot
D: Call ctx.abort_job() whenever rejected_orders has no rows, so that both outputs are aborted together and stay consistent for the next build
K: A
G: ## Aborting in incremental transforms
- `ctx.abort_job()` aborts the whole job: every output's transaction is aborted, the job still completes successfully, and incremental transforms ignore aborted transactions, so the next build can run incrementally.
- `abort()` on an individual output is possible in PySpark but **not recommended** for incremental transforms. If only a subset of outputs is aborted, their job specs point at an older input range than the committed outputs, so the next build runs as a snapshot with `Provenance records for the previous build are inconsistent`; with `require_incremental=True` it fails instead.
- With `v2_semantics`, `abort_job()` is the only way to abort outputs while keeping later builds incremental.
## Aborting discards input
Aborted builds count as successful and advance the input transaction pointers, so aborting a job whose input had rows discards those rows. Abort only when there is nothing to process.
W: abort_job on empty input only: aborting the whole job keeps provenance consistent, and doing it only for empty batches never discards valid orders.
X: B=Abort both outputs separately: individual aborts are still the pattern that breaks incrementality, and aborting valid_orders in a batch with valid rows throws those rows away.
C=require_incremental: it turns the forced snapshot into a failed build; the inconsistent provenance remains.
D=abort_job when no rejects: the whole job is aborted while valid_orders had rows, and the advanced input pointer means those valid orders are lost.
T: In incremental transforms abort the whole job with ctx.abort_job(), and only when there is no input to process.

After deployment, objects show stale duplicate states and deleted accounts remain visible. G: ## Keys on streams
- **Partition keys** group records with the same key so their order is kept.
- **Primary keys (CDC mode)** are deduplication columns, optionally with a deletion column. CDC-aware consumers, such as an object type hydrated from the stream, read only the most recent record per key and delete records whose deletion flag is true. Setting a primary key also sets the same columns as partition keys.

Pipeline Builder propagates keys through transforms that do not invalidate key columns. But **keys never propagate through user-defined functions**, because the platform cannot infer the intended strategy. The docs say to apply the `Key by` transform after the UDF.
## Configuring Key by
With CDC mode on, supply the key columns and, if available, the deletion column. The docs highly recommend leaving the optional ordering columns blank for streaming use cases.

X: B=Key by before the UDF: keys set before the UDF are dropped again by the UDF, so the output stream still has no primary key.
C=CDC mode off: this restores only partitioning; without a primary key the object type cannot deduplicate or apply deletions.
D=Ordering column without deletion column: deduplication returns, but without the deletion column deleted accounts would still remain.
T: Keys never propagate through UDFs; re-key the output with Key by in CDC mode after the UDF.

@ PLTR-DE D4 T4.3 expert troubleshooting
S: Every Monday at about 09:00 for the past three weeks, a schedule's duration check has fired because its Python transforms take three times longer than usual. Job Comparison shows no code changes and no library changes, input row counts and file sizes are flat, and the schedule's versions history shows no edits. Build progress details show the extra time is compute rather than queuing. Filtering the Builds application shows other teams' Python jobs slowing at the same hour, while Java jobs run normally. The schedule's outputs feed a weekly board report, so the on-call engineer must route the issue correctly today. What is the BEST next step?

B: Classify it as a change in the pipeline and pin every Python library in meta.yml to the versions that were in use three weeks ago

G: ## Three categories of problems
The pipeline debugging guide classifies problems as:
- **Change**: anything changed within the pipeline you monitor, such as code, libraries, schedules or data size. The most common category.
- **Upstream issue**: delayed, missing or incorrect data from sources or Projects upstream.
- **Platform issue**: Foundry services not working as expected.
## Identifying a platform issue
Once user changes are ruled out, the guide suggests checking for the same symptoms elsewhere: is it reproducible, does it follow a pattern (it even gives "fails on Monday at 9am" as an example), and what is the scope, for example only Python jobs. The Builds application can filter job history across the platform.
## Action
For a platform issue, contact your Palantir representative with as much specific information as possible, including what was observed and what changed.
W: Platform issue with evidence: no code, library, data or schedule changes, compute-bound slowdown, a weekly pattern and other teams' Python jobs affected all point outside the pipeline.
