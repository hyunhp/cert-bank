@ PLTR-DE D2 T2.2 applied use-case
S: A dataset of product events has a JSON column containing nested attributes that differ by product category. The business wants a few common attributes as typed columns and the rest preserved. Which transformation approach is right?
A: Casting the whole JSON column to a string and asking consumers to parse whatever they need from it in their own tools
B: Parsing the JSON, extracting the agreed common attributes into validated typed columns, keeping the original JSON for the long tail
C: Exploding every nested key into its own column, producing thousands of mostly empty columns so that nothing is ever missed
D: Dropping the JSON column entirely from the curated dataset because nested data cannot be handled properly in a tabular pipeline
K: B
G: ## Semi-structured data in transforms
The exam guide lists expressions and enrichment among transformations and asks for clear contracts. Promote what is agreed; preserve the rest.
## Design
- Parse JSON; extract `color`, `size`, `weight` into typed columns with validation (numeric weight, allowed sizes).
- Keep `attributes_json` for the long tail; consumers can parse specific keys on demand.
- Document the promoted attributes as the contract; add new promotions through the normal change process.
Example: three typed columns serve 90% of queries; a new attribute is promoted later without re-ingesting anything.
W: Promote agreed attributes to typed columns and keep the raw JSON for the rest: usable structure with nothing lost.
X: A=String for consumers: every consumer re-implements parsing; the common attributes are never typed or validated.
C=Explode everything: a sparse, unmanageable schema that changes whenever a category adds a key.
D=Drop it: the attributes consumers ask for live inside the JSON; dropping the column discards them, and nested data is routinely parsed in pipelines.
T: Promote common nested attributes to typed columns and preserve the raw semi-structured column for the long tail.
V: Pipeline Builder, Code Repositories

@ PLTR-DE D2 T2.3 applied troubleshooting
S: A Spark join between a 1 TB fact table and a 10 MB dimension table is slow because Spark shuffles the large table. What is the standard fix?
A: Collect the fact table to the driver and loop over it in Python, since loops are easier to reason about than shuffles
B: Use a broadcast join so the small dimension is sent to every executor and the fact table joins in place without a shuffle
C: Split the fact table into one dataset per day and join each one separately in a loop of 365 builds
D: Convert the dimension table to a JSON string and parse it inside a UDF for every row of the fact table
K: B
G: ## Broadcast joins
The exam guide asks you to use Spark details to diagnose shuffles and to apply efficient join strategies. When one side is small, broadcasting it avoids shuffling the large side.
## Practice
- Broadcast the 10 MB dimension; each executor joins its partitions locally.
- Confirm in Spark details: no shuffle on the fact table; stage time drops.
- Keep an eye on the dimension's size over time; broadcasting a large table causes memory problems.
Example: the join stage drops from 40 minutes to 4 with identical output.
W: Broadcast the small side: the standard, verifiable fix for a large-to-small join that shuffles the large table.
X: A=Collect to the driver: 1 TB cannot be collected; this fails immediately.
C=365 separate builds: enormous overhead and still shuffles each piece.
D=JSON in a UDF: parsing a 10 MB string inside a per-row function repeats the work a billion times; catastrophically slow.
T: Broadcast small dimension tables to avoid shuffling large fact tables, and confirm in Spark details.
V: Spark Details, Code Repositories

@ PLTR-DE D2 T2.4 applied use-case
S: A transform's logic depends on a dozen business thresholds that change quarterly. The thresholds are currently hard-coded. What should the data engineer do?
A: Keep them hard-coded and redeploy the transform every quarter when the business sends the new values
B: Move them into a governed reference dataset the business maintains through review, read at build time, with an expectation
C: Ask the business to stop changing the thresholds every quarter so that the transform's code can stay stable and tested
D: Put the thresholds in a comment at the top of the transform so they are easy to find when editing
K: B
G: ## Configuration as data
The exam guide asks for maintainable transformations and governed change. Business parameters that change on a schedule belong in data, not code.
## Design
- Reference dataset `thresholds` with name, value, effective date, owner.
- Transform joins or looks up values at build time; expectation checks completeness and plausible ranges.
- Changes go through the business's reviewed process; lineage shows which thresholds each build used.
Example: the quarterly update lands on the 1st; the next build applies it with no code change and the values are auditable.
W: Governed reference data read at build time with completeness expectations: changes flow through data, auditable and without redeployment.
X: A=Hard-coded redeploys: a code release for a data change every quarter, with the risk of typos.
C=Stop changing: the thresholds change because the business changes; asking it to freeze them to suit the code is backwards.
D=Comment: still hard-coded; the comment just documents the problem.
T: Store changing business parameters in governed reference data, not in transform code.
V: Code Repositories, expectations

@ PLTR-DE D2 T2.2 applied use-case
S: A pipeline must compute each customer's rolling 7-day spend ending on each day for the last year. Which transformation construct is appropriate?
A: A self-join of the transactions table to itself for every pair of days within a week, which produces the rolling sums after filtering
B: A window function partitioned by customer, ordered by date, with a range frame over the preceding 7 days summing spend
C: A group-by on customer and week, which gives weekly totals that can be used as the rolling value
D: A Python loop over customers on the driver that slides a window through each customer's transactions one at a time
K: B
G: ## Range-based window frames
The exam guide lists aggregations and expressions; rolling computations are window functions with range frames.
## Pattern
- Partition by customer; order by date.
- Frame: range between 7 days preceding and the current row (on a daily calendar; fill missing days if needed).
- Sum of spend within the frame per row.
Example: every (customer, day) row carries `spend_7d`, computed distributedly in one pass.
W: Partitioned, date-ordered window with a 7-day range frame: the precise construct for rolling sums at scale.
X: A=Self-join on day pairs: a large cross-product that recomputes the same sums repeatedly; slow and error-prone.
C=Weekly group-by: calendar weeks are not rolling 7-day windows ending on each day.
D=Driver loop: collects all transactions to one node; fails at scale.
T: Compute rolling aggregates with window functions using range frames over ordered partitions.
V: Code Repositories, Pipeline Builder

@ PLTR-DE D2 T2.1 applied comparison
S: A pipeline step must run a trained machine-learning model's inference library on each row, with the library's own Python dependencies. Which authoring choice fits?
A: Pipeline Builder, since model inference is a transformation like any other and can be configured visually
B: A code transform with the library and its dependencies declared, using batched inference, with tests on representative inputs
C: A Contour analysis that applies the model interactively whenever an analyst needs scores for a particular set of rows
D: A notebook that an analyst runs weekly on their own machine and whose scored output is uploaded to the platform as a dataset
K: B
G: ## Custom libraries mean code
The exam guide ties Code Repositories to custom libraries and processing needs. Model inference with its own dependencies is a code transform.
## Design
- Dependencies declared and versioned in the repository.
- Inference in batches (or a vectorized UDF) to avoid per-row overhead.
- Tests on representative rows; expectations on score ranges.
Example: the transform scores 20 million rows nightly with the library pinned to a tested version.
W: Code transform with declared dependencies and batched inference: the only authoring choice that can import the library and run at scale.
X: A=Pipeline Builder: cannot import an arbitrary Python library with dependencies.
C=Contour: an interactive analysis tool for exploration; it is not a scheduled production step with lineage and expectations.
D=Weekly notebook: depends on a person running it, has no version control or lineage, and the library environment is unmanaged.
T: Custom-library inference belongs in Code Repositories with declared dependencies and batched execution.
V: Code Repositories

@ PLTR-DE D2 T2.4 applied troubleshooting
S: A transform that aggregates sales by region started producing a new "null" region bucket containing 8% of revenue. Nothing in the transform changed. What is the right investigation and fix?
A: Rename the null bucket to "Other" in the output so that the dashboard looks tidy and the revenue is still counted somewhere
B: Trace it upstream: the region join fails for new store codes or the source stopped populating region; fix it and add an expectation
C: Filter out the null-region rows in the transform so that the dashboard shows only the valid regions and no confusing bucket
D: Ask the dashboard owners to ignore the null bucket for now and revisit the issue when the team has more time next quarter
K: B
G: ## Nulls from broken joins
The exam guide asks you to trace changes upstream with lineage and never to mask incorrect output. A sudden null bucket is a mapping failure, not a category.
## Investigation
- Which rows have null region? Likely new store codes absent from the dimension, or a source change.
- Fix: update the region dimension (reference data) or the source; left-join behaviour reviewed.
- Guard: an expectation that `region` is non-null for sales rows, so the next gap fails the build visibly.
Example: 12 new stores opened last week without dimension entries; adding them removes the null bucket and the expectation prevents a repeat.
W: Upstream diagnosis of the failed mapping with a fix and a non-null expectation: the cause is removed and guarded.
X: A=Rename to Other: hides a mapping failure as a category; 8% of revenue is misattributed.
C=Filter out: 8% of revenue silently disappears from every regional total; the dashboard becomes wrong in a less visible way.
D=Ignore: every new store adds to the null bucket; the misattribution persists and grows while decisions are made on the numbers.
T: A new null bucket is a broken mapping; fix it upstream and add a non-null expectation.
V: Data Lineage, expectations

@ PLTR-DE D2 T2.3 applied tradeoff
S: A team runs twenty small transforms, each on Spark, each processing under 50 MB and taking three minutes, mostly startup. What should they consider?
A: Nothing, since three minutes per transform is acceptable to consumers and Spark is the platform's standard engine for every transform
B: Moving these small transforms to a lightweight engine (or consolidating related ones), validated by comparing outputs on a branch
C: Increasing executor count on each transform so the three minutes become shorter
D: Combining all twenty into a single giant transform regardless of what they do
K: B
G: ## Startup cost at scale
The exam guide asks for engine choice by startup cost and feature compatibility and for right-sized compute. Twenty startup-dominated Spark jobs waste an hour of compute a day.
## Options
- Lightweight engine for each small transform: seconds instead of minutes.
- Consolidation where transforms share inputs and purpose.
- Branch validation of outputs; cost comparison.
Example: total daily runtime drops from 60 minutes to 4 with identical outputs.
W: Lightweight engines (and sensible consolidation) for startup-dominated small jobs: the overhead disappears and the outputs are unchanged.
X: A=Acceptable: an hour a day of pure startup is avoidable waste.
C=More executors: startup overhead does not shrink with executors.
D=One giant transform: couples unrelated logic; failures and reviews become harder.
T: Run small, startup-dominated transforms on lightweight engines; consolidate only where logic is related.
V: Code Repositories

@ PLTR-DE D2 T2.4 advanced use-case
S: A team wants every transform in a critical pipeline to be covered by automated checks before merge. Which combination gives meaningful coverage?
A: A single automated test that checks the whole pipeline compiles and runs without errors on a small sample before merge
B: Unit tests on transformation functions, a branch build compared against production, expectations on outputs, and required review
C: A monthly manual review of all transforms in the pipeline by the team lead, who reads through the code for anything suspicious
D: A rule that every transform must have a header comment explaining its purpose, enforced by a check that the comment is present
K: B
G: ## Meaningful pre-merge coverage
The exam guide asks for tested, validated, reviewed transformations with expectations. Coverage means several complementary checks.
## Combination
- Unit tests: logic correctness on representative and edge inputs.
- Branch build: real data; compare counts, keys, values with production.
- Expectations: contract enforcement at build time.
- Review: a second pair of eyes; enforced by branch protection.
Example: a refactor passes unit tests but the branch comparison shows 0.5% of rows changed; the review finds a null-handling difference before merge.
W: Unit tests, branch comparison, expectations and review together: logic, real-data behaviour, contract and judgement are all checked.
X: A=Compiles: a transform that compiles can still drop rows, duplicate keys or compute the wrong number; it proves nothing about correctness.
C=Monthly manual: a month of merges goes unreviewed, and reading code does not catch what a branch comparison on real data catches.
D=Comments: a comment describes intent; it does not check that the transform does what the comment says.
T: Protect critical pipelines with unit tests, branch comparisons, expectations and reviews before merge.
V: Code Repositories, expectations, branches
