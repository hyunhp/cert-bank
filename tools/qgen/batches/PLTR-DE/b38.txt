# PLTR-DE batch 38: Domain 5 round 5 (Data Quality and Health Monitoring), 8 questions

@ PLTR-DE D5 T5.1 applied use-case
S: A dataset backs an object type whose primary key must be unique, but the team also wants to know when the share of rows with a missing optional "phone" field rises above 20%, which may indicate a source change but is not an error. Which configuration fits both?
A: Build-blocking expectations for both conditions, since any deviation from expected data should stop the pipeline until someone reviews it
B: A build-blocking uniqueness expectation on the key, and a health check on the phone null rate with an alert at 20%
C: Health checks for both conditions, since alerts are less disruptive than build failures
D: Neither, since monitoring optional fields is not worth the effort
K: B
G: ## Block invariants, monitor signals
The exam guide's self-check asks whether a requirement needs a blocking expectation, a health alert, or both. Key uniqueness is an invariant; a null-rate threshold on an optional field is a signal.
## Configuration
- Expectation: `customer_id` unique; failure blocks publication.
- Health check: null rate of `phone` with an alert above 20%; the build proceeds.
- Alert routed to the owner with the trend.
Example: a source change drops phone capture; the alert fires; the pipeline keeps publishing valid data while the source team investigates.
W: Blocking for the invariant and alerting for the signal: each requirement gets the control proportionate to its consequence.
X: A=Block both: a legitimate change in an optional field would halt a correct dataset.
C=Alert both: duplicate keys would be published to the object type before anyone reacts.
D=Nothing: a 20% jump in missing phones is worth knowing about.
T: Enforce invariants with expectations and watch informational thresholds with health checks.
V: expectations, Data Health

@ PLTR-DE D5 T5.3 applied troubleshooting
S: A health check on a dataset's size has fired because the dataset grew 3× overnight. The build succeeded. What should the engineer check first?
A: Whether the project's storage quota is about to run out, since dataset growth alerts are primarily there to warn about capacity
B: Whether a join multiplied rows, an upstream delivered a duplicate load, or an incremental transform re-appended, via keys and inputs
C: Whether the health check's growth threshold is simply too tight for this dataset and should be tripled so it stops firing
D: Whether any consumers have complained about the dataset, since a size alert that nobody has noticed downstream is probably not real
K: B
G: ## Interpreting a size spike
The exam guide warns that successful runs can produce duplicated data and asks you to investigate with inputs and keys. A 3× jump is a classic duplication signature.
## Checks
- Key uniqueness in the output: duplicates confirm a join explosion or double load.
- Input transactions: a repeated upstream delivery.
- Transform mode: a fallback or re-append.
- Fix the cause; add a uniqueness expectation.
Example: the customer dimension gained duplicate rows; every order joined three times; the dimension is fixed and an expectation added.
W: Duplication diagnosis via keys and inputs: the fastest explanation of a 3× size jump and the one that prevents recurrence.
X: A=Capacity: the alert is about data correctness; quota is a secondary concern.
C=Loosen threshold: the check caught a real tripling of the data; raising the threshold hides the duplication it found.
D=Wait for complaints: the alert exists to act before consumers notice.
T: A sudden size spike usually means duplication; check keys and input transactions before anything else.

@ PLTR-DE D5 T5.2 applied use-case
S: A new source sometimes delivers a file with an entirely wrong schema (a different report accidentally dropped into the folder). The team wants the pipeline to keep publishing good data while isolating the bad file. What should be configured?
A: A build-blocking expectation on the parsed dataset so that the entire build fails and nothing publishes whenever a wrong file appears
B: Per-file schema validation at parse time that routes non-conforming files to quarantine with an alert while conforming files continue
C: Manual inspection of every incoming file by an engineer before it is moved into the folder the pipeline reads from
D: Deleting any file that fails to parse immediately, so that the pipeline never stalls and the folder stays clean
K: B
G: ## Quarantine for bad inputs
The exam guide asks for layered ingestion with quarantine rather than blanket failure. Isolating a bad file preserves the flow of good data and the evidence.
## Design
- Per-file schema validation at parse time.
- Non-conforming files to a quarantine dataset with metadata (name, time, reason) and an alert.
- Curated output built from conforming files; expectations there still block genuine data errors.
Example: the stray report lands in quarantine with an alert; the day's valid files publish on time.
W: Per-file validation with quarantine and alerting: bad files are isolated and visible, good data keeps flowing.
X: A=Block the whole build: one stray report stops the day's valid files from publishing until someone intervenes.
C=Manual inspection: a person checking every file every day does not scale and delays all data on the day they are away.
D=Delete failures: destroys evidence and may discard a misnamed but needed file.
T: Quarantine non-conforming input files with alerts instead of failing the whole build.

@ PLTR-DE D5 T5.3 applied use-case
S: Which health-check design detects that a daily dataset was built with yesterday's input again (the source delivered nothing new but the build ran)?
A: A build-status check on the dataset, since the build would fail or be skipped automatically when the input is unchanged
B: A content-freshness check on the maximum event date, plus a freshness check on the upstream source dataset
C: A schema check on the dataset, since reprocessing yesterday's input a second time changes the schema of the output
D: A row-count check with a tight threshold, since reprocessed data always produces a noticeably different row count
K: B
G: ## Reprocessed inputs look fresh but are not
The exam guide stresses that successful builds can publish stale data. The build's own timestamp is new; the content is not.
## Design
- Content freshness: max(event_date) within the expected window.
- Upstream freshness: the source dataset's latest transaction age.
- Optionally, a build condition that skips when the input has no new transaction.
Example: the source stalls; the nightly build reruns on the same input; the content check fires at 06:00 instead of a consumer noticing a week later.
W: Content and upstream freshness checks: they measure the age of the data, not of the build.
X: A=Build status: the build ran and succeeded on the old input; a status check sees a healthy green build.
C=Schema: reprocessing the same input produces the same columns and types; a schema check sees nothing.
D=Row count: the same input yields exactly the same number of rows, so a count check cannot distinguish the rerun.
T: Detect reprocessed-but-stale builds with content-freshness and upstream-freshness checks.
V: Data Health

@ PLTR-DE D5 T5.1 applied comparison
S: A data engineer is explaining to a new colleague how expectations and health checks should be used on a critical curated dataset. Which statement about their relationship is accurate?
A: Expectations and health checks are mutually exclusive mechanisms, so a dataset should be configured with one or the other but never both
B: They complement each other: expectations block invalid transactions at build time, health checks detect drift over time; use both
C: Health checks are the newer replacement for expectations and should be used instead of them on any dataset created from now on
D: Expectations only apply to streaming datasets while health checks only apply to batch datasets, so the dataset's mode decides
K: B
G: ## Complementary layers
The exam guide describes expectations as proactive (build-time, blocking) and health checks as reactive (over time, alerting), and asks for both where appropriate.
- Expectations: the gate; invalid data never publishes.
- Health checks: the monitor; staleness, size, schema, content anomalies.
- Critical datasets: both, because some problems are build-time invariants and others are temporal.
Example: an expectation blocks null keys at 02:00; a freshness check alerts at 06:00 that no build happened at all.
W: Prevention at build time plus detection over time on the same dataset: expectations stop invalid data from publishing while health checks catch what only shows up afterwards, such as staleness or drift; critical datasets need both.
X: A=Mutually exclusive: nothing prevents both; a dataset routinely has blocking expectations and monitoring checks together.
C=Replacement: a health check cannot stop a bad transaction from publishing; it alerts afterwards, so it cannot replace an expectation.
D=Streaming versus batch: expectations and health checks are used on batch and streaming datasets alike; the mode does not decide.
T: Use expectations to gate builds and health checks to monitor published data; critical datasets need both.
V: expectations, Data Health

@ PLTR-DE D5 T5.3 applied troubleshooting
S: Consumers report that a dataset's `amount` column has been in cents since last week instead of dollars. No check fired. Which checks would have caught it, and what should be added?
A: A build-status check on the dataset, since a unit change in a numeric column causes the build to fail with a type error
B: Statistical content checks on the column (median band, ratio to a related column) and reconciliation against a source total
C: A null-rate check on the amount column, since a unit change in the source usually produces null values during conversion
D: A schema check on the dataset, since the column's type effectively changed from a dollar amount to a cent amount
K: B
G: ## Catching semantic shifts
The exam guide asks for content checks because successful builds can publish wrong values. A unit change keeps schema, counts and nulls identical; only the values move.
## Add
- Distribution check: median amount within a historical band.
- Relationship check: `amount / quantity` within a plausible range.
- Reconciliation: dataset total versus the source's reported total.
Example: the median jumps from 42 to 4,200; the distribution alert fires on the first build after the change.
W: Statistical and reconciliation checks: the only monitors that see a 100× value shift with everything else unchanged.
X: A=Build status: the build succeeded with the new values; nothing about a unit change fails a build.
C=Null rate: every row still has a value, just 100 times larger; the null rate is unchanged.
D=Schema: the type stayed numeric; cents and dollars share a type.
T: Monitor value distributions and reconcile totals to catch unit and semantic errors.

@ PLTR-DE D5 T5.2 applied tradeoff
S: An expectation requires that `country` be one of 40 codes. The business adds a 41st country, and the build fails on the first rows from it. Which process should be in place so this does not block the business?
A: Removing the allowed-values expectation entirely, since the list of countries changes over time and the check keeps causing failures
B: An expansion process where the business updates the governed country reference the expectation reads before go-live, so the new code passes
C: Having the on-call engineer edit the expectation's hard-coded list whenever the build fails on a new country code
D: Changing the expectation to a non-blocking warning so that any country value passes and the build never fails on it
K: B
G: ## Expectations tied to governed references
The exam guide asks for expectations that encode the real contract and for governed change. A hard-coded list fails on legitimate growth; a reference-backed list grows through process.
## Process
- Reference dataset `countries_active` maintained by the business through a reviewed Action.
- Expectation: values must be in the reference.
- Go-live checklist: update the reference before the first rows arrive.
Example: the 41st country is added on Monday; Tuesday's first rows pass; "UK" mistyped as "UJ" still fails.
W: A reference-backed expectation with a business-owned update process: growth passes by design, errors stay blocked.
X: A=Remove: typos and unknown codes now reach the curated dataset and the object type with nothing to stop them.
C=Engineer edits on failure: reactive, unreviewed and delays the business each time.
D=Warning only: the check no longer blocks anything, so a mistyped code publishes just as freely as a legitimate new one.
T: Back evolving allowed-value expectations with governed reference data that the business updates before changes land.
V: expectations, Ontology

@ PLTR-DE D5 T5.3 advanced use-case
S: A team wants a weekly data-quality report for a domain's datasets that is useful to both engineers and business owners. What should it contain?
A: Only a count of alerts fired during the week, since that is the simplest metric to compute and the easiest for everyone to read
B: Per dataset: expectation history, check status and incidents, freshness against SLA, content metrics, owned open issues, layered by audience
C: A raw dump of every check result from the week in a single table, so that nothing is left out of the report
D: A screenshot of the monitoring dashboard taken on Friday afternoon and attached to an email to the domain owners
K: B
G: ## Quality reporting
The exam guide treats monitoring, incident investigation and communication as operational responsibilities. A report serves two audiences with two levels of detail.
## Contents
- Business view: SLA met? Open issues and impact; trend.
- Engineer view: which checks failed, when, why; incident links; reconciliation deltas.
- Ownership: each issue has a name and a due date.
Example: the owner sees "freshness SLA met 29/30 days; one source outage, resolved"; the engineer sees the failing check and the fix.
W: Layered content with trends, incidents and owners: both audiences get what they need and issues get closed.
X: A=Alert count: twelve alerts could be one stale source or twelve different problems; the count says nothing about what or why.
C=Raw dump: thousands of rows of check results are unreadable for business owners and unhelpful for engineers without context.
D=Screenshot: a point-in-time picture with no trend, no incident detail and no owner for any open issue.
T: Report data quality per dataset with SLA status, incidents, metrics and owned open issues, layered by audience.
