# PLTR-DE batch 36: Domain 3 round 5 (Pipeline Processing Modes), 8 questions

@ PLTR-DE D3 T3.1 applied use-case
S: An insurance claims dataset receives new claims continuously, but the downstream fraud model only needs scores by the start of each business day. Claims occasionally receive corrections for up to 30 days. Which processing design fits?
A: A streaming pipeline that scores every claim within seconds of arrival and never revisits it, since streaming is the most capable mode available
B: A nightly incremental run over new and corrected claims (by key and update time), with a periodic recompute over the 30-day window
C: A full batch over all claims ever received every night, so that corrections are always reflected regardless of when they arrive
D: A lightweight single-node transform every hour over the complete claims history, since the logic is simple
K: B
G: ## Daily freshness with late corrections
The exam guide asks you to choose modes by freshness, source behaviour and cost and to handle corrections safely. Daily need plus a bounded correction window suggests incremental with reconciliation.
## Design
- Nightly incremental: new claims plus claims updated since the last run, keyed for idempotent merge.
- Weekly recompute over the trailing 30 days to catch anything missed.
- Freshness check against the morning deadline.
Example: 15,000 new and 800 corrected claims are scored each night in minutes; the weekly window recompute confirms consistency.
W: Keyed incremental with a bounded periodic recompute: daily freshness, corrections handled, and cost proportional to change.
X: A=Streaming, never revisit: corrections are ignored, and seconds-level freshness has no value for a morning deadline.
C=Full batch nightly: recomputes years of claims to handle corrections confined to 30 days.
D=Hourly lightweight over all history: the history does not fit one node, and hourly adds nothing for a daily deadline.
T: Use keyed incremental processing with a bounded reconciliation window when corrections arrive late and freshness is daily.
V: incremental transforms, schedules

@ PLTR-DE D3 T3.2 applied troubleshooting
S: A downstream dataset shows twice as many rows as its input after a run. Transaction history on the input shows an APPEND of the same file name that already existed in a previous APPEND. What happened?
A: The input dataset silently converted its APPEND into an UPDATE, which is the platform's default behaviour when a file name repeats
B: The upstream appended a file whose name already existed; APPEND adds files, so both copies are in the view; fix names, correct it
C: The downstream transform has a bug that duplicates every row, unrelated to the input
D: Row duplication is normal after any APPEND and consumers should always deduplicate
K: B
G: ## APPEND does not replace
The exam guide asks you to understand transaction semantics. An APPEND adds files to the view regardless of name; a re-appended file is a second copy.
## Fix
- Upstream: unique file names per run (timestamp or run id), or an UPDATE transaction when a file is meant to replace one of the same name.
- Repair: a corrective transaction removing the duplicate file, or a rebuild from a clean snapshot.
- Guard: an expectation on key uniqueness downstream.
Example: the sync wrote `data.parquet` twice; switching to `data_<runid>.parquet` and removing the duplicate fixes the counts.
W: A re-appended file duplicated the data because APPEND adds rather than replaces: the transaction history shows it, and the upstream write pattern must change.
X: A=Silent conversion: APPEND never converts to UPDATE; it added the file as the history shows.
C=Downstream bug: the doubling is already present in the input view; the transform is faithful.
D=Normal: duplication is a defect in how the input was written, not a property of APPEND.
T: APPEND adds files even with repeated names; writers must use unique names or explicit replace semantics.
V: transactions

@ PLTR-DE D3 T3.4 applied use-case
S: A streaming pipeline computes per-customer session metrics with 30-minute inactivity windows. Events can arrive up to 10 minutes late. How should watermarks and windows be configured?
A: No watermark, so that every late event is always included no matter when it arrives, at the cost of never finalizing any window
B: Event-time session windows with a 30-minute gap and about 10 minutes of allowed lateness, with events beyond that routed to a late-data path
C: Processing-time windows, so that lateness does not matter because every event is assigned to a window by its arrival time at the pipeline
D: A 10-second watermark, so that windows finalize quickly and late events are simply dropped
K: B
G: ## Event time, watermarks and lateness
The exam guide names state, backlogs and replay among streaming concerns; watermark configuration is how late data is bounded.
## Configuration
- Event-time sessionization: gap 30 minutes.
- Allowed lateness: 10 minutes, matching observed delays; windows close after it.
- Beyond the bound: a side output for late events, reconciled in batch.
Example: an event 8 minutes late joins its session; one 25 minutes late goes to the late path and is reconciled nightly.
W: Event-time session windows with lateness matching observed delay and a late-data path: correct sessions, bounded state, nothing silently lost.
X: A=No watermark: windows never close, state grows forever, no results are final.
C=Processing time: a session is defined by when the customer acted, not when the event reached the pipeline; late arrivals would split or merge sessions wrongly.
D=10-second watermark: most late events (up to 10 minutes) are dropped.
T: Configure event-time windows with allowed lateness equal to observed delay and route anything later to a reconciliation path.
V: streaming

@ PLTR-DE D3 T3.3 applied comparison
S: Which of the following would NOT cause an incremental transform to fall back to a full recompute?
A: An UPDATE transaction on one of its inputs that replaced a previously processed file
B: An APPEND transaction on an input that added two new files since the last run
C: A SNAPSHOT transaction on an input that rewrote the whole dataset
D: A DELETE transaction on an input that removed a file the transform had already processed
K: B
G: ## Fallback triggers
The exam guide asks why incremental transforms fall back. The increment is safe only when inputs changed additively.
- APPEND: new files only; the transform processes them incrementally.
- SNAPSHOT, UPDATE, DELETE: previously processed data changed or vanished; the transform cannot know what to adjust and recomputes.
Example: two new daily files arrive as APPEND; the transform processes exactly those two; a monthly SNAPSHOT upstream triggers one full run.
W: An APPEND of new files: the one transaction type incremental processing handles without fallback.
X: A=UPDATE replacing a processed file: the rows the transform already counted have changed, so its earlier results are invalid; fallback.
C=SNAPSHOT: the whole input was replaced, so nothing previously processed can be trusted; the transform recomputes fully.
D=DELETE of a processed file: contributions from that file must be removed from the output, which the increment cannot express; fallback.
T: Only APPEND inputs keep incremental transforms incremental; the other transaction types trigger fallback.
V: incremental transforms, transactions

@ PLTR-DE D3 T3.1 applied tradeoff
S: A batch pipeline is asked to deliver results "as fresh as possible" by a stakeholder who cannot say what freshness they need. How should the data engineer proceed?
A: Build a streaming pipeline immediately, since "as fresh as possible" means real time
B: Elicit the real requirement (what decision, how often), choose the cheapest mode that meets it, document and monitor it
C: Keep the current nightly batch exactly as it is and tell the stakeholder that the pipeline's freshness cannot be changed
D: Run the full batch every minute to be safe, so that whatever freshness the stakeholder has in mind is certainly met
K: B
G: ## Freshness is a requirement to elicit
The exam guide asks you to choose processing modes by latency requirement and cost, and warns against streaming without a continuous need. "As fresh as possible" is not a requirement until quantified.
## Approach
- Ask: what decision, how often, what happens if the data is an hour old?
- Choose: hourly incremental if hourly decisions; daily if daily.
- Document and monitor the agreed freshness; revisit when needs change.
Example: the stakeholder reviews the dashboard each morning; daily incremental at 06:00 meets the need at a fraction of streaming's cost.
W: Elicit, choose the cheapest adequate mode, document and monitor: the requirement is met without over-engineering.
X: A=Streaming by default: expensive and complex for an unquantified need.
C=Refuse: freshness can change; the need just has to be understood.
D=Every minute: a full batch every minute burns compute continuously, and the stakeholder may only look once a day.
T: Quantify freshness requirements before choosing a processing mode; pick the simplest mode that meets them.
V: schedules, incremental transforms

@ PLTR-DE D3 T3.4 applied troubleshooting
S: A streaming pipeline's lag grows steadily every afternoon and recovers overnight. What does this pattern indicate and what should be done?
A: The source system is broken in the afternoons and should be restarted automatically every day at 14:00 to clear the problem
B: Throughput is below the afternoon input rate: scale processing or reduce per-event cost, and set a lag alert threshold
C: Lag growth during busy hours is normal for any streaming pipeline and requires no action as long as it recovers by the next morning
D: The pipeline should be switched to batch mode during the afternoon peak and back to streaming when the input rate drops again
K: B
G: ## Reading lag patterns
The exam guide lists backlogs among streaming concerns. Lag that grows under load and drains afterwards means throughput is lower than the peak input rate.
## Response
- Measure the afternoon input rate and the pipeline's throughput.
- Scale: more parallelism or resources; or reduce per-event work (cheaper enrichment, batching).
- Alerting on lag so a day with a higher peak does not become an unbounded backlog.
Example: doubling parallelism keeps lag under a minute at peak; the alert threshold is set at five minutes.
W: Capacity below peak rate, fixed by scaling or cheaper processing with lag alerts: the pattern is explained and the risk bounded.
X: A=Restart the source: the source is producing normally; the pipeline is slow to consume.
C=Normal: a peak slightly higher than usual would leave a backlog that never drains; it is a capacity warning.
D=Batch in the afternoon: mode switching mid-day adds complexity; the pipeline needs capacity.
T: Lag that grows under load and recovers later means insufficient throughput; scale and alert on lag.
V: streaming

@ PLTR-DE D3 T3.2 applied use-case
S: A dataset must be rebuilt from scratch monthly to apply a corrected definition, but consumers must never see an empty or partial dataset during the rebuild. Which transaction approach achieves this?
A: Deleting all of the existing files first and then appending the recomputed files over several hours while consumers wait for the rebuild
B: Writing the full recomputed output as one SNAPSHOT transaction, which atomically replaces the previous view only when complete
C: Appending the recomputed files on top of the old ones and asking every consumer to filter by build date to get the corrected version
D: Rebuilding into the same dataset file by file with UPDATE transactions as each recomputed file completes over the course of the run
K: B
G: ## Atomic replacement with SNAPSHOT
The exam guide asks you to understand SNAPSHOT semantics. A SNAPSHOT replaces the view atomically at commit; readers never observe an intermediate state.
## Practice
- Compute the full output; commit as one SNAPSHOT.
- Downstream incremental transforms will fall back once; schedule accordingly.
- Expectations run before commit so a bad recompute never replaces good data.
Example: the monthly recompute takes three hours; consumers read the old version throughout and the new one the instant it commits.
W: One SNAPSHOT commit: the replacement is atomic, so consumers never see an empty or partial dataset.
X: A=Delete then append: consumers see an empty dataset immediately and a partial one for hours while files trickle in.
C=Append over old: the dataset doubles in size and every consumer must know to filter; the old definition remains visible.
D=File-by-file UPDATEs: a mixed old-and-new view during the rebuild.
T: Replace a dataset atomically with a single SNAPSHOT transaction so consumers never see partial state.
V: transactions

@ PLTR-DE D3 T3.3 advanced tradeoff
S: A team wants an incremental transform to be safe against duplicate processing if a run is retried after a partial failure. Which design principle must the transform follow?
A: Processing must be made as fast as possible so that failures and therefore retries become rare enough not to matter
B: Idempotency: processing an increment once or several times must yield the same output (keyed merges or deduplication)
C: Retries must be disabled entirely in the schedule so that duplicate processing of any increment becomes impossible
D: Each run must write its output to a brand-new dataset so that any duplicates from a retry are isolated in a separate place
K: B
G: ## Idempotent incremental processing
The exam guide asks for state handled safely across retries and replay. A retried increment may be processed twice; the transform must make that harmless.
## Principle
- Keyed outputs: merge by primary key so a second pass overwrites rather than appends.
- Deterministic computation: same input, same output.
- Dedupe on a run or event id where appends are unavoidable.
Example: a run fails after writing half its output; the retry reprocesses the increment and the keyed merge leaves exactly one row per key.
W: Idempotency through keyed merges or deterministic deduplication: retries become safe by construction.
X: A=Speed: fast runs still fail sometimes; speed does not make retries safe.
C=Disable retries: transient failures then require manual intervention and leave gaps.
D=New dataset per run: fragments the output and pushes deduplication onto consumers.
T: Make incremental transforms idempotent so retries after partial failures cannot duplicate or double-count.
V: incremental transforms
