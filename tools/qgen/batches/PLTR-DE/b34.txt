# PLTR-DE batch 34: Domain 1 round 5 (Data Connectivity and Ingestion), 8 questions

@ PLTR-DE D1 T1.1 applied use-case
S: A team must ingest data from a mainframe system that exposes only fixed-width text files delivered once a day by file transfer. Which ingestion design is appropriate?
A: A JDBC connection to the mainframe, since every enterprise system can be queried with SQL once the right driver is installed on the agent host
B: A file sync that lands the files unchanged, then a transform that parses the fixed column positions from a documented layout, with expectations
C: A streaming sync that reads each line of the daily file as it is written and emits it as a message to a streaming dataset for immediate processing
D: A manual process in which an operator opens each file in a spreadsheet, splits the columns by hand and uploads the result through the browser each morning
K: B
G: ## Landing raw, parsing deterministically
The exam guide asks you to select connectors by protocol and to layer ingestion (land raw, then validate and transform). Fixed-width files are files; the layout is a parsing concern for a transform.
## Design
- File sync: daily file picked up by name pattern; append transaction.
- Transform: parse by column positions from a documented layout; cast types; expectations on counts and keys.
- Raw files retained as the audit trail; the layout lives in version control.
Example: the 02:00 file lands raw; the parsing build produces a typed dataset by 02:20 and fails loudly if a column shifts.
W: File sync plus a layout-driven parsing transform with expectations: the right connector and clean separation of landing from parsing.
X: A=JDBC: the mainframe exposes files, not a database endpoint; a driver cannot query something that is not served.
C=Streaming per line: a daily file is a batch artefact; treating lines as a stream adds complexity for no freshness gain.
D=Manual spreadsheet: unrepeatable and error-prone, and the fixed-width layout is exactly what a transform parses reliably.
T: Land fixed-format files with a file sync and parse them in a versioned transform with expectations.
V: Data Connection, Code Repositories

@ PLTR-DE D1 T1.2 applied troubleshooting
S: An append sync keyed on an auto-incrementing id has started missing rows since the source migrated to a new database whose ids are no longer monotonic (a sharded id scheme). What should change?
A: Keep the id-based append sync and accept the missing rows, since sharded ids are a source problem that the sync cannot be expected to work around
B: Switch the change signal to something monotonic (a commit timestamp or sequence number) or use CDC, and reconcile the rows missed
C: Run the sync twice per hour instead of once, since more frequent runs give each row more chances to be picked up before the watermark moves past it
D: Sort the source table by id before each run so that the ids become monotonic again from the sync's point of view
K: B
G: ## The watermark assumption again
The exam guide asks you to understand incremental sync patterns and their failure modes. An append sync needs a value that only increases; sharded ids interleave and break that.
## Fix
- New signal: commit timestamp (UTC) or a change sequence number from the new database.
- Or CDC, which does not rely on a watermark column at all.
- Reconcile: a one-off snapshot comparison to recover rows missed since the migration.
Example: switching to the database's change sequence number restores completeness; a reconciliation snapshot backfills 12,000 missed rows.
W: A monotonic signal or CDC plus reconciliation: the sync's assumption is restored and the gap repaired.
X: A=Accept losses: missing rows corrupt every downstream consumer; a sync must adapt to the source it reads.
C=More frequent runs: the watermark logic is broken, not slow; interleaved ids are missed at any frequency.
D=Sort the source: sorting does not change the values; ids below the watermark are still skipped.
T: When a source change breaks watermark monotonicity, change the signal (or use CDC) and reconcile the gap.

@ PLTR-DE D1 T1.3 applied use-case
S: A regulator requires that a monthly extract delivered to them contains exactly the agreed fields and is traceable to the source data used. How should the export be designed?
A: Have an analyst assemble the extract by hand each month from several datasets and email it to the regulator with a note about where the data came from
B: A transform producing the extract with the agreed schema enforced by an expectation, lineage to the sources, and a governed, logged export
C: A direct export of the raw source datasets so the regulator has everything and can derive the fields they need themselves
D: A shared screen-sharing session in which the regulator views the dashboards and takes screenshots of the figures they need
K: B
G: ## Regulatory extracts as governed outputs
The exam guide covers exports and egress policies, lineage and expectations. A regulatory deliverable needs an enforced contract, provenance and a governed, logged transfer.
## Design
- Extract dataset: agreed columns and types, schema expectation blocks any deviation.
- Lineage: the extract traces to its curated sources and their transactions.
- Export: approved destination under policy; each run logged.
Example: the March extract's export log shows the dataset version, time and destination; lineage shows the source transactions it was built from.
W: Contracted extract dataset with lineage and a governed export: exact fields, traceability and an audit trail.
X: A=Hand-assembled email: unrepeatable, unverifiable and outside egress governance.
C=Raw datasets: far more than agreed, potentially sensitive, and the regulator should not derive fields themselves.
D=Screenshots: images of dashboards are not a data extract, contain no agreed fields, and cannot be traced to source transactions.
T: Produce regulatory extracts as contracted datasets with lineage and export them under policy.
V: exports, expectations, Data Lineage

@ PLTR-DE D1 T1.4 applied troubleshooting
S: A sync has started taking four times longer than usual, though the record count is unchanged. Execution history shows the run spending most of its time waiting on the source. What should be investigated?
A: The agent's installation, which should be reinstalled because slowdowns usually indicate a corrupted agent binary on the host
B: Source-side conditions: a dropped index on the queried column, increased source load, or a changed query plan
C: The dataset's expectations, since slow syncs are usually caused by expectation checks running on every row during ingestion
D: The downstream transforms, since a slow consumer can hold up the sync that feeds it
K: B
G: ## Waiting on the source
The exam guide asks you to diagnose ingestion with execution history and source evidence. Time spent waiting on the source with unchanged volume points at the source's query performance.
## Investigation
- The sync's query: does it filter on an indexed column? Did the source drop or rebuild an index?
- Source load: backups, other jobs, locking.
- Query plan changes after a source upgrade.
Example: the source team rebuilt a table and lost the index on `modified_at`; restoring it returns the sync to its normal duration.
W: Source-side query performance (index, load, plan): the evidence says the sync is waiting on the source, so that is where to look.
X: A=Reinstall the agent: an agent waiting on a slow source is behaving correctly; reinstalling destroys evidence and fixes nothing.
C=Expectations: expectations run in transforms, not inside a sync's extraction.
D=Downstream consumers: a sync does not wait for its consumers; dependencies flow the other way.
T: A sync that waits on its source has a source-side performance issue; check indexes, load and query plans.
V: Data Connection

@ PLTR-DE D1 T1.1 applied comparison
S: A data engineer must choose between a direct connection and an agent for a cloud-hosted database that the platform can reach over a private network link. Which is the better default and why?
A: An agent, because agents are always more secure than direct connections regardless of the network topology between platform and source
B: A direct connection, because the source is reachable and a direct connection avoids an agent host; agents are for unreachable sources
C: An agent, because cloud databases cannot be connected to directly from the platform
D: Both at once, so that if one fails the other still delivers the data
K: B
G: ## Agent only when needed
The exam guide asks you to select connection architectures by network reachability. Agents exist for sources the platform cannot reach; when it can, a direct connection is simpler to operate.
## Reasoning
- Reachable over a private link: direct connection with credentials in the source configuration.
- No agent host to patch, monitor or size.
- Agents remain the answer for closed networks.
Example: the cloud database is synced directly nightly; the on-premises ERP next to it still needs an agent.
W: Direct connection for a reachable source: simpler operations, with agents reserved for unreachable sources.
X: A=Agents always more secure: security comes from credentials, encryption and network design, not from the agent itself; agents add an extra host to secure.
C=Cannot connect directly: cloud databases reachable over a private link can be connected directly.
D=Both: double the configuration and two syncs writing the same dataset; redundancy is not achieved this way.
T: Use direct connections where the platform can reach the source; use agents where it cannot.
V: Data Connection, agents

@ PLTR-DE D1 T1.2 applied use-case
S: A source table has a reliable `updated_at` column but rows are also physically deleted, and the consumers need deletions reflected within a day. CDC is not available. Which pattern fits?
A: An update sync on `updated_at` only, since it captures every insert and update and those are the changes consumers care about most
B: An update sync on `updated_at` for inserts and updates, plus a daily key-only snapshot (or a soft-delete flag) to detect deletions
C: A streaming sync, since deletions can only be captured by continuous replication of the source
D: A full snapshot every hour, since deletions make incremental patterns impossible
K: B
G: ## Deletions without CDC
The exam guide asks you to combine patterns to match source behaviour. Timestamps see inserts and updates; deletions leave no row to timestamp.
## Design
- Update sync: cheap capture of inserts and updates.
- Daily key-only snapshot: a lightweight list of surviving keys; keys missing from it are deletions, applied downstream.
- Alternative: a soft-delete flag in the source.
Example: the key snapshot is 2% of the table's size; a transform marks 300 rows deleted each night.
W: Update sync plus a key-only snapshot for deletions: all change types captured within a day at low cost.
X: A=Update sync alone: a deleted row leaves nothing with a new timestamp, so it persists downstream forever as if it still existed.
C=Streaming: a batch table with no change log is not a stream; streaming is not required for daily deletion detection.
D=Hourly full snapshot: correct but far more expensive than needed for a daily requirement.
T: Capture deletions without CDC by combining an update sync with a key-only snapshot or a soft-delete flag.
V: Data Connection

@ PLTR-DE D1 T1.3 applied troubleshooting
S: A virtual table over an external system suddenly returns an authentication error for all users, though nothing in Foundry was changed. What is the likely cause and the right fix?
A: The virtual table definition is corrupted and must be deleted and recreated from scratch by an administrator
B: The connection's credentials or token expired or were rotated externally; update them in the governed source configuration and test
C: Every user's personal permissions on the external system were revoked at once, and each user must request access again individually
D: The external system no longer supports virtual tables, so the data must be copied into Foundry instead
K: B
G: ## Credentials behind virtual tables
Virtual tables query the source through a connection whose credentials are managed in the source configuration. The exam guide lists credentials among ingestion diagnostics.
## Fix
- Check the connection's credential status: expiry, rotation by the external team.
- Update the secret in the connection (never in code or on individual users).
- Test the connection; confirm queries resume.
- Add a credential-expiry reminder or health check.
Example: the external team rotated the service account password; updating the connection restores every user's queries at once.
W: Expired or rotated connection credentials, fixed in the source configuration: an all-users failure with no Foundry change points straight at the shared credential.
X: A=Corrupted definition: definitions do not corrupt spontaneously; an authentication error names the real cause.
C=All users revoked: the connection uses a shared service credential, not per-user permissions on the external system.
D=Unsupported: an authentication error says nothing about support; the source still works once the credential is fixed.
T: An all-users authentication failure on a virtual table means the shared connection credential expired; rotate it in the source configuration.
V: virtual tables, Data Connection

@ PLTR-DE D1 T1.4 advanced tradeoff
S: A team must design ingestion for a source that is known to be unreliable: late files, occasional duplicates, and sporadic schema drift. What design absorbs these without manual intervention?
A: A strict sync that fails the moment anything deviates, so that the on-call engineer can review every problem by hand
B: Layered: tolerant landing, parsing that absorbs additive drift and fails on breaking drift, key dedupe, realistic checks, quarantine
C: Asking the source team to fix their system's lateness, duplicates and drift before any ingestion is built on top of it
D: Skipping validation entirely so that the pipeline never fails, and letting consumers deal with duplicates and schema changes themselves
K: B
G: ## Designing for an unreliable source
The exam guide asks for layered ingestion, expectations, health checks and quarantine rather than brittle failure or blind acceptance.
## Layers
- Landing: accept late files; append.
- Parsing: tolerate additive columns; fail on removed or retyped columns with a clear error.
- Dedupe: by key, idempotent.
- Monitoring: freshness windows that match real lateness; size checks.
- Quarantine: unparseable files set aside with an alert, not blocking the good ones.
Example: a late, duplicated file lands, is deduplicated, and a file with a renamed column is quarantined with an alert while the rest publish.
W: Tolerant landing, strict-where-it-matters parsing, dedupe, realistic monitoring and quarantine: the known failure modes are handled automatically.
X: A=Fail on everything: the on-call engineer handles the same late file every week by hand.
C=Wait for the source: the data is needed now; the pipeline must cope.
D=No validation: duplicates and broken schemas reach consumers silently.
T: Design ingestion for unreliable sources with tolerant landing, targeted strictness, deduplication and quarantine.
V: Data Connection, expectations, Data Health
