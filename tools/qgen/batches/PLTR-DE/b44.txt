# PLTR-DE batch 44: Domain 3 round 6 (Pipeline Processing Modes), 8 questions

@ PLTR-DE D3 T3.1 applied use-case
S: A logistics company needs vehicle positions on an operations map within seconds, and also a daily report of distance driven per vehicle. Positions arrive as a continuous stream of GPS events. Which processing design fits both needs?
A: A nightly batch over all GPS events that updates both the operations map and the daily distance report once per day at midnight
B: A streaming pipeline for latest positions on the map, plus a daily batch over the persisted events for distances
C: A streaming pipeline that also recomputes every vehicle's lifetime distance from scratch on every incoming GPS event
D: A lightweight single-node transform run every minute over the complete history of GPS events for every vehicle in the fleet
K: B
G: ## Different freshness, different modes
The exam guide asks you to choose modes by latency and to combine them when requirements differ. Live positions need seconds; daily distance needs completeness once a day.
## Design
- Streaming: latest position per vehicle with bounded state, feeding the map.
- Persist the events; nightly batch computes distance per vehicle per day.
- Reconciliation between the two where needed.
Example: the map shows a truck moving in near real time; the 06:00 report lists yesterday's 412 km for that truck.
W: Streaming for the live view and batch for the daily aggregate: each output is produced in the mode its freshness requires, at reasonable cost.
X: A=Nightly batch for both: the operations map would show positions up to a day old, which defeats its purpose entirely.
C=Lifetime recompute per event: recomputing history for every GPS ping multiplies cost enormously for a report needed once a day.
D=Minute-by-minute full history on one node: the history grows beyond one node and still does not give second-level positions.
T: Combine streaming and batch when one source feeds outputs with different freshness needs.
V: streaming, schedules

@ PLTR-DE D3 T3.2 applied use-case
S: A dataset is corrected by replacing a few hundred rows in one file each week. Downstream consumers use incremental transforms. Which transaction approach minimizes downstream impact?
A: Rewrite the entire dataset as a SNAPSHOT every week, since that guarantees the correction is applied everywhere at once
B: Design the corrections as appended correction records keyed to the original rows, merged downstream by key
C: Delete the dataset and recreate it each week so that consumers always see a clean copy with every correction applied
D: Edit the file in place outside the platform and hope the transaction history does not notice the change
K: B
G: ## Corrections without breaking incrementality
The exam guide asks you to understand how transaction types affect incremental consumers. A weekly SNAPSHOT or UPDATE forces every incremental consumer to fall back; append-only corrections do not.
## Design
- Correction records with the original key, new values and an effective timestamp, appended.
- Downstream keyed merge applies the latest correction per key.
- Expectations: every correction references an existing key.
Example: 300 corrections arrive as an APPEND; consumers process 300 rows instead of recomputing the whole dataset.
W: Appended, keyed corrections merged downstream: corrections flow incrementally and no consumer is forced into a full recompute.
X: A=Weekly SNAPSHOT: correct but forces every incremental consumer into a full recompute each week for a few hundred changed rows.
C=Delete and recreate: destroys history and lineage and also triggers full recomputes downstream.
D=Edit outside the platform: bypasses transactions entirely, leaving consumers with silently inconsistent data and no audit trail.
T: Express small recurring corrections as appended keyed records to keep downstream processing incremental.
V: transactions, incremental transforms

@ PLTR-DE D3 T3.4 applied troubleshooting
S: A streaming aggregation's state size grows without bound over weeks, eventually slowing the job. The aggregation counts events per user per day. What is the likely cause and fix?
A: The stream simply has more users every week, so unbounded state growth is expected and only more memory can address it
B: State for past days is never expired; add a time-to-live or watermark-based cleanup so finished days are emitted and dropped
C: The checkpoint location is too small, so it should be moved to a larger storage location without any other change
D: The streaming engine leaks memory, so the job should be restarted every night to clear the state manually
K: B
G: ## Bounded state
The exam guide lists state handling among streaming concerns. Per-day aggregates are finite: once a day is past the lateness bound, its state is no longer needed.
## Fix
- Watermark on event time with a lateness bound.
- Emit and drop state for windows past the watermark (or TTL on keys).
- Monitor state size as a metric.
Example: state stabilizes at two days' worth of users instead of growing with every day since launch.
W: Expire finished windows via watermarks or TTL: state size becomes bounded by the active window rather than by the job's age.
X: A=More users: user growth adds a little state; unbounded growth over weeks comes from never discarding old days.
C=Larger checkpoint storage: the checkpoint mirrors the state; enlarging storage accepts the growth instead of fixing it.
D=Nightly restarts: either loses state or reloads the same oversized state; the cause remains untouched.
T: Bound streaming state with watermarks or TTLs so completed windows are emitted and released.
V: streaming

@ PLTR-DE D3 T3.3 applied use-case
S: An incremental transform aggregates daily sales. A new requirement adds a column computed from a reference table that changes monthly. How should the transform handle a monthly reference change?
A: Ignore the reference change, since incremental transforms only process new sales rows and cannot use reference tables at all
B: Treat a reference change as a controlled recompute: detect the new version and rerun the affected range
C: Copy the reference values into every sales row at the source so that the reference table is never needed by the pipeline
D: Hard-code the current reference values into the transform and update the code manually each month after the change
K: B
G: ## When a dimension changes under an incremental fact
The exam guide asks for incremental processing with correct handling of changed inputs. New sales are incremental; a changed reference invalidates earlier outputs.
## Design
- Track the reference version used for each output partition.
- On a new version: recompute the affected range (or fully, if all history depends on it), as a planned backfill.
- Normal days remain incremental.
Example: on the 1st of each month a backfill reapplies the new rates to last month's partition; other days process only new sales.
W: Version-aware recompute on reference change with incremental processing otherwise: outputs stay consistent with the reference without permanent full recomputes.
X: A=Ignore changes: earlier outputs silently keep old reference values and become inconsistent with new ones.
C=Copy into the source: pushes pipeline concerns onto the source team and duplicates reference data in every row.
D=Hard-code monthly: a code release for a data change every month, with the same stale-output problem.
T: When reference data changes, recompute the affected range deliberately while keeping routine runs incremental.
V: incremental transforms

@ PLTR-DE D3 T3.1 applied comparison
S: Which situation most clearly calls for streaming rather than frequent incremental batch?
A: A finance report reviewed every morning that needs data complete up to midnight of the previous day
B: Fraud detection on card transactions where a decision must be made within a second, before the purchase completes
C: A weekly marketing dashboard refreshed on Monday mornings for the leadership meeting at nine o'clock
D: A monthly regulatory filing that is prepared from a complete and audited set of the previous month's ledger entries
K: B
G: ## The streaming criterion
The exam guide places streaming where continuous, low-latency processing is required. Sub-second decisions during a transaction cannot wait for any batch.
- Morning finance report, weekly dashboard, monthly filing: batch cadences.
- Card fraud before authorization completes: streaming.
Example: the scoring service reads the transaction stream and returns a decision in 300 ms.
W: Sub-second fraud decisions during a transaction: the one case among the four where only continuous processing can meet the requirement, because any batch interval would let the purchase complete before a decision exists.
X: A=Morning finance report: a nightly batch after midnight meets a morning review with no need for streaming.
C=Weekly dashboard: a scheduled weekly or daily batch is fully sufficient for a Monday meeting.
D=Monthly filing: requires complete, audited data, which favours a deliberate batch after month end.
T: Reserve streaming for decisions that must happen within seconds of an event.
V: streaming

@ PLTR-DE D3 T3.2 applied troubleshooting
S: Consumers of a dataset report that rows they saw yesterday have disappeared today, although the source still has them. Transaction history shows yesterday's APPEND followed by today's SNAPSHOT containing only today's rows. What happened?
A: The platform automatically expired yesterday's rows because they were older than the dataset's default retention period
B: Today's run wrote a SNAPSHOT of only new rows, replacing the view; the writer should append, or snapshot the full intended contents
C: The consumers are reading a cached version of the dataset and should refresh their browsers to see the missing rows again
D: The source deleted the rows overnight and the dataset correctly reflects that deletion, even though the source still shows them
K: B
G: ## SNAPSHOT replaces the view
The exam guide asks you to read transaction semantics. A SNAPSHOT containing only today's rows makes yesterday's rows invisible, which matches the symptom exactly.
## Fix
- Writer: use APPEND for incremental additions, or include the full intended contents in a SNAPSHOT.
- Repair: restore from the previous transaction plus today's rows.
- Expectation: row count not lower than the previous build without an explained reason.
Example: a configuration change switched the write mode to snapshot; reverting it and rebuilding restores the rows.
W: A partial SNAPSHOT replaced the dataset's view: the transaction history shows it, and the write mode or contents must be corrected.
X: A=Automatic expiry: datasets do not silently expire rows; the history shows a replacing transaction, not retention.
C=Browser cache: the dataset's current view really lacks the rows; refreshing changes nothing.
D=Source deletion: the source still has the rows, so the dataset is wrong rather than faithful.
T: A SNAPSHOT with partial contents hides everything else; use APPEND for additions or snapshot the full contents.
V: transactions

@ PLTR-DE D3 T3.4 applied use-case
S: A streaming pipeline must join each event with the latest customer tier, which changes a few times a year and lives in a dataset. What is a sound approach?
A: Query the customer dataset with a full scan for every single event as it arrives, so the tier is always perfectly current
B: Load the customer tiers as a lookup (broadcast state or reference table) refreshed when the dataset updates, joining in-stream
C: Copy the customer tier into every event at the source system so that the streaming pipeline never needs to join at all
D: Skip the tier in the stream and add it in a nightly batch, since streaming pipelines cannot use reference data
K: B
G: ## Stream–reference joins
The exam guide lists state and reference data among streaming design concerns. Slowly changing reference data is held as lookup state and refreshed on change.
## Design
- Load tiers into lookup state at start.
- Refresh when the customer dataset gets a new transaction.
- Join each event against the in-memory lookup.
Example: a tier change in the dataset is reflected in the stream within minutes, without a scan per event.
W: Refreshed lookup state joined in-stream: each event gets the customer's current tier from memory at very low cost, and tier changes in the dataset flow into the stream within minutes of landing.
X: A=Scan per event: thousands of full scans per second for data that changes a few times a year.
C=Copy into source events: couples the source to downstream needs and duplicates reference data everywhere.
D=Defer to nightly batch: loses the stream's freshness for a value that is readily available as reference state.
T: Join streams with slowly changing reference data through refreshed lookup state.
V: streaming

@ PLTR-DE D3 T3.3 advanced use-case
S: A team must backfill three years of history for a new incremental transform without blocking the daily runs that consumers depend on. What approach is appropriate?
A: Run the three-year backfill as one enormous build on the production branch during business hours and pause daily runs until it ends
B: Backfill in validated monthly chunks on a branch or separate schedule, then merge so daily runs continue
C: Skip the backfill and tell consumers the history starts today
D: Copy three years of output from another team's similar dataset and hope it matches the new logic
K: B
G: ## Backfills alongside live processing
The exam guide asks for bounded reruns and safe operations. A huge single backfill risks the daily window; chunked backfills with validation do not.
## Approach
- Chunks: one month per build, oldest first.
- Validation per chunk (counts, totals versus source).
- Merge into the production state; daily incremental runs continue unaffected.
Example: 36 monthly chunks run overnight over a week; daily builds keep their 06:00 deadline throughout.
W: Chunked, validated backfill that converges with live incremental state: history is filled without disrupting consumers.
X: A=One huge build pausing daily runs: consumers lose their daily data, and a failure late in the build wastes everything.
C=Skip the backfill: consumers need the history; the requirement is unmet.
D=Copy another team's output: different logic means different numbers, with no validation.
T: Backfill history in validated chunks without interrupting live incremental runs.
V: incremental transforms, branches
