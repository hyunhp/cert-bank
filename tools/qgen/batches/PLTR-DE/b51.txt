@ PLTR-DE D1 T1.1 applied tradeoff
S: A retailer's order system runs on one production database server that also serves its web shop. Analysts need the orders table in Foundry every night. The database team has a read replica available. Which source setup is best?
A: Read from the production primary at lunchtime, when the table is smallest and the replica is considered unnecessary overhead
B: Read from the read replica on a nightly schedule outside shop peak hours, with a limited number of parallel reads
C: Read from the primary with the maximum parallelism available, so the sync finishes before the web shop opens
D: Read from the replica every minute with full snapshots, so analysts always see the very latest orders
K: B
G: ## Protect the source system
A sync is a real workload on the source. The exam guide asks you to choose connector settings that meet the business need without harming the system of record.
## What to weigh
- A read replica takes analytical reads away from the primary that serves customers.
- A schedule outside peak hours lowers contention further.
- Parallelism speeds a sync up but adds load, so it is a dial to limit, not maximise.
- Freshness should match the stated need (nightly), not the most extreme possible.
Example: a nightly sync at 02:00 from the replica finishes in 20 minutes and the web shop never notices.
W: Replica, off-peak schedule and modest parallelism: meets the nightly need and keeps the production primary safe from analytical load.
X: A=Primary at lunchtime: a small table does not make the load harmless, and lunch is often a busy shop period.
C=Primary with maximum parallelism: finishing early does not matter if the sync slows live orders while it runs.
D=Minute-by-minute full snapshots: freshness nobody asked for, and it multiplies load on the replica.
T: Ingest from a replica, off-peak and with limited parallelism, unless the business need requires more.

@ PLTR-DE D1 T1.1 applied comparison
S: A team can ingest from a relational source in two ways: write a custom SQL query at the source that joins five tables into one wide result, or sync the five tables as they are and join them in a transform. Which approach is usually preferable, and why?
A: The custom query, because joins always run faster inside the source database than in any transform engine
B: The custom query, because it hides the source schema from everyone and removes any need for documentation
C: Sync the tables as they are, so the joins live in versioned, reviewable transform logic
D: Sync the tables as they are, because a joined result can never be ingested incrementally at the source
K: C
G: ## Where to put the join
The guide asks you to keep ingestion simple and put business logic in the transform layer.
## Reasons to ingest raw tables
- The raw tables are reusable: another team can build a different join without a new sync.
- Join logic in transforms is reviewed, tested and shown in lineage.
- A schema change in one table is visible and fixable in one place.
- A custom query is opaque logic inside the connection and cannot be tested the same way.
Example: a second team needs customers joined to returns; with raw tables they reuse two existing datasets.
W: Raw tables synced as they are keep logic in versioned, reviewable transforms with lineage and let several teams reuse the same ingested data.
X: A=Joins faster at the source: a claim that is not always true, and speed is not the deciding concern against maintainability.
B=Hide the schema: hiding structure from people makes the pipeline harder to understand and own, not easier.
D=Joined tables cannot be incremental: a false statement, a joined query can be filtered by a key or timestamp too; it is just opaque.
T: Ingest raw tables and do business joins in transforms where they can be tested and traced.

@ PLTR-DE D1 T1.2 applied troubleshooting

- Overwritten content is not picked up, with no error to alert you.
- Fixes: partner writes date-stamped file names, or the sync uses snapshot mode so each run ingests everything.

W: Already-synced detection is keyed on path, so a daily overwrite of the same path is skipped silently and the data never changes.
X: B=Size limit: no such rule exists; APPEND concerns adding files rather than comparing sizes.
C=Missing timestamp column: the filter looks at file paths, not at contents of columns.
D=One-hour trailing window: a trailing window is a different mode and would not explain data frozen after day one.
T: Exclude-already-synced syncs track path names, so overwritten same-name files are never re-ingested.
