@ PLTR-DE D4 T4.2 applied troubleshooting
S: A transform's output row count dropped by 40% overnight with no code change, and the build succeeded. Which evidence sequence finds the cause fastest?
A: Rewriting the transform from scratch and comparing the new version's output with the old one to see whether the counts come back
B: Comparing input transactions since the last good build (counts, schema), then walking lineage to the first dataset whose count dropped
C: Increasing the transform's executor memory, since dropped rows are usually caused by memory pressure during the join stage
D: Asking consumers whether they noticed the difference, since their feedback indicates which rows disappeared
K: B
G: ## First bad stage for a count drop
The exam guide's playbook: compare inputs with the last known-good run and find the first bad stage with lineage. A 40% drop with unchanged code means an input shrank.
## Sequence
- Input transactions: which input lost rows or changed schema?
- Lineage: follow that input upstream to where the drop first appears.
- That stage's sync or transform: a failed partial sync, a filter on a changed value, a source outage.
Example: the orders sync delivered only 60% of the day's rows after a source timeout; the sync is rerun and the counts recover.
W: Input comparison then lineage to the first shrinking dataset: the fastest route to the stage that actually lost rows.
X: A=Rewrite: the code did not change; rewriting it cannot explain a change in the data.
C=More memory: a successful build did not fail on memory; memory does not silently drop 40% of rows.
D=Consumer feedback: slow and vague; the datasets themselves show exactly where the rows went.
T: A count drop with unchanged code is an input problem; compare inputs and walk lineage to the first stage that shrank.
V: Data Lineage, builds

@ PLTR-DE D4 T4.1 applied use-case
S: Three independent source syncs feed one curated dataset, and each source lands at a different, unpredictable time. The business wants the curated dataset refreshed whenever any one source updates, not only when all three have. How should the schedule be configured?
A: A single daily schedule at midnight that builds the curated dataset once, since partial refreshes are confusing for consumers
B: An event-based schedule triggered by an update to any of the three inputs, with a minimum interval to avoid rapid repeated builds
C: Three separate copies of the curated dataset, one per source, each rebuilt when its own source lands
D: A schedule every five minutes that force-builds the curated dataset regardless of input changes
K: B
G: ## Any-input triggers
The exam guide asks for event-based triggers configured to the real requirement without unnecessary builds. "Whenever any source updates" is an any-of condition.
## Configuration
- Trigger: any of the three inputs has a new transaction.
- Debounce: a minimum interval between builds so two sources landing a minute apart produce one build.
- Freshness checks per source so a silent source is still noticed.
Example: sources land at 01:10, 01:12 and 03:40; the dataset builds at 01:15 (both early sources) and again at 03:45.
W: Any-input event trigger with debouncing: refresh follows each source's arrival and redundant builds are avoided.
X: A=Midnight only: the dataset ignores updates for up to a day, which is not what the business asked for.
C=Three copies: consumers want one curated dataset, not three partial ones.
D=Five-minute force-builds: 288 builds a day, most on unchanged inputs.
T: For "refresh on any input update", use an any-of event trigger with a debounce interval.
V: schedules

@ PLTR-DE D4 T4.3 applied troubleshooting
S: A build fails with a message that the output dataset's schema is incompatible with the existing dataset (a column type changed). The change was intentional. What is the correct release step?
A: Deleting the output dataset and letting the build recreate it, losing history and breaking consumers
B: Releasing it deliberately: notify consumers via lineage, choose a compatible rollout (new column or schema snapshot), validate on a branch
C: Casting the column back to its old type in the transform so that the build passes, abandoning the intended change for now
D: Disabling schema checks on the dataset permanently so that any future type change goes through
K: B
G: ## Intentional breaking changes
The exam guide asks you to classify schema changes and release breaking ones with consumer coordination. The failure is the platform protecting consumers; the release needs a plan.
## Release
- Lineage: find consumers; notify.
- Rollout: a new column during a transition, or an explicit schema-changing snapshot at an agreed time.
- Branch: build and validate consumers against the new schema.
- Expectations updated; merge; monitor.
Example: `quantity` becomes an integer via a new `quantity_int` column for two weeks, then the old column is dropped.
W: A coordinated, branch-validated release of the type change: consumers keep working and the change lands.
X: A=Delete and recreate: destroys history and breaks consumers without warning.
C=Cast back: the type change was needed; reverting it to make the error go away leaves the real requirement unmet.
D=Disable checks: removes the protection that caught exactly this.
T: Treat an intentional schema change as a coordinated release, not as an error to silence.
V: Data Lineage, branches, expectations

@ PLTR-DE D4 T4.4 applied use-case
S: A pipeline's compute cost has grown 300% over a year while its data grew 20%. Which review approach finds the waste?
A: Switching every transform in the pipeline to the smallest executor configuration available and seeing which ones fail under the new limits
B: Reviewing build frequency against consumption, Spark details for partitioning, skew and full recomputes, and orphaned pipelines, fixing by impact
C: Deleting the oldest half of the datasets, since old datasets are the most likely to be wasteful
D: Asking the platform team to lower the price of compute
K: B
G: ## Cost reviews as engineering
The exam guide lists resource usage and cost among operational responsibilities and names Spark details and schedules as the evidence. Cost growth far above data growth means structural waste.
## Review
- Frequency: builds nobody consumes (hourly builds for daily dashboards).
- Efficiency: Spark details for partition counts, skew, spill, full recomputes where incremental would do.
- Orphans: pipelines with no consumers, duplicated logic.
- Fix by impact.
Example: two hourly pipelines with daily consumers and one over-partitioned transform account for 70% of the growth.
W: Frequency, efficiency and orphan review with impact-ordered fixes: the waste is found where it is, not guessed.
X: A=Shrink everything: a blunt experiment that breaks working pipelines without diagnosing waste.
C=Delete old datasets: age is not waste; some old datasets are the most important.
D=Lower prices: not within the team's control and does not remove waste.
T: Review cost by build frequency, Spark efficiency and orphaned pipelines, fixing the largest contributors first.
V: Spark Details, schedules

@ PLTR-DE D4 T4.3 applied use-case
S: A transform fails intermittently with an error indicating that an input file was not found, although the file exists when the engineer checks afterwards. What is the likely cause and remedy?
A: The platform randomly hides files from builds under load; the only remedy is to retry the build until the file happens to appear
B: The read overlaps an in-progress upstream write or compaction; trigger the transform on the upstream's commit instead of a timer
C: The transform's code references the file by an incorrect name on some days of the week because of a date-formatting bug in the path
D: The file is too large and sometimes fails to load within the read timeout, which the platform reports as a file-not-found error
K: B
G: ## Read-during-write races
The exam guide asks you to classify failures and to schedule on input updates rather than overlapping timers. A file that "does not exist" at build time but exists later points to a timing overlap with the upstream write.
## Remedy
- Trigger on the upstream dataset's committed transaction instead of a fixed time.
- If timers must stay, ensure the upstream completes well before.
- Investigate compaction or replacement jobs on the input.
Example: moving the transform from a 02:30 timer to an input-update trigger ends the intermittent failures.
W: A timing race with an in-progress upstream write, fixed by triggering on commit: the intermittency and the "exists later" symptom match exactly.
X: A=Random hiding: the platform does not hide files; the read overlapped a write.
C=Wrong name on some days: a name error would be consistent, not tied to timing.
D=Too large: a size problem would be a timeout, not a not-found error.
T: Intermittent "not found" inputs mean a read overlapping an upstream write; trigger on commit instead of a timer.
V: schedules, transactions

@ PLTR-DE D4 T4.1 applied tradeoff
S: A pipeline currently rebuilds a 500 GB curated dataset hourly to serve a dashboard that most users open between 08:00 and 18:00. Overnight builds are never looked at. What scheduling change is reasonable?
A: Keeping hourly builds around the clock exactly as now, since a consistent cadence matters more than the compute cost of overnight builds
B: Hourly builds during business hours and a single overnight build (or event-triggered builds), serving users when they actually look
C: Stopping all scheduled builds and asking users to request a manual refresh from the team whenever they need current data
D: Building every 15 minutes during business hours to be extra fresh
K: B
G: ## Schedules shaped by consumption
The exam guide asks for schedules without unnecessary builds. Builds nobody reads are cost without value.
## Change
- Business hours: hourly (or on input change).
- Overnight: one build to catch up, so 08:00 is fresh.
- Freshness checks adjusted to the schedule.
Example: 24 builds a day become 11; the 08:00 dashboard is as fresh as before.
W: Business-hours cadence with an overnight catch-up: the same experience for users at half the cost.
X: A=Around the clock: pays for 13 builds a day that nobody sees.
C=On request: users should not have to request data; the morning view would be stale.
D=Every 15 minutes: quadruples daytime cost for freshness nobody asked for.
T: Align build schedules with when consumers actually use the data.
V: schedules

@ PLTR-DE D4 T4.4 applied use-case
S: An engineer must hand over a pipeline to another team. What should the handover include so the new team can operate it?
A: A verbal walkthrough over a couple of meetings and a copy of the engineer's personal notes about the pipeline's quirks
B: Documented contracts, schedule and triggers, checks with rationale, rerouted alerts, runbooks, consumer list, and an access review
C: Just the repository link and a short message, since well-written transform code explains itself to any competent engineer
D: A copy of the pipeline's datasets placed in the new team's project, so that they have the data they need from day one
K: B
G: ## Operational handover
The exam guide treats operations (schedules, checks, alerts, ownership) as part of pipeline engineering. A handover transfers the ability to operate, not just the code.
## Contents
- Contracts, schedule, triggers.
- Quality controls and why they exist.
- Alerts rerouted; ownership recorded.
- Runbooks; consumer list from lineage.
- Access: build identities and permissions reviewed.
Example: the new team's first incident is resolved from the runbook without calling the previous owner.
W: Contracts, operations, controls, ownership and runbooks: the complete transfer of operational knowledge.
X: A=Verbal plus notes: unstructured knowledge fades within weeks and the notes assume context only the original engineer had.
C=Repository only: code does not explain schedules, alerts or why a threshold is set.
D=Dataset copies: static data without the pipeline, schedule, checks or alerts that keep it current; the copies go stale immediately.
T: Hand over pipelines with documented contracts, operations, controls, ownership and runbooks.
V: Data Lineage, Data Health

@ PLTR-DE D4 T4.2 advanced troubleshooting
S: A build runs successfully but takes four hours, and Spark details show 95% of the time in a single final stage writing output with one task. What is the cause and fix?
A: The output dataset's underlying storage is slow for large writes; request faster storage from the platform team for this dataset
B: The output is written through a single partition (after a coalesce(1) or global sort); repartition before writing and confirm
C: The transform has too many small input files to read efficiently; compact the input datasets so the build reads fewer, larger files
D: The build identity lacks write permissions on the output and the platform is silently retrying the write for hours before giving up
K: B
G: ## Single-task writes
The exam guide asks you to read Spark details for code-level inefficiency. A one-task final stage means the output was collapsed to one partition before writing.
## Fix
- Find the cause: `coalesce(1)`, a global `orderBy`, or a window without partitioning.
- Repartition before the write (by a sensible key or count).
- Verify: the final stage has many tasks and finishes in minutes.
Example: removing a coalesce(1) left over from a debugging session turns a four-hour build into a twelve-minute one.
W: A single-partition write identified in Spark details and fixed by repartitioning: the stage parallelizes and the time collapses.
X: A=Slow storage: storage speed would affect all writes, not just this one's single task.
C=Input compaction: the input stage is fine; the write stage is the bottleneck.
D=Permissions: a permission error fails the build; it does not slow a successful write.
T: A one-task output stage means a single-partition write; repartition before writing.
V: Spark Details, Code Repositories
