# PLTR-DE batch 03: Domain 2 (Data Transformation and Pipeline Authoring), 8 questions

@ PLTR-DE D2 T2.1 applied comparison
S: A team of business analysts with no programming background needs to build a pipeline that joins three datasets, filters rows, derives a few columns and runs daily. Two engineers can help occasionally. Which authoring tool should the team start with?
A: Code Repositories with PySpark transforms, since every pipeline eventually needs code and the analysts should learn it from the start
B: Pipeline Builder, where the joins, filters and derived columns are configured visually and the pipeline is scheduled like any other
C: Code Workspaces notebooks, since analysts are comfortable with notebook-style exploration and can schedule the notebook as the pipeline
D: Contour analyses saved as datasets, since Contour is designed for analysts and can express joins and filters
K: B
G: ## Choosing an authoring tool
The exam guide asks you to choose Pipeline Builder, Code Workspaces or Code Repositories based on complexity, team skills, custom libraries and processing needs.
- **Pipeline Builder**: visual authoring of transforms (joins, unions, filters, expressions, aggregations), with branching, scheduling and lineage. Best for standard transformations and teams without code skills.
- **Code Repositories**: code transforms (Python/PySpark, SQL, Java) with tests, custom libraries and full control; best for complex logic and engineering teams.
- **Code Workspaces**: interactive notebooks for exploration and model development, not the primary place for production pipelines.
Example: the analysts build the three-way join and the derived columns in an afternoon; an engineer reviews the pipeline and sets the schedule.
W: Pipeline Builder: the transformations are standard and the team cannot write code, which is the situation Pipeline Builder is built for; it remains a governed, scheduled pipeline.
X: A=Code Repositories: the team lacks the skills and the pipeline does not need custom code; starting here would stall the project.
C=Notebook as pipeline: notebooks suit exploration; running production pipelines from them weakens testing, review and lineage discipline.
D=Contour: an analysis tool for interactive exploration; it is not the authoring tool for a maintained production pipeline.
T: Standard transformations by non-programmers belong in Pipeline Builder; code repositories are for complex or library-dependent logic.
V: Pipeline Builder, Code Repositories

@ PLTR-DE D2 T2.1 applied comparison
S: A pipeline must parse a proprietary binary log format using a vendor's Python library, run unit tests in CI before deployment, and apply complex stateful logic. Which authoring environment fits?
A: Pipeline Builder, using built-in expressions to decode the binary format field by field
B: Code Repositories, with Python transforms that import the vendor library as a dependency and are covered by unit tests
C: A Code Workspace notebook that runs on a schedule and imports the vendor library interactively
D: A sequence of Pipeline Builder pipelines, one per processing stage, with the binary parsing done in the first one
K: B
G: ## When code is required
The same decision criteria (complexity, team skills, custom libraries, processing needs) point the other way here:
- A vendor library must be declared as a dependency and versioned with the transform.
- Unit tests in CI require a repository with a test framework.
- Complex stateful logic is easier to express and review in code.
Code Repositories provide dependency management, branching, pull-request review, tests and builds, and the transform still participates in lineage and scheduling like any other dataset.
Example: `parse_logs.py` imports `vendorlogs`, has tests for malformed records, and is reviewed before merge; the dataset builds nightly.
W: Code Repositories: custom libraries, CI tests and complex logic are the three signals that the guide associates with code-based authoring.
X: A=Pipeline Builder expressions: a proprietary binary format cannot be decoded with built-in expressions, and there is no way to import the vendor library.
C=Scheduled notebook: notebooks lack the CI testing and review workflow; running production parsing from a notebook is fragile.
D=Chained Builder pipelines: splitting the work does not create the ability to import a library or run unit tests.
T: Custom libraries, tests and complex logic mean Code Repositories.
V: Code Repositories

@ PLTR-DE D2 T2.2 advanced troubleshooting
S: After joining an orders dataset (1 million rows) to a customers dataset on `customer_id`, the output has 1.4 million rows. The join was meant to add the customer's name to each order. What is the correct response?
A: Deduplicate the output on the order id after the join, keeping the first row for each order, so the count returns to 1 million
B: Check whether `customer_id` is unique in the customers dataset; if it is not, fix the customer data or the join contract before rerunning the join
C: Change the join to an inner join, since the extra rows come from orders without a matching customer that the join is padding
D: Filter the customers dataset to the most recent record per customer inside the join step without telling consumers, since the output count is what matters
K: B
G: ## Joins and cardinality
A join adds the customer name per matching customer row. If a customer appears twice in the customers dataset (two addresses, two historical versions), every order for that customer is duplicated. The exam guide warns that a successful join is not necessarily a meaningful relationship, and asks you to check keys and cardinality.
## Correct handling
- Measure: count distinct `customer_id` versus rows in customers.
- Diagnose: which customers are duplicated and why (history table, source quality issue).
- Fix the contract: a "current customer" dataset with one row per customer, documented as such, or a deliberate choice of which version to use.
- Then re-run; the count should match the number of orders.
Example: 8,000 customers have two rows because address changes create new rows; a curated `customers_current` dataset resolves it for every consumer.
W: Verify key uniqueness and fix the data contract: this addresses the cause (a one-to-many relationship that was assumed to be one-to-one) rather than hiding its symptom.
X: A=Deduplicate after the join: it hides the duplication, picks an arbitrary customer version, and leaves the bad contract for every other consumer.
C=Inner join: unmatched orders would reduce the count, not increase it; the extra rows come from duplicated customers.
D=Silent filter inside the join: an undocumented choice buried in one transform is exactly the "arbitrary filter" the guide warns against; consumers would not know which version they get.
T: When a join multiplies rows, inspect key uniqueness and cardinality and fix the contract; never mask it with deduplication.
V: Pipeline Builder, Code Repositories

@ PLTR-DE D2 T2.2 applied use-case
S: A dataset of support tickets contains a free-text description. The team wants a structured `category` column (one of 10 values) for every ticket, refreshed with the nightly build. Which transformation approach is appropriate?
A: A structured LLM enrichment step that classifies each description into one of the 10 categories, with enumerated output and validation
B: A keyword lookup expression that assigns a category whenever a listed keyword appears in the description, since it is deterministic and needs no model
C: A manual categorization task sent to the support team each morning for the previous day's tickets
D: A Workshop app where analysts pick the category when they open a ticket, so no pipeline step is needed
K: A
G: ## LLM enrichment inside pipelines
The exam guide lists structured LLM enrichment among the transformation operations, alongside joins, aggregations, geospatial and media processing. Classifying free text into a fixed set of categories at pipeline scale is a typical case.
## Doing it well
- Enumerated output: the model may only return one of the 10 categories.
- Validation: anything else is rejected and routed for review.
- Keep the prompt and raw response for audit; cache by description so unchanged tickets are not reclassified.
- Downstream, the category becomes an Ontology property for filters and dashboards.
Example: 20,000 nightly tickets are classified in the build; 1% fail validation and are flagged.
W: Structured LLM enrichment with constrained output and validation: it turns free text into a governed categorical column at pipeline scale, on the nightly schedule.
X: B=Keyword expressions: free-text descriptions vary too much; keyword rules miss most tickets and misclassify many, and maintaining the rules is endless.
C=Manual categorization: it does not scale to daily volumes and the column would always lag by a day of human work.
D=Pick in Workshop: categories would exist only for tickets someone opened; dashboards and filters need every ticket classified.
T: Use structured LLM enrichment in the pipeline for text-to-category tasks, with enumerated output and validation.
V: Pipeline Builder, AIP

@ PLTR-DE D2 T2.3 applied tradeoff
S: A transform aggregates 3 billion event rows per day into hourly metrics. The current single-node Python implementation runs out of memory. What should be done?
A: Request a machine with more memory for the single-node engine, since the aggregation logic is simple and only the data size is the problem
B: Move the transform to a distributed Spark engine, which partitions the data across executors so the aggregation fits
C: Split the daily input into 24 hourly files and run the single-node transform 24 times, merging the results by hand
D: Sample 10% of the events and scale the metrics by ten, which fits in memory and is close enough for hourly reporting
K: B
G: ## Compute engine by scale
The exam guide asks you to choose a compute engine based on scale, memory, API needs, startup cost and feature compatibility. Three billion rows is beyond what one node can hold; this is the case for distributed computation.
## Spark for large aggregations
- Data is partitioned across executors; each aggregates its partitions, and results are combined.
- Memory per executor can be tuned, and skew (one hour or one key with most of the data) can be addressed with repartitioning.
- The transform's code may change little: a groupBy on hour and key.
The reverse rule also holds: small inputs belong on lightweight engines, which is why the engine choice is made per transform.
Example: 3 billion rows over 200 partitions aggregate in minutes; the previous implementation failed after an hour.
W: Distributed Spark: the workload exceeds a single node's memory, and distribution is the direct answer to scale, with the same aggregation logic.
X: A=Bigger single node: memory grows linearly with data on one machine, and 3 billion rows per day will keep growing; vertical scaling is a short-lived fix.
C=24 manual runs: an ad hoc manual batch loses the pipeline's scheduling and lineage and still risks memory limits in busy hours.
D=Sampling: hourly metrics from a sample are estimates, not the required aggregates; rare keys are lost entirely.
T: Workloads beyond one node's memory go to a distributed engine; keep lightweight engines for small inputs.
V: Code Repositories, Spark

@ PLTR-DE D2 T2.4 applied troubleshooting
S: A transform produces a revenue column that is 30% lower than the finance team's own figure for last month. The build succeeds and the schema is correct. What should the data engineer do first?
A: Add a correction factor to the transform so that the revenue matches the finance figure, since the finance number is the source of truth
B: Debug on a branch with the same inputs, comparing intermediate counts and sums with the finance definition to find the gap
C: Rebuild the pipeline with a forced snapshot, since successful builds with wrong results usually mean stale incremental state
D: Ask finance to adjust their figure to match the pipeline, since the pipeline's logic has been reviewed and the build succeeded
K: B
G: ## Debugging rather than masking
The exam guide says to test, debug and refactor transformations rather than masking incorrect output. A discrepancy has a cause: a filter that excludes a channel, a join that drops rows, a currency not converted, a different definition of "revenue" (gross versus net, refunds, timing).
## Approach
- Reproduce on a branch with the same inputs.
- Compare at each step: row counts by stage, sums by segment, against finance's breakdown.
- Reconcile definitions: the 30% may be refunds that finance includes and the pipeline excludes.
- Fix the logic or document the definitional difference; then add an expectation that catches a repeat.
Example: the join to the product dimension used an inner join and silently dropped orders for discontinued products, which finance still counts.
W: Debug on a branch with intermediate comparisons: this finds the actual cause of the 30% gap and leads to a real fix that consumers can trust.
X: A=Correction factor: multiplying by a fudge factor hides an unknown error; it will be wrong next month when the cause changes size.
C=Forced snapshot: there is no evidence of incremental staleness; rebuilding the same logic on the same inputs reproduces the same result.
D=Ask finance to change: dismissing the discrepancy without diagnosis risks shipping wrong revenue; a successful build says nothing about correctness.
T: A successful build is not a correct result; trace discrepancies step by step on a branch and fix the logic.
V: Code Repositories, Pipeline Builder

@ PLTR-DE D2 T2.2 applied use-case
S: A logistics dataset has delivery points as latitude and longitude, and a separate dataset of warehouse service areas as polygons. The business wants each delivery assigned to the service area that contains it. Which approach is correct?
A: A geospatial operation that performs a point-in-polygon join between the delivery coordinates and the service-area polygons
B: A string match between the delivery city name and the warehouse city name, since service areas follow city boundaries
C: A nearest-warehouse calculation using the straight-line distance from each delivery to each warehouse's location
D: A manual lookup table that maps postal codes to service areas, maintained by the operations team
K: A
G: ## Geospatial operations in pipelines
The exam guide includes geospatial operations among the transformation operations to apply appropriately. Assigning points to containing polygons is a spatial join: for each delivery point, find the polygon that contains it.
## Why spatial, not approximations
- City names and postal codes do not follow service-area polygons; boundaries cut across them.
- Nearest warehouse by distance ignores the actual service area shapes (rivers, roads, contracts).
- A point-in-polygon join uses the real geometries, so the assignment is exactly what the business defined.
Example: a delivery on the east side of a river is 2 km from warehouse A but inside warehouse B's polygon; the spatial join assigns B.
W: Point-in-polygon spatial join: it implements the business rule literally, using the polygons that define the service areas.
X: B=City name match: service areas are polygons, not cities; many deliveries would be assigned to the wrong area or to none.
C=Nearest warehouse: distance is not the rule; the nearest warehouse may not serve that location.
D=Postal-code table: postal codes straddle area boundaries and the table must be maintained by hand; the polygons already encode the answer.
T: When the rule is "inside this area", use a spatial point-in-polygon join rather than name, distance or code proxies.
V: Pipeline Builder, geospatial

@ PLTR-DE D2 T2.4 applied use-case
S: A critical transform is being refactored to improve performance. The output must remain identical. How should the engineer validate the refactor before merging?
A: Merge the refactor and compare tomorrow's production output with today's; if consumers do not complain, the refactor is correct
B: Build the refactor on a branch against the same inputs and compare row counts, key sets and column values with the current output
C: Review the code carefully and merge if it reads correctly, since a performance refactor by definition does not change the logic
D: Run the refactored transform on a 1,000-row sample and merge if the sample output matches, since any logic error would show in a sample
K: B
G: ## Branches as a safety net
Foundry pipelines support branching: a transform can be built on a branch with the same inputs, producing an output that does not touch production. The exam guide asks you to test and refactor rather than trust, and to manage branches as an operational responsibility.
## Equivalence check
- Same inputs on both sides (pin the input transactions or build at the same time).
- Compare row counts, the set of primary keys, and column values (hash or direct comparison); report any difference.
- Check nulls and types, which performance changes (different join strategy, different engine) can alter.
- Only then merge, and measure the performance gain.
Example: the refactor changed a left join to an inner join for speed; the comparison shows 1,200 missing rows and the refactor is corrected before merge.
W: Branch build and output comparison on identical inputs: it proves equivalence with evidence before production is affected, which is what "must remain identical" requires.
X: A=Compare after merging: production is already changed when the comparison happens, and consumers often do not notice subtle differences.
C=Code review alone: refactors frequently change behaviour in edge cases (nulls, duplicates, ordering); reading cannot replace comparing outputs.
D=1,000-row sample: rare keys, skewed partitions and edge cases are unlikely to appear in a small sample; the full comparison is cheap on a branch.
T: Validate refactors by building on a branch and comparing the full output with production before merging.
V: Code Repositories, branches
