# PLTR-DE batch 05: Domain 4 (Pipeline Operations and Scheduling), 8 questions

@ PLTR-DE D4 T4.2 applied troubleshooting
S: A transform that used to finish in 10 minutes now takes 90 minutes, with no code change. The input dataset has grown slightly. Which evidence should the data engineer examine to find the cause?
A: The transform's code, re-reading it to find inefficient operations that were always present
B: The build's Spark details and a Job Comparison with the last fast build: stage durations, shuffle sizes, task skew, input files
C: The downstream health checks, since a slow build is usually reported first by its consumers
D: The project's permission settings, since changed roles can slow down a build that must check access on every input file it opens
K: B
G: ## Diagnostic evidence for performance
The exam guide names builds, logs, Data Lineage, Spark Details, Job Comparison and the Linter as diagnostic evidence, and asks you to distinguish code-level inefficiency, data skew, resource limits, permission failures and upstream cascades.
## Reading Spark details
- Stage durations: which stage grew from 10 to 90 minutes.
- Task skew: one task taking most of the time means a hot key or partition.
- Shuffle read/write: a join that now moves far more data.
- Input files: a small growth in rows but a large growth in file count (small files) slows reading.
Job Comparison puts the fast and slow runs side by side so the changed metric stands out.
Example: the comparison shows one task processing 80% of the data after a new customer with millions of rows arrived: data skew, fixed by salting the join key.
W: Spark details and Job Comparison: they show where the time went and what differs from the last fast run, which identifies skew, resource or input changes without guessing.
X: A=Re-reading code: the code did not change; reading it cannot explain a change in behaviour, and inefficiencies that always existed were already acceptable.
C=Downstream health checks: they report lateness, not the cause of the slow build.
D=Permissions: permission problems fail builds; they do not make a successful build nine times slower.
T: For a sudden slowdown without a code change, compare the slow and fast builds' Spark details to find skew, shuffle or input changes.
V: Spark Details, Job Comparison

@ PLTR-DE D4 T4.3 applied troubleshooting
S: Twelve downstream datasets failed their scheduled builds overnight. Their error messages differ, but all of them read from the same curated customer dataset, which also failed. What is the correct way to handle this?
A: Investigate each of the twelve failures separately, since their error messages are different and may have different causes
B: Treat it as an upstream cascade: fix the curated customer dataset first, then rebuild the downstream datasets in order
C: Rebuild all thirteen datasets immediately with force, since a transient failure is the most common reason for overnight errors
D: Disable the twelve downstream schedules until each owner has reviewed their transform for defects
K: B
G: ## Upstream cascades
The exam guide asks you to distinguish upstream cascades from code-level failures. When many datasets fail together and share a failed input, the input is the first bad stage; the downstream errors (missing files, schema mismatch, empty input) are symptoms of it.
## Handling
- Use Data Lineage to confirm the shared dependency.
- Diagnose and fix the upstream build.
- Rebuild downstream in dependency order; most will succeed without changes.
- Investigate only the downstream datasets that still fail after the input is healthy.
Example: the customer build failed on a source schema change; after fixing the ingestion, eleven of the twelve downstream builds pass and the twelfth has an unrelated bug.
W: Fix the shared upstream first: the twelve failures share a cause, so repairing it and rebuilding in order resolves them efficiently instead of twelve separate investigations.
X: A=Twelve separate investigations: the different messages are consequences of one missing input; investigating each wastes the night and repeats the same discovery.
C=Force-rebuild everything: with the upstream still broken, downstream builds fail again, and force-building without a diagnosis can reprocess full history needlessly.
D=Disable schedules: it stops the alerts without fixing anything, and the transforms are not defective.
T: Many failures with one shared failed input mean fix the upstream first, then rebuild downstream.
V: Data Lineage, builds

@ PLTR-DE D4 T4.1 applied use-case
S: A report dataset depends on three ingestions that complete at different, unpredictable times between 01:00 and 04:00. The report must build once all three inputs for the day are present and never partially. How should the build be scheduled?
A: A time-based schedule at 04:30 every day, which is after the latest usual completion time
B: An event-based schedule that waits for all three inputs to have updated since the last run and then triggers one build
C: A schedule that runs every fifteen minutes from 01:00 to 05:00, so that at least one run sees all three inputs
D: Three separate schedules, one triggered by each input, so the report is refreshed whenever any input arrives
K: B
G: ## Event-based triggers with multiple inputs
The exam guide asks you to configure schedules and event-based triggers without unnecessary builds. A time-based schedule guesses; an event-based schedule reacts. With several inputs, the condition can require all of them to have new transactions before building.
## Why this is correct
- No partial builds: the report does not run until the third input lands.
- No wasted builds: one run per day, when ready.
- No late data: if an ingestion is delayed to 05:00, the report waits instead of building on yesterday's data.
Example: inputs land at 01:40, 02:55 and 03:48; the report builds at 03:48. The next day one input lands at 05:10 and the report follows it.
W: Event trigger on all three inputs: it builds exactly once, exactly when the day's inputs are complete, with no partial or redundant builds.
X: A=04:30 timer: on a slow night an input arrives later and the report builds on stale data; on fast nights it waits needlessly.
C=Fifteen-minute polling: this builds many times on partial inputs and wastes compute; "at least one run" is not "never partially".
D=Per-input triggers: each arrival rebuilds the report on partial data, which is the opposite of the requirement.
T: Build when all inputs have arrived using an event-based trigger that waits for every input, not a time guess.
V: schedules, builds

@ PLTR-DE D4 T4.4 applied use-case
S: An engineer needs to change the logic of a production transform that feeds a dashboard used by executives. How should the change be developed and released?
A: Edit the transform on the main branch during a quiet hour and watch the dashboard afterwards for problems
B: Develop on a branch, build and validate the output there, get the change reviewed, then merge so production changes only once verified
C: Copy the transform to a new dataset with a different name, point the dashboard at the copy, and delete the original later
D: Make the change in a notebook, run it manually to produce the new output, and upload the result over the production dataset
K: B
G: ## Branches and releases
The exam guide lists managing branches and releases among ongoing operational responsibilities. A branch gives the engineer a parallel version of the pipeline whose builds do not affect production datasets or the dashboard.
## The workflow
- Branch from main; implement the change.
- Build on the branch with real inputs; compare outputs; run expectations.
- Pull request review by a colleague.
- Merge to main; the next production build carries the change; keep the previous build for rollback.
This is the same discipline as software delivery and it is what protects an executive dashboard from an untested edit.
Example: the branch build reveals a null-handling difference that would have shown as blank revenue on the dashboard; it is fixed before merge.
W: Branch, validate, review, merge: production and the dashboard change only after the new logic is proven on the branch and reviewed.
X: A=Edit on main: the first production build after the edit is the test, with executives as the testers.
C=Copy-and-repoint: this duplicates datasets, breaks lineage, and still releases untested logic to the dashboard.
D=Notebook upload: a manual overwrite bypasses the pipeline, lineage and schedules; the next scheduled build replaces it anyway.
T: Change production pipelines through branches with validation and review, then merge.
V: Code Repositories, branches

@ PLTR-DE D4 T4.3 applied troubleshooting
S: A build fails with a message saying the executing identity cannot read one of the transform's inputs. The engineer who wrote the transform can open and preview that input. What is going on, and what should be done?
A: The input dataset is corrupted and must be rebuilt by its owner before the transform can read it
B: The build runs under a different identity that lacks access to the input; grant that identity the specific access it needs
C: The transform's code references the wrong dataset path, and the error message about permissions is misleading and should be ignored
D: The engineer's permissions have expired and must be renewed, after which the build will succeed
K: B
G: ## Pipeline execution permissions
The exam guide asks you to explain separately why a user can open a resource, why they can read its data, and why a pipeline can or cannot execute. Builds run under an execution context whose permissions are not necessarily the author's.
## Fixing it
- Identify which identity the build runs as.
- Check its access to the failing input (Check Access).
- Grant that identity the minimal access, for example read on the input through the appropriate role or marking; do not open the dataset to everyone.
Example: the input carries a marking the build identity does not hold; adding the identity to the marking's membership fixes the build, and the dataset's audience stays unchanged.
W: Execution identity lacking access, fixed with targeted access: the message says exactly that, and granting the executing identity what it needs is the smallest safe repair.
X: A=Corrupted input: the message is about permissions, not data integrity; the engineer can read the input fine.
C=Wrong path: a wrong path gives a not-found error; the message is specific about the executing identity's access.
D=Engineer's permissions: the engineer can open the input; the build identity is the one failing.
T: Build failures on access are about the executing identity, not the author; grant it the specific access it lacks.
V: Check Access, builds

@ PLTR-DE D4 T4.4 applied tradeoff
S: A monthly cost review shows that one pipeline accounts for 40% of the team's compute. Its transforms run hourly, but the consuming dashboard is refreshed once a day, and each run reprocesses the full input. What should the engineer do?
A: Keep the hourly schedule but reduce executor sizes, which lowers cost per run while preserving the current freshness
B: Align the schedule with the daily consumption and convert the transforms to incremental where inputs append
C: Move the pipeline to a lightweight engine, since lightweight compute is always cheaper regardless of data size
D: Ask the dashboard owners to refresh more often so that the hourly builds are justified by usage
K: B
G: ## Cost as an operational responsibility
The exam guide lists resource usage and cost among ongoing operational responsibilities and asks to right-size compute. Two inefficiencies are visible: runs that nobody consumes (24 per day for one daily refresh), and full reprocessing when the inputs append.
## The fix
- Schedule to consumption: daily, or event-based on the inputs' daily arrival.
- Incremental processing for append inputs, with occasional full recompute for reconciliation.
- Then right-size executors with Spark details as evidence.
Together, the pipeline does about 1/24 of the runs, each doing a fraction of the work.
Example: compute for the pipeline drops from 40% of the team's spend to under 3%, with the dashboard unchanged.
W: Align schedule with consumption and go incremental: these remove the two sources of waste, which is far more effective than tuning the cost of runs that should not happen at all.
X: A=Smaller executors hourly: still 24 full runs a day; smaller executors may just make each run longer.
C=Lightweight engine: lightweight is for small inputs; a full-input pipeline that costs 40% of the budget is not small, and it would still run hourly.
D=More frequent refresh: inventing demand to justify waste inverts the goal; cost should follow the real requirement.
T: Match build frequency to consumption and process incrementally; right-size compute only after removing unnecessary work.
V: schedules, incremental transforms

@ PLTR-DE D4 T4.2 applied use-case
S: The team wants to catch common anti-patterns in transforms, such as unnecessary full-input scans or missing partitioning, before they reach production. Which tool supports this?
A: The Linter, which analyses pipelines and flags inefficient or risky patterns that the team can address before release
B: Data Health, which runs after the build and reports the resulting dataset's size
C: Job Comparison, which compares two completed builds and therefore cannot run before the first production build
D: The Ontology Manager, which validates object types but not transforms
K: A
G: ## Preventive checks
The exam guide lists the Linter among the diagnostic tools. A linter inspects pipelines statically or against build metadata and raises findings about patterns known to cause problems: inefficient operations, missing incremental configuration, risky joins, oversized outputs.
## Where it fits
- Before release: findings are addressed on the branch.
- Periodically: as pipelines evolve, new findings appear.
- Together with Spark details (after a run) and Data Health (on datasets), it covers prevention, diagnosis and monitoring.
Example: the Linter flags a transform that reads a 2 TB input without any filter pushdown; the author adds a partition filter before merging.
W: The Linter: it is the tool that surfaces anti-patterns in pipelines before they cost production time.
X: B=Data Health: it monitors datasets after builds (freshness, size, schema), not transform code quality.
C=Job Comparison: it compares completed runs; it diagnoses rather than prevents.
D=Ontology Manager: it governs object types and links, not transform efficiency.
T: Use the Linter to catch pipeline anti-patterns before release; use Spark details and Data Health afterwards.
V: Linter

@ PLTR-DE D4 T4.3 advanced troubleshooting
S: A scheduled pipeline occasionally fails with an out-of-memory error on a join, roughly once a week, and succeeds when retried. The failure days correlate with a monthly bulk upload in one source. What is the smallest safe repair?
A: Double the executor memory permanently, which removes the failures at the cost of higher spend on every run
B: Fix the skew on bulk-upload days by repartitioning or salting the join key, add a retry policy, and monitor memory in Spark details
C: Move the monthly bulk upload to a weekend so that the failure happens when nobody is watching the dashboard
D: Replace the join with a broadcast join, which never runs out of memory because the smaller side is simply copied to every executor in the cluster
K: B
G: ## Resource limits versus skew
The exam guide distinguishes code-level inefficiency, data skew, resource limits and upstream cascades, and asks for the smallest safe repair. Intermittent out-of-memory on a join that correlates with a specific data pattern suggests skew (a few keys carrying most of the bulk) rather than a general shortage.
## Targeted fix
- Confirm with Spark details on a failing day: a few tasks with huge shuffle reads.
- Repartition or salt the hot keys so the data is spread across tasks.
- Keep a retry policy for genuine transient failures and watch memory metrics.
- Only if the evidence shows uniform pressure, raise resources.
Example: one supplier's monthly file has 60% of the rows under one key; salting the join spreads them, and the failures stop without extra spend on the other 29 days.
W: Skew-targeted fix with retries and monitoring: it addresses the actual pattern on the days it occurs, with no permanent cost increase, and the evidence confirms it.
X: A=Double memory for all runs: it pays for the monthly peak every day and may still fail if the skew grows.
C=Move the upload: it hides the failure rather than fixing it; the dashboard would still be stale that day.
D=Broadcast join: a broadcast works only when one side is small; broadcasting a large side is a common cause of out-of-memory, not a cure.
T: Intermittent memory failures tied to a data pattern are usually skew; fix the distribution rather than permanently buying memory.
V: Spark Details, Code Repositories
