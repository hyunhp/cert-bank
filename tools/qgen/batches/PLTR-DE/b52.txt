@ PLTR-DE D4 T4.1 applied troubleshooting
S: A schedule builds a dataset every 30 minutes, but the build sometimes takes 50 minutes. An engineer fears that two builds of the same dataset will run at once and write over each other. What actually happens when the schedule's trigger is satisfied again while the previous run is still in progress?
A: The new trigger stays pending and the schedule runs only after the previous run finishes
B: The running build is cancelled and restarted immediately so the newest trigger always wins
C: The new trigger is dropped permanently and the schedule waits for the following 30-minute slot
D: Both runs start in parallel and the platform merges their transactions when each one completes
K: A
G: ## Triggers while a run is active
A schedule has a trigger that defines when its build should run. When the trigger is satisfied and a build is performed, the schedule has "run".
## What the docs say
- If a schedule is triggered while the previous run is still in action, it remains triggered and runs only after the previous run has finished.
- So overlapping builds of the same schedule do not happen; instead the schedule can fall behind its nominal interval.
Example: a 30-minute schedule with 50-minute builds effectively runs back to back, and the real fix is to shorten the build or relax the interval.
W: Pending trigger: the schedule stays triggered and starts its next run after the current one completes, so there is no overlap and no lost trigger.
X: B=Cancel and restart: the platform does not abort a running build because a new trigger arrived.
C=Dropped trigger: the trigger is kept, not discarded, so the work is still done once the build ends.
D=Parallel runs merged: a schedule never runs against itself in parallel, so there are no two transactions to merge.
T: A trigger that fires during a run stays pending and runs after the previous run finishes.

@ PLTR-DE D4 T4.1 applied troubleshooting
S: In the run history of a schedule, a junior engineer sees many runs marked Ignored on days when the upstream source delivered nothing. They want to open an incident for "failed builds". What do these runs indicate?
A: The schedule's trigger is misconfigured and must be rebuilt before any further runs can be created
B: The runs were blocked by a permission problem and the build identity needs the marking added again
C: The runs were attempted but created no build, usually because everything was already up to date
D: The runs created builds that failed, so the logs of those builds should be opened for the error
K: C
G: ## Reading schedule run history
Run history records when a schedule ran and what happened. A run can be Succeeded, Ignored or Failed, and the three mean different things.
## Meanings
- Succeeded: the run started a build. The build itself may still be running or may fail later.
- Ignored: the run was attempted but no build was created, which usually means there was no work to do because outputs were not stale.
- Failed: the schedule itself failed to run.
Example: an upstream source that delivers nothing leaves the dataset up to date, so the schedule is Ignored, which is the desired outcome.
W: Ignored means a run was attempted with no build created, typically because inputs had not changed; it is saved compute, not an error.
X: A=Misconfigured trigger: the trigger clearly fired, otherwise there would be no run record at all.
B=Permission problem: a permission failure would not be reported as an up-to-date skip.
D=Failed builds: no build was created, so there are no failed build logs to open.
T: An Ignored schedule run created no build, typically because nothing was stale.

@ PLTR-DE D4 T4.1 applied troubleshooting
S: A schedule on a reporting dataset fires when two upstream datasets have both updated. It was paused for a holiday week; during the pause both upstream datasets updated several times. After the engineer resumes it, no build starts. What best explains this?
A: Pausing converts the schedule to a manual one, so it must be recreated as a new schedule
B: Resuming always replays every missed trigger at once, and these replays are still queued
C: The schedule is waiting for the holiday period to be marked as a non-business interval
D: Pausing reset the trigger state and events observed during the pause were forgotten

A schedule that waits for several events, such as two inputs both updating, remembers which events it has seen. A pause changes that memory.
## Behaviour
- While paused, the schedule cannot be triggered and ignores all observed events.
- Pausing resets the trigger state and the events observed so far are forgotten.
- After resuming, the trigger needs fresh events, so a one-off manual build of the dataset brings the output up to date straight away.
Example: after the holiday, run one manual build, then let the trigger work from the next update onwards.
W: Reset trigger state: events seen during the pause were forgotten, so the schedule waits for new updates and a manual catch-up build is the quick fix.
X: A=Manual conversion: a paused schedule stays the same schedule and resumes with its original trigger.
B=Replayed triggers: the docs say observed events are forgotten, not queued, so there is nothing to replay.
C=Business interval marking: the trigger depends on the upstream updates, not on any holiday flag.
T: Pausing a schedule discards observed trigger events, so catch up with a manual build after resuming.

@ PLTR-DE D4 T4.2 applied troubleshooting
S: A PySpark transform on a 2 billion row table finishes the early stages quickly but then stalls for an hour in a stage that runs on a single node. The code ends by calling `toPandas()` on the full joined result to reshape it in pandas before writing. What is the best fix?
A: Request a larger driver profile so the full result fits in one process and keep the pandas step
B: Wrap the pandas step in a retry loop so that it succeeds once enough memory frees up
C: Express the reshape with distributed DataFrame operations so the work stays spread across executors
D: Repartition the input into thousands of tiny partitions before collecting to make the collect faster
K: C
G: ## Keep large data distributed
Spark scales because transformations run in parallel across executors. Collecting a large DataFrame into one process, such as with `toPandas()` or `collect()`, serialises the whole job onto a single machine.
## Symptoms and fix
- A late stage that runs on one node while executors sit idle points to a collect.
- The fix is to express the logic with DataFrame functions, window functions or grouped operations that stay distributed.
- Collecting is only safe for small results, such as an aggregate of a few thousand rows.
Example: replacing a pandas pivot on 2 billion rows with a grouped pivot in Spark brings the stage back to minutes.
W: Distributed operations: keeping the reshape in Spark removes the single-node bottleneck instead of making it bigger or hiding it.
X: A=Larger driver: a bigger machine postpones the memory error but the work still runs on one node and scales poorly as data grows.
B=Retry loop: retrying a collect that needs more memory than exists does not make memory appear.
D=Tiny partitions: more partitions add scheduling overhead, and the result is still collected into one process.
T: Do not collect large results to one node; use distributed DataFrame operations.

@ PLTR-DE D4 T4.2 applied use-case

A regular join shuffles both sides by key across the cluster. When one side is tiny, Spark can send a copy of it to every executor and join each fact partition locally.

- A broadcast hint on the small table removes the big shuffle.
- Broadcasting only suits tables that fit comfortably in executor memory.

X: B=Pre-sorting: ordering both tables in a separate step adds work and the join still shuffles.
C=Enlarging the lookup: making the small side bigger removes the one property that allows a cheap join.
D=Caching the fact table: it is too large to cache on every executor and the shuffle would still happen.
T: Broadcast a tiny table to avoid shuffling the large side of a join.

@ PLTR-DE D4 T4.2 applied tradeoff
S: A transform joins two wide tables (300 columns each) and only afterwards filters to the last 90 days and selects 12 columns. Runs are slow with heavy spill to disk. Which restructuring is the best first step?
A: Add more executors and keep the logic as it is, since the plan is correct and only the cluster is small

Joins and aggregations shuffle data. Every column and row that reaches the shuffle costs network, memory and disk, so shrinking inputs early is usually the cheapest optimisation.

Example: cutting 300 columns to 12 and 3 years to 90 days can shrink the shuffle by a factor of well over 50.
W: Early filter and column pruning: smaller shuffles mean less spill and shorter runs without needing more hardware.
X: A=More executors: spending on hardware hides an avoidable inefficiency, and costs grow with the oversized data.
C=Duplicate join: repeating a join adds cost and does not make the optimiser behave differently.
D=Casting to strings: string comparisons are typically larger and slower, and could change join semantics.
T: Filter rows and prune columns before joins to shrink shuffles.

A build runs on a branch and carries a sequence of fallback branches. For inputs that do not exist on the build branch, the build falls back along the sequence.

- Datasets you did not change are therefore read from master, which makes branch testing cheap.

S: An administrator plans to add a marking to a widely used project of raw data so that only the data-protection team can read it. The project feeds 30 downstream datasets used by other teams. What should be done before applying it?
A: Apply it immediately, since inheritance only affects datasets inside the same project folder
B: Review the downstream lineage first, since the marking is inherited immediately by derived datasets
C: Apply it on a Friday evening to reduce the number of users who notice downstream problems
D: Apply it only on the 30 downstream datasets and leave the project itself without any marking
K: B
G: ## Applying a marking is sensitive
Markings are inherited along the file hierarchy and along data dependencies, and they take effect immediately.
## Consequences
- Everything in the project inherits the marking.
- Any dataset derived from a marked dataset inherits it too, so users who are not members lose access to data downstream.
- The marking should be applied with the downstream consumers known, with membership prepared and communication sent.
Example: lineage shows two executive dashboards depend on the raw data; their owners are told and their users are added to the marking beforehand.
W: Review lineage first: inheritance is immediate and reaches derived datasets, so impact and membership are planned before the change.
X: A=Immediately, folder only: inheritance also follows data dependencies outside the folder.
C=Friday evening: timing hides the impact and does not prevent lockouts.
D=Only downstream datasets: leaves the raw source unprotected, which is where the requirement started.
T: Check downstream impact before applying a marking, because it is inherited at once.
V: markings, lineage

@ PLTR-DE D6 T6.1 applied definition
S: A derived dataset joins one source carrying a PII marking with another carrying a FINANCE marking. An analyst is a member of the PII marking only and holds Viewer on the project. What access does the analyst have to the derived dataset's data?
A: Full access, because membership of one marking satisfies the requirement for the other
B: Read access to the PII columns only, because the platform splits the data by marking
C: No access to the data, because a user must be a member of all markings on a resource
D: Access after a delay, because the platform grants the missing marking once a Viewer role exists
K: C
G: ## Markings are conjunctive
A user needs membership of every marking applied to a resource, an AND rather than an OR. Roles do not substitute for a missing marking.
## In the example
- The derived dataset inherits both markings along its data dependencies.
- The analyst satisfies PII but not FINANCE, so the data is closed.
- Access requires a marking administrator to add the analyst to FINANCE, if appropriate.
Example: the analyst may still see that the dataset exists and view metadata, but not its contents.
W: Conjunctive markings: missing FINANCE means no data access, whatever roles the analyst holds.
X: A=One is enough: markings are combined with AND, never OR, so the PII membership cannot cover the FINANCE requirement.
B=Column split: markings apply to the whole resource and do not split columns.
D=Delayed grant: roles never assign marking membership automatically.
T: A user needs every marking on a resource; one missing marking blocks access.
V: markings

@ PLTR-DE D6 T6.2 applied use-case
S: Analysts want to experiment with new aggregations on curated data, and sometimes leave half-finished datasets behind. Production pipelines in the same project have been cluttered and an experiment once overwrote a table. Which structure best reduces this risk?
A: Give analysts the Owner role on the production project so they can tidy up whatever they leave behind
B: Ask analysts to prefix experiments with their initials and keep the production project as it is
C: Move the production pipeline to a personal folder of one engineer who guards it from changes
D: A sandbox project for experiments with read-only curated access, promoted by review
K: D
G: ## Separate experimentation from production
Projects are the main unit of access and organisation in Foundry. Separating sandbox from production is a common best practice rather than a fixed rule in the docs. Mixing exploration and production in one project means everyone with write access can alter production resources.
## Structure
- Production project: few editors, reviewed changes.
- Sandbox project: analysts have editor rights and can create freely.
- Curated datasets are referenced read-only from the sandbox; good results are promoted through review.
Example: an analyst's new aggregation lives in the sandbox until the engineers adopt it.
W: Sandbox project with read-only curated access: experiments stay away from production resources, and only reviewed work is promoted.
X: A=Owner on production: widens the risk, since owners can change or delete anything.
B=Naming prefixes: a convention does not stop an accidental overwrite.
C=Personal folder: concentrates ownership on one person and breaks team operations.
T: Give experiments their own project and promote results to production through review.

@ PLTR-DE D6 T6.2 applied use-case
S: Ten pipeline engineers have Editor on a project that holds raw synced data and transforms. Only three of them maintain the syncs; seven only write transforms and merely read the raw data. How should access be restructured?
A: Keep everybody as Editor, since they all work in the same pipeline and trust each other
B: Make all ten Owners so that nobody is blocked when a raw dataset needs a quick fix
C: Split raw and transform projects, with Editor on raw for the three and Viewer for the seven
D: Remove all editing rights and ask a platform administrator to apply each change on request
K: C
G: ## Least privilege by stage
Roles describe what a person may do in a project. People who only read a stage should not be able to change it.
## Design
- Raw project: three sync maintainers as Editor, others as Viewer.
- Transform project: the transform engineers as Editor.
- Grants given to groups, not to individuals.
Example: an accidental deletion of a raw dataset is only possible for the three people who maintain syncs.
W: Separate projects and roles by stage: each engineer holds the rights their job needs and no more.
X: A=Everyone Editor: any of seven readers can change or delete raw data.
B=All Owners: maximises rights and the ability to change permissions.
D=Administrator-only changes: creates a bottleneck and does not match how the team works.
T: Split projects by stage and give editing rights only to the people who maintain that stage.

@ PLTR-DE D6 T6.2 applied troubleshooting
S: A project holds ordinary reference data (country codes) and a salary dataset. The team added a restrictive marking to the whole project to protect the salary data, and now nobody outside HR can use the country codes. What is the best correction?
A: Keep the marking on the project and copy the country codes into each team's own project too
B: Remove the marking altogether and rely on Viewer roles to keep salary data safe
C: Add every employee to the marking so that the project works for everyone again
D: Move the salary data to its own project carrying the marking and leave the reference data unmarked
K: D
G: ## Markings follow the hierarchy
A marking on a project is inherited by every file inside it, so everything shares one audience. A project should hold resources with the same sensitivity.
## Fix
- Create a project for the sensitive data and apply the marking there.
- Keep the shared reference data in an unmarked project that all teams can read.
- Pipelines that use both will still carry the marking on derived data, as intended.
Example: only the HR project is closed; country codes become usable by everybody again.
W: Separate the salary data: the marking protects only what needs it and the reference data is available to all.
X: A=Copies of the codes: duplicates data and creates maintenance work without addressing the structure.
B=Marking removed: relying on roles drops the mandatory control that protected the salary data.
C=Everyone in the marking: defeats the purpose and exposes salaries to all.
T: Group resources of equal sensitivity into a project so a marking affects only what needs it.
V: Projects, markings

@ PLTR-DE D6 T6.3 applied comparison
S: An Ontology object type holds employees. Managers should see only their own department's employees, and the `salary` property must additionally be visible only to HR. Which design fits the Ontology?
A: An object security policy for the department rows and a property security policy covering salary
B: A restricted view on the backing dataset, because one policy there covers both rows and columns
C: One property security policy only, since it also decides which rows each manager can see
D: A separate dataset per department, each with its own copy of the salary column
K: A
G: ## Policies on object types
Object security policies configure which object instances a user can see, giving row-level security independent of the backing dataset's permissions. Property security policies guard selected properties and give column-level security.
## How they combine
- By default an object policy applies to all properties.
- When a property policy covers a property, the user must pass both policies to see its value.
- Together they give cell-level control.
The docs recommend object security policies over restricted views for most Ontology use cases because they give unified cell-level security, near-instant policy updates, and support for streaming and branching.
Example: a manager passes the department rule but not the HR rule, so the salary cell stays hidden.
W: Object plus property security policies: rows are filtered by department and the salary property needs an extra HR condition.
X: B=Restricted view: its policy decides which rows a user can see, so it does not give a separate column-level policy for salary, and the docs recommend object security policies for Ontology use.
C=Property policy alone: it guards values of properties, while row visibility comes from the object policy.
D=Per-department datasets: multiplies copies and still leaves salary visibility unsolved.
T: Use object security for rows and property security for columns on Ontology object types.
V: Ontology, object security

@ PLTR-DE D6 T6.3 applied troubleshooting
S: A team protects a sales table with a restricted view that shows each rep only their region. An engineer with access to the backing dataset builds a pipeline that copies it into a new dataset in a shared project, and the new dataset is visible to the whole team. Why did the row restriction not follow the data?
A: The restricted view was misconfigured and every restricted view leaks rows into pipelines that it feeds
B: Granular policies on a restricted view are discretionary and do not propagate to data derived from the backing dataset
C: The pipeline's build identity bypasses all permissions, so what it writes loses inherited markings
D: Restricted views stop working as soon as two or more users have access to the same backing dataset
K: B
G: ## Which controls travel with data
Markings are mandatory and propagate through transforms. Granular policies on restricted views are discretionary and do not propagate to derived data.
## Implication
- A restricted view controls who sees which rows when reading through the view.
- A copy made from the backing dataset is a separate dataset governed by its own project roles and markings.
- To protect the backing data wherever it goes, restrict access to the backing dataset itself, and apply markings when the sensitivity must follow derived data.
Example: marking the backing dataset means the copy inherits the marking and the broad team loses access.
W: Discretionary, non-propagating policy: the row filter applies to reads through the view only, so derived data needs its own protection such as markings.
X: A=Misconfiguration: the view works as designed for reads through it; propagation is simply not part of it.
C=Identity bypass: markings propagate through transform logic regardless of who builds.
D=Multiple users: the number of users with backing access does not disable a view.
T: Row filters on restricted views do not propagate; protect derived data with markings.
V: restricted views, markings

@ PLTR-DE D6 T6.4 applied troubleshooting
S: A project-scoped schedule has run reliably for months. The engineer who created an older, user-scoped schedule on a sister pipeline moved to another team and lost access to that project. Since then that schedule's builds fail with permission errors although nothing else changed. What is the best fix?
A: Give the engineer back access to the project so that the user-scoped schedule can run as before
B: Recreate the schedule scoped to the project so it no longer depends on any individual's permissions
C: Add the builds to a daily manual checklist so someone runs them in the engineer's place
D: Pause the schedule indefinitely, because permission errors in a schedule cannot be solved
K: B
G: ## Schedule scope and permissions
A schedule can be saved in user mode, where it runs as if that user ran the build, or in project-scoped mode, where it depends on the set of projects containing the datasets it builds.
## Why it matters
- User mode is prone to unexpected changes when the user's permissions change.
- Project-scoped mode is more consistent and independent of one user's permissions.
- Saving a schedule scoped to the project removes the personal dependency.
Example: when the engineer left, the user-scoped schedule lost the rights it needed; the project-scoped one kept running.
W: Project-scoped schedule: the schedule is independent of any user's permissions, so staff moves no longer break it.
X: A=Restoring the old access: keeps a person who left the team tied to the pipeline and repeats the risk.
C=Manual checklist: replaces automation with a process that can be forgotten.
D=Pause indefinitely: the cause is fixable, and pausing stops fresh data.
T: Prefer project-scoped schedules so builds do not depend on one person's access.
V: Schedules, Projects
