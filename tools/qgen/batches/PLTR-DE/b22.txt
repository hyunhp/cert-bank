# PLTR-DE batch 22: Domain 5 round 3 (Data Quality and Health Monitoring), 8 questions

@ PLTR-DE D5 T5.1 applied use-case
S: A dataset must never contain rows where `end_date` is before `start_date`. Such rows have appeared twice from a source bug. Which control is appropriate?
A: A health check that counts such rows after each build and alerts the owner so they can fix them in the source eventually
B: A build-blocking expectation asserting `end_date >= start_date` for every row, since a violation must never be published
C: A transform that swaps the two dates when they are reversed, which corrects the source bug automatically
D: A note in the dataset description warning consumers that date ordering is not guaranteed
K: B
G: ## Always-true rules are expectations
The exam guide asks you to use expectations to stop invalid transactions when correctness matters. "Never" plus a rule that has no legitimate exception is the clearest case for a build-blocking expectation.
## Why block, not alert
- Consumers would receive invalid rows between the alert and the fix.
- The source bug is surfaced immediately, at the build, with the failing rows identified.
Example: the third occurrence fails the build at 02:10, the on-call engineer sees 14 rows, and the source team fixes the job before any consumer is affected.
W: Build-blocking expectation on the date rule: the invariant is enforced and invalid data never reaches consumers.
X: A=Alert after publishing: invalid rows are already visible to consumers until someone acts.
C=Auto-swap: guessing which date is wrong fabricates data and hides the source bug.
D=Warning note: a disclaimer is not a control; the requirement says never.
T: Encode invariants with no legitimate exception as build-blocking expectations.
V: expectations

@ PLTR-DE D5 T5.3 applied troubleshooting
S: A content health check on null rate started alerting daily after a new, legitimately optional column was added to the dataset. What should be done?
A: Remove the null-rate check entirely, since it clearly cannot handle datasets that contain optional columns alongside required ones
B: Scope the check to columns where nulls matter, with column-specific thresholds, and document that the new column is optional
C: Fill the optional column with empty strings so that the null rate drops back below the threshold
D: Ignore the alerts, since everyone knows the new column is optional
K: B
G: ## Checks must match the contract
A null-rate check across all columns assumes nulls are always bad. The exam guide asks you to design checks that reflect the data contract and to keep alerts actionable.
## Adjustment
- Column-level thresholds: required columns at 0%, optional columns exempt or at a sensible level.
- Documentation: the contract states which columns may be null.
- Review other checks that may have the same blind assumption.
Example: the check now watches `customer_id` and `amount` for nulls and ignores `notes`; alerts stop while protection remains.
W: Scoped, column-specific checks with documentation: the monitor reflects the real contract and stops crying wolf.
X: A=Remove: required columns such as keys lose their null monitoring, so a real source defect would go undetected.
C=Empty strings: corrupts the data (empty is not the same as absent) to satisfy a monitor.
D=Ignore: an alert that fires daily and is ignored trains the team to ignore the channel, so a genuine null surge in a required column is missed.
T: Configure quality checks per column according to the contract; optional columns are allowed nulls.
V: Data Health

@ PLTR-DE D5 T5.2 applied tradeoff
S: An expectation on a referential rule (every order's `customer_id` must exist in the customers dataset) fails whenever the customer feed lags the order feed by a few hours. Orders are legitimate and the customers arrive later. What is a sound design?
A: Remove the referential expectation, since timing differences make it impossible to enforce
B: Keep the rule on the published dataset; stage orders whose customers have not arrived in a pending dataset, and sequence customers first
C: Drop the orders whose customers have not arrived yet, since the pipeline cannot publish invalid data and those orders can be re-sent
D: Insert placeholder customers for the missing ids so the expectation passes
K: B
G: ## Referential integrity with feed timing
The exam guide asks for data contracts that handle late data and for expectations where correctness matters. The rule is valid; the schedule and staging must accommodate arrival order.
## Design
- Sequence: build customers before orders, triggered on the customer feed.
- Staging: orders without a customer go to `orders_pending` with a status; a later run promotes them.
- Expectation on the published dataset stays strict; a health check watches the pending backlog.
Example: 300 orders wait in pending for two hours, then publish once their customers land; the curated dataset never contains orphans.
W: Sequencing plus a pending stage with a strict expectation on the published output: integrity is preserved and legitimate late data is not lost.
X: A=Remove the rule: orphan orders would reach the Ontology and applications, breaking links and reports that assume every order has a customer.
C=Drop the orders: legitimate orders are lost from the curated dataset; the data was correct, only early, and nothing guarantees it is re-sent.
D=Placeholder customers: fabricated entities corrupt the customer dataset.
T: Keep referential expectations strict on published data; handle feed timing with sequencing and staging.
V: expectations, schedules

@ PLTR-DE D5 T5.3 applied use-case
S: A dataset's schema health check fired because a new column was added by the upstream team as planned. The team wants future planned additions not to alert but unexpected changes still to. What should they configure?
A: Disable the schema check, since planned changes are now common and the alerts are no longer useful
B: Alert on removed or retyped columns while allowing additive ones, and update the expected schema for planned changes as part of release
C: Have the upstream team stop adding columns altogether, since schema stability for consumers is more important than any new fields
D: Set the check to alert only once a month so that planned changes are batched
K: B
G: ## Distinguishing breaking from additive
The exam guide asks you to classify schema changes as additive or breaking and to design alerts accordingly. A schema check can be as precise as the contract.
## Configuration
- Alert on: column removal, type change, rename.
- Allow: additive columns (optionally alert at low severity).
- Process: planned changes update the expected schema as part of release, so the check reflects the new contract.
Example: the next additive column is added with a schema update in the same release; the check stays quiet; a later accidental type change still fires.
W: Breaking-only alerts with a release process for planned changes: unexpected changes are caught and planned ones are routine.
X: A=Disable: a dropped or retyped column, the kind of change that breaks consumers, would then go unnoticed until something fails.
C=Freeze the schema: additive evolution is normal and healthy.
D=Monthly: batching the check means a breaking change could go unnoticed for weeks while consumers are affected.
T: Alert on breaking schema changes and absorb planned additive changes through the release process.
V: Data Health

@ PLTR-DE D5 T5.1 applied use-case
S: A business rule states that order amounts must be positive except for refunds, and that refund amounts must not exceed the original order's amount. Which combination enforces these?
A: Two health checks that alert when violations appear in the published dataset
B: A row-level expectation for the sign rule, plus a transform-computed cross-row flag (refund vs original) with an expectation that it is never true
C: A single expectation that the total of all refunds is less than the total of all orders across the whole dataset, checked on every build
D: Documentation of the rules in the dataset description for consumers to verify themselves
K: B
G: ## Row-level and cross-row rules
Some rules concern one row; others relate rows. The exam guide asks you to use expectations for correctness and to compute what a check needs in the transform.
## Implementation
- Row-level: `amount > 0 OR order_type = 'refund'`, `amount < 0 OR order_type != 'refund'` (as fits the model).
- Cross-row: a transform joins refunds to their originals and computes `refund_exceeds_original`; an expectation asserts the flag is never true.
- Both build-blocking; both documented.
Example: a refund of 150 against an order of 120 sets the flag; the build fails and the source team investigates.
W: Row-level expectation plus a computed cross-row flag with its own expectation: both rules are enforced at build time.
X: A=Alerts only: violating rows are published to the Ontology before anyone reacts; the rules say they must not be.
C=Aggregate comparison: totals can balance while individual refunds exceed their originals.
D=Documentation: a description tells consumers what should be true; it does not check anything or stop a bad build.
T: Enforce cross-row rules by computing a violation flag in the transform and asserting on it with an expectation.
V: expectations, Code Repositories

@ PLTR-DE D5 T5.3 applied troubleshooting
S: Freshness alerts for a dataset fire every Monday morning because the source does not deliver on weekends. What is the right change?
A: Disable the freshness check on Mondays, which is the only day it fires
B: Set the freshness threshold to the source's real delivery calendar (a longer window over weekends, or a schedule-aware check)
C: Ask the source to deliver on weekends so the check can stay as it is
D: Replace the freshness check with a build-status check, which does not care about delivery days and therefore cannot fire on Monday mornings
K: B
G: ## Calendar-aware freshness
The exam guide asks for alerts that reflect genuine lateness. A source with a business-day cadence needs a check that understands it.
## Configuration
- Threshold: 26 hours on weekdays, 74 hours spanning the weekend (or a check that evaluates against expected delivery times).
- Document the delivery calendar on the dataset.
Example: the Monday alert stops; a Wednesday delivery failure still fires within hours.
W: Calendar-aware threshold: the check models the source's real cadence and alerts only on actual lateness.
X: A=Disable on Mondays: a genuine Monday failure would be missed, and the window is still wrong.
C=Change the source: the source's cadence is a business fact to model, not a bug.
D=Build-status instead: a missing delivery is not a failed build; the staleness would be invisible.
T: Model the source's delivery calendar in freshness thresholds.

@ PLTR-DE D5 T5.2 applied use-case
S: An expectation failure blocks a build at night, and the on-call engineer confirms the data is wrong at the source. The business asks for the dashboard to be updated anyway. What is the right response?
A: Override the expectation and publish the new data, since the business asked for it explicitly and they are the owners of the dashboard
B: Keep the previous good data published, explain that known-bad data would mislead, escalate to the source owner, publish after the fix
C: Delete the bad rows and publish the rest without telling anyone
D: Publish the bad data with a note in the dashboard title saying it may be wrong
K: B
G: ## Known-bad data does not get published
The exam guide asks you to investigate failures without allowing known-bad data to reach consumers. The expectation did its job; the previous good transaction is still what the dashboard shows.
## Response
- Communicate: the dashboard shows the last correct data; the delay is the source problem.
- Escalate to the source owner with the evidence.
- Publish after the fix; consider partial publication only with the owner's explicit decision and clear labelling.
Example: finance sees yesterday's correct figures with a banner noting the delay; the corrected feed arrives at noon and the build passes.
W: Hold the good data, escalate, publish after the fix: this protects decision-makers from wrong numbers while keeping them informed.
X: A=Override: publishes numbers known to be wrong into executive decisions.
C=Silent deletion: hides a data problem and misrepresents completeness.
D=Publish with a disclaimer: a caveat does not stop wrong numbers from being used.
T: When an expectation catches bad source data, keep the last good version published and escalate; never override.
V: expectations

@ PLTR-DE D5 T5.3 advanced use-case
S: A team wants to detect subtle corruption where values are present and typed correctly but wrong (for example, a currency conversion applied twice). Which monitoring approach can catch this?
A: Schema checks, since any corruption of the values would also change the data types of the affected columns in a detectable way
B: Statistical content checks (amount distribution, ratios between related columns, reconciliation against a source total) with alerts
C: Build-status checks, since corrupt transforms fail to build
D: Row-count checks, since corruption usually changes the number of rows
K: B
G: ## Catching semantic corruption
Semantic errors leave schema, counts and build status untouched. The exam guide warns that a successful run can still produce incorrect data and asks for content checks and reconciliation.
## Approaches
- Distribution monitoring: mean and percentiles of `amount` versus history.
- Relationship checks: `amount_eur / amount_usd` within the plausible rate band.
- Reconciliation: dataset totals versus a source-provided control total; mismatch alerts.
Example: a double conversion drops the mean amount by 10%; the distribution alert fires, and the reconciliation against the source total confirms the defect.
W: Statistical and reconciliation content checks: they see wrongness that structural checks cannot.
X: A=Schema: a doubled conversion produces a perfectly valid number of the same type; schema checks see nothing.
C=Build status: the transform built successfully and committed its transaction; the defect is in the values, not the run.
D=Row count: every row is still present with a wrong amount; the count is identical to a correct build.
T: Detect semantic corruption with statistical content checks and reconciliation against independent totals.
V: Data Health
