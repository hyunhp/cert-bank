# PLTR-DE batch 21: Domain 4 round 3 (Pipeline Operations and Scheduling), 8 questions

@ PLTR-DE D4 T4.1 applied use-case
S: A dataset is rebuilt by its schedule even on days when its only input has not changed, wasting compute. Which schedule setting addresses this?
A: Moving the schedule to a later hour so that the input is more likely to have changed by the time the build runs each day
B: Configuring the schedule to build only when the input has a new transaction since the last successful build
C: Reducing the dataset's executor size so that the unnecessary builds at least cost less compute than before
D: Removing the schedule and asking the consuming team to trigger a build manually whenever they need fresh data
K: B
G: ## Build only on change
The exam guide asks for schedules that avoid unnecessary builds. A condition on input updates is the standard mechanism: no new input transaction, no build.
## Configuration
- Trigger: input dataset updated.
- Or a timer with a condition "inputs changed since last build".
- Health check on freshness so that a stuck input is still noticed.
Example: the dataset built 30 times last month instead of 31 because one day the source did not deliver; compute fell on all the days the input was unchanged.
W: Build-on-input-update condition: it removes exactly the wasted builds while keeping the dataset current.
X: A=Later hour: still builds daily whether or not the input changed.
C=Smaller executors: the unnecessary builds still run every day; making each one cheaper does not remove the waste, and it slows the useful builds.
D=Manual triggers: unreliable and unnecessary when the platform can react to input changes.
T: Condition schedules on input changes so unchanged inputs do not trigger builds.
V: schedules

@ PLTR-DE D4 T4.2 applied troubleshooting
S: A build failed and the error message says a column referenced by the transform does not exist in the input. The transform's code has not changed. What should the engineer check first?
A: The transform's code for typos in column names, since a missing column error almost always means a mistake in the column reference
B: The input's latest schema against the previous transaction, since an upstream rename or drop is likely with unchanged code
C: The executor memory, since schema errors are sometimes a symptom of running out of memory during parsing
D: The schedule, since a column may be missing if the build ran before the input finished writing
K: B
G: ## Unchanged code, changed input
The exam guide's playbook says to compare the current input and schema with the last known-good run. A column that existed yesterday and is gone today points upstream.
## Checks
- Schema of the input's latest transaction versus the previous: renamed, dropped, or retyped column.
- Lineage: which upstream transform or source changed.
- Classify: breaking change; coordinate with the upstream owner; restore the column or adapt the transform deliberately.
Example: the source team renamed `cust_id` to `customer_id`; the schema diff shows it immediately.
W: Input schema comparison with the last good run: it finds the upstream change that the unchanged code cannot have caused.
X: A=Typos: the code worked yesterday; a typo would have failed from the start.
C=Memory: memory errors do not manifest as "column does not exist".
D=Schedule race: an incomplete transaction is not visible to a build; a missing column is a schema change, not timing.
T: A "missing column" failure with unchanged code means the input's schema changed; compare schemas with the last good run.
V: Data Lineage, builds

@ PLTR-DE D4 T4.3 applied use-case
S: An on-call engineer receives an alert that a critical dataset's build failed at 03:00. Which sequence matches the troubleshooting playbook?
A: Immediately force-rebuild the dataset, and if that fails, force-rebuild all of its upstream datasets as well
B: Read the symptom, find the first failing stage via lineage and logs, classify it, repair minimally, rebuild, verify
C: Escalate to the data owner and wait for the morning, since builds that fail at night are usually fixed by the next scheduled run
D: Roll back the transform's code to last week's version, since recent code changes are the most common cause of failures
K: B
G: ## The playbook
The exam guide's troubleshooting playbook: state the symptom, find the first bad stage, separate data from code failure, check permissions, assess blast radius, choose the smallest safe repair, verify.
## In practice
- Error message and build logs identify the stage and type.
- Lineage: is an upstream input missing or stale?
- Classification drives the fix: data (fix at source), code (fix on a branch), resource (adjust), permission (grant specifically).
- Rebuild and verify counts, freshness and downstream.
Example: the log shows an upstream sync produced an empty file; the sync is rerun, the build passes, and the dashboard is verified.
W: Diagnose, classify, repair minimally, verify: the structured response the guide prescribes.
X: A=Force-rebuild everything: no diagnosis; may reprocess history for nothing and will fail again if the cause remains.
C=Wait until morning: a critical dataset is down; the next run will fail the same way.
D=Blind rollback: the code may be fine; rolling back can introduce a different regression.
T: Follow the playbook: symptom, first bad stage, classification, smallest safe repair, verification.
V: builds, Data Lineage

@ PLTR-DE D4 T4.4 applied use-case
S: A team wants to be able to restore a dataset to yesterday's state quickly if a bad build publishes wrong data. What capability should they rely on?
A: A nightly manual export of the dataset to a file share so that it can be re-uploaded if needed
B: The dataset's transaction history: earlier transactions remain available, so it can be restored and downstream rebuilt
C: A duplicate copy of the dataset maintained by a second, identical pipeline that runs one day behind the first so yesterday's state always exists
D: Nothing, since once a build publishes, the previous data is gone and cannot be recovered
K: B
G: ## Transactions as versions
A dataset's transactions are its history. The exam guide treats reruns, backfills and restoring a compatible version as standard repairs.
## Practice
- Identify the last good transaction.
- Restore or branch from it; rebuild consumers from the restored state.
- Fix the cause before resuming the schedule.
- Add an expectation that would have caught the bad build.
Example: the bad transaction from 02:00 is superseded by a restore to the 02:00-of-yesterday transaction; the dashboard is correct within minutes.
W: Transaction history: versions are already kept, so restoration is a platform capability rather than an external backup.
X: A=Manual export: a nightly file copy is slow to restore, easy to get wrong, and unnecessary when the platform keeps transaction history.
C=Lagging duplicate: double cost for something the transaction history already provides.
D=Gone: previous transactions are retained in the dataset's history; a bad build does not erase what came before it.
T: Use dataset transaction history to restore a known-good version after a bad build.
V: transactions, builds

@ PLTR-DE D4 T4.3 applied troubleshooting
S: A build fails with a permission error reading a dataset that it read successfully yesterday. No permissions were intentionally changed. What should be investigated?
A: Whether the transform code was modified to reference a different dataset, since permission errors are usually caused by code changes
B: Whether a marking was newly applied upstream or the build identity's group membership changed, using Check Access to pinpoint the requirement
C: Whether the dataset was deleted and recreated, which resets the file paths and causes permission errors
D: Whether the cluster was restarted overnight, which temporarily revokes build permissions
K: B
G: ## New permission failures
The exam guide asks you to diagnose access failures with Check Access and lineage. Something changed; the likely candidates are a new marking flowing from upstream or a change to the identity's memberships.
## Investigation
- Check Access for the build identity on the input: which requirement fails now?
- Lineage upstream: did an input gain a marking yesterday?
- Identity: was the build identity removed from a group?
- Grant the specific requirement or route the pipeline to unmarked data if appropriate.
Example: an upstream team marked a source as PII; the marking propagated and the build identity lacks it; the identity is added after approval.
W: New marking or membership change, pinpointed with Check Access: the only things that make a read fail today that worked yesterday.
X: A=Code change: the transform's code is unchanged and still references the same dataset, so a code edit cannot explain a new permission failure.
C=Delete and recreate: would show as not found, not permission denied.
D=Cluster restart: permissions are not affected by compute restarts.
T: When reads start failing on permissions, look for new markings upstream or identity changes with Check Access.
V: Check Access, markings

@ PLTR-DE D4 T4.1 applied tradeoff
S: Two independent pipelines read the same large input and both run at 02:00, competing for compute and slowing each other down. Both must finish by 06:00. What is a reasonable scheduling adjustment?
A: Schedule both at 00:00 so that they have more time before the deadline, even though they will still compete with each other for compute
B: Stagger or sequence them (one triggered on the other's completion, or a different time) so they do not contend, and verify the window
C: Give both pipelines the maximum executor count so that each gets as much compute as possible
D: Merge the two pipelines into one transform so that only one job runs
K: B
G: ## Avoiding contention
Scheduling is also about shared resources. The exam guide asks for operational management of resource usage and cost.
## Adjustment
- Sequence: pipeline B triggers when A completes, or shift one to 03:00.
- Verify: both complete before 06:00 with margin.
- Monitor: durations over time so a growing input is noticed before the window is missed.
Example: A runs 02:00-03:10, B runs 03:15-04:20; both finish faster than when they overlapped.
W: Staggered or sequenced scheduling with verification: contention disappears and the deadline is still met.
X: A=Both earlier: moving both to 00:00 keeps them running at the same time, so the contention and the slowdown are unchanged.
C=Max executors for both: they contend for the same pool; cost rises and the slowdown may remain.
D=Merge: couples two unrelated pipelines; a failure in one breaks both.
T: Spread independent heavy jobs across time rather than letting them contend.
V: schedules

@ PLTR-DE D4 T4.4 applied use-case
S: A pipeline must be modified by a contractor who should not be able to merge changes into production without review. How should repository permissions and workflow be set?
A: Give the contractor full edit rights on the main branch and trust them to request a review before merging
B: Let the contractor create branches and pull requests, require a team member's approval before merging, and restrict direct writes to main
C: Give the contractor no repository access at all and have them send code changes by email for a team member to paste in and commit
D: Let the contractor work directly on main during a scheduled window when the team is watching
K: B
G: ## Branch protection and review
The exam guide lists branch and release management among operational responsibilities. Branches with protected main and required review are the standard control.
## Setup
- Contractor: branch creation and pull requests.
- Main: protected; merges require approval from an owner.
- Branch builds for validation before review.
Example: the contractor's change is reviewed, validated on a branch and merged by the owner, with history showing who did what.
W: Branch-based contribution with protected main and required review: contributions are possible and controlled.
X: A=Trust: not a control; an accidental merge is one click away.
C=Email patches: unworkable and loses the branch build and review workflow.
D=Watched window: watching is not review; the change still lands untested.
T: Protect main and require reviewed pull requests for contributors who must not release unilaterally.
V: Code Repositories, branches

@ PLTR-DE D4 T4.2 advanced troubleshooting
S: A dataset's build succeeds but takes twice as long every Monday. Spark details show the Monday runs read many more input files. What is the cause and the fix?
A: Monday builds are slower because the cluster is busy catching up after the weekend; the fix is to move the build to Tuesday morning
B: The weekend's incremental syncs accumulate many small files the Monday build must read; compact the input and write larger files
C: The transform has a bug that only triggers on Mondays; the fix is to add a day-of-week condition to the code
D: Monday data is larger; nothing can be done except accepting the longer build
K: B
G: ## File count as a performance driver
Reading many small files costs more than reading few large ones with the same total size. The exam guide names small-file accumulation and asks you to use Spark details as evidence.
## Fix
- Compaction: a scheduled step that rewrites accumulated small files into larger ones (for example, Sunday night).
- Sync configuration: fewer, larger files per run where possible.
- Monitor input file counts as a metric.
Example: after a Sunday compaction, the Monday build reads 40 files instead of 4,000 and runs as fast as any other day.
W: Small-file accumulation over the weekend, fixed by compaction: it matches the evidence (more files, same logic) exactly.
X: A=Busy cluster: Spark details show the Monday runs reading far more input files, not waiting for resources; the evidence points at file count.
C=Monday-only bug: the logic is the same; the input shape differs.
D=Accept: the file count is a controllable property of the input; compaction removes the Monday penalty entirely.
T: When builds slow with file count, compact inputs; file count is a performance variable.
V: Spark Details, datasets
