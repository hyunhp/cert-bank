# PLTR-DE batch 13: Domain 4 round 2 (Pipeline Operations and Scheduling), 8 questions

@ PLTR-DE D4 T4.2 applied troubleshooting
S: A dataset consumer reports that a value changed unexpectedly between yesterday and today. The data engineer wants to find which transform in a twelve-step pipeline introduced the change. Which tool and approach are right?
A: Rebuild the entire twelve-step pipeline from the top with force and check whether the value changes back to yesterday's figure
B: Walk upstream with Data Lineage, comparing the key's value in each intermediate dataset across the two builds, to the first stage that differs
C: Ask every transform owner to check their code for bugs
D: Compare the two builds' Spark details for all twelve transforms and treat whichever transform ran noticeably longer today as the one that changed the value
K: B
G: ## Tracing to the first bad stage with lineage
The exam guide asks you to find the first bad stage using lineage and intermediate evidence. A pipeline is a graph; for a specific key, each intermediate dataset can be checked for the value in both builds.
## Method
- Start at the output; confirm the change.
- Step upstream one dataset at a time (Data Lineage shows the graph); check the key's value in yesterday's and today's transaction.
- The first dataset where the values diverge is where to look: its inputs changed (source) or its code did (deployment).
- Fix at that stage; downstream will follow on rebuild.
Example: the divergence is at step 4, whose input sync received a corrected source row; the change is legitimate, and consumers are told.
W: Lineage-guided bisection over intermediate datasets: it finds the first stage where the value differs instead of guessing across twelve transforms.
X: A=Rebuild and watch: the inputs are the same, so the value does not change back, and nothing is learned.
C=Ask everyone: twelve owners reading code is slow and ignores the evidence available in the datasets.
D=Longer run time: duration does not indicate which transform changed a value.
T: Use lineage to bisect a value change through intermediate datasets to the first stage that differs.
V: Data Lineage

@ PLTR-DE D4 T4.1 applied use-case
S: A pipeline must run once a day but must not start before 03:00, and must also wait for its input to be updated that day. How should the schedule be expressed?
A: A time trigger at 03:00 only, assuming the input is always updated by then
B: One schedule combining both conditions: triggered by the input update, with the build not starting before 03:00
C: A time trigger every hour from 03:00 that force-builds regardless of the input
D: Two independent schedules on the same dataset, one firing at 03:00 and one firing on each input update, so whichever condition is met first builds
K: B
G: ## Combining time and event conditions
Schedules can combine triggers and conditions: a time window and an input-update requirement. The exam guide asks you to configure schedules and triggers without unnecessary builds.
## Design
- Condition 1: the input dataset has a new transaction since the last successful build.
- Condition 2: current time is at or after 03:00.
- Result: exactly one build per day when both hold; no build on a day the input never updates; no build before 03:00.
Example: the input lands at 02:20; the build starts at 03:00. The next day the input lands at 04:10; the build starts at 04:10.
W: Time floor plus input-update condition: it encodes both requirements and produces one build per day at the right moment.
X: A=03:00 only: on a day the input is late, the build runs on stale data.
C=Hourly force-builds: many unnecessary builds and no guarantee the input was fresh at any of them.
D=Two independent schedules: up to two builds a day, one possibly before 03:00.
T: Express compound scheduling requirements as combined trigger conditions, not as multiple schedules.
V: schedules

@ PLTR-DE D4 T4.3 applied troubleshooting
S: A build fails with a Spark error indicating a single task failed repeatedly with a serialization exception on a particular input file. Other tasks succeed. What classification and action are appropriate?
A: Resource limit; add more executors
B: A data problem in one input file; inspect it, quarantine or correct it at the source, and add validation so a bad file fails clearly
C: Upstream cascade; rebuild the upstream dataset
D: Permission failure on that file; grant the build identity broader access to the input dataset's project so every task can read every file
K: B
G: ## Classifying a failure from its evidence
The exam guide asks you to distinguish code-level inefficiency, data skew, resource limits, permission failures and upstream cascades. A repeated failure of one task on one file with a parsing or serialization error points to the data in that file.
## Action
- Identify the file from the task error.
- Inspect it: encoding, truncated content, unexpected format.
- Fix at the source or quarantine the file; rerun.
- Add validation that detects malformed files early with a clear error.
Example: a partially uploaded file from the source; the sync is configured to skip files still being written, and the file is re-sent.
W: Data-level problem in one file, fixed at source with validation added: the evidence (one task, one file, serialization error) points there directly.
X: A=More executors: the task fails on content, not capacity; it will fail on any executor.
C=Upstream rebuild: the upstream file is corrupt; rebuilding downstream does not fix it.
D=Permissions: a permission failure would prevent reading the file at all, not fail during parsing.
T: A single task failing on one file is a data problem; inspect the file, fix at source, add validation.
V: Spark Details, Data Connection

@ PLTR-DE D4 T4.4 applied use-case
S: Two engineers are working on different changes to the same pipeline. One change is urgent; the other is a large refactor that will take weeks. How should branches and releases be managed?
A: Both edit the main branch, coordinating by chat to avoid conflicts
B: Separate branches; the urgent fix is validated, reviewed and merged first; the refactor branch stays synchronized with main and merges when complete
C: The refactor is paused until the urgent fix is finished and released, after which both engineers work on the main branch one after the other
D: The urgent fix is applied directly in production and the refactor branch ignores it
K: B
G: ## Branching for parallel work
The exam guide treats branch and release management as an operational responsibility. Branches isolate changes; each is validated independently and merged when ready.
## Practice
- Short-lived branch for the urgent fix: build, compare, review, merge, release.
- Long-lived branch for the refactor: periodically merge main into it so it does not diverge; validate on the branch; merge when complete.
- Branch builds use real inputs without touching production datasets.
Example: the fix ships on day one; the refactor absorbs it on day two via a merge from main and continues.
W: Independent branches with the fix merged first and the refactor kept current: both proceed safely without blocking each other.
X: A=Shared main: untested interleaved edits reach production; conflicts corrupt both changes.
C=Pause the refactor: unnecessary; branches exist so that work can continue in parallel.
D=Hotfix outside the branch flow: the refactor would later overwrite the fix, reintroducing the bug.
T: Use separate branches for parallel changes; merge the urgent one first and keep long branches synchronized with main.
V: Code Repositories, branches

@ PLTR-DE D4 T4.2 applied use-case
S: After an incident, the team wants to prevent a repeat of a pipeline that silently processed an empty input. Which operational safeguards should be added?
A: An email to the team asking everyone to be more careful
B: A build-blocking minimum-row-count expectation on the input, a Data Health size check with an alert to the owner, and a runbook entry
C: A nightly manual check of input sizes by the on-call engineer
D: Doubling the schedule frequency so that if an empty input is processed, the next build picks up the real data twice as quickly
K: B
G: ## Turning an incident into controls
The exam guide expects pipelines to be operated with expectations, health checks, alerts and documented diagnostics. "Silently processed an empty input" is a missing guard, not a people problem.
## Safeguards
- Expectation: input row count above a floor; the build fails before producing an empty output.
- Health check: input size anomaly alert, catching partial inputs too.
- Alert routing: the owner, with context.
- Runbook: steps to verify the source, rerun or escalate.
Example: the next time the source sends an empty file, the build stops at 02:05 and the owner is paged with a link to the runbook.
W: Expectation, health check, routed alert and runbook: these prevent the silent case and make the loud case actionable.
X: A=Be more careful: not a control; the next empty file arrives at 02:00 with nobody watching.
C=Manual nightly check: slow, unreliable and unnecessary when it can be automated.
D=Run more often: reprocessing an empty input faster produces the same empty output.
T: Convert incidents into expectations, health checks, alerts and runbooks.
V: expectations, Data Health

@ PLTR-DE D4 T4.3 applied troubleshooting
S: A pipeline that was fast became slow after the team added a new column computed by a Python UDF applied to every row of a 2 billion row dataset. Spark details show that stage dominating. What is the appropriate fix?
A: Accept the slowdown, since the column is required
B: Replace the row-wise Python UDF with native dataframe functions or a vectorized UDF so the computation stays inside the engine
C: Double the executor count to run the UDF faster
D: Move the UDF to run on the driver node after collecting the dataset, since the driver typically has more memory than any single executor
K: B
G: ## Code-level inefficiency
The exam guide names code-level inefficiency among the failure classes. Row-wise Python UDFs serialize data between the engine and Python for every row, which is very slow at billions of rows.
## Fix
- Express the computation with built-in functions (string, date, arithmetic, conditional).
- If a UDF is truly needed, use a vectorized (batch) UDF that processes arrays.
- Validate on a branch: same output, lower runtime.
Example: a date-difference UDF becomes a native `datediff`; the stage drops from 50 minutes to 2.
W: Native or vectorized computation: it removes the per-row Python overhead, which is the cause of the slowdown.
X: A=Accept: the requirement is the column, not the slow method of computing it.
C=More executors: parallelizing an inefficient per-row operation costs more and still scales badly.
D=Driver: collecting 2 billion rows onto one node fails outright with memory errors; the driver is not a place to run row-wise work on big data.
T: Avoid row-wise Python UDFs on large data; use native functions or vectorized UDFs.
V: Spark Details, Code Repositories

@ PLTR-DE D4 T4.1 applied tradeoff
S: A team asks for every dataset in their project to build every 10 minutes "so that nothing is ever stale". What should the data engineer recommend?
A: Agree to the request, since more frequent builds can only improve freshness and compute cost is a secondary concern compared with stale data
B: Schedule each dataset by its source cadence and consumer needs, with event-based triggers where inputs update unpredictably
C: Build everything once a week to minimize cost
D: Build every 10 minutes but only on weekdays
K: B
G: ## Freshness without waste
The exam guide asks for schedules without unnecessary builds, and treats cost as an operational responsibility. A 10-minute timer on a dataset whose source updates daily produces 143 builds a day that do nothing but cost money and clutter history.
## Recommendation
- Daily sources: daily builds after the source lands (event trigger).
- Hourly sources: hourly or event-triggered.
- Genuinely continuous needs: consider streaming rather than rapid batch.
- Document each dataset's expected freshness and monitor it with health checks.
Example: of 40 datasets, 35 move to event triggers, 5 stay hourly; cost falls by 90% and freshness is unchanged.
W: Cadence by source and consumer need with event triggers: freshness where it matters and no wasted builds.
X: A=Agree: most builds would process no new data; cost and noise rise for no gain.
C=Weekly: it ignores consumers that need daily or hourly data.
D=Weekdays only: still wasteful, and some sources update at weekends.
T: Schedule by data arrival and consumer need, not by a blanket rapid timer.
V: schedules

@ PLTR-DE D4 T4.4 advanced use-case
S: A pipeline change is ready on a branch and validated. The release will change a column's semantics that two downstream teams depend on. How should the release be executed?
A: Merge immediately, since the branch is validated; the two downstream teams will notice the change in their next builds and adapt their logic
B: Announce the change with a date, provide a transition period with both columns, merge at the agreed time, monitor downstream, keep rollback
C: Merge at night when nobody is watching to reduce complaints
D: Never change column semantics; create a new pipeline instead
K: B
G: ## Releasing breaking changes
The exam guide asks you to assess lineage and existing consumers before changing schemas or semantics and to plan non-disruptive changes. A semantic change is breaking even if the schema looks the same.
## Release plan
- Lineage: identify all consumers.
- Communication: what changes, when, what they must do.
- Transition: add the new column alongside the old for a period, or version the dataset.
- Release at the agreed time; watch consumer builds and health checks; rollback ready.
Example: `amount` becomes net of tax; for four weeks both `amount_gross` and `amount` exist, then the old one is removed after both teams confirm.
W: Communicate, transition, release at the agreed time with monitoring and rollback: consumers are not broken and the change still lands.
X: A=Merge and let them notice: both teams' outputs become wrong silently.
C=Night merge: it hides the change rather than managing it; the breakage is the same.
D=Never change: pipelines must evolve; the discipline is managed change, not a ban.
T: Breaking semantic changes need consumer communication, a transition period and a monitored release.
V: Data Lineage, branches
