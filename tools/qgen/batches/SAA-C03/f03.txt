@ SAA-C03 D3 T3.1 applied use-case
S: A financial services company runs a self-managed relational database on an EC2 instance that requires sustained 64,000 IOPS with sub-millisecond latency and 99.999% durability. Which EBS volume type should the solutions architect choose to meet this requirement?
A: io2 Block Express SSD
B: gp3 General Purpose SSD
C: sc1 Cold HDD
D: st1 Throughput Optimized HDD
K: A
G: ## Choosing an EBS volume type
EBS volume types fall into two groups:
- **SSD-backed** (`gp3`, `io2 Block Express`, `io1`) for random, small I/O such as databases, measured mainly in IOPS.
- **HDD-backed** (`st1`, `sc1`) for large sequential reads and writes such as logs or data warehouses, measured in MiB/s, with low IOPS.
## What makes io2 Block Express different
- **Durability**: io2 volumes are designed for 99.999% durability (an annual failure rate around 0.001%), compared with 99.8%-99.9% for gp3.
- **Performance**: io2 Block Express supports far more than 64,000 provisioned IOPS per volume with consistent sub-millisecond latency, which is why it is aimed at large, critical databases such as SAP HANA, Oracle or SQL Server.
- **Provisioned IOPS**: you set the IOPS you need, and the volume delivers it consistently.
Example: a 2 TiB io2 Block Express volume provisioned with 64,000 IOPS gives the database steady performance and the durability figure the requirement asks for.
W: io2 Block Express: it is the only option listed that meets the 99.999% durability requirement, and it delivers 64,000 sustained IOPS with sub-millisecond latency.
X: B=gp3: gp3 is a general-purpose SSD whose durability is designed at 99.8%-99.9%, so it fails the 99.999% durability requirement for this critical database.
C=sc1: Cold HDD is the cheapest type for infrequently accessed sequential data, with very low IOPS and high latency; it cannot come close to 64,000 IOPS.
D=st1: Throughput Optimized HDD is built for large sequential throughput, not the small random I/O of a relational database, and its IOPS and latency are far from the requirement.
T: When a requirement combines very high sustained IOPS, sub-millisecond latency and 99.999% durability, choose io2 Block Express; gp3's durability is lower and HDD types lack the IOPS.
V: Amazon EBS

@ SAA-C03 D4 T4.2 applied use-case
S: A global company wants to reduce the compute cost and latency of processing user image uploads for a website distributed through Amazon CloudFront by performing lightweight resizing logic closer to end users, instead of running dedicated servers in a central region. Which AWS service enables this?
A: Amazon EC2 Auto Scaling groups
B: AWS Batch jobs on AWS Fargate
C: Lambda@Edge or CloudFront Functions
D: EC2 instances in several AWS Local Zones
K: C
G: ## Running code at CloudFront
CloudFront offers two ways to run your code near viewers:
- **CloudFront Functions**: lightweight JavaScript at edge locations, sub-millisecond, for viewer request and viewer response events. Ideal for URL rewrites, header changes, redirects or choosing which image variant to fetch. No network calls and no access to the body.
- **Lambda@Edge**: Node.js or Python functions that run at regional edge caches for viewer and origin events, with more memory, longer run time and network access. This suits heavier work such as generating a resized image.
Both are serverless and billed per request and execution, so there are no central servers to run.
## Example
A CloudFront Function normalizes `/img/cat.jpg?w=300` to `/img/300/cat.jpg` so the cache key is consistent. On a cache miss, a Lambda@Edge origin-response function creates the 300-pixel version and returns it; later requests are served from the cache.
W: Lambda@Edge or CloudFront Functions: code runs at CloudFront locations close to users, removing the central servers and lowering latency; Functions handle the light request logic and Lambda@Edge the actual resizing.
X: A=EC2 Auto Scaling groups: they scale servers inside one Region, so requests still travel to that Region and the company keeps managing dedicated instances.
B=Batch jobs on Fargate: Batch schedules queued jobs in a Region; even without servers to manage, it does not execute per-request logic in the CloudFront path near users.
D=EC2 in Local Zones: Local Zones put compute closer to some metropolitan areas, but the company would still run and pay for dedicated instances in each zone, which is what it wants to avoid.
T: Per-request logic near users on a CloudFront site means CloudFront Functions or Lambda@Edge, not Regional compute.
V: Amazon CloudFront, AWS Lambda

@ SAA-C03 D2 T2.2 applied comparison +SOA-C03:D2
S: A company wants the lowest possible RTO and RPO and is willing to pay to run full production capacity simultaneously in two Regions, actively serving live traffic from both. Which DR strategy does this describe?
A: Multi-site active-active across Regions
B: Pilot light in a second Region
C: Backup and restore to a second Region
D: Warm standby in a second Region
K: A
G: ## Lowest RTO and RPO
**RTO** is how long recovery takes; **RPO** is how much recent data may be lost. The AWS DR strategies trade cost for lower RTO/RPO:
- **Backup and restore**: hours.
- **Pilot light**: tens of minutes (compute must be launched).
- **Warm standby**: minutes (running stack must scale up).
- **Multi-site active-active**: near zero. Both Regions run full production capacity and serve live traffic, with data replicated continuously (for example Aurora Global Database or DynamoDB global tables).
## How failover works in active-active
Route 53 (latency, weighted or health-checked records) or Global Accelerator spreads users across both Regions. If one Region fails, health checks remove it and the other Region, already at full size, keeps serving; there is nothing to launch or scale.
W: Multi-site active-active: full production capacity runs and serves traffic in both Regions at once, so a Region failure needs only traffic redirection, giving the lowest RTO and RPO at the highest cost.
X: B=Pilot light: application servers are not running in the DR Region, so they must be launched and the database promoted, which takes longer.
C=Backup and restore: infrastructure and data must be restored from backups after the event, the slowest option with the largest possible data loss.
D=Warm standby: the DR copy runs at reduced capacity and does not carry the full production load, so it must scale up before taking over.
T: Paying for full capacity in two Regions that both serve traffic = active-active, the only strategy with near-zero RTO and RPO.
