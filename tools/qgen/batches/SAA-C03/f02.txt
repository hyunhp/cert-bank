S: A company generates large volumes of log data in S3 that are frequently accessed for 30 days, rarely accessed for the next 60 days, and then must be retained for 7 years for compliance at the lowest possible cost, with retrieval times of several hours being acceptable. Which S3 feature should be used to automate this with no manual work?
A: S3 Transfer Acceleration for incoming log uploads
B: S3 Cross-Region Replication to a second bucket
C: Lifecycle rules to Standard-IA, then Deep Archive
D: S3 Requester Pays on the compliance log bucket
K: C
G: ## S3 Lifecycle transitions
An S3 Lifecycle configuration automatically moves objects between storage classes, or expires them, based on age.
- **S3 Standard**: frequent access, no retrieval fees.
- **S3 Standard-IA**: lower storage price, per-GB retrieval fee, 30-day minimum storage; good for data read rarely but needed quickly.
- **S3 Glacier Deep Archive**: the lowest storage price, 180-day minimum, retrieval within about 12 hours (standard) or up to 48 hours (bulk).
## Example for these logs
- Day 0-30: Standard.
- Day 30: transition to Standard-IA.
- Day 90: transition to Glacier Deep Archive.
- About day 2,555 (7 years): expire the objects.
Rules can be scoped by prefix, such as `logs/`, or by tag, so they run with no manual work.
W: Lifecycle rules to Standard-IA, then Glacier Deep Archive: they match each phase of declining access with the cheapest suitable class, and Deep Archive's hours-long retrieval is explicitly acceptable.
X: A=Transfer Acceleration: it speeds up uploads to S3 over long distances; it does not change storage classes or cost over time.
B=Cross-Region Replication: it copies objects to another bucket in another Region, which adds storage cost rather than lowering it, and does not move data between classes by age.
D=Requester Pays: it shifts request and data transfer charges to the requester; storage cost for the logs stays the same.
T: When access drops predictably with age and slow retrieval is fine, use S3 Lifecycle transitions ending in Glacier Deep Archive.
V: S3

@ SAA-C03 D3 T3.1 applied use-case
S: A company wants to extend on-premises storage to the cloud so that frequently accessed data is kept on local disks for low-latency access while the full data set is durably stored in Amazon S3, presented to on-premises applications as an iSCSI block device. Which AWS solution meets this requirement?
A: Storage Gateway S3 File Gateway with SMB shares
B: Storage Gateway Volume Gateway in cached mode
C: Storage Gateway Tape Gateway with a virtual library
D: AWS DataSync scheduled tasks into Amazon S3
K: B
G: ## The AWS Storage Gateway types
Storage Gateway is a VM or appliance on premises that connects local applications to AWS storage. Each type presents a different interface:
- **S3 File Gateway**: NFS or SMB file shares; each file becomes an S3 object.
- **Volume Gateway**: iSCSI block volumes that servers mount as disks.
- **Tape Gateway**: an iSCSI virtual tape library for existing backup software.
## Cached versus stored volumes
- **Cached volumes**: the primary copy of all data is in AWS (held in S3), and only frequently accessed data is cached on the local gateway disks. This lets you extend capacity beyond what you have on premises.
- **Stored volumes**: the full data set stays on premises, and it is backed up asynchronously to AWS as snapshots.
Example: a 20 TiB volume with a 2 TiB local cache; hot blocks are served locally with low latency, everything else is fetched from AWS on demand.
W: Volume Gateway in cached mode: it presents iSCSI block volumes to on-premises servers, keeps the full data set durably in AWS, and caches only the frequently accessed data locally for low latency.
X: A=S3 File Gateway with SMB shares: File Gateway presents NFS or SMB file shares, not iSCSI block devices, so applications that expect a block volume cannot use it.
C=Tape Gateway with a virtual library: although it uses iSCSI, it exposes virtual tape drives and a tape library for backup software, not a general-purpose block volume for live applications.
D=DataSync scheduled tasks: DataSync copies data between locations on a schedule; it provides no local cache and no iSCSI device that applications can read and write directly.
T: iSCSI block storage with the full data set in AWS and hot data cached locally is Volume Gateway in cached mode; stored mode keeps all data on premises instead.
V: AWS Storage Gateway, Amazon S3

@ SAA-C03 D2 T2.2 advanced tradeoff
S: A company compares pilot light and warm standby DR strategies. Which statement is correct?
A: Pilot light runs full production capacity in both Regions to serve traffic
B: Warm standby keeps backups in the second Region with no running servers
C: Warm standby runs a smaller live copy; it recovers faster but costs more
D: Pilot light recovers faster than warm standby and costs more to operate
K: C
G: ## The four AWS DR strategies
From cheapest and slowest to most expensive and fastest:
- **Backup and restore**: only backups in the recovery Region; everything is rebuilt after a disaster (RTO of hours).
- **Pilot light**: core data is replicated live (for example a database replica), but application servers are off or not yet created. Recovery means starting and scaling them (RTO of tens of minutes).
- **Warm standby**: a complete, working copy of the environment runs at reduced size. Recovery means scaling it up to full capacity (RTO of minutes).
- **Multi-site active/active**: full capacity in both Regions serving traffic (RTO near zero, highest cost).
## Pilot light versus warm standby
The difference is whether the application tier is already running. Warm standby can take some traffic immediately and only needs scaling, so it recovers faster, but it costs more because servers run all the time.
W: Warm standby runs a smaller live copy: the whole stack is already running at small size, so recovery is only scale-up, making it faster than pilot light and more expensive.
X: A=Pilot light runs full capacity: full production capacity in both Regions describes multi-site active/active; pilot light keeps only core components such as data running.
B=Warm standby keeps backups with no running servers: backups with no running resources is the backup and restore strategy; warm standby has running resources.
D=Pilot light faster and more expensive: it is the reverse; pilot light is cheaper because less runs, and slower because servers must be started and scaled.
T: Pilot light keeps only the core (data) running and is cheaper but slower; warm standby keeps a small full copy running and is faster but costs more.

@ SAA-C03 D3 T3.1 advanced use-case
S: A big data job runs every day and reads large files sequentially from block storage at a high rate of MiB per second, and cost matters. Which EBS type fits?
A: Cold HDD (sc1) volumes
B: Throughput Optimized HDD (st1)
C: General Purpose SSD (gp3) volumes
D: Provisioned IOPS SSD (io2) volumes
K: B
G: ## Throughput versus IOPS
- **IOPS** counts input/output operations per second and matters for many small random reads and writes, such as databases.
- **Throughput** measures megabytes per second and matters for large sequential reads, such as scanning log files or big data sets.
## The EBS HDD types
- **Throughput Optimized HDD (`st1`)**: low-cost HDD for **frequently accessed**, throughput-heavy sequential workloads such as big data, data warehouses and log processing; up to 500 MiB/s per volume.
- **Cold HDD (`sc1`)**: the lowest cost per GB, for **infrequently accessed** data; up to 250 MiB/s per volume with lower baseline throughput.
SSD types (`gp3`, `io2`) can also be fast, but you pay SSD prices per GB for performance a sequential job does not need.
W: Throughput Optimized HDD (st1): it is built for frequently accessed, large sequential reads at high throughput and costs much less per GB than SSD.
X: A=Cold HDD (sc1): it is meant for rarely accessed data; its lower baseline throughput makes a job that reads heavily every day slower than on st1.
C=General Purpose SSD (gp3): it works but costs more per GB than st1, and its strength is balanced IOPS rather than cheap sequential throughput for large data sets.
D=Provisioned IOPS SSD (io2): it is the most expensive type and pays for random IOPS that a sequential big data job does not use.
T: Large, frequent sequential reads at low cost means st1; sc1 is for cold data and SSD types pay for IOPS you do not need.
V: Amazon EBS
