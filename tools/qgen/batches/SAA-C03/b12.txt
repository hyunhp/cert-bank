@ SAA-C03 D3 T3.1 advanced use-case
S: A trading firm runs a self-managed PostgreSQL database on a Nitro-based EC2 instance. The data volume needs about 60,000 IOPS of 16 KiB random I/O, and the firm's latency budget requires an average I/O latency under 500 microseconds with as few slow outliers as possible. Data must persist through instance stops, and the database must sit on a single EBS volume to keep snapshots simple. Which storage choice meets the latency requirement?
A: A gp3 volume provisioned with 60,000 IOPS and 1,000 MiB/s of throughput, sized at 120 GiB or more to respect the 500 IOPS per GiB ratio
B: Four gp3 volumes of 15,000 IOPS each, striped together with RAID 0 in the operating system so that their IOPS add up on one device
C: An io2 Block Express volume provisioned with 60,000 IOPS, a type designed for sub-500-microsecond average latency on 16 KiB I/O
D: The NVMe instance store volumes of a storage-optimized instance, combined into one device and mounted as the database data directory
K: C
G: ## Two SSD families with different latency goals
Amazon EBS offers General Purpose SSD (`gp3`) and Provisioned IOPS SSD (`io2` Block Express). Both can now reach high IOPS, so the deciding factor is often **latency**, not IOPS.
- `gp3`: baseline 3,000 IOPS and 125 MiB/s, provisionable up to **80,000 IOPS** and **2,000 MiB/s** at 500 IOPS per GiB. It delivers **single-digit millisecond** latency.
- `io2` Block Express: up to **256,000 IOPS** and 4,000 MiB/s on Nitro instances, designed for an **average latency under 500 microseconds** for 16 KiB I/O, with far fewer outliers above 800 microseconds. AWS recommends it for latency-sensitive workloads.
## Persistence
EBS volumes keep their data when an instance stops. Instance store disks are physically attached to the host and lose data on stop or termination.
W: io2 Block Express: it meets the 60,000 IOPS on one volume and is the EBS type built for sub-millisecond average latency with fewer outliers, while keeping data across stops.
X: A=gp3 at 60,000 IOPS: the IOPS figure is within gp3 limits, but gp3 delivers single-digit millisecond latency, so it misses the 500-microsecond budget.
B=RAID 0 of gp3: striping adds IOPS but not lower per-I/O latency, and it breaks the single-volume requirement that keeps snapshots simple.
D=Instance store: local NVMe gives very low latency, but the data is lost when the instance stops, which violates the persistence requirement.
T: When the requirement is sub-millisecond average latency on EBS, choose io2 Block Express; gp3 can match the IOPS but not the latency.
V: Amazon EBS, Amazon EC2

@ SAA-C03 D3 T3.1 advanced troubleshooting
S: A media company's render farm mounts a 200 GiB Amazon EFS file system that uses Bursting throughput. For about 20 hours every day the farm reads and writes a steady 150 MiB/s, and CloudWatch shows BurstCreditBalance falling to zero by mid-morning, after which jobs crawl. The data set will not grow, and the team refuses to store padding files. Following AWS guidance for a known, steady requirement, which change restores throughput at the LOWEST cost?
A: Switch the file system to Elastic throughput, so that EFS scales throughput automatically and bills for each gigabyte of data and metadata read or written
B: Switch the file system to Provisioned throughput at 150 MiB/s, which delivers that rate regardless of the stored data size or burst credit balance
C: Write about 3 TiB of placeholder data into EFS Standard storage, so the Bursting baseline, which grows with stored data, rises to 150 MiB/s
D: Recreate the file system in the Max I/O performance mode, which is designed for highly parallel workloads with many clients reading at once
K: B
G: ## How EFS throughput modes work
- **Bursting**: baseline throughput is tied to storage in the Standard class, 50 KiB/s per GiB. A 200 GiB file system has only about 10 MiB/s of baseline. Credits accrue below baseline and are spent above it, so a steady 150 MiB/s drains them.
- **Elastic**: scales automatically and you pay per GB of data and metadata transferred. AWS recommends it for spiky or unpredictable workloads, or an average-to-peak ratio of **5% or less**.
- **Provisioned**: you set a throughput level that applies independently of size and credits, and you pay for the provisioned amount above the included baseline. AWS recommends it when you **know** the requirement or the average-to-peak ratio is **5% or more**.
## Reading the evidence
A zero BurstCreditBalance with a flat, high demand for 20 hours a day is the textbook case for Provisioned throughput.
W: Provisioned throughput: the workload is steady and known, which is exactly where AWS recommends Provisioned; it removes the dependency on credits without storing extra data.
X: A=Elastic throughput: it would fix the slowdown, but it targets spiky workloads with a low average-to-peak ratio; for a flat 150 MiB/s for 20 hours a day, paying per GB transferred is the costlier fit.
C=Placeholder data: 3 TiB at 50 MiB/s per TiB would lift the baseline, but the team ruled out padding files and would pay storage for useless data.
D=Max I/O mode: it is a previous-generation performance mode for parallel access with higher latency; it does not raise the throughput limit that the credits impose.
T: For EFS, use Provisioned throughput when the throughput need is known and steady, and Elastic when it is spiky or unpredictable.
V: Amazon EFS, Amazon CloudWatch

@ SAA-C03 D3 T3.1 advanced troubleshooting
S: A geospatial analytics service on a network-optimized EC2 instance downloads 40 GB satellite images from an S3 bucket in the same Region, and each object is fetched with a single GET request. A download takes several minutes while the instance's network interface stays below 15 percent use. The upload process and object key layout belong to another team and cannot change, and the data must not be copied elsewhere. Which change shortens the downloads the MOST?
A: Enable S3 Transfer Acceleration on the bucket and download through the accelerate endpoint, which routes requests over CloudFront edge locations to the bucket
B: Have the keys spread across many hashed prefixes, so that the bucket supports more GET requests per second for each partitioned prefix
C: Copy the images into an S3 Express One Zone directory bucket in the instance's Availability Zone and read them from there with single requests
D: Split each download into many concurrent byte-range GET requests over separate connections, for example with the SDK transfer manager
K: D
G: ## Where S3 throughput comes from
Amazon S3 is a large distributed system, not a single server. One GET over one connection is limited by that single flow, no matter how fast the instance is. AWS's performance guidance is to **scale horizontally**: issue many concurrent requests over separate connections.
## Byte-range fetches
A GET can carry a `Range` header and return only part of an object. Fetching different ranges of the same object in parallel gives much higher aggregate throughput, and a failed range can be retried alone. Objects uploaded with multipart upload are best read in the same part sizes. The AWS SDK transfer manager does this automatically, and single instances can reach up to 100 Gb/s to S3.
## Request-rate limits are a different problem
S3 supports at least 3,500 writes and 5,500 reads per second per partitioned prefix. That matters for many small objects, not for a few very large ones.
W: Parallel byte-range GETs: they turn one slow stream into many concurrent streams, filling the idle network capacity without touching keys, uploads or storage location.
X: A=Transfer Acceleration: it speeds long-distance transfers to a bucket through edge locations; the instance is already in the bucket's Region, so it adds a charge without fixing the single-stream limit.
B=Hashed prefixes: per-prefix request rates are not the bottleneck for a few huge objects, and the key layout cannot change.
C=S3 Express One Zone: it offers single-digit millisecond access, but it requires copying the data, which is not allowed, and single requests would still be one stream each.
T: To speed up large S3 downloads, use parallel byte-range GETs; prefix spreading only helps request-rate limits.
V: Amazon S3, Amazon EC2

@ SAA-C03 D3 T3.2 advanced troubleshooting
S: An order-import Lambda function is triggered by an SQS standard queue whose redrive policy sends messages to a dead-letter queue after three receives. During sales Lambda scales to hundreds of concurrent invocations, and the Aurora writer, which handles about 50 concurrent writes well, slows sharply. The team set reserved concurrency to 50, but valid messages then reached the DLQ. Messages must not be retried because of throttling, and other functions must keep their concurrency. What should the team do?
A: Remove the reserved concurrency and set maximum concurrency to 50 on the SQS event source mapping, so Lambda stops reading new batches instead of being throttled
B: Keep reserved concurrency at 50 and raise maxReceiveCount on the redrive policy to 20, so throttled messages get more attempts before reaching the DLQ
C: Raise the event source mapping batch size to 10,000 messages with a batching window, so that each invocation writes many more orders to Aurora
D: Configure provisioned concurrency of 50 on the function alias, so that only 50 pre-initialized execution environments can process messages from the queue
K: A
G: ## Two ways to limit a queue consumer
- **Reserved concurrency** caps the whole function. When the SQS poller tries to invoke beyond the cap, the invocation is **throttled**, the batch goes back to the queue, and each return counts as a receive. With a low `maxReceiveCount`, valid messages land in the DLQ.
- **Maximum concurrency** on the SQS event source mapping (minimum 2) limits how many concurrent invocations that queue can drive. Lambda simply stops polling more batches, so messages wait in the queue without being throttled. It costs nothing.
AWS's guidance: if you use both, keep reserved concurrency at least as high as the total maximum concurrency of the queues, otherwise throttling returns.
## Protecting a database
Capping consumer concurrency at the level the database handles is a standard way to stop a burst of queue traffic from overloading a downstream writer.
W: Maximum concurrency on the mapping: it caps the work sent to Aurora at 50 without throttles, so no message is counted as a failed receive, and it does not reserve any account concurrency away from other functions.
X: B=Higher maxReceiveCount: messages would still be throttled and retried, which the team explicitly ruled out; it only delays the DLQ problem.
C=Larger batches: fewer, bigger invocations do not bound concurrency, so hundreds of invocations can still hit Aurora at once with even larger transactions.
D=Provisioned concurrency: it pre-initializes environments to cut cold starts; it does not cap concurrency, and it adds cost.
T: To throttle an SQS-triggered Lambda gently, set maximum concurrency on the event source mapping, not reserved concurrency.
V: AWS Lambda, Amazon SQS, Amazon Aurora

@ SAA-C03 D3 T3.2 advanced use-case
S: A booking API runs on an EC2 Auto Scaling group behind an Application Load Balancer. Every weekday at 08:00, traffic triples within minutes, and smaller unplanned spikes occur during the day. Each new instance needs about seven minutes to download a large reference data set to its EBS volume before it passes health checks, so users see errors during scale-out. The company wants fast scale-out for both kinds of surge without paying for idle running instances. Which TWO actions should the solutions architect take? (Select TWO)
A: Add a predictive scaling policy, so the group forecasts the recurring weekday surge from its history and launches capacity ahead of 08:00
B: Add a scheduled action that raises the minimum capacity to the 08:00 peak for the whole business day, so enough instances always run
C: Shorten the health check grace period to 60 seconds, so that new instances join the load balancer before the data download completes
D: Add a warm pool that keeps instances in the Stopped state, with a lifecycle hook so each one finishes the download before it is stopped
E: Add a warm pool that keeps instances in the Running state, so pre-initialized instances can join the group without any boot delay
K: A,D
G: ## Two problems, two tools
Slow initialization hurts in two different situations:
- **Recurring surges**. Predictive scaling analyzes past load to find daily or weekly patterns and launches capacity **before** the forecast load arrives. AWS recommends it for cyclical traffic and for applications that take a long time to initialize.
- **Unplanned spikes**. No forecast can see them, so the group must react; the fix is to make the reaction faster. A **warm pool** is a set of pre-initialized instances next to the group. A lifecycle hook keeps each instance from being stopped until its initialization is done.
## Warm pool states and cost
- `Stopped`: you pay only for EBS volumes and attached Elastic IPs; this is AWS's recommended way to minimize cost.
- `Hibernated`: also saves RAM to the root volume.
- `Running`: possible but highly discouraged, because you pay for idle instances.
W: A=Predictive scaling: it launches capacity before the known 08:00 surge, so the seven-minute download finishes before users arrive.
D=Stopped warm pool with a lifecycle hook: instances already hold the data on EBS, so an unplanned spike is met by starting them, while stopped instances bill only for storage.
X: B=Scheduled high minimum: it covers the morning, but it keeps peak capacity running all day, paying for idle instances the company wants to avoid.
C=Shorter grace period: instances would receive traffic or be judged before their data is ready, causing more errors, not fewer.
E=Running warm pool: it is fast, but those instances are billed as running instances while idle, which the requirement forbids.
T: Combine predictive scaling for recurring surges with a stopped warm pool for unplanned spikes when instances initialize slowly.
V: Amazon EC2 Auto Scaling, Elastic Load Balancing

@ SAA-C03 D3 T3.2 advanced use-case
S: A company is moving a 60-node Apache Cassandra cluster to EC2 in one Region with three Availability Zones, placing 20 nodes in each zone. A single rack failure inside a zone must never take out more than one replica of the same data, so Cassandra needs to know which rack each node is on. All three zones must be used, and node-to-node network performance only needs to be normal for the zone. Which placement design fits?
A: A spread placement group across the three Availability Zones, so that every one of the 60 nodes runs on its own distinct rack with separate power
B: A partition placement group with partitions in each Availability Zone, mapping each partition to a Cassandra rack using the partition number EC2 exposes
C: A cluster placement group in each Availability Zone, so that the 20 nodes in each zone share a low-latency, high-bandwidth network segment
D: A single partition placement group in one Availability Zone with seven partitions, mapping each partition to a Cassandra rack for replica placement
K: B
G: ## Three placement strategies
- **Cluster**: packs instances close together in one zone for the lowest latency and highest bandwidth, which also means instances can share hardware failures.
- **Spread**: every instance on a distinct rack, but at most **seven running instances per Availability Zone** per group. Good for a few critical instances.
- **Partition**: divides the group into partitions, each on its own set of racks with its own network and power. Up to **seven partitions per zone**, and the number of instances is limited only by account limits. EC2 shows which partition each instance is in, so topology-aware systems such as HDFS, HBase and **Cassandra** can place replicas on different partitions. A partition placement group can span several zones in a Region.
W: Partition placement group across zones: 20 nodes per zone fit easily, partitions do not share racks, and the visible partition number maps directly to Cassandra's rack setting.
X: A=Spread placement group: it isolates racks, but it allows only seven running instances per zone, far fewer than 20.
C=Cluster placement group: it maximizes network speed that is not needed and places nodes close together, so one hardware failure can hit several replicas.
D=One-zone partition group: it gives rack awareness, but it ignores the requirement to use all three zones.
T: For large, rack-aware distributed databases on EC2, use partition placement groups; spread groups cap at seven instances per zone.
V: Amazon EC2

@ SAA-C03 D3 T3.2 advanced troubleshooting
S: A mobile backend runs on Lambda functions with 128 MB of memory. Tracing shows three problems: requests right after the 09:00 traffic jump spend 3 seconds in initialization, a CPU-bound scoring step takes 900 ms, and every invocation spends 150 ms opening a new TLS connection to an RDS for MySQL database. The company wants lower p99 latency and accepts a higher Lambda bill. Which THREE changes address the observed problems? (Select THREE)
A: Configure provisioned concurrency on the function alias, scheduled through Application Auto Scaling to rise before 09:00, so initialized environments are waiting
B: Configure reserved concurrency equal to the 09:00 peak, so that the function always has enough execution environments set aside for it alone
C: Raise the memory setting to about 1,769 MB or more, because Lambda allocates CPU in proportion to memory and the scoring step is CPU-bound
D: Increase the function timeout from 3 seconds to 30 seconds, so that slow invocations during initialization finish instead of failing with a timeout
E: Add an RDS Proxy in front of the database and open the connection outside the handler, so that warm environments reuse pooled connections
F: Increase ephemeral storage in /tmp from 512 MB to 10 GB, so the function can keep scoring results on local disk between invocations

D=Longer timeout: it stops failures but does not make any request faster; p99 latency stays the same.
F=Larger /tmp: local storage does not address initialization, CPU or connection time, and the scoring step is CPU-bound, not disk-bound.
T: For Lambda latency: provisioned concurrency for cold starts, more memory for CPU-bound code, and connection reuse with RDS Proxy for database setup time.
V: AWS Lambda, Amazon RDS Proxy, Application Auto Scaling

@ SAA-C03 D3 T3.3 advanced troubleshooting
S: A ticketing site added a three-node DynamoDB Accelerator (DAX) cluster in front of its seat-map table, but read latency and consumed read capacity did not change at all. Investigation shows that every GetItem call sets ConsistentRead to true, a setting copied from an old code sample. Product owners confirm that seat maps may be up to two seconds stale. What should the team do to get the expected benefit from DAX?
A: Scale the DAX cluster to a larger node type and add nodes, so that the item cache can hold the entire seat-map table in memory at once
B: Raise the item cache TTL in the DAX parameter group from 5 minutes to 1 hour, so that cached seat maps stay in memory much longer
C: Change the GetItem calls to eventually consistent reads, so that DAX can answer them from its item cache instead of passing them to DynamoDB
D: Switch the table to on-demand capacity mode, so that DynamoDB serves the strongly consistent reads behind DAX with no capacity planning
K: C
G: ## How DAX treats each kind of read
DAX is a write-through, in-memory cache that sits in front of DynamoDB.
- **Eventually consistent** `GetItem`/`BatchGetItem`: served from the **item cache** when the item is there (microsecond latency); on a miss, DAX reads from DynamoDB and caches the result.
- **Strongly consistent** reads (`ConsistentRead=true`) and `TransactGetItems`: DAX **passes them to DynamoDB** and returns the result **without caching it**, because DAX is not tightly coupled to the table and cannot guarantee the latest value.
## Reading the evidence
No change in latency and no drop in consumed read capacity means DAX never served a read. The two-second staleness allowance makes eventually consistent reads acceptable.
W: Eventually consistent reads: only these can be served from the DAX item cache, so latency drops and the table's read capacity use falls.
X: A=Bigger cluster: more memory does not help when no strongly consistent read is ever cached; every request still goes to DynamoDB.
B=Longer item TTL: TTL controls how long cached items live, but these reads never enter the cache at all.
D=On-demand mode: it changes how DynamoDB bills and scales, not latency; DAX would still pass every read through.
T: DAX caches only eventually consistent reads; strongly consistent and transactional reads always go to DynamoDB.
V: Amazon DynamoDB Accelerator (DAX), Amazon DynamoDB

@ SAA-C03 D3 T3.3 advanced use-case
S: A gaming company keeps player profiles in Aurora MySQL and wants a real-time global leaderboard that returns the top 100 players in under a millisecond. Scores change thousands of times per second. If a cache node fails, the leaderboard must fail over automatically within the Region without being rebuilt from the database. Which design meets these requirements?
A: ElastiCache for Valkey with Multi-AZ replicas and automatic failover, keeping scores in a sorted set and reading the top 100 with a range command
B: ElastiCache for Memcached with several nodes, storing each player's score under its own key and computing the top 100 in the application
C: A DynamoDB Accelerator cluster placed in front of the Aurora MySQL tables, caching the result of the top-100 query for one second at a time
D: Aurora Replicas with an index on the score column, reading the top 100 through the reader endpoint with ORDER BY and LIMIT clauses
K: A
G: ## Choosing an ElastiCache engine
ElastiCache supports Valkey, Redis OSS and Memcached. They are all in-memory key-value stores, but their features differ:
- **Memcached**: simplest model, multithreaded, easy to scale out; no replication, no automatic failover, no sorted sets.
- **Valkey / Redis OSS**: replication with Multi-AZ automatic failover, backups, pub/sub and rich data types such as **sorted sets**.
## Why sorted sets fit leaderboards
A sorted set keeps members ordered by score. Updating a score and reading the top N are single commands that run in memory, so the ranking is always current without scanning all players.
W: ElastiCache for Valkey: sorted sets keep the ranking ready at sub-millisecond speed, and replicas with automatic failover keep the leaderboard alive when a node fails.
X: B=Memcached: it has no replication or automatic failover, so a node loss means rebuilding from the database, and ranking all players in the application is slow.
C=DAX: it caches DynamoDB only and cannot sit in front of Aurora MySQL.
D=Aurora Replicas with ORDER BY: reads go to disk-backed database instances with millisecond-range latency, not sub-millisecond, under thousands of updates per second.
T: For real-time leaderboards that must survive node failure, use ElastiCache (Valkey or Redis OSS) sorted sets with Multi-AZ failover.
V: Amazon ElastiCache, Amazon Aurora

@ SAA-C03 D3 T3.3 advanced use-case
S: An Aurora PostgreSQL cluster has a writer and four db.r6g.large replicas serving a web application through the reader endpoint. Analysts need long-running reports, so two db.r6g.4xlarge replicas were added. Since then, some web reads land on the large replicas and some reports land on the small ones, making web latency unpredictable. Web reads must never share instances with reports, and all instances must stay in this cluster. What should the solutions architect do?
A: Point the reporting tool at the reader endpoint and give the two large replicas failover priority tier 15, so that the reader endpoint avoids sending them traffic
B: Move the reports to a separate Aurora cluster created as a clone every night, and point the reporting tool at that cluster's own reader endpoint
C: Turn on Aurora Auto Scaling for replicas with a 60 percent CPU target, so that the reader endpoint always has spare capacity for both workloads
D: Create one custom endpoint for the two large replicas and another for the four small ones, and point reports and web reads at their own endpoints
K: D
G: ## Aurora endpoints
- **Cluster (writer) endpoint**: the current primary.
- **Reader endpoint**: balances connections across **all** Aurora Replicas.
- **Custom endpoints** (up to five per cluster): a set of instances you choose. Aurora balances connections only among the members. AWS suggests them when replicas differ in size or purpose, for example small instances for ad hoc reporting and large ones for production, and notes that you then usually stop using the reader endpoint.
## Why two custom endpoints
A custom endpoint for reports alone is not enough: the web tier would still use the reader endpoint, which includes the large reporting replicas. Giving each group its own endpoint separates them in both directions.

D=Web tier on Spot only: interruptions would remove capacity, which the web tier must never lose, even if Auto Scaling replaces instances later.
E=Dedicated Hosts: they add cost for a physical server and do nothing about instances that sit idle outside office hours.
T: Commit to the baseline, use Spot for interruptible work, and stop part-time instances when they are idle.
V: Savings Plans, Amazon EC2 Spot Instances, Amazon EC2

@ SAA-C03 D4 T4.3 advanced use-case
S: A company runs an RDS for PostgreSQL database on a db.r6i.xlarge Single-AZ instance and wants to buy a three-year reserved DB instance today. In about four months it will convert the database to a Multi-AZ DB instance deployment and scale it to db.r6i.2xlarge, staying on the r6i class in the same Region. It wants the discount to cover the database without paying for unused reservations in the meantime. What should it buy?
A: A reserved DB instance for db.r6i.2xlarge Multi-AZ today, so that the final configuration is fully covered from the very first day of the term
B: A db.r6i.xlarge Single-AZ reservation now, and more r6i reservations after the change, as size flexibility applies normalized units across sizes and deployments
C: A Compute Savings Plan sized to the database's hourly On-Demand cost, because it applies regardless of instance family, size, or AWS Region
D: A reserved DB instance for db.r7g.xlarge Single-AZ, because newer Graviton classes give a lower hourly rate for the same normalized size

G: ## Reserved DB instances
A reserved DB instance gives a discount for a commitment in a Region, for a DB engine and an instance class type.
- **Size flexibility** (RDS for MySQL, MariaDB, PostgreSQL, Oracle BYOL, and Db2): the discount applies to any size of the **same instance class type** in the same Region and engine, measured in **normalized units**. Buy for today's usage; after the change, the existing reservation covers part of the larger Multi-AZ instance, and a second purchase covers the rest.

C=Compute Savings Plan: it covers EC2, Fargate and Lambda, not RDS DB instances.
D=db.r7g reservation: the database stays on r6i, and reservations do not apply across class types.
T: RDS reservations are size-flexible within the same class type, engine and Region, across Single-AZ and Multi-AZ, so buy for current usage and add later.

@ SAA-C03 D4 T4.3 advanced use-case
S: A DynamoDB table in provisioned capacity mode stores 400 million session items. Each night a Lambda function scans the table and deletes items older than 30 days, consuming so many write capacity units that the table is scaled up for two hours. Expired items may remain for a few days before deletion, but every deleted session must be archived to S3 for compliance. Which TWO changes meet the requirements at the LOWEST cost? (Select TWO)
A: Keep the nightly delete job but switch the table to on-demand capacity mode, so the burst of deletes is billed per request instead of by scaled capacity
B: Change the table class to DynamoDB Standard-Infrequent Access, which lowers storage costs for tables that keep many rarely read items
C: Enable Time to Live on an expiry attribute set to 30 days after creation, because DynamoDB deletes expired items without using write throughput
D: Enable DynamoDB Streams and use a Lambda function that writes to S3 the records whose userIdentity principal is dynamodb.amazonaws.com
E: Run a daily full export of the table to S3, so that an archive copy of every session exists in S3 before the delete job removes it
K: C,D
G: ## Time to Live
TTL lets each item carry an expiry timestamp (a Number in Unix epoch seconds). DynamoDB deletes expired items, typically **within a few days**, **without consuming write throughput**. Expired items not yet deleted can be filtered out of reads.
## Archiving TTL deletions
With DynamoDB Streams enabled, each TTL deletion appears as a stream record. Deletions made by TTL carry `userIdentity.type` = `Service` and `userIdentity.principalId` = `dynamodb.amazonaws.com`, so a Lambda function can archive exactly those items (for example to S3) and ignore deletes made by users.
W: C=Time to Live: deletions stop consuming write capacity, so the nightly scan and the two-hour scale-up disappear; the few-day delay is acceptable.
D=Streams with a filtered Lambda: each TTL-deleted session is captured and written to S3, meeting the archive requirement.
X: A=On-demand with the same job: the scan and deletes are still paid, now per request, so cost does not fall.
B=Standard-IA table class: it lowers storage price but deletes nothing and archives nothing.
E=Daily full export: exporting 400 million items every day costs far more than streaming only the deleted ones, and the delete job still uses write capacity.
T: Use DynamoDB TTL for free expiry deletes, and DynamoDB Streams to archive the TTL-deleted items.
V: Amazon DynamoDB, AWS Lambda, Amazon S3

@ SAA-C03 D4 T4.3 advanced use-case
S: A QA department needs five test copies of a 6 TB Aurora MySQL production cluster, refreshed every Monday. Each copy changes less than 2 percent of the data during its week, testers need full read and write access, and copies must be ready within an hour of the refresh starting. The company wants to keep the extra storage cost of the test copies as low as possible. Which approach fits BEST?
A: Create five Aurora clones of the production cluster each Monday, which share unchanged pages through copy-on-write and add storage only for changes
B: Restore the latest automated snapshot into five new clusters each Monday, giving every test team an independent full copy of the 6 TB volume
C: Add five Aurora Replicas to the production cluster and give each test team the instance endpoint of one replica for its testing during the week
D: Use AWS DMS full load plus ongoing replication into five separate Aurora clusters, keeping every test copy continuously in step with production
K: A
G: ## Aurora cloning
Aurora cloning creates a new cluster whose volume **initially shares the same data pages** as the source. It uses a **copy-on-write** protocol: new storage is allocated only when the source or the clone changes data. AWS describes it as faster and more space-efficient than restoring a snapshot and highlights it for test environments using production data.
Limits to know: up to **15 copy-on-write clones** per source (later ones are full copies), and clones stay in the same Region (they can be in another VPC or shared with other accounts).
W: Aurora clones: five clones store only the roughly 2 percent of pages each one changes, are writable, and are created quickly each Monday.
X: B=Snapshot restores: each cluster is a full 6 TB copy, so storage cost is about five times the production volume, and large restores take longer.
C=Aurora Replicas: replicas are read-only and share production capacity, so testers cannot write and production is put at risk.
D=DMS replication: it keeps five full copies continuously, paying for full storage and replication instances, and changes made by testers would conflict with replication.
T: For writable test copies of Aurora that change little, use clones; copy-on-write stores only the differences.
V: Amazon Aurora

@ SAA-C03 D4 T4.4 advanced troubleshooting
S: A company routes all outbound traffic from 40 spoke VPCs through a transit gateway to NAT gateways in a central egress VPC in the same Region. Most of this traffic is reads from S3 buckets in that Region. The team added an S3 gateway endpoint to the egress VPC, but NAT gateway and transit gateway data processing charges did not drop. Which change reduces these charges the MOST?
A: Add routes on the transit gateway route tables that send the S3 prefix list to the egress VPC attachment, so traffic reaches the gateway endpoint there
B: Create an S3 interface endpoint in the egress VPC and resolve its DNS names from the spoke VPCs, so S3 traffic no longer passes through NAT
C: Deploy a NAT gateway in each spoke VPC, so that S3 traffic leaves directly from each spoke without crossing the transit gateway at all
D: Create an S3 gateway endpoint in each spoke VPC and associate it with the spoke route tables, so S3 traffic skips both transit gateway and NAT
K: D
G: ## What a gateway endpoint can reach
An S3 gateway endpoint is a route-table target in **one VPC**. It has **no additional charge**. AWS documents its limits: it cannot be used from **on-premises networks**, from **peered VPCs in other Regions**, or **through a transit gateway**. For those paths you need an interface endpoint, which bills per hour and per GB.
## Where the charges come from
- **Transit gateway**: billed per attachment-hour and per GB processed.
- **NAT gateway**: billed per hour and per GB processed.
Traffic from a spoke that crosses the transit gateway to reach the egress VPC pays transit gateway processing, and the gateway endpoint in the egress VPC cannot serve it.
W: Gateway endpoint in each spoke: S3 traffic is routed straight from each spoke VPC to S3 at no endpoint charge, removing both transit gateway and NAT processing for it.
X: A=Transit gateway routes to the egress endpoint: gateway endpoints are not reachable through a transit gateway, so this routing does not work.
B=Interface endpoint in the egress VPC: it removes NAT processing, but traffic still crosses the transit gateway and adds interface endpoint hourly and per-GB charges.
C=NAT gateway per spoke: it removes transit gateway processing, but 40 more NAT gateways still charge per hour and per GB for the S3 traffic.
T: S3 gateway endpoints work only inside their own VPC (not through a transit gateway), so put one in every VPC that reads from S3 in the same Region.
V: Amazon VPC, AWS Transit Gateway, Amazon S3

S: An application VPC and a search-cluster VPC in the same Region exchange about 300 TB a month through the company's transit gateway, which also connects 25 other VPCs. The instances that talk to each other are in the same Availability Zones in both VPCs. Data processing charges for this one pair now dominate the transit gateway bill. Which change reduces cost the MOST without changing how the other VPCs connect?
A: Expose the search cluster through an AWS PrivateLink endpoint service behind a Network Load Balancer, with an interface endpoint in the application VPC
B: Attach both VPCs to a second, dedicated transit gateway, so that their traffic no longer shares processing with the 25 other VPC attachments
C: Create a VPC peering connection between the two VPCs and add routes for each other's CIDR blocks, which are more specific than the transit gateway routes
D: Enable appliance mode on both transit gateway VPC attachments, so that traffic between the pair stays in one Availability Zone and avoids cross-AZ charges
K: C
G: ## Cost of inter-VPC paths
- **Transit gateway**: hourly charge per attachment plus a charge for every GB processed.
- **VPC peering**: no hourly charge. Data transfer over a peering connection that **stays within an Availability Zone is free**; crossing zones is charged at standard in-Region rates. AWS describes peering as the lowest overall cost and highest aggregate performance option for inter-VPC connectivity.
- **PrivateLink**: interface endpoints bill per hour and per GB processed.
## Routing both side by side
Route tables use the most specific match. Adding peering routes for the exact VPC CIDRs takes this pair off the transit gateway, while broader routes keep sending everything else through it.
W: VPC peering for the heavy pair: same-zone traffic over peering is free and has no processing charge, and the other 25 VPCs keep using the transit gateway.

B=Dedicated transit gateway: each transit gateway still bills per GB processed, so the 300 TB keeps the same charge.
D=Appliance mode: it keeps flows symmetric through one zone for inspection appliances; it does not remove transit gateway processing charges.
T: For a high-volume pair of VPCs, add VPC peering alongside the transit gateway; same-AZ peering traffic is free.
V: Amazon VPC, AWS Transit Gateway

S: An application runs on 120 EC2 instances in public subnets behind an internet-facing Application Load Balancer, and each instance has an auto-assigned public IPv4 address. The instances receive traffic only from the load balancer and download packages only from an S3 bucket in the same Region. The VPC has no IPv6 CIDR block, and re-addressing is out of scope. Which change removes the public IPv4 charges at the LOWEST cost?

AWS charges for **all public IPv4 addresses**, including addresses auto-assigned to running instances and Elastic IP addresses. A fleet that gives every instance a public address pays for each one.

@ SAA-C03 D4 T4.4 advanced troubleshooting
S: A Spark cluster in eu-west-1 reads the same 50 TB reference dataset about ten times a month from an S3 bucket in us-east-1 through a NAT gateway in its private subnets. The dataset changes by only a few gigabytes each day. The team created an S3 gateway endpoint in the eu-west-1 VPC, but NAT charges did not change. Which approach reduces data transfer and NAT charges the MOST?
A: Copy the dataset once to a bucket in eu-west-1 with S3 Batch Replication, keep it current with Cross-Region Replication, and read it through the endpoint
B: Add the us-east-1 bucket's ARN to the gateway endpoint policy in eu-west-1, so that the endpoint carries requests for that bucket instead of the NAT
C: Enable S3 Transfer Acceleration on the us-east-1 bucket and have the cluster read through the accelerate endpoint for faster cross-Region transfers
D: Create an S3 interface endpoint in a us-east-1 VPC and reach it from the cluster over inter-Region VPC peering, so reads no longer use the NAT gateway
K: A
G: ## Gateway endpoints are Regional
An S3 gateway endpoint works only for buckets **in its own Region**: prefix lists are Region-specific, so traffic to a bucket in another Region keeps following the default route (here, the NAT gateway). An endpoint policy cannot change that.
## Pay for distance once, not ten times
Reading 50 TB across Regions ten times a month pays inter-Region transfer (and NAT processing) on 500 TB. A local copy pays inter-Region transfer **once** for the initial copy and then only for the daily changes.
- **S3 Batch Replication** copies objects that existed before replication was configured.
- **Cross-Region Replication** then copies new and changed objects automatically.
Reads of the local copy use the free gateway endpoint.
W: Local replica plus gateway endpoint: inter-Region transfer happens once plus a few GB a day, and ten monthly reads go through the free endpoint instead of the NAT gateway.
X: B=Endpoint policy with the remote bucket: a gateway endpoint cannot route to another Region no matter what its policy allows.
C=Transfer Acceleration: it adds a per-GB acceleration charge on top of the same cross-Region reads and still uses the NAT path.
D=Interface endpoint over inter-Region peering: it avoids NAT, but every read still crosses Regions and adds endpoint charges.
T: S3 gateway endpoints serve only same-Region buckets; for data read repeatedly from another Region, replicate it locally.
V: Amazon S3, Amazon VPC
