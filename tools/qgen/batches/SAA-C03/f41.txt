S: A company must rotate its KMS keys every 180 days to meet an internal policy. Its applications use a customer managed symmetric key through an alias, and existing S3 objects and EBS snapshots must stay readable without being re-encrypted or reconfigured. Which approach meets this?
A: Run a Lambda function on a 180 day schedule that calls ReEncrypt on each object protected by the key, storing the new ciphertext
B: Import the company's own key material into the key and rely on automatic rotation to replace the imported material at a 180 day interval
C: Enable automatic rotation on the key with a 180 day period; the key ID and alias stay the same and older key material is retained
D: Create a new key each 180 days, repoint the alias to it, and re-encrypt existing objects and snapshots before deleting the old key
K: C
G: ## How KMS key rotation works
For a customer managed symmetric encryption key with KMS-generated material, automatic rotation creates new key material on a schedule. The key ID, ARN, alias and policy stay the same. KMS keeps all older material, so data encrypted before a rotation still decrypts, and new encryption operations use the newest material. You can set the rotation period from 90 to 2,560 days (the default is 365).
## What rotation does not do
Rotation does not re-encrypt existing data. It also is not available for keys with imported key material, so those need manual rotation with a new key and an alias change.
W: Automatic rotation with a 180 day period: it meets the schedule with no application change and no data re-encryption.
X: A=ReEncrypt on a schedule: this makes a large, costly job for all objects and snapshots, and it is unnecessary because KMS keeps the old material for decryption.
B=Imported key material: KMS does not generate new material for keys with imported material, so automatic rotation is not supported for them.
D=New key and re-encryption: this is the manual pattern, needed only when automatic rotation is not available. It means re-encrypting all data and much operational effort.
T: Turn on automatic rotation with a custom period for customer managed symmetric keys: key ID and ciphertext stay valid, and no data is re-encrypted.
V: AWS KMS

@ SAA-C03 D1 T1.3 applied use-case
S: Ransomware attackers who stole administrator credentials in another company deleted all of its backups before encrypting data. A company using AWS Backup wants its recovery points protected so that no one, including the account root user, can delete them before the 35-day retention ends. What should it configure?
A: A backup vault access policy that denies backup:DeleteRecoveryPoint to the IAM users and roles in the account
B: AWS Backup Vault Lock in compliance mode on the backup vault, with a minimum retention of 35 days
C: An SCP that denies backup:DeleteRecoveryPoint in the member accounts, combined with CloudTrail alerts on the vault
D: S3 Versioning and MFA Delete on the bucket where AWS Backup writes the recovery points of the protected resources
K: B
G: ## Why backups need immutability
Attackers often delete backups first, then encrypt production data, so the victim has nothing to restore. Protection must hold even if an attacker gets administrator or root credentials.
## AWS Backup Vault Lock
A backup vault holds recovery points. Vault Lock adds a write-once-read-many (WORM) setting:
- `MinRetentionDays` / `MaxRetentionDays`: bounds for recovery points in the vault, for example a minimum of 35 days.
- **Governance mode**: users with special IAM permissions can remove the lock. Good for testing.
- **Compliance mode**: after a grace period (at least 3 days), the lock can no longer be changed or removed by anyone.
## Example
A daily backup plan writes to `prod-vault` with compliance-mode Vault Lock of 35 days. A stolen admin session calling `DeleteRecoveryPoint` is refused. For extra isolation, copies can also go to a vault in a separate account.
W: Vault Lock in compliance mode: once the grace period ends, the lock becomes immutable. Recovery points cannot be deleted or their retention shortened by anyone, including the root user and AWS, until the minimum retention has passed.
X: A=Vault access policy deny: an administrator with the stolen credentials can edit or remove the access policy and then delete the backups. It raises the bar but is not immutable.
C=SCP with alerts: SCPs do not restrict the management account, can be changed by whoever controls the management account, and an alert only tells you after the backups are gone.
D=S3 Versioning and MFA Delete: AWS Backup stores recovery points in its own managed storage, not in a bucket you own, so there is no bucket to configure. MFA Delete is also tied to root credentials that could be stolen.
T: For backups that even root cannot delete, use Backup Vault Lock in compliance mode; access policies and SCPs can be changed by a compromised administrator.
V: AWS Backup

@ SAA-C03 D1 T1.2 applied use-case
S: A company serves a web application through Amazon CloudFront with an Application Load Balancer as the origin. Security requires that the ALB is not reachable from the internet at all, and only this CloudFront distribution may send it traffic. Which solution meets the requirement with the LEAST operational overhead?
A: Keep the ALB internet-facing and add network ACL rules that allow the CloudFront IP ranges, updated by a scheduled function
B: Keep the ALB internet-facing and attach an AWS WAF web ACL with a geo match rule that allows the CloudFront edge countries
C: Keep the ALB internet-facing and allow inbound HTTPS from the CloudFront origin-facing managed prefix list in its security group
D: Move the ALB to private subnets as an internal load balancer and register it as a CloudFront VPC origin for the distribution
K: D
G: ## Ways to lock an ALB behind CloudFront
- **Public ALB + prefix list**: the security group allows `com.amazonaws.global.cloudfront.origin-facing`. This limits traffic to CloudFront servers, but every customer's distribution uses the same servers, so a custom secret header checked by the ALB is usually added too.
- **VPC origin**: CloudFront connects to an internal ALB, NLB or EC2 instance in a private subnet. The load balancer is never exposed to the internet, and there is no header secret to rotate.
## Example layout
- `internal-app-alb` in two private subnets, security group allowing HTTPS from the CloudFront VPC origin.
- The distribution uses the VPC origin as its origin; users reach `www.example.com` only through CloudFront, where WAF and caching apply.
With no public endpoint, scanners and attackers have nothing to hit directly, which is the strongest form of "only through CloudFront".
W: CloudFront VPC origin: CloudFront can deliver to an internal ALB in private subnets through a VPC origin. The ALB has no public IP address, so it cannot be reached from the internet, and only CloudFront, through the VPC origin, can connect to it.
X: A=NACL with CloudFront ranges: NACLs have a small rule limit, CloudFront publishes many ranges that change, and the scheduled updater is extra code to run. The ALB would still be internet-facing and reachable from any distribution.
B=WAF geo blocking: CloudFront edge locations are in most countries, so geography does not identify CloudFront traffic. Attackers in allowed countries could still reach the public ALB directly.
C=Managed prefix list in security group: the ALB is still internet-facing, and the prefix list covers all CloudFront edge servers, including distributions owned by other AWS customers. Anyone could point their own distribution at the ALB.
T: To make an origin truly private behind CloudFront, use a VPC origin with an internal ALB; a prefix list only narrows a public ALB to all of CloudFront.
V: Amazon CloudFront, Elastic Load Balancing, Amazon VPC

@ SAA-C03 D4 T4.2 advanced use-case
S: A company has variable workloads and wants to combine Spot and On-Demand capacity in one Auto Scaling group. Which feature fits?
A: Manual scaling of a fleet that runs On-Demand capacity
B: A mixed instances policy with capacity rebalancing
C: A single Spot instance type with a fixed desired capacity
D: A launch template that places instances on Dedicated Hosts
K: B
G: ## Mixing purchase options in one Auto Scaling group
An Auto Scaling group normally launches one instance type at one price model. A **mixed instances policy** lets one group launch several instance types and combine On-Demand and Spot.
- `OnDemandBaseCapacity` sets a floor of On-Demand instances that always run.
- `OnDemandPercentageAboveBaseCapacity` sets the On-Demand share of everything above that floor; the rest is Spot.
- A Spot allocation strategy such as `price-capacity-optimized` chooses pools with low interruption risk and low price.
- Listing several similar instance types gives Spot more pools to draw from.
## Capacity Rebalancing
When EC2 signals that a Spot instance is at elevated risk of interruption (a rebalance recommendation), **Capacity Rebalancing** launches a replacement first and then terminates the at-risk instance, reducing gaps in capacity.
Example: base of 2 On-Demand, then 25% On-Demand and 75% Spot across `m6i`, `m6a` and `m7i` sizes, with Capacity Rebalancing on.
W: Mixed instances policy with capacity rebalancing: it blends On-Demand and Spot across several instance types in one group and proactively replaces Spot instances likely to be interrupted.
X: A=Manual On-Demand scaling: it uses no Spot capacity at all, so it misses the savings, and manual changes cannot follow variable load.
C=Single Spot instance type: there is no On-Demand baseline, and relying on one Spot pool means an interruption or shortage in that pool can remove most capacity at once.
D=Dedicated Hosts: hosts cost more than shared-tenancy instances and cannot be combined with Spot, so neither requirement is met.
T: Blend Spot and On-Demand in one group with a mixed instances policy, diversify instance types, and let Capacity Rebalancing replace at-risk Spot instances.
V: Amazon EC2 Auto Scaling

B: Compute Savings Plans
C: Dedicated Hosts for the three years

G: ## Commitment-based discounts for EC2
AWS offers lower prices when you commit to steady usage for one or three years:
- **Savings Plans** commit to a dollar amount of compute per hour (for example `$10/hour`) and discount usage up to that amount.
- **Compute Savings Plans** apply automatically to EC2 in any instance family, size, Region, operating system or tenancy, and also to AWS Fargate and AWS Lambda.

D=Spot Instances: they are cheap even when spread across pools, but AWS can reclaim them with a two-minute warning, which is unsuitable for a steady workload that must run continuously.

S: Which TWO measures reduce the attack surface of EC2 instances in a web architecture? (Select TWO)
A: Assign public IPs to the instances for easier access
B: Place instances in private subnets behind a load balancer
C: Share one SSH key among the engineers for convenience
D: Open inbound traffic from 0.0.0.0/0 in security groups for testing
E: Use Session Manager instead of opening SSH to the internet
K: B,E
G: ## Reducing the attack surface of EC2
The attack surface is everything an attacker can reach. For web architectures, the goal is that only the load balancer is exposed and administrators do not need open ports.
- **Private subnets behind a load balancer**: instances have no public IPs; only the ALB in public subnets accepts internet traffic, and the instance security group allows traffic only from the ALB's security group.

## Example
Instance SG inbound: TCP 80 from `sg-alb` only. No port 22 rule at all. An engineer opens a shell with `aws ssm start-session --target i-0abc...` after authenticating with IAM.
W: B=Private subnets behind a load balancer: removes direct internet reachability from instances, so only the load balancer is exposed.
E=Session Manager instead of SSH: closes the inbound admin port completely and replaces shared keys with IAM-controlled, audited sessions.
X: A=Public IPs on the instances: makes each instance directly reachable from the internet, increasing rather than reducing exposure.
C=One shared SSH key: a single leaked key compromises every instance, and you cannot tell which engineer did what.
D=Inbound from 0.0.0.0/0: opens the instances to any source on the internet, the largest possible attack surface.
T: Keep instances private behind a load balancer and use Session Manager for admin access so no instance port faces the internet.

@ SAA-C03 D4 T4.4 applied use-case +SOA-C03:D5
S: A company has 25 VPCs across multiple AWS accounts that all need to communicate with each other and with a shared services VPC, and the network topology is expected to keep growing. Using full-mesh VPC peering has become operationally complex and costly to manage. What should the solutions architect implement instead to simplify connectivity while controlling cost as scale grows?
A: Deploy an AWS Transit Gateway and attach each VPC to it
B: Create a Site-to-Site VPN connection between each pair of VPCs
C: Keep adding individual VPC peering connections as new VPCs join
D: Use AWS Direct Connect to link the VPCs to one another
K: A
G: ## Why full-mesh peering stops scaling
VPC peering is a one-to-one link and is **not transitive**: if VPC 1 peers with VPC 2 and VPC 2 peers with VPC 3, VPC 1 still cannot reach VPC 3 through it. Connecting every VPC to every other one needs n(n-1)/2 peerings.
- 26 VPCs (25 plus shared services) need 325 peerings, each with its own route table entries in both VPCs.
- Every new VPC adds 26 more peerings and route updates across accounts.
## How a transit gateway changes this
AWS Transit Gateway is a Regional router that VPCs, VPNs and Direct Connect gateways attach to. Each VPC needs one attachment and one route (for example `10.0.0.0/8` pointing at the transit gateway). The transit gateway route tables decide who can reach whom, and it can be shared with other accounts through AWS Resource Access Manager.
- Adding VPC number 27 means one new attachment, not 26 new peerings.
- Route table segmentation lets you allow spoke-to-shared-services traffic while isolating other groups.
W: Transit Gateway hub-and-spoke: each VPC attaches once, routing is managed centrally in transit gateway route tables, and cross-account sharing via RAM keeps growth linear instead of quadratic.
X: B=VPN between each pair: this recreates the full mesh with IPsec tunnels, each needing its own gateways, tunnels and hourly charges, so it is more complex and costlier than the peering it replaces.
C=More peering connections: the number of peerings grows with the square of the VPC count and each needs routes on both sides, which is exactly the operational burden the company is trying to escape.
D=Direct Connect: Direct Connect is a dedicated link between on-premises networks and AWS; it is not a way to route traffic between VPCs inside AWS.
T: Many VPCs that all need to talk means one hub (Transit Gateway) with one attachment per VPC, not a mesh of peerings or VPNs.
V: AWS Transit Gateway, Amazon VPC, AWS Direct Connect

@ SAA-C03 D4 T4.4 advanced use-case
S: A company transfers large amounts of data from EC2 to the internet in a single Region and wants lower transfer costs for downloads. Which option fits?
A: Serve downloads via CloudFront
B: Add more Elastic IP addresses
C: Use larger EC2 instance types
D: Move the data to EBS io2 volumes
K: A
G: ## What you pay for when EC2 serves downloads
Data sent from EC2 to the internet is charged per GB as data transfer out. If thousands of users download the same files, the same bytes leave the instance again and again.
## How CloudFront changes the bill
- CloudFront caches the files at edge locations close to users.
- **Transfer from an AWS origin such as EC2, an ALB or S3 to CloudFront is not charged**, and each file is fetched from the origin only on a cache miss.
- Users are then billed at CloudFront's delivery rates, which are typically comparable to or lower than EC2 internet egress, come with a larger free tier, and drop further at volume or with pricing commitments.
- The instances also do less work, and users get faster downloads from nearby edges.
Example: a 1 GB installer downloaded 100,000 times is fetched from the origin a small number of times per edge cache; the rest is served from edge caches.
W: Serve downloads via CloudFront: caching at the edge removes repeated origin egress, origin-to-CloudFront transfer is free, and CloudFront delivery rates are typically no higher than direct EC2 egress.
X: B=More Elastic IP addresses: extra addresses change nothing about how many bytes leave AWS; they only add charges for public IPv4 addresses.
C=Larger instance types: a bigger instance can push more bandwidth, but every GB sent to the internet is still billed at the same egress rate, and the instance costs more.
D=EBS io2 volumes: the storage type affects disk performance, not the network egress charge, and io2 adds provisioned-IOPS cost.
T: To cut repeated download egress, put CloudFront in front of the origin; instance, IP or storage changes do not change per-GB transfer charges.

@ SAA-C03 D2 T2.2 applied use-case
S: A company needs to recover a deleted DynamoDB item that was removed by mistake two days ago. Which feature allows this?
A: Point-in-time recovery
B: Time to live (TTL)
C: DynamoDB Streams
D: DynamoDB Accelerator (DAX)
K: A
G: ## Point-in-time recovery in DynamoDB
**Point-in-time recovery (PITR)** continuously backs up a DynamoDB table. Once enabled, you can restore the table to any second within the recovery period, which is up to the last 35 days (the period is configurable from 1 to 35 days).
## How a restore works
A PITR restore always creates a **new table**; it does not modify the existing one. To recover one deleted item:
- Restore the table to a time just before the deletion, for example 10:14 two days ago, into a new table.
- Read the item from the restored table and write it back into the production table.
- Delete the temporary table.
PITR must already be enabled before the mistake happens.
W: Point-in-time recovery: continuous backups let you restore the table to the moment before the item was deleted, then copy the item back.
X: B=Time to live: TTL automatically deletes items after a timestamp attribute expires. It removes data; it has no way to bring a deleted item back.
C=DynamoDB Streams: a stream keeps item-level change records for only 24 hours, so a deletion from two days ago is no longer available there, and a stream is not a restore feature.
D=DynamoDB Accelerator: DAX is an in-memory read cache that speeds up reads; it holds no backups and cannot restore deleted data.
T: Recovering data deleted days ago needs a backup feature (PITR, up to 35 days); TTL deletes items, Streams keep only 24 hours and DAX is just a cache.
V: Amazon DynamoDB

S: A company wants to route events from AWS services and SaaS applications to different targets based on event content. Which service fits?
A: Amazon EventBridge

G: ## Event buses and rules
**Amazon EventBridge** receives events on an **event bus**: the default bus gets events from AWS services, partner event buses get events from SaaS applications (for example Zendesk or Datadog), and custom buses take your own events.
A **rule** has an **event pattern** that matches on the event's content, and sends matches to targets such as Lambda, Step Functions, SQS, SNS or API destinations.

S: An application tier must be reachable only from the web tier, and the database only from the application tier. Which design fits?
A: Public subnets for each tier with the security groups open to 0.0.0.0/0
B: Network ACLs on each subnet that allow traffic from anywhere in the VPC CIDR range

G: ## Chaining security groups between tiers
A **security group** is a stateful firewall on each network interface. It has only allow rules, and a rule's source can be another security group instead of a CIDR.

W: One security group per tier: each tier accepts traffic only from the group of the tier in front of it, which enforces exactly web to app to database and nothing else.

B=NACLs allowing the whole VPC CIDR: any subnet in the VPC could reach the database directly, so the tiers are not isolated from each other.
C=One shared group allowing all inbound: a single permissive group lets any source reach any tier and cannot express per-tier rules.
T: Tier isolation comes from one security group per tier with rules that reference the previous tier's group, not from broad CIDR or shared rules.

S: A web tier in public subnets and an application tier in private subnets must be isolated so only the web tier can reach the application tier on port 8080. Which control fits?
A: Public IP addresses on the application instances, protected by a host firewall script

G: ## Security groups that reference other security groups
A **security group** is a stateful firewall attached to network interfaces. An inbound rule's source can be a CIDR or **another security group**.

- Instances can be added or replaced by Auto Scaling and the rule still applies, because it follows group membership, not IPs.

D=NACL allowing everything: allowing all traffic between all subnets is the opposite of isolation and does nothing to limit access to port 8080.
T: Isolate tiers by allowing a port from a source security group; routes and permissive NACLs do not restrict which instances can connect.

G: ## Stopping an RDS instance
You can stop an Amazon RDS DB instance (or an Aurora cluster) when it is not needed. While it is stopped:
- you are **not billed for instance hours**, which is usually the largest part of the bill;

Use Amazon EventBridge Scheduler to call the RDS `StopDBInstance` and `StartDBInstance` APIs at set times, or deploy the Instance Scheduler on AWS solution with tags.
