@ SAA-C03 D1 T1.3 expert troubleshooting
S: A security account owns a customer managed KMS key that encrypts the EBS snapshots behind a hardened AMI, and it shares the AMI with a workload account. The key policy already allows the workload account (its account principal) kms:Encrypt, kms:Decrypt, kms:ReEncrypt*, kms:GenerateDataKey*, kms:DescribeKey, and kms:CreateGrant. An engineer in the workload account launches the AMI manually without problems. However, an Auto Scaling group in the workload account that uses the AMI through a launch template, with the default service-linked role, fails every launch with "Client.InternalError: Client error on launch". The security team will not add individual workload-account roles to its key policy, and every volume must stay encrypted with the security account's key. What should the team do?
A: From the workload account, create a KMS grant on the security account's key that names the workload account's AWSServiceRoleForAutoScaling role as the grantee principal
B: In the security account, add the workload account's AWSServiceRoleForAutoScaling role ARN as a principal in the key policy statement that allows kms:CreateGrant
C: In the workload account, attach an inline policy to the AWSServiceRoleForAutoScaling role that allows kms:Decrypt and kms:CreateGrant on the key's ARN
D: Copy the AMI into the workload account and re-encrypt its snapshots with the aws/ebs AWS managed key, which the service-linked role can already use
K: A
G: ## Who actually uses the key when Auto Scaling launches an instance
When you call RunInstances yourself, **your** principal needs permission on the KMS key of an encrypted snapshot. When an Auto Scaling group launches the instance, the **service-linked role** `AWSServiceRoleForAutoScaling` makes the calls. Its predefined permissions cover AWS managed keys only, never customer managed keys, so it needs explicit access. Without it, the launch fails with `Client.InternalError: Client error on launch`.
## The cross-account pattern
When the key lives in another account than the Auto Scaling group, the documented setup has two steps, in this order:
- The key owner's **key policy** allows the other **account** (`arn:aws:iam::<workload>:root`) to use the key and to call `kms:CreateGrant`. This alone gives no user access.
- From the workload account, a principal with `kms:CreateGrant` permission runs `aws kms create-grant` with `--grantee-principal` set to the workload account's service-linked role ARN and the operations Encrypt, Decrypt, ReEncryptFrom, ReEncryptTo, GenerateDataKey, GenerateDataKeyWithoutPlaintext, DescribeKey, and CreateGrant.
## Reading the evidence
The manual launch works because the engineer's own role has the permissions; only the service-linked role is missing access. The key policy already has step 1, so only the grant is missing.
W: A=Grant to the service-linked role: the grant delegates the key permissions that the workload account already holds to the Auto Scaling service-linked role, which is the documented cross-account method and needs no further key policy change.
X: B=Service-linked role in the key policy: AWS documents a grant combined with the key policy for cross-account use, and this approach names individual workload-account roles in the key policy, which the security team refuses.
C=Inline policy on the service-linked role: the permissions of a service-linked role are defined by the service; administrators can view but not edit them, so no policy can be attached to it.
D=Re-encrypt with aws/ebs: this would make the launch work, but the volumes would no longer use the security account's key, which breaks the encryption requirement.
T: Auto Scaling launches use its service-linked role, so a cross-account customer managed key needs a key policy for the account plus a grant to that role.
V: Amazon EC2 Auto Scaling, AWS KMS, Amazon EBS

@ SAA-C03 D1 T1.1 expert troubleshooting
S: A finance bucket's policy has one Deny statement for s3:* on the bucket and its objects, with a NotIpAddress condition on aws:SourceIp that lists the office range 203.0.113.0/24 and 198.51.100.7, the Elastic IP of the VPC's NAT gateway. Reporting instances in private subnets used to reach the bucket through that NAT gateway. To cut NAT data processing charges, the network team added an S3 gateway endpoint, vpce-0a1b2c, to the private route tables. Since then the instances get 403 AccessDenied from the bucket, while office users still succeed. The bucket must stay reachable only from the office range and through this one endpoint, and the endpoint must stay. What should the solutions architect change?
A: Add a StringNotEquals condition on aws:SourceVpce with the value vpce-0a1b2c to the same Deny statement, so only requests that fail both tests are denied
B: Add the VPC's private CIDR 10.40.0.0/16 to the aws:SourceIp values in the Deny statement's NotIpAddress condition, so the instances' addresses match
C: Add a separate Allow statement for s3:* with an aws:SourceVpce condition equal to vpce-0a1b2c, so requests through the endpoint are allowed next to the Deny
D: Attach an endpoint policy to vpce-0a1b2c that allows s3:* on the finance bucket for the reporting role, so the endpoint itself authorizes those requests
K: A
G: ## What changes when traffic moves to a VPC endpoint
Through a NAT gateway, S3 sees the request coming from the NAT gateway's public IP, so `aws:SourceIp` matched `198.51.100.7`. Through a **gateway endpoint**, the request reaches S3 over the endpoint and `aws:SourceIp` is **not available**; AWS documents that you can't use it for requests that traverse a VPC endpoint and should use VPC keys such as `aws:SourceVpce`, `aws:SourceVpc`, or `aws:VpcSourceIp` instead.
## How a Deny with two conditions behaves
Within one statement, different condition operators are combined with a logical **AND**. A Deny with both conditions:
- `NotIpAddress aws:SourceIp [office]`
- `StringNotEquals aws:SourceVpce vpce-0a1b2c`
fires only when the request is from outside the office **and** not through that endpoint. Office users fail the first test, endpoint traffic fails the second, and everything else is denied.
## Why an Allow cannot fix it
An explicit Deny always overrides any Allow, in bucket policies and endpoint policies alike, so the fix must change when the Deny applies.
W: A=Add aws:SourceVpce to the Deny: with AND logic, the Deny now matches only requests that are neither from the office range nor through vpce-0a1b2c, which is exactly the required perimeter.
X: B=Private CIDR in aws:SourceIp: aws:SourceIp is not present for requests through a VPC endpoint and only works with public ranges, so the private CIDR never matches; use aws:VpcSourceIp for private addresses.
C=Separate Allow statement: the Deny still matches endpoint traffic because aws:SourceIp is not the office range, and an explicit Deny overrides the new Allow.
D=Endpoint policy Allow: an endpoint policy can only further limit what passes through the endpoint; the bucket policy's explicit Deny still applies to those requests.
T: After adding a VPC endpoint, replace or combine aws:SourceIp conditions with aws:SourceVpce, because S3 no longer sees a public source IP.
V: Amazon S3, Amazon VPC, AWS IAM

@ SAA-C03 D1 T1.1 expert troubleshooting
S: A shared-services account stores a database credential in AWS Secrets Manager. The secret is encrypted with the default aws/secretsmanager key and rotated every 30 days by a Lambda function in that account. An application role in a separate workload account must now read the secret at startup. The workload role's identity policy already allows secretsmanager:GetSecretValue on the secret's ARN and kms:Decrypt on every KMS key in the shared-services account, yet its calls fail with AccessDenied. Security rules: the credential must live in exactly one secret so rotation stays in one place, and no principal other than that one workload role may gain access. Which THREE actions together grant the access? (Select THREE)
A: Re-encrypt the secret with a new customer managed KMS key in the shared-services account, and give the rotation function's role access to that key
B: Add a statement to the new customer managed key's key policy that allows the workload role's ARN to use kms:Decrypt and kms:DescribeKey
C: Attach a resource-based policy to the secret that allows the workload role's ARN, and only that ARN, to call secretsmanager:GetSecretValue
D: Add a statement to the aws/secretsmanager key's policy that allows the workload role's ARN to use kms:Decrypt, so the secret keeps its current key
E: Replicate the secret into the workload account with ReplicateSecretToRegions, so the application role reads a local replica that rotation keeps in sync
F: Attach a resource-based policy to the secret that allows the workload account's root principal, so the account's administrators can delegate access
K: A,B,C
G: ## Cross-account access to a secret needs three doors
For a principal in another account, Secrets Manager requires permission in **both** a resource policy and an identity policy, and the principal also needs to use the **KMS key** that encrypts the secret:
- **Identity policy** in the workload account: `secretsmanager:GetSecretValue` on the secret and `kms:Decrypt` on the key (already in place here).
- **Resource policy** on the secret in the shared-services account that names the workload role.
- **Key policy** on the encryption key that allows the workload role `kms:Decrypt`.
## Why the current key blocks everything
The secret uses `aws/secretsmanager`, an **AWS managed key**. AWS managed keys can only be used by principals in their own account, and you can't change their policies. AWS states that you can't use `aws/secretsmanager` for cross-account access: you must switch the secret to a customer managed key. The rotation function then needs permission on the new key too, or the next rotation fails.
W: A=Customer managed key: only a customer managed key can have a key policy that admits another account; the rotation function needs it as well to keep rotating the secret.
B=Key policy for the workload role: the cross-account role can decrypt only when the key policy names it, and its identity policy already allows kms:Decrypt.
C=Secret resource policy for one role: cross-account access needs the resource policy, and naming only the role ARN keeps every other principal out.
X: D=Edit the aws/secretsmanager key policy: AWS managed keys have policies that you cannot manage, and they cannot be used for cross-account access at all.
E=ReplicateSecretToRegions: replication creates replicas in other Regions of the same account, not in another account, and it would create a second copy of the credential.
F=Resource policy for the account root: this trusts the whole workload account, so its administrators could give any principal access, which breaks the one-role rule.
T: To share a secret across accounts, use a customer managed key and allow the role in the secret's resource policy, the key policy, and its own identity policy.

@ SAA-C03 D1 T1.2 expert tradeoff
S: A document service on Amazon ECS on Fargate emails each partner a download link to its quarterly report in a private S3 bucket. The task role creates S3 presigned URLs with a 7-day expiration, but partners report 403 responses with an ExpiredToken error when they open a link more than a few hours after the email arrives. Security policy bans long-term IAM user access keys, and the bucket must stay private. Links must work for the full 7 days, and if the signing material ever leaks, the company must be able to stop honoring all outstanding links at once without rotating anything in IAM. What should the solutions architect do?
A: Front the bucket with a CloudFront distribution that uses origin access control, and issue CloudFront signed URLs from a trusted key group with a 7-day expiry
B: Raise the ECS task role's maximum session duration to 12 hours, so the credentials that sign each 7-day presigned URL remain valid long enough for partners
C: Have the task call AssumeRole on a dedicated signing role with DurationSeconds set to 604,800, and sign the presigned URLs with that session's credentials
D: Create a signing IAM user, store its access keys in Secrets Manager with 90-day rotation, and sign the 7-day presigned URLs with those long-term keys
K: A
G: ## Why the presigned URLs die early
A presigned URL is only as valid as the **credentials that signed it**. S3 checks both the configured expiration and the signer's credentials, and the URL stops working at whichever comes first:
- IAM role credentials: the URL expires when the role session expires, even if a longer expiration was set.
- ECS task role credentials are short-lived temporary credentials (AWS cites about 6 hours for role credentials on EC2), which matches the "few hours" in the evidence.
- `AssumeRole` sessions last 900 seconds to the role's maximum session duration, which can be at most **12 hours** (43,200 seconds).
So no role-based signer can produce a 7-day S3 presigned URL. Only long-term IAM user keys can, and they are banned here.
## Signing at CloudFront instead
CloudFront signed URLs are verified with a **public key in a trusted key group**; the private key belongs to the application and is not tied to an IAM session, so the expiry in the policy is what counts. Origin access control keeps the bucket private behind the distribution. If the private key leaks, removing its public key from the key group makes CloudFront stop accepting every URL signed with it.
W: A=CloudFront signed URLs with a key group: the expiry is independent of IAM session lifetimes, the bucket stays private through OAC, and removing the public key from the key group revokes all outstanding links at once.
X: B=12-hour maximum session: ECS manages and rotates task role credentials, and even a 12-hour session is far shorter than the 7 days the links must work.
C=DurationSeconds 604,800: AssumeRole accepts at most 43,200 seconds (12 hours), so the call fails, and a session could never cover 7 days anyway.
D=Signing IAM user keys: long-term keys would make 7-day links work, but they are exactly what security policy bans, and revoking links would mean rotating IAM keys.
T: An S3 presigned URL never outlives the credentials that signed it; for long-lived private links, use CloudFront signed URLs with a trusted key group.
V: Amazon S3, Amazon CloudFront, Amazon ECS, AWS STS

@ SAA-C03 D1 T1.2 expert troubleshooting
S: Application instances run Amazon Linux in private subnets behind an Application Load Balancer and call a payment provider's HTTPS API through a NAT gateway in a public subnet. The security team replaced the private subnets' network ACL with one that has these rules. Inbound: allow TCP 8080 from the ALB subnets; then deny all. Outbound: allow TCP 443 to 0.0.0.0/0, allow TCP 1024-65535 to the ALB subnets; then deny all. The public subnets keep the default network ACL. Web pages still load, but every payment call now times out. VPC flow logs on an instance's network interface show 10.0.2.15 to 203.0.113.50, destination port 443, ACCEPT, and 203.0.113.50 to 10.0.2.15, source port 443, destination port 45512, REJECT. What should the team add?
A: An inbound rule in the private subnets' network ACL that allows TCP 32768-65535 from 0.0.0.0/0, placed before the final deny rule
B: An inbound rule in the private subnets' network ACL that allows TCP 443 from 0.0.0.0/0, placed before the final deny rule
C: An outbound rule in the private subnets' network ACL that allows TCP 1024-65535 to 0.0.0.0/0, the port range a NAT gateway uses
D: An inbound rule in the instances' security group that allows TCP 443 from 0.0.0.0/0, so the payment provider's responses can return
K: A
G: ## Stateless network ACLs need a rule for the return traffic
Security groups are **stateful**: a response to an allowed request is allowed automatically. Network ACLs are **stateless**: the response is a separate packet that must match its own rule.
When an instance is the **client**, its operating system picks the source port of the connection (the **ephemeral port**). Many Linux kernels, including the Amazon Linux kernel, use `32768-61000`. The server's reply comes back **to that ephemeral port**, so the inbound ACL must allow it.
## Reading the flow log
- `10.0.2.15 -> 203.0.113.50:443 ACCEPT`: the outbound request left (outbound 443 is allowed). Through a NAT gateway the instance still addresses the provider's public IP, so the reply arrives from that public IP.
- `203.0.113.50:443 -> 10.0.2.15:45512 REJECT`: the reply to ephemeral port 45512 hit the inbound "deny all" rule.
## Why web pages still work
The ALB traffic arrives on 8080 (allowed inbound) and the replies go back to the ALB's ports 1024-65535 (allowed outbound).
W: A=Inbound TCP 32768-65535 from 0.0.0.0/0: it admits replies addressed to the Amazon Linux ephemeral ports, including 45512, which is the rejected packet in the flow log.
X: B=Inbound TCP 443: an ACL rule matches the destination port, and the replies are sent to port 45512, not 443, so they are still rejected.
C=Outbound 1024-65535: the NAT gateway's port range matters for the ACL of the NAT gateway's subnet; the flow log shows the outbound request was already accepted and the inbound reply was rejected.
D=Security group inbound 443: security groups are stateful and already allow responses to the instance's own outbound connections; the reject comes from the stateless network ACL.
T: When an instance is the client, its subnet's network ACL must allow inbound replies to the client's ephemeral ports, not to the server's port.

@ SAA-C03 D1 T1.2 expert troubleshooting
S: A company inspects all traffic between spoke VPCs with stateful firewall instances in an inspection VPC attached to a transit gateway. The inspection VPC has one firewall instance per Availability Zone in AZ-a and AZ-b; each transit gateway attachment subnet routes 0.0.0.0/0 to the firewall in the same zone. Spoke VPC 1 has workloads only in AZ-a, and spoke VPC 2 has workloads only in AZ-b. Connections between two instances in the same zone work, but TCP sessions between spoke VPC 1 and spoke VPC 2 fail, and the firewall logs show SYN-ACK packets dropped as out of state. The inspection design must stay as is. What should the network team change?
A: Enable appliance mode support on the transit gateway attachment of the inspection VPC
B: Enable appliance mode support on the transit gateway attachments of both spoke VPCs
C: Add a subnet in AZ-b to spoke VPC 1's transit gateway attachment and a subnet in AZ-a to spoke VPC 2's attachment
D: Turn on equal-cost multipath routing support on the transit gateway so return traffic can use either firewall
K: A
G: ## How the transit gateway picks an Availability Zone
By default, a transit gateway tries to keep traffic in the **Availability Zone where it entered**. When a flow goes from spoke VPC 1 (AZ-a) to spoke VPC 2 (AZ-b) through the inspection VPC:
- the request enters in AZ-a and is sent to the inspection VPC attachment in AZ-a, so the **AZ-a firewall** sees the SYN;
- the reply enters from spoke VPC 2 in AZ-b and goes to the attachment in AZ-b, so the **AZ-b firewall** sees the SYN-ACK.
The AZ-b firewall never saw the SYN, so a stateful device drops the reply as out of state. This is **asymmetric routing**.
## Appliance mode
When you enable **appliance mode support** on the VPC attachment **in which the appliance is located**, the transit gateway uses the same Availability Zone of that attachment for the whole life of a flow, in both directions. Both packets of the session then reach the same firewall. Network Firewall and Gateway Load Balancer network function attachments turn it on automatically; a self-managed inspection VPC needs it set by hand.
W: A=Appliance mode on the inspection VPC attachment: the transit gateway then pins each flow to one Availability Zone of the inspection VPC, so the same firewall sees the request and the reply.
X: B=Appliance mode on the spoke attachments: the setting matters on the attachment of the VPC that holds the stateful appliance; on the spokes it does not stop the inspection VPC traffic from switching zones.
C=Extra spoke subnets: adding zones to the spoke attachments changes where spoke traffic enters, but replies can still enter and be inspected in a different zone than the request.
D=ECMP support: equal-cost multipath spreads traffic over VPN or Connect paths; it does not keep a flow on one firewall and would make asymmetry more likely.
T: For stateful appliances behind a transit gateway, enable appliance mode on the inspection VPC's attachment so both directions of a flow use the same zone.
V: AWS Transit Gateway, Amazon VPC, Amazon EC2

@ SAA-C03 D1 T1.2 expert troubleshooting
S: A team runs Docker containers in the default bridge network on EC2 instances that it manages itself, without Amazon ECS. Code in the containers uses an AWS SDK and gets credentials from the instance profile through the instance metadata service. To meet a new security baseline, the team updated the launch template to set HttpTokens to required, keeping all other metadata options at their defaults. Agents running directly on the host still work, but SDK calls inside the containers now hang and then fail to find credentials. The baseline requires IMDSv2 only, and the metadata token must not be usable more than one network hop beyond the containers. What should the team change in the launch template?
A: Set HttpPutResponseHopLimit to 2 and keep HttpTokens set to required
B: Set HttpTokens to optional for these instances so containers can use IMDSv1
C: Enable HttpProtocolIpv6 so containers reach the IPv6 metadata endpoint instead
D: Keep the defaults and pass the AWS Region to each container as an environment variable
K: A
G: ## The IMDSv2 token and the hop limit
IMDSv2 is session based: a client first sends a `PUT` request for a token, then uses the token on every metadata request. The IP packets of the `PUT` **response** carry a hop limit (`HttpPutResponseHopLimit`), which defaults to **1** for a launch template that does not set it.
In a container environment, the container is **one additional network hop** from the instance. With a hop limit of 1, the token response never reaches the container, so the SDK waits, may retry, and fails if it requires IMDSv2. AWS recommends raising the hop limit to **2** in container environments, or passing settings such as the Region directly to the container.
## Picking the value
- Hop limit 2: host processes and containers on the bridge network receive the token.
- Larger values would let the token travel further, which the baseline forbids.
W: A=Hop limit 2 with IMDSv2 required: the token response survives the extra hop into the bridge network, and IMDSv1 stays disabled as the baseline demands.
X: B=HttpTokens optional: the SDK could fall back to IMDSv1, but that re-enables the version the baseline explicitly removes.
C=IPv6 metadata endpoint: the IPv6 endpoint uses the same IMDSv2 token flow and the same hop limit, so the token still does not reach the containers.
D=Pass the Region as a variable: this avoids one metadata lookup, but credentials still come from the metadata service, so the credential calls keep failing.
T: Containers on EC2 that use IMDSv2 need a PUT response hop limit of 2, because the container is one network hop beyond the instance.
V: Amazon EC2, Instance Metadata Service, Docker

@ SAA-C03 D1 T1.1 expert use-case
S: In a shared account, 40 developers create and update Lambda functions. Each function must run with one of the pre-approved execution roles named app-lambda-*, which trust lambda.amazonaws.com. The account also holds older admin roles that trust both Lambda and EC2; developers must never be able to give a function one of those roles, or hand an app-lambda-* role to any other service. Auditors also want a monthly report of which role each function received and who set it. A first attempt tagged the approved roles approved=true and allowed iam:PassRole only on resources with that tag, but it behaved inconsistently. Which TWO actions meet the requirements? (Select TWO)
A: Allow iam:PassRole only on arn:aws:iam::<account>:role/app-lambda-*, with an iam:PassedToService condition equal to lambda.amazonaws.com
B: Allow iam:PassRole on all roles when aws:ResourceTag/approved equals true, adding an iam:PassedToService condition for lambda.amazonaws.com
C: Build the report from CloudTrail CreateFunction and UpdateFunctionConfiguration events, which record the role passed and the identity that called
D: Build the report from CloudTrail events whose event name is PassRole and event source is iam.amazonaws.com, filtered to the app-lambda-* roles
E: Add a condition to each admin role's trust policy that lets lambda.amazonaws.com assume it only when aws:SourceAccount equals this account
K: A,C
G: ## What iam:PassRole controls
When a user creates a function with an execution role, Lambda checks whether the **caller** has `iam:PassRole` on that role. Two parts of the policy limit it:
- the **Resource** element limits which roles can be passed (here, names that begin with `app-lambda-`);
- the `iam:PassedToService` condition limits which service principal may receive the role (here, `lambda.amazonaws.com`).
AWS warns not to control PassRole with role tags and `ResourceTag` conditions, because that approach does not give reliable results. That explains the inconsistent first attempt.

- **DNS caching**: clients keep the old answer for the record's TTL. An **alias record** to an AWS resource cannot have its own TTL; Route 53 uses the resource's default, and Elastic Load Balancing's DNS entries use **60 seconds**.
## Working the numbers
- Today: 30 s x 3 = 90 s + 60 s TTL = **150 s**, matching the drill.
- 10 s x 2 = 20 s + 60 s = **80 s**, under 90 s, and one failed check is tolerated.
- 30 s x 1 = 30 s + 60 s = **90 s**, not under 90 s, and a single failure triggers failover.
## A setting you cannot edit
The **request interval cannot be changed** after a health check is created. Moving to the fast (10-second) interval, which costs extra, means creating a new health check and associating it with the record.
W: A=New 10-second check with threshold 2: detection drops to about 20 seconds, the total is about 80 seconds, and two consecutive failures are still needed.
X: B=Edit the existing interval: Route 53 does not allow the request interval of an existing health check to be changed.
C=TTL of 10 seconds: alias records pointing to a load balancer use the load balancer's 60-second TTL and cannot be given their own, and 90 seconds of detection already misses the target.
D=Threshold 1: about 90 seconds in total is not under 90 seconds, and a single failed check would now trigger failover.
T: Route 53 failover time is about interval x failure threshold plus the TTL; alias records to ELB keep 60 seconds, and the interval needs a new health check.

S: A standard accelerator in AWS Global Accelerator has two endpoint groups, us-east-1 and eu-west-1, each with one Application Load Balancer endpoint, and both traffic dials at 100 percent. Since Tuesday all traffic, including from US clients, has gone to eu-west-1, and the accelerator shows the us-east-1 endpoint as unhealthy. Yet the us-east-1 ALB's main /app/* target group has 12 healthy targets, and direct tests against the ALB succeed. On Tuesday a team stopped both instances of a /legacy-reports/* target group on that ALB, which a listener rule still uses. US users must return to us-east-1 while the legacy path stays offline. What should the team do?
A: Remove the /legacy-reports/* listener rule and its target group from the us-east-1 ALB, so that every remaining target group has at least one healthy target
B: Raise the threshold count and shorten the interval in the us-east-1 endpoint group's Global Accelerator health check settings, so the ALB is rechecked faster
C: Change the /legacy-reports/* target group's success codes to 200-499, so its health checks pass while that path deliberately returns errors to users

G: ## How Global Accelerator judges an ALB endpoint
For load balancer endpoints, Global Accelerator does **not** use its own health check settings (port, protocol, interval, threshold count); those apply only to EC2 instance and Elastic IP endpoints. It relies on the load balancer's target group health:
- an **Application Load Balancer is healthy only if every target group has at least one healthy target**;
- a Network Load Balancer is healthy if at least one Availability Zone is healthy.
An unhealthy endpoint gets no new connections, so traffic goes to the next endpoint group, here eu-west-1.
## Reading the evidence
The main target group is fine, but the legacy target group's only two instances are stopped, so it has **zero healthy targets**. One empty target group is enough to make the whole ALB unhealthy in the accelerator's view.
## Traffic dials and weights
A traffic dial limits the share of traffic an endpoint group accepts, and a weight divides traffic among endpoints in a group; neither makes an unhealthy endpoint receive traffic.
W: A=Remove the empty target group: with the stopped target group detached, every remaining target group has a healthy target, so the accelerator marks the ALB healthy and US traffic returns.
X: B=Accelerator health check settings: these settings are not used for ALB or NLB endpoints, whose health comes from Elastic Load Balancing target groups.
C=Success codes 200-499: the stopped instances do not answer health checks at all, so any response code range still fails, and the target group stays without a healthy target.
D=Weight 255: weights only split traffic among healthy endpoints in a group; an unhealthy endpoint still receives no new connections.

@ SAA-C03 D2 T2.1 expert troubleshooting
S: A Lambda function with a 60-second timeout consumes a standard SQS queue (4-day retention) through an event source mapping with a 20-second batching window. The queue's visibility timeout is 60 seconds, and its redrive policy moves messages to a dead-letter queue after a maxReceiveCount of 1; the DLQ also keeps messages for 4 days. During bursts, some messages are processed twice, and messages land in the DLQ with no function error logged when Lambda is throttled. After weekend backlogs, messages can wait up to 2 days before their first receive, and operations needs 7 full days to review anything in the DLQ. Which THREE changes meet these needs? (Select THREE)
A: Set the source queue's visibility timeout to 380 seconds, six times the function timeout plus the batching window
B: Set the source queue's visibility timeout to 360 seconds, six times the function timeout with no batching allowance
C: Set the redrive policy's maxReceiveCount to 5, so throttled batches get several chances before moving to the DLQ
D: Keep maxReceiveCount at 1 and turn on ReportBatchItemFailures, so only the messages that really failed return to the queue
E: Set the dead-letter queue's retention period to 14 days, longer than the source queue's 4-day retention period
F: Set the dead-letter queue's retention period to 7 days, the same length as the operations team's review window
K: A,C,E
G: ## Visibility timeout for Lambda consumers
When Lambda reads a batch, the messages become invisible for the **visibility timeout**. If they reappear before the batch is finished or retried after throttling, another invocation processes them again. AWS recommends a visibility timeout of at least **six times the function timeout**, plus `MaximumBatchingWindowInSeconds` when a batching window is used: 6 x 60 + 20 = **380 seconds**.
## maxReceiveCount and throttling
Each receive counts toward `maxReceiveCount`, even when the invocation is **throttled** and the function never runs. With a value of 1, a single throttled attempt sends the message to the DLQ. AWS recommends **at least 5** for Lambda sources.
## DLQ retention in standard queues
For **standard** queues, a message's expiration is based on its **original enqueue timestamp**, which does not change when it moves to the DLQ. AWS's best practice is a DLQ retention **longer than the source queue's**.
- A message can wait 2 days before its first receive, so with a 7-day review window it must survive about 9 days from enqueue.
- 4 or 7 days of DLQ retention would delete it early; 14 days (the maximum) keeps it for at least 12 days after a 2-day wait.
W: A=380-second visibility timeout: six times the 60-second timeout plus the 20-second batching window keeps messages hidden through processing and throttling retries, stopping the duplicates.
C=maxReceiveCount 5: throttled receives no longer send messages straight to the DLQ, because each message gets several attempts first.
E=14-day DLQ retention: because the DLQ keeps the original enqueue time, only a retention well beyond the 9 days needed (2-day wait plus 7-day review) keeps every message long enough.
X: B=360 seconds: the batching window adds up to 20 seconds before the function starts, so the recommended value is 380 seconds, not 360.
D=maxReceiveCount 1 with partial batch responses: partial batch responses help with function errors, but a throttled receive still counts, so one throttle still moves the message to the DLQ.
F=7-day DLQ retention: the clock keeps running from the original enqueue time, so a message that waited 2 days would be deleted after only 5 days in the DLQ.
T: For Lambda on SQS, set visibility to 6x timeout plus batching window, maxReceiveCount of at least 5, and DLQ retention longer than the source queue's, since standard queues keep the enqueue time.
V: Amazon SQS, AWS Lambda
