@ SAA-C03 D1 T1.1 advanced use-case
S: A company runs 40 member accounts in AWS Organizations. Only a pipeline role named NetworkDeployRole, which exists in every account, may change route tables, internet gateways, and VPC peering connections. Account administrators hold AdministratorAccess and must be blocked from these changes even if they edit their own IAM policies. The security team wants a preventive control that needs no per-account IAM work. Which solution meets these requirements with the LEAST operational overhead?
A: Attach an SCP to the organization root that denies the networking actions unless aws:PrincipalArn matches the NetworkDeployRole ARN pattern used in every account
B: Attach a permissions boundary that excludes the networking actions to every administrator role, and leave NetworkDeployRole as the only role without that boundary
C: Attach an SCP that allows the networking actions only for NetworkDeployRole, and keep the default FullAWSAccess SCP attached to the root and every OU
D: Deploy an AWS Config rule in every account that detects route table and gateway changes and calls a remediation runbook that reverts each change
K: A
G: ## How SCPs limit administrators
A service control policy (SCP) sets the maximum permissions for every IAM user and role in a member account, including the account's root user. An administrator cannot grant around it: if an SCP denies an action, `AdministratorAccess` does not help.
## Exempting one role
SCPs accept a `Condition` element. A deny statement with `ArnNotLike` on `aws:PrincipalArn` (for example `arn:aws:iam::*:role/NetworkDeployRole`) denies everyone except that role. For roles, `aws:PrincipalArn` holds the role ARN, not the session ARN, so the condition works for every session of the pipeline role.
## Limits to remember
- SCPs do not affect the management account or service-linked roles.
- Allow statements in an SCP only filter what other SCPs pass; with `FullAWSAccess` still attached, an extra allow restricts nothing.
W: SCP deny with PrincipalArn exception: one policy at the root blocks every principal in all member accounts, administrators included, and the ArnNotLike condition leaves the pipeline role untouched.
X: B=Permissions boundary: account administrators can remove or change boundaries on their own roles, so the control is not preventive against the very people it targets, and it needs work in each account.
C=Allow-list SCP with FullAWSAccess: SCP allows are intersected across policies; while FullAWSAccess stays attached, the narrower allow does not remove anything from administrators.
D=Config auto-remediation: Config detects a change after it has happened and then reverts it, so it is a detective control with a window of exposure, not a preventive one.
T: To block administrators in member accounts with one exception, use an SCP deny with an aws:PrincipalArn condition.
V: AWS Organizations, AWS IAM

@ SAA-C03 D1 T1.1 advanced troubleshooting
S: A platform team lets developers create IAM roles only when a managed permissions boundary named DevBoundary is attached; developers cannot edit DevBoundary. DevBoundary allows S3, SQS, and CloudWatch Logs actions. A developer's new Lambda role has an identity policy that allows dynamodb:PutItem on the orders table, yet every write fails with AccessDenied. The SCPs allow DynamoDB. The boundary model must stay in place. What should be done to let the function write to the table?
A: The platform team adds dynamodb:PutItem on the orders table ARN to DevBoundary, so the boundary and the identity policy both allow the write
B: The developer adds a resource-based policy to the orders table that grants dynamodb:PutItem to the Lambda execution role ARN in the same account
C: The developer attaches the AWS managed AmazonDynamoDBFullAccess policy to the Lambda role, so a broader identity policy covers every table action
D: The platform team detaches DevBoundary from this one Lambda role, documents the exception, and reviews the role's identity policy every quarter
K: A
G: ## Effective permissions with a boundary
A permissions boundary sets the **maximum** permissions of a user or role. The effective permissions are the **intersection** of the identity-based policies and the boundary (and any SCPs). An action that the identity policy allows but the boundary does not mention is implicitly denied.
## Resource-based policies and role boundaries
IAM documents a special case: within the same account, a resource-based policy that names an IAM **user** ARN is not limited by the boundary. A resource-based policy that names an IAM **role** ARN *is* limited by an implicit deny in the role's permissions boundary. Only a grant to the exact role *session* ARN bypasses it, which is impractical for Lambda.
## The fix
Widen the boundary in a controlled way, for example by adding the DynamoDB write action scoped to approved table ARNs.
W: Add the action to DevBoundary: the write needs an allow in both the identity policy and the boundary; adding it to the boundary keeps the model and removes the implicit deny.
X: B=Table resource policy for the role ARN: a resource-based policy that grants permissions to a role ARN is still limited by the implicit deny in that role's permissions boundary.
C=AmazonDynamoDBFullAccess: a broader identity policy changes nothing, because the boundary still allows no DynamoDB actions and the intersection stays empty.
D=Detach the boundary: it would work, but it breaks the rule that every developer-created role keeps DevBoundary.
T: An action must be allowed by both the identity policy and the permissions boundary; a resource policy naming the role ARN does not bypass the boundary.
V: AWS IAM, Amazon DynamoDB, AWS Lambda

@ SAA-C03 D1 T1.1 advanced troubleshooting
S: A nightly export runs for about six hours on an EC2 instance. It uses its instance profile role to call AssumeRole on a partner account role with DurationSeconds set to 28800, and the partner already raised that role's maximum session duration to 12 hours. The call fails with a validation error. Company policy forbids long-term access keys. What should the solutions architect change so the export can run to completion?
A: Request DurationSeconds of 3600 or less and let the SDK credential provider assume the partner role again before each set of credentials expires
B: Ask the partner to raise the role's maximum session duration from 12 hours to 36 hours, so a single AssumeRole call covers the whole export window
C: Create an IAM user in the partner account, store its access key in Secrets Manager, and have the export read the key when it starts each night
D: Raise the instance profile role's maximum session duration to 12 hours, so the first credentials in the chain last as long as the export runs
K: A
G: ## Role chaining
Role chaining means using one role's temporary credentials to assume a second role. Credentials from an EC2 instance profile are role credentials, so assuming the partner role from them is a chain.
IAM limits a chained role session to **one hour**, regardless of the maximum session duration configured on the target role. If `DurationSeconds` in a chained `AssumeRole` call is greater than 3600, the call fails.
## Long jobs with chained roles
Request a session of up to one hour and refresh: the AWS SDKs' assume-role credential providers call `AssumeRole` again before expiry, so a six-hour job keeps working without long-term keys.
## Other limits
- Maximum session duration on a role can be set up to 12 hours, which applies only to non-chained sessions.
W: One-hour sessions with refresh: chained sessions are capped at one hour, so the export must use short sessions and re-assume the role, which the SDK credential providers do automatically.
X: B=Longer maximum on the partner role: the setting tops out at 12 hours and, more importantly, the one-hour chaining limit applies regardless of it.
C=IAM user access key: it would avoid chaining, but it introduces a long-term access key, which company policy forbids.
D=Longer instance profile session: the instance profile credentials are already refreshed by EC2; the failing call is the chained AssumeRole, which stays capped at one hour.
T: A role assumed from another role's credentials is limited to one-hour sessions; refresh instead of asking for longer ones.
V: AWS STS, AWS IAM, Amazon EC2

@ SAA-C03 D1 T1.1 advanced comparison
S: A SaaS company is building a customer-facing web portal. Each of its 60 business customers wants employees to sign in with that customer's own SAML 2.0 identity provider, routed by email domain. The application must receive standard OIDC JSON Web Tokens and must not create IAM principals for customer users. The company's own staff already use IAM Identity Center with its corporate directory to reach AWS accounts. Which solution meets these requirements?
A: Create an Amazon Cognito user pool, add one SAML identity provider per customer with identifiers matching each email domain, and validate the user pool tokens
B: Add each customer's SAML identity provider to the existing IAM Identity Center instance, and assign the portal as a customer managed application for those users
C: Create one IAM SAML identity provider per customer, and let the portal call AssumeRoleWithSAML so each signed-in user receives temporary role credentials
D: Create an Amazon Cognito identity pool with one SAML provider per customer, and have the portal use the issued AWS credentials as each user's session
K: A
G: ## Customer identities versus workforce identities
- **Amazon Cognito user pools** are user directories for your own applications. A user pool can federate many external SAML 2.0 or OIDC identity providers and issues standard JWTs (ID, access, refresh) to the app. SAML providers can have **identifiers** (such as email domains) so managed login routes each user to the right IdP.
- **Cognito identity pools** exchange a token for temporary **AWS credentials**; they are not a sign-in directory and do not issue app JWTs.
- **IAM Identity Center** gives a workforce single sign-on to AWS accounts and applications. You can have **only one identity source** per organization.
- **IAM SAML providers** with `AssumeRoleWithSAML` return AWS role credentials, not application tokens.
W: Cognito user pool with per-customer SAML IdPs: one user pool federates all 60 IdPs, routes by domain identifier, and gives the portal OIDC-standard JWTs without any IAM principals.
X: B=IAM Identity Center: an organization can have only one identity source, which is already the corporate directory, so 60 customer IdPs cannot be added.
C=IAM SAML providers: each sign-in returns AWS role credentials through IAM roles, which are IAM principals, and the portal gets no OIDC tokens.
D=Cognito identity pool: identity pools hand out AWS credentials, not the user pool JWTs the portal must validate for its own sessions.
T: Use Cognito user pools to federate many customer IdPs into one app; Identity Center is for the workforce and has one identity source.
V: Amazon Cognito, AWS IAM Identity Center, AWS IAM

@ SAA-C03 D1 T1.1 advanced troubleshooting
S: A role in member account 222222222222 has an identity policy allowing s3:* on all resources and a permissions boundary allowing only s3:GetObject and s3:PutObject. An SCP on its OU denies s3:DeleteObject. A bucket in account 333333333333, with ACLs disabled, has a bucket policy that grants this role s3:GetObject and s3:DeleteObject. No other policies apply. Which THREE statements about the role's requests are correct? (Select THREE)
A: GetObject on the bucket in account 333333333333 succeeds, because the identity policy, boundary, SCP, and that bucket's policy all allow it
B: DeleteObject on the bucket in account 333333333333 is denied, and the grant in that bucket policy cannot override the SCP's explicit deny
C: PutObject to the bucket in account 333333333333 is denied, because a cross-account request also needs an allow in that bucket's policy
D: DeleteObject on the bucket in account 333333333333 succeeds, because a resource-based policy in another account takes precedence over the caller's SCP
E: GetObject on a bucket in account 222222222222 with no bucket policy fails, because same-account access also needs a bucket policy naming the role
F: ListBucket on buckets in account 222222222222 succeeds, because the identity policy allows s3:* and the SCP does not deny that action
K: A,B,C
G: ## Same-account evaluation
Inside the principal's own account, a request is allowed when an identity-based policy (or a resource-based policy) allows it and nothing else blocks it. The **permissions boundary** and **SCPs** cap what the identity policy can grant; the effective permissions are the intersection. An explicit deny anywhere wins.
## Cross-account evaluation
For a cross-account request AWS evaluates both sides: the caller's account (identity policy, boundary, SCPs) and the resource account (resource-based policy). The request succeeds only if **both** evaluations return Allow.
## Applying it here
- GetObject: allowed by identity policy, boundary, SCP, and the bucket policy.
- DeleteObject: denied by the SCP (and not in the boundary).
- PutObject cross-account: the caller side allows it, but the bucket policy does not.
W: A=Cross-account GetObject: every layer on both sides allows the action, so the two evaluations both return Allow.
B=DeleteObject: the SCP's explicit deny ends the evaluation in the caller's account; no resource policy in another account can undo it.
C=Cross-account PutObject: the trusting account must allow the action in its resource-based policy, and this bucket policy grants only GetObject and DeleteObject.
X: D=Resource policy beats SCP: there is no such precedence; an explicit deny in any applicable policy, including the caller's SCP, overrides every allow.
E=Same-account needs bucket policy: within one account, an identity policy allow is enough when the boundary and SCP also allow; no bucket policy is required.
F=ListBucket allowed: the permissions boundary allows only GetObject and PutObject, so ListBucket is implicitly denied despite s3:* in the identity policy.
T: Explicit denies win everywhere; boundaries and SCPs cap identity policies; cross-account access needs an allow on both sides.
V: AWS IAM, AWS Organizations, Amazon S3

@ SAA-C03 D1 T1.1 advanced use-case
S: A research bucket serves several partner teams over the internet, and its bucket policy already delegates access control to access points owned by the account. New rule: objects under the restricted/ prefix may be read only by the HPC role from the HPC VPC, which reaches S3 through a gateway endpoint whose policy lists allowed buckets. Partner access point policies cover only other prefixes, and partners must keep that internet access. Which TWO steps meet these requirements? (Select TWO)
A: Create a new access point with a VPC network origin set to the HPC VPC, and grant the HPC role read access to restricted/ in its policy
B: Update the gateway endpoint policy to allow requests to both the new access point ARN and the underlying bucket ARN for the HPC role
C: Change the network origin of the existing internet access point used by partner teams to the HPC VPC, and add a restricted/ statement
D: Add a bucket policy statement that denies every request to the whole bucket unless aws:SourceVpce equals the HPC VPC's gateway endpoint
E: Turn on all four S3 Block Public Access settings for the new access point, so that the restricted/ prefix cannot be read from outside the HPC VPC
K: A,B
G: ## Access points with a VPC network origin
An S3 access point has a **network origin** of `Internet` or `VPC`. With a VPC origin, S3 rejects every request through that access point that does not come from the named VPC. The origin is set **only at creation** and cannot be changed later.
## The endpoint policy must agree
Requests from the VPC travel through the VPC endpoint, and its policy is evaluated too. A request through an access point succeeds only if the **endpoint policy allows both the access point and the underlying bucket**.
## Layered access
- Bucket policy: delegates to access points (already done here).
- Access point policy: which principals and prefixes.
- Network origin: which VPC.
W: A=VPC-origin access point: it confines restricted/ reads to the HPC VPC and scopes the HPC role to the prefix without touching partner access.
B=Endpoint policy update: the gateway endpoint policy lists allowed buckets, so it must also allow the new access point and the bucket or the HPC requests fail.
X: C=Change the existing access point: network origin cannot be changed after creation, and switching the partners' access point would cut off their internet access anyway.
D=Bucket-wide SourceVpce deny: it would protect restricted/, but it also blocks every partner request from the internet to the other prefixes.
E=Block Public Access on the access point: it blocks public grants, not authenticated access from other networks, so it does not tie reads to the HPC VPC.
T: To lock a dataset to one VPC, create a VPC-origin access point and allow both it and the bucket in the endpoint policy.
V: Amazon S3, Amazon VPC

@ SAA-C03 D1 T1.2 advanced use-case
S: A company's on-premises backup servers upload about 5 TB to Amazon S3 every night. The data center connects to a VPC through AWS Direct Connect with a private virtual interface. Security policy forbids sending this traffic to public IP addresses or adding a public virtual interface, and the operations team will not run proxy servers. Which solution meets these requirements?
A: Create an S3 interface VPC endpoint, and point the backup servers at its endpoint-specific DNS names so uploads use private IP addresses
B: Create an S3 gateway VPC endpoint in the VPC, and advertise the S3 prefix list to the data center over the private virtual interface's BGP session
C: Add a public virtual interface on the existing Direct Connect connection, and filter the advertised Amazon prefixes to only the Regional S3 ranges
D: Run an Auto Scaling group of HTTP proxy instances behind a Network Load Balancer, and send S3 traffic from the proxies through a gateway endpoint
K: A
G: ## Two kinds of S3 VPC endpoints
- **Gateway endpoint**: a route-table target for S3 public IP ranges. It is free, but it works only for traffic that starts inside the VPC; it does **not** allow access from on premises or from another Region.
- **Interface endpoint (AWS PrivateLink)**: elastic network interfaces with **private IP addresses** in your subnets. On-premises clients reach them over Direct Connect or Site-to-Site VPN. Clients use endpoint-specific DNS names (or on-premises DNS that resolves to the endpoint), and the endpoint is billed per hour and per GB.
## Choosing
If the traffic originates on premises and must stay on private addresses, the interface endpoint is the managed option.
W: S3 interface endpoint: it gives S3 private IP addresses inside the VPC that the data center reaches over the private virtual interface, with no public IPs and no servers to run.
X: B=Gateway endpoint for on premises: gateway endpoints are reachable only from within the VPC, so traffic from the data center cannot use them.
C=Public virtual interface: it reaches S3 public endpoints over Direct Connect, which is exactly the public addressing and public VIF that security has forbidden.
D=Proxy fleet: it would work through the gateway endpoint, but it is a self-managed proxy tier that the operations team refuses to run.
T: On-premises access to S3 over private IPs needs an S3 interface endpoint; gateway endpoints serve only the VPC itself.
V: Amazon S3, AWS PrivateLink, AWS Direct Connect

@ SAA-C03 D1 T1.2 advanced troubleshooting
S: A web application runs behind an Application Load Balancer with an AWS WAF web ACL. A third-party CDN sits in front and puts each client's address in X-Forwarded-For. A rate-based rule of 100 requests per 5 minutes per IP, meant to stop credential stuffing, blocked most real users during a sale. Limits must apply per real client, only to the /login path, and nowhere else on the site. How should the rule be changed?
A: Aggregate on the IP address in the X-Forwarded-For header, and add a scope-down statement matching URI paths that start with /login
B: Keep aggregating on the source IP address, add a scope-down statement for the /login path, and raise the rate limit to 10,000 requests
C: Aggregate on the IP address in the X-Forwarded-For header, and keep the rule without a scope-down so all paths share the same limit
D: Subscribe to AWS Shield Advanced for the load balancer and turn on automatic application layer DDoS mitigation in place of the rule
K: A
G: ## How a rate-based rule counts
A rate-based rule counts requests per **aggregation key** over an evaluation window (60, 120, 300, or 600 seconds; default 300) and applies its action above the limit (minimum 10).
- The default key is the **source IP**. Behind a proxy or CDN, that is the proxy's address, so thousands of users share one counter.
- **IP address in header** (forwarded IP) aggregates on a client address in a header such as `X-Forwarded-For`, with a fallback for malformed values. Use it only when the proxy sets the header reliably.
## Narrowing what is counted
A **scope-down statement** limits the requests that the rule counts and rate limits, for example `URI path starts with /login`. Other paths are not counted at all.
W: Forwarded IP with a /login scope-down: counters are per real client from the header, and only login requests are counted and limited, leaving the rest of the site untouched.
X: B=Source IP with a higher limit: the counter is still per CDN node, so one attacker hides among all users and the limit no longer applies per client.
C=Forwarded IP without scope-down: the limit becomes per client, but it now applies to every path, which breaks the rule that only /login is limited.
D=Shield Advanced automatic mitigation: it responds to detected DDoS events with managed rules; it is not a per-client limit on one path for credential stuffing.
T: Behind a proxy, aggregate rate-based rules on the forwarded IP header and scope them down to the path you want to protect.
V: AWS WAF, Elastic Load Balancing

@ SAA-C03 D1 T1.2 advanced use-case
S: A subscription video service delivers HLS streams through Amazon CloudFront. Each title has a manifest and about 2,000 segment files that the player requests with relative URLs, and the manifests cannot be rewritten. Only paying subscribers may fetch any file, and access must expire after four hours. Signing keys must be managed through the CloudFront API without the root user, and the team will not write edge code. Which solution fits?
A: Issue CloudFront signed cookies with a four-hour custom policy for the title's path, signed with a key from a trusted key group
B: Issue a CloudFront signed URL for each segment file with a four-hour expiry, signed with a key from a trusted key group
C: Issue CloudFront signed cookies with a four-hour custom policy for the title's path, signed with a CloudFront key pair that the root user created
D: Issue Amazon S3 presigned URLs with a four-hour expiry for each manifest and segment, signed by a role that can read the origin bucket

G: ## Signed URLs or signed cookies
Both restrict CloudFront content to holders of a valid signature. AWS guidance:
- **Signed URLs** for individual files, or for clients that do not support cookies.
- **Signed cookies** to grant access to **many restricted files** (for example all files of an HLS video) or when you **do not want to change your URLs**.
A custom policy can cover a path with a wildcard and set an expiry time.
## Who signs
A signer is either a **trusted key group** (recommended) or an AWS account with a CloudFront key pair. Key groups are managed through the CloudFront API and IAM, need no root user, and support automated rotation; account key pairs need the root user in the console.
W: Signed cookies with a trusted key group: one cookie set covers every segment under the title's path without changing URLs, expires after four hours, and the keys are managed through the API.
X: B=Signed URL per segment: each request URL would carry its own signature, so the manifests' relative URLs would have to be rewritten, which is ruled out.
C=Root user key pair: the cookies would work, but CloudFront key pairs on the account require the root user and cannot be managed through the API.
D=S3 presigned URLs: they point at S3 rather than CloudFront and change every file URL, so the manifests would need rewriting and the CDN would be bypassed.
T: For many files and unchanged URLs, use CloudFront signed cookies signed through a trusted key group.
V: Amazon CloudFront

@ SAA-C03 D1 T1.2 advanced use-case

The **health check grace period** is how long Auto Scaling waits after an instance enters `InService` before acting on failed checks. It should cover the boot time of the application, here about 4 minutes. A value of 0 turns the grace period off.
W: ELB health checks with a 300-second grace period: crashed instances are replaced based on the ALB's view, while new instances get time to start before checks count.
X: B=Grace period 0: failed ELB checks would count immediately, so instances still starting up would be marked unhealthy and replaced in a loop.
C=Faster ALB checks: the ALB already detects the crash; without ELB health checks on the group, Auto Scaling still ignores its result.
D=Status check alarm with reboot: the EC2 status checks still pass after an application crash, so the alarm never fires.
T: Turn on ELB health checks in the Auto Scaling group and set a grace period that covers application startup.

@ SAA-C03 D2 T2.2 advanced troubleshooting
S: Route 53 latency alias records point to Application Load Balancers in eu-west-1 and us-east-1, both with Evaluate Target Health set to Yes. European users are suddenly routed to us-east-1 although the main application in eu-west-1 is healthy. The eu-west-1 ALB also has a second target group for a retired reporting service whose stopped instances are still registered. Regional failover must keep working. What should the team do?
A: Remove the listener rule that forwards to the retired target group and delete that group, so only the main application's group is evaluated
B: Set Evaluate Target Health to No on the eu-west-1 latency alias record, so Route 53 always answers with that Region regardless of ALB health
C: Associate a Route 53 health check on the main application's URL with the eu-west-1 record, in addition to Evaluate Target Health
D: Lower the TTL of the latency alias records to 10 seconds, so that resolvers in Europe pick up the healthy eu-west-1 answer much faster
K: A
G: ## Evaluate Target Health on an ALB alias
With an alias record that points to an Application or Network Load Balancer and **Evaluate Target Health = Yes**, Route 53 uses the load balancer's own health. An ALB counts as healthy only if **every target group that contains targets has at least one healthy target**. A target group with only unhealthy targets makes the whole ALB unhealthy, and Route 53 routes to the next-best latency record.
A target group with no registered targets is also considered unhealthy, so merely deregistering the stopped instances would not fix it: the retired group must be removed from the load balancer.
## Combining with a health check
If you also attach a Route 53 health check to an alias record with Evaluate Target Health on, both must be healthy for the record to be used.
W: Delete the retired target group: once the load balancer has no target group that is empty or holds only unhealthy targets, the eu-west-1 ALB is healthy again and latency routing returns European users there, while failover still works.
X: B=Evaluate Target Health No: European users return, but Route 53 would keep sending them to eu-west-1 during a real outage, breaking failover.
C=Extra health check: the record is used only when both the health check and the target health are healthy, so the unhealthy target group still blocks it.
D=Lower TTL: Route 53 is giving the us-east-1 answer on purpose, so a shorter TTL only makes resolvers ask more often for the same answer.
T: An ALB is healthy for Route 53 only if every associated target group has a healthy target; delete stale target groups instead of leaving them empty.
