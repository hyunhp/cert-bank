@ DBX-CEA D1 T1.6 applied use-case
S: A ticket-triage agent labels each incoming message with one of six categories and extracts the order id. It handles a very high volume. Its traces show extended thinking enabled, and most output tokens of each request go to reasoning. An MLflow evaluation shows the same label accuracy with thinking turned off. Which reasoning mode should this step use?
A: Extended thinking with a larger thinking budget, because more reasoning tokens raise accuracy on classification as well
B: Extended thinking with a smaller maximum output, so the visible label is cut to the shortest possible text
C: Standard or reduced thinking, because a simple and well-specified task gains nothing from extra reasoning tokens
D: Extended thinking plus worked reasoning chains in the prompt, so the model writes shorter thoughts for each category
K: C
G: ## Reasoning modes trade tokens for depth
Many hosted models let you choose how much the model reasons before it answers. The Databricks page on querying reasoning models describes hybrid models where thinking can be switched on or off, and effort or budget settings that control reasoning depth. It states that higher reasoning effort can improve accuracy on complex tasks at the cost of increased latency and token usage.
## Standard, extended and reduced thinking
- **Standard** (answer directly) and **reduced thinking** keep latency and cost low.
- **Extended thinking** gives the model room to work through a hard problem before answering; its tokens are paid for and take time.
The names "standard, extended, reduced" are the exam guide's vocabulary; which mode to pick for a task is a design judgement that the evaluation results settle.
## The decision rule
Compare the modes on the same dataset and scorers. If accuracy is equal, the cheaper mode wins. For a short, well-defined labeling step there is little to reason about, so the extra tokens are pure cost.
W: Standard or reduced thinking: the evaluation shows the same accuracy without thinking, so the cheaper and faster mode is the right choice for a high-volume, well-specified step.
X: A=Larger thinking budget: the docs tie higher effort to better accuracy on complex tasks only; here accuracy did not move, so the larger budget only adds cost and latency.
B=Smaller maximum output: the label is already short; the cost is in reasoning tokens, so cutting visible output does not remove them and may truncate the answer.
D=Reasoning chains in the prompt: this adds prompt tokens to every request and keeps extended thinking running, so cost goes up instead of down.
T: Use extended thinking only where the evaluation shows it improves accuracy; otherwise pick the cheaper mode.

Reasoning modes help most on tasks with many dependent steps or interacting constraints, where an answer produced in one pass tends to miss something. The Databricks reasoning-model page says that higher reasoning effort or budget can improve quality on complex tasks, at the price of latency and token usage.
## Reading the scenario

S: A team enables extended thinking on `databricks-claude-sonnet-4-5` through the Anthropic Messages API, with `budget_tokens` set to 8000 and `max_tokens` also set to 8000. The request is rejected, and even a request that ran would leave no room for the visible answer after the reasoning. Which change fits?

G: ## Thinking tokens share the output allowance
For hybrid reasoning models that take a manual budget on Databricks (for example `databricks-claude-sonnet-4-5`), the page on querying reasoning models says `budget_tokens` controls how many tokens the model can use for internal thought and that `budget_tokens` must be less than `max_tokens`. The thinking budget therefore sits inside the total output allowance, and the visible answer needs room beyond it.

- Keep the thinking budget at the level the task needs.
- Set `max_tokens` high enough for thinking plus the answer.

W: Raising `max_tokens` above the budget: it satisfies the documented rule and leaves space for the final answer after the reasoning tokens.
X: A=Lowering `max_tokens`: it makes the violation worse, because the output allowance shrinks while the thinking budget stays the same.
B=Removing the setting: it switches the model to a different mode and the reasoning depth the team wanted is lost, so the quality gain disappears.
C=Prompt text: the budget is a request parameter, not a sentence the model obeys, so the prompt does not change what the API allows.
T: The thinking budget must be smaller than the output allowance; plan max tokens for thinking plus answer.

@ DBX-CEA D1 T1.7 applied troubleshooting
S: A policy agent places 40 retrieved passages, about 70,000 tokens, in its prompt. An MLflow evaluation shows correct answers when the relevant clause is among the first or last few passages and frequent misses when it sits in the middle, although the model's window is far from full. Which change addresses this most directly?
A: Keep a handful of top-ranked passages and put the most relevant one next to the question, instead of all 40
B: Move to a model with a larger window so the 40 passages fit and the middle gets equal attention

G: ## Length and position hurt before the window is full
A larger window means the text fits, not that the model uses all of it equally well. A widely reported pattern in long-context use is that information in the middle of a very long prompt is used less reliably than information at the start or end. This is a generally accepted observation rather than a Databricks-defined behavior; the exam guide frames it as a point where context length degrades retrieval and reasoning.
## What to do
- Send fewer, better passages (rank, filter, rerank).
- Place the most important text close to the question.
- Measure with an evaluation, because the effect depends on the model and the task.
W: Few top passages near the question: it removes the long middle where the clause was lost and keeps the key clause where the model reads it reliably.
X: B=Larger window: capacity is not the problem here (the window is far from full), and a longer prompt makes the middle even longer.
C=Duplicating the list: it doubles the token cost and keeps the same long, noisy input, with the answer still diluted among 80 passages.
D=Higher reasoning effort: it adds tokens and latency but does not change where the clause sits in the input, so the position effect remains.
T: Fix long-context misses by sending less and placing the key text near the question, not by adding capacity.

@ DBX-CEA D1 T1.7 applied troubleshooting
S: An agent calls its AI Search tool with the entire conversation transcript as the query text. Early in a chat the retrieved chunks are on topic; after dozens of turns they drift toward unrelated subjects that appeared earlier in the chat. Which change restores retrieval quality?
A: Increase the number of results returned, so on-topic chunks will appear among the drifting ones
B: Switch to a larger embedding model, since a long transcript query needs a bigger vector to represent its meaning
C: Increase the chunk overlap in the index so each chunk repeats more neighbouring text
D: Have the agent write a short, self-contained query for the current need and send only that to the retriever

G: ## A long query dilutes the match
Semantic search compares the meaning of the query with the meaning of chunks. A query made of a whole transcript mixes many topics, so its embedding sits between them and retrieves a blend. This is a context-length effect on the retrieval step. The usual remedy (generally accepted practice, often called query rewriting) is to retrieve with a focused query that states only what is needed now.
## In an agent
The retriever is a tool whose input comes from the model, so the fix is in how the model fills the query argument: a standalone, specific query, not the conversation history.
W: Short standalone query: it keeps the retriever's input focused on the current need, so the embedding matches the right chunks regardless of how long the chat is.
X: A=More results: it returns more drifting chunks and raises the token load without changing what the query represents.
B=Larger embedding model: the problem is a query that mixes topics, and a bigger model still embeds a blend of them.
C=More chunk overlap: this changes the index side and duplicates text there, while the failure comes from the query side.
T: Retrieve with a focused query, not the whole transcript.
