@ DBX-CEA D6 T6.2 applied definition
S: A team writes the first version of a compaction prompt for a long Databricks agent trace. They plan to iterate on it over several rounds and want to know what the first round should optimize. Which instruction for the first draft follows the recall-first approach?
A: Ask the summarizer to capture every decision, constraint, identifier, result and open item that could matter later, then check the summary against the raw trace
B: Ask the summarizer to keep the summary under a small fixed size so the token savings are visible from the first round, and add detail only if tests fail
C: Ask the summarizer to describe only the final outcome of each task phase in one sentence, because short summaries are the easiest to review by hand
D: Ask the summarizer to remove every tool output and quote only the user's messages, so the first draft contains nothing superfluous and can be extended later
K: A
G: ## Recall first, then precision
Compaction replaces older context with a summary. "Compaction" and the recall/precision tuning order are generally accepted context-engineering practice and the exam guide's wording, not a Databricks-defined feature; the Databricks docs do not describe a compaction prompt.
- **Recall**: of the facts later steps need, how many survive in the summary.
- **Precision**: of what the summary contains, how much is useful (not repeated, not superfluous output).
- Tuning order: first make the prompt capture everything relevant, checking the summary against the raw trace; only then iterate to remove noise.
The order matters because a fact lost in round one is invisible later: nothing in a short summary tells you what is missing, while noise in a long summary is easy to see and cut.
W: Capture everything first: a deliberately generous prompt gives a summary that can be checked against the raw trace, so any remaining gaps are found and fixed before the summary is shortened.
X: B=Small fixed size first: a size cap in round one forces the summarizer to choose what to drop before anyone knows which facts matter, which is precision work done too early.
C=One sentence per phase: this discards identifiers, values and constraints that downstream steps use, so recall starts low and nothing shows what was lost.
D=User messages only: removing all tool outputs drops results the agent still needs, and a summary that only repeats the user adds no state to the compacted context.
T: Tune a compaction prompt for recall first by capturing everything relevant, then raise precision by removing noise.

S: After two rounds of tuning, a compaction prompt for a data-pipeline agent now keeps every fact that the later steps of five sample traces use. A: Raise the maximum summary size so the repeated text fits, because the facts are already preserved and cost is only a secondary concern

D: Remove the instruction that lists the categories to preserve, so the summarizer can decide freely what is relevant and drop the noisy output itself

G: ## Iterating for precision
Once recall is acceptable, the remaining defect is noise: repeated output and long retry text that make the summary costly and distracting. Precision tuning removes this noise while the recall check stays in place.
- Edit one kind of noise at a time (duplicates, retry text, boilerplate).
- Re-run the same sample traces and re-check the facts that downstream steps use, so a precision edit that removes something needed is caught at once.
This is a generally accepted tuning practice and the exam's convention, not a documented Databricks procedure.
W: Targeted precision edit: merging duplicates and dropping retry text removes the observed noise, and re-checking the same traces proves that recall was not traded away.
X: A=Larger size cap: this accepts the noise and spends more tokens on every later call, which is the cost compaction was meant to reduce.
C=Last ten messages: this is trimming, not tuning, and it would throw away the facts that tuning has just made the summary keep.
D=Free choice: removing the category list drops the guard that protects recall, so the summarizer may delete needed facts along with the noise.
T: After recall is good, add narrow instructions that remove repeated or superfluous output and re-check the same traces.

@ DBX-CEA D6 T6.3 applied use-case
S: A FAQ agent answers independent single questions in a chat widget. A session may last 60 turns, but each question is self-contained, and the answer never depends on anything said more than a few turns ago. Context pressure is building in long sessions. Is a hard-coded trimming heuristic enough?
A: No, because any long session needs model-based summarization to keep the system prompt and the earlier answers of the agent intact
B: Yes, keeping the last few turns and dropping older ones fits this task, because relevance falls with age and nothing old is needed later
C: No, because trimming by age always breaks the order of the messages and the agent can no longer tell which question came last
D: Yes, but only if the trimming rule is changed to remove the newest turns first, so the earliest instructions stay in the window
K: B
G: ## Does the relevance pattern fit a fixed rule?
A hard-coded trimming heuristic (for example "keep the last N turns" or "drop tool results older than N steps") is cheap and predictable: no extra model call, same behavior every time. It works when the relevance of information follows a simple pattern, usually recency. When relevance depends on content rather than age, a rule cannot see the difference, and a more sophisticated approach (model-based compaction that judges what to keep) is needed.
- Independent questions: relevance decays with age, so a recency window is enough.
- Early decisions or constraints that matter late: age tells nothing, so rules fail.
Trimming vs compaction is the exam's vocabulary and a generally accepted practice, not a Databricks-defined feature.
W: Recency window: because each question is self-contained, old turns carry no needed information, so the simplest rule discards exactly what is irrelevant at no extra model cost.
X: A=Always summarize: summarization adds a model call and a risk of drift to solve a problem that a free rule already solves here.
C=Order breaks: dropping the oldest turns leaves the remaining messages in their original order, so the agent still sees which question came last.
D=Newest first: removing the latest turns discards the question being asked now, which makes the agent unable to answer it.
T: A fixed trimming rule is enough when relevance simply decays with age.

B: Aggressive compaction with a short summary, because the cost of the agent per case is the main factor in the decision
C: No summary of any kind and a hard cap on the number of turns, so that the case ends before the context grows
D: Aggressive compaction followed by a human review of every summary, since people can add back the details the summarizer lost in the process
K: A
G: ## Cost of an error decides
Subtle context (a condition, an exception, a negation) is what aggressive compaction loses first. When one lost qualifier can cause a wrong payout, fidelity is worth the extra tokens, and the high-stakes details are kept verbatim.
- Low stakes, high volume: aggressive.
- High stakes, low volume: conservative.
Exam convention and general practice.
W: Conservative posture: keeping qualifiers and clauses verbatim protects against the specific failure that is expensive, and moderate cost and low volume make the premium affordable.
X: B=Short summary for cost: it would compress the clauses the decision turns on, trading a small saving for a risk of wrong payouts.
C=Turn cap: cutting the case off does not preserve the clauses and ends reviews before they are complete.
D=Human review of every summary: reviewers see only the summary, so they cannot restore details that are no longer there; this also adds cost and delay.
T: When a lost detail is costly, favor conservative compaction.

@ DBX-CEA D7 T7.1 applied troubleshooting
S: A coordinating agent splits a vendor contract review between a pricing sub-agent and a legal sub-agent. The pricing agent recommends accepting a 25 percent discount, while the legal agent, working at the same time, flags that discounts above 15 percent need executive approval and recommends against it. Neither saw the other's work. What is the best diagnosis?
A: The model of the legal agent is too cautious, so it should be replaced by one that gives fewer conflicting recommendations
B: The agents work from different assumptions with no shared context, so their decisions conflict and the cap should reach both
C: The orchestrator's context is too small, so the answer is a longer window for the coordinator to hold both outputs together
D: The pricing agent ran too early, so the fix is to run all the sub-agents in sequence with a longer waiting time between steps in the plan
K: B
G: ## Insufficient shared context in multi-agent systems
In a multi-agent system, a coordinator decomposes a task and sub-agents work on pieces. If sub-agents do not share the facts, constraints and decisions that apply to the whole task, each acts on its own assumptions. Typical symptoms:
- conflicting decisions (one agent assumes a limit the other does not know about)
- inconsistent outputs (different terminology, formats or definitions)
- degraded reliability (results change from run to run depending on what each agent happened to infer)
Diagnosing these failure modes from shared-context gaps is the exam's convention and general practice, not a documented Databricks feature.
W: Missing shared constraint: the 15 percent cap is a fact that applies to both pieces of work, and because it was not shared, the agents reached opposite decisions from the same contract.
X: A=Model fault: both agents behaved reasonably with the information they had, and a different model given the same isolated task would also be unaware of the cap.
C=Coordinator window: the coordinator's size is irrelevant, since the conflict was produced inside the sub-agents before any output reached it.
D=Run in sequence with waits: waiting does not pass information along, so the second agent still lacks the first agent's assumptions unless they are shared.
T: Conflicting sub-agent decisions usually come from missing shared constraints; pass the common facts to every sub-agent.

@ DBX-CEA D7 T7.1 advanced use-case
S: A multi-agent trip planner has a flight agent, a hotel agent and an itinerary agent. Occasionally the itinerary agent books a hotel for dates that differ from the flight dates, and reruns of the same request give different results. Traces show that the flight agent decided on the dates in its own context, while the hotel agent inferred dates from the original request. What is the root cause?

B: The itinerary agent lacks authority to override the other agents, so a vote across the three outputs would settle the dates reliably

G: ## Decisions are shared state
Dates are a decision made by one agent that others depend on. When the decision exists only in one agent's context, the others infer it, and inferences vary between runs; this is the source of the degraded reliability seen on reruns. Making such decisions explicit shared context (decisions and constraints, not whole histories) removes the guesswork.
Post-hoc voting or stricter reading of the request only choose among or restate conflicting inputs; they do not supply the missing decision. The diagnosis is the exam's convention and general practice.
W: Unshared decision: the flight agent's dates were never visible to the hotel agent, which inferred its own, and inference differs from run to run.
X: A=Careless reading: the request does not contain the decision the flight agent made, so quoting it exactly cannot recover the dates.
B=No authority: majority resolution picks among conflicts after the work is done, and it does not tell the hotel agent what the flight agent decided.
C=Short request: the other agents did plan from it; the conflict came from a decision made in only one context, which more detail would not share.
T: Decisions that other agents depend on must be shared context; if they stay private, the others infer them differently.
