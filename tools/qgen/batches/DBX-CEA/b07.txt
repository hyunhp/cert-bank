@ DBX-CEA D5 T5.3 applied definition
S: An analytics agent can reach 60 registered tools. Its traces show that every model call starts with the full name, description and parameter schema of all 60 tools, and most of the attention budget is gone before the user's question is read. The team adopts progressive disclosure for tools. What does the context window hold at the first stage, before the agent has picked a tool?
A: A compact index of tool names with one-line descriptions, while the full parameter schema of a tool is added only after the agent selects it
B: The full schemas of the ten most frequently used tools, with the remaining fifty tools hidden until the agent asks for them by exact name
C: Only the user's question, with no tool information at all, so the agent must guess a tool name and wait for an error to learn its parameters
D: The full schema of every tool, compressed by removing parameter descriptions so that all 60 tools still fit in a smaller footprint
K: A
G: ## Progressive disclosure of tools
Every tool definition sent to the model costs tokens on every call and competes for the attention budget. Progressive disclosure reveals tool information in stages, and each stage adds only what the next decision needs.
- Stage 1, discovery: a compact index (names plus a short description of what each tool does and when to use it).
- Stage 2, selection: the agent picks a tool, and only then is that tool's full parameter schema loaded.
- Stage 3, use: the call is made and its result enters the window, scoped to what the task needs.
Naming note: "progressive disclosure" for tool definitions is the exam guide's term and a generally accepted context-engineering idea; the Databricks docs do not define it for tools. The docs do state the same loading idea for Agent Skills, which are "loaded automatically and only in the relevant context".
W: Index first, schema on selection: the first stage carries just enough (name and a one-line purpose) for the agent to choose, so the cost of 60 tools becomes the cost of 60 short lines and one full schema.
X: B=Top ten schemas: preloading full schemas for a fixed subset still pays their full cost on every call, and the hidden fifty can only be found by exact name, which the agent does not know.
C=No tool information: with nothing to choose from, the agent cannot plan and wastes turns on failing calls; staging reduces the amount shown, it does not remove the discovery step.
D=Stripped schemas for all tools: this still lists every tool at full breadth and deletes the parameter descriptions the model needs to fill arguments correctly, so it hurts accuracy without staging anything.
T: Progressive disclosure shows a light index first and loads a tool's full schema only after the agent selects it.

@ DBX-CEA D5 T5.3 applied use-case
S: A support agent connects to several tool servers. To apply progressive disclosure, an engineer must add something to the agent so that it can move from the light tool index to the full definition of one tool. Which design supplies that step?
A: Increase the index descriptions to hold every parameter name and type so the agent never needs a second step
B: Add a lookup step the agent calls with a tool name to receive that tool's full schema
C: Rewrite the system prompt to list all tool schemas in a collapsible section the model is told to ignore until needed
D: Remove tools from the index after their first use so the model sees each definition only once
K: B
G: ## The step between stages
Staging only works if the agent has a way to ask for more detail. Without it, the index would either contain too little to call a tool correctly or grow back into the full dump.
- The index answers "which tool?" and stays short.
- A lookup (a describe or load step, implemented as a small tool or by the agent framework) answers "how do I call it?" for one tool at a time.
- Tool servers expose names, descriptions and input schemas through the Model Context Protocol (MCP), which is the discovery mechanism Databricks documents for agents ("Discover tools and make your first tool call"), so a framework can fetch one tool's definition on demand.
The staging itself is the exam's convention (a generally accepted context-engineering practice), not a named Databricks feature.
W: Lookup step: the agent calls it with the name it chose and gets only that tool's full schema, so the window grows by one definition at the moment it is needed and not before.
X: A=Detailed index: putting every parameter in the index recreates the full tool dump in a different place and spends the attention budget again, which defeats the purpose.
C=Ignorable section: text in the window is read whether or not the model is told to ignore it, so it still costs tokens and still distracts; instructions do not make content free.
D=Show each tool once: hiding a definition after one use leaves the agent unable to call that tool again correctly, and it does not reduce the first-turn cost of the full list.
T: Progressive disclosure needs a lookup that returns one tool's full schema on request, keeping the index short.

Under staged disclosure the index replaces the full dump, and full schemas are added only for the tools the request uses.
- Full dump: 60 x 500 = 30,000 tokens on every call.
- Staged: 60 x 20 = 1,200 for the index, plus 3 x 500 = 1,500 for the loaded schemas, about 2,700 tokens.
- Cost: each lookup is an extra model round trip, so latency grows with the number of tools used. A small catalog whose tools are all used gains little.
The saving depends on catalog size and on how many tools a request touches; the figures here are illustrative. Naming note: this staging is the exam guide's term and generally accepted context-engineering practice; the Databricks docs do not define progressive disclosure for tools.
W: 1,200 + 1,500 = about 2,700 tokens against 30,000, a saving of roughly 90%, and the price is one extra lookup round trip for each of the 3 tools.
X: A=Index added on top: the index replaces the list of full schemas instead of adding to it; only the 3 chosen schemas are loaded.
C=Index only: this forgets the 3 schemas that are loaded after selection, and each lookup is a round trip, so the cost is not zero.
D=Always half: the saving follows the ratio of tools used to tools available, so it is not a fixed fraction.

@ DBX-CEA D5 T5.4 applied use-case
S: A research agent is close to its context limit. The history holds a 30,000-character JSON result from `get_orders`, returned 25 turns ago. Since then, the agent has written the three order ids and totals it needed into its running plan, and it will not use the raw JSON again. Which action frees space without hurting the task?
A: Delete the plan entries along with the JSON, because the plan also repeats information that the JSON already contained
B: Truncate the JSON to its first 2,000 characters so that part of every old result remains available to the model
C: Clear the assistant's reasoning messages from the last ten turns, since reasoning is less important than tool data
D: Clear the raw `get_orders` result, keep the plan entries and leave a short note of the call
K: D
G: ## Tool result clearing
In long tasks, raw tool outputs are usually the largest items in the message history, and they are most useful in the turn that produced them. Once the agent has extracted what it needs, the raw payload is dead weight that adds distraction and cost.
- Safe to clear: a raw result whose needed facts are already captured elsewhere (a plan, a note, a state object).
- Keep: the facts extracted from it and a record that the call happened.
"Tool result clearing" is the exam guide's term and a generally accepted context-engineering technique; the Databricks docs do not define it.
W: Clear the payload, keep the facts: the three ids and totals live in the plan, so removing the raw JSON loses nothing the task needs and frees the most space.
X: A=Delete the plan too: the plan holds the distilled facts the agent still relies on; deleting them and the source would leave the task without the data.
B=Truncate to the start: a cut JSON string is partial and may be invalid, and it keeps tokens that carry no needed facts while hiding the rows that might matter.
C=Clear reasoning: reasoning messages can hold decisions and constraints that are not recorded anywhere else, and they are much smaller than the payload that is the real problem.
T: When the needed facts are already captured, clear the raw tool output and keep the extracted facts and a record of the call.

B: Package the procedure, its examples and its script as an Agent Skill so that it is loaded only for requests where it is relevant
C: Move the procedure into a tool description, so that it is part of the tool list on every call
D: Split the procedure into ten parts and place one part in the prompt of each of ten requests
K: B
G: ## Agent Skills
Databricks documents skills as packages that "package domain-specific knowledge and workflows" and "can include guidance, best practices, reusable code, and executable scripts". They follow the open standard of Agent Skills. Unlike custom instructions, which are applied globally, skills "are loaded automatically and only in the relevant context."
- A skill is a folder with a required `SKILL.md` (frontmatter `name` and `description`, then instructions) plus optional scripts and reference files.
- The agent decides from the name and description whether the skill applies, so the cost is paid only when it does.
- The docs example of a good workspace skill is a "PII-handling skill that masks sensitive columns".
The docs describe skills in the Genie Code page; the context-cost reasoning (pay only when relevant) is the exam's framing of the same loading behavior.
W: Agent Skill: the procedure, examples and script are packaged together and loaded only when a request is about PII, so the 90% of requests that do not need it pay nothing.
X: A=One-sentence version: it deletes the steps and script that make the procedure reliable, so PII requests lose accuracy to save a cost that a skill avoids anyway.
C=Tool description: tool descriptions also sit in the window on every call, so this keeps the same always-on cost under a different heading.
D=Ten partial prompts: splitting by request gives each request an incomplete procedure and no rule for which part appears when.
T: Package a long, occasionally needed procedure as an Agent Skill so it loads only when relevant.

@ DBX-CEA D6 T6.1 applied troubleshooting
S: A debugging agent's history is compacted by a summarization prompt. After compaction the agent repeatedly asks the user for the exact stack trace and the file path it had already seen. The summaries read well but contain phrases like "an error occurred in the loader". Which change to the compaction prompt best addresses the problem?

G: ## What compaction may lose
Compaction replaces older history with a summary so the task can continue within the window. A summarizer without guidance tends to keep the narrative and drop exact strings, because they look like detail.
- Exact values, such as error text, file paths, identifiers, numbers and commands, cannot be reconstructed from a paraphrase.
- A diagnosis starts by comparing the summary with the raw history and naming the information type that was dropped.
- The fix is to name that type in the compaction prompt and require it to be kept verbatim.
Compaction and its prompts are the exam guide's topic and generally accepted context-engineering practice; the Databricks docs do not define compaction.
W: Verbatim preservation: the missing information is the exact strings, so naming them in the prompt makes the summary keep them while still compressing the narrative.
X: A=Shorter summary: this removes even more detail and makes the loss of the stack trace and path more likely.
B=Narrative tone: the symptom is the loss of exact strings; a friendlier style adds words without keeping the data.
D=Earlier compaction: running compaction sooner does not change what the summarizer chooses to drop, and it discards more history for the same lossy prompt.
