@ DBX-CEA D4 T4.6 advanced troubleshooting
S: A travel agent injects the 25 closest memories from its Lakebase-backed memory store into every request. As the store grew, answers got worse: asked to rebook a flight, the agent quoted a seat preference from a hotel stay two years ago and ignored the new date. The trace shows only 3 of the 25 injected memories relate to flights. Which diagnosis and fix fit best?
A: Under-retrieval, because the agent ignored the new date, so raise the number of injected memories until the date appears again
B: Context clash, because the memories contradict each other, so delete the older memories and keep only the newest 25 entries
C: Over-retrieval that pollutes the window, so cap the injected memories and require a relevance score before a memory enters the prompt
D: A weak embedding model, so re-embed the whole memory store with a larger model and keep injecting all 25 closest memories
K: C
G: ## Over-retrieval and under-retrieval
These are generally accepted retrieval terms and this exam's convention; the Databricks docs do not define them. A memory system can fail in two opposite directions.
- **Over-retrieval** (context pollution): too many or weakly relevant memories are injected. They spend the attention budget, distract the model and let an old, unrelated fact steer the answer.
- **Under-retrieval**: a relevant memory exists in the store but never reaches the prompt, so the agent behaves as if it had forgotten.
Databricks agent memory is retrieved by semantic search, so "closest" means most similar, not necessarily relevant to the task. A fixed count such as 25 always injects something, even when only a few memories matter.
## Reading the trace
Compare what retrieval returned with what the answer needed. Many returned items and few used, plus an unrelated fact echoed in the answer, points to over-retrieval. The usual fixes are a smaller cap, a relevance threshold and a query that states the current task.
W: Over-retrieval with a cap and relevance gate: only 3 of 25 memories relate to the task, so the other 22 are noise that competes with the new date; limiting what enters the prompt restores focus and cuts tokens per call.
X: A=More memories: the symptom is too many weakly related items, not too few; raising the count adds more irrelevant text and makes the old preference even more likely to win.
B=Context clash: the memories do not contradict each other here; a hotel seat preference is simply unrelated to a flight rebooking. Deleting old entries also removes memories that may still matter.
D=Larger embedding model: a better embedder may rank slightly better, but injecting all 25 closest items still floods the window with low-relevance text, so pollution remains.
T: When most injected memories go unused and an unrelated one steers the answer, the problem is over-retrieval: gate and cap what enters the window.

@ DBX-CEA D4 T4.6 applied troubleshooting
S: A meal-planning agent recalls memories through a lookup that returns only items whose similarity score passes a very strict threshold. A user said in an earlier conversation, "I'm vegetarian," and the fact is in the memory store. In a new conversation the agent proposes a steak dinner. The trace shows the memory search span returned zero results for "what should I cook tonight". What is the failure and the best change?
A: Over-retrieval, so lower the number of results returned and keep the strict threshold so fewer memories are used
B: Under-retrieval, so relax the threshold or query with the user's constraints, then confirm the memory returns
C: Memory poisoning, so rewrite the stored fact as an instruction in the system prompt and delete the entry from the memory store for good
D: A pipeline delay, so schedule the memory pipeline to run more often and then re-run the same strict retrieval afterwards
K: B
G: ## Under-retrieval
Under-retrieval means a relevant memory exists but the retrieval step does not return it (exam convention; the docs do not define the term). Typical causes:
- A similarity threshold so strict that a short, generic query such as "what should I cook tonight" never matches the stored sentence "I'm vegetarian".
- A query that does not mention the constraint the memory is about.
- A cap so low that relevant items rank below it.
## Diagnose before changing
The trace separates two cases. If the store has the fact but the retrieval span returns nothing, the gap is in retrieval. If the store does not have the fact, the gap is in writing (the memory pipeline or the agent's memory-writing). Here the fact is stored, so the fix belongs to retrieval: relax the gate or improve the query, and keep checking for the opposite failure (over-retrieval) after the change.
W: Under-retrieval from a strict gate: the memory is stored but never returned, so relaxing the threshold or building the query from the user's stated constraints surfaces it, and re-checking the trace confirms it reaches the prompt.
X: A=Fewer results: this treats a missing memory as a pollution problem. With zero results already returned, a lower cap with the same threshold still returns nothing.
C=Poisoning: nothing false was stored; the fact is correct. Moving one user's diet into a shared system prompt also breaks per-user scoping.
D=Pipeline frequency: the fact is already in the memory store, so a faster pipeline adds nothing; the unchanged strict retrieval would still return zero results.
T: Fact stored but retrieval returns nothing is under-retrieval: fix the gate or the query, not the writer.

@ DBX-CEA D4 T4.6 advanced tradeoff
S: To stop context pollution, a team cuts memory retrieval from 10 results to 2. The evaluation dataset now shows fewer unrelated details in answers, but questions that need three separate stored facts (diet, budget, dates) lose accuracy. Which next step best balances both failures?
A: Return to 10 results and accept the pollution, since recall failures are always more damaging than extra tokens
B: Keep 2 results and ask users to repeat the missing facts, since the store cannot support multi-fact questions
C: Run the memory search a second time for every question and inject both result sets, doubling the retrieved text on each turn
D: Set a relevance score gate with a moderate cap, then re-run the same evaluation to check both unrelated details and missing facts
K: D
G: ## Tuning both failures together
Lowering a cap trades one failure for the other: fewer results reduce over-retrieval but raise the chance of under-retrieval for questions that need several facts (exam convention terms). A fixed small number cannot adapt to a question that needs one fact and a question that needs three.
- A **relevance gate** lets the number of injected memories follow how many are actually relevant.
- A **moderate cap** bounds the worst case so a broad question cannot flood the window.
- Re-running the **same evaluation dataset** with the same judges (for example in an MLflow 3 evaluation run) shows whether pollution and recall both improved, instead of fixing one and silently breaking the other.
W: Relevance gate plus moderate cap, then re-evaluate: the injected count adapts to the question, the cap bounds the window, and the same evaluation measures both unrelated details and missing facts.
X: A=Back to 10: this restores recall by reintroducing the original pollution and tokens; it treats one failure as free and measures neither.
B=Keep 2 and ask users: the store does hold the facts; the cap, not the store, is the problem, and pushing the work to users hides a configuration defect.
C=Second search for every question: it doubles retrieved text on every turn, including simple questions, which raises distraction and cost while still using no relevance gate.
T: Tune cap and relevance gate together and measure both pollution and recall on the same evaluation.

@ DBX-CEA D4 T4.6 applied use-case
S: A wellness agent stores each past conversation transcript as one memory entry. For a question about the user's sleep goal, retrieval returns three entries that are about two thousand tokens each; the goal is a single sentence inside one of them. Most of the returned text is unrelated chat. Which change reduces over-retrieval without losing the goal?
A: Distill conversations into short durable facts, one entry per goal, and retrieve those instead of whole transcripts
B: Return a single transcript entry per question and hope the closest one contains the goal sentence

D: Tell the model in the system prompt to ignore unrelated chat inside each retrieved memory entry

Over-retrieval can come from the size of what each hit carries as well as from the number of hits (exam convention). A hit that is a whole transcript brings thousands of tokens of unrelated chat with one useful sentence.
Databricks agent memory is meant to store durable facts, preferences and decisions, and memory pipelines distill conversations in a session store into those memories. The raw record belongs in the session store; the memory store holds the distilled result.
## Fix
Store one durable fact per entry. Retrieval then returns a few short, high-signal items, which costs fewer tokens and leaves less to distract the model.

@ DBX-CEA D4 T4.7 applied troubleshooting
S: A shopping agent's memory pipeline runs nightly. After months of use, one customer's memory store holds about forty near-identical entries such as "prefers aisle seats" and "likes aisle seat", and retrieval of the top five fills with these copies while the customer's allergy note ranks sixth and never reaches the prompt. Which change fits best?
A: Raise the retrieval count to fifty, so that the allergy note is always among the injected memories
B: Delete the whole memory store each week and let the agent rebuild its preferences from new chats
C: Have the memory pipeline consolidate duplicate facts into one durable entry each when it distills the sessions
D: Add a system prompt line telling the model that repeated preferences are not important to the customer
K: C
G: ## Memory that is distilled and consolidated
The Databricks agent memory and sessions page describes a memory pipeline as the process that distills the sessions in a session store into memories, and its memory-research mapping says it also consolidates them over time. The memory store is meant to hold durable facts, not a log of every mention.
Without consolidation the same fact is written again and again. Because recall is semantic search, near-identical copies all score high and can occupy every slot of a small result list, which pushes a different relevant fact out (under-retrieval caused by duplicates; this wording is the exam's convention).
## Fix at write time
Merge duplicates into one entry per fact when the pipeline distills, so each retrieval slot carries a different fact. Cleaning the store once is cheaper than filtering copies on every request.
W: Consolidate in the pipeline: one durable entry per fact frees the retrieval slots, so the allergy note ranks within the few injected memories and the window carries less repeated text.
X: A=Retrieve fifty: the forty copies still come first and cost tokens on every call; the cap grows without removing the repeated text, and over-retrieval replaces under-retrieval.
B=Weekly wipe: this erases facts that the customer stated once and that are not repeated in new chats, such as the allergy, so durable memory is lost.
D=Prompt line: the copies are still retrieved and still use the window, and a prompt cannot make the allergy note appear in the results.
T: Consolidate duplicate facts when memory is written so retrieval slots carry different facts.

@ DBX-CEA D4 T4.7 applied use-case
S: An engineer deletes an entire session store that belonged to a retired version of a support agent, to clean up. A product owner worries that every user's saved preferences will disappear and that the agent will start over with each person. What actually happens?
A: Preferences are lost, because memory is stored as a child object of the session store and is removed with it
B: Preferences are lost, because the memory pipeline automatically rebuilds the memory store from sessions that no longer exist
C: Preferences stay but become read-only until a new session store with the same name is created
D: Preferences stay, because deleting a session or a session store does not delete memory kept in a memory store
K: D
G: ## Independent stores
In the Databricks stateful agents model the session store and the memory store are separate. A memory pipeline, the agent or the application distills durable facts out of a session and writes them to memory. After that the session can be cleared or can age out, and the memory persists.
The docs state it directly: deleting a session, or an entire session store, does not delete memory retained in a memory store.
## Design implication
Clean up session data on its own schedule without fearing loss of long-term personalization. If memory itself must be removed, for example for a user request, that is a separate action on the memory store.
W: Independent stores: memory was written to its own store, so removing the session store clears interaction history only and the distilled preferences continue to be recalled in later conversations.
X: A=Child object: the memory store is not nested inside the session store, so deleting the latter removes no memory entries.
B=Automatic rebuild: a pipeline distills sessions into memory when it runs; it does not erase memory when its source sessions disappear.
C=Read-only until recreated: nothing in the stores' relationship makes memory depend on a same-named session store, and memory is still recalled normally.
T: Sessions and memory are independent stores, so deleting sessions does not delete memory.

@ DBX-CEA D4 T4.7 advanced troubleshooting
S: A shopping agent writes memories keyed by the current chat ID. A customer who set a size preference on Monday opens a new chat on Wednesday, and the agent shows no knowledge of it, although the memory entry exists. What configuration change fixes the recall?
A: Retain each chat longer, so Wednesday's chat can load Monday's chat in full as its session state
B: Make the embeddings more precise so Monday's chat ID is matched against Wednesday's chat ID
C: Scope memories to the customer as the subject rather than to a chat, so any later conversation can recall them
D: Write the preference again at the start of each chat with a tool call, so every chat holds its own copy
K: C
G: ## Memory is scoped to a subject
The docs contrast two scopes. A session is scoped to one interaction. A memory is scoped to a subject, not an interaction: durable facts such as a user's stable preferences, a past decision or an ongoing project that should matter in a future, unrelated conversation. The agent recalls them whenever they are relevant, regardless of which conversation surfaced them.
## The bug
Keying memory by chat ID makes a durable fact behave like session state: it can only be found from the chat that created it. Choose the subject (here the customer) as the scope when you write and when you recall, and keep per-user separation so one customer's memories are never recalled for another.
W: Subject scope: memories keyed to the customer survive across chats, so Wednesday's conversation recalls Monday's preference while other customers' memories stay separate.
X: A=Longer chat retention: replaying Monday's chat in Wednesday's session loads old transcript text and keeps the memory tied to an interaction instead of a subject.
B=Better embeddings: the entry is not found because of its scope key, not because of similarity quality; precise embeddings cannot match different chat IDs.
D=Rewrite each chat: duplicating the fact in every chat multiplies stale copies and leaves the real defect, chat-level scope, in place.
T: Key durable memory to the subject, not to the conversation.

Retrieval can only be as good as its query. "What did they decide about it?" has no content the index can match. @ DBX-CEA D4 T4.8 applied definition
S: An engineer sketches four stages for an agent that answers from memory and tables. Which order puts intent resolution where the exam expects it?
A: Receive message with session state, resolve intent, retrieve with the resolved query, inject the results
B: Receive message, retrieve with the raw text, inject the results, resolve intent from what was retrieved
C: Resolve intent from the retrieved items, receive the message, inject the results, retrieve with the raw text
D: Receive message, inject the entire memory store, retrieve what remains useful, resolve intent last
K: A
G: ## Where intent resolution sits
Intent resolution is the stage that decides what the user is asking and where to look. It belongs after the message and its session state are available and before retrieval, so the query used for retrieval is already clear (exam convention; not a Databricks docs term).
- Before retrieval: expand pronouns, resolve ambiguous names, choose between sources such as structured lookup or semantic search.
- After retrieval, the same decisions are too late, because the window already holds whatever the raw query matched.
## Why order matters
Every retrieved item costs tokens and attention. Spending them on a query that has not been resolved is the main source of over-retrieval.
W: Message, resolve, retrieve, inject: the resolved query drives retrieval, so only items matching the user's real intent enter the window.
X: B=Resolve after injection: retrieval ran on the raw text and its results are already in the window, so intent cannot filter what was retrieved without extra cost.
C=Resolve from retrieved items: this needs retrieval to have run first, so the resolution cannot guide it, and the message cannot be handled before it is received.
D=Inject the whole store: this defeats retrieval and floods the window with unrelated memories before any decision is made.
T: Resolve intent after reading the message and session, but before any retrieval.

@ DBX-CEA D4 T4.8 advanced tradeoff
S: A team adds a model call that rewrites every user message into a standalone query before memory retrieval. Latency rose noticeably. - Clear messages go straight to retrieval.

G: ## Progressive disclosure for MCP tools
An MCP server tells a client which tools it offers, each with a name, a description and an input schema. If the agent loads every tool from every server at the start, the schemas sit in each call whether they are used or not.
**Progressive disclosure** loads tool information in layers: a light first layer (what each server or tool group is for), and the full schema only for the tool or server the agent decides to use. The docs describe MCP as a way to query data, search documents and call external services; progressive disclosure is an exam concept for managing the tool information, not a Databricks setting.
## Why it helps
The window carries the catalog instead of dozens of schemas, so the attention budget is spent on the task. The cost is one extra step when a server is first used.
W: Catalog then on-demand schemas: the first layer tells the agent where to look, and only the chosen server's tools are loaded, which removes unused schemas from every call.
X: A=One-word descriptions: shorter text lowers cost but the full list remains, and tool selection gets worse because descriptions no longer say when to use a tool.
B=Drop servers: this permanently removes capabilities the agent needs on some tasks; progressive disclosure keeps them reachable.
C=List in the system prompt: caching can reduce price, but the tokens remain in the window and still dilute attention.
T: Disclose a light catalog first and load full tool schemas on demand.
V: MCP

@ DBX-CEA D5 T5.1 applied use-case
S: A finance agent calls a generic SQL tool on a custom MCP server for "Which three regions had the highest gross margin last quarter?". The tool returns about four thousand transaction rows, which the model then sorts and totals itself, and the answer is sometimes wrong. What change cuts the tokens most while keeping the result reliable?
A: Raise the tool's row limit so that the model always sees every transaction of the quarter
B: Add a tool that aggregates and ranks in the warehouse and returns only the three regions with their margins
C: Ask the model in the system prompt to total each region carefully and double-check its sums
D: Compress the four thousand rows into a shorter text table before they are returned to the model
K: B
G: ## Do the work where the data lives
A tool result is part of the context. A tool can run the aggregation itself, for example as a query on a SQL warehouse behind a custom MCP server hosted on Databricks Apps, and return a few rows. The model then reads the answer instead of computing it from thousands of rows.
This is the context-engineering idea of scoping tool results (exam convention: it is not a Databricks setting). It costs one purpose-built tool, but it removes both the token load and the arithmetic errors of a model summing rows.
## Compare with the alternatives
Bigger limits and reformatting still put all the rows in the window. Prompts do not change what is in the window.
W: Server-side aggregation: the warehouse sorts and totals the quarter, so only three rows enter the window and the figures are computed by SQL rather than estimated by the model.
X: A=Bigger limit: more rows mean more tokens and more room for arithmetic mistakes, so the problem grows.
C=Careful-totals prompt: the four thousand rows remain in the window and the model still does the arithmetic by itself; a reminder does not make sums reliable.
D=Reformatted table: a tighter layout of the same rows saves only a fraction of the tokens, and the model must still total them.
T: Aggregate in the tool and return the answer, not the rows.

@ DBX-CEA D5 T5.1 advanced troubleshooting

How should the tool be redesigned to apply progressive disclosure to its output?

Progressive disclosure is not only about tool definitions. A tool result is part of the context, so a tool can return a light first layer (the identifiers and the fields most likely needed) and a second tool or parameter that returns the detail for one item when the agent asks. @ DBX-CEA D5 T5.1 applied troubleshooting
S: A support agent is connected to a registered MCP server with 30 tools. The agent's callers can use only 18 of them under their Unity Catalog permissions. The trace shows the model choosing a tool it is not allowed to call, getting a permission error and retrying, and the 12 unusable definitions sit in every call. What is the best change?
A: Tell the agent in the prompt which 12 tools are unavailable and to skip them each time
B: Grant every caller access to all 30 tools so that no call returns a permission error
C: Add a retry loop that tries the next tool whenever a call comes back with a permission error
D: Restrict the tools exposed to this agent to the 18 its callers may use, so the other 12 are never loaded
K: D
G: ## Expose only what can be used
The Databricks MCP docs say that Databricks-provided and registered MCPs use Unity Catalog permissions, and that governing an MCP includes sharing access and restricting tools. A tool the caller cannot run is pure cost: its definition fills the window and the model may still pick it.
Restricting the exposed tools to the permitted set keeps unusable tools out of the context and out of reach. This also keeps least privilege intact, instead of widening access to stop errors. Treating this as a context strategy (smallest useful tool set) is the exam's convention.
W: Restrict to the permitted 18: the 12 unusable definitions leave every call, the model cannot select them, and no tokens are spent on permission errors.

@ DBX-CEA D5 T5.1 advanced tradeoff
S: After switching to a tool catalog, an agent that answers customer chats loads tool schemas only on demand. Latency increased, because the same five tools, such as order lookup and refund, are used in almost every chat and each now needs an extra step to load. Which design keeps most of the savings?
A: Disclose every tool progressively, as designed, and accept the added round trip for all of them
B: Load every tool schema up front again, because latency matters more than context cost
C: Add more tools to the catalog so the agent can find a shortcut for common requests
D: Keep the five common tools fully loaded and put the rarely used ones behind the catalog
K: D
G: ## Not everything should be deferred
Progressive disclosure trades extra steps for a smaller baseline window. It pays off for tools that are rarely needed. For tools used in nearly every conversation, deferral means a repeated extra round trip and no saving on average, so their definitions belong in the always-on layer.
This is an exam-convention engineering tradeoff, not a documented Databricks setting.
## Split by frequency
- Always loaded: the few frequently used tools with short schemas.
- Behind the catalog: the long tail used occasionally.
That keeps the baseline context small and removes the extra step for common requests.
W: Hot tools loaded, tail disclosed: the five frequent tools cost a few tokens and need no extra step, while the rest of the tools stay out of the window until needed.
X: A=Defer everything: this keeps the design but pays an extra round trip in almost every chat for tools that would have been loaded anyway.
B=Load all again: it restores the original cost for every rarely used tool, undoing the benefit of the catalog.
C=More tools: extra tools increase the catalog and the chance of a wrong choice without removing the extra step for the common five.
T: Defer the long tail of tools, but keep the frequently used ones loaded.

@ DBX-CEA D5 T5.2 applied troubleshooting
S: An agent has two MCP tools. `find_customer` is described as "Looks up customer information." `get_account` is described as "Retrieves account information for a customer." The agent calls them almost at random for questions such as "What is the billing address for Dana Lee?" Which change fixes the confusion?
A: Rewrite each description to state what it returns, its key input and when to use it instead of the other tool
B: Rename the two tools `tool_a` and `tool_b` so the names cannot suggest anything misleading
C: Add the same example call to the system prompt for both tools so the model sees how each is called
D: Append all synonyms of "customer" and "account" to both descriptions so every question matches strongly
K: A
G: ## Overlapping tool descriptions
The model chooses a tool mainly from its name and description. If two descriptions say almost the same thing, nothing distinguishes them and the choice becomes close to random (a confusion failure; "overlapping tool descriptions" is the exam's term, not defined in the Databricks docs).
## What a good description states
- What the tool returns (fields, entity).
- The input it expects.
- When to prefer it, and when not to use it, especially against the neighboring tool.
For example: "Returns name and contact details for a person; input is a customer name. For billing address use `get_account`." and "Returns billing address, plan and balance; input is a customer ID."
W: Distinct, contrastive descriptions: each description names what it returns, the input and the boundary with the other tool, so the model can match a question about a billing address to a single tool.
X: B=Meaningless names: removing meaning from names takes away the signal the model has, so choices get worse.
C=Identical example in the prompt: the same example for both tools does not separate them and adds prompt text.
D=Synonym stuffing: adding the same words to both makes the overlap larger, not smaller.
T: Make each description state what it returns and when to use it instead of its neighbors.
V: MCP

@ DBX-CEA D5 T5.2 advanced comparison
S: A billing agent has four MCP tools. `get_invoice`: "Returns billing documents for a customer, including invoices and credit notes." `list_payments`: "Returns payment transactions for a customer, including refunds." `get_billing_history`: "Returns billing documents and payments for a customer." `get_shipment_status`: "Returns the current delivery status of a shipment." The agent often picks the wrong tool for billing questions. Where is the overlap?
A: `get_invoice` and `get_shipment_status` overlap, because both return documents and statuses about a customer's orders
B: `list_payments` and `get_shipment_status` overlap, because both return a status-like result
C: `get_billing_history` overlaps `get_invoice` and `list_payments`, because it describes the union of their outputs
D: There is no overlap, because every tool has a different name and returns a different noun
K: C
G: ## Finding the overlap
To find confusing tools, read the descriptions as the model does and ask, for a sample question, which descriptions would all seem to fit. Overlap shows up as a description whose scope contains another's (a superset), or two descriptions that name the same entity and the same operation.
"Overlap" and "superset descriptions" are the exam's convention here (generally accepted tool-design vocabulary; the docs do not define them).
## Fixes
- Remove the superset tool if it adds nothing, or describe what it adds ("Use only when both documents and payments are needed in one call").
- State in each description what the tool does not cover.
W: Superset tool: `get_billing_history` describes billing documents and payments, which is exactly what `get_invoice` and `list_payments` return together, so a billing question fits all three.
X: A=Invoice versus shipment: invoices and delivery status are different entities and operations; the word "customer" appears in both but the content differs.
B=Payments versus shipment: payment transactions and a shipment's delivery state are unrelated outputs, so no question fits both.
D=Different names: the model chooses from the descriptions as well as names, and here three descriptions cover the same billing content.
T: Look for descriptions whose scope contains or repeats another's.

@ DBX-CEA D5 T5.2 applied use-case
S: Two tools from different MCP servers are called `search_docs` ("Finds relevant documents") and `search_wiki` ("Finds relevant articles"). The agent uses them interchangeably, sometimes missing the right answer. Which TWO edits remove the overlap? (Select TWO)
A: Describe both tools with the same longer text so they are equally likely to be chosen for every question
B: Rename them `search1` and `search2` so that the names carry no meaning that could bias the choice
C: State the source and content type of each, such as policy PDFs in a volume versus engineering wiki pages

When two tools do similar things, a description has to tell the model what is different. Two ways work together:
- **Scope statements**: say which source and which content the tool covers, so a question can be matched to one of them.
- **Boundaries**: name the neighboring tool and when to prefer it, which handles questions that sit between the two.

A wrong tool call spends tokens on an irrelevant result, which then sits in the window.
W: C=Source and content type: naming what each tool covers lets the model match a question about policies or a wiki how-to to the right one.

B=Meaningless names: removing meaning from the names takes away a signal the model uses, while the descriptions still overlap.
D=Whichever seems best: this hands the decision back to the model with no information to decide on, which is the original problem.
T: Give each similar tool a scope statement and a boundary against its neighbor.
