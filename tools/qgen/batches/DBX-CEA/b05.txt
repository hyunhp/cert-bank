@ DBX-CEA D4 T4.1 applied use-case
S: A travel agent is built on LangGraph, and the framework's own checkpointer already persists the graph state of each chat, so a chat resumes after a restart. Travelers now complain that a seat preference stated in one chat is unknown in the next chat. What should the team add?
A: Replace the checkpointer's persisted graph state with agent memory so that no per-chat state is stored by the agent at all
B: Move the checkpointer state into an agent session store, since a session carries the traveler's state into every later chat
C: Add agent memory for durable preferences recalled by semantic search, and keep the checkpointer for in-chat state
D: Append a growing list of every traveler's stated preferences to the shared system prompt that all the chats receive
K: C
G: ## Two stores, two scopes
Databricks documents two Lakebase-backed stores usable from agents built on any framework.
- **Agent sessions** hold the state of one interaction: usually the ordered transcript of messages, tool calls and results, but any state a framework persists, such as a LangGraph graph. A session is scoped to one interaction.
- **Agent memory** holds durable facts, preferences and decisions recalled in later, separate conversations by semantic search. Memory is scoped to a subject such as a user.
The docs say to use both together for most use cases, sessions alone for in-interaction state only, and memory alone when the framework already manages session state.
## Reading the mismatch
Here in-chat state is already handled by the framework, so the gap is cross-conversation recall, which only memory covers. Short-term versus long-term memory is general agent vocabulary; the docs name the stores sessions and memory.
W: Agent memory beside the checkpointer: the missing information must survive into an unrelated chat, which is the scope of memory, while the checkpointer keeps doing its in-chat job.
X: A=Replace the checkpointer: memory holds distilled facts retrieved by similarity, not a replayable graph, so chats would stop resuming after a restart.
B=Session store for cross-chat state: a session is scoped to one interaction, so moving the same state there does not make it visible in a different chat.
D=Shared system prompt: a single prompt holding every traveler's preferences leaks one traveler's data into another's context and grows without bound; per-subject facts need a per-subject store.
T: Information needed beyond one conversation is agent memory; sessions and framework checkpoints only cover the interaction in progress.
V: Lakebase

@ DBX-CEA D4 T4.1 applied use-case
S: A planning agent crashes midway through a long conversation and restarts. Its memory store still holds the user's stable preferences, but after the restart the agent has lost the tool calls and intermediate results it had gathered in this conversation. Which memory strategy closes the gap?
A: Persist the interaction's working state in an agent session and read it at the start of each turn so the conversation resumes
B: Run the memory pipeline more often so every tool result becomes a long-term memory entry the moment it is produced
C: Remove the memory store and keep all preferences in the conversation, so that one component holds all state
D: Store the intermediate results as embeddings in the memory store and rely on semantic search to rebuild the plan order
K: A
G: ## Session state versus memory
An agent session stores the state an agent or framework keeps for one interaction: usually the conversation history with tool calls and results, but it can be any state a framework persists, such as a LangGraph graph. The agent reads it at the start of a turn and appends as the interaction runs, so an interaction survives restarts.
Agent memory stores durable facts and is retrieved by semantic search; it is not designed to replay an ordered transcript.
## Symptom to store
- Lost transcript, tool calls or graph state inside one conversation: a session problem.
- Lost preference or decision in a later conversation: a memory problem.
Here the memory store is healthy, so the gap is in-interaction state.
W: Agent session: the stores are independent, and the session is the one that keeps the ordered transcript, tool calls and results, so reading it at the start of a turn resumes the interaction after a restart.
X: B=Pipeline per tool result: memory holds distilled durable facts, not raw intermediate results, so this floods the memory store with items that will not matter in a future conversation and still gives no ordered replay.
C=Remove memory store: the preferences were retrieved correctly. Deleting the store creates the opposite failure, because they would then have to be repeated or replayed in each conversation.
D=Embeddings of results: semantic search returns relevant items by similarity, not in the order they happened, so the plan sequence and exact tool calls cannot be reliably rebuilt.
T: Resuming one interaction after a restart is session state; keeping facts across interactions is memory.
V: Lakebase

@ DBX-CEA D4 T4.1 applied definition
S: A team lead reads the Databricks memory research mapping and asks which component plays which role. Which statement matches how the docs map the session store, the memory store and the memory pipeline?
A: The session store holds derived memory, the memory store holds episodic memory, and the pipeline copies the episodic records back into sessions
B: Both stores hold episodic memory, and the pipeline fine-tunes the model on them during an offline step so that sessions are no longer needed
C: The session store holds episodic memory, the raw record of each session; the memory store holds derived memory; the pipeline distills the first into the second
D: The session store holds derived memory, the memory store holds the raw record, and the pipeline replays that record into every new prompt
K: C
G: ## Mapping to memory research
The stateful-agents page says Databricks memory research describes the same architecture with different terms.
- The session store holds **episodic memory**, the raw record of each session.
- The memory store holds **derived memory**, the facts and workflows distilled from those sessions.
- A **memory pipeline** reads sessions, extracts the durable facts and writes them to the memory store, on demand or on a schedule; the docs call this offline process the dreaming process that distills episodic into derived memory and consolidates it over time.
## Why it matters for context
Recalled memory enters the context window. Raw episodic records spend attention budget on greetings and repeated text, while distilled facts carry the signal in few tokens.
W: Episodic in sessions, derived in memory, pipeline between them: the raw record stays replayable, and the distilled facts are what recall puts in the window.
X: A=Roles swapped: the raw transcripts are in the session store, and the pipeline reads sessions and writes memory, not the reverse.
B=Both episodic plus training: a pipeline writes distilled memories to a store; it does not train model weights, and sessions are still needed for in-interaction state.
D=Derived in sessions and replay: sessions hold the raw record, and nothing replays the whole record into every prompt, which would waste attention budget.
T: Sessions hold episodic records, memory holds derived facts, and the memory pipeline turns the first into the second.
V: Lakebase

@ DBX-CEA D4 T4.1 applied troubleshooting
S: A research agent works on one very long task in a single conversation. Its trace shows the context filling up with early tool outputs, and a teammate proposes adding a cross-user long-term memory store to fix it. Why is that the wrong memory strategy, and what fits better?
A: Long-term memory cannot be searched semantically, so the agent should use keyword lookups of its earlier tool outputs instead
B: The problem is in-interaction state growth, so trim or compact the session's context and keep large results outside the window
C: Long-term memory is only for system prompts, so the earlier tool outputs should be moved into the system prompt
D: Memory stores are deleted whenever a session ends, so nothing could be recalled for the remainder of the task
K: B
G: ## Match the store to the need
A symptom inside one interaction, such as a window filling with early tool outputs, is a working-state problem. The relevant levers are the ones for the session: trim or compact the history, or keep large results outside the window and read them when needed. Context compaction and trimming are context-engineering vocabulary used elsewhere in this guide; Databricks documents the stores, not the management policy.
Long-term memory addresses a different problem: durable facts that must carry across unrelated conversations. Adding it does not shrink the current window, and recalled items add tokens.
## The distinction
The exam convention is: fix within-conversation growth in the session and context policy; add long-term memory only for cross-conversation continuity.
W: Session context management: the need is limited to one task, so trimming, compaction or storing large outputs outside the window controls context growth, while a cross-user memory store adds recall tokens and solves nothing here.
X: A=Memory without semantic search: agent memory is documented as retrieved by semantic search, so the claim is false, and keyword lookups do not address window growth.
C=System prompt: memory is not restricted to prompts, and moving large outputs into the system prompt would spend attention budget on every request.
D=Deleted at session end: memory is independent of sessions, and deleting a session does not delete retained memory. Persistence is not the issue.
T: Window growth inside one task is a session and context-policy problem, not a reason to add long-term memory.

@ DBX-CEA D4 T4.1 applied tradeoff
S: A compliance team wants a complete record of every interaction an assistant had, available for replay, and also wants the assistant to personalize answers from what it learned about each customer. Which store layout matches these two information needs?
A: Keep the full replayable records in the session store and the distilled customer facts in the memory store, fed by a memory pipeline
B: Keep both needs in one memory store, since distilled facts and replayable records have the same scope
C: Keep both needs in the session store, and let the agent search old transcripts each time it personalizes an answer
D: Keep replayable records in the memory store and distilled facts in the system prompt, rewritten whenever a customer returns
K: A
G: ## Two layers
Sessions hold the raw, ordered record of each interaction. Memory holds the durable facts distilled from them. The two stores are independent: deleting a session, or an entire session store, does not delete memories retained in the memory store.
## Why a layered design fits
- The raw record is complete and replayable but expensive to put in a context window.
- Distilled facts are short and relevant across conversations.
A memory pipeline distills the first into the second on demand or on a schedule. Databricks recommends using both together for most use cases.
W: Session store plus memory store: the first keeps the full replayable record, the second serves compact personalization facts, and the pipeline connects them without a memory-writing tool in the agent.
X: B=One memory store: memory is scoped to a subject and holds distilled facts, not replayable interaction records, so replay would not be complete.
C=Session store only: searching raw transcripts for each answer puts long text in the window and gives no distilled durable facts to retrieve semantically.
D=Prompt rewrite: a system prompt rewritten per customer is hard to maintain and audit, and memory is not a store for ordered transcripts.
T: Raw records live in sessions, distilled facts live in memory, and a pipeline links them.

@ DBX-CEA D4 T4.2 applied use-case
S: An agent runs a multi-day vendor onboarding workflow across many job runs. It tracks which of the checklist steps are done in a scratchpad it writes into its own context. After a restart and after a compaction, the checklist is gone and finished steps are repeated. What should the team change?
A: Write the steps to a longer scratchpad in the system prompt so that the checklist is always at the top of the window
B: Store task and step status in a Delta table that the agent reads and updates, and load only the rows it needs each step
C: Ask the model to keep a running summary of the checklist at the end of every reply so compaction preserves it
D: Increase the maximum output length so the scratchpad can hold the full checklist history in each response
K: B
G: ## What a scratchpad is
A scratchpad is working notes kept inside the context window, such as a plan or a running list. It is a generally accepted agent term rather than a Databricks-documented one; in this guide the exam uses it for state that lives only in context.
## Why in-context notes fail for long work
In-context notes live and die with the window. They are lost on a restart, can be summarized away by compaction, and cost attention budget on every turn.
## Delta-backed state object
A state object stored in a Delta table (a plain Unity Catalog table; nothing Preview is needed) is durable, queryable with SQL and shared by every run. The agent reads only the relevant row, such as the next pending step, and writes status changes back. That keeps the window small and survives restarts.
W: Delta state table: status lives outside the window, so restarts and compaction cannot erase it, and the agent loads only the rows it needs at each step.
X: A=Longer scratchpad in the prompt: it is still in context, so restarts and compaction still remove it and the longer notes use more attention budget.
C=Running summary each reply: the summary is still in the window and can be dropped or distorted by compaction, and it adds tokens to every reply.
D=Longer output: output length does not make anything durable, so the next run still starts without the checklist.
T: When state must survive restarts, compaction or other runs, move it from a scratchpad to a Delta-backed state object.
V: Delta Lake, Unity Catalog

@ DBX-CEA D4 T4.2 applied tradeoff
S: A data-quality agent compares thousands of rows across tables and must track a counter, a list of failed checks and the last row processed. Runs can be interrupted and resumed hours later by a different worker. Which approach is the most reliable?
A: Ask the model to track the counter and failed checks in its scratchpad and recompute them whenever the run resumes

@ DBX-CEA D4 T4.3 applied use-case
S: A billing agent stores each customer's facts as rows in Lakebase Postgres. A user asks, "What is my current plan tier?" The tier is a single column on the customer row identified by the authenticated customer id. Which retrieval approach fits?
A: Embed all customer rows into an index and run a similarity search with the question text
B: Run a hybrid keyword and similarity search over the whole table and take the top-ranked row
C: A structured SQL query that filters the row by customer id and selects the tier column
D: Ask the model to guess the tier from the previous conversation summary and verify it later
K: C
G: ## Two retrieval styles for stored memory
- **Structured queries** use SQL against known columns and keys. They return exact values deterministically, with predictable cost and latency. Lakebase is managed Postgres, so ordinary SQL, keys and indexes apply.
- **Semantic search** (for example through Databricks AI Search, formerly Vector Search, or the semantic recall that agent memory provides) ranks items by similarity of meaning. It suits free-text recall where the query and the stored text may use different words.
## Choosing
When the agent knows the key and the field, a structured query is exact and cheap. Similarity ranking only adds uncertainty. Which style is better is an exam convention built from these documented behaviors.
W: Structured SQL query: the customer id identifies the row and the tier is a column, so a keyed lookup returns the exact value without ranking risk.
X: A=Similarity search over rows: it returns the nearest-meaning text, not guaranteed to be this customer's current tier, and it costs embedding work for a keyed fact.
B=Hybrid search over whole table: keyword plus similarity ranking still searches across customers, so it may return another customer's row and cannot guarantee exact selection.
D=Guess from summary: a summary can be stale or lossy, and this is not retrieval of the stored value.
T: Use structured queries for known keys and exact fields; use semantic search for fuzzy recall.

@ DBX-CEA D4 T4.3 applied troubleshooting
S: An agent keeps memory about product orders, with notes such as "replacement for XK-9921-B shipped late". When a user asks about order "XK-9921-B", pure embedding search ranks notes about other products with similar-sounding descriptions above the exact identifier match. What is the best fix?
A: Use hybrid keyword-similarity search so exact identifier matches are scored alongside semantic matches
B: Increase the embedding dimension of the notes so identifiers become more distinct in vector space
C: Remove identifiers from the notes before embedding so the search focuses on meaning only
D: Lower the number of results returned to one so the first similarity hit is always the right one
K: A
G: ## Why identifiers hurt pure vector search
Embedding models capture meaning, not exact strings. A SKU such as `XK-9921-B` carries little semantic signal, so similar-sounding text can rank above the exact record.
## Hybrid keyword-similarity search
Databricks AI Search supports hybrid keyword-similarity search. It combines vector-based search with keyword matching and merges the two result lists with Reciprocal Rank Fusion. The docs describe it as particularly useful in RAG applications whose data has unique keywords such as SKUs or identifiers that are not well suited to pure similarity search. When the identifier is the key, a structured SQL equality query on the identifier column is also exact; hybrid search suits free-text notes where identifier and prose mix.
W: Hybrid search: the keyword side matches the exact identifier and the vector side keeps semantic matches, and rank fusion merges them so the right order rises.
X: B=Embedding dimension: the dimension is fixed by the embedding model and a larger one does not make a model weigh exact strings.
C=Removing identifiers: the user searches by the identifier, so deleting it removes the signal that identifies the right note.
D=Return one result: the wrong note would then be returned alone, so it does not fix ranking and loses recall.
T: Identifier-heavy text needs keyword matching combined with similarity, which hybrid search provides.

@ DBX-CEA D4 T4.3 applied troubleshooting
S: A shared agent stores memories for many customers. A semantic search for "my last complaint" returns a close match that belongs to a different customer, and the trace shows the other customer's note in the prompt. What is the right fix?
A: Raise the similarity threshold so that only near-identical notes are returned for any query
B: Add instructions to the system prompt telling the model to ignore notes that mention other customers
C: Switch to a larger embedding model so that notes from different customers become easier to tell apart by meaning
D: Apply a customer id filter as a predicate on the search, so only that customer's notes are candidates

G: ## Scope is a predicate, not a similarity
Similarity ranking knows nothing about who owns a note. Ownership is metadata, and the right control is a filter applied to the query so other customers' rows never become candidates. Databricks AI Search queries can include metadata filters on columns of the source table. The docs also state that row and column level permissions are not supported on an index, so application-level access control can be implemented with the filter API. In Postgres tables on Lakebase the same idea is a `WHERE customer_id = ...` predicate.
## Why prompts and thresholds fall short

X: A=Higher threshold: a note from another customer can still be a close match, and a strict threshold also drops the right customer's paraphrased notes.
B=Prompt instruction: the foreign note is already in the window, which exposes it and relies on the model to ignore it.
C=Larger embedding model: more accurate similarity does not encode ownership, so a similar complaint from someone else will still rank high.
T: Scope retrieval by a structured filter on owner metadata; do not rely on similarity or prompts.

@ DBX-CEA D4 T4.5 applied use-case
S: A concierge agent always needs the traveler's name, home airport, language and loyalty tier for every request, and these fields are stable columns on one Lakebase row. Which retrieval approach to this memory is best?

G: ## Static and dynamic retrieval
These two terms are the exam's vocabulary; the Databricks docs do not define them.
- **Static retrieval**: the application fetches a known, fixed piece of memory with a predetermined query before the model call and places it in the prompt. It is predictable and needs no extra model round trip.
- **Dynamic retrieval**: the model decides during the run to call a retrieval tool, forming the query itself. It loads only what the task needs but adds a tool-call round trip and depends on the model choosing to call it.
## The Lakebase angle
Lakebase is managed Postgres for low-latency transactional reads, which suits a fixed keyed lookup before every request.
## Rule of thumb
Always needed and small: static. Sometimes needed, large or unpredictable: dynamic.
W: Static retrieval: the fields are always needed and small, so a pre-model keyed read gives them with no extra round trip and no chance the model forgets to ask.
X: B=Dynamic only: the model might skip the lookup and answer without the traveler's language or tier, and each request would pay an extra tool round trip for data that is always needed.
C=Semantic search of everything: the fields sit in a known row, so ranking all memories risks returning unrelated items and spends tokens.
D=Retrieve after reply: the data must be in the context before the model writes the answer, so adding it afterwards cannot influence it.
T: Always-needed, small, stable memory suits static retrieval; occasional or large memory suits dynamic retrieval.
