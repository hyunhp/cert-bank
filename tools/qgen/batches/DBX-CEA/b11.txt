@ DBX-CEA D1 T1.5 expert troubleshooting
S: A procurement agent runs on a model with a 32,000-token window, and the team reserves 4,000 tokens for output, leaving an input budget of 28,000 tokens. Requests began failing after new tools were added. One MLflow trace shows these input sizes: system prompt 2,400 tokens; 28 tool definitions of about 400 tokens each; 12 injected memories of 300 tokens each; 8 retrieved chunks of 900 tokens each; conversation history 9,400 tokens. Tool-call logs show that six tools cover 95 percent of calls, and the remaining tools are still needed for the other 5 percent. `RetrievalRelevance` is low only for chunks ranked 5 to 8. The compliance team signed off the system prompt and forbids editing it. Which change brings requests under budget with the least risk to quality?
A: Replace the 28 full definitions with a 25-token index line per tool, and load a full definition on demand once a tool is picked
B: Cut retrieved chunks from 8 to 4 and injected memories from 12 to 6, removing the low-relevance chunks and the six oldest memories
C: Cut retrieved chunks from 8 to 4 and shorten the system prompt by a third, keeping every tool definition and memory as they are now
D: Keep only the six most-used tools and remove the other 22 from the agent, saving about 8,800 tokens of tool definitions per request
K: A
G: ## Working the budget
Add the spans: 2,400 + 11,200 (28 x 400) + 3,600 (12 x 300) + 7,200 (8 x 900) + 9,400 = 33,800 tokens, which is 5,800 over the 28,000-token input budget. The exam guide calls this finding the elements that consume a disproportionate share of the attention budget; MLflow traces record token usage per step, which is how the breakdown is known.
## Checking each change
- Tool index with on-demand schemas: 28 x 25 = 700 tokens, plus about 800 for the two schemas a typical request loads. Saves about 9,700, giving roughly 24,100. Every tool stays reachable.
- Fewer chunks and memories: saves 3,600 + 1,800 = 5,400, giving 28,400, still 400 over.
- Fewer chunks plus a shorter system prompt: violates the compliance sign-off and still lands near 29,400.
- Six tools only: 25,000 tokens, under budget, but the 5 percent of requests that need the other 22 tools now fail.
The tool index is progressive disclosure, which is the exam's vocabulary.
W: Tool index with on-demand schemas: it removes the largest block (11,200 tokens) while keeping every tool reachable, which brings the request to about 24,100 tokens without touching the signed-off prompt.
X: B=Fewer chunks and memories: the saving of 5,400 tokens leaves the request at about 28,400, still over the 28,000-token budget, and the oldest memories may matter.
C=Fewer chunks and a shorter prompt: editing the system prompt breaks the compliance rule, and the total stays over budget.
D=Six tools only: it fits the budget, but 5 percent of requests lose the tools they need, a capability loss the index avoids.
T: Add up the trace's token spans first, then cut the largest disproportionate block in a way that keeps every capability reachable.

Context poisoning is the exam guide's name for a wrong statement, often a hallucination, that enters the context and is then reused. C=Distraction, compact more often: compaction would keep the note, because notes are re-injected after compaction, so the false column survives.
D=Confusion, remove a tool: there is no sign of a wrong tool choice, and removing `describe_table` removes the one way to verify the schema.

@ DBX-CEA D3 T3.3 expert troubleshooting
S: A field-service agent queries a Delta Sync index on a standard endpoint with Databricks-computed embeddings, synced in Triggered mode from `kb.manual_chunks` (`chunk_id`, a `section_title` of about eight words and a `chunk_text` of about 400 tokens). An MLflow 3 evaluation shows `RetrievalRelevance` of 0.88 for questions that echo a section title, but 0.31 for questions phrased like the body text, such as "torque for the M8 flange bolts", although each answer sits in the `chunk_text` of an existing row. The index details show `embedding_source_column="section_title"`. A documentation site reads `section_title` from the same table, and the agent must keep answering during the fix. Which remediation fits?
A: Create a second index on the same table with `chunk_text` as the embedding source, switch the agent to it when ready, then delete the old one
B: Start a sync of the existing index with Sync now, so that AI Search recomputes the embeddings of every row from the current source table
C: Append a one-line summary of each chunk's body to its `section_title` value in the table, then sync so that the titles carry more meaning
D: Raise `num_results` from 5 to 30, so that sections whose titles match the question less closely still reach the agent with their body text
K: A
G: ## What a Delta Sync index embeds
With Databricks-computed embeddings, a Delta Sync index embeds one source column, the `embedding_source_column` given in the creation call, and AI Search embeds each query with the same model. Similarity is measured between the question and that column only; other synced columns come back with the results but do not shape the vector match.
## Reading the evidence
- Questions that echo titles score 0.88; questions in body wording score 0.31.
- The answers exist in `chunk_text`, which is not the embedded column.
So the index compares questions with eight-word titles, and body-level questions cannot match. `RetrievalRelevance` (no ground truth needed) judges whether the retrieved context is relevant to the request, which is where the gap shows.
## Fixing it without downtime
The create-index page says the index schema is fixed at creation and gives a no-downtime procedure: create a new index, switch traffic once it is ready, then delete the original. Its update section offers only syncs for a Delta Sync index, and on a standard endpoint a sync processes only the data that changed since the last sync; it never changes which column is embedded.
W: New index on `chunk_text`: body-level questions are matched against the body text, and switching only after the new index is ready keeps the agent answering throughout.
X: B=Sync now: a sync on a standard endpoint processes only changed rows and still embeds `section_title`, so the match does not change.
C=Longer titles: it adds some body meaning to the vectors, but it rewrites a column the documentation site displays, and a one-line summary still misses most body details.
D=More results: candidates are still ranked by title similarity, so body-level answers stay scattered, and 30 chunks of about 400 tokens flood the context.
T: When retrieval works only for wording that echoes one column, check which column the index embeds and rebuild the index on the right one without downtime.

@ DBX-CEA D3 T3.5 expert use-case
S: A developer-support agent answers questions about an internal REST API from 900 reference pages. Each page has a 30-token endpoint path line, a 120-token description, a 330-token parameter table and two code examples of about 300 tokens each. The pipeline embeds one chunk per page with `databricks-bge-large-en`, which the platform team mandates. Parameter questions such as "which field sets the run timeout?" score well, but example questions such as "show paging through job runs" almost always miss. B: Fixed 512-token chunks across each page with 20 percent overlap, so that every part of the page, examples included, is embedded
C: One chunk per page with both code examples moved ahead of the parameter table, so that example questions match the start of each chunk
D: One chunk with path, description and parameters (about 480 tokens), and leave the code examples out of the index to save tokens
K: A
G: ## Three inputs to a chunking decision
The exam guide asks you to choose a chunking strategy from document structure, the embedding model's context length and the query types.
- Embedding window: the supported-models page gives BGE Large (En) a 512-token embedding window, and the RAG pipeline guide warns that chunks over the model's limit are truncated, losing information.
- Structure: a reference page has natural sections (path, description, parameters, examples); the guide recommends format-specific chunking along such boundaries.
- Query types: parameter lookups and requests for an example.

- Today: 30 + 120 + 330 + 2 x 300 = 1,080 tokens per page. Only the first 512 are embedded: the path, description and parameters (480) plus 32 tokens of the first example. Parameter questions match; example questions cannot.

- Budget: four chunks take at most 4 x 480 = 1,920 tokens, under 2,000.
- Examples first: 30 + 600 = 630 tokens before the table, so the parameter table falls outside the window.
- Fixed 512-token windows: the path appears only in the first window of each page, and cuts land inside tables and code.
W: Section chunks with the path: every chunk fits the 512-token window, example questions now match an embedded example, parameter questions keep working, and four chunks stay within 2,000 tokens.
X: B=Fixed windows with overlap: the examples get embedded, but most chunks lose the endpoint path and cuts split tables and code, which breaks the naming rule.
C=Examples first: the path and two examples already take 630 tokens, so the parameter table is no longer embedded and parameter questions start to miss.
D=Drop the examples: the parameter chunk fits, but example questions then have nothing to retrieve, so the failure becomes permanent.
T: Split documents along their own sections so that each chunk fits the embedding window, carries its identifying header and serves one query type.

@ DBX-CEA D3 T3.9 expert use-case
