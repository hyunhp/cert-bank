@ DBX-CEA D4 T4.6 advanced tradeoff
S: To stop context pollution, a team cuts memory retrieval from 10 results to 2. The evaluation dataset now shows fewer unrelated details in answers, but questions that need three separate stored facts (diet, budget, dates) lose accuracy. Which next step best balances both failures?
A: Return to 10 results and accept the pollution, since recall failures cost more than extra tokens in most tasks
B: Keep 2 results and ask users to repeat the missing facts, since the store is not designed for multi-fact questions
C: Set a relevance score gate with a moderate cap, then re-run the evaluation for unrelated details and missing facts
D: Run the memory search a second time per question and inject both result sets, doubling the retrieved text per turn
K: C
G: ## Tuning both failures together
Lowering a cap trades one failure for the other: fewer results reduce over-retrieval but raise the chance of under-retrieval for questions that need several facts (exam convention terms). A fixed small number cannot adapt to a question that needs one fact and a question that needs three.
- A **relevance gate** lets the number of injected memories follow how many are actually relevant.
- A **moderate cap** bounds the worst case so a broad question cannot flood the window.
- Re-running the **same evaluation dataset** with the same judges (for example in an MLflow 3 evaluation run) shows whether pollution and recall both improved, instead of fixing one and silently breaking the other.
W: Relevance gate plus moderate cap, then re-evaluate: the injected count adapts to the question, the cap bounds the window, and the same evaluation measures both unrelated details and missing facts.
X: A=Back to 10: this restores recall by reintroducing the original pollution and tokens; it treats one failure as free and measures neither.
B=Keep 2 and ask users: the store does hold the facts; the cap, not the store, is the problem, and pushing the work to users hides a configuration defect.
D=Second search per question: it doubles retrieved text on each turn, including simple questions, which raises distraction and cost while still using no relevance gate.
T: Tune cap and relevance gate together and measure both pollution and recall on the same evaluation.

@ DBX-CEA D4 T4.5 applied tradeoff
S: A team moves an agent from static memory injection to a dynamic memory lookup tool on Lakebase. Which TWO trade-offs should they expect? (Select TWO)
A: Context size stays fixed, because the tool returns the same number of tokens for each question asked
B: Each lookup adds a tool-call round trip, so requests that use memory take longer than a preloaded block
C: Recall improves over static injection, because the model calls the tool whenever memory could help
D: Tool descriptions can stay vague, because the model reads the memory store's contents on its own
E: The agent may skip the lookup or phrase a poor query, which can leave relevant memories out of the context
K: B,E
G: ## What changes with dynamic retrieval
Static retrieval loads memory before the model call. Dynamic retrieval gives the model a tool, so the model chooses whether and how to query. Both terms are the exam's convention, not Databricks-defined.
## Costs
- The model must decide to retrieve and form a good query. If it does not, memory is missing, which is under-retrieval.
- Each lookup is another step in the loop, adding latency.
## Benefit
The window holds only what was asked for, so tokens are saved when memory is rarely needed.
W: B=Added round trip: a tool call and its result are extra steps before the answer, so memory-using requests are slower.
E=Skipped or poor lookups: the model owns the decision and the query, so relevant memories can be missed.
X: A=Fixed context size: tool results vary with the query and how many results return, so context size varies.
C=Better recall: nothing forces the model to call the tool, which is exactly the weakness of this approach compared with static injection.
D=Vague descriptions: the model learns the tool only from its description, so the tool must still say what it retrieves and when.
T: Dynamic retrieval saves tokens but adds latency and depends on the model choosing to retrieve well.
V: Lakebase

@ DBX-CEA D4 T4.1 applied use-case
S: A travel agent is built on LangGraph, and the framework's own checkpointer already persists the graph state of each chat, so a chat resumes after a restart. Travelers now complain that a seat preference stated in one chat is unknown in the next chat. What should the team add?
A: Append a growing list of the travelers' stated preferences to the shared system prompt used by the chats
B: Add agent memory for durable preferences recalled by semantic search, and keep the checkpointer for in-chat state
C: Replace the checkpointer's persisted graph state with agent memory so the agent keeps one store for both needs
D: Move the checkpointer state into an agent session store, since a session carries the traveler's state into later chats
K: B
G: ## Two stores, two scopes
Databricks documents two Lakebase-backed stores usable from agents built on any framework.
- **Agent sessions** hold the state of one interaction: usually the ordered transcript of messages, tool calls and results, but any state a framework persists, such as a LangGraph graph. A session is scoped to one interaction.
- **Agent memory** holds durable facts, preferences and decisions recalled in later, separate conversations by semantic search. Memory is scoped to a subject such as a user.
The docs say to use both together for most use cases, sessions alone for in-interaction state only, and memory alone when the framework already manages session state.
## Reading the mismatch
Here in-chat state is already handled by the framework, so the gap is cross-conversation recall, which only memory covers. Short-term versus long-term memory is general agent vocabulary; the docs name the stores sessions and memory.
W: Agent memory beside the checkpointer: the missing information must survive into an unrelated chat, which is the scope of memory, while the checkpointer keeps doing its in-chat job.
X: A=Shared system prompt: a single prompt holding every traveler's preferences leaks one traveler's data into another's context and grows without bound; per-subject facts need a per-subject store.
C=Replace the checkpointer: memory holds distilled facts retrieved by similarity, not a replayable graph, so chats would stop resuming after a restart.
D=Session store for cross-chat state: a session is scoped to one interaction, so moving the same state there does not make it visible in a different chat.
T: Information needed beyond one conversation is agent memory; sessions and framework checkpoints only cover the interaction in progress.
V: Lakebase

@ DBX-CEA D2 T2.3 applied troubleshooting
S: A 2,000-token system prompt works well except for refund questions, which are a few percent of requests: traces show the agent skipping the identity check that must precede any refund. The team wants the cheapest fix that is easy to maintain. Which is best?
A: Rewrite the whole prompt from scratch with a new structure, so that the refund rules receive more weight
B: Add one short, specific rule: before any refund, verify the customer's identity, and say which tool to call first
C: Paste the full 1,500-word refund policy into the prompt, so the agent has the policy's details at hand
D: Add ten worked refund examples at the end of the prompt, covering the main refund situations in the policy
K: B
G: ## Targeted repair, smallest change
A revision should address the observed failure at the lowest token cost and with the least risk of breaking what works. The failure here is narrow: one missing step in one request type. A short, specific, conditional rule ("before any refund, verify identity with `verify_customer`") names the step and the trigger in a few tokens.
## Why the larger options cost more
- A rewrite re-opens behavior that works and must be re-evaluated in full.
- Policy text and many examples add tokens to every request, although refunds are a few percent of them.
The cost-of-maintenance framing is the exam's convention; verify the change by re-running the evaluation.
W: One specific rule: it targets the missing step with a handful of tokens and leaves the rest of the tested prompt untouched.
X: A=Full rewrite: it risks regressions in rules that work today and needs the whole evaluation re-checked for a narrow failure.
C=Full policy text: 1,500 words are paid for on each request, while refunds are rare, and a long policy still need not produce the identity check.
D=Ten examples: it adds many tokens to each request for a rare case, and examples are costlier than a one-line rule.
T: Fix a narrow failure with a short, specific rule, not a rewrite or a large addition.

@ DBX-CEA D2 T2.2 advanced tradeoff
S: A support agent's prompt has 12 few-shot examples of about 150 tokens each. In an MLflow evaluation on a fixed dataset, correctness is 0.61 with no examples, 0.82 with three, 0.83 with six and 0.83 with twelve. Token cost matters. Which set should the team keep?
A: Zero examples, since zero-shot is the cheapest configuration and the token savings outweigh accuracy
B: The full twelve, since each added example scored at least as high as the set before it
C: Six examples that are most similar to each other, so the output format is reinforced more strongly
D: The three examples that produced the main gain, dropping those with near-zero marginal value
K: D
G: ## Marginal contribution under a token budget
Every few-shot example is paid for on every request. The useful measure is the marginal contribution: how much the score rises when one more example is added. "Marginal contribution" and "token budget" are the exam guide's vocabulary for this trade-off, not terms the Databricks docs define.
## Reading the numbers
- 0 to 3 examples: a large gain (0.21), worth the tokens.
- 3 to 6 and 6 to 12: gains near zero, but the cost per request doubles and quadruples.
Run the comparison as separate MLflow evaluation runs with the same dataset and scorers, then keep the smallest set that holds the gain.
W: Keep three: they deliver almost all of the improvement, and the further examples cost tokens on each request for no measurable gain.
X: A=Dropping all examples: it throws away the large 0.21 gain, which is worth far more than the 450 tokens spent.
B=Keeping twelve: "at least as high" ignores that the extra nine examples add about 1,350 tokens per call for a 0.01 change.
C=Six similar examples: similarity adds redundancy, not coverage, and doubles the example cost without the evidence of a gain.
T: Keep the smallest few-shot set that captures the measured gain.

@ DBX-CEA D1 T1.2 applied use-case
S: A log-analysis agent must answer questions about incident reports stored in Unity Catalog volumes. Loading every report into the prompt would fill the window before the first question. Which proactive strategy reduces context pressure while keeping every report reachable?
A: Summarize each report once into a single paragraph and keep the paragraphs, deleting the original files
B: Keep an index of report IDs and titles in context, plus a tool that loads one report when details are needed
C: Split each report into sentences and load the sentences in random order, so no report takes much space
D: Load the five newest reports at the start of each run, as recent incidents are likeliest to be asked
K: B
G: ## Just-in-time retrieval
Just-in-time (JIT) retrieval is a generally accepted context-engineering strategy: the agent holds light references (IDs, titles, file paths, queries) and loads the full content only at the moment it is needed, using a tool. The window then holds what the current step needs instead of everything that might be needed.
## What it trades
- Context stays small, and every report stays reachable.
- It costs an extra tool call per lookup, and the agent has to know what to ask for, so the index or tool description must say what each item is.
Databricks documents the tool side of this: give a retriever tool a description that tells the agent when to search, and it fetches documents on demand.
W: Index plus load-on-demand tool: it keeps the window small and every report reachable; the agent fetches only the report relevant to the current question.
X: A=Summaries only: deleting the originals loses detail the next question may need, and there would be no way to get it back.
C=Random sentences: every sentence still enters the context, so the window is just as full, and the order destroys the report's meaning.
D=Five newest: this guesses what will be asked; questions about older incidents would fail, and the five reports still take window space on each run.
T: When the corpus is too big to preload, keep lightweight references in context and load the full item on demand with a tool.

@ DBX-CEA D1 T1.1 applied use-case
S: A personal-assistant agent re-asks every user for their preferred report format and time zone in each new conversation. Raw transcripts of past chats are kept in a session store. Which two changes best fit the failure? (Select TWO)
A: Keep the preferences in the in-context history of the current conversation and repeat them in its prompt
B: Keep the memories scoped to the user they describe, so recall returns that user's preferences only
C: Lengthen the session store's retention, so earlier transcripts stay available when a new chat starts
D: Paste the user's full past transcripts into the system prompt at the start of each new conversation
E: Store the stable preferences as durable facts in agent memory, recalled by semantic search when relevant
K: B,E
G: ## Two kinds of state
Databricks documents two managed stores for agents, both backed by Lakebase and usable from agents built on any framework:
- **Agent sessions** hold the state of one interaction: usually the conversation history (messages, tool calls, results).
- **Agent memory** holds durable facts, preferences and decisions that the agent recalls in later, separate conversations, retrieved by semantic search.
Memories are scoped to a subject (for example a user), not to an interaction, so the facts that matter in a future, unrelated conversation are recalled whenever they are relevant. The stores are independent: deleting a session store does not delete what a memory store retains.
## Why this fixes the symptom
A preference such as a time zone should survive the end of a conversation. That is memory's job. Sending every old transcript is the opposite of context engineering: it fills the window with mostly irrelevant text.
W: B=User-scoped memories: because memories belong to a subject rather than a conversation, the agent recalls this user's preferences in later conversations and does not mix in other users' facts.
E=Agent memory: preferences are durable facts scoped to the user, recalled by semantic search in later conversations, so the agent no longer re-asks.
X: A=In-context history: the history belongs to one interaction, so a new conversation starts without it.
C=Longer session retention: a session is scoped to one interaction, so keeping transcripts longer does not make them visible in a different conversation, and raw transcripts are not distilled preferences.
D=Pasting all transcripts: it spends the attention budget on old chat text and grows without bound; memory retrieval returns only relevant facts.
T: Within one interaction use sessions; across conversations use agent memory, and distill sessions into memories with a pipeline.

@ DBX-CEA D4 T4.6 applied comparison
S: An engineer compares two agent traces to tell over-retrieval from under-retrieval in a memory system. Which TWO observations point to over-retrieval? (Select TWO)
A: The memory search returns one item, and the answer uses it correctly and cites the stored detail
B: The memory search returns no items, and the agent asks the user for a preference already in the store
C: The answer lacks a fact that exists in the store but was missing from the list the memory search returned
D: The search returns twenty items, the answer uses two, and an unrelated item's detail shows up in it
E: Input tokens per model call keep rising as the store grows, although the kind of questions has not changed
K: D,E
G: ## What each failure looks like in a trace
Over-retrieval and under-retrieval are the exam's convention terms (generally accepted, not defined in the Databricks docs).
- Over-retrieval shows as many injected items with few used, unrelated details echoed in the answer, or prompt size that grows with the store because nothing bounds or gates the injection.
- Under-retrieval shows as an empty or incomplete result for a fact that is in the store, followed by the agent asking again or answering without it.
- A small result that is used correctly is the healthy case.
Compare three things in the trace: what the store contains, what retrieval returned and what the answer used.
W: D=Many returned, few used: injected items outnumber what the answer needs and an unrelated detail leaked into the response, which is the signature of pollution.
E=Prompt size rising with the store: when input tokens track store growth without a gate or cap, more and more weakly related memory is entering each call.
X: A=One item used correctly: retrieval returned what was needed and nothing more, so neither failure is present.
B=Empty result for a stored preference: nothing was injected at all, and the fact the agent needed was left out, which is under-retrieval.
C=Missing stored fact: the store held it but retrieval did not return it, so the window lacked the item; this is under-retrieval, not too much context.
T: Many items injected and few used means over-retrieval; a stored fact that never arrives means under-retrieval.
V: Lakebase

@ DBX-CEA D5 T5.6 applied troubleshooting
S: A team packaged its data-quality workflow as a skill whose description reads "Helpful workflow stuff." Users report that the agent either ignores the skill for data-quality requests or sometimes applies it to unrelated tasks. The `SKILL.md` instructions themselves are correct. What fixes the loading behavior?
A: Inline the referenced scripts into `SKILL.md` so that the skill loads as one self-contained file with no extra reads
B: Rewrite the name and description to state what the skill does and when to use it, keeping it to one workflow
C: Copy the instructions into the system prompt as well, so that the agent has them whatever the description says
D: Merge this skill with the team's other skills into one large skill so that the agent has a single description to match
K: B
G: ## The description is the loading trigger
The agent decides whether to load a skill from its name and description. A vague description gives it nothing to match, which causes both misses and false loads. The docs' guidance for skill authors is to:
- "Use clear names and descriptions": a concise, descriptive name and summary help the agent match the right skill to the right request.
- "Keep skills focused": skills work best on a single task or workflow, which makes it easier to recognize when one applies.
- "Avoid unnecessary context", since extra detail makes a skill harder to apply reliably.
The context-cost framing (the metadata is the always-visible part) is the exam's convention.
W: Clear description, focused skill: a specific statement of what the skill does and when to use it gives the agent a reliable trigger and cuts both missed loads and false loads.
X: A=Inline all scripts: this makes the file larger and loads every script text whenever the skill loads, instead of referencing files that are read only when needed, and the vague description still decides loading.
C=Duplicate into the prompt: this pays the always-on cost the skill was meant to avoid and leaves the real defect, the vague description, unfixed.
D=One large merged skill: the docs advise a narrow scope per skill; a merged skill's description would be even less specific and loads a lot of unrelated text.
T: A skill loads according to its name and description, so make them specific and keep each skill focused.

@ DBX-CEA D4 T4.5 applied troubleshooting
S: An assistant retrieves user memories dynamically through a lookup tool on Lakebase. Traces show that on questions about the user's earlier decisions, the agent answers directly without calling the tool, so personalization is missing. Which change addresses this with the least extra context?
A: State in the tool description what it returns and when to call it, or preload the few always-needed fields
B: Replace the tool with a larger system prompt that repeats each memory category in full on each turn
C: Remove the lookup tool and ask the model to recall earlier decisions from its general training knowledge
D: Preload all stored memories for the user into every prompt so that the tool call is no longer needed
K: A
G: ## Dynamic retrieval depends on the model choosing the tool
With dynamic retrieval the model decides whether to call a lookup tool, so the tool description is the main lever: it should state what memory holds and the kinds of question that need it. Static and dynamic retrieval are exam vocabulary, not Databricks-defined terms.
## Balancing cost
Fields that every answer needs can be loaded statically from Lakebase before the call. Everything else stays behind the tool, so the window carries only what is requested.
W: Clearer tool description or small static preload: the first makes the model call the tool when it should, and the second guarantees the always-needed fields, both without loading the whole store.
X: B=Larger repeating prompt: it spends tokens on each turn and does not retrieve the user's actual stored decisions.
C=Training knowledge: the model has no knowledge of this user's decisions, so it would invent them.
D=Preload everything: it removes the skipped-call risk but injects every memory into every request, which is the over-injection cost dynamic retrieval avoids.
T: If a model skips dynamic lookups, improve the tool description or preload only the small always-needed fields.
