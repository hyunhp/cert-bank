@ DBX-CEA D3 T3.5 applied use-case
S: A maintenance agent answers questions from Markdown runbooks stored in a Unity Catalog volume. Each runbook has `##` sections such as "Prerequisites", "Procedure" and "Rollback". The current pipeline cuts every file into fixed 800-character pieces, and traces show retrieved chunks that start in the middle of a procedure step or mix the end of "Procedure" with the start of "Rollback". Which chunking change fits the document structure?
A: Keep the fixed 800-character pieces but double the overlap, so every cut point is repeated in the next chunk and no step is ever split
B: Chunk each runbook as one whole file, so the full procedure and rollback always travel together in a single retrieved chunk
C: Split on the Markdown headers so each section becomes a chunk, and store the runbook title and section heading as metadata with the chunk
D: Switch to splitting on single sentences so that no chunk can ever contain parts of two different steps or two different sections
K: C
G: ## Chunking follows structure, not an arbitrary character count
Chunking is the pipeline step that breaks parsed documents into pieces that are embedded and retrieved. The Databricks guide on building an unstructured data pipeline for RAG lists these strategies:
- Fixed-size chunking: split by a set number of characters or tokens. Quick, but it ignores meaning, so chunks are rarely semantically coherent and the guide says it rarely works for production-grade applications.
- Paragraph-based chunking: use natural paragraph boundaries.
- Format-specific chunking: formats such as Markdown or HTML have inherent structure (for example headers) that can define chunk boundaries.
- Semantic chunking: use topic shifts to find boundaries.
The guide also advises storing metadata such as the source document name and section heading with each chunk, because it helps match queries to chunks. A chunk should be a meaningful unit that can stand alone.
That is the exam's reading of task 3.5: read the document structure first, then pick the strategy that preserves it.
W: Section-based splitting on Markdown headers: each runbook section becomes a coherent, self-contained chunk, so a procedure is never cut mid-step or glued to the rollback text, and the title and heading metadata tell both the retriever and the model where the chunk came from.
X: A=More overlap: overlap helps continuity across cuts, but it still cuts at arbitrary character positions, and doubling it duplicates text, so the same passage consumes several result slots. The structure is still ignored.
B=Whole file: the file mixes prerequisites, procedure and rollback, so a question about one section returns the other two as distractors and spends tokens; whole-file chunks also dilute the embedding.
D=Single sentences: a sentence loses the surrounding step, so the retrieved text often cannot stand alone and the model sees fragments without the procedure around them.
T: Pick the chunk boundary the document already offers (headers, clauses, paragraphs) and carry the heading as metadata.

@ DBX-CEA D3 T3.5 advanced troubleshooting
S: A policy agent indexes 3,000-token sections with an embedding model whose documented maximum input is far smaller. Questions about content late in a section are never retrieved, although the text is in the Delta table, while questions about the first few paragraphs work. Tracing shows the right sections ranked low for those late-content questions. What is the most direct fix?
A: Re-chunk on subheadings so each chunk fits the embedding model's maximum input, or pick a model that accepts longer input
B: Raise `num_results` so the sections with the late content come back, even though their embeddings cover only part of the text
C: Switch the generation model to one with a larger context window, so that the long sections can be read in full by the agent
D: Add a longer system prompt telling the agent to look at the end of each retrieved section before answering any question
K: A
G: ## The embedding model's input limit sets an upper bound for chunk size
An embedding model turns a chunk into one vector. Each model has a maximum input length in tokens. The Databricks RAG pipeline guide says that if chunks exceed that limit they will be truncated, potentially losing important information (its example is an older embedding model with a short limit). Truncated text is never represented in the vector, so similarity search cannot find it, even though the text sits in the table.
- Symptom: early content retrievable, late content not.
- Diagnosis: compare chunk token counts with the embedding model's documented maximum input.
- Fix: chunk to fit (preferably on structural boundaries) or select an embedding model with longer input, then re-embed.
The generation model's context window is a separate limit: it decides how much retrieved text the LLM can read, not how much text an embedding can represent.
W: Re-chunk to fit the embedding limit (or use a longer-input embedding model): the late text was truncated before embedding, so only a chunk that fits entirely gives every part of the section a searchable vector.
X: B=More results: the late content has no vector of its own, so the section is ranked by its first paragraphs only; returning more sections adds tokens without making the late text findable.
C=Larger generation window: the failure happens before generation, at embedding time. A bigger LLM window changes nothing about what the vector represents.
D=Longer prompt: the agent only sees what retrieval returns, and the sections that match are not the ones returned for these questions, so an instruction about reading section ends cannot recover them.
T: Keep every chunk inside the embedding model's maximum input, or the unseen tail is invisible to retrieval.

The Databricks RAG pipeline guide states that finding the proper chunking method is iterative and context-dependent and that no approach fits all. Its trade-off: smaller chunks focus on specific details but lose surrounding context; larger chunks capture more context but can include irrelevant information or cost more.

G: ## Two retrieval timings
Retrieval can run in two places. These terms are generally accepted context-engineering vocabulary and the exam's convention; the Databricks docs describe the mechanisms but do not define the terms.
- Pre-inference retrieval: the application retrieves relevant chunks before calling the model and places them in the prompt. Deterministic, one model call, no dependence on the model choosing to search.
- Just-in-time (JIT) agentic retrieval: the agent gets a retriever tool and decides when and what to retrieve during its run. Databricks documents this pattern: the AI Bridge `VectorSearchRetrieverTool` exposes an AI Search index as a tool, with a description that tells the agent when to search.
Choose by use case: when every request needs the same knowledge source and grounding is mandatory, pre-inference retrieval is simple and predictable.
W: Pre-inference retrieval: the index is queried on every question before the model call, so retrieval always happens, latency stays predictable, and one model call is enough.
X: A=JIT agentic retrieval: the model might skip the search, or loop, which breaks the guarantee of retrieval on each question and the one-call latency.
C=Full documentation in the prompt: that spends the attention budget on text that is mostly irrelevant to any one question and does not scale with the corpus.
D=Retrieve after answering: the first answer is produced without grounding, so ungrounded content can already reach the user, and it adds a second model call.
T: When every request needs the knowledge, retrieve before inference; let the agent decide only when need varies.
