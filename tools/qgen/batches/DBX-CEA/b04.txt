@ DBX-CEA D3 T3.5 applied use-case
S: A coding assistant answers questions from a Python repository stored in a Unity Catalog volume. The pipeline cuts every file into pieces of 60 lines, and traces show retrieved chunks that start inside a function body or hold the end of one function and the start of the next, so the model cannot tell which function a snippet belongs to. Which chunking change fits the structure of source code?
A: Cut every 30 lines instead of 60, so that fewer functions are split across two chunks and each chunk holds less unrelated code
B: Embed each whole source file as one chunk, so every function stays together with its neighbors and no definition is ever cut in a result
C: Split on blank lines and comment lines, so that every block of code becomes a small chunk of its own and statements stay on separate chunks
D: Split on function and class definitions so each one stays whole, and keep the file path and enclosing class or function name with the chunk
K: D
G: ## Chunking follows structure, not an arbitrary line or character count
Chunking is the pipeline step that breaks parsed documents into pieces that are embedded and retrieved. The Databricks guide on building an unstructured data pipeline for RAG lists these strategies:
- Fixed-size chunking: split by a set number of characters or tokens. Quick to set up, but it typically does not give semantically coherent chunks.
- Paragraph-based chunking: use natural paragraph boundaries.
- Format-specific chunking: formats such as Markdown or HTML have an inherent structure (for example headers) that can define chunk boundaries.
- Semantic chunking: use topic shifts to find boundaries.
The guide also asks for chunks that are semantically coherent and can stand independently as a meaningful unit, and for metadata such as the source document name or section heading, because it helps match queries to chunks.
Source code is not a format the guide names, but the same idea applies: its inherent structure is the function or class definition. Reading task 3.5 this way is the exam's convention: look at the document structure first, then pick the strategy that preserves it, and carry the parent (file path, class name) as metadata.
W: Splitting on function and class definitions: each chunk is a complete, self-contained unit of code, and the file path and enclosing name tell the retriever and the model which function a snippet comes from.
X: A=Shorter line windows: a smaller fixed window still cuts at arbitrary lines, so definitions are still split, and shorter pieces lose even more of the surrounding function.
B=Whole file: a question about one function returns every other function in the file as distraction, spends tokens, and dilutes the single embedding of the file.
C=Blank and comment lines: these are not definition boundaries, so a function body is split into fragments that cannot stand alone, and the model still cannot tell what they belong to.
T: Cut where the document's own structure ends a unit (here a definition) and keep its parent name as metadata.

@ DBX-CEA D3 T3.5 advanced troubleshooting
S: A policy agent embeds 400-token body chunks. Before embedding, the pipeline prepends a 150-token header (document summary, title, section path) to each body. The embedding model's documented maximum input is 512 tokens. Questions about the last part of each body are never retrieved, although the text is in the Delta table, while questions about the first paragraphs work. What is the most direct fix?
A: Raise `num_results` so that the chunks holding the late content come back, even though their embedded vectors reflect only the header and the early body
B: Keep header plus body within the embedding model's maximum input, for example by cutting the body to about 350 tokens, or choose a model that accepts longer input
C: Switch the generation model to one with a larger context window, so that the full chunks can be read in whole by the agent once they are returned
D: Raise the chunk overlap to 25% so that late sentences of one chunk are also repeated at the start of the next chunk, where they fit within the limit
K: B
G: ## The embedding model's input limit applies to everything that is embedded
An embedding model turns the text it receives into one vector. Each model has a maximum input length in tokens. The Databricks RAG pipeline guide says that if chunks exceed that limit they will be truncated, potentially losing important information. Truncated text is never represented in the vector, so similarity search cannot find it, even though the text sits in the table.
- What counts is the full text passed to the embedding model: the body plus any prefix the pipeline adds (header, summary, title). Here 150 + 400 = 550 tokens exceeds the 512-token limit, so the tail of every body is cut.
- Symptom: early content retrievable, late content not.
- Diagnosis: compare the token count of the exact embedded text with the model's documented maximum input.
- Fix: size the body so prefix plus body fit (or move the header to metadata columns), or select an embedding model with a longer input, then re-embed.
The generation model's context window is a separate limit: it decides how much retrieved text the LLM can read, not how much text an embedding can represent.
W: Fit header plus body in the embedding limit (or use a longer-input model): the late text was truncated before embedding, so only a text that fits entirely gives every part of the chunk a searchable vector.
X: A=More results: the late content has no vector of its own, so each chunk is ranked by its header and early body only; returning more chunks adds tokens without making the late text findable.
C=Larger generation window: the failure happens before generation, at embedding time. A bigger LLM window changes nothing about what the vector represents.
D=More overlap: the overlapping sentences are repeated, but each embedded text is still header plus body over the limit, so its tail is still cut; overlap also adds duplicate text.
T: Count everything that goes into the embedding call, and keep it inside the model's maximum input.

@ DBX-CEA D3 T3.5 applied comparison
S: An agent answers questions over 20-page quarterly reports chunked by section. Narrow questions such as "What was churn in the EMEA segment?" work well. Broad questions such as "Summarize the main risks in the Q3 report" retrieve a few arbitrary risk-related sections and the answer misses most of the report. Which change to the index suits both query types?
A: Add one summary chunk per report, generated at ingestion and linked to the report by an id, next to the existing section chunks
B: Replace the section chunks by one chunk per sentence, since a very small unit makes broad questions find every sentence about risks
C: Raise the section chunk size to a whole report, since this alone makes the narrow questions work as well as before for each segment
D: Raise `num_results` to 40 so that most of the sections of the report are returned for every question, narrow ones included, to cover all risks

G: ## Match the chunk granularity to the query type
The Databricks RAG pipeline guide states that finding the proper chunking method is iterative and context-dependent and that there is no one-size-fits-all approach. Its trade-off: smaller chunks focus on specific details but lose surrounding context; larger chunks capture more context but can include irrelevant information. The guide also lists content-based metadata such as summaries and topics, stored alongside the chunks.
- Narrow lookups: the answer sits in one section, so section-level chunks fit.
- Broad, whole-document questions: no single section holds the answer. A summary chunk written once at ingestion gives the retriever a unit that matches the question and gives the model the report's overall picture at a small token cost.
Using both granularities for the two query types is the exam's reading of task 3.5 (query type drives chunk design); the docs state the trade-off, not this recipe.
W: Section chunks plus a per-report summary chunk: narrow questions still match their section, and broad questions match the summary, which covers the whole report in a few tokens.
X: B=Sentence chunks: a risk is rarely one sentence, so the retrieved fragments cannot stand alone, and narrow questions lose the surrounding context they need.
C=Whole-report chunks: each report mixes all segments and quarters, so narrow questions return a long text full of unrelated figures, and the single embedding is diluted.
D=Forty results: this multiplies the tokens and still returns whichever sections score highest; the broad question has no unit that represents the whole report, and narrow questions are flooded.
T: Offer the granularity each query type needs: sections for lookups, a summary unit for whole-document questions.

A: The number of articles in the corpus, because a larger corpus always needs a larger chunk size to keep the index small
B: The maximum input length of the chosen embedding model, which caps the tokens that can be represented in one vector

G: ## What decides the chunk size
The Databricks RAG pipeline guide says the best chunk size and method depend on the use case and the nature of the data, that the process is iterative, and that there is no one-size-fits-all approach. It lists the factors:
- Chunk size trade-off: smaller chunks focus on details but lose context; larger chunks carry more context but can include irrelevant information or cost more.
- Embedding model: chunks that exceed its maximum token limit are truncated, potentially losing important information.
- Semantic coherence: chunks should be independent, meaningful units, which follows from the structure of the data and from the question types you expect.

C=File extension alone: the format can suggest boundaries (headers, paragraphs), but no format has a fixed best size, since the guide says it depends on the use case and the data.
D=Chat model speed: the chunk size is set by retrieval needs; output speed does not depend on how the documents were split.

The trace shows retrieval results that account for most of the prompt, and the answer is usually one sentence located in a single subsection. Answers often cite the right chapter but include unrelated details from other subsections. What should change in the pipeline?

G: ## Oversized chunks are a context-distraction source
The Databricks RAG guide says segmenting large documents into smaller, semantically concentrated chunks ensures that retrieved data fits in the LLM's context while minimizing distracting or irrelevant information. When chunks are chapters, every retrieval pulls in large amounts of unrelated text; the model's attention is spread over it. G: ## Context elements for scoping and executing a task
A task has to be scoped (what is asked, what is allowed, who is asking) and executed (the data to act on and the means to act). A practical checklist, which is the exam's own convention rather than a Databricks docs definition:
- Instruction and constraints: the goal, the rules that bound it (refund policy), the output expected.
- Task data: the specific record the request names.
- Identity and permissions: who the user is, what they may do.
- Tools: only the definitions needed to act, with parameters.
The same checklist excludes what the task does not need. Everything extra consumes the attention budget; this is why the Databricks tracing pages stress inspecting inputs and token usage of each step.
W: Task instruction with policy, the specific order, the customer's identity and the refund tool: these four cover scope (what and under what rules), the data to act on and the means to act, and nothing else.

C=Everything available: the whole handbook, every tool and the lifetime orders bury the relevant policy and order under irrelevant text and tool definitions.
D=Message only: the model cannot know the order's status, the current policy or which tool exists; missing context leads to guessing.
T: Give the task its instruction and constraints, the one record it acts on, the user identity and the needed tools, no more.

@ DBX-CEA D3 T3.7 applied use-case
S: A product-FAQ chatbot answers customers from a single documentation index. Every question needs documentation to answer correctly, the application cannot tolerate an answer given without retrieval, and the team wants predictable latency with one model call per question. Which retrieval pattern fits?
A: Just-in-time agentic retrieval, where the model decides on each turn whether to call the search tool and may call it repeatedly while it works
B: Pre-inference retrieval: the application queries the index with the user's question before the model call and places the top chunks in the prompt

K: B
G: ## Two retrieval timings
Retrieval can run in two places. These terms are generally accepted context-engineering vocabulary and the exam's convention; the Databricks docs describe the mechanisms but do not define the terms.
- Pre-inference retrieval: the application retrieves relevant chunks before calling the model and places them in the prompt. Deterministic, one model call, no dependence on the model choosing to search.
- Just-in-time (JIT) agentic retrieval: the agent gets a retriever tool and decides when and what to retrieve during its run. Databricks documents this pattern: the AI Bridge `VectorSearchRetrieverTool` exposes an AI Search index as a tool, with a description that tells the agent when to search.
Choose by use case: when every request needs the same knowledge source and grounding is mandatory, pre-inference retrieval is simple and predictable.
W: Pre-inference retrieval: the index is queried on every question before the model call, so retrieval always happens, latency stays predictable, and one model call is enough.
X: A=JIT agentic retrieval: the model might skip the search, or loop, which breaks the guarantee of retrieval on each question and the one-call latency.
C=Full documentation in the prompt: that spends the attention budget on text that is mostly irrelevant to any one question and does not scale with the corpus.
D=Retrieve after answering: the first answer is produced without grounding, so ungrounded content can already reach the user, and it adds a second model call.
T: When every request needs the knowledge, retrieve before inference; let the agent decide only when need varies.
