@ DBX-CEA D1 T1.6 applied troubleshooting
S: A team enables extended thinking on `databricks-claude-sonnet-4-5` through the Anthropic Messages API, with `budget_tokens` set to 8000 and `max_tokens` also set to 8000. The request is rejected. The team wants to keep the same depth of reasoning. Which change fits?
A: Increase `max_tokens` well past 8000 while keeping `budget_tokens` as it is, so the thinking and the reply both fit
B: Remove the thinking setting entirely and expect the same reasoning depth from the standard mode
C: Lower `max_tokens` below `budget_tokens`, so the model is forced to think more briefly and still answers within the limit
D: Keep `max_tokens` and `budget_tokens` at 8000 and add "think for 8000 tokens" to the system prompt
K: A
G: ## Thinking tokens share the output allowance
For hybrid reasoning models that take a manual budget on Databricks (for example `databricks-claude-sonnet-4-5`), the page on querying reasoning models says `budget_tokens` controls how many tokens the model can use for internal thought and that `budget_tokens` must be less than `max_tokens`. The thinking budget therefore sits inside the total output allowance, and the visible answer needs room beyond it.
## What to adjust
- Keep the thinking budget at the level the task needs.
- Set `max_tokens` high enough for thinking plus the answer.
Newer Claude models reject or deprecate `budget_tokens` and use adaptive thinking with `output_config.effort` instead; the exam guide's point is that reasoning tokens are a budget you must plan for.
W: Raising `max_tokens` above the budget: the documented rule is that `budget_tokens` must be less than `max_tokens`, so a larger output allowance makes the request valid, keeps the 8000-token reasoning depth and leaves space for the final answer after the reasoning tokens.
X: B=Removing the setting: it switches the model to a different mode and the reasoning depth the team wanted is lost, so the quality gain disappears.
C=Lowering `max_tokens` below the budget: it makes the violation worse, because the output allowance shrinks while the thinking budget stays the same.
D=Prompt text with unchanged settings: `budget_tokens` still equals `max_tokens`, so the request is still rejected; the budget is a request parameter, and a sentence in the prompt does not change what the API allows.
T: The thinking budget must be smaller than the output allowance; plan max tokens for thinking plus answer.

@ DBX-CEA D1 T1.2 applied use-case
S: A team registers an external MCP server in the workspace so its agent can use it. The server exposes many tools, but this agent's job needs only three of them. Governance lets the team share access and restrict which tools are available. Which choice best reduces context pressure?
A: Use the governance setting to expose only the required subset, so the other definitions never enter the model's context
B: Disable tool calling and let the agent describe what it would have called, to be run by hand afterwards
C: Register the server separately once for every tool, so the agent loads each tool definition one at a time
D: Leave all tools available, and add a system-prompt line telling the agent which three to use and to skip the rest
K: A
G: ## MCP tools are context too
Model Context Protocol (MCP) servers expose tools. When an agent connects, the tool definitions it can see are part of its context. In Databricks, registered and Databricks-provided MCPs use Unity Catalog permissions, and the Unity Gateway documentation lists, under governing an MCP, the ability to share access, restrict tools and apply policies.
## Minimal tool sets
Restricting which of a server's tools an agent can see is a governance setting that doubles as a context-engineering one: fewer definitions are sent, and the model cannot pick a tool the job never needed. A prompt instruction does not shrink the definitions; it only adds more text.
W: Expose only the needed tools: restricting the registered server to the three tools the job needs removes the other definitions from what the agent sees, so the window holds only relevant tool context and the agent cannot call the others.
X: B=No tool calling: the agent could no longer retrieve anything, so the task fails; the goal was a smaller tool set, not no tools.
C=One registration per tool: registration is an administrative step and does not change which definitions the agent receives; it would also multiply maintenance.
D=Prompt line: all tool definitions are still sent and the added instruction costs tokens; the model can still call an unwanted tool.
T: Fewer visible tool definitions means less context pressure; restrict a registered MCP server to the tools the agent actually needs.

@ DBX-CEA D3 T3.4 applied comparison
S: An operations agent needs eight short Markdown runbooks stored in a Unity Catalog volume. Each runbook must be read in full to be safe to follow, the set changes occasionally, and nobody wants an indexing pipeline for it. Which approach fits?
A: Build a parse, chunk, embed and Delta Sync index pipeline over the runbooks, and return the top chunks for each question
B: Give it Files API tools to list and open documents directly, loading a whole file only when a task calls for it
C: Split the runbooks into one row per sentence in a Delta table and index it with hybrid search, returning the best sentences
D: Paste all eight runbooks into the system prompt so every call carries the complete, current set
K: B
G: ## Direct file reads versus indexing
Databricks documents two ways to put volume content in front of an agent: query an AI Search index built from chunks, or create tools that use the SDK Files API to list and read files directly (needing `USE CATALOG`, `USE SCHEMA` and `READ VOLUME`).
- Direct read tools suit a small set of short files that must be read whole: nothing is split, nothing is indexed, and the file is loaded only when needed.
- Indexing suits large corpora where only fragments are relevant.
- Putting everything in the system prompt spends tokens on every call whether or not it is needed, and gives the model material the task may not need (distraction).
The exam's wider theme here is fetching context when needed rather than always; the details of just-in-time retrieval belong to another section.
W: List and read tools: a small corpus that must be read whole is opened on demand through tools that list and read the volume's files, with no pipeline to maintain, and only the runbook needed enters the window.
X: A=Index pipeline: chunks would split step-by-step procedures that must be followed whole, and the pipeline is maintenance the scenario does not want.
C=Sentence index: splitting into rows and indexing them adds a pipeline and returns fragments, which defeats the need for whole runbooks.
D=System prompt: all eight runbooks would be paid on every call, including calls that need none of them.
T: For a few short documents read whole, give the agent read tools over the volume; index only when fragments are what you need.
