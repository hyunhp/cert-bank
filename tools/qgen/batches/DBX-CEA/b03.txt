@ DBX-CEA D2 T2.4 applied use-case
S: A support agent's system prompt v1 is compared in MLflow 3 with a rewritten v2 that adds worked policy examples and roughly doubles the prompt's token count. Both versions ran through `mlflow.genai.evaluate()` on the same evaluation dataset with the same scorers. Correctness is 0.81 for v1 and 0.82 for v2, the Guidelines pass rate is identical, and the traces show several LLM calls per task. Should v2 replace v1?
A: Yes, because any gain on a quality scorer is evidence that the extra instructions help, and the added input tokens are cheap next to wrong answers
B: No, because a one-point gain is within what the evidence can support while the doubled prompt is paid on every LLM call, so the extra tokens are not yet justified
C: Yes, once more judges are added, because only a larger scorer set can show whether a longer system prompt is better than a shorter one
D: No, ever, because a longer system prompt always lowers accuracy by diluting the model's attention, regardless of what the scores show
K: B
G: ## Judging a prompt change from experiment results
In MLflow 3 on Databricks, `mlflow.genai.evaluate()` runs your app over an evaluation dataset and scores each trace with scorers (LLM judges such as `Correctness` and `Guidelines`, or code-based checks). Each run is recorded in the experiment, and you compare runs side by side to see whether a new version improved quality or caused regressions. Tracing also records latency, token usage and cost for every intermediate step.
A prompt change is a trade: more instruction tokens may buy quality, but they cost tokens, latency and attention on every call. The question is whether the measured benefit is worth the measured cost.
- Same dataset and same scorers are the fair comparison, which this scenario has.
- A tiny score difference with no change on the other scorers is weak evidence of benefit (judges are model-based, so small differences can be noise; that is a generally accepted evaluation caution, not a Databricks-documented threshold).
- A system prompt is sent with each LLM call, so a doubled prompt multiplies across the several calls of an agent task.
"Attention budget" and the cost of extra context are context-engineering vocabulary used by the exam; the Databricks docs describe the mechanics (evaluation runs, scorers, token usage in traces), and the cost-benefit reading is the exam's convention.
W: Keep v1 for now: the evidence shows a negligible quality gain and an identical guideline pass rate, while the token cost doubles on each of several calls per task. The longer prompt has not earned its place; shorten v2 or target it at a measured failure first.
X: A=Any gain wins: a gain this small on one scorer is not a reliable signal, and ignoring a doubled per-call token cost treats context as free. Cost per call is part of the decision.
C=More judges: adding scorers can reveal regressions, but it does not turn a one-point gain into a justification for doubled tokens. The comparison is already valid; the benefit is just small.
D=Always worse: the claim is too absolute. A longer prompt can improve results when it addresses a real failure, so the decision must come from the measured effect, not a rule that ignores the scores.
T: Ship a longer system prompt only when the measured gain, on the same dataset and scorers, is worth the tokens it adds to every call.

@ DBX-CEA D2 T2.4 advanced tradeoff
S: An MLflow 3 evaluation of an HR agent compares v1 with a v2 system prompt that adds a 300-token section on leave-policy exceptions. On the same dataset and scorers, the leave-policy slice (a minority of questions) rises from 0.52 to 0.88 Correctness, all other slices stay flat, `RetrievalGroundedness` and `Safety` do not regress, and the overall mean rises from 0.80 to 0.84. What does the experiment support?
A: Adopt v2, because the extra tokens target exactly the failing slice, the gain is large there, and nothing else regressed, so the cost buys a measured fix
B: Reject v2, because the overall mean rose by only a few points and any prompt that adds tokens must lift every slice to be acceptable
C: Reject v2, because added instruction text is by definition context poisoning and should be removed whatever the scorers show
D: Defer v2 until production traffic is tested, because an evaluation dataset can never show whether prompt text changes behavior
K: A
G: ## Reading results by slice, not only by mean
An overall average hides where a change helps. When a prompt addition is written for one failure pattern, the right evidence is the slice of cases that pattern covers, plus a check that other scorers and slices did not move the wrong way.
- Targeted gain: Correctness on the slice the new section addresses rises sharply.
- No regression: other slices, `RetrievalGroundedness` and `Safety` are unchanged.
- Cost: the added tokens are paid on every call, so a targeted gain is judged against that standing cost.
Context poisoning in the exam's vocabulary means incorrect or hallucinated content entering the context and being reused as truth; accurate policy instructions that fix a measured failure are not poisoning. This is the exam's convention for the term, a generally accepted context-engineering definition rather than a Databricks docs page.
Once a section is proven valuable, you can still ask whether it should load only when the topic appears (that is a later design step, see progressive disclosure); the experiment alone justifies keeping it over the baseline.
W: Adopt v2: the experiment shows a large, targeted gain on the slice the new tokens were written for, flat results elsewhere and no regression on groundedness or safety, so the standing token cost buys a measured fix.
X: B=Every slice must improve: a change aimed at one failure pattern should improve that pattern and not harm others; demanding gains everywhere would reject almost every targeted fix.
C=Poisoning by definition: poisoning is about wrong or hallucinated content entering the context. Accurate policy text that raised Correctness on its target slice is evidence against that claim.
D=Evaluation cannot show it: evaluation runs on a fixed dataset with fixed scorers exist precisely to measure the effect of a prompt change; production monitoring complements them but is not a prerequisite.
T: Judge a larger prompt by its effect on the slice it targets and by the absence of regressions, then weigh that against the token cost paid on every call.

@ DBX-CEA D2 T2.4 applied troubleshooting
S: A team reports that its longer system prompt v2 "hurt quality": the MLflow experiment shows v1 at 0.84 Correctness and v2 at 0.71. Opening the runs, v1 was evaluated on the long-standing evaluation dataset, while v2 was evaluated on a newly built dataset of harder questions with an extra `Guidelines` scorer enabled. What is the right next step?
A: Accept the result and revert, because a lower score on any dataset proves the new prompt is worse than the old one
B: Average the two runs' scores, because pooling them removes the difference between datasets and scorers
C: Add more few-shot examples to v2 until its score exceeds 0.84, because the score gap is the thing to close
D: Re-run both versions on the same evaluation dataset with the same scorers, then compare, because the two runs are not comparable as recorded
K: D
G: ## What makes two evaluation runs comparable
Evaluation runs are comparable when the inputs that define the measurement are held constant: the evaluation dataset (including its expectations) and the scorers. MLflow's evaluate-and-compare workflow runs each app version through the same dataset and the same judges so that a difference in scores can be attributed to the version.
- A different dataset changes question difficulty, so a lower score may only mean harder questions.
- A different scorer set changes what is measured, so a new `Guidelines` judge can introduce failures the old judge never checked.
In the Databricks tutorial the improved version is evaluated "with the same judges as before" on the same dataset, then runs are compared. The same discipline applies to any prompt-length decision, because tokens are only justified by a valid delta.
W: Re-run both versions on the same dataset and scorers: the recorded runs differ in two things besides the prompt, so the 0.84 versus 0.71 gap cannot be attributed to the longer prompt until the measurement is held constant.
X: A=Revert on any lower score: the lower score may come from harder questions and an extra judge, not from the prompt, so reverting acts on a confounded comparison.
B=Average the runs: pooling scores from different datasets and scorers produces a number that measures neither version, so it hides the confound rather than removing it.
C=Add few-shot examples: chasing the number adds tokens and makes the prompt longer without first knowing whether it is actually worse, which is the opposite of an evidence-based decision.
T: Attribute a score change to a prompt change only when dataset and scorers are the same in both runs.

A: The longer prompt reads as more thorough to the team when they review it, and a reviewer approved its wording

A larger system prompt is justified by measured benefit on a valid comparison plus measured cost that stays acceptable. MLflow evaluation gives quality evidence (scorers attached to each trace) and tracing gives cost evidence (token usage and latency per step).
- Quality: improvement on the slice the new text targets, without regressions on the other scorers.
- Cost: token usage and latency per trace, summed across the agent's LLM calls, against the budget.
- Not evidence: opinions, a single anecdotal trace, or a longer list of scorers (scorers measure; they do not prove improvement).
"Attention budget" in the exam's vocabulary is the idea that every token competes for the model's focus; it is a context-engineering term and not defined by a Databricks docs page.
W: B=Targeted gain without regression: a substantial Correctness gain on the cases the new examples cover, with groundedness and safety unchanged, is a valid quality benefit on the same dataset and scorers.

@ DBX-CEA D2 T2.4 applied definition
S: A reviewer wants to estimate what v2's extra 400 system-prompt tokens cost per task in an agent whose MLflow 3 traces show six LLM spans per task. The system prompt is sent with every LLM call. Which estimate uses the experiment data correctly?
A: Count only the 400 added tokens once per task, because the system prompt is read by the model a single time at the start of the run
B: Compare the character length of the two prompt versions in the prompt registry, because token counts in traces are an unreliable measure of cost
C: Multiply the added prompt tokens by the number of LLM calls per task, using per-span token usage in the traces to confirm, so about 2,400 extra input tokens per task
D: Read only the root span's output tokens, because input tokens in intermediate spans are billed to the tool and not to the model
K: C
G: ## Where prompt tokens are paid
LLM APIs are stateless: every call receives the full prompt, so the system prompt is part of the input of each call in an agent loop. An agent that calls the model six times per task pays for the system prompt six times (this is a generally accepted property of LLM APIs, not a Databricks-specific rule).
MLflow Tracing records the inputs, outputs, latency, token usage and cost of every intermediate step, so you can read input tokens on each LLM span and sum them. That is how to check the arithmetic: 400 extra tokens times six calls is about 2,400 extra input tokens per task, before any caching effects.
This is why a seemingly small prompt addition deserves scrutiny in multi-step agents.
W: Multiply by LLM calls: because the system prompt is part of each call's input, the added 400 tokens recur on all six spans, and per-span token usage in the traces shows the real total instead of an assumption.
X: A=Counted once: the prompt is resent with each stateless call, so counting it once underestimates the cost by a factor equal to the number of calls.
B=Character length: characters are a rough proxy at best, and traces record actual token usage per step, which is the measurement the cost decision needs.
D=Root span only: input tokens on intermediate LLM spans are part of the task's consumption; looking at the root's output alone ignores where the added prompt is actually paid.
T: A system prompt is paid on every LLM call, so multiply its added tokens by calls per task and verify with per-span token usage.

@ DBX-CEA D3 T3.1 applied troubleshooting
S: A Genie Agent over a billing table returns the wrong amount for "total revenue". The table has columns `amt_1`, `amt_2` and `amt_3` (gross invoiced, net of discounts, and refunded) and none has a Unity Catalog comment. Genie sometimes sums `amt_1` and sometimes `amt_3`. Which change has the largest effect on accuracy?
A: Write a general text instruction that lists what every cryptic column means and tell Genie to prefer one of them for revenue
B: Enable entity matching on the three amount columns so Genie can read their stored values and infer the meaning from them

G: ## Metadata is the context Genie reads first
Genie turns a question into SQL using the Unity Catalog metadata of the tables you give it. The Databricks curation guidance says quality table and column descriptions in Unity Catalog are critical for accuracy, and recommends text instructions only when other methods do not apply.
- Cryptic names such as `amt_1` give the model nothing to choose between, so choices are guesses.
- A precise column comment (what it holds, units, what is excluded) removes the ambiguity at the source, where every consumer of the table benefits.
- Comments are metadata fields on securable objects; viewing them needs the `BROWSE` privilege.
- Entity matching works on string columns, to match user-typed values to stored values; it does not explain what a numeric column means.
W: Column comments in Unity Catalog: documenting each amount column states the meaning Genie needs to choose the right one, and the description lives with the data so every agent and user of the table benefits.

B=Entity matching: it supports string columns and matches user wording to stored values; the amount columns are numeric, and values do not say whether a figure is gross or net.
D=Schema export table: an extra table of column notes adds more objects to the agent's context and is not metadata Genie reads from the table itself; it adds noise instead of resolving the ambiguity.

@ DBX-CEA D3 T3.1 applied use-case
S: A Genie Agent over a `sales` table fails on "show me Florida orders for Q1": it generates `WHERE state ILIKE '%Florida%'` and returns no rows, because the `state` column stores two-letter codes such as `FL`. Which configuration fixes the mismatch while keeping the instruction set small?

G: ## Matching user wording to stored values
Users write conversationally ("Florida", with typos), while data stores codes. The Databricks docs describe prompt matching with two parts: format assistance (representative values for eligible columns) and entity matching (curated lists of distinct values for columns where users reference specific entries, such as states or product categories). With entity matching on `state`, Genie can see that `FL` corresponds to Florida and writes `WHERE state = 'FL'`.
- Entity matching supports string columns only and requires format assistance to be on.
- Genie prevents enabling it on tables with row filters or column masks; for views over such tables or dynamic views, authors must turn it off.
- Refresh the stored values when new values appear.

@ DBX-CEA D3 T3.2 advanced use-case

@ DBX-CEA D3 T3.2 applied use-case
S: Users of a regional sales Genie Agent repeatedly ask "What were sales in <region> for <quarter>?". Each answer should be a verified answer, not freshly generated SQL, and new regions and quarters appear every month. Which setup meets this?
A: One static example SQL query per region and quarter combination, each titled with its exact question
B: A parameterized example SQL query titled with the typical question, with typed region and quarter parameters whose comments describe the allowed values
C: A general text instruction containing the SQL once, with a note to substitute the region and quarter on each question
D: A knowledge-store join relationship between the sales and region tables so Genie derives the answer on its own

G: ## Parameterized example queries
Example SQL queries teach Genie how to answer common questions. Queries can be static or parameterized: a parameter inserts a value from the user's question at run time. In chat mode, when the exact text of a parameterized query is used to generate a response, Genie provides a verified answer.
- Title the example with the most typical phrasing of the question; this improves matching.
