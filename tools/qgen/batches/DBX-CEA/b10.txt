@ DBX-CEA D1 T1.1 advanced use-case
S: An insurance claims agent on Databricks holds sessions of about 120 turns. After turn 90, requests fail because the input exceeds the model's 128,000-token window. The MLflow trace shows that 70 percent of the input is raw output from policy-lookup tool calls in earlier turns, which the agent has already acted on. Governance allows only the current model, and the 8-second latency budget leaves no room for an extra model call on every turn. Which technique fixes the failure with the LEAST added latency?
A: Clear the raw output of tool calls older than the last few turns, leaving a stub that names the tool and its arguments for a repeat call
B: Summarize the whole conversation with a separate model call before every turn, so that the history sent to the agent stays far below the window size
C: Move the agent to a model with a one-million-token window, so that the full history of every session fits without changing how tool output is handled
D: Shorten the system prompt and its list of rules to free space for history, since instructions are sent again with every request in the session
K: A
G: ## Tool result clearing
The exam guide lists tool result clearing among the context management techniques. A tool's raw output matters on the turn the agent reads it; once the agent has acted on it, the output mostly occupies the attention budget. Clearing replaces that old output with a short stub such as `[cleared: lookup_policy(policy_id=P-2231)]`.
- It is a deterministic edit of the message list, so it adds no model call and almost no latency.
- The stub keeps the record that the call happened and how to repeat it, so the agent can call the tool again if it needs the data.
- Compaction (a model-written summary) also shrinks history, but each run is a model call.
## Reading the numbers
An MLflow trace records the inputs, outputs and token usage of every step (tracing overview). If 70 percent of a 128,000-token input is stale tool output, clearing frees roughly 90,000 tokens without touching user messages or the system prompt. Clearing, compaction and stubs are the exam's vocabulary; the Databricks docs do not define them.
W: Tool result clearing: the stale tool output is the 70 percent that overflows the window, and removing it is a cheap edit of the history with no extra model call, which fits the 8-second budget.
X: B=Summarize every turn: compaction would shrink the history, but running it before every turn adds a model call each time, which the latency budget rules out.
C=One-million-token model: governance allows only the current model, and a larger window would also keep the stale output in place to distract the agent.
D=Shorter system prompt: the system prompt is not the 70 percent consumer, so trimming it delays the overflow by a few turns at most.
T: When stale tool output fills the window and latency is tight, clear old tool results to stubs instead of adding a summarization call.

@ DBX-CEA D1 T1.2 advanced use-case
S: A finance team is designing a reconciliation agent before its first release. Forty Unity Catalog functions exist in the team schema, but the reconciliation job uses six of them, and two of those six return entire ledgers of up to 50,000 rows. The per-request token budget is 20,000 tokens, and the team wants to prevent context pressure from the start instead of reacting to failures in production. Which TWO design choices are proactive strategies for this agent? (Select TWO)
A: Give the agent only the six functions the reconciliation job needs instead of all forty in the schema, keeping tool definitions small
B: Change the two ledger functions to return the matched totals and the unmatched rows, with a row limit, instead of the entire ledgers
C: Give the agent all forty functions and add a system prompt rule telling the model to ignore the functions that do not concern reconciliation
D: Load both full ledgers into the system prompt at session start, so that the agent never needs a tool call and avoids repeated round trips
E: Plan to turn on compaction once production traces show the window filling, because summarizing history later costs less than redesigning tools
K: A,B
G: ## Proactive strategies
The exam guide names three proactive strategies that reduce context pressure before it appears: minimal tool sets, just-in-time retrieval and tool result scoping. They are design-time choices, unlike reactive fixes (compaction, clearing) that run once the window is already full.
- Minimal tool set: every tool definition is sent with every model call, so 40 definitions cost tokens and invite wrong choices even when 34 are never used.
- Tool result scoping: a tool returns what the task needs (totals, exceptions, a row limit), not everything it can read. A 50,000-row ledger cannot fit a 20,000-token budget at all.
## Databricks detail
Unity Catalog functions are a documented way to give agents predefined logic whose parameters the agent supplies (create-custom-tool page). Which functions an agent receives, and what they return, is the team's choice. The strategy names are the exam's vocabulary.
W: A=Minimal tool set: the agent receives only the six functions it uses, so tool definitions take a small, fixed share of the 20,000-token budget.
B=Scoped tool results: totals and unmatched rows answer the reconciliation question and keep each result far below the budget.
X: C=All forty plus an ignore rule: every definition still enters the context on every call, and a rule to ignore text does not make that text free.
D=Ledgers in the prompt: two 50,000-row ledgers alone exceed the 20,000-token budget on every request, which is the opposite of prevention.
E=Compaction later: compaction is a reactive technique applied once the window fills, so it does not meet the goal of preventing pressure at design time.
T: Prevent context pressure at design time with a minimal tool set and tool results scoped to what the task needs.

@ DBX-CEA D1 T1.3 advanced troubleshooting
S: An inventory agent's MLflow trace for one request shows: step 4, `get_stock('SKU-77')` returns 120 units; step 9, a reservation tool confirms an order of 40 units; step 11, `get_stock('SKU-77')` returns 80 units. The final answer says 120 units are available, and the reasoning at step 12 notes "two different stock figures, using the first". Every tool returned correct data at the time of its call. Which diagnosis and fix fit the evidence while adding the fewest tokens?
A: Context clash: an outdated tool result sits next to its newer replacement, so clear or mark superseded results when a call returns fresh data
B: Context poisoning: a hallucinated stock figure entered the context and was reused, so add a judge that checks every answer against the stock table
C: Context confusion: too many tools led the agent to call the wrong one, so remove the reservation tool and keep only the stock lookup tool
D: Context distraction: the long history crowds out what the model knows, so compact the whole history into a summary each time it passes ten steps
K: A
G: ## The four failure modes
The exam guide asks you to diagnose four context failure modes from a trace:
- Poisoning: a wrong statement (often a hallucination) enters the context and is reused.
- Distraction: a very long context pulls the model toward repeating its history instead of reasoning.
- Confusion: superfluous content, such as too many tools, leads to a wrong choice.
- Clash: two pieces of information in the context disagree, and the model picks the wrong one.
## Reading this trace
Both stock figures were true when returned, so nothing was hallucinated (not poisoning). The reasoning explicitly says it saw two figures and used the first: that is a clash between a stale result and its replacement. The cheapest fix removes or labels the superseded result, for example replacing step 4's output with `[superseded by step 11]`, which costs a few tokens. The mode names are the exam's vocabulary; MLflow tracing supplies the step-by-step evidence.
W: Context clash: the step-4 and step-11 results disagree and the model chose the stale one; clearing or marking superseded results removes the conflict at almost no token cost.
X: B=Poisoning with a judge: no figure was hallucinated, and a judge on every answer adds a model call without removing the stale result that caused the error.
C=Confusion, remove a tool: the agent called the right tools in the right order, and removing the reservation tool would break the ordering workflow.
D=Distraction, compact every ten steps: the trace is short and the model reasoned about the figures; a summary might even keep the stale 120 figure.
T: Two true results from different moments that disagree are a context clash; clear or mark the superseded one.
V: MLflow

@ DBX-CEA D1 T1.4 advanced use-case
S: A retail team must compare two versions of its shopping agent on 300 questions taken from last month's production traffic before releasing version 2. Security requires that the evaluation evidence be governed with schema- and table-level access control and be queryable in SQL by auditors. Both versions must be scored with the same criteria so that the results are comparable. Which part of the Databricks stack should carry this work?
A: MLflow 3, evaluating both versions with the same scorers on a dataset built from production traces, with traces stored in Unity Catalog tables
B: Lakebase, writing each version's answers into Postgres tables and letting auditors compare the two answer sets with SQL joins on question text
C: Unity Catalog volumes, saving each version's answers as JSON files and granting auditors READ VOLUME so that they can open and compare the files
D: A custom MCP server that exposes both agent versions as tools, so that a third agent calls each version and reports which answer it prefers
K: A
G: ## Matching the need to the stack
The exam guide expects you to pick among Unity Catalog, Lakebase, MCP and MLflow 3 for a scenario. Here the need is an evaluation: the same questions, the same scoring criteria, two versions, and governed evidence.
- MLflow 3 evaluation runs an app over a dataset and applies scorers such as the built-in judges (`Correctness`, `RetrievalGroundedness`, `Guidelines`), so two versions scored by the same scorers are directly comparable.
- MLflow tracing on Databricks can store traces as Unity Catalog Delta tables with schema- and table-level access control and direct SQL access (tracing overview).
- Lakebase is an operational Postgres database for application state; volumes hold files; MCP connects agents to tools. None of them scores answers.
W: MLflow 3: evaluation applies the same scorers to both versions on a dataset from production traces, and Unity Catalog storage of traces gives auditors governed SQL access.
X: B=Lakebase tables: Postgres can hold the answers, but nothing scores them, so auditors would compare raw text rather than consistent quality measures.
C=Volumes with JSON: files can be governed, but there are no scorers and no SQL comparison, so the results are neither comparable nor easy to audit.
D=MCP and a judging agent: an ad hoc preference agent is not a repeatable scorer, and MCP is a tool protocol, not an evaluation or evidence store.
T: Evaluation with consistent scorers and governed, SQL-queryable evidence is MLflow 3 with traces in Unity Catalog.

@ DBX-CEA D1 T1.5 advanced use-case
S: A product-support agent's system prompt is 11,500 tokens: 2,000 tokens of rules and a 9,500-token product catalog appended "for reference". Traces show that the catalog is needed in about 3 percent of requests, and that in other requests the agent drifts into recommending catalog products nobody asked about. The 3 percent of requests that need the catalog require exact SKU and price values. Which change best improves focus without losing those answers?
A: Move the catalog behind a lookup tool that returns entries for the products named in a request, and keep only the rules in the prompt
B: Replace the catalog with a 2,000-token summary of product families, which keeps the general picture in the prompt at a fifth of the size
C: Move the catalog to the end of the system prompt, so that the rules come first and receive more of the model's attention on every request
D: Keep the catalog in the prompt and add a rule telling the agent to mention products only when the user asks for a recommendation by name
K: A
G: ## Attention budget
The exam guide treats the context window as an attention budget: every token competes for the model's focus. Content that is large and rarely relevant has a poor cost-to-value ratio and can actively distract.
- Here 9,500 of 11,500 prompt tokens (83 percent) serve 3 percent of requests.
- The off-topic recommendations show the catalog is not just costly but distracting.
## The change that keeps exactness
Just-in-time access moves the catalog out of the prompt and behind a tool: the agent fetches the few rows it needs when a request names products. The 3 percent still receive exact SKUs and prices, and the other 97 percent never see the catalog. A summary would remove the exact values; reordering or a rule leaves every catalog token in the window. The attention-budget framing is the exam's vocabulary.
W: Lookup tool: the catalog leaves the always-on prompt, removing the distraction, while the few requests that need it still get exact SKU and price rows on demand.
X: B=Summary of families: it shrinks the prompt but drops exact SKUs and prices, so the 3 percent of requests would get wrong or vague answers.
C=Catalog at the end: every catalog token is still read on every request, so the cost and the drift toward product talk remain.
D=Rule to mention products only on request: the catalog still occupies 83 percent of the prompt, and instructions do not stop large content from pulling attention.
T: Move large, rarely needed reference content behind a just-in-time lookup instead of keeping it in the system prompt.

@ DBX-CEA D1 T1.6 advanced tradeoff
S: A voice assistant for a utility company must start speaking within 2 seconds on routine turns. About 90 percent of turns are simple lookups such as balance or outage status; 10 percent are multi-step billing disputes, where standard mode gives wrong answers and callers are told to hold while the agent works. A rules engine already labels every request with an intent, and the model accepts a per-request reasoning effort setting. Which configuration best balances accuracy, latency and token cost?
A: Send lookup intents with the lowest reasoning effort and billing disputes with a high effort, using the label the rules engine sets
B: Send every request with a high reasoning effort, since disputes need it and a single setting is simpler to operate than per-intent settings
C: Send every request with the lowest reasoning effort and add billing examples to the prompt, so disputes improve without extra reasoning tokens
D: Send every request with a medium reasoning effort as a compromise, accepting slower lookups and only partly improved answers on disputes
K: A
G: ## Reasoning modes and their cost
Reasoning models on Databricks expose controls such as `reasoning_effort` or a thinking setting. The query-reason-models page notes that higher reasoning effort can improve accuracy on complex tasks at the cost of increased latency and token usage. The exam guide calls the choice standard, extended or reduced thinking.
- Simple lookups gain nothing from extra reasoning; they pay its latency.
- Multi-step disputes are where more reasoning pays off, and here the caller is already holding, so latency matters less.
## Routing by intent
Because every request already carries an intent label, the effort can be chosen per request at no extra cost: low for the 90 percent, high for the 10 percent. Average latency stays near the low-effort level, and token spend rises only on the requests that benefit. Accepted effort values vary by model; the decision logic, not a specific value, is what the exam tests.
W: Effort per intent: lookups stay fast and cheap, disputes get the extra reasoning that fixes them, and the existing label makes routing free.
X: B=High effort for all: 90 percent of turns would pay latency and tokens they do not need, threatening the 2-second target.
C=Lowest effort plus examples: examples cannot replace the multi-step reasoning that disputes need, so dispute accuracy stays low.
D=Medium for all: lookups get slower than necessary and disputes still get less reasoning than they need, so neither constraint is served well.
T: Choose reasoning effort per request from the task's complexity, keeping simple turns fast and spending reasoning only where it pays off.

@ DBX-CEA D1 T1.7 advanced use-case
S: An HR assistant keeps the full conversation in context. An MLflow evaluation of long sessions shows that adherence to a rule the user set in turn 2 ("only show figures for my department") drops sharply once the history passes about 60,000 tokens, although the window holds 200,000. Compliance requires the full transcript to be kept for audit. Which intervention restores adherence while meeting the audit requirement?
A: Keep the full transcript in the session store for audit, and send the model a compacted history restating the user's constraints verbatim
B: Keep sending the full transcript because the audit rule requires the model to see every message, and move to a model with twice the window
C: Drop every message older than the last 20 turns from both the model input and the session store, so the history stays below 60,000 tokens
D: Append the complete conversation so far to the end of each new user message, so that earlier rules appear near the end of the input again
K: A
G: ## Where long context degrades
A model can accept far more tokens than it uses well. The evaluation shows the knee: past about 60,000 tokens, an early instruction is followed less reliably, even though the 200,000-token window is far from full. The fix is to keep the input below the knee while keeping what matters.
## Storage is not context
Databricks agent sessions store the conversation history of an interaction (messages, tool calls and results), backed by Lakebase (agent memory and sessions page). Keeping the transcript for audit is a storage requirement; what the model reads on each turn is a separate decision. Compacting the context while the session store keeps every message satisfies both. W: Session store plus compacted context: auditors keep the complete transcript, and the model sees a short history in which the department rule is stated exactly, so adherence returns.
X: B=Full transcript and a bigger window: the audit rule concerns stored records, not the model input, and a bigger window does not move the 60,000-token degradation point.
C=Drop old messages everywhere: deleting from the session store breaks the audit requirement, and trimming the context would also drop the turn-2 rule.
D=Append the whole conversation again: this doubles the input on every turn and pushes it further past the point where adherence drops.
T: Keep complete transcripts in storage for audit, but give the model a compacted history with key constraints restated.

@ DBX-CEA D2 T2.2 advanced tradeoff

Five exist only to show the exact JSON layout; two show how to handle invoices with credit notes, which the agent used to get wrong. The team must cut the prompt by at least 1,200 tokens without losing accuracy on credit notes, and the serving endpoint supports structured outputs. Which change fits every constraint?

X: B=Drop the credit-note examples: it saves only about 600 tokens and removes the examples that carry the hard-won accuracy.

G: ## Three long-horizon strategies
The exam guide pairs long tasks with three strategies and asks you to spot a mismatch:
- Compaction: one agent keeps going by summarizing its history; suits continuous, conversational, tightly coupled work.
- Structured note-taking: the agent keeps durable notes outside the window; suits long tasks with clear milestones.
- Multi-agent: sub-agents work in parallel on independent parts; suits breadth, not tightly coupled back-and-forth.
## The mismatch
Interactive refinement in short, dependent turns is the opposite of independent parallel work. Each dispatch loses the conversation, so corrections vanish. A single agent with compaction keeps the corrections in one context. The strategy names are the exam's vocabulary.
W: Single agent with compaction: every turn builds on the same conversation, so "keep the old key" and other corrections stay in force, and compaction keeps the context manageable.
X: B=Reviewer sub-agent: it checks only the latest message, so earlier corrections are still lost, and it adds a fourth handoff.
C=Larger windows with the full conversation: it repeats the whole conversation into three agents on every turn, multiplying cost for coupled work that does not benefit from splitting.
D=Nightly batch: users need answers within the conversation, and a batch rebuild removes the interaction altogether.
T: Use a single agent with compaction for interactive, tightly coupled work; reserve multi-agent designs for independent parallel parts.
