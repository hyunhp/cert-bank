@ DBX-DAA D1 T1.1 applied definition
S: An analyst new to Databricks asks where the web application, notebook service and SQL editor backend run, compared with the place where a serverless SQL warehouse processes the data. Which description is correct?
A: The web application runs in the control plane, and serverless compute runs in a serverless plane in the Databricks account
B: The web application runs in the customer's cloud account, and serverless compute runs in the classic compute plane inside the customer's virtual network
C: Both the web application and serverless compute run in the customer's cloud account, and Databricks only supplies the query engine software
D: Both the web application and serverless compute run in the control plane, so they cannot read customer cloud storage
K: A
G: ## Control plane and compute plane
A workspace is split in two.
- The **control plane** holds the backend services Databricks manages in its own account: the web application, notebooks, the SQL editor, job scheduling and workspace metadata.
- The **compute plane** is where data is processed. With **classic** compute (classic and pro SQL warehouses, clusters) it sits in the customer's cloud account and virtual network. With **serverless** compute it runs in a serverless compute plane in the Databricks account, in the same region as the workspace.
## Why an analyst cares
Serverless warehouses start fast because Databricks owns the infrastructure, yet they still read data in your cloud storage under Unity Catalog permissions.
W: Control plane plus serverless plane: the web application is a Databricks-managed service, and serverless compute is created in a serverless compute plane in the Databricks account, isolated per workspace.
X: B=Reversed planes: the web application is never deployed into the customer's account, and the classic compute plane, not serverless, is the part that lives in the customer's virtual network.
C=Everything in the customer account: Databricks hosts the web application and workspace services itself, and serverless resources belong to the Databricks account, so this misplaces both.
D=Everything in the control plane: processing happens in a compute plane, and serverless warehouses can read customer cloud storage (governed by Unity Catalog), so the stated consequence is false.
T: Control plane = Databricks-managed services; compute plane = where data is processed (customer account for classic, Databricks account for serverless).
V: Databricks workspace architecture

@ DBX-DAA D1 T1.1 applied use-case
S: A retail company keeps sales history as files in cloud object storage. Analysts need reliable SQL queries with ACID transactions, while data scientists read the same data for ML. Which platform capability provides the transactional table layer on top of the files?
A: Delta Lake, the open table format that adds a transaction log to Parquet files and gives consistent versions
B: Photon, the vectorized query engine that stores each table in a proprietary format for transactional updates
C: Auto Loader, the file source that guarantees ACID behavior for every query that later reads the files it ingested
D: Catalog Explorer, the browser that maintains a lock file next to each dataset so analysts never read half-written files
K: A
G: ## The lakehouse needs a table layer
A data lake holds cheap files but gives no transactions: a reader can see half-written output. A data lakehouse adds a table format on top of open files.
- **Delta Lake** is the default table format on Databricks. It stores data as Parquet files plus a **transaction log** (`_delta_log`). A write is visible only when its commit lands in the log, so readers get consistent snapshots and writers do not corrupt each other.
- The same tables serve SQL analysts, BI and ML users, which removes copies between a warehouse and a lake.
Photon, Auto Loader and Catalog Explorer are different layers: execution, ingestion and discovery.
W: Delta Lake: the transaction log over Parquet files provides ACID commits and snapshot reads, so analysts and data scientists share one reliable copy.
X: B=Photon: Photon is a query execution engine that speeds up processing; it does not define the table format or add transactions, and tables stay in open formats.
C=Auto Loader: it incrementally ingests new files and tracks which are processed, but ACID guarantees on reads come from the table format, not the ingestion tool.
D=Catalog Explorer: it is a UI for discovering and managing assets and writes no lock files; consistency is handled by the Delta transaction log.
T: Delta Lake = Parquet files + transaction log, giving ACID tables in the lakehouse.
V: Delta Lake

@ DBX-DAA D1 T1.1 applied comparison
S: A team lead asks which Databricks component an analyst uses to run SQL queries and build dashboards against lakehouse data without managing clusters, as opposed to the component data engineers use to build ingestion and transformation pipelines. Which pairing is correct?
A: Analysts use Databricks SQL with SQL warehouses; data engineers use Lakeflow for ingestion, pipelines and jobs
B: Analysts use Lakeflow Jobs to run ad hoc queries; data engineers use Databricks SQL to schedule and orchestrate their pipelines
C: Analysts use Mosaic AI to run SQL queries; data engineers use Unity Catalog to transform and load the data into tables
D: Analysts use Lakebase to build dashboards; data engineers use Delta Sharing to run scheduled transformations in notebooks
K: A
G: ## Who uses what
- **Databricks SQL** is the data warehousing experience: SQL editor, SQL warehouses (the compute that executes queries), AI/BI dashboards, alerts and Genie. Analysts work here.
- **Lakeflow** is the data engineering solution: **Lakeflow Connect** (ingestion connectors), **Lakeflow Declarative Pipelines** (transformations) and **Lakeflow Jobs** (orchestration).
- **Unity Catalog** governs data and AI assets for everyone; **Mosaic AI** covers building and serving AI models and agents; **Lakebase** is a managed Postgres database for applications.
Older docs call Lakeflow Jobs "Workflows" and Declarative Pipelines "Delta Live Tables".
W: Databricks SQL plus Lakeflow: analysts query through SQL warehouses and dashboards, while engineers build ingestion, pipelines and orchestration with Lakeflow.
X: B=Swapped roles: Lakeflow Jobs orchestrates tasks and is not the analyst's ad hoc query tool, and Databricks SQL is not the pipeline orchestrator.
C=Mosaic AI and Unity Catalog: Mosaic AI is about building and serving AI, and Unity Catalog is a governance layer; neither is the SQL query interface or the loading tool.
D=Lakebase and Delta Sharing: Lakebase is a transactional Postgres database for apps, and Delta Sharing (OpenSharing) shares data across organizations rather than running transformations.
T: Analysts = Databricks SQL + SQL warehouses; engineers = Lakeflow; governance = Unity Catalog.
V: Databricks SQL, Lakeflow

@ DBX-DAA D1 T1.1 applied use-case
S: A product team needs a low-latency transactional backend for an internal app that records order status updates, and it wants the lakehouse tables in Unity Catalog available to the same app with Postgres queries. Which Databricks component fits?
A: Lakebase, the managed Postgres database that can sync Unity Catalog tables for low-latency app reads
B: A serverless SQL warehouse, because it is optimized for many small single-row transactions issued by application users
C: A Lakeflow Declarative Pipeline, because it hosts the Postgres endpoints applications connect to
D: A Databricks Marketplace listing, because installing it turns a Delta table into a row-store with millisecond updates

G: ## OLTP versus analytics
Analytical engines scan many rows to aggregate; transactional apps update single rows quickly. Databricks covers the second need with **Lakebase**, a fully managed Postgres database integrated with the platform (autoscaling, scale to zero, branching, Unity Catalog integration). Applications connect with `psql` or any Postgres driver, and Unity Catalog tables can be synced into Lakebase so apps read lakehouse data at low latency.
A SQL warehouse is built for analytical queries, pipelines transform data, and Marketplace distributes data products.
W: Lakebase: it is a managed Postgres database for transactional applications and can serve lakehouse data to them through synced tables.
X: B=SQL warehouse: it runs analytical SQL over large data and is not an OLTP row-store for application transactions.
C=Lakeflow Declarative Pipeline: a pipeline defines and refreshes datasets; it exposes no Postgres endpoints for applications.
D=Marketplace listing: Marketplace is where providers publish datasets, models and notebooks, and it does not change a table's storage layout.
T: Lakebase = managed Postgres for transactional apps next to the lakehouse; SQL warehouses = analytics.
V: Lakebase

@ DBX-DAA D1 T1.1 applied use-case
S: A company runs a workspace for finance analysts and a second workspace for marketing analysts in the same cloud region, both attached to the same Unity Catalog metastore. A marketing analyst who was granted SELECT on `finance.reports.q3_summary` opens the marketing workspace. What does the analyst see?
A: The same table, because the metastore holds the metadata and permissions that every attached workspace shares
B: Nothing, because each workspace keeps its own catalogs and the table must be copied into the marketing workspace
C: The table only after a workspace admin recreates the grant separately inside the marketing workspace
D: A read-only snapshot taken when the analyst was granted access, which is not refreshed afterwards
K: A
G: ## One metastore, many workspaces
The Unity Catalog **metastore** is the top-level container for metadata and permissions. A region has one metastore that all workspaces in that region can share, so catalogs, schemas, tables and grants are defined once instead of per workspace.
- Objects are addressed as `catalog.schema.object` in every attached workspace.
- A privilege granted on an object applies wherever the user connects from, unless the catalog is bound to specific workspaces (workspace-catalog binding).
- Compute still runs per workspace, but the data view and the governance are the same.
W: Shared metastore: the table and the analyst's SELECT grant live in the metastore, so the marketing workspace shows the same table without copying data.
X: B=Per-workspace catalogs: catalogs belong to the metastore, not to one workspace, so no copy is needed.
C=Recreated grant: privileges are stored in the metastore and apply in every attached workspace; nothing is granted again per workspace.
D=Snapshot: the analyst queries the live table, and Unity Catalog does not create a copy at grant time.
T: One metastore per region is shared by its workspaces, so tables and grants are defined once.
V: Unity Catalog

@ DBX-DAA D1 T1.2 applied use-case
S: An analyst sees the table reference `sales.emea.orders` in a query. Which reading of the three-level name is correct?
A: Catalog `sales`, schema `emea`, table `orders`
B: Workspace `sales`, catalog `emea`, table `orders`
C: Metastore `sales`, schema `emea`, view `orders`
D: Schema `sales`, table `emea`, column `orders`
K: A
G: ## The Unity Catalog hierarchy
Objects are addressed as `catalog.schema.object`. The metastore sits above; catalogs hold schemas, and schemas hold tables, views, volumes, functions and models.
- Catalog: top-level container, often per business unit or environment.
- Schema (database): groups related objects.
- Object: table, view, volume and so on.
`SELECT * FROM sales.emea.orders` therefore reads table `orders` in schema `emea` of catalog `sales`.
W: Catalog, schema, table: the three parts of the name always map in that order, so `sales` is the catalog, `emea` the schema and `orders` the table inside it.
X: B=Workspace first: a workspace is not part of the name, and the middle part is the schema, not a catalog.
C=Metastore first: the metastore is the container above catalogs and is not written in names; `orders` is a table here.
D=Schema first: the first part is always the catalog, and a column is never part of the object name.
T: `catalog.schema.object` is the Unity Catalog three-level namespace.
V: Unity Catalog, Catalog Explorer

@ DBX-DAA D1 T1.2 applied use-case
S: Data scientists drop PDF contracts, images and CSV extracts into a shared location. Analysts need these files governed by the same Unity Catalog permissions as tables, addressed with a catalog.schema name, although the files are not rows and columns. Which object fits?

@ DBX-DAA D1 T1.2 applied use-case
S: An analyst gets a table with salary, home address and several business columns. Sales managers need only the business columns, and the team wants them to query a governed object without being granted SELECT on the table itself. What fits?

@ DBX-DAA D1 T1.2 applied use-case
S: Three dashboards each define "revenue per distinct customer" slightly differently, and the figures do not match. The team wants one governed definition that every dashboard, notebook and Genie agent reuses while allowing grouping by any field. What should they create?
A: A Unity Catalog metric view that defines the measure once and lets users group by any dimension

Standard views lock in aggregations and groupings at creation. It is defined in YAML or SQL DDL on a source table, view or query, governed by Unity Catalog and queried with SQL from the SQL editor, notebooks, dashboards, Genie and alerts. The engine generates the correct computation for whichever grouping is requested, so ratios stay correct at any level.

C=Pasted temporary views: copies drift apart over time, which is the original problem, and temp views are not governed objects.
D=External table column: a stored value for one grouping becomes wrong when users change the grouping, and it must be rebuilt as data changes.
T: Metric views centralize business measures and keep them correct for any grouping.

@ DBX-DAA D1 T1.2 applied troubleshooting
S: A table was created in a notebook as `CREATE TEMPORARY VIEW recent_orders AS SELECT ...`. A colleague cannot find `recent_orders` in Catalog Explorer and gets "table or view not found" in her own notebook. Why?
A: A temporary view is scoped to the session or query that created it and is not registered in any schema or catalog
B: Temporary views are registered in the metastore but are visible only after the workspace admin certifies them
C: The view was dropped automatically because Unity Catalog allows views only inside the default catalog
D: Views cannot be shared between users, so every analyst must recreate the view in a separate workspace
K: A
G: ## Scope of views
A **view** created with `CREATE VIEW` is registered in a schema (`catalog.schema.view`) and can be queried from anywhere you have permission. A **temporary view** is not registered in any schema or catalog:
- in notebooks and jobs it is scoped to the notebook and disappears when the notebook detaches from compute;
- in Databricks SQL it is scoped to the query and cannot be referenced from other queries, even in the same dashboard.
To share logic, create a persistent view or a materialized view in a schema and grant access.
W: Session scope: the temporary view exists only for the notebook or query that defined it, so Catalog Explorer and other users never see it.
X: B=Certification: certification is a tag for trust signals and does not control the visibility of views.
C=Default catalog only: views can be created in any catalog and schema where the user has privileges.
D=Cannot be shared: persistent views are designed for sharing and can be granted to other users and groups.
T: Temporary views are session-scoped and unregistered; persistent views live in a schema.
V: Views

@ DBX-DAA D1 T1.2 applied comparison
S: A table in the `finance` catalog is queried with `SELECT * FROM delta.`s3://bucket/path``, referencing storage by path. Compared with querying it by table name, what is the effect on lineage?
A: Catalog Explorer shows no column lineage, because it needs both source and target referenced by table name

Lineage is captured automatically for queries that reference objects by name. If the source or target is referenced by a path or URI, the Catalog Explorer lineage view and the lineage API do not show column lineage. This is one reason Databricks recommends defining views and queries with table or view names, not paths. Other gaps: renamed objects lose lineage, and UDFs give table-level lineage but not column-level lineage.
W: Name versus path: only name references let Unity Catalog map columns between source and target.
X: B=More detailed: a path reference removes the metadata link, so less is captured, not more.
C=Identical: a path reference bypasses the registered object, so the lineage is not identical.
D=Reset after restart: lineage is stored centrally in the metastore and is not tied to cluster lifetimes.
T: Reference tables by name to keep column lineage; paths break it.
V: Lineage
