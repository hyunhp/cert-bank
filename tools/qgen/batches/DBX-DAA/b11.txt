@ DBX-DAA D1 T1.2 expert troubleshooting
S: The metric view `sales.semantic.revenue_mv` feeds a busy executive dashboard. To speed it up, the analyst adds a `materialization` block with an aggregated materialized view by month and region and a six-hour schedule, but the change is rejected. The serverless setting is on and the SQL warehouse runs a current version. While checking the sources, she notices that `sales.gold.orders`, one of the joined tables, has had a row filter since last quarter so that country managers see only their own countries, and the dashboard is published with individual data permissions. Query profiles of the dashboard never show `METRIC_VIEW_MATERIALIZATION_MATCH`. What explains this, and what is the right next step?
A: Materialization is unavailable while a source uses a row filter, because it is computed once as the owner; keep live queries and tune the sources
B: Materialization is unavailable while the dashboard uses individual permissions, because each viewer needs a cache; publish with shared permissions
C: Materialization needs the schedule removed when a source has a row filter, because each refresh must run as the viewer; refresh it manually instead
D: Materialization needs an unaggregated materialized view when a source has a row filter, because filters apply to rows; replace the aggregated one
K: A
G: ## How metric view materialization works
A metric view can declare a `materialization` block: Databricks then builds and refreshes materialized views (aggregated by chosen fields and measures, or unaggregated) in a managed Lakeflow pipeline. At query time the optimizer rewrites queries to read a matching materialization; the query profile shows the applied acceleration `METRIC_VIEW_MATERIALIZATION_MATCH`. If none fits, queries fall back to the source tables.
## The security limit
A metric view **cannot be materialized** when the view or any of its source tables uses **row filters (row-level security), column masks or ABAC policies**. A materialization is computed once with the owner's identity; serving it to every user would bypass the per-user filtering these controls enforce at query time.
## What remains
The country managers' row filter must stay, so materialization is not an option for this metric view. Live queries on the metric view still apply the filter per user; speed comes from the source tables (clustering, predictive optimization) and the warehouse.
W: Row filter blocks materialization: the precomputed result would be built once as the owner and would leak rows across country managers, so the documented rule forbids it; the analyst keeps live, filtered queries and improves the source layout instead.
X: B=Individual permissions are the cause: the publishing mode of a dashboard is not a materialization requirement; the block comes from the row filter on a source table, and switching to shared permissions would also stop per-viewer filtering.
C=Drop the schedule: the schedule is optional, and removing it does not change the rule; materialized results are always computed as the owner, so a filtered source cannot be materialized at all.
D=Use unaggregated instead: both materialization types are precomputed with the owner's identity, so the restriction applies to unaggregated materialized views as well.
T: A metric view whose sources use row filters, column masks or ABAC cannot be materialized, because materializations are computed as the owner.
V: Unity Catalog metric views

@ DBX-DAA D2 T2.2 expert troubleshooting

Today an analyst who owns `fin.reporting.budget` tries to change its tag from `fin` to the allowed value `finance` and gets a permission error, although the same change worked last month and she can still add other free tags to the table. What explains this?
A: Existing owner_team assignments became governed when the tag was created, so changing them now needs ASSIGN, which only stewards hold
B: Existing owner_team assignments were deleted when the tag was created, so the analyst must first recreate the old value fin before changing it
C: Existing owner_team assignments stay free tags until a steward converts them, so the error comes from a missing APPLY TAG on her table

G: ## Turning an existing tag key into a governed tag
A governed tag is an account-level tag with a policy: allowed values and control over who may assign it. When a governed tag is created with the **same key as tags already in use**, all existing assignments with that key **automatically become governed**. Governance thus applies to tags already in use, without retagging.
## Permissions after the change
Assigning or changing a governed tag needs **ASSIGN** on that tag (account-wide or on that one tag) in addition to the object-level right (ownership or `APPLY TAG`). Values must come from the allowed list. Free tags with other keys are not affected.
## Reading the evidence

W: Auto-governed existing assignments: creating the governed tag put every existing owner_team assignment under its policy, so editing it now needs ASSIGN, which the stewards alone hold.
X: B=Assignments deleted: creating a governed tag governs existing assignments; it does not remove them, and the analyst is changing a tag that still exists.
C=Still free tags: existing assignments with the key become governed automatically, and her working free tags show that object-level rights are not the issue.
D=Old value must be allowed: the check applies to the value being assigned, finance, which is allowed; the failure is a permission error, not a value error.
T: Creating a governed tag over a key already in use governs all existing assignments, so changing them then requires ASSIGN on the tag.

@ DBX-DAA D2 T2.3 expert troubleshooting
S: An analyst cleans duplicate imports in `crm.raw.contacts` with a view: `SELECT * FROM crm.raw.contacts QUALIFY row_number() OVER (PARTITION BY contact_id ORDER BY imported_at DESC) = 1`. Reconciliation shows that for about 2% of contacts the kept phone number changes from one run to the next, although the source table did not change. Inspecting those contacts, she finds two rows with the same `imported_at` second from a batch loader, differing in `phone` and in `source_file`, which holds names such as `batch_0412.csv` that increase with load order. The rule is "keep the row from the latest file". Which change makes the view deterministic and correct?
A: Order the window by imported_at DESC, source_file DESC, so that ties on the timestamp are broken by the later file name every time
B: Replace row_number() with rank() under the same ORDER BY, so that tied rows on the timestamp receive the same rank and are both kept
C: Replace row_number() with dense_rank() under the same ORDER BY, so that tied rows share a rank and the next one follows without a gap
D: Order the window by imported_at DESC, phone DESC, so that ties on the timestamp are broken by the phone number in a fixed order every time
K: A
G: ## Deduplicating with QUALIFY
`QUALIFY` filters on a window function result, so `row_number() OVER (PARTITION BY key ORDER BY ...) = 1` keeps one row per key.
## Ties make results non-deterministic
When rows have equal values in **all** ORDER BY expressions, their order is not deterministic. `row_number()` must still number them 1, 2, ..., so which tied row gets 1 can change between runs. That explains phone numbers that flip without any data change.
## Choosing the tie-breaker
Add ORDER BY expressions until each partition is totally ordered, and choose them from the business rule. The rule is "latest file", and the file names increase with load order, so `source_file DESC` breaks the tie the right way. A tie-breaker on another column (such as phone) would be deterministic but would encode no business meaning.
W: Add source_file DESC: the order becomes total within each contact, and the tie is broken by the latest file as the rule demands, so every run keeps the same correct row.
X: B=rank(): tied rows both get rank 1, so the view keeps two rows per contact and the duplicates come back.
C=dense_rank(): tied rows also share rank 1, so both duplicates survive the filter, exactly as with rank().
D=Tie-break on phone: the result becomes stable, but it keeps the larger phone number rather than the row from the latest file, which breaks the stated rule.
T: Deduplicate with row_number() only over a total order; add tie-breakers that follow the business rule.
V: Databricks SQL window functions, QUALIFY

@ DBX-DAA D3 T3.1 expert tradeoff
S: Analysts query a busy SQL Server order database through a foreign catalog. Five dashboards refresh every 15 minutes and each refresh reads several million rows, and the database team reports that these federated reads now slow the order application at peak hours. The business needs order data in Databricks no more than 15 minutes old, at higher volumes next year, with joins to Delta tables. The database team has agreed to enable change tracking on the source tables and wants to stop the repeated full reads. Which approach fits BEST?
A: A Lakeflow Connect SQL Server connector that ingests the tables incrementally into Unity Catalog through change tracking on a 15-minute schedule
B: A materialized view over each foreign table refreshed every 15 minutes, so dashboards read Delta while each refresh still reads the source in full
C: Query federation kept with a larger JDBC fetchSize on each dashboard query, so every refresh pulls the same rows in fewer network round trips
D: Catalog federation to the SQL Server catalog, so queries read the database files directly from object storage using Databricks compute only
K: A
G: ## Federation or ingestion
- **Query federation** pushes queries to the external database over JDBC. It suits ad hoc reporting and proof-of-concept access with no data movement, but every query uses the source's compute.
- **Lakeflow Connect** ingests data into Unity Catalog tables. Its database connectors read only changes from the source; for SQL Server that is **change tracking** or **change data capture** (with both enabled, the connector uses change tracking), so each run moves only new and changed rows.
The docs say: when a source supports both, Databricks recommends **Lakeflow Connect if performance on higher data volumes and lower latency are priorities**.
## Applying the constraints
- Full reads hurt the source: incremental CDC replaces them with small change reads.
- 15-minute freshness: a schedule at that interval meets it.
- Joins with Delta and growth next year: ingested Delta tables join and scale on Databricks compute.
W: Lakeflow Connect with change tracking: after the initial load only changes are read from SQL Server, which removes the repeated full scans, keeps data within 15 minutes and scales with volume.
X: B=Materialized views over foreign tables: dashboards get faster, but every refresh still scans the source over JDBC, so the load on the order database stays.
C=Larger fetchSize: it changes batch size per round trip, not the number of rows read, so the source keeps serving full reads.
D=Catalog federation: it is for external catalogs whose tables live in object storage (Hive metastore, Glue, Snowflake catalog); an operational SQL Server database has no such files to read.
T: When a federated source suffers from repeated heavy reads and needs fresh data at scale, ingest it incrementally with Lakeflow Connect CDC.
V: Lakeflow Connect, Lakehouse Federation

@ DBX-DAA D4 T4.9 expert troubleshooting
S: An auditor asks for the contents of the Unity Catalog managed table `finance.gold.accruals` as of 12 days ago. `DESCRIBE HISTORY` lists versions going back about four weeks, and the analyst picks version 318 from 12 days ago, but `SELECT * FROM finance.gold.accruals VERSION AS OF 318` fails with an error saying the version is outside the retention window. Nobody has run VACUUM manually, the table properties show no custom retention settings, and the query runs on a current serverless SQL warehouse. Future audits will need 60 days. Which explanation and change are right?
A: Time travel stops at deletedFileRetentionDuration (7 days by default) on managed tables; raise it and logRetentionDuration to 60 days
B: Time travel is blocked past logRetentionDuration (30 days by default) on managed tables; raise it to 60 days and keep the file retention as it is
C: Time travel is blocked past deletedFileRetentionDuration (7 days by default) on managed tables; raise only that property to 60 days for audits
D: Time travel is blocked only after a manual VACUUM on managed tables; tell the team never to run VACUUM so that 60 days of versions stay readable
K: A
G: ## Two retention settings
- `logRetentionDuration` (default **30 days**) controls how long the table **history** is kept. It is why `DESCRIBE HISTORY` still lists four weeks.
- `deletedFileRetentionDuration` (default **7 days**) is the threshold VACUUM uses to delete data files no longer referenced by the current version.
## Time travel limits on managed tables
For Unity Catalog managed tables (Databricks Runtime 12.2 and above, which SQL warehouses run), time travel queries are **blocked** when they request a version older than `deletedFileRetentionDuration`, even if its history entry still exists. Predictive optimization can run VACUUM for you, so the files may really be gone. Databricks also requires `logRetentionDuration` to be at least `deletedFileRetentionDuration`.
## Planning for 60 days
Set both, for example `ALTER TABLE ... SET TBLPROPERTIES ('delta.deletedFileRetentionDuration' = 'interval 60 days', 'delta.logRetentionDuration' = 'interval 60 days')`. Version 318 itself cannot be brought back this way if its files were removed.
W: Raise both retentions: the 7-day file retention blocks the 12-day-old version, and for 60-day audits the file retention must grow while the 30-day log retention must grow with it, since it may not be shorter.
X: B=Log retention is the limit: history still shows four weeks, so the 30-day log setting is not what blocks a 12-day-old version; the file retention is.
C=Raise only file retention: a 60-day file retention with the 30-day default log retention is not allowed, because log retention must be at least as long.
D=Only manual VACUUM blocks it: on managed tables the block follows the retention property, and predictive optimization may vacuum without any manual run.
T: On managed tables, time travel is limited by deletedFileRetentionDuration; extend it together with logRetentionDuration for longer audits.
V: Delta Lake time travel, table properties

@ DBX-DAA D4 T4.4 expert tradeoff
S: The source table `pos.silver.transactions` is a date-partitioned Delta table, and a compliance job deletes rows older than 400 days every night. Finance wants a table of yearly revenue per store that keeps the totals for every past year forever, refreshed daily. An analyst built it as a materialized view on a serverless SQL warehouse: `CREATE MATERIALIZED VIEW fin.gold.yearly_rev SCHEDULE EVERY 1 DAY AS SELECT store_id, year(ts) AS yr, sum(amount) AS rev FROM pos.silver.transactions GROUP BY ALL`. Two months after go-live, the totals for the oldest year began shrinking, while the refresh history shows only successful incremental refreshes. Which change meets the requirement?
A: Build the yearly totals from a streaming table that reads new source rows once, so later deletions in the source leave the stored totals in place
B: Keep the materialized view and switch its refresh to FULL each night, so that the yearly totals are recomputed from every row on each run
C: Keep the materialized view and enable row tracking on the source table, so that incremental refreshes ignore rows removed by the deletion job
D: Keep the materialized view and add TRIGGER ON UPDATE to it, so that the totals are refreshed before each nightly deletion job removes any rows
K: A
G: ## Materialized views follow their source
A materialized view guarantees the **same result as its defining batch query** over the current source. Incremental refresh is an optimization: its output equals a full recompute. When the source loses old rows, the aggregates over those rows shrink accordingly.
The docs therefore say not to define a materialized view over a source **where you plan to delete or archive data after processing but need to keep its information downstream**, such as a date-partitioned table with a retention job. Use a **streaming table** instead: it processes each new row once, and later deletes in the source are not replayed into it (the stream must ignore those change commits rather than fail).
## Applying it
Daily revenue rows can be appended to a streaming table as they arrive; yearly totals are then computed from that table, which keeps every year even after the source purges old rows.
W: Streaming table as the history store: rows are captured once on arrival and stay after the compliance job deletes them at the source, so past years stay complete.
X: B=Full refresh: a full recompute over the purged source gives exactly the same shrinking totals; it only costs more.
C=Row tracking: it helps incremental refresh detect changes, and the result must still equal the batch query, so deletions are still reflected.
D=TRIGGER ON UPDATE: the next refresh after the deletion runs anyway, and the result again reflects the current, smaller source.
T: A materialized view always mirrors its current source; to keep data that the source later deletes, capture it in a streaming table.
V: Materialized views, streaming tables

@ DBX-DAA D4 T4.3 expert troubleshooting
S: A dashboard dataset reads the MySQL table `ops_fed.crm.tickets` (40 million rows, six years of history) through query federation with `SELECT ticket_id, subject, created_at FROM ops_fed.crm.tickets WHERE subject ILIKE '%refund%'`. The only chart on the page shows refund tickets from the last 30 days, trimmed by a date setting inside the chart. MySQL cannot be changed, and the dashboard must keep showing the same tickets. Which change reduces the rows fetched over the network?
A: Add AND created_at >= :start_date to the dataset query, so the pushable date predicate reaches MySQL while ILIKE runs on Databricks
B: Change the dataset to OR created_at >= :start_date, so MySQL evaluates the date predicate while Databricks evaluates the ILIKE part
C: Build a materialized view over the foreign table refreshed hourly, so the dashboard reads Delta while each refresh fetches the same rows
D: Set a larger fetchSize on the dataset query, so the warehouse reads the full table in fewer round trips and filters it locally as before
K: A
G: ## Predicate pushdown in query federation
Query federation translates filters into the remote database's SQL when it can. A predicate without a translation is evaluated on Databricks after the rows arrive; the docs use `ILIKE` on MySQL as the example. If that is the only predicate, the remote query has no WHERE clause and the whole table is fetched.

## Applying it
The chart only needs the last 30 days, so a date predicate in the dataset changes nothing the viewer sees. `created_at >= :start_date` is a simple comparison that MySQL can run, so only recent tickets travel; ILIKE then filters them on Databricks.
W: AND a pushable date predicate: MySQL returns only recent tickets, ILIKE filters those on Databricks, and the chart shows the same refund tickets as before.
X: B=OR instead of AND: the condition now means any refund ticket or any recent ticket, which changes the result, and a disjunction with a non-pushable part cannot be pushed as a whole.
C=Materialized view: dashboards get faster, but every refresh of the view still fetches the full table from MySQL, so network reads do not shrink.
D=Larger fetchSize: it only batches the same full-table read into fewer round trips; all 40 million rows are still fetched.
T: In federated queries, AND a pushable predicate next to a non-pushable one so the remote database filters first, and check the result with EXPLAIN FORMATTED.

@ DBX-DAA D5 T5.2 expert troubleshooting
S: The managed table `web.gold.clicks` (8 TB) uses liquid clustering with `CLUSTER BY (event_date)`, where `event_date` is a DATE column filled from the TIMESTAMP column `event_ts` at load time. A dashboard dataset filters `WHERE event_ts >= :start_ts AND event_ts < :end_ts` for one-day windows, and the profile shows almost no files pruned and the insight `COVERAGE_FILTER_KEYS_CLUSTERING`. Statistics are complete, and other dashboards on the table filter by `event_date` and run fast. About 200 store managers open the dashboard every morning. The analyst may change only the dataset query, not the table or its clustering keys. Which change fits?
A: Keep the timestamp range and add AND event_date BETWEEN to_date(:start_ts) AND to_date(:end_ts), so the scan filters on the clustering key
B: Keep the timestamp range and add AND to_date(event_ts) BETWEEN to_date(:start_ts) AND to_date(:end_ts), so the scan filters by day
C: Replace the timestamp range with CAST(event_ts AS DATE) = to_date(:start_ts), so the scan compares one day just like the key column

G: ## Clustering helps only filters on the clustering keys
Liquid clustering organizes files by the **clustering key columns**, so filters on those columns skip files. Here the key is `event_date`, but the dataset filters only on `event_ts`. Even though the two columns are related, the engine does not infer one from the other.

W: Add a filter on event_date: a redundant predicate on the actual clustering key lets file skipping work, and the original timestamp range keeps the exact result.
X: B=to_date(event_ts) filter: it filters a function of event_ts, not the clustering key column event_date, so the insight and the full scan remain.
C=Cast in place of the range: it is still an expression on event_ts rather than the key column, and it changes the result for windows that do not start at midnight.
D=ORDER BY event_date: sorting the output happens after the scan and does not decide which files are read.
T: For a clustered table, put a predicate on the clustering key column itself; filters on related columns do not trigger file skipping.
