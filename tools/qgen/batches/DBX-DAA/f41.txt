@ DBX-DAA D9 T9.3 applied use-case
S: An analyst builds the production table `retail.gold.kpi_daily` that feeds several dashboards and is therefore its owner. The team wants to avoid broken refreshes and unmanaged access when staff leave. What is the best practice?
A: Transfer ownership to a group that represents the team, so that people can change without changing the owner
B: Grant the analyst `ALL PRIVILEGES` and keep ownership with them so that the grants can be audited
C: Transfer ownership to the metastore admin, so that production tables are owned by a single administrator account
D: Keep the analyst as owner, because Unity Catalog reassigns ownership to a workspace admin when a user leaves
K: A
G: ## Who should own a table
The creator of an object is its first owner. Owners can grant and revoke access, transfer ownership and drop the object, and a refresh or a dashboard run under an owner's identity can break when that person leaves.
Databricks best practices:
- Assign ownership of production objects to groups, not to individuals; creators should reassign ownership.
- Be sparing with metastore admins, `MANAGE` and `ALL PRIVILEGES`.
A group owner means that team changes are group membership changes, and the owner stays valid.
W: Group ownership: the owner is a stable principal, so grants, refreshes and administration continue after any individual leaves.
X: B=ALL PRIVILEGES for the analyst: this still ties the table to one person, and `ALL PRIVILEGES` is not even the same as ownership, since it excludes `MANAGE`.
C=Metastore admin as owner: that concentrates control in one broad role, which the guidance says to assign sparingly, and it makes day-to-day administration slower.
D=Reassignment on departure: Unity Catalog does not reassign objects when a user is removed, so a person-owned table is left with an orphaned owner.
T: Give production tables to a group as owner so staff changes never orphan them.

S: Customer data in the catalog `prod_customers` must be processed only in the production workspace. A group holds `SELECT` on its tables, yet its analysts in the development workspace, attached to the same metastore, get an error when they open the catalog. Which setting explains this?
A: The development workspace uses a classic SQL warehouse, which is blocked from reading catalogs that hold customer data
B: Each workspace keeps its own copy of the metastore, so a catalog created in production is missing from the development one
C: The group lacks `BROWSE` on the catalog, a privilege that is checked when a catalog is queried from another workspace
D: The catalog is bound to selected workspaces, and an unbound workspace is denied even for principals with explicit grants
K: D
G: ## Workspace-catalog binding
By default every catalog of a metastore is reachable from every workspace attached to it. Workspace-catalog binding overrides that default: the catalog owner (or a holder of `MANAGE`) restricts a catalog to chosen workspaces, optionally read-only.
- Access from an unbound workspace fails even when the user has `USE CATALOG`, `SELECT` and other grants.
- Catalog Explorer, lineage and `information_schema` in an unbound workspace do not list the catalog.
- Bindings isolate environments (production versus development) or sensitive domains; privileges still decide who may use the catalog inside a bound workspace.
## How an analyst diagnoses it
A permission error that follows the workspace rather than the user points to a binding, not to a missing grant.
W: Workspace binding: the production-only catalog is unreachable from the development workspace, whatever privileges the group holds.
X: A=Classic warehouse: the compute type does not decide catalog access, and no warehouse type is barred from catalogs with customer data.
B=Own copy of the metastore: workspaces in a region share one metastore, so the data is not workspace-local unless a binding limits it.
C=BROWSE: it affects discovery of metadata and is not checked per workspace; it is not what blocks queries.
T: A catalog bound to selected workspaces is denied elsewhere even for users with grants.

@ DBX-DAA D2 T2.3 advanced troubleshooting
S: A query `SELECT count(*) FROM payments WHERE id NOT IN (SELECT payment_id FROM refunds)` returns 0, although many payments have no refund. The `refunds.payment_id` column contains some NULL values. Which rewrite returns the payments without refunds?
A: `... WHERE payments.id NOT IN (SELECT DISTINCT r.payment_id FROM refunds r)`
B: `... WHERE payments.id NOT IN (SELECT r.payment_id FROM refunds r) OR payments.id IS NULL`
C: `... WHERE payments.id <> ALL (SELECT r.payment_id FROM refunds AS r)`
D: `... WHERE NOT EXISTS (SELECT 1 FROM refunds r WHERE r.payment_id = payments.id)`
K: D
G: ## NOT IN and NULL
`x NOT IN (list)` is true only if `x` differs from every item. If the list contains a NULL, the comparison with that item is unknown, so the whole predicate can never be true. A single NULL in the subquery therefore returns no rows.
Safer patterns:
- `NOT EXISTS` with a correlated subquery, which ignores NULL join keys.
- Exclude NULLs in the subquery: `WHERE payment_id IS NOT NULL`.
- A `LEFT ANTI JOIN`.
W: NOT EXISTS: it checks for a matching row per payment, so NULL keys in the refunds table do not poison the result.
X: A=DISTINCT: removing duplicates leaves the NULL value in the list, so the predicate is still never true.
B=OR id IS NULL: adds only rows whose id itself is NULL and does not rescue the other rows.
C=`<> ALL`: this is the same logic as NOT IN and behaves identically with NULLs.
T: Prefer NOT EXISTS or an anti join over NOT IN when NULLs are possible.
