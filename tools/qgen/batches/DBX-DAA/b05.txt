@ DBX-DAA D5 T5.2 applied use-case
S: An analyst runs a report that joins `orders` to `order_items`. The result has far more rows than either table holds, and the query is slow. In the query's performance insights, which insight points to this problem, and what does it recommend?
A: `EXPLODING_JOIN`: the join returns far more rows than it reads, so the join condition should be fixed or the inputs reduced
B: `SELECTIVE_JOIN`: the join returns far more rows than it reads, so the join type should be switched to a cross join
C: `REDUNDANT_JOIN`: the join returns far more rows than it reads, so the warehouse should be resized to a larger cluster size
D: `DATA_SKEW`: the join returns far more rows than it reads, so the key columns should be hashed before they are compared
K: A
G: ## Query performance insights
When a query runs on a SQL warehouse, Databricks can attach performance insights to it. Each insight has a name, a short description of what was observed and a recommendation. Insights appear in the query history details panel (ranked by their estimated effect on task duration) and in the Performance insights tab of the query profile.
## Join-related insights
- `EXPLODING_JOIN`: the join produces significantly more rows than it reads, typically because the join key is not unique on both sides (many-to-many).
- `SELECTIVE_JOIN`: the opposite, the join produces far fewer rows than it reads, so filtering earlier would help.
- `REDUNDANT_JOIN`: an outer join that changes no row count and uses no column of the joined table.
W: `EXPLODING_JOIN` matches the symptom of an output much larger than the inputs. Its recommendation is to decide which result subset you need, then tighten the join condition or reduce the input rows on both sides.
X: B=SELECTIVE_JOIN: this insight describes the reverse case, a join that returns far fewer rows than it reads, and its fix is adding filters before the join. A cross join would multiply rows even more.
C=REDUNDANT_JOIN: this insight flags an outer join whose joined columns are unused, so removing it changes nothing. It says nothing about row growth, and resizing the warehouse does not change the row count.
D=DATA_SKEW: this insight is about work being unevenly spread across compute resources, fixed by salting or pre-aggregation. It does not describe an output larger than the inputs.
T: A result with many more rows than the inputs is an exploding join: fix the join condition or shrink the inputs.

@ DBX-DAA D5 T5.2 applied use-case
S: A dashboard query that used to finish in seconds now takes minutes. An analyst opens the query's details from query history and wants to see which individual steps of the execution consumed the most time, without reading the whole plan graph. Which part of the query profile helps most?
A: The Query text panel, which lists the full SQL statement along with the warehouse and the user that executed it earlier
B: The Top operators panel, which lists the longest running operators so costly steps stand out
C: The Details panel, which shows only the status and the user who started the query run
D: The query source link, which opens the dashboard dataset and shows its last edit time and author
K: B
G: ## Reading a query profile
A query profile visualizes how a query executed. The left side has tabs (Details, Top operators, Query text), and the right side shows the directed acyclic graph (DAG) of operators such as Scan, Join, Shuffle, Hash/Sort and Filter. In the graph you can switch the displayed metric between time spent, memory peak and rows.
## Finding the slow part quickly
The Top operators panel ranks the most expensive operators, which is the fastest way to find optimization opportunities. The same query details panel also offers a See longest operators for this query button that opens it.
W: Top operators puts the longest running operators in one list, so the analyst can go straight to the scan, join or shuffle that dominates the runtime.
X: A=Query text: this panel only shows the statement that was run. It is useful for reading the SQL but carries no timing information about operators.
C=Details panel: it holds query summary metrics (durations, I/O), not a ranking of operators, and it is not limited to status and user.
D=Query source link: it navigates to the object that issued the query, such as the dashboard or editor, and tells you nothing about which execution step was slow.
T: To find the costly step of a slow query, open its profile and use Top operators or the DAG time-spent metric.

@ DBX-DAA D5 T5.2 applied troubleshooting
S: An analyst opens a query in query history and selects See query profile, but the page reports that no query profile is available. The query finished successfully moments ago, and the same text was run by a colleague a minute earlier on the same unchanged tables. What is the most likely explanation, and how can the analyst still get a profile?
A: The query was served from the query cache, so it never executed; changing it trivially, such as removing the `LIMIT`, forces a real run
B: The query text is too long for the profile feature, so the analyst has to split it into several statements first
C: The profile expired because it is deleted automatically a few minutes after the query ends, so the analyst must wait for a rerun
D: The warehouse is serverless, and serverless warehouses never produce profiles, so the query must move to a pro warehouse
K: A
G: ## When a profile exists
A query profile is built from the operators that actually ran. If the result came straight from the query cache, nothing executed, so there are no operators to show and the profile is unavailable.
## How to get one anyway
The documentation suggests circumventing the cache by making a trivial change to the query, such as changing or removing the `LIMIT`. Result caches are keyed on the query and invalidated when the underlying tables change, so an identical query on unchanged tables can be answered from the cache.
For benchmarking only, `SET use_cached_result = false` disables result caching in the SQL editor.
W: An identical query on unchanged tables is a classic cache hit. No execution means no profile, and a small change to the statement makes the engine run it again so a profile is recorded.
X: B=Statement length: long statements are shown with a "more lines" link in the summary, they do not block the profile. Splitting the query would also change what is being analyzed.
C=Expiry after minutes: no such rule is documented. Profiles are tied to the query in history, and waiting does not create one for a run that never executed.
D=Serverless limitation: queries on serverless warehouses do have profiles, and the performance insights also cover them. The cause here is the cache hit, not the warehouse type.
T: A cache hit has no profile; tweak the statement (for example the LIMIT) to force a real run.

@ DBX-DAA D5 T5.2 applied definition
S: In the query details panel, a query shows a wall-clock duration of 40 seconds and an aggregated task time of 6 minutes. What does the aggregated task time represent?
A: The time the query waited in the warehouse queue before any compute resources were assigned to it
B: The time spent reading the final result back from cloud storage into the SQL editor session after the run
C: The combined execution time across all cores of all nodes, which can exceed wall-clock time
D: The time the optimizer needed to plan the query and to prune files before the execution started
K: C
G: ## Two clocks in one summary
The query details panel reports time in more than one way.
- **Wall-clock duration** is the elapsed time from the start of scheduling to the end of execution. Below it, a breakdown separates scheduling, query optimization and file pruning, and execution time.
- **Aggregated task time** adds up the time that every task spent running on every core of every node.
## Why they differ
Many tasks run at the same time, so their times add up to more than the elapsed time. A 40-second query using many cores in parallel can easily total 6 minutes of task time. It can also be shorter than wall-clock time if tasks waited for available nodes.
W: Aggregated task time is the sum of task execution across all cores and nodes, so parallel work makes it larger than the wall-clock duration. A large ratio simply means the query was well parallelized.
X: A=Queue wait: waiting for the warehouse is part of the scheduling portion of the wall-clock breakdown (and may raise an `EXCESSIVE_QUEUE_TIME` insight), not the task-time total.
B=Result fetch: fetching rows into a client is not what this metric counts. It measures task execution on the compute.
D=Planning and pruning: optimization and file pruning appear as their own part of the wall-clock breakdown before execution, separate from task time.
T: Wall-clock is elapsed time; aggregated task time sums work over all cores, so it can be much larger.

@ DBX-DAA D5 T5.2 applied use-case
S: Many analysts query a shared pro SQL warehouse at the same time. During the morning rush, an analyst's simple query shows an `EXCESSIVE_QUEUE_TIME` insight, although the query itself runs in under a second once it starts. What does the insight recommend?
A: Rewrite the query to project only the needed columns, because wide projections are what causes queuing
B: Collect Delta statistics on the table so the engine can skip files and leave the queue sooner
C: Reduce the warehouse size so that fewer large clusters compete with each other for storage
D: Increase the maximum number of clusters on the warehouse so more queries can run at once
K: D
G: ## Compute and resource insights
Some insights concern the warehouse rather than the SQL. `EXCESSIVE_QUEUE_TIME` means the query waited in the warehouse queue. `DATA_SPILL` means data did not fit in memory and spilled to disk. `IO_THROTTLING` means the cloud provider throttled storage requests.
## Size versus clusters
A warehouse size sets the power of each cluster and helps one big query. The maximum number of clusters sets how many clusters can be added for concurrent queries. Queuing under many simultaneous users is a concurrency problem, so the recommendation is more clusters, not a different query.
W: The query was fast once it ran, so the delay was waiting for a free slot. Raising the maximum number of clusters lets the warehouse scale out for the morning concurrency.
X: A=Wide projection: `WIDE_PROJECTION` is a separate insight about reading all columns and bytes read. It is not the cause of waiting in the queue, and the query already runs in under a second.
B=Delta statistics: missing statistics (`COVERAGE_STATS_DELTA`) make scans read more files. The query here is already quick once it starts, so scan work is not the issue.
C=Smaller warehouse: shrinking makes each cluster weaker and would not remove queuing. Competition is for execution slots, not for storage.
T: Queue time under concurrency is fixed with more clusters; DATA_SPILL is fixed with a larger size.

@ DBX-DAA D5 T5.2 applied troubleshooting
S: A query on a table made of thousands of tiny files is slow, and its profile shows a `DATA_FILE_SIZE` insight. The table is a Unity Catalog managed table partitioned by date. Which recommendation set matches the insight?
A: Enable predictive optimization or run `OPTIMIZE` to compact files, and consider liquid clustering for partitioned tables
B: Disable the disk cache on the warehouse, because small files only appear when cached copies are never evicted
C: Run `VACUUM` with a zero-hour retention so that all small files disappear from the table immediately
D: Convert the managed table into an external table so that the cloud store merges small files by itself
K: A
G: ## Small files and scans
Every file a scan opens has a fixed overhead. Thousands of small files make the scan slow even when the total data is small. `DATA_FILE_SIZE` is the data layout insight that reports this.
## Documented fixes
- Enable predictive optimization on the table so file sizes are optimized automatically.
- Run `OPTIMIZE` to compact small files.
- Switch partitioned tables to liquid clustering, because predictive optimization cannot compact small files across partitions.
W: The insight lists compaction through predictive optimization or `OPTIMIZE`, and for partitioned tables it points to liquid clustering since compaction does not cross partition boundaries.
X: B=Disabling the disk cache: the cache stores copies of data read from storage and does not create small files. Turning it off only slows repeated reads.
C=Zero-hour VACUUM: VACUUM deletes files that are no longer referenced, it does not merge live small files, and a zero retention would break time travel and concurrent readers.
D=External table: cloud storage never merges files by itself, and the insight actually recommends moving external tables to managed ones for automatic maintenance.
T: DATA_FILE_SIZE means too many small files: compact them with predictive optimization or OPTIMIZE, and use liquid clustering for partitioned tables.

@ DBX-DAA D5 T5.3 applied use-case
S: An auditor asks which user last changed the `finance.ledger` Delta table, when, and with what kind of operation (for example MERGE or DELETE). Which command returns this information?
A: `SELECT * FROM finance.ledger VERSION AS OF 0`, because it lists the users who edited the table in the past
B: `DESCRIBE DETAIL finance.ledger`, because it returns the audit trail with one row for each write operation
C: `SHOW TBLPROPERTIES finance.ledger`, because it keeps a log of each user who modified the table
D: `DESCRIBE HISTORY finance.ledger`, which returns the operation, user and timestamp of each write, newest first
K: D
G: ## The Delta transaction log as an audit trail
Every write to a Delta table is a commit in its transaction log. `DESCRIBE HISTORY table_name` returns one row for each commit with the version, timestamp, user, operation (WRITE, MERGE, DELETE, OPTIMIZE and so on), `operationParameters` and `operationMetrics`. Rows come back in reverse chronological order, and `LIMIT 1` gives only the last operation.
## Related commands
- `DESCRIBE DETAIL` shows the table's current state (location, file count, size, format), not who changed it.
- `VERSION AS OF` reads the data as it was, it does not tell who wrote it.
- Catalog Explorer shows the same history visually on the History tab.
W: `DESCRIBE HISTORY` returns exactly the columns the auditor needs: operation type, user and time of each commit.
X: A=VERSION AS OF: it returns rows from an older version of the data. It does not list users or operations.
B=DESCRIBE DETAIL: it reports current properties such as location, number of files and size. It has no per-write audit rows.
C=SHOW TBLPROPERTIES: it lists table property key-value pairs. It is not a log of modifications.
T: Use DESCRIBE HISTORY (or the History tab) for who, when and what on a Delta table.

@ DBX-DAA D5 T5.3 applied use-case
S: A monthly revenue figure changed between Monday's board report and Tuesday's. The analyst needs to compare the `sales_summary` Delta table as of Monday's last commit with its current state to find the rows that differ. What is the right approach?
A: Read Monday's state with `VERSION AS OF` or `TIMESTAMP AS OF` and compare it with the current table using `EXCEPT`
B: Run `RESTORE TABLE sales_summary` to Monday's version, query it, then restore forward again to the latest one
C: Clone the table with `CREATE TABLE ... DEEP CLONE` after the change so that the older rows are available for comparison
D: Ask the data engineers to rebuild the table from the source system and compare the rebuilt copy to the current table
K: A
G: ## Time travel for comparison
Delta keeps earlier table versions, so you can read the table as it was without changing it.
```
SELECT * FROM sales_summary VERSION AS OF 41
EXCEPT
SELECT * FROM sales_summary;
```
`VERSION AS OF` takes a version number from `DESCRIBE HISTORY`; `TIMESTAMP AS OF` takes a timestamp. Running the query in both directions shows rows that were removed and rows that were added.
## Why not change the table
`RESTORE` rewrites the current state of the table (and is itself a new commit), which affects every other reader and downstream job. Reading an old version is read-only.
W: Time travel reads an old version without modifying anything, and set operators such as `EXCEPT` then show exactly which rows differ between Monday and now.
X: B=RESTORE: it changes the live table twice and creates new commits that downstream streams may treat as new data. It is the wrong tool for a read-only comparison.
C=Deep clone afterwards: cloning the table now copies the already-changed state, so Monday's rows are not available unless a clone was taken before. Cloning can use a version, but that is again time travel.
D=Rebuild from source: this is slow, depends on engineers, and rebuilds current logic. It cannot reproduce what the table contained on Monday.
T: Compare two moments of a Delta table with VERSION AS OF or TIMESTAMP AS OF and a set operator; do not restore to just look.

@ DBX-DAA D5 T5.3 applied troubleshooting
S: An analyst accidentally ran `DELETE FROM customers` without a filter. The table history shows the delete as version 57, and the previous version is 56. The table was last vacuumed two days ago with the default retention. Which action restores the data, and what is required?
A: `RESTORE TABLE customers TO VERSION AS OF 56`, which needs MODIFY and the version's data files to still exist
B: `RESTORE TABLE customers TO VERSION AS OF 57`, because the delete commit holds the last consistent data
C: `VACUUM customers RETAIN 0 HOURS`, which reverses the latest operation by returning removed files to the table
D: `INSERT INTO customers SELECT * FROM customers VERSION AS OF 57`, which copies every row from the deleted version
K: A
G: ## Rolling back a Delta table
`RESTORE TABLE name TO VERSION AS OF n` (or `TO TIMESTAMP AS OF`) returns a Delta table to an earlier state. Find the version in `DESCRIBE HISTORY`. The state before a bad operation is the version immediately before it.
## Requirements and limits
- You need `MODIFY` permission on the table.
- Restore only works while the data files of the target version still exist. After `VACUUM` removes files no longer referenced (default retention 7 days), you cannot restore to a version that used them.
- `RESTORE` is a data-changing commit, so it appears in history with `dataChange` true.
W: Version 56 is the last state before the delete, and a vacuum two days ago with a 7-day default retention has not yet removed its files. Restoring to it needs MODIFY on the table.
X: B=Version 57: this version is the state after the delete, with an empty table, so restoring to it changes nothing.
C=VACUUM RETAIN 0 HOURS: VACUUM permanently deletes unreferenced files, so it would destroy the very files needed for recovery. It never brings data back.
D=Insert from version 57: version 57 is already empty, so this copies no rows. Even from version 56 it would be a workaround when `RESTORE` is the intended command.
T: RESTORE to the version before the mistake, if its files survive VACUUM and you hold MODIFY.

@ DBX-DAA D5 T5.3 applied comparison
S: A team lead says, "We can always time travel 30 days back because table history is kept for 30 days." Why is this statement unreliable with default settings?
A: History is kept 7 days by default, while time travel reaches 30 days, so the claim has the two numbers reversed
B: History (`logRetentionDuration`, 30 days) and file retention (`deletedFileRetentionDuration`, 7 days) differ, so VACUUM may remove files
C: Time travel only works on external tables, and history is kept only for managed tables in the metastore
D: Time travel needs the table to be re-optimized every day, and history vanishes if OPTIMIZE has not run recently
K: B
G: ## Two retention settings
Delta table history and time travel are controlled by different thresholds.
- `delta.logRetentionDuration` controls how long history (log entries) is kept. The default is 30 days.
- `delta.deletedFileRetentionDuration` is the threshold `VACUUM` uses to delete data files that are no longer referenced by the current version. The default is 7 days.
To query an older version you need both its log entry and its data files. So by default you can rely on about 7 days of time travel even though `DESCRIBE HISTORY` may list entries from further back. To go longer, raise both properties. The documentation also advises against using table history as a long-term backup.
W: The 30-day number only describes the log. Data files older than the VACUUM threshold (7 days by default) can be gone, so queries on the older versions fail.
X: A=Reversed numbers: it is the log that defaults to 30 days and files to 7 days, not the other way around.
C=Table type: both managed and external Delta tables have history and time travel. Table type does not decide retention.
D=Daily OPTIMIZE: OPTIMIZE compacts files and does not extend or shorten history. History is not tied to running it.
T: History defaults to 30 days, time travel files to 7 days; raise both properties for longer time travel.

@ DBX-DAA D5 T5.3 applied use-case
S: After a data fix, an analyst wants to confirm that the nightly MERGE actually touched the expected number of rows. Where does the evidence sit in the table history?
A: In the `userName` column, which lists how many rows each user has changed in total
B: In the `operationMetrics` column of the MERGE row, which reports rows inserted, updated and deleted

G: ## Verifying a result with history
Each row of `DESCRIBE HISTORY` includes `operationParameters` (for a MERGE, for example the predicate) and `operationMetrics`, a map of numbers recorded for that operation. For a MERGE these include counts of rows inserted, updated and deleted and files added or removed.
## Using it
```
SELECT version, operationMetrics.numTargetRowsUpdated
FROM (DESCRIBE HISTORY sales)
WHERE operation = 'MERGE'
ORDER BY version DESC;
```
Comparing the numbers to the expected change confirms the job did what was intended without scanning the data.
W: `operationMetrics` holds per-operation counters, so the MERGE row shows how many rows were inserted, updated and deleted.
X: A=userName: this column only names the user who ran the operation. It carries no row totals.
C=readVersion: this is the table version the operation read as its starting snapshot, a version number, not a row count.
D=isolationLevel: it names the isolation level used for the commit (for example WriteSerializable), and says nothing about affected rows.
T: Check operationMetrics of the MERGE row in DESCRIBE HISTORY to verify how many rows changed.

@ DBX-DAA D5 T5.4 applied use-case
S: A BI user reruns the same aggregate query on a SQL warehouse several times in a row. The underlying tables have not changed. The second and third runs return almost instantly. Which mechanism explains this?
A: The Delta transaction log, which stores the aggregated results of every query with each table version
B: Result caching, which returns the stored result of an identical query while the tables are unchanged
C: Photon, which permanently stores the output of every aggregate query that it has ever run
D: Liquid clustering, which rewrites the table after the first run so repeated queries skip the work
K: B
G: ## Result cache
Databricks SQL keeps query results so that an identical query can be answered without computing it again.
- The **local result cache** is an in-memory cache on the warehouse cluster. It lives until the cluster stops or restarts or the cache is full.
- The **remote result cache** is available on serverless SQL warehouses only. It stores results as workspace system data, survives warehouse stop and restart, and is shared across the workspace's warehouses.
Both have a lifetime of 24 hours starting at cache entry and are invalidated when the underlying tables are updated. A cache hit also means no query profile is recorded.
W: With unchanged tables, an identical query hits the result cache and returns the stored result, which makes repeated runs nearly instant.
X: A=Transaction log: the log records file-level commits and statistics, not query results.
C=Photon: Photon is a faster vectorized engine. It speeds execution but does not store outputs for later reuse.
D=Liquid clustering: it reorganizes data layout through OPTIMIZE, asynchronously and not as a side effect of a query. It would not explain identical reruns being instant.
T: Identical repeat queries on unchanged tables are answered from the result cache.

@ DBX-DAA D5 T5.4 applied troubleshooting
S: A pro SQL warehouse is stopped every night by its auto stop setting. Each morning, the first execution of a heavy dashboard query is slow, while reruns later in the day are fast. A colleague says the cache is why. What does the warehouse lose when it stops?
A: The query history entries and query profiles, which are deleted whenever the warehouse stops
B: The Delta table data files, which are removed from storage when the warehouse stops
C: The local result cache and the disk cache, which are cleared on stop or restart and must be repopulated
D: The access permissions on the tables, which have to be granted again after each warehouse start
K: C
G: ## What lives in compute
Two caches sit on the cluster itself.
- The **local result cache** holds query results in memory.
- The **disk cache** keeps copies of data files from cloud storage on the workers' local SSDs, so repeated reads are faster. It detects changed files and invalidates stale entries automatically.
Both disappear when the cluster is stopped or restarted, so the first query after a start reads from cloud storage and recomputes.
## What survives
Table data lives in cloud storage, history and permissions live in Unity Catalog and the workspace, not on the warehouse. On serverless warehouses, the remote result cache is stored as workspace system data, so it persists across restarts.
W: Stopping the cluster clears in-memory and local SSD caches. The first morning query must warm them again, while later runs hit the caches.
X: A=History deletion: query history is kept by the workspace and does not depend on the warehouse staying up.
B=Data files: the tables are in cloud object storage and are not tied to the warehouse lifecycle.
D=Permissions: grants are held in Unity Catalog and are unaffected by compute starting or stopping.
T: Stopping a warehouse empties its local caches; the first run afterwards is cold, and only the serverless remote result cache survives.

@ DBX-DAA D5 T5.5 applied use-case
S: A managed table used to be partitioned by `event_date`, but analysts now filter mostly by `customer_id` or `region`, and these patterns keep shifting. The team wants the data layout to adapt automatically. Which statement fits?

K: A
G: ## Automatic liquid clustering
Liquid clustering replaces partitioning and `ZORDER`. With `CLUSTER BY AUTO`, Databricks analyzes the historical query workload of a Unity Catalog managed table and picks clustering keys that reduce the data read. If the query pattern changes, it can select new keys. It requires predictive optimization and runs asynchronously.
## Converting a partitioned table
```
ALTER TABLE events REPLACE PARTITIONED BY WITH CLUSTER BY AUTO;
```
This uses the current partition columns as the initial clustering columns and lets predictive optimization adapt over time. Changing the clustering columns later does not rewrite existing data upfront, unlike changing partitions.
W: `CLUSTER BY AUTO` gives workload-driven key selection, and the `REPLACE PARTITIONED BY` form converts an existing partitioned table.

T: CLUSTER BY AUTO lets predictive optimization pick and adjust clustering keys based on how the table is queried.

@ DBX-DAA D5 T5.5 applied troubleshooting

K: B
G: ## When automatic clustering does nothing
Automatic liquid clustering is cost-aware. Databricks changes clustering keys only when the predicted savings from data skipping outweigh the cost of reclustering. It might not select keys when:
- the table is too small to benefit,
- the table already has an effective layout, from earlier manual keys or from natural insertion order that matches queries,
- the table does not have frequent queries,
- Databricks Runtime 15.4 LTS or above is not used.

D=ORDER BY requirement: the analysis looks at filter and access patterns of the query workload and not at sorting clauses.

@ DBX-DAA D5 T5.5 applied comparison
S: Predictive optimization is enabled at the account level, but the finance team wants it off for the `archive` schema, which is rarely queried. Predictive optimization is a Unity Catalog setting with inheritance. What is the correct way to do this?

B: Drop the `archive` schema and recreate it, because inheritance is fixed when an object is created and cannot change later

D: Revoke the SELECT privilege from analysts on the archive tables, which stops maintenance for them
K: C
G: ## Inheritance model
Predictive optimization can be set for an account, a catalog, a schema or a table. Catalogs, schemas and tables inherit the value of the level above by default, and an explicit setting at a lower level overrides it.
```
ALTER CATALOG c { ENABLE | DISABLE | INHERIT } PREDICTIVE OPTIMIZATION;
ALTER SCHEMA s { ENABLE | DISABLE | INHERIT } PREDICTIVE OPTIMIZATION;
ALTER TABLE t { ENABLE | DISABLE | INHERIT } PREDICTIVE OPTIMIZATION;
```
`INHERIT` resets an object back to its parent's value. The Predictive Optimization field of an object shows whether the value is set directly or inherited.
W: A schema-level `DISABLE` overrides the inherited account value only for that schema and its tables, leaving other schemas enabled.
X: A=Top level only: this would switch off maintenance for everything, and lower levels can be overridden.
B=Recreate the schema: the setting is a changeable property, so recreating adds risk and no benefit.
D=Revoking SELECT: access privileges do not control maintenance operations, which are system tasks.
T: Override predictive optimization at the catalog, schema or table level with ENABLE, DISABLE or INHERIT.
