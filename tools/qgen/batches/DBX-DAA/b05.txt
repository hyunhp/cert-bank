@ DBX-DAA D5 T5.2 applied use-case
S: An analyst opens the performance insights of a slow report query. One insight needs a change to the SQL text, and another needs a layout change on a table. The analyst selects Optimize next to the insights. What does Genie Code do?
A: It rewrites the query for insights that need a query change and presents the changes for approval, and it summarizes table or compute changes as plain text
B: It applies every recommendation straight to the query, the tables and the warehouse, without asking for approval, and reports afterwards what it changed
C: It rewrites the query for insights that need a query change, and then silently runs `OPTIMIZE` on the tables and resizes the warehouse on its own
D: It opens the documentation page of each insight and lists the links, because it can neither edit SQL statements nor summarize recommended actions
K: A
G: ## Insights with a next step
Each query performance insight carries a recommendation. Insights appear in query history and in the Performance insights tab of the query profile. When a query has actionable insights, an Optimize button opens Genie Code (formerly Databricks Assistant) with the insights as context.
## What Genie Code does with them
- For an insight that requires a query change (for example a wide projection or an exploding join), it rewrites the query and shows the changes so the analyst can approve them.
- For an insight that involves table or compute changes (for example small files or queue time), it summarizes the recommended actions as plain-language text. The analyst or the table owner then carries them out.
W: Genie Code splits the work by insight type: it drafts query rewrites for approval and explains table or compute actions in text, leaving those changes to the people who own the objects.
X: B=Applies everything: the query change is presented for approval, and table or compute changes are only summarized, so nothing is changed behind the analyst's back.
C=Silent OPTIMIZE and resize: Genie Code does not run maintenance or change the warehouse for the analyst. It describes those actions in text.
D=Links only: it does edit the query for insights that need a SQL change, and it writes a summary of the recommended actions instead of only listing pages.
T: Optimize turns insights into a query rewrite for approval, or a plain-text action list for table and compute changes.
@ DBX-DAA D5 T5.2 applied use-case
S: A dashboard query that used to finish in seconds now takes minutes. An analyst opens the query's details from query history and wants to see which individual steps of the execution consumed the most time, without reading the whole plan graph. Which part of the query profile helps most?
A: The Query text panel, which lists the full SQL statement along with the warehouse and the user that executed it earlier

C: The Details panel, which shows only the status and the user who started the query run

G: ## Reading a query profile
A query profile visualizes how a query executed. The left side has tabs (Details, Top operators, Query text), and the right side shows the directed acyclic graph (DAG) of operators such as Scan, Join, Shuffle, Hash/Sort and Filter. In the graph you can switch the displayed metric between time spent, memory peak and rows.

The Top operators panel ranks the most expensive operators, which is the fastest way to find optimization opportunities. The same query details panel also offers a See longest operators for this query button that opens it.
W: Top operators puts the longest running operators in one list, so the analyst can go straight to the scan, join or shuffle that dominates the runtime.
X: A=Query text: this panel only shows the statement that was run. It is useful for reading the SQL but carries no timing information about operators.
C=Details panel: it holds query summary metrics (durations, I/O), not a ranking of operators, and it is not limited to status and user.

@ DBX-DAA D5 T5.2 applied definition
S: The Performance insights tab of a dashboard query shows `SHORT_QUERY_PRIORITIZATION` with the label Accelerated and no other insight. What does this tell the analyst?
A: Databricks predicted that the query would be short and ran it at once through a fast path although the cluster was at capacity, so no action is needed
B: Databricks found the query too heavy for the warehouse and queued it behind lighter queries, so the analyst should raise the maximum number of clusters
C: Databricks found that the query spilled to disk while running at capacity, so the analyst should select a larger warehouse size for this query
D: Databricks flagged the query as short but held it in the queue until capacity was free, so the analyst should split the dataset into several queries
K: A
G: ## Two kinds of insight
Most insights flag a problem and carry a recommendation, such as `DATA_FILE_SIZE` or `EXCESSIVE_QUEUE_TIME`. A second group, applied accelerations, reports optimizations that Databricks already applied during execution. These appear in the Performance insights tab with an Accelerated label and require no action.
## Examples of applied accelerations
- `SHORT_QUERY_PRIORITIZATION`: the cluster was at capacity, but the query was predicted to be short, so it ran immediately instead of waiting behind heavier queries. This keeps interactive work responsive under load.
- `HISTORY_BASED_JOIN_STRATEGY`: a broadcast join was chosen from measurements of earlier similar runs.
- `AUTO_LIQUID_CLUSTERING`: the query read less data because its tables use automatic liquid clustering.
W: An Accelerated label means a benefit already given. For this insight the query skipped the queue thanks to the short-query prediction, so there is nothing to fix.
X: B=Queued behind others: this is the opposite, as the insight says the query was not held in the queue. Queue problems show as `EXCESSIVE_QUEUE_TIME`, without an Accelerated label.
C=Spill: disk spill is reported by `DATA_SPILL`, a problem insight whose fix is a larger size. It has nothing to do with the fast path.
D=Held in the queue: the query ran immediately, so splitting it would not help, and accelerations do not ask for action.
T: An Accelerated insight reports an optimization already applied, so the analyst does not need to act.
@ DBX-DAA D5 T5.2 applied definition
S: In the query details panel, a query shows a wall-clock duration of 40 seconds and an aggregated task time of 6 minutes. What does the aggregated task time represent?
A: The time the query waited in the warehouse queue before any compute resources were assigned to it
B: The time spent reading the final result back from cloud storage into the SQL editor session after the run
C: The combined execution time across all cores of all nodes, which can exceed wall-clock time
D: The time the optimizer needed to plan the query and to prune files before the execution started
K: C
G: ## Two clocks in one summary
The query details panel reports time in more than one way.
- **Wall-clock duration** is the elapsed time from the start of scheduling to the end of execution. Below it, a breakdown separates scheduling, query optimization and file pruning, and execution time.
- **Aggregated task time** adds up the time that every task spent running on every core of every node.
## Why they differ
Many tasks run at the same time, so their times add up to more than the elapsed time. A 40-second query using many cores in parallel can easily total 6 minutes of task time. It can also be shorter than wall-clock time if tasks waited for available nodes.
W: Aggregated task time is the sum of task execution across all cores and nodes, so parallel work makes it larger than the wall-clock duration. A large ratio simply means the query was well parallelized.
X: A=Queue wait: waiting for the warehouse is part of the scheduling portion of the wall-clock breakdown (and may raise an `EXCESSIVE_QUEUE_TIME` insight), not the task-time total.
B=Result fetch: fetching rows into a client is not what this metric counts. It measures task execution on the compute.
D=Planning and pruning: optimization and file pruning appear as their own part of the wall-clock breakdown before execution, separate from task time.
T: Wall-clock is elapsed time; aggregated task time sums work over all cores, so it can be much larger.

@ DBX-DAA D5 T5.2 applied troubleshooting
S: A query on a table made of thousands of tiny files is slow, and its profile shows a `DATA_FILE_SIZE` insight. The table is a Unity Catalog managed table partitioned by date. Which recommendation set matches the insight?
A: Enable predictive optimization or run `OPTIMIZE` to compact files, and consider liquid clustering for partitioned tables
B: Disable the disk cache on the warehouse, because small files only appear when cached copies are never evicted from local storage

G: ## Small files and scans
Every file a scan opens has a fixed overhead. Thousands of small files make the scan slow even when the total data is small. `DATA_FILE_SIZE` is the data layout insight that reports this.
## Documented fixes
- Enable predictive optimization on the table so file sizes are optimized automatically.
- Run `OPTIMIZE` to compact small files.
- Switch partitioned tables to liquid clustering, because predictive optimization cannot compact small files across partitions.
W: The insight lists compaction through predictive optimization or `OPTIMIZE`, and for partitioned tables it points to liquid clustering since compaction does not cross partition boundaries.

@ DBX-DAA D5 T5.3 applied use-case
S: An auditor asks which user last changed the `finance.ledger` Delta table, when, and with what kind of operation (for example MERGE or DELETE). Which command returns this information?
A: `SELECT * FROM finance.ledger VERSION AS OF 0`, because it lists the users who edited the table in the past
B: `DESCRIBE DETAIL finance.ledger`, because it returns the audit trail with one row for each write operation
C: `SHOW TBLPROPERTIES finance.ledger`, because it keeps a log of each user who modified the table
D: `DESCRIBE HISTORY finance.ledger`, which returns the operation, user and timestamp of each write, newest first
K: D
G: ## The Delta transaction log as an audit trail
Every write to a Delta table is a commit in its transaction log. `DESCRIBE HISTORY table_name` returns one row for each commit with the version, timestamp, user, operation (WRITE, MERGE, DELETE, OPTIMIZE and so on), `operationParameters` and `operationMetrics`. Rows come back in reverse chronological order, and `LIMIT 1` gives only the last operation.
## Related commands
- `DESCRIBE DETAIL` shows the table's current state (location, file count, size, format), not who changed it.
- `VERSION AS OF` reads the data as it was, it does not tell who wrote it.
- Catalog Explorer shows the same history visually on the History tab.
W: `DESCRIBE HISTORY` returns exactly the columns the auditor needs: operation type, user and time of each commit.
X: A=VERSION AS OF: it returns rows from an older version of the data. It does not list users or operations.
B=DESCRIBE DETAIL: it reports current properties such as location, number of files and size. It has no per-write audit rows.
C=SHOW TBLPROPERTIES: it lists table property key-value pairs. It is not a log of modifications.
T: Use DESCRIBE HISTORY (or the History tab) for who, when and what on a Delta table.

@ DBX-DAA D5 T5.3 applied use-case
S: A monthly revenue figure changed between Monday's board report and Tuesday's. The analyst needs to compare the `sales_summary` Delta table as of Monday's last commit with its current state to find the rows that differ. What is the right approach?
A: Read Monday's state with `VERSION AS OF` or `TIMESTAMP AS OF` and compare it with the current table using `EXCEPT`
B: Run `RESTORE TABLE sales_summary` to Monday's version, query it, then restore forward again to the latest one
C: Clone the table with `CREATE TABLE ... DEEP CLONE` after the change so that the older rows are available for comparison
D: Ask the data engineers to rebuild the table from the source system and compare the rebuilt copy to the current table
K: A
G: ## Time travel for comparison
Delta keeps earlier table versions, so you can read the table as it was without changing it.
```
SELECT * FROM sales_summary VERSION AS OF 41
EXCEPT
SELECT * FROM sales_summary;
```
`VERSION AS OF` takes a version number from `DESCRIBE HISTORY`; `TIMESTAMP AS OF` takes a timestamp. Running the query in both directions shows rows that were removed and rows that were added.
## Why not change the table
`RESTORE` rewrites the current state of the table (and is itself a new commit), which affects every other reader and downstream job. Reading an old version is read-only.
W: Time travel reads an old version without modifying anything, and set operators such as `EXCEPT` then show exactly which rows differ between Monday and now.
X: B=RESTORE: it changes the live table twice and creates new commits that downstream streams may treat as new data. It is the wrong tool for a read-only comparison.
C=Deep clone afterwards: cloning the table now copies the already-changed state, so Monday's rows are not available unless a clone was taken before. Cloning can use a version, but that is again time travel.
D=Rebuild from source: this is slow, depends on engineers, and rebuilds current logic. It cannot reproduce what the table contained on Monday.
T: Compare two moments of a Delta table with VERSION AS OF or TIMESTAMP AS OF and a set operator; do not restore to just look.

@ DBX-DAA D5 T5.3 applied troubleshooting
S: In `DESCRIBE HISTORY`, an analyst sees many `OPTIMIZE` rows for a table and wants to know which ones were started by a person or a scheduled job and which were automatic compaction after writes. Which column separates them?
A: `operationParameters`, where `auto` is `true` for automatic compaction and `false` for a command run by a user or a scheduled job
B: `operation`, which reads `OPTIMIZE AUTO` for automatic compaction and `OPTIMIZE MANUAL` for runs started by a person or a job
C: `userMetadata`, which holds the word AUTO for each compaction triggered by a write and stays empty for every manual run
D: `readVersion`, which stays empty for automatic compaction because that kind of run never reads an earlier table version
K: A
G: ## OPTIMIZE rows in history
Auto compaction, liquid clustering and Z-ordering all appear in table history as `OPTIMIZE` operations, so the `operation` column alone does not tell them apart. The `operationParameters` map does.
- `auto` = `true`: automatic compaction triggered after a write. `false`: a user or scheduled job ran `OPTIMIZE`.
- `clusterBy` filled with column names: liquid clustering. An empty array means file compaction only.
- `zOrderBy` filled with column names: Z-ordering.
```
SELECT version, operationParameters.auto
FROM (DESCRIBE HISTORY sales)
WHERE operation = 'OPTIMIZE';
```
W: The `auto` parameter inside `operationParameters` is the documented switch between automatic compaction and a command that a user or a job ran.
X: B=operation column: every kind of compaction shows the single value `OPTIMIZE`, so this column cannot separate them.
C=userMetadata: it holds custom text set by the writer and is not the documented marker for automatic compaction.
D=readVersion: it records the snapshot version an operation started from, which is set for compaction runs of both kinds.
T: In DESCRIBE HISTORY, read operationParameters (auto, clusterBy, zOrderBy) to classify OPTIMIZE runs.

@ DBX-DAA D5 T5.4 applied use-case
S: A BI user reruns the same aggregate query on a SQL warehouse several times in a row. The underlying tables have not changed. The second and third runs return almost instantly. Which mechanism explains this?
A: The Delta transaction log, which stores the aggregated results of every query with each table version
B: Result caching, which returns the stored result of an identical query while the tables are unchanged
C: Photon, which permanently stores the output of every aggregate query that it has ever run
D: Liquid clustering, which rewrites the table after the first run so repeated queries skip the work
K: B
G: ## Result cache
Databricks SQL keeps query results so that an identical query can be answered without computing it again.
- The **local result cache** is an in-memory cache on the warehouse cluster. It lives until the cluster stops or restarts or the cache is full.
- The **remote result cache** is available on serverless SQL warehouses only. It stores results as workspace system data, survives warehouse stop and restart, and is shared across the workspace's warehouses.
Both have a lifetime of 24 hours starting at cache entry and are invalidated when the underlying tables are updated. A cache hit also means no query profile is recorded.
W: With unchanged tables, an identical query hits the result cache and returns the stored result, which makes repeated runs nearly instant.
X: A=Transaction log: the log records file-level commits and statistics, not query results.
C=Photon: Photon is a faster vectorized engine. It speeds execution but does not store outputs for later reuse.
D=Liquid clustering: it reorganizes data layout through OPTIMIZE, asynchronously and not as a side effect of a query. It would not explain identical reruns being instant.
T: Identical repeat queries on unchanged tables are answered from the result cache.

@ DBX-DAA D5 T5.4 applied troubleshooting
S: A pro SQL warehouse is stopped every night by its auto stop setting. Each morning, the first execution of a heavy dashboard query is slow, while reruns later in the day are fast. A colleague says the cache is why. What does the warehouse lose when it stops?
A: The query history entries and query profiles, which are deleted whenever the warehouse stops
B: The Delta table data files, which are removed from storage when the warehouse stops
C: The local result cache and the disk cache, which are cleared on stop or restart and must be repopulated
D: The access permissions on the tables, which have to be granted again by an owner after each warehouse start
K: C
G: ## What lives in compute
Two caches sit on the cluster itself.
- The **local result cache** holds query results in memory.
- The **disk cache** keeps copies of data files from cloud storage on the workers' local SSDs, so repeated reads are faster. It detects changed files and invalidates stale entries automatically.
Both disappear when the cluster is stopped or restarted, so the first query after a start reads from cloud storage and recomputes.
## What survives
Table data lives in cloud storage, history and permissions live in Unity Catalog and the workspace, not on the warehouse. On serverless warehouses, the remote result cache is stored as workspace system data, so it persists across restarts.
W: Stopping the cluster clears in-memory and local SSD caches. The first morning query must warm them again, while later runs hit the caches.
X: A=History deletion: query history is kept by the workspace and does not depend on the warehouse staying up.
B=Data files: the tables are in cloud object storage and are not tied to the warehouse lifecycle.
D=Permissions: grants are held in Unity Catalog and are unaffected by compute starting or stopping.
T: Stopping a warehouse empties its local caches; the first run afterwards is cold, and only the serverless remote result cache survives.

@ DBX-DAA D5 T5.4 applied use-case

The documentation states that `SET use_cached_result = false` disables query result caching in the SQL editor, and it should be used only for testing or benchmarking. With it, each run executes for real and the timing reflects the query itself.

The disk cache of file reads still exists, so later runs can be faster because data files are warm. For fair comparisons run each version several times or alternate them.

@ DBX-DAA D5 T5.5 applied use-case
S: A managed table used to be partitioned by `event_date`, but analysts now filter mostly by `customer_id` or `region`, and these patterns keep shifting. The team wants the data layout to adapt automatically. Which statement fits?
A: `ALTER TABLE events REPLACE PARTITIONED BY WITH CLUSTER BY AUTO`, so clustering keys follow query patterns

K: A
G: ## Automatic liquid clustering
Liquid clustering replaces partitioning and `ZORDER`. With `CLUSTER BY AUTO`, Databricks analyzes the historical query workload of a Unity Catalog managed table and picks clustering keys that reduce the data read. If the query pattern changes, it can select new keys. It requires predictive optimization and runs asynchronously.
## Converting a partitioned table
```
ALTER TABLE events REPLACE PARTITIONED BY WITH CLUSTER BY AUTO;
```
This uses the current partition columns as the initial clustering columns and lets predictive optimization adapt over time. Changing the clustering columns later does not rewrite existing data upfront, unlike changing partitions.
W: `CLUSTER BY AUTO` gives workload-driven key selection, and the `REPLACE PARTITIONED BY` form converts an existing partitioned table.
X: B=Add partitions: partitioning is rigid, and one partition per customer creates a huge number of small partitions. It will not follow changing filters.
C=Made-up property: there is no `layout` table property that makes tables adapt. Automatic behavior comes from `CLUSTER BY AUTO` with predictive optimization.
D=Weekly ZORDER on the old column: the target stays `event_date`, which is no longer the main filter, and predictive optimization ignores Z-ordered files.
T: CLUSTER BY AUTO lets predictive optimization pick and adjust clustering keys based on how the table is queried.

G: ## When automatic clustering does nothing
Automatic liquid clustering is cost-aware. Databricks changes clustering keys only when the predicted savings from data skipping outweigh the cost of reclustering. It might not select keys when:
- the table is too small to benefit,
- the table already has an effective layout, from earlier manual keys or from natural insertion order that matches queries,
- the table does not have frequent queries,
- Databricks Runtime 15.4 LTS or above is not used.

D=ORDER BY requirement: the analysis looks at filter and access patterns of the query workload and not at sorting clauses.
T: No automatic keys usually means a small table, a layout that is already good, or too few queries; check the History tab.
