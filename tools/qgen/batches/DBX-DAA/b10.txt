@ DBX-DAA D1 T1.1 advanced use-case
S: Each morning a retail analytics team needs three steps in a fixed order: a Lakeflow Connect pipeline loads Salesforce data, a SQL script on a SQL warehouse rebuilds two summary tables, and an AI/BI dashboard is refreshed and emailed to regional managers. Each step may start only after the previous one succeeds, the on-call analyst must hear about any failure, and the team wants no custom orchestration code. Which approach meets these requirements with the LEAST effort?
A: One Lakeflow Jobs job with a pipeline task, a SQL task and a dashboard task linked by dependencies, plus failure notifications to on-call
B: A dashboard schedule at 07:00 with the managers as subscribers, and separate schedules for the pipeline at 05:00 and for the SQL script at 06:00
C: Materialized views for both summary tables with TRIGGER ON UPDATE, and a SQL alert that emails the managers when either view has refreshed
D: A notebook that polls the pipeline status through the REST API, runs the SQL script when it ends and then calls the dashboard publish API
K: A
G: ## Orchestration on the platform
Lakeflow Jobs (formerly Databricks Workflows) is the orchestrator of the Data Intelligence Platform. A job is a graph of tasks of different types that run in dependency order:
- a **pipeline task** runs a Lakeflow pipeline, including Lakeflow Connect ingestion;
- a **SQL task** runs a query or SQL file on a SQL warehouse;
- a **dashboard task** refreshes a published AI/BI dashboard and sends it to its own list of subscribers (it needs a pro or serverless warehouse).
A task starts only when the tasks it depends on succeed, and the job sends notifications on failure.
## Why fixed clock times are fragile
Separate schedules only guess how long each step takes. When the 05:00 load runs late, the 06:00 script reads incomplete data and the 07:00 email still goes out, with no link between the steps.
W: Lakeflow Jobs with chained tasks: task dependencies enforce the order and the success condition, the dashboard task refreshes and emails the dashboard, and job notifications reach the on-call analyst, all configured without code.
X: B=Three clock schedules: the steps are not linked, so a late or failed load still lets the script and the email run on stale data, and no single place reports the failure.
C=Triggered views plus an alert: the views would refresh on source changes, but an alert evaluates a query condition; it does not deliver the dashboard and does not tie the three steps into one sequence with failure handling.
D=Polling notebook: it works, but it is exactly the custom orchestration code the team wants to avoid, and the team must maintain retries and error handling itself.
T: Chain different step types (pipeline, SQL, dashboard) in one Lakeflow Jobs job so that order, success checks and failure alerts are handled for you.
V: Lakeflow Jobs, AI/BI dashboards

@ DBX-DAA D1 T1.2 advanced troubleshooting
S: The metric view `sales.semantic.orders_mv` defines the measure `Total Revenue` and the field `customer_id`. An analyst needs revenue per customer segment, and the segment column exists only in `crm.core.customers`. Her query `SELECT c.segment, MEASURE(m.`Total Revenue`) FROM sales.semantic.orders_mv m JOIN crm.core.customers c ON m.customer_id = c.id GROUP BY c.segment` fails. The metric view definition must stay unchanged, because other dashboards depend on it. What should she do?
A: Aggregate the metric view by customer_id with MEASURE() inside a CTE, then join that CTE to the customers table and sum per segment
B: Replace MEASURE() with SUM() on the measure column, because a query that joins other tables must aggregate measures with standard functions
C: Read the metric view with SELECT * in a subquery, so that every measure becomes an ordinary column the outer query can join and group
D: Create a standard view that joins the metric view to customers, because only a view definition may join a metric view to other tables
K: A
G: ## How metric views are queried
A Unity Catalog metric view separates **measures** (aggregations such as total revenue) from **fields** (columns to group and filter by). Users group by any field at query time, and the engine computes the measure correctly for that grouping.
Two rules matter here:
- every measure must be evaluated with the `MEASURE()` aggregate function, and `SELECT *` is not allowed because measures need that function;
- a metric view **cannot be joined directly** with other tables at query time.
## The documented pattern
Query the metric view in a CTE at a grain that has the join key, then join the CTE result:
`WITH o AS (SELECT customer_id, MEASURE(`Total Revenue`) AS rev FROM orders_mv GROUP BY customer_id) SELECT c.segment, SUM(o.rev) FROM o JOIN customers c ON o.customer_id = c.id GROUP BY c.segment`
Summing per-customer revenue is correct for an additive measure such as total revenue. For a ratio measure, add the segment to the metric view instead.
W: CTE then join: the metric view is evaluated on its own with MEASURE() at customer grain, and the plain result can then be joined and re-aggregated by segment, which is the documented way to combine a metric view with other tables.
X: B=SUM instead of MEASURE: measures in a metric view must be evaluated with MEASURE(); replacing it does not lift the restriction on joining the metric view directly.
C=SELECT * subquery: SELECT * is not supported on a metric view, because each measure has to be requested explicitly through MEASURE().
D=Standard view with the join: the restriction is on joining the metric view itself; putting the same join inside a view definition does not make it valid, while the CTE pattern does.
T: To combine a metric view with other tables, compute the measures in a CTE at a joinable grain and join the CTE result.
V: Unity Catalog metric views

@ DBX-DAA D1 T1.2 advanced troubleshooting
S: A data steward owns the gold table `finance.gold.revenue_daily` and wants analysts to see it marked as certified in Catalog Explorer and in search results. When she sets the certification status, the action fails with a permission error, yet she can still add ordinary tags such as `team = finance` to the same table. Her account admin confirms that the table and its schema are fine. What is she missing?
A: The ASSIGN permission on the system.certification_status governed tag, which certification needs in addition to tag rights on the table
B: The APPLY TAG privilege on the table itself, which object owners do not receive automatically and which a metastore admin grants
C: The MANAGE privilege on the parent catalog, because certification status is a catalog-level setting that every table below inherits
D: Workspace admin rights, because only workspace admins can mark Unity Catalog tables as certified or deprecated with the system tag
K: A
G: ## Certification is a governed system tag
Catalog Explorer shows a certified or deprecated badge from the system tag `system.certification_status` (values `certified` and `deprecated`). It can be applied to catalogs, schemas, tables, dashboards, Genie Agents, notebooks and more, and users can search by it.
Two permission layers apply:
- **On the object**: to add any tag you must own the object, or hold `APPLY TAG` on it plus `USE SCHEMA` and `USE CATALOG` on its parents.
- **On the governed tag**: governed tags (and this system tag) also require the **ASSIGN** permission on the tag itself. ASSIGN is granted at account level or per governed tag.
## Reading the symptom
Ordinary tags work, so the object-level rights are in place (she owns the table). Only the governed tag fails, so the missing piece is ASSIGN on `system.certification_status`.
W: ASSIGN on the certification tag: certification uses a governed system tag, and applying it requires ASSIGN on that tag; her ownership already covers the object-level tag rights, as the working free tags show.
X: B=APPLY TAG on the table: an owner can already tag her own object, which is why the free tag `team = finance` succeeds; the failure is specific to the governed tag.
C=MANAGE on the catalog: certification is a tag value on each object, not a catalog-wide setting, and catalog privileges do not grant the governed tag permission.
D=Workspace admin rights: no admin role is required; anyone with ASSIGN on the tag and tag rights on the object can certify it.
T: Certifying an object takes ASSIGN on the system.certification_status governed tag plus the normal right to tag that object.
V: Unity Catalog governed tags, Catalog Explorer

Two teammates in the same workspace now get permission errors when they query its tables, and the listing does not show among their own installed products. The team wants them to read the data without installing a second copy or contacting the provider. What should the analyst do?
A: Grant the teammates USE CATALOG, USE SCHEMA and SELECT on demo_census, because the requester owns the catalog of the installed product
B: Ask each teammate to request the same listing, because Marketplace data is licensed per user and each install is visible only to its requester
C: Ask the provider to add the teammates as recipients of the share, because only the provider can extend access to an installed catalog

Marketplace datasets arrive through OpenSharing as a **read-only catalog** in your Unity Catalog metastore. The user who requested the data product **owns** that catalog.
As owner, the requester can grant team members access at catalog, schema, table, view, row and column level like any other Unity Catalog data, or transfer ownership. Read-only means nobody can write to the shared tables; it does not mean the catalog cannot be shared inside your account.

Installing needs `USE MARKETPLACE ASSETS` on the metastore (on by default), or `CREATE CATALOG` plus `USE PROVIDER`, or metastore admin. Reading an installed catalog needs only ordinary grants.

D=Copy with CTAS: read-only stops writes to the shared tables, not grants; a copy duplicates data and goes stale, which the team wants to avoid.

@ DBX-DAA D2 T2.2 advanced troubleshooting
S: The governance team created the governed tag `data_domain` with the allowed values `finance`, `sales` and `hr`. An analyst who owns `ops.reporting.cost_centers` runs `ALTER TABLE ops.reporting.cost_centers SET TAGS ('data_domain' = 'finance')` and gets a permission error, while `SET TAGS ('project' = 'q4_review')` on the same table works. The value is spelled exactly as in the allowed list. Which change lets the analyst apply the governed tag?
A: Someone with MANAGE on data_domain grants the analyst ASSIGN on that tag, since owning the table covers only the object-level tag right
B: A metastore admin grants the analyst APPLY TAG on the table, because table owners may set only ungoverned tags until it is granted explicitly
C: The analyst retries with the value written as 'Finance', because governed tag values are checked against the allowed list case-sensitively
D: An account admin grants the analyst CREATE on governed tags at account level, which is required before any governed tag can be assigned
K: A
G: ## Governed tags have their own permissions
A **governed tag** is an account-level tag with a policy: a fixed key, a list of allowed values and control over who may use it. Its permissions are:
- `CREATE` (account scope): create new governed tags;
- `MANAGE` (account or one tag): edit the tag and grant MANAGE or ASSIGN to others;
- `ASSIGN` (account or one tag): assign the tag to Unity Catalog objects.
ASSIGN is separate from the object-level right to tag something (ownership, or `APPLY TAG` plus usage privileges). Both are needed for a governed tag; ungoverned tags need only the object-level right.
## Reading the symptom
The free tag works, so object-level tagging is fine. The value `finance` is in the allowed list, so the only gap is ASSIGN on `data_domain`.
W: ASSIGN on the governed tag: a user with MANAGE on data_domain (or an account admin) can grant it, which completes the two rights a governed tag needs.
X: B=APPLY TAG on the table: as owner the analyst already has the object-level right, proven by the working free tag; the error comes from the tag policy.
C=Capitalized value: the analyst already used an allowed value; changing its spelling cannot fix a permission error.
D=CREATE on governed tags: CREATE lets a user define new governed tags; it is not what allows assigning an existing tag to a table.
T: A governed tag needs ASSIGN on the tag plus the right to tag the object; ungoverned tags need only the second.
V: Governed tags, Unity Catalog

@ DBX-DAA D2 T2.3 advanced use-case
S: The STRING column `signup_dt` in `crm.raw.signups` holds dates from two source systems, written as `2026-03-14` or as `14/03/2026`, and a few rows contain junk such as `unknown`. The analyst needs a DATE column in a cleaned view. Junk must become NULL instead of failing the query, both valid layouts must parse, and the workspace runs with ANSI mode on. Which expression should the view use?
A: `coalesce(try_to_date(signup_dt, 'yyyy-MM-dd'), try_to_date(signup_dt, 'dd/MM/yyyy'))`, keeping the first layout that parses and NULL when neither does
B: `try_cast(signup_dt AS DATE)`, which detects either separator and layout by itself and returns NULL for any value that it cannot read at all
C: `coalesce(to_date(signup_dt, 'yyyy-MM-dd'), to_date(signup_dt, 'dd/MM/yyyy'))`, which falls through to the second layout whenever the first one fails
D: `to_date(nullif(signup_dt, 'unknown'), 'yyyy-MM-dd')`, which turns the junk value into NULL first and then converts all the remaining strings
K: A
G: ## Parsing dates safely
- `to_date(expr, fmt)` parses with one pattern and **raises an error** when a value does not match it (ANSI behavior).
- `try_to_date(expr, fmt)` does the same parse but returns **NULL** when the value cannot be parsed with that pattern.
- `try_cast(expr AS DATE)` (and `try_to_date` without a pattern) only understands the default `yyyy-MM-dd` layout.
## Several layouts in one column
Try each pattern with the safe function and keep the first success:
`coalesce(try_to_date(s, 'yyyy-MM-dd'), try_to_date(s, 'dd/MM/yyyy'))`
For `14/03/2026` the first call returns NULL and the second returns 2026-03-14; for `unknown` both return NULL, so the row stays with a NULL date instead of failing the query.
W: try_to_date per layout inside coalesce: each attempt returns NULL instead of an error, so coalesce picks the layout that worked and junk ends up NULL.
X: B=try_cast to DATE: without a pattern only the default yyyy-MM-dd layout is recognized, so every dd/MM/yyyy value becomes NULL and real dates are lost.
C=to_date inside coalesce: coalesce never gets a chance to fall through, because to_date raises an error on the first value that does not match its pattern.
D=nullif then to_date: it removes one known junk word, but every dd/MM/yyyy value still fails to_date with a single pattern, and any other junk value fails the query too.
T: Combine try_to_date calls with coalesce to parse several date layouts and turn unparseable values into NULL.
V: Databricks SQL functions

@ DBX-DAA D3 T3.1 advanced troubleshooting
S: A supplier shares the table `inventory_snapshot` with your company through Databricks-to-Databricks OpenSharing, and it appears in the catalog `supplier_share`. Ordinary SELECT queries work. To settle a disputed delivery, an analyst runs `SELECT * FROM supplier_share.ops.inventory_snapshot VERSION AS OF 120`, and the query fails, although the supplier confirms that version 120 still exists on its side. What explains the failure, and what fixes it?
A: The table was added to the share without history, so the supplier must share it WITH HISTORY before recipients can run time travel
B: Recipients can never time travel on shared tables, so the supplier must export version 120 as a separate table and add it to the share
C: The analyst lacks MODIFY on the shared catalog, which time travel needs because it reads older data files from the provider's storage
D: Version 120 is past the recipient's own seven-day retention window, so the analyst must raise deletedFileRetentionDuration on the table
K: A
G: ## What a share exposes
A provider adds tables to a share and chooses whether to include **history**. History sharing lets recipients:
- run time travel queries (`VERSION AS OF`, `TIMESTAMP AS OF`);
- read the table with Structured Streaming;
- run transactions on it (and, with change data feed enabled first, use `table_changes()`).
Without history, recipients read only the current snapshot. Whole schemas are shared with history by default; individual tables are shared `WITH HISTORY` when the provider chooses it.
## Who controls what
The shared catalog is read-only for the recipient. Retention settings, history and the files belong to the provider's table; the recipient cannot change them.
W: Share WITH HISTORY: time travel on a shared table works only when the provider has shared its history, so the provider must update the share.
X: B=Never possible: recipients can time travel once the table is shared with history; a separate exported table is unnecessary.
C=MODIFY on the catalog: shared catalogs are read-only and reading needs only SELECT; MODIFY is a write privilege and cannot be granted on a share.
D=Recipient retention window: retention is a property of the provider's table, not something the recipient owns or can change, and the provider confirms the version exists.
T: Recipients can query older versions of a shared table only when the provider shares it WITH HISTORY.

@ DBX-DAA D3 T3.2 advanced use-case
S: Each month a store operations analyst receives a CSV of store codes such as `00731`, which she uploads into the volume `ops.raw.monthly_files`. She needs one Unity Catalog managed table, `ops.ref.stores`, replaced with each new month's file, and the codes must keep their leading zeros. She prefers the UI to writing SQL, holds CREATE TABLE on `ops.ref`, and has access to a running SQL warehouse. Which approach fits?

Catalog Explorer can create a **Unity Catalog managed table** from a file, several files or a directory in a volume. It needs `CREATE TABLE` in the target schema and a running SQL warehouse. The dialog shows a preview and lets you:

T: When creating a table from volume files in the UI, override column types in the preview so codes with leading zeros stay STRING.

@ DBX-DAA D4 T4.2 advanced tradeoff
S: A team runs everything on a classic SQL warehouse. It now wants a Genie Agent for sales managers and a Lakeflow Jobs dashboard task that refreshes a dashboard after each nightly load. Demand is bursty, idle in the evening with a rush at 9 a.m., and the team wants the LEAST sizing and scaling work with fast startup. Which warehouse choice fits?
A: A serverless SQL warehouse, which supports Genie and dashboard tasks and lets Intelligent Workload Management add and remove clusters
B: A pro SQL warehouse with a minimum of one and a maximum of ten clusters, sized by the rule of one cluster for every ten concurrent queries
C: The existing classic warehouse with a larger cluster size and more maximum clusters, since Genie and dashboard tasks run on any type
D: A classic warehouse for the dashboard task and a separate pro warehouse for the Genie Agent, each set to the longest auto stop value
K: A
G: ## Warehouse types and what they unlock
- **Classic**: basic Databricks SQL; you size and set cluster counts yourself.
- **Pro**: more features, still with manual min/max cluster settings (guide: about one cluster per 10 concurrent queries).
- **Serverless**: compute managed by Databricks with fast startup and **Intelligent Workload Management (IWM)**, which predicts each query's needs, queues when needed and quickly adds or removes clusters.
Genie Agents need a **pro or serverless** warehouse, and so does a Lakeflow Jobs dashboard task. A classic warehouse can serve neither.
## Matching the constraints
Both new features rule out classic. Between pro and serverless, the bursty pattern and "least sizing work" favor serverless, where IWM handles the 9 a.m. rush and idle evenings without manual cluster limits.
W: Serverless warehouse: it supports both Genie and dashboard tasks, starts fast, and IWM scales clusters up for the morning rush and down when idle, with the least manual tuning.

G: ## Identifiers in the three-level namespace
Unity Catalog objects are addressed as `catalog.schema.object`. Each part is an identifier:
- **regular identifiers** contain letters, digits and underscores;
- **delimited identifiers** are wrapped in **backticks** and may contain other characters such as a hyphen, space or `@`.
Without backticks, `emea-sales` is read as `emea` minus `sales`, so the parser fails before any permission is checked. Identifiers are case-insensitive when referenced.
W: Backtick-delimited catalog name: backticks make the hyphenated name one identifier, so the three-level name resolves and her existing privileges apply.
X: B=Double quotes: Databricks SQL delimits identifiers with backticks; double quotes denote string literals by default.
C=Underscore spelling: names are stored as written, so emea_sales is a different, non-existent catalog.
D=Unquoted USE CATALOG: the same parsing rule applies in USE statements, so the hyphen still needs backticks.
T: Delimit identifiers that contain special characters, such as hyphens, with backticks in Databricks SQL.

G: ## Column masks
A **column mask** is a SQL function attached to a column with `ALTER TABLE ... ALTER COLUMN email SET MASK fn`. Every query of that table, from any tool, returns the function's output instead of the raw value. The function can check membership with `is_account_group_member()`.
## Masks that keep analytics working
A constant such as `'REDACTED'` hides the value but makes all rows equal, so `count(DISTINCT email)` returns 1 and joins on email match everything or nothing. A **deterministic hash** such as `sha2(email, 256)` hides the address while keeping equal emails equal, so distinct counts and joins across both tables still work (as long as both tables apply the same function).
W: Hash mask on both tables: analysts see only hashes, equal addresses still hash alike for distinct counts and joins, the privacy group sees real values, and the existing table names keep working everywhere.
X: B=Constant REDACTED: every row gets the same value, so distinct counts collapse to one and joins on email break.
C=Dynamic views: they need new object names and moving every dashboard, which the requirement rules out.
D=Column-level SELECT: Unity Catalog grants SELECT on tables and views, not on single columns, so this control does not exist.
T: Mask PII with a deterministic hash when analysts still need to count or join on it without seeing it.
