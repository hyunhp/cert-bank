@ DBX-DAA D5 T5.6 applied troubleshooting
S: An analyst runs `SELECT region, product, SUM(amount) AS total FROM sales GROUP BY region` and the query fails with a MISSING_AGGREGATION error. The report must show one row per region and product. Which change fixes the query?
A: Wrap product in SUM so that it is aggregated together with the amount column in each group
B: Replace GROUP BY region with GROUP BY region, product so every non-aggregated column is grouped
C: Move the GROUP BY clause above the FROM clause so the grouping runs before the table is read
D: Add HAVING product IS NOT NULL after the table name so that the unlisted column is dropped
K: B
G: ## The rule behind the error
When a query uses GROUP BY or an aggregate function, every column in the SELECT list must be either listed in the GROUP BY clause or wrapped in an aggregate function such as `SUM`, `COUNT` or `MAX`. Otherwise Databricks SQL raises MISSING_AGGREGATION, because one output row per region cannot show several different product values.
The fix depends on the business question. If the report needs one row per region and product, the grain of the result is region plus product, so both columns belong in GROUP BY.
W: Group by both columns: `GROUP BY region, product` makes the grain of each output row match the SELECT list, so every non-aggregated column is a grouping column and the error disappears.
X: A=Wrap product in SUM: SUM works on numbers, and the request needs product shown as a label. Aggregating it would either fail on a text column or hide the product the report must show.
C=Move GROUP BY above FROM: clause order is fixed (SELECT, FROM, WHERE, GROUP BY, HAVING, ORDER BY). Reordering gives a syntax error and does not change what is grouped.
D=HAVING product IS NOT NULL: HAVING filters groups after aggregation. It does not make product a grouping column, so the same error remains.
T: Every non-aggregated SELECT column must be in GROUP BY; match the grouping columns to the grain the report needs.

@ DBX-DAA D5 T5.6 applied troubleshooting
S: A query lists every customer with their orders: `SELECT c.name, o.order_id FROM customers c LEFT JOIN orders o ON c.id = o.customer_id WHERE o.status = 'shipped'`. The analyst expected customers without any orders to appear with NULL, but they are missing. What fixes it?
A: Replace LEFT JOIN with FULL JOIN so that all rows of both tables are kept regardless of the WHERE clause
B: Add DISTINCT to the SELECT list so that customers without orders are no longer removed as duplicates
C: Move the status condition into the ON clause so unmatched customers keep their NULL-filled row
D: Swap the table order in the query so that the orders table becomes the left side of the join
K: C
G: ## Why a WHERE filter can undo an outer join
A LEFT JOIN keeps every row of the left table and fills the right-side columns with NULL when no match exists. A `WHERE` clause runs after the join. For a customer without orders, `o.status` is NULL, and `NULL = 'shipped'` is not true, so the row is filtered out. The query then behaves like an INNER JOIN.
To filter the right table while keeping unmatched left rows, put the condition in the `ON` clause (`ON c.id = o.customer_id AND o.status = 'shipped'`), which restricts which orders match instead of which result rows survive.
W: Condition in ON: the status filter then limits which orders are joined, and customers with no shipped orders still appear once with NULL in the order columns.
X: A=FULL JOIN: it also keeps unmatched rows, but the WHERE clause still runs afterward and removes every row with a NULL status, so the missing customers stay missing.
B=DISTINCT: it removes duplicate result rows. The customers are not duplicates; they were already filtered out by WHERE, so there is nothing to bring back.
D=Swapping table order: it would keep all orders and drop customers without orders, which is the opposite of the requirement, and the WHERE condition would still apply.
T: A WHERE condition on the right table of a LEFT JOIN turns it into an inner join; put that condition in ON to keep unmatched rows.

@ DBX-DAA D5 T5.6 applied troubleshooting
S: An analyst wants all employees without a manager and writes `SELECT name FROM employees WHERE manager_id = NULL`. The query runs without error but returns no rows, although many employees have no manager. Which correction returns them?
A: Use WHERE manager_id IS NULL, because comparing to NULL with an equals sign never evaluates to true
B: Use WHERE manager_id == 'NULL', because the missing value is stored as the text string NULL
C: Use WHERE manager_id <=> 0 so that missing values are compared as the number zero
D: Use WHERE NOT manager_id, because a missing value is treated as false in a Boolean test
K: A
G: ## NULL means unknown
In SQL, NULL stands for a missing or unknown value. Comparing anything to NULL with `=`, `<>` or `<` gives NULL (unknown), not true, and a WHERE clause keeps only rows where the condition is true. So `manager_id = NULL` filters out every row and runs without an error, which makes the bug easy to miss.
Use `IS NULL` or `IS NOT NULL` to test for missing values. Databricks also has the null-safe equality operator `<=>`, which treats two NULLs as equal, and functions such as `coalesce`.
W: IS NULL: this predicate is the defined way to test for a missing value, and it evaluates to true exactly for rows where manager_id is NULL.
X: B=Comparing to the text 'NULL': a missing value is not the string NULL, and comparing a numeric ID column to text would not select missing values.
C=Null-safe equality with 0: `<=>` is useful for comparing two values where NULL equals NULL, but 0 is a real number, so the query would select employees whose manager ID is zero, not missing ones.
D=NOT manager_id: the column is an identifier, not a Boolean, and NULL is unknown rather than false. The expression would not return the missing rows either.
T: Never compare with `= NULL`; test missing values with IS NULL or IS NOT NULL.

@ DBX-DAA D5 T5.6 applied troubleshooting
S: An analyst needs customers whose total order value is above 1000 and writes `SELECT customer_id, SUM(amount) AS total FROM orders WHERE SUM(amount) > 1000 GROUP BY customer_id`. The query fails. What is the correct fix?
A: Replace WHERE with HAVING SUM(amount) > 1000 placed after the GROUP BY clause
B: Replace SUM(amount) in the condition with the alias total and keep it in the WHERE clause
C: Move GROUP BY customer_id before the FROM clause so the sums exist when WHERE is evaluated
D: Wrap the table name in parentheses so that the aggregate is calculated in the FROM step
K: A
G: ## WHERE versus HAVING
`WHERE` filters individual rows before grouping, so it cannot contain an aggregate such as `SUM(amount)`: the sum does not exist yet. `HAVING` filters groups after aggregation and can reference aggregate functions, and in Databricks SQL it can also refer to the alias of an aggregate.
Use WHERE for row-level conditions (for example `order_date >= '2026-01-01'`) and HAVING for group-level conditions.
W: HAVING after GROUP BY: it is evaluated once per group after the sums are computed, so the condition on the total order value is allowed there.
X: B=Alias in WHERE: WHERE runs before the SELECT list is computed, so the alias total and the aggregate behind it are not available to it.
C=GROUP BY before FROM: clause order is fixed by the syntax; this is a syntax error and does not change when WHERE is evaluated.
D=Parentheses around the table: they do not change the evaluation order of WHERE; the aggregate in WHERE would still be rejected.
T: Row filters go in WHERE (before grouping); conditions on aggregates go in HAVING (after grouping).

@ DBX-DAA D6 T6.1 applied use-case
S: An analyst is building an AI/BI dashboard where six charts on two pages all show different views of the same sales data. The analyst wants to define the query logic once and keep every chart consistent. What is the best approach?
A: Define one dataset on the Data tab and point all six visualization widgets at that dataset
B: Write six separate datasets with copied SQL so that each widget has its own private query
C: Save the SQL as a notebook cell and let each widget read the notebook output when it renders
D: Create one visualization and take a screenshot of it for each of the other five pages
K: A
G: ## Datasets and widgets
An AI/BI dashboard has two parts. The **Data** tab holds the datasets: SQL queries (or a table, view or metric view) that define the data. The **canvas** holds pages with widgets such as visualizations, filters, text and images. A widget does not contain its own query; it points to a dataset and chooses fields from it.
Because many widgets can share one dataset, a change to the dataset (a corrected column or an extra filter) flows to every chart that uses it. Datasets travel with the dashboard when it is shared, imported or exported.
W: One shared dataset: all six widgets read the same query result, so the logic is written once, stays consistent and is edited in one place.
X: B=Six copied datasets: each copy can drift when someone edits only one of them, which is exactly the inconsistency to avoid, and the dashboard carries needless duplicate queries.
C=Notebook output: dashboard widgets read dashboard datasets, not the output of notebook cells. A notebook cell is not a data source for them.
D=Screenshots: an image is static and has no connection to data, so it cannot filter, refresh or stay consistent with the dataset.
T: Define datasets once on the Data tab and reuse them across widgets and pages.

S: A dashboard dataset holds a few thousand rows and viewers only need to narrow it by customer segment. A teammate proposes a query parameter for the segment. What is the better design and why?
A: A parameter, because it is the only way to make a dashboard interactive for viewers
B: A parameter, because field filters cannot be changed by viewers after publishing
C: A field filter on the segment column, which small datasets can apply in the browser without rerunning the query
D: A widget-level filter, because it lets viewers pick the segment on each individual chart
K: C
G: ## Field filters versus parameters
- A **field filter** is applied to a dataset field without modifying the dataset. For relatively small datasets the filter is applied in the browser, so no query rerun is needed. Field filters also cascade by default: options in other filters update to compatible values. On large datasets Databricks adds the predicate to the query instead.
- A **parameter** substitutes a value into the query at runtime, so the query reruns for every change. It is more flexible: the condition can sit in a subquery or before a join, which can reduce processed data on large inputs.
For a small dataset and a simple category filter, the field filter is the faster and simpler choice.
W: Field filter: with a few thousand rows the filtering happens in the browser, viewers get instant interaction, and no SQL needs changing.
X: A=Only way to be interactive: field filters, cross-filtering and others also provide interactivity. A parameter is one option.
B=Viewers cannot change field filters: interactive field filters are changeable by viewers; widget-level filters are the fixed ones.
D=Widget-level filter: these are static and set by the author, so viewers cannot choose a segment with them.
T: Small data, simple narrowing: field filter; filtering before a join or inside a subquery on large data: parameter.

@ DBX-DAA D6 T6.3 advanced use-case
S: A dashboard author wants a drop-down of customer segments that automatically includes new segments as they appear in the data. The drop-down must set a parameter in the sales dataset. Which design is recommended?
A: Hardcode the segment names in the sales dataset query so that the parameter checks them
B: Add a text entry filter and ask viewers to type the segment name exactly as it appears
C: Use a global filter on the sales dataset's segment field, with no parameter in the sales query
D: Create a dedicated dataset with SELECT DISTINCT segment and a filter widget that uses that field and the parameter
K: D
G: ## Query-based parameters
A query-based parameter gives viewers a list of values from a query. The author:
- creates a dataset whose result is just the list of possible values (for a dynamic list, `SELECT DISTINCT segment FROM ...`; new values appear automatically; a static list can be built from `VALUES`)
- writes the sales dataset query with a parameter
- configures one filter widget with the list dataset's field and the parameter
Databricks recommends a dedicated dataset for the list, because a selection made on a dataset that is also used by other visualizations modifies all connected queries.
W: Dedicated DISTINCT dataset plus a filter on the field and parameter: the list updates itself as new segments appear, and the selection feeds the parameter without touching other charts.
X: A=Hardcoded names: this is a static list. New segments would not appear unless someone edits the query.
B=Text entry filter: viewers must type exact values and nothing lists the existing segments, so it is not a drop-down.
C=Global filter without a parameter: it filters on a field after the query, which differs from setting the parameter that the question specifies.
T: Dynamic drop-down for a parameter: separate DISTINCT dataset, one filter widget bound to its field and to the parameter.

@ DBX-DAA D6 T6.4 applied use-case
S: An analyst publishes an AI/BI dashboard of regional sales for managers who have no access to the underlying Unity Catalog tables. The managers should be able to view the numbers. Which publishing setting does the analyst choose?
A: Individual data permissions, so each manager's own table privileges control the results
B: Share data permissions, so that viewers run queries with the publisher's data permissions
C: Individual data permissions with CAN MANAGE for every manager on the dashboard
D: Draft sharing, because draft dashboards always run queries with the publisher's credentials
K: B
G: ## The two publishing options
When you publish, you choose how queries run.
- **Share data permissions** (default): viewers run queries with the publisher's data permissions. They can see the dashboard without direct access to the tables. This can expose data to users who have not been granted it, so use it deliberately.
- **Individual data permissions**: each viewer runs queries with their own credentials, so they need access to the underlying data. Compute access is always provided by the publisher's credentials.
Draft dashboards always apply the viewer's own data permissions, even if the published version uses shared permissions.
W: Share data permissions: managers without table access can still see results, because the queries run as the publisher.
X: A=Individual data permissions: managers lack table access, so their queries would return errors or nothing.
C=Individual with CAN MANAGE: dashboard permissions do not grant data permissions. Managing the dashboard would not let them read the tables.
D=Draft sharing: the viewer's data permissions always apply to drafts, so this is the opposite of the claim.
T: Viewers without data access: share data permissions; row-level or per-user security: individual data permissions.
