@ DBX-DAA D6 T6.5 applied use-case
S: A published AI/BI dashboard is slow to open on Monday mornings because dozens of managers open it at the same time and every dataset query runs from scratch. The dashboard is published with shared data permissions. What should the dashboard author set up to improve the first-load time for all viewers?
A: A schedule that runs before the managers arrive, so the dataset queries execute in advance and fill a shared result cache
B: A second copy of the dashboard for each manager, each published with individual data permissions and its own warehouse
C: A filter on every page that forces viewers to pick a date range before any of the dataset queries are allowed to start
D: A dataset change that adds ORDER BY to each query so the warehouse can sort results ahead of time and keep them for viewers
K: A
G: ## What a dashboard schedule does
A schedule on an AI/BI dashboard is a recurring update. On each run, all the SQL that defines the datasets is executed on the chosen cadence (frequency, start time and time zone). The results fill the query result cache, so a viewer who opens the dashboard later is served from the cache instead of waiting for the warehouse to compute every dataset.
## Shared versus individual data permissions
- With **shared data permissions** (the dashboard runs with the publisher's credentials), a scheduled update fills a **shared cache** that every viewer benefits from.
- With **individual data permissions**, each viewer's results are cached for that viewer only, so a schedule helps that person only if they take part in it.
Besides keeping data fresh, a schedule reduces repeated query load and warehouse cost, because the same results are reused.
Example: a schedule at 06:30 on weekdays means the 08:00 rush reads results computed an hour and a half earlier.
W: Schedule that warms the shared cache: the dataset queries run once at a time the author chooses and the shared result cache serves all viewers, so the Monday rush does not recompute anything.
X: B=Copies per manager: duplicating the dashboard multiplies the queries run against the warehouse and gives each copy its own individual cache, which is the opposite of sharing one set of cached results.
C=Mandatory filter: forcing a date selection does not run anything in advance. Each viewer still starts queries from scratch, and the extra choice only delays seeing the first chart.
D=ORDER BY in datasets: sorting is part of the query itself and does not store results anywhere. Sorting can even add work, and the next viewer still pays the full execution time.
T: A dashboard schedule runs the dataset queries ahead of time; with shared data permissions the cached results help every viewer.

@ DBX-DAA D6 T6.5 applied troubleshooting
S: A dashboard is published with individual data permissions, so each viewer runs queries with their own identity. An analyst with CAN VIEW access wants her own results to be fresh when she opens the dashboard at 09:00, but she does not want any email. What should she choose on an existing schedule of the dashboard?
A: Inactive for me, because refreshing the cache is a task that only the dashboard owner may perform for everyone
B: Refresh data for me & email, and then filter the incoming messages in her mailbox so the daily snapshots are not shown
C: Refresh data for me, which triggers cache refreshes for her without sending her dashboard notifications
D: Delete the schedule and recreate it with a new name, because refresh-only options cannot be added to an existing schedule
K: C
G: ## Refresh-only participation
When a dashboard uses individual data permissions, each viewer has a personal result cache. A viewer with at least CAN VIEW can join an existing schedule and pick how to take part:
- **Inactive for me**: she does not take part in that schedule.
- **Refresh data for me**: her own cache is refreshed on each run, with no notification (refresh-only).
- **Refresh data for me & email**: the cache is refreshed and she also receives the snapshot by email.
Refresh-only schedules give the performance benefit without any inbox traffic.
W: Refresh data for me: this is the refresh-only choice, so the schedule runs the dataset queries under her identity and refreshes her cache, and nothing is sent to her.
X: A=Inactive for me: that option opts her out of the schedule, so her cache is not warmed. Viewers can refresh their own cache; it is not reserved for the owner.
B=Refresh and email: it does refresh the data but also sends the PDF snapshot every time. A mailbox rule hides the symptom while the sends still happen, and a refresh-only choice already exists.
D=Delete and recreate: deleting a schedule also removes its subscriber settings for everyone, and it is unnecessary because every existing schedule offers the refresh-only choice to viewers.
T: With individual data permissions, viewers join a schedule as "Refresh data for me" to keep their own cache warm without notifications.

@ DBX-DAA D6 T6.5 applied definition
S: An analyst creates a dashboard schedule that repeats every 4 hours with a start time of 15:10. Which description of the runs follows how Databricks applies a defined start time?
A: The cadence begins at 15:10 each day, runs every 4 hours until 15:09 the next day, and then resets to 15:10
B: The first run is at 15:10, and later runs fall at the next full hour that is a multiple of 4, such as 16:00 and 20:00
C: The cadence runs only between 15:10 and midnight, and the dashboard is not updated again until the next start time
D: The first run is at 15:10 and it is the only run, because a defined start time turns a schedule into a one-time update
K: A
G: ## Start time and cadence
In the schedule dialog you choose a frequency, a start time and a time zone (or edit Quartz cron syntax directly). For a schedule with a defined start time, the cadence begins at that time **each day**.
Example: every 4 hours starting at 15:10 gives 15:10, 19:10, 23:10, 03:10, 07:10 and 11:10, continuing until 15:09 the following day. The cadence then resets and begins again at 15:10. Run times therefore do not drift from day to day, and a dashboard fed by a daily 14:00 load can reliably be refreshed at 15:10.
W: Daily anchor at the start time: the 4-hour cadence is counted from 15:10 and restarts at 15:10 each day, so the minute and hour of every run stay the same from day to day.
X: B=Aligned to the hour: the schedule uses the minute you set, so runs fall at :10 past the hour, not at full hours.
C=Evening only: the cadence continues through the night until 15:09 the next day, so the early-morning hours are covered too.
D=Single run: a schedule is recurring; it keeps running at its cadence until it is paused or deleted, and it can be edited at any time.
T: A schedule with a start time repeats at its interval from that time each day, then resets to the start time the next day.

@ DBX-DAA D6 T6.6 applied use-case
S: A support lead wants an email when the open ticket count exceeds a limit, and wants it repeated until someone brings the count back under the limit, not only on the first breach. Where is this configured in a Databricks SQL alert?
A: In the Notifications section, by setting a notification frequency that repeats the message until the alert returns to OK
B: In the alert query, by adding a loop that selects the same row again on each run until the value falls below the limit
C: In the dashboard schedule of the ticket dashboard, by adding the support lead as a subscriber with a repeat count
D: In the SQL warehouse settings, by setting a retry policy that sends failed statements again until they finish
K: A
G: ## Notifications on an alert
A Databricks SQL alert evaluates its condition on its own schedule. When the state becomes TRIGGERED, the recipients in the **Notifications** section (users or notification destinations) are alerted.
- By default a message is sent when the condition is met.
- You can optionally set a **notification frequency** so the message repeats until the alert returns to `OK`.
- In **Advanced settings**, **Notify on OK** sends a message when the alert recovers, and a **template** customizes the message.
The query only returns data; reminders are a property of the notification, not of the SQL.
W: Notification frequency: the repeat interval is a notification setting of the alert, so the lead is reminded on a regular basis until the count is back under the limit.
X: B=Loop in the query: the query only returns data for the condition. It has no control over how often recipients are messaged.
C=Dashboard subscriber: dashboard schedules send snapshots of a dashboard. Alert recipients and repeat behavior are configured on the alert itself.
D=Warehouse retry policy: a warehouse runs statements and does not decide who is notified or how often when a threshold is exceeded.
T: Use the notification frequency in the alert to repeat messages until the alert returns to OK.

@ DBX-DAA D6 T6.6 applied definition
S: A SQL alert checks whether failed_orders is above 50. On Tuesday the last evaluation returned 80. On Wednesday the scheduled evaluation returns 30. What is the status of the alert in the alert list after Wednesday's run?
A: The status remains TRIGGERED until a user acknowledges it in the alert, because a triggered alert never resets by itself
B: The status is OK, because OK only means the latest evaluation did not meet the condition, even though the alert fired earlier
C: The status is ERROR, because a value that moves back below the threshold is treated as a failure of the alert query
D: The status is UNKNOWN, because the value changed since the previous run and the alert cannot tell which value counts
K: B
G: ## Alert states
Alerts in the current Databricks SQL alerts resolve each evaluation to one of three states:
- `TRIGGERED`: on the most recent execution the checked value met the condition and threshold.
- `OK`: on the most recent execution it did **not** meet the condition. This does not mean that the alert never fired before.
- `ERROR`: an error occurred during evaluation, such as a failing query.
The old `UNKNOWN` state belongs to legacy alerts and does not exist in the current ones.
Because the state follows each evaluation, an alert goes back to OK automatically when the metric recovers.
W: OK reflects only the latest evaluation: 30 is not above 50, so the state returns to OK on its own, while the alert history still shows the earlier triggered evaluation.
X: A=Needs acknowledgement: there is no acknowledgement step that holds an alert in TRIGGERED. The state is recalculated on every scheduled evaluation.
C=Treated as ERROR: ERROR is reserved for evaluation problems such as a query failure. A value that simply no longer meets the condition is a normal result.
D=UNKNOWN: that state existed only in legacy alerts. The current alerts resolve to OK, TRIGGERED or ERROR.
T: Current alert states are OK, TRIGGERED and ERROR; each evaluation sets the state again, so a recovered metric shows OK.

@ DBX-DAA D6 T6.6 applied use-case
S: An on-call analyst receives an alert email when daily failed orders exceed a limit, but nobody is told when the figure is back to normal, so the incident stays open for hours. What should be enabled so that recovery is also reported?
A: A dashboard schedule that refreshes the orders dashboard every minute and sends its PDF snapshot to the on-call analyst
B: The Notify on OK advanced setting of the alert, so that a message is sent when the alert returns to OK
C: A second alert on the same table with a limit of zero, so that it is triggered whenever orders are healthy
D: A larger SQL warehouse for the alert, because recovery messages are only sent from warehouses with enough capacity
K: B
G: ## Recovery notifications
By default an alert notifies when it is TRIGGERED. The alert's **Advanced settings** also contain:
- **Notify on OK**: sends a notification when the alert returns to `OK`, so recipients learn that the metric recovered.
- **Empty result state**: the status to use when the query returns no rows.
- **Template**: the notification message layout.
Recovery is therefore a setting on the same alert, with no second alert or dashboard needed.
W: Notify on OK: the alert sends a message on the transition back to OK, so the on-call analyst learns that the metric recovered without checking the alert page.
X: A=Minute-level dashboard schedule: this sends repeated snapshots of a dashboard whether or not anything changed, and it does not report an alert state change.
C=Second alert with a zero limit: this duplicates the rule in reverse and is hard to keep in step with the first alert; the existing alert already offers a recovery message.
D=Larger warehouse: warehouse size affects how fast the query runs, not whether a notification is sent on recovery.
T: Enable Notify on OK in the advanced settings to be told when an alert recovers.

@ DBX-DAA D6 T6.6 applied troubleshooting
S: An analyst has a saved query in the SQL editor that returns the daily failed order count. She wants to create an alert on it in the current Databricks SQL alerts, expecting to pick the saved query from a list. What applies?
A: She picks the saved query, and every later edit of that query changes the alert condition for all users automatically
B: She must first publish the query in a dashboard, because alerts can only read results from dashboard datasets
C: She writes or pastes the SQL into the alert editor, because each current alert owns its own query definition
D: She must convert the query into a SQL function in Unity Catalog, because alerts can only call registered functions
K: C
G: ## Each alert owns its query
In the current Databricks SQL alerts, an existing saved SQL query cannot be reused when creating an alert. Each alert has its own query definition, authored in the alert editor, where you can run it and use **Test condition** before saving. Legacy alerts, which could be built on saved queries, remain available side by side.
Consequently an edit to a query in the SQL editor does not change the condition of an alert; the alert's own SQL is edited in the alert.
W: Query written in the alert editor: the alert owns its query, so the analyst copies the SQL into it, then tests the condition and sets the schedule.
X: A=Pick a saved query: current alerts cannot reuse a saved query, and an alert has its own SQL that is not updated when a saved query changes.
B=Publish in a dashboard first: alerts run their own query on a SQL warehouse and do not read dashboard datasets.
D=Convert to a SQL function: alerts run ordinary SQL written in the alert; registering a Unity Catalog function is not required.
T: Current alerts own their query; a saved query cannot be picked from a list and its SQL must be entered in the alert.

@ DBX-DAA D6 T6.7 applied use-case
S: A finance analyst must show how monthly revenue developed over the last three years in an AI/BI dashboard, so that executives can see the trend and seasonal peaks at a glance. Which visualization fits best?
A: A pie chart with one slice for each month, because the slices show the share of every month
B: A line chart with the month on the x-axis and revenue on the y-axis
C: A word cloud sized by revenue, so the biggest months appear in larger text
D: A counter showing only the total revenue, with a comparison value from the prior year
K: B
G: ## Match the chart to the question
Choosing a visualization starts with the question being asked.
- **Change over time**: line charts (one or more metrics over time), area charts, and bar charts for discrete periods.
- **Parts of a whole**: pie charts show proportion between a few categories; they are not meant for time series.
- **Single headline number**: a counter, optionally with a comparison.
- **Relationship between two numbers**: scatter charts.
A three-year monthly series has 36 points in time order, which is a trend question.
W: Line chart: the ordered time axis makes the slope and recurring seasonal peaks visible, and several years can be drawn as separate lines for comparison.
X: A=Pie chart: pies show proportion and are not meant for conveying time series data. Thirty-six slices would also be impossible to compare.
C=Word cloud: text size hides exact values and loses the time order, so a trend cannot be read from it.
D=Counter: one number with a comparison shows a total, not the development over months, so the trend and seasonal peaks stay hidden.
T: Trends over time call for a line (or area) chart; pie charts show shares, not time series.

@ DBX-DAA D6 T6.7 applied use-case
S: A product analyst wants to understand how a signup flow loses users: visited the site, created an account, verified the email, completed the first order. The goal is to see at which step the largest share of users drops out. Which visualization is designed for this?
A: A funnel chart that has the step name as one field and the number of users as the value
B: A choropleth map with each step shown as a country and the user count as its color
C: A histogram of the user count, with a bin for each of the four steps in the flow
D: A box chart of the user count per step, so the quartiles of each step can be compared
K: A
G: ## Funnel charts
A funnel chart analyzes how a metric changes **across ordered stages**. You provide a `step` column and a `value` column, and the size of each stage reflects how many users reached it. The drop between two neighbouring stages is the conversion loss.
Other chart types answer different questions: histograms show how often values fall into ranges, box charts summarize the spread of a numeric column, and choropleth maps color geographic areas.
W: Funnel chart: stages are shown in order with a size proportional to the users reaching them, so the widest drop is visible immediately.
X: B=Choropleth map: it colors geographic localities such as countries or states by an aggregated value. A signup step is not a location.
C=Histogram: it plots the frequency of values in ranges (bins) of one numeric column, not the user count at named process stages.
D=Box chart: it summarizes the distribution of many numeric values per category with quartiles. Here every step has just one count, so there is no distribution to summarize.
T: Drop-off across ordered stages of a process is a funnel chart question.

@ DBX-DAA D7 T7.1 applied definition
S: A sales director asks what a Genie Agent (formerly called a Genie space) gives her team that an AI/BI dashboard does not. Which description is accurate?
A: It lets business users ask questions in natural language and get answers from governed data that analysts curated
B: It is a fixed set of visuals that the author builds in advance, so users can only change the filters that were published

G: ## What a Genie Agent is
A Genie Agent is the natural-language chat interface where business users ask questions of their data in Databricks. **Data analysts configure** each agent with Unity Catalog data, example SQL queries, instructions and trusted assets; **business users query** it through the chat UI. Answers are grounded in the organization's data and governed through Unity Catalog. (Genie Agents were formerly called Genie Spaces.)
A dashboard answers the questions its author foresaw, using fixed visuals with filters. A Genie Agent lets users ask new questions in their own words, with the analyst's curated context steering the SQL that is generated.
W: Natural-language questions on curated, governed data: analysts set up tables, instructions and examples once, and business users then get answers without writing SQL.
X: B=Fixed visuals: this describes a dashboard, whose pages and widgets the author builds beforehand. A Genie Agent builds answers for questions asked at chat time.

D=Catalog object that copies data: a Genie Agent reads Unity Catalog tables where they are; it does not copy tables to new storage or change how they are stored.
T: A Genie Agent is a curated natural-language interface over governed data, configured by analysts and used by business users.

@ DBX-DAA D7 T7.1 applied troubleshooting
S: Two users ask the same question in one Genie Agent. One is a regional manager who has SELECT only on the EMEA rows of the sales table through a row filter, the other is a global analyst with access to all rows. Both users have no permission on the SQL warehouse itself. What happens?
A: The query fails for both users, because every Genie user needs CAN USE permission on the warehouse of the agent
B: Both users see all rows, because the data access of an agent follows the credentials of the author who created it
C: Both users see only EMEA rows, because the agent applies the most restrictive access found among the people it is shared with
D: Each user gets an answer based on their own Unity Catalog permissions, because warehouse access comes from embedded credentials
K: D
G: ## Two separate credentials
A Genie Agent uses two kinds of access:
- **Compute**: the SQL warehouse is reached with the **embedded credentials** of the author who configured the warehouse in the agent, so end users do not need warehouse permissions.
- **Data**: always evaluated with **each end user's own Unity Catalog identity**. Row filters and column masks defined in Unity Catalog are enforced per user. A question about data a user cannot access produces an empty response.
Each query is also attributed to the end user in query history and on the agent's monitoring page.
W: Embedded compute credentials plus per-user data access: both users can run queries without warehouse rights, and the row filter returns EMEA rows to the manager and all rows to the analyst.
X: A=CAN USE for everyone: the author needs at least CAN USE on the warehouse to set it, but consumers do not, as the author's embedded credentials grant warehouse access only.
B=Author's data access: the author's credentials are used for the warehouse only. Using them for data would bypass governance, and Genie does not do this.
C=Most restrictive among users: there is no intersection of all recipients. Access is calculated for the person asking, so the analyst keeps full visibility.
T: In Genie, the warehouse uses the author's embedded credentials, but data access is always the asking user's own Unity Catalog permissions.

@ DBX-DAA D7 T7.1 applied definition
S: Which combination of requirements must be met before an analyst can build a working Genie Agent on the company's sales data?
A: The data is stored in Unity Catalog, a pro or serverless SQL warehouse is available, and the author has SELECT on the data and CAN USE on the warehouse
B: The data is exported to CSV files in a workspace folder, a classic all-purpose cluster is running, and the author has the workspace admin role
C: The data is in a Delta table outside Unity Catalog, a classic SQL warehouse is selected, and the author has CAN MANAGE on every user in the workspace
D: The data is replicated into a materialized view for every question, a job cluster runs nightly, and the author owns the metastore

G: ## Technical requirements
- **Unity Catalog**: the data must be registered in Unity Catalog (tables, views or metric views).
- **Compute**: a **pro or serverless** SQL warehouse; serverless is recommended for performance. The creator needs at least CAN USE on the selected warehouse.

G: ## Prompt matching
User questions are conversational and may contain misspellings or words that differ from the data. **Prompt matching** helps Genie match columns and values to the question:

- **Entity matching** supplies curated lists of distinct values for columns where users name specific entries (states, product categories), so user wording can be linked to stored values.
