@ DBX-DAA D7 T7.3 applied use-case
S: An analyst owns a Genie Agent for the sales team. A colleague should be able to add example SQL queries and edit instructions, but must not be able to change who has access or delete the agent. Which permission level on the Genie Agent fits?
A: CAN RUN, because it lets people ask questions and also edit the instructions that guide the answers
B: CAN VIEW, because it adds read access to instructions and lets the holder modify them in place
C: CAN EDIT, because it covers instructions, sample questions and included tables but not permissions
D: CAN MANAGE, because it is the only level that can change instructions and add example queries
K: C
G: ## Genie Agent permission levels
A Genie Agent has its own access control list with four levels, from least to most privileged: CAN VIEW, CAN RUN, CAN EDIT and CAN MANAGE.
- **CAN VIEW and CAN RUN** give the same abilities for a Genie Agent: see it in the list, ask questions, give response feedback and upload files to a conversation.
- **CAN EDIT** adds the authoring tasks: add or edit instructions and sample questions, and add or remove included tables.
- **CAN MANAGE** adds administration: monitor the agent, modify permissions, delete the agent and view other users' conversations.
The creator of an agent automatically gets CAN MANAGE.
W: CAN EDIT: it is the level that unlocks instructions, example queries and table selection, while permission changes and deletion stay with CAN MANAGE.
X: A=CAN RUN: this level only lets a person ask questions, give feedback and upload files. It cannot change instructions or example queries.
B=CAN VIEW: viewers can open the agent and ask questions, but cannot edit anything. It grants the same abilities as CAN RUN for a Genie Agent.
D=CAN MANAGE: it also allows editing, but it is not the only level that does, and it would hand over permission changes and deletion, which the colleague must not get.
T: Use CAN EDIT for co-authors of a Genie Agent; CAN MANAGE adds permissions, monitoring and deletion.

@ DBX-DAA D7 T7.3 applied troubleshooting
S: A team lead shares a Genie Agent with the group "all account users" at CAN RUN. A finance employee opens it, asks a question and gets no data back, although the SQL warehouse is running. The employee has no grants on the finance schema. What is the correct fix?
A: Grant the employee CAN USE on the agent's SQL warehouse, because the question needs warehouse permission first
B: Grant the employee SELECT on the Unity Catalog tables used by the agent, because data access is checked per user
C: Raise the group's agent permission to CAN MANAGE, because CAN RUN does not allow queries on data
D: Ask the agent author to share the author's own SELECT privileges by adding the employee to the agent
K: B
G: ## Sharing does not grant data access
A Genie Agent separates three kinds of access:
- **Agent access**: an ACL level (at least CAN VIEW or CAN RUN) on the agent itself.
- **Compute**: the SQL warehouse is reached with the embedded credentials of the author who configured it, so end users do not need warehouse permissions.
- **Data**: always evaluated with the asking user's own Unity Catalog identity. Users need at least `SELECT` on every data object the agent uses, and they only ever see data they are authorized to see.
Sharing an agent with a broad group therefore never exposes data to people who lack grants. The missing piece is a Unity Catalog grant, for example `GRANT SELECT ON TABLE finance.sales.orders TO finance_team`.
W: SELECT on the tables: the agent is shared correctly, the warehouse works through embedded credentials, and only the Unity Catalog grant on the data is missing for this user.
X: A=Warehouse CAN USE: end users reach the warehouse through the author's embedded credentials, so no warehouse permission is needed for them. The author needs CAN USE, not every user.
C=CAN MANAGE for the group: CAN RUN already lets people ask questions. Higher agent levels add authoring and administration, and none of them grants rights on Unity Catalog data.
D=Borrowing the author's SELECT: agents never use the author's data permissions for other users. Data access is evaluated per asking user, which is what keeps governance intact.
T: Sharing a Genie Agent grants agent access only; each user still needs SELECT on the data in Unity Catalog.

@ DBX-DAA D7 T7.3 applied use-case
S: A product team wants to show an existing Genie Agent inside its internal customer portal, so that portal users can ask data questions without opening Databricks. The author has CAN MANAGE on the agent. What else must be in place?
A: A workspace admin has to configure the allowed embedding surfaces, and portal users need access to the agent and its data
B: The agent must be cloned into every portal user's folder first, since embedded agents cannot be shared with other people
C: A SQL alert must be attached to the agent, because the portal can only receive content that was pushed by an alert
D: The portal needs the agent's embedded warehouse credentials copied into its code so that the iframe can authenticate to the warehouse
K: A
G: ## Embedding a Genie Agent
A Genie Agent can be placed as an **iframe** in an external website or application. Three roles are involved:
- **Workspace admin**: configures the allowed embedding surfaces (the trusted domains where embedding is permitted) in the workspace settings.
- **Agent author**: needs at least CAN MANAGE on the agent and generates the iframe code from the Share dialog.
- **End users**: need explicit access to the agent and to the underlying data assets. Users who are not signed in to Databricks are asked to authenticate.
Embedded users can send prompts but cannot edit the agent. Adding `allow="clipboard-write"` to the iframe lets them copy CSV data and conversation links. Only trusted domains belong on the allowed list.
W: Admin-approved surfaces plus user access: embedding works only on domains an admin allowed, and each portal user still needs the agent and Unity Catalog data permissions.
X: B=Clone per user: cloning creates an independent copy and is not part of embedding. The same agent can be embedded for many users who hold access to it.
C=SQL alert: alerts notify about query thresholds. They have nothing to do with showing a chat interface inside another application.
D=Copied warehouse credentials: embedded compute credentials stay inside Databricks and are never pasted into application code. Users authenticate to Databricks themselves.
T: Embedding needs an admin-approved surface, an author with CAN MANAGE, and end users who hold both agent and data access.

@ DBX-DAA D7 T7.3 applied use-case
S: A company builds a scheduled backend service that sends questions to a Genie Agent through the Genie API. No person is present to sign in with a browser. Which setup follows the documented guidance?
A: Authenticate as a service principal with OAuth M2M, and give it CAN VIEW on the agent plus SELECT on the data
B: Embed the agent as an iframe and let the service read the answers from the rendered page of the portal
C: Use the personal access token of the agent author for every call so that all users get the same answers
D: Share the agent with all account users at CAN MANAGE, then call the API without any credentials at all
K: A
G: ## Calling Genie programmatically
The Genie conversation API lets an application send prompts to an agent in Chat mode or Agent mode. Rules that matter for analysts and admins:
- The caller needs at least **CAN VIEW** on the agent and at least `SELECT` on the Unity Catalog objects the agent uses. Responses contain only data the caller may access.
- Where a person with a browser is present, use **OAuth for users (U2M)**. Where browser sign-in is not possible, use a **service principal** with **OAuth M2M**. The service principal must hold permissions on the required data and SQL warehouses.
Management APIs for creating or updating agents need more: the Databricks SQL entitlement, CAN USE on a pro or serverless warehouse, and CAN EDIT on an existing agent.
W: Service principal with OAuth M2M: it authenticates without a browser, and CAN VIEW plus SELECT satisfy the documented minimum for sending prompts.
X: B=Scraping an iframe: an embedded agent is for people to use in a page. A backend service should call the API rather than read rendered content.
C=Author's token for all calls: this attributes every question to one person and breaks per-user governance. A service principal gives a dedicated, auditable identity.
D=No credentials: every API call must authenticate. Broad CAN MANAGE sharing is not needed to send prompts and would be far more access than required.
T: Headless Genie API clients use a service principal with OAuth M2M plus CAN VIEW on the agent and SELECT on the data.

@ DBX-DAA D7 T7.3 applied use-case
S: A team keeps its Genie Agents together in one workspace folder and wants all agents in it to be usable by the support group without sharing each one separately. Which statement is true about how Genie Agents handle permissions?
A: Agents ignore folders, so each agent must be shared individually, and folder permissions have no effect on agent access

New Genie Agents are saved to the creator's user folder by default. Like other workspace objects, they **inherit permissions from their enclosing folder**, so a team can use its workspace folder structure to share many agents at once. You can also share one agent with named users or groups (including all account users) at CAN MANAGE, CAN EDIT, CAN RUN or CAN VIEW, and copy a link to it from the Share dialog.
Unity Catalog grants are a separate layer: they decide which data the user can read once the agent is open.
W: Folder inheritance: placing agents in a shared folder gives the support group their access level through the folder, with no need to share each agent one by one.

@ DBX-DAA D7 T7.4 applied use-case
S: Users of a Genie Agent click "Fix it" on many answers about fiscal quarters and add comments. The analyst expects the agent to behave better next week without any further work. What actually happens?
A: Genie retrains itself nightly on the comments, so repeated feedback on one topic changes its answers automatically

G: ## Feedback is a signal, not a fix
Each Genie response asks "Is this correct?" with three choices: **Yes**, **Fix it** (flag as incorrect, optionally pick a common issue or explain, then resubmit or just submit) and **Request review** (flag for a manual review with an optional comment).
Editors can see the feedback and flagged responses. **The agent's behavior does not change based on user feedback alone.** Databricks recommends encouraging feedback and then using it to improve context: example SQL queries for repeated misses, SQL expressions for business terms such as a fiscal-quarter definition, and clearer metadata.

W: Feedback as input to the analyst: it shows where answers fail, but the agent only improves once someone adds instructions, examples or expressions.

C=Tables dropped by ratings: ratings never remove tables. Included tables are changed only by users with CAN EDIT or higher.
D=Private feedback: flagged responses are visible to editors and to users with CAN MANAGE on the monitoring page, so the owner can act on them.
T: Genie feedback does not change the agent by itself; use it to decide which instructions or example queries to add.

@ DBX-DAA D7 T7.4 applied use-case
S: An analyst adds benchmark questions to a Genie Agent but leaves the SQL Answer field empty for most of them. After a run, the accuracy value is not shown and most rows are marked for review. Why?
A: Only questions with a SQL Answer are scored automatically; the others need manual review before accuracy is reported
B: Benchmarks without SQL are skipped by the run, so they are removed from the list as soon as the run completes
C: The run needs a pro warehouse for questions without SQL, which is a different type from the one the agent uses
D: Genie scores questions without SQL by comparing them to the text instructions, which takes a full week to finish
K: A
G: ## How benchmarks are scored
Benchmarks are a set of test questions (up to 500 per agent) that you run to measure overall accuracy. In **Chat mode** (the default) Genie generates SQL for each question and the result is compared with the **SQL Answer** you provided, which can be a query or a Unity Catalog SQL function. Only questions with a SQL Answer can be assessed automatically; the others carry a "Manual review needed" label and the accuracy figure appears only after a reviewer rates them Good or Bad.
In **Agent mode** an LLM judge grades responses, guided by an optional evaluation note. Users with at least CAN EDIT can run benchmarks.
W: SQL Answer needed for automatic scoring: without a reference query Genie cannot judge a result, so the question waits for a manual Good or Bad rating.
X: B=Skipped and removed: such questions still run and appear in the evaluation. They are flagged for manual review, not deleted.
C=Different warehouse type: the run uses the agent's configuration. The missing SQL Answer, not the warehouse, is the reason scoring cannot be automatic.
D=Compared with instructions: scoring compares result sets with the SQL Answer. Text instructions are not a ground truth, and no week-long process exists.
T: Give each Chat mode benchmark question a correct SQL Answer so accuracy is calculated automatically.

@ DBX-DAA D7 T7.4 applied tradeoff
S: An analyst designs benchmarks for a Genie Agent that answers revenue questions. Users phrase the same question in many ways. Which design follows Databricks recommendations?
A: One benchmark per question, because repeated questions inflate the accuracy value and hide real weaknesses
B: Only the most formal phrasing of each question, because informal wording is never expected from business users
C: Several phrasings of the same question, each using the same SQL Answer, so wording variations are tested
D: One phrasing with a long evaluation note, because phrasing variations are checked by the SQL warehouse itself
K: C
G: ## Testing phrasing variations
Benchmark questions should reflect the **different ways users phrase** common questions, because Genie interprets natural language and wording can change the SQL it writes. Databricks recommends adding **multiple phrasings of the same question with the same example SQL**; most agents should include between two and four phrasings. Benchmark questions run as **new conversations**, without the context of a threaded chat, and use the instructions, example SQL and functions defined in the agent.
Chat mode rates a result Good when it matches the SQL Answer result (even if sorted differently), and Bad for an empty result, an error, extra columns or a different single value.
W: Several phrasings, same SQL Answer: it checks whether the agent is robust to wording, and every phrasing is graded against one trusted result.
X: A=One benchmark per question: a single wording tests only one path. Varied phrasings expose cases where small wording changes lead to different SQL.
B=Formal wording only: real users write casually, so a formal-only set would report accuracy that business users never see.
D=Single phrasing with note: the evaluation note guides an LLM judge in Agent mode. It does not test alternate wording, and the warehouse does not interpret phrasing.
T: Add two to four phrasings per common question, all pointing to the same SQL Answer, when building Genie benchmarks.

@ DBX-DAA D7 T7.4 applied troubleshooting
S: A benchmark expects a result with the columns region and total_revenue. Genie's generated SQL returns the same rows but adds a third column, avg_order_value. How does a Chat mode run rate this response?
A: Good, because every value in the expected columns matches and extra columns are ignored by the comparison
B: Good, because Chat mode rates only the generated SQL text, which is similar enough to the SQL Answer
C: Bad, because a result set with extra columns compared to the SQL Answer does not count as a match
D: Manual review needed in every case, because Chat mode cannot compare result sets that differ in shape
K: C
G: ## Chat mode ratings
Chat mode compares Genie's result with the result of the SQL Answer. Rated **Good**: exactly matching SQL, an exactly matching result set, the same data sorted differently, or numeric values that round to the same four significant digits. Rated **Bad**: SQL that returns an empty result or an error, a result set with **extra columns**, or a single-cell result that differs.
Chat mode compares up to 5,000 rows, so for large results add `ORDER BY` to both the SQL Answer and the expected output; otherwise a matching result can be rated Bad because of truncation. A Bad rating comes with an explanation of the mismatch, and a reviewer can edit the label or use Update ground truth.
W: Extra column means Bad: the result set no longer equals the expected one, so the response is rated Bad and the explanation names the mismatch.
X: A=Extra columns ignored: the documented criteria list extra columns as a reason for a Bad rating, not as an allowed difference.
B=SQL text similarity: the rating looks at results, and a result with the same data in a different order is Good even when the SQL text differs.
D=Always manual review: manual review applies when Genie cannot assess correctness or when no exact match is found for a case that has a SQL Answer. A shape mismatch has a defined Bad rating.
T: In Chat mode, extra columns, empty results, errors and different single values are Bad; reordered rows are still Good.

@ DBX-DAA D8 T8.1 applied definition
S: A retailer's analytics model has one table of sales transactions with numeric measures and foreign keys, joined directly to flat tables for product, store, customer and date. Which data model is this?
A: A data vault, because the central table is linked to several descriptive tables by keys
B: A third normal form model, because each table stores one kind of business entity
C: A star schema, with a central fact table surrounded by denormalized dimension tables
D: A snowflake schema, because the dimensions are connected to the central table by keys
K: C
G: ## Star schema
A **star schema** has a central **fact table** holding events and numeric measures (quantity, amount) plus foreign keys, surrounded by **dimension tables** holding descriptive attributes (product name, store city, month). Dimensions are typically **denormalized**: each one is a single flat table, so a query needs one join per dimension.
Typical query: `SELECT d.month, p.category, SUM(f.amount) FROM sales f JOIN dim_date d ON ... JOIN dim_product p ON ... GROUP BY ALL`.
The shape is easy for analysts and BI tools to understand, which is why it is the common design for the reporting layer.
W: Fact table with flat dimensions: the single central table joined directly to denormalized dimension tables is the defining shape of a star schema.
X: A=Data vault: a vault is built from hubs, links and satellites for business keys, relationships and history. A fact table with flat dimensions is not a vault.
B=Third normal form: 3NF removes redundancy by splitting data into many related entity tables, and it does not center on a fact table of measures.
D=Snowflake schema: it also has a fact table, but its dimensions are normalized into further sub-tables. Here the dimensions are flat, so this is not a snowflake.
T: A fact table joined directly to flat, denormalized dimension tables is a star schema.

@ DBX-DAA D8 T8.1 applied definition
S: In a sales model, the product dimension was split into product, category and department tables, each linked to the next by a key, and the sales fact table links only to product. What is this design called, and what is the main trade-off?
A: A snowflake schema; it removes repeated attribute values but needs more joins in queries
B: A star schema; it removes repeated values but forces a full copy of the fact table per dimension
C: A data vault; it keeps history in satellites but cannot be queried by BI tools at all
D: A flat wide table; it needs no joins but stores one extra copy of every dimension row for each fact
K: A
G: ## Snowflake schema
A **snowflake schema** normalizes the dimensions of a star schema: a dimension is split into several related tables (product to category to department). Benefits are less repeated text and easier maintenance of a hierarchy, such as renaming a category in one row. The cost is **more joins** for every query that wants a higher level of the hierarchy, which makes SQL longer and can slow queries.
Databricks documentation notes that star and snowflake models both perform well because they have fewer joins than heavily normalized designs. For an analyst, the choice is usually star when simplicity and speed matter, snowflake when shared hierarchies must be maintained once.
W: Snowflake schema with more joins: dimension hierarchies are normalized into linked tables, which reduces redundancy but adds joins to reach category and department.
X: B=Star schema: a star keeps dimensions flat and denormalized. Splitting a dimension into chained tables is exactly what a star avoids, and nothing is copied per dimension.
C=Data vault: a vault uses hubs, links and satellites rather than chained dimension tables, and BI tools can query it, usually through views or marts.
D=Flat wide table: a wide table would combine everything into one table. Here the dimension is split into several tables, which is the opposite.
T: A snowflake schema normalizes dimensions into sub-tables, saving redundancy at the price of extra joins.

@ DBX-DAA D8 T8.1 applied definition
S: A data team models its integration layer with tables named hub_customer (one row per business key), link_customer_order (relationships between keys) and sat_customer_details (descriptive attributes with load timestamps). Which modeling technique is this?
A: A star schema, where hub tables hold measures and satellite tables hold the flat dimension rows
B: A snowflake schema, where link tables are the sub-dimensions of the customer dimension
C: A medallion layout, where hub, link and satellite are the names of the bronze, silver and gold layers
D: A data vault, which splits business keys, relationships and history into hubs, links and satellites
K: D
G: ## Data vault
**Data vault** is a modeling technique for integrating data from many source systems while keeping full history.
- **Hubs** store the unique business keys (customer id, order id).
- **Links** store relationships between hubs (a customer placed an order).
- **Satellites** store descriptive attributes and their changes over time, with load timestamps and record sources.
New sources and attributes can be added as new satellites without reworking existing tables, and history is preserved for audit. Analysts rarely query raw vault tables directly: they use views or a downstream dimensional model, such as a star schema.
W: Hubs, links and satellites: keys, relationships and history are stored separately, which is the structure of a data vault.
X: A=Star schema: a star has fact and dimension tables. Hubs hold business keys, not measures, and satellites are not flat dimensions.
B=Snowflake schema: links record relationships between business keys, not dimension hierarchies, so they are not sub-dimension tables.
C=Medallion layout: bronze, silver and gold describe data quality stages, not table roles. A vault is a modeling pattern that can sit inside those layers.
T: Hubs (keys), links (relationships) and satellites (history) make a data vault.

@ DBX-DAA D8 T8.1 applied tradeoff
S: A new lakehouse will serve dashboards and ad hoc SQL for business analysts. Which modeling guidance matches Databricks recommendations for such analytical workloads?
A: Use a heavily normalized third normal form model, because it keeps every attribute in exactly one table
B: Use a star or snowflake schema, which needs fewer joins and lets the optimizer skip data with file statistics
C: Use one table per source system and join them at query time, since joins are always cheap on Delta
D: Use a data vault in the reporting layer, because analysts need hubs and links for every dashboard
K: B
G: ## What Databricks recommends
For a new lakehouse, Databricks **recommends against a heavily normalized model such as 3NF**. Star and snowflake schemas perform well because standard queries need **fewer joins**, there are fewer keys to keep in sync, and wider tables with more fields in one place help the optimizer **skip large amounts of data using file-level statistics**.
The optimizer can struggle when one query joins many tables, and it may fail to skip files when a filter is on a field that lives in another table, which can cause a full table scan. Existing models can run on Databricks as they are; evaluate performance before re-architecting.
W: Star or snowflake: fewer joins, fewer keys to synchronize and better data skipping make dimensional models a good fit for dashboards and ad hoc SQL.
X: A=Heavy normalization: this is the pattern the documentation advises against for new lakehouses, because queries then join many tables.
C=One table per source joined at query time: this pushes many joins into every query, which the optimizer can struggle with, and joins are not always cheap.
D=Vault for reporting: a data vault suits integration and history. Dashboards are better served by a dimensional model that hides hubs and links.
T: For analytical workloads on Databricks, prefer star or snowflake schemas over heavily normalized models.

@ DBX-DAA D8 T8.1 applied troubleshooting

B: The insert succeeds, because primary and foreign key constraints are informational and not enforced
C: The second row is dropped silently, because Delta Lake deduplicates rows on the declared primary key
D: The table becomes read-only, because duplicate keys put the table into a quarantined state for repair
K: B
G: ## Informational constraints
In Databricks, **primary key and foreign key constraints are informational**: they document relationships between tables, which helps people and tools understand a star schema, and they may improve performance through query optimizations. They are **not enforced**, so duplicates in a primary key column do not raise an error.
**Enforced** constraints are different: `NOT NULL` and `CHECK` verify data before rows are added and fail the transaction when violated.
So for a dimension table the analyst should validate key uniqueness in the pipeline (for example with a `CHECK`-style test or a `COUNT(*) vs COUNT(DISTINCT customer_id)` query) rather than rely on the key declaration.
W: Informational keys: the declaration documents the model but does not stop duplicates, so both rows are written and uniqueness has to be checked elsewhere.
X: A=Enforced keys: only NOT NULL and CHECK constraints are enforced. Primary and foreign keys are informational for Delta tables in Unity Catalog.
C=Silent deduplication: Delta Lake does not remove rows because of a key declaration. Deduplication needs a MERGE or a query.
D=Read-only quarantine: there is no such state. Duplicate keys do not change the table's mode or availability.
T: Primary and foreign keys on Databricks are informational; use NOT NULL and CHECK for enforcement and test uniqueness yourself.

The medallion architecture organizes data into layers of increasing quality: bronze (raw), silver (validated) and gold (enriched). Following it is a recommended best practice, not a requirement.

@ DBX-DAA D8 T8.1 applied troubleshooting
S: Total revenue from a fact_sales and dim_customer join is higher than the sum on fact_sales alone. dim_customer keeps one row per customer version, with columns valid_from, valid_to and is_current, and the query has no filter on it. What is the most likely cause and fix?
A: Delta time travel returned older table versions, so the query must add VERSION AS OF to the fact table
B: The foreign key from the fact table to the dimension is enforced, so duplicated checks double the totals
C: The star schema is missing a snowflake sub-dimension, so the customer table must be normalized further
D: Several customer versions match each sale, so the join fans out rows; filter on is_current or the date range
K: D
G: ## Join fan-out with history dimensions
A fact table stores one row per event at a fixed **grain** (for example one row per order line). A dimension that keeps history (a slowly changing dimension with several rows per business key, marked with `valid_from`, `valid_to` or `is_current`) has **more than one row per customer**. Joining only on the customer key then matches each sale to every version, repeating the fact row and inflating `SUM(amount)`.
Fix: restrict the dimension to the right version, for example `JOIN dim_customer c ON f.customer_id = c.customer_id AND c.is_current = TRUE`, or match `f.sale_date BETWEEN c.valid_from AND c.valid_to` to get the version valid at the time of the sale. A check such as comparing `COUNT(*)` before and after the join reveals the fan-out.
W: Fan-out from multiple versions: each sale matches every customer version, so filtering to the current row or the valid date range restores one match per sale.
X: A=Time travel: no time travel clause is used, and the symptom appears in a plain join. Adding VERSION AS OF would not remove duplicate dimension matches.
B=Enforced foreign key: foreign keys are informational and are not enforced, and constraints never multiply rows in a query.
C=Missing sub-dimension: a snowflake design splits attributes into more tables and would add joins, not reduce duplicated matches.
T: A dimension with several rows per business key duplicates fact rows in a join; filter to the current or valid version.
