@ DBX-DAA D9 T9.1 applied troubleshooting
S: The data office published the SQL function `corp.utils.net_revenue` for analysts. The group `finance_analysts` has `USE CATALOG` on `corp`, `USE SCHEMA` on `corp.utils` and `SELECT` on `corp.sales.invoices`. A query that calls `corp.utils.net_revenue(amount, tax)` fails with a permission error. Which grant fixes it?
A: `SELECT` on the function, the privilege that lets a query call it in the same way that it reads a table
B: `EXECUTE` on the function, which can also be granted on the schema to cover current and future functions
C: `MODIFY` on the schema `corp.utils`, because running a function writes its result into that schema
D: `CREATE FUNCTION` on the schema `corp.utils`, since each caller must register a function before using it
K: B
G: ## Functions are securable objects
A Unity Catalog function (a SQL or Python UDF stored as `catalog.schema.function`) has its own privileges, separate from tables.
- To run a function you need `EXECUTE` on it, plus `USE SCHEMA` on its schema and `USE CATALOG` on its catalog.
- `SELECT` is a table and view privilege; it does not apply to functions.
- Like other privileges, `EXECUTE` granted on a schema or catalog inherits to current and future functions below it.
## How an analyst diagnoses it
When a query works without the function and fails with it, look for a missing `EXECUTE`. The usage privileges and `SELECT` on the table are already in place in this case.
W: EXECUTE on the function (or on its schema): it is the privilege that allows calling a function, and the usage privileges and table `SELECT` are already granted.
X: A=SELECT: it is a table and view privilege and does not apply to functions, so granting it on a function changes nothing.
C=MODIFY on the schema: `MODIFY` allows changing data of tables, and evaluating a function does not write anything into the schema.
D=CREATE FUNCTION: it lets a principal create new functions in the schema; callers never register a function that already exists, they only need to execute it.
T: Calling a Unity Catalog function needs EXECUTE on it plus the usage privileges on its catalog and schema.
V: Unity Catalog functions

@ DBX-DAA D9 T9.1 applied use-case
S: A supplier also uses Databricks with Unity Catalog, in another cloud region and account. The company wants to give the supplier's analysts read-only access to a gold table, with governance and auditing on both sides and no credential files to manage. Which setup fits?
A: A share with the table and a recipient created with the supplier's metastore sharing identifier, which the supplier mounts as a catalog
B: A share with the table and a recipient with a token, then send the supplier the credential file so analysts read it with pandas
C: Add the supplier's analysts as users of the company's workspace and grant them `SELECT` in the company's own metastore
D: A nightly job that copies the table into the supplier's metastore, and `SELECT` granted to the supplier's group on that copy
K: A
G: ## Databricks-to-Databricks sharing
OpenSharing has two protocols for Databricks providers.
- **Databricks-to-Open** is for recipients on any platform and uses a token or credential file.
- **Databricks-to-Databricks** is for recipients whose workspace is attached to a different Unity Catalog metastore. The recipient is defined by the sharing identifier of the recipient's metastore (`<cloud>:<region>:<uuid>`), so no token or credential file is needed.
The recipient creates a catalog from the share and reads it like any other catalog. Unity Catalog governance, auditing and usage tracking apply to both sides, and notebooks, volumes and models can be shared too.
W: Sharing identifier recipient: the share is bound to the supplier's metastore, read as a catalog, read-only, and both sides keep Unity Catalog governance and audit with no credential files.
X: B=Token recipient: it works for any client but uses a credential file the company has to distribute and rotate, and it lacks the Unity Catalog integration that a Databricks supplier can have.
C=Supplier as users: this mixes outside people into the company's own account and permissions and is not the sharing mechanism for another organization.
D=Nightly copy: it duplicates data, goes stale between runs and needs a job and write access to the supplier's metastore, where a share needs nothing to be copied.
T: Share with a Databricks recipient through a recipient defined by its sharing identifier (Databricks-to-Databricks).
V: OpenSharing, Unity Catalog shares

@ DBX-DAA D9 T9.1 applied use-case
S: Customer data in the catalog `prod_customers` must be processed only in the production workspace. A group holds `SELECT` on its tables, yet its analysts in the development workspace, attached to the same metastore, get an error when they open the catalog. Which setting explains this?
A: The catalog is bound to selected workspaces, and an unbound workspace is denied even for principals with explicit grants
B: The group lacks `BROWSE` on the catalog, a privilege that is checked only in workspaces other than the production one
C: Catalogs can be read only in the workspace that created them, because each workspace keeps its own copy of the metastore
D: The development workspace uses a classic SQL warehouse, which cannot read a catalog that contains customer data
K: A
G: ## Workspace-catalog binding
By default every catalog of a metastore is reachable from every workspace attached to it. Workspace-catalog binding overrides that default: the catalog owner (or a holder of `MANAGE`) restricts a catalog to chosen workspaces, optionally read-only.
- Access from an unbound workspace fails even when the user has `USE CATALOG`, `SELECT` and other grants.
- Catalog Explorer, lineage and `information_schema` in an unbound workspace do not list the catalog.
- Bindings isolate environments (production versus development) or sensitive domains; privileges still decide who may use the catalog inside a bound workspace.
## How an analyst diagnoses it
A permission error that follows the workspace rather than the user points to a binding, not to a missing grant.
W: Workspace binding: the production-only catalog is unreachable from the development workspace, whatever privileges the group holds.
X: B=BROWSE: it only affects discovery of metadata and is not checked per workspace; it is not what blocks queries.
C=Own copy of the metastore: workspaces in a region share one metastore, so the data is not workspace-local unless a binding limits it.
D=Classic warehouse: the compute type does not decide catalog access, and no warehouse type is barred from catalogs with customer data.
T: A catalog bound to selected workspaces is denied elsewhere even for users with grants.
V: Unity Catalog workspace-catalog binding

@ DBX-DAA D9 T9.1 advanced troubleshooting
S: A workspace admin who owns nothing in the catalog `retail`, which belongs to the data office group, runs `GRANT USE CATALOG ON CATALOG retail TO sales_team` so that the team can query a table. It fails with a permission error. What is the reason and the fix?
A: The role is workspace-local, so the admin has to join the group `sales_team` before anything is granted to it
B: Workspace admins cannot grant on objects they do not own; the owner, a `MANAGE` holder or a metastore admin must do it
C: Workspace admins may grant only on tables, so the grant has to be run on a schema or table instead of the catalog
D: The grant works once the admin owns every table in the catalog, because only table ownership allows granting
K: B
G: ## Admin roles are not data roles
Workspace admin manages workspace membership, jobs and workspace objects, and can create catalogs and other top-level securables. It is not the same as a metastore admin.
- Privileges on an object can be granted by its owner, the owner of the catalog or schema containing it, a principal with `MANAGE` on it, or a metastore admin.
- Workspace admins can create objects, but cannot grant on or change ownership of existing objects they do not own. (They do own the default workspace catalog.)
- An account admin can assign the metastore admin role, ideally to a group.
Granting on the catalog `retail` therefore needs its owner group, someone holding `MANAGE` on it, or a metastore admin.
W: Owner, MANAGE holder or metastore admin: the admin has no ownership or MANAGE on `retail`, and the workspace admin role does not allow granting on objects it does not own.
X: A=Group membership: you do not have to belong to a group to grant privileges to it; the missing piece is authority over the catalog.
C=Tables only: the privilege model allows grants on catalogs, schemas and tables alike; what matters is who holds authority over the object.
D=Owning every table: ownership of children does not allow granting on the parent catalog, which still has its own owner.
T: Workspace admin does not allow granting on objects it does not own; use the owner, MANAGE or a metastore admin.
V: Unity Catalog admin roles

@ DBX-DAA D9 T9.1 applied use-case
S: A company must give a partner organization daily read-only access to a gold table. The partner does not use Databricks and analyzes data in pandas on its own servers. Which approach fits?
A: Create a share with the table and a recipient for the partner on the open sharing protocol, read with an open-source connector
B: Add the partner staff as users of the company's Databricks account and grant them `SELECT` so they can open the SQL editor daily
C: Grant `SELECT` on the table to All account users and email the partner the SQL warehouse connection details
D: Export the table to CSV every night into a publicly readable cloud bucket and send the partner the bucket link
K: A
G: ## Sharing outside the organization
OpenSharing (the open protocol formerly named Delta Sharing) lets a provider share governed data with recipients on any platform.
- A **share** is a Unity Catalog object that collects tables, views, volumes and other assets; a **recipient** represents the partner. Read-only access is granted to the recipient, and the provider can add or remove assets at any time.
- For recipients without a Unity Catalog workspace, the Databricks-to-Open protocol serves tabular data to open-source clients such as pandas. Databricks-to-Databricks sharing is for recipients who also have a Unity Catalog workspace.
- Views can be shared, including dynamic views that restrict rows and columns.
W: Share and recipient with the open protocol: the partner gets read-only governed access from pandas without any Databricks account, and the provider keeps control of what is shared.
X: B=Account users: that makes outsiders members of the company's own Databricks account, mixes internal and external identities and requires them to use Databricks, which the partner does not.
C=All account users: that group contains only your own account's users, so it does not reach the partner, and giving out warehouse connection details does not grant access.
D=Public CSV bucket: files readable by anyone cannot be restricted to the partner or audited, which defeats governance of the shared table.
T: Share outside the company with a share plus recipient on OpenSharing; use Databricks-to-Open when the partner has no Databricks.
V: OpenSharing, Unity Catalog shares

@ DBX-DAA D9 T9.1 applied tradeoff
S: Forty analysts move between three product teams every month, and each team needs `SELECT` on its own schemas only. The data office wants access changes to need the fewest administrative actions. What is the best approach?
A: Run a script that grants and revokes `SELECT` on each schema for each of the forty analysts as they move
B: Create groups only inside one workspace's admin console and grant the privileges to those workspace-local groups
C: Make every analyst the owner of the schemas of the team they work for and transfer ownership on each move
D: Grant the privileges to account-level groups synced from the identity provider, and change group membership there
K: D
G: ## Grant to groups, not people
Unity Catalog principals must exist at the account level to receive privileges. Databricks best practices:
- Define groups in the identity provider and sync them to the account; manage membership there.
- Grant privileges to groups, and avoid direct grants to individual users.
- Use groups to own objects, too.
With group grants, moving an analyst is a single membership change and all inherited privileges follow, with no `GRANT` or `REVOKE` statements and no stale access left behind.
W: Account-level groups from the identity provider: access follows membership, so a move is one change in one place and every grant stays unchanged.
X: A=Scripted per-user grants: it works but creates a long list of direct grants that must be revoked precisely on each move and easily drifts, which the best practice avoids.
B=Workspace-local groups: privileges are assigned to account-level principals, and local groups are not synchronized to the account, so they are a legacy pattern that Databricks recommends migrating away from.
C=Ownership per analyst: ownership gives full control including granting and dropping, far more than `SELECT`, and a schema has one owner, so this breaks least privilege.
T: Grant privileges to account-level groups managed in the identity provider so that role changes are membership changes.
V: Unity Catalog groups

@ DBX-DAA D9 T9.1 advanced troubleshooting
S: An analyst with `SELECT` on `retail.sales.orders` opens the Permissions tab of the table and sees only the analyst's own grant, although the team wants a list of every group that can read it. Which additional access gives the complete list?
A: `BROWSE` on the catalog `retail`, which lets users discover objects and also lists everyone who holds a grant on them
B: `MANAGE` on the table, which shows all of its grants and also lets the holder change them
C: `SELECT` on the schema `retail.sales`, because a broader read privilege reveals the grants of the objects inside it
D: `USE SCHEMA` on `retail.sales`, because the usage privilege decides whose grants are visible for its objects
K: B
G: ## Who can see grants
Everybody can see their own grants on an object. Seeing all grants is a separate permission.
- The owner of the object, the owner of its catalog or schema, a metastore admin, or a principal with `READ METADATA` or `MANAGE` on the object sees every grant (Catalog Explorer Permissions tab or `SHOW GRANTS ON TABLE retail.sales.orders`).
- Data privileges (`SELECT`), `BROWSE` and the usage privileges do not reveal other principals' grants.
- `MANAGE` also allows changing grants, so for an audit-only need ask the owner for a list.
W: MANAGE on the table: it is one of the permissions that lists every grant on the object, and it is the one given here that does.
X: A=BROWSE: it exposes names, comments and tags for discovery and never shows who holds grants.
C=SELECT on the schema: it grants reading data and has nothing to do with seeing other principals' grants.
D=USE SCHEMA: it is a prerequisite for reading objects inside the schema and does not widen which grants are visible.
T: Seeing all grants on an object needs ownership, MANAGE, READ METADATA or a metastore admin; SELECT does not.
V: Unity Catalog privileges

@ DBX-DAA D9 T9.1 advanced troubleshooting
S: Analysts query the view `retail.reporting.v_margin` on a SQL warehouse. They have `SELECT` on the view and the usage privileges, but no privileges on the base tables, and it worked for months. Today every query fails with a permission error on a base table. The view's owner, an engineer, was removed from the group that held `SELECT` on those tables. What should be done?
A: Grant each analyst `SELECT` on the base tables so that the view no longer depends on its owner
B: Move the dashboards to a classic SQL warehouse, which checks the analysts' own permissions on the base tables
C: Have a metastore admin transfer the view's ownership to a group that holds `SELECT` on the base tables
D: Grant the analysts `MANAGE` on the view, so that Unity Catalog uses their permissions instead of the owner's
K: C
G: ## Whose permissions does a view use?
For views read on SQL warehouses, Unity Catalog checks the **view owner's** permissions on the underlying tables. Readers need `SELECT` on the view plus the usage privileges, but not rights on the base tables. This is what lets a view expose a safe slice of a table.
The flip side: if the owner loses access to the sources, the view breaks for every reader. Best practices:
- Make a group the owner of production views, and give that group access to the source tables.
- Only a metastore admin can transfer a view to an arbitrary principal; owners and `MANAGE` holders are limited to themselves or groups they belong to.
W: Group ownership with source access: the view again runs with the owner's permissions, readers keep seeing only the view, and the dependency no longer rests on one engineer.
X: A=Direct base-table grants: analysts would see everything in the base tables, which the view was meant to prevent, and it does not fix the ownership problem.
B=Classic warehouse: SQL warehouses of every type use the view owner's permissions for the base tables, so the compute type does not change the outcome.
D=MANAGE on the view: it delegates grant and ownership operations, not the identity used for the base-table check, so the view still fails.
T: A view reads base tables with its owner's permissions, so a group should own production views and keep access to their sources.
V: Unity Catalog views

@ DBX-DAA D9 T9.2 applied troubleshooting
S: In the SQL editor an analyst runs `SELECT * FROM orders` and gets a table-not-found error, although the table is shown in Catalog Explorer as `retail.sales.orders`. What fixes the query?
A: Use `retail.sales.orders`, or first run `USE CATALOG retail` and `USE SCHEMA sales`
B: Rename the table to `orders_retail_sales`, because names must be unique across the whole metastore
C: Convert the table to an external table, because only external tables can be referenced by a short name in the editor
D: Ask a workspace admin to add the analyst to the workspace admins group so that short names resolve
K: A
G: ## Qualified and unqualified names
Unity Catalog uses a three-level namespace: `catalog.schema.table`.
- A name with fewer parts is resolved against the **current catalog** and **current schema**. If you do not set them, the workspace's default catalog is used (a workspace admin can change it) and the default schema.
- `USE CATALOG retail` and `USE SCHEMA sales` change the current ones for the session, so the short name `orders` resolves to `retail.sales.orders`.
- A fully qualified name works regardless of session settings and is the safest form in saved queries, views and dashboards.
W: Fully qualify or set the current catalog and schema: the short name `orders` was looked up in a different catalog and schema than the one holding the table.
X: B=Rename the table: names need to be unique only within a schema, which is why the same table name can exist in many schemas and catalogs.
C=External table: managed and external tables are both resolved the same way, and the table type has no effect on name resolution.
D=Workspace admin: admin role changes privileges, not how a partially qualified name is resolved, so the lookup would still point at the same default location.
T: Names resolve against the current catalog and schema; qualify them or set USE CATALOG and USE SCHEMA.
V: Unity Catalog namespace

@ DBX-DAA D9 T9.2 applied use-case
S: The catalogs `dev` and `prod` both contain a schema `crm` with a table `customers`. An analyst with access to both wants to compare their row counts in a single query on one SQL warehouse. Which statement describes what is possible?
A: It needs two warehouses, one per catalog, and the results must be joined in a spreadsheet afterwards
B: It is only possible after copying one table into the other catalog, because a query reads from one catalog at a time
C: It is possible with `crm.customers` written twice, if `USE CATALOG` is executed between the two subqueries of the same statement
D: It is possible by naming `dev.crm.customers` and `prod.crm.customers` in the same statement, since both live in one metastore
K: D
G: ## One metastore, many catalogs
Catalogs are the top containers of a metastore, and all catalogs of a metastore are visible to a query that has privileges on them. Three-part names make each reference unambiguous, so one statement can mix tables from several catalogs:
```
SELECT 'dev', count(*) FROM dev.crm.customers
UNION ALL
SELECT 'prod', count(*) FROM prod.crm.customers
```
The same table name in different schemas or catalogs is normal and is the reason qualification matters. Privileges still apply to each object, so the analyst needs access on both.
W: Three-part names in one statement: both catalogs belong to the same metastore, so the query can reference both objects directly.
X: A=Two warehouses: a warehouse is compute and is not tied to a catalog, so one warehouse can read all catalogs the user may access.
B=Copy first: a single query can read several catalogs, so no copy is needed, and copying would add cost and staleness.
C=USE CATALOG between subqueries: the session catalog is fixed for the duration of a statement and cannot be switched within it, so both subqueries would resolve to the same catalog.
T: Fully qualified catalog.schema.table names let one query combine objects from several catalogs of the same metastore.
V: Unity Catalog namespace

@ DBX-DAA D9 T9.2 applied definition
S: Which description of the Unity Catalog object hierarchy is correct?
A: A workspace contains databases, databases contain tables, and views and volumes live in the top-level catalog
B: A metastore contains catalogs, catalogs contain schemas, and schemas contain tables, views, volumes and functions
C: A catalog contains tables, tables contain schemas, and each metastore is created separately for every workspace
D: A schema contains catalogs, catalogs contain tables, and views sit in a separate namespace outside the metastore
K: B
G: ## The object model
Unity Catalog stores data and metadata in a **metastore** (one per cloud region, shared by the workspaces in that region). Inside it, objects follow the three-level namespace `catalog.schema.object`:
- **Catalogs** are the top level and the typical unit of data isolation.
- **Schemas** (databases) organize objects inside a catalog.
- **Tables, views, volumes, functions and models** are the objects in a schema.
Catalogs and schemas are container objects: privileges granted on them inherit to current and future children.
W: Metastore, catalog, schema, object: each level contains the next, which is why a table is addressed as `catalog.schema.table`.
X: A=Workspace > database: a workspace is not a level in the object model, and views and volumes sit in schemas, not directly in a catalog.
C=Tables contain schemas: containers are the other way around, and workspaces in a region share a metastore instead of each having one.
D=Schemas contain catalogs: the nesting is reversed, and views are objects in schemas that follow the same namespace and governance as tables.
T: Metastore contains catalogs, catalogs contain schemas, schemas contain tables, views, volumes and functions.
V: Unity Catalog object model

@ DBX-DAA D9 T9.3 applied use-case
S: An analyst builds the production table `retail.gold.kpi_daily` that feeds several dashboards and is therefore its owner. The team wants to avoid broken refreshes and unmanaged access when staff leave. What is the best practice?
A: Keep the analyst as owner, because Unity Catalog moves the ownership automatically when a user leaves
B: Grant the analyst `ALL PRIVILEGES` and keep ownership with them so that the grants can be audited
C: Transfer ownership to the metastore admin, so that all production tables are owned by one administrator
D: Transfer ownership to a group that represents the team, so that people can change without changing the owner

G: ## Who should own a table
The creator of an object is its first owner. Owners can grant and revoke access, transfer ownership and drop the object, and a refresh or a dashboard run under an owner's identity can break when that person leaves.
Databricks best practices:
- Assign ownership of production objects to groups, not to individuals; creators should reassign ownership.
- Be sparing with metastore admins, `MANAGE` and `ALL PRIVILEGES`.
A group owner means that team changes are group membership changes, and the owner stays valid.
W: Group ownership: the owner is a stable principal, so grants, refreshes and administration continue after any individual leaves.
X: A=Automatic transfer: Unity Catalog does not reassign objects when a user is removed, so a person-owned table is left with an orphaned owner.
B=ALL PRIVILEGES for the analyst: this still ties the table to one person, and `ALL PRIVILEGES` is not even the same as ownership, since it excludes `MANAGE`.
C=Metastore admin as owner: that concentrates control in one broad role, which the guidance says to assign sparingly, and it makes day-to-day administration slower.
T: Give production tables to a group as owner so staff changes never orphan them.

@ DBX-DAA D9 T9.3 applied use-case
S: A dashboard for regional managers needs only customer counts by region and age band. The source table `crm.core.customers` holds names, emails and birth dates. Managers must not reach personal data even by writing their own queries. What is the best design?
A: A gold table or view that outputs only counts by region and age band, with managers granted `SELECT` on it and nothing on the source
B: The source table in the dashboard dataset, with the name, email and birth date columns left out of the charts by the dashboard author
C: `SELECT` on the source table for the managers, plus a table comment that asks them not to query the personal columns
D: A dashboard parameter that managers must set to a single region, so that each viewer queries only a small slice of personal rows

G: ## Minimize what leaves the source
The strongest protection for personal data is not to expose it. Build a derived object (gold table, view or metric view) that contains only what the audience needs, here aggregates by region and age band, and grant access to that object only.
- Hiding columns in charts, parameters and comments are presentation or convention; anyone with `SELECT` on the source can still query every column.
- A view runs with its owner's access to the source, so managers need no privileges on the source table.
- Where individual rows must stay available to some users, use column masks or row filters instead.
W: Aggregated gold object: the audience gets only region and age band counts and has no privilege on the source, so personal data is out of reach even with custom queries.
X: B=Hidden chart columns: this is presentation only; managers with access to the source can query name, email and birth date directly.
C=Table comment: a comment is documentation and enforces nothing, so any manager can still select the personal columns.
D=Region parameter: it narrows the rows shown in one chart but does not restrict the columns or what a custom query can read.
T: Expose a derived, aggregated object and keep the source with personal data closed.

@ DBX-DAA D9 T9.3 applied troubleshooting
S: The `email` column of `retail.crm.customers` has a column mask for everyone outside `crm_admins`. An analyst outside that group runs `SELECT count(DISTINCT email) FROM retail.crm.customers` and gets 1, although the table has millions of customers. What is the best explanation and remedy?
A: Masks are skipped on serverless SQL warehouses, so a classic warehouse will return the correct count
B: Ask for `ALL PRIVILEGES` on the table, which lets the query read the unmasked values
C: The mask returns the same constant for this user, so count a non-sensitive key such as `customer_id`
D: The query result cache is stale, so clearing it and re-running the query will give the unmasked count
K: C
G: ## Masked values are what the analyst really sees
A column mask replaces the value before the query engine uses it. Every function applied afterwards, including `count(DISTINCT ...)`, `GROUP BY` and joins, works on the masked value.
- If the mask returns a constant such as `'***'`, all rows look identical, so distinct counts, grouping and joins on that column collapse.
- This is the mask working as designed, not a bug.
- Analysts should use a non-sensitive key (for example `customer_id`) for counting and joining, or ask the table owner for a mask that keeps analytic value (such as a hash) when policy permits.
Privileges such as `ALL PRIVILEGES` do not bypass a mask, since the mask applies to whoever is not in the exempt group.
W: Constant mask value: the 1 is correct for masked data, and counting `customer_id` answers the business question without touching PII.
X: A=Serverless versus classic: masks are enforced on SQL warehouses of every type, so switching type cannot reveal the values.

@ DBX-DAA D9 T9.3 applied use-case
S: Analysts want to save intermediate tables while exploring but must not be able to change or drop production tables. What is the best practice?
A: Make every analyst the owner of the production schemas, since owners can create tables without any extra privileges
B: Grant `ALL PRIVILEGES` on the production catalog to the analyst group so that they can create tables wherever they need
C: Grant `USE CATALOG`, `USE SCHEMA` and `CREATE TABLE` on a separate sandbox schema, and only `SELECT` on production schemas
D: Let analysts write into the production schemas and have the data office delete the scratch tables each week
K: C
G: ## Separate sandbox from production
Privileges are granted per securable object, so write access can be limited to one schema.
- A **sandbox** schema (or catalog) per team gets `USE SCHEMA` and `CREATE TABLE` (plus `USE CATALOG` on its catalog) for the analyst group. The creator of a table becomes its owner there.
- Production schemas get only `USE CATALOG`, `USE SCHEMA` and `SELECT` for analysts.
- Databricks recommends granting to groups, giving ownership of production catalogs and schemas to groups, and using `ALL PRIVILEGES` and ownership sparingly.
W: Sandbox schema plus read-only production: analysts can create and own scratch tables in their schema, and production tables stay protected by read-only grants.
X: A=Production ownership: owners can drop, grant and change everything in the object, far beyond what exploration needs, which is the opposite of least privilege.
B=ALL PRIVILEGES on production: it includes the write privileges (for example `MODIFY` and `CREATE TABLE`) on every production object, so analysts could change or clutter production.
D=Scratch tables in production: they mix experiments with governed data and depend on manual clean-up, while write access to production remains open.
T: Give analysts write access to a sandbox schema and read-only access to production.

@ DBX-DAA D9 T9.3 applied definition
S: An analyst creates a table with `CREATE TABLE ... AS SELECT` in a schema that a data office group owns. Which statement about the ownership of this table is correct?
A: The data office group owns it automatically, because a schema owner becomes the owner of each table created in the schema
B: The table has no owner until a metastore admin assigns one, and until then nobody can grant privileges on it
C: The analyst is the initial owner, and a table has exactly one owner, who can grant, transfer and drop it
D: Every principal with `SELECT` or `MODIFY` on the schema is a co-owner of the table next to the analyst
K: C
G: ## Ownership basics
Every securable object in Unity Catalog has an owner.
- The creator of an object is its first owner; ownership of a schema does not pass to the tables created in it, although the schema owner can still grant on them.
- An object has exactly one owner (a user, service principal or group). The owner has all privileges on the object, can grant and revoke, transfer ownership and drop it.
- `MANAGE` shares administration of one object with other principals; it does not share ownership.
- Because a person-owned table is at risk when staff move on, creators should transfer ownership of production objects to a group.
W: Creator as sole owner: the analyst owns the new table, and the single owner can grant, transfer and drop it.
X: A=Schema owner as owner: ownership is not inherited by children; the schema owner can grant on the table but the table is owned by its creator.
B=No owner: every object has an owner from creation, so the table can be administered at once.
D=Co-owners via SELECT or MODIFY: those are data privileges and do not make anybody an owner; an object has one owner only.
T: The creator is the initial and only owner of a table; transfer production tables to a group.
V: Unity Catalog ownership

@ DBX-DAA D9 T9.3 applied comparison
S: Compliance requires that when an analyst drops a staging table that holds personal data, Databricks removes the underlying data files too, and does not leave a copy in a bucket nobody tracks. Which table type should the analyst create?
A: A managed table, because Unity Catalog manages both the metadata and the lifecycle of its data files
B: An external table, because dropping it deletes the files at its registered storage location
C: A view over the source files, because dropping a view removes the data it reads
D: An external table with `MANAGE` granted to the analyst, because that privilege deletes files on drop
K: A
G: ## Managed versus external
- **Managed tables**: Unity Catalog controls the data files as well as governance. Dropping one lets Unity Catalog delete the data (after its recovery window). Databricks recommends managed tables for most use cases because they get full governance and optimization features.
- **External tables**: Unity Catalog governs access, but the file layout and lifecycle belong to you and your cloud provider. Dropping the table removes only the registration; the files stay in storage until someone deletes them.
For personal data that must disappear on drop, the lifecycle must belong to the platform, not to a separate storage process.
W: Managed table: because the lifecycle of the files is owned by Unity Catalog, dropping the table also takes care of the data, not only the metadata.
X: B=External table: dropping an external table leaves the files at their location, which is exactly the untracked copy that compliance wants to avoid.
C=View: a view stores no data, so dropping it removes only the definition and the source files remain.
D=External with MANAGE: `MANAGE` controls privileges and ownership operations and does not change what a drop does to external files.
T: Managed tables get their data lifecycle handled by Unity Catalog; dropping an external table leaves the files.
V: Managed and external tables
