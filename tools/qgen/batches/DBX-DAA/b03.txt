@ DBX-DAA D4 T4.1 applied use-case
S: An analyst runs a SQL cell in a notebook and it fails because a column name in the SELECT list has a small typo. The analyst wants the fastest way to correct it with a suggested change that can be accepted and run. Which Genie Code capability fits?
A: Quick Fix, which proposes an automatic correction for a basic error that the analyst can accept and run
B: Genie Migrate, which converts SQL written for other data warehouse dialects into Databricks SQL
C: Genie Ontology, which adds organization-wide business definitions to the prompt before writing SQL
D: Full page Genie Code, which opens a separate command center to start a new multi-step project
K: A
G: ## What Genie Code offers for debugging
Genie Code (the Databricks AI coding and data assistant, formerly called Databricks Assistant) works in notebooks, the SQL editor, Lakeflow Pipelines Editor and dashboards. For errors it has two built-in levels of help.
- **Quick Fix** suggests an automatic recommendation for basic errors, such as a misspelled column or a missing keyword. You review it and choose Accept and run.
- **Diagnose Error** analyzes more complex problems, including environment errors, and tries to fix them.
Databricks recommends always reviewing generated code before running it, because it can make mistakes.
W: Quick Fix: a typo in a column name is a basic error, and Quick Fix presents a recommended correction that the analyst can accept and run in place.
X: B=Genie Migrate: it translates SQL from other warehouse dialects in a migration project. The code here is already Databricks SQL with a typo, so there is nothing to convert.
C=Genie Ontology: it supplies business context such as metric definitions and join hints so new SQL is more accurate. It does not repair a failed cell, and it is not what the question describes.
D=Full page Genie Code: a layout for starting and running several chats from a dedicated page. It is a place to work, not a one-click fix for a failing cell.
T: Basic error in a cell, quick accept: Quick Fix; harder or environment errors: Diagnose Error; always review the code.

@ DBX-DAA D4 T4.1 applied troubleshooting
S: A notebook cell that reads a table fails with a long error caused by the notebook environment rather than by the SQL text. A simple suggested edit of the statement does not help. Which Genie Code feature should the analyst use to investigate and attempt a repair?
A: Quick Fix, because it proposes edits only to the statement text and is meant for environment-level failures
B: Diagnose Error, which analyzes more complex errors, including environment errors, and attempts to fix them
C: Inline suggestions, which complete the next tokens of code while the analyst is typing a new statement
D: Command shortcuts, which let the analyst start a prompt directly inside a notebook cell before running it
K: B
G: ## Choosing between the two debugging features
Genie Code separates error help by complexity.
- **Quick Fix** handles basic errors such as typos and offers a one-click Accept and run.
- **Diagnose Error** reads the error and the surrounding context and handles more complex cases, including environment errors, then attempts a fix.
Choosing the right one saves time: a typo does not need a deep diagnosis, and an environment failure is not solved by editing one keyword.
W: Diagnose Error: it is built for errors beyond simple syntax, including environment errors, and it analyzes the failure and tries to repair it.
X: A=Quick Fix: it targets basic errors with a simple recommended edit. Docs assign environment and more complex failures to Diagnose Error, so this does not match the case.
C=Inline suggestions: they help while you write new code. They do not read a failed run and explain the error.
D=Command shortcuts: they let you prompt Genie Code from within a cell to generate or change code. They are a way to ask, not an error-analysis feature.
T: Simple error: Quick Fix; complex or environment error: Diagnose Error.

@ DBX-DAA D4 T4.1 applied use-case
S: An analyst asks Genie Code in the SQL editor for "monthly revenue per region", but the generated query keeps picking the wrong columns from a table with names like c1 and amt_x. What most improves future suggestions for everyone who uses the table?
A: Switching the SQL warehouse type from pro to serverless so that prompts are interpreted with more compute
B: Pasting the full table data into every prompt so that the model can read the values directly each time
C: Adding clear descriptions to the table and its columns in Unity Catalog so the assistant gets better metadata
D: Renaming the personal notebook so that its title explains the revenue logic to the assistant when it runs

G: ## What Genie Code reads
Genie Code uses Unity Catalog metadata, meaning table and column names, descriptions and popular data assets, to give personalized answers while you write, debug and run code. It also uses the code you are working with.
Cryptic column names give the assistant little to go on. A comment such as "Net revenue in USD after discounts" on the column lets it choose correctly, and the description is stored once in Unity Catalog, so every user benefits.
W: Descriptions in Unity Catalog: the assistant draws on table and column descriptions, so documenting the cryptic columns improves results for all users and all surfaces.
X: A=Serverless warehouse: the warehouse runs the SQL after it is generated. It does not change how the assistant understands column meaning.
B=Pasting data: the assistant already sends relevant context within the user's permissions, and pasting data is unnecessary, risky for sensitive values and does not document the table for others.
D=Renaming the notebook: a title is not table metadata, helps only that one notebook and does not tell the assistant what the columns mean.
T: Better Unity Catalog metadata (names, descriptions) gives better Genie Code SQL for every user.

@ DBX-DAA D4 T4.1 applied definition
S: A manager asks whether Genie Code can read tables an analyst has not been granted access to, because the analyst wants help with a query on a finance table. How does Genie Code treat access to data?
A: It uses a service credential with broad read rights, so it can answer from any table in the metastore

G: ## Genie Code and governance
Genie Code is governed by Unity Catalog permissions. It can only access data and perform operations that the signed-in user has permissions for. To complete a task it sends the prompt and relevant context, such as table and column names, descriptions and the code in use, to the model, all within the user's permissions.
So an analyst without SELECT on a finance table will not get content from it, and an administrator does not need a separate policy for the assistant.
W: User's Unity Catalog permissions: the assistant acts with the permissions of the person asking, so it cannot go beyond what that person can already do.

C=Default catalog only: access depends on privileges, not on which catalog is the workspace default.
D=Split enforcement: permissions are not applied differently to metadata and values in this way; the assistant works within what the user is permitted to see.

@ DBX-DAA D4 T4.1 applied tradeoff
S: Genie Code generated a long query with several joins and the analyst plans to publish its output in a weekly report right away. What is the right practice?
A: Run it unchanged because generated code is always validated against the table schema before it is shown
B: Reject the assistant output and rewrite the query manually, because generated joins cannot be trusted at all
C: Run it in production first and compare the report to last week afterwards, to avoid delaying publication
D: Review the logic and test the results on a sample before publishing, since the assistant can make mistakes
K: D
G: ## Treat generated SQL as a draft
The documentation recommends always reviewing code generated by Genie Code before running it, because it can sometimes make mistakes. Typical problems are a join on the wrong key, which duplicates rows, or a filter that drops valid rows.
A good check is to compare row counts and one known total with a trusted source. This keeps the speed benefit and still protects the report.
W: Review and test: the assistant is a productivity tool whose output must be verified, and a sample check catches wrong joins or filters before anyone relies on them.
X: A=Run unchanged: nothing guarantees the logic matches the business question; passing the schema check does not mean the join keys or filters are right.
B=Reject everything: the output is often a useful draft; the advice is to review it, not to avoid it.
C=Run first, compare later: this puts unchecked numbers in front of readers, so errors would already have been published.
T: Review and verify generated SQL before publishing; it is a draft, not a guarantee.

@ DBX-DAA D4 T4.2 applied definition
S: An analyst opens the SQL editor and runs a query against Unity Catalog tables. What role does the SQL warehouse play in this execution?
A: It stores the table data files and enforces the table schema, so the query reads only from the warehouse
B: It is the compute resource that executes the query, while the data stays in the governed tables
C: It defines which users may see each column, replacing the privileges set in Unity Catalog
D: It converts the SQL text into a dashboard automatically when the query returns an aggregate result
K: B
G: ## Compute versus storage versus governance
- **Data** lives in cloud storage and is registered as Unity Catalog tables.
- **Governance** (who can read which table, column or row) comes from Unity Catalog privileges.
- **Compute** is what runs the query. In Databricks SQL that is a **SQL warehouse**, a compute resource that lets you query and explore data.
The SQL editor, Catalog Explorer and dashboards each pick a warehouse from a compute drop-down.
W: Compute that executes the query: the warehouse runs the SQL, while storage holds the data and Unity Catalog governs access.
X: A=Storing data: warehouses are compute; table files remain in cloud storage under Unity Catalog and do not live in the warehouse.
C=Replacing privileges: Unity Catalog governs data access; the warehouse has its own ACL for who can use it, but that does not grant column access.
D=Building dashboards: a dashboard is built by a user on top of datasets; a warehouse does not convert result sets into one.
T: SQL warehouse = the compute that runs Databricks SQL; Unity Catalog = governance; cloud storage = the data.

@ DBX-DAA D4 T4.2 applied troubleshooting
S: An analyst runs a query in the SQL editor and sees that the selected warehouse is stopped. The analyst has permission to use it. What happens?
A: The query fails immediately and an administrator must start the warehouse before any query can run
B: The query is queued on another running warehouse that the workspace chooses at random
C: The warehouse starts automatically and runs the query once it is up, after a short startup delay
D: The query runs on the SQL editor's own local engine until the warehouse is restarted manually
K: C
G: ## Warehouse auto-start
A SQL warehouse auto-restarts when a query is run against it while stopped, when a job assigned to it is scheduled, when a JDBC/ODBC connection is made, or when a dashboard tied to it is opened. Users need the right permission on the warehouse (Can use to run queries).
Auto stop saves cost when nobody is querying; auto start keeps this transparent for analysts. Serverless warehouses start much faster than other types.
W: Automatic start: running a query on a stopped warehouse starts it if the user has access, so the query runs after the startup delay.
X: A=Administrator must start: manual start is possible for people with Can monitor or more, but it is not required, since a query triggers auto-start.
B=Random other warehouse: queries run on the warehouse the user selected, not on one picked by the workspace.
D=Local engine: the SQL editor has no local engine; SQL always executes on a SQL warehouse.
T: A query on a stopped warehouse auto-starts it for users with access.

@ DBX-DAA D4 T4.2 applied tradeoff
S: A retail team runs interactive dashboards whose load swings from near zero at night to many users at once during sales events. They do not want to manage capacity or wait for clusters to start. Which warehouse choice best fits?
A: A classic SQL warehouse with a fixed maximum, because it adds Intelligent Workload Management
B: A pro SQL warehouse with the minimum number of clusters set to one for the whole day
C: A classic SQL warehouse sized for peak load and left running continuously to avoid delays
D: A serverless SQL warehouse, which starts in seconds and scales up and down automatically
K: D
G: ## Serverless, pro and classic
All three types include the Photon engine. They differ elsewhere.
- **Serverless** adds Predictive IO and Intelligent Workload Management (IWM). It typically starts in a few seconds, upscales quickly when queries queue, and downscales fast when demand drops. Databricks manages capacity, patching and upgrades.
- **Pro** has Predictive IO but no IWM, and uses manual cluster counts.
- **Classic** has Photon only.
Variable demand with no capacity management points to serverless.
W: Serverless: rapid startup, elastic scaling and Databricks-managed capacity match spiky dashboard demand without over-provisioning.
X: A=Classic with fixed maximum: classic does not include IWM, and a fixed maximum does not adapt to a spike.
B=Pro with one cluster: pro scales by configured cluster counts and has no IWM; a one-cluster minimum leaves cost running overnight with slower elasticity.
C=Classic sized for peak: it removes startup delays but pays for idle capacity most of the day and still needs hand-tuning.
T: Variable BI load with minimal admin effort: serverless SQL warehouse.

@ DBX-DAA D4 T4.2 applied troubleshooting
S: On a pro SQL warehouse, many analysts run queries at 9 a.m. and some wait in a queue, although each individual query runs fast once it starts. Which change addresses the symptom?
A: Increase the maximum number of clusters so autoscaling can add clusters for the concurrent queries
B: Increase only the cluster size, because bigger clusters allow more queries to run in parallel
C: Disable Photon, because it limits how many queries can be admitted at the same time
D: Move the queries into a materialized view so the warehouse no longer needs to run them
K: A
G: ## Size versus number of clusters
For classic and pro warehouses you pick a **cluster size** and a **minimum and maximum number of clusters**.
- Cluster size mainly speeds up a single query (more memory and cores).
- The number of clusters governs **concurrency**. Autoscaling adds clusters based on the estimated time to process running and queued queries, and Databricks suggests about one cluster per 10 concurrent queries.
Queueing with fast individual queries is a concurrency problem, so raise the maximum clusters.
W: More clusters: queueing under concurrent load is addressed by letting autoscaling add clusters, up to a higher maximum.
X: B=Larger size only: size accelerates a single query; it is not the main lever for concurrent users, and fast queries show size is not the issue.
C=Disabling Photon: Photon speeds up queries and does not restrict admission, so turning it off would not reduce queueing.
D=Materialized view: it may help specific heavy queries, but it does not answer the stated problem of many concurrent users waiting.
T: Queueing at peak: raise the maximum number of clusters; slow single queries: increase size.

@ DBX-DAA D4 T4.3 applied use-case
S: An analyst needs to join a Delta table of orders in Unity Catalog with a customers table that lives in an operational PostgreSQL database. The analyst wants to query it in place, governed by Unity Catalog, without copying the data first. What is the approach?
A: Export the PostgreSQL table to CSV and upload it through the workspace UI before every query
B: Create a connection and a foreign catalog for PostgreSQL, then join its tables with the Delta table in one query
C: Create a share with Delta Sharing so that PostgreSQL appears as a recipient catalog in the workspace
D: Convert the Delta table to PostgreSQL and run the join inside the remote database only
K: B
G: ## Query federation
Query federation lets you run queries against external relational databases through JDBC. You create a **connection** to the database and a **foreign catalog** in Unity Catalog that mirrors it. Its tables then appear with three-level names, for example `pg_cat.public.customers`, and you can join them with Delta tables:
`SELECT ... FROM sales.orders o JOIN pg_cat.public.customers c ON o.cust_id = c.id`
Access is governed by Unity Catalog, and parts of the query are pushed down to the remote database.
W: Connection plus foreign catalog: this is query federation, which queries the database in place under Unity Catalog governance and joins with Delta tables.
X: A=CSV export and upload: it creates a stale copy that needs repeating, and the question asks to query in place.
C=Delta Sharing: sharing is a protocol for exchanging data between Delta or Unity Catalog parties, not a way to expose a PostgreSQL database.
D=Convert to PostgreSQL: Delta tables are not moved into the remote database for the join; federation joins them on the Databricks side.
T: Join Delta with an external relational database in place: connection and foreign catalog (query federation).

@ DBX-DAA D4 T4.3 applied troubleshooting
S: After a foreign catalog was created for a MySQL database, an analyst runs UPDATE on a foreign table to fix a customer record and gets an error. What explains it?
A: Foreign catalog tables are read-only in Databricks, so data changes must be made in the source database
B: The SQL warehouse is a classic type, and only serverless warehouses can write to foreign tables
C: Foreign tables can be updated only after they are cloned into the default catalog of the metastore
D: The UPDATE needs the OPTIMIZE command to run first so the remote table is compacted
K: A
G: ## Federated data is read-only
A foreign catalog mirrors an external system in Unity Catalog and lets you run **read-only** queries on it. Writes are not supported through query federation; they happen in the source system. You can grant read-only access to foreign tables with standard Unity Catalog privileges.
If you need changes visible in Databricks, ingest or replicate the data into Delta, or keep updating the source.
W: Read-only: foreign catalogs only support reads, so the correction must be made in the MySQL database.
X: B=Warehouse type: serverless is not what makes federated tables writable; they are read-only for every compute type.
C=Cloning: cloning copies the data into Delta, which is a different table; the foreign table itself stays read-only.
D=OPTIMIZE: that is a Delta maintenance command, and a remote relational table has no Delta files to compact.
T: Foreign catalogs and federated tables are read-only; write at the source.

@ DBX-DAA D4 T4.3 advanced tradeoff
S: A team wants quick, ad hoc reports that combine a Delta table with an operational PostgreSQL database for a one-week proof of concept. Nothing should be built or scheduled to copy data. Which method matches best?
A: Query federation through a foreign catalog, which suits ad hoc reporting and proof-of-concept access
B: A full ingestion pipeline with Lakeflow Connect, which suits a long-term, high-volume replica
C: An external location on object storage, because a PostgreSQL database cannot be queried live
D: A Marketplace listing, because all operational databases are published there as ready tables
K: A
G: ## When federation fits
Query federation is described as best for ad hoc reporting, BI and proof-of-concept access to operational databases. The query runs on both Databricks and remote compute, so heavy or frequent queries load the source system.
If the workload becomes regular or large, ingest the data (for example with Lakeflow Connect) or materialize results, which removes pressure from the source and usually improves performance.
W: Query federation: it provides live, governed access with no pipeline to build, ideal for a short proof of concept.
X: B=Lakeflow Connect ingestion: appropriate for a durable, regularly refreshed copy, but it is a build and scheduling effort that the team wants to avoid for a one-week test.
C=External location: this registers cloud storage paths; it is not how a PostgreSQL database is queried, and the database can be queried live through federation.
D=Marketplace: it lists shared data products and not your internal operational databases.
T: Ad hoc or proof-of-concept access to an operational database: federation; regular heavy use: ingest or materialize.

@ DBX-DAA D4 T4.3 applied definition
S: In a federated join between a Delta table and a table in a foreign catalog, which statement about how the query executes is correct?
A: All of the work runs on the remote database, which returns only the final joined result set
B: The remote database is never contacted, as a copy of its tables is kept in the metastore
C: Parts of the query are pushed down to the remote database, and the rest runs on Databricks compute
D: The Delta table is first copied into the remote database so the join happens there
K: C
G: ## Pushdown in query federation
Federated queries use JDBC with automatic query pushdown: the query runs on both Databricks and remote compute. Filters and some operations are pushed to the external database so less data crosses the network, while the join with a Delta table happens on Databricks.
Because the remote system does real work, expensive federated queries put load on the source database.
W: Pushdown plus Databricks execution: some operators are pushed to the source, and the remaining processing, such as the join with Delta, runs on Databricks.
X: A=All remote: the Delta table lives in Databricks, so the join cannot run entirely in the remote database.
B=No contact and a copy: federation reads the remote database at query time; no standing copy is kept.
D=Copy Delta to remote: Databricks does not push the Delta table into the external system for the join.
T: Federation = JDBC, pushdown of what the source can do, the rest (including joins with Delta) on Databricks.

@ DBX-DAA D4 T4.3 applied use-case
S: A governance lead wants analysts in the "sales_analysts" group to read only the federated customers table from a foreign catalog, and nothing else in that remote database. How is this controlled?
A: By giving the group admin rights on the remote database so it can choose which tables it sees

Foreign catalogs are securable objects in Unity Catalog. You grant read-only access to foreign tables with the same privileges as other tables (for example USE CATALOG, USE SCHEMA and SELECT). X: A=Remote admin rights: that grants far more power than needed and bypasses Unity Catalog governance.

@ DBX-DAA D4 T4.4 applied use-case
S: A dashboard aggregates billions of sales rows by region and day, and it is slow whenever it opens. The source table receives updates and deletes, and the numbers can be a few minutes old. What object should the analyst create in Databricks SQL?
A: A temporary view, which stores its result for all sessions until the cluster is restarted
B: A standard view, because it computes on demand and therefore is always the fastest to read
C: A streaming table, because it handles updates and deletes to the source by reprocessing rows
D: A materialized view, which stores precomputed results and refreshes them as the source changes
K: D
G: ## Materialized views
A materialized view is a Unity Catalog managed table that physically stores the results of a query. Unlike standard views, which compute on demand each time they are read, it caches results and updates them when source tables change. It suits dashboards and reports that need precomputed aggregates, and in many cases refreshes incrementally rather than recomputing everything.
Create it in the SQL editor with `CREATE MATERIALIZED VIEW`; a serverless pipeline processes the creation and refreshes.
W: Materialized view: it precomputes the aggregation once, serves quick reads to the dashboard, and handles changing sources through refresh.
X: A=Temporary view: it is visible only to the session that created it and stores no results, so the dashboard would still run the whole aggregation on every open.
B=Standard view: it re-runs the full aggregation on every read, so it does not remove the slowness.
C=Streaming table: it processes each new row once from append-only style sources; a changed or deleted source row raises an error, so it is unsuitable here.
T: Slow repeated aggregation over a changing table: materialized view.

@ DBX-DAA D4 T4.4 applied comparison
S: An analyst ingests clickstream events from cloud storage. Files only ever arrive, never change, and each event must be processed exactly once as new files appear. Which object is designed for this?
A: A streaming table, which is stateful and processes each row only once as the dataset grows
B: A materialized view, which recomputes aggregates and is meant for sources that change
C: A dynamic view, which filters rows per user when the query runs against the table
D: A standard view, which stores nothing and re-reads every file on each query

G: ## Streaming table versus materialized view
- **Streaming table**: stateful, handles each row only once while a dataset grows, suits ingestion with data freshness and low latency. Its query uses `STREAM` on the source, and `REFRESH` processes the latest data. Safest with static or append-only sources.
- **Materialized view**: stores the result of a query and updates it as sources change; best for transformations and aggregates.

@ DBX-DAA D4 T4.4 advanced tradeoff
S: A materialized view feeds a morning report. Upstream loads land at unpredictable times, and the team wants the view to update shortly after source data changes without keeping a fixed cron schedule. Which option fits?
A: Define the materialized view with a daily cron schedule at the earliest possible hour
B: Convert the materialized view to a temporary view so that it is always current
C: Define the view with TRIGGER ON UPDATE so it refreshes when upstream source data changes
D: Disable refreshes and run a full CREATE OR REPLACE by hand whenever someone remembers
K: C
G: ## Refresh options
A materialized view can refresh by a **cron schedule** (`SCHEDULE CRON ...`), **on trigger** (`TRIGGER ON UPDATE`, refreshes whenever the upstream source data changes), or manually with `REFRESH MATERIALIZED VIEW`. Databricks says to use trigger-based refresh for production workloads, especially when upstream dependencies don't run on predictable schedules.
Refresh may be incremental (only changed data) or full; a cost model chooses by default.
W: TRIGGER ON UPDATE: the view refreshes after the source changes, which fits loads at unpredictable times and avoids a fixed schedule.
X: A=Daily cron early: a fixed time either runs before late loads and shows stale data, or wastes work if the data arrives sooner.
B=Temporary view: it stores no results, so it would re-run the full query on every read instead of precomputing.
D=Manual refresh: this relies on memory and defeats automation for a recurring report.
T: Unpredictable upstream timing: TRIGGER ON UPDATE; known timing: cron schedule.

@ DBX-DAA D4 T4.4 applied troubleshooting
S: A streaming table reads from a source Delta table. After a data correction updated several existing rows in that source, the next refresh of the streaming table fails. What is the cause and the better fit?
A: Streaming reads expect append-only input and error on changed rows; a materialized view suits changing sources
B: The streaming table reached its row limit; deleting the table and recreating it as a view fixes this
C: The SQL warehouse is out of cache; restarting it lets streaming tables process updates normally
D: Streaming tables cannot be refreshed after creation; a new table is needed for every new batch
K: A
G: ## Source semantics
A streaming table reads its source with streaming semantics. If the read encounters a change or deletion to an existing record, an error is thrown, so it is safest to read from static or append-only sources. Each row is processed once, and later changes in the source are not re-evaluated.
When source rows change, a **materialized view** is more appropriate because it recomputes or incrementally updates its result to match the source.
W: Append-only expectation: updated rows break the streaming read, and a materialized view handles changing source data.
X: B=Row limit and view: no such limit causes this; a standard view would not store data and does not replace ingestion logic.
C=Cache: caching does not affect streaming semantics; this error comes from the source change.
D=No refresh: streaming tables accept the `REFRESH` command to process new data, so recreating for every batch is unnecessary.
T: Changing source rows break streaming tables; use a materialized view for sources that update or delete.
