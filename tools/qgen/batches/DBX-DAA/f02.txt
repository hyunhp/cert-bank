@ DBX-DAA D1 T1.1 applied use-case
S: A product team needs a low-latency transactional backend for an internal app that records order status updates, and it wants the lakehouse tables in Unity Catalog available to the same app with Postgres queries. Which Databricks component fits?
A: A serverless SQL warehouse, because it is optimized for many small single-row transactions issued by application users
B: Lakebase, a fully managed OLTP database service with synced copies of lakehouse data and standard driver access
C: A Lakeflow Declarative Pipeline, because it hosts the Postgres endpoints applications connect to
D: A Databricks Marketplace listing, because installing it turns a Delta table into a row-store with millisecond updates
K: B
G: ## OLTP versus analytics
Analytical engines scan many rows to aggregate; transactional apps update single rows quickly. Databricks covers the second need with **Lakebase**, a fully managed Postgres database integrated with the platform (autoscaling, scale to zero, branching, Unity Catalog integration). Applications connect with `psql` or any Postgres driver, and Unity Catalog tables can be synced into Lakebase so apps read lakehouse data at low latency.
A SQL warehouse is built for analytical queries, pipelines transform data, and Marketplace distributes data products.
W: Lakebase: it is a managed Postgres database for transactional applications and can serve lakehouse data to them through synced tables.
X: A=SQL warehouse: it runs analytical SQL over large data and is not an OLTP row-store for application transactions.
C=Lakeflow Declarative Pipeline: a pipeline defines and refreshes datasets; it exposes no Postgres endpoints for applications.
D=Marketplace listing: Marketplace is where providers publish datasets, models and notebooks, and it does not change a table's storage layout.
T: Lakebase = managed Postgres for transactional apps next to the lakehouse; SQL warehouses = analytics.
V: Lakebase

@ DBX-DAA D9 T9.2 applied use-case
S: The catalogs `dev` and `prod` both contain a schema `crm` with a table `customers`. An analyst with access to both wants to compare their row counts in a single query on one SQL warehouse. Which statement describes what is possible?
A: It is only possible after copying one table into the other catalog, because a query reads from one catalog at a time
B: It is possible with `crm.customers` written twice, if `USE CATALOG` is executed between the two subqueries of the same statement
C: It needs two warehouses, one per catalog, and the results must be joined in a spreadsheet afterwards
D: It is possible with fully qualified three-part names for each table, since every catalog of the metastore is reachable
K: D
G: ## One metastore, many catalogs
Catalogs are the top containers of a metastore, and all catalogs of a metastore are visible to a query that has privileges on them. Three-part names make each reference unambiguous, so one statement can mix tables from several catalogs:
```
SELECT 'dev', count(*) FROM dev.crm.customers
UNION ALL
SELECT 'prod', count(*) FROM prod.crm.customers
```
The same table name in different schemas or catalogs is normal and is the reason qualification matters. Privileges still apply to each object, so the analyst needs access on both.
W: Three-part names in one statement: both catalogs belong to the same metastore, so the query can reference both objects directly.
X: A=Copy first: a single query can read several catalogs, so no copy is needed, and copying would add cost and staleness.
B=USE CATALOG between subqueries: the session catalog is fixed for the duration of a statement and cannot be switched within it, so both subqueries would resolve to the same catalog.
C=Two warehouses: a warehouse is compute and is not tied to a catalog, so one warehouse can read all catalogs the user may access.
T: Fully qualified catalog.schema.table names let one query combine objects from several catalogs of the same metastore.
V: Unity Catalog namespace

@ DBX-DAA D4 T4.8 applied comparison
S: A team has a curated sales table in Unity Catalog that only Databricks users read, and the analyst wants Databricks to handle file compaction, optimization and storage placement automatically. Which table type does this?
A: Managed table, because the platform owns its files and runs predictive optimization on them
B: External table, because Unity Catalog optimizes only data that sits in a customer-owned bucket
C: Foreign table, because it copies the source into managed storage and tunes the layout
D: Temporary view, because it stores a tuned version of the data for the session
K: A
G: ## What managed tables add
Unity Catalog managed tables are the default and recommended type for Delta Lake and Apache Iceberg. Unity Catalog handles reads, writes, storage and optimization, using features such as automatic file compaction and intelligent statistics collection, and predictive optimization maintains them. Compared to external or foreign tables they usually cost less to store and query. External tables keep control of the files with you; foreign tables only point at data in another system (for example through federation) and Databricks does not maintain their files.
W: Managed table: storage location and table maintenance are handled by Unity Catalog, so compaction and optimization happen without the analyst doing anything.
X: B=External table: Unity Catalog governs metadata but does not manage the data lifecycle, optimization or storage location of an external table.
C=Foreign table: it represents data in an external system through federation, and it is not copied or tuned by Databricks.
D=Temporary view: it holds only a query definition for the session and stores no tuned data.
T: Want Databricks to own storage and optimization: managed table.

@ DBX-DAA D4 T4.4 advanced tradeoff
S: A materialized view feeds a morning report. Upstream loads land at unpredictable times, and the team wants the view to update shortly after source data changes without keeping a fixed cron schedule. Which option fits?
A: Convert the materialized view to a temporary view so that it is always current
B: Define the materialized view with a daily cron schedule at the earliest possible hour
C: Disable refreshes and run a full CREATE OR REPLACE by hand whenever someone remembers
D: Define the view with TRIGGER ON UPDATE so it refreshes once its input tables are written
K: D
G: ## Refresh options
A materialized view can refresh by a **cron schedule** (`SCHEDULE CRON ...`), **on trigger** (`TRIGGER ON UPDATE`, refreshes whenever the upstream source data changes), or manually with `REFRESH MATERIALIZED VIEW`. Databricks says to use trigger-based refresh for production workloads, especially when upstream dependencies don't run on predictable schedules.
Refresh may be incremental (only changed data) or full; a cost model chooses by default.
W: TRIGGER ON UPDATE: the view refreshes after the source changes, which fits loads at unpredictable times and avoids a fixed schedule.
X: A=Temporary view: it stores no results, so it would re-run the full query on every read instead of precomputing.
B=Daily cron early: a fixed time either runs before late loads and shows stale data, or wastes work if the data arrives sooner.
C=Manual refresh: this relies on memory and defeats automation for a recurring report.
T: Unpredictable upstream timing: TRIGGER ON UPDATE; known timing: cron schedule.
