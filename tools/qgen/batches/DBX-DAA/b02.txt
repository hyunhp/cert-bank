@ DBX-DAA D2 T2.1 applied use-case
S: A finance analyst must build a quarterly report on customer revenue. Three similar tables exist in the workspace, and the analyst wants the one the data team has signed off as meeting the organization's standards. Which approach finds it?
A: Sort the three tables by creation date in Catalog Explorer and use the newest, because newer tables are always the approved ones
B: Search with the certification status filter, or `certificationStatus:certified`, and pick the table that shows the certified check mark
C: Choose the table with the longest comment, because only certified tables are allowed to carry detailed column descriptions
D: Run `SHOW TABLES` in each schema and pick the table whose name ends in `_final`, since Unity Catalog marks certified tables with that suffix
K: B
G: ## Certified and deprecated data
Unity Catalog lets owners flag a data asset with the **certification status** system tag, whose key is `system.certification_status`.
- `certified` means the asset met internal standards for accuracy, completeness and trust. It shows a check mark in the workspace.
- `deprecated` warns that the asset is outdated and should not be used in new work. It shows a restricted icon.
The tag can be applied to catalogs, schemas, tables, views, volumes, dashboards and more. Only users with the `ASSIGN` permission on that governed tag (plus the usual `APPLY TAG` rights) can set it, so the badge is a trustworthy signal, unlike a naming habit.
## Finding certified data
In search you can add the `certificationStatus` keyword, for example `type:table certificationStatus:certified`, or use the Certification status filter. Updates can take a few minutes to appear.
W: Certification search: the certification status tag is the governed signal that a table was approved, and the filter or keyword returns only assets carrying it.
X: A=Newest table: creation date says nothing about approval; a fresh copy may be an unreviewed experiment while the certified table is older.
C=Longest comment: comments are free text anyone with the right privilege can write on any table, and there is no rule tying detail to certification.
D=`_final` suffix: names are conventions only; `SHOW TABLES` lists names and Unity Catalog never adds a suffix to certified assets.
T: Look for the certification status tag (check mark), not for age, comments or names.
V: Unity Catalog, Catalog Explorer

@ DBX-DAA D2 T2.1 applied definition
S: An analyst can see a table in Catalog Explorer search results but gets a permission error when running `SELECT * FROM main.sales.orders`. The analyst has `BROWSE` on the catalog. What explains this?
A: The `BROWSE` privilege lets a user discover an object's metadata, but reading rows also needs `USE CATALOG`, `USE SCHEMA` and `SELECT`
B: The table is a managed table, and Unity Catalog allows only external tables to be queried from a SQL editor
C: Search results only list objects that are deprecated, and deprecated tables are blocked from all queries
D: `BROWSE` already gives read access, so the error means the SQL warehouse is stopped and must be restarted by an administrator
K: A
G: ## Discovering is not reading
Unity Catalog separates seeing that data exists from reading it.
- `BROWSE` lets a user see an object's metadata (name, comments, lineage) in Catalog Explorer and search, without reading data.
- To query a table you need `USE CATALOG` on the catalog, `USE SCHEMA` on the schema and `SELECT` on the table. Access is checked at every level of the three-level name `catalog.schema.table`.
So a request-access flow starts with the owner granting the missing privileges, not with a change of compute.
W: Privilege levels: `BROWSE` exposes metadata only; a query additionally needs `USE CATALOG`, `USE SCHEMA` and `SELECT`.
X: B=Table type: managed tables are fully queryable, and no rule limits SQL editors to external tables.
C=Deprecated filter: search lists any object you may browse; deprecation is a label and does not block queries.
D=Warehouse state: a stopped warehouse starts on demand or reports a compute error, not a permission error, and `BROWSE` never grants data reads.
T: BROWSE = see metadata; querying needs USE CATALOG, USE SCHEMA and SELECT.
V: Unity Catalog

@ DBX-DAA D2 T2.2 applied definition
S: A governance team wants every table that holds personal data to carry a `classification` tag, and only the values `public`, `internal` and `pii` must be accepted. Analysts must not invent other values. Which tag type fits?
A: A governed tag, which is account-level and lets administrators define allowed values and control who can assign it
B: An ungoverned tag, because it validates its values against a centrally maintained list of allowed entries
C: A table comment, since Unity Catalog parses comment text and rejects any value outside an allowed list
D: A system table column, which the SQL warehouse fills in automatically with a default classification for every new table
K: A
G: ## Tags in Unity Catalog
Tags are key-value labels on securable objects (catalogs, schemas, tables, columns, volumes and others). They support search and classification.
- **Ungoverned tags** are free form: users with `APPLY TAG` can use any key and value.
- **Governed tags** are account-level tags with enforced rules: the allowed keys and values are defined centrally, and only users or groups with the right permission (`ASSIGN`) can assign them. They are marked with a lock in the UI.
- **System tags** are governed tags predefined by Databricks, such as `system.certification_status`.
If a governed tag is deleted, existing assignments become ungoverned and anyone can edit them, so deletion needs care.
W: Governed tag: allowed values are defined once at account level and assignment is permission controlled, which keeps classifications consistent.
X: B=Ungoverned tag: free-form tags accept any value, so inconsistent labels like `PII` and `personal` could appear.
C=Table comment: comments are plain text that Unity Catalog does not validate or search by tag semantics.
D=System table column: system tables report metadata and usage but do not classify data automatically.
T: Governed tags enforce allowed values and who may assign them.
V: Unity Catalog tags

- Lineage requires tables to be registered in Unity Catalog and queries to use Spark DataFrames or Databricks SQL interfaces such as notebooks and the SQL editor.

@ DBX-DAA D2 T2.3 applied use-case
S: A table `orders` has a nullable column `discount`. The analyst needs `total - discount` for every order and wants rows with a missing discount to be treated as zero rather than producing NULL totals. Which expression does this?
A: `total - NULLIF(discount, 0)`
B: `total - COALESCE(discount, 0)`
C: `total - discount WHERE discount IS NOT NULL`
D: `total - CAST(discount AS STRING)`
K: B
G: ## NULL arithmetic
In SQL, any arithmetic with NULL gives NULL. `total - NULL` is NULL, so rows with a missing discount would vanish from sums.
- `COALESCE(a, b, ...)` returns the first non-null argument; `COALESCE(discount, 0)` replaces NULL with 0.
- `NULLIF(a, b)` does the opposite: it returns NULL when `a = b`.
- Filtering with `WHERE discount IS NOT NULL` removes rows rather than keeping them.
W: COALESCE: it substitutes 0 for a missing discount, so the subtraction returns the total for every row.
X: A=NULLIF: it converts a zero discount to NULL, which makes more NULL results instead of fewer.
C=Invalid placement: `WHERE` is a clause of a query and not part of an expression; filtering would also drop rows with a missing discount.
D=CAST to STRING: subtracting from a string is not a numeric operation and leaves NULL as NULL.
T: COALESCE replaces NULL with a default so arithmetic keeps every row.

@ DBX-DAA D2 T2.3 applied troubleshooting
S: A `customers` table stores country as free text, with values such as `USA`, `usa`, `Usa ` (trailing space) and `U.S.A.`. A report grouped by `country` lists the first three as separate rows. Which change merges the first three spellings into one group without altering the table?
A: Group by `lower(trim(country))` in the query, so case and surrounding spaces no longer split the groups
B: Add `DISTINCT` to the select list, because it treats text that differs only in case as equal
C: Sort the result with `ORDER BY country`, because sorting merges neighboring spellings of one value
D: Filter with `WHERE country IS NOT NULL`, because the extra spellings are stored as missing values
K: A
G: ## Standardizing text before grouping
Text comparison in Databricks SQL is case sensitive and counts every character, including spaces. `USA`, `usa` and `Usa ` are therefore different values, and `GROUP BY` and `DISTINCT` keep them apart.
- `lower(col)` (or `upper`) removes case differences, and `trim(col)` removes leading and trailing spaces.
- Apply them in the query, in a view or in a cleaned copy of the table, so raw data stays intact.
- Different spellings such as `U.S.A.` need a mapping (for example a `CASE` expression or a lookup table) because no function can guess that they mean the same country.
W: lower and trim: normalizing the text inside the grouping expression makes the three spellings identical, so they form one group.
X: B=DISTINCT: it removes duplicate rows by exact value, and values that differ in case or spaces are not duplicates.
C=ORDER BY: sorting only changes row order and never merges groups.
D=IS NOT NULL: the extra spellings are real text values and not NULL, so the filter changes nothing.
T: Normalize text with lower() and trim() before grouping or joining.
V: Databricks SQL

@ DBX-DAA D2 T2.3 advanced troubleshooting
S: A query `SELECT count(*) FROM payments WHERE id NOT IN (SELECT payment_id FROM refunds)` returns 0, although many payments have no refund. The `refunds.payment_id` column contains some NULL values. Which rewrite returns the payments without refunds?
A: `... WHERE id NOT IN (SELECT DISTINCT payment_id FROM refunds)`
B: `... WHERE id <> ALL (SELECT payment_id FROM refunds)`
C: `... WHERE NOT EXISTS (SELECT 1 FROM refunds r WHERE r.payment_id = payments.id)`
D: `... WHERE id NOT IN (SELECT payment_id FROM refunds) OR id IS NULL`
K: C
G: ## NOT IN and NULL
`x NOT IN (list)` is true only if `x` differs from every item. If the list contains a NULL, the comparison with that item is unknown, so the whole predicate can never be true. A single NULL in the subquery therefore returns no rows.
Safer patterns:
- `NOT EXISTS` with a correlated subquery, which ignores NULL join keys.
- Exclude NULLs in the subquery: `WHERE payment_id IS NOT NULL`.
- A `LEFT ANTI JOIN`.
W: NOT EXISTS: it checks for a matching row per payment, so NULL keys in the refunds table do not poison the result.
X: A=DISTINCT: removing duplicates leaves the NULL value in the list, so the predicate is still never true.
B=`<> ALL`: this is the same logic as NOT IN and behaves identically with NULLs.
D=OR id IS NULL: adds only rows whose id itself is NULL and does not rescue the other rows.
T: Prefer NOT EXISTS or an anti join over NOT IN when NULLs are possible.
V: Databricks SQL

@ DBX-DAA D2 T2.3 applied use-case
S: A raw `sales_raw` table stores `amount` as STRING, and some values are text like `n/a`. A plain `CAST(amount AS DOUBLE)` fails the query in ANSI mode. The analyst wants invalid values to become NULL instead. Which function should be used?
A: `try_cast(amount AS DOUBLE)`, which returns NULL for unconvertible values
B: `nvl(amount, 'n/a')`, which replaces NULL values with the text `n/a`
C: `ifnull(amount, 0)`, which replaces NULL values with the number zero
D: `typeof(amount)`, which returns the data type name of the column
K: A
G: ## Safe conversion
In ANSI mode, `CAST` raises an error when a value cannot be converted. `try_cast(expr AS type)` returns NULL instead when the cast is unsupported for that value. You can then combine it with other functions: `COALESCE(try_cast(amount AS DOUBLE), 0)` or filter rows where the result `IS NULL` to review the bad records.
`nvl` and `ifnull` replace NULLs, which does not help here because the bad values are not NULL, and `typeof` only reports a data type.
W: try_cast: it converts valid text to numbers and returns NULL for values such as `n/a`, so the query keeps running.
X: B=nvl: it substitutes a value only when the input is NULL, and the text `n/a` is not NULL.
C=ifnull: it replaces NULL with zero, but `n/a` is text and not NULL, and it does not convert types or catch cast errors.
D=typeof: it returns the data type name of the expression and changes no data.
T: try_cast turns un-castable values into NULL instead of failing the query.
V: Databricks SQL

@ DBX-DAA D2 T2.3 applied use-case
S: A `signups` table has several rows for the same `user_id` because of repeated imports. The analyst needs one row per user, keeping the most recent `updated_at`. Which query pattern fits?
A: `SELECT DISTINCT user_id, updated_at FROM signups`, removing duplicate user rows
B: `SELECT user_id, MAX(updated_at) FROM signups`, taking the newest timestamp per user
C: `SELECT * FROM signups ORDER BY updated_at DESC LIMIT 1`, taking the newest row of the whole signups table
D: `SELECT * FROM signups QUALIFY row_number() OVER (PARTITION BY user_id ORDER BY updated_at DESC) = 1`
K: D
G: ## De-duplicating rows
Duplicates that differ in some columns cannot be removed with `DISTINCT`, which only collapses fully identical rows.
- Number the rows in each group with `row_number() OVER (PARTITION BY key ORDER BY updated_at DESC)`.
- Keep number 1. Databricks SQL supports `QUALIFY` to filter on window results directly; a subquery with `WHERE rn = 1` works as well.
- `MAX(updated_at)` alone needs a `GROUP BY user_id` and returns only the key and timestamp, not the other columns of the latest row.
W: row_number with QUALIFY: it picks exactly one most recent row per user and keeps every column.
X: A=SELECT DISTINCT: each version has a different timestamp, so all versions remain.
B=Aggregate without GROUP BY: this is invalid with a non-aggregated column, and even with grouping it returns just the latest timestamp.
C=LIMIT 1: it returns one row for the whole table, not one per user.
T: Use row_number() over a partition (with QUALIFY) to keep one row per key.

@ DBX-DAA D2 T2.3 applied use-case
S: An analyst finds 40 rows in a managed Delta table `sensors` where `temperature` is -999, a placeholder for failed readings. The analyst owns the table and wants those rows permanently removed so that all dashboards stop using them. Which statement does this?
A: `SELECT * FROM sensors WHERE temperature <> -999`
B: `DROP TABLE sensors`
C: `DELETE FROM sensors WHERE temperature = -999`
D: `TRUNCATE sensors WHERE temperature = -999`

G: ## Filter or delete
- A `SELECT ... WHERE` filter hides bad rows only for that query. Anyone reading the table still sees them.
- On a Delta table the owner can run `DELETE FROM table WHERE condition`, a transactional change that removes the matching rows (the old files stay for time travel until `VACUUM`).
- Another approach is a cleaned copy: `CREATE OR REPLACE TABLE sensors_clean AS SELECT ... WHERE ...`, or a view that filters the placeholder, which keeps raw data intact.
Pick the permanent delete only when the rows are truly invalid and you are allowed to modify the table.
W: DELETE with a predicate: it removes exactly the placeholder rows from the Delta table for every reader.
X: A=SELECT filter: this leaves the 40 rows in the table, so other dashboards still read them.
B=DROP TABLE: it removes the whole table and all valid readings.
D=TRUNCATE with WHERE: `TRUNCATE` removes all rows and does not accept a row filter.
T: Use DELETE ... WHERE for permanent row removal; a SELECT filter only hides rows per query.

C: `revenue / abs(orders)`

K: A
G: ## Avoiding divide by zero
Division by zero errors in ANSI mode, while dividing by NULL returns NULL. `NULLIF(orders, 0)` returns NULL when `orders` is 0 and the original value otherwise, which turns the dangerous divisor into a NULL result.
Alternatives: `try_divide(revenue, orders)`, which returns NULL on division by zero. Wrapping with `COALESCE(..., 0)` afterwards sets a display default if required.
W: NULLIF: a zero divisor becomes NULL, so the division returns NULL rather than raising an error.
X: B=COALESCE on divisor: it would turn NULL into 0, which creates the error instead of avoiding it.
C=abs: the absolute value of 0 is still 0, so the division by zero error remains.
D=orders + 1: it changes the arithmetic for all rows and produces wrong values.
T: NULLIF(divisor, 0) is the standard guard against divide-by-zero.

@ DBX-DAA D3 T3.1 applied comparison

@ DBX-DAA D3 T3.2 applied troubleshooting
S: An analyst tries to upload a CSV into the volume `main.raw.files` through Catalog Explorer and the upload is rejected with a permission error, although the analyst can read the volume. Which privilege is missing?
A: `WRITE VOLUME` on the volume, together with `USE SCHEMA` and `USE CATALOG` on its parents

Reading and writing files in a Unity Catalog volume use separate privileges.
- `READ VOLUME` lets a user list and read files.
- `WRITE VOLUME` lets a user upload, overwrite and delete files; the UI upload also needs `USE SCHEMA` on the parent schema and `USE CATALOG` on the parent catalog.

Being able to read a volume therefore says nothing about being able to upload to it.

X: B=MODIFY: it controls changing rows of a table and has no role for files in a volume.
C=CREATE SHARE: it is for creating shares to send data out and has nothing to do with writing files.
D=SELECT: it applies to tables and views, while reading a volume uses `READ VOLUME`.
