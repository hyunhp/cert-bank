@ AIP-C01 D5 T5.1 advanced definition
S: An agent's final answers are correct 95% of the time, but traces show it often calls the payment tool twice and uses nine tool calls where three would do. Which evaluation approach would detect these problems?
A: Trajectory evaluation of the tool-call sequence and arguments against expected paths
B: End-to-end latency percentiles per session, tracked against a service-level target
C: Counting guardrail interventions per session and alerting when the rate rises
D: Final-answer correctness scoring against a golden dataset of expected replies
K: A
G: ## Final-answer evaluation versus trajectory evaluation
- **Final-answer (outcome) evaluation** compares the agent's last answer with an expected answer. It says whether the result is right.
- **Trajectory evaluation** looks at the path: which tools were called, in which order, with which arguments, and how many steps were taken. The observed path is compared with one or more expected paths, for example "look up order, then call payment once".
## Why an agent can be right and still wrong
An agent can reach the correct answer by an unsafe or wasteful route. Calling a payment tool twice might charge the customer twice even though the reply text looks fine. Nine tool calls instead of three add latency and cost. Trajectory checks catch both:
- duplicate side-effecting calls (the same `payment` call with the same arguments)
- step count above the expected path length
- wrong arguments or wrong ordering
The trace data from Bedrock Agents, AgentCore Observability or your own tool-call logs provides the sequence to score.
Note: Amazon Bedrock Agents was renamed Bedrock Agents Classic and closed to new customers on 2026-07-30; existing customers can keep using it, and AWS points new agent builds to Amazon Bedrock AgentCore. Trajectory evaluation works the same way whichever runtime produced the trace.
W: Trajectory evaluation of tool-call sequence and arguments: it scores the path itself, so duplicate payment calls and redundant steps are flagged even when the final answer is correct.
X: B=End-to-end latency percentiles: extra calls may raise latency, but the percentile cannot say which calls were redundant or that a payment ran twice.
C=Guardrail intervention counts: guardrails check content against policies. Duplicate or excessive tool calls do not violate content policies, so the count would not move.
D=Final-answer correctness against a golden dataset: answers are already correct 95% of the time, so this metric would look healthy while duplicate payments continue.
T: When the answer is right but the path is wrong, only trajectory evaluation (tools, order, arguments, step count) can see the problem.
V: Amazon Bedrock Agents, Amazon Bedrock AgentCore

@ AIP-C01 D3 T3.2 applied use-case
S: A company wants only its 'ml-research' IAM role to be able to invoke a specific set of approved, cost-controlled foundation models in Bedrock, while blocking that role from invoking any other model. Which approach best achieves this?
A: An identity policy on that principal allowing bedrock:InvokeModel on vetted model ARNs only
B: A CloudWatch alarm on invocation counts per model that notifies when other roles call them
C: A Bedrock guardrail with denied topics that name each unapproved model to block
D: An S3 bucket policy on the model artifacts bucket restricting reads to the role
K: A
G: ## How Bedrock model access is authorized
Every call to a model in Amazon Bedrock is an API action checked by IAM: `bedrock:InvokeModel` (also used by the Converse API) and `bedrock:InvokeModelWithResponseStream` (also used by ConverseStream). The resource in the policy is the model's ARN, for example `arn:aws:bedrock:us-east-1::foundation-model/amazon.nova-pro-v1:0`.
## Allow lists and implicit deny
IAM denies everything by default. If the `ml-research` role's only Bedrock permission is an Allow on a short list of model ARNs, any other model is implicitly denied and the call fails with AccessDenied before a single token is generated.
- List each approved foundation model ARN (and any inference profile ARN the role must use, since cross-Region inference calls target the profile).
- Optionally add an explicit Deny with `NotResource` so a later, broader Allow cannot widen access.
W: Model-scoped IAM policy: an Allow for `bedrock:InvokeModel` on only the approved model ARNs is a preventive control on the exact caller and the exact resource, so unapproved models are blocked at authorization time.
X: B=CloudWatch alarm: a metric alarm only notifies after invocations have already run and been billed; it cannot stop the role from calling an unapproved model.
C=Guardrail denied topics: denied topics filter the subject matter of prompts and responses (for example, "investment advice"); they have no notion of which model ID the caller chose and cannot refuse a call based on it.
D=S3 bucket policy: Bedrock foundation models are served by Bedrock, not read from a bucket in your account, so restricting an artifacts bucket has no effect on which models can be invoked.
T: Deciding who may call which model is an IAM authorization problem (Allow on specific model ARNs), not a content filter or an after-the-fact alarm.
V: Amazon Bedrock, AWS IAM
