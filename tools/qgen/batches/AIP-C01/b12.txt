@ AIP-C01 D1 T1.4 expert troubleshooting
S: A company builds a Bedrock knowledge base on an Amazon S3 vector bucket. A developer created the vector index with the AWS CLI using only the dimension and distance metric. Chunking is fixed-size at 500 tokens (about 2,300 characters), a size the team tuned and must keep. Each document has a .metadata.json file with 40 attributes, including a 1.4 KB summary field. The first sync fails for every document with an exception that vector metadata exceeds the allowed size. The team wants the fewest changes that let every document ingest. Which TWO changes are required? (Select TWO)
A: Create a new vector index declaring AMAZON_BEDROCK_TEXT and AMAZON_BEDROCK_METADATA as non-filterable keys, and re-create the knowledge base on it
B: Reduce each document's custom metadata to at most 35 keys and 1 KB in total, for example by moving the long summary into the document body
C: Switch to hierarchical chunking with 300-token child chunks, so that each stored vector carries less text in its metadata than a 500-token chunk
D: Request a service quota increase for filterable metadata per vector to 8 KB, so that the chunk text fits beside all of the custom attributes on each vector
E: Lower the fixed chunk size to 400 tokens and raise the overlap, so that each chunk's text fits under the filterable metadata limit per vector
K: A,B
G: ## Where a knowledge base puts data in S3 Vectors
For every chunk, Bedrock writes a vector plus metadata. Two service fields carry the chunk text (`AMAZON_BEDROCK_TEXT`) and Bedrock's own metadata (`AMAZON_BEDROCK_METADATA`); your `.metadata.json` attributes are added too.
## Limits that apply
- In S3 Vectors, metadata is **filterable by default**; keys can be declared **non-filterable only when the index is created**. Filterable metadata per vector is limited to **2 KB**.
- AWS instructs you to add `AMAZON_BEDROCK_TEXT` and `AMAZON_BEDROCK_METADATA` as non-filterable keys when you create the index for a knowledge base.
- With Knowledge Bases, custom metadata is limited to **1 KB** and **35 keys** per vector. If metadata exceeds the limits, the ingestion job throws an exception.
## Working the numbers
A 500-token chunk is about 2,300 characters, already above 2 KB if the text field is filterable. Separately, 40 attributes break the 35-key limit, and a 1.4 KB summary alone breaks the 1 KB custom metadata limit. Two independent problems, so two fixes.
W: A=New index with non-filterable service keys: the chunk text and Bedrock metadata move out of the 2 KB filterable budget; because that setting exists only at index creation, a new index (and knowledge base) is needed.
B=Trim custom metadata: 35 keys and 1 KB are fixed knowledge base limits, so the summary must leave the metadata file and the key count must drop.
X: C=Hierarchical chunking: AWS warns that hierarchical chunking can exceed S3 Vectors metadata limits because parent-child context is stored as metadata, and it leaves the custom metadata problem untouched.
D=Quota increase: the 2 KB filterable limit is a documented S3 Vectors restriction, and the requirement is to store the text as non-filterable, not to enlarge filterable space.
E=400-token chunks: about 1,850 characters plus Bedrock metadata still crowd the 2 KB limit, the team must keep 500 tokens, and the 40-key metadata still fails.
T: For S3 Vectors knowledge bases, declare AMAZON_BEDROCK_TEXT and AMAZON_BEDROCK_METADATA non-filterable at index creation and keep custom metadata within 1 KB and 35 keys.
V: Amazon Bedrock Knowledge Bases, Amazon S3 Vectors

@ AIP-C01 D1 T1.5 expert troubleshooting
S: A maintenance assistant uses a Bedrock knowledge base on Amazon OpenSearch Serverless with hierarchical chunking: 1,500-token parent chunks and 300-token child chunks. Retrieve is called with numberOfResults set to 5. Technicians ask broad questions such as "what changes between the summer and winter service of pump model P7?", which need text from six or more sections, but each answer cites only one or two sections. Logs show that the five matching child chunks usually belong to the same two parents. The prompt can hold at most 12,000 tokens of retrieved text, and the team wants to keep hierarchical chunking. Which change fixes the problem within the budget?
A: Raise numberOfResults to 8, so up to eight child matches resolve to at most eight parents, which is 12,000 tokens in the worst case
B: Raise numberOfResults to 20, so the retrieval returns many more child matches and can cover up to twenty different sections per answer
C: Raise the parent chunk size to 3,000 tokens, so that each returned parent holds more of the surrounding manual sections for the model
D: Lower the child chunk size to 150 tokens, so that the five child matches are spread over more parents and more of the sections come back
K: A
G: ## How hierarchical retrieval counts results
With hierarchical chunking, the vector search runs over **child** chunks, and each matching child is then **replaced by its parent**. AWS documents two consequences:
- `numberOfResults` maps to the **number of child chunks** retrieved.
- Children that share a parent collapse into **one** result, so you can get fewer results than requested.
## Working the numbers
- Today: 5 children in 2 parents -> 2 results -> 3,000 tokens, too few sections.
- With 8 children: at most 8 distinct parents -> at most 8 x 1,500 = **12,000 tokens**, exactly the budget, and enough slots to reach six sections.
- With 20 children: up to 20 parents -> up to **30,000 tokens**, far over the budget.
- Bigger parents (3,000 tokens) halve how many fit in the budget; smaller children do not raise the cap of 5 results.
W: numberOfResults 8: more child matches give more chances to land in different parents, and the worst case of eight distinct parents is still exactly 12,000 tokens.
X: B=numberOfResults 20: it reaches more sections, but twenty distinct parents would be 30,000 tokens, more than twice the prompt budget.
C=3,000-token parents: still only two parents come back, each twice as long, and only four parents would fit the budget at all.
D=150-token children: with numberOfResults at 5 the answer can never contain more than five parents, and smaller children cluster in the same sections just as before.
T: In hierarchical chunking, numberOfResults counts child chunks; size it so the worst case of distinct parents fits the prompt budget.
V: Amazon Bedrock Knowledge Bases, Amazon OpenSearch Serverless

@ AIP-C01 D1 T1.2 expert troubleshooting
S: An insurer wants to distill a large model into a smaller student for claim triage, reusing responses that production already paid for. Invocation logging delivers to Amazon S3, and 60,000 logged calls carry requestMetadata with project=claims and an intent key. The production model was upgraded to version 2 three months ago, but the distillation job names version 1 as the teacher and selects prompt-response pairs, using the filter project=claims AND (intent=fnol OR intent=update). The job is rejected. There is no budget for new teacher inference, and only claims traffic may be used. Which change lets the job run within these rules?
A: Name the version 2 model behind the logged responses as teacher, and filter with one AND on project=claims and a new distill=yes key
B: Keep version 1 as teacher and switch to using prompts only, so that Bedrock generates fresh teacher responses for the logged claims prompts
C: Keep both filter groups but submit them as two separate distillation jobs, one for intent=fnol and one for intent=update, each with version 1
D: Switch invocation logging from Amazon S3 to CloudWatch Logs only, because distillation jobs read prompt-response pairs from log groups directly
K: A
G: ## Distillation from invocation logs
Amazon Bedrock Model Distillation can build its training data from **invocation logs**:
- Logging must be on and delivered to an **Amazon S3** destination that Bedrock can read.
- You choose **prompts only** (Bedrock calls the teacher again and pays teacher inference) or **prompt-response pairs** (existing responses are reused).
- For pairs, the teacher named in the job must **match the model in the logs**; if not, the logs are not used, and you need **at least 100 pairs** that exactly match the teacher.
- `requestMetadata` attached at invocation time can filter the logs. With multiple metadata conditions you use **a single Boolean operator** (AND, OR, or NOT); operators cannot be combined.
## Reading the rejection
Two rules are broken at once: every logged response came from version 2 (zero matching pairs for a version 1 teacher), and the filter mixes AND with OR. Tagging the desired claims traffic with one extra key lets a single AND express the selection.
W: Version 2 teacher plus single-operator filter: the logged pairs match the teacher, no new teacher inference is needed, and a single AND on project=claims and distill=yes selects only approved claims traffic.
X: B=Prompts only with version 1: Bedrock would call the teacher again for every prompt, which is the new teacher inference the budget forbids.
C=Two jobs with version 1: each job still names a teacher that produced none of the logged responses, so neither finds matching pairs.
D=CloudWatch Logs only: distillation reads invocation logs stored in S3; moving away from S3 removes the data source instead of fixing it.
T: Distilling from logged pairs requires the job's teacher to match the logged model exactly and metadata filters that use a single Boolean operator.
V: Amazon Bedrock, Amazon S3

@ AIP-C01 D1 T1.1 expert use-case
S: A German bank designs a RAG assistant on Amazon Bedrock with a guardrail contextual grounding check. Customers chat in German, answers paraphrase and reason over policy text, and a pilot on Classic tier blocked many correct answers as ungrounded. All prompts and responses must stay in the EU. Retrieve returns 25 chunks of about 5,000 characters each, conversations average 4,000 characters of history, and answers are at most 3,000 characters. The team wants the grounding check to be reliable and to stay within the documented input sizes. Which THREE design decisions meet these requirements? (Select THREE)
A: Use Standard tier for the grounding check with an EU guardrail profile, so inference stays in EU Regions and conversational answers are handled
B: Reduce numberOfResults to 15, so the grounding source is about 75,000 characters and stays below the 100,000-character limit for the source
C: Tag only the customer's latest question as the query, not the whole conversation, so the query stays below the 1,000-character limit for queries
D: Keep Classic tier and lower the grounding threshold to 0.2, so that paraphrased German answers pass while ungrounded answers are still blocked
E: Tag the full 4,000-character conversation history as the query, so the relevance check can compare each answer with all earlier customer turns
F: Keep numberOfResults at 25 and tag every chunk as a grounding source, because each grounding_source tag is evaluated separately against the limit
K: A,B,C
G: ## What the contextual grounding check needs
The check scores a model response against a **grounding source** (the retrieved text) and a **query** (the user's question), producing grounding and relevance scores compared with your thresholds.
## Documented limits and behavior
- Maximum sizes: **100,000 characters** for the grounding source, **1,000 characters** for the query, **5,000 characters** for the response.
- Multiple `grounding_source` tags are **combined and evaluated together**, as are multiple query tags.
- **Classic tier** evaluates strict grounding (reasonable inferences and conversational phrasing lower the score) and supports English, French, and Spanish.
- **Standard tier** supports reasoning and conversational responses and more languages, and **requires cross-Region inference** through a guardrail profile, which keeps guardrail inference inside the geography.
## Working the numbers
25 x 5,000 = 125,000 characters (over the limit); 15 x 5,000 = 75,000 (under). A 4,000-character history is four times the query limit; the latest question fits. Answers of 3,000 characters fit the 5,000 response limit.
W: A=Standard tier with an EU profile: it handles German and conversational, reasoning answers, and the EU guardrail profile keeps inference inside the EU.
B=15 results: the combined grounding source drops to about 75,000 characters, inside the 100,000 limit.
C=Latest question as query: it keeps the query under 1,000 characters while still letting the relevance check compare the answer with what was asked.
X: D=Classic at 0.2: Classic tier does not support German, and a very low threshold lets ungrounded answers through, so reliability falls.
E=History as query: 4,000 characters is four times the 1,000-character query limit.
F=Tag every chunk: multiple grounding_source tags are combined and evaluated together, so 125,000 characters still exceeds the limit.
T: Size grounding checks to their limits (100,000-character source, 1,000-character query) and use Standard tier with a geography-scoped profile for conversational, non-English answers.

@ AIP-C01 D1 T1.6 expert tradeoff
S: A legal chatbot calls Converse with explicit prompt caching. Each request has 600 tokens of tool definitions, a 700-token system prompt, a 30,000-token contract in the first user message, and then the user's question, timestamp, and conversation history. The model card states a minimum of 1,024 tokens per cache checkpoint, at most 4 checkpoints per request, and TTLs of 5 minutes or 1 hour. Lawyers send a question about every 8 minutes during a session. CacheReadInputTokenCount stays near zero, and the team must not change models or move to batch processing. Which THREE changes make the contract reliably cacheable? (Select THREE)
A: Place a checkpoint after the system prompt, where the cumulative prefix of 1,300 tokens meets the 1,024-token minimum, instead of after the tools alone
B: Place the timestamp, the question, and the conversation history after the checkpoint that follows the contract, so the 31,300-token prefix stays identical
C: Use the 1-hour TTL for the checkpoint after the contract, because questions arrive every 8 minutes and a 5-minute cache entry expires between them
D: Place a checkpoint after the 600 tokens of tool definitions only, because tool definitions are cached independently of the minimum token count per checkpoint
E: Add six checkpoints, one every 5,000 tokens inside the contract, so that each part of the contract is cached separately with finer granularity
F: Move the contract analysis to batch inference jobs, so the shared contract is cached once and reused across all records of the job
K: A,B,C
G: ## Rules for explicit prompt caching
- A checkpoint caches the **prefix** before it. The **minimum token count applies cumulatively** to the whole prefix (tools, system, messages). A checkpoint placed before the minimum is reached does not fail, but nothing is cached.
- Each model has a **maximum number of checkpoints** (here 4).
- The **TTL resets on every hit**; with no hit inside the TTL the entry expires. Some models offer a 1-hour TTL.
- Any change inside a prefix causes a miss, so dynamic content belongs after the last checkpoint.
- Prompt caching is **not supported** with the batch inference API.
## Working the numbers
- After tools: 600 tokens, below 1,024, so no cache.
- After system: 600 + 700 = 1,300 tokens, valid.
- After contract: 1,300 + 30,000 = 31,300 tokens, valid, and the part worth caching.
- Questions every 8 minutes are longer than a 5-minute TTL, so every request would write instead of read; a 1-hour TTL is reset by each hit.
W: A=Checkpoint after the system prompt: the cumulative 1,300 tokens meet the minimum, so the stable header is cacheable.
B=Dynamic content last: keeping question, timestamp, and history after the contract checkpoint makes the 31,300-token prefix identical on every request.
C=1-hour TTL: with 8-minute gaps, only a TTL longer than the gap lets the next question hit the cache, and each hit resets it.
X: D=Checkpoint after tools only: 600 tokens is below the cumulative minimum, so the checkpoint is accepted but nothing is cached.
E=Six checkpoints: the model allows at most four checkpoints per request.
F=Batch inference: prompt caching is not supported with the batch inference API, and the stem rules out batch processing.
T: Place checkpoints where the cumulative prefix meets the minimum, keep dynamic content after them, and choose a TTL longer than the gap between requests.

@ AIP-C01 D2 T2.1 expert troubleshooting
S: A bank runs an advisor assistant on Amazon Bedrock AgentCore Runtime with default lifecycle settings, and the agent keeps conversation history only in process memory. Advisors often pause for 20 to 45 minutes during client meetings, and some continue a conversation the next morning, about 16 hours later. In both cases the agent has forgotten everything, although the client sends the same runtimeSessionId. Security forbids the team from operating its own database, and each advisor's context must stay isolated from other advisors. Which change keeps the conversation context available in both cases?
A: Store each turn as events in AgentCore Memory, and on any new session load the advisor's recent events with ListEvents before answering
B: Raise idleRuntimeSessionTimeout to 28,800 seconds, so the microVM and its in-memory history survive any pause of up to eight hours
C: Raise maxLifetime to 1,209,600 seconds, so that each advisor's microVM keeps its conversation history in memory for up to 14 days
D: Write the history to the session's /tmp directory and reuse the same runtimeSessionId, so that the files are found again the next morning
K: A
G: ## Why the agent forgets
An AgentCore Runtime session runs in a dedicated microVM. Its memory and disk are **ephemeral**: they live only as long as the compute.
- A session stops after **inactivity (default 900 seconds, 15 minutes)** or at **maximum lifetime (default 28,800 seconds, 8 hours)**.
- On microVMs both settings range from 60 to 28,800 seconds; up to 1,209,600 seconds applies to Instances.
- The next invocation with the same `runtimeSessionId` gets a **new** microVM, so in-process history is gone.
## Where conversation state belongs
AWS recommends **AgentCore Memory** for data that must outlive a session. Short-term memory stores each turn as an **event** (`CreateEvent`) with a session ID; `ListEvents` returns the history so a new microVM can reload it. Long-term strategies can add preferences and summaries on top.
## Working the numbers
- 20-45 minute pause > 15-minute default idle timeout: session stops.
- 16-hour gap > 8-hour maximum lifetime on microVMs: no timeout setting can bridge it.
W: AgentCore Memory events: the history is stored outside the microVM, so it survives both the idle stop and the overnight gap, and it is keyed per advisor session without running a database.
X: B=Idle timeout 28,800 seconds: it covers the meeting pauses, but a 16-hour overnight gap is twice the 8-hour maximum, so the next morning still starts empty.
C=maxLifetime 1,209,600 seconds: that value is valid only for Instances; microVM lifetimes stop at 28,800 seconds, and an idle stop would still discard memory.
D=/tmp files: the filesystem is ephemeral by default and disappears with the stopped microVM, even if the client reuses the session ID.
T: AgentCore Runtime sessions are ephemeral; keep conversation state in AgentCore Memory so it survives idle stops and long gaps.

G: ## How a global profile is authorized
A request through a global cross-Region inference profile is authorized against **three** resources:
1. the inference profile in the source Region (`arn:aws:bedrock:eu-west-1:<acct>:inference-profile/global.<model>`), with the source Region as `aws:RequestedRegion`;
2. the foundation model in the source Region;
3. the **Region-agnostic global model** `arn:aws:bedrock:::foundation-model/<model>`, for which `aws:RequestedRegion` is **`unspecified`**.
The `bedrock:InferenceProfileArn` condition key is populated for the two foundation model evaluations.
## Two independent failures
- **Role A** is blocked by the SCP: a Region allow-list without `unspecified` denies evaluation 3. AWS documents two fixes: allow `unspecified`, or exempt requests by `bedrock:InferenceProfileArn`, which keeps the Region rule for every other service.
- **Role B** lacks the third statement of the documented three-part IAM policy.
## Other facts
Cross-Region inference does not require manually enabling destination Regions.
W: A=SCP exemption by profile ARN: it permits the global model evaluation for this profile only, so other services keep the Region restriction security insists on.
B=Third IAM statement: it grants the global model ARN with the unspecified Region and the profile ARN condition, completing role B's permissions.
X: C="unspecified" for all actions: it works, but it relaxes the Region rule for every service, which security forbids.

S: A telecom company classifies 900,000 support transcripts each weekend with an Amazon Bedrock batch inference job. Each record must use the model's tool calling, because the downstream parser reads the toolUse blocks and cannot change. The job was created with modelInvocationType Converse and every record includes toolConfig; records fail with 400 errors. A smaller test job that did run stopped at its default timeout before finishing its records. A Lambda function that polls GetModelInvocationJob every 30 seconds to start the next workflow keeps hitting API throttling. Which THREE changes fix these problems? (Select THREE)
A: Create the job with the InvokeModel invocation type and write each modelInput in the model's native request format with its tool definitions
B: Set timeoutDurationInHours to 72 when creating the job, which is within the allowed range of 24 to 168 hours for a batch inference job
C: Start the next workflow from an EventBridge rule that matches the batch job state-change event instead of polling the job status every 30 seconds
D: Keep the Converse invocation type and move toolConfig from each record into the job-level settings, so that tool calling applies to every record in the job
E: Set timeoutDurationInHours to 336, so that the largest weekend jobs have two full weeks to finish before the batch job is stopped by Bedrock
F: Run the job against a Provisioned Throughput model ARN, so that the job gets dedicated capacity and finishes within the default 24-hour timeout
K: A,B,C
G: ## Batch inference facts that decide this case
- **Invocation type**: a job uses `InvokeModel` (default, model-native request bodies) or `Converse` format. Batch inference **does not support tool calling for Converse-type jobs**: records with `toolConfig` fail with a 400 error. For tool calling, use the `InvokeModel` type with the tools in each native `modelInput`. Structured outputs work with both types.
- **Timeout**: `timeoutDurationInHours` defaults to **24** and accepts **24 to 168** hours.
- **Provisioned models**: batch inference isn't supported for them.
- **Status**: instead of polling, Amazon EventBridge receives Bedrock job state-change events in near real time (best effort), which avoids API rate limits.
## Working the timeout
If the test job could not finish its records in 24 hours, 900,000 records need a longer window; 72 hours fits inside the 168-hour maximum and a weekend.
W: A=InvokeModel type: native request bodies may carry tool definitions in batch jobs, so tool calling and the toolUse output the parser needs keep working.
B=72-hour timeout: it lifts the 24-hour default that cut the test short and stays within the documented 24 to 168 range.
C=EventBridge rule: state-change events start the next workflow without any polling, which removes the throttling.
X: D=Job-level toolConfig: tool calling is unsupported for Converse-type batch jobs as such; moving the setting does not change the invocation type.
E=336 hours: two weeks is above the 168-hour maximum, so the request is invalid.
F=Provisioned Throughput ARN: batch inference isn't supported for provisioned models.
T: For batch tool calling use the InvokeModel invocation type, size timeoutDurationInHours within 24-168, and react to job state changes with EventBridge.
V: Amazon Bedrock, Amazon EventBridge, AWS Lambda
