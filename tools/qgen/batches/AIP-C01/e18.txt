@ Q001573 explain
G: ## Final-answer evaluation versus trajectory evaluation
- **Final-answer (outcome) evaluation** compares the agent's last answer with an expected answer. It says whether the result is right.
- **Trajectory evaluation** looks at the path: which tools were called, in which order, with which arguments, and how many steps were taken. The observed path is compared with one or more expected paths, for example "look up order, then call payment once".
## Why an agent can be right and still wrong
An agent can reach the correct answer by an unsafe or wasteful route. Calling a payment tool twice might charge the customer twice even though the reply text looks fine. Nine tool calls instead of three add latency and cost. Trajectory checks catch both:
- duplicate side-effecting calls (the same `payment` call with the same arguments)
- step count above the expected path length
- wrong arguments or wrong ordering
The trace data from Bedrock Agents, AgentCore Observability or your own tool-call logs provides the sequence to score.
Note: Amazon Bedrock Agents was renamed Bedrock Agents Classic and closed to new customers on 2026-07-30; existing customers can keep using it, and AWS points new agent builds to Amazon Bedrock AgentCore. Trajectory evaluation works the same way whichever runtime produced the trace.
W: Trajectory evaluation of tool-call sequence and arguments: it scores the path itself, so duplicate payment calls and redundant steps are flagged even when the final answer is correct.
X: B=End-to-end latency percentiles: extra calls may raise latency, but the percentile cannot say which calls were redundant or that a payment ran twice.
C=Guardrail intervention counts: guardrails check content against policies. Duplicate or excessive tool calls do not violate content policies, so the count would not move.
D=Final-answer correctness against a golden dataset: answers are already correct 95% of the time, so this metric would look healthy while duplicate payments continue.
T: When the answer is right but the path is wrong, only trajectory evaluation (tools, order, arguments, step count) can see the problem.

@ Q001586 explain
G: ## The context window problem in chat
A model has no memory between calls; the application sends the conversation history with each request. History grows with every turn, so it must eventually be trimmed to fit the context window and control cost.
Keeping only the last N messages is simple but blind: anything older is lost, however important. An account number given in message 2 is gone by message 8.
## Memory patterns
- **Running summary**: after each turn (or every few turns) a model call updates a short summary of key facts and decisions: account number, the problem, what has been tried. The prompt holds the summary plus the recent raw messages.
- **Structured memory store**: extract facts into a store such as DynamoDB (for example `account_id`, `preferred_language`) and insert them into the prompt when relevant.
- **Managed memory**: Amazon Bedrock AgentCore Memory stores recent conversation events (short-term) and extracts long-term memories such as facts, preferences and summaries. Amazon Bedrock Agents (now Bedrock Agents Classic) can also keep session summaries across sessions.
All of these keep the prompt small while preserving important facts.
Note: Amazon Bedrock Agents was renamed Bedrock Agents Classic and closed to new customers on 2026-07-30; existing customers can keep using it, and AWS points new agent builds, including managed memory, to Amazon Bedrock AgentCore.
W: Running summary or memory store alongside recent messages: key facts survive in compact form no matter how long the conversation runs, while recent turns stay verbatim, so the prompt fits the context window without forgetting.
X: A=Keep the last 20 messages: a bigger fixed window only moves the cutoff; facts from message 2 of a 30-message conversation are lost the same way, and every request becomes more expensive.
B=Disable history: treating each message as a new session removes all context, so the assistant cannot follow any multi-turn conversation.
C=Smaller context window: less room means even more truncation; a smaller window does not make the truncation any smarter.
T: Replace blind truncation with memory: summarize or store key facts and send them with the recent messages.

@ Q001980 explain
G: ## One agent versus a team of agents
A single agent with many tools and instructions from different domains gets harder to prompt and less accurate at choosing the right tool as it grows. Splitting the work into specialized agents keeps each one focused.
## Multi-agent collaboration in Amazon Bedrock Agents
- A **supervisor agent** is the single entry point. It is associated with **collaborator agents**, here flights, hotels and visa rules.
- The supervisor plans the request, sends sub-tasks to the right collaborators (possibly several), and combines their answers into one response.
- In routing mode, simple requests go straight to one collaborator; complex ones get full orchestration.
Example: "Book Paris flights and a hotel, and do I need a visa?" is split three ways, and the supervisor merges the results.
This is configured in Bedrock Agents, so little custom orchestration code is needed.
## Availability note
Amazon Bedrock Agents was renamed Bedrock Agents Classic and closed to new customers on 2026-07-30. Existing customers can keep using it, including multi-agent collaboration, and AWS points new agent builds to Amazon Bedrock AgentCore, where a supervisor pattern is built with an agent framework running on AgentCore Runtime. Exam questions may still name Bedrock Agents.
W: Supervisor with collaborators: the supervisor routes each part of a request to the flight, hotel or visa agent and combines the results, giving one entry point without custom orchestration code. It remains the answer the exam expects, even though new customers would now build this pattern on AgentCore.
X: A=Three knowledge bases, no action groups: knowledge bases only retrieve documents; without action groups the agent cannot search flights or make bookings, and the specialized agents are not used.
C=Call all three and concatenate: every request pays for three agents even when one is enough, and pasting answers together gives no coherent, combined response.
D=One merged action group: putting every tool into one agent loses the specialization, and tool selection gets less reliable as the number of tools grows.
T: For several specialist agents behind one entry point, use multi-agent collaboration with a supervisor instead of merging everything or calling every agent blindly.

@ Q001991 explain
G: ## How a Bedrock agent picks an action
An agent's orchestration prompt tells the foundation model which tools exist. For each action group, the model sees the action names, their descriptions and the parameter descriptions (from the OpenAPI schema or function details). It chooses a tool by reading that text, the same way a person would read an API catalog.
- Vague descriptions such as "gets status" for both `getOrderStatus` and `getShipmentStatus` leave the model guessing.
- Clear descriptions say what each action returns and when to use it, for example "Use getShipmentStatus when the user asks where a package is, about delivery or tracking; returns carrier, tracking number and location."
## Using the trace
The agent trace shows the model's rationale for each step. If it says "the user asks about an order, so I call getOrderStatus", the descriptions are the thing to fix, then re-test the same prompts.
Note: Amazon Bedrock Agents was renamed Bedrock Agents Classic and closed to new customers on 2026-07-30; existing customers can keep using it, and AWS points new agent builds to Amazon Bedrock AgentCore. Exam questions may still name Bedrock Agents, and clear tool descriptions matter just as much for AgentCore agents.
W: Clarify action and parameter descriptions: the model routes to tools based on those descriptions, so making the two actions clearly distinct in purpose and inputs fixes the wrong selection while both APIs keep working.
X: B=Guardrail blocking "package": a guardrail filter on that word would block legitimate customer questions instead of steering them to the right action, and it does not change how the agent chooses tools.
C=Longer idle session timeout: the timeout only controls how long conversation state is kept between turns; it has no influence on which action group the model selects.
D=Larger embedding model: agents do not choose actions through an embedding model; the choice is made by the orchestration model reading the tool descriptions, so an embedding change has no effect.
T: When an agent calls the wrong tool but both tools work, rewrite the action and parameter descriptions and confirm with the trace; timeouts, guardrails and embeddings do not drive tool choice.

@ Q002891 explain
G: ## How Bedrock agents call APIs
An agent in Amazon Bedrock Agents reasons about a user request and decides which action to take. Actions are defined in **action groups**.
- The action group describes the operations the agent can call, either with an **OpenAPI schema** (paths, parameters, descriptions) or with simpler **function details**.
- The descriptions tell the model when to use each operation, for example `GET /orders/{orderId}` "returns the current status of an order".
- When the agent chooses the action, it fills in parameters from the conversation and invokes the **AWS Lambda function** attached to the action group (or returns control to the application).
- The Lambda function calls the internal REST API, gets the live status and returns the result, which the agent uses to answer.
Example: "Where is order 1234?" leads the agent to call `getOrderStatus` with `orderId=1234`; Lambda queries the order service and returns "shipped, arriving Thursday".
## Availability note
Amazon Bedrock Agents was renamed Bedrock Agents Classic and closed to new customers on 2026-07-30. Existing customers can keep using it, and AWS points new agent builds to Amazon Bedrock AgentCore, where AgentCore Gateway can turn an OpenAPI-described API or a Lambda function into a tool the agent calls. Exam questions may still name Bedrock Agents.
W: Action group with OpenAPI schema and Lambda: the schema tells the agent what the operation does and which parameters it needs, and Lambda performs the real API call, so answers use live order data. For an agent built with Bedrock Agents this remains the answer the exam expects.
X: A=Knowledge base of nightly JSON: indexing responses once a day gives stale status and does not call the API per request; knowledge bases are for retrieving documents, not executing operations.
C=Guardrail policy: guardrails filter or block content in inputs and outputs; they cannot call an API or return order data.
D=Order states in instructions: a list of possible states tells the model what statuses exist, not the status of a specific order, which only the live API can provide.
T: Agents take actions through action groups (schema plus Lambda or return of control); knowledge bases and guardrails do not call APIs.

@ Q002892 explain
G: ## Return of control in Bedrock Agents
Normally an action group runs an AWS Lambda function that the agent invokes directly. With **return of control**, the action group is configured so that the agent does not execute anything itself.
- The agent decides which action to call and with which parameters (for example `issueRefund` with `orderId` and `amount`).
- Instead of invoking Lambda, the `InvokeAgent` response returns this action and its parameters to the client application.
- The application can show a confirmation to the user, apply its own business checks, call the refund API with its own credentials, and send the result back to the agent in the next `InvokeAgent` request, so the conversation continues.
This fits cases where the action is sensitive, needs user approval, or must run inside the application's own systems.
## Availability note
Amazon Bedrock Agents was renamed Bedrock Agents Classic and closed to new customers on 2026-07-30. Existing customers can keep using it, including return of control, and AWS points new agent builds to Amazon Bedrock AgentCore, where the agent code you deploy decides how to pause for approval. Exam questions may still name Bedrock Agents.
W: Return of control: the agent hands the chosen action and parameters to the application, which collects user confirmation and executes the refund itself, exactly the required pause. It remains the Bedrock Agents feature the exam expects here.
X: A=Longer session timeout: it only keeps the session alive longer; the agent would still run the action without any confirmation step.
B=Higher temperature: temperature changes how random the model's text is; it adds no pause and makes decisions less predictable, which is the opposite of what a refund needs.
D=Knowledge base on the action group: knowledge bases supply documents for answers; they cannot stop an action or hand execution to the application.
T: When the application, not the agent, must confirm and run an action, use return of control instead of a Lambda executor.

@ Q002909 explain
G: ## Model APIs are stateless
A call to a model API such as the Amazon Bedrock `Converse` API is independent: the model keeps no memory of earlier requests. Everything the model should consider must be in the current request.
To hold a conversation, the **application** keeps the history and resends it.
- Store each user message and model reply, for example in memory for a session or in Amazon DynamoDB.
- On each new turn, send the `messages` list containing the relevant prior turns plus the new question.
- When history grows beyond the context window or becomes costly, keep the last N turns, summarize older turns into a short recap, or retrieve only relevant earlier facts.
Managed options such as Amazon Bedrock AgentCore Memory or session features in Bedrock Agents handle this storage for you, but they still work by supplying context to each model call.
Note: Amazon Bedrock Agents was renamed Bedrock Agents Classic and closed to new customers on 2026-07-30; existing customers can keep using its session features, and AWS points new agent builds to Amazon Bedrock AgentCore.
Example: turn 3 asks "And what about the second one?"; only because turns 1 and 2 are included can the model know what "the second one" refers to.
W: Send the relevant prior messages with each request: the model sees only what is in the current request, so resending history (or a summary) is how context carries across turns.
X: B=Higher temperature: temperature controls randomness in token selection; it adds no memory and makes replies less consistent.
C=New model identifier per turn: switching models does nothing to carry context, and each model is just as stateless as the last.
D=Rely on model memory: the model retains nothing between API calls, so earlier turns are simply unknown to it unless sent again.
T: With a stateless model API, the application owns conversation memory and sends the needed history on every call.

@ Q002912 explain
G: ## Guardrails without a Bedrock model call
Guardrails are usually attached to a Bedrock call such as `InvokeModel` or `Converse` by passing a guardrail ID and version. The **`ApplyGuardrail`** API decouples the guardrail from the model: you send any text and say whether it is an input (`source=INPUT`) or an output (`source=OUTPUT`), and the service returns whether a policy intervened plus any masked text.
## Example flow for a self-hosted model
- The app sends the user prompt to `ApplyGuardrail` as input; if it is blocked, the app returns the blocked message.
- Otherwise it calls the self-hosted model on Amazon SageMaker AI or a third-party API.
- It sends the model's answer to `ApplyGuardrail` as output and returns the (possibly masked) result.
Because every path calls the same guardrail version, denied topics, content filters and PII rules stay identical everywhere, and changes are made once.
Note: Amazon Bedrock Agents was renamed Bedrock Agents Classic and closed to new customers on 2026-07-30; existing customers can keep using it, and AWS points new agent builds to Amazon Bedrock AgentCore. `ApplyGuardrail` is independent of either agent service, which is one more reason it suits mixed environments.
W: ApplyGuardrail API: it evaluates text against a guardrail without invoking a Bedrock model, so the same policies can wrap self-hosted models and third-party APIs on both input and output.
X: A=Copy the word list into code: this reproduces only one policy type, loses denied topics, content filters and PII masking, and drifts as each copy is edited separately.
B=Attach to Bedrock agents only: a guardrail attached to an agent protects that agent's calls; traffic to other models never passes through it, so enforcement is not consistent.
D=Provider safety filters: each provider applies its own, different rules, so the company cannot guarantee one consistent policy or audit it centrally.
T: To enforce one guardrail across any model, call `ApplyGuardrail` around the call instead of relying on per-model or per-provider filtering.

@ Q002948 explain
G: ## Seeing why a Bedrock agent chose an action
An Amazon Bedrock agent decides which **action group** (a set of API operations or Lambda functions) to call based on the user input, the agent instructions and each action group's description and schema. When it picks the wrong one, you need to see its reasoning.
The **agent trace** exposes this:
- Enable it with `enableTrace` in the `InvokeAgent` call, or view it in the console test window.
- The trace includes pre-processing, **orchestration** steps (the model's rationale, the chosen action group and API, the input parameters, and the observation returned), knowledge base lookups and post-processing.
- Example: the rationale shows the agent treated "cancel my booking" as a lookup because the cancellation action's description was vague, so you rewrite that description.

G: ## Two human-in-the-loop options in Bedrock Agents
- **User confirmation** asks the end user of the agent to confirm or deny an action before the agent runs it. It suits cases where the person chatting is the right approver.
- **Return of control** hands the function call details back to the application instead of running a Lambda function. The application decides how to run it, including routing it to other people, then returns the results so that the agent continues.
## Choosing
When the approver is a different person and the wait is long, the workflow belongs in the application, which can persist state and wait.

Existing customers can keep using it, including user confirmation and return of control, and AWS points new agent builds to Amazon Bedrock AgentCore, where the deployed agent code implements the approval pause. @ Q004453 explain
G: ## Bedrock has several endpoint services
Bedrock APIs are split across services, and each has its own interface VPC endpoint service name. The control plane (create and manage resources), the runtime (InvokeModel, Converse), the agent build-time API and the agent runtime API (InvokeAgent, Retrieve, RetrieveAndGenerate) are separate. An endpoint for one does not carry calls for another.
- `InvokeModel` and `Converse` go to the Bedrock runtime endpoint.
- `Retrieve`, `RetrieveAndGenerate` and `InvokeAgent` go to the agent runtime endpoint.
A private-subnet workload therefore needs an endpoint per API family it uses, with private DNS enabled and security groups permitting HTTPS from the callers.
Note: Amazon Bedrock Agents was renamed Bedrock Agents Classic and closed to new customers on 2026-07-30; existing customers can keep using it, and AWS points new agent builds to Amazon Bedrock AgentCore, which has its own separate API endpoints. Knowledge base retrieval still goes through the agent runtime API.
W: Missing agent runtime endpoint: Retrieve and InvokeAgent go to the agent runtime service, which is not covered by the runtime endpoint that InvokeModel uses.
X: A=Cross-Region endpoint: an endpoint must be in the same Region as the VPC and the API; placing it elsewhere would not fix reachability.
B=NAT requirement: PrivateLink is offered for the other Bedrock API families and keeps traffic off the internet; NAT is not needed.
C=Per-document endpoint policy: endpoint policies are IAM-style policies on actions and resources; they do not enumerate documents.
T: Each Bedrock API family (runtime, agent runtime, control plane) has its own VPC endpoint; create one for every API used from private subnets.

@ Q004455 explain
G: ## Two layers of least privilege for agents
An agent has two identities.
- Its **service role** is what Bedrock assumes to call foundation models and other resources, so it should list only the approved model ARNs.
- The **action group Lambda** is invoked by the Bedrock service, so the function's resource-based policy decides who may call it. Using the Bedrock service principal together with a condition on the agent's ARN (source ARN) stops other agents, including ones in the same account, from calling the function, which is the confused-deputy protection AWS recommends.
Example: the function policy allows `bedrock.amazonaws.com` to call `lambda:InvokeFunction` only when `AWS:SourceArn` equals the agent's ARN, and the service role allows `bedrock:InvokeModel` only on the approved model's ARN.
Note: Amazon Bedrock Agents was renamed Bedrock Agents Classic and closed to new customers on 2026-07-30; existing customers can keep using it, and AWS points new agent builds to Amazon Bedrock AgentCore. The same least-privilege idea (scoped roles, resource policies with source conditions) applies there.
W: D=Resource policy with source ARN: only that agent can invoke the function, whatever other agents know about it.
E=Model-scoped service role: the agent can call only the approved model, so a changed configuration cannot switch it to an unapproved or more expensive one.
X: A=Public function URL: it exposes the function to the internet and replaces IAM authorisation with a shared secret; resource-based policies are exactly how Bedrock is granted access.
B=AdministratorAccess: the opposite of least privilege, giving an injected agent action access to everything in the account.
C=Wildcard model access: convenient, but it lets the agent invoke any model and defeats the approval requirement.
T: Restrict agent service roles to approved model ARNs and protect action group Lambdas with resource policies conditioned on the agent's ARN.

@ Q004437 explain
G: ## What Amazon A2I does
Amazon Augmented AI (A2I) lets you build human review workflows for machine learning predictions. You define a flow definition with a work team (your own private employees or a vendor workforce) and a task template. Your application calls `StartHumanLoop` when a condition is met, and A2I collects the reviewer's decision.
Built-in task types exist for Amazon Textract and Amazon Rekognition, and a custom task type supports any model, including an FM.
## Triggers
Conditions such as low confidence or a business rule can start a loop, and a random percentage can be sampled for quality audits.
Example: the application starts a human loop when the guardrail intervened, when the disputed amount is above the threshold, or when `random() < 0.05`.
## Availability note
Amazon Mechanical Turk reached end of support on 2026-09-29, so the Mechanical Turk public workforce option is gone. A2I and SageMaker Ground Truth still work with private or vendor workforces.
W: A2I with a custom task type and a private workforce: it provides reviewer tasks, decision capture and an auditable record. The application decides when to call it, which covers guardrail, amount and random sampling triggers.
X: B=Slack emoji: it has no structured task, no controlled workforce and no dependable audit record of who approved what.
C=Mechanical Turk public workforce: customer dispute data is sensitive and the bank wants trained employees, so a public workforce is inappropriate; in addition, Amazon Mechanical Turk closed on 2026-09-29, so this workforce no longer exists.
D=Higher guardrail strength: a guardrail is an automated control. It does not replace the human review the policy requires, and a stricter filter cannot judge disputes.
T: For human review of FM output, use Amazon A2I with a custom task type, a private workforce and application-defined triggers, including random sampling.
