@ AIP-C01 D3 T3.1 advanced use-case
S: A policy assistant must verify that answers are logically consistent with complex eligibility rules and explain any violations. Which guardrail capability fits?
A: Automated Reasoning checks built from the policy document
B: Prompt attack detection applied to retrieved policy passages
C: Content filters raised to high strength across harm categories
D: A word filter listing the eligibility terms from the policy
K: A
G: ## Automated Reasoning checks
Most guardrail policies are probabilistic classifiers. **Automated Reasoning checks** in Amazon Bedrock Guardrails use formal logic instead:
- You upload a source document, such as an eligibility policy, and the service extracts variables and logical rules into an Automated Reasoning policy, which you review and refine.
- At run time, the guardrail translates the question and the model's answer into logic and checks them against the rules.
- The findings classify each answer, for example as valid, invalid, or only satisfiable under some assumptions, and flag cases the check could not translate reliably. For an invalid answer they identify the rules it contradicts, which the application can use to explain or correct the answer.
## Example
Rule: "Employees with under 12 months of service are not eligible for sabbatical." If the model answers "Yes, with 8 months you can take a sabbatical", the check returns an invalid finding that identifies the contradicted rule, giving an explainable reason.
W: A=Automated Reasoning checks: they verify logical consistency of answers against rules built from the policy document and explain which rules an answer violates, exactly what the requirement asks.
X: B=Prompt attack detection on passages: this detects jailbreak and injection attempts; it says nothing about whether an answer satisfies eligibility rules.
C=Content filters at highest strength: content filters detect harmful categories such as hate or violence; an eligibility error is not harmful content and would pass.
D=Word filter of eligibility terms: blocking policy terms would block correct answers too, and word matching cannot evaluate logic between conditions.
T: When answers must be provably consistent with complex rules and violations explained, use Automated Reasoning checks, not classifier-based filters.

@ AIP-C01 D2 T2.2 advanced tradeoff
S: A company hosts dozens of small fine-tuned variants of the same base model, each with light traffic. Which hosting approach is most cost-effective?
A: Deploy each variant on its own dedicated GPU endpoint that runs around the clock
B: Merge the variants' instructions into one long prompt sent to the base model
C: Run each fine-tuned variant in its own Lambda function backed by CPU and memory
D: Serve adapters on a shared endpoint, such as multi-adapter or inference components
K: D
G: ## Many small fine-tuned variants, one base model
Parameter-efficient fine-tuning methods such as **LoRA** do not change the whole model. They train a small **adapter** (often megabytes) that is applied on top of a shared base model (often many gigabytes).
If each variant gets its own GPU endpoint, dozens of copies of the same base model sit mostly idle. Sharing is much cheaper.
- **SageMaker AI inference components** let one endpoint host several models or adapters, each with its own resource allocation and scaling, including scaling individual components down to zero copies.
- **Multi-adapter (LoRA) serving** loads the base model once and applies the requested adapter per request, so dozens of variants share the same GPU memory and instances.
Example: 40 customer-specific adapters on one base model run on two GPU instances instead of 40, and each request names the adapter to use.
W: Adapters on a shared endpoint: the base model is loaded once and variants are selected per request, so dozens of low-traffic models share a few instances instead of each paying for idle GPUs.
X: A=Own dedicated GPU endpoint per variant: each variant pays for a full GPU instance that is idle most of the time, multiplying cost by the number of variants.
B=Merge variants into one prompt: fine-tuned behavior lives in trained weights; instructions in a prompt cannot reliably reproduce dozens of specialized behaviors and make every request longer.
C=Separate Lambda functions on CPU: Lambda has no GPUs and limited memory and package size, so large language models run far too slowly or cannot be loaded at all.
T: Light-traffic variants of one base model belong on a shared endpoint serving adapters, not on dedicated GPU endpoints each.

@ AIP-C01 D1 T1.2 advanced tradeoff
S: A team can fine-tune a model or use RAG for an assistant whose answers depend on thousands of product specifications that change monthly. Which choice fits best?
A: RAG, because specifications change and must be cited from current sources
B: Neither, because the base model learned the specifications in pretraining
C: Fine-tuning, because it embeds the specifications directly in the weights
D: Both, retrained monthly from scratch, since training improves accuracy
K: A
G: ## RAG versus fine-tuning
- **Retrieval-augmented generation (RAG)** looks up relevant documents at query time and gives them to the model. Updating knowledge means updating the documents and re-syncing the index, and answers can cite their sources.
- **Fine-tuning** adjusts model weights with training examples. It is good at teaching style, format, tone or a task pattern, but facts learned this way are frozen at training time, are hard to cite, and may be recalled inaccurately.
## Applying it here
Thousands of product specifications change every month. With RAG, a new spec sheet is added to the knowledge base and the next query can use it, with a citation to the exact document. With fine-tuning, every monthly change would require a new training run, and the model could still mix old and new values without any source to check.
W: RAG: changing, citable facts are best kept in an updatable index, so answers reflect the current specifications and can point to the source document.
X: B=Neither, the base model learned the specs: a base model has not seen private, frequently changing product specifications, so it would invent or give outdated values.
C=Fine-tuning embeds specs in the weights: baked-in facts go stale after the next monthly change, cannot be cited and are not reliably recalled.
D=Both retrained monthly from scratch: RAG does not need retraining at all, and training a model from scratch every month is extremely costly with no accuracy guarantee.
T: Use RAG for facts that change and must be cited; use fine-tuning for behavior, style or format, not for frequently updated knowledge.

@ AIP-C01 D1 T1.6 applied use-case
S: A team uses the same prompt across three applications with different product names and tones. Which approach keeps prompts maintainable?
A: A prompt that asks users to type the product and tone each time
B: A prompt template with variables for product name and tone
C: One prompt that lists the three product names and tones together
D: Three separate prompts that are copied and edited by hand
K: B
G: ## Prompt templates
A prompt template is one reviewed prompt with placeholders that are filled in at runtime. Example:
- Template: "You are the assistant for `{{product_name}}`. Answer in a `{{tone}}` tone. Use only the provided context."
- App 1 fills `product_name = CloudNotes`, `tone = friendly`.
- App 2 fills `product_name = LedgerPro`, `tone = formal`.
The shared logic (instructions, format, safety rules) exists once, so a fix or improvement reaches all three applications. Amazon Bedrock Prompt Management supports variables in `{{variable}}` form, and prompt libraries in frameworks such as LangChain offer the same idea.
## Why copies drift
When three copies are edited by hand, one team adds a safety rule, another changes the format, and soon the prompts behave differently and each must be tested separately.
W: Template with variables: one reviewed prompt serves every application, and only the parts that differ (product name and tone) change per app, so maintenance and testing happen in one place.
X: A=Ask users for the details: pushes prompt configuration onto end users, who give inconsistent or missing values, so output quality and tone vary from request to request.
C=Three products listed in one prompt: the model has to guess which product each request is about and may mix names and tones between products.
D=Three hand-edited copies: every change must be repeated three times, the copies drift apart, and each needs its own testing.
T: Keep one prompt with variables for what differs between apps instead of maintaining hand-copied variants or one blended prompt.
V: Amazon Bedrock Prompt Management

@ AIP-C01 D1 T1.3 applied use-case
S: A team wants each chunk in its knowledge base tagged with department and document date so queries can be filtered. How should metadata be supplied for S3 data sources?
A: Put the department name and date in each document's file name
B: Add the metadata as a header line in each generated answer
C: Provide metadata JSON files alongside the source documents
D: Create a separate knowledge base for each department and year
K: C
G: ## Metadata files for S3 data sources
For an S3 data source, a Bedrock knowledge base reads optional metadata from a companion file with the same name plus `.metadata.json`. For `policy-2024.pdf`, the file is `policy-2024.pdf.metadata.json` in the same location.
The file holds a `metadataAttributes` object, for example `"department": "finance"` and `"doc_date": 2024`. At ingestion, these attributes are attached to every chunk from that document.
At query time, a filter in the retrieval configuration restricts the search, for example `equals` department = finance combined with `greaterThanOrEquals` doc_date = 2023 using `andAll`. Only matching chunks are considered, which improves precision and supports access separation.
W: Metadata JSON files next to the documents: this is the supported way to attach attributes like department and date to S3 documents, and those fields can then be used in query filters.
X: A=Department and date in the file name: a file name is not a structured metadata attribute, so department and date would not be available as typed fields for equality and date-range filters.
B=Metadata as a header in answers: generated answers are output; adding text to them does nothing to tag chunks or filter retrieval.
D=A knowledge base per department and year: this multiplies the knowledge bases to sync and manage, and a query that spans several years or departments has to search many of them. It replaces filtering instead of enabling it, and still gives no exact date-range filter.
T: Tag S3 documents with `.metadata.json` companion files, then filter on those attributes at query time.

@ AIP-C01 D3 T3.4 advanced use-case
S: An external auditor wants evidence that a company's generative AI product both (a) is documented with its intended use, limitations, and risk assessment, and (b) technically enforces the organization's content policy at runtime. Which combination of artifacts should the team present?
A: The Model Card plus the attached Guardrails configuration and CloudTrail logs showing it is invoked
B: The Guardrails configuration by itself, since runtime enforcement also demonstrates that intended use was documented
C: The SageMaker Model Card by itself, since documenting the controls satisfies both documentation and enforcement
D: The company's general privacy policy, which describes how its AI products handle customer data
K: A
G: ## Documentation evidence versus enforcement evidence
Responsible-AI audits usually ask two separate questions.
- **Is the system documented?** A **SageMaker Model Card** records intended uses, out-of-scope uses, limitations, risk rating, training details and evaluation results in one versioned record that can be exported as a PDF for auditors.
- **Is policy actually enforced?** The **Bedrock Guardrails configuration** shows which denied topics, content filters and sensitive-information filters exist. Logs show it is really used: CloudTrail records the Bedrock API calls, and model invocation logs or guardrail traces can show the guardrail being applied to requests.
Configuration alone proves only that a control exists; the logs prove the application calls it. A document alone proves only intent.
## Example
Model Card: "Intended use: answering billing questions; not for legal advice; risk rating: medium." Guardrail `support-gr` version 3 denies "legal advice"; logs show requests carrying that guardrail.
W: Model Card plus guardrail configuration and logs: the card satisfies the documentation requirement, while the guardrail configuration together with logs of its use proves runtime enforcement.
X: B=Guardrails only: a guardrail shows what is blocked, not the documented intended use, limitations or risk assessment the auditor asked for.
C=Model Card only: describing controls in a document does not prove they run on each request; the auditor also needs technical evidence of enforcement.
D=General privacy policy: a company-wide privacy notice covers data handling in general. It is neither product-specific documentation nor evidence of runtime content controls.
T: Auditors need both a record of intent (Model Card) and proof of enforcement (guardrail configuration plus logs of it being applied).

@ AIP-C01 D3 T3.1 advanced tradeoff
S: A team is deciding how to detect potential hallucinations in a Bedrock RAG pipeline. Option one is Bedrock Guardrails contextual grounding check; option two is capturing the model's own self-reported confidence score in the prompt response. What is the key limitation of relying solely on option two?
A: Confidence scores require a dedicated VPC endpoint separate from the Bedrock runtime one
B: Self-reported scores come from the same model and are not verified against sources
C: Confidence scores are supported for text-to-SQL and classification tasks, not for RAG
D: Confidence scores are excluded from CloudWatch logs, so hallucination rates go untracked
K: B
G: ## Two ways to spot hallucinations
- **Self-reported confidence**: you ask the model to add "confidence: 0.95" to its answer. The number is just more generated text from the same model and the same reasoning that produced the answer, so a model that invented a fact can also be confident about it.
- **Contextual grounding check** in Amazon Bedrock Guardrails: a separate check compares the response with the reference source (the retrieved chunks) and the user query, then returns grounding and relevance scores. Responses below your thresholds are blocked or flagged.
## Why independence matters
A verification step should use evidence the answer can be checked against. The grounding check does that; self-assessment does not look at the sources in any enforced way.
Example: the source says "refunds within 30 days". The model answers "60 days, confidence 0.9". The grounding check scores the claim as unsupported; the self-reported score does not reveal the error.
W: Unverified self-assessment: the score comes from the same model that may be hallucinating and is not checked against the retrieved sources, so it can be confidently wrong.
X: A=Needs a separate VPC endpoint: asking for a confidence value is just part of the prompt and needs no extra networking, so this is not a real limitation.
C=Restricted to text-to-SQL and classification: a model can be asked to report a confidence value for any kind of output, so there is no such restriction.
D=Excluded from CloudWatch logs: the score is part of the response text and can be logged like any other value. The problem is that it is unreliable, not that it is untrackable.
T: Detect hallucinations with an independent check against the sources (contextual grounding), not with the model's own confidence.
V: Amazon Bedrock

@ AIP-C01 D1 T1.5 advanced troubleshooting
S: A knowledge base returns correct chunks, but answers still omit key details from them. Which TWO changes are most likely to help? (Select TWO)
A: Disable citations so the model spends its output on shorter, direct answers
B: Replace the vector store with a different engine that has higher recall
C: Reduce the retrieved chunks to one per question so the context stays focused
D: Evaluate faithfulness and completeness to confirm generation causes the gap
E: Change the generation prompt to require using all relevant retrieved details
K: D,E
G: ## Retrieval gap or generation gap?
A RAG answer can fail at two stages:
- **Retrieval**: the right chunks were never found.
- **Generation**: the right chunks were in the prompt, but the model ignored, shortened or misused them.
Here the chunks are already correct, so the problem most likely sits in generation. Two steps address it.
- **Measure it**: Amazon Bedrock evaluations can score retrieve-and-generate output with metrics such as **faithfulness** (is the answer supported by the retrieved context?) and **completeness** (does it cover everything the question needs?). Low completeness with good context confirms a generation problem and gives a baseline to compare fixes.
- **Fix the prompt**: tell the model explicitly to use all relevant retrieved details, to list every step or condition found in the sources, and to say when information is missing. Structured output formats (for example a required section per item) also reduce omissions.
Re-run the evaluation after each prompt change to confirm the improvement.
W: D=Evaluate faithfulness and completeness: it confirms that retrieval is fine and generation is dropping details, and it gives a measurable baseline for checking fixes.
E=Change the generation prompt: since the needed details are already in the context, instructing the model to use all relevant details directly targets the omissions.
X: A=Disable citations: citations do not cause missing details; removing them only makes answers harder to verify.
B=Replace the vector store: the store already returns the correct chunks, so a higher-recall engine costs effort without touching the stage that fails.
C=Retrieve one chunk per question: key details are often spread across several chunks; a focused context of one chunk would remove information and make omissions worse.
T: When retrieval is already correct, measure and fix generation; do not rebuild the retrieval layer.
V: Amazon Bedrock

@ AIP-C01 D1 T1.6 advanced use-case
S: Prompt changes must be approved by a reviewer and tested against a golden dataset before reaching production. Which process fits?
A: A CI/CD pipeline that runs evaluations and gates promotion on reviewer approval
B: A pipeline that deploys each new prompt version to production as soon as it is saved
C: A weekly meeting where the team reads new prompts aloud and votes on each change
D: Developers editing prompts directly in production whenever users report issues
K: A
G: ## Treating prompt changes like code changes
A small wording change in a prompt can change answers for thousands of users. Teams therefore apply the same controls they use for code: automated tests, human review and controlled promotion.
## A prompt CI/CD pipeline
A typical flow:
- A developer creates a new prompt version (for example in Amazon Bedrock Prompt Management or in a repository).
- The pipeline runs the version against a **golden dataset**: fixed questions with expected answers or scoring rules. Scores come from checks such as exact match, LLM-as-a-judge or Amazon Bedrock evaluation jobs.
- If scores meet thresholds, the pipeline pauses for a manual **approval** step (for example an approval action in AWS CodePipeline).
- Only then is the application pointed at the new version; the previous version stays available for rollback.
The result is traceable: each production prompt has evaluation results and an approver attached.
W: Evaluate, approve, then promote: the pipeline tests every prompt version on the golden dataset and requires reviewer approval before production uses it, which is exactly the stated requirement.
X: B=Deploy each version on save: saving a version would push it straight to users, skipping both the golden-dataset tests and the reviewer approval.
C=Weekly read-aloud meeting: a vote is a form of review, but reading prompts does not measure their output on the golden dataset, and a weekly cadence delays every fix.
D=Editing directly in production: changes reach users with no testing, no approval and no record of what changed, so a bad edit can break answers for everyone.
T: Prompt changes need both automated evaluation on a golden dataset and a human approval gate before promotion, just like code.

@ AIP-C01 D1 T1.6 applied use-case
S: A prompt asks the model to 'be concise' but responses vary widely in length. Which improvement is most effective?
A: Repeat 'be concise' several times in different places in the prompt
B: Set a concrete limit, such as three sentences, and show an example
C: Remove the instruction so the model chooses the best length itself
D: Raise the temperature so the model explores different answer lengths
K: B
G: ## Vague versus concrete instructions
Words like "concise", "short" or "detailed" mean different things to different readers, and a model interprets them differently from one request to the next. The result is inconsistent output.
Concrete instructions remove that ambiguity:
- Give a measurable limit: "Answer in at most three sentences" or "use no more than 50 words".
- Show the target format with an example (few-shot prompting), such as one sample question with a three-sentence answer.
- Optionally set the `maxTokens` inference parameter as a hard stop, remembering it truncates text rather than making the model plan a shorter answer.
## Example
"Be concise" might produce one line or three paragraphs; "Reply in exactly three sentences, like this example: ..." produces answers of nearly the same length every time.
W: Concrete limit plus an example: a specific, measurable constraint and a demonstration tell the model exactly what length is expected, which makes length consistent.
X: A=Repeat "be concise": repeating a vague word does not make it measurable, so the model still has to guess what concise means.
C=Remove the instruction: with no guidance, length depends entirely on the model and the question, so variation increases.
D=Raise the temperature: higher temperature increases randomness in token choice, so exploring lengths makes length and wording less consistent, not more.
T: Replace vague adjectives with measurable constraints and an example; repetition or randomness does not make output consistent.

@ AIP-C01 D2 T2.4 advanced comparison
S: A team is comparing static routing rules hardcoded in application logic against a Step Functions-based dynamic routing workflow that evaluates a classifier's output at runtime and can incorporate retries, fallback, or human review before selecting a model. Which approach offers better resilience and flexibility for a complex, evolving routing policy, accepting some added latency and complexity as the tradeoff?
A: Either one, because both approaches are functionally identical for this routing policy
B: The hardcoded rules, because static code paths are simpler to test as the policy evolves
C: The workflow, because routing and failure handling live in an editable state machine
D: API Gateway usage plans in front of the models, which give equivalent routing control
K: C
G: ## Static versus orchestrated dynamic routing
- **Static routing** hardcodes rules in application logic. It is fast and simple, but every policy change needs a code change and redeployment, and it has no built-in retries or review steps.
- **Dynamic routing with AWS Step Functions** runs a workflow per request: a task calls a classifier, a **Choice** state picks a model based on the output, and states can add **Retry** and **Catch** (fallback to another model) or a human review step using a task token callback.
## Tradeoff
Step Functions adds state transitions, which means some extra latency, cost and complexity. In return, routing logic is visible, testable and changeable in the state machine definition without touching the application code.
## Example
A new rule "if classifier confidence is below 0.6, send to human review" becomes one new Choice branch in the workflow instead of a release of the application.
W: Step Functions dynamic routing: a runtime classifier drives the model choice, and built-in retries, fallbacks and human review steps make a complex, changing policy resilient. Because the routing logic lives in the state machine definition rather than in application code, the policy can evolve without rewriting the app.
X: A=Functionally identical: static rules cannot use runtime classifier output or add retries, fallback and human review without new code, so the two differ in exactly the dimensions asked about.
B=Hardcoded rules are simpler: static routing wins on simplicity and latency for simple, stable rules, but each policy change means editing and redeploying application code, and retries, fallback and human review must be hand-built, so it is inflexible for complex, evolving policies.
D=Usage plans alone: API Gateway usage plans throttle and set quotas per API key; they do not inspect requests or choose between models.
T: For complex, evolving routing policies, accept some latency for an orchestrated dynamic router; keep static rules for simple, stable choices.
V: AWS Step Functions

@ AIP-C01 D2 T2.1 applied comparison
S: A tool server must maintain a long-lived, stateful headless-browser automation session for an agent's tool calls, with individual sessions sometimes running for over 20 minutes. Which hosting approach for the MCP server is most appropriate?
A: AWS Step Functions Express Workflows, running each browser action as a separate state in a single high-throughput execution
B: Amazon ECS on Fargate, running the MCP server as a container task that stays up between calls
C: A static website on Amazon S3 that runs the headless browser in the client and reports results back to the agent
D: An AWS Lambda function that keeps the browser session in memory and handles the entire session in one invocation
K: B
G: ## Matching the tool host to the workload
Where an MCP server runs depends on how long its work lasts and whether it keeps state:
- **AWS Lambda** suits short, stateless tool calls. An invocation can run for at most 15 minutes, and memory is not guaranteed to survive between invocations.
- **Amazon ECS on AWS Fargate** runs containers as long as you want without managing servers. A task can keep a headless browser process, cookies and page state in memory for the whole session.
- **Step Functions** orchestrates steps but does not keep a process alive between them; an Express workflow is also limited to 5 minutes.
Example: a Playwright-based MCP server on Fargate holds one browser context per agent session, and the agent sends "open page", "fill form", "click" tool calls over 25 minutes against the same live session.
W: ECS on Fargate: long-running containers keep the stateful browser session alive for more than 20 minutes without server management, which Lambda and Express workflows cannot do.
X: A=Step Functions Express Workflows: an Express execution lasts at most 5 minutes, and a live browser process cannot be carried from one state to the next.
C=Static site on S3: S3 serves files only, so the browser would run on an end user's device, outside the agent's control and security boundary, which is not a server-side tool at all.
D=Lambda holding the session: the 15-minute maximum invocation time ends sessions that run past 20 minutes, and state in memory is lost when the invocation ends.
T: Long-lived, stateful tool servers belong in containers such as ECS on Fargate; Lambda and Express workflows have hard duration limits.
