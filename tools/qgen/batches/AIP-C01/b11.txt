@ AIP-C01 D1 T1.1 advanced tradeoff
S: A media company in Frankfurt runs two Amazon Bedrock workloads on the same model. Workload A drafts marketing copy from public product data, has no data residency rule, and finance wants its token cost as low as possible. Workload B summarizes customer support chats, which a contract requires to be processed only inside the EU. Both workloads must stay available during demand peaks without buying reserved capacity. Which TWO configurations meet these requirements at the lowest cost? (Select TWO)
A: Invoke Workload A through the global cross-Region inference profile, accepting routing to any supported commercial AWS Region worldwide
B: Invoke Workload B through the EU geographic cross-Region inference profile, so requests are routed only among the EU Regions listed in that profile
C: Invoke Workload B through the global cross-Region inference profile and add an SCP that denies every non-EU Region for all of the Bedrock runtime API actions
D: Purchase Provisioned Throughput for the model and attach it to the EU inference profile, so that both workloads share guaranteed capacity in the EU
E: Invoke Workload A in eu-central-1 only with the single-Region model ID, because cross-Region routing adds a per-request data transfer charge
K: A,B
G: ## Two kinds of cross-Region inference profile
Cross-Region inference sends a request to one of several Regions so that a demand peak in one Region does not become an outage. Amazon Bedrock offers two kinds of profile:
- **Geographic** profiles (for example an `eu.` profile) route only among the Regions of one geography. This is the choice for data residency rules.
- **Global** profiles route to any supported commercial Region worldwide. AWS documents them as roughly **10% cheaper** than geographic profiles, and they are the choice when cost matters and there is no residency rule.
## Facts that decide the other options
- There is no extra routing charge for cross-Region inference; the price is based on the Region the profile is called from.
- Inference profiles currently do not support Provisioned Throughput.
- For a global profile, Bedrock evaluates the Region-agnostic model ARN with `aws:RequestedRegion` set to `unspecified`, so a Region-deny SCP cannot turn a global profile into an EU-only one.
W: A=Global profile for Workload A: there is no residency rule, global routing gives the widest capacity during peaks, and it carries the documented price advantage over geographic profiles.
B=EU profile for Workload B: requests are spread over several EU Regions for peak capacity, but never leave the EU geography, so the contract is met.
X: C=Global profile plus SCP: a global profile is designed to route worldwide, and its global model evaluation uses the Region value unspecified. An SCP either blocks the calls or does not keep processing inside the EU; it cannot make global routing EU-only.
D=Provisioned Throughput on a profile: inference profiles do not support Provisioned Throughput, and the stem rules out reserved capacity anyway.
E=Single-Region for Workload A: cross-Region inference has no additional routing charge, so this gives up both the global price advantage and the extra peak capacity.
T: Use a geographic inference profile when data must stay in a geography and a global profile when cost and capacity matter more than location.

@ AIP-C01 D1 T1.1 advanced use-case
S: An industrial company is building an Amazon Bedrock knowledge base over 18,000 PDF service manuals. Many answers depend on wiring diagrams and torque charts, technicians must see the page number of every cited passage, and each technician may only retrieve manuals for the product lines assigned to them in the company's identity provider. The team wants as few knowledge bases to manage as possible. Which THREE design decisions meet these requirements? (Select THREE)
A: Parse the PDFs with Amazon Bedrock Data Automation, so diagrams and charts are extracted and become retrievable content next to the text
B: Use a chunking strategy with a maximum token size, such as fixed-size chunking, so that citations keep the page number of each chunk
C: Add a product_line attribute in a .metadata.json file for each manual and pass a metadata filter built from the technician's assignments
D: Choose no chunking so each manual stays one complete chunk and the model always sees the whole manual together with its diagrams and charts
E: Keep the default parser because it reads the text layer of every PDF and has no usage charges for a large collection of manuals
F: Create one knowledge base per product line, and let the application query only the knowledge bases that match the technician's assignments
K: A,B,C
G: ## Three requirements, three settings
A knowledge base design is a chain of independent choices: how files are **parsed**, how parsed text is **chunked**, and how results are **filtered** at query time.
- **Parsing**: the default parser outputs text only. Amazon Bedrock Data Automation (BDA) and foundation model parsers also extract figures, charts, and tables from PDFs, so diagram content can be retrieved.
- **Chunking**: with *no chunking*, each document is a single chunk, and you cannot view the page number in citations or filter by the `x-amz-bedrock-kb-document-page-number` attribute. Any strategy that keeps chunks below a token limit keeps page-level citations.
- **Filtering**: for an S3 data source, a `fileName.extension.metadata.json` file attaches attributes to a document. A Retrieve or RetrieveAndGenerate request can pass a metadata filter, for example `product_line in [...]` built from the user's identity-provider groups.
## Example
`manual-4711.pdf.metadata.json` holds `{"metadataAttributes": {"product_line": "compressors"}}`; a technician assigned to compressors and pumps gets a filter on those two values.
W: A=BDA parser: extracts diagrams and charts from the PDFs, which the default parser drops, so torque and wiring questions become answerable.
B=Chunking with a token limit: keeps chunks small enough to carry their page number, so every citation shows the page.
C=Metadata filter: one knowledge base serves all product lines, and each query only returns manuals the technician may see.
X: D=No chunking: a whole manual becomes one chunk, and Bedrock documents that page numbers are then unavailable in citations and as a filter, which breaks the page requirement.
E=Default parser: it outputs only text, so the wiring diagrams and torque charts are never indexed and those answers stay out of reach.
F=One knowledge base per product line: it would isolate data, but it multiplies the number of knowledge bases to manage, which the stem asks to minimize; metadata filters do the same job in one knowledge base.
T: Pick the parser for content type, a token-limited chunking strategy for page citations, and metadata filters for per-user scope in one knowledge base.

@ AIP-C01 D1 T1.2 advanced tradeoff
S: A training company stores 9,000 hours of recorded lectures in Amazon S3. Learners type questions such as "where does the instructor explain lease accounting?" and expect a written answer that cites the lecture and the timestamp. Almost all of the useful information is in what the instructors say, not in what appears on screen. The team wants Amazon Bedrock Knowledge Bases to generate the answers with RetrieveAndGenerate. How should the knowledge base process the videos?
A: Use the Amazon Bedrock Data Automation parser, so the speech is transcribed into text that is chunked, embedded, and used by RetrieveAndGenerate
B: Use Amazon Nova Multimodal Embeddings so that each video segment is embedded natively, and set the video chunk duration to 30 seconds per segment
C: Use Amazon Nova Multimodal Embeddings with a 5-second video chunk duration, and add semantic chunking so sentence boundaries in the speech are kept
D: Use Amazon Titan Multimodal Embeddings G1, so video frames and the spoken words share one vector space for RetrieveAndGenerate queries
K: A
G: ## Two ways a knowledge base handles video
Amazon Bedrock Knowledge Bases offers two processing approaches for audio and video:
- **Amazon Nova Multimodal Embeddings** keeps the native format. Video and audio segments are embedded directly, which is ideal for *visual or audio similarity* (for example, search with an image as the query). The segment length is set by the video or audio chunk duration (1-30 seconds, default 5).
- **Amazon Bedrock Data Automation (BDA)** converts media to text: speech is transcribed with automatic speech recognition, and video gets scene summaries and transcripts. Normal text chunking and embedding then apply.
## Why generation matters here
Retrieval results for media carry timestamps either way. But AWS documents that RetrieveAndGenerate is supported when you use BDA processing or when the knowledge base contains text content. Lectures whose value is in speech are a text problem, so the BDA path fits both the content and the API.
W: BDA parser: speech becomes transcripts, which are chunked and embedded as text; answers can be generated with RetrieveAndGenerate and cite the lecture with its timestamp metadata.
X: B=Nova embeddings, 30-second segments: native video embeddings capture visual and audio similarity rather than searchable spoken text, and the generation requirement is documented only for BDA or text content.
C=Nova embeddings with semantic chunking: text chunking strategies affect only text documents when Nova Multimodal Embeddings is used, so semantic chunking would not touch the videos at all.
D=Titan Multimodal Embeddings G1: it embeds text and images; the knowledge base's video paths are Nova Multimodal Embeddings or BDA, and frames would still lose the spoken content.
T: Use BDA when the value of audio or video is in what is said and you need generated answers; use Nova Multimodal Embeddings for visual or audio similarity search.

@ AIP-C01 D1 T1.2 advanced troubleshooting
S: A logistics company runs a quarterly forecasting-commentary job on one Amazon Bedrock model and does not call that model anywhere else. The model card now shows the model in the Legacy state with an end-of-life date eight months away. The team planned to buy Provisioned Throughput before the next quarterly run in ten weeks and to migrate to a newer model at some point before end of life. Which plan avoids a failed run with the LEAST risk?
A: Evaluate and switch to an Active model now, since Legacy models get no new Provisioned Throughput and idle customers may lose access after 15 days
B: Buy the Provisioned Throughput today, before the Legacy state takes full effect, then keep using it until the end-of-life date and migrate after that date
C: Keep the current plan but schedule a small weekly invocation of the model, so the account stays active until the next quarterly run arrives
D: Fine-tune a copy of the Legacy model now, because custom models created from it keep working after the base model reaches its end-of-life date
K: A
G: ## Model lifecycle on Amazon Bedrock
Every model is **Active**, **Legacy**, or **End-of-Life (EOL)**. The state is shown in the console and in the `modelLifecycle` field of GetFoundationModel and ListFoundationModels.
When a model enters **Legacy**:
- the EOL date is added to the model card (most models have a 6-month Legacy period, some 45 days);
- new customers cannot adopt it, and existing customers **may lose access after 15 days of inactivity**;
- you **cannot create new Provisioned Throughput** and cannot start new fine-tuning jobs on it.
After EOL, requests fail; migration never happens automatically.
## Applying it to a quarterly job
A job that runs every 90 days is inactive for far longer than 15 days between runs, and the capacity plan depends on something Bedrock no longer sells for this model.
W: Switch now: evaluating and moving to an Active model removes both risks at once, the 15-day inactivity rule and the ban on new Provisioned Throughput, well before the next run.
X: B=Buy Provisioned Throughput today: the model is already Legacy, and new Provisioned Throughput cannot be created for Legacy models, so the purchase fails.
C=Weekly keep-alive calls: this may keep access, but the plan still depends on buying Provisioned Throughput, which is not possible, and it only postpones a migration that is mandatory before EOL.
D=Fine-tune a copy: new fine-tuning jobs cannot be created on a Legacy model, so there is no new custom model to fall back on.
T: When a model turns Legacy, plan the migration immediately: no new Provisioned Throughput or fine-tuning, and idle accounts can lose access after 15 days.

@ AIP-C01 D1 T1.3 advanced use-case
S: A support platform keeps resolved tickets as documents in the Amazon S3 data source of a Bedrock knowledge base. About 300 tickets close every hour, and agents expect a newly closed ticket to be retrievable within two minutes. A full data source sync currently takes 25 minutes, and only one ingestion job can run at a time for the data source. Which approach meets the freshness target with the LEAST operational overhead?
A: Write each closed ticket to S3 and also index it at once with IngestKnowledgeBaseDocuments, sending up to 25 documents in each request
B: Start an ingestion job from an S3 event notification for every new ticket object, so that each ticket is synced as soon as it is written
C: Split the data source into twelve data sources by ticket category and start all of their ingestion jobs in parallel every two minutes
D: Replace the knowledge base with a custom Lambda function that embeds each ticket and writes its vectors to an index outside of Bedrock
K: A
G: ## Sync versus direct ingestion
A knowledge base can learn about new documents in two ways:
- **Sync** (`StartIngestionJob`): Bedrock scans the whole data source and indexes what changed. Quotas allow **1 concurrent ingestion job per data source** and **1 per knowledge base** (5 per account), so syncs cannot overlap.
- **Direct ingestion** (`IngestKnowledgeBaseDocuments`): you submit documents and they are indexed into the vector store in one step, without a sync. A request carries up to **25 documents** and up to **6 MB** of payload.
## The S3 caveat
For an S3 data source, direct ingestion does not change the S3 bucket. Write the same document to S3 as well, or the next sync can overwrite the change. Do not run a direct ingestion request and an ingestion job at the same time.
## Sizing
300 tickets per hour is 5 per minute, so a request every minute with a handful of documents stays far below the 25-document limit.
W: Direct ingestion: each batch of closed tickets becomes retrievable within seconds, without waiting for a 25-minute sync, and writing to S3 too keeps the data source consistent for later syncs.
X: B=Ingestion job per object: only one job can run per data source and per knowledge base, and each job scans the source for about 25 minutes, so most start requests would be rejected and freshness would not improve.
C=Twelve data sources: the knowledge base itself is limited to one concurrent ingestion job, and the account to five, so parallel syncs every two minutes cannot run.
D=Custom pipeline: it can be made fast, but it rebuilds chunking, embedding, and indexing by hand and drops managed retrieval, which is far more overhead than one API call.
T: When documents must be searchable within minutes, index them with IngestKnowledgeBaseDocuments instead of waiting for a full data source sync.

@ AIP-C01 D1 T1.3 advanced troubleshooting
S: A legal team syncs an S3 data source into a Bedrock knowledge base. The ingestion job finishes, but its statistics show hundreds of failed documents. The failures are scanned court bundles of 60 to 140 MB each and exhibit photographs saved as 6 MB PNG files; smaller PDFs and images ingest normally. The team must make all of this content searchable without changing the vector store. What should the team do?
A: Split each bundle into PDF files under 50 MB, and downscale or re-encode the PNG exhibits below 3.75 MB before running the next sync
B: Request a service quota increase for the maximum ingestion file size, then run the same ingestion job again once AWS approves the change
C: Switch the parser to a foundation model parser, because it reads the large scanned files and images that the default parser rejects
D: Switch the data source to no chunking, so each large bundle is stored as a single chunk instead of exceeding the maximum chunk size
K: A
G: ## Size limits are checked per file
Amazon Bedrock Knowledge Bases checks each source file against fixed limits before it parses or chunks anything:
- a file with text content (such as `.pdf`, `.txt`, `.docx`) may be at most **50 MB**; the quota "Ingestion job file size with text content" is **not adjustable**;
- `.jpeg` and `.png` images may be at most **3.75 MB**.
Files above a limit fail, while the rest of the job continues, which is exactly the pattern of "job completed, some documents failed".
## Chunk size is something else
The maximum *chunk* size quota applies to the text pieces created by the chunking strategy, not to the source file. A large document is split into many chunks automatically.
W: Split and downscale: once every PDF is under 50 MB and every PNG under 3.75 MB, the files pass the per-file checks and ingest like the smaller documents already do.
X: B=Quota increase: the 50 MB file size quota is not adjustable, so there is nothing to request.
C=Foundation model parser: the parser runs after the file size check, so a 140 MB file is still rejected; it would only add parsing cost for the files that already work.
D=No chunking: the failures are about source file size, not chunk size, and no chunking would also remove page-level citations for every document.
T: Knowledge base ingestion rejects text files over 50 MB and images over 3.75 MB, so split or shrink files before syncing.

@ AIP-C01 D1 T1.4 advanced troubleshooting
S: A knowledge base uses semantic chunking on long policy documents with maximum tokens 1,000, buffer size 0, and breakpoint percentile threshold 95. Evaluations show that retrieved chunks are often close to the 1,000-token limit and mix two or three unrelated policy clauses, which dilutes the answers. The team wants to keep semantic chunking and avoid a large rise in ingestion cost. Which change addresses the problem?
A: Lower the breakpoint percentile threshold, so less dissimilarity between sentences is needed to start a new chunk and chunks get smaller
B: Raise the breakpoint percentile threshold to 99, so that only the clearest topic changes split chunks and each chunk then covers a single clause
C: Raise the buffer size to 3, so each sentence is embedded with more neighbors and the clause boundaries are detected by the embedding model
D: Raise maximum tokens to 2,000, so that a clause and its neighbors fit in one chunk and the model sees each clause completely and in context
K: A
G: ## How semantic chunking draws boundaries
Semantic chunking embeds sentences and measures how different each sentence is from the next. A **breakpoint** is placed where the dissimilarity is above a percentile of all measured distances.
- **Breakpoint percentile threshold**: a *higher* threshold requires sentences to be more distinguishable before they are split, which gives **fewer chunks with a larger average size**. A lower threshold splits more often.
- **Buffer size**: how many neighboring sentences are combined with each sentence when it is embedded (buffer 1 = previous, current, next). More buffer captures more context but can add noise.
- **Maximum tokens**: a hard upper bound on chunk size, while honoring sentence boundaries.
Semantic chunking uses a foundation model, so its cost depends on the amount of data; changing the threshold does not change how much data is processed.
## Reading the symptom
Chunks that run up to the token cap and contain several topics mean the threshold is so high that few breakpoints are found; the cap, not meaning, is cutting the text.
W: Lower threshold: at the 95th percentile only the most extreme topic changes split the text, so clauses run together; a lower percentile places more breakpoints, producing smaller, single-topic chunks for about the same ingestion cost.
X: B=Threshold 99: a higher threshold makes splits rarer and chunks larger, which worsens the mixing of clauses.
C=Buffer size 3: blending more neighbors into each sentence's embedding smooths the distance signal and can add noise; it does not lower the bar for creating a breakpoint.
D=Maximum tokens 2,000: a higher cap allows even larger chunks containing more unrelated clauses.
T: In semantic chunking, a higher breakpoint percentile threshold means fewer, larger chunks; lower it when chunks mix topics.

@ AIP-C01 D1 T1.5 advanced use-case
S: A travel insurer's knowledge base holds policy wordings for 14 countries and five plan tiers, and each document is tagged with country and plan_tier metadata. Users type questions such as "Does the Gold plan in Spain cover ski injuries?" Retrieval currently returns clauses from other countries and tiers. The team does not want to build or maintain its own parser that turns questions into filters. Which configuration fits?
A: Add implicitFilterConfiguration with the country and plan_tier attribute schemas to the Retrieve request, letting a Claude model build the filter
B: Enable query decomposition, so the question is split into sub-queries for the country and the plan tier and each sub-query is retrieved separately
C: Attach a reranker model to the retrieval configuration, so clauses that mention the right country and plan tier move to the top of the results
D: Switch the search type to hybrid, so the exact words Spain and Gold in the question are matched against the raw text of every clause
K: A
G: ## Explicit versus implicit metadata filters
A metadata filter restricts retrieval to chunks whose attributes match, for example `country = "ES" AND plan_tier = "Gold"`. With an explicit filter, your code must work out those values from the question.
**Implicit filtering** lets a model do that step: in `vectorSearchConfiguration` you add `implicitFilterConfiguration` with `metadataAttributes` (name, type, description of each attribute) and the model that generates the filter. Bedrock derives a filter from the user's question and applies it to the search. AWS lists Anthropic Claude models as supported for this.
## Why ranking is not filtering
Rerankers and hybrid search change the *order* or the *matching signal*, but chunks from Italy or the Silver tier can still appear. Only a filter excludes them.
W: Implicit filter: the model turns "Gold plan in Spain" into a filter on country and plan_tier, so only matching wordings are searched, and no in-house parser is needed.
X: B=Query decomposition: it splits complex questions into sub-queries to retrieve more relevant text, but it does not apply metadata conditions, so clauses from other countries can still come back.
C=Reranker: it reorders retrieved chunks by relevance; it cannot remove chunks that belong to the wrong country, and similar wording across countries keeps them close.

@ AIP-C01 D5 T5.1 advanced use-case
S: A team changed the chunking strategy of its Bedrock knowledge base and wants to know whether retrieval now captures all the facts needed to answer, independent of any generator model. It plans a retrieve-only RAG evaluation job with the Context relevance and Context coverage metrics, using 500 questions taken from production logs. What must the prompt dataset contain for the job to report Context coverage?
A: A ground truth answer for each question, because coverage measures how much of the ground truth information the retrieved texts contain
B: The model responses previously served for each question, because coverage compares the retrieved text with what users were actually told
C: A list of expected document IDs for each question, because coverage is calculated as recall over the expected source documents only
D: Nothing beyond the questions, because the evaluator model infers which facts are required from the question text and scores the passages
K: A
G: ## Two retrieve-only metrics, two different inputs
A retrieve-only RAG evaluation scores only what the knowledge base returns, so it isolates retrieval changes such as chunking from the generator.
- **Context relevance** (`Builtin.ContextRelevance`): how relevant the retrieved texts are to the question. The question alone is enough to judge this.
- **Context coverage** (`Builtin.ContextCoverage`): how much of the information in the **ground truth** the retrieved texts cover. AWS states you **must supply a ground truth** in the prompt dataset to use it.
## Example record
`{"conversationTurns": [{"prompt": {"content": [{"text": "What is the refund window for annual plans?"}]}, "referenceResponses": [{"content": [{"text": "30 days from purchase, pro-rated after that."}]}]}]}`
The evaluator checks whether the retrieved chunks contain both facts, 30 days and pro-rating.
W: Ground truth answers: coverage is defined against the ground truth, so each question needs a reference answer that lists the facts retrieval should surface.
X: B=Previously served responses: past answers may be wrong or incomplete, and coverage is defined against ground truth, not against what users were told.
C=Expected document IDs: the metric judges information in the retrieved text against the ground truth answer; it is not a document-ID recall calculation.
D=Questions only: questions are enough for context relevance, but coverage cannot be computed without knowing which facts a complete answer requires.
T: Context coverage needs a ground truth answer per question; context relevance needs only the question.
V: Amazon Bedrock, Amazon Bedrock Knowledge Bases

@ AIP-C01 D5 T5.1 advanced use-case
S: Legal reviewers report that a contract assistant built on Amazon Bedrock Knowledge Bases cites passages that do not support the sentences they are attached to, and that some claims carry no citation at all. The team will run a retrieve-and-generate RAG evaluation job to compare two prompt templates on exactly these two problems before release. Which TWO built-in metrics should the job include? (Select TWO)
A: Citation precision, which measures how many of the cited passages were correctly cited for the statements in each response
B: Citation coverage, which measures how well each response is supported by its cited passages and whether any citations are missing
C: Context relevance, which measures how relevant the retrieved passages are to each question before any answer has been generated at all
D: Faithfulness, which measures how well each response avoids hallucinating information that is absent from the retrieved passages
E: Completeness, which measures how well each response answers and resolves every aspect of the question that the user has asked
K: A,B
G: ## Citation metrics in RAG evaluations
Retrieve-and-generate RAG evaluation jobs include two metrics aimed at citations:
- **Citation precision** (`Builtin.CitationPrecision`): how many of the cited passages were correctly cited. A citation that does not support its sentence lowers it.
- **Citation coverage** (`Builtin.CitationCoverage`): how well the response is supported by the cited passages and whether citations are **missing**.
## Neighbors that measure something else
- **Faithfulness** checks whether the response invents information absent from the retrieved texts, regardless of which passage is cited.
- **Context relevance** is a retrieve-only metric about the retrieved passages.
- **Completeness** checks whether all parts of the question are answered.
## Mapping the complaint
"Cites passages that do not support the sentence" is a precision problem; "claims with no citation" is a coverage problem.
W: A=Citation precision: it directly scores wrong citations, the first complaint.
B=Citation coverage: it directly scores claims that lack supporting citations, the second complaint.
X: C=Context relevance: it judges retrieval before generation and belongs to retrieve-only jobs, so it cannot see how citations are attached.
D=Faithfulness: an answer can be faithful to the retrieved set as a whole while citing the wrong passage for a sentence, so it misses both complaints.
E=Completeness: it measures whether every part of the question is answered, not whether citations are correct or present.
T: Use citation precision for wrong citations and citation coverage for missing citations in Bedrock RAG evaluations.
V: Amazon Bedrock, Amazon Bedrock Knowledge Bases

@ AIP-C01 D5 T5.2 advanced troubleshooting
S: A Python service on Amazon EKS calls Amazon Bedrock through an interface VPC endpoint with a pooled boto3 client. After quiet periods of 10 minutes or more, the first request often hangs for over a minute and then fails with a connection reset, while the requests that follow are fast. Bedrock metrics show no throttling or server errors at those times. Which TWO changes fix the problem? (Select TWO)
A: Create the boto3 client with Config(tcp_keepalive=True), so that the SDK enables TCP keep-alive on its pooled endpoint connections
B: Set the pods' net.ipv4.tcp_keepalive_time to a value well below 350 seconds, such as 45 seconds, through the pod security context
C: Raise the client read_timeout to 300 seconds, so that the first request after a quiet period waits long enough for the endpoint to reconnect
D: Raise the SDK max retry attempts to 10 with exponential backoff, so a reset connection is retried until the pooled connection recovers
E: Replace the interface VPC endpoint with a NAT gateway path, because NAT gateways keep idle TCP connections open without any time limit
K: A,B
G: ## The 350-second idle timeout
NAT gateways, interface VPC endpoints, and Network Load Balancers drop a TCP connection that has been **idle for 350 seconds**, without telling either side. A pooled SDK connection that sat idle for 10 minutes is already dead; the client finds out only when it reuses it and waits for the operating system's TCP retries to time out. That produces the "first call after a quiet period hangs, then resets" pattern, with nothing wrong on the Bedrock side.
## Both settings are needed
- The SDK must **enable keep-alive** on its sockets (boto3 `Config(tcp_keepalive=True)`; the default is False).
- The OS must **send keep-alives often enough**: Linux defaults `net.ipv4.tcp_keepalive_time` to 7,200 seconds (2 hours), far above 350, so SDK keep-alive alone has no effect. AWS suggests a value such as 45 seconds; on EKS apply it in the pod security context, an init container, or the node AMI.
W: A=SDK keep-alive: turns on TCP keep-alive probes for the pooled connections, which is half of the documented fix.
B=Kernel keep-alive interval: makes those probes fire well before the 350-second idle limit, so the endpoint never drops the connection.
X: C=Longer read timeout: the connection is already silently dropped; waiting longer only stretches the hang before the reset.
D=More retries: retries recover after the failure, but the first request still hangs through the TCP timeout, so the symptom remains.
E=NAT gateway instead: NAT gateways have the same fixed 350-second idle timeout, and the change would also drop private connectivity.
T: Behind NAT gateways, interface endpoints, or NLBs, enable SDK keep-alive and lower the kernel keep-alive time below 350 seconds.
V: Amazon Bedrock, Amazon EKS, AWS PrivateLink

@ AIP-C01 D5 T5.2 advanced troubleshooting
S: During a product launch, a chatbot receives HTTP 529 overloaded_error responses from an Amazon Bedrock model in us-east-1, sometimes with a Retry-After header. Service Quotas shows the account at 40 percent of its tokens-per-minute quota, and the InvocationThrottles metric is near zero. The team's runbook says to request a quota increase for any capacity error. What should the team do instead?
A: Retry with exponential backoff and jitter that honors Retry-After, and route through a cross-Region inference profile if the model supports one
B: Request a tokens-per-minute quota increase immediately, because 529 responses indicate that the account exceeded its on-demand quota
C: Retry every failed request immediately from all clients at the same moment, so that requests are served as soon as model capacity becomes available
D: Lower max_tokens on every request, because 529 errors occur when the reserved quota of input plus max_tokens exceeds the per-minute limit
K: A
G: ## Three different capacity errors
- **429 ThrottlingException**: the request exceeded **your account's quota**. Remedies include backoff, quota increases, Reserved tier, or Provisioned Throughput.
- **503 ServiceUnavailable**: the service is temporarily unable to handle the request; not related to account quotas.
- **529 overloaded_error**: the **model** is temporarily unable to serve because of high demand or insufficient serving capacity. AWS calls it a transient capacity error, different from a 429.
## Documented handling for 529
- Retry with **exponential backoff and random jitter**; if the response has `Retry-After`, wait that long.
- Avoid immediate or synchronized retries from many clients, which increase load and delay recovery.
- If the model supports it, use **cross-Region inference** to spread requests over several Regions.
- If it persists, contact AWS Support with the request ID, model ID, Region, and timestamp.
W: Backoff with jitter plus cross-Region inference: this is the documented response to a transient serving-capacity error, and routing across Regions adds capacity that a quota change cannot.
X: B=Quota increase: the account is at 40 percent of its quota and is not being throttled; 529 is about model serving capacity, so a higher quota changes nothing.
C=Immediate synchronized retries: AWS warns that they increase load and delay recovery.
D=Lower max_tokens: the max_tokens reservation affects quota throttling (429), not the model-side overload that produces 529.
T: A 529 overloaded_error is a transient model-capacity problem: back off with jitter and use cross-Region inference, not a quota increase.
V: Amazon Bedrock

@ AIP-C01 D5 T5.2 advanced troubleshooting
S: A team deployed an agent on Amazon Bedrock AgentCore Runtime together with an AgentCore Memory resource. The AgentCore observability dashboard in CloudWatch shows no traces or spans for the agent, although the runtime's built-in metrics appear and the agent is instrumented with the ADOT SDK. The team also needs spans for the memory operations to debug slow recalls. What should the team do?
A: Turn on CloudWatch Transaction Search once for the account, and get memory spans by enabling tracing when the memory is created
B: Add an AWS X-Ray daemon sidecar to the runtime, because AgentCore Runtime sends spans only through a locally running X-Ray daemon process
C: Enable CloudTrail data events for the runtime and memory resources, because AgentCore observability builds its traces from CloudTrail
D: Create a CloudWatch Logs subscription filter on the runtime log group, so that span data in the logs is copied into the observability dashboard
K: A
G: ## What AgentCore observability needs
AgentCore emits metrics, spans, and logs in OpenTelemetry-compatible form and stores them in Amazon CloudWatch.
- **Built-in metrics** for runtime, memory, gateway, built-in tools, and identity appear by default.
- To view **spans and traces**, you must complete a **one-time setup**: turn on **CloudWatch Transaction Search**.
- To view **service-provided spans for memory resources**, you must also **enable tracing when you create the memory**.
- The ADOT SDK adds custom spans, metrics, and logs from your agent code, including for agents hosted outside AgentCore Runtime.
## Reading the symptom
Metrics without traces is the signature of the missing Transaction Search setup; the instrumentation is already in place.
W: Transaction Search plus memory tracing: the one-time Transaction Search setup makes runtime spans and traces visible, and memory spans need tracing enabled at memory creation.
X: B=X-Ray daemon sidecar: AgentCore Runtime is a managed runtime that emits OTEL telemetry to CloudWatch; the documented gap is Transaction Search, not a missing daemon.
C=CloudTrail data events: CloudTrail is for auditing API activity; traces in AgentCore observability come from emitted spans, not CloudTrail records.
D=Subscription filter: a log subscription streams log events to another destination; it does not turn logs into the dashboard's traces.
T: AgentCore traces need CloudWatch Transaction Search turned on once, and memory spans need tracing enabled when the memory is created.
V: Amazon Bedrock AgentCore, Amazon CloudWatch
