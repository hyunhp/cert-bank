@ Q001430 explain
G: ## Supervisor and router patterns for multi-agent systems
With many domains (billing, returns, technical support), one agent with one huge prompt becomes slow, expensive and error-prone. A common pattern splits the work:
- A **classifier or supervisor** reads the user's message and conversation history and decides which specialist should handle it.
- **Specialized agents** each have a focused prompt, their own tools and their own knowledge sources.
- The supervisor forwards the request, and in some designs coordinates several agents and combines their replies.
**AWS Agent Squad** (formerly Multi-Agent Orchestrator) is an open-source AWS Labs framework for this pattern: a classifier selects the best agent for each message, it keeps per-agent conversation context, and it also offers a supervisor agent for team-style coordination. Amazon Bedrock Agents supports a similar supervisor and collaborator setup.
Note: Amazon Bedrock Agents was renamed Bedrock Agents Classic and closed to new customers on 2026-07-30; existing customers can keep using it, and AWS points new agent builds to Amazon Bedrock AgentCore, which can host multi-agent systems built with open-source frameworks. Exam questions may still name Bedrock Agents.
W: Classifier-based routing to specialized agents: interpreting intent and delegating to the right specialist is exactly the supervisor pattern that Agent Squad implements.
X: A=One monolithic prompt: packing every domain's instructions into one prompt is the design this pattern replaces; it dilutes instructions and grows token cost with every domain added.
B=Daily batch transform: offline batch scoring has no interactive intent detection or delegation, and cannot serve live customer conversations.
C=Direct client-side model calls: calling one model straight from the client has no routing layer, no specialists, and exposes model access to the client.
T: A supervisor that classifies intent and hands off to specialist agents is the router or supervisor multi-agent pattern, as in Agent Squad; one giant prompt or a direct model call has no routing at all.

@ Q001455 explain
G: ## Two problems: network path and protocol
A cloud agent calling a legacy on-premises system must solve two separate problems.
**Private connectivity**
- **AWS Site-to-Site VPN** creates encrypted IPsec tunnels over the internet between the VPC and the data center; it is quick to set up.
- **AWS Direct Connect** is a dedicated private link with consistent bandwidth and latency.
Either lets a Lambda function in the VPC reach the SOAP endpoint's private IP without exposing it to the internet.
**Protocol translation**
Agents call tools with JSON (for example a Bedrock agent action group backed by Lambda, or a Lambda target behind an Amazon Bedrock AgentCore Gateway). A SOAP service expects XML envelopes. A Lambda function, or an API Gateway integration with mapping templates, translates `{"sku":"A-100"}` into a SOAP `GetStock` request and maps the XML response back to JSON.
## Result
The agent gets real-time, write-capable access to inventory through a normal tool interface, while the legacy system stays private.
Note: Amazon Bedrock Agents was renamed Bedrock Agents Classic and closed to new customers on 2026-07-30; existing customers can keep using it, and AWS points new agent builds to Amazon Bedrock AgentCore. The connectivity and translation design is the same either way.
W: Hybrid connectivity plus translation: VPN or Direct Connect gives a private path, and Lambda or API Gateway converts REST/JSON tool calls to SOAP, so the agent sees live inventory securely.
X: A=Expose SOAP to the internet: AWS IP ranges are shared by many customers, so an allowlist of them does not restrict access to this account, and the legacy system becomes an internet-facing attack surface.
B=Knowledge Base over exports: retrieval over exported files is read-only and only as fresh as the last export, so the agent cannot check live stock or place reservations.
C=Periodic S3 copies with Athena: the snapshot is stale between copies and read-only, so order processing could promise stock that no longer exists.
T: Legacy integration needs both a private network path and a protocol translation layer; copies or public exposure trade away freshness or security.

@ Q001470 explain
G: ## How a Bedrock agent learns what an API can do
An **action group** tells an Amazon Bedrock agent which operations it may call and what each one expects. You define it with either function details or an **OpenAPI schema** (JSON or YAML), and a Lambda function or a return-of-control flow carries out the call.
The agent reads the schema at run time:
- The `summary` and `description` of each path and operation help it decide which of the 12 operations matches the user's request.
- Parameter `type`, `required` flags and `enum` values tell it which values it must collect or ask the user for before calling.
## One contract, many uses
OpenAPI is an industry standard. The same document that guides the agent can feed code generators (for example OpenAPI Generator) to produce client SDKs and API documentation.
Example: `POST /orders/{orderId}/cancel` with a required `reason` string lets the agent pick cancel instead of refund, and ask the user for the reason when it is missing.
## Availability note
Amazon Bedrock Agents was renamed Bedrock Agents Classic and closed to new customers on 2026-07-30; existing customers can keep using it, and AWS points new agent builds to Amazon Bedrock AgentCore. Exam questions may still name Bedrock Agents. The OpenAPI lesson carries over: an AgentCore Gateway can also take an OpenAPI specification as a target and expose its operations as tools.
W: OpenAPI schema for the action group: descriptions steer operation selection, typed and required parameters make the agent build complete, valid calls, and the same machine-readable definition generates client SDKs. It remains the answer the exam expects.
X: A=IAM policy on the service role: IAM decides which AWS actions the agent's role may perform, such as invoking the action group's Lambda function. It says nothing about your order API's operations or parameters, so it cannot fix wrong choices or missing fields.
B=Natural-language list in instructions: free text gives hints but no types or required flags the agent can check against, gets crowded as operations grow, and cannot be fed to an SDK generator.
C=CloudFormation template as definition: a template describes infrastructure resources to deploy, not request and response shapes. Action groups do not accept CloudFormation templates as their API definition.
T: Agents choose and call APIs well when given a typed OpenAPI contract with good descriptions, and that same contract also generates SDKs; prose in the instructions does neither reliably.

@ Q001487 explain
G: ## Amazon Bedrock model evaluation
**Model evaluation jobs** in Amazon Bedrock measure model output quality in a repeatable way:
- **Automatic evaluation** runs a dataset of prompts (built-in datasets or your own JSON Lines file in S3) through the model and scores the outputs with built-in metrics such as **accuracy**, **robustness** and **toxicity**.
- **LLM-as-a-judge** uses another model to score qualities like helpfulness or harmfulness.
- **Human evaluation** sends responses to a work team of your own reviewers when human judgment is needed.
Results are saved to S3 and shown in the console, so the same job can be rerun on each new model version and compared.
Example: before release, run the fine-tuned model on 2,000 prompts, check that its toxicity score stays under the target and that robustness does not drop when prompts contain typos or small changes.
Note: Amazon Bedrock Agents (which offers multi-agent collaboration) was renamed Bedrock Agents Classic and closed to new customers on 2026-07-30; existing customers can keep using it, and AWS points new agent builds to Amazon Bedrock AgentCore. Exam questions may still name Bedrock Agents.
W: Bedrock model evaluation jobs: they give repeatable, quantitative scores for toxicity and robustness across many prompts, without a person reading every response.
X: A=Knowledge Bases hybrid search: hybrid search combines keyword and semantic retrieval to find documents. It improves retrieval, it does not score a model's outputs for toxicity.
B=Provisioned Throughput benchmarks: Provisioned Throughput buys dedicated model capacity for predictable throughput. It is about capacity and cost, not output safety.
C=Multi-agent collaboration tests: multi-agent collaboration lets a supervisor agent coordinate other agents. It is an orchestration feature, not a toxicity or robustness measurement.
T: Quantitative, repeatable checks of output quality and safety before release are Bedrock model evaluation jobs, not retrieval, capacity or agent orchestration features.

@ Q001510 explain
G: ## Management events and data events
AWS CloudTrail records two main kinds of events:
- **Management events**: control plane operations such as `CreateAgent` or `CreateGuardrail`. Logged by default, and the last 90 days are visible in Event history.
- **Data events**: high-volume operations on resources. Not logged by default; you must enable them on a trail or a CloudTrail Lake event data store, choosing the resource type.
## Where Bedrock calls land
Bedrock runtime `InvokeModel` and `Converse` calls are logged as management events. Bedrock Agents runtime calls such as `InvokeAgent` (and knowledge base `Retrieve` / `RetrieveAndGenerate`) are data events, so they appear only if data event logging was enabled for that resource type, for example agent aliases.
Data events cannot be recovered for past dates when logging was off.
Note: Amazon Bedrock Agents was renamed Bedrock Agents Classic and closed to new customers on 2026-07-30; existing customers can keep using it (and its `InvokeAgent` logging works as described), and AWS points new agent builds to Amazon Bedrock AgentCore. Exam questions may still name Bedrock Agents.
W: InvokeAgent is a data event: it is not in management events, so data event logging for Bedrock agent aliases must be enabled to record the calling principal going forward.
X: A=CloudTrail ignores Bedrock: CloudTrail does record Bedrock calls; model invocation logging captures prompts and responses, which is a different purpose than recording the caller.
C=24-hour retention: CloudTrail Event history keeps 90 days of management events, and trails or event data stores can keep them much longer.
D=Roles not recorded: CloudTrail records the assumed-role session in `userIdentity`, including the role ARN and session name, so role callers are identifiable.
T: InvokeAgent calls are CloudTrail data events that must be enabled explicitly; they never appear among management events, so missing entries mean data events were off, not that the caller was hidden.

G: ## AWS Config for configuration compliance
AWS Config continuously evaluates resource configurations against rules and marks each resource `COMPLIANT` or `NON_COMPLIANT`.
- **Managed rules** cover common checks.
- **Custom rules** (AWS Lambda or Guard) implement your own logic and can run on configuration changes or on a periodic schedule.
- **Conformance packs** and organization rules deploy the same rules to every account, and an aggregator shows results in one place.
## Checking agents for guardrails
A periodic custom rule can list the Bedrock agents in each account, read each agent's configuration (the `GetAgent` response includes its guardrail configuration), and report a non-compliant result that names every agent without one. EventBridge can then notify owners or start remediation.
Note: Amazon Bedrock Agents was renamed Bedrock Agents Classic and closed to new customers on 2026-07-30; existing customers can keep using it, and AWS points new agent builds to Amazon Bedrock AgentCore. Exam questions may still name Bedrock Agents; the AWS Config approach applies to whatever agent resources the organization runs.
W: AWS Config rule: Config is built to evaluate resource configurations continuously across accounts, so a custom rule can flag every Bedrock agent without an attached guardrail.
X: A=Comprehend classification: Comprehend labels natural-language text you send it; it does not read resource configurations or track compliance over time.
B=Macie discovery: Macie scans S3 objects for sensitive data such as PII; it does not inspect Bedrock agent settings.
D=Glue crawlers: crawlers infer data schemas to build the Data Catalog; they do not evaluate service configurations against a policy.
T: Continuous "is every resource configured correctly?" checks are AWS Config rules, not data-analysis services such as Comprehend, Macie or Glue.

@ Q001518 explain
G: ## What an agent trace contains
Amazon Bedrock Agents can return a trace for each invocation (`enableTrace`). It shows the agent's internal workings:
- Preprocessing and orchestration steps, including the model's rationale.
- Action group and function names, and the parameters the agent chose.
- Knowledge base queries and retrieved references.
- Observations returned by tools and parts of the prompt templates.
## Why this is sensitive
An attacker who sees tool names like `issueRefund(orderId, amount)`, prompt instructions and data sources can craft prompt injections that target them precisely. Show customers a curated answer (and citations if useful), and keep full traces in an internal audit view or logs with restricted access.
Note: Amazon Bedrock Agents was renamed Bedrock Agents Classic and closed to new customers on 2026-07-30; existing customers can keep using it, and AWS points new agent builds to Amazon Bedrock AgentCore, whose observability traces carry the same kind of internal detail. Exam questions may still name Bedrock Agents.
W: Traces reveal internals: raw traces expose tool names, prompts and data sources, which gives attackers a map for targeted prompt injection.
X: A=Customers correct reasoning: agents do not learn from customers reading traces, and exposing internals adds risk without improving accuracy.
B=Traces are encrypted: encryption in transit and at rest protects data from third parties, but it does nothing once the trace is deliberately displayed to the customer.
C=Tracing only for testing: traces can be enabled on production invocations, so this is not a limitation and not the risk.
T: Keep full agent traces internal and show customers only curated output, because traces reveal the internals attackers exploit; encryption does not help once you display them.

@ Q001519 explain
G: ## Debugging an agent step by step
A Bedrock agent answer comes from a chain: the model reasons, picks an action group, fills parameters, the tool (for example a Lambda function) returns data, and the model writes the answer. A wrong refund can come from any link.
## Reading the trace
With tracing enabled, each step shows:
- **Rationale**: why the model chose the next action.
- **Invocation input**: which action and parameters, for example `calculateRefund(orderId="A-1043", items=2)`.
- **Observation**: what the tool returned, for example `{"refund": 19.99}`.
- **Final response**: what the model told the customer.
If the tool returned 39.98 but the answer says 19.99, the model misread the result. If the parameters were wrong, the reasoning or prompt is at fault. If the tool returned 19.99 from bad order data, the backend or data is the problem.
Note: Amazon Bedrock Agents was renamed Bedrock Agents Classic and closed to new customers on 2026-07-30; existing customers can keep using it, and AWS points new agent builds to Amazon Bedrock AgentCore, where AgentCore Observability provides step-by-step traces for the same kind of debugging.
W: Inspect the agent trace: stepping through reasoning, tool parameters and tool results pinpoints whether the error came from the model, the tool call or the data.
X: A=Majority vote of reruns: repeating the prompt samples the model's output again but gives no insight into which step failed, and a consistently wrong tool result would win the vote.
C=Disable the refund tool: this is a temporary mitigation that stops the harm but does not identify the cause.
D=Retrain the model: retraining before knowing the cause wastes effort, and it cannot fix a bug in the tool or bad backend data.
T: Diagnose agent errors with the trace, step by step; reruns, disabling tools or retraining do not tell you where it went wrong.

@ Q001520 explain
G: ## Two different kinds of "explainability"
Explaining a prediction depends on what kind of system made it.
- A **traditional ML model** (for example, gradient-boosted trees on tabular credit data) maps input features to a score. The question is "how much did each feature push this prediction up or down?" **SHAP** answers that: it assigns each feature a contribution, and the contributions add up to the difference between this prediction and a baseline. SageMaker Clarify computes SHAP values per prediction and globally.
- A **Bedrock agent** has no fixed feature vector. It reasons in steps: read the request, pick an action group or knowledge base, call a tool, read the result, decide again. The question is "why did it take these steps?" The agent **trace** (enable it with `enableTrace` on `InvokeAgent`) returns the pre-processing, orchestration (rationale, invocation input, observation) and post-processing steps.
## Example
A loan is declined: SHAP might show `debt_to_income` contributed -0.30 and `credit_history_months` -0.12. An agent that refunded an order: the trace shows it called `lookupOrder`, then `issueRefund`, with its rationale for each step.
Note: Amazon Bedrock Agents was renamed Bedrock Agents Classic and closed to new customers on 2026-07-30; existing customers can keep using it, and AWS points new agent builds to Amazon Bedrock AgentCore, whose observability traces play the same role. Exam questions may still name Bedrock Agents.
W: Clarify SHAP for the tabular model and agent trace for the agent: each tool answers the question its system actually poses, feature attribution for the tabular model and step-by-step orchestration reasoning for the agent.
X: A=Agent trace for both: a trace records an agent's orchestration steps. A tabular model makes a single prediction with no steps or tool calls, so there is nothing to trace and no per-feature attribution.
C=Amazon Comprehend for both: Comprehend is an NLP service for entities, sentiment, key phrases and classification. It does not explain predictions of other models or agents.
D=SHAP for both: SHAP attributes a score to fixed input features. An agent's decision to call a tool comes from multi-step LLM reasoning over text, which SHAP values cannot reconstruct.
T: Feature attribution (Clarify SHAP) explains tabular predictions; the agent trace explains an agent's multi-step reasoning, and neither substitutes for the other.

@ Q001555 explain
G: ## Why end-to-end metrics are not enough for agents
An agent completes a task in several steps: the foundation model reasons, chooses a tool, the tool runs, and the model uses the result to decide the next step. A single "task failed" signal cannot say which step broke.
## Instrument each step
- Record, for every tool call: the tool name, success or failure, latency and error type (timeout, authorization error, bad input, empty result).
- Keep the end-to-end task success rate next to it.
- Use traces (for example OpenTelemetry spans viewed in CloudWatch or AWS X-Ray, Amazon Bedrock AgentCore Observability, or Bedrock agent traces) to follow one task across model and tool steps.
## Reading the result
Example: if the database-query tool's error rate jumped from 1% to 30% while the others are stable, the tool is the problem. If all tools succeed when called but tasks fail because the model calls the search API for math problems, the model's tool selection is the problem.
Note: Amazon Bedrock Agents was renamed Bedrock Agents Classic and closed to new customers on 2026-07-30; existing customers can keep using it, and AWS points new agent builds to Amazon Bedrock AgentCore. Per-tool monitoring applies to either.
W: Per-tool metrics alongside task success: success, latency and error type for each tool show whether a specific tool is failing or the tools work and the model is choosing or using them badly, which isolates the root cause.
X: A=Assume the model is at fault: replacing or retraining the model is expensive and slow, and if a tool is actually failing the change would not fix anything; the evidence has to come first.
B=End-to-end success only: this is the signal that already dropped. It shows that something fails but cannot say whether it is the model's reasoning or one of three tools.
D=Remove per-tool monitoring: this throws away exactly the signal needed for diagnosis, and model error messages do not reliably describe tool-side failures such as timeouts or bad responses.
T: To debug an agent, instrument every tool call separately and compare it with task success, so you can tell tool failures from reasoning failures.

G: ## Human-in-the-loop review
Some model outputs should be checked by a person before they are trusted or reused. A human review workflow needs three things: a rule that decides which items go to a person, a workforce and task UI, and a structured place where the reviewers' answers land.
## How Amazon Augmented AI (A2I) provides this
- A **flow definition** sets the review task, the instructions, the worker task template and where results are written in Amazon S3.
- A **workforce** can be your own private team or a vendor workforce (the same workforce options as SageMaker Ground Truth).
- A **custom task type** lets any application, including one built on Amazon Bedrock, call `StartHumanLoop` for items it chooses, for example responses whose confidence score is below `0.6` or a random 5% sample.
The reviewers' corrected labels arrive as JSON in S3, ready to be merged into an evaluation or tuning dataset.
## Availability note
- Amazon Mechanical Turk reached end of support on 2026-09-29, so the public Mechanical Turk workforce option is gone from A2I and Ground Truth; private and vendor workforces still work.
- Amazon Bedrock Agents was renamed Bedrock Agents Classic and closed to new customers on 2026-07-30; existing customers can keep using it, and AWS points new agent builds to Amazon Bedrock AgentCore. A2I works the same with either, because the application calls `StartHumanLoop` itself.
W: Amazon A2I human review workflows: A2I is built for exactly this pattern (route selected predictions to qualified people, collect structured corrections) and runs the task UI, worker management and result storage for you, so almost no custom infrastructure is needed.
X: B=Guardrails with human review: Amazon Bedrock Guardrails evaluates prompts and responses against policies (content filters, denied topics, sensitive information, grounding) and blocks or masks automatically. It has no reviewer workforce, task queue or labeling output.
C=X-Ray trace annotations: annotations are indexed key-value pairs on traces used to filter and search request paths. They record what happened in a request; they do not send items to people or collect corrected labels.
D=AWS Config rules: Config evaluates the configuration of AWS resources (for example, whether a bucket is encrypted). It never sees model responses and cannot run a labeling task.
T: Sending selected model outputs to people and collecting their corrections is a human-review workflow, which is A2I's job; Guardrails filters automatically and involves no humans.

@ Q001571 explain
G: ## Outcome metrics versus activity metrics for agents
An agent turns a user request into a series of steps: it reasons, calls tools (action groups in Amazon Bedrock Agents), reads results and answers. Metrics fall into two groups:
- **Activity or efficiency metrics** describe how the agent worked: latency per tool call, tokens used, number of steps.
- **Outcome metrics** describe whether the user got what they came for.
Every tool call can return HTTP `200` and the session can still fail. Example: the user asks for a refund, the agent looks up the order successfully, then answers "your order has shipped" and never starts the refund. All calls succeeded, but the goal was missed.
## Measuring task completion
Task completion rate is the share of sessions where the underlying goal was achieved: the status was reported correctly, the refund was actually issued, or the case was escalated when it should be. It is judged with labeled test scenarios, human review or an LLM-as-a-judge that compares the session with the expected outcome.
Note: Amazon Bedrock Agents was renamed Bedrock Agents Classic and closed to new customers on 2026-07-30; existing customers can keep using it, and AWS points new agent builds to Amazon Bedrock AgentCore. Exam questions may still name Bedrock Agents; task completion is the outcome metric on either platform.
W: Task completion rate: it directly measures whether the user's goal was achieved in the session, which is exactly the "did the agent actually succeed" question, independent of whether individual calls succeeded technically.
X: A=Average tool latency: latency tells you how fast calls return, and a fast agent that issues the wrong refund or never escalates still scores well.
C=Tokens per session: token counts track cost and verbosity. A session can use few tokens and fail, or many tokens and succeed.
D=Number of action groups used: this reflects which tools were touched, not whether they were the right ones or whether the goal was met; using more tools is not better.
T: Judge an agent on outcomes (was the goal achieved), not on activity metrics like latency, tokens or tool counts that can look healthy while users fail.

@ Q001572 explain
G: ## Where agent failures hide
An Amazon Bedrock agent calls an action group, usually an AWS Lambda function, and expects a response in a specific shape: fields such as `messageVersion` and a `response` object that names the action group and the API path or function and carries the response body. If the Lambda returns malformed or unexpected content, the agent cannot use the result, may retry, and often gives up.
Aggregate metrics such as overall task completion only show that something got worse. To find what got worse, break results down per component.
## Per-tool metrics
For each action group, record over a test set (and in production):
- success rate: calls that returned a well-formed, usable result
- error rate: exceptions, timeouts, non-success status codes
- unparsable-output rate: responses that did not match the expected schema
Bedrock Agents traces (the orchestration trace shows each invocation input and observation) provide the raw data. Running this per-tool evaluation before release would show the new payment action group failing while the others stay healthy.
Note: Amazon Bedrock Agents was renamed Bedrock Agents Classic and closed to new customers on 2026-07-30; existing customers can keep using it, and AWS points new agent builds to Amazon Bedrock AgentCore. Exam questions may still name Bedrock Agents; per-tool evaluation applies on either platform.
W: Per-action-group success versus error or unparsable-output rates: it isolates each tool, so the new payment action group's malformed responses show up as a spike in unparsable output even while tool selection is correct.
X: A=Final response toxicity score: toxicity measures harmful language in answers. Malformed Lambda output causes abandoned tasks, not toxic text, so the score would stay flat.
B=Tokens generated per turn: longer or shorter reasoning is at most an indirect side effect and does not tell you which tool failed or why.
C=Increase the session timeout: the agent does not fail because the session expires; it fails because the tool response cannot be parsed. More time only gives it more time to fail, and this is not an evaluation approach at all.
T: After adding a tool, measure success and error rates per tool; aggregate metrics show that quality dropped, per-tool metrics show where.
