G: ## Imperative versus declarative
A pipeline is a set of declared datasets (streaming tables, materialized views, views) and flows into Delta tables or sinks. The engine plans the order, retries failed flows and manages checkpoints. Dataset functions describe a query result; arbitrary side effects inside them can run more than once during planning and retries and are not supported as a design.
**Structured Streaming `foreachBatch`** hands each microbatch to your function as a DataFrame with a batch id. There you can write to several targets, call services and run custom `MERGE` statements, and you manage the checkpoint and the job yourself.
## Pipelines have a ForEachBatch sink too
Lakeflow pipelines now offer a **ForEachBatch sink** (Python, `@dp.foreach_batch_sink()`), fed by a streaming flow such as `append_flow`. It gives each micro-batch to custom Python logic, for example merging into an external table or writing to several destinations, while the pipeline manages the checkpoint per flow. The pipeline does not track or clean up what the function writes, and a full refresh restarts `batch_id` at 0 without resetting the targets.
So per-batch side effects inside a pipeline belong in that sink, never in expectations or in the queries that define streaming tables and materialized views.
## Decision
- Standard ingestion and transformation into Delta tables, CDC, expectations, automatic orchestration: pipeline datasets.
- Imperative per-batch logic with external side effects and several different writes: Structured Streaming `foreachBatch` in a job, or a ForEachBatch sink if the logic is part of a pipeline.
W: Structured Streaming with foreachBatch in a job: the function receives each microbatch and can combine a Delta write, a service call and a JDBC merge under your control. Among the listed designs it is the only one with a defined place for per-batch side effects; the pipelines ForEachBatch sink would also work, but none of the pipeline options here uses it.
X: A=Expectation failure action: expectations only warn, drop the row or fail the update; they cannot run custom actions such as a REST call.
C=Materialized view: it is a batch result defined by a query; putting a REST call or a JDBC merge into the query has no defined per-batch execution.
D=Table definitions with side effects: dataset functions are declarations that may be evaluated more than once, so service calls inside them are not a reliable place for external effects; in a pipeline that work would go to a ForEachBatch sink instead.
T: Put imperative multi-target per-batch logic in foreachBatch (Structured Streaming in a job, or a pipeline's ForEachBatch sink), never in expectations or dataset definitions.
