S: A query unions an `orders` stream (late by up to 1 hour) with a partner feed (late by up to 2 hours), each with its own `withWatermark`. By default the dashboard waits for the slow feed and results are late. An engineer sets `spark.sql.streaming.multipleWatermarkPolicy` to `max`. What does this change?
A: Each input keeps its own watermark for its own state, so late records from the slower partner feed are still guaranteed to be processed by the query
B: The global watermark follows the slowest input, so no record from either feed is ever dropped and state grows without limit
C: The global watermark follows the fastest input, so state is evicted sooner and output is earlier, but late records from the slower feed may be dropped
D: The query now rejects inputs that declare different delays, and both feeds must use the same threshold again
K: C
G: ## One global watermark
A streaming query can union or join several input streams, each with its own `withWatermark` delay. Structured Streaming tracks the maximum event time per input, derives a watermark from each input's delay, and then uses a single global watermark for the stateful operations. The default policy is `min`: the slowest stream decides, so nothing is dropped because one input lags, at the price of holding more state and delaying results.
## Trade-off
Setting the policy to `max` lets the global watermark move at the pace of the fastest stream. Latency and state shrink, but data from slower streams that falls behind the global watermark is dropped. The Spark guide says to use the setting judiciously, and Databricks recommends applying it with caution.
Example: if orders reach event time 12:00 and the partner feed is at 10:30, the `min` watermark is based on the partner feed, the `max` watermark on orders.
W: Global watermark follows the fastest input: this is the documented effect of `max`, trading completeness of late partner data for lower latency and less state.
X: B=Slowest input: that is the default `min` policy, not `max`; also state is bounded by the watermark in both policies, it is not unbounded.
A=Per-input watermarks: there is a single global watermark for the query; per-input delays only feed into its calculation, and late data is never guaranteed once the watermark passes it.
D=Rejecting different delays: the engine accepts different delays per input by design; that is why the policy setting exists.
T: min protects slow inputs and costs latency; max lowers latency and state but can silently drop late data.
