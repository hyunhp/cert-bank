@ DBX-DEP D1 T1.3 advanced use-case
S: A retailer must fit one small demand-forecast model per store with a pandas-based library and write one row of forecasts per store and day. There are 2,000 stores, each with about 50,000 history rows, and the library needs all rows of one store at once in a single pandas DataFrame. The team wants Spark to run the stores in parallel with the least custom plumbing. Which API fits this requirement best?
A: A scalar pandas UDF of type `pd.Series` to `pd.Series`, applied to the sales column, with the store id passed in as an extra column argument
B: `df.groupBy("store_id").applyInPandas(fit_and_forecast, schema=...)`, which hands all of a store's rows to the function as one pandas DataFrame
C: `df.mapInPandas(fit_and_forecast, schema=...)`, which streams Arrow batches of the whole input to the function and returns all the rows that it yields
D: A Python UDF registered in Unity Catalog that receives one row at a time and keeps a per-store buffer in a module-level dictionary
K: B
G: ## Split-apply-combine with pandas function APIs
Databricks documents three pandas function APIs: grouped map, map and cogrouped map. **Grouped map** (`groupBy().applyInPandas()`) implements split-apply-combine: Spark splits the data by the grouping key, calls your Python function once per group with a `pandas.DataFrame` that holds all rows of that group, and combines the returned DataFrames into one Spark DataFrame with the schema you declare.
## What to watch
- All data of one group is loaded into memory before the function runs, and `maxRecordsPerBatch` does not apply to groups. 50,000 rows per store is small, but a very skewed group can cause out-of-memory errors.
- Groups run in parallel across executors, so 2,000 stores become 2,000 independent function calls.
## Example
`df.groupBy("store_id").applyInPandas(fit_and_forecast, schema="store_id string, day date, forecast double")` fits one model per store.
W: Grouped map: each call receives the complete history of one store as a pandas DataFrame, which is exactly what the forecasting library needs, and Spark parallelizes the groups.
X: A=Scalar pandas UDF: it receives Arrow batches of a column that can mix stores and split one store across batches, so a per-store model cannot be fitted reliably.
C=mapInPandas: it iterates over batches of the input without grouping, so one store's rows can arrive in several batches mixed with other stores.
D=Row-at-a-time UDF with a buffer: a module-level dictionary is per Python worker and per task, so rows of one store are scattered and the buffer never sees the whole history.
T: When a function needs all rows of a key at once, use `groupBy().applyInPandas()` and keep group sizes within memory.
V: PySpark, pandas function APIs

@ DBX-DEP D1 T1.8 advanced use-case
S: A Python pipeline builds `silver_orders` as a streaming table. A partner-facing Delta table `ops.order_status`, which a support tool also writes, must receive every changed order as an upsert on `order_id`, not as an extra row. The team wants this step inside the same pipeline, with its lineage and update monitoring, rather than in a separate job. Full refreshes of the pipeline are rare. Which design fits these needs?
A: A ForEachBatch sink whose function runs `MERGE INTO ops.order_status` on `order_id` for each micro-batch, used as the target of an append flow over `silver_orders`
B: A Delta sink created with `create_sink` for `ops.order_status` and an append flow over `silver_orders`, so each changed order reaches the partner table in the same update
C: An AUTO CDC flow with `keys=["order_id"]` and `ops.order_status` as its target, so the pipeline applies the changed orders to that table as SCD type 1 upserts
D: A separate Structured Streaming job that reads `silver_orders` and merges into `ops.order_status` in `foreachBatch`, scheduled after the pipeline in a Lakeflow Jobs job
K: A
G: ## Sinks in Lakeflow pipelines
By default a pipeline flow writes to a streaming table or materialized view that the pipeline manages. A **sink** is an output outside those datasets, used as the `target` of an append flow (sinks exist in Python only). Sink types:
- **Delta sink** (`create_sink`): writes the flow's rows to a Unity Catalog managed or external Delta table.
- **Kafka and Event Hubs sinks**: write to a message bus.
- **ForEachBatch sink** (`@dp.foreach_batch_sink`): your Python function receives each micro-batch and can **merge, upsert or write to several targets**.
Limitations from the docs: only append flows and update flows can write to sinks, `create_auto_cdc_flow` cannot; expectations do not apply to sinks; a full refresh does not clean up data already written to a sink.
## Applying it
The partner table lies outside the pipeline and needs upserts, so a ForEachBatch sink that runs `MERGE` per micro-batch keeps the step in the pipeline. Keep the merge idempotent: after a full refresh the flow's checkpoint restarts and earlier data is sent again.
Before the ForEachBatch sink existed, the usual answer was a separate Structured Streaming job with `foreachBatch`; it still works but leaves the pipeline.
W: ForEachBatch sink with MERGE: the function upserts each micro-batch into the external table on `order_id`, and the flow stays in the pipeline with its lineage and event log.
X: B=Delta sink: a Delta sink appends the flow's rows, so every change of an order would add another row instead of updating the existing one.
C=AUTO CDC flow: AUTO CDC flows write into a streaming table of the pipeline and cannot use sinks, so they cannot target the shared partner table.
D=Separate job: it works technically, but it moves the step out of the pipeline, which the team explicitly wants to avoid.
T: To upsert from a pipeline into a table outside it, use a ForEachBatch sink with an idempotent MERGE.
V: Lakeflow Spark Declarative Pipelines, Delta Lake

@ DBX-DEP D1 T1.7 advanced use-case
S: A logistics system publishes CDC events with `op` values `INSERT`, `UPDATE`, `DELETE` and, after its monthly purge, a single `TRUNCATE` event that has no key. The target `depot_status` must always mirror the current source state; nobody needs history. An engineer drafts `create_auto_cdc_flow` with `stored_as_scd_type="2"` and `apply_as_truncates=expr("op = 'TRUNCATE'")`. Topic retention is seven days, so the target cannot be rebuilt from the topic later. Which configuration should the team use instead?
A: Keep SCD type 2 and handle the purge with `apply_as_deletes=expr("op IN ('DELETE','TRUNCATE')")`, so that the keyless purge event closes every open row of the target
B: Keep SCD type 2 with `apply_as_truncates`, and add `track_history_except_column_list` so that the purge event is ignored by history tracking
C: Use SCD type 1 with `apply_as_deletes` for `DELETE` and `apply_as_truncates` for `TRUNCATE`, since truncates are supported only for SCD type 1
D: Use SCD type 1 without truncate handling and run a full refresh of the target after each monthly purge, so the table is rebuilt from the topic
K: C
G: ## Truncate handling in AUTO CDC
The AUTO CDC APIs (formerly APPLY CHANGES) accept `apply_as_deletes` to turn matching events into deletes by key and `apply_as_truncates` to treat an event as a **full table TRUNCATE**. The Python reference states that `apply_as_truncates` is supported **only for SCD type 1**; SCD type 2 does not support truncate operations.
## Choosing the SCD type
- SCD type 1 keeps one current row per key and overwrites it, which is exactly a mirror of the current state.
- SCD type 2 keeps history rows with start and end columns; it has no meaning for "clear everything".
## Example
`create_auto_cdc_flow(target="depot_status", source="cdc_view", keys=["depot_id"], sequence_by="seq", apply_as_deletes=expr("op = 'DELETE'"), apply_as_truncates=expr("op = 'TRUNCATE'"), except_column_list=["op","seq"], stored_as_scd_type=1)`.
W: SCD type 1 with deletes and truncates: the target mirrors current state, which needs no history, and type 1 is the only type that accepts truncate events.
X: A=TRUNCATE as delete: a delete is applied by key, and the truncate event carries no key, so it cannot remove all rows.
B=SCD 2 with truncates: SCD type 2 does not support `apply_as_truncates`, and the history-tracking list only controls which column changes create new versions.
D=Full refresh after each purge: it reprocesses the whole source on every purge, and with limited topic retention it can lose rows that are no longer in the source.
T: `apply_as_truncates` works only with SCD type 1, which also fits a target that mirrors current state.
V: Lakeflow Spark Declarative Pipelines, AUTO CDC

@ DBX-DEP D1 T1.10 advanced use-case
S: A nightly job runs a legacy PySpark library that builds its input with `sc.parallelize()` and several RDD transformations before converting to a DataFrame. The job must read Unity Catalog tables, rewriting the library is out of scope this quarter, and only the job's service principal should use the compute. On a standard access mode cluster the job fails on the RDD calls. Which compute choice fits all constraints?
A: Keep standard access mode and add the RDD functions to an allowlist in the cluster's Spark configuration, so the Unity Catalog checks accept them
B: Use serverless compute for jobs, because it runs Unity Catalog workloads with the full Spark API surface, including the RDD and SparkContext methods
C: Use a no-isolation shared cluster, which allows RDD APIs, and grant the service principal access to the Unity Catalog tables it has to read
D: Use a jobs cluster in dedicated access mode assigned to the service principal, which supports Unity Catalog and the RDD APIs the library needs

C=No-isolation shared: that legacy mode does not enforce Unity Catalog, so the job could not read the governed tables.
T: Workloads that need RDD or SparkContext APIs with Unity Catalog belong on dedicated access mode compute.

@ DBX-DEP D1 T1.12 advanced use-case
S: A fleet platform must emit an `OFFLINE` row for a vehicle when no telemetry event arrives for 10 minutes, even if the vehicle never sends another event, and must clear that vehicle's state after it reconnects or after 24 hours. Built-in aggregations and joins cannot express the rule. The team writes Python and runs Structured Streaming on a current runtime. Which approach does Databricks recommend for this logic?
A: `flatMapGroupsWithState` with a processing-time timeout, because it is the recommended operator for new arbitrary stateful applications in Python
B: `transformWithStateInPandas` with a `StatefulProcessor` that registers a timer per vehicle and sets a TTL on its state values
C: A windowed `groupBy(window("event_ts", "10 minutes"), "vehicle_id")` aggregation in append mode with a 24-hour watermark on `event_ts`
D: `dropDuplicatesWithinWatermark("vehicle_id")` with a 10-minute watermark, then a filter that keeps rows where the latest event is older than 10 minutes
K: B
G: ## Custom stateful logic
For arbitrary state, Databricks recommends `transformWithState` (Python: `transformWithStateInPandas`) instead of the legacy `flatMapGroupsWithState` and `mapGroupsWithState`. A `StatefulProcessor` implements:
- `handleInputRows`: update state and emit rows for keys that receive data in a micro-batch;
- `handleExpiredTimer`: runs time-based logic **whether or not the key receives new rows**;
- state values with individual **time-to-live (TTL)** to bound state size.
## Applying it
On every event the processor resets a 10-minute timer for the vehicle. If the timer expires, `handleExpiredTimer` emits `OFFLINE`. A 24-hour TTL removes state for vehicles that disappear.
## Why built-ins do not fit
Window aggregations and deduplication only emit results for keys that have rows; they cannot produce a row for silence.
W: transformWithStateInPandas: timers fire for keys without new input, so silence becomes an `OFFLINE` row, and TTL bounds state, which is the documented recommended API.
X: A=flatMapGroupsWithState: Databricks lists it as a legacy arbitrary stateful operator and recommends `transformWithState` for new applications.
C=Windowed aggregation: a window with no events for a vehicle produces no row, so the absence of telemetry is never reported.
D=Deduplication plus filter: deduplication only removes repeated keys among arriving rows and cannot emit output for a vehicle that sends nothing.
T: Use `transformWithState` timers and TTL when output must be produced for keys that stop sending data.
V: Structured Streaming, transformWithState

@ DBX-DEP D1 T1.5 advanced troubleshooting
S: A job runs as the service principal `prod_sp`, which has `SELECT` on `finance.gold.revenue`. One task is a SQL query task that runs the saved query `q_revenue`, owned by analyst Dana. After Dana lost access to the finance catalog, the task fails with a permission error, while notebook tasks in the same job still read the table. Nobody wants to grant Dana access again. The job must keep using `prod_sp` for all data access. What explains the failure, and what is the fix?
A: The query uses the sharing setting Run as owner, so it runs as Dana; switch it to Run as viewer so the task uses the job's Run as identity
B: SQL tasks ignore the job's Run as field and always use the identity of the user who last edited the job; re-save the job as `prod_sp`
C: The SQL warehouse caches the owner's credentials for 24 hours; restart the warehouse so that `prod_sp` is picked up by the next run
D: Service principals cannot run saved queries; replace the SQL task with a notebook task, because notebook tasks are the only ones that respect Run as
K: A
G: ## Two identities in a job
A job's **Run as** identity is used for its tasks' data access. Saved SQL queries and alerts add their own **sharing setting**:
- **Run as owner**: scheduled runs of the SQL task always use the identity of the query's owner.
- **Run as viewer**: scheduled runs use the identity set in the job's Run as field.
The jobs privileges page shows this exact case: a query owned by user A with Run as owner runs as A even when the job runs as a service principal; changing the query to Run as viewer makes the job use the service principal.
## Applying it
Dana's lost grant breaks only the SQL query task. Setting `q_revenue` to Run as viewer makes it run as `prod_sp`, which already holds `SELECT`.
W: Run as owner sharing: the query runs as its owner, Dana; switching it to Run as viewer makes the task use `prod_sp`, which has the needed grant.
X: B=Last editor identity: tasks run as the Run as identity or, for owner-shared queries, the query owner; the last editor of the job plays no role.
C=Cached credentials: there is no documented credential cache of this kind; the identity comes from the query's sharing setting on every run.
D=Notebook tasks only: SQL tasks with Run as viewer queries, and SQL file tasks, do use the job's Run as identity.
T: A saved query shared as Run as owner ignores the job's Run as identity; use Run as viewer to run it as the job's principal.
V: Lakeflow Jobs, Databricks SQL

@ DBX-DEP D1 T1.5 advanced troubleshooting
S: An engineer wants to change the Run as identity of a production job, deployed from a bundle, to the service principal `etl-prod`. The engineer has CAN MANAGE on the job, but the deployment fails with a permission error naming `etl-prod`. Workspace admins should not be involved in every deploy, and the job's owner must stay the same. The bundle's `run_as` mapping names `etl-prod`, and the job already reads only tables that `etl-prod` may read. Which missing permission must the engineer receive?
A: CAN MANAGE on every notebook and file the job references, because changing the Run as identity re-checks the deployer's access to each task's source
B: The workspace admin role, because only admins can assign a service principal as the Run as identity of a job deployed from a bundle
C: The Service Principal User role on `etl-prod`, which lets a user set that service principal as the Run as identity of jobs they manage
D: IS OWNER on the job, because the Run as identity can only be changed by the job owner and never by a user who holds CAN MANAGE

G: ## Who may set Run as
To change the Run as setting of a job you need **CAN MANAGE or IS OWNER** on the job. The value can be yourself or **any service principal on which you have the Service Principal User role** (entitlement). Workspace admins can by default change Run as to any principal, unless account admins restrict this.
## Bundles
A bundle's `run_as` mapping is applied by the deploying identity, so the same rule applies: the deployer needs the Service Principal User role on the target principal.
## Applying it
The engineer has CAN MANAGE, so the only missing piece is the role on `etl-prod`. Ownership does not need to change.
W: Service Principal User role: CAN MANAGE already allows changing Run as, and the role on `etl-prod` is what permits choosing that principal.
X: A=CAN MANAGE on notebooks: notebook access is checked for the Run as identity at run time, not as a prerequisite for changing the setting.
B=Admin role: admins can do it, but the documented non-admin path is CAN MANAGE plus the Service Principal User role.
D=IS OWNER only: the docs allow CAN MANAGE or IS OWNER to change Run as; ownership would also change the owner, which is forbidden here.
T: Setting a job's Run as to a service principal needs CAN MANAGE on the job and the Service Principal User role on that principal.

An engineer adds an init script that upgrades pandas, as on the old classic cluster, but the task still imports the older version. The fix must avoid classic compute and keep dependency settings with the task. The job must keep running on serverless compute. Which approach fits serverless compute?

@ DBX-DEP D8 T8.2 advanced troubleshooting
S: A nightly job has a single notebook task, `load_kpis`, which replaces the rows of `gold.kpis` for its `run_date` job parameter. Last night it failed on a short source timeout that has since cleared. The on-call engineer wants to rerun the failed work with the same `run_date` and calls the Jobs API repair endpoint for that run, which returns an error. The job's structure must not change tonight. What explains the error, and what fits?
A: Repair is supported only for jobs with two or more tasks; start a new run with Run now and the same `run_date`, which is safe because the task replaces that date
B: Repair of a single-task job requires `rerun_all_failed_tasks` set to true; send the repair request again with that flag and the original `run_date` value
C: A run can be repaired only within one hour after it failed; ask an administrator to extend the repair window and then repeat the same repair request
D: A failed run must be cancelled before it can be repaired; cancel the run, then call the repair endpoint again with `load_kpis` listed in `rerun_tasks`
K: A
G: ## What a repair does
A repair reruns the **unsuccessful tasks of a multi-task run and their dependents** with the current job and task settings; successful tasks are not rerun. Each repair adds a column to the run's matrix view.
## The single-task case
The docs state that repair is supported only with jobs that orchestrate **two or more tasks**. To rerun a failed single-task job, trigger it again with **Run now**, passing the same job parameters.
## Is a new run safe?
Both a repair and a new run start the task from the beginning; Lakeflow Jobs does not make tasks idempotent. This task replaces the rows of one date, so a rerun with the same `run_date` gives the same result without duplicates.
W: Run now for a single-task job: repair is documented only for jobs with two or more tasks, and this idempotent task can simply run again with the same parameter.
X: B=rerun_all_failed_tasks: the flag selects which tasks a repair reruns; it does not lift the rule that repair needs a multi-task job.
C=Repair window: the docs set no such time limit; the error comes from the single-task job, not from the age of the run.
D=Cancel first: a failed run has already ended, so there is nothing to cancel, and naming the task in `rerun_tasks` does not make a single-task job repairable.
T: Repair is for multi-task jobs; rerun a failed single-task job with Run now and the same parameters, and keep the task idempotent.
V: Lakeflow Jobs

@ DBX-DEP D2 T2.4 advanced use-case
S: A provider shares the Unity Catalog table `sales.orders` with a partner's Databricks workspace through Databricks-to-Databricks sharing. The partner wants to process new orders with Structured Streaming and to read row-level changes with `table_changes()`. The provider updates rows daily with `MERGE`. The partner must not get write access, and the provider does not want to maintain a second copy of the data. Which provider-side setup lets the partner do both?
A: Share the table without history and grant the recipient `MODIFY` on the share, so the recipient can track changes in its own copy of the table
B: Share only a view over the table with a filter on the last day, so the recipient streams from the view and reads changes from its output
C: Enable change data feed on the table, then add it to the share `WITH HISTORY`, so recipients can stream from it and query `table_changes()`
D: Add the table with a partition filter on the order date and enable deletion vectors, so the recipient can stream only the newest partitions
K: C
G: ## History sharing
When a provider adds a table to a share it can include its **history** (`WITH HISTORY`). History sharing lets recipients:
- run time travel queries (`VERSION AS OF`, `TIMESTAMP AS OF`);
- use the table as a **Structured Streaming source** (options such as `ignoreChanges` or `skipChangeCommits` handle updates);
- query the **change data feed** with `table_changes()`, but only if CDF was **enabled on the table before** it was shared with history.
Tables with deletion vectors or column mapping must also be shared with history.
## Applying it
Enable `delta.enableChangeDataFeed`, then `ALTER SHARE ... ADD TABLE sales.orders WITH HISTORY`.
W: CDF plus WITH HISTORY: history sharing enables streaming reads and time travel, and enabling CDF beforehand makes `table_changes()` available to the recipient.
X: A=No history plus MODIFY: shares are read-only for recipients, and without history neither streaming nor the change feed is available.
B=Filtered view: a view does not expose the table's change feed, and streaming from shared data requires a table shared with history.
D=Partition filter and deletion vectors: a partition filter limits rows but does not enable the change feed, and deletion vectors themselves require history sharing.
T: Recipients can stream and read CDF only from tables shared WITH HISTORY, with CDF enabled before sharing.
V: OpenSharing (Delta Sharing), Change Data Feed

S: A Kafka topic carries Protobuf-encoded order events. Producers evolve the schema several times a month and register every version in a Confluent Schema Registry. The ingestion stream decodes `value` into a struct for the bronze table. The team does not want to redeploy the stream each time a descriptor changes, and the registry needs basic authentication. Malformed records must not stop the stream. Which decoding setup fits?
A: Call `from_protobuf` with `descFilePath` pointing to a descriptor file in a volume, and replace that file and restart the stream whenever a producer registers a new version

A streaming read of a Delta table fails on commits that delete or modify rows unless told otherwise. `skipChangeCommits` ignores such transactions and processes only appends, which is exactly right when upstream deletes must not reach downstream. Each payment is processed once, so its contribution stays in gold after silver trims it. The daily totals are a streaming aggregation with a watermark on the payment time: each day is emitted once its watermark passes and is never recomputed from the trimmed silver table.
W: Streaming table with skipChangeCommits: it processes each appended row once and ignores the retention deletes, so history survives in gold.
X: A=Strict refresh policy: a materialized view may still need a full recompute in some cases, and a policy that forbids it makes refreshes fail rather than preserving history.
C=Nightly deep clone: each clone copies the current trimmed silver, so it never contains rows older than 90 days.
D=Static history plus view: the static table covers only go-live data; days that age out later fall into neither part.
T: When sources delete processed data that downstream must keep, use a streaming table (with `skipChangeCommits` for Delta deletes), not a materialized view.
V: Lakeflow Spark Declarative Pipelines, Structured Streaming

@ DBX-DEP D2 T2.2 advanced troubleshooting
S: A partner writes order data into an Iceberg table registered as a foreign table through catalog federation. A serverless materialized view aggregates it hourly, and every refresh is a full recompute that takes 40 minutes, although only a few thousand rows arrive per hour. The partner keeps writing to its own catalog. The aggregate must stay a materialized view in Unity Catalog. Which change enables incremental processing at Databricks?
A: Enable row tracking on the foreign Iceberg table, because row tracking is the only missing requirement for incremental refresh of any Iceberg source
B: Ingest the foreign table incrementally into a Unity Catalog managed table and define the materialized view on that table instead
C: Set the refresh policy of the materialized view to incremental strict, so the engine is forced to process only the new rows of the foreign table
D: Replace the materialized view with a standard view over the foreign table, so each query reads only the newly arrived rows from the partner
K: B
G: ## Supported sources for incremental refresh
Materialized views support base tables such as Delta tables, Unity Catalog managed Iceberg tables (v2 and v3), materialized views and streaming tables. The docs state that **materialized views can read foreign Iceberg tables, but incremental refresh isn't supported for these sources**. Volumes, external locations and foreign catalogs are not supported as incremental sources either.
## Applying it
Because the partner's catalog cannot change, bring the data under Unity Catalog management first (for example a streaming or scheduled incremental load into a managed table), then build the aggregate on that table so its refreshes can be incremental.
W: Managed copy as source: incremental refresh is supported on Unity Catalog managed tables but not on foreign Iceberg tables.
X: A=Row tracking on a foreign table: row tracking is a Delta feature of tables Databricks manages, and foreign Iceberg sources are excluded from incremental refresh regardless.
C=Incremental strict policy: the policy makes a refresh fail when incrementalization is impossible; it cannot make an unsupported source incremental.
D=Standard view: a view runs the full query on every read and stores nothing, so each query scans the whole foreign table.
T: Foreign Iceberg tables can feed materialized views only through full recompute; land them in managed tables for incremental refresh.
V: Materialized views, Apache Iceberg, Unity Catalog

@ DBX-DEP D4 T4.1 advanced use-case
S: A platform lead suspects that full refreshes drive pipeline costs. For the last 60 days and all pipelines in the region's workspaces, the lead wants one SQL query that lists each full refresh with the tables it covered and whether a job task or a user started it. Most pipelines do not publish their event logs, and the query must use generally available system tables. Which source fits this need?
A: `system.lakeflow.pipeline_update_timeline`, using `update_type`, `full_refresh_selection`, `trigger_type` and `trigger_details` of each pipeline update
B: `system.lakeflow.pipelines`, whose rows record every change to a pipeline's settings, including each time a user requested a full refresh of it
C: `system.billing.usage` for pipeline workloads, where an hourly cost spike identifies a full refresh and the job run that requested it
D: `system.access.audit` filtered on pipeline actions, which records each full refresh request with its list of tables and the job that started it
K: A
G: ## Pipeline system tables
- `system.lakeflow.pipelines`: a slowly changing dimension of pipeline settings (a new row per change).
- `system.lakeflow.pipeline_update_timeline`: start and end times and compute of each **pipeline update**; long updates are sliced into hourly rows, and `result_state` is set only on the last one.
Useful columns of the update timeline:
- `update_type`: `FULL_REFRESH`, `REFRESH` or `VALIDATE`;
- `full_refresh_selection` and `refresh_selection`: tables updated with or without a full refresh; `reset_checkpoint_selection`: flows whose checkpoints were cleared;
- `trigger_type`, such as `JOB_TASK`, `USER_ACTION`, `API_CALL` or `RETRY_ON_FAILURE`, and `trigger_details.job_task.job_id` when a job task started the update;
- `run_as_user_name`.
The table is regional, supports streaming and keeps 395 days.
## Applying it
Filter on `update_type = 'FULL_REFRESH'` or a non-empty `full_refresh_selection`, keep one row per `workspace_id` and `update_id`, and read `trigger_type` and `trigger_details`.
W: Pipeline update timeline: it records every update with its type, the tables refreshed in full and what triggered it, across pipelines and without published event logs.
X: B=pipelines table: it tracks pipeline settings over time, not the updates that ran or the tables they refreshed.
C=Billing spikes: usage shows cost per period, not the update type or the table list, so a spike cannot prove a full refresh or who started it.
D=Audit table: the audit log system table is in Public Preview, which the requirement for generally available tables excludes.
T: Audit pipeline updates, their full-refresh selections and triggers with `system.lakeflow.pipeline_update_timeline`.
V: system tables, Lakeflow Spark Declarative Pipelines

@ DBX-DEP D5 T5.4 advanced troubleshooting
S: A downstream job sums `amount` from `table_changes('silver.orders', start_version)` to update a running revenue total. Silver receives `MERGE` updates that change `amount` on existing orders. After a week, the total is clearly too high, and the excess grows with the number of updated orders. Inserts and deletes are handled correctly. The job must keep reading the change feed incrementally. What causes the error, and what is the fix?
A: Updates appear as `update_preimage` and `update_postimage` rows; subtract preimage amounts and add postimage amounts instead of summing both
B: The change feed writes every update in two separate commits; filter on `_commit_version` and keep only even versions before summing the amounts
C: The merge writes its updates as delete plus insert rows; read the table with `readChangeFeed` disabled and sum the current snapshot of silver instead
D: The change feed omits the old value of updated rows; enable row tracking on silver so that the feed starts recording preimages for every update
K: A
G: ## Change data feed row types
CDF output has metadata columns `_change_type`, `_commit_version` and `_commit_timestamp`. `_change_type` contains `insert`, `update_preimage`, `update_postimage` and `delete`: an update produces **two rows**, the value before (preimage) and the value after (postimage).
## Applying it
Summing every change row adds both the old and the new amount for each update. A correct delta is `+amount` for `insert` and `update_postimage`, and `-amount` for `update_preimage` and `delete`. Alternatively keep only postimages and apply them by key with a merge.
## Why the excess grows
Every updated order adds its old amount once more, so the error is proportional to the number of updates, exactly as observed.
W: Pre- and postimage rows: both are in the feed, and treating preimages as negative turns the feed into a correct net change.
X: B=Duplicate commits: an update is one commit with two rows of different change types; version parity has no meaning.
C=Delete plus insert: CDF reports merges as preimage/postimage pairs, and dropping the feed would lose the incremental design.
D=Missing preimages: preimages are always part of CDF output for updates; the problem is that they are counted positively.
T: CDF records updates as preimage and postimage rows; net them out instead of summing all change rows.
V: Delta Lake, Change Data Feed
