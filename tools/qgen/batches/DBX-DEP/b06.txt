@ DBX-DEP D4 T4.1 advanced troubleshooting
S: A finance analyst totals `system.billing.usage` by `usage_metadata.job_id` to chart the cost of the job `daily_agg`. Last month the job was moved from its own job compute to a shared all-purpose cluster. Runs still succeed, but since the move the job shows no billed usage at all. What explains this, and how can the cost still be attributed?
A: Records of the job are delayed for several weeks after a compute change, so the analyst should wait until the usage is back-filled under the same job ID
B: The usage is now billed as ALL_PURPOSE and has no job ID, so the analyst attributes it through `usage_metadata.cluster_id` and the cluster's tags or owner
C: Jobs that run on all-purpose compute are not billed at all, because the cluster already carries the cost and only job compute creates billable records
D: The job ID is populated only in the first hourly record of a run, so the analyst should group by `usage_start_time` to find the remaining rows
K: B
G: ## What the usage table can tell you
`system.billing.usage` has one row per product, SKU and hour. The `usage_metadata` struct names the objects behind the row, but only some fields are filled for each compute type.
- `job_id` and `job_run_id` are populated for serverless jobs and for jobs that run on job compute. They are not populated for jobs run on all-purpose compute.
- `cluster_id` is populated for non-serverless usage, and `billing_origin_product` tells you whether the row is `JOBS`, `ALL_PURPOSE`, `DLT` and so on.
## Consequence for cost attribution
When a task runs on a shared all-purpose cluster, the bill is for the cluster, not for the job. Per-job cost is lost, and the cost can only be split by cluster, by `custom_tags` on the cluster, or by the cluster owner (join `system.compute.clusters.owned_by` on `cluster_id`). This is one reason production jobs are moved to job compute or serverless: the billing record then carries the job and run IDs.
W: ALL_PURPOSE without job ID: the job ID is not filled for all-purpose usage, so the rows exist under the cluster; attribution has to use the cluster ID, its tags or its owner.
X: A=Back-fill delay: billable usage normally appears within about half a day, not weeks, and a delayed record would still carry the same field values once it arrives.
C=Not billed: all-purpose compute is billed, and it appears in the usage table under its own product; it is only the job link that is missing.
D=First hourly record: the job ID is filled on every row that has it; grouping by start time does not recover a field that is null on all-purpose rows.
T: Job and run IDs in billing rows exist only for jobs compute and serverless jobs; all-purpose usage is attributed by cluster, tag or owner.
V: system.billing.usage

@ DBX-DEP D4 T4.1 advanced troubleshooting
S: A monthly cost report sums `usage_quantity` for the account with the filter `WHERE record_type = 'ORIGINAL'`, chosen to avoid negative numbers. The finance team notes that the report no longer matches the invoice for a month in which Databricks corrected some earlier records. Which change makes the report correct?
A: Keep only `RESTATEMENT` rows, because they contain the corrected values and the other record types are duplicates of them
B: Remove the filter on `record_type` and sum every row, so each retraction cancels its original and the restatement adds the corrected amount
C: Group by `record_id` and take the row with the latest `ingestion_date`, which always holds the final quantity for that record
D: Keep `ORIGINAL` rows and add 12 hours of lag to the report window, because corrections are written into the original rows after they arrive
K: B
G: ## Corrections in the usage table
Billable usage rows are append-only. When Databricks corrects a record, it adds two rows rather than editing the old one:
- a `RETRACTION` row, identical to the original except that `usage_quantity` is negative and cancels it;
- a `RESTATEMENT` row with the corrected fields and quantity.
Both carry the same time window as the original. A correction that removes a record entirely may add only the retraction.
## Why the filter is wrong
Summing everything yields the right total, because original plus retraction is zero and the restatement remains. Filtering to `ORIGINAL` keeps the incorrect values and drops the correction; filtering to `RESTATEMENT` drops every record that was never corrected. The negative numbers are not an error, they are the mechanism.
```sql
SELECT usage_metadata.job_id, SUM(usage_quantity) AS dbus
FROM system.billing.usage
WHERE usage_date >= date_trunc('month', current_date())
GROUP BY ALL
```
W: Sum all record types: each retraction negates its original and the restatement carries the corrected value, so a plain sum over all rows matches the invoice.
X: A=Only restatements: most records are never corrected, so they exist only as original rows and would vanish from the total.
C=Latest ingestion per record_id: retraction and restatement rows are new rows with their own IDs, so this picks neither the corrected total nor a consistent set of rows.
D=Original plus lag: records are not edited after they arrive and the availability lag does not apply to corrections, so waiting never repairs the figure.
T: Never filter billing usage to ORIGINAL; sum all record types so retractions cancel originals.
V: system.billing.usage

@ DBX-DEP D4 T4.1 advanced troubleshooting
S: A report joins usage to job names and gets totals above the billed amount for jobs that were renamed or had their schedule edited.
```sql
SELECT j.name, SUM(u.usage_quantity) AS dbus
FROM system.billing.usage u
JOIN system.lakeflow.jobs j
  ON u.workspace_id = j.workspace_id AND u.usage_metadata.job_id = j.job_id
GROUP BY j.name
```
Which correction fixes the inflated totals and also keeps the cost of jobs that have since been deleted?
A: Replace the inner join with a join on job name and apply `SELECT DISTINCT` to the usage rows before summing them
B: Add `WHERE j.delete_time IS NULL` to the same query, so that only rows without a deletion time are joined to the usage rows of each job
C: Keep only the latest row per workspace and job (`ROW_NUMBER()` by `change_time` descending), then LEFT JOIN usage to it
D: Group by `j.change_time` as well, so that every historical version of a job reports its own total next to the others
K: C
G: ## `jobs` is a history table
`system.lakeflow.jobs` (like `job_tasks` and `pipelines`) is a slowly changing dimension. Every change to a job emits a new row with a new `change_time`, and a deletion emits a row with `delete_time` set. A job edited three times therefore has four rows.
Joining usage to all of those rows repeats each usage row once per version, so sums inflate.
## The pattern
First reduce the dimension to one row per entity: `ROW_NUMBER() OVER (PARTITION BY workspace_id, job_id ORDER BY change_time DESC)` and keep row number 1. Then join. Use a LEFT JOIN from usage if deleted jobs must stay in the cost report. Filtering `delete_time IS NULL` in the same query that reads the table does not remove deleted jobs; it only removes the deletion rows and returns the last state before deletion. A filter on `delete_time` belongs after the latest row is chosen, and only when you want live jobs.
W: Latest row, then LEFT JOIN: one row per job removes the fan-out, and the LEFT JOIN keeps usage of jobs whose latest row records a deletion.
X: A=Join on name with DISTINCT: names are not unique across jobs or workspaces, and DISTINCT on usage rows would also collapse legitimately identical hourly rows.
B=delete_time filter in the same query: the history rows of live jobs are still multiplied, and deleted jobs lose their cost from the report.
D=Group by change_time: this leaves every version as a separate line, so totals per job are split across versions instead of being correct.
T: Collapse SCD2 system tables to the latest row per key before joining them to fact tables.
V: system.lakeflow.jobs

@ DBX-DEP D4 T4.1 advanced use-case
S: An account runs workspaces in two cloud regions. An analyst in a us workspace runs the "most expensive jobs" cost query that joins `system.billing.usage` with `system.lakeflow.jobs` through a LEFT JOIN. Costs of the eu workspaces appear, but their job names are NULL. What is the cause, and what is the fix?
A: Usage covers all regions but the jobs table only the current region, so the name lookup must run in an eu workspace
B: The analyst lacks `SELECT` on the eu catalogs, so the account admin must grant read access to every eu job to make the names visible
C: The eu jobs run on serverless compute, which writes no rows to `system.lakeflow.jobs`, so their names exist only in billing tags and custom tags
D: The LEFT JOIN drops rows from other regions, so switching to an INNER JOIN returns the names and keeps the costs of both regions
K: A
G: ## Global versus regional system tables
System tables are shared with your metastore's region, and the overview lists each table as regional or global.
- `system.billing.usage` is global: usage from every workspace of the account appears, whichever region the querying workspace is in.
- The `system.lakeflow` tables (jobs, job_tasks, job_run_timeline, pipelines and so on) are regional: they hold only the workspaces deployed in the same cloud region as the workspace where you run the query.
So a cost query that joins a global table to a regional dimension shows costs for all regions but names only for the local one. The documented remedy is to run the query in a workspace of the other region (or run it once per region and combine the results).
W: Global usage, regional jobs table: eu usage is visible everywhere, but eu job definitions are only in eu-region system tables, so the name lookup must run there.
X: B=Missing grants: a permission problem would block the whole table rather than return costs for one region and no names; the grant on system tables also covers the entire table.
C=Serverless exclusion: serverless jobs are recorded in the jobs tables, and the cost rows of serverless jobs carry the same job ID as other jobs.
D=INNER JOIN: an INNER JOIN would remove the eu rows whose names are missing, which loses the costs the analyst can currently see.
T: Billing usage is account-global but the lakeflow system tables are regional; enrich names in the region that owns the jobs.
V: system.billing.usage, system.lakeflow.jobs

@ DBX-DEP D4 T4.1 advanced use-case
S: A nightly job on classic job compute with one driver and eight workers has become slow. The team suspects the driver (large collects) rather than the workers, and the cluster is already terminated when the issue is reported. Which system-table source lets them compare driver and worker pressure for the last run?
A: `system.compute.node_timeline`, with minute-level CPU, memory and network metrics per node and a driver flag
B: `system.billing.usage`, whose `node_type` field reports the instance type of the driver and each worker for every hour of the run
C: `system.lakeflow.job_run_timeline`, which stores the peak memory and CPU of the driver for each run next to the result state
D: `system.query.history`, which records resource metrics for every Spark task that classic job compute runs, including the node it ran on and its memory use
K: A
G: ## Utilization lives in the compute schema
`system.compute.node_timeline` records one row per node per minute for all-purpose and jobs compute (and Lakeflow pipeline compute). Useful columns are `cluster_id`, `instance_id`, a `driver` boolean, `cpu_user_percent`, `cpu_wait_percent`, `mem_used_percent`, `mem_swap_percent`, network bytes and disk free space. Because the data is kept after the cluster is terminated, it supports after-the-fact right-sizing.
## Comparing driver and workers
Filter on the `cluster_id` of the run and the minute range, then aggregate per `driver` value: a driver with high memory use and swap while workers are idle points to collects or driver-side Python, whereas busy workers with an idle driver point to shuffle or data volume.
## Why the other tables do not help
`billing.usage` shows cost and `node_type`, which does not distinguish driver from worker. `job_run_timeline` has states and durations, not utilization. `query.history` covers SQL warehouses, serverless compute and pipelines, not Spark tasks of classic jobs.
W: node_timeline: minute-level utilization per node with a driver flag survives cluster termination, so driver and worker memory and CPU can be compared for the exact run window.
X: B=billing.usage node_type: this is a cost record whose node type does not tell driver from worker and has no utilization values at all.
C=job_run_timeline: it keeps one row per run slice with states and termination codes; it has no CPU or memory columns.
D=query.history: it captures queries of SQL warehouses, serverless compute and pipelines; it does not log Spark tasks of a classic jobs cluster.
T: Use system.compute.node_timeline for after-the-fact driver versus worker utilization.
V: system.compute.node_timeline

@ DBX-DEP D4 T4.1 advanced tradeoff
S: Before dropping a legacy table, a steward queries `system.access.table_lineage` for the last year and finds no reader other than the nightly pipeline that writes it. A colleague proposes dropping the table immediately since no consumer was recorded. What is the most accurate guidance?
A: Drop it, because lineage records every read and write of a Unity Catalog table, so an empty reader list proves that there is no consumer
B: Drop it only after querying `system.lakeflow.jobs`, since lineage is generated from job definitions and the jobs table lists every reader
C: Do not rely on it alone, because the tables hold only events whose lineage could be inferred; confirm with a staged deprecation
D: Wait for the retention window to roll over, because lineage tables keep a rolling window and older entries would then appear again in the table
K: C
G: ## What the lineage tables guarantee
`system.access.table_lineage` and `column_lineage` hold a record for each read or write event on a Unity Catalog table or path, from job runs, notebooks, dashboards and queries. The documentation states that they represent a subset of all read/write events: records are only emitted when lineage can be inferred, and the general lineage limitations also apply.
## Consequence
Absence of a row is evidence, not proof. Readers using unsupported paths, access outside Unity Catalog or events older than the rolling window can be missing. Safe decommissioning combines lineage with a visible deprecation period (for example revoking access or renaming the table first and waiting), and the usage signals available to the team, such as query history or audit events (the audit log table is in Public Preview).
W: Lineage is a subset: the tables record only events whose lineage could be inferred, so no recorded reader is not a guarantee and a staged deprecation covers the gap.
X: A=Complete record: the docs state that lineage tables are a subset of read and write events, so an empty result cannot prove that nothing reads the table.
B=Jobs table: system.lakeflow.jobs stores job definitions and settings; it neither generates lineage nor lists tables that jobs read.
D=Waiting for the window: events that left the rolling window do not return later, so waiting makes the history shorter instead of more complete.
T: Lineage system tables are a subset of access events; treat an empty result as evidence and decommission in stages.
V: system.access.table_lineage

@ DBX-DEP D4 T4.1 advanced use-case
S: Platform administrators want each regional team lead to query `system.billing.usage` for the lead's own workspaces only. By default only users who are both account admin and metastore admin can read system tables, and the tables are read-only. Which design gives the leads the narrower view?
A: Grant `SELECT` on `system.billing` to the leads and attach a row filter to `usage` that checks the workspace IDs of each lead
B: Make every team lead a metastore admin, because metastore admins automatically see only the system rows of their own workspaces
C: Create a view in a governed schema that filters `usage` by workspace and group membership, and grant `SELECT` on the view only
D: Copy `system.billing.usage` into each team's catalog once a month with a different filter, and grant read access on those copies
K: C
G: ## Sharing system tables safely
System tables are owned by Databricks, governed by Unity Catalog and read-only. Granting access means `USE CATALOG` on `system`, `USE SCHEMA` on the schema and `SELECT` on it, and that gives the reader every row from all workspaces of the account (for tables in the account's region or global). The docs recommend a dynamic view for sharing a subset with a user or group.
## Dynamic view
A view in a normal catalog can use `is_account_group_member()` and a mapping of workspace IDs to groups to return only the allowed rows. Readers get `SELECT` on the view; the view owner needs access to the system table. Because system tables cannot be modified, a row filter or column mask cannot be attached to them directly.
W: View with group-based filter: the view returns only the rows each team may see and the leads never receive access to the underlying system table.
X: A=Grant plus row filter: system tables are read-only and cannot be altered, so a row filter cannot be attached, and the grant alone would expose the whole account.
B=Metastore admin role: this role gives broad rights over the metastore and does not restrict system-table rows to the leads' own workspaces.
D=Monthly copies: copies go stale within a month, multiply the data and require a separate pipeline per team, while a view is always current.
T: Share a slice of a system table through a dynamic view, never by granting the table itself.
V: system.billing.usage, Unity Catalog

@ DBX-DEP D4 T4.2 advanced troubleshooting
S: A monitoring script runs `databricks jobs list-runs --completed-only --expand-tasks` every night and counts failed runs. After the number of runs per day grew, the counts stopped matching the Jobs UI, and the missing runs are always the oldest ones in the window. What is the likely cause and fix?
A: The command returns one page of results, so the script must follow `next_page_token` with `--page-token` and bound the window
B: Completed runs older than a day are removed from the API, so the script must read the older ones from the system tables only
C: The `--expand-tasks` option caps the response to the newest runs only, so the script should drop it and count job-level states instead
D: List calls return runs in ascending order by start time, so the script should reverse the output to see the newest runs first
K: A
G: ## Paged list APIs
The Jobs API and the CLI commands built on it return runs in pages, newest first (descending start time). A response contains `next_page_token` when more results exist; the next call passes it as `--page-token` (REST `page_token`). A script that reads only the first response sees the newest runs and silently loses the rest, which is why the oldest runs of the window are the ones missing.
## Making the script robust
- Loop until no `next_page_token` is returned.
- Bound the query with `--start-time-from` and `--start-time-to` (epoch milliseconds) so each night reads a defined window.
- Use `--completed-only` or `--active-only` to cut the volume, and `--expand-tasks` only if you need task details.
SDK clients wrap the same API as iterators that fetch pages for you, which is easier than hand-written loops.
W: Follow the page token: the list call returns a page at a time, newest first, so a script that never requests the next page drops the oldest runs of the window.
X: B=API removal after a day: run history is kept for about two months in the Jobs UI and API, so a one-day-old run is still returned.
C=expand-tasks cap: this option only adds task and cluster details to each run; it does not change how many runs are returned.
D=Ascending order: the documented order is descending by start time, so the newest are first and the missing ones are at the end.
T: Always follow next_page_token (and bound the time window) when counting runs through the Jobs API or CLI.
V: Jobs API, Databricks CLI

@ DBX-DEP D4 T4.2 advanced troubleshooting
S: A job has three notebook tasks. The last task exits with `dbutils.notebook.exit(json_result)`. An engineer calls `databricks jobs get-run-output` with the job run ID returned by `run-now` and gets no usable notebook result. How should the result of the last task be retrieved?
A: Call `get-run` for the job run, read the `run_id` of the task in `tasks`, and pass that task run ID to `get-run-output`
B: Call `get-run-output` with the job ID instead, because outputs are stored per job and the newest value is returned
C: Run `list-runs --expand-tasks`, whose result already contains the exit value of each notebook task as a field
D: Repeat the call every minute until the job finishes, because the output is available only once the whole run has terminated
K: A
G: ## Runs and task runs
A multi-task job run has its own `run_id`, and every task in it has another `run_id`. `get-run-output` returns the output and metadata of a single task run, including the value passed to `dbutils.notebook.exit()`. The run ID of a job run with several tasks is therefore not the identifier to use.
## The sequence
- `databricks jobs get-run <job_run_id>` returns the run with its `tasks` array (paged when it is long); each element has a task `run_id` and `task_key`.
- `databricks jobs get-run-output <task_run_id>` returns the notebook result, an error message and trace for a failed task, or logs.
The notebook output is limited to the first part of the value; larger results should be written to cloud storage and only the path returned. Run history is kept for a limited time, so results needed later must be saved by the caller.
W: Task run ID from get-run: the task has its own run_id in the tasks array, and get-run-output is defined for a single task run.
X: B=Job ID: the output belongs to a run, not to a job definition, and the API does not return a latest value by job.
C=list-runs expansion: expand-tasks adds task and cluster details, not the notebook exit value, which is only returned by the run output call.
D=Polling until termination: a finished task run returns its output while other tasks are still running, so waiting for the whole run is not required.
T: get-run-output takes the run ID of a task, found in the tasks array returned by get-run.
V: Jobs API, Databricks CLI

@ DBX-DEP D4 T4.2 advanced troubleshooting
S: A Python service pages through pipeline events with the REST endpoint `GET /api/2.0/pipelines/{id}/events`. The first call sends `filter=level='ERROR'` and `max_results=100`. For the following pages it sends `filter`, `max_results` and the returned `page_token` again, and every second call fails with an error. What is the correct way to page?
A: Send only `page_token` for later pages, with at most `max_results`, because the token already encodes the filter and other query fields
B: Send the filter on every page but remove `max_results`, because the token and the page size cannot be combined
C: Reduce `max_results` to a smaller value, because the endpoint rejects tokens when the page is larger than the number of matching events
D: Send `order_by` instead of the token, because the events are paged by their timestamp and the token is only a fallback
K: A
G: ## Event retrieval through the Pipelines API
`list-pipeline-events` (CLI: `databricks pipelines list-pipeline-events <pipeline_id>`) returns events from a pipeline's event log. Options are `filter` (SQL-like: `level='ERROR'`, `level in ('INFO','WARN')`, `timestamp > '...'`, combinable with AND), `order_by` (by timestamp, newest first by default), `max_results` and `page_token`.
## Paging rule
`page_token` is mutually exclusive with every other request field except `max_results`; the API returns an error if the token is combined with a filter or order. The first call defines the query, and later calls pass only the token (and optionally the page size).
This endpoint is the choice for an external service that has no SQL warehouse access, whereas analysis across many updates is easier by querying the event log table with SQL.
W: Token plus page size only: the token already carries the original filter and order, and the API rejects any other field together with it.
X: B=Filter without page size: the filter cannot be sent with the token at all, and max_results is the only field that may be combined with it.
C=Smaller page size: the error comes from the extra fields, not from the page size, which may be changed between calls.
D=Order instead of token: order_by only sets the sort order of one query; it does not continue a previous result.
T: Pass only page_token (and max_results) when continuing a list-pipeline-events call.
V: Pipelines API, Databricks CLI

@ DBX-DEP D4 T4.2 advanced use-case
S: A notebook collects the status of 300 pipelines. To go faster, the code calls the Databricks SDK from a `mapInPandas` function: `WorkspaceClient()` is created inside the function and fetches one pipeline per row. On the cluster the calls fail with authentication errors, but the same code works when it runs on the driver. What is the correct design?
A: Install a newer SDK on the workers, because notebook authentication works on every executor once versions match
B: Switch to a personal access token of the engineer in the notebook, because that is the only type that executors can use
C: Create the client on the driver (a thread pool suffices) or pass explicit credentials such as OAuth M2M of a service principal
D: Use `dbutils.notebook.run` for every pipeline, because each child notebook receives its own authentication on the executors
K: C
G: ## Where default authentication works
`WorkspaceClient()` uses the unified authentication standard. In a notebook it falls back to default notebook authentication, a temporary token generated for the notebook session. The documentation states that this works only on the driver node, not on workers or executors, and not with Databricks Container Services or configuration profiles.
## Design consequences
Monitoring calls are small and I/O bound, so Spark parallelism is not needed: collect the IDs on the driver and call the API there, using a thread pool if latency matters. If code must run on executors, or outside Databricks, pass explicit credentials, preferably OAuth machine-to-machine of a service principal, with the secret read from a secret scope (the worker needs access to the value). The SDK for Python is documented as Beta, and pinning its version is recommended.
W: Driver-side client or explicit credentials: notebook authentication exists only on the driver, so parallel calls either run there or carry their own service-principal credentials.
X: A=Newer SDK on workers: the limitation is that notebook authentication is driver-only, not a version mismatch, so upgrading libraries changes nothing.
B=Personal token: a user token shares one person's identity, expires with the person and is not the only type usable on executors; OAuth M2M works too.
D=Child notebooks: each child run is still a notebook on the driver side of its own cluster; this adds cost and does not give executors credentials.
T: Default notebook authentication works on the driver only; use driver-side calls or service-principal credentials on executors.

@ DBX-DEP D4 T4.2 advanced use-case
S: A job run shows Succeeded in the CLI output of `databricks jobs get-run`, but the on-call engineer suspects that tasks of this run had been repaired after a first failure and wants to see which repairs happened and when. Which call returns this information?
A: `databricks jobs get-run <run_id> --include-history`, which adds the repair history to the run object
B: `databricks jobs list-runs --run-type WORKFLOW_RUN`, which lists every repair as an extra run of the same job
C: `databricks jobs get-run-output <run_id>`, whose result contains the repair attempts of the whole job run
D: `databricks jobs get-run <run_id> --include-resolved-values`, which adds the resolved parameter and task values of each repair that ran
K: A
G: ## Retries and repairs are different records
- A **retry** (task retry policy) creates a new attempt of the task inside the same run; `attempt_number` starts at 0 and attempts after the first carry `original_attempt_run_id`.
- A **repair** reruns failed tasks (and their dependents) of a finished run. The run keeps its ID and gains an entry in `repair_history`, with the start time, state and the tasks repaired.
## API access
`get-run` returns the run with `repair_history` only if asked: the CLI flag is `--include-history` (REST `include_history`). Large arrays such as `tasks` and `repair_history` are paged, so follow `next_page_token`. `--include-resolved-values` returns parameter values that were resolved at run time; it is unrelated to repairs.
W: --include-history on get-run: the run object then contains repair_history with each repair of the run, which is what the engineer needs.
X: B=WORKFLOW_RUN list: run types such as JOB_RUN, SUBMIT_RUN and WORKFLOW_RUN distinguish how a run was created; a repair is not a separate run in the list.

K: C
G: ## Runs tab: graph and list
The Runs tab of Jobs & Pipelines lists recent runs of jobs and pipelines of the workspace, including runs started by external tools. It has a **Finished runs count graph** of recently finished runs, by default failed, skipped and succeeded, and a **Top 5 error types** table that shows the most frequent errors in the selected range. Filters at the top (name, type, run as, time range, status, run ID, error code) apply to the graph and the list.
## When the graph is visible
- It appears only when the type filter is **Jobs** or **Pipelines**; with **All** it is not shown.
- It is shown for admins for all runs; non-admins must set **Run as** to themselves to see their own runs in it.
- Dragging over the graph selects a time range and updates the list.
The list itself keeps run history for a limited time (60 days), and a run's results should be exported if they are needed longer.
W: Type and run-as filters: the graph needs the Jobs or Pipelines filter and, for non-admins, the Run as filter set to the user, so the engineer must set both.
X: A=One-hour window: the graph covers a longer recent period and can be zoomed by selecting a range.
B=Jobs filter blocks it: the graph is shown for Jobs or Pipelines filters and hidden for All, which is the opposite of this option.
D=Admin-only feature: non-admins can see the graph for their own runs once they filter on Run as themselves.
T: The Finished runs count graph appears only when filtered to Jobs or Pipelines (non-admins also filter Run as to themselves).

S: A multi-task job that used to finish in 40 minutes now takes 70, although every task succeeds. The engineer needs to see which tasks take the time, which ones overlap in parallel branches, and where a task waited for its dependencies. Which view of the job run details shows this best?
A: The Timeline view of the run, which shows when each task ran and for how long, with dependencies and overlap
B: The Graph view, because the colors of the task nodes show the duration of each task and the waiting time between them
C: The Finished runs count graph, because the height of each bar is the duration of the task that ran last
D: The Top 5 error types table, because slow tasks appear there as soft errors with the time they exceeded
K: A
G: ## Views of a job run
The Job run details page has Graph, Timeline and List views.
- **Graph**: the DAG with each task's status; clicking a node opens its details (run as, start and end times, cluster, source code, metrics).
- **Timeline**: tasks along a time axis, intended to find tasks that take long and to understand dependencies and overlap when debugging or optimizing. For serverless jobs the queries of a task and their profiles are integrated, and tasks with performance insights show a lightbulb.
- **List**: status, name, type, resource, duration and dependencies, with search, filters and sorting by duration.
Across runs, the matrix view of the job's Runs tab compares total duration and per-task bars, and an expected completion time adds a warning when the run exceeds it.
## Choosing
A regression within a run (which branch is critical, where waiting occurs) is a Timeline question; a regression across runs is a matrix question; counts of failures and top errors belong to the Runs tab graph.
W: Timeline view: tasks are placed on a time axis, so the critical path, parallel overlap and waiting for dependencies can be read at a glance.
X: B=Graph view: node colors show status and details are one click away, but the graph does not lay tasks out in time, so overlap and waiting are not visible.
C=Finished runs count graph: it counts finished runs by status over recent hours and has no per-task durations.
D=Top 5 error types: it ranks error codes of failed runs, and a slow successful task produces no error entry.
T: Use the run's Timeline view to locate slow tasks, overlap and dependency waits.
