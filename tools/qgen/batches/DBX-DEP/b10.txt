@ DBX-DEP D7 T7.2 advanced troubleshooting
S: An engineer is the owner of the Unity Catalog catalog `lab`. A colleague created the table `lab.exp.runs` and holds no grant for the engineer on it. The engineer, who has no other privileges and is in no admin role, runs `SELECT * FROM lab.exp.runs` and gets a permission error. What explains this, and what is the correct fix?
A: Ownership does not inherit downward, so the owner has no `SELECT` on child tables; as owner of the catalog the engineer can grant `SELECT` on the table, or on the catalog, to themselves
B: Catalog owners receive `SELECT` only on tables that existed when they took ownership, so the engineer must transfer ownership of the catalog again to pick up the new table
C: Ownership inherits downward only to schemas, so the engineer must also become owner of the schema `lab.exp` before the engineer can read any table in it
D: The owner of a catalog implicitly holds `ALL PRIVILEGES` on every child, so the error means the table's owner explicitly executed a `DENY` against the catalog owner
K: A
G: ## Ownership versus privileges
Every Unity Catalog securable has an owner, and the owner can do everything on that object. Ownership is **not** a privilege and it **does not inherit downward**. Owning a catalog does not make you the owner of its schemas or tables.
What an owner does get is the automatic ability to **manage** all child objects, which works like `MANAGE` on each child without being listed as a grant. `MANAGE` lets you grant and revoke privileges, transfer ownership and drop objects. It does not include data privileges such as `SELECT`.
## Consequence
- The owner of `lab` can run `GRANT SELECT ON TABLE lab.exp.runs TO ...` including to themselves, because the right to grant is automatic.
- Until someone grants it, the owner has no `SELECT` on the child table, so reads fail.
- Granting `SELECT` on the catalog or schema instead gives the principal read access to current and future tables through privilege inheritance.
`ALL PRIVILEGES` is not the same thing either: it does not include `MANAGE`.
W: Ownership does not inherit: the catalog owner can manage children, which includes granting privileges, but holds no automatic `SELECT` on the table. A self-grant of `SELECT` on the table, schema or catalog fixes the error.
X: B=Re-transfer of ownership: privileges are not tied to a snapshot of existing tables, and transferring ownership again would not add data access to child tables.
C=Schema ownership required: ownership never inherits to schemas or tables, and owning the schema would give nothing on the table either, since schema ownership is not data access to child tables.
D=Implicit ALL PRIVILEGES on children: owners are not given `ALL PRIVILEGES` on child objects, and the table owner does not need to issue a `DENY` to cause this error. The simple cause is the missing grant.
T: Owners can manage and grant on child objects but get no data privilege on them until a grant, including a self-grant, exists.
V: Unity Catalog

@ DBX-DEP D7 T7.2 applied use-case
S: A security auditing group must be able to see grants, row filters, column masks, ABAC policies and view definitions on every object in the metastore, including catalogs created next year, without being able to read or change data. The team wants a single grant and no per-catalog maintenance. Which grant fits?
A: Grant `BROWSE` on the metastore, since `BROWSE` shows names, descriptions, tags and the full security configuration of every object in the metastore
B: Grant `READ METADATA` on the metastore, which is the one metastore-level privilege that inherits to all objects and needs no usage privileges
C: Grant `USE CATALOG` and `USE SCHEMA` on the metastore, since usage privileges granted there inherit to all current and future catalogs and schemas
D: Grant `SELECT` on each existing catalog and add a new grant whenever a catalog is created, because metastore-level grants never apply to child objects
K: B
G: ## Which privileges inherit
Privileges granted on a catalog or schema apply to all current and future children. **Privileges granted on the metastore do not inherit** to catalogs, schemas or tables: they control metastore-scoped operations such as `CREATE CATALOG` or `CREATE EXTERNAL LOCATION`.
`READ METADATA` is the documented exception. Granted on the metastore, it inherits to every object, and no `USE CATALOG` or `USE SCHEMA` is required to exercise it.
## What it shows
`READ METADATA` gives read-only visibility into the same metadata an owner or a user with `MANAGE` sees: privilege grants, row filters and column masks, ABAC policies, view and function definitions. It exposes no table data. Databricks recommends it for security auditors and SREs and only for trusted principals.
`BROWSE` is a lighter privilege for discovery (name, description, tags). For data objects it can be granted only at catalog level.
W: READ METADATA on the metastore: a single grant that inherits to all current and future objects, gives the security metadata auditors need, requires no usage privileges, and grants no access to data.
X: A=BROWSE: it is limited to discovery metadata, and for tables, views, volumes and functions it can be granted at catalog level only, not on the metastore. It also does not reveal grants, masks or policies.
C=Usage privileges on the metastore: ordinary metastore-level grants do not inherit to child objects, and usage privileges only open the path to children without showing their security metadata.
D=Per-catalog SELECT: it grants data access, which the requirement forbids, and it creates the maintenance the team wants to avoid. The claim that nothing at metastore level can inherit is wrong because READ METADATA does.
T: Only `READ METADATA` inherits when granted on the metastore; other metastore privileges are scoped to the metastore itself.
V: Unity Catalog

@ DBX-DEP D8 T8.1 advanced troubleshooting
S: A nightly job on a classic cluster takes three times longer than expected. In the Spark UI the jobs timeline shows many gaps of several minutes with no Spark job running. The cluster Metrics view shows one machine, the driver, in red and all workers in blue. The code launches 40 concurrent Structured Streaming queries from threads and loops in plain Python between them. What is the best next step?
A: Add more workers to the cluster, because idle workers in the timeline mean the cluster has too little parallelism for the stages
B: Increase `spark.sql.shuffle.partitions` so each stage creates more tasks, because the gaps are the time between oversized shuffle stages
C: Reduce the concurrent queries, move them to separate compute or choose a larger driver node type, and rewrite the Python loops with Spark
D: Enable autoscaling on the workers, because the red driver tile is Spark reporting that the executors need to scale out
K: C
G: ## What a gap in the jobs timeline means
A gap is a period in which no Spark job runs. Workers are idle but the cluster is still billed. The common causes are no work on an all-purpose cluster, a very complex plan, non-Spark code, an **overloaded driver**, or a malfunctioning cluster.
## Telling them apart
- Open the Metrics view and the server load distribution. A red driver tile with blue workers means the driver is the bottleneck.
- An overloaded driver cannot schedule tasks fast enough. Typical causes: too many concurrent streams, queries or threaded Spark jobs; Python code that runs on the driver; many attached notebooks.
## Fixes
- Run fewer concurrent operations or spread them over several clusters.
- Choose a larger driver node type (the docs suggest starting by doubling it).
- Rewrite non-Spark code to use Spark, or move it to serverless compute where idle time is not billed.
More workers do not help, because the workers are already waiting for the driver.
W: Reduce driver load: the red driver with idle workers shows the driver is the bottleneck, so cut concurrency or spread it over compute, enlarge the driver and move the Python loops into Spark.
X: A=More workers: the workers are idle already, so extra executors only add cost while the driver still cannot hand out tasks.
B=More shuffle partitions: the gaps are periods without any Spark job, not long shuffle stages, and more tasks create more work for the already busy driver.
D=Autoscaling: a red driver tile reflects driver load, not a request for executors, and autoscaling adds workers, which the driver cannot keep busy.
T: Gaps in the timeline with a red driver and blue workers point to an overloaded driver, which more workers cannot fix.
V: Spark UI

@ DBX-DEP D8 T8.1 applied troubleshooting
S: A batch job on an autoscaling classic cluster finishes successfully but slower than usual. The Spark UI shows executors being removed several times during the run, and a colleague suspects out-of-memory crashes. What is the right first diagnostic step?
A: Read the compute Event log for resize or lost-instance events: autoscaling removals are expected, spot reclaims show up there, and only unexplained ones point to memory
B: Open the Streaming tab of the Spark UI, which lists every removed executor together with the exception that caused the removal and the batch it was serving
C: Query `system.lakeflow.job_run_timeline`, which stores one row per executor removal with the termination code of the executor and the node that hosted it
D: Increase the driver node type first, because executors are removed whenever the driver heap fills with task metadata, and then rerun the job to compare
K: A
G: ## Why executors disappear
When the jobs timeline shows removed executors, there are three usual explanations:
- **Autoscaling** scaling the cluster down. This is expected, not an error.
- **Spot instance losses**, where the cloud provider reclaims VMs.
- **Executors running out of memory**, which needs a deeper memory analysis.
## Order of checks
1. Open the compute **Event log** and look for events that explain the loss: resizing events or lost spot instances.
2. If the log has no explanation, open the Spark UI Executors tab and read the logs of the failed executors.
3. If the cause points to memory, continue with the Spark memory guidance.
Spark reruns the unfinished tasks of a removed executor, which explains a slower but successful run.
W: Event log first: it records compute lifecycle events such as resizes and instance losses, so it separates expected removals from real failures before any memory tuning.
X: B=Streaming tab: it exists only when a streaming job runs on the compute and shows batch and input information, not a record of executor removals for a batch job.
C=Job run timeline system table: it records job and run level periods, states and termination codes, not individual executors.
D=Larger driver: the driver does not remove executors because its heap fills with metadata, and the guide does not treat that as a cause. Check the explanations in the event log first.
T: Check the compute Event log first, because autoscaling and spot reclaims explain removed executors without any fault.

@ DBX-DEP D8 T8.1 applied tradeoff
S: Job clusters are terminated after each run. After a failure at night the on-call engineer needs the driver and worker logs, but the cluster is gone and the compute's Event log tab holds only lifecycle events. The platform team asks how to make Spark logs available for later analysis. Which approach fits?
A: Query `system.compute.node_timeline`, which stores the log4j and stdout text of each node at minute granularity for later searches
B: Download the compute Event log as CSV after each failure, because it includes the driver stack trace and the executor stderr output
C: Configure a log delivery location for the compute, so driver and worker logs are delivered to storage that outlives the cluster
D: Give the engineers access to the Executors tab of the Spark UI, because it keeps the worker log files of terminated clusters indefinitely
K: C
G: ## Three kinds of compute logging
Databricks provides:
- **Compute event logs**: lifecycle events such as creation, termination and configuration edits. They are kept for 60 days, and a download is capped at 10,000 rows. They are not Spark logs.
- **Driver and worker logs**: stdout, stderr and log4j output used for debugging. Driver logs are in the Driver logs tab; worker logs are reached through the Spark UI.
- **Init-script logs**, for debugging init scripts.
## Keeping logs beyond the cluster
Interactive access exists only while the compute is reachable. For post-mortems on terminated job clusters, configure a **log delivery location** for the compute: both the driver and worker logs are delivered there.
Access also depends on the access mode. With Standard access mode only workspace admins can open driver logs and executor logs are not available; with Dedicated mode the dedicated user or group and admins can.
W: Log delivery: it ships driver and worker logs to a location you choose, so they remain available after the job cluster terminates.
X: A=Node timeline: this system table stores utilization metrics such as CPU and memory per minute and node, not log text.
B=Event log CSV: the event log contains lifecycle events with details in JSON, not stack traces or executor stderr output.
D=Executors tab: the Spark UI is tied to the running application and compute, and it is not a retention mechanism for worker log files of terminated clusters.
T: Configure compute log delivery when driver and worker logs must outlive a terminated job cluster.

@ DBX-DEP D8 T8.1 advanced use-case
S: A platform engineer wants to list jobs whose runs were repaired, with the number of repairs per run, using `system.lakeflow.job_run_timeline`. Runs longer than one hour are stored as several hourly rows. Which query logic counts repairs correctly?
A: Count all rows per `run_id` and subtract one, because every repair adds one hourly slice row to the table
B: Count rows where `termination_code` is not `SUCCESS`, because every repair attempt is preceded by a failed row for that run
C: Group by `job_id` and count distinct `run_id` values, because a repair creates a new run identifier for the same job
D: Count rows with a non-null `result_state` per `run_id` and subtract one, as only the last row of each attempt has a result
K: D
G: ## Slices and results
`system.lakeflow.job_run_timeline` records the active period of a run in slices of up to one hour. A long run therefore produces several rows with the same `run_id`.
The columns `result_state` and `termination_code` are filled **only in the row that ends the run**. A repair run continues the same `run_id` and ends with its own row carrying a result.
## Counting repairs
```
SELECT workspace_id, job_id, run_id, COUNT(*) - 1 AS retries_count
FROM system.lakeflow.job_run_timeline
WHERE result_state IS NOT NULL
GROUP BY ALL HAVING retries_count > 0
```
Each attempt (the original run and every repair) contributes one end row, so the number of end rows minus one is the number of repairs. Counting every row would count time slices, not attempts.
W: Non-null result rows minus one: each attempt closes with exactly one row that has a result state, so the count of those rows less the original attempt equals the repairs.
X: A=All rows minus one: the number of rows reflects how many hourly slices a run produced, so long runs without any repair would appear as repaired.
B=Non-success termination codes: the termination code is set only on end rows, a repaired run can fail repeatedly or end in other states, and the successful final attempt would not be counted.
C=Distinct run ids: repairs keep the same run id, so a distinct count cannot see them.
T: Count end-of-attempt rows (non-null `result_state`) per `run_id` in `job_run_timeline` and subtract one to get repairs.

S: Analysts report that scheduled runs of a job were "skipped overnight". In `system.lakeflow.job_run_timeline` the affected runs appear with `period_start_time` equal to `period_end_time`, and no compute is listed. Which column should the engineer inspect to find out why the runs did not start?
A: `result_state`, because a run that never started has a state that names the missing cluster or the quota that was exceeded
B: `termination_code`, because a row with equal start and end time shows a run that never began and the code explains why
C: `compute_ids`, because an empty array proves that the cluster failed to start and lists the failed node types
D: `trigger_type`, because the trigger of a skipped run records the reason the scheduler declined to start it

The timeline tables describe the **active** time of a run. If a run never began execution, it is stored as a row whose `period_start_time` equals `period_end_time`, which means no runtime. The explanation is in the **`termination_code`** column.
## Typical codes
Values such as `MAX_CONCURRENT_RUNS_EXCEEDED` (concurrency limit hit while queueing was off), `CLUSTER_ERROR` or `CLOUD_FAILURE` separate configuration problems from capacity and cloud problems. W: Termination code: it is the documented place to look for the reason a run did not begin, and the equal start and end times are the signal that it never ran.
X: A=Result state: it holds the outcome of the run, but the reason a run did not begin is in the termination code, not in a state that names missing quota.
C=Compute ids: an empty array shows only that no compute is recorded, and it does not list node types or the reason.
D=Trigger type: it shows how a run was triggered, such as a schedule, and does not carry a reason for not starting.
T: A zero-duration row in `job_run_timeline` means the run never began, and `termination_code` tells why.

@ DBX-DEP D8 T8.1 advanced troubleshooting
S: A job task runs a SQL statement on a shared SQL warehouse and its duration has doubled. In `system.query.history`, filtered through `query_source` to that job run, the statement shows `execution_duration_ms` about the same as before but `waiting_at_capacity_duration_ms` of several minutes. What is the conclusion and the remedy?
A: The statement is queued for compute capacity, so add warehouse capacity (size or clusters) or reduce competing load rather than tune the SQL
B: The statement is executing slowly because of data skew, so rewrite the join with a salted key and rebuild the table with Liquid Clustering
C: The statement is waiting for the warehouse cluster to start up, so keep the warehouse running permanently and the wait will go away completely
D: The statement is blocked by lock contention in the Delta transaction log, so serialize all writers of the table in one single job at night
K: A
G: ## Where the time goes
`system.query.history` has one row per statement run on SQL warehouses, serverless compute for notebooks and jobs, and pipelines. Besides the statement text it splits the wall-clock time:
- `waiting_for_compute_duration_ms`: waiting for compute to be provisioned.
- `waiting_at_capacity_duration_ms`: waiting in a **queue for available capacity**.
- `compilation_duration_ms`: planning and optimization.
- `execution_duration_ms`: actually executing.
Other columns give `execution_status`, `error_message`, scanned and pruned bytes, spill and shuffle volume.
## Linking to a job
`query_source` holds the identifiers of the entities involved, for example `job_info.job_id`, `job_info.job_run_id` and `job_info.job_task_run_id`, plus notebook, dashboard or alert ids.
## Reading this case
Execution time did not change; queue time did. The warehouse is saturated by concurrent statements, so the remedy is capacity or workload separation. Changing the SQL would not remove queue time. For a slow execution phase, open the query profile via the `statement_id`.
W: Queue time, not execution time: `waiting_at_capacity_duration_ms` shows the statement waited for capacity on a busy warehouse, so capacity or workload isolation is the fix.
X: B=Skew and clustering: skew would raise `execution_duration_ms`, which is unchanged in this case, so rewriting the join targets the wrong phase.
C=Cluster start: waiting for provisioning is recorded in a different column, `waiting_for_compute_duration_ms`, and the case shows queueing at capacity instead.
D=Transaction log contention: it is not what this column measures, and serializing writers would not reduce time spent waiting for warehouse capacity.
T: Compare the duration columns in `system.query.history` first, because queue time at capacity calls for compute changes, not SQL tuning.

@ DBX-DEP D8 T8.1 applied troubleshooting
S: A dashboard query joins `orders` to `order_events` and returns millions of rows while the finance team expected about 200,000 (one row per order). In the query profile, the Join operator shows few input rows on each side but a very large number of output rows, and the aggregated runtime is dominated by that operator. What does this pattern indicate, and what is the fix?
A: An exploding join: the key is not unique on a side, so rows multiply; correct the join keys or deduplicate or aggregate that side first
B: A full table scan: the scan operators read every file of both tables, so adding a filter on the partition column would shrink the join output
C: A shuffle problem: data is redistributed between executors, so raising the shuffle partition count would reduce the join output
D: A query cache hit: the result was served from the query cache, so a trivial change to the query would reduce the number of rows returned
K: A
G: ## Reading the query profile
The query profile shows each operator with metrics such as time spent, rows and peak memory. The **Top operators** panel lists the most expensive ones, which helps to find where to start. Common operators are Scan, Join, Union, Shuffle, Hash/Sort and Filter.
The documentation names two typical mistakes the profile exposes: **exploding joins** and **full table scans**.
## Telling them apart
- Scan with a very large amount read relative to the rows kept: full scan or poor data skipping.
- Join whose **output rows far exceed the input rows**: exploding join. If the join key is not unique on one side (many-to-many), each match multiplies rows. Fix the join condition, deduplicate or pre-aggregate one side, and verify the expected cardinality.
- Shuffle: data movement between executors, expensive in time but not a cause of more rows.
A query served from the query cache has no profile at all.
W: Exploding join: output rows far above inputs mean the key repeats on both sides, so rows multiply. Correct the keys, deduplicate or aggregate first.
X: B=Full scan: a scan problem shows up as a large amount of data read in the Scan operator, and adding a filter does not change a join that multiplies rows.
C=Shuffle partitions: shuffle moves rows between executors without changing how many rows the join produces.
D=Query cache: a result served from the cache has no query profile, and the profile in this case shows a running Join operator.
T: A Join operator with far more output than input rows in the query profile signals a non-unique key and an exploding join.

@ DBX-DEP D8 T8.2 applied troubleshooting
S: A job has the tasks `ingest` → `transform` → `publish`. The run failed in `transform` because its notebook path pointed to a moved file, and `publish` shows "Upstream failed". `ingest` succeeded and uses a job cluster shared by all three tasks. The engineer edits the `transform` task to the new path and starts a repair run. What happens?
A: Only `transform` runs again with the new path, and `publish` stays in its failed state until the next scheduled run
B: All three tasks run again, because a repair after a settings change must start from the root task to stay consistent
C: `transform` and `publish` run with the updated settings on a new copy of the shared job cluster, and `ingest` is not run again
D: `transform` and `publish` run again with the path stored in the original run, because a repair restores the settings of that run
K: C
G: ## What repair does
Repair re-runs only the **unsuccessful tasks and the tasks that depend on them**. Successful tasks and their dependents-already-satisfied are not repeated, which saves time and cost.
## Settings used
- Unsuccessful tasks run with the **current** job and task settings. If you fix a notebook path or a cluster setting first, the repair uses the fixed one.
- If tasks share a job cluster, a repair creates a **new job cluster** from the current settings of the original one, named with a version suffix such as `my_job_cluster_v1`. The original run's cluster stays visible for comparison.
- The run duration shown includes time from the first start to the last repair.
## Limits
Repair works only for jobs with two or more tasks, and each repaired task starts from its beginning, so non-idempotent writes can duplicate data.

A: Give developers Can Edit on the production Git folder and ask them to pull `main` every morning, because pulls reconcile local edits with the branch
B: Give developers Can Run only, and let a CI job running as a service principal with a Git credential update the folder after each merge into the deployment branch
C: Let each developer create a personal branch inside the production Git folder, so the folder always contains the newest feature code for testing
D: Schedule a job under a developer's personal credential that hard-resets the folder to `main` once a day, so drift is corrected within 24 hours
K: B
G: ## Admin, user and merge flows
Databricks describes three flows for Git folders in CI/CD:
- **Admin flow**: a workspace admin creates top-level folders that host *production* Git folders, each cloned from a repository and a deployment branch.
- **User flow**: each developer clones into their own folder under `/Workspace/Users/<email>/`, works on a personal branch and pushes to the remote.
- **Merge flow**: after a pull request is merged, automation pulls the change into the production folder using the Repos API.
## Production Git folder rules
- It should be updated **only by automation** when PRs merge into the deployment branch.
- Create or use a **service principal** with a Git credential, so no personal token is involved.
- Permissions: **Can Run** for project users who need to run workflows and for the service principal that runs automation; optionally Can View for others. Only admins and service principals edit.
- Keep it in sync with external CI/CD (for example GitHub Actions) or, if unavailable, a scheduled job that updates the folder.
W: Run-only users and automated sync: the production folder stays an exact copy of the deployment branch, because only a service principal updates it after reviewed merges.
X: A=Can Edit with manual pulls: developers could still change code in production between pulls, and local edits would not be reviewed, which is the existing problem.
C=Branches in the production folder: development belongs in user-level folders, and switching branches in a production folder would change what jobs run.
D=Daily hard reset under a personal credential: drift would remain for up to a day, and it ties production to a personal credential instead of a service principal.
T: Production Git folders are run-only for users and updated by a service principal after PRs merge into the deployment branch.

@ DBX-DEP D8 T8.4 advanced troubleshooting
S: A job has three tasks that all point at notebooks in a workspace Git folder. A sync job pulls the folder at 02:00, and the data job runs at 01:55 for about 15 minutes, so the sync lands while the run is active. Some tasks of one run execute old code and others new code. Which change addresses the cause?
A: Configure the job to use the remote Git repository with a branch, tag or commit, so the run snapshots it and all tasks use one commit
B: Move the sync job to 01:50 so the pull always completes before the data job starts, and keep the notebooks in the Git folder
C: Give each task its own Git folder with a separate branch, so tasks cannot see each other's code changes during one run
D: Keep the Git folder and set the maximum concurrent runs of the data job to 1, so that no run of it can overlap with the sync job
K: A
G: ## Two ways for a task to get code
- **Workspace path in a Git folder**: the task runs whatever the folder contains at that moment. You must keep the folder in sync yourself, and a pull during a run changes the files under it.
- **Remote Git repository**: the job's Git settings name the repository URL, provider and one reference: a **branch, tag or commit**. When a run begins, Databricks takes a **snapshot** of that reference, so all tasks of a run use the same commit. The task run details show the commit SHA.
## Recommendation
Databricks recommends workspace Git-folder paths only for rapid iteration and testing in development. For staging and production, reference a remote Git repository. A tag or a commit gives a fixed release; a branch picks up new commits at the next run start.
If the job runs as a group (role), the role's Git credential is used for cloning, so it must be configured first.
W: Remote Git source: the run starts from one snapshot of the reference, so a later push or sync cannot give tasks of the same run different code, and the commit is recorded.
X: B=Moving the sync: it only shifts the schedule, and the timing depends on run duration, so a longer run or a delayed sync would bring back the same race.
C=Folder per task: tasks of one job would use unrelated copies of the code and each folder would need its own sync, which adds drift risk instead of a consistent version.
D=Single concurrent run: it limits overlap between runs of the same job, not between the data job and the separate sync job.
T: For production jobs, reference a remote Git repository (branch, tag or commit) so all tasks of a run use one snapshot.

@ DBX-DEP D8 T8.4 applied tradeoff
S: A team's repository holds notebooks, a job definition and a pipeline definition with different cluster sizes and schedules for staging and production. Today an admin clones the repository into a production Git folder and recreates jobs by hand after each release. Releases are slow and the two environments differ. What does Databricks recommend for this CI/CD flow?
A: Keep the production Git folder, because it also deploys the job and pipeline definitions from the repository and applies the target settings of each environment
B: Define the jobs and pipelines per target with Declarative Automation Bundles and deploy from CI; use a production Git folder for code-only deployment
C: Replace Git folders with the Workspace UI export of notebooks and import them per environment, because exports include job settings and schedules
D: Use a scheduled job in each workspace that copies the repository files to a shared folder, then compares job settings by hand
K: B
G: ## What a Git folder does and does not do
A Git folder syncs **files** (notebooks, scripts, configuration) between a repository and the workspace. It does not create or update jobs, pipelines or compute settings from definitions in the repository.
## Choosing the approach
Databricks recommends **Declarative Automation Bundles** to package and deploy CI/CD workflows: resources (jobs, pipelines, permissions, variables) are defined in source and deployed per target, so staging and production differ only through target overrides. If you only need to deploy code into the workspace, use a **production Git folder** updated by automation.
The approaches combine: define resources in source with bundles and create, deploy and manage them in workspace Git folders. Bundles formerly had the name Databricks Asset Bundles.
W: Bundles for resources: they deploy job and pipeline definitions per target from CI, removing the manual recreation, while a production Git folder remains the option for code-only deployments.
X: A=Git folder as deployer: a Git folder syncs files only, so it cannot create jobs or pipelines or apply target settings.
C=Manual export and import: exports carry notebook source, not job settings, and the process stays manual and drift-prone.
D=Copy job with manual comparison: it automates only the file copy and keeps the manual, error-prone comparison of job settings between environments.
T: Use Declarative Automation Bundles to deploy jobs and pipelines per target, and a production Git folder only for code-only deployment.
