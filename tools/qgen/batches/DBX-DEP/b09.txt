@ DBX-DEP D6 T6.2 advanced troubleshooting
S: A column mask ABAC policy on the catalog `fin` matches every column tagged `sensitivity` and calls `mask_all(v STRING) RETURNS STRING`, which returns `'REDACTED'`. Stewards then tag a `DOUBLE` column `salary` and a `DATE` column `birth_date`. Queries on those tables now fail for users the policy applies to, while masked `STRING` columns work. The team wants to keep a single policy. What is the right fix?
A: Re-create the function as a Python UDF in Unity Catalog, because the engine does not cast the return value of Python UDFs and so accepts `'REDACTED'` for any type
B: Add the affected users to the policy's `EXCEPT` clause for tables that contain numeric or date columns, so the mask function is not evaluated for them at all
C: Replace it with a `VARIANT` based function that branches on `schema_of_variant()` and returns a value castable to the column type, such as `0.0` or a fixed date
D: Mark `mask_all` as `DETERMINISTIC`, because a function that is not declared deterministic cannot be cast to the type of the column it masks
K: C
G: ## Mask output must fit the column type
A column mask function takes the column value and returns a value that Databricks casts back to the column's data type. The return type must match or be castable to the column type, in every branch of the function.
- `'REDACTED'` is castable to `STRING` but not to `DOUBLE` or `DATE`, so every query that evaluates the mask on those columns fails at runtime.
- Wide-to-narrow overflow is the same failure: a mask that adds 1000 to a `TINYINT` column returns a value the column type cannot hold.
## One policy for many types
A single mask function that accepts and returns `VARIANT` can serve columns of many types. The engine casts the column value to `VARIANT`, runs the function, and casts the result back following ANSI rules. Inside, `schema_of_variant()` lets you branch on the type (integers widen to `BIGINT`), and each branch returns something castable to the target.
```
CREATE FUNCTION flexible_mask(data VARIANT) RETURNS VARIANT
RETURN CASE WHEN schema_of_variant(data) = 'BIGINT' THEN 0::VARIANT
WHEN schema_of_variant(data) = 'DATE' THEN DATE'1970-01-01'::VARIANT
WHEN schema_of_variant(data) = 'DOUBLE' THEN 0.00::VARIANT
ELSE NULL::VARIANT END;
```
Test with `SELECT CAST(mask(col) AS <type>)` for every type the tag can reach before attaching the policy to a catalog.
W: VARIANT mask with type branches: one function and one policy cover string, numeric and date columns because every branch returns a value the column type accepts.
X: A=Python UDF: the return value is cast back to the column type whatever language the function uses, and policies recommend SQL UDFs because Python UDFs must be wrapped in a SQL UDF and cannot be inlined by the optimizer.
B=EXCEPT clause: it removes the protection for exactly the users the mask exists for, and it hides the defect instead of fixing the function.
D=DETERMINISTIC: the keyword only tells the engine the function returns the same result for the same input, which helps optimization; it has no effect on type casting.
T: A column mask must return a value castable to each column type it can reach; use a VARIANT function to cover several types with one policy.

@ DBX-DEP D6 T6.3 advanced tradeoff
S: An analytics team pseudonymizes the 10-digit `phone_number` column with `sha2(phone_number, 256)` and states in its documentation that the data is anonymized. A reviewer shows that the original numbers can be recovered by hashing every possible number and comparing. Tables from several systems must still be joinable on the pseudonym. Which change addresses the weakness?
A: Switch the digest to `sha2(phone_number, 512)`, because a longer digest cannot be reversed by hashing the candidate numbers
B: Hash the number with a secret key kept outside the data plus a version number, so output stays deterministic for joins but cannot be recomputed from guesses
C: Replace the hash with `uuid()` generated per row, since a random value cannot be recomputed from the phone number by anyone who holds the original
D: Keep the plain hash and add a column mask that shows the hash only to members of the analytics group, hiding it from everyone else
K: B
G: ## Why a bare hash is weak
Hashing is deterministic and one-way, but the input space matters. A phone number has only about ten billion possibilities, so an attacker (or an insider) can hash all of them and look up the match. This is a dictionary or rainbow-style attack, and a longer digest does not change the size of the input space.
## Keyed, versioned pseudonymization
Add a secret that the attacker does not have, such as a key read from a secret scope, and concatenate it with the value before hashing. Include a version number so the key can rotate: new data uses version 2, and the policy or function parameter controls which version a pipeline uses.
```
CREATE FUNCTION pseudonymize(val STRING, version INT) RETURNS STRING
DETERMINISTIC
RETURN SHA2(CONCAT(val, CAST(version AS STRING)), 256);
```
The Databricks pattern for consistent hashing uses a `version` parameter; the secret part should be added on top of it so the digest cannot be recomputed from candidates.
## Pseudonymized is not anonymous
Whoever holds the key can still link records to people, so this data remains personal data. Complete deletion is the safest option when re-identification risk must be eliminated.
W: Keyed, versioned hash: the same input and key give the same pseudonym in every table, so joins work, while an outsider without the key cannot confirm a guess.
X: A=Longer digest: SHA-512 has the same small input space, so trying all ten billion numbers still works; only the secret changes the outcome.
C=Random UUID per row: it cannot be recomputed, but the same number gets different values in each row and table, so the joins that the team needs stop working.
D=Mask over the hash: a mask controls who reads the stored value at query time; the weak hash is still in storage and in any copy, export or time travel version.
T: Make a pseudonym deterministic but keyed (secret plus version); a bare hash of a small input space can be reversed by enumeration.
V: Unity Catalog functions, column masks

@ DBX-DEP D6 T6.3 applied use-case
S: Analysts study the age distribution and regional sales of customers. The `customers` table has the exact `birth_date` and a full postal code. Privacy counsel wants a lower re-identification risk, and nobody in the analytics group needs exact values. Which method fits the need?
A: Replace `birth_date` and the postal code with salted hashes, because a hashed value hides the original and the analysts can still group by it
B: Suppress both columns by returning `NULL` in a mask for the analytics group, since the group does not need individual attributes
C: Tokenize both columns with random tokens held in a restricted mapping table, so that analysts can look up the original values when needed
D: Generalize the values: expose an age band computed from `birth_date` and only the first digits of the postal code, so each group has many people
K: D
G: ## Choosing the technique by the analytic need
- **Suppression** removes a value (NULL or dropped column). It is safe but destroys any analysis that needs the attribute.
- **Generalization** replaces a value by a coarser one: a date by an age band, a postal code by its first digits. The attribute still supports distributions and group-by, and many people share each value, which lowers re-identification risk.
- **Hashing and tokenization** replace a value by a stable stand-in. Each person still has a unique value, so records stay linkable, but ranges and distributions are lost and the stand-in does not reduce the uniqueness of the person.
## Where to apply it
Use a column mask (or an ABAC mask policy on the tagged columns) when the same table serves privileged and unprivileged readers. Materialize a generalized column in a curated table when no reader needs the exact value.
```
CASE WHEN age < 30 THEN '<30' WHEN age < 50 THEN '30-49' ELSE '50+' END
```
W: Generalization: age bands and short postal prefixes keep the distributions the analysts need while many customers share each value.
X: A=Salted hash: each birth date or postal code maps to a stable but meaningless value, so the analysts lose the ranges and regions they want to analyze.
B=Suppression: the requirement is to analyze age and region, and removing the columns outright makes that analysis impossible.
C=Tokenization: random tokens are reversible by design and do nothing for distributions; they suit cases where authorized users must re-identify, which nobody needs here.
T: Pick the technique by the analytic need: generalize when distributions matter, suppress when the attribute is not needed, hash or tokenize to keep linkability.

@ DBX-DEP D6 T6.3 advanced use-case
S: A product events table with billions of rows carries `email`. Support agents must occasionally re-identify a customer, analytics must join events across systems, and a right-to-erasure request must make a customer's events non-attributable without rewriting the large events table. Which design meets all three?
A: Replace the email with a random token at ingestion, keep the token-to-email mapping in a tightly restricted table, and on an erasure request delete the mapping row
B: Replace the email with `sha2(email, 256)` at ingestion, and on an erasure request delete the customer from the source system so the hash can no longer be matched
C: Keep the plain email and attach a column mask that returns `'***'` for analysts, then run `DELETE` on the events table for each erasure request
D: Replace the email with a generalized domain value such as the part after `@`, which groups customers and needs no mapping table for erasure
K: A
G: ## Tokenization as a vault
Tokenization replaces a value by a random token and keeps the mapping in a separate, tightly governed table (the vault). The events keep the token, so they join across systems; only holders of access to the vault can reverse it.
- Re-identification: authorized support looks up the token in the vault.
- Erasure: deleting the vault row severs the link. Remaining events carry a token that points to nobody, so no rewrite of the large table is needed. A small `DELETE` on the vault is cheap.
## Why a hash does not get there
A hash is recomputable by anyone who still has the email, so linking events to a person stays possible. Deleting the source record does not help if the email exists elsewhere, in backups or another system. Keyed hashes need the key destroyed to get the same effect.
Remember that the vault's history is also retained by Delta time travel: run `VACUUM` after the delete so deleted vault rows leave storage, and restrict the vault with Unity Catalog privileges.
W: Token plus restricted mapping: events stay joinable, support can re-identify through the vault, and deleting one mapping row makes the customer's events non-attributable.
X: B=Plain hash: support cannot reverse it, and anyone with the email can recompute the hash and relink the events, so deleting the source row does not sever attribution.
C=Mask plus DELETE: a mask only hides the value at query time, and per-customer deletes on billions of rows rewrite many files, which the design wanted to avoid.
D=Email domain: it is a generalization that cannot identify an individual at all, so support cannot re-identify and events cannot be joined per customer.
T: Tokenization with a governed vault supports re-identification and erasure by deleting the mapping, without rewriting the fact table.
V: Delta Lake, Unity Catalog

@ DBX-DEP D6 T6.3 advanced troubleshooting
S: A team runs `CREATE TABLE dev.crm.customers DEEP CLONE prod.crm.customers` to give developers realistic data. The prod table has column masks from ABAC policies on its PII columns, and the statement fails for regular users. The developers must not see raw PII in dev. Which approach achieves this?
A: Run the deep clone as the owner of the prod table and attach the same ABAC policies in dev, so developers see masked values in the clone
B: Add the developers to the `EXCEPT` clause of the policy so they can clone the table, then mask the columns again in the dev catalog
C: Build the dev table with a job that reads prod as an exempt principal and writes anonymized values (hashed, generalized or suppressed) into dev
D: Point a dev external table at the Delta files of the prod table, so developers read the same files through their own governed dev catalog
K: C
G: ## Masks apply at read time, not in the files
Row filters and column masks are enforced when a user queries. The stored files still contain the real values. Therefore a copy that is meant to leave the protected zone must be **materialized with anonymized values**, not copied and masked later.
- Deep and shallow clones are not supported on tables that have row filters or column masks. With ABAC, a user who is excluded from a policy can still clone, which would put raw PII into the clone.
- Path-based access to the files of a table that has policies is not supported either.
- A scheduled job running as a principal exempt from the policy can read raw values and write only the anonymized form (keyed hash, generalized bands, suppressed columns). Grant developers access to the output only.
Because the dev table is created from anonymized values, there is nothing to mask later and no raw data in its history.
W: Anonymizing job: an exempt principal reads prod and writes only de-identified values, so dev holds no raw PII in its files or history.
X: A=Clone as owner: clones are not supported on tables with column masks, and where an exempt user can clone, the copy contains the raw values that the dev policy would then have to hide.
B=Exempting developers: it gives them the right to read raw values and to clone them, the opposite of the requirement.
D=External table on prod files: path-based access to tables that have policies is not supported, and the files hold the unmasked data in any case.
T: Masks protect reads, not files: create non-production copies by materializing anonymized values with an exempt principal.

@ DBX-DEP D6 T6.4 advanced troubleshooting
S: Partners drop JSON events in cloud storage. Bronze is loaded with Auto Loader using `cloudFiles.schemaEvolutionMode = rescue`; silver selects named columns and masks `email` and `phone`. One partner starts sending a new field `national_id`. Compliance asks where the field lands and whether silver is still compliant. What is the correct assessment?
A: The stream fails with `UnknownFieldException` until restarted, after which `national_id` becomes a bronze column that silver then ignores
B: The new field is dropped silently because it is not in the schema, so no unmasked identifier is stored anywhere in the lakehouse
C: Auto Loader adds `national_id` to the schema automatically and a masking policy already covers it because policies apply to new columns
D: The stream keeps running and `national_id` sits unmasked in bronze inside `_rescued_data`, so that column needs the same protection as other identifiers
K: D
G: ## What the rescued data column holds
With `rescue` evolution Auto Loader never evolves the schema and the stream does not fail. Any column that is not in the schema, or that mismatches in type or case, is stored in `_rescued_data` as a JSON blob together with the source file path.
- A pipeline that masks named columns does not see inside the blob, so a new sensitive field passes through bronze in clear text.
- Other modes behave differently: the default `addNewColumns` stops the stream with `UnknownFieldException` and adds the column after a restart; `none` ignores new columns unless a rescued column is configured.
## What a compliant pipeline does
- Treat `_rescued_data` as potentially sensitive: restrict it to the ingestion principal, mask it or exclude it from silver.
- Add a check that alerts or fails when `_rescued_data` is non-null for fields not on an approved list, so stewards review a new field, tag it and extend masking before it spreads.
W: Rescued data blob: in rescue mode the new field lands unmasked inside `_rescued_data`, so it must be governed like any identifier and monitored for new keys.
X: A=Failure on a new column: that is the default `addNewColumns` behavior; in `rescue` mode the stream does not fail on schema changes.
B=Silent drop: the `none` mode ignores new columns, but in `rescue` mode Auto Loader records them in the rescued column, so the identifier is stored.
C=Automatic coverage: policies match tagged columns; a new field is unclassified until a steward tags it, and it is not a column in this mode.
T: In rescue mode unknown fields live in `_rescued_data`; protect and monitor that column or new PII slips through unmasked.

@ DBX-DEP D6 T6.4 advanced tradeoff
S: A pipeline masks `ssn` before writing the silver table. Compliance requires that no record with an unmasked value (a nine-digit pattern) ever reaches silver, that other records continue to flow, and that offending records are kept for investigation by a small group. Which approach meets all three?
A: Add a pattern expectation on the masked column, route offending rows to a restricted quarantine table, and feed silver only from rows that pass
B: Use the default `expect` on the pattern check, which flags violating rows in the metrics and keeps them out of the target table
C: Use `expect_or_drop` on the pattern check, because dropped rows are logged and the offending records can be read back from the event log
D: Use `expect_or_fail` on the pattern check, so the update stops and rolls back when a violating row appears, protecting silver completely
K: A
G: ## Expectation actions
- **warn** (the default `expect`): violating records are written to the target and counted in metrics. They are retained, so PII would reach silver.
- **drop** (`expect_or_drop`): violating records are removed before the write and only counted, not stored.
- **fail** (`expect_or_fail`): the update fails and rolls back atomically. Nothing bad is committed, but all processing stops until someone fixes the data or the code.
- **Quarantine pattern**: combine expectations with a temporary view that tags each row valid or invalid, then write invalid rows to a separate table and valid rows to the target. This keeps the invalid data for review without blocking the flow.
## Matching the requirements
Compliance needs a hard barrier (nothing invalid in silver), continuity (the rest keeps flowing) and retention for investigation. Only the quarantine pattern gives all three; the quarantine table itself holds raw sensitive values, so grant it only to the review group.
W: Quarantine pattern: invalid rows are diverted to a restricted table, silver reads only passing rows, and the pipeline keeps running.
X: B=Default expect: it retains violating rows in the target and only counts them, so unmasked values would reach silver.
C=expect_or_drop: the barrier works, but dropped records are only counted in metrics; their content is not stored, so there is nothing to investigate.
D=expect_or_fail: nothing invalid is committed, but one bad record halts the whole pipeline, which breaks the requirement that other records continue to flow.
T: Use the quarantine pattern when invalid PII must be kept out of the target and kept for review while the pipeline continues.

@ DBX-DEP D6 T6.4 advanced use-case
S: A catalog-level ABAC policy masks `email` for `account users`. A Lakeflow job runs as the service principal `sp_etl`, which is not exempt, and writes `silver.customers` with `email_token = sha2(email, 256)` read from bronze. After the policy was added every `email_token` in silver is identical, and joins on it collapse. How should the pipeline be fixed?
A: Remove the policy from bronze so the job sees real emails, and rely on the hashed token in silver to protect the email values everywhere in the lakehouse
B: Add `sp_etl` to the policy's `EXCEPT` clause, keep bronze restricted, compute the token in the job, and tag silver for its own policy
C: Run the job as a user in the compliance group, because their identity is already exempt from the masking policy on bronze
D: Hash the email inside the policy's masking function and have the job read the hashed value instead of the original

G: ## Masks apply to whoever reads, including pipelines
An ABAC mask is evaluated for the principal that runs the query. A job principal that is not exempt reads `'***'` (or whatever the function returns) and then computes its transformation on that constant, so a hash or join key built from it is the same for every row.
## Patterns for compliant pipelines
- Bronze holds raw values, so restrict who can read it. Exempt the pipeline's service principal in the policy's `EXCEPT` clause (or give the policy `TO` only the human groups), so the job sees real values while ordinary users stay masked.
- The job produces the protected form (keyed hash, generalization) as a stored column in silver, and silver is covered by its own tags and policies.
- Keep the exemption narrow: a named service principal, not broad groups, and audit tag and policy changes.
Running as a person's identity makes lineage and audits unreliable and breaks when the person changes team.
W: Exempt service principal: the job reads real emails from restricted bronze, derives the token itself, and silver carries its own protection.
X: A=Removing the policy: every user could then read raw emails in bronze, so the hashing in silver would protect nothing.
C=Compliance user identity: it works technically but ties a production pipeline to a person, hides who accesses PII, and fails when the person leaves.
D=Hashing inside the mask: the hashed value would be what every non-exempt reader sees, which changes the semantics of masking for analysts and ties the token to the policy function.
T: Pipelines read through masks like any user; exempt the service principal on restricted bronze and create the protected form inside the job.

@ DBX-DEP D6 T6.4 advanced troubleshooting
S: A streaming job deduplicates events with `withWatermark("event_time", "1 day").dropDuplicates(["email", "event_id"])` and writes to a Delta table that has masking. A privacy review finds raw emails in the checkpoint directory in cloud storage, outside the reach of table masks and of the erasure `DELETE`. How should the job be changed?
A: Add a column mask on the sink table, because masks also apply to the state that the stream stores in its checkpoint
B: Run `VACUUM` on the sink table after each erasure, since vacuum also removes files under the checkpoint folder
C: Reduce the watermark to one hour, which makes the raw emails leave the stream state after a shorter time
D: Replace `email` by a keyed token in a projection before `dropDuplicates`, so the state holds only tokens
K: D
G: ## Stateful operators store their keys
Operators such as `dropDuplicates`, stream-stream joins and aggregations keep state for the grouping keys in the checkpoint location. That state is written before the data reaches the sink, so anything used as a key lands in storage in clear text.
- Column masks and table-level privileges protect reads of tables, not files in a checkpoint directory.
- `DELETE` and `VACUUM` act on the Delta sink; a checkpoint is not part of a table's data files.
- A shorter watermark shrinks how long state is kept, but while it is kept the raw value is still stored.
## Design rule
Pseudonymize sensitive keys before the stateful operator (keyed hash or token from a vault) and deduplicate or join on the token. The state then holds no raw identifier, and an erasure request can be satisfied by deleting the vault mapping as well as the table rows.
W: Tokenize before the operator: the stream state contains only tokens, so the checkpoint holds no raw email.
X: A=Sink mask: masks are enforced when users query the table, not on the state files in the checkpoint.
B=VACUUM on the sink: vacuum cleans unreferenced data files of the Delta table; the checkpoint is a separate location and has no relation to the table history.
C=Shorter watermark: it limits retention time of state, but the raw email is still written to the checkpoint while the state lives, so the exposure remains.
T: Keys of stateful streaming operators are stored in the checkpoint; pseudonymize them before the operator.

@ DBX-DEP D6 T6.5 advanced troubleshooting
S: A managed table has deletion vectors enabled. For an erasure request the team ran `DELETE FROM customers WHERE id = 42` and, in the same hour, `VACUUM customers`. A later audit still finds the customer's row in the Parquet files in storage. What explains this, and what completes the erasure?
A: The delete wrote only a deletion vector, so the file still holds the row; run `REORG TABLE ... APPLY (PURGE)`, then `VACUUM` once old files pass retention
B: The `VACUUM` ran too early in the day; running it again after 24 hours removes every file that contained the deleted row, whatever the retention
C: Deletion vectors must be disabled with `ALTER TABLE ... SET TBLPROPERTIES`, which rewrites all files at once and removes the row from storage
D: Run `VACUUM customers LITE`, which reads the transaction log and deletes data files that still contain rows marked as deleted
K: A
G: ## Soft deletes need a purge
With deletion vectors enabled, `DELETE`, `UPDATE` and `MERGE` do not rewrite data files; a small metadata file marks rows as removed. Readers hide the rows, but they are still in the Parquet file. `VACUUM` only deletes files that the current table version no longer references, so it has nothing to remove for such a file.
## Physical removal sequence
1. `DELETE` the rows (logical removal).
2. `REORG TABLE customers APPLY (PURGE)`: rewrites the files so the current version no longer holds the data, and creates a new version. The old files still exist for time travel.
3. `VACUUM customers`: removes those old files, but only when they are older than the retention threshold (7 days by default). Run it with a delay after the reorg, or shorten the retention with the understanding that it reduces history.
This applies equally to materialized views and streaming tables with deletion vectors.
W: Purge then vacuum after retention: the reorg rewrites the file without the row, and a later vacuum deletes the old file once it has expired.
X: B=Waiting a day: the file with the row is still referenced by the current version, so no later vacuum removes it, and retention governs old versions, not the current file.
C=Disabling the feature: turning deletion vectors off for future writes does not rewrite existing files, so the row stays in storage until a purge.
D=VACUUM LITE: it is a Public Preview mode that skips directory listing; it still deletes only files the table no longer references, which excludes the current file.
T: With deletion vectors, erasure means DELETE, then REORG ... APPLY (PURGE), then VACUUM after the retention period.

`ALL PRIVILEGES` implies the data and object privileges that apply to the object type, and it inherits like any other privilege. It does **not** include `MANAGE` (or `READ METADATA`, `EXTERNAL USE SCHEMA`, `EXTERNAL USE LOCATION`), to avoid accidental privilege escalation.
- Granting privileges on an object requires being its owner or holding `MANAGE` on it (or on a parent: `MANAGE` on a container applies to all current and future children).
- The lead can read and write the data through `ALL PRIVILEGES`, but cannot pass access on to others.
```
GRANT MANAGE ON CATALOG prod TO `team_lead`;
```
Hand out `MANAGE` deliberately and to few principals, because a manager can also grant themselves data privileges.
W: Missing MANAGE: `ALL PRIVILEGES` leaves out `MANAGE`, so the lead needs it granted on the catalog to administer grants on the tables below.
X: B=No inheritance: privileges granted on a catalog apply to its current and future tables; the failure is about grant authority, not data access.
C=Table owner only: owners and holders of `MANAGE`, including on a parent container, can grant privileges on the table.
D=Group membership: nothing requires a grantor to belong to the grantee group.
T: ALL PRIVILEGES excludes MANAGE; to administer grants, hold ownership or MANAGE.

@ DBX-DEP D7 T7.2 applied troubleshooting
S: A new platform team received `CREATE CATALOG` and `CREATE EXTERNAL LOCATION` on the metastore and assumed they could also read the tables in existing catalogs. Queries on those tables fail with permission errors. Why?
A: They must also be made metastore admins, because privileges granted on a metastore are active only for the admins of the workspace and account
B: The grants need a workspace re-assignment, after which metastore privileges propagate to the catalogs within an hour
C: Metastore privileges inherit to catalogs but stop there, so they would also need `USE SCHEMA` on every schema to read a table
D: Metastore grants cover operations such as creating catalogs and do not inherit to data objects, so catalog or schema grants are needed
K: D
G: ## Where inheritance starts
The hierarchy is metastore, catalog, schema, then tables, views, volumes and functions. Privileges granted on a container inherit to current and future children, but **privileges granted on the metastore do not inherit** to its catalogs. They govern metastore-scoped operations such as `CREATE CATALOG`, `CREATE EXTERNAL LOCATION`, `CREATE STORAGE CREDENTIAL` or `CREATE SHARE`.
- The exception is `READ METADATA`: granted on the metastore it inherits to all objects and needs no usage privileges, giving metadata visibility, not data access.
- Reading a table requires `USE CATALOG`, `USE SCHEMA` and `SELECT` (granted on the table or inherited from the schema or catalog).
- A principal who creates a catalog becomes its owner and so has full rights there, but that does not extend to catalogs made by others.
W: Metastore grants do not inherit: creating catalogs and locations says nothing about reading existing data, which needs catalog-level or lower grants.
X: A=Admin only: metastore privileges are ordinary grants that work for non-admins; they simply cover different operations.
B=Propagation delay: there is no propagation to wait for, because the privileges never apply to data objects.
C=Inherit to catalogs only: metastore-level grants do not inherit at all, with `READ METADATA` as the one exception.
T: Metastore-level privileges do not inherit to data objects (READ METADATA aside); grant access at catalog or below.

@ DBX-DEP D7 T7.2 advanced troubleshooting
S: `prod.gold.v_revenue` is a view over `prod.silver.orders`. Analysts have `SELECT` on the view and query it on a SQL warehouse. The view was created by Dana, who has since changed teams and lost `SELECT` on `prod.silver.orders`. Analysts now get permission errors on the view. What is the proper fix?
A: Transfer ownership of the view to a group or service principal that keeps `SELECT` on the base table, so the underlying check succeeds
B: Grant the analysts `SELECT` on `prod.silver.orders` so that their own permissions are checked on the base table
C: Grant the analysts `USE CATALOG` on `prod` again, because losing the base table grant removes the usage privilege of the view
D: Recreate the view in a notebook on a dedicated cluster, where the permissions of the view user instead of the view owner are checked on the base table
K: A
G: ## Whose permissions are checked
To read a view, a user needs `SELECT` on the view, `USE CATALOG` on its catalog and `USE SCHEMA` on its schema. Unity Catalog also checks the permissions on the underlying tables and views. On SQL warehouses (and standard compute, and recent dedicated compute with fine-grained access control) the check on the base data is made for the **view owner**, not for the reader. So the view owner must keep access to everything the view uses.
- This design lets you expose a restricted slice (filtered rows, selected columns) without granting analysts the base table.
- If the owner loses the base privilege, every reader fails.
- Make a group or service principal the owner of production views so they do not depend on a person's team membership. Only the view owner (not `MANAGE`) can edit the definition and comment.
W: Change the owner: a durable owner with SELECT on the base table restores the checks that run as the owner, while analysts keep seeing only the view.
X: B=Grant on the base table: it removes the protective purpose of the view and the readers' own rights are not what is checked on this compute.
C=USE CATALOG: the readers' usage privileges are unaffected; the failing check is the owner's access to the underlying table.
D=Dedicated cluster rebuild: a different compute does not move the check to the reader on modern runtimes, and it would hide the ownership problem.
T: View readers are checked against the view; the base-table check runs as the view owner, so give views a durable owner.
V: Unity Catalog views

@ DBX-DEP D7 T7.2 advanced troubleshooting
S: Alex, a data engineer who left the company, owns about 200 tables in `prod.etl` that pipelines created while running under his identity. Ownership is shown as a deactivated user, and the schema owner wants to fix the situation. What is the correct way?
A: Only a metastore admin can change ownership of tables, so the request goes to the account team and the schema owner cannot do it
B: The schema owner can transfer each table to a group or service principal, because owners manage child objects; ownership does not move with the schema
C: Transfer ownership of the schema to a group, which automatically makes that group the owner of all 200 tables under it
D: The tables become ownerless after Alex is deactivated, so any user with `SELECT` can claim each of them with `ALTER TABLE ... OWNER TO`
K: B
G: ## Ownership rules
- An object has exactly one owner (user, service principal or group), initially its creator.
- Owners can grant and revoke, transfer ownership and drop. Owning a container also gives the ability to manage every child, because owners effectively hold `MANAGE` on them, so a schema owner can transfer table ownership.
- Ownership does **not** inherit: changing the schema's owner leaves the tables with their current owners.
## Operational practice
Make a group or service principal the owner of production objects, run pipelines as a service principal so new tables get a stable owner, and review owners from the information schema. For 200 tables use a scripted loop:
```
ALTER TABLE prod.etl.t1 OWNER TO `etl_admins`;
```
W: Schema owner transfers each table: manage rights on children allow it, and a group or service principal avoids repeating the issue.
X: A=Metastore admin only: owners and holders of `MANAGE` can transfer ownership of the objects they manage.
C=Schema transfer: ownership never inherits, so the tables keep their old owner after the schema changes hands.
D=Ownerless tables: every object always has an owner, and a user cannot claim ownership just because of `SELECT`.
T: Ownership does not inherit; a schema owner can reassign each child to a group or service principal.
