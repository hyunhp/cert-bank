@ DBX-DEP D3 T3.1 advanced use-case
S: A silver job receives one meter reading per row, and the device often sends NULL when a sensor skips a measurement. Analysts need every row to carry the most recent non-NULL `temp` of the same `device_id` at or before its `ts`. Which expression does this without a self-join?
A: `last(temp, true) OVER (PARTITION BY device_id ORDER BY ts ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)`
B: `max(temp) OVER (PARTITION BY device_id ORDER BY ts ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)` to carry the highest earlier value
C: `lag(temp, 1) OVER (PARTITION BY device_id ORDER BY ts)`, which returns the value of the previous row even when it is NULL
D: `first_value(temp, true) OVER (PARTITION BY device_id ORDER BY ts ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)` to read the earliest non-NULL value
K: A
G: ## Forward fill with a window
A window function computes a value for each row from a frame of related rows, without collapsing the rows as `GROUP BY` does. Three parts define it:
- `PARTITION BY device_id` keeps each device independent.
- `ORDER BY ts` gives the rows a sequence.
- The frame (`ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`) limits the rows to "everything up to now".
Aggregate-style functions such as `first_value` and `last` take an `ignoreNull` flag (`IGNORE NULLS`). With the flag on, NULL rows are skipped, so `last(temp, true)` over a frame that ends at the current row returns the newest known reading. This is the standard forward-fill pattern and is a single shuffle on `device_id`.
W: Last non-NULL over a growing frame: with `ignoreNull` set to true and the frame ending at the current row, each row gets the latest measurement that is not NULL, and a row with its own reading simply returns it.
X: B=Running max: `max` returns the highest value seen so far, not the most recent one, so a drop in temperature would still show the old peak.
C=lag by one row: `lag` looks only at the immediately preceding row and respects NULLs by default, so two consecutive missing readings still give NULL; it does not search backwards for a value.
D=first_value: with the same frame it returns the earliest non-NULL reading of the device, which stays constant after the first measurement and is not the latest.
T: Forward-fill NULLs with `last(col, true)` over a frame from the unbounded preceding row to the current row.

@ DBX-DEP D3 T3.1 advanced tradeoff
S: A gold job needs one row per `sensor_id` that holds the three readings with the latest `ts` as an array. The team wants a single `GROUP BY sensor_id` aggregate, with no window function and no self-join. Which expression does this?
A: `max_by(reading, ts, 3)`, which returns an array with the readings of the three rows with the largest `ts`
B: `max_by(reading, ts)`, which returns the `reading` values of the three rows with the largest `ts` as an array
C: `collect_list(reading)`, which returns the readings as an array sorted by `ts` from the newest to the oldest
D: `first(reading, 3)`, which returns the first three `reading` values of each group in arrival order
K: A
G: ## Top-N values inside an aggregate
`max_by(expr, ordExpr)` returns the `expr` value of the row with the largest `ordExpr` in each group. It has an optional third argument, `limit`:
- Without `limit` the result has the type of `expr`: one value, taken from one row.
- With `limit` (an `INT` from 1 to 100,000) the result is an `ARRAY` of up to `limit` values, taken from the rows with the largest `ordExpr` values.
- Rows whose `ordExpr` is NULL are not included, and ties on the largest values make the result non-deterministic.
This gives a "latest N per key" array in one aggregation step. When the full rows are needed, or ties must be broken in a repeatable way, a window function such as `row_number()` with a unique tie-breaker is the alternative.
W: max_by with a limit: the third argument turns the result into an array of the values that belong to the three largest `ts` values per sensor, in one aggregate.
X: B=max_by without limit: it returns a single value of the type of `reading`, from the one row with the largest `ts`, not an array of three.
C=collect_list: the order of the elements in the array is non-deterministic, and it collects all readings, so neither the sorting by `ts` nor the limit of three is applied.
D=first: its second argument is the boolean `ignoreNull`, not a count, so `3` is not a valid argument, and `first` would pick by arrival order rather than by `ts`.
T: Use `max_by(expr, ordExpr, n)` to collect the n values with the latest ordering key per group in one aggregate.

@ DBX-DEP D3 T3.1 advanced troubleshooting
S: A report uses `GROUP BY ROLLUP(region, channel)` and shows a row with `region = 'EU'` and `channel = NULL`. Some analysts read it as "EU sales with no channel recorded", but the source also contains genuine NULL channels. How should the query tell the subtotal row from real NULL data?
A: Replace `ROLLUP` with `GROUP BY region, channel` and add the totals later in a separate union with the same two columns
B: Wrap `channel` in `coalesce(channel, 'ALL')`, which returns the label only for subtotal rows and never for source NULLs
C: Select `grouping(channel)` next to the columns; it is 1 for rows where `channel` was aggregated away and 0 for real values, including NULL
D: Add `DISTINCT` to the select list, which removes the subtotal rows that repeat a region and leaves only the genuine NULL channels
K: C
G: ## Grouping analytics and the NULL ambiguity
`ROLLUP`, `CUBE` and `GROUPING SETS` compute several aggregation levels in one pass over the data. In the subtotal rows the column that was rolled up is reported as NULL, so it looks the same as a source NULL.
- `grouping(col)` returns 1 when the column was aggregated away in that output row and 0 otherwise.
- `grouping_id(...)` combines several columns into one bit mask that identifies the grouping level.
Using these flags is the supported way to label subtotals. It avoids replacing NULLs before the grouping, which would merge real "unknown" data with the label.
W: grouping flag: `grouping(channel)` is computed by the engine from the grouping level, so subtotal rows get 1 and rows with a real NULL channel get 0.
X: A=Plain GROUP BY: this drops the subtotal and total rows the report needs, and a manual union would recompute them with another scan of the data.
B=coalesce: it turns both the subtotal NULLs and the source NULLs into the same label, so the ambiguity stays; it only hides it.
D=DISTINCT: it removes only fully identical rows, so subtotal rows with different aggregated values stay, and it cannot tell why a NULL appears.
T: Use `grouping()` or `grouping_id()` to separate rollup subtotal NULLs from real NULL values.
V: Spark SQL aggregations

@ DBX-DEP D3 T3.2 advanced troubleshooting
S: Events were stored as JSON strings and queried with `payload:Customer_ID`. After the table was migrated to a VARIANT column built with `parse_json`, the same query returns NULL for every row, while the data still contains the key `customer_id`. What explains this?
A: VARIANT paths are case-sensitive, so `Customer_ID` and `customer_id` are different fields and the exact key is required
B: `parse_json` renames keys to lower case on conversion, so the query needs the stored key written in upper case instead
C: The `:` operator works only on STRING columns, so the query needs `get_json_object` over the column
D: `parse_json` stores keys in alphabetical order and the engine matches by position, so a renamed key cannot be found
K: A
G: ## VARIANT is not a JSON string
Databricks recommends VARIANT over JSON strings for semi-structured data. The query syntax is similar (`col:field`, `.sub`, `[0]`), but some semantics differ, and these differences can break queries when migrating:
- Path elements are matched **case-sensitively** for VARIANT; JSON string queries are case-insensitive.
- `[*]` is not supported to unpack all array elements.
- Null handling differs (variant null versus SQL NULL).
A path that is not found returns NULL rather than an error, which is why the symptom looks like missing data.
W: Case sensitivity: the JSON string functions matched `Customer_ID` to `customer_id`, but VARIANT path elements must match the stored case exactly, so the old spelling finds nothing and returns NULL.
X: B=Key renaming: `parse_json` keeps the key names exactly as they appear in the JSON text; it does not change their case.
C=Operator on STRING only: the colon operator is documented for VARIANT as the shorthand for `variant_get`, and `get_json_object` is for JSON strings.
D=Positional matching: keys are looked up by name; the key ordering is arbitrary and plays no role in path lookup.
T: Migrating JSON strings to VARIANT makes key lookups case-sensitive, so a mismatch returns NULL instead of an error.

@ DBX-DEP D3 T3.2 advanced troubleshooting
S: A VARIANT column `raw` contains the key `zip.code`. The query `SELECT raw:`zip.code` FROM addresses` returns NULL for every row, although the key is present with values. Which change returns the values?
A: Write `raw:['zip.code']`, because bracket notation escapes periods and square brackets in field names
B: Write `raw:zip.code`, because the VARIANT operator takes a dotted name as one field key
C: Wrap the whole column in `to_json(raw)` and apply the colon operator to the resulting string
D: Cast the column first with `raw::string`, since VARIANT paths cannot contain periods before a cast
K: A
G: ## Special characters in field names
With VARIANT the `.` operator selects a sub-field, so `raw:zip.code` means "field `zip`, then sub-field `code`". A field whose name contains a period, a colon, a space or square brackets must be escaped.
- `raw:['zip.code']` is the recommended syntax for every field name with a special character; in `variant_get` the same escape is the path `$['zip.code']`.
- Backticks escape spaces and colons, but they do **not** escape periods or square brackets, so a name with a period returns NULL when written in backticks.
A missing path never raises an error, which is why the result is NULL and not a failure.
W: Bracket escape: `['zip.code']` addresses the single field named `zip.code`, so the lookup finds it instead of searching for `zip` and then `code`.
X: B=Dotted name: without escaping, the dot starts a nested path, so the engine looks for an object `zip` that does not exist and returns NULL.
C=to_json first: this serializes the VARIANT to a string and gives up the typed access; the period problem stays in whatever path syntax is used afterwards.
D=Cast to string: casting the whole value does not help to address a field, and the claim that periods are forbidden in paths is wrong, since bracket notation is the documented answer.
T: Escape VARIANT field names that contain periods or brackets with `col:['name']`; backticks do not cover them.
V: VARIANT

@ DBX-DEP D3 T3.2 advanced use-case
S: A VARIANT column `payload` holds an order with an array `items` of objects such as `{"sku":"A1","qty":2}`. A fact table needs one row per item with `sku` and `qty` as typed columns. Which query builds it?
A: `SELECT o.id, payload:items[*].sku FROM orders o`, which expands all array elements into separate rows
B: `SELECT o.id, i.value:sku::string AS sku, i.value:qty::int AS qty FROM orders o, LATERAL variant_explode(o.payload:items) i`
C: `SELECT o.id, explode(o.payload:items) FROM orders o`, because the generic function is the only one that unpacks arrays
D: `SELECT o.id, payload:items:sku::string FROM orders o GROUP BY o.id`, which flattens the array while grouping by order
K: B
G: ## Flattening VARIANT arrays
`variant_explode` is the table-valued function for VARIANT. It returns the columns `pos`, `key` and `value`.
- For an **array**, `key` is NULL and `value` is one array element (still a VARIANT).
- For an **object**, `key` and `value` are the field names and values.
- A NULL or non-array/object input yields no rows (use `variant_explode_outer` to keep one NULL row).
After the explode, extract fields from `value` with `:` and cast with `::` to typed columns. A `LATERAL` join (or a comma join in the FROM clause) correlates the function with each order row.
Note that `[*]` is not supported for VARIANT, so the element-wise syntax from JSON strings does not carry over.
W: variant_explode with LATERAL: each item becomes a row, and `value:sku::string` and `value:qty::int` give typed columns for the fact table.
X: A=Wildcard path: `[*]` is not supported for VARIANT, so this form cannot unpack the array.
C=Generic explode: `explode` expects an ARRAY or MAP type, and a VARIANT array needs the VARIANT-specific function, which is why the documentation lists `variant_explode` as its counterpart.
D=Chained fields with GROUP BY: grouping does not flatten anything, and `items:sku` on an array does not return one value per element.
T: Flatten VARIANT arrays and objects with `variant_explode` in a lateral join, then cast the extracted fields.
V: VARIANT

S: A bronze table stores webhook bodies from 30 partners as VARIANT. Before promoting stable fields into typed silver columns, the team wants one summary of the combined structure and types seen across the whole column, including fields that appear only in some rows. Which function fits?
A: `schema_of_variant(payload)` applied to the first row only, since one row always holds all possible fields
B: `schema_of_json_agg(payload)`, which accepts VARIANT input and merges the field types of every row

A VARIANT column has no declared inner schema, so the structure must be inferred from the data.
- `schema_of_variant(v)` returns the schema of one value.

B=schema_of_json_agg: that is the counterpart for JSON strings; the VARIANT function is `schema_of_variant_agg`.
D=DESCRIBE: table metadata shows the column as VARIANT and does not list inner fields, because they are not part of the schema.
T: Use `schema_of_variant_agg` to inspect the combined schema of a VARIANT column before extracting typed fields.

@ DBX-DEP D3 T3.2 advanced troubleshooting
S: A nightly ingest runs `SELECT parse_json(body) AS v FROM bronze_raw`. One partner occasionally sends truncated JSON and the whole job fails. Bad rows must be kept for inspection, and good rows must flow. What is the best design?
A: Use `try_parse_json(body)`, which returns NULL on invalid JSON, and route NULL results with non-NULL input to a rejects table
B: Keep `parse_json` and set `failOnError => false` on the call so that the failed rows come back as error messages for review
C: Cast with `body::variant`, which silently converts malformed JSON text to a VARIANT string value
D: Wrap the call in `ai_query` to repair broken JSON before parsing, so that no row ever fails

G: ## Tolerant parsing
`parse_json` raises an error when the input is malformed, exceeds the VARIANT size limit or is otherwise invalid, so a single bad row fails the batch.
`try_parse_json` is the tolerant variant: it returns NULL when parsing fails. The usual production pattern is:
1. Parse with `try_parse_json`.
2. Rows where the result is NULL but the input was not NULL are rejects; write them (with the raw `body`) to a rejects or quarantine table.
3. The remaining rows continue to the silver table.
This keeps the pipeline running without losing the evidence for the data provider.
W: try_parse_json plus a reject path: invalid text turns into NULL instead of an exception, and filtering on NULL result with non-NULL input isolates exactly the broken rows.
X: B=failOnError: this is an argument of `ai_query`, not of `parse_json`, so it does nothing here.
C=Cast to variant: a cast of text produces a VARIANT string holding the whole text, it does not parse the JSON structure, so downstream paths find nothing.
D=Repair with a model: it adds cost and non-deterministic output to a simple parsing step, and a model can still return invalid JSON, so failures remain possible.
T: Use `try_parse_json` and a reject path so malformed JSON is quarantined instead of failing the job.

S: A VARIANT column `v` holds events like `{"id":1,"coupon":null}` and `{"id":2}`. A data quality check must count events where the key `coupon` is present with an explicit JSON null, separately from events without the key. Which predicates separate the two cases?
A: `v:coupon IS NULL` is true for both cases, so the cases cannot be told apart in SQL at all
B: `is_variant_null(v:coupon)` is true when the key holds an explicit null, while `v:coupon IS NULL` is true when the key is missing
C: `v:coupon = 'null'` is true for the explicit null, while a missing key returns the string `'missing'`
D: `try_variant_get(v, '$.coupon', 'string') IS NULL` is true only for the explicit null and false for a key that is missing

VARIANT distinguishes a SQL NULL from a JSON null stored inside the value.
- If a path is not found, the extraction returns a SQL `NULL`, so `v:coupon IS NULL` is true.
- If the key exists with the JSON value `null`, the extraction returns a VARIANT that stores a null; `IS NULL` is false for it, and `is_variant_null(...)` returns true.
This is different from JSON string functions, which handle nulls differently, and matters for data quality rules that must tell "not sent" from "sent as null".
W: is_variant_null versus IS NULL: the first detects a stored JSON null and the second detects a missing path, so the two predicates split the cases.
X: A=Both identical: the documentation describes `is_variant_null` precisely to separate a VARIANT-encoded null from a SQL NULL, so SQL can tell them apart.
C=String comparison: the extracted value is a VARIANT, not a string, and a missing key returns NULL, not the text `'missing'`.
D=Typed extraction: a cast of either case to a string yields NULL, so the predicate is true for both cases and cannot separate them.
T: Use `is_variant_null` for explicit JSON nulls and `IS NULL` for missing keys in VARIANT data.

S: A team wants to enable VARIANT on an existing Delta table that is also read by an external engine using a Delta Lake reader library. What must the team consider before running `ALTER TABLE ... SET TBLPROPERTIES('delta.feature.variantType' = 'supported')`?

@ DBX-DEP D3 T3.2 advanced tradeoff
S: A compliance team must be able to prove the exact text of every webhook body received. The bronze table stores `body` as STRING and a derived column `v = parse_json(body)`. An engineer proposes to drop `body` and keep only `v`, converting back with `to_json(v)` when needed. What is the problem?
A: `to_json` cannot convert a VARIANT value back to text, so the conversion is not available at all
B: The conversion only changes the data type, so the proposal is safe and the original text can be rebuilt byte for byte from the stored VARIANT value
C: `parse_json` is not exactly reversible: whitespace, key order and trailing zeros are not preserved, so keep the raw text
D: VARIANT values are stored as compressed archives that cannot be read after 30 days, so the raw text must be kept
K: C
G: ## VARIANT is a parsed representation
`parse_json` turns text into the binary VARIANT encoding, and `to_json(variant)` converts it back to a JSON string. The round trip is not exact:
- whitespace is not preserved,
- the ordering of keys is arbitrary,
- trailing zeros in numbers might be truncated.
For analytics this is irrelevant, so VARIANT is the right type for query access. For evidence and replay, keep the original string in the bronze layer (or the raw files) and treat VARIANT as the derived column, which can also be rebuilt when the parsing logic changes.
W: Not an exact inverse: the VARIANT keeps the meaning, not the formatting, so the original bytes cannot be rebuilt and the raw column must stay.
X: A=No conversion: Databricks Runtime 15.3 and above extend `to_json` to cast VARIANT values to JSON strings.
B=Byte-for-byte rebuild: the documented differences in whitespace, key order and number formatting show that it is not byte for byte.
D=Archive expiry: no such time-based loss exists; the reason is the representation, not age.
T: VARIANT preserves content, not formatting, so keep the raw JSON text where exact evidence is required.

@ DBX-DEP D3 T3.3 advanced troubleshooting
S: A batch enrichment job runs `SELECT id, ai_query('databricks-llama', 'Summarize: ' || text) AS summary FROM tickets` over 8 million rows. A few hundred rows hit endpoint errors, and the entire query fails and discards hours of work. The team wants the other rows to complete and the failures to be retried later. What should change?
A: Add `failOnError => false`; each result becomes a struct with response and error message, so failed rows can be selected and retried later
B: Split the table into thousands of small queries run one after another, so that an endpoint error only hits a small part of the data
C: Wrap the call in `try_cast`, which turns any endpoint error into NULL before it can fail the query

G: ## Row-level errors in ai_query
By default (`failOnError => true`) an endpoint error on a row fails the whole query. With `failOnError => false`, `ai_query` returns a `STRUCT` with two fields: the parsed `response` and an `errorMessage`.
- Success: `errorMessage` is NULL.
- Endpoint error for that row: `response` is NULL and `errorMessage` carries the reason.
- Other kinds of errors still fail the whole query.
A production pattern stores the struct, writes successful rows downstream and selects `errorMessage IS NOT NULL` rows into a retry set for the next run.
W: failOnError => false: row-level endpoint errors turn into error messages in the result struct, so the query finishes and the failed rows can be selected and retried.
X: B=Manual splitting: the documentation advises submitting the full dataset in one query because AI Functions handle parallelism, retries and scaling; many small queries add overhead and still fail on any error.
C=try_cast: casting works on the returned value, not on the function call, and an endpoint failure is not a cast failure.
D=Provisioned throughput: dedicated capacity does not remove errors, and the documentation recommends Databricks-hosted foundation model endpoints for batch work.
T: Use `failOnError => false` in `ai_query` to get per-row errors instead of failing the batch.

@ DBX-DEP D3 T3.3 advanced use-case
S: A pipeline uses `ai_query` to extract `vendor`, `total` and `due_date` from invoice text. The current prompt asks for JSON and a downstream `from_json` step fails on about 3% of rows because the model adds explanatory text. Which change makes the output reliably parseable?
A: Lower the model temperature to zero in `modelParameters`, which guarantees that the model returns valid JSON every time
B: Pass a `responseFormat` with a JSON schema or DDL schema, so the chat model must return output that follows it
C: Add a second `ai_query` call that asks the model to check whether its first answer was valid JSON
