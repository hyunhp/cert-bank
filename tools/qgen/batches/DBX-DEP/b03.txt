@ DBX-DEP D1 T1.10 advanced troubleshooting
S: A team moves an always-on ingestion task from classic jobs compute to serverless compute for jobs. The code ends with `.writeStream.trigger(processingTime="30 seconds").toTable("main.bronze.events")`. The task now fails at start with `INFINITE_STREAMING_TRIGGER_NOT_SUPPORTED`, yet the stream must keep a latency of tens of seconds without a cluster start per run. Which change fits?
A: Move the logic into a Lakeflow pipeline on serverless compute in continuous mode, which is not bound by the trigger restriction of serverless jobs
B: Keep the task on serverless compute and switch to `Trigger.Once()`, which is supported there and runs a continuous micro-batch loop that keeps the 30-second latency in place
C: Keep the task on serverless compute and set a Spark property in the serverless environment that re-enables the `ProcessingTime` trigger for job tasks
D: Move the task to a serverless SQL warehouse, since warehouses accept Structured Streaming triggers of any interval and keep running between queries
K: A
G: ## Where triggers are restricted
Serverless compute for notebooks and jobs supports only the triggers that end on their own: `Trigger.AvailableNow()` (recommended) and the deprecated `Trigger.Once()`. `Trigger.ProcessingTime(interval)` and `Trigger.Continuous(interval)` are rejected with `INFINITE_STREAMING_TRIGGER_NOT_SUPPORTED`, and an omitted trigger defaults to `ProcessingTime("0 seconds")`, which fails too.
## Options for a continuous stream
- A serverless Lakeflow pipeline (formerly Delta Live Tables) in continuous mode: the restriction does not apply to pipeline processing modes.
- A continuous job with `Trigger.AvailableNow()`: the job loops, but each iteration is an incremental batch, not a 30-second micro-batch loop.
- Classic jobs compute, if the code needs settings that serverless lacks.
Example: a fraud feature stream with a 10-second SLA belongs in a continuous pipeline, not in a serverless job task with a processing-time trigger.
W: Serverless pipeline in continuous mode: it keeps the stream running with managed compute, offers streaming latency in seconds, and is explicitly exempt from the notebook and job trigger restriction.
X: B=Trigger.Once: it is supported only as a one-shot batch of the available data, then the query stops; it is also deprecated and cannot provide a 30-second loop.
C=Spark property: serverless compute allows only a short list of Spark properties, and none of them re-enables the unsupported triggers.
D=SQL warehouse: warehouses run SQL statements, not Python Structured Streaming tasks, so a `writeStream` query cannot run there with any trigger.
T: Serverless jobs run only self-terminating triggers; continuous streaming on serverless belongs in a continuous Lakeflow pipeline.
V: Serverless compute, Lakeflow Jobs, Lakeflow Pipelines

@ DBX-DEP D1 T1.10 advanced use-case
S: A nightly job task depends on a Python package that links against a native library. The library needs an operating system package that a cluster init script installs on every node. The platform team wants the lowest-maintenance compute that still supports this, and the task must not run on shared interactive clusters. Which choice fits?
A: Classic jobs compute with a compute-scoped init script that installs the system package, because serverless compute does not support compute-scoped init scripts
B: Serverless compute for jobs with the init script attached to the task environment, because serverless environments run the same init scripts as classic compute
C: Classic all-purpose compute shared with the analysts, because all-purpose clusters are the recommended compute for automated production workloads
D: Serverless compute for jobs with the system package listed in the environment dependencies, because that list accepts operating system packages as well as Python ones
K: A
G: ## Serverless is the default, with exceptions
Databricks recommends serverless compute for most automated workloads: fewer settings, fast start-up, automatic scaling. Classic jobs compute is the choice for non-SQL tasks that need custom cluster settings serverless does not offer.
## What serverless does not offer
- Compute-scoped init scripts and compute policies. Python packages are installed through the environment (a base environment plus a dependency list), not through scripts.
- Most Spark compute configurations, Maven coordinates, RDD APIs, R.
## All-purpose compute for jobs
Classic all-purpose compute is not optimized for automated workloads; jobs should use job compute (created per run, terminated afterwards).
Example: a geospatial package that needs `libgdal` installed as an OS package requires a cluster init script, so it runs on classic jobs compute.
W: Classic jobs compute with an init script: it lets the cluster run the script that installs the OS package, and it is created per run and shut down afterwards, which suits a nightly automated task.
X: B=Init scripts on serverless: compute-scoped init scripts are listed among the unsupported features; serverless installs only what the environment dependency list describes.
C=Shared all-purpose cluster: all-purpose compute is meant for interactive work, is not optimized for automated workloads, and the stem forbids shared interactive clusters.
D=Environment dependencies: the list installs Python packages (for example from a requirements file or wheel), not operating system packages that a native library needs.
T: Pick serverless for most jobs, but fall back to classic jobs compute when the task needs init scripts or other custom cluster settings.

@ DBX-DEP D1 T1.11 applied troubleshooting
S: A pytest test checks `df.groupBy("region").agg(avg("price").alias("avg_price"))` against expected values with `assert actual.collect() == expected.collect()`. It fails intermittently: rows come back in a different order between runs, and averages differ in the twelfth decimal. The output contract defines no row order. Which replacement makes the test stable without hiding real errors?
A: `assertDataFrameEqual(actual, expected)` from `pyspark.testing`, which ignores row order by default and compares numeric values within a small tolerance
B: `assertDataFrameEqual(actual, expected, checkRowOrder=True)`, which sorts both sides first so that every run yields identical collected lists
C: `assert actual.count() == expected.count()`, because comparing counts avoids both the ordering and the rounding differences
D: `assert actual.orderBy("region").collect() == expected.collect()`, which fixes the ordering and compares every value exactly as before
K: A
G: ## Why collect-and-compare is brittle
Spark gives no ordering guarantee after a shuffle, and floating-point aggregations can differ in the last digits when the same values are added in a different order. A test that compares collected lists is therefore flaky even when the code is right.
## PySpark test utilities
`pyspark.testing.assertDataFrameEqual(actual, expected, checkRowOrder=False, rtol=1e-05, atol=1e-08, ...)` compares schema and rows, ignores row order by default, and uses a relative and absolute tolerance for floating-point columns. It raises an error that lists the differing rows. `assertSchemaEqual` checks only the schemas.
Example: use `checkRowOrder=True` only when the contract defines an order, such as a sorted export.
W: assertDataFrameEqual with defaults: order-insensitive comparison plus a float tolerance fixes both causes, while still failing on wrong keys, wrong values or a wrong schema.
X: B=checkRowOrder=True: it does not sort anything; it requires the same order on both sides, which makes the flaky ordering failure worse.
C=Count comparison: it stops flakiness but also stops detecting wrong averages, wrong regions or swapped values, so the test no longer verifies the logic.
D=orderBy and collect: the order is fixed on one side only, and exact equality on doubles still fails when the twelfth decimal differs.
T: Compare DataFrames with assertDataFrameEqual, which ignores row order and uses tolerances for floats unless you opt into strictness.
V: PySpark testing utilities, pytest

@ DBX-DEP D1 T1.11 advanced troubleshooting
S: A unit test builds the expected DataFrame with `spark.createDataFrame([(1, "a"), (2, "b")], ["id", "code"])`. The function under test returns a column `id` computed with `cast("int")`. The values look identical, but `assertDataFrameEqual(actual, expected)` fails. What is the most likely cause and the right fix?
A: Python integers are inferred as `LongType` in the expected data but the function returns `IntegerType`; declare an explicit schema for the expected DataFrame
B: The comparison ignores column types, so the failure comes from row order; add `checkRowOrder=True` and sort both inputs by `id` before comparing
C: `assertDataFrameEqual` accepts only DataFrames read from tables, so the expected data must first be written to a Delta table in a test schema
D: The nullability of `id` differs, because `assertDataFrameEqual` always compares nullable flags, so the test must be called with `ignoreNullable=False` to tolerate the difference
K: A
G: ## Schema is part of equality
`assertDataFrameEqual` compares schemas as well as rows. Column types must match unless you pass `ignoreColumnType=True`; nullability is ignored by default (`ignoreNullable=True`); column order matters unless `ignoreColumnOrder=True`.
## The inference trap
`createDataFrame` from Python tuples infers integers as 64-bit `LongType`. A function that casts to `int` returns `IntegerType`, so the values print the same while the types differ. Defining the expected schema explicitly (a `StructType` or a DDL string such as `"id INT, code STRING"`) states the contract in the test and avoids accidental inference.
W: Explicit expected schema: the failure is a type mismatch (`LongType` versus `IntegerType`), and declaring the schema documents and enforces the output contract instead of loosening the assertion.
X: B=Row order: comparison is order-insensitive by default and column types are compared, so the type mismatch, not the order, is what raises the error.
C=Tables only: the utility compares any two DataFrames or lists of rows, so writing test data to Delta adds slowness and no benefit.
D=Nullability: `ignoreNullable` already defaults to `True`, so a nullability difference would not fail the test, and passing `False` would make it stricter, not more tolerant.
T: assertDataFrameEqual checks types; define the expected schema explicitly so inference does not decide the contract.
V: PySpark testing utilities

A: Move the join and derived columns into a DataFrame-in, DataFrame-out function in a Python module, keep I/O in a thin entry point, and test the function with small in-memory DataFrames

Databricks recommends keeping functions and their tests outside of notebooks for Python: import the functions from a module (a file in a Git folder or a bundle's source folder) and test them with `pytest`. @ DBX-DEP D1 T1.12 advanced use-case
S: A stream computes hourly revenue per store with `.withWatermark("event_ts", "30 minutes").groupBy(window("event_ts", "1 hour"), "store").sum("amount")` and appends to a Delta table. Operators see the 09:00 window only after about 10:30, but the dashboard needs running totals within a few minutes. Which design meets the need?
A: Use update mode and upsert each micro-batch by window and store in `foreachBatch`, so partial totals appear early and state is still dropped
B: Stay in append mode and lower the trigger interval to one second, so that each window is written to the Delta table as soon as new events for that window arrive
C: Switch to complete mode, which writes the full result table at each trigger and drops old windows from state once the watermark has passed them
D: Remove the watermark and keep append mode, so that every window is emitted as soon as its hour ends instead of after the extra delay
K: A
G: ## Output modes with a watermark
- **Append**: a window row is written once, after the watermark passes the end of the window. Every result is delayed by the lateness threshold; old state is then dropped.
- **Update**: rows are written as soon as they change in a trigger and can be rewritten with later values; old state is dropped after the watermark.
- **Complete**: the whole result table is rewritten each trigger and aggregation state is never dropped.
## Consequences
Update mode lowers latency but the sink must accept changed rows, which a plain Delta append does not: write through `foreachBatch` with a `MERGE` on the window and store key (idempotent by design). Append mode is right when consumers can wait for final values.
W: Update mode with an upsert: the dashboard sees partial totals each trigger, the merge keeps one row per window and store, and state is still evicted when the watermark expires.
X: B=Faster trigger in append mode: append still holds a window back until the watermark passes its end plus 30 minutes, so the trigger interval does not change when results appear.
C=Complete mode: it emits early but keeps all windows in state forever and rewrites the entire result each trigger, and it cannot use the watermark to drop state.
D=Removing the watermark: streaming aggregations in append mode require a watermark on the event time to know when a window is final, so the query is rejected.
T: Append emits after the watermark; update emits early and needs an upsert-capable sink; complete never drops state.
V: Structured Streaming, Delta Lake

@ DBX-DEP D1 T1.12 advanced troubleshooting
S: A team joins an `impressions` stream with a `clicks` stream using a left outer join to list impressions that got no click within 10 minutes. The query is rejected at start. Both streams have event-time columns and no watermarks. What must the team do, and what behavior should they expect afterwards?
A: Set a watermark on both inputs and add an event-time range condition; impressions without a click are emitted with NULL columns after the watermark passes
B: Set a watermark on the impressions stream only and switch to update mode, so that unmatched impressions are emitted immediately with NULL click columns and later corrected
C: Replace the left outer join with an inner join, which needs no watermark, and detect the missing clicks later with a batch anti-join on the sink table
D: Keep the query as is and set `spark.sql.streaming.multipleWatermarkPolicy` to `max`, which supplies a watermark for streams that declare none
K: A
G: ## Stream-stream joins and state
A stream-stream join buffers rows from both sides in state until a match can no longer arrive. Joins support append mode only.
- **Inner join**: watermarks are recommended on each input so old state can be discarded; without them every key stays in state and performance suffers.
- **Outer join**: watermarks are mandatory, together with an event-time range condition (for example, click time between impression time and impression time plus 10 minutes). The engine can only declare a row unmatched once the watermark proves that no match can still arrive, so the NULL-padded row is written late.
Example: with a 10-minute range condition and a 15-minute watermark, an unclicked impression appears in the sink roughly 25 minutes after it happened.
W: Watermarks on both sides plus a time-range condition: this is what the outer join requires, and the delayed NULL rows are the expected result of append-only output.
X: B=Impressions watermark only and update mode: outer joins need watermarks on the inputs they buffer, and joins do not support update mode, so unmatched rows cannot be sent early.
C=Inner join: an inner join cannot return impressions that have no click at all, and the anti-join afterwards recreates the logic with a batch job and more latency.
D=multipleWatermarkPolicy: that setting only picks among watermarks that already exist on several inputs; it creates none.
T: Stream-stream outer joins need watermarks and a time-bound condition, and unmatched rows surface only after the watermark.
V: Structured Streaming

@ DBX-DEP D1 T1.12 advanced tradeoff
S: A query unions an `orders` stream (late by up to 1 hour) with a partner feed (late by up to 2 hours), each with its own `withWatermark`. By default the dashboard waits for the slow feed and results are late. An engineer sets `spark.sql.streaming.multipleWatermarkPolicy` to `max`. What does this change?
A: The global watermark follows the fastest input, so state is evicted sooner and output is earlier, but late records from the slower feed may be dropped
B: The global watermark follows the slowest input, so no record from either feed is ever dropped and state grows without limit
C: Each input keeps its own watermark for its own state, so late records from the slower partner feed are still guaranteed to be processed by the join
D: The query now rejects inputs that declare different delays, and both feeds must use the same threshold again
K: A
G: ## One global watermark
With several watermarked inputs, Structured Streaming tracks the maximum event time per input, derives a watermark from each input's delay, and then uses a single global watermark. The default policy is `min`: the slowest stream decides, so nothing is dropped because one input lags, at the price of holding more state and delaying results.
## Trade-off
Setting the policy to `max` follows the fastest stream. Latency and state shrink, but data from slower streams that falls behind the global watermark is dropped. Databricks recommends using it with caution.
Example: if orders reach event time 12:00 and the partner feed is at 10:30, the `min` watermark is based on the partner feed, the `max` watermark on orders.
W: Global watermark follows the fastest input: this is the documented effect of `max`, trading completeness of late partner data for lower latency and less state.
X: B=Slowest input: that is the default `min` policy, not `max`; also state is bounded by the watermark in both policies, it is not unbounded.
C=Per-input watermarks: there is a single global watermark for the query; per-input delays only feed into its calculation, and late data is never guaranteed once the watermark passes it.
D=Rejecting different delays: the engine accepts different delays per input by design; that is why the policy setting exists.
T: min protects slow inputs and costs latency; max lowers latency and state but can silently drop late data.
V: Structured Streaming

@ DBX-DEP D1 T1.12 advanced use-case
S: Device events carry a unique `guid`, but a gateway re-sends some events with a new `event_time` stamp up to 3 hours after the first send. A stream currently uses `dropDuplicates(["guid", "event_time"])` and duplicates still reach the silver table. The team wants one row per `guid` with bounded state. Which implementation fits?
A: `withWatermark("event_time", "4 hours").dropDuplicatesWithinWatermark(["guid"])`, with a threshold above the largest gap between duplicates
B: `dropDuplicates(["guid"])` without a watermark, since state per key is small and the table will not grow noticeably
C: `withWatermark("event_time", "1 hour").dropDuplicatesWithinWatermark(["guid"])`, because a shorter threshold keeps less state and still guarantees all duplicates are removed
D: `distinct()` on the full row after `withWatermark("event_time", "4 hours")`, which removes any event that arrived twice within the threshold
K: A
G: ## Deduplication needs state
Structured Streaming guarantees exactly-once processing of its input but does not deduplicate records that a source delivers twice. Deduplication keeps the keys it has seen in state.
- `dropDuplicates(cols)` without a watermark keeps every key forever: state grows without bound.
- `dropDuplicates` including the event time column only drops rows that match on all listed columns, so re-stamped duplicates survive.
- `dropDuplicatesWithinWatermark(cols)` (needs a watermark) deduplicates on a subset of columns even when event time differs between duplicates, and removes the key from state after the watermark. Duplicates within the threshold are always dropped; to guarantee all of them, the threshold must exceed the maximum timestamp difference between duplicate events.
## Rule
Size the watermark from the data: here 3 hours between copies needs more than 3 hours.
W: dropDuplicatesWithinWatermark on guid with a 4-hour watermark: it ignores the changing timestamp, bounds state, and the threshold covers the 3-hour gap.
X: B=Unbounded dropDuplicates: without a watermark, every guid stays in state indefinitely, which eventually causes memory and checkpoint problems.
C=One-hour threshold: copies arriving up to 3 hours later fall outside it, so duplicates are only dropped sometimes, not guaranteed.
D=distinct on the full row: rows that differ in the re-stamped event time are not identical, so the stamped duplicates are not removed.
T: Use dropDuplicatesWithinWatermark on the business key, with a watermark larger than the maximum gap between duplicates.
V: Structured Streaming

@ DBX-DEP D1 T1.12 advanced troubleshooting
S: A `foreachBatch` function appends each micro-batch to `silver.orders` and then to `silver.orders_audit` with plain Delta appends. After a failure between the two writes and an automatic job retry, `silver.orders` contains the rows of that batch twice. Which change gives the strongest guarantee for the replayed batch?
A: Write both tables with a stable `txnAppId` and a `txnVersion` bound to the `batchId`, and let errors propagate so the job retries the whole batch
B: Wrap both writes in a `try/except` that retries the failed write inside the function until it succeeds, so the retry never has to reach the job orchestrator at all
C: Rely on the checkpoint alone, because the commit log records the batch as processed and a restarted query never re-sends it to `foreachBatch`
D: Generate a new random `txnAppId` per run and set `txnVersion` to the current timestamp, so that every replay is treated as a fresh transaction
K: A
G: ## At-least-once in foreachBatch
`foreachBatch` gives at-least-once guarantees. The checkpoint's offset log records a batch before it runs and its commit log records it afterwards. If the query fails after some of the writes inside the function but before the commit, the restart replays the same batch with the same `batchId`.
## Making Delta writes idempotent
For DataFrame writes to Delta tables, set the `txnAppId` and `txnVersion` write options and bind `txnVersion` to `batchId`. Delta then skips a write whose (app id, version) pair it has already committed for that table. Do not catch and retry exceptions locally; let the error propagate so metrics stay accurate and the orchestrator retries the whole batch. For external sinks (OLTP databases, APIs) you must build your own idempotency: the same `batchId` must give the same result.
W: Stable txnAppId plus txnVersion=batchId: the replayed batch is recognized per table, so the table that was already written is not appended twice, and the failed write completes.
X: B=Local retry loop: Databricks advises against it, since partial or duplicate writes and wrong Spark metrics become possible, and the function can still fail between the two tables.
C=Checkpoint only: a failure inside the function happens before the commit entry, so the restarted query runs the same batch again; foreachBatch is at-least-once.
D=Random app id and timestamp version: the pair must be identical on replay to be recognized, so a new value each run makes Delta accept the duplicate.
T: foreachBatch can replay a batch; make Delta writes idempotent with a stable txnAppId and txnVersion = batchId.
V: Structured Streaming, Delta Lake

@ DBX-DEP D1 T1.12 advanced troubleshooting
S: A stateful stream falls over with an out-of-memory error on a huge micro-batch after a long outage. The engineer lowers `maxFilesPerTrigger` in the code and restarts the job with the same checkpoint and the same cluster size. The first batch fails with the same error. What explains this, and what is the fix?
A: The restart re-runs the micro-batch planned before the failure with its original offsets, so the new limit applies only later; scale compute up for that batch
B: The new `maxFilesPerTrigger` is ignored for the whole life of a checkpoint, so the checkpoint must be deleted and the full source history must be reprocessed from scratch
C: The commit log is incomplete after an out-of-memory error, so the stream restarts from the beginning of the source and rebuilds all state
D: Rate limits are read only from the original run configuration, so the job must be recreated with a new name before a changed limit is honored
K: A
G: ## Offset log and commit log
For each micro-batch the query first writes the planned source offsets to the checkpoint's offset log, runs the batch, then writes a commit log entry. After a crash, a batch that has an offset entry but no commit is planned again with exactly the same offsets so the sink receives that data once (exactly-once with an idempotent or transactional sink).
## Consequence for tuning
A changed configuration applies to the first newly planned batch, not to the batch that was already planned. If the planned batch is too large, the restart needs more resources; after it commits, the new rate limit shapes the following batches. Rate limits such as `maxFilesPerTrigger`, `maxBytesPerTrigger` or `maxOffsetsPerTrigger` are among the changes that are safe between restarts.
Example: after the outage the stuck batch holds 40,000 files; the next batches hold 500 each.

- **Legacy CDF** materializes change records at write time, requires a per-table setting, and supports Delta Lake tables only. Iceberg tables are not supported.
- **Automatic CDF** computes changes at read time from row-level lineage metadata (row tracking for Delta, row lineage for Iceberg v3), without per-table configuration. It requires a recent runtime and a Unity Catalog managed table in Iceberg v3 format (or Delta with row tracking enabled). It uses the same `table_changes()` and `readChangeFeed` APIs, in batch and in Structured Streaming.
## Limits
Change data feed is not part of the Iceberg specification, so external Iceberg clients cannot query it; only Databricks readers can. Because changes are computed at read time for `MERGE` and `UPDATE`, writes are cheaper and storage does not grow.
W: Automatic change data feed: it supports managed Iceberg v3 tables with the same APIs as Delta, and its Databricks-only scope matches the incremental job in the stem.
X: B=Legacy property on Iceberg: the legacy approach is Delta only, and the feed is not in the Iceberg spec, so external engines cannot read it.
C=Delta only: that describes the legacy feed; automatic change data feed also supports Iceberg v3 tables, so no conversion is needed.
D=Copy storing change files: automatic CDF computes changes during reads and stores nothing extra at write time, which is why writes become cheaper.
T: Iceberg v3 tables get automatic change data feed for Databricks readers; legacy CDF and external readers are not supported.
V: Apache Iceberg, Delta Lake, Change data feed

S: A CDC target in Delta has deletion vectors enabled because `MERGE` deletes are frequent. A partner using Trino needs to read it as Iceberg. The engineer runs `ALTER TABLE ... SET TBLPROPERTIES ('delta.universalFormat.enabledFormats' = 'iceberg')` and the command is rejected. How should the team proceed?
A: Purge and turn off deletion vectors with `REORG` while enabling Iceberg reads, with column mapping on, and accept asynchronous metadata generation
B: Convert the table to an external Delta table in a different catalog, because Iceberg reads are supported only for tables that sit outside of Unity Catalog entirely
C: Enable Iceberg reads and keep deletion vectors, because Iceberg clients apply the vectors when they read the data files
D: Replace the merge with `INSERT OVERWRITE` so that no deletion vectors are ever written, and then set the property
K: A
G: ## Iceberg reads on Delta (UniForm)
Enabling Iceberg reads makes a Delta table generate Iceberg metadata asynchronously next to the Delta log; the Parquet files are shared. Requirements include a Unity Catalog table (managed or external), column mapping enabled, a minimum reader and writer protocol, and writes from a supported runtime.
## Deletion vectors
Deletion vectors cannot be enabled on a table that has Iceberg reads enabled. For an existing table with them, use `REORG` to turn off and purge deletion vectors while enabling Iceberg reads. Afterwards, merges rewrite files instead of marking rows, which costs more write effort.
## Operational notes
Metadata generation is asynchronous and uses the writing compute; wait for it to complete before external clients query.
W: REORG while enabling Iceberg reads: it purges the vectors, enables the format, and fits the documented upgrade path, with column mapping and asynchronous metadata as conditions.
X: B=External table elsewhere: both managed and external tables in Unity Catalog support Iceberg reads, so no move is needed.
C=Keeping deletion vectors: the combination is not allowed on one table, so the property change is rejected rather than tolerated.
D=INSERT OVERWRITE: the existing vectors remain until purged, and replacing merges with overwrites changes the CDC design, rewriting far more data.
T: To expose a Delta CDC table to Iceberg readers, purge deletion vectors with REORG, enable column mapping, and expect asynchronous metadata.
V: Delta Lake, UniForm, Apache Iceberg

@ DBX-DEP D2 T2.2 advanced troubleshooting
S: A streaming job reads the change data feed of a source table and its checkpoint is lost. The engineer starts a new checkpoint with `startingVersion` set to a version from two months ago. The stream fails to start because that version is not available. How should the target be recovered?
A: Rebuild the target from a current full snapshot of the source, then start a new change feed stream on a new checkpoint at the snapshot version
B: Run `VACUUM` with a retention of zero hours, which recreates the missing change files from the transaction log
C: Set `startingVersion` to 0 so that the change feed replays the complete history from the first commit of the table
D: Reuse the lost checkpoint path with `startingVersion` unchanged, since an existing checkpoint path restores the stream offsets from all of the earlier runs
K: A
G: ## CDF is transient
Change data feed is not a permanent record of changes. Its records are kept only for a retention window; transaction log cleanup and `VACUUM` remove old versions and their change files, and once a version is gone its changes can no longer be read. For managed tables, history is cleaned up automatically, so a fixed starting version eventually becomes unavailable. A new stream with an unavailable `startingVersion` fails to start.
## Recovery pattern
- Re-establish the baseline: copy or merge a full snapshot of the source into the target (the table at a known version).
- Start a new stream from that version (or the current one) with a new checkpoint, and write with an idempotent merge.
- Monitor the lag so streams never fall behind the retention window.
Also: a corrupted checkpoint cannot be reused; the new stream needs a new checkpoint path.
W: Snapshot rebuild then a new stream: the target gets the missing state from the source table itself, and the feed continues from a version that still exists.
X: B=VACUUM with zero retention: vacuum deletes files and can never recreate missing change data; it makes the problem worse.
C=startingVersion 0: versions older than the retained history are gone, so the stream still fails to start.
D=Reusing the lost path: a lost or corrupted checkpoint holds no usable offsets; the databricks guidance is to write the new stream to a new checkpoint location.
T: Change data feed history expires; recover a lost checkpoint by reloading a snapshot and restarting the feed from a retained version.
V: Delta Lake, Change data feed
