@ DBX-DEP D1 T1.5 applied troubleshooting
S: A nightly job `refresh_dim` has one notebook task that failed after a short outage of the source system. The source is healthy again and the notebook is idempotent. The engineer opens the failed run and looks for the repair option to re-run only the failed work, but repair cannot be used. What explains this, and what should be done?
A: Repair needs the run to be canceled first, so the engineer cancels the failed run in the Jobs UI and then repairs it
B: Repair is blocked for tasks on serverless compute, so the task must move to a classic job cluster before the run is repaired
C: Repair is supported only for jobs that orchestrate two or more tasks, so the job is triggered again with Run now
D: Repair needs a task-level retry policy, so the engineer adds retries to the notebook task and then repairs the failed run
K: C
G: ## What repair run does
A repair run re-runs only the unsuccessful tasks of a multi-task job run (failed, canceled, or skipped because an upstream task failed) together with the tasks that depend on them. Successful tasks are not repeated, which saves time and compute. Unsuccessful tasks run again from their beginning with the current job and task settings, so a configuration fix is picked up.
- Repair is supported only with jobs that orchestrate **two or more tasks**.
- A failed single-task job is re-run by triggering it again with **Run now**.
- Lakeflow Jobs does not make tasks idempotent, so a task that wrote partial output can duplicate it when repaired. Here the notebook is idempotent, so a fresh run is safe.
## Example
Job `refresh_dim` has the single task `rebuild_dim`. The run failed on a source outage. There is nothing to repair selectively, so Run now starts a new run of the one task. If the job also had a `publish` task after `rebuild_dim`, a repair would re-run `rebuild_dim` and `publish` only.
W: Run now for a single-task job: repair exists only for jobs with two or more tasks, and with an idempotent notebook a new run gives the same result as a repair would.
X: A=Cancel first: repair applies to failed or canceled runs, so the run state is not the reason; the task count is.
B=Serverless block: a repair re-runs tasks on any compute with the current settings; compute type is not the condition.
D=Retry policy: retries are not a prerequisite of repair; the condition is the number of tasks, and a single-task job simply runs again with Run now.
T: Repair needs two or more tasks; a failed single-task job is re-run with Run now.

@ DBX-DEP D1 T1.6 advanced tradeoff
S: Raw order files land in cloud storage, and a lifecycle rule archives files older than 30 days out of the monitored path. The bronze layer must keep every order forever, and a gold dataset aggregates revenue by day and region from the silver layer in the same pipeline. Which choice of dataset types fits?
A: Bronze as a materialized view over the file path and gold as a materialized view, with a refresh policy that fails instead of running a full refresh
B: Bronze and gold both as streaming tables, because streaming tables recompute their aggregates when old input files are corrected or archived
C: Bronze as a view that holds the files' records and gold as a materialized view, because views persist rows even after the source files are removed
D: Bronze as a streaming table that ingests each file once and gold as a materialized view that recomputes the aggregate from the silver layer
K: D
G: ## Two processing models
A pipeline dataset is either a streaming table or a materialized view (or an unpersisted view).
- A **streaming table** processes each input record once, as long as the source is append-only. Rows that were ingested stay in the table even if the source later loses them.
- A **materialized view** guarantees the result of the batch query over the current inputs. Its refresh may be incremental or a full recompute, but the answer always equals the query over what the source holds now.
## Why ingestion belongs in a streaming table
Databricks recommends streaming tables for ingestion and says not to define a materialized view over sources that should be processed once: ingest with Auto Loader, sources without history such as Kafka, and sources where data is deleted or archived after processing. A materialized view over archived files would lose rows at the next recompute. Aggregations and joins, where inputs can change, belong in materialized views.
Example: `CREATE OR REFRESH STREAMING TABLE bronze_orders AS SELECT * FROM STREAM read_files(...)` for ingestion, and `CREATE MATERIALIZED VIEW gold_revenue AS SELECT day, region, SUM(amount) ... GROUP BY day, region` for the aggregate.
W: Streaming table for ingestion and materialized view for aggregation: bronze keeps rows after the files are archived, and the gold result is kept consistent with the silver data.
X: A=Materialized view for bronze: a recompute reads only what the path still holds, so archived orders would disappear; a refresh policy only controls incremental or full behavior and does not protect rows.
B=Streaming tables for both: a streaming table handles each row once and is meant for append-only data, so it does not recompute aggregates when upstream data changes.
C=View for bronze: a view is evaluated on demand and not persisted, so it stores nothing and cannot keep history that the source no longer holds.
T: Ingest once into streaming tables; use materialized views where the result must stay correct for changing inputs.

@ DBX-DEP D1 T1.6 applied comparison
S: A streaming table `orders_enriched` joins a stream of orders with the `customers` dimension and stores `segment`. Marketing re-segments customers every month, and the revenue-by-segment report must show the current segment for all historical orders. The orders are in a Delta table that keeps all history. Which design satisfies the report?
A: Define the report dataset as a materialized view that joins the orders table with `customers`, so a dimension change causes the join to be recomputed
B: Keep the streaming table and shorten the trigger interval, so a changed customer segment is picked up by the next microbatch for all earlier orders
C: Keep the streaming table and join it to a second streaming table that stores `customers` with SCD Type 2 history, matching on the key only
D: Keep the streaming table and add a watermark on the order timestamp, so rows are re-joined while they are inside the watermark delay
K: A
G: ## Joins in streaming tables do not recompute
In a stream-static join, each order row is joined once, with the dimension as it is at that moment. If the dimension changes later, rows that were already written are not touched. That is "fast but wrong" when the report must reflect the current dimension.
A **materialized view** is always correct at the time of its update: Databricks recomputes the join when the dimension changes (incrementally when the query supports it) and the result equals the batch query over the current tables.
## Choosing
- Dimension changes must flow into old rows: materialized view.
- Point-in-time attribution is wanted (segment at the time of the order): streaming table, or a dimension with SCD Type 2 and a join on the validity interval.
- Large inputs where a recompute is too costly: streaming table, accepting the point-in-time semantics.
W: Materialized view join: the engine recomputes the join result when `customers` changes, so every historical order carries the current segment without reprocessing the stream by hand.
X: B=Shorter trigger interval: a faster microbatch still joins only new order rows; previously written rows are never revisited, so older orders keep the old segment.
C=SCD Type 2 dimension joined on key: every order matches all historical versions of a customer, which duplicates rows and double counts revenue, and the stream join still does not revisit old rows.
D=Watermark: a watermark bounds state for stream-stream operations and late data; it does not re-join rows that were already emitted.
T: Use a materialized view when dimension changes must reach historical rows; stream-static joins in streaming tables never recompute.

@ DBX-DEP D1 T1.6 advanced troubleshooting
S: A materialized view computes `SELECT account_id, SUM(amount) AS total FROM main.pay.txns GROUP BY account_id` on a large Delta table where `amount` is `DOUBLE`. It runs in a serverless pipeline and a small share of rows change per day, yet each refresh recomputes everything and the cost is high. The planning information of the event log reports a full recompute. What is the most likely repair?
A: Switch the pipeline to classic compute with Photon, because incremental refresh of floating-point sums is implemented only on classic clusters
B: Convert the materialized view into a streaming table so that the sum is kept per row and never needs a recompute of the table
C: Set the refresh policy to FULL, so the cost becomes predictable and the floating-point result no longer varies between refreshes
D: Cast the summed value to a decimal type in the query, and enable row tracking on the source table so the engine can plan an incremental refresh
K: D
G: ## When a materialized view cannot refresh incrementally
Incremental refresh runs only on serverless pipelines (classic pipelines always recompute fully). Even there it is best effort: Databricks examines the cost and the query and may choose a full recompute, but the output is the same either way.
- Summing `FLOAT` or `DOUBLE` values (SUM, AVG, covariance) gives results that depend on the order of addition, so the engine cannot update the previous result incrementally and plans a full refresh. Casting to `DECIMAL`, for example `SUM(CAST(amount AS DECIMAL(18,2)))`, makes the aggregate deterministic.
- Some incremental operations need **row tracking** on the source tables; deletion vectors improve performance.
## How to check
The pipeline event log has `planning_information` events that say whether a flow was planned as incremental or as a full recompute, and the reason.
W: Decimal aggregate with row tracking: the nondeterministic floating-point sum is what forces the full refresh, and the decimal cast plus row tracking on the source lets the engine plan an incremental one.
X: A=Classic compute: incremental refresh needs serverless; classic pipelines always recompute materialized views completely, so this makes the cost problem worse.
B=Streaming table: an aggregate over all history in a streaming table needs unbounded state without a watermark, and it would not reflect updates or deletes in the source.
C=FULL policy: it makes the full recompute permanent. The cost is predictable but remains high, and the repeatable result is not a reason for a full refresh.
T: Floating-point sums force full recomputes of materialized views; cast to decimal and enable row tracking.

@ DBX-DEP D1 T1.6 advanced tradeoff
S: A materialized view over a large fact table refreshes hourly in about 4 minutes because it is refreshed incrementally. After a source table was recreated without row tracking, the next refresh silently fell back to a full recompute that took two hours and breached the SLA and budget. The team wants the refresh to fail loudly instead of recomputing when incremental refresh is not possible. Which setting does that?
A: The refresh policy AUTO, which chooses by cost and stops the update when a full recompute would exceed the previous duration
B: The refresh policy INCREMENTAL STRICT, which requires incremental refresh and fails the refresh when incrementalization is not possible
C: The refresh policy INCREMENTAL, which prefers incremental refresh and raises an error when the query plan no longer supports it
D: The refresh policy FULL, which separates full recomputes from the hourly schedule so they cannot delay the incremental ones
K: B
G: ## Refresh policies for materialized views
By default Databricks picks incremental or full refresh by cost and by what the query supports. A `REFRESH POLICY` in the definition makes this explicit:
- `AUTO` (default): cost-based choice between incremental and full.
- `INCREMENTAL`: prefer incremental, but fall back to a full refresh if the plan no longer supports incremental refresh.
- `INCREMENTAL STRICT`: incremental refresh is required; if it is not possible, the refresh (or the create) fails, so the owner can debug instead of paying for a full recompute.
- `FULL`: always full refresh.
Strict is recommended when cost or an SLA makes unexpected full refreshes unacceptable. Example: `CREATE MATERIALIZED VIEW mv REFRESH POLICY INCREMENTAL STRICT AS SELECT ...`.
W: INCREMENTAL STRICT: the update fails when incremental refresh is impossible, which turns the silent two-hour recompute into an alert the team can fix by re-enabling row tracking.
X: A=AUTO: it is the cost-based default that already produced the fallback; it has no rule that stops an update based on the previous duration.
C=INCREMENTAL: it is allowed to fall back to a full refresh when incrementalization becomes unavailable, which is exactly the behavior that caused the incident.
D=FULL: it performs a full refresh at every update, so the cheap hourly incremental refresh would be lost entirely.
T: Use INCREMENTAL STRICT when an unexpected full recompute must fail the update instead of running.

@ DBX-DEP D1 T1.6 applied use-case
S: Append-only clickstream events must feed 5-minute windowed counts that dashboards read within a few seconds of event arrival, around the clock, at a high event rate. Which design fits?
A: A streaming table with a windowed aggregation and a watermark, in a pipeline that runs continuously
B: A materialized view over the events table, refreshed by a scheduled triggered pipeline every minute
C: A standalone streaming table created in Databricks SQL and refreshed on a one-minute schedule
D: A streaming table with the same windowed aggregation but no watermark, in a continuous pipeline
K: A
G: ## Latency and dataset types
- A **streaming table** handles each row once and is good for low-latency streaming transformations that reason over rows and windows. Stateful operations need a naturally bounded stream or a **watermark**, otherwise state grows without limit and the pipeline can fail from memory pressure.
- A **materialized view** is not designed for low latency: refresh latency is seconds to minutes, because each refresh is an update of a triggered pipeline.
- **Pipeline mode** is independent of the dataset type. Triggered suits updates every 10 minutes to daily; continuous fits freshness between about 10 seconds and a few minutes. Refreshes of standalone streaming tables and materialized views always run in triggered mode.
## Applying it
Windowed counts with a watermark keep the state bounded: windows older than the watermark delay are finalized and dropped from state.
W: Streaming table, watermark, continuous mode: rows are processed as they arrive, the watermark bounds the window state, and continuous mode avoids waiting for scheduled updates.
X: B=Triggered materialized view: every refresh is a pipeline update with start-up and planning time, and materialized views target seconds-to-minutes latency, not a few seconds around the clock.
C=Standalone streaming table on a schedule: standalone refreshes always use triggered pipeline mode, so freshness is limited by the schedule and update overhead.
D=No watermark: the window state of an unbounded stream is never finalized, so memory use grows until the pipeline fails.
T: Low-latency windowed streaming is a streaming table with a watermark in continuous mode, not a scheduled materialized view.

@ DBX-DEP D1 T1.6 applied troubleshooting
S: Kafka events (topic retention is seven days) are ingested into the streaming table `bronze_events`, which holds all history. The streaming table `silver_events` reads `bronze_events`. An engineer changes the silver query from `SELECT id, LOWER(email) AS email` to also `TRIM` the value. After deployment only new rows are trimmed; older rows still have spaces. What is the safest way to correct all rows?
A: Run a default refresh again, since Databricks detects the changed query and reprocesses the rows that were produced by the old definition
B: Run a full refresh of the whole pipeline, so that every table is rebuilt with the same definition and nothing stays inconsistent
C: Run a full refresh of `silver_events` only, because its source `bronze_events` still holds the complete history
D: Reset only the checkpoints of the silver flow, which makes the table rewrite its existing rows with the new definition
K: C
G: ## Streaming tables see each row once
A change to a streaming table query affects only rows processed after the change; existing rows are not rewritten. To reprocess history there are three refresh semantics for streaming tables:
- **Refresh (default)** processes new records only.
- **Full refresh** clears the table data and the flow checkpoints and reprocesses all records from the source. It can drop records if the source no longer holds them.
- **Reset checkpoints** (selected flows, through the REST API) clears only the checkpoints and keeps the data, so the source is read again and appended next to the old rows.
## Choosing the scope
Select the tables for the full refresh. The silver table can be rebuilt because its source is a Delta table with all history. A full refresh of `bronze_events` would empty it and re-read Kafka, which holds only seven days, so older events would be lost for good.
W: Full refresh of silver only: the table is cleared and rebuilt from bronze, which still holds the whole history, and bronze keeps its Kafka data.
X: A=Default refresh: it only processes new records, so rows written by the old query stay as they are.
B=Whole pipeline: this includes `bronze_events`, which would be cleared and re-read from a topic that only retains seven days, so older events would be lost permanently.
D=Checkpoint reset: the data is kept and the source is read again, so every row is appended a second time next to the old untrimmed rows instead of replacing them.
T: Full refresh only the downstream streaming table whose source keeps the full history; never full refresh a table whose source has expired data.

@ DBX-DEP D1 T1.7 advanced troubleshooting
S: A Debezium topic is applied with `create_auto_cdc_flow(..., keys=["id"], sequence_by="source_ts", apply_as_deletes=expr("op = 'd'"), stored_as_scd_type=1)`. Delete events from one connector carry `source_ts = NULL`, while every event has a numeric `log_position` that grows with the source order. Deletes are not applied correctly. What is the best fix?
A: Set `ignore_null_updates=True` on the flow, so that a NULL `source_ts` keeps the stored sequence value of the key
B: Sequence by a column that is never NULL and follows the source order, such as `log_position`, or a struct that starts with it
C: Replace the NULL with `current_timestamp()` in the source view, so that a delete always sorts after the earlier updates
D: Leave the NULL values in place, because the flow sorts NULL sequence values first and applies those deletes before any update
K: B
G: ## Requirements for the sequence column
`AUTO CDC` (formerly APPLY CHANGES) applies events in the order of the `sequence_by` column, not in arrival order. The column must be sortable, must be a monotonically increasing representation of the correct event order, and must have **one distinct update per key at each sequencing value**. `NULL` sequencing values are not supported.
- A delete event is an event like any other: it needs a real sequence value so that the flow can decide whether it is newer than the stored row.
- A struct such as `SEQUENCE BY STRUCT(log_position, source_ts)` orders by the first field and breaks ties with the next one.
- `ignore_null_updates` is about the attribute columns of an update, not about the sequence column.
## Example
Delete for key 7 with `log_position = 1042` and `source_ts = NULL`. Sequencing by `log_position` gives the delete a defined place after the update at 1041.
W: Non-null source-order sequence: every event, including deletes, gets a defined position in the source order, which the flow requires.
X: A=Ignore NULL updates: the option controls whether NULL attribute values overwrite stored columns; it does not give a NULL sequence value a position.
C=Processing time: a value assigned in the pipeline follows arrival, not the order of changes in the source, so a late old event would look newest.
D=Leave NULL: NULL sequencing values are not supported, so the flow cannot rely on any placement of those events.
T: The AUTO CDC sequence column must be non-null and follow the source order for every event, deletes included.

@ DBX-DEP D1 T1.7 advanced use-case
S: A customer-profile CDC feed sends updates that contain only the changed attributes; unchanged `phone` and `email` arrive as NULL. The attribute `status` is always sent with its full current value, and NULL is a real value that must be able to clear it. The target is an SCD Type 1 table. Which configuration protects `phone` and `email` without blocking NULL for `status`?
A: Set `ignore_null_updates_column_list=["phone", "email"]` on the flow, so only those two columns keep their value when NULL arrives
B: Set `ignore_null_updates=True` for the flow, because it keeps existing values for every column when the incoming value is NULL
C: Leave the default and add `expect_or_drop("phone IS NOT NULL")` expectations, so records with a missing phone never reach the target
D: Set `except_column_list=["phone", "email"]`, which makes the flow apply updates only to the remaining columns
K: A
G: ## NULL handling in AUTO CDC
By default a matching change event overwrites target columns with the values of the event, including NULL. For sources that send **partial updates**, the flow can ignore NULL values so existing values survive:
- `ignore_null_updates=True` (SQL `IGNORE NULL UPDATES`) applies to all columns.
- `ignore_null_updates_column_list` (SQL `IGNORE NULL UPDATES ON columnList`) limits it to the listed columns; the other columns still apply explicit NULL.
- `ignore_null_updates_except_column_list` (SQL `IGNORE NULL UPDATES ON * EXCEPT (cols)`) does the opposite.
`except_column_list` and `column_list` decide which columns exist in the target; they are unrelated to NULL handling.
## Trade-off
A column that ignores NULL can no longer be cleared by an event; use the column list so only attributes that arrive partially get this protection.
W: Column-level NULL ignoring: `phone` and `email` keep their stored values when NULL arrives, and `status` still takes NULL as an explicit new value.
X: B=Flow-wide setting: it also ignores NULL for `status`, so a legitimate clearing of the status would never reach the target.
C=Expectation on phone: it drops whole records with a missing phone, including valid updates that change only another column, so those changes are lost.
D=Except column list: it removes the two columns from the target schema, so the phone and email values would not exist in the table at all.
T: Use the column-list variant of ignore-null so that only partially delivered columns are protected from NULL overwrites.

@ DBX-DEP D1 T1.7 applied tradeoff
S: A customer dimension is maintained with `create_auto_cdc_flow(..., stored_as_scd_type="2")`. The column `last_seen_at` changes daily for every active customer, so the history table grows by millions of versions, although analysts only need the history of address and tier changes and the current `last_seen_at`. What is the best change?
A: Switch the flow to `stored_as_scd_type=1`, because Type 1 still keeps the history of address and tier changes in the target
B: Use `except_column_list=["last_seen_at"]`, which keeps history for the other columns
C: Filter out events in which only `last_seen_at` changed before the flow, since those events never need to reach the target
D: Add `track_history_except_column_list=["last_seen_at"]`, so changes to that column update the current version in place
K: D
G: ## Which columns create new versions
In an SCD Type 2 target, every change to any tracked column closes the current version (`__END_AT` is set) and opens a new one (`__START_AT`). By default all columns are tracked. With `track_history_column_list` (the columns to track) or `track_history_except_column_list` (the columns to exclude, `TRACK HISTORY ON * EXCEPT (...)` in SQL), changes to the other columns update the current row in place instead.
## Why not the alternatives
- SCD Type 1 keeps no history at all.
- `column_list` and `except_column_list` change which columns exist in the target.
- Pre-filtering a stream cannot compare the event with the target and would leave `last_seen_at` stale.
W: Untracked column: with `last_seen_at` excluded from history tracking, its daily changes update the current version in place, so history grows only for address and tier changes.
X: A=SCD Type 1: it overwrites rows and keeps no previous versions, so the address and tier history that analysts need would be gone.
B=Excluding the column from the target: `last_seen_at` would no longer exist in the dimension, but the current value is still needed.
C=Pre-filtering events: a stream filter cannot tell whether other columns changed without looking at the target, and the dropped events would leave the current `last_seen_at` stale.
T: In SCD Type 2 flows, exclude volatile columns with track-history options so they update in place without new versions.

@ DBX-DEP D1 T1.7 applied troubleshooting
S: A pipeline applies a Kafka CDC topic into an SCD Type 1 table with `sequence_by = F.current_timestamp()` added by an upstream view. Messages from different partitions arrive out of order, and users see that old values sometimes replace newer ones in the target. What is the root cause and fix?
A: The sequence follows processing time, not source order, so use a source column such as the commit position as `sequence_by`
B: AUTO CDC applies events in arrival order unless the target is SCD Type 2, so switch to `stored_as_scd_type=2`
C: The micro-batches are too large for sorting, so the trigger interval should be reduced until each batch holds one event per key
D: Late events should be removed by a watermark on the processing timestamp, so only on-time events reach the target
K: A
G: ## Order of events versus arrival
AUTO CDC compares the `sequence_by` value of an event with the value stored for the key. An older event (lower sequence value) arriving after a newer one is ignored in SCD Type 1, and in SCD Type 2 it is placed in the right position of the history. This works only when the sequence column carries the **true order of changes in the source**: a database log sequence number, a commit version or a monotonically increasing source timestamp with tie-breaker.
- A value assigned at processing time (`current_timestamp()`) gives later-arriving events a higher value, so a delayed old event looks newest.
- Out-of-order handling is built into the API; no watermark or custom dedupe logic is needed.
W: Source-order sequence: processing time makes late messages look newest, and a source-provided order lets the flow discard or reposition them correctly.
X: B=SCD Type 2: sequence-based ordering applies to both types; with a processing-time sequence the history would simply record wrong validity intervals.
C=Smaller batches: ordering uses the sequence column, not batch boundaries, so smaller batches would not fix a sequence that follows arrival time.
D=Watermark on processing time: a watermark discards data by event-time lateness; with a processing timestamp it removes nothing meaningful and the flow still orders events by arrival.
T: Sequence AUTO CDC by a column that reflects the source order of changes, never by processing time.

@ DBX-DEP D1 T1.7 applied definition
S: A customer table is built with `AUTO CDC` as SCD Type 2 and `apply_as_deletes = expr("op = 'DELETE'")`. Customer 42 has a current version with `__START_AT = 2`. A `DELETE` event for key 42 arrives with sequence value 6. What does the target contain, and how do analysts select the customers that are active now?
A: The current version of customer 42 keeps its row and receives `__END_AT = 6`; active customers are the rows where `__END_AT IS NULL`
B: The rows of customer 42 are physically removed, as in SCD Type 1, so all remaining rows in the table are active customers
C: A new row for key 42 with NULL attributes and `__START_AT = 6` is added, and the active ones are the highest `__START_AT` per key
D: The delete is rejected, because SCD Type 2 targets do not support `apply_as_deletes`, so deletes must be handled outside the flow
K: A
G: ## Deletes in SCD Type 2
An SCD Type 2 target stores one row per version with `__START_AT` and `__END_AT`, which receive the sequence values of the events. The current version has `__END_AT = NULL`.
- A delete event **closes** the current version by setting `__END_AT` to the delete's sequence value; history rows stay.
- Customers that are active now are the rows with `__END_AT IS NULL`; time travel over validity is a filter such as `__START_AT <= t AND (__END_AT IS NULL OR t < __END_AT)`.
- To handle out-of-order data in SCD Type 2, a deleted row may be kept temporarily as a tombstone in the underlying table, with a view hiding it.
- `apply_as_truncates` (full-table truncate) is supported only for SCD Type 1.
W: Closed version: the delete sets `__END_AT` on the existing row, so history is retained and a null end date marks active customers.
X: B=Physical removal: that is SCD Type 1 behavior; in Type 2 the earlier versions are history and must stay.
C=Tombstone row: AUTO CDC does not add an all-NULL version; it closes the current one, and the latest `__START_AT` of a key would wrongly still look active.
D=Rejected: `apply_as_deletes` is supported with SCD Type 2; only the truncate option is limited to Type 1.
T: In SCD Type 2 a delete closes the current version by setting `__END_AT`; active rows are those with a null end.

A: Apply a compute policy that allows the cache commands, because serverless honors policies for the Spark caching APIs
B: Use `df.cache()` or `df.persist()` for the reused DataFrame, and write the intermediate result to a Delta table instead of `df.checkpoint()`
C: Rewrite the notebook in Scala, because serverless notebooks support the full cache and checkpoint API for Scala code
D: Replace the catalog call with the SQL statement `CACHE TABLE dim_customer`, which serverless accepts in place of the API
K: B
G: ## Caching on serverless compute
Serverless compute does not support some cache and lineage APIs; using them raises an exception.
- Not supported: `df.checkpoint()`, `spark.catalog.cacheTable()`, `uncacheTable()`, `clearCache()`, and the SQL commands `CACHE TABLE`, `UNCACHE TABLE`, `REFRESH TABLE` and `CLEAR CACHE`.
- Supported: `df.cache()`, `df.persist()` and `df.unpersist()`.
- Serverless does not support compute policies, and Scala and R are not supported in notebooks.
## Example
`df = spark.table("dim_customer").persist()` replaces `cacheTable`; `df.write.mode("overwrite").saveAsTable("main.tmp.stage")` followed by a read replaces `checkpoint()` as the way to cut the lineage.
W: DataFrame persist plus a Delta table: both are supported on serverless and cover the caching and lineage-cutting needs of the notebook.
X: A=Compute policy: serverless has no compute policies, and policies would not change the list of unsupported APIs.
C=Scala: Scala is not supported in serverless notebooks, so this does not run at all.
D=CACHE TABLE: the SQL command is on the same unsupported list as the catalog API.
T: On serverless use persist() and tables instead of cacheTable, CACHE TABLE and checkpoint().
V: Serverless compute

@ DBX-DEP D1 T1.10 applied troubleshooting
S: Two notebook tasks of one job exchange intermediate data. The first runs `CREATE GLOBAL TEMPORARY VIEW stage_orders AS ...` and the second reads `global_temp.stage_orders`. This works on a shared job cluster but fails after the tasks move to serverless compute. What is the recommended approach?
A: Share the data through a table, because serverless does not support global temporary views and each task runs in its own environment
B: Replace the global temporary view with a session temporary view, because both tasks of a job share one session on serverless
C: Pass the view's rows to the second task through task values, because they carry any volume of data between tasks
D: Pin both tasks to the same serverless environment version, because the version decides which temporary views are shared
K: A
G: ## Passing data between tasks
Global temporary views are not supported on serverless compute. Databricks recommends session temporary views or tables when data must be passed across sessions.
- Each job task runs in an isolated environment, so a session temporary view of one task is not visible in another task.
- A table (Unity Catalog managed table or Delta table) persists the data and works for any size.
- Task values carry small scalar results (a count, a path) between tasks; they are limited in size and are not a data transport.
## Example
Task 1 ends with `df.write.mode("overwrite").saveAsTable("main.tmp.stage_orders")`; task 2 starts with `spark.table("main.tmp.stage_orders")`.
W: Table as hand-off: it survives the end of the first task, is visible to the second task and does not depend on global temporary views.
X: B=Session view: a session temporary view lives in one session, and each task has its own isolated environment, so the second task cannot read it.
C=Task values: they are meant for small values and have a size limit; they are not a way to pass tables.
D=Environment version: the version defines the base libraries and runtime, not the sharing of temporary views between tasks.
T: Serverless has no global temporary views; hand data between tasks through tables.
V: Serverless compute
