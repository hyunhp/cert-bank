@ DBX-DEP D5 T5.4 advanced use-case
S: Compliance requires the full row-level change history of `core.accounts` for three years. A data engineer proposes to keep the change data feed enabled and let auditors query `table_changes('core.accounts', 0)` whenever they need it. Which design meets the requirement?
A: Run a daily `readChangeFeed` stream with the `availableNow` trigger and its own checkpoint that appends the change rows to a separate history table kept for three years
B: Keep the proposal and raise the table's log and file retention periods to three years, so that the change data feed is retained as the permanent record of every change
C: Schedule a nightly job that records the current table version number, because any earlier version can later be read with `VERSION AS OF` and compared by auditors
D: Keep the proposal but start every audit query at `startingVersion` 0, because the change data feed of a managed table is never removed from the transaction log
K: A
G: ## The change data feed is transient
Change data feed (CDF) records row-level changes with `_change_type`, `_commit_version` and `_commit_timestamp`. It is meant for incremental processing, not as an archive.
- The feed only exists for table versions that still exist. The transaction log removes old versions at regular intervals, and with legacy CDF the change data files follow the table's retention policy, so `VACUUM` deletes them.
- A version that has been cleaned up can no longer be read through the feed, and a start version that is no longer in the history makes a new stream fail to start.
## Archiving for permanent history
When a permanent history is needed, write the changes to a table of their own with incremental logic. A stream over `readChangeFeed` with `trigger(availableNow=True)` processes everything available since the last run and stops, which suits a daily or hourly job.
```
(spark.readStream.option("readChangeFeed", "true").table("core.accounts")
  .writeStream.option("checkpointLocation", cp)
  .trigger(availableNow=True).toTable("audit.accounts_history"))
```
The history table is an ordinary table: its retention is a business decision, and it survives cleanup of the source's log.
W: Archive with availableNow: the stream copies each change into an append-only history table, so the three-year record no longer depends on how long the source keeps its versions.
X: B=Longer retention: Databricks states that a change data feed is not intended to serve as a permanent record, and stretching log and file retention for years bloats the source table and slows its metadata instead of creating an audit table.
C=Version numbers only: time travel needs the old versions to still exist, and the same cleanup that removes feed data also removes those versions, so a stored number does not preserve any history.
D=Start at version 0: versions are removed from the history at regular intervals, so a start at 0 fails or loses early changes, and managed tables clean up historic versions automatically.
T: The change data feed is transient, so archive it into its own table with an availableNow stream when a permanent audit history is required.
V: Delta change data feed, Structured Streaming

@ DBX-DEP D5 T5.4 advanced troubleshooting
S: Legacy change data feed (`delta.enableChangeDataFeed`) on the managed table `sales.orders` was switched off for two weeks during a migration and then switched on again. Downstream teams now need the row-level changes of exactly that two-week interval, and `table_changes` over those versions does not return them. The table has row tracking enabled and meets the other requirements for automatic change data feed. What is the correct way to get the changes?
A: Re-enable legacy change data feed and call `table_changes` again over the interval, because the feed is rebuilt from the transaction log for versions that were committed while it was off
B: Rebuild the interval with `spark.read.option("readChangeFeed", "true")` and a `startingTimestamp` from two weeks ago, because a timestamp bypasses the legacy table property
C: Unset `delta.enableChangeDataFeed` so that automatic change data feed is used, and then query the interval through `table_changes` or `readChangeFeed`
D: Run `FSCK REPAIR TABLE` on the table so the missing change data files of the interval are regenerated from the data files that were committed
K: C
G: ## Two ways to produce a change data feed
- **Legacy CDF** materializes the change records at write time and needs `delta.enableChangeDataFeed = true` on each table. Only changes committed while the property was on exist as change data.
- **Automatic CDF** computes the changes when the table is read, using row tracking on Delta tables (or row lineage on Iceberg v3). It needs no per-table switch, so the question "was it on at that time" does not arise.
## The gap
If legacy CDF is turned off for some interval and turned on again, that interval is not queryable through the legacy feed. Databricks recommends moving to automatic CDF, and the documented way to read the changes of such an interval is automatic CDF. The two modes cannot be used together, so the migration step is to unset `delta.enableChangeDataFeed`:
```
ALTER TABLE sales.orders UNSET TBLPROPERTIES ('delta.enableChangeDataFeed');
SELECT * FROM table_changes('sales.orders', 120, 160);
```
The reading APIs (`table_changes`, `readChangeFeed`) stay the same, so consumers need no code change.
W: Switch to automatic CDF: it derives changes from row tracking at read time, so the interval is queryable, and the same `table_changes` and `readChangeFeed` APIs keep working.
X: A=Re-enable legacy CDF: legacy change data is written at commit time, so turning the property on later cannot create change records for commits made while it was off.
B=Timestamp start: the start option only selects a range of versions. The legacy feed still has no change data for the interval, and the table property is not bypassed by using a timestamp.
D=FSCK REPAIR TABLE: it removes transaction log entries that point to files that no longer exist. It does not generate change data files for old commits.
T: A gap in legacy change data feed is not recoverable through the legacy feed; automatic change data feed derives the changes from row tracking at read time.
V: Delta change data feed

@ DBX-DEP D5 T5.4 applied troubleshooting
S: A scheduled SQL task keeps its own `last_version` value and every hour runs `SELECT * FROM table_changes('sales.orders', ${last_version} + 1)` to load new changes. During quiet hours, when no commit has happened since the previous run, the query fails with `timestampGreaterThanLatestCommit`. The task must remain a batch SQL task that manages its own version bookmark. What is the smallest correct fix?
A: Start the next read at `last_version` instead of `last_version + 1`, so that the start is never beyond the latest commit and an empty hour no longer fails
B: Set an ending version that equals `last_version`, because a closed range that ends at the latest commit is accepted even when no new commit exists
C: Run `OPTIMIZE` on the source table before each read so that a new commit exists and moves the latest version beyond the saved bookmark
D: Enable `spark.databricks.delta.changeDataFeed.timestampOutOfRange.enabled` so that a start version beyond the last commit returns an empty result instead of an error
K: D
G: ## Version ranges in batch reads
`table_changes(name, start[, end])` reads the changes between versions or timestamps. Start and end are **inclusive**, and a batch read must give a start. By default, a version or timestamp that exceeds the last commit raises `timestampGreaterThanLatestCommit`.
A job that stores the last processed version and asks for `last_version + 1` asks for a version that does not exist yet when nothing was committed, which is the error case.
## Tolerating out-of-range input
Setting `spark.databricks.delta.changeDataFeed.timestampOutOfRange.enabled = true` changes the behavior:
- A start beyond the last commit returns an empty result.
- An end beyond the last commit returns all changes from the start to the last commit.
A streaming read with `readChangeFeed` would track versions through its checkpoint, but that changes the design that the task must keep.
W: Out-of-range tolerance: with the setting on, a start beyond the latest commit returns zero rows, so the quiet hour is an empty load and the bookmark logic stays unchanged.
X: A=Start at last_version: start versions are inclusive, so the last commit would be read again every hour and its changes applied twice.
B=Closed range: it does not remove the error, because the start version (`last_version + 1`) still exceeds the last commit, and an end version below the start is not a valid range.
C=OPTIMIZE: compaction does not change data, so it is not a way to produce changes, and forcing a commit for every run only adds writes to work around a read option.
T: To keep a batch bookmark design, enable the change data feed out-of-range tolerance so an empty interval returns no rows; remember that start versions are inclusive.
V: Delta change data feed

@ DBX-DEP D5 T5.5 advanced troubleshooting
S: The query profile of a dashboard query on a SQL warehouse shows a join that reads 3 million rows from `orders` and 50,000 rows from `customers` and outputs 900 million rows. A performance insight of the type `EXPLODING_JOIN` is attached. The business expects roughly one output row per order. Which action addresses the cause?
A: Increase the warehouse size so that the large intermediate result of the join fits into memory and the sort stage stops spilling
B: Check whether the join key is unique on the `customers` side, then deduplicate it or tighten the join condition so each order matches one row
C: Add a `BROADCAST(customers)` hint to the join, because broadcasting the smaller side prevents the row count of the join output from growing
D: Raise `spark.sql.shuffle.partitions` so that the 900 million output rows are spread over more tasks and each task finishes sooner
K: B
G: ## What an exploding join is
A join is exploding when it produces many more rows than it reads. The query profile shows the row counts per operator, and the `EXPLODING_JOIN` insight flags this pattern. The result size is a logical problem, not a resource problem.
Typical causes:
- A join key that is not unique on the side that should be a lookup (duplicates in a dimension, for example after a slowly changing dimension load that kept all versions).
- A missing part of a composite key, which turns the join into a many-to-many match.
## Fix the logic first
The recommendation is to decide which subset of the result is needed and then change the join condition or reduce the input rows of both relations. In the case above, one order should match one customer, so verify uniqueness of the key and deduplicate (or add the missing key part or filter such as the current-row flag). Resources and join strategy only make a wrong result faster or slower to produce.
W: Fix the join logic: the output is far above the input because a key matches several rows, so make the lookup side unique or complete the join condition.
X: A=Bigger warehouse: it adds memory but still computes 900 million rows. The row explosion is a data or logic defect, not a lack of memory.
C=Broadcast hint: the hint changes the physical join strategy (no shuffle of the small side). The number of matching rows and thus the output size stays the same.
D=More shuffle partitions: this spreads the same exploding result over more tasks. It does not reduce the output, and it does not remove the duplicate matches.
T: An EXPLODING_JOIN insight points to duplicate or incomplete join keys; correct the join logic instead of adding compute.
V: Databricks SQL, query profile

@ DBX-DEP D5 T5.5 advanced troubleshooting
S: The query profile of a selective query on a wide external Delta table shows a scan that reads nearly all files although the filter `tenant_id = 'T-4471'` should match a small part of the data. A `COVERAGE_STATS_DELTA` insight reports the statistics status of the filter as Unavailable. The table has 140 columns and `tenant_id` is column 97. Which fix lets data skipping work for the existing files?
A: Add `tenant_id` to `delta.dataSkippingStatsColumns` and run `ANALYZE TABLE ... COMPUTE DELTA STATISTICS` so that statistics are recomputed for the existing files
B: Run `OPTIMIZE ... ZORDER BY (tenant_id)`, because the sort order alone provides the statistics that data skipping uses for the filter
C: Move `tenant_id` into the first position of the schema with `ALTER TABLE`, because data skipping statistics are collected for existing files in column order
D: Set `delta.dataSkippingStatsColumns` to include `tenant_id` only, because changing the property rewrites the statistics of all files that are already in the table
K: A
G: ## Where data skipping statistics come from
Delta collects per-file statistics (minimum and maximum values, null counts and record counts) when data is written. At query time these statistics let the engine skip files that cannot match a filter. For Unity Catalog external tables, statistics are collected by default for the **first 32 columns** of the schema. A filter on a later column has no statistics, so the query falls back to in-file filtering and reads (almost) everything. The `COVERAGE_STATS_DELTA` insight reports exactly this.
## Fixing it
- Name the columns that matter with the table property `delta.dataSkippingStatsColumns` (or change `delta.dataSkippingNumIndexedCols`).
- The property only affects data written afterwards. Recompute statistics for existing files with `ANALYZE TABLE t COMPUTE DELTA STATISTICS`.
- For Unity Catalog managed tables, predictive optimization also collects statistics for frequently filtered columns, which is one reason managed tables need less manual work.
`ZORDER` columns need statistics too, so ordering does not replace them.
W: Property plus ANALYZE: the property makes `tenant_id` a statistics column, and the ANALYZE command computes its statistics for files that were written before the change.
X: B=ZORDER only: Z-ordering colocates data, but it relies on statistics collected for the column, and `tenant_id` has none, so skipping cannot use the layout.
C=Reordering the schema: moving a column in a wide table does not recompute statistics of existing files, and a schema change is a disruptive way to tune statistics.
D=Property alone: setting the property only changes future statistics collection. Files already in the table keep their old statistics until they are recomputed.
T: Data skipping needs file statistics on the filter column; set the statistics columns and recompute them with ANALYZE for existing files.
V: Delta Lake data skipping

@ DBX-DEP D5 T5.5 advanced troubleshooting
S: A SQL warehouse query aggregates `GROUP BY country` over a table in which about 70% of the rows have `country IS NULL`. The query profile shows the aggregation stage dominated by a few tasks, and a `DATA_SKEW` insight is attached. Adaptive query execution is on. A colleague suggests a skew join hint. Which action fits the situation?
A: Add `/*+ SKEW('events') */` to the query, because adaptive execution splits skewed aggregation partitions only when the hint is present
B: Raise `spark.sql.shuffle.partitions`, because a larger number of partitions divides the rows of the single hot grouping key among more tasks
C: Pre-aggregate in two stages: group by `country` and a random salt first, then combine the partial results so several tasks share the hot key
D: Enlarge the warehouse until the longest task fits, because skew is a lack of parallel capacity and disappears when more cores are available
K: C
G: ## Skew in an aggregation
In a shuffle, all rows with the same grouping key go to the same partition. When one key holds most of the rows, one task receives most of the data, and the stage lasts as long as that task. In the query profile this shows up as a shuffle or aggregate operator with a large share of the time and memory, and the `DATA_SKEW` insight.
## What helps and what does not
- AQE splits skewed partitions of **sort merge joins and shuffle hash joins** automatically. It does not split the hot key of a plain aggregation.
- More shuffle partitions do not help, because one key still hashes to one partition.
- A larger warehouse adds cores, but the hot partition is still handled by one task.
- The documented remedies for the insight are **key salting or pre-aggregation**: aggregate partial results by `(key, salt)` first, then aggregate the partials by key. The hot key is spread over several tasks, and the second stage handles only small partial results.
W: Salting or pre-aggregation: the first stage spreads the hot key over several partitions, and the second stage merges small partial sums.
X: A=Skew hint: skew join handling applies to joins. An aggregation has no join to optimize, so the hint has nothing to act on.
B=More shuffle partitions: all rows with the same key still hash to one partition, so the largest task does not become smaller.
D=Bigger warehouse: more cores let the other tasks finish quickly, but the one task with the hot key still runs the same amount of work.
T: Skew in a GROUP BY is fixed by salting or pre-aggregation; AQE skew handling covers joins, and more partitions or cores do not split a hot key.
V: Databricks SQL, adaptive query execution

@ DBX-DEP D5 T5.5 advanced troubleshooting
S: A report query joins a fact table with a dimension table and sorts the result. Its profile shows a `DATA_SPILL` insight. The warehouse size is fixed by a platform policy and cannot be changed. The intermediate result carries a 4 KB `raw_payload` string per row that the report never displays. Which change addresses the spill without touching the warehouse?
A: Increase the maximum number of clusters of the warehouse, because additional clusters give each running query a bigger share of memory
B: Select only the needed columns before the join and sort, so that `raw_payload` is not carried through memory-heavy operators
C: Enable the query result cache for the report, so that the join and sort operators no longer need memory when the query runs again
D: Add filters on the clustering keys of the fact table, because clustering keys control how much memory is reserved for sort operators
K: B
G: ## Spill in the query profile
A spill means an operator (sort, aggregate, join) needed more memory than it had and wrote data to disk. The `DATA_SPILL` insight and the memory-peak metric of the operator show it. The recommendations are: increase the warehouse size to add memory, or reduce the rows, columns, or size of large columns (strings, arrays, maps, structs) that the operators hold.
## Why width matters
Memory use of a sort or hash operator grows with the size of each row. A 4 KB string that is never displayed is carried through every shuffle, join and sort. Dropping it before those operators (explicit column list instead of `SELECT *`, or selecting from the fact table only what is needed) lowers the memory peak without any compute change. The `WIDE_PROJECTION` insight is the same idea for scans.
W: Project only needed columns: the large string is not loaded into the join and sort, so the memory peak falls and the operators stay in memory.
X: A=More clusters: additional clusters absorb more concurrent queries (they address queueing). A single query still runs on one cluster with the same memory.
C=Result cache: it may skip a repeated query entirely, but the first execution and every cache miss still spill, so the cause remains.
D=Filtering on clustering keys: filters on clustering keys can reduce the bytes read, but clustering keys do not reserve sort memory, and the row width stays the same.
T: Spill is addressed by more memory per query or by carrying fewer rows and narrower columns through the memory-heavy operators.

@ DBX-DEP D5 T5.5 applied troubleshooting
S: At 09:00 dozens of dashboards refresh at the same time on one SQL warehouse. The query profile of a slow dashboard query shows an `EXCESSIVE_QUEUE_TIME` insight. Its execution time is short, and the wall-clock duration is dominated by the time the query waited. Which change targets this bottleneck?
A: Increase the maximum number of clusters of the warehouse, so that more clusters can start and queries wait less for free capacity
B: Switch the tables to liquid clustering, because clustering removes the queue that forms in front of the scan operators
C: Increase the shuffle partitions of the warehouse, because more partitions shorten the time that queries wait for an execution slot
D: Collect Delta statistics on the dashboard tables, because statistics prevent queries from being queued behind long-running scans
K: A
G: ## Reading the time breakdown
The query details show the wall-clock duration split into scheduling, query optimization and file pruning, and execution. A query can be slow without being expensive: when most of the time is spent waiting, the cost is in the **queue**, not in the operators.
## Queueing is a capacity problem
A warehouse cluster runs a limited number of queries at once. If more arrive, they queue until capacity frees up. `EXCESSIVE_QUEUE_TIME` recommends raising the **maximum number of clusters**, so that the warehouse can scale out under concurrent load. This is different from the warehouse **size**, which makes a single query faster but does not add concurrency in the same way.
Layout fixes (clustering, statistics) reduce the work of a query, which helps a little, but they do not address why the query waited before it started.
W: More maximum clusters: the warehouse can scale out for the 09:00 burst, so queries start sooner instead of waiting for capacity.
X: B=Liquid clustering: it improves file skipping inside scans. The query waited before any operator started, so the layout of the table is not the bottleneck.
C=Shuffle partitions: this setting controls the number of partitions after a shuffle in a running query. It has no influence on admission to the queue.
D=Delta statistics: statistics improve data skipping and join planning. They do not change how many queries a warehouse admits at once.
T: EXCESSIVE_QUEUE_TIME is a concurrency problem; raise the maximum number of clusters rather than tuning the query.

@ DBX-DEP D5 T5.5 applied troubleshooting
S: An engineer runs the same slow report query a second time to capture its profile, but the query history shows the run without a query profile. Nothing was changed between the runs, and the first run had a profile. What is the explanation and the way to get a profile?
A: The second run was answered from the query cache, which has no profile, so a trivial change such as changing or removing the `LIMIT` forces a real execution

W: Cached result: the identical rerun was served from the query cache, so no operators ran; altering the statement slightly forces execution and a new profile.

@ DBX-DEP D5 T5.5 advanced tradeoff
S: The profile of a daily BI query shows a broadcast hash join, and the query details list the insight `HISTORY_BASED_JOIN_STRATEGY` with the label Accelerated. The query previously used a sort merge join with a shuffle of the large table. An engineer wants to make the join strategy permanent by adding a `BROADCAST` hint on the small side. What should the engineer conclude?
A: Add the hint, because the Accelerated label means the optimizer will drop the broadcast again as soon as the hint is missing from the statement
B: Replace the hint with a `SHUFFLE_HASH` hint, because a broadcast chosen from earlier runs is unstable and a shuffle strategy is safer
C: Leave the query unchanged, because the optimizer chose broadcast from earlier runs; a hint would force it even if that side grows
D: Disable adaptive query execution, because only then will the engine keep the join strategy that the history-based optimization selected
K: C
G: ## Applied accelerations
The query profile lists two kinds of insights. Most are recommendations for the user. The **applied accelerations**, shown with an Accelerated label, report optimizations that Databricks has already applied and need no action. `HISTORY_BASED_JOIN_STRATEGY` means the join was optimized with measurements from earlier runs of similar queries, so a broadcast was used instead of a shuffle based on the workload history.
## Hints versus the optimizer
- A `BROADCAST(t)` hint forces a broadcast of that side **regardless of the autoBroadcastJoinThreshold**. If the table grows later, a forced broadcast can exhaust memory or slow the query.
- Without the hint, the optimizer decides again from statistics and history, so the strategy follows the data.
- Hint priority when sides are hinted differently: `BROADCAST` over `MERGE` over `SHUFFLE_HASH` over `SHUFFLE_REPLICATE_NL`.
Use a hint when the optimizer is demonstrably wrong and statistics cannot be fixed, not to freeze a good decision.
W: No change: the Accelerated label reports a decision already taken from measured history, and leaving it out lets the strategy adapt when the table sizes change.
X: A=Hint as a safeguard: nothing in the insight says the optimization depends on a hint. The optimizer applies the history-based choice by itself on later runs.
B=SHUFFLE_HASH hint: it also forces a strategy, and it would bring back a shuffle of the large table that the broadcast removed, so the query would get slower.
D=Disabling AQE: AQE can convert joins at runtime. It is a separate feature, and switching it off would remove adaptive optimizations without any benefit here.
T: An Accelerated insight needs no action; avoid forcing a broadcast with a hint when the optimizer already picks it from measured history.

@ DBX-DEP D5 T5.5 advanced comparison
S: An engineer runs `EXPLAIN` on a slow query and sees a `SortMergeJoin` over a large and a 12 MB table, but the query profile of the real run shows a broadcast hash join. The engineer suspects that the profile is wrong. Which statement explains the difference?
A: `EXPLAIN` does not run the query, so adaptive execution cannot re-optimize it and shows the initial plan, while the executed query changed the join from actual sizes
B: The profile is rendered from compile-time estimates, while `EXPLAIN` prints statistics measured during execution, so the explain output is reliable
C: Adaptive query execution is switched off for queries that are explained, and it switches itself on only for SQL warehouses that are running in serverless mode
D: A join strategy is fixed when the table statistics are collected, so one of the two outputs belongs to an older run of the query with a different data volume
K: A
G: ## Initial plan and final plan
Before a query runs, the optimizer builds a plan from estimates. Adaptive query execution (AQE) re-optimizes while the query runs, using the real sizes at the end of each shuffle or broadcast exchange. One of its capabilities is to **convert a sort merge join to a broadcast hash join** when one side turns out to be small (a runtime threshold applies), for example after filters made it smaller than estimated.
## Seeing which plan you look at
- `SQL EXPLAIN` does not run the query, so AQE cannot change anything. It shows only the **initial plan**.
- `DataFrame.explain()` shows the initial and the current plan under an `AdaptiveSparkPlan` node; the `isFinalPlan` flag is `true` after the query finished, and statistics show `isRuntime=true` once a stage has run.
- The query profile and the Spark UI describe what was executed.
Comparing the initial and final plans shows what AQE did: a different join node means the strategy was changed.
W: Initial versus executed plan: EXPLAIN stops before execution, so it cannot contain AQE's runtime change, which the query profile of the real run does show.
X: B=Reversed roles: the profile reflects the execution with measured metrics. EXPLAIN without running contains only compile-time estimates.
C=AQE switched off for EXPLAIN: AQE is on by default and applies to supported queries. EXPLAIN simply does not execute, so there is nothing to adapt.
D=Strategy fixed by statistics: statistics only inform the initial plan. AQE can still change the strategy at runtime, so both outputs can come from the same run.
T: SQL EXPLAIN shows the initial plan; the join changes made by AQE appear only in the executed plan or query profile.

@ DBX-DEP D5 T5.6 advanced tradeoff
S: A managed table of about 8 TB receives device telemetry. Most queries filter on `device_id` (several million distinct values) and on a recent range of `event_date`. A team member proposes `PARTITIONED BY (device_id)` plus a nightly `OPTIMIZE ... ZORDER BY (event_date)`. Which design should the lead recommend?

- Identity functions such as `is_account_group_member()` are resolved **once during query analysis**, not per row, and several calls result in a single Unity Catalog call.
- Use `TO` and `EXCEPT` to decide who is subject to the policy. Excepted principals skip the function completely.
Therefore a 90-million-row user-by-store lookup is the wrong design. Model the entitlement as groups (for example one group per region), keep the function a simple CASE on group membership and the tagged column, and leave administrators out through `EXCEPT`.
W: Groups and identity functions: membership is resolved once per query, the function is a cheap CASE, and exempt principals do not run it.
X: B=Python UDF: Databricks recommends SQL functions, since a Python UDF cannot be inlined or optimized, and caching in it does not solve a per-row lookup.
C=Table-level filters: the same function would run per row on every table, and moving it removes the consistency of tag-based policies.
D=Bigger warehouse: a table of this size is not broadcast by adding memory, and a large lookup prevents the broadcast join the guidance relies on.
T: Keep ABAC functions simple SQL, avoid large lookup tables, use group membership and TO/EXCEPT for principals.
V: Unity Catalog ABAC

@ DBX-DEP D6 T6.2 advanced use-case
S: Ingestion teams create new tables in the schema `landing` every week, and some are not classified by a steward for days. During that time unclassified columns holding personal data are readable. The governance lead wants a design under which untagged new data is protected by default. Which approach follows the ABAC best practices?
A: Rely on a weekly audit of tag changes in the audit log and revoke access for any table found without classification
B: Create a column mask policy on the catalog for columns tagged `pii`, since every new column holding personal data will carry that tag once teams follow the tagging standard
C: Tag the schema `classification = unverified`, which new tables inherit, and add a policy restricting tables with that value until a steward changes it
D: Add a table-level column mask to each new table through a trigger, because table-level masks apply earlier than ABAC policies
K: C
G: ## Fallback rules for unclassified data
ABAC policies only protect what their tags describe, so missing tags leave data unprotected. The best-practice answer is a **default restrictive tag**:
- Apply a default governed tag such as `classification = unverified` where new objects appear. Tables inherit governed tags from their parent catalog or schema (column tags do not inherit from the table).
- Create a policy whose condition matches the default value, for example a row filter that returns no rows to everyone except the stewards in `EXCEPT`.
- A steward reviews the table and changes the tag to its real value, which lifts the restriction and activates the specific policies.
```
CREATE POLICY quarantine_unverified ON SCHEMA landing
ROW FILTER sec.deny_all TO `account users` EXCEPT `data_stewards`
FOR TABLES WHEN has_tag_value('classification', 'unverified');
```
Audits find the gap after the fact. A policy keyed on the personal-data tag fails exactly in the unclassified case, because the tag is the thing that is missing.
W: Default unverified tag with a restrictive policy: new tables are closed automatically, and classification by a steward opens them.
X: A=Weekly audit: it detects exposure after it happened and relies on people to revoke, so the unprotected window remains.
B=PII mask on the tag: the policy matches only columns that already carry the tag, so the unclassified columns are the ones it does not cover.
D=Trigger-created masks: table-level masks are per-table configuration, which is the sprawl ABAC is meant to avoid, and they are not applied earlier than policies.
T: Protect unclassified data by default with a restrictive governed tag value and a policy that matches it.
V: Unity Catalog ABAC, governed tags

@ DBX-DEP D6 T6.2 advanced use-case
S: A governance team wants the `data_stewards` group to classify columns in the schema `crm` with the governed tag `pii`. Stewards must not read table data, change policies, or become table owners. Which privileges give them exactly this ability?
A: `ASSIGN` on the governed tag `pii` alone, because the tag policy is the only control that decides who may set the tag on objects
B: `MANAGE` on the schema `crm`, because managing a schema includes assigning every governed tag to the objects in it
C: Ownership of every table in `crm`, because tags can only be set by the owner of the object, and policies stay with the catalog owner and the metastore admins
D: `APPLY TAG` on `crm` (inherited by its tables) and `ASSIGN` on the governed tag, plus the usage privileges to reach the objects
K: D
G: ## Two permissions for a governed tag
Tagging is a security boundary in ABAC: whoever sets a tag decides which policies apply. For that reason applying a governed tag needs two things:
- `APPLY TAG` on the securable object (applicable to tables, views, volumes and others, and grantable on a schema or catalog to be inherited), and
- `ASSIGN` on the governed tag itself, which the tag policy manages and which can restrict the allowed values.
Neither implies the other. `APPLY TAG` is not `SELECT`, so stewards can classify without reading data, and it is not `MANAGE`, so they cannot create or change policies (that needs `MANAGE` on the securable and `EXECUTE` on the function). Usage privileges (`USE CATALOG`, `USE SCHEMA`) are still needed to reach objects.
```
GRANT APPLY TAG ON SCHEMA crm TO `data_stewards`;
-- plus ASSIGN on the governed tag `pii`, managed in the tag's permissions
```
W: APPLY TAG plus ASSIGN: the first allows tagging objects without data or policy rights, the second allows using the governed tag.
X: A=ASSIGN alone: it allows using the tag, but setting a tag on an object also needs `APPLY TAG` on that object.
B=MANAGE on the schema: it includes the right to create policies and change grants, which stewards must not have, and it does not replace ASSIGN on the governed tag.
C=Ownership: owning tables would let stewards change grants and drop tables, which far exceeds tagging, and tags do not require ownership.
T: Setting a governed tag needs APPLY TAG on the object and ASSIGN on the tag, so stewards can classify without data or policy rights.
V: Unity Catalog governed tags, ABAC

@ DBX-DEP D6 T6.2 advanced troubleshooting
S: A nightly Spark job read `prod.hr.employees` as files with `spark.read.format("delta").load("s3://acme-hr/employees")`. After a platform team attached ABAC column mask policies to the catalog (the table now has tagged columns), the job fails. The job must keep processing the same data, and the masks must stay in force for the job's identity. What is the correct change?
A: Add the job's service principal to the `EXCEPT` clause of the policies, because exempt principals can read the files of a table directly
B: Grant the service principal `READ FILES` on the external location, because file access to the table path is then allowed and masked by the policy engine for that principal
C: Remove the governed tag from the columns during the job's run window and apply it again afterwards, so that the path is accessible
D: Read the table by its name `prod.hr.employees` so the engine enforces the masks; path-based access to tables with policies is not supported
K: D
G: ## Why path access is blocked
Row filters and column masks are enforced by the engine when a table is queried through Unity Catalog. Reading the underlying files directly would bypass them, so Databricks lists **path-based access to files of tables with policies as not supported**. That applies to table-level filters and masks and to ABAC policies alike.
## The fix
Move the job to name-based access:
```
df = spark.table("prod.hr.employees")
```
The job then needs the table privileges (`SELECT`, `USE CATALOG`, `USE SCHEMA`) and sees masked values unless the policy lists the principal in `EXCEPT` for a legitimate reason. Exempting a principal is a governance decision about data exposure, not a way to restore a file path. Changing tags during a run window would expose the data to everyone else for that time.
W: Name-based access: the engine applies the policies, which is the only supported way to read a table that has row filters or column masks.
X: A=EXCEPT: it changes who sees masked values. It does not make a path-based read of a policy-protected table supported.
B=READ FILES: it is a storage privilege on the external location, and it would be the very bypass that policies are meant to prevent.
C=Remove the tag: this turns the protection off for every user during the window, and it still leaves the path-based design in place.
T: Tables with ABAC policies must be read by name; path-based file access to them is not supported.
V: Unity Catalog ABAC
