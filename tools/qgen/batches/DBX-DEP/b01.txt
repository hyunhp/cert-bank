@ DBX-DEP D1 T1.1 advanced use-case
S: A repository hosts several bundles. The bundle in `bundles/orders/` has its `databricks.yml` there, and its jobs import a package `common_transforms` that lives in `libs/common_transforms/`, outside the bundle folder. After `bundle deploy` the job fails with `ModuleNotFoundError` because the shared folder never reaches the workspace. Which change makes the shared code deploy with the bundle while keeping one copy in the repository?
A: Add `../../libs` to the top-level `include` mapping so the CLI treats the shared folder as part of the bundle configuration
B: Add a `../../libs/**` glob to `sync.include`, because include globs may reach any folder in the repository
C: Set `workspace.root_path` to the repository root so the CLI uploads every parent folder of the bundle with it
D: Add `../../libs` and `.` to the `sync.paths` mapping so the shared folder is synchronized next to the bundle root
K: D
G: ## What a bundle deploys
`databricks bundle deploy` uploads the files under the bundle root (the folder with `databricks.yml`) to the workspace, minus anything excluded by `.gitignore` and `sync.exclude`. Three similarly named mappings control different things, and mixing them up is a classic project-structure mistake:
- `include` (top level) lists additional bundle **configuration** files, for example `resources/*.yml`. It never selects code.
- `sync.include` and `sync.exclude` **filter** files that are already inside the synchronized folders.
- `sync.paths` selects the **folders** to synchronize and may point outside the bundle root.
## Sharing code across bundles in a monorepo
When a path in `sync.paths` traverses above the bundle root, the CLI determines a common ancestor so the folder structure stays intact. With `paths: [../../libs, .]` the workspace receives `libs/` and `orders/` side by side, so a job can add the sibling folder to its import path. `include` and `exclude` globs are applied afterwards, relative to the bundle root.
W: sync.paths: it is the mapping meant for synchronizing folders outside the bundle root, so listing the shared folder and the bundle root deploys both with their relative layout intact and keeps a single copy in the repository.
X: A=Top-level include: this mapping only lists extra YAML configuration files for the bundle, so the shared package would never be uploaded as code.
B=sync.include glob: include and exclude only filter files within the folders selected for synchronization, and a glob relative to the bundle root does not add a folder that is not synchronized.
C=workspace.root_path: this setting is the destination folder in the workspace where the bundle is deployed, not a switch that widens what is uploaded from the local repository.
T: Use `sync.paths` to deploy shared folders outside the bundle root; `include` is for config files and `sync.include/exclude` only filter.

@ DBX-DEP D1 T1.1 applied troubleshooting
S: A team splits its bundle into `databricks.yml` plus `resources/ingest.job.yml` and `resources/silver.pipeline.yml`. `databricks bundle validate` reports no errors, and `databricks bundle deploy` completes, but the workspace shows neither the ingest job nor the silver pipeline from those files. A job declared directly in `databricks.yml` was created normally. What is the most likely cause?
A: The `databricks.yml` file has no `include` mapping that references the `resources/` files, so the CLI never reads their definitions
B: The resource files must be listed under `sync.include`, because only synchronized files contribute resources to the deployment
C: The resources folder needs a `bundle.resources.yml` index file that lists every resource file by its absolute workspace path
D: Resources defined outside `databricks.yml` are created only when the deploy command is run with the `--force` flag
K: A
G: ## One entry file, many configuration files
A bundle has exactly one entry file, `databricks.yml`. Other configuration files take part in the bundle only when the top-level `include` mapping references them, using globs relative to the file that declares them. A typical layout is:
`include:` followed by `- resources/*.yml`
Files that exist in the repository but are not matched by `include` are simply not parsed, so validation passes and nothing from them is deployed. That is why the failure is silent, and why a project that grows past one file should add the include glob at the same time as the first split.
## Separate concerns
The `sync` mappings decide which **files** are uploaded (source code, notebooks), while `include` decides which **YAML** contributes resource definitions. They are independent.
W: Missing include mapping: aside from `databricks.yml`, every configuration file must be matched by the top-level `include` array, otherwise its jobs and pipelines are not part of the bundle and are never deployed.
X: B=sync.include: that mapping filters which source files are uploaded to the workspace, and it has no influence on which configuration files define resources.
C=Index file: no bundle.resources.yml index exists; the documented mechanism for pulling in other configuration files is the include mapping with relative globs.
D=Force flag: the force option only overrides checks such as Git branch validation; resources from referenced files are deployed without it, and unreferenced files are not read even with it.
T: Only `databricks.yml` is read automatically; every other bundle YAML must be matched by the top-level `include`.

@ DBX-DEP D1 T1.1 advanced troubleshooting
S: A bundle builds an internal package with `artifacts: {etl_lib: {type: whl, build: uv build --wheel}}`, and a serverless job task installs the resulting wheel. Developers merge a bug fix, CI redeploys the bundle, yet the job keeps running the old behavior. The `version` in `pyproject.toml` is unchanged at 0.1.0 and nobody bumps it by hand. Which bundle setting solves the problem without a manual version bump?
A: Set `dynamic_version: true` on the artifact, so the wheel version is patched from the build timestamp
B: Set `max_retries` on the task, so a failed run reinstalls the wheel on the next attempt
C: Run `bundle deploy --force` in CI, which makes the CLI remove all cached environments for the target
D: Move the wheel to a `pypi` library entry with the same name, so the job resolves the newest build from the default pip index each time
K: A
G: ## Why the same version stays stale
Serverless compute caches the virtual environment of a task, and job tasks with the same dependency set share it within a run. Python resolves a wheel by name and version, so a rebuilt wheel that still says `0.1.0` looks identical to what is already installed or cached. The documentation states that when you change a custom package used by a serverless job you must also update its version number so the job picks up the new implementation.
## Dynamic version for artifacts
For artifacts of `type: whl`, the setting `dynamic_version: true` makes the CLI patch the wheel version from the timestamp of the built file during deployment. New code can then be deployed without editing `pyproject.toml` or `setup.py`. It is valid only for wheel artifacts.
W: dynamic_version: it rewrites the wheel version on every deploy, so the changed implementation arrives with a new version and the cached environment no longer matches.
X: B=Retries: a retry runs the same environment with the same wheel version, so it cannot pick up the new build.
C=Force flag: this option overrides checks like the Git branch validation; it neither alters the wheel version nor clears serverless environment caches.
D=PyPI entry: the wheel is an internal build artifact and is not published to the default index, so a pypi library entry would not find it, and it would not fix the unchanged version either.
T: A rebuilt wheel with an unchanged version is not reinstalled; use `dynamic_version: true` or bump the version.

@ DBX-DEP D1 T1.1 applied troubleshooting
S: A bundle keeps third-party dependencies in `pyproject.toml` under `[project] dependencies`. Jobs get them through an environment that installs the project. A developer adds `rapidfuzz` there, and the Lakeflow Pipelines pipeline in the same bundle still fails with `ModuleNotFoundError: rapidfuzz` after redeploying. Which fix follows the documented pattern for pipelines?
A: Add a `%pip install rapidfuzz` line at the top of the pipeline source file
B: Declare it in the pipeline's `environment` section, for example as an editable install of `${workspace.file_path}`
C: Attach a cluster-scoped init script to the pipeline compute that runs `pip install rapidfuzz`
D: Call `dbutils.library.restartPython()` at the end of the first source file so the pipeline reloads its Python path
K: B
G: ## Pipelines resolve dependencies differently from jobs
For job tasks, a bundle can install the project through an environment or libraries entry. For Lakeflow Pipelines, the template for `pyproject.toml` carries a warning: pipeline dependencies are cached during development, so you add them to the **`environment`** section of the pipeline definition instead.
A bundle pipeline definition can therefore contain:
`environment:` with `dependencies:` and the entry `--editable ${workspace.file_path}`
This installs the deployed project and, with it, every dependency in `pyproject.toml`. Pinning versions is recommended so a runtime upgrade cannot change results silently.
## What pipelines do not support
Pipelines do not support restarting the Python process manually, and serverless pipelines do not support init scripts. Installing at runtime also prevents the reuse of cached libraries across runs.
W: Pipeline environment: declaring the dependency (or an editable install of the deployed project) in the pipeline's environment settings is the documented way, and it allows cached libraries to be reused across updates.
X: A=Runtime pip install: pipelines expect dependencies to be declared in the environment settings; installing during execution bypasses the cache and is not the supported pattern.
C=Init script: serverless pipelines do not support init scripts, and even on classic compute the documentation recommends environment settings instead because init scripts raise the risk of runtime-upgrade issues.
D=restartPython: pipelines do not support manually restarting the Python process, so this call cannot make a missing package appear.
T: In a bundle, pipeline dependencies belong in the pipeline `environment` section, not in runtime installs or restarts.

@ DBX-DEP D1 T1.1 applied tradeoff
S: A security review finds that the team stores `.whl` files used by production jobs in the DBFS root, where any workspace user can overwrite them. The jobs are defined in a bundle and must keep installing the same internal packages. Which target location fits the recommendation?
A: A folder on the DBFS root with a cluster policy that blocks library installs by ordinary users
B: A public PyPI project with the same name, so the jobs no longer depend on any workspace storage for the package
C: A Unity Catalog volume writable only by the release service principal, referenced as a `/Volumes/...` path
D: The notebook-scoped `%pip` cache of each job cluster, which is rebuilt from nothing on every run
K: C
G: ## Where library files should live
Libraries can still be read from the DBFS root on older runtimes, but any workspace user can modify files there. Storing libraries in the DBFS root is therefore deprecated and disabled by default on current runtimes. The documented recommendations are workspace files, Unity Catalog volumes, or a package repository; cloud object storage is the fallback.
## Why volumes fit production
A Unity Catalog volume is governed by privileges (`READ VOLUME`, `WRITE VOLUME`), so only the release process needs write access and jobs need read access. In a bundle, the job `libraries` entry then uses a `whl` mapping with a path such as `/Volumes/main/default/my-volume/my-wheel-0.1.0.whl`, or the bundle builds and uploads the wheel as an artifact.
W: Unity Catalog volume: privileges on the volume restrict who can replace the wheel, and the job library entry can point at the `/Volumes/...` path.
X: A=DBFS root plus policy: a cluster policy governs cluster settings, not who can write to the DBFS root, so any workspace user could still replace the files.
B=Public PyPI: publishing internal packages publicly exposes proprietary code and replaces access control with an open registry; it also does not address the DBFS risk with a governed store.
D=Notebook-scoped cache: notebook-scoped libraries are reinstalled each session and are not a storage location for the package files that jobs install from.
T: Keep production wheels in a governed location such as a Unity Catalog volume, not in the DBFS root.

@ DBX-DEP D1 T1.1 advanced tradeoff
S: A platform team needs one ingestion job per source table (about 40 tables). Each job needs its own schedule, owner permissions and alerts, and the table list lives in a metadata file that changes weekly. Copy-pasting 40 YAML blocks is rejected. Which approach fits?
A: A single job with a For each task over the table list, because every table then gets its own schedule and permissions in the Jobs list
B: `bundle generate job` run once per table, committing the output and rerunning it whenever the metadata changes
C: Python support for bundles, with a function that reads the metadata file and creates one job resource per table during deployment
D: A single notebook that creates jobs through the Jobs API at the start of each run, so no job exists in the bundle
K: C
G: ## Deploy-time versus run-time repetition
There are two ways to repeat logic across many tables:
- **Run time**: a For each task inside one job iterates over inputs. It is one job with one schedule, one permission set and one alert configuration.
- **Deploy time**: Python support for bundles can create resources dynamically from metadata while the bundle is deployed, and can also modify resources defined in YAML or Python. Each generated resource is a normal job with its own schedule, permissions and notifications, and it can coexist with hand-written YAML resources.
When the requirement is separate, individually governed jobs defined from data, deploy-time generation keeps everything under version control. When one orchestration with shared settings is enough, For each is simpler.
W: Python support for bundles: a function that reads the metadata and returns one job per table creates real, separately configurable jobs at deploy time while staying in the bundle.
X: A=For each task: it loops inside one job, so the tables share a single schedule, permission set and alert setup, which contradicts the per-table requirements.
B=bundle generate: the command snapshots an existing workspace resource into YAML once; it does not derive new resources from a changing metadata file and leaves 40 YAML files to maintain.
D=Jobs API from a notebook: jobs created at run time live outside the bundle, so they are not versioned, validated or removed by bundle commands.
T: Use deploy-time generation (Python for bundles) for many governed jobs from metadata and For each for repetition inside one job.

@ DBX-DEP D1 T1.2 advanced troubleshooting
S: A serverless job task installs an internal data-quality package from a volume. The package declares `pyspark==3.5.1` as a dependency. The task now fails during setup, and the session ends before any notebook code runs. What should the engineer do?
A: Remove the library that brings in PySpark from the task environment, since the serverless environment already provides Spark
B: Pin the package to the exact PySpark version of the runtime so that the installed copies are identical
C: Reinstall PySpark in the first notebook cell with `%pip install --force-reinstall`, so the pinned copy replaces the preinstalled one
D: Increase the memory of the task, because the extra PySpark download exhausts the environment
K: A
G: ## Serverless supplies Spark
On serverless compute, Spark is part of the managed environment. The documentation warns not to install PySpark, or any library that installs PySpark as a dependency, in serverless notebooks or tasks: doing so stops the session and produces an error. The fix is to remove the library and reset the environment.

Libraries that run on Databricks should list PySpark as a development or optional dependency, not a hard runtime requirement. The same package then installs on serverless, on classic clusters (which also bring their own PySpark), and in tests that install PySpark locally.
W: Remove the PySpark-pulling library: the managed environment already contains Spark, and a second PySpark install breaks the session, so the dependency must not be installed.
X: B=Pinning to the runtime version: the problem is a second installation of PySpark, not a version mismatch; an identical version is still installed over the managed one.
C=Forced reinstall in a cell: installing PySpark at all is what stops the session on serverless, and task dependencies are resolved before any cell runs, so a cell cannot repair the setup failure.

@ DBX-DEP D1 T1.2 advanced troubleshooting
S: A serverless job installs `fastvector-1.4-cp311-cp311-manylinux_x86_64.whl`, which contains compiled C extensions. Some runs succeed, others fail during dependency installation with an architecture error, and the Python code itself never starts. Which change makes the environment reliable?
A: Add a retry policy with a longer interval
B: Provide wheels for both `x86_64` and `aarch64`, each with a `platform_machine` marker, or a pure-Python wheel
C: Select a larger instance type for the task, because the larger family always uses the CPU architecture of the wheel
D: Install the wheel at runtime with `%pip` after checking `platform.machine()` in the first cell of the notebook
K: B
G: ## Serverless does not pin a CPU architecture
A serverless notebook or job can run on `aarch64` or `x86_64`, and the architecture can change between runs. A wheel with native extensions is a prebuilt binary for one architecture, so installation fails whenever the compute lands on the other one. This explains the symptom: intermittent, install-time failures with unchanged code.
## Options that work
- Prefer **pure-Python wheels** (`py3-none-any`).
- Otherwise list both architecture variants as dependencies and constrain each one with an environment marker, for example `fastvector @ <x86 wheel path>; platform_machine == 'x86_64'` and the same for `aarch64`.
Dependencies are resolved before any user code runs, so the notebook cannot repair this afterwards.
W: Both architecture wheels with markers: the resolver then picks the matching binary on every run, and pure-Python wheels avoid the problem entirely.
X: A=Retries: the architecture can change between runs, so a retry may pass by luck, but the underlying mismatch stays and failures keep returning.
C=Larger instance type: serverless compute does not offer instance type selection, and no instance size guarantees an architecture.
D=Runtime pip install: dependencies for a serverless task are resolved before the code runs, and an inline check cannot change which binary the environment installed.
T: Serverless may run on either CPU architecture, so native wheels need both variants with `platform_machine` markers.

@ DBX-DEP D1 T1.2 advanced troubleshooting
S: A Lakeflow Pipelines pipeline written in Python must call a vendor library that ships as a JAR (JVM). The engineer first tries an init script on classic compute to copy the JAR onto the classpath, and the pipeline behaves unpredictably. What is the right way to handle the requirement?

Lakeflow Pipelines supports SQL and Python only. JVM libraries are not supported: installing them, for example with an init script, causes unpredictable behavior and may break with future pipeline releases. Python libraries may still be installed through the environment settings.

Lakeflow Jobs can run a JAR or notebook task on suitable compute and write the result to a Unity Catalog table. A later pipeline task then reads that table as a source. The dependency stays out of the pipeline runtime, and the job's task order makes the handoff explicit.
W: Separate task writing to a table: the JVM library runs where it is supported, and the pipeline consumes governed output without needing the JAR.

@ DBX-DEP D1 T1.3 advanced use-case
S: A scoring step applies a 600 MB ML model to 800 million rows with a pandas UDF. The current scalar `pd.Series -> pd.Series` UDF loads the model from a volume inside the function body, and executors spend most of their time deserializing the model. Which design removes the repeated load?
A: An iterator pandas UDF that loads the model once before looping over the batches
B: A row-at-a-time Python UDF that loads the model into a module-level global on the first row it sees in each task
C: A pandas UDF that reads a broadcast variable holding the model, created once on the driver
D: A Series-to-scalar pandas UDF so that each group of rows is scored by a single model call
K: A
G: ## Pandas UDF flavors
A pandas (vectorized) UDF transfers data with Apache Arrow and runs on batches of rows. There are variants:
- **Series to Series**: the function is called per batch, so any initialization in the body repeats for every batch.
- **Iterator of Series to Iterator of Series**: the function receives an iterator of batches and yields results. State such as a model can be initialized once before the loop, then reused for every batch in that task. Wrap it in `try/finally` or a context manager to release resources.
- **Series to scalar**: an aggregation, returning one value per group or window.
## Why not the others
PySpark UDFs on serverless compute and standard access mode clusters do not support broadcast variables, and a row-at-a-time UDF pays serialization cost per row.
W: Iterator pandas UDF: it initializes the model once per task before iterating, and still scores whole Arrow batches, so both the load cost and the per-row overhead disappear.
X: B=Row-at-a-time UDF with a global: Python UDFs serialize row by row, which is far slower than vectorized batches, and the global is only a workaround for the missing initialization hook.
C=Broadcast variable: broadcast variables are not supported for PySpark UDFs on serverless and standard access mode compute, so the design fails on common compute types.
D=Series-to-scalar UDF: this variant aggregates a group into one value, so it cannot return one prediction per input row.
T: Use an iterator pandas UDF when a UDF needs expensive one-time initialization such as loading a model.

@ DBX-DEP D1 T1.3 advanced troubleshooting
S: A Python UDF registered as `strlen(s)` fails with an error on null input. The query is `SELECT s FROM test1 WHERE s IS NOT NULL AND strlen(s) > 1`, and the author assumed the null check runs first. The failure appears only after a plan change. What is the supported fix?
A: Swap the two predicates so the null check appears to the right of the UDF call
B: Make the UDF handle null itself, or wrap the call in `CASE WHEN s IS NOT NULL THEN strlen(s) END`
C: Add a `/*+ ORDERED */` hint, which guarantees left-to-right predicate evaluation
D: Cache the table first, because a cached table is evaluated strictly in the written order of predicates
K: B
G: ## Spark SQL does not promise evaluation order
Spark SQL, including the DataFrame API, does not guarantee the order of evaluation of subexpressions. Operator inputs are not necessarily evaluated left to right, and `AND`/`OR` do not have guaranteed short-circuiting. The optimizer may reorder `WHERE` and `HAVING` predicates, so a UDF can be called with rows that a preceding predicate was supposed to exclude.
## Safe patterns
- Make the UDF itself null-aware.
- Use `IF` or `CASE WHEN` so the UDF is invoked only inside the branch where the input is valid.
W: Null-aware UDF or CASE WHEN: either one moves the null handling into the expression itself so it holds regardless of the optimizer's predicate order.
X: A=Swapping predicates: no order is guaranteed in either direction, so the problem would reappear after another plan change.
C=Hint: no such hint exists that fixes evaluation order of predicates; correctness cannot depend on the order the optimizer picks.
D=Caching: caching changes where data is read from, not the order in which Spark evaluates the predicates of the query.
T: Never rely on predicate order for UDF null checks; make the UDF null-safe or use CASE WHEN.

G: ## Two parameter styles
Tasks take parameters in one of two forms:
- **Key-value pairs**: notebook, SQL, Run Job, and Python wheel (keyword arguments). Job parameters are pushed down to these tasks automatically; if a task parameter shares a key with a job parameter, the job parameter takes precedence.
- **JSON array of strings**: Python script, Python wheel (positional arguments), JAR, Spark Submit and For each. The array content is passed as arguments, as if run from the command line. Job parameters are **not** pushed down automatically; reference them with the dynamic value `{{job.parameters.<name>}}`.
## Overriding at run time
Values given when triggering a run with the API or the run-now UI override the job parameter defaults. A default is not a security control, because users with CAN MANAGE RUN can override it.
