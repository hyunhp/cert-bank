@ DBX-DEP D2 T2.3 advanced tradeoff
S: A team ingests 120 SQL Server tables with Lakeflow Connect. Every table has a primary key, and the DBA warns that the source server has little spare capacity. Which source-side change feed should the team enable for the connector?
A: Change data capture on every table, because it records only that a row changed and is the lightest method for tables that have keys
B: Both change tracking and change data capture on every table, so the connector can merge the two feeds and cross-check each change
C: Change tracking on the database and its tables, because it records that rows changed with little source overhead and needs primary keys
D: Neither, because the ingestion gateway reads the SQL Server transaction log directly and needs no change feed on the source
K: C
G: ## Two ways to track changes in SQL Server
The Lakeflow Connect SQL Server connector reads a change feed that SQL Server itself maintains, so the source must be prepared before any pipeline runs.
- **Change tracking** records the fact that a row changed, not the sequence of operations. It requires a primary key on the table and adds little load to the source.
- **Change data capture (CDC)** records every operation and keeps a history of changes. It works for tables without a primary key, but it costs the source more (capture jobs, change tables).
Databricks recommends change tracking for every table that has a primary key, to keep the load on the source low. If both are enabled on a table, the connector uses change tracking, so enabling both only adds source overhead.
## Where this fits
SQL Server is the generally available relational connector in the guide's trio. The MySQL and PostgreSQL connectors were in Public Preview when this was written, and PostgreSQL has its own prerequisites (logical replication, a replication user, publications and replication slots).
W: Change tracking: it is the lightweight option for tables with primary keys and is the method Databricks recommends there, which fits a source with little spare capacity.
X: A=CDC for keyed tables: CDC captures every operation and has the larger impact on the source, so it is the heavier method, not the lighter one, and it is intended for tables without keys.
B=Both methods: when both are enabled the connector uses change tracking anyway, so the CDC half only adds capture work on the busy source with no benefit.
D=No change feed: the connector depends on SQL Server's own change tracking or CDC data, so skipping the source setup leaves nothing to read incrementally.
T: Use change tracking for keyed SQL Server tables to minimize source load; use CDC when a table has no primary key.

@ DBX-DEP D2 T2.3 advanced troubleshooting
S: A SQL Server table `audit_events` has no primary key and no unique index, and it is ingested with CDC. The destination holds fewer rows than the source because the source contains fully identical rows. The destination must keep one row per source row. What should the team do?
A: Set the `primary_keys` table option in the ingestion definition to a surrogate column, which the connector then uses as the key
B: Switch the table to change tracking, which copes with keyless tables by hashing the full row before applying each change
C: Run a full refresh of the destination table, which re-reads the source rows without collapsing duplicates into one row
D: Add a unique key or unique index, such as a surrogate identity column, to the source table and then refresh the table
K: D
G: ## How the connector picks a key
A managed database connector must apply updates and deletes to the destination, so it needs a key for every table. It decides on its own from the source:
- If the source table has a primary key, that key is used.
- Otherwise, if it has a unique key or unique index, that is used.
- Otherwise all columns except large objects become a bundled key. Rows that are identical in every such column are ingested as a single row.
The connector ignores the `primary_keys` table configuration option and always derives the key from the source table. The only way to keep identical rows apart is therefore to give them something that differs at the source.
## Why a refresh is needed
Rows already collapsed in the destination cannot be split again by the connector, so after the source gets its key the table is refreshed to rebuild it with the new key.
W: Source key then refresh: a unique key or unique index at the source gives each duplicate a distinct identity, and the connector derives its key from the source, so the rebuilt table keeps every row.
X: A=primary_keys option: the connector ignores this option and determines the key from the source table, so naming a surrogate column in the definition changes nothing.
B=Change tracking: change tracking requires a primary key on the table, so it cannot handle a keyless table and does not hash rows.
C=Full refresh alone: a refresh re-reads the same rows and applies the same bundled key, so the identical rows are collapsed again.
T: The connector derives the key from the source (primary key, unique index, or all non-LOB columns), so duplicates survive only if the source has a distinguishing key.
V: Lakeflow Connect, SQL Server

@ DBX-DEP D2 T2.3 advanced troubleshooting
S: During a maintenance window an engineer stopped the ingestion gateway of a SQL Server pipeline for several days, while the source keeps its change logs for only two days. After the gateway is restarted, the team wants to know what is needed to get correct data. Which statement is accurate?
A: The gateway resumes from its saved position and replays the missed changes from the source database backups, so no further step is needed
B: The missing changes are gone from the source logs, so the affected tables need a full refresh, and the gateway should stay in continuous mode afterward
C: The next ingestion pipeline update detects the gap and backfills it automatically with an incremental query on the source tables
D: Only the tables that changed during the outage must be refreshed, and the team can choose them by comparing row counts at the source
K: B
G: ## Why the gateway must keep running
In the gateway-based architecture, the ingestion gateway runs continuously on classic compute and reads the change logs of the source database. The ingestion pipeline (serverless) applies the extracted changes to the destination tables.
Databricks keeps track of what has been extracted and applied, so after a failure it resumes from that point, but only as long as the logs are still on the source. The gateway cannot be put on a custom schedule for this reason: if it is down longer than the source's log retention, changes are dropped.
## Repair
When changes have been dropped, a full refresh is required for all affected tables. Prevent it by not stopping the gateway manually and by setting source retention longer than the longest tolerable outage.
W: Full refresh and continuous gateway: the changes beyond retention no longer exist at the source, so the destination can only be rebuilt from a new snapshot, and continuous operation prevents a repeat.
X: A=Replay from backups: the connector reads the change logs kept by the source database and has no way to replay changes from database backups.
C=Automatic backfill: the pipeline only applies what the gateway extracted, and there is no incremental query that can recover changes that are no longer in the logs.
D=Refresh only changed tables: after dropped changes the documented repair is a full refresh of the affected tables, and a row-count comparison cannot prove that nothing else differs.
T: Never stop the gateway; if the outage exceeds source log retention, changes are lost and a full refresh of the affected tables is the only repair.

@ DBX-DEP D2 T2.3 advanced tradeoff
S: A product team wants SQL Server changes in the Delta tables within a few minutes, at the lowest cost that still meets this goal. An engineer proposes running the ingestion pipeline in continuous mode and stopping the gateway at night. Which design follows the connector's operating model?
A: Run the gateway continuously on classic compute, and trigger the serverless ingestion pipeline on a short schedule of a few minutes
B: Run the ingestion pipeline in continuous mode, and start the gateway only when the pipeline reports that it has caught up
C: Move the gateway to serverless compute so that it can scale to zero between changes, and run the pipeline on a daily schedule
D: Stop the gateway after each ingestion update to save compute, and rely on the source logs to hold every change until the next start
K: A
G: ## Two components, two modes
A gateway-based SQL Server pipeline has two parts with different operating rules:
- The **ingestion gateway** extracts snapshots and change logs from the source. It must run on classic compute and must stay in continuous mode so that changes are not lost to the source's log retention. Stopping it also re-provisions a VM on every start, which is slow.
- The **ingestion pipeline** applies the data to the destination tables on serverless compute. It runs as triggered updates on a schedule; continuous mode is not supported for it.
## Latency and cost
Latency is therefore set by the pipeline's schedule. Databricks suggests leaving a few minutes between runs because serverless startup takes time. A short schedule meets "within a few minutes"; running the gateway continuously is the price of not losing changes.
W: Continuous gateway plus scheduled pipeline: this matches the documented model, and a schedule of a few minutes gives the needed latency while the serverless pipeline only runs for its updates.
X: B=Continuous pipeline: the ingestion pipeline does not support continuous mode, and a gateway that starts late risks missing changes the source has already truncated.
C=Serverless gateway: the gateway must run on classic compute, and a daily schedule would not meet a latency goal of a few minutes.
D=Stopping the gateway: the gateway must not be stopped manually, because changes can be dropped when the source log retention passes, which forces a full refresh.
T: Keep the gateway running continuously on classic compute and set the latency with the schedule of the serverless ingestion pipeline.

@ DBX-DEP D2 T2.3 advanced comparison
S: A company runs SQL Server in an Availability Group. After an unplanned failover the ingestion must resume without a full refresh of all tables. Which setup gives that?
A: Change tracking on every table, connecting to the node that is primary today, because its change data is replicated to the secondary nodes
B: Change tracking on every table, connecting to a readable secondary so the primary is not loaded by the ingestion gateway
C: Change data capture on the tables, connecting through the Availability Group listener address, since log sequence checkpoints are portable across replicas
D: Change data capture on the tables, connecting to a readable secondary, since that node already holds a copy of every captured change
K: C
G: ## Availability Groups and the change feed
Change feeds behave differently when the source fails over:
- **Change tracking data is not replicated to secondary nodes.** Any source node change, including an Availability Group failover, requires a full refresh of all tables in the pipeline.
- **CDC checkpoints (LSNs) are portable across replicas.** If the connector connects through the **AG listener** address, the pipeline can resume after an unplanned failover without data loss.
## Where the connector can connect
Support is limited to the primary instance. Change tracking and CDC are not supported on read replicas or secondary instances, so a readable secondary cannot be the ingestion source.
This is the trade-off with the first question of this topic: change tracking is lighter, but CDC through the listener is what survives failovers.
W: CDC through the listener: LSN checkpoints are portable across replicas and the listener follows the primary, so ingestion resumes after failover without a full refresh.
X: A=Change tracking on the primary: change tracking data is not replicated to the secondaries, so a failover forces a full refresh of every table in the pipeline.
B=Change tracking on a secondary: secondary instances are not supported as a source, and change tracking data is not replicated there anyway.
D=CDC on a secondary: the connector supports only primary instances, because CDC cannot be used on read replicas or secondary instances.
T: For failover-resilient SQL Server ingestion use CDC through the Availability Group listener; change tracking needs a full refresh after failover.

@ DBX-DEP D2 T2.3 advanced troubleshooting
S: A column `region_code` was dropped from a source table, and weeks later a different column with the same name `region_code` was added to it. The Lakeflow Connect pipeline now fails on that table. Which statement explains it and gives a fix?
A: The connector marked the dropped column `inactive` in the destination, and the new same-named column conflicts with it, so drop the inactive column or run a full refresh of the table
B: The connector deleted the dropped column in the destination, and the failure is caused by the source rejecting a column name that was used before
C: Column additions are never supported after the first update, so the only option is to recreate the gateway and the pipeline from scratch
D: The connector converts the new column to the old column's data type, and the failure is fixed by re-running the update after the conversion completes
K: A
G: ## Schema evolution in database connectors
The connector handles some schema changes by itself and others only with a refresh:
- New columns are picked up on the next update (you can opt out), and so are new tables if you ingest a whole schema.
- A column deleted at the source is **not** dropped in the destination. A table property sets it to `inactive`, so history stays queryable.
- Column renames and data type changes need a full refresh of the table (for SQL Server renames; MySQL treats a rename as a new plus a deleted column).
## The conflict case
Because the inactive column keeps its name in the destination, a later column with the same name conflicts with it and the pipeline fails. Either drop the inactive column manually or run a full refresh of the table.
W: Inactive column conflict: the old column stays in the destination marked inactive, so the new same-named column cannot be added, and dropping it or a full refresh clears the conflict.
X: B=Deleted in destination: the connector keeps the column as inactive instead of deleting it, and the source has no objection to reusing a name.
C=Recreate everything: new columns are supported, and this particular conflict is resolved at table level without rebuilding the gateway or the pipeline.
D=Automatic type conversion: the connector does not convert types, and data type changes are not handled automatically but need a full refresh.
T: Dropped source columns stay as inactive columns in the destination; a later column with the same name fails the pipeline until the inactive column is dropped or the table is fully refreshed.
V: Lakeflow Connect, SQL Server

@ DBX-DEP D2 T2.3 advanced use-case
S: An admin wants data engineers who are not admins to create their own SQL Server ingestion gateway-pipeline pairs, without handing them the database password or making them metastore admins. What should the admin do?
A: Prepare the source database, create a Unity Catalog connection that stores the credential, and let the engineers create their pairs with that connection
B: Store the password in a secret scope shared with the engineers, so each engineer can create a private connection to the database
C: Make each engineer an owner of the source database, so they can enable change tracking and create the pipelines in their own name
D: Create one shared ingestion pipeline owned by the admin, and give the engineers a role that lets them edit its table list
K: A
G: ## Personas in a database ingestion setup
Two user models are documented for the connectors:
- **Single user:** an admin configures the source database, creates the Unity Catalog connection, the ingestion gateway and the ingestion pipeline.
- **Multi-user:** an admin configures the source database (a dedicated ingestion user, change tracking or CDC) and creates a **connection** that non-admin users can use to create gateway-pipeline pairs.
The credential lives in the Unity Catalog connection object, so access to it is governed by Unity Catalog privileges and engineers never see the password.
## Not shareable
Each ingestion pipeline is associated with exactly one gateway, and gateways cannot be shared across pipelines, so each engineer creates a pair.
W: Admin-created connection: the credential stays inside the Unity Catalog connection and the engineers build their own gateway-pipeline pairs from it, which is the documented multi-user path.
X: B=Shared secret scope: it exposes the password to every engineer, which is exactly what the admin wants to avoid, and it bypasses the connection object.
C=Database owner role: the ingestion needs a dedicated user with the documented privileges, and ownership of the whole source database is far beyond least privilege.
D=One shared pipeline: each pipeline has exactly one gateway and the requirement is that engineers create their own pairs, so a single admin-owned pipeline does not meet it.
T: In a multi-user setup the admin prepares the source and creates the Unity Catalog connection; non-admins then create their own gateway-pipeline pairs.

@ DBX-DEP D2 T2.3 applied troubleshooting
S: A source table `dim_promo` was dropped in SQL Server after a retirement. Weeks later analysts still query `dim_promo` in the destination schema, and the data engineer expected it to vanish with the source table. What is the behavior of Lakeflow Connect database connectors?
A: The destination table is not deleted automatically, so it must be dropped manually, which differs from the behavior of Spark Declarative Pipelines
B: The destination table is dropped on the next pipeline update, and the analysts see stale data only because of a caching delay in the catalog
C: The destination table is converted to a snapshot copy that is read-only, and it is removed after the table retention period expires
D: The pipeline fails on every update until the missing source table is removed from the ingestion definition, and then drops the destination table
K: A
G: ## Dropped sources and destination tables
Managed database connectors treat the destination as the system of record once ingested. The documented behavior for all database connectors:
- When a source table is deleted, the destination table is **not** deleted. You delete it manually.
- This is not consistent with Spark Declarative Pipelines, where removing a dataset from the pipeline code drops it from the pipeline's managed objects.
- If a source table name conflicts with an existing destination table, the update fails.
## Operational consequence
Retiring a source table needs an explicit clean-up step for the destination, including grants and downstream readers, or consumers will keep seeing the last ingested state.
W: Manual clean-up: database connectors never delete the destination of a dropped source table, so the engineer must drop it and handle consumers, unlike the declarative pipeline behavior.
X: B=Dropped on next update: the connector does not remove destination tables, and the stale rows are not a cache delay but the last ingested data.
C=Read-only snapshot with expiry: no conversion or expiry happens, the table simply stays as it was and remains writable according to its grants.
D=Fail until removed from the definition: the dropped table does not make the update fail by itself, and removing it from the definition still would not drop the destination table.
T: Database connectors keep the destination table when the source table is dropped; delete it manually.

@ DBX-DEP D2 T2.4 advanced comparison
S: A retailer wants to give a logistics partner a Unity Catalog table, a folder of PDF delivery notes in a volume, and a notebook explaining the data. The partner has its own Unity Catalog-enabled Databricks workspace in another cloud. Which sharing approach covers all three?
A: Databricks-to-Open sharing with a bearer token, because that protocol supports tables, volumes and notebooks for any recipient platform
B: Databricks-to-Databricks sharing, because notebooks and volumes can be shared only with recipients that use a Unity Catalog-enabled workspace
C: Databricks-to-Open sharing with OIDC federation, because short-lived tokens extend the protocol to volumes and notebook files
D: Two separate shares through Databricks-to-Open sharing, one for tables and one for the files exported to cloud storage
K: B
G: ## Two OpenSharing modes
OpenSharing (named Delta Sharing in older docs and in some product pages) has two protocols that use the OpenSharing server built into Databricks:
- **Databricks-to-Databricks** shares data and AI assets with users who have a Unity Catalog-enabled workspace. It adds notebook sharing, volume sharing, model sharing, Unity Catalog governance, auditing and usage tracking on both sides. It works across accounts, clouds and regions.
- **Databricks-to-Open** shares tabular data with a recipient on any computing platform (Power BI, pandas, Apache Spark, and others). Tables, not notebooks, volumes or models.
## Choosing
Notebooks, volumes, models (and metric views) can only be shared with the Databricks-to-Databricks flow. When the recipient is on Databricks with Unity Catalog, that mode is both richer and token free, since the sharing identifier replaces bearer tokens.
W: Databricks-to-Databricks: the recipient has a Unity Catalog workspace, and this is the only mode that can carry volumes and notebook files in addition to tables.
X: A=Open with bearer token: the open protocol shares tabular data, so volumes and notebook files cannot be included, whatever the recipient platform is.
C=Open with OIDC federation: OIDC changes how the recipient authenticates, not what the protocol can carry, so the share would still be tables only.
D=Two open shares with exported files: this moves files out of governance and loses auditing, and the recipient has a Databricks workspace for which the integrated mode exists.
T: Notebooks, volumes and models need Databricks-to-Databricks sharing; Databricks-to-Open is for tabular data to any platform.
V: OpenSharing, Unity Catalog

@ DBX-DEP D2 T2.4 advanced use-case
S: A bank shares a Unity Catalog table with an analytics vendor that uses Power BI and Python, with no Databricks workspace. Security rejects long-lived bearer tokens that the vendor would have to store, and wants the vendor's own identity provider to enforce multi-factor authentication. What should the bank configure?
A: A Databricks-to-Databricks recipient identified by the vendor's metastore sharing identifier, which needs no token on either side
B: A Databricks-to-Open recipient with OIDC federation, so the vendor's identity provider issues short-lived tokens that Databricks validates
C: A Databricks-to-Open recipient with a bearer token that expires quickly, and an activation link sent by email every morning
D: A customer-managed open source OpenSharing server that copies the table into a bucket the vendor reads with its own credentials
K: B
G: ## Authentication for Databricks-to-Open recipients
Recipients without a Unity Catalog workspace use the Databricks-to-Open protocol. The provider chooses how they authenticate:
- **Bearer token**: Databricks generates a long-lived credential file and an activation link. Providers should configure token lifetime, can restrict recipients with IP access lists, and must ask recipients to store the file securely.
- **OIDC federation**: the provider defines a federation policy naming the issuer of the recipient's identity provider (such as Microsoft Entra ID or Okta) and the allowed user, group, service principal or application. The recipient's IdP issues a short-lived JWT, enforces policies such as MFA, and Databricks only validates the JWT against the policy. Databricks does not create or manage these tokens.
## Why the other mode does not fit
Databricks-to-Databricks needs a Unity Catalog-enabled workspace on the recipient side. Email invitations were in Beta and do not support OIDC federation.
W: OIDC federation: it fits recipients on any platform, uses short-lived tokens from the vendor's own IdP with its MFA, and removes shared credentials that need to be stored.
X: A=Sharing identifier: Databricks-to-Databricks requires the recipient to have a Unity Catalog-enabled workspace, which the vendor does not have.
C=Short-lived bearer token plus daily links: the credential is still a Databricks-issued bearer token that the vendor must store, and MFA is not enforced by the vendor's IdP.
D=Self-managed server and copy: it duplicates the data outside Unity Catalog governance and gives up the integrated provider-side controls, and the question needs none of it.
T: For non-Databricks recipients that need short-lived credentials and IdP-enforced MFA, use Databricks-to-Open sharing with OIDC federation.

@ DBX-DEP D2 T2.4 advanced troubleshooting
S: A provider granted a Databricks-to-Databricks recipient access to a share. The recipient's analysts see the provider in the workspace but none of the shared tables in any catalog, and cannot query them. What must happen on the recipient side?
A: A metastore admin or privileged user creates a catalog from the share, and then grants the analysts the usual Unity Catalog privileges on it
B: The analysts each need a bearer token file from the provider, which they upload to the workspace to mount the tables
C: The provider has to copy the tables into the recipient's metastore, since shared tables are only visible after a replication job ran
D: A workspace admin runs a refresh of the share metadata, after which the tables appear under the default `hive_metastore` catalog
K: A
G: ## Consuming a Databricks-to-Databricks share
Granting the recipient access on the provider side makes the share available, but data appears in the recipient's catalogs only after the recipient creates a catalog from the share:
1. The provider creates the share and a recipient (identified by the metastore sharing identifier, in the form `<cloud>:<region>:<uuid>`) and grants the recipient access.
2. In the recipient's workspace, a metastore admin or a user with sufficient privileges (such as `CREATE CATALOG` on the metastore) creates a catalog from the share.
3. That user, or another with the right privileges, grants access on the catalog to others with standard Unity Catalog grants.
## Important properties
Objects in shared catalogs are read only. Shared notebooks live at the catalog level, and `USE CATALOG` is enough to open them. Nothing is replicated, so there is no copy job.
W: Create a catalog from the share: this mounts the shared objects into the recipient's metastore, after which standard Unity Catalog grants decide which analysts can read them.
X: B=Bearer token upload: token files belong to the Databricks-to-Open protocol, and a Databricks-to-Databricks recipient needs no token.
C=Replication into the recipient's metastore: OpenSharing reads the provider's data in place without a replication job, so no copy is needed.
D=Refresh into hive_metastore: shares are exposed through a Unity Catalog catalog that is created from the share, not through the legacy Hive metastore.
T: In Databricks-to-Databricks sharing the recipient must create a catalog from the share, then manage read access with ordinary Unity Catalog grants.

@ DBX-DEP D2 T2.4 advanced troubleshooting
S: Two companies created a Databricks clean room. Months later a third company must join the same collaboration, but the invitation cannot be added to the existing clean room. What is the correct way forward?
A: Create a new clean room that includes all three companies, because a clean room is locked against new collaborators after it is created
B: Ask the creator to temporarily switch the clean room to open mode, add the third company, and then lock it again
C: Share the central clean room's tables with the third company through Databricks-to-Open sharing so it can read the same data
D: Let any collaborator rename the clean room and re-invite all parties, which resets the membership list of the collaboration
K: A
G: ## Clean room safeguards
Databricks Clean Rooms builds on OpenSharing and serverless compute. A "central" clean room is an isolated, ephemeral environment managed by Databricks; each collaborator also has a securable clean room object in its own metastore. Safeguards include:
- After a clean room is created it is locked down, so no new collaborators can join.
- Each clean room is limited to ten collaborators.
- The clean room cannot be renamed, and its name must be unique in every collaborator's metastore.
- If any collaborator deletes the clean room, the central clean room is void and nobody can run tasks.
## Consequence
Membership is fixed at creation, so adding a party means creating a new clean room with the complete list of participants. All collaborators in a no-trust clean room have equal privileges.
W: New clean room: the clean room is locked against new collaborators, so a new collaboration with all three companies has to be created.
X: B=Open mode toggle: there is no way to reopen a clean room, because the lock is a deliberate safeguard of the no-trust model.
C=Sharing central tables: collaborators share data only with the central clean room, never with each other or outsiders, and the central environment is not a share the creator can hand on.
D=Rename and re-invite: clean rooms cannot be renamed, and there is no membership reset operation.
T: A clean room is locked after creation (maximum ten collaborators), so a new participant needs a new clean room.

@ DBX-DEP D2 T2.4 advanced tradeoff
S: An advertiser and a retailer want the overlap of their customer lists and conversion rates per campaign. Neither may receive the other's raw records, and both want to review the code before it touches their data. Which approach fits, compared with a normal OpenSharing share?
A: A normal share in both directions, because each party can then run its own code on the other's table and get only aggregate output
B: A clean room where each party shares its tables with the central clean room, and a notebook runs there after the other collaborators approved it
C: A normal Databricks-to-Open share with row filters, because filtered rows protect identifiers while the partner joins the data locally
D: A clean room where the creator holds admin rights over all shared tables and approves the other party's notebooks on their behalf
K: B
G: ## Share versus clean room
- A normal **OpenSharing** share gives the recipient read access to the provider's data, so the recipient sees the rows and can run any code on them. It fits data distribution.
- A **Clean Room** lets parties combine sensitive data without direct access to each other's data. Assets are shared only with the central clean room (using OpenSharing), where approved notebook code runs on serverless compute. Collaborators see column names and types but not the data.
## No-trust model
All collaborators have equal privileges, including the creator. Every notebook must be approved by all collaborators except its uploader before it can run, and there is one designated runner. Only the latest version of a notebook runs, and actions are logged in the clean room events system table and in the audit log.
W: Clean room with approved notebook: data stays in the central clean room, neither side sees the other's rows, and approval by the other collaborators gives each party the code review it wants.

@ DBX-DEP D3 T3.1 advanced troubleshooting

G: ## The default window frame
A window function sees only the rows in its **frame**. When the window has an `ORDER BY` and no explicit frame, Spark uses a growing frame: a range from the unbounded preceding row to the current row (rows with equal ordering values count as the current row). Without `ORDER BY` the frame is the whole partition.
- With the default frame, `last_value` returns the value of the current row (or the last of its ties), because the frame ends there.

- An equivalent that uses the default frame is `first_value(status) OVER (PARTITION BY order_id ORDER BY ts DESC)`.

`IGNORE NULLS` only skips NULL values, and moving data between partitions does not change which rows a frame contains.

C=max(status): it returns the alphabetically highest string, not the status of the latest timestamp.
D=Repartitioning: window results depend on the frame definition, not on physical partitioning, and the engine already groups rows by `order_id` for the window.
T: With ORDER BY and no frame, the window ends at the current row; extend the frame to UNBOUNDED FOLLOWING to read the partition's last value.

- `row_number()` gives 1, 2, 3, 4, 5 and splits ties arbitrarily.
- `rank()` gives 1, 1, 3, 4, 5. Ties share a rank and the next rank skips numbers, so `<= 3` returns only 100, 100 and 90.
- `dense_rank()` gives 1, 1, 2, 3, 4. Ranks do not skip, so `<= 3` returns the three highest distinct values with all their ties.
- `ntile(3)` splits the ordered rows into three buckets by position, it does not rank by value.
## QUALIFY
`QUALIFY` filters the results of window functions without a wrapping subquery, like `HAVING` for aggregates. At least one window function must be in the `SELECT` list or in the `QUALIFY` clause itself, and the clause cannot contain aggregate functions.
W: dense_rank with QUALIFY: consecutive ranks make the three highest distinct revenues (100, 90, 80) all pass, and tied products share a rank so none is dropped.
X: A=row_number: it numbers rows 1 to 5 and returns only three rows, losing one of the tied 100 products and the 80 product.
B=rank: it gives 1, 1, 3, 4, 5, so the product with revenue 80 (rank 4) is excluded even though it is the third distinct value.
C=ntile(3): it divides the rows into buckets of nearly equal size by position, which has no relation to the three highest distinct values.
T: Use `dense_rank()` for top-N distinct values with ties, and `QUALIFY` to filter on a window result without a subquery.
