@ DBX-DEP D4 T4.5 advanced troubleshooting
S: A Lakeflow Jobs job has the chain `extract` -> `load` -> `cleanup`, where `cleanup` uses the run-if condition "All done". In one run `load` fails and `cleanup` still runs and succeeds. The on-call dashboard counts only runs whose result is "Failed". What does the Jobs UI report for this run, and what does that mean for monitoring?
A: The run is Succeeded with failures, because its only leaf task succeeded, so a filter on "Failed" misses it and task-level statuses are needed
B: The run is Failed, because any failed task fails the whole run, so the dashboard counts it and the result of `cleanup` has no effect
C: The run is Succeeded, because tasks with run-if conditions are left out of the status, so only the result of `extract` decides the run state
D: The run is Skipped, because `cleanup` replaced the failed task, so the dashboard ignores it until the failed task is repaired
K: A
G: ## How a job run status is derived
Lakeflow Jobs does not compute the run status from every task. It looks at the **leaf tasks**, the tasks that have no downstream dependents.
- **Succeeded**: all tasks succeeded.
- **Succeeded with failures**: some tasks failed, but all leaf tasks succeeded.
- **Failed**: one or more leaf tasks failed.
- **Skipped**: the run did not execute, for example because the maximum number of concurrent runs was exceeded.
## Why this matters for monitoring
A task with a run-if condition such as "All done" executes even when its upstream failed. When that task is the leaf and it succeeds, the failure of an inner task is not visible in the run-level status. Dashboards and alerts that filter on run status alone can miss real failures, so production jobs should also notify on task-level failures or inspect the task statuses in the run matrix and the Graph, Timeline and List views of the run.
W: Succeeded with failures: `cleanup` is the only leaf task and it succeeded while `load` failed, which is exactly the definition of this status, so a filter on "Failed" does not list the run.
X: B=Any failure fails the run: run status is derived from the leaf tasks, not from every task, so a failed inner task does not make the run Failed on its own.
C=Run-if tasks ignored: a run-if condition only decides whether a task executes. The failed `load` is still recorded and is what produces the "with failures" qualifier.
D=Skipped run: Skipped describes a run that was not executed, for example because of the concurrency limit. A run in which tasks ran and one failed is never reported as Skipped.
T: Run status follows the leaf tasks, so a successful "All done" leaf hides an inner failure behind Succeeded with failures.
V: Lakeflow Jobs

@ DBX-DEP D4 T4.5 applied troubleshooting
S: An Apache Airflow DAG starts Databricks work with `DatabricksSubmitRunOperator`. An engineer opens the workspace Runs list and types the Airflow task name into the Name filter, but the runs do not appear, although the Run status filter shows failures from that hour. How should the engineer find the runs, and what is the more durable design?
A: Filter by Run ID, Run as or start time, because submitted runs are one-time runs not backed by a saved job; for durable searchable history create a job and trigger it
B: Wait for the 60-day retention window to index the runs under the Airflow DAG name, because one-time runs are added to the Name filter only after retention completes
C: Filter by the Launched column set to schedule, because Airflow runs are always scheduled runs that carry the DAG name as the job name in the list
D: Export the runs to HTML first, because runs from external orchestrators are visible in the Runs list only after their notebook output has been exported
K: A
G: ## One-time runs versus jobs
The Jobs API `runs/submit` endpoint, also used by the Airflow `DatabricksSubmitRunOperator`, creates a **one-time run**. No saved job exists behind it, so the run has no job Name, no stored settings and no built-in retry configuration.
## Finding them in the Runs list
The Runs tab of the Jobs & Pipelines area lists runs of all jobs and pipelines you can access for 60 days, including runs started by external orchestrators. Because a one-time run has no job, you cannot find it by job Name. Use filters that do apply: **Run ID**, **Run as**, the start or end time window, status or error code.
## Durable design
When the team wants searchable history, tags and retries per job, define a real job with `jobs/create` and trigger it with `run-now` from Airflow (`DatabricksRunNowOperator`), so runs are grouped under one job.
W: Filter by run attributes: one-time runs lack a job name, so Run ID, Run as and time filters find them, and a saved job triggered by the orchestrator gives a durable, named history.
X: B=Retention indexing: retention only removes history after 60 days. Nothing ever adds a one-time run to the Name filter, because there is no job name to match.
C=Launched filter: the Launched column shows how a run was triggered, such as a schedule, an API request or a manual start. Airflow submissions arrive as API requests and carry no job name.
D=HTML export first: exporting is a way to keep a rendered notebook run after expiry. It plays no role in whether a run is listed.
T: Runs from `runs/submit` are one-time runs without a job name, so find them by run ID, run-as or time, and use saved jobs for durable history.

@ DBX-DEP D5 T5.1 applied tradeoff
S: A platform team owns 300 external Delta tables in Unity Catalog. Every table needs hand-scheduled compaction, `VACUUM`, statistics refresh and clustering-key reviews, and the team wants to remove that operations work without writing new maintenance jobs. Which approach delivers the most overhead reduction?
A: Convert the tables to Unity Catalog managed tables and enable predictive optimization with automatic liquid clustering, so Databricks schedules maintenance and adapts the keys
B: Keep the tables external and enable predictive optimization on their catalog, because the setting applies to every table type as long as the schema inherits it
C: Keep the tables external and add `delta.autoOptimize.optimizeWrite` on each table, because optimized writes replace `VACUUM`, statistics refresh and key selection
D: Move the maintenance into one serverless Lakeflow Jobs job per schema that runs `OPTIMIZE` and `VACUUM`, because scheduled jobs are what predictive optimization uses on any table
K: A
G: ## What managed tables add
Unity Catalog **managed tables** are the default and recommended table type. Unity Catalog manages their storage, reads, writes and optimization. Several features exist only for managed tables, not for external or foreign tables:
- **Predictive optimization** runs `OPTIMIZE`, `VACUUM` and `ANALYZE` when its analysis says the table benefits.
- **Automatic liquid clustering** (`CLUSTER BY AUTO`) selects and updates clustering keys from query history.
- Automatic file deletion after `DROP TABLE`, catalog commits and multi-statement transactions.
## The decision
Predictive optimization only supports Unity Catalog managed tables. The way to remove the maintenance work is therefore to convert external tables to managed tables first, then enable predictive optimization (and automatic liquid clustering where the query patterns change).
W: Managed tables plus predictive optimization: the conversion makes the tables eligible, and the platform then runs compaction, vacuum, statistics and key selection with no team-owned jobs.
X: B=Catalog setting on external tables: predictive optimization supports only managed tables, so enabling it on the catalog leaves external tables without maintenance.
C=Optimized writes: optimized writes only improve file sizes during a write. They do not vacuum unreferenced files, refresh statistics or choose clustering keys.
D=Per-schema jobs: this keeps the team-owned maintenance the requirement tries to remove, and predictive optimization does not run as a user-defined job.
T: Predictive optimization and automatic liquid clustering work only on Unity Catalog managed tables, so convert external tables first.
V: Unity Catalog managed tables, Predictive optimization

@ DBX-DEP D5 T5.1 advanced troubleshooting
S: A team enables predictive optimization on a catalog whose tables hold 90 days of history for audits and sometimes need time travel of 30 days. Weeks later, queries with `VERSION AS OF` older than 8 days fail because files are gone. No one ran `VACUUM`. What should have been done, and what fixes the future behavior?
A: Set `delta.deletedFileRetentionDuration` to 30 days on the tables before relying on predictive optimization, because its `VACUUM` honors that property
B: Disable `VACUUM` in the predictive optimization settings for the catalog, because the operation list can be edited per operation type on every table
C: Increase the `delta.logRetentionDuration` only, because the log retention alone controls how long data files stay on storage after vacuum
D: Run `OPTIMIZE` more often so that old versions are compacted into the newest version, because compaction keeps the files needed for time travel
K: A
G: ## Time travel depends on file retention
Delta time travel reads old table versions through data files that the transaction log no longer references but that still exist on storage. `VACUUM` deletes unreferenced files older than the retention threshold, which comes from the table property `delta.deletedFileRetentionDuration` (default 7 days).
## Predictive optimization and VACUUM
Predictive optimization runs `VACUUM` for managed tables. It respects the retention property, and even when the property is set below 7 days, it keeps files for a minimum of 7 days. If you need longer time travel, **set the property before enabling predictive optimization**, for example:
`ALTER TABLE t SET TBLPROPERTIES ('delta.deletedFileRetentionDuration' = '30 days')`
Log retention (`delta.logRetentionDuration`) controls how long the history metadata stays, but a missing data file still breaks the read.
W: Table-level file retention: setting the deleted file retention to 30 days makes predictive optimization's `VACUUM` keep unreferenced files that long, so older versions stay readable.
X: B=Operation toggles: predictive optimization is enabled or disabled for an account, catalog, schema or table. The documentation gives no per-operation switch for `VACUUM`.
C=Log retention only: the log can still list the version, but the read fails when its data files were vacuumed, so file retention is the control that matters.
D=More OPTIMIZE: compaction writes new files and leaves old files unreferenced. Those old files are what `VACUUM` then removes, so compaction does not preserve history.
T: Set `delta.deletedFileRetentionDuration` for the needed time-travel window before predictive optimization starts vacuuming.
V: Predictive optimization, Delta time travel

@ DBX-DEP D5 T5.1 advanced troubleshooting
S: A managed table has predictive optimization enabled through its schema, yet analysts see slow filters on `order_date` and the table was never given clustering keys. The engineer wants the reason predictive optimization did or did not act on automatic clustering key selection. Which action gives that information?
A: Run `DESCRIBE TABLE EXTENDED ... AS JSON` and read `predictive_optimization_evaluations`, or open the table History in Catalog Explorer
B: Query `system.access.audit` for failed `OPTIMIZE` statements, because skipped evaluations are written there as errors with a reason code
C: Read the Spark UI of the last writer cluster, because predictive optimization evaluations run on that cluster and log skipped keys there
D: Run `ANALYZE TABLE ... COMPUTE STATISTICS` and compare the row counts, because clustering is skipped whenever statistics are older than the table
K: A
G: ## Why automatic clustering may do nothing
Automatic liquid clustering (`CLUSTER BY AUTO`) picks keys only when it is cost-aware worthwhile. It can skip a table when:
- the table is too small to benefit,
- the table already has an effective layout, such as keys that match the query pattern or insertion order,
- the table has few queries to learn from.
## How to find out
After predictive optimization evaluates a managed table, each operation type has a latest evaluation result: `COMPACTION`, `CLUSTERING`, `AUTO_CLUSTERING_COLUMN_SELECTION` and `VACUUM`. You can read them with `DESCRIBE TABLE EXTENDED ... AS JSON` (field `predictive_optimization_evaluations`) or in the History tab of Catalog Explorer, where rows labelled "Not applied" carry the skip reason. Results can take some time to appear, and only the latest evaluation is kept. Note also that automatic clustering has to be turned on for the table, not only predictive optimization.
W: Evaluation results: the JSON describe output and the History tab are the documented places where the skip reason of each predictive optimization operation is shown.
X: B=Audit log search: skipped evaluations are not statement failures, and the audit system table is not the documented source for skip reasons.
C=Writer cluster Spark UI: predictive optimization runs on serverless jobs compute, not on the cluster that wrote the data, so that Spark UI has nothing about it.
D=Statistics comparison: stale statistics are not the documented reason, and running `ANALYZE` returns no information about key selection.
T: Use `predictive_optimization_evaluations` from `DESCRIBE TABLE EXTENDED ... AS JSON` or the Catalog Explorer History tab to see why an operation was skipped.

@ DBX-DEP D5 T5.1 applied tradeoff
S: An engineer drops several external Delta tables and several managed tables in the same catalog to cut costs, then notices that cloud storage cost fell only for some of them. Which statement explains the difference and the operational advantage of managed tables?
A: Dropping a managed table makes Databricks delete its files after a recovery period, while files of an external table stay and must be deleted manually from storage
B: Dropping an external table deletes its files immediately, while files of a managed table stay until `VACUUM` is run with a zero-hour retention
C: Dropping either type deletes the files after the recovery period, so the difference comes from the clusters that were still caching old files
D: Dropping a managed table leaves files in place permanently, because the catalog cannot delete data it does not own, whereas external table files expire with the metastore
K: A
G: ## Dropping tables
- **Managed table**: Unity Catalog owns the data files. After `DROP TABLE`, the table can be recovered for a recovery period (7 days by default, configurable at catalog or schema level), and then Databricks automatically deletes the files in cloud storage.
- **External table**: Unity Catalog owns only the metadata. `DROP TABLE` removes the table definition, and the files in your own bucket stay until you delete them.
## Operational impact
Forgotten external data keeps costing storage and may keep sensitive data longer than intended. Managed tables remove this clean-up task and are one of the features that reduce operational overhead.
W: Managed versus external drop behavior: files of a managed table are removed automatically after the recovery period, while an external table's files remain until someone deletes them.
X: B=Reversed behavior: dropping an external table never deletes its files, and managed table files are removed by the platform without a manual `VACUUM`.
C=Caching explanation: cached copies live on worker disks and do not stop cloud storage deletion, so they cannot explain different storage bills.
D=Permanent managed files: Unity Catalog does own managed table files and deletes them after the recovery period; external files are not removed by the metastore.
T: Managed tables get automatic file deletion after the drop recovery period; external table files must be removed manually.
V: Unity Catalog managed tables

@ DBX-DEP D5 T5.1 advanced use-case
S: A streaming job appends micro-batches of about 5 MB each to a liquid-clustered managed table. Over weeks the data skipping on the clustering keys degrades, although the table definition never changed. Predictive optimization is disabled for this table. What explains the degradation and what is the lowest-overhead fix?
A: Clustering on write only triggers when a transaction reaches a size threshold, so small batches stay unclustered; enable predictive optimization so incremental clustering runs
B: Liquid clustering clusters only data written by batch jobs, so streaming writers never produce clustered files; convert the sink to a partitioned table to restore skipping
C: Clustering keys expire after a fixed number of commits, so the keys must be re-declared with `ALTER TABLE ... CLUSTER BY` every night by a scheduled job
D: Streaming checkpoints block clustering metadata, so the stream must be restarted with a new checkpoint each week to rebuild the data layout
K: A
G: ## Clustering on write
Liquid clustering clusters data during some writes (`INSERT INTO`, CTAS/RTAS, `COPY INTO`, append writes). Clustering on write only triggers when the data in the transaction meets a **size threshold** that depends on the number of clustering columns (lower for managed tables than for other Delta tables). Small micro-batches fall below it and land unclustered. Structured Streaming needs an additional setting for eager clustering on write, and then only when recent updates exceed the thresholds.
## Incremental clustering
`OPTIMIZE` clusters the data that is not yet clustered, incrementally. Predictive optimization runs `OPTIMIZE` for enabled managed tables, and Databricks recommends disabling scheduled `OPTIMIZE` jobs when it is on. So enabling predictive optimization removes the maintenance work.
W: Threshold plus predictive optimization: tiny micro-batches are not clustered at write time, and predictive optimization's incremental `OPTIMIZE` clusters them without a manual job.
X: B=Batch only: streaming writes into clustered tables are supported; they are just clustered on write under extra conditions, so partitioning is not required.
C=Expiring keys: clustering keys stay in the table metadata until changed. They do not expire and need no nightly re-declaration.
D=Checkpoint blocking: checkpoints track stream progress and do not hold clustering metadata, so recreating them rebuilds nothing.
T: Small writes skip clustering on write, so rely on predictive optimization's incremental `OPTIMIZE` instead of manual clustering jobs.
V: Liquid Clustering, Predictive optimization

@ DBX-DEP D5 T5.2 advanced tradeoff
S: A 20 TB Delta table receives a nightly `MERGE` that updates about 0.1% of rows scattered across most files. The job rewrites a large share of the Parquet files and runs for hours, while the reading queries are already fast. Which change targets the write cost, and what does it add?
A: Enable deletion vectors, so changed rows are marked in metadata instead of rewriting files; reads apply them until compaction rewrites the files
B: Add more clustering keys with `CLUSTER BY`, so changed rows land in fewer files; reads then need no extra work because keys are free
C: Turn on the disk cache on all workers, so the files rewritten by `MERGE` are served from local SSD; reads then pay only the first fetch
D: Run `VACUUM` before every merge, so old files do not slow the file lookup; reads then apply a lower retention threshold
K: A
G: ## Write amplification
Without deletion vectors, changing one row requires rewriting the whole Parquet file that contains it. A `MERGE` that touches few rows in many files rewrites most of the table.
## Deletion vectors
With deletion vectors, `DELETE`, `UPDATE` and `MERGE` mark rows as removed in a small side structure and write the new row versions elsewhere. The file is not rewritten. Readers apply the vector at query time to compute the current state.
## Trade-offs
- Reads carry a small extra cost until the files are physically rewritten (`OPTIMIZE`, `REORG TABLE ... APPLY (PURGE)`, or auto-compaction).
- Enabling them upgrades the table protocol, so clients without support cannot read the table.
- Tables with deletion vectors support row-level concurrency.
They fit write-heavy patterns with scattered modifications, whereas clustering improves read pruning.
W: Deletion vectors: marking modified rows in metadata avoids rewriting the scattered files, which is the actual cost, and the price is query-time application until compaction.
X: B=More clustering keys: clustering improves read pruning and does not stop a merge from rewriting the files that contain changed rows. Extra keys can even reduce skipping for single-column filters on smaller tables.
C=Disk cache: caching accelerates reads of unchanged data files and does nothing about the writing of new Parquet files during the merge.
D=VACUUM before merges: vacuum deletes unreferenced files after the retention period and is unrelated to the amount of data a merge rewrites.
T: Deletion vectors cut the cost of scattered row-level changes by avoiding file rewrites, at the price of read-time application until compaction.
V: Delta deletion vectors

@ DBX-DEP D5 T5.2 advanced troubleshooting
S: After a platform team enabled deletion vectors on a Delta table, a downstream analytics service that uses an older open-source Delta reader begins failing on reads of the table, while Databricks queries work. The team cannot upgrade that reader this quarter. What is the supported way to restore compatibility?
A: Drop the deletion vectors table feature from the table, which removes the feature from the protocol so older clients can read it again
B: Delete the `_delta_log` entries that mention deletion vectors, because readers fail on protocol actions that are older than the table
C: Rewrite the table with `VACUUM` at zero retention, because vacuum removes the deletion vector files and resets the protocol
D: Set `spark.databricks.delta.reorg.purgeMode` to `rows` on the older reader, because that configuration makes the reader ignore protocol features
K: A
G: ## Deletion vectors change the protocol
When you enable deletion vectors, Databricks upgrades the table protocol. Clients without deletion vector support can no longer read the table. Support varies by client and version, so external engines are the usual place where this shows up.
## Reverting
Disabling the table property only stops new deletion vectors; it does not downgrade the protocol by itself. To restore compatibility, **drop the table feature** with `ALTER TABLE ... DROP FEATURE deletionVectors`, which purges existing deletion vectors and downgrades the protocol (supported in newer runtimes, with legacy support in older ones). The purge configuration `spark.databricks.delta.reorg.purgeMode` only affects how large purges are scoped.
Editing `_delta_log` by hand corrupts the table.
W: Drop the table feature: this rewrites files that have deletion vectors and removes the feature from the protocol, so the older reader can read again.
X: B=Editing the log: manual log edits risk corrupting the table, and the protocol is changed with a documented command, not by deleting entries.
C=Zero-retention VACUUM: vacuum deletes unreferenced files and never rewrites data with pending deletion vectors or downgrades the protocol.
D=Purge mode on the reader: that setting belongs to purge operations on the Databricks side and does not change what protocol features a reader understands.
T: To make a table readable by clients without deletion vector support, drop the deletion vectors table feature.
V: Delta deletion vectors

@ DBX-DEP D5 T5.2 applied troubleshooting
S: A table with deletion vectors enabled feeds a Presto-compatible symlink manifest, and the `GENERATE symlink_format_manifest` step now fails. Writers keep running throughout the day. Which sequence resolves it?
A: Run `REORG TABLE ... APPLY (PURGE)` with no concurrent writes, then generate the manifest; incremental generation stays unsupported
B: Run `OPTIMIZE ZORDER BY` on the table, then enable incremental manifest generation with the table property, which supports deletion vectors natively
C: Run `VACUUM` with the default retention, then run the generation; vacuum rewrites files with deletion vectors into clean files
D: Disable the disk cache on the cluster, then rerun the generation, because cached deletion vectors cause manifest generation to fail
K: A
G: ## Manifest generation and deletion vectors
Symlink-format manifests list the Parquet files for engines such as Presto or Athena. Those engines cannot apply deletion vectors, so Databricks does not generate a manifest for a table whose files use deletion vectors.
## Workaround
1. Make sure no concurrent writes run.
2. Run `REORG TABLE ... APPLY (PURGE)`, which rewrites all files that carry deletion vector changes.
3. Run `GENERATE` for the manifest.
Incrementally generated manifests (the symlink-format-manifest table property) are also not supported for tables with deletion vectors enabled, so each refresh needs the purge first, or the table feature must be dropped.
W: Purge then generate: rewriting the files with deletion vectors makes them plain Parquet files that a manifest can list, provided nothing writes meanwhile.
X: B=ZORDER and incremental manifests: Z-ordering does not purge deletion vectors, and incremental manifest generation is documented as unsupported with deletion vectors.
C=Default VACUUM: vacuum removes unreferenced files only; it does not rewrite files that have soft-deleted rows.
D=Disk cache: the cache holds file data for reads and has no effect on manifest generation.
T: Purge deletion vectors with `REORG TABLE ... APPLY (PURGE)` before generating a symlink manifest.

@ DBX-DEP D5 T5.2 advanced use-case
S: A Delta table in the team's own external storage (not Unity Catalog managed) is queried all day with filters on `tenant_id` and `event_date`; this access pattern has been stable for a year. The team wants better data skipping without partitioning. Which choice is correct?
A: Set manual keys with `CLUSTER BY (tenant_id, event_date)`, because automatic key selection is only available for Unity Catalog managed tables
B: Use `CLUSTER BY AUTO`, because automatic liquid clustering selects keys for any Delta table, including external tables outside Unity Catalog management
C: Enable deletion vectors, because they store min and max values per file and improve data skipping on filtered columns
D: Enable predictive optimization on the table and leave the keys unset, because it chooses keys for external tables from query history
K: A
G: ## Choosing the technique by access pattern
- Selective filters on known columns of a table with a stable query pattern: **liquid clustering with explicit keys** (`CLUSTER BY (col1, col2)`).
- Changing or unknown query patterns on a Unity Catalog managed table: **`CLUSTER BY AUTO`** lets predictive optimization pick and evolve keys.
- Scattered row-level changes making writes expensive: **deletion vectors**.
## The managed table constraint
Automatic liquid clustering and predictive optimization are available only for Unity Catalog managed tables. For an external table, you choose the keys yourself. Deletion vectors do not store statistics: they mark deleted rows, so they are unrelated to data skipping.
W: Manual clustering keys: the filters are stable and the table is external, so declaring the keys yourself is both possible and effective.
X: B=CLUSTER BY AUTO on external: automatic liquid clustering requires predictive optimization, which supports only managed tables, so it cannot be used here.
C=Deletion vectors for skipping: they record which rows were removed from files, not min/max statistics, so they do not improve filtering.
D=Predictive optimization on external: predictive optimization supports only managed tables, so it ignores this table.
T: Use explicit liquid clustering keys for stable filters on external tables; automatic keys need managed tables with predictive optimization.
V: Liquid Clustering

@ DBX-DEP D5 T5.2 applied use-case
S: A managed table uses explicit keys `CLUSTER BY (region)`. Analysts always filter on `region` but other filters have drifted over time. The team wants to keep `region` as a starting hint and let Databricks adapt further. Which statements do this?
A: `ALTER TABLE sales CLUSTER BY (region);` then `ALTER TABLE sales CLUSTER BY AUTO;`
B: `ALTER TABLE sales CLUSTER BY AUTO (region);` because the column list is an argument of the auto keyword
C: `ALTER TABLE sales CLUSTER BY NONE;` then `OPTIMIZE sales ZORDER BY (region);` to let Databricks adapt the z-order
D: `ALTER TABLE sales SET TBLPROPERTIES ('delta.autoClustering' = 'region');` to seed the key selection
K: A
G: ## Seeding automatic liquid clustering
`CLUSTER BY AUTO` can be enabled on an existing table, including a table with manually specified keys. To give the selection **initial hints**, set the clustering keys first and then turn on automatic clustering:
`ALTER TABLE sales CLUSTER BY (region);`
`ALTER TABLE sales CLUSTER BY AUTO;`
Databricks analyzes the query workload, and changes the keys only when the predicted data skipping gain outweighs the cost of re-clustering. It runs asynchronously through predictive optimization, so the table must be a Unity Catalog managed table.
`CLUSTER BY NONE` removes clustering. Z-ordering is not combined with liquid clustering.
W: Set keys, then AUTO: the explicit keys act as the initial hints and the second statement lets predictive optimization adapt them over time.
X: B=AUTO with a column list: the automatic clause takes no column arguments, so the statement is invalid.
C=NONE plus ZORDER: removing clustering and using Z-order brings back the manual technique the team is moving away from, and `ZORDER` never adapts.
D=Invented property: there is no such table property; the documented way is the two-statement sequence.
T: Set explicit keys first and then `CLUSTER BY AUTO` to seed automatic liquid clustering with hints.
V: Liquid Clustering

@ DBX-DEP D5 T5.2 advanced troubleshooting
S: A table with `CLUSTER BY AUTO` used to skip well. After a refactor, a nightly job runs `CREATE OR REPLACE TABLE sales_agg AS SELECT ...` without a clustering clause, and filter performance on the table falls back to full scans. The previous clustering columns are also gone. What happened and how is it fixed?
A: Replacing the table without `CLUSTER BY AUTO` turns off automatic clustering and drops the columns, so restate the clause
B: The nightly job exhausted the key budget of predictive optimization, so its clustering is paused until the next billing month starts
C: `CREATE OR REPLACE` keeps all clustering properties, so the scans come from stale statistics and need a manual `ANALYZE` on the table
D: Automatic clustering is disabled for tables created with CTAS, so the table must be created empty and then loaded with `INSERT`
