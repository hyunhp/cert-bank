@ DBX-DEP D2 T2.5 advanced troubleshooting
S: A data engineer has `CREATE FOREIGN CATALOG` on a connection and `CREATE CATALOG` on the metastore, created a foreign catalog, and has `SELECT` on its tables. Queries on a dedicated access mode cluster fail, while the same queries on a serverless SQL warehouse work. What explains it?
A: Dedicated access mode compute does not support foreign catalogs, so the queries have to move to standard access mode
B: The `SELECT` grant covers SQL warehouses, and clusters also need a separate `USE CONNECTION` privilege on the connection
C: The foreign catalog has to be bound to the cluster's workspace, because bindings are checked on dedicated clusters
D: The user must own the underlying connection on that compute type, and the granted catalog-creation privileges do not count
K: D
G: ## Access mode matters for foreign catalogs
Querying a foreign catalog follows Unity Catalog privileges, with one exception documented for federation:
- On **dedicated access mode** compute, you must **own the underlying connection** to query data in the foreign catalog. The `CREATE FOREIGN CATALOG` privilege on the connection is not enough.
- On **standard access mode** and serverless compute, standard catalog privileges apply.
## How to fix
Either run the workload on standard access mode compute or a serverless SQL warehouse, or make the user (or a group that is the owner) the connection owner. For shared work the first option keeps the connection ownership restricted to the admin who manages the credential.
W: Connection ownership: dedicated compute checks that the user owns the connection, so the creator-level privilege is not sufficient there, while serverless compute applies ordinary privileges.
X: A=No dedicated support: dedicated compute can query foreign catalogs, but with the stricter ownership rule on the connection.
B=USE CONNECTION on clusters: standard privileges apply on standard and serverless compute, and no separate cluster-only privilege exists for the grant.
C=Workspace binding: workspace binding is not tied to the compute type, and the same workspace works with a serverless warehouse.
T: On dedicated access mode compute, querying a foreign catalog requires owning the connection; standard and serverless compute use normal privileges.
V: Lakehouse Federation, Unity Catalog

@ DBX-DEP D8 T8.4 advanced troubleshooting
S: Two engineers each have a Git folder cloned from the same remote repository and both work on the shared remote branch `feature_a`. One engineer pulls and the Git folders UI reports conflicts with local edits. To get rid of the conflict, the engineer uses Reset to the `main` branch from the branch menu. What is the consequence?
A: The branch is overwritten with the history of `main` in the folder and upstream, so commits pushed to it by both are lost
B: The engineer's own Git folder is reset, while the teammate's commits stay on the remote branch and come back with the next pull
C: A revert commit is added on top of the branch to undo the conflicting files, so the earlier history stays on the remote branch
D: Databricks blocks the reset because other users have pushed to the branch, so the remote commits are kept as they are
K: A
G: ## Resolve versus reset
When a pull conflicts with local changes in a Git folder, Databricks offers two very different paths.
- **Resolve merge conflicts** in the Git folders UI: choose the lines to keep, mark the file as resolved and continue, or abort the operation and try again. Nothing is lost that you did not choose to drop.
- **Reset a branch**: documented as equivalent to `git reset --hard` combined with `git push --force`. The selected branch takes the contents and history of another branch, and the remote branch is reset as well.
## Why it hurts on a shared branch
With a reset, uncommitted and committed changes are lost in both the local and the remote version of the branch. Anyone else who pushed to that branch loses their commits there. Reset suits a personal branch whose edits you want to throw away, not a branch several people use.
Example: the engineer should resolve the conflicts, or create a new personal branch from the current state before experimenting.
W: Reset rewrites the remote branch: it is a hard reset plus a force push, so both the local and the remote `feature_a` take the state of `main` and the commits of both engineers on that branch are discarded.
X: B=Local-only reset: the Git folders reset also resets the upstream branch, so the teammate's commits are not kept on the remote and a pull cannot bring them back.
C=Revert commit: reset replaces the branch contents and history instead of adding a commit on top, so no history is preserved by the operation itself.
D=Blocked for shared branches: the operation behaves like a force push and is not blocked because several people use the branch; only the remote provider's branch protection rules can stop it.
T: Resolve conflicts in the Git folder; use Reset only on a personal branch, because it resets the remote branch too and loses commits.
V: Databricks Git folders
I: Q011105
