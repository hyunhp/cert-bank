S: A stream joins `impressions` and `clicks` (both from Kafka) with an inner join on `ad_id` to count clicked impressions. The code calls `impressions.withWatermark("imp_ts", "2 hours")` and joins on `ad_id` only; `clicks` has no watermark. After nine days the driver shows growing micro-batch durations, and `StreamingQueryProgress` reports `stateOperators[0].numRowsTotal` rising every batch while `numRowsDroppedByWatermark` stays 0. A click always happens within 1 hour after its impression. The team must keep the same output, keep the checkpoint if possible, and bound state. The output feeds a billing dashboard that reads the Delta sink every hour. Which change addresses the evidence?
A: Add a watermark on `clicks` only and keep the join condition on `ad_id`, so the engine can evict rows from both buffered sides once both watermarks pass
B: Add a watermark on `clicks` and a time-range condition `click_ts BETWEEN imp_ts AND imp_ts + INTERVAL 1 HOUR`, so old rows on both sides can be evicted
C: Keep the single watermark and add the time-range condition `click_ts BETWEEN imp_ts AND imp_ts + INTERVAL 1 HOUR`, so the impressions side alone bounds all state
D: Replace the inner join with a left outer join that keeps the single watermark, so unmatched impressions are emitted and removed from the join state
K: B
G: ## State in stream-stream joins
In a stream-stream join, each side buffers past rows as **state**, because any future row from the other side might match. For an inner join, the Spark guide warns that state **keeps growing indefinitely** unless you add both:
- **watermark delays on both inputs**, so the engine knows how late each side can be;
- an **event-time constraint** in the join condition, either a time-range condition (`click_ts BETWEEN imp_ts AND imp_ts + INTERVAL 1 HOUR`) or a join on event-time windows.
Only with both can the engine work out when an old row can no longer match and drop it.
## Reading the evidence
`numRowsTotal` climbs every batch and nothing is dropped by watermark: no row is ever evicted. One watermark without a time constraint cannot limit state for either side.
## Checkpoint note
Changing a stateful query's join can be incompatible with the existing checkpoint; plan a controlled restart if the engine rejects it.
W: Second watermark plus time range: the guide requires watermarks on both inputs and an event-time constraint, and the business rule supplies the 1-hour range.
X: A=Watermark without time range: the engine still cannot tell when a row can no longer match, because the condition joins on `ad_id` alone.
C=Time range with one watermark: without a watermark on `clicks`, the engine cannot bound how late clicks arrive, so state is not reliably cleared.
D=Left outer join: outer joins need watermarks and time constraints even more strictly, and it changes the output to include unclicked impressions.
T: A stream-stream join bounds state only with watermarks on both sides and an event-time constraint in the join condition.

C=Rollback of an earlier commit: Delta did not roll anything back; the history shows a new commit that removed files.
D=Dynamic partition overwrite: it needs a partitioned table and its SQL form is limited to classic compute, so it does not fit this serverless job on a clustered table.
T: REPLACE WHERE can delete data when the source is empty; REPLACE USING never deletes on empty input.
