G: ## Recovery semantics after query changes
Structured Streaming restores state from the checkpoint and assumes that the **state schema stays the same** across restarts. The Spark guide lists which changes are allowed with the same checkpoint:

- **streaming aggregation**: any change in the number or type of grouping keys **or aggregates** is not allowed;
- streaming deduplication: no change in the deduplication columns; stream-stream joins: no change in schema, equi-join columns or join type; arbitrary stateful operations: no change in the state schema or timeout type.

W: Revert aggregates, add a query: the original aggregation state stays compatible, the filter is an allowed change, and the new metrics start cleanly in their own query.
X: A=Delete the state folder: offsets would continue, but the partial sums of open windows are lost, so in-flight windows would be written with wrong totals.
C=Revert the filter too: adding filters is an allowed change; only the change in aggregates breaks state recovery.
D=Complete mode: the aggregation's state schema still changes, and complete mode would rewrite all results each trigger and keep every window in state.

G: ## Three ways to replace part of a table

## Applying it
Write the replace condition with the NULL-safe operator `<=>` on all three key columns, then remove the duplicates already written, for example by recomputing the affected days once.
W: REPLACE ON with <=>: NULL-safe equality matches the NULL-coded keys, so each run replaces them instead of adding a copy, and keys outside the result stay unchanged.
X: B=Partition the table: equality still never matches NULL, and partitioning instead of liquid clustering does not change how `REPLACE USING` compares keys.
C=REPLACE WHERE on 14 days: it deletes every row of those days, including keys that the nightly query did not return and that must stay untouched.
D=Dynamic partition overwrite: it is a Public Preview, classic-compute option for partitioned tables and replaces whole partitions, not individual keys.
T: `REPLACE USING` compares keys with equality; use `REPLACE ON` with `<=>` when key columns can be NULL.

W: Longer tombstone retention: tombstones then outlive the late files, so an older UPDATE meets the newer delete and is discarded.
X: B=Sequence by arrival time: the stale UPDATE would then count as newer than the delete and win on purpose, the opposite of the requirement.
C=SCD type 2: both types order changes by `sequence_by`; the expired tombstone, not the SCD type, caused the resurrection.
D=apply_as_truncates: a truncate clears the whole target table, so using it for single-subscriber deletes would remove every row.
T: With late CDC files, raise `pipelines.cdc.tombstoneGCThresholdInSeconds` above the maximum delay so deletes win over older late changes.
