@ DBX-ASD D2 T2.4 applied troubleshooting
S: A notebook cell registers a DataFrame three times in the same session, in this order:
```
df.createTempView("v")
df.createOrReplaceTempView("v")
df.createTempView("v")
```
What happens when the cell runs?
A: The first two lines succeed and the third raises an AnalysisException, because createTempView refuses an existing name
B: All three lines succeed, because a temporary view with the same name is overwritten by any of the registration methods
C: The second line raises the AnalysisException, because a name that already has a view can never be registered again in a session
D: Only the first line succeeds; the later lines are ignored with a warning and the view keeps the first registration
K: A
G: ## Two ways to register a temporary view
A local temporary view is a name in the session catalog that points to a logical plan. PySpark offers two calls:
- `df.createTempView("v")` creates the view and fails with an `AnalysisException` if a temporary view called `v` already exists in the session.
- `df.createOrReplaceTempView("v")` creates it, or replaces the existing plan under that name.
## Why the difference matters
Notebook cells are re-run all the time. The OrReplace form is idempotent, so a cell can be run again. The strict form is useful when a second registration under a name would be a bug you want to catch.
W: createTempView on a taken name: the first line creates `v`, the second replaces it silently, and the third asks for a plain create on a name that is already registered, so the analyzer rejects it.
X: B=Overwrite assumption: only the OrReplace form overwrites. The plain create form is strict by design, so it cannot be treated as an alias.
C=Second line: this is the OrReplace form, which exists exactly to swap the plan under a taken name, so it succeeds.
D=Silent ignore: Spark does not skip duplicate registrations quietly. The strict call fails loudly and the OrReplace call really replaces the plan.
T: Use createOrReplaceTempView for re-runnable code; plain createTempView fails if the name is taken.

spark.sql("CREATE OR REPLACE TEMP VIEW big AS SELECT * FROM orders WHERE amt > 100")

What is `df2`?

`spark.sql(...)` and `spark.table(...)` both return DataFrames. A `CREATE TEMP VIEW ... AS SELECT` statement registers a name for a query in the session catalog; `spark.table("big")` then returns a DataFrame whose logical plan reads that view.

Neither call starts a job. Filters, joins and aggregations on `df2` are merged into the same plan and optimized together when an action runs.
W: spark.table on a view: the call resolves the name in the catalog and returns a DataFrame whose plan is the view's query. SQL and the DataFrame API share one catalog and one optimizer, so both can be mixed.

B=SQL-only claim: views created with SQL are ordinary catalog entries, and `spark.table` reads tables and views alike.
C=Stored copy: a temporary view does not store data. Without caching, each action re-reads `orders` through the view's plan.

@ DBX-ASD D2 T2.4 advanced comparison
S: A table `default.sales` has 1,000 rows. In the same session a developer runs:
```
spark.range(3).createOrReplaceTempView("sales")
a = spark.sql("SELECT count(*) AS n FROM sales").first().n
b = spark.sql("SELECT count(*) AS n FROM default.sales").first().n
```
What are `a` and `b`?
A: a is 1000 and b is 1000, because a persistent table always wins over a temporary view with the same name
B: a is 3 and b is 3, because registering the view overwrites the persistent table's data in the metastore
C: a is 3 and b is 1000, because the temp view wins for the unqualified name and the qualified name reaches the table
D: Both statements fail with an AnalysisException, because a view and a persistent table cannot share a name in one session
K: C
G: ## Temporary views and tables live in different namespaces
A temporary view belongs to the session, not to a database. When SQL refers to a single-part name, the analyzer checks the session's temporary views before the current database. A qualified name such as `default.sales` is looked up in that database only.
## Practical consequence
A forgotten temp view can silently change the meaning of a query that works in a fresh session. Qualify table names in shared code, or use distinct view names.
W: Name resolution: an unqualified name is looked up among the session's temporary views first. A name qualified with a database skips them and reaches the table.
X: A=Table wins: it is the reverse. A temporary view shadows a persistent table of the same unqualified name.
B=Overwrites the table: a temp view lives only in the session and never touches the metastore entry or its files.
D=Name clash: Spark allows the pair. The view sits in the session's temporary namespace and the table in a database, so no clash.
T: An unqualified name resolves to the temp view first; a database-qualified name reaches the table.

@ DBX-ASD D2 T2.4 applied use-case
S: A table `t` has the ids 1, 2, 3, 4 and 5 in a column `id`. What does this code return?
```
spark.range(1, 6).createOrReplaceTempView("t")
spark.sql("SELECT count(*) AS n FROM t WHERE id > :lo",
          args={"lo": 3}).collect()
```
A: [Row(n=3)], because the bound value is included and the ids 3, 4 and 5 qualify
B: [Row(n=2)], because `:lo` is bound to 3 and the ids 4 and 5 pass the strict comparison
C: An error, because `args` accepts only a list of values and a dict cannot be passed to spark.sql at all
D: [Row(n=5)], because parameter markers are ignored and the predicate is not applied
K: B
G: ## Parameterized queries
`spark.sql(query, args=...)` accepts parameter markers so that values are passed as typed literals instead of being pasted into the SQL text.
- Named markers use `:name` with a dict, for example `args={"lo": 3}`.
- Positional markers use `?` with a list, for example `args=[3]`.
This avoids quoting mistakes and SQL injection from user input, which string formatting of the query does not.
## The example
`spark.range(1, 6)` gives ids 1 to 5. With `id > 3`, only 4 and 5 remain, so the count is 2.
W: Named parameter: `:lo` is a parameter marker, a dict in `args` supplies the values by name, and `id > 3` keeps 4 and 5.
X: A=Inclusive bound: the operator is `>`, not `>=`, so the value 3 itself is excluded.
C=Wrong container: a dict binds named markers (`:name`) and a list binds positional markers (`?`). Both are accepted.
D=Ignored marker: the marker is replaced by the supplied literal during analysis. A missing value would raise an error rather than skip the filter.
T: Pass values with spark.sql(..., args=) and :name markers; do not paste user input into the text.

@ DBX-ASD D2 T2.4 applied troubleshooting
S: A job registers a view in one application: `df.createOrReplaceTempView("daily")`. A scheduled second `spark-submit` application then runs `spark.table("daily")` and fails with a table or view not found error. What is the cause and the fix?
A: The view expired because the default time to live is one day; raise the setting for view lifetime in the session configuration
B: A temporary view lives only in the session that created it; write the data with `saveAsTable` or to files and let the second application read that
C: The second application needs `spark.table("global_temp.daily")`, because the global_temp prefix makes any view visible to every application
D: The name `daily` is a reserved keyword; rename the view and both applications will then find it
K: B
G: ## Scope of a temporary view
- A local temporary view is visible to one `SparkSession` only.
- A global temporary view (`createGlobalTempView`, read with the `global_temp.` prefix) is visible to all sessions of the same Spark application.
- Neither survives the application. Data that must outlive the application or be shared with another one has to be written: `saveAsTable` registers a table in the metastore, and `write.parquet(path)` leaves files.
W: Session scope: the view is a catalog entry in memory of one application. Another application has its own empty catalog, so only persisted data or a metastore table can be shared.
X: A=TTL idea: temporary views have no time to live. They last until the session ends or the view is dropped.
C=global_temp: global temporary views are shared by sessions of the same application only, and disappear when it ends.
D=Reserved name: the failure comes from scope, not spelling. A renamed view would be just as invisible to a different application.
T: Views end with the application; share across applications by persisting a table or files.

@ DBX-ASD D2 T2.4 advanced definition
S: A developer runs the code below. The data in `df` has five rows, and the filter keeps only two of them.
```
df.createOrReplaceTempView("t")
df = df.filter("x > 10")
spark.sql("SELECT count(*) FROM t").show()
```
Which statement about the count in the output is correct?
A: It counts all five rows, because the view captured the original plan and reassigning the variable does not change it
B: It counts two rows, because a view follows the latest value of the Python variable that was registered under its name
C: It counts two rows, because Spark pushes any later filter back into every view that was built from the same DataFrame object
D: It fails, because a view can no longer be queried once the DataFrame it was created from has been reassigned in Python
K: A
G: ## DataFrames are immutable
Every transformation returns a new DataFrame with a new logical plan; the original is untouched. `createOrReplaceTempView("t")` registers the plan of the DataFrame at that moment.
## What the example shows
After `df = df.filter(...)`, the name `df` points to a new object. The view `t` still has the plan without the filter, so the count is 5. To get the filtered data into SQL, register the new DataFrame again under the same name.
W: Immutable plan: `filter` returns a new DataFrame. The name `t` still points to the plan that was registered before the reassignment.
X: B=Variable link: the view stores a plan, not the Python variable name. Rebinding `df` has no effect on the catalog.
C=Pushdown into views: optimizer rules rewrite the plan of one query only. They never edit another registered plan.
D=Dangling view: the old DataFrame object is only a handle. The plan lives in the catalog and stays valid.
T: A view captures the plan at registration; reassigning the variable does not update it.

@ DBX-ASD D3 T3.1 applied definition
S: A DataFrame has one row with `s = 'a-b-c-d'`. A developer evaluates this:
```
from pyspark.sql import functions as F
df.select(F.split("s", "-", 2).alias("p")).first().p
```
What does the expression return?
A: ['a', 'b'], because the limit discards everything after the second element
B: ['a', 'b', 'c', 'd'], because the limit is only used when the pattern is written as a regular expression
C: ['a-b', 'c-d'], because a limit of 2 splits the string into two equal parts
D: ['a', 'b-c-d'], because a limit of 2 caps the array length and the last element keeps the rest of the string

G: ## split(str, pattern, limit=-1)
`F.split` returns an array of strings. The pattern is a Java regular expression, and `limit` controls how often it is applied:
- `limit > 0`: the array has at most `limit` elements and the last one holds all input after the last match.

## The example
With limit 2 the pattern is applied once. The first element is `a`, the second is the rest, `b-c-d`.
W: The limit argument: with a positive limit the pattern is applied at most limit minus one times, and the last entry holds everything after the last match.
X: A=Truncation: nothing is discarded. The last element carries the unsplit remainder.
B=Limit ignored: the limit applies to every pattern, and a plain dash is also treated as a regex.
C=Equal halves: split works left to right on matches and has no notion of balanced parts.
T: split with a positive limit keeps the remainder in the last array element.

@ DBX-ASD D3 T3.1 applied use-case
S: `df` has the columns `id` and `tags` (array of strings) with three rows: `(1, ['x','y'])`, `(2, [])` and `(3, NULL)`. A report must contain one row per tag and must still list ids 2 and 3. The developer runs `df.select("id", F.explode("tags").alias("tag"))`. What is the result and what fixes the requirement?
A: Ids 1, 2 and 3 appear, with null tags for 2 and 3; no change is needed
B: The query fails because explode cannot take a null array; replace the null with an empty array and the problem is solved
C: Only id 1 appears, in two rows; use explode_outer to keep ids 2 and 3 with a null tag
D: Only id 1 appears, in two rows; use posexplode, which also keeps rows whose array is empty or null
K: C
G: ## Generators and empty arrays
`explode` is a generator: each input row produces zero or more output rows.
- `explode(col)` returns a row per array element (or per map entry) and produces no rows for an empty or null collection, so the parent row disappears.
- `explode_outer(col)` returns one row with null for an empty or null collection, so the parent row stays.
- `posexplode` and `posexplode_outer` do the same and add a `pos` column.
## Check for silent row loss
When a join key or id suddenly goes missing after a flatten step, an inner-style explode is the usual cause.
W: explode vs explode_outer: explode emits one row per element and nothing for an empty or null array. The outer variant emits one row with null for those cases.
X: A=Null rows: that is the outer behavior. Plain explode produces no row at all for an empty or null array.
B=Null failure: explode accepts nulls without error. An empty array would be dropped as well, so the replacement would not keep id 3.
D=posexplode: it adds a position column but drops empty and null arrays just like explode. Its outer variant is the one that keeps them.
T: explode drops rows with empty or null arrays; explode_outer keeps them with a null value.

@ DBX-ASD D3 T3.1 advanced tradeoff
S: A feature-engineering step adds 300 derived columns with a Python loop, `for c in cols: df = df.withColumn(c + "_z", expr(c))`. The job takes minutes to plan before any data is read. What is the best change?
A: Call `df.cache()` after each loop pass so every projection is stored and need not be planned again
B: Raise `spark.sql.shuffle.partitions` so that the planning work is spread across many more executor tasks
C: Replace the loop with a `repartition(300)` call so that one task runs for each new derived column
D: Build the expressions first and add them in one `withColumns` or `select` call, so the plan has one projection
K: D
G: ## Where the time goes
Transformations are lazy, but analysis is not: each `withColumn` creates a new logical plan that the analyzer resolves against the previous one. Hundreds of chained calls produce a deep plan and slow driver-side planning.
## What to do
Create the column expressions in a Python list or dict, and add them together:
- `df.withColumns({name: expr, ...})` (available since Spark 3.3), or
- `df.select("*", *exprs)`.
The result is the same data with one projection.
W: Single projection: each withColumn call adds a projection that the analyzer must resolve again. One call with all expressions keeps the plan small.
X: A=Cache: caching stores data after an action, and the planning cost is paid before data is touched. It also fills the storage memory.
B=Shuffle partitions: planning runs on the driver and has nothing to do with the number of shuffle tasks.
C=repartition: it changes data layout at run time. The slow part here is the analysis on the driver.
T: Add many columns in one withColumns or select call, not in a long withColumn loop.

@ DBX-ASD D3 T3.1 advanced troubleshooting
S: `df` has two array columns, `a` and `b`. A developer writes `df.select(F.explode("a"), F.explode("b"))` to get all combinations of their elements, and the query is rejected at analysis. What is the correct way to get the combinations?
A: Wrap both columns in `F.array(...)` and explode the result once, which pairs every element of a with one of b
B: Set `spark.sql.allowMultipleGenerators` to true, then the same select works
C: Use `posexplode` for both columns, which accepts two array columns in a single call
D: Explode one array per step, for example `df.withColumn("x", F.explode("a")).withColumn("y", F.explode("b"))`
K: D
G: ## One generator per select
Spark allows only one generator (`explode`, `posexplode`, ...) in a select list. Two in the same select fail analysis.
## Combinations
Applying the generators in separate steps works. The first step multiplies rows by the length of `a`; the second multiplies again by the length of `b`, so a row with 2 and 3 elements gives 6 rows. Use `explode_outer` if rows with empty arrays must survive.
W: One generator per projection: two generators in one select are not allowed. Chained steps each hold one, and the second multiplies the rows of the first.
X: A=Array of arrays: one explode over that array gives two rows holding whole arrays, not the pairing of single elements.
B=No such setting: Spark does not ship a switch that permits several generators in one select.
C=posexplode: it takes one collection, like explode. Two calls in a single select hit the same rule.
T: Only one explode per select; chain them to produce the cross product of two arrays.

@ DBX-ASD D3 T3.2 applied use-case
S: A table of customer events has several rows per `id`, each with a `ts`. The pipeline must keep exactly the newest row per `id`. Which approach is guaranteed to do that?
A: Sort with `orderBy(F.col("ts").desc())` and then call `dropDuplicates(["id"])` on the sorted data
B: Call `dropDuplicates(["id", "ts"])`, which keeps the row with the highest ts for each id
C: Use `row_number()` over a window partitioned by `id` and ordered by `ts` descending, then keep row number 1
D: Use `distinct()`, which keeps the first row it meets for each id in the order of the input files
K: C
G: ## dropDuplicates does not choose
`dropDuplicates(subset)` keeps one row per distinct combination of the subset columns, but it does not say which one. The result can change between runs and after a shuffle.
## Choosing the row
When the choice matters (latest, highest, first), define it with a window: `row_number().over(Window.partitionBy("id").orderBy(F.col("ts").desc()))`, then `filter("rn = 1")`. An aggregate with `max_by` is another way, but the window keeps whole rows.
W: Window ranking: the order is part of the window specification, so the winner per id is defined by the data.
X: A=Sort then dedup: the dedup is a shuffle on id, and the sort order before it is not preserved, so the surviving row is arbitrary.
B=Subset with ts: this removes only rows that match on both columns. Rows with different ts values per id all stay.
D=distinct: it compares whole rows and does not pick by id. File order is not a guarantee either.
T: dropDuplicates keeps an arbitrary row; use a window with row_number to choose the winner.

S: `df` has the columns `id`, `name`, `ts` and the rows `(1,'a',10)`, `(1,'a',20)`, `(2,'b',30)`. What do `df.distinct().count()` and `df.dropDuplicates(["id","name"]).count()` return?

@ DBX-ASD D3 T3.2 applied use-case
S: `df` has the columns `id`, `c1`, `c2` and the rows `(1,'a','b')`, `(2,NULL,NULL)`, `(3,'x',NULL)`. A validation step runs `df.dropna(how="all", subset=["c1","c2"])`. Which ids remain?
A: Ids 1 and 3, because a row is dropped only when every listed column is NULL
B: Only id 1, because any NULL in the listed columns removes the row
C: Ids 1, 2 and 3, because dropna with a subset reports problems and does not remove rows
D: Only id 3, because how=all keeps the rows that are partly NULL and removes the complete ones
K: A
G: ## dropna parameters
`df.dropna(how, thresh, subset)` (also `df.na.drop`):
- `how="any"` (default) drops a row if any examined column is NULL; `how="all"` drops it only if all examined columns are NULL.
- `thresh=n` keeps rows with at least n non-null values and overrides `how`.
- `subset` limits the columns that are examined; other columns are ignored.
## The example
With subset `c1`, `c2` and `how="all"`, only row 2 has no value in either column.
W: how=all: only row 2 has NULL in both c1 and c2. Row 3 has one non-null value among the listed columns, so it stays.
X: B=how=any: that is the default behavior, and it would drop rows 2 and 3.
C=Report only: dropna really removes the rows that match its rule and returns a smaller DataFrame, it does not flag them.
D=Reversed: rows 1 and 3 are not removed. Row 1 has no NULL at all and stays.
T: dropna(how=all, subset=...) drops rows only if all listed columns are NULL.

@ DBX-ASD D3 T3.2 advanced troubleshooting
S: A validation step splits records into valid and invalid sets:
```
ok  = df.filter(F.col("age").between(0, 120))
bad = df.filter(~F.col("age").between(0, 120))
```
Rows with a NULL `age` are in neither set, and `ok.count() + bad.count()` is lower than `df.count()`. What is the reason and the fix?
A: The between function excludes both bounds, so ages 0 and 120 are missing; use two comparisons with >= and <= instead
B: A NULL age makes the predicate NULL, and a negated NULL is still NULL, so filter drops it; include `age.isNull()` in the invalid set
C: Filter runs lazily, so the two counts were computed on different snapshots of the data; call cache() before both
D: The invalid rows are written to a bad-records folder by the reader and never reach the DataFrame
K: B
G: ## Three-valued logic in filters
In SQL and in Spark, comparisons with NULL yield NULL (unknown). `filter` keeps only rows where the condition is `true`. `NOT NULL` is still NULL, so the row fails both a condition and its negation.
## Writing a complete split
Make the rule total: `bad = df.filter(F.col("age").isNull() | ~F.col("age").between(0, 120))`, or compute the flag once with `coalesce(cond, F.lit(False))`. A final check that the two sets add up to `df.count()` shows silent losses.
W: Three-valued logic: filter keeps a row only when the predicate is true. NOT of NULL is NULL, so the row is lost in both branches.
X: A=Bounds: between is inclusive on both ends. NULL ages are the rows that vanish.
C=Snapshots: both filters read the same plan. Missing NULL rows are a logic outcome, not a timing effect.
D=Bad-records folder: that is a different feature of the file reader. A filter has no such side effect.
T: A filter and its negation both drop NULL rows; handle NULL explicitly in validation splits.

@ DBX-ASD D3 T3.3 advanced tradeoff
S: A dashboard shows the number of unique visitors from a table with billions of events. Exact values are not needed, but memory use and shuffle volume matter. The team wants to tighten the accuracy from the default. Which call fits?
A: `F.approx_count_distinct("visitor_id", rsd=0.5)`, which makes the estimate more exact because it samples half of the rows
B: `F.count_distinct("visitor_id")`, because the approximate function cannot take an accuracy argument
C: `df.sample(0.01).select(F.count_distinct("visitor_id"))`, because a sample gives a count within one percent
D: `F.approx_count_distinct("visitor_id", rsd=0.01)`, which trades a larger sketch for a lower error than the 5% default
K: D
G: ## Exact versus approximate distinct counts
`count_distinct` must track every distinct value, so Spark shuffles values by key and the memory use grows with the number of distinct values.
`approx_count_distinct(col, rsd)` uses the HyperLogLog++ algorithm: each partition builds a small, fixed-size sketch, and sketches are merged. The default maximum relative standard deviation is 5%.
## Tuning
A smaller `rsd` (for example 0.01) improves accuracy, and the sketch grows, so it costs more memory than at the default but still far less than exact counting for high-cardinality columns.
W: HyperLogLog++ sketch: the rsd parameter sets the target relative standard deviation. A smaller value gives more accurate results with a bigger sketch.
X: A=Larger rsd: a higher value allows more error. It is not a sample fraction.
B=No argument: approx_count_distinct accepts rsd, so the claim is wrong and exact counting is costlier.
C=Sampling: the distinct count of a sample is not scaled to the full table, so the estimate is far too low.
T: approx_count_distinct with a smaller rsd tightens the error; it stays cheaper than exact counting.

@ DBX-ASD D3 T3.3 advanced comparison
S: Why is `approx_count_distinct` usually cheaper than `count_distinct` on a column with hundreds of millions of distinct values?
A: It scans one tenth of the rows and scales the result by ten, so most of the input is never read
B: Each partition builds a small HyperLogLog++ sketch and only sketches are merged, instead of moving every distinct value
C: It keeps all the distinct values in the memory of the driver, which avoids using the executors completely
D: It reads column statistics from the Parquet footers instead of the data itself, so no job is needed
K: B
G: ## Why exact distinct counts are costly
A distinct count needs the set of values. Spark first deduplicates (value, group) pairs with a shuffle, then counts, so the shuffle and the hash tables scale with the number of distinct values.
## What the sketch changes
`approx_count_distinct` uses HyperLogLog++. Every task makes a compact sketch of a fixed size for its rows, and partial sketches are merged, so only tiny structures cross the network. The price is an estimation error, with a default maximum relative standard deviation of 5%.
W: Sketch aggregation: the intermediate data per partition has a bounded size, so shuffle volume and memory do not grow with cardinality.
X: A=Sampling: the function reads all rows. It estimates through a sketch and not through a sample.
C=Driver collection: the work is distributed on the executors. Pulling all values to a driver would be less scalable.
D=File statistics: footers hold min, max and null counts, not distinct counts, and the function does not use them.
T: Approximate distinct counting merges small bounded sketches; exact counting must track every value.
