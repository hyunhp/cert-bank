@ DBX-ASD D3 T3.4 applied use-case
S: A DataFrame `events` has a `ts` column of type `bigint` that holds Unix epoch seconds, for example `1767225600`. The report needs a string column such as `2025-12-31` (the calendar date in the session time zone). Which expression produces it?
A: `F.unix_timestamp("ts", "yyyy-MM-dd")`
B: `F.from_unixtime("ts", "yyyy-MM-dd")`
C: `F.to_date(F.col("ts"), "yyyy-MM-dd")`
D: `F.col("ts").cast("date")`
K: B
G: ## Two directions of conversion
Spark keeps three representations of a moment: a number of seconds since 1970-01-01 00:00:00 UTC (a Unix epoch value, `bigint`), a `timestamp`/`date` type, and a formatted string. Each conversion has its own function.
- `from_unixtime(seconds, fmt)` turns epoch seconds into a **string** in the session time zone (`spark.sql.session.timeZone`). The default format is `yyyy-MM-dd HH:mm:ss`.
- `unix_timestamp(string, fmt)` goes the other way: it parses a string and returns epoch seconds as a `bigint`.
- `to_date(string, fmt)` parses a string into a `date`. The format describes how the *input text* looks.
## Example
`F.from_unixtime("ts", "yyyy-MM-dd")` on `1767225600` returns the text `2025-12-31` when the session time zone is a few hours behind UTC, and `2026-01-01` when it is UTC. The pattern letters (`yyyy`, `MM`, `dd`) follow the Spark datetime patterns.
W: from_unixtime: it takes epoch seconds, applies the given pattern in the session time zone and returns a string, which is exactly the requested date text.
X: A=unix_timestamp: this converts a string into epoch seconds, the opposite direction. Passing a number and a date pattern would not give a date string.
C=to_date with a pattern: the pattern describes how to parse a string. A number is not text in the form `yyyy-MM-dd`, so this does not read epoch seconds, and the result would be a `date`, not a string.
D=cast to date: Spark does not cast an integral number to a `date`, so the plan is rejected, and even a successful cast would give a `date`, not the string the report needs.
T: Epoch seconds to a readable string is `from_unixtime`; string to epoch seconds is `unix_timestamp`.

S: A DataFrame `df` has a `date` column `d` with the single value `2024-03-10`, which was a Sunday. What does the following code return?

`df.select(F.dayofweek("d").alias("n")).first()["n"]`
A: `0`, because Spark numbers weekdays from 0 for Sunday
B: `7`, because Sunday is the last day of the ISO week
C: `6`, because Spark numbers weekdays from 0 for Monday
D: `1`, because Spark numbers weekdays from 1 for Sunday
K: D
G: ## Numbering of weekdays in Spark
`dayofweek(col)` extracts the day of the week as an integer from 1 (Sunday) to 7 (Saturday). This is different from the ISO convention (Monday is 1) used by Python's `isoweekday()` and from the zero-based `weekday()` in Python.
- `dayofweek` accepts a date, a timestamp or a string that can be cast to one of them.
- `date_format(d, "E")` returns the name of the day (for example `Sun`), when the numeric value is not needed.
- `weekofyear` and `dayofyear` extract other components in the same way; `year`, `month` and `dayofmonth` exist as well.
## Example
For `2024-03-10` (Sunday) the result is `1`; for the following Monday, `2024-03-11`, it is `2`.
W: dayofweek counts from 1 for Sunday up to 7 for Saturday, so the Sunday 2024-03-10 returns 1.
X: A=Zero-based Sunday: Spark's weekday extraction is one-based; no value `0` is ever returned by `dayofweek`.
B=ISO-style 7: in the ISO week Sunday is day 7, but Spark's `dayofweek` is not ISO numbered; it starts the week on Sunday.
C=Zero-based Monday: this is the Python `datetime.weekday()` convention, which Spark does not follow.
T: `dayofweek` runs 1 (Sunday) to 7 (Saturday); do not assume the ISO or the Python numbering.

@ DBX-ASD D3 T3.4 applied comparison
S: `df` has a `date` column `d` that holds `2026-11-08`. The code below is run and the schema of the result is printed.

`out = df.select(F.date_format("d", "yyyy-MM").alias("a"), F.month("d").alias("b"), F.trunc("d", "month").alias("c"))`

Which data types do columns `a`, `b` and `c` have?
A: `a` string, `b` integer, `c` date
B: `a` date, `b` integer, `c` date
C: `a` string, `b` string, `c` timestamp
D: `a` timestamp, `b` integer, `c` string
K: A
G: ## Which date function returns which type
Extracting, formatting and truncating are three different jobs and their results have different types.
- `date_format(col, pattern)` formats a date or timestamp into text, so it always returns a **string** (`2026-11`).
- `month`, `year`, `dayofmonth`, `hour` and similar extractors return an **integer**.
- `trunc(date, unit)` cuts a `date` down to the start of the year, quarter, month or week and returns a **date** (`2026-11-01`). `date_trunc(unit, timestamp)` does the same for a timestamp and returns a **timestamp** (`2026-11-01 00:00:00`).
## Why it matters
A string like `2026-11` sorts and groups correctly but cannot be used in date arithmetic; the date from `trunc` can be used in `datediff` or range filters.
W: date_format yields text, month yields an int, and trunc on a date column yields a date, so the printed types are string, integer and date.
X: B=date_format as date: a formatted value is text, not a date, even when the pattern looks like a date. Only `to_date` or `trunc` return a `date`.
C=month as string: extractors return numbers (an `int`), and `trunc` of a date column stays a date. A timestamp would come from `date_trunc` on a timestamp.
D=date_format as timestamp: the pattern letters only decide the text layout; the output is a string. `trunc` returns a date, not a string.
T: Format returns string, extract returns int, trunc returns date, date_trunc returns timestamp.

@ DBX-ASD D3 T3.4 applied troubleshooting
S: A delivery report computes the transit time in days with the code below. Orders shipped after they were ordered show negative values such as `-4`.

`df.withColumn("days", F.datediff("order_date", "ship_date"))`

How does the developer fix it?
A: Wrap the result in `F.abs(...)` after converting both columns to timestamps first, so all values are positive
B: Replace `datediff` with `months_between` and multiply the fractional months result by 30 to obtain days
C: Swap the arguments to `F.datediff("ship_date", "order_date")`, because the end date comes first
D: Cast both columns to string first so that Spark compares the two values in calendar order, not numerically
K: C
G: ## Argument order of datediff
`datediff(end, start)` returns the number of days **from start to end**. The later date goes first, which is the reverse of how many people read "difference between order and ship". With the arguments swapped the sign flips.
- The result is an integer number of whole days; time of day is ignored for timestamps because the inputs are cast to dates.
- `date_add(d, n)` / `date_sub(d, n)` move a date by days; `add_months` and `months_between` work in months.
## Example
Order `2026-03-01`, ship `2026-03-05`: `datediff("ship_date", "order_date")` is `4`; with the arguments swapped it is `-4`.
W: With `datediff(end, start)` the shipping date is the end and the order date is the start, so swapping the arguments gives the positive transit time.
X: A=abs on timestamps: it hides the sign but also hides a true data error (a ship date before the order date would look valid), and converting to timestamps changes nothing about argument order.
B=months_between: it returns months as a double, not days, so the unit would be wrong, and it is also negative when the first date is earlier.
D=Cast to string: strings do not give a day count at all; `datediff` expects dates and converts them itself. The sign comes only from the argument order.
T: `datediff(end, start)`: the later date goes first.

@ DBX-ASD D3 T3.4 applied use-case
S: A subscription is billed on the same day each month. For customers whose start date is `2024-01-31`, the renewal date must be the last day of February, `2024-02-29`, and no date may spill into March. Which expression gives the renewal date?
A: `F.add_months("start_date", 1)`
B: `F.date_add("start_date", 30)`
C: `F.trunc(F.date_add("start_date", 30), "month")`
D: `F.next_day("start_date", "Sun")`
K: A
G: ## Month arithmetic versus day arithmetic
Months have different lengths, so adding a month and adding 30 days are different operations.
- `add_months(start, n)` moves the date by `n` calendar months. If the target month is shorter than the day of the month, the result is the last day of that month (`2024-01-31` plus 1 month is `2024-02-29`, because 2024 is a leap year).
- `date_add(start, n)` adds exactly `n` days. `2024-01-31` plus 30 days is `2024-03-01`, which falls in March.
- `last_day(d)` returns the last day of the month of `d`; `trunc(d, "month")` returns the first day.
W: add_months clamps to the end of the shorter month, so one calendar month after January 31 is February 29 in a leap year, which is the required date.
X: B=date_add 30: 30 days after January 31 is March 1 (February 2024 has 29 days), which is exactly the spill into March the requirement forbids.
C=trunc after adding days: it first lands on March 1 and then truncates to the first day of March, so the result is `2024-03-01`, a different month and the wrong day.
D=next_day: it returns the first date after the start that is the given weekday. It has no relation to calendar months.
T: Use `add_months` for monthly schedules; it never spills into the next month.

@ DBX-ASD D3 T3.4 applied comparison
S: A single-row DataFrame has `ts = '2026-11-08 17:45:10'` (cast to `timestamp`). What does `df.select(F.date_trunc("month", "ts"))` return?
A: The `date` `2026-11-01`
B: The string `2026-11`
C: The `timestamp` `2026-11-01 00:00:00`
D: The `timestamp` `2026-11-08 00:00:00`
K: C
G: ## trunc and date_trunc
Both functions cut a point in time down to the start of a unit, but they differ in argument order and in output type.
- `trunc(date, unit)` takes a `date` and a unit (`year`, `quarter`, `month`, `week`) and returns a `date`.
- `date_trunc(unit, timestamp)` takes the unit first, accepts finer units (`day`, `hour`, `minute`, `second` and more) and returns a `timestamp`.
Truncation keeps the type of its family: dates stay dates, timestamps stay timestamps, with the cut-off parts set to their minimum.
## Example
`date_trunc("year", ts)` gives `2026-01-01 00:00:00`; `date_trunc("hour", ts)` gives `2026-11-08 17:00:00`.
W: date_trunc keeps the timestamp type and resets everything below the month to the start: the first day of November at midnight.
X: A=A date value: a `date` result comes from `trunc` on a date column. `date_trunc` always returns a timestamp.
B=A string: only formatting functions such as `date_format` return text. Truncation returns a time type.
D=Day-level truncation: the unit is `month`, not `day`, so the day of the month also goes back to 01.
T: `date_trunc(unit, ts)` returns a timestamp, `trunc(date, unit)` returns a date.

@ DBX-ASD D3 T3.4 advanced troubleshooting
S: The same job runs on two clusters. One has `spark.sql.session.timeZone` set to `UTC`, the other to `America/Los_Angeles`. For the epoch value `0`, `F.from_unixtime(F.lit(0))` returns `1970-01-01 00:00:00` on the first cluster and `1969-12-31 16:00:00` on the second. What explains the difference, and what should the developer do?
A: Spark ignores the session setting and always uses the operating system time zone of each node, so the nodes need identical OS time zones
B: The epoch value itself changes with the time zone, so the source column has to be rewritten with `unix_timestamp` on both clusters
C: The function rounds to the nearest hour in each region, so the developer should pass an explicit pattern such as `yyyy-MM-dd HH`
D: `from_unixtime` renders the instant in the session time zone, so the developer should set the same `spark.sql.session.timeZone` on both clusters
K: D
G: ## Instants and local text
A Unix epoch value names one instant, independent of any time zone. A string such as `1969-12-31 16:00:00` is a local reading of that instant, and it is only meaningful together with a zone.
- `from_unixtime` converts the instant to text using the **session time zone** (`spark.sql.session.timeZone`, default: the JVM zone of the driver unless set).
- The same setting affects casts between timestamp and string, `to_date` of a timestamp, `hour`, `date_format` and similar functions.
- Setting it explicitly in the session (`spark.conf.set("spark.sql.session.timeZone", "UTC")`) or in the cluster configuration makes results reproducible.
## Example
Epoch `0` is midnight in UTC. Los Angeles is 8 hours behind UTC in winter, so the local reading is `16:00` on the previous day.
W: The instant is the same; the text is rendered in each cluster's session time zone, so aligning `spark.sql.session.timeZone` makes both outputs identical.
X: A=Node OS time zone: the OS zone only matters as the default when the session setting is unset; here the setting is explicit, so it decides and aligning operating system zones changes nothing.
B=Epoch changes with zone: epoch seconds are zone independent by definition. `unix_timestamp` would only parse text back to the same number.
C=Rounding to the hour: no rounding happens; the whole 8 hour shift comes from the zone. A different pattern would change the layout of the text, not the instant it shows.
T: Epoch is zone-free; the text from `from_unixtime` depends on `spark.sql.session.timeZone`, so set it explicitly.

@ DBX-ASD D3 T3.5 applied troubleshooting
S: `orders` has `customer_id` values 1, 2, NULL and 4. `customers` has `customer_id` values 1, 2 and NULL. A developer runs `orders.join(customers, "customer_id", "left_anti")` to list the orders without a matching customer. Which rows are returned?
A: Only the order with `customer_id` 4, because a NULL key matches a NULL key
B: The orders with `customer_id` NULL and 4, because a NULL key never equals another key
C: No rows, because every order has a row with the same key in `customers`
D: All four orders, because an anti join with a NULL on both sides is not evaluated
K: B
G: ## NULL keys in joins
A join condition on column names is an equality test, and in SQL semantics `NULL = NULL` is not true. A row whose key is NULL therefore never has a match on the other side, even when the other side also holds NULL.
- `inner` and `left_semi` drop such rows from the result.
- `left` and `left_anti` keep them: with `left_anti` a NULL-key row counts as "no match" and is returned.
- `Column.eqNullSafe` (`<=>` in SQL) treats two NULLs as equal; use it as the condition when NULL keys must match.
`left_anti` and `left_semi` return only the columns of the left side.
## Example
Orders 1 and 2 match. Order 4 has no customer. The order with a NULL key cannot match the NULL customer, so both the NULL order and order 4 are returned.
W: left_anti keeps the left rows without a match; the NULL key never matches, so the rows with NULL and 4 are returned, with orders columns only.
X: A=NULL matches NULL: that is the null-safe comparison (`eqNullSafe`), which a plain column-name join does not use.
C=No rows: the NULL-key order has no equal key on the other side, since NULL equals nothing, and order 4 has no customer at all.
D=All four orders: orders 1 and 2 do match customers 1 and 2 and are removed; only unmatched rows are kept.
T: Join keys with NULL never match, so `left_anti` returns them; use `eqNullSafe` when NULLs must pair up.

@ DBX-ASD D3 T3.5 applied definition
S: `df1` has columns `k1, k2, x` with rows `(1,'a',10)`, `(1,'b',20)`, `(2,'a',30)`. `df2` has columns `k1, k2, y` with rows `(1,'a',100)`, `(1,'a',200)`, `(2,'b',300)`, `(2,'a',400)`. What does `df1.join(df2, ["k1", "k2"])` return?
A: 4 rows with columns `k1, k2, x, y`, because every row of `df2` matches on `k1`
B: 3 rows with columns `k1, k2, x, k1, k2, y`, because the key columns stay on both sides
C: 3 rows with columns `k1, k2, x, y`, where `(1,'a',10)` appears twice
D: 2 rows with columns `k1, k2, x, y`, because duplicate keys are removed first
K: C
G: ## Multi-key joins with a list of column names
When `on` is a list of strings, Spark performs an equi-join on **all** listed columns (they must exist on both sides) and returns each key column **once**, followed by the remaining columns of both sides. Joins do not remove duplicates: a left row is repeated once per matching right row.
- Rows match when `k1` and `k2` are both equal.
- With a list of `Column` conditions (`df1.k1 == df2.k1`) the key columns of both sides stay in the result, which can cause ambiguous names later.
## Example
`(1,'a')` exists once in `df1` and twice in `df2`, so it produces two rows; `(2,'a')` matches once; `(1,'b')` and `(2,'b')` match nothing. Total 3 rows.
W: Matching on both keys gives `(1,'a')` twice (two right rows) plus `(2,'a')` once, with the key columns shown once.
X: A=Matching on k1 only: the join uses both columns, so `(1,'b')` does not match anything and the row count is not 4.
B=Duplicate key columns: the key columns appear twice only when the condition is given as `Column` expressions. A list of names merges them.
D=Deduplicated keys: joins never deduplicate; the repeated right key produces repeated output rows.
T: A list of names joins on all of them and keeps one copy of each key; duplicate keys multiply rows.

@ DBX-ASD D3 T3.5 applied comparison
S: `a` holds the single column `v` with rows 1, 1, 2. `b` holds `v` with the single row 1. A developer compares `a.subtract(b)` with `a.exceptAll(b)`. What do the two calls return?
A: `subtract` returns the rows 1 and 2, and `exceptAll` returns only the row 2
B: Both return only the row 2, because the value 1 occurs in `b`
C: `subtract` returns only the row 2, and `exceptAll` returns the rows 1 and 2
D: `subtract` returns the rows 1, 1 and 2, and `exceptAll` returns only the row 2
K: C
G: ## Set operations on DataFrames
Both methods return the rows of one DataFrame that are missing from another, but they treat duplicates differently.
- `subtract` is SQL `EXCEPT DISTINCT`: it removes duplicates from the result and removes every row that also appears in the other DataFrame.
- `exceptAll` is SQL `EXCEPT ALL`: it keeps duplicates and subtracts one occurrence per matching row of the other side.
- `intersect` / `intersectAll` follow the same split. Columns are matched by position.
## Example
`a` has 1 twice. `subtract` removes all rows equal to 1 and returns `2`. `exceptAll` removes only one `1` (the single row in `b`) and returns `1` and `2`.
W: subtract is a distinct set difference, so 1 disappears completely; exceptAll removes one copy per row of the other side, leaving 1 and 2.
X: A=Swapped behavior: it gives each method the other one's semantics; the distinct variant is the one that drops the value 1 entirely.
B=Both return 2: that holds only for `subtract`; `exceptAll` counts occurrences, and `a` has two 1s against one in `b`.
D=Duplicates in subtract: `subtract` returns distinct rows only, and it would not keep any 1, because 1 is present in `b`.
T: `subtract` = EXCEPT DISTINCT; `exceptAll` = EXCEPT ALL, which respects row counts.

@ DBX-ASD D3 T3.5 applied comparison
S: A team migrates a SQL query that combines two tables with `UNION` into the DataFrame API and writes `a.union(b)`. The row count is now higher than in the SQL result, because `a` and `b` share 1,000 identical rows. What causes the difference, and what restores the SQL result?
A: DataFrame `union` is an alias of SQL `UNION`, so the extra rows come from the join hints; hints must be removed
B: DataFrame `union` behaves like SQL `UNION ALL` and keeps duplicates; add `.distinct()` to match SQL `UNION`
C: DataFrame `union` removes duplicates within each side only; call `unionAll` to remove them across both
D: DataFrame `union` keeps duplicates only for strings; casting the columns to integers removes them
K: B
G: ## UNION versus UNION ALL
In SQL, `UNION` removes duplicate rows from the combined result and `UNION ALL` keeps them. In the DataFrame API there is no deduplicating union:
- `union` and its alias `unionAll` both behave like SQL `UNION ALL` (no deduplication; the docs say to use `distinct()` for that).
- A SQL-style `UNION` equals `a.union(b).distinct()`.
- Deduplication requires a shuffle, so use plain `union` when duplicates cannot occur or do not matter.
## Example
`a` and `b` share 1,000 rows. `a.union(b)` has `count(a) + count(b)` rows; with `.distinct()` the shared rows count once.
W: union is positional UNION ALL and keeps all duplicates; chaining distinct() reproduces SQL UNION, which removes the 1,000 shared rows.
X: A=Alias of UNION: that is the mistaken assumption; the DataFrame method is not deduplicating, and join hints play no role.
C=unionAll: `unionAll` is only an alias of `union` and also keeps duplicates, so it would not change the count.
D=Strings only: duplicates are kept for every data type; casting columns does not remove rows.
T: DataFrame `union` = SQL `UNION ALL`; add `distinct()` to get SQL `UNION`.

@ DBX-ASD D3 T3.5 applied definition
S: A DataFrame `big` has 1,000 rows and `small` has 50 rows with no columns in common. A developer writes `big.join(small)` without a join condition or join type, and no Spark configuration was changed. What happens in current Spark versions?
A: An `AnalysisException` is raised, because a cross join needs `crossJoin` or an explicit `how="cross"`
B: Spark joins on the first column of each DataFrame, because an empty condition falls back to position
C: Spark returns an empty DataFrame, because an inner join without a condition has no matching rows
D: Spark returns the Cartesian product of 50,000 rows, because implicit cross joins are allowed by default
K: D
G: ## Joins without a condition
An `inner` join with no condition matches every left row with every right row: a Cartesian product (a cross join). Since Spark 3.0 the setting `spark.sql.crossJoin.enabled` is internal and true by default, so a join with no condition runs instead of raising the error that Spark 2.x gave.
- `big.crossJoin(small)` or `how="cross"` states the intention explicitly, which is clearer to readers and recommended.
- The result has `rows(big) * rows(small)` rows; this grows very quickly and is almost always unintended on large inputs.
## Example
1,000 x 50 = 50,000 rows. With 1 million x 1 million rows the result would have a trillion rows.
W: Without a condition the join is a cross join, and since Spark 3.0 it is allowed by default, so 1,000 x 50 = 50,000 rows are returned.
X: A=Error on implicit cross join: this was the behavior in Spark 2.x with the old default. Spark 3.0 and later allow it unless the internal configuration is turned off.
B=Positional fallback: Spark never picks join keys on its own; without a condition it does not guess.
C=Empty result: no condition does not mean no match; every pair satisfies "no condition", which is why the result is so large.
T: A join without a condition is a Cartesian product; write `crossJoin` so the intent is explicit.

@ DBX-ASD D3 T3.5 applied use-case
S: `customers` has one row per customer. `orders` has many rows per customer. A report needs the customers that have placed at least one order, each customer exactly once, and only customer columns. Which join does this without a later `dropDuplicates`?
A: `customers.join(orders, "customer_id", "inner")`
B: `customers.join(orders, "customer_id", "left")`
C: `orders.join(customers, "customer_id", "left_semi")`
D: `customers.join(orders, "customer_id", "left_semi")`
K: D
G: ## left_semi as an existence test
A semi join answers the question "does a match exist?". It returns left rows only, once each, however many right rows match, and it never adds right columns.
- `inner` multiplies a left row by the number of matching right rows.
- `left` also multiplies and in addition keeps customers without orders.
- `left_semi` is equivalent to SQL `WHERE EXISTS (...)` / `IN (subquery)`.
- The side that is written first (the receiver of `join`) is the "left" one: `a.join(b, k, "left_semi")` keeps columns of `a`.
## Example
A customer with 40 orders is returned once, as one row with customer columns.
W: customers as the left side with left_semi keeps each customer who has any order exactly once and exposes only customer columns.
X: A=inner: a customer with 40 orders appears 40 times, and the order columns are included, so a later deduplication would be needed.
B=left: it keeps customers with no orders too, and repeats customers per order, so both requirements fail.
