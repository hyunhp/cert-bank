@ DBX-ASD D5 T5.4 applied use-case
S: A streaming job removes repeated events with the code below. No watermark is defined anywhere in the query, and the job runs for months. What happens to the deduplication state?
```
events = spark.readStream.table("raw_events")
deduped = events.dropDuplicates(["guid"])
```
A: Spark keeps state only for the current micro-batch, so a duplicate that arrives in a later micro-batch is written again
B: Spark stores every `guid` it has seen as state with no time-based cleanup, so the state keeps growing for as long as the query runs
C: Spark drops state older than the longest trigger interval that was configured, which makes the state size level off
D: Spark spills the seen `guid` values to the checkpoint and removes them once the sink has acknowledged the write
K: B
G: ## Streaming deduplication needs memory of the past
A batch `dropDuplicates` sees all rows at once. A stream does not: to decide that a new row is a repeat, Spark must remember the rows (or at least the key columns) it has already emitted. That memory is the streaming state, kept by the executors and checkpointed.
## Without a watermark
- Spark may deduplicate on a unique identifier column, with or without event time.
- With no watermark, Spark has no rule that says an old key can never come back, so it keeps every key it has seen as state.
- Deduplication is exact across the whole history, but the state grows without bound and eventually causes memory pressure.
## With a watermark
A watermark tells Spark how late data can be, so state for keys older than the watermark can be dropped. The next questions in this area cover how to combine it with the key columns.
W: Unbounded state: without a watermark nothing tells Spark when a key is safe to forget, so every `guid` stays in state indefinitely.
X: A=Per-batch state: deduplication across micro-batches is the whole point of the state. If state lived for one batch only, repeats in a later batch would pass through, which is not how `dropDuplicates` behaves.
C=Trigger interval cleanup: state cleanup is driven by the watermark, not by the trigger interval. The trigger only controls how often micro-batches start.
D=Sink acknowledgement: the sink acknowledging a write does not release deduplication state. The checkpoint stores state for recovery; it does not decide which keys can be forgotten.
T: Streaming dropDuplicates without a watermark remembers every key forever, so state grows without bound.
V: Structured Streaming

@ DBX-ASD D5 T5.4 applied use-case
S: A team wants exact deduplication of a stream of events that carry `guid` and `event_time`. Duplicates always have the same `event_time` as the original and arrive at most 10 minutes late. They want the state to stop growing. Which query fits?
A: `events.dropDuplicates(["guid"]).withWatermark("event_time", "10 minutes")`, because the watermark added after the deduplication trims its state
B: `events.withWatermark("event_time", "10 minutes").dropDuplicates(["guid"])`, because a watermark alone is enough to bound the state of any key
C: `events.dropDuplicatesWithinWatermark(["event_time"])`, because the event time is the column that the watermark bounds
D: `events.withWatermark("event_time", "10 minutes").dropDuplicates(["guid", "event_time"])`, because the event time column in the key lets old state be dropped
K: D
G: ## Bounding the state of dropDuplicates
Spark documents streaming deduplication with a watermark as: define the watermark on the event-time column, then call `dropDuplicates` with the unique identifier and the event-time column.
```
streamingDf \
  .withWatermark("eventTime", "10 seconds") \
  .dropDuplicates(["guid", "eventTime"])
```
## Why the event time must be in the key
- Spark can only drop a state entry when it can tell that the entry's event time is older than the watermark.
- If the key is only `guid`, no event-time value is part of the state row, so the watermark cannot clean it and the state still grows.
- Order matters as well: the watermark must be defined before the deduplication on the same DataFrame.
## When the event time differs between duplicates
Then it cannot be part of the key, and `dropDuplicatesWithinWatermark` is the tool (Spark 3.5 and later).
W: Watermark plus event time in the key: the watermark gives Spark the cutoff, and the event-time column in the key lets it match state entries to that cutoff and remove them.
X: A=Watermark afterwards: a watermark applied after the deduplication cannot influence state that the earlier operator already holds, and `guid` alone has no event time to expire.
B=Key with only guid: a watermark exists, but the state rows have no event-time value to compare with it, so the documented pattern requires the event-time column in the key.
C=Key on event_time only: that treats different events with the same timestamp as duplicates and loses data. It also swaps the identifier for the wrong column.
T: Streaming dropDuplicates with a watermark must include the event-time column in the key columns so old state can expire.

@ DBX-ASD D5 T5.4 advanced comparison
S: A producer retries failed writes. Each retry gets a new `event_time` stamped at write time, but keeps the same `guid`. Retries arrive within 2 hours of the first write. Which approach removes the duplicates and keeps state bounded?
A: Define a 2-hour watermark on `event_time` and call `dropDuplicatesWithinWatermark(["guid"])`, which ignores event time when matching rows
B: Define a 2-hour watermark on `event_time` and call `dropDuplicates(["guid", "event_time"])`, which treats each retry as the same row
C: Call `dropDuplicates(["guid"])` and set the checkpoint retention to 2 hours so that older keys leave the state
D: Call `distinct()` on the stream, because Spark compares whole rows and then removes the retries after 2 hours
K: A
G: ## Two streaming deduplication APIs
- `dropDuplicates(cols)` with a watermark: the event-time column belongs in `cols`, so rows are duplicates only when both the identifier and the event time are equal.
- `dropDuplicatesWithinWatermark(cols)` (added in Spark 3.5): requires a watermark with a delay threshold, but the event time does not have to be in `cols`. Duplicates are removed when they arrive within the watermark delay of the first copy.
## When to use which
Spark's guide names the second as the answer for cases where the event time cannot be part of the unique identifier, for example a non-idempotent writer that issues the event time at write. Retries then carry different timestamps for the same logical event.
The guide also advises setting the delay threshold longer than the maximum timestamp difference among duplicated events.
W: Within-watermark deduplication: the guid alone identifies the event, the retry timestamps differ, and a 2-hour watermark gives the state a cutoff to expire guids.
X: B=Event time in the key: retries have different `event_time` values, so rows with equal `guid` but different timestamps are not duplicates under that key and all pass through.
C=Checkpoint retention: checkpoint files are not a state expiry mechanism for deduplication keys. Only the watermark lets Spark drop old keys.
D=distinct: `distinct()` compares whole rows, so retries with a new timestamp are not equal. A plain distinct on a stream also has no time-based cleanup without a watermark.
T: Use dropDuplicatesWithinWatermark when duplicates share an id but not an event time; it needs a watermark delay.

@ DBX-ASD D5 T5.4 applied troubleshooting
S: A developer runs the query below on a rate-source stream. The query is rejected before it processes any data. Which change fixes it?
```
df = spark.readStream.format("rate").load()
out = df.dropDuplicatesWithinWatermark(["value"])
(out.writeStream.format("console")
    .option("checkpointLocation", cp).start())
```
A: Switch the output mode to complete, because within-watermark deduplication only supports complete mode on the console sink
B: Replace the key list with `["timestamp"]`, because the method accepts only the event-time column as a key
C: Add `withWatermark("timestamp", "10 minutes")` before the deduplication, because the method requires a watermark delay threshold
D: Call `repartition(1)` before the deduplication, because the state for that method must sit in a single partition
K: C
G: ## What dropDuplicatesWithinWatermark needs
The method deduplicates on the given columns for as long as the watermark says the first copy is still inside the delay. Without a watermark there is no such period, so Spark cannot run it.
- Spark's guide says the feature requires a watermark with a delay threshold to be set on the streaming DataFrame.
- The watermark column does not need to be in the key list.
- Output mode and partitioning are independent of this requirement. Deduplication emits only new rows, so it works with append mode.
## Fix
Define the watermark on the event-time column first, then call the method:
```
df.withWatermark("timestamp", "10 minutes") \
  .dropDuplicatesWithinWatermark(["value"])
```
W: Missing watermark: the query has no `withWatermark`, and the method requires a watermark delay threshold, so adding one on `timestamp` makes the query valid.
X: A=Complete mode: deduplication produces only new rows, so append mode is the natural one. Changing to complete mode does not supply the missing watermark.
B=Key restricted to event time: the method takes any identifier columns, such as `value` here. Using only the event-time column would not deduplicate by id.
D=repartition(1): the state is partitioned by the key and spread across shuffle partitions by design. Forcing one partition would not add a watermark and would hurt parallelism.
T: dropDuplicatesWithinWatermark fails without an earlier withWatermark; the watermark column need not be in the key.

@ DBX-ASD D5 T5.4 advanced tradeoff
S: A job uses `withWatermark("event_time", "1 hour").dropDuplicatesWithinWatermark(["guid"])`. Some duplicates are produced by a batch replay and carry the same `guid` up to 3 hours after the first copy. Some of them still appear in the output. What explains this, and what is the fix?
A: Spark forgets a `guid` once the watermark passes it, so copies later than the delay can pass; the delay must exceed the largest gap between copies
B: Spark deduplicates only within one micro-batch for this method, so every copy in a later batch passes; use `dropDuplicates` instead
C: Spark keeps the first copy only until the executor restarts, so replays are not caught; a larger executor memory setting fixes this
D: Spark matches the event time as well as the `guid`, so replayed copies with other timestamps differ; add the event time to the key
K: A
G: ## Deduplication is bounded by the watermark
Both streaming deduplication styles trade exactness for bounded state. A key is kept in state only while it is inside the watermark window; after that the state is released.
- A copy that arrives within the delay of the first copy is removed.
- A copy that arrives after the state is gone looks like a new event and is emitted.
## Choosing the delay
Spark's guide advises setting the watermark delay threshold longer than the maximum timestamp difference among duplicated events. If copies can be 3 hours apart, a 1-hour delay is too short.
The cost of a longer delay is more state held for longer, and with event-time windows downstream it also delays results. If exactness across unbounded time is required, the only option is deduplication without a watermark, accepting unbounded state.
W: Delay shorter than the gap: the 1-hour watermark releases a `guid` after about an hour, so copies 3 hours later are treated as new; a delay above 3 hours keeps them caught.
X: B=Per-batch scope: deduplication works across micro-batches, within the watermark period. The failure is time based, not batch based.
C=Executor restart: state is checkpointed and restored on restart, so a restart does not forget keys. Memory size is not the reason copies pass.
D=Event time in the key: this method ignores event time when matching on `guid`, so different timestamps are not the cause.
T: Copies later than the watermark delay are not deduplicated; set the delay above the largest gap between copies.
V: Structured Streaming

@ DBX-ASD D6 T6.1 applied definition
S: A PySpark script in a web service uses Spark Connect. What does the client send to the Spark server, and how do results come back?
A: Serialized Python bytecode of the whole script over Py4J, with results returned as pickled rows
B: Optimized physical plans compiled on the client, with results returned as files in a shared directory
C: Unresolved logical plans encoded as protocol buffers over gRPC, with results streamed back as Arrow-encoded batches
D: SQL strings only over JDBC, with results returned as JSON documents that the client parses
K: C
G: ## Client-server split
Spark Connect (introduced in Spark 3.4) decouples the application from the Spark driver. The client is a thin library that builds DataFrame operations but does not run in the driver process.
## What travels over the wire
- The client turns DataFrame operations into unresolved logical plans, encoded with protocol buffers.
- The plans are sent over the gRPC framework to the Spark Connect endpoint on the server.
- The server resolves them into Spark logical plans and runs the normal optimizer and execution, so all Spark optimizations still apply.
- Results are streamed back as Apache Arrow-encoded row batches.
W: Unresolved plans over gRPC: that is the protocol described for Spark Connect, with Arrow batches for results.
X: A=Bytecode over Py4J: the PySpark Connect client does not use Py4J and does not ship the script. It sends plans, not code.
B=Physical plans through files: the client does not plan physically at all. The server does analysis, optimization and physical planning, and results are not exchanged through shared files.
D=SQL over JDBC: Spark Connect is not JDBC. It carries DataFrame operations as plans, and SQL is just one kind of relation inside the same protocol.
T: Spark Connect sends unresolved logical plans as protobuf over gRPC and receives Arrow batches.
V: Spark Connect

@ DBX-ASD D6 T6.1 applied troubleshooting
S: A team moves a PySpark job from a classic driver to a Spark Connect session. Exactly one of the lines below fails, and the others run. Which line fails?
A: `rdd = spark.sparkContext.parallelize(range(10))`, because the protocol describes plans and does not support RDD execution APIs
B: `df = spark.range(10).filter("id > 3")`, because filter conditions cannot be encoded as unresolved logical plans for the server
C: `df.groupBy("id").count().show()`, because aggregations are executed only inside a classic driver process of the cluster
D: `spark.sql("SELECT 1 AS x").collect()`, because SQL text cannot cross the gRPC connection between client and server
K: A
G: ## What Spark Connect does not carry
The Spark Connect protocol describes work declaratively as logical plans. That covers the DataFrame and SQL APIs, but not everything in classic Spark.
- RDDs are not supported, because they are low-level objects tied to the driver JVM and cannot be described as a logical plan.
- The client has no access to `SparkContext` or to the static Spark configuration.
- Private JVM fields such as `df._jdf` are not reachable.
## Migration rule
Code that uses the DataFrame, Spark SQL and Column APIs moves without change. Code that calls `sparkContext`, RDDs or Py4J has to be rewritten with DataFrame operations.
W: RDD API: `spark.sparkContext.parallelize` needs a SparkContext and RDDs, and the Spark Connect protocol supports neither, because it carries logical plans only.
X: B=Filter: filter conditions are core DataFrame operations and are translated into plan nodes like every other transformation, so the line runs.
C=Aggregation: a `groupBy().count()` is sent as a plan and executed on the server with the usual optimizer; only the result is streamed to the client.
D=SQL: `spark.sql` is supported. The client wraps the text into a relation of the plan, and the collected rows come back as Arrow batches.
T: Spark Connect clients use DataFrame and SQL APIs but cannot use RDDs or the SparkContext.
V: Spark Connect

@ DBX-ASD D6 T6.1 advanced use-case
S: One Spark server hosts many notebooks. One analyst's notebook keeps loading a huge pandas DataFrame and runs out of memory, and in the current setup that takes down the driver for every user. What does moving the notebooks to Spark Connect clients change?
A: The server stores each analyst's pandas data in its own isolated pool, so the shared driver never has to receive it
B: The server caps each client at a fixed number of cores, so memory pressure from one user cannot reach other users
C: The client library compresses pandas data before it is shared, so the memory footprint on the driver shrinks a lot
D: Client code runs in its own process, so an application that uses too much memory only affects its own environment
K: D
G: ## Operational benefits
In classic client mode, user code runs inside the driver JVM and its Python process. Anything heavy a user does runs in the same place as scheduling for everyone else on that driver.
Spark Connect separates the two. Spark documents these benefits:
- Stability: applications that use too much memory only affect their own environment because they run in their own processes. Users can define their own dependencies on the client without conflicts with the Spark driver.
- Upgradability: the driver can be upgraded independently of applications.
- Debuggability and observability: applications can be debugged from an IDE and monitored with their own metrics and logging libraries.
## Limit
The server still executes the DataFrame work for the client, so very heavy plans still consume server resources. The isolation is of client-side code and dependencies.
W: Process isolation: the client is a separate process from the driver, so a client that exhausts its memory fails alone and the shared server keeps serving other users.
X: A=Server-side pandas pool: the pandas object lives in the client process. Spark Connect does not host user Python objects in a server-side pool.
B=Core cap: Spark Connect does not impose per-client core limits. The protection comes from running client code in a different process.
C=Compression: the client does not compress user objects to save driver memory; the object was never in the driver in the first place.
T: Spark Connect isolates client code in its own process, so one application's memory problem does not take down the shared driver.
V: Spark Connect

@ DBX-ASD D6 T6.1 applied use-case
S: A platform team runs one Spark server for many applications. A security fix and a performance improvement are released for the server side of Spark. What does Spark Connect allow the team to do?
A: Rebuild and redeploy every application together with the server, because the plan format changes with each release
B: Upgrade the driver on its own, because applications stay compatible while the server RPC definitions are backward compatible
C: Upgrade the applications first, because newer clients can send plans that an older server will rewrite for itself
D: Move every client session to a new server and resend the data, because old servers cannot talk to existing sessions

G: ## Decoupled lifecycles
In classic Spark an application embeds the Spark libraries and runs the driver itself, so upgrading Spark means rebuilding or redeploying the application. With Spark Connect the application depends only on a thin client library and speaks a defined RPC protocol to the server.
- The Spark driver (server) can be upgraded without touching applications, so they benefit from performance improvements and security fixes.
- This holds as long as the server-side RPC definitions are designed to be backward compatible. Applications are then forward-compatible.
## Practical reading
Upgrade the server first and the clients on their own schedule; clients keep working against a newer server within the compatibility promise.
W: Independent upgrade: the protocol is the contract between client and server, so the server can move ahead while client applications stay as they are.
X: A=Joint redeploy: that is the classic embedded model, and avoiding it is exactly what Spark Connect was designed for.
C=Clients first: the documented benefit is that the driver is upgraded independently. An older server does not rewrite plans that it does not understand.
D=Moving sessions and data: client sessions hold plans, not datasets. A server upgrade needs no data movement from the client.
T: Spark Connect lets the server be upgraded independently of applications while the RPC stays backward compatible.

@ DBX-ASD D6 T6.1 applied troubleshooting
S: After switching a notebook to Spark Connect, the helper below fails with an AttributeError. Why does it fail?
```
def jvm_plan(df):
    return df._jdf.queryExecution().toString()
```
A: The method `queryExecution` was renamed in a recent Spark version, and the old name was removed from the JVM class
B: The call needs `spark.sparkContext` first, which a Spark Connect session creates lazily on the first action
C: The DataFrame must be cached first, because an uncached plan has no JVM representation on the server

- The client does not run in the same process as the Spark driver and cannot interact with the driver JVM.
- The client does not use Py4J, so private fields holding the JVM implementation of `DataFrame`, `Column` or `SparkSession` are not available.

Use public APIs that work through the protocol, for example `df.explain()` to see the plans.
W: No Py4J and no JVM object: the Connect client has no JVM handle at all, so the attribute `_jdf` does not exist on the Python DataFrame.
X: A=Renamed method: the failure is raised on the attribute `_jdf`, before any JVM method name is looked up, so the name of the method is irrelevant.
B=Lazy SparkContext: a Spark Connect client has no SparkContext, lazily created or not, and therefore no gateway to a JVM.
C=Caching: caching has nothing to do with JVM access, and every DataFrame already has a plan on the server.
T: Spark Connect clients cannot reach JVM internals; use public DataFrame APIs such as explain().

@ DBX-ASD D6 T6.2 applied definition
S: A developer launches `spark-submit --master yarn app.py` on an edge node and passes no `--deploy-mode` option. Where does the driver run?
A: Inside the `spark-submit` process on the edge node, because the default deploy mode is client
B: On a worker node of the cluster, because the default deploy mode is cluster for YARN

G: ## Deploy mode
The deploy mode says where the driver program runs.
- `client` (default): the driver is launched directly within the `spark-submit` process, which acts as a client to the cluster. The input and output of the application are attached to the console.
- `cluster`: the driver is deployed on one of the worker nodes of the cluster.

`--master` selects the cluster manager (standalone, YARN, Kubernetes) or `local`. The deploy mode is a separate choice. Executors run on the cluster either way.
W: Default client mode: Spark's Submitting Applications page gives client as the default value of `--deploy-mode`, so the driver stays in the submitting process.

C=Gateway service: Spark has no per-application gateway. The driver is a part of the application and is started by the deploy mode.
D=Driver at first executor: executors are requested by an already running driver, so the driver cannot be placed according to where an executor starts.
T: The default deploy mode is client, so the driver runs inside spark-submit.

@ DBX-ASD D6 T6.2 advanced tradeoff
S: A data scientist submits a batch application that runs for hours, from a laptop on a home network far away from the cluster. The laptop is often closed during the day. Which deploy mode is the better choice?
A: Client mode, because the driver stays on the laptop and the console keeps the output attached to the session
B: Cluster mode, because the driver runs next to the executors and does not depend on the laptop staying online
C: Client mode, because a driver on the laptop needs less network bandwidth towards the worker nodes
D: Cluster mode, because it removes the need for a cluster manager in the submission setup
K: B
G: ## Choosing the deploy mode
Spark's guidance:
- Client mode suits a gateway machine physically co-located with the workers. It also suits REPL use, where input and output are attached to the console.
- Cluster mode is the common choice when the application is submitted from a machine far from the workers, such as a laptop, to minimize network latency between the driver and the executors.
## Why driver location matters
The driver schedules every task and must be network addressable from the worker nodes for its whole lifetime. A driver on a laptop across a wide-area link pays latency on every scheduling round, and if the laptop sleeps the application is lost.
W: Cluster mode: the driver is placed on a worker node close to the executors, so latency stays low and the application outlives the laptop session.
X: A=Client mode on the laptop: the driver would sit across a slow link and would disappear when the laptop is closed, which kills the application.
C=Less bandwidth: a remote driver does not reduce traffic; the long distance between driver and executors is the expensive path.
D=No cluster manager: cluster mode still needs a cluster manager, which starts the driver on a worker node of the cluster.
T: When submitting from far away, use cluster mode so that the driver sits next to the executors.

C=No index: pandas API on Spark always has an index; one is attached when the index is unknown.
D=toPandas: it collects everything on the driver, which defeats the purpose and can run out of memory.
T: Avoid the sequence default index for big data; choose a distributed type or name the index column.
