@ DBX-ASD D3 T3.8 applied troubleshooting
S: A developer defines a Python UDF and applies it to a nullable `name` column in which some rows are `null`:

`up = F.udf(lambda s: s.upper(), "string")`
`df.select(up("name")).show()`

What happens?
A: Spark skips the function for null inputs and returns `null` for those rows, so the query finishes without any error
B: The query fails with a Python exception in a worker, because the lambda receives `None` and calls `.upper()` on it
C: Spark passes an empty string for each null, so the function returns an empty string for those rows
D: The analyzer rejects the plan before execution, because a nullable column cannot be passed to a UDF
K: B
G: ## How a Python UDF sees nulls
A Python UDF is ordinary Python code that runs in a Python worker process next to each executor. Spark serializes each row's column values to Python, calls the function, and converts the return value back to the declared `returnType`.
- A SQL `null` arrives in Python as `None`. Spark does not skip the call and does not substitute a default.
- Any exception raised in the function fails the task. After the task retries are used up the whole job fails, and the Python traceback appears in the executor log and in the driver error.
- The UDF documentation shows the safe pattern: test for `None` inside the function (`if s is not None: return s.upper()`), and the function then returns `None`, which becomes `null`.
## Example
`F.udf(lambda s: s.upper() if s is not None else None, "string")` returns `null` for the null rows and the upper-case text for the others.
W: Exception from None: the null reaches the lambda as `None`, `None.upper()` raises `AttributeError` in the worker, and the failed task fails the job after retries.
X: A=Automatic null skipping: Spark never skips a Python UDF for null inputs; null handling is the function's job, so no `null` result is produced for these rows.
C=Empty-string substitution: Spark does not invent a replacement value, and the function would see `None`, not `""`.
D=Plan-time rejection: nullability is irrelevant to analysis of a UDF call; the plan is valid and the failure happens at run time, inside a task.
T: A Python UDF receives `None` for null and fails the job if it does not handle it.

@ DBX-ASD D3 T3.8 applied definition
S: A developer registers a Python function for use in SQL and checks the result type:

`spark.udf.register("name_len", lambda s: len(s))`
`spark.sql("SELECT name_len('test') AS n").printSchema()`

No `returnType` is passed. What is the data type of column `n`?
A: `int`, because Spark infers the type from the Python `len` result
B: `bigint`, because Python integers map to Spark `LongType`
C: None, because `register` requires a return type and raises an error without one
D: `string`, because the return type defaults to `StringType` when it is omitted
K: D
G: ## Registering a UDF for SQL
`spark.udf.register(name, f, returnType=None)` makes a Python function (or an existing UDF from `F.udf` / `F.pandas_udf`) callable by name in SQL and `selectExpr`. It returns the UDF object, so it can also be used in the DataFrame API.
- When `f` is a plain Python function and `returnType` is omitted, the return type is `StringType`. Spark does not infer a type from the Python value.
- The value the function returns must match the declared type; a mismatch usually produces `null` values.
- When `f` is already a UDF, `returnType` must not be given, because the UDF already carries its type.
## Example
`spark.udf.register("name_len", lambda s: len(s), "int")` returns an `int` column; without the third argument the documented example yields the text `'4'` for `'test'`.
W: Default StringType: the registration documentation states that omitting `returnType` works as if `StringType()` was passed, so `n` is a string holding `4`.
X: A=Type inference: Spark does not look at the Python return value to pick a type; the declared or default type is used, so `int` is not chosen automatically.
B=LongType mapping: a long type would only appear when `returnType` is `LongType` or `"bigint"`; here nothing was declared.
C=Required return type: the argument is optional for a Python function, so the call succeeds and uses the default.
T: `register` without a return type gives a string column; declare the type you want.

@ DBX-ASD D3 T3.8 applied use-case
S: A UDF generates a random token per row: `tok = F.udf(lambda: str(random.random()), "string")`. A query uses the same expression `tok()` twice in one select, and the developer needs each call to be treated as an independent, non-repeatable evaluation. What should be changed?
A: Mark the UDF with `asNondeterministic()` so the optimizer does not assume the same output for repeated calls
B: Wrap the UDF in `F.broadcast` so every executor receives the same random seed before running it
C: Register it with `useArrow=False` so each row is serialized through pickle and evaluated exactly once
D: Call `cache()` on the DataFrame afterwards so that the optimizer can no longer merge identical UDF expressions in the plan
K: A
G: ## Determinism is an assumption the optimizer makes
User-defined functions are considered deterministic by default: the same input gives the same output. Because of this, the optimizer may eliminate duplicate invocations, reuse a result, or call the function more times than it appears in the query.
- For a function with side effects or random output, call `.asNondeterministic()` on the UDF. Spark then treats it as nondeterministic and does not rely on the assumption.
- To register a nondeterministic Python function for SQL, build the UDF first, mark it, and register the marked UDF.
## Example
`tok = F.udf(lambda: str(random.random()), "string").asNondeterministic()`.
W: asNondeterministic: this is the documented way to tell Spark that the function must not be treated as deterministic, so repeated calls are not assumed interchangeable.
X: B=F.broadcast: `broadcast` marks a DataFrame as small for joins; it does not apply to UDFs and has no influence on determinism.
C=useArrow=False: the setting only changes how data moves between the JVM and Python (pickle instead of Arrow); it says nothing about determinism or the number of calls.
D=cache(): caching stores computed rows; it does not change how the optimizer treats the UDF in the query plan and would freeze one random value per row instead.
T: A UDF is assumed deterministic unless you mark it with `asNondeterministic()`.

@ DBX-ASD D3 T3.8 advanced troubleshooting
S: A UDF `parse_qty(s)` raises an exception for the text `'n/a'`. The developer guards the call with `df.select(F.when(F.col("raw") != "n/a", parse_qty("raw")))` but the job still fails on rows containing `'n/a'`. What is the reliable fix?
A: Replace `when` with `filter("raw != 'n/a'")` placed after the select, since conditions are applied in order
B: Set `spark.sql.shuffle.partitions` to a smaller value so the failing rows are evaluated on fewer tasks
C: Put the check inside `parse_qty` and return `None` for bad text, because Spark does not short-circuit UDF calls
D: Declare the return type as `string` so that the exception is converted into a `null` value
K: C
G: ## UDFs are not short-circuited
In SQL expressions `CASE WHEN` and boolean operators suggest an evaluation order, but the UDF documentation warns that UDFs do not support conditional expressions or short circuiting: a UDF in a branch can still be executed for rows where the condition is false, and the UDF in a boolean `AND` can run before the other side.
- If the function can fail on special rows, the documented workaround is to put the condition in the function itself.
- Returning `None` produces `null`, which downstream code can filter.
## Example
`def parse_qty(s): return int(s) if s != "n/a" else None`
W: Guard inside the function: the condition then travels with the code, so it holds regardless of the order in which Spark evaluates expressions.
X: A=Filter after select: the plan can still evaluate the UDF before the filter; moving the check to a later step does not guarantee the UDF never sees the bad value.
B=Fewer shuffle partitions: the setting changes the number of shuffle tasks, not which rows the function receives or whether it raises on them.
D=String return type: the return type only converts a successfully returned value; an exception raised inside the function is not converted into `null`.
T: Never rely on `when` or `AND` to protect a UDF; handle bad input inside the function.

@ DBX-ASD D3 T3.8 applied use-case
S: A Structured Streaming job in Python must keep a per-`user_id` session record across micro-batches and receive, for each user, all new rows of the batch as pandas DataFrames. The developer uses `groupBy("user_id").applyInPandasWithState(...)`. Which function shape does the API expect?
A: A function `(key, Iterator[pandas.DataFrame], state)` that updates `state` and returns an `Iterator[pandas.DataFrame]` of output rows
B: A function `(pandas.DataFrame) -> pandas.DataFrame` that is called once per group and keeps its session data in a module-level dictionary
C: A function `(Row) -> Row` that is called once per record and returns the updated session as a tuple
D: A function `(key, pandas.DataFrame) -> int` that returns the number of rows, with the session data held in an accumulator
K: A
G: ## Stateful grouped functions
A grouped function without state (`applyInPandas`) sees only the data of one group of one call. A streaming job that must remember something about a key between micro-batches needs a stateful operator, where Spark stores the per-key state and restores it after a failure.
- `applyInPandasWithState` (added in Spark 3.4, Spark Connect since 3.5) applies a function to each group while it maintains a user-defined per-group state. The function takes `(key, Iterator[pandas.DataFrame], state)`; the key is a tuple, and `state` is a `GroupState` read with `state.get` and written with `state.update(tuple)`.
- The function must return an iterator of pandas DataFrames; the output schema and the state schema are declared as `outputStructType` and `stateStructType`, plus `outputMode` and `timeoutConf`.
- The call needs a full shuffle, and the state lives in the state store, which is checkpointed.
- Since Spark 4.0 the guide encourages the newer `transformWithState` family for new applications; the older operator remains documented.
## Example
`df.groupBy("id").applyInPandasWithState(fn, "id long, n string", "len long", "Update", GroupStateTimeout.NoTimeout)`
W: Key, iterator and state: the documentation states exactly this signature and an iterator of DataFrames as return value, with the state updated by tuple.
X: B=Stateless shape: a one-argument function matches `applyInPandas`; the module-level dictionary is local to one Python worker and is not checkpointed, so it is lost on restart or move.
C=Row function: a per-record function is a plain UDF or `map`; it has no per-group state and does not receive pandas batches.
D=Accumulator as state: accumulators can only be added to in tasks and read on the driver; they are not per-key state and are not the state store.
T: `applyInPandasWithState` takes `(key, Iterator[pdf], state)` and returns an iterator of pandas DataFrames.

@ DBX-ASD D3 T3.8 advanced definition
S: A team builds a new stateful streaming job on Spark 4 with `groupBy("id").transformWithStateInPandas(processor, ...)`. The processor is a `StatefulProcessor` subclass. Where does it declare a persistent state variable, such as a value that counts violations for each key?
A: In the Python class constructor as `self.count = 0`, because instance attributes are checkpointed with the query
B: In `handleInputRows`, by creating a new accumulator for every key on each micro-batch
C: In `init(self, handle)`, by calling a handle method such as `handle.getValueState("numViolations", schema)`
D: In `close()`, which Spark calls after each batch to write the state variables out to the checkpoint
K: C
G: ## transformWithState and its processor
`transformWithState` (Spark 4.0, "arbitrary state API v2") is the operator the Structured Streaming guide recommends for complex stateful applications; `mapGroupsWithState` and `flatMapGroupsWithState` are described as legacy. In Python the grouped API is `transformWithStateInPandas`, which needs protobuf, pandas and pyarrow.
- The user supplies a `StatefulProcessor`. Its `init(handle)` method declares the state variables with the `StatefulProcessorHandle` (for example `getValueState(name, schema)`); `handleInputRows(key, rows)` is called for each key with its new rows and may yield zero or more output rows; `close()` releases resources.
- State variables are read with `exists()` and `get()` and written with `update(tuple)`. They live in the state store and survive restarts through the checkpoint.
- `timeMode` selects timers and time-to-live semantics, and `outputMode` the output mode. The operator needs a full shuffle.
- The documentation example sets `spark.sql.streaming.stateStore.providerClass` to the RocksDB provider.
## Example
`def init(self, handle): self.v = handle.getValueState("numViolations", state_schema)`
W: init with the handle: state variables are created from the handle, so Spark knows them, stores them in the state store and restores them from the checkpoint.
X: A=Constructor attribute: a plain Python attribute lives only in that worker process memory and is neither stored in the state store nor recovered after a restart.
B=Accumulator per key: accumulators are not keyed state; tasks cannot read them and updates are not part of the checkpointed state.
D=close(): this method only releases resources; state variables are written through their own `update` calls during processing.
T: In `transformWithStateInPandas`, declare state in `init` via the handle; plain attributes are not durable state.

@ DBX-ASD D3 T3.8 advanced use-case
S: A streaming deduplication-and-session job holds tens of millions of keys in state. Micro-batch durations vary widely and executor logs show long JVM garbage-collection pauses. The state store is the built-in default. What change targets the cause?
A: Raise `spark.sql.shuffle.partitions` to 2000 so each state store instance becomes small enough to stay on the heap
B: Set `spark.sql.streaming.stateStore.rocksdb.compactOnCommit` to `true` on the default provider to compact state objects
C: Call `cache()` on the streaming DataFrame so state rows are moved from the heap to the storage memory pool
D: Set `spark.sql.streaming.stateStore.providerClass` to `org.apache.spark.sql.execution.streaming.state.RocksDBStateStoreProvider`
K: D
G: ## The state store
A state store is a versioned key-value store that the stateful operators (streaming aggregation, `dropDuplicates`, stream-stream joins, `mapGroupsWithState`, `flatMapGroupsWithState`, `transformWithState`) use to keep state across micro-batches. Updates are committed in sets, each commit incrementing the version, and the state is saved to the checkpoint location for fault tolerance.
- The default provider is the HDFS-backed state store: the state is kept in an in-memory map in the executor JVM and backed by files. With millions of keys, many state objects put pressure on the JVM heap and cause long GC pauses.
- Since Spark 3.2 the RocksDB state store provider keeps state in native memory and local disk instead, with the same fault-tolerance guarantees. Enable it with `spark.sql.streaming.stateStore.providerClass` set to `RocksDBStateStoreProvider`.
- RocksDB tuning options (`compactOnCommit`, block cache size and so on) apply only after the RocksDB provider is chosen.
## Example
`spark.conf.set("spark.sql.streaming.stateStore.providerClass", "org.apache.spark.sql.execution.streaming.state.RocksDBStateStoreProvider")` before the query starts.
W: RocksDB provider: it moves state out of the JVM heap into native memory and disk, which removes the GC pressure that comes from many on-heap state objects.
X: A=More shuffle partitions: this spreads the keys over more state store instances but the state stays on the heap, and changing the count of a running stateful query is not supported with an existing checkpoint.
B=compactOnCommit: this option belongs to the RocksDB provider and does nothing while the default provider is in use.
C=cache(): caching a streaming DataFrame is not how state is held; state is managed by the state store, not by the storage memory pool.
T: Many keys plus GC pauses in a stateful stream point to switching the state store provider to RocksDB.

@ DBX-ASD D3 T3.9 applied use-case
S: A PySpark UDF looks up each customer's region in a 50 MB Python dictionary `lookup` that is referenced directly in the function body, and the UDF is used in several stages. The team wants the dictionary delivered to each executor once instead of being shipped with every task. What do they use?
A: `acc = sc.accumulator(lookup)` so that tasks can read the dictionary from the accumulator value
B: `bc = sc.broadcast(lookup)` and read `bc.value` inside the UDF
C: `df.checkpoint()` on the DataFrame so the dictionary is saved with the lineage
D: `sc.parallelize(lookup)` so each executor owns a slice of the dictionary
K: B
G: ## Shared variables
Normally Spark ships a copy of every variable a function uses to each task. Spark offers two kinds of shared variables for cases where that is wasteful or wrong.
- A **broadcast variable** keeps a read-only value cached on each machine instead of sending it with tasks. It is created with `sc.broadcast(v)` and read with `.value`. Spark already broadcasts the data a stage needs automatically, so explicit broadcast variables pay off mainly when tasks in several stages need the same data, or when the data is large.
- An **accumulator** is a variable that tasks can only add to with an associative and commutative operation; the driver reads the result.
- The broadcast value must not be modified after broadcasting, so that all nodes see the same content.
## Example
`bc = spark.sparkContext.broadcast({"A1": "EU"})`, then `F.udf(lambda k: bc.value.get(k), "string")`.
W: Broadcast variable: it caches the 50 MB dictionary once per executor and tasks read it locally through `.value`, rather than receiving a copy in every task closure.
X: A=Accumulator: accumulators are write-only for tasks and meant for counters and sums; tasks cannot read their value.
C=checkpoint(): this truncates the lineage of a DataFrame by saving its data; it does not distribute a Python object to executors.
D=parallelize: this splits the data into partitions across executors, so no task would hold the full dictionary needed for any lookup.
T: Read-only lookup data used by many tasks belongs in a broadcast variable.

@ DBX-ASD D3 T3.9 applied definition
S: A developer creates `acc = sc.accumulator(0)` and, inside a UDF running on executors, tries to read `acc.value` to decide how to proceed. Which statement describes the Spark accumulator contract?
A: Tasks may add to and read the accumulator, and each read returns the sum of all tasks that finished so far
B: Tasks may read the value, but it only reflects the state at the start of the stage
C: Tasks can only add to an accumulator; only the driver program can read its value
D: Reading works in tasks only when the accumulator has been given a name that is shown in the web UI
K: C
G: ## Accumulators
An accumulator is created on the driver from an initial value (`sc.accumulator(0)`, or `sc.longAccumulator()` / `sc.doubleAccumulator()` in Scala). Tasks add to it with `add` or `+=`. Because the updates must be combinable in any order, the operation has to be associative and commutative.
- Tasks cannot read the value. Only the driver reads it with `.value`. In PySpark an attempt to read it inside a task raises an error.
- Named accumulators appear in the web UI for the stage that changes them (the guide notes that this display is not yet supported in Python); naming has no effect on who may read.
- Typical uses are counters such as the number of malformed records, or sums.
## Example
`acc.add(1)` inside the function; `print(acc.value)` on the driver after an action.
W: Add-only for tasks: the programming guide says tasks running on the cluster can add but cannot read, and only the driver reads `value`.
X: A=Read of running total: executors have no view of other tasks' updates; a running total across tasks exists only on the driver.
B=Stage-start snapshot: tasks have no read access at all, so there is no snapshot to read.
D=Named accumulator: a name only labels the accumulator for the web UI; it does not grant task access to the value.
T: Tasks add to accumulators; only the driver reads them.

@ DBX-ASD D3 T3.9 applied use-case
S: What does this code print?

`acc = sc.accumulator(0)`
`rdd = sc.parallelize([1, 2, 3, 4])`
`mapped = rdd.map(lambda x: acc.add(x) or x)`
`print(acc.value)`
A: `0`, because `map` is lazy and no action has run, so no task has added yet
B: `10`, because the four elements are added to the accumulator as soon as the `map` call is submitted
C: An error, because an accumulator cannot be updated inside `map`
D: `4`, because `map` runs once per partition and adds one per partition
K: A
G: ## Accumulators and lazy evaluation
Accumulators do not change the lazy evaluation model. If an accumulator is updated inside a transformation such as `map`, the value changes only when that RDD is computed as part of an action.
- The snippet defines `mapped` but never runs `count`, `collect` or another action, so no task executes and the driver still sees the initial value.
- After `mapped.count()` the value would be `10`, assuming no task is re-executed.
- For updates done inside actions (such as `foreach`), Spark guarantees that each task's update is applied only once, even when a task restarts. Updates inside transformations carry no such guarantee.
## Example
`mapped.count()` followed by `acc.value` gives `10` for the data above.
W: Lazy map: nothing computes the RDD, so the accumulator keeps its initial value `0` when printed.
X: B=Eager addition: `map` returns immediately and only describes the computation; the additions happen when an action runs the tasks.
C=Update error: tasks may add to accumulators from inside `map`; the guide even uses that pattern to explain lazy behavior.
D=Per-partition add: the function runs once per element, not once per partition, and in any case would run only after an action.
T: An accumulator changed in a transformation has no new value until an action runs.

@ DBX-ASD D3 T3.9 advanced troubleshooting
S: A job counts malformed rows in an accumulator that a UDF inside `withColumn` increments. After an executor was lost and a stage re-executed, the accumulator total is larger than the real number of malformed rows. What explains this?
A: Accumulators are not thread-safe, so concurrent adds from several tasks are counted twice
B: Spark applies each accumulator update twice when a DataFrame is written with `mode("overwrite")`
C: The accumulator value is read on the driver while the tasks are still running, so it holds partial results of retried attempts
D: Updates made inside a transformation can be applied again when tasks or stages are re-executed, unlike updates in actions
K: D
G: ## When accumulators can overcount
Spark guarantees exactly-once accumulator updates only for updates performed inside **actions** such as `foreach`: a restarted task does not add again. For updates in **transformations** (the map-like functions behind `withColumn` and UDFs) each task's update may be applied more than once if a task or a stage is re-executed, for example after executor loss, speculative execution or recomputation of a non-cached DataFrame.
- Use accumulators in transformations only for approximate diagnostics such as monitoring counters.
- For exact counts, compute them with the DataFrame API (`filter(...).count()`) or update the accumulator inside an action.
- Evaluating the same non-cached DataFrame in two actions also repeats the transformation and its updates.
## Example
A UDF that increments `bad_rows` runs again when a lost stage is recomputed, so `bad_rows.value` can exceed the true number.
W: Re-execution: the retried tasks run the UDF again and add again, and Spark only protects against this for updates made in actions.
X: A=Thread-safety: accumulator updates from different tasks are merged by Spark on the driver in a safe way; concurrency does not double count.
B=Overwrite write: the save mode controls how existing files are handled and does not duplicate accumulator updates.
C=Early read: reading early gives a smaller value, not a larger one; the observed excess comes from repeated updates.
T: Accumulator updates in transformations may repeat on retries; only action updates are exactly once.

@ DBX-ASD D3 T3.9 applied troubleshooting
S: A developer counts rows with a Python global and runs the job on a cluster:

`counter = 0`
`def inc(row):`
`    global counter`
`    counter += 1`
`df.foreach(inc)`
`print(counter)`

On the driver, `counter` is still `0`. Which explanation and fix are correct?
A: `foreach` is not an action, so the function never ran; add `.collect()` to start the job
B: Each executor changed its own copy of `counter`; Spark does not send it back, so an accumulator should be used
C: Spark sums the executor copies back into the driver variable only when `spark.sql.shuffle.partitions` is larger than the partition count; raise it
D: The global must be declared with `broadcast` first so that executors can write back to the driver
K: B
G: ## Closures and shared state
When Spark runs a function on the cluster, it serializes the function together with the variables it uses (its closure) and sends copies to the executors. Each task changes its own copy, and the driver's variable is never updated.
- Code that mutates a driver-side variable inside `foreach` or `map` may appear to work in local mode, but Spark does not define or guarantee its behavior on a cluster.
- The programming guide says to use an accumulator when a variable must be safely updated by tasks and read by the driver.
- `foreach` is an action: the function does run, just on copies.
## Example
`acc = sc.accumulator(0)`; `df.foreach(lambda r: acc.add(1))`; `print(acc.value)` gives the row count.
W: Accumulator for shared updates: the executors changed local copies, which is why the driver still sees 0, and an accumulator is the supported way to collect task-side counts.
X: A=foreach not an action: `foreach` is an action and runs the job; the function did execute, only on executor-side copies.
C=Shuffle partitions: this setting controls the number of shuffle partitions and never merges closure copies.
D=Broadcast writeback: broadcast variables are read-only on executors and cannot send values back to the driver.
T: Never mutate driver variables in tasks; use an accumulator.

@ DBX-ASD D3 T3.9 applied comparison
S: A job reuses a broadcast variable `bc` in several stages. After the last use, the developer wants to free its memory on the executors but might use `bc` again in a later job and accept that it would be sent again. Which call fits?
A: `bc.unpersist()`, which releases executor copies and re-broadcasts the value on next use
B: `bc.destroy()`, which releases the executor copies permanently and lets `bc` be reused in later jobs with a fresh broadcast
C: `del bc.value`, which removes the data from the executors and keeps the handle valid
D: `sc.broadcast(None)`, which replaces the executor copies and clears the old value
K: A
G: ## Releasing a broadcast variable
A broadcast variable occupies memory on every executor until it is released.
- `unpersist()` removes the copies from the executors. If the variable is used again, Spark re-broadcasts it from the driver.
- `destroy()` permanently releases all resources used by the variable; it cannot be used afterwards.
- Both calls are non-blocking by default; pass the blocking option to wait until the resources are freed.
- Do not change the broadcast object after it was broadcast, so that all nodes see the same value.
## Example
`bc.unpersist()` after stage N; a later `bc.value` use triggers a new broadcast. `bc.destroy()` makes any later use fail.
W: unpersist: it frees the executor copies but keeps the variable valid, which matches the need to reuse it later at the cost of sending it again.
X: B=destroy: it releases resources permanently, so the variable cannot be used again.
C=Deleting value: `value` is read access to the data; it does not manage executor memory, and the executor copies would remain.
D=New broadcast of None: creating another broadcast does nothing to the earlier variable's copies; they stay until released.
T: `unpersist()` frees executor copies but allows reuse; `destroy()` is final.

@ DBX-ASD D3 T3.10 applied use-case
S: A batch job joins `orders` (3 TB) with `countries` (2 MB) using `orders.join(F.broadcast(countries), "country_code")`. What does `F.broadcast` do here?
A: It persists `countries` on the driver only and forces a sort-merge join on both inputs
B: It copies the large `orders` table to every executor so that each task can filter and join it locally without any network transfer
C: It marks `countries` as small enough to be sent to every executor, so `orders` is not shuffled
D: It repartitions `countries` by `country_code` to match the partitioning of `orders`
K: C
G: ## Purpose of the broadcast join
A shuffle join (sort-merge or shuffle-hash) moves both inputs across the network so that equal keys meet. With a very large and a very small input, most of that cost is wasted on the large side.
- In a **broadcast hash join** the small side is collected, sent to every executor and held as a hash table; each partition of the large side is joined locally. The large side is not shuffled.
- `pyspark.sql.functions.broadcast(df)` marks a DataFrame as small enough for broadcast joins. It is the same as the SQL hint `BROADCAST`.
- The small side must fit in driver and executor memory; sizes above that make the broadcast fail.
## Example
`orders.join(F.broadcast(countries), "country_code")` runs as a `BroadcastHashJoin` in the plan, without an exchange on `orders`.
W: Marks the small side for broadcast: every executor receives `countries`, so `orders` partitions are joined in place without a shuffle.
X: A=Driver-only copy: the broadcast goes to executors, and the purpose is to avoid the sort-merge join that would shuffle `orders`.
B=Broadcasting orders: the hint is on the small DataFrame; broadcasting a 3 TB table would exhaust memory.
D=Repartitioning: a repartition by key is a shuffle (the cost the broadcast avoids), and `broadcast` does not partition anything.
T: `F.broadcast(small)` sends the small side to all executors so the big side is not shuffled.

## Example
Static `-1`, adaptive unset: the 3 MB side stays in a sort-merge join. Adaptive set to `10MB`: AQE can convert it.
W: Default inheritance: the adaptive threshold takes the static value when not set, so with `-1` AQE has no threshold to convert with.
X: A=Ignoring the static value: the documented default of the adaptive threshold is the static one, so the static setting matters.
B=Failure: two settings that resolve to the same value do not conflict, and nothing makes the query fail.
D=Local shuffle reader: this controls shuffle reading after a conversion and has no effect on the decision.
T: The AQE broadcast threshold falls back to the static one; `-1` switches off both.
