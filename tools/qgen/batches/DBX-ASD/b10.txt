@ DBX-ASD D1 T1.5 expert troubleshooting
S: A nightly join-and-aggregate job shuffles about 1.6 TB. AQE is enabled with default adaptive settings, and the platform team forbids turning it off. A year ago an engineer put `spark.sql.shuffle.partitions=200` into the job configuration with the comment "AQE will size partitions anyway". The Stages tab for the post-shuffle stage now shows 200 tasks, a median shuffle read of about 8 GB per task, several terabytes of Spill (Disk) in total, and a duration of three hours. The cluster has 400 cores and healthy executors. Input grows about 10% a month, so the fix should keep working as volume grows without daily retuning. Which change addresses the evidence?
A: Set spark.sql.adaptive.coalescePartitions.initialPartitionNum to about 16000, so the shuffle starts near 100 MB partitions and AQE merges any that end up small
B: Set spark.sql.adaptive.advisoryPartitionSizeInBytes to 16 MB, so that AQE splits each 8 GB post-shuffle partition into many smaller ones after the shuffle stage
C: Set spark.sql.adaptive.coalescePartitions.minPartitionSize to 100 MB, so AQE builds the post-shuffle partitions at that size and no task has to read 8 GB
D: Set spark.sql.adaptive.coalescePartitions.parallelismFirst to false, so that AQE stops coalescing for parallelism and resizes the 200 partitions to its advisory size
K: A
G: ## AQE can merge partitions, not create more
After a shuffle stage, AQE's coalescing merges **contiguous small** partitions toward a target size. It starts from `spark.sql.adaptive.coalescePartitions.initialPartitionNum`; if that is unset, the start is `spark.sql.shuffle.partitions`. So the count you set is a **ceiling**: AQE can reduce it but never raise it. Splitting oversized partitions happens only for skewed partitions in shuffled joins and for `REBALANCE`, where one partition is far above the median, not when every partition is large.
## The numbers
1.6 TB / 200 partitions = 8 GB per task: far more than execution memory, hence the spill. 1.6 TB / 16,000 = 100 MB per partition, a healthy size. With a high initial number, AQE coalesces back down on smaller nights, so the setting tolerates growth. The tuning guide says the same in general: when a task's working set is too large, raise parallelism so each task's input is smaller.
W: initialPartitionNum 16000: AQE gets a high starting count to coalesce from, so tasks read about 100 MB instead of 8 GB and stop spilling.
X: B=Smaller advisory size: the advisory size guides coalescing and skew splitting; equal 8 GB partitions are not skewed, so AQE has nothing to split and nothing small to merge.
C=minPartitionSize 100 MB: it is a floor for coalesced partitions; it cannot cut 200 partitions of 8 GB into smaller ones.
D=parallelismFirst false: it changes how far AQE coalesces toward the advisory size; it still cannot exceed the starting count of 200.
T: Under AQE the initial shuffle partition count is a ceiling; set it high and let AQE coalesce down.

@ DBX-ASD D1 T1.4 expert troubleshooting
S: A four-hour batch job runs on a shared YARN cluster whose high-priority queue often preempts containers of this job; the nodes themselves stay up. When an executor is preempted during stage 7, a reduce stage, several of its tasks fail with `FetchFailedException`, and the Spark UI then shows stage 6, which had completed an hour earlier, as a new attempt that reruns many of its map tasks before stage 7 continues. The YARN administrators already run the Spark shuffle service as a NodeManager auxiliary service on every node, and the team cannot change queue priorities. Which change stops completed map output from being recomputed after a preemption?
A: Set spark.shuffle.service.enabled to true for the job, so the node's shuffle service keeps serving map output files written by a preempted executor
B: Set spark.stage.maxConsecutiveAttempts to 16 for the job, so stage 6 can be resubmitted many more times before the whole job is aborted
C: Set spark.task.maxFailures to 16 for the job, so the failed reduce tasks of stage 7 retry the fetch more often before the stage is resubmitted
D: Call cache() on the DataFrame produced by stage 6, so its map output is kept in executor storage memory and survives a preempted executor
K: A
G: ## Where shuffle files live
A map stage writes its shuffle output as files on the local disk of the executor's node. A reduce stage fetches those blocks from the executors that wrote them. Spark keeps shuffle files so that later stages, or a recomputed lineage, do not need to recreate them.
## What happens when an executor is lost
Without an external shuffle service, the executor itself serves its shuffle files. When the executor disappears, its blocks cannot be fetched: reducers raise `FetchFailedException`, and the scheduler resubmits the **parent map stage** to regenerate the missing output. `spark.stage.maxConsecutiveAttempts` (default 4) limits these consecutive attempts.
## The external shuffle service
`spark.shuffle.service.enabled=true` makes executors register their shuffle files with a long-running service on the node (on YARN, a NodeManager auxiliary service). The configuration docs say it preserves shuffle files so executors can be removed safely or shuffle fetches can continue when an executor fails. Since the nodes stay up, the files remain readable after a preemption.
W: External shuffle service: the files outlive the preempted executor because the node's service serves them, so stage 6 does not rerun.
X: B=More stage attempts: the job survives longer, but every preemption still reruns completed map work, which is what the team wants to stop.
C=More task failures: the missing files do not come back with retries; a fetch failure leads to a resubmission of the map stage anyway.
D=cache() the DataFrame: cached blocks also live in the lost executor, and the reduce stage reads shuffle files, not cached DataFrame blocks.
T: With the external shuffle service, map output survives executor loss on a healthy node; without it, the parent stage is recomputed.

@ DBX-ASD D1 T1.3 expert troubleshooting
S: A team packages helper functions in a wheel that many PySpark jobs import. One helper, `write_report(df, path)`, ends with `spark.stop()` "to free resources". In a job that calls the helper and then keeps working with an `orders` DataFrame that was cached before the call, the next action fails with an error that methods cannot be called on a stopped SparkContext. A colleague proposes calling `SparkSession.builder.getOrCreate()` right after the helper. The job runs on a classic cluster without Spark Connect, the cached `orders` data must be reused after the helper returns, and the helper's signature must not change. Which fix is correct?
A: Remove spark.stop() from the helper and stop the session once at the end of the job's entry point, so the context and the cached data live for the whole job
B: Keep spark.stop() in the helper and call SparkSession.builder.getOrCreate() after it, so the job continues on a new context that still holds the cached data
C: Replace spark.stop() in the helper with spark.catalog.clearCache(), so the helper frees memory but leaves the context and the job's cached data available
D: Replace spark.stop() in the helper with spark.newSession().stop(), so only a child session is stopped while the job's own session and its cache keep running
K: A
G: ## Session, context and their lifecycle
In classic PySpark, a `SparkSession` wraps one `SparkContext`, the connection to the cluster that owns executors, cached blocks and broadcast variables. `SparkSession.stop()` **stops the underlying SparkContext**. Every session of the application, including those from `newSession()`, shares that context, so stopping any of them stops all of them.
After a stop:
- DataFrames built on the old context can no longer run actions.
- `getOrCreate()` builds a **new** context with new executors; nothing cached before (data, temp views) carries over.
## Who should stop the session
The code that creates the application (the job's entry point) owns its lifecycle and stops it once at the end. Library helpers should never stop a session they did not create.
W: Remove stop from the helper: the context lives until the entry point ends it, so the cached orders data stays usable after the helper returns.
X: B=getOrCreate after stop: it creates a new context; the old cache and executors are gone, so orders must be recomputed and its DataFrame object still points at the stopped context.
C=clearCache in the helper: the context survives, but every cached table and DataFrame is removed, so the cached orders data is lost.
D=Stop a new session: newSession shares the same SparkContext, and stop() stops that context, so the job fails in the same way.
T: SparkSession.stop() stops the shared SparkContext; only the application's entry point should call it, once.

To fail fast, the developer calls `df2.count()` right after it, which succeeds in two minutes. The following `df2.write.parquet(out)` then fails after 40 minutes with a Python exception raised inside `parse_udf` on a malformed payload, and running `count()` again still succeeds. Nothing is cached, and the input files did not change between the calls. The team wants a pre-check that evaluates the UDF on every row and writes nothing. Which statement explains the evidence and gives a working pre-check?
A: count() needs no columns, so the optimizer drops the unused UDF column; df2.filter(F.col("parsed").isNull()).count() references it and runs the UDF
B: count() reads Parquet footer row counts only; adding option("mergeSchema", "true") to the read makes the next count() run the UDF on every row
C: count() hides Python exceptions from the UDF; enabling spark.sql.execution.pyspark.udf.faulthandler.enabled makes the next count() raise them
D: count() reused an earlier job's result through AQE; setting spark.sql.adaptive.enabled to false makes the next count() run the UDF on every row
K: A
G: ## Lazy evaluation plus column pruning
Transformations only build a plan; an action triggers optimization of the whole plan. Catalyst's **column pruning** removes expressions whose results nothing uses. `count()` needs the number of rows, not the `parsed` column, so the projection that calls the UDF is pruned away and the UDF never runs. Reference the column in a way the action needs: `df2.filter(F.col("parsed").isNull()).count()` must compute `parsed` for every row (and also counts parse failures if the UDF returns NULL for them). `df2.select("parsed").write.format("noop").save()` is another option.
W: Column pruning: count() does not need parsed, so the UDF is pruned; a filter on parsed forces the UDF to run on every row before the write.
X: B=Footer row counts plus mergeSchema: mergeSchema only merges file schemas; count() over df2 would still not need the parsed column.
C=Hidden exceptions: count() never called the UDF, so there was nothing to hide; the faulthandler setting only adds tracebacks for crashes of Python workers.
D=AQE reuse: AQE re-plans around shuffles and does not reuse results across actions; with or without it, count() prunes the UDF column.
T: Actions compute only what they need; count() can skip a UDF column entirely, so validate by using the column.

@ DBX-ASD D2 T2.1 expert troubleshooting

It was written two years ago, when ids stopped near one million. The table now has 180 million rows with ids from 1 to about 180,000,000, spread roughly evenly. The Stages tab shows 19 read tasks finishing in seconds with about 50,000 rows each and one task running for hours with almost all of the rows. The database allows at most 20 concurrent connections from this job, and every row must still be read. Which change fixes the evidence?
A: Set upperBound to 180000000 and keep numPartitions at 20, so the stride grows to about 9 million ids and each read task gets a similar share
B: Raise numPartitions to 200 and keep upperBound at 1000000, so the stride shrinks to about 5,000 ids and the rows spread over more read tasks
C: Keep the bounds and add the predicate payment_id <= 1000000 to the read, so the last read task no longer receives the rows above the upper bound
D: Keep the bounds and set fetchsize to 100000, so the last read task fetches its rows in fewer round trips and finishes as quickly as the others
K: A
G: ## How a partitioned JDBC read splits rows
With `partitionColumn`, `lowerBound`, `upperBound` and `numPartitions`, Spark builds one WHERE clause per partition from a **stride** of about `(upperBound - lowerBound) / numPartitions`. The docs stress that the bounds only decide the stride and **do not filter**: all rows are returned. The first partition takes everything below the second boundary (including NULLs), and the **last partition takes everything at or above its start**.
## The numbers

With `upperBound=180000000`, the stride is about 9,000,000 ids and each of the 20 tasks reads about 9 million rows. `numPartitions` also caps concurrent connections, so 20 matches the database limit.
W: upperBound at the real max id: the stride covers the actual id range, so the 20 connections each read a similar share of the 180 million rows.
X: B=More partitions with old bounds: the last partition still starts near one million and takes about 179 million rows, and 200 partitions exceed the 20-connection limit.
C=Filter at the upper bound: it removes every row above one million, so about 179 million rows would never be read.
D=Larger fetchsize: fewer round trips help a little, but one task still reads almost all rows alone.
T: JDBC bounds set the stride, not a filter; stale bounds put everything outside them into the first or last partition.

S: A daily backfill rewrites a year of events with `events.write.mode("overwrite").partitionBy("event_date").parquet(out)`. The input has 400 scan partitions of about 256 MB each, and rows from all 365 dates are spread across every input partition. The output has about 146,000 files averaging 0.7 MB, and the downstream engine lists them slowly. Each date holds about 280 MB and no date exceeds 1 GB. The output must stay partitioned by `event_date`, and the team wants one file of a few hundred megabytes per date. AQE is on with default settings. Which change before the write fixes the file count?
A: Call events.repartition("event_date") before the write, so each date's rows land in one task and every date folder receives one file
B: Call events.coalesce(365) before the write, so the 400 scan partitions merge into 365 tasks and every date folder receives one file

D: Set spark.sql.files.maxRecordsPerFile to 0 before the write, so each task writes all rows of a date into one file in every date folder

G: ## Files per partitioned write
With `partitionBy`, each write task writes **one file per partition value it holds**. Total files = sum over tasks of the distinct dates in that task.
- Here: 400 tasks x 365 dates = 146,000 files; 100 GB / 146,000 = about 0.7 MB each.

`repartition("event_date")` hash-partitions by the column, so all rows of one date go to the same shuffle partition. Each date is written by one task: 365 files of about 280 MB. - `repartition(365)` is round-robin: every partition gets rows of every date.
- `maxRecordsPerFile` only **caps** rows per file (0 = no cap, the default); it can add files, never merge across tasks.
W: repartition by event_date: all rows of a date meet in one task, so each date folder gets a single file of about 280 MB.
X: B=coalesce(365): merged tasks still contain rows of every date, so each writes up to 365 files.
C=repartition(365) without a column: round-robin spreads every date over all 365 tasks.
D=maxRecordsPerFile 0: it is already the default, meaning no limit per file; files are still one per task and date.

@ DBX-ASD D2 T2.3 expert troubleshooting
S: `sales` is stored as Parquet folders partitioned by `year` and `month` (for example `year=2026/month=11`), with an `order_date` DATE column inside the files. Analysts run `SELECT sum(amount) FROM sales WHERE order_date BETWEEN DATE'2026-11-01' AND DATE'2026-11-07'`. In the SQL tab, the scan node reports 96 partitions read, the full eight years, although the matching rows all sit in one month, and the query reads far more files than expected. The layout cannot be rewritten this quarter, and analysts must keep filtering by `order_date`. Which change lets Spark skip the other partition folders?
A: Add AND year = 2026 AND month = 11 to the WHERE clause, so a predicate on the partition columns lets Spark prune the folders before files are listed
B: Add the hint /*+ REPARTITION(year, month) */ to the query, so Spark groups the scan by the partition columns and reads only the matching folders
C: Write the range with string literals such as '2026-11-01', so the predicate on order_date is pushed into the Parquet reader and prunes the folders
D: Enable spark.sql.parquet.filterPushdown for the session, so the predicate on order_date reaches the Parquet reader and prunes the partition folders
K: A
G: ## Two kinds of skipping
- **Partition pruning** works on partition columns only (`year`, `month`): their values live in folder names, so Spark knows before listing files which folders can match. A filter on a partition column skips whole folders.
- **Parquet filter pushdown** (on by default with `spark.sql.parquet.filterPushdown`) applies to data columns such as `order_date`: Spark still opens every file in every folder and uses row-group statistics to skip blocks inside them.
Spark cannot derive `year = 2026 AND month = 11` from a condition on `order_date`, because it does not know the relationship between the data column and the folder values.
## The fix
Keep the analysts' filter and add the matching partition predicate:
`WHERE order_date BETWEEN DATE'2026-11-01' AND DATE'2026-11-07' AND year = 2026 AND month = 11`
The SQL tab then shows one partition read.
W: Partition predicate: filters on year and month are known at planning time, so Spark lists and reads only the one matching folder.
X: B=REPARTITION hint: it adds a shuffle of the scanned rows after the scan; it does not change which folders are read.
C=String literals: they change only how the date is written; it is still a data-column predicate, which cannot prune folders.
D=filterPushdown: it is already on by default and works inside files through row-group statistics; every folder is still listed and opened.
T: Only predicates on partition columns prune folders; add them alongside data-column filters.

@ DBX-ASD D2 T2.3 expert troubleshooting
S: Two tables were saved with `bucketBy` and `sortBy` on `customer_id` through `saveAsTable`: `orders_b` with 64 buckets and `customers_b` with 16 buckets. A daily query `spark.table("orders_b").join(spark.table("customers_b"), "customer_id")` still shows an Exchange above one of the two scans in the physical plan, although the team expected a shuffle-free join. Rewriting the 40 TB `orders_b` with 16 buckets is not possible this quarter, `spark.sql.sources.bucketing.enabled` is at its default, and the join must remain a sort-merge join. Which single setting change removes the Exchange?
A: Set spark.sql.bucketing.coalesceBucketsInJoin.enabled to true, so the 64-bucket side is read as 16 coalesced buckets that match the other side
B: Set spark.sql.bucketing.coalesceBucketsInJoin.maxBucketRatio to 16, so the 64-bucket side is read as 16 coalesced buckets that match the other side
C: Set spark.sql.shuffle.partitions to 64, so that the 16-bucket side is read as 64 bucket partitions that match the buckets of the other side
D: Set spark.sql.sources.bucketing.enabled to true, so both tables are read bucket by bucket and the planner stops inserting the Exchange
K: A
G: ## When bucketing avoids a shuffle
A sort-merge join needs both sides hash-partitioned the same way on the join key. Two bucketed tables satisfy this without a shuffle when they are bucketed on the join key with the **same number of buckets**. With 64 and 16 buckets, partition k of one side does not match partition k of the other, so the planner inserts an Exchange on one side.
## Bucket coalescing
`spark.sql.bucketing.coalesceBucketsInJoin.enabled` (default **false**): when two bucketed tables with different bucket counts are joined, the side with more buckets is coalesced to the other side's count. The larger count must be divisible by the smaller, and the ratio must be at most `spark.sql.bucketing.coalesceBucketsInJoin.maxBucketRatio` (default **4**). It applies to sort-merge and shuffled hash joins.
Here 64 / 16 = 4: divisible and within the default ratio, so turning the feature on is enough. The docs warn that coalescing reduces parallelism.
W: coalesceBucketsInJoin enabled: 64 is divisible by 16 with a ratio of 4, within the default limit, so both sides line up and the Exchange disappears.
X: B=maxBucketRatio only: it raises the allowed ratio, but coalescing itself stays disabled by default, so nothing changes.
C=Shuffle partitions 64: the 16-bucket side would still be reshuffled to match; that Exchange is exactly what the team wants to remove.
D=bucketing.enabled: it is already true by default; bucketed reads are on, and the mismatch in bucket counts is the cause.
T: Bucketed joins skip the shuffle only with matching bucket counts; coalesceBucketsInJoin can align divisible counts.

@ DBX-ASD D3 T3.10 expert troubleshooting
S: A report must list every campaign with its click count, including campaigns with zero clicks. The developer writes `F.broadcast(campaigns).join(clicks, "campaign_id", "left").groupBy("campaign_id").count()`, where `campaigns` is 40 MB and `clicks` is 6 TB. AQE is on. The physical plan shows a SortMergeJoin with Exchanges on both sides, and the 6 TB shuffle dominates the run. The developer notes that a broadcast hint should override `spark.sql.autoBroadcastJoinThreshold`. Executor memory comfortably holds 40 MB, and the counts must stay identical, with 0 for campaigns without clicks. Which rewrite lets Spark avoid shuffling the raw clicks into the join?
A: Count clicks per campaign_id first, then campaigns.join(F.broadcast(counts), "campaign_id", "left") and fill missing counts with 0
B: Raise spark.sql.autoBroadcastJoinThreshold to 100 MB and keep the left join with campaigns on the left, so campaigns is broadcast automatically
C: Rewrite it as clicks.join(F.broadcast(campaigns), "campaign_id", "right"), so the hinted campaigns side becomes the broadcast build side
D: Keep the left join and replace the hint with F.broadcast(clicks), so Spark broadcasts the right side of the left outer join to every executor
K: A
G: ## Which side can be broadcast
A broadcast hash join builds a hash table from the broadcast (**build**) side on every executor and streams the other side's partitions through it. For an outer join, the **preserved** side must emit rows even when they have no match; a task that only sees part of the streamed side cannot know whether a build-side row matched anywhere else. So the build side must be the **non-preserved** side: the right side of a left outer join, the left side of a right outer join.
The tuning guide states that Spark does not guarantee the hinted strategy, because a strategy may not support every join type. Here `campaigns` is the preserved side, so the hint cannot be honored and Spark falls back to a sort-merge join.
## Making the big side small
Partial aggregation shrinks 6 TB of clicks to one row per campaign before any join:
`counts = clicks.groupBy("campaign_id").count()`
`campaigns.join(F.broadcast(counts), "campaign_id", "left").fillna(0, ["count"])`
Now the small, non-preserved side is broadcast, and campaigns without clicks get 0.
W: Aggregate then broadcast counts: the raw clicks never enter the join, and the per-campaign counts sit on the non-preserved side, where a broadcast is allowed.
X: B=Higher threshold: size was never the problem; campaigns is the preserved side of the outer join, so it cannot be the build side.
C=Right join with hint: campaigns is still the preserved side, now on the right, so the broadcast is not possible and the plan stays a sort-merge join.
D=Broadcast clicks: 6 TB cannot be collected and broadcast to executors; the job would fail long before the join.
T: In an outer join only the non-preserved side can be broadcast; shrink the other input first if needed.

S: The Parquet folder `/lake/orders` receives new files every day. Three weeks ago the producing team added a `discount` column; older files do not have it. A job reads `spark.read.parquet("/lake/orders")`, and `"discount" in df.columns` returns False, so a new revenue metric is silently missing. A hand-written `.schema(...)` was rejected because the producer will add more columns over time. The folder has 30,000 files, other reads in the same session must keep their current behavior, and the new columns must appear automatically, with NULL for older files. Which change fits?

W: mergeSchema read option: it merges all footers for this read only, so discount and future columns appear, with NULLs for older files.

C=inferSchema: it is a CSV and text option; Parquet already has schemas in its files, and the option does not merge them.
D=basePath: it tells partition discovery where the table root is; it does not merge file schemas.
T: Parquet schema merging is off by default; enable it per read with mergeSchema.
