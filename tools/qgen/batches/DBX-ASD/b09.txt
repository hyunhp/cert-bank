@ DBX-ASD D1 T1.1 advanced tradeoff
S: A retailer already runs nightly Spark jobs that aggregate 3 TB of orders into one status row per customer. A new mobile feature must fetch a single customer's status in under 50 milliseconds, thousands of times per second, and the platform team does not want long-running Spark applications that exist only to answer this API. The nightly Spark output may be reused. Which design best matches Spark's strengths and limits for this lookup requirement?
A: Keep Spark for the nightly aggregation, load its per-customer rows into a low-latency key-value or relational store, and serve API reads from it
B: Run a long-lived Spark application that caches the status table in executor memory and answers each API call with a filtered DataFrame query and collect
C: Start a separate Spark application in local mode for every API request, so each lookup gets its own driver, its own session and isolated memory
D: Write the nightly Parquet output with partitionBy on customer_id, so each API request runs spark.read with a filter that prunes the scan to a single folder
K: A
G: ## What Spark is good at, and what it is not
Apache Spark is a unified engine for **large-scale data processing**: batch ETL, SQL, streaming and machine learning over data that is spread across a cluster. Its strengths are throughput and scale: the driver plans a job, splits it into stages and tasks, and many executors process partitions in parallel.
That design has a fixed cost per query:
- The driver must analyze and optimize the plan and schedule tasks before any data is read.
- Even a tiny filtered query becomes at least one job with tasks sent to executors, and results travel back to the driver.
This cost is small next to a multi-terabyte job but large next to a 50 ms budget. Spark is not a serving database for high-rate point lookups.
## The usual pattern
Spark computes the result in batch, then writes it into a store built for single-row reads (a key-value store or an indexed relational table). The API reads from that store; Spark is not on the request path.
W: Batch plus serving store: Spark does the heavy nightly aggregation it is built for, and the per-request reads hit a store designed for millisecond single-row lookups.
X: B=Long-lived cached application: every request still becomes a planned and scheduled Spark job, which cannot meet 50 ms at thousands of calls per second, and the team ruled out long-running applications for the API.
C=Application per request: starting a driver and session takes seconds, which is far outside the latency budget before any data is read.
D=Partition by customer_id: millions of customers create millions of tiny folders and files, and every request still pays Spark's job startup and file listing cost.
T: Spark is a high-throughput engine with per-job overhead; serve point lookups from a store fed by Spark, not from Spark itself.

@ DBX-ASD D1 T1.2 advanced troubleshooting
S: An application runs 6 executors with `spark.executor.cores=8`. Months ago someone set `spark.task.cpus=4` for a multithreaded library that the job no longer uses. A stage now has 480 single-threaded tasks of about one minute each, and the Executors tab shows only 12 tasks running at any time while CPU use stays low. The team may not add nodes or change the executor size. Which change gives the stage the most concurrent tasks?
A: Set spark.task.cpus back to 1, so each executor runs eight tasks at once and the six executors run 48 tasks in parallel
B: Raise spark.executor.instances to 12 on the same nodes, so each executor gets four cores and the cluster runs 48 tasks in parallel
C: Repartition the input into 48 larger partitions, so the scheduler can place all of the stage's tasks on the executors in a single wave
D: Set spark.default.parallelism to 48, so the scheduler places more tasks on each executor regardless of the per-task CPU setting
K: A
G: ## Task slots
An executor runs tasks in parallel threads. The number of tasks it can run at once (its **task slots**) is `floor(spark.executor.cores / spark.task.cpus)`.
- Here: `floor(8 / 4) = 2` slots per executor, times 6 executors = **12** concurrent tasks, exactly what the Executors tab shows.
- With `spark.task.cpus=1`: `floor(8 / 1) = 8` slots per executor, 48 in total.
## What that means for the stage
480 one-minute tasks on 12 slots run in 40 waves (about 40 minutes). On 48 slots they run in 10 waves (about 10 minutes). `spark.task.cpus` above 1 only makes sense when each task really uses several threads.
## Settings that do not change slots
- `spark.default.parallelism` sets a default partition count for RDD operations; it does not change how many tasks fit on an executor.
- Changing the partition count changes the number of tasks, not the slots that run them.
W: spark.task.cpus=1: slots per executor rise from two to eight, so the same executors run four times as many single-threaded tasks at once.
X: B=More executors: splitting each node into more, smaller executors changes the executor size, which the team may not do, and leaves the misconfigured task CPU setting in place.
C=48 larger partitions: fewer tasks would each run longer, but only 12 could still run at once, so the stage would not finish sooner and each task would need more memory.
D=spark.default.parallelism: it is a default partition count, not a scheduling limit; slots are still floor(8 / 4) per executor.
T: Concurrent tasks per executor = floor(executor cores / spark.task.cpus); a stale spark.task.cpus quietly idles cores.

@ DBX-ASD D1 T1.3 advanced use-case
S: An analyst benchmarks five SQL reports that all read the temporary view `v_sales`, which joins two large Parquet tables. The harness accepts only SQL statements, the first report must already read cached data rather than pay for building the cache, and the report list must stay unchanged, so no extra counting query may be added to it. Which single statement, run once before the reports, meets all of these constraints?
A: CACHE TABLE v_sales, which computes the view's result right away and stores it, so the first report already reads the cached copy
B: CACHE LAZY TABLE v_sales, which marks the view for caching and fills the cache during the first report, so later reports read memory
C: spark.table("v_sales").cache() run from Python before the harness starts, so the view's result is held in memory before any report runs
D: REFRESH TABLE v_sales, which reloads the view's metadata and data files into memory, so that the reports that follow skip the Parquet scan
K: A
G: ## Lazy and eager caching
Caching keeps the result of a query in memory (and disk, by storage level) so later queries do not recompute it.
- `DataFrame.cache()` is **lazy**: it only marks the DataFrame. The data is stored when an action computes it for the first time. Its default storage level is `MEMORY_AND_DISK_DESER`.
- SQL `CACHE TABLE name` is **eager** by default: it caches the table or view immediately when the statement runs.
- `CACHE LAZY TABLE name` behaves like the DataFrame method: it caches only when the table is first used.
`CACHE TABLE` also accepts `OPTIONS ('storageLevel' 'MEMORY_ONLY')` and an `AS query` form. Cached data is shared across Spark sessions on the cluster.
## Example
`CACHE TABLE v_sales;` runs the join once, now. Each report afterwards reads from the cache, including the first.
W: Eager CACHE TABLE: the statement is pure SQL and materializes the view at once, so all five reports, including the first, read the cached data.
X: B=CACHE LAZY TABLE: the cache is built while the first report runs, so that report pays the full cost, which the benchmark forbids.
C=DataFrame cache from Python: the harness accepts SQL only, and cache() is lazy, so nothing would be stored until the first report runs anyway.
D=REFRESH TABLE: it invalidates and refreshes cached metadata and file listings; it does not load the view's rows into memory.
T: CACHE TABLE is eager, CACHE LAZY TABLE and DataFrame.cache() wait for the first action.

@ DBX-ASD D1 T1.4 advanced troubleshooting
S: A job reads 800 GB of CSV files with `spark.read.option("header", True).option("inferSchema", True).csv(path)` and then writes Parquet. The Jobs tab shows a long job that starts at the read line, before any action, followed by the write job, and both scan all files. The column names and types are fixed by a contract and never change. The team wants to remove the extra full pass without changing the output types. What should they change?
A: Pass an explicit schema with .schema(ddl) and drop inferSchema, so no data pass is needed to find types and only the write job scans
B: Keep inferSchema and set samplingRatio to 0.01, so the read-time job disappears and Spark derives the types from the write job's first rows
C: Call cache() on the DataFrame right after the read, so the inference job stores the rows and the write job reads them from executor memory
D: Turn off the header option, so the reader takes column names from the first data row and no longer launches a job to infer the column types
K: A
G: ## Why a read can start a job
Transformations are lazy, but `spark.read` must know the schema immediately, because the DataFrame's columns and types are part of its definition.
- With `inferSchema` on a CSV source, Spark gets the types by reading the data: the docs say it "requires one extra pass over the data". That pass is a real job, visible in the Jobs tab at the read line.
- `samplingRatio` (default 1.0) lowers the share of rows used for inference, but inference still runs as a job.
- With an explicit schema (a `StructType` or a DDL string such as `"id INT, amount DOUBLE, ts TIMESTAMP"`), no inference is needed and the read is lazy again.
## Job count
Inference job + write job = two scans of 800 GB. With a schema: one scan, in the write job.
W: Explicit schema: the reader knows the contract's names and types up front, so no inference job runs and the only full scan is the write.
X: B=samplingRatio: a smaller sample shortens inference but it still runs as its own job at the read line; it is not taken from the write job.
C=cache() after the read: the inference job runs before the DataFrame exists, so caching cannot reuse it, and caching 800 GB adds memory pressure without removing the pass.
D=Header off: column names would become the header text or _c0 style names, the header line would become a data row, and inferSchema would still run its pass.
T: inferSchema costs a full extra job; supply the schema when the types are known.

@ DBX-ASD D1 T1.5 advanced use-case
S: A job scans 2 TB of splittable Parquet files with default file-source settings and gets about 16,000 read tasks of roughly 128 MB each. Each task finishes in under a second, so scheduling overhead dominates the scan stage. The team wants about 4,000 larger read tasks, may not add a shuffle before the first aggregation, and may not rewrite the source files. Which change meets these constraints?
A: Set spark.sql.files.maxPartitionBytes to 512 MB for this job, so the scan packs about four times as much data into each read partition
B: Call repartition(4000) right after spark.read, so the scan output is redistributed into 4,000 evenly sized partitions before any aggregation
C: Set spark.sql.shuffle.partitions to 4000, which decides how many partitions the file scan creates when it splits the Parquet input files
D: Raise spark.sql.files.openCostInBytes to 512 MB, so Spark counts each file as more expensive and packs fewer, larger splits into each task
K: A
G: ## How file scans are split
For file sources (Parquet, ORC, JSON, CSV) Spark builds read partitions from file splits:
- `spark.sql.files.maxPartitionBytes` (default 128 MB) is the most data packed into one read partition.
- `spark.sql.files.openCostInBytes` (default 4 MB) is an estimated cost of opening a file; it is added per file when packing small files together.
- The real split size is roughly `min(maxPartitionBytes, max(openCostInBytes, totalBytes / defaultParallelism))`, so for 2 TB the max setting is what binds.
## The numbers
2 TB / 128 MB is about 16,000 partitions. With 512 MB: 2 TB / 512 MB is about 4,000. No shuffle is added, because this only changes how the scan is planned.
## What the other settings do
- `spark.sql.shuffle.partitions` sets partitions after a shuffle, not for scans.
- `repartition(n)` always shuffles.
W: maxPartitionBytes 512 MB: the scan planner puts up to 512 MB in each read partition, giving about 4,000 tasks with no shuffle and no file rewrite.
X: B=repartition(4000): the 16,000 small scan tasks still run, and a full shuffle is added before the aggregation, which the team ruled out.
C=spark.sql.shuffle.partitions: it controls partitions created by shuffles; the file scan ignores it, so the scan keeps about 16,000 tasks.
D=openCostInBytes: a higher open cost makes Spark put fewer files into a partition, which matters for many small files; it does not raise the 128 MB cap on large splittable files.
T: Read partition size comes from spark.sql.files.maxPartitionBytes; shuffle partition count is a different setting.

@ DBX-ASD D1 T1.6 advanced use-case
S: A developer reviews this code on a 4 TB Parquet table with 43 columns: `df = spark.read.parquet(p)`, `j = df.join(dims, "country")`, `out = j.filter("country = 'KR'").select("ts", "amount")`, followed by a write. A teammate wants to move the filter and the column selection above the join by hand to cut the data read. The team prefers the current readable order and asks whether the rewrite changes what Spark scans. What should they conclude?
A: No rewrite is needed: nothing runs before the write, so the optimizer sees the whole plan and pushes the filter and pruning into the scan
B: The rewrite is required, because transformations run one by one in the order written, so the join reads all 43 columns before the filter applies
C: The rewrite helps only after df is cached, because the optimizer can push a filter below a join only for DataFrames that are held in memory
D: The rewrite is required, because Parquet filter pushdown works only when the filter is the first transformation written after spark.read
K: A
G: ## Lazy evaluation lets the optimizer see everything
Transformations (`join`, `filter`, `select`) only build a logical plan. When an action such as a write runs, Catalyst optimizes the **whole** plan before anything executes. Typical rules:
- **Predicate pushdown**: a filter on the join key `country` is moved below the inner join, to both sides where it applies, and into the Parquet scan, which can skip row groups by min/max statistics.
- **Column pruning**: only the columns needed later (`ts`, `amount`, `country` and the columns used from `dims`) are read from Parquet, a columnar format.
## How to check
`out.explain()` shows `PushedFilters` and a `ReadSchema` with only the needed columns in the scan node. Writing the code in a readable order costs nothing.
W: Whole-plan optimization: because execution waits for the action, Catalyst reorders the filter below the inner join and prunes unused columns at the scan.
X: B=Run in written order: that is how eager code runs; Spark builds a plan and optimizes it as a whole before executing.
C=Only after caching: caching does not enable pushdown; caching df would in fact store all 43 columns and stop the pushdown into the Parquet scan for later queries.
D=First transformation only: pushdown is decided on the optimized plan, not on the position of the filter in the code.
T: Lazy evaluation lets Catalyst push filters and prune columns across the whole plan, whatever order the code uses.

@ DBX-ASD D1 T1.7 advanced comparison
S: A team is porting a churn model built years ago on `pyspark.mllib` RDD APIs. The new version must take features straight from a DataFrame produced by their Spark SQL pipeline, chain the feature steps and the estimator into one reusable object, tune it with cross-validation, and use the MLlib API that still receives new features. Which choice meets these requirements?
A: The pyspark.ml package with a Pipeline of transformers and an estimator, because the DataFrame-based API is MLlib's primary API
B: The pyspark.mllib package with LabeledPoint RDDs converted from DataFrames, because the RDD-based API is still MLlib's primary API
C: Pandas API on Spark with scikit-learn estimators run on each partition, because MLlib no longer ships estimators that accept DataFrames
D: Structured Streaming with a foreachBatch function that refits the model per micro-batch, because MLlib pipelines need streaming input
K: A
G: ## Two MLlib APIs
Spark's machine learning library MLlib has two APIs:
- `spark.ml` (`pyspark.ml`): the **DataFrame-based** API. It is the primary ML API, with `Pipeline`, transformers (for example `VectorAssembler`), estimators, `CrossValidator` and `ParamGridBuilder`.
- `spark.mllib` (`pyspark.mllib`): the **RDD-based** API. Since Spark 2.0 it is in **maintenance mode**: bug fixes only, no new features.
## Why the DataFrame API fits here
A `Pipeline` chains feature stages and a model into one estimator; fitting it returns a `PipelineModel` that can be saved and reused. `CrossValidator` can tune the whole pipeline. It consumes DataFrames directly, so the SQL pipeline output feeds it without conversion.
W: pyspark.ml Pipeline: it works on DataFrames, bundles feature steps and the estimator, tunes with CrossValidator and is where new MLlib features land.
X: B=RDD-based mllib: the RDD API has been in maintenance mode since Spark 2.0 and gets no new features; it also needs conversion from DataFrames.
C=scikit-learn per partition: MLlib does ship DataFrame estimators; per-partition scikit-learn models are separate models on data slices, not one tuned pipeline.
D=Streaming refits: MLlib pipelines train on batch DataFrames; Structured Streaming is not required and refitting per micro-batch is a different design.
T: Use pyspark.ml (DataFrame-based) for new MLlib work; pyspark.mllib is in maintenance mode.

@ DBX-ASD D1 T1.2 advanced troubleshooting
S: A script loops over 5,000 store IDs on the driver and, for each one, runs `df.filter(F.col("store") == s).agg(F.sum("amount")).collect()`. The cluster has 200 cores, yet the Executors tab shows most cores idle for the whole run, which takes six hours. The output must still be one total per store, and the team cannot add hardware. Which change addresses the cause of the idle cores?
A: Replace the loop with one df.groupBy("store").agg(F.sum("amount")) query, so one distributed job computes all store totals in parallel
B: Cache df before the loop, so each of the 5,000 per-store jobs reads from executor memory and the executors stay busy with filters and sums
C: Raise spark.sql.shuffle.partitions to 5,000, so that each store gets its own partition inside every one of the per-store jobs in the loop
D: Run the script in cluster deploy mode, so the driver sits next to the executors and sends the 5,000 per-store jobs with lower network delay
K: A
G: ## The driver runs jobs one after another
The driver is the process that runs your Python program, builds plans and schedules jobs. A Python `for` loop on the driver submits one job, waits for `collect()` to return, then submits the next. Each job here is small: a filter, a tiny aggregation and a result of one row. Most of the time goes to planning, scheduling and job start-up, and only a few cores do any work at once.
## Let one job do the work
`df.groupBy("store").agg(F.sum("amount"))` is a single job:
- Each input partition computes partial sums per store (map-side partial aggregation).
- One shuffle brings the partial sums of a store together, and the final sums are computed in parallel across many tasks.
The result is the same 5,000 totals, computed with the whole cluster busy.
W: One groupBy job: all stores are aggregated in a single distributed job, which uses all cores instead of 5,000 small sequential jobs.
X: B=Cache first: each job reads faster, but the 5,000 jobs still run one at a time from the loop, so most cores stay idle between and during them.
C=More shuffle partitions: each per-store job only has one group to aggregate, so more partitions add empty tasks without changing the sequential loop.
D=Cluster deploy mode: moving the driver saves network time per job but keeps the same 5,000 sequential jobs; the work pattern, not the latency, is the cause.
T: Express per-key work as one grouped query, not a driver-side loop of small jobs.

@ DBX-ASD D2 T2.1 advanced use-case
S: An upload tool writes files into folders such as `/raw/events/dt=2026-11-01/`, mixing finished `.json` files with temporary `.tmp` files that are still being written. A job reads the folder with `spark.read.json("/raw/events")`, and downstream queries filter on `dt`, so `dt` must remain a partition column discovered from the folder names. The `.tmp` files must never be read. Which read option meets both requirements?
A: Set pathGlobFilter to *.json, so only files whose names match are read and partition discovery of the dt folders is unchanged
B: Set recursiveFileLookup to true and pass a *.json pattern, so the reader walks every folder level and still adds dt as a partition column
C: Set ignoreCorruptFiles to true, so the reader skips the .tmp files as unreadable input while keeping dt as a partition column from folders
D: Set modifiedAfter to the time of the last upload, so that files still being written are skipped and dt stays a discovered partition column
K: A
G: ## Generic file-source options
These options work for Parquet, JSON, CSV, ORC and text sources:
- `pathGlobFilter`: includes only files whose **names** match a glob such as `*.json`. The docs state it does **not** change partition discovery.
- `recursiveFileLookup`: loads files from all subfolders, and **disables partition inference**, so `dt=...` folder names no longer become a column.
- `ignoreCorruptFiles`: lets the job continue when a file cannot be read; files that parse are still loaded.
- `modifiedBefore` / `modifiedAfter`: filter files by modification time in batch reads.
## Example
`spark.read.option("pathGlobFilter", "*.json").json("/raw/events")` returns the JSON rows with a `dt` column taken from the folder names.
W: pathGlobFilter *.json: it filters by file name, so .tmp files are never opened, and partition discovery still turns dt=... folders into the dt column.
X: B=recursiveFileLookup: the docs say it disables partition inferring, so the dt column disappears.
C=ignoreCorruptFiles: it only skips files that fail to read; a partly written .tmp file that still parses as JSON lines would be loaded.
D=modifiedAfter: it filters by time, not by name; a .tmp file written after that time is read, and finished files from before it are skipped.
T: pathGlobFilter selects files by name and keeps partition discovery; recursiveFileLookup turns partition discovery off.

@ DBX-ASD D2 T2.1 advanced troubleshooting
S: A job writes `sales` with `partitionBy("dt")` to `/lake/sales`. A partner reads the Parquet files with a non-Spark tool that opens the files directly, ignores folder names, and reports that the `dt` column is missing, although every row had it in Spark. Spark readers of the folder must keep partition pruning on `dt`, and the partner cannot change its tool. Which change satisfies both readers?
A: Copy dt with withColumn("dt_part", F.col("dt")) and partition by dt_part, so dt stays in each file while dt_part names the folders
B: Add option("mergeSchema", "true") to the write, so Spark stores the partition column in each file footer next to the other data columns
C: Drop partitionBy and sort the output by dt with sortWithinPartitions, so the files keep dt and readers can still prune whole partitions
D: Add option("basePath", "/lake/sales") to the write, so the writer keeps the partition column inside the files as well as in the folders
K: A
G: ## Where partition values live
With `partitionBy("dt")`, Spark writes one folder per value (`/lake/sales/dt=2026-11-01/part-...parquet`) and **removes the partition column from the data files**: the value is stored once, in the folder name. Spark's partition discovery rebuilds the column from the path when it reads the folder, and filters on `dt` skip whole folders (partition pruning).
A tool that reads single files and ignores the path therefore sees no `dt` column.
## Keeping both
Partition by a copy of the column:
`sales.withColumn("dt_part", F.col("dt")).write.partitionBy("dt_part").parquet("/lake/sales")`
The files keep `dt`; the folders are `dt_part=...`. Spark readers filter on `dt_part` (or on both) to prune.
W: Copy of the column: the data files keep dt for the partner, and the folder layout on dt_part keeps folder-level pruning for Spark readers.
X: B=mergeSchema: it is a read option that merges different file schemas; it does not make the writer keep partition columns in files.
C=Sort without partitionBy: files keep dt, but there are no dt folders anymore, so Spark readers lose partition pruning and rely only on row-group statistics.
D=basePath: it is a read option that tells partition discovery where the table root is; it does not change what the writer stores in files.
T: partitionBy moves the column into folder names; duplicate the column if file-only readers need it.

@ DBX-ASD D2 T2.2 advanced use-case
S: A SQL-only scheduler can submit Spark SQL statements but no Python. Each night it must export the result of a query that joins `orders` and `customers` as Parquet files into `/exports/daily`, replacing whatever the previous night left there. The security team does not allow the export to be registered as a table or a view in the catalog. Which statement meets these constraints?
A: INSERT OVERWRITE DIRECTORY '/exports/daily' USING parquet followed by the join query, which replaces the folder's files without any catalog entry
B: CREATE TABLE daily USING parquet LOCATION '/exports/daily' AS the join query, which writes the files and replaces the earlier run's output each night
C: CREATE OR REPLACE TEMPORARY VIEW daily AS the join query, which writes the result as Parquet files under the warehouse for the next scheduler run
D: INSERT OVERWRITE TABLE daily with the join query, after a one-time CREATE TABLE daily USING parquet LOCATION '/exports/daily' for the folder
K: A
G: ## Writing query results to a path with SQL
`INSERT OVERWRITE [LOCAL] DIRECTORY path USING file_format [OPTIONS (...)] query` overwrites the data in a directory with the query result, using a Spark file format (or Hive SerDe with Hive support). No table is created.
## Example

## Related statements

S: A CI pipeline runs PySpark unit tests on a shared build agent with 16 logical cores and no cluster. The tests must exercise real parallel task execution to catch thread-safety bugs, but the build team limits each pipeline to 4 worker threads so other pipelines are not starved. A: local[4], which runs the driver and four worker threads in one process on the agent, so up to four tasks run in parallel
B: local, which runs the driver and executor in one process on the agent and gives the tests the parallelism of four cores
C: local[*], which runs the driver and executor in one process on the agent and limits the worker threads to four by default
D: spark://localhost:7077, which connects to a standalone master on the agent and starts one executor with four cores for the tests
K: A
G: ## Local mode master URLs
In local mode, Spark runs the driver and the executor in **one JVM** on the current machine, with no cluster manager.
- `local`: one worker thread, so no parallelism at all.
- `local[K]`: K worker threads (ideally the number of cores you want to use).
- `local[*]`: as many worker threads as the machine has logical cores.
- `local[K,F]`: K threads and F task failures allowed.
Any `spark://host:port` URL needs a running standalone master and worker daemons.
## Example
`SparkSession.builder.master("local[4]").getOrCreate()` in a pytest fixture runs up to four tasks at the same time.
W: local[4]: four worker threads give real parallel tasks, within the agent's limit, and no daemon is needed.
X: B=local: plain local uses a single worker thread, so tasks never run in parallel and thread-safety bugs stay hidden.
C=local[*]: it uses all 16 logical cores, which breaks the four-thread limit.
D=Standalone master URL: it needs a standalone master and worker running on the agent, which may not be installed.
T: local[K] gives K parallel task threads in one process; local is single-threaded and local[*] uses all cores.

G: ## Operations across different DataFrames
In pandas, `df1["a"] + df2["b"]` aligns the two Series by index. In pandas API on Spark, the two frames are separate distributed datasets, so alignment needs an internal **join**, which can be expensive. To prevent accidental joins, pandas API on Spark **disallows** operations between different DataFrames or Series by default; the option `compute.ops_on_diff_frames` (default False) enables them.
## Scoping an option
- `ps.set_option(name, value)`: changes the option until reset, for all later code.
- `with ps.option_context(name, value): ...`: sets it only inside the block and restores the old value on exit.
W: option_context: the join-based alignment is allowed only inside the block, so the rest of the code keeps the default check.
X: B=set_option at the top: the option stays on for every later step, removing the safety check the team wants to keep.
C=to_pandas: it collects 600 GB to the driver, which does not fit in a single machine's memory.
D=distributed index type: it changes how a default index is generated; it does not allow operations between different frames.
T: compute.ops_on_diff_frames allows cross-frame operations via a join; scope it with option_context.

@ DBX-ASD D7 T7.2 advanced use-case
S: A pandas UDF scores a text column with a model whose loading takes 20 seconds. In the current Series to Series UDF the model is loaded inside the function, and the Spark UI shows tasks spending most of their time loading it, because the function runs once per Arrow batch. The output must stay one score per input row, and the model should load at most once per task. Which UDF form meets these constraints?
A: An Iterator of Series to Iterator of Series pandas UDF that loads the model before the loop and yields one scored Series per batch
B: A Series to scalar pandas UDF used in groupBy().agg(), which loads the model one time and returns a single score for each group of rows
C: The same Series to Series pandas UDF marked asNondeterministic(), so Spark calls the function only once per task instead of once per batch
D: The same Series to Series pandas UDF with the model path in a broadcast variable, so every Arrow batch reuses the loaded model in memory
K: A
G: ## pandas UDF types and their call pattern
pandas UDFs exchange data with Python in Arrow record batches (`spark.sql.execution.arrow.maxRecordsPerBatch`, default 10,000 rows).
- **Series to Series**: the function is called once per batch with one pandas Series and returns a Series of the same length. Anything loaded inside it is loaded again for every batch.
- **Iterator of Series to Iterator of Series**: the function is called once for an iterator over all batches of the partition. The docs say it is useful when execution needs some expensive state initialization: load once, then loop and `yield` results.
- **Series to scalar**: an aggregation that returns one value per group.
## Example
`@F.pandas_udf("double")`
`def score(it: Iterator[pd.Series]) -> Iterator[pd.Series]:`
`    model = load_model()`
`    for s in it: yield pd.Series(model.predict(s))`
W: Iterator UDF: the model is loaded once per task, before the loop, and each batch still gets one score per row.
X: B=Series to scalar: it aggregates and returns one value per group, so the one-score-per-row output is lost.
C=asNondeterministic: it changes how the optimizer treats repeated calls, not how often the function runs per batch.
D=Broadcast path: broadcasting the path does not keep a loaded model; the function body still loads it for every batch.
T: Use the iterator pandas UDF form when an expensive setup must run once per task rather than once per batch.
