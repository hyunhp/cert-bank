@ DBX-ASD D2 T2.2 applied use-case
S: A directory `/data/events` holds JSON Lines files. An analyst wants a DataFrame with all rows, using SQL and without first reading the files into a DataFrame or registering a view. Which call does that?
A: spark.sql("SELECT * FROM '/data/events' USING json")
B: spark.sql("SELECT * FROM json.'/data/events'")
C: spark.sql("SELECT * FROM json.`/data/events`")
D: spark.sql("SELECT * FROM file('/data/events', 'json')")
K: C
G: ## Run SQL on files directly
Spark SQL can query a file without a read call or a view. The table identifier is the data source name, a dot, and the path in backticks:
- `SELECT * FROM parquet.`/data/users.parquet``
- `SELECT * FROM json.`/data/events``
The source name before the dot (`parquet`, `json`, `csv`, `orc`, `text`, `delta`) tells Spark which reader to use, and the backticks mark the path as one identifier. `spark.sql(...)` returns a normal DataFrame, so you can keep transforming it.
## What this form does not give you
The files are read with the default options of that source. If you need options such as a header, a delimiter or an explicit schema, use `spark.read.option(...).schema(...)` instead.
W: Source name plus backticked path: `json.` followed by the path in backticks is the documented "run SQL on files directly" form, and the result is a DataFrame.
X: A=USING clause: `USING json` belongs to `CREATE TABLE` and `CREATE TEMPORARY VIEW` statements; it is not valid inside a plain SELECT, so the query fails to parse.
B=Single quotes: a quoted string is a literal, not an identifier. The path has to sit in backticks after the source name, so this statement is a syntax error.
D=file() function: Spark SQL has no table function with this name for reading paths. Direct file queries use the `source.`path`` identifier.
T: Query a file in place with `SELECT ... FROM format.`path``; backticks, not quotes, and default reader options only.
V: Spark SQL

@ DBX-ASD D2 T2.2 applied troubleshooting
S: A nightly job runs the line below. The first run on a fresh path succeeds. The next night, the same line runs again with a new DataFrame and the path already contains the first night's files.
```
df.write.parquet("/out/daily")
```
What happens on the second run?
A: It fails with an AnalysisException, because the default mode raises an error when data exists, and the old files stay
B: It succeeds and appends the new rows next to the first night's files, because adding files is the default behavior of a path write
C: It succeeds and replaces the first night's files, because a write without options overwrites the target path directory
D: It succeeds without writing anything, because the default save mode skips the write when data already exists at the path
K: A
G: ## Save modes
`DataFrameWriter.mode()` tells Spark what to do when the target already holds data. The four modes:
- `errorifexists` (also `error`, the default): throw an exception if data exists.
- `append`: add the DataFrame's rows to the existing data.
- `overwrite`: replace the existing data with the DataFrame.
- `ignore`: do nothing if data exists, like `CREATE TABLE IF NOT EXISTS`.
## Why the default matters
A script that works the first time and fails the second is the signature of the default mode. Nothing is written by the failing call, so the old output is still there.
W: Default errorifexists: with no `mode()` call the writer uses `errorifexists`, so the second write sees data at `/out/daily` and throws an exception before changing anything.
X: B=Append: appending needs an explicit `mode("append")`; it is not the default, and a silent append would duplicate rows on every rerun.
C=Overwrite: overwriting also needs `mode("overwrite")`. Replacing data without being asked would be dangerous, which is why the default refuses.
D=Ignore: skipping an existing target is what `mode("ignore")` does. The default does not skip quietly; it raises an error so the failure is visible.
T: No `mode()` means `errorifexists`: a rerun on the same path fails instead of appending, overwriting or skipping.
V: Spark SQL

@ DBX-ASD D2 T2.2 applied use-case
S: `/out/ref` already holds a reference dataset with 100 rows from a previous load. A job holds a DataFrame `df` with 500 different rows and runs the line below. The call returns without an error.
```
df.write.mode("ignore").parquet("/out/ref")
```
What does `spark.read.parquet("/out/ref").count()` return afterwards?
A: 600, because ignore keeps the existing rows and adds the new ones
B: 500, because ignore resolves the conflict in favor of the new data
C: An exception, because writing to an existing path always fails unless the mode is set to overwrite or append
D: 100, because ignore leaves existing data alone and does not write the DataFrame
K: D
G: ## What ignore means
`ignore` is the "create if not exists" save mode. If data is already present at the target, the writer neither fails nor changes anything; the DataFrame is simply not saved. If the target is empty or missing, the write happens as usual.
## When to use it
It fits one-time seeding of a reference dataset, where reruns must be harmless. It is a poor fit for incremental loads, because new rows are dropped without any message.
W: Ignore skips the write: because `/out/ref` already has data, Spark leaves the 100 existing rows as they are and discards the 500 new ones, so the count stays 100.
X: A=Append result: adding rows to existing data is `mode("append")`. Ignore never touches the existing data, so no rows are added.
B=Overwrite result: replacing the data with the new rows is `mode("overwrite")`. Ignore never deletes anything, so the old rows are not replaced.
C=Exception: raising an exception on existing data is the `errorifexists` mode. Ignore was chosen here exactly so that the call succeeds silently.
T: `ignore` = write only if nothing is there yet; otherwise do nothing and report no error.
V: Spark SQL

@ DBX-ASD D2 T2.2 applied troubleshooting
S: A load job writes `df` (3 rows) with the line below. The job's scheduler retries it once after a transient network error that occurred after the write had already finished. Both attempts ran to completion.
```
df.write.mode("append").json("/out/orders")
```
How many rows does `spark.read.json("/out/orders")` return, assuming the path was empty before the first attempt?
A: 3, because append merges rows that are identical to ones already stored
B: 6, because each completed attempt appended its own copy of the 3 rows
C: 3, because the second attempt is skipped when the output path already exists
D: 0, because a path written twice is invalidated until it is repaired
K: B
G: ## Append is not idempotent
`append` adds new files next to the old ones. Spark does not compare rows, and a plain file source has no primary key or transaction log that recognizes a repeated batch. Running the same write twice therefore stores the data twice.
## Consequences for retries
- Retrying an `append` job after it already finished duplicates data.
- To make reruns safe, overwrite a deterministic location (for example one folder per batch date), or deduplicate on a key when reading.
- Transactional table formats can add idempotent writes; with plain files you design it yourself.
W: Append twice: two successful runs add two sets of files, so the 3 rows are stored twice and the read returns 6.
X: A=Row merging: Spark does not deduplicate on append and never compares new rows with stored rows, so identical rows are kept.
C=Skipping: skipping an existing output belongs to `mode("ignore")`. Append writes new files whenever it is called.
D=Invalidated path: no such state exists for a file path. Readers simply see all part files that are present.
T: `append` is not idempotent: a retried successful write doubles the rows unless you deduplicate or overwrite a fixed location.
V: Spark SQL

@ DBX-ASD D2 T2.2 advanced troubleshooting
S: A job rebuilds a plain Parquet dataset with `df.write.mode("overwrite").parquet("/out/sales")`. One night the executors are lost halfway through the write and the job fails. The team assumed that the previous night's data would still be there. What does the Spark documentation say about this situation?
A: The previous data is intact, because Spark writes into a temporary directory and swaps it in atomically after the last task
B: The previous data is restored by Spark, because a failed write is rolled back using the transaction log of the output path
C: The old data may already be gone, because overwrite is not atomic, takes no lock and deletes the old data first
D: The previous data is kept in a hidden backup folder, which Spark deletes only after the next successful overwrite of the path
K: C
G: ## Save modes are not transactions
The Spark guide states two warnings about save modes: they "do not utilize any locking and are not atomic", and when performing an `Overwrite`, "the data will be deleted before writing out the new data".
## What that means for a plain file path
- A crash between the delete and the end of the write leaves no complete old copy and no complete new copy.
- Readers that run at the same time can see missing or partial data.
- Safer patterns: write to a new, dated location and switch readers to it afterwards, or use a table format with transactions (such as Delta) so a failed write leaves the last committed version intact.
W: Delete first, no atomicity: Spark clears the target before writing, so a failure halfway through can leave the previous night's data missing or the output partial, and the documented behavior gives no rollback.
X: A=Atomic swap: a temporary-directory swap would make overwrite atomic, which the guide says it is not. Writing happens at the target path.
B=Rollback from a log: plain Parquet paths have no transaction log. Only table formats such as Delta provide that, not the generic `overwrite` mode on files.
D=Hidden backup: Spark creates no backup copy of overwritten data. Once deleted, the old files are not recoverable through Spark.
T: Overwrite on a file path is delete-then-write, not atomic and not locked; a mid-write failure can lose the old data.
V: Spark SQL

@ DBX-ASD D2 T2.2 advanced use-case
S: `/out/events` is written with `partitionBy("dt")` and currently has the partitions dt=2024-01-01, dt=2024-01-02 and dt=2024-01-03. Each night a job recomputes only the latest day and runs the line below with the default Spark configuration. After the run, only dt=2024-01-03 remains and the older days are gone.
```
new_day.write.mode("overwrite").partitionBy("dt").parquet("/out/events")
```
Which change makes the job replace only the partitions that appear in `new_day`?
A: Add `.option("partitionOverwriteMode", "dynamic")` to the writer (or set `spark.sql.sources.partitionOverwriteMode` to `dynamic`)
B: Change the mode to `append`, because append replaces partitions that already exist with the same name
C: Change the mode to `ignore`, because ignore keeps old partitions and rewrites only the matching ones
D: Call `new_day.coalesce(1)` before the write, because a single write task only touches the one partition it writes to
K: A
G: ## Static and dynamic partition overwrite
For a partitioned data source, `spark.sql.sources.partitionOverwriteMode` controls what an overwrite deletes:
- `STATIC` (the default): Spark deletes the matching target before writing, which for a plain `overwrite` with `partitionBy` means every existing partition.
- `dynamic`: Spark does not delete ahead of time and overwrites only the partitions that receive data at runtime.
The setting can also be passed as a writer option, `partitionOverwriteMode`, and the option takes precedence over the session setting.
## Why not other modes
`append` and `ignore` change what happens to existing data in the whole target; neither means "replace the partitions I have data for".
W: Dynamic mode: with `partitionOverwriteMode=dynamic` only dt=2024-01-03 is rewritten and the other days stay, because Spark overwrites just the partitions that hold rows in the DataFrame.
X: B=Append: append adds files to dt=2024-01-03 beside the old ones instead of replacing them, so a rerun would double that day.
C=Ignore: ignore skips the whole write because the path already has data, so tonight's day would never be written.
D=coalesce(1): reducing the number of write tasks changes file counts, not which directories are deleted. In static mode the delete still happens first.
T: Replace only the partitions you have data for with `partitionOverwriteMode=dynamic`; static overwrite removes all of them.
V: Spark SQL

@ DBX-ASD D2 T2.2 applied troubleshooting
S: `/data/people.csv` has a header line `id,name` followed by data lines. An analyst runs the query below and receives an AnalysisException saying that column `id` cannot be resolved.
```
spark.sql("SELECT id FROM csv.`/data/people.csv`")
```
What is the cause?
A: The file must first be registered as a temporary view, because `csv.` paths can only be queried by name
B: Direct SQL uses the source's default options, so no header is used: columns are `_c0` and `_c1` and the header is data
C: The csv source supports direct queries only for whole directories, so a single file path must be wrapped in a glob pattern

When you query `csv.`path``, Spark reads the file with the CSV source's default options. The `header` option defaults to `false`, so the first line is a data row and the columns are named `_c0`, `_c1`, ... with string type.

X: A=View required: direct file queries need no view. The same statement works, but with default-named columns.

D=Case sensitivity: Spark SQL resolves column names case-insensitively by default, and the problem is that no column called `id` exists at all.

@ DBX-ASD D2 T2.2 applied use-case
S: `/logs/app` is a directory of plain text files. An engineer wants the number of lines containing `ERROR`, using direct SQL on files. Which query is correct?
A: spark.sql("SELECT count(*) FROM text.`/logs/app` WHERE line LIKE '%ERROR%'")
B: spark.sql("SELECT count(*) FROM text.`/logs/app` WHERE _c0 LIKE '%ERROR%'")
C: spark.sql("SELECT count(*) FROM text.`/logs/app` WHERE text LIKE '%ERROR%'")
D: spark.sql("SELECT count(*) FROM text.`/logs/app` WHERE value LIKE '%ERROR%'")
K: D
G: ## The text source schema
The `text` data source reads each line of every file as one row with a single string column called `value`. When partition directories are present, partition columns are added to it. Everything the other sources infer (types, headers, field names) does not exist for text, so you parse `value` yourself with `split`, `regexp_extract` or `from_json`.
## Contrast with CSV
CSV direct queries expose `_c0`, `_c1`, ...; JSON exposes the field names found in the data. Text always exposes `value`.
W: The value column: `text.` returns lines in a single string column named `value`, so filtering on `value LIKE '%ERROR%'` and counting rows gives the number of matching lines.
X: A=line: no column called `line` exists for the text source, so the query fails to resolve it.
B=_c0: `_c0` is the first column name produced by the CSV source with no header; the text source does not use positional names.
C=text: the source name is not a column name. The query would fail with an unresolved column.
T: Reading text files gives one string column named `value` per line.
V: Spark SQL

@ DBX-ASD D2 T2.2 applied definition
S: A developer misremembers the writer API and calls `df.write.mode("replace").parquet("/out/x")`. Which statement describes what Spark does?
A: It treats replace as a synonym for overwrite because the writer accepts common aliases of the four modes
B: It treats replace as append when the path exists and as a normal write when the path does not exist
C: It raises an error because replace is not a save mode; accepted names are append, overwrite, ignore, error/errorifexists
D: It falls back to the default mode and carries on, writing the data if the path is empty or failing if it is not
K: C
G: ## Valid save mode names
The writer accepts exactly the save modes in the Spark guide:
- `error` or `errorifexists` (default)
- `append`
- `overwrite`
- `ignore`
Any other string is rejected with an error that lists the accepted modes. Spark does not guess intent from a near-synonym.
## Useful habit
Pass the mode as a string from this list, or in Scala/Java use the `SaveMode` enum, so that typos fail early rather than changing behavior.
W: Unknown mode name: replace is not in the list of save modes, so Spark rejects it with an error instead of mapping it to overwrite.
X: A=Aliases: the only alternative spellings are `error` for `errorifexists`; there is no alias like replace for overwrite.
B=Mixed behavior: no mode behaves as "append when exists, plain write otherwise" other than the append mode itself, and replace is not recognized.
D=Silent fallback: Spark does not fall back to the default for an unrecognized name; a misspelled mode is an error.
T: Only error/errorifexists, append, overwrite and ignore are valid; other strings raise an error.
V: Spark SQL

@ DBX-ASD D2 T2.2 applied troubleshooting
S: A DataFrame `df` has columns `id` (int) and `msg` (string). The developer runs `df.write.text("/out/msgs")` and the job fails with an AnalysisException. What is the cause and the fix?
A: The text sink takes one string column only; combine columns with `concat_ws`, or write a format such as CSV or JSON
B: The text sink writes every column separated by tabs, but the target directory must be created first with `mkdir`
C: The text sink supports only the first column, so Spark drops `msg`; the exception warns about data loss and `mode("overwrite")` suppresses it
D: The text sink needs the `header` option for multi-column data, so adding `.option("header", True)` fixes the write

G: ## The text writer is single column
The `text` source reads each line as one string column named `value`, and writes in the mirror image: the DataFrame must have exactly one column of string type, and each row becomes one line. A DataFrame with two columns is rejected before anything is written.
## Ways to write several fields
- Build one string column (`concat_ws(",", "id", "msg")`) and write it as text. You then own quoting and escaping.
- Use `csv` or `json` writers, which handle several columns, headers and quoting.
W: Single string column only: the text writer cannot represent two columns, so the analysis fails; concatenating into one string column or choosing CSV/JSON solves it.
X: B=Tab separation and mkdir: the text writer never joins columns with tabs, and Spark creates output directories itself, so the missing folder is not the problem.
C=Drop the second column: Spark does not silently truncate columns; the writer rejects the schema, and the save mode does not affect schema checks.
D=header option: `header` is a CSV option. The text source has no header concept.
T: `write.text` needs exactly one string column; join columns into one or use csv/json.

@ DBX-ASD D2 T2.2 advanced troubleshooting
S: A job reads a dataset and rewrites it in place after filtering:
```
df = spark.read.parquet("/out/orders")
df.filter("status = 'OK'").write.mode("overwrite").parquet("/out/orders")
```
What is the outcome?
A: It succeeds, because Spark buffers the filtered rows in memory before it deletes the target path
B: It fails with an AnalysisException saying the path is also being read from; the rows must go to a different location
C: It succeeds, because the filter is pushed down so only the matching files are touched and the other files stay in place
D: It succeeds but returns an empty dataset, because overwrite always deletes the data before the filter runs
K: B
G: ## Reading and writing the same path
DataFrames are lazy: `spark.read.parquet(path)` does not read data until an action runs, and the write is that action. Overwrite deletes the target before writing, so the reader would find its own input deleted.
Spark detects this plan and raises an `AnalysisException` such as "Cannot overwrite a path that is also being read from". A workaround that is only safe in a table format with transactions is to read a snapshot; for plain files, write to a new path (or a staging path) and switch consumers after the job succeeds.
W: Self overwrite is refused: the query both reads and overwrites `/out/orders`, so Spark rejects it before data is lost instead of reading from files it just deleted.
X: A=Memory buffering: Spark does not hold the whole result in memory in order to delete its own input; output is produced by distributed tasks reading the files.
C=Filter pushdown: pushdown limits which row groups are read, not which files overwrite deletes. Overwrite removes the whole target path.
D=Empty result: Spark's analysis step catches the conflict first, so the job fails instead of finishing with an empty dataset.
T: You cannot overwrite a file path you are lazily reading from: write elsewhere, then switch.
V: Spark SQL

@ DBX-ASD D2 T2.3 applied comparison
S: A program runs these two statements in a session that has a Hive metastore and a warehouse directory configured. Then the application stops and a new application starts against the same metastore.
```
df.createOrReplaceTempView("t1")
df.write.saveAsTable("t2")
```
Which statement is true in the new application?
A: Both t1 and t2 can be queried, because the metastore stores all views and tables registered in a session
B: Only t1 can be queried, because views are stored as query plans, which are cheap to keep, whereas tables cannot be recovered
C: Neither can be queried, because tables created from DataFrames last only as long as their session
D: Only t2 can be queried, because saveAsTable writes the data and a metastore entry, while a temp view lives in its session
K: D
G: ## saveAsTable versus a temporary view
- `saveAsTable("name")` writes the DataFrame's data to files (under the warehouse directory unless a `path` option is given) and creates a table entry in the metastore. It survives application restarts as long as the same metastore is used, and it can be read again with `spark.table("name")`.
- `createOrReplaceTempView("name")` registers a name for the DataFrame's query plan in the current session only. No data is written, and the name disappears when the session ends.
No Hive installation is needed: by default Spark creates a local metastore.
W: Persistent table: t2 has real files and a metastore entry, so it remains after the first application ends; the temporary view t1 was only a session-scoped name.
X: A=Both survive: a temporary view is never written to the metastore, so it cannot be found by another application.
B=Only the view: this reverses the behavior. The view holds a plan inside session memory, and the table is the object that persists.
C=Neither survives: tables created by `saveAsTable` are persistent, which is the point of the call; session-only lifetime applies to temporary views.
T: `saveAsTable` = data plus metastore entry that outlives the session; a temp view = a session-scoped name for a plan.

@ DBX-ASD D2 T2.3 applied troubleshooting
S: A developer wants the user table to be bucketed on `user_id` and writes:
```
df.write.bucketBy(8, "user_id").parquet("/out/users")
```
What happens?
A: The write fails with an AnalysisException, because bucketing is supported only for persistent tables saved with `saveAsTable`
B: The write succeeds and creates eight bucket files for each partition of the DataFrame under the output path folder
C: The write succeeds and ignores `bucketBy`, because bucket information cannot be stored without a table
D: The write succeeds only if `sortBy("user_id")` is also called, since a bucketed layout needs sorted files
K: A
G: ## Bucketing needs a table
The guide says that for file-based data sources "bucketing and sorting are applicable only to persistent tables". The bucket count and columns are stored as table metadata in the metastore; later queries use that metadata to avoid shuffles. A plain path write has no place to keep it, so `save`-style methods (`parquet(path)`, `save(path)`) reject `bucketBy`.
## Correct form
```
df.write.bucketBy(8, "user_id").sortBy("user_id").saveAsTable("users")
```
`sortBy` is optional and sorts rows within each bucket. It can be used only together with `bucketBy`.
W: Persistent tables only: bucketBy requires `saveAsTable`, so a path-based Parquet write is rejected with an AnalysisException.
X: B=Bucket files per partition: a bucketed table does hold bucket files, but Spark creates them only through `saveAsTable`.
C=Silent ignore: Spark does not drop a layout request quietly; it raises an error because the metadata could not be stored.
D=sortBy requirement: the dependency runs the other way. `sortBy` needs `bucketBy`, while `bucketBy` works alone with a table.
T: `bucketBy` (and `sortBy`) work only with `saveAsTable`; path writes raise an error.
V: Spark SQL

@ DBX-ASD D2 T2.3 advanced use-case
S: `orders` and `customers` were both written with `bucketBy(16, "cust_id").sortBy("cust_id").saveAsTable(...)`. A job joins them on `cust_id` with `spark.sql.autoBroadcastJoinThreshold` set to -1 and bucketing left at its defaults. What does the physical plan show?
A: A broadcast hash join of customers, because the broadcast threshold only applies to tables that are not bucketed
B: A sort-merge join with an Exchange (shuffle) on both inputs, because bucket metadata is used only for filters and never for joins
C: A sort-merge join with no Exchange on either input, because both tables are bucketed on the join key into the same number of buckets
D: A shuffled hash join where only the larger table is shuffled, because bucketing replaces the shuffle for the smaller table
K: C
G: ## Bucketing and joins
A bucketed table stores rows in a fixed number of files chosen by a hash of the bucket column. If two tables use the same bucket column (the join key) and the same bucket count, then rows with equal keys are already in matching buckets. Spark can join bucket i with bucket i and skip the shuffle that would otherwise be inserted as an `Exchange` before a sort-merge join.
- The setting `spark.sql.sources.bucketing.enabled` is `true` by default; when it is `false`, bucketed tables are treated as normal tables.
- Sorting within buckets (`sortBy`) can also save the local sort.
- Check the result with `df.explain()`: no `Exchange hashpartitioning(cust_id)` below the join.
## Why mention the broadcast threshold
Setting it to -1 turns off automatic broadcast joins, so the plan shows a sort-merge join and the benefit of bucketing is visible.
W: Co-bucketed join: both tables share the join key and bucket count 16, so Spark reads matching buckets together and the plan has a sort-merge join with no shuffle for either side.
X: A=Broadcast: the threshold is -1, so no automatic broadcast happens, and the threshold has nothing to do with bucketing.
B=Always shuffles: that is the unbucketed behavior. Bucket metadata is used for joins and aggregations on the bucket columns precisely to avoid the shuffle.
D=Half shuffle: when both sides are compatibly bucketed no side needs a shuffle; a one-sided shuffle occurs only if just one table is bucketed.
T: Same bucket column and count on both tables = shuffle-free sort-merge join.

@ DBX-ASD D2 T2.3 advanced tradeoff
S: A table of 50 million devices is queried by `device_id`, and the team also joins it on `device_id`. A developer proposes `partitionBy("device_id")` when saving it as a table. Which assessment is correct?
A: It is the best choice, because one directory per device makes every device lookup read exactly one file
B: It creates millions of tiny directories and files; `bucketBy` on `device_id` gives a fixed layout for a high-cardinality key
C: It fails, because partitionBy is allowed only for string columns and `device_id` is numeric
D: It hashes devices into 200 partitions automatically, so the number of directories is bounded by `spark.sql.shuffle.partitions`
K: B
G: ## Partitioning versus bucketing
- `partitionBy(col)` writes one directory per distinct value (`device_id=123/`). It gives partition pruning for filters on that column, but the directory count equals the number of distinct values. The guide notes it "has limited applicability to columns with high cardinality".
- `bucketBy(n, col)` hashes the column into a fixed number `n` of buckets. It "can be used when the number of unique values is unbounded", and helps joins and aggregations on that column.
## Rule of thumb
Partition on low-cardinality columns that queries filter on (date, country). Bucket on high-cardinality keys used for joins or lookups (user id, device id).
W: Too many directories: partitionBy on 50 million values makes millions of small directories and files, which overloads listing and the metastore; bucketBy gives a fixed layout for a column with unbounded values.
X: A=One file per device: each directory holds at least one small file, but the cost of listing and tracking millions of them outweighs the pruning benefit.
C=String only: numeric, date and timestamp columns can be partition columns, and automatic type inference exists for them.
D=200 partitions: the shuffle partition setting concerns shuffles, not the output directory layout. partitionBy writes a directory per value.
T: Partition by low-cardinality filter columns; bucket by high-cardinality key columns.

@ DBX-ASD D2 T2.3 applied definition
S: A DataFrame `sales` contains the columns `country`, `year` and `amount`. It is saved with the line below. In which directory does a row with country `KR` and year `2025` end up?
```
sales.write.partitionBy("country", "year").parquet("/out/s")
```
A: /out/s/KR/2025/part-...parquet, because partition values become plain nested folder names
B: /out/s/year=2025/country=KR/part-...parquet, because Spark orders directories alphabetically by column name
C: /out/s/country=KR_year=2025/part-...parquet, because Spark joins all partition columns into one folder name
D: /out/s/country=KR/year=2025/part-...parquet, because folders follow the partitionBy order in column=value form
K: D
G: ## Hive-style partition directories
`partitionBy` creates one directory level per column, in the order the columns are listed, and each level is named `column=value`. Example layout:
```
/out/s/country=KR/year=2025/part-00000-....parquet
/out/s/country=KR/year=2026/...
/out/s/country=US/year=2025/...
```
The column order matters for the layout: put the column most often used in filters first, and the one with the fewest distinct values at the top to avoid too many directories at the first level.
## Why this format
All built-in file sources can discover these `name=value` directories and infer the partition columns when they read the root path.
W: Order and name=value: partitionBy("country","year") produces `country=KR` first and `year=2025` under it, which readers use to rebuild both columns.
X: A=Plain nesting: without `column=` prefixes the partition values could not be recovered by partition discovery.
B=Alphabetical order: Spark uses the order in which you list the columns, not alphabetical order.
C=Single folder name: each partition column gets its own directory level; Spark does not combine them with underscores.
T: `partitionBy(a, b)` writes `a=<v>/b=<v>/` folders in the listed order.

```
spark.range(3).createOrReplaceTempView("t")

spark.sql("SELECT count(*) AS n FROM t").collect()
```
A: [Row(n=3)], because the first registration of a name wins
B: [Row(n=5)], because registering the same name again replaces the earlier view

G: ## createOrReplaceTempView versus createTempView
- `createOrReplaceTempView(name)` creates a session-scoped view, or replaces an existing view with the same name.
- `createTempView(name)` fails with a `TempTableAlreadyExistsException` (an AnalysisException) if the name already exists.
Replace semantics make re-running a notebook cell safe, which is why the "OrReplace" form is the usual choice.
## What the name points to
A temporary view is one name for one query plan. Registering the same name again swaps the plan; it does not combine them.

X: A=First wins: nothing keeps the first registration when the "replace" variant is used.
C=Union of both: a view holds a single plan; Spark never merges plans registered under one name.
D=Name conflict: that error belongs to `createTempView`. The replace variant is designed not to raise it.
T: `createOrReplaceTempView` swaps the plan behind a name; `createTempView` errors if it exists.

@ DBX-ASD D2 T2.4 applied use-case
S: What does this code print?
```
df = spark.createDataFrame([("a", 1), ("b", 2), ("a", 3)], ["k", "v"])
df.createOrReplaceTempView("t")
q = "SELECT k, sum(v) AS s FROM t GROUP BY k HAVING sum(v) > 2 ORDER BY k"
print(spark.sql(q).collect())
```
A: [Row(k='a', s=4), Row(k='b', s=2)], because HAVING only labels the groups and does not remove any of them
B: [Row(k='b', s=2)], because HAVING keeps the groups whose sums fall below the limit of two
C: [Row(k='a', s=4)], because the groups are summed first and HAVING then keeps those whose sum is above 2
D: [Row(k='a', s=2)], because sum(v) counts the rows in each group instead of adding the values
K: C
G: ## SQL on a view
`spark.sql(...)` runs a SQL statement and returns a DataFrame; the temporary view `t` is just the DataFrame under another name. The usual SQL evaluation order applies: `WHERE` filters rows before grouping, `GROUP BY` forms groups, aggregates are computed, `HAVING` filters groups on aggregate results, `ORDER BY` sorts.
Here the groups are `a` with values 1 and 3 (sum 4) and `b` with value 2 (sum 2). Only `a` has a sum greater than 2. The sum of integers is a long, shown as `s=4`.
W: HAVING on the aggregate: group `a` sums to 4 and passes, group `b` sums to 2 and is removed, so one row `Row(k='a', s=4)` is printed.
X: A=HAVING ignored: HAVING removes groups, so b with sum 2 does not appear.
B=Reversed condition: HAVING keeps rows where the condition is true, which means sums greater than 2.
D=Row count: `sum(v)` adds the values (1 + 3 = 4), while `count(*)` would return the number of rows (2).
T: SQL on a temp view evaluates GROUP BY, then HAVING on the aggregates; `spark.sql` returns a DataFrame.
