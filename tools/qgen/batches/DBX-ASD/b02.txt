@ DBX-ASD D1 T1.5 applied use-case
S: Adaptive query execution is disabled and `spark.sql.shuffle.partitions` is set to 50. A job runs `df.groupBy("country").count().collect()`, and `country` has only 12 distinct values. How many tasks does the stage that reads the shuffled data run?
A: 12 tasks, because Spark creates one reduce task per distinct grouping key and no more.
B: 50 tasks, because the shuffle always produces the configured number of partitions, and some of them stay empty.
C: 1 task, because the final aggregation of a `groupBy` is always merged on a single executor.
D: As many tasks as the input DataFrame has partitions, because shuffles never change the partition count.
K: B
G: ## Where the shuffle partition count comes from
A wide transformation such as `groupBy`, `join` or `orderBy` redistributes rows across the cluster. Each map task writes its output into shuffle files split by the target partition, and each reduce task reads one target partition.
- `spark.sql.shuffle.partitions` (default 200) sets how many target partitions a DataFrame or SQL shuffle creates.
- Rows are assigned by hashing the grouping key and taking it modulo that number, so 12 keys spread across 50 partitions leave at least 38 of them empty.
- With adaptive query execution (AQE, on by default) Spark can coalesce small shuffle partitions at runtime. In this stem AQE is off, so the configured number applies as it is.
W: The post-shuffle stage has one task per shuffle partition, so it runs 50 tasks. Twelve of them process the keys and the rest read nothing.
X: A=One task per key: Spark does not size the shuffle by the number of distinct keys; it hashes keys into a fixed number of partitions.
C=Single task: partial aggregates are merged in parallel across all shuffle partitions, not on a single executor.
D=Input partition count: the shuffle breaks the link between input and output partitioning. The output count comes from the shuffle setting.
T: With AQE off, a DataFrame shuffle yields exactly `spark.sql.shuffle.partitions` partitions, empty ones included.

@ DBX-ASD D1 T1.5 advanced troubleshooting
S: AQE is disabled and `spark.sql.shuffle.partitions` is 64. A DataFrame `df` has 3 distinct values in column `k` and 10 input partitions. What does the code below print?
`print(df.repartition("k").rdd.getNumPartitions())`
A: 3, because Spark creates one partition for each distinct value of the column and no others.
B: 10, because `repartition` without a number keeps the existing partition count.
C: 1, because partitioning by a low-cardinality column puts all rows into one partition.
D: 64, because without an explicit number the hash repartition uses the shuffle partition setting.
K: D
G: ## Repartition by column
`DataFrame.repartition(numPartitions, *cols)` returns a hash-partitioned DataFrame. The first argument may be left out: `repartition("k")` then uses the default number of partitions for DataFrame shuffles, which is `spark.sql.shuffle.partitions`.
- Rows with the same value of `k` always land in the same partition.
- Different keys can share a partition, and some partitions can be empty. The count does not depend on the number of distinct values.
- With AQE on, the runtime may coalesce the result of a column-only repartition. The stem turns AQE off so the configured value shows through.
W: The partition count equals `spark.sql.shuffle.partitions`, so the code prints 64. Three of those partitions hold data, and the others are empty.
X: A=One partition per value: hash partitioning does not size itself by cardinality. It uses the configured shuffle count.
B=Keep the existing count: `repartition` is a full shuffle, so it does not keep the input layout. `coalesce` can only lower the existing count.
C=One partition: equal keys share a partition, but nothing merges the whole DataFrame into one.
T: `repartition(col)` without a number hashes into `spark.sql.shuffle.partitions` partitions (AQE aside).

@ DBX-ASD D1 T1.5 applied definition
S: A single splittable Parquet file of about 1 GB is read with default settings (`spark.sql.files.maxPartitionBytes` is 128 MB). Roughly how many input partitions does Spark create for the scan?
A: About 8, because Spark splits the file into pieces of at most the maximum size.
B: Exactly 1, because a single file is never divided between several tasks.
C: 200, because the scan uses the default number of shuffle partitions of the session.
D: One per Parquet column, because Spark reads each column of the file in its own task.
K: A
G: ## Input partitions for file sources
Reading files does not shuffle, so `spark.sql.shuffle.partitions` plays no role. Spark plans the scan from file sizes.
- `spark.sql.files.maxPartitionBytes` (default 128 MB) is the maximum number of bytes packed into one partition for Parquet, ORC, JSON, CSV and similar sources.
- A splittable file larger than that is cut into several byte ranges. About 1024 MB / 128 MB gives roughly 8 partitions.
- Small files are packed together up to the same limit, with `spark.sql.files.openCostInBytes` added per file as an estimated open cost.
W: The 1 GB file is split at the 128 MB limit, which gives about 8 scan tasks that run in parallel.
X: B=One partition per file: only non-splittable inputs (for example a gzip-compressed CSV) are bound to a single task. A plain Parquet file is split.
C=Shuffle partitions: that setting applies after a shuffle, not when reading files.
D=One per column: Parquet is columnar, but Spark parallelizes by byte ranges of the file, and each task reads the columns the query needs.
T: File scans are sized by `spark.sql.files.maxPartitionBytes`, not by the shuffle setting.

@ DBX-ASD D1 T1.5 applied comparison
S: `df_a` has 3 partitions and `df_b` has 5 partitions, with the same schema. What does the code below print, and does it shuffle?
`print(df_a.union(df_b).rdd.getNumPartitions())`
A: 5, because Spark keeps the larger of the two partition counts for the union.
B: 200, because every union ends in a shuffle with the default shuffle partition count.
C: 8, because union concatenates the partitions of both inputs and does not shuffle.
D: 3, because the first DataFrame decides the layout and the second one is merged into it.
K: C
G: ## Narrow and wide dependencies
A narrow transformation lets each output partition depend on a limited set of input partitions, so no data has to move between executors. `filter`, `select`, `withColumn` and `union` are narrow. A wide transformation (`groupBy`, `join`, `distinct`, `repartition`) needs a shuffle.
- `union` simply places the partitions of the two inputs next to each other, so the result has 3 + 5 = 8 partitions.
- It does not remove duplicates; `union` behaves like SQL `UNION ALL`.
- A later wide operation then creates the shuffle partitions again.
W: Union is a narrow operation that appends the 5 partitions to the 3 existing ones, so it prints 8 and runs without a shuffle.
X: A=Larger count: partition counts are added for a union. Nothing takes a maximum.
B=Shuffle on every union: union does not redistribute rows, so `spark.sql.shuffle.partitions` does not apply.
D=First input decides: both inputs keep their own partitions in the result.
T: `union` is narrow: the output partition count is the sum of the input counts.

@ DBX-ASD D1 T1.5 applied use-case
S: A job reads 400 CSV files of 1 MB each (400 MB in total) with default file-source settings. Which description of the scan partitions is correct?
A: 400 partitions, because Spark always creates one partition for every input file.
B: 200 partitions, because the scan uses the default number of shuffle partitions.
C: Far fewer than 400, because Spark packs several small files into each partition and adds an open cost per file.
D: About 4, because Spark divides the total bytes by 128 MB and the cost of opening a file is not counted.
K: C
G: ## Packing small files into partitions
For file sources Spark first lists the files and sorts them by size. It then fills partitions up to `spark.sql.files.maxPartitionBytes` (128 MB). Every file adds `spark.sql.files.openCostInBytes` (default 4 MB) to the running total, to reflect that opening a file is not free.
- Here each file counts as about 1 MB + 4 MB = 5 MB, so a partition takes about 25 files.
- 400 files give roughly 16 partitions, far fewer than 400 tasks, but more than the 4 that the raw byte count suggests.
- Millions of tiny files are still slow: listing and opening them costs time even when they are packed.
W: Several small files go into one partition and every file carries an open cost, so the scan has far fewer than 400 partitions, about 16 here.
X: A=One per file: that holds for large non-splittable files, but Spark packs small files together.
B=Shuffle default: no shuffle happens in a plain scan, so the setting does not apply.
D=Bytes divided by 128 MB: that ignores the per-file open cost, which pushes the real count up.
T: File scans pack small files into partitions using maxPartitionBytes plus an open cost per file.

@ DBX-ASD D1 T1.5 advanced comparison
S: A job must write Parquet output in which each file covers a separate, non-overlapping range of `ts` values, so that a downstream reader can skip files by min/max statistics. The output should have 8 files. Which call prepares the DataFrame?
A: `df.repartitionByRange(8, "ts")`, which samples the data and assigns contiguous ranges of `ts` to the partitions.
B: `df.repartition(8, "ts")`, which hash-partitions the rows, so every file receives values spread over the whole range.
C: `df.coalesce(8)`, which merges existing partitions and keeps whatever value ranges they already hold.
D: `df.repartition(8)`, which distributes rows round-robin, so each file holds a random sample of `ts` values.
K: A
G: ## Hash, range and round-robin partitioning
Spark offers several ways to lay out rows across partitions.
- `repartition(n, col)` is hash partitioning: equal keys share a partition, but neighboring values scatter, so every partition spans the full range.
- `repartitionByRange(n, col)` samples the column to pick range boundaries and gives each partition a contiguous slice of values.
- `repartition(n)` without columns spreads rows evenly (round-robin) and says nothing about values. `coalesce(n)` only merges partitions without a shuffle.
Range partitioning is what makes per-file min/max statistics selective, because files do not overlap.
W: `repartitionByRange` places contiguous `ts` ranges in separate partitions, so each of the 8 files has a narrow min/max range that readers can use for skipping.
X: B=Hash repartition: it groups equal `ts` values but scatters neighbors, so each file's min and max cover nearly the whole domain.
C=Coalesce: it keeps the existing layout, which comes from the reader and not from `ts`, and it cannot guarantee ranges.
D=Round-robin repartition: rows are spread by position, so every file contains a random sample of `ts`.
T: Use `repartitionByRange` when files must hold contiguous value ranges; hash partitioning only keeps equal keys together.

@ DBX-ASD D1 T1.6 applied use-case
S: A notebook runs the lines below on a large Parquet dataset. The first three lines return within a second, and the fourth keeps the cluster busy. Which line starts the Spark job?
`df = spark.read.parquet(path)`
`a = df.filter("x > 1")`
`b = a.select("x", "y")`
`c = b.count()`
A: `df = spark.read.parquet(path)`, because the files have to be read before the later lines can use them.
B: `a = df.filter("x > 1")`, because a filter must scan every row to decide which ones stay.
C: `b = a.select("x", "y")`, because selecting columns rewrites the data in memory.
D: `c = b.count()`, because `count()` is an action that forces the whole chain of transformations to run.
K: D
G: ## Transformations are lazy, actions are not
Spark splits DataFrame operations into two groups.
- Transformations such as `read`, `filter`, `select`, `withColumn`, `join` and `groupBy` only add a step to the logical plan. No data moves, and they return a new DataFrame immediately.
- Actions such as `count()`, `collect()`, `show()`, `take()` and `write` ask for a result. Each action submits a job that executes the optimized plan.
- Because the plan is built first, Spark can optimize the whole chain, for example by reading only the columns `x` and `y` and pushing `x > 1` into the Parquet scan.
W: Only `count()` is an action. It triggers execution of the read, filter and select together, so it is the line that keeps the cluster busy.
X: A=read: it only defines the source (apart from reading file footers or listing paths for planning). The scan itself waits for an action.
B=filter: it records a predicate in the plan. The rows are tested when an action runs the scan.
C=select: it adds a projection to the plan and does not materialize anything.
T: Transformations build a plan; the first action runs it.

@ DBX-ASD D1 T1.6 advanced troubleshooting
S: A UDF turns a text column into an integer, and one input row contains the text `"abc"`. The code runs as follows. When does the error appear?
`@udf("int")`
`def parse(s): return int(s)`
`df2 = df.withColumn("n", parse("txt"))`
`print("built")`
`rows = df2.collect()`
A: At the `withColumn` call, because Spark validates every value of the column while it defines the new column.
B: At the `collect()` call, inside a task, as a Python exception in the failed job. The `print` still runs.
C: Never, because a UDF returns NULL for any value that it cannot convert and moves on.
D: At the `print` call, because Spark flushes all pending transformations before any output.
K: B
G: ## Errors in data surface at action time
`withColumn` only records a projection with the UDF in the plan, so no row is passed to Python yet. The UDF runs inside executor tasks when an action evaluates the column.
- Problems found while resolving the plan (a missing column, a wrong function name) can be raised when the transformation is called, in classic PySpark.
- Problems in the data (a bad value, a failing UDF, a failed cast under ANSI mode) show up only when the affected rows are processed, as a failed task and a failed job.
- An exception inside a UDF is not turned into NULL. Wrap the conversion in `try`/`except` if NULL is wanted.
W: Building `df2` runs nothing, so `built` is printed. The failure occurs when `collect()` evaluates the UDF on the bad row and the task raises.
X: A=At withColumn: nothing evaluates row values while the plan is defined.
C=Returns NULL: a UDF that raises fails the task. Only code that catches the error and returns `None` produces NULL.
D=At print: `print` is plain Python and does not trigger a Spark job.
T: Data errors appear when an action processes the rows, not when the transformation is defined.

@ DBX-ASD D1 T1.6 applied comparison
S: A developer runs each of the calls below on an uncached DataFrame `df` that was read from Parquet. Which call returns immediately without starting a Spark job?
A: `df.cache()`, which only marks the DataFrame for caching. The data is stored when a later action first runs.
B: `df.first()`, which has to read at least one row, so it launches a job over a small number of partitions.
C: `df.collect()`, which brings every row back to the driver and therefore launches a job over all partitions.
D: `df.write.parquet(out)`, which writes the result and therefore launches a job that produces the output files.
K: A
G: ## Which calls are actions
`cache()` and `persist()` are lazy. They register a storage level for the plan, and the first action that computes the DataFrame fills the cache.
- Actions return a value to the driver or write data out: `count`, `collect`, `first`, `head`, `take`, `show`, `foreach`, `toPandas` and every `write` call.
- `limit`, `select`, `filter`, `repartition` and `explain` do not start a job on the data. `explain` prints the plan and returns.
- Forgetting that `cache()` is lazy leads to the surprise that nothing appears in the Storage tab until an action runs.
W: `cache()` only records the persist request in the plan, so it returns at once and the Storage tab stays empty until an action runs.
X: B=first(): it returns a row to the driver, which is an action, so Spark launches a job.
C=collect(): it is the classic action and runs a job over all partitions.
D=write.parquet: every write is an action and executes the plan to produce the files.
T: `cache()` is lazy; actions return data to the driver or write it out.

@ DBX-ASD D1 T1.6 applied definition

A DataFrame is a recipe, not stored data. Every action submits a new job that runs the whole plan from the source, unless a cache or a reused shuffle output shortens it.
- Two `count()` calls on an uncached DataFrame read and filter the files twice.
- `df.cache()` before the first action stores the filtered partitions, so the second action reads from memory.

@ DBX-ASD D1 T1.6 applied use-case
S: A DataFrame `df` has 1,000 partitions and 500 million rows. A developer calls `df.filter("status = 'ERR'").take(3)`, and the first partitions that Spark scans already contain three matching rows. What is the likely behavior?
A: Spark filters all 1,000 partitions first and then cuts the result down to three rows on the driver.

C: Spark always processes exactly one partition, so `take` may return fewer rows than were requested.

G: ## Actions that need only a few rows
`take(n)`, `head(n)`, `first()` and `limit(n)` followed by an action do not have to touch the whole dataset.
- For `take(n)` the driver starts by scanning one partition. If that does not yield enough rows, it scans more partitions in later rounds, with a growing number of partitions per round.
- When the requested rows are found early, the remaining partitions are never computed, which makes `take` far cheaper than `collect()` on large data.
- If few rows match the filter, many partitions may be needed, and the cost approaches a full scan.
W: `take(3)` is an action that reads partitions incrementally and stops once three rows are available, so a matching filter makes it cheap.
X: A=Full filter first: the driver scans a few partitions at a time and does not need to process everything.

D=Transformation: `take` returns a Python list of `Row` objects, so it is an action.
T: `take(n)` scans partitions incrementally, so it is much cheaper than `collect()` when matches are plentiful.

@ DBX-ASD D1 T1.6 advanced definition
S: A developer writes `spark.read.parquet(p).select("a", "b", "c").filter("a = 5").select("b")`. The physical plan shows a scan that reads only columns `a` and `b` and a filter on `a` pushed into the Parquet reader. Which property of Spark's execution model makes this possible?
A: Eager evaluation, because each step is executed as soon as it is written and its result is stored.
B: Tungsten code generation, because it rewrites the Parquet files so that unused columns are removed.
C: Lazy evaluation, because Catalyst optimizes the whole chain of transformations as one plan when an action runs.
D: Speculative execution, because Spark guesses which columns later steps need and reads them ahead of time.
K: C
G: ## Why laziness helps the optimizer
When transformations only build a logical plan, Catalyst can analyze and rewrite the whole plan before any data is read.
- Column pruning: only `a` and `b` are needed, so the Parquet scan skips `c`.
- Predicate pushdown: the filter `a = 5` is handed to the reader, which can skip row groups using min/max statistics.
- Operator reordering and combining: adjacent projections collapse, and narrow operations are pipelined into a single stage.
- `df.explain()` prints this optimized plan without running a job.
W: Because transformations are lazy, the optimizer sees the full chain at action time and prunes columns and pushes the filter down before the scan runs.
X: A=Eager evaluation: executing each step on its own would read all three columns first, so there would be nothing left to prune.
B=Tungsten code generation: it speeds up in-memory execution, and it never rewrites source files.
D=Speculative execution: it re-launches slow tasks and has nothing to do with choosing columns.
T: Lazy evaluation lets Catalyst optimize the whole plan at once, which enables pruning and pushdown.
