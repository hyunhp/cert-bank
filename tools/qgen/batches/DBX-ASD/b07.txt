@ DBX-ASD D4 T4.2 applied definition
S: A colleague says that Adaptive Query Execution (AQE) can pick a better plan than the one built before the query started. Which statement describes what AQE actually does?
A: It rewrites the logical plan at analysis time by using column statistics that were computed earlier with ANALYZE TABLE on the source tables
B: It re-optimizes the rest of the plan while the query runs, by using accurate statistics from shuffle stages that have already finished
C: It adds executors to the cluster during a long stage, so that a slow stage gets more cores without any change to the query plan
D: It caches the output of every finished stage on the executors, so that a failed task never has to recompute any upstream data
K: B
G: ## Static plan versus adaptive plan
Before a query runs, the optimizer builds a physical plan from estimates: file sizes, table statistics, default selectivity guesses. Estimates are often wrong, especially after filters, joins and user code.
Adaptive Query Execution (AQE) is a Spark SQL feature that uses runtime statistics to choose a more efficient plan. It is enabled by default since Spark 3.2.0 and is controlled by the umbrella setting `spark.sql.adaptive.enabled`.
## How it works
- A shuffle ends a stage and writes map output files, so Spark knows the real size of every shuffle partition when the stage finishes.
- AQE uses those numbers to re-plan the stages that have not started yet.
- Its three main optimizations are: coalescing small post-shuffle partitions, switching a join strategy (sort-merge join to broadcast hash join), and splitting skewed partitions in a sort-merge join.
W: Runtime re-optimization: the setting is described as re-optimizing the query plan in the middle of execution based on accurate runtime statistics, which become available once a shuffle stage has finished.
X: A=Table statistics: statistics from ANALYZE TABLE feed the static, cost-based planning that happens before execution. AQE is the opposite idea: it uses what it measures while the query runs.
C=Adding executors: growing or shrinking the executor set is dynamic allocation, a cluster resource feature. AQE changes the query plan, not the number of cores.
D=Caching stage output: AQE does not cache stage results for recovery. Shuffle files do survive on executors, but that is normal fault tolerance and has nothing to do with choosing a better plan.
T: AQE re-plans the remaining stages with real shuffle statistics; it is on by default and changes plans, not cluster size.
V: Spark SQL

@ DBX-ASD D4 T4.2 applied use-case
S: A daily job groups about 30 MB of aggregated sales rows by `store_id`. The Spark UI shows that the stage after the shuffle ran far fewer than 200 tasks, although `spark.sql.shuffle.partitions` has the default of 200 and nobody changed any adaptive setting. What explains the small task count?
```
daily = (sales.groupBy("store_id")
         .agg(F.sum("amount").alias("total")))
daily.write.mode("overwrite").parquet(out)
```
A: Spark reduces `spark.sql.shuffle.partitions` automatically at session start by looking at the number of input files that the query is going to read
B: The optimizer pushed the aggregation into the Parquet scan, so each file produced its own output partition and the data was never shuffled
C: Dynamic allocation released most executors, so only 3 of the 200 shuffle partitions could be read, and the rest were processed inside those tasks
D: AQE coalesced contiguous small shuffle partitions after the shuffle stage, based on the partition sizes it measured in the map output
K: D
G: ## Why 200 partitions are often too many
A wide transformation such as `groupBy` creates `spark.sql.shuffle.partitions` post-shuffle partitions (default 200). With 30 MB of data that means about 150 KB per task: scheduling cost is larger than the work.
## What AQE does about it
When `spark.sql.adaptive.enabled` and `spark.sql.adaptive.coalescePartitions.enabled` are true (both default to true), AQE reads the map output statistics and merges contiguous small partitions. By default `spark.sql.adaptive.coalescePartitions.parallelismFirst` is true, so Spark ignores the advisory size (`spark.sql.adaptive.advisoryPartitionSizeInBytes`, 64 MB) and only respects the minimum partition size (`spark.sql.adaptive.coalescePartitions.minPartitionSize`, 1 MB) to keep parallelism high; with it set to false the advisory size is the target. The starting number of partitions is `spark.sql.adaptive.coalescePartitions.initialPartitionNum`; if unset it equals `spark.sql.shuffle.partitions`.
The result is that you do not have to tune the shuffle partition count to fit each dataset.
W: Partition coalescing: the 200 initial shuffle partitions were tiny, so AQE merged contiguous ones after the shuffle and the next stage needed far fewer than 200 tasks.
X: A=Automatic setting change: `spark.sql.shuffle.partitions` is a plain configuration value that Spark does not recompute from the input file count. The reduction happens after the shuffle, per query, by AQE.
B=Aggregation pushdown: a full aggregation across files cannot be done inside the scan, because rows of one store sit in many files. A shuffle is still required, which is why a post-shuffle stage exists at all.
C=Dynamic allocation: executors do not decide how many partitions exist. Fewer executors would make tasks queue up, not merge 200 partitions into a few tasks.
T: With AQE on, a high initial shuffle partition count is safe because small post-shuffle partitions are coalesced at runtime.

@ DBX-ASD D4 T4.2 applied use-case
S: A join of a large `orders` table with a `regions` table is planned as a sort-merge join, because without statistics Spark assumes `regions` is large. The filter below keeps only a small slice, and after the first shuffle stage AQE sees that this side is only a few MB. What can AQE do with the remaining plan?
```
eu = regions.filter("continent = 'EU'")
res = orders.join(eu, "region_id")
res.write.mode("overwrite").parquet(out)
```
A: Convert the sort-merge join into a broadcast hash join, because the runtime size of one side is below the adaptive broadcast threshold
B: Keep the sort-merge join, because a join strategy is chosen once during planning and cannot change after the first stage has run
C: Replace the join with a cross join, because small tables can be matched against every large row without the key in the join condition
D: Cancel the shuffle stage that has already finished and restart the query with the small side broadcast from the very beginning
K: A
G: ## Join strategy and size estimates
A broadcast hash join sends the small side to every executor, so the large side is not shuffled. It is the cheapest strategy, but Spark picks it at planning time only when its size estimate is under the broadcast threshold. After filters, joins or UDFs the estimate is often far too high, so the planner falls back to a sort-merge join.
## Converting at runtime
AQE converts a sort-merge join to a broadcast hash join when the runtime statistics of either join side are smaller than the adaptive broadcast threshold. The setting `spark.sql.adaptive.autoBroadcastJoinThreshold` defaults to the value of `spark.sql.autoBroadcastJoinThreshold`.
The documentation notes that this is not as efficient as planning a broadcast join from the start, but it is better than continuing with the sort-merge join, because both sides do not need sorting and, with the local shuffle reader enabled (default), the shuffle files can be read locally.
W: Runtime join conversion: the measured size of the filtered side is under the adaptive broadcast threshold, so AQE switches the remaining join to a broadcast hash join and reads the existing shuffle files locally.
X: B=Fixed strategy: this describes the behaviour without AQE. With AQE enabled, the join selection for stages that have not started can be changed from runtime statistics.
C=Cross join: the join condition is part of the query semantics. AQE changes the physical strategy only; it never changes the logical result.
D=Restart: AQE does not throw away finished shuffle stages. It reuses their output files, which is how it can read them locally after the conversion.
T: AQE can turn a sort-merge join into a broadcast hash join when real sizes turn out small, reusing the shuffle output it already has.

@ DBX-ASD D4 T4.2 advanced use-case
S: A join on `user_id` is slow because 90% of the rows in `events` share one `user_id` value. One task in the shuffle stage reads far more data than the others. AQE is enabled. How does AQE's skew handling deal with this sort-merge join?
```
res = events.join(users, "user_id")
res.write.mode("overwrite").parquet(out)
```
A: It adds a random suffix to the skewed key on both sides, performs the join on the salted keys and then removes the suffix again
B: It broadcasts the rows of the skewed key to every executor and runs a separate map-side join for them, leaving the other keys alone
C: It splits the oversized partition into smaller sub-partitions and replicates the matching partition of the other side
D: It drops the skewed partition from the join as soon as it exceeds the median size by the configured skew factor, to protect the stage
K: C
G: ## Data skew in a sort-merge join
In a sort-merge join both sides are shuffled by the join key, so all rows of one key land in one partition. If one key holds most of the rows, one task does most of the work while the other cores wait.
## AQE skew join
When `spark.sql.adaptive.enabled` and `spark.sql.adaptive.skewJoin.enabled` are true (the defaults), AQE splits skewed partitions of a sort-merge join into roughly evenly sized tasks and replicates the matching data of the other side if needed.
- A partition counts as skewed when it is larger than `spark.sql.adaptive.skewJoin.skewedPartitionFactor` (5) times the median partition size and also larger than `spark.sql.adaptive.skewJoin.skewedPartitionThresholdInBytes` (256 MB).
- The target size of the pieces is guided by `spark.sql.adaptive.advisoryPartitionSizeInBytes`.
- It works for sort-merge joins, and it is handled automatically; no code change is needed.
W: Splitting and replicating: AQE cuts the huge partition of the skewed side into several sub-partitions, each joined with a copy of the matching partition of the other side, so many tasks share the work.
X: A=Salting: manual key salting is a code-level technique that developers add themselves. AQE splits partitions by size and does not rewrite keys.
B=Separate broadcast path: AQE does not route one key through a different join. The skewed partition stays in the same sort-merge join, only divided into parts.
D=Dropping data: removing a partition would give wrong query results. The skew thresholds only decide which partitions are split.
T: AQE skew join splits an oversized sort-merge join partition into smaller tasks and replicates the other side, without changing the result.

@ DBX-ASD D4 T4.2 advanced tradeoff
S: Daily input for one pipeline varies from 1 GB to 2 TB. The team runs on Spark with AQE at its default and wants good task sizes without editing configuration every day. Which setup fits AQE's design best?
A: Set `spark.sql.shuffle.partitions` to a small value such as 20, because AQE will split the partitions on large days up to the advisory size
B: Disable AQE and compute the partition count in driver code from the input size, then call `spark.conf.set` before each query
C: Set the advisory partition size to 1 byte, so that AQE always creates one task per row range and never leaves any partition too large
D: Set a high initial partition count that suits the biggest day and leave coalescing on, so that small days are merged at runtime
K: D
G: ## Coalescing only goes down
AQE's coalescing merges contiguous small shuffle partitions after the shuffle. It starts from `spark.sql.adaptive.coalescePartitions.initialPartitionNum` (or `spark.sql.shuffle.partitions` if unset) and can only reduce that number. It does not add partitions to get below the advisory size (default 64 MB) on a huge day; splitting happens only for skewed join partitions.
## The consequence for tuning
The documentation says you do not need to set the right shuffle partition number for each dataset: set a large enough initial number and let Spark pick the proper number at runtime.
- 1 GB day: thousands of tiny initial partitions are merged into a few tasks.
- 2 TB day: the high initial count keeps each partition manageable.
W: High initial count plus coalescing: the starting number covers the largest day, and AQE merges partitions on small days, so no daily tuning is needed.
X: A=Low initial count: coalescing cannot increase the count. With only 20 partitions, a 2 TB day gives huge partitions that risk spilling or running out of memory.
B=Manual computation: this brings back the daily tuning that AQE removes, and turning AQE off also loses join conversion and skew handling.
C=Tiny advisory size: this is a nonsensical value; the advisory size is the target for merged partitions, and a tiny target would keep every partition unmerged and tasks tiny, which is the opposite of what is wanted.
T: Coalescing only reduces the partition count, so start high enough for the largest input and let AQE shrink it for small ones.

@ DBX-ASD D4 T4.2 applied troubleshooting
S: A developer expects AQE to speed up the job below. The input is two large gzip-compressed CSV files, the Spark UI shows 2 tasks in the only stage, and no shuffle happens. AQE is on. Why does AQE not add parallelism here?
```
df = spark.read.csv(path, header=True)
out = df.filter("amount > 0")
out.write.mode("overwrite").parquet(dest)
```
A: AQE re-optimizes plans around shuffle boundaries, and this plan has none, so the number of scan partitions stays as the file layout gives it
B: AQE is disabled automatically whenever the source format is CSV, because text sources do not report any size statistics to the engine
C: AQE only starts after the first 1,000 tasks have finished, and this job has not reached that task count yet so no change is allowed
D: AQE splits scan partitions only when the output format is Delta, so the Parquet write in this snippet receives no adaptive treatment
K: A
G: ## Where AQE works
AQE uses statistics from finished shuffle stages. Its optimizations act on shuffle partitions (coalescing), on joins (strategy switch, skew splitting) and on the plan between stages.
A map-only job has no exchange: the scan partitions are determined by the files and by settings such as `spark.sql.files.maxPartitionBytes`. Gzip-compressed files cannot be split, so two files give two scan tasks and AQE has nothing to adapt.
## What to do instead
- Increase the number of partitions with `repartition(n)` after reading (this adds a shuffle, so later stages run wider).
- Store the data in a splittable format such as Parquet or uncompressed CSV so files can be divided by size.
W: No shuffle boundary: AQE needs map output statistics from a finished shuffle stage, so a plan without exchanges keeps the scan parallelism that the files provide.
X: B=CSV disables AQE: AQE does not depend on the file format being CSV or not. The reason here is the lack of any shuffle in the plan.
C=Task count threshold: there is no minimum count of finished tasks before AQE acts. It acts when a shuffle stage completes and statistics exist.
D=Delta only: AQE is a Spark SQL feature, independent of the output format. A Parquet write is eligible in the same way as any other write.
T: AQE tunes what happens after shuffles; it does not change scan parallelism, so use repartition or a splittable input for that.

@ DBX-ASD D4 T4.3 applied troubleshooting
S: A notebook runs `rows = big_df.collect()` and the job aborts with the message "Total size of serialized results of 480 tasks is bigger than spark.driver.maxResultSize". The next step needs only the number of rows per country. What is the best fix?
A: Raise `spark.executor.memory`, because the serialized results are held in the executors until the action returns them to the driver
B: Set `spark.driver.maxResultSize` to 0 and keep the code, so that results of any size can be pulled back to the driver
C: Aggregate on the cluster with `groupBy("country").count()` and collect only that small result, or write the data out
D: Call `coalesce(1)` before `collect()`, so the data is delivered to the driver as one partition instead of 480 results
K: C
G: ## What collect() does
`collect()` is an action that sends the serialized result of every task to the driver and builds one list there. The setting `spark.driver.maxResultSize` (default 1g) limits the total size of those serialized results for each action; above it, the job is aborted. The documentation also warns that a high limit may cause out-of-memory errors in the driver, so the limit protects it.
## Developer rule
Do heavy work where the data lives. Reduce data with filters and aggregations first, then collect a small result; or write large results to storage instead of bringing them to the driver.
```
counts = big_df.groupBy("country").count()
rows = counts.collect()   # a few hundred small rows
```
W: Aggregate before collecting: the cluster computes the counts and the driver receives only one row per country, so the limit is never approached.
X: A=Executor memory: the failure is a size check at the driver. More executor memory does not shrink the data that must be sent back.
B=Unlimited result size: setting the limit to 0 removes the check, but the same volume will then sit in driver memory, risking a driver out-of-memory error. It hides the problem instead of removing it.
D=Single partition: `coalesce(1)` makes one big task result, which is the same total size, and it removes parallelism from the stage before it.
T: A driver result-size error means too much data is pulled to the driver; aggregate or write on the cluster instead of raising limits.

S: A join stage fails with `java.lang.OutOfMemoryError: Java heap space` inside tasks. Only 40 shuffle partitions are used and each one holds roughly 20 GB. The driver is healthy. Which change addresses the cause?
A: Raise `spark.driver.maxResultSize`, because the shuffle partitions are collected by the driver when the join stage starts

D: Reduce the number of executor cores to one, so that the cluster has fewer parallel tasks reading shuffle files at the same time

Shuffle operations such as `join`, `groupBy` and `sortBy` build a hash table (or sort buffer) in each task for its share of the data. If a task's partition is huge, that structure exceeds the executor's memory.
The Spark tuning guide says the simplest fix is to increase the level of parallelism so each task's input is smaller. Spark handles short tasks well, and you can go above the number of cores.

- Raise `spark.sql.shuffle.partitions` or use `repartition(n)` before the wide operation.

X: A=Driver result size: that setting only limits what actions return to the driver. The error here is an executor heap error inside tasks, and the driver is healthy.
C=Caching both inputs: caching stores the input in memory, which competes with execution memory and does not shrink the 20 GB a single task must process.
D=One core per executor: this reduces concurrency and gives each task more memory, but the partition size stays at 20 GB and the job gets much slower. It treats a symptom.

@ DBX-ASD D4 T4.3 applied troubleshooting
S: A cluster with 8 executors of 4 cores each (32 cores) processes the pipeline below. The Stages tab shows only 4 tasks in the long UDF stage, and the Executors tab shows most cores idle. What diagnosis and fix is correct?
```
df = spark.read.parquet(src).coalesce(4)
res = df.withColumn("score", slow_udf("text"))
res.write.mode("overwrite").parquet(dest)
```
A: Executors are too small; add more executors so the 4 tasks can be spread over additional machines and finish sooner
B: Executor memory is too low for the UDF; raise `spark.executor.memory` so the 4 tasks stop waiting for free memory
C: The Python worker is the bottleneck; enable Kryo serialization so the 4 tasks can use the idle cores for a shared pool
D: Only 4 partitions exist, so at most 4 tasks run at once; repartition to a multiple of the 32 cores before the UDF
K: D
G: ## Parallelism equals partitions
A stage runs one task per partition, and a task occupies one core. With 4 partitions at most 4 cores are busy, regardless of cluster size. This is underutilization: the Executors tab shows idle cores while the Stages tab shows few tasks.
`coalesce(4)` is a narrow transformation that reduces partitions without a shuffle; it propagates upstream, so the expensive UDF also runs with 4 partitions.
## Fix
```
df = spark.read.parquet(src).repartition(96)   # 2-3x the 32 cores
```
The tuning guide notes that Spark supports short tasks well, so using more partitions than cores is safe and keeps all cores busy.
W: Too few partitions: the stage cannot run more tasks than partitions, so repartitioning to a multiple of the available cores lets every core work on the UDF.
X: A=More executors: extra machines add cores that still have no tasks to run, since the stage has only 4 tasks. Cost goes up and runtime stays the same.
B=More executor memory: the symptom is idle cores and a small task count, not tasks waiting for memory. Nothing in the stem points to memory pressure.
C=Kryo serialization: this affects how JVM objects are serialized and does not create tasks or let a Python UDF stage use more cores.
T: If cores sit idle in a stage with few tasks, increase the partition count; adding executors does not add tasks.

@ DBX-ASD D4 T4.3 applied troubleshooting
S: On Kubernetes, executors of a PySpark job disappear mid-stage. The driver log reports that the executor pods were killed for exceeding their memory limit, and the executor logs show no `OutOfMemoryError`. The job uses Python UDFs and large native libraries. Which setting should be raised first?
A: `spark.executor.logs.rolling.maxSize`, which sets the file size at which executor log files are rolled over to a new file
B: `spark.driver.maxResultSize`, which limits the total size of serialized task results that the driver may accept in one action
C: `spark.eventLog.compress`, which controls whether the Spark event log is compressed before it is written to storage
D: `spark.executor.memoryOverhead`, which sizes the non-heap memory per executor for native allocations and the Python worker processes
K: D
G: ## Heap versus container memory
An executor runs in a container whose limit is the JVM heap (`spark.executor.memory`) plus extra non-heap memory. When the process uses more than the container limit, the cluster manager kills it. The JVM never gets a chance to throw `OutOfMemoryError`, so the executor log shows nothing.
`spark.executor.memoryOverhead` is the additional memory per executor for VM overheads, interned strings and other native overheads. It defaults to executor memory times `spark.executor.memoryOverheadFactor` (0.10), with a minimum, and the option is supported on YARN and Kubernetes. Python workers and native libraries use this non-heap space.
## Diagnose from the logs
- Driver log or cluster manager events: "killed by the cluster manager / exceeding memory limits".
- Executor log: no Java heap error.
W: Memory overhead: the pods exceeded their container limit through non-heap use by Python and native code, so more overhead memory is the targeted fix.
X: A=Log rolling size: log rolling controls the size of the log files on disk, not the memory the executor process is allowed to use.
B=Result size limit: this applies to results sent back to the driver after an action. It has no effect on executor pod memory.
C=Event log compression: this only changes how event log files are stored; it neither reduces memory use nor changes pod limits.
T: A container kill without a Java heap error points to non-heap memory; raise spark.executor.memoryOverhead.

@ DBX-ASD D4 T4.3 applied troubleshooting
S: Executor logs of a long job show that a full garbage collection ran several times before a single task completed, and task times are growing. What does the Spark tuning guide say this means?
A: The network is saturated, so shuffle fetches are retried and objects pile up in the heap while waiting for remote blocks
B: Too many tiny partitions exist, so the scheduler creates more task objects than the driver is able to garbage collect
C: There is not enough memory available for executing tasks, so consider more memory or less memory used for caching
D: The old generation is empty, which shows that all cached data was evicted and the job can safely keep running unchanged

Spark runs on the JVM, and tasks create many short-lived objects. The Spark tuning guide recommends collecting GC statistics to see how often collection happens and how much time it takes.

- A full GC invoked several times before a task finishes: there is not enough memory for task execution.

W: Insufficient execution memory: repeated full GCs before a task completes mean the task's working set does not fit, which is the guide's signal to add memory or cache less.

B=Too many small partitions: many tiny tasks create scheduling overhead on the driver side; they do not cause repeated full GCs within one executor task.
D=Empty old generation: the guide reads a nearly full old generation as the warning sign. An empty one would not cause repeated full collections.
T: Several full GCs before one task finishes means tasks lack execution memory; add memory, cache less or shrink partitions.

@ DBX-ASD D4 T4.3 applied troubleshooting
S: The driver log of a job shows the warning that a stage contains a task of very large size. The job passes a 400 MB Python dictionary into a UDF by referencing it directly inside the function. What is the likely cause and the standard remedy?
A: The dictionary is serialized into every task along with the function, so it should be sent once to each executor as a broadcast variable
B: The dictionary is stored in the driver's event log, so reducing `spark.eventLog.dir` retention will make the task size smaller
C: The UDF runs on the driver, so its memory should be raised with `spark.driver.maxResultSize` to allow the larger objects
D: The dictionary was cached by the optimizer, so calling `unpersist()` on the DataFrame removes the object from task payloads
K: A
G: ## Closures travel with tasks
When a UDF references a driver-side object, Spark serializes that object with the function and ships it in every task. If the object is large, each task payload becomes large: the driver sends the same 400 MB again and again, scheduling slows down and memory is used on both sides.
The Spark tuning guide says that broadcast variables can greatly reduce the size of each serialized task. Spark prints the serialized size of each task on the master, so you can check whether tasks are too large; tasks above about 20 KiB are probably worth optimizing.
## Fix
```
bc = spark.sparkContext.broadcast(big_dict)
lookup = F.udf(lambda k: bc.value.get(k), "string")
res = df.withColumn("v", lookup("key"))
```
The broadcast copy is sent once per executor and read from there by all tasks.
W: Large closure: the dictionary rides inside every task, so a broadcast variable ships it once per executor and keeps the task payload small.
X: B=Event log retention: the event log records what happened; it does not feed task payloads. Changing its directory has no influence on task size.
C=Driver result size: this setting limits data returned from executors to the driver, and UDFs run on the executors, not on the driver.
D=unpersist: the object is part of the function closure, not a cached DataFrame block, so unpersisting a DataFrame does not remove it from the tasks.

@ DBX-ASD D5 T5.1 applied comparison
S: A team wants end-to-end exactly-once results from a Structured Streaming query after any failure and restart. Which combination of source, sink and engine features delivers this guarantee?

G: ## Three ingredients
Delivering end-to-end exactly-once semantics was a key goal of Structured Streaming. The design combines:
- Sources that are replayable: each has offsets (like Kafka offsets or Kinesis sequence numbers) so the engine can re-read exactly the same range after a failure.

D=No window yet: the engine updates the windows immediately; a watermark only decides when state is dropped or when append output is released.
T: With a sliding window, an event counts in every window that contains its time; window length divided by slide gives the maximum number.

@ DBX-ASD D5 T5.3 applied comparison
S: A product team wants to group each user's clicks into activity bursts: a burst ends when the user is silent for 5 minutes, so bursts have different lengths. Which grouping fits the requirement?
A: A tumbling window with `window("ts", "5 minutes")`, which creates fixed non-overlapping 5-minute buckets for each user
B: A sliding window with `window("ts", "5 minutes", "1 minute")`, which creates overlapping windows that start every minute
C: A global aggregation with `groupBy("user").count()`, which keeps one running row per user and never ends a burst
D: A session window with `session_window("ts", "5 minutes")`, which extends a window while events arrive within the gap
K: D
G: ## Session windows
Tumbling and sliding windows have a fixed length. A session window has a dynamic size that depends on the input: it starts with an event and expands while later events arrive within the gap duration. With a static gap, the session closes when no event arrives within the gap after the last one.
## Use
```
sessions = (events.groupBy("user", F.session_window("ts", "5 minutes"))
            .count())
```
- Fixed buckets answer "how many per interval".
- Session windows answer "how many per burst of activity".
W: Session window: its length follows the data, growing with each event within 5 minutes of the last one, which matches variable-length bursts.
X: A=Tumbling: fixed 5-minute buckets cut bursts at arbitrary boundaries and ignore silence between events.
B=Sliding: overlapping fixed windows count events several times and still have a fixed length.
C=Global count: it has no time dimension, so it cannot separate bursts.
T: Use session_window for activity bursts separated by inactivity; window() gives fixed-size buckets.

S: A developer wants windowed counts to be finalized in append mode. The query is rejected, or never frees state, because of the order of the calls. What is wrong?
```
agg = (events.groupBy("ts").count()
             .withWatermark("ts", "1 minute"))
agg.writeStream.outputMode("append").format("console").start()
```
A: `withWatermark` must come before the aggregation, on the same event-time column that the aggregation groups by
B: `withWatermark` must be written after `writeStream`, as an option of the sink, to take effect in append mode
C: The watermark delay must be larger than the window length, otherwise append mode rejects the query at start
D: `withWatermark` works only with the `update` output mode, so append mode is never valid with a watermark
K: A
G: ## Watermark rules for state cleanup
The programming guide lists the conditions for a watermark to clean aggregation state:
- Output mode must be append or update (complete keeps everything).
- The aggregation must use the event-time column, or a `window` on it.
- `withWatermark` must be called on the same column as the timestamp used in the aggregate. `df.withWatermark("time", "1 min").groupBy("time2").count()` is invalid in append mode.
- `withWatermark` must be called before the aggregation. `df.groupBy("time").count().withWatermark("time", "1 min")` is invalid in append mode.
## Correct code
```
agg = (events.withWatermark("ts", "1 minute")
             .groupBy(F.window("ts", "5 minutes")).count())
```
W: Watermark first: applied after the aggregation it has no effect on the state, which is the documented invalid pattern for append mode.
X: B=After writeStream: the watermark is a DataFrame transformation defined on the input side, not a sink option.
C=Delay longer than window: the delay is a lateness tolerance; there is no rule that it must exceed the window size.
D=Update only: watermarks are valid with append and update; only complete mode cannot use them.
T: Call withWatermark before the aggregation, on the same event-time column, or state is not cleaned and append is invalid.
