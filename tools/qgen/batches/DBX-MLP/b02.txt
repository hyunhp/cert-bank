@ DBX-MLP D1 T1.5 applied use-case
S: A claims classifier predicts five damage types, indexed 0 to 4 by a `StringIndexer`. Type 3 (structural damage) is only 1% of the rows but is the one the insurer cannot afford to miss. The team reports the default `MulticlassClassificationEvaluator` score, which looks excellent. Which evaluation change reflects the business risk?
A: Keep the default `f1` metric and set `metricLabel=3.0`, because the evaluator then restricts the F1 score to the structural-damage class
B: Use `metricName="recallByLabel"` with `metricLabel=3.0`, so the evaluator reports the share of true structural-damage claims that the model catches
C: Switch to `metricName="accuracy"`, since the share of correct predictions over all rows is a stricter measure than the default F1 score
D: Set `metricName="weightedPrecision"`, because precision averaged over all five classes guarantees that no single class is ignored by the model
K: B
G: ## What the default metric hides
`MulticlassClassificationEvaluator` defaults to `metricName="f1"`, an average of per-class F1 values weighted by how many rows each class has. A class with 1% of the rows contributes about 1% of the score, so a model can miss most structural-damage claims and still score well.
## Per-label metrics
The evaluator also offers `precisionByLabel`, `recallByLabel`, `fMeasureByLabel`, `truePositiveRateByLabel` and `falsePositiveRateByLabel`. They are computed for the single class named by `metricLabel` (a double equal to the indexed label value, default 0.0). When missing a class is the costly error, recall for that class is the metric to track and to use as the tuning metric.
W: Per-label recall answers the business question directly: of all real structural-damage claims, how many did the model flag. It is not diluted by the 99% of other rows and can also drive `CrossValidator` selection.
X: A=metricLabel with f1: `metricLabel` is read only by the `...ByLabel` metrics; with the default `f1` it is ignored, so the score stays the all-class weighted average and still hides type 3.
C=Accuracy: accuracy is dominated by the majority classes and is no stricter than weighted F1 for a 1% class; a model that never predicts type 3 loses only about one point.
D=Weighted precision: the weights are the class frequencies, so the average is again dominated by common classes, and precision says nothing about missed claims (recall).
T: For a rare but costly class, evaluate a per-label metric with `metricLabel` instead of a frequency-weighted average.

@ DBX-MLP D1 T1.5 applied comparison
S: A retailer scores a Spark ML `ALS` model on a held-out table. For each user, `recs` holds the top 10 recommended item ids as an array and `actual` holds the items the user really bought, also as an array. Product owners care whether purchased items appear near the top of the list. Which evaluation fits this?
A: `RegressionEvaluator(metricName="rmse")` on the predicted rating of each user-item pair, because a lower rating error produces a better ordering
B: `BinaryClassificationEvaluator` on a purchased/not-purchased label, because ALS predictions are probabilities that can be thresholded like those of a classifier
C: `MulticlassClassificationEvaluator(metricName="accuracy")` on the first recommended item, because only the top item is shown to the user
D: `RankingEvaluator(metricName="ndcgAtK", k=10)` with the recommendation array as prediction column and the purchases array as label column
K: D
G: ## Rating error is not ranking quality
RMSE measures how close predicted ratings are to observed ratings. A recommender is used as a ranked list, and two models with the same RMSE can order the items very differently. Ranking metrics compare the ordered list of recommended items with the items the user actually interacted with.
## RankingEvaluator
`pyspark.ml.evaluation.RankingEvaluator` expects an array of recommended items in `predictionCol` and an array of relevant items in `labelCol`. Its metrics are `meanAveragePrecision` (the default), `meanAveragePrecisionAtK`, `precisionAtK`, `ndcgAtK` and `recallAtK`, with the cutoff set by `k` (default 10). NDCG rewards putting relevant items higher in the list.
W: `ndcgAtK` with `k=10` scores exactly the delivered artifact, the top-10 list, and gives more credit when purchased items rank high, which is the stated product requirement.
X: A=RMSE: it grades predicted rating values over many pairs, including items never shown, and a better RMSE does not guarantee a better top-10 order.
B=BinaryClassificationEvaluator: ALS outputs a predicted score, not a calibrated purchase probability, and the evaluator measures a ranking over all pairs with area under a curve rather than the ordered top-10 list per user.
C=Accuracy on the first item: it looks at one position only and compares to a single class label, ignoring whether purchases appear in positions two to ten.
T: Evaluate recommenders with ranking metrics such as NDCG at K, using `RankingEvaluator` on recommended and actual item arrays.

@ DBX-MLP D1 T1.5 applied troubleshooting
S: A data scientist trains a Spark ML `LogisticRegression` on the 80% training split and prints `lr_model.summary.areaUnderROC`. The value is 0.99 and goes into the model card. After release the production AUC is about 0.82. What is wrong with the reported number, and what should be reported instead?
A: `summary` describes the training set, so evaluate on the held-out split with `lr_model.evaluate(test_df)` or a `BinaryClassificationEvaluator` on `transform(test_df)`
B: `summary.areaUnderROC` is computed with a different formula than the evaluator, so the value is inflated and must be rescaled by the class ratio before reporting
C: The metric is calculated on a 1% sample of the training data for speed, so `summary` must be recomputed with a larger sample size before the value is reliable
D: The summary reports the area under the precision-recall curve, so the team should read `summary.roc` and integrate it by hand to get the value
K: A
G: ## Training summary versus held-out evaluation
`LogisticRegressionModel.summary` returns a `LogisticRegressionTrainingSummary`: predictions and metrics such as `areaUnderROC` computed on the data the model was fitted on. A model that overfits scores well on its own training rows, so the number is optimistic by construction.
## How to get an honest number
- `lr_model.evaluate(test_df)` returns a `LogisticRegressionSummary` computed on the new DataFrame.
- Or call `lr_model.transform(test_df)` and pass the result to `BinaryClassificationEvaluator(metricName="areaUnderROC")`.
The test split must not be used for tuning; keep it for the final report.
W: The 0.99 is a training-set metric, which explains the drop to 0.82 on unseen data. Evaluating on the held-out split, with `evaluate` or the evaluator, gives an estimate of production behavior.
X: B=Different formula: the area under the ROC curve is the same quantity in both places; the difference comes from the data it is computed on, not from the formula, and no class-ratio rescaling exists.
C=1% sample: the summary uses all training rows, not a sample; making it larger would change nothing about the optimism.
D=Precision-recall confusion: the attribute named `areaUnderROC` is the ROC area, and integrating `summary.roc` by hand would still be on training data.
T: A model's training summary is computed on training data; report metrics from a held-out set via `evaluate` or an evaluator.

@ DBX-MLP D1 T1.5 advanced troubleshooting
S: A pipeline imputes missing values with an `Imputer`, scales with `StandardScaler`, and then fits a `GradientBoostedTrees` model. The team fits the `Imputer` and scaler on the full dataset, then runs `CrossValidator` over the tree parameters on the transformed data. Cross-validated AUC is 0.91, but the held-out AUC is 0.87. Which change gives trustworthy cross-validation scores?
A: Increase `numFolds` from 3 to 10, because more folds reduce the optimism that comes from fitting the preprocessing steps once
B: Replace `CrossValidator` with `TrainValidationSplit`, because one split cannot leak statistics from the validation rows into the training rows
C: Put the `Imputer`, scaler and model into one `Pipeline` and pass it as the estimator, so every fold refits the preprocessing on its own training rows
D: Cache the transformed DataFrame before `CrossValidator.fit`, because recomputing the stages in each fold changes the data between folds
K: C
G: ## Preprocessing leakage inside cross-validation
An `Imputer` learns medians and a `StandardScaler` learns means and standard deviations. If they are fitted on all rows first, every validation fold has already influenced those statistics, so fold scores are slightly too good and the gap shows up on a truly held-out set.
## The Spark ML fix
`CrossValidator` accepts any `Estimator`, including a `Pipeline`. When the whole pipeline is the estimator, each fold fits all stages on that fold's training rows only and applies them to the validation rows. The parameter grid can address stages of the pipeline (for example the tree depth of the last stage).
W: A pipeline estimator makes each fold learn the imputation and scaling statistics from its own training rows only, so the validation rows stay unseen and the fold metrics become honest.
X: A=More folds: ten folds still use preprocessing statistics learned from all rows, so each fold remains contaminated, and the run only becomes slower.
B=TrainValidationSplit: it evaluates one split, but with the same pre-fitted preprocessing the validation rows already shaped the statistics, so the leakage remains.
D=Caching: caching only avoids recomputation of the same data; it does not change which rows the preprocessing statistics came from.
T: Pass the full `Pipeline`, preprocessing included, to `CrossValidator` so each fold refits every stage on its training rows only.

@ DBX-MLP D1 T1.5 advanced use-case
S: A fraud model is a Spark ML `LogisticRegression` on 0.5% positive rows. Analysts need a decision threshold so that at least 90% of the flagged transactions are fraud. The data scientist proposes using the threshold that maximizes `lr_model.summary.fMeasureByThreshold`. What is the best approach?
A: Use the proposed threshold, because the maximum F-measure operating point always meets any precision target that is below the model's recall
B: Raise `maxIter` and tune `regParam` until the model's accuracy on the training data is above 99%, then keep the default 0.5 threshold for scoring
C: Score a validation split, find the smallest probability cut-off with precision of at least 90%, set it with `setThreshold`, and confirm on the test split
D: Choose the ROC curve point nearest the top-left corner of the plot, since that point balances the true-positive and false-positive rates for the model
K: C
G: ## A threshold is a business decision
Spark ML's binary classifiers output a probability column, and `threshold` (default 0.5) turns it into a 0/1 prediction. Metrics such as area under ROC or PR are threshold-free: they rate the ranking, and do not choose the operating point.
## Choosing it correctly
- Use data the model was not trained on: a validation split for choosing, a test split for confirming.
- Compute precision (and recall) at candidate cut-offs from the probability column, then pick the cut-off that meets the stated constraint, here precision at least 90%.
- Set it with `setThreshold` on the model or in the fitted model's params.
With 0.5% positives, 0.5 is rarely a sensible cut-off, and the training summary's curves describe training rows.
W: The requirement is a precision floor, so the cut-off must be derived from precision measured on unseen data, then verified on the test split. This also keeps the choice independent of the training-set optimism.
X: A=Maximum F-measure: F1 balances precision and recall and its best threshold may sit at precision well below 90%; it is also read from training data.
B=Accuracy and default threshold: with 0.5% positives a model predicting nothing is 99.5% accurate, and the 0.5 cut-off says nothing about precision among flagged rows.
D=Top-left ROC point: the ROC point nearest the corner balances true-positive and false-positive rates, which on rare positives can still yield low precision, and it does not target the stated 90%.
T: Pick an operating threshold for a stated precision or recall target on a validation split, then confirm it on a test split.

@ DBX-MLP D1 T1.5 applied use-case
S: A model scored 400 million rows in a Delta table, which now has `label` and `prediction` columns. The team needs the full confusion matrix across 12 classes for a review. A colleague suggests `predictions.toPandas()` and scikit-learn's `confusion_matrix`. What is the better approach?
A: Aggregate on the cluster with `predictions.groupBy("label", "prediction").count()` and collect only the small result of at most 144 rows
B: Take `predictions.limit(1000000).toPandas()` and use scikit-learn, because a million rows always preserve the rare cells of the matrix
C: Use `MulticlassClassificationEvaluator(metricName="accuracy")` once per class pair, as the evaluator returns the cell counts of a matrix
D: Convert the DataFrame to an RDD and call `collect()`, because RDD collection avoids the memory limit of the driver that `toPandas()` has
K: A
G: ## Keep evaluation distributed
A confusion matrix is a count of rows for each (label, prediction) pair. For 12 classes that is at most 144 numbers, however many rows were scored. A `groupBy().count()` computes these on the workers, and only the tiny result goes to the driver, where it can be pivoted or plotted.
## What to avoid
- `toPandas()` and `collect()` bring all rows to the driver; at 400 million rows this fails or is very slow.
- `limit()` followed by `toPandas()` yields an arbitrary subset, not a uniform sample, so rare cells are lost or biased.
- Spark ML evaluators return scalar metrics, not matrices.
W: The aggregation reduces 400 million rows to at most 144 counts on the cluster, exact and cheap, and can then be pivoted into a matrix.
X: B=Limit then toPandas: `limit` is not random, a million rows can be one partition, and rare off-diagonal cells may have zero counts, which defeats the review.
C=Accuracy per pair: the evaluator returns a single scalar metric per call, never cell counts, and accuracy for a pair is not defined.
D=RDD collect: the same data would still land in driver memory; the RDD API changes nothing about where the rows end up.
T: Compute confusion matrices and other count-based evaluations with a distributed aggregation, not by collecting predictions to the driver.

@ DBX-MLP D1 T1.6 applied troubleshooting
S: A streaming job reads events with `spark.readStream` and tries to run `Pipeline([StringIndexer(...), VectorAssembler(...), LogisticRegression()]).fit(stream_df)` to build a model that will score the same events continuously. The query fails with an analysis error about queries with streaming sources. How should the design change?
A: Convert `fit` into a `foreachBatch` function that refits the whole pipeline on each micro-batch and writes only the final prediction column
B: Add a watermark to the stream and call `fit` again, because the error is raised only when no event-time column exists
C: Run `fit` with `trigger(continuous="1 second")` so the estimator receives rows incrementally and keeps its state between triggers
D: Fit the pipeline on a static training table once, save the `PipelineModel`, and call its `transform` on the streaming DataFrame
K: D
G: ## Estimators need static data, transformers can stream
`fit` is an action: it runs several passes over the data, for example one to learn the label index and more for solver iterations. A streaming DataFrame has no end and can only be executed through `writeStream`. Spark therefore rejects `fit` on a streaming source.
A fitted `PipelineModel`, in contrast, is made of row-wise transformers that Spark can apply to a streaming DataFrame with `transform`, then write with `writeStream` and a checkpoint.
## Pattern
1. Train on a static table (a Delta snapshot) in a scheduled job and register the model.
2. In the streaming job, load the model once and call `model.transform(stream_df)`.
W: Training happens offline on static data and the resulting `PipelineModel` is applied to the stream, which is the supported split between `fit` and `transform`.
X: A=foreachBatch refit: each micro-batch would train a model on a few rows only, with different category indices and coefficients in every batch, so predictions would not be consistent.
B=Watermark: a watermark manages state for event-time aggregations; it does not make multi-pass `fit` executable on an unbounded source.
C=Continuous trigger: continuous processing does not turn estimators into online learners, and Spark ML solvers keep no incremental state between triggers.
T: Fit a Spark ML pipeline on static data, then apply the `PipelineModel` to a stream with `transform`.

@ DBX-MLP D1 T1.6 advanced tradeoff
S: Click events arrive as a stream and must be enriched with a customer feature table of 20 million rows (updated nightly in Delta) before a fitted `PipelineModel` scores them. The scoring query should keep no state and need no watermark. Which design fits?
A: Join the stream to another stream that reads the feature table with `readStream`, using a watermark on both sides to bound the state
B: Join the streaming DataFrame to the static feature DataFrame on the customer key, then call `model.transform` on the joined result
C: Collect the feature table to the driver every micro-batch and attach the values to each event in a Python loop before scoring
D: Run `model.transform` on the raw stream and look up features afterward in a separate batch job that joins the prediction table
K: B
G: ## Stream-static joins
Structured Streaming supports joining a streaming DataFrame with a static one. The join runs incrementally for each micro-batch against the static side and, as the Spark guide notes, stream-static joins are not stateful, so no state management or watermark is required.
## Stream-stream joins cost more
A stream-stream join must buffer rows from both sides until a match can arrive. That needs a watermark and keeps state on the executors. It is justified only when both sides are really changing event streams.
## Scoring consequence
Features must exist before the model runs, because a `PipelineModel` expects its input columns. Joining first, then calling `transform`, produces predictions in one query.
W: A stream-static join adds the 20-million-row Delta table as a lookup per micro-batch without state, and the joined rows go straight into `transform`.
X: A=Stream-stream join: it needs state and a watermark for a table that is not an event stream, which adds cost and risk when late data must be dropped.
C=Driver loop: collecting 20 million rows per micro-batch and joining in Python on the driver does not scale and discards Spark's join machinery.
D=Late lookup: the model needs the features as input columns to produce a prediction, so scoring before the join cannot work, and a second batch job adds delay.
T: Enrich streams with a stream-static join, which is stateless, and score the joined stream with the fitted pipeline.

@ DBX-MLP D1 T1.6 applied use-case
S: A nightly batch job scores one day of orders with a Spark ML `PipelineModel` and appends the result to the table `ml.scores`. When the job is retried after a late failure, the day's scores appear twice. The table has a `score_date` column. Which write pattern makes reruns safe?
A: Write with `mode("overwrite")` and `option("replaceWhere", f"score_date = '{d}'")`, so a rerun replaces only that day's rows
B: Keep `mode("append")` and add a nightly `DISTINCT` job that removes duplicate rows from the whole `ml.scores` table
C: Use `mode("overwrite")` without any option, since overwrite is the only write mode that Delta tables support for batch output
D: Run `model.transform` twice and compare the outputs, writing only when the two runs produce different rows
K: A
G: ## Idempotent batch scoring
A scoring job should produce the same table state however often it is retried. Appending is not idempotent: a retry after a partial success duplicates rows.
## Selective overwrite on Delta
With Delta Lake, `mode("overwrite")` together with `option("replaceWhere", "<predicate>")` atomically replaces only the rows matching the predicate (and checks that written rows match it). A rerun for `score_date = '2026-11-07'` replaces that day and leaves history intact. `MERGE` on a key is the alternative when rows are updated rather than replaced by partition.
W: `replaceWhere` makes the day's write replace the day's data, so the first run, the retry and any later rerun end in the same state.
X: B=Nightly DISTINCT: it rewrites a growing table every night, hides duplicates instead of preventing them, and would also collapse legitimate repeated rows.
C=Plain overwrite: it would delete all earlier days, losing history, and Delta supports append, selective overwrite and merge too.
D=Compare two runs: scoring twice doubles cost and does not address the rows that were already written during the failed attempt.
T: Make scoring writes idempotent with `replaceWhere` (or `MERGE`) so retries replace rather than duplicate.

@ DBX-MLP D1 T1.6 advanced troubleshooting
S: A long-running streaming job scores with a model loaded once at start-up (`mlflow.spark.load_model("models:/main.ml.churn@champion")`). The team promotes a new version by moving the `champion` alias, yet the stream still produces the old model's predictions for days. Which explanation and fix are correct?

`load_model` with an alias URI resolves the alias to a concrete version at the moment of the call, downloads that version's artifacts, and returns an in-memory object. A streaming query whose `transform` uses that object keeps using it until the query is restarted, whatever happens to the alias later.
## Options to adopt a new version
- Restart the streaming query (for example from a scheduled job or after the promotion step) so the start-up code resolves the alias again. The checkpoint lets the query continue without reprocessing.

B=Version pin only: aliases resolve fine in any job; the problem is the single resolution at start, and pinning a version would just make promotion a code change.
D=Cluster lifetime: executors receive the transformed work from the driver's model object; recreating the cluster is unneeded, a query restart on the same cluster reloads it.
T: A model loaded by alias is fixed for the life of the query; restart the stream or load the model per micro-batch to adopt a new version.

A: Nightly: `toPandas()` on the table and `predict` on the driver in chunks; checkout: the same driver notebook, called by the web service for each request
B: Nightly: `mlflow.pyfunc.spark_udf` applied with `withColumn` so workers score partitions; checkout: a Model Serving endpoint on the same registered model
C: Nightly: a Model Serving endpoint called once per row from a Python loop; checkout: a Spark job on an all-purpose cluster started for each request
D: Nightly: retrain the model as a Spark ML pipeline and call `transform`; checkout: a Structured Streaming query whose output table the service polls
K: B
G: ## One model, two execution modes
Batch and real-time inference have opposite needs. Nightly scoring wants throughput over billions of rows and tolerates start-up time. A checkout call wants low latency for one row and tolerates no cluster scheduling. A single-node model can serve both without retraining because the registered MLflow model is the shared contract.
## Batch side
`mlflow.pyfunc.spark_udf(spark, model_uri)` wraps a logged model as a Spark UDF. Each executor loads the model and scores its partitions, so scoring scales with the number of workers and the result is written to Delta without collecting it.
## Real-time side
A model logged in MLflow format (a built-in flavor such as scikit-learn, or pyfunc) and registered in Unity Catalog can be deployed to a Model Serving endpoint, a managed REST service that is queried with the request features.
W: Distributed UDF scoring handles the 2 billion rows without moving them to one machine, and a Model Serving endpoint answers single requests over REST, both from the same registered model and with no retraining.
X: A=Driver loop and notebook: all rows pass through one machine in chunks, so the nightly run is serial, and a notebook is not a low-latency request service.
C=Per-row endpoint and per-request job: two billion REST calls from a loop are far slower and costlier than partition-parallel scoring, and a Spark job per checkout request cannot meet 50 ms.
D=Spark ML retraining and polling: retraining changes the model and may lower accuracy, and a stream written to a table that is polled adds delay far above 50 ms.
T: Score a single-node model in batch with `spark_udf` and in real time from a Model Serving endpoint, both on the registered model.
V: MLflow, Model Serving, Unity Catalog

A: Increase the cluster to 48 workers, because UDF scoring time falls in proportion to the number of executors for any data size
B: Convert the sklearn model to Spark ML to remove the Python worker overhead, since JVM scoring is faster for 15,000 rows

Spark parallelism pays when data or computation is large. Starting executors, shipping the model to them and running tasks has overhead that does not shrink for small inputs. With 15,000 rows and a few megabytes of features, the scoring itself takes seconds on one machine.
## Right-size the design
- Small, regular batches: single-node cluster, `mlflow.pyfunc.load_model`, `toPandas()` (or a read with pandas) and `predict`, then write the result back.
- Large tables or heavy models: `spark_udf` on a multi-worker cluster.

W: At this size a single node loads the model once and scores quickly, with no cluster start-up for many workers; the logged model and its signature are reused unchanged.

B=Convert to Spark ML: it changes the model for no real gain at this volume, and the time was start-up, not Python overhead.
D=Streaming: a stream adds checkpointing and trigger management and is not a cheaper way to score a table that changes once a day.
T: For small scoring batches use a single node with a loaded pyfunc model; use `spark_udf` only when volume warrants distribution.

@ DBX-MLP D1 T1.7 applied troubleshooting
S: A 1.5 GB Keras image model is stored as a file in a Unity Catalog volume and is not logged to MLflow. A Series-to-Series `pandas_udf` loads the file inside its body to score 800 million rows. Tasks spend most of their time reloading the model and run out of memory on large inputs. Which Spark helper is built for this pattern?
A: `pyspark.ml.functions.predict_batch_udf` with a `make_predict_fn` that loads the model once per Python worker and a `batch_size` that the hardware can hold
B: Lower `spark.sql.execution.arrow.maxRecordsPerBatch` to one, so each call to the function holds the model for fewer rows and memory pressure falls
C: Replace the pandas UDF with a plain Python `udf`, because a row-at-a-time function keeps imported objects cached across all rows of a task
D: Call `df.coalesce(1)` before the UDF, so that the model file is read just a single time and shared with every task in the whole job
K: A
G: ## Where the model gets loaded
A Series-to-Series pandas UDF is called once for every Arrow batch of a partition (10,000 rows by default). Anything in its body, including a model load, runs again on each call, so a 1.5 GB file is read many times per task.
## predict_batch_udf
`pyspark.ml.functions.predict_batch_udf(make_predict_fn, return_type=..., batch_size=...)` returns a pandas UDF wrapper for inference. Its `make_predict_fn` loads the model and returns a predict function that Spark caches, so loading happens once per Python worker. The wrapper converts input columns to numpy arrays and calls predict on batches of `batch_size` rows, a limit set by the model and the hardware rather than by the partition size.
## Alternatives
An Iterator of Series pandas UDF also loads state once. `mlflow.pyfunc.spark_udf` fits models that are logged to MLflow, which this one is not.
W: `predict_batch_udf` loads the model once per Python worker, caches its predict function and feeds it fixed-size numpy batches, which removes the repeated loads and bounds memory while scoring stays parallel.
X: B=Batch size of one: the function would then run for every row and reload the model each time, which makes the problem far worse.
C=Plain Python UDF: it is row-at-a-time with serialization cost per row, and it offers no hook that keeps a loaded model between calls.
D=coalesce(1): one task removes all parallelism, and a scalar pandas UDF in that single task would still reload the model for every batch.
T: Use `predict_batch_udf` so a large model is loaded once per worker and applied in fixed-size batches.
V: Spark ML, pandas UDFs

@ DBX-MLP D1 T1.7 applied troubleshooting
S: A streaming job scores purchases with a scikit-learn model. The sink function is `foreachBatch(lambda b, i: write(model.predict(b.toPandas())))`, and micro-batches can hold 40 million rows after outages. The driver runs out of memory on large batches. Which redesign keeps the single-node model?
A: Call `b.repartition(1)` before `toPandas()` in the sink function, since a single partition is converted to pandas with less memory than several
B: Increase `spark.driver.maxResultSize` above the size of the largest micro-batch, because that limit is the only cause of the failure
C: Set the micro-batch trigger interval to one second so that each batch stays small, accepting that lag can grow during long outages
D: Score in the query with `mlflow.pyfunc.spark_udf` or an iterator pandas UDF in `withColumn`, so workers score the partitions and the driver collects nothing
K: D
G: ## Scoring should not pass through the driver
`toPandas()` collects the micro-batch to the driver. The single-node model then runs there, serially, so memory and time grow with the batch, and the cluster's workers sit idle. Batch size in a stream is not fixed: after a backlog it can be orders of magnitude larger than usual.
## Keep the model, change the execution
`spark_udf` or an iterator pandas UDF is applied in `transform`-style code: `scored = df.withColumn("score", udf(...))`. Each executor scores its partitions in parallel, and the stream writes the result with the usual sink. Rate limiting options such as `maxFilesPerTrigger` or `maxOffsetsPerTrigger` can also bound batch size, but they do not solve the serial driver scoring.
W: Distributed UDF scoring keeps the same sklearn model but moves the work to executors, so micro-batch size no longer decides driver memory.
X: A=repartition(1): it concentrates all rows into a single partition and still collects everything to the driver; it does not reduce memory.
B=maxResultSize: raising the limit allows larger transfers but the driver still needs memory for the data, and scoring remains serial.
C=One-second trigger: a trigger interval does not cap batch size; after an outage the next batch still contains the entire backlog.
T: Score single-node models in a stream with a UDF on the workers, never by collecting each micro-batch to the driver.
V: MLflow, Structured Streaming

@ DBX-MLP D1 T1.8 advanced tradeoff
S: A team has 600 million labeled rows and a scikit-learn random forest that they like. It cannot fit in one node's memory. A developer proposes `df.repartition(40).rdd.mapPartitions` / `mapInPandas` to fit one forest per partition, and then average the 40 forests' predictions. What is the accurate assessment?
A: It is a valid scale-out ensemble over data shards, but each forest sees only 1/40 of the rows, so validate its accuracy against a Spark ML forest
B: It is invalid, because `mapInPandas` cannot return a trained model object, so no pandas function API can be used for training in Spark
C: It is identical to training one forest on all rows, because averaging the shard-level forests reproduces the global split decisions exactly
D: It works only when rows are sorted by label, so each partition holds one class and its forest becomes a specialist for that class
K: A
G: ## Training with pandas function APIs
`mapInPandas` (and `applyInPandas`) run arbitrary Python on each partition or group, so single-node libraries can be used in parallel. For training, each task fits a model on its slice of data. The tasks return what the schema allows (metrics, serialized bytes, a path), and a driver-side step combines them.
## What the result is
Fitting one model per shard and averaging is a form of bagging or ensembling by data partitioning. It scales memory, but each model sees a fraction of the rows. X: B=Cannot return a model: the function must return a DataFrame matching the schema, but it can return the model serialized as bytes, or write it to a Unity Catalog volume and return the path.
C=Identical result: averaging forests trained on disjoint shards is a different estimator, since tree splits are chosen from the shard, not from all rows.
D=Sorted by label: a label-sorted partition contains one class and cannot learn to discriminate; partitions should be random.
T: Per-partition training with pandas function APIs is shard-level ensembling: scalable, but validate it against a global distributed learner.

@ DBX-MLP D1 T1.8 advanced use-case
S: A product team trains 40 independent Spark ML `LogisticRegression` models, one per target label, from the same 500-million-row feature DataFrame. A loop that calls `fit` one label after another keeps the cluster at low utilization because each fit has short stages with idle slots. What should the engineer do?
A: Convert the loop to `applyInPandas` and run each Spark ML fit inside the pandas function on the executors
B: Use a Python `for` loop but call `time.sleep` between fits, so Spark has time to release cluster slots
C: Cache the shared features, then submit the fits from several driver threads, because Spark runs jobs from separate threads concurrently
D: Merge the 40 targets into one multiclass label column, since one multiclass model always matches 40 independent binary models
K: C
G: ## Concurrent jobs in one application
The Spark job scheduling guide states that inside a Spark application multiple parallel jobs can run simultaneously if they were submitted from separate threads. A `fit` is a set of jobs. When one model's stages do not fill the cluster, running several fits at once uses the idle slots.
## Practical steps
- Persist the shared feature DataFrame so each thread reads memory, not recomputation.
- Use a thread pool of modest size and give each thread its own estimator with its own label column.
- Remember that `CrossValidator` has a similar `parallelism` setting for models inside a tuning run.
## Why not other forms
Spark ML estimators need the SparkSession and cannot be run inside executor-side pandas functions.
W: Several driver threads submitting independent fits keep more tasks in flight, using idle capacity, while the cache avoids rereading the shared features 40 times.
X: A=Spark ML inside a pandas function: executors have no SparkSession for distributed jobs, so a Spark ML `fit` cannot run within `applyInPandas`.
B=sleep: waiting does nothing for utilization; slots are released when tasks end, and the fits would still be serial.
D=Single multiclass model: 40 independent targets (possibly several true at once) are not one multiclass label; the model type and the predictions would change.
T: Fit many independent Spark ML models by submitting fits from multiple driver threads on a cached DataFrame.
V: Spark ML
