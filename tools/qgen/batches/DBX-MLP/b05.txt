@ DBX-MLP D1 T1.18 advanced troubleshooting
S: A churn model trains on `ml.crm.customer_features`, a table with one row per `customer_id` that a nightly job overwrites in place. Labels span the last 12 months and carry `churn_event_ts`. Offline AUC is 0.97, but the endpoint reaches only 0.71. What is the right repair?
A: Add `lookback_window=timedelta(days=7)` to the existing `FeatureLookup` so that feature values older than a week are excluded from the joined training set
B: Keep every nightly row in a time series feature table keyed `(customer_id, ts TIMESERIES)` and pass `timestamp_lookup_key="churn_event_ts"` in the `FeatureLookup`
C: Repartition the label DataFrame by `customer_id` before `create_training_set` so each label is joined to the feature row computed on its own executor
D: Raise the number of cross-validation folds and stratify by the churn label so that the rows whose features leak the outcome are spread evenly across folds
K: B
G: ## Why the offline score is too good
A feature table that is overwritten nightly holds only the newest value per entity. Joining 12 months of labels to it gives every old label the feature values computed today, which can include behavior that happened after the churn event. The model learns from information it will never have at prediction time. This is data leakage, and it shows up as a large gap between offline and production quality.
## Point-in-time correctness
Databricks Feature Store solves this with time series feature tables: a Unity Catalog Delta table whose primary key includes one `DATE` or `TIMESTAMP` column declared `TIMESERIES` (or `timeseries_columns` in `FeatureEngineeringClient.create_table`). Every nightly row is kept. In `create_training_set`, a `FeatureLookup` on such a table names a `timestamp_lookup_key`, a column of the label DataFrame. The join is an AS OF join: for each label it returns the latest feature row at or before that timestamp, or `null` if none exists.
- This is unrelated to Delta Lake time travel; it is a feature-store join.
- The same metadata is packaged with the model, so `score_batch` repeats the logic at inference.
W: A time series feature table that keeps each nightly row, queried with `timestamp_lookup_key` set to the label's event time, returns for every label only the feature values known before the churn event, which removes the leakage.
X: A=lookback_window on the overwritten table: the window only drops values older than a limit from rows that already exist. The table still has just today's row per customer, so the future values stay in every training row.
C=Repartitioning labels: partitioning changes where the join runs, not which feature version a label receives. Results are identical, so the leakage and the gap remain.
D=More folds and stratification: cross-validation only re-splits data that already contains leaked features. Every fold sees the same leaked values, so offline scores stay inflated.
T: Leakage from overwriting features is fixed by keeping history in a time series feature table and joining with `timestamp_lookup_key`, never by tuning the split.

@ DBX-MLP D1 T1.18 advanced use-case
S: A fraud model was trained with `FeatureLookup(table_name="ml.risk.acct_features", feature_names=["spend_30d"], lookup_key="acct_id", timestamp_lookup_key="txn_ts", lookback_window=timedelta(days=7))`. In training, accounts with no feature row in the prior 7 days got `null`. In production, the endpoint returns 40-day-old `spend_30d` for dormant accounts and scores shift. What explains this and what should the team do?
A: The window is enforced online once the online table is republished in `SNAPSHOT` mode, so schedule a nightly snapshot publish to apply the limit
B: The endpoint enforces the window when a request carries a `txn_ts` field, so add the transaction time to each scoring request
C: The online store retains every historical row, so add the current date to the lookup key and make the application pass today's date with each request
D: The window applies to training and batch scoring only; online lookups always return the latest value, so the team must flag stale values itself, e.g. with a last-updated feature
K: D
G: ## What lookback_window does
`lookback_window` is a `datetime.timedelta` on a `FeatureLookup` of a time series feature table. During `create_training_set` and `score_batch` it excludes feature values older than the window from the as-of join, so a very old value becomes `null` instead of being treated as current. The default is `None`: every value counts regardless of age.
## Where it does not apply
The documentation states that during online inference the latest feature value is always used, regardless of the lookback window. An online store keeps the latest value per entity (published time series tables are deduplicated to the latest row), so no timestamp request can change what is returned.
That creates a training-serving skew whenever stale values are possible: training sees `null` after 7 days, serving sees the old number. Typical remedies are a feature that carries its age (a last-updated timestamp turned into "days since update" by an on-demand function), or a pipeline that writes an explicit default after the cut-off.
W: The seven-day window is not applied online, where the latest value is always returned. Aligning training and serving therefore needs an explicit staleness signal or default written by the pipeline, since the endpoint will not null old values.
X: A=Snapshot republish: the publish mode controls how rows are copied (full copy versus incremental), not what age is allowed. A snapshot of the same latest rows still contains the 40-day-old value.
B=Timestamp in the request: the online lookup is keyed on the entity, not on a time, so the extra field changes nothing about which stored value is returned.
C=Date in the key: that turns the table into an exact-match store with a changed schema and breaks the model's lookup metadata. It also does not recreate the window behavior used in training.
T: `lookback_window` works in training and batch scoring only; online inference returns the latest value, so staleness must be handled in the data.

@ DBX-MLP D1 T1.18 advanced troubleshooting
S: A time series feature table `ml.iot.room_features` has key `(room, ts TIMESERIES)` and features `temp`, `co2`, `light`. A temperature job writes rows with only `room`, `ts` and `temp`. Training sets now show `null` for `co2` on many rows although a valid `co2` row exists a few minutes earlier. What is the cause and the fix?
A: As-of lookup takes the latest row at or before the label time and keeps its nulls, so write complete rows with every feature per timestamp
B: As-of lookup skips null cells only when `lookback_window` is set, so set a one-day window on the `FeatureLookup` and the earlier `co2` value is selected again
C: `write_table` in merge mode cannot target a time series feature table, so switch the job to overwrite so that nulls are replaced with the last known readings
D: Features are joined per column, so list `co2` as a separate primary key column and the join then falls back to an earlier timestamp
K: A
G: ## One row, all features
In a time series feature table the as-of join selects one row per label: the latest row whose timestamp is not later than the label timestamp. The row is taken as a whole. The documentation states that point-in-time lookup does not skip rows with `null` feature values.
That is why writes to a time series table must supply values for all features of the table, unlike regular feature tables where partial `merge` updates are fine. If a job writes only `temp`, the new row has `co2 = null`, and a label that falls after it receives `null` for `co2` even though an earlier `co2` is stored.
## Practical pattern
- Compute all features in one pipeline per timestamp, or join the source readings first and forward-fill missing sensor values before `write_table`.
- Stream or batch writes are both supported, but each row must be complete.
W: Because the lookup treats a row as a unit and keeps null cells, partial rows mask earlier values. Writing complete rows (all features at each timestamp, with missing readings filled upstream) restores the expected values.
X: B=lookback_window skips nulls: the window only drops values older than a limit. It never skips a null in a newer row, so the earlier `co2` value stays hidden.
C=Overwrite instead of merge: merge works with time series tables, and overwrite would delete the history needed for training. It also would not fill any nulls.
D=Feature as a primary key: making measurements part of the key breaks the entity design and the model metadata. The join still takes a whole row by key and timestamp.
T: As-of joins return whole rows and keep nulls, so every write to a time series feature table must carry all features.

The nightly batch DataFrame has `cust_id` and `order_date` (a `DATE` column). What must the DataFrame passed to `fe.score_batch` contain?
A: Only `cust_id`, because `score_batch` uses the time of the scoring job as the as-of time for every row that it looks up
B: `cust_id` and any `DATE` or `TIMESTAMP` column, because `score_batch` finds the time column by type and casts it as needed

G: ## How batch scoring finds features
A model logged with `FeatureEngineeringClient.log_model` carries the `FeatureLookup` definitions it was trained with. `score_batch` replays them: it looks up each feature by the lookup keys in the incoming DataFrame and joins offline-store values before calling the model, so callers pass only keys (plus raw columns the model needs).
## Time series tables add one requirement
For a time series feature table, the lookup is a point-in-time one, so the incoming DataFrame must contain a timestamp column with the same name and data type as the `timestamp_lookup_key` used at training time. Here that is `order_ts`. The values define for which instant the latest feature values are fetched. A column with another name or type is not matched by position or type.
W: The DataFrame needs the lookup key and a timestamp column called `order_ts` of the same data type used during training, so the stored point-in-time lookup can run exactly as it did for the training set.
X: A=Only the key: batch scoring never substitutes the current time. A time series lookup needs a timestamp per row, and without it the lookup cannot run.
B=Any date or timestamp column: the column is matched by name, not discovered by type. A differently named column is not used, and a different type is not silently cast.
D=The table's `ts` column: that is the stored feature timestamp, and rows to score do not have one. The name that must match is the label-side `timestamp_lookup_key`.
T: `score_batch` needs a column named like the training `timestamp_lookup_key`, with the same type, to run point-in-time lookups.

@ DBX-MLP D1 T1.18 advanced tradeoff
S: A time series feature table with 8 billion rows is joined to 200 million labels through `create_training_set`. Training-set builds are slow. The table has primary key `(user_id, ts TIMESERIES)`. Which change best speeds up the point-in-time joins without changing results?
A: Partition the table by date and by `user_id` so that every as-of lookup scans a single small partition for its timestamp
B: Enable liquid clustering on the table, use a current `databricks-feature-engineering`, and pass `use_spark_native_join=True` on Photon-enabled compute
C: Add `hour` and `minute` columns to the primary key so that each lookup matches a narrower key before the timestamp comparison
D: Declare the table as a regular feature table keyed `(user_id, ts)` as strings so that lookups become exact matches that are simpler to execute
K: B
G: ## Why as-of joins are expensive
An AS OF join matches on the entity key and then finds the latest timestamp at or before each label timestamp. With billions of feature rows, file layout decides how much data is read per lookup.
## Documented guidance
- Databricks recommends liquid clustering on time series feature tables (client 0.6.0 and later) and data skipping for better point-in-time lookup performance.
- With Photon enabled, `use_spark_native_join=True` in `create_training_set` (and `score_batch`) uses a faster join; it needs `databricks-feature-engineering` 0.6.0 or above.
- A time series feature table must have one timestamp key and cannot have partition columns, and Databricks recommends at most two primary key columns for performant writes and lookups.
W: Liquid clustering lays out data for key and time ranges, and the native Spark join speeds the lookup itself. Both are documented for point-in-time joins and keep the result the same.
X: A=Partition columns: a time series feature table cannot have partition columns, and partitioning on a high-cardinality `user_id` would create far too many small partitions anyway.
C=Longer primary key: the guidance is at most two primary key columns, and each timestamp part makes the key wider while still needing the as-of comparison on top.
D=String keys with exact match: string keys give exact-match semantics, which would return nothing for labels between feature timestamps and so change the results.
T: Speed up point-in-time joins with liquid clustering and `use_spark_native_join`, not with partitions or a longer key.

@ DBX-MLP D1 T1.18 advanced comparison
S: A reviewer suggests dropping time series feature tables: "read the single-row feature table with `VERSION AS OF` at each label's date and union the results." Why is Delta time travel not a replacement for a point-in-time join in a feature store?
A: Time travel reads the whole table at one commit per query, while an as-of join picks the latest row per key for each label, and time travel depends on log retention
B: Time travel cannot read tables that have a primary key constraint, so feature tables are excluded from older-version reads and only plain tables qualify
C: Time travel returns data only for the 30 most recent commits, which is shorter than any labeling period, whereas as-of joins keep every historical row
D: Time travel and as-of joins are the same operation, so the union of versions gives identical results, only slower because every version is read separately
K: A
G: ## Two features with similar names
The docs note that point-in-time lookup is sometimes called "time travel" but is not related to Delta Lake time travel.
- **Delta time travel** queries a table as it was at a version or timestamp of its transaction log. One query sees one consistent snapshot, and reachable history depends on log retention and `VACUUM`.
- **Point-in-time (as-of) join** in Feature Store joins every label row to the latest feature row at or before that row's own timestamp, in one pass, using the timeseries key.
Reproducing 12 months of labels through time travel would need one query per snapshot, retained history for the whole period, and manual matching of labels to snapshots. The feature-store join also stores the metadata so that `score_batch` repeats the logic.
W: Time travel reads whole-table snapshots at chosen versions and depends on retention, while a time series feature table matches each label to its own latest earlier row in a single join, with the lookup recorded in the model.
X: B=Primary key blocks time travel: constraints do not prevent reading an older Delta version. The reason lies in the semantics, not in a restriction on constraints.
C=30 commits limit: there is no fixed commit count; history depends on retention settings. Unlimited history is also not a property of as-of joins.
D=They are the same: they are different operations with different outputs, and the claim of identical results is false whenever labels fall between two commits.
T: Delta time travel gives table snapshots; a time series feature table gives per-row as-of matching.

@ DBX-MLP D1 T1.19 advanced use-case
S: `ml.sales.store_stats` is an existing Delta table with no constraints, owned by the analyst. Its `store_id` and `snap_ts TIMESTAMP` columns are nullable and hold 14 months of hourly history. It must become a point-in-time feature table in place, without copying the data. Which sequence works?
A: Run `ALTER TABLE ... ADD CONSTRAINT store_stats_pk PRIMARY KEY (store_id, snap_ts TIMESERIES)` directly, because Unity Catalog sets key columns to NOT NULL while it adds the constraint
B: Create a new table with `CREATE TABLE AS SELECT` that declares the key and `TIMESERIES` in its DDL, because a primary key can only be declared when a table is first created
C: Add `PRIMARY KEY (store_id, snap_ts)` after setting both columns to NOT NULL, then pass `timeseries_columns="snap_ts"` in every `FeatureLookup` so that the lookups run as of the label time
D: Run `ALTER COLUMN ... SET NOT NULL` on both key columns, then `ADD CONSTRAINT ... PRIMARY KEY (store_id, snap_ts TIMESERIES)`, which makes it a time series feature table
K: D
G: ## Turning an existing Delta table into a feature table
Any Unity Catalog Delta table with a primary key constraint can serve as a feature table. A table without a key is converted in place with two kinds of statements, and only the table owner can declare the constraint.
- Key columns must be `NOT NULL`: run `ALTER TABLE <t> ALTER COLUMN <col> SET NOT NULL` for each key column first.
- Add the constraint: `ALTER TABLE <t> ADD CONSTRAINT <name> PRIMARY KEY (store_id, snap_ts TIMESERIES)`. The `TIMESERIES` keyword on one key column (Databricks Runtime 13.3 LTS or above) is what makes the table a time series feature table.
## Where the time designation lives
Point-in-time behavior is a property of the table key, not of the lookup. The `FeatureLookup` only names `timestamp_lookup_key`, a column of the label DataFrame. Once the constraint exists, the table appears in the Features UI and works with `create_training_set` and `score_batch`.
W: Setting the key columns to NOT NULL and then adding a primary key with `TIMESERIES` on the timestamp converts the existing table in place and keeps all its history.
X: A=Constraint only: the documented procedure sets each key column to NOT NULL first, and a key over nullable columns is not accepted, so the single statement does not work on this table.
B=Copy with CTAS: a constraint can be added to an existing table with `ALTER TABLE`, so copying 14 months of history is unnecessary and the stem asks for an in-place change.
C=Designation in the lookup: `timeseries_columns` belongs to table creation. A plain key without `TIMESERIES` gives no as-of join, and a `DATE` or `TIMESTAMP` key left undeclared is rejected by `create_training_set`.
T: Convert a Delta table in place with SET NOT NULL, then `PRIMARY KEY (..., ts TIMESERIES)`; the time designation sits in the key.

A `DATE` or `TIMESTAMP` primary key column that is not declared as a time series column cannot be used with `create_feature_spec()`, `create_training_set()` or `publish_table()`. These APIs require every such column to be declared as a timeseries column.

W: Declaring the date as the time series key gives the as-of join the label needs, and the existing history is kept.
X: B=STRING key: this is the documented route for plain exact-match lookups, so labels on dates without a snapshot receive nothing instead of the latest earlier one.

D=Newer client: the requirement is part of the API contract, so no release infers the designation. Only the table definition can declare it.

@ DBX-MLP D1 T1.19 applied use-case
S: A platform team wants to expose the view `ml.crm.v_cust_orders`, defined as `SELECT c.id, SUM(o.amt) spend FROM customers c JOIN orders o USING(id) GROUP BY c.id`, as a feature table. Registering it fails. What is the correct approach?
A: Add a `PRIMARY KEY (id)` constraint directly on the view, then reuse it in `create_training_set` with no change to its definition

G: ## Views as feature tables
A Unity Catalog view can act as a feature table only if it is a simple SELECT view: created from a single Delta table that itself can be a feature table, with primary keys selected without `JOIN`, `GROUP BY` or `DISTINCT`. An aggregate over several tables is a feature computation. Materialize it into a Delta table with a primary key, refresh it with `write_table(mode="merge")` in a scheduled job, and register that table. The result is also stable for training, point-in-time use and publishing to an online store.

T: Only simple SELECT views can be feature tables; materialize joins and aggregations into a keyed Delta table.

@ DBX-MLP D1 T1.19 advanced use-case
S: Training rows have `user_id`, `ad_id`, `session_start_ts` and `impression_ts`. User features (time series table) must be as of the session start; ad features (another time series table) as of the impression. How should the training set be built?
A: Create two training sets, one per feature table with its own timestamp, then union the outputs and drop the duplicate label rows
B: Choose one `timestamp_lookup_key` for the whole call and shift the other timestamp in the source data so that both tables agree
C: Define one `FeatureLookup` per table, each with its own `timestamp_lookup_key`, and pass both to a single `create_training_set` call
D: Put both timestamp columns into the primary key of each feature table and join on the composite key in the label DataFrame

G: ## Independent as-of lookups
Each `FeatureLookup` describes one join: the feature table, the features, the `lookup_key` columns of the label DataFrame, and for time series tables a `timestamp_lookup_key`. `create_training_set` accepts a list of lookups and performs each join independently on the same label DataFrame. Splitting the work into two calls and unioning produces mismatched column sets, not a join. W: Separate lookups with their own timestamp keys are evaluated independently in one call, so each feature table is joined as of the right moment and the model records both definitions.
X: A=Two training sets and a union: a union stacks rows rather than adding columns, so the features end up in separate rows, and the label rows could not be matched to both.
B=One shared timestamp: shifting data changes the business meaning of the timestamps and loses the true difference between session start and impression.
D=Timestamps in the primary key: the timeseries column is the only time key in each table, and putting several would stop as-of matching and break the recommended key design.
T: Give each `FeatureLookup` its own `timestamp_lookup_key` when tables need different as-of times.

G: ## Two ways to serve features
- **Model Serving** deploys a model trained on feature tables; the same endpoint looks up or computes features and returns predictions. Recommended when features are ultimately used for model inference.
- **Feature Serving** deploys a `FeatureSpec` directly, without a model; the endpoint returns the requested feature outputs. Use it when an application needs feature values.
A `FeatureSpec` is a Unity Catalog entity that combines `FeatureLookup`s and `FeatureFunction`s. The tables it references must be published to an online store (Databricks Online Feature Store or a third-party store). Both approaches support precomputed and on-demand features.

G: ## Overriding looked-up features
With a model logged by `fe.log_model`, Model Serving looks up every required feature from the online store automatically. To override a feature value when scoring through the REST API, include that feature in the API payload. The new value must conform to the data type the model expects for that feature.
## When to use it
Overrides suit what-if checks or a caller that knows a fresher value for this one call. If the value is always supplied by the request, an on-demand feature (a `FeatureFunction`) or a plain model input is the cleaner long-term design, but it is not required here.
W: Putting the value in the payload overrides the lookup for that request, with no change to the model, as long as the type matches.
X: A=Retrain first: retraining is not needed; the lookup override works for the current model.
C=Write and publish: this changes the stored value for all callers and adds sync latency, while the need is one request's fresher value.
D=Custom header: Model Serving does not map headers onto features; overrides are carried in the request payload.
T: Override a looked-up feature per request by sending it in the payload, with the expected data type.
