G: ## Why serving cannot read your volume
Real-time workloads at scale perform best when every dependency is captured statically at deployment. For that reason Model Serving requires files that live in Unity Catalog volumes to be packaged into the model artifact itself. The serving container does not mount your workspace file systems, and fetching files over the network at request time makes startup fragile.
## The pattern
`mlflow.pyfunc.log_model(..., artifacts={"name": "<path>"})` copies the files into the model. Inside the model class the copies are reachable at `context.artifacts["name"]`. Load them once in `load_context`, not in `predict`.
```
def load_context(self, context):
self.w = torch.load(context.artifacts["weights"])
```
W: Package the file as a model artifact: anything a pyfunc reads at inference must travel with the model, so passing the file through the `artifacts` argument copies it into the model and `load_context` reads the copy from `context.artifacts`.
X: A=DBFS path: serving containers do not share the cluster's file systems or mounts, so a path that works in a notebook does not exist there.
C=Instance profile: it gives the container credentials for AWS resources your code accesses itself, but a volume path is not mounted in the container. It would also be a runtime network dependency.
D=READ VOLUME grant: the problem is not a missing privilege. Serving requires volume artifacts to be packaged into the model, so a grant does not make the path exist in the container.
T: Files go into the model with artifacts= and are read from context.artifacts.
