@ DBX-MLP D2 T2.10 advanced comparison
S: A pricing model uses the predicted default probability directly in a formula (expected loss = probability x exposure). Retraining yields two candidates: model X has the higher AUC, model Y has the lower log loss and a reliability curve close to the diagonal. Which should the pipeline prefer, and why?
A: Model X, because AUC is threshold independent, which makes it the right selection metric for a probability used inside a formula
B: Model X, because a higher AUC means its probabilities sit closer to observed default rates, which log loss and the curve merely restate
C: Model Y, because a lower log loss shows that Y has fewer parameters, so it will overfit less on next month's applications
D: Model Y, because the formula needs probabilities matching observed frequencies, which log loss and calibration measure and AUC does not
K: D
G: ## Discrimination and calibration
- Discrimination (AUC, PR AUC): does the model rank positives above negatives? Invariant under any monotonic transformation of the scores.
- Calibration: does a predicted 0.2 correspond to about 20% observed? Measured with log loss, Brier score and reliability curves.
Two models can have identical AUC and very different calibration, because stretching the scores keeps the order. When the score is used as a probability in arithmetic (expected loss, expected value, a decision cost), calibration matters and log loss or the Brier score is the selection metric. A model with good ranking but poor calibration can often be repaired with a post-hoc calibration step (Platt scaling or isotonic regression) fitted on held-out data.
W: Calibrated probabilities: the formula multiplies the probability by the exposure, so the probabilities themselves must be right; log loss and a diagonal reliability curve show that, while AUC ignores it.
X: A=AUC as the selection metric: AUC ignores the scale of the scores, so it cannot say whether 0.2 means 20%; it is the right metric for ranking tasks, not for this formula.
B=Higher AUC means calibrated: it does not; any monotonic distortion of the scores leaves AUC unchanged and breaks calibration.
C=Log loss as a complexity measure: log loss is a measure of probability quality on the holdout and says nothing about the number of parameters; the argument is not valid.
T: Select on log loss and calibration when probabilities are consumed as numbers, and on AUC when only the ranking matters.

G: ## What a grouped-map function can hand back
The function runs in a Python worker process on an executor. Whatever it returns must be a `pandas.DataFrame` whose columns match the declared output schema (see the pandas function APIs page); Spark converts it to rows of a new DataFrame. Nothing else leaves the executor process.
- A column declared as `binary` carries `bytes`, so a pickled or serialized model fits in an ordinary DataFrame next to the key and metrics. Saving that DataFrame as a Delta table versions the models with the data and makes them readable by any later job.

@ DBX-MLP D1 T1.18 advanced use-case
S: A fraud model was trained with `FeatureLookup(table_name="ml.risk.acct_features", feature_names=["spend_30d"], lookup_key="acct_id", timestamp_lookup_key="txn_ts", lookback_window=timedelta(days=7))`. In training, accounts with no feature row in the prior 7 days got `null`. In production, the endpoint returns 40-day-old `spend_30d` for dormant accounts and scores shift. What explains this and what should the team do?
A: Online lookups ignore the window and return the latest value, so the team must flag stale values itself, e.g. with a last-updated feature
B: The online store retains every historical row, so add the current date to the lookup key and make the application pass today's date with each request
C: The endpoint enforces the window when a request carries a `txn_ts` field, so add the transaction time to each scoring request
D: The window is enforced online once the online table is republished in `SNAPSHOT` mode, so schedule a nightly snapshot publish to apply the limit
K: A
G: ## What lookback_window does
`lookback_window` is a `datetime.timedelta` on a `FeatureLookup` of a time series feature table. During `create_training_set` and `score_batch` it excludes feature values older than the window from the as-of join, so a very old value becomes `null` instead of being treated as current. The default is `None`: every value counts regardless of age.
## Where it does not apply
The documentation states that during online inference the latest feature value is always used, regardless of the lookback window. An online store keeps the latest value per entity (published time series tables are deduplicated to the latest row), so no timestamp request can change what is returned.
That creates a training-serving skew whenever stale values are possible: training sees `null` after 7 days, serving sees the old number. Typical remedies are a feature that carries its age (a last-updated timestamp turned into "days since update" by an on-demand function), or a pipeline that writes an explicit default after the cut-off.
W: Window not applied online: the seven-day window is not applied online, where the latest value is always returned. Aligning training and serving therefore needs an explicit staleness signal or default written by the pipeline, since the endpoint will not null old values.
X: B=Date in the key: that turns the table into an exact-match store with a changed schema and breaks the model's lookup metadata. It also does not recreate the window behavior used in training.
C=Timestamp in the request: the online lookup is keyed on the entity, not on a time, so the extra field changes nothing about which stored value is returned.
D=Snapshot republish: the publish mode controls how rows are copied (full copy versus incremental), not what age is allowed. A snapshot of the same latest rows still contains the 40-day-old value.
T: `lookback_window` works in training and batch scoring only; online inference returns the latest value, so staleness must be handled in the data.
