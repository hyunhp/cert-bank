@ DBX-MLP D2 T2.13 applied use-case
S: A governed table `ml.crm.customer_dim` is fully rewritten every night by a pipeline. It has no event timestamp that describes when a row happened, and it holds no model predictions. The team wants data quality metrics, such as null rates and distributions, tracked for each nightly state of the whole table. Which profile type fits?
A: A time series profile on the `updated_at` column, with a daily granularity, so that each nightly rewrite becomes a separate time window
B: A snapshot profile, which processes the complete table at every refresh and records the metrics for the state of the table at that time
C: An inference profile with the customer id as the model id column, so that every customer is profiled as a separate model
D: No profile at all, because profiles can be attached only to tables that grow by appending rows and never to rewritten tables
K: B
G: ## Three profile types
Data profiling (documented earlier as Lakehouse Monitoring, which the exam guide still calls it) attaches a profile to a Unity Catalog table and writes two Delta metric tables, the profile metrics table and the drift metrics table, plus a dashboard. The profile type decides how the table is cut into windows.
- Snapshot: for any table that does not fit the other two. The complete table is processed at every refresh and the window is a single point in time. The maximum table size is 4TB.
- Time series: the table has a timestamp column that says when each row happened; metrics are computed per time window at the chosen granularities.
- Inference: a request log with timestamp, model inputs, prediction, optional label and a model id column; adds model quality metrics.
## Why this matters
A rewritten dimension table has no meaningful event time, so time windows would describe `updated_at` values rather than the state of the table. Snapshot keeps one metric set per refresh, and the drift metrics table can compare refreshes.
W: Snapshot is the type for tables without a meaningful time axis or predictions: each refresh profiles the whole current table, so the nightly states can be compared.
X: A=Time series on updated_at: windows would group rows by modification time, not by nightly state, so the metrics would describe how old rows are rather than how the full table looks after each rewrite.
C=Inference profile: that type expects a request log with predictions and a model id column; a customer id is not a model, and no model quality metrics could be computed.
D=No profile: profiles work on managed or external Delta tables, views and materialized views, and rewritten tables are fine for a snapshot profile.
T: Use a snapshot profile when the whole table is the unit to profile at each refresh and there is no time axis or prediction log.
V: Unity Catalog, Data profiling

@ DBX-MLP D2 T2.13 advanced use-case
S: A serving endpoint logs requests and responses to an inference table. The request and response columns hold JSON strings with the feature values and the prediction, and true labels arrive later in a separate table. The team wants an inference profile with accuracy and F1 trends. What should the pipeline do before creating the profile?
A: Create the inference profile directly on the logged table and set the prediction column to the response JSON column, which the profile parses automatically
B: Create a time series profile on the logged table, because inference profiles accept only tables written by batch scoring jobs and never endpoint logs, and it would give the same metrics
C: Export the table to a CSV file in a volume every night, because profiles are able to read only files and cannot read Delta tables
D: Schedule a job that unpacks the JSON into one column per feature and prediction, joins the labels, and profile the resulting Delta table
K: D
G: ## What an inference profile expects
An inference profile reads a flat table in which each row is one request, with a timestamp, the model inputs as columns, a prediction column, an optional label column and a model id column. Model quality metrics need both `prediction_col` and `label_col`.
## Inference table payloads
An endpoint inference table stores the raw request and response payloads. The documented workflow is: enable inference tables, schedule a job that unpacks the JSON payloads according to the schema of the endpoint, optionally join the unpacked rows with ground-truth labels, and then create the monitor over the resulting Delta table and refresh it.
W: Unpacking the JSON into typed columns and joining the late labels produces the flat request log that the inference profile needs, so accuracy and F1 can be computed per window.
X: A=Response JSON as the prediction: the profile does not parse payloads; a string of JSON would be treated as a categorical value and no classification metrics could be computed.
B=Time series profile: endpoint logs are fine as a source once flattened, and a time series profile would give no model quality metrics at all.
C=CSV export: profiles read Delta tables in Unity Catalog directly; exporting to files adds a step and loses the table that the profile attaches to.
T: Flatten and label-join the payloads first; the inference profile attaches to the flat Delta table, not to the raw log.

S: A team creates a time series profile today on an events table that has two years of history, expecting two years of daily metrics. The first refresh finishes, but the dashboard shows only about the last month. No error is reported. What explains this?
A: When a time series or inference profile is created, only the data from the 30 days before its creation is analyzed; new data is processed after that
B: The daily granularity discards all windows older than the retention period of the metric tables, which is set to 30 days by default in the profile
C: The dashboard was created by a different user, and Unity Catalog row filters hide the older windows from everyone except the table owner

When a time series or inference profile is created, Databricks analyzes only the data of the 30 days before creation. After that, all new data is processed on each refresh. Because the 30-day cut-off can fall in the middle of a window, the first window may be partial.

If a long history is needed for trend comparison, do not expect the profile to backfill it. Plan for a baseline table that represents the earlier acceptable distribution, or contact the account team about the look-back period, which the documentation says is the way to adjust it.

X: B=Retention setting: the metric tables are ordinary Delta tables without a profile-level retention setting that deletes old windows; the limit applies to the initial analysis only.
C=Row filters: no row filter is applied by the profile, and the metric tables are governed by regular Unity Catalog grants; the short history is the same for all viewers.
D=Optimize-based skipping: profiles do not depend on optimization state; with change data feed enabled only appended data is processed, but the history cut-off is the 30-day look-back.
T: Time series and inference profiles look back 30 days at creation, then process all new data.

@ DBX-MLP D2 T2.13 advanced tradeoff
S: A 6TB append-only table of clickstream events, with an `event_ts` timestamp, must be profiled for null rates and distribution drift. A first attempt with a snapshot profile is rejected for size. Refresh cost must also stay low as the table grows. Which configuration meets both needs?
A: A snapshot profile with a slicing expression on `event_ts`, so that each slice is smaller than the maximum table size for snapshots
B: An inference profile, because it supports larger tables than snapshot and does not require predictions when the label column is omitted
C: A time series profile on `event_ts` with change data feed enabled on the table, so that each refresh processes only newly appended data
D: A snapshot profile on a deep clone refreshed monthly, which keeps the profiled table under the limit while the source continues to grow
K: C
G: ## Size limit and incremental processing
A snapshot profile processes the complete table on every refresh and is limited to 4TB; for larger tables, the documentation points to time series profiles. For time series and inference profiles, it is a best practice to enable change data feed (CDF) on the table: then only newly appended data is processed instead of re-processing the table at every refresh, which keeps cost under control across many tables. Profiles over materialized views do not support incremental processing.
## Applying it
An append-only event table with a timestamp is the textbook time series case: windows by event time, new rows only per refresh.
W: A time series profile has no 4TB snapshot limit, gives windowed metrics by `event_ts`, and CDF limits each refresh to the new appended rows.
X: A=Slicing on event_ts: slices are computed in addition to the whole table, so the full table still has to be processed and the snapshot size limit still applies.
B=Inference profile: it needs a prediction column and a model id and exists for request logs; it is not a way around a size limit for plain event data.
D=Clone and monthly snapshot: a stale clone profiles old data, still carries the full-table cost at each refresh, and breaks as soon as the clone itself exceeds 4TB.
T: Large append-only tables with a timestamp: time series profile plus change data feed.

@ DBX-MLP D2 T2.13 advanced use-case
S: A classifier was trained and evaluated on a validation set stored in `ml.churn.validation`. The team now builds an inference profile on the unpacked endpoint log and wants drift alerts that tell them when production inputs differ from what the model saw during development. Which baseline should they supply?
A: The first 30 days of the unpacked production log, because the baseline must be taken from the same table so that the schema matches exactly the primary one
B: A random sample of the latest production week, refreshed each night, so that the baseline always represents current traffic
C: The training pipeline's raw input files, joined with all columns of the source systems, to include as many fields as possible
D: The validation set, with the same feature columns and model id value as the primary table, so drift is measured against the evaluation data
K: D
G: ## Baseline tables
In addition to the primary table, a profile can use a baseline table: a reference with the same schema (except the timestamp column for time series and inference profiles). Drift is then computed relative to those expected values. For an inference profile, the documented good choice is the data used to train or validate the model, so users are alerted when data has drifted relative to what the model was trained and validated on. The baseline should contain the same feature columns as the primary table and the same `model_id_col` so that data are aggregated consistently. Ideally the test or validation set used to evaluate the model is used, which also makes the quality metrics comparable.
W: The validation set represents the distribution on which the model was evaluated, and with matching columns and model id the baseline drift metrics measure production against that reference.
X: A=First 30 days of production: this encodes whatever production looked like at the start, which may already differ from training data, and a baseline is a separate table, not a time slice of the primary table.
B=Latest production week: a baseline that moves with the traffic always looks like the current data, so baseline drift stays near zero and real shifts are hidden.
C=Raw source files: columns that do not match the primary table are only handled with best-effort heuristics, and the raw data is not what the model consumed after feature engineering.
T: For inference profiles, use the training or validation data, with matching feature and model id columns, as baseline.

@ DBX-MLP D2 T2.14 advanced troubleshooting
S: An inference profile is refreshing on schedule and the drift tables fill normally, but the accuracy, precision and recall columns are NULL for every window. The prediction column is configured. Which cause is most likely?
A: The model was registered in Unity Catalog instead of the workspace registry, which blocks the quality metrics of an inference profile
B: The profile is set to a daily granularity, and quality metrics are computed only for windows of one week or longer
C: No label column is configured, or the ground-truth labels were never joined to the logged predictions, so model quality cannot be calculated
D: The drift metrics are computed first and block the quality metrics until baseline drift has been calculated for each column

G: ## Model quality needs labels
For an inference profile, model quality is calculated only if both `label_col` and `prediction_col` are provided. The label is optional in the configuration, so a profile can be created without it and still produce data quality and drift metrics, while the accuracy, precision, recall and F1 (or the regression metrics) stay null.
## Fix
Join the ground truth to the unpacked request log (for example by a request identifier such as `client_request_id`), add the label column to the profile configuration, and refresh. Where labels arrive late, drift on inputs and predictions is still available in the meantime.
W: Without a label column that holds the ground truth, quality metrics cannot be derived, even though drift and distribution statistics are produced.

B=Granularity: every granularity from five minutes to a year supports the same set of metrics; the window size changes the number of rows per window, not which metrics exist.
D=Metric ordering: the metrics tables are computed in the same refresh and do not depend on each other; baseline drift is not a precondition for quality metrics.
T: Quality metrics in an inference profile exist only when prediction and label columns are both present.

@ DBX-MLP D2 T2.14 advanced use-case
S: A lending model gets ground-truth repayment labels only about 60 days after scoring. The team wants a monitoring design that gives useful signals during those 60 days and also reports true quality later. Which design does that?

@ DBX-MLP D2 T2.15 applied use-case

Profile alerts are normal Databricks SQL alerts: you write a query on the profile metrics table or the drift metrics table, then create an alert on that query that is evaluated at a chosen frequency and sends notifications when triggered. @ DBX-MLP D2 T2.15 advanced tradeoff
S: An inference profile covers a model with 120 features. Alerting on each feature separately would create 120 alert objects to own and tune, and a single event can shift many features together. Which design gives the team a manageable but still specific alert?
A: One alert whose query returns, for the latest window, the columns whose drift against the baseline is above the agreed threshold; the alert fires if any row is returned and lists the columns
B: One alert on the average of all drift values across the 120 columns, which hides a single strongly drifting feature in the mean
C: One alert on the number of rows in the profile metrics table, because a new window is written only when some feature has drifted
D: 120 alerts created by script, one per feature, each with its own destination and threshold, because grouping features cannot be done in a query
K: C
G: ## Alert granularity
A SQL alert evaluates one query and triggers on a condition on its result, for example when rows are returned or when a value passes a threshold. The drift metrics table has one row per column, window, slice and drift type, so a single query can filter the latest window and the right `drift_type`, apply the threshold with a `WHERE` clause, and return the offending columns.
## Trade-offs
- Per-feature alerts: precise but heavy to maintain and noisy when one cause shifts many features.
- One aggregated number: easy but a mean hides a single feature that has drifted a lot.
- One alert that lists the drifted columns: one object, specific content in the message.
W: A single query that returns the columns above the threshold gives one alert to manage and still tells the responder which features drifted.
X: A=Average of all drift values: averaging dilutes one severe drift among 119 stable features and the alert would stay quiet.
B=Row count of the metrics table: windows are written at each refresh whether or not there is drift, so the count says nothing about the distribution.
D=120 scripted alerts: queries can filter by `column_name`, window and threshold together, so grouping is possible, and many alerts only add maintenance and noise.
T: Alert on a query that returns the drifted columns, not on one alert per feature or one blended average.
