@ DBX-MLP D2 T2.9 advanced use-case
S: A data profile on an inference table refreshes every night and writes its drift metrics table each time, whether or not anything drifted. A table update trigger on that table starts the retraining job, and now a model is trained and registered every night, mostly on unchanged data. What is the best fix?
A: Point the trigger at the profile metrics table instead, because that table receives new rows only in windows where some feature has drifted
B: Replace the trigger by a weekly cron schedule, because a table update trigger always starts a run and offers no check of the table contents
C: Raise the minimum time between triggers to seven days, so that the trigger itself inspects the table and skips the run when no drift is found
D: Keep the trigger; a first task counts features above the baseline drift limit as a task value, and an If/else task trains only when the count is at least 1
K: D
G: ## A table update trigger fires on commits, not on content
A table update trigger starts a run when a monitored Unity Catalog table is updated, merged into or deleted from. It does not look at what changed. The drift metrics table is written by every profile refresh, so a trigger on it means "a refresh finished", which is the right moment to look at drift but not a reason to retrain.
- The trigger needs `SELECT` on the table for the Run as principal, plus `USE CATALOG` and `USE SCHEMA`, or the job does not run.
- Minimum time between triggers only delays runs after a previous run; it never inspects data.
## Trigger plus gate
Use the trigger for timing and a condition for the decision: a first task queries the drift rows (`drift_type = 'BASELINE'`), counts columns above the agreed limit and sets a task value with `dbutils.jobs.taskValues.set`. An `If/else condition` task compares `{{tasks.check_drift.values.n_drifted}}` with `>= 1` and only the true branch trains.
W: The trigger makes the check run right after fresh drift rows exist, and the If/else gate lets training start only when drift is above the limit, so unchanged nights cost one cheap task.
X: B=Weekly cron: it keeps the same fixed-time race and retrains or checks on a calendar rather than on evidence; the premise is also wrong, because a gate task and If/else task add the content check.
C=Longer minimum time: this setting only delays the next run after a previous one completed and never reads the table, so a run still starts and trains.
A=Profile metrics table: both metric tables are rewritten on every refresh, so this trigger fires just as often and still says nothing about drift.
T: Use a table update trigger for timing and an If/else gate on a drift count for the decision to retrain.

S: In a retraining job, a `train` notebook task registers a new model version and a downstream `validate` task must evaluate exactly that version. Today `validate` loads the highest version number of the model from the registry. Twice, two overlapping job runs made `validate` test a version that the other run had trained. How should the version reach the validation task?
A: Let `train` write the version number to a file on its driver's local disk and let `validate` read that file
B: Let `train` set a task value `model_version` with `dbutils.jobs.taskValues.set` and give `validate` the reference `{{tasks.train.values.model_version}}`
C: Add a fixed sleep at the start of `validate`, so that the other run has finished registering its own version before the highest one is read
D: Define a job parameter for the version number and let the scheduler fill it in before the run starts

G: ## Passing results between tasks
Task values pass a JSON-serializable value (up to 48 KiB) from one task of a job run to later tasks of the same run. A Python notebook sets one with `dbutils.jobs.taskValues.set(key, value)`, and downstream tasks reference it with the dynamic value `{{tasks.<task_key>.values.<key>}}`, also in non-Python tasks.

- The version number does not exist before training, so nothing can be set at schedule time.
- Tasks of one job can run on different compute, so a local file on the driver of one task is not visible to the next.
W: Task values are scoped to the run, so each `validate` receives the version its own `train` registered, whatever other runs do.
X: A=Local file: tasks can run on different clusters, and driver disk is not shared or durable; it also has no run isolation if the path is reused.
C=Fixed sleep: it hides the race rather than removing it, and the highest version can still belong to the other run.
D=Job parameter filled before the run: the version is created by `train` during the run, so no value exists at start time.
T: Hand the trained version to later tasks with a task value, not by asking the registry for the latest.

@ DBX-MLP D2 T2.9 advanced tradeoff
S: A drift alert fires and starts the retraining job. The investigation shows that an upstream pipeline change set a feature to null for 40% of rows (`percent_null_delta` jumped), and the real customer behavior did not change. Retraining on the new data would bake the defect into the model. How should the automated pipeline be designed?
A: Add a data quality gate before training that checks null rates and schema against expectations and stops the run, then route the incident to the data owner
B: Retrain immediately on the newest data so that the new model learns the missing values, and lower the alert threshold to catch such cases earlier
C: Disable drift alerts for that feature permanently, because a feature that can be corrupted upstream is not reliable enough to monitor
D: Retrain twice, on the old and on the new data, and promote whichever model has the higher training accuracy, to avoid a decision about the data
K: A
G: ## Not every drift is a reason to retrain
Drift metrics describe that a distribution changed, not why. Two very different causes produce the same alert.
- Real-world change (covariate shift): the population or behavior moved, so retraining on recent data helps.
- Data defect: a broken pipeline, a schema change or a unit change; retraining on it teaches the model the defect.
The drift metrics table also holds integrity deltas such as `percent_null_delta`, `percent_zeros_delta` and `count_delta`, which show a defect pattern next to the distribution tests. An automated retraining pipeline therefore starts with a validation task (expectations on null rate, ranges, schema) that fails the run, and the alert goes to the owner of the data.
W: Gating on data quality first keeps a defect out of training and sends the incident to the team that can fix the source, while genuine drift passes the gate and retrains.
X: B=Retrain immediately: the model would learn a pipeline bug as if it were behavior, and it would degrade again once the upstream defect is fixed.
C=Disable alerts on the feature: the alert did its job by exposing the defect; removing it leaves the model blind to the next corruption of that feature.
D=Compare training accuracy: training accuracy is not a holdout measure, and training twice does not address whether the data itself is valid.
T: Put a data validation gate in front of automated retraining, because drift alone cannot tell behavior change from a defect.

@ DBX-MLP D2 T2.10 advanced comparison
S: A pricing model uses the predicted default probability directly in a formula (expected loss = probability x exposure). Retraining yields two candidates: model X has the higher AUC, model Y has the lower log loss and a reliability curve close to the diagonal. Which should the pipeline prefer, and why?
A: Model Y, because the formula needs probabilities matching observed frequencies, which log loss and calibration measure and AUC does not
B: Model X, because AUC is threshold independent and therefore the only metric that matters for any model that outputs a probability
C: Model X, because a higher AUC guarantees that its probabilities are better calibrated, so log loss and the reliability curve would only repeat the same information
D: Model Y, because log loss is always lower for the simpler model, so lower log loss proves that Y generalizes better than X
K: A
G: ## Discrimination and calibration
- Discrimination (AUC, PR AUC): does the model rank positives above negatives? Invariant under any monotonic transformation of the scores.
- Calibration: does a predicted 0.2 correspond to about 20% observed? Measured with log loss, Brier score and reliability curves.
Two models can have identical AUC and very different calibration, because stretching the scores keeps the order. When the score is used as a probability in arithmetic (expected loss, expected value, a decision cost), calibration matters and log loss or the Brier score is the selection metric. A model with good ranking but poor calibration can often be repaired with a post-hoc calibration step (Platt scaling or isotonic regression) fitted on held-out data.
W: The formula multiplies the probability by the exposure, so the probabilities themselves must be right; log loss and a diagonal reliability curve show that, while AUC ignores it.
X: B=AUC as the only metric: AUC ignores the scale of the scores, so it cannot say whether 0.2 means 20%; it is the right metric for ranking tasks, not for this formula.
C=AUC guarantees calibration: it does not; any monotonic distortion of the scores leaves AUC unchanged and breaks calibration.
D=Simpler model has lower log loss: log loss is a measure on the holdout and has no built-in preference for simplicity; the argument is not valid.
T: Select on log loss and calibration when probabilities are consumed as numbers, and on AUC when only the ranking matters.
