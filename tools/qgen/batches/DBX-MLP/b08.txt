@ DBX-MLP D2 T2.9 advanced use-case
S: A data profile refreshes nightly on an inference table, and its drift metrics table is written by each refresh. The team wants a retraining job to start only after fresh drift metrics exist, not at a fixed hour that may come before the refresh finishes. The first task of the job will read the drift rows. Which trigger fits?
A: A cron schedule at 06:00 each day, which the team moves later whenever the profile refresh starts to take longer than before
B: A table update trigger on the drift metrics table, so that a job run starts when the profile refresh commits new rows to it
C: A continuous job that runs the drift query in a loop all day and starts the training notebook when the output changes
D: A file arrival trigger on the volume that holds the dashboard export, because the dashboard is regenerated after each refresh
K: B
G: ## Triggers for retraining jobs
A retraining pipeline is a Lakeflow job. A job can be started by a schedule, by a file arrival trigger, by a continuous run, or by a table update trigger. The best trigger is the one that matches the event that makes retraining meaningful.
- A table update trigger watches Unity Catalog tables (Delta and Iceberg managed tables, external Delta tables, materialized views, streaming tables) for updates, merges and deletes, and starts a run when they change. It needs no always-on cluster.
- The principal in the job's Run as field must have `SELECT` on every monitored table, plus `USE CATALOG` and `USE SCHEMA`, or the trigger fails to evaluate and the job does not run.
## Where the drift signal lives
Data profiling (documented earlier as Lakehouse Monitoring) writes a profile metrics table and a drift metrics table as Delta tables. Writing the drift rows is the event that tells the pipeline new evidence exists, so that table is the natural source for the trigger.
W: Table update trigger: the run starts when the refresh commits new drift rows, so the job never reads stale metrics and needs no guess about how long the refresh takes.
X: A=Cron schedule: a fixed hour races against the refresh; when the refresh runs long the job reads yesterday's drift rows, and each delay forces a manual change of the schedule.
C=Continuous job: it keeps a cluster running all day to poll a table that changes once a night, and "output changed" is not a reliable signal that new drift rows were written.
D=File arrival trigger: it fires on new files in a storage location, and the dashboard export is not the data the job needs; the dashboard is a view of the metric tables, not their source.
T: Start retraining from the event that produces the evidence (new drift rows) with a table update trigger instead of guessing a time.

@ DBX-MLP D2 T2.9 advanced troubleshooting
S: A job has a `check_drift` notebook task that sets a task value with `dbutils.jobs.taskValues.set("n_drifted", 2.0)`. A downstream `If/else condition` task uses the expression `{{tasks.check_drift.values.n_drifted}} == 2`, and the retraining branch never runs, although two features have drifted. What is the cause and the fix?
A: Task values cannot hold numbers, so the notebook must write the count as a string such as "two" and compare it with the `contains` operator
B: The If/else task reads only job parameters, so the count must be passed as a job parameter that the schedule sets before the run
C: The retraining task needs its Run if condition changed to "All done", because the If/else task stays pending until all tasks have run
D: The equality operator compares strings, so "2.0" is not equal to "2"; use a numeric operator, for example `>= 2`, or write the value as an integer
K: D
G: ## If/else tasks and task values
An `If/else condition` task evaluates a boolean expression with two operands. Operands can be job parameters, task parameters or task values, for example `{{tasks.check_drift.values.n_drifted}}`. A Python notebook sets a task value with `dbutils.jobs.taskValues.set(key, value)`.
## Comparison rules
- `==` and `!=` compare their operands as strings, so `12.0 == 12` is false.
- `>`, `>=`, `<`, `<=` compare numbers, so `12.0 >= 12` is true.
- Only numeric, string and boolean values are allowed; other types make the expression fail.
Write retraining gates with numeric operators (`>=`, `>`) against thresholds, which is also the more robust rule: "at least 2 features drifted" instead of "exactly 2".
W: The notebook stores 2.0, and `==` compares text, so "2.0" and "2" differ; a numeric operator such as `>= 2` evaluates as a number and the branch runs.
X: A=String count with contains: task values can be numeric; turning a count into words makes numeric thresholds impossible and the condition becomes fragile.
B=Job parameters only: operands can reference task values written upstream, which is the documented way to branch on a result computed inside the job.
C=Run if "All done": that setting controls how a task reacts to the outcome of its dependencies; it does not change how the expression is evaluated, and the If/else task completes normally.
T: Branch on computed values with numeric operators; `==` is a string comparison.

@ DBX-MLP D2 T2.9 advanced tradeoff
S: A drift alert fires and starts the retraining job. The investigation shows that an upstream pipeline change set a feature to null for 40% of rows (`percent_null_delta` jumped), and the real customer behavior did not change. Retraining on the new data would bake the defect into the model. How should the automated pipeline be designed?
A: Add a data quality gate before training that checks null rates and schema against expectations and stops the run, then route the incident to the data owner
B: Retrain immediately on the newest data so that the new model learns the missing values, and lower the alert threshold to catch such cases earlier
C: Disable drift alerts for that feature permanently, because a feature that can be corrupted upstream is not reliable enough to monitor
D: Retrain twice, on the old and on the new data, and promote whichever model has the higher training accuracy, to avoid a decision about the data
K: A
G: ## Not every drift is a reason to retrain
Drift metrics describe that a distribution changed, not why. Two very different causes produce the same alert.
- Real-world change (covariate shift): the population or behavior moved, so retraining on recent data helps.
- Data defect: a broken pipeline, a schema change or a unit change; retraining on it teaches the model the defect.
The drift metrics table also holds integrity deltas such as `percent_null_delta`, `percent_zeros_delta` and `count_delta`, which show a defect pattern next to the distribution tests. An automated retraining pipeline therefore starts with a validation task (expectations on null rate, ranges, schema) that fails the run, and the alert goes to the owner of the data.
W: Gating on data quality first keeps a defect out of training and sends the incident to the team that can fix the source, while genuine drift passes the gate and retrains.
X: B=Retrain immediately: the model would learn a pipeline bug as if it were behavior, and it would degrade again once the upstream defect is fixed.
C=Disable alerts on the feature: the alert did its job by exposing the defect; removing it leaves the model blind to the next corruption of that feature.
D=Compare training accuracy: training accuracy is not a holdout measure, and training twice does not address whether the data itself is valid.
T: Put a data validation gate in front of automated retraining, because drift alone cannot tell behavior change from a defect.

@ DBX-MLP D2 T2.9 advanced tradeoff
S: A fraud model receives its true labels about 45 days after scoring. A team wants automated retraining but worries that waiting for accuracy to drop means 45 days of damage. Feature drift against the training baseline is available daily. Which trigger design best balances speed and reliability?
A: Retrain on every drift alert and ignore labels, since waiting for performance numbers would only delay each model update further
B: Retrain only when labelled accuracy falls below the target, and never use drift, because drift can occur while the model stays accurate
C: Use feature drift as an early signal that starts a candidate run, and let labelled performance and a champion comparison confirm the promotion
D: Retrain every night on a rolling window, because a schedule is the only trigger type that does not depend on delayed labels
K: C
G: ## Leading and lagging signals
- Input and prediction drift are leading signals: available at scoring time, no labels needed, but they do not prove that quality fell.
- Labelled performance (accuracy, recall, log loss) is the lagging signal: it measures quality, but only after labels arrive.
A robust trigger design uses both. Drift opens a candidate run (train and register a challenger). The decision to put it in production is made with labelled data that already exists for the recent window, compared against the current champion.
This avoids both extremes: promoting every drifted model (some drift is harmless) and waiting passively for lagging proof.
W: Drift gives the early start and the labelled evaluation against the champion decides, so the response is fast without promoting models that merely look different.

B=Accuracy only: with a 45-day delay the team would learn about degradation weeks late, which is exactly the damage the design must limit.
D=Nightly schedule: a schedule can be used, but it retrains regardless of need, and it still has to answer the question of when a new model is better, which needs the labelled comparison.
T: Drift starts a challenger; labelled evaluation against the champion decides the promotion.

@ DBX-MLP D2 T2.9 advanced troubleshooting
S: After a retraining run, the new model is serving, but the profile still reports high baseline drift for the same features. The drift alert fires again after every refresh, and the retraining job starts again every time. The baseline table is the training snapshot of the original model. What should be changed?
A: Raise the alert threshold until the alert stops firing, because the new model is already in production and no further action is needed
B: Set the baseline table of the profile to the training data of the newly promoted model as a part of the retraining job
C: Switch the profile to consecutive drift only, by deleting the baseline table, so that the old snapshot is no longer compared with
D: Increase the profile granularity to monthly windows so that the drift is averaged away and the alert cannot reach the threshold

G: ## The baseline must follow the model
For an inference profile the recommended baseline is the data used to train or validate the model being monitored, with the same feature columns and the same model id column. Baseline drift compares each window with that table.
After a retrain the training distribution changed. If the baseline still describes the old model, every window keeps looking drifted, and a trigger on that alert becomes a retraining loop. The retraining job should therefore update the baseline table (and the profile configuration that points to it) as part of promotion, so drift is measured against what the serving model actually saw.

W: Updating the baseline to the new training data makes baseline drift mean "different from what the serving model learned", which ends the loop and keeps the alert meaningful.
X: A=Raise the threshold: the signal is a false alarm only because the reference is stale; a higher threshold also hides real drift in the future.
C=Delete the baseline: consecutive drift only detects abrupt changes between windows and would miss a slow drift away from the training distribution.
D=Monthly windows: averaging over a longer window delays detection and still compares to the old model's data, so a persistent shift continues to show.
T: Move the profile baseline to the new model's training data whenever retraining promotes a model.

@ DBX-MLP D2 T2.9 applied use-case
S: Retraining needs three feature tables that three different pipelines update between 01:00 and 03:00, in any order, with several commits each. A table update trigger exists on the training job. The team wants one run after all three have been refreshed, not one run per commit. Which configuration fits?
A: Monitor the tables with the trigger set to start when any table is updated, and let the training task skip itself when inputs are incomplete
B: Create three separate jobs, each triggered by one table, and ask the last job to cancel the runs of the two jobs that started earlier

A table update trigger can monitor several tables. With more than one, "Trigger when" decides whether a run starts when any table or all tables are updated. Two advanced options shape the timing:

B=Three jobs with cancellation: this builds fragile orchestration by hand for something the trigger already supports.
C=Cron with retries: table update triggers do monitor multiple tables, and a fixed time repeats the race that the pipeline updates finish at different times.
T: Combine "all tables updated" with a wait after the last change to run retraining once per complete data refresh.

@ DBX-MLP D2 T2.9 advanced use-case
S: A scheduled retraining job trains a model and registers it in Unity Catalog as `prod.ml.churn`. Batch scoring and a serving endpoint load `models:/prod.ml.churn@Champion`. The team wants retraining to be fully automatic, but a new version must not reach production unless it beats the current model. Which last stage of the job fits?
A: Register the new version and set the Champion alias to it at once, then run the evaluation in a later job and roll back by deleting the version
B: Register the version, give it a Challenger alias, evaluate it against the champion, and move Champion to it only if the gate passes
C: Overwrite the files of the champion version in the registry with the new model weights so that the alias keeps its target
D: Write the new model to a volume as a pickle file and ask a reviewer to copy it over the champion by hand
K: B
G: ## Automatic training, controlled promotion
In Unity Catalog, each registered model has versions, and aliases such as `Champion` and `Challenger` are mutable named pointers to a version. Consumers that load `models:/<name>@Champion` follow the pointer, so a promotion is one call, `client.set_registered_model_alias(name, "Champion", version)`, and a rollback is the same call with the older version.

- Train and register a new version (never overwrite an existing version, which are immutable records of a run).

- Evaluate against the champion; if the gate holds, reassign `Champion`.
This keeps retraining automatic while promotion stays conditional.
W: The challenger alias lets the evaluation task load the candidate, and the Champion pointer moves only after the gate passes, so consumers never see an unvalidated version.
X: A=Set Champion first: production and the endpoint would use the unvalidated version immediately, and deleting a version afterwards is not a rollback.
C=Overwrite the champion version: registered versions are immutable records tied to a run, and replacing weights in place destroys lineage and the ability to roll back.
D=Pickle on a volume and manual copy: it removes the automation and bypasses the registry that gives governance, lineage and aliases.
T: Register every retrained model as a new version with a Challenger alias, and move Champion only through the gate.

@ DBX-MLP D2 T2.10 applied use-case
S: The nightly retraining job produces a challenger. The registry stores metrics from the time each version was trained, and the champion's stored AUC is 0.91 from three months ago. The challenger scores 0.89 on today's holdout. An engineer suggests promoting only if the challenger's number beats the stored one. What is the flaw, and what should the job do?
A: The comparison is fine; a lower number means the challenger is worse, so the job should keep the champion and stop
B: The stored metric is a training-time value; the challenger should be compared on test data from the training pipeline only, never on newer data
C: Both models should be scored on the same current holdout, including the champion, because the stored number came from older data and a different split
D: The challenger should be compared by its training loss, since loss does not depend on which holdout was used for the comparison

G: ## Compare candidates on the same data
A metric is a property of a model and a dataset. A stored metric for the champion describes its performance on the data of three months ago; the challenger's number describes today's holdout. The two values are not comparable, because the data distribution and often the split are different.
## The champion-challenger evaluation task
In an automated retraining job, an evaluation task loads the champion (for example `models:/prod.ml.churn@Champion`) and the challenger, scores both on the same recent holdout, and compares the same metrics. W: Scoring champion and challenger on the same current holdout removes the difference of data and split, so the comparison measures the models rather than the datasets.
X: A=Comparing against the stored number: the 0.91 may have been reached on easier or older data; the challenger could be better on today's data, or the champion could be worse than 0.91 now.
B=Old test data only: restricting the check to the training pipeline's test set hides precisely the shift that triggered retraining.
D=Training loss: it measures how well the model fits the data it saw and says nothing about generalization to a holdout.
T: Evaluate champion and challenger on the same fresh holdout; never compare against a stale stored metric.

@ DBX-MLP D2 T2.10 advanced comparison
S: A pricing model uses the predicted default probability directly in a formula (expected loss = probability x exposure). Retraining yields two candidates: model X has the higher AUC, model Y has the lower log loss and a reliability curve close to the diagonal. Which should the pipeline prefer, and why?
A: Model Y, because the formula needs probabilities matching observed frequencies, which log loss and calibration measure and AUC does not
B: Model X, because AUC is threshold independent and therefore the only metric that matters for any model that outputs a probability
C: Model X, because a higher AUC guarantees that its probabilities are better calibrated, so log loss and the reliability curve would only repeat the same information
D: Model Y, because log loss is always lower for the simpler model, so lower log loss proves that Y generalizes better than X
K: A
G: ## Discrimination and calibration
- Discrimination (AUC, PR AUC): does the model rank positives above negatives? Invariant under any monotonic transformation of the scores.
- Calibration: does a predicted 0.2 correspond to about 20% observed? Measured with log loss, Brier score and reliability curves.
Two models can have identical AUC and very different calibration, because stretching the scores keeps the order. When the score is used as a probability in arithmetic (expected loss, expected value, a decision cost), calibration matters and log loss or the Brier score is the selection metric. A model with good ranking but poor calibration can often be repaired with a post-hoc calibration step (Platt scaling or isotonic regression) fitted on held-out data.
W: The formula multiplies the probability by the exposure, so the probabilities themselves must be right; log loss and a diagonal reliability curve show that, while AUC ignores it.
X: B=AUC as the only metric: AUC ignores the scale of the scores, so it cannot say whether 0.2 means 20%; it is the right metric for ranking tasks, not for this formula.
C=AUC guarantees calibration: it does not; any monotonic distortion of the scores leaves AUC unchanged and breaks calibration.
D=Simpler model has lower log loss: log loss is a measure on the holdout and has no built-in preference for simplicity; the argument is not valid.
T: Select on log loss and calibration when probabilities are consumed as numbers, and on AUC when only the ranking matters.

S: A weekly retraining job promotes the challenger whenever its validation AUC exceeds the champion's. @ DBX-MLP D2 T2.10 advanced troubleshooting
S: A retraining job runs a hyperparameter search and then selects the best run. The final reported performance in production is regularly lower than the logged value. The selection code is:
runs = mlflow.search_runs(experiment_ids=[exp_id],
    order_by=["metrics.test_auc DESC"], max_results=1)
best = runs.iloc[0]["run_id"]
What is the main problem with this approach?
A: It orders by the metric ascending, so the job selects the worst run of the whole experiment and the result is lower in production than logged
B: `search_runs` reads only the first run of an experiment, so the best run is never part of the result

G: ## Selection bias
Every comparison against a dataset uses information from it. If dozens of runs are compared on the test set and the best is kept, the winner's test score is optimistically biased (a maximum of noisy estimates), and the test set can no longer report honest generalization.

- Train set: fit parameters.

- Test set: scored once for the selected model, as the number reported to stakeholders and used in the promotion gate.

W: The query ranks on test_auc, so the test set has influenced the choice; ranking on a validation metric and scoring the test set once restores an unbiased final number.
X: A=Ascending order: the clause says DESC, so the highest value comes first and `max_results=1` returns the best run by that metric.
B=Only the first run: `search_runs` returns all runs that match the filter, ordered and limited as requested.
D=Training AUC: this is the most optimistic metric and rewards overfitting; the registry has nothing to do with availability of test data.
T: Choose on validation, report on a test set touched once.

@ DBX-MLP D2 T2.10 advanced tradeoff
S: A demand model is retrained weekly from a table of daily records. The retraining job shuffles all rows randomly, puts 80% into training and 20% into the holdout, and the challenger always looks better than the champion; in production the new models often disappoint. Which change gives a more trustworthy selection?
A: Increase the holdout to 50% of the rows while keeping the random shuffle, to reduce the variance of the estimate
B: Normalize the holdout features with statistics computed on the holdout itself, so that its scale matches the production data at scoring time

Daily records of a series are correlated over time. ## Time-based evaluation
Train on data up to a cut-off and evaluate on the period after it, which mimics how the model will be used. In retraining this also matches the question the gate answers: does the challenger beat the champion on the newest period? Both are scored on the same later window, and the cut-off moves forward with each run.
W: A time-based split evaluates on data the model could not have seen, as in production, and scoring the champion on the same later period keeps the comparison fair.
X: A=Larger random holdout: the estimate would be less noisy but still leaky, because the rows around each held-out day are in training.
B=Normalize with holdout statistics: this leaks information from the evaluation data into preprocessing and makes the score less honest.
C=Stratify by product id: it balances products across parts but does not stop neighboring days from landing on both sides of the split.
T: For time-dependent data, select models with a time-ordered split and compare champion and challenger on the same later window.
