@ DBX-MLP D1 T1.13 advanced comparison
S: A nightly pipeline must (1) join and aggregate several terabytes of Delta tables into model features, then (2) train and tune many compute-heavy models whose runtimes differ widely and which are scheduled dynamically. The team runs both stages in one Databricks job on one cluster. Which split of frameworks fits the strengths of each?
A: Ray for both stages, because it parallelizes arbitrary Python and therefore also replaces Spark for terabyte-scale joins and aggregations
B: Spark for the terabyte-scale joins and aggregations, then Ray on the same cluster for the dynamic, compute-heavy training and tuning tasks
C: Spark for both stages, running the training loop inside a `mapInPandas` function so that no second framework has to be started
D: Two separate clusters, one for Spark features and one for Ray training, exporting the features to CSV files between the stages
K: B
G: ## Two kinds of parallelism
Databricks documents Ray and Apache Spark as complementary frameworks.
- **Spark** specializes in *data parallelism*: one operation runs over partitions of a large dataset. This is the right model for ETL, joins, aggregations and analytics over tables that do not fit one machine.
- **Ray** excels at *logical parallelism*: many dynamic, compute-intensive tasks (training runs, simulations, reinforcement learning) that are scheduled on demand and may have very different runtimes.
## Running both
Ray on Databricks creates the Ray cluster inside the Spark cluster (Ray 2.3.0 and above), so one compute resource, one governance layer (Unity Catalog), one MLflow tracking server and one job can host both stages. Ray applications can read Delta tables.
W: Spark does the data-parallel feature work it was designed for, and Ray on the same cluster schedules the uneven, compute-heavy training tasks dynamically. The documentation presents exactly this combination.
X: A=Ray for both: Ray can distribute Python and read Delta, but terabyte-scale joins and aggregations are the data-parallel case Spark specializes in, so replacing it gives up the engine built for that stage.
C=Spark for both: a training loop inside `mapInPandas` is bound to the Spark partition model, with no dynamic task scheduling for tasks of very different length. Ray is available on the same cluster, so nothing forces avoiding it.
D=Two clusters with CSV: Ray runs inside a Databricks cluster, so a second cluster and a lossy file export add cost, copies and lost types and governance for no benefit.
T: Use Spark for data parallelism over big tables and Ray, on the same cluster, for dynamic compute-heavy logical parallelism.

@ DBX-MLP D1 T1.13 applied use-case
S: A reinforcement-learning team runs thousands of simulators. Each simulator keeps its own mutable state (environment, policy copy) between many calls, and results from finished simulators decide which new ones to start. Which framework model matches this workload best?
A: Spark tasks, because every `groupBy().applyInPandas()` call keeps its Python state alive between stages for reuse
B: Spark ML, because its estimators hold the environment state in each partition and update it iteratively
C: A single-node scikit-learn loop on the driver, because stateful simulators cannot be parallelized on any cluster
D: Ray actors and tasks, which hold state in long-lived workers and let new work be launched from results as they arrive
K: D
G: ## Task model differences
Spark runs a job as a fixed plan of stages. Each task processes one partition, is stateless between stages and is planned before it starts.
Ray exposes Python primitives for **tasks** (stateless functions) and **actors** (long-lived workers that keep state between calls). Work can be created while the program runs, from earlier results. Databricks lists reinforcement learning and other dynamic, compute-intensive jobs as Ray use cases.
W: Ray actors keep simulator state across calls, and Ray tasks can be submitted dynamically as results arrive. This is the logical parallelism the documentation describes for reinforcement learning.
X: A=Spark applyInPandas: each call receives its group, processes it and returns; Spark does not keep Python objects alive between stages, and the stage plan is fixed up front.
B=Spark ML: estimators implement fixed distributed algorithms over DataFrames. They are not a runtime for arbitrary stateful simulators.
C=Single node on the driver: Ray and similar frameworks exist precisely to parallelize such workloads across a cluster, so the claim is wrong.
T: Dynamic, stateful, compute-heavy work (simulators, RL) fits Ray's tasks and actors; Spark fits fixed data-parallel stages.

@ DBX-MLP D1 T1.13 advanced definition
S: A Ray cluster created with `setup_ray_cluster` is running. In the Spark UI the team sees one long-running Spark job whose number of tasks equals the number of Ray worker nodes, and it is not finishing. An engineer wants to kill it as "stuck". What is this job?
A: The background Spark job that hosts the Ray cluster: one task per Ray worker node, with the head node on the driver
B: A Spark ML training job that Ray submits for every trial, which should finish when the first trial completes
C: A broadcast of the Ray dependencies, which ends once every executor has copied the Python packages
D: The Spark external shuffle service, which Ray starts so that its tasks can exchange objects through shuffle files between executors
K: A
G: ## How Ray on Spark is built
`ray.util.spark.setup_ray_cluster` creates a Ray cluster *on* Apache Spark. Internally it starts a background Spark job. Each Spark task in that job starts a Ray worker node and keeps running, so the Ray worker lives as long as the task. The Ray head node is created on the Spark driver.
Consequences: Ray workers occupy Spark task slots for their whole lifetime; the number of Ray workers is set by `min_worker_nodes` and `max_worker_nodes`; calling `shutdown_ray_cluster` ends the job. By default the head node gets 0 CPUs and 0 GPUs, since the driver is shared.
W: The long-running job is the Ray cluster itself: one Spark task per Ray worker node. Killing it takes the Ray cluster down, so the correct way to end it is shutting down the Ray cluster.
X: B=Per-trial Spark ML job: Ray tasks run on the Ray workers, not as Spark ML jobs; this job exists once per Ray cluster, not per trial.
C=Dependency broadcast: libraries are installed before the cluster starts and nothing is being broadcast; such a step would end quickly.
D=Shuffle service: Ray has its own object store and does not use Spark shuffle files; the documented design is one task per Ray worker.
T: Ray on Spark = a background Spark job with one task per Ray worker and the head on the driver.

@ DBX-MLP D1 T1.13 advanced use-case
S: Forecasts for 3,000 products use a library that is single-threaded and takes between one second and forty minutes per product. The output of the first pass decides which products get an expensive second pass, and the pass count is unknown in advance. The team compares Spark and Ray. Which choice gives the best load balance with the least extra code?
A: Ray tasks submitted per product, with follow-up tasks created from the first results as futures complete
B: One `groupBy("product").applyInPandas()` call with a second call afterwards that is started by a cron schedule
C: A Spark ML `Pipeline` with a custom transformer per pass, because pipelines can have any number of stages
D: One wide `mapInPandas` call over all rows, with the second pass hard-coded for every product regardless of outcome
K: A
G: ## When tasks are uneven and dependent
In Spark, a stage ends when its slowest task ends and the plan is fixed before the job starts. A second pass whose size depends on first-pass results needs a second job, with a barrier between them.
Ray schedules tasks dynamically and lets code launch new tasks from results as they arrive (futures). Databricks lists time series forecasting with Prophet or ARIMA as a Ray use case (concurrent estimates) and compute-intensive tasks as the area where Ray excels.
W: Ray tasks give dynamic scheduling for uneven durations and let follow-up work start as soon as each first result is known, without waiting for the slowest product.
X: B=Two applyInPandas calls: the first stage waits for the slowest product, and a cron-started second job is a manual barrier with extra orchestration and no dynamic choice of work.
C=Pipeline stages: a Spark ML pipeline has a fixed list of stages, and a custom transformer per pass does not make the number of passes dynamic or fix the uneven task lengths.
D=Hard-coded second pass: the expensive pass would run for every product, wasting most of the compute that the first-pass decision was supposed to save.
T: Dynamic, uneven, dependent compute is Ray's strength; Spark stages are fixed and wait for the slowest task.

@ DBX-MLP D1 T1.14 applied use-case
S: A retailer needs one forecasting model per store for 2,000 stores. Each store's history is 5-200 MB, the training function is plain pandas code, and the output must be a table with one row of metrics per store. Which implementation fits?
A: Collect the distinct store ids on the driver and fit the models one after another in a Python `for` loop
B: One Spark ML estimator on the whole table, with the store id one-hot encoded as a feature
C: `df.groupBy("store_id").applyInPandas(train_store, schema="store_id string, rmse double")`
D: `df.mapInPandas(train_store, schema)` on the unpartitioned table, assuming each store's rows share one batch
K: C
G: ## The split-apply-combine pattern
Grouped map with `groupBy().applyInPandas()` splits the DataFrame by key, calls your Python function once per group with all of the group's rows as a `pandas.DataFrame`, and combines the returned DataFrames into a new Spark DataFrame. You provide the function and the output schema. Groups run in parallel across the cluster.
## Limits
All data of a group is loaded into memory before the function is applied, so skewed groups can cause out-of-memory errors, and `maxRecordsPerBatch` is not applied to groups.
W: Each store is one group, so the function runs per store in parallel and returns a metrics row; that is the intended use of grouped map.
X: A=Driver loop: 2,000 sequential fits on the driver ignore the cluster and take as long as the sum of all fits.
B=One Spark ML model: it fits a single global model with a store feature, not 2,000 independent models, and the requested metrics per store would not exist.
D=mapInPandas without grouping: batches follow partitions, not stores, so one store's rows can be split across batches and tasks; mapInPandas has no per-key guarantee.
T: One model per key at scale is `groupBy(key).applyInPandas(fn, schema)`.

@ DBX-MLP D1 T1.14 advanced tradeoff
S: A tuning job fits one model per region for 12 regions with `groupBy("region").applyInPandas(fit_and_score, schema)`, trying 40 hyperparameter configurations inside the function in a loop. The cluster has 200 cores, but only 12 tasks run and the job takes hours. What is the best redesign?
A: Cross join the regions with the 40 config rows and group by region and config id, so each (region, config) is an independent task
B: Raise `spark.sql.shuffle.partitions` to 2,000, so that Spark splits each region's rows over more tasks
C: Switch to `mapInPandas`, which divides each region into small batches that run on all 200 cores in parallel and keeps one model per region
D: Add more worker nodes to the cluster, since extra cores let each of the 12 groups use several tasks
K: A
G: ## Parallelism of grouped map equals the number of groups
`applyInPandas` runs one call per group, and all the data of a group goes to one task. With 12 groups, at most 12 tasks do work, regardless of cluster size or shuffle partition count.
## Create more independent units
If the work can be expressed independently, make each unit a group: replicate the region data for each candidate configuration (cross join with a small config table), group by `(region, config_id)` and train once per pair. This gives 480 tasks. The price is that each region's data is replicated 40 times in the shuffle, so use it when data per group is small relative to compute.
W: Grouping by region and config id turns 12 long tasks into 480 shorter ones that can use the cores, at the cost of replicating each region's data per configuration.
X: B=More shuffle partitions: the groupBy still sends all rows of a key to one partition, so 12 keys still means 12 busy tasks.
C=mapInPandas: it does not preserve the per-region grouping that the function needs, and batches of a region would be fitted separately instead of as one model.
D=More workers: extra cores stay idle because the number of groups caps parallelism; the redesign is about the unit of work, not capacity.
T: Grouped-map parallelism is bounded by the number of groups; add a config key to the grouping to create more tasks.

@ DBX-MLP D1 T1.14 applied tradeoff
S: A 1.5 GB model must score a table of 800 million rows. The scoring function currently loads the model inside a Series-to-Series pandas UDF, which runs once for every Arrow batch. Executors are slow and memory churn is high. Which change fits best?
A: Keep the UDF and raise `maxRecordsPerBatch` to a very large value so that each partition has one batch
B: Use `mapInPandas`, load the model once before iterating over the batches of the iterator, and yield a result frame for each batch
C: Replace the UDF with `groupBy("id").applyInPandas()`, so that the model is loaded only once per customer id and the shuffle is free
D: Collect the model to the driver and call `predict` there in a loop over `toLocalIterator()` of the table
K: B
G: ## Iterator-based map functions
`DataFrame.mapInPandas()` passes your function an *iterator* of `pandas.DataFrame` batches and expects an iterator of `pandas.DataFrame` back. Code before the loop runs once per task, so expensive setup (loading a model) is paid once and reused for every batch of the partition.
A Series-to-Series pandas UDF that loads the model in its body repeats the load for each batch. (Iterator-of-Series pandas UDFs offer the same one-time setup.)
W: Loading before the loop in `mapInPandas` pays the 1.5 GB cost once per task instead of once per batch, and scoring stays parallel over all partitions.
X: A=Huge maxRecordsPerBatch: a bigger batch means fewer loads but needs memory for a whole partition's Arrow data and can cause out-of-memory errors; it only hides the repeated-setup flaw.
C=applyInPandas by id: it would load the model for each group (many loads) and force a shuffle by key that scoring does not need.
D=Driver loop: scoring 800 million rows on a single machine is exactly what distributed scoring avoids.
T: For per-task setup such as model loading, use mapInPandas (or iterator UDFs) and load before the batch loop.

@ DBX-MLP D1 T1.14 applied use-case
S: A grouped-map function fits one gradient-boosting model per store with `applyInPandas`, and a separate nightly job must load each store's model later. The cluster is shared, and its executors are replaced between jobs. Which output design keeps the fitted models available to that later job?
A: Pickle each model to `/tmp` on the executor and return only the file path, because the local disks of all executors form one shared volume
B: Return a one-row `pandas.DataFrame` per store with the key, the metric and the pickled model bytes in a column declared as `binary` in the schema, and write the result to a Delta table
C: Return the fitted estimator objects in a pandas `object` column that the schema declares as `string`, so that Spark converts them with `str()` for storage
D: Assign each model to a module-level dictionary in the function and read that dictionary on the driver after the job has finished
K: B
G: ## What a grouped-map function can hand back
The function runs in a Python worker process on an executor. Whatever it returns must be a `pandas.DataFrame` whose columns match the declared output schema (see the pandas function APIs page); Spark converts it to rows of a new DataFrame. Nothing else leaves the executor process.
- A column declared as `binary` carries `bytes`, so a pickled or serialized model fits in an ordinary DataFrame next to the key and metrics. Saving that DataFrame as a Delta table versions the models with the data and makes them readable by any later job.
- Python state in the worker (module globals, local files in `/tmp`) is not shared between executors, is invisible to the driver and disappears when the executor is replaced.
- An estimator object is not a Spark SQL type, so it cannot be returned as an `object` column that is silently turned into a string.
For models that must be registered, the usual next step is to log the bytes (or the loaded model) to MLflow from the driver or from a later job.
W: A `binary` column in the output schema moves each serialized model through the normal result path, and the Delta table keeps it after the executors are gone.
X: A=Executor `/tmp`: local disks belong to one executor each, are not shared and vanish when the executor is replaced, so the returned path would point to nothing.
C=Object column declared as string: the schema must describe a convertible type; `str()` of an estimator is only a text description and cannot be loaded back as a model.
D=Module-level dictionary: it lives in the executor's Python process and the driver never sees it, so the dictionary on the driver stays empty.
T: To keep per-group models from `applyInPandas`, return serialized bytes in a `binary` column and persist the result.

@ DBX-MLP D1 T1.14 advanced troubleshooting
S: A grouped-map function builds its result like this and the job fails with a schema error:
```
def train(pdf):
    ...
    return pd.DataFrame({"store": [pdf.store_id.iloc[0]], "rmse": [e]})
df.groupBy("store_id").applyInPandas(train, schema="store_id string, rmse double")
```
Which change fixes it?
A: Cast the `rmse` value to a string column and change the schema to match, because grouped-map outputs must be strings
B: Name the returned column `store_id`, so the labels of the pandas result match the field names of the schema
C: Add `.cache()` to the input DataFrame so that the schema is inferred from cached data
D: Replace `applyInPandas` with `.collect()` and build the output DataFrame on the driver
K: B
G: ## Output schema contract
For `applyInPandas` you pass a schema (a `StructType` or a DDL string). The Databricks docs say the column labels of the returned `pandas.DataFrame` must match the field names of the schema if it is given as strings, or match the field data types by position if the labels are not strings (for example, integer indices).
In the snippet the schema expects `store_id` and `rmse`, but the function returns `store` and `rmse`. The label mismatch is the failure. Types must also convert (double for `rmse`).
W: Renaming the returned column to `store_id` makes the pandas labels match the schema's field names, which satisfies the documented contract.
X: A=Cast to string: the schema declares `rmse double`; schemas support many types, and changing the value type to string would create a type mismatch.
C=cache: the schema for `applyInPandas` is declared by the caller, never inferred from cached input.
D=collect on the driver: it moves all rows to the driver and abandons parallelism, but the contract error is only about a column label.
T: applyInPandas output labels must equal the declared schema's field names (or match by position when labels are not strings).

@ DBX-MLP D1 T1.14 advanced use-case
S: For each of 5,000 customers, a team has a training DataFrame `train_df` and a separate holdout DataFrame `hold_df`, both keyed by `cust_id`. One function should fit on the customer's training rows and score the same customer's holdout rows in a single task. Which API fits best?
A: Join both DataFrames on `cust_id`, then use `applyInPandas`, which fits on all joined rows and scores the same rows
B: Union the two DataFrames with a flag column, then train on the whole union and filter by the flag after training
C: `train_df.groupBy("cust_id").cogroup(hold_df.groupBy("cust_id")).applyInPandas(fit_and_score, schema)`
D: Broadcast `hold_df` and call `mapInPandas` on `train_df`, joining with the holdout rows inside the function
K: C
G: ## Cogrouped map
`groupBy().cogroup().applyInPandas()` shuffles two DataFrames so that the groups sharing a key are together, then calls your function with two `pandas.DataFrame` objects (and optionally the key), one per input. The function returns one `pandas.DataFrame`, and the results are combined into a new Spark DataFrame. As with grouped map, all data of a cogroup is loaded into memory before the function runs.
Typical use: train/test pairs per key, as-of joins between two datasets, or comparing two sources per entity.
W: Cogroup hands each task the customer's training and holdout frames separately, so the function can fit on the first and score the second without mixing them.
X: A=Join then applyInPandas: the joined frame multiplies rows, mixes training and holdout data in one frame, and leaves the function to separate them again; evaluation can leak.
B=Union with a flag: a single group would hold both parts, which the function would have to split by hand, and a 5,000-way flag filter invites leakage if the split is wrong.
D=Broadcast with mapInPandas: broadcasting all holdout rows to every task wastes memory, batches are not per customer, and the join logic moves into custom code.
T: Two inputs per key in one function means cogroup().applyInPandas().

@ DBX-MLP D1 T1.15 applied use-case
S: A tuning function calls `train_and_log(params)` for 30 configurations from inside one `with mlflow.start_run(run_name="search"):` block. Each call opens its own run for the trial. The team wants every trial to appear as a child of the search run. How should each trial's run be opened?
A: With `mlflow.start_run(run_name=...)` and a tag `parent` holding the search run's name
B: In a different experiment per trial, because experiments are the only grouping level in MLflow
C: With plain `mlflow.start_run()`, which attaches itself to the active run automatically when one exists
D: With `mlflow.start_run(nested=True)`, which creates a child run under the currently active run
K: D
G: ## Parent and child runs
MLflow runs can be nested: starting a run with `nested=True` while another run is active creates a child that is linked to the active run through the system tag `mlflow.parentRunId`. A child run has its own parameters, metrics and artifacts. The UI groups children under the parent, and search can filter by the parent tag.
The Databricks Hyperopt documentation uses the same structure for tuning: the call to `fmin()` is the main (parent) run and each tried hyperparameter setting is a child run. A search that logs trials as nested runs follows this convention.
The `nested=True` argument and the `mlflow.parentRunId` tag are standard MLflow behavior; no docs.databricks.com page spells them out, so the keys rely on MLflow semantics and the Hyperopt child-run structure above.
W: `nested=True` is how MLflow records the parent link, so each trial becomes a child of the search run with its own parameters and metrics.
X: A=Tag by name: a custom tag is not the parent link; the UI and `mlflow.parentRunId` searches would not group the trials, and names can collide.
B=One experiment per trial: experiments are containers for many runs; splitting 30 trials across experiments makes comparison harder and does not model a hierarchy.
C=Plain start_run: with a run already active, a plain call without `nested=True` raises an error about an active run instead of attaching.
T: Hierarchical tracking = `mlflow.start_run(nested=True)` inside an active parent run.

@ DBX-MLP D1 T1.15 applied troubleshooting
S: A search function opens a parent run and calls a helper for each trial. The second call fails with an error that a run is already active:
```
with mlflow.start_run(run_name="search"):
    for p in grid:
        with mlflow.start_run():
            fit_and_log(p)
```
The engineer proposes calling `mlflow.end_run()` before the inner block. What is the correct fix?
A: Call `mlflow.end_run()` before the inner block, so that the parent is closed and every trial starts clean with no active run
B: Change the inner call to `mlflow.start_run(nested=True)`, so each trial becomes a child and the parent stays active
C: Set the environment variable `MLFLOW_RUN_ID` to the parent id, so that new calls reuse the parent run
D: Wrap the loop in `mlflow.autolog(disable=True)` so that the inner run is not created twice
K: B
G: ## Why the error occurs
`mlflow.start_run()` uses a thread-local stack of active runs. Starting a run while one is active raises an exception unless `nested=True` is given. The inner `start_run()` therefore fails when called inside the parent block.
## Fix versus workaround
- `nested=True` keeps the parent open and records the child link.
- Ending the parent first would also remove the error, but the later trials would not be children of anything and the parent could not log its summary metrics at the end.
W: `nested=True` is the supported way to start a run inside an active run: the parent stays open for its summary and each trial is linked to it.
X: A=end_run first: it closes the parent, so trials are no longer children and the parent block cannot log the best metric afterwards; it hides the error and breaks the hierarchy.
C=MLFLOW_RUN_ID: reusing the parent's id would log all 30 trials into one run, which collides on parameter names (parameters cannot be overwritten) and gives no per-trial view.
D=autolog disable: autologging does not create the inner run in this code; the explicit `start_run` call does.
T: Starting a run inside an active run needs `nested=True`; ending the parent breaks the hierarchy.

@ DBX-MLP D1 T1.15 applied use-case
S: A parent run named `sweep-42` has 200 child runs that each logged `val_auc`. A job must find the child with the highest `val_auc` and register its model. How should the job locate that run?
A: Open the experiment table, sort manually by `val_auc` and copy the run id into the job configuration
B: Call `mlflow.get_run` for the parent and read its `val_auc` metric, because parents copy their best child's metrics
C: `mlflow.search_runs(filter_string=f"tags.mlflow.parentRunId = '{pid}'", order_by=["metrics.val_auc DESC"], max_results=1)`
D: List all runs of the experiment with `search_runs` and pick the newest one, because the last trial is the best
K: C
G: ## Children are searchable by parent
Every child created with `nested=True` carries the system tag `mlflow.parentRunId`. `mlflow.search_runs` accepts a `filter_string` (including `tags.` and `metrics.` fields) and `order_by`, so a job can select the best child programmatically and use its run id, for example to build a `runs:/<run_id>/model` URI for registration.
