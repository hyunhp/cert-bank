@ DBX-MLP D3 T3.2 advanced use-case
S: A fraud team wants to run a rewritten model on real production requests for two weeks while no caller ever receives its score. The production endpoint `fraud-prod` serves `current` at 100% of traffic. Which design implements this shadow evaluation?
A: Add the candidate as a second served entity at a 50% traffic percentage and discard its responses inside the calling service, so that half of all the live requests are scored by the new model
B: Keep `current` as the only model answering callers, and have the caller send a duplicate of each request to the candidate on its own endpoint, logging that output for offline comparison
C: Register the candidate under the `champion` alias in Unity Catalog, so that the registry mirrors every production request into the new version for scoring
D: Enable scale to zero on a second served entity, so that the candidate wakes up only for a sample of the requests and its answers stay hidden from callers
K: B
G: ## Three rollout patterns
- **Canary**: a small share of live requests is answered by the new model, so real users see its output. Risk is limited by the share.
- **Blue-green**: two full environments exist; clients are switched from one to the other and the old one is kept for rollback.
- **Shadow**: the new model receives a copy of live traffic but its output is never returned to users, so it carries no user risk.
## What the traffic split does and does not do
In Model Serving, `traffic_config` routes each request to exactly one served entity by percentage, and the response of that entity goes back to the caller. It is a canary or A/B tool. It has no mirroring mode. A shadow test therefore needs the duplication to happen outside the split: the caller (or a gateway in front of it) sends the same payload to the candidate, which lives on its own endpoint, or is addressed through the served-model route `/serving-endpoints/<endpoint>/served-models/<name>/invocations`, which ignores traffic settings. Only the production answer is returned, and the candidate's output is stored for comparison against the production output and later labels.
W: A duplicate request to a separately deployed candidate gives the candidate real inputs while the production entity remains the only source of answers, which is the definition of shadow mode.
X: A=Served entity at 50%: the split sends each request to one entity and returns that entity's answer to the caller. Half of the users would receive candidate scores, so this is a risky canary, not a shadow test.
C=Alias mirroring: aliases are named pointers to model versions in Unity Catalog. They do not copy or replay requests, and they have no connection to which requests an endpoint receives.
D=Scale to zero: this setting only releases compute after idle time and adds cold-start latency. It does not select a sample of requests and does not hide any response from callers.
T: Shadow mode needs request duplication outside the traffic split, because the split returns the chosen entity's answer.

@ DBX-MLP D3 T3.2 advanced troubleshooting
S: A `challenger` served entity receives 5% of the requests of an endpoint and was created with `scale_to_zero_enabled: true` to save cost. In the canary comparison its p99 latency shows irregular spikes, while `current` is steady, although both models run the same code path. What explains the spikes and what should be changed?
A: The update that added the challenger is still replacing the configuration, so requests alternate between old and new containers; wait for it to finish, then recompare
B: The challenger's model signature differs from the current model's, which slows request parsing on that entity only; relog the model with the earlier signature
C: Route optimization applies only to the `current` entity, so the challenger uses the slower path; enable route optimization on the challenger served entity too
D: The challenger's low request volume lets it idle and scale to zero, so some requests pay a cold start; turn off scale to zero for the canary so that the latency comparison is fair
K: D
G: ## Why a small canary can look slow
A canary receives a small share of traffic. If scale to zero is on, the served entity scales down after a period of inactivity (about half an hour without requests) and the next request waits for a cold start. Databricks notes that scaling up from zero usually takes seconds but can take minutes and has no latency SLA, and it advises against scale to zero for production workloads that need consistent response times.
## Compare like with like
A canary comparison is only meaningful if the entities differ in the model, not in infrastructure behavior. Give the challenger the same availability settings as `current` (scale to zero off), and size it for its own share of traffic.
## What is endpoint-level
Route optimization is chosen once for the whole endpoint when it is created, not per served entity. During a configuration update the old configuration keeps serving until the new one is ready, so requests are not mixed between old and new containers.
W: Cold starts after idle periods hit a lightly loaded entity, and disabling scale to zero on the canary removes that confounder from the comparison.
X: A=Update still running: during an update the previous configuration keeps serving until the new one is ready. Requests are not split between old and new containers, so this would not give intermittent spikes on one entity.
B=Signature mismatch: a signature describes the schema that is validated for inputs and outputs. It does not slow one served entity relative to another, and relogging a model is not the remedy for cold-start behavior.
C=Per-entity route optimization: route optimization is configured for the whole endpoint at creation time. It cannot be switched on for one served entity, so the premise is wrong.
T: Configure canary and baseline entities with identical availability settings, otherwise cold starts masquerade as model latency.

@ DBX-MLP D3 T3.2 advanced troubleshooting
S: An engineer submits a configuration update that moves `challenger` from 10% to 50%. While the endpoint shows Not ready (Updating), an alert shows that the error rate of the challenger's current 10% share is rising. The engineer wants to keep the 50% split from going live. What should be done?
A: Cancel the in-progress update from the endpoint details page; the previous configuration keeps serving, and a new update can then set the split the team really wants
B: Send a second update that sets `current` back to 100%; the endpoint queues it and applies it ahead of the pending 50% change, so the split never goes live
C: Stop the endpoint, which discards the pending configuration and restores the 90/10 split when the endpoint is started again after the investigation
D: Delete the `challenger` served entity through its served-model route, which takes effect immediately and bypasses the configuration update in progress
K: A
G: ## Updates are not instant
Changing a served entity, size or traffic split on a custom model endpoint is a configuration update. It can take many minutes because the new configuration is built and provisioned while the old one keeps serving traffic. You are billed for both until the switch is complete, and if the update fails, the old configuration stays active.
## While an update is in progress
- Another update cannot be submitted until the running one finishes.
- The running update can be cancelled (UI: Cancel update on the endpoint details page).
- Only an endpoint with no in-progress update can be stopped.
For a rollback in a release process: cancel the pending update if the risk shows up mid-flight, or submit a new configuration that sets `current` to 100% once the endpoint accepts updates. Because a rollback is itself an update, keep canary shares small so that the damage during the update window stays small.
W: Cancelling the pending update keeps the already-serving configuration, which is exactly the one the team trusts, and then a new update can follow.
X: B=Stop the endpoint: stopping is only possible for endpoints without an in-progress update, and it shuts resources down so queries fail with a 400 error. It does not discard configurations to restore a previous split.
C=Second update: only one update can be in progress at a time, so a second configuration is rejected rather than queued ahead of the pending one.
D=Deleting via the served-model route: that route is for sending queries to one served entity, with traffic settings ignored. It is not a management API and cannot remove an entity.
T: A running configuration update is cancelled, not overtaken; the old configuration serves until a successful switch.

@ DBX-MLP D3 T3.2 advanced tradeoff
S: `recs-api` is a custom model endpoint created without route optimization. Traffic has grown, and the team wants the lower overhead latency of route optimization, with a rollback path that leaves the old service untouched. Which plan fits?
A: Edit the existing endpoint's configuration to turn on route optimization, and roll back by editing it off again if the latency does not improve for the clients
B: Add a route-optimized served entity to the existing endpoint at 100% traffic and set the old entity to 0%, which keeps the previous version available for a quick rollback later
C: Create a new route-optimized endpoint for the same model version, validate it with OAuth test calls to its own URL, move clients over, and keep the old endpoint until confidence is high
D: Create the route-optimized endpoint and keep clients on personal access tokens, since only the endpoint URL changes and authentication stays as it was before
K: C
G: ## Blue-green on Model Serving
Blue-green means running two complete environments and switching clients between them. On Model Serving the natural form is two endpoints: the live one (blue) and a new one (green) that you validate fully before moving callers.
## Why route optimization forces it
Route optimization can only be enabled when an endpoint is created. An existing endpoint cannot be updated to become route optimized, and the setting belongs to the endpoint, not to a served entity. A route-optimized endpoint also changes the client contract:
- it is queried at its own dedicated URL (`endpoint_url` from the endpoint's details), not at the workspace invocations URL;
- it accepts only OAuth tokens, not personal access tokens, and a token must carry `authorization_details` for the endpoint.
Plan for client changes (service principal, token minting, URL) as part of the cutover.
W: A second, route-optimized endpoint is the only way to adopt the feature, and keeping the first one running gives an immediate rollback target.
X: A=Editing the existing endpoint: route optimization can be chosen only at creation time. An existing endpoint cannot be switched, so neither the enabling nor the rollback edit exists.
B=Route-optimized served entity: route optimization is an endpoint property, so a single served entity cannot be route optimized inside a standard endpoint.
D=Keeping personal access tokens: route-optimized endpoints reject them. Clients need OAuth tokens (a service principal for applications) and the new URL.
T: Route optimization is fixed at endpoint creation, so adopting it is a blue-green move to a new endpoint with new OAuth clients.

@ DBX-MLP D3 T3.2 advanced tradeoff
S: An endpoint serves `current` at 95% and `challenger` at 5%. Peak load is 200 requests per second and the model needs about 0.1 s per request. Both entities were created with the same large compute scale-out. Which configuration follows Databricks sizing guidance better?
A: Give every served entity the concurrency for the full endpoint peak, because the platform may route any request to any entity and each entity must be able to take all of the load alone
B: Size each served entity from its own share: concurrency is roughly queries per second times execution time, so the challenger needs about 5% of the peak load's concurrency and `current` about 95%
C: Give the challenger the largest scale-out available, because a new model version is slower on its first requests and needs the extra capacity until it warms up
D: Use one scale-out value for both entities that is derived from the average of their sizes, so that comparisons of their latency are not distorted by compute differences
K: B
G: ## Concurrency per served entity
Provisioned concurrency is the number of requests a served entity can process in parallel. Databricks gives the estimate: provisioned concurrency is about queries per second times model execution time in seconds. At 200 QPS and 0.1 s per request the whole endpoint needs about 20 concurrent slots at peak.
## Each entity sees its share
The traffic split sends each request to one entity, so an entity only needs capacity for its share. A 5% challenger needs about 1 slot, a 95% entity about 19. Oversizing the challenger costs money for compute that the split never uses. If the share is raised later, the same configuration update can resize the entity.
## Guard rails
Keep a small margin for bursts: undersizing leads to 429 "Too many concurrent requests" errors, which tell you to raise provisioned concurrency (or let autoscaling raise it up to the configured maximum).
W: Concurrency is estimated from QPS times execution time and per-entity QPS is the endpoint QPS times its traffic share.
X: A=Full load on each entity: the split delivers each request to one entity only, so no entity ever receives the whole load. Sizing both for it doubles cost without improving results.
C=Largest scale-out: warm-up of a new version does not need a bigger entity, and the biggest size multiplies cost for a 5% share of traffic.
D=Averaged size: an average of two different loads fits neither entity. The 95% entity would be undersized and would return 429 errors at peak.
T: Size every served entity for its own share of QPS times execution time.

@ DBX-MLP D3 T3.2 advanced use-case
S: A release plan for a custom model endpoint has three edits: add `challenger` as a served entity, set the split to 90/10, and enlarge the compute size of `current`. The engineer plans to submit them as three consecutive API calls. What is the problem and the better approach?
A: Only one update can run at a time and each is billed for both configurations while it runs; submit a single configuration update that contains all three changes together
B: There is no problem, because the platform merges queued updates for the same endpoint into a single rebuild before the new configuration is provisioned
C: Each call must go to a different endpoint, because a single endpoint accepts exactly one changed property per update to keep rollbacks atomic
D: Traffic split changes need no configuration update, so only the first and third edits are sent as updates and the split is applied later as a request parameter by clients
K: A
G: ## One update at a time
A custom model endpoint applies a new configuration in the background: the new containers are built and provisioned (this can take many minutes), and the existing configuration serves requests until the new one is ready. During this time you pay for both configurations, and a second update cannot be made until the first finishes.
## Batch related changes
The configuration is declarative: `served_entities` and `traffic_config` are sent together in `PUT /api/2.0/serving-endpoints/{name}/config`. Sending the complete target state in a single call:
- builds and provisions once;
- avoids a window in which the challenger exists with a split that was never intended;
- gives one success or failure result, with the old configuration kept if anything fails.
W: Send the whole desired served_entities and traffic_config in one update, because updates do not queue and each one costs a full build.
X: B=One property per update: an update carries the full configuration, not a single property, and nothing limits an endpoint to one change per update.
C=Split as request parameter: the percentages live in `traffic_config` of the endpoint configuration, so changing them is a configuration update. A request body field cannot change the split.
D=Merged queued updates: updates are not queued. While one is in progress another cannot be made, so consecutive calls collide.
T: Treat the endpoint configuration as one declarative document and update it once.

@ DBX-MLP D3 T3.2 advanced tradeoff
S: A challenger model was trained on restricted data, and only the data science group may send requests to it. All application services may query the current model. How should the challenger be exposed for validation?
A: Add it to the production endpoint as a served entity with a small traffic percentage and set a separate query permission on that served entity for the data science group
B: Serve it from the production endpoint and restrict EXECUTE on the model in Unity Catalog to the data science group, so other callers are rejected when the split picks it
C: Deploy it on its own endpoint and grant CAN_QUERY on that endpoint only to the data science group, because permissions are assigned per endpoint, not per served entity
D: Alias the challenger version as `challenger` and grant the alias to the group; applications calling the endpoint then can never be routed to it by the traffic split
K: C
G: ## Where access is enforced
- **Who may query**: CAN_QUERY (and higher levels) is granted on the serving endpoint. All served entities of an endpoint share the same endpoint permissions.
- **What the endpoint may read**: the endpoint acts with the identity of its recorded creator, which needs USE CATALOG, USE SCHEMA and EXECUTE on each Unity Catalog model it serves. Callers do not need grants on the model.
## Consequence for rollouts
A traffic split mixes models behind one name and one permission set, so every caller of that name can be answered by every entity. If the audience for the new model differs (restricted data, internal testing, a different team), the two models belong on different endpoints. A split is for models that the same audience may use.
W: Endpoint permissions are per endpoint, so a restricted audience needs a separate endpoint.
X: A=Entity-level permission: there are no query permissions on individual served entities. Access control is set on the endpoint, so the production audience could still be answered by the challenger.
B=EXECUTE for callers: EXECUTE on the model is checked for the endpoint's creator when the endpoint is created or updated, not for the callers, so it does not filter who is answered by which entity.
D=Alias grants: aliases are pointers to model versions and carry no endpoint access rules. A traffic split is also driven by percentages, not by aliases.
T: Different audiences need different endpoints: access control is per endpoint, and a split puts everyone behind the same permissions.

@ DBX-MLP D3 T3.3 advanced troubleshooting
S: A custom pyfunc model is registered in Unity Catalog. It works in a notebook but fails when served:
```
def predict(self, context, model_input):
    w = torch.load("/Volumes/ml/prod/weights/model.pt")
    return score(w, model_input)
```
Which change makes the file available at serving time?
A: Grant the endpoint's service principal READ VOLUME on the volume and keep the path in the code, because the endpoint mounts Unity Catalog volumes while it serves
B: Attach an instance profile to the endpoint so that it can read the volume path directly from cloud storage at request time, then keep the code unchanged
C: Copy the file to a DBFS root folder and read it from a `/dbfs/...` path inside `predict`, since serving containers share the cluster's mounted file systems
D: Log the model with `artifacts={"weights": "/Volumes/ml/prod/weights/model.pt"}` and load the file in `load_context` through `context.artifacts["weights"]`
K: D
G: ## Why serving cannot read your volume
Real-time workloads at scale perform best when every dependency is captured statically at deployment. For that reason Model Serving requires files that live in Unity Catalog volumes to be packaged into the model artifact itself. The serving container does not mount your workspace file systems, and fetching files over the network at request time makes startup fragile.
## The pattern
`mlflow.pyfunc.log_model(..., artifacts={"name": "<path>"})` copies the files into the model. Inside the model class the copies are reachable at `context.artifacts["name"]`. Load them once in `load_context`, not in `predict`.
```
def load_context(self, context):
    self.w = torch.load(context.artifacts["weights"])
```
W: Anything a pyfunc reads at inference must be in the model: pass it through the artifacts argument and read context.artifacts.
X: A=READ VOLUME grant: the problem is not a missing privilege. Serving requires volume artifacts to be packaged into the model, so a grant does not make the path exist in the container.
B=Instance profile: it gives the container credentials for AWS resources your code accesses itself, but a volume path is not mounted in the container. It would also be a runtime network dependency.
C=DBFS path: serving containers do not share the cluster's file systems or mounts, so a path that works in a notebook does not exist there.
T: Files go into the model with artifacts= and are read from context.artifacts.

@ DBX-MLP D3 T3.3 advanced tradeoff
S: A custom pyfunc loads a large embedding file and builds a tokenizer inside `predict` on every call. After deployment, median latency is far above what the same model reaches in a notebook loop. How should the class be restructured?
A: Build the tokenizer and read the embedding file once in `load_context`, store them on `self`, and keep only the per-request logic in `predict`
B: Cache the loaded objects in a module-level global of the notebook that logged the model, so every served replica reuses the same in-memory copy
C: Enable scale to zero so that idle replicas release memory between requests and each new request loads the objects into a freshly started container
D: Raise the endpoint's request timeout so slow loads in `predict` finish successfully, and size the served entity up to hide the repeated cost
K: A
G: ## Two methods, two lifetimes
A `mlflow.pyfunc.PythonModel` has two required parts:
- `load_context(self, context)` runs once when the model is loaded into a replica. Put everything that is expensive and request-independent here: reading weights and artifacts, building tokenizers, opening clients.
- `predict(self, context, model_input)` runs for every request. It should contain only per-request work such as input formatting, calling the model and formatting outputs.
Databricks calls this out as critical to minimize the work done in `predict`, which speeds up inference.
## Why other fixes fail
Objects held in a notebook's memory are not part of the logged model and do not exist in the serving container. Capacity and timeout settings change how long repeated work is tolerated, not whether it repeats.
W: One-time loading belongs in load_context; predict runs per request and must stay light.
X: B=Scale to zero: this adds cold starts and reloads the objects whenever a replica restarts, making latency worse. It does not remove repeated work from `predict`.
C=Notebook global: the serving container runs the logged model in its own process, so notebook memory is not available to it. The code would fail or reload anyway.
D=Higher timeout and size: the repeated load still happens on every request. A larger entity burns more compute to hide the symptom and the timeout is a ceiling, not a cure.
T: Heavy initialisation goes in load_context; predict is per-request only.

S: A pyfunc model is logged from a Databricks Runtime ML cluster without `pip_requirements`. Registration in Unity Catalog works, but every endpoint build fails. The model's `conda.yaml` lists `mlflow-skinny`. What is the fix?
A: Add `mlflow-skinny` to `extra_pip_requirements` with an exact version pin, which makes the container builder accept the skinny package as the MLflow dependency

Databricks Runtime ML includes `mlflow-skinny`, not the full `mlflow` package. A pyfunc logged without explicit `pip_requirements` records `mlflow-skinny` in `conda.yaml`. Model Serving requires `mlflow` and cannot build the container image otherwise.
## The pattern
```
mlflow.pyfunc.log_model(

```

W: Always declare the full mlflow in pip_requirements for pyfunc models logged on Databricks Runtime ML.
X: A=Pinned skinny package: the problem is the skinny flavor itself. Pinning it only fixes which skinny version is installed and the build still lacks `mlflow`.
B=GPU workload: the workload type changes hardware, and the build still uses the environment recorded in the model. It does not replace it, and GPU builds are slower.
D=Removing signature: signature and input example are metadata. They do not decide the MLflow package in the environment file, and Unity Catalog requires a signature anyway.
T: On Databricks Runtime ML log pyfunc models with pip_requirements that include full mlflow, never rely on the default skinny capture.

@ DBX-MLP D3 T3.3 advanced comparison
S: A pyfunc preprocessing module is published as an internal wheel on the company's Artifactory mirror. Policy forbids public internet access from endpoints, and workspace admins have set Artifactory as the workspace default package repository. What is the simplest correct way to include the library?
A: Package the wheel in a Unity Catalog volume and list the volume path in `extra_pip_requirements`, since serving never uses a configured package mirror
B: List the library in the model's pip requirements, so that Model Serving installs it from the workspace default package repository while building the container
C: Run `%pip install` of the wheel in the notebook that logs the model; Model Serving copies the installed packages of the cluster into the container
D: Set a `PIP_INDEX_URL` environment variable on the served entity, so that the container downloads the wheel from the mirror each time a request arrives
K: B
G: ## Two supported ways to ship private libraries
- **Option 1, private package repository**: workspace admins configure the mirror (such as Nexus or Artifactory) as the default package repository. Model Serving uses that workspace-level configuration when it builds the model environment. You then list the library like any other requirement.
- **Option 2, wheel files**: when no mirror is reachable, or the library is not in any repository, upload the wheel (to a Unity Catalog volume) and reference it in `extra_pip_requirements`, or pack it with the code-path parameter and reference `code/<wheel>.whl`. `mlflow.models.utils.add_libraries_to_model(<model-uri>)` can also create a new version with all dependencies as wheels.
## Choosing
A configured mirror is simplest and keeps one source of truth, so use Option 1. Use wheels when the mirror cannot serve the package. Libraries are resolved at build time, not per request.
W: With a workspace default repository set, declare the library as a normal requirement and let the build resolve it.
X: A=Wheel in a volume: this works as Option 2, but the claim that serving never uses a configured mirror is false, and it adds a packaging step that is unnecessary here.
C=Notebook %pip: a notebook installation affects only that cluster session. The container is built from the requirements recorded in the model, not from the cluster's installed set.
D=Index URL variable: dependencies are installed when the image is built, not when requests arrive, so an environment variable on the served entity at request time has no effect on installation.
T: Use the workspace default package repository for private libraries; fall back to wheel files only when the mirror cannot provide them.

@ DBX-MLP D3 T3.3 applied troubleshooting
S: A team registers a pyfunc to Unity Catalog:
```
mlflow.set_registry_uri("databricks-uc")
mlflow.pyfunc.log_model(name="m", python_model=M(),
    registered_model_name="ml.prod.scorer")
```
The call fails with an error saying the model has no signature metadata. What resolves it?
A: Request the EXECUTE privilege on the schema for the logging identity, since the registration fails until the identity may run models in that schema
B: Pass a model signature (for example `infer_signature(sample_input, sample_output)`) when logging, because Unity Catalog requires input and output schemas
C: Register under a two-level name such as `prod.scorer`, because three-level names are only accepted by the legacy workspace model registry
D: Switch the registry URI to the workspace model registry, because pyfunc models without a signature are accepted only there and not in Unity Catalog

B: Use express deployments: register the custom model to Unity Catalog from a serverless notebook so the environment is packaged then, and accept a longer registration step
C: Set scale to zero on the served entity so that the container image is cached between versions, at the price of cold starts on the first request
D: Pin every dependency to the latest release in `pip_requirements`, which removes dependency resolution from the build, at the price of frequent relogging
K: B
G: ## Standard versus express deployments
- **Standard**: a container image is built at deployment time from the model's recorded requirements. This is slower, can fail in dependency resolution or the image build, and the serving environment might not match the training environment.
- **Express**: artifacts and the environment are packaged when you register the model (from a serverless notebook, for a custom model in Unity Catalog), so deployment skips the image build. The serving environment is identical to the notebook environment you registered from. Registration takes longer (seconds to a minute), the deployment event log no longer shows image creation events, and there are version requirements for MLflow and the SDK listed on the docs page.
## Other levers
Route optimization addresses request latency, not deployment. Scale to zero affects idle behavior. Pinning versions helps reproducibility but still builds an image.
W: Express deployments move packaging to registration, skipping the container build and matching the notebook environment.
X: A=Route optimization: it improves request routing and throughput. It cannot be enabled on an existing endpoint and has no effect on image builds or environment consistency.
C=Scale to zero: this releases compute when idle and adds cold starts. It does not cache images across versions or change what is built.
D=Latest versions: unpinned or latest releases make the environment less reproducible and do not skip the image build. The build still resolves and installs packages.
T: Express deployments shift packaging to registration, removing the image build from deploys.

S: After a release, a post-processing step in a pyfunc triples the model execution time per request. Traffic is unchanged, and clients now receive 429 with `Too many concurrent requests. Consider increasing the provisioned concurrency of the served entity`. What is the right remedy?
A: Enable scale to zero on the served entity, so that the platform keeps fewer idle slots and the pool of slots grows only when 429 errors appear in the client logs
B: Increase the client request timeout above the model execution time, since a longer wait lets concurrency rise by itself without config changes
C: Raise the served entity's scale-out (or autoscaling maximum) to about three times the earlier concurrency, since required concurrency is roughly QPS times execution time
D: Switch the request format to `dataframe_records` so that rows are scored in parallel, which divides the execution time by the number of rows
K: C
G: ## Capacity is concurrency
A served entity's provisioned concurrency is the number of requests it can process at the same time. Databricks estimates it as queries per second times model execution time in seconds, and the Serving UI scale-out sizes (Small, Medium, Large) correspond to ranges of concurrency. At constant QPS, tripling execution time triples the concurrency needed.
## What the 429 means
`Too many concurrent requests...` says the entity's current provisioned concurrency cannot handle the load. With autoscaling the platform adds concurrency up to the configured maximum, so raise the maximum or the fixed size. Validate the new value with load testing. Optimizing the new post-processing step (for example moving work into `load_context`) is the other lever, because it lowers the execution time.
W: Required concurrency = QPS x execution time, so slower inference at the same QPS needs more provisioned concurrency.
X: A=Scale to zero: this releases capacity when idle and adds cold starts. It does not add slots under load.
B=Longer client timeout: waiting does not create capacity. Requests that the entity cannot admit still receive 429, and long waits tie up more concurrency.
D=Records format: the body format does not parallelise the scoring inside the model and does not shorten execution time.
T: Provisioned concurrency tracks QPS x execution time; slower models need more of it.
