@ DBX-MLP D1 T1.6 expert troubleshooting
S: A Structured Streaming job scores card transactions with a Spark ML PipelineModel inside `foreachBatch(score_and_write)`. The function first writes the scored micro-batch to the Delta table `ml.risk.scores`, then appends a one-row summary of the batch to the Delta table `ml.risk.score_audit`. Last night the cluster restarted in the middle of micro-batch 5121, after the first write had committed but before the second. After recovery, `scores` contains 18,400 duplicated rows, all from batch 5121, while `score_audit` has exactly one row for that batch. Both writes must stay inside the same function, the team follows the guidance not to catch and retry exceptions locally, and downstream readers must not deduplicate. Which change makes a replayed batch safe for both tables?
A: Add .option("txnAppId", stable query id) and .option("txnVersion", batch_id) only to the audit write, which is the last write in the function
B: Add .option("txnAppId", new UUID per batch) and .option("txnVersion", batch_id) to both Delta writes inside the function
C: Add .option("txnAppId", stable query id) and .option("txnVersion", batch_id) to both Delta writes inside the function
D: Add .option("txnAppId", stable query id) and .option("txnVersion", current epoch milliseconds) to both Delta writes inside the function
K: C
G: ## Why foreachBatch can duplicate
Structured Streaming guarantees that a micro-batch is processed again after a failure, but `foreachBatch` gives you the batch as a plain DataFrame. Two writes inside it are two separate Delta commits; if the first commits and the job dies before the checkpoint records the batch as done, the replay writes it again.
## Idempotent Delta writes
Delta Lake supports idempotent writes with two options on each write:
- `txnAppId`: a stable string that identifies the writing application (the same across restarts).
- `txnVersion`: a monotonically increasing number; Databricks recommends binding it to `batchId`.
Delta records the pair in the table's log and **skips** a write whose `(txnAppId, txnVersion)` it has already committed. Databricks docs: use both options on every Delta write in foreachBatch, and let errors propagate instead of retrying locally.
## Evidence check
Batch 5121 was written twice to `scores` (committed before the crash) and once to `audit` (not committed before the crash): exactly the replay pattern.
W: Stable app id and batch_id on both writes: on replay Delta sees that version 5121 of this app was already committed to scores and skips it, while the audit write commits once.
X: A=Only on the audit write: the scores write, the one that actually duplicated, stays unprotected.
B=New UUID per batch: the replay generates a different app id, so Delta treats it as a new writer and commits the duplicate.
D=Epoch milliseconds as version: the replayed batch gets a new, larger version, so Delta cannot recognize it as already written.
T: In foreachBatch, give every Delta write txnAppId (stable) and txnVersion (batchId) to make replays idempotent.

G: ## How Spark trees treat categorical features
Spark ML tree models (decision tree, random forest, GBT) read **column metadata**: features produced by `StringIndexer` (or `VectorIndexer`) are marked as categorical with their number of values. Trees then split on groups of categories instead of thresholds.
## maxBins
`maxBins` (default 32) is the maximum number of bins used to discretize continuous features **and** the maximum number of categories a categorical feature may have. If any categorical feature has more values than `maxBins`, the fit fails with exactly this message. The fix is to set `maxBins` on the **tree estimator** to at least the largest category count (57 here; 64 leaves room).

C=maxBins=16: the rule requires maxBins to be at least the number of categories, so a smaller value fails the same way.
D=maxBins on the VectorAssembler: the assembler only combines columns and has no maxBins parameter.
T: For Spark ML trees, maxBins on the estimator must be at least the largest categorical feature's number of values.
