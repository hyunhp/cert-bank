@ DBX-MLP D2 T2.1 applied use-case
S: A multitask Lakeflow job runs `train`, then `validate`, then `deploy`. The validation task must evaluate exactly the model version that this run's training task registered, even when two runs execute at the same time. How should the version reach the validation task?
A: The validation task loads `models:/prod.ml.churn@champion`, because the alias always names the newest candidate version
B: The training task publishes the model URI as a task value, and the validation task reads it from the upstream task
C: The validation task calls `get_latest_versions` on the model name, because the highest version number is always the current run's
D: The training task writes the model URI to a file under `/tmp`, and the validation task reads that file from its own compute
K: B
G: ## Passing the model between pipelines
In the recommended Databricks workflow the training pipeline, the model validation pipeline and the deployment pipeline are tasks of one multitask job. The training task ends by registering the model in Unity Catalog and yields a model URI. The validation task takes that URI, loads the model from Unity Catalog and runs its checks. Databricks says to use task values (`dbutils.jobs.taskValues.set` in the producer, `.get(taskKey=..., key=...)` in the consumer) to hand the URI over.
## Why identity matters
A pipeline stage must test the artifact its own run produced. Anything that resolves "the newest" or "the current" version at read time can point to another run's model.
W: A task value is scoped to the job run, so the validation task receives exactly the URI its upstream training task produced, regardless of concurrent runs.
X: A=Champion alias: the alias points to the model already serving production, so validation would test the old release instead of the new candidate.
C=Latest version lookup: with two concurrent runs, the highest version can belong to the other run, so the wrong model is validated.
D=File in /tmp: local disk of one task's compute is not shared with the next task, which may run on different compute, so the file is not found.
T: Pass the model URI between job tasks with task values, never by resolving the latest version.
V: Lakeflow Jobs, Unity Catalog, MLflow

@ DBX-MLP D2 T2.1 applied troubleshooting
S: A deployment task gives the Champion alias to every model version that the validation task marked as Challenger, with no further step. After two weeks, a version with a lower AUC than its predecessor is serving production. What is missing from the deployment pipeline in the recommended Databricks workflow?
A: A second validation task that repeats the same format and metadata checks directly before the alias is moved
B: A Model Serving endpoint with a traffic split, because an alias update is only allowed behind a served endpoint
C: A retraining step that loops until the new version shows a higher AUC than the current Champion version
D: A comparison of the Challenger with the existing Champion on held-out data, and an alias update only when it wins
K: D
G: ## What the deployment pipeline does first
Validation decides whether a version may be a Challenger. It does not say that the version is better than what is serving. The recommended deployment pipeline therefore starts by confirming that the Challenger performs at least as well as the current Champion. Databricks describes two forms: an offline comparison that evaluates both models on a held-out dataset and tracks the results in MLflow, and an online comparison (an A/B test or a gradual rollout) for real-time serving.
## Then the alias moves
Only if the Challenger wins does it replace the Champion alias. A pipeline can also promote directly, but then it has chosen to accept the risk that this question shows.
W: Comparing the Challenger with the Champion on the same held-out data before the alias update stops a weaker version from replacing a better one.
X: A=Repeat validation: the same checks pass again with the same result, and they never compare the new version with the one in production.
B=Endpoint traffic split: an alias is a Unity Catalog name for a version and can be changed without any endpoint, and a split alone does not decide which model wins.
C=Retrain until better: a loop on the same code and data does not make a better model, and it spends compute on a gate that a single comparison provides.
T: Compare Challenger with Champion before the Champion alias moves.
V: Unity Catalog, MLflow

Model validation loads the model from Unity Catalog and runs checks that depend on the organization: format and metadata, performance on selected data slices, compliance checks for tags or documentation. @ DBX-MLP D2 T2.1 applied comparison
S: A team promotes only the model artifact (deploy models). After months, the production inference notebook no longer matches the feature engineering code used in development, and predictions are skewed. Which statement gives the structural cause and the recommended remedy?
A: Only the artifact is promoted, so supporting code goes separately; adopt deploy code so all pipelines pass the same tests
B: Unity Catalog models cannot store feature dependencies, so the team must export the feature code into every model
C: Aliases do not work with batch inference, so the inference job should load models by hard-coded version numbers
D: The model should be retrained in production every day, because stale models cause feature code to drift
K: A
G: ## What each pattern promotes
Deploy models trains in development, tests the artifact in staging and moves it to production. Databricks lists as a disadvantage that supporting code, such as pipelines for feature engineering, inference and monitoring, needs to be deployed to production separately. Nothing forces that code through the same review and integration test, so it can diverge.
Deploy code promotes the training code and the supporting code together. All of it goes through code review and integration tests in staging, and the production model is trained on production code. Deploy models still fits when training is very expensive or hard to reproduce, work happens in one workspace, or there is no CI/CD.
W: The skew comes from supporting code that is shipped by a separate, untested path, and deploy code removes it because every pipeline is promoted and integration-tested together.
X: B=Feature dependencies: models trained with Unity Catalog feature tables do store feature and function dependencies, so this is not a limitation, and the problem is code that is out of step.
C=Hard-coded versions: aliases work for batch and streaming inference, and hard-coding versions removes the decoupling without fixing code drift.
D=Daily retraining: a fresh model trained with the old feature code is still scored by mismatched inference code, so the skew remains.
T: Deploy models leaves supporting code on a separate path, deploy code promotes it with the model code.
V: Unity Catalog, MLflow

@ DBX-MLP D2 T2.1 applied tradeoff
S: Security policy blocks the development workspace from reading production data. A team that promotes only trained models (deploy models) therefore trains on synthetic samples in development. Which limitation of the pattern does this show, and what does Databricks recommend in most situations?
A: Models cannot be registered in Unity Catalog from development, so the team has to register them from production

In deploy models the artifact is produced by training code in development and then tested in staging and deployed. Databricks lists as a disadvantage that if production data is not accessible from the development environment (which may be true for security reasons), the architecture may not be viable. The model would be trained on data that does not represent production.
## Deploy code removes the problem
In deploy code the training code moves to production and the final model is trained there on production data, even when access to that data is restricted for people. This is why Databricks recommends promoting code rather than models in most situations.

@ DBX-MLP D2 T2.2 applied definition
S: An auditor asks which parameters, input data and code produced version 12 of a registered model. Which Databricks capability records that link at training time?

G: ## Tracking is the system of record for development
Databricks recommends managing model development with MLflow. A training run logs parameters, metrics, artifacts and code snapshots to the MLflow Tracking server. @ DBX-MLP D2 T2.3 advanced troubleshooting
S: A unit test for a function that deduplicates transactions reads `prod.ml.transactions` and runs the function that deletes duplicate rows in place. A colleague objects. What is the right design?
A: Run the test only at night, when fewer users query the production table

Databricks says it is a best practice not to run unit tests against functions that work with data in production. This matters most for functions that add, remove or change data. @ DBX-MLP D2 T2.3 applied troubleshooting
S: A notebook job runs the lines below. The job task always shows success, even when a test fails.
```
import pytest
pytest.main([".", "-v", "-p", "no:cacheprovider"])
```
What is the fix?
A: Add the `-x` flag so that pytest stops at the first failure and the stop is reported as the status
B: Keep the return value of `pytest.main` and assert it equals 0, so a failure fails the cell
C: Install pytest with `%pip` in the same cell, so that failures stop being swallowed
D: Wrap the call in try/except and print any exception, so that failures show up in the cell output
K: B
G: ## Make failures visible to the job
`pytest.main` returns an exit code instead of raising an exception. If the notebook ignores it, the cell finishes normally and the job task is marked successful. The Databricks pattern stores the return code and asserts it:
`retcode = pytest.main([".", "-v", "-p", "no:cacheprovider"])` followed by `assert retcode == 0, "The pytest invocation failed. See the log for details."`
The assertion fails the cell, and therefore the task and the CI check. Results appear in the cluster's driver logs.
W: Asserting that the return code is 0 turns failing tests into a failing cell, so the job task and CI stage fail as intended.
X: A=The `-x` flag: it only stops after the first failed test, while the exit code is still ignored by the notebook, so the cell and task stay green.
