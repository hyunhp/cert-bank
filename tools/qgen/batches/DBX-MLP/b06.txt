@ DBX-MLP D2 T2.1 applied use-case
S: A multitask Lakeflow job runs `train`, then `validate`, then `deploy`. The validation task must evaluate exactly the model version that this run's training task registered, even when two runs execute at the same time. How should the version reach the validation task?
A: The validation task loads `models:/prod.ml.churn@champion`, because the alias always names the newest candidate version
B: The training task publishes the model URI as a task value, and the validation task reads it from the upstream task
C: The validation task calls `get_latest_versions` on the model name, because the highest version number is always the current run's
D: The training task writes the model URI to a file under `/tmp`, and the validation task reads that file from its own compute
K: B
G: ## Passing the model between pipelines
In the recommended Databricks workflow the training pipeline, the model validation pipeline and the deployment pipeline are tasks of one multitask job. The training task ends by registering the model in Unity Catalog and yields a model URI. The validation task takes that URI, loads the model from Unity Catalog and runs its checks. Databricks says to use task values (`dbutils.jobs.taskValues.set` in the producer, `.get(taskKey=..., key=...)` in the consumer) to hand the URI over.
## Why identity matters
A pipeline stage must test the artifact its own run produced. Anything that resolves "the newest" or "the current" version at read time can point to another run's model.
W: A task value is scoped to the job run, so the validation task receives exactly the URI its upstream training task produced, regardless of concurrent runs.
X: A=Champion alias: the alias points to the model already serving production, so validation would test the old release instead of the new candidate.
C=Latest version lookup: with two concurrent runs, the highest version can belong to the other run, so the wrong model is validated.
D=File in /tmp: local disk of one task's compute is not shared with the next task, which may run on different compute, so the file is not found.
T: Pass the model URI between job tasks with task values, never by resolving the latest version.
V: Lakeflow Jobs, Unity Catalog, MLflow

@ DBX-MLP D2 T2.1 advanced troubleshooting
S: The training notebook ends with `mlflow.register_model(uri, "prod.ml.churn")`. When the same job is deployed to staging for integration tests, new test versions appear in the production catalog. What is the correct fix under the deploy code pattern?
A: Keep the hard-coded name and tell staging runs to delete the extra versions after each test has finished
B: Give staging write access to the production catalog so that the registration always succeeds there
C: Duplicate the notebook for each environment and edit the model name in each copy by hand
D: Read the catalog name from an environment-specific job parameter and build the registered model name from it
K: D
G: ## One code base, one catalog per environment
In the deploy code pattern the same pipeline code runs in development, staging and production. Each environment normally corresponds to a catalog in Unity Catalog, and Databricks says to set up the pipeline code to register the model to the catalog of the environment where the pipeline runs. Assets written to the staging catalog are temporary and kept only until testing is complete.
## Parameterize, do not fork
The environment-specific value (catalog, schema, endpoint name) belongs in configuration such as job parameters or bundle variables, so reviewed code is identical everywhere.
W: Deriving the registered model name from an environment-specific parameter keeps the code identical while each run registers into its own catalog, so staging tests never touch production assets.
X: A=Cleanup after tests: the run still writes into production assets and can race with real consumers or fail when cleanup does not run, so isolation is already broken.
B=Staging write access to production: this removes the isolation between environments and lets test code change production models.
C=Per-environment copies: the code that is tested in staging is no longer the code that runs in production, which defeats code promotion.
T: Parameterize the catalog so identical code registers models into the catalog of the environment it runs in.
V: Unity Catalog, MLflow, Lakeflow Jobs

@ DBX-MLP D2 T2.1 advanced tradeoff

@ DBX-MLP D2 T2.3 applied troubleshooting
S: The function below is hard to unit test: callers sometimes get a DataFrame and sometimes a boolean.
```
def prepare(df, name):
    if name not in df.columns:
        return False
    return df.filter(col(name).isNotNull())
```
Which change follows Databricks guidance on testable functions?
A: Keep one function and return a tuple of the DataFrame and a flag
B: Split it into a function returning a boolean for column existence and one always returning the DataFrame
C: Wrap the body in try/except and return None on any failure, so that the type is at least consistent
D: Return the string "missing" when the column is absent and keep the DataFrame result otherwise

G: ## Design for tests
The Databricks unit testing page advises that, for the best results, a function should return a single predictable outcome and be of a single data type. A check for existence returns true or false. W: Two small functions each have one predictable outcome and one return type, so each is tested with simple asserts.
X: A=Tuple: one function still mixes two concerns, and every caller must unpack the pair, which keeps the test logic complicated.
C=Return None on failure: this hides real errors and adds a third possible outcome, so the function becomes less predictable.
D=String marker: the return type stays mixed (string or DataFrame), so callers and tests must still check the type.

@ DBX-MLP D2 T2.3 applied troubleshooting

```
import pytest
pytest.main([".", "-v", "-p", "no:cacheprovider"])
```

A: Add `import sys` so that pytest can write the cache files into the repository

By default pytest looks for `.py` files whose names start with `test_` (or end with `_test`) and, inside them, for functions whose names start with `test_`. @ DBX-MLP D2 T2.4 applied definition
S: A model team reviews three automated checks. One calls a feature function on a three-row DataFrame and asserts the result. One triggers the feature, training and inference pipelines in sequence against the staging catalog. One sends a few requests to a temporary staging endpoint. Which classification is right?
A: The first is a unit test, and the second and third are integration tests
B: The first and second are unit tests, because they run on small data, and the third is a load test
C: All three are integration tests, because each runs in the staging workspace
D: The first and third are unit tests, because they use test data, and the second is a system test
K: A
G: ## Unit versus integration
A unit test checks a self-contained unit of code, such as a function, in isolation, using fake input. An integration test runs the pipelines together (feature engineering, training, inference, monitoring) to prove that they work correctly together. When the application is real-time, the integration test also creates serving infrastructure by triggering the deployment pipeline and may send small requests to a temporary endpoint.
## Size is not the criterion
A check is an integration test because it exercises hand-offs between components, not because of the environment or data volume. Data volume can be reduced in integration tests to save time.
W: The three-row function check isolates one unit, while the pipeline sequence and the temporary endpoint check exercise several components together, which defines integration tests.
X: B=Small data: reduced data does not turn a pipeline run into a unit test, which is defined by isolation of a function.
C=Environment: the location does not define the type. A function test can run in staging and remains a unit test.
D=Test data and system test: the endpoint request tests the serving path of the pipeline, and the sequence is an integration test by the documented definition.
T: A unit test isolates a function, an integration test runs pipelines or endpoints together.

@ DBX-MLP D2 T2.4 applied tradeoff
S: Twelve data scientists open pull requests against the same main branch every day. Each pull request passes its integration tests, but the pipeline sometimes breaks on main after several merges. What does Databricks suggest in addition?
A: Require every pull request to wait for the previous one to merge, and drop all integration tests from CI

C: Merge without integration tests and rely on production monitoring to catch the failures
D: Schedule periodic integration tests on the main branch to catch interactions between merged changes
K: D
G: ## Concurrent changes
Each pull request is tested against the main branch as it was when the test ran. When many users merge concurrently, two individually passing changes can interact badly. Databricks notes that you can schedule periodic integration tests on the main branch, which is a good idea if the branch is updated frequently with concurrent pull requests from multiple users. If tests fail, the CI/CD system should notify users and post results on the pull request.
W: Scheduled integration tests on main run the combined state of all merged changes and surface conflicts that no single pull request test could show.
X: A=Serial merging, no integration tests: serialization slows the team and without integration tests, interface breaks still go undetected.
B=Release branch only: the release branch triggers the production update, so defects would be found after main is already broken.
C=Monitoring as test: production monitoring detects effects on real users and not pipeline faults before release, which is the purpose of staging.

@ DBX-MLP D2 T2.4 applied use-case
S: Integration tests on a pull request fail in the inference stage. The CI system currently only turns its status red. What should the CI/CD system also do, according to Databricks guidance, before the code can reach the main branch?
A: Merge the change anyway and open a ticket, because inference failures are repaired after release
B: Rerun only the unit tests until the status turns green, then merge the change automatically
C: Notify the users and post the results on the pull request, and merge only after the tests pass
D: Delete the pull request branch and ask the author to create the change again from the main branch
K: C
G: ## Failure handling in CI
In the staging stage the new code is merged into the main branch only if all tests pass. If tests fail, Databricks says the CI/CD system should notify users and post results on the pull request. The author then sees which stage failed (here inference) and fixes the branch, while main stays releasable.
## Why the result belongs on the pull request
The pull request is where review happens, so the evidence of which pipeline stage failed is attached to the change that caused it.
W: Notifying users and posting the results on the pull request tells the author which stage failed and keeps the change out of main until all tests pass.
X: A=Merge anyway: broken inference code would reach main and then the release branch, where production jobs are updated from.
B=Rerun unit tests: the failure is in an integration stage, and unit tests do not exercise the hand-offs between pipelines, so a green unit run proves nothing about it.
D=Delete the branch: the author loses the history needed for debugging, and the failure feedback is still not delivered.
T: On failing tests, notify users and post results on the pull request, and do not merge.
