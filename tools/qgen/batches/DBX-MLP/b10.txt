@ DBX-MLP D2 T2.18 applied use-case
S: A profile already stores the custom aggregate metric `squared_avg` (the mean of squared values of `f1` and `f2`). The team now wants the root mean square of the same columns in the metric tables, without scanning the monitored table again. How should the metric be defined?
A: As another aggregate metric with `sqrt(avg(f1*f1))`, stored in the drift metrics table because it is a transformation of a value
B: As a derived metric with `sqrt(squared_avg)`, stored in the profile metrics table and computed from the existing aggregate values
C: As a drift metric with `sqrt({{current_df}}.squared_avg)`, stored in the drift metrics table next to the other drift statistics
D: As a derived metric that reads `f1` and `f2` from the primary table, because derived metrics may use both columns and earlier metrics
K: B
G: ## Three kinds of custom metric
Data profiling (documented earlier as Lakehouse Monitoring, which the exam guide still calls it) adds your own metrics to the two metric tables it writes. A metric is a `MonitorMetric` whose `type` decides where it reads and where it is stored.
- Aggregate: computed from columns of the monitored (primary) table; stored in the profile metrics table.
- Derived: computed from aggregate or derived metrics that already exist; it does not read the primary table; stored in the profile metrics table.
- Drift: compares aggregate or derived values of two windows, or of the primary table and the baseline; stored in the drift metrics table.
## Why it matters
Only aggregate metrics touch the primary table. Documentation recommends derived and drift metrics where possible, since they reuse values that are already computed and avoid another pass over a large table.
```python
MonitorMetric(type=MonitorMetricType.CUSTOM_METRIC_TYPE_DERIVED,
  name="root_mean_square", input_columns=["f1", "f2"],
  definition="sqrt(squared_avg)",
  output_data_type=T.StructField("output", T.DoubleType()).json())
```
W: Derived metric: the definition names the stored aggregate `squared_avg`, so no data of the primary table is read, and the result lands in the profile metrics table.
X: A=Second aggregate: it would work, but it rescans the primary table, and aggregate results are stored in the profile metrics table, not the drift metrics table.
C=Drift metric: drift metrics compare two windows or a baseline; a square root of one window is not a comparison and would belong in the profile metrics table.
D=Derived on raw columns: a derived metric does not use primary table data; a definition that reads raw columns is an aggregate.
T: Derived metrics build on stored aggregates (profile metrics table), drift metrics compare windows (drift metrics table), aggregates alone scan the table.

@ DBX-MLP D2 T2.18 advanced troubleshooting
S: An inference profile for a regression model should track the share of rows where the absolute error exceeds 5 units in every window. An engineer proposes a derived metric built from the existing `avg` and `count` statistics of the prediction and label columns. Why does this not work, and what is the correct definition?
A: Derived metrics only accept one input column; the engineer should define two derived metrics, one per column, and subtract them in the dashboard query
B: Drift metrics hold all per-row results of the windows; define a drift metric over `{{current_df}}` and `{{base_df}}` that counts the rows above 5 units
C: Averages cannot recover per-row errors; define an aggregate metric with `input_columns=[":table"]` and `avg(CASE WHEN abs({{prediction_col}} - {{label_col}}) > 5 THEN 1 ELSE 0 END)`
D: Averages of prediction and label give the exact error share; the engineer only has to set a different `output_data_type`, such as an integer type
K: C
G: ## Which metric type can see rows
A derived metric is a function of numbers that were already computed per window. The mean of predictions and the mean of labels cannot tell how many individual rows had a large difference, because many different row-level errors share the same two means.
## Multi-column aggregates
A metric that needs several columns uses `input_columns=[":table"]`, and in an inference profile the Jinja parameters `{{prediction_col}}` and `{{label_col}}` are replaced with the profile's prediction and label column names. The result is a column in the profile metrics table on the row where `column_name` is `:table`.
W: Aggregate over the table: only an aggregate metric evaluates a row-level condition, and the Jinja parameters keep the definition independent of the real column names.
X: A=Two derived metrics: nothing limits derived metrics to one column, and subtracting two means still would not give a share of rows above a threshold.
B=Drift metric: drift metrics compare values of two windows or the baseline and are stored in the drift metrics table; they do not hold per-row results.
D=Output data type: the type only describes the stored value; the means cannot reproduce a row-level count, whatever type is chosen.
T: A row-level condition needs an aggregate metric; derived metrics can only recombine numbers that already exist.

@ DBX-MLP D2 T2.18 advanced troubleshooting
S: A team wants a custom metric that multiplies each row's churn probability by `margin` from the table `finance.dim_margin`. The definition below is rejected. What is the supported fix?
`definition="avg(p.churn_prob * m.margin) FROM main.ml.scores p JOIN finance.dim_margin m USING (cust_id)"`
A: Make `margin` a column of the monitored table (join upstream or monitor a view that contains it) and write `avg(churn_prob * margin)`
B: Move the join into the Jinja template with `{{base_df}}`, which can read a second table because it stands for the baseline data
C: Keep the join, but declare the metric as derived so that the second table is read at refresh time rather than the monitored table of the profile
D: Split the expression into two metrics on each table and subtract them, because each metric may read one table without joining
K: A
G: ## What a definition can contain
The `definition` of a custom metric is a Jinja template for a single SQL column expression over the monitored table. It cannot contain joins or subqueries. Data that lives in another table therefore has to be present in the monitored table, or in a view over it, before the refresh.
## Design choice
Joining upstream (or using a view) keeps the metric an ordinary aggregate that is cheap to evaluate, and keeps the logic of the join in a pipeline that can be tested, instead of inside a metric string.
W: Add the column to the monitored data: the expression stays a plain column expression, which is what the definition format allows.
X: B=Baseline template parameter: `{{base_df}}` stands for the baseline data in drift definitions; it does not open access to other tables.
C=Derived metric: a derived metric is computed from existing metrics and cannot read tables at all, so the join would not be allowed there either.
D=Two metrics subtracted: each metric still sees only the monitored table, and a difference of two averages is not the average of products.
T: A custom metric is a join-free column expression; bring other tables in through the monitored table or a view.

@ DBX-MLP D2 T2.18 advanced use-case
S: A profile has the custom aggregate metric `weighted_error`. The team needs to know how much it moved against the previous window and against the baseline table, and to alert on both. Which implementation fits?
A: A second aggregate metric that subtracts `weighted_error` from itself, stored in the profile metrics table with one row per window
B: A derived metric with `{{current_df}}.weighted_error - {{base_df}}.weighted_error`, stored in the profile metrics table
C: A drift metric that uses `{{current_df}}` and `{{base_df}}` with `weighted_error`, stored in the drift metrics table for both comparison types
D: A job that reads the profile metrics table and writes differences to a separate Delta table, since profiles cannot compute differences of custom values
K: C
G: ## Custom drift metrics
A drift-type custom metric compares an aggregate or derived metric between two windows, or between the primary table and the baseline table. In the definition, `{{current_df}}` and `{{base_df}}` refer to the current window and to the comparison window, which is the baseline or the previous window.
```python
MonitorMetric(type=MonitorMetricType.CUSTOM_METRIC_TYPE_DRIFT,
  name="error_rate_delta", input_columns=[":table"],
  definition="{{current_df}}.weighted_error - {{base_df}}.weighted_error",
  output_data_type=T.StructField("output", T.DoubleType()).json())
```
Drift metrics are stored in the drift metrics table, where `drift_type` says whether a row compares to the baseline or to the previous window, and the alert on it can read that table.
W: Drift metric: the platform evaluates it for every comparison it already makes and stores the value in the drift metrics table, so one definition serves both comparisons.
X: A=Aggregate subtraction: an aggregate sees one window of the primary table and cannot subtract another window; its results would also be in the profile metrics table.
B=Derived with window references: derived metrics are computed inside one row of the profile metrics table and cannot refer to a comparison window.
D=External job: it would work as a workaround, but profiles do compute custom differences natively, and a job adds a pipeline to maintain.
T: A change of a metric between windows or against the baseline is a drift-type custom metric in the drift metrics table.

S: A profile defines `squared_avg` with `input_columns=["f1", "f2"]` and `avg_diff_f1_f2` with `input_columns=[":table"]`. An analyst queries the profile metrics table. Where does each metric show a value?
A: Both appear as separate rows, with `column_name` set to the metric name, so a filter on `column_name` is required
B: Both appear only on the rows of columns `f1` and `f2`, since `:table` is not allowed for custom metrics
C: Both appear as columns that are filled only in the `:table` row, as every custom metric describes the whole table

G: ## Where custom metrics land
The `name` of a custom metric becomes a column in the metric table. The `input_columns` list says for which rows (`column_name` values) the metric is computed. A list of column names gives one value on each of those column rows. The special value `:table` means the metric uses several columns together, and it is computed once per window and slice on the row whose `column_name` is `:table`. Model quality metrics use the same row.
## Query
```sql
SELECT window.start, column_name, squared_avg, avg_diff_f1_f2
FROM main.ml.t_profile_metrics WHERE slice_key IS NULL
```
W: Metric names are columns, and `input_columns` selects the rows: per-column metrics on their column rows, multi-column metrics on the `:table` row.
X: A=Metric name as a row: names are columns of the table; `column_name` holds the monitored column or `:table`.
B=Only column rows: `:table` is a documented value of `input_columns`, used for metrics over more than one column.
C=Everything on the table row: a metric over listed columns is computed for each of them, so it has a value on each listed column's row.
T: The metric name is the column; `input_columns` picks the row (`f1`, `f2`, or `:table` for multi-column metrics).

@ DBX-MLP D2 T2.19 applied use-case
S: An inference profile should report quality for each combination of `region` and `device_type` (EU/mobile, EU/web, US/mobile, ...). The engineer sets `slicing_exprs=["region", "device_type"]`. The result only shows slices for single regions and single device types. What is needed?
A: Increase the granularity to one hour, which forces slices of more than one column to be formed from smaller time windows
B: Add a second profile for the same table, because one profile can only evaluate one slicing expression in a refresh
C: Add a column such as `region_device` (or a single expression that combines both) to the data and list it in `slicing_exprs`
D: Set the model id column to `region`, so that an inference profile slices on the second expression within each model id
K: C
G: ## How slicing works
Each expression in `slicing_exprs` defines slices through a single slice key: `["col_1", "col_2 > 10"]` gives one slice per distinct value of `col_1` and one for each outcome of `col_2 > 10`. Two separate expressions therefore never form a cross product. In the metric tables a slice is identified by `slice_key` and `slice_value`, and the whole table is `slice_key` NULL.
## Combinations
A combination is one more expression: a derived column such as `concat(region, '-', device_type)` in the monitored data, or an expression of that kind, becomes its own slice key with one slice per combination.
W: Single combined key: because each slice has one key, a combined column is the way to get region and device slices together.
X: A=Hourly granularity: granularity cuts the time axis and has no influence on how slices are formed.
B=Second profile: one profile accepts a list of expressions; the limit is that each defines its own single key, not a refresh limit.
D=Model id column: the model id adds slices per model; it does not combine the other expressions.
T: A slice has one key, so a combination of columns needs a combined column or expression.

@ DBX-MLP D2 T2.19 applied troubleshooting
S: A time series profile on `main.ml.orders` uses `slicing_exprs=["region"]` with three regions and a daily granularity. An analyst sums `count` of the column `amount` over one week from the profile metrics table and gets about twice the real number of rows. What explains this and how is it avoided?
A: Slices add rows next to the whole-table rows; filter `slice_key IS NULL` for the total, or one `slice_key` for the regional view
B: The daily granularity duplicates each day once for the profile and once for the baseline, so the baseline rows must be removed
C: Each refresh appends the full week again; the analyst should select only the most recent refresh of the table
D: Slices overlap by definition, so the counts of the three regions should be divided by the number of slices
K: A
G: ## Rows in the profile metrics table
Metrics are always computed for the entire table. If slicing expressions are present, metrics are computed again for each slice. The whole table has `slice_key` NULL and `slice_value` NULL; each slice has its key and value. The statistics of one window are therefore stored once for the total and once more for the slices.
- Summing across all rows adds the total and the slice rows: with three regions that cover all data, the sum is about double.
- To read the total, filter `slice_key IS NULL`.
- To read regions, filter one `slice_key` and group by `slice_value`.
W: Total plus slice rows: both are in the same table, so a plain sum counts the data twice; the filter on `slice_key` selects one view.
X: B=Baseline duplicates: a baseline table is compared in the drift metrics table; it does not write extra rows into the profile metrics table.
C=Repeated refresh: windows are recalculated per window and are identified by `window`, not appended as extra copies of the week.
D=Dividing by slice count: slices of a column with three values do not overlap, and the doubling comes from the whole-table rows.
T: Always filter `slice_key` (NULL for the total) before summing profile metric rows.

@ DBX-MLP D2 T2.20 applied troubleshooting
S: Users of a custom model endpoint report slow answers during the daily peak. In the Metrics tab, total latency (P99) rises sharply, request queue time (P99) is high, and model inference latency (P99) is flat and low. CPU usage is high on all replicas. What is the best action?
A: Switch the endpoint to a smaller workload size, which will shorten the queue because each replica starts faster
B: Rewrite the model code with a faster algorithm, as the time spent inside the model dominates the response time
C: Move the feature lookups to an online feature store, because lookup time is the part of the latency that request queue time measures in the metrics
D: Widen the compute scale-out range (raise the maximum, and the minimum if baseline traffic already queues) so that more requests are processed in parallel

G: ## Reading the metrics together
Endpoint health metrics are infrastructure metrics: latency, request rate, request error rate, CPU and memory usage (plus provisioned concurrency, queue time, GPU metrics). They are most useful in combination.
- Latency (ms): P50 and P99 round-trip time within Databricks (without authentication and rate limiting).
- Model inference latency: time the model spends computing a prediction, including feature store lookups.
- Request queue time: how long a request waits for a replica to start working on it. High queue time indicates the endpoint is under-provisioned, and widening the compute scale-out range can reduce it.
## Diagnosis
High total latency with high queue time and flat inference latency means requests wait, not that the model is slow.
W: Scale-out range: queued requests wait for a free replica, so more provisioned concurrency removes the waiting.
X: B=Faster algorithm: the model's own time (inference latency) is flat, so changing it would not touch the cause.
C=Online feature store: feature lookups are counted in model inference latency, which is flat; queue time measures waiting for a replica.
A=Smaller workload: less capacity per replica would add more queuing, and replica start time is not what queue time measures.
T: High queue time with flat inference latency means too little capacity; widen the scale-out range.

@ DBX-MLP D2 T2.20 applied use-case
S: An endpoint shows a rising request error rate. The metric combines 4xx and 5xx responses per second, and the team needs to know whether clients send bad requests or the service fails. Where does the split come from?
A: The request error rate chart itself, because it shows 4xx and 5xx as separate lines of the same panel
B: The CPU and memory charts, since high usage always means 5xx errors and low usage means 4xx errors
C: The build logs of the endpoint, which list every failed request with its response code for 30 days
D: The inference table, grouped by `status_code` (together with the service logs for the failing requests)
K: D
G: ## What the error metric tells
The request error rate is the number of 4xx and 5xx HTTP responses per second, computed by totalling the failed requests in a minute and dividing by 60. It is one number, so it says that errors rose, not which kind.
## Finding the cause
- Inference table (AI Gateway-enabled): records each request and response, including the status code, in a Unity Catalog Delta table, so a query can count 4xx against 5xx per hour or per client.
- Ephemeral service logs: `stdout` and `stderr` of the model server, useful for the tracebacks behind 5xx.
- Build logs only describe the build of the environment at deployment.
4xx usually points at the clients (payload shape, authentication, schema); 5xx at the model or platform.
W: Inference table by status code: it keeps one row per request with the response status, so the error classes can be counted, and logs explain 5xx.
X: A=Separate lines: the health metric is a single combined rate of 4xx and 5xx.
B=CPU and memory: usage does not map to error classes; a 4xx caused by a wrong payload happens at any load.

@ DBX-MLP D2 T2.20 advanced use-case
S: Load tests show an average latency of 160 ms per request. The endpoint must serve a steady 250 requests per second without queueing. Using the documented sizing rule, what minimum provisioned concurrency should the scale-out range have?
A: 250, one unit per request per second, regardless of how long a request takes
B: 40, because required concurrency is the request rate multiplied by the average latency in seconds
C: 1,563, because required concurrency is the request rate divided by the latency in seconds
D: 6, because required concurrency is the latency in milliseconds divided by the request rate per second
K: B
G: ## Provisioned concurrency
Provisioned concurrency is the maximum number of parallel requests the endpoint can handle; it moves between the minimum and maximum of the compute scale-out range as traffic changes. The documentation gives the sizing rule
`required concurrency = target QPS x average latency (seconds)`
which is Little's law: requests in flight equal arrival rate times time in the system. Here `250 x 0.16 = 40`.
## Practice
Set the minimum high enough for baseline traffic without queueing, the maximum for spikes while keeping cost under control, and check the result with load tests and the queue time metric.
W: 250 x 0.16 = 40 requests in flight on average; that is the concurrency that avoids queueing at steady load.
X: A=250: that would hold if each request lasted one second; at 160 ms the number in flight is much smaller.
C=Dividing: division by the latency gives a larger number for faster models, which is the reverse of the relationship.
D=Latency over rate: the result has no unit of concurrency, and it falls as traffic rises.
T: Required concurrency is QPS times average latency in seconds; size the minimum for baseline load.

W: Separate endpoint with a controlled cutover: the contract change is released together with the clients, and nobody receives a mismatched model.

With scale to zero enabled, an entity that receives no traffic releases its compute after a period and needs a cold start (compute allocation and model load) when requests return. - Updates of the traffic split on an existing endpoint apply to existing served entities; they do not rebuild them.
- Scale to zero suits entities that tolerate a first slow request.
