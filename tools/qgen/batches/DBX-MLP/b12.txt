@ DBX-MLP D1 T1.1 advanced tradeoff
S: A telecom team keeps 3 TB of raw call events in Delta. Aggregated per subscriber, the training set becomes 2 million rows and about 1.5 GB. The model must use the monotonic constraints of LightGBM, which Spark ML tree models do not offer, and the nightly job must finish within two hours. Which design meets these constraints at the LOWEST compute cost?
A: Train a Spark ML GBTClassifier directly on the raw 3 TB of events across a large cluster, then impose the monotonic behavior afterwards by post-processing the scores
B: Aggregate the raw events with Spark into the 1.5 GB subscriber table, then convert it with toPandas and fit LightGBM with monotonic constraints on a single node
C: Fit one LightGBM model per Spark partition of the raw events with mapInPandas, then average the partition models into one ensemble used for nightly scoring
D: Start a Ray cluster on the Spark cluster and run distributed LightGBM over the raw 3 TB of events, so that every single event row contributes directly to the fit
K: B
G: ## Scale the step that is large, not every step
SparkML is the right tool when the data that the **learning algorithm** sees does not fit on one machine, or when the algorithm you need exists in Spark ML. Neither is true here:
- The raw data (3 TB) is large, but the **model's training grain is one row per subscriber**, and that table is only 1.5 GB.
- The required feature (monotonic constraints in LightGBM) is not available in Spark ML trees.
## The usual pattern
1. Use Spark for what it is good at: scanning, joining and aggregating terabytes into features.
2. Hand the small result to a single-node library (`toPandas()` on a driver with enough memory) and train there.
This keeps the expensive distributed part short and avoids paying for a cluster during training.
W: Aggregate with Spark, train on one node: Spark handles the 3 TB scan once, the 1.5 GB subscriber table fits easily in one node's memory, and LightGBM provides the required monotonic constraints.
X: A=Spark ML GBT on raw events: Spark ML trees lack monotonic constraints, post-processing does not make a model monotonic, and training on raw events uses the wrong grain at a much higher cost.
C=Per-partition models averaged: each partition sees an arbitrary slice of subscribers' events, so the models are trained on the wrong grain, and averaging independent boosted models is not equivalent to one fit.
D=Distributed LightGBM on Ray: it pays for distributed training on 3 TB of event rows, although the model is defined per subscriber and the aggregated data fits on one node.
T: Use Spark to shrink terabytes into the training grain; if the result fits on one node and needs a single-node library, train there.
V: Spark ML, Databricks Runtime ML

@ DBX-MLP D1 T1.2 advanced troubleshooting
S: A weekly job refits a Spark ML Pipeline of StringIndexer on `merchant_category`, VectorAssembler and RandomForestClassifier, and a daily job scores new transactions with the latest fitted PipelineModel. New merchant categories appear between refits, and the daily job fails with an unseen-label error. Risk rules forbid dropping any transaction from scoring, and the model must keep using the category. Which change to the pipeline definition fixes the failure from the next refit on?
A: Set handleInvalid="skip" on the StringIndexer, so that rows whose category was not seen at fit time are filtered out before they reach the assembler stage
B: Fill nulls in merchant_category with the string "unknown" before indexing, so that every value that reaches the indexer belongs to an already known label
C: Set handleInvalid="keep" on the StringIndexer, so that categories unseen at fit time map to one extra index value and every transaction is still scored
D: Replace the StringIndexer with a VectorIndexer that has a high maxCategories, so that new merchant categories are recognized automatically while scoring
K: C
G: ## What a fitted StringIndexer does with new values
`StringIndexer` learns a fixed mapping from string to index at `fit` time. When the fitted model meets a string it never saw, the `handleInvalid` parameter decides what happens:
- `error` (default): throw an exception, which is what stops the daily job.
- `skip`: drop the row.
- `keep`: put all unseen values into one extra bucket at index `numLabels`.
## Choosing under the stated rules
"No transaction may be dropped" rules out `skip`. "Keep using the category" rules out removing the column. `keep` scores every row; unseen categories share one extra index until the next weekly refit learns them properly. Tree models handle the extra index like any other value.
W: handleInvalid="keep": the fitted indexer maps every unseen category to the extra index, so the job no longer fails and no row is dropped.
X: A=handleInvalid="skip": it removes the rows with new categories, which the risk rules forbid.
B=Fill nulls with "unknown": the failing values are new non-null categories, not nulls, so they are still unseen labels after the fill.
D=VectorIndexer: it works on numeric vector columns, not on string columns, so it cannot replace the string-to-index step.
T: StringIndexer handleInvalid="keep" scores unseen categories through one extra index instead of failing or dropping rows.
V: Spark ML

Which approach meets both requirements?
A: Wrap GBTClassifier in OneVsRest, which trains one binary boosted model per queue and predicts the queue whose model gives the highest confidence
B: Set the lossType of GBTClassifier to a multinomial loss, so that the boosted trees fit all six queues jointly inside one single classification model

@ DBX-MLP D1 T1.4 advanced use-case
S: A team tunes a Spark ML GBTClassifier on 900 million rows. Nobody knows how many boosting iterations help, and a CrossValidator grid over maxIter would repeat a 3-hour fit several times, which the nightly window cannot afford. The team wants training to stop adding trees once loss on held-out rows stops improving, within one single fit. What should it configure?
A: A CrossValidator with numFolds=2 and a grid of three maxIter values, so that the search needs fewer model fits than the default number of folds
B: A checkpointInterval of 10 with a large maxIter, so that the fit writes intermediate trees and later resumes from the best saved checkpoint
C: A TrainValidationSplit with trainRatio=0.9 over several maxIter values, run with parallelism=3 so that the candidates are fitted together
D: A Boolean column that marks the validation rows, set as validationIndicatorCol with a validationTol, together with a large maxIter value
K: D
G: ## Early stopping in Spark ML boosting
`GBTClassifier` and `GBTRegressor` accept `validationIndicatorCol`: the name of a Boolean column where `false` marks training rows and `true` marks validation rows. While boosting, the algorithm measures the validation error after each iteration and stops when the improvement falls below `validationTol`. `maxIter` then acts as an upper bound, not as the number you must guess.
## Why it fits the constraints
- One fit instead of a grid: no repeated 3-hour runs.
- The stop rule uses held-out rows, which is what the team asked for.
Example: add `is_val = rand(seed=7) < 0.1`, set `validationIndicatorCol="is_val"`, `maxIter=500`.
W: validationIndicatorCol with validationTol: the single fit evaluates the marked validation rows after each tree and stops adding trees when the improvement becomes smaller than the tolerance.
X: A=Two-fold CrossValidator over maxIter: it still fits several full models (folds times grid values), which the nightly window cannot afford.
B=checkpointInterval: checkpointing truncates lineage for fault tolerance; it does not evaluate held-out loss or stop boosting early.
C=TrainValidationSplit with parallelism: it still trains one full model per maxIter value; running them together needs more cluster capacity rather than fewer fits.
T: For Spark ML boosted trees, validationIndicatorCol plus validationTol gives early stopping in one fit.
V: Spark ML

@ DBX-MLP D1 T1.5 advanced use-case
S: A logistics firm predicts one of four delivery outcomes and feeds the class probabilities, not the predicted labels, into a capacity plan that sums the expected parcels per outcome. Two Spark ML models are tuned with CrossValidator, and the chosen model must give the most trustworthy probabilities. The evaluator still uses its default metric. Which evaluator setting should drive model selection?
A: MulticlassClassificationEvaluator with metricName="accuracy", because the largest share of correct labels also yields the best probability estimates
B: MulticlassClassificationEvaluator with metricName="logLoss", which reads the probability column and penalizes confident wrong probabilities
C: MulticlassClassificationEvaluator with its default metricName="f1", which weights each class by its frequency in the evaluation data
D: BinaryClassificationEvaluator with metricName="areaUnderROC", computed once for every outcome so that each class receives its own ranking score
K: B
G: ## Match the metric to how predictions are used
When a business process **uses the probabilities themselves** (summing expected counts, pricing risk), the model must be judged on probability quality. Accuracy and F1 only look at the arg-max label, and ranking metrics (AUC) only look at order.
## Log loss in Spark ML
`MulticlassClassificationEvaluator` supports `metricName="logLoss"`; it reads `probabilityCol` and grows sharply when the model is confident and wrong. For log loss smaller is better, and `CrossValidator` reads the evaluator's `isLargerBetter()` so it still picks the right model.
The default metric of this evaluator is `f1` (weighted by class frequency), which says nothing about calibration.
W: logLoss: it scores the full probability vector of each row, so the selected model is the one whose probabilities best match observed outcomes, which the capacity plan relies on.
X: A=Accuracy: two models with equal accuracy can have very different probabilities; accuracy ignores everything but the top label.
C=Default f1: weighted F1 also judges only predicted labels and is the setting that is already failing the requirement.
D=Per-class areaUnderROC: AUC measures ranking, not whether probabilities are well calibrated, and BinaryClassificationEvaluator expects a binary label.
T: When probabilities feed a calculation, select models with a probability metric such as logLoss.
V: Spark ML

S: A feature job computes a 30-day rolling spend per customer with groupBy("customer_id").applyInPandas and pandas rolling windows. Three wholesale customers hold 40% of the 5 billion rows, and their tasks fail with out-of-memory errors, while the other tasks finish in minutes. The features feed a nightly training job. The cluster size is fixed by budget, and the features must stay exact. Which change fixes the job?
A: Replace the grouped pandas function with a Spark window function partitioned by customer_id, ordered by event time, with a 30-day range frame
B: Raise spark.sql.execution.arrow.maxRecordsPerBatch, so that each customer group reaches the Python worker in fewer but larger Arrow batches
C: Add a random salt to customer_id before applyInPandas and combine the salted partial results, so that large customers spread over many tasks
D: Switch from applyInPandas to a Series-to-Series pandas UDF, so that the rolling sum runs per Arrow batch without loading a whole group at once
K: A
G: ## Why grouped map fails on skew
`applyInPandas` hands each **whole group** to Python as one pandas DataFrame. A customer with billions of rows must fit into one Python worker's memory, whatever the Arrow batch settings are.
## Native window functions
A rolling sum is a built-in Spark operation: `Window.partitionBy("customer_id").orderBy(col("ts").cast("long")).rangeBetween(-30*86400, 0)`. X: B=maxRecordsPerBatch: that setting splits batches for scalar pandas UDFs; grouped map still loads the whole group, so the big customers still run out of memory.
C=Salted groups: a rolling window needs every earlier row of the same customer, so salting splits windows across groups and the features stop being exact.
D=Series-to-Series pandas UDF: each call sees an arbitrary batch of rows without group boundaries or order, so a correct per-customer rolling sum cannot be computed.
T: Prefer native Spark window functions for per-key rolling features; grouped pandas functions load each whole group into memory.

@ DBX-MLP D1 T1.9 advanced tradeoff
S: A team tunes a gradient-boosted model with MlflowSparkStudy and the default TPE sampler. The budget is 120 trials of about 10 minutes each, the job must finish within 3 hours, and the cluster could run 64 trials at the same time. Earlier searches showed that adaptive sampling found clearly better parameters than random sampling. Which n_jobs value balances the deadline and search quality BEST?
A: n_jobs=64, so that almost all trials start in the first two rounds and the whole search finishes in roughly twenty minutes of wall-clock time
B: n_jobs=1, so that every trial is informed by all previous results and the sampler stays fully adaptive across the entire trial budget
C: n_jobs=120, so that every trial starts at once and cluster autoscaling adds the capacity that is missing for the additional 56 trials
D: n_jobs=8, so that 15 rounds of about 10 minutes fit the deadline while most trials can still learn from many completed results
K: D
G: ## Parallelism versus adaptivity
TPE (the default sampler of `MlflowSparkStudy`) proposes the next trial from the results of **finished** trials. Trials that run at the same time cannot learn from each other.
- With n_jobs close to n_trials, most trials start before any result exists, so the search behaves almost like random sampling.
- With n_jobs=1, the search is fully adaptive but slowest.
## Work the numbers
- n_jobs=1: 120 x 10 min = 1,200 min (20 h), far past 3 h.
- n_jobs=8: 120 / 8 = 15 rounds x 10 min = 150 min, inside 180 min.
- n_jobs=64: about 2 rounds, about 20 min, but nearly no adaptivity.
The smallest parallelism that meets the deadline keeps the most adaptivity.
W: n_jobs=8: 150 minutes fits the 3-hour limit, and later trials still benefit from more than a hundred completed results.
X: A=n_jobs=64: it meets the deadline easily but launches nearly every trial without feedback, throwing away the adaptive advantage the team measured.
B=n_jobs=1: fully adaptive, but 20 hours of sequential trials miss the 3-hour deadline.
C=n_jobs=120: everything starts blind (pure random-like search), and the cluster cannot even run more than 64 trials at once.
T: With adaptive samplers, use the lowest parallelism that still meets the time budget.
V: Optuna, MLflow

@ DBX-MLP D1 T1.12 advanced use-case
S: A recommender has a 90 GB embedding table and small dense layers. It is trained with PyTorch on nodes that each have 4 GPUs with 24 GB of memory. Plain DistributedDataParallel fails with out-of-memory errors at start-up because each process holds a full model copy. The team wants to use all 16 GPUs of 4 nodes without dropping embedding rows. Which strategy addresses the root cause?
A: Shard the model parameters across the GPUs with fully sharded data parallelism or DeepSpeed ZeRO, so that no single GPU holds the whole table
B: Use gradient accumulation with a smaller per-GPU batch size, so that activations shrink until each full copy of the model fits on one GPU
C: Increase the number of DistributedDataParallel processes to 16, so that each process trains on a smaller share of the training data
D: Switch all GPUs to mixed-precision training only, so that each copy of the 90 GB table becomes small enough to fit on one 24 GB GPU
K: A
G: ## Data parallelism copies the model
`DistributedDataParallel` (DDP) gives every GPU a **full replica** of the parameters, gradients and optimizer state, and splits only the data. It speeds up training of models that fit on one GPU; it cannot help when the model itself is too big.
## Sharding the model
Fully sharded data parallelism (PyTorch FSDP) and DeepSpeed ZeRO split parameters, gradients and optimizer states across the GPUs, gathering pieces only when a layer needs them. A 90 GB table over 16 GPUs is about 5.6 GB of parameters per GPU (plus the sharded optimizer state). On Databricks, `TorchDistributor` and the DeepSpeed distributor launch such multi-node jobs.
W: FSDP or ZeRO sharding: splitting the parameters (and their optimizer state) across all GPUs removes the need for any GPU to hold the full 90 GB table.
X: B=Gradient accumulation: it reduces activation memory per step, but the 90 GB of parameters per replica still cannot fit into 24 GB.
C=More DDP processes: each extra process still holds a full model copy, so every one of them runs out of memory the same way.
D=Mixed precision alone: halving the bytes per value still leaves about 45 GB of embeddings per replica, well over 24 GB.
T: When the model does not fit on one GPU, shard it (FSDP/ZeRO); plain data parallelism only splits the data.
V: PyTorch, TorchDistributor, DeepSpeed

The team must use its existing Databricks cluster, which also runs the Spark data preparation, and log every trial to MLflow. Which approach supports this method with the LEAST custom code?

G: ## Ray and Spark have different strengths
Databricks describes Ray as strong at **logical parallelism**: dynamic, stateful, compute-heavy tasks such as reinforcement learning and tuning, while Spark excels at **data parallelism** over large datasets. Ray runs on Databricks through `setup_ray_cluster` on an existing Spark cluster.
## Population-based training
PBT needs a scheduler that can pause trials, copy checkpoints between them and mutate hyperparameters while they run. Ray Tune ships this scheduler, and Ray Tune trials can log to MLflow. Optuna pruners only stop trials; they do not exploit or copy state between trials.

B=CrossValidator grid: it fits fixed Spark ML parameter combinations independently and has no notion of pausing or exchanging state between running trials.
D=applyInPandas per member: groups run independently with no way to exchange checkpoints during training, so the population logic would have to be built by hand.
T: Stateful, dynamic tuning such as population-based training fits Ray Tune on Ray on Spark.
V: Ray on Databricks, Ray Tune, MLflow
