@ DBX-MLP D1 T1.1 applied use-case
S: A media company keeps 1.2 billion click events in a Delta table. After feature encoding the training set is far larger than the memory of the biggest node type available, and a churn-style logistic regression must be retrained nightly on the full history. Scoring later runs on the same Spark cluster. Which training approach fits these constraints?
A: Call `toPandas()` on the full training DataFrame and fit scikit-learn `LogisticRegression` on the driver, using the largest driver type available
B: Build a Spark ML `Pipeline` ending in `LogisticRegression` and fit it on the DataFrame so the rows stay partitioned across the workers
C: Train scikit-learn on a 0.1% random sample, because the rare customer segments in the business requirements are not needed for the model
D: Move the job to a single-node cluster and enlarge the swap space, so the whole training set can be paged in and fitted by scikit-learn
K: B
G: ## Why the data size decides
Single-node libraries such as scikit-learn load the whole training matrix into the memory of one machine (on Databricks, the driver). Databricks recommends keeping training on one machine when possible, because distributed code is more complex and slower from communication overhead, but says to consider distributed training when the data or model is too large to fit in memory on a single machine.
## What Spark ML adds
Spark ML (`pyspark.ml`, the DataFrame-based MLlib API) runs each algorithm as Spark jobs: rows stay in partitions on the workers, and each iteration aggregates partial results (for example gradients) instead of collecting the data. Adding workers adds memory and compute. The same `Pipeline` also runs where the data already lives, so there is no copy to the driver.
- Choose Spark ML when the training data cannot fit on one node, when the features are produced by Spark transformations on a big table, or when scoring happens inside Spark jobs.
- Choose a single node (scikit-learn, XGBoost, PyTorch) when the data fits comfortably and you need an algorithm or accuracy that Spark ML does not offer.
W: A Spark ML pipeline is the design that scales with the data. The 1.2 billion rows never leave the workers, the logistic regression is trained by the distributed solver, and the fitted `PipelineModel` can score on the same cluster.
X: A=toPandas on the driver: `toPandas()` collects every row to the driver process, so it fails with out-of-memory exactly because the data is larger than the largest node.
C=0.1% sample: a sample can be a valid choice when a learning curve is flat, but here the requirement explicitly needs the full history and rare segments, and a 0.1% sample would drop them.
D=Swap space: paging a training matrix from disk makes each pass over the data orders of magnitude slower and is not a supported way to extend memory; it does not give a usable nightly job.
T: When the training data does not fit on one node, use a distributed library such as Spark ML; otherwise stay on a single node.
V: Spark ML, Delta Lake

@ DBX-MLP D1 T1.1 advanced tradeoff
S: A pricing team has a 3 GB table of features. Their best model so far is a scikit-learn `HistGradientBoostingRegressor` tuned by hand, and no Spark ML regressor has matched its error on this data. The team asks whether to rewrite training as a Spark ML pipeline "because the platform is Spark". What should the ML engineer recommend?
A: Rewrite it as a Spark ML `GBTRegressor` on a 16-worker cluster, since distributed training is faster for tree ensembles
B: Keep scikit-learn but run `fit` inside a `mapInPandas` call so that the data is split over the workers and each worker trains a part of the model
C: Convert the model to a Spark ML `LinearRegression`, because linear models are the only family that can be trained on Spark clusters
D: Keep scikit-learn on a single-node cluster, prepare features in Spark and read them with `toPandas()`, and move to Spark ML if the data outgrows memory
K: D
G: ## Fit the tool to the data and the algorithm
The 3 GB table fits easily in memory on one node. Distributed training pays communication and scheduling costs in every iteration, so for data this small a single node is usually faster and simpler. A model that already beats the Spark ML alternatives is a second reason to keep it.
## A common split of work
- Use Spark for what it is good at: reading, joining and aggregating the large source tables into a feature table.
- Convert the finished feature table to pandas (`toPandas()` or the Spark-to-pandas Arrow path) and train on a single node with the library the team trusts.
- Revisit Spark ML or another distributed option (Ray, TorchDistributor for neural networks) only when the data or model no longer fits on one machine.
W: Preparing features in Spark and training scikit-learn on a single node keeps the better algorithm, avoids distribution overhead on 3 GB, and leaves a clear trigger (data outgrowing memory) for moving to Spark ML.
X: A=Rewrite as GBTRegressor: distributed training is not always faster. On 3 GB the per-iteration communication outweighs the gain, and the team has measured that Spark ML does not reach the same error.
B=Training inside mapInPandas: `mapInPandas` runs a function on each partition independently, so each worker would train its own separate model on a slice; it does not combine them into one model.
C=Linear regression only: Spark ML has many families (trees, ensembles, GBT, ALS, KMeans); the claim is false, and switching to a linear model would likely lose accuracy.
T: When the data fits on one node and the single-node algorithm is better, use Spark for data preparation and train on a single node.
V: Spark ML, scikit-learn

@ DBX-MLP D1 T1.1 applied use-case
S: A telecom team trains on 300 GB with a `StringIndexer`, a `VectorAssembler` and a random forest. The same feature logic and model must run on historical backfills and on events read from a Kafka source with Structured Streaming, without a separate serving endpoint and without re-implementing the encodings in another language. Which design matches?
A: Train a Spark ML `Pipeline`, keep the fitted `PipelineModel`, and call its `transform` on the streaming DataFrame inside the streaming query
B: Train scikit-learn on a sample and score each micro-batch by calling `toPandas()` on it inside `foreachBatch` on the driver
C: Train a Spark ML model but copy its coefficients into a hand-written UDF, so that the streaming query does not depend on Spark ML classes
D: Call `fit` on the streaming DataFrame so that the `PipelineModel` keeps learning from every micro-batch while it scores
K: A
G: ## Spark ML stages are DataFrame operators
A fitted `PipelineModel` is a chain of `Transformer`s. Each stage's `transform` takes a DataFrame and returns a DataFrame with extra columns, and that works on both batch and streaming DataFrames. The indexer mapping, the assembler and the forest therefore run inside the Spark engine, once for backfills and once for the stream, from one saved artifact.
## What does not work
- A streaming DataFrame cannot be passed to `fit`: estimators need to read the data several times, which a stream does not allow. Fit on a batch DataFrame (historical data) and apply the resulting model to the stream.
- Models do not learn online in Spark ML; retraining is a separate job that produces a new `PipelineModel`.
W: Applying the fitted `PipelineModel` with `transform` on the streaming DataFrame reuses the exact same encodings and model for batch and stream, runs distributed, and needs no extra endpoint.
X: B=toPandas in foreachBatch: it pulls each micro-batch to the driver, loses the distributed scoring, and a model trained on a sample plus hand-ported encodings reintroduces the training-serving gap.
C=Coefficients in a UDF: a random forest has no coefficient vector, and even for linear models a hand copy breaks the single artifact and drifts from the trained pipeline.
D=fit on a stream: Spark ML estimators cannot be fitted on streaming DataFrames, and a fitted model does not update itself with new micro-batches.
T: Fit on batch data, then apply the fitted PipelineModel to batch and streaming DataFrames alike.
V: Spark ML, Structured Streaming

@ DBX-MLP D1 T1.1 advanced tradeoff
S: A 1 TB Delta table feeds a gradient-boosted tree model. A learning curve shows validation error flat once the training set exceeds roughly 2% of the rows (about 20 GB), and the team has a tuned XGBoost model for this problem. Spark ML training on the full table takes hours on a large cluster. Which plan is the best trade-off?
A: Train the Spark ML `GBTClassifier` on all 1 TB, since more rows can only improve the model and the cluster is already paid for
B: Add more workers to the Spark ML job until the full-data run takes minutes, and accept the higher cost because only the runtime was a concern
C: Sample about 5% of the rows with Spark, train the tuned XGBoost model on a single large node, and re-check the curve when the data changes
D: Split the table by month and train 24 separate Spark ML models, then average their predictions, which makes each fit smaller
K: C
G: ## Use the learning curve
A learning curve plots validation error against training-set size. When the curve is flat, extra rows add cost without adding accuracy. Training on a representative sample on one node can then give the same quality at a fraction of the cost, and lets the team use an algorithm that is only available as a single-node library.
## Conditions for this trade-off
- The sample must be representative (stratified on the label or key segments if they are rare).
- The learning curve must be re-checked when the data or the problem changes, because the plateau can move.
- If rare segments need the full history, or the curve is still falling, Spark ML (or another distributed option) on the full table is justified.
W: A sample past the plateau keeps accuracy, cuts compute from hours of cluster time to a single node, and lets the team keep XGBoost. Re-running the learning curve guards against distribution change.
X: A=Train on all 1 TB: the curve shows more rows do not lower validation error here, so the cost buys nothing and the team gives up its tuned model.
B=Add workers: scaling out reduces wall-clock time but not cost per unit of accuracy, and it does not address that the extra data is not improving the model.
D=24 monthly models averaged: this changes the problem (each model sees one month and misses seasonal or cross-month patterns) and the averaged ensemble is not a drop-in for the original model.
T: A flat learning curve means a representative sample on one node can match full-data distributed training at far lower cost.
V: Spark ML, XGBoost

@ DBX-MLP D1 T1.1 applied troubleshooting
S: After a scikit-learn `RandomForestClassifier(n_jobs=-1)` job moved from a single-node cluster to a cluster with one driver and 16 workers, the training time did not change at all and the worker CPU utilization stays near zero. What explains this?
A: The workers are not attached to the notebook until `spark.conf.set("spark.ml.distributed", "true")` is set
B: scikit-learn runs in the Python process of the driver, so only the driver cores are used and the workers have no part of the fit
C: `n_jobs=-1` limits scikit-learn to one process per Spark executor, and the executors must first be restarted
D: The Delta table was read with too few partitions, so the workers were never scheduled; repartitioning to 16 would spread the fit
K: B
G: ## Where single-node libraries run
Libraries such as scikit-learn, XGBoost (single-node) and PyTorch on one device execute in the Python process where the code is called, which is the driver of a Databricks cluster. Spark does not distribute them automatically. A cluster with workers helps only if the code uses Spark APIs (Spark ML, Spark SQL, pandas function APIs) or a distributed framework (Ray, TorchDistributor, `joblibspark` for parallel trials).
## Options for using more machines
- Use one bigger single node when the data fits, since the fit then uses all of its cores.
- Switch to Spark ML (or a distributed variant of the algorithm) when the data no longer fits.
- Parallelize independent trials or per-group models, not one model fit, with pandas function APIs, Ray or Optuna on Spark.
W: The fit is plain scikit-learn in the driver process, so extra workers sit idle. Choose a bigger single node, a distributed algorithm, or parallelize many independent fits.
X: A=Config flag: there is no such Spark setting; workers are already part of the cluster, they just are not used by non-Spark code.
C=n_jobs per executor: `n_jobs` sets processes or threads inside the one Python process, not executors, and restarting executors changes nothing.
D=Repartitioning: partition count affects Spark jobs, but the scikit-learn fit does not run on Spark partitions at all, so repartitioning does not move the work.
T: Single-node libraries run on the driver only; extra workers help only with Spark or distributed frameworks.
V: scikit-learn, Databricks Runtime ML

@ DBX-MLP D1 T1.1 applied comparison
S: A team compares two prototypes on a 5 GB table: scikit-learn on a single-node cluster trains in 40 seconds, while the same algorithm in Spark ML on 10 workers takes 6 minutes. Management asks whether Spark ML is just configured badly. Which explanation is most accurate?
A: For data that fits in memory, fixed costs of distributed training (task scheduling, shuffles, network aggregation) can dominate, so one node is faster
B: Spark ML always reads the data twice as often as scikit-learn, so it is expected to be slower at every data size and cluster size
C: Spark ML uses only the driver for tree algorithms, so adding workers cannot reduce the runtime at any data size
D: The result shows that the 10 workers are too small, and doubling the cluster would bring Spark ML below the single-node time at this data size
K: A
G: ## Distribution has overhead
A distributed algorithm splits rows over workers, computes partial results, and combines them over the network at every iteration or tree level. Scheduling tasks and moving partial results costs time that does not shrink with more workers. If one node holds the data and has enough cores, the single-node library avoids these costs.
## When the picture changes
- When data no longer fits in the memory of one node, single node is not an option and Spark ML scales better.
- When the number of rows or features grows large, the compute per iteration grows and the fixed overhead becomes small in comparison.
- A cluster-size increase helps only when per-task work, not overhead, is the bottleneck.
W: With 5 GB the compute is small and the overhead of the distributed algorithm dominates, so the single node wins. Spark ML pays off when the data outgrows one machine.
X: B=Always slower: it is not true at every size. Past the memory limit of a single node, scikit-learn cannot run at all and Spark ML wins.
C=Driver-only trees: Spark ML tree algorithms distribute the work to executors, which is why they scale to large data.
D=More workers: adding workers increases coordination, and for small data it can make the run slower rather than faster.
T: For data that fits on one node, distribution overhead makes a single node faster; Spark ML pays off beyond the memory of one machine.
V: Spark ML, scikit-learn

@ DBX-MLP D1 T1.2 applied troubleshooting
S: A training job saves a fitted model with `model.write().overwrite().save(path)`, where `model = pipeline.fit(train)`. A scoring job loads it with `Pipeline.load(path)` and calls `transform(batch)`, which raises an `AttributeError` for `transform`. What is the fix?
A: Replace `Pipeline.load` with `PipelineModel.load(path)`, because the saved artifact is the fitted model
B: Call `fit(batch)` on the loaded object first so that the stages learn the batch schema, then call `transform`
C: Save with `pipeline.write().save(path)` instead, because only an unfitted `Pipeline` can be restored in another job without version conflicts
D: Load the path as a single `LogisticRegressionModel`, since a saved pipeline always stores only its last stage
K: A
G: ## Two classes, two roles
`Pipeline` is an `Estimator`: it holds stages and its `fit(df)` returns a `PipelineModel`. `PipelineModel` is a `Transformer`: it holds the fitted stages (learned indexer mappings, scaler statistics, the trained model) and offers `transform`.
## Persistence
Both can be saved and loaded (ML persistence). Loading must use the matching class: `Pipeline.load` for an unfitted pipeline and `PipelineModel.load` for a fitted one. The scoring job needs the fitted artifact, so it must load `PipelineModel`.
## Why not refit
Calling `fit` in scoring would relearn mappings and scaler statistics from the scoring batch, which breaks consistency with training.
W: The saved path holds a fitted `PipelineModel`; loading it with `PipelineModel.load` restores all learned state and exposes `transform`.
X: B=Fit on the batch: that would learn new statistics from the scoring data and produce a different model; the loaded object also has no `transform` to call after a mismatched load.
C=Save the unfitted pipeline: an unfitted pipeline has no learned state, so scoring would again need training data.
D=Last stage only: a saved `PipelineModel` stores every stage in order, which is why loading the whole model reproduces the feature steps.
T: Save and load the fitted artifact as `PipelineModel`; `Pipeline` is the unfitted recipe.
V: Spark ML

@ DBX-MLP D1 T1.2 applied use-case
S: The feature `ctr = clicks / impressions` is added with `df.withColumn("ctr", ...)` in the training notebook, and the logistic regression pipeline is fitted on the result. The scoring team receives the saved `PipelineModel` and finds the model fails because `ctr` is missing from the raw tables. How should the training code be changed so the logic travels with the model?
A: Document the formula in the model description so that each consuming team can add the column before scoring
B: Write `ctr` to the raw table in a nightly job so that all consumers read it, and keep the notebook step unchanged for training runs
C: Create a Python UDF in the scoring job that computes `ctr`, and register it under the same name as the column
D: Add a `SQLTransformer` stage (`SELECT *, clicks / impressions AS ctr FROM __THIS__`) as the first stage, so the saved `PipelineModel` computes it
K: D
G: ## Keep feature logic inside the pipeline
Anything computed outside the pipeline must be repeated by hand at scoring, and the two copies drift. Spark ML offers stateless `Transformer` stages for row-level logic. `SQLTransformer` runs a SQL statement in which `__THIS__` stands for the input DataFrame, so a derived column becomes a stage of the `Pipeline`. It is saved and loaded with the `PipelineModel`.
## Rules of thumb
- Row-level derived columns (ratios, flags, date parts): `SQLTransformer`.
- Anything that has to learn from the data (scaling, indexing, imputing): an Estimator stage whose fitted state is stored in the model.
- Logic that cannot be expressed in a stage belongs in a documented, versioned feature pipeline, not in an ad hoc notebook cell.

B=Nightly job on the raw table: this adds a second pipeline that must stay in step with the model, and the column stays absent for any source that is not that table.
C=Scoring-side UDF: it duplicates the logic in a second place and can differ in null and division-by-zero handling from the notebook version.
T: Put row-level feature logic in the pipeline (SQLTransformer) so the saved PipelineModel reproduces it.
V: Spark ML

@ DBX-MLP D1 T1.2 advanced tradeoff
S: A pipeline for 200 million rows has `VectorAssembler`, `StandardScaler`, `StringIndexer` and a random forest. The team tunes with `CrossValidator(numFolds=3)` and wants to avoid recomputing the featurization for every fold and parameter combination. Which stages can they safely fit or run once outside the cross-validated estimator?
A: Only stateless stages such as `VectorAssembler`; the `StandardScaler` and `StringIndexer` must stay inside so each fold fits its own statistics
B: All featurization stages, because the scaler and indexer are unsupervised and cannot leak label information
C: None of them, because `CrossValidator` rejects a `Pipeline` that has been partly fitted and requires an unfitted estimator
D: The `StringIndexer` and `StandardScaler`, but not the `VectorAssembler`, since only stages that learn from data are deterministic
K: A
G: ## Where leakage enters
Estimator stages learn from data: `StandardScaler` stores mean and standard deviation, `StringIndexer` stores the category mapping. If they are fitted on the whole training set before cross-validation, every validation fold has influenced those values. The effect is small for a scaler but real, and the reported metric is slightly optimistic. It becomes serious for supervised preprocessing (target encoding, feature selection).
## Practical rule
- Put learning stages inside the `Pipeline` passed to `CrossValidator`, so each fold fits them on its own training split.
- Stateless transformers (`VectorAssembler`, `SQLTransformer` with row-level logic) learn nothing, so applying them once, before cross-validation, gives identical results and saves repeated work.
- The extra cost of fitting scalers and indexers inside every fold is usually small compared with fitting the forest.
W: Only stateless stages can be hoisted out without changing the results; stages that learn statistics stay inside so every fold fits them on its own training split.
X: B=All stages are safe: the claim that unsupervised stages cannot leak is wrong; fitting on the full set lets validation rows shape the statistics, and the habit leads to real leakage with supervised preprocessing.
C=CrossValidator rejects it: `CrossValidator` accepts any `Estimator`, including a `Pipeline`; it also happily takes a pipeline whose first stages were applied to the data beforehand.
D=Learning stages outside: this reverses the rule; stages that learn from data are exactly the ones that must be fitted per fold, while the deterministic assembler is the one that is free to move.
T: Hoist only stateless transformers out of cross-validation; keep stages that learn from data inside the cross-validated pipeline.
V: Spark ML

@ DBX-MLP D1 T1.2 applied use-case
S: Several models (churn, upsell, support risk) share one featurization: indexing four categorical columns, one-hot encoding them, and assembling a vector. The team wants one reusable, fitted artifact for the shared featurization and separate model stages per use case. Which design applies Spark ML correctly?
A: Fit the shared stages once with `fit` and call `collect()` on the result, then rebuild a `Pipeline` per model from the collected rows
B: Create three copies of the same stage objects and put one copy into each `Pipeline`, because a stage instance may be used in only one pipeline
C: Build a featurization `Pipeline` and use it as the first stage of each model `Pipeline`, since a `Pipeline` is itself an `Estimator`
D: Replace the shared stages by a `PipelineModel` object in the stage list of each model pipeline after calling `fit`
K: C
G: ## A Pipeline is an Estimator
A `Pipeline` has `fit` and returns a `PipelineModel`, so it is an `Estimator` and can be a stage in another `Pipeline`. The outer `fit` fits the nested pipeline (producing a nested `PipelineModel`) and passes its output to the later stages.
## Why this helps
- The shared featurization is defined in one place and versioned once.
- Each model pipeline is `Pipeline(stages=[featurization, classifier])`, so the saved outer `PipelineModel` is a single artifact that scores raw columns.
- Tuning with `CrossValidator` still re-fits the nested stages per fold, as needed to avoid leakage.
## When to separate
If many models must use the same fitted encodings (for instance, identical index values), fit the featurization once, save the `PipelineModel`, and reuse it as a transformer stage; accept that tuning then does not refit it.
W: Using the featurization `Pipeline` as the first stage of each model pipeline keeps one definition and gives a self-contained artifact per model.
X: A=Collect and rebuild: `collect()` moves the data to the driver, and rebuilding pipelines from rows throws away the fitted stage state and does not scale.
B=Three stage copies: sharing a stage definition is exactly what nesting a pipeline provides; copying objects gives three diverging definitions, and the claim about single-use is not a rule.
D=Fitted PipelineModel in the stage list: a fitted `PipelineModel` is a `Transformer` and can be placed as a stage, but then it is fixed to the training data of the first fit, and the option as written replaces rather than reuses the definition.
T: A Pipeline is an Estimator, so a shared featurization Pipeline can be the first stage of many model pipelines.
V: Spark ML

@ DBX-MLP D1 T1.2 advanced tradeoff
S: A weekly job refits a whole `Pipeline` (`StringIndexer` on `merchant_category`, then a model) and also writes the indexed column to a Delta feature table that other teams read. After a refit, an older downstream model started producing wrong predictions, although the indexer code did not change. What is the most robust fix?
A: Set `stringOrderType="alphabetAsc"` on the indexer, which keeps the indices identical across refits even when new categories appear
B: Increase `maxCategories` on the indexer so that it learns every category and keeps the old indices stable
C: Store the raw category in the shared table and apply each model's fitted `PipelineModel` at read time, so the index mapping matches that model
D: Refit the indexer on 10% of the data, because indices only depend on the sample size, not on the content
K: C
G: ## Indices are learned state
`StringIndexer` is an `Estimator`: `fit` computes a mapping from category to index (by default ordered by frequency, most frequent first). When the data changes, frequencies and categories change, so the next `fit` can assign different numbers to the same category. A model trained on the old numbers then receives indices with a different meaning.
## Design consequences
- Treat indexed values as private to the fitted model, not as shared data. Store raw values and let each model's `PipelineModel` map them at scoring time.
- Alphabetical ordering makes the order deterministic for a fixed set of categories, but a new category still shifts alphabetical positions of the ones after it.
- If an indexed column must be shared, fit the indexer once, version the fitted model, and reuse it without refitting.

B=maxCategories: that is a `VectorIndexer` parameter for deciding which vector features are categorical, not a stability setting for `StringIndexer`.
D=Fit on a 10% sample: the mapping depends on the content of the data used, not on the sample size, and a sample would miss rare categories too.
T: Index mappings are learned model state; share raw values and apply each model's own fitted pipeline.
V: Spark ML

@ DBX-MLP D1 T1.3 applied use-case
S: A support-ticket model must predict the priority labels "low", "medium" and "high" stored as strings. Fitting a `LogisticRegression` on the string label column fails, and downstream reports need the original strings in the prediction output. Which stages solve both needs?
A: A `StringIndexer` on the label before the classifier, and an `IndexToString` stage after it that maps `prediction` back with the indexer's labels

`IndexToString` is a `Transformer` that converts indices to the original labels, using either the metadata attached to the column by the indexer or an explicit `labels` list. T: Use StringIndexer for string labels and IndexToString to turn predictions back into the original text.

S: A feature `age` must become five bins. The business wants bins with roughly equal numbers of customers in the training data, learned once and reused unchanged when scoring later batches. Which stage fits?
A: `Bucketizer` with splits computed again on each scoring batch, so the bins always follow the current customer population
B: `Binarizer` applied five times with different thresholds, each producing one bin indicator
C: `QuantileDiscretizer(numBuckets=5)` in the pipeline, which learns quantile splits and returns a `Bucketizer` with those fixed splits
D: `StandardScaler`, because z-scores split in the same way as quantiles
K: C
G: ## Estimator that learns, Transformer that applies
`Bucketizer` is a `Transformer`: you give it explicit `splits` and it maps values to bucket indices. `QuantileDiscretizer` is an `Estimator`: `fit` computes approximate quantiles of the input column and returns a `Bucketizer` model with those splits. The number of buckets can be smaller than requested if the input has too few distinct values.
## Why it matters for scoring
The splits are learned once from the training data and stored in the fitted `PipelineModel`. New batches are binned with the same boundaries, so a customer of a given age always lands in the same bin, and the model's learned coefficients stay valid.
- Use `Bucketizer` when the business defines the boundaries.
- Use `QuantileDiscretizer` when equal-frequency bins should be learned from training data.
W: `QuantileDiscretizer` learns equal-frequency boundaries from the training data and freezes them in a `Bucketizer`, which the pipeline applies unchanged to later batches.
X: A=Splits per scoring batch: boundaries recomputed on each batch change the meaning of every bin between batches and break the model's learned weights.
B=Repeated Binarizer: `Binarizer` thresholds a value to 0/1 and thresholds are fixed numbers you must choose, so it does not learn quantiles and gives overlapping indicators rather than one bin.
D=StandardScaler: it centers and scales values; it does not bin, and z-scores are not equal-frequency groups.
T: QuantileDiscretizer (an Estimator) learns equal-frequency splits and keeps them as a Bucketizer; Bucketizer alone applies fixed splits.

@ DBX-MLP D1 T1.3 advanced comparison
S: A text classifier uses `Tokenizer`, then either `HashingTF` or `CountVectorizer`, then `IDF`, then logistic regression. Reviewers require a report of the ten words with the largest positive weights for each class, and the corpus has several million distinct terms. Which choice satisfies the requirement?
A: `HashingTF` with `numFeatures` of 2^10, because the hashing trick keeps the vocabulary and gives each word a readable name
B: `CountVectorizer` with a limited `vocabSize` and `minDF`, because its fitted model stores the vocabulary so that coefficient positions map back to words
C: `HashingTF` with a very large `numFeatures`, because with enough buckets the hash index can be inverted to the word with no extra information
D: Neither; `IDF` already keeps the term names, so either vectorizer works and the report can be produced from the `IDF` model
K: B
G: ## Two ways to build term-frequency vectors
- `HashingTF` is a `Transformer` that hashes each term into one of `numFeatures` buckets (default 2^18). It needs no global dictionary, which is cheap for huge corpora, but different words can share a bucket (collisions) and the word-to-position mapping is not stored.
- `CountVectorizer` is an `Estimator`: `fit` builds a vocabulary (limited by `vocabSize` and by document-frequency thresholds such as `minDF`) and the resulting model keeps `vocabulary`, so position i can be mapped back to a word.
## Trade-off
Hashing scales without a vocabulary pass and has fixed memory, but weights cannot be reliably named. If model explanations by word are required, use `CountVectorizer` and cap the vocabulary so that the vector size stays manageable.
W: Only `CountVectorizer` keeps the term list, so coefficients of the logistic regression can be matched to words; capping `vocabSize` and `minDF` handles the huge number of terms.
X: A=HashingTF with 2^10 buckets: hashing never stores the words, and so few buckets cause heavy collisions that merge unrelated terms.
C=HashingTF with a huge size: more buckets reduce collisions but cannot invert a hash; several words can still map to one index and the word is not recoverable.
D=IDF keeps names: `IDF` learns inverse document frequencies per vector position; it holds no vocabulary, so it cannot name positions.
T: Use CountVectorizer when you must map weights back to words; HashingTF is stateless and cheap but not reversible.

@ DBX-MLP D1 T1.4 advanced troubleshooting
S: A fraud model is tuned with `CrossValidator(numFolds=5)`. Each customer has many transactions, and cross-validation scores are far higher than the scores on later customers. The team suspects the folds. What change is the best fix?
A: Raise `numFolds` to 20 so that each validation fold is smaller

G: ## Random folds leak groups

`CrossValidator` accepts `foldCol`, a column with user-specified fold numbers. Spark then skips random k-fold and uses your assignment. D=Fixed seed: a seed makes the random folds repeatable but they stay random with respect to customers.
