@ DBX-MLP D2 T2.5 applied use-case
S: An ML team promotes code through development, staging and production. Before a release branch is cut, CI must show that the feature pipeline, the training pipeline, the batch inference pipeline and the monitoring setup work correctly together. Which integration test design follows Databricks guidance?
A: Run the unit tests of every function in the staging workspace, because passing unit tests already prove that the pipelines cooperate
B: Trigger all pipelines in the staging environment against its own staging catalog, in pipeline order, and check the output of each stage
C: Train the model in the development workspace, copy the artifact to staging, and skip the feature and inference pipelines because they did not change
D: Run the pipelines against the production catalog with a test flag, so that the data volume and values match production exactly
K: B
G: ## What an integration test covers
A unit test checks one function in isolation. An integration test runs the real pipelines together so that the hand-offs between them are exercised: feature tables written by the feature pipeline, read by training, a model registered in Unity Catalog, loaded by inference, and monitoring tables created for the outputs.
## Where it runs
In the Databricks MLOps workflow, the staging environment exists to test the ML pipeline code. It has its own catalog in Unity Catalog, so tests can write tables and register models without touching production. The staging environment should match production as closely as is reasonable. Integration tests run all pipelines (feature engineering, model training, inference and monitoring), and the assets they write are temporary and kept only until testing is complete.
W: Running every pipeline in staging against the staging catalog tests the interfaces between the stages with production-like configuration, and a failure points to the stage whose output was wrong, without any risk to production data or models.
X: A=Unit tests only: they validate functions in isolation and cannot reveal a schema mismatch between a feature table and the training code, or a model that fails to load in inference.
C=Copying a dev artifact: this is the deploy-models shortcut. It skips the feature and inference code that must also be reviewed and tested, and the artifact was never produced by the staging pipelines.
D=Production catalog with a test flag: tests would write temporary tables and model versions into production assets, which breaks the isolation of environments and risks polluting real data and registered models.
T: Integration tests run all ML pipelines together in staging against the staging catalog.
V: Unity Catalog, MLflow, Lakeflow Jobs

@ DBX-MLP D2 T2.5 advanced tradeoff
S: A model takes nine hours to train on the full dataset. Pull-request integration tests must finish within about 30 minutes, but must still run the training code, register the model and feed it to the inference pipeline. Which approach keeps the test meaningful?
A: Replace the training task with a check that the training notebook parses without syntax errors, and register a model from the previous release
B: Skip integration testing for training code and rely on the first production retraining run to reveal any failure after release
C: Train once a week on the full dataset and let every pull request reuse that model, without executing the changed training code
D: Run the same training pipeline in staging on a small data sample or with fewer iterations, accepting lower model quality but executing every step
K: D
G: ## Fidelity versus speed
An integration test is a smoke test of the whole chain, not a measurement of model quality. Databricks guidance says some steps can trade off fidelity of testing against speed or cost: if models are expensive or time-consuming to train, use small subsets of data or run fewer training iterations.
## What must stay real
The code path must still run. The same training pipeline is triggered, metrics are logged, the model is registered to the staging catalog, and the next pipeline loads it. Only the data volume and the number of iterations shrink.
W: A reduced sample or fewer iterations keeps the training code, logging, registration and hand-off to inference all executing, so a pull request that breaks any of them fails within the time budget.
X: A=Syntax check: a notebook can parse and still fail at runtime on schema, permissions, library versions or model logging, and reusing an old model means the changed code is never executed.
B=Test in production: the point of staging is to find failures before release. Waiting for production retraining exposes users and downstream consumers to the failure.
C=Reuse a weekly model: the pull request's training changes never run, so the test passes even when the new code is broken. It validates an older version of the code.
T: Shrink data or iterations, not the steps: keep every pipeline executing in the integration test.
V: MLflow, Unity Catalog

@ DBX-MLP D2 T2.5 applied use-case
S: A real-time application will call a Model Serving endpoint in production. The team wants the staging integration test to cover the serving path of the release candidate. Which test design is the best fit?
A: Run the deployment pipeline in staging so it creates a temporary endpoint with the model, send small test requests, then remove it
B: Load the model in the CI runner with `mlflow.pyfunc.load_model` and call `predict` locally, because the endpoint serves the same artifact
C: Create the production endpoint from the pull request branch and watch its error rate for a few minutes before the merge
D: Unit-test the JSON request schema with a mocked HTTP client, because network calls to real endpoints do not belong in automated tests
K: A
G: ## Serving is part of the pipeline
For an application with real-time inference, the serving infrastructure itself can fail: the endpoint may not build, the model may not load in the serving container, or the request and response format may not match the client. A local `predict` call cannot detect those problems.
## The Databricks approach
In the staging environment you trigger the model deployment pipeline, which creates a serving endpoint in staging and loads the model. Depending on production requirements you can do full-scale load testing, or only send small batch jobs or requests to a temporary endpoint. The second option keeps cost and duration low.
W: Running the real deployment pipeline against a temporary staging endpoint tests endpoint creation, model loading and the request path, while small test requests keep the cost low and nothing in production is touched.
X: B=Local `predict`: it proves the artifact works in a Python process, not that the serving environment can build, load and answer requests, so the deployment pipeline stays untested.
C=Endpoint in production: a candidate that has not passed staging would be exposed to live traffic. Testing belongs before the release, in an environment that matches production.
D=Mocked HTTP client: a mock only checks the test's own assumptions about the schema. It never exercises the real endpoint, so deployment errors and runtime failures pass undetected.
T: Test real-time inference by deploying a temporary staging endpoint and sending small requests.

@ DBX-MLP D2 T2.5 applied troubleshooting
S: A staging integration test ends with the following code and always passes, even when the training task of the same CI run fails to register a new model version.
```
model = mlflow.pyfunc.load_model("models:/prod.ml.churn@champion")
sample = spark.table("staging.ml.test_sample").toPandas()
preds = model.predict(sample)
assert len(preds) == len(sample)
```
What is the flaw?
A: `predict` on a pandas DataFrame never keeps the row count, so the assertion must compare with a Spark DataFrame instead
B: Tables in the staging catalog cannot be read from CI, so the sample must be exported to a parquet file before it is loaded
C: It loads the production champion, so it tests the old model; it should load the version URI the staging training task produced
D: The URI should use the legacy stage form `models:/churn/Staging`, so that the registry stage matches the environment under test
K: C
G: ## Test the artifact the run produced
An integration test must exercise the output of the pipeline run under test. In the recommended workflow the training task yields a model URI, and later tasks (validation, deployment, inference) use it, for example passed with task values. The environment decides which catalog the version is registered to: a staging run registers into the staging catalog.
## Why the snippet is blind
An alias such as `champion` points to a version that was released earlier. Loading it tests yesterday's model against today's sample, so the assertion succeeds whether or not the new training code works.
W: The test never touches the new version. Reading the URI emitted by the training task, in the staging catalog, makes the assertion depend on the candidate that the pipeline just produced.
X: A=Row counts: `predict` on a pandas DataFrame returns one prediction per input row for ordinary models, so the comparison is valid and is not what makes the test pass wrongly.
B=Staging read access: reading a staging table with `spark.table` works for principals that have privileges on it. Exporting to parquet adds work and does not touch the real flaw.
D=Legacy stage URI: workspace registry stages are legacy. Unity Catalog uses catalogs for environments and aliases or version numbers, and a stage name would still not select the new version.
T: Integration tests load the model URI produced by the run under test, never a released alias.

@ DBX-MLP D2 T2.5 advanced tradeoff
S: Several pull requests run integration tests at the same time. All of them write to the fixed names `staging.ml.features` and `staging.ml.churn`, so runs overwrite each other and fail randomly. The team wants pull requests to keep testing in parallel. What should they do?
A: Give every pull request its own workspace and metastore, and copy the staging catalog into each of them before the test starts
B: Point the integration tests at the dev catalog, where data scientists already overwrite tables freely, instead of the staging catalog
C: Create a uniquely named schema per CI run, for example with the run ID, in the staging catalog, write all assets there, and drop it afterwards
D: Cap the integration job at one concurrent run so that tests queue up, and keep the fixed table and model names
K: C
G: ## Staging assets are temporary
The staging catalog exists for testing ML pipelines and registering test models. Assets written there are generally temporary and retained only until testing finishes. That makes it safe to create and drop them automatically.
## Isolating parallel runs
Collisions come from shared names, not from shared compute or the shared catalog. Parameterising the schema (a run-unique name passed to every pipeline) lets each run own its tables and model, and a final cleanup step drops the schema. Runs stay parallel and the catalog stays tidy.
W: A schema per run gives every pipeline run separate tables and models inside the staging catalog, so parallel pull requests no longer overwrite each other, and cleanup keeps the temporary assets from accumulating.
X: A=Workspace and metastore per pull request: this is heavy, slow and expensive, and a separate metastore cannot share the governed staging assets. Unique names inside one catalog solve the problem.
B=Dev catalog: it is meant for free experimentation and the same overwrite problem would continue there. It also defeats the purpose of testing in a production-like staging environment.
D=Concurrency of one: it removes the collision but also removes parallelism, which the team wants to keep, and long-running tests would make every pull request wait in a queue.
T: Give each integration run its own schema in the staging catalog and drop it afterwards.

Databricks guidance suggests scheduling periodic integration tests on the main branch when it is updated frequently by concurrent pull requests from multiple users. The scheduled run tests the merged state in staging and fails before a release branch exists.

@ DBX-MLP D2 T2.5 applied comparison
S: The team designs the CI stage that guards the merge into the main branch. Which sequence follows the Databricks MLOps workflow?
A: Run integration tests on every commit and unit tests only when the release branch is cut, because integration tests are the stronger check
B: Run unit tests and integration tests as one combined step after the merge, and report failures in a daily summary
C: Merge first, then run unit and integration tests on main, and revert the merge if either of them fails
D: Run unit tests on the pull request and reject it if they fail, then run integration tests in staging, and merge only when both pass
K: D
G: ## Cheap checks first
Unit tests are fast and are continuously added during development, so they run as soon as a pull request is opened. If they fail, the pull request is rejected. Only then do the slower integration tests run in the staging environment, which matches production as closely as is reasonable.
## Gate the merge
If all tests pass, the code is merged to the main branch. If any test fails, the CI/CD system should notify users and post the results on the pull request. A release branch, created afterwards, triggers the update of production jobs.

B=Combined after the merge: main would already contain failing code, and a daily summary delays feedback so far that the author has moved on.
C=Merge then test: broken code reaches main and blocks everyone else. Testing is meant to gate the merge, not to clean up after it.

@ DBX-MLP D2 T2.6 applied use-case
S: A Python team has cleaning functions used by notebooks in three projects and by a Python script task in a job. They want pytest to discover and run unit tests in CI. How should they organize functions and tests?
A: Keep each function and its unit tests in the same notebook, because a single file is the easiest to track
B: Store the functions and their tests as Python files in a Git folder, import them from notebooks and tasks, and run them with pytest
C: Store the functions in one notebook and the tests in another, and load the functions into other notebooks with the `%run` magic
D: Copy the functions into every notebook that needs them, so that each notebook is self-contained and does not depend on shared files
K: B
G: ## Three ways to organize functions and tests
Databricks describes common layouts for Python, R and Scala code, and each has benefits and challenges.
- Outside notebooks: functions and tests in files. Callable from notebooks and from anywhere else; test frameworks are designed to run tests outside notebooks, and the workspace has tools to discover, run and track Python unit tests. The cost is more files to maintain.
- Functions in one notebook, tests in another: easier to reuse across notebooks, but more notebooks to maintain, functions are not usable outside notebooks and are harder to test outside them.
- Both in one notebook: easy to track, harder to reuse across notebooks, not usable outside notebooks.
For Python and R notebooks, Databricks recommends storing functions and unit tests outside of notebooks.
W: Files in a Git folder can be imported by notebooks and by a job script task, and pytest discovers them in CI, which matches the requirement of reuse inside and outside notebooks.
X: A=Same notebook: simple to track, but the functions cannot be used outside notebooks, so the script task cannot import them, and reuse across the three projects is harder.
C=Function and test notebooks with `%run`: reusable between notebooks, but the functions remain notebook code that a script task cannot use, and testing them outside notebooks is awkward.
D=Copies everywhere: three copies drift apart, and a bug fix has to be repeated in each, which makes testing and maintenance worse than a shared module.
T: For Python, keep functions and tests in files outside notebooks so that they are shared and pytest can run them.

@ DBX-MLP D2 T2.6 applied use-case
S: Analysts and ML engineers share a business rule that buckets customers by margin. It is called from many SQL notebooks and ought to be unit-tested. Which design does Databricks recommend for SQL notebooks?
A: Define the rule as a temporary view in every notebook, and compare the view output with a CSV file of expected values kept in a volume
