@ DBX-MLP D1 T1.9 applied troubleshooting
S: A team launches 40 parallel Optuna workers on Spark, but each worker builds its own study with the default in-memory storage, as in `study = optuna.create_study()`. Every worker reports a different "best" result, and TPE never learns from the trials of other workers. Which change fixes the design?
A: Raise the number of trials on each worker so that every in-memory study collects enough history to find the same optimum
B: Create the study with `MlflowStorage` for the experiment and run it through `MlflowSparkStudy`, so all workers share one study
C: Make every worker use `RandomSampler` with the same seed, so that all in-memory studies visit the same points in order
D: Collect each worker's study on the driver after the run and merge the trial lists into one summary table by hand
K: B
G: ## Why a distributed Optuna study needs shared storage
An Optuna `Study` is a record of trials: the parameters tried and the objective value returned. A sampler such as TPE reads that record to decide which parameters to try next. With the default in-memory storage the record lives inside one Python process. If 40 workers each create a study, there are 40 separate records and 40 separate searches that only look alike.
## The Databricks integration
The Databricks page "Hyperparameter tuning with Optuna" describes two classes from MLflow 3:
- `MlflowStorage` lets Optuna use the MLflow tracking server (one experiment) as its storage backend, so every worker reads and writes the same trial history.
- `MlflowSparkStudy` wraps an Optuna `Study` and runs the parallel optimization on PySpark executors.
```
storage = MlflowStorage(experiment_id=exp_id)
study = MlflowSparkStudy(study_name="tune", storage=storage)
study.optimize(objective, n_trials=200, n_jobs=40)
```
W: A shared storage backend turns 40 separate searches into one study: each new suggestion by the sampler sees all finished trials, and the result is one set of best parameters. MlflowStorage on the MLflow experiment plus MlflowSparkStudy is the documented way to get it on Spark.
X: A=More trials per worker: each in-memory study still sees only its own trials, so there are still 40 independent searches. More history per worker costs compute and does not make the workers agree.
C=Same seed, RandomSampler: random sampling does not learn from past trials at all, so it gives up the benefit of TPE. Identical seeds would also make the workers repeat the same points instead of covering the space.
D=Merge on the driver afterwards: merging after the fact gives a table, but the sampler never used the other workers' results while searching. The problem is shared state during the run, not reporting at the end.
T: Distributed Optuna needs one shared study record: MlflowStorage as the backend and MlflowSparkStudy to run it on executors.

@ DBX-MLP D1 T1.9 applied definition
S: A team compares its Optuna setup with an older Hyperopt job. It calls `MlflowSparkStudy(study_name="gbt", storage=storage)` without passing a sampler or pruner. Which algorithms does the study use by default?
A: A random-search sampler with no early stopping, so the study behaves like a fixed grid until a pruner is set
B: A grid sampler over the first suggested values and a successive-halving pruner that stops half of the trials
C: The CMA-ES sampler for continuous spaces and a hyperband pruner that allocates resources to promising trials
D: `TPESampler` to propose new parameters and `MedianPruner` to stop trials that look worse than the median
K: D
G: ## Two pluggable parts of every Optuna study
- The **sampler** decides which hyperparameters to try next, using the finished trials. Examples are random, grid, TPE and CMA-ES samplers.
- The **pruner** decides whether to stop a running trial early, based on intermediate values the objective reports. Examples are median, successive-halving and hyperband pruners.
## Defaults in MlflowSparkStudy
The Databricks reference for `MlflowSparkStudy` lists the parameters `study_name`, `storage`, `sampler` and `pruner`. It states that `optuna.samplers.TPESampler` is used as the default sampler and `optuna.pruners.MedianPruner` as the default pruner. TPE is a Bayesian method (it models good and bad regions of the space), so it is closer to Hyperopt's `tpe.suggest` than to random search.
W: TPESampler is the default sampler and MedianPruner is the default pruner, so an unconfigured study already searches with a Bayesian method and can stop trials that look worse than the median of earlier trials at the same step.
X: A=Random search, no pruning: random sampling is an option you can pass, but it is not the default. A default pruner also exists.
B=Grid sampler and successive halving: a grid sampler needs an explicit search grid and is never the default, and successive halving is a different pruner that must be passed in.
C=CMA-ES and hyperband: both are valid Optuna components when you pass them yourself, but the documented defaults are TPE and the median pruner.
T: MlflowSparkStudy defaults to a TPE sampler and a median pruner; anything else is passed in explicitly.

@ DBX-MLP D1 T1.9 advanced troubleshooting
S: A team tunes a neural network for 50 epochs per trial with `MlflowSparkStudy` and the default `MedianPruner`. Poor trials still run all 50 epochs, and the log shows no pruned trials. The objective only trains the model and returns the final validation loss. What should the engineer change?
A: Switch the storage backend from `MlflowStorage` to a local SQLite file on the driver, because MLflow storage disables every pruner in the study
B: Replace `n_jobs` with a larger value so that Spark can interrupt long trials from outside the executor task
C: In the training loop call `trial.report(val_loss, epoch)` and raise `optuna.TrialPruned` when `trial.should_prune()` is true
D: Increase `n_trials` above 100, because the median pruner stays inactive until it has seen a hundred completed trials
K: C
G: ## How pruning works in Optuna
A pruner can only judge a trial by **intermediate values**. The objective must report them with `trial.report(value, step)` after each epoch or fold, then ask `trial.should_prune()`. If it returns true, the objective raises `optuna.TrialPruned` and the trial ends early, freeing its executor slot for a new, better-chosen trial.
```
for epoch in range(50):
    val_loss = train_one_epoch(model)
    trial.report(val_loss, epoch)
    if trial.should_prune():
        raise optuna.TrialPruned()
```
## Why it matters on Spark
Each trial occupies an executor task. Pruned trials give the slot back quickly, so the same cluster completes many more trials. Without reports, the median pruner has nothing to compare, and every trial looks like a single final value.
W: The pruner needs per-step values. Reporting the validation loss each epoch and raising TrialPruned when told to gives the default MedianPruner what it needs to stop poor trials early.
X: A=SQLite storage: pruning does not depend on the storage type, and a local file would not be shared by executors. The change would break the shared study rather than enable pruning.
B=Larger n_jobs: n_jobs sets how many trials run at once. It does not let Spark cancel a running function, and it does not produce intermediate values for the pruner.
D=More than 100 trials: the median pruner starts working after a small number of startup trials, not a hundred. The real cause is that nothing reports intermediate values.
T: Pruners act on intermediate values: report them with trial.report and exit with TrialPruned when should_prune is true.

@ DBX-MLP D1 T1.9 applied use-case
S: An objective tunes a gradient-boosting model with `lr = trial.suggest_float("lr", 1e-6, 1e-1)`. After 100 trials, nearly every sampled learning rate lies between 0.01 and 0.1, and small rates such as 1e-4 were hardly tried although they are often best. What is the best change?
A: Add `log=True` so Optuna samples the learning rate on a logarithmic scale and spreads trials across the orders of magnitude
B: Replace `suggest_float` with `suggest_categorical` over six learning rates, which makes TPE evaluate each one in turn
C: Narrow the range to `0.05` through `0.1`, because TPE converges faster when the search space has fewer orders of magnitude
D: Convert the objective to a grid search over 1e-6, 1e-4 and 1e-1 on the driver, since Optuna cannot sample small numbers
K: A
G: ## Scale of the search space
A parameter such as a learning rate or a regularization strength matters in orders of magnitude, not in absolute steps. A uniform draw from `1e-6` to `1e-1` puts about 90% of the samples in the top decade (0.01 to 0.1) because that decade holds 90% of the interval's length.
## Log sampling
`trial.suggest_float(name, low, high, log=True)` samples uniformly in log space, so each decade gets about the same share of trials. The Databricks Optuna example uses `log=True` for the SVR `C` parameter, which spans `1e-10` to `1e10`. The same applies to `suggest_int` for sizes that cover several orders of magnitude.
W: log=True gives each order of magnitude an equal share of the trials, so the small learning rates the team missed are tried as often as the large ones.
X: B=Six categories: a categorical parameter has no order, so TPE cannot exploit that nearby values give similar scores. It also fixes the choices up front instead of searching a continuous range.
C=Narrower range: it cuts away the very region the team wanted to explore and hides a good optimum instead of finding it.
D=Three-point grid on the driver: Optuna samples small numbers without trouble. A three-point grid would give up adaptive search and distribution on executors.
T: Use log=True for parameters that span orders of magnitude, so the search is not dominated by the largest decade.

@ DBX-MLP D1 T1.9 advanced tradeoff
S: A study runs several hundred concurrent trials on Spark. Each trial reports its parameters and metrics to the MLflow tracking server, and the team sees throttled REST calls and slow trials. A colleague proposes dropping `MlflowStorage` in favor of a custom `mlflow.log_param` call in each objective. Why is `MlflowStorage` the better design?
A: It caches all trial results in driver memory and writes a single batch after the last trial, so no REST call happens during the search
B: It replaces the MLflow tracking server by a Delta table, so REST calls to the tracking server are never made at all
C: It samples a subset of the trials and logs only those, which keeps the number of REST calls roughly constant
D: It batches writes and flushes them on an interval or at a size threshold, which avoids throttling of the tracking REST API
K: D
G: ## The cost of fine-grained logging
Every trial writes parameters, intermediate values and a final value. At several hundred concurrent trials this is a large stream of small REST calls to the MLflow tracking server, and a service that throttles will answer with errors or delays, which slows the objective itself.
## Batching in MlflowStorage
The Databricks API reference describes `MlflowStorage` as an MLflow-based storage class for Optuna with batch processing to avoid REST API throttling. Two parameters control it:
- `batch_flush_interval`: seconds between automatic flushes (default 1.0).
- `batch_size_threshold`: maximum number of items collected before a flush is triggered (default 100).
Because the storage is also what Optuna reads for the shared study, it serves both as logging and as coordination for the samplers.
W: MlflowStorage collects writes in a batch and flushes on an interval or when the batch reaches a size threshold. That reduces the number of REST calls and avoids throttling, while still keeping the whole shared study in the experiment.
X: A=One write after the last trial: nothing could then be shared during the search, so TPE would not see other workers' results, and a driver failure would lose all trials. The flush happens during the run.
B=Delta table instead of tracking server: the storage is based on the MLflow experiment, so it still talks to the tracking server. It reduces the call rate by batching, not by changing the backend.
C=Logging only a sample: sampling would drop trials from the study history, which harms the sampler. All trials are recorded.
T: MlflowStorage batches Optuna writes (flush interval and size threshold) to avoid MLflow REST throttling at high concurrency.

S: A nightly job tunes models with Ray Tune. Several analysts also want to submit Ray tasks to the same Ray cluster during the day through `ray.init()` from their own notebooks. A cluster created with `setup_ray_cluster` in the first analyst's notebook disappears whenever that notebook detaches. Which setup fits?
A: Run `setup_ray_cluster` in every analyst's notebook with the same arguments, so that all of them share the first cluster's workers
B: Start a global mode Ray cluster with `setup_global_ray_cluster` from a notebook job, and let users connect with `ray.init()`

A: Run `%pip install` from a second notebook, because only the notebook that created the Ray cluster is affected by pip
B: Install the library with `%pip` on every Ray worker through a Ray remote function that calls `subprocess` at the start of each trial

@ DBX-MLP D1 T1.10 advanced tradeoff
S: A fixed-size Databricks cluster of 10 workers runs a Spark feature job for two hours and then a Ray Tune search for two hours. A Ray cluster created with a fixed `max_worker_nodes=10` keeps all workers busy as Ray nodes, so the Spark stage queues behind it. How should the team configure the hybrid workload?
A: Reduce the Ray cluster to a single worker for the whole day, because Ray and Spark cannot share a cluster at all
B: Raise `spark.executor.memory` as high as possible so that Spark caches more data and finishes before Ray starts
C: Enable Ray-on-Spark autoscaling with minimum and maximum worker nodes, and keep `spark.executor.memory` small, so idle Ray workers are freed
D: Start one global Ray cluster for each Spark task with `setup_global_ray_cluster`, so that every Spark job owns its own Ray head and workers
K: C
G: ## Hybrid Spark and Ray
Ray on Databricks runs inside a Spark cluster. Both frameworks want the same machines: Spark executors use JVM heap and cache memory, Ray workers use Python heap and an object store. The scaling page gives two rules for hybrid workloads:
- **Compute**: with a fixed number of nodes, enable Ray-on-Spark autoscaling. When no Ray work is running, the Ray cluster scales down and the nodes are free for Spark tasks; when Ray is used again, it scales up. Use `min_worker_nodes` and `max_worker_nodes` (Ray 2.10 and above); scale-down speed can be tuned with `autoscale_idle_timeout_minutes`.
- **Memory**: reduce `spark.executor.memory` to a small value (the docs give 4g as an example), because the Spark executor holds dataset caches and triggers garbage collection lazily, which takes memory away from Ray and can cause out-of-memory errors.
You can also make the Databricks cluster itself autoscale and cap Ray at a subset, for example Ray on at most 4 of up to 10 nodes.
W: Autoscaling the Ray-on-Spark cluster lets idle Ray workers go away so Spark tasks can use the nodes, and a small executor memory leaves room for Ray. This is the documented hybrid configuration.
X: A=One Ray worker all day: the two frameworks do share a cluster by design, and a single worker would remove the parallelism the search needs.
B=Maximum executor memory: large executor heaps make the competition worse because Ray's heap and object store are then starved. The docs recommend the opposite.
D=A Ray cluster per Spark task: a global cluster is one per Databricks cluster and is for sharing among users. More heads would multiply the head overhead and not release workers to Spark.
T: For hybrid Spark and Ray, autoscale the Ray cluster so idle workers return to Spark, and keep spark.executor.memory small.

@ DBX-MLP D1 T1.10 applied use-case
S: A team preprocesses data with Spark and then trains with Ray Tune on a GPU cluster. Spark preprocessing tasks sometimes grab GPUs, which leaves fewer GPUs for Ray, and the CPU-only Spark stages have fewer task slots than the instance has cores. Which cluster setting does Databricks recommend?
A: Set `spark.executor.memory` to the full node memory so that Spark never competes for resources with the Ray object store

- Higher Spark parallelism, because a GPU instance usually has many more CPU cores than GPU devices.
- On a shared cluster, Spark jobs do not compete for GPUs with concurrently running Ray workloads.
W: Setting the GPU amount per Spark task to 0 lets DataFrame transformations run on all CPU cores without claiming GPUs, so Ray keeps the GPUs and Spark gets more parallelism.
X: A=Full executor memory: it does not stop Spark tasks from requesting GPUs, and a very large executor heap reduces what is left for Ray.
C=Zero head node resources: the Ray head already defaults to 0 CPUs and 0 GPUs on Databricks, so this changes nothing about GPU contention from Spark tasks.
D=All GPUs to each Spark task: it would make Spark reserve even more GPUs per task, so fewer Spark tasks run and Ray has no GPUs left.
T: For Spark preprocessing before GPU Ray training, set spark.task.resource.gpu.amount to 0.

@ DBX-MLP D1 T1.11 applied tradeoff
S: A team trains a PyTorch network that fits easily in the memory of one GPU, on a dataset that also fits on one machine. A colleague proposes an 8-node GPU cluster with distributed training "to be faster". What does Databricks guidance recommend?
A: Train on one machine, moving to a larger or multi-GPU instance if needed, and distribute only when model or data exceed memory
B: Always distribute neural network training, because communication overhead is smaller than the compute gained on every dataset size and model
C: Use a CPU cluster of 8 nodes, since GPU instances cannot be combined with distributed training libraries in Databricks Runtime ML
D: Convert the network to a Spark ML pipeline, because Spark ML models scale better than neural networks on a single node
K: A
G: ## Scale up first, then out
**Vertical scaling** means a bigger machine (more memory, cores or GPUs). **Horizontal scaling** means more machines. For deep learning the Databricks "Distributed training" page says: when possible, train neural networks on a single machine, because distributed code for training and inference is more complex than single-machine code and slower due to communication overhead. Consider distributed training and inference when the model or the data are too large to fit in memory on a single machine.
## The cost of going out
Synchronous distributed training exchanges gradients between processes every step. Over a network that takes time that a single machine with fast links (or one GPU) never spends. The compute saved is only worth the overhead when a single machine cannot hold the work.
W: The documentation prefers one machine and distributes only when the model or data exceed memory. Here both fit, so a bigger single instance is the cheapest path.
X: B=Always distribute: the documentation says the opposite, because of code complexity and communication overhead.
C=CPU cluster: Databricks Runtime ML includes TorchDistributor, the DeepSpeed distributor and Ray for GPU clusters, so GPUs and distributed training can be combined. CPU nodes would also train a network much more slowly.
D=Convert to Spark ML: Spark ML trains classical algorithms on DataFrames; a PyTorch network is not converted into a Spark ML pipeline by a flag.
T: Prefer one machine for neural networks; scale out only when the model or data exceed single-machine memory.

S: A scikit-learn `RandomForestRegressor` is trained on a pandas DataFrame of 1.5 TB of tabular data. Training fails with out-of-memory errors even on the largest memory-optimized node available, and the data volume grows every month. Which direction is right?

G: ## When vertical scaling hits the ceiling
A scikit-learn estimator trains in one Python process on one machine. If the data does not fit in that machine's memory, a bigger node helps only until you reach the largest node type. A growing dataset will pass that limit sooner or later.
## Horizontal scaling for data
Spark ML algorithms are written for data parallelism: the DataFrame is split into partitions across executors, each executor computes partial statistics, and the driver combines them. Adding workers adds memory and compute. The cost is the communication between nodes and the restricted set of algorithms and options compared with scikit-learn.

Single-node models are simpler and faster while the data fits. When it can no longer fit, and sampling would lose signal, switch to the distributed implementation (Spark ML, or another framework that distributes data).
W: A Spark ML random forest keeps the data in distributed partitions, so memory grows with the cluster. It is the horizontal option when one node cannot hold the data.

C=GPU nodes: standard scikit-learn random forests are CPU-only and do not use GPUs, so accelerators would only add cost.

@ DBX-MLP D1 T1.11 advanced troubleshooting
S: A team distributes PyTorch training over 8 GPU nodes and measures a 6x speed-up compared with 1 node. Doubling to 16 nodes gives only 1.2x more. GPU utilization on each node drops during the steps. What is the most likely cause and the right reaction?

G: ## Diminishing returns in synchronous training
In data-parallel training each step ends with a gradient exchange between all processes. The compute per step shrinks when the batch is split across more processes, but the exchange time stays or grows with node count and network latency. Past a point, extra nodes mostly wait.
## What to do
- Stay on the smallest number of machines that meets the time target; the Databricks "Distributed training" page notes that distributed code can be slower because of communication overhead.

- **Within one fit**: split data or model across machines (distributed training). Worthwhile when one machine cannot hold the data or model.

A small model with a 3-minute fit and low memory use does not need to be distributed. @ DBX-MLP D1 T1.12 applied use-case
S: A vision team has a model that fits in the memory of one GPU, but the 4 TB image dataset takes days to cover per epoch on one GPU. The team has a cluster of GPU nodes and wants faster epochs. Which parallelization strategy fits?
A: Model parallelism, where each GPU holds a different layer block and the batch moves through them as a pipeline
B: Hyperparameter parallelism, where each GPU trains the same model on the same full dataset with another learning rate and a different seed

G: ## Data parallelism versus model parallelism
- **Data parallelism**: every process keeps a complete copy of the model. The dataset is divided into shards, each process computes gradients for its shard, and the gradients are averaged (all-reduce) so the copies stay identical. It speeds up training when the model fits in one device but the data (or the number of steps) is large.
- **Model parallelism** (including pipeline parallelism): the model itself is split across devices because it does not fit in one. It is a memory solution, not a throughput one.
## On Databricks
`TorchDistributor` (a PySpark module in Databricks Runtime ML) launches PyTorch training as a Spark job, initializes the communication channels and uses `torch.distributed.run`. A typical function uses `DistributedDataParallel` and a `DistributedSampler` and is run with `TorchDistributor(num_processes=..., local_mode=False, use_gpu=True).run(train, ...)`.
W: The model fits on one GPU and the problem is data volume, so data parallelism is the match. TorchDistributor runs DDP across the GPU workers, each with its own shard.
X: A=Model parallelism: it is used when the model does not fit in one GPU. This model fits, so splitting layers adds pipeline waiting without addressing the data volume.
B=Different learning rates per GPU: that is a hyperparameter search, which finds a setting but does not shorten the time to pass over the data for a given model.
D=Bigger driver: training runs in the worker processes, and a larger driver does not speed up epochs.
T: Model fits and data is large: data parallelism (full model copies on shards, gradients synchronized), for example with TorchDistributor.

G: ## How the training function reaches the workers
`TorchDistributor.run(main, *args)` calls `main(**kwargs)` for a function (or runs `torchrun` for a file path). A function defined in a notebook is serialized on the driver and sent to the executors, where each process starts its own Python interpreter. The TorchDistributor page lists a common notebook error where objects cannot be found or pickled because import statements were not distributed to the executors. @ DBX-MLP D1 T1.12 applied troubleshooting
S: A team moves single-GPU code to 4 processes with `TorchDistributor`. The model is wrapped in `DistributedDataParallel`, but the data loader is still `DataLoader(dataset, batch_size=64)`. Epoch time barely improves, and each process sees every sample. What should be changed?
A: Increase `batch_size` to the size of the whole dataset, so that every process finishes in one step

C: Set `spark.task.resource.gpu.amount` to `0`, because Spark tasks otherwise read the data twice on each GPU of a node
D: Pass `sampler=DistributedSampler(dataset)` to the `DataLoader`, so each process reads a distinct shard of every epoch

G: ## What DDP does and does not do
`DistributedDataParallel` replicates the model per process and synchronizes **gradients**. It does not shard the data. Each process builds its own `DataLoader`, so without a distributed sampler all processes iterate over the full dataset. The work is repeated 4 times and the gradients are averaged over nearly identical batches.
## Sharding the data
`torch.utils.data.DistributedSampler` divides the dataset indices among the processes by rank, so each process reads about one quarter of the data per epoch. The Databricks TorchDistributor example does exactly this: it builds `DDP(model)`, `DistributedSampler(dataset)` and `DataLoader(dataset, sampler=sampler)` inside the training function.

```
sampler = DistributedSampler(dataset)
loader = DataLoader(dataset, sampler=sampler, batch_size=64)
```
W: A distributed sampler splits each epoch's samples across the processes, which is what makes the data-parallel step faster. Gradient synchronization by DDP is then useful because each process sees different data.
X: A=Whole-dataset batch: it would exceed GPU memory, and each process would still read all samples.
B=DataParallel on the driver: it is the older single-process, multi-GPU approach, not a way to split data across Spark workers, and TorchDistributor is set up for DDP.
C=GPU amount per Spark task: this setting is about Spark tasks and GPU claims, and does not control how a PyTorch loader selects samples.
T: DDP only synchronizes gradients: add a DistributedSampler so each process trains on its own shard.

@ DBX-MLP D1 T1.12 advanced tradeoff
S: A team has 64 GPUs. Each tuning trial of its model trains with data parallelism over 8 GPUs, and there are 40 trials to run. The team wants the search to finish as fast as possible with this budget. Which plan is best?
A: Run the 40 trials one at a time on all 64 GPUs, since a single distributed fit always has the highest total throughput
B: Run about 8 trials at a time, each on its own 8 GPUs, rather than every trial on all 64 GPUs in sequence
C: Run each trial on a single GPU and skip data parallelism, because trial-level parallelism always beats data parallelism
D: Run all 40 trials at once on 64 GPUs by giving each trial 1.6 GPUs through fractional sharing
K: B
G: ## Two levels of parallelism share one budget
Hyperparameter tuning is parallel across trials and each trial may be parallel within itself (data parallelism). Both draw from the same GPU pool, so the split is a trade-off.
- Trial-level parallelism has almost no communication cost, because trials are independent.
- Data parallelism inside a trial has a synchronization cost that grows with the number of processes (see the Databricks distributed training page about communication overhead).
## Reasoning
If a trial scales well to 8 GPUs but poorly to 64, spend the budget on 64 / 8 = 8 concurrent trials: the 40 trials then need 5 waves. Running one trial on 64 GPUs wastes capacity on diminishing returns. Trial-level concurrency is also where Optuna and Ray Tune help, by allocating resources per trial. The per-trial size depends on the measured scaling curve and the model memory, not on a rule.
W: Eight concurrent trials of 8 GPUs each keep every GPU busy and avoid the large synchronization cost of a 64-process job, so the 40 trials finish in about five waves.
X: A=One trial at a time on 64 GPUs: communication overhead grows with process count, so gains from 8 to 64 GPUs are usually small. That leaves trials waiting in a queue.
C=Single-GPU trials: the statement is not generally true. If one GPU cannot hold the data volume or the time per trial grows too much, the data parallelism inside the trial pays for itself.
D=Fractional GPUs: a model that needs 8 GPUs for data parallelism cannot be given 1.6 GPUs without changing the design, and 40 simultaneous trials would not fit.
T: Split the GPU budget between concurrent trials and the width of each trial using the measured scaling curve; avoid wide jobs with poor scaling.
