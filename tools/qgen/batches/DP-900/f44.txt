@ DP-900 D4 T4.1 applied definition
S: Large-scale analytics platforms such as Microsoft Fabric and Azure Databricks process terabytes of data with Apache Spark. What lets Spark handle such high data volumes quickly?
A: It converts the data into a normalized relational schema with row locks before running queries on it.
B: It loads the files into the memory of one very large server and reads the rows one after another in order.
C: It is a distributed engine that splits the work across cluster nodes and processes the data in parallel.
D: It reads from preaggregated cubes built in advance, so it skips scanning the detailed rows in the data lake.
K: C
G: ## Why large-scale analytics is distributed
Learn notes that data processing in large-scale analytics is often performed by **distributed systems** that process high volumes of data **in parallel using multi-node clusters**.
## Apache Spark
**Apache Spark** is the open-source distributed processing engine used by Fabric (Data Engineering notebooks and Spark jobs) and by Azure Databricks.
- A **cluster** is a set of computation resources: a driver that plans the work and worker nodes that run it.
- A large dataset is split into partitions, and each worker processes some partitions at the same time.
- Adding nodes adds processing capacity, so large jobs finish sooner.
## Example
A 2 TB folder of clickstream files is split into thousands of partitions. Twenty workers each process a share of them in parallel, instead of one server reading every file.
W: Distributed, parallel processing: Spark splits a large dataset into partitions and spreads them across the worker nodes of a cluster, which process their share at the same time; adding nodes adds capacity, so high volumes are handled quickly.
X: A=Normalized schema with row locks: normalization and row locking are traits of transactional databases. Spark reads files in a lake, often with schema on read, without row locks.
B=One large server: reading everything on one machine in sequence is the bottleneck that distributed engines are designed to avoid.
D=Preaggregated cubes: cubes are a reporting model. Spark processes the detailed data in the lake; it does not depend on pre-built totals.
T: Spark handles big data by splitting it across a multi-node cluster and processing the parts in parallel.

S: A company is building a new lakehouse with elastic compute. Data scientists want the untouched source data kept for future, still-unknown analyses. Which TWO statements explain why an ELT approach suits this design? (Select TWO)
A: ELT runs transformations on a separate server in front of the store, so heavy business rules use no lakehouse compute.
B: ELT validates and cleans each record before the write, so the lakehouse holds no duplicates or badly formatted raw files.
C: ELT suits small datasets best, so it keeps lakehouse storage costs low by rejecting files larger than a set size limit.
D: ELT copies the source data into the store first, so the raw data is preserved and can be transformed again later in new ways.
E: ELT uses the processing power of the target store for transformations, so scaling the lakehouse compute also scales the pipeline.
K: D,E
G: ## ELT in a nutshell
In **extract, load, transform (ELT)** the data is copied into the target store first and transformed there afterwards. The transformation uses the target's own engine (for example Spark notebooks or SQL in a lakehouse) instead of a separate transformation server.
## When Learn recommends ELT
The Azure Architecture Center lists these reasons to choose ELT:
- The target is a modern data warehouse or **lakehouse with elastic compute scaling**.
- You need to **preserve raw data** for exploratory analysis or future schema changes.
- The transformation logic benefits from the target system's native capabilities.
## When ETL is still better
ETL fits when the target system is constrained and heavy transformations must run elsewhere, when complex business rules need a specialized engine, or when compliance requires audited staging before loading.
W: D=Raw data preserved: data lands in the store before any change, so the original copy stays available and new transformations can be written later for questions nobody has asked yet.
E=Target compute does the work: ELT removes the separate transformation engine and uses the store's own processing power, so scaling the lakehouse compute also scales the transformation work.
X: A=Separate transformation server: that is the ETL pattern. ELT deliberately removes the separate engine and transforms data inside the target store.
B=Clean before the write: validating each record before it is written is also ETL behavior. In ELT the raw, possibly messy data is loaded first and cleaned afterwards.
C=Small datasets: the opposite is true. Typical ELT use cases are big data workloads, where skipping extra copy steps saves time on large datasets.
T: Choose ELT when the target (lakehouse or modern warehouse) has elastic compute and you want to keep raw data for future transformations.

@ DP-900 D3 T3.2 advanced tradeoff
S: A team is choosing a partition key for a Cosmos DB container of customer orders that will grow large. Which choice follows the guidance on Learn?
A: A property that changes on each update, such as `lastModified`, so that new writes land in new partitions.
B: A property with many distinct values and an even spread of data, such as `customerId`, to balance throughput.
C: A property with two values, such as `isPriority`, so that the data stays in a small number of partitions.
D: A property shared by nearly every item, such as `country` in a one-country shop, so orders stay together.
K: B
G: ## What a partition key does
Every container has a **partition key**: a property whose value decides which **logical partition** an item belongs to. Cosmos DB spreads logical partitions across servers, which is how a container grows beyond one machine. Each logical partition can hold up to 20 GB.
## A good partition key
- Has **many distinct values** (high cardinality).
- Spreads data and requests **evenly** across those values, so no single partition becomes a hot spot.
## Example
With `customerId` as the key, thousands of customers give thousands of partitions, each small. With `isPriority`, everything lands in two partitions, and the one holding normal orders gets almost all the traffic and size.
W: Many distinct, evenly spread values: Learn says a good partition key has many distinct values and spreads data and requests evenly, which keeps throughput balanced as the container grows; `customerId` gives thousands of small logical partitions.
X: A=Frequently changing timestamp: keying on write time sends the new writes to the newest values, creating a hot spot, and a partition key value is part of the item's identity rather than something to change on each update.
C=Two-value property: two values mean at most two logical partitions, which concentrates traffic and quickly runs into the size limit per logical partition.
D=Value shared by nearly every item: almost all orders would fall into one logical partition, so the container could not spread data or load.
T: Choose a partition key with many distinct values and an even spread of data and requests.
V: Azure Cosmos DB

@ DP-900 D3 T3.1 applied troubleshooting
S: An analyst tries to download a two-year-old backup file from Azure Blob Storage and gets an error saying the blob can't be read. The blob's access tier shows Archive. What must happen before the file can be downloaded?
A: The blob must be converted from a block blob to a page blob, because page blobs can be read while they are archived.
B: The storage account's redundancy must be changed to zone-redundant storage, which reads archived data in place.
C: The blob must be rehydrated to an online tier such as hot, cool or cold, which can take hours.
D: The analyst must be given access to the container again, because moving a blob to archive resets its permissions.
K: C
G: ## The archive tier is offline
While a blob is in the **archive** tier it **can't be read or modified**. Its metadata stays available, so you can still list the blob and see its properties, but not its content.
To read it, you **rehydrate** it to an online tier (hot, cool or cold), either by changing its tier or by copying it to a new blob in an online tier.
- **Standard priority** (default): can take up to 15 hours for objects under 10 GB.
- **High priority**: costs more and can complete in under an hour for objects under 10 GB; meant for emergencies.
## Why this is acceptable
Archive is meant for long-term backups and compliance data that is hardly ever read, so waiting hours for a restore is a fair trade for the lowest storage cost.
W: Rehydrate to an online tier: an archived blob is offline, so its content can be read only after it is rehydrated to hot, cool or cold, by changing its tier or copying it; that takes hours at standard priority and less at the higher-cost high priority.
X: A=Convert to a page blob: a blob's type cannot be changed after creation, and access tiers, including archive, apply to block blobs.
B=Change to ZRS: redundancy does not make archived data readable; in fact the archive tier is supported in LRS, GRS and RA-GRS accounts, not in ZRS accounts.
D=Restore permissions: archiving does not remove permissions; the analyst sees the blob and its tier, and the obstacle is the offline state of the data itself.
T: Archived blobs are offline: rehydrate them to hot, cool or cold (hours) before reading.

@ DP-900 D1 T1.2 applied definition
S: A new team member hears the term "NoSQL database" and asks what it means. Which TWO statements about nonrelational (NoSQL) databases are accurate? (Select TWO)
A: They require each record to have the same set of fields, which the database checks on each write.
B: They store data as tables of rows that reference one another through primary and foreign keys.
C: They cannot be queried with any SQL-like language, which is where the NoSQL name comes from.
D: Some of them support a variant of the SQL language, even though they are called NoSQL databases.
E: They are data management systems that do not apply a relational schema to the data they store.
K: D,E
G: ## Relational and nonrelational databases
A **database** is a central system in which data is stored and queried, usually a dedicated system for managing records rather than files.
- **Relational databases** store structured data in tables with keys and are queried with SQL.
- **Nonrelational databases** are data management systems that **do not apply a relational schema** to the data.
## The NoSQL name
Nonrelational databases are often called **NoSQL** databases, **even though some support a variant of the SQL language**. Read it as "not only SQL" or "not relational", not as "no query language".
## Four common types
- Key-value
- Document (a key-value store whose values are JSON documents)
- Column family
- Graph
They usually allow flexible schemas and scale out horizontally, and relax some relational behaviors to do so.
W: D=Some support SQL variants: the NoSQL label is historical; several nonrelational databases offer a SQL-like query language.
E=No relational schema: Microsoft defines nonrelational databases as data management systems that do not apply a relational schema to their data.
X: A=Same fields for each record: a fixed schema checked on write is a feature of relational, structured data; nonrelational stores usually allow flexible schemas.
B=Tables linked by keys: tables that reference each other through keys describe the relational model, the opposite of nonrelational.
C=No SQL-like language: some nonrelational databases do support a variant of SQL, so the name does not mean SQL is impossible.
T: NoSQL = nonrelational (no relational schema imposed); some NoSQL databases still offer SQL-like queries.

@ DP-900 D1 T1.1 applied use-case
S: An app saves each customer as a JSON document. Most customers have one email address, some have several phone numbers and email addresses, and a few have no contact details at all. Which description fits this data?
A: Binary data, because JSON documents are stored as raw bytes that the writing app must decode and render.
B: Unstructured data, because the number of contact entries differs by customer, so no common layout exists.
C: Semi-structured data, because the documents share a general shape but their fields vary by customer.
D: Structured data, because each document is stored in JSON, and JSON enforces a fixed set of fields per entity.
K: C
G: ## What makes data semi-structured
Semi-structured data has **some structure** (named fields, nesting) but **allows variation** between entity instances. Microsoft's own example is customer contact details: most customers have an email address, some have several, and some have none.
## JSON as the usual example
JavaScript Object Notation (JSON) is the most common format for semi-structured data. Each document carries its field names with the values, so two customer documents can differ:
- Customer 1 has an address and two contact entries (a home phone and an email).
- Customer 2 has an address with an extra `unit` field and only one contact entry.
JSON is just one way to represent semi-structured data; XML and key-value data are others.
## Why it matters
A store for this data must accept records whose fields differ, instead of forcing every customer into the same set of columns.
W: Semi-structured data: the customers share a common shape (name, address, contacts), but the number and kind of fields differ between documents, which is exactly the variation semi-structured data allows and Microsoft's own example of it.
X: A=Binary data: JSON is human-readable text in which bytes map to printable characters; raw binary that applications must render describes files such as images and video.
B=Unstructured data: the documents still have named fields and nesting; unstructured data means content such as images, audio or free text with no field layout.
D=Structured data: JSON does not enforce a fixed set of fields; that flexibility is why JSON is the standard example of semi-structured data.
T: Shared overall shape with fields that vary between records, as in JSON documents = semi-structured data.

@ DP-900 D2 T2.2 advanced troubleshooting
S: A team moved its SQL Server database to a single Azure VM and assumed the VM's availability SLA protected the database. During a SQL Server service crash, the VM stayed up but the database was offline. What explains this?
A: The VM SLA applies when the database is also registered in an Azure SQL Database elastic pool on a logical server.
B: Microsoft's VM SLA includes SQL Server restarts on Linux images, so the team should have chosen a Linux VM instead.
C: The VM SLA covers the virtual machine, not the SQL Server service on it, so database HA is the team's job.
D: SQL Server on Azure VMs runs the Express edition, which lacks a restart of the database service after a crash.
K: C
G: ## Who keeps the database available
- With **Azure SQL Database** and **Azure SQL Managed Instance** (PaaS), high availability of the database is built in. Microsoft runs the engine and fails over to healthy resources.
- With **SQL Server on Azure VMs** (IaaS), Microsoft's SLA covers the **virtual machines**, not the SQL Server processes running on them. Learn's comparison lists "You need to implement your own High-Availability solution" as a point for the VM option.
## What the team must add on a VM
To protect the database itself, the team configures SQL Server high availability features across two or more VMs, placed in an availability set or across availability zones. Registering with the SQL IaaS Agent extension adds help such as automated backup, but HA design stays with the customer.
W: VM SLA, not SQL Server SLA: on IaaS the agreement covers the VM infrastructure, so a crash of the SQL Server service on a running VM is the customer's problem; the team must build its own high availability with SQL Server features across two or more VMs.
X: A=Elastic pool registration: elastic pools belong to the PaaS Azure SQL Database service; a VM-hosted SQL Server cannot be placed in one, and the VM SLA does not depend on it.
B=Linux restarts in the SLA: the operating system choice does not change the SLA. On Windows and Linux VMs alike, the SLA covers the VM, not SQL Server.
D=Express edition: supported versions and editions of SQL Server, including Standard and Enterprise, can be installed on Azure VMs, and the edition is not why the database went offline.
T: SQL Server on Azure VMs: the SLA covers the VM; you build SQL Server high availability yourself. PaaS options include it.
V: SQL Server on Azure Virtual Machines

@ DP-900 D2 T2.2 applied use-case
S: A developer needs an Azure SQL Database for a test environment that is used for a few hours on some days and sits idle for long periods. She wants compute charges only while the database is in use. Which option fits best?
A: The Hyperscale service tier with read-only geo-replicas, which take over the workload while the primary is idle.
B: An elastic pool with one database in it, which bills per minute for the time the database runs queries.
C: The provisioned compute tier, which keeps a fixed amount of compute allocated and billed per hour of the day.
D: The serverless compute tier, which scales compute with demand and can pause the database when it is inactive.
K: D
G: ## Compute tiers in Azure SQL Database
In the vCore purchasing model, a single database can use one of two compute tiers:
- **Provisioned**: you choose a fixed amount of compute, which is reserved and billed per hour whether or not it is used.
- **Serverless**: compute scales automatically between a minimum and maximum, and you are billed per second for the compute actually used.
## Auto-pause
Serverless can **automatically pause** a database after a configurable period of inactivity. While paused, only storage is billed; the database resumes on the next login or activity. Auto-pause can also be turned off.
## Example
A test database used on Tuesday and Thursday afternoons pauses at night and over the weekend, so compute is billed only during the test sessions. The first connection after a pause takes a little longer while the database resumes.
W: Serverless compute tier: compute scales between a minimum and maximum and is billed per second for what is used, and auto-pause stops compute billing during inactive periods, when only storage is billed; that matches intermittent test use.
X: A=Hyperscale with geo-replicas: geo-replicas add readable copies in other regions; they do not stop billing for the primary's compute and would raise cost.
B=Pool with one database: an elastic pool is billed for each hour it exists at its configured size, regardless of use, and a pool with one database shares nothing.
C=Provisioned compute: resources stay allocated and are billed per hour, so the idle periods would still cost compute.
T: Intermittent, unpredictable use of a single database with pay-for-use compute means the serverless compute tier with auto-pause.
V: Azure SQL Database

@ DP-900 D2 T2.2 applied use-case
S: A software company sells a SaaS app and gives each of its 300 customers a separate Azure SQL Database. Most databases are idle most of the day, but each one has short, unpredictable peaks. The company wants to cut costs without starving any database at its peak. What should it use?
A: The Business Critical service tier for each database, so that each one keeps a local read-only replica for peaks.
B: A larger SQL Server VM size, so that the databases run inside one instance whose memory and CPU can be resized.
C: One SQL Managed Instance, so that the 300 customers share a single database with a tenant ID column per table.
D: An elastic pool, so that the databases share a set amount of compute and storage purchased for the whole group.
K: D
G: ## The problem elastic pools solve
A common SaaS pattern gives every customer its own database. Each database must be sized for its own peak, so if peaks are short and rare, most of the paid capacity sits idle.
## How an elastic pool works
An **elastic pool** is a set of resources (compute, memory, storage) that you buy once for a group of databases on the same logical server.
- A busy database can use more of the pool while it peaks; idle databases use little or nothing.
- You can set minimum and maximum resources per database so one tenant cannot take everything.
- You pay for the pool, not for each database, which gives a predictable budget.
Pools fit best when databases have **large differences between peak and average use** and their peaks do not all happen at the same time.
## Example
Twenty databases that each peak at 90 units but average under 5 can share a pool of 100 units instead of buying 20 separate databases sized for 90.
W: Elastic pool: databases in a pool share one set of resources bought for the group, so their scattered, unpredictable peaks are covered by capacity that is paid for once instead of 300 times. This is the scenario Learn uses to introduce elastic pools.
X: A=Business Critical for each database: a higher tier gives each database more dedicated resources and costs more, the opposite of the cost saving the company wants.
B=Larger SQL Server VM: moving to IaaS adds operating system and backup work, and a VM sized for combined peaks still pays for idle capacity; elastic pools solve this in the PaaS service.
C=One shared database on Managed Instance: merging the customers into one database is an application redesign, not a cost setting, and it removes the per-customer database isolation the app relies on.
T: Many databases with varying, unpredictable usage that peak at different times call for an Azure SQL Database elastic pool.
V: Azure SQL Database

@ DP-900 D2 T2.1 applied use-case
S: A developer writes `CREATE TABLE Product (ID INT PRIMARY KEY, Name VARCHAR(20) NOT NULL, Price DECIMAL NULL);`. Which statement about the new table is correct?
A: Name holds whole numbers, because VARCHAR stores integer values of up to twenty digits in length.
B: ID may repeat across rows, because a PRIMARY KEY sorts the rows rather than enforcing uniqueness.
C: Price must have a value in each row, because DECIMAL columns are mandatory in relational tables.
D: ID uniquely identifies each row, Name is a mandatory text column, and Price may be left empty as NULL.
K: D
G: ## Reading a CREATE TABLE statement
Inside the parentheses each column gets a name, a **data type** and optional rules:
- `INT`: an integer (whole number). `DECIMAL`: a decimal number. `VARCHAR(20)`: variable-length character (text) data, up to 20 characters here.
- `NOT NULL`: a **mandatory** column; every row must supply a value.
- `NULL` (or no nullability clause): the column may be empty in a row.
- `PRIMARY KEY`: the column uniquely identifies each row.
## Example
`INSERT INTO Product (ID, Name, Price) VALUES (99, 'Drill', NULL);` succeeds: Price may be NULL. Leaving out Name would fail.
W: Read each column: ID is the primary key (unique per row), Name is `VARCHAR(20) NOT NULL` (mandatory text) and Price is `DECIMAL NULL` (optional), exactly as stated.
X: A=VARCHAR holds numbers: VARCHAR stores variable-length character (text) data; whole numbers would use INT.
B=ID may repeat: a primary key enforces uniqueness; its job is to identify each row, not to sort rows.
C=Price is mandatory: Price is declared `NULL`, so rows may omit it; a data type alone does not make a column mandatory.
T: In CREATE TABLE, the data type sets what a column holds, NOT NULL makes it mandatory, and PRIMARY KEY makes it the unique row identifier.

@ DP-900 D3 T3.2 applied tradeoff
S: A company already uses Azure Cosmos DB for its mobile app. It now wants interactive dashboards and large batch analysis over years of sales history for its data analysts. What does Microsoft recommend for this analytical workload?
A: Running the analysts' large aggregate queries directly against the app's Cosmos DB containers during business hours.
B: Creating a second Cosmos DB account with the Apache Gremlin API, because graph queries are built for sales dashboards.
C: Moving the app's data into Azure Table storage, because a key-value store is built for batch analysis of sales history.
D: Mirroring the operational data into Microsoft Fabric, with no ETL pipeline to build, and doing the reporting work there.
K: D
G: ## Operational versus analytical workloads
- An **operational** (OLTP) workload reads and writes small amounts of data per request, many times a second: a cart update, a profile read.
- An **analytical** (OLAP) workload scans and aggregates large volumes of data: sales by month over five years.
Azure Cosmos DB is built for the first kind. Learn names its good fits as latency-sensitive, highly elastic, high-throughput and mission-critical apps, and lists analytical workloads (interactive, streaming and batch analytics for data analysts and scientists) as a **poor fit**, pointing to **Microsoft Fabric** instead.
## Keeping both
Cosmos DB data can be brought into Fabric without building an ETL pipeline (Fabric mirroring), so the app keeps its fast database and the analysts work in an analytics platform.
W: Mirror into Microsoft Fabric: Learn lists analytical workloads (interactive, streaming and batch analytics) as a poor fit for Cosmos DB and points to Fabric for them. Fabric mirroring copies the data without an ETL pipeline, so the analysts work in an analytics platform while the app stays on Cosmos DB.
X: A=Large queries on the app's containers: big scans and aggregations consume request units and compete with the app's own traffic, and this is exactly the workload Learn calls a poor fit.
B=Gremlin API account: the Gremlin API is for graph data such as social networks; it is another operational API of Cosmos DB, not an analytics platform for dashboards.
C=Azure Table storage: Table storage is a simple key-value store for fast lookups by key, not an analytics engine for aggregations over years of history.
T: Cosmos DB serves operational app data; large-scale analytics (OLAP) belongs in Microsoft Fabric.
