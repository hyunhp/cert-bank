@ DP-900 D4 T4.2 applied definition
S: A credit card company sends each customer one bill a month that lists all of that month's purchases, instead of a bill after every purchase. Which kind of data processing does this describe?
A: Stream processing, because each purchase is read as an event the moment the card is swiped at the shop.
B: Batch processing, because the month's purchases are collected and stored, then processed together in one run.
C: Real-time processing, because the billing system watches the purchase feed and reacts within a few seconds.
D: Transactional processing, because each purchase is written to the database as a separate atomic operation.
K: B
G: ## Two ways to process data
Data processing turns raw data into useful information. Learn describes two general approaches:
- **Batch processing**: new data records are collected and stored first, and then the whole group is processed together in a single operation.
- **Stream processing**: a data source is monitored constantly, and each new data event is processed as it arrives.
## When a batch runs
A batch can be triggered in several ways: on a schedule (every hour, every night, once a month), when a certain amount of data has arrived, or by some other event.
## Example
Learn's own example of batch processing is credit card billing: the customer does not get a bill per purchase but one monthly bill for all purchases in that month. The purchases pile up, and the billing job processes the whole month at once.
W: Batch processing: the purchases are gathered over a period (a month) and then processed together in one job, which is exactly the definition of a batch. The delay between a purchase and the bill is normal and accepted here.
X: A=Stream processing: streaming would handle each purchase as it happens and produce a result immediately; the scenario explicitly waits a month and processes everything together.
C=Real-time processing: nothing in the billing process reacts within seconds; results only appear when the monthly run finishes, which is the opposite of real time.
D=Transactional processing: recording each purchase is an OLTP operation, but the question is about producing the monthly bill, which processes many stored records together as a batch.
T: Collect first, process the whole group later (for example, one monthly bill) = batch processing.

G: ## Time-critical work needs streaming
In **stream processing**, each new piece of data is processed when it arrives. There is no waiting for the next batch interval, so results are available in seconds or milliseconds.
Learn says stream processing is ideal for **time-critical operations that require an instant response**, and uses this exact kind of system as an example: a building monitor that must trigger alarms and unlock doors immediately when there is a fire.
## Why batch does not fit
Batch processing always has a delay between data arriving and results being produced, because data waits until the batch runs. That delay is fine for reports and bills, but not for safety actions.
## Example
A sensor reports 70 °C at 10:02:15. A streaming query sees the reading at once, matches the "fire" condition and calls the alarm system a moment later. A batch job scheduled for 11:00 would react 58 minutes too late.
W: Stream processing: each reading is checked the moment it arrives, so the alarm and door actions happen immediately, which is what a safety system requires.
X: A=Hourly batch: readings wait up to an hour before they are checked, which is far too slow for a fire.
B=Batch on data volume: the trigger depends on how many readings have piled up, not on how urgent they are, so a fire could go unnoticed until the file is big enough.
D=Nightly warehouse load: keeping history is useful for later analysis, but a load that runs once a night cannot react to a fire as it happens.
T: When a result must trigger an action immediately, use stream processing, not batch.

G: ## How batch and streaming differ
Learn lists four differences beyond the basic "collect then process" versus "process on arrival":
- **Data scope**: batch can process all the data in the dataset; streaming typically sees only the most recent data, or the data inside a rolling time window (for example, the last 30 seconds).
- **Data size**: batch handles large datasets efficiently; streaming handles individual records or micro-batches of a few records.
- **Performance (latency)**: batch latency is typically a few hours; stream processing usually happens immediately, with latency of seconds or milliseconds.
- **Analysis**: batch is used for complex analytics; streaming is used for simple response functions, aggregates and calculations such as rolling averages.
## Example
A traffic dashboard shows cars counted in the last minute (streaming, rolling window). A yearly traffic report reads every count ever stored (batch, full dataset).
W: A=Rolling window scope: a streaming query usually sees only recent events or a time window such as the last 30 seconds, not the whole history.
D=Low latency: stream processing occurs as data arrives, so results come within seconds or milliseconds.
X: B=Hours of latency: a delay of a few hours is the typical latency of batch processing, not streaming.
C=Complex analytics on full history: reading every record for complex analysis is the batch pattern; streaming focuses on simple functions and aggregates such as rolling averages.
E=All input prepared first: needing all input ready and checked before the job starts is listed by Learn as a disadvantage of batch processing.
T: Streaming = recent data or a rolling window, simple aggregates, seconds or milliseconds; batch = all data, complex analysis, hours.

C=Straight into Power BI: Power BI is a visualization tool that sits on top of data stores; Learn's pattern stores the history in an analytical data store, not inside report visuals.

G: ## The common elements of a streaming solution
Products differ, but Learn describes the same four elements in most stream processing architectures:
- **An event** generates data, for example a sensor signal, a social media post or a log entry.
- **A streaming source** captures the data: in simple cases a folder or a database table, in advanced cases a queue that keeps events in order and processes each event once.
- **A perpetual query** processes the event data, selecting certain types of events, projecting values, or aggregating values over temporal (time-based) windows.
- **An output (sink)** receives the results: a file, a database table, a real-time dashboard, or another queue for a downstream query.
## Why "perpetual"
A normal query runs once and returns a result. A streaming query never finishes: it keeps running and produces new results as new events arrive.
## Example
"Count the sensor emissions per minute" runs all day and emits a new count every minute.
W: Continuous query over events: the perpetual query is the processing step that keeps running and filters, projects or aggregates events over time windows as they arrive.
X: A=One-time copy of history: a query that runs once and copies everything is a batch load, the opposite of a query that never stops.
C=Defining the event format: agreeing on event structure is the job of a schema (for example a schema registry), not of the query that processes events.
D=Nightly rebuild: a scheduled nightly job is batch processing; a perpetual query works continuously while events stream in.
T: Stream architecture = event, streaming source, perpetual (always-running) query, output sink.

G: ## Where a stream starts
A streaming solution needs a **source** that can accept a constant flow of events from many producers and hand them to processing. On Azure, Learn lists Azure Event Hubs, Azure IoT Hub, Azure Data Lake Storage Gen2 and Apache Kafka as common sources.
## Azure Event Hubs
- A fully managed (PaaS) real-time data streaming platform that can ingest millions of events per second with low latency.
- Producers send events to an **event hub**, which stores them in **partitions**. Events within a partition are delivered in order, and delivery is at least once.
- Consumers (for example a Stream Analytics job, a Fabric eventstream or a Spark job) read the events independently.
- Events are kept for a configurable retention period, so a consumer that falls behind can catch up.
## Example

W: Azure Event Hubs: it is the Azure ingestion service built for high volumes of event data, and it is one of the most common sources for stream processing on Azure.
X: B=Azure SQL Database: it can store events and appear as an output, but it is a transactional database, not an event ingestion service built for millions of incoming events.
C=Azure Files: a file share read nightly turns the design into batch processing, and it is not built for constant event ingestion.
D=Power BI: Power BI is where processed results are visualized (a sink), not the managed service that ingests raw events from thousands of devices.
T: High-volume event ingestion as a streaming source on Azure = Azure Event Hubs.

@ DP-900 D4 T4.2 applied use-case
S: A streaming job must report the number of events from each sensor for every one-minute period, with no overlap, so that each event is counted exactly once. Which kind of time window fits?
A: A hopping window of five minutes that moves forward every minute, so each event appears in five results.
B: A tumbling window of one minute, which splits the stream into fixed, non-overlapping one-minute segments.
C: A session window, which groups events that arrive close together and closes after a period with no events.
D: A sliding window of one minute, which produces a result whenever an event enters or leaves the window.
K: B
G: ## Why streams use windows
A stream never ends, so "count all events" has no final answer. Streaming queries therefore aggregate over **temporal windows**, time periods that give each result a start and an end. Azure Stream Analytics supports five window types:
- **Tumbling**: fixed-size, contiguous, **non-overlapping** segments. Each event belongs to exactly one window.
- **Hopping**: fixed-size windows that hop forward by a smaller period, so they overlap and one event can be in several results.
- **Sliding**: emits output only when the window's contents change (an event enters or leaves).
- **Session**: groups events that arrive close together and closes after a timeout with no data.
- **Snapshot**: groups events that have the same timestamp.
## Example
With `TumblingWindow(minute, 1)`, events at 10:00:10 and 10:00:50 are counted in the 10:00 to 10:01 window, and an event at 10:01:05 starts the next one.
W: Tumbling window: it divides time into contiguous, fixed, non-overlapping periods, so each event lands in exactly one one-minute count, which matches the requirement.
X: A=Hopping window: hopping windows overlap when the hop is smaller than the window, so an event is counted in several results; the requirement forbids overlap.
C=Session window: session windows vary in length with the gaps in the data, so they cannot give a count for every fixed minute.
D=Sliding window: sliding windows emit a result whenever the contents change and events can fall into more than one result, not one count per fixed minute.
T: Fixed, non-overlapping periods where every event is counted once = tumbling window.

G: ## Spark for streaming
Apache Spark splits processing across a cluster of machines and handles both **batch** and **stream** processing. On Azure it runs in Microsoft Fabric and Azure Databricks, with code in Python, Scala, Java, R or SQL.
## Spark Structured Streaming
Structured Streaming is a library built into Spark. Learn's way of picturing it: a live stream treated like a table that keeps growing as new data arrives.
1. Connect to a streaming source, such as Azure Event Hubs, a folder of files or a network feed.

@ DP-900 D4 T4.2 applied tradeoff
S: A team writes events from Spark Structured Streaming into a data lake. It wants the same table to receive the live stream and also serve batch queries for history, with protection against partial writes. What should it write to?
A: A folder of CSV files, one per micro-batch, which batch jobs read later by listing every file in the folder.
B: An Azure Event Hubs event hub, which keeps the processed events in partitions that batch queries read directly.
C: A Delta Lake table, which tracks changes reliably and can be both a streaming sink and a batch query source.
D: A Power BI report, which stores the streamed rows inside its visuals and lets analysts query their history later.
K: C
G: ## The problem with plain files
By default a data lake is just a collection of files. Nothing guarantees that a write finished completely, that every file has the same structure, or that a reader sees a consistent set of files while a stream is still writing.
## Delta Lake
Delta Lake is an open-source storage format that makes data lake storage behave more like a database. Learn lists three key benefits:
- **Reliability**: changes are tracked, so partial or failed writes do not corrupt the data.
- **Schema enforcement**: data must match a defined structure before it is accepted.
- **Unified batch and streaming**: the same Delta table can be a streaming sink (written in real time) and a source for batch queries, so you do not need separate stores for live and historical data.
The Spark runtimes in Microsoft Fabric and Azure Databricks include built-in support for Delta Lake.
## Example
A streaming query appends sensor readings to a Delta table every few seconds, while an analyst runs a SQL query over the same table for last quarter's averages.
W: Delta Lake table: it tracks changes so failed writes do not corrupt data and it lets one table act as both the streaming sink and the batch source, which are the two requirements.
X: A=CSV files per micro-batch: plain files give no protection against partial writes or schema drift, and readers can see an incomplete set of files.
B=Event hub: an event hub is a short-term ingestion buffer with limited retention, not a table store for historical batch queries.
D=Power BI report: a report visualizes data from a store; it is not a storage format that a Spark stream writes into for later queries.
T: Spark Structured Streaming plus Delta Lake gives one reliable table for both real-time ingestion and historical analysis.
