@ DP-900 D1 T1.1 advanced use-case
S: An online grocer exports each order as a JSON document. Every order has an order number, a customer ID and a date, plus an array of line items whose length varies from one to more than eighty. The data must be loaded into a relational data warehouse with a fixed schema, and no line item may be lost. How should the data be modeled in the warehouse?
A: Create an Orders table for order-level fields and an OrderLines table with one row per line item, linked to its order by order number.
B: Create one wide Orders table with columns LineItem1 through LineItem100, leaving the unused columns empty for orders with fewer items.
C: Keep only the first line item of each order in the Orders table and store a count of the remaining items in a separate column.
D: Store each complete JSON document as a binary image file in the warehouse, because nested arrays can never be represented in relational tables.
K: A
G: ## Turning semi-structured data into structured tables
Semi-structured data has some structure but allows variation between instances. A JSON order is a good example: every order has the same top-level fields, but the **array** of line items has a different length each time.
A relational table is **structured**: a fixed schema where every row has the same columns. A repeating group (a list of values whose length varies) does not fit into a single row, so relational design moves it into its own table:
- An `Orders` table holds one row per order (order number, customer ID, date).
- An `OrderLines` table holds one row per line item, with the order number as a foreign key back to `Orders`.
## Example
Order `1001` with three items becomes one row in `Orders` and three rows in `OrderLines`, each carrying `OrderNo = 1001`. An order with eighty items simply adds eighty rows; the schema does not change.
W: Orders plus OrderLines: a separate child table holds any number of line items as rows, linked by a key, so the fixed schema stays the same while every item is kept.
X: B=LineItem1 to LineItem100 columns: repeating columns waste space, break as soon as an order has more items than columns, and make queries over all items awkward. This is the kind of design normalization removes.
C=First item plus a count: this throws away line items, which breaks the requirement that no item may be lost.
D=JSON as a binary file: arrays can be represented relationally as related rows, and storing the documents as opaque binary objects would make the data unusable for SQL queries in the warehouse.
T: To load a variable-length array from semi-structured data into a fixed relational schema, move it into a child table with one row per element, linked by a key.
V: Data warehouse

@ DP-900 D1 T1.1 advanced comparison
S: A logistics company is cataloguing its data sources before choosing data stores. The list includes shipment rows exported from its ERP system with the same nine columns, customs declarations in XML where some elements appear only for certain goods, JSON tracking events in which newer scanners add extra fields, and photos of damaged parcels. Which TWO sources are semi-structured data? (Select TWO)
A: The customs declarations in XML, because elements and attributes give them structure while optional elements vary between declarations.
B: The JSON tracking events, because each event is self-describing with field names, yet the set of fields differs between scanners.
C: The ERP shipment rows, because a header row names the nine fields and the values follow the same order in every exported row.
D: The photos of damaged parcels, because the camera adds a timestamp and location to each image file when the photo is saved.
E: All four sources, because any data that is stored in a file instead of a database table is classified as semi-structured data by default.
K: A,B
G: ## Three ways to represent data
- **Structured** data follows a fixed schema: every record has the same fields, usually as rows and columns in a table.
- **Semi-structured** data has some structure, but individual records can vary. Fields are described inside the data itself (JSON names, XML tags), so one record can have extra or missing fields.
- **Unstructured** data, such as documents, images, audio and video, has no field-and-value structure that applications can query directly.
## How to classify a source
Ask whether every record must have the same fields. If yes, it is structured, even when it is stored in a file. If the records describe their own fields and can differ, it is semi-structured. If there are no fields at all, it is unstructured.
## Example
A CSV export with a header and nine columns in every row is structured. A JSON event where some scanners add a `temperature` field is semi-structured. A JPEG photo is unstructured, even if the file has some metadata.
W: A=XML customs declarations: XML uses tags for elements and attributes, and optional elements that appear only for some goods are exactly the variation that makes data semi-structured.
B=JSON tracking events: JSON names every field, and newer scanners adding fields means records in the same feed have different shapes, the classic semi-structured case.
X: C=ERP shipment rows: a fixed set of nine columns in the same order in every row is a fixed schema, so this is structured data even though it arrives as a file.
D=Parcel photos: the content of an image is raw binary data that must be interpreted by an application; a little file metadata does not turn a photo into semi-structured data.
E=Everything in files: the storage location does not decide the category. Files can hold structured (CSV), semi-structured (JSON, XML) or unstructured (images) data.
T: Classify data by its shape, not by where it is stored: fixed fields = structured, self-describing and varying = semi-structured, no fields = unstructured.
V: JSON, XML

@ DP-900 D1 T1.1 advanced use-case
S: A furniture retailer keeps product photos in object storage and product details in a relational database. It now wants shoppers to upload a picture of a chair and see products that look similar, even when no product name or tag matches the shopper's words. The catalog database must stay as it is. What kind of data must the retailer generate from the photos to support this search?
A: Vector embeddings, numerical representations of each photo's content that AI applications compare to find semantically similar items.
B: A CSV file per photo that lists the image's file name, size and upload date, so that a keyword search can compare the photos.
C: An XML description of each photo's folder path, so that photos stored in the same folder are returned as the most similar matches.
D: A new Category column in the relational product table, so that a SQL query returns every product in the same category that the shopper typed.
K: A
G: ## Vector data
Learn lists a newer kind of data that organizations work with alongside structured, semi-structured and unstructured data: **vector data**, also called **embeddings**. An embedding is a list of numbers that represents the content of something such as a text or an image. Items with similar content get vectors that are close to each other, so an AI application can find content that is **semantically similar** instead of matching keywords.
## Why it fits this case
- The photos themselves are unstructured, so a database cannot compare their content directly.
- File names, sizes and tags only match when words match; the shopper may type nothing at all.
- Embeddings are generated from the photos and stored next to the existing data, so the catalog database can stay as it is.
## Example
A shopper uploads a photo of a green armchair. The app converts it into a vector and returns the products whose image vectors are nearest, including a "teal lounge seat" that shares no words with the query.
W: Vector embeddings: they encode what each photo looks like as numbers, so the application can compare the shopper's photo with the catalog photos and return the closest matches without any keyword overlap.
X: B=CSV of file properties: name, size and upload date say nothing about what is in the picture, so two similar chairs would not be found.
C=XML of folder paths: the folder a photo sits in is an organizational choice, not a measure of visual similarity.
D=Category column: a category still depends on the shopper's words and returns everything in the category, not the items that look like the uploaded photo. It would also change the catalog database.
T: To search unstructured content by meaning instead of keywords, generate vector embeddings and compare them for similarity.
V: Vector data

@ DP-900 D1 T1.2 advanced use-case
S: A healthcare analytics team stores patient-visit data in a data lake as files that Apache Spark processes. Regulators now require that individual records can be corrected or deleted on request, and auditors must be able to see the table as it was before each change. The team wants to keep an open file format that Spark reads natively. Which file format should it use?
A: Delta Lake, which builds on Parquet and adds a transaction log for ACID transactions, data versioning and reliable record updates.
B: CSV, because plain text files can be opened in an editor so that a single record can be corrected or deleted directly by hand.
C: Avro, because its JSON header records the schema and each new file automatically keeps a full history of every earlier version of the file.
D: XML, because each element is tagged, so a changed record can keep its earlier values in an extra attribute for the auditors to read.
K: A
G: ## Data lake files and their limits
A data lake is a collection of files. Common formats each have strengths:
- **CSV** is human-readable delimited text.
- **Parquet** is a columnar format widely used in data lakes and lakehouses; it compresses well and lets queries read only the columns they need.
- **Avro** is row-based; a JSON header describes the schema and the data is stored as binary blocks.
None of these on its own tracks changes: updating a record means rewriting files, and nothing records which version existed before.
## Delta Lake
Delta Lake is an open-source storage format that builds on Parquet by adding a **transaction log**. The log enables:
- **ACID transactions**, so partial or failed writes do not corrupt the table.
- **Reliable updates and deletes** of individual records.
- **Data versioning**, so earlier versions of a table can be queried.
Both Microsoft Fabric and Azure Databricks use Delta Lake as their table format.
## Example
A record for visit `V-881` is corrected on 3 March. A query of the current table shows the new value, and a query of the table version from 2 March shows the old one for the auditors.
W: Delta Lake: the transaction log turns Parquet files into tables that support record-level updates and deletes with ACID guarantees and keep earlier versions, while Spark still reads the format natively.
X: B=CSV: editing a text file by hand gives no transactions and no history, so auditors could not see the earlier version, and manual edits do not scale to a data lake.
C=Avro: the header describes the schema of the file; it does not keep a history of earlier versions or provide transactional updates of single records.
D=XML: XML is a verbose interchange format, and an extra attribute holding old values is a hand-made workaround, not versioning. Spark analytics also do not use XML as a lake table format.
T: When data lake files need record-level updates, deletes and history, use Delta Lake: Parquet plus a transaction log.
V: Delta Lake, Apache Spark

@ DP-900 D1 T1.2 advanced use-case
S: A start-up is planning the data stores for its new e-commerce platform on Azure. It must store millions of product images served to browsers, shopping carts held as JSON whose shape changes often and that shoppers on several continents update with low latency, and orders that need ACID transactions and joins with customer data. Which THREE choices fit these needs? (Select THREE)
A: Store the product images as blobs in Azure Blob Storage, which keeps large amounts of unstructured binary data and serves it over HTTP.
B: Store the shopping carts in Azure Cosmos DB, a globally distributed NoSQL database with flexible JSON items and low-latency access.
C: Store the orders in Azure SQL Database, a relational PaaS database that enforces ACID transactions and supports table joins.
D: Store the orders in Azure Table storage, because its tables enforce foreign keys and support multi-table joins with the related customer data.
E: Store the shopping carts in an Azure Files share, so that every shopper's browser mounts the share and edits the cart file over SMB.
F: Store the product images inside Azure SQL Database rows, because a relational table is the cheapest store for large media files.
K: A,B,C
G: ## Matching data to Azure data stores
Each kind of data has a natural home on Azure:
- **Unstructured files** (images, video, documents): **Azure Blob Storage**, object storage that holds binary large objects and serves them over HTTP or HTTPS.
- **Semi-structured, fast-changing data with global users**: **Azure Cosmos DB**, a schema-agnostic NoSQL database that replicates data to the regions you add and gives low-latency reads and writes.
- **Structured, transactional data with relationships**: a relational database such as **Azure SQL Database**, which enforces ACID transactions, keys and constraints and lets you join tables.
## Example
A product page loads the photo from `https://<account>.blob.core.windows.net/images/chair-42.jpg`, reads the cart from Cosmos DB in the nearest region, and the checkout writes the order and its lines to Azure SQL Database in one transaction.
W: A=Blob Storage for images: Blob Storage is built for massive amounts of unstructured data and makes it available to browsers over HTTP.
B=Cosmos DB for carts: Cosmos DB stores JSON items whose shape can vary and replicates them to several regions for low-latency access near each shopper.
C=Azure SQL Database for orders: a relational database gives ACID transactions and joins between orders and customers, which the order process needs.
X: D=Table storage for orders: Table storage is a NoSQL key/attribute store for data that does not need complex joins, foreign keys or stored procedures, so it cannot meet the join and integrity needs.
E=Azure Files for carts: file shares are mounted by computers over SMB or NFS; browsers do not mount shares, and a shared file gives no low-latency, per-shopper database operations across continents.
F=Images in SQL rows: storing large media files in a relational database is costly and puts load on the transactional system; object storage is the intended store for binary files.
T: Unstructured files go to Blob Storage, flexible global JSON to Cosmos DB, and transactional related data to a relational database such as Azure SQL Database.
V: Azure Blob Storage, Azure Cosmos DB, Azure SQL Database

@ DP-900 D1 T1.2 advanced comparison
S: A statistics office publishes a daily 2 GB table. Hundreds of citizens download it and open it in spreadsheet programs, and the office's own Apache Spark jobs read it to compute trends that usually touch only five of its 120 columns. The office wants each audience to get a suitable format at the lowest processing cost. Which approach fits best?
A: Publish CSV for citizens because it is human-readable, and a Parquet copy for Spark because its columnar layout reads only needed columns.
B: Publish Parquet for citizens because spreadsheets read binary columns fastest, and keep a CSV copy for Spark because plain text compresses best.
C: Publish XML for both audiences, because angle-bracket tags make the file readable to people and also let Spark skip unneeded columns.
D: Publish one Avro file for both audiences, because its row-based layout is human-readable and lets Spark read only five of the columns.
K: A
G: ## Human-readable versus optimized formats
Learn explains that the choice of file format depends on the type of data, the applications that read it, and whether people need to read it.
- **Delimited text (CSV)** maps bytes to printable characters. Anyone can open it in a text editor or spreadsheet, but it is not optimized for size or processing.
- **Parquet** is a **columnar** format. Data for each column is stored together inside row groups, and the file's metadata lets an application locate just the columns and rows it needs. It compresses well and is the standard in data lakes.
- **Avro** is a **row-based** binary format with a JSON header that describes the schema; it is good for compressing data and for writing whole records, but it is not meant to be opened by people.
## Example
A Spark query that needs 5 of 120 columns reads only those 5 column chunks from Parquet, while it would have to scan every character of every row in CSV.
W: CSV for citizens, Parquet for Spark: each audience gets the format built for it. CSV opens in any spreadsheet, and Parquet's columnar storage lets Spark read only the five columns it needs.
X: B=Parquet for spreadsheets, CSV for Spark: this reverses the strengths. Typical spreadsheet users cannot open Parquet, and CSV is the least efficient format for Spark column queries.
C=XML for both: XML is verbose text and has largely been replaced by JSON; it is not columnar, so Spark still reads entire documents.
D=One Avro file: Avro is binary and row-based, so it is neither readable in a spreadsheet nor able to skip unneeded columns the way a columnar format can.
T: Use human-readable formats such as CSV for people and optimized columnar formats such as Parquet for analytical engines that read a few columns.
V: Parquet, CSV

@ DP-900 D1 T1.3 advanced troubleshooting
S: An inventory database has a rule that the quantity in stock can never be negative. A warehouse clerk submits a transaction that ships 12 units of an item when only 9 are in stock. The database rejects the whole transaction and the stock level stays at 9, while other clerks' transactions continue normally. Which ACID property is the database enforcing when it refuses this change?
A: Consistency, because a transaction may only move the data from one valid state to another state that satisfies the database's rules.
B: Durability, because committed changes must survive a restart, so the database refuses changes that it cannot save permanently to disk.
C: Isolation, because concurrent transactions must not interfere, so any change that conflicts with other clerks' work is cancelled at once.
D: Availability, because the database must keep serving other clerks, so it drops any transaction that would slow the system down.
K: A
G: ## The four ACID properties
OLTP systems use transactions with ACID semantics:
- **Atomicity**: a transaction succeeds completely or fails completely.
- **Consistency**: a transaction can only take the data from one **valid state** to another. Rules such as constraints (stock cannot be negative, an order must refer to an existing customer) define what valid means.
- **Isolation**: concurrent transactions cannot interfere with each other or see each other's half-finished work.
- **Durability**: once committed, a change stays committed, even after a power failure.
## Reading the scenario
The transaction was not interrupted and did not clash with another transaction. It was rejected because its result (stock of `-3`) would break a rule of the database. Protecting valid states is consistency.
## Example
`CHECK (QuantityInStock >= 0)` on the `Stock` table makes the database refuse any transaction that would end with a negative quantity; the table keeps its last valid value.
W: Consistency: the rule defines which states are valid, and the database refuses a transaction whose result would break it, so the data moves only between valid states.
X: B=Durability: durability is about keeping committed transactions after a failure. This transaction was never committed, and disk space was not the problem.
C=Isolation: isolation keeps concurrent transactions from seeing or disturbing each other's intermediate work. Nothing here conflicted with another clerk; the change itself broke a rule.
D=Availability: availability is not one of the ACID properties, and a database does not drop transactions for being slow.
T: Consistency in ACID means a transaction can only move the data from one valid state to another; a change that would break a rule is rejected.
V: Relational database

@ DP-900 D1 T1.3 advanced comparison
S: A hospital group reviews five of its data activities: admitting a patient while updating bed availability, recording each medication dose given and reducing pharmacy stock, a monthly readmission-rate dashboard covering five years, data scientists exploring years of anonymized records in notebooks, and a nightly job that aggregates the day's visits. Which TWO activities are transactional (OLTP) workloads? (Select TWO)
A: Admitting a patient and updating bed availability, because both changes must be recorded together and reliably as they happen.
B: Recording each medication dose and reducing pharmacy stock, because each small write must complete as a unit that keeps data valid.
C: The monthly readmission-rate dashboard, because it reads large amounts of historical data and therefore needs strict ACID transactions.
D: Data scientists exploring years of records, because notebooks create, update and delete individual rows in the operational database.
E: The nightly aggregation job, because it processes the whole day's visits in one large operation instead of one small operation per event.
K: A,B
G: ## Transactional versus analytical work
**Transactional (OLTP)** systems record business events as they happen: many small create, read, update and delete (CRUD) operations, each applied as an ACID transaction so the data stays valid. They support live line-of-business applications.
**Analytical** processing works on large volumes of historical data in read-only or read-mostly stores to find trends and support decisions. It includes reports and dashboards, exploration by data scientists, and batch jobs that aggregate data.
## Quick test
- Does the activity change operational records the moment something happens, and must several changes succeed or fail together? Transactional.
- Does it read lots of history, summarize it or explore it? Analytical.
## Example
"Assign bed 4B to patient 1182 and mark 4B occupied" is one transaction. "Show readmissions per month since 2021" is an analytical query.
W: A=Admission and bed update: both changes describe one live event and must succeed or fail together, which is a typical OLTP transaction.
B=Medication dose and stock: each dose is a small write that must update two records as one unit and keep stock valid, again OLTP.
X: C=Readmission dashboard: it reads five years of history to show a trend; that is analytical work on a read-optimized store, not a transactional workload.
D=Data science exploration: exploring historical records in notebooks is interactive analytical work, and it reads data rather than changing operational rows.
E=Nightly aggregation: summarizing a whole day at once is batch analytical processing, typically loading results for reports the next morning.
T: OLTP records live events as small ACID transactions; dashboards, exploration and nightly aggregations are analytical workloads.
V: OLTP, OLAP

@ DP-900 D1 T1.3 advanced troubleshooting
S: A retailer's sales managers use a semantic model, an aggregated analytical model built from the data warehouse, because its drill-down from region to store is almost instant. On Tuesday, finance corrected Monday's sales in the warehouse, but the managers still see the old Monday totals. The data team wants to keep the fast drill-down. What explains the stale totals, and what should the team do?
A: The model stores preaggregated values that are calculated when it is loaded, so it must be refreshed after the warehouse data changes.
B: The warehouse rolled back finance's correction because analytical stores are read-only, so the team must rerun the correction on the OLTP system.
C: Semantic models keep only the first version of each day's data, so the team must delete and rebuild the whole model with new hierarchies.
D: The drill-down hierarchy caches results per region, so the team must remove the hierarchy and let managers query the warehouse tables directly.
K: A
G: ## Why analytical models are fast
In a common analytics architecture, data flows from operational systems into a data lake or data warehouse, and then into an **OLAP model**, today usually called a **semantic model** (historically a cube). The model holds **measures** aggregated across **dimensions** and their hierarchies, such as sales by region, city and store.
Because values are aggregated when the model is loaded and refreshed, queries return almost instantly; but the model only knows the data it held at its last refresh.
## The trade-off
- Fast drill-down comes from data that is prepared ahead of time.
- Changes in the warehouse appear in the model only after the model is refreshed (processed) again.
## Example
The model was refreshed Monday night. Finance changed Monday's figures on Tuesday at 10:00. Until the next refresh, the model still shows the Monday-night values.
W: Preaggregated model needs a refresh: the model's aggregates reflect the data at its last load, so refreshing it after the correction brings in the new totals while keeping the fast drill-down.
X: B=Warehouse rolled back the change: being read-mostly for users does not mean the warehouse undoes corrections loaded into it, and the problem is in the model, not in the warehouse.
C=Only the first version kept: models do not lock in the first version of a day; a normal refresh picks up changed data without redesigning hierarchies.
D=Remove the hierarchy: the hierarchy is what gives the fast drill-down the managers want, and querying the warehouse directly gives up the speed instead of fixing the freshness.
T: Semantic (OLAP) models are fast because they aggregate data ahead of time; they show changes only after they are refreshed.
V: Semantic model

@ DP-900 D1 T1.3 advanced use-case
S: A research institute keeps raw instrument files, JSON logs and CSV exports for its data scientists, who use Spark notebooks. Its analysts also need SQL tables with enforced schemas over the same curated data, and the institute does not want to maintain a second copy of the data in a separate database. Which kind of analytical data store fits these needs best?
A: A data lakehouse, which keeps the files in a data lake and adds relational tables in Delta format that a SQL endpoint can query.
B: A relational data warehouse only, loading every file into tables so that raw instrument files can be explored in notebooks.
C: A data lake of CSV and JSON files only, because schema-on-read lets analysts enforce a schema on the files when data is written.
D: An OLTP database tuned for analysis, so that notebooks and SQL users share one normalized schema built for many small transactions.
K: A
G: ## Data lake, data warehouse and lakehouse
- A **data lake** is a file store for structured, semi-structured and unstructured data. It applies a schema **on read**, so no structure is enforced when files are written. Data scientists like it for exploration with Spark.
- A **data warehouse** is a relational database with a schema optimized for analytics. It is a good choice when data fits a structured schema and users query it with SQL.
- A **data lakehouse** combines them: the data stays as files in the lake, and table formats such as **Delta Lake** add relational capabilities on top, including schema enforcement. A **SQL analytics endpoint** exposes the tables to SQL users.
## Example
In a Fabric lakehouse, raw files live under `Files/`, curated Delta tables under `Tables/`, notebooks read both, and analysts query the tables through the SQL analytics endpoint, all from one copy in OneLake.
W: Data lakehouse: it serves notebooks on raw files and SQL users on schema-enforced Delta tables from the same storage, so no second copy in another database is needed.
X: B=Warehouse only: loading everything into relational tables does not suit raw instrument files and still leaves the data scientists without the file-based lake they work in.

- Separate each **entity** (customer, product, order) into its own table.
- Separate each **discrete attribute** into its own column.
- Identify each row uniquely with a **primary key**.

G: ## Temporal windows in stream processing
A perpetual query often aggregates events over time windows. Azure Stream Analytics offers five kinds: tumbling, hopping, sliding, session and snapshot.
- **Tumbling**: fixed-size, non-overlapping, contiguous windows; an event belongs to exactly one window.
- **Hopping**: fixed-size windows that hop forward by a fixed period, so they can **overlap** and be emitted **more often than the window size**; an event can belong to several windows.
- **Sliding**: emits only when the content of the window changes (an event enters or leaves).
- **Session**: groups events that arrive close together, separated by periods of no data.
- **Snapshot**: groups events that have the same timestamp.

`GROUP BY HoppingWindow(minute, 15, 5)` emits at 10:05 (09:50-10:05), 10:10 (09:55-10:10) and so on; a bag scanned at 10:01 appears in three results.
W: Hopping window: a 15-minute window that hops every 5 minutes gives an overlapping 15-minute count every 5 minutes.
X: B=Tumbling window: tumbling windows never overlap; a 15-minute tumbling window emits only every 15 minutes.
C=Session window: session windows depend on gaps in the data, not on a fixed 15-minute size and 5-minute schedule.
D=Snapshot window: snapshot windows group events with identical timestamps; they do not cover a 15-minute period.
T: For overlapping fixed-size windows emitted more often than their size, use a hopping window; tumbling windows never overlap.

@ DP-900 D4 T4.3 advanced troubleshooting
S: A Power BI model has a Sales table with Revenue and Cost columns. An analyst added a calculated column MarginPct = (Revenue - Cost) / Revenue for each row and shows its average in a matrix by region. Finance says the regional margins are wrong, because a region's margin must equal total profit divided by total revenue for whatever is filtered. What should the analyst build instead?
A: A measure that divides the sum of profit by the sum of revenue, so it is calculated at query time for the current filter context.
B: A second calculated column that stores each row's revenue share, because calculated columns are recalculated when a slicer changes.
C: A hierarchy on the MarginPct column, so that the matrix averages the row-level margins correctly as users drill down by region.
D: A pie chart of the MarginPct column, because pie charts sum the row values and show each region's margin as a share of the total.
K: A
G: ## Measures versus calculated columns
- A **calculated column** is computed **row by row** when data is loaded or refreshed and stored in the table. Aggregating it (sum, average) aggregates the stored row values.
- A **measure** is calculated **at query time** in the current filter context, such as the region, year or slicer selection of a visual. Ratios that must hold for any group are measures.
## Why the average is wrong
The average of row-level percentages gives every sale the same weight. A tiny sale with a 90% margin counts as much as a large sale with 10%.
## Example
Two sales: revenue 100 cost 10 (90%), revenue 1,000 cost 900 (10%). The average of the percentages is 50%, but total profit / total revenue is 190 / 1,100 = 17.3%.
`Margin % = DIVIDE(SUM(Sales[Revenue]) - SUM(Sales[Cost]), SUM(Sales[Revenue]))`
W: Measure: a measure computes total profit over total revenue for whatever the visual or slicer filters, so every region, year or product gets the correct weighted margin.
X: B=Another calculated column: calculated columns are computed per row at refresh, not per filter selection, so they cannot produce a correct ratio for every grouping.
C=Hierarchy on MarginPct: hierarchies are for drilling through levels of a dimension; they do not change how row values are aggregated.
D=Pie chart of MarginPct: changing the visual does not fix the calculation, and summing percentages is even less meaningful than averaging them.
T: Values that must be recomputed for each filter, such as ratios of totals, belong in measures; calculated columns are fixed row by row at refresh.

@ DP-900 D4 T4.3 advanced comparison
S: An analyst builds a Power BI semantic model over an on-premises SQL Server sales database. Users need the fastest possible interaction with visuals, data that is up to a day old is acceptable, and the database's administrators want report queries to put as little load as possible on the source during business hours. Which storage mode should the analyst use?
A: Import mode, which loads the data into an in-memory columnar store and refreshes it on a schedule, such as once each night.
B: DirectQuery mode, which sends each visual's query to the SQL Server database so that every interaction reads the current data.
C: Direct Lake mode, which loads Delta tables from OneLake into memory and therefore reads the on-premises tables without copying.
D: Live editing in Power BI Desktop, which keeps the .pbix file connected to the database so that each user queries it from their laptop.
K: A
G: ## Storage modes in a Power BI semantic model
- **Import**: data is copied into the model, stored in the in-memory columnar **VertiPaq** engine, and refreshed on a schedule. Queries are fast and do not hit the source; data is as fresh as the last refresh.
- **DirectQuery**: no data is imported; each visual sends queries to the source. Data is current, but performance depends on the source, and every interaction adds load to it.
- **Direct Lake** (Microsoft Fabric): loads **Delta tables from OneLake** into memory. It needs data that is already in OneLake as Delta tables.
## Reading the scenario
Fast interaction, day-old data acceptable and minimal load on the source during the day point to Import with a nightly refresh.
## Example
The model refreshes at 02:00 through a data gateway; during the day hundreds of users slice the data in memory while the SQL Server sees no report queries.
W: Import mode: VertiPaq gives the fastest visuals, a nightly refresh meets the one-day freshness, and daytime report use does not query the source.
X: B=DirectQuery: every interaction queries SQL Server, which adds daytime load and is usually slower; its benefit, current data, is not needed here.
C=Direct Lake: it reads Delta tables in OneLake; the data here sits in an on-premises SQL Server database, not in OneLake.
D=Live .pbix connections: sharing a Desktop file is not a storage mode, and every user's laptop would query the database directly.
T: Import gives the fastest Power BI performance and no source load between refreshes; DirectQuery trades speed and source load for current data.
