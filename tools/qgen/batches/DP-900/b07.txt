@ DP-900 D4 T4.1 applied definition
S: A data engineer describes a nightly process: data is read from the order database, cleaned and reshaped on a separate processing engine, and only then written into the analytical store. What is this process called?
A: Extract, transform, load (ETL), because the data is changed before it is written to the destination store.
B: Extract, load, transform (ELT), because the data is changed using the compute power of the destination store.
C: Reverse ETL, because curated data is pushed from the analytical store back into an operational application.
D: Change data capture, because only the rows that changed since the last run are copied to the analytical store.
K: A
G: ## Getting data into an analytical store
Large-scale analytics usually starts with **data ingestion and processing**: data from transactional databases, files and other sources is copied into a data lake or a relational data warehouse, and cleaned, filtered and restructured for analysis on the way.
## Where the transformation happens
The two classic patterns differ only in **when and where** the data is transformed:
- **ETL (extract, transform, load)**: data is extracted, transformed on a separate engine (often using staging tables), and the finished result is loaded into the analytical store.
- **ELT (extract, load, transform)**: data is extracted and copied into the target store as it is, then transformed there using the target's own compute.
## Example
A retailer extracts yesterday's orders, removes duplicates and converts currencies in a processing step, and then loads the clean rows into warehouse tables. The warehouse only ever sees transformed data: that is ETL.
W: ETL: the order is extract, then transform on a separate engine, then load, so the analytical store receives data that is already cleaned and reshaped.
X: B=ELT: in ELT the raw data is loaded first and transformed inside the target store. Here the transformation happens before the write, on a separate engine.
C=Reverse ETL: reverse ETL moves curated data out of an analytical store into operational tools such as a CRM. This process moves data in the usual direction, into analytics.
D=Change data capture: CDC is a way to pick up only changed rows from a source. It says nothing about where the data is transformed, and the stem describes a full clean-and-reshape step.
T: ETL transforms data before loading it into the analytical store; ELT loads raw data first and transforms it in the store.
V: Microsoft Fabric

S: A company is building a new lakehouse with elastic compute. Data scientists want the untouched source data kept for future, still-unknown analyses. Which TWO statements explain why an ELT approach suits this design? (Select TWO)
A: ELT copies the source data into the store first, so the raw data is preserved and can be transformed again later in new ways.
B: ELT uses the processing power of the target store for transformations, so scaling the lakehouse compute also scales the pipeline.
C: ELT requires a separate transformation server in front of the store, so heavy business rules never consume any lakehouse compute.
D: ELT validates and cleans every record before the write, so the lakehouse never contains duplicates or badly formatted raw files.
E: ELT only works with small datasets, so it keeps lakehouse storage costs low by refusing to load files larger than a set limit.
K: A,B
G: ## ELT in a nutshell
In **extract, load, transform (ELT)** the data is copied into the target store first and transformed there afterwards. The transformation uses the target's own engine (for example Spark notebooks or SQL in a lakehouse) instead of a separate transformation server.
## When Learn recommends ELT
The Azure Architecture Center lists these reasons to choose ELT:
- The target is a modern data warehouse or **lakehouse with elastic compute scaling**.
- You need to **preserve raw data** for exploratory analysis or future schema changes.
- The transformation logic benefits from the target system's native capabilities.
## When ETL is still better
ETL fits when the target system is constrained and heavy transformations must run elsewhere, when complex business rules need a specialized engine, or when compliance requires audited staging before loading.
W: A=Raw data preserved: because data lands in the store before any change, the original copy stays available, and new transformations can be written later for questions nobody has asked yet.
B=Target compute does the work: ELT removes the separate transformation engine and uses the store's processing power, so scaling the lakehouse compute also scales the transformation work.
X: C=Separate transformation server: that is the ETL pattern. ELT deliberately removes the separate engine and transforms data inside the target store.
D=Clean before the write: validating every record before it is written is also ETL behavior. In ELT the raw, possibly messy data is loaded first and cleaned afterwards.
E=Only small datasets: the opposite is true. Typical ELT use cases are big data workloads, where skipping extra copy steps saves time on large datasets.
T: Choose ELT when the target (lakehouse or modern warehouse) has elastic compute and you want to keep raw data for future transformations.

G: ## Elements of large-scale analytics
Learn describes a typical analytics architecture as a set of layers:
- **Data ingestion and processing**: ETL or ELT processes load data from sources into an analytical store, often on distributed multi-node clusters.
- **Analytical data store**: a relational data warehouse, a file-based data lake, or a hybrid lakehouse.
- **Analytical data model**: a layer that makes the data easier to report on.
- **Data visualization**: reports, dashboards and self-service analysis.
## The analytical data model
Analysts can query the store directly, but it is common to build a model on top. Historically these were **cubes** with pre-aggregated values (for example total sales by product and region). Today the preferred approach is a **semantic model**, the tabular model behind Power BI and Microsoft Fabric. It defines tables, relationships, hierarchies and measures written in DAX, and computes aggregations at query time.
W: Analytical data model: this is the layer whose job is to describe tables, relationships, hierarchies and measures so that reports and dashboards are easier to build. In Fabric and Power BI it is the semantic model.
X: B=Data ingestion: ingestion moves and processes data into the store. It does not define the relationships and measures that report authors use.
C=Analytical data store: the store holds the data itself. The question describes the layer analysts would otherwise skip when they query the store directly.
D=Data visualization: visualizations consume the model to show trends and KPIs. They are the output, not the layer that defines measures and hierarchies.
T: Ingestion loads the data, the store holds it, the semantic model describes it for reporting, and visualization presents it.
V: Microsoft Fabric, Power BI

G: ## What a pipeline is
In Fabric Data Factory (and in Azure Data Factory) a **pipeline** is a workflow made of **activities**. An activity can copy data, run a stored procedure, run a notebook, call a dataflow and more.
- Activities can run **in sequence or in parallel**.
- Pipelines can contain control-flow logic such as loops and conditions.
- Pipelines can run **on a schedule** or be **triggered by events**.
- Pipelines use connections to reach sources and destinations, and can write results to a lakehouse, a warehouse or another supported destination.
## Orchestration
Because one pipeline chains many steps, it is the tool for **orchestrating** ingestion and transformation: the place that decides what runs, in which order, and when.
W: Data Factory pipeline: pipelines chain activities such as copy, stored procedure and notebook into one workflow, run them in order or in parallel, and run on a schedule, which matches every requirement.

C=Semantic model: a semantic model describes data for reporting. It does not orchestrate data movement or run processing steps.
D=SQL analytics endpoint: the endpoint lets you query lakehouse tables with T-SQL. It is a query surface, not a workflow tool that runs notebooks on a schedule.
T: To orchestrate several ingestion and transformation steps on a schedule in Fabric, use a Data Factory pipeline.

G: ## Zero-copy access with shortcuts
A **shortcut** in OneLake is a reference to data stored somewhere else: another workspace in OneLake, Azure Data Lake Storage, Azure Blob storage, Amazon S3, Google Cloud Storage and other sources. The files and folders look as if they were stored in your lakehouse, but **no data is copied or moved**.
## Why it matters
- Data can stay where it is for **compliance or cost** reasons and still be queried from Fabric.
- No pipelines are needed to keep a copy up to date: the shortcut points to the source, so analysts see the current data.
- Teams can share data between workspaces without duplicating it.
## Shortcut or copy?
If you need a transformed copy in OneLake, use a pipeline or dataflow. If the data must stay in place, use a shortcut.
W: OneLake shortcut: shortcuts are live references to external storage such as Amazon S3. The data stays in the bucket, nothing is duplicated, and the lakehouse can still query it together with other data.
X: B=Copy activity: a copy activity creates a second copy of the files in OneLake, which breaks the rule that data must not be copied.
C=Dataflow Gen2: a dataflow also writes its output to a destination, so it produces a copy of the data in the lakehouse.
D=Database mirroring: mirroring replicates operational databases (such as Azure SQL Database or Azure Cosmos DB) into OneLake, which copies data. An S3 bucket of files is not a mirroring source in this sense, and copying is not allowed.
T: Data must stay where it is but be usable in Fabric → OneLake shortcut (zero-copy).

G: ## Three kinds of analytical store
- **Data warehouse**: a relational database with a schema optimized for analytics, often a star schema of fact and dimension tables, queried with SQL.
- **Data lake**: a file store, usually on a distributed file system, processed with engines like Apache Spark, often schema on read.
- **Data lakehouse**: a **hybrid** that combines both. Raw data is stored as **files in a data lake**, and a **SQL analytics endpoint** exposes those files as tables.
## What makes a lakehouse possible
Lakehouses are enabled by **Delta Lake**, the open-source table format used by both Microsoft Fabric and Azure Databricks. Delta Lake adds relational capabilities on top of Parquet files: tables with schemas, transactional consistency, support for batch and streaming loads, and a SQL API.
W: Files in a lake queried as tables: a lakehouse keeps data as files in a data lake and uses a table format (Delta Lake) plus a SQL endpoint, so the same files support both Spark processing and SQL queries.
X: B=Relational warehouse only: fact and dimension tables in a relational database describe a classic data warehouse. A lakehouse keeps its data as files in the lake.
C=Operational database for everything: running analytics on the live transactional database is not a separate analytical store at all, and it is not what a lakehouse means.
D=Cubes: pre-aggregated cubes are a historical form of the analytical data model, not an analytical store that keeps raw files.
T: Lakehouse = data lake files + a table layer (Delta Lake) and SQL access, combining lake flexibility with warehouse-style querying.
V: Microsoft Fabric, Azure Databricks

@ DP-900 D4 T4.1 advanced definition
S: Both Microsoft Fabric and Azure Databricks store lakehouse tables in Delta Lake format. Which TWO capabilities does Delta Lake add on top of plain Parquet data files? (Select TWO)
A: A file-based transaction log that gives ACID transactions, so concurrent writes do not leave a table half-updated.
B: A table history in which each write creates a new version, so earlier versions of the table can still be queried.
C: A proprietary binary format that only one analytics engine can read, which keeps the data locked to one vendor.
D: A row-by-row storage layout tuned for single-record updates, so it can replace the transactional order database.
E: An automatic copy of every table into a relational database, so SQL queries never need to read the data lake files.
K: A,B
G: ## Parquet and Delta Lake
**Parquet** is an open, columnar file format: good compression and fast analytical scans, but a folder of Parquet files on its own is just files. Nothing stops a reader from seeing a half-finished write.
**Delta Lake** is open-source software that **extends Parquet data files with a file-based transaction log**. That log gives:
- **ACID transactions**: a write either completes fully or not at all, even with concurrent readers and writers.
- **Schema enforcement**: data that does not match the table's schema is rejected.
- **Versioning (time travel)**: each write creates a new table version, and you can query previous versions through the table history.
- One copy of data for both **batch and streaming** processing.
## Why both platforms use it
Delta Lake is the default table format in Azure Databricks, and Fabric stores lakehouse and warehouse tables as Delta tables in OneLake. Because the transaction log protocol is open, different engines can read the same tables.
W: A=Transaction log with ACID: Delta Lake adds a file-based transaction log to Parquet files, which provides ACID transactions so readers never see partial writes.
B=Versions and history: each write to a Delta table creates a new version, and the transaction log lets you review changes and query earlier versions (time travel).
X: C=Proprietary format: Delta Lake is open source with an open transaction log protocol, and it is chosen precisely so that many engines can read the same data.
D=Row-by-row OLTP layout: Delta tables sit on columnar Parquet files built for analytics. They are not designed to replace a transactional order database.
E=Automatic copy to a relational database: Delta Lake adds table features to the files in the lake itself. SQL engines read the Delta tables directly; no separate relational copy is made.
T: Delta Lake = Parquet files + a transaction log, giving ACID transactions, schema enforcement and versioned tables.
V: Microsoft Fabric, Azure Databricks

**OneLake** is the single, tenant-wide, logical data lake for Microsoft Fabric. It is often compared to OneDrive: every Fabric workload uses it automatically, the way Office apps use your organization's OneDrive.

X: C=Storage account per workspace: workspaces are containers inside the single OneLake, not separate storage accounts. There is no OneLake storage to provision or size; the region comes from the workspace's capacity.
D=Only relational tables: OneLake is a data lake. Lakehouses in it hold both tables and files, including semi-structured and unstructured data.
E=One copy per engine: the opposite is true. OneLake's design goal is one copy of data that every engine reads without duplication.
T: OneLake = one automatic, tenant-wide data lake on ADLS Gen2, with open Delta tables shared by every Fabric engine.

The **medallion architecture** organizes lakehouse data into layers of increasing quality. Fabric documents it as the recommended design approach, and Azure Databricks recommends it as a best practice.

D=Semantic model: the semantic model is a reporting layer on top of the store. Data cleaning belongs in the lakehouse layers, not in report definitions.
T: Medallion: bronze = raw as it arrived, silver = cleaned and validated, gold = curated for reporting.
