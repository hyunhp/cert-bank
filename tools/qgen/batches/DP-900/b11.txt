@ DP-900 D1 T1.2 expert use-case
S: A fleet-telematics company is choosing Azure data stores for three kinds of data. Trip records arrive with the same twelve fields, and billing runs transactions that join them with customer contracts. Driver feedback from the mobile app is JSON with nested objects and optional fields, and the support team filters it by properties inside the nested objects. Dashcam clips must be served directly to the support portal in a web browser over HTTPS. Costs should stay reasonable, but every requirement must be met. Which THREE choices fit? (Select THREE)
A: Store the trip records in Azure SQL Database, a relational service that enforces the fixed schema and runs transactions joining trips with contracts.
B: Store the driver feedback in Azure Cosmos DB for NoSQL, which keeps JSON items with nested objects and indexes their properties by default.
C: Store the dashcam clips as block blobs in Azure Blob Storage, which holds unstructured binary data and serves each clip to browsers over HTTPS.
D: Store the driver feedback in Azure Table storage, which keeps nested JSON objects inside each entity and filters on any property within those objects.
E: Store the dashcam clips in an Azure Files SMB share, which the support portal's users mount inside their web browsers to stream each of the clips on demand.
F: Store the trip records in Azure Blob Storage as CSV files, which billing then joins with contract files inside each storage transaction it runs.
K: A,B,C
G: ## Matching data shape to a data store
The DP-900 skill "Identify Azure datastores for common use cases" comes down to the shape of the data and how it is used:
- **Structured data used in transactions with relationships**: a relational database such as **Azure SQL Database** (fixed schema, ACID transactions, joins).
- **Semi-structured JSON with nesting and optional fields**: a document store such as **Azure Cosmos DB for NoSQL**. Items in a container do not need the same shape, and Cosmos DB indexes all item properties by default, so queries can filter on nested properties.
- **Unstructured binary files served to users**: **Azure Blob Storage**, whose block blobs suit large, discrete objects that change rarely and are read over HTTP or HTTPS.
## The hidden detail
The feedback is filtered by properties **inside nested objects**. Azure Table storage entities are flat sets of name-value properties (plus partition key, row key and timestamp), so it does not query inside nested JSON.
## Example
`SELECT * FROM f WHERE f.vehicle.model = "E-Van"` runs against the Cosmos DB feedback container; clip `trip-8812.mp4` is linked from the portal at its blob URL.
W: A=Azure SQL Database for trips: a fixed twelve-field schema and transactions that join trips with contracts are classic relational, OLTP needs.
B=Cosmos DB for NoSQL for feedback: it stores JSON items with nesting and optional fields and indexes properties automatically, so nested properties can be filtered.
C=Blob Storage for clips: block blobs are designed for large binary objects such as video and are served directly over HTTPS.
X: D=Table storage for feedback: Table storage is a key/attribute store with flat properties per entity; it does not hold and query nested JSON objects the way a document database does.
E=Azure Files for clips: Azure Files shares are mounted by operating systems over SMB or NFS; browsers do not mount file shares, so this does not serve clips to a web portal.
F=CSV files for trips: Blob Storage has no relational transactions or joins between files, so billing could not run its transactional joins there.
T: Relational data with transactions goes to Azure SQL Database, nested JSON queried by property to Cosmos DB for NoSQL, and media files to Blob Storage.
V: Azure SQL Database, Azure Cosmos DB, Azure Blob Storage, Azure Table storage

@ DP-900 D1 T1.2 expert comparison
S: An energy company lands meter readings in its data lake. A gateway writes each reading as a separate record as soon as it arrives, so files are written record by record. The readings' structure changes a few times a year when new fields are added, and the landing files must carry a description of their own structure so that older and newer files can both be read. Downstream, analysts run Spark queries that read only three of the sixty fields across billions of readings. Which approach to file formats fits best?
A: Land the readings as Avro, a row-based format whose JSON header describes the schema, then convert them to columnar Parquet for analytical queries.
B: Land the readings as Parquet, a columnar format suited to writing one record at a time, then convert them to Avro so that the analysts can read only three fields.
C: Land the readings as CSV with a header row that describes the schema, then keep CSV for analytics because Spark reads three fields from each text row.
D: Land the readings as Avro, then keep Avro for the analytical queries, because its row-based layout lets Spark skip the fifty-seven unneeded fields.
K: A
G: ## Row-based and columnar formats
Learn describes two optimized formats that are both Apache projects:
- **Avro** is **row-based**. Each file has a header, stored as JSON, that describes the structure of the data; the records follow as binary blocks. Applications use the header to parse the records. Writing whole records one after another fits this layout.
- **Parquet** is **columnar**. Data for each column is stored together in row groups, and metadata lets an application locate the columns and rows it needs, so queries that touch a few columns read far less data.
CSV is human-readable text with an optional header of field names, but it does not describe data types or make column reads efficient.
## The constraints in this scenario
1. Records are written one at a time as they arrive: a row-based write pattern.
2. Files must describe their own structure as it evolves: a schema in the file header.
3. Analytics read 3 of 60 fields over billions of rows: a columnar format.
No single choice is best at all three, so the data is landed in one format and converted for analysis.
## Example
`landing/2026/11/17/readings-0001.avro` is written by the gateway; a nightly Spark job converts each day into Parquet files under `curated/readings/`.
W: Avro for landing, Parquet for analytics: Avro's row layout and self-describing JSON header fit record-by-record writes with an evolving structure, and Parquet's columnar layout lets Spark read only the three fields it needs.
X: B=Parquet then Avro: this reverses the strengths. Parquet is the columnar format suited to reading a few columns, and Avro, being row-based, does not let readers skip unneeded fields.
C=CSV throughout: a header row only names fields; it does not describe types or evolving structure, and Spark must scan every character of every row to read three fields.
D=Avro throughout: Avro handles the landing well, but its row-based layout stores whole records together, so analytics cannot skip the 57 unneeded fields as they could with a columnar format.
T: Use a row-based, self-describing format such as Avro to land records as they arrive, and a columnar format such as Parquet for analytical queries over a few columns.
V: Avro, Parquet

@ DP-900 D1 T1.1 expert comparison
S: A data governance team is writing classification rules for its catalog. Its examples include an API export in JSON where every record has exactly the same eight fields with no nesting, Parquet files produced from a relational table whose column names and types are stored in the file's metadata, CSV files with a header row, and scanned PDF contracts that a database stores in a binary column. The team must classify by the shape of the data, not by the file extension or by where it is stored. Which TWO rules are correct? (Select TWO)
A: JSON records that all share the same fixed fields can be treated as structured data, because JSON suits both structured and semi-structured data.
B: Parquet files built from a relational table hold structured data, even though the file is binary and cannot be read in a text editor by a person.
C: CSV files with a header row are semi-structured data, because the field names are stored inside the file itself rather than in a separate schema definition.
D: Scanned PDF contracts become structured data once they are stored in a binary column of a relational table, because the table has a fixed schema.
E: Any JSON file is semi-structured data by definition, because the JSON format always allows records in the same file to have different fields.
K: A,B
G: ## Shape, not container
Learn's definitions are about the **shape** of the data:
- **Structured**: a fixed schema; every record has the same fields, usually as rows and columns.
- **Semi-structured**: some structure, but records can vary (optional, repeated or nested fields).
- **Unstructured**: no field structure, such as documents, images, audio, video and other binary files.
Learn also notes that **JSON is a flexible format that is good for both structured and semi-structured data**, and that **Parquet** is an optimized columnar format whose metadata describes the data in it.
## Common traps
- A file being **binary** (Parquet) does not make it unstructured; a binary image or PDF is unstructured because its content has no fields.
- Storing an image or PDF in a database column does not give its **content** a schema.
- A CSV header just names the fixed columns that every row has; the data is still structured.
## Example
`{"id":1,"sku":"A7","qty":4,...}` with the same eight fields in every record is structured data written in JSON; `{"id":2,"tags":["x"],"extra":{...}}` with varying fields is semi-structured.
W: A=Fixed-field JSON is structured: when every record has the same fields, the data follows a fixed schema; JSON is only the notation, and Learn says it suits both structured and semi-structured data.
B=Parquet from a table is structured: the data keeps the table's fixed columns and types, recorded in the file's metadata; being binary is about encoding, not shape.
X: C=CSV with header is semi-structured: a header names the same columns that every row must have, so the data is structured; the location of the field names does not change that.
D=PDFs in a binary column are structured: the table only stores the files as opaque binary values; the contract content still has no fields, so it remains unstructured data.
E=Any JSON is semi-structured: JSON allows variation but does not require it, so records with identical fixed fields are structured data written in JSON.
T: Classify data by whether its records share fixed fields: the file format, encoding or storage location does not decide the category.
V: JSON, Parquet, CSV

@ DP-900 D1 T1.3 expert use-case
S: A lakehouse team ingests raw CRM and web-log data every hour into Microsoft Fabric. Data scientists insist that the exact records received from each source are always kept, because business rules change and they rebuild downstream tables from scratch a few times a year. Analysts need tables with duplicates removed and data types standardized. Power BI reports must read aggregated, business-ready tables that answer questions such as revenue by region and month, without repeating heavy calculations. How should the team organize the data?
A: Keep the raw records unchanged in a bronze layer, write cleansed, deduplicated tables to a silver layer, and build aggregated reporting tables in gold.
B: Cleanse and deduplicate the records as they land in the bronze layer, copy them to a silver layer for reports, and keep raw backups in the gold layer.
C: Keep the raw records in a silver layer, write the aggregated reporting tables to a bronze layer, and expose cleansed tables to analysts in a gold layer.
D: Load the records straight into aggregated gold tables for reporting, and rebuild the raw data from the gold layer whenever the business rules change.
K: A
G: ## The medallion architecture
A common way to organize lakehouse data in both Microsoft Fabric and Azure Databricks uses three layers:
- **Bronze**: raw data ingested as-is from the sources, with **no transformations**, preserving the original records for **reprocessing**.
- **Silver**: cleansed and conformed data, with **duplicates removed** and **data types standardized**.
- **Gold**: **aggregated, business-ready** data modeled for specific reporting and analytics.
Learn notes that teams use this pattern because each layer is a clear quality boundary, and data can always be reprocessed from the original bronze records when requirements change.
## Mapping the requirements
1. Exact source records kept for rebuilds: bronze.
2. Deduplicated, typed tables for analysts: silver.
3. Aggregated tables for Power BI: gold.
## Example
`bronze.web_logs` keeps every JSON line as received; `silver.page_views` removes duplicate hits and casts timestamps; `gold.revenue_by_region_month` feeds the Power BI report.
W: Bronze raw, silver cleansed, gold aggregated: this is the medallion pattern, and keeping bronze untouched is what lets the data scientists rebuild silver and gold after a rule change.
X: B=Cleanse in bronze: changing data as it lands destroys the exact source records, so nothing remains to rebuild from, and gold is not a backup layer.
C=Layers reversed: silver and gold hold processed data, and bronze is the raw layer; putting aggregates in bronze breaks the quality boundaries the pattern relies on.
D=Straight to gold: aggregated tables cannot be turned back into the detailed source records, so rebuilds after a rule change would be impossible.
T: Medallion layers: bronze keeps raw data for reprocessing, silver holds cleansed and deduplicated data, gold holds aggregated business-ready data.
V: Microsoft Fabric, Azure Databricks

@ DP-900 D2 T2.2 expert use-case
S: A SaaS provider hosts 40 customer databases on Azure SQL Database. Most customers are small, each busy for an hour or two at a different time of day and quiet otherwise, and the provider wants to minimize total cost without starving any database at its peak. One customer is a hospital group whose contract states that its database must never share compute resources with any other customer's database. The provider wants to stay on Azure SQL Database. Which TWO actions fit these requirements? (Select TWO)
A: Place the 39 smaller customer databases in an elastic pool, so they share one set of resources and each can use more capacity during its own peak.
B: Deploy the hospital group's database as a single database with its own resources, outside the elastic pool that the other customers share.
C: Place all 40 databases, including the hospital group's, in one elastic pool, because a pool keeps each database's compute separate from the others.
D: Deploy each of the 39 smaller databases as its own single database sized for its peak, because pools cost more when peaks happen at different times.
E: Move the hospital group's database into the elastic pool and give it the highest priority, so that its compute is reserved and never shared.
K: A,B
G: ## Single databases and elastic pools
Azure SQL Database offers two deployment models:
- **Single database**: one database with its own allocated resources, managed through a logical server.
- **Elastic pool**: several databases share a set of resources, such as memory, storage and processing power, through multiple tenancy. It suits databases whose resource needs **vary over time**, and it can reduce costs compared with sizing every database for its own peak.
## Why staggered peaks favour a pool
If 39 databases each need high capacity for one or two hours at different times, buying peak capacity 39 times wastes money most of the day. A pool is sized for the combined load, and each database can use more of the pool while it is busy.
## The hidden constraint
A pool, by design, **shares** resources among its databases. The hospital contract forbids sharing, so that one database stays out of the pool as a single database.
## Example
`pool-standard` holds `cust01` to `cust39`; `cust-hospital` is a single database on the same logical server with its own resources.
W: A=Pool for the 39 smaller databases: staggered peaks are the pattern elastic pools are designed for, so they share capacity and cost less than 39 peak-sized databases.
B=Single database for the hospital group: a single database has its own resources, which satisfies the contract that forbids sharing compute with other customers.
X: C=All 40 in one pool: databases in a pool share its resources, which is exactly what the hospital contract forbids.
D=39 peak-sized single databases: paying for each database's peak separately is the costly approach that pools avoid when peaks are staggered.
E=Hospital in the pool with priority: a pool's resources are shared among its databases; placing the database in the pool still breaks the no-sharing contract.
T: Elastic pools cut cost for many databases with varying, staggered load; keep a database that must not share resources as a single database.
V: Azure SQL Database

@ DP-900 D2 T2.1 expert use-case
S: A Product table in Azure SQL Database already holds 80,000 rows that other tables reference by ProductID. A release script must add a SupplierName column to it, fill that column for every existing row by looking up each product's supplier in the Supplier table, and let the reporting_role database role query Product without being able to change it. All existing rows and their keys must be kept, and the table must not be recreated. Which sequence of statements meets these requirements?
A: `ALTER TABLE Product ADD SupplierName ...`, then `UPDATE Product SET SupplierName = ...` from Supplier, then `GRANT SELECT ON Product TO reporting_role`.
B: `DROP TABLE Product` and `CREATE TABLE Product` with SupplierName, then `INSERT` the rows again, then `GRANT SELECT ON Product TO reporting_role`.
C: `ALTER TABLE Product ADD SupplierName ...`, then `INSERT INTO Product` the supplier names from Supplier, then `GRANT SELECT ON Product TO reporting_role`.
D: `ALTER TABLE Product ADD SupplierName ...`, then `UPDATE Product SET SupplierName = ...` joined to Supplier, then `GRANT UPDATE ON Product TO reporting_role`.
K: A
G: ## Three kinds of SQL statement in one script
- **DDL** (Data Definition Language) changes database objects: `CREATE`, `ALTER`, `DROP`, `RENAME`. `ALTER TABLE ... ADD` adds a column and keeps the existing rows.
- **DML** (Data Manipulation Language) works with rows: `SELECT`, `INSERT` (adds new rows), `UPDATE` (changes values in existing rows), `DELETE`.
- **DCL** (Data Control Language) manages permissions: `GRANT`, `DENY`, `REVOKE`.
## Filling a new column
A new column starts empty (NULL) in every existing row. To fill it you **update** those rows; `INSERT` would add 80,000 new rows instead.
## Example
```
ALTER TABLE Product ADD SupplierName NVARCHAR(100) NULL;
UPDATE p SET p.SupplierName = s.Name
FROM Product p JOIN Supplier s ON p.SupplierID = s.SupplierID;
GRANT SELECT ON Product TO reporting_role;
```
W: ALTER, UPDATE, GRANT SELECT: ALTER TABLE adds the column without touching the rows, UPDATE fills it in the existing rows from Supplier, and GRANT SELECT gives the role read-only access.
X: B=DROP and CREATE: dropping the table deletes it and its rows; recreating it breaks the requirement that the table is not recreated and risks changing keys.
C=INSERT the supplier names: INSERT adds new rows rather than filling a column in existing ones, so the 80,000 rows would still have no supplier name.
D=GRANT UPDATE: UPDATE permission lets the role change data in Product, but the role must only query the table.
T: Add a column with ALTER TABLE, fill existing rows with UPDATE (not INSERT), and grant read-only access with GRANT SELECT.
