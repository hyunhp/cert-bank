@ DP-900 D2 T2.1 applied definition
S: A bookshop designs a relational database with a Customer table, a Book table and an Order table. In the Customer table, what does a single row represent?
A: One attribute that is recorded for every customer, such as the email address of each person.
B: One instance of the customer entity, holding all of the recorded data for a single customer.
C: One data type that the database allows in the table, such as text, integer or date values.
D: One relationship that links the Customer table to the Order table through a matching value.
K: B
G: ## Tables, rows and columns
A relational database models the real-world things you want to record, called **entities**, as **tables**. In a retail system you might have tables for customers, products, orders and the line items inside an order.
- A **row** is one instance of the entity: one customer, one product, one order.
- A **column** is one attribute that every row has: `FirstName`, `Email`, `City`.
- Every row in a table has the **same columns**, which is what makes relational tables a format for structured data.
## Example
In a `Customer` table, the row for customer 17 holds that customer's name, email and city. The `Email` column holds the email address of every customer in the table.
W: One entity instance: each row in an entity table stores the data for exactly one occurrence of that entity, so one row in Customer is one customer.
X: A=One attribute for every customer: that describes a column, which runs down every row and holds the same attribute (such as email) for all customers.
C=One allowed data type: data types are properties of columns (an `Email` column stores text), not something a row represents.
D=One relationship to another table: relationships are made by storing a key value (a foreign key) in a column, not by a whole row of the Customer table.
T: Table = entity, row = one instance of the entity, column = one attribute shared by every row.

@ DP-900 D2 T2.1 applied use-case
S: A Customer table has a MiddleName column. Many customers have no middle name, or the company does not know it. How should the column be defined so these customers can still be stored?
A: Define the column as the primary key so the database fills in a unique value for each row that has none.
B: Define the column as NOT NULL so the database stores an empty text string whenever no value is supplied.
C: Define the column as nullable so rows can be saved with no value, which the database records as NULL.
D: Define the column as a foreign key so the missing value is looked up from a related table automatically.
K: C
G: ## Mandatory and optional columns
Every row in a relational table has the same columns, but not every column needs a value in every row.
- A column defined with `NOT NULL` is a **mandatory** column: every row must supply a value.
- If you leave out `NOT NULL` (or write `NULL`), the column is **optional**. A row with no value in that column holds a **NULL**, meaning "no value / unknown".
## Example
```
CREATE TABLE Customer (ID INT PRIMARY KEY, FirstName VARCHAR(30) NOT NULL, MiddleName VARCHAR(30) NULL, ...)
```
A customer called "Ana Silva" is stored with `MiddleName` set to NULL.
W: Nullable column: an optional column accepts rows with no value and records the missing value as NULL, which is exactly what customers with no or unknown middle name need.
X: A=Primary key: a primary key identifies each row and its columns can't be NULL, so it would block the missing values instead of allowing them, and the database does not invent middle names.
B=NOT NULL: this makes the column mandatory, so a row without a middle name would be rejected rather than stored with a default empty string.
D=Foreign key: a foreign key links a row to a row in another table; it doesn't fill in missing attribute values and a middle name is not a reference to another entity.
T: NOT NULL makes a column mandatory; a nullable column lets a row have no value, stored as NULL.

@ DP-900 D2 T2.1 applied tradeoff
S: A sales spreadsheet stores "Jane Smith, 42 Oak St Seattle" in one cell and the price "9.99 USD" as text. The team moves it into a relational table with a separate column for each attribute. Which TWO benefits does this give? (Select TWO)
A: Each value can be constrained to a suitable data type, such as decimal for prices and integer for quantities.
B: The table no longer needs a primary key, because every column now holds just one separate piece of data.
C: Queries can easily filter on a single attribute, such as finding only the customers who live in Seattle.
D: The table can store a different set of columns for each row, so every customer keeps only the fields it uses.
E: The database stops needing data types at all, because one value per column is already clear to every reader.
K: A,C
G: ## One attribute per column
A simple rule of normalization is: **separate each discrete attribute into its own column**. A spreadsheet cell that holds "name, street, city" mixes three attributes.
Splitting them gives two benefits that Microsoft Learn calls out:
- **Data types**: each column stores one data type, so a `Price` column can be `DECIMAL` and a `Qty` column `INT`. The database then rejects text like "nine" in a price column.
- **Query granularity**: you can filter, sort and group on one attribute, for example `WHERE City = 'Seattle'`.
## What does not change
Every row still has the same columns, and each table should still have a primary key to identify its rows.
W: A=Suitable data types: once an attribute is in its own column, the column can be defined as decimal, integer, date or text, so each value is constrained to the right type.
C=Filter on one attribute: a separate `City` column lets a query select only Seattle customers, which is hard when city is buried inside an address string.
X: B=No primary key needed: splitting attributes has nothing to do with identifying rows; each table should still have a primary key.
D=Different columns per row: relational tables are structured, so every row has the same columns; a flexible set of fields per item describes semi-structured data instead.
E=No data types needed: the opposite is true, because the main gain of separate columns is that each one gets a specific data type.
T: One attribute per column lets each value have the right data type and makes filtering on that attribute easy.

@ DP-900 D2 T2.1 applied definition
S: An Employee table has an EmployeeID column. Every employee gets a different EmployeeID, and the database must reject any row that repeats an existing ID or leaves it empty. What is EmployeeID?
A: A foreign key, because it stores a value that refers to a row in another table of the database.
B: An index, because it holds a sorted copy of the column with pointers back to the table rows.
C: A view, because it presents a virtual table built from the results of a SELECT query on the data.
D: A primary key, because it uniquely identifies each row and can't hold duplicate or NULL values.
K: D
G: ## Primary keys
Normalization says: **uniquely identify each entity instance (row) using a primary key**. A primary key is a column, or a set of columns, whose value is different for every row.
In SQL Server and Azure SQL:
- A table can have **only one** primary key constraint.
- All primary key columns are **NOT NULL**; the database sets them that way automatically.
- The database enforces uniqueness by creating a **unique index** on the key, which also speeds up lookups by ID.
## Example
```
CREATE TABLE Employee (EmployeeID INT PRIMARY KEY, Name VARCHAR(50) NOT NULL)
```
Inserting a second row with `EmployeeID = 7` fails because 7 already exists.
W: Primary key: it identifies each row, so the database enforces that values are unique and never NULL, which matches both rules in the stem.
X: A=Foreign key: a foreign key stores the primary key of a related row in another table; it is not unique in its own table, since many orders can point at one customer.
B=Index: an index speeds up searches; a primary key gets a unique index behind the scenes, but the concept that defines row identity is the primary key itself.
C=View: a view is a saved SELECT query shown as a virtual table; it is a separate object, not a column of the Employee table.
T: A primary key uniquely identifies each row: unique, not NULL, one per table.

@ DP-900 D2 T2.1 applied use-case
S: An Order table must record which customer placed each order, and customer details such as the address are stored only in a Customer table whose primary key is ID. What should the Order table contain?
A: A copy of the customer's name and address columns in every order row, so each order can be read on its own.
B: A CustomerID column defined as a foreign key that holds the ID of the related row in the Customer table.
C: A second primary key that combines the order number with the customer's name, so both stay unique together.
D: A view named Customer inside the Order table that lists the customer's details for each order number.
K: B
G: ## Foreign keys link related entities
Normalization keeps each entity in its own table and then **uses foreign key columns to link related entities**.
- The **primary key** of the related entity (Customer `ID`) is stored in the referencing table (Order) as a **foreign key**.
- To find an order's delivery address, you look up the matching Customer row, where the address is stored **only once**.
- Many orders can hold the same CustomerID, because one customer places many orders.
## Example
`Order(OrderNo PK, OrderDate, CustomerID FK -> Customer.ID)`
Order 1001 has `CustomerID = 17`; the address of customer 17 is read from the Customer table with a join.
W: Foreign key column: storing the Customer ID in a CustomerID foreign key links each order to its customer while the address stays in one place.
X: A=Copy customer columns: repeating name and address in every order duplicates data, so an address change would have to be made in many rows; normalization removes this.
C=Second primary key: a table can have only one primary key, and the customer's name is not a reliable unique identifier or a link to the Customer row.
D=View inside the table: a view is a database object of its own, defined by a query; it can't be stored inside a table as a column.
T: Link a row to a related entity by storing that entity's primary key as a foreign key.

@ DP-900 D2 T2.1 applied use-case
S: In an OrderLine table, OrderNo alone repeats for each item on an order and ItemNo alone repeats across orders, but each OrderNo and ItemNo pair occurs only once. How can each line be uniquely identified?
A: Define a composite primary key on OrderNo and ItemNo, because their combination is unique for every line.
B: Define two separate primary keys, one on OrderNo and one on ItemNo, so each column is checked on its own.
C: Define an index on OrderNo only, because a sorted index makes every value of the column unique by itself.
D: Define a foreign key from ItemNo to OrderNo, because linking the two columns makes every line distinct.
K: A
G: ## Composite keys
A primary key (or a foreign key) can be **composite**: defined on a unique combination of several columns.
- In a composite primary key, values **may repeat within one column**, but each combination of values must be unique.
- A table still has **only one** primary key; that one key simply spans more than one column.
## Example
- Order 1, item 1: Widget A
- Order 1, item 2: Widget B
- Order 2, item 1: Gadget X
OrderNo 1 repeats and ItemNo 1 repeats, but the pair (1, 1) appears once, so `PRIMARY KEY (OrderNo, ItemNo)` identifies each line.
W: Composite primary key: a key on the pair of columns allows each column to repeat on its own while guaranteeing that every combination, and so every line, is unique.
X: B=Two separate primary keys: a table can contain only one primary key constraint, and each column on its own has duplicates, so neither could be a key alone.
C=Index on OrderNo only: an ordinary index speeds up searches but doesn't make values unique, and OrderNo repeats for every item on an order.
D=Foreign key between the columns: a foreign key references a key in a related table to link entities; it does not create uniqueness inside the table.
T: When no single column is unique, a composite key on the column combination identifies each row.

@ DP-900 D2 T2.1 applied troubleshooting
S: An app tries to insert an order with CustomerID 950, but no customer with ID 950 exists. The database rejects the insert. Which relational feature caused this?
A: Normalization, which blocks any row that would duplicate data already held in a different table of the database.
B: A NOT NULL constraint on the CustomerID column, which requires that every new order supplies a customer value.
C: An index on the CustomerID column, which refuses values that are not already present in its sorted copy of data.
D: Referential integrity from a foreign key, which requires the value to match an existing primary key row.
K: D
G: ## Referential integrity
A relational database management system (RDBMS) can enforce **referential integrity** through a **foreign key constraint**: a value entered in a foreign key column must have a matching primary key in the related table.
- Inserting an order for a nonexistent customer fails.
- The constraint also protects the other direction: by default, deleting a customer that still has orders, or changing that customer's ID, fails, so no orders are left orphaned.
- You can define other actions (for example `CASCADE`, which also deletes or updates the related orders), but the default is to raise an error.
## Example
`Order.CustomerID` references `Customer.ID`. `INSERT ... CustomerID = 950` fails while no row with `ID = 950` exists in Customer.
W: Foreign key referential integrity: the constraint checks that every CustomerID in Order has a matching Customer row, so an order for customer 950 is rejected until that customer exists.
X: A=Normalization: normalization is a design process for the schema; it is not a run-time check, and the insert duplicates nothing.
B=NOT NULL: NOT NULL only rejects a missing value; 950 is a value, so a NOT NULL rule would accept it.
C=Index on CustomerID: an index only speeds up searches on the column; it never checks whether a value exists in another table, so it can't reject this insert.
T: A foreign key constraint enforces referential integrity: no foreign key value without a matching primary key.

@ DP-900 D2 T2.1 applied tradeoff
S: A company tracks sales in one spreadsheet where the customer's address is repeated on every sale. When a customer moves, staff must edit dozens of rows and sometimes miss some. How does a normalized relational design fix this?
A: It stores the address once in a Customer table, and orders reference that row, so a move changes a single row.
B: It adds an index on the address column so every repeated copy of the address can be found and edited together.
C: It creates a view over the spreadsheet so the address shown in each row can be edited in one place at once.
D: It keeps all data in one wide table but makes the address column NOT NULL so no row can be missed by staff.
K: A
G: ## Why normalize
**Normalization** is a schema design process that **minimizes data duplication** and **enforces data integrity**. The practical rules are:
- Separate each entity into its own table.
- Separate each discrete attribute into its own column.
- Uniquely identify each row with a primary key.
- Use foreign key columns to link related entities.
## The duplication problem
In a flat sales sheet the customer's name and address repeat on every sale. Changing one customer's address means editing every copy, and a missed row leaves the data inconsistent.
## After normalization
The address lives in one row of `Customer`; each `Order` row holds only `CustomerID`. To change a customer's address, you modify one row, and every order sees the new value through the key.
W: Store once and reference: putting each customer in its own table removes the repeated copies, so the address is changed in exactly one row and can't get out of step.
X: B=Index on the address: an index makes finding rows faster but leaves every duplicate copy in place, so staff still have to update each one.
C=View over the data: a view is a saved query; it doesn't remove the duplicated values in the underlying table, which still have to be changed row by row.
D=One table with NOT NULL: NOT NULL only stops empty values; the address is still repeated in many rows and can still be updated inconsistently.
T: Normalization stores each fact once, so a change is made in a single row.

A: Store every entity in one shared table so that no join is ever needed to read the related data.

G: ## Normalization in practice
Normalization has formal rules (first, second, third normal form and more), but for practical purposes Microsoft Learn sums it up in four steps:
- **Separate each entity into its own table** (Customer, Product, Order, LineItem).
- **Separate each discrete attribute into its own column** (FirstName, City, UnitPrice).
- **Uniquely identify each row using a primary key.**
- **Use foreign key columns to link related entities.**
The goal is to **minimize data duplication** and **enforce data integrity**.
## Example
A sales spreadsheet becomes four tables: `Customer`, `Product`, `Order` (with `CustomerID`) and `LineItem` (with `OrderNo` and `ProductID`).
W: B=Each entity in its own table: recording each entity in an entity-specific table removes duplication, the first rule of normalization.
C=Foreign keys link entities: once entities are split up, foreign key columns store the related row's primary key to connect them again.
X: A=One shared table: putting everything in one table is the flat spreadsheet design that normalization moves away from, since it repeats data.
D=Copy customer details on every order: this is the duplication normalization removes; the order should store only the customer's key.
E=Combine attributes into one column: normalization does the opposite and gives each discrete attribute its own column.
T: Normalize: one table per entity, one column per attribute, a primary key per row, foreign keys between related tables.

@ DP-900 D2 T2.1 applied definition
S: A developer writes a script with the statements CREATE TABLE, ALTER TABLE and DROP TABLE. To which group of SQL statements do these belong?
A: Data Manipulation Language (DML), which reads rows from tables and adds, changes or removes those rows.
B: Data Control Language (DCL), which grants, denies or revokes permissions on objects for users and groups.
C: Data Definition Language (DDL), which creates, modifies and removes tables and other database objects.
D: Transaction control statements, which commit or roll back a group of changes as one unit of database work.
K: C
G: ## Three main groups of SQL statements
Microsoft Learn groups SQL statements into three logical groups:
- **DDL (Data Definition Language)**: create, modify and remove database **objects** (tables, views, stored procedures). `CREATE`, `ALTER`, `DROP`, `RENAME`.
- **DCL (Data Control Language)**: manage **permissions**. `GRANT`, `DENY`, `REVOKE`.
- **DML (Data Manipulation Language)**: work with the **rows** in tables. `SELECT`, `INSERT`, `UPDATE`, `DELETE`.
## A quick test
Ask what the statement acts on. If it changes the structure of the database (a table, a column, a view), it is DDL. If it changes or reads data in the rows, it is DML. If it changes who may do what, it is DCL.
W: DDL: CREATE, ALTER and DROP define, change and remove the structure of database objects such as tables, which is exactly what Data Definition Language covers.
X: A=DML: DML statements (SELECT, INSERT, UPDATE, DELETE) work on rows inside tables, not on the table objects themselves.
B=DCL: DCL statements (GRANT, DENY, REVOKE) manage permissions; none of these three statements changes who has access.
D=Transaction control: COMMIT and ROLLBACK end a transaction; they don't create, change or remove objects.
T: CREATE, ALTER, DROP = DDL (objects); SELECT, INSERT, UPDATE, DELETE = DML (rows); GRANT, DENY, REVOKE = DCL (permissions).

@ DP-900 D2 T2.1 applied use-case
S: A database administrator must let a reporting user named user1 read and add rows in the Product table without changing any table design. Which statement fits?
A: `ALTER TABLE Product ADD user1 VARCHAR(20);`, adding the user to the table so it can read and insert rows.
B: `GRANT SELECT, INSERT ON Product TO user1;`, giving the user permission to read and add rows in the table.
C: `INSERT INTO Product (user1) VALUES ('SELECT');`, storing the user's allowed actions as a row in the table.
D: `CREATE VIEW user1 AS SELECT * FROM Product;`, creating a view named after the user that it can edit freely.
K: B
G: ## Data Control Language
Database administrators use **DCL** statements to manage access to objects by granting, denying or revoking permissions for users or groups.
- `GRANT` gives permission to perform specific actions.
- `DENY` explicitly blocks specific actions.
- `REVOKE` removes a permission that was previously granted (or denied).
## Example
```
GRANT SELECT, INSERT, UPDATE ON Product TO user1;
```
This lets `user1` read, insert and modify rows in `Product`. Dropping `UPDATE` from the list gives read and insert only.
W: GRANT: this DCL statement gives user1 the SELECT and INSERT permissions on Product without touching the table's structure.
X: A=ALTER TABLE ADD: ALTER is DDL and adds a column to the table design; it doesn't give anyone permissions, and it changes the design, which the stem forbids.
C=INSERT a row: INSERT adds data to the table; a row containing text such as 'SELECT' is just data and grants nothing.
D=CREATE VIEW: a view is a saved query object; naming it after the user does not give the user any permission to read or insert rows.
T: Permissions are managed with DCL: GRANT gives, DENY blocks, REVOKE removes.

@ DP-900 D2 T2.1 applied comparison
S: Last month a DBA granted user2 permission to update the Price table. That access is no longer needed, and the DBA wants simply to remove the earlier grant. Which DCL statement does this?
A: `DENY`, which removes a permission that was given earlier and returns the user to having no explicit permission.
B: `DROP`, which removes a permission from the database permanently so it can't be granted to any user again later.

D: `REVOKE`, which removes a permission that was previously granted so the user no longer has it on that table.

G: ## GRANT, DENY and REVOKE
The three main DCL statements each do one thing:
- `GRANT`: give permission to perform specific actions.
- `DENY`: deny permission to perform specific actions.
- `REVOKE`: remove a previously granted permission.
## REVOKE versus DENY
`REVOKE` takes back what was given: the earlier `GRANT` is gone. `DENY` is an explicit "no" that blocks the action. Use REVOKE when you just want to undo a grant.
## Example
```
REVOKE UPDATE ON Price FROM user2;
```
W: REVOKE: it removes a permission that was previously granted, which is exactly undoing last month's GRANT.
X: A=DENY: DENY is an explicit block on an action, not the removal of an earlier grant; the DBA only wants the old grant gone.
B=DROP: DROP is DDL and removes database objects such as tables or views; it is not used to take back a user's permission.
C=DELETE: DELETE is DML and removes rows of data from a table; permissions are not rows in the user's table.
T: REVOKE removes an earlier GRANT; DENY explicitly blocks an action.

@ DP-900 D2 T2.1 applied definition
S: Which TWO statements belong to Data Manipulation Language (DML), the group that works with the rows stored in tables? (Select TWO)
A: `UPDATE`, which modifies the data in rows that already exist in a table, usually matched by a WHERE clause.
B: `ALTER`, which modifies the structure of an existing table, for example by adding a new column to the table.
C: `GRANT`, which gives a user or group the permission to perform specific actions on a database object.
D: `INSERT`, which adds new rows to a table, with a list of values for the columns named in the statement.
E: `CREATE`, which adds a new object to the database, such as a table, a view or a stored procedure.
K: A,D
G: ## DML works on rows
Data Manipulation Language statements let you query and change the **rows** in tables. The four main ones are:
- `SELECT`: read rows from a table.
- `INSERT`: insert new rows into a table.
- `UPDATE`: modify data in existing rows.
- `DELETE`: delete existing rows.
`SELECT`, `UPDATE` and `DELETE` apply to every row by default, so you usually add a `WHERE` clause to choose rows.
## Not DML
- `CREATE`, `ALTER`, `DROP` change database **objects**: DDL.
- `GRANT`, `DENY`, `REVOKE` change **permissions**: DCL.
W: A=UPDATE: it changes values in rows that already exist, one of the four main DML statements.
D=INSERT: it adds new rows of data to a table, another of the four main DML statements.
X: B=ALTER: ALTER changes the structure of an object, such as adding a column to a table, so it is DDL; it does not touch the data in the rows.
C=GRANT: GRANT gives users or groups permission to act on an object, so it belongs to DCL, the permission statements.
E=CREATE: CREATE adds a new object such as a table or view to the database, so it is DDL rather than a statement that works on rows.
T: DML = SELECT, INSERT, UPDATE, DELETE: statements that read or change rows.

@ DP-900 D2 T2.1 applied troubleshooting
S: A developer meant to change the address of customer 1 and ran `UPDATE Customer SET Address = '123 High St.';`. Now every customer has that address. What caused this?
A: The statement used UPDATE instead of ALTER, and only ALTER can change the value of a single row in a table.
B: The Customer table had no index on the Address column, so the change was applied to the whole table instead.
C: The statement had no WHERE clause, so UPDATE applied the new value to every row in the Customer table.
D: The Address column was defined as NOT NULL, so the database copied the new value into every row of the table.
K: C
G: ## WHERE decides which rows change
`SELECT`, `UPDATE` and `DELETE` apply to **every row** in the table by default. A `WHERE` clause limits them to the rows that match a condition.
```
UPDATE Customer
SET Address = '123 High St.'
WHERE ID = 1;
```
This changes only the row with `ID = 1`; all other rows are left unchanged.
## No safety prompt
SQL doesn't ask "are you sure?". An `UPDATE` or `DELETE` without `WHERE` changes or removes every row at once, so check the condition before running it and keep backups.
W: Missing WHERE clause: without a condition, UPDATE modifies every row, so all customers received the new address.
X: A=Should have used ALTER: ALTER is DDL and changes a table's structure; UPDATE is the correct statement for changing values, it just needed a WHERE clause.
B=No index: an index only speeds up finding rows; it never decides which rows an UPDATE changes.
D=NOT NULL column: NOT NULL only requires that each row has a value; it does not copy values between rows.
T: UPDATE and DELETE without WHERE affect every row in the table.

@ DP-900 D2 T2.1 applied comparison
S: A Promotions table holds last year's offers. The team wants to remove all of its rows but keep the table, with its columns and keys, ready for new offers. Which statement fits?
A: `DROP TABLE Promotions;`, which empties the table's rows while keeping the column definitions for reuse.
B: `DELETE FROM Promotions;`, which removes every row of data while the table itself stays in the database.
C: `ALTER TABLE Promotions;`, which resets the table to its original empty state with the same set of columns.
D: `REVOKE SELECT ON Promotions;`, which hides every existing row so that only newly inserted rows are visible.
K: B
G: ## DELETE removes rows, DROP removes the object
- `DELETE` is **DML**. It removes rows from a table. With a `WHERE` clause it removes only matching rows; without one it removes every row. The table, its columns and its constraints remain.
- `DROP` is **DDL**. It removes the **object** itself. When you drop a table, the table definition and all its rows are gone, and without a backup the data can't be retrieved.
## Example
```
DELETE FROM Product WHERE ID = 162;   -- one row
DELETE FROM Promotions;               -- all rows, table stays
DROP TABLE Promotions;                -- table and rows gone
```
W: DELETE without WHERE: it removes every row but leaves the table definition, so new offers can be inserted straight away.
X: A=DROP TABLE: DROP permanently removes the table object along with its rows; the columns and keys would have to be created again.
C=ALTER TABLE: ALTER changes a table's structure, such as adding a column; it doesn't remove data, and it has no "reset" behavior.
D=REVOKE: REVOKE removes a permission from a user; the rows stay in the table and are still there for anyone allowed to read them.
T: DELETE removes rows and keeps the table; DROP removes the table and everything in it.

Adding, changing or removing a column changes the **structure** of a table, so it is a **DDL** job.
- `CREATE` makes a new object.
- `ALTER` modifies an existing object, "for instance, altering a table to add a new column".
- `DROP` removes an object.
The existing rows stay; the new column is empty (NULL) or takes a default value until you set it.

After the column exists, `UPDATE Product SET Weight = 1.2 WHERE ID = 99;` stores a value in a row.
W: ALTER TABLE: modifying an existing table to add a column is the textbook use of ALTER, and the existing rows are kept.
X: B=UPDATE: UPDATE changes values in columns that already exist; it can't add a new column to the table.
C=CREATE TABLE: CREATE makes a new object, and a table called Product already exists, so this would fail rather than add a column.
D=INSERT: INSERT adds a new row of data; a row containing the word "Weight" doesn't change the table's columns.
T: Add or change columns with ALTER (DDL); change values in rows with UPDATE (DML).

@ DP-900 D2 T2.1 applied troubleshooting

G: ## Rows have no guaranteed order
A relational table is a set of rows. When a query returns many rows, they **don't necessarily appear in any specific sequence**; the order can change as the data or the query plan changes.
## ORDER BY sorts the result
```
SELECT FirstName, LastName, Address, City
FROM Customer
WHERE City = 'Seattle'
ORDER BY LastName;
```
The only reliable way to get a sorted result is an `ORDER BY` clause on the column (or columns) you want.
W: ORDER BY: it sorts the result by the named column, so the names come back in the same last-name order on every run.

@ DP-900 D2 T2.1 applied use-case
S: An Order table has a CustomerID foreign key and a Customer table holds addresses under the primary key ID. A query must list each order number with its customer's city. What should the query use?
A: A `GRANT` that lets the Order table read the Customer table, so the city appears in the order rows directly.
B: A `UNION` that stacks the rows of the Order table on top of the Customer table, matched by the column order.
C: An `ALTER TABLE` that adds a City column to Order, so the query can read the city from one table only.
D: A `JOIN` that matches Order.CustomerID with Customer.ID, so each order row is combined with its customer row.
K: D
G: ## JOIN combines related tables
Normalization splits data across tables, so many queries need to read from more than one table. A **JOIN** clause tells the database how rows in one table connect to rows in the other.
- A typical join condition matches a **foreign key** in one table with the **primary key** it refers to in the other.
- Table aliases (`o`, `c`) keep the query short.
## Example
```
SELECT o.OrderNo, o.OrderDate, c.City
FROM [Order] AS o
JOIN Customer AS c
ON o.CustomerID = c.ID;
```
`ORDER` is a reserved word in Transact-SQL, so the table name is in square brackets.
W: JOIN on the keys: matching the foreign key with the related primary key combines each order with exactly its customer, so the city can be selected next to the order number.
X: A=GRANT: GRANT gives a user permission on an object; tables don't read each other, and permissions never combine rows in a result.
B=UNION: UNION appends the rows of one query under another with compatible columns; it doesn't match orders to customers by key.
C=ALTER TABLE: copying City into Order duplicates customer data, which normalization avoids; the city can be read with a join instead.
T: To combine related tables, JOIN the foreign key to the primary key it references.

@ DP-900 D2 T2.1 advanced comparison
S: A marketing list must show every customer, including customers who have never placed an order. Orders that exist should appear beside each customer. Which join gives this result?
A: An inner join from Customer to Order, which returns all customers and fills in orders where they exist.
B: A left outer join from Customer to Order, which keeps every customer and shows NULL where no order matches.
C: A cross join between Customer and Order, which pairs each customer only with the orders that customer placed.
D: An inner join from Order to Customer, which returns every order and adds the customers who have no orders.
K: B
G: ## Logical join types
SQL Server and Azure SQL support these logical joins:
- **Inner join**: returns only rows that have a match in **both** tables.
- **Left outer join**: returns **every row from the left table**; where the right table has no match, its columns are **NULL**.
- **Right outer join**: the same, keeping every row from the right table.
- **Full outer join**: keeps unmatched rows from both sides.
- **Cross join**: pairs every row of one table with every row of the other (no join condition).
## Example
```
SELECT c.Name, o.OrderNo
FROM Customer AS c
LEFT OUTER JOIN [Order] AS o ON o.CustomerID = c.ID;
```
Customer "Lee", who never ordered, appears once with `OrderNo` NULL.
W: Left outer join: it keeps all rows from the left table (Customer) and returns NULL order columns when a customer has no orders, which is exactly the list required.
X: A=Inner join from Customer: an inner join returns only matched rows, so customers with no orders are left out whichever table is written first.
C=Cross join: a cross join pairs every customer with every order, not just their own, so the result is a large list of meaningless combinations.
D=Inner join from Order: swapping the table order doesn't change an inner join; customers without orders still have no match and are dropped.
T: Inner join = matches only; left outer join = all rows of the left table plus matches (NULL where none).

@ DP-900 D2 T2.1 applied use-case
S: Analysts often need order numbers with each customer's name and delivery address, which requires joining the Order and Customer tables. The DBA wants to give them one object they can query like a table. What should the DBA create?
A: A view defined by a SELECT that joins Order and Customer, which analysts can query and filter like a table.
B: An index on the Order and Customer tables, which stores the joined columns so analysts can query the index.
C: A new table that copies the joined order and customer data, refreshed by hand whenever an analyst asks.
D: A foreign key between Order and Customer, which lets analysts read both tables as one combined table.
K: A
G: ## Views
A **view** is a **virtual table based on the results of a SELECT query**, like a window on chosen rows and columns of one or more underlying tables.
- The view stores the query, not a separate copy of the data, so it always reflects the current tables.
- You query and filter a view in much the same way as a table.
## Example
```
CREATE VIEW Deliveries AS
SELECT o.OrderNo, o.OrderDate, c.FirstName, c.LastName, c.Address, c.City
FROM [Order] AS o JOIN Customer AS c ON o.Customer = c.ID;

SELECT OrderNo, LastName, Address FROM Deliveries WHERE City = 'Seattle';
```
W: View: a view wraps the join in one named object that analysts query and filter like a table, and it reads the current data each time.
X: B=Index: an index is a sorted copy of a column with pointers to rows that speeds up searches; analysts don't query an index as an object.
C=Copied table: a copy duplicates data and goes stale between manual refreshes, which a view avoids by reading the base tables.
D=Foreign key: a foreign key enforces the link between the tables, but queries still need a join; it does not make the two tables one object.
T: A view is a saved SELECT that you query like a table.

@ DP-900 D2 T2.1 applied use-case
S: Several applications rename products by running the same UPDATE logic with a product ID and a new name. The team wants that logic kept inside the database and run on command with parameters. Which object fits?
A: A view, which stores a SELECT query and lets applications pass a product ID to update the matching row.
B: An index, which keeps a sorted copy of the Name column so applications can change product names faster.
C: A stored procedure, which holds SQL statements with parameters that applications run on command with EXEC.
D: A foreign key, which links each product row to its new name stored in a separate table of product names.

G: ## Stored procedures
A **stored procedure** defines SQL statements that can be run on command. It **encapsulates programmatic logic in the database** for actions that applications perform on data.
- Parameters make it flexible: the same procedure works for any product ID and new name.
- Every application calls the same logic, so a change to the logic is made once.
## Example
```
CREATE PROCEDURE RenameProduct @ProductID INT, @NewName VARCHAR(20)
AS
UPDATE Product SET Name = @NewName WHERE ID = @ProductID;

EXEC RenameProduct 201, 'Spanner';
```
W: Stored procedure: it stores the UPDATE inside the database with parameters for the ID and name, and each application runs it with EXEC.
X: A=View: a view is a virtual table defined by a SELECT; it takes no parameters and is not used to package update logic for applications.
B=Index: an index speeds up searches on a column; it holds no logic and can't rename anything.
D=Foreign key: a foreign key enforces a link between tables; it doesn't run statements or take parameters.
T: Stored procedure = parameterized SQL logic kept in the database and run on command.

@ DP-900 D2 T2.1 applied use-case
S: A Product table has millions of rows, and a search page runs `SELECT * FROM Product WHERE Name = @name;` many times a minute. Each query scans the whole table and is slow. What should be added?
A: A view on the Product table that selects the Name column, so the search page reads fewer rows.
B: An index on the Name column, so the database can find matching rows without reading every row.
C: A foreign key on the Name column, so the database links each name to the matching product row.
D: A stored procedure that runs the SELECT, so the database caches the full Product table in memory.
K: B
G: ## Indexes
An **index** helps you search for data in a table, like the index at the back of a book.
- When you create an index on a column, the index holds a **sorted copy of that column's data with pointers to the rows**, in a tree-based structure.
- When a query filters on that column in its `WHERE` clause, the query optimizer can use the index to fetch the rows **without scanning the whole table**.
- On large tables this can dramatically improve query performance; on a table with few rows, the optimizer may ignore the index because a scan is just as fast.
## Example
```
CREATE INDEX idx_ProductName ON Product(Name);
```
W: Index on Name: the sorted index lets the optimizer go straight to the rows with the requested name instead of scanning millions of rows.
X: A=View: a view is a saved query; querying it still reads the base table the same way, so it doesn't remove the full scan.
C=Foreign key: a foreign key links to a primary key in another table; Name is not a reference, and a foreign key doesn't create an index automatically.
D=Stored procedure: wrapping the query in a procedure packages the logic, but the database still has to scan the table to find matching names.
T: Index the column used in WHERE on a large table to avoid scanning every row.

@ DP-900 D2 T2.1 advanced troubleshooting
S: To speed up reports, a developer added indexes on almost every column of a busy Orders table. Reports are faster, but inserting and updating orders is now slower. Which TWO explain this? (Select TWO)

G: ## Indexes are not free
An index speeds up queries that filter on its column, but it has costs:
- **Maintenance on writes**: each time you insert, update or delete data, every index on the table must be updated too. That extra work slows down data changes.
- **Storage**: an index holds a copy of the indexed data in sorted order, so it consumes storage space.

You can create many indexes on one table, but you must strike a balance between faster queries and slower inserts, updates and deletes. A write-heavy transactional table usually has only the indexes its most important queries need.

G: ## Primary key facts
A **primary key** is the column or combination of columns that uniquely identifies each row, enforcing the **entity integrity** of the table. In SQL Server and Azure SQL Database:
- A table can contain **only one** primary key constraint (it may span several columns).
- All columns in a primary key must be **NOT NULL**; if nullability isn't stated, they are set to not null.

Data from two tables can be combined in a join even if no primary or foreign key is defined; keys show the tables are designed to be joined on those columns.

E=Joins refuse tables without keys: SQL doesn't require a primary key, and joins work on any matching columns even without key constraints.
