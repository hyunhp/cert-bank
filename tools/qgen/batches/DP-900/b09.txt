@ DP-900 D4 T4.3 applied use-case
S: A data analyst must import data from an Excel workbook and a SQL database, shape it, define relationships between the tables and design a multi-page interactive report. Which Power BI tool is the usual starting point for this work?
A: The Power BI mobile app, which lets the analyst build the model and the report pages on a tablet while travelling.
B: Power BI Desktop, a Windows application for importing and modeling data and designing interactive reports.
C: The Power BI service dashboard editor, which builds the model by pinning tiles from each of the two data sources.
D: A workspace app, which bundles the source files together and generates the relationships and report pages.
K: B
G: ## The Power BI workflow
Power BI is a suite of tools and services and a core workload of Microsoft Fabric. A typical workflow has three steps:
- **Build** in **Power BI Desktop**, a Windows application. You import data from many sources, clean and shape it with Power Query Editor, combine it into a data model (relationships, measures, calculated columns) and design report pages with visuals.
- **Publish** the model and report to the **Power BI service**, the cloud service where business users interact with content, refreshes are scheduled and content is shared.
- **Consume** reports, dashboards and apps in a web browser or in the **Power BI mobile app** on phones and tablets.
The service also allows some basic modeling and report editing in the browser, but Learn notes that this is more limited than Desktop.
## Example
An analyst pulls monthly budgets from Excel and actual sales from SQL Server into Power BI Desktop, relates both to a Date table, builds three report pages and then publishes them.
W: Power BI Desktop: it is the tool Learn names for importing data from many sources, combining it in a data model and creating reports with interactive visuals. Its full modeling and design tools make it the normal starting point.
X: A=Mobile app: the mobile app is for viewing and interacting with published reports, dashboards and apps on phones and tablets, not for building data models.
C=Dashboard editor: dashboards are single-page canvases of tiles pinned from existing reports. Pinning tiles does not import data or create relationships, so a model and report must exist first.
D=Workspace app: an app packages finished reports and dashboards for distribution. It does not import source files or design a model.
T: Build models and reports in Power BI Desktop, publish and share in the Power BI service, view anywhere including the mobile app.
V: Power BI

G: ## Dashboards in Power BI
A **dashboard** is a single page, often called a canvas, that shows the most important parts of a story at a glance.
- Its visuals are **tiles**, pinned from reports; each report is based on a semantic model.
- One dashboard can draw on **one or more reports and semantic models**, even mixing on-premises and cloud data.
- You can set **alerts** on certain tiles, so Power BI emails you when a value meets a condition.
- Dashboards are a feature of the **Power BI service** only; they are not available in Power BI Desktop.
- Selecting a tile usually opens the report page it came from, where the detail lives.
## Example
A CEO dashboard has four tiles: revenue from the Sales report, headcount from the HR report, and two cost tiles from the Finance report. An alert fires if monthly cost passes a set value.

B=Desktop report page: a report is based on a single semantic model and alerts are not available on reports; dashboards do not exist in Desktop at all.
D=Semantic model: the semantic model holds the tables, relationships and measures behind reports. It is not a page that users view, and it does not send threshold alerts.
T: One page, tiles from many reports, alerts → dashboard; multi-page, one semantic model, filtering and slicing → report.

S: In a Power BI semantic model for sales analysis, which statement best describes the difference between measures and dimensions?

G: ## What an analytical model contains
An analytical model, called a **semantic model** in Power BI and Microsoft Fabric, is built from related tables. It defines two things:
- **Measures**: the numeric values you want to analyze or report, such as revenue or quantity sold.
- **Dimensions**: the entities you aggregate those values by, such as product, customer and time.
## Why the split matters
Because measures and dimensions are separated, the same measure can be summarized many ways: total revenue by customer, items sold by product per month, or revenue by city and year. Each visual picks a measure and one or more dimensions.

C=Tables and pages: report pages are part of a report, not of the model. Measures and dimensions are model concepts, independent of how pages are laid out.
D=Relationships and keys: relationships connect tables and use key columns, but they are neither measures nor dimensions. They are what lets a dimension filter a measure.
T: Measures = numbers you analyze; dimensions = entities you group and filter them by.

@ DP-900 D4 T4.3 applied definition
S: A Power BI model has a Sales table in which each row records one transaction with its quantity sold and revenue, and a Product table with one row per product. How are these tables classified in dimensional modeling?
A: Sales is a dimension table because it lists each event, and Product is a fact table because it holds product facts.
B: Both are fact tables, because every table that has a key column is treated as a fact table in a semantic model.
C: Sales is a fact table that stores the numeric measures, and Product is a dimension table that describes products.
D: Both are dimension tables, because a semantic model only uses fact tables when the data is loaded in Direct Lake.
K: C
G: ## Fact and dimension tables
Star schema modeling classifies every table as one of two types:
- **Fact tables** store observations or events, such as sales orders. Each row is one recorded event, with numeric measure columns (quantity, revenue) and key columns that point to dimensions. Fact tables tend to have many rows and keep growing.
- **Dimension tables** describe business entities, such as products, customers, places and time. Each row has a unique key, and the other columns are attributes (name, category, city) used to filter and group. They usually have fewer rows.
## A useful check
In a one-to-many relationship, the "one" side is the dimension table and the "many" side is the fact table: one product appears on many sales rows.
## Example
`Sales(DateKey, ProductKey, CustomerKey, Quantity, Revenue)` is a fact table. `Product(ProductKey, Name, Category, Color)` is a dimension table.
W: Sales fact, Product dimension: a table whose rows are recorded events with numeric values is a fact table, and a table with one row per entity and descriptive attributes is a dimension table.
X: A=Reversed roles: it swaps the definitions. Event rows with numbers are facts; descriptive entity tables are dimensions.
B=Key column means fact: dimension tables also have key columns (their unique keys). The type depends on what the table stores and its side of the relationship, not on having a key.
D=Direct Lake decides: the storage mode controls how data is loaded, not whether a table is a fact or a dimension. Models in any storage mode use both types.
T: Fact table = events with numeric measures (many rows); dimension table = entities with attributes (one row per entity).

@ DP-900 D4 T4.3 applied comparison
S: A model has a Sales fact table related to Product, Customer and Date tables. The Product table is also related to a separate Category table that holds category details. What is this design called?
A: A star schema, because every dimension table in the model relates directly to the one central fact table.
B: A snowflake schema, because a dimension table relates to an additional detail table for its categories.
C: A flat schema, because Power BI merges all the related tables into one wide table when the model loads.
D: A many-to-many schema, because the Product table has relationships with both the Sales and Category tables.
K: B
G: ## Star and snowflake schemas
- **Star schema**: one fact table in the middle, related directly to its dimension tables (Product, Customer, Date). Drawn out, it looks like a star.
- **Snowflake schema**: some dimension tables relate to further detail tables. For example, Product relates to Category, and Category might relate to Department. The branches look like a snowflake.
## Which to prefer in Power BI
Learn's guidance recommends star schema design for Power BI semantic models because it fits how visuals query a model: dimension tables filter and group, fact tables summarize. A snowflake dimension is often flattened (denormalized) into a single Product table that already contains category columns.
## Example
Sales → Product → Category is a snowflake. Merging Category's columns into Product turns it back into a star.
W: Snowflake schema: Learn describes a design in which dimension tables relate to additional detail tables, such as Category linked to Product, as a snowflake schema.
X: A=Star schema: in a pure star every dimension relates directly to the fact table. The Category table hangs off Product instead, which is what makes it a snowflake.
C=Flat schema: Power BI keeps separate tables with relationships; it does not merge them into one wide table on load.
D=Many-to-many schema: having two relationships does not make a table many-to-many. Product is on the "one" side of both, which are ordinary one-to-many relationships.
T: Fact table with directly related dimensions = star; dimensions that branch into further detail tables = snowflake.
V: Power BI

A **calculated column** adds new data to a table that is already in the model. Instead of loading the values from the source, you write a **DAX** formula, and Power BI calculates a result **for every row**.
Typical uses:
- Concatenate text from two columns.
- Do arithmetic across columns of the same row.

D=Dashboard tile: tiles are pinned visuals on a dashboard. They do not add fields to the model that a map or slicer can use.

E=Service only: Power BI Desktop has full modeling tools, including creating measures in the Report, Table and Model views.

@ DP-900 D4 T4.3 applied definition
S: In a Power BI model, a Product table has one row per ProductKey and a Sales table has many rows for each ProductKey. Which relationship cardinality connects Sales to Product?
A: One to one, because each product key value appears exactly once in the Sales table and once in the Product table.
B: Many to many, because both tables contain the ProductKey column and each column holds many different key values.
C: Many to one, because ProductKey can repeat in Sales while each value appears only once in the Product table.
D: No relationship is needed, because Power BI always joins tables at query time by matching their column names.
K: C
G: ## Relationships in a Power BI model
A relationship connects a column in one table to a column in another, so filters on one table flow to the other and visuals can combine fields from both.
## Cardinality options
- **Many to one** (`*:1`): the most common type. The column on the "many" side can repeat a value; the related lookup table has only one instance of each value. One to many (`1:*`) is the same relationship seen from the other side.
- **One to one** (`1:1`): each value appears once in both tables.
- **Many to many** (`*:*`): neither side requires unique values (used with composite models).
## Fact and dimension sides
In a star schema the "one" side is the dimension table (Product) and the "many" side is the fact table (Sales).
## Autodetect
When tables are loaded together, Power BI Desktop tries to detect relationships from matching column names and sets the cardinality. It creates nothing when it is not confident, so you can create or edit relationships yourself.
W: Many to one: ProductKey repeats in Sales (many sales per product) but is unique in Product, which is the many-to-one pattern Learn describes as the most common relationship type.
X: A=One to one: a product key appears on many sales rows, so the Sales side is not unique.
B=Many to many: having many different values in a column does not make it many-to-many. The Product side is unique, so a normal many-to-one relationship applies.
D=No relationship: autodetect can create relationships when names match, but it is a load-time helper. The model still stores a relationship; there is no automatic name-matching join at query time.
T: Fact table key repeats, dimension key is unique → many-to-one (dimension on the "one" side).

D=Column chart: a chart compares categories visually, but the team asked for an exact grid of values with subtotals and drill-down rows.

S: A company's Power BI report uses a large Azure SQL Database. Security policy says the data must stay in the database and must not be copied into the semantic model. Which connectivity mode fits?
A: Import mode, which loads the tables into the model's in-memory store and refreshes the copy on a schedule.
B: DirectQuery mode, which imports no data and sends queries to the source database each time a visual loads.
C: Direct Lake mode, which reads Delta tables stored in OneLake into memory instead of querying the database.
D: A calculated table, which copies the source rows into the model with a DAX formula evaluated at refresh.
K: B
G: ## How a semantic model gets its data
Power BI semantic models connect to sources in different **connectivity (storage) modes**:
- **Import**: the data selected by the queries is loaded into the model's in-memory cache. Visuals query only the cached copy, so they are fast and fully interactive, but they show source changes only after a refresh. Learn recommends Import by default.
- **DirectQuery**: **no data is imported**. Publishing creates only the model definition (schema and metadata), and each visual sends one or more queries to the underlying source. Performance depends on the source.
- **Direct Lake**: a Microsoft Fabric mode for Delta tables in OneLake.
- **Live connection**: connects to an existing published semantic model or Analysis Services model.
## When DirectQuery fits
Choose it when constraints such as data size, latency, governance or security mean the data should stay in the source and not be copied into Power BI.
## Example
A report on a governed `Orders` table in Azure SQL Database uses DirectQuery: when a manager changes a slicer, Power BI sends a new SQL query to the database.
W: DirectQuery: Learn states that with DirectQuery no data is imported and each visual triggers queries to the underlying source, so the data stays in the database as the policy requires.
X: A=Import mode: Import loads all the queried data into the semantic model's in-memory cache, which is exactly the copy the policy forbids.
C=Direct Lake mode: Direct Lake works with Delta tables in OneLake in Microsoft Fabric. The data here lives in Azure SQL Database, which is queried, not read from a lake.
D=Calculated table: a calculated table is built with DAX from data already in the model and is stored there, so it still means a copy inside the model.
T: Data must stay in the source and visuals query it live → DirectQuery; fastest in-memory copy with scheduled refresh → Import.
