@ DP-900 D2 T2.2 applied use-case
S: A startup is building a new cloud-native web application that needs one relational database. The team wants the latest stable SQL Server features and no responsibility for operating systems, patching or backups. Which Azure service fits best?
A: SQL Server on an Azure virtual machine, installed from a SQL Server image in the Azure Marketplace.
B: Azure SQL Database as a single database, with its own dedicated resources managed through a logical server.
C: Azure SQL Managed Instance, deployed into a dedicated subnet of the startup's own Azure virtual network.
D: Azure Database for MySQL flexible server, running the MySQL Community Edition engine that Azure manages.
K: B
G: ## The Azure SQL family
Azure SQL is a family of services that all use the SQL Server database engine:
- **SQL Server on Azure Virtual Machines**: infrastructure as a service (IaaS). You get a VM with SQL Server installed and manage the operating system and SQL Server yourself.
- **Azure SQL Managed Instance**: platform as a service (PaaS). A whole SQL Server instance with near-100% compatibility, aimed at migrating existing SQL Server workloads.
- **Azure SQL Database**: PaaS. A fully managed database built for the cloud, based on the latest stable SQL Server engine.
## Single database
Azure SQL Database can be deployed as a **single database** (its own guaranteed compute, memory and storage) or in an **elastic pool** (resources shared by several databases). Microsoft handles updates, backups and high availability; the team configures the database, creates tables and loads data.
## Example
A two-person team builds a booking site. They create one Azure SQL Database, connect the app, and never log on to a server.
W: Single Azure SQL Database: Learn describes it as the option for new cloud applications that want the latest stable SQL Server features, with patching, backups and recovery built in. One database with its own resources is exactly the need.
X: A=SQL Server on a VM: this is IaaS, so the team would patch the operating system and SQL Server and manage backups, which is the work it wants to avoid.
C=SQL Managed Instance: it is also PaaS, but it is aimed at migrating existing SQL Server instances with instance-level features. For one new cloud-born database it adds networking setup the team does not need.
D=MySQL flexible server: it is a managed service, but it runs MySQL, not SQL Server, so it does not give the SQL Server features the team asked for.
T: New cloud application, one database, SQL Server engine, minimal administration → Azure SQL Database (single database).
V: Azure SQL Database

@ DP-900 D2 T2.2 applied use-case
S: A software company sells a SaaS app and gives each of its 300 customers a separate Azure SQL Database. Most databases are idle most of the day, but each one has short, unpredictable peaks. The company wants to cut costs without starving any database at its peak. What should it use?
A: An elastic pool, so that the databases share a set amount of compute and storage purchased for the whole group.
B: The Business Critical service tier for every database, so that each one keeps a local read-only replica for peaks.
C: One SQL Managed Instance, so that all 300 customers share a single database with a tenant ID column in each table.
D: A larger SQL Server VM size, so that all databases run inside one instance whose memory and CPU can be resized.
K: A
G: ## The problem elastic pools solve
A common SaaS pattern gives every customer its own database. Each database must be sized for its own peak, so if peaks are short and rare, most of the paid capacity sits idle.
## How an elastic pool works
An **elastic pool** is a set of resources (compute, memory, storage) that you buy once for a group of databases on the same logical server.
- A busy database can use more of the pool while it peaks; idle databases use little or nothing.
- You can set minimum and maximum resources per database so one tenant cannot take everything.
- You pay for the pool, not for each database, which gives a predictable budget.
Pools fit best when databases have **large differences between peak and average use** and their peaks do not all happen at the same time.
## Example
Twenty databases that each peak at 90 units but average under 5 can share a pool of 100 units instead of buying 20 separate databases sized for 90.
W: Elastic pool: databases in a pool share one set of resources, so their scattered, unpredictable peaks are covered by capacity that is paid for once instead of 300 times. This is the scenario Learn uses to introduce elastic pools.
X: B=Business Critical for every database: a higher tier gives each database more dedicated resources and costs more, which is the opposite of the cost saving the company wants.
C=One shared database on Managed Instance: merging all customers into one database is an application redesign, not a cost setting, and it removes the per-customer database isolation the app relies on.
D=Larger SQL Server VM: moving to IaaS adds operating system and backup work, and a VM sized for combined peaks still pays for idle capacity; elastic pools exist to solve this in the PaaS service.
T: Many databases with varying, unpredictable usage that peak at different times → Azure SQL Database elastic pool.
V: Azure SQL Database

@ DP-900 D2 T2.2 applied definition
S: Which statement correctly describes an Azure SQL Database elastic pool?
A: A group of database copies kept in several Azure regions so that the application can fail over during an outage.
B: A set of compute and storage resources shared by several databases on one logical server, billed for the pool.
C: A cluster of SQL Server virtual machines that together host one very large database split across many nodes.
D: A collection of SQL Managed Instances in one subnet that share one set of logins, jobs and linked servers.
K: B
G: ## Deployment options of Azure SQL Database
Azure SQL Database has two ways to deploy a database:
- **Single database**: the database has its own guaranteed resources that no other database uses.
- **Elastic pool**: several databases on the same logical server share a pool of resources at a set price.
## What sharing means
Inside a pool, a database under heavy load can use more resources, and a database with no load uses none. You can move single databases into or out of a pool, with only a short connection drop at the end of the move. The pool is billed per hour for the resources it has, with no extra charge per database.
## What a pool is not
A pool is about **sharing resources to save money**, not about copying data. Copies in other regions for disaster recovery are a different feature (geo-replication and failover groups).
W: Shared pool on one logical server: an elastic pool is a collection of databases with a shared set of resources managed through a logical server, and you pay for the pool rather than per database.
X: A=Copies in several regions: that describes geo-replication or failover groups for disaster recovery. A pool shares resources between different databases; it does not copy any of them.
C=Cluster of SQL Server VMs: elastic pools are part of the PaaS Azure SQL Database service, where no VMs are visible to you. A database split across many nodes is a sharding design, not a pool.
D=Group of Managed Instances: Managed Instance has its own way to share resources between small instances, called instance pools, which is a different feature from Azure SQL Database elastic pools.
T: Elastic pool = several Azure SQL databases sharing one set of resources at one price; single database = dedicated resources per database.
V: Azure SQL Database

@ DP-900 D2 T2.2 applied use-case
S: A company runs an on-premises SQL Server instance with 40 databases. The applications use SQL Server Agent jobs, cross-database queries and linked servers. It wants a managed PaaS service and as few application changes as possible. Which service should it choose?
A: Azure SQL Database single databases, one per on-premises database, managed together through one logical server.
B: Azure SQL Database in an elastic pool, so that all 40 databases share resources and keep running their Agent jobs.
C: Azure SQL Managed Instance, which provides a SQL Server instance with near-100% compatibility as a managed service.
D: SQL Server on Azure Virtual Machines, which provides full SQL Server compatibility and access to the operating system.
K: C
G: ## Instance-level features
Some SQL Server features belong to the **instance**, not to one database: SQL Server Agent jobs, cross-database queries and transactions, linked servers, Service Broker, Database Mail and CLR modules. Applications that rely on them need a service that offers a whole instance.
## Which Azure SQL service offers what
- **Azure SQL Database** supports the core database-level features of SQL Server. Some features an on-premises app depends on are missing; Learn notes that apps with SQL Agent dependencies can be hard to migrate.
- **Azure SQL Managed Instance** is PaaS with near-100% compatibility with SQL Server Enterprise Edition. It lists SQL Server Agent, cross-database queries, linked servers and CLR among its supported features, and it automates patching and backups.
- **SQL Server on Azure VMs** has full compatibility but is IaaS: you manage the OS and SQL Server.
## Example
A finance team's nightly Agent job copies rows from the sales database into the reporting database with a cross-database query. On Managed Instance the job and the query move as they are.
W: SQL Managed Instance: it is the PaaS option Learn recommends for most migrations with minimal changes, because it keeps instance-level features such as SQL Server Agent, cross-database queries and linked servers while Microsoft handles patching and backups.
X: A=Single databases: each Azure SQL Database is isolated and supports database-level features, so instance-scoped features such as Agent jobs and linked servers would have to be redesigned.
B=Elastic pool: a pool only shares resources between Azure SQL databases; it does not add instance-level features, so the Agent jobs and linked servers still would not move as they are.
D=SQL Server on VMs: it is fully compatible, but it is IaaS, so the company would manage the operating system, SQL Server updates and backups, which a managed PaaS service avoids.
T: Lift-and-shift of a SQL Server instance with instance-level features into PaaS → Azure SQL Managed Instance.
V: Azure SQL Managed Instance

@ DP-900 D2 T2.2 applied use-case
S: A manufacturer's SQL Server database works with a vendor monitoring agent that must be installed on the same server as SQL Server and needs access to the operating system. It wants to move to Azure quickly without changing anything. Which option should it use?
A: Azure SQL Managed Instance, because it has near-100% compatibility with SQL Server Enterprise Edition features.
B: Azure SQL Database Hyperscale, because it separates compute and storage and scales to very large databases.
C: SQL Server on Azure Virtual Machines, because it gives full control of the SQL Server engine and the operating system.
D: Azure Database for PostgreSQL flexible server, because it lets you add extensions that run inside the database.
K: C
G: ## IaaS versus PaaS for SQL Server
- In **PaaS** (Azure SQL Database, Azure SQL Managed Instance), Microsoft runs the operating system and the database engine. You never log on to the host, so you cannot install software on it.
- In **IaaS** (SQL Server on Azure VMs), you get a Windows or Linux VM with SQL Server. You have full administrative rights over the operating system and the SQL Server instance.
## When the VM is the right choice
Learn names SQL Server on Azure VMs as best for migrations and applications that require **OS-level access**, and lists "the ability to deploy application or services on the host where SQL Server is placed" as a capability only the VM option has. Moving to the VM is like moving databases from one on-premises server to another.
## Example
A plant uses a vendor agent that reads SQL Server error logs from the local disk. It keeps working on an Azure VM, because the VM is a normal server the company controls.
W: SQL Server on Azure VMs: it is the only Azure SQL option that gives operating-system access and lets you install other software on the same host, so the vendor agent and the database move unchanged.
X: A=SQL Managed Instance: it is highly compatible at the database-engine level, but as PaaS it gives no access to the host operating system, so the agent cannot be installed next to SQL Server.
B=SQL Database Hyperscale: Hyperscale is about size and scaling inside a PaaS database. It still hides the operating system, so it does not solve the agent requirement.
D=PostgreSQL flexible server: it runs a different database engine, so the SQL Server database would need conversion, and the service is PaaS without OS access as well.
T: Needs OS access or other software on the database host → SQL Server on Azure Virtual Machines (IaaS).
V: SQL Server on Azure Virtual Machines

G: ## Service models in the Azure SQL family
- **IaaS** (infrastructure as a service): Azure provides virtualized compute, storage and networking. You install, patch and run the software. SQL Server on Azure VMs is IaaS.
- **PaaS** (platform as a service): Azure also runs the operating system and the database engine, and automates updates, backups and recovery. You work with databases, logins, tables and queries.
## The two PaaS options
- **Azure SQL Database**: database-level service for new cloud apps (single database or elastic pool).
- **Azure SQL Managed Instance**: instance-level service for migrating existing SQL Server workloads with minimal changes.
## Tip
If you could log on to a server and install Windows updates, the option is IaaS, whatever software runs on it.
W: A=Azure SQL Database: Learn classifies it as a relational database as a service, in the PaaS category, with patching and backups built in.

X: B=SQL Server on Azure VMs: this is IaaS. The VM image saves installation time, but you still manage the operating system and SQL Server.
D=VM Scale Sets with SQL Server: scale sets are a compute service for groups of identical VMs, so SQL Server on them is still customer-managed IaaS, and SQL Server does not scale out this way.
E=Azure Dedicated Host: it reserves physical hardware for your VMs, which is even more infrastructure-level control, not a managed database platform.
T: Azure SQL Database and Azure SQL Managed Instance are PaaS; SQL Server on Azure VMs is IaaS.

@ DP-900 D2 T2.2 applied tradeoff
S: A team moves a database from SQL Server on an Azure VM to Azure SQL Database. Which TWO tasks will Microsoft perform for the team after the move? (Select TWO)
A: Applying updates and patches to the database engine and to the operating system underneath it.
B: Deciding which indexes to create and rewriting slow queries that the application sends to the database.
C: Creating database logins and users and granting them permissions on the tables of the database.
D: Taking automatic database backups that the team can use for a point-in-time restore when needed.
E: Choosing which application data to keep, which to delete and how sensitive each column of data is.

G: ## What PaaS takes off your plate
With SQL Server on a VM, the team manages everything above the hardware: the operating system, SQL Server updates, backups and high availability. With Azure SQL Database (PaaS), Microsoft manages the database engine, the OS and the hardware.
- **Microsoft**: patching and upgrading the engine and OS, automatic backups with point-in-time restore, built-in high availability.
- **Still the customer**: databases and logins, index and query tuning, auditing and security settings, and the data itself.
## Example
After the move, nobody on the team schedules a Patch Tuesday window or a backup job any more. They still review slow queries and decide who may read the payroll table.
W: A=Engine and OS patching: Learn states that with SQL Database you no longer manage the database engine, the operating system or the hardware; updates are applied automatically.
D=Automatic backups: backups are built in, and Azure SQL Database supports point-in-time restore to an earlier state.
X: B=Index and query tuning: Learn lists index and query tuning among the tasks you continue to administer. Built-in intelligence can recommend indexes, but the database design stays the team's job.
C=Logins and permissions: databases and logins remain the customer's responsibility in PaaS; Microsoft does not decide who gets access.
E=Data retention and classification: the data and how it is governed always stay with the customer, in every service model.
T: Moving to Azure SQL Database hands patching, backups and high availability to Microsoft; logins, tuning and data stay with you.
V: Azure SQL Database

@ DP-900 D2 T2.2 applied use-case
S: A developer needs an Azure SQL Database for a test environment that is used for a few hours on some days and sits idle for long periods. She wants compute charges only while the database is in use. Which option fits best?
A: The provisioned compute tier, which keeps a fixed amount of compute allocated and billed every hour of the day.
B: The serverless compute tier, which scales compute with demand and can pause the database when it is inactive.
C: An elastic pool with one database in it, which bills only for the minutes when the database runs queries.
D: The Hyperscale service tier with read-only geo-replicas, which turn off compute in the primary when idle.
K: B
G: ## Compute tiers in Azure SQL Database
In the vCore purchasing model, a single database can use one of two compute tiers:
- **Provisioned**: you choose a fixed amount of compute, which is reserved and billed per hour whether or not it is used.
- **Serverless**: compute scales automatically between a minimum and maximum, and you are billed per second for the compute actually used.
## Auto-pause
Serverless can **automatically pause** a database after a configurable period of inactivity. While paused, only storage is billed; the database resumes on the next login or activity. Auto-pause can also be turned off.
## Example
A test database used on Tuesday and Thursday afternoons pauses at night and over the weekend, so compute is billed only during the test sessions. The first connection after a pause takes a little longer while the database resumes.
W: Serverless compute tier: it bills compute per second for what is used and pauses the database during inactive periods, when only storage is billed, which matches intermittent test use.
X: A=Provisioned compute: resources stay allocated and are billed every hour, so the idle periods would still cost compute.
C=Pool with one database: an elastic pool is billed for each hour it exists at its configured size, regardless of use, and a pool with one database shares nothing.
D=Hyperscale with geo-replicas: geo-replicas add readable copies in other regions; they never stop billing for the primary's compute and would raise cost.
T: Intermittent, unpredictable use of a single database with pay-for-use compute → serverless compute tier with auto-pause.
V: Azure SQL Database

S: In Azure SQL Database, what is the role of the logical server (the SQL Database server) that you create along with your databases?

When you create an Azure SQL Database, you also create (or pick) a **server**. This is not a machine you can see or log on to. Learn calls it a **logical construct** that acts as a central administrative point for multiple single or pooled databases.

W: Central administrative point: the logical server groups single and pooled databases and holds their logins, firewall rules, auditing rules, threat detection policies and failover groups.

@ DP-900 D2 T2.2 advanced troubleshooting
S: A team moved its SQL Server database to a single Azure VM and assumed the VM's availability SLA protected the database. During a SQL Server service crash, the VM stayed up but the database was offline. What explains this?
A: The VM SLA covers the virtual machines, not the SQL Server processes on them, so database high availability is the team's job.
B: SQL Server on Azure VMs supports only the Express edition, which has no automatic restart of the database service after a crash.
C: The VM SLA applies only when the database is also registered in an Azure SQL Database elastic pool on the same logical server.
D: Microsoft restarts SQL Server automatically only on Linux VMs, so the team should have chosen a Linux image for the database.
K: A
G: ## Who keeps the database available
- With **Azure SQL Database** and **Azure SQL Managed Instance** (PaaS), high availability of the database is built in. Microsoft runs the engine and fails over to healthy resources.
- With **SQL Server on Azure VMs** (IaaS), Microsoft's SLA covers the **virtual machines**, not the SQL Server processes running on them. Learn's comparison lists "You need to implement your own High-Availability solution" as a point for the VM option.
## What the team must add on a VM
To protect the database itself, the team configures SQL Server high availability features across two or more VMs, placed in an availability set or across availability zones. Registering with the SQL IaaS Agent extension adds help such as automated backup, but HA design stays with the customer.
W: VM SLA, not SQL Server SLA: on IaaS the agreement covers the VM infrastructure, so a crash of the SQL Server service on a running VM is the customer's problem to design for with their own HA setup.
X: B=Express edition only: all supported versions and editions of SQL Server, including Standard and Enterprise, can be installed on Azure VMs, and the edition is not why the database went offline.
C=Elastic pool registration: elastic pools belong to the PaaS Azure SQL Database service; a VM-hosted SQL Server cannot be placed in one, and the VM SLA does not depend on it.
D=Linux-only restart: the operating system choice does not change the SLA. On both Windows and Linux VMs, the SLA still covers only the VM.
T: SQL Server on Azure VMs: the SLA covers the VM; you build SQL Server high availability yourself. PaaS options include it.
V: SQL Server on Azure Virtual Machines

G: ## What you gain and lose with IaaS
SQL Server on Azure VMs is a normal SQL Server installation on a Windows or Linux VM.
**Gains compared with PaaS**

G: ## High availability options in flexible server
