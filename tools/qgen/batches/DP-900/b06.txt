@ DP-900 D3 T3.2 applied use-case
S: An online retailer has shoppers on four continents. Its shopping-cart service stores JSON data whose shape changes often, and every shopper must get fast reads and writes from a nearby region. Which Azure data service fits best?
A: Azure Cosmos DB, with the account replicated to several Azure regions and multi-region writes turned on.
B: Azure SQL Database, with one database in a central region and a fixed table schema for every cart row.
C: Azure Blob Storage, with each shopping cart saved as a separate JSON file in a container in one region.
D: Azure Database for PostgreSQL flexible server, with one server in one region and JSON stored in columns.
K: A
G: ## What Azure Cosmos DB is
Azure Cosmos DB is a fully managed NoSQL database service (platform as a service). Microsoft runs the servers, patching, updates and backups; you create databases and containers and store items.
## Why it suits global, fast-changing apps
- **Flexible schema**: items in the same container do not need the same structure, so the cart format can change without a schema migration.
- **Global distribution**: you add Azure regions to the account and Cosmos DB replicates the data to each one automatically.
- **Low latency everywhere**: users read from the nearest replica, and with **multi-region writes** they also write to the nearest region.
## Example
A shopper in Sydney adds an item to a cart. The write goes to the Australia region of the account, and Cosmos DB replicates it to the other regions in the background.
W: Azure Cosmos DB with several regions: it is schema-agnostic, replicates data to every region you add, and with multi-region writes each shopper reads and writes against a nearby replica, which keeps latency low worldwide.
X: B=Azure SQL Database in one region: a relational database expects a fixed schema, and a single central region means shoppers far away pay the network round trip on every request.
C=Blob Storage files: object storage keeps files, not a queryable database of cart items, and one region does not give nearby reads and writes to users on other continents.
D=PostgreSQL flexible server in one region: it is a managed relational service that can store JSON, but one regional server does not give users on four continents local writes.
T: Flexible-schema data plus fast reads and writes for users around the world → Azure Cosmos DB with global distribution.
V: Azure Cosmos DB

@ DP-900 D3 T3.2 applied tradeoff
S: A company already uses Azure Cosmos DB for its mobile app. It now wants interactive dashboards and large batch analysis over years of sales history for its data analysts. What does Microsoft recommend for this analytical workload?
A: Running the analysts' large aggregate queries directly against the app's Cosmos DB containers during business hours.
B: Mirroring the Cosmos DB data into Microsoft Fabric and running the analysts' dashboards and batch analysis there.
C: Moving all of the app's data into Azure Table storage, because a key-value store is designed for analytical queries.
D: Creating a second Cosmos DB account with the Apache Gremlin API, because graph queries are designed for sales reporting.
K: B
G: ## Operational versus analytical workloads
- An **operational** (OLTP) workload reads and writes small amounts of data per request, many times a second: a cart update, a profile read.
- An **analytical** (OLAP) workload scans and aggregates large volumes of data: sales by month over five years.
Azure Cosmos DB is built for the first kind. Learn names its good fits as latency-sensitive, highly elastic, high-throughput and mission-critical apps, and lists analytical workloads (interactive, streaming and batch analytics for data analysts and scientists) as a **poor fit**, pointing to **Microsoft Fabric** instead.
## Keeping both
Cosmos DB data can be brought into Fabric without building an ETL pipeline (Fabric mirroring), so the app keeps its fast database and the analysts work in an analytics platform.
W: Mirror into Microsoft Fabric: Learn says analytical workloads are a poor fit for Cosmos DB and recommends Fabric for them; Fabric mirroring copies the data with no ETL pipeline, so the analysts work there while the app stays on Cosmos DB.
X: A=Large queries on the app's containers: big scans and aggregations consume request units and compete with the app's own traffic, and this is exactly the workload Learn calls a poor fit.
C=Azure Table storage: Table storage is a simple key-value store for fast lookups by key, not an analytics engine for aggregations over years of history.
D=Gremlin API account: the Gremlin API is for graph data such as social networks; it is another operational API of Cosmos DB, not an analytics platform.
T: Cosmos DB serves operational app data; large-scale analytics (OLAP) belongs in Microsoft Fabric.
V: Azure Cosmos DB, Microsoft Fabric

@ DP-900 D3 T3.2 applied definition
S: A developer is starting a new app on Azure Cosmos DB and wants the native API, which stores JSON documents and is queried with a SQL-like syntax. Which API is it?
A: Azure Cosmos DB for Table, which stores rows that are found by a partition key and a row key.
B: Azure Cosmos DB for MongoDB, which stores BSON documents queried with the MongoDB Query Language.
C: Azure Cosmos DB for NoSQL, the API that older documentation and samples refer to as the SQL API.
D: Azure Cosmos DB for Apache Cassandra, which stores column-family tables queried with CQL statements.
K: C
G: ## The native API
Every Azure Cosmos DB account uses one API, chosen when you create the account. **Azure Cosmos DB for NoSQL** is the native API: data is stored as JSON documents and queried with a SQL-like language.
- It was previously called the **SQL API**; old documents that say "SQL API" mean the same thing.
- Microsoft recommends it for new high-scale apps that need instant autoscale and automatic failover across regions.
## Example query
`SELECT * FROM customers c WHERE c.id = "joe@litware.com"` returns a JSON document such as `{"id": "joe@litware.com", "name": "Joe Jones"}`.
The other APIs (MongoDB, Table, Apache Cassandra, Apache Gremlin) are compatibility APIs that let apps use the drivers and query languages of other database systems.
W: Azure Cosmos DB for NoSQL: it is the native API, stores JSON documents, uses a SQL-like query syntax and was formerly named the SQL API.

B=Cosmos DB for MongoDB: it also stores documents, but it is a compatibility API that uses MongoDB drivers and MQL method calls, not the native SQL-like language.
D=Cosmos DB for Apache Cassandra: CQL looks like SQL, but this API stores column-family data for Cassandra apps; it is a compatibility API, not the native one.
T: Native Cosmos DB API = Azure Cosmos DB for NoSQL (formerly SQL API): JSON documents plus SQL-like queries.

@ DP-900 D3 T3.2 applied use-case
S: A development team has years of experience with MongoDB drivers and the MongoDB Query Language. It wants to keep using them while gaining the request-unit-based, globally distributed Cosmos DB model. Which Azure Cosmos DB API should it choose?
A: Azure Cosmos DB for MongoDB, which supports the MongoDB wire protocol and stores data in BSON format.
B: Azure Cosmos DB for NoSQL, which stores JSON documents but needs the Cosmos DB SDKs and SQL-like queries.
C: Azure Cosmos DB for Apache Gremlin, which stores vertices and edges and is queried by graph traversals.
D: Azure Cosmos DB for Table, which stores entities and is queried through Azure Table storage SDK calls.
K: A
G: ## Compatibility APIs
Cosmos DB exposes several **wire-protocol-compatible APIs**. The API decides which drivers, query language and data format your app uses; internally Cosmos DB stores the data in its own format.
## Azure Cosmos DB for MongoDB
- Works with existing MongoDB drivers, SDKs and tools, often with only a new connection string.
- Stores documents in **BSON** (binary JSON) and uses the **MongoDB Query Language (MQL)**, for example `db.products.find({id: 123})`.
- Learn describes it as a fit for teams with MongoDB skills that want the globally distributed, request-unit-based Cosmos DB model.
## A related service
Learn points to **Azure DocumentDB** (a separate service with MongoDB wire protocol compatibility) for migrating existing MongoDB apps or using the full MQL feature set. Within Cosmos DB itself, the MongoDB-compatible API is Azure Cosmos DB for MongoDB.
W: Azure Cosmos DB for MongoDB: it supports the MongoDB wire protocol, so the team keeps its drivers and MQL skills, and the data lives in the request-unit-based, globally distributed Cosmos DB service.
X: B=Cosmos DB for NoSQL: it is a document API too, but the team would have to rewrite queries in the SQL-like syntax and switch to the Cosmos DB SDKs, which is what it wants to avoid.
C=Cosmos DB for Apache Gremlin: it serves graph data with Gremlin traversals; MongoDB drivers cannot talk to it.
D=Cosmos DB for Table: it uses the Azure Table storage programming model for key-value entities, not MongoDB drivers or MQL.
T: MongoDB skills and drivers on Cosmos DB → Azure Cosmos DB for MongoDB (BSON documents, MQL).
V: Azure Cosmos DB

@ DP-900 D3 T3.2 applied use-case
S: A social networking startup stores people, the groups they join and who follows whom. Its most important queries walk these relationships, such as "friends of friends who like this band". Which Azure Cosmos DB API fits this data best?
A: Azure Cosmos DB for Table, storing each person as an entity with a partition key and a row key.
B: Azure Cosmos DB for Apache Cassandra, storing each person as a row in a column-family table.
C: Azure Cosmos DB for MongoDB, storing each person as a BSON document in a single collection.
D: Azure Cosmos DB for Apache Gremlin, storing people as vertices and relationships as edges.
K: D
G: ## Graph data
In a **graph**, entities are **vertices** (nodes) and the relationships between them are **edges**. Both can carry properties. Graphs help when the connections between data matter as much as the data: social networks, recommendation engines, fraud detection, organization charts.
## Azure Cosmos DB for Apache Gremlin
- Built on the open-source Apache TinkerPop framework and queried with the **Gremlin** traversal language.
- Example: `g.V('3').addE('reports to').to(g.V('1'))` adds an edge from one employee vertex to another.
- A traversal such as "friends of friends" follows edges hop by hop instead of joining tables.
W: Azure Cosmos DB for Apache Gremlin: it stores property graphs of vertices and edges, and Gremlin traversals are designed for multi-hop relationship queries like friends of friends.
X: A=Cosmos DB for Table: key-value entities are fast to look up by key, but following chains of relationships would need many separate lookups in application code.
B=Cosmos DB for Apache Cassandra: column-family tables suit high write volumes such as sensor data; they do not model relationships as traversable edges.
C=Cosmos DB for MongoDB: documents hold rich data per item, but multi-hop relationship queries are not what a document model is built for.
T: Relationships are the main query target (social graph, recommendations) → Azure Cosmos DB for Apache Gremlin.
V: Azure Cosmos DB

@ DP-900 D3 T3.2 applied definition
S: In the Azure Cosmos DB resource hierarchy, at which level do you set the partition key, the throughput and the indexing policy for a set of items?
A: The account, which is the top-level Azure resource and sets one partition key for all of its databases.
B: The database, which is a logical namespace and sets one indexing policy shared by all of its items.
C: The item, which is a single document, row, node or edge and carries its own throughput settings.
D: The container, which is the primary unit of storage and scaling where these settings are configured.
K: D
G: ## Four levels
Azure Cosmos DB organizes data in a four-level hierarchy:
- **Account**: the top-level Azure resource; it can manage an unlimited amount of data and throughput.
- **Database**: a logical namespace that groups related containers.
- **Container**: the primary unit of **storage and scaling**. Its partition key, throughput, indexing policy and optional time to live (TTL) are set here.
- **Item**: one data entity in a container. Depending on the API, an item is called a document, row, node or edge.
## Example
An account `contoso-shop` holds a database `sales`, which holds containers `orders` (partition key `/customerId`) and `products` (partition key `/category`).
W: The container: Learn calls it the primary unit of storage and scaling and lists partition key, throughput, indexing policy and TTL as container-level settings.
X: A=The account: it is the top-level resource and the place where regions and the default consistency level are set, not a single partition key for everything.
B=The database: it groups containers; it can share throughput across containers, but the partition key and indexing policy belong to each container.
C=The item: items are the data themselves; they carry property values, not throughput or indexing settings.
T: Account → database → container → item; the container is where partition key, throughput and indexing are configured.
V: Azure Cosmos DB

@ DP-900 D3 T3.2 applied definition
S: In one Azure Cosmos DB for NoSQL container, one item has five properties and another item has fifteen completely different properties. Which characteristic of Cosmos DB does this show?
A: Strict schema enforcement, because the container rejects items whose properties differ from the first item.
B: Schema-agnostic storage, because items in the same container do not need to share the same structure.
C: Table normalization, because the extra properties are split automatically into separate linked tables.
D: Column-family storage, because the native API stores every property as its own column on disk storage.
K: B
G: ## Schema-agnostic data
A relational table defines its columns up front, and every row must follow them. Azure Cosmos DB is **schema-agnostic**: you do not define a schema before storing data, and items in the same container can have different properties.
## Why this matters
- Apps whose data shape changes over time can add new properties without a migration.
- Records that are naturally different (a book and a laptop in one product catalog) can live side by side.
Cosmos DB also **indexes all properties automatically** by default, so queries still work across items of different shapes.
W: Schema-agnostic storage: Learn states that items in the same container do not need to share the same structure, so one item can have five properties and another fifteen different ones.
X: A=Strict schema enforcement: Cosmos DB does not require a schema up front and does not reject items because their properties differ.
C=Table normalization: normalization is a relational design practice; Cosmos DB stores each item whole, as one JSON document, and does not split it into linked tables.
D=Column-family storage: that is the model of the Apache Cassandra API; the NoSQL API stores JSON documents.
T: Items in one Cosmos DB container may have different structures: the service is schema-agnostic.
V: Azure Cosmos DB

@ DP-900 D3 T3.2 applied tradeoff
S: Developers moving from a relational database to Azure Cosmos DB ask how indexes are created for the properties their queries filter on. What is the default behavior?
A: Cosmos DB automatically creates and maintains indexes on all item properties, with no manual index management.
B: Cosmos DB creates no indexes until a database administrator runs a CREATE INDEX statement for each property.
C: Cosmos DB indexes only the item id property, so every other filter performs a full scan of the container.
D: Cosmos DB builds indexes once per night in a batch job, so new items are not searchable until the next day.

G: ## Indexing in a relational database
In a relational database, a database administrator decides which columns get indexes and creates them with statements such as `CREATE INDEX`. Missing indexes make queries slow; too many make writes slow.
## Indexing in Azure Cosmos DB
- By default, Cosmos DB **automatically indexes every property** of every item.
- The index is kept up to date as items are written, so new data can be queried right away.
- You can change the **indexing policy** on a container (for example, to exclude properties you never query), but you do not have to.
This fits the schema-agnostic model: since items can have any properties, the service indexes whatever arrives.
W: Automatic indexing of all properties: Learn states that Cosmos DB creates and maintains indexes on all item properties by default, so no schema or manual index work is needed.
X: B=Manual CREATE INDEX: that is how relational databases work; Cosmos DB needs no index statements for its default behavior.
C=Only the id property: the default policy covers every property, not just the id, so filters on other properties use the index.
D=Nightly batch indexing: the index is maintained as data is written; there is no nightly delay before new items can be found.
T: Azure Cosmos DB indexes every property automatically by default; an indexing policy is optional tuning.

@ DP-900 D3 T3.2 advanced tradeoff
S: A team is choosing a partition key for a Cosmos DB container of customer orders that will grow large. Which choice follows the guidance on Learn?
A: A property with only two values, such as `isPriority`, so that the data stays in as few partitions as possible.
B: A property that is the same for every item, such as `country` in a one-country shop, so all orders stay together.
C: A property with many distinct values and an even spread of data, such as `customerId`, to balance throughput.
D: A property that changes on every update, such as `lastModified`, so that new writes always go to new partitions.
K: C
G: ## What a partition key does
Every container has a **partition key**: a property whose value decides which **logical partition** an item belongs to. Cosmos DB spreads logical partitions across servers, which is how a container grows beyond one machine. Each logical partition can hold up to 20 GB.
## A good partition key
- Has **many distinct values** (high cardinality).
- Spreads data and requests **evenly** across those values, so no single partition becomes a hot spot.
## Example
With `customerId` as the key, thousands of customers give thousands of partitions, each small. With `isPriority`, everything lands in two partitions, and the one holding normal orders gets almost all the traffic and size.
W: Many distinct, evenly spread values: Learn says a well-chosen partition key has many distinct values and an even spread of data, which keeps throughput balanced as the container grows; `customerId` fits that.
X: A=Two-value property: two values mean at most two logical partitions, which concentrates traffic and quickly runs into the size limit per logical partition.
B=Same value for every item: all orders would fall into one logical partition, so the container could not spread data or load at all.
D=Frequently changing timestamp: a partition key value is part of the item's identity, and keying on write time sends all new writes to the newest values, creating a hot spot.
T: Choose a partition key with many distinct values and an even spread of data and requests.
V: Azure Cosmos DB

@ DP-900 D3 T3.2 applied use-case
S: A multiplayer game stores player profiles in Azure Cosmos DB. Players in Europe and Asia complain that saving their progress is slow, because every write goes to the single write region in the US. Which feature addresses this?
A: Switching the account to the Strong consistency level, so that each save is confirmed by every region.
B: Enabling multi-region writes, so that each player writes to the nearest region and data is replicated.

A player in Seoul saves a level. With multi-region writes, the save is accepted by the Korea region in milliseconds instead of crossing the Pacific.

@ DP-900 D3 T3.2 applied definition
S: A banking app on Azure Cosmos DB must never show a balance that is older than the latest committed write, even if this adds latency. Which consistency level gives this guarantee?
A: Session, which guarantees consistency only within a single client session that made the write.
B: Eventual, which lets replicas converge over time and gives the weakest guarantee of the levels.
C: Consistent prefix, which never shows writes out of order but may still return some stale data.
D: Strong, which guarantees that every read reflects the most recent committed write to the data.
K: D
G: ## Why consistency levels exist
When data is replicated to several regions, a write reaches some replicas before others. A database must choose between waiting for every replica (consistent but slower) and answering from the nearest one (fast but possibly stale).
## The five levels in Azure Cosmos DB, strongest to weakest
- **Strong**: every read sees the most recent committed write.
- **Bounded staleness**: reads lag behind writes by at most a set time or number of versions.
- **Session**: within one client session, you read your own writes; the most widely used level.
- **Consistent prefix**: never see writes out of order, but data may be stale.
- **Eventual**: replicas converge over time; weakest guarantee, highest availability.
Stronger levels add write latency; weaker levels give better performance and availability.
W: Strong: it guarantees that every read returns the most recent committed write, which is the banking requirement; Learn notes the cost is higher write latency because data must commit across regions.
X: A=Session: it guarantees that the client that wrote the data reads its own writes, but other users in other sessions may still read an older balance.
B=Eventual: replicas converge only over time, so a read may return an older balance; it is the opposite of what the bank needs.
C=Consistent prefix: it keeps writes in order but explicitly allows stale reads, so an outdated balance is possible.
T: Every read must see the latest write → Strong consistency; accept the extra latency as the trade-off.
V: Azure Cosmos DB

@ DP-900 D3 T3.2 applied comparison
S: In a shopping app, each user must always see the items they just added to their own cart, while it is fine if other users see changes a little later. Which consistency level does this describe, the one Learn calls the most widely used?
A: Strong, which makes every read in every region wait until the latest write is committed everywhere.
B: Session, which guarantees that within a client session the user reads the writes made in that session.
C: Eventual, which gives no ordering guarantee, so a user may not see their own newest change at once.
D: Bounded staleness, which lets all reads lag behind writes by a set time or number of item versions.
K: B
G: ## Read your own writes
Many apps need one specific guarantee: **the person who changed data sees the change immediately**. Whether other people see it a moment later usually does not matter.
## Session consistency
- Consistency is guaranteed **within a single client session**: reads in the session reflect writes made in that session.
- Other sessions may see the update slightly later.
- Learn calls Session the **most widely used** level for both single-region and globally distributed apps, because it gives users a correct view of their own data without the latency cost of Strong.
## Example
Ana adds a lamp to her cart and refreshes the page: the lamp is there. Ben, browsing the same store, is not affected by Ana's cart at all.
W: Session: it guarantees read-your-own-writes inside one client session while letting other sessions lag slightly, which is exactly this cart requirement, and Learn names it the most widely used level.
X: A=Strong: it would also show the user their change, but it makes every read wait for the latest write everywhere, which is more guarantee and more latency than the app needs.
C=Eventual: replicas converge only over time, so the user could refresh and briefly not see the item they just added.
D=Bounded staleness: it caps how far reads in other regions may lag (K versions or T time), so a user served from another region could briefly miss their own change; Learn names Session, not this level, as the most widely used.
T: Users must see their own changes; others may lag → Session consistency (the most widely used level).
V: Azure Cosmos DB

@ DP-900 D3 T3.2 applied definition
S: Azure Cosmos DB measures and bills database capacity in request units (RUs). Which statement describes a request unit correctly?
A: A single performance currency for all operations, roughly the cost of reading one 1-KB item by its ID and partition key.
B: A fixed hourly fee for each container, charged the same amount no matter how many reads and writes it handles.
C: The number of virtual CPU cores assigned to the account, chosen from a list of sizes when the account is created.
D: A count of client connections that may be open at once, after which further requests are queued by the service.
K: A
G: ## Request units
Cosmos DB uses **request units per second (RU/s)** as one measure of capacity. Every operation (read, write, query, delete) costs some number of RUs.
- One RU is roughly the cost of a **point read**: reading one 1-KB item by its ID and partition key.
- Bigger items, writes and complex queries cost more RUs.
## Why one unit helps
Instead of sizing CPU, memory and disk separately, you think about one number for both performance and cost. You can reserve RU/s for a container or database (provisioned throughput) or pay for the RUs consumed (serverless).
W: Single performance currency: Learn defines one RU as roughly the cost of reading one 1-KB item by ID and partition key, and every operation consumes some number of RUs.
X: B=Fixed hourly fee per container: cost follows the RUs used or provisioned, not a flat charge per container regardless of activity.
C=Virtual CPU cores: vCore sizing belongs to other services; the RU model deliberately hides CPU and memory behind one throughput number.
D=Count of open connections: RUs measure the work done by operations, not how many clients are connected.
T: Request unit = Cosmos DB's single currency for the cost of operations; one point read of a 1-KB item ≈ 1 RU.

S: A small team is building an internal tool on Azure Cosmos DB. Traffic is intermittent and hard to predict, there are hours with no requests, and the tool runs in one Azure region. Which throughput option fits best?
A: Dedicated provisioned throughput on each container, reserving a fixed number of RU/s around the clock.
B: Shared provisioned throughput at database level, reserving RU/s that up to 25 containers can share.
C: Serverless, with no throughput to provision upfront and billing only for the RUs requests consume.
D: Multi-region writes with provisioned throughput, so idle capacity in one region serves the others.
K: C
G: ## Ways to get throughput
- **Dedicated provisioned throughput**: a set amount of RU/s reserved for one container.
- **Shared provisioned throughput**: RU/s set on the database and shared by its containers.
- **Autoscale**: provisioned throughput with a maximum RU/s; Cosmos DB scales within the range by demand.
- **Serverless**: nothing to provision; you pay for the RUs your requests consume.
## When serverless fits
Learn recommends serverless for **intermittent, unpredictable** traffic. Idle hours cost nothing for throughput.
One limit: **serverless accounts run in a single Azure region**. Apps that need global distribution use provisioned throughput.
W: Serverless: there is no throughput to provision and the team pays only for RUs consumed, which suits intermittent traffic with idle hours, and the tool's single region fits the serverless single-region limit.
X: A=Dedicated provisioned throughput: reserved RU/s are billed every hour even when no request arrives, which wastes money on a tool that is often idle.
B=Shared database throughput: sharing RU/s between containers still reserves capacity around the clock, so idle hours are still paid for.
D=Multi-region writes: this is a global distribution feature for users in many regions; it adds regions and cost and does nothing for idle time in one region.
T: Intermittent, unpredictable traffic in one region → serverless; global distribution needs provisioned throughput.

S: Which TWO Azure Cosmos DB APIs use a query language with a syntax similar to SQL? (Select TWO)
A: Azure Cosmos DB for NoSQL, queried with statements such as SELECT * FROM customers c WHERE c.id = "joe".
B: Azure Cosmos DB for MongoDB, queried with method calls on collections such as db.products.find({id: 123}).
C: Azure Cosmos DB for Apache Cassandra, queried with CQL statements such as SELECT * FROM Employees WHERE ID = 2.
D: Azure Cosmos DB for Apache Gremlin, queried with traversals such as g.V().hasLabel('employee').order().by('id').
E: Azure Cosmos DB for Table, queried through REST-style addresses such as Customers(PartitionKey='1',RowKey='124').
K: A,C
G: ## How each API is queried
The API you pick decides the query language your app uses:
- **NoSQL**: a SQL-like language over JSON documents, for example `SELECT * FROM customers c WHERE c.id = "joe@litware.com"`.
- **MongoDB**: the MongoDB Query Language (MQL), an object-oriented style of method calls such as `db.products.find({id: 123})`.
- **Apache Cassandra**: Cassandra Query Language (CQL), whose syntax is similar to SQL, such as `SELECT * FROM Employees WHERE ID = 2`.
- **Apache Gremlin**: graph traversals such as `g.V().hasLabel('employee')`.
- **Table**: the Azure Table storage model; an entity is fetched by PartitionKey and RowKey, for example through a REST-style address.
## Tip
Seeing `SELECT ... FROM ... WHERE` means NoSQL or Cassandra; seeing `db.collection.find(...)` means MongoDB; seeing `g.V()` means Gremlin.
W: A=Cosmos DB for NoSQL: its native query language is SQL-like and runs over JSON documents.
C=Cosmos DB for Apache Cassandra: CQL has a syntax similar to SQL, with SELECT, FROM and WHERE clauses.
X: B=Cosmos DB for MongoDB: MQL is an object-oriented syntax of method calls on collections, not SQL-like statements.
D=Cosmos DB for Apache Gremlin: Gremlin is a graph traversal language that chains steps over vertices and edges.
E=Cosmos DB for Table: entities are read by partition key and row key through the Table storage model, not with SQL-like statements.
T: SQL-like syntax: NoSQL API (SQL-like over JSON) and Cassandra API (CQL); MongoDB uses MQL, Gremlin uses traversals.

- the query language (SQL-like, MQL, CQL, Gremlin);
- the client libraries and drivers.
## Under the hood
Cosmos DB stores data in its own internal format; each API is an **abstraction layer** on top. That is why every API gets the same managed features: global distribution, elastic throughput, automatic indexing and tunable consistency.
