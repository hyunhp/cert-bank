@ DP-900 D3 T3.1 applied use-case
S: A media company needs to store millions of product photos and short videos and serve them directly to web browsers over HTTPS. The files have no fixed schema. Which Azure storage service is designed for this?
A: Azure Blob Storage, which stores large amounts of unstructured data as objects that clients reach by URL over HTTP or HTTPS.
B: Azure Table storage, which stores each photo and video as an entity with a partition key and a row key for fast lookups.
C: Azure Files, which stores the photos in an SMB file share that each web browser mounts as a network drive before viewing.
D: Azure SQL Database, which stores each photo and video in a table column so the website can query them with Transact-SQL.
K: A
G: ## Object storage for unstructured data
**Azure Blob Storage** is Microsoft's object storage service. It is optimized for storing massive amounts of **unstructured data**: data with no fixed data model, such as images, video, audio, documents and log files.
Microsoft Learn lists what Blob Storage is designed for:
- serving images or documents directly to a browser
- streaming video and audio
- storing files for distributed access, backup, restore and archiving
- storing data for analysis
Every blob has its own address, so clients reach it over HTTP or HTTPS from anywhere, for example `https://contosomedia.blob.core.windows.net/photos/shoe-001.jpg`.
W: Azure Blob Storage: it is object storage built for huge volumes of unstructured files, and each blob has a URL that a browser can request directly over HTTPS, which is exactly how a website serves photos and video.
X: B=Azure Table storage: Table storage holds structured, non-relational records made of name-value properties (an entity can be at most 1 MB), not large binary media files served to browsers.
C=Azure Files: Azure Files provides SMB and NFS file shares that servers and PCs mount; public web browsers don't mount network drives, so it is the wrong way to serve media to website visitors.
D=Azure SQL Database: a relational database is built for structured rows queried with SQL; storing millions of videos inside table columns is costly and is not how media is delivered to browsers.
T: Unstructured files such as images and video that must be served by URL belong in Azure Blob Storage.

@ DP-900 D3 T3.1 applied definition
S: A developer is learning how Azure Blob Storage organizes data. Which statement correctly describes the relationship between a storage account, a container and a blob?
A: A container holds one or more storage accounts, and each storage account holds the blobs for a single application.
B: A blob holds one or more containers, and each container stores one file together with its metadata and properties.
C: A storage account holds containers, and each container organizes a set of blobs, much like a folder holds files.
D: A storage account holds exactly one container, and that container must hold blobs of only one blob type at a time.
K: C
G: ## The three Blob Storage resources
Blob Storage has three levels of resources:
- **Storage account**: gives your data a unique namespace in Azure. The account name is part of every address, for example `https://contosodata.blob.core.windows.net`.
- **Container**: organizes a set of blobs, similar to a directory in a file system. An account can have an unlimited number of containers.
- **Blob**: the actual object (a file such as an image, a CSV or a backup). A container can hold an unlimited number of blobs.
## Example
`https://contosodata.blob.core.windows.net/invoices/2026/inv-0042.pdf` is the blob `2026/inv-0042.pdf` in the container `invoices` in the account `contosodata`.
W: Account, then container, then blob: the storage account is the top-level namespace, containers inside it group blobs, and each blob is one stored object, so a container plays the role of a folder.
X: A=Container holds accounts: the order is reversed; the storage account is the outermost resource and provides the namespace that contains the containers.
B=Blob holds containers: a blob is the lowest level, a single object with its properties and metadata; it cannot contain containers.
D=Exactly one container: a storage account can include an unlimited number of containers, and one container can hold block, append and page blobs together.
T: Storage account (namespace) > container (groups blobs like a folder) > blob (the stored object).

@ DP-900 D3 T3.1 applied comparison
S: A team will store three kinds of data in Azure Blob Storage: uploaded PDF documents, an application log that only ever has new lines added to its end, and the virtual hard disk of a VM that needs fast random reads and writes. Which blob type matches each?
A: Page blobs for the PDFs, block blobs for the log file, and append blobs for the VM disk that is read and written at random.
B: Block blobs for the PDFs, append blobs for the log file, and page blobs for the VM disk that is read and written at random.
C: Append blobs for the PDFs, page blobs for the log file, and block blobs for the VM disk that is read and written at random.
D: Block blobs for all three, because the blob type is chosen automatically by Azure from the file extension during upload.
K: B
G: ## Three blob types
You choose a blob's type when you create it, and it can't be changed later.
- **Block blobs** are made of blocks and are optimized for uploading large amounts of data efficiently. They are the normal choice for files such as documents, images and video.
- **Append blobs** are made of blocks too, but new blocks can only be added at the end; existing blocks can't be updated or deleted. That makes them ideal for logging.
- **Page blobs** are collections of 512-byte pages optimized for random read and write operations. Azure virtual machine disks are backed by page blobs.
## Example
`report.pdf` is a block blob, `app-2026-10-30.log` is an append blob, and a VM's data disk is a page blob.
W: Block, append, page: documents are uploaded as block blobs, a log that only grows at the end fits append blobs, and random read/write disk access is what page blobs are built for.
X: A=Page, block, append: page blobs are for random-access disks, not documents, and append blobs can't update existing data in place, so they can't back a VM disk.
C=Append, page, block: append blobs only add to the end, which is a poor fit for whole documents, and VM disks are backed by page blobs, not block blobs.
D=Block blobs for everything: the type is chosen by the client when the blob is created, not detected from the file extension, and block blobs don't give the in-place random writes a disk needs.
T: Block blobs for files, append blobs for append-only logs, page blobs for random-access VM disks.

@ DP-900 D3 T3.1 applied troubleshooting
S: An application writes audit events to an append blob. A developer now tries to correct an event that was written an hour ago by overwriting that part of the blob, and the operation is not supported. Why?
A: Append blobs are read-only once they reach 1 MB in size, so any older event becomes locked until the blob is copied to a new block blob.
B: Append blobs can only be changed by an administrator who has a lease on the container, so the developer needs the container lease first.
C: Append blobs are stored in the archive tier by default, so the blob must be rehydrated to an online tier before any part is changed.
D: Append blobs only allow new blocks to be added at the end, and updating or deleting existing blocks is not supported for this blob type.
K: D
G: ## How append blobs work
An **append blob** is built from blocks, like a block blob, but it is optimized for **append operations**:
- The only way to modify it is the Append Block operation, which adds a block at the **end** of the blob.
- Updating or deleting existing blocks is **not supported**.
This makes append blobs a natural fit for logs and audit trails: every new event is added to the end, and earlier entries stay as they were written.
## What to do instead
To "correct" an event, write a new event that records the correction. If data really must be rewritten in place, use a block blob (replace blocks and commit a new block list) or a page blob (overwrite pages).
W: Only appends at the end: append blobs accept new blocks at the end of the blob and do not support changing or removing blocks that are already there, so an in-place overwrite fails by design.
X: A=Read-only at 1 MB: there is no 1 MB lock; an append blob keeps accepting new blocks up to its maximum size, but at no size can existing blocks be changed.
B=Container lease needed: a container lease only locks the container against deletion, and even the holder of a lease on the blob itself can only append; the limitation comes from the blob type, not from permissions.
C=Archive tier by default: access tiers can only be set on block blobs, so an append blob is never in the archive tier; new data lands in an online tier.
T: Append blobs only grow at the end; existing blocks can't be modified, which suits logs and audit trails.

@ DP-900 D3 T3.1 applied use-case
S: A retailer keeps its product images in Azure Blob Storage. The images are viewed thousands of times a day by the online store. Which access tier gives the lowest access cost for this data?
A: Cool tier, because it has lower storage costs than hot and is meant for data that the store reads many times every day.
B: Hot tier, because it is the online tier for data in active use, with the highest storage cost but the lowest access cost.
C: Cold tier, because it has the lowest access cost of the online tiers when data is read thousands of times every day.
D: Archive tier, because it has the lowest storage cost and still lets the store read each image immediately when needed.
K: B
G: ## Access tiers trade storage cost against access cost
Azure Blob Storage lets you put each block blob in an **access tier** that matches how often it is used:
- **Hot** (online): data accessed or modified frequently. Highest storage cost, lowest access cost.
- **Cool** (online): infrequently accessed data, kept at least 30 days. Lower storage cost, higher access cost than hot.
- **Cold** (online): rarely accessed data that still needs fast retrieval, kept at least 90 days. Lower storage cost and higher access cost than cool.
- **Archive** (offline): rarely accessed data that can wait hours to be retrieved, kept at least 180 days. Lowest storage cost.
The more often data is read, the more the per-access cost matters, which pushes busy data to hot.
W: Hot tier: data in active use, read thousands of times a day, is what hot is optimized for; its access costs are the lowest of all tiers, so it is cheapest overall for heavily read images.
X: A=Cool tier: cool is meant for infrequently accessed data; its access costs are higher than hot, so frequent reads would cost more.
C=Cold tier: cold has even higher access costs than cool and is meant for rarely accessed data, the opposite of this workload.
D=Archive tier: archive is offline; blobs there can't be read until they are rehydrated, which can take hours, so a store could not display the images.
T: Frequently read data belongs in the hot tier: highest storage cost, lowest access cost.

@ DP-900 D3 T3.1 applied tradeoff
S: A company keeps monthly reports in Azure Blob Storage. After a few months, reports are opened only a few times a year, but when someone asks for one it must open immediately. The company wants to cut storage cost. Which tier fits best?
A: Archive tier, because it is the cheapest tier and it returns each report within a few seconds whenever a user requests it.
B: Hot tier, because older data accessed only a few times a year costs the least to store when it stays in the hot tier.
C: Cold tier, because it is an online tier for rarely accessed data that still needs fast retrieval, at a lower storage cost.
D: Premium block blob performance, because SSD-based storage has the lowest storage cost for data that is rarely accessed.
K: C
G: ## Online versus offline tiers
Hot, cool and cold are **online** tiers: a blob in any of them can be read immediately, with the same retrieval latency and throughput. The difference is cost:
- each cooler online tier has **lower storage cost** and **higher access cost**
- cooler tiers have a **minimum storage period** (cool 30 days, cold 90 days); moving or deleting earlier incurs an early deletion charge
**Archive** is **offline**: it has the lowest storage cost, but a blob must be rehydrated to an online tier before it can be read, which can take up to 15 hours at standard priority.
## Choosing
Rarely read + must be available immediately = cold (or cool). Rarely read + can wait hours = archive.
W: Cold tier: it is online, so a report opens immediately, and it is designed for rarely accessed data, with lower storage costs than hot and cool in exchange for higher access costs that matter little at a few reads a year.
X: A=Archive tier: archive is cheapest to store but is offline; a report must first be rehydrated, which can take hours, so it fails the "open immediately" requirement.
B=Hot tier: hot has the highest storage cost of all tiers; it only pays off for data in active use, not for reports opened a few times a year.
D=Premium block blob performance: premium accounts use SSDs for consistently low latency and high transaction rates; they cost more to store data, not less, and suit busy workloads rather than rarely read reports.
T: Rarely accessed data that must still be readable immediately goes to an online cool or cold tier, not to offline archive.

@ DP-900 D3 T3.1 applied troubleshooting
S: An analyst tries to download a two-year-old backup file from Azure Blob Storage and gets an error saying the blob can't be read. The blob's access tier shows Archive. What must happen before the file can be downloaded?
A: The blob must be rehydrated to an online tier such as hot, cool or cold, which can take several hours depending on the priority.
B: The storage account's redundancy must be changed to zone-redundant storage, because archived blobs are only readable from ZRS.
C: The blob must be converted from a block blob to a page blob, because only page blobs can be downloaded once they are archived.
D: The analyst must be given access to the blob's container again, because archived blobs lose all permissions after 180 days.
K: A
G: ## The archive tier is offline
While a blob is in the **archive** tier it **can't be read or modified**. Its metadata stays available, so you can still list the blob and see its properties, but not its content.
To read it, you **rehydrate** it to an online tier (hot, cool or cold), either by changing its tier or by copying it to a new blob in an online tier.
- **Standard priority** (default): can take up to 15 hours for objects under 10 GB.
- **High priority**: costs more and can complete in under an hour for objects under 10 GB; meant for emergencies.
## Why this is acceptable
Archive is meant for long-term backups and compliance data that is hardly ever read, so waiting hours for a restore is a fair trade for the lowest storage cost.
W: Rehydrate to an online tier: archived blobs are offline, so their content can only be read after rehydration to hot, cool or cold, which takes hours at standard priority and less at a higher-cost high priority.
X: B=Change to ZRS: redundancy doesn't make archived data readable; in fact the archive tier is supported only in LRS, GRS and RA-GRS accounts, not in ZRS accounts.
C=Convert to a page blob: a blob's type can't be changed after creation, and access tiers, including archive, apply only to block blobs.
D=Restore permissions: archiving doesn't remove permissions; the analyst sees the blob and its tier, and the obstacle is the offline state of the data itself.
T: Archived blobs are offline: rehydrate them to hot, cool or cold (hours) before reading.

@ DP-900 D3 T3.1 applied use-case
S: A company stores invoice scans in Azure Blob Storage. Scans should move to the cool tier 30 days after they were last modified and to archive after 180 days, without anyone moving them by hand. What should the company use?
A: Azure Files snapshots, which copy each blob to a cooler file share automatically on the schedule that the administrator defines.
B: A lifecycle management policy, a set of rules that moves blobs to cooler tiers or deletes them based on conditions such as age.
C: The default account access tier, which moves every blob one tier cooler on its own each time 30 days pass since its last change.
D: Azure Table storage, which records the age of each blob in an entity and moves the blob when its row key value has expired.
K: B
G: ## Automating tier changes
A **lifecycle management policy** is a collection of rules (a JSON document) on a storage account. Each rule has filters and actions. With it you can:
- move blobs to a cooler tier when they haven't been modified or accessed for a number of days
- delete blobs, previous versions or snapshots at the end of their life
- apply rules to the whole account, to selected containers, or to blobs that match a name prefix or blob index tag
## Example
A rule for the `invoices/` prefix: tier to cool 30 days after last modification, tier to archive after 180 days, delete after 7 years. The storage service runs the policy; no one has to move blobs by hand.
W: Lifecycle management policy: its rules automatically transition blobs to cooler tiers, or delete them, when conditions such as days since last modification are met, which matches the cool-then-archive schedule.
X: A=Azure Files snapshots: share snapshots are point-in-time copies of an Azure file share; they don't apply to blobs and don't change access tiers.
C=Default account access tier: this setting only decides the online tier (hot, cool or cold) for blobs without an explicit tier; it never ages blobs over time, and archive can't be the default.
D=Azure Table storage: Table storage is a separate NoSQL key-attribute store; it has no feature that moves blobs, and a row key is just an entity's identifier.
T: Use a lifecycle management policy to move blobs to cooler tiers or delete them automatically by age.

@ DP-900 D3 T3.1 applied definition
S: A data team wants Azure Data Lake Storage capabilities for a new analytics project. What do they need to do to get them?
A: Create a separate Azure Data Lake Storage service resource that is unrelated to Blob Storage and has its own APIs.
B: Enable the hierarchical namespace setting on an Azure Storage account, so its Blob Storage gains data lake features.
C: Create an Azure file share that uses the NFS protocol, because Data Lake Storage is a feature of Azure Files shares.
D: Create an Azure Table storage table with a partition key per folder, because Data Lake Storage is built on tables.
K: B
G: ## Data Lake Storage is Blob Storage plus a hierarchical namespace
Azure Data Lake Storage isn't a dedicated service or account type. It is a set of capabilities for big data analytics built on **Azure Blob Storage**, unlocked by enabling the **hierarchical namespace** on a storage account.
Because the data is still stored as blobs, you keep Blob Storage benefits such as low-cost access tiers, lifecycle management, high availability and disaster recovery, and you add:
- a real directory and subdirectory structure
- Hadoop-compatible access (the ABFS driver, endpoint `dfs.core.windows.net`)
- POSIX-style access control lists on directories and files
## Terminology
Data Lake Storage documentation says "file" and "file system" where Blob Storage says "blob" and "container"; they are the same things.
W: Enable hierarchical namespace: Data Lake Storage is implemented as capabilities of Blob Storage in a storage account, switched on by the hierarchical namespace setting.
X: A=Separate unrelated service: Learn states explicitly that Data Lake Storage isn't a dedicated service or account type; it is built on Blob Storage and shares its features.
C=NFS file share: NFS shares are an Azure Files feature for Linux clients; Data Lake Storage is built on Blob Storage, not on Azure Files.
D=Table storage table: Table storage holds key-attribute entities for applications; it is not the foundation of Data Lake Storage and has no folder hierarchy.
T: Data Lake Storage = Azure Blob Storage with the hierarchical namespace enabled.

@ DP-900 D3 T3.1 applied tradeoff
S: A data engineering team stores raw sales files in a storage account and organizes them into folders by year and month. Which TWO benefits do they gain by enabling the hierarchical namespace? (Select TWO)
A: Renaming or deleting a whole directory becomes a single atomic metadata operation instead of a change to every blob.
B: The files become rows in a relational table, so the team can join them to other tables with foreign key constraints.
C: Permissions can be set on individual directories and files with POSIX access control lists as well as Azure RBAC.
D: The files no longer count toward storage costs, because directory data is billed only when it is read by a query.
E: Every file is automatically converted to Parquet format, so analytics engines can read it without any extra steps.
K: A,C
G: ## What the hierarchical namespace adds
In a flat Blob Storage namespace, "folders" are only name prefixes such as `sales/2026/10/file.csv`. Renaming the "folder" `sales/2026` means processing every blob that shares that prefix.
With the **hierarchical namespace** (the core of Azure Data Lake Storage), directories are real objects:
- **Atomic directory operations**: renaming or deleting a directory is one metadata operation, with no need to enumerate all objects under it.
- **Finer-grained security**: Azure RBAC plus **POSIX access control lists (ACLs)**, set at the directory or file level.
- Efficient navigation for analytics frameworks such as Apache Spark that access the data through the Hadoop-compatible ABFS driver.
Data is still billed at Blob Storage prices and kept in its original format.
W: A=Atomic directory operations: with a hierarchical namespace, renaming or deleting a directory is a single metadata operation, not a per-blob job.
C=Directory and file ACLs: Data Lake Storage supports POSIX ACLs on directories and files in addition to Azure RBAC, so each folder can have its own permissions.
X: B=Relational table rows: the files stay files (blobs) in a data lake; the namespace doesn't turn them into relational tables with keys and constraints.
D=Free storage: Data Lake Storage is priced at Blob Storage levels; stored data is still billed, whether or not it is queried.
E=Automatic Parquet conversion: a data lake stores data in its raw, native format; converting files to Parquet is a separate processing step.
T: The hierarchical namespace gives real directories (atomic rename/delete) and directory- and file-level POSIX ACLs.

@ DP-900 D3 T3.1 applied comparison
S: A team compares the two protocols that Azure Files offers for file shares. Which TWO statements are correct? (Select TWO)
A: SMB file shares can be mounted by Windows, Linux and macOS clients, and are the usual choice to replace Windows file servers.
B: NFS file shares are the usual choice for Windows desktop users, because Windows mounts them as drive letters by default.
C: A single Azure file share can expose both SMB and NFS at the same time, so mixed clients can share one set of files.
D: NFS file shares are intended for Linux clients and workloads, such as containers and high-performance computing (HPC).
E: Azure Files supports only the NFS protocol, while SMB shares require a Windows Server VM that runs the file server role.
K: A,D
G: ## SMB and NFS in Azure Files
Azure Files supports two industry-standard protocols:
- **SMB**: supported clients Windows, Linux and macOS. Best for general-purpose file shares, lift-and-shift apps, and hybrid setups with Azure File Sync. Available on SSD and HDD media tiers.
- **NFS** (version 4.1): supported clients Linux. Best for Linux workloads, containers and HPC. SSD only, and reachable only from restricted networks.
- Applications can also use the **REST API** from any platform.
A single share uses **one** protocol: Azure file shares don't support both SMB and NFS on the same share, although one storage account can contain SMB shares and NFS shares.
W: A=SMB for Windows, Linux and macOS: SMB shares are supported by all three client types and are the general-purpose choice for replacing file servers and lifting and shifting apps.
D=NFS for Linux workloads: Learn lists Linux as the supported client for NFS shares and names Linux workloads, containers and HPC as its best fit.
X: B=NFS for Windows desktops: Learn lists only Linux as the supported client for NFS shares; Windows users connect to Azure Files over SMB.
C=Both protocols on one share: a share uses either SMB or NFS; you can have both kinds of shares in one account, but not both protocols on the same share.
E=NFS only: Azure Files natively offers SMB shares as well; no Windows Server VM with a file server role is needed.
T: Azure Files: SMB for Windows/Linux/macOS and file-server replacement, NFS for Linux workloads; one protocol per share.

@ DP-900 D3 T3.1 applied use-case
S: A company moved its file shares to Azure Files, but branch offices with slow internet links still want fast local access to frequently used files from an on-premises Windows Server. What can provide this?
A: Azure File Sync, which caches Azure file shares on on-premises Windows Servers so frequently used files are read locally.
B: Azure Data Lake Storage, which copies the hierarchical namespace to each branch so that users read directories locally.
C: A lifecycle management policy, which moves frequently used files from Azure Files to a server in each branch office.
D: Azure Table storage replication, which keeps a copy of each file's entity on every branch server for local access.
K: A
G: ## Hybrid file shares
Azure Files can **replace or supplement** on-premises file servers in two ways:
- **Mount directly**: clients map the Azure file share over SMB.
- **Cache with Azure File Sync**: Windows Servers on-premises (or in Azure) keep a local cache of an Azure file share. Users read and write against the nearby server, and Azure File Sync keeps the server and the cloud share in step.
Learn lists "hybrid with Azure File Sync" as one of the main uses of SMB file shares.
## Example
A branch office server caches the `Projects` share. Opening a large drawing happens at LAN speed, while the authoritative copy lives in Azure Files.
W: Azure File Sync: it caches Azure file shares on Windows Servers, so branch users read frequently used files from a local server while the full share stays in Azure Files.
X: B=Data Lake Storage: the hierarchical namespace organizes analytics data in a storage account; it doesn't cache file shares on branch office servers.
C=Lifecycle management policy: lifecycle rules move blobs between Blob Storage access tiers or delete them; they don't apply to file shares or copy data to on-premises servers.
D=Table storage replication: Table storage holds structured entities, not files, and has no feature that caches files on branch servers.
T: Azure File Sync caches Azure file shares on Windows Servers for fast local access in hybrid setups.

@ DP-900 D3 T3.1 applied definition
S: A developer is choosing where to keep app data and reads about Azure Table storage for the first time. Which statement best describes this service?
A: A relational database service that enforces a fixed schema on each table and supports foreign keys and stored procedures.
B: An object store for large unstructured files such as images and video, organized into containers inside a storage account.
C: A NoSQL key-attribute store for structured, non-relational data, where a table doesn't enforce a schema on its entities.
D: A managed file share service that clients mount over SMB or NFS to store documents in a shared hierarchy of folders.
K: C
G: ## Azure Table storage
**Azure Table storage** stores large amounts of **structured, non-relational** data (structured NoSQL data) as a **key/attribute store** with a **schemaless** design.
- A **table** is a collection of **entities**, and tables don't enforce a schema, so entities in one table can have different sets of properties.
- An **entity** is a set of properties, similar to a row; each **property** is a name-value pair.
- It suits data that doesn't need complex joins, foreign keys or stored procedures and can be denormalized for fast access, such as user data for web apps, address books and device information.
It is usually cheaper than a traditional SQL database for similar volumes of data.
W: NoSQL key-attribute store: Table storage keeps structured but non-relational data as entities of name-value properties, and tables don't force all entities to share the same columns.
X: A=Relational database: Table storage is non-relational; it has no fixed schema, foreign keys or stored procedures, which is precisely what sets it apart from a SQL database.
B=Object store for files: that describes Azure Blob Storage, which keeps unstructured files as blobs in containers.
D=Managed file share: that describes Azure Files, which offers SMB and NFS shares with folders.
T: Azure Table storage = schemaless NoSQL key-attribute store for structured, non-relational data.

@ DP-900 D3 T3.1 applied definition
S: An app stores customer orders as entities in Azure Table storage, using CustomerId as the partition key and OrderId as the row key. Which TWO statements about these keys are true? (Select TWO)
A: Entities that share the same partition key can be queried more quickly and can be inserted or updated in atomic operations.
B: The partition key must be a foreign key that refers to a row in another table, which keeps the orders linked to customers.
C: The row key uniquely identifies an entity within its partition, so the partition key plus row key identify one entity.
D: The row key decides which properties each entity must have, so every order in the table has exactly the same columns.
E: Partition keys are optional, so an entity can be saved with only a row key and a timestamp to identify it in the table.
K: A,C
G: ## Keys in Table storage
Every Table storage entity has three **system properties**: a **partition key**, a **row key** and a **timestamp**. Up to 252 more properties hold your own data.
- **Partition key**: groups related entities. Entities with the same partition key can be **queried more quickly** and **inserted or updated in atomic operations**.
- **Row key**: the entity's **unique identifier within a partition**.
- Together, partition key + row key identify exactly one entity; queries by these keys use the table's clustered index.
## Example
Partition key `C1042` (a customer), row keys `O-5001`, `O-5002` (that customer's orders). Reading every order of customer `C1042` stays inside one partition and is fast.
W: A=Same partition, fast and atomic: Learn states that entities with the same partition key can be queried more quickly and inserted or updated atomically.
C=Row key unique within partition: the row key is the unique identifier inside a partition, so the pair of keys identifies one entity.
X: B=Foreign key: Table storage is non-relational and doesn't support foreign keys; the partition key is just a grouping value.
D=Row key defines properties: tables don't enforce a schema, so entities can have different properties; the row key is only an identifier.
E=Optional partition key: the partition key is one of the three system properties that every entity has; it can't be left out.
T: Partition key groups entities (fast, atomic within a partition); row key is unique inside the partition.

@ DP-900 D3 T3.1 applied tradeoff
S: A web app stores user preferences and device settings. Each record is looked up by a known key, records vary in their fields, and no joins or stored procedures are needed. The team wants the lowest-cost option. Which service fits?
A: Azure SQL Database, because a relational schema with joins is the cheapest way to store records that have changing fields.
B: Azure Table storage, a low-cost schemaless key-attribute store for structured data that doesn't need joins or foreign keys.
C: Azure Files, because storing each user's settings as a file on an SMB share gives the fastest lookups by key at low cost.
D: Azure Blob Storage archive tier, because it has the lowest storage cost and returns small records instantly by their key.
K: B
G: ## When Table storage is a good fit
Learn describes Table storage as fast and cost-effective for many applications, typically **lower in cost than traditional SQL** for similar volumes of data. It fits datasets that:
- need fast lookups by key (partition key + row key)
- have flexible, changing fields (schemaless entities)
- **don't require complex joins, foreign keys or stored procedures** and can be denormalized
Typical examples: user data for web apps, address books, device information and other metadata.
## When it isn't
If you need joins, relationships enforced by foreign keys, or complex transactions across many tables, a relational database such as Azure SQL Database fits better.
W: Azure Table storage: key lookups, records with varying fields and no relational features are exactly the profile Learn gives for Table storage, which is typically cheaper than SQL for the same data.
X: A=Azure SQL Database: a relational database enforces a fixed schema and is usually more expensive for this pattern; its joins and stored procedures are features the app doesn't need.
C=Azure Files: a file share is built for shared folders mounted by clients; one file per user gives no key-based query model and adds file handling to the app.
D=Archive tier: archived blobs are offline and must be rehydrated for hours before reading, so they can't serve app settings on each request.
T: Key-based, schemaless, join-free app data at low cost fits Azure Table storage.

@ DP-900 D3 T3.1 applied comparison
S: A new employee asks how the core Azure Storage services differ. Which pairing of service and typical use is correct?
A: Blob Storage for SMB shares mapped by PCs, Azure Files for key-attribute app data, and Table storage for images and video.
B: Blob Storage for key-attribute app data, Azure Files for images and video, and Table storage for SMB shares mapped by PCs.
C: Blob Storage for images and video, Azure Files for SMB shares mapped by PCs, and Table storage for key-attribute app data.
D: Blob Storage for images and video, Azure Files for key-attribute app data, and Table storage for SMB shares mapped by PCs.
K: C
G: ## Three storage services in one account
A standard general-purpose v2 storage account can hold several data services:
- **Blob Storage** (`<account>.blob.core.windows.net`): object storage for unstructured data such as images, video, documents, backups and data lake files.
- **Azure Files** (`<account>.file.core.windows.net`): managed file shares mounted over SMB or NFS by servers and PCs.
- **Table storage** (`<account>.table.core.windows.net`): a schemaless NoSQL key-attribute store for structured, non-relational data.
(Queue storage is the fourth service in the account; it carries messages between application components.)
## How to choose
Ask what the data looks like and how it is used: files served by URL go to blobs, shared folders go to Azure Files, and small records looked up by key go to tables.
W: Blobs, files, tables: Blob Storage holds unstructured objects like media, Azure Files provides SMB shares that clients map, and Table storage keeps structured key-attribute data.
X: A=Blob for SMB, Files for key data, Table for media: every pairing is swapped; Blob Storage is object storage, not SMB shares, and Table storage can't hold large media.
B=Blob for key data, Files for media, Table for SMB: Blob Storage isn't a key-attribute database and Table storage offers no file shares that PCs map.
D=Files for key data, Table for SMB: the Blob Storage pairing is right, but Azure Files is the SMB share service and Table storage is the key-attribute store, not the other way round.
T: Blob = unstructured objects, Azure Files = SMB/NFS shares, Table storage = NoSQL key-attribute data.
