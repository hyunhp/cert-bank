@ DP-900 D1 T1.1 applied definition
S: A retail company keeps its product list in a table where every product has the same fields: ProductID, Name, Category and Price. Each product is a row and each field is a column. How is this data best described?
A: Structured data, because every record follows the same fixed schema of named fields set out as rows and columns.
B: Semi-structured data, because the fields have names that describe their values, much like the keys in a JSON document.
C: Unstructured data, because product names are free text that an application has to interpret before it can use them.
D: Vector data, because each product row is a list of values that can be compared numerically with the other rows.
K: A
G: ## Three ways to represent data
Data is a collection of facts (numbers, descriptions, observations). It usually describes **entities** such as customers or products, and each entity has **attributes** such as a name or a price. Data is classified by how strictly it follows a structure:
- **Structured data** adheres to a **fixed schema**: every record has the same fields. Most often it is **tabular**, with a row for each instance of an entity and a column for each attribute.
- **Semi-structured data** has some structure but allows variation between instances (JSON is the common example).
- **Unstructured data** has no specific structure: documents, images, audio, video and other binary files.
## Example
A `Product` table with the columns `ProductID`, `Name`, `Category`, `Price` holds one row per product. A new product cannot arrive with a different set of fields; it must fit the same columns.
W: Structured data: the defining feature is a fixed schema that every record shares, shown here as rows (one per product) and columns (one per attribute).
X: B=Semi-structured data: having named fields is not enough; semi-structured data lets the fields vary between records, while here every product has exactly the same four fields.
C=Unstructured data: a text value inside a well-defined column is still part of a structured record; unstructured data means whole files such as documents, images or video with no field layout.
D=Vector data: vectors (embeddings) are numerical representations of content produced for similarity search, not ordinary rows of product attributes.
T: Same fields for every record, set out as rows and columns = structured data.

@ DP-900 D1 T1.1 applied use-case
S: An app saves each customer as a JSON document. Most customers have one email address, some have several phone numbers and email addresses, and a few have no contact details at all. Which description fits this data?
A: Structured data, because each document is stored in JSON and JSON always enforces one fixed set of fields per entity.
B: Semi-structured data, because the documents share a general structure but their fields can vary from one customer to the next.
C: Unstructured data, because the number of contact entries differs by customer, so there is no structure at all to rely on.
D: Binary data, because JSON documents are stored as raw bytes that only the app that wrote them can interpret and render.
K: B
G: ## What makes data semi-structured
Semi-structured data has **some structure** (named fields, nesting) but **allows variation** between entity instances. Microsoft's own example is customer contact details: most customers have an email address, some have several, and some have none.
## JSON as the usual example
JavaScript Object Notation (JSON) is the most common format for semi-structured data. Each document carries its field names with the values, so two customer documents can differ:
- Customer 1 has an address and two contact entries (a home phone and an email).
- Customer 2 has an address with an extra `unit` field and only one contact entry.
JSON is just one way to represent semi-structured data; XML and key-value data are others.
## Why it matters
A store for this data must accept records whose fields differ, instead of forcing every customer into the same set of columns.
W: Semi-structured data: the customers share a common shape (name, address, contacts), but the number and kind of fields differ between documents, which is exactly the variation semi-structured data allows.
X: A=Structured data: JSON does not enforce one fixed set of fields; that flexibility is why JSON is the standard example of semi-structured data.
C=Unstructured data: the documents still have named fields and nesting; unstructured data means content such as images, audio or documents with no field layout.
D=Binary data: JSON is human-readable text in which bytes map to printable characters; raw binary that applications must render describes files such as images and video.
T: Shared overall shape with fields that vary between records, as in JSON documents = semi-structured data.

@ DP-900 D1 T1.1 applied definition
S: A law firm stores scanned contract images, recordings of client phone calls and short training videos. None of these files follow a field-and-value layout. How is this content classified?
A: Structured data, because each file has a name, a size and a creation date that are recorded the same way for every file.
B: Semi-structured data, because the files are grouped into folders by client, which gives the collection a loose hierarchy.
C: Unstructured data, because documents, images, audio and video have no specific internal structure of fields and values.
D: Relational data, because each file can be linked to a client record by storing the client's key next to the file's path.
K: C
G: ## Unstructured data
Not all data is structured or even semi-structured. **Documents, images, audio, video and binary files** might not have a specific structure: there are no named fields and values inside them for a query to pick out. This is **unstructured data**.
## What does not change the classification
- **File properties** such as name, size and date are metadata about the file, not the content itself.
- **Folders** organize files, but they do not give the content of a recording or an image any fields.
- **Links from a database** can point to a file, but the file remains unstructured.
## Example
A scanned contract is a picture of text. To answer "which contracts mention a penalty clause?", an application first has to interpret the image (for example with optical character recognition), because the file itself has no field to filter on.
W: Unstructured data: scanned images, audio recordings and videos are the standard examples of content with no specific internal structure.
X: A=Structured data: the file name, size and date are metadata that describe each file; the content inside the scans, recordings and videos still has no fields.
B=Semi-structured data: semi-structured means records with named fields that can vary, such as JSON; a folder hierarchy organizes files without adding fields to their content.
D=Relational data: storing a client key next to a file path creates a structured record about the file, but the images, audio and video themselves stay unstructured.
T: Documents, images, audio and video with no field layout = unstructured data, whatever folders or metadata surround them.

@ DP-900 D1 T1.1 applied tradeoff
S: Customers are stored in a relational table with a fixed schema. A developer now wants to record a loyalty tier, but only for a few customers. What does the fixed schema mean for this change?
A: The value can be added to just those customer rows, because each row in a table can carry its own extra fields.
B: A new column must be defined in the table schema, and rows without a loyalty tier simply hold no value in it.
C: The tier must be kept in a separate file, because a relational table's schema cannot change after it is created.
D: The whole table must be converted to JSON first, because relational tables cannot hold a value that is optional.
K: B
G: ## Fixed schema versus flexible schema
Structured data **adheres to a fixed schema, so all of the data has the same fields**. In a relational table, the schema is the list of columns; every row has a value slot for every column.
- To store a new attribute, you change the **schema** (add a column), and the column then exists for **every** row.
- Rows that have no value for it hold an empty value (in SQL, `NULL`).
- Tables can be altered after they are created; the schema is fixed in the sense that all rows share it, not that it can never change.
## The semi-structured alternative
In a JSON document store, one customer document could simply include `"loyaltyTier": "Gold"` while others leave it out. This flexibility is the main difference between semi-structured and structured data.
## Example
After the change, the `Customer` table has a `LoyaltyTier` column; 30 rows contain `Gold` or `Silver` and the remaining rows contain no value.
W: New column for all rows: a fixed schema means every row shares the same columns, so the new attribute is added to the schema and customers without a tier leave it empty.
X: A=Extra fields per row: rows in a table cannot carry their own private fields; that per-record flexibility belongs to semi-structured data such as JSON documents.
C=Schema cannot change: relational schemas can be altered after creation (for example by adding a column); the point is that every row then shares the change.
D=Convert to JSON: relational tables handle optional values with empty (null) column values, so converting the whole table to another format is unnecessary.
T: Structured data = one schema shared by every record; adding an attribute means adding it to the schema for all rows.

@ DP-900 D1 T1.1 applied definition
S: A data model describes customers, products and sales orders. For each customer it records a name, an address and a phone number. In data terms, what are the name, address and phone number?
A: Entities, because each one is a separate thing that the organization needs to keep track of over time.
B: Attributes, because each one is a characteristic that describes an instance of the customer entity.
C: Keys, because each one is a value that uniquely identifies a single customer among all the others.
D: Schemas, because each one defines the full set of fields that every customer record must contain.
K: B
G: ## Entities and attributes
Data structures usually represent the **entities** that matter to an organization: customers, products, sales orders. Each entity has one or more **attributes**, its characteristics.
- **Entity**: the thing being described (a customer).
- **Attribute**: a characteristic of that thing (the customer's name, address, phone number).
- **Instance**: one particular entity (the customer Joe Jones).
## How this maps to each representation
- In a **table**, each row is an instance and each column is an attribute.
- In a **JSON document**, each document is an instance and each name-value pair is an attribute.
## Example
In `{"firstName": "Joe", "lastName": "Jones"}` the document is one customer instance and `firstName` and `lastName` are attributes.
W: Attributes: name, address and phone number are characteristics that describe each customer, which is what attributes are.
X: A=Entities: the entity here is the customer (alongside products and orders); its name, address and phone number describe it rather than being separate things tracked on their own.
C=Keys: a key uniquely identifies one instance, but names, addresses and phone numbers can repeat or change, so none of them is a dependable identifier.
D=Schemas: a schema is the whole definition of fields for an entity; each single field in it is one attribute.
T: Entity = the thing (customer); attributes = its characteristics (name, address, phone).

@ DP-900 D1 T1.1 applied use-case
S: A support team wants its search to find articles that mean the same thing as a question, even when they share no words. Its developers convert each article into a list of numbers that represents its meaning. What is this kind of data called?
A: Vector data (embeddings), a numerical representation of content that AI applications use to find similar content.
B: Column-family data, a set of logically related columns that are grouped together and stored in the same family.
C: Delimited text data, in which every number in the list is separated by a comma and each article ends with a new line.
D: Key-value data, in which each number in the list is a key that points to one stored copy of the original article.
K: A
G: ## Vector data
Organizations increasingly work with **vector data**, also called **embeddings**: a numerical representation of content such as text or images. A model turns each item into a list of numbers so that items with similar meaning end up close together.
- AI applications compare vectors to find content that is **semantically similar**, not just content that shares the same words.
- Vector search data stores keep these high-dimensional vectors and run similarity (nearest neighbor) queries over them.
## Example
The question "my laptop will not turn on" and the article "fixing a device that fails to power up" share almost no words, but their embeddings are close, so a vector search returns the article.
W: Vector data (embeddings): lists of numbers that represent the meaning of content, used by AI applications to find similar items, is exactly how Microsoft describes vector data.
X: B=Column-family data: column families group related columns in a nonrelational database; they describe how a store organizes columns, not a numeric representation of meaning.
C=Delimited text data: CSV-style files describe how values are written in a text file; the scenario is about what the numbers represent and how they are compared.
D=Key-value data: in a key-value store each record is a unique key with a value; the numbers in an embedding are coordinates of meaning, not keys pointing to copies.
T: Numbers that capture the meaning of text or images for similarity search = vector data (embeddings).

@ DP-900 D1 T1.1 applied troubleshooting
S: Thermostats send JSON readings. After a firmware update, newer devices add a humidity field that older devices never send. A loader that maps every message to a fixed set of table columns now drops the new field. What is the underlying cause?
A: The messages are unstructured data, so no loader can read individual fields from them without first rendering them.
B: The messages are semi-structured data whose fields vary by device, while the loader assumes one fixed structured schema.
C: JSON can hold only one level of fields, so the humidity value has to travel in a separate message from the temperature.
D: The loader reads the messages as binary large objects, so it ignores any field name that appears after the first record.
K: B
G: ## When semi-structured data meets a fixed schema
**Semi-structured** data such as JSON lets each record carry its own set of fields. **Structured** data requires every record to fit the same fixed set of fields.
A pipeline that copies semi-structured messages into a fixed table has to decide what happens to fields the table does not have:
- the field is dropped (what happened here), or
- the schema is changed to add a column, or
- the data is kept in a store that accepts flexible documents.
## Example
Old message: `{"deviceId": "t-17", "temp": 21.5}`. New message: `{"deviceId": "t-90", "temp": 22.0, "humidity": 41}`. Both are valid JSON; only the second has `humidity`, and a loader built for the old columns has nowhere to put it.
W: Semi-structured data with a fixed-schema loader: the messages vary between devices, which semi-structured data allows, but the loader only knows the original columns, so the new field is lost.
X: A=Unstructured data: the readings have named fields and values, so they are semi-structured; unstructured data means images, audio, video and similar content.
C=One level only: JSON supports nested objects and collections, and in any case humidity is just one more field at the same level, not a nesting problem.
D=Binary large objects: JSON is human-readable text, and the loader clearly reads its fields; the problem is the missing column, not a binary read.
T: Semi-structured records can gain fields at any time; a process that assumes a fixed schema must be changed to handle them.

@ DP-900 D1 T1.1 applied comparison
S: A supplier sends purchase orders as XML. Each order has elements for the buyer and a list of line items, and some orders also include delivery instructions that others leave out. How should this data be classified?
A: Structured data, because XML tags require every element to appear in every order in one fixed sequence.
B: Unstructured data, because XML is plain text, and any text without a table layout is unstructured data.
C: Semi-structured data, because the tags give the orders a structure while the elements can vary per order.
D: Graph data, because the nested elements of each order form nodes and edges linked to the other orders.
K: C
G: ## XML as semi-structured data
**Extensible Markup Language (XML)** uses tags in angle brackets to define elements and attributes, such as `<Customer name="Joe">`. Like JSON, it is a common way to represent **semi-structured** data:
- The tags give the data a structure (a buyer element, a list of line items).
- Elements can be nested, repeated or left out, so records can differ.
## Comparing the categories
- **Structured**: the same fields in every record (tables, CSV with fixed columns).
- **Semi-structured**: named, nested fields that may vary (JSON, XML).
- **Unstructured**: no field layout at all (images, audio, video, documents).
## Example
Order 1 contains `<DeliveryInstructions>Leave at gate</DeliveryInstructions>`; order 2 has no such element. Both are valid orders in the same feed.
W: Semi-structured data: XML's tags define a structure, but elements such as delivery instructions can be present in some orders and absent in others.
X: A=Structured data: XML does not force every element into every document; optional and repeated elements are normal, which is why XML is semi-structured.
B=Unstructured data: being text does not make data unstructured; XML text is organized into named elements that applications can read field by field.
D=Graph data: nesting inside one document is a hierarchy, not a graph of nodes and edges linking separate entities.
T: XML and JSON represent semi-structured data: named, nestable fields that can vary between records.

@ DP-900 D1 T1.1 applied tradeoff
S: An online store sells TVs, which have a screen size and resolution, and shirts, which have a size, color and fabric. A single fixed table for all products would leave most columns empty in most rows. Which representation suits this catalog best?
A: Structured data in one table with a column for every attribute of every product type, as fixed schemas handle variety best.
B: Unstructured data, saving a photo of each product label so the attributes never need to be recorded as fields at all.
C: Semi-structured data, such as one JSON document per product holding only the attributes that apply to that product.
D: Delimited text, writing all products to a CSV file in which each line may have a different number of values on it.
K: C
G: ## Matching representation to the data
When entities of the same kind have **different attributes**, a fixed schema becomes awkward: one wide table needs a column for every possible attribute, and most cells stay empty.
**Semi-structured** data fits better: each record holds only the fields that apply to it.
- TV document: `{"id": 1, "type": "TV", "screenSize": 55, "resolution": "4K"}`
- Shirt document: `{"id": 2, "type": "Shirt", "size": "M", "color": "Blue", "fabric": "Cotton"}`
## The trade-off
- **Structured**: every record has the same fields, which makes consistent queries and totals simple, but variety is costly.
- **Semi-structured**: flexible per record, but the application must cope with fields that may be missing.
Document databases are commonly used for product catalogs for this reason.
W: Semi-structured JSON documents: each product stores only its own attributes, so TVs and shirts can sit in the same catalog without a mostly empty table.
X: A=One wide fixed table: this is exactly the design the stem describes as leaving most columns empty; fixed schemas suit uniform records, not varied ones.
B=Photos of labels: images are unstructured, so the store could no longer filter or sort by size, color or screen size without first interpreting every picture.
D=Variable-length CSV lines: CSV relies on position, so lines with different numbers of values lose the meaning of each column; CSV suits records that share the same fields.
T: Entities that share a type but differ in attributes, such as a product catalog, suit semi-structured documents.

@ DP-900 D1 T1.1 applied tradeoff
S: A payroll team must be sure that every employee record has a salary, a tax code and a bank account, and it runs the same totals over all records every month. Why does structured data suit this better than semi-structured data?
A: Structured data lets each record add or omit fields freely, so new payroll fields never need a change to the schema.
B: Structured data is always smaller on disk than semi-structured data, so the monthly totals finish in less time.
C: Structured data has a fixed schema, so every record has the same fields and the totals can rely on them existing.
D: Structured data can be stored only as binary objects, so the payroll values cannot be read without permission.
K: C
G: ## The strength of a fixed schema
**Structured data adheres to a fixed schema, so all of the data has the same fields.** That consistency is valuable when:
- every record must contain certain values (salary, tax code, bank account);
- the same calculations run over all records, such as monthly totals by department;
- data is shared by many applications that all expect the same fields.

G: ## Object stores
An **object store** keeps large binary or semi-structured objects with metadata that rarely changes.
- Strengths: virtually unlimited scale, tiered cost, durability and parallel reads.
- Considerations: operations work on **whole objects**, and querying by metadata is limited.
- Typical workloads: **media assets**, backups, raw zones of a data lake, log archives.
## Azure Blob Storage
**Azure Blob Storage** is Azure's scalable object store for unstructured data such as images, documents and backups. Files can be served to browsers over HTTP(S), and it also hosts static website content.
## Choosing a store by data type
- Structured, transactional records: a relational database such as Azure SQL Database.
- Small values looked up by key with very low latency: an in-memory store such as Azure Managed Redis.
- Large unstructured files: an object store such as Azure Blob Storage.

G: ## Relational and nonrelational databases
A **database** is a central system in which data is stored and queried, usually a dedicated system for managing records rather than files.
- **Relational databases** store structured data in tables with keys and are queried with SQL.
- **Nonrelational databases** are data management systems that **do not apply a relational schema** to the data.
## The NoSQL name
Nonrelational databases are often called **NoSQL** databases, **even though some support a variant of the SQL language**. Read it as "not only SQL" or "not relational", not as "no query language".
## Four common types
- Key-value
- Document (a key-value store whose values are JSON documents)
- Column family
- Graph
They usually allow flexible schemas and scale out horizontally, and relax some relational behaviors to do so.

S: A legacy mainframe exports customer data as plain text with no commas or tabs. Every name takes exactly 20 characters, padded with spaces, and every date takes 8. A new tool that splits lines on commas returns each line as one field. What format is the export?
A: Avro, a binary row-based format whose JSON header tells the tool the length of each field in every record.
B: Fixed-width text, a delimited-text variant in which each field is given a fixed number of characters.
C: XML, a tagged text format in which each field is padded to a set length inside its own element tags.
D: Parquet, a columnar binary format that stores each field in a column chunk with a fixed byte length.
K: B
G: ## Delimited text and its variants
Delimited text stores data as plain text, with something that marks where each field and each row ends.
- **CSV**: fields separated by commas, rows ended by a new line.
- **TSV**: fields separated by tabs.
- **Space-delimited**: fields separated by spaces.
- **Fixed-width**: each field is allocated a **fixed number of characters**, so position, not a separator, marks where a field ends.
## Why the tool failed
A reader that splits on commas finds no commas in fixed-width text, so it returns the whole line as one field. The reader must be told the field positions instead (for example, characters 1-20 = name, 21-28 = date).
## Example
`Joe Jones           20261030` is a 20-character name followed by an 8-character date.
W: Fixed-width text: fields with a set number of characters, padded with spaces and no separators, are the fixed-width form of delimited text, so the reader must split by position.
X: A=Avro: Avro stores records as binary blocks, not as readable padded text; the export described here is plain text.
C=XML: XML marks fields with angle-bracket tags; the export has no tags, only padded characters.
D=Parquet: Parquet is a compressed binary columnar format; a mainframe text export with padded fields is not Parquet.
T: Plain text where each field has a set number of characters = fixed-width text, read by position rather than by delimiter.
