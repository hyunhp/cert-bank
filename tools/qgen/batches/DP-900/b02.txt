@ DP-900 D1 T1.3 applied definition
S: A bank moves $40 from a customer's checking account to her savings account. The debit succeeds, but the server fails before the credit is written. The database undoes the debit so neither balance changes. Which ACID property does this behavior show?
A: Atomicity, because the debit and the credit form one unit of work that either completes fully or is rolled back as a whole.
B: Isolation, because other transactions running at the same time cannot see the half-finished transfer between the two accounts.
C: Durability, because the database keeps the balances on disk so they survive the server failure and are there after restart.
D: Consistency, because the database checks that each account balance stays within the allowed overdraft limit for the bank.
K: A
G: ## Transactions and ACID
A **transaction** is a small, discrete unit of work that a transactional (OLTP) system records, such as a payment or a funds transfer. Relational databases protect transactions with four properties known as **ACID**:
- **Atomicity**: the transaction succeeds completely or fails completely. If one step cannot finish, the steps already done are rolled back.
- **Consistency**: a transaction can only move the data from one valid state to another valid state.
- **Isolation**: concurrent transactions cannot interfere with each other or see each other's half-finished work.
- **Durability**: once a transaction is committed, it stays committed, even if the system is switched off.
## Example
A transfer has two steps: `debit checking` and `credit savings`. If the credit fails, a database with atomicity automatically reverses the debit, so the bank never "loses" $40 halfway through.
W: Atomicity: the two steps of the transfer are treated as one unit, so when the credit cannot be written the database rolls back the debit and the transfer fails as a whole.
X: B=Isolation: isolation is about concurrent transactions not seeing each other's in-progress changes; the scenario is about undoing a partly finished transaction after a failure.
C=Durability: durability protects work that was already committed. Here the transfer never committed, and the point is that its first step was undone, not kept.
D=Consistency: consistency means the data moves only between valid states; it is not the mechanism that reverses an incomplete set of steps, and no overdraft rule is involved here.
T: All-or-nothing behavior of a multi-step transaction is atomicity.

@ DP-900 D1 T1.3 applied definition
S: While a transfer between two accounts is in progress, a second query reads both balances. The query must never return one balance from before the transfer and the other from after it. Which ACID property guarantees this?
A: Durability, which makes sure the committed balances are written to storage and survive a restart of the database server.
B: Atomicity, which makes sure the debit and the credit of the transfer are applied together or not applied at all.
C: Isolation, which makes sure concurrent transactions cannot interfere with each other or see each other's partial changes.
D: Consistency, which makes sure that a completed transfer leaves the two balances adding up to the same total as before.
K: C
G: ## Concurrency in transactional systems
Transactional systems often handle many users at once, so two transactions frequently touch the same rows at the same time. The ACID property that covers this situation is **isolation**:
- A transaction's in-progress changes are not visible to other transactions as if they were final.
- Concurrent transactions must still result in a consistent database state.
Databases implement isolation with **locking strategies** (pessimistic or optimistic locking) so that readers and writers do not trip over each other.
## Example
A transfer of $40 from account A ($100) to account B ($50) is running. A balance report that runs at the same moment must see either `A=100, B=50` (before) or `A=60, B=90` (after), never `A=60, B=50`.
W: Isolation: it stops the balance-checking query from seeing the transfer's half-applied state, so the reader gets a consistent picture of both accounts.
X: A=Durability: durability is about keeping committed changes after a crash or power loss, not about what a concurrent reader can see while a transaction is still running.
B=Atomicity: atomicity makes the transfer all-or-nothing, but it does not by itself control what another transaction sees while the transfer is still in progress.
D=Consistency: consistency describes the valid end state of the data; the requirement here is specifically about two transactions running at the same time.
T: Concurrent transactions not seeing each other's partial work is isolation.

@ DP-900 D1 T1.3 applied definition
S: An online store's database confirms to a customer that her order is committed. A moment later the datacenter loses power. When the database comes back, the order is still there. Which ACID property is the reason?
A: Consistency, because the order moved the database from one valid state to another valid state when it was committed.
B: Durability, because a transaction that has been committed stays committed even if the system is switched off.
C: Isolation, because the order transaction was kept separate from other customers' orders running at the same time.
D: Atomicity, because every row of the order was written together as a single unit of work before the power failed.
K: B
G: ## What "committed" promises
When a transactional database reports that a transaction is **committed**, it promises that the change is permanent. That promise is the **durability** property of ACID.
- The database writes committed changes (or a log of them) to persistent storage before it confirms the commit.
- After a crash or power loss, the database recovers and the committed transaction is reflected when it is switched on again.
## How it differs from the other properties
- **Atomicity** decides whether a transaction completes at all.
- **Consistency** keeps data in valid states.
- **Isolation** handles concurrent transactions.
- **Durability** keeps what was committed.
## Example
A customer sees "Order 1052 confirmed". Even if the server loses power one second later, order 1052 is in the database after the restart.
W: Durability: a committed transaction is persisted so that it survives a system failure, which is exactly why the confirmed order is still present after power returns.
X: A=Consistency: moving between valid states is true of the order, but it does not explain why the order survived a power failure after the commit.
C=Isolation: keeping concurrent orders apart matters while transactions run, not for whether a committed order survives a power loss.
D=Atomicity: atomicity explains why the order was written as all-or-nothing; surviving the outage after the commit is the role of durability.
T: Committed changes surviving a crash or power loss is durability.

@ DP-900 D1 T1.3 applied comparison
S: A team is describing the database behind its point-of-sale system to a new hire. Which TWO characteristics are typical of a transactional (OLTP) workload like this one? (Select TWO)
A: Data is stored in a highly normalized schema so that each fact is kept once and many small transactions can run independently.
B: The workload is mostly read-only, and the stored data is refreshed in large loads every night from several source systems.
C: Data is preaggregated across dimensions such as date and region so that summary queries return without scanning detail rows.
D: Records are created, read, updated and deleted many times a day, and each change must be available to the application at once.
E: The store keeps many years of history so that analysts can compare trends across long periods without touching other systems.
K: A,D
G: ## Two kinds of data workload
Data workloads are usually described as **transactional** or **analytical**.
## Transactional workloads (OLTP)
- Record business events as they happen: sales, payments, orders, stock movements.
- Many small, discrete transactions, often millions a day, using **CRUD** operations (create, read, update, delete).
- Data is **highly normalized**: split into smaller, less redundant tables so each transaction touches little data and integrity is easy to keep.
- **Schema on write**, strong consistency and ACID guarantees; heavy writes with moderate reads.
- Changes must be available immediately to the live line-of-business application.
## Analytical workloads (OLAP)
- Read-only or read-mostly, large volumes of **historical** data.
- Loaded or refreshed at intervals from operational systems.
- Often **denormalized** or **preaggregated** so that summary queries are fast.
## Example
A store's checkout writes a sale row each time a barcode is scanned (OLTP). A head-office report of five years of sales by region reads a separate analytical store (OLAP).
W: A=Highly normalized schema: OLTP stores normalize data into small, less redundant tables so that large numbers of transactions can be processed independently while integrity is preserved.
D=Frequent CRUD changes available at once: transactional systems create, update and delete records continuously, and each committed change must be visible to the live application immediately.
X: B=Read-only with nightly loads: being read-mostly and refreshed at intervals describes an analytical store, not the system that takes the sales.
C=Preaggregated across dimensions: preaggregated measures by date or region describe an OLAP or semantic model built for analysis.
E=Many years of history: OLTP systems usually keep a relevant window, such as the current fiscal year, and offload older history to a data warehouse.
T: OLTP = normalized data, many small CRUD transactions, changes visible immediately.

@ DP-900 D1 T1.3 applied use-case
S: A ticketing company sells concert seats on its website. Each purchase must reserve a seat, take payment and record the sale, and no seat may ever be sold twice. Which type of data workload is this?
A: An analytical workload, because each sale adds rows that later feed reports on how many seats sold for each concert and venue.
B: A batch workload, because the purchases are collected through the day and processed together in one scheduled job each night.
C: A transactional workload, because each purchase is a small unit of work that must be recorded at once with ACID guarantees.
D: A data lake workload, because ticket sales arrive from many devices and are kept in their raw format for later exploration.
K: C
G: ## Recognizing a transactional workload
A transactional (OLTP) workload records the business events an organization runs on, as they happen. Clues in a scenario:
- A user action that must take effect **immediately** (buy, book, pay, transfer).
- Several steps that must succeed or fail **together**.
- Rules that must never be broken, such as "no seat sold twice", enforced by **ACID** transactions and locking.
- The application is a live **line-of-business (LOB)** system.
## Where analytics fits
The same sales data is later copied to an analytical store for reporting. That later use does not change what the website's own database is: it is the transactional system of record.
## Example
Two fans click "Buy" for seat C14 at the same moment. Isolation and locking make sure only one purchase commits; the other buyer is told the seat is gone.
W: Transactional workload: every purchase is a discrete unit of work (reserve, pay, record) that must commit immediately and safely, which is what OLTP systems with ACID transactions are built for.
X: A=Analytical workload: the sales may feed reports later, but the system that takes payments and reserves seats is the transactional one; reporting would run on a separate analytical store.
B=Batch workload: collecting purchases and processing them overnight would let two people buy the same seat during the day; the sale must be recorded the moment it happens.
D=Data lake workload: a data lake holds raw files for later analysis and does not enforce the all-or-nothing, no-double-booking rules each purchase needs.
T: Immediate, all-or-nothing business events such as purchases and payments are a transactional workload.

@ DP-900 D1 T1.3 applied use-case
S: A retail chain's leaders want to see total sales by region, product category and month for the last five years, and compare this year with previous years. Which type of data workload supports this need?
A: A transactional workload on the point-of-sale database, querying the live sales tables directly every time a manager opens the report.
B: An analytical workload on a read-optimized store that holds historical sales copied from the operational systems at intervals.
C: A transactional workload with stronger locking, so the five-year totals cannot change while each manager's report query is running.
D: A file share workload, exporting each store's daily receipts to a shared folder where managers open and total them in a spreadsheet.
K: B
G: ## Analytical workloads
Analytical processing uses **read-only or read-mostly** systems that store **large volumes of historical data** or business metrics. Typical traits:
- Data is copied (for example by ETL or ELT) from operational systems into a **data warehouse**, **data lake** or **lakehouse**.
- Queries aggregate many rows: totals, averages and trends by time, product, customer or region.
- Data is refreshed at intervals that suit the business, rather than at the moment each sale happens.
- Often modeled into an **OLAP or semantic model** with measures and dimensions for fast summaries.
## Why not just query the OLTP database?
Aggregating millions of transactions is resource-intensive for an OLTP system, can block live transactions, and OLTP databases usually keep only a recent window of data, not five years.
## Example
Sales from 400 stores are loaded each night into a warehouse; a report shows `revenue by region by month` for 2021-2026 in seconds.
W: Analytical workload: historical sales copied into a read-optimized store let leaders aggregate and compare five years of data without loading the system that takes live sales.
X: A=Live point-of-sale queries: large aggregations over millions of rows slow down and can block the live transactions, and the OLTP system usually does not keep five years of history.
C=Stronger locking: more locking on the operational database would make checkout slower for customers and still does not supply the long history or the read-optimized structure.
D=File share with spreadsheets: manually totaling exported receipt files does not scale to five years of sales across a chain and gives no shared, consistent model for reporting.
T: Aggregating and comparing large amounts of historical data is an analytical workload, kept separate from the OLTP system.

@ DP-900 D1 T1.3 applied troubleshooting
S: Every month-end, finance runs a large report that totals millions of order rows directly on the order-entry database. During the report, customers complain that placing orders becomes very slow. What is the most suitable fix?
A: Normalize the order tables further so that each order row is smaller and the report reads fewer bytes for every order it adds up.
B: Remove the ACID guarantees from the order-entry database so that orders no longer wait for locks held by the month-end report.
C: Copy the order data on a schedule into a separate analytical store such as a data warehouse and run the month-end report there.
D: Ask customers to place orders outside business hours at month-end so that the finance report can use the database without contention.
K: C
G: ## Mixing workloads on one database
An OLTP database is tuned for many small reads and writes. Analytics that rely on **aggregate calculations over millions of transactions** are a poor fit there:
- They are resource-intensive and slow on a normalized schema, because the query must join many tables.
- They can **block other transactions**, so the live application slows down.
## The usual separation
Keep a relevant window of data in the OLTP system for the application, and copy data at intervals into an **analytical store** (data mart, data warehouse, lakehouse) built for heavy reads. Reporting then runs there without competing with customers.
## A related idea
Some platforms support **HTAP** (hybrid transactional and analytical processing), for example SQL Server columnstore indexes, to run some analytics on the operational system. For a big month-end report hurting customers, moving the analytics to a separate store is the classic answer.
W: Separate analytical store: moving the heavy aggregation to a data warehouse that is loaded on a schedule removes the contention, so order entry keeps its performance and finance gets a read-optimized store.
X: A=Further normalization: more normalization usually means more joins for a report, which makes analytical queries more complex, not lighter, and does nothing about the contention.
B=Removing ACID guarantees: ACID protects the correctness of every order; dropping it would risk corrupt orders and is not how workload contention is solved.
D=Ordering outside business hours: telling customers when they may buy is not an acceptable fix; the system has to keep serving its live transactional workload.
T: Heavy reporting on an OLTP database hurts transactions; copy the data to an analytical store and report there.

@ DP-900 D1 T1.3 applied definition
S: Sales managers want to see revenue totals by region, then drill down to city and to individual store, and get answers almost instantly. Which part of an analytical solution is designed for this?
A: A normalized transactional database with primary and secondary indexes on every column that a manager is likely to filter on.
B: A data lake folder of raw daily sales files that managers query with their own scripts each time they need a new total.
C: A message queue that delivers every new sale to the managers' devices as it happens so that they can add up the totals themselves.
D: An OLAP or semantic model that stores measures preaggregated across dimensions and hierarchies such as region, city and store.
K: D
G: ## OLAP and semantic models
In an enterprise analytics architecture, data in a warehouse or lakehouse is often loaded into an **OLAP model**, today usually called a **semantic model** (historically a **cube**). Power BI semantic models are a common example.
- **Measures** are numeric values such as sales revenue, taken from fact tables.
- **Dimensions** are the ways you slice them, such as date, customer, product or location, taken from dimension tables.
- Measures are aggregated at the intersections of dimensions, across **hierarchy levels**.
## Why it is fast
Because the totals are **preaggregated**, a query for "total sales by region" does not have to add up every detail row each time. Users can **drill up and down** (region > city > store) and **slice and dice** without knowing how the tables are related.
## Example
A model holds `Revenue` by `Region > City > Store` and by `Year > Month`. A manager clicks a region bar and immediately sees its cities.
W: OLAP or semantic model: it holds measures preaggregated across dimension hierarchies, so totals and drill-down from region to city to store return quickly for business users.
X: A=Normalized transactional database: OLTP stores are built for small transactions; summary queries over them must join and aggregate detail rows every time and are not designed for drill-down.
B=Raw files in a data lake: raw files are a flexible source for exploration, but managers would wait for processing at query time and need technical skills to write the scripts.
C=Message queue to devices: delivering each event to people's devices is a messaging pattern, not an analytical model, and leaves the aggregation work to the managers.
T: Preaggregated measures across dimension hierarchies with drill-down = OLAP / semantic model.

G: ## Data lake versus data warehouse
Both are analytical stores, but they make different promises.
## Data lake
- Holds **large volumes of data in its native, raw format**: structured tables, semi-structured JSON, XML or logs, and unstructured images, audio or video.
- **Schema on read**: data is stored untransformed and given structure only when it is used.
- Low storage cost and very scalable; ideal for exploratory analytics, data science and machine learning, and for keeping raw data whose value is not yet known.
## Data warehouse
- Holds **structured, curated** data in **relational schemas** optimized for read queries such as reporting and BI.
- **Schema on write**: data is shaped and transformed as it is loaded.
- Low query latency, but more expensive and less flexible about data types.
## Example
Photos and raw sensor logs go into the lake as they are. Later, a cleaned sales table built from the ERP exports is loaded into a warehouse for the monthly finance reports.
W: Data lake: it stores mixed structured, semi-structured and unstructured data cheaply in raw form and applies structure only when someone reads it, which suits data whose future use is not yet decided.
X: B=Data warehouse: a warehouse expects structured, curated data in a schema defined up front, so photos and raw logs whose use is still unknown do not fit.
C=OLAP semantic model: a semantic model holds aggregated, modeled data for business reporting, not raw photos and log files kept for future exploration.
D=Transactional database: an OLTP database records live business transactions in normalized tables; it is neither low-cost bulk storage nor suited to images and raw logs.
T: Many data types, raw format, use decided later = data lake (schema on read).

@ DP-900 D1 T1.3 applied tradeoff
S: An order-entry database has slowed down because it holds ten years of orders. The company still needs the old orders for trend reports. What is the common approach for transactional systems?
A: Delete orders older than the current year from all systems, because historical data has no further value once orders are fulfilled.
B: Keep a relevant window such as the current fiscal year in the OLTP system and offload older history to a data warehouse.
C: Copy all ten years of orders into every table of the OLTP database so that each query finds the old data without needing a join.
D: Move the entire order-entry application into the data warehouse so that live orders and history are stored in one read-optimized place.
K: B
G: ## History in a transactional system
Storing the history of transactions indefinitely, or too much data in any one table, slows down query performance in an OLTP system. The live application usually needs only recent data.
## The common solution
- Keep a **relevant window of time** (for example the current fiscal year) in the OLTP database.
- **Offload historical data** to systems built for analysis, such as a **data mart** or **data warehouse**.
- Run long-range trend reports against the analytical store.
## Why not merge the two
A data warehouse is optimized for heavy reads and large aggregations, not for many small writes with immediate ACID guarantees. OLTP and OLAP stores have different strengths, so most architectures keep both and copy data between them.
## Example
The orders database holds 2026 orders. Orders from 2016-2025 live in the warehouse, where the "ten-year trend by product" report runs.
W: Window plus offload: keeping only recent data in the OLTP system restores its performance, and moving older orders to a data warehouse keeps them available for trend reports.
X: A=Delete old orders: the company has said it still needs the history for trends, and history is exactly what an analytical store is meant to keep.
C=Copy history into every table: duplicating data across tables adds redundancy and makes the OLTP database even larger and slower, the opposite of the goal.
D=Run order entry in the warehouse: an analytical store is read-optimized and refreshed at intervals; it is not designed to be the live system that records each order.
T: OLTP keeps a recent window; history is offloaded to a data warehouse for analysis.

@ DP-900 D1 T1.3 applied definition
S: When data is copied from a highly normalized OLTP database into an analytical store, designers often combine some tables and repeat values such as product names in many rows. Why do they do this?
A: To enforce stronger ACID guarantees, because repeated values let the analytical store roll back each load if any of the rows fails.
B: To save storage space, because repeating a product name in many rows takes less space than storing it once in a separate table.
C: To make analytical queries perform faster, because fewer joins are needed when related values already sit in the same table.
D: To make inserts and updates simpler, because changing a product name then only needs to touch a single row in the store.
K: C
G: ## Normalization and denormalization
- **Normalization** splits data into smaller, less redundant tables. It suits OLTP: each transaction touches little data and there is one place to update each fact.
- The cost: reports must **join** many tables to put the facts back together, which makes analytical queries complex and slower.
## Denormalizing for analysis
Analytical stores often accept some **denormalization**, introducing duplication so queries perform faster. Analytical models usually use a **star** or **snowflake** schema instead of full normalization: a central fact table surrounded by dimension tables.
## The trade-off
- Faster, simpler reads: fewer joins.
- More storage and repeated values; updates touch more rows. In an analytical store that is acceptable, because the data is read far more often than it is changed.
## Example
Instead of joining `Sales > Product > Subcategory > Category`, a `DimProduct` table already holds the product, subcategory and category names in each row.
W: Faster analytical queries: duplicating some values removes joins, and analytical stores are read far more than written, so the extra redundancy pays off in query speed.
X: A=Stronger ACID guarantees: repeating values has nothing to do with transaction rollback; analytical loads are not made more atomic by duplication.
B=Saving storage: storing the same value many times uses more space, not less; saving space is a benefit of normalization.
D=Simpler updates: with repeated values, a change must be applied to many rows; single-row updates are the benefit of a normalized design.
T: Analytical stores denormalize (some duplication) to cut joins and speed up reads.

| | Transactional (OLTP) | Analytical (OLAP) |
|---|---|---|
| Purpose | Record business events as they happen | Analyze history and trends |
| Operations | Many small CRUD transactions | Large reads and aggregations |
| Writes | Heavy | Read-only or read-mostly |

Inconsistent formats and duplicates are **data quality** problems that come from integration. Data engineers apply **data cleaning routines** and **cleansing and transformation activities** as data moves into analytical stores.
## Why fixing it downstream fails
- A report filter hides the issue in one report, but every other report and model still reads the bad data.
- Restoring a backup brings back the same bad data, because the problem is in the load itself.
- Manual correction in spreadsheets creates more inconsistent copies.
## Example
The data engineer converts all dates to one `YYYY-MM-DD` format and removes duplicate order ids in the pipeline. From the next load on, finance and sales see the same totals.
W: Data engineer: cleansing and transformation in the pipeline fixes the problem once, at its source, so every report reads standardized, deduplicated data.
X: A=Report filters: patching each report treats a symptom; other reports still read the duplicates, and the analyst does not own the load process.
C=Nightly restore: a backup holds the same badly loaded data, so restoring it does not fix the inconsistency and is not what backups are for.
D=Manual checks in spreadsheets: users correcting totals by hand creates more conflicting copies and leaves the root cause in place.
T: Inconsistent or duplicate data from integration is fixed in the pipeline by the data engineer.

G: ## The three core roles side by side
| Role | Focus | Typical tasks |
|---|---|---|
| Database administrator | Operational databases | Availability, performance, backup and recovery, security and access |
| Data engineer | Data integration | Ingestion pipelines, cleansing, transformation, analytical stores, monitoring loads, privacy and governance |
| Data analyst | Insights | Exploring trends, analytical models, reports and visualizations |
## How they connect
The DBA keeps the source database healthy, the data engineer moves its data into an analytical store, and the analyst turns that data into reports. In small organizations one person may do all three, but the tasks still map to these roles.

D=Analyst for moving data, engineer for reports: this swaps the last two roles; pipelines are engineer work and reports are analyst work.

G: ## Building the analytical platform

## How the other roles contribute
- **Data analysts** design and build **analytical models** and reports on top of the stores, and tell engineers what they need.
- **DBAs** handle availability, performance, backup and security of database systems.
- **Business users** provide requirements and consume the results.
