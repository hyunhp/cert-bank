@ DBX-GAI D3 T3.11 applied use-case
S: A team has a working LangGraph agent that calls a foundation model and two Unity Catalog functions. They want to run it on Databricks with built-in tracing, a signature that MLflow infers by itself, and compatibility with AI Playground and agent evaluation, without rewriting the graph. What should they do?
A: Wrap the existing agent in a `mlflow.pyfunc.ResponsesAgent` subclass and convert the messages inside `predict`
B: Replace the graph with the OpenAI Agents SDK, because `ResponsesAgent` is designed around that SDK's agent objects
C: Keep the graph unchanged and log it as a generic pyfunc model, then write the input and output signature by hand
D: Rewrite the graph as an MLflow `ChatModel` subclass, because AI Playground and evaluation require that interface
K: A
G: ## Authoring interface for agents
Databricks recommends the MLflow interface `ResponsesAgent` for production agents. It is framework neutral: you build the agent with LangGraph, the OpenAI SDK, DSPy or pure Python, and `ResponsesAgent` is the adapter that connects it to Databricks logging, tracing, evaluation, deployment and monitoring. Its schema is compatible with the OpenAI Responses schema.
## Wrapping an existing agent
You do not rewrite an existing LangChain or LangGraph agent. You write a wrapper class that inherits from `mlflow.pyfunc.ResponsesAgent`, keep the agent as an attribute (`self.agent`), and implement `predict` (and `predict_stream` for streaming). Inside `predict` you convert the incoming `ResponsesAgentRequest` messages into what the agent expects and convert its output into a `ResponsesAgentResponse`.
Databricks now recommends the Agent Bricks CLI and Databricks Apps for new agents; the Model Serving path shown here is still documented.
## What you get
MLflow infers a valid signature automatically at logging time, traces `predict` and `predict_stream` automatically, and the agent works with AI Playground and agent evaluation. The older `ChatAgent` and `ChatModel` interfaces still work but are not the recommended choice for new agents.
W: ResponsesAgent wrapper: the wrapper class keeps the LangGraph code intact and gives the agent the `ResponsesAgent` contract, which brings automatic signature inference, automatic tracing and out-of-the-box compatibility with AI Playground and evaluation.
X: B=Move to the OpenAI Agents SDK: `ResponsesAgent` lets you use any third-party framework, so no framework migration is required.
C=Generic pyfunc with manual signature: this works technically, but it throws away the automatic signature inference and the tracing of streamed output that `ResponsesAgent` provides, and adds hand-maintained signatures.
D=Rewrite as ChatModel: `ChatModel` and `ChatAgent` are older interfaces that are still supported, but they are not the recommended one for new agents and no rewrite is needed.
T: Wrap an existing agent in `ResponsesAgent` instead of rewriting it, and Databricks infers the signature and traces it for you.

S: Which TWO statements are true when an index built with a 512-token embedding model is replaced with one that uses an 8,192-token embedding model? (Select TWO)
A: The chunk size should still be chosen for good retrieval granularity, not simply raised to the new maximum
B: The new window makes chunking unnecessary, because whole documents give the best retrieval
C: The existing document vectors can stay, and new documents are embedded with the new model
D: The change affects the chat model's context, because embedding models do not produce stored vectors
E: The corpus must be re-embedded with the new model, and queries must be embedded with the same model
K: A,E
G: ## Switching embedding models
Vectors from different embedding models live in different vector spaces. Distances between a query vector from one model and document vectors from another are meaningless, even when the dimension is the same.
- Documents and queries must always be embedded with the same model.
- Replacing the model means re-embedding the entire corpus and rebuilding the index (in Databricks AI Search the index refers to one embedding model or its endpoint).
## Window versus granularity
A larger window permits larger chunks but does not make them better. One vector per very large chunk blends many topics, and the chunk that is retrieved also uses more of the chat model's context. Chunk size is tuned by retrieval evaluation.
W: A=Chunk size by granularity: a bigger window allows larger chunks, but retrieval quality and prompt budget still decide the right size.
E=Re-embed everything: vectors from the two models are not comparable, so both the corpus and the queries use the new model.
X: B=No chunking: whole documents blur many topics into one vector and fill the chat model's context.
C=Keep old vectors: mixing vectors from two models in one index gives meaningless similarity scores.
D=Chat model context: embedding models create the stored vectors, so the index is directly affected.
T: A new embedding model means re-embedding documents and queries, and chunk size is still a retrieval decision.

S: What does the embedding window of 512 tokens mean for a text embedding model?

G: ## Three numbers that are easy to confuse
- Embedding window (input length): the maximum number of input tokens the embedding model reads for one text. Beyond it the text is truncated.
- Embedding dimension (output size): the number of floating point values in the vector, for example 1,024 for the hosted GTE and BGE models.
- Number of results (`num_results`): how many nearest neighbors a similarity query returns, a property of the query rather than of the model.
## Why it matters
Chunking choices must respect the window; the dimension must match the index definition; the result count is tuned to the generation step.
## Chat context window
A chat model's context window is a different limit that covers prompt and answer.
W: Input limit: the window is the number of input tokens the model reads, and tokens past it are cut off, which is why chunks must not be longer than the window.
X: A=Chat turn: this describes the context window of a generative model, not an embedding model.
B=512 results: result count is set in the query and is unrelated to the model's input limit.
C=512 dimensions: dimension is the vector length, which is a separate property (1,024 in the hosted models).
T: Embedding window is the input limit; dimension is the vector length; they are not related.
