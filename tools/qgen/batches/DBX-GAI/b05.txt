@ DBX-GAI D3 T3.11 applied use-case
S: A team has a working LangGraph agent that calls a foundation model and two Unity Catalog functions. They want to run it on Databricks with built-in tracing, a signature that MLflow infers by itself, and compatibility with AI Playground and agent evaluation, without rewriting the graph. What should they do?
A: Rewrite the graph as a plain MLflow `ChatModel` subclass, because only that interface is compatible with AI Playground and the evaluation tooling
B: Wrap the existing agent in a class that inherits from `mlflow.pyfunc.ResponsesAgent` and convert request and response messages inside `predict`
C: Keep the graph unchanged and log it as a generic pyfunc model, then define the input and output signature by hand for every new version
D: Replace the graph with the OpenAI Agents SDK, because `ResponsesAgent` only accepts agents that were written with that SDK
K: B
G: ## Authoring interface for agents
Databricks recommends the MLflow interface `ResponsesAgent` for production agents. It is framework neutral: you build the agent with LangGraph, the OpenAI SDK, DSPy or pure Python, and `ResponsesAgent` is the adapter that connects it to Databricks logging, tracing, evaluation, deployment and monitoring. Its schema is compatible with the OpenAI Responses schema.
## Wrapping an existing agent
You do not rewrite an existing LangChain or LangGraph agent. You write a wrapper class that inherits from `mlflow.pyfunc.ResponsesAgent`, keep the agent as an attribute (`self.agent`), and implement `predict` (and `predict_stream` for streaming). Inside `predict` you convert the incoming `ResponsesAgentRequest` messages into what the agent expects and convert its output into a `ResponsesAgentResponse`.
## What you get
MLflow infers a valid signature automatically at logging time, traces `predict` and `predict_stream` automatically, and the agent works with AI Playground and agent evaluation. The older `ChatAgent` and `ChatModel` interfaces still work but are not the recommended choice for new agents.
W: The wrapper class keeps the LangGraph code intact and gives the agent the `ResponsesAgent` contract, which brings automatic signature inference, automatic tracing and out-of-the-box compatibility with AI Playground and evaluation.
X: A=Rewrite as ChatModel: `ChatModel` and `ChatAgent` are older interfaces that are still supported, but they are not the recommended one for new agents and no rewrite is needed.
C=Generic pyfunc with manual signature: this works technically, but it throws away the automatic signature inference and the tracing of streamed output that `ResponsesAgent` provides, and adds hand-maintained signatures.
D=Move to the OpenAI Agents SDK: `ResponsesAgent` lets you use any third-party framework, so no framework migration is required.
T: Wrap an existing agent in `ResponsesAgent` instead of rewriting it, and Databricks infers the signature and traces it for you.

S: A streaming `ResponsesAgent` emits `output_text.delta` events with a fresh random `item_id` for each chunk and never sends a closing event. Users see text arriving, but the trace and the aggregated inference-table record show no complete answer. What is the fix?
A: Disable streaming and return the whole answer from `predict_stream`, because tracing only works for non-streamed output
B: Emit one delta event per word, because the trace only aggregates events that contain a single word
C: Use the same `item_id` for the delta events and finish with a `response.output_item.done` event that carries the complete text and that same `item_id`

K: C
G: ## Streaming contract of ResponsesAgent
To stream with `ResponsesAgent` you emit a series of delta events and then a final event:
- **Delta events**: several `output_text.delta` events that share one `item_id`, each carrying a chunk of text for the client.
- **Done event**: a final `response.output_item.done` event with the same `item_id`, containing the complete final output text.
## Why the done event matters
The done event tells Databricks to trace the agent's output with MLflow tracing, to aggregate the streamed response in AI Gateway inference tables (now documented under Unity Gateway), and to show the complete output in AI Playground. Without a matching done event, the pieces are never joined into one answer.
W: Matching `item_id` values tie the deltas to one output item, and the done event with the full text is what lets tracing and inference tables record the complete response.
X: A=Disable streaming: streaming is supported; the problem is the missing closing event, and `predict_stream` exists for streamed output.
B=One delta per word: chunk size is irrelevant. What matters is that the deltas share an `item_id` and are closed by a done event.
D=`custom_outputs` only: that field carries extra outputs such as source links; it is not where the answer is aggregated for tracing.
T: Stream deltas with one `item_id` and end with `response.output_item.done` carrying the full text.
