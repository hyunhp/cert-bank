@ DBX-GAI D2 T2.7 advanced use-case
S: A RAG application answers questions about long insurance policies. Small chunks of about 150 tokens match the user's question precisely, but the generator then lacks the surrounding clauses and gives incomplete answers. Larger chunks of about 1,500 tokens give complete context but make retrieval noisy. Which chunking design addresses both problems?
A: Keep 1,500-token chunks and add a 50% overlap between neighbors so that every sentence appears in two chunks and the retrieved text is longer
B: Embed and search small child chunks, store a parent identifier with each child, and pass the larger parent section to the LLM after a child matches
C: Embed each policy as a single document so the retriever always returns the complete policy and the LLM sees every clause
D: Keep 150-token chunks and raise the number of results returned from the index so that more fragments reach the prompt in arbitrary order
K: B
G: ## Small-to-big (parent-child) retrieval
A chunk size is a compromise: small chunks give precise embeddings and precise matches, large chunks give the generator enough context. Parent-child chunking (also called small-to-big retrieval) removes the compromise by separating what is searched from what is sent to the LLM.
- Split each document into larger **parent** sections (for example a policy section), then split each parent into small **child** chunks.
- Embed and index only the children, and store a `parent_id` (or the parent text) as metadata next to each child in the Delta table that backs the index.
- At query time, search the children, then look up the parents of the best matches and pass those parents to the prompt, removing duplicates when two children share a parent.
Databricks documents chunking as an iterative, use-case dependent choice with metadata stored beside the chunks; parent-child is one of the advanced patterns built on that metadata. The exam guide lists "advanced chunking strategies" without naming products; the pattern is generic and you implement it with your own pipeline and an AI Search index (formerly Vector Search).
W: Child chunks for search, parent for context: the small child embeddings keep matching precise, and returning the parent section gives the LLM the clauses around the match, so answers are complete without making the index noisy.
X: A=Large chunks with 50% overlap: overlap protects against a fact being cut at a boundary but does not make embeddings more specific. It also doubles stored text and returns near-duplicate passages, which makes noise worse.
C=One embedding per policy: a single vector for a long policy blurs many topics, so similarity to a narrow question is weak, and the policy can exceed the embedding model's maximum token limit, in which case it is truncated and part of the text is lost.
D=More small results: returning more fragments only adds sibling pieces by chance, in similarity order rather than document order, so the clauses are still not guaranteed to be contiguous and the prompt grows with unrelated text.
T: Parent-child retrieval searches small chunks for precision and returns their larger parent for context.

S: Many chunks in a product-manual index start with phrases such as "It must be replaced every year" or "This setting is disabled by default", so queries naming the product or setting rarely retrieve them. Which TWO changes add the missing context to these chunks? (Select TWO)
A: Prepend the document title and section heading to each chunk's text before embedding it, so the vector carries the subject of the passage
B: Replace the embedding model with a model that has a smaller maximum token limit so each chunk is processed in a shorter window
C: Remove every chunk shorter than 200 tokens from the index so that only long passages that name their subject remain
D: Store the heading path and a short document summary as metadata columns, and return them with the chunk (and, if a reranker is used, list them as columns for it to consider)

G: ## Contextual chunks
A chunk is embedded and retrieved on its own. A passage that says "it" or "this setting" has no subject, so neither the vector nor a keyword match connects it to the product the user names. Advanced chunking fixes this by attaching the context that the chunk lost when it was cut out of the document.

- **Metadata columns**: keep the heading path, product name and a short parent-document summary as columns next to the chunk in the Delta table. They support filters, can be returned to the LLM, and AI Search lets you name metadata columns (`columns_to_rerank`) that the reranker uses as extra context when it scores each passage.
Databricks guidance for RAG pipelines stresses storing metadata with the chunks and using semantically coherent chunks that can stand alone.

D=Heading and summary metadata: the context travels with the chunk, can be used for filtering, can be shown to the LLM, and can be passed to the reranker as extra columns to improve its relevance judgment.
X: B=Smaller token limit: a smaller maximum window only truncates more text. It adds no subject to a passage that never mentions one.
C=Dropping short chunks: length does not mean a chunk names its subject, and short chunks often hold the facts users ask about, so removing them reduces recall.
E=Zero overlap: overlap repeats text from a neighbor and can occasionally carry a subject forward, but removing it cannot add missing context and makes boundary losses more likely.
T: Fix context-poor chunks by adding titles and headings to the embedded text and storing them as metadata.

@ DBX-GAI D2 T2.7 applied comparison
S: Support answers often depend on a single sentence inside a long troubleshooting article, but the sentences before and after it explain the exception. The team wants to retrieve with very precise embeddings and still give the model the neighboring text. Which approach matches this goal?
A: Sentence-window retrieval: embed individual sentences, and for each hit return the sentence together with a fixed number of sentences on each side
B: Fixed-size chunking at 2,000 characters with no overlap, so that each chunk is large enough to contain the sentence and its neighbors
C: Keyword-only retrieval on the article title, so that the full article is always returned whenever a title term matches
D: Summarize each article and embed only the summary, so the retriever returns one short abstract per article
K: A
G: ## Sentence-window retrieval
Sentence-window retrieval is a variant of small-to-big retrieval. The unit that is embedded is one sentence, which gives the most specific vector possible, while the unit that is returned is a window of the surrounding sentences. The window size is a tunable parameter that you set from evaluation results.
- Index: one row per sentence with its position, document id and the neighbor text (or the position so the neighbors can be fetched).
- Query: find the best sentences, expand each into its window, merge overlapping windows, and pass them to the LLM.
Compare this with parent-child retrieval: the parent there is a structural unit (a section), while the window is purely positional. Choose structural parents when documents have clean headings and windows when they are flowing prose.
W: Sentence windows: single sentences give sharp retrieval, and expanding each hit by a few neighbors supplies the explanation of the exception without embedding large noisy blocks.
X: B=Large fixed chunks with no overlap: fixed-size chunks cut at arbitrary offsets, so the sentence and the neighbors that explain it may still land in different chunks, and the large embedding is less specific.
C=Title keyword retrieval: matching on the title returns whole articles by topic, not the sentence that answers the question, and wastes prompt space on irrelevant content.
D=Embedding only summaries: a summary drops the exact exception wording that the user needs, so retrieval would hit the article but the model would not see the sentence.
T: Sentence-window retrieval embeds single sentences and returns each hit with its neighbors.

@ DBX-GAI D2 T2.7 advanced tradeoff
S: A legal team is choosing between recursive character splitting and semantic chunking (splitting where the topic changes, based on embedding similarity between adjacent sentences) for 4 million pages that must be re-chunked each time the policy changes. Which statement describes the trade-off correctly?
A: Semantic chunking is cheaper than recursive splitting because it does not call an embedding model, and it always yields chunks of equal length
B: Recursive splitting is unsuitable for production because it can only cut at an exact character count, ignoring paragraph and sentence boundaries
C: Semantic chunking aligns boundaries with topic shifts and produces more self-contained chunks, but it needs embedding calls during ingestion and gives variable chunk sizes that must be capped
D: Both approaches yield the same chunks when the overlap is set to the same value, so the choice only affects the code library used
K: C
G: ## Choosing a splitter
Databricks describes four families of chunking strategy:
- **Fixed-size** chunking (for example LangChain `CharacterTextSplitter`): quick, but it rarely gives coherent chunks and Databricks says it rarely works for production applications.
- **Paragraph-based** chunking (for example `RecursiveCharacterTextSplitter`): tries separators from large to small (paragraphs, lines, words), so it keeps natural boundaries when it can.
- **Format-specific** chunking (for example `MarkdownHeaderTextSplitter` or HTML header splitters): uses the document's structure.
- **Semantic** chunking (for example LangChain `SemanticChunker`): analyzes content to find topic shifts, which is more involved than the basic approaches.
## The trade-off
Semantic chunking needs to embed sentences or windows during ingestion, which adds compute and cost for a large corpus, and its chunk sizes vary, so a maximum size must still be enforced to fit the embedding model's token limit. Recursive splitting is cheap, deterministic and fast to re-run.
W: Semantic chunking: boundaries follow topic changes so each chunk stands alone, at the price of embedding calls during ingestion and variable-size chunks that need a size cap.
X: A=Cheaper and uniform: semantic chunking relies on embeddings to detect topic shifts, so it costs more at ingestion, and its chunks are variable in length rather than equal.
B=Only exact cuts: a recursive splitter tries paragraph, line and word separators first, and only falls back to smaller separators when a piece is still too large. Fixed-size splitting is the one that ignores structure.
D=Same chunks: the algorithms choose boundaries differently, so overlap does not make them equivalent. The choice changes chunk content, cost and retrieval quality.
T: Semantic chunking gives coherent, variable-size chunks at higher ingestion cost; recursive splitting is cheap and predictable.

@ DBX-GAI D2 T2.8 applied definition
S: A RAG pipeline retrieves 50 candidate passages by vector similarity and passes the top 5 to the LLM. Answer quality improves when a second model re-scores the 50 candidates against the query first. What is the role of that re-ranking step?
A: It replaces the embedding model so that the documents no longer need to be embedded when the index is built
B: It expands the user's question into several paraphrases so that the first-stage search covers more vocabulary
C: It re-orders a small set of candidates with a model that reads the query and each passage together, so the most relevant passages reach the prompt and weaker ones are dropped
D: It compresses each passage into a shorter summary so more passages fit into the LLM context window
K: C
G: ## Two-stage retrieval
First-stage retrieval has to search millions of chunks quickly, so it compares precomputed vectors (a bi-encoder: the query and each chunk are embedded separately) or keywords. That is fast but approximate: the query and the chunk never "see" each other.
A **re-ranker** is the second stage. It takes a small candidate list (tens of passages) and scores each query-passage pair together, typically with a cross-encoder, which is more accurate but too slow to run on the whole corpus. The best-scoring passages go to the LLM.
- Retrieve broadly (high recall), then re-rank to keep the best few (high precision).
- Re-ranking changes the order and the selection, not the index content.
Databricks AI Search (formerly Vector Search) offers a reranker you add to a query; the docs describe it as a cross-encoder second pass on top of any retrieval strategy.
W: Re-scoring candidates: a cross-encoder-style model judges the query and each passage together, so the order reflects true relevance and the prompt receives the best few passages.
X: A=Replacing the embedding model: the re-ranker works on retrieved candidates. Documents are still embedded (or managed embeddings are used) when the index is built.
B=Query expansion: paraphrasing the question is a pre-retrieval technique that happens before the first search; re-ranking happens after it.
D=Summarizing: compressing passages is context compression and does not rank them; a summary of a weak passage is still a weak passage.
T: A re-ranker is a second-stage model that re-scores a small candidate set and keeps the most relevant passages.

In the Python SDK, a reranker is passed to `similarity_search`:

D=Final result count: `num_results` is what the caller gets back; the candidates scored by the reranker are chosen separately by the service.
X: B=Candidates limited by num_results: the docs say `num_results` does not affect the number of results used for reranking.
C=Replacing query_type: the reranker is a second pass on top of any strategy, and the docs example combines it with `query_type="hybrid"`.
E=Separate embedding model: the reranker is a service applied at query time; the index and its embeddings are unchanged.
T: Set reranker columns separately and in priority order; `num_results` is the final count, not the candidate count.

@ DBX-GAI D2 T2.8 advanced tradeoff
S: Two applications use the same AI Search index. One is an internal RAG chatbot where answer quality matters most and users accept a response time of a few seconds. The other is an autocomplete box that must answer within tens of milliseconds at high request volume. How should the reranker be used?
A: Enable it for both, because the reranker adds no measurable time and always improves ordering
B: Disable it for both, because a reranker lowers retrieval quality whenever hybrid search is already in use
C: Enable it only for the autocomplete box, since short queries have too little text for hybrid search and need a second pass

The AI Search docs describe the reranker as an optional second pass that improves quality (documented as roughly 10% on typical workloads) but adds latency, typically under one second per query. C=Only for autocomplete: this reverses the trade-off; a latency-critical box is the worst place for an added model call.
T: Reranking trades latency for precision: use it for quality-first RAG, skip it for latency-critical lookups.

@ DBX-GAI D3 T3.2 applied troubleshooting
S: A RAG assistant tells a user that the premium plan includes 24/7 phone support. The retrieved passages, visible in the MLflow trace, mention only email support and do not mention phone support at all. Which diagnosis and check fit this symptom?
A: A retrieval failure; the fix is a larger embedding model, since the answer must have come from the index
B: A latency problem; the fix is to raise the endpoint's concurrency so the model has time to finish reading
C: A formatting problem; the fix is to add a JSON schema to the prompt

G: ## Reading a response qualitatively
Qualitative assessment means reading real inputs, retrieved context and outputs and labeling the failure. Common categories:
- **Ungrounded or hallucinated**: a claim that the retrieved context does not support. Compare the answer with the retrieved passages in the trace.
- **Irrelevant**: the answer does not address the question.
- **Retrieval miss**: the right passage was never retrieved, so even a faithful model cannot answer well.

C=Repeat the question: repeating gives the user text more weight against the context, which worsens the problem.
D=Replace context with the question: the model then lacks the knowledge base content and will answer from its own memory.
T: Structure the template with instructions first and delimited context and question sections.
