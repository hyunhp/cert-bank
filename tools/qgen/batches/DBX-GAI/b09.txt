@ DBX-GAI D1 T1.1 advanced tradeoff
S: A claims team uses a chat model to label each incoming claim note as `fraud_review`, `standard` or `fast_track`. Asking the model to reason step by step raised accuracy on a 400-note evaluation set from 81% to 89%, but the downstream parser now fails on 30% of replies because the label is buried in free text. The team must keep the accuracy gain, keep one model call per note, and give the parser a field it can read from valid JSON on every reply. Which prompt design meets all three requirements?
A: Request a JSON object through a structured response format, with a `reasoning` string field first and a `label` field limited to the three allowed values
B: Drop the step-by-step instruction and ask for the bare label only, because a one-word reply is always easy for the downstream parser to read
C: Make a second model call that receives the first free-text reply and returns only the label, so the parser always gets a single clean value
D: Keep the free-text reasoning and tell the model to finish with the word LABEL followed by the value, then split each reply on that marker
K: A
G: ## Reasoning and a machine-readable answer in one reply
Step-by-step reasoning often improves accuracy on judgment tasks, because the model writes out intermediate steps before it commits to an answer. The cost is free text that a program cannot read reliably.
A structured response format solves both needs in one call. On Databricks Foundation Model APIs, a chat request can carry a `response_format` of type `json_schema`; the model must then return JSON that matches the schema. Two details matter:
- **Field order**: put `reasoning` before `label`, so the model still reasons first and the label is generated after the reasoning.
- **Enum**: restrict `label` to the allowed values, so the parser never sees a fourth spelling.
## Example
Schema `{"reasoning": string, "label": enum[fraud_review, standard, fast_track]}`; the parser reads `reply["label"]` and can store `reasoning` for audits.
W: Structured output with reasoning first: one call keeps the reasoning that produced the accuracy gain, and the schema guarantees valid JSON with a `label` field restricted to the three values.
X: B=Bare label: removing the reasoning gives up the measured gain from 81% to 89%, which the team must keep.
C=Second extraction call: it works for parsing but doubles the calls per note, breaking the one-call requirement.
D=Marker in free text: splitting on a word is still string parsing of free text; replies that omit or repeat the marker break it, and the requirement asks for a JSON field.
T: Put the reasoning and the answer in separate fields of a JSON schema, reasoning first, to keep accuracy and parse every reply.

@ DBX-GAI D1 T1.2 advanced use-case
S: An insurer routes 400,000 customer e-mails a day to 12 queues. Operations writes the routing rules in plain language, for example "disputes older than 30 days go to collections unless the customer is a broker", and rewrites them every quarter. There is no labeled training data, auditors want a short reason stored with each routing decision, and the team wants no retraining when the rules change. Which model task and setup fit best?
A: Zero-shot classification with an instruction-following chat model, with the 12 queues and current rules in the prompt, returning a label and a one-line reason
B: A fine-tuned smaller classification model trained on e-mails labeled with the current queues, then retrained each quarter after operations rewrite the rules
C: Embedding similarity, routing every e-mail to the queue whose written description vector is closest to the e-mail vector by cosine similarity
D: Summarization with a chat model followed by a keyword rule engine that routes the summary, storing the summary text as the audit reason for each e-mail
K: A
G: ## Matching the model task to the requirement
Choosing the task means looking at what the output must be and what the inputs are:
- **Classification with an instruction-following model** (zero-shot or few-shot) reads rules written in natural language, applies conditions such as "older than 30 days unless broker", and can return a label plus a short justification. Changing the rules means changing the prompt, not the model.
- **Fine-tuned classifiers** need labeled examples and retraining when the label definitions change.
- **Embedding similarity** measures topical closeness. It cannot evaluate conditions (dates, customer type) and produces no reason text.
- **Summarization** compresses text; it does not decide anything by itself.
## Cost note
A small instruction-following model often handles a 12-way routing task well; the evaluation set decides the size.
W: Zero-shot classification with rules in the prompt: the chat model applies conditional rules written in plain language, returns the reason auditors need, and a quarterly rule change is only a prompt update.
X: B=Fine-tuned classifier: there is no labeled data to train on, and every quarterly rule change would force relabeling and retraining.
C=Embedding similarity: topical closeness cannot check conditions such as dispute age or broker status, and it yields no reason for the audit.
D=Summary plus keywords: keyword rules over a summary cannot evaluate the conditional rules reliably, and a summary is not a reason for the routing decision.
T: When rules are written in language, change often and need a stated reason, classify with an instruction-following model and put the rules in the prompt.

@ DBX-GAI D1 T1.3 advanced use-case
S: A logistics firm wants to turn each inbound customer e-mail, up to 5,000 tokens long, into a ticket with three fields: `category`, `order_id` and `urgency`. The ticket must be created within 3 seconds, the budget allows only one model call per e-mail, and the e-mail already contains every fact needed, so no company documents are involved. Which chain composition fits these requirements best?
A: A prompt template holding the e-mail, a chat model with a JSON schema response format for the three fields, and a JSON output parser that returns a dictionary
B: A retriever over past tickets that adds similar examples to the prompt, a chat model, and an output parser that reads the three fields from the free-text reply
C: A map-reduce summarization chain that splits the e-mail, summarizes each part, and then extracts the three ticket fields from the combined summary
D: A tool-calling agent that may call an order lookup tool and a classifier tool in a loop until it decides the three ticket fields are complete
K: A
G: ## Pick only the components the input and output need
A chain is a sequence of components: prompt template, retriever, model, output parser, tools. Each extra component adds latency, cost and failure points, so the design starts from the required input and output:
- Input: one e-mail that already holds the facts, so no retriever is needed.
- Output: three named fields, so a structured response format plus a parser gives a dictionary directly.
- Budget: one call and 3 seconds rule out multi-call patterns such as map-reduce or agent loops.
## Context length
5,000 tokens fits easily in the context window of common chat models, so splitting the e-mail is unnecessary.
W: Template, structured model call, parser: a single call over the full e-mail returns the three fields as JSON, which the parser turns into a dictionary within the latency and call budget.
X: B=Retriever of past tickets: the e-mail already holds the facts, so retrieval adds latency and cost, and parsing a free-text reply is less reliable than a schema.
C=Map-reduce summarization: it makes several model calls per e-mail and can drop the order ID during summarizing, breaking the one-call budget.
D=Tool-calling agent: the loop makes an unknown number of model calls and tool calls, which breaks both the one-call budget and the 3-second target.
T: Compose the smallest chain that maps the given input to the required output; add retrievers or agents only when the task needs them.

@ DBX-GAI D1 T1.4 advanced use-case
S: Support agents spend about seven minutes writing each reply. Management wants that time cut in half during a four-week pilot, but legal forbids sending any AI-written text to customers without an agent's approval, and every reply must point to the knowledge-base article it relies on so that quality reviewers can check it. Which description of the pipeline's inputs and outputs translates this goal correctly?
A: Input: ticket text, customer tier and retrieved articles; output: a draft reply with article links shown to the agent, who edits and approves it before sending
B: Input: ticket text and retrieved articles; output: a final reply sent to the customer automatically, with article links appended so reviewers can audit it later
C: Input: ticket text only; output: a three-sentence summary of the customer's problem shown to the agent, who then writes the full reply from scratch
D: Input: ticket text and customer tier; output: a predicted ticket category and priority that the agent uses to pick a reply template from the existing library
K: A
G: ## From business goal to pipeline specification
A business goal becomes buildable when it is written as inputs, outputs, constraints and a success measure:
- **Goal**: halve reply-writing time, so the system must produce most of the reply text.
- **Constraint**: a human approves every message, so the output is a draft, not a sent message (human in the loop).
- **Traceability**: each reply cites its article, so the inputs must include retrieved articles and the output must carry their links.
- **Measure**: time per reply and edit distance between draft and sent reply during the pilot.
## Typical mistake
Specs that automate the last step (sending) violate approval rules, and specs that only summarize or classify leave the expensive work, writing, to the human.
W: Draft with links for approval: generating the reply text from the ticket, tier and retrieved articles removes most of the writing time, the agent's approval satisfies legal, and the links satisfy reviewers.
X: B=Automatic sending: sending AI text without an agent's approval is exactly what legal forbids, even with links attached.
C=Summary only: the agent still writes the full reply, so the time saved is small, and no article links are produced for reviewers.
D=Category and template: a predicted category does not write the reply or cite the article it relies on, so neither the time goal nor the review requirement is met.
T: Translate the goal into inputs, outputs and constraints; when a human must approve, the output is a cited draft, not a sent message.

@ DBX-GAI D1 T1.5 advanced troubleshooting
S: A billing agent has three tools: `get_invoice(invoice_id)`, `get_refund_policy(region)` and `issue_refund(invoice_id, amount)`. In testing, the model sometimes calls `issue_refund` with an amount it guessed before reading the invoice, and twice it refunded an invoice from a region where refunds need a manager's approval. Refunds cannot be undone, and the team wants to keep a single agent. Which TWO changes make the tool sequence safe? (Select TWO)
A: Make `issue_refund` reject the call unless the same request already holds a successful `get_invoice` result and a policy check for that invoice's region
B: Require a human confirmation step before `issue_refund` runs, showing the invoice amount, the policy outcome and the requested refund to an approver
C: Lower the sampling temperature to zero so that the model always plans the same tool order and stops guessing refund amounts before it reads invoices
D: Merge the three tools into one `handle_refund` tool that reads, checks and refunds in a single call with whatever amount the model passes in
E: State in the system prompt that invoices must always be read first and add three examples of the right tool order, leaving the tools unchanged
K: A,B
G: ## Ordering tools in a multi-step agent
An agent chooses its tool calls from the descriptions and the conversation. Prompts and examples make the right order **likely**, but only code makes it **certain**. For irreversible actions, the safe pattern has two layers:
- **Preconditions in the tool**: the action tool checks that the read tools ran first in the same request (the invoice was fetched, the policy for its region was checked) and rejects the call otherwise, returning an error message the model can act on.
- **Human in the loop**: a confirmation step shows the facts and the proposed action to a person before the irreversible call executes. Agent frameworks support this (for example, an interrupt in LangGraph or a confirmation message in the `ResponsesAgent` interface).
## Why not just prompt harder
Temperature and examples reduce variance but do not stop a wrong call, and one wrong refund cannot be undone.
W: A=Precondition check in the tool: code enforces that the invoice was read and the region's policy was checked before any refund, so a guessed amount is rejected.
B=Human confirmation: the approver sees the real amount and policy outcome before the irreversible call, which covers the manager-approval regions.
X: C=Temperature zero: deterministic sampling makes the same plan repeat, including a wrong one; it does not enforce reading the invoice first.
D=One merged tool: the refund still uses whatever amount the model supplies, and the manager approval for some regions is lost inside the single call.
E=Prompt rule and examples: they make the right order more likely but cannot guarantee it, which is not enough for refunds that cannot be undone.
T: Enforce tool order for irreversible actions in code and with a human confirmation, not only in the prompt.

@ DBX-GAI D1 T1.5 advanced troubleshooting
S: A retail agent has two tools, `search_orders(query)` and `search_returns(query)`, both described as "Searches customer records". MLflow traces show that for questions such as "Where is the refund for my returned jacket?" the agent calls `search_orders` in 40% of cases and then answers that no return exists. The team cannot merge the two data sources and wants the fix that changes the fewest components. What should the team change?
A: Rewrite both tool descriptions to state what each one returns, when to use it, and give an example question, so the model can tell the two tools apart
B: Rename both tools to `tool_1` and `tool_2` and list them in the system prompt in the order the model should try them for every customer question
C: Replace the chat model with a larger one, because a bigger model infers the right tool from the tool names alone without any change to the descriptions
D: Remove `search_orders` from the agent and answer all order questions from `search_returns`, which also holds the order IDs of returned items
K: A
G: ## How a model chooses between tools
In tool calling, the model sees each tool's name, description and parameter schema, and nothing else. When two tools have the same description, the choice is close to a guess. The description is therefore part of the prompt and should say:
- what the tool returns (orders with shipping status vs. return requests with refund status),
- when to use it and when not to,
- the expected argument format, ideally with a short example.
## Reading the evidence
The trace shows the wrong tool was called, not that the tool failed. That points to tool selection, which the descriptions drive, rather than to the data, the model size or the retrieval quality.
W: Distinct, specific descriptions: the model chooses tools from their descriptions, so stating what each returns and when to use it fixes the 40% mis-selection with no other change.
X: B=Generic names and fixed order: meaningless names remove information, and a fixed order makes every question hit the first tool regardless of intent.
C=Larger model: identical descriptions leave even a larger model guessing between the tools, and it costs more on every request.
D=Remove a tool: order questions about items that were never returned would no longer find their data, so the agent loses a capability.
T: Tool descriptions are prompts: make each one say what it returns and when to use it.

@ DBX-GAI D2 T2.1 advanced use-case
S: A telecom company indexes 2 million support chat transcripts so that agents can find how similar problems were solved before. A transcript averages 40 turns, and the fix is usually spread over several consecutive turns by the customer and the agent. The embedding model reads at most 512 tokens, and agents want each retrieved passage to show who said what. Which chunking strategy fits these documents and this model?
A: Split each transcript into windows of consecutive turns that stay under 512 tokens, overlap the windows by a few turns, and keep the speaker label on every turn
B: Embed every transcript as one chunk so that the model reads its first 512 tokens, and return the full transcript so agents can scroll down to the fix
C: Split each transcript into single turns and embed every turn on its own, so each customer or agent message is matched precisely against the query
D: Split each transcript into fixed 2,000-character pieces without overlap, strip the speaker labels to save tokens, and keep the transcript ID as metadata
K: A
G: ## Chunking follows the structure of the document
A chunk should be the smallest unit that still answers a question on its own, and it must fit the embedding model's input window; text beyond the window is truncated and never influences the vector.
For conversations, the natural unit is a **window of consecutive turns**:
- The fix spans several turns, so single turns lose the problem-solution link.
- A sliding window with a small overlap keeps a solution that crosses a window border in at least one chunk.
- Speaker labels (`Customer:`, `Agent:`) are short and carry meaning for both the embedding and the reader.
## Size check
512 tokens is roughly a few hundred words: about 8-15 short chat turns, so windows of that size fit the model.
W: Turn windows under 512 tokens with overlap and speakers: each chunk keeps the multi-turn fix together, fits the embedding window, and shows who said what.
X: B=Whole transcript: only the first 512 tokens are embedded, so fixes later in a 40-turn conversation are invisible to retrieval.
C=Single turns: a turn such as "that worked, thanks" or a lone instruction loses the problem it solves, so matches lack context.
D=Fixed characters without labels: cuts fall in the middle of turns and solutions, and dropping speaker labels removes what agents asked to see.
T: Chunk conversations as overlapping windows of whole turns that fit the embedding window and keep speaker labels.

@ DBX-GAI D2 T2.2 advanced troubleshooting
S: A legal team builds a RAG assistant over 300,000 exported e-mail threads. Every message repeats the full quoted history of earlier replies and ends with the same 120-word confidentiality disclaimer. Retrieval tests show that the top five chunks for most questions are near-identical copies of one quoted passage, and many chunks match the disclaimer rather than the question. The index must also shrink. Which preprocessing step addresses both problems?
A: Remove the quoted reply history and the standard disclaimer from each message before chunking, keeping each message's new text with sender and date metadata
B: Keep every message intact and raise the number of retrieved chunks from five to twenty, so that distinct passages also make it into the prompt
C: Add a reranker on top of vector search so that copies of the same quoted passage score lower than passages that contain new information
D: Make each whole thread one chunk, so that the quoted history and the disclaimer each appear only once per thread in the index
K: A
G: ## Boilerplate and duplication hurt retrieval
RAG quality depends on what is indexed. Content that repeats across documents (quoted replies, signatures, legal footers, navigation menus) causes two problems:
- **Duplicates crowd the top-k**: the same text appears in many chunks, so the top results are copies and the other relevant passages are pushed out.
- **Boilerplate attracts matches**: a disclaimer mentioning "confidential" or "legal" is similar to many questions and pulls irrelevant chunks up.
The fix belongs in data preparation: strip quoted history (each message keeps only its new text), remove fixed footers, and keep useful metadata (sender, date, thread ID) as columns for filtering and citation.
## Side effect
Removing repeated text shrinks the number of chunks and embeddings, which lowers index size and cost.
W: Strip quoted history and disclaimers: each passage then appears once, boilerplate no longer matches questions, and the index shrinks because repeated text is gone.
X: B=More chunks: duplicates still fill the results and the prompt grows, while the index stays the same size.
C=Reranker: it reorders candidates but identical copies receive identical scores, and the index still stores every duplicate.
D=Whole thread per chunk: long threads exceed the embedding window and are truncated, and each message's quoted history is still inside the thread text.
T: Remove repeated boilerplate and quoted text before chunking; downstream tricks cannot undo duplicated data.

@ DBX-GAI D2 T2.4 advanced troubleshooting
S: A nightly job parses new and changed PDFs, chunks them and appends the chunks to a Unity Catalog Delta table that feeds a Delta Sync index on a standard endpoint. After a job retry last week the index returned the same passage twice for many questions, and chunks of deleted PDFs still appear. Re-embedding all 5 million chunks every night is too costly, and each run must be safe to repeat. Which write design fixes this?
A: Give each chunk a deterministic ID from the document ID and chunk position, MERGE each run's chunks on that ID, and delete the rows of removed or re-chunked documents
B: Keep appending, but add a `run_id` column and filter every index query to the latest run ID so that older duplicate chunks are ignored at query time
C: Overwrite the whole table each night with chunks of every PDF, so that duplicates and deleted documents disappear because the table is rebuilt from scratch
D: Generate a random UUID for each chunk at write time and use it as the index primary key, so that every chunk row stays unique across retries and reruns
K: A
G: ## Idempotent chunk tables
A Delta Sync index mirrors its source table: every row becomes an index entry keyed by the primary key, and with change data feed enabled (required for standard endpoints) only changed rows are re-processed. So the table must hold exactly one row per current chunk.
- **Deterministic keys**: an ID built from the document ID and the chunk position (or a hash of them) is the same on every run, so a retry produces the same keys.
- **MERGE**: inserting or updating on that key makes a rerun harmless instead of adding copies.
- **Deletes**: removing rows for deleted or re-chunked documents lets the sync remove them from the index.
## Cost
Only changed rows flow through change data feed, so unchanged chunks are not re-embedded.
W: Deterministic ID with MERGE and deletes: reruns update the same rows instead of duplicating them, deleted documents leave the index, and only changed rows are re-embedded.
X: B=Run ID filter: the latest run holds only new and changed PDFs, so filtering to it hides every unchanged document from retrieval.
C=Nightly overwrite: rewriting every row changes all of them, so the whole corpus is re-embedded each night, which the stem rules out as too costly.
D=Random UUID: a retry gives the same chunk a new random key, which is exactly how the duplicates arose; uniqueness of keys is not uniqueness of content.
T: Make chunk writes idempotent with deterministic keys, MERGE and explicit deletes so the synced index mirrors the current corpus.

@ DBX-GAI D2 T2.6 advanced comparison
S: A team compares two retrievers for a RAG assistant on 200 questions, each labeled with the IDs of every relevant chunk. The prompt has room for only three chunks, so an answer can use only what lands in the top three. The team wants one metric that shows how often the needed evidence reaches the prompt and one that rewards placing the first relevant chunk higher in the ranking. Which TWO metrics should they compare? (Select TWO)
A: Recall at 3, the share of each question's labeled relevant chunks found in the top three results, averaged over all 200 questions
B: Mean reciprocal rank, the average over all questions of one divided by the rank position of the first relevant chunk returned
C: Recall at 50, the share of labeled relevant chunks found anywhere in the first fifty results, averaged over all 200 questions
D: Average cosine similarity between each question embedding and its top three chunk embeddings, which needs no relevance labels
E: Index build time and the number of chunks per document, which show how costly each retriever's chunking is to maintain
K: A,B
G: ## Retrieval metrics and the context budget
With labeled relevant chunks (ground truth for retrieval), the standard metrics are:
- **Recall@k**: share of relevant chunks found in the top k. The k that matters is the number of chunks that actually reach the prompt.
- **Precision@k**: share of the top k that is relevant.
- **MRR (mean reciprocal rank)**: average of `1/rank` of the first relevant chunk; 1.0 means it is always first, 0.33 means third on average.
## Matching metric to design
Recall@50 counts evidence the model never sees when only three chunks fit. Similarity scores measure closeness in vector space, not relevance. Build cost is an operations metric, not retrieval quality.
W: A=Recall at 3: it counts the evidence that actually reaches the three-chunk prompt.
B=Mean reciprocal rank: it rewards retrievers that put the first relevant chunk at the top, which the team asked for.
X: C=Recall at 50: it credits chunks in positions 4 to 50 that never reach the prompt, so it overstates what the model can use.
D=Average cosine similarity: a high similarity is not relevance, and it ignores the labels the team already has.
E=Build time and chunk counts: these describe maintenance cost, not whether the right evidence is retrieved.
T: Measure recall at the k that fits the prompt and use MRR for ranking quality.

@ DBX-GAI D2 T2.7 advanced use-case
S: Annual reports in a RAG corpus contain wide financial tables of about 2,000 tokens each. When a recursive text splitter cuts the tables, questions such as "What was operating margin in 2024?" retrieve fragments without the column headers, and answers mix up years. The embedding model reads 512 tokens and the generator accepts 8,000 tokens of context. Which design improves retrieval and answers for table facts?
A: Index a short generated description of each table, with its title and row and column headers, for search, and pass the whole table to the generator as one block
B: Raise the chunk size to 2,000 tokens so each table stays in one chunk, and embed every full table chunk with the 512-token embedding model already in use
C: Drop all tables from the corpus during parsing so that only narrative text is indexed, since the generator can explain the margins from the report text
D: Keep the recursive splitter but double the chunk overlap, so that each table fragment repeats more of the rows from the previous fragment of the same table
K: A
G: ## Multi-representation indexing (parent-child for tables)
Some content is too large or too structured to embed well as one piece. A common advanced pattern separates **what is searched** from **what is returned**:
- A short representation (a summary, or the title plus header rows) is embedded and searched. It fits the embedding window and contains the words users ask about.
- Each short representation keeps the ID of its parent, the full table, which is fetched and passed to the generator.
## Why fragments fail
A table fragment without its header row has numbers without meaning ("12.4  9.8  11.1"); the model cannot tell which year or metric a value belongs to. Overlap repeats rows, not headers.
## Budget check
A 2,000-token table fits easily in an 8,000-token generation context.
W: Searchable table description, full table returned: the description fits the 512-token embedding window and matches the question's terms, and the generator receives the complete table with headers, so years are not mixed up.
X: B=2,000-token chunks: the embedding model reads only the first 512 tokens, so most of each table never influences retrieval.
C=Drop tables: the facts users ask about live in the tables, so removing them removes the answers.
D=More overlap: fragments still lack the header row, so values remain unlabeled and the index grows.
T: Search a compact representation and return the full parent when a unit is too large or structured to embed well.

@ DBX-GAI D3 T3.1 advanced use-case
S: A procurement agent drafts purchase orders. It gathers supplier quotes with tools, may loop back to request a missing quote, and must pause for a manager's approval before it submits an order. Approvals can take two days, the run must resume from the same step after the approval or after a server restart, and the team wants every step traced in MLflow. Which framework choice fits these needs?
A: A LangGraph graph with one node per step, a conditional edge for the loop, and a checkpointer that persists the state between the approval interrupt and the resume
B: A LangChain expression language chain that pipes the quote step, the drafting step and the submit step in a fixed linear order, invoked once per order
C: A SQL statement with `ai_query` that reads quotes from a table, drafts each order in one call, and writes the drafts to a table for managers to review
D: A single chat-model prompt that lists all steps, asks the model to remember where it stopped, and is called again once the manager replies
K: A
G: ## Chains vs. graphs
- A **chain** (LangChain expression language, `prompt | model | parser`) runs a fixed sequence once. It has no loops, no branching on results and no durable pause.
- A **graph** framework such as LangGraph models steps as nodes and transitions as edges, including **conditional edges** (loop back when a quote is missing). A **checkpointer** saves the graph state after each step, so a run can stop at an **interrupt** (human approval) and resume later, even after a restart, from the saved state.
## Observability
MLflow tracing supports LangGraph through LangChain autologging (`mlflow.langchain.autolog()`), which records a span for each step.
## Choosing
Use the simplest tool that meets the control-flow needs: fixed steps, a chain; loops, branches and pauses, a graph with persisted state.
W: LangGraph with a checkpointer: nodes and a conditional edge express the loop, the interrupt pauses for approval, and the persisted state lets the run resume after two days or a restart, with steps traced by MLflow autologging.
X: B=Linear LCEL chain: a fixed pipe cannot loop back for a missing quote and has no durable pause for a two-day approval.
C=SQL with ai_query: a batch statement drafts text but cannot call quote tools, loop, or wait for an approval before submitting.
D=One prompt that remembers: a model keeps no state between calls, so after two days or a restart there is nothing to resume from.
T: Use a graph framework with persisted state when an agent needs loops, human approval pauses and resume after restarts.

@ DBX-GAI D3 T3.2 advanced troubleshooting
S: Reviewers read 100 answers of an HR assistant. In 14 answers the stated parental leave is 12 weeks, although the 2025 policy grants 16 weeks. The MLflow traces show that each of these answers matches its retrieved passage word for word, and that the passage comes from a 2023 policy PDF still present in the index. Groundedness scores are high for all 14 answers. Which conclusion and fix follow from this evidence?
A: The source data is at fault because superseded policy versions are indexed, so remove them or filter by status and effective date rather than changing the prompt

S: A product-description generator uses a prompt with two worked examples, both about stainless-steel kettles. The format of the examples (a title, three bullets, one call to action) is exactly what marketing wants, and every fact must come from the input specification. Which prompt revision keeps the format and stops this leakage?
A: Use examples from varied product categories, mark them clearly as format examples between delimiters, and state that facts must come only from the input specification
B: Remove both examples and describe the format in one sentence, accepting that titles, bullet counts and call-to-action wording will vary between outputs
C: Add three more kettle examples so the model sees more variation in wording, and move all the examples after the input specification in the prompt
D: Keep the two kettle examples and raise the sampling temperature so that the model copies less wording from them and writes more varied descriptions
K: A
G: ## Few-shot examples teach content as well as form
Examples in a prompt (few-shot prompting) are the strongest signal about the desired output. Models imitate everything in them: structure, tone and also **content**. If all examples share a topic, facts from that topic leak into unrelated outputs.
Good practice:
- Vary the examples across categories, so the only constant is the format.
- Separate examples from the real input with clear delimiters and labels ("Example output format").
- State the grounding rule explicitly: facts come only from the input specification.
## Why randomness is not a fix
A higher temperature changes word choice randomly; it does not stop copying and adds a risk of invented details.
W: Varied, delimited examples with a grounding rule: the format stays the only shared pattern, the model sees examples as format guides, and the rule ties facts to the specification.
X: B=No examples: leakage stops, but the consistent format that marketing wants is lost.
C=More kettle examples: five examples on one product type strengthen the kettle content the model copies.
D=Higher temperature: randomness does not remove the copying signal and makes invented features more likely.
T: Vary few-shot examples so only the intended pattern repeats, and state where facts must come from.

G: ## Guardrails for "no answer in the documents"
An ungrounded answer usually starts when retrieval returns nothing useful and the model fills the gap from its general training. Two cheap guardrails work together:
- **Retrieval gate (code)**: if no retrieved chunk scores above a threshold, skip the model call and return a fixed message. The threshold is tuned on labeled questions, so it separates relevant from irrelevant results for this index.
- **Grounding instruction (prompt)**: tell the model to use only the context and give the exact fallback text to use when the answer is missing. This catches cases where some chunk passes the gate but does not contain the answer.
## Heavier options
LLM-as-judge checks after generation also work, but they add a model call per request, which the city excluded.
W: A=Relevance gate: when nothing relevant is retrieved, no generation happens, so general-knowledge answers about fees cannot appear, at no extra model cost.
B=Grounding instruction with fallback text: the model is told to rely only on the context and to give the fixed message when the context does not answer.
X: C=Second judge call: it adds one model call per request, which the city ruled out.
D=Thirty chunks: more weakly related text makes it easier for the model to build an answer that is not supported, and raises cost.
E=Fine-tuning: training does not make answers grounded in current documents and still leaves general knowledge to fill gaps.
T: Combine a retrieval score gate with a grounding instruction to return a fixed fallback instead of an invented answer.
