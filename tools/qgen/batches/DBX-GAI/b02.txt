@ DBX-GAI D1 T1.6 applied use-case
S: A team has an agent written with its own Python framework. Long research runs sometimes die when the host restarts, and the team wants managed hosting without rewriting the agent. Which Agent Bricks capability fits?
A: Databricks Sandbox, which gives code written by the agent an isolated place to run
B: A Genie Agent, which would replace the custom framework with a data environment configured by the data team
C: Agent Runtime with AgentKit, which hosts any framework and adds durable execution that survives restarts
D: MLflow Tracing, which records every step of a run and automatically replays the failed step after the host comes back
K: C
G: ## What Agent Bricks is today
Agent Bricks is the Databricks agent developer platform. The exam guide still uses the older meaning of the name (a set of low-code builders: Knowledge Assistant, Multi-Agent Supervisor and Information Extraction), but the current docs describe a code-first platform and mark those builders Legacy. The platform covers the workflow of a production agent:
- **Deploy**: Agent Runtime hosts agents built with any framework or harness, stateful or stateless. AgentKit adds durable execution, so a run survives restarts and crashes.
- **Run code safely**: Databricks Sandbox is an isolated environment for code that the agent writes.
- **Enrich context**: agent memory and sessions, MCP servers and tools, AI Search.
- **Debug and test**: MLflow Tracing records each step.
The Agent Bricks CLI scaffolds the agent code and connects it to these services.
## Matching the problem to the piece
A run that dies when its host restarts is a hosting and durability problem, so the answer is the runtime layer, not a tracing or sandbox feature.
W: Agent Runtime with AgentKit: it hosts agents regardless of framework and adds durable execution, which is exactly the "survive restarts and crashes" need.
X: A=Databricks Sandbox: it isolates code the agent generates for safe execution; it does not host the agent or keep a run alive across a restart.
B=Genie Agent: a Genie Agent is a configured environment of trusted data and business rules, not a host for an existing custom framework, so adopting it would mean rewriting the agent.
D=MLflow Tracing: tracing records what happened for debugging, but it does not replay failed steps or restore a run after the host restarts.
T: Hosting and durable execution of an agent built with any framework belong to Agent Runtime with AgentKit in Agent Bricks.

G: ## Low-code or code-first
The guide asks when to use the three Agent Bricks builders. The docs now give a simpler rule, and they mark Knowledge Assistant, Supervisor Agent (the guide's Multi-Agent Supervisor) and Information Extraction as Legacy:
- For a **new low-code agent** over documents and data, use **Genie Agents**. These are domain-specific environments where data teams configure trusted data, metrics and business rules, so answers are grounded in governed (Unity Catalog) data.
- For an **agent written in code**, use the **Agent Bricks CLI**.

Genie Agents were called Genie spaces in earlier docs and in the guide.

T: New low-code agents over governed data use Genie Agents, new code agents use the Agent Bricks CLI, and batch row work uses AI Functions.

@ DBX-GAI D2 T2.1 applied troubleshooting
S: A contract-search RAG index was built by cutting every document into 800-character pieces with a fixed-size splitter. Retrieved chunks often start in the middle of a sentence and end in the middle of the next clause, and answers cite half a clause. What is the best change to the chunking step?
A: Raise the chunk size to the whole document so that no clause is ever cut
B: Switch to a recursive splitter that prefers paragraph and sentence boundaries before it cuts by length
C: Keep the 800-character pieces but remove every period so that sentences cannot be split
D: Lower the embedding dimension so that each cut piece carries less ambiguity about its meaning in the index
K: B
G: ## Chunking in the Databricks pipeline
Chunking turns parsed documents into pieces that fit the LLM context and keep distracting text out. The Databricks unstructured-data pipeline article lists these strategies:
- **Fixed-size**: cut at a number of characters or tokens. Fast to set up but not semantically coherent, and the article says it rarely works for production-grade applications.
- **Paragraph-based**: use paragraph boundaries (LangChain `RecursiveCharacterTextSplitter` is the named example).
- **Format-specific**: use structure such as Markdown headers or HTML sections.
- **Semantic**: split where the topic changes.
The aim is chunks that contain related information and can stand alone as a unit of text.
## This scenario
Cuts in the middle of a clause are the classic symptom of blind fixed-size splitting. A splitter that tries paragraph and sentence boundaries first keeps clauses whole while still bounding the length.
W: Recursive splitting on natural boundaries: it cuts at paragraph and sentence breaks first, so clauses stay intact and chunk length stays bounded.
X: A=Whole document as one chunk: the chunk would no longer fit many embedding models or the LLM context and would bury the relevant clause in unrelated text.
C=Removing periods: this destroys the sentence signal the splitter and embedding model rely on, and the cuts would still be placed by length.
D=Lower embedding dimension: it changes the vector size, not where the text is cut, so half clauses would remain half clauses.
T: Prefer chunk boundaries that follow paragraphs, sentences or document structure over blind fixed-size cuts.

@ DBX-GAI D2 T2.1 applied use-case
S: A user question needs an exception that is stated in the first sentence of the next chunk. Retrieval returns the earlier chunk, so the answer omits the exception. The team keeps the chunk size but wants to lower the chance that facts at a boundary are separated. Which change fits?
A: Cut each chunk to a single sentence so that any exception becomes its own chunk
B: Remove the overlap and rely on a deduplication job to repair the cuts afterwards
C: Raise the embedding dimension so that the two chunks become more similar to each other
D: Add a modest overlap between adjacent chunks so that text near each boundary appears in both
K: D
G: ## Why overlap exists
When a splitter cuts text, sentences next to the cut sit in different chunks. The pipeline article lists overlap as one of the main factors: including some overlap between adjacent chunks helps ensure that important information is not lost at splits, preserves continuity and context, and can improve retrieval results.
## The trade-off
Overlap duplicates text. A modest overlap (for example about 10-20% of the chunk) increases index size slightly. Very large overlaps create near-identical neighbours that can fill the top results with the same passage.
W: Modest overlap: text near each boundary appears in two neighbouring chunks, so a fact and its exception are more likely to arrive together.
X: A=Single-sentence chunks: they separate related sentences even more and strip the context each piece needs to be understood.
B=Remove overlap: overlap is what protects boundary facts; deduplication cannot recreate a context that the cut already separated.
C=Higher embedding dimension: it changes the vector size, not the text, so the exception still sits in a different chunk.
T: Overlap carries boundary text into both neighbours; keep it modest to avoid redundant chunks.

@ DBX-GAI D2 T2.2 applied troubleshooting
S: A knowledge base was copied into several shared drives. For many questions the top five chunks are the same paragraph repeated from different copies, so the model receives one fact five times and misses the others. Which preprocessing step addresses the cause?
A: Deduplicate documents before chunking, with metadata for exact copies and MinHash joins for near duplicates
B: Reduce the chunk size so that fewer words repeat inside each one of the retrieved chunks in the top results
C: Switch to a larger embedding model so that identical text receives more varied vectors across the different copies
D: Raise the temperature of the chat model so that the repeated retrieved text produces more varied answers
K: A
G: ## Duplicates waste the context window
If duplicates or near duplicates stay in the corpus, the index contains highly redundant chunks that decrease the application's performance. The Databricks pipeline article describes two steps:
- **Metadata**: same title and creation date from different locations can be filtered with metadata alone.
- **Content similarity**: locality-sensitive hashing with **MinHash** (available in Spark ML). Build a feature vector per document, fit a MinHash model for Jaccard distance, run a similarity join on the hashes, and filter out the duplicates you do not want to keep (for example keep the most recent or most authoritative version).
## Why other fixes fail
Smaller chunks do not remove copies, and a better model gives identical text identical vectors. The fix is upstream, in the corpus.
W: Deduplicate before chunking: metadata handles exact copies and MinHash similarity joins find near duplicates, so each fact appears once.
X: B=Smaller chunks: copies of the document still produce copies of each smaller chunk, so the top results stay redundant.
C=Larger embedding model: identical text still gets the same vector, so all copies tie for the top positions.
D=Higher temperature: it changes sampling randomness at generation time, not the redundant retrieved context.
T: Remove exact and near-duplicate documents (metadata, MinHash) before chunking so retrieval returns varied facts.
V: Spark ML, AI Search

G: ## Incremental writes
A Delta Sync index applies the changes it finds through the change data feed: inserts, updates and deletes. Overwriting a whole table makes every row look changed, which defeats incremental sync. The Databricks article recommends ingesting scalably and incrementally.
## A safe pattern
1. Detect new or modified documents (for example by file modification time or content hash).
2. Parse and chunk only those documents.
3. `MERGE` into the chunk table: delete or replace the existing chunks of each changed document (identify them by a document id column) and insert the new chunks.

G: ## Two retrieval metrics
Retrieval can be scored without an LLM when the evaluation set records which documents are relevant to each question:
- **Precision@k** = relevant chunks in the top k divided by k. It measures how clean the retrieved set is.
- **Recall@k** = relevant chunks in the top k divided by all relevant chunks. It measures how much of the needed evidence was found.
These are generally accepted information-retrieval definitions. They need ground-truth relevance labels, such as the identifiers of the documents (`doc_uri`) that answer each question.
## This scenario
Precision@5 = 2 / 5 = 0.4. Recall@5 = 2 / 4 = 0.5.

B=0.8 and 0.4: 0.8 is four of five, which would need four relevant retrieved chunks; only two were relevant.
D=0.4 and 0.8: recall of 0.8 would need four of five relevant chunks to exist, but only four are relevant overall and two were found.
T: Precision@k = relevant in top k / k; recall@k = relevant in top k / all relevant.

G: ## Rank-aware retrieval metrics
Some metrics ignore position inside the cut-off:
- **Hit rate@k / recall@k** give credit if a relevant chunk appears anywhere in the top k.
- **MRR** (mean reciprocal rank) averages 1/rank of the first relevant result: rank 1 scores 1, rank 9 scores about 0.11.
- **NDCG** weights gains by position for graded relevance.
When only the first few chunks reach the LLM, position matters, so a rank-aware metric is needed. These are generally accepted definitions. A re-ranking model or a different retriever is the usual remedy for a low rank.

D=Hit rate@10: it is also position-insensitive within the top ten, so both retrievers get the same score.
