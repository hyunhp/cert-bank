@ DBX-GAI D1 T1.1 applied use-case
S: A prompt asks a chat model for the total cost of a shipment after weight tiers, a fuel surcharge and a discount. Asked for the number directly, the model often returns a wrong total, although each single rule is applied correctly when asked alone. Which prompt change most directly helps?
A: Tell the model that its answer is very important and that it must not make any mistakes in the total
B: Ask for the total in a single line of at most five words so that the answer cannot drift
C: Ask the model to work through each rule step by step and then give the final total on a last line
D: Move the pricing rules to the end of the prompt, since the last instruction is always the one followed
K: C
G: ## Prompting for multi-step problems
A model writes the answer token by token, so a total that depends on several rules is unreliable when the first token has to be the result. Asking for intermediate reasoning (chain-of-thought) lets each step be written out and used by the steps after it. Pair this with a fixed marker for the final line (for example `Total:`), so application code can read the result and ignore the working.
- Generic urgency ("be careful", "this is critical") does not add computation.
- Forcing a very short answer removes the room for intermediate steps.
- Instruction position matters less than clear structure. Delimiters and labelled sections help more than moving text around.
If the output must also be machine readable, combine the reasoning with a structured `response_format` that has a `reasoning` field before the `answer` field.
W: Step-by-step working lets the model apply each rule in turn and carry the intermediate values forward, and a marked last line keeps the total easy to extract.
X: A=Stress the importance: urgency wording adds no reasoning steps, so the model still has to produce the total in one jump.
B=Force a five-word answer: a short reply leaves no room for intermediate values, which makes multi-rule arithmetic worse.
D=Move the rules to the end: models do not simply obey the last instruction, and the missing part is the stepwise working, not rule placement.
T: For multi-step reasoning, prompt for step-by-step working and a clearly marked final answer.

@ DBX-GAI D1 T1.1 applied troubleshooting
S: A developer sends a `json_schema` `response_format` to a Foundation Model APIs chat endpoint. In the schema the `currency` property has a regex `pattern` and `price` uses `anyOf` to accept either a string or a number. The request is rejected or the constraints are not applied, and the team still needs schema-conforming JSON. What should the developer do?
A: Keep the schema and switch `type` to `json_object`, which applies the schema's regular expression during decoding
B: Move the `anyOf` branches into a `$ref` definition, since references express alternatives
C: Declare `price` as `"type": ["string", "number"]`, since a list of types replaces `anyOf` in this subset
D: Use plain `string` and `number` properties, list the allowed currency codes in the field description, and validate in code
K: D
G: ## Structured outputs accept a subset of JSON schema
Foundation Model APIs support the structured outputs accepted by OpenAI, but only a subset of JSON schema: a simpler schema gives higher quality generation. The documented unsupported keys are:
- Regular expressions with `pattern`.
- Composition and complex nesting with `anyOf`, `oneOf`, `allOf`, `prefixItems` or `$ref`.
- Lists of types, except the special case `[type, "null"]` for an optional value.
## Design consequence
Keep the schema flat and typed. Where you need a rule the subset cannot express (a regex check, a union), describe it in the field `description` and validate the parsed object in application code. A nullable field is still allowed through `["number", "null"]`.
W: Using a flat schema with `string` and `number` properties stays inside the supported subset; the currency rule moves to the field description and an application-side check.
X: A=Switch to `json_object`: that format only guarantees valid JSON, it does not apply any schema and does not apply a regex at all.
B=Use `$ref`: `$ref` is listed among the unsupported keys, so moving the alternatives there does not help.
C=List of types: lists of types are unsupported except the pair of one type and `"null"`, so a string-or-number list is not accepted.
T: Structured outputs take a simple JSON schema: no `pattern`, no `anyOf`/`oneOf`/`allOf`/`$ref`, and only `[type, "null"]` type lists.

@ DBX-GAI D1 T1.1 applied use-case
S: A prompt asks a chat model to label support tickets as `billing`, `outage` or `other`. Replies vary between "Billing", "This looks like a billing issue" and "billing." Which TWO changes most directly make the output a single, stable label? (Select TWO)
A: Include two or three example tickets in the prompt, each followed by exactly the label text the application expects
B: Raise the temperature to 2 so the model explores more phrasings and settles on one
C: Set the temperature to 0 so that sampling is deterministic and the same ticket gets the same reply each time
D: Increase `max_tokens` so that the model has enough room to finish its explanation before the label
E: Add "be creative with the label wording" to the system message to prompt a consistent style
K: A,C
G: ## Two levers for consistent output
Output format has two sources of variance: what the prompt shows the model, and how the model samples.
- **Few-shot examples**: input/output pairs inside the prompt demonstrate the exact format. Models imitate the pattern, which is much stronger than a description of it. Pair the examples with a closed list of allowed labels.
- **Sampling parameters**: `temperature` ranges from 0 to 2 in the Foundation Model API. 0 is deterministic and higher values add randomness.
Neither lever guarantees a format the way `response_format` does; when a schema fits the case, use that, and keep these levers for free-text labels.
W: A=Few-shot examples: showing the exact label text in context teaches the model the output pattern to copy.
C=Temperature 0: removing sampling randomness makes repeated runs of the same ticket give the same wording.
X: B=Temperature 2: higher temperature increases randomness, so labels get less consistent.
D=More `max_tokens`: this only raises the ceiling on length and invites the longer explanations the application does not want.
E=Ask for creativity: this encourages varied wording, the opposite of a stable label.
T: Stable labels come from few-shot examples that show the format plus a low temperature, not from more tokens or more creativity.

@ DBX-GAI D1 T1.1 applied comparison
S: A support assistant must always answer in Korean, in at most three bullet points, and never speculate beyond the supplied context. Each turn carries a new user question and new retrieved passages. Where should these standing rules live in the chat request?
A: In the system message, with only the question and passages sent in each user message
B: In the first user message only, relying on later turns to remember them without repeating
C: In an assistant message placed before the first user turn so the model treats them as its own earlier output
D: In a one-time setup request per session, because the endpoint stores them for later calls
K: A
G: ## Roles in a chat request
A chat request is a list of messages with roles.
- `system`: durable instructions about role, tone, language, format and limits. It frames every reply.
- `user`: the turn-specific input: the question, and often the retrieved context.
- `assistant`: earlier model replies, used to carry the conversation or to show examples.
Chat endpoints are stateless. Each call must contain everything the model should see, so standing rules are repeated in the system message of every call, while the changing content goes in the user message.
W: Putting the standing rules in the system message keeps role, language and format constraints separate from the question and passages, and they apply to every call.
X: B=Rules in the first user message: later requests do not include that first turn unless the application sends it again, and a user message mixes instructions with data.
C=Rules as a prior assistant message: the assistant role holds the model's own earlier replies, and it is a weaker place for instructions than the system message.
D=One-time setup request: serving endpoints do not keep state between calls, so nothing stored is available to later requests.
T: Standing instructions go in the system message of every call; per-turn data goes in the user message.

@ DBX-GAI D1 T1.1 advanced use-case
S: A tool lets analysts paste any text and name whichever fields they want extracted (for example "supplier, due date" one day and "diagnosis, dosage" the next). The field list is not known at development time, but the reply must always be valid JSON. Which `response_format` fits?
A: A `json_schema` that lists every field name any analyst might ask for, all marked optional
B: Plain text, then a regular expression in application code that pulls the key-value pairs
C: `{"type": "json_object"}` with the requested field names given in the prompt
D: A `json_schema` using `anyOf` so that each analyst's field list becomes its own branch
K: C
G: ## json_object versus json_schema
`json_schema` is the right choice when the shape is fixed and known in advance, because the endpoint enforces property names and types. When the schema is not known beforehand, Databricks documents the `json_object` format: the model returns a valid JSON object, and you tell it in the prompt which fields to include.
The trade-off: `json_object` guarantees syntax, not the keys. Check that the requested keys are present before using the result.
W: `json_object` guarantees valid JSON without a fixed schema, and the prompt supplies the per-request field names.
X: A=One giant optional schema: it cannot cover names that nobody has asked for yet, and every optional field invites noise from the model.
B=Plain text plus regex: nothing makes the reply valid JSON, so the fragile parsing the format option removes comes back.
D=`anyOf` branches: `anyOf` is not supported in the schema subset, and branches would still need the field lists in advance.
T: Unknown fields at design time mean `json_object` plus a prompt; known shape means `json_schema`.

@ DBX-GAI D1 T1.1 applied troubleshooting
S: A team uses a `json_schema` response format with five fields and `max_tokens=64`. Short documents give correct objects, but for long documents the JSON stops in the middle of a string and fails to parse. What is the fix?
A: Raise the temperature so the model produces a more compact object for long documents
B: Raise `max_tokens` above the length of the largest expected object
C: Remove `response_format` so the model is free to shorten its output
D: Add a stop sequence at the closing brace so the model ends the object itself
K: B
G: ## max_tokens is a hard ceiling
`max_tokens` is an upper bound on the number of tokens the model can generate, and on reasoning models it includes reasoning tokens as well as visible output. When the answer needs more tokens than allowed, generation is cut off at the limit even in the middle of a JSON string, which gives invalid JSON.
Size the limit from the longest expected structure and leave headroom. Constrained formats do not shorten the content; they only fix its shape.
W: The output is cut at the 64-token ceiling, so the limit must be higher than the largest object that can be produced.
X: A=Higher temperature: temperature changes randomness, not length, and it does not make the model aware of a limit.
C=Remove the format: the answer is still capped by `max_tokens`, and losing the schema brings back free text.
D=Stop sequence at a brace: a stop sequence ends generation early at a match, it does not extend a reply that was truncated by the limit and nested objects contain many braces.
T: JSON that breaks mid-string on long inputs points to a `max_tokens` ceiling that is too low.

@ DBX-GAI D1 T1.2 applied use-case
S: A helpdesk wants to show agents the five past tickets that are closest in meaning to a new ticket, even when no keywords match. Which model task should the application use?
A: A chat model that is asked to recall similar tickets from its training data and list their numbers

Models on Databricks serve different tasks. The choice follows from what the application must produce.

T: Similarity by meaning is an embedding task; generation, classification and extraction are different tasks.

S: Analysts must assign each of three million rows in a Unity Catalog table to one of six topic labels using SQL. They have no prompt-engineering experience and want the least setup. Which option fits best?

S: Which TWO requirements are best served by an embedding model rather than by a chat model? (Select TWO)

An embedding model maps a piece of text to a fixed-length vector. It does not write text. Similar meaning gives nearby vectors, so you can compare texts numerically. Typical uses:

- Clustering and topic grouping.
- Deduplication and recommendation by similarity.
Anything that must generate new text (replies, summaries, translations) is a generation task for a chat or completion model.

C=Summarizing a transcript: summarization generates new condensed text.
D=Translation: output text in another language is generation (or a task-specific function such as `ai_translate`).
T: Embedding models compare and group texts by meaning; chat models produce text.

@ DBX-GAI D1 T1.2 advanced tradeoff
S: Employees ask questions about internal HR policies that change every week. Answers must reflect the latest version and name the policy they came from. Which design meets this need?
A: Fine-tune a chat model on the policy documents each month and let the model answer from what it learned
B: Retrieve the matching policy passages for each question and pass them to a chat model as context
C: Classify every question into one policy ID and return the stored policy text without a language model
D: Use only an embedding model, returning the vector of the closest policy as the answer
K: B
G: ## Retrieval plus generation
This need combines two tasks. Retrieval finds the relevant passages by embedding similarity. Generation writes the answer from those passages. This is retrieval-augmented generation (RAG).
Why not tuning? Fine-tuned weights are a snapshot: when policies change weekly, the model is stale until the next training run, it does not reliably name sources, and facts learned in weights are hard to correct. RAG reads the current documents at question time, so updating the index updates the answers, and the retrieved passages give the source for citations.
W: Retrieval brings in the current policy text and its source at question time, and the chat model writes a grounded answer from it.
X: A=Monthly fine-tuning: the model is out of date for up to a month and cannot point to the exact policy.
C=Classify to a policy ID: it returns whole policies instead of an answer to the question, and misses questions that span several policies.
D=Embedding-only: an embedding is a vector, not an answer; a generation step is needed to write the reply.
T: Fast-changing private knowledge with citations is a RAG job: retrieve current passages, then generate.

@ DBX-GAI D1 T1.3 applied use-case
S: A team builds a RAG chain whose input is the user's question as a string and whose output is the answer as a string. Which component order produces this?
A: Retriever, then a prompt template merging passages and question, then the chat model, then a parser
B: Chat model first, then the retriever on its answer, then a prompt template that formats the text
C: Prompt template, embedding model for the whole prompt, then chat model that returns the passages
D: Retriever, then an output parser on the raw passages, then the chat model without a prompt template
K: A
G: ## Chain components and their input/output types
A chain is a sequence of components whose output type matches the next component's input type.
- **Retriever**: takes a query string, returns documents (chunks plus metadata).
- **Prompt template**: takes a dict of variables (for example `context`, `question`) and returns a prompt or messages.
- **Chat model**: takes messages, returns a message object.
- **Output parser**: takes the message and returns the shape the application needs, such as a string.
A RAG chain is therefore retriever, prompt template, chat model, parser. In LangChain this is written with the pipe operator: `retriever | format_docs | prompt | llm | StrOutputParser()`. On Databricks the retriever is typically an AI Search index (the exam guide still calls it Vector Search) and the chat model is a Foundation Model APIs endpoint reached through `ChatDatabricks`.
W: The retriever supplies the context first, the template builds the prompt from it, the model answers, and the parser returns a plain string.
X: B=Model before retriever: the model would answer without context, and retrieving by its answer defeats grounding.
C=Embedding the whole prompt: embedding models return vectors, not passages, and cannot generate an answer.
D=Parser before model with no template: the model would receive raw documents with no instruction or question.
T: Order the components so each output feeds the next input: retrieve, template, generate, parse.

prompt = ChatPromptTemplate.from_template(
    "Context: {context}\nQuestion: {question}")
chain = prompt | llm | StrOutputParser()
chain.invoke({"input": "What is the refund window?"})

What is the correct fix?

@ DBX-GAI D1 T1.5 applied troubleshooting
S: A developer passes a `tools` list to a Foundation Model APIs chat endpoint. The reply contains a tool call with JSON arguments for `get_weather`, but the weather lookup never happens and the user sees no answer. What explains this?
A: The caller lacks `EXECUTE` privilege on the endpoint, so the tool call is dropped

C: Pay-per-token endpoints run functions on the server side only when streaming is switched on for the request

K: D
G: ## Function calling is a loop that your code drives
With function calling the model never runs your code. The sequence is:
1. Send the question with the function definitions in `tools`.
2. The model decides whether to call a function. If so, it returns a JSON object with the function name and arguments that follow your schema.
3. Your code parses the arguments and calls the real function or API.
4. Your code calls the model again with the result appended as a new message, and the model writes the final answer.
An agent framework (for example LangGraph with Unity Catalog function tools) wraps this loop for you, but the principle stays: execution is outside the model.
W: The model only proposes the call; the application must execute it and append the result as a message for the final answer.
X: A=Privilege on the endpoint: a permission error would raise an error, not return a valid tool call.
B=Registration in Unity Catalog: a plain `tools` list with a JSON schema works without registering anything; Unity Catalog functions are one option.
C=Streaming switch: streaming changes how tokens arrive, not who executes the function.
T: Function calling returns a call request; your code executes it and feeds the result back.

The `tool_choice` parameter has four documented settings.
