@ DBX-GAI D3 T3.5 applied use-case
S: A support assistant built on a foundation model answers correctly, but its replies are long, formal and full of marketing phrases. The brand team wants short, friendly replies of two sentences that sound like a set of approved sample replies. Which change to the prompt moves the output from this baseline to the desired style most reliably?
A: Add a sentence that says "be friendly and brief" to the instructions and raise the temperature so the model sounds less formal and more varied
B: Add three to five approved question-and-reply pairs before the new question and state the two-sentence limit
C: Paste the whole brand style guide into the prompt and ask the model to follow every rule in it, without showing any sample replies
D: Ask the model to write the long formal reply first and then to shorten it later in the same answer, keeping both versions visible
K: B
G: ## Moving a baseline response toward the output you want
A baseline response is whatever the model produces for your first, simple prompt. Prompt engineering is the loop of reading what is wrong with that baseline and changing the prompt to close the gap. The main levers are the instruction (what to do and what limits apply), the role or system message (who the model is), examples (what good looks like) and the context (what facts it may use).
## Few-shot examples
When the gap is about style, tone or layout, showing is stronger than telling. A few-shot prompt places a handful of input/output pairs before the real input, and the model imitates their length, voice and structure. Keep the examples consistent with each other, because the model copies inconsistencies too. A short explicit rule (here: two sentences) next to the examples removes ambiguity that examples alone leave open.
## Settings are not a substitute
Temperature only changes how random the sampling is. It does not tell the model what style to use.
W: Approved question-and-reply pairs demonstrate the exact tone and length, and the explicit two-sentence limit states the constraint in words. Together they address both the voice and the length gap seen in the baseline.
X: A=Vague adjectives plus higher temperature: "friendly and brief" is open to interpretation and a higher temperature adds randomness without moving the style, so replies become less predictable rather than more on-brand.
C=Whole style guide pasted in: a long rule document dilutes the instruction, uses context for text the model must weigh against the question, and gives no concrete example of an acceptable reply.
D=Write long then shorten in one answer: the final answer would still contain the long draft or an unpredictable mix, since the instruction does not define what is returned.
T: To change style or tone, show a few consistent examples and state the hard limits in the instruction.

@ DBX-GAI D3 T3.5 applied troubleshooting
S: A prompt asks a model to compute the total cost of a basket with discounts and tax. The baseline answer is a single number that is often wrong, and the model does not show how it got there. The team wants the final value to remain easy to parse. Which prompt change fits best?
A: Tell the model to answer with the number only and to double check it silently before replying, without showing any working steps
B: Add a system message that says the model is the world's best mathematician and that it is forbidden to ever make an arithmetic mistake
C: Set `max_tokens` to a very small value so that the model has no room to ramble before it prints the final number
D: Ask for the discounts and tax to be worked out step by step, ending with a last line `Answer:` and the number
K: D
G: ## Reasoning prompts
Multi-step arithmetic or logic often fails when a model must jump straight to the result, because each generated token depends only on the text before it. Chain-of-thought prompting asks the model to write intermediate steps before the conclusion. The steps act as working memory and the final token sequence is conditioned on them.
## Keeping the output parseable
Intermediate reasoning makes the response longer and more variable. Combine the instruction with a fixed marker, such as a last line that begins with `Answer:`, so that code can cut the reasoning away and read the value after the marker.
## Common non-fixes
- Role flattery does not add capability.
- A small output budget truncates the reasoning that creates accuracy.
- A hidden "double check" without visible steps gives the model no extra tokens to compute with.
W: Step-by-step reasoning gives the model room to compute each part before the result, and the `Answer:` marker keeps the final number easy to extract by code.
X: A=One word, no steps: asking for an immediate result removes the intermediate tokens that make the arithmetic reliable, so the "double check" has nothing to work on.
B=Expert persona: a persona line does not add arithmetic ability and does not change how many reasoning tokens the model produces.
C=Tiny `max_tokens`: this cuts the reply off, and it removes any room for reasoning, so accuracy gets worse and long answers can be truncated.
T: For multi-step problems ask for visible step-by-step reasoning plus a fixed final-answer marker.

@ DBX-GAI D3 T3.5 applied use-case
S: A RAG prompt is `Answer the question. {context} {question}`. In testing, the model sometimes answers from its own memory when the retrieved passages do not contain the answer, and it is hard to tell where the context ends. The team wants answers grounded in the passages only. Which rewrite fixes the baseline best?
A: Wrap the passages in delimiters, limit the answer to them, and give a fixed "not found in the documents" reply for missing answers
B: Put the question first and the passages last, because models only pay attention to the final lines of a prompt and ignore the start
C: Add the sentence "Do not hallucinate and be accurate" at the end of the prompt and keep the rest of the template exactly as it is
D: Remove the passages from the prompt and rely on a larger model that has already seen similar documents during its training
K: A
G: ## Grounding instructions
In retrieval-augmented generation the prompt must tell the model which text is allowed as evidence and what to do when the evidence is missing. Three habits make that reliable:
- Separate the instruction, the context and the question with delimiters such as `<context> ... </context>` so the model can tell data from instructions.
- Say explicitly that the answer must come only from the supplied context.
- Define a fallback reply for the missing-answer case. Without it the model fills the gap with its own knowledge.
## Why a short warning is weak
A bare "do not hallucinate" is a goal, not an instruction the model can act on. It gives no evidence boundary and no fallback behavior.
W: Delimiters mark where evidence starts and ends, the restriction defines the allowed source, and the fallback sentence gives the model a safe thing to say when the passages do not answer the question.
X: B=Reordering: models read the entire prompt, and ordering alone does not tell them to avoid outside knowledge or what to say when the answer is missing.
C=A bare warning: "Do not hallucinate" has no concrete boundary or fallback, so the model still fills gaps from memory.
D=Dropping the passages: without retrieved evidence the application is no longer a RAG application and cannot cite current or private documents.
T: A grounded prompt marks the context, limits answers to it, and defines a fallback for missing answers.

@ DBX-GAI D3 T3.5 advanced tradeoff
S: A team has a baseline prompt that scores 70% on a fixed set of 100 evaluation questions. A colleague rewrites the persona, adds four rules, swaps the examples and changes the output layout in one edit. The score rises to 74%, but nobody knows why. What is the best way to continue improving the prompt?
A: Keep the large edit, because any score gain proves that each of the changes was useful
B: Judge each version on a handful of favorite questions, since a big set hides the effect of small changes
C: Change one element at a time, rerun the same fixed evaluation set after each change and keep only the changes that help
D: Test every new version only on the questions that failed before, because questions that already pass cannot teach the team anything
K: C
G: ## Prompt engineering is an experiment loop
A prompt is a hypothesis about what makes the model produce the output you want. To learn from it you need a stable measuring instrument and controlled changes.
- Fix an evaluation set that represents real inputs and does not change between versions.
- Change one element per iteration (instruction wording, example set, layout, or constraint) and record the score. This isolates which edit moved the metric.
- Keep a list of the versions and their scores so you can return to the best one.
## What goes wrong
A multi-edit change can include one helpful and two harmful edits that cancel each other. Testing only on previously failing questions hides regressions on questions that used to pass.
W: Single-element changes measured on the same fixed set show which edit caused which score change, so the team keeps what helps and discards what hurts.
X: A=Accepting the big edit: a combined edit can hide harmful changes behind helpful ones, so the 4-point gain does not show that every change is useful.
B=A few favorite questions: a handful of cases is noisy and cherry-picked, so small effects cannot be told from chance.
D=Only previously failing questions: this ignores regressions on the questions that passed before, which is exactly where a rewrite often causes new failures.
T: Improve prompts like an experiment: one change at a time, one fixed evaluation set, keep what measurably helps.

@ DBX-GAI D3 T3.5 applied use-case
S: A product manager gives the prompt `Summarize this ticket.` The baseline summaries vary widely in length and focus, and the agents who read them want the customer's problem, the steps already tried and the requested outcome. Which rewritten prompt is the best fix?
A: Summarize the ticket for a support agent in at most 60 words: the problem, the steps tried and the wanted outcome, as three labeled lines.
B: Summarize this ticket very well and make sure the summary is useful, accurate, complete and short, written the way an expert would write it.

G: ## Specific prompts beat general ones
A vague instruction leaves the audience, length, content and layout to chance, so outputs vary from run to run. A specific prompt names the reader, the content to include, a size limit and a layout. Each missing detail in the baseline can be turned into one explicit requirement.
## A quick checklist
- Audience: who reads the output.
- Content: which items must be covered.
- Constraints: length or forbidden content.
- Format: labeled lines, bullets or JSON.
Quality adjectives such as "very good" or "expert" do not specify anything the model can check.
W: The rewrite names the reader, lists the three required items, caps the length and fixes a labeled layout, which turns each observed gap of the baseline into a checkable requirement.
X: B=Quality adjectives: "useful, accurate, complete and short" are goals without measurable limits, and "complete" and "short" even pull in opposite directions.
C=Creative freedom: inviting extra content increases the variation between summaries, which is the opposite of the consistency the agents need.
D=Repeated summarizing: recursive shortening loses the items the agents need and gives no guidance about which details to keep.
T: Turn every observed gap in a baseline output into a specific instruction about audience, content, length and format.

@ DBX-GAI D3 T3.6 applied use-case
S: A public assistant for a bank must only discuss the bank's own products. Users sometimes ask for medical advice or help with homework, and the assistant currently answers. The team wants to prevent these off-topic answers before they reach users. Which guardrail design is most suitable?
A: Lower the temperature to zero, because a deterministic output cannot go off topic when the system prompt describes the bank
B: Increase the number of retrieved passages so the model has more banking material to talk about instead of unrelated subjects
C: Add an input classifier that labels each request in scope or out of scope, and return a fixed polite refusal for out-of-scope requests
D: Rely on the model's built-in training, since foundation models already refuse everything that is unrelated to the system prompt
K: C
G: ## What a guardrail is
A guardrail is a control around the model that prevents a negative outcome, such as off-topic answers, unsafe content, ungrounded claims or malformed output. Guardrails are layered around the model, because model behavior alone is not guaranteed. A guardrail sits at one of two places:
- Input side: inspect the request before the main model is called. A cheap classifier or a rule decides whether the request is allowed.
- Output side: inspect the generated answer before it reaches the user.
## Topic restriction
For scope control, an input classifier plus a fixed refusal message is the standard design. Calling the main model for a blocked request is wasted cost, and a fixed refusal is predictable. The system prompt should also state the scope, but a prompt instruction is soft: a classifier gives an enforceable check.
## Naming
Older Databricks material called the gateway features for this "AI Guardrails" at serving endpoints; current docs put guardrails under Unity Gateway service policies (AI Gateway was renamed Unity Gateway).
W: A scope classifier on the input decides before generation, so out-of-scope requests receive a predictable refusal and never reach the main model.
X: A=Temperature zero: temperature controls randomness of sampling, not what topics the model is willing to discuss, so the assistant would still give the same medical advice every time.
B=More retrieved passages: extra banking text in the prompt does not stop the model from answering an unrelated question; it only adds cost and context.
D=Trusting built-in behavior: models follow system prompts only on a best-effort basis and can be steered off topic, so an enforceable check is needed.
T: Enforce scope with an input classifier and a fixed refusal, not with sampling settings.

@ DBX-GAI D3 T3.6 applied use-case
S: A children's education app uses a foundation model to write short stories. Rarely, a story contains violent or otherwise unsuitable content, and the team must make sure such text is never shown. Which guardrail placement protects the users?
A: Run a safety classifier on each generated story and replace unsafe results with a safe fallback message or a regeneration

G: ## Output guardrails
Even a safe request can produce an unsafe answer, because the model generates new text. The only place that sees the real answer is the output side. An output guardrail evaluates the response (with a safety classifier, rules, or an LLM judge) and decides to return it, block it, or regenerate it.
## Fallbacks
When the check fails, return a pre-written message or try again with the same prompt. The fallback must be defined in advance, so that the user never sees the blocked text.
## Monitoring is not a guardrail
Logging and later review are valuable for improvement, but they happen after the user has already seen the content. A guardrail acts in the request path.
W: A safety classifier on the output inspects the text the model actually wrote and blocks it before display, with a defined fallback if it is unsafe.
X: B=Terms of use: a notice shifts responsibility to the user but does nothing to stop unsuitable stories being shown to children.
C=Prompt-only check: a clean prompt can still lead to an unsafe story, and the check never sees the generated text.
D=Weekly review: log review is detection after delivery, so children can see harmful stories for days before anyone looks.
T: Only an output-side check can stop unsafe text the model generates from a clean request.

@ DBX-GAI D3 T3.6 applied use-case
S: Which TWO guardrails directly reduce the risk of an ungrounded or malformed answer reaching the application that calls a RAG chain? (Select TWO)
A: Run a groundedness check of the answer against the retrieved passages and return "not found" when claims are unsupported
B: Increase the embedding dimension of the index so that more information fits in every vector and the passages are richer
C: Validate the model output against the required JSON schema and retry or return an error response when validation fails
D: Move the retriever to a larger cluster so that the retrieved passages arrive at the model faster and with less delay
E: Raise the maximum output tokens so that the model can write longer answers when a question needs more detail
K: A,C
G: ## Functional guardrails for RAG
A functional guardrail is an automatic check in the request path with a defined action on failure. Two typical failures in RAG are:
- Ungrounded answers: claims not supported by the retrieved passages. A groundedness check (often an LLM judge, or an entailment classifier) compares the answer with the evidence, and the application blocks or replaces failing answers.
- Malformed output: downstream code expects a specific structure. Validating output against a schema, with a retry or an explicit error, stops broken data from flowing on.
## What is not a guardrail
Index dimension, retrieval speed and output length can affect quality or latency, but they contain no check with a failure action.
W: A=Groundedness check: compares the answer with the retrieved evidence and replaces unsupported answers with a not-found message.
C=Schema validation: rejects malformed output before it reaches the caller and triggers a retry or error.
X: B=Larger embedding dimension: a retrieval design choice that does not check the answer and cannot block anything.
D=Faster retriever: improves latency only, with no inspection of the answer.
E=More output tokens: lengthens answers and, if anything, gives more room for unsupported claims.
T: A guardrail is a check with an action on failure, such as a groundedness check or output validation.

@ DBX-GAI D3 T3.6 advanced troubleshooting
S: A team added an output safety check to a streaming chat application. It checks the full answer only after the model has finished, but users read tokens while they stream, so unsafe text is already visible when the check blocks the answer. What is the best fix that keeps the guardrail?
A: Turn off streaming on the safety-critical path, or buffer and check chunks of text before they go to the user interface

G: ## Guardrails and streaming
A guardrail can only prevent harm if it runs before the user sees the content. With streaming, tokens reach the interface as they are generated, so a check that waits for the full answer is too late. ## Options
- Do not stream on safety-critical paths: generate, check, then return.
- Buffer and check: collect a sentence or paragraph, check it, then release it. The user sees text with a small delay.
- Accept a risk only where the content is low risk.
## Why a prompt cannot replace the check
A system prompt asks the model to behave; a check verifies what the model actually produced.
W: Buffering or turning off streaming places the check between generation and display, so unsafe text is blocked before the user sees it.
X: B=Warning label after the fact: the unsafe text has already been displayed, so the label only reports a failure that the guardrail was meant to prevent.
C=One-time deployment check: a check at start-up cannot inspect answers that do not exist yet.
D=Longer system prompt: this only asks for good behavior and offers no verification of the generated text.
T: A guardrail must run before display, so streaming needs buffered checks or a non-streaming path.
