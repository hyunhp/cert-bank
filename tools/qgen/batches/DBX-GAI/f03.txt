@ DBX-GAI D4 T4.3 applied tradeoff
S: Every request to a billing assistant follows the same path: look up the customer's plan with a fixed SQL function, then answer from a prompt using that result. No step depends on the model deciding what to call next. Latency and predictable behavior matter. What is the best design?
A: A tool-calling agent that chooses among many tools and loops until it decides the answer is complete
B: A supervisor with three worker agents, one for lookups, one for answers and one for formatting
C: A developer-defined chain that runs the same two steps in order, with no model-chosen tool calls
D: A fine-tuned model that memorizes every customer's plan, so the SQL lookup step can be dropped
K: C
G: ## Chain or agent
- A **chain** has a fixed sequence of steps decided by the developer. Behavior is predictable, latency is bounded and each step is easy to evaluate.
- An **agent** lets the model decide which tools to call and how many times, which suits tasks where the path is not known in advance. That flexibility costs extra model calls, variance and evaluation effort.
## Applying it
The billing flow is always the same, so there is nothing for the model to decide. A chain with a fixed lookup step, a prompt template and a model matches the requirement with the least complexity.
## Source note
This is generic LangChain expression language (LCEL) behavior and is not described on the Databricks docs pages; it is not a Databricks-specific feature.
W: Developer-defined chain: the path never varies, so a chain that runs the SQL lookup and then the prompt and model in a fixed order gives bounded latency and predictable behavior and is easy to test.
X: A=Free tool-calling loop: extra model calls and variance for a decision that never needs making.
B=Supervisor with workers: multi-agent routing adds latency and complexity for a flow without branching.
D=Memorizing plans: plan data changes and is private per customer, so a model cannot hold it reliably; the lookup returns current data.
T: Use a simple chain when the steps are fixed; use an agent when the model must choose the path.

@ DBX-GAI D1 T1.6 applied comparison
S: Finance analysts want a business-user assistant that answers natural-language questions about governed sales tables. The data team wants to configure trusted data, metrics and business rules and does not want to write agent code. Which option fits best?
A: An AI Search index over the text columns of the tables, queried by a prompt template that contains the question
B: An `ai_query` call run once per table row, which would write each answer into a new table
C: An agent scaffolded with the Agent Bricks CLI, with SQL generation written by the team in Python
D: A Genie Agent, set up through configuration instead of code and grounded in Unity Catalog data
K: D
G: ## Low-code or code-first
The guide asks when to use the three Agent Bricks builders. The docs now give a simpler rule, and they mark Knowledge Assistant, Supervisor Agent (the guide's Multi-Agent Supervisor) and Information Extraction as Legacy:
- For a **new low-code agent** over documents and data, use **Genie Agents**. These are domain-specific environments where data teams configure trusted data, metrics and business rules, so answers are grounded in governed (Unity Catalog) data.
- For an **agent written in code**, use the **Agent Bricks CLI**.
- For **batch work over rows** (classify, extract, parse), AI Functions such as `ai_query` fit (this line is a summary, not a quoted docs rule).
- For **retrieval over text**, use an AI Search index.
Genie Agents were called Genie spaces in earlier docs and in the guide.
## This scenario
Business questions over governed tables, configured by a data team and with no code, is the Genie Agent use case.
W: Genie Agent: the data team configures the tables, metrics and business rules without writing agent code, answers are grounded in governed Unity Catalog data, and business users ask in natural language.
X: A=AI Search over text columns: similarity retrieval over text finds passages, but it cannot compute revenue totals or apply metric definitions over tables.
B=Row-wise `ai_query`: it is a batch function that applies a prompt to each row; it is not an interactive assistant for ad hoc questions.
C=Agent Bricks CLI agent: it is the right route when the team wants to write the agent in code, but the stated requirement is a configured, no-code environment.
T: New low-code agents over governed data use Genie Agents, new code agents use the Agent Bricks CLI, and batch row work uses AI Functions.

@ DBX-GAI D3 T3.5 applied use-case
S: A product manager gives the prompt `Summarize this ticket.` The baseline summaries vary widely in length and focus, and the agents who read them want the customer's problem, the steps already tried and the requested outcome. Which rewritten prompt is the best fix?
A: Summarize the ticket for a support agent in at most 60 words, as three labeled lines: problem, steps already tried, requested outcome.
B: Summarize this ticket very well, making sure it covers the customer's problem, the steps already tried and the requested outcome.
C: Summarize this ticket in a creative way, and feel free to add anything else you think the reader might find interesting or fun.
D: Summarize this ticket, then keep summarizing the summary until only the problem, the steps tried and the outcome remain.
K: A
G: ## Specific prompts beat general ones
A vague instruction leaves the audience, length, content and layout to chance, so outputs vary from run to run. A specific prompt names the reader, the content to include, a size limit and a layout. Each missing detail in the baseline can be turned into one explicit requirement.
## A quick checklist
- Audience: who reads the output.
- Content: which items must be covered.
- Constraints: length or forbidden content.
- Format: labeled lines, bullets or JSON.
Quality adjectives such as "very good" or "expert" do not specify anything the model can check.
W: Audience, content, length and format: the rewrite names the reader, lists the three required items, caps the length and fixes a labeled layout, which turns each observed gap of the baseline into a checkable requirement.
X: B=Content list without limits: naming the three items fixes the focus, but with no length cap or layout the summaries still vary widely in size and shape, and "very well" specifies nothing the model can check.
C=Creative freedom: inviting extra content increases the variation between summaries, which is the opposite of the consistency the agents need.
D=Repeated summarizing: recursive shortening has no defined stopping point or layout, and each pass risks dropping details of the items the agents need.
T: Turn every observed gap in a baseline output into a specific instruction about audience, content, length and format.
