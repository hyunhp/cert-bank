@ DBX-GAI D4 T4.13 applied comparison
S: A finance team's agent must answer free-form business questions such as "what was churn by region last quarter?" and the answers must use the company's governed metric definitions and business terms, not whatever the model guesses from raw table names. The team wants a Databricks-provided MCP server, with no server to host. Which one should the agent connect to?
A: The Genie One MCP server (`system.ai.genie_one_mcp`), which answers questions grounded in the governed semantic layer
B: The Databricks SQL MCP server (`system.ai.dbsql`), which lets the model write and run SQL directly against any raw tables it has permission to see
C: The `system.ai.web_search` MCP server, so the agent can look up churn definitions and regional churn figures on the public web
D: A custom MCP server on Databricks Apps that wraps a single hard-coded churn query and returns the same fixed result set each time
K: A
G: ## Three kinds of MCP server on Databricks
Model Context Protocol (MCP) is the open standard through which an agent discovers and calls tools. Databricks offers three ways to get a server:
- **Databricks-provided MCP servers** live in the `system.ai` schema. Each one is a Unity Catalog securable that is invoked through Unity Gateway, so you govern who may call it with grants and govern individual calls with policies. You do not host or register anything.
- **External MCP servers** are self-hosted or third-party servers that you register and then share with your team.
- **Custom MCP servers** are built on Databricks Apps, either from a template with your own Python tools or by exposing an existing REST API.
## Choosing among the analytics servers
The docs recommend the Genie One MCP server for business questions asked in natural language: it resolves business terms, metric definitions and table relationships through the governed semantic layer, which gives more accurate answers than an agent writing SQL against raw tables. The Databricks SQL MCP server is meant for specific SQL work such as validating syntax or authoring a pipeline, and a Genie Agent MCP is scoped to one curated agent. (Naming note: the exam guide era called these Genie spaces; they are now Genie Agents, and Unity Gateway was called AI Gateway. The SQL, sandbox and web search servers are currently behind the Unity Gateway beta, so only the Genie One server is relied on here.)
W: Genie One MCP: it is the Databricks-provided server for natural-language business questions, it grounds answers in the governed semantic layer so metric definitions are consistent, and it needs no hosting.
X: B=Databricks SQL MCP: it is built for running specific SQL (development, data engineering). The model would have to infer churn logic from raw tables, which is what the team wants to avoid.
C=Web search MCP: it returns a synthesized answer from the public internet. It knows nothing about internal churn definitions and cannot read the governed tables.
D=Custom MCP with one fixed query: it must be built and hosted by the team and answers only that one question, so it does not handle free-form business questions.
T: Natural-language business analytics on governed data points to the Genie One MCP server; use the SQL MCP server when you need specific SQL.
V: Unity Gateway, MCP, Genie

@ DBX-GAI D4 T4.13 applied use-case
S: A company has an internal customer-lookup REST API described by an OpenAPI 3 specification. The agent framework the team uses can talk only to MCP servers, and the API needs a backend credential that must never appear in agent code. What is the recommended way to expose the API on Databricks?
A: Deploy the MCP Server (Starter) template on Databricks Apps, write one tool per endpoint, and keep the API key as a constant in `server/tools.py`
B: Register the API as a `system.ai` MCP and route calls through `system.ai.github`, which forwards requests to any HTTP endpoint
C: Deploy the MCP Server (OpenAPI) template on Databricks Apps, with `spec.json` in a Unity Catalog volume and the credential in an HTTP connection
D: Store the OpenAPI spec in a Delta table and let the model compose each raw HTTP request itself from the spec when a question arrives
K: C
G: ## Turning a REST API into MCP tools
When you already have an HTTP API, you do not rewrite it. Databricks Apps provides an **MCP Server (OpenAPI)** template that reads the API description and gives the agent tools to list and call the endpoints. It needs two things:
- The OpenAPI 3.x specification saved as `spec.json` at the root of a Unity Catalog volume, which the app reads through a volume resource.
- A Unity Catalog **HTTP connection** that stores the authentication credentials (bearer token, OAuth machine-to-machine, or per-user OAuth). The app finds it through the `UC_CONNECTION_NAME` setting in `app.yaml`.
Callers need CAN USE on the app and `USE CONNECTION` on the connection, so the secret stays in Unity Catalog and is governed like any other securable. The app URL plus `/mcp` is what the agent connects to.
## Why the other designs fail
The `system.ai` servers are fixed, Databricks-provided integrations for specific services, so you cannot add your own API to them. The Starter template is meant for hand-written Python tools, and a secret in source code is exactly what the requirement forbids.
W: OpenAPI template with spec in a volume and an HTTP connection: it exposes the existing API as MCP tools with no rewrite, and the credential lives in a governed Unity Catalog connection rather than in code.
X: A=Starter template with a hard-coded key: it hosts a custom server, but the credential sits in source code, which breaks the requirement, and each endpoint would be hand-coded.
B=GitHub MCP as a proxy: `system.ai.github` talks to GitHub only. The system MCPs are fixed integrations and do not forward calls to arbitrary HTTP APIs.
D=Spec in a Delta table: this gives the model text to read but no MCP server, no secure credential handling and no governed call path, so the agent framework still cannot call the API.
T: Existing REST API plus OpenAPI spec: host the OpenAPI MCP template on Databricks Apps and keep the credential in a Unity Catalog HTTP connection.
V: Databricks Apps, Unity Catalog, MCP

@ DBX-GAI D4 T4.14 applied use-case
S: A support agent has its system prompt written as a string inside `agent.py`. Prompt wording changes often, and the team must review each change in a pull request and know exactly which registered agent version used which prompt text, without editing agent logic. Which design fits best?
A: Keep the string in `agent.py` and add a code comment above it with the date, author and reason of each change
B: Store the prompt in a notebook cell that is run before each request, so that the latest edit is picked up at once
C: Keep the prompt in a notebook widget on the serving cluster and let the on-call engineer type the current text when needed
D: Keep the prompt in a YAML file in Git, read through `ModelConfig` and logged with the agent in Unity Catalog
K: D
G: ## Treat the prompt as versioned configuration
Prompt text changes more often than agent logic and can change behavior as much as a model swap, so it should be reviewed, tested and traced like code. (Databricks also has an MLflow Prompt Registry, labelled Beta in the docs at the time of writing; this question uses only the generally available pieces and the principle that holds for any prompt store.)
- **Git** gives a reviewed history: every change is a commit in a pull request with an author and a message.
- **`ModelConfig`** (`mlflow.models.ModelConfig`) is the documented way to keep parameters such as the system prompt outside the agent code. The docs describe a dictionary in development and a `.yaml` file for production deployment and CI/CD.
- **Logging the config with the agent** (`mlflow.pyfunc.log_model` with `model_config`) stores the exact values in the logged model, so the Unity Catalog model version is a snapshot of code plus prompt.
Example: `prompt: "You are a support agent. Answer only from the retrieved context."` in `configs/prod.yml`, read in the agent with `config.get("prompt")`.
W: YAML in Git read through `ModelConfig` and logged with the agent: pull requests review each wording change, and every Unity Catalog model version records the exact prompt it was built with.
X: A=Comment above the string: a comment is unverifiable text, not a review gate, and the prompt is still mixed into logic so every wording change touches agent code.
B=Notebook cell run per request: the live text depends on whoever last ran or edited the cell, so there is no review, no frozen snapshot and no link to a model version.
C=Widget on the cluster: a typed value leaves no history and no review, and nobody can later say which text a given agent version used.
T: Keep the prompt as reviewed configuration and log it with the agent, so each model version identifies its prompt.
V: MLflow, Unity Catalog

@ DBX-GAI D4 T4.14 applied use-case
S: A team keeps its agent code and prompt file in one Git repository and serves the agent from dev, staging and production workspaces. A prompt edit must reach production only after it has been tested. Which promotion process follows the deploy-code pattern?
A: Edit the prompt directly on the production endpoint, test it with a few live users, and copy the text back to Git afterwards
B: Merge the change, run the evaluation in staging on a fixed dataset, and deploy the same commit to production only if it passes
C: Keep a separate hand-written copy of the prompt in each workspace, and update the production copy once developers say it works
D: Build the agent once in dev, then copy the finished model artifact to production without running any further test in staging
K: B
G: ## Promote code and configuration, not hand-made copies
Databricks recommends the deploy-code pattern for MLOps: the same code moves from development to staging and then to production, and each environment runs its own tests. For a GenAI agent the prompt file is part of that code, so a prompt change is promoted like any other change:
1. Develop and test the change in dev, then merge it through a pull request.
2. A CI pipeline deploys the commit to staging and runs an evaluation (for example `mlflow.genai.evaluate()`) on a fixed dataset with the same scorers each time.
3. If the scores meet the threshold, the pipeline deploys the identical commit to production. Rolling back means deploying an earlier commit.
This keeps one source of truth, gives a reviewable history and stops untested text from reaching users. (The docs name deploy code as the recommended pattern; the evaluation step is a standard application of it to prompts.)
W: Merge, evaluate in staging, deploy the same commit: the prompt moves like code through environments, the staging evaluation is the gate, and production receives exactly what was tested.
X: A=Edit on the production endpoint: users become the test, the change bypasses review and the Git history is only filled in afterwards, so the repository may not match what actually ran.
C=Hand-kept copies per workspace: the copies drift apart, so what was tested in staging need not be what runs in production, and there is no single reviewed history.
D=Copy the artifact with no staging test: that is the deploy-models pattern without its checks, and a prompt regression would reach users before any environment evaluated it.
T: Promote prompt changes as code: review, evaluate in staging, then deploy the same commit to production.
V: MLflow

@ DBX-GAI D4 T4.14 advanced troubleshooting
S: After a prompt wording change was logged with the agent as Unity Catalog model version 12, answer quality drops in production. Version 11, with the earlier prompt in its logged config, passed evaluation and is still registered. The team needs the earlier behavior restored quickly. What should they do?
A: Edit the prompt stored inside version 12 in place, because a registered version can be rewritten when its text turns out to be wrong
B: Deploy model version 11 to the serving endpoint again, since its logged config holds the earlier prompt
C: Delete the registered model and log the agent again from the old code, so that version numbering starts at 1
D: Scale up the serving endpoint, because answer quality falls when requests wait too long in the queue
K: B
G: ## Rollback with immutable versions
A logged model version is a snapshot: it contains the agent code and the `model_config` that was logged with it, so the prompt text cannot differ between runs of the same version. A new prompt means a new version, and the previous version stays registered.
- **Rollback** is a deployment of the earlier version (for example by deploying version 11 again with the agent deployment API), not an edit.
- **Traceability**: logging the model version with each trace tells you which prompt produced an answer.
- **Do not rewrite or delete history**: that removes the evidence needed to audit the incident and to compare the versions.
Capacity changes help latency and throttling, not wording quality. (Immutability of registered model versions and rollback by redeploying a version are standard Unity Catalog model practice.)
W: Redeploy version 11: it is the immutable snapshot that passed evaluation, so serving it restores the earlier prompt without code edits and keeps version 12 available for analysis.
X: A=Edit version 12 in place: logged versions are snapshots that are replaced by registering a new one, and rewriting history destroys the audit trail for the incident.
C=Delete the model and relog: this removes the registered history, restarts numbering and takes longer than serving a version that already exists and passed evaluation.
D=Scale up the endpoint: more capacity speeds up or unblocks requests but cannot change the text of the answers, and the symptom is wording quality.
T: Keep versions immutable and roll back by redeploying the earlier version; never edit or delete registered history.

@ DBX-GAI D4 T4.15 advanced troubleshooting
S: A chat app on Databricks Apps queries tables through an agent. Every employee, including interns, can see rows only a finance group is allowed to read, and the app runs under its own dedicated service principal. The company requires Unity Catalog permissions to apply to the person asking. What should the team change?
A: Grant the app's service principal access to fewer tables, so that no one can read the finance rows through the app
B: Enable user authorization so the app calls Databricks with the signed-in user's identity, and declare the scopes the app needs
C: Create one copy of the app per department and give each copy its own service principal with a matching group of tables
D: Add a check in the app's code that hides rows whose text contains the word "finance" before showing the answer
K: B
G: ## App authorization versus user authorization
A Databricks app has two ways to act:
- **App authorization**: each app has a dedicated service principal that is its identity. Everything the app does uses that principal's permissions, so all users share the same access and the app cannot enforce user-level rules.
- **User authorization** (on-behalf-of-user): Databricks forwards the signed-in user's access token to the app, which uses it to reach resources. Databricks then enforces Unity Catalog permissions for that user, including row filters and column masks.
## Scopes
An app that uses user authorization declares scopes (for example `sql`, or `model-serving` for serving endpoints) that limit what it may do on the user's behalf. Users consent once per app and set of scopes, and access outside the approved scopes is blocked even if the user has permission. Use app authorization only for actions the app takes on its own.
W: User authorization: the app acts with each user's identity, so Unity Catalog applies that person's permissions and the finance rows stay hidden from others, with scopes keeping the app to least privilege.
X: A=Fewer tables for the service principal: this removes finance data for finance staff too, because the principal's rights are the same for everyone using the app.
C=One app per department: it multiplies deployments and still ties many users to one shared identity per app; users change departments and permissions drift.
D=Hide rows containing "finance": a text match in app code is not an access control; the data was already read under the shared identity and is easily bypassed.
T: When data access must follow the person, use user authorization; app authorization means all users share the service principal's rights.

@ DBX-GAI D4 T4.15 applied use-case
S: A Databricks App only sends inference requests to a model serving endpoint that hosts the agent and needs an API key for a downstream service. The security team wants least privilege and no secrets in source code. How should the app be configured?
A: Give the app's service principal `CAN MANAGE` on the endpoint and keep the downstream key in a plain-text file in the app folder
B: Give the app's service principal workspace admin rights, so it can read every resource it might ever need
C: Hard-code the endpoint name and API key in the code, then restrict who may view the app's source in Git
D: Add the endpoint as an app resource with `CAN QUERY` and the key as a secret resource, then reference them with `valueFrom` in `app.yaml`
K: D
G: ## Resources keep apps least-privilege
In Databricks Apps, platform features that the app uses are called **resources**: SQL warehouses, Lakeflow Jobs, model serving endpoints, secrets and more. You add a resource to the app with a specific permission, and the app's service principal receives it. You then assign the resource a key and reference it in the `env` section of `app.yaml` with `valueFrom`, so the code reads an environment variable instead of a literal value.
- A serving endpoint resource supports permissions such as `Can query`. The docs advise granting `CAN QUERY` when the app only sends inference requests.
- A secret resource lets the app read a Databricks secret at run time, so credentials never enter the code or repository.
## Why this matters for agents
The chat UI of an agent should be able to call the endpoint and nothing more. Over-broad rights (`CAN MANAGE`, admin) let a bug or injection in the app change the endpoint or read unrelated data.
W: Endpoint resource with `CAN QUERY` plus a secret resource, bound by `valueFrom`: the app can only send inference requests and reads the key at run time, with nothing sensitive in the code.
X: A=`CAN MANAGE` and a plain file: `CAN MANAGE` lets the app change or delete the endpoint, far more than inference needs, and a key in a file ships with the app source.
B=Workspace admin for the principal: it grants unrelated access everywhere, the opposite of least privilege, and one compromised app could affect the whole workspace.
C=Hard-coded name and key: restricting Git views does not remove the key from builds, logs and history; resources and secrets exist so literals are not needed.
T: Give an app only the resources it needs, with the smallest permission (`CAN QUERY` to infer), and read secrets via resources, not code.

@ DBX-GAI D5 T5.1 applied use-case
S: A support-assistant RAG pipeline indexes call transcripts that contain customer e-mail addresses and card numbers. Compliance says the assistant must never display them, and a later audit must also show that the search index itself holds none. Where should masking be applied?
A: Only on the model's final answer, by scanning the response text before it is shown to the user
B: In the ingestion pipeline before chunking and embedding, so the chunk table and the index never store them
C: By telling the model in the system prompt that card numbers and e-mails are confidential and must not be repeated
D: By encrypting the index at rest, so that unauthorized people cannot read the stored vectors
K: B
G: ## Mask at the earliest point you control
Masking is a guardrail that replaces sensitive values (names, e-mails, card numbers) with placeholders. In a RAG pipeline, data passes through several stages: source documents, the chunk table, the embeddings and index, the prompt, the model's answer, and logs and traces. Sensitive text that enters the pipeline can be copied into every later stage.
- Masking **at ingestion**, before chunking and embedding, means the chunk Delta table, the index, the retrieved context, prompts and traces never contain the raw values, which also makes an audit simple.
- Masking **at output** is a second layer: it catches what slips through, but the index and prompts still hold the original text.
- A prompt instruction is not a control, because a model can be talked out of it.
- Encryption at rest protects storage from outsiders, not from the application's own retrieval.
In Databricks, ingestion masking is typically a step in a pipeline that writes the chunk table. (This is generally accepted data-protection practice, "data minimisation".) Table-level column masks in Unity Catalog control what each viewer sees but do not rewrite text that is already embedded inside chunk strings.
W: Ingestion masking: removing values before chunking and embedding means they never reach the index, the retrieved context or the model, which satisfies both the display rule and the audit.
X: A=Output scanning only: the index and the prompt would still contain raw card numbers, so the audit fails and the model still saw them; a missed pattern would show up to the user.
C=Prompt instruction: a rule in the prompt is advisory, a model may repeat sensitive text, and the index would still hold the raw values.
D=Encryption at rest: it protects stored files from outside access, but retrieval decrypts normally, so the assistant can still return the card numbers.
T: Mask sensitive data as early as possible (before chunking and embedding), then add output checks as a second layer.

@ DBX-GAI D5 T5.1 applied comparison
S: A team masks personal data in documents before sending them to a foundation model that summarizes meeting notes. The summaries must still say who said what and how many different people took part. Which masking technique keeps this quality?
A: Delete each detected name and e-mail from the note, leaving the surrounding sentences as they are
B: Replace every detected value with the same string of asterisks, whatever its type
C: Replace every name with a randomly generated real-looking name, choosing a fresh random name each time that person is mentioned
D: Replace each detected value with a typed placeholder such as `<PERSON_1>`, reusing the same one for the same entity
K: D
G: ## Masking can hurt answer quality
A mask that removes information the model needs lowers answer quality. Common techniques:
- **Deletion**: simple, but sentences lose their subject and the model cannot tell speakers apart.
- **Fixed redaction (`*****`)**: hides the value but also its type and identity; two different people look identical.
- **Typed, consistent placeholders** (`<PERSON_1>`, `<EMAIL_2>`): the model still knows the entity type and that the same token refers to the same entity, so summaries, counts and relations survive.
- **Random substitution**: if names change from mention to mention, one person turns into several.
A mapping from placeholder to original value can be stored separately and applied to the final answer for authorised viewers, so the sensitive values never go to the model. These are generally accepted privacy-engineering practices rather than a Databricks feature.
W: Typed consistent placeholders: they preserve the entity type and the identity of each speaker, so the summary can attribute statements and count participants without seeing real data.
X: A=Deletion: removing the names leaves statements with no speaker, so "who said what" cannot be reconstructed.
B=Identical asterisks: all values look the same, so two people merge into one and the count of participants is wrong.
C=New random name for each mention: the same person would appear under several names, which breaks speaker counts and creates fake people.
T: Use typed, consistent placeholders so masking protects data without destroying meaning.

@ DBX-GAI D5 T5.1 advanced tradeoff
S: A chatbot has a strict response-time budget. Inputs may contain card numbers and SSN-style identifiers (fixed patterns) and free-text names. The team wants masking in the request path without blowing the latency budget or letting structured identifiers through. Which design meets this best?
A: Match fixed-format identifiers with regular expressions plus checksum validation inline, and add a light entity-recognition step for names
B: Call a second large language model on every request to find and rewrite every sensitive value in the message before the main model call is made
C: Skip inline masking and have a reviewer examine a sample of the conversation logs once a week for leaked values
D: Mask only inputs longer than a few hundred tokens, since short messages rarely contain personal data
K: A
G: ## Masking has a performance cost
A masking step in the request path adds latency and cost to every call, so the method should match the data type:
- **Structured identifiers** (card numbers, SSNs, phone numbers) follow fixed formats. Regular expressions, often with a checksum such as the Luhn check for card numbers, are fast, cheap and deterministic.
- **Free-text entities** (names, places) need a statistical or small NER model, which is slower but still much faster than a general LLM call.
- A **second LLM** on every request can catch more but doubles latency and cost; it fits asynchronous scans of stored data better than the hot path.
- **Sampling afterwards** finds leaks only after the data left, so it is not a guardrail.
Databricks offers guardrails through Unity Gateway service policies (built-in, custom and external policies), and the legacy endpoint AI Guardrails offered PII detection that could Block or Mask. The detection technique itself is a general engineering choice.
W: Deterministic rules plus a light NER model: the fixed formats are matched cheaply and reliably, and only names need the slower model, which keeps the added latency small while closing the structured-data gap.
X: B=Second LLM per request: it adds a full model call to every request, so latency and cost rise sharply, and its output is not deterministic enough to guarantee masking.
C=Weekly log review: leaks are noticed only after exposure, so it does not mask anything in the request path.
D=Only long inputs: length does not predict whether a message holds a card number; a short message can contain one.
T: Match masking to the data: pattern rules for fixed formats, a small model for names, an LLM only where its cost is justified.
V: Unity Gateway

@ DBX-GAI D5 T5.1 applied tradeoff
S: A gateway in front of an external model provider detects personal data in user messages. The company policy says the data must never leave the workspace, but customers should still receive an answer to their question whenever possible. Which gateway action fits?
A: Block the whole request with an error whenever any personal data is detected
B: Log the personal data to an inference table and still send the original text to the provider
C: Mask the detected spans (replace them with placeholders) and forward the rest of the request
D: Send the request unchanged and rely on the provider's data-retention terms
K: C
G: ## Block versus mask
A PII guardrail can respond to a detection in two main ways:
- **Block**: reject the request or response entirely. It is the safest choice when any exposure is unacceptable, but the user gets no answer and may retry with the same data.
- **Mask**: replace the detected values with placeholders and let the rest through. The user still gets a useful answer and the sensitive values never leave.
Databricks documents guardrails for model traffic as service policies in Unity Gateway. The earlier endpoint-level AI Guardrails (now legacy) had a PII detection setting with exactly these two choices, Block or Mask, plus a Safety option; output guardrails there were not supported for embeddings models or streaming. Gateway logging, such as inference tables, helps verify that the guardrail works.
W: Masking the detected spans: the personal values are replaced before leaving, and the remaining question is still answered, which meets both the policy and the helpfulness goal.
X: A=Block everything: it satisfies the policy but gives no answer whenever any personal data appears, which conflicts with the goal to respond when possible.
B=Log and forward the original: logging records the data but does not stop it leaving; the policy is violated.
D=Retention terms: a contract does not enforce the rule that the data must never leave; masking before sending does.
T: Block when any exposure is unacceptable; mask when the request should still be answered without the sensitive values.
