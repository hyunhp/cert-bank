@ DBX-GAI D1 T1.4 expert use-case
S: A telecom's analytics team works only in SQL. Every night, 2 million new call transcripts must get two columns: `cancel_intent` (true or false) and `competitor` (the competitor the caller names). A compliance note in the data contract says that transcripts naming no competitor must store NULL, never a guessed or placeholder name. A pilot ran two separate `ai_query` passes, one per column, and the finance review rejected it for doubling the model cost. Malformed replies broke the downstream load twice. The job uses a Databricks-hosted foundation model. Which pipeline output definition meets every constraint?
A: One `ai_query` call per row with `responseFormat` set to a JSON schema holding a boolean `cancel_intent` and a nullable `competitor` string field
B: One `ai_query` call per row with `responseFormat` set to `{"type": "json_object"}` and the two field names described only in the prompt text
C: Two `ai_query` calls per row, one for `cancel_intent` and one for `competitor`, each using a JSON schema response format for its single field
D: One `ai_query` call per row with `responseFormat` set to a JSON schema holding a boolean `cancel_intent` and a required non-null `competitor` string
K: A
G: ## Turning the requirement into an output contract
The business need becomes a precise output definition: which fields, which types, and what "no value" looks like. In SQL, `ai_query` takes a `responseFormat` argument for chat foundation models:
- `{"type": "text"}`: free text.
- `{"type": "json_object"}`: some valid JSON, but no guarantee of field names or types.
- `{"type": "json_schema", ...}`: JSON that follows the given schema, including types, required fields and nullable fields.
## The detail that decides
The compliance note requires NULL when no competitor is named. A schema that forces a non-null string pushes the model to invent a value; a nullable field lets it return null honestly. One call returning both fields keeps the cost at one pass.
W: One call with a schema and a nullable competitor: both fields come from a single pass, the schema prevents malformed replies, and null is allowed exactly where the contract demands it.
X: B=json_object with names in the prompt: the reply is valid JSON, but field names and types are not enforced, so the downstream load can still break.
C=Two calls with schemas: output is well formed, but two passes per row is the doubled cost that finance rejected.
D=Schema with a required non-null competitor: one pass and valid JSON, but a non-null string forces a value for transcripts that name no competitor, breaking the NULL rule.
T: Write the output contract as a JSON schema, including nullability, and return all fields from one ai_query pass.

@ DBX-GAI D2 T2.6 expert comparison
S: A team compares two retrievers on 300 labeled questions, each with one relevant chunk. Retriever X: recall@3 0.64, recall@10 0.93, MRR 0.58. Retriever Y: recall@3 0.79, recall@10 0.86, MRR 0.71. The prompt can hold only three chunks. Design 1 sends the top 3 straight to the model. Design 2 retrieves the top 10 and reranks them; a pilot found that the reranker puts the relevant chunk into its top 3 for 95% of questions where that chunk is among the 10 candidates. Rerank latency fits the budget in both designs. Which TWO statements are correct? (Select TWO)
A: In Design 1, retriever Y should be chosen, because only the top three reach the prompt and Y has the higher recall at 3
B: In Design 2, retriever X gives the evidence to the prompt about 88% of the time versus about 82% for retriever Y
C: In Design 1, retriever X should be chosen, because its recall at 10 is higher and the model can infer from fewer chunks
D: In Design 2, retriever Y should be chosen in any case, because its higher MRR carries over unchanged after the reranking step
E: In both designs the choice is the same, because recall at 10 does not matter when only three chunks can reach the prompt
K: A,B
G: ## The metric that matters depends on the pipeline
What reaches the prompt decides the answer. So the relevant metric is "relevant chunk in the final top 3":
- **Design 1 (no reranker)**: the final top 3 is the retriever's top 3, so recall@3 decides: Y 0.79 vs X 0.64.
- **Design 2 (rerank top 10)**: the reranker can only promote chunks that are among its 10 candidates, so the chance is recall@10 x reranker hit rate: X 0.93 x 0.95 = about 0.88; Y 0.86 x 0.95 = about 0.82.
## Lesson
A first-stage retriever feeding a reranker should be judged on recall at the candidate depth; a retriever feeding the prompt directly is judged on recall at the prompt depth and on rank quality (MRR).
W: A=Y for Design 1: with no reranker, recall@3 measures what reaches the prompt, and Y leads 0.79 to 0.64.
B=X for Design 2: the reranker can only promote what is among the 10 candidates, so 0.93 x 0.95 = about 0.88 beats 0.86 x 0.95 = about 0.82.
X: C=X for Design 1: chunks at positions 4 to 10 never reach a three-chunk prompt, so X's recall@10 does not help here.
D=Y for Design 2 by MRR: reranking replaces the first-stage order, so Y's better MRR does not carry over; candidate recall decides.
E=Same choice in both: recall@10 is exactly what bounds Design 2, so the best retriever differs between the designs.
T: Judge a first-stage retriever by recall at the depth the next stage sees: prompt depth without a reranker, candidate depth with one.

The AI Search docs list the requirements for creating an index:

F=Direct Vector Access: it is a different index type that is written through the API rather than synced, so it breaks the managed Delta Sync requirement.

D=Lowercasing: "x200 pro" still differs from `X200-PRO` in case, hyphen and space, so the exact filter still returns nothing.

G: ## Fair comparisons in GenAI evaluation
An evaluation result depends on three things: the **application version** (prompt, model, retrieval), the **dataset** (version), and the **scorers**, including the model that powers an LLM judge. To attribute a score difference to one change, everything else must be identical.
Here two things changed: the prompt and the judge model. A different judge model can score the same answers differently, so the 0.10 gap mixes both effects.
## The fix
Re-run both configurations in one evaluation setup with the same judge model and the same dataset version, then compare per-question results.
W: Judge model differs, so re-run both: the gap mixes prompt and judge effects; running A and B together with identical judges and data isolates the prompt change.
X: B=Same judge names: the judge name is the same, but the model behind it differs, so the scores are not comparable.
C=Compare RelevanceToQuery only: it is an LLM judge too, so its scores also depend on the judge model, and it does not measure correctness, which promotion needs.
D=Production drift: both runs used the same fixed dataset version, so traffic drift cannot explain the difference.
T: Attribute a score change to one variable only when the dataset version and the judges, including their models, are identical.
