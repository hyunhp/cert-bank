@ DBX-GAI D6 T6.1 applied use-case
S: A team must choose one of three foundation models for a support-ticket classifier. All three were run on the same 300 labeled tickets with the same prompt. Model 1: accuracy 95%, p95 latency 4.8 s, cost 9 USD per 1,000 requests. Model 2: accuracy 92%, p95 latency 1.4 s, cost 2 USD per 1,000 requests. Model 3: accuracy 85%, p95 latency 0.8 s, cost 0.60 USD per 1,000 requests. The requirements are accuracy of at least 90%, p95 latency under 2 s, and the lowest cost that satisfies both. Which model should the team select?
A: Model 1, because accuracy is the quality metric that matters most and it has the highest value on the labeled evaluation set
B: Model 2, because it is the only one that meets both the accuracy and the latency threshold, at the lowest cost among those
C: Model 3, because it has the lowest latency and cost, and the accuracy gap can be closed later by lengthening the prompt
D: None of them yet, because a 300-ticket labeled evaluation set is too small to compare models and the team must first collect production data
K: B
G: ## Choosing a model from quantitative metrics
Model selection is a constrained optimization: define the metrics that matter for the use case, set a threshold for each requirement, run every candidate on the same evaluation set with the same prompt and scorers, and pick the cheapest or smallest candidate that clears all thresholds. Typical metrics are task quality (accuracy, F1, groundedness or correctness scores from judges), latency (p95, time to first token), throughput and cost per request or per token.
## Size and architecture
A larger model usually scores higher on quality but costs more and answers slower. If a smaller model already clears the quality bar, the extra size is wasted spend and latency. The decision therefore compares each candidate to the requirements, not to the best number in a single column.
## Names
Databricks serves foundation models through Foundation Model APIs and governs them through Unity Gateway (the exam guide still calls this area AI Gateway). The selection logic is the same for any model.
W: Threshold filtering: Model 2 is the only candidate with accuracy of at least 90% and p95 latency under 2 s, and among the models that pass, it has the lowest cost, so it is the right pick.
X: A=Highest accuracy: Model 1 has the best accuracy but its p95 latency of 4.8 s violates the latency requirement and it is the most expensive, so it fails the stated constraints.
C=Cheapest and fastest: Model 3 falls below the 90% accuracy requirement, and a longer prompt is an untested hope that also raises the token cost, not a measured result.
D=Wait for more data: a labeled evaluation set that is representative is a normal basis for model selection, and the differences here are large against the thresholds, so a decision can be made now and revisited with monitoring.
T: Pick the smallest or cheapest model that clears every quality and latency threshold on the same evaluation set.

S: Four candidate models are being compared for a retrieval-augmented assistant. A colleague proposes to rank them by their public leaderboard average, a second colleague proposes to rank them by parameter count, and a third proposes to compare perplexity numbers that the vendors published. Which approach gives the most trustworthy comparison for this assistant?
A: Rank the candidates by their published perplexity, because a lower perplexity means the model gives better answers on any task
B: Rank the candidates by parameter count, because a larger model has been shown to give better answers for every domain

Numbers published elsewhere answer other questions. Public leaderboards measure general benchmarks, parameter count is a rough proxy for capability and cost, and perplexity values from different vendors depend on tokenizers and test text, so they cannot be compared directly and say little about answer quality in a RAG workflow.
A trustworthy comparison fixes everything except the model: the same evaluation questions that represent the real workload, the same prompt and retrieval, and the same scorers (for example `mlflow.genai.evaluate()` with `Correctness` and `RetrievalGroundedness`). W: Own evaluation set: only a like-for-like run on the assistant's own representative questions with identical prompts and scorers measures the quality, latency and cost that matter for this workload.
X: A=Published perplexity: perplexity depends on the tokenizer and the text it was measured on, so vendor values are not comparable, and a low value does not show that retrieved context is used faithfully.
B=Parameter count: size correlates only loosely with quality on a given domain, and a larger model adds cost and latency that may not be needed.
C=Leaderboard average: general benchmarks do not cover the private documents and question styles of this assistant, so the ranking can differ from results on the real workload.

@ DBX-GAI D6 T6.1 advanced use-case
S: A contract-summarization app is evaluated with ROUGE-L only. The larger of two candidate models scores 0.02 higher, but reviewers who read samples report that it sometimes adds clauses that are not in the source contract. The team wants a quantitative way to include this problem in the model choice. What should they do?
A: Keep ROUGE-L, add a groundedness judge that scores every summary against its source, then compare the models on quality, latency and cost
B: Replace ROUGE-L with the model's perplexity on the contracts, because perplexity measures whether the summary stays true to the source
C: Choose the larger model, because a higher overlap score is direct evidence that no clause is added
D: Raise the sampling temperature for both models and rerun ROUGE-L, because a more varied output exposes the invented clauses
K: A
G: ## Overlap metrics are not faithfulness metrics
ROUGE-style metrics count n-gram overlap with a reference. They reward similar wording but cannot see whether a sentence is supported by the source text, and a summary can add an invented clause and still overlap well. To quantify hallucination you need a metric that compares output with the source, such as a groundedness or faithfulness judge. In MLflow, `RetrievalGroundedness` checks whether a response is grounded in the context provided, and a custom LLM judge can encode a source-faithfulness rubric for summaries.
Combine the quality metrics with latency and cost, and pick the model that meets the requirement set, not the model with the highest value in one column.
W: Add a faithfulness metric: scoring each summary against its source quantifies the invented-clause problem on the whole evaluation set, and it can be weighed next to ROUGE-L, latency and cost.
X: B=Perplexity: perplexity is how surprised a model is by a text, it is not a measure of whether a generated summary is supported by the source.
C=Trust the higher overlap: overlap with a reference does not exclude extra claims, and the reviewers have already shown that extra claims occur.
D=Higher temperature: more randomness makes outputs less predictable and typically adds unsupported content, it does not give a reliable measure of how often invention occurs.
T: When overlap scores hide hallucination, add a groundedness metric and decide on all metrics together.

@ DBX-GAI D6 T6.2 applied use-case
S: A streaming chat assistant runs on a Databricks serving endpoint. Users say that replies feel slow and that some requests fail at busy hours. Which set of metrics should the team watch to detect this kind of service degradation?
A: Training loss and validation perplexity from the original fine-tuning run, plotted for every model release

G: ## Metrics for a deployed LLM
Monitoring splits into three families:
- **Operational health**: latency percentiles (p50, p95, p99), time to first token or first byte for streaming, throughput, request rate, error rate and throttling (HTTP 429).
- **Cost**: input and output tokens per request, tokens per user or team.
- **Quality and safety**: groundedness, relevance, correctness, safety or user feedback on a sample of live traffic.
Slow replies and failures at busy hours are operational symptoms, so latency, errors and request volume are the right start. B=Retrieval build settings: embedding size, index size and overlap describe how the index was built, they do not measure how the endpoint behaves under load.
D=Design-time prompt properties: template length and few-shot count are static configuration, so they cannot reveal degradation that appears only at busy hours.

@ DBX-GAI D6 T6.3 applied troubleshooting
S: An agent answers correctly, but users complain that it takes far too long. The agent uses a retriever, one tool call and two model calls. It is instrumented with MLflow tracing. How can the team find which step is responsible for the delay?
A: Run the Safety judge on the slow requests, because slow answers are usually unsafe answers
B: Run the Correctness judge on the slow requests and compare each answer with its expected answer

G: ## What a trace records
MLflow Tracing records the inputs, outputs, latency, token usage and cost of every intermediate step in an agent: model calls, retrieval, tool calls and sub-agents. Each step is a span in a tree, so the trace of a slow request shows how the total time splits across steps. Retriever spans are shown as documents, and span inputs and outputs allow root-cause analysis.
Judges and scorers answer quality questions (is it correct, safe, grounded?). Latency is a property of the trace itself. A scorer can also read trace data, but the first diagnostic step is to read the span timings.

@ DBX-GAI D6 T6.3 applied use-case

```
mlflow.genai.evaluate(data=eval_dataset, predict_fn=agent_v1,
```

What should they run?

@ DBX-GAI D6 T6.8 advanced troubleshooting
S: A model service on Unity Gateway has a service-level limit and a default per-user limit. A nightly batch job runs as a service principal with its own generous custom limit, yet it receives HTTP 429 responses. At the same time other users report errors. What best explains this?
A: The custom limit of the service principal is ignored for batch jobs, so only the default per-user limit applies to it
B: The service-level limit was reached by combined traffic, which blocks all requests regardless of user or group limits
C: HTTP 429 is returned only for authentication failures, so the service principal has lost its permission
D: Custom limits apply only to groups and not to service principals, so the job falls into a group limit
K: B
G: ## How rate limits combine
Rate limits can be set on the **service** (all traffic), as a **default per user**, and as **custom** limits for individual users or service principals or for groups. Key rules:
- The service limit is a global maximum: if it is exceeded, all requests are blocked, regardless of user or group limits.
- A custom limit overrides the default per-user limit, and a user-specific limit wins over a group limit.
- If a request limit and a token limit both exist, the more restrictive applies.
- An exceeded limit returns HTTP 429, so clients should retry with exponential backoff.
So the fix is to raise the service limit or spread the load, and to add retry logic to the batch job.
W: Service limit reached: the aggregate traffic exhausted the service-wide limit, which blocks everyone, including a principal with a high personal limit.
X: A=Custom limit ignored: custom limits for users and service principals take priority over the default per-user limit.
C=429 as authentication: a 429 means too many requests, and authentication problems return other status codes.
D=Groups only: custom limits can target individual users or service principals as well as groups.
T: The service-level limit overrides every user limit, so total traffic can throttle even a privileged caller.

Code-based scorers are Python functions used when built-in or custom LLM judges do not fit, for example for a deterministic heuristic, format validation or exact matching. The recommended definition is the `@scorer` decorator (a function taking arguments such as `inputs`, `outputs`, `expectations` or `trace`).
