@ VLT-VA003 D2 T2.1 applied definition
S: A new policy named `empty-reader` is written with no `path` stanzas at all and attached to a user's token. Which statement about that token is accurate?
A: It can use any path that no policy explicitly denies, because policies only list the exceptions
B: It can read paths under `secret/` only, because that mount is the default target for policies
C: It gets no permissions from this policy, because Vault policies are deny by default
D: It is rejected at login, because Vault refuses to attach a policy that contains no rules
K: C
G: ## Deny by default
Everything in Vault is path-based, and a policy is a list of statements saying which operations are allowed on which paths. Vault starts from "no access": a request is permitted only when some policy attached to the token has a matching `path` stanza that lists the needed capability.
- A policy with no stanzas adds nothing, so on its own it grants nothing.
- Writing a rule is therefore always an act of granting access; there is no implicit "allow everything except".
- The `deny` capability exists only to carve exceptions out of a broad grant.
The token above may still hold the `default` policy, which gives basic abilities such as looking up itself, but `empty-reader` contributes no permissions.
W: Deny by default: access exists only where a stanza grants it, and a policy without stanzas grants none, so the token gains nothing from it.
X: A=Allow unless denied: that is the opposite model; Vault never treats unlisted paths as open.
B=Default mount: policies have no default target path; every stanza names its own path, and nothing grants `secret/` by implication.
D=Rejected at login: an empty policy is valid and can be attached; it is simply harmless, so no login error occurs.
T: Vault policies are deny by default, so an empty policy grants no permission.

@ VLT-VA003 D2 T2.1 applied use-case
S: A token carries only a policy containing `path "secret/data/app1/*" { capabilities = ["read"] }`. The holder runs `vault kv get secret/app2/db` against a KV v2 mount at `secret/`. What happens?
A: The request is denied, because no stanza in the token's policies matches the path that is requested
B: The request succeeds, because read on one application path implies read on sibling application paths
C: The request succeeds, but the returned fields are redacted until a second policy approves them
D: The request is denied, but only after Vault asks the auth method to re-evaluate the token
K: A
G: ## How Vault evaluates a request
For every request Vault builds the token's ACL from all its policies, finds the stanza that best matches the request path, and checks whether the stanza lists the capability the operation needs.
- No matching stanza means no capability, and the response is `permission denied` (HTTP 403).
- Matching is on the path of the request. With KV v2 the CLI command `vault kv get secret/app2/db` is sent to `secret/data/app2/db`, which is outside `secret/data/app1/*` in any case.
Policies are evaluated by Vault itself; the auth method is only consulted at login.
W: No matching stanza: the requested path is outside the one granted, so the deny-by-default rule produces permission denied.
X: B=Implied sibling access: there is no inheritance between sibling paths; the glob stops at its own prefix.
C=Redaction: Vault has no approval step or partial redaction for ACL policies; a request is allowed or denied as a whole.
D=Re-evaluation by the auth method: authorization decisions are made by Vault policies at request time; the auth method is not asked again.
T: With no matching path stanza a request is denied, and sibling paths are not covered by a neighbor's rule.

@ VLT-VA003 D2 T2.1 applied tradeoff
S: A CI job must read a single database password stored at `secret/data/ci/db` in a KV v2 mount. Which policy follows the principle of least privilege?
A: Read, list and update on `secret/data/ci/*` so the job can also rotate the password
B: Read on `secret/data/ci/db`, the only path and capability the job needs
C: Read and list on `secret/*` so the job keeps working if the secret moves
D: Read and sudo on `secret/data/ci/db` so the job is never blocked by protection rules
K: B
G: ## Least privilege in practice
Least privilege means granting the narrowest paths and the fewest capabilities that let a workload do its job.
- Prefer an exact path to a glob when only one secret is involved.
- Add a capability only when an operation requires it: `read` to fetch, `list` to enumerate, `update` or `create` to write.
- `sudo` is for root-protected endpoints such as audit device management; a KV read never needs it.
A broad policy is convenient, but a leaked CI token then exposes everything that policy covers.
W: Exact read: the job reads one secret, so a single stanza with `read` on that exact path gives it what it needs and nothing else.
X: A=Wider grant: update and list on the whole `ci/` prefix let a compromised job overwrite the password or enumerate neighbors, which the requirement never asked for.
C=Whole mount: read on `secret/*` would expose every secret in the mount, and it would not even match the v2 `data/` paths correctly.
D=Extra sudo: `sudo` only matters on root-protected paths; adding it widens the policy without helping a KV read.
T: Least privilege means the exact path and only the capabilities the workload uses.

@ VLT-VA003 D2 T2.1 applied comparison
S: Which TWO statements about how Vault policies relate to tokens are accurate? (Select TWO)
A: A token refers to its policies by name, so changing a policy's rules affects existing tokens the next time they are used
B: Logging in a second time invalidates the first token, so a user holds only one valid token at a time
C: Vault keeps a copy of the corporate directory so that group membership can be mapped to policies without a lookup
D: Policies are attached when a token is created, so changing a token's policy set means obtaining a new token
E: Policies must be written in HCL, and a JSON policy document is rejected when it is uploaded
K: A,D
G: ## Policies, names and tokens
A policy is stored in Vault under a name, and that name works like a symlink to its rules. Auth methods map identities (such as an LDAP group) to policy names, and the token created at login carries those names.
- The rules are read when the token is used, so an edited policy takes effect on the next request without re-login.
- The list of names is fixed at creation. Vault documents no way to change it afterwards: revoke the token and get a new one.
- Authenticating again returns a new token with the same permissions; the earlier token keeps working until it expires or is revoked.
- Policies can be written in HCL or JSON.
W: A=Name reference: tokens store the policy name, and the rules are parsed at use time, so edits apply immediately.
D=Fixed at creation: a token's policy list cannot be edited in place; revoke it and obtain a new one.
X: B=Single token: a second login produces another token and does not invalidate the first.
C=Directory copy: Vault delegates authentication to the auth method and does not store a copy of the LDAP database.
E=HCL only: Vault accepts policies written in either HCL or JSON, so a JSON document uploads without any rejection.
T: Tokens carry policy names fixed at creation, while policy contents are evaluated live on each request.

@ VLT-VA003 D2 T2.2 applied definition
S: A policy contains `path "secret/foo" { capabilities = ["read"] }` on a KV v1 mount at `secret/`. Which request does it permit?
A: Reading `secret/food`, because the path is matched as a prefix
B: Reading `secret/foo/bar`, because child paths inherit the capability
C: Writing a new value to `secret/foo`, because read implies write on that key
D: Reading `secret/foo`, because the stanza names that exact path
K: D
G: ## Exact paths versus globs
A `path` without a trailing `*` is an exact match.
- `path "secret/foo"` matches only `secret/foo`: not `secret/food`, not `secret/foo/bar`.
- `path "secret/foo*"` would instead be a prefix match, because a trailing `*` is a glob.
Capabilities are separate for every operation: `read` lets you fetch data, but changing it needs `create` or `update`, and removing it needs `delete`.
W: Exact path: with no glob, the stanza applies to the single path `secret/foo`, and read is the only operation it grants.
X: A=Prefix match: only a trailing `*` makes a prefix; without it `secret/food` does not match.
B=Child inheritance: Vault paths are not inherited by children, so `secret/foo/bar` needs its own stanza or a glob such as `secret/foo/*`.
C=Read implies write: capabilities are independent, so writing would need `create` or `update`.
T: A path with no `*` matches exactly one path, and each capability must be granted explicitly.

@ VLT-VA003 D2 T2.2 applied comparison
S: A policy grants read with `path "secret/bar/*"`. Which of these requests would it still NOT cover?
A: Reading `secret/bar/zip`, because only direct children match
B: Reading `secret/bar/zip/zap`, because the glob stops at one segment
C: Reading `secret/bars/zip`, because the prefix ends with a slash
D: Reading `secret/bar/zip/zap/zong`, because depth is capped at three
K: C
G: ## What the glob does
A trailing `*` turns the path into a prefix match. For `secret/bar/*`, the prefix is `secret/bar/`, including the trailing slash.
- `secret/bar/zip` matches.
- `secret/bar/zip/zap` matches, since a glob is not limited to one segment (that is what `+` is for).
- `secret/bars/zip` does not match, because it does not begin with `secret/bar/`.
The glob is not a regular expression and is only supported as the last character of the path.
W: Different prefix: `secret/bars/zip` does not begin with `secret/bar/`, so the stanza does not cover it.
X: A=Direct children only: the glob matches any depth under the prefix, so the child is covered, and the claim of a one-level limit is wrong.
B=One segment: crossing several segments is exactly what a trailing `*` allows; the single-segment wildcard is `+`.
D=Depth cap: there is no maximum depth for a glob, so deep paths are covered as well.
T: A trailing `*` matches everything beginning with the prefix, at any depth, but nothing outside it.

@ VLT-VA003 D2 T2.2 applied use-case
S: A team wants to read the `teamb` secret under any single application folder, as in `path "secret/+/teamb"`. Which request matches this stanza?
A: Reading `secret/alpha/beta/teamb`, because `+` spans any number of segments
B: Reading `secret/teamb`, because `+` can stand for an empty segment
C: Reading `secret/alpha/teamb/notes`, because the stanza acts as a prefix
D: Reading `secret/alpha/teamb`, because `+` fills exactly one segment
K: D
G: ## The `+` segment wildcard
`+` replaces any characters bounded within a single path segment (supported since Vault 1.1).
- `secret/+/teamb` matches `secret/alpha/teamb` and `secret/billing/teamb`.
- It does not match `secret/alpha/beta/teamb` (two segments); use `secret/+/+/teamb` for that.
- It does not match `secret/teamb`, because one segment is required in its place.
- With no trailing `*`, the end of the path is exact, so `secret/alpha/teamb/notes` is not covered.
W: One segment: `+` fills exactly one segment and the rest is literal, so `secret/alpha/teamb` is the only listed path that fits.
X: A=Any number of segments: spanning several segments is the job of the trailing glob, while `+` is limited to one, so the extra level does not fit.
B=Empty segment: the pattern requires a segment between `secret/` and `teamb`, so `secret/teamb` does not match.
C=Prefix behavior: only a trailing `*` makes a stanza a prefix; this one ends exactly at `teamb`.
T: `+` stands for exactly one path segment anywhere in the path, while `*` is a prefix glob only at the end.

@ VLT-VA003 D2 T2.2 applied troubleshooting
S: A policy author wrote `path "secret/data/*/config"` so that every application can read its own `config` secret, but requests are denied. What is the accurate diagnosis and fix?
A: A glob is supported only as the last character of a path, so `+` should replace the middle `*`
B: The policy must be written in JSON because HCL does not allow wildcards in the middle of a path
C: The `list` capability is missing, and adding it will make the middle `*` expand to each folder
D: The path needs a second trailing `*` after `config`, which turns the middle one into a wildcard
K: A
G: ## Where `*` and `+` are allowed
Vault documents the asterisk as "not a regular expression" and "only supported as the last character of the path". It is not a wildcard in the middle of a path.
- To match one segment in the middle, use `+`: `secret/data/+/config`.
- Combine both when needed: `secret/data/+/config/*` matches anything under each application's `config/` prefix.
Denials with a path that looks right are often a pattern that never matches the path being requested; `vault token capabilities <token> <path>` shows the capabilities Vault computes.
W: Glob placement: `*` works only at the end, so `secret/data/+/config` is the correct way to match one folder name in the middle.
X: B=JSON requirement: HCL and JSON are interchangeable here, so changing the syntax would not change what a pattern matches.
C=Missing list: listing is unrelated to how the pattern expands; a read of a specific secret needs `read`, and no capability makes a middle `*` a wildcard.
D=Second trailing glob: a trailing `*` after `config` would extend the prefix, and the one in the middle would still not become a wildcard.
T: `*` is only a trailing glob; use `+` to match a single segment in the middle of a path.

@ VLT-VA003 D2 T2.2 applied use-case
S: An application uses `vault kv get secret/app/db` on a KV v2 mount named `secret`. Which stanza lets it succeed, and nothing more?
A: `path "secret/app/db" { capabilities = ["read"] }`
B: `path "secret/metadata/app/db" { capabilities = ["read"] }`
C: `path "secret/data/app/db" { capabilities = ["read"] }`
D: `path "secret/data/app/db" { capabilities = ["list"] }`
K: C
G: ## KV v2 has data and metadata paths
A KV v2 mount keeps versions of every secret, and its API puts different operations under different prefixes:
- `secret/data/<path>`: read (GET) fetches a version, create/update (POST) writes a new one, patch (PATCH) merges fields, delete (DELETE) soft-deletes the latest version.
- `secret/metadata/<path>`: list (LIST) enumerates keys, read (GET) returns version metadata, delete removes the key and all versions permanently.
- `secret/delete/`, `secret/undelete/` and `secret/destroy/` act on specific versions.
The CLI hides this: `vault kv get secret/app/db` sends a GET to `secret/data/app/db`, so the policy must name the `data/` path.
W: Data path: the CLI request is a GET on `secret/data/app/db`, so `read` on that exact path is the minimum that works.
X: A=Missing data segment: the stanza names `secret/app/db`, which is how a v1 mount looks; on KV v2 the request path contains `data/`, so it never matches.
B=Metadata path: read here returns version information about the key, not the secret values.
D=List capability: list belongs to key enumeration under `metadata/`, and a GET on a data path needs `read`.
T: On KV v2, secret values are read through `secret/data/...` and key listing and metadata through `secret/metadata/...`.

@ VLT-VA003 D2 T2.2 applied use-case
S: Operators run `vault kv list secret/apps` on a KV v2 mount named `secret` to enumerate the application keys. Which stanza grants that?
A: `path "secret/data/apps/*" { capabilities = ["list"] }`
B: `path "secret/metadata/apps/*" { capabilities = ["read"] }`
C: `path "secret/list/apps/*" { capabilities = ["list"] }`
D: `path "secret/metadata/apps/*" { capabilities = ["list"] }`
K: D
G: ## Listing in KV v2
Listing sends a `LIST` request to `secret/metadata/<path>` on a v2 mount, so the policy needs the `list` capability on a `metadata/` path.
- Listing always works on a prefix, and Vault sanitizes the request path to a prefix, so the stanza is written as a prefix such as `secret/metadata/apps/*`.
- `read` on a metadata path returns details of one key; it does not allow enumerating keys.
- The keys returned by a list are not filtered by policy, so key names should never hold sensitive information.
W: Metadata list: `list` on the `metadata/` prefix is what Vault checks for a KV v2 listing.
X: A=Data prefix: `data/` holds secret values; a LIST request is never sent there, so list on it does not help.
B=Read only: read on metadata returns key information but does not authorize enumerating keys.
C=Invented path: a KV v2 mount has no `list/` prefix; the paths are `data`, `metadata`, `delete`, `undelete`, `destroy` and a few others.
T: KV v2 listing needs `list` on `secret/metadata/...`, and reading values needs `read` on `secret/data/...`.

@ VLT-VA003 D2 T2.2 applied comparison
S: Which TWO statements about KV v2 policy paths are accurate? (Select TWO)
A: Reading and writing secret versions are authorized on paths that start with `secret/data/`
B: Listing keys and reading version metadata are authorized on paths that start with `secret/metadata/`
C: A stanza on `secret/app/*` protects KV v2 secrets exactly as it would on a KV v1 mount
D: Permanently destroying specific versions is authorized with the `delete` capability on `secret/data/`

G: ## Mapping KV v2 operations to paths
A KV v2 mount named `secret` exposes:
- `secret/data/<path>`: GET read, POST create/update, PATCH patch, DELETE soft-delete of the latest version.
- `secret/metadata/<path>`: LIST list, GET read metadata, POST/PATCH update metadata, DELETE remove all versions and metadata.

W: A=Data prefix: values and versions are read and written through `secret/data/`.

E=Sudo for metadata: these are ordinary paths protected by ordinary capabilities, not root-protected endpoints.
T: KV v2 splits access between `data/` for values and `metadata/` for keys, with separate paths for delete, undelete and destroy.

@ VLT-VA003 D2 T2.2 applied use-case
S: A cleanup role must permanently remove one KV v2 secret, `secret/app/db`, including all versions and its metadata, e.g. with `vault kv metadata delete secret/app/db`. Which stanza grants only that?
A: `path "secret/data/app/db" { capabilities = ["delete"] }`
B: `path "secret/destroy/app/db" { capabilities = ["update"] }`
C: `path "secret/metadata/app/db" { capabilities = ["delete"] }`
D: `path "secret/undelete/app/db" { capabilities = ["update"] }`
K: C
G: ## Soft delete, destroy and metadata delete
KV v2 distinguishes several removal operations, each with its own path:
- `DELETE secret/data/<path>`: soft-deletes the latest version; it can be restored.
- `POST secret/delete/<path>` and `POST secret/undelete/<path>`: soft-delete or restore chosen versions.
- `PUT secret/destroy/<path>`: permanently removes chosen versions; the key and its metadata remain.
- `DELETE secret/metadata/<path>`: permanently removes the key, all versions and its metadata.
PUT and POST map to the `update` capability, DELETE maps to `delete`.
W: Metadata delete: the command sends a DELETE to the `metadata/` path, which needs `delete` there and erases all versions.
X: A=Data delete: that only soft-deletes the latest version, which can be restored, so history and metadata remain.
B=Destroy path: destroy permanently removes specific versions, but the key's metadata stays, and it uses `update` rather than `delete`.
D=Undelete path: undelete restores soft-deleted versions, the opposite of what the role must do.
T: Permanent removal of a whole KV v2 secret is a DELETE on the `metadata/` path, so grant `delete` there.

@ VLT-VA003 D2 T2.3 applied definition

Policy capabilities map to the HTTP verb of the request, not to what the backend does internally.

@ VLT-VA003 D2 T2.3 applied troubleshooting

W: Sudo: enabling an audit device is a root-protected POST, which needs `sudo` together with the capabilities already granted.

@ VLT-VA003 D2 T2.3 applied use-case
S: An integration partially updates one field of an existing KV v2 secret with an HTTP PATCH to `secret/data/app/db`, and must not be able to replace the whole secret. Which capability on that path fits?

D: `patch`, because it allows partial updates only

- `update` (POST/PUT) changes the data at a path, and for KV v2 it writes a complete new version.
- `patch` (PATCH) allows partial updates: only the supplied fields are merged into the existing data.
Giving an integration `patch` without `update` lets it adjust fields but not rewrite everything, which keeps a compromised integration from replacing an entire secret.
For the same mount, `read` is a separate grant: an integration that only patches does not need it.
W: Patch: the HTTP PATCH verb maps to the `patch` capability, which is the narrowest grant for merging fields.
X: A=Update: that would authorize POST/PUT, which can write a complete replacement version, more than the requirement allows.
B=Create: it covers writing data where nothing exists yet, not merging into an existing secret.
C=Sudo: partial writes are not root-protected, so `sudo` adds privilege without enabling the PATCH.
T: The `patch` capability allows partial updates only, which is narrower than `update`.

@ VLT-VA003 D2 T2.4 applied comparison
S: A token holds two policies. The first has `path "secret/data/app/*" { capabilities = ["read"] }` and the second has the identical path with `capabilities = ["create", "update"]`. What can the token do on `secret/data/app/x`?
A: Only read, because the first policy attached to the token is the one that wins
B: Only create and update, because the most recently written policy replaces the earlier one
C: Read, create and update, because the same pattern in several policies is combined as a union
D: Nothing at all, because two policies that disagree on a path cancel each other out
K: C
G: ## Same pattern in several policies
A token's ACL is built from all attached policies. When the same path pattern appears more than once, Vault takes the union of the capabilities.
- Policy one gives `read`; policy two gives `create` and `update`; for `secret/data/app/*` the token holds all three.
- Attachment order and write time do not matter.
- The exception is `deny`: if any policy lists `deny` on that same pattern, the result is no access.
This makes policies additive, so splitting duties across several small policies is safe.
W: Union: identical patterns merge their capabilities, giving read, create and update.
X: A=First wins: a token's policies have no ordering, so the one attached first has no priority over the second one.
B=Latest wins: policies are not replaced by each other; the token carries all of them.
D=Cancel out: disagreement does not subtract; only an explicit `deny` removes access.
T: The same path pattern in multiple policies results in the union of capabilities, unless one policy denies.

@ VLT-VA003 D2 T2.4 advanced comparison
S: A token holds one policy granting read and update on `secret/data/*` and another granting only read on the more specific `secret/data/app/*`. Which statement about an update to `secret/data/app/x` is accurate?
A: It is allowed, because the broader policy grants update and Vault merges capabilities from all matches
B: It is denied, because only the highest-priority matching pattern applies and it grants no update
C: It is allowed, because update is granted by at least one attached policy and read does not forbid it
D: It is denied, because a token cannot hold two policies that both match one request path
K: B
G: ## Different patterns: the most specific one wins
Union applies only to the same pattern. When different patterns in the token's policies match a request, Vault uses only the highest-priority match; capabilities of lower-priority matches are ignored.
Priority rules for two matching paths P1 and P2 (P1 is lower priority if):
- its first wildcard (`+`) or glob (`*`) occurs earlier;
- it ends in `*` and the other does not;
- it has more `+` segments;
- it is shorter;
- it is smaller lexicographically.
Here `secret/data/app/*` is longer than `secret/data/*`, so it wins, and its capability list contains only `read`.
To allow an update, the specific stanza must list it.
W: Highest priority only: the specific pattern wins and lists only read, so the update is denied.
X: A=Merging across patterns: merging happens only for identical patterns; for different ones the lower-priority stanza is ignored.
C=Any policy grants: capabilities are not checked policy by policy; the single matching stanza decides.
D=Conflicting policies: a token may hold many policies with overlapping paths; Vault resolves overlaps by priority.
T: Identical patterns are merged, but for different patterns only the most specific match applies.

G: ## Deny always wins
`deny` disallows access and takes precedence regardless of any other capabilities defined for the path, including `sudo`. When the same pattern appears in two policies, the union of capabilities contains `deny`, which cancels the result.
- Use it to carve an exception out of a broad grant, such as a global `secret/*` policy with `deny` on a specific sensitive path.
- A separate "block" policy is a convenient way to remove access from selected users without editing a shared policy.
- Because a token's policy list is fixed, removing a deny means editing the policy or getting a new token.
W: Deny precedence: any `deny` on the matched pattern overrides all grants for it, so the read fails.
X: A=Grant first: there is no grants-before-denials order; deny wins on the path no matter which policy lists it.
B=Sudo rescue: `sudo` does not override deny, which is explicitly stronger.
C=Group-only: deny applies the same way no matter how a policy was attached to the token.
