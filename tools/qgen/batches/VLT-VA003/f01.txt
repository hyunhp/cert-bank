S: A script calls `POST /sys/leases/revoke-prefix/database/creds` and gets a success response, but a few database users still exist a moment later. Which behavior explains this?
A: Revocations are queued by default, and setting `sync=true` makes the call return when they are done
B: Revoke-prefix handles a fixed batch of one hundred leases per call, so the rest need another call
C: Revoke-prefix marks the leases as expired, and Vault drops the users when their original TTL ends
D: A success response confirms that the prefix exists in Vault, and revocation is a separate request
K: A
G: ## Queued revocation
Both `revoke` and `revoke-prefix` accept `sync` (default false). By default Vault queues the revocations and works through them in the background. With `sync=true` (CLI `-sync`) the call returns only after revocation is complete.
- Use sync when a script must know the credentials are gone before it continues.
- The queue is an implementation detail; revocation still happens promptly.
W: Queued by default: the response confirms acceptance, so some users briefly remain until the queue drains; `sync=true` makes the call wait for completion.
X: B=Hundred-lease batch: the API reference documents no per-call limit on how many leases a prefix revocation handles.
C=Waits for the TTL: revoke acts immediately, not at the end of the TTL.
D=Prefix check only: the call does perform real revocation of the leases it finds; it does not merely test whether the prefix exists.
T: Revocation is queued unless `sync=true`/`-sync` is set.

@ VLT-VA003 D8 T8.3 applied use-case
S: An operator runs `vault operator init -key-shares=5 -key-threshold=3` on a new self-managed cluster with a Shamir seal. Two of the five key holders leave the company. Can the cluster still be unsealed?
A: No, because the unseal key is rebuilt from the full set of five shares created at initialization
B: No, because the threshold counts shares held by the original group of five named key holders
C: Yes, once the two missing shares have been regenerated with a command run on an unsealed node
D: Yes, because three remaining holders meet the threshold, whatever order they enter shares in
K: D
G: ## Shamir's Secret Sharing
With the default seal, Vault splits the unseal key into shares using Shamir's Secret Sharing. `-key-shares` sets how many shares are produced; `-key-threshold` sets how many are needed to rebuild the key (defaults 5 and 3, and the threshold must not exceed the shares).
- Any threshold-sized subset works, in any order.
- Fewer than the threshold reveal nothing about the key.
- Holders can enter their shares from different machines, because the unseal process is stateful.
## Operational lesson
Losing shares is tolerable up to `shares - threshold` of them (here 2). Past that, the cluster cannot be unsealed; plan a rekey (`vault operator rekey`) when holders leave, while the threshold is still met.
W: Threshold of three: three holders remain, which meets the threshold, and the order they enter shares in does not matter.
X: A=Full set of five: that would make the threshold equal to the shares. The threshold of three is chosen exactly so that some shares can be lost.
B=Original named holders: the shares are numbers, not identities; any holder of three valid shares can contribute them.
C=Regeneration first: no regeneration is needed here, and a sealed Vault cannot run such operations anyway. Rekeying is a separate, planned operation.
T: Any threshold-sized subset of Shamir shares unseals, so up to shares minus threshold can be lost.

@ VLT-VA003 D8 T8.3 applied troubleshooting
S: Two key holders leave a company that runs a Shamir-sealed cluster with five shares and a threshold of three. Which TWO statements about rekeying the unseal key with `vault operator rekey` are accurate? (Select TWO)
A: It is authorized by submitting the current threshold number of unseal key shares from existing holders
B: The cluster has to be sealed first, because new shares are not created while the data is readable
C: The old shares keep working next to the new ones until the nodes of the cluster are restarted
D: It can set a new share count and threshold, and the new shares can be handed to different holders
E: It re-encrypts the secrets in the storage backend, so its duration grows with the size of the data
K: A,D
G: ## Rekeying Shamir unseal keys
`vault operator rekey` (or the matching `sys/rekey` API) replaces the set of unseal key shares with a new one. It runs against an unsealed Vault and is authorized when the threshold of current unseal keys is provided. You can pick a new `-key-shares` and `-key-threshold` and, optionally, PGP keys to encrypt each new share.
- Use it when key holders leave or when the split must change.
- After it completes, the old shares are no longer valid.
- Only the root key is re-encrypted with the new unseal key; the stored data is not rewritten.
With auto-unseal the equivalent for the recovery key is `-target=recovery`.
W: A=Threshold authorizes: the current threshold of shares proves quorum before new shares are issued.
D=New split: the operator chooses a new number of shares and threshold, which allows handing shares to different holders.
X: B=Sealed first: rekey runs on an unsealed Vault; sealing is not needed to create new shares.
C=Old shares until restart: once rekeyed, the old shares are replaced and are no longer valid.
E=Re-encrypts stored secrets: the new unseal key protects the root key; the stored secrets are not rewritten, so data size does not matter.
T: Rekeying issues a new set of unseal shares, authorized by the current threshold, when holders change.
