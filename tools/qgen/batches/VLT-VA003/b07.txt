@ VLT-VA003 D7 T7.1 applied definition
S: A new engineer asks how Vault protects the data it writes to storage. Which statement about the key chain is accurate?
A: The unseal key encrypts the root key, the root key encrypts the encryption key, and the encryption key encrypts the stored data
B: The unseal key encrypts the stored data directly, and the root key is only used to sign tokens that clients present to Vault
C: The root key encrypts the stored data, and the unseal key is a copy of the root key that is kept in the storage backend
D: The encryption key encrypts the root key, the root key encrypts the unseal key, and the unseal key encrypts each secret
K: A
G: ## The key chain
Vault never writes plaintext to its storage backend. Three layers of keys stand between an operator and a stored secret.
- The **encryption key** (kept in the keyring) encrypts almost all data Vault stores.
- The **root key** encrypts the encryption key. The encrypted encryption key is stored alongside the data.
- The **unseal key** encrypts the root key. With the default Shamir seal the unseal key is itself split into shares, so no single person holds it.
Unsealing means working back up this chain: shares become the unseal key, the unseal key decrypts the root key, the root key decrypts the encryption key.
## Why layers?
Changing the outer layer (rekeying) is cheap because only a small key has to be re-encrypted, not all stored data.
W: Correct order: the unseal key protects the root key, the root key protects the encryption key, and the encryption key protects the data, which matches the documented chain.
X: B=Unseal key encrypts data: the unseal key never touches stored data, it only decrypts the root key, and the root key does not sign tokens.
C=Root key encrypts data: the root key protects only the encryption key, and the unseal key is not a copy of it; the stored root key is encrypted by the unseal key.
D=Reversed chain: protection runs from the outer unseal key inward; a key never encrypts the key that protects it.
T: Unseal key (or its shares) decrypts the root key, the root key decrypts the encryption key, the encryption key protects data.

@ VLT-VA003 D7 T7.1 applied comparison
S: A security reviewer asks what the Vault security barrier does for data on its way to the storage backend. Which statement is accurate?
A: It encrypts every object with AES-256-GCM before it leaves Vault and checks the authentication tag when the object is read back
B: It encrypts only values marked as sensitive by the secrets engine and leaves path names and policies in plaintext in storage
C: It relies on the storage backend to encrypt data at rest, and adds TLS only between Vault and the backend
D: It hashes each object with SHA-256 before writing it, so a modified object is detected but its content is stored readable
K: A
G: ## The security barrier
Vault treats its storage backend as untrusted. Everything Vault writes passes through the **security barrier**, which encrypts data with 256-bit AES in Galois/Counter Mode (GCM) with 96-bit nonces. A new random nonce is generated for every encrypted object.
When data is read back, the GCM authentication tag is verified during decryption. If someone modified the stored bytes, verification fails and Vault aborts the transaction, so tampering is detected as well as hidden.
- Encryption applies to all data leaving Vault, not only secret values.
- TLS to the backend is an extra layer where the backend supports it, not a replacement.
W: Barrier behavior: AES-256-GCM encrypts every object before it reaches storage and the authentication tag check on read detects tampering.
X: B=Only sensitive values: the barrier encrypts all data leaving Vault, not a selected subset.
C=Backend encryption: storage is untrusted by design, so Vault does its own encryption and does not rely on the backend; TLS is merely optional extra protection.
D=SHA-256 hash only: a hash would detect change but would leave content readable; the barrier provides confidentiality and integrity together.
T: The barrier encrypts everything Vault writes (AES-256-GCM) and verifies the tag on read, so an untrusted backend sees only ciphertext.

@ VLT-VA003 D7 T7.1 advanced use-case
S: An attacker copies a full snapshot of the storage backend files from a stopped Vault node. The attacker has no unseal keys and no Vault token. What can the attacker read?
A: All secrets in plaintext, because the node's storage files are readable with filesystem access
B: Only encrypted data; the encryption key and root key are stored encrypted and cannot be decrypted without the unseal key
C: All secrets in plaintext, once the attacker replays stored token records against the sealed server
D: Only the names of auth methods, because those are intentionally stored unencrypted for use during unseal
K: B
G: ## Untrusted storage
The security model assumes an attacker may read the storage backend. Everything Vault stores is encrypted by the barrier, including the encryption key (encrypted by the root key) and the root key (encrypted by the unseal key). The unseal key is never stored in the clear; with Shamir seals only the operators hold its shares.
## What the model does not promise
Per the threat model, an attacker who reads storage may still learn that secret material exists. Vault also does not defend against memory analysis of a running, unsealed Vault or arbitrary control of the backend (deleting or rolling back data).
W: Ciphertext only: without the unseal key the root key stays encrypted, so the encryption key and all data are unreadable.
X: A=Plaintext files: file access does not help because everything is encrypted before it is written.
C=Replaying tokens: client tokens are stored inside the same encrypted data, and a sealed server answers no login requests anyway.
D=Plaintext mount names: nothing is stored unencrypted for unseal use; Vault holds the data it needs encrypted and requires the keys from operators.
T: A stolen storage snapshot reveals only ciphertext; confidentiality depends on the unseal key staying out of the attacker's hands.

@ VLT-VA003 D7 T7.1 applied definition
S: Which TWO statements about the root key and the encryption key are accurate? (Select TWO)
A: The root key is stored in the storage backend, encrypted by the unseal key
B: The encryption key is kept in the keyring and encrypts most of the data Vault stores

K: A,B
G: ## Keys versus tokens
The names are confusing, so separate three things.
- **Root key**: generated during `vault operator init`. Stored in the storage backend, encrypted by the unseal key. Held in memory while the node is unsealed.
- **Encryption key**: in the keyring, encrypted by the root key and stored with the data. It encrypts the data itself.
- **Initial root token**: a client token with the `root` policy, unrelated to the key chain. It authenticates API requests.
W: A=Root key in storage: init generates it once and keeps it in storage encrypted by the unseal key, so a restart can recover it after unsealing.
B=Encryption key: the keyring holds the key that encrypts almost all data; it is protected by the root key.
X: C=Generated every unseal: the root key is created once at initialization and stored encrypted; unsealing only decrypts it.
D=Shares rebuild encryption key: the shares rebuild the unseal key, which decrypts the root key, not the encryption key directly.
E=Same as root token: the root token is a client credential for API requests and has no role in encrypting data.
T: Shares make the unseal key, which decrypts the stored root key, which decrypts the encryption key; the root token is a separate credential.

@ VLT-VA003 D7 T7.1 applied use-case

A: It is written to a file under the Vault data directory so that a restarted node can read it automatically
B: It exists only in the memory of the unsealed node, and `vault operator seal` discards it from memory
C: It exists in the client token cache at `~/.vault-token` on the machine of the operator who unsealed

After unsealing, Vault holds the plaintext root key in memory so it can decrypt the encryption key and serve requests. It is never stored in plaintext. Sealing deletes it from memory, which blocks all operations until another unseal supplies the shares again.
- Restarting the process also loses the in-memory key.
- The memory of a running unsealed Vault is outside the threat model: an attacker able to inspect it could compromise confidentiality.
W: Memory only: the plaintext root key lives in memory while unsealed, and sealing discards it.
X: A=Written to disk: a plaintext key on disk would defeat the barrier; only the encrypted root key is stored.

D=Always in memory: a sealed node has discarded the key and cannot decrypt anything until it is unsealed again.

@ VLT-VA003 D7 T7.2 applied definition
S: What does `vault operator init` accomplish on a brand-new Vault server?
A: It prepares storage for data, generates the root key, and returns the key shares and an initial root token
B: It unseals the server for the first time, using shares that it reads from the configuration file
C: It creates the first KV secrets engine mount and a policy that grants the operator full access
D: It copies the data of a peer node into the new server so both hold the same secrets
K: A
G: ## Initialization
A new Vault has an empty storage backend. Initialization prepares that storage so it can receive data: Vault generates the root key, stores it encrypted, and splits the unseal key into shares for the operators. The command prints the shares (or recovery keys with auto-unseal) and an initial root token.
- Initialization happens once per cluster, not per node.
- After `init` the server is still sealed until the threshold of shares is supplied.
- The command does not mount secrets engines or write policies.
W: Storage preparation: init sets up storage, generates the root key, and hands operators the key shares and root token.
X: B=Unseal from config: init does not unseal; operators supply shares afterwards, and shares are never kept in a config file.
C=First mount and policy: mounting engines and writing policies require a token and an unsealed Vault, which come after init.
D=Copy a peer: init copies nothing; joining and replicating are separate cluster operations.
T: `vault operator init` readies storage, creates the root key and outputs key shares plus the initial root token, once per cluster.

@ VLT-VA003 D7 T7.2 applied troubleshooting
S: Three Vault servers share one storage backend in an HA cluster. Node 1 was initialized and unsealed. An operator now runs `vault operator init` against node 2. What happens?
A: The command succeeds and generates a second set of key shares that either node can use
B: The command fails because the cluster is already initialized; node 2 only needs to be unsealed
C: The command succeeds only if the operator first runs `vault operator seal` on node 1
D: The command succeeds and replaces the earlier shares, which invalidates the keys of node 1
K: B
G: ## One init per storage backend
Servers in an HA cluster share the same storage backend, so initializing one initializes the storage for all. The `operator init` command cannot be run against an already-initialized cluster.
- Node 2 reports `Initialized true` in `vault status` but remains sealed after a start.
- With Shamir seals, each node must be unsealed separately with the threshold of shares.
Re-initialization would mean new keys, which is why Vault refuses it.
W: Already initialized: init is rejected for an initialized cluster, so node 2 needs only unsealing with the existing shares.
X: A=Second share set: a second set would imply a second root key for the same data, which Vault does not allow.
C=Seal first: sealing does not reset initialization state; it is stored in the shared backend.
D=Replace the shares: init never replaces keys; changing them is done with rekey on an initialized Vault.
T: Initialize once per storage backend; further nodes of the cluster are only unsealed.

@ VLT-VA003 D7 T7.2 applied use-case
S: A provisioning script must decide whether to run `vault operator init` and wants to use only exit codes. Which command and result fit?
A: `vault operator init -status` returns exit code 2 when Vault is not initialized
B: `vault operator init -status` returns exit code 1 when Vault is not initialized
C: `vault status` returns exit code 0 when Vault is not yet initialized
D: `vault operator init -status` returns exit code 0 when Vault is not initialized
K: A
G: ## Checking initialization state
`vault operator init -status` prints the initialization state without changing anything. Its exit codes:
- `0`: Vault is already initialized.
- `1`: an error occurred (for example, the server is unreachable).
- `2`: Vault is not initialized.
A script can run it and call `init` only on exit code 2, treating 1 as a failure to investigate. Note that `vault status` exit codes describe the seal state (0 unsealed, 1 error, 2 sealed), not initialization.
W: Exit code 2: the status flag signals a not-yet-initialized Vault with 2, so the script can branch on it and run init only then.
X: B=Exit code 1: 1 means an error such as an unreachable server, which is a different situation from an uninitialized one.
C=Status exit 0: `vault status` returns 0 only for an unsealed Vault, which an uninitialized server is not.
D=Exit code 0: 0 means already initialized, the opposite result.
T: `operator init -status`: 0 initialized, 2 not initialized, 1 error.

@ VLT-VA003 D7 T7.2 applied definition
S: Which TWO statements about the default behavior of `vault operator init` are accurate? (Select TWO)
A: It splits the unseal key into 5 key shares
B: It requires 3 of the shares to reconstruct the key

D: It prints no root token and expects one to be generated later

G: ## Defaults
Without flags, `vault operator init` uses `-key-shares=5` and `-key-threshold=3`. The threshold must be less than or equal to the number of shares. Shares are printed in plaintext unless `-pgp-keys` is used, and an initial root token is printed unless it is encrypted with `-root-token-pgp-key`.
- Aliases: `-n` for shares, `-t` for threshold.
- With auto-unseal, `-recovery-shares` and `-recovery-threshold` default to 5 and 3 for the recovery key.
W: A=Five shares: the default key share count is 5.
B=Threshold of three: the default threshold is 3 shares.
X: C=Three shares, all required: neither the default count nor the default threshold is 3-of-3.
D=No root token: init returns an initial root token; it can only be encrypted with a PGP key.
E=PGP key per share: PGP keys are optional and merely encrypt the printed shares.
T: Default init is 5 shares with a threshold of 3 and prints an initial root token.

@ VLT-VA003 D7 T7.2 applied comparison
S: A lab operator runs `vault operator init -n=1 -t=1`. Which statement about the result is accurate?
A: Vault creates one share with a threshold of one, so whoever holds that single share can unseal the node alone

G: ## Shares and threshold shortcuts
`-n` is an alias for `-key-shares` and `-t` for `-key-threshold`. With one share and a threshold of one, the unseal key is effectively held by one person, so a single compromise or a single loss decides the outcome.
- This suits labs and test servers.
- The default of 5 shares with a threshold of 3 spreads trust and tolerates lost shares.
- No separate confirmation step exists: the number of shares supplied against the threshold is the only control.
W: One-of-one: a single share meets the threshold of one, so its holder can unseal the node alone, which removes the two-person protection that Shamir splitting gives.
X: B=Second operator: nothing beyond the threshold is demanded, and with a threshold of one a single share completes the unseal.
C=Minimum of three: Vault accepts a single share with a threshold of one, and the threshold only has to be less than or equal to the number of shares.
D=Five shares anyway: the flags set the real counts; they do not label a master share and are not overridden by the defaults.
T: `-n` and `-t` alias the share count and threshold; one-of-one lets a single holder unseal alone, so it fits only labs.

@ VLT-VA003 D7 T7.2 applied use-case
S: A monitoring probe hits a Vault node that was just restarted and is sealed. Which TWO operations can the node still perform? (Select TWO)
A: Reading secrets from KV mounts created before the restart, since the data is still in storage
B: Reporting its seal state through `vault status`

D: Logging in with auth methods and issuing tokens, but returning no secret values
E: Serving transit encrypt requests with cached keys, but creating no new mounts

G: ## What a sealed Vault can do
A sealed Vault can reach its storage but cannot decrypt anything in it. Until unsealed, the only possible operations are to **unseal** the Vault and **check its status**.

- Auth methods, policies, tokens, mounts and secrets all live in encrypted storage, so none are available.

W: B=Status: the status command prints regardless of whether the server is sealed, so probes can read the seal state.

@ VLT-VA003 D7 T7.2 applied definition

Sealing deletes the root key from memory and requires a new unseal to restore it. Because it is meant as an emergency brake, it needs only a single operator with root privileges (a root token or a policy with `sudo` on `sys/seal`). Quorum is demanded for the opposite direction, unsealing.

D=Two operators: no quorum is needed for sealing, which is deliberate so one person can react fast to an intrusion.
