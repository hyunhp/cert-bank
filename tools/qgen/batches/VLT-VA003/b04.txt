@ VLT-VA003 D4 T4.1 applied use-case
S: An application runs `vault read database/creds/readonly` and gets a username, a password and a long identifier. Which value does the application keep so that it can later renew or revoke these credentials?
A: The `lease_id`, since lease commands identify credentials by it
B: The username, because Vault indexes every dynamic credential by the database login name
C: The token accessor, because it names the credential issued by the read request
D: The mount path `database/`, because one lease covers every credential issued from a mount
K: A
G: ## What a lease is
When Vault hands out a dynamic secret, it also creates a **lease**: metadata with a time duration (TTL), renewability and more. Vault promises the secret stays valid for that duration, and the consumer must check in again before it ends.
## The lease ID
Reading a dynamic secret always returns a `lease_id`, for example `database/creds/readonly/27e1b9a1-...`. That ID is what `vault lease lookup`, `vault lease renew` and `vault lease revoke` take. Without it the application cannot manage the credentials it holds.
W: Lease ID: it is the handle returned with every dynamic secret and the only identifier that the lease commands and the `/sys/leases` endpoints accept for a single secret.
X: B=Username: the database login name is only the secret's content; Vault does not look up leases by it, so passing it to a lease command fails.
C=Token accessor: an accessor refers to a token, not to a secret issued by a secrets engine, so it cannot name this lease.
D=Mount path: the mount path is only the leading part of the lease ID. Using it as a prefix would address every lease under it, not this one secret.
T: Every dynamic secret comes with a `lease_id`; keep it to renew or revoke that one secret.
V: Vault

@ VLT-VA003 D4 T4.1 applied definition
S: A lease ID for AWS credentials looks like `aws/creds/deploy/abcd-1234`. Which statement about the structure of lease IDs is accurate?
A: The prefix of a lease ID is the path the secret was requested from, which makes revocation by prefix possible
B: The prefix of a lease ID is the name of the token that requested the secret, so it changes per client
C: The prefix is a random string and the final path segment is the role, so IDs reveal nothing about origin
D: The prefix is always the mount type, so every lease of one engine type shares an identical ID prefix
K: A
G: ## Lease IDs are paths
A lease ID is built so that its prefix is always the path where the secret was requested. For `aws/creds/deploy/abcd-1234` the request path was `aws/creds/deploy` and the last segment is a unique suffix.
- This lets operators address whole trees of secrets: `aws/` covers every AWS lease, `aws/creds/deploy/` covers only one role.
- It also lets you list leases under a path with `vault list sys/leases/lookup/aws/creds/deploy`.
W: Request path as prefix: the ID structure mirrors where the secret came from, so a prefix selects a mount, a role path or a single lease.
X: B=Token name: the requesting token is not encoded in the lease ID. Revoking that token revokes its leases, but through the token relationship, not through the ID.
C=Random prefix: the unique part is the final segment only; the beginning is the readable request path, which is exactly what revoke-by-prefix relies on.
D=Mount type: the prefix follows the mount path chosen by the operator, which may differ from the engine type, and includes the role path.
T: A lease ID starts with the path the secret was requested from, so prefixes group leases.
V: Vault

@ VLT-VA003 D4 T4.1 applied definition
S: Which two kinds of items get a lease from Vault? (Select TWO)
A: Dynamic secrets, such as database credentials generated on demand
B: Static key/value entries written with `vault kv put`
C: Service type authentication tokens
D: Policies attached to an auth method role
E: Batch type authentication tokens
K: A,C
G: ## Where leases come from
Vault creates a lease with every dynamic secret and with every `service` type authentication token. All dynamic secrets are required to have one, even when the data is meant to live a long time, because the lease forces the consumer to check in routinely.
- The key/value engine stores arbitrary data and does not issue leases.
- Policies are configuration, not credentials, so there is nothing to expire.
W: A=Dynamic secrets: every dynamic secret must have a lease, which carries its TTL and lets Vault revoke the credentials.
C=Service tokens: service type tokens carry a lease, so they can be renewed and are revoked when they expire.
X: B=KV entries: the key/value engine does not issue leases; the data stays until someone deletes it.
D=Policies: a policy is an access rule set; it has no TTL or lease to renew or revoke.
E=Batch tokens: they are lightweight and not tracked in storage, so they carry no lease of their own; only service tokens get one.
T: Dynamic secrets and service tokens have leases; static KV data does not.
V: Vault

@ VLT-VA003 D4 T4.1 applied troubleshooting
S: An engineer lost the lease ID of database credentials issued from `database/creds/readonly` and wants to find it from the CLI. Which approach works?
A: Run `vault list sys/leases/lookup/database/creds/readonly`, which needs sudo capability on that path
B: Run `vault lease list database/creds/readonly`, which any authenticated token may run
C: Run `vault read database/creds/readonly` again, which returns the original lease ID unchanged
D: Run `vault token lookup -accessor` on the database user, which returns its lease IDs
K: A
G: ## Finding lease IDs
The `/sys/leases/lookup/:prefix` endpoint accepts the `LIST` method and returns the lease IDs stored under a prefix. The CLI form is `vault list sys/leases/lookup/<prefix>`. Because the result exposes the lease IDs of other clients, the endpoint requires `sudo` capability.
## Why the other tries fail
There is no `vault lease list` subcommand: the `lease` command offers `lookup`, `renew` and `revoke`. Reading the path again does not recover an old lease; it creates a new credential and a new lease.
W: Listing lease IDs: the LIST endpoint under `sys/leases/lookup` returns the IDs below the prefix, and a token with sudo on it can then look up, renew or revoke the one wanted.
X: B=`vault lease list`: that subcommand does not exist; only `lookup`, `renew` and `revoke` are available, and listing is a sudo operation.
C=Reading again: each read issues a brand new credential with a new lease, so the first credential stays active and unmanaged.
D=Token accessor lookup: accessors describe tokens, and the database user is not a Vault token.
T: To find lost lease IDs, LIST `sys/leases/lookup/<prefix>` with sudo; reading the path again creates another secret.
V: Vault

`vault lease lookup <lease_id>` is the CLI form of `POST /sys/leases/lookup` with a `lease_id` in the body. It shows when the lease was issued, when it expires, the remaining `ttl` and whether it is `renewable`.

- It does not return the secret itself. The credentials were shown once when the secret was read.

X: B=Extending the lease: extension is `vault lease renew`; lookup never changes an expiration time.

@ VLT-VA003 D4 T4.1 applied use-case
S: A script must check how much time is left on a lease through the HTTP API instead of the CLI. Which call matches `vault lease lookup`?
A: `POST /v1/sys/leases/lookup` with the `lease_id` in the JSON body
B: `GET /v1/sys/leases/renew` with the `lease_id` as a query string
C: `POST /v1/auth/token/lookup` with the `lease_id` in the JSON body
D: `DELETE /v1/sys/leases/lookup` with the `lease_id` in the JSON body
K: A
G: ## The /sys/leases endpoints
All lease management sits under `sys/leases`:
- `POST /sys/leases/lookup` returns issue time, expiration time, last renewal, renewable and TTL.
- `POST /sys/leases/renew` and `POST /sys/leases/revoke` change the lease.
- `LIST /sys/leases/lookup/:prefix` lists IDs.
Requests carry the token in the `X-Vault-Token` header and a payload such as `{"lease_id": "aws/creds/deploy/abcd-1234"}`.
W: POST to lookup: reading lease metadata is a POST with the lease ID in the payload, and the response shows `ttl` and `renewable`.
X: B=GET on renew: renewal is a POST that changes the lease, and lookup does not use the renew path.
C=Token lookup: `auth/token/lookup` describes tokens; a secret's lease is not a token.
D=DELETE on lookup: lookup is read-only; revocation is done through `sys/leases/revoke`.
T: Lease metadata comes from `POST /sys/leases/lookup`; change comes from renew and revoke.

@ VLT-VA003 D4 T4.1 applied troubleshooting
S: A developer reads a secret from a version 1 `kv` mount and the response includes a `lease_duration`, but `vault lease lookup` finds no lease for it. What explains this?
A: KV issues no lease; the duration is only a hint of how often to check back
B: The lease was created but lookup works only for leases that were renewed at least once
C: The duration is wrong because KV leases are stored per namespace and not per mount
D: Lookup finds only leases of tokens, while KV leases are tracked by the audit log
K: A
G: ## KV returns a duration, not a lease
The lease documentation notes that the key/value backend does not issue leases, although it sometimes returns a lease duration. The KV v1 page explains that the `lease_duration` is a hint for how often consumers should check back for a new value (a `ttl` key in the data is also only advisory); the engine never removes data on its own, so nothing expires and nothing is revoked at that time.
- Dynamic engines (database, AWS) create real leases that Vault enforces.
- KV data stays until deleted, so there is no lease to look up.
W: No lease for KV: the returned duration is only a refresh hint, so lookup has nothing to find and no automatic revocation happens.
X: B=Renewal requirement: lookup finds any existing lease whether or not it was renewed, and KV simply has none.
C=Per-namespace storage: leases are not what limits KV, and no per-namespace KV lease exists.
D=Tokens only: lookup handles leases of dynamic secrets too, and audit logs do not hold leases.
T: KV may print a lease duration, but it does not create a lease, so nothing is looked up or revoked.
V: Vault

@ VLT-VA003 D4 T4.2 applied definition
S: A lease has 10 minutes left and the client runs `vault lease renew -increment=3600 <lease_id>`. What TTL does the client request?
A: One hour counted from now, so the lease should end up with about 3600 seconds left
B: Seventy minutes, because the increment is added to the 10 minutes left
C: One hour counted from the original issue time, so about 50 minutes more are granted
D: Ten minutes, because renewal is capped at the remaining time on the lease
K: A
G: ## The increment is rooted at now
When renewing, a client can ask for a specific amount of time to remain on the lease: the `increment`. It is not added to the end of the current TTL; it is measured from the current time. `-increment=3600` asks for a lease with one hour left.
This makes it easy to shorten a lease too. Asking for less than what remains lets credentials expire sooner so resources are cleaned up earlier.
The value is only a request: the backend may limit or ignore it.
W: Counted from now: the increment states the desired remaining lifetime, so the request here is 3600 seconds from this moment.
X: B=Adding to the end: the increment is not stacked on the existing TTL.
C=Counted from issue time: the clock starts at the renewal request, not at when the secret was created.
D=Capped at remaining time: nothing caps a request at the current remainder; renewal exists precisely to lengthen it, within backend limits.
T: Increment means "make the remaining TTL this long, starting now", and it is only a request.
V: Vault

@ VLT-VA003 D4 T4.2 applied tradeoff
S: A team asks why every dynamic secret must carry a lease even when the credential is meant to stay valid for a very long time. Which reason does the lease documentation give?
A: A lease forces the consumer to check in with Vault routinely, which makes audit logs more valuable and key rolling easier
B: A lease lets the consumer cache the credential indefinitely because Vault pushes a notification when it changes
C: A lease makes the credential static, so it can be stored in the key/value engine and read without renewal
D: A lease encrypts the credential with the requesting token so that only that token can use it
K: A
G: ## Why leases are mandatory
All dynamic secrets in Vault are required to have a lease. Even if the data is meant to be valid for eternity, a lease is required to force the consumer to check in routinely: either renew the lease (if allowed) or request a replacement secret.
- Routine check-ins appear in the audit logs, so the logs show who still uses which credential.
- Key rolling gets easier because consumers already expect to fetch new credentials.
## What a lease does not do
A lease is metadata (TTL, renewability) about a secret. It does not encrypt the secret, push changes to clients or turn a dynamic credential into stored data.
W: Routine check-in: the documented benefit is that consumers must come back to Vault to renew or request a replacement, which improves auditing and makes rotating credentials simple.
X: B=Indefinite caching: Vault does not push notifications; the lease tells the consumer when it must check back, which is the opposite of caching forever.
C=Static data: a lease belongs to dynamic secrets; the key/value engine stores static data and does not issue leases.
D=Token encryption: a lease is metadata with a duration and renewability, not an encryption wrapper bound to a token.
T: Leases make consumers check in routinely, so audits improve and rotation is easy.
V: Vault

@ VLT-VA003 D4 T4.2 applied troubleshooting
S: A service asks `vault lease renew -increment=86400 <lease_id>` and the output shows `lease_duration 1h`. What should the operator conclude?
A: The backend capped the request; the returned duration is the lease
B: The command failed silently and the old lease continues unchanged
C: The renewal doubled the lease because lease durations always grow in whole hour steps
D: The client token TTL overrides the lease and must be raised first
K: A
G: ## The increment is advisory
The backend in charge of a secret may reduce or ignore the requested increment. Most backends try to respect it but cap it so clients renew regularly. For that reason, the documentation says to inspect the renewal's return value to learn the new lease.
The output fields are `lease_id`, `lease_duration` and `lease_renewable`.
W: Backend cap: the result shows what Vault granted; applications must read `lease_duration` from the response and schedule the next renewal from it.
X: B=Silent failure: a renewal that fails returns an error; a shorter duration is a successful, limited renewal.
C=Hour steps: lease durations do not grow by fixed steps; the engine returns whatever duration it grants after applying its own limits.
D=Token override: the request was processed and a duration returned, so the token was not the limit; the cap came from the secret's backend.
T: Never assume the requested increment was granted; read `lease_duration` from the renew response.
V: Vault

@ VLT-VA003 D4 T4.2 applied troubleshooting
S: `vault lease lookup` on some credentials shows `renewable false`. The application's lease ends in five minutes. How does the application keep working?

A lease marked non-renewable cannot be extended. The consumer's option is to request a replacement secret by reading the path again, ideally before expiry to avoid a gap. This is the "request a replacement secret" half of the lease contract, along with renewal.
W: Read again: a new read issues a fresh credential with its own lease, which the application switches to before the old one ends.
X: B=`-force`: renew has only an `-increment` flag; `-force` belongs to revoke and is unrelated.
C=Automatic renewal: Vault never renews a lease on the client's behalf; reaching the end of the TTL leads to revocation, with no hidden one-time extension.
D=Prefix revoke: revoking removes credentials; it never creates a renewable replacement.
T: Non-renewable lease means replace it by reading the secret again, not extend it.

@ VLT-VA003 D4 T4.3 applied use-case
S: Intrusion detection suggests an attacker may hold AWS keys generated through the `aws/` mount. What is the fastest way to invalidate all of them?
A: `vault lease revoke -prefix aws/`, which revokes every lease under that path
B: `vault lease revoke aws/`, which treats the path as the lease to revoke
C: `vault lease renew -increment=1 aws/`, which shortens every lease under the mount to one second
D: Wait for lease expiry, since expired leases cannot be abused
K: A
G: ## Prefix-based revocation
Since lease IDs start with the request path, operators with proper access can revoke whole trees: `vault lease revoke -prefix aws/`. This is the response to an intrusion in a specific system, as all secrets of one mount or role can be revoked quickly.
- The API equivalent is `POST /sys/leases/revoke-prefix/aws`, which needs `sudo` capability.
- Use a narrower prefix such as `aws/creds/deploy/` to hit one role.
W: Prefix revoke: one command invalidates all keys issued under the mount, instead of one at a time.
X: B=No `-prefix`: the path is treated as an exact lease ID, which does not exist.
C=Renew a path: renew takes one exact lease ID and only requests a duration, so a mount path is not a lease and nothing under it is revoked.
D=Wait: waiting leaves the keys usable for their remaining TTL, which is the exposure being closed.
T: `-prefix` turns a path into a tree-wide revoke for incident response.

@ VLT-VA003 D4 T4.3 applied troubleshooting
S: A DBA manually dropped a database user that Vault had issued. Now `vault lease revoke` on its lease ID keeps failing because the database reports the user is missing, and the lease remains. Which command removes the lease from Vault?
A: `vault lease revoke -force -prefix` followed by the full lease ID
B: `vault lease revoke -sync` followed by the full lease ID
C: `vault lease renew -increment=1` followed by the full lease ID
D: `vault lease revoke -force` followed by the full lease ID, without `-prefix`
K: A
G: ## Force revoke
Normal revocation asks the secrets engine to remove the credential. If the target system fails (the user was already removed manually), the lease is stuck. `-force` deletes the lease from Vault even when the engine's revocation fails. It is meant for recovery situations, and **`-prefix` is also required**, so you pass the lease ID as the prefix.
- Vault warns that force-removing can leave it out of sync with secret engines.
- API: `POST /sys/leases/revoke-force/:prefix`, with `sudo` required.
W: Force with prefix: this removes the dangling lease entry despite the backend error, and the full ID as the prefix targets just that lease.
X: B=`-sync`: synchronous revocation still asks the engine, so it fails the same way.
C=Renew: a stuck lease does not need renewal, and renewal would hit the same backend.
D=Force alone: the docs say `-prefix` is required with `-force`, so the command is rejected.
T: When the backend cannot revoke, `-force -prefix <lease_id>` removes the lease, at the cost of Vault no longer tracking the secret.
V: Vault

@ VLT-VA003 D4 T4.3 applied comparison
S: An operator compares `revoke-prefix` with `revoke-force` on `/sys/leases`. What distinguishes the force variant?
A: It ignores backend errors during revocation, for emergencies where cleanup is failing
B: It skips the sudo check so non-privileged tokens can use it in outages
C: It revokes leases of a single token only, never of a prefix
D: It keeps the secrets valid in the backend and deletes the lease record on a schedule
K: A
G: ## Two prefix endpoints
- `POST /sys/leases/revoke-prefix/:prefix` revokes everything under the prefix and reports errors from the backend.

G: ## Expiry
