@ VLT-VA003 D9 T9.1 applied definition
S: A legacy application reads its database password from a local properties file and cannot be changed to call Vault. Which capability of Vault Agent lets it use Vault without code changes?
A: Templating, which renders secrets into a file the application already reads, using the token from auto-auth
B: Tokenization, which replaces the password in the properties file with a lookup key that Vault resolves at read time
C: Seal wrapping, which makes the host file system decrypt the properties file with a key held in Vault
D: Namespace mapping, which makes the application's file reads appear as requests to a Vault KV mount
K: A
G: ## Why Vault Agent exists
Vault Agent is a client daemon that sits next to an application. Its goal is to remove the hurdle of adopting Vault: the application does not need Vault client code, because Agent talks to Vault on its behalf.
- Auto-auth logs in and keeps the token renewed.
- Templating renders secrets into files using Consul Template markup, authenticated with the auto-auth token.
- Caching holds tokens and leased secrets, and Process Supervisor Mode injects secrets as environment variables.
## Example
A template such as `{{ with secret "secret/db" }}{{ .Data.data.password }}{{ end }}` writes the password to the file the legacy application already opens. When the secret changes, Agent re-renders the file.
W: Templating: Agent renders the secret into a file the application already reads, so the application stays unaware of Vault.
X: B=Tokenization: Agent does not swap values for lookup keys. It writes real secret values into files or environment variables.
C=Seal wrapping: seal wrap protects values inside Vault's own storage. It has nothing to do with decrypting files on the application host.
D=Namespace mapping: namespaces partition Vault's data. Agent does not translate file reads into Vault requests.
T: Agent templating renders Vault secrets into files so unmodified applications can consume them.

@ VLT-VA003 D9 T9.1 applied troubleshooting
S: Vault Agent uses AppRole auto-auth with a role created with token_num_uses=3. After a short time the agent fails to renew its token and secrets stop updating. What is the most likely cause?
A: The role needs a longer secret_id_ttl, because the agent logs in again with the same expired secret ID after each renewal
B: The sink must be changed to a wrapped file sink, since a limited-use token cannot be written to disk in plain form
C: Auto-auth does not track remaining uses, so the limited-use token can run out before a renewal; use token_num_uses=0
D: The template stanza must set a lower lease_renewal_threshold so the token is renewed after only three requests
K: C
G: ## Tokens with limited uses and auto-auth
Auto-auth keeps one token alive by renewing it and every renewal consumes a use. The Vault Agent docs state that auto-auth does not support tokens with a limited number of uses: it does not track the uses remaining and may allow the token to expire before it attempts to renew.
## Fix
Create the AppRole with `token_num_uses=0` (unlimited). Control exposure with `token_ttl`, `token_max_ttl` and policies instead. The AppRole bootstrap secret (`secret_id`) can still be limited, because it is used only at login.
W: Limited-use token: auto-auth cannot count uses, so the token is exhausted before renewal. The documented value for AppRole auto-auth is `token_num_uses=0`.
X: A=Longer secret_id_ttl: an expiring secret ID would break new logins, but the described failure is a token running out of uses during renewal, not a login problem.
B=Wrapped file sink: tokens with limited uses can be written to any sink. Wrapping a sink does not change how many uses the token has.
D=Lower lease_renewal_threshold: that setting controls when templates refresh leased secrets, not how many times a token can be used.
T: Use token_num_uses=0 for AppRole auto-auth, because Agent does not track remaining token uses.

@ VLT-VA003 D9 T9.1 advanced comparison
S: A platform team response-wraps the auto-auth token with wrap_ttl set in the method block, not in the sink block. Which statement is accurate about the trade-off?
A: Method wrapping lets the end client verify the creation_path, but auto-auth cannot renew the token, so the client must do it
B: Method wrapping keeps the token renewed by Agent, but the creation_path is always sys/wrapping/wrap and cannot be validated
C: Method wrapping is only possible with several sinks, since the wrap occurs after the token reaches each sink
D: Method wrapping encrypts the token with AES-GCM, so the client does not need to unwrap it before using it
K: A
G: ## Two places to wrap the token
Tokens written by auto-auth can be response-wrapped in two ways.
- Wrapped by the auth method (`wrap_ttl` in the `method` block): Vault wraps the token as it is returned, so the client can inspect `creation_path` and detect a man-in-the-middle. Auto-auth cannot unwrap and rewrap without changing the `creation_path`, so it cannot renew the token; the end client must renew it.
- Wrapped by a sink (`wrap_ttl` in the `sink` block): the token is wrapped after it is fetched, so `creation_path` is always `sys/wrapping/wrap`. This is less secure, but auto-auth keeps the token renewed and re-authenticates on expiry.
W: Method wrapping: the client can verify the creation_path, and renewal falls to the client because Agent cannot rewrap without altering it.
X: B=Sink-wrapping properties: that description (renewed by Agent, fixed sys/wrapping/wrap path) belongs to wrapping in a sink, not in the method.
C=Needs several sinks: sinks wrap tokens after they are fetched, which is why several sinks can be used. Method wrapping happens at login and needs no sink.
D=AES-GCM encryption: encryption is a separate sink option based on a Diffie-Hellman exchange. It is not part of response wrapping, and a wrapped token must be unwrapped before use.
T: Wrapping in the method allows creation_path validation but stops Agent from renewing; wrapping in the sink keeps renewal.

@ VLT-VA003 D9 T9.1 applied use-case
S: A Vault Agent template renders a KV v2 secret to a file. An operator updates the secret in Vault and sees the file change only after several minutes, and nothing else in the config is set. Why?
A: The secret has no lease, so Agent polls it on a five-minute default render interval
B: KV v2 secrets are leased for one hour, and Agent refreshes them when two thirds of the lease has passed
C: Agent subscribes to KV events and applies each change as soon as the secret's lease is revoked
D: The sink must be restarted, as the template engine reads KV v2 data only when a new token is written
K: A
G: ## How templates refresh secrets
Template renewal depends on the kind of secret.
- Renewable secrets or tokens: renewed after 2/3 of the lease duration has elapsed.
- Non-renewable, non-leased secrets such as KV v2: fetched every 5 minutes by default. `template_config { static_secret_render_interval = "10m" }` changes the interval.
- Non-renewable leased secrets, such as many database credentials: fetched again at about 90% of the TTL (with jitter); `lease_renewal_threshold` changes the fraction.
- Static roles with a `rotation_period`: re-fetched as their TTL runs down.
W: Static render interval: KV v2 has no lease, so Agent polls it on `static_secret_render_interval`, five minutes by default.
X: B=Hour-long lease: KV v2 values are not leased, so the two-thirds rule for renewable leases does not apply.
C=Event subscription: Agent templating polls. It does not subscribe to Vault events, and a KV update does not revoke any lease.
D=Sink restart: templates and sinks are independent. Templating runs with the auto-auth token and does not wait for a new token to be written.
T: Non-leased secrets such as KV v2 are re-rendered by polling every five minutes unless static_secret_render_interval says otherwise.

@ VLT-VA003 D9 T9.1 applied troubleshooting
S: A Vault Agent template for secret/app reads .Data.data.apikey, but the secret has the key api_key. The file renders "<no value>" and Agent keeps running. What makes Agent fail instead?
A: Setting error_on_missing_key = true in the template stanza alone, since a missing key then stops the agent process
B: Setting exit_on_err = true in the auto_auth method, since a template error counts as an authentication failure
C: Setting num_retries = -1 in the vault stanza, since disabling retries makes Agent exit on a missing key
D: Setting both error_on_missing_key = true in the template and exit_on_retry_failure = true in template_config
K: D
G: ## Missing key vs missing secret
- If the secret itself does not exist, the templating engine always errors.
- If the secret exists but the key is absent, the engine by default prints `<no value>` and continues.
- `error_on_missing_key = true` in the `template` stanza makes the engine error on a missing key. The docs recommend it.
- Whether Agent exits after a templating error depends on `exit_on_retry_failure` in `template_config` (default `false`). With only the first setting, Agent keeps retrying until the key exists.
So both settings are needed to make Agent fail and exit.
W: Both settings: `error_on_missing_key` turns the missing key into an error, and `exit_on_retry_failure` makes Agent exit once template retries fail.
X: A=Template setting alone: the template then errors, but without `exit_on_retry_failure` Agent retries until the key appears or the process is stopped.
B=exit_on_err: it affects login attempts for new tokens in auto-auth, not template rendering errors.
C=num_retries -1: retries are disabled for requests, but templating does not treat a missing key as a request failure, and the key error is controlled by the two template settings.
T: To exit on a missing key, set error_on_missing_key in the template and exit_on_retry_failure in template_config.

@ VLT-VA003 D9 T9.1 applied comparison
S: Which TWO statements about Vault Agent caching are accurate? (Select TWO)
A: Agent can cache a new token from a login request when the parent token is already managed by Agent, or the new token is an orphan
B: Agent caching caches KV v1 and KV v2 reads without a lease, so repeated reads never reach the Vault server
C: Agent renews cached tokens and leases in memory, and these renewals stop immediately when Agent shuts down
D: Agent writes its renewal state to Vault, so a restarted Agent resumes every renewal where the old one stopped
E: Responses are matched by path only, so a different header on a repeated request still returns the same entry
K: A,C
G: ## What Agent caching does
Caching holds responses that contain newly created tokens and leased secrets generated from those tokens. Agent also renews the cached tokens and leases.
- Tokens: cached only when the token creation request goes through Agent and the parent token is already managed by Agent, or the new token is an orphan.
- Leased secrets: cached when the request uses a token that Agent manages.
- Not cached: static KV secrets. The docs recommend Vault Proxy for static secret caching.
- Uniqueness: a hash of the request, including headers and body, is the cache index.
- Shutdown: renewals run in memory only, so they end when Agent stops. Shutdown does not revoke anything, but renewal responsibility returns to the client.
W: A=Managed parents and orphans: those are the cases in which Agent keeps a new token and its leases and renews them.
C=In-memory renewals: Agent keeps no renewal state outside memory, so renewals end when the process stops (unless persistent caching restores them).
X: B=Static KV caching: Vault Agent does not support static secret caching. Vault Proxy is recommended for that purpose.
D=State in Vault: Agent performs all operations in memory and persists nothing to Vault. Only the optional persistent cache file can bring state back.
E=Path-only matching: the request is serialized and hashed together with its headers and body, so any difference creates a different cache entry.
T: Agent caches tokens and leased secrets of tokens it manages and renews them in memory, but it does not cache static KV reads.

@ VLT-VA003 D9 T9.1 advanced troubleshooting
S: An operator revokes a lease by running vault lease revoke directly against Vault, bypassing Agent. Applications that use Agent's cache still receive the credentials from it. What explains this and what is the remedy?
A: Agent learns of revocations through a Vault event stream, so the credentials will be evicted after the next renewal fails
B: Agent cannot see revocations made directly on the server, so the entry is stale; clear it with the cache-clear endpoint
C: The cache keeps entries until the secret's maximum TTL even when the server revokes them, and nothing can remove them early
D: Revoking directly on Vault also revokes the token owned by Agent, so the cache is refilled with a new token automatically
K: B
G: ## Cache eviction
Agent evicts cache entries when it can no longer renew them (maximum TTL reached, or a renewal error) and by best effort when a revoke request passes through it: a token or lease revocation made via Agent that succeeds on the server evicts the related entries.
## Direct revocations
Revocations made straight against the Vault server are invisible to Agent, so entries can go stale. The `POST /agent/v1/cache-clear` endpoint lets an operator evict entries by `type` (`request_path`, `lease`, `token`, `token_accessor`, or `all`) and `value`.
W: Stale entry: Agent cannot observe revocations made directly on the server, and the cache-clear API removes entries by lease, token, accessor, path or all.
X: A=Event stream: Agent does not subscribe to events. It evicts entries only when renewal fails or when it sees a revoke request pass through it.
C=No early removal: entries can be removed early, both by intercepted revocations and manually through cache-clear.
D=Token revoked too: revoking a single lease leaves the token intact, and Agent does not mint a replacement for a cache entry in that way.
T: Agent can serve stale entries after a direct revocation; use /agent/v1/cache-clear to evict them.

@ VLT-VA003 D9 T9.1 advanced use-case
S: A Kubernetes pod restarts, and Vault Agent should reuse the tokens and leases of its previous run instead of requesting new ones. Which TWO statements about the persistent cache are accurate? (Select TWO)
A: It restores only leased secrets, so a KV v2 secret is read from Vault again after the restart
B: It works on any platform, and the cache file may be placed on any shared network drive
C: It can be used without auto-auth, because the restored token comes from the file itself
D: It is invalidated if the auto-auth token has expired by the time the cache is restored, and secrets are fetched again
E: It stores secret values unencrypted in the file so the application can read them directly
K: A,D
G: ## Persistent caching
Agent can restore tokens and leases from a cache file created by a previous Agent process. The file is a BoltDB file whose tuples (the token, leases for tokens and secrets, and secret values) are encrypted with a generated key.
- Only leased secrets are restored. Non-renewable secrets such as KV v2 are not persisted.
- Auto-auth must be used. If the auto-auth token expired before the restore, the cache is invalidated and secrets are re-fetched.
- It is currently supported only in a Kubernetes environment (`persist "kubernetes"`), typically on a volume shared by the Agent init and sidecar containers.
- With templating enabled, template requests are routed through the cache automatically.
W: A=Leased secrets only: non-leased data such as KV v2 is not stored, so it is fetched from Vault again.
D=Expired auto-auth token: the token that unlocks the restored state is no longer valid, so the cache is dropped.
X: B=Any platform: persistent caching is supported only in Kubernetes at present, using the `kubernetes` type.
C=No auto-auth: auto-auth is required, because the restored entries belong to the auto-auth token.
E=Unencrypted values: the stored tuples are encrypted with a generated encryption key, not written in plain text.
T: The persistent cache restores leased entries in Kubernetes, requires auto-auth, and is discarded if the auto-auth token has expired.

@ VLT-VA003 D9 T9.1 applied use-case
S: Vault Agent runs in process supervisor mode with an exec block and one env_template. A static secret behind the env_template changes. With default settings, what does Agent do?
A: It updates the variable inside the running child process, which keeps its PID
B: It stops rendering and leaves the child running with the old value until Agent is restarted
C: It exits with code 0 and relies on the init system to start the child again
D: It restarts the child with SIGTERM, then SIGKILL after 30 seconds if it does not stop
K: D
G: ## Process supervisor mode
Agent renders each `env_template` at least once and then starts the child defined in the single top-level `exec` block. Environment variables cannot be changed in a running process, so:
- `restart_on_secret_changes` defaults to `always`: when a static secret updates (on `static_secret_render_interval`) or a dynamic secret nears expiry, Agent restarts the child.
- `restart_stop_signal` defaults to `SIGTERM`; after 30 seconds Agent sends `SIGKILL`.
- Agent forwards stdin, stdout and stderr, and exits with the child's exit code when the child exits on its own.
The mode needs at least one `env_template` and is incompatible with file `template` stanzas.
W: Restart with SIGTERM: Agent stops the child with the configured signal, SIGTERM by default, and kills it after 30 seconds, then starts it with new values.
X: A=In-place update: a process cannot have its environment changed from outside. Agent must restart the child.
B=Leaves it alone: that only happens with `restart_on_secret_changes = "never"`, which is not the default.
C=Agent exit: Agent itself keeps running. It exits only when the child exits on its own, and then with the child's exit code.
T: In process supervisor mode Agent restarts the child on secret changes by default, using SIGTERM and then SIGKILL after 30 seconds.

@ VLT-VA003 D9 T9.1 applied use-case
S: A batch job needs secrets rendered once before it starts, and the Agent must then stop so the job pod can finish. Which Agent setting does this when it runs as an init-style process?
A: exit_after_auth = true, so Agent renders its templates and then exits with code 0
B: pid_file set to a path, so Agent quits as soon as that file is deleted by the job
C: disable_keep_alives set for templating, so Agent closes after each rendered template
D: A listener with the agent_api quit endpoint, so Agent exits when the job calls it
K: A
G: ## Running Agent once
`exit_after_auth` (default `false`) makes Agent exit with code `0` after one successful authentication, where success means a token was retrieved and all sinks wrote it. When `template` stanzas exist, Agent waits until the templates have rendered successfully before exiting. This suits init containers and one-off jobs.
Exceptions and notes:
- With `env_template` in process supervisor mode and `exit_after_auth = true`, Agent does not run the child process in `exec`.
- The Vault Agent Injector uses an init container to pre-populate secrets and a sidecar to keep them updated; the init container can run once and exit.
W: exit_after_auth: Agent authenticates, waits for templates to render, and exits with code 0, which lets an init container finish.
X: B=pid_file: it only records the process ID. It does not control when Agent exits.
C=disable_keep_alives: this turns off HTTP keep-alive connections for the listed features. It has no influence on process lifetime.
D=Quit endpoint: `/agent/v1/quit` is disabled by default and can be enabled, but it is a manual shutdown call with no authorization, not a run-once setting, and the job would have to call it.
T: exit_after_auth = true makes Agent render templates once and exit with code 0.

@ VLT-VA003 D9 T9.1 applied comparison
S: A Vault Agent template issues TLS certificates from a PKI role. The agent process restarts every few hours, and the team wants to avoid issuing a new certificate each time. Which template function fits?
A: secret, because it fetches a certificate only when its lease reaches 90% of its TTL, regardless of restarts
B: pkiCert, because it fetches on startup only if none was rendered or the rendered one has expired
C: secret, because it never fetches again after the first render until the template file is deleted
D: pkiCert, because it fetches a fresh certificate on every re-authentication to keep the chain current
K: B
G: ## Certificates in templates
Both `secret` and `pkiCert` can render PKI certificates, but they behave differently around restarts and re-authentication:
- `pkiCert`: on startup, fetch only if no certificate has been rendered yet or the current one has expired. After auto-auth re-authentication (for example a token expiry), skip fetching unless the current certificate has expired. Rotation happens at a share of the certificate validity period, set by `lease_renewal_threshold`.
- `secret`: fetches a new certificate on startup even if the old one is still valid, and fetches and re-renders after re-authentication.
The docs recommend `pkiCert` to avoid needlessly generating certificates.
W: pkiCert: it keeps a still-valid rendered certificate across Agent restarts and re-authentication, so no extra certificates are issued.
X: A=secret on restart: with `secret`, startup always fetches a new certificate, so each restart issues another one.
C=Never fetches again: secret re-fetches by certificate validity (or by lease rules when `generate_lease` is true), so nothing waits for a deleted file.
D=Fresh on re-authentication: that is how `secret` behaves. `pkiCert` skips the fetch on re-authentication unless the certificate expired.
T: Use pkiCert in Agent templates to avoid reissuing a valid certificate on every restart or re-authentication.

@ VLT-VA003 D9 T9.1 advanced troubleshooting
S: Vault Agent is started on a host where VAULT_ADDR is exported as the Agent's own listener address, while the config file sets address in the vault stanza to the Vault cluster. Agent logs show repeated connection attempts and port exhaustion. What is wrong?
A: The listener stanza must use type unix, because a tcp listener cannot be combined with the vault stanza
B: The variable overrides the vault stanza, so Agent dials itself; unset it or point it at Vault
C: The vault stanza overrides the environment variable, so VAULT_ADDR is ignored and the retry stanza loops
D: The token in the sink points at a different cluster, and Agent retries with an incremented port number each time
K: B
G: ## Address precedence
The Vault address can be set in three places. In increasing order of priority: the configuration file, environment variables, CLI flags. If `VAULT_ADDR` is exported where Agent runs, it takes precedence over `address` in the `vault` stanza.
Agent's own listener is where applications send requests. If `VAULT_ADDR` is set to that listener (a common habit so that the CLI uses Agent), Agent tries to connect to itself. The connection fails, and Agent increments the port and tries again, which leads to port exhaustion.
Use `VAULT_AGENT_ADDR` for CLI clients that should talk to the Agent listener, and keep `VAULT_ADDR` out of the Agent's own environment.
W: Environment override: the variable outranks the config file, so Agent's upstream is itself. Removing it or pointing it at the Vault cluster fixes the loop.
X: A=Unix listener: a tcp listener is valid with a vault stanza. The problem is which address the Agent dials.
C=Config wins: the opposite is true. The environment variable has a higher priority than the config file.
D=Sink token mismatch: the sink holds a token and has no address. The port increments come from Agent redialing itself.
T: VAULT_ADDR in Agent's environment overrides the vault stanza; do not point it at Agent itself.

@ VLT-VA003 D9 T9.1 applied use-case
S: Pods in a cluster get secrets from the Vault Agent Injector, and an application needs its credentials in place before its container starts and kept fresh while it runs. Which injector behavior provides that?
A: Only a sidecar is injected, and it renders the files once the application container reports healthy
B: An init container fills a shared memory volume first, then a sidecar keeps rendering to it
C: An init container renders the files and stays running, while the sidecar is used only for TLS settings
D: A mutating webhook writes the secrets into the pod specification as environment variables at admission time
K: B
G: ## What the injector adds to a pod
The Vault Agent Injector is a Kubernetes mutating webhook. It watches pod `CREATE` and `UPDATE` events and, when the annotation `vault.hashicorp.com/agent-inject: "true"` is present, changes the pod:
- Every container mounts a shared memory volume at `/vault/secrets`.
- An init container pre-populates that volume with the requested secrets before the other containers start.
- A sidecar container keeps authenticating and rendering to the same location while the pod runs.
Annotations can disable either container. Secrets are requested with `vault.hashicorp.com/agent-inject-secret-<name>` annotations, or with a ConfigMap of Agent configuration (`vault.hashicorp.com/agent-configmap`) for advanced cases.
The pod's service account is the default way to authenticate with Kubernetes auth; the role should not be bound to the `default` service account.
W: Init plus sidecar: the init container makes secrets available before startup, and the sidecar refreshes them for the pod's lifetime.
X: A=Sidecar only: a sidecar alone cannot guarantee files exist before the application starts. The init container is what provides that.
C=Long-lived init container: init containers run to completion before the app starts. The sidecar is what keeps running and renders updates.
D=Environment variables at admission: the injector does not put secret values in the pod spec. It renders them to a memory volume at runtime.
T: The injector uses an init container for the first render and a sidecar for continuous refresh in a shared memory volume.

@ VLT-VA003 D9 T9.2 applied use-case
S: A KV v2 secret holds the keys user, password and internal_note. A VaultStaticSecret syncs it, and the destination Kubernetes Secret must not contain internal_note. Which setting does this?
A: destination.transformation.excludes with a regex pattern that matches internal_note
B: destination.transformation.excludeRaw set to true, which drops every field Vault marks as internal
C: hmacSecretData set to false, which stops VSO from copying fields it cannot compute a MAC for
D: refreshAfter set to a short value, which makes VSO discard fields that did not change on a sync
K: A
G: ## Shaping the destination Secret
By default VSO copies every top-level key of the source secret into the destination Kubernetes Secret, and may also add a raw copy of the whole source response. The `destination.transformation` block changes this before the Secret is written.
- `excludes`: regex patterns for top-level source fields to leave out. Exclusions are applied before inclusions.
- `includes`: regex patterns for fields to keep.
- `templates`: build new keys from the source data.
- `excludeRaw`: leave out only the raw copy of the source data.
## Example
`transformation: { excludes: ["^internal_note$"] }` leaves `user` and `password` in the Secret and drops `internal_note`.
W: excludes: the regex pattern filters top-level source fields out of the destination Secret, so internal_note is never written.
X: B=excludeRaw: it removes only the raw copy of the whole response. It does not know which fields are internal, and the individual keys stay in the Secret.
C=hmacSecretData false: the HMAC is only used for drift detection and comparison with Vault, and has no role in choosing which fields are copied.
D=Short refreshAfter: it only sets how often VSO syncs. Every sync copies the same fields, whatever changed.
T: Use destination.transformation.excludes (or includes) to control which source fields reach the Kubernetes Secret.

@ VLT-VA003 D9 T9.2 applied definition
S: A platform administrator configures VSO and wants one resource to hold the address and TLS settings of the Vault server, and another to hold the login method, mount and role. Which pair of CRDs is this?
A: VaultAuth holds the address and TLS settings, and VaultConnection holds the login method, mount and role
B: VaultConnection and VaultStaticSecret, with the secret resource also storing the login role
C: VaultConnection holds the address and TLS settings, and VaultAuth holds the login method, mount and role
D: VaultAuth and VaultDynamicSecret, with the dynamic resource also storing the Vault address
K: C
G: ## The foundation resources
Two CRDs describe how the operator reaches and logs in to Vault; every secret-sync resource builds on them.
- `VaultConnection`: a single Vault server. Required `address`; optional headers, `tlsServerName`, `skipTLSVerify` and `caCertSecretRef` for the CA chain.
- `VaultAuth`: how to authenticate to that server. It refers to a connection with `vaultConnectionRef`, and sets `method` (kubernetes, jwt, appRole, aws or gcp), `mount`, and method settings such as the Kubernetes `role` and `serviceAccount`.
The secret resources (`VaultStaticSecret`, `VaultDynamicSecret`, `VaultPKISecret`) point to a VaultAuth with `vaultAuthRef`. If no connection is named, the operator uses the `default` VaultConnection in its own namespace.
W: Connection and auth: VaultConnection carries the server address and TLS options, and VaultAuth carries the method, mount and role.
