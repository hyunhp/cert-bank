@ VLT-VA003 D5 T5.1 applied use-case
S: A web service must reach a PostgreSQL database, and the security team wants every running instance to hold its own username and password that disappears automatically after a few hours. Which secrets engine fits?
A: The database secrets engine, with a role whose creation statements make a new database user per request
B: The KV version 2 secrets engine, with one secret per instance whose versions are rotated by a nightly job
C: The transit secrets engine, with a key per instance that encrypts a password kept in the database itself
D: The cubbyhole secrets engine, with each instance writing its own password into its private token storage
K: A
G: ## Choosing an engine by what the consumer needs
Start from the question "who creates the secret?" If a person or system creates it and Vault only stores it, use a storage engine such as KV. If the target system can have credentials created on demand, use an engine that generates them.
## The database secrets engine
The database secrets engine connects to a database through a plugin using a privileged "root" user configured for Vault. Roles contain the SQL statements that create a user. Each read of a creds path produces a new username and password with a lease, and Vault revokes the user when the lease ends.
- Setup: `vault secrets enable database`, then configure the connection and a role.
- Result: every instance has distinct credentials, so audit logs point to one instance.
W: Database secrets engine: it generates a unique database user per request from the role's statements and removes the user when the lease expires, which is exactly the per-instance, self-expiring requirement.
X: B=KV version 2: it stores values somebody else has already created. A nightly job would create shared or long-lived passwords by hand, and nothing makes them disappear after a few hours.
C=Transit: it encrypts and decrypts data for applications and does not create database accounts, so a password kept in the database would still be a static credential.
D=Cubbyhole: it is a private store tied to one token. It keeps whatever a client writes and does not create database users or expire them on its own schedule.
T: When the target system can mint accounts on demand, use a dynamic engine like database so each consumer gets unique, expiring credentials.
V: Vault

@ VLT-VA003 D5 T5.1 applied use-case
S: A deployment pipeline needs short-lived AWS access keys scoped by an IAM policy, and nobody wants long-lived keys stored in the CI system. Which engine and mechanism fits?
A: The AWS secrets engine, with a role that returns credentials generated through IAM or STS and removed when the lease ends
B: The KV version 1 secrets engine, with the IAM user's access key stored once and read by the pipeline at each run
C: The PKI secrets engine, with a role that issues a client certificate the pipeline presents to the AWS API endpoints
D: The identity secrets engine, with an entity alias that maps the pipeline to an IAM user of the same name in AWS
K: A
G: ## Dynamic cloud credentials
The AWS secrets engine generates AWS credentials from IAM policies defined in a Vault role. The credentials are time-based and are revoked when the Vault lease expires.
Four credential types exist:
- `iam_user`: Vault creates an IAM user for each lease and deletes it at expiry.
- `assumed_role`, `federation_token`, `session_token`: Vault calls STS and returns an access key, secret key and session token.
The pipeline authenticates to Vault with its own auth method, so no AWS secret needs to live in the CI system.
W: AWS secrets engine: roles map to IAM policies or STS calls, so each pipeline run receives fresh keys that Vault removes at lease expiry. Nothing long-lived has to be stored in CI.
X: B=KV version 1: a stored access key is exactly the long-lived static credential the team wants to avoid; reading it repeatedly does not make it short-lived.
C=PKI: it issues X.509 certificates, and AWS API calls are authorized with access keys or STS sessions rather than a client certificate from Vault.
D=Identity: it keeps entities and aliases inside Vault to unify logins, and does not create or map IAM users in AWS.
T: The AWS secrets engine turns an IAM policy into short-lived access keys, so CI never stores long-term AWS credentials.
V: Vault

@ VLT-VA003 D5 T5.1 applied use-case
S: Hundreds of microservices need their own TLS certificates, issued without anyone filing certificate signing requests by hand. Which secrets engine addresses this?
A: PKI, which issues X.509 certificates on demand from a role that holds the allowed names and a maximum TTL
B: Transit, which creates a private key for each service and returns signed certificates as the output of the encrypt call
C: SSH, which signs the public key of each service so that the signed output can be used as a TLS server certificate
D: KV version 2, which keeps every certificate file as a versioned secret that a certificate authority team uploads
K: A
G: ## Certificates as dynamic secrets
The PKI secrets engine generates dynamic X.509 certificates. Services obtain certificates without generating a key and CSR, submitting it to a certificate authority and waiting for approval; Vault authentication and policies replace the manual verification.
Keeping TTLs short means revocation is rarely needed, CRLs stay small, and each running instance can hold its own certificate.
- Roles define allowed domains and TTLs.
- Certificates can be held in memory and discarded at shutdown.
W: PKI: it works as a certificate authority and issues a certificate on request, constrained by role settings, which removes the manual CSR process for every microservice.
X: B=Transit: it performs cryptographic operations on data such as encrypt, sign and HMAC. It does not act as a certificate authority that issues X.509 certificates.
C=SSH: its signed certificates are SSH certificates for logging in to machines, a different format from the X.509 certificates TLS requires.
D=KV version 2: storing certificates only holds files someone else produced, so the manual issuance process stays in place and nothing is generated on demand.
T: PKI makes certificate issuance an API call, ideally with short TTLs.
V: Vault

@ VLT-VA003 D5 T5.1 advanced comparison
S: An operations team wants to stop distributing permanent SSH keys to servers and instead give engineers short-lived access. Which statement about the SSH secrets engine is accurate?
A: It supports signed SSH certificates and one-time SSH passwords, while the older dynamic keys mode was removed in Vault 1.13
B: It supports dynamic keys that create a new key pair on the host per login, in addition to certificates and one-time passwords
C: It supports only one-time passwords, because signed certificates are issued by the PKI secrets engine instead
D: It stores each engineer's private key in encrypted form and returns it on every login until the key is rotated
K: A
G: ## SSH secrets engine modes
The SSH secrets engine manages access to machines over the SSH protocol. It provides two documented modes:
- Signed SSH certificates: Vault signs a public key presented by the client, and servers trust the Vault CA.
- One-time SSH passwords: Vault issues a password valid for one login, checked by a helper on the host.
The dynamic keys mode was deprecated in Vault 1.12 and removed in 1.13, so it is not a choice for Vault 1.19.
W: Certificates and one-time passwords: those are the two current modes, and dynamic keys no longer exist after Vault 1.13, so any design must use one of the first two.
X: B=Dynamic keys: that mode was removed in Vault 1.13 and is not available in current versions.
C=Passwords only: signed SSH certificates are a mode of the SSH engine itself; PKI produces X.509 certificates, not SSH certificates.
D=Stored private keys: the engine does not hold private keys for engineers to retrieve; it signs public keys or issues one-time credentials.
T: SSH engine means signed certificates or one-time passwords, with no permanent keys to distribute.
V: Vault

@ VLT-VA003 D5 T5.1 applied use-case
S: A team must store a third-party payment API key that Vault cannot generate, and it wants to read earlier values after an accidental overwrite. Which choice fits?
A: A KV version 2 mount, because it keeps a configurable number of versions of each key
B: A KV version 1 mount, because it keeps every earlier write as a recoverable history by default
C: A cubbyhole path, because it keeps older values for as long as the writing token stays valid
D: The database secrets engine, because it records earlier values of every stored static secret
K: A
G: ## KV is for static secrets that you supply
The KV secrets engine stores arbitrary key-value data that you provide. It has two modes.
- Version 1 stores only the latest value; an update overwrites the old one and it is not recoverable. It uses less storage and has fewer storage calls.
- Version 2 retains a configurable number of versions (default 10), supports check-and-set to avoid unintended overwrite, and lets deleted versions be restored.
A third-party API key is a static secret that Vault cannot create, which is a KV use case.
W: KV version 2: versions let an operator read an earlier value or roll back after a mistaken write.
X: B=KV version 1: updates overwrite the old value and it cannot be recovered. The saving in storage is the trade-off for no history.
C=Cubbyhole: values are replaced on write and are destroyed with the token, so they offer neither history nor durable storage for the team.
D=Database engine: it generates database credentials and is not a general store for third-party keys or their earlier values.
T: Pick KV version 2 for static secrets that need history and recovery.
V: Vault

@ VLT-VA003 D5 T5.1 advanced comparison
S: Which TWO secrets engines create their output on demand instead of only storing values a user supplied? (Select TWO)
A: Database, which creates database users from role statements when credentials are read
B: KV version 2, which creates a new random value for a key at every read
C: PKI, which creates certificates and private keys from role settings when requested
D: Cubbyhole, which creates a private value for a token whenever a lease is renewed
E: KV version 1, which creates a replacement value each time the key is listed
K: A,C
G: ## Store, generate or encrypt
Secrets engines are grouped by function: some store and read data, some generate dynamic credentials, some provide encryption and similar operations.
- Storing: KV (both versions) and cubbyhole return what a client wrote.
- Generating: database, AWS, PKI and SSH produce credentials, certificates or signed keys on request.
A quick test is whether you can read a value from the engine that you never wrote there.
W: A=Database: reading a creds path executes the role's creation statements and returns a new user.
C=PKI: issuing a certificate generates a key pair and certificate from the role's constraints.
X: B=KV version 2: it returns the data an operator wrote; versioning keeps history and never invents values.
D=Cubbyhole: it stores only what a client writes in the token's private space, and renewing a lease does not generate anything.
E=KV version 1: it returns the last value written. Listing shows key names and does not create values.
T: Dynamic engines create the secret; storage engines only return what you wrote.
V: Vault

@ VLT-VA003 D5 T5.3 applied use-case
S: An application encrypts customer records before writing them to its own MySQL database, but the team does not want developers to handle encryption keys. Which approach uses the transit secrets engine as intended?
A: The application sends plaintext to Vault, stores the returned ciphertext in MySQL, and Vault keeps the key without storing the data
B: The application sends records to Vault, which stores them encrypted under the key and returns them on request
C: The application receives the transit key from Vault, encrypts locally, and discards the key after each insert
D: The application asks transit for a lease on the key, and the database engine uses it to encrypt the table
K: A
G: ## Encryption as a service
The transit secrets engine handles cryptographic functions on data in transit. Vault does not store the data sent to it. Applications keep the ciphertext in their own primary data store, and the burden of correct encryption moves from developers to Vault operators.
Besides encrypt and decrypt, transit can sign and verify data, generate hashes and HMACs, and return random bytes. Details of rotation and rewrap are a separate topic.
W: Send plaintext, store ciphertext: Vault performs the cryptography with a key that never leaves it, and the data itself remains in MySQL.
X: B=Vault stores records: transit does not store the data sent to it; storing is the job of the application's database or a KV engine.
C=Key returned to the app: the main benefit of transit is that the named key stays inside Vault, so developers never handle it.
D=Lease on the key for the database engine: transit has no such lease and the database engine produces credentials, not encryption of table contents.
T: Transit encrypts data for applications while the ciphertext stays in their own store and the key stays in Vault.
V: Vault

@ VLT-VA003 D5 T5.3 advanced definition
S: Which statement about what the transit secrets engine does is accurate?
A: It can sign and verify data, generate hashes and HMACs, and supply random bytes, in addition to encrypting data
B: It stores the data it encrypts under a path so that Vault can return it again after a user is authenticated
C: It creates dynamic database logins whose passwords are encrypted before they are returned to the client
D: It encrypts the other secrets engines' storage, replacing the encryption done by the Vault barrier
K: A
G: ## Transit at purpose level
Transit is cryptography as a service. For this exam you should know what it is for, and when to prefer it over KV or database.
- Encrypt and decrypt application data without Vault storing it.
- Sign and verify, hash, HMAC, random bytes.
- Key derivation, including optional convergent encryption, and data key generation.
Choose KV when Vault should hold the secret itself; choose transit when the data belongs in another system.
W: Broader cryptographic functions: signing, verification, hashing, HMACs and random bytes are documented functions of transit besides encryption.
X: B=Stores the data: transit does not store the data sent to it; KV is the engine for storing data in Vault.
C=Dynamic database logins: producing logins is the database engine's role, and transit has no connection to databases.
D=Replaces barrier encryption: the barrier protects everything Vault writes to storage, and transit is a separate service for client data.
T: Transit is a general cryptography service and not a store.

@ VLT-VA003 D5 T5.2 advanced comparison
S: Which statement correctly contrasts dynamic and static secrets in Vault?
A: A dynamic secret is generated when requested and tied to a lease, while a static secret is stored by someone and stays until it is changed
B: A dynamic secret is stored by an operator and encrypted at rest, while a static secret is generated and encrypted for each client
C: A dynamic secret has no expiry and is revoked only manually, while a static secret always expires with the token that read it
D: A dynamic secret can be read only through the UI, while a static secret is available only through the HTTP API
K: A
G: ## Static versus dynamic
- Static secrets are values placed in Vault, as in KV. They are read as many times as needed and remain until someone updates or deletes them. Anyone with read access sees the same value.
- Dynamic secrets do not exist until a client asks. Vault generates the credential on demand (database, AWS, and so on) and attaches a lease so it expires and can be revoked.
Because each request produces a distinct credential, dynamic secrets support per-client auditing and limit blast radius.
W: Generated with a lease vs stored: that is the defining contrast; dynamic values come from a request, expire and can be revoked, and static values persist until changed.
X: B=Reversed roles: operators supply static secrets, while Vault itself generates dynamic ones.
C=No expiry for dynamic: dynamic secrets carry leases that expire, and static KV values do not depend on the reader's token lifetime.
D=Access path limits: every secret type can be accessed through the CLI, API and UI.
T: Dynamic means generated on request with a lease; static means stored until changed.
V: Vault

@ VLT-VA003 D5 T5.2 advanced tradeoff
S: A legacy application is hard-wired to one existing database username and cannot request new users, yet security requires the password to change regularly without anyone doing it by hand. Which Vault option fits best?
A: A database static role, which maps one existing database user to a Vault role and rotates its password on a schedule
B: A database dynamic role, which creates a different user for each read and expects the application to reconnect
C: A KV version 1 secret holding the password, which Vault rotates by itself when the key is read twice
D: A cubbyhole entry, which Vault refreshes every time the token that wrote it is renewed
K: A
G: ## Static roles in the database engine
Static roles are a one-to-one mapping between a Vault role and an existing database username. Vault stores the password and rotates it based on a period or schedule. Clients receive the current password for the user.
- Trade-off: access is not unique per client, and anyone allowed to read the role can use the same database account.
- Never assign the root credentials Vault uses in `config/` to a static role; rotating them would break the other roles.
Dynamic roles are the better choice when an application can request fresh credentials.
W: Database static role: the account stays the same and Vault handles password rotation on a controlled schedule, which suits an application tied to one username.
X: B=Dynamic role: every request creates a new user, which suits applications that can fetch credentials again but not one tied to a fixed account.
C=KV version 1: KV stores whatever is written and never rotates values or has any logic tied to reads.
D=Cubbyhole: values change only when a client writes them, and renewing the token does not touch the contents.
T: Static roles keep a fixed database user but have Vault rotate its password.
V: Vault

@ VLT-VA003 D5 T5.4 advanced definition
S: Which statement best describes the purpose of a secrets engine in Vault?
A: It is a component mounted at a path that stores, generates or encrypts data, and each engine defines its own paths
B: It is a component that verifies client identity at a path and issues tokens containing the matching policies
C: It is a component that stores Vault's own encryption keys and releases them to nodes during unseal
D: It is a component that writes request and response details to files or a socket for later review
K: A
G: ## What a secrets engine is
Secrets engines are enabled at a path. When a request arrives, the router sends anything under that prefix to the engine, which defines its own paths and properties. To users they act like a virtual filesystem with read, write and delete operations.
- Some engines store data (KV), some generate credentials (database, AWS), some encrypt (transit), and others produce certificates (PKI).
- Auth methods, audit devices and the seal are separate components.
W: Mounted component that stores, generates or encrypts: the router sends requests under the mount's prefix to the engine, which handles them with its own API.
X: B=Auth method: verifying identity and issuing tokens is what auth methods do, mounted under `auth/`.
C=Seal and key storage: protecting keys and unsealing belong to the seal mechanism, not to engines.
D=Audit device: logging requests and responses is done by audit devices.
T: A secrets engine is a path-mounted component that stores, generates or encrypts data.
V: Vault

@ VLT-VA003 D5 T5.4 advanced troubleshooting
S: An operator tries to run vault secrets enable -path=apps/team1 kv while an engine already exists at apps/. What is the result?
A: The command fails because a mount cannot be prefixed by an existing mount, while apps/team1 and apps/team2 could coexist
B: The command succeeds and the new engine shares the apps/ engine's data, because paths are only a naming convention
C: The command succeeds and moves the existing apps/ engine below apps/team1, preserving its leases
D: The command fails only if both engines are the same type, otherwise nested mounts are accepted
K: A
G: ## Mount points cannot overlap
Mount points must not conflict. You cannot create a mount that is prefixed by an existing one, and you cannot create a mount whose name is a prefix of an existing one.
- `foo/bar` and `foo/baz` can coexist.
- `foo` and `foo/baz` cannot.
Each engine is isolated to its own path, so mounts never share data.
W: Prefix conflict: `apps/team1` is under the existing `apps/` mount, so Vault rejects it; sibling mounts below a common prefix that is not itself a mount are fine.
X: B=Shared data: each engine is isolated and has its own storage prefix, so it never shares data with another.
C=Automatic move: enabling never relocates an engine; moving is a separate `vault secrets move` operation that revokes leases.
D=Depends on type: the rule applies to every pair of mounts, regardless of type.
T: Mounts may be siblings but never a prefix of one another.
V: Vault

@ VLT-VA003 D5 T5.4 advanced definition
S: Why can an enabled secrets engine not read the data stored for another engine, even if the engine contains a bug?
A: Each engine gets a barrier view prefixed by a random UUID, and storage does not allow relative access such as ../
B: Each engine is encrypted with a separate unseal key that the operator must supply at mount time
C: Each engine is run on its own Vault node and communicates only through replicated tokens
D: Each engine is limited by the policies of the token that enabled it, so other paths return denied
K: A
G: ## Barrier view
When a secrets engine is enabled, Vault generates a random UUID that becomes the data root of that engine. Everything it writes is prefixed with it, and since storage has no relative access like `../`, an engine cannot reach beyond its folder. This works like a chroot, so even a malicious engine cannot read the data of other engines.
This is separate from policy checks that apply to API callers.
W: Barrier view with UUID prefix: the engine can only address its own folder in storage, which isolates engines from one another.
X: B=Separate unseal keys: Vault has one seal and unseal process for the whole barrier, not one per engine.
C=Separate nodes: engines run inside the same Vault process and do not need separate nodes.
D=Enabling token's policy: policies govern API callers, but internal storage access by engine code is limited by the barrier view.
T: Engines see storage through a UUID-prefixed barrier view, like a chroot.
V: Vault

@ VLT-VA003 D5 T5.4 advanced comparison
S: Which TWO statements about the cubbyhole secrets engine are accurate? (Select TWO)
A: Its paths are scoped per token, and no token can read another token's cubbyhole
B: It is enabled by default and cannot be disabled, moved or enabled multiple times
C: Its values are versioned and kept for a configurable number of writes per key
D: Its contents remain available after the token expires until an operator deletes them
E: A token with the root policy can read the cubbyhole of any other token
K: A,B
G: ## Cubbyhole
Cubbyhole is private per-token storage. The lifetime of its data is tied to the token, so there is no TTL or refresh interval for the values, and the data is destroyed when the token expires. Writing a key replaces the old value.
It is enabled by default and cannot be disabled, moved or enabled again. Response wrapping builds on it: the wrapped response sits in the cubbyhole of a single-use token.
W: A=Per-token scope: each token only has access to its own cubbyhole, which is what makes it suitable for wrapping.
B=Always present: it is on by default and cannot be disabled, moved or enabled a second time.
X: C=Versioned values: cubbyhole replaces the old value on write and keeps no history.
D=Survives the token: the cubbyhole is destroyed with its token.
E=Root can read others: no token can access another token's cubbyhole, including privileged ones.
T: Cubbyhole is private to one token and disappears with it.
V: Vault

@ VLT-VA003 D5 T5.5 advanced definition
S: A trusted provisioning service requests a secret with the CLI flag -wrap-ttl=5m and hands the result to a new machine. What does the machine receive?
A: A single-use token that references the secret in its cubbyhole, which the machine unwraps once
B: The secret itself in plaintext, with the lease shortened to five minutes
C: An encrypted copy of the secret that the machine decrypts with its own transit key
D: A renewable token that gives repeated read access to the original path for five minutes
K: A
G: ## Response wrapping
Response wrapping lets Vault take the response it would have returned and place it in the cubbyhole of a new single-use token, returning that token instead. Wrapping is per request, triggered by a TTL in the `X-Vault-Wrap-TTL` header or `-wrap-ttl` on the CLI.
- The original response is serialized and stored in the new token's cubbyhole.
- The reply carries the token, its TTL, creation time and creation path.
- Unwrapping is done with `sys/wrapping/unwrap`, and works once.
W: Single-use token: the wrapping token only references the data, and a single unwrap returns the original response.
X: B=Plaintext with short lease: wrapping replaces the response with a token, so the secret is not on the wire.
C=Transit-encrypted copy: wrapping does not involve transit or any key on the receiving machine.
D=Renewable read token: the wrapping token is single-use and gives access only to the stored response.
T: Wrapping swaps the secret for a single-use token that unwraps once.
V: Vault

@ VLT-VA003 D5 T5.5 advanced troubleshooting
S: A new server receives a wrapping token and the unwrap call fails with an invalid token error, although the token's TTL has not elapsed. What should the team conclude?
A: Someone may already have unwrapped it, so a security investigation should start using audit logs
B: Vault has lost the wrapped data because response-wrapping tokens are cached in memory only
C: The token needs to be renewed first because wrapping tokens always begin in an inactive state
D: The server needs a policy for the original secret path, because unwrapping rechecks that policy
K: A
G: ## Validating wrapping tokens
A wrapping token can be unwrapped only once, so a failure suggests that another party got there first. Recommended validation:
- Alert if an expected token never arrives.
- Look up the token (`sys/wrapping/lookup`, unauthenticated for the holder); it shows creation time, creation path and TTL.
- Check that the creation path matches expectations, such as `pki/issue/...` for a certificate. Paths from `cubbyhole` or `sys/wrapping/wrap` are suspicious.
- Unwrap. A failure triggers investigation.
A failure does not prove interception, because a slow start can also let the TTL pass, but it must be investigated.
W: Possible earlier unwrap: single-use semantics mean a valid, unexpired token that fails to unwrap may have been used by someone else, which is the malfeasance detection that wrapping provides.
X: B=Lost data: wrapped responses are stored in the token's cubbyhole, which is persisted, so loss is not the expected explanation.
C=Inactive state: wrapping tokens are usable immediately and need no renewal.
D=Policy for original path: the token itself authorizes the unwrap; the holder needs no policy for the original path.
T: A wrapping token that cannot be unwrapped before its TTL ends is a security signal.
V: Vault

G: ## Where did it come from
The lookup operation on `sys/wrapping/lookup` returns the creation time, creation path and TTL of the wrapping token. It is unauthenticated for the holder so that validation is always allowed. @ VLT-VA003 D5 T5.5 advanced comparison
S: Which TWO benefits does response wrapping give when a secret travels through an intermediate system? (Select TWO)

G: ## What wrapping provides
Response wrapping performs three duties:

- Malfeasance detection: only one party can unwrap, and a failed unwrap or lookup raises an alert.

D=Data removed: soft deletes keep the data so that recovery is possible.
T: KV v2 delete is soft and undelete reverses it; destroy and metadata delete are permanent.
