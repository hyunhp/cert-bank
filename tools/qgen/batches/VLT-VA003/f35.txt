G: ## Quorum in Integrated Storage
Integrated Storage uses the Raft consensus protocol. A log entry is committed only when a majority of the peer set has stored it. Quorum is the smallest majority: for a peer set of `N` voters it is `ceil((N + 1) / 2)`.
- 3 servers: quorum 2, failure tolerance 1
- 5 servers: quorum 3, failure tolerance 2
- 7 servers: quorum 4, failure tolerance 3
If quorum is lost the cluster cannot elect a leader, commit writes or change membership, and recovery is manual.
## Why five nodes is a common production size
Losing two of five leaves three, which is still a majority, so the cluster rides through two simultaneous failures without operator action.
W: Quorum survives: three of five is a majority, so the remaining peers keep a leader and commit new writes. A five-node cluster is designed to tolerate two failures.

C=Read-only until remove-peer: `vault operator raft remove-peer` removes a node from the peer set, but it is not needed here. Quorum is not lost, so the cluster keeps accepting writes without manual removal.

Vault substitutes identity values before matching the path. Substituted values are treated as literal text and cannot introduce wildcards.

X: B=List requests: there is no special wildcard handling for list requests in template output.
C=Wildcard expansion: that would let metadata values widen access, which Vault explicitly prevents.
D=Fallback: Vault does not fall back to a policy without the template; the request is simply denied.
T: Wildcards (`+` or `*`) in a rendered template value cause permission denied.

G: ## Delete, undelete, destroy
KV v2 keeps versions and uses soft deletes.

- `vault kv undelete -versions=N`: restores them.
- `vault kv destroy -versions=N`: permanently removes the version data.
- `vault kv metadata delete`: removes all versions and metadata of the key.
Policies can restrict who may soft delete, undelete or destroy.

D=Data removed: soft deletes keep the data so that recovery is possible.

G: ## What convergent encryption needs
Convergent encryption makes the same plaintext and context always produce the same ciphertext. It works by deriving a key from a context and deterministically deriving the nonce, so it is available only for symmetric AEAD key types that support derivation: `aes128-gcm96`, `aes256-gcm96` and `chacha20-poly1305`.
## Why the others fail
`ed25519` supports derivation, but as a signing analogue (the same context gives the same signature), not for encrypting. RSA keys use OAEP padding and ECDSA keys only sign, so neither has a key-derivation mode.

E=ChaCha20-Poly1305: a symmetric AEAD key listed as supporting derivation and convergent encryption.
X: B=ECDSA P-384: it supports signing and verification only, with no encryption and no derivation mode.
C=RSA-4096: it does encrypt, decrypt and sign, but it has no derivation or convergent mode.
D=Ed25519: it supports derivation, but for signing only; it cannot encrypt, so convergent encryption does not apply.
T: Convergent encryption is for the symmetric AEAD types (AES-GCM and ChaCha20-Poly1305) with derivation enabled.

@ VLT-VA003 D7 T7.1 advanced use-case
S: An attacker copies a full snapshot of the storage backend files from a stopped Vault node. The attacker has no unseal keys and no Vault token. What can the attacker read?
A: Plaintext secrets, after the attacker replays stored token records against the restarted sealed server
B: The names of auth methods and mounts, which are kept unencrypted so a sealed node can start up
C: Encrypted data only, because the keys in storage are themselves encrypted and the unseal key is not stored
D: Plaintext secrets, because the storage files of a stopped node are readable with filesystem access

G: ## Untrusted storage
The security model assumes an attacker may read the storage backend. Everything Vault stores is encrypted by the barrier, including the encryption key (encrypted by the root key) and the root key (encrypted by the unseal key). The unseal key is never stored in the clear; with Shamir seals only the operators hold its shares.
## What the model does not promise
Per the threat model, an attacker who reads storage may still learn that secret material exists. Vault also does not defend against memory analysis of a running, unsealed Vault or arbitrary control of the backend (deleting or rolling back data).
W: Ciphertext only: without the unseal key the root key stays encrypted, so the encryption key and all data are unreadable.
X: A=Replaying tokens: client tokens are stored inside the same encrypted data, and a sealed server answers no login requests anyway.
B=Plaintext mount names: nothing is stored unencrypted for unseal use; Vault holds the data it needs encrypted and requires the keys from operators.
D=Plaintext files: file access does not help because everything is encrypted before it is written.
T: A stolen storage snapshot reveals only ciphertext; confidentiality depends on the unseal key staying out of the attacker's hands.
