@ VLT-VA003 D3 T3.1 applied use-case
S: A CI system authenticates tens of thousands of short pipeline jobs per hour. Each job reads a few secrets and finishes in minutes, and nothing needs to renew, revoke or create child tokens. Which token type reduces storage load on Vault the most?
A: Batch tokens, because they are encrypted blobs that need no storage writes when they are created.
B: Service tokens with a short TTL, because Vault removes their storage entries immediately after the last use.
C: Periodic service tokens, because the fixed period lets Vault skip tracking each token in its token store.
D: Root tokens with a use limit, because root tokens bypass the token store when they are generated.
K: A
G: ## Two token types
- **Service tokens** are the normal Vault tokens. They support renewal, revocation, child tokens, accessors and a cubbyhole, so Vault writes several records to storage for each one and tracks them until they expire.
- **Batch tokens** are encrypted blobs that carry the information needed to use them. Vault stores nothing when one is created, which makes them lightweight and scalable, but they cannot be renewed, manually revoked or used to create child tokens.
## Choosing
Pick batch tokens for high-volume, short-lived, simple workloads. Pick service tokens when you need renewal, revocation by accessor, child tokens or an explicit max TTL.
W: Batch tokens: creation involves no storage cost, so a burst of short jobs does not load the token store; the jobs do not need any of the features batch tokens lack.
X: B=Short-TTL service tokens: a service token is still written to storage when it is created and tracked until it expires or is revoked. A short TTL does not turn it into a stateless token.
C=Periodic service tokens: periodic tokens are a kind of service token and are heavier, since they are stored and renewed. The period controls lifetime, not tracking cost.
D=Root tokens with a use limit: root tokens are service tokens, and handing out root to pipelines would break least privilege; no storage-free root token exists.
T: Many short, simple jobs and no need to renew or revoke: batch tokens. Anything needing renewal, accessors or child tokens: service tokens.

@ VLT-VA003 D3 T3.1 applied comparison
S: Which statement about batch tokens, compared with service tokens, is accurate?
A: A batch token is always issued with a fixed TTL and cannot be renewed to extend it.
B: A batch token can be revoked early by looking up its accessor and revoking that accessor.
C: A batch token can be created as periodic when the role sets a period value.
D: A batch token can create child tokens, which expire together with it.
K: A
G: ## Batch token limits
The tokens documentation compares the two types side by side. Batch tokens are not renewable, not manually revocable, cannot be periodic, have no explicit max TTL (they always use a fixed TTL), have no accessor, no cubbyhole and cannot create child tokens. They also cannot be root tokens.
Because Vault does not store them, there is nothing to renew or revoke. A batch token simply stops working when its TTL ends, or when its parent token is revoked.
W: Fixed TTL: a batch token lives for the TTL it was created with and then stops working; the only way to get a longer-lived credential is to authenticate again.
X: B=Revoke by accessor: batch tokens have no accessors and cannot be manually revoked, so there is no accessor to look up.
C=Periodic batch token: only service tokens can be periodic, because periodic behavior depends on renewal, which batch tokens do not support.
D=Child tokens: batch tokens cannot create child tokens; creating children is a service token feature.
T: Batch tokens are stateless and fixed: no renewal, manual revocation, accessor, periodic behavior or children.

@ VLT-VA003 D3 T3.1 applied troubleshooting
S: An application obtained a token with `vault token create -type=batch -ttl=15m`. After ten minutes it runs `vault token renew` and gets an error. What explains the failure?
A: Batch tokens are not renewable, so the application must request a new token before the TTL ends.
B: The application first has to call the renewal endpoint with the accessor, which batch tokens return at creation.
C: Batch tokens can only be renewed after the first half of the TTL has passed, and ten minutes is too early.
D: The token must be created with the `-period` flag before Vault will accept renewals for it.
K: A
G: ## Renewal needs state
Renewing a token extends its TTL. Service tokens have a record in storage that Vault can update; batch tokens do not, because they are self-contained encrypted blobs. As a result, a batch token is never renewable and always expires at the TTL it was issued with.
If a workload runs longer than expected, plan for it at creation time: request a longer TTL, or use a service token when renewal is needed.
W: Not renewable: renewal is not supported for batch tokens, so the fixed 15-minute TTL is final and a new token must be obtained.
X: B=Accessor renewal: batch tokens do not have accessors, so there is no accessor to renew with.
C=Half-TTL rule: Vault has no minimum elapsed time before renewal; the error comes from the token type, not the timing.
D=The `-period` flag: periodic tokens are a service token feature, and `-period` cannot be combined with a batch token to make it renewable.
T: Need renewal or a long run? Use a service token. A batch token ends at its issued TTL.

@ VLT-VA003 D3 T3.1 applied tradeoff
S: A platform team runs Vault with performance replication and wants orphan tokens that clients can use against any performance cluster. Which choice fits, and what is the trade-off?
A: Batch orphan tokens, accepting that they cannot be renewed or revoked individually.
B: Service tokens, accepting that they are written to storage on every cluster that serves the client.
C: Periodic service tokens, accepting that the period must be identical on every cluster.
D: Root tokens, accepting that they need a quorum of unseal key holders for every creation.
K: A
G: ## Tokens across replication clusters
Service tokens live in the storage of the cluster that created them, so they cannot be used across performance replication clusters. Batch tokens carry their own data, so they can be used across performance replication clusters, but only when they are orphans; a non-orphan batch token depends on its parent, whose validity another cluster cannot check.
Batch token creation also scales with the number of performance standby nodes, which is another reason they suit large deployments.
## The price
You give up renewal, manual revocation, periodic behavior, accessors and child tokens.
W: Batch orphan tokens: stateless, orphan batch tokens are the documented way to work across performance replication clusters, at the cost of the missing features.
X: B=Service tokens: service tokens cannot be used across performance replication clusters, and the reason is the opposite of the claim: they stay in the creating cluster rather than being written everywhere.
C=Periodic service tokens: they are still service tokens, so they cannot be used across performance clusters, whatever the period.
D=Root tokens: root tokens are service tokens and are not meant for application traffic; a root token made with `generate-root` needs a quorum of unseal key holders, which is not a create-per-client model.
T: Cross-cluster use needs an orphan batch token; the price is no renewal, accessor, manual revoke or children.

@ VLT-VA003 D3 T3.1 applied use-case
S: A release pipeline creates one token per deployment for a deploy agent. The agent must be able to start a helper process that gets its own sub-token, and an operator wants to revoke the agent's access mid-run if needed. Which token fits?
A: A service token, because it can create child tokens and can be revoked before it expires.
B: A batch token, because an operator can revoke it on its own with `vault token revoke`.
C: A batch token with `-orphan`, because orphan batch tokens can create their own children.
D: A recovery token, because it is the only type meant for short-lived automation.
K: A
G: ## Features that force service tokens
Child tokens and manual revocation are service token features. Batch tokens cannot create children and cannot be manually revoked. A batch token does stop working when its parent is revoked, but that only helps when a parent exists and is revoked, which is not "revoke this specific job's token on demand".
Recovery tokens are a third type, documented on their own page, and are not meant for pipelines.
W: Service token: it supports creating child tokens for the helper and explicit revocation (by token or accessor) if the operator needs to cut the agent off.
X: B=Batch token: batch tokens cannot create child tokens and cannot be manually revoked; only revoking their parent stops them, which would also kill every other token below that parent.
C=Orphan batch token: orphan only means it has no parent; it still cannot create child tokens.
D=Recovery token: recovery tokens are for recovery operations, not for ordinary pipeline automation.
T: Child tokens plus on-demand revocation require service tokens.

@ VLT-VA003 D3 T3.2 applied definition
S: A new administrator asks what makes a root token different from the other tokens a Vault cluster issues. Which statement about root tokens is accurate?
A: A root token has the `root` policy attached and is the only token that can be set to never expire.
B: A root token always has a 32 day TTL so that a forgotten one revokes itself.
C: A root token is a batch token with an added `root` policy, so it needs no storage.
D: A root token can be created by any token whose policy grants `create` on `auth/token/create`.
K: A
G: ## What makes a token root
A root token is any token that has the `root` policy, which allows everything in Vault. It is the only token type that can have no expiration at all (a TTL of 0) without needing renewal, and the root token printed by `vault operator init` is exactly that.
## How they get created
Only three ways exist: the initial root token from `vault operator init`, another root token (an expiring root cannot create a non-expiring one), and `vault operator generate-root`, which needs a quorum of unseal key holders.
W: Root policy and no expiry: root tokens carry the `root` policy and are the only tokens in Vault that may live forever without renewal.
X: B=32 day TTL: 32 days is the default system max TTL for ordinary tokens. The initial root token has no expiration.
C=Batch token plus root: batch tokens cannot be root tokens, so a root token is always a service token.
D=Any token with create access: creating a root token needs a root token or `generate-root` with a quorum of key holders; policy permission on the create endpoint does not grant root.
T: Root = `root` policy, can be non-expiring, and can only be made by init, another root, or generate-root.

@ VLT-VA003 D3 T3.2 applied use-case
S: Which TWO of the following are documented ways to create a root token? (Select TWO)
A: Running `vault operator init`, which prints the initial root token.
B: Running `vault operator generate-root` with a quorum of unseal key holders.
C: Running `vault token create -policy=root` with a token that has the `default` policy.
D: Enabling the `userpass` auth method and assigning the `root` policy to a user.
E: Running `vault login -method=token` with any token that has `sudo` on `auth/token/create`.
K: A,B
G: ## Only three sources
Root tokens are made purposely hard to obtain. The documented creators are:
- the initial root token created at `vault operator init`, which has no expiration;
- another root token (a root with an expiry cannot create one that never expires);
- `vault operator generate-root`, run with the permission of a quorum of unseal key holders.
Tokens only receive policies the creator already has, so a token without the `root` policy cannot hand it out.
W: A=Initial root token: `vault operator init` returns the first root token with no expiration.
B=generate-root: the command builds a new root token once enough unseal key holders submit their key shares.
X: C=Create with `-policy=root`: a child token cannot be given policies its creator lacks, so a `default`-only token cannot make a root token.
D=Userpass root policy: auth methods issue tokens with the policies you configure, but the `root` policy cannot be attached this way; root tokens come only from the three documented sources.
E=`sudo` on create: `sudo` unlocks options like orphan and periodic tokens; it does not allow creating a token with the `root` policy.
T: Root tokens come from init, another root token, or generate-root with a quorum.

@ VLT-VA003 D3 T3.2 applied use-case
S: All operators lost the root token, and the production cluster is healthy and unsealed. Which action produces a new root token without restarting Vault?
A: Start it with `vault operator generate-root -init`, then have key holders submit shares up to the threshold.
B: Run `vault token create -policy=root` using any token that has the `admin` policy attached to it.
C: Run `vault operator init` again so that Vault prints a brand new initial root token for the team.
D: Restart the nodes in dev mode so that Vault creates a fresh root token on every startup.
K: A
G: ## Regenerating a root token
`vault operator generate-root` creates a fresh root token on demand using a quorum of unseal key holders. The process is:
- `-init` starts the attempt and returns a nonce. You supply an OTP (generate one with `-generate-otp`) or a PGP key so that the final token is not readable in transit.
- Each key holder runs the command and submits an unseal key share along with the nonce.
- When the threshold is reached, Vault returns the encoded token, and you recover the real token with `-decode` and the OTP.
`-status` shows progress and `-cancel` discards the attempt.
W: Run generate-root: it needs no restart, only a quorum of key holders, and it is the documented route when the initial root token is gone.
X: B=Create with the root policy: policies come from the creator's own set, so an `admin` policy token cannot mint a root token.
C=Run init again: an already initialized Vault refuses to initialize again, and re-initializing would not be a recovery path anyway.
D=Dev mode restart: dev mode starts an in-memory server with a fixed unsealed state and loses all data; it is not a way to recover a production cluster.
T: Lost the root token? Use `vault operator generate-root` with a quorum of unseal key holders.

@ VLT-VA003 D3 T3.2 applied definition
S: During `vault operator generate-root`, the team passes `-otp=<value>` when they start the attempt. What is the OTP for?
A: The final root token is XORed with it, so you recover the real token with `-decode` and the same OTP.
B: It authenticates each unseal key holder, so only people with that code can submit key shares.
C: It sets how many seconds the new root token stays valid before it is revoked automatically.
D: It replaces the unseal key threshold, so a single holder can finish the attempt with the OTP.
K: A
G: ## Protecting the new token in transit
The new root token is sensitive. Vault never returns it in plain text at the end of generate-root. One of two protections must be chosen when the attempt starts:
- a base64 one-time password via `-otp` (create it with `-generate-otp`): the result is XORed with the OTP, and `-decode` with the same OTP turns it into the real token;
- a PGP key via `-pgp-key`: the token is encrypted with the public key.
The unseal key quorum is still required either way.
W: XOR and decode: the OTP masks the returned value; only someone who holds the OTP can run `-decode` to reveal the root token.
X: B=Authenticating key holders: unseal key shares are themselves the proof of authority; the OTP does not authenticate anyone.
C=Token validity: the generated root token's expiry is not set by the OTP; it is only an encoding secret.
D=Replacing the threshold: the quorum requirement is unchanged, and the OTP cannot lower it.
T: The OTP (or PGP key) only protects the new token in transit; the quorum is still needed.

@ VLT-VA003 D3 T3.2 applied tradeoff
S: Which practice best matches HashiCorp's guidance for root tokens in a production cluster?
A: Use a root token only for initial setup or emergencies, then revoke it and generate a new one later if needed.

Root tokens can do anything, and they can be non-expiring, so a leaked one is a worst-case incident. The guidance in the tokens documentation:
- use a root token only for just enough initial setup (auth methods and policies that let administrators get limited tokens) or in emergencies;

@ VLT-VA003 D3 T3.2 applied definition
S: An admin finishes initial setup using the root token and wants to remove it. Which command revokes the root token currently set in `VAULT_TOKEN`?
A: `vault token revoke -self`
B: `vault operator generate-root -cancel`
C: `vault token renew -increment=0`
D: `vault operator seal`
K: A
G: ## Revoking the current token
`vault token revoke` revokes a token and its children. Without a token argument it uses the locally authenticated token, and `-self` makes that explicit. After the call, the token is invalid; any further requests with it return `403` with `permission denied`.
Other commands do different things:
- `generate-root -cancel` discards an in-progress generation attempt, not an existing token.
- `token renew` extends a token lease.
- `operator seal` seals the whole Vault.
W: `vault token revoke -self`: it revokes the token you are authenticated with, along with its child tokens and leases.
X: B=generate-root -cancel: resets an unfinished root token generation attempt; an already issued root token stays valid.
C=`token renew -increment=0`: renewing does not revoke; a zero increment just asks for the default behavior.
D=`operator seal`: sealing blocks all requests until unseal but does not revoke the token, which is valid again after unsealing.
T: Revoke your own token with `vault token revoke -self`.

@ VLT-VA003 D3 T3.3 applied definition
S: An auditor sees that every `vault token create` response includes both a `token` and a `token_accessor` field. What is a token accessor?
A: A reference returned at token creation that allows limited actions on the token without exposing its ID.
B: A second secret that must be sent together with the token to authenticate on every request.
C: The policy name that Vault attaches to a token so that it can read its own details.
D: A hash of the token that Vault stores in the audit log as the secret value of the token.
K: A
G: ## The accessor
When a token is created, Vault also creates and returns an accessor. It is a reference to the token, not the token itself. With the accessor you can only:
- look up the token's properties (not the token ID);
- look up the token's capabilities on a path;
- renew the token;
- revoke the token.
It cannot be used to authenticate and make ordinary requests. The caller must still hold permission for the lookup, renew or revoke endpoints.
W: A reference to the token: the holder can inspect, renew or revoke it, but cannot use it to log in or read secrets.
X: B=Second authentication secret: authentication uses only the token; an accessor alone cannot authenticate a request.
C=Policy name: an accessor is a random reference, unrelated to policies; the `default` policy is what lets a token look up itself.
D=Hash in the audit log: audit devices HMAC token IDs, and by default accessors are also hashed, but the accessor is not a hash of the token.
T: An accessor lets you manage a token (lookup, renew, revoke) without holding the token itself.

@ VLT-VA003 D3 T3.3 applied use-case
S: A scheduler creates a token for each job and stores only the accessor. Which TWO actions can it perform later with just that accessor? (Select TWO)

An accessor is limited to lookup, capability check, renew and revoke. The lookup output deliberately does not contain the token ID. Policies attached to a token are fixed at creation; they cannot be edited later through an accessor.
The scheduler pattern: store the accessor next to the job ID; at job end, revoke by accessor. That also revokes the token's child tokens and leases.

X: C=Use as client token: an accessor cannot authenticate normal requests, so it cannot read secrets.

@ VLT-VA003 D3 T3.3 applied troubleshooting
S: A security team needs to list every active token in a Vault cluster for an audit. Which statement about this is accurate?
A: The only way to list tokens is `auth/token/accessors`, which returns accessors rather than tokens.

@ VLT-VA003 D3 T3.4 applied definition
S: A developer reads `token_duration 768h` in the output of `vault token create` and asks what the TTL of a Vault service token actually describes. Which is accurate?
A: The period of validity since the token's creation or its last renewal, whichever is more recent.
B: The total lifetime from creation that can never be extended, no matter how often it is renewed.
C: The number of times the token can be used before Vault revokes it automatically.
D: The time since the token's last use, after which Vault revokes it as inactive.
K: A
G: ## TTL
Every non-root token has a time-to-live. It measures the current period of validity from creation or the latest renewal. When the TTL ends, the token stops working and the token and its leases are revoked. A token needs to be renewable, and below its maximum TTL, to extend this.
Related settings:
- **max TTL**: the upper bound on total lifetime when renewing;
- **explicit max TTL**: a hard limit set on the token at creation;
- **use limit** (`-use-limit`): number of uses, a separate control.
Root tokens may have a TTL of 0 meaning they never expire.
W: TTL = current validity window, restarted by creation or renewal; the max TTL decides how far renewals can go.
X: B=Fixed lifetime: that describes an explicit max TTL; the ordinary TTL is reset by renewal.
C=Number of uses: usage counting is `-use-limit` / `num_uses`, not TTL.
D=Idle timeout: Vault does not revoke tokens for being idle; they expire on TTL only.
T: TTL is the current validity window from creation or last renewal; max TTL caps total renewals.

@ VLT-VA003 D3 T3.4 applied troubleshooting
S: A service token was created with a 1 hour TTL, and the application renews it every 30 minutes. After several weeks a renewal returns a TTL shorter than requested, and later the token stops working. What is the most likely cause?
A: The token reached the maximum TTL that applies to it, so renewals can no longer extend it.
B: Vault revokes any token that is renewed more than 48 times in a row.
C: The token became an orphan, and orphan tokens cannot be renewed after one day.
D: The 30 minute interval is shorter than the TTL, so Vault treats it as abusive and stops extending.
K: A
G: ## Max TTL limits renewal
Renewing a non-periodic token does not give it unlimited life. At renewal Vault compares the token's age with the maximum TTL, which is derived from:
- the system max TTL (32 days by default, configurable);
- the mount's tuned max TTL, which may be longer or shorter;
- a value from the auth method's role, group or user, which can be lower but not higher than the mount or system value.
When the cap is reached the renewal returns a smaller TTL, and the token then expires. The client should read the TTL in each renewal response, and re-authenticate when it stops growing. Vault does not revoke a token before the TTL it last returned has passed, except through direct operator action.
W: Max TTL reached: the renewal is trimmed to the remaining time before the cap, and afterwards the token expires; a new token is needed.
X: B=Renewal count: there is no limit on the number of renewals; only the TTL ceiling matters.
C=Orphan after one day: orphan tokens renew like any other service token; orphan status has no time limit.
D=Renewing too often: renewing early is allowed; it just resets the TTL window to the lesser of the requested increment and what the max TTL allows.
T: Renewals stop helping at the max TTL; then re-authenticate.

@ VLT-VA003 D3 T3.4 applied comparison
S: A token is created with `vault token create -ttl=1h -explicit-max-ttl=4h`. The application renews it each hour. How long can this token live in total?
A: Four hours, because the explicit max TTL is a hard limit that renewals cannot extend.
B: Thirty-two days, because the system max TTL replaces an explicit max TTL.
C: Indefinitely, because renewing before expiry resets the explicit max TTL each time.
D: One hour, because the explicit max TTL applies only if the token is not renewed.
K: A
G: ## Explicit max TTL
An explicit max TTL is set on the token at creation. It is a hard limit on lifetime measured from creation: whatever the system, mount and auth method max TTLs say, the token cannot live past it, and later changes to those values do not affect it. Renewals do not reset or extend it. It applies to service tokens only (batch tokens always use a fixed TTL).
In this example the token gets a 1 hour TTL, can be renewed up to the fourth hour, and then expires.
W: Four hours: renewals extend the TTL window, but never beyond the explicit cap of four hours from creation.
X: B=System max TTL: the explicit value takes priority as the hard cap; it does not fall back to 32 days.
C=Reset on renewal: renewal resets the TTL, not the explicit max TTL.
D=Only if not renewed: the limit applies to the token's whole life, renewed or not.
T: Explicit max TTL is a hard cap from creation that renewal cannot move.

@ VLT-VA003 D3 T3.4 applied use-case
S: A long-running service keeps a database connection pool and must not lose its Vault token while it is alive, but the token should expire soon after the service is shut down. Which TWO statements about using a periodic token for this are accurate? (Select TWO)
A: Create it with `vault token create -period=2h`; each successful renewal resets the TTL to two hours.
B: If the service stops renewing, the token expires within the period, and its leases are revoked.
C: A periodic token can have no TTL at all because the period is only a hint to clients.
D: Periodic tokens are batch tokens, so renewals are performed by the service without storage.
E: A periodic token can be created by any token with `create` on `auth/token/create` and no further privileges.
K: A,B
G: ## Periodic tokens
A periodic token has no max TTL (unless an explicit max TTL is also set). At creation its TTL equals the period, and every renewal resets the TTL to that period. As long as the system renews within each period, the token never expires; if renewals stop, it expires within one period. Keep the period as short as the service can reliably renew.
Creating one needs `sudo` on the create endpoint (or a root token), a token store role with a period, or an auth method that issues them, such as AppRole. A token with both a period and an explicit max TTL behaves as periodic until the explicit max TTL is reached.
W: A=`-period`: the TTL starts at the period and goes back to the period after each renewal.
B=Expiry on silence: a stopped service stops renewing, so the token and its leases are cleaned up within the period.
X: C=No TTL: a periodic token has a TTL equal to its period; the period is not advisory.
D=Batch tokens: periodic behavior depends on renewal, which only service tokens support.
E=Plain create access: setting `-period` requires `sudo` or a root token, not just `create`.
T: Periodic tokens renew to a fixed period; they live as long as renewals continue and expire quickly after they stop.

@ VLT-VA003 D3 T3.4 applied troubleshooting
S: A client received a `403` with `invalid token` and `permission denied` messages when calling Vault with a token that worked yesterday. The token has a 24 hour TTL and was never renewed. What is the most likely explanation?
A: The token passed its TTL, so Vault revoked it and rejects it as invalid.
B: The policy attached to the token was deleted, which turns every call into an invalid token response.
C: Vault was sealed and unsealed overnight, and sealing deletes all service tokens.
D: The client IP changed, and Vault answers an unknown source address with `invalid token`.
K: A
G: ## Reading the error
Vault returns `403` with `invalid token` and `permission denied` when a token has been revoked, has exceeded its TTL, or is otherwise invalid. A token with the wrong policy access gets `403` with only `permission denied`.
Here the token was not renewed, so it expired after 24 hours. It and its leases were revoked, which is the intended outcome. The fix: renew before TTL ends, or authenticate again for a new token.
W: Expired TTL: an unrenewed token is revoked at the end of its TTL, so the next request fails as an invalid token.
X: B=Deleted policy: missing policy access shows `permission denied` only, and does not make the token invalid.
C=Seal and unseal: tokens are persisted in storage, so they survive a seal/unseal cycle; sealing does not delete them.
D=Changed IP: CIDR-bound tokens do restrict client IPs, but nothing in the scenario says the token is bound; the simplest cause is expiry.

@ VLT-VA003 D3 T3.5 applied definition
S: During a design review the team debates whether to use orphan tokens for long-lived integrations. Which statement about orphan tokens is accurate?
A: An orphan token has no parent, so it is the root of its own tree and is not revoked with other tokens.
B: An orphan token is a token whose parent has expired, so Vault immediately revokes it.
C: An orphan token can only be a batch token, because service tokens always have a parent.
D: An orphan token is a root token without an expiration, created once at `vault operator init` time.
K: A
G: ## Hierarchy and orphans
Normally a token created by another token is its child. Revoking a parent revokes all children, along with their leases, so nobody can escape revocation by building a tree of tokens. An orphan token has no parent, so it is not removed when other tokens are revoked.
Orphans can be created by:
- write access to `auth/token/create-orphan`;
- `sudo` or `root` on `auth/token/create` with `no_parent` set to true;
- token store roles configured as orphan;
- logging in with any non-`token` auth method (these tokens are orphans).
W: No parent: the orphan token starts its own tree and is not tied to anyone else's revocation.
X: B=Parent expired: revocation of the parent revokes the children, so children never turn into orphans this way (except via `revoke-orphan`).
C=Batch only: service tokens can be orphans, and batch orphans only matter for cross-cluster use.
D=Initial root token: an orphan is defined only by having no parent; it can carry any policies, and most orphans (for example tokens from auth method logins) are not root tokens.
T: Orphan = no parent; revoking other tokens does not affect it.

@ VLT-VA003 D3 T3.5 applied use-case
S: An engineer logged in with `vault login -method=userpass username=alice` and then ran `vault token create -policy=app` from that session. Later Alice's session token is revoked with `vault token revoke -self`. What happens to the `app` token?
A: Vault revokes it too, because it is a child of the revoked session token.
B: It keeps working, because tokens created with `-policy` are always orphans.
C: It keeps working, because only the leases of the parent are revoked.
D: It becomes an orphan with the same TTL, and an operator must revoke it separately.
K: A
G: ## Parent-child revocation
A token created by an existing token is its child by default (no `-orphan`, no orphan role). Revoking a token revokes its entire subtree and all their leases. In this case, Alice's token is revoked, so the `app` token and anything derived from it goes too.
To keep a child alive, the creator would need `sudo` to use `-orphan`, a `create-orphan` endpoint, or an orphan role. Alternatively `vault token revoke -mode=orphan <token>` revokes only that token and orphans its children.
W: Child of the revoked token: the revoke cascades down the tree, taking the app token with it.
X: B=Always orphans: `-policy` only sets policies; the token is still a child unless `-orphan` or an orphan role is used.
C=Only leases revoked: revoking a token removes its children as well as the leases; "leases only" is not the behavior.
D=Becomes an orphan: that only happens with `-mode=orphan` or `revoke-orphan`, which was not used here.
T: By default, revoking a parent token revokes all child tokens and their leases.

@ VLT-VA003 D3 T3.6 applied use-case
S: A team wants a token for a scheduler that must have only the `batch-jobs` policy, with no `default` policy. Which command creates it?
A: `vault token create -policy=batch-jobs -no-default-policy`
B: `vault token create -policy=batch-jobs -orphan`
C: `vault token create -policy=batch-jobs -type=batch`
D: `vault token create -policy=batch-jobs -use-limit=0 -renewable`

G: ## Policies on new tokens
In the same namespace a child token inherits all the parent's policies unless you assign policies with `-policy`. Even then, the `default` policy is usually added. `-no-default-policy` detaches it, so the token holds only the listed policies.

@ VLT-VA003 D3 T3.6 applied use-case
S: A deployment script needs a credential that works for exactly one request to Vault, then dies. Which creation option provides that?
A: `-use-limit=1`
B: `-ttl=1`
C: `-explicit-max-ttl=1`
D: `-renewable=false`
K: A
G: ## Use limit
`-use-limit` (API `num_uses`) sets how many times a token can be used. After the last use the token is revoked. Zero means no limit. Time options like `-ttl` and `-explicit-max-ttl` bound the duration and a bare number is parsed as seconds, so they would expire the token without respecting a usage count. `-renewable=false` stops renewal beyond the initial TTL, nothing more.
A token that must create child tokens should keep the default of 0 (unlimited), because the limit counts every request the token makes.
W: `-use-limit=1`: the token counts its uses and Vault revokes it automatically after the first one, which gives a one-shot credential regardless of how much TTL remains.
X: B=`-ttl=1`: this bounds time, not use; the token could be used many times within that second.
C=`-explicit-max-ttl=1`: a hard time cap from creation, again unrelated to usage count.
D=`-renewable=false`: it only prevents extending the token; the token could still be used many times before expiry.
T: One-shot token: `-use-limit=1`.

@ VLT-VA003 D3 T3.6 applied tradeoff
S: An operator wants workers to create their own tokens for a monitoring job, and these tokens must be periodic and orphan, but workers must not get `sudo` on `auth/token/create`. Which design fits?
A: A role with `period` and `orphan` set, plus a policy allowing `update` on `auth/token/create/monitor`.
B: Give workers a policy with `sudo` on `auth/token/create` so they can pass `-period` and `-orphan` themselves.
C: A batch token role, because batch tokens can be periodic and orphan when created from a role.
D: A shared root token that workers use to create tokens, revoked at the end of every day.
K: A
G: ## Roles delegate privilege
Setting `-period` or `-orphan` on plain create needs `sudo`. A role can apply those settings without the caller having `sudo`. The administrator writes the role (period, orphan, allowed policies, type) and grants workers only `update` on `auth/token/create/monitor`:
```
path "auth/token/create/monitor" {
  capabilities = ["update"]
}
```
Workers then run `vault token create -role=monitor`. This keeps least privilege: they can mint only what the role allows.
W: Role plus narrow path policy: the role carries the privileged settings, and workers need only permission on the role's create path.
X: B=`sudo` for workers: it works but gives each worker broad ability to create any token shape, violating least privilege.
C=Batch role: batch tokens cannot be periodic, so this cannot meet the requirement.
D=Shared root token: sharing root defeats the point; a daily revoke leaves hours of full access exposed.
T: Use a role to hand out period/orphan tokens without granting `sudo`.
