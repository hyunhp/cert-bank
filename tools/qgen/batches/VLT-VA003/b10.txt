@ VLT-VA003 D1 T1.2 advanced use-case
S: A retailer runs inventory workers on Google Compute Engine VMs, each with an attached service account. Security forbids copying any credential file onto the VMs, and only instances in zone `europe-west1-b` that carry the label `tier:inventory` may receive the `inventory-read` policy. Another team suggests reusing the AppRole method that already serves the on-premises servers. Which configuration meets the requirements with the LEAST credential handling?
A: Enable the gcp auth method and create a gce-type role with bound_zones europe-west1-b, bound_labels tier:inventory and token_policies inventory-read
B: Create an AppRole role with secret_id_bound_cidrs set to the VPC range, and bake its role ID and a long-lived secret ID into the VM image at build time
C: Enable the gcp auth method and create an iam-type role bound to the workers' service account, so that any VM using that account can log in from any zone
D: Enable the jwt auth method with Google as the OIDC discovery URL, and have an operator paste a freshly signed identity token into each VM after it boots
K: A
G: ## Platform identity instead of shipped secrets
The Google Cloud auth method lets workloads prove who they are with credentials that Google signs for them, so nothing has to be copied onto the machine. It supports two role types:
- **iam** roles authenticate a Google Cloud IAM service account; `bound_service_accounts` is required.
- **gce** roles authenticate a Compute Engine **instance** and can compare instance facts with bound fields such as `bound_zones`, `bound_regions`, `bound_labels` and instance groups.
## Matching the constraints
The rule here is about **where** the VM runs and **how it is labelled**, which only a gce role checks. Example:
`vault write auth/gcp/role/inventory type=gce bound_zones=europe-west1-b bound_labels=tier:inventory token_policies=inventory-read`
W: gce-type role: the VM signs in with its own platform identity, so no file is copied, and Vault checks the zone and label before issuing a token with inventory-read.
X: B=AppRole with a baked secret ID: a long-lived secret ID inside the image is exactly the credential file security forbids, and anyone who copies the image can log in from that range.
C=iam-type role: it identifies the service account, not the instance, so it cannot enforce the zone and label conditions; every VM using that account would qualify.
D=JWT with a pasted token: pasting a token after every boot is manual credential handling, and it does not check zone or label unless claims are bound separately.
T: For Compute Engine instances that must be filtered by zone, label or instance group, use a gce-type role of the gcp auth method.

@ VLT-VA003 D1 T1.4 advanced use-case
S: Engineers sign in to Vault through the OIDC auth method mounted at `oidc/`, backed by the corporate identity provider, which sends group names in a `groups` claim of the ID token. Access must follow IdP membership: a person added to the IdP group `payments-oncall` must receive the Vault policy `payments-ops` at their next login, and no administrator may create per-user objects in Vault. Which TWO configuration steps are required? (Select TWO)
A: Set groups_claim to groups on the OIDC role, so Vault reads each user's group names from the ID token claims during every login
B: Create an external group with policy payments-ops and a group alias named payments-oncall that uses the mount accessor of the oidc/ method
C: Create an internal group with policy payments-ops and add each engineer's entity ID to its member list whenever the IdP group changes
D: Set user_claim to groups on the OIDC role, so the alias name of each engineer's entity becomes the name of the IdP group they belong to
E: Add payments-ops to the token_policies of the OIDC role, so each engineer who completes the OIDC login receives the policy right away
K: A,B
G: ## Internal and external groups
Vault identity has two kinds of groups:
- **Internal groups**: an administrator manages the member list (entity IDs) inside Vault.
- **External groups**: membership comes from an outside system. An external group has exactly **one alias**, whose name is the outside group's name and whose mount accessor points at the auth method that reports it. Vault adds the entity to the group at login (and token renewal) when the auth method reports a matching group.
## Where OIDC group names come from
For JWT/OIDC roles, `groups_claim` names the claim that holds the user's groups; `user_claim` names the claim used as the entity alias name (for example `sub` or `email`).
So the two pieces are: read the groups claim, and map the IdP group to an external group that carries the policy.
W: A=groups_claim: without it the OIDC method reports no groups, so no external group membership can be computed at login.
B=External group with a group alias: the alias ties the IdP group name on this mount to the Vault group, and the group's policy flows to every member automatically.
X: C=Internal group: its members are entity IDs that an administrator must add and remove by hand, which is the per-user work the requirement forbids.
D=user_claim set to groups: user_claim identifies the person; pointing it at the groups claim would merge everyone in a group into one alias and breaks individual identity.
E=Policy on the OIDC role: every engineer who can log in through the role would get payments-ops, whether or not they belong to payments-oncall.
T: To drive Vault policies from IdP groups, read groups with groups_claim and map each IdP group to an external group alias on that auth mount.

@ VLT-VA003 D1 T1.6 advanced troubleshooting
S: A trusted orchestrator on host 10.20.0.5 logs in with AppRole and hands the resulting Vault token to batch workers in subnet 10.30.0.0/24. The role was written with `vault write auth/approle/role/batch token_bound_cidrs=10.20.0.0/24 secret_id_bound_cidrs=10.20.0.0/24`. Logins succeed, but every request the workers send with that token is rejected. The orchestrator must remain the only network location that can log in with the role. Which change fixes the workers while keeping that rule?
A: Add 10.30.0.0/24 to token_bound_cidrs and keep secret_id_bound_cidrs at 10.20.0.0/24, so tokens work from the workers while logins stay restricted
B: Add 10.30.0.0/24 to secret_id_bound_cidrs and keep token_bound_cidrs unchanged, so the secret ID and its tokens become usable from the worker subnet
C: Remove both CIDR settings and set bind_secret_id=false, so the role ID alone identifies the orchestrator and tokens are accepted from any address
D: Response-wrap the login response before handing it over, so that unwrapping on each worker re-binds the token to that worker's own address
K: A
G: ## Two different CIDR bindings on an AppRole role
- `secret_id_bound_cidrs` limits **which addresses may perform the login** with a secret ID of the role.
- `token_bound_cidrs` ties the **resulting token** to address blocks: Vault rejects requests that use the token from anywhere else.
Both can be set at once, and they answer different questions: "who may log in?" and "where may the token be used?"
## What happened here
The token was bound to `10.20.0.0/24`, so it works only from the orchestrator's network. The workers in `10.30.0.0/24` present a valid token from an address outside its binding and are refused.
The fix widens only the token binding; the login binding stays on the orchestrator's subnet.
W: Widen only token_bound_cidrs: tokens become usable from the worker subnet, while secret_id_bound_cidrs still allows logins only from 10.20.0.0/24.
X: B=Widen secret_id_bound_cidrs: this lets the worker subnet log in, which breaks the orchestrator-only rule, and the tokens stay bound to 10.20.0.0/24, so worker requests still fail.
C=Remove bindings and secret ID: anyone who learns the role ID could log in from anywhere, the opposite of restricting logins to the orchestrator.
D=Response wrapping: unwrapping returns the same token with the same bindings; wrapping protects the token in transit but never changes where it may be used.
T: secret_id_bound_cidrs controls where logins come from; token_bound_cidrs controls where the issued token may be used.

@ VLT-VA003 D1 T1.5 advanced use-case
S: An operator's laptop runs a maintenance script that must log in with userpass as `svc-maint` and pass the resulting token to one later `curl` call in the same script. The operator is already logged in as themselves, and the script must not replace the token stored in `~/.vault-token`, because the operator's next manual commands would otherwise run as `svc-maint`. The password is typed when the command prompts for it. Which login command fits the script?
A: `vault login -token-only -method=userpass username=svc-maint`, capturing its output in a shell variable to use as the token for the curl call
B: `vault login -method=userpass username=svc-maint`, then copying `~/.vault-token` into a variable and restoring the operator's previous file afterwards
C: `vault login -no-print -method=userpass username=svc-maint`, because that flag keeps the new token out of the token helper and shows nothing on screen
D: `vault login -method=userpass -path=svc-maint username=svc-maint`, so the new token is stored under a separate token helper entry for that path
K: A
G: ## How the CLI keeps tokens
After a successful `vault login`, the CLI hands the token to the **token helper**, which by default writes it to `~/.vault-token`. Later commands use that file, so a second login silently changes who you are.
## Login flags that matter
- `-no-store`: do not persist the token in the token helper; it is only printed.
- `-token-only`: print only the token without verification; a shortcut for `-field=token -no-store`.
- `-no-print`: hide the token in the output, **but still store it** in the token helper.
- `-path`: the mount path of the auth method (defaults to the method type), not a storage slot.
Example: `TOKEN=$(vault login -token-only -method=userpass username=svc-maint)` then `curl -H "X-Vault-Token: $TOKEN" ...`.
W: -token-only: it prints just the token and implies -no-store, so the operator's own token in ~/.vault-token stays untouched.
X: B=Login then restore the file: the file is overwritten first, and if the script fails before restoring it, the operator is left running as svc-maint; it is fragile by design.
C=-no-print: the flag only hides the token from the output; the documentation states the token is still stored in the token helper, which is the exact problem.
D=-path=svc-maint: -path names the mount where userpass is enabled; there is no auth method at svc-maint/, and the flag has nothing to do with where tokens are stored.
T: For scripts that must not disturb the operator's session, use `vault login -token-only` (or `-no-store`); `-no-print` still stores the token.

@ VLT-VA003 D1 T1.3 advanced tradeoff
S: A bank's 30 database administrators share one AppRole role ID and secret ID, kept in a password manager, to reach Vault from their laptops. Auditors now require that each request in the audit log be traceable to one named person, that access ends on the day someone leaves the corporate directory, and that no credential is shared between people. The bank already runs Active Directory for all staff. What should the Vault team do?
A: Enable the ldap auth method against Active Directory for the administrators, and keep AppRole only for unattended applications without a human user
B: Generate one AppRole secret ID per administrator with secret_id_num_uses=0, and record in a spreadsheet which administrator received which secret ID
C: Create a userpass account for each administrator with a password policy matching Active Directory, and disable each account by hand on departure
D: Issue each administrator a periodic token from a token store role, and revoke it through its accessor when HR reports that the person has left
K: A
G: ## Humans and machines authenticate differently
- **Machine methods** such as AppRole, Kubernetes or cloud IAM methods prove the identity of a workload. They suit unattended processes.
- **Human methods** such as LDAP, OIDC or userpass prove the identity of a person, ideally against the system that already manages people.
## Why the shared AppRole fails the audit
Every administrator logs in as the same role, so audit entries show one identity; the secret ID is shared; and nothing links access to employment status.
## What LDAP adds
With the ldap method, each person logs in with their own directory account. Vault creates an entity alias per user, so audit entries carry that person's identity, and a disabled directory account can no longer log in. Group mappings can carry the policies.
W: LDAP against Active Directory: each administrator signs in with a personal directory account, so actions are attributable and disabling the account in AD stops new logins the same day.
X: B=Secret ID per person: the audit log still shows the shared role, attribution depends on a spreadsheet, and access is not tied to the directory at all.
C=Userpass per person: attribution works, but a second password store must be kept in step with AD by hand, so a departure is only effective when someone remembers to disable the account.
D=Periodic tokens per person: a long-lived token per human is a bearer credential with no link to the directory, and revocation depends on a manual HR hand-off.
T: Give people a human auth method backed by the existing directory, and keep AppRole for workloads.

@ VLT-VA003 D2 T2.3 advanced use-case
S: Help-desk staff restore application secrets that developers soft-delete by mistake on the KV v2 mount `secret/`, using commands such as `vault kv undelete -mount=secret -versions=3 apps/web`. Staff must never be able to make any version permanently unrecoverable, and they must not be able to read secret values. Every restore is reviewed weekly by the security team. Which policy stanza gives the help desk exactly the access it needs?
A: `path "secret/undelete/apps/*" { capabilities = ["update"] }`, which allows restoring soft-deleted versions of keys below apps/ without reading them
B: `path "secret/data/apps/*" { capabilities = ["update"] }`, which allows every change to the stored versions of keys below apps/, including restoring them
C: `path "secret/destroy/apps/*" { capabilities = ["update"] }`, which allows the version-level maintenance actions for keys below apps/, such as restoring
D: `path "secret/metadata/apps/*" { capabilities = ["update", "delete"] }`, which allows managing the version list of keys below apps/ and restoring entries
K: A
G: ## KV v2 splits actions into separate API paths
A KV v2 mount does not expose one path per secret; it exposes one path **per action**:
- `secret/data/<key>`: read and write versions (and soft-delete the latest version)
- `secret/delete/<key>`: soft-delete specific versions
- `secret/undelete/<key>`: restore soft-deleted versions (`POST`)
- `secret/destroy/<key>`: permanently remove version data (`POST`)
- `secret/metadata/<key>`: read or write metadata; `DELETE` here removes **all** versions and metadata permanently
Because each action is a different path, a policy can allow one action and not the others.
## Applying it
`vault kv undelete` sends a POST to `secret/undelete/apps/web`, which needs `update` on that path, and it never returns secret data.
W: Undelete path with update: it permits only the restore action, gives no read on secret/data, and grants nothing on destroy or metadata.
X: B=Update on data paths: this lets staff write new versions over production secrets, and it does not cover the separate undelete endpoint the command calls.
C=Update on destroy paths: destroy permanently removes version data, which is exactly the irreversible action staff must never have; it does not restore anything.
D=Update and delete on metadata: delete on metadata permanently removes every version and the key's metadata, so staff could make data unrecoverable.
T: In KV v2, undelete, delete, destroy and metadata are separate paths; grant update on undelete only to let someone restore without destroying.

@ VLT-VA003 D2 T2.4 advanced use-case
S: Vault uses the LDAP auth method mounted at `ldap/` with mount accessor `auth_ldap_8c2f1a7d`. Each engineer needs a private KV v2 folder named exactly after their directory login, such as `secret/data/users/jdoe/`, so that support staff can find it by username. Entity names in this cluster are the values Vault generated automatically. One shared policy must serve every engineer. Which path should the policy use to give each engineer only their own folder?
A: `secret/data/users/{{identity.entity.aliases.auth_ldap_8c2f1a7d.name}}/*`, which resolves to the LDAP login name of the engineer's alias on that mount
B: `secret/data/users/{{identity.entity.name}}/*`, which resolves to the name of the requesting entity, the same value as the engineer's directory login
C: `secret/data/users/{{identity.entity.id}}/*`, which resolves to the identifier of the requesting entity, a stable value tied to the engineer's account
D: `secret/data/users/+/*` combined with a deny on other users' folders, which matches one folder segment for each engineer under the users/ path
K: A
G: ## Templated policy paths
A policy path can contain `{{ }}` parameters that Vault fills from the requesting token's identity at request time. Useful ones:
- `identity.entity.id` and `identity.entity.name`: the entity's ID and name.
- `identity.entity.aliases.<mount accessor>.name`: the **alias name** for a given auth mount, which for LDAP is the login username.
- `identity.groups.ids.<id>.name` and similar for groups.
## Choosing the parameter
The folder must be named after the directory login. The entity name is whatever Vault generated when it created the entity, and the entity ID is a UUID, so neither equals `jdoe`. The alias on the LDAP mount carries exactly that login name.
Example result for jdoe: `secret/data/users/jdoe/*`.
W: Alias name for the LDAP mount accessor: it expands to the engineer's LDAP username, so each person gets the folder support staff expect and nothing else.
X: B=Entity name: auto-created entity names are generated by Vault and do not match the directory login, so the folder names would not be jdoe.
C=Entity ID: it is stable and unique, but it is a UUID, so folders would not be named after the username as required.
D=Plus segment with denies: `+` matches any one segment, so every engineer could read every folder unless a deny is written for each pair of users, which does not scale.
T: To key a policy path on an auth method's username, use identity.entity.aliases.<mount accessor>.name.

@ VLT-VA003 D2 T2.3 advanced use-case
S: A provisioning bot creates and updates userpass accounts at `auth/userpass/users/<name>`. All policies for those users come from identity groups, so the bot must be able to set a password and nothing else; even if an attacker controls the bot, it must not be able to set token_policies, token_ttl or any other field on an account. Which policy stanza enforces this?
A: The path with capabilities create and update and `allowed_parameters = { "password" = [] }`, so any parameter other than password is refused
B: The path with capabilities create and update and `denied_parameters = { "token_policies" = [] }`, so the field that assigns policies is refused
C: The path with capabilities create and update and `required_parameters = ["password"]`, so every request has to supply a password value
D: The path with capabilities create and patch only, without update, so the bot can add new accounts but can never change any field on them
K: A
G: ## Parameter constraints in policies
A path stanza can restrict request parameters, not only capabilities:
- `allowed_parameters`: only the listed keys may appear (an empty list `[]` means any value for that key). When it is set, **every unlisted parameter is denied**.
- `denied_parameters`: the listed keys are refused; when used alone, all other parameters stay allowed.
- `required_parameters`: the listed keys must be present; it does not limit other keys.
These constraints are evaluated without regard to default values, and they are not supported for KV v2 paths, but they work on auth method endpoints such as userpass users.
## Example
`path "auth/userpass/users/*" { capabilities = ["create", "update"] allowed_parameters = { "password" = [] } }`
W: allowed_parameters with only password: it is an allow list, so token_policies, token_ttl and every other field are rejected while password can take any value.
X: B=denied_parameters on token_policies: it blocks that one field, but token_ttl, token_bound_cidrs and every other field remain allowed, which fails "nothing else".
C=required_parameters password: it only forces the password to be present; the request may still carry token_policies or any other field.
D=create and patch without update: creating an account already allows setting every field, including token_policies, so the attacker gains the escalation on new accounts.
T: To permit exactly one field on a path, use allowed_parameters, which denies every parameter it does not list.

@ VLT-VA003 D2 T2.4 advanced use-case
S: A token holds two policies. Policy `team` has `path "kv/data/team/*" { capabilities = ["read"] }` and policy `shared-writer` has `path "kv/data/team/shared" { capabilities = ["create", "update"] }`. The mount `kv/` is KV v2. A developer expects the token to read everything under team/ and also write the shared secret, and asks for a review before production use. Which THREE statements about this token are accurate? (Select THREE)
A: Reading kv/data/team/app1/config succeeds, because the glob in the team policy matches every path that starts with kv/data/team/
B: Reading kv/data/team/shared succeeds, because Vault merges the read from the glob stanza with the exact stanza's capabilities
C: Updating kv/data/team/shared succeeds, because the exact path stanza in shared-writer is the highest-priority match for that path
D: `vault token capabilities <token> kv/data/team/shared` returns create and update only, without read, for the shared secret path
E: Updating kv/data/team/app1 succeeds, because the create and update capabilities from shared-writer apply to the parent folder as well
F: Reading kv/data/team succeeds, because the team/* glob also matches the folder path itself when no trailing slash is present
K: A,C,D
G: ## How Vault picks the rule for a path
When a token has several policies, Vault gathers all their path stanzas and then uses the **most specific match** for the request path:
- If the **same pattern** appears in several policies, their capabilities are combined (union).
- If **different patterns** match, Vault applies only the **highest-priority** one. A pattern that ends in `*` ranks below one that does not, so an exact path beats a glob.
## Applying it
- `kv/data/team/shared` matches both `kv/data/team/*` and the exact path. The exact path wins, so the token has **create and update but not read** there.
- `kv/data/team/app1/config` matches only the glob, so it can be read.
- `kv/data/team/app1` gets only read from the glob; nothing grants update.
- `kv/data/team` (no trailing slash) does not start with `kv/data/team/`, so nothing matches and the default deny applies.
W: A=Deep read through the glob: a glob matches any path with that prefix, including deeper levels such as app1/config.
C=Update on the exact path: the exact pattern is the highest-priority match for kv/data/team/shared, and it grants create and update.
D=Capabilities without read: only the winning stanza counts, so read from the glob does not apply to the shared path.
X: B=Merged read: capabilities are unioned only for identical patterns; for different patterns Vault takes just the highest-priority match, so read is lost on shared.
E=Update on app1: the exact path covers only kv/data/team/shared and nothing below or beside it; app1 matches only the read glob.
F=Folder path: the glob requires the prefix kv/data/team/ including the slash, so kv/data/team itself is not matched and is denied.
T: Different patterns never merge: the highest-priority match wins, so an exact path stanza can take away capabilities a broader glob would give.

@ VLT-VA003 D2 T2.5 advanced use-case
S: A change pipeline manages the policy `app` stored in `app.hcl`. Each run must normalise the file's formatting so that reviews show only real changes, upload the policy to Vault, and then confirm what a test token that carries only `app` may do on `secret/data/app/db`. The pipeline authenticates with its own token, which holds a broad admin policy. Which command sequence meets all three needs?
A: `vault policy fmt app.hcl`, then `vault policy write app app.hcl`, then `vault token capabilities <test-token> secret/data/app/db`
B: `vault policy read app`, then `vault policy write app app.hcl`, then `vault token lookup <test-token>` to list the capabilities of the token on each path
C: `vault policy write app app.hcl`, then `vault policy list`, then `vault read sys/policy/app` to confirm which capabilities apply on secret/data/app/db
D: `vault policy fmt app.hcl`, then `vault write sys/policy/app policy=@app.hcl`, then `vault token capabilities secret/data/app/db` with no token argument
K: A
G: ## Policy commands in a pipeline
- `vault policy fmt <file>` rewrites a local policy file in the canonical format, so diffs only show real changes.
- `vault policy write <name> <file>` uploads the policy (equivalent to writing `sys/policy/<name>`).
- `vault token capabilities [token] <path>` returns the capabilities a token has on a path. With a token argument it uses `/sys/capabilities`; **without one it checks the caller's own token** through `/sys/capabilities-self`.
## Why the test token matters
The pipeline's own token holds a broad admin policy, so checking its own capabilities proves nothing about what `app` allows. The check must name the test token that carries only `app`.
W: fmt, write, capabilities with the test token: the file is normalised, the policy is uploaded, and the capability check runs against the token that holds only app.
X: B=Token lookup: lookup shows a token's properties and policy names, not its capabilities on a path, and reading the old policy first does not normalise the file.
C=Policy list and read: these show the policy names and the raw rules text; they do not evaluate capabilities for a path, and nothing formats the file.
D=Capabilities without a token argument: the first two steps work, but the check runs against the pipeline's admin token, so it says nothing about the app policy.

- **Super-user access**: instead of generating a root token, you click Generate token in the HCP portal, which returns an **admin token valid for 6 hours**.
- Upgrades, backups and snapshots are handled by HashiCorp.
W: admin namespace and portal admin token: scripts target the namespace where customer mounts live, and the short-lived admin token replaces root-token generation.
X: B=generate-root with recovery keys: on HCP Vault Dedicated privileged access comes from the portal's admin token; the root namespace is not where customer mounts live.
C=Manual unseal with the KMS key: auto-unseal is configured for every cluster, so there is no unseal step, and a KMS key ID is not an unseal key.
D=Consul storage stanza: the storage backend is Integrated Storage and is managed by HashiCorp; customers do not configure it.
T: On HCP Vault Dedicated, work in the admin namespace and use the portal's 6-hour admin token; seal and storage are managed for you.

@ VLT-VA003 D9 T9.1 advanced troubleshooting
S: Vault Agent on long-lived VMs uses AppRole auto-auth with `role_id_file_path` and `secret_id_file_path`. A trusted orchestrator writes the secret ID file once at provisioning. Days later, after a reboot and after Agent's last token had expired, Agent cannot log in and reports that the secret ID file is missing. Security requires that a secret ID never stays on disk after use. What is the best fix?
A: Have the orchestrator write a fresh wrapped secret ID before each Agent start, and set secret_id_response_wrapping_path to the role's secret-id path
B: Set remove_secret_id_file_after_reading=false in the approle method config, so Agent can read the same secret ID file again after every restart
C: Update the AppRole role with bind_secret_id=false, so that Agent can log in with the role ID file alone each time the VM restarts in the future
D: Raise secret_id_ttl and secret_id_num_uses on the AppRole role, so that the original secret ID stays valid for every later login after a reboot
K: A
G: ## Agent and the secret ID file
The Agent `approle` auto-auth method reads a role ID and a secret ID from files. By default it **deletes the secret ID file after reading it** (`remove_secret_id_file_after_reading` defaults to `true`). Agent caches the values in memory, so a running Agent can re-authenticate, but a restarted Agent has nothing to read unless a new file is written.
## Wrapped secret IDs
With `secret_id_response_wrapping_path`, Agent expects the file to contain a **response-wrapping token** whose creation path must match the configured value (for example `auth/approle/role/web/secret-id`). The secret ID itself never sits on disk in plain form, and a token created elsewhere is rejected.
W: Fresh wrapped secret ID per start: each restart gets a new single-use credential, Agent deletes the file after reading, and the creation-path check guards against substitution.
X: B=Keep the file: Agent could reuse it, but a plain secret ID would remain on disk permanently, which security forbids.
C=bind_secret_id=false: logins would rely on the role ID alone, removing the secret ID requirement instead of delivering it safely.
D=Longer secret ID TTL and uses: the file is still deleted after the first read, so a longer-lived secret ID does not help Agent after a restart.
T: Agent deletes the AppRole secret ID file after reading; deliver a fresh, ideally wrapped, secret ID before each start instead of keeping it on disk.

@ VLT-VA003 D9 T9.1 advanced use-case
S: Nginx on a VM serves a TLS certificate that Vault Agent renders from the PKI engine with a file `template` stanza. The private key file must be readable only by its owner, and nginx must be reloaded every time Agent writes a new certificate, but not on other occasions. Nginx reads the certificate from disk and must keep running while Agent renews. Which TWO settings meet these needs? (Select TWO)
A: An exec block in the template stanza with command ["systemctl", "reload", "nginx"], which runs only when the rendered output has changed
B: perms = "0600" in the template stanza, so Agent writes the rendered certificate and key file with owner-only read and write permissions
C: Process supervisor mode with an env_template for the certificate and an exec block for nginx, so Agent restarts nginx when the value changes
D: static_secret_render_interval = "1m" in template_config, so that Agent re-renders the certificate every minute and nginx picks it up on its own
E: exit_after_auth = true in the Agent configuration, so that Agent exits after rendering and systemd restarts nginx together with Agent each time
K: A,B
G: ## Template stanza options
A file `template` stanza renders a destination file and can control what happens around it:
- `exec { command = [...] }` runs a command **when the template is rendered and the output has changed** (it replaces the deprecated `command` option).
- `perms` sets the file permissions of the rendered file, for example `"0600"`.
- `backup`, `wait` and `error_on_missing_key` tune other behaviour.
## Process supervisor mode is different
In process supervisor mode Agent injects secrets as **environment variables** into one child process and restarts it on changes. It requires `env_template` blocks and one top-level `exec`, and it is **incompatible with file templates**, so it does not fit a program that reads its certificate from disk.
W: A=exec block: nginx is reloaded exactly when Agent writes a changed certificate.
B=perms 0600: the rendered key file is created readable only by its owner.
X: C=Process supervisor mode: it delivers environment variables to a child process and cannot be combined with file templates, while nginx needs files on disk.
D=Render interval: this setting governs non-leased secrets such as KV, and re-rendering alone does not make nginx load a new certificate.
E=exit_after_auth: Agent would stop after authenticating and rendering once, so it would no longer renew the certificate.
T: For file-based consumers, use the template exec block to reload on change and perms to protect the rendered file; supervisor mode is for env-var consumers.

@ VLT-VA003 D9 T9.2 advanced troubleshooting
S: A team adds a VaultStaticSecret for the KV v2 secret `app/db` with `destination.name: app-db` and no other destination fields. No Kubernetes Secret named app-db exists yet, and the team wants Vault Secrets Operator to create and own it. The resource reports a sync error and the Secret never appears, although the VaultAuth works for other resources in the namespace. Which change fixes it?
A: Set destination.create: true, so that the operator creates the app-db Secret itself instead of expecting an existing Secret to update
B: Set destination.overwrite: true, so that the operator replaces the app-db Secret on every sync even though create stays at its default value
C: Set hmacSecretData: false, so that the operator skips computing a data MAC, which is what blocks the first write of a brand-new Secret
D: Set refreshAfter: 10s, so that the operator retries the sync more often until Kubernetes allows the new Secret to be written into the namespace
K: A
G: ## The destination block
Every VSO secret resource syncs into a Kubernetes Secret described by `destination`:
- `name`: the Secret's name;
- `create` (default **false**): create the Secret; if the Secret already exists, it should be left false;
- `overwrite` (default false): replace an existing Secret when `create` is true, useful when migrating to VSO;
- `labels` and `annotations` also require `create: true`.
With the default `create: false`, VSO expects the Secret to exist already and only updates it.
## Example
```
destination:
  name: app-db
  create: true
```
W: create: true: VSO then creates and owns the app-db Secret and keeps it in sync with the KV secret.
X: B=overwrite: it applies only when create is true and a Secret already exists; with create false nothing is created.
C=hmacSecretData false: the MAC is used for drift detection and does not block creation; turning it off also disables rollout restarts.
D=Shorter refreshAfter: syncing more often repeats the same failure, because VSO is still not allowed to create the Secret.
T: VSO only updates an existing Kubernetes Secret unless destination.create is true.

@ VLT-VA003 D9 T9.2 advanced use-case
S: A Deployment reads PostgreSQL credentials from a Kubernetes Secret synced by a VaultDynamicSecret from `db/creds/orders`. The application reads the credentials only at start-up, and when the team deletes the VaultDynamicSecret during a decommission, the database user it holds must be removed at once rather than at lease expiry. Renewal timing can stay at the default. Which TWO settings on the VaultDynamicSecret meet these needs? (Select TWO)
A: rolloutRestartTargets listing the Deployment, so the operator triggers a rollout restart whenever it syncs new credentials into the Secret
B: revoke: true, so that the operator revokes the existing lease, and with it the database user, when the VaultDynamicSecret resource is deleted
C: renewalPercent: 95, so that the operator renews the lease closer to its end and the application keeps its credentials for a longer time
D: allowStaticCreds: true, so that the operator treats the credentials as rotated by Vault and restarts the Deployment after each rotation
E: refreshAfter: 1h, so the operator fetches new credentials every hour and the Deployment picks them up the next time its pods restart
K: A,B
G: ## VaultDynamicSecret fields that matter here
- `rolloutRestartTargets`: for applications that cannot reload a rotated secret. VSO triggers a rollout restart of each target whenever the secret changes.
- `revoke`: revoke the existing lease when the resource is deleted.
- `renewalPercent`: when to renew, as a percent of the lease duration; default 67, **maximum 90**.
- `allowStaticCreds`: only for credentials that Vault rotates itself (database static roles, `static-creds` paths).
- `refreshAfter`: only needed when the source returns no lease TTL; a lease duration takes precedence.
## Applying it
The application reads credentials only at start-up, so it needs restarts when VSO syncs new ones, and decommissioning needs immediate revocation.
W: A=rolloutRestartTargets: new credentials reach the application because its pods restart after each sync.
B=revoke: true: deleting the resource revokes the lease, so the database user disappears at once.
X: C=renewalPercent 95: the maximum allowed is 90, and renewal timing was to stay at the default anyway.
D=allowStaticCreds: it is meant for static roles under static-creds paths; db/creds is a dynamic role, so this setting does not apply.
E=refreshAfter 1h: the dynamic lease duration takes precedence over refreshAfter, and without a restart target the application would still keep old credentials.
T: For a VaultDynamicSecret feeding an app that reads secrets only at start-up, add rolloutRestartTargets; set revoke: true to remove credentials when the resource is deleted.
