@ VLT-VA003 D1 T1.1 applied definition
S: A new engineer asks what Vault does when a client presents credentials to an auth method such as userpass or LDAP. Which statement is accurate?
A: The auth method verifies the credentials, then Vault issues a token that carries the identity and the policies mapped at login
B: The auth method verifies the credentials, then Vault returns the secrets the caller is permitted to read in the same response
C: The auth method stores the credentials in the barrier, then Vault issues a lease that the client must renew to stay logged in
D: The auth method verifies the credentials, then Vault applies its policies to later requests using the original username each time
K: A
G: ## What an auth method does
Before a client can do anything in Vault it must authenticate. An auth method is the component that performs that authentication and assigns an identity and a set of policies to the caller. Many auth methods delegate the actual decision to an external system (GitHub, LDAP, Kubernetes, a cloud provider); others, such as userpass, hold the credentials themselves.
## The result is a token
On success Vault generates a token. Conceptually it is like a session ID on a website: the client sends it with every later request, and the policies attached to it at login decide what is allowed.
- The CLI attaches the token automatically after `vault login`.
- With the API the client must send the token itself, for example in the `X-Vault-Token` header.
- Secrets are not returned by login; they are read afterwards with the token.
W: Token with identity and policies: authentication verifies who the caller is, and the output is a token carrying the policies mapped at login time. Every later request is authorized from that token.
X: B=Secrets in the login response: login returns only a token and its metadata. Reading secrets is a separate request that the token's policies must allow.
C=Credentials stored with a lease to renew: the credential check is not a lease on the credentials; the token Vault returns has a TTL, and the client renews or re-authenticates when it expires. The auth method does not copy the credentials into a renewable lease.
D=Policies by username on each request: later requests are authorized from the token, not by re-checking the username. The username is not sent again after login.
T: An auth method verifies the caller and Vault answers with a token that holds the identity and policies for later requests.
V: Vault

@ VLT-VA003 D1 T1.6 applied use-case
S: An operator runs vault auth enable -path=corp-ldap ldap. Where is this auth method now reachable, and what does a path-based mount allow?
A: At auth/corp-ldap, and the same method type can be mounted again at another path with its own configuration
B: At auth/ldap, since the type fixes the mount path and the flag only sets a label
C: At corp-ldap, outside the auth/ prefix, because custom paths are mounted like secrets engines
D: At sys/auth/corp-ldap, and only one mount of a given method type is allowed per cluster
K: A
G: ## Mounting auth methods
Auth methods are mounted in the Vault mount table, much like secrets engines, but always under the `auth/` prefix. By default an auth method mounts at `auth/<type>`, so enabling `github` gives `auth/github`.
The path is customizable with `-path`. That lets one cluster run several instances of the same type, for example two LDAP directories for two business units, each with its own configuration.
- `vault auth enable -path=corp-ldap ldap` creates `auth/corp-ldap`.
- Login then goes to `auth/corp-ldap/login/<username>`.
- Use `vault auth list` to see the mounts.
W: Custom path under auth/: the path flag replaces the default mount name, and since each mount has its own configuration, the same type can be mounted more than once.
X: B=Type decides the path: the default path uses the type only when no path is given. The flag changes the real mount location and the API path.
C=Outside the auth prefix: every auth method is mounted under `auth/`; only secrets engines mount at top-level paths of their own.
D=sys/auth only, one mount per type: `sys/auth` is the management API used to enable and list mounts, not where login happens, and nothing limits a type to a single mount.
T: Auth methods live under auth/ at the path you choose, and the same method type can be mounted several times.
V: Vault

@ VLT-VA003 D1 T1.1 advanced troubleshooting
S: A team disables the GitHub auth method that contractors used for a month. What happens to contractors who are still logged in through it?
A: They are automatically logged out, because disabling an auth method also invalidates the tokens it issued
B: They stay logged in until their tokens expire, because tokens are independent of the method that issued them
C: They keep working for 24 hours until Vault refreshes its mount table, then every request is rejected
D: They stay logged in, but their policies are reduced to default because the method no longer supplies mappings
K: A
G: ## Tokens are tied to the method that issued them
When an auth method is disabled, Vault logs out every user who authenticated through it: the tokens it created are revoked along with their leases. This makes disabling a method a fast way to cut off a whole population, for example after a contractor engagement ends or a provider is compromised.
## Related behavior with external providers
For external methods such as GitHub, Vault calls the provider at login and again at token renewal. If an account is disabled in the external system, Vault denies renewal, but an already issued token stays valid for its original period unless it is revoked in Vault. That is why operators set appropriate token TTLs and why disabling the method is the stronger tool.
W: Automatic logout: disabling the method revokes the tokens it issued, so the contractors lose access immediately without anyone listing tokens or revoking them one by one.
X: B=Valid until expiry: that describes an account disabled at the external provider, not a disabled method. Disabling the mount revokes the tokens it issued.
C=24-hour refresh: Vault has no mount-table refresh delay; the change takes effect when the disable completes.
D=Reduced to default: the tokens are not downgraded; they are revoked, so even the default policy no longer helps them.
T: Disabling an auth method logs out everyone who authenticated through it.
V: Vault

@ VLT-VA003 D1 T1.2 applied use-case
S: A platform team wants developers to log in to Vault from the CLI and the UI with the accounts they already use in their corporate Active Directory. Which auth method fits best?
A: LDAP, which checks passwords against the existing directory and maps its groups to policies
B: Userpass, because it can import usernames and passwords from an external directory on a schedule
C: AppRole, because each developer receives a RoleID and SecretID that match the directory account
D: TLS certificates, because directory users sign in with a client certificate
K: A
G: ## Matching the method to the identity source
The best auth method is usually the one that reuses an identity system that already exists.
- **LDAP** authenticates users with a directory username and password and lets Vault map LDAP users and groups to policies through its `users/` and `groups/` paths. No second set of passwords is created.
- **Userpass** keeps its own username and password list in Vault; it cannot read from an external source.
- **AppRole** is aimed at machines and automated workflows, not at people.
- **Cert** authenticates TLS client certificates that you have configured as trusted.
W: LDAP: it integrates Vault with the existing directory so people use the credentials they already have, and group membership drives the policies they receive.
X: B=Userpass import: userpass is configured directly through its `users/` path and cannot read usernames or passwords from an external source.
C=AppRole for developers: AppRole is oriented to automated workflows and is less useful for human operators; it has no link to directory accounts.
D=TLS certificates: certificate auth trusts certificates or CAs configured in Vault, and does not look up directory accounts.
T: For people who already have directory accounts, use LDAP so Vault reuses them instead of keeping a second password list.
V: Vault

@ VLT-VA003 D1 T1.2 applied use-case
S: A company uses Okta-style single sign-on and wants employees to open the Vault UI and sign in with their browser through the identity provider. Which Vault auth method serves this?
A: JWT/OIDC, with an OIDC role that redirects users to the provider and returns verified claims
B: GitHub, because its personal access token carries the single sign-on provider session
C: Userpass, because the UI form posts the provider session cookie
D: AppRole, because the UI exchanges the browser session for a RoleID
K: A
G: ## OIDC in Vault
The `jwt` auth method can authenticate with Vault using OIDC or by providing a JWT directly. For OIDC, the user's browser is sent to the configured provider, the user signs in there, and the browser returns to Vault with a code that Vault exchanges for claims. This can start from the Vault UI or from `vault login -method=oidc`.
- The role defines `allowed_redirect_uris`, and those must match what is registered with the provider.
- Claims such as `groups` can be bound with `bound_claims` and mapped to policies.
- The alias name comes from the claim named in `user_claim`.
W: JWT/OIDC: it is built for browser sign-in via a provider and for verifying JWTs, mapping claims to Vault policies.
X: B=GitHub PAT: that method accepts a GitHub personal access token with `read:org`; it does not trust an SSO provider's session.
C=Userpass cookie: userpass checks a username and password held in Vault and knows nothing about provider sessions.
D=AppRole from a session: AppRole needs a RoleID and usually a SecretID, and has no browser flow.
T: Browser single sign-on against an identity provider maps to the JWT/OIDC auth method.
V: Vault

@ VLT-VA003 D1 T1.2 advanced comparison
S: A CI system already receives signed JSON Web Tokens from its own platform, and no browser is available. Which approach lets it log in to Vault without a stored password?
A: A JWT-type role on the jwt method, verified with discovery-URL keys or static public keys
B: An OIDC-type role, because it always opens a local browser callback on port 8250
C: A userpass entry whose password is the JWT string, since userpass accepts any signed token value
D: The cert auth method, because a JWT is a client certificate in PEM format
K: A
G: ## Two modes in one method
The `jwt` auth method has two role types, chosen per role.
- **OIDC role**: interactive. It uses the Authorization Code flow with the user's browser and redirect URIs. The CLI listens on a localhost callback such as `http://localhost:8250/oidc/callback`.
- **JWT role**: non-interactive. The client sends a JWT to Vault, which verifies the signature using static public keys (`jwt_validation_pubkeys`) or keys fetched from an OIDC discovery URL (`oidc_discovery_url`), checks bound claims, and returns a token.
A pipeline that already holds a JWT uses a JWT role.
W: JWT role: Vault verifies the signature locally or through discovery and applies claim bindings, so a machine without a browser can authenticate with the JWT it already has.
X: B=OIDC role: it depends on a browser redirect, which a CI system does not have.
C=JWT as a password: userpass checks the stored password hash for a user; it does not validate tokens.
D=Cert method: it authenticates TLS client certificates presented during the handshake, and a JWT is a different format.
T: Use a JWT role for machines that hold a JWT and an OIDC role for people who sign in through a browser.
V: Vault

@ VLT-VA003 D1 T1.2 applied use-case
S: A service running as a pod in a Kubernetes cluster needs a Vault token without anyone copying a secret into the pod. Which auth method fits?
A: Kubernetes, which validates the pod's service account token against a bound role
B: Userpass, with the password injected as an environment variable at deploy time
C: GitHub, with a personal access token of the developer who deployed the pod

G: ## Kubernetes auth
The `kubernetes` auth method authenticates a client with a Kubernetes service account token, which makes it simple to introduce a Vault token into a pod. The pod posts its JWT and a role name to `auth/kubernetes/login`.
- Vault validates the JWT with the Kubernetes TokenReview API.
- The role restricts who may use it: `bound_service_account_names` and `bound_service_account_namespaces`.
- The token's policies come from the role.
The service account token is already present in the pod, so no secret has to be distributed.
W: Kubernetes auth: the identity is the pod's own service account, bound to a role by name and namespace, so nothing is copied into the pod.
X: B=Injected password: that creates a long-lived secret to distribute and rotate, which is what a platform-native method avoids.
C=Developer's GitHub token: it ties a service to a person's account and its `read:org` scope.
D=Node name in LDAP: LDAP validates user passwords against a directory, and node names are not accounts.

@ VLT-VA003 D1 T1.2 advanced use-case
S: EC2 instances and Lambda functions must log in to Vault with no operator pre-provisioning credentials to them. Which auth method and type is recommended?
A: aws with the iam type, signing an sts:GetCallerIdentity request with credentials the workload already has
B: aws with the ec2 type only, since it is the recommended type for every compute service
C: approle with a SecretID baked into the machine image so every instance shares it
D: cert with the instance's public IP address used as the certificate subject
K: A
G: ## Cloud auth methods
Vault has auth methods for AWS, Google Cloud and Azure (among others). They let a workload prove its identity with something the cloud already gave it.
## AWS: iam versus ec2
- **iam**: the client signs an `sts:GetCallerIdentity` request with IAM credentials supplied by an instance profile or the Lambda environment and sends it to Vault. Vault forwards it to AWS STS. The Vault server needs network access to STS; the client does not.
- **ec2**: uses signed instance identity metadata, so it works only for EC2 instances.
The docs say the `iam` method is the recommended approach because it is more flexible and aligns with AWS access-control best practices.
W: aws iam type: Lambda functions and EC2 instances both hold IAM credentials, so signing a GetCallerIdentity request needs no secret placed by an operator.
X: B=ec2 only: the ec2 type works only for EC2 instances, so Lambda cannot use it, and the docs recommend iam.
C=Shared SecretID in an image: a secret baked into an image is exactly the pre-provisioned credential the question rules out, and every instance would share it.
D=Cert by public IP: certificate auth matches trusted certificates, not IP addresses, and instances do not hold client certificates by default.
T: On AWS, the iam type lets compute services authenticate with credentials they already have.
V: Vault, AWS IAM, AWS Lambda, Amazon EC2

@ VLT-VA003 D1 T1.6 advanced use-case
S: Services in a private network already hold X.509 client certificates issued by the company CA. Which Vault configuration lets them authenticate with those certificates?
A: Enable cert auth, register the trusted CA on a role, and let the listener accept client certificates
B: Enable userpass and use each certificate's serial number as the account username with a shared password
C: Enable the token auth method and upload the CA certificate to the token store
D: Enable the approle auth method and set the certificate fingerprint as the RoleID
K: A
G: ## TLS certificate authentication
The `cert` auth method authenticates SSL/TLS client certificates that are signed by a CA or self-signed. Trusted certificates and CAs are configured directly on the method under `certs/`, each as a named role with policies.
- The certificate must have `ExtKeyUsage` set to `ClientAuth` or `Any`.
- The certificate is sent during the TLS handshake, so the listener must allow client certificates: `tls_disable` and `tls_disable_client_certs` must be false in the Vault configuration.
- CRLs or OCSP can be used for revocation checks.
- CLI: `vault login -method=cert -client-cert=cert.pem -client-key=key.pem name=web`.
W: Cert auth with a registered CA: this is the method built for client certificates, and the role decides which policies the certificate holder gets.
X: B=Userpass with serials: userpass compares passwords stored in Vault; it never inspects certificates.
C=Token store upload: the token auth method creates and validates Vault tokens and has no place for CA certificates.
D=AppRole with fingerprint: a RoleID is a Vault-generated identifier, and AppRole does not read certificates.
T: Use the cert auth method with a registered CA and a listener that accepts client certificates.
V: Vault

@ VLT-VA003 D1 T1.6 applied use-case
S: A deployment pipeline needs to give a new application a way to log in with AppRole while limiting the time and number of times the application's login secret can be used. Which role settings do this?
A: secret_id_ttl and secret_id_num_uses on the role, which cap each SecretID's lifetime and uses
B: token_policies and token_type, which bound the SecretID's lifetime and the uses it allows
C: bind_secret_id=false, which makes the SecretID single use automatically
D: role_id_ttl, which expires the RoleID after the first login
K: A
G: ## The two AppRole credentials
An AppRole login needs a `role_id` and, by default, a `secret_id`.
- **RoleID** identifies the role. It is like a username and is not secret in the same way.
- **SecretID** is the credential that is meant to stay secret. It can be generated against a role (Pull mode).
Roles can restrict SecretIDs with settings such as `secret_id_ttl` (lifetime) and `secret_id_num_uses` (number of logins). Other settings, like `token_ttl` and `token_type`, apply to the token issued after login, not to the SecretID.
## Example
`vault write auth/approle/role/my-role token_type=batch secret_id_ttl=10m secret_id_num_uses=40`
W: Role SecretID settings: lifetime and use count are set on the role and limit each SecretID that it issues.
X: B=Token settings: token_policies and token_type shape the issued token, not the SecretID's validity.
C=bind_secret_id=false: this removes the requirement for a SecretID altogether, which weakens login rather than limiting use.
D=role_id_ttl: no such mechanism expires the RoleID after one login; SecretIDs carry the limits.
T: Limit a SecretID with secret_id_ttl and secret_id_num_uses on the AppRole.
V: Vault

@ VLT-VA003 D1 T1.6 advanced troubleshooting
S: Pods in the namespace demo fail to log in with the Kubernetes method, while the same service account works in namespace default. The role has bound_service_account_namespaces=default. What fixes it?
A: Add demo to the role's bound service account namespaces, or write a role that lists it
B: Re-enable the auth method with -path=demo so that the namespace becomes its mount
C: Give the pods a RoleID, since namespaces other than default need AppRole
D: Set disable_local_ca_jwt on every pod so Vault ignores the namespace

G: ## Role binding in Kubernetes auth
A Kubernetes auth role limits which service accounts may use it:
- `bound_service_account_names`: names of the service accounts (or `*`).
- `bound_service_account_namespaces`: namespaces the accounts must be in.
Vault accepts the login only if the JWT's service account matches both. A pod in another namespace is rejected even with the same name, so you either extend the role or write a separate role for the new namespace.
`vault write auth/kubernetes/role/demo bound_service_account_names=myapp bound_service_account_namespaces=demo token_policies=app`
W: Extend the namespace binding: the failure comes from the role's namespace constraint, so the role must allow the second namespace.
X: B=Mount per namespace: the mount path is unrelated to Kubernetes namespaces; roles hold the bindings.
C=Switch to AppRole: nothing in Kubernetes auth limits it to the default namespace; the role's namespace binding is the cause.
D=disable_local_ca_jwt: this option controls how Vault trusts the cluster CA and reviewer token and does not relax the namespace binding.
T: Kubernetes roles accept only the service account names and namespaces they list.
V: Vault, Kubernetes

@ VLT-VA003 D1 T1.3 applied definition
S: Which statement best describes the difference between how humans and machines should authenticate to Vault?

@ VLT-VA003 D1 T1.3 advanced troubleshooting
S: An audit review finds that five operators log in with the same userpass account. Which problem does this create, and what is the better design?
A: Audit entries name one entity for all five, so actions cannot be tied to a person; give each their own login
B: Vault allows one token per userpass account, so four people are locked out; raise a limit
C: The shared account's policies are merged with each person's group policies, which grants extra access
D: Userpass tokens cannot be audited, so enable the file audit device with a higher log level
K: A
G: ## Identity and the audit trail
When a client authenticates (with any method except the token method), Vault creates or reuses an entity and ties its ID to the issued token. When that token is used, the entity ID is audit logged, which gives a trail of actions by specific users.
If five people log in as one user, all of their actions map to a single entity, so the log cannot say who did what.
- Give each operator their own identity: LDAP, OIDC, or at least individual userpass entries.
- Use groups to give shared permissions to a set of entities, rather than shared credentials.
W: One entity for five people: audit attribution is lost; individual logins plus group policies keep both attribution and shared permissions.
X: B=One token per account: Vault does not limit userpass accounts to a single token.
C=Merged group policies: a shared account has no per-person group membership, so nothing is merged; the problem is attribution.
D=Userpass not audited: logins and requests are audited like any other; the audit log is limited by who the entity is, not by the method.
T: Individual logins keep the entity in audit logs meaningful; share permissions through groups, not credentials.
V: Vault

@ VLT-VA003 D1 T1.4 applied definition
S: Which statement about entities and aliases in Vault identity is accurate?
A: An entity is the consolidated identity of a client, and an alias maps one of its accounts on an auth method mount to it
B: An alias is the consolidated identity, and an entity is the login name used on one auth method mount
C: An entity is created only when an operator writes it by hand, and logins without an entity are rejected
D: An alias belongs to the whole auth method type, so every mount of that type shares one alias
K: A
G: ## Entities and aliases
A person may have accounts with several identity providers. Vault Identity ties those authentications to a single representation, the **entity**. Each account is mapped as an **alias**: a login name on a particular auth method mount.
- Example: someone with a GitHub account and an LDAP account can be one entity with two aliases.
- An entity can hold zero or more aliases.
- An alias is identified by the alias name together with the accessor of the auth mount, not the type alone.
## Implicit creation
When a client authenticates (except through the token method) and no matching entity exists, Vault creates an entity and attaches a new alias. Operators can also create entities in advance.
W: Entity plus aliases: the entity is the consolidated identity, and each alias ties an account on an auth mount to it.
X: B=Reversed terms: the alias is per mount; the entity is the whole identity.
C=Entities only by hand: they are created implicitly at login, and login does not require a hand-made entity.
D=Alias per type: the alias is bound to the mount's accessor, so two mounts of the same type have separate aliases.
T: An entity consolidates a client's identity and each alias maps one account on one auth mount to it.

@ VLT-VA003 D1 T1.4 advanced comparison
S: An engineer has accounts at two GitHub auth mounts, auth/github-a and auth/github-b, and one at auth/ldap. Which statement describes what Vault allows?
A: One entity can hold all three aliases, because each lives on a different mount
B: One entity holds only one alias per auth type, so the two GitHub aliases need two entities
C: The three accounts are merged into one entity automatically when the usernames match
D: An entity may hold two aliases from the same mount but not from different types
K: A
G: ## One alias per mount
The identity docs say an entity cannot have more than one alias for a particular authentication backend (mount). Aliases of the same type are fine, as long as the mounts are different.
- github-a plus github-b plus ldap on one entity: allowed.
- Two aliases from the same github-a mount on one entity: not allowed.
Merging is not automatic. Entities are separate unless an operator creates the alias on the same entity or merges the entities. The alias name and the mount accessor identify the alias.
W: One alias per mount: all three mounts differ, so the three aliases can belong to the same entity if an operator ties them together.
X: B=One alias per type: the restriction is per mount, not per type.
C=Automatic merge by username: Vault does not match usernames across mounts; each login creates its own implicit entity unless identity was set up in advance.
D=Same mount allowed: that is the forbidden case; the rule is one alias per mount.
T: An entity holds at most one alias per auth mount, but aliases of one type from different mounts can share an entity.

@ VLT-VA003 D1 T1.4 applied use-case
S: Which TWO statements about policies attached to an identity entity are accurate? (Select TWO)
A: They add capabilities on top of the policies on the token
B: They replace the policies that were set on the token at login
C: They are evaluated at request time, so changing them affects tokens already issued
D: They are copied into the token when it is created and never change afterward
E: They apply only to tokens created through the userpass auth method
K: A,C
G: ## Entity policies
Policies can be assigned to an entity. If a token carries an entity ID and that entity has policies, the token may perform actions the entity's policies allow, in addition to what its own policies allow.
- Before identity, the names of policies on a token were fixed at creation. Entity policies are evaluated at request time, which lets operators change the access of tokens that were already issued.
- They are additive: they do not replace the token's policies.
- Group memberships add further policies at request time.
Be careful with write access to identity endpoints: changing an entity, alias or group membership can raise privileges.
W: A=Additive: the full capability set is the token's policies plus the entity's (and groups').
C=Request-time evaluation: updating entity policies changes the effective access of tokens that already exist.
X: B=Replacement: the entity's policies are only a means to grant additional capabilities.
D=Copied at creation: that was true of token policy names alone; entity policies are looked up when a request is made.
E=Userpass only: any auth method that creates an entity (everything except the token method) can give its tokens entity policies.
T: Entity policies add to token policies and are re-evaluated at each request.

@ VLT-VA003 D1 T1.4 applied definition
S: A group in the identity store is configured as an external group with an alias that maps to the LDAP group sre. What does that provide?
A: LDAP users who belong to sre are added to the Vault group at login and renewal
B: Operators add and remove each member by hand, since external groups never track outside systems at all
C: All Vault entities become members at once, because an external alias applies to the whole mount
D: Membership is refreshed in real time every time the LDAP group changes
K: A
G: ## Internal and external groups
- **Internal groups** are the default. Membership is managed manually (by operators or automation). Groups can also be nested: members of a subgroup inherit policies of the parent group.
- **External groups** map to a group that lives outside the identity store, such as an LDAP group or a GitHub team. They can have one, and only one, alias, which maps to the outside group.
## Timing
With an external group, a user's entity is added as a member automatically during login and token renewal. If the user is removed from the LDAP group, Vault drops the membership only on the next login or renewal, not immediately.
W: Automatic membership at login or renewal: the alias links the Vault group to the directory group, so policies on the Vault group follow directory membership.
X: B=Manual only: manual membership is the behavior of internal groups.
C=Everyone is a member: only entities whose login reports membership in the mapped external group are added.
D=Real time: Vault learns about changes only at login and renewal, so removal can lag.
T: External groups mirror outside groups, updated when members log in or renew.

@ VLT-VA003 D1 T1.4 advanced tradeoff
S: An LDAP user is removed from the directory group sre, which maps to an external Vault group granting production access. The user's Vault token has hours left. What does Vault do?
A: Membership is dropped only at the next login or renewal, so the policies can apply until then
B: The membership is removed instantly because Vault subscribes to directory change events
C: The token is revoked at once because group removal revokes every child token
D: The membership stays forever until an operator deletes the alias
K: A
G: ## Lag in external group sync
Group membership for external groups is evaluated when the user authenticates and when the token is renewed. Vault serves as a cache of identities, not a source. A removal in the directory does not push into Vault.
- The user keeps the external group's policies until the next login or renewal updates membership.
- To act sooner, revoke the user's tokens in Vault, or use short token TTLs so renewal happens often.
Because of this, a short TTL on tokens issued by directory-backed methods narrows the exposure window.
W: Updated at next login or renewal: Vault reads group membership from the directory at those moments, so removal lags.
X: B=Instant watch: Vault does not poll or subscribe to the directory.
C=Auto revoke: no revocation is triggered; the token remains valid until it expires or an operator revokes it.
D=Forever: membership is refreshed at login and renewal, so it does not persist after the directory change is seen.
T: External group membership follows the directory only at login and renewal, so use short TTLs where fast removal matters.

@ VLT-VA003 D1 T1.4 applied comparison
S: Group a has subgroup b, and entity e is a direct member of b only. Which policies does e receive from groups?
A: The policies of b and of a, since subgroup members are indirect members of the parent
B: Only the policies of b, because policies never flow from a parent group to its subgroup members
C: Only the policies of a, because the parent group overrides its subgroups
D: None, because entities obtain group policies only through direct membership in external groups
K: A
G: ## Group hierarchy
Groups can contain entities and other groups. Policies set on a group are granted to all its members. If group a has group b as a subgroup, members of b are indirect members of a, so they receive the policies on both b and a. The policies are combined at request time with the entity's own policies and the token's policies.
- Direct member: entity listed in the group.
- Indirect member: entity of a subgroup.
Use nesting to model org structure, for example `engineering` containing `sre`.
W: Both groups: indirect membership through the subgroup includes the parent group's policies as well as the subgroup's.
X: B=Only b: that would ignore inheritance, because group policies are granted to indirect members through every parent group above them.
C=Only a: policies do not override or replace one another; the subgroup's own policies accumulate with the parent's.
D=None: internal groups also grant policies to their members, directly or indirectly.
T: Members of a subgroup inherit the policies of the groups above them.

@ VLT-VA003 D1 T1.5 applied comparison
S: An application authenticates with AppRole through the HTTP API. Where in the response does it find the Vault token to use on later requests, and how does it send it?
A: In auth.client_token, sent in the X-Vault-Token header
B: In data.token, sent as a query string parameter
C: In auth.accessor, sent in the X-Vault-Token header
D: In lease_id, sent in the Authorization header as Basic
K: A
G: ## API login
Every auth method has a login endpoint (AppRole: `auth/approle/login`; the API path is prefixed with `/v1/`). A request such as `POST /v1/auth/approle/login` with `role_id` and `secret_id` in the JSON body returns JSON in which the `auth` object contains the token:

- `auth.accessor`: a reference to the token that cannot be used to authenticate.

@ VLT-VA003 D1 T1.6 advanced troubleshooting
S: After the AppRole login endpoint is called with a valid role_id but without a secret_id, the request fails. The role was created with default settings. Why?
A: The role has bind_secret_id enabled by default, so a SecretID is also required

@ VLT-VA003 D1 T1.5 applied use-case
S: Which TWO ways of presenting a Vault token on an HTTP API request are accepted? (Select TWO)
A: The X-Vault-Token request header

Each auth method reports a name for the entity alias, which together with the mount accessor identifies the alias.
