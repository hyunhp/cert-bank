@ VLT-VA003 D1 T1.6 expert troubleshooting
S: Vault 1.19 runs on virtual machines outside Kubernetes. Last year an operator configured the Kubernetes auth method with `token_reviewer_jwt` set to a token copied from the projected volume of the `vault-reviewer` service account. Logins worked for months, then every pod login began failing on the same day, although no role or bound service account had changed. The cluster now issues only short-lived projected service-account tokens, and the security policy forbids creating long-lived token Secrets. Security also requires that deleting a service account stops its pods' logins at once, not when a token expires. The platform team accepts maintaining extra ClusterRoleBindings. What should the Vault team change?
A: Remove token_reviewer_jwt, so that Vault presents each client's own JWT to the TokenReview API, and bind system:auth-delegator to the client service accounts
B: Remove token_reviewer_jwt and kubernetes_ca_cert, so that Vault loads a reviewer token and CA certificate from its own local service account mount path
C: Create a service-account token Secret for vault-reviewer, which Kubernetes does not expire, and set that Secret's value as the new token_reviewer_jwt
D: Replace the Kubernetes method with the jwt method and the cluster's OIDC discovery URL, so that pod tokens are validated offline without any TokenReview
K: A
G: ## How Kubernetes auth validates a pod
The pod sends its service-account JWT to Vault. Vault calls the Kubernetes **TokenReview API** to confirm the token, and it needs a token of its own (the reviewer JWT) for that call.
## Options with short-lived tokens
The documentation compares four set-ups:
- **Local token as reviewer**: Vault reads its own pod's token and CA from `/var/run/secrets/kubernetes.io/serviceaccount/`; only possible when Vault runs in Kubernetes.
- **Client JWT as reviewer**: omit `token_reviewer_jwt`; Vault uses the client's JWT for the TokenReview call. All tokens stay short-lived and can be revoked early, at the cost of giving each client service account the `system:auth-delegator` ClusterRole.
- **Long-lived reviewer token**: a service-account token Secret; it works but keeps a long-lived credential.
- **JWT auth instead**: Kubernetes acts as an OIDC provider; no reviewer is needed, but tokens **cannot be revoked before their TTL** ends.
## Why it broke
The copied projected token expired, so Vault could no longer call TokenReview and every login failed.
W: Client JWT as reviewer: no stored reviewer token can expire again, TokenReview still sees deleted service accounts immediately, and the extra ClusterRoleBindings are accepted overhead.
X: B=Local token and CA: that mode reads files that exist only when Vault runs in a Kubernetes pod; these VMs have no such mount path.
C=Long-lived token Secret: it would fix the expiry, but the security policy explicitly forbids long-lived service-account token Secrets.
D=jwt method with OIDC discovery: it avoids a reviewer, but tokens are checked offline and cannot be revoked early, which fails the requirement on deleted service accounts.
T: When Vault runs outside Kubernetes with short-lived tokens, omit token_reviewer_jwt so the client's own JWT is used, and grant clients system:auth-delegator.

@ VLT-VA003 D1 T1.4 expert troubleshooting
S: An on-call engineer, mlee, logs in with userpass. Until this morning the userpass user had token_policies `default,prod-admin`; at 09:00 an administrator ran `vault write auth/userpass/users/mlee token_policies=default`. At 09:40 mlee can still change production secrets. mlee's token was issued at 08:30 with an 8-hour TTL, and `vault token lookup -accessor <accessor>` shows `policies [default prod-admin]` and `identity_policies []`; mlee's entity belongs to no groups. Security wants mlee's production access gone now, without affecting other users who hold prod-admin, and mlee should keep working with the default policy only. What should the administrator do?
A: Revoke mlee's current token by its accessor and have mlee log in again, because the policy names on a token are fixed when the token is created
B: Wait for mlee's next token renewal, because at renewal Vault replaces the token's policy names with the user's updated token_policies value
C: Remove prod-admin from mlee's entity through the identity API, because the entity's policies are what still grant the production access today
D: Edit the prod-admin policy to deny the production paths, because Vault re-reads the contents of every policy named on a token for each request
K: A
G: ## Token policies versus identity policies
A token carries two kinds of policies:
- **Token policies** (`policies` in a lookup): the policy **names** attached when the token was created, for example from the userpass user's `token_policies`. The names are immutable for the life of the token, although the policy contents can change.
- **Identity policies** (`identity_policies`): policies from the entity and its groups, evaluated **at request time**, so changes apply immediately.
## Reading the evidence
`identity_policies []` and "no groups" show that identity is not the source. prod-admin is a token policy, set at 08:30 before the user record changed. Changing the user record only affects tokens issued later.
## The narrow fix
Revoking the token ends access now, and the accessor lets the administrator do it without ever holding the token. mlee's next login receives `default` only.
W: Revoke by accessor and log in again: the old token with prod-admin stops working at once, and the new login reflects the updated token_policies.
X: B=Wait for renewal: token policy names do not change during the token's life, and waiting would leave access in place for hours anyway.
C=Entity policies: the lookup shows no identity policies, so removing anything from the entity changes nothing; prod-admin sits on the token.
D=Deny in prod-admin: this would stop mlee, but it also removes production access from every other holder of prod-admin, which is ruled out.
T: Changing an auth method's user or role policies affects only new tokens; revoke existing tokens to remove token policies now, while identity policies change at request time.

@ VLT-VA003 D1 T1.2 expert use-case

Workloads on EC2 have instance profiles, and the security team rejects any method that relies on the EC2 instance identity document, because that document is readable by every process on the instance. No long-lived secret may be stored for any of these clients. Which THREE configurations should the team use? (Select THREE)
A: The oidc auth method with a role whose allowed_redirect_uris cover the UI and the localhost CLI callback, so engineers sign in through Okta
B: The jwt auth method with a role that sets bound_audiences and bound_claims for the repository and ref, so only main-branch workflows log in
C: The aws auth method with an iam-type role bound to the instance profile's IAM role ARN, so EC2 workloads log in with signed STS requests
D: The github auth method for GitHub Actions workflows, sending each workflow's OIDC ID token in place of a GitHub personal access token
E: The userpass auth method for engineers, with a password policy matched to Okta, so that Okta's MFA also applies when engineers log in
F: The aws auth method with an ec2-type role bound to the AMI ID, so EC2 workloads log in with the PKCS#7 signature of their identity document

G: ## Choosing a method per client
- **OIDC** (oidc mount of the JWT/OIDC plugin): a browser-based login through an identity provider. Roles list `allowed_redirect_uris`, including `http://localhost:8250/oidc/callback` for `vault login -method=oidc`; MFA happens at the IdP.

W: A=OIDC role with redirect URIs: engineers authenticate in the browser at Okta, where MFA is enforced, from both the UI and the CLI.
B=JWT role with bound claims: GitHub's ID token is verified and only tokens whose repository and ref claims match main of payments are accepted.

@ VLT-VA003 D2 T2.4 expert troubleshooting
S: A token holds the policies `app` and `ops`. Policy app contains `path "secret/data/billing/*" { capabilities = ["read"] }`, and policy ops contains `path "secret/data/+/reports" { capabilities = ["create", "update", "read"] }`. An operator expects to update `secret/data/billing/reports`, but `vault kv put -mount=secret billing/reports total=10` returns permission denied, `vault kv get` on the same key succeeds, and `vault token capabilities` for that path prints only `read`. The policy app must not change, ops must keep its grant for every other folder's reports secret, and the operator must not gain write access to any other billing secret. Which change gives update on billing/reports?
A: Add `path "secret/data/billing/reports"` with create, update and read to ops, because an exact path outranks the billing/* glob for that key
B: Add `path "secret/data/billing/*"` with create, update and read to ops, because identical patterns from two policies have their capabilities merged
C: Change the ops path to `secret/data/+/reports*`, because a pattern that ends in a glob ranks above billing/* when both match the same key path
D: Move the ops stanza into the app policy, because the priority rules apply only between path stanzas that come from two different policies
K: A
G: ## Priority between different patterns
Vault merges the stanzas of all a token's policies. For one request path:
- identical patterns from several policies are **unioned**;
- different matching patterns are **not** combined: only the highest-priority one applies.
For two patterns P1 and P2 the documentation ranks P1 lower if, in order: its first wildcard (`+` or `*`) comes **earlier**; it ends in `*` and P2 does not; it has more `+` segments; it is shorter; it is lexicographically smaller.
## Working the example
- `secret/data/+/reports`: first wildcard at the segment after `data/`.
- `secret/data/billing/*`: first wildcard after `billing/`, which is later.
So the billing glob wins and grants only `read`; the ops `update` never applies to this key, matching the capabilities output.
## Fixes and side effects
An exact path has no wildcard and outranks both, so it restores update on that one key only. Adding the same billing/* pattern to ops would union `update` into every billing secret.
W: Exact path in ops: it is the highest-priority match for billing/reports and grants update there, while other billing keys and other folders' reports are unchanged.
X: B=Same billing/* pattern in ops: the union would grant create and update on every billing secret, which the operator must not get.
C=Glob after reports: the first wildcard is still the `+` right after data/, earlier than in billing/*, so the pattern still loses.
D=Move into app: Vault merges all stanzas before ranking them, so the result is the same whichever policy holds the stanza, and app must not change.
T: When several patterns match, only the highest-priority one counts; an earlier wildcard loses, and an exact path beats any glob.

@ VLT-VA003 D2 T2.2 expert use-case
S: A KV v2 mount is enabled at `kv/`. A token holds exactly one policy with two stanzas: `path "kv/data/apps/+/config*" { capabilities = ["read"] }` and `path "kv/metadata/apps/*" { capabilities = ["list"] }`. Keys that exist include `apps/web/config`, `apps/web/config-eu`, `apps/web/eu/config` and `apps/config`. A reviewer must predict, before rollout, which commands this token can run successfully, because the application team plans its deployment scripts around the answer. No other policy, including default, grants anything on these mounts, and the reviewer has only this policy text and the key list. Which THREE commands succeed? (Select THREE)
A: `vault kv get -mount=kv apps/web/config`, because + matches the single segment web and the config* glob matches the key name config itself
B: `vault kv get -mount=kv apps/web/config-eu`, because the glob after config also matches the extra suffix -eu at the end of that key name
C: `vault kv list -mount=kv apps/web`, because listing reads the path kv/metadata/apps/web, which falls under the list stanza's glob pattern
D: `vault kv get -mount=kv apps/web/eu/config`, because + matches the two segments web/eu that come between apps and the config key name
E: `vault kv metadata get -mount=kv apps/web/config`, because list on the metadata path also covers reading the key's version history
F: `vault kv get -mount=kv apps/config`, because + also matches an empty segment, so apps/config fits the read stanza's pattern
K: A,B,C
G: ## Wildcards in policy paths
- `+` matches **exactly one** path segment (any characters except `/`).
- `*` at the end is a **glob**: it matches any remaining characters, including further segments.
## KV v2 paths behind the commands
- `vault kv get` reads `kv/data/<key>`.
- `vault kv list` lists `kv/metadata/<prefix>`.
- `vault kv metadata get` **reads** `kv/metadata/<key>`.
## Working through the keys
- `kv/data/apps/web/config`: `+` = web, `config*` matches config. Allowed.
- `kv/data/apps/web/config-eu`: `config*` matches config-eu. Allowed.
- `kv/data/apps/web/eu/config`: `+` cannot span web/eu. Denied.
- `kv/data/apps/config`: `config` would have to be the `+` segment, and nothing follows for `config*`. Denied.
- `kv/metadata/apps/web` with list: matched by `apps/*`. Allowed.
- `kv/metadata/apps/web/config` with read: the stanza grants only list. Denied.
W: A=Exact config key: one segment for +, and the glob matches the key name config with nothing after it.
B=Suffixed key: a trailing glob matches any characters after config, including -eu.
C=List under web: the list command uses the metadata path, which apps/* covers with the list capability.
X: D=Two segments: + matches exactly one segment, so web/eu does not fit.
E=Metadata read: reading version history needs read on the metadata path; list does not include read.
F=Empty segment: + must match one real segment, and apps/config leaves no segment for config* after it.
T: + matches exactly one segment, a trailing * matches everything after it, and each KV v2 command maps to its own data or metadata path and capability.

@ VLT-VA003 D3 T3.4 expert use-case
S: The AppRole mount is tuned with `default-lease-ttl=1h` and `max-lease-ttl=8h`, and the system max TTL is the default 32 days. The role `report` sets token_ttl=2h, token_max_ttl=12h and token_explicit_max_ttl=6h; no period is used. A report job logs in at 09:00 and runs `vault token renew` without an increment at 10:30, 12:00 and 13:30, and it plans to renew again at 15:00. The job needs Vault until 16:30 and must not fail midway, so the team wants to know exactly what the renewals will return and checks each one with `vault token lookup`. Which statement is accurate?
A: The 13:30 renewal returns a TTL of 1h30m, the token expires at 15:00, and the job must log in again before 15:00 to keep working until 16:30
B: The 13:30 renewal returns a TTL of 2h, the token expires at 17:00 under the 8-hour mount cap, and the renewal at 15:00 carries the job to 16:30
C: The 13:30 renewal returns a TTL of 2h, the token expires at 21:00 under the role's 12-hour cap, and the planned renewals carry the job to 16:30
D: The 13:30 renewal returns a TTL of 1h, the token expires at 14:30, because the mount's 1-hour default replaces token_ttl at every renewal
K: A
G: ## Three ceilings on a token
- **System max TTL**: 32 days by default.
- **Mount max TTL** from tuning: here 8 hours.
- **Auth method suggestion**: the role's token_max_ttl may lower the mount max but never raise it, so 12 hours becomes 8 hours.
- **Explicit max TTL**: a hard cap encoded on the token at creation; no renewal can go past it. Here 6 hours.
The role's `token_ttl` (2 hours) is the length of each renewal period; the mount default applies only when the role sets none.
## Timeline
- 09:00 login: TTL 2h, explicit cap at 15:00.
- 10:30 renew: until 12:30.
- 12:00 renew: until 14:00.
- 13:30 renew: 2h would reach 15:30, so Vault returns 1h30m, ending at 15:00.
- 15:00: the token has expired; the planned renewal fails.
W: 1h30m and 15:00: the explicit max TTL of 6 hours is the lowest ceiling, so the last renewal is shortened and the job must re-authenticate before 15:00.
X: B=17:00 under the mount cap: the mount cap is 8 hours, but the explicit max TTL of 6 hours is lower and always wins.
C=21:00 under the role cap: the role's token_max_ttl cannot exceed the 8-hour mount maximum, and the explicit 6-hour cap is lower still.
D=Mount default replaces token_ttl: the role's token_ttl overrides the mount default, so renewals return 2 hours until a cap applies.
T: A token lives until the lowest ceiling: explicit max TTL, then the lower of the role and mount max TTLs; check renewal responses for a shrinking TTL.

@ VLT-VA003 D3 T3.1 expert troubleshooting
S: A Vault Enterprise customer runs a performance primary in Frankfurt and a performance secondary in Singapore. A CI system in Frankfurt mints tokens for build agents that run in Singapore and call the Singapore cluster for KV reads. The CI system authenticates with AppRole, and its token has update on `auth/token/create` and `auth/token/create/*` but no sudo. Today it runs `vault token create -type=batch -ttl=20m -policy=build`; every request with those tokens to the Singapore cluster is rejected, while the same tokens work in Frankfurt. Token creation must stay lightweight, and agents must not log in themselves. Which change fixes this?
A: Create a token store role with orphan=true, token_type=batch and allowed_policies=build, and have CI create the tokens through auth/token/create/<role>

G: ## Tokens across performance replication
Performance secondaries share configuration and policies with the primary but keep **their own tokens and leases**. W: Orphan batch tokens from a role: they are lightweight, carry no parent dependency, and are accepted by the performance secondary; the CI token already has update on auth/token/create/*.
X: B=-orphan flag: the flag requires sudo, which the CI token does not have, so the command fails.
C=Orphan service tokens: service tokens are not usable across performance clusters and are the heavyweight type the team wants to avoid.
D=Longer TTL: tokens are never replicated to performance secondaries, so a longer TTL changes nothing; the parent dependency is the problem.
T: For tokens used on performance secondaries, issue orphan batch tokens, for example from a token store role with orphan=true and token_type=batch.

@ VLT-VA003 D3 T3.6 expert use-case
S: Two weeks ago a token store role `svc` was created with token_period=24h, and a long-running service holds a periodic token created from it; the service renews that token every 6 hours. After a review, an administrator runs `vault write auth/token/roles/svc token_period=1h token_explicit_max_ttl=720h` and expects new tokens to be tighter while the existing service continues as before. The service team will not change its renewal interval this quarter, and nobody has revoked any token; the role's other settings are unchanged. Which TWO statements about the existing service token are accurate? (Select TWO)
A: At the service's next renewal the token's TTL is reset to 1 hour, because a periodic token from a role uses the role's current period at renewal
B: The token will expire about an hour after its next renewal, unless the service starts renewing at intervals shorter than one hour
C: The token keeps renewing to 24 hours, because a periodic token's period is fixed at the moment the token is created from the role
D: The token will be revoked 720 hours after the role change, because the new explicit max TTL also applies to tokens already issued
E: The token is revoked straight away, because changing a role's token_period invalidates every token that was issued from that role
K: A,B
G: ## Periodic tokens and roles
A periodic token's TTL is reset to its period at every renewal, so it can live indefinitely while it is renewed in time. The tokens documentation adds two details:
- When a periodic token was created via a **token store role**, the **current** value of the role's period is used at renewal time.
- A token with both a period and an explicit max TTL is revoked when the explicit max TTL is reached; the explicit max TTL is **encoded on the token at creation**.
## Applying it
- Next renewal (within 6 hours): Vault applies the role's new 1-hour period, so the TTL becomes 1 hour.
- The service waits 6 hours before renewing again, so the token expires about 1 hour after that renewal.
- The existing token was created without an explicit max TTL, and the new role value is encoded only on tokens created later.
W: A=Current role period at renewal: the role change reaches the existing token at its next renewal, which returns a 1-hour TTL.
B=Expiry after one hour: with 6-hour renewals and a 1-hour period, the token lapses about an hour after the next renewal.
X: C=Period fixed at creation: for role-created periodic tokens the documentation says the role's current period is used at renewal.
D=Explicit max for old tokens: token_explicit_max_ttl is encoded onto tokens when they are created, so it does not reach a token issued two weeks ago.
E=Immediate revocation: changing a role does not revoke tokens; the effect appears only when the token renews.
T: Role-created periodic tokens pick up the role's current period at renewal, while an explicit max TTL is fixed onto each token when it is created.

@ VLT-VA003 D4 T4.2 expert troubleshooting
S: The `database/` mount is tuned with max-lease-ttl=4h. The role `etl` sets default_ttl=2h and max_ttl=6h. A job obtained credentials at 08:00, and at 09:30 it ran `vault lease renew -increment=4h <lease_id>`; the output shows `lease_duration 2h30m` and `lease_renewable true`. The job must keep the same database user until 13:00 because its open transactions are tied to that login, and nobody may change Vault configuration today. A colleague claims the renewal failed. The job's own Vault token is periodic and stays valid all day. The output above is the only evidence available. Which conclusion and plan are correct?
A: The 4-hour mount maximum caps the role's 6-hour max_ttl, so the lease ends at 12:00 whatever the increment, and the job cannot keep this user until 13:00
B: The role's 6-hour max_ttl applies, so the lease can reach 14:00, and the job should renew again at 11:30 with -increment=2h to stay valid until 13:30
C: The renewal failed and the output shows the previous lease's remaining time, so the job should retry the renewal with the increment given as 14400
D: The increment was honoured in full, so the lease now ends at 13:30, and the 2h30m value shows the remaining TTL of the job's token, not of the lease
K: A
G: ## How renewal answers are computed
`vault lease renew -increment=4h` asks for a TTL of 4 hours **from now**. The increment is advisory; the engine grants at most what the lease's maximum allows. The maximum comes from:
- the role's `max_ttl`, which may be lower than the mount max but **not longer**;
- the mount's `max-lease-ttl` from tuning.
Here 6 hours on the role cannot exceed 4 hours on the mount, so the lease may live until **08:00 + 4h = 12:00**.
## Reading the output
At 09:30 the remaining time to 12:00 is 2h30m, exactly the returned `lease_duration`. If the renewal had failed, the old lease would have shown about 30 minutes (issued at 08:00 with a 2-hour TTL, ending 10:00), and the command would report an error.
## Consequence
After 12:00 the credentials are revoked; the job would need new credentials, which means a different database user, so the 13:00 requirement cannot be met without a configuration change.
W: Mount cap at 12:00: the returned 2h30m is the time left until the 4-hour mount ceiling, and no increment can push the lease past it.
X: B=Role max applies: the role's max_ttl may not be longer than the mount maximum, so 14:00 is never reachable.
C=Renewal failed: a failed renewal returns an error; the old lease had only 30 minutes left, and 14400 seconds equals the 4h already requested.
D=Increment honoured: lease_duration in a lease renewal is the lease's TTL, and a full 4-hour increment would have shown 4h, not 2h30m.
T: Renewal output shows the lease's new TTL; when it is shorter than requested, a max TTL (the lower of role and mount) has been reached.

@ VLT-VA003 D4 T4.3 expert use-case
