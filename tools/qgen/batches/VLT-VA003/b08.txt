@ VLT-VA003 D8 T8.1 applied use-case
S: A team runs a self-managed Vault cluster with Integrated Storage on five nodes. Two nodes fail at the same time because of a rack power loss. What is the state of the cluster?
A: The remaining three nodes still form a quorum, so the cluster keeps electing a leader and committing writes
B: The remaining three nodes are read-only until the two failed peers are removed with a manual peer-removal command
C: The remaining three nodes stay available only if the failed pair held no more than one of the unseal key shares
D: The remaining three nodes lose quorum because Raft needs every voting peer to acknowledge each committed write
K: A
G: ## Quorum in Integrated Storage
Integrated Storage uses the Raft consensus protocol. A log entry is committed only when a majority of the peer set has stored it. Quorum is the smallest majority: for a peer set of `N` voters it is `ceil((N + 1) / 2)`.
- 3 servers: quorum 2, failure tolerance 1
- 5 servers: quorum 3, failure tolerance 2
- 7 servers: quorum 4, failure tolerance 3
If quorum is lost the cluster cannot elect a leader, commit writes or change membership, and recovery is manual.
## Why five nodes is a common production size
Losing two of five leaves three, which is still a majority, so the cluster rides through two simultaneous failures without operator action.
W: Quorum survives: three of five is a majority, so the remaining peers keep a leader and commit new writes. A five-node cluster is designed to tolerate two failures.
X: B=Read-only until manual removal: loss of quorum would stop writes, but quorum is not lost here. No manual peer removal is needed for the cluster to keep working.
C=Depends on unseal key shares: unseal key shares are held by operators and are used to unseal a node. They play no role in Raft quorum, which counts running voting peers.
D=Every peer must acknowledge: Raft needs only a majority, not all peers. If every peer had to acknowledge, one failed node would stop the cluster.
T: Quorum is a majority of voters, so a five-node Raft cluster tolerates two failed nodes.

@ VLT-VA003 D8 T8.1 applied tradeoff
S: An architect proposes growing a three-node Integrated Storage cluster to four nodes "for more resilience". Which statement about this change is accurate?
A: Four nodes raise failure tolerance to two, since the extra node can vote on behalf of a failed peer
B: Four nodes keep failure tolerance at one, so the extra node adds cost and no extra fault tolerance
C: Four nodes lower failure tolerance to zero because Raft needs an odd number of nodes to elect a leader
D: Four nodes keep failure tolerance at one and also double read throughput, because standbys serve reads
K: B
G: ## Quorum size and failure tolerance
Failure tolerance is the cluster size minus quorum size.
- 3 servers: quorum 2, tolerance 1
- 4 servers: quorum 3, tolerance 1
- 5 servers: quorum 3, tolerance 2
An even-sized cluster adds a node without adding tolerance, and it can produce voting stalemates, so HashiCorp recommends an odd number of nodes. For production, five servers keep a tolerance of two.
## Standby nodes and scale
In HA mode only the active node handles requests; standbys forward or redirect. HA improves availability, not throughput.
W: Same tolerance, more cost: quorum for four voters is three, so only one node can fail, exactly as with three. The fourth node adds cost without more resilience; five nodes is the next useful step.
X: A=Tolerance of two: a fourth voter raises quorum to three, so a second failure would still lose quorum. A node cannot vote on behalf of another.
C=Tolerance of zero: an even-sized cluster is not broken and still tolerates one failure. Odd sizes are recommended to avoid voting stalemates, not required for election.
D=Doubled read throughput: standbys in Vault Community do not serve requests; they forward or redirect to the active node. HA does not provide increased scalability.
T: Failure tolerance is size minus quorum, so adding a fourth node to three gains nothing.

@ VLT-VA003 D8 T8.1 applied troubleshooting
S: A two-node Integrated Storage cluster was built for a lab. One node crashes. The remaining node still answers `vault status` but cannot accept writes. What explains this?
A: The surviving node sealed itself automatically, since a Shamir seal requires both nodes to stay online
B: The surviving node is a standby that never held the HA lock, so it must wait for the lease to expire
C: The peer set of two has a quorum of two, so one node alone cannot commit entries or elect a leader
D: The surviving node lacks the Enterprise license that is needed to run a cluster of fewer than three
K: C
G: ## Why two nodes are not fault tolerant
Quorum for a peer set of two is two, so both nodes must take part in every commit. If one fails, the other cannot commit log entries, elect a leader or change membership; the peer set is unavailable. Recovery is manual: remove the failed node and restart the remaining node in bootstrap mode so it elects itself leader.
The same math shows why a single server or two servers is discouraged for production, and why three is the smallest size that tolerates a failure.
W: Quorum of two: with two peers a majority is both of them, so one survivor cannot commit writes. That is a cluster-sizing problem, not a seal or license problem.
X: A=Automatic seal: a node does not seal because a peer died. A node stays unsealed until it is resealed, restarted or hits an unrecoverable storage error.
B=Waiting for a lease: Raft leadership uses elections, and with Integrated Storage the HA lock goes to the Raft leader. No lease timer would unblock the survivor without quorum.
D=Missing license: Vault Community runs Integrated Storage clusters of any size. Clustering does not require an Enterprise license.
T: Two Raft peers need both online, so three is the smallest cluster that tolerates a failure.

@ VLT-VA003 D8 T8.1 applied definition
S: A cluster of three Vault nodes shares one storage backend that supports high availability. Which statement about how the nodes behave is accurate?
A: Every node serves reads and writes in parallel, and the load balancer should spread requests evenly
B: One node holds the HA lock and is active, while the others are standbys that forward or redirect requests to it
C: One node is active, and a standby only starts forwarding after an operator unseals it with the root key
D: Writes go to all nodes at once, and each node signs its replies so that clients accept the first one
K: B
G: ## Active and standby nodes
When the storage backend supports high availability, Vault enters HA mode automatically. One node acquires a lock in the data store and becomes active; the others are standbys. Standbys forward requests to the active node (request forwarding is on by default) or answer with a `307` redirect to its `api_addr`. If the active node is sealed, fails or loses connectivity, a standby takes the lock.
## What HA does not do
HA protects against outages. It does not increase scalability, because only the active node processes requests; Vault is bound by storage I/O.
Standbys must already be unsealed to take over. Sealed nodes cannot act as standbys.
W: Lock holder is active: one node owns the HA lock and handles requests, and standbys forward or redirect to it. This gives failover, not load sharing.
X: A=Parallel active nodes: in Vault Community only the active node processes requests, so a load balancer does not turn standbys into extra capacity.
C=Standby needs the root key: a standby is already unsealed with its own seal mechanism before it joins; forwarding does not depend on an operator providing the root key.
D=Writes to all nodes: Vault does not broadcast writes to all nodes with signed replies; the active node writes to the storage backend.
T: HA means one active node holding the lock and unsealed standbys that forward, for availability only.
V: Vault

@ VLT-VA003 D8 T8.1 applied troubleshooting
S: A three-node HA cluster uses auto-unseal. Two standbys were restarted by an automated patch job and an operator ran `vault operator seal` on them for testing, so they are sealed. The active node then crashes. What happens?
A: A sealed node takes the HA lock and unseals itself with the KMS, which restores service within seconds
B: The cluster promotes the sealed nodes, which answer read requests from their local copy of the data
C: The cluster stays unavailable because sealed servers cannot act as standbys or take over as active
D: The third node continues alone because Raft quorum counts only nodes that run an unsealed process
K: C
G: ## Only unsealed nodes are standbys
HA failover depends on standbys that are running and unsealed. When the active node fails, unsealed standbys compete for the HA lock; a sealed node cannot take part and cannot serve requests. A manual `vault operator seal` (the seal API) keeps a node sealed until restart or unseal, even when auto-unseal is configured.
## Design consequence
Monitor seal status of every node, and keep enough unsealed nodes to maintain quorum and a standby after patching.
W: Sealed nodes cannot take over: with no unsealed standby left, no node can obtain the HA lock, and requests fail until a node is unsealed.
X: A=Self-unsealing takeover: a node that was sealed through the API stays sealed until restarted or unsealed; it does not unseal itself in order to take the lock.
B=Read-only local copy: sealed nodes cannot decrypt data and answer only unseal and status operations. Serving reads from a local copy is a feature of Enterprise performance standbys, which must be unsealed.
D=Solo survivor: with Integrated Storage the sole remaining node cannot reach quorum in a three-node peer set. The statement also ignores that the third node must be unsealed.
T: Standbys must be unsealed to take over, so sealed nodes provide no failover.
V: Vault

@ VLT-VA003 D8 T8.1 applied comparison
S: In a Vault Enterprise HA cluster, administrators enable performance standby nodes. Which statement about their role is accurate?
A: They serve requests that do not modify storage and forward requests that need a write to the active node
B: They accept all writes locally and later replicate them to the active node through a replication token
C: They are separate clusters in another region that hold a copy of the data and serve only disaster recovery
D: They replace the HA lock, so any performance standby can answer writes without contacting the active node
K: A
G: ## Performance standbys (Enterprise)
In a standard HA cluster, standbys only forward or redirect. With Vault Enterprise, performance standby nodes can service read-only requests, meaning requests that do not change storage, which scales operations such as KV reads and transit calls nearly linearly with the number of nodes. A request that needs a storage write is forwarded to the active node.
Like ordinary standbys, a performance standby becomes active when the active node is sealed, fails or loses connectivity.
## Do not confuse with replication
Performance standbys live inside one cluster and share its storage. Performance and DR replication connect separate clusters.
W: Read locally, forward writes: performance standbys scale read-only traffic within one cluster, and writes still pass through the active node that holds the HA lock.
X: B=Local writes later replicated: write requests are forwarded to the active node, not applied locally. Replication tokens bootstrap replication between clusters, not standbys.
C=Separate DR cluster: performance standbys are nodes of the same cluster. A cluster in another region with copied data is a replication secondary.
D=Replaces the HA lock: the HA lock still determines which node is active. A performance standby cannot write on its own.
T: Performance standbys are Enterprise nodes in one cluster that serve reads and forward writes.
V: Vault

@ VLT-VA003 D8 T8.1 applied use-case
S: Which TWO statements about Autopilot in a self-managed Integrated Storage cluster are accurate? (Select TWO)
A: A newly joined node becomes a non-voter until it has synced and reached the configured stability threshold
B: Autopilot replaces the Shamir seal so that new nodes join without any unseal key or recovery key
C: Dead server cleanup can remove unhealthy nodes from the Raft cluster without an operator doing it manually
D: Autopilot converts a standby into an active node when the stability threshold is set to zero seconds
E: Autopilot is available only if the cluster is configured with Consul as an external storage backend
K: A,C
G: ## What Autopilot does
Autopilot is enabled by default for Integrated Storage. It decides whether a node is healthy enough to be a voter in the quorum list.
- A joining node starts as a non-voter, syncs to the current Raft index and becomes a voter only after the stability threshold passes.
- Dead server cleanup, when enabled through the Autopilot API, removes unhealthy nodes automatically.
Without Autopilot, a joining node cannot vote while syncing yet is counted for quorum, so adding several nodes at once can lose quorum.
W: A=Non-voter stage: new nodes catch up first and vote later, which protects quorum during scale-out.
C=Dead server cleanup: Vault removes unhealthy peers from the Raft cluster automatically instead of waiting for an operator.
X: B=Replaces the seal: Autopilot manages Raft membership and health. Joining nodes still need a seal mechanism; with Shamir they need unseal keys, and with auto-unseal the seal handles the join challenge.
D=Promotes to active: leadership comes from Raft elections. A stability threshold concerns voter eligibility, and a threshold set too low risks instability.
E=Consul only: Autopilot is a feature of Integrated Storage (Raft). Consul has its own, separate mechanisms.
T: Autopilot admits joining nodes as non-voters until stable and can remove dead servers automatically.

@ VLT-VA003 D8 T8.2 applied comparison
S: A company is designing a new self-managed Vault cluster and has no existing Consul infrastructure. Which choice matches HashiCorp's recommendation for the storage backend?
A: Consul, because only a separate Consul cluster supports high availability with a lock in the data store
B: A local file backend on each node, with a shared network drive so that every node reads the same files
C: Integrated Storage, since it needs no extra software, keeps data on the Vault hosts and is HashiCorp supported
D: Integrated Storage on the active node and an external database on the standbys for faster read access

G: ## Integrated Storage as the default
HashiCorp recommends Integrated Storage for most use cases. It is built into Vault (version 1.4 or later), so it needs no additional software, adds no extra network hop, and Vault is the only system to monitor and troubleshoot. The encrypted data lives on the same hosts as the Vault servers. It also supports HA and Enterprise replication. Before Vault 1.4, Consul was the recommended storage.

External backends such as Consul or DynamoDB can be used, with limited HashiCorp support and extra operational work, for example clustering the external system for HA.
W: Built-in and supported: Integrated Storage is the recommended default; it adds no extra system to install, monitor or secure.
X: A=Only Consul does HA: Integrated Storage supports HA, and the HA lock goes to the Raft leader. Several other backends support HA too.
B=File backend on a shared drive: the file backend does not support high availability and is not meant for a clustered deployment.
D=Mixed backends per role: a cluster has one storage backend (optionally a separate `ha_storage` for the lock), not a different backend per node role.
T: Choose Integrated Storage by default; external storage costs extra operations and support.

E=No unseal needed: the storage backend is untrusted. Vault encrypts data before writing, so Consul access does not replace unsealing.

@ VLT-VA003 D8 T8.3 applied use-case
S: An operator runs `vault operator init -key-shares=5 -key-threshold=3` on a new self-managed cluster with a Shamir seal. Two of the five key holders leave the company. Can the cluster still be unsealed?
A: No, because every one of the five shares is needed to rebuild the unseal key
B: No, because the threshold applies only to key holders who are in the original group
C: Yes, but only after the two missing shares are regenerated with a command run on an unsealed node
D: Yes, because any three of the remaining shares reconstruct the unseal key, and the shares can be entered in any order
K: D
G: ## Shamir's Secret Sharing
With the default seal, Vault splits the unseal key into shares using Shamir's Secret Sharing. `-key-shares` sets how many shares are produced; `-key-threshold` sets how many are needed to rebuild the key (defaults 5 and 3, and the threshold must not exceed the shares).
- Any threshold-sized subset works, in any order.
- Fewer than the threshold reveal nothing about the key.
- Holders can enter their shares from different machines, because the unseal process is stateful.
## Operational lesson
Losing shares is tolerable up to `shares - threshold` of them (here 2). Past that, the cluster cannot be unsealed; plan a rekey (`vault operator rekey`) when holders leave, while the threshold is still met.
W: Threshold of three: three holders remain, which meets the threshold, and the order they enter shares in does not matter.
X: A=All five required: that would make the threshold equal to the shares. The threshold of three is chosen exactly so that some shares can be lost.
B=Original group only: the shares are numbers, not identities; any holder of three valid shares can contribute them.
C=Regeneration needed first: no regeneration is needed here, and a sealed Vault cannot run such operations anyway. Rekeying is a separate, planned operation.
T: Any threshold-sized subset of Shamir shares unseals, so up to shares minus threshold can be lost.
V: Vault

@ VLT-VA003 D8 T8.1 applied use-case
S: A new node must join an existing three-node Integrated Storage cluster whose leader listens at `https://vault-1.example.com:8200`. Which command, run on the new node, starts the join?
A: `vault operator raft join https://vault-1.example.com:8200`
B: `vault operator init -join=https://vault-1.example.com:8200`
C: `vault operator unseal -join https://vault-1.example.com:8200`
D: `vault operator raft peers add https://vault-1.example.com:8200`

G: ## Joining a Raft cluster
A node that should become part of an Integrated Storage cluster is started with a `storage "raft"` block and its own `node_id`. It is then pointed at an existing cluster member with `vault operator raft join <leader-api-addr>`; the same can be configured with a `retry_join` stanza in the `storage "raft"` block so the node joins by itself at startup.
- The joining node learns the peer set from the cluster, so it is not initialized with `vault operator init`; only the first node is initialized.
- After joining, the node must still be unsealed (with a Shamir seal) or unseals itself (with auto-unseal).
- With Autopilot the new node first joins as a non-voter and becomes a voter after the stability threshold.
W: Raft join: `vault operator raft join` points the new node at a cluster member so it receives the Raft peer set and data from the leader.
X: B=Init with a join flag: `vault operator init` creates a new encryption setup for an empty cluster and has no `-join` flag; initializing a second node would not add it to the existing cluster.
C=Unseal with a join flag: `vault operator unseal` only submits unseal key shares and has no `-join` flag; unsealing is a separate step after the node has joined.
D=Raft peers add: there is no `raft peers add` subcommand; membership grows with `raft join`, and `vault operator raft remove-peer` is used to remove nodes.
T: A new Integrated Storage node joins an existing cluster with `vault operator raft join`.

@ VLT-VA003 D8 T8.3 applied troubleshooting
S: Two key holders leave a company that runs a Shamir-sealed cluster with five shares and a threshold of three. Which TWO statements about rekeying the unseal key with `vault operator rekey` are accurate? (Select TWO)
A: The rekey is authorized by supplying the threshold number of current unseal key shares
B: The cluster must be sealed first, because new shares cannot be created while data is readable
C: Old shares keep working next to the new ones until the next restart of every node
D: The operation can set a new share count and threshold, and new shares can go to different holders
E: Rekeying re-encrypts every secret in the storage backend, so it takes as long as the data set is large
K: A,D
G: ## Rekeying Shamir unseal keys
`vault operator rekey` (or the matching `sys/rekey` API) replaces the set of unseal key shares with a new one. It runs against an unsealed Vault and is authorized when the threshold of current unseal keys is provided. You can pick a new `-key-shares` and `-key-threshold` and, optionally, PGP keys to encrypt each new share.
- Use it when key holders leave or when the split must change.
- After it completes, the old shares are no longer valid.
- Only the root key is re-encrypted with the new unseal key; the stored data is not rewritten.
With auto-unseal the equivalent for the recovery key is `-target=recovery`.
W: A=Threshold authorizes: the current threshold of shares proves quorum before new shares are issued.
D=New split: the operator chooses a new number of shares and threshold, which allows handing shares to different holders.
X: B=Must be sealed: rekey runs on an unsealed Vault; sealing is not needed to create new shares.
C=Old shares overlap: once rekeyed, the old shares are replaced and are no longer valid.
E=Rewrites all data: the new unseal key protects the root key; the stored secrets are not rewritten, so size does not matter.
T: Rekeying issues a new set of unseal shares, authorized by the current threshold, when holders change.

@ VLT-VA003 D8 T8.3 applied definition
S: A security team is reviewing how the default Shamir seal protects a self-managed cluster. Which statement about it is accurate?
A: The threshold of shares is combined to reconstruct the unseal key, which is then used to decrypt the root key
B: A single share is enough to decrypt data, provided the holder has a root token for the cluster
C: A Shamir seal fits large dynamic clusters well, since nodes automatically unseal after every restart
D: Shamir shares are stored in the storage backend so that standby nodes can rebuild the key themselves
K: A
G: ## How a Shamir seal works
Shamir's Secret Sharing splits the unseal key into shares. Vault needs a threshold of them to reconstruct the unseal key, then uses it to decrypt the root key, which decrypts the keyring that protects the data.
- Fewer shares than the threshold reveal nothing about the key.
- After a restart a node is sealed again, so Shamir unseal is manual and awkward to automate.
W: Rebuilds the unseal key: the threshold of shares recreates the unseal key, which unlocks the root key and so the rest of the key chain.
X: B=One share and a root token: one share reveals nothing, and a token does not decrypt data at rest.
C=Automatic after restart: a restarted node is sealed and needs operators; automatic unseal is what auto-unseal provides, so Shamir suits large dynamic clusters poorly.
D=Shares in storage: storing shares with the data would defeat the purpose; they are given to operators at initialization.
T: Shamir shares rebuild the unseal key when the threshold is met; that key unlocks the root key.

@ VLT-VA003 D8 T8.4 applied comparison
S: A platform team runs dozens of Vault clusters in autoscaling groups, and nodes are replaced several times per week. Why does the team move from a Shamir seal to auto-unseal?
A: A trusted external service such as a cloud KMS decrypts the root key at start, so nodes unseal without human operators
B: Auto-unseal removes the root key from the design, so there is no key to protect, only the policies
C: Auto-unseal makes unseal keys unnecessary by storing them in the data store next to the encrypted secrets
D: A node with auto-unseal no longer needs a storage backend, because the KMS holds the encrypted data
K: A
G: ## Why auto-unseal
Auto-unseal delegates the protection of the unseal key to a trusted device or service, for example a cloud KMS, an HSM or another Vault's transit engine. At startup Vault connects to that service and has it decrypt the root key from storage. No operator has to type shares, which makes installs and node replacement easy to automate.
## What stays the same
The key chain still exists (the data is still encrypted by Vault's keyring and root key). Operations that need a quorum of humans, such as generating a root token, use recovery keys instead of unseal keys. Auto-unseal creates a lifecycle dependency on the external seal service.
W: Delegated unseal: the external service decrypts the root key on startup, so replaced or restarted nodes unseal on their own.
X: B=No root key: Vault still protects data with a keyring and root key; auto-unseal changes who decrypts the root key.
C=Keys beside the data: storing a usable unseal key next to the encrypted data would defeat the barrier; the external service does the decrypting.
D=No storage backend: data stays in the storage backend, and the KMS is used only for the root-key decryption.
T: Auto-unseal lets a trusted service unseal nodes automatically, trading human shares for a dependency.
V: Vault

@ VLT-VA003 D8 T8.4 applied definition
S: An operator initializes a cluster that uses a cloud KMS for auto-unseal. The output lists five recovery key shares. For which task are the recovery keys used?
A: Unsealing a node when the KMS is unavailable, as a replacement for the unseal keys
B: Decrypting the root key offline so a backup of the storage backend can be restored
C: Authorizing quorum operations such as generating a root token, in place of Shamir unseal keys
D: Signing the replication token that links a performance secondary to a primary cluster
K: C
G: ## Recovery keys
With auto-unseal, initialization returns recovery keys instead of unseal keys. Vault builds them from an internal recovery key split with Shamir's Secret Sharing, with `-recovery-shares` and `-recovery-threshold` (and `-recovery-pgp-keys`) at init.
- Operations that need a quorum of operators, such as `generate-root` or `vault operator rekey`, ask for recovery keys when auto-unseal is in use.
- Recovery keys cannot decrypt the root key, so they cannot unseal Vault if the seal mechanism does not work.
## Consequence
Treat the KMS key as critical: if it is lost, recovery keys will not bring the cluster back.
W: Quorum operations: recovery keys authorize operations such as root token generation that unseal keys authorize with a Shamir seal.
X: A=Substitute unseal keys: recovery keys cannot decrypt the root key, so they cannot unseal a Vault whose KMS is unreachable.
B=Offline root key decryption: only the seal mechanism can decrypt the root key, and recovery keys have no such ability.
D=Signing replication tokens: replication tokens are created by the primary through the replication API and are unrelated to recovery keys.
T: Recovery keys authorize quorum operations under auto-unseal but cannot unseal Vault.
V: Vault

@ VLT-VA003 D8 T8.4 applied troubleshooting
S: A self-managed cluster uses a cloud KMS key for auto-unseal. During cleanup an administrator schedules that KMS key for permanent deletion, before any seal migration. The nodes are still running. What is the risk?
A: Nothing changes, because the five recovery key shares can unseal the cluster if the KMS key disappears
B: After the key is gone, restarted nodes cannot unseal and the cluster cannot be recovered, even from backups

G: ## Lifecycle dependency on the seal
Auto-unseal creates a strict dependency on the seal mechanism. Recovery keys cannot decrypt the root key. @ VLT-VA003 D8 T8.5 applied comparison
S: A Vault Enterprise customer needs a warm standby cluster in another region. After a regional outage, applications should keep their existing tokens and leases with no new logins. Which replication type fits?

C: Disaster recovery replication, since the secondary shares the primary's token and lease data and is promoted on failure

G: ## DR vs performance replication (Enterprise)
Both copy configuration from a primary, but they target different goals.
- Disaster recovery (DR): a warm standby that mirrors the primary, including tokens, leases and local mounts. It does not serve client requests until it is promoted. Designed against the loss of a whole cluster.
- Performance: secondaries serve client requests locally (scaling reads, cutting latency) and keep their own tokens and leases. Local mounts are not visible to the other side.
## Failover consequence
After a DR promotion, clients can continue with existing tokens and leases. With performance secondaries, applications must re-authenticate and obtain new leases when a secondary is promoted.
W: DR replication: it mirrors tokens and leases and serves no clients until promotion, matching the warm-standby requirement.
X: A=Performance with own tokens: performance secondaries do keep their own tokens and leases, which means clients need new logins after promotion, the opposite of the requirement.
B=Performance mirrors tokens: performance replication does not mirror tokens, leases or local mounts from the primary.
D=DR serves reads: DR secondaries do not forward or serve requests until elected primary, so they cannot give clients local reads.
T: DR replication is a warm standby that keeps tokens and leases; performance replication serves local clients.
