@ AZ-305 D1 T1.1 expert use-case
S: A company has 120 key vaults in West Europe and 80 in East US. Every vault's AuditEvent logs must go to the security team's Log Analytics workspace, to the operations team's workspace, to an Azure Event Hubs-based SIEM feed, and to a storage account for seven-year archive. Each vault already carries three diagnostic settings owned by other teams that can't be changed or removed. The network team also wants as few new Event Hubs namespaces and storage accounts as the platform allows, and the SIEM can read from several event hubs. Which THREE design decisions should you recommend? (Select THREE)
A: Create one Event Hubs namespace and one archive storage account in each of the two regions, used only by the vaults in that region
B: Add one diagnostic setting per vault that sends AuditEvent to the security workspace, the regional event hub and the regional storage account
C: Add a second diagnostic setting per vault that sends AuditEvent to the operations team's Log Analytics workspace as its only destination
D: Create one Event Hubs namespace and one archive storage account in West Europe, used by all 200 vaults so the SIEM reads a single feed
E: Add four diagnostic settings per vault, one for each destination, so that every owning team can change its own setting independently
F: Add one diagnostic setting per vault that sends AuditEvent to both Log Analytics workspaces, the regional event hub and the regional storage account
K: A,B,C
G: ## Three rules of diagnostic settings
- **Up to five diagnostic settings per resource.**
- **One destination of each type per setting**: a setting can send to one Log Analytics workspace, one storage account, one event hub and one partner solution. Two workspaces need two settings.
- **Same region for storage and Event Hubs**: for regional resources, the storage account and event hub must be in the resource's region. Log Analytics workspaces can be in any region.
## Working the numbers
- Existing settings: 3 per vault, so at most **2 new** settings fit under the limit of 5.
- Destinations needed: 2 workspaces, 1 event hub, 1 storage account. The two workspaces force 2 settings; the event hub and the storage account can ride along in either.
- Vaults sit in 2 regions, so the minimum is **2 Event Hubs namespaces and 2 storage accounts** (one pair per region).
Result: setting 1 = security workspace + regional event hub + regional storage; setting 2 = operations workspace.
W: A=One namespace and storage account per region: Event Hubs and storage destinations must be in the vault's region, so two pairs is the smallest design that the platform allows.
B=Combined setting: one setting may hold one workspace, one event hub and one storage account, which covers three of the four destinations in a single setting.
C=Second setting for the operations workspace: a second workspace needs its own setting, and this brings each vault to exactly five settings.
X: D=Single West Europe namespace and storage: East US vaults can't send diagnostic logs to an event hub or storage account in another region.
E=Four separate settings: three existing plus four new is seven, above the five-setting limit per resource.
F=Both workspaces in one setting: a diagnostic setting can define only one destination of each type, so two workspaces can't share a setting.
T: Diagnostic settings: max 5 per resource, one destination of each type per setting, and storage/Event Hubs in the resource's region.
V: Azure Monitor, Azure Key Vault, Azure Event Hubs, Log Analytics

Its federated identity credential has the subject repo:contoso/infra:ref:refs/heads/main, and deployments worked for months. To require approvals, the team added environment: production to the deploy job. Since then the Azure sign-in step fails, saying that no matching federated identity record was found for the presented assertion. Security requires that only jobs that passed the production approval can deploy, and no secrets may be stored in GitHub. A nightly drift-check job on main, without an environment, uses the same identity and must keep working. What should you recommend?
A: Add a second federated credential to the identity with the subject repo:contoso/infra:environment:production and keep the approval
B: Change the existing credential's subject to repo:contoso/infra:ref:refs/heads/* so that the main branch and every other branch match it
C: Remove environment: production from the deploy job and enforce approvals with a required-reviewers rule in the main branch protection
D: Replace the federated credential with a client secret for the identity's app, stored as an environment secret of the production environment
K: A
G: ## How the token exchange matches
With workload identity federation, Microsoft Entra ID trusts an external token when its **issuer** and **subject** (`sub` claim) exactly match a federated identity credential on the app or managed identity. There's no pattern matching for branches or tags.
## GitHub's subject formats
- Job **tied to an environment**: `repo:<org>/<repo>:environment:<name>`
- Job not tied to an environment: `repo:<org>/<repo>:ref:<ref path>`, for example `refs/heads/main`

Adding `environment: production` changed the token's subject from the `ref` form to the `environment` form, so the old credential no longer matches. A wrong subject is accepted when the credential is created; the error appears only at token exchange.
W: Environment subject credential: the job's token now carries the environment subject, so a second credential for exactly that subject restores sign-in, only jobs in the approved production environment can match it, and the existing ref credential keeps the nightly job working.
X: B=Wildcard branch subject: federated credentials don't support pattern matching, so the change would also break the nightly job, and the deploy job's subject is the environment form anyway.
C=Branch protection instead of environment: it restores the old subject, but approvals would gate merges, not the deploy job, weakening the rule that only approved jobs deploy.
D=Client secret in an environment secret: it works technically, but it reintroduces a stored secret, which security forbids.
T: GitHub jobs that use an environment present the subject repo:org/repo:environment:name; the federated credential must match it exactly.

Which THREE actions should you recommend? (Select THREE)
A: Enable the option that lets trusted Microsoft services bypass the key vault firewall, or add a private endpoint for the vault

The database encryption key is wrapped by the **TDE protector** in Key Vault. The server's managed identity needs **Get, wrapKey and unwrapKey** on that key, continuously.

X: D=Virtual network rule for the server's subnet: an Azure SQL logical server doesn't run in a customer subnet, so a virtual network rule can't identify its traffic.

F=Temporary service-managed key: it breaks the rule that the key must stay customer-managed, even if only for a while.

Last night an engineer deleted resource group rg-core, and every tagged resource in it was deleted with no error. Teams must still be able to update tagged resources, and to delete untagged resources in the same resource groups whenever they like. Locks were rejected because some groups mix tagged and untagged resources. The policy definition uses mode indexed. What should you change?
A: Set cascadeBehaviors for resourceGroup to deny in the denyAction rule, so a group holding tagged resources can't be deleted
B: Add a CanNotDelete lock on each resource group that contains tagged resources, so the group and the resources in it can't be deleted
C: Change the policy definition's mode from indexed to all, so the policy also evaluates resource group deletions that remove tagged resources
D: Move the assignment from the subscription to its management group, so delete operations started at higher scopes are also evaluated
K: A
G: ## What denyAction protects
`denyAction` blocks requests by intended action; today the only action is **DELETE**. A delete call aimed directly at a matching resource fails.
## Cascade deletes
Deleting a parent deletes its children implicitly, and policy doesn't stop that by default:
- During a **resource group deletion**, Azure Policy evaluates indexed resources (those that support tags and location) against `denyAction` policies, but **only policies with `cascadeBehaviors` set to `deny` block the group deletion**.
- Policy doesn't block removal of resources that don't support tags and location, nor any policy with `mode: all`.
- A subscription deletion isn't blocked.
## Example
`"details": { "actionNames": ["delete"], "cascadeBehaviors": { "resourceGroup": "deny" } }`
W: cascadeBehaviors set to deny: with it, deleting rg-core fails while it holds protect=yes resources, and teams can still update tagged resources and delete untagged ones directly.
X: B=CanNotDelete locks: a lock on a group blocks deleting any resource in it, including the untagged ones teams must be able to delete, which is why locks were rejected.
C=Mode all: the docs say policy doesn't block removal for policies with mode all, so this would make protection weaker, not stronger.
D=Assign at the management group: the scope of the assignment isn't the gap; without cascadeBehaviors, resource group deletion still isn't blocked at any scope.
T: denyAction blocks direct deletes; set cascadeBehaviors.resourceGroup to deny to stop resource group deletion from removing protected resources.

@ AZ-305 D1 T1.2 expert troubleshooting
S: Twenty function apps each have their own user-assigned managed identity. To simplify access, the platform team added all twenty identities to a Microsoft Entra security group that holds Storage Blob Data Reader on a storage account. Four hours later, several apps still get 403 AuthorizationPermissionMismatch when reading blobs, while a test user added to the same group succeeded after signing in again. Permission changes must take effect within minutes in future, and adding more apps should need as few role assignments as possible. Restarting the apps didn't help. What should you recommend?
A: Attach one user-assigned managed identity to all twenty apps and grant Storage Blob Data Reader directly to it on the account
B: Keep the group and restart each function app twice, so the apps request new tokens that include the group membership in their claims
C: Replace the identities with system-assigned identities, add them to the same group, and wait for the next sign-in to refresh the claims
D: Keep the group and enable continuous access evaluation for the storage account, so that group membership changes are applied at once
K: A
G: ## Why the group change is slow
Group memberships and roles are claims in the access token, so authorization changes take effect only when a new token is issued. A user can sign in again (tokens last about an hour). **Managed identity tokens are cached by the Azure infrastructure per resource URI for around 24 hours**, and you can't force a refresh, so group or role membership changes for a managed identity can take hours.
## Microsoft's recommendation
When the delay isn't acceptable, don't use group membership for managed identities. Instead, attach **one user-assigned managed identity** to the resources that share access and **grant roles directly** to it. The user-assigned identity behaves like a group: adding an app means attaching the identity, not changing memberships.
## Example
`id-blob-readers` holds Storage Blob Data Reader on `stdocs`; a new function app gets `id-blob-readers` assigned and works without a role change.
W: Shared user-assigned identity with a direct role: no group claim is involved, so the token cache doesn't delay access, and new apps need no new role assignment.
X: B=Restart the apps: the token cache sits in the managed identity back end, not in the app, so restarts don't fetch a token with the new group claim.
C=System-assigned identities in the group: the group-claim caching is the same for any managed identity, and system-assigned identities can't be shared, so assignments multiply.
D=Continuous access evaluation: it isn't a way to push group changes into managed identity tokens for storage access, so the cached token stays in use.
T: Managed identity tokens are cached about 24 hours; grant roles directly to a shared user-assigned identity instead of using group membership.
V: Managed identities, Azure Storage, Azure Functions

@ AZ-305 D2 T2.2 expert troubleshooting
S: An IoT platform stores readings in an Azure Cosmos DB for NoSQL container partitioned by /tenantId, with 60,000 RU/s of manual throughput. There are 40 tenants; the largest one needs about 14,000 RU/s at peak, while the whole container uses about 35,000 RU/s then. Metrics show 429 responses only for that tenant's requests. Every query reads one device's readings by deviceId, and no query spans devices. The team asked finance for 120,000 RU/s, but the architect says that won't fix it, and finance wants provisioned throughput to stay at 60,000 RU/s. What should you recommend?
A: Create a new container partitioned by /deviceId and migrate the data to it, because one logical partition can never exceed 10,000 RU/s
B: Raise the container's manual throughput to 120,000 RU/s, so that the physical partition that holds the largest tenant gets twice the RU/s
C: Switch the container to autoscale with a maximum of 60,000 RU/s, so the largest tenant's partition scales up instantly when its load rises
D: Enable dynamic autoscale on the container, so the physical partition of the largest tenant scales independently of the other partitions
K: A
G: ## Logical and physical partitions
All items with the same partition key value form a **logical partition**, and every logical partition lives on exactly **one physical partition**. Each physical partition can serve **up to 10,000 RU/s**, so a single logical partition is also capped at 10,000 RU/s, however much throughput the container has.
## Working the numbers
- Container: 60,000 RU/s, so 35,000 RU/s total demand is well within it.
- The largest tenant needs 14,000 RU/s, but its key value is one logical partition capped at 10,000 RU/s, so 4,000 RU/s of its demand is throttled.
- Doubling the container to 120,000 RU/s adds physical partitions, but a single key value still can't use more than one.
## The fix
Pick a key with many values that matches the queries: `/deviceId` spreads each tenant over many logical partitions, and every query stays single-partition. A container's partition key can't be changed in place, so create a new container and migrate.
W: New container on /deviceId: the busy tenant's load spreads across many logical partitions below the 10,000 RU/s cap, and the device-scoped queries stay single-partition.
X: B=120,000 RU/s: more throughput creates more physical partitions, but the tenant's single logical partition is still capped at 10,000 RU/s.
C=Autoscale to 60,000: autoscale changes how the container's throughput is provisioned, not the per-partition cap that throttles the tenant.
D=Dynamic autoscale: partitions scale independently, but no physical partition can exceed 10,000 RU/s, so the 14,000 RU/s tenant still throttles.
T: A hot partition key value is capped at 10,000 RU/s; fix the key, not the container's throughput.
V: Azure Cosmos DB

S: A booking app's Cosmos DB container has 50,000 RU/s of manual throughput all month. Load reaches 50,000 RU/s during about six hours of each of 22 business days, at times that vary from day to day, and otherwise stays near 3,000 RU/s. The month has about 730 hours. The team won't write code that changes throughput, requests must never be throttled below 50,000 RU/s, and finance wants the cheapest configuration that meets both rules. The account has a single write region, and its other containers stay on manual throughput. Which configuration should you recommend?
A: Autoscale with a maximum of 50,000 RU/s, scaling between 5,000 and 50,000 RU/s and billing each hour at its highest level
B: Manual throughput of 50,000 RU/s kept as it is, because peak hours are unpredictable and manual throughput is billed at the lower rate per RU/s
C: Autoscale throughput with a maximum of 25,000 RU/s, sized from the monthly average load so that most hours bill at the 2,500 RU/s floor
D: Manual throughput of 3,000 RU/s with a timer-triggered function that raises it to 50,000 RU/s at 08:00 and lowers it again at 14:00
K: A
G: ## How autoscale works and bills
With autoscale you set a maximum `Tmax`; Cosmos DB scales instantly between **0.1 × Tmax and Tmax** and bills each hour for the **highest** throughput reached in that hour. The autoscale rate per RU/s is higher than the manual rate, so Learn's rule of thumb is that autoscale saves money if the full `Tmax` is used for **66% or fewer** of the hours in a month.
## Working the numbers
- Peak hours: 6 × 22 = **132 hours**, about **18%** of 730 hours, far below 66%.
- Other hours bill at the floor: 0.1 × 50,000 = **5,000 RU/s**, instead of 50,000 RU/s all month with manual throughput.
- A maximum of 25,000 RU/s would cap peaks at half the demand and throttle.
## Why not scheduled scaling
The peak times vary, so a fixed schedule misses peaks, and it is code the team won't write.
W: Autoscale with Tmax 50,000: full throughput is used about 18% of the hours, well under the 66% break-even, the floor is 5,000 RU/s the rest of the time, and peaks are never throttled.
X: B=Keep manual 50,000: it is safe, but it pays for 50,000 RU/s in all 730 hours although only about 132 hours need it.
C=Autoscale with Tmax 25,000: peaks need 50,000 RU/s, so half of each peak's requests would be throttled.
D=Timer-scaled manual throughput: it is the code the team refuses, and peaks that fall outside 08:00 to 14:00 would be throttled at 3,000 RU/s.
T: Cosmos DB autoscale pays off when Tmax is needed in 66% or fewer of the hours; it scales between 10% of Tmax and Tmax.
