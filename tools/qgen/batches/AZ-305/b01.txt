@ AZ-305 D1 T1.1 advanced tradeoff
S: A company with one Microsoft Entra tenant is designing its Log Analytics architecture and wants as few workspaces as possible. Which two requirements justify creating an additional workspace? (Select TWO)
A: Logs from resources in the EU must be stored only in an EU region, while US resources may log to a US region
B: The same table must keep data from production resources for two years but data from test resources for 30 days
C: Total ingestion is expected to reach several terabytes, which would slow down queries in a single workspace
D: Each application team wants its own dashboards and should see only the logs of the resources it manages
E: Security analysts need to correlate sign-in data, firewall logs and VM events from every team in one query
K: A,B
G: ## Start with one workspace
Microsoft's workspace design guidance says a design should always **start with a single Log Analytics workspace** and add workspaces only when a specific criterion requires it. One workspace is simpler to manage and to query, and the amount of data in a workspace does not impose performance limits.
## Criteria that do justify more workspaces
- **Azure regions / data residency**: each workspace lives in one region. If data from some resources must stay in a geography, create a workspace in that geography.
- **Data retention**: retention is set per workspace and per table. If the *same table* needs different retention for different resources, those resources need different workspaces.
- **Microsoft Entra tenants**: most resources can only send to a workspace in their own tenant.
- **Data ownership** and **split billing** (when Cost Management or a log query is not granular enough).
- **Operational versus security data** (Microsoft Sentinel), and **resilience** across regions.
## Criteria that do not
Per-team visibility is handled by access control (resource-context access, table-level RBAC), not by more workspaces. Cross-team correlation is easier in one workspace.
## Example
A company with EU and US subsidiaries uses `law-eu-prod` in West Europe and `law-us-prod` in East US, and nothing more until another criterion appears.
W: A=Data residency: a workspace resides in exactly one Azure region, so a requirement to keep EU data in the EU while US data lives in the US can only be met with a workspace in each geography.
B=Different retention in one table: retention is configured per workspace and per table, not per resource, so two retention periods for the same table need two workspaces.
X: C=Large data volume: Learn states that the amount of data in a workspace doesn't impose performance limitations, so volume alone is not a reason to split.
D=Per-team views: the default access control mode lets users query the logs of resources they can read (resource-context), and workbooks or dashboards can be scoped per team, all inside one workspace.
E=Cross-team correlation: this requirement argues for keeping data together; spreading it over more workspaces makes such queries slower and harder to write.
T: Begin with one workspace and add more only for concrete criteria such as data residency, per-resource retention in the same table, separate tenants, ownership or billing.
V: Azure Monitor Logs, Log Analytics workspace

@ AZ-305 D1 T1.1 applied tradeoff
S: A security team will run Microsoft Sentinel and wants sole ownership of its data. The operations team ingests large volumes of performance and application logs that never need security analytics. Cost must be minimized. Which workspace design should you recommend?
A: One combined workspace with Microsoft Sentinel enabled, and table-level RBAC that hides the security tables from operators
B: A dedicated workspace for Microsoft Sentinel and a separate workspace without Sentinel for the operational data
C: One combined workspace with Microsoft Sentinel enabled, and resource-context access for every operations team member
D: A separate workspace per resource group, each with Microsoft Sentinel enabled so that both teams see the same tools
K: B
G: ## Operational and security data
Azure Monitor (operations) and Microsoft Sentinel (security) both store data in Log Analytics workspaces. A design can combine them or separate them, and each choice has a cost and an ownership effect.
- **Combined workspace**: one place to query, and the larger volume may reach a commitment tier. Access can be limited with table-level RBAC or resource-context access.
- **Dedicated workspaces**: the security team owns its workspace and its artifacts, and costs can be lower because **when Sentinel is enabled on a workspace, all data in that workspace is subject to Sentinel pricing**, including operational data collected by Azure Monitor.
## Deciding
Learn's guidance: separate them if the security team requires it or if it saves money; combine them for better visibility or to reach a commitment tier. Here both deciding facts (ownership and high-volume operational data with no security use) point to separation.
W: B=Separate Sentinel and operations workspaces: the security team gets a workspace it owns, and the large operational volume stays in a workspace without Sentinel, so it is not billed at Sentinel rates.
X: A=Combined with table-level RBAC: table-level RBAC controls who reads which tables, but with Sentinel enabled every gigabyte of operational data in the workspace still falls under Sentinel pricing, and ownership is shared.
C=Combined with resource-context access: resource-context access limits operators to their own resources' logs, yet the workspace and its Sentinel cost model are still shared, so neither the ownership nor the cost requirement is met.
D=Workspace per resource group with Sentinel: this multiplies workspaces without a design criterion and puts Sentinel pricing on every one of them, which is the most expensive option.
T: Enabling Microsoft Sentinel makes all data in that workspace subject to Sentinel pricing, so keep large operational data in a separate workspace when cost or security ownership requires it.
V: Log Analytics workspace, Microsoft Sentinel

@ AZ-305 D1 T1.1 advanced use-case
S: Eight business units each keep their own Log Analytics workspace in West Europe; together they ingest about 300 GB per day. Compliance requires customer-managed encryption keys. How should you meet this and lower ingestion cost?
A: Set a commitment tier on each of the eight workspaces and configure a customer-managed key on each workspace directly
B: Merge the eight workspaces into one workspace and give each unit resource-context access to its own resources' data
C: Create a Log Analytics dedicated cluster in West Europe with a commitment tier and link all eight workspaces to it
D: Add all eight workspaces to one Azure Monitor Private Link Scope so that their data is encrypted with a private key
K: C
G: ## What a dedicated cluster adds
A Log Analytics **dedicated cluster** is an Azure Monitor resource that existing workspaces can be linked to without interrupting ingestion or queries. Capabilities listed on Learn:
- **Customer-managed keys**: encrypt data with a key you control in Azure Key Vault.
- **Lockbox** and **double encryption**.
- **Cost optimization**: link workspaces *in the same region*, and the cluster's commitment tier discount applies to data ingested from all linked workspaces.
- Faster cross-workspace queries between linked workspaces.
## Pricing model
Dedicated clusters use commitment tiers starting at 100 GB per day; usage above the tier is charged per GB.
## Example
Eight workspaces at 30 to 50 GB per day each are too small for good per-workspace tiers, but together (about 300 GB per day) they fill a cluster commitment tier, and every workspace stays separate for its business unit.
W: C=Dedicated cluster with linked workspaces: the cluster provides customer-managed keys, and its commitment tier applies to the combined ingestion of all linked workspaces in the same region, while each business unit keeps its own workspace.
X: A=Per-workspace commitment tier and keys: commitment tiers apply per workspace, so the volume is not pooled, and customer-managed keys for Log Analytics are a dedicated cluster capability rather than a setting on a standalone workspace.
B=Merge into one workspace: a single workspace would pool the volume, but it removes the separate workspaces the business units own and still provides no customer-managed key without a cluster.
D=Azure Monitor Private Link Scope: AMPLS makes ingestion and queries flow over private endpoints; it controls network paths and does not provide customer-managed key encryption or any pricing discount.
T: Many workspaces in one region that need customer-managed keys or a shared commitment discount point to a Log Analytics dedicated cluster.
V: Log Analytics dedicated cluster, customer-managed keys

@ AZ-305 D1 T1.1 applied use-case
S: A central workspace receives logs from all subscriptions. App teams have Reader on their own resource groups and must query only their resources' logs, without being granted any workspace permissions. What should you recommend?
A: Set the access control mode to Require workspace permissions and grant each team Log Analytics Reader on the workspace
B: Keep the access control mode Use resource or workspace permissions and let teams query logs from their resources (resource-context)
C: Create one workspace per team and redirect each resource's diagnostic settings to the workspace of the team that owns it
D: Configure table-level RBAC that grants each team read access only to the tables that its own resources write data into
K: B
G: ## Two ways to open a workspace (access modes)
- **Workspace-context**: you open the workspace itself and can query all data in the tables you have permission to. Intended for central administrators.
- **Resource-context**: you open Logs from a resource, resource group or subscription. Queries are scoped to data associated with those resources (`_ResourceId`), in any workspace.
## Access control mode (a workspace setting)
- **Use resource or workspace permissions** (default): a user with read permission on a resource can query that resource's logs in resource-context, with no workspace role at all.
- **Require workspace permissions**: users must be granted access to the workspace or specific tables; resource permissions alone are not enough.
## Example
A team with Reader on `rg-payments` opens Logs from that resource group and sees only rows whose `_ResourceId` belongs to `rg-payments`, even though the workspace holds every subscription's data.
W: B=Resource or workspace permissions with resource-context: the default mode lets resource permissions grant access to the matching log data, so the teams' existing Reader roles are enough and they never see other teams' rows.
X: A=Require workspace permissions with Log Analytics Reader: workspace-level read lets every team query all data in the workspace, which breaks the "only their resources" rule and the "no workspace permissions" constraint.
C=One workspace per team: Learn recommends the fewest workspaces; access separation is an access-control problem that resource-context already solves, so extra workspaces add management and query cost for nothing.
D=Table-level RBAC per team: tables such as `AzureDiagnostics` or `Perf` hold rows from many teams' resources, so table-level access cannot separate one team's rows from another's.
T: Let owners see only their resources' logs in a shared workspace by keeping "Use resource or workspace permissions" and relying on resource-context queries.
V: Log Analytics workspace, Azure RBAC

@ AZ-305 D1 T1.1 applied comparison
S: A managed service provider monitors Azure resources, including PaaS services, for 40 customers, each in its own Microsoft Entra tenant. Customers require isolated data, their own retention and billing. Admins must not sign in to each tenant. What should you recommend?
A: One workspace in the provider's tenant that collects every customer's logs, with each customer separated by subscription ID in queries
B: A workspace in each customer tenant, with each provider admin invited as a Microsoft Entra B2B guest user into every customer tenant
C: A workspace in each customer tenant, with provider admins given delegated access to all of them through Azure Lighthouse onboarding
D: A workspace in each customer tenant, with a scheduled Logic App that copies all customer data into a single provider workspace daily
K: C
G: ## Multitenant workspace strategies
Learn describes three strategies for service providers:
- **Distributed**: a workspace in each customer tenant. It is the only option that monitors Azure services other than VMs, keeps each customer's settings (retention, data cap) separate, isolates data for compliance and bills each customer's own subscription.
- **Centralized**: one workspace in the provider's subscription. It only collects from VMs with agents or PaaS through Lighthouse delegation, mixes customers' data, and forces one region, one bill and one retention for all.
- **Hybrid**: per-tenant workspaces plus a mechanism that pulls selected or summarized data to a central place.
## Reaching the customer workspaces
- **Azure Lighthouse**: provider admins in a group of the provider's tenant are granted access during onboarding and work on customer workspaces from their own tenant.
- **B2B guests**: each customer adds each admin as a guest; admins must sign in to each tenant's directory.
W: C=Distributed workspaces with Azure Lighthouse: each customer keeps an isolated workspace with its own retention and billing, and Lighthouse lets provider admins work across all of them from their own tenant without signing in to each one.
X: A=Central provider workspace: all customers share one retention setting, region and bill, data is separated only by query filters, and SaaS connectors and some data sources can't send to another tenant's workspace.
B=Workspaces with B2B guests: isolation is right, but guest access requires the admins to sign in to each customer's directory, which the stem rules out, and each customer must manage every guest.
D=Copy everything into a provider workspace: duplicating all data defeats the isolation requirement and doubles ingestion cost; Learn's hybrid model only centralizes a small subset or a summary.
T: Service providers that need per-customer isolation, retention and billing use a workspace per customer tenant and reach them through Azure Lighthouse.
V: Log Analytics workspace, Azure Lighthouse

@ AZ-305 D1 T1.1 applied use-case
S: Resource logs from regional Azure resources must reach a non-Microsoft SIEM in near real time and also be archived for seven years at low cost so that no one can alter them. Which two destinations should the diagnostic settings use? (Select TWO)
A: An Event Hubs namespace in the same region as the monitored resources, read by the SIEM's connector
B: A Standard storage account in the same region with a time-based immutability policy on the container
C: A Log Analytics workspace with a seven-year total retention that the SIEM queries through the API
D: A Premium block blob storage account with a legal hold placed on the container that stores the logs
E: An Event Grid custom topic in the same region that forwards each log record to the SIEM's endpoint
K: A,B
G: ## Where diagnostic settings can send data
A diagnostic setting collects resource logs (not collected by default), platform metrics or the activity log and sends them to one or more destinations:
- **Log Analytics workspace**: KQL queries, workbooks and log alerts.
- **Azure Storage account**: low-cost storage for audit, static analysis or backup, kept as long as you need. Send to **immutable storage** to prevent modification. Premium storage accounts are not supported as destinations.
- **Azure Event Hubs**: stream data to external systems such as non-Microsoft SIEM solutions.
- **Azure Monitor partner solutions**: specific Azure Native ISV integrations.
## Rules that matter for the design
- For regional resources, the storage account and event hub must be in the **same region** as the monitored resource.
- One setting can include each destination type once; Event Hubs and Storage can be combined in one setting.
- Data in a Log Analytics workspace can't be edited, but it **can be purged**, so it is not a tamper-proof archive.
W: A=Event Hubs in the same region: Event Hubs is the diagnostic settings destination intended for streaming to external SIEM tools in near real time.
B=Standard storage with immutability: a Standard storage account is the low-cost long-term destination, and a time-based immutability policy stops anyone from modifying or deleting the archived logs during the retention period.
X: C=Workspace with seven-year retention: retention up to 12 years is possible, but data in a workspace can be purged, so it does not satisfy "no one can alter them", and long retention in a workspace costs more than blob storage.
D=Premium block blob account: Learn states that Premium storage accounts aren't supported as diagnostic settings destinations; only Standard accounts are.
E=Event Grid custom topic: Event Grid is not a diagnostic settings destination; the streaming destination is Event Hubs.
T: Diagnostic settings stream to external SIEMs through Event Hubs and archive cheaply and tamper-proof to a Standard storage account with an immutability policy.
V: Diagnostic settings, Event Hubs, Azure Storage

@ AZ-305 D1 T1.1 applied use-case
S: Auditors need to know who created or deleted resources in a subscription over the past three years, queried with KQL together with other operational logs. Today only the portal's activity log is used. What should you recommend?
A: Increase the activity log retention period of the subscription to three years from the subscription's activity log settings
B: Create a diagnostic setting for the subscription activity log that sends it to a Log Analytics workspace with three-year table retention
C: Use Azure Resource Graph queries, because Resource Graph stores every create and delete operation for the lifetime of a subscription
D: Export the activity log to CSV from the portal every month and upload the files to a storage account that auditors can query with KQL
K: B
G: ## The activity log
The activity log records subscription-level control-plane events: who created, changed or deleted a resource, and when. It is collected automatically and free of charge, but **Azure keeps activity log events for 90 days and then deletes them**. Retention in the activity log itself can't be changed.
## Keeping it longer
Create a **diagnostic setting for the activity log** (at subscription level). Learn notes that one of the most common reasons is to preserve resource creator information, which only the activity log contains.
- To a **Log Analytics workspace**: entries land in the `AzureActivity` table, which can be queried with KQL alongside other logs and kept as long as the table's retention allows (analytics retention up to two years, total retention up to 12 years).
- To **Storage**: cheapest archive, but no KQL queries in place.
- To **Event Hubs**: stream to external tools.
W: B=Activity log diagnostic setting to a workspace: the setting copies every activity log event into the `AzureActivity` table, where table retention can cover three years and auditors can join it with other operational logs in KQL.
X: A=Longer activity log retention: the activity log's 90-day retention is fixed; keeping events longer requires routing them elsewhere with a diagnostic setting.
C=Azure Resource Graph: Resource Graph is for querying the current inventory and properties of resources at scale; it is not a multi-year audit trail of who performed each operation.
D=Monthly CSV exports: a manual export can miss events and be forgotten, and CSV files in blob storage can't be queried with KQL alongside other logs in Log Analytics.
T: The activity log keeps 90 days; send it with a diagnostic setting to a Log Analytics workspace (or storage) for longer retention and KQL analysis.
V: Azure Monitor activity log, Log Analytics workspace

@ AZ-305 D1 T1.1 applied use-case
S: A company has 250 Windows VMs in Azure and 150 Windows servers on-premises. It needs the same Windows event IDs and performance counters from all of them, managed from one central definition. What should you recommend?
A: Install the legacy Log Analytics agent on all servers and configure event and counter collection in each workspace's agent settings
B: Enable a diagnostic setting on each Azure VM resource, and use the same diagnostic setting on the on-premises servers through VPN
C: Arc-enable the on-premises servers, install Azure Monitor Agent on all 400 machines and associate one data collection rule with them
D: Write a scheduled script on each server that reads the events and posts them to the workspace through the Logs Ingestion API
K: C
G: ## Azure Monitor Agent and data collection rules
**Azure Monitor Agent (AMA)** is the supported agent for collecting guest OS data (events, performance counters, syslog, text logs). It replaces the legacy Log Analytics agent.
AMA collects whatever its associated **data collection rules (DCRs)** describe:
- A DCR defines the data sources (for example specific event IDs and counters), optional transformations and the destination workspace.
- A **data collection rule association (DCRA)** links one machine to one DCR. One DCR can be associated with many machines, and one machine can have several DCRs.
- Learn recommends designing a DCR as a reusable collection policy: change it once and every associated machine follows.
## Machines outside Azure
On-premises and other-cloud servers are onboarded with **Azure Arc-enabled servers** (the Azure Connected Machine agent). After that, AMA and DCRs work on them exactly as on Azure VMs.
W: C=Azure Arc, AMA and one shared DCR: Arc gives the on-premises servers an Azure identity, AMA runs on all 400 machines, and a single DCR associated with every machine defines the event IDs and counters centrally.
X: A=Legacy Log Analytics agent: the legacy agent has been replaced by Azure Monitor Agent, and its configuration lives in workspace settings rather than in reusable rules that can be targeted at chosen machines.
B=Diagnostic settings on VM resources: diagnostic settings route platform metrics and resource logs of Azure resources; they do not read guest OS event logs and can't be applied to on-premises servers.
D=Custom Logs Ingestion API scripts: the API is for custom applications that send their own data; scripting event collection on 400 servers recreates what AMA already does and has no central definition.
T: For guest OS data from Azure and on-premises servers, use Azure Arc where needed, Azure Monitor Agent everywhere and shared DCRs as central collection policies.
V: Azure Monitor Agent, data collection rules, Azure Arc

@ AZ-305 D1 T1.1 applied use-case
S: Azure Monitor Agent collects a custom application text log into a Log Analytics table. One column contains customer account numbers that must never be stored in the workspace. Other columns must still be collected. What should you recommend?
A: Grant table-level RBAC on the custom table so that only the security team can read the column with account numbers in it
B: Add an ingestion-time transformation to the data collection rule that removes the account number column before storage
C: Create a data export rule for the table with a filter that drops the account number column before data is sent to storage
D: Move the custom table to the Basic table plan so that the account number column is kept out of interactive query results
K: B
G: ## Transformations
A **transformation** is a KQL statement in a data collection rule (DCR) that filters or modifies incoming data **before** it is written to a Log Analytics workspace. Typical uses:
- Drop rows you do not need (cost and noise).
- Remove or mask sensitive columns so they are never stored.
- Add calculated columns or parse a string into fields.
Transformations run on the Azure Monitor ingestion pipeline. For data paths that do not use a DCR (for example many diagnostic settings), a **workspace transformation DCR** applies them at the workspace instead.
## Example
`source | project-away AccountNumber` in the DCR's data flow keeps every other column and stores no account numbers at all.
W: B=Ingestion-time transformation in the DCR: the transformation runs before the data is written, so the sensitive column is removed while all other columns are still collected and stored.
X: A=Table-level RBAC: access control decides who can read the data, but the account numbers would still be stored in the workspace, which the requirement forbids.
C=Data export rule with a filter: export rules copy data that has already reached the workspace and have no filter of their own; the table would still contain the column.
D=Basic table plan: the plan changes cost and query capabilities, not the schema; every column is still stored and can still be queried.
T: To keep data out of a workspace entirely (rows or columns), filter it with a DCR transformation before ingestion, not with access control or export.
V: Data collection rules, transformations, Log Analytics

@ AZ-305 D1 T1.1 applied tradeoff
S: A custom app sends very verbose debug logs to a DCR-based custom table, tens of GB per day. Engineers query them only during incident investigations within 30 days, and no alerts use them. How should you minimize cost?
A: Keep the Analytics plan on the table and lower its analytics retention to four days so that much less data is billed
B: Set the table to the Basic plan, which lowers ingestion cost and still supports KQL queries during investigations
C: Move the table to a new workspace that uses the highest commitment tier so that each GB of debug logs costs less
D: Stop sending the logs to Log Analytics and write them only to blob storage that engineers download and search by hand
K: B
G: ## Table plans
Each table in a Log Analytics workspace has a plan:
- **Analytics**: full features for continuous monitoring, alerts and latency-sensitive analysis. The default for Azure tables.
- **Basic**: for troubleshooting and incident response. Cheaper ingestion, extra charge per query, interactive queries over a fixed 30-day period, data older than that only through search jobs.
- **Auxiliary**: high-volume, verbose data for long-term, inexpensive storage.
All DCR-based custom tables support every plan; support on Azure tables varies by table.
## Retention is not a cost lever below 31 days
Learn notes that 31 days of analytics retention are included in the ingestion price, so lowering analytics retention below 31 days does not reduce costs.
W: B=Basic plan: the logs are high-volume, used only for occasional troubleshooting inside 30 days and not used for alerts, which is exactly the Basic plan's purpose and gives a lower ingestion cost while keeping KQL available.
X: A=Four-day analytics retention: ingestion is the main charge and 31 days of retention are included in it, so cutting retention to four days saves nothing.
C=Commitment tier workspace: a commitment tier gives a discount only when the workspace reliably ingests a high daily volume; it still bills debug data at Analytics rates and adds a workspace.
D=Blob storage only: storage is cheap, but engineers lose KQL queries during incidents and must search downloaded files by hand, which slows investigations.
T: High-volume logs used only for occasional troubleshooting go into Basic tables; lowering retention below 31 days doesn't cut cost.
V: Log Analytics table plans

@ AZ-305 D1 T1.1 applied use-case
S: A compliance policy requires sign-in audit data to be interactively queryable for 180 days and kept for seven years in total. The data must stay in Log Analytics without a separate export pipeline. What should you recommend?
A: Set the table's analytics retention to seven years so that every record stays available for interactive queries for the whole period
B: Set analytics retention to 180 days and total retention to seven years, and use search jobs for records older than 180 days
C: Set the table to the Basic plan with seven-year total retention so that all seven years stay interactively queryable at lower cost
D: Keep the default workspace retention and rely on Azure Backup for Log Analytics to restore older records into the workspace
K: B
G: ## Analytics, long-term and total retention
A table in Log Analytics keeps data in two states:
- **Analytics retention**: data is available for interactive queries, alerts and workbooks. For Analytics tables it can be extended up to two years.
- **Long-term retention**: a low-cost state after analytics retention ends. **Total retention** (analytics plus long-term) can be set up to 12 years.
Data in long-term retention is retrieved with a **search job**: an asynchronous query that writes its results into a new Analytics table (`_SRCH`) that you can then query normally.
## Example
Analytics retention 180 days, total retention seven years: queries over the last 180 days run as usual; for an audit of a three-year-old event, a search job pulls the matching rows into a results table.
W: B=180 days analytics plus seven years total: this matches both requirements exactly, keeps everything in the workspace, and the five and a half years of long-term retention are billed at the low-cost long-term rate.
X: A=Seven years of analytics retention: analytics retention for Analytics tables can be extended only up to two years, and even within that limit it is the expensive state.
C=Basic plan for seven years: Basic tables are interactively queryable for only 30 days, so the 180-day interactive requirement is not met.
D=Azure Backup for Log Analytics: Azure Backup has no workload that protects Log Analytics data; long retention is set on the table itself.
T: Combine analytics retention (interactive, up to two years) with total retention (up to 12 years) and use search jobs to reach older data.
V: Log Analytics data retention, search jobs

@ AZ-305 D1 T1.1 applied comparison
S: Azure Monitor Agent sends security events from hundreds of VMs to a workspace. A downstream analytics platform must receive every new SecurityEvent record continuously as it arrives. What should you recommend?
A: A diagnostic setting on the Log Analytics workspace that streams the workspace's logs to an event hub in the same region
B: A Log Analytics data export rule for the SecurityEvent table with an event hub destination in the workspace's region
C: A summary rule in the workspace that aggregates SecurityEvent every hour and writes the results to an event hub topic
D: A Logic App that runs a log query every five minutes and posts the returned SecurityEvent rows to the analytics platform
K: B
G: ## Ways to get data out of a workspace
- **Data export rules**: continuously export the selected **tables** to a storage account or Event Hubs as data arrives in Azure Monitor. Up to 10 active rules per workspace; destinations must be in the same region as the workspace; data is exported unfiltered (use transformations to shape it).
- **Diagnostic settings on the source resource**: if a resource already sends logs through a diagnostic setting, adding another destination there is lower latency, but agent data such as `SecurityEvent` comes from AMA, not from a diagnostic setting.
- **Scheduled queries** (Logic Apps, Functions, Data Factory): can filter and aggregate, but are subject to query limits and are not intended for scale.
- **Summary rules**: aggregate data on a schedule into a custom table in the same workspace.
## A workspace's own diagnostic setting
A diagnostic setting on the workspace resource exports the workspace's own resource logs (such as audit of queries), not the contents of its tables.
W: B=Data export rule to Event Hubs: an export rule streams every new record of the selected table to an event hub as it arrives, at scale, which is exactly continuous delivery of SecurityEvent.
X: A=Workspace diagnostic setting: it exports logs about the workspace itself, such as query audit records, not the security events stored in its tables.
C=Summary rule: a summary rule writes aggregated results into a custom table inside the workspace; it neither sends to an event hub nor delivers every individual record.
D=Scheduled Logic App query: query-based export is limited by log query limits, can miss or duplicate records between runs, and Learn states it isn't intended for scale.
T: Continuous, per-table export of workspace data goes through data export rules to Storage or Event Hubs in the workspace's region.
V: Log Analytics data export, Event Hubs

@ AZ-305 D1 T1.1 applied comparison
S: An on-premises application must send custom JSON logs to a Log Analytics workspace that is reachable only through an Azure Monitor Private Link Scope. Records must be reshaped before storage. Which ingestion method should you recommend?
A: The HTTP Data Collector API, signing each request with the workspace's shared key and the workspace ID

@ AZ-305 D1 T1.1 applied tradeoff
S: A workspace ingests about 20 GB per day, mainly from diagnostic settings that use the allLogs category group and from AMA. Much of it is never queried. Which two changes should you recommend to reduce ingestion cost? (Select TWO)
A: Add transformations that drop rows nobody uses before they are written to the workspace's tables

The main charge is **data ingestion** (per GB). Retention up to 31 days is included in the ingestion price, so the biggest savings come from **sending less data**.

X: C=Seven-day retention: 31 days of retention are included in the ingestion price, so reducing analytics retention below 31 days doesn't lower cost.
D=Enable Microsoft Sentinel: once Sentinel is enabled, all data in the workspace is subject to Sentinel pricing, which raises the cost of this operational data.
E=Add AllMetrics: platform metrics are already free in metrics explorer; also sending them to the workspace adds ingestion instead of removing it.

V: Log Analytics cost, diagnostic settings, transformations

@ AZ-305 D1 T1.1 advanced use-case
S: VNets and on-premises networks (over ExpressRoute private peering) share one DNS. Monitoring traffic must use only private connectivity, and clients must not be able to send data to workspaces outside the company's approved list. What should you recommend?
A: A private endpoint for each Log Analytics workspace, each in its own private DNS zone, with public network access left enabled
B: A service endpoint for Azure Monitor on every subnet, with the workspaces' firewalls allowing only those subnets to connect
C: One Azure Monitor Private Link Scope with the approved resources and a private endpoint, using Private Only access mode
D: One Azure Monitor Private Link Scope per virtual network with a private endpoint, each configured to use the Open access mode
K: C
G: ## Azure Monitor Private Link Scope (AMPLS)
Private link for Azure Monitor works differently from most services. Instead of a private endpoint per resource, a virtual network connects through **one private endpoint to an AMPLS**, and the AMPLS lists the Azure Monitor resources (Log Analytics workspaces, data collection endpoints, Application Insights) that form the boundary of your monitoring network.
- Some endpoints are **shared** (for example log queries and Application Insights ingestion), so adding one resource changes DNS for all resources of that type. That is why Learn says to use **a single AMPLS for all networks that share the same DNS**; multiple AMPLS resources override each other's DNS zones and break existing environments.
- On-premises clients reach it through VPN or ExpressRoute private peering.
## Access modes
- **Open**: clients reach AMPLS resources privately and other Azure Monitor resources publicly; good for gradual onboarding, but it doesn't prevent exfiltration.
- **Private Only**: clients reach only resources in the AMPLS; Learn calls it the most secure option that prevents data exfiltration.
W: C=Single AMPLS with Private Only: one scope matches the shared DNS, the private endpoint keeps traffic on private connectivity, and Private Only mode blocks sending data to any workspace that isn't in the approved scope.
X: A=Private endpoint per workspace: Azure Monitor uses a private endpoint to an AMPLS rather than one per workspace, separate DNS zones would conflict on shared endpoints, and public access left enabled allows other paths.
B=Service endpoints: Azure Monitor private connectivity is built on Private Link with AMPLS; this design neither covers on-premises clients nor restricts which workspaces clients can send to.
D=One AMPLS per virtual network in Open mode: multiple scopes sharing one DNS override each other's records, and Open mode still lets clients reach resources outside the scope.
T: Private, exfiltration-proof Azure Monitor access is one AMPLS per shared DNS, with a private endpoint and Private Only access mode.
V: Azure Monitor Private Link Scope, Private Link
