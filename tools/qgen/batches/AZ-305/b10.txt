@ AZ-305 D4 T4.4 applied comparison
S: A retailer runs the same HTTPS web app in App Service in two Azure regions. It needs one global entry point that caches static content at the edge, applies a web application firewall, sends each user to the closest healthy region, and fails over without waiting for DNS caches to expire. Which solution should you recommend?
A: Azure Front Door with a WAF policy, and both regional apps configured as origins in one origin group
B: Azure Traffic Manager with Performance routing, and both regional apps added as Azure endpoints
C: One Azure Application Gateway WAF v2 in the primary region, with both regional apps in its backend pool
D: A global Azure Load Balancer whose backend pool holds a regional Standard Load Balancer for each app
K: A
G: ## Two questions decide the load balancer
Azure's load-balancing guidance sorts the services along two axes:
- **Global or regional**: global services spread traffic across regions (Front Door, Traffic Manager, the global tier of Load Balancer); regional services spread it across VMs or instances inside one region (Application Gateway, Load Balancer).
- **HTTP(S) or not**: Layer 7 services understand URLs, terminate TLS and can run a WAF (Front Door, Application Gateway); the others work at Layer 4 or through DNS.
## Where Front Door fits
Azure Front Door is a global HTTP(S) entry point and content delivery network. Clients connect to the nearest Microsoft edge location, Front Door can cache static content there, a WAF policy inspects requests, and Front Door forwards each request to the best healthy origin. Because clients keep talking to the same edge, a failed origin is removed from rotation without any DNS change.
## Example
`www.contoso.com` points to a Front Door endpoint. Origins `app-weu.azurewebsites.net` and `app-eus.azurewebsites.net` sit in one origin group with health probes; if West Europe fails, users are served from East US on their next request.
W: Front Door with WAF: it is the global Layer 7 service in the list, so it combines edge caching, WAF, latency-based origin selection and fast failover that doesn't depend on DNS caching.
X: B=Traffic Manager: it routes at the DNS level only. It has no cache and no WAF, and failover waits for clients and resolvers to drop the cached DNS answer.
C=Single Application Gateway: Application Gateway is a regional service. Putting it in one region makes that region a single point of failure and adds latency for users near the other region; it also has no edge caching.
D=Global Load Balancer: the global tier of Azure Load Balancer is a Layer 4 service. It can't run a WAF or cache content, because it never looks inside the HTTP request.
T: Global HTTP(S) app that needs WAF, edge caching and fast failover → Azure Front Door.
V: Azure Front Door, Azure Traffic Manager, Azure Application Gateway, Azure Load Balancer

@ AZ-305 D4 T4.4 applied comparison
S: A gaming company runs UDP game servers behind a regional Standard Load Balancer in three Azure regions. Players must connect to one static anycast IP address, reach the closest healthy region, keep their client IP visible to the servers, and fail over without relying on DNS. Which solution should you recommend?
A: Azure Front Door Premium, with each regional load balancer frontend added as an origin in one origin group
B: Azure Traffic Manager with Performance routing, with each regional load balancer's public IP as an endpoint
C: A global Azure Load Balancer, with each regional Standard Load Balancer added to its backend pool
D: Azure Application Gateway v2 in one region, with the game servers of all three regions in its backend pool
K: C
G: ## Global load balancing for non-HTTP traffic
Most global entry points in Azure are built for web traffic. When the protocol is plain TCP or UDP, the choice narrows to two services:
- **Traffic Manager** answers DNS queries with the address of a healthy endpoint. Clients then connect directly, so failover depends on DNS time-to-live and on clients that honour it.
- **Global (cross-region) Azure Load Balancer** is the global tier of Standard Load Balancer. Its frontend is a **static anycast IP** advertised across most Azure regions; its backend pool contains regional Standard Load Balancers.
## How the global tier behaves
- Traffic enters the closest participating Azure region and travels over the Microsoft backbone to the closest healthy regional load balancer (geo-proximity).
- Health probes check each regional load balancer every few seconds and take a failed region out of rotation, so failover is not tied to DNS.
- It is a pass-through Layer 4 service and preserves the client IP address.
W: Global Load Balancer: one static anycast IP, Layer 4 support for UDP, client IP preservation and probe-driven regional failover are exactly the global tier's features.
X: A=Front Door Premium: Front Door handles HTTP(S) only, so it can't carry UDP game traffic at all.
B=Traffic Manager: it works for any protocol, but it hands out DNS answers rather than one static anycast IP, and failover waits for DNS caches to expire.
D=Application Gateway: it is a regional proxy built for web traffic that can't carry UDP game sessions, and one regional gateway in front of three regions creates a single point of failure.
T: Non-HTTP traffic that needs a static anycast IP and instant cross-region failover → global (cross-region) Azure Load Balancer.
V: Azure Load Balancer, Azure Traffic Manager, Azure Front Door

@ AZ-305 D4 T4.4 applied use-case
S: A company publishes a TCP-based licensing service from Azure regions in Europe and North America. Regulations require clients located in Europe to always be directed to the European deployment and all other clients to the North American one. DNS-level routing is acceptable. Which solution should you recommend?
A: Traffic Manager with the Geographic routing method, mapping Europe to one endpoint and World to the other
B: Traffic Manager with the Performance routing method, so each client gets the endpoint with lowest latency
C: Azure Front Door Premium with one origin group per region and a rule that matches the client's country code
D: A global Azure Load Balancer with both regional load balancers in its backend pool and geo-proximity routing
K: A
G: ## Traffic Manager routing methods
Traffic Manager is a DNS-based global load balancer. Each profile uses one routing method:
- **Priority**: all traffic to a primary endpoint, with backups for failover.
- **Weighted**: split traffic by weights, for example for canary releases.
- **Performance**: the endpoint with the lowest network latency for the client.
- **Geographic**: the endpoint mapped to the geographic region the DNS query comes from.
- **Multivalue** and **Subnet**: return several healthy IPs, or map client IP ranges to endpoints.
## Why Geographic is deterministic
In Geographic routing each geographic region (World, a regional grouping such as Europe, a country, or a state) can be mapped to **only one** endpoint. Traffic Manager looks up the most specific match first, so a client in France always gets the endpoint mapped to Europe, and everything else falls through to the endpoint mapped to World. Microsoft names data sovereignty as a typical reason to use it.
W: Geographic routing: mapping Europe to the European endpoint and World to the North American one guarantees each client's DNS answer is decided by location, which satisfies the regulation for any protocol.
X: B=Performance routing: it picks the lowest-latency endpoint, which usually but not always matches location; a European client could be sent to North America if that measures faster.
C=Front Door rules: Front Door only proxies HTTP(S) traffic, so it can't front a raw TCP licensing protocol.
D=Global Load Balancer: its geo-proximity distribution sends clients to the closest healthy region and fails over to another region, so it gives no guarantee that European clients stay in Europe.
T: Route by the client's location for compliance → Traffic Manager Geographic routing; route by speed → Performance.
V: Azure Traffic Manager, Azure Front Door, Azure Load Balancer

@ AZ-305 D4 T4.4 applied use-case
S: A company hosts a web application on VMs in one Azure region. Requests for /api/* must go to one VM pool and all other paths to a second pool, TLS must be terminated in Azure, and common web attacks such as SQL injection must be blocked before they reach the VMs. Global distribution isn't needed. Which solution should you recommend?
A: A public Standard Load Balancer with two backend pools and a load-balancing rule on TCP port 443 for each pool
B: Azure Application Gateway WAF v2 with a path-based rule that sends /api/* to one backend pool and the rest to another
C: Azure Traffic Manager with two nested profiles, one per VM pool, and the Weighted routing method between them
D: Azure Firewall Premium with DNAT rules on port 443 that forward traffic to the private IPs of both VM pools
K: B
G: ## Regional Layer 7 load balancing
Application Gateway is Azure's regional application delivery controller. It terminates the client's TLS session, reads the HTTP request and decides where to send it:
- **Path-based routing** maps URL paths such as `/api/*` or `/images/*` to different backend pools.
- **TLS offload** keeps the public certificate in one place.
- The **WAF v2** tier adds a web application firewall with managed rule sets that block common attacks such as SQL injection and cross-site scripting.
## When not to add a global service
Front Door or Traffic Manager become useful when users or back ends span regions. For a single-region app, Application Gateway alone covers routing, TLS and WAF.
W: Application Gateway WAF v2: it is the regional Layer 7 service, so it can route by URL path, terminate TLS and run WAF rules in front of the VM pools.
X: A=Standard Load Balancer: it works at Layer 4 and never reads the URL, so it can't route `/api/*` separately, terminate TLS or inspect requests for attacks.
C=Traffic Manager: it only answers DNS queries for a host name. It can't see URL paths, and weighted DNS answers would send random users to the wrong pool.
D=Azure Firewall Premium: DNAT forwards ports without reading URL paths, and Microsoft's SKU comparison lists inbound TLS termination for Azure Firewall as done "using Azure Application Gateway".
T: Single-region web app needing URL path routing, TLS termination and WAF → Application Gateway WAF v2.
V: Azure Application Gateway, Azure Web Application Firewall, Azure Load Balancer, Azure Firewall

@ AZ-305 D4 T4.4 applied use-case
S: A company exposes an App Service web app globally through Azure Front Door. Security policy requires public network access to the app to be disabled entirely, so Front Door must reach the origin only over a private connection. Which solution should you recommend?
A: Front Door Standard, with the app's access restrictions allowing only the AzureFrontDoor.Backend service tag
B: Front Door Premium, with Private Link enabled on the origin and the private endpoint connection approved on the app
C: Front Door Standard, with a Microsoft.Web service endpoint enabled on the app's virtual network integration subnet
D: Front Door Premium, with the app placed behind an internal Standard Load Balancer used directly as the origin
K: B
G: ## Locking an origin to Front Door
There are two levels of protection for an origin behind Azure Front Door:
- **Public origin with filtering**: the app stays public, but its access restrictions allow only the `AzureFrontDoor.Backend` service tag (and usually check the `X-Azure-FDID` header for your profile). Traffic still arrives on a public endpoint.
- **Private origin with Private Link** (Front Door **Premium** only): Front Door creates a private endpoint to the origin from a Front Door managed network. The origin owner approves the connection, and traffic travels over the Microsoft backbone. The origin can then have public access disabled.
## Supported origins
Private Link origins include App Service (web apps and function apps), Storage, and internal load balancers exposed through a Private Link service.
W: Front Door Premium with Private Link: Premium can connect to App Service through a private endpoint that the app owner approves, so the app can turn public network access off and still serve Front Door.
X: A=Service tag restriction: this is a valid hardening step, but the app stays publicly reachable at the network level, which the policy forbids.
C=Service endpoint: service endpoints secure traffic from a virtual network subnet to a service. Front Door's edge doesn't run in your subnet, and virtual network integration only affects the app's outbound calls.
D=Internal load balancer as origin: Front Door can't reach a private frontend IP directly; an internal load balancer is usable only through a Private Link service, and App Service isn't placed behind one anyway.
T: Origin with public access disabled behind Front Door → Front Door Premium with Private Link to the origin.
V: Azure Front Door, Azure Private Link, Azure App Service

@ AZ-305 D4 T4.4 applied troubleshooting
S: VMs in an autoscaling scale set in one subnet call a partner API that allows only a short list of known source IP addresses. Under load the VMs run out of SNAT ports. The VMs must not accept inbound connections from the internet, and the team wants minimal configuration. Which solution should you recommend?
A: Assign a Standard public IP address to each scale set instance and give the partner the full list of IPs
B: Associate an Azure NAT Gateway with the subnet and attach a public IP prefix that is shared with the partner
C: Place the instances behind a public Standard Load Balancer and use its inbound rule's SNAT for outbound calls
D: Deploy Azure Firewall Premium in the subnet and enable TLS inspection so outbound sessions reuse fewer ports
K: B
G: ## What SNAT exhaustion is
A VM with a private IP reaches the internet through source network address translation (SNAT): its packets leave from a public IP, and each connection to the same destination needs its own source port on that IP. When many instances share few public IPs and open many connections, the ports run out and new connections fail.
## Azure NAT Gateway
NAT Gateway is a managed outbound-only NAT service that you attach to subnets:
- It **dynamically allocates SNAT ports** across all VMs in the subnet, which minimizes the risk of exhaustion.
- You attach public IP addresses or a **public IP prefix**, so outbound traffic always leaves from a known, contiguous range that a partner can allowlist.
- It **doesn't permit unsolicited inbound connections**; only responses to outbound flows come back.
- Setup is attaching it to a subnet and a public IP; no routes or per-VM changes are needed, and new scale set instances use it automatically.
W: NAT Gateway with a public IP prefix: it scales SNAT ports dynamically, gives one predictable range for the partner allowlist, blocks unsolicited inbound traffic and needs only a subnet association.
X: A=Public IP per instance: each instance becomes directly reachable from the internet, and the partner list changes every time the scale set scales out.
C=Load balancer SNAT: SNAT taken from a load-balancing rule uses a limited, pre-allocated number of ports per instance, which is exactly what tends to run out; it also exposes an inbound frontend.
D=Firewall with TLS inspection: TLS inspection decrypts traffic for threat detection; it doesn't reduce the number of connections, and a firewall is far more to run than outbound NAT alone.
T: Predictable outbound IPs plus SNAT scale for a whole subnet with no inbound exposure → Azure NAT Gateway.
V: Azure NAT Gateway, Azure Load Balancer, public IP prefix

@ AZ-305 D4 T4.4 advanced comparison
S: A payment processor sends all outbound internet traffic from its Azure workloads through one central firewall. Compliance requires decrypting outbound TLS so that payloads can be checked with signature-based intrusion detection and prevention, and filtering on the full URL path. Which solution should you recommend?
A: Azure Firewall Basic with threat intelligence in alert mode and application rules that use FQDN tags
B: Azure Firewall Standard with web categories, DNS proxy, and threat intelligence set to alert and deny
C: Azure Firewall Premium with TLS inspection, IDPS, and URL filtering configured in a firewall policy
D: Azure Application Gateway WAF v2 with custom rules that inspect the request body and the URL path
K: C
G: ## Azure Firewall SKUs
Azure Firewall is a managed, stateful network firewall usually placed in a hub virtual network. It comes in three SKUs:
- **Basic**: for small environments; FQDN filtering for HTTP/S and SQL, and threat intelligence in alert mode only.
- **Standard**: adds network-level FQDN filtering, web categories, DNS proxy, and threat intelligence that can alert and deny.
- **Premium**: adds **outbound TLS inspection** (a TLS forward proxy), a fully managed **IDPS** with signature-based detection, and **URL filtering** on the full path, including for decrypted HTTPS traffic.
## Why decryption matters
Without TLS inspection a firewall sees only the server name in the TLS handshake (SNI), not the path or the payload. Path filtering and payload signatures on HTTPS traffic therefore need Premium with TLS inspection, which uses an intermediate CA certificate kept in Key Vault.
W: Firewall Premium: it is the only Azure Firewall SKU with outbound TLS inspection, managed IDPS and full-path URL filtering, which are the three stated requirements; Microsoft positions it for sensitive workloads such as payment processing.
X: A=Firewall Basic: Basic filters by FQDN only and can only alert on threat intelligence; it has no TLS inspection or IDPS.
B=Firewall Standard: web categories and threat intelligence work on domains and IPs, but Standard can't decrypt TLS, run IDPS signatures on payloads or filter full URL paths.
D=Application Gateway WAF: a WAF protects inbound web traffic to your own apps. It isn't a forward proxy for the workloads' outbound internet traffic.
T: Outbound TLS inspection, IDPS and full URL filtering → Azure Firewall Premium.
V: Azure Firewall, Azure Firewall Manager, Azure Application Gateway

@ AZ-305 D4 T4.4 applied use-case
S: A company uses a hub-spoke topology built with virtual network peering. Traffic between spoke virtual networks must now be allowed, but all of it must pass through a central firewall for inspection and logging. Which TWO actions should you recommend? (Select TWO)
A: Deploy Azure Firewall in the hub virtual network so that it acts as the central router and inspection point
B: Add user-defined routes to each spoke subnet that send other spokes' prefixes to the firewall's private IP
C: Enable Allow gateway transit on every spoke peering so that traffic between spokes is forwarded by the hub
D: Peer every spoke directly with every other spoke so traffic between them takes the shortest network path
E: Enable service endpoints on each spoke subnet so that traffic between spokes stays on the Azure backbone
K: A,B
G: ## Peering is not transitive
In a hub-spoke design each spoke is peered with the hub. Virtual network peering is **nontransitive**: spoke 1 and spoke 2 can both talk to the hub but not to each other through it, because the hub doesn't route between peerings by itself.
## Three ways to connect spokes
- **Through a hub router**: put Azure Firewall (or another network virtual appliance) in the hub and add **user-defined routes (UDRs)** in the spokes that send the other spokes' address ranges to the firewall's private IP. Every flow is inspected and logged, at the cost of an extra hop and firewall processing charges.
- **Direct peering or Virtual Network Manager direct connectivity**: lowest latency, but traffic bypasses the hub's inspection.
- **VPN gateway transit**: possible but limits throughput and adds latency.
## Example
Spoke A is `10.1.0.0/16` and spoke B is `10.2.0.0/16`. A route table on spoke A's subnets sends `10.2.0.0/16` to the firewall's IP `10.0.1.4`, and spoke B's sends `10.1.0.0/16` to the same IP; a firewall network rule then allows the required ports.
W: A=Azure Firewall in the hub: the firewall becomes the router between spokes and the single place where the traffic is inspected and logged.
B=UDRs to the firewall: without routes that point at the firewall, spoke traffic has no path to the other spoke; the UDRs make every spoke-to-spoke flow go through the inspection point.
X: C=Gateway transit: this setting lets spokes use the hub's VPN or ExpressRoute gateway for on-premises connectivity; it doesn't make the hub route between spokes or inspect their traffic.
D=Direct spoke peering: it connects the spokes, but the traffic skips the hub firewall completely, which breaks the inspection requirement.
E=Service endpoints: they optimize traffic from a subnet to Azure PaaS services such as Storage or SQL Database; they have no effect on traffic between virtual networks.
T: Spoke-to-spoke traffic with central inspection → firewall in the hub plus UDRs in every spoke pointing to it.
V: Azure Firewall, Azure Virtual Network, user-defined routes

@ AZ-305 D4 T4.4 applied comparison
S: An on-premises application reaches Azure over ExpressRoute private peering and must read data from an Azure Storage account. The storage account must have public network access disabled, and the traffic must use a private IP address from the company's network space. Which solution should you recommend?
A: Enable a Microsoft.Storage service endpoint on the gateway subnet and add a virtual network rule to the account
B: Create a private endpoint for the storage account in a virtual network that is linked to the ExpressRoute circuit
C: Configure ExpressRoute Microsoft peering and allow the company's NAT public IP addresses in the storage firewall
D: Add the on-premises address ranges as IP network rules in the storage firewall and keep public access enabled
K: B
G: ## Service endpoints versus private endpoints
Both features keep traffic to Azure PaaS services on the Microsoft backbone, but they work differently:
- A **service endpoint** is a subnet setting. Traffic from that subnet reaches the service's **public** endpoint, carrying the virtual network's identity so a virtual network rule can allow it. Microsoft's documentation states that service endpoints **can't be used for traffic from on-premises** to Azure services.
- A **private endpoint** is a network interface with a **private IP** from your virtual network that maps to one resource (for example one storage account's blob service). Anything that can route to that IP can use it: the same virtual network, peered virtual networks, and **on-premises networks over VPN or ExpressRoute**. The resource can then have public network access disabled.
## DNS is part of the design
Clients must resolve the storage account's name to the private endpoint's IP, usually through a private DNS zone such as `privatelink.blob.core.windows.net` and DNS forwarding from on-premises.
W: Private endpoint: it gives the storage account a private IP that on-premises clients reach over ExpressRoute private peering, so public access can be turned off entirely.
X: A=Service endpoint: service endpoints only apply to traffic originating in Azure subnets; Microsoft states they can't secure traffic from on-premises, and the account would still use its public endpoint.
C=Microsoft peering with NAT IPs: this reaches the account's public endpoint from public NAT addresses, which needs public network access enabled and doesn't use a private IP.
D=IP network rules: allowing on-premises public ranges keeps the public endpoint open, which contradicts the requirement to disable public network access.
T: Private IP access to a PaaS resource from on-premises, with public access off → private endpoint (Private Link), not a service endpoint.
V: Azure Private Link, Azure Storage, Azure ExpressRoute

@ AZ-305 D4 T4.4 applied tradeoff
S: Workloads in one Azure subnet must connect to an Azure SQL Database logical server, and the server must reject connections from every other network. Clients may keep resolving the server's public DNS name, no on-premises access is needed, and the company wants no extra per-hour or per-GB networking charges. Which solution should you recommend?
A: Enable a Microsoft.Sql service endpoint on the subnet and add a virtual network rule to the server's firewall
B: Create a private endpoint for the server in the subnet and link a private DNS zone to the virtual network
C: Deploy Azure Firewall in the subnet and allow only the firewall's public IP address in the server firewall
D: Associate a NAT gateway with the subnet and allow its public IP prefix in the logical server's firewall rules
K: A
G: ## When a service endpoint is the better fit
Private endpoints are the most complete way to make PaaS traffic private, but they aren't always required. A **virtual network service endpoint**:
- is enabled per subnet for a service such as `Microsoft.Sql` or `Microsoft.Storage`;
- makes traffic from that subnet reach the service with the subnet's **private source IP** over the Azure backbone, so the service can recognize it;
- lets the service owner add a **virtual network rule** that allows only that subnet;
- keeps DNS unchanged: the service's name still resolves to its public IP;
- has **no extra charge**, according to Microsoft's pricing note.
Its limits: it works only for traffic from Azure subnets (not on-premises), and the resource keeps a public endpoint that simply refuses other sources.
## Trade-off in one line
Private endpoint = private IP, works from on-premises and peered networks, billed per hour and per GB. Service endpoint = subnet-level allow rule, free, Azure-only.
W: Service endpoint with a VNet rule: it restricts the server to the one subnet, keeps public DNS, needs no on-premises reach and adds no networking charge, which matches every stated requirement.
X: B=Private endpoint: it would work, but private endpoints are billed per hour and per GB processed and need private DNS changes, which the company explicitly wants to avoid.
C=Azure Firewall IP allow rule: the firewall adds hourly and data processing charges, and its public IP may be shared by other traffic, so the server isn't truly limited to one subnet.
D=NAT gateway IP rule: NAT Gateway also has hourly and data processing charges, and an IP allow rule identifies any traffic using that prefix rather than the subnet itself.
T: Restrict a PaaS resource to Azure subnets at no extra cost and without DNS changes → service endpoint; need private IPs or on-premises access → private endpoint.
V: Azure Virtual Network service endpoints, Azure SQL Database, Azure Private Link

@ AZ-305 D4 T4.4 applied use-case
S: Private endpoints in Azure have their records in Azure Private DNS zones linked to a hub virtual network. On-premises clients connected by ExpressRoute must resolve these names to the private IPs, and the company doesn't want to run DNS server VMs in Azure. Which TWO actions should you recommend? (Select TWO)
A: Deploy Azure DNS Private Resolver with an inbound endpoint in the hub virtual network linked to the zones
B: Create conditional forwarders on the on-premises DNS servers that point to the inbound endpoint's IP address
C: Create an outbound endpoint with a forwarding ruleset that sends on-premises queries to Azure Private DNS
D: Copy the private endpoint records into a public Azure DNS zone so that on-premises clients can resolve them
E: Add the private endpoint IP addresses to the hosts files of the domain controllers in the Azure hub network
K: A,B
G: ## Why on-premises can't see Azure Private DNS zones
An Azure Private DNS zone is answered only by Azure's internal resolver for virtual networks linked to the zone. On-premises DNS servers can't query that resolver directly.
## Azure DNS Private Resolver
DNS Private Resolver is a managed service deployed into a virtual network, so you don't run and patch DNS VMs:
- An **inbound endpoint** gets a private IP in the virtual network. On-premises DNS servers add a **conditional forwarder** for zones such as `privatelink.blob.core.windows.net` that points at this IP over ExpressRoute or VPN. The resolver answers from the Private DNS zones linked to its virtual network.
- An **outbound endpoint** with a **forwarding ruleset** handles the opposite direction: Azure resources resolving on-premises names.
Remember the direction: inbound = queries coming **into** Azure; outbound = queries leaving Azure.
W: A=Inbound endpoint: it exposes Azure's private DNS resolution on a private IP that on-premises servers can reach over ExpressRoute, without any DNS VMs.
B=Conditional forwarders: on-premises DNS must be told to send the privatelink zone queries to the inbound endpoint; without them, clients keep resolving the public IPs.
X: C=Outbound endpoint and ruleset: outbound endpoints forward queries from Azure to other DNS servers, the reverse of what is needed here.
D=Public DNS zone: publishing private IPs in public DNS exposes internal addressing on the internet and breaks the private DNS design for Azure clients.
E=Hosts files on Azure domain controllers: hosts files are static and must be updated by hand for every endpoint, and they still need DNS servers running on VMs, which the company wants to avoid.
T: On-premises resolution of Azure private DNS zones → DNS Private Resolver inbound endpoint plus on-premises conditional forwarders.
V: Azure DNS Private Resolver, Azure Private DNS, Azure Private Link

@ AZ-305 D4 T4.4 applied comparison
S: A company has more than 100 public IP addresses across several virtual networks in different subscriptions of one tenant. It wants access to the DDoS Rapid Response team during an attack and cost protection for resources that scale out because of a documented attack. Which solution should you recommend?
A: Rely on Azure DDoS infrastructure protection, which is on by default for every public IP at no extra cost
B: Enable Azure DDoS IP Protection on each public IP address that hosts an internet-facing workload
C: Create one Azure DDoS Network Protection plan and associate the virtual networks of each subscription with it
D: Put Azure Front Door with a WAF policy in front of each workload and add rate-limiting custom rules to it
K: C
G: ## Three levels of DDoS protection
- **DDoS infrastructure protection** is built in and free for every Azure service with a public IP. It needs no configuration but isn't tuned to your applications and gives you no reports or support.

T: PostgreSQL to Azure Database for PostgreSQL flexible server with minimal downtime → the built-in migration service in online mode.
V: Azure Database for PostgreSQL, Azure Database Migration Service

@ AZ-305 D4 T4.3 applied tradeoff
S: A media company must move 400 TB from on-premises NAS SMB shares to Azure Blob Storage. Its 200-Mbps internet link would need months for the full copy, and users keep changing files until the final cutover. Which TWO services should you recommend? (Select TWO)
A: Azure Data Box devices to ship the initial bulk copy of the data offline to the target storage account
B: Azure Storage Mover to synchronize the changes made after the bulk copy, right up to the cutover
C: Azure Data Box Gateway on-premises as the only tool, uploading the entire data set over the link
D: AzCopy sync jobs scheduled from one workstation as the only method, copying the full data set nightly
E: Azure Migrate server migration to replicate the NAS appliance to Azure as a virtual machine with disks
K: A,B
G: ## Online or offline transfer
The first design question is whether the network can move the data in time. At 200 Mbps, 400 TB takes far longer than a migration window allows, so the bulk copy should travel **offline**.
## Azure Data Box
Data Box is a rugged device that Microsoft ships to you. You copy data onto it over SMB or NFS, ship it back, and Microsoft uploads it into your storage account. Microsoft positions it for data sets larger than about 40 TB with little or no network connectivity. Current next-generation devices hold 120 TB or 525 TB of usable capacity; the older Data Box Heavy has been retired.
## Seeding plus delta sync
Microsoft's storage migration guide recommends **Data Box for seeding** followed by **Azure Storage Mover for delta sync** when you need to move a lot of data quickly and the source keeps changing:
1. Copy the bulk of the shares to Data Box and ship it.
2. After the upload, run Storage Mover jobs from an agent near the NAS to copy files changed since the snapshot.
3. At cutover, stop writes, run a final Storage Mover job, and switch users.
W: A=Data Box seeding: the devices move hundreds of terabytes without using the internet link, which removes the months-long online copy.
B=Storage Mover delta sync: it copies the files that changed after the snapshot from the SMB shares to Blob Storage, so the final cutover only moves a small delta.
X: C=Data Box Gateway alone: it is a virtual appliance that uploads data over the network, so it hits the same bandwidth limit and would still take months.
D=AzCopy from a workstation alone: AzCopy is suited to small and medium transfers; nightly full copies of 400 TB over a 200-Mbps link can't finish.
E=Azure Migrate server migration: Azure Migrate moves servers and VMs, not the contents of NAS file shares into Blob Storage.
T: Too much data for the link and data that keeps changing → Data Box for the bulk seed plus Storage Mover for delta sync.
V: Azure Data Box, Azure Storage Mover, Azure Blob Storage

@ AZ-305 D4 T4.3 applied comparison
S: A company is migrating 40 SMB file shares from NAS appliances in several countries to Azure file shares. It wants one Azure resource to plan and track every share's migration, to keep NTFS ACLs and timestamps, and to avoid writing its own copy scripts. Which solution should you recommend?
A: Azure Storage Mover with a migration project per workload and migration agents deployed near each NAS
B: AzCopy run from a scheduled task on one server per country, with a separate command for each file share
C: Azure File Sync with a cloud endpoint per share and the sync agent installed directly on each NAS device
D: Azure Data Box ordered once per country, with the shares copied to each device by using Robocopy scripts
K: A
G: ## Azure Storage Mover
Storage Mover is a fully managed migration service for files and folders. Its design suits large, multi-site migrations:
- **One storage mover resource** manages migrations of shares anywhere in the world.
- **Migration projects** group the shares of one workload; each job defines a source, a target and settings, and the portal shows progress and results per share.
- An **agent** deployed near each source share moves the data directly to Azure; the Azure resource only orchestrates.
- For SMB sources going to Azure file shares, it keeps the **same file fidelity** as Azure Files: folder structure, timestamps, ACLs and attributes.
Microsoft's storage migration guide recommends it for managed, automated migrations from NAS, typically above 1 TB or millions of files.
W: Storage Mover: one resource with per-workload projects gives central planning and tracking across countries, agents near each NAS do the copying, and SMB-to-Azure Files migration keeps ACLs and timestamps without custom scripts.
X: B=AzCopy per country: AzCopy can copy SMB data, but it means writing and running scripts per share with no central view of progress, which the company wants to avoid.
C=Azure File Sync on the NAS: the File Sync agent runs on Windows Server, so it can't be installed on NAS appliances.
D=Data Box per country: Data Box suits offline transfers when bandwidth is the problem; here the company asks for central tracking without scripts, and Robocopy runs are scripts.
T: Many SMB/NFS shares across sites, managed and tracked centrally with full fidelity → Azure Storage Mover.
V: Azure Storage Mover, Azure Files, AzCopy, Azure File Sync

@ AZ-305 D4 T4.3 applied comparison
S: A developer needs a one-off copy of about 300 GB of objects from an Amazon S3 bucket into an Azure Blob Storage container. The copy should run from a script with filters on object names, and the company doesn't want to deploy any new Azure resources, agents, or devices for it. Which tool should you recommend?
A: Azure Storage Mover with an S3 source endpoint, a migration project, and a job definition for the bucket
B: AzCopy, copying from the S3 bucket URL to the container so that the data moves service to service
C: Azure Data Box ordered for the copy, loaded from the S3 bucket and then shipped to an Azure datacenter
D: Azure Data Factory with a copy pipeline and a self-hosted integration runtime installed on a VM in AWS
K: B
G: ## Picking a transfer tool by scale
Microsoft's storage migration guide matches tools to the job:
- **AzCopy**: rapid, one-off or incremental transfers of small to medium size (typically under 1 TB per job), scripting needs such as filters, and sources including local file systems, other Azure storage, Amazon S3 and Google Cloud Storage.
- **Azure Storage Mover**: managed, tracked migrations at larger scale (typically above 1 TB or millions of files), from NAS shares or S3.
- **Azure Data Box**: offline transfer when the network can't carry the data in time.
## How AzCopy copies from S3
AzCopy authenticates to S3 with an access key and to Azure with Microsoft Entra ID or a SAS token. It uses the **Put Block From URL** API, so the data moves **directly between S3 and Azure Storage** and doesn't pass through the machine that runs the command.
W: AzCopy: a single command-line tool with name filters that copies S3 objects server-side into Blob Storage, needs no new Azure resource or agent, and fits a 300-GB one-off job.
X: A=Storage Mover: it is designed for larger, managed migrations and requires a storage mover resource and project, which the company doesn't want to create.
C=Data Box: shipping a device for 300 GB is slow and unnecessary, and it is still a device the company would have to order and handle.
D=Data Factory: a data factory and a self-hosted runtime VM are new resources to deploy and maintain for a one-off copy.
T: Small, scripted one-off copy from S3 or between storage accounts with nothing new to deploy → AzCopy.
V: AzCopy, Azure Blob Storage, Azure Storage Mover
