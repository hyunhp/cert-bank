@ AZ-305 D4 T4.2 applied use-case
S: A retailer is designing order processing. All messages for one customer order must be processed in the order they were sent, and a message that a client resubmits after a timeout must not be processed twice. Which messaging solution should you recommend?
A: Azure Storage queues with a visibility timeout long enough for each worker to finish one message
B: Azure Service Bus queues with message sessions keyed on the order ID and duplicate detection enabled
C: Azure Event Grid custom topics with an event subscription filtered on the order ID subject prefix
D: Azure Event Hubs with the order ID as partition key and a checkpoint stored for every consumer
K: B
G: ## Messages versus events
Learn separates two kinds of traffic. An **event** is a lightweight notice that something happened; the publisher does not care what consumers do with it. A **message** carries data that the consumer is expected to act on, with a contract between sender and receiver. Order processing is a message workload, which is what Azure Service Bus is built for.
## Ordering and duplicates in Service Bus
- **Message sessions**: messages with the same session ID (for example the order ID) are handed to one receiver at a time and delivered first in, first out. Different sessions are processed in parallel, so throughput still scales.
- **Duplicate detection**: Service Bus remembers the message IDs it received during a time window and drops a second message with the same ID. A client that resends after a timeout cannot create a second order.
- **Transactions and dead-lettering** complete the enterprise feature set.
## Example
Each message carries `SessionId = order-4711` and `MessageId = order-4711-line-3`. The resend of line 3 is discarded, and lines 1 to 5 of order 4711 arrive in sequence at one worker.
W: B=Service Bus sessions plus duplicate detection: sessions give guaranteed FIFO delivery per order while other orders run in parallel, and duplicate detection removes resubmitted messages based on the message ID, so both requirements are met by built-in features.
X: A=Storage queues: Learn lists no ordering guarantee and no duplicate detection for Storage queues; a visibility timeout only hides a message while one worker processes it.
C=Event Grid custom topics: Event Grid routes discrete events with at-least-once delivery, no ordering guarantee and no duplicate detection, so it fits reactions to state changes, not ordered transactions.
D=Event Hubs partition key: a partition keeps events in order, but Event Hubs has no duplicate detection and is designed for high-volume streams read by offset, not for settling individual business messages.
T: Ordered, de-duplicated business messages point to Service Bus: sessions for FIFO per key, duplicate detection on the message ID.
V: Azure Service Bus

@ AZ-305 D4 T4.2 applied use-case
S: When a PDF is uploaded to a storage account, an Azure Functions app must create a thumbnail and a Logic Apps workflow must notify reviewers, but only for files under the /contracts/ path. The design must be serverless with no polling. What should you recommend?
A: An Azure Service Bus topic that the storage account writes to directly, with one SQL filter per subscriber on the path
B: An Azure Event Hubs namespace that receives storage logs, read by both handlers through separate consumer groups
C: An Azure Event Grid system topic for the storage account with two event subscriptions filtered on the subject prefix
D: An Azure Storage queue that receives a message per upload, polled by the Functions app, which then calls Logic Apps
K: C
G: ## Event Grid for reactive, serverless designs
Azure Event Grid is a publish-subscribe service that **pushes** events to handlers. Azure services such as Blob Storage publish events (for example `Microsoft.Storage.BlobCreated`) to a **system topic** without any code. You add **event subscriptions**, one per handler, and each one can filter what it receives.
## Filtering
- **Event type filter**: only `BlobCreated`, not deletions.
- **Subject filters**: "begins with" `/blobServices/default/containers/docs/blobs/contracts/` and "ends with" `.pdf`.
- **Advanced filters** on data fields.
## Fan-out
Two subscriptions on the same topic each receive their own copy, so the Functions app and the Logic Apps workflow react independently, and nothing polls.
W: C=Event Grid system topic: Blob Storage publishes BlobCreated events natively, each event subscription pushes to its own handler (Functions and Logic Apps both are supported handlers), and subject filters keep only the contracts path, giving a serverless design with no polling.
X: A=Service Bus topic written by storage: a storage account cannot send to a Service Bus topic by itself; something would have to publish the messages, and Service Bus consumers receive by pulling rather than being pushed events by the storage service.
B=Event Hubs fed by storage logs: storage logs are a telemetry stream for analysis, not a per-blob trigger, and both handlers would have to read and filter the stream themselves.
D=Storage queue polled by Functions: someone still has to write a message per upload, the Functions app polls the queue, and the second handler is chained behind the first instead of reacting independently.
T: React to Azure resource state changes with Event Grid: system topic, one filtered event subscription per handler, push delivery.
V: Azure Event Grid, Azure Blob Storage, Azure Functions, Azure Logic Apps

@ AZ-305 D4 T4.2 applied comparison
S: A manufacturer will stream telemetry from 200,000 sensors, several million readings per second in total. A real-time dashboard and a separate anomaly-detection service must each read the full stream at their own pace. Which ingestion service should you recommend?
A: Azure Event Hubs, with each reader using its own consumer group and its own position in the partitions
B: Azure Service Bus Premium, with a topic and one subscription each for the dashboard and the anomaly service
C: Azure Event Grid custom topics, with an event subscription per reader that pushes each reading as it arrives
D: Azure Storage queues, with one queue per reader and the sensors writing every reading into both queues
K: A
G: ## Streams versus discrete messages
Learn's comparison puts the three brokers in different roles:
- **Event Hubs**: big-data streaming and ingestion, millions of events per second, ordering per partition, time-based retention.
- **Service Bus**: high-value enterprise messages with transactions and duplicate detection.
- **Event Grid**: reactive routing of discrete events.
## How Event Hubs serves several readers
An event hub is an append-only log split into **partitions**. Readers do not remove events; they track an **offset** per partition. A **consumer group** is an independent view of the stream, so the dashboard and the anomaly service each keep their own position and can fall behind or replay without affecting the other.
## Example
Sensors send with `partitionKey = sensorId`; the dashboard reads in consumer group `cg-dashboard`, the anomaly job in `cg-anomaly`. Both see every reading.
W: A=Event Hubs with consumer groups: it is built to ingest millions of events per second, and each consumer group keeps its own offset in the partitions, so the two services read the full stream independently.
X: B=Service Bus Premium topic: topics fan out business messages, but Service Bus is designed for reliable transactional messaging, not for ingesting a telemetry stream of millions of small readings per second.
C=Event Grid custom topics: Event Grid pushes discrete events to handlers; it has no retention or replay of a stream, so a slow reader cannot catch up from its own position.
D=Storage queues per reader: sensors would have to double every write, a dequeued message is gone for that queue, and queues are a work backlog, not a high-throughput replayable stream.
T: High-volume telemetry read by several independent consumers is an Event Hubs workload: partitions for scale, a consumer group per reader.
V: Azure Event Hubs

@ AZ-305 D4 T4.2 applied tradeoff
S: An image service puts work items on a queue. The backlog can grow beyond 100 GB during month-end, messages are under 10 KB, ordering does not matter, and auditors require a server-side log of every queue operation. Cost must stay low. Which queue should you recommend?
A: Azure Service Bus Standard queues with partitioning enabled so that the queue can grow to its largest size
B: Azure Storage queues in a general-purpose v2 storage account with storage diagnostic logging enabled
C: Azure Service Bus Premium queues with enough messaging units to keep the backlog within the queue quota
D: Azure Event Hubs Standard with long retention so that unprocessed work items remain available for workers
K: B
G: ## When Learn recommends Storage queues
Learn's "Storage queues and Service Bus queues compared" page lists the cases for each. Consider **Storage queues** when:
- the queue must hold **more than 80 GB** of messages (a Storage queue can grow to the capacity of the storage account);
- workers need to update a message to track progress;
- you need **server-side logs of all transactions** against the queue.
Consider **Service Bus queues** for FIFO through sessions, duplicate detection, transactions, messages over 64 KB, or role-based send/receive rights. A Service Bus queue's maximum size is set between 1 GB and 80 GB.
## Example
A month-end backlog of 120 GB of 8 KB messages fits in one Storage queue; storage logs record every put, get and delete for the auditors.
W: B=Storage queues: they can hold far more than 80 GB, the small messages fit the 64 KB limit, storage logging gives a server-side record of every operation, and the simple pay-per-use model keeps cost low because no broker features are needed.
X: A=Service Bus Standard partitioned: partitioning a Standard queue reaches at most 80 GB (16 partitions of up to 5 GB), so a backlog above 100 GB would be rejected.
C=Service Bus Premium queues: a Service Bus queue is still capped at 80 GB regardless of messaging units, and dedicated messaging units cost much more than a Storage queue for a feature-free backlog.
D=Event Hubs retention: Event Hubs keeps a time-based stream that readers track by offset; workers cannot delete or lock individual work items, so it is not a competing-consumer work queue.
T: Very large, simple backlogs with transaction logging fit Storage queues; Service Bus queues stop at 80 GB but add ordering, duplicate detection and transactions.
V: Azure Queue Storage, Azure Service Bus

@ AZ-305 D4 T4.2 applied use-case
S: An order service publishes each confirmed order once. Billing and shipping must receive every order, while the fraud team must receive only orders above 10,000 EUR. Adding a new consumer later must not require a change in the publisher. What should you recommend?
A: An Azure Service Bus queue that billing reads first and forwards each message to shipping and then to fraud
B: Three Azure Storage queues, with the order service checking the amount and writing to the right queues itself
C: An Azure Service Bus topic with a subscription per consumer and a SQL filter on the fraud subscription
D: An Azure Event Hubs event hub with a consumer group per team and the fraud team discarding small orders
K: C
G: ## Topics and subscriptions
A Service Bus **queue** delivers each message to one competing receiver. A **topic** is publish-subscribe: the sender writes once, and each **subscription** behaves like its own queue that gets a copy of every message it selects.
## Subscription rules
Each subscription has rules made of a **filter** (and an optional action):
- the default rule is the true filter, so the subscription gets every message;
- a **SQL filter** such as `amount > 10000` selects by message properties;
- a **correlation filter** matches exact property values and is cheaper to evaluate.
## Why this decouples the publisher
New consumers are added by creating a subscription with its own rule. The publisher only knows the topic name, so it never changes.
W: C=Service Bus topic with filtered subscriptions: billing and shipping keep the default rule and get every order, the fraud subscription uses a SQL filter on the amount property, and future consumers just add a subscription without touching the publisher.
X: A=Forwarding queue chain: a queue delivers each message to one receiver, so chaining billing to shipping to fraud couples the teams, adds latency and lets one failing consumer block the others.
B=Publisher-routed Storage queues: the order service would have to know every consumer and its routing rule, so each new consumer means a code change in the publisher.
D=Event Hubs consumer groups: every group reads the whole stream, so the fraud team would receive and discard all small orders, and Event Hubs lacks the per-message settlement and dead-lettering that business orders need.
T: One message to many consumers with per-consumer selection is a Service Bus topic with filtered subscriptions.
V: Azure Service Bus

@ AZ-305 D4 T4.2 applied use-case
S: A company runs dozens of Apache Kafka producer and consumer apps against a self-managed Kafka cluster. It wants to move streaming to Azure with no code changes in the apps and no Kafka brokers or ZooKeeper nodes to operate. What should you recommend?
A: A Kafka cluster on Azure Virtual Machine Scale Sets with managed disks and the cluster spread across zones
B: An Azure Service Bus Premium namespace, pointing the Kafka clients at its AMQP endpoint with JMS 2.0 enabled
C: An Azure Event Grid namespace, with the Kafka clients reconfigured to publish their records over MQTT topics
D: An Azure Event Hubs namespace, pointing the existing Kafka clients at its Kafka endpoint by changing their configuration
K: D
G: ## Event Hubs speaks Kafka
Azure Event Hubs has built-in Apache Kafka compatibility. An event hub plays the role of a **Kafka topic** and its partitions are Kafka partitions. Existing Kafka producers and consumers connect to the namespace's Kafka endpoint by changing their **configuration** (bootstrap server and authentication), not their code.
## What you no longer run
There are no brokers, ZooKeeper or KRaft controllers to patch and scale; capacity is bought as throughput units, processing units or dedicated capacity.
## Example
`bootstrap.servers=contoso-ns.servicebus.windows.net:9093` plus SASL settings is all a Kafka producer needs to start writing to an event hub named `orders`.
W: D=Event Hubs Kafka endpoint: Event Hubs accepts the Kafka protocol natively, so existing clients only change connection settings, and the platform is fully managed with no brokers to operate.
X: A=Kafka on scale sets: this keeps the apps unchanged but leaves the company running brokers, controllers, patching and scaling, which the requirement explicitly rules out.
B=Service Bus Premium AMQP/JMS: Service Bus speaks AMQP and supports JMS 2.0, not the Kafka protocol, so every Kafka app would need to be rewritten with a different client.
C=Event Grid MQTT: Event Grid supports MQTT and HTTP, so Kafka clients would need new protocol code, and it is a routing service rather than a replayable stream.
T: "Existing Kafka apps, no code change, no cluster to manage" points to Event Hubs and its Kafka endpoint.
V: Azure Event Hubs

@ AZ-305 D4 T4.2 applied tradeoff
S: An insurance platform sends policy documents of up to 40 MB as messages between services. It needs predictable latency unaffected by other tenants and access to the broker only through a private endpoint. Which messaging solution should you recommend?
A: Azure Service Bus Standard, with the large documents split into many 256 KB messages that the receiver joins
B: Azure Service Bus Premium, sized with dedicated messaging units and reached through Azure Private Link
C: Azure Storage queues, with a private endpoint on the storage account and messages Base64-encoded for safety
D: Azure Event Grid Basic custom topics, delivering each document by push to a private webhook on the receiver
K: B
G: ## Service Bus tiers
- **Standard**: shared, multi-tenant resources, messages up to 256 KB, variable throughput and latency.
- **Premium**: dedicated resources isolated at the CPU and memory level in **messaging units** (1, 2, 4, 8 or 16 per namespace), messages up to **100 MB**, virtual network integration and **Private Link**, geo-replication and JMS 2.0.
## When large payloads still belong in a store
Even with Premium, the Claim Check pattern (payload in Blob Storage, reference in the message) is often cheaper. Here, though, the stated needs are message size, isolation from other tenants and private access, which is exactly what Premium sells.
W: B=Service Bus Premium: it accepts messages up to 100 MB, dedicated messaging units give predictable latency independent of other tenants, and Premium namespaces support Private Link for private-only access.
X: A=Standard with 256 KB chunks: splitting and reassembling 40 MB documents adds custom code and failure modes, and Standard runs on shared resources, so latency can vary with other tenants' load.
C=Storage queues: a queue message is limited to 64 KB (about 48 KB of Base64 payload), so a 40 MB document cannot be sent as a message.
D=Event Grid push to webhook: Event Grid delivers small discrete event notifications, not multi-megabyte document payloads with brokered receive semantics.
T: Large messages, tenant isolation and Private Link are Service Bus Premium features; Standard is shared and limited to 256 KB.
V: Azure Service Bus

@ AZ-305 D4 T4.2 advanced use-case
S: A medical imaging app must hand off scans of 300 MB to 2 GB from an upload service to processing workers through Azure Service Bus. The broker must stay small and fast for routing. Which design should you recommend?
A: Send each scan in a Service Bus Premium message, because Premium raises the maximum message size for this purpose
B: Compress each scan with gzip in the uploader and send it in parts through a session so that workers rebuild it in order
C: Write each scan to Azure Blob Storage and send a Service Bus message with the blob reference and the scan metadata
D: Store each scan in Azure Cache for Redis and send the cache key, so that workers read the payload at memory speed
K: C
G: ## The Claim Check pattern
Messaging systems are optimized for many small messages. Large payloads cause broker resource pressure, slower serialization and higher cost, and may exceed size limits.
**Claim Check** separates the two concerns:
1. The sender stores the full payload in an external store (Blob Storage is the usual choice on Azure).
2. It sends a small message containing a **reference** (the claim check), such as the blob URL, plus routing metadata.
3. The receiver uses the reference to fetch the payload when it needs it.
## Practical points
- Give receivers access through managed identity or a short-lived SAS, not a public URL.
- Use a lifecycle policy or the receiver to delete payloads after processing.
- Event Grid can even raise the message for you when the blob is created.
W: C=Claim Check with Blob Storage: the multi-gigabyte scan lives in durable, cheap object storage and only a small reference message passes through Service Bus, so the broker stays fast and no size limit is hit.
X: A=Premium large messages: Premium supports messages up to 100 MB, which is far below scans of up to 2 GB, and pushing huge payloads through the broker is what the requirement wants to avoid.
B=Gzip chunks in a session: sessions can keep parts in order, but the full payload still crosses the broker and the reassembly code becomes a fragile custom protocol.
D=Redis as payload store: a cache is volatile memory sized for small hot items; holding many gigabyte scans there is costly and risks losing payloads on eviction.
T: Large payloads go to Blob Storage; the message carries only a reference (Claim Check pattern).
V: Azure Service Bus, Azure Blob Storage

@ AZ-305 D4 T4.2 applied use-case
S: A ticketing web app writes bookings straight to an Azure SQL database. During ticket releases, traffic spikes to 50 times normal for a few minutes, the database throttles, and users see errors. The business accepts bookings being confirmed a minute later. What should you recommend?
A: Scale the database to the largest service objective permanently so that it can absorb every release peak directly
B: Add an Azure Cache for Redis tier in front of the database and write each booking to the cache before the database
C: Put Azure Front Door in front of the web app and enable caching of the booking API responses at the edge locations
D: Have the web app place bookings on a Service Bus queue and let worker instances write them to the database at a steady rate
K: D
G: ## Queue-Based Load Leveling
When a service cannot handle sudden peaks, place a **queue** between the task that creates work and the service that does it. The producer posts messages as fast as users arrive; consumers take them at the rate the backend can sustain. The queue absorbs the burst.
## Benefits named on Learn
- Availability: the backend is not flooded and does not fail during peaks.
- Cost: you provision for the **average** load, not the peak.
- Scalability: consumers can scale out independently, within the limit the backend tolerates.
## Trade-off
Work becomes asynchronous. The user gets "booking received" immediately and the confirmation slightly later, which the business accepted here.
W: D=Queue-based load leveling: the queue buffers the burst, workers write at a rate the database can sustain, and because confirmation may be delayed, the asynchronous hand-off removes throttling errors without sizing for the peak.
X: A=Largest service objective permanently: paying for peak capacity all month for a few minutes of spikes is the cost problem the pattern avoids, and even the largest size may throttle at 50 times normal.
B=Redis before the database: a cache speeds up repeated reads; using it as a write buffer adds a second store to keep consistent and risks losing bookings on eviction.
C=Front Door caching: bookings are unique writes that must reach the database, so caching API responses at the edge does not reduce the write load at all.
T: To protect a backend from short write peaks when delay is acceptable, buffer the work in a queue and drain it at a steady rate.
V: Azure Service Bus, Azure SQL Database

@ AZ-305 D4 T4.2 applied troubleshooting
S: An Event Grid subscription pushes resource events to a webhook. During a two-day outage of the webhook, some events were dropped after the retries ended, and the security team could not investigate them. What should you add to the design?
A: A dead-letter location on the event subscription that writes undeliverable events to a blob container
B: Duplicate detection on the custom topic so that retried events are stored once and kept until delivered
C: A second event subscription to the same webhook so that each event is delivered twice in case one fails
D: Event Hubs Capture on the topic, so that all events are archived to Data Lake Storage before Event Grid sends them
K: A
G: ## Event Grid delivery and retry
Event Grid delivers events at least once and retries failed deliveries according to the subscription's **retry policy** (maximum attempts and event time-to-live). When the retries are exhausted, the event is **dropped** unless dead-lettering is configured.
## Dead-lettering
On the event subscription you set a **dead-letter location**: a blob container in a storage account. Event Grid writes the undeliverable events there, so they can be inspected and replayed later. A system-assigned or user-assigned managed identity with write access to the storage can be used for the dead-letter writes.
## Design tip
Pair dead-lettering with an alert on dead-lettered events, and make the handler idempotent because at-least-once delivery can send an event more than once.
W: A=Dead-letter to blob storage: Event Grid writes events it can no longer deliver to the configured container, so an outage longer than the retry policy no longer loses them and the team can investigate or replay them.
X: B=Duplicate detection: Event Grid has no duplicate detection; that is a Service Bus feature, and it removes repeats rather than keeping events that could not be delivered.
C=Second subscription to the same endpoint: both copies fail while the webhook is down, so both are dropped after retries end, and the handler now processes duplicates in normal times.
D=Event Hubs Capture: Capture archives an event hub's stream; it is not a feature of an Event Grid topic and does not hold Event Grid deliveries that failed.
T: Configure a dead-letter blob container on Event Grid subscriptions so events that exhaust retries are kept instead of dropped.
V: Azure Event Grid, Azure Blob Storage

@ AZ-305 D4 T4.2 advanced use-case
S: Clickstream events flow into Azure Event Hubs Standard. A real-time personalization service and a nightly fraud job must each read every event independently, and the fraud job must be able to reprocess the last five days after a failed run. Which two design choices should you recommend? (Select TWO)
A: Create a separate consumer group for the personalization service and for the fraud job
B: Set the event hub's retention period to at least five days, within the Standard tier limit of seven
C: Enable duplicate detection on the event hub so that reprocessed events are not counted twice
D: Create one event hub per reader and have the producers send every event to both event hubs
E: Configure Event Grid to forward each event from the hub to the fraud job as soon as it arrives
K: A,B
G: ## Reading a stream more than once
Event Hubs keeps events in partitions for a **retention period** and never deletes them when they are read. Readers track an **offset** per partition.
- A **consumer group** is an independent view of the stream: each group has its own offsets, so two applications read the same events without interfering.
- **Retention** decides how far back a reader can go. Learn gives up to 7 days in Standard and 90 days in Premium and Dedicated.
## Reprocessing
To rerun the last five days, the fraud job simply resets its offsets in its own consumer group to five days ago. The personalization service is unaffected.
W: A=Consumer group per reader: each application keeps its own position in the partitions, so both see every event and neither slows the other.
B=Retention of five days or more: events stay in the hub long enough for the fraud job to rewind its offsets and reprocess the last five days; seven days is the Standard maximum.
X: C=Duplicate detection: Event Hubs has no duplicate detection; replay idempotency is handled in the consumer, for example by event IDs in the fraud store.
D=One event hub per reader: doubling every send doubles cost and producer complexity, and consumer groups already give independent reads of one stream.
E=Event Grid forwarding: pushing events one by one gives the nightly job no way to rewind five days, and replay comes from Event Hubs retention, not from Event Grid.
T: Independent readers of one Event Hubs stream use separate consumer groups; how far they can replay is set by the retention period.
V: Azure Event Hubs

@ AZ-305 D4 T4.2 applied use-case
S: A bank runs APIs in its own datacenter and on another cloud. Regulations require API traffic to stay local to where each API runs, but the team wants one Azure API Management instance for policies, products and the developer portal. What should you recommend?
A: An API Management Standard v2 instance with virtual network integration and site-to-site VPN connections to every location
B: An API Management Consumption instance, with each backend exposed to it through Azure Relay hybrid connections
C: An API Management Premium instance with self-hosted gateways deployed in containers next to each set of APIs
D: An API Management Premium instance with additional regional gateways added in the Azure regions closest to each site
K: C
G: ## Managed gateway versus self-hosted gateway
Every API Management instance has a **management plane**, a **managed gateway** (data plane) in Azure and a **developer portal**. By default all API calls flow through Azure, which adds latency and can conflict with data-residency rules when backends live elsewhere.
The **self-hosted gateway** is a containerized version of the gateway that you run on Docker, Kubernetes or Azure Arc-enabled Kubernetes **next to your APIs**: on premises or in other clouds. Calls go client to local gateway to local backend; only configuration, heartbeats and telemetry go to Azure over outbound port 443.
## Tiers and resilience
- Available in the **Developer** (single node, non-production) and **Premium** tiers.
- Designed to "fail static": a running gateway keeps serving with its in-memory configuration if the Azure connection drops, and with configuration backup a stopped gateway can also start.
W: C=Premium with self-hosted gateways: the container gateways run beside each API so traffic stays local, while the single Azure instance still manages all APIs, policies, products and the developer portal.
X: A=Standard v2 with VNet integration: the managed gateway still runs in Azure, so every call travels from the datacenter to Azure and back, which breaks the stay-local rule.
B=Consumption with Azure Relay: the Consumption tier does not support self-hosted gateways, and relaying through Azure again routes every call through the cloud.
D=Premium extra regions: additional regional gateways still run inside Azure regions, not in the bank's datacenter or the other cloud, so traffic still leaves the site.
T: Hybrid or multicloud APIs that must keep traffic local use API Management self-hosted gateways (Developer or Premium tier).
V: Azure API Management

@ AZ-305 D4 T4.2 applied tradeoff
S: A travel company exposes its APIs to partners in North America, Europe and Asia. It wants one API Management instance with gateways in three Azure regions so that partners connect to a nearby gateway, and the gateway must survive a zone failure. Which tier should you recommend?
A: Premium (classic) tier, adding regional gateway locations and enabling availability zones
B: Standard v2 tier, scaled out to several units with zone redundancy turned on in each region
C: Premium v2 tier, with one instance per region and partners sent to the closest of the three
D: Developer tier, with self-hosted gateways deployed in containers in each of the three regions
K: A
G: ## API Management tier features that matter here
Learn's tier comparison table lists, among others:
- **Multi-region deployment**: Premium (classic) only. One instance gets additional gateway locations in other Azure regions, and the instance's management plane and configuration are shared.
- **Availability zones**: Premium and Premium v2.
- **Self-hosted gateway**: Developer and Premium.
- The **Developer** tier is for non-production and has no SLA.
## Reading the requirement
"One instance with gateways in three Azure regions" is the multi-region feature, and "survive a zone failure" adds availability zones. Only one tier offers both.
W: A=Premium (classic) multi-region with zones: it is the only tier that supports multi-region deployment of one instance, and it also supports availability zones, so partners hit a nearby gateway and each region tolerates a zone outage.

@ AZ-305 D4 T4.2 applied use-case
S: A retail site's product pages read the same catalog rows from Azure SQL Database thousands of times per minute, and the rows change a few times per day. Database CPU is high. The app must keep working, more slowly, if the cache is unavailable. Which approach should you recommend?

G: ## The Cache-Aside pattern
With **cache-aside** the application, not the cache, manages the data:
1. Look for the item in the cache.
2. On a miss, read it from the data store and put it in the cache with an **expiration**.
3. On an update, write to the data store and **invalidate** the cached item.
## Why it fits read-heavy data
Rows read thousands of times between changes are served from memory, so the database handles only misses. Because the data store remains the system of record, the app can fall back to it when the cache is down.
## Things to design
- Expiration that matches how often data changes.
- Cache-aside does not guarantee consistency; a short window of stale reads is possible.
W: D=Cache-aside with Azure Managed Redis: hot catalog rows are served from memory and loaded on demand, SQL stays the source of truth for fallback, and an expiration bounds how long a changed row can be stale.
X: A=Cosmos DB with strong consistency: replatforming the catalog is a large migration, and it does not add a cache; strong consistency also adds read cost rather than reducing it.
B=Redis as system of record: making a volatile cache the master risks data loss on eviction or failover, and the app could no longer work when the cache is unavailable.
C=SQL read replicas: replicas add read capacity but every request still runs a database query, which is more costly per read than an in-memory cache and leaves latency unchanged.
T: For read-heavy, rarely changing data, apply cache-aside: read the cache first, load from the store on a miss, expire and invalidate entries.

G: ## Deployment stacks
A **deployment stack** (`Microsoft.Resources/deploymentStacks`) manages the resources declared in a Bicep or ARM template as **one unit**, across resource groups when the stack is at subscription or management group scope.
## actionOnUnmanage
When a resource disappears from the template on update, or when the stack itself is deleted, this setting decides what happens:
- `detachAll`: resources and resource groups stay in Azure but are no longer managed.
- `deleteResources`: managed resources are deleted, resource groups are detached.
- `deleteAll`: managed resources **and** resource groups are deleted.
## Lifecycle example
Project ends: delete the stack with `deleteAll`, and all three resource groups and their contents are removed in one operation. A what-if preview can show what would be detached or deleted first.
W: C=Deployment stack with deleteAll: the stack tracks every resource it deployed across the three resource groups, deletes resources removed from the template on the next update, and deleting the stack removes the whole environment in one step.
X: A=Incremental mode: incremental deployments leave resources that are no longer in the template untouched, so removals and project cleanup remain manual.
B=Template spec plus Policy: a template spec only stores and versions the template; Azure Policy evaluates resource properties and has no effect that deletes resources missing from a template.
D=CanNotDelete locks: locks prevent deletion rather than performing it, and cleanup would still mean removing locks and resources group by group.
