@ AZ-305 D4 T4.2 applied use-case
S: Forty microservices on AKS each keep settings in their own config files, and some files contain database passwords. You need central, per-environment settings that change without redeploying, while secrets stay in Azure Key Vault. What should you recommend?
A: Azure Key Vault for both secrets and plain values, read by each service through the secrets API when it starts
B: Azure App Configuration for settings, with the passwords stored as encrypted key-values labeled per environment
C: Azure App Configuration for settings, using Key Vault references for secrets and managed identities for the services
D: Kubernetes ConfigMaps for settings and Kubernetes Secrets for passwords, maintained separately in each AKS namespace
K: C
G: ## App Configuration and Key Vault work together
**Azure App Configuration** centrally stores application settings and feature flags: hierarchical keys, **labels** per environment (`Dev`, `Prod`), dynamic refresh without redeploying or restarting, point-in-time replay and managed identity access. Learn states it **complements Key Vault**, which remains the store for secrets.
## Key Vault references
A **Key Vault reference** is a key in App Configuration whose value is only the **URI of a secret** in Key Vault, never the secret itself. The App Configuration provider recognizes it and fetches the value from Key Vault, so the app needs access to **both** stores (for example a managed identity with App Configuration Data Reader and Key Vault Secrets User).
## Example
`Orders:Db:Password` with label `Prod` points to `https://kv-prod.vault.azure.net/secrets/orders-db`; the app reads it like any other setting.
W: App Configuration with Key Vault references: settings are central and per environment through labels, change without redeploying, and secrets stay in Key Vault because App Configuration holds only references resolved with the services' managed identities.
X: A=Key Vault for everything: Key Vault is designed for secrets, keys and certificates, not for hierarchical app settings with labels, feature flags and dynamic refresh across many services.
B=Passwords as App Configuration values: storing secrets as key-values moves them out of Key Vault, which contradicts the requirement; App Configuration is meant to reference them.
D=ConfigMaps and Kubernetes Secrets: they are copied per namespace and cluster, so settings are not central, and the passwords would leave Key Vault.
T: Central app settings belong in App Configuration; secrets stay in Key Vault and are surfaced through Key Vault references.
V: Azure App Configuration, Azure Key Vault, Azure Kubernetes Service

@ AZ-305 D4 T4.3 advanced use-case
S: Azure Migrate has discovered 300 servers, but no one knows which servers make up each application. The team wants to move interdependent servers together in waves without installing agents. Which TWO actions should you recommend? (Select TWO)
A: Run an assessment of the 300 servers with as-is sizing, then migrate the servers in alphabetical order
B: Enable Azure Site Recovery replication for the servers so its recovery plans reveal which ones are related
C: Enable agentless dependency analysis on the discovered servers to capture their TCP connections over time
D: Onboard the servers to agent-based dependency analysis in a Log Analytics workspace using Service Map
E: Review the dependency map, then group the interdependent servers and assess each group as one application
K: C,E
G: ## Why dependencies matter
Servers rarely work alone: a web server calls an app server that calls a database. Migrating one without the others can cause outages after cutover. Azure Migrate's **dependency analysis** lets you review network dependencies, group interdependent servers into applications and find servers that must move together.
## Two options, one recommended
- **Agentless dependency analysis**: generally available for VMware VMs, Hyper-V VMs, physical servers and servers in other clouds. The appliance polls TCP connection data (processes, applications, destination ports) without agents, and you view it as a map or export it as CSV. Learn calls it the recommended approach.
- **Agent-based analysis**: uses Service Map with agents on each server. It exists only in the classic view, which is scheduled for deprecation, and new servers can no longer be onboarded.
## From map to waves
After the dependency data is collected, create groups (or application assessments) of the servers that talk to each other, assess them together and plan each group as a migration wave.
W: C=Agentless dependency analysis: it captures each server's TCP connections through the appliance with no agents, which is what reveals the hidden application boundaries.
E=Group and assess as applications: grouping the servers the map shows as interdependent turns raw connection data into application-sized migration waves that move together.
X: A=As-is assessment in alphabetical order: sizing tells you which Azure VMs to buy, not which servers depend on each other, so alphabetical waves would split applications apart.
B=Site Recovery recovery plans: recovery plans group servers that you already know belong together. Replication does not discover network dependencies.
D=Agent-based Service Map: it needs agents on each server, which the team ruled out, and Learn says new servers can no longer be onboarded to agent-based analysis.
T: To find which servers must migrate together, enable agentless dependency analysis and build groups or application assessments from the dependency map.
V: Azure Migrate

@ AZ-305 D3 T3.2 applied troubleshooting
S: An architect proposes deploying an app's VMs and databases only into the primary region of an Azure region pair, saying the pairing alone will fail the workload over to the paired region in a regional outage. What should you tell the architect?
A: The proposal works for PaaS services, because Azure fails each PaaS service over to its paired region by itself.
B: Pairing triggers failover once the workload is tagged as critical, so tagging the resources is the missing step.
C: The proposal works for VMs, because Azure Site Recovery is switched on for VMs placed in a paired region.
D: Pairing doesn't add high availability or failover; the team must design replication and failover for each component.
K: D
G: ## What region pairs do and don't do
Some Azure regions are paired with another region in the same geography. Pairing gives platform-level benefits:
- **Recovery sequence**: in a geography-wide outage one region of each pair is prioritized for recovery.
- **Sequential updating**: Azure tries to stagger planned updates across the two regions of a pair.
- Some services use the pair by default for geo-replication, such as geo-redundant storage.
Microsoft states that deploying resources into a paired region **doesn't** automatically make them more resilient or provide automatic high availability, disaster recovery or failover. You plan your own HA and DR, whether or not you use pairs.
## Nonpaired regions
Many newer regions are nonpaired and rely on availability zones; many services replicate between any regions you choose, so a pair is not required for a multi-region design.
W: Plan your own failover: a region pair only influences recovery order, update sequencing and some default replication targets; the workload fails over only if the team configures replication and failover for its VMs, databases and other components.
X: A=PaaS fails over by itself: PaaS services need their own geo-features (for example SQL failover groups or geo-redundant storage); pairing alone doesn't fail them over.
B=Tag-based failover: tags are metadata for organization and cost; they do not trigger failover.
C=Site Recovery switched on: Site Recovery must be enabled and configured per VM; it is not switched on by placing VMs in a paired region.
T: Region pairs don't give automatic failover; design replication and failover for every component, paired or not.
V: Azure regions

@ AZ-305 D3 T3.2 applied tradeoff
S: A line-of-business app needs a second region for regional outages. It can tolerate a short recovery period, the budget rules out running full capacity twice, and the team wants the fastest recovery among active-passive designs. Which approach should you recommend?
A: A warm spare secondary region that runs minimum-sized compute and data without load and is scaled up after failover.
B: A redeploy-on-demand design that rebuilds the resources in a secondary region from templates when an outage begins.
C: An active-active overprovisioned design in which each region is sized to carry the full load of both regions at once.
D: A cold spare secondary region whose full-size compute is deployed but stopped, and started when a failover begins.
K: A
G: ## Active-passive options
Active-passive designs keep one region serving all traffic and another ready to take over.
- **Warm spare**: the secondary runs the smallest possible compute and data sizing, with no load, and is scaled up after failover. Microsoft lists it as the **shortest recovery time** among active-passive designs, with the **highest operating cost** among them.
- **Cold spare**: the secondary is sized for full load but its compute is **stopped**; it must be started before failover. Lower cost, longer recovery.
- **Redeploy on demand**: nothing runs in the secondary until needed, so recovery includes deployment time and depends on capacity being available.
## Active-active
All regions serve traffic; overprovisioned active-active means paying for spare full capacity in every region all the time.
W: Warm spare: it avoids paying for a second full-size environment yet recovers fastest of the passive designs, because services are already running and only need scaling.
X: B=Redeploy on demand: deploying everything during the outage gives the longest recovery and risks capacity shortages in the secondary region.
C=Active-active overprovisioned: each region is permanently sized for the full load, which is exactly the double capacity the budget forbids.
D=Cold spare: cheaper to run, but starting stopped compute lengthens recovery, so it's not the fastest passive option.
T: Among active-passive designs, warm spare recovers fastest at higher standby cost; cold spare is cheaper but slower.
V: Azure Well-Architected Framework

@ AZ-305 D1 T1.1 applied use-case
S: Every Saturday from 01:00 to 05:00, a subscription's VMs are patched. Alerts must still be recorded during the window, but no one should be emailed or paged. You need the simplest solution to maintain. What should you recommend?
A: Change the metric alert rules to stateless so that each alert fires once and then stays silent until 05:00
B: An Azure Automation runbook that disables the alert rules at 01:00 and re-enables them at 05:00 each Saturday
C: Remove the action groups from the alert rules and ask on-call staff to check the Alerts page for new alerts
D: An alert processing rule scoped to the subscription that suppresses action groups on a recurring weekly schedule
K: D
G: ## Alert processing rules
An **alert processing rule** modifies alerts as they fire, without changing the alert rules themselves. It can:
- **Suppress** action groups (notifications and automation) or **add** action groups.
- Apply to a **scope** (subscription, resource group, resources) with **filters** (for example severity or alert rule name).
- Run **always, once in a time window, or on a recurring schedule** (daily, weekly).
Suppression still lets the alert fire and appear on the Alerts page; only the actions are not triggered.
## Example
Scope: the patching subscription. Action: remove all action groups. Schedule: weekly, Saturday 01:00 to 05:00. Every alert rule in the subscription follows it, including rules added later.
W: Scheduled alert processing rule: one rule suppresses notifications for the whole subscription on a recurring weekly schedule, and the alerts are still fired and recorded.
X: A=Stateless alert rules: stateless rules fire each time the condition is met, so they notify more often, not less, and they have no time-window setting.
B=Disable rules with a runbook: disabled rules don't evaluate, so no alerts are recorded during the window, and the runbook is extra code to maintain.
C=Remove action groups: this silences alerts all the time, not just during patching, and depends on people checking a page manually.
T: Silence notifications for a planned window, while still recording alerts, with an alert processing rule on a schedule.
V: Azure Monitor alert processing rules, action groups

@ AZ-305 D2 T2.1 advanced use-case
S: A multitenant SaaS application on PostgreSQL has outgrown the largest single Azure Database for PostgreSQL flexible server. The company wants to stay on managed PostgreSQL and spread tenant data across several nodes, adding nodes as it grows. What should you recommend?
A: Azure SQL Database Hyperscale, which keeps PostgreSQL wire compatibility while growing storage up to 128 TB
B: Elastic clusters, Azure's managed Citus option, which shards tables or schemas across multiple database servers
C: Several read replicas of the flexible server, with each tenant's writes sent to the replica that is closest to its users
D: A single flexible server on the Memory Optimized tier with zone-redundant high availability to add a second node
K: B
G: ## Scaling PostgreSQL out
A single flexible server scales up (more vCores, memory, storage) until the largest size. To go beyond one machine you need **horizontal sharding**.
## Elastic clusters
**Elastic clusters** are a managed offering of the open-source **Citus** extension in Azure Database for PostgreSQL flexible server. Several flexible server nodes form one cluster in a shared-nothing architecture:
- **Row-based sharding**: a distributed table is split by a distribution column such as `tenant_id`.
- **Schema-based sharding**: each tenant's schema lives on one node, a natural fit for multitenant apps.
You scale out by **adding nodes and rebalancing**, which is an online operation. Queries are routed to one node or parallelized across nodes based on Citus metadata.
W: Elastic clusters: they keep the app on managed PostgreSQL while distributing tenant data across nodes by row or schema sharding, and new nodes can be added with online rebalancing as the tenant count grows.
X: A=SQL Database Hyperscale: Hyperscale is the SQL Server engine; it doesn't speak the PostgreSQL protocol, so the application would need a full database migration and rewrite.
C=Read replicas: replicas are read-only copies that receive changes asynchronously; they can't accept tenants' writes, so they don't spread the write workload or the data.
D=HA on one server: the HA standby is a failover copy that doesn't serve traffic, so the workload still runs on one node and the size limit remains.
T: To scale PostgreSQL beyond one server on Azure, shard it with elastic clusters (managed Citus) in Azure Database for PostgreSQL flexible server.
V: Azure Database for PostgreSQL flexible server

@ AZ-305 D2 T2.2 applied use-case
S: An IoT platform writes device readings to an Azure Cosmos DB container. Readings are only needed for 30 days, and the design must remove older items automatically without writing or scheduling any cleanup code. What should you recommend?
A: A change feed processor in Azure Functions that deletes each item 30 days after it was written
B: A container default time to live of -1, so that each item expires on its own schedule
C: An Azure Storage lifecycle management policy that deletes items when they are older than 30 days
D: A container default time to live of 2,592,000 seconds, counted from each item's last write
K: D
G: ## Time to live (TTL) in Cosmos DB
TTL makes Cosmos DB delete items automatically after a period counted **from the last time the item was modified**. The value is in seconds.
- Set `DefaultTimeToLive` on the container; items can override it with their own `ttl` property.
- `DefaultTimeToLive = -1` means "infinity": items do not expire unless they set their own `ttl`.
- Expired items disappear from query results immediately; physical deletion runs as a background task. On provisioned accounts it uses leftover RUs not consumed by user requests; on serverless accounts it is charged like delete operations.
## Example
30 days x 86,400 seconds = `2592000`. With that default, a reading written on 1 May disappears from queries on 31 May with no client delete calls.
W: Default TTL of 2,592,000 seconds: Cosmos DB expires each item 30 days after its last write and deletes it in the background, so no cleanup code or schedule is needed.
X: A=Change feed processor with deletes: it would work, but it is custom code to write, run and pay for, which the requirement rules out, and each delete consumes RUs.
B=Default TTL of -1: -1 means items do not expire by default; only items with their own `ttl` value would be removed, so old readings stay.
C=Storage lifecycle management policy: lifecycle policies act on blobs in Azure Storage accounts; they cannot see or delete items in a Cosmos DB container.
T: Automatic expiry of Cosmos DB items: set the container's default TTL in seconds (-1 means never expire unless an item sets its own).
V: Azure Cosmos DB
