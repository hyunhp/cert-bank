@ AZ-305 D1 T1.2 applied use-case
S: A company syncs its on-premises Active Directory users to Microsoft Entra ID. Security requires that cloud sign-ins be refused immediately when an account is locked out, disabled or outside its permitted logon hours in Active Directory. The company does not want to run federation servers. Which sign-in method should you recommend?
A: Password hash synchronization with seamless single sign-on, so that the cloud validates passwords against the synced hashes
B: Pass-through Authentication, with lightweight agents that validate each password against on-premises domain controllers
C: Federation with Active Directory Federation Services, so that every sign-in is redirected to an on-premises farm of servers
D: Microsoft Entra Cloud Sync with password writeback, so that account state changes are written back to the cloud directory
K: B
G: ## Three ways to sign in hybrid users
Microsoft Entra ID offers three sign-in methods for users synced from Active Directory:
- **Password hash synchronization (PHS)**: a hash of the password hash is synced; Microsoft Entra ID validates sign-ins in the cloud. Simplest, and it keeps working if on-premises fails.
- **Pass-through Authentication (PTA)**: lightweight agents on-premises validate each password directly against domain controllers.
- **Federation (for example AD FS)**: sign-ins are redirected to an on-premises identity provider farm.
## Where the account policy is enforced
With PTA the on-premises account policy is checked at sign-in: access is denied when the account is disabled, locked out, its password expired, or the sign-in is outside the allowed logon hours. With PHS, account state changes only reach the cloud at the next sync, and Learn notes that locked-out and password-expired states are not synced at all.
## Example
An employee is locked out on-premises at 09:00 after failed attempts. With PTA, a cloud sign-in at 09:01 is refused because the agent asks a domain controller. With PHS, the cloud would still accept the correct password.
W: Pass-through Authentication: the agents validate every sign-in against Active Directory, so lockout, disabled state, expiry and logon hours are enforced at the moment of sign-in, without any federation servers.
X: A=Password hash synchronization: cloud validation does not enforce on-premises account state immediately; lockout and password-expired states are not synced, so the requirement fails.
C=AD FS federation: it does enforce on-premises policy, but it needs a federation server farm, which the company explicitly does not want to run.
D=Cloud Sync with writeback: Cloud Sync is a synchronization engine, not a sign-in method, and writeback sends changes from the cloud to Active Directory rather than enforcing lockout at sign-in.
T: When on-premises account policies (lockout, logon hours) must apply at every cloud sign-in without federation, choose Pass-through Authentication.
V: Microsoft Entra ID, Microsoft Entra Connect, Pass-through Authentication

@ AZ-305 D1 T1.2 applied tradeoff
S: A retailer is moving its users to Microsoft 365 and wants the least on-premises infrastructure for cloud sign-in. Users must keep signing in to cloud apps if the datacenter goes offline after a ransomware attack, and the company wants the leaked credentials report from Microsoft Entra ID Protection. Which sign-in method should you recommend?
A: Pass-through Authentication with three agents spread across separate on-premises servers for high availability
B: Federation with AD FS deployed on a pair of virtual machines in Azure in front of the on-premises domain controllers
C: Password hash synchronization, where Microsoft Entra ID validates sign-ins in the cloud against synced password hashes
D: Microsoft Entra Domain Services with a forest trust to the on-premises domain so that Azure handles the authentication
K: C
G: ## Cloud authentication without on-premises dependency
With **password hash synchronization (PHS)** Microsoft Entra Connect (or Cloud Sync) syncs a hash of each user's password hash. The sign-in itself happens entirely in Microsoft Entra ID, so it scales with the cloud service and does not depend on on-premises servers being online.
## Why Learn recommends PHS in every design
- **On-premises outage survival**: organizations hit by ransomware that had PHS could keep users working in cloud apps while the datacenter was rebuilt.
- **Leaked credentials**: Microsoft Entra ID Protection needs PHS to produce the leaked credentials report, whatever the main sign-in method is (the report itself needs Microsoft Entra ID P2).
- **Effort**: no extra agents or federation servers for sign-in.
## Example
A domain controller farm is encrypted by ransomware. PTA agents and AD FS servers can no longer validate passwords, but users with PHS still sign in to Exchange Online and Teams.
W: Password hash synchronization: validation happens in Microsoft Entra ID, so sign-in survives an on-premises outage, it needs no sign-in servers on-premises, and it is the prerequisite for the leaked credentials report.
X: A=Pass-through Authentication: every sign-in still needs a domain controller reached through on-premises agents, so a datacenter outage stops sign-ins, and leaked credentials detection would still require PHS.
B=AD FS in Azure: federation adds servers to run and still depends on domain controllers for validation, the opposite of least infrastructure.
D=Entra Domain Services with a trust: a managed domain serves LDAP and Kerberos for Azure workloads; it is not a sign-in method for Microsoft 365 cloud apps.
T: Password hash synchronization gives the simplest, outage-resilient cloud sign-in and is required for leaked credentials detection.
V: Microsoft Entra ID, Microsoft Entra ID Protection, password hash synchronization

@ AZ-305 D1 T1.2 advanced tradeoff
S: A bank chose Pass-through Authentication so that on-premises account policies apply to cloud sign-ins. The architecture review asks for resilience against agent failures and an option to keep users signing in during a major on-premises outage. Which TWO design elements should you add? (Select TWO)
A: Install Pass-through Authentication agents on two more servers inside the internal network, for three agents in total
B: Install additional Pass-through Authentication agents in the perimeter network so they can be reached from the internet
C: Enable password hash synchronization as well, so that the sign-in method can be switched to it if the agents fail
D: Add a third-party on-premises MFA server through federation so that the agents can hand off strong authentication
E: Deploy Microsoft Entra Domain Services so that cloud sign-ins fall back to the managed domain when agents are offline
K: A,C
G: ## How Pass-through Authentication stays available
PTA depends on lightweight agents that need outbound internet access and direct access to domain controllers. Learn recommends **three agents in total** (the first on the Microsoft Entra Connect server plus two more), so one agent can fail while another is down for maintenance. Agents in a perimeter network are **not supported**, because they need unconstrained access to domain controllers.
## A backup for a full outage
Enabling **password hash synchronization** alongside PTA gives a backup sign-in method if the agents cannot validate credentials during a major on-premises failure. The failover is **not automatic**: an administrator switches the sign-in method in Microsoft Entra Connect. PHS also unlocks leaked credentials detection.
## MFA with PTA
Organizations using PTA must use Microsoft Entra multifactor authentication or Conditional Access custom controls; third-party or on-premises MFA that relies on federation is not possible.
W: A=Three internal agents: Learn recommends two extra agents beside the first, so authentication requests keep flowing when one agent fails and another is in maintenance.
C=Password hash sync as backup: with hashes already in the cloud, administrators can switch sign-in to PHS when the on-premises environment cannot validate passwords.
X: B=Agents in the perimeter network: this placement is explicitly not supported, because agents need unconstrained network access to domain controllers and use only outbound connections anyway.
D=Federated third-party MFA: PTA cannot use third-party or on-premises MFA that relies on federation, and MFA does not improve availability of password validation.
E=Domain Services fallback: a managed domain does not act as a sign-in backend for Microsoft Entra ID cloud sign-ins, so it adds nothing when agents are offline.
T: Make PTA resilient with three internal agents and keep password hash sync enabled as a manual fallback.
V: Microsoft Entra Connect, Pass-through Authentication, password hash synchronization

@ AZ-305 D1 T1.2 applied use-case
S: A company acquired three firms, each with its own Active Directory forest. The forests have no trusts and no network connectivity to each other. All users must be synced into one Microsoft Entra tenant quickly, with lightweight agents that update themselves and fail over automatically. Which solution should you recommend?
A: One Microsoft Entra Connect Sync server in the head office with a connector configured for each of the acquired forests
B: Microsoft Entra Cloud Sync, with provisioning agents installed in each forest and the configuration managed in the cloud
C: A separate Microsoft Entra tenant for each acquired firm, linked afterwards with B2B invitations for every user
D: Microsoft Entra Domain Services with forest trusts to each acquired forest so that it can synchronize their users
K: B
G: ## Two sync engines
- **Microsoft Entra Connect Sync**: a full sync server installed on-premises. It must reach every connected forest from that server.
- **Microsoft Entra Cloud Sync**: orchestration runs in Microsoft Entra ID; you install **lightweight provisioning agents** that need only outbound connections and update automatically.
## Disconnected forests
Learn lists **disconnected forest synchronization** as a key Cloud Sync capability: it natively handles multiple Active Directory forests that have no connectivity between them, a common mergers-and-acquisitions case. Several active agents provide **automatic failover** without configuration changes.
## Example
Each acquired firm installs two provisioning agents on its own servers. Each forest then syncs to the head-office tenant without opening a network path between forests.
W: Cloud Sync: its agents sit inside each forest and talk only outbound to the cloud, so disconnected forests sync into one tenant, with self-updating agents and multi-agent failover.
X: A=Single Connect Sync server: one server must reach every forest, which the lack of connectivity between the forests prevents, and it is a heavy server rather than lightweight agents.
C=Separate tenants with B2B: this leaves the users outside the single tenant the company wants and adds per-user invitations instead of synchronizing identities.
D=Domain Services with trusts: a managed domain syncs one way from Microsoft Entra ID; it is not a tool for syncing Active Directory forests into a tenant.
T: For several disconnected Active Directory forests and a light footprint, choose Microsoft Entra Cloud Sync.
V: Microsoft Entra Cloud Sync, Microsoft Entra Connect Sync

@ AZ-305 D1 T1.2 applied use-case
S: An app runs on 20 identical VMs in a scale set and on an App Service web app, and all of them need the same read access to two storage accounts. Identity creation needs an approval process, and the role assignments must exist before the compute is deployed. Which identity design should you recommend?
A: Enable a system-assigned managed identity on every VM and on the web app, and add each identity to a shared security group
B: Register one application in Microsoft Entra ID and store its client secret in Azure Key Vault for each instance to retrieve
C: Create one user-assigned managed identity, grant it the storage roles in advance, and attach it to the scale set and web app
D: Enable a system-assigned managed identity on the scale set only, and let the web app call the VMs to reach the storage accounts
K: C
G: ## System-assigned versus user-assigned
- **System-assigned**: created with the resource, deleted with it, and usable by that one resource only.
- **User-assigned**: a standalone Azure resource with its own life cycle that can be attached to **many resources, even of different types**.
## When Learn recommends user-assigned
- **Replicated resources** that need the same permissions: one identity, fewer role assignments.
- **Compliance**: if identity creation needs approval, one shared identity means fewer approvals.
- **Access needed before deployment**: role assignments can be created in advance; a system-assigned identity does not exist until the resource does.
- **Rapid creation**: many system-assigned identities at once can hit Microsoft Entra object-creation limits.
## Example
Four VMs reading two storage accounts need eight role assignments with system-assigned identities, but only two with one shared user-assigned identity.
W: User-assigned identity: one pre-created identity with two role assignments serves the VMs and the web app, needs a single approval, and exists before deployment.
X: A=System-assigned plus group: each resource creates a new identity on deployment, so approvals multiply and the identities cannot be granted access before the resources exist.
B=App registration with secret: it reintroduces a credential that must be stored, rotated and protected, which managed identities exist to avoid.
D=Proxy through the VMs: routing storage access through the VMs adds a dependency and does not give the web app its own Azure-managed identity.
T: Shared, pre-approved access for many resources points to one user-assigned managed identity.
V: Managed identities for Azure resources, Azure RBAC

@ AZ-305 D1 T1.2 applied tradeoff
S: Each of 12 Azure Functions apps processes data for a different customer and needs its own permissions. Auditors want logs to show exactly which app performed each action, and permissions must disappear automatically when an app is deleted. Which identity design should you recommend?
A: A system-assigned managed identity on each function app, with role assignments scoped to that customer's resources only
B: One user-assigned managed identity shared by all 12 apps, with role assignments that cover every customer's resources
C: One user-assigned managed identity per customer, created ahead of time in a central resource group and reused by new apps
D: One service principal per app with a certificate credential stored in Key Vault and rotated by an automation account
K: A
G: ## Matching the identity to the resource
User-assigned identities are usually more efficient, but Learn lists two cases where **system-assigned** is the better fit:
- **Audit logging**: when you need to log which specific resource carried out an action rather than which identity, each resource needs its own identity.
- **Permissions life-cycle management**: a system-assigned identity, and with it the permissions granted to it, is removed when the resource is deleted.
## Example
`func-customer07` is deleted. Its system-assigned service principal is deleted with it, so no orphaned identity keeps rights to customer 07's storage account.
W: System-assigned per app: each app's identity appears in its own logs and is deleted with the app, while scoping the role assignments gives each app only its own customer's resources.
X: B=One shared user-assigned identity: every app could reach every customer's data, and logs show one identity for all 12 apps.
C=Per-customer user-assigned identity: it has an independent life cycle, so deleting an app leaves the identity and its permissions behind.
D=Service principal with certificate: it brings back credentials to rotate and does not disappear when the app is deleted.
T: Choose system-assigned managed identities when actions must be traced to one resource and permissions must vanish with it.
V: Managed identities for Azure resources, Azure Functions

@ AZ-305 D1 T1.2 applied use-case
S: A GitHub Actions workflow deploys Bicep templates to an Azure subscription. Security policy forbids long-lived secrets or certificates in GitHub, and nothing should need rotating. How should the workflow authenticate to Azure?
A: Create a service principal with a client secret, store the secret as an encrypted GitHub repository secret, and rotate it often
B: Run the workflow on a self-hosted runner VM in Azure and read a storage account key from Key Vault at the start of each run
C: Configure workload identity federation on a user-assigned managed identity or app registration that trusts the GitHub repository
D: Generate a shared access signature for the subscription with a one-year expiry and pass it to the deployment step as a variable
K: C
G: ## Workloads outside Azure need an identity too
Managed identities work only for workloads running on Azure. A workload outside Azure, such as a GitHub Actions job, traditionally used an app registration with a **secret or certificate**, which must be stored, rotated and can leak or expire.
## Workload identity federation
You configure a **federated identity credential** on a user-assigned managed identity or an app registration. It names the external issuer (GitHub), the subject (for example a repository and branch) and the audience. At run time:
1. The workflow gets a token from GitHub.
2. It exchanges that token with the Microsoft identity platform for an access token.
3. It uses the access token against Azure Resource Manager.
No secret is stored anywhere, and nothing has to be rotated.
W: Workload identity federation: Microsoft Entra ID trusts tokens issued by GitHub for that repository, so the workflow gets Azure access tokens without any stored secret.
X: A=Client secret in GitHub: the secret is still a long-lived credential stored outside Azure, which the policy forbids, and it must be rotated.
B=Storage key from Key Vault: the runner still needs credentials to reach Key Vault, and a storage account key cannot deploy resources to a subscription.
D=Subscription SAS: shared access signatures exist for storage resources, not for Azure Resource Manager deployments, and a one-year token is a long-lived secret.
T: For GitHub Actions and other external workloads, use workload identity federation instead of secrets.
V: Microsoft Entra Workload ID, managed identities, GitHub Actions

@ AZ-305 D1 T1.2 applied use-case
S: Engineers at a partner company need access to an internal engineering web app registered in your Microsoft Entra tenant. They must sign in with their own corporate accounts, and your Conditional Access MFA policy must apply to them. Which solution should you recommend?
A: Create cloud-only member accounts for each partner engineer in your tenant and send them passwords through a secure channel
B: Use Microsoft Entra External ID B2B collaboration to invite the engineers as guests in your workforce tenant
C: Create a Microsoft Entra tenant in an external configuration and register the engineering web app in that new tenant
D: Synchronize the partner's Active Directory into your tenant with Microsoft Entra Cloud Sync installed at the partner site
K: B
G: ## External ID has two configurations
- **Workforce tenant with B2B collaboration**: business partners are added as **guest users** to the tenant that holds your employees and apps. They authenticate with their home organization or identity provider; no new credentials are created for them.
- **External tenant**: a separate tenant for publishing apps to consumers and business customers (customer identity and access management).
## Policies for guests
In a workforce tenant, Conditional Access policies apply to B2B collaboration users the same way as to employees. Cross-tenant access settings can also be set to trust MFA claims from the partner's Microsoft Entra tenant, so users who already did MFA at home are not prompted twice.
W: B2B collaboration: guests use their partner credentials, sit in the workforce tenant where the app is registered, and fall under the same Conditional Access policies.
X: A=Local member accounts: you create and own new credentials for outsiders, and they no longer sign in with their own corporate identity.
C=External tenant: that configuration targets consumer and customer apps; the internal app and its workforce Conditional Access policies live in the workforce tenant.
D=Sync the partner's directory: syncing another company's Active Directory makes its users members of your directory and needs an agent in their network, far beyond what guest access requires.
T: Partners who use their own work accounts to reach your internal apps belong in B2B collaboration in the workforce tenant.
V: Microsoft Entra External ID, B2B collaboration, Conditional Access

@ AZ-305 D1 T1.2 applied comparison
S: A fitness company is building a consumer mobile app. Customers must sign up themselves with email and password or their Google or Facebook accounts, with branded sign-up pages, and must be kept apart from the employee directory. Which identity solution should you recommend for a new deployment?
A: Microsoft Entra External ID in an external tenant, with self-service sign-up user flows and social identity providers
B: Microsoft Entra External ID B2B collaboration in the workforce tenant, inviting each customer as a guest by email
C: A new Azure AD B2C tenant with custom policies built in the Identity Experience Framework for the sign-up journey
D: Microsoft Entra Domain Services with LDAP accounts created on demand by the app back end when a customer registers
K: A
G: ## Customer identity and access management (CIAM)
Microsoft Entra External ID in an **external tenant** is Microsoft's CIAM solution for apps published to consumers and business customers. The external tenant is separate from the workforce tenant and contains the app registrations and the customer accounts.
- **Self-service sign-up user flows** define sign-up steps and sign-in methods: email and password, one-time passcodes, or social accounts from Google or Facebook.
- **Branding** can be customized for the organization or per application.
## What about Azure AD B2C?
Azure AD B2C is the legacy CIAM product. Effective May 1, 2025 it is **no longer available for new customers to purchase**, so a new deployment should use External ID.
W: External tenant: it keeps customers out of the workforce directory and provides branded self-service sign-up with email, Google and Facebook.
X: B=B2B collaboration: guests are invited into the employee tenant, which mixes consumers with the workforce and does not scale to self-service consumer sign-up.
C=Azure AD B2C: it is the legacy product and no longer sold to new customers since May 1, 2025, so it is not the choice for a new deployment.
D=Entra Domain Services: a managed domain offers LDAP and Kerberos for legacy apps; it has no consumer sign-up flows or social identity providers.
T: New consumer-facing apps use Microsoft Entra External ID in an external tenant; Azure AD B2C is legacy.
V: Microsoft Entra External ID

@ AZ-305 D1 T1.2 advanced use-case
S: After acquisitions, a group runs five Microsoft Entra tenants. Employees in each tenant need access to apps registered in the others, without invitation emails or consent prompts, and their accounts must be removed automatically from the other tenants when they leave. Which solution should you recommend?
A: Microsoft Entra Cloud Sync agents in each tenant that copy employee accounts from one tenant's directory into the others
B: Manual B2B invitations from each resource tenant, with a quarterly script that deletes guests who no longer have accounts
C: Cross-tenant synchronization configured between the tenants, which creates and removes B2B users automatically
D: Microsoft Entra External ID external tenants created for every subsidiary, each holding a copy of the employee accounts
K: C
G: ## Organizations with several tenants
Mergers often leave one organization with several Microsoft Entra tenants. Users in one tenant reach apps in another as **B2B collaboration users**. Creating them by invitation means each user gets an email and a consent prompt, and someone must remember to delete them later.
## Cross-tenant synchronization
Cross-tenant synchronization **automates creating, updating and deleting B2B collaboration users** (and groups) across tenants in an organization:
- users reach resources without receiving an invitation email or accepting a consent prompt in each tenant
- accounts are updated automatically and removed when the user leaves
- the synced users still fall under Conditional Access and cross-tenant access settings
W: Cross-tenant synchronization: it provisions B2B users into the target tenants automatically, skips invitations and consent, and deprovisions them when they leave.
X: A=Cloud Sync agents: Cloud Sync synchronizes from Active Directory to Microsoft Entra ID; it is not used to copy users between Microsoft Entra tenants.
B=Manual invitations with cleanup script: users still receive invitation emails, and custom scripts are exactly the maintenance burden the feature removes.
D=External tenants: external tenants are for consumer and customer apps, not for employees of the same organization working across workforce tenants.
T: A multitenant organization that wants automatic B2B user life cycle across its tenants uses cross-tenant synchronization.
V: Microsoft Entra ID, cross-tenant synchronization, B2B collaboration

@ AZ-305 D1 T1.2 applied use-case
S: A company wants users to be prompted for MFA only when Microsoft detects that a sign-in is probably not made by the account owner, such as an unfamiliar location or an anonymous IP address. Routine sign-ins should not be interrupted. What should you recommend?
A: A Conditional Access policy with a named-location condition that requires MFA for every sign-in from outside the corporate network
B: Per-user MFA enabled for every user, combined with a remembered-device setting that skips prompts on trusted devices
C: Security defaults for the tenant, which register every user for MFA and prompt users when a sign-in looks unusual
D: A Conditional Access policy with a sign-in risk condition of medium and high that requires MFA, licensed with Entra ID P2
K: D
G: ## Risk signals from Microsoft Entra ID Protection
ID Protection evaluates each sign-in and computes a **sign-in risk** (the probability that this sign-in is not authorized, for example anonymous IP, unfamiliar sign-in properties) and a **user risk** (the probability that the account is compromised, for example leaked credentials).
## Risk-based Conditional Access
Conditional Access can use those levels as conditions. A typical policy requires MFA when sign-in risk is **medium or high**; users are prompted only at that level, and completing MFA self-remediates the risky sign-in. Risk-based policies require **Microsoft Entra ID P2**; Conditional Access itself needs P1.
## Example
A user signs in from the office every day without prompts. A sign-in from an anonymizing proxy gets medium risk and is challenged for MFA.
W: Sign-in risk policy: it challenges only sign-ins that ID Protection scores as medium or high risk and leaves routine sign-ins alone.
X: A=Named location: it prompts every sign-in from outside the network regardless of risk, so routine remote work is interrupted and risky sign-ins inside are missed.
B=Per-user MFA: it prompts based on the user, not on the risk of a sign-in, and offers no risk evaluation of individual sign-ins.
C=Security defaults: they apply a fixed baseline for all users and cannot be tuned into a policy that targets a chosen sign-in risk level.
T: Prompting only for risky sign-ins means a sign-in risk-based Conditional Access policy, which needs Microsoft Entra ID P2.
V: Microsoft Entra ID Protection, Conditional Access

@ AZ-305 D1 T1.2 advanced use-case
S: Administrators of a government agency must sign in to the Azure portal only with phishing-resistant methods. Other employees may keep using any MFA method. Which design meets the requirement with built-in capabilities?
A: A Conditional Access policy for the admin roles that requires the built-in Phishing-resistant MFA authentication strength
B: A Conditional Access policy for the admin roles that requires multifactor authentication and a sign-in frequency of one hour
C: Disable SMS and voice in the authentication methods policy for the whole tenant so that only app-based methods remain
D: A Conditional Access policy for the admin roles that requires the built-in Passwordless MFA authentication strength
K: A
G: ## Authentication strengths
An authentication strength is a Conditional Access grant control that says **which methods** satisfy a policy. Three are built in:
- **Multifactor authentication strength**: the same combinations as "Require multifactor authentication".
- **Passwordless MFA strength**: MFA methods that need no password, which includes Microsoft Authenticator phone sign-in.
- **Phishing-resistant MFA strength**: only methods that bind the authentication to the sign-in surface: **Windows Hello for Business or platform credential, FIDO2 security key, and multifactor certificate-based authentication**.
## Targeting
Because the strength sits in a Conditional Access policy, you can scope it to privileged roles or sensitive apps while other users stay on a weaker strength.
W: Phishing-resistant MFA strength: it accepts only FIDO2 keys, Windows Hello for Business or platform credentials and multifactor CBA, and the policy can target just the admin roles.
X: B=Require MFA with frequency: any MFA method, including SMS and push, still satisfies the policy, and re-prompting more often does not make the method phishing-resistant.
C=Disable SMS and voice tenant-wide: it changes the methods for every employee and still leaves methods such as push notifications that are not phishing-resistant.
D=Passwordless MFA strength: it also allows Microsoft Authenticator phone sign-in, which is passwordless but not part of the phishing-resistant strength.
T: Require phishing-resistant sign-in for a subset of users with a Conditional Access policy using the Phishing-resistant MFA authentication strength.
V: Conditional Access, authentication strengths

@ AZ-305 D1 T1.2 applied comparison
S: A company plans to issue phishing-resistant credentials to its finance users and will enforce the built-in Phishing-resistant MFA authentication strength. Which TWO authentication methods satisfy that strength? (Select TWO)
A: Microsoft Authenticator phone sign-in, which approves the sign-in on the phone without a password
B: FIDO2 security keys registered as passkeys, which users plug in or tap during the sign-in
C: Temporary Access Pass issued by the help desk, which is a time-limited passcode for onboarding
D: Windows Hello for Business on corporate laptops, which uses a PIN or biometric bound to the device
E: A password combined with a one-time code sent by text message to the registered mobile phone
K: B,D
G: ## What makes a method phishing-resistant
Phishing-resistant methods require an interaction between the authenticator and the sign-in surface (the real site), so a fake site cannot relay the credential. The built-in **Phishing-resistant MFA strength** allows exactly:
- Windows Hello for Business or platform credential
- FIDO2 security key (passkey)
- Microsoft Entra certificate-based authentication (multifactor)
## Strong, but not phishing-resistant
- **Microsoft Authenticator phone sign-in** counts for the MFA and Passwordless MFA strengths, not the phishing-resistant one.
- **Temporary Access Pass** satisfies only the MFA strength.
- **Password plus SMS** satisfies only the MFA strength.
W: B=FIDO2 security key: it is bound to the origin of the sign-in, which puts it in the Phishing-resistant MFA strength.

@ AZ-305 D1 T1.2 advanced tradeoff
S: A key vault will hold the customer-managed key that encrypts a production storage account. The design must stop an attacker with admin rights from permanently destroying the key, and the key must rotate yearly with no outage. Which TWO settings should you recommend? (Select TWO)
A: Soft delete with purge protection enabled on the vault, so deleted keys stay recoverable for the whole retention period
B: The legacy access policy permission model, so that only the storage account identity has rights to the key material
C: A key rotation policy on the key, with the storage account configured to use the versionless key URI
D: A daily export of the key to a file in a second storage account, from where it can be imported if it is deleted
E: Soft delete turned off, so that a deleted vault name can be reused immediately to restore the service after an incident

G: ## Protecting keys from deletion
- **Soft delete** keeps deleted vaults and objects recoverable for 7 to 90 days (90 by default); it is on by default for new vaults and cannot be turned off once enabled.
- **Purge protection** is optional and off by default. When on, a deleted vault or object **cannot be purged until the retention period ends**, even by an administrator. Learn recommends it whenever keys are used for encryption, and services such as Storage require it for customer-managed keys.

A **key rotation policy** makes Key Vault create a new key version at a chosen frequency, and can send an Event Grid notification before expiry. Note that services take from an hour to a day or more to apply a new version, so don't disable the old one at once.
W: A=Soft delete with purge protection: a malicious or accidental delete can be recovered, and nobody can purge the key before the retention period ends.

X: B=Legacy access policies: Learn advises against them because contributors can grant themselves data access, and they do nothing against deletion.
D=Daily key export: HSM-protected key material is not exportable in plain form, and copies kept outside the vault widen exposure; recovery from deletion is what soft delete with purge protection provides.
E=Soft delete off: soft delete can't be disabled once on, and turning it off would make permanent destruction easier, not harder.
T: Encryption keys need soft delete plus purge protection, and a rotation policy with versionless key URIs for outage-free rotation.
