@ AZ-305 D2 T2.2 applied use-case
S: A retailer is designing a shopping cart service on Azure Cosmos DB for NoSQL with one write region and two read regions. Each shopper must always see the items they just added to their own cart, while read latency, availability and RU cost should stay as close as possible to the weakest consistency level. Which default consistency level should you recommend?
A: Session consistency, which gives each client session read-your-writes using its session token
B: Strong consistency, which makes every read return the latest committed write in all regions
C: Eventual consistency, which serves each read from any single replica in the local region
D: Bounded staleness, which keeps every read region within a configured lag of K versions or T time
K: A
G: ## The five consistency levels
Azure Cosmos DB offers five levels, from strongest to weakest: **Strong**, **Bounded staleness**, **Session**, **Consistent prefix** and **Eventual**. Stronger levels give fresher reads but cost more latency, availability or throughput.
## What each level costs
- **Strong** and **Bounded staleness** read from two replicas (a local minority), so a read costs twice the RUs of the weaker levels. Strong also commits each write in every region, which adds cross-region round trips to write latency.
- **Session**, **Consistent prefix** and **Eventual** read from a single replica and commit writes to a local majority, with asynchronous replication to other regions.
## Session in practice
After each write the client receives a session token. On the next read it sends the token, and Cosmos DB only answers from a replica that has caught up to that token. So the user who wrote the data always reads it back, while other users may see it a moment later. Learn calls session the most widely used level: its latency, availability and read throughput are comparable to eventual.
W: A=Session: the session token guarantees read-your-writes and write-follows-reads for the shopper's own session, while reads still come from a single replica, so latency and RU cost match the weak levels.
X: B=Strong: it does give the latest write, but every write waits for all regions to commit and every read costs double RUs, which is far more than the cart needs, since only the shopper's own writes matter.
C=Eventual: a read can hit a lagging replica and return stale or missing data, so a shopper could add an item and not see it in the cart on the next page load.
D=Bounded staleness: reads use two replicas and cost twice the RUs, and the guarantee is a maximum lag across regions, not that a client sees its own latest writes immediately.
T: Users must see their own writes at weak-level cost: choose session consistency, the default most applications use.
V: Azure Cosmos DB

@ AZ-305 D2 T2.2 advanced tradeoff
S: A market data service uses Azure Cosmos DB with a single write region in West Europe and read regions on three other continents. Readers in every region must never be more than 10 minutes behind the writer and must see updates in order, but write latency must not depend on cross-continent round trips. Which consistency level should you recommend?
A: Strong, so that every read region always returns the most recent committed version of each item
B: Bounded staleness, with the time bound set so that read regions lag the write region by 10 minutes at most
C: Session, so that each reader session receives a token that limits how stale its reads can become
D: Eventual, combined with a monitoring alert on the Probabilistically Bounded Staleness metric for each region
K: B
G: ## Bounded staleness
With bounded staleness the lag between regions is always less than a configured amount: **K** versions of an item or a **T** time interval, whichever is reached first. Reads in a region return the newest data available there, within that bound, and in order.
- If a region falls further behind than the bound, Cosmos DB throttles writes for that partition until the lag is back inside the limit.
- For multi-region accounts the minimum bound is 100,000 writes or 300 seconds, so a 10-minute (600-second) bound is valid.
- Writes still commit to a local majority in the write region, so write latency does not include cross-region round trips.
## When to use it
Learn describes bounded staleness as best for globally distributed apps with a **single write region** that want near-strong consistency across regions. In accounts with multiple write regions it is an anti-pattern.
## Compare with strong
Strong commits each write in every region before acknowledging it; write latency becomes about twice the round-trip time between the two farthest regions plus 10 ms, and accounts spanning more than 8,000 km are blocked from strong by default.
W: B=Bounded staleness: it puts a hard upper limit on how far behind any read region can be and preserves order, while writes are acknowledged after a local majority commit, so latency stays regional.
X: A=Strong: every write waits for all regions to commit, so write latency would include cross-continent round trips, which the requirement forbids; it is stronger than the 10-minute bound needs.
C=Session: the guarantee is read-your-writes inside one client session. Readers who did not write the data have no bound on how stale their reads can be.
D=Eventual with a PBS alert: the PBS metric only reports how often reads happen to be consistent; it does not enforce a limit, and eventual reads can even go backward in time.
T: Need a guaranteed maximum lag across regions with a single write region and regional write latency: bounded staleness with a K/T bound.
V: Azure Cosmos DB

@ AZ-305 D2 T2.2 advanced tradeoff
S: An Azure Cosmos DB account with one write region and one read region uses session consistency. The architects propose switching the default consistency to strong. Which two effects should you expect from this change? (Select TWO)
A: Write latency increases, because each write must commit in both regions before it is acknowledged
B: Each read consumes about twice as many request units, because reads are served from two replicas
C: The account can then enable multiple write regions to lower the write latency added by strong mode
D: Reads in the read region can return items that are up to K versions older than the write region
E: The RU charge for reads is halved, because strong reads come from a single replica with no token
K: A,B
G: ## How strong consistency works
With **strong** consistency, reads always return the most recent committed version of an item. To guarantee this, a write is committed only after every region acknowledges it (a global majority), instead of a local majority in the write region.
## Latency and throughput effects
- **Writes**: for an account with more than one region, write latency becomes about twice the round-trip time between the two farthest regions plus 10 ms at the 99th percentile.
- **Reads**: strong and bounded staleness read from two replicas in the four-replica set (a local minority). Learn states that the RU cost of these reads is twice that of the weaker levels, so for the same RU/s read throughput is halved.
- Session, consistent prefix and eventual read from a single replica.
## Strong and multiple write regions
Accounts with multiple write regions cannot use strong consistency: a distributed system cannot give an RPO of zero and an RTO of zero at the same time, and multi-write would not lower latency anyway because writes must still commit everywhere.
W: A=Higher write latency: strong commits each write in every region (global majority), so the inter-region round trip is added to every write.
B=Double read RU cost: strong reads go to two replicas (local minority), and Learn states these reads cost twice the RUs of session or eventual reads.
X: C=Enable multiple write regions: Cosmos DB does not allow strong consistency on accounts with multiple write regions, so this cannot offset the added latency.
D=Reads up to K versions old: that describes bounded staleness. With strong, every read returns the latest committed version.
E=Halved RU charge: it is the opposite. Session reads use a single replica; strong reads use two and cost twice as much.
T: Strong consistency adds cross-region commit latency to writes and doubles read RU cost, and it cannot be combined with multiple write regions.
V: Azure Cosmos DB

@ AZ-305 D2 T2.2 applied comparison
S: An online store will keep orders for about 50,000 customers in an Azure Cosmos DB for NoSQL container. Most queries read all orders of one customer, and writes surge during flash sales. Which partition key should you recommend?
A: /orderDate, so that each day's orders form one logical partition that is easy to archive later
B: /orderStatus, so that open, shipped and returned orders are each grouped into their own partition
C: /customerId, so that one customer's orders share a partition and writes spread across many values
D: /id, so that every order gets its own logical partition and writes spread as evenly as possible
K: C
G: ## What a partition key does
Items with the same partition key value form a **logical partition**. Cosmos DB hashes the value and maps logical partitions to physical partitions; throughput is divided evenly across physical partitions, and each physical partition serves at most 10,000 RU/s. A logical partition can hold up to 20 GB.
## What makes a good key
- **High cardinality**: many distinct values, so data and requests spread out.
- **Even request distribution**: no single value receives most reads or writes (a "hot" partition).
- **Matches the main queries**: a query that filters on the partition key goes to one partition; one that does not becomes a cross-partition (fan-out) query.
- **Immutable**: the value cannot be updated in place, so pick a property that never changes.
## Example
With `/customerId`, the query "all orders for customer 4711" hits one logical partition, and 50,000 customers give enough distinct values to spread a flash-sale burst.
W: C=/customerId: high cardinality spreads writes during sales, the dominant query is a single-partition query, and a customer ID never changes on an order.
X: A=/orderDate: during a flash sale all writes target today's value, creating one hot partition capped at a single physical partition's throughput.
B=/orderStatus: only a handful of values exist, so data and traffic pile into a few partitions, and status changes over time while partition key values cannot be updated.
D=/id: writes spread evenly, but "all orders of a customer" no longer filters on the partition key, so the main query fans out to every partition and costs far more RUs.
T: Pick a high-cardinality, immutable partition key that the main queries filter on; avoid dates and low-cardinality status values.
V: Azure Cosmos DB

@ AZ-305 D2 T2.2 advanced use-case
S: A SaaS provider stores events for all tenants in one Azure Cosmos DB for NoSQL container partitioned by /tenantId. A few large tenants are approaching the 20 GB logical partition limit, and most queries filter on a single tenant. What should you recommend for a new container?
A: A synthetic partition key that appends a random suffix from 1 to 10 to each tenantId value
B: A partition key of /userId, so that each user's events form their own small logical partition
C: The same /tenantId key with a much higher autoscale maximum, which raises the logical partition size limit
D: Hierarchical partition keys of /tenantId then /userId, so that one tenant's data can span partitions
K: D
G: ## The 20 GB logical partition limit
Every item with the same partition key value lives in one logical partition, and a logical partition can store at most 20 GB (and use at most 10,000 RU/s, the limit of the physical partition it sits on). Adding throughput does not change this limit.
## Hierarchical partition keys (subpartitioning)
With hierarchical partition keys you define up to **three levels**, for example `TenantId`, then `UserId`, then `SessionId`. Learn's multitenant example:
- Data for one `TenantId` can exceed 20 GB and span several physical partitions, because the full key path, not the first level alone, defines the logical partition.
- Queries that filter on the prefix (`TenantId`) are routed only to the partitions that hold that tenant, not fanned out to all partitions.
- Hierarchical keys can only be set when a container is created, so existing data moves to a new container (for example with container copy jobs).
## Why not the alternatives
Learn notes that a synthetic key combining tenant and another value adds application complexity, and tenant queries stay cross-partition unless all values are known in advance. Partitioning by `UserId` alone makes every tenant query cross-partition.
W: D=Hierarchical keys /tenantId, /userId: large tenants scale past 20 GB because each tenant-user pair is its own logical partition, and tenant-scoped queries are still routed efficiently by the tenantId prefix.
X: A=Random-suffix synthetic key: it spreads a tenant over ten partition values, but each tenant query must now query all ten values or fan out, and the application has to build and track the suffixes.
B=/userId only: no user partition gets large, but the dominant tenant-scoped queries become cross-partition queries over the whole container.
C=Higher autoscale maximum: more RU/s adds physical partitions, yet a single logical partition stays limited to 20 GB, so the large tenants still hit the ceiling.
T: Tenants that outgrow 20 GB but are queried per tenant: use hierarchical partition keys with the tenant as the first level.

@ AZ-305 D2 T2.2 applied tradeoff
S: A team is building a proof-of-concept app on Azure Cosmos DB in one region. Traffic is idle most of the week with short, unpredictable bursts, and the team wants to pay only for the database operations that actually run. Which capacity option should you recommend?
A: Autoscale provisioned throughput with a low maximum, so throughput drops to a fraction of the maximum between bursts
B: Serverless capacity mode, which bills for the request units consumed with no throughput provisioned in advance
C: Standard (manual) provisioned throughput set to the expected peak, reduced by a scheduled job outside office hours
D: Provisioned throughput shared at the database level, so that idle containers lend their RU/s to busy containers
K: B
G: ## Two capacity modes
Azure Cosmos DB accounts run in **provisioned throughput** or **serverless** mode. Both support the same database operations; billing differs.
- **Provisioned throughput**: you configure RU/s per container or database and pay every hour for what is provisioned, whether or not it is used. It can be manual (standard) or **autoscale**.
- **Serverless**: nothing is provisioned; each hour you pay for the RUs your operations consumed.
## Choosing
Learn's comparison: provisioned suits sustained traffic needing predictable performance; serverless suits **intermittent or unpredictable traffic with a low average-to-peak ratio**. Trade-offs of serverless: one Azure region only (no geo-distribution), and writes are covered by an SLO rather than the provisioned SLA.
## Autoscale billing
Autoscale scales between 10% of the maximum (`0.1 * Tmax`) and `Tmax`, and you are billed each hour for the highest throughput reached, so even an idle hour still costs 10% of the maximum.
W: B=Serverless: the PoC is single-region, mostly idle and bursty, which is exactly the low average-to-peak profile serverless targets; idle hours cost nothing for throughput.
X: A=Autoscale with a low maximum: it never drops below 10% of the maximum, so idle hours are still billed, and the team must pick a maximum high enough for unknown bursts.
C=Manual throughput with a schedule: the team pays for the peak during every scheduled hour, and unpredictable bursts outside the schedule would be throttled.
D=Shared database throughput: sharing RU/s between containers still provisions and bills a fixed amount every hour, regardless of whether any operation runs.
T: Single-region, intermittent, unpredictable traffic where you want to pay per use: serverless; sustained or geo-distributed traffic: provisioned (manual or autoscale).
V: Azure Cosmos DB

@ AZ-305 D2 T2.2 applied use-case
S: A company runs a self-managed Apache Cassandra cluster for device telemetry. It wants a fully managed Azure service with global distribution, without sizing or patching nodes, and it must keep its existing CQL drivers and queries with minimal code changes. What should you recommend?
A: Azure Cosmos DB for NoSQL, with the application rewritten to use the NoSQL SDK and SQL queries
B: Azure Table Storage, with each Cassandra table mapped to a table keyed by PartitionKey and RowKey
C: Azure Cosmos DB for Apache Cassandra, which supports the Cassandra Query Language and existing drivers
D: Azure Database for PostgreSQL flexible server, with the wide-column tables converted to relational schemas
K: C
G: ## Azure Cosmos DB APIs
Azure Cosmos DB exposes several APIs on the same distributed engine: **NoSQL** (native, SQL-like queries over JSON), **MongoDB**, **Apache Cassandra**, **Apache Gremlin** and **Table**. The wire-compatible APIs let existing applications keep their drivers and query languages.
## API for Apache Cassandra
Learn describes it as a fully managed NoSQL service that runs Cassandra workloads with minimal changes to application code: it supports CQL and is compatible with existing Cassandra drivers and tools. It suits wide-column data such as time series and sensor data with high write throughput, and it inherits Cosmos DB features: automatic scaling, global distribution and no infrastructure to manage.
## Choosing an API
- Migrating an existing app: pick the API that matches its current protocol (Cassandra, MongoDB, Table) to avoid rewrites.
- New cloud-native app: Learn points to the NoSQL API for the broadest feature set.
W: C=Cosmos DB for Apache Cassandra: it speaks CQL, works with the existing Cassandra drivers, and is fully managed and globally distributable, so the code barely changes and no nodes need care.
X: A=Cosmos DB for NoSQL: it is managed and global, but the application would have to be rewritten for a different SDK and query language, breaking the minimal-change requirement.
B=Azure Table Storage: a simple key-value store with its own API; CQL drivers cannot talk to it and it has no multi-region write or query capabilities matching Cassandra.
D=PostgreSQL flexible server: converting wide-column tables to a relational schema means rewriting data access, and it is not a wire-compatible Cassandra target.
T: Keep CQL and Cassandra drivers on a fully managed, globally distributed service: Azure Cosmos DB for Apache Cassandra.

@ AZ-305 D2 T2.2 applied use-case
S: An IoT platform writes device readings to an Azure Cosmos DB container. Readings are only needed for 30 days, and the design must remove older items automatically without writing or scheduling any cleanup code. What should you recommend?
A: An Azure Storage lifecycle management policy that deletes items when they are older than 30 days
B: A change feed processor in Azure Functions that deletes each item 30 days after it was written
C: Setting the container's default time to live to -1, so that every item expires on its own schedule
D: Setting the container's default time to live to 2,592,000 seconds, so items expire 30 days after their last change
K: D
G: ## Time to live (TTL) in Cosmos DB
TTL makes Cosmos DB delete items automatically after a period counted **from the last time the item was modified**. The value is in seconds.
- Set `DefaultTimeToLive` on the container; items can override it with their own `ttl` property.
- `DefaultTimeToLive = -1` means "infinity": items do not expire unless they set their own `ttl`.
- Expired items disappear from query results immediately; physical deletion runs as a background task. On provisioned accounts it uses leftover RUs not consumed by user requests; on serverless accounts it is charged like delete operations.
## Example
30 days x 86,400 seconds = `2592000`. With that default, a reading written on 1 May disappears from queries on 31 May with no client delete calls.
W: D=Default TTL of 2,592,000 seconds: Cosmos DB expires each item 30 days after its last write and deletes it in the background, so no cleanup code or schedule is needed.
X: A=Storage lifecycle management policy: lifecycle policies act on blobs in Azure Storage accounts; they cannot see or delete items in a Cosmos DB container.
B=Change feed processor with deletes: it would work, but it is custom code to write, run and pay for, which the requirement rules out, and each delete consumes RUs.
C=Default TTL of -1: -1 means items never expire by default; only items with their own `ttl` value would be removed.
T: Automatic expiry of Cosmos DB items: set the container's default TTL in seconds (-1 means never expire unless an item sets its own).

@ AZ-305 D2 T2.2 applied tradeoff
S: A hospital must keep scanned records in Azure Blob Storage for 10 years. Each record is opened perhaps once a year, but when a doctor requests one it must open within seconds. Which access tier should you recommend to minimize cost?
A: Archive tier, with standard-priority rehydration when a doctor requests a record
B: Cold tier, an online tier with lower storage cost than cool and immediate reads
C: Cool tier, an online tier for data kept at least 30 days and read occasionally
D: Hot tier, with reserved capacity purchased to lower the storage price per gigabyte
K: B
G: ## Blob access tiers
- **Hot**: online, highest storage cost, lowest access cost; for data in active use.
- **Cool**: online, lower storage cost and higher access cost; data should stay at least **30 days**.
- **Cold**: online, lower storage cost than cool and higher access cost; for data that is rarely accessed but still needs fast retrieval; at least **90 days**.
- **Archive**: offline, lowest storage cost; data cannot be read until it is rehydrated to an online tier, which takes hours; at least **180 days**.
Moving or deleting a blob before its tier's minimum period incurs a prorated early deletion charge.
## The deciding requirement
Cool and cold tiers have the same retrieval latency and throughput as hot. Only archive is offline. So the question is: what is the cheapest tier that still opens a record immediately?
W: B=Cold tier: records are read about once a year and kept far longer than 90 days, so the low storage price outweighs the higher read cost, and reads are still immediate because cold is an online tier.
X: A=Archive tier: cheapest to store, but archived blobs cannot be read until rehydrated, which can take up to 15 hours at standard priority, so a doctor could not open a record within seconds.
C=Cool tier: also immediate, but it is built for data read occasionally and costs more to store than cold, so rarely read records would cost more for no benefit.
D=Hot tier: the highest storage price of the online tiers; reserved capacity lowers it somewhat but still wastes money on data that is almost never read.
T: Rarely read but needs instant access and long retention: cold tier; hours of delay acceptable: archive.

@ AZ-305 D2 T2.2 advanced troubleshooting
S: A company keeps documents in a ZRS general-purpose v2 storage account. A new lifecycle rule should move audit files older than one year to the archive tier, but the blobs never change tier. What should you recommend?
A: Enable blob versioning on the account, because lifecycle actions to archive apply only to blob versions
B: Change the account's default access tier to archive, so that existing audit files inherit the archive tier
C: Upgrade the account to a premium block blob account, because the archive tier requires SSD-backed storage
D: Store the audit files in a separate LRS or GRS account, because the archive tier is not supported with ZRS
K: D
G: ## Archive tier and redundancy
Learn states that only accounts configured for **LRS, GRS or RA-GRS** support moving blobs to the archive tier. Archive is **not supported for ZRS, GZRS or RA-GZRS** accounts. Hot, cool and cold support every redundancy option.
Changing the redundancy of an account that already holds archived blobs requires rehydrating them first, so Microsoft recommends deciding the redundancy of archive data up front.
## Design consequence
A common design is two accounts:
- a ZRS or GZRS account for active data that needs zone resilience, and
- an LRS or GRS account for long-term archive data, with a lifecycle policy or copy job moving aged files there.
## Other archive facts
- The archive tier cannot be the default access tier of an account.
- Premium block blob accounts do not offer hot, cool, cold or archive tiers at all.
W: D=Separate LRS or GRS account: the archive tier is not available on ZRS accounts, so the aged audit files must live in an account with LRS, GRS or RA-GRS redundancy to be archived.
X: A=Enable versioning: lifecycle rules can tier current versions, previous versions and snapshots; versioning is not a prerequisite for archive and does not change the ZRS limitation.
B=Default tier set to archive: the default access tier can only be hot, cool or cold; archive is never allowed as the account default.
C=Premium block blob account: premium accounts store data on SSDs for low latency and do not offer the archive tier, so this moves further away from the goal.
T: The archive tier works only with LRS, GRS or RA-GRS accounts; zone-redundant accounts (ZRS, GZRS, RA-GZRS) cannot archive.

@ AZ-305 D2 T2.2 applied use-case
S: A legal team needs a 4 GB contract that was moved to the archive tier last year. The file must be readable in under an hour, and extra cost is acceptable. What should you recommend?
A: Rehydrate the blob to the hot tier with standard priority, which completes within one hour for blobs under 10 GB
B: Generate a SAS for the archived blob, so that the legal team can download it directly from the archive tier
C: Rehydrate the blob to an online tier with high priority, which can complete in under an hour for blobs under 10 GB
D: Change the account's default access tier to hot, so that the archived blob is moved back online automatically
K: C
G: ## Reading archived blobs
A blob in the archive tier is **offline**: it cannot be read or modified. Its metadata and properties can still be listed. To read it you **rehydrate** it to hot, cool or cold, either by changing its tier (Set Blob Tier) or by copying it to a new online blob (Copy Blob).
## Rehydration priority
- **Standard** (default): requests are processed in order and can take up to **15 hours** for objects under 10 GB.
- **High**: prioritized over standard requests and can complete in **under one hour** for objects under 10 GB; it costs more. Learn recommends reserving it for emergency restores.
- A pending standard request can be raised to high, but not lowered.
- Throughput is shared per account (up to 10 GiB per hour with priority retrieval), so bulk restores take longer.
## Copy versus change tier
Copying to a new blob leaves the original in archive and avoids the early deletion charge if the blob has been archived for less than 180 days.
W: C=High-priority rehydration: for a 4 GB blob it can complete in under an hour, which meets the deadline, and the extra cost was declared acceptable.
X: A=Standard priority: standard rehydration can take up to 15 hours for blobs under 10 GB; it gives no one-hour guarantee.
B=SAS on the archived blob: a SAS only authorizes access; an archived blob is offline and cannot be read by anyone until it is rehydrated.
D=Default tier to hot: the default tier only applies to blobs whose tier is inferred; a blob explicitly in archive is not rehydrated by this change.
T: Archived data needed urgently: rehydrate with high priority (under an hour for blobs under 10 GB); standard priority can take up to 15 hours.

@ AZ-305 D2 T2.2 advanced use-case
S: A media company wants blobs moved from hot to cool automatically when nobody has read them for 60 days, even if they were created years ago, and wants this done without custom code. Which two actions should you recommend? (Select TWO)
A: Enable last access time tracking on the storage account
B: Add a lifecycle rule that moves blobs to cool when daysAfterLastAccessTimeGreaterThan is 60
C: Add a lifecycle rule that moves blobs to cool when daysAfterModificationGreaterThan is 60
D: Enable blob versioning, so that lifecycle rules can see each blob's read history
E: Change the account's default access tier to cool, so that unread blobs move after 60 days
K: A,B
G: ## Lifecycle management conditions
A lifecycle management policy is a set of rules. Each rule has **filters** (prefixes or blob index tags), **conditions** and **actions** (tier to cool, cold or archive, or delete). Conditions are based on three blob properties:
- creation time,
- last modified time,
- **last accessed time**, but only if **access time tracking** is enabled on the account.
Policies are free to run; you pay for the Set Blob Tier operations, and each last-access-time update is billed as an "other" transaction at most once per 24 hours per object. Rule changes can take up to 24 hours to take effect.
## Read versus modify
A blob that is read every day but never rewritten has an old modification time. A rule based on modification time would cool it even though it is in active use. Only the last access time reflects reads.
## Example
`"tierToCool": {"daysAfterLastAccessTimeGreaterThan": 60}` with tracking enabled cools a 2019 video only after 60 days without reads.
W: A=Enable access time tracking: without it, the last accessed time is not recorded and lifecycle rules cannot use it as a condition.

@ AZ-305 D2 T2.3 advanced use-case
S: Analysts in Microsoft Fabric need near-real-time reports over an Azure Cosmos DB for NoSQL container without consuming its request units, and must also use existing Delta tables in an Azure Data Lake Storage account without copying them. Which two features should you recommend? (Select TWO)
A: Mirroring in Fabric for the Azure Cosmos DB database, which replicates its data into OneLake
B: A OneLake shortcut in a lakehouse that points to the Delta tables in the Data Lake Storage account
C: Azure Synapse Link for Azure Cosmos DB, which exposes the container's analytical store to Synapse
D: A Data Factory copy pipeline that reads the Cosmos DB container every 15 minutes into a lakehouse
E: A Fabric pipeline that copies the Delta tables from Data Lake Storage into the lakehouse Tables folder
K: A,B
G: ## Mirroring in Fabric
Mirroring continuously replicates an operational database into **OneLake** as Delta tables, with no ETL pipelines to build. Sources include Azure SQL Database, SQL Managed Instance, Azure Database for PostgreSQL and **Azure Cosmos DB**.
For Cosmos DB, Learn states that mirroring gives near-real-time access **without any performance impact on transactional workloads and without consuming RUs**. Mirroring currently supports Azure Cosmos DB for NoSQL accounts only, and continuous backup must be enabled on the account (standard continuous backup charges apply).
## OneLake shortcuts
A shortcut is an object in OneLake that points to another storage location, such as a Data Lake Storage account, Amazon S3 or another OneLake item. It behaves like a symbolic link: data stays in place, and Fabric engines read it through OneLake. Delta data under the lakehouse Tables folder is recognized as tables automatically.
## Synapse Link status
Learn states that **Synapse Link for Cosmos DB is no longer supported for new projects** and points to Cosmos DB mirroring in Fabric instead.
W: A=Mirroring for Cosmos DB: data is replicated into OneLake in near real time with no ETL and without consuming the container's RUs.
B=OneLake shortcut: the lakehouse references the existing Delta tables in place, so Fabric can query them without making a copy.
X: C=Synapse Link for Cosmos DB: Learn marks it as not supported for new projects, and it targets Synapse rather than Fabric.
D=Copy pipeline every 15 minutes: it is an ETL job that reads the container and consumes its RUs, and data is only as fresh as the last run.
E=Copy the Delta tables: it creates the duplicate the requirement forbids and must be rerun to stay current.
T: Fabric analytics without ETL: mirroring for operational databases such as Cosmos DB, and shortcuts for data already in a lake.
V: Microsoft Fabric, Azure Cosmos DB, Azure Data Lake Storage

@ AZ-305 D2 T2.3 advanced tradeoff
S: Security policy disables public network access on the storage accounts and Azure SQL databases that Azure Data Factory copies between. The team must not run or patch any integration runtime VMs and wants protection against data exfiltration. What should you recommend?
A: A self-hosted integration runtime on Azure VMs in a spoke virtual network that has private endpoints to the stores
B: An Azure integration runtime in a managed virtual network, with managed private endpoints to each data store
C: An Azure integration runtime without a managed network, with its regional IP ranges added to each store's firewall
D: An Azure-SSIS integration runtime joined to a virtual network, running the copy logic as SSIS packages
K: B
G: ## Managed virtual network in Data Factory
When you enable a **managed virtual network** for an Azure integration runtime, Data Factory deploys the IR inside a virtual network that Data Factory manages. You do not create subnets or VMs.
- **Managed private endpoints** are private endpoints that Data Factory creates in that managed network, each mapped to one specific resource (a storage account, SQL server, Cosmos DB account and so on) after the resource owner approves it.
- Traffic between the IR and the stores stays on the Microsoft backbone through Private Link, so the stores can keep public access disabled.
- Learn states that a managed virtual network with managed private endpoints protects against **data exfiltration**, because connectivity is limited to approved resources.
- The managed virtual network must be in the same region as the data factory.
## Other ways in
A self-hosted IR on your own VMs also reaches private endpoints, but you operate and patch those VMs. An IP-allow list requires public network access to be enabled.
W: B=Managed virtual network with managed private endpoints: the Azure IR reaches each store privately while public access stays off, Data Factory runs the compute, and approved per-resource endpoints limit exfiltration.
X: A=Self-hosted IR on Azure VMs: it works over private endpoints, but the team would have to run and patch those VMs, which the requirement forbids.
C=IP ranges in store firewalls: firewall IP rules apply to the public endpoint, which is disabled; reopening it contradicts the policy and allows other traffic from those ranges.
D=Azure-SSIS IR in a virtual network: it is meant for running SSIS packages, and rewriting copies as packages adds work while still leaving a cluster to manage.
T: Private connectivity to locked-down stores with no IR VMs to manage: Azure IR in a managed virtual network with managed private endpoints.
V: Azure Data Factory, Azure Private Link
