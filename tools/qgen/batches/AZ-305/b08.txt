@ AZ-305 D4 T4.1 applied use-case
S: A retailer is moving an in-memory analytics engine and a large relational database server to Azure VMs. Both need far more RAM per vCPU than a balanced size offers, and CPU use is moderate. Which VM size family should you recommend?
A: The E-family memory optimized sizes, which offer a high memory-to-CPU ratio for databases and in-memory analytics
B: The F-family compute optimized sizes, which offer a high CPU-to-memory ratio for application servers and batch work
C: The L-family storage optimized sizes, which offer high local disk throughput and IO for NoSQL and big data stores
D: The B-family burstable sizes, which bank CPU credits while idle and spend them during short spikes of heavy load
K: A
G: ## How Azure groups VM sizes
Learn sorts VM sizes by **type**, and each type contains **families** named by a letter:
- **General purpose** (A, B, D, DC): balanced CPU-to-memory ratio for dev/test, small databases and web servers.
- **Compute optimized** (F, FX): high CPU-to-memory ratio for medium traffic web servers, network appliances, batch processes and application servers.
- **Memory optimized** (E, Eb, EC, M): high memory-to-CPU ratio for relational database servers, medium to large caches and in-memory analytics. The M-family goes further for extremely large databases.
- **Storage optimized** (L): high disk throughput and IO for Cassandra, MongoDB and data warehousing.
- **GPU** (NC, ND, NG, NV), **FPGA** and **HPC** (HB, HC, HX) for specialised work.
## Picking a family
Start from the bottleneck. A database whose working set must sit in RAM is limited by memory, not CPU, so a memory optimized family gives the RAM without paying for cores the engine will not use.
W: E-family memory optimized: Learn lists relational databases, medium to large caches and in-memory analytics as the E-family's workloads, which is exactly a memory-bound engine with moderate CPU.
X: B=F-family compute optimized: these sizes have the opposite ratio, many cores per GB of RAM. The team would buy CPU it does not need and still run short of memory.
C=L-family storage optimized: the L-family is built for high local disk throughput and IO. The stated limit is RAM per vCPU, which the L-family does not target.
D=B-family burstable: burstable sizes suit workloads that idle most of the time and spike briefly. They are general purpose sizes with a balanced or smaller memory footprint, not a high memory-to-CPU ratio.
T: Memory-bound databases and in-memory analytics map to the memory optimized E-family (M-family for the very largest); compute optimized F is for CPU-bound work.
V: Azure Virtual Machines

@ AZ-305 D4 T4.1 advanced use-case
S: An engineering firm runs computational fluid dynamics simulations whose processes exchange data through MPI during each run. It wants Azure to schedule jobs and manage the node pool so the team does not operate any cluster software. Which solution should you recommend?
A: An Azure Container Apps environment running the solver as an event-driven job that scales out on queue length
B: An Azure Batch pool of HB-family HPC VMs that runs the solver as MPI jobs submitted through the Batch APIs
C: Azure Functions on the Premium plan running each simulation step as a function that fans out across instances
D: A Virtual Machine Scale Set of F-family VMs with an autoscale rule based on the CPU percentage of the nodes
K: B
G: ## Two kinds of parallel work
Learn separates batch workloads into two shapes:
- **Intrinsically parallel** ("embarrassingly parallel"): each task runs on its own and never talks to the others, for example image rendering or file conversion.
- **Tightly coupled**: the processes communicate during the run, normally through the **Message Passing Interface (MPI)**. Fluid dynamics, finite element analysis and weather models are typical examples.
## What Azure Batch adds
Azure Batch creates and manages a pool of compute nodes, installs the applications and schedules jobs on them. There is no cluster or job scheduler software to install or scale; you submit independent tasks or MPI jobs through the Batch APIs. Batch runs tightly coupled jobs with Microsoft MPI or Intel MPI.
## The right hardware
The HPC families (HB, HC, HX) are optimized for this work. Learn lists fluid dynamics and weather modeling under the HB-family because those codes need high memory bandwidth.
W: Batch pool of HB-family VMs: Batch supplies the scheduler and node management, supports MPI for tightly coupled jobs, and the HB-family is the HPC family Learn names for fluid dynamics.
X: A=Container Apps job: Container Apps jobs run finite containerised tasks triggered manually, on a schedule or by events. Nothing in that model provides an MPI fabric or HPC sizes for processes that must talk to each other during a run.
C=Functions Premium plan: functions are short event-driven executions on general instances. Splitting a coupled solver into independent functions breaks the constant data exchange the simulation depends on.
D=Scale set with CPU autoscale: a scale set adds or removes VMs but has no job scheduler, so the team would have to run its own cluster software. The F-family is also general compute, not an HPC family.
T: Tightly coupled MPI jobs with scheduling as a service point to Azure Batch on HPC sizes (HB/HC/HX); independent tasks also fit Batch, and neither needs a self-run scheduler.
V: Azure Batch, Azure Virtual Machines

@ AZ-305 D4 T4.1 applied tradeoff
S: A studio renders animation frames on hundreds of VMs. Any frame can be rerun if a VM disappears, and the studio wants the lowest compute cost with no charges left behind after Azure reclaims capacity. Which TWO design choices should you recommend? (Select TWO)
A: Deploy the render nodes as Azure Spot Virtual Machines so they run on unused Azure capacity at a discount
B: Set the eviction policy to Delete so evicted VMs and their disks are removed instead of being deallocated
C: Buy a three-year reservation for the render nodes so they are protected from eviction during busy periods
D: Place the render nodes on Azure Dedicated Hosts so no other customer can reclaim the underlying capacity
E: Set the eviction policy to Deallocate so evicted VMs keep their disks and restart automatically later
K: A,B
G: ## Azure Spot Virtual Machines
Spot VMs run on unused Azure capacity at a significant discount. The trade-off is that Azure can **evict** them at any time when it needs the capacity back (or when the price rises above your maximum), with about 30 seconds' notice through Scheduled Events. There is no SLA. Learn recommends them for workloads that tolerate interruption: batch jobs, dev/test and large compute work such as rendering.
## Eviction policy
You choose what happens at eviction:
- **Deallocate** (default): the VM moves to stopped-deallocated. Its disks remain and are billed, and it still counts against quota. Azure does not restart it for you, and a later restart is not guaranteed to get capacity.
- **Delete**: the VM and its disks are deleted, so nothing keeps billing.
## Example
A render farm keeps its job queue outside the VMs. When a node is evicted, the frame returns to the queue and another node picks it up, so losing a VM costs only a little time.
W: A=Spot Virtual Machines: rerunnable frames are exactly the interruption-tolerant work Spot is meant for, and Spot capacity is the lowest-cost way to run hundreds of nodes.
B=Delete eviction policy: Delete removes the VM together with its disks, so an evicted node leaves no storage charges behind, which the studio asked for.
X: C=Three-year reservation: a reservation is a billing discount for steady, always-on VMs. It does not apply to Spot capacity, and it commits spend for years for a bursty farm.
D=Dedicated Hosts: dedicated hosts give physical isolation and maintenance control at a full host price. They raise cost instead of lowering it, and they are unrelated to Spot eviction.
E=Deallocate eviction policy: deallocated Spot VMs keep their disks, which continue to bill, and Azure does not restart them automatically after eviction.
T: Interruptible, rerunnable work goes on Spot VMs; choose the Delete eviction policy when you want no disk charges after an eviction.
V: Azure Virtual Machines

@ AZ-305 D4 T4.1 applied use-case
S: A bank's compliance team requires that its Windows Server VMs never share a physical server with other customers' VMs, and that the team can choose a window for platform maintenance on those servers. Which compute option should you recommend?
A: Azure confidential VMs, which encrypt the VM's memory and disks with keys bound to a hardware-backed virtual TPM
B: A Virtual Machine Scale Set in Flexible orchestration spread across three availability zones in the region
C: Azure Dedicated Host, which gives the subscription a whole physical server that hosts only that bank's VMs
D: An availability set with three fault domains, which places the bank's VMs on separate racks in the datacenter
K: C
G: ## What a dedicated host is
Azure Dedicated Host provides a **physical server** assigned to one Azure subscription. You create a **host group** (in a region, and optionally an availability zone with a fault domain count), add hosts to it, and place VMs on those hosts. Each host runs VMs of one size series.
## Benefits Learn lists
- **Security**: hardware isolation at the physical server level; no other customer's VMs are placed on your hosts.
- **Reliability**: you can opt in to a maintenance window for platform-initiated maintenance.
- **Cost**: Azure Hybrid Benefit lets you bring Windows Server and SQL Server licenses.
- **Performance**: you decide which workloads share the host's memory and storage.
## High availability still needs design
A host is one server. For resilience you deploy VMs across at least two hosts, using fault domains inside a host group and one host group per availability zone.
W: Azure Dedicated Host: it is the only option here that reserves an entire physical server for one subscription, so no other customer's VM lands on it, and it offers an opt-in maintenance window.
X: A=Confidential VMs: they protect data in use with a hardware-enforced boundary against the host and hypervisor, but they still run on shared multitenant servers and do not give a maintenance window.
B=Flexible scale set across zones: zones spread VMs for availability, yet each VM still runs on shared hosts. Nothing in a scale set reserves hardware for one customer.
D=Availability set with fault domains: fault domains separate the bank's own VMs across racks to survive hardware failures. Other customers' VMs can still share those physical servers.
T: "No other tenant on my physical server" plus maintenance control means Azure Dedicated Host; confidential VMs protect memory, availability options protect uptime.
V: Azure Dedicated Host, Azure Virtual Machines

@ AZ-305 D4 T4.1 advanced tradeoff
S: A company runs a fleet of VMs for a stateless web tier. It wants a mix of Spot and regular instances in one scale set, spread automatically across availability zones, while still managing instances with the standard VM APIs. Which design should you recommend?
A: A Virtual Machine Scale Set with Uniform orchestration and a single placement group set across all three zones
B: Individual VMs in an availability set, with a runbook that creates Spot VMs whenever the average CPU is high
C: Two Azure Dedicated Host groups, one for regular VMs and one for Spot VMs, each pinned to its own zone
D: A Virtual Machine Scale Set with Flexible orchestration, which Microsoft recommends for new scale sets
K: D
G: ## Scale set orchestration modes
A Virtual Machine Scale Set manages a group of VMs as one resource. It has two orchestration modes:
- **Flexible orchestration** (recommended): the instances are standard Azure IaaS VMs, so you manage them with the normal VM APIs. Azure spreads them across availability zones or fault domains. It can mix operating systems, and with max spreading it can mix **Spot and on-demand** instances and different VM sizes.
- **Uniform orchestration**: the scale set creates identical "child" VMs from one model, managed through scale set APIs.
## Why mix Spot and regular instances
A web tier can keep a base of regular instances for guaranteed capacity and add cheaper Spot instances for extra throughput. If Spot capacity is evicted, the regular base keeps serving.
W: Flexible orchestration scale set: Learn names it the recommended mode, it spreads instances across zones, manages them as standard VMs, and supports mixing Spot and on-demand instances in one scale set.
X: A=Uniform orchestration: Uniform mode builds identical child instances from one scale set model and manages them through scale set APIs, which is the opposite of the "standard VM APIs" requirement.
B=Availability set with a runbook: availability sets spread VMs across racks in one datacenter, not across zones, and a hand-built runbook replaces the autoscale and instance management a scale set provides.
C=Two dedicated host groups: host groups reserve whole physical servers at full price. They do not host Spot capacity and add cost and management instead of an automatic mix.
T: New scale sets should use Flexible orchestration: standard VM APIs, zone spreading and Spot plus on-demand in one set.
V: Virtual Machine Scale Sets, Azure Virtual Machines

@ AZ-305 D4 T4.1 applied use-case
S: A healthcare company must process patient records on Azure VMs while keeping the data protected in memory from the hypervisor and host administrators. The application should move without code changes. Which compute option should you recommend?
A: Azure Dedicated Host with automatic VM placement, so that the records run on hardware that only the company uses
B: Azure confidential VMs, which use a hardware-enforced boundary and attestation to protect the VM's memory and state
C: Standard VMs with Azure Disk Encryption turned on, so the operating system and data disks are encrypted at rest
D: Trusted launch VMs with Secure Boot and a virtual TPM, so that boot kits and rootkits cannot load at VM startup
K: B
G: ## Three states of data
Data is protected **at rest** (disk encryption), **in transit** (TLS) and **in use** (while it sits in memory being processed). Confidential computing targets the last one.
## Azure confidential VMs
Confidential VMs create a hardware-enforced boundary between the workload and the virtualization stack, so the hypervisor and host management code cannot read the VM's memory. Learn lists:
- Hardware-based isolation between VMs, hypervisor and host management code.
- Attestation policies that validate the platform before the workload starts.
- Optional confidential OS disk encryption bound to the VM's virtual TPM.
Many applications move **without code changes**, because protection is applied to the whole VM. The DC and EC families are the confidential versions of the D and E families.
W: Confidential VMs: they are designed to protect data in use from the host and hypervisor, with attestation before boot, and they lift existing applications without code changes.
X: A=Dedicated Host: a dedicated host keeps other customers off the server, but the host and hypervisor still see VM memory as usual, so data in use is not protected from host administrators.
C=Azure Disk Encryption: disk encryption protects data at rest on the OS and data disks. Once the records are loaded into memory they are not covered.
D=Trusted launch: Trusted launch protects the boot chain against boot kits and rootkits. It does not isolate the running VM's memory from the virtualization stack.
T: Protecting data in use from the host and hypervisor calls for confidential VMs (DC/EC families); disk encryption covers data at rest only.
V: Azure confidential computing, Azure Virtual Machines

@ AZ-305 D4 T4.1 applied use-case
S: A small business runs a line-of-business web server that sits near idle most of the day and has short CPU spikes when staff log in each morning. The owner wants the cheapest VM family that still handles the spikes. Which VM family should you recommend?
A: The F-family compute optimized sizes, since a higher CPU-to-memory ratio absorbs the morning login spike easily
B: The D-family general purpose sizes, sized for the morning peak so that every core is available all day long
C: The B-family burstable sizes, which build up CPU credits while idle and spend them during short bursts of load
D: The E-family memory optimized sizes, since a larger memory cache serves repeated logins without using more CPU
K: C
G: ## Burstable VMs
The **B-family** is a general purpose family Learn describes as low-cost burstable VMs. They use a **CPU credit model**:
- Each size has a baseline CPU level. While the VM runs below that baseline, it accumulates credits.
- When load rises, the VM spends credits to run above the baseline, up to the full vCPU capacity.
- If the credits run out, performance drops back to the baseline.
## When they fit
B-series sizes fit workloads with low average CPU and occasional short bursts: small web servers, dev/test machines, small databases. They are a poor fit for sustained high CPU, because the credits drain and the VM is throttled to its baseline.
W: B-family burstable: a server that is idle most of the day earns credits and spends them on the short morning spike, so it costs less than a size reserved for the peak all day.
X: A=F-family compute optimized: these sizes deliver full CPU all the time at a higher CPU-to-memory ratio. Paying for that capacity all day is wasteful for a near-idle server.
B=D-family sized for the peak: a D-family size fits balanced workloads, but sizing it for a brief peak means paying for cores that sit unused for most of the day.
D=E-family memory optimized: the bottleneck is a short CPU spike, not memory. Extra RAM per vCPU adds cost without addressing the burst.
T: Low average CPU with short spikes fits the burstable B-family; sustained high CPU does not, because credits run out.
V: Azure Virtual Machines

@ AZ-305 D4 T4.1 applied use-case
S: An architecture firm will give designers GPU-accelerated remote desktops for CAD and 3D modelling through Azure Virtual Desktop. Which VM size family should you recommend for the session hosts?
A: The HC-family high performance compute sizes, which target finite element analysis with dense CPU cores
B: The M-family memory optimized sizes, which offer the largest memory configurations for very big databases
C: The L-family storage optimized sizes, which provide high local disk throughput for large design files
D: The NV-family GPU accelerated sizes, which Learn lists for virtual desktop and visualization workloads
K: D
G: ## GPU VM families
Learn groups GPU VMs into several families, each aimed at a workload:
- **NC**: compute-intensive, graphics-intensive and visualization work, often AI training and inference.
- **ND**: large memory compute-intensive work such as training big models.
- **NV** and **NG**: virtual desktop (VDI) workloads, where users need a GPU for graphics in a remote session.
## Designing GPU desktops
For Azure Virtual Desktop, the session host size decides what each user can do. Designers working in CAD and 3D tools need a GPU to render the viewport, so the host pool should use a VDI-oriented GPU family. CPU-only HPC or memory families give no graphics acceleration.
W: NV-family: it is the GPU family Learn lists for virtual desktops, giving each designer GPU-accelerated graphics in the Azure Virtual Desktop session.
X: A=HC-family HPC: HC sizes are CPU-based HPC nodes for finite element analysis and molecular dynamics. They have no GPU for interactive graphics.
B=M-family memory optimized: the M-family targets extremely large databases with huge RAM. It provides no graphics acceleration for CAD sessions.
C=L-family storage optimized: L sizes give high local disk throughput for NoSQL and big data stores, not GPU rendering for remote desktops.
T: GPU-accelerated virtual desktops point to the NV (or NG) family; NC and ND target GPU compute such as AI training.
V: Azure Virtual Desktop, Azure Virtual Machines

@ AZ-305 D4 T4.1 advanced use-case
S: A call center will give 600 shift workers the same set of desktop apps through Azure Virtual Desktop. Costs must stay low, and each worker's settings must follow them to whichever session host they land on. Which TWO design choices should you recommend? (Select TWO)
A: A pooled host pool, so several users share each session host and sessions are load balanced across hosts
B: FSLogix profile containers stored on Azure Files in the same region as the session host VMs
C: A personal host pool, so that each worker is assigned a dedicated session host for every shift
D: User profiles kept on the OS disk of each session host, backed up nightly with Azure Backup
E: FSLogix profile containers stored in an Azure Blob Storage container in a paired region
K: A,B
G: ## Host pool types
A host pool is a set of session host VMs registered to Azure Virtual Desktop. It is one of two types:
- **Personal**: each session host is assigned to one user. Good for dedicated desktops and data separation; the user's profile can live on the VM's OS disk.
- **Pooled**: user sessions are load balanced to any host (breadth-first or depth-first), and many users share each host. Learn notes this gives lower costs and greater efficiency. Because a user can land on a different host each time, profiles must roam.
## FSLogix profile containers
FSLogix stores the whole user profile in a VHD(X) file that is attached at sign-in, so the profile looks local on any host. Learn's best practices:
- Store profile containers on **Azure Files** or **Azure NetApp Files**.
- Keep the storage account in the **same region** as the session host VMs.
W: A=Pooled host pool: many shift workers sharing each host is what keeps cost low, and they all use the same apps, so dedicated machines add nothing.
B=FSLogix on Azure Files: profiles roam to whichever host a worker lands on, and Learn recommends Azure Files in the same region as the session hosts.
X: C=Personal host pool: one VM per worker is the costly option meant for dedicated desktops. It contradicts the low-cost goal for 600 identical workers.
D=Profiles on the OS disk: in a pooled pool a worker may connect to a different host each shift, so a profile on one host's disk does not follow them.
E=Blob Storage in a paired region: FSLogix profile containers are recommended on Azure Files or Azure NetApp Files, and the storage must be in the same region as the hosts to avoid sign-in latency.
T: Many users with the same apps at low cost means a pooled host pool, with FSLogix profile containers on Azure Files (or NetApp Files) in the session hosts' region.
V: Azure Virtual Desktop, Azure Files

@ AZ-305 D4 T4.1 applied comparison
S: A software team needs persistent Windows desktops where each developer installs tools with admin rights and keeps them between sessions. Machines should start on demand and deallocate when unused. Which Azure Virtual Desktop design should you recommend?
A: A pooled host pool using depth-first load balancing, so that each session host fills up before the next one starts
B: A personal host pool with each developer assigned a session host, using Start VM on Connect and autoscale
C: A pooled host pool with a validation environment, so that new tools are tested before reaching the production hosts
D: A RemoteApp application group in a pooled host pool, so that each developer launches tools rather than full desktops
K: B
G: ## Personal versus pooled desktops
- In a **personal** host pool each user is assigned to one session host and always returns to it. Learn says this optimizes for performance and data separation, and the user's profile can stay on the VM's OS disk. Hosts are updated like normal PCs (Windows Update, Configuration Manager).
- In a **pooled** host pool users share hosts and can land on a different host each time. Hosts are updated by redeploying from new images, so per-user installs do not persist.
## Keeping cost down for personal desktops
Autoscale for personal host pools starts VMs on a schedule or with **Start VM on Connect**, and deallocates or hibernates them based on session state (sign-out or disconnect). The developer gets a dedicated machine that does not run all night.
W: Personal host pool with Start VM on Connect: each developer keeps one dedicated host with their own installed tools, and autoscale starts it on connection and deallocates it when the session ends.
X: A=Pooled with depth-first: depth-first only decides how sessions fill the shared hosts. Developers still share hosts and can land on a different one, so their installs do not persist.
C=Pooled with a validation environment: a validation environment previews Azure Virtual Desktop service updates before production. It does not give anyone a persistent personal machine.
D=RemoteApp group in a pooled pool: RemoteApp publishes individual applications instead of a desktop, on shared hosts, so users cannot install and keep their own tools.
T: Persistent per-user desktops with admin installs need a personal host pool; Start VM on Connect and autoscale keep those dedicated VMs from running when idle.
V: Azure Virtual Desktop

@ AZ-305 D4 T4.1 applied comparison
S: A startup is building a dozen containerised microservices that scale on HTTP traffic and on Service Bus queue length, including to zero when idle. The team has no Kubernetes skills and does not need the Kubernetes API. Which hosting service should you recommend?
A: Azure Kubernetes Service with the cluster autoscaler, so that node pools grow and shrink as the services get busier
B: Azure Container Instances, creating one container group per microservice and adding more groups during busy periods
C: Azure Container Apps, which runs the microservices with KEDA-based event scaling, service discovery and scale to zero
D: Azure App Service on a Premium plan, deploying each microservice as a container web app with autoscale rules on CPU
K: C
G: ## Azure container hosting options
Learn compares the main ways to run containers:
- **Azure Container Apps**: serverless microservices and jobs, built on Kubernetes, Dapr, KEDA and Envoy. It scales on traffic and on event sources such as queues, **including to zero**, and has service discovery and traffic splitting. It does **not** expose the Kubernetes API.
- **Azure Kubernetes Service (AKS)**: a managed Kubernetes cluster with full access to the Kubernetes API; you own cluster configuration and operations (less so with AKS Automatic).
- **Azure Container Instances (ACI)**: a single pod of Hyper-V isolated containers on demand, a low-level building block with no built-in scale, load balancing or certificates.
- **Azure App Service**: optimized for web apps and APIs, deployed as code or containers.
## Choosing
Many teams start microservices on Container Apps; they pick AKS only when they need the Kubernetes API and control plane.
W: Azure Container Apps: it is designed for container microservices, scales on HTTP and queue events through KEDA down to zero, and hides Kubernetes from a team that does not need it.
X: A=AKS with cluster autoscaler: AKS gives the full Kubernetes API the team does not need, and the team would still have to design and operate the cluster, which it lacks the skills for.
B=Container Instances: ACI has no built-in scaling or event triggers; to scale you create more container groups yourself, and there is no service discovery between microservices.
D=App Service Premium plan: App Service is optimized for web apps and scales on metrics such as CPU. It does not scale on queue length or down to zero instances.
T: Event-driven container microservices without the Kubernetes API fit Azure Container Apps; need the Kubernetes API or control plane, choose AKS.
V: Azure Container Apps, Azure Kubernetes Service, Azure Container Instances

@ AZ-305 D4 T4.1 advanced comparison
S: A platform team must run third-party software delivered as Helm charts that installs custom resource definitions and Kubernetes operators, and the team needs direct access to the Kubernetes API. Which hosting service should you recommend?
A: Azure Container Apps with Dapr enabled, so that the vendor's components communicate through managed sidecars
B: Azure Kubernetes Service, which supports direct access to the Kubernetes API and can run any Kubernetes workload
C: Azure App Service for Containers, deploying each chart's images as separate web apps behind one custom domain
D: Azure Container Instances in a virtual network, deploying each chart's containers as an individual container group
K: B
G: ## When the Kubernetes API matters
Some software is packaged for Kubernetes itself: Helm charts that create **custom resource definitions (CRDs)**, **operators** that watch those resources, admission webhooks or cluster-wide controllers. These need a real cluster and its API server.
## What each service exposes
- **AKS** supports direct access to the Kubernetes API and can run any Kubernetes workload. It comes as AKS Standard (you manage cluster configuration) or AKS Automatic (Azure handles node management, scaling and upgrades).
- **Azure Container Apps** is built on Kubernetes but does not provide access to the Kubernetes APIs; Learn says to use AKS if you need them.
- **App Service** and **Container Instances** run containers but have no Kubernetes control plane at all.
W: Azure Kubernetes Service: CRDs, operators and Helm charts need the Kubernetes API, and AKS is the Azure service that gives direct API access and runs any Kubernetes workload.
X: A=Container Apps with Dapr: Container Apps hides the Kubernetes API, so the operators and CRDs cannot be installed. Dapr sidecars help service-to-service calls but do not change that.
C=App Service for Containers: App Service runs container images as web apps. It has no Kubernetes API, so Helm charts with operators cannot be installed at all.
D=Container Instances in a virtual network: ACI runs container groups on demand with no Kubernetes control plane, so nothing would reconcile the vendor's custom resources.
T: Need CRDs, operators or the Kubernetes API itself → AKS; Container Apps runs on Kubernetes but does not expose its API.
V: Azure Kubernetes Service, Azure Container Apps

@ AZ-305 D4 T4.1 applied use-case
S: A finance team has a containerised script that builds reports every night at 02:00, runs for about 40 minutes and then exits. It should cost nothing between runs and share networking and logging with the team's existing container apps. Which solution should you recommend?
A: A Container Apps job using the Schedule trigger type with a cron expression, in the existing Container Apps environment
B: A container app with a minimum of one replica that sleeps inside the container until 02:00 and then runs the script
C: An AKS CronJob on a new cluster with a dedicated node pool reserved for the nightly report workload each night
D: An App Service web app for containers with Always On enabled and a WebJob that triggers the script each night
K: A
G: ## Apps versus jobs in Azure Container Apps
Container Apps has two kinds of compute resources:
- **Apps** run continuously, such as HTTP APIs and background services; a failed container restarts automatically.
- **Jobs** start, run for a finite time and stop. Each execution does one unit of work.
Jobs have three trigger types: **Manual** (start on demand through the API), **Schedule** (a cron expression) and **Event** (for example, messages in a queue).
Learn's own example: "A process that generates financial reports nightly" maps to a job with the Schedule type and a cron expression.
## Shared environment
Apps and jobs run in the same Container Apps environment, so they share networking and logging. A job uses resources only while an execution runs.
W: Scheduled Container Apps job: a cron-triggered job runs the 40-minute script, stops when finished, and lives in the same environment as the team's apps, sharing their networking and logs.
X: B=Always-on container app: a minimum of one replica keeps a container running and billed all day just to wait for 02:00, which breaks the cost-nothing-between-runs goal.
C=AKS CronJob on a new cluster: a cluster and a reserved node pool run continuously for a single nightly task, and they sit outside the existing Container Apps environment.
D=App Service with Always On: Always On keeps the app's instance running around the clock, so the plan is billed all day for a job that needs 40 minutes.
T: Finite, scheduled container work belongs in a Container Apps job (Schedule trigger); apps are for services that run continuously.

G: ## Not every workload should move
CAF's migration strategies include two that do not move the workload to Azure:
- **Retire**: decommission workloads with limited business value, or where migration costs outweigh the benefits. Confirm there are no critical dependencies first.
- **Retain**: keep the workload as it is. The business driver is "need stability and no change"; indicators are a workload that is stable, compliant and meets business needs, no near-term driver to move, and low ROI from migration.
## Revisiting later
A retained workload is reviewed again when something changes: hardware end of life, a new compliance need or a new business driver. Rationalization is about choosing the right strategy per workload, not moving everything.
