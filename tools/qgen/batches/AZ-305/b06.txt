@ AZ-305 D3 T3.1 advanced tradeoff
S: A company runs an order-processing app on Azure VMs in one region. After a regional outage the app must run in another region within two hours, losing at most a few minutes of data. Which solution should you recommend?
A: Azure Site Recovery replicating the VMs continuously to a second region, with a recovery plan used to fail the app over
B: Azure Backup with a geo-redundant Recovery Services vault and Cross Region Restore enabled for all the app's VMs
C: Azure Backup with the Enhanced policy taking VM backups every four hours and keeping the snapshots for 30 days
D: Azure Disk Backup taking several incremental snapshots per day of every OS and data disk attached to the VMs
K: A
G: ## RPO and RTO drive the choice
- **Recovery point objective (RPO)**: how much data, measured in time, you can afford to lose.
- **Recovery time objective (RTO)**: how long the workload may be down before it runs again.
Backup and disaster recovery answer different questions. Backup keeps restorable copies for weeks or years; disaster recovery keeps a running copy close to current so you can switch over quickly.
## Azure Site Recovery
Site Recovery provides **continuous replication** for Azure VMs to a secondary region. When the primary region fails you fail over: Azure creates the VMs from the replicated data, and a recovery plan starts them in the right order. RPO is typically minutes and RTO is the time to boot the VMs and run the plan.
## Azure Backup across regions
With a geo-redundant vault and Cross Region Restore (CRR), Azure VM backups can be restored in the paired region. Learn notes the secondary-region RPO for VM backups can be **up to 36 hours** in the worst case (daily vaulting plus replication lag), and a restore must rebuild every disk from the vault.
## Example
An app with a 5-minute RPO and 2-hour RTO needs Site Recovery; a reporting server that can lose a day of data and be down a day can rely on backups with CRR.
W: Site Recovery: continuous replication keeps the secondary copy minutes behind the primary, and a recovery plan brings the app up in the target region well inside a two-hour window.
X: B=Backup with Cross Region Restore: the secondary copy depends on daily vaulting and asynchronous geo-replication, so the worst-case RPO is many hours, not minutes, and restoring every VM from the vault is slow.
C=Enhanced policy every four hours: the policy shortens the interval to four hours at best, and its snapshots stay in the primary region, so they do not help when that region is down.
D=Disk Backup: disk snapshots are crash-consistent copies kept in the same region; they neither meet a minutes-level RPO nor rebuild the VMs in another region.
T: Minutes of RPO and hours of RTO for VMs across regions point to Azure Site Recovery, not to backup and restore.
V: Azure Site Recovery, Azure Backup

@ AZ-305 D3 T3.1 applied use-case
S: A bank runs VMs in an Azure region with availability zones in its home country; the country has no second Azure region. Regulators require that data never leave that region. The VMs must recover from a zone failure. What should you recommend?
A: Azure Backup with a geo-redundant Recovery Services vault and Cross Region Restore enabled for each of the VMs
B: Azure Site Recovery zone-to-zone disaster recovery that replicates each VM to another zone in the same region
C: Azure Site Recovery replication of each VM to the nearest Azure region in a neighboring country as the DR site
D: An availability set for each tier so that the VMs are spread across fault domains inside the same datacenter
K: B
G: ## Zone-to-zone disaster recovery
Azure Site Recovery can replicate, fail over and fail back Azure VMs **from one availability zone to another inside the same region**. Microsoft recommends it as the disaster recovery option for protecting applications from zone failures within a region.
## Data residency
Learn states that with zone-to-zone disaster recovery, Site Recovery **doesn't move or store data out of the region** where it is deployed. The Recovery Services vault holds only metadata, not customer data. Zone-to-zone DR is supported in a listed set of regions, so confirm the region is on that list.
## Region pairs are not automatic DR
Geo-redundant options (GRS vaults, cross-region replication) copy data to another region by design, which a residency rule forbids. Many newer regions are nonpaired and rely on availability zones for resilience.
## Example
A VM in zone 1 replicates to zone 2. If zone 1 fails, the operator fails over and the VM starts in zone 2 with its replicated disks, all inside the same region.
W: Zone-to-zone Site Recovery: replicating to a different zone of the same region protects against a zone outage while keeping all replicated data inside the region, as the regulator requires.
X: A=Geo-redundant vault with Cross Region Restore: GRS copies the backup data to a secondary region, which breaks the residency rule, and a restore from backup is far slower than a failover.
C=Replication to a neighboring country: the replicated disks would live in a foreign region, which is exactly what the regulator prohibits.
D=Availability sets: fault domains spread VMs across racks in one datacenter, so a zone failure still takes them all down; they are a high-availability feature, not a recovery solution.
T: When data must stay in one region but VMs must survive a zone failure, use Site Recovery zone-to-zone disaster recovery.
V: Azure Site Recovery

@ AZ-305 D3 T3.1 applied comparison
S: A company is standardizing on Azure Backup and wants to place each workload in the correct vault type. Which TWO workloads are protected by using a Recovery Services vault? (Select TWO)
A: SQL Server databases running inside Azure virtual machines, backed up with the workload-aware SQL backup
B: Azure Files shares in a general-purpose storage account, backed up with snapshot or vaulted backup
C: Azure managed disks protected with Azure Disk Backup using scheduled incremental snapshots per disk
D: Azure Blob Storage block blobs protected with vaulted backup on a schedule set by the backup policy
E: Azure Kubernetes Service clusters protected with the Backup extension and their persistent volumes
K: A,B
G: ## Two vault types
Azure Backup uses two kinds of vault, and you create the one that matches the data source.
- **Recovery Services vault**: Azure VMs, SQL Server in Azure VMs, SAP HANA in Azure VMs, Azure Files shares, and on-premises workloads through the MARS agent, Azure Backup Server (MABS) and System Center DPM. It is also the vault for Azure Site Recovery.
- **Backup vault**: the newer workloads such as Azure Blob Storage, Azure Disk Backup, Azure Database for PostgreSQL, and Azure Kubernetes Service (AKS).
## Design impact
Both vault types support immutability, soft delete and multiuser authorization, but policies and monitoring live in the vault of the workload. A design that protects VMs, file shares and blobs usually needs both kinds.
## Example
A landing zone has one Recovery Services vault for VMs, SQL in VMs and file shares, and one Backup vault for blobs, managed disks and AKS, per region.
W: A=SQL Server in Azure VMs: the stream-based SQL backup for databases in Azure VMs is managed from a Recovery Services vault.
B=Azure Files shares: file share backup, both the snapshot tier and the vaulted tier, is configured from a Recovery Services vault.
X: C=Azure Disk Backup: the disk snapshot solution is one of the newer workloads that is configured in a Backup vault.
D=Blob vaulted backup: operational and vaulted backups for blobs use a Backup vault, not a Recovery Services vault.
E=AKS backup: the Backup extension in the cluster works with a Backup vault, which also needs Trusted Access to the cluster.
T: Recovery Services vaults hold VMs, SQL/SAP HANA in VMs, Azure Files and on-premises agents; Backup vaults hold blobs, disks, PostgreSQL and AKS.
V: Azure Backup

@ AZ-305 D3 T3.1 advanced use-case
S: After a ransomware attack at a peer company, you must ensure that nobody, including a vault administrator, can delete VM recovery points before their retention ends, and that this protection itself can never be turned off. What should you recommend?
A: Increase the soft-delete retention of the Recovery Services vault to 180 days so deleted recovery points stay recoverable
B: Protect the vault with multiuser authorization through a Resource Guard owned by the security operations team
C: Enable immutability on the Recovery Services vault and then lock it so that the setting becomes irreversible
D: Encrypt the backup data with customer-managed keys kept in a Key Vault that the backup team cannot access
K: C
G: ## Immutable vault
An immutable vault **blocks operations that could lead to the loss of recovery points**, such as deleting them early or reducing retention, for every item in the vault. It is available for Recovery Services vaults and Backup vaults.
Immutability has three states:
- **Disabled**: nothing is blocked.
- **Enabled**: risky operations are blocked, but an administrator can disable the setting again.
- **Enabled and locked**: the setting is **irreversible**. Azure Backup also uses WORM (write once, read many) storage where available so malicious actors cannot turn immutability off and delete backups.
## Related controls
- **Soft delete** keeps deleted backup data for 14 days by default (up to 180) so you can undelete it, but deletion itself is still allowed.
- **Multiuser authorization (MUA)** requires approval on a Resource Guard for critical operations; whoever holds rights on the Resource Guard can still approve them.
## Example
A team first enables immutability, checks that daily operations still work, and then locks it.
W: Locked immutable vault: immutability blocks deletion of recovery points before expiry for all items, and locking makes the setting irreversible, so not even a vault administrator can switch it off.
X: A=Longer soft delete: soft delete only delays permanent removal of data that has already been deleted; the deletion is still allowed, and the data is gone once the soft-delete window ends.
B=Multiuser authorization: Resource Guard adds an approval step, but an authorized user on the Resource Guard can still approve the deletion, and the protection can be removed with that approval.
D=Customer-managed keys: CMK controls who can decrypt backup data; it does not stop anyone with vault rights from deleting recovery points.
T: To make recovery points undeletable before expiry by anyone, enable immutability on the vault and lock it.
V: Azure Backup

@ AZ-305 D3 T3.1 applied use-case
S: Backup administrators manage several Recovery Services vaults. Security policy says a single compromised backup admin account must not be able to disable soft delete or shorten retention without approval from the security team. What should you recommend?
A: Require backup admins to activate the Backup Contributor role through Privileged Identity Management with approval
B: Associate the vaults with a Resource Guard in a separate subscription that only the security team can manage
C: Enable immutability on every vault and leave it unlocked so the security team can still turn it off when needed
D: Create a custom Azure role for backup admins that removes the permission to delete backup items from vaults
K: B
G: ## Multiuser authorization with Resource Guard
Multiuser authorization (MUA) adds a second authorization check for **critical operations** on Recovery Services vaults and Backup vaults. The check uses a separate Azure resource, the **Resource Guard**.
- To run a protected operation, the user needs permissions on the vault **and** on the Resource Guard.
- A different user or team must own the Resource Guard, and vault admins must not hold Contributor or Backup MUA roles on it.
- Placing the Resource Guard in another subscription or tenant gives stronger separation.
## Which operations are protected
Disabling soft delete and removing MUA protection are mandatory. Others, on by default, include modifying a policy to reduce retention or lower backup frequency, deleting protection, disabling immutability and modifying encryption settings.
## Example
The security team owns `rg-guard` in its own subscription. When a backup admin tries to shorten retention, the request fails until a security team member grants time-bound access on the Resource Guard.
W: Resource Guard in a separate subscription: critical operations such as disabling soft delete or reducing retention now also need rights on the Resource Guard, which only the security team holds, so one compromised admin account is not enough.
X: A=PIM for Backup Contributor: just-in-time activation limits when the role is active, but once activated the same admin performs every critical operation alone.
C=Unlocked immutability: immutability blocks loss of recovery points, but it does not block disabling soft delete, and an unlocked setting can be disabled by any vault admin.
D=Custom role without delete: removing one permission does not cover policy changes that reduce retention or disabling soft delete, and an admin who can manage roles can restore it.
T: Use multiuser authorization with a Resource Guard owned by a different team so critical backup operations need a second party.
V: Azure Backup, Resource Guard

@ AZ-305 D3 T3.1 applied tradeoff
S: A security review finds that attackers often stay undetected for months before deleting backups. The company wants backup data deleted from its vaults to remain recoverable for about six months after deletion. What should you recommend?
A: Switch the vaults to geo-redundant storage and enable Cross Region Restore so a second copy exists elsewhere
B: Use the Enhanced VM policy and keep snapshot-tier recovery points for the maximum of 30 days on every VM
C: Raise the soft-delete retention period of each vault from the 14-day default to 180 days for deleted data
D: Turn on long-term retention in each backup policy with monthly recovery points kept for seven years
K: C
G: ## Soft delete in Azure Backup
Soft delete is **on by default** for Recovery Services vaults and Backup vaults. When backup data is deleted, it is kept in a soft-deleted state and can be undeleted.
- Default retention: **14 days**, at no extra cost.
- Configurable: **14 to 180 days**. Days beyond 14 are charged at normal backup rates.
- Learn notes that longer durations help recover from threats that take time to identify, such as advanced persistent threats.
- The retention active at the time of deletion governs how long that item stays soft-deleted.
## Retention versus soft delete
Policy retention controls how long recovery points are kept while protection runs. Soft delete controls how long data survives after someone deletes it. An attacker who deletes protection removes all recovery points at once, whatever the policy retention was.
## Example
With 180-day soft delete, backups deleted on 1 March can still be restored at the end of August.
W: 180-day soft delete: extending soft-delete retention to its maximum keeps deleted backup data recoverable for six months, covering attacks that are discovered late.
X: A=Geo-redundant storage with CRR: the secondary copy mirrors the vault, so data deleted in the vault is deleted from the secondary copy too.
B=Enhanced policy snapshots: snapshot-tier retention only sets how long instant restore points are kept; it does not keep data after someone deletes the backups.
D=Long retention in the policy: long policy retention keeps recovery points while protection exists, but an attacker who deletes the backup data removes them regardless of their planned retention.
T: To recover backups deleted long before the attack is noticed, extend vault soft-delete retention up to 180 days.
V: Azure Backup

@ AZ-305 D3 T3.1 applied use-case
S: Auditors require a company to prove, at any time and without waiting for Microsoft to declare an outage, that its daily Azure VM backups can be restored in the secondary region. Which design should you recommend?
A: A Recovery Services vault with geo-redundant storage and Cross Region Restore enabled at the vault level
B: A Recovery Services vault with zone-redundant storage, restoring the VMs into another availability zone
C: A second Recovery Services vault in the secondary region that receives a copy of each VM backup every night
D: A Recovery Services vault with geo-redundant storage, relying on its default replication to the paired region
K: A
G: ## Vault storage redundancy
A Recovery Services vault stores data as LRS, ZRS or GRS. The replication type can be changed only **before** backups are stored in the vault.
- **GRS** replicates vault data to the Azure paired region.
- Without Cross Region Restore, the secondary copy is only used if Microsoft declares a disaster for the primary region.
## Cross Region Restore (CRR)
CRR is enabled at the vault level on a GRS vault. It lets you **restore in the secondary region any time you choose**, for audit and compliance tests or during an outage, without waiting for a disaster declaration. Only vault-tier data is replicated (snapshots are not), so secondary restores take about as long as vault-tier restores in the primary region.
## Backups are regional
A vault protects VMs in its own region; Azure Backup cannot back up to a vault in another region, and backup data cannot be moved between vaults.
## Example
A team enables CRR on `rsv-weu` (GRS) and restores a VM in the paired region every quarter as an audit drill.
W: GRS vault with Cross Region Restore: CRR gives the customer control to restore replicated recovery points in the paired region whenever needed, which is what the audit asks for.
X: B=Zone-redundant vault: ZRS keeps data in one region, so it supports restores into another zone, not into a secondary region.
C=Second vault in the secondary region: Azure Backup backs up VMs only to a vault in their own region, and recovery points cannot be copied between vaults.
D=GRS without CRR: the secondary copy exists, but it can only be used after Microsoft declares a disaster, so the company cannot prove restorability on demand.
T: To restore VM backups in the paired region at will, use a GRS vault with Cross Region Restore enabled.
V: Azure Backup

@ AZ-305 D3 T3.1 applied use-case
S: A company deploys Trusted Launch VMs with Premium SSD v2 disks. It needs whole-VM and file-level restores, several backups per day, and zone-resilient instant restore snapshots. Which backup approach should you recommend?
A: Azure VM backup in a Recovery Services vault with the Standard policy plus on-demand backups taken during the day
B: Azure Disk Backup in a Backup vault with a policy that takes several incremental snapshots of each disk per day
C: Azure VM backup in a Recovery Services vault with the Enhanced policy scheduled every four hours on each VM
D: The MARS agent installed in each VM, backing up its volumes and system state to the vault three times a day
K: C
G: ## Standard and Enhanced VM backup policies
Azure VM backup in a Recovery Services vault offers two policy types.
- **Standard**: one scheduled backup per day.
- **Enhanced**: multiple backups per day (as often as **every 4 hours**), zone-redundant storage for instant restore snapshots, up to 30 days of snapshot-tier retention, and support for newer offerings such as **Trusted Launch VMs, Premium SSD v2 and Ultra Disks**.
After a VM is protected with the Enhanced policy, it cannot be switched back to Standard.
## VM backup versus Disk Backup
VM backup restores whole VMs, individual disks or files, and can be app-consistent. Azure Disk Backup takes crash-consistent incremental snapshots of single disks without an agent, but it cannot restore a whole VM or individual files.
## Example
A policy with an hourly schedule of `every 4 hours` gives six recovery points a day per VM, each restorable as a full VM or as files.
W: Enhanced VM policy: it is required for Premium SSD v2 and supports Trusted Launch VMs, schedules backups as often as every four hours, keeps snapshots zone resilient, and still gives full-VM and file-level restore.
X: A=Standard policy with on-demand backups: the Standard policy doesn't protect Premium SSD v2 disks, and manual on-demand jobs are not a reliable schedule.
B=Disk Backup: per-disk snapshots are crash consistent and cannot restore a whole VM or single files, which the company needs.
D=MARS agent: MARS backs up files, folders and system state, not whole VMs, so a full-VM restore is not possible.
T: For several daily VM backups, Trusted Launch or Premium SSD v2/Ultra disks, use the Enhanced VM backup policy.
V: Azure Backup

@ AZ-305 D3 T3.1 advanced use-case
S: A two-node Windows Server Failover Cluster on Azure VMs writes to a shared managed disk. The line-of-business app doesn't support VSS, agents are not allowed, and the shared disk needs several backups per day. What should you recommend?
A: Azure Site Recovery replication of both cluster nodes to a second region using crash-consistent recovery points
B: Azure VM backup with the Enhanced policy for both nodes, scheduled every four hours with all their disks included
C: Azure Disk Backup in a Backup vault with a policy that takes several incremental snapshots of the shared disk per day
D: The MARS agent installed on the active cluster node, backing up the shared disk's volume three times a day
K: C
G: ## Azure Disk Backup
Azure Disk Backup automates **incremental snapshots of managed disks** on a schedule and keeps them for the configured retention, in a Backup vault.
- **Agentless** and **crash-consistent**: no extension, no scripts, no impact on app performance.
- **Multiple backups per day**.
- Supports OS and data disks, **including shared disks**, attached or not.
Learn lists clusters writing to shared disks, agent restrictions and apps without VSS support as typical reasons to choose it.
## Limits of VM backup here
Azure VM backup is the choice when you need app-consistent backups, whole-VM restore or file restore. The Enhanced policy can exclude shared disks and back up the other disks, but it doesn't back up the shared disk itself.
## Example
A disk backup policy takes a snapshot of `disk-shared-01` every 4 hours and keeps them for 7 days, while the nodes' OS disks keep a daily VM backup.
W: Disk Backup: it backs up shared disks with agentless, crash-consistent incremental snapshots several times a day, which fits a cluster app that has no VSS support and cannot run agents.
X: A=Site Recovery replication: it is a disaster recovery tool for failing over VMs, not a backup with point-in-time restores of the disk, and it relies on the Mobility extension in the VMs.
B=Enhanced VM policy: the Enhanced policy supports excluding shared disks so the other disks can be protected; it doesn't back up the shared disk, and it relies on the VM backup extension.
D=MARS agent: it is an agent, which the policy forbids, and it is not designed to back up a clustered shared disk consistently.
T: For agentless, multiple-per-day backups of specific or shared managed disks, use Azure Disk Backup.
V: Azure Disk Backup

@ AZ-305 D3 T3.1 applied tradeoff
S: A media company stores irreplaceable assets as block blobs. It needs protection even if the whole storage account is deleted or compromised, with recovery points kept on a schedule for one year. What should you recommend?
A: Operational backup for blobs, which enables point-in-time restore, versioning and change feed in the source account
B: Vaulted backup for blobs in a Backup vault, which copies the data offsite on the schedule and retention in the policy
C: Blob soft delete and blob versioning on the account, both with retention set to the maximum number of days allowed
D: Object replication to a second storage account in the same subscription, with a lifecycle rule deleting old versions
K: B
G: ## Two blob backup tiers
Azure Backup protects blobs with a Backup vault in two ways.
- **Operational backup (continuous)**: a local solution. It turns on point-in-time restore, soft delete, versioning and change feed in the **source storage account** and adds a delete lock. Data stays in that account, so it doesn't survive the loss of the account.
- **Vaulted backup (periodic)**: a managed **offsite** solution. Data is copied to the Backup vault on the schedule in the policy and kept for the policy's retention, which protects against accidental or malicious deletion of blobs or the storage account.
New blob backup policies include vaulted backup by default and can combine it with operational backup.
## Example
A policy takes a daily vaulted backup kept for 12 months, plus 30 days of operational backup for quick point-in-time restores of individual blobs.
W: Vaulted backup: copies are stored in the Backup vault outside the source account, so a deleted or compromised account does not take the recovery points with it, and the policy keeps them for a year.
X: A=Operational backup: all its data stays inside the source account, so it protects against blob deletion or corruption but not against losing the account itself.
C=Soft delete and versioning: both live in the same account and are lost with it, and an attacker with account rights can change their settings.
D=Object replication: it copies changes as they happen, including unwanted changes from an attack, and it is not a scheduled backup with governed retention.
T: For offsite blob backups that survive storage account deletion, use vaulted backup in a Backup vault; operational backup stays in the source account.
V: Azure Backup, Azure Blob Storage

@ AZ-305 D3 T3.1 applied use-case
S: A firm keeps contracts in Azure Files shares. Backups must survive a malicious deletion of the storage account, support restore in another region, and be kept for ten years. What should you recommend?
A: Azure Files backup in a Recovery Services vault using the snapshot tier with daily and yearly retention rules
B: Azure Files backup in a Recovery Services vault using the vaulted tier, with long retention in the backup policy
C: Azure File Sync to an on-premises server with cloud tiering disabled so every file has a local full copy as well
D: Share soft delete on the storage account with the longest retention, plus share snapshots taken by a runbook
K: B
G: ## Snapshot tier and vaulted tier for Azure Files
Azure Files backup is managed from a **Recovery Services vault** and supports two tiers in one policy.
- **Snapshot tier**: share snapshots stored in the same storage account. Restores are instant, but the snapshots depend on the source account.
- **Vaulted tier (Vault-Standard)**: backup data is copied **offsite** into the vault. Learn describes it as protection against any type of data loss regardless of blast radius, with ransomware defence, **cross-region recovery** and compliance-ready long retention. Vaulted backup for Azure Files is generally available.
## Built-in safety
Azure Backup also turns on share soft delete at the storage account level and takes a lease on its snapshots to guard them against accidental deletion.
## Example
A policy keeps daily vaulted backups for 30 days and yearly recovery points for 10 years in a GRS vault with Cross Region Restore.
W: Vaulted tier: data is stored in the vault, independent of the storage account, can be restored in another region, and follows long daily to yearly retention rules.
X: A=Snapshot tier: share snapshots live in the source storage account, so deleting the account removes them, and they cannot be restored in another region.
C=Azure File Sync without tiering: sync replicates deletions and encryptions to the server, so it is not a point-in-time backup and it has no ten-year retention.
D=Share soft delete with scripted snapshots: both depend on the same storage account, and custom runbooks give no managed retention or cross-region restore.
T: For Azure Files backups that survive account loss and support cross-region restore, use the vaulted tier in a Recovery Services vault.
V: Azure Backup, Azure Files

@ AZ-305 D3 T3.1 applied use-case
S: SQL Server 2022 runs in an Always On availability group on Azure VMs. The business needs point-in-time restore of individual databases with an RPO of about 15 minutes and central retention management. What should you recommend?
A: Azure VM backup with the Enhanced policy every four hours, restoring the whole VM to recover a database
B: Azure Disk Backup of the data and log disks, taking incremental snapshots of each disk every hour instead
C: Azure Backup for SQL Server in Azure VMs, with frequent transaction log backups set in the backup policy
D: The MARS agent on each replica, backing up the folders that hold the database and log files three times a day
K: C
G: ## Azure Backup for SQL Server in Azure VMs
Azure Backup offers a **workload-aware** solution for SQL Server in Azure VMs, managed from a Recovery Services vault.
- Full, differential and **transaction log backups**; log backups can run as often as every 15 minutes, which Learn describes as a **15-minute RPO**.
- **Point-in-time restore** of individual databases to a chosen time.
- Awareness of Always On availability groups, central policies and long-term retention.
A snapshot-based option combines disk snapshots with log backups for large databases.
## Why VM-level copies are not enough
A VM backup or disk snapshot captures the whole server at intervals of hours. Restoring one database to 10:45 needs a log chain, which only a SQL-aware backup provides.
## Example
A policy takes a weekly full, daily differential and log backups every 15 minutes, and a DBA restores `Orders` to 10:45 on the secondary replica's server.
W: SQL Server in Azure VM backup: its log backups every 15 minutes and database-level point-in-time restore meet the RPO, and the policy manages retention centrally across the availability group.
X: A=Enhanced VM policy: four-hour VM snapshots give an RPO of hours and restore whole VMs, not one database to a chosen minute.
B=Disk Backup: crash-consistent disk snapshots have no transaction log chain, so they cannot restore a database to a specific point in time.
D=MARS agent on database files: copying live data and log files with a file agent does not give a consistent, point-in-time restorable database, and three runs a day misses the RPO.
T: For database-level point-in-time restore with a 15-minute RPO for SQL Server on Azure VMs, use Azure Backup's SQL Server in Azure VM workload backup.
V: Azure Backup, SQL Server on Azure VMs

@ AZ-305 D3 T3.1 applied use-case
S: An Azure SQL Database must support restore to any point in the last four weeks, and compliance requires the first full backup of each month to be kept for seven years. Which TWO actions should you recommend? (Select TWO)
A: Set the short-term point-in-time restore retention of the database to at least 28 days
B: Configure a long-term retention policy that keeps the monthly full backups for seven years
C: Protect the database with Azure Backup in a Recovery Services vault using a monthly policy
D: Export the database to a BACPAC file each month and store the files in an archive tier blob
E: Create an active geo-replication secondary and keep it in another region for seven years
K: A,B
G: ## Short-term retention (PITR)
Azure SQL Database takes full, differential and transaction log backups automatically. **Point-in-time restore (PITR)** works within the short-term retention period: **7 days by default, configurable from 1 to 35 days** (Basic: 1 to 7).
## Long-term retention (LTR)
LTR copies **full backups** to separate storage and keeps them for **up to 10 years**. A policy has four parameters:
- `W`: weekly backups and how long to keep them
- `M`: the first backup of each month and how long to keep it
- `Y`: one backup in the week given by `WeekOfYear`, and how long to keep it
LTR backups are restored as new databases and survive deletion of the logical server.
## Example
`PITR = 35 days`, `M = 7 years`: any minute in the last five weeks can be restored, and each month's first full backup is retained for seven years.
W: A=PITR retention of 28 days or more: short-term retention up to 35 days covers restores to any point in the last four weeks.
B=LTR with monthly retention: the `M` parameter copies the first full backup of each month and keeps it for the configured seven years, within the ten-year maximum.
X: C=Recovery Services vault backup: Azure Backup protects SQL Server in Azure VMs, not Azure SQL Database, which has its own automated backups and LTR.
D=Monthly BACPAC exports: an export is a logical copy that is not transactionally consistent unless taken from a copy, and it is a hand-built process rather than managed retention.
E=Active geo-replication: a readable secondary mirrors the current data, including mistakes, so it keeps no history of past monthly states.
T: Azure SQL Database: PITR (1-35 days) for recent points in time, long-term retention (up to 10 years) for weekly, monthly or yearly full backups.
V: Azure SQL Database

@ AZ-305 D3 T3.1 applied tradeoff
S: A small internal app uses a non-critical Azure SQL Database. If its region fails, a recovery time of several hours and the loss of recent changes are acceptable, and cost must be minimal. What should you recommend?
A: An auto-failover group with a secondary server in another region and a read-write listener for the app
B: Geo-restore from the default geo-redundant backup storage to a server in another region when needed
C: Zone-redundant backup storage for the database, restoring into a different zone during a regional event
D: Active geo-replication to a readable secondary database in the paired region with manual failover
K: B
G: ## Geo-restore
By default Azure SQL Database stores backups in **geo-redundant storage** replicated to the paired region. **Geo-restore** creates a new database on any server in any region from the most recent geo-replicated backups, even when the source region is unavailable.
- Available only with geo-redundant (GRS) or geo-zone-redundant (GZRS) backup storage; it is disabled for LRS or ZRS backup storage.
- Replication to the secondary is asynchronous, so recent changes can be lost, and a large restore can take hours. Target-region capacity is not guaranteed during a big outage.
## When to use it
Learn calls geo-restore the most basic DR solution: suitable for relatively small, non-critical databases. Business-critical apps that need low RPO/RTO and guaranteed capacity should use failover groups, which cost a full secondary.
## Example
After an outage in West Europe, the team restores `db-inventory` from its latest geo-replicated backup onto an existing server in North Europe.
W: Geo-restore: it uses backups that already exist at no extra compute cost and accepts hours of recovery and some data loss, matching a non-critical, cost-sensitive database.
X: A=Auto-failover group: it gives low RPO and RTO but runs and bills a secondary database all the time, which the cost goal does not justify.
C=Zone-redundant backup storage: ZRS keeps backups in one region and disables geo-restore, so a regional failure leaves no copy elsewhere.
D=Active geo-replication: a continuously running secondary database adds ongoing cost for recovery targets the app does not need.
T: For small, non-critical Azure SQL databases, geo-restore from geo-redundant backups is the low-cost regional DR option.
V: Azure SQL Database

@ AZ-305 D3 T3.1 advanced troubleshooting
S: Auditors ask how an Azure SQL Database could be recovered if an operator deletes the entire logical server by mistake. The current design keeps 35 days of point-in-time backups. What should you recommend adding?
A: Rely on the deleted databases restore option on the server, which keeps dropped databases for 35 days
B: Change the backup storage redundancy from geo-redundant to zone-redundant for both STR and LTR backups
C: Increase the differential backup frequency to every 12 hours so that more recent restore points exist
D: A long-term retention policy, because LTR backups are kept after the server is deleted and can be restored
K: D
G: ## What happens when a logical server is deleted
Deleting a logical server deletes all its databases **and their PITR backups**. A deleted server cannot be restored, and its databases cannot be recovered from PITR backups.
## LTR survives server deletion
Long-term retention backups are **not deleted** with the server. They can be restored to a different server (or managed instance) in the same subscription, to the time each LTR backup was taken. If the server is gone, you list and restore them with Azure CLI or PowerShell.
## Restoring a dropped database
Restoring a deleted database to its deletion time works only while its **server still exists**; it uses the server's PITR backups.
## Example
With `W = 4 weeks`, the team can rebuild the database on a new server from last week's LTR backup even after the original server is gone.
W: Long-term retention: LTR backups outlive the logical server and can be restored to a new server, which gives a recovery path the 35-day PITR backups do not.
X: A=Deleted databases restore: it is a server feature that uses the server's own PITR backups, so it disappears along with the deleted server.
B=Zone-redundant backup storage: it changes where backups are stored inside the region but does nothing for backups that are deleted with the server, and it disables geo-restore.
C=More frequent differentials: they shorten restore time inside the PITR window, but those backups are still removed when the server is deleted.
T: PITR backups die with a deleted logical server; only long-term retention backups survive and can be restored to a new server.
V: Azure SQL Database

@ AZ-305 D3 T3.1 applied comparison

A: Periodic backup mode with the backup interval shortened to one hour and the retention raised to 30 days
B: Continuous backup mode with the 30-day tier, restoring the container to the point just before the deletion

S: A company wants disaster recovery to Azure for 200 VMware vSphere VMs in its datacenter, with continuous replication and failover to Azure VMs. Which TWO components must it deploy? (Select TWO)

B: The Mobility service on each VMware VM to be replicated, ideally installed automatically by Site Recovery
C: The Azure Site Recovery Provider and Recovery Services agent installed on each ESXi host in the cluster

G: ## Site Recovery for VMware to Azure
The modernized architecture uses two main on-premises components:
- **Azure Site Recovery replication appliance**: the building block of the on-premises setup. It hosts a proxy (so production VMs need no other internet path), a process server that caches and compresses data before sending it to Azure, and handles monitoring and automatic updates.

@ AZ-305 D3 T3.1 applied use-case
S: A three-tier app on Azure VMs is protected by Azure Site Recovery. On failover, the database tier must start first, then the app tier, then the web tier, and a connection string must be updated automatically. What should you recommend?
A: Separate replication policies for each tier, with shorter app-consistent snapshot intervals set for the database
B: A recovery plan with one startup group per tier in order and an Azure Automation runbook to update the setting
C: Traffic Manager priority routing between the regions, with endpoint monitoring on each web tier VM's address
D: An Azure Automation runbook triggered by a Service Health alert that fails over each VM one at a time by name

G: ## Recovery plans in Site Recovery
A recovery plan gathers machines into **groups** that fail over as a unit.
- Machines **in one group** fail over in parallel.
- **Groups run in order**: Group 2 starts only after every machine in Group 1 has failed over and started.
- You can add **Azure Automation runbooks** or scripts and **manual actions** before or after a group, for tasks such as changing a connection string, adding a public IP or assigning an NSG.
- Recovery plans support failover, failback and test failover, and reduce RTO by automating steps.
## Example
Group 1: SQL VMs. Group 2: app VMs, then a runbook that updates the app's connection string. Group 3: web VMs. One failover action runs the whole sequence.
W: Recovery plan with ordered groups and a runbook: groups enforce the database, app, web start order, and the runbook automates the connection string change, all in one failover.
X: A=Separate replication policies: policies set recovery point and snapshot frequency; they do not control start order or run post-failover tasks.
C=Traffic Manager: it can redirect users to the recovered region but does not orchestrate VM start order or change settings inside the app.
D=Alert-triggered runbook: a hand-written failover script duplicates what recovery plans do natively and gives no test failover or ordered groups.
T: Use a Site Recovery recovery plan to sequence multi-tier failover in groups and automate steps with runbooks or manual actions.

@ AZ-305 D3 T3.1 applied use-case
S: Compliance requires a quarterly disaster recovery drill for VMs protected by Azure Site Recovery. The drill must not interrupt production or ongoing replication, and recovered VMs must not conflict with live ones. What should you recommend?
A: A test failover into an isolated Azure virtual network that mirrors the production subnets and addressing
B: A planned failover to the target region each quarter followed by a failback after the drill is finished
C: An unplanned failover of a single VM each quarter, followed by re-enabling replication for that VM again
D: A test failover into the production recovery virtual network while the source VMs keep running normally
K: A
G: ## Test failover
A **test failover** is a disaster recovery drill that validates replication and the recovery process **without data loss or downtime**. It doesn't affect ongoing replication or the production environment, and it can run on one VM or on a recovery plan.
## Choosing the test network
Learn recommends a test network **isolated from the production recovery network**, built to mimic it: the same subnet names and the same IP ranges, with DNS pointing at a test domain controller. A new Azure virtual network is isolated by default.
If you test into the production network instead, you must shut down the primary VMs first; otherwise two VMs with the same identity run at once, and production is down during the test.
## After the drill
Clean up the test failover to delete the test VMs. Learn recommends a test failover for each app every quarter.
W: Isolated test failover: it starts copies of the VMs in a separate network without touching production or replication, and the isolation avoids duplicate identities and address conflicts.
X: B=Planned failover: it shuts down the source VMs and moves production to the target region, which interrupts the business it is meant to test.
C=Unplanned failover: it is a real failover that ends normal replication for that VM, so protection must be rebuilt afterwards.
D=Test failover into production network: with the source VMs running, two machines with the same identity share the network, which Learn warns against.
T: Run DR drills as Site Recovery test failovers into an isolated network that mirrors production.
