@ AZ-305 D4 T4.1 advanced comparison
S: A platform team must run third-party software delivered as Helm charts that installs custom resource definitions and Kubernetes operators, and the team needs direct access to the Kubernetes API. Which hosting service should you recommend?
A: Azure Kubernetes Service, installing the vendor's packages onto a managed cluster that you administer
B: Azure App Service for Containers, deploying each chart's images as separate web apps behind one custom domain
C: Azure Container Instances in a virtual network, deploying each chart's containers as an individual container group
D: Azure Container Apps with Dapr enabled, so that the vendor's components communicate through managed sidecars
K: A
G: ## When the Kubernetes API matters
Some software is packaged for Kubernetes itself: Helm charts that create **custom resource definitions (CRDs)**, **operators** that watch those resources, admission webhooks or cluster-wide controllers. These need a real cluster and its API server.
## What each service exposes
- **AKS** supports direct access to the Kubernetes API and can run any Kubernetes workload. It comes as AKS Standard (you manage cluster configuration) or AKS Automatic (Azure handles node management, scaling and upgrades).
- **Azure Container Apps** is built on Kubernetes but does not provide access to the Kubernetes APIs; Learn says to use AKS if you need them.
- **App Service** and **Container Instances** run containers but have no Kubernetes control plane at all.
W: Azure Kubernetes Service: CRDs, operators and Helm charts need the Kubernetes API, and AKS is the Azure service that gives direct API access and runs any Kubernetes workload.
X: B=App Service for Containers: App Service runs container images as web apps. It has no Kubernetes API, so Helm charts with operators cannot be installed at all.
C=Container Instances in a virtual network: ACI runs container groups on demand with no Kubernetes control plane, so nothing would reconcile the vendor's custom resources.
D=Container Apps with Dapr: Container Apps hides the Kubernetes API, so the operators and CRDs cannot be installed. Dapr sidecars help service-to-service calls but do not change that.
T: Need CRDs, operators or the Kubernetes API itself → AKS; Container Apps runs on Kubernetes but does not expose its API.
V: Azure Kubernetes Service, Azure Container Apps

@ AZ-305 D4 T4.1 advanced use-case
S: An engineering firm runs computational fluid dynamics simulations whose processes exchange data through MPI during each run. It wants Azure to schedule jobs and manage the node pool so the team does not operate any cluster software. Which solution should you recommend?
A: An Azure Batch pool of HB-family virtual machines, with the solver submitted to the Batch service
B: Azure Functions on the Premium plan running each simulation step as a function that fans out across instances
C: An Azure Container Apps environment running the solver as an event-driven job that scales out on queue length
D: A Virtual Machine Scale Set of F-family VMs with an autoscale rule based on the CPU percentage of the nodes
K: A
G: ## Two kinds of parallel work
Learn separates batch workloads into two shapes:
- **Intrinsically parallel** ("embarrassingly parallel"): each task runs on its own and never talks to the others, for example image rendering or file conversion.
- **Tightly coupled**: the processes communicate during the run, normally through the **Message Passing Interface (MPI)**. Fluid dynamics, finite element analysis and weather models are typical examples.
## What Azure Batch adds
Azure Batch creates and manages a pool of compute nodes, installs the applications and schedules jobs on them. There is no cluster or job scheduler software to install or scale; you submit independent tasks or MPI jobs through the Batch APIs. Batch runs tightly coupled jobs with Microsoft MPI or Intel MPI.
## The right hardware
The HPC families (HB, HC, HX) are optimized for this work. Learn lists fluid dynamics and weather modeling under the HB-family because those codes need high memory bandwidth.
W: Batch pool of HB-family VMs: Batch supplies the scheduler and node management, supports MPI for tightly coupled jobs, and the HB-family is the HPC family Learn names for fluid dynamics.
X: B=Functions Premium plan: functions are short event-driven executions on general instances. Splitting a coupled solver into independent functions breaks the constant data exchange the simulation depends on.
C=Container Apps job: Container Apps jobs run finite containerised tasks triggered manually, on a schedule or by events. Nothing in that model provides an MPI fabric or HPC sizes for processes that must talk to each other during a run.
D=Scale set with CPU autoscale: a scale set adds or removes VMs but has no job scheduler, so the team would have to run its own cluster software. The F-family is also general compute, not an HPC family.
T: Tightly coupled MPI jobs with scheduling as a service point to Azure Batch on HPC sizes (HB/HC/HX); independent tasks also fit Batch, and neither needs a self-run scheduler.
V: Azure Batch, Azure Virtual Machines

@ AZ-305 D4 T4.4 applied tradeoff
S: A company connects 12 branch offices to Azure with a site-to-site VPN. It wants the Azure side of the VPN to survive both a gateway instance failure and an availability zone failure, with both tunnels from each branch active and no extra charge for the second instance. Which solution should you recommend?
A: Two separate VPN gateways in two peered virtual networks of the same region, with Traffic Manager choosing between them
B: An ExpressRoute gateway in the virtual network, with each branch tunnel terminated on the gateway's ExpressRoute links
C: An AZ gateway SKU configured active-active, with every on-premises router peering with both instance addresses
D: A Basic SKU VPN gateway in active-passive mode, with a second Basic gateway in another region kept as a standby
K: C
G: ## How a VPN gateway is built
An Azure VPN gateway runs on two instances. In **active-passive** mode one instance carries the tunnels and the other takes over after a failure, which causes a brief interruption. In **active-active** mode both instances have their own public IP, and each on-premises device builds a tunnel to both, so traffic keeps flowing over the surviving tunnel if an instance fails. Microsoft notes that an active-active setup costs the same as active-passive.
## Zone redundancy
Gateway SKUs with zone-redundant options (the AZ SKUs that Microsoft recommends for new deployments) spread the instances across availability zones, so a zone failure doesn't take down the gateway. The Basic SKU supports neither active-active nor zone redundancy, and BGP isn't available on it.
W: Zone-redundant AZ SKU in active-active mode: instances in different zones protect against zone failure, both instance public IPs carry tunnels from each branch, and active-active costs the same as active-passive.
X: A=Two gateways behind Traffic Manager: Traffic Manager answers DNS queries for applications; VPN devices connect to fixed gateway IPs, and two gateways double the cost.
B=ExpressRoute gateway: an ExpressRoute gateway terminates ExpressRoute circuits, not IPsec site-to-site tunnels from branch devices.
D=Basic SKU with a standby: Basic gateways have no zone redundancy or active-active mode, and a gateway in another region adds a full second gateway charge plus a manual failover.
T: Resilient site-to-site VPN in Azure → zone-redundant gateway SKU in active-active mode, with tunnels from each device to both instances.
V: Azure VPN Gateway, availability zones

@ AZ-305 D4 T4.1 applied use-case
S: An architecture firm will give designers GPU-accelerated remote desktops for CAD and 3D modelling through Azure Virtual Desktop. Which VM size family should you recommend for the session hosts?
A: The L-family storage optimized sizes, which provide high local disk throughput for large design files
B: The HC-family high performance compute sizes, which target finite element analysis with dense CPU cores
C: The NV-family sizes, which Learn lists for VDI and remote visualization of graphics-heavy applications
D: The M-family memory optimized sizes, which offer the largest memory configurations for very big databases
K: C
G: ## GPU VM families
Learn groups GPU VMs into several families, each aimed at a workload:
- **NC**: compute-intensive, graphics-intensive and visualization work, often AI training and inference.
- **ND**: large memory compute-intensive work such as training big models.
- **NV** and **NG**: virtual desktop (VDI) workloads, where users need a GPU for graphics in a remote session.
## Designing GPU desktops
For Azure Virtual Desktop, the session host size decides what each user can do. Designers working in CAD and 3D tools need a GPU to render the viewport, so the host pool should use a VDI-oriented GPU family. CPU-only HPC or memory families give no graphics acceleration.
W: NV-family: it is the GPU family Learn lists for virtual desktop (VDI) workloads, giving each designer GPU-accelerated graphics in the Azure Virtual Desktop session.
X: A=L-family storage optimized: L sizes give high local disk throughput for NoSQL and big data stores, not GPU rendering for remote desktops.
B=HC-family HPC: HC sizes are CPU-based HPC nodes for finite element analysis and molecular dynamics. They have no GPU for interactive graphics.
D=M-family memory optimized: the M-family targets extremely large databases with huge RAM. It provides no graphics acceleration for CAD sessions.
T: GPU-accelerated virtual desktops point to the NV (or NG) family; NC and ND target GPU compute such as AI training.
V: Azure Virtual Desktop, Azure Virtual Machines
