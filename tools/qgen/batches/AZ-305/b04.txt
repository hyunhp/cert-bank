@ AZ-305 D2 T2.1 applied use-case
S: A company is launching a new internal app backed by one Azure SQL database. Usage is unpredictable, with busy mornings and long idle nights and weekends, and there is no usage history to size compute from. A short delay on the first connection after an idle period is acceptable. Which compute option should you recommend?
A: The serverless compute tier in General Purpose, with an auto-pause delay so compute isn't billed while the database is idle
B: The provisioned compute tier in General Purpose, sized for the morning peak and scaled down by hand every night and weekend
C: A DTU-based Standard elastic pool that holds only this database, so its eDTUs drop to zero during the idle periods
D: The Business Critical tier with provisioned compute, using its readable secondary replica to absorb the morning peak
K: A
G: ## Provisioned and serverless compute
In the vCore purchasing model, Azure SQL Database offers two compute tiers:
- **Provisioned**: you pick a fixed number of vCores and pay per hour for them whether the database is busy or idle. You scale by hand.
- **Serverless**: you set a minimum and maximum vCore range. Compute scales automatically inside that range and is billed **per second for what is used**. After a configurable **auto-pause delay** with no activity, the database pauses and only storage is billed; the next login resumes it.
## When each fits
Microsoft recommends serverless for single databases with **intermittent, unpredictable usage** and periods of inactivity, and for **new databases without usage history** where sizing is hard to estimate. The trade-off is a warm-up delay after a pause. Provisioned compute fits regular, predictable load or workloads that can't accept that delay.
## Example
An app busy from 8 to 11 a.m. and idle overnight pays for compute only during the active hours with serverless; a provisioned database sized for 8 a.m. pays for that size around the clock.
W: Serverless General Purpose: it autoscales between the configured vCore limits, bills compute per second of use, and auto-pauses during the idle nights and weekends so only storage is charged, which matches a new, unpredictable single database that can tolerate a resume delay.
X: B=Provisioned with manual scaling: provisioned compute is billed per hour for the size you set, independent of activity, and depends on someone (or a script) to resize it, which is exactly the effort and waste serverless removes.
C=Single-database elastic pool: a pool is billed for its eDTUs for every hour it exists regardless of usage, and its value comes from many databases sharing resources; a pool holding one database saves nothing and never drops to zero cost.
D=Business Critical: it adds three replicas and costs several times more than General Purpose; its readable secondary serves read-only queries, not the main write workload, and nothing about it reduces cost while the app is idle.
T: For one database with unpredictable, intermittent use and no sizing history, pick serverless (auto-scale, per-second billing, auto-pause) if a resume delay is acceptable.
V: Azure SQL Database

@ AZ-305 D2 T2.1 applied use-case
S: A SaaS vendor gives each of its 300 customers a separate Azure SQL database. Each database is idle most of the day and spikes briefly, and the spikes of different customers rarely happen at the same time. The vendor wants predictable cost without sizing every database for its own peak. What should you recommend?
A: Place the databases in an elastic pool so they share one set of vCores or eDTUs sized for their combined load
B: Move every database to the serverless compute tier so that each one scales and pauses on its own schedule
C: Consolidate all customers into one Hyperscale database and scale its compute up during the busiest hours
D: Provision each database as a Business Critical single database sized for the largest customer peak load
K: A
G: ## What an elastic pool is
An **elastic pool** is a set of resources (eDTUs in the DTU model or vCores in the vCore model) bought once and shared by many databases on the same logical server. Each database can burst when it needs resources and uses little or nothing when idle. You pay per hour for the pool, with no per-database charge.
## When pools save money
Microsoft describes the ideal pool candidates as databases with:
- a **large gap between peak and average** utilization,
- **peaks at different times** from each other,
- enough databases to share the resources.
Databases with persistent medium-high utilization shouldn't share a pool.
## Example
Twenty databases that each peak at 90 DTUs for a few minutes but average under 5 DTUs, at different times, can share a 100 eDTU pool instead of twenty separate 100 DTU databases.
W: Elastic pool: the pool is sized for the aggregate load, which stays low because the customers' spikes don't overlap; each database still gets resources when it spikes, and the vendor pays one predictable price for the pool instead of 300 peak-sized databases.
X: B=Serverless per database: serverless is designed for single databases; billing per database per second makes the monthly cost less predictable, and Microsoft's guidance is that many intermittent databases that can be consolidated get better price-performance from a provisioned elastic pool.
C=One Hyperscale database: merging 300 tenants into one database throws away the per-customer isolation the vendor already has, and scaling compute for the busiest hours still sizes for a peak rather than sharing idle capacity.
D=Business Critical per database: sizing every database for the largest peak is the overprovisioning problem pools exist to solve, and Business Critical's extra replicas multiply that cost further.
T: Many databases with low average use and non-overlapping spikes belong in an elastic pool: shared resources, one predictable price.
V: Azure SQL Database elastic pools

@ AZ-305 D2 T2.1 applied use-case
S: An order-processing database in Azure SQL Database is 3 TB today and is expected to reach 40 TB within three years. Backups must not slow the workload, and restoring a copy for testing must take minutes rather than hours. Which service tier should you recommend?
A: Hyperscale, which grows storage up to 128 TB and uses file-snapshot backups and restores that don't load compute
B: Business Critical, which keeps data on local SSD storage and adds three replicas for faster recovery from failures
C: General Purpose, which stores data files in Azure Blob storage and grows the database by raising its maximum size
D: Premium in the DTU model, which bundles compute, storage and I/O so that backups and restores run at a fixed speed
K: A
G: ## Storage limits of the vCore tiers
- **General Purpose** and **Business Critical**: up to 4 TB of data per database. Backups are streamed from the database files.
- **Hyperscale**: storage is decoupled from compute and grows automatically from 10 GB up to **128 TB**; you are billed for allocated storage, not a maximum size.
## Why Hyperscale backups are different
Hyperscale backups and restores are **based on file snapshots** taken in the storage layer. They are nearly instantaneous regardless of database size and put **no I/O load on the compute replicas**. Restores and database copies take minutes rather than hours or days, even for tens of terabytes.
## Other Hyperscale traits
Compute scales quickly without moving data, up to four high-availability replicas and up to 30 named replicas can be added for reads, and Microsoft calls it the recommended default tier for new OLTP and HTAP workloads.
W: Hyperscale: it is the only Azure SQL Database tier that reaches 40 TB (up to 128 TB), and its snapshot-based backups and restores happen in the storage layer, so they don't slow the workload and complete in minutes.
X: B=Business Critical: local SSD gives low latency and the replicas speed up failover, but a database is limited to 4 TB, far below the 40 TB target, and backup and restore time still grows with data size.
C=General Purpose: its data files do live in Azure Blob storage, but the maximum data size is 4 TB, and backups and restores scale with the size of the database rather than taking minutes.
D=DTU Premium: the DTU model offers preconfigured bundles with storage limits well below 40 TB, and bundling resources says nothing about backup speed; large databases and fast restores point to Hyperscale in the vCore model.
T: Databases that will outgrow 4 TB or need size-independent, minutes-long backups and restores belong in Hyperscale (up to 128 TB, snapshot backups).
V: Azure SQL Database Hyperscale

@ AZ-305 D2 T2.1 advanced comparison
S: A trading application on Azure SQL Database needs storage latency of 1-2 ms, uses In-Memory OLTP tables, and runs end-of-day reports that must not slow the primary. The company doesn't want to pay for an extra database for reporting. Which service tier should you recommend?
A: Business Critical, with local SSD storage, In-Memory OLTP support and a built-in read-only replica for the reports
B: General Purpose, with remote premium storage and a geo-secondary in another region used for the daily reports
C: Hyperscale, with a named replica for the reports and its multi-tier cache for low-latency reads and writes
D: General Purpose serverless, with automatic compute scaling during reporting and pausing after the trading day
K: A
G: ## How the vCore tiers differ
- **General Purpose** separates compute from storage: data files sit in remote Azure premium storage, giving storage latency of roughly 5-10 ms. There are no readable replicas.
- **Business Critical** runs a cluster of four database engine nodes (a primary and three secondaries) using **locally attached SSD**, with average storage latency of 1-2 ms. It supports **In-Memory OLTP**, and **read scale-out** gives one secondary for read-only queries at no extra charge.
- **Hyperscale** separates compute and storage with multi-level caching. It supports only limited, non-persistent In-Memory OLTP objects (such as memory-optimized table variables), not memory-optimized tables.
## Matching requirements to the tier
Consistent 1-2 ms storage latency, in-memory tables and free read offload together describe Business Critical.
W: Business Critical: local SSD gives the 1-2 ms latency, it is the vCore tier that supports In-Memory OLTP tables, and its built-in read-only replica runs the reports without touching the primary or adding a paid database.
X: B=General Purpose with a geo-secondary: remote storage latency is about 5-10 ms, In-Memory OLTP isn't supported, and a geo-secondary is a separately billed database, which the company wants to avoid.
C=Hyperscale: In-Memory OLTP is limited to non-persistent objects such as memory-optimized table variables, so the trading tables wouldn't work, and each named replica is compute you pay for.
D=Serverless General Purpose: serverless changes how compute is scaled and billed, not the storage latency or the missing In-Memory OLTP support, and pausing an active trading database risks a warm-up delay.
T: Low storage latency, In-Memory OLTP tables and a free readable replica are the signature of the Business Critical tier.
V: Azure SQL Database

@ AZ-305 D2 T2.1 applied use-case
S: A company is moving a line-of-business SQL Server instance to Azure PaaS. Its databases use SQL Server Agent jobs, cross-database queries with three-part names, CLR assemblies and Database Mail. The company wants as few code changes as possible and no operating system to patch. Which service should you recommend?
A: Azure SQL Managed Instance, which supports these instance-scoped features with near-complete SQL Server compatibility
B: Azure SQL Database single databases on Hyperscale, using elastic jobs to replace SQL Server Agent and the other features
C: SQL Server on Azure Virtual Machines, registered with the SQL IaaS Agent extension to automate patching and backups
D: Azure SQL Database in an elastic pool, so all the databases share resources and query each other by three-part name
K: A
G: ## Three ways to run SQL Server in Azure
- **Azure SQL Database**: PaaS at the database level. Instance-scoped features are missing: no SQL Server Agent (use elastic jobs), no cross-database three-part-name queries, no CLR, no Database Mail.
- **Azure SQL Managed Instance**: PaaS at the instance level with near 100% compatibility with the latest SQL Server Enterprise engine. SQL Server Agent, cross-database queries and transactions within the instance, CLR, Database Mail, Service Broker and linked servers are supported. Microsoft calls it the best target for most migrations to the cloud.
- **SQL Server on Azure VMs**: IaaS with full engine and OS control, but you own the operating system.
## Picking for "lift and shift with minimal changes, no OS"
When an application depends on instance-level features and the company wants PaaS, SQL Managed Instance is the fit; a VM would work technically but keeps the OS in your hands.
W: SQL Managed Instance: it supports SQL Server Agent, three-part-name cross-database queries, CLR and Database Mail, so the databases move with minimal code changes, and as PaaS it patches the OS and engine for the company.
X: B=SQL Database Hyperscale: Azure SQL Database supports none of cross-database queries, CLR or Database Mail; elastic jobs replace Agent jobs only after rework, and Hyperscale changes the storage architecture, not the feature surface.
C=SQL Server on VMs: it is fully compatible, but it is IaaS; even with automated patching through the extension, the company still owns and manages the operating system, which the requirement rules out.
D=SQL Database elastic pool: a pool shares compute among databases but doesn't turn them into one instance; three-part-name queries, CLR and Database Mail remain unsupported in Azure SQL Database.
T: PaaS plus instance-scoped features (Agent, cross-database queries, CLR, Database Mail) points to Azure SQL Managed Instance.
V: Azure SQL Managed Instance, Azure SQL Database

@ AZ-305 D2 T2.1 advanced comparison
S: A company is deciding between Azure SQL Managed Instance and SQL Server on Azure Virtual Machines for a legacy application. Which TWO requirements can be met only by SQL Server on Azure Virtual Machines? (Select TWO)
A: The application stores documents in SQL Server FILESTREAM filegroups on the database server
B: A vendor monitoring agent must be installed on the database server's operating system
C: Nightly maintenance runs as SQL Server Agent jobs that call stored procedures in each database
D: Stored procedures join tables across several databases on the instance using three-part names
E: The database uses CLR assemblies that are deployed with CREATE ASSEMBLY from binary values
K: A,B
G: ## Where the line between PaaS and IaaS falls
SQL Managed Instance covers almost the whole SQL Server engine: SQL Server Agent, cross-database queries and transactions within the instance, CLR (without file system access), Service Broker, Database Mail and linked servers all work.
A few things still need a full SQL Server you control:
- **FILESTREAM / FileTable**: not supported in SQL Database or SQL Managed Instance.
- **Operating system access**: neither PaaS service lets you sign in to the host or install software on it.
- Running SSRS or SSAS on the same server, choosing when maintenance happens, or older SQL Server versions.
## SQL Server on Azure VMs
A SQL Server VM gives 100% SQL Server compatibility and OS-level access. Registering it with the SQL IaaS Agent extension adds automated backup and patching options, but the OS stays your responsibility.
W: A=FILESTREAM: Microsoft's feature comparison lists FILESTREAM as unsupported in SQL Managed Instance, so keeping that storage design means running SQL Server on a VM.
B=OS-level agent: SQL Managed Instance is PaaS with no access to the host operating system; only an Azure VM lets the vendor's agent be installed next to the engine.
X: C=SQL Server Agent jobs: SQL Managed Instance supports SQL Server Agent, so the nightly jobs move without a VM.
D=Three-part-name queries: cross-database queries and transactions within the instance are supported in SQL Managed Instance.
E=CLR assemblies: SQL Managed Instance supports CLR as long as assemblies are created from binary values rather than from a file path, which is exactly how these are deployed.
T: FILESTREAM and anything that needs the server's operating system force SQL Server on Azure VMs; Agent, CLR and cross-database queries don't.
V: SQL Server on Azure Virtual Machines, Azure SQL Managed Instance

@ AZ-305 D2 T2.1 applied comparison
S: A company has Software Assurance on its SQL Server core licenses and is moving several databases to Azure SQL Database. It wants to apply those licenses to lower cost, buy reserved capacity for three years, and size compute and storage independently. Which purchasing model should you recommend?
A: The vCore-based model, which supports Azure Hybrid Benefit and reservations and scales compute apart from storage
B: The DTU-based model, which bundles compute, storage and I/O and applies Azure Hybrid Benefit to each DTU bundle
C: The DTU-based model with eDTU elastic pools, which apply the existing licenses once at pool level instead of per database
D: Either model, because Azure Hybrid Benefit and reserved capacity apply the same way to DTU and vCore databases
K: A
G: ## Two purchasing models
- **DTU-based**: a DTU is a blended measure of CPU, memory, reads and writes. You choose a preconfigured bundle in the Basic, Standard or Premium tier; storage is included in the bundle and you can't pick the hardware.
- **vCore-based** (Microsoft's recommended model): you choose vCores, memory/hardware and storage separately, in the General Purpose, Business Critical or Hyperscale tier.
## Discounts only in vCore
The vCore page lists benefits over DTU, including:
- **Azure Hybrid Benefit**: reuse SQL Server licenses with Software Assurance for a discount.
- **Reserved capacity** (reservations): available **only** in the vCore model.
- Higher limits and finer scaling granularity, with compute and storage chosen independently.
W: vCore model: it is the model that supports Azure Hybrid Benefit for SQL Server and reservations, and it lets the company size vCores and storage separately, meeting all three requirements.
X: B=DTU with Hybrid Benefit: DTU bundles include the license in the price and don't support Azure Hybrid Benefit; the bundling is also the opposite of sizing compute and storage independently.
C=DTU elastic pools: pools change how resources are shared, not how licenses are applied; eDTU pools still offer no Hybrid Benefit and no reserved capacity.
D=Either model: Microsoft's comparison is explicit that reservations are available only in the vCore model, and Hybrid Benefit is listed as a vCore advantage, so the two models are not equivalent.
T: License reuse (Azure Hybrid Benefit), reservations and independent compute/storage sizing all point to the vCore purchasing model.

@ AZ-305 D2 T2.1 applied use-case
S: A Business Critical Azure SQL database serves an order application. Analysts now run heavy read-only reports during business hours, and the company wants to keep them off the primary replica without deploying another database. What should you recommend?
A: Have the reporting tool connect with ApplicationIntent=ReadOnly so read scale-out sends it to a secondary replica
B: Put the reporting users in a separate Resource Governor workload group that limits them on the primary replica
C: Create a geo-replica in another region and point the reporting tool at that secondary for its read-only sessions
D: Move the database into an elastic pool so the reports consume spare pool resources instead of the primary's own
K: A
G: ## Replicas you already have
A Business Critical (or Premium) database is a cluster of a primary read-write replica and several secondary replicas that exist for high availability. The **read scale-out** feature lets you use one of those secondaries for read-only work at no extra charge. It is enabled by default on new Premium, Business Critical and Hyperscale databases.
## How a connection reaches a secondary
The client chooses with the connection string:
- `ApplicationIntent=ReadWrite` (default) goes to the primary.
- `ApplicationIntent=ReadOnly` is routed to a read-only replica.
## Things to design for
Reads on a replica are asynchronous with respect to the primary: data is usually milliseconds to seconds behind, with no fixed upper bound. Fine for reports, not for read-after-write logic. General Purpose has no such replica; geo-replicas can play a similar role there but are separate, billed databases.
W: ApplicationIntent=ReadOnly: Business Critical already includes a readable secondary through read scale-out, so changing the reporting tool's connection string moves the reports off the primary at no extra cost and without a new database.
X: B=Resource Governor group: limiting the analysts still runs their queries on the primary and slows the reports; Azure SQL Database also doesn't expose Resource Governor configuration for user-defined workload groups.
C=Geo-replica: a geo-secondary is an additional database billed separately, which the company wants to avoid, and it is meant for disaster recovery rather than the free in-region read replica the tier already has.
D=Elastic pool: a pool shares resources among several databases; the reports would still run on the same primary replica of this database, competing with the order workload.
T: In Business Critical and Hyperscale, offload read-only work by connecting with `ApplicationIntent=ReadOnly`; the readable replica is already there.
V: Azure SQL Database

@ AZ-305 D2 T2.1 advanced use-case
S: A Hyperscale database supports an e-commerce site. Three teams (data science, a partner API and finance reporting) need read access, each with its own compute size and without competing with each other or with the high-availability replicas. What should you recommend?
A: Create a named replica for each team, each with its own compute size and connection, on the shared Hyperscale storage
B: Raise the number of high-availability secondary replicas to four and route every team with ApplicationIntent=ReadOnly
C: Create three database copies and refresh each of them nightly with a scheduled export from the primary database
D: Configure three geo-replicas in the same region, because Hyperscale offers read access only through geo-replicas
K: A
G: ## Replica types in Hyperscale
Hyperscale separates compute from a shared storage layer, so extra compute nodes can be attached without copying data:
- **High-availability (HA) secondary replicas**: 0 to 4. They follow the primary's compute size, serve as failover targets and can take `ApplicationIntent=ReadOnly` connections.
- **Named replicas**: up to 30. Each has its **own name, compute size and connection endpoint**, so it can be sized and secured for a specific workload.
- **Geo-replicas**: in another region for disaster recovery and geo-distributed reads.
## Why named replicas fit separate teams
Named replicas give workload isolation and access isolation: data science can run on a large replica, the partner API on a small one, and none of them takes resources from the HA replicas that protect the primary.
W: Named replicas: each team gets a replica with its own compute size and endpoint over the same storage, isolating the three workloads from each other and from the failover replicas, with no data copying.
X: B=More HA replicas: HA replicas share the primary's compute size and all ReadOnly connections are spread over them, so the teams would compete with each other and with the replicas meant for failover.
C=Nightly copies: copies refreshed by export are a day stale and require storage and maintenance for each copy; named replicas read the live data from shared storage.
D=Same-region geo-replicas: Hyperscale offers in-region read access through HA and named replicas; geo-replicas are aimed at another region for disaster recovery, not at isolating local teams.
T: For several isolated read workloads with different sizes on Hyperscale, use named replicas (up to 30), not more HA replicas.

@ AZ-305 D2 T2.1 advanced tradeoff
S: A SaaS company is evaluating sharding its tenant data across many Azure SQL databases with the Elastic Database client library, instead of scaling up one database. Which TWO requirements are good reasons to choose sharding? (Select TWO)
A: Some tenants' data must stay in a specific geography to meet compliance rules
B: The combined transaction throughput exceeds what any single database can deliver
C: Most transactions must update data of many tenants together in one ACID transaction
D: The application must avoid adding a sharding key and request routing to its data tier
E: The team wants every schema change applied only once to a single database for simplicity
K: A,B
G: ## Scaling up and scaling out
- **Vertical scaling (scale up)**: give one database more compute, for example a larger service objective.
- **Horizontal scaling (scale out)**: add databases. **Sharding** spreads identically structured data across many independent databases (shards), each holding a subset of keys such as tenant IDs.
## Microsoft's reasons for sharding
- The total data is too large for one database.
- The **transaction throughput exceeds the capabilities of one database**.
- Tenants need physical isolation from each other.
- Parts of the data must **reside in different geographies** for compliance, performance or geopolitical reasons.
## The cost of sharding
Sharding works best when each transaction stays within **one sharding key value**. The application tier must route each request to the right shard (the Elastic Database client library keeps a shard map for this), and schema changes must be rolled out to every shard, for example with elastic jobs.
W: A=Data residency: placing shards in different regions keeps each tenant's data in its required geography, which a single database in one region can't do.
B=Throughput beyond one database: when the combined workload exceeds the largest single database, splitting it across shards adds capacity that scaling up can't.
X: C=Cross-tenant transactions: sharding works best when every transaction touches one sharding key; transactions that regularly span many tenants become distributed and are a reason not to shard.
D=No sharding key or routing: sharding requires a sharding key and application-side routing through the shard map; avoiding them is an argument for scaling up instead.
E=One schema to change: with sharding the same schema change must be applied to every shard, so wanting a single database to change is a point against it.
T: Shard when one database can't hold the throughput or data, or when tenants need isolation or specific geographies; keep transactions within one sharding key.
V: Azure SQL Database, Elastic Database tools

@ AZ-305 D2 T2.1 applied use-case
S: A SaaS app keeps free-trial tenants together in a multitenant sharded Azure SQL database. When a trial customer buys a subscription, it must move to its own single-tenant database with the data it created during the trial. Which tool should you recommend?
A: The split-merge tool of the Elastic Database tools, which moves the tenant's rows between sharded databases
B: A point-in-time restore of the multitenant database into a new database, then deleting all other tenants' rows
C: An elastic job that copies the schema into a new database and then runs on every shard in the shard map at once
D: Active geo-replication of the multitenant database to a new secondary, then a forced failover of that tenant
K: A
G: ## Multitenant and single-tenant shards
Elastic Database tools support two sharding patterns:
- **Single-tenant**: one database per tenant, giving isolation, per-tenant backup/restore and scaling.
- **Multitenant**: many tenants share a database; every row carries the tenant ID (sharding key).
A common SaaS design keeps cheap trial tenants in a multitenant database and gives paying customers their own database.
## Moving one tenant
The **split-merge tool** (deployed as a service) moves data between sharded databases, including from a multitenant database to a single-tenant database, and updates the shard map so the application routes the tenant to its new home.
Microsoft notes that restoring a multitenant database to a single tenant isn't possible: a restore brings back the whole database.
W: Split-merge tool: it moves one tenant's rows out of the multitenant shard into the new single-tenant database and keeps the shard map consistent, which is the scenario Microsoft describes for trial-to-customer moves.
X: B=Point-in-time restore: a restore brings back the entire database with every trial tenant at an earlier time, so the newest trial data is missing and other tenants' data must be removed by hand; Microsoft states a multitenant restore to a single tenant isn't possible.
C=Elastic job: elastic jobs run administrative T-SQL (such as schema changes) across many databases; they don't move a tenant's data or update the shard map.
D=Geo-replication with failover: a geo-secondary is a full copy of the whole database for disaster recovery; failing over moves every tenant, not one, and geo-replication can't select rows.
T: To move a tenant between shards, for example from a shared trial database to its own database, use the Elastic Database split-merge tool.

@ AZ-305 D2 T2.1 applied use-case
S: A company runs an Azure Database for PostgreSQL flexible server (General Purpose) for its web app. A new BI dashboard issues heavy read queries, and a few seconds of data delay is acceptable. The company wants to protect write performance on the main server. What should you recommend?
A: Create a read replica and point the BI dashboard at it, while all writes keep going to the primary server
B: Enable zone-redundant high availability and send the BI queries to the standby server in the other zone
C: Move the server to the Burstable tier and run the BI queries only at night using the accumulated CPU credits
D: Turn on read scale-out with ApplicationIntent=ReadOnly so the BI queries are sent to a built-in secondary
K: A
G: ## Read replicas in PostgreSQL flexible server
A **read replica** is a separate, read-only flexible server kept up to date **asynchronously** with PostgreSQL's native physical (streaming) replication. Typical uses:
- isolate read-heavy work such as **BI and analytics** on the replica while writes stay on the primary,

With high availability, the standby server receives changes synchronously so it can take over on failure, but **you can't use the standby HA server for read queries**.

C=Burstable tier: Burstable is meant for nonproduction or mostly idle workloads and loses performance once credits run out; it also doesn't support read replicas, so it makes the problem worse.

G: ## Serverless and pools solve similar problems differently
- **Serverless** optimizes a **single database** with intermittent, unpredictable use: per-second billing, autoscaling and auto-pause, at a higher unit price than provisioned compute and with warm-up delays.
- **Elastic pools** (provisioned compute) optimize **many databases** with intermittent use by letting them share resources.
## Microsoft's guidance
The serverless documentation lists, under scenarios suited to provisioned compute: "multiple databases with intermittent, unpredictable usage patterns that can be consolidated into elastic pools for better price-performance optimization." Serverless is the better fit when there is a single database, or when databases can't be pooled.
## Example
Forty branch databases that each spike briefly at different times can share a small pool whose cost is set by their combined load; forty serverless databases each pay a minimum compute charge while active and a warm-up delay after every pause.
W: Provisioned elastic pool: Microsoft recommends pooling multiple intermittent databases for better price-performance, because the pool is sized for the combined load and avoids per-database warm-up delays.
X: B=Serverless with short auto-pause: it can work, but each database is billed separately at the higher serverless unit price and frequent pauses add resume delays; for a group that can be pooled, Microsoft points to elastic pools.
C=One Business Critical database: consolidating branches removes isolation, and Business Critical's extra replicas cost several times more than General Purpose for a light workload.
D=Forty provisioned databases: each is billed per hour whether used or not, and manual scaling for unpredictable peaks is the effort and overprovisioning pools avoid.
T: Serverless suits a single intermittent database; many intermittent databases usually get better price-performance from a provisioned elastic pool.
V: Azure SQL Database

@ AZ-305 D2 T2.1 applied comparison
S: An architect must choose between Azure SQL Database and Azure SQL Managed Instance for a migrated application. Which TWO requirements point to SQL Managed Instance? (Select TWO)
A: The application uses Service Broker and distributed transactions coordinated by MS DTC
B: Full .bak backups taken on premises must be restored natively from Azure Blob storage
C: A single database must grow to 100 TB with fast snapshot-based backups and restores
D: The database must pause automatically when idle so that only its storage is billed
E: The database must use the DTU purchasing model with compute and storage bundled
K: A,B
G: ## Azure SQL Database versus SQL Managed Instance
Both are PaaS on the SQL Server engine, but they target different needs.
**SQL Managed Instance**
- Instance-level compatibility: Service Broker, SQL Server Agent, CLR, cross-database queries, linked servers and **distributed transactions with MS DTC**.
- **Native backup and restore**: `RESTORE ... FROM URL` accepts full `.bak` backups of SQL Server placed in Azure Blob storage, a common offline migration path.
- Native virtual network deployment into a dedicated subnet (Azure SQL Database reaches a private IP through private endpoints instead).
- vCore purchasing model with General Purpose and Business Critical tiers.
**Azure SQL Database**
- **Hyperscale** (up to 128 TB, snapshot backups) exists only in SQL Database.
- **Serverless** compute with auto-pause is a SQL Database single-database option.
- Offers both **DTU** and vCore purchasing models.
- No `RESTORE` statement: it restores only from its own automated backups; on-premises data arrives through BACPAC import, BCP or replication.
W: A=Service Broker and MS DTC: both are supported in SQL Managed Instance and not in Azure SQL Database, which has no Service Broker and uses elastic transactions instead of DTC.
B=Native .bak restore: SQL Managed Instance supports `RESTORE` from full backups in Azure Blob storage; Azure SQL Database has no `RESTORE` statement and restores only from its own automated backups.
X: C=100 TB with snapshot backups: that describes Hyperscale, which is available only in Azure SQL Database, not in SQL Managed Instance.
D=Auto-pause when idle: auto-pause is part of the serverless compute tier of Azure SQL Database single databases.
E=DTU model: SQL Managed Instance uses only the vCore model; the DTU bundles are an Azure SQL Database option.
T: Instance features (Service Broker, DTC) and native `.bak` restore point to SQL Managed Instance; Hyperscale, serverless and DTU are Azure SQL Database options.
V: Azure SQL Managed Instance, Azure SQL Database

@ AZ-305 D2 T2.1 advanced tradeoff
S: A team plans to convert a 2 TB General Purpose Azure SQL database to Hyperscale but worries about being locked in if the workload later needs the Business Critical tier. Which statement should guide the design?
A: Reverse migration from Hyperscale goes only to General Purpose, within 45 days; from there the tier can change again
B: A Hyperscale database can move to Business Critical at any time with an online change of its service objective
C: A Hyperscale database can never leave Hyperscale, so the only way out is an export and import into a new database
D: Reverse migration from Hyperscale is possible to any vCore tier for one year, provided the database stays under 4 TB
K: A
G: ## Moving into and out of Hyperscale
Converting an existing database to Hyperscale is an online operation whose duration depends on data size. Leaving Hyperscale is more restricted:
- **Reverse migration** is supported only for databases that were previously migrated to Hyperscale from another tier, **only to the General Purpose tier**, and **only within 45 days** of the original migration.
- To reach another tier such as Business Critical, first reverse migrate to General Purpose, then change the service tier.
- After the 45-day window, moving the data out of Hyperscale needs a data movement approach such as export and import.
## Design consequence
Run performance tests during the first weeks after conversion. If Hyperscale doesn't fit, decide within the window.
W: Reverse migration rule: Microsoft supports going back from Hyperscale only to General Purpose and only within 45 days of the original migration; from General Purpose the database can then move to Business Critical.
X: B=Direct move to Business Critical: there is no direct service objective change from Hyperscale to Business Critical; the documented path goes through General Purpose by reverse migration.
C=Never leaves Hyperscale: within 45 days a migrated database can be reverse migrated to General Purpose, so export and import is needed only after that window.
D=Any tier for one year: the window is 45 days and the only reverse-migration target is General Purpose.
T: Hyperscale can be undone only by reverse migrating to General Purpose within 45 days; test early and decide inside that window.
V: Azure SQL Database Hyperscale
