@ AZ-305 D1 T1.1 advanced use-case
S: A retailer runs about 220 VMs in each of three subscriptions, all in one region. CPU and inbound network traffic follow strong daily and weekly patterns that differ from VM to VM, and the small operations team has no time to tune thresholds per VM. It wants one alert rule per subscription that fires a separate alert for each VM that behaves abnormally, without paging on the normal Monday peak and without writing custom code. Which solution should you recommend with the LEAST operational overhead?
A: A multi-resource metric alert rule per subscription on CPU and network in, using dynamic thresholds for every VM in the region
B: A multi-resource metric alert rule per subscription on CPU and network in, using one static threshold at twice the fleet's average value
C: A scheduled log search alert per subscription whose KQL compares each VM's counters with that VM's own average over the past week
D: An Azure Automation runbook that recalculates each VM's static threshold every night and rewrites the matching metric alert rules
K: A
G: ## Two decisions in one alert design
An alert rule needs a **scope** (which resources) and a **threshold** (what is abnormal).
- Scope: a metric alert rule can monitor many resources of the same type in the same region with one rule. Azure Monitor tracks each VM as its own time series and sends an individual notification per VM.
- Threshold: a **static** threshold is one number for everything. A **dynamic** threshold uses machine learning on the metric's history and learns hourly, daily and, after about three weeks of data, weekly patterns, separately for every time series.
## Why it matters here
The VMs have different baselines and a weekly rhythm. One static number either fires every Monday for busy VMs or never fires for quiet ones. Dynamic thresholds give each VM its own band and need no tuning or code.
W: Dynamic thresholds, multi-resource rule: one rule per subscription covers every VM in the region, each VM is evaluated as its own series with a learned daily and weekly band, so Monday peaks are normal and nobody tunes numbers.
X: B=Static threshold at twice the average: one number for 220 different VMs is too high for quiet VMs and too low for busy ones, so it misses real anomalies and pages on normal peaks.
C=Log search alert with KQL baseline: it can work, but it is custom query logic the team must write and maintain, it needs the counters in a workspace, and it reimplements what dynamic thresholds already do.
D=Nightly runbook: it is custom code to build and run, it still produces static thresholds that ignore the time of day, and it multiplies the number of rules to manage.
T: Many resources with different, seasonal baselines → one multi-resource metric alert rule with dynamic thresholds.
V: Azure Monitor alerts, Azure Virtual Machines

@ AZ-305 D1 T1.1 advanced troubleshooting
S: An ASP.NET Core app sends about 400 GB of Application Insights telemetry per month, and the bill has doubled. The app is frozen for a regulatory audit, so no code or configuration change can be redeployed for three months, and the SDK's own sampling is turned off in the deployed settings. Developers must still be able to open a failed request and see its related exceptions and dependency calls. What should you recommend to cut ingestion cost now?
A: Turn on ingestion sampling on the Application Insights resource at about 25%, so the endpoint keeps each operation's related items together
B: Set a daily cap on the Application Insights resource at about half of today's average daily volume, so ingestion stops once the cap is reached each day
C: Enable adaptive sampling in the SDK with a target of five telemetry items per second, so the volume drops automatically during traffic peaks
D: Lower the workspace retention for the Application Insights tables from 90 days to 30 days, so less telemetry is kept and billed every month
K: A
G: ## Three places to sample
Application Insights offers three kinds of sampling:
- **Adaptive sampling** and **fixed-rate sampling** run in the SDK inside the app. They reduce the traffic the app sends, but changing them means changing and redeploying the app or its configuration.
- **Ingestion sampling** runs at the Application Insights service endpoint. It discards a share of incoming telemetry at a rate you set, and you can change it without redeploying. It only applies when the SDK is not already sampling.
## What sampling keeps
The sampling algorithm keeps or drops whole operations (by operation ID). When a failed request is kept, its exceptions and traces are kept with it, and the portal renormalizes counts so metrics stay statistically correct.
## Daily cap is a different tool
A daily cap stops collecting data once the cap is hit, so everything after that point of the day is lost, including failures.
W: Ingestion sampling: it is set on the resource, needs no redeployment, works because SDK sampling is off, and keeps the telemetry of each sampled operation together.
X: B=Daily cap: it does lower the bill, but once the cap is reached it drops all telemetry for the rest of the day, so later failures can't be investigated at all.
C=Adaptive sampling in the SDK: it would reduce volume, but it is SDK configuration that must be redeployed, which the audit freeze forbids.
D=Shorter retention: ingestion is billed when data arrives, so cutting retention below the included period barely changes this bill and doesn't reduce the 400 GB at all.
T: Need to cut Application Insights volume without redeploying → ingestion sampling at the service endpoint (only when the SDK isn't sampling).
V: Application Insights, Azure Monitor

A partner's SIEM, which reads only from Azure Event Hubs, must receive every new row of those three tables within minutes. None of this data comes from diagnostic settings, and the team will not run scheduled query code. Which solution should you recommend?
A: A Log Analytics data export rule for the three tables with an Event Hubs namespace as the destination, exporting new data as it arrives
B: A diagnostic setting on the Log Analytics workspace resource that sends its allLogs category group to the partner's Event Hubs namespace

@ AZ-305 D1 T1.2 advanced use-case
S: A company runs 60 Azure SQL logical servers across 15 subscriptions under one management group. An audit found shared SQL logins in connection strings, so every connection must now use Microsoft Entra identities, including servers created later. Database teams hold the SQL Server Contributor role and must not be able to switch SQL authentication back on. Which solution should you recommend?
A: Enable Microsoft Entra-only authentication on every server and enforce it with a built-in Azure Policy assigned at the management group
B: Drop every SQL login and contained SQL user with a T-SQL script on each server, and run the script again every week to catch any new logins
C: Set a Microsoft Entra administrator on every server and add a Conditional Access policy that requires MFA for the Azure SQL Database app
D: Enable Microsoft Defender for SQL on the subscriptions and send its alerts on SQL authentication attempts to the security operations team
K: A
G: ## Turning SQL authentication off
**Microsoft Entra-only authentication** is a server (or managed instance) setting. When it's on, SQL authentication is disabled for the whole server, including the server admin login: existing SQL logins remain in the database but can't connect, and new SQL logins can be created but can't connect either.
## Who can change it
Separation of duties is built in: Owners, Contributors and **SQL Security Manager** can enable or disable it, but **SQL Server Contributor** and **SQL Managed Instance Contributor** can't. That protects the setting from the database teams.
## Covering new servers
Azure Policy has built-in definitions that require Entra-only authentication; assigned at a management group with deny, they stop new servers from being created without it.
W: Entra-only authentication plus policy: the setting blocks all SQL-authenticated connections, the database teams' role can't disable it, and the management-group policy covers servers created later.
X: B=Weekly T-SQL cleanup: logins created between runs still work for up to a week, and the server admin SQL login remains usable, so SQL authentication is never actually off.
C=Entra admin plus Conditional Access: adding an Entra admin enables Entra sign-in but leaves SQL authentication on, and Conditional Access can't affect SQL logins at all.
D=Defender for SQL alerts: it detects suspicious activity after the fact; it doesn't stop SQL logins from connecting or keep the setting from being changed.
T: Force Entra-only connections to Azure SQL at scale → enable Microsoft Entra-only authentication and enforce it with Azure Policy.
V: Azure SQL Database, Microsoft Entra ID, Azure Policy

@ AZ-305 D1 T1.2 advanced use-case
S: A storage account receives invoice uploads from a partner whose staff have no identities in your tenant. Compliance now forbids account keys for any data access, so Shared Key authorization will be disallowed on the account. Partners must still get upload links that work for only a few hours, and a backend web app with a managed identity creates those links. Which solution should you recommend?
A: Set AllowSharedKeyAccess to false and have the web app use its managed identity to get a user delegation key and issue user delegation SAS links
B: Set AllowSharedKeyAccess to false and have the web app create service SAS links that are signed with a storage account key stored in Key Vault

- A **service SAS** or **account SAS** is signed with the storage **account key**, so it is a form of Shared Key authorization.

When `AllowSharedKeyAccess` is `false`, requests signed with the account key (including service and account SAS) are denied. A user delegation SAS is authorized through Microsoft Entra ID, so it still works on Blob Storage.
## Example
The web app's managed identity has Storage Blob Data Contributor on container `invoices`, calls Get User Delegation Key, and returns a write-only SAS that expires in three hours.
W: User delegation SAS: it keeps time-limited links for partners without identities, is signed with an Entra-issued key rather than an account key, and keeps working when Shared Key is disallowed.
X: B=Service SAS with key in Key Vault: a service SAS is still signed with the account key, so it violates the rule and is rejected once Shared Key access is disallowed.
C=Rotating keys every few hours: account keys are still used for data access, which compliance forbids, and rotation would break links already handed out.
D=B2B guests with RBAC: it adds identities for every partner user that the business wants to avoid, and it gives standing access instead of short-lived upload links.
T: Need SAS links but no account keys → disallow Shared Key and issue user delegation SAS from an Entra identity.
V: Azure Blob Storage, Microsoft Entra ID, Managed identities

@ AZ-305 D1 T1.2 advanced use-case
S: A company syncs 40,000 users with Microsoft Entra Connect Sync and password hash synchronization, and it relies on custom sync rules that only Connect Sync supports. Its single sync server runs in the main datacenter. If that server or datacenter fails, synchronization and password hash sync must resume within one hour, with configuration identical to production. Which solution should you recommend?
A: A second Entra Connect Sync server in staging mode in the secondary datacenter, with the same configuration, ready to switch to active
B: A second Microsoft Entra Connect Sync server in active mode in the secondary datacenter, exporting to the same tenant at the same time as the first
C: Daily Azure Backup of the sync server VM, restored into the secondary datacenter's network and started after a datacenter failure is declared

C=Restore from daily backup: restoring and starting a day-old VM takes long and needs a full sync to catch up, so the one-hour target is at risk.
D=Cloud Sync agent: Cloud Sync doesn't support the custom sync rules this company depends on, and it doesn't take over a Connect Sync configuration.
T: Fast recovery for Microsoft Entra Connect Sync → a second server in staging mode in another site.
V: Microsoft Entra Connect, Microsoft Entra ID

@ AZ-305 D1 T1.2 advanced use-case

Each service must get only its own permissions, and security forbids client secrets or certificates stored in the cluster or in pipelines. Auditors also want each service's access to show up as a distinct identity in the logs. Which solution should you recommend with the LEAST ongoing secret management?

@ AZ-305 D1 T1.3 advanced troubleshooting

It should deploy a diagnostic setting to every key vault, and its details section holds only existenceCondition and deployment. New key vaults still show no diagnostic setting and the deployments fail, and the 300 existing vaults are listed as non-compliant. The team needs both new and existing vaults fixed. Which THREE actions should you recommend? (Select THREE)
A: Add the roles that the deployment needs to the roleDefinitionIds property in the details section of the custom policy definition
B: Give the policy assignment a managed identity and grant that identity those roles at the management group where the policy is assigned
C: Create a remediation task for the assignment so that the deployIfNotExists template is deployed to the existing non-compliant vaults

G: ## ExpressRoute Direct
ExpressRoute Direct gives you **dedicated physical ports** into the Microsoft global network at a peering location: dual 10-Gbps, 100-Gbps or 400-Gbps ports in active-active. It suits large data ingestion and industries that need **physical isolation**, and you create the circuits on your own ports.
## MACsec
**MACsec** (IEEE 802.1AE) encrypts traffic at layer 2 between your edge routers and Microsoft's edge routers. It is configured on ExpressRoute Direct ports, with keys stored in Azure Key Vault.
## Provider circuits
A normal ExpressRoute circuit runs over a provider's shared infrastructure; MACsec isn't available on it, and encryption would have to be added at a higher layer, such as IPsec.
W: ExpressRoute Direct with MACsec: dedicated 100-Gbps ports give physical isolation and headroom above 60 Gbps, and MACsec encrypts the router-to-Microsoft link at layer 2.
X: B=Provider circuits with IPsec: the ports are shared provider infrastructure, IPsec is layer 3 not layer 2, and VPN gateway throughput limits the encrypted traffic.
C=Virtual WAN with Azure Firewall: Virtual WAN still uses a shared provider circuit, and Azure Firewall inspects traffic; it doesn't encrypt the physical link.
D=Site-to-site VPN: VPN traffic crosses the internet, and VPN gateway bandwidth is far below 60 Gbps of steady traffic.
T: Dedicated physical ports plus layer 2 encryption to Azure → ExpressRoute Direct with MACsec.
V: Azure ExpressRoute

@ AZ-305 D4 T4.4 advanced use-case
S: A hub virtual network hosts two SD-WAN appliances that learn hundreds of branch prefixes, and the list changes weekly. Today engineers update user-defined routes in 40 spoke subnets by hand, and mistakes have caused outages. The company wants spoke VMs to learn the branch routes automatically from the appliances, and the appliances to learn the virtual network prefixes, without replacing the hub design. Which solution should you recommend?
A: Azure Route Server in the hub, peering over BGP with both SD-WAN appliances so learned routes are programmed automatically
B: An Automation runbook that reads the appliances' route tables every hour and rewrites the user-defined routes in all spoke subnets
C: A VPN gateway in the hub with BGP, and IPsec tunnels from both SD-WAN appliances to the gateway to exchange the branch routes
D: A Virtual WAN hub that replaces the existing hub, with the SD-WAN appliances redeployed as partner appliances inside the new hub
K: A
G: ## Dynamic routing for network virtual appliances
Without help, Azure only knows routes from the virtual network, peering, gateways and **user-defined routes (UDRs)**. A network virtual appliance (NVA) that learns routes over BGP can't tell Azure about them.
**Azure Route Server** is a managed service that peers over **BGP** with NVAs in the virtual network. It programs the routes the NVAs advertise (for example branch prefixes) into the Azure SDN, so VMs use them without UDRs, and it advertises the virtual network prefixes back to the NVAs. With peering configured to use the remote gateway or route server, spokes learn the routes too.
W: Route Server: BGP sessions with both appliances keep routes in step automatically in both directions, inside the existing hub, with no UDRs to maintain.
X: B=Hourly runbook: it automates the same fragile UDR edits, routes can be up to an hour stale, and a runbook bug can still break every spoke.
C=VPN gateway with BGP tunnels: it adds IPsec tunnels inside the virtual network just to exchange routes, which is a workaround that Route Server makes unnecessary.
D=Virtual WAN replacement: it can work, but replacing the hub is exactly the redesign the company wants to avoid.
T: NVAs that must exchange routes with Azure dynamically → Azure Route Server (BGP), not hand-maintained UDRs.
V: Azure Route Server, Azure Virtual Network

@ AZ-305 D4 T4.4 advanced use-case
S: A central network team must block inbound RDP and SSH from the internet on about 300 virtual networks across 60 subscriptions, including virtual networks created later. Application teams own their NSGs and must not be able to override this rule with an NSG allow rule. The design should not route traffic through a new firewall. Which TWO components should you recommend? (Select TWO)
A: An Azure Virtual Network Manager security admin configuration with Deny rules for inbound TCP 3389 and 22 from the internet
B: A network group in Azure Virtual Network Manager with dynamic membership defined by Azure Policy conditions on the virtual networks
C: An Azure Policy definition that denies NSG rules allowing TCP 3389 or 22 from any source, assigned at each subscription separately
D: An Azure Firewall in each region's hub with DNAT disabled, and route tables that send all inbound internet traffic to the firewall
E: An Azure Virtual Network Manager security admin rule with the Always Allow action for TCP 3389 and 22 from the operations jump hosts only
K: A,B
G: ## Security admin rules
Azure Virtual Network Manager (AVNM) applies **security admin rules** to all virtual networks in a **network group**. They are **evaluated before NSG rules** and have higher priority:
- **Deny** stops traffic regardless of any NSG allow.
- **Allow** lets traffic continue to NSG evaluation.
- **Always Allow** permits traffic and skips NSG evaluation.
## Network groups
Membership is **static** (pick virtual networks) or **dynamic**, where Azure Policy evaluates conditions you define (subscription, tag, name) and virtual networks that match join the group automatically.
## Example
Network group `all-spokes` (dynamic: every virtual network under management group `Corp`) plus a security admin configuration with Deny for `Internet` → TCP 3389, 22.
W: A=Security admin Deny rules: they are evaluated before NSGs, so no team's NSG allow can reopen RDP or SSH.
B=Dynamic network group: Azure Policy conditions add new virtual networks to the group automatically, so the rule covers networks created later.
X: C=Policy deny on NSG rules: it blocks new allow rules but doesn't block traffic itself, can't fix rules that already exist, and per-subscription assignment misses new subscriptions.
D=Azure Firewall in hubs: it adds the firewall routing the design excludes, and VMs with public IPs in spokes would still bypass it.
E=Always Allow rule: it permits traffic and skips the NSGs entirely, which opens access instead of blocking it.
T: Central network rules that NSG owners can't override → AVNM security admin rules on a (dynamic) network group.
V: Azure Virtual Network Manager, Azure Policy
