@ AZ-305 D3 T3.2 applied troubleshooting
S: A company runs a line-of-business web tier on two VMs that it deployed to availability zone 1 of a region with three zones. A zone 1 outage took the whole application offline. The tier must survive the loss of any single zone. Which solution should you recommend?
A: Move both VMs into an availability set in zone 1 so that they are placed in separate fault domains and update domains.
B: Run the VMs as zonal instances spread over zones 1, 2 and 3, behind a load balancer with a zone-redundant frontend.
C: Keep both VMs in zone 1 and convert their managed disks to zone-redundant storage so the data survives a zone loss.
D: Place both VMs in a proximity placement group in zone 1 and add a third VM in the same group to provide spare capacity.
K: B
G: ## Zonal, zone-redundant and nonzonal resources
An availability zone is a group of one or more datacenters in a region with its own power, cooling and networking. Azure resources relate to zones in three ways:
- **Zonal**: you pin the resource to one zone you choose. It is isolated from faults in other zones, but it is **not** resilient to an outage of its own zone.
- **Zone-redundant**: the service itself spreads instances or data over several zones and fails over between them for you.
- **Nonzonal (regional)**: Azure places the resource anywhere in the region; an outage of any zone may hit it.
## Making zonal VMs zone-resilient
Microsoft's guidance is that zonal resources become zone-resilient only when **you** deploy separate instances in several zones and handle failover yourself. For VMs the usual pattern is VMs in zones 1, 2 and 3 behind a Standard Load Balancer whose frontend is zone-redundant; health probes take a failed zone's VMs out of rotation.
## Example
Web VMs `web-1` (zone 1), `web-2` (zone 2), `web-3` (zone 3) behind one zone-redundant frontend: losing zone 2 leaves two VMs serving traffic through the same IP address.
W: Zonal VMs across zones: spreading the instances over three zones and fronting them with a zone-redundant load balancer means one zone outage removes only that zone's VMs while the others keep serving through the same frontend.
X: A=Availability set in zone 1: an availability set spreads VMs over fault and update domains within one datacenter's infrastructure, so it guards against rack and maintenance failures but not against losing the zone that holds every VM.
C=ZRS disks in zone 1: zone-redundant disks keep the data available, but the compute is still only in zone 1, so the application stays down until someone builds new VMs elsewhere and attaches the disks.
D=Proximity placement group: a proximity placement group keeps VMs physically close for low latency, which is the opposite of spreading them; adding a third VM in the same zone adds capacity, not zone resilience.
T: A zonal resource is never resilient to its own zone's outage; deploy instances in several zones (or use a zone-redundant service) behind a zone-redundant entry point.
V: Azure Virtual Machines, Azure Load Balancer

@ AZ-305 D3 T3.2 applied use-case
S: A company must deploy a two-VM application in an Azure region that has no availability zones. The design must reduce the chance that one hardware rack, power or network switch failure, or a platform maintenance event, takes both VMs down. Which solution should you recommend?
A: Deploy the VMs as zonal instances in zone 1 and zone 2, and use zone-redundant managed disks for every data disk.
B: Deploy each VM on its own Azure dedicated host so that no other customer's workloads share the physical servers.
C: Deploy both VMs into one availability set so that Azure places them in separate fault domains and update domains.
D: Deploy both VMs with Ultra Disks, which replicate synchronously across datacenters in the region for redundancy.
K: C
G: ## Availability sets
An availability set is a logical grouping of VMs that tells Azure how to spread them inside a region's datacenter infrastructure:
- **Fault domains** (up to 3) are groups of VMs that share a power source and network switch. VMs in different fault domains don't fail together when one rack or switch fails.
- **Update domains** (up to 20) are groups that Azure restarts together during planned maintenance; only one update domain is restarted at a time.
The set itself is free; you pay only for the VMs. Microsoft calls availability sets especially useful in regions that don't support availability zones.
## Limits and trade-offs
- An availability set does not protect against a datacenter-level outage; availability zones give more resilience where they exist.
- Availability sets give lower VM-to-VM latency than zones because the VMs sit physically closer.
- Microsoft now recommends Virtual Machine Scale Sets with Flexible orchestration for new designs; they also spread VMs over fault domains when no zones are used.
W: Availability set: the two VMs land in different fault domains and update domains, so a single rack, power or switch failure or one maintenance wave affects at most one of them, and it works in a region without zones.
X: A=Zonal VMs and ZRS disks: the region has no availability zones, so neither zonal VMs nor zone-redundant disks can be deployed there.
B=Dedicated hosts: a dedicated host gives physical isolation from other customers for compliance or licensing; it does not by itself spread the two VMs across fault and update domains.
D=Ultra Disks: Ultra Disks are locally redundant high-performance disks; they don't replicate across datacenters, and disk choice does nothing about both VMs restarting in the same maintenance wave.
T: In a region without zones, an availability set (or a Flexible scale set spread over fault domains) protects VMs from rack-level failures and maintenance, not from datacenter loss.
V: Azure Virtual Machines, availability sets

@ AZ-305 D3 T3.2 advanced comparison
S: A company needs a VM fleet that spreads across three availability zones, mixes Spot and regular-priority VMs, and protects each instance with Azure Backup and Azure Site Recovery like a standalone VM. Which compute option should you recommend?
A: A Virtual Machine Scale Set that uses Flexible orchestration, with its instances spread across availability zones 1, 2 and 3.
B: A Virtual Machine Scale Set that uses Uniform orchestration, with its instances spread across availability zones 1, 2 and 3.
C: One availability set per availability zone, each holding a mix of Spot and regular VMs, joined behind one load balancer.
D: Individual VMs grouped in a proximity placement group that spans zones, with Spot priority enabled on half of the VMs.
K: A
G: ## Two orchestration modes
The orchestration mode is chosen when a scale set is created and can't be changed later.
- **Flexible** (Microsoft's recommended mode): instances are standard Azure VMs (`Microsoft.Compute/virtualMachines`). You manage them with the normal VM APIs, and features such as tagging, RBAC, Azure Backup and Azure Site Recovery work on each instance. A Flexible set can hold Spot and regular instances together and different VM sizes, and spreads instances over zones or fault domains.
- **Uniform**: instances are scale-set-specific VMs built from one profile. They don't support standard VM API commands, Azure Backup or Azure Site Recovery, and a set's instances must be all Spot or all regular.
## Where availability sets fit
Availability sets don't support availability zones and allow regular-priority VMs only.
W: Flexible orchestration across zones: Flexible scale sets manage ordinary VMs, so each instance supports Azure Backup and Site Recovery, can mix Spot and regular priority, and can be spread over the three zones.
X: B=Uniform orchestration: Uniform instances aren't compatible with Azure Backup or Site Recovery, and a Uniform set must be entirely Spot or entirely regular.
C=Availability set per zone: availability sets don't support availability zones and accept only regular-priority VMs, so neither the zone placement nor the Spot mix works.
D=Proximity placement group across zones: a proximity placement group keeps VMs close together for latency and is used within one zone or none; it is not a way to spread instances across zones.
T: For zone-spread fleets that need per-VM features (Backup, Site Recovery, mixed Spot), choose Virtual Machine Scale Sets with Flexible orchestration.
V: Azure Virtual Machine Scale Sets, Azure Backup, Azure Site Recovery

@ AZ-305 D3 T3.2 applied tradeoff
S: An Azure SQL Database runs on the Standard tier of the DTU purchasing model. It must now stay available with no loss of committed data if one availability zone fails, at the lowest cost and without adding another region. Which solution should you recommend?
A: Keep the Standard DTU tier and enable the zone-redundant setting on the database, which needs no service tier change.
B: Add an active geo-replication secondary on another logical server in the same region and fail over to it manually.
C: Keep the Standard DTU tier and change the backup storage redundancy of the database to zone-redundant storage.
D: Move the database to the General Purpose vCore service tier and enable zone redundancy on the database.
K: D
G: ## Local versus zone redundancy in Azure SQL Database
By default a database is **locally redundant**: failovers happen inside one datacenter. If the whole zone fails, the database can be unavailable until the outage ends or until you use a disaster recovery option such as a geo-failover.
**Zone redundancy** places compute and storage in two or more zones of the region, and Microsoft states that every implementation gives an RPO of zero committed-data loss when one zone fails.
## Which tiers support zone redundancy
- General Purpose, Business Critical and Hyperscale (vCore): yes.
- Premium (DTU): yes.
- Basic and Standard (DTU): no.
General Purpose keeps data and log files on zone-redundant storage and keeps spare stateless compute nodes in other zones; it is the budget-oriented tier among those that support zone redundancy.
W: General Purpose with zone redundancy: General Purpose is the lower-cost vCore tier that supports zone redundancy, giving zero committed-data loss in a zone outage without a second region.
X: A=Zone-redundant Standard DTU: the Basic and Standard DTU tiers don't support zone redundancy, so the setting isn't available without changing tier.
B=Same-region geo-secondary: Microsoft states that a geo-replica in the same region doesn't guarantee availability zone isolation and isn't a suitable failover target; it also doubles compute cost and needs manual failover.
C=ZRS backup storage: backup storage redundancy decides where backups are kept for restores; the running database still fails over only within one datacenter.
T: Zone redundancy in Azure SQL Database needs a vCore tier (General Purpose, Business Critical, Hyperscale) or DTU Premium; Basic and Standard can't be zone redundant.
V: Azure SQL Database

@ AZ-305 D3 T3.2 applied use-case
S: An order system uses five Azure SQL databases on one logical server in West Europe. In a regional outage, all five must fail over together to North Europe, and the application's connection strings must not change. Which solution should you recommend?
A: Configure active geo-replication separately for each database and have the application track which server is primary.
B: Enable zone redundancy on every database and rely on the region's availability zones to absorb the regional outage.
C: Create a failover group to a server in North Europe and connect the application to the group's read-write listener.
D: Configure geo-redundant backup storage and plan to geo-restore all five databases into North Europe during an outage.
K: C
G: ## Failover groups
A failover group is a named group of databases on one logical server that is replicated to a logical server in **another region** and fails over **as a unit**. It is built on top of active geo-replication and adds:
- **Listeners**: a read-write listener (`<fog-name>.database.windows.net`) that always points to the current primary, and a read-only listener (`<fog-name>.secondary.database.windows.net`) for readable secondaries. After a geo-failover the DNS records are updated automatically, so connection strings stay the same.
- **Group failover**: one action switches all secondaries in the group to primary.
## Active geo-replication on its own
Active geo-replication is configured per database. After a failover the new primary is on a different logical server, so its connection endpoint changes.
## Not a regional answer
Zone redundancy survives a zone outage, not a region outage. Geo-restore recovers from backups, so the RPO and RTO are much longer than with a replicated secondary.
W: Failover group with listener: the five databases replicate to North Europe and fail over together, and the read-write listener follows the primary, so the application keeps the same connection string.
X: A=Per-database geo-replication: each database fails over separately and the endpoint moves to another server, so the application would have to change connections and coordinate five failovers.
B=Zone redundancy: zones protect against losing a datacenter group inside West Europe, not against an outage of the whole region.
D=Geo-restore: restoring from geo-redundant backups creates new databases with new endpoints and takes far longer, and the latest transactions since the last replicated backup are lost.
T: Several databases that must fail over together with an unchanged connection string point to an Azure SQL failover group and its listeners.
V: Azure SQL Database

@ AZ-305 D3 T3.2 advanced tradeoff
S: A company uses an Azure SQL Database failover group. Its RTO for a regional outage is 30 minutes, and it wants to decide itself when to fail over after checking dependent services. Which failover policy should you recommend?
A: Customer managed failover policy, with the operations team initiating a failover of the group when an outage is confirmed.
B: Microsoft managed failover policy with the grace period set to a few minutes, so that Azure starts the failover quickly.
C: Microsoft managed failover policy, because Azure fails over only the affected group and checks dependent services first.
D: No failover policy, because the read-write listener moves to the secondary automatically as soon as the primary is down.
K: A
G: ## Two failover policies
- **Customer managed** (Microsoft's recommendation; `manual` in CLI and API): you start a failover, or a forced failover, of a specific group when you decide it's needed.
- **Microsoft managed** (`automatic`): during a widespread regional outage the Azure SQL team triggers forced failover of **all** Microsoft-managed groups in the region after a grace period that **can't be set below one hour**. It ignores your application's dependencies and the synchronization state, so data loss is unknown.
Microsoft states to use Microsoft managed only when the application tolerates at least one hour of database downtime and you want to hand over the decision.
## Listener behaviour
The listener follows whichever server holds the primary role; it doesn't create a failover by itself.
W: Customer managed policy: it keeps the timing in the team's hands, lets them check dependent services first, and allows a failover well inside a 30-minute RTO.
X: B=Short grace period: the grace period of a Microsoft managed policy can't be lower than one hour, so the RTO would already be missed, and the team wouldn't control the decision.
C=Microsoft managed as selective: Microsoft managed failover acts on all such groups in the region at once and explicitly doesn't consider the application's dependencies.
D=Listener-driven failover: the listener only points to the current primary; something must still fail over the group before the listener moves.
T: Use the customer managed failover policy when the RTO is under an hour or you need to control when and which group fails over.
V: Azure SQL Database

@ AZ-305 D3 T3.2 applied use-case
S: A single Azure SQL database in East US serves read-heavy reporting from users in Europe and Asia. The design needs readable copies in West Europe and Southeast Asia that can also be promoted if East US fails. Which solution should you recommend?
A: Enable read scale-out on a Business Critical database so that the built-in replicas serve the reports from each continent.
B: Configure active geo-replication with geo-secondaries in West Europe and Southeast Asia and route reports to them.
C: Enable zone redundancy on the database so that replicas are placed in availability zones close to each user group.
D: Create two copies of the database each night with a database copy job and point the regional reports at the copies.
K: B
G: ## Active geo-replication
Active geo-replication continuously replicates a database to readable **geo-secondaries** on other logical servers by asynchronously streaming the transaction log.
- Up to **four** geo-secondaries per primary, normally in other regions.
- Each secondary is readable, so it can offload read-only queries near the users.
- Any secondary can be promoted with a planned failover (no data loss) or a forced failover (possible data loss); the other secondaries then link to the new primary.
## Other read options
- **Read scale-out** (Business Critical, Premium) uses the high-availability replicas that sit in the same region as the primary.
- **Zone redundancy** spreads replicas over zones inside one region; it doesn't put copies on other continents.
W: Active geo-replication to two regions: each geo-secondary is a readable, continuously updated copy close to its users and can be promoted if East US fails.
X: A=Read scale-out: the built-in read replicas live in the primary's region, so European and Asian users still read from East US and the replicas can't serve as a cross-region failover target.
C=Zone redundancy: availability zones are inside one region, so zone redundancy gives no copies in Europe or Asia.
D=Nightly database copies: copies are a day old, aren't kept in sync and can't be promoted as a current primary, so they meet neither the freshness nor the failover need.
T: Readable, promotable copies of one database in other regions are what active geo-replication provides (up to four geo-secondaries).
V: Azure SQL Database

@ AZ-305 D3 T3.2 advanced use-case
S: A company must run SQL Server on Azure VMs because it uses instance-level features. The database layer needs automatic failover with no data loss if an availability zone fails. Which solution should you recommend?
A: A single SQL Server VM with zone-redundant Premium SSD disks, so the disks can be attached to a new VM after a zone failure.
B: Two SQL Server VMs in one availability set with an Always On failover cluster instance that uses a shared disk in one zone.
C: Azure Site Recovery replication of the SQL Server VM to another availability zone, with a recovery plan for failover.
D: An Always On availability group with synchronous-commit replicas on SQL Server VMs placed in different availability zones.
K: D
G: ## HA options for SQL Server on Azure VMs
- **Always On availability groups**: database-level protection. Replicas run on separate VMs; synchronous-commit replicas can fail over automatically without data loss. Microsoft recommends placing replicas in different availability zones for higher redundancy, and in other regions for disaster recovery.
- **Failover cluster instances (FCI)**: instance-level HA that needs shared storage.
- **Availability sets**: place nodes in separate fault and update domains within a datacenter; they don't protect against losing a zone.
## Why Site Recovery isn't HA here
Azure Site Recovery replicates VMs for disaster recovery. Microsoft's managed disks guidance notes that cross-zone Site Recovery doesn't provide zero RPO, and failover is an orchestrated recovery, not an automatic database failover.
W: Availability group across zones: synchronous-commit replicas in other zones hold every committed transaction, and the cluster fails over automatically when the primary's zone fails.
X: A=Single VM with ZRS disks: the data survives, but recovery means force-detaching the disks and attaching them to another VM, which is a manual rebuild rather than automatic failover.
B=FCI in an availability set: an availability set doesn't span zones, so a zone outage can take down both nodes and the shared disk together.
C=Site Recovery to another zone: Site Recovery is a disaster recovery tool with a non-zero RPO and a recovery-plan failover, not automatic zero-loss failover.
T: For SQL Server on VMs that must survive a zone loss automatically, use an Always On availability group with synchronous replicas spread over availability zones.

@ AZ-305 D3 T3.2 applied use-case
S: Data residency rules allow a new Azure Cosmos DB for NoSQL account to store data in only one Azure region, which supports availability zones. The account must keep serving reads and writes if one zone fails, with no application code changes. Which solution should you recommend?
A: Create the account in that region with zone redundancy enabled, so that Azure spreads the replicas across availability zones.
B: Add a read region in a neighbouring country and enable service-managed failover, so the account fails over automatically.
C: Set the default consistency level to strong, so that every write is committed in replicas of several datacenters.
D: Enable multiple write regions on the account, so that each zone in the region accepts writes from the application.
K: A
G: ## Zone redundancy in Azure Cosmos DB
When zone redundancy is enabled for a region, Azure distributes that region's replicas across availability zones (Microsoft chooses the zones). A single-region, zone-redundant account keeps read and write availability when one zone fails.
- No discernible effect on performance or latency, no consistency change and no code change.
- Configured per region; Microsoft highly recommends it for single-region accounts and for single-write-region accounts.
- For most existing accounts it's set when a region is added; serverless accounts must enable it at creation.
## What it doesn't cover
A single-region account loses access if several zones or the whole region fail. Surviving that needs more regions, which this scenario's residency rule forbids.
W: Zone-redundant single region: replicas spread over the region's zones keep reads and writes running through a zone failure, without leaving the permitted region or changing code.
X: B=Read region abroad: a second region outside the allowed one breaks the data residency rule.
C=Strong consistency: consistency levels control what reads see across replicas and regions; they don't move a nonzonal account's replicas into separate zones.
D=Multiple write regions: multi-region writes apply to regions, not to zones inside one region, and would need more regions than residency permits.
T: For a Cosmos DB account restricted to one region, zone redundancy is the way to survive a zone outage; regions protect against regional outages.
V: Azure Cosmos DB

@ AZ-305 D3 T3.2 advanced comparison
S: A gaming company uses Azure Cosmos DB for NoSQL with players in four regions. Each region's app must write locally with low latency and keep writing during any single-region outage without waiting for a failover. Which configuration should you recommend?
A: One write region with three read regions, service-managed failover enabled, and failover priorities set for each region.
B: One write region with zone redundancy enabled in every region and the strong consistency level set as the account default.
C: Multiple write regions across all four regions, with a conflict resolution policy and SDK clients set to prefer their local region.
D: Multiple write regions across all four regions with strong consistency, so that writes never conflict between the regions.
K: C
G: ## Single-write versus multi-write accounts
- **Single write region** (with read regions): all writes go to one region. If it fails, writes stop until a region-offline operation, a forced failover or service-managed failover. Microsoft warns that service-managed failover can take **one hour or more**.
- **Multiple write regions**: every region accepts writes. If one region fails, SDK clients route to healthy regions without a failover step.
## Costs of multi-write
- Replication between regions is asynchronous; **strong consistency isn't supported** with multiple write regions.
- Writes to the same item in two regions can conflict, so you set a conflict resolution policy (last-writer-wins or custom). Unreplicated writes from a failed region appear in the conflict feed after recovery.
- Configure each client with a preferred region list so it writes to the nearest region.
W: Multi-region writes with conflict policy: each region writes locally with low latency, and when a region fails the SDK sends traffic to another write region immediately, so no failover has to finish first.
X: A=Single write region with service-managed failover: remote players write across regions, and writes wait for a failover that Microsoft says can take an hour or more.
B=Zone redundancy and strong consistency: zones protect against zone failure inside a region; with one write region a regional outage still stops writes, and strong consistency adds cross-region write latency.
D=Multi-write with strong consistency: strong consistency can't be used with multiple write regions, so this configuration isn't possible.
T: Local writes everywhere plus continuous write availability through a regional outage call for Cosmos DB multi-region writes with a conflict resolution policy.
V: Azure Cosmos DB

@ AZ-305 D3 T3.2 advanced tradeoff
S: A payments ledger on Azure Cosmos DB for NoSQL spans three regions. The business requires no loss of committed writes if a region fails and accepts higher write latency. Which design should you recommend?
A: Multiple write regions with session consistency, so that every region holds its own committed copy of each write.
B: A single write region with the strong consistency level, so writes commit only after the regions acknowledge them.
C: A single write region with bounded staleness consistency set to its minimum values for item versions and time.
D: Multiple write regions with eventual consistency and a last-writer-wins conflict resolution policy on each container.
K: B
G: ## Consistency level decides regional RPO
For accounts with two or more regions, Microsoft lists the RPO for a region outage by consistency level:
- Strong: 0.
- Bounded staleness: K versions and T time (minimum 100,000 writes or 300 seconds in multi-region accounts).
- Session, consistent prefix, eventual: less than 15 minutes.
## Strong consistency
A write is committed only when the account's regions acknowledge it, so reads always return the latest committed version and no committed write is lost. With three or more regions, "dynamic quorum" can drop one unresponsive region and keep writing. The price is higher write latency, and strong consistency can't be combined with multiple write regions.
W: Single write region with strong consistency: synchronous commit across regions gives an RPO of zero for a region outage, and the business has accepted the extra write latency.
X: A=Multi-write with session: session consistency replicates asynchronously to other regions, so recent writes in the failed region can be lost (RPO up to 15 minutes).
C=Bounded staleness at minimum: the lag bound in a multi-region account is still at least 100,000 writes or 300 seconds, so it isn't zero data loss.
D=Multi-write with eventual: eventual is the weakest level with asynchronous replication; last-writer-wins settles conflicts but doesn't prevent loss of unreplicated writes.
T: Zero RPO across regions in Cosmos DB needs strong consistency, which means a single write region and higher write latency.
V: Azure Cosmos DB

@ AZ-305 D3 T3.2 applied comparison
S: A web app stores product images in Azure Blob Storage. It must keep working through an availability zone outage in the primary region, and it must still be able to read the images if the primary region becomes unavailable, before any failover. Which redundancy option should you recommend?
A: Geo-zone-redundant storage (GZRS), which copies data across zones in the primary region and asynchronously to a secondary region.
B: Read-access geo-redundant storage (RA-GRS), which keeps three local copies in one primary datacenter plus a readable secondary.
C: Zone-redundant storage (ZRS), which copies data synchronously across three or more availability zones within the primary region.
D: Read-access geo-zone-redundant storage (RA-GZRS), which uses zones in the primary region and a readable copy in the secondary region.
K: D
G: ## Two questions decide storage redundancy
1. **Inside the primary region**: LRS keeps three copies in one datacenter; ZRS copies synchronously across three or more availability zones and stays readable and writable when a zone fails.
2. **To a secondary region**: GRS (LRS primary) and GZRS (ZRS primary) copy asynchronously to the paired secondary region.
## Read access to the secondary
With GRS or GZRS the secondary copy can't be read until you fail over the account. The **RA-** variants (RA-GRS, RA-GZRS) make the secondary always readable through a `-secondary` endpoint, for example `myaccount-secondary.blob.core.windows.net`, even while the primary region is down.
## Summary for this case
- Zone outage: needs ZRS-based primary (ZRS, GZRS, RA-GZRS).
- Reads during a regional outage without failover: needs RA-GRS or RA-GZRS.
Only RA-GZRS meets both.
W: RA-GZRS: zone-redundant copies keep reads and writes going through a zone outage, and the always-readable secondary endpoint lets the app read images while the primary region is down.
X: A=GZRS: the zone part is right, but the secondary can't be read until an account failover completes, which the requirement rules out.
B=RA-GRS: the secondary is readable, but the primary uses LRS in a single datacenter, so a zone outage can interrupt access until failover.
C=ZRS: it survives a zone outage but keeps no copy outside the primary region, so a regional outage leaves nothing to read.
T: Zone resilience means a ZRS-based option; reading during a regional outage without failover means an RA- option; both together is RA-GZRS.
V: Azure Blob Storage

@ AZ-305 D3 T3.2 applied use-case
S: A company hosts an SMB file share in Azure Files that application servers in three availability zones mount. If one zone fails, clients must keep using the share without remounting it. Which redundancy option should you recommend for the storage account?
A: Zone-redundant storage (ZRS), which writes every change synchronously to three or more availability zones in the region.
B: Locally redundant storage (LRS), which keeps three synchronous copies of the share inside one datacenter in the region.
C: Read-access geo-redundant storage (RA-GRS), which lets clients read the share from the secondary region during outages.
D: Geo-redundant storage (GRS), which copies the share asynchronously to the paired region for use after an account failover.
K: A
G: ## Azure Files and zones
Azure Files supports LRS, ZRS, GRS and GZRS (SSD file shares support LRS and ZRS only). It does **not** support the read-access options RA-GRS or RA-GZRS.
Microsoft recommends **ZRS** for Azure Files workloads: if a zone becomes unavailable, connected clients don't need to remount the share. A write returns only after it is stored in all available zones, so no acknowledged data is lost when a zone fails. Clients should still use retry logic, because DNS updates happen during a zone failure.
## Geo options
GRS and GZRS add an asynchronous copy in a secondary region, but that copy is usable only after an account failover; they protect against regional disasters, not zone outages (GRS keeps the primary copies in one datacenter).
W: ZRS: the share's data is synchronously stored in several zones, so a zone outage leaves the share available and Microsoft states clients don't need to remount it.
X: B=LRS: all copies are in one datacenter, so if that datacenter's zone fails the share is unavailable until the zone recovers.
C=RA-GRS: Azure Files doesn't support RA-GRS, and a read-only secondary wouldn't let the application servers keep writing.
D=GRS: the primary copies still sit in one datacenter, and the secondary is reachable only after an account failover, which interrupts clients.
T: For Azure Files that must ride through a zone outage without remounting, choose ZRS; RA- options aren't available for Azure Files.

G: ## Managed disk redundancy
Managed disks have two redundancy options:
- **LRS**: three copies in one datacenter; lowest write latency; lost with that zone.
- **ZRS**: synchronous copies across three availability zones; slightly higher write latency; survives a zone failure.

@ AZ-305 D3 T3.2 advanced tradeoff
S: A mission-critical retail platform must have near-zero downtime if an entire Azure region fails, and the business accepts higher infrastructure cost and operational complexity. Which multi-region approach should you recommend?
A: Active-passive with a cold spare region whose compute is fully sized but stopped and started only during a failover.
B: Active-passive with a warm spare region that runs minimum-sized compute and data and is scaled up after a failover.
C: A single region with zone-redundant services and deployments into its paired region scheduled after any outage.
D: Active-active deployment stamps in two or more regions, each serving live traffic and able to absorb the other's load.
K: D
G: ## Multi-region patterns
Azure Well-Architected describes redundancy at the workload level with **deployment stamps**: complete, self-contained copies of the workload.
- **Active-active**: all stamps serve traffic at once. If one fails, traffic is rerouted to healthy stamps without a failover step. Ideal for mission-critical workloads needing uninterrupted availability, at higher cost and complexity (data consistency, coordinated updates). Variants: *at capacity* (scale up after loss) or *overprovisioned* (already sized for the extra load).
- **Active-passive**: one location serves traffic; others stand by.
  - *Warm spare*: minimum-sized resources running without load; scaled after failover. Shortest recovery of the passive designs, highest passive cost.
  - *Cold spare*: full-size resources stopped; started during failover. Cheaper, slower.
Zones in one region protect against zone failure only; a full-region outage needs another region.
W: Active-active stamps: every region already serves live traffic, so losing one region just shifts users to the others with no activation delay, which is what near-zero downtime needs and the business accepts the cost.
X: A=Cold spare: the stopped compute has to be started before it can take traffic, giving the longest recovery of these options.
B=Warm spare: faster than cold, but there's still a failover and a scale-up period before the secondary handles full load.
C=Single region plus later deployment: zone redundancy doesn't survive a region outage, and building in the paired region after the event means hours of downtime; pairing doesn't add automatic failover.
T: Near-zero downtime through a region loss is active-active; active-passive (warm or cold) trades recovery time for lower cost.

@ AZ-305 D3 T3.2 applied tradeoff
S: A line-of-business app needs a second region for regional outages. It can tolerate a short recovery period, the budget rules out running full capacity twice, and the team wants the fastest recovery among active-passive designs. Which approach should you recommend?

B: A cold spare secondary region whose full-size compute is deployed but stopped and started only during a failover.

G: ## Active-passive options
Active-passive designs keep one region serving all traffic and another ready to take over.
- **Warm spare**: the secondary runs the smallest possible compute and data sizing, with no load, and is scaled up after failover. Microsoft lists it as the **shortest recovery time** among active-passive designs, with the **highest operating cost** among them.
- **Cold spare**: the secondary is sized for full load but its compute is **stopped**; it must be started before failover. Lower cost, longer recovery.
- **Redeploy on demand**: nothing runs in the secondary until needed, so recovery includes deployment time and depends on capacity being available.
## Active-active
All regions serve traffic; overprovisioned active-active means paying for spare full capacity in every region all the time.
W: Warm spare: it avoids paying for a second full-size environment yet recovers fastest of the passive designs, because services are already running and only need scaling.

@ AZ-305 D3 T3.2 applied troubleshooting
S: An architect proposes deploying an app's VMs and databases only into the primary region of an Azure region pair, saying the pairing alone will fail the workload over to the paired region in a regional outage. What should you tell the architect?
A: The proposal works for VMs only, because Azure Site Recovery is enabled automatically for every VM in a paired region.

G: ## What region pairs do and don't do
Some Azure regions are paired with another region in the same geography. Pairing gives platform-level benefits:
- **Recovery sequence**: in a geography-wide outage one region of each pair is prioritized for recovery.
- **Sequential updating**: Azure tries to stagger planned updates across the two regions of a pair.
- Some services use the pair by default for geo-replication, such as geo-redundant storage.
Microsoft states that deploying resources into a paired region **doesn't** automatically make them more resilient or provide automatic high availability, disaster recovery or failover. You plan your own HA and DR, whether or not you use pairs.
## Nonpaired regions
Many newer regions are nonpaired and rely on availability zones; many services replicate between any regions you choose, so a pair is not required for a multi-region design.

B=Automatic PaaS failover: PaaS services need their own geo-features (for example SQL failover groups or geo-redundant storage); pairing alone doesn't fail them over.
D=Tag-based failover: tags are metadata for organization and cost; they never trigger failover.
T: Region pairs don't give automatic failover; design replication and failover for every component, paired or not.
