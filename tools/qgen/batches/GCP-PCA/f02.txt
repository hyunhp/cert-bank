@ GCP-PCA D1 T1.2 applied definition
S: A broadcaster stores newly produced footage in a Cloud Storage dual-region bucket for a production tool that must continue after a regional outage. The business sets a recovery point objective of 15 minutes for newly written objects across both regions, and default replication targets are too slow for that. What should the architect enable?
A: The Archive storage class on the dual-region bucket, which lowers the cost of footage kept long term
B: A retention policy on the dual-region bucket, so new objects cannot be deleted for their first 15 minutes
C: Turbo replication, the premium replication option that comes with a much shorter copy-time objective
D: Object Versioning on the bucket, keeping older versions of objects overwritten or deleted in either region
K: C
G: ## Replication targets for dual-region buckets
Cloud Storage writes an object to one region across zones and then replicates it asynchronously to the other region of a dual-region bucket.
- **Default replication** targets 99.9% of newly written objects within one hour and 100% within 12 hours (most finish in minutes).
- **Turbo replication** is an optional, premium feature of dual-region buckets, designed to replicate 100% of newly written objects between the two regions within a recovery point objective of 15 minutes.
## Other features solve other problems
Versioning and retention protect against deletion or overwrite, and storage classes affect cost and access pattern. None of them changes how fast data reaches the second region. Note that replication is not a full BCDR plan on its own.
W: Turbo replication: it is designed to replicate 100% of newly written objects between the two regions of a dual-region bucket within 15 minutes, which is exactly the stated recovery point objective for new footage.
X: A=Archive storage class: this class lowers storage cost for rarely read data and has no effect on replication time, and it would make a production tool's reads slower and costlier.
B=Retention policy: it blocks deletion or replacement for a period, which supports compliance, not a replication time objective; a 15-minute lock does not move data to the second region any faster.
D=Object Versioning: it protects older object generations against overwrites and deletes, and it does not speed up copying to the second region.
T: To tighten the RPO of a dual-region Cloud Storage bucket, enable turbo replication; versioning, retention and classes address other needs.

@ GCP-PCA D5 T5.1 applied troubleshooting
S: EHR Healthcare suffered past outages in which email alerts went unnoticed. The operations lead wants to shorten the time from alert to understanding the cause across a multi-tier service. Which Gemini Cloud Assist capability helps most directly?
A: A replacement for Cloud Monitoring alerting policies, so the operations lead no longer needs to define or route any alerts
B: An automatic fix that applies production configuration changes without review when an alert fires in any tier of the service
C: Proactive investigations started by alerting policies, which group related alerts and draft a likely cause with next steps
D: Natural-language drafting of status-page notices as soon as an alert fires, so outages across the tiers are announced faster
K: C
G: ## AI-assisted operations
Gemini Cloud Assist is an AI collaborator across the application lifecycle: designing, deploying, troubleshooting and optimizing. For troubleshooting it offers:
- **Investigations**: AI-driven analysis that ingests logs, metrics and configuration, explores hypotheses in parallel and traces root causes across multi-tier topologies.
- **Proactive alert investigations**: an alerting policy can trigger Gemini Cloud Assist automatically; it analyzes the issue in the background, clusters related alerts and generates a preliminary root-cause analysis with recommended next steps.
- **Support handoff**: investigation results can be passed to Google Cloud support as context.
It builds on the signals you already collect; it does not replace alert definitions or human judgment.
## Availability
Gemini Cloud Assist capabilities differ in availability. Google's product page (cloud.google.com/products/gemini/cloud-assist, read 2026-10-31) labels the investigations tool and proactive investigations "private preview" and says Gemini Cloud Assist is in preview, while the documentation overview (docs.cloud.google.com/gemini/docs/cloud-assist/overview) shows no preview label on them. The exam guide names Gemini Cloud Assist, so know what each capability does, and check the current status before relying on it.
W: Proactive alert investigations: they start analysis when the alert fires, group related alerts and give a preliminary root-cause analysis and next steps, so the team does not depend on someone reading the email and starting from scratch.
X: A=Replace alerting policies: Gemini Cloud Assist is triggered by alerting policies and uses logs and metrics, so alerts are still needed.
B=Unreviewed automatic fixes: the capability produces analysis and recommendations; applying production changes unreviewed would add risk and contradict change control.
D=Status-page drafting: generating customer notices is communication work and does not diagnose the technical fault that delays recovery.
T: Alert-triggered investigations cut time to root cause by building on your monitoring, while humans keep control of changes.
V: Gemini Cloud Assist, Cloud Monitoring

@ GCP-PCA D2 T2.5 advanced use-case
S: A company already runs a customer-support virtual agent built with Dialogflow and a custom supply-chain agent built with the Agent Development Kit (ADK) and hosted on Agent Runtime. Leadership wants employees to reach both from the Gemini Enterprise web app without rebuilding them. Which TWO actions fit? (Select TWO)
A: Register the Dialogflow conversational agent as an available agent in the Gemini Enterprise app
B: Give each team the agents' API endpoints to build its own chat front end beside the Gemini Enterprise app
C: Rebuild both agents in Workflow Builder, since only agents made there can appear in the Gemini Enterprise app
D: Export the agents' prompts into Model Garden, where the Gemini Enterprise app lists them as tuned models
E: Register the ADK agent hosted on Agent Runtime as a custom agent in the Gemini Enterprise app
K: A,E
G: ## Agent types in Gemini Enterprise
Gemini Enterprise gives admins central oversight of the agents used by an organization, whoever built them:
- **Employee-made agents** built with Workflow Builder (no-code/low-code).
- **Google-made agents** such as the Core Assistant and Deep Research.
- **Custom agents:** ADK agents hosted on Agent Runtime on Agent Platform, agents built with the Agent2Agent (A2A) protocol, and conversational agents built with Dialogflow can be registered by admins so they appear in the web app.
Registering preserves the investment in existing agents and avoids rebuilding. Model Garden is a model catalog, not an agent directory.
W: A=Register the Dialogflow agent: admins can register Dialogflow conversational agents in Gemini Enterprise, which makes the support agent available without rebuilding it.
E=Register the ADK agent: ADK agents hosted on Agent Runtime can be registered as custom agents, which publishes the supply-chain agent to the same app.
X: B=Team-built front ends: this fragments the experience and defeats the goal of reaching both agents from one app with central governance.
C=Rebuild in Workflow Builder: registration of existing agents is supported, so rebuilding wastes work, and agents made elsewhere are not excluded from the app.
D=Export prompts to Model Garden: Model Garden catalogs models, not agents, and Gemini Enterprise does not list agents from it.
T: Existing Dialogflow, ADK and A2A agents are registered with Gemini Enterprise, not rebuilt.

@ GCP-PCA D4 T4.2 applied tradeoff
S: A four-person team with no container experience must run a stateless HTTP API that has variable traffic and no special networking needs. The platform decision is due this week. Which choice best reflects the team's skills and the requirements?
A: Compute Engine VMs behind a load balancer with software installed by hand, since VMs are familiar
B: Cloud Run: deploy a container and let the platform handle scaling, with GKE kept as a later option
C: A GKE Standard cluster with custom node pools, so that the team keeps full control of every node
D: Self-managed Kubernetes on Compute Engine for portability, learned by the team during the project
K: B
G: ## Operating burden is a design constraint
The Well-Architected operational excellence pillar asks you to match the solution to the team that will run it. Each platform moves some responsibility to the customer:
- Cloud Run: serverless; the team supplies a container, and Google manages servers, scaling (including to zero) and much of the operations.
- GKE: strong for complex, multi-service platforms, but cluster upgrades, node pools, networking and security policy are skills to build.
- Self-managed Kubernetes on VMs: most control and the highest operating burden.
## Decision under constraints
No special networking, stateless, variable traffic: nothing requires Kubernetes' extra control, while the skills gap is a real risk. Choose the simplest platform that meets the requirements and revisit if requirements change; a container is portable to GKE later.
W: Cloud Run: it fits a stateless, variable HTTP workload, minimizes operational skill needs and scales automatically, and the container image keeps a later move to GKE open.
X: A=Hand-installed VMs: familiar but manual and hard to scale or reproduce, which increases toil and risk.
C=GKE Standard with custom pools: still requires node and cluster operations skills the team lacks, for control nobody asked for.
D=Self-managed Kubernetes: highest operating burden, with the team learning on a production system; portability is not required by the stem.
T: Choose the simplest platform that meets the requirements for the team's skills; managed serverless reduces operating burden.
V: Cloud Run, GKE
