@ GCP-PCA D4 T4.1 applied troubleshooting
S: EHR Healthcare keeps legacy insurer interfaces on premises, linked to Google Cloud over a private connection. After a new claims service is deployed, the insurer's on-premises server cannot reach it, and network and platform teams each say their side is fine. Which first step most quickly shows where the packet path breaks?
A: Run Connectivity Tests from the on-premises source address to the claims service and read which route or firewall rule stops the path
B: Open a firewall rule that allows all ingress from any address to the claims service so the cause can be ruled out by trial and error
C: Delete and recreate the private connection to the on-premises data center, hoping that a reset restores whatever routes are missing
D: Enable Packet Mirroring on every subnet in the project and review the captured traffic once the next insurer attempt arrives
K: A
G: ## Troubleshooting a path, not a symptom
When two teams each report "our side is fine", the cheapest evidence is a model of the end-to-end path. Connectivity Tests, part of Network Intelligence Center, analyzes your configuration: it simulates the expected forwarding path of a packet through VPC networks, Cloud VPN tunnels and VLAN attachments, and for supported routes it also sends probe packets on the data plane for baseline latency and packet loss.
- A configuration analysis result names the step where the path ends, such as no matching route, an ingress rule that denies the packet, or a missing next hop.
- It works from an on-premises IP address to a cloud endpoint, so it fits hybrid designs like EHR Healthcare's.
- It changes nothing, so it is safe in production and gives both teams one shared fact.
## Root cause analysis habit
Form a hypothesis from evidence before changing anything. Opening firewalls or rebuilding links are changes with their own risk and can hide the cause.
W: Connectivity Tests: it simulates the path from the on-premises address to the endpoint and reports the route or firewall rule where it stops, so the owning team knows exactly what to fix without touching production.
X: B=Allow all ingress: this is a risky change that weakens the security of patient-related systems, and it does not help if the real fault is a missing route or an on-premises rule.
C=Recreate the connection: this causes an outage for every other insurer on that link and is guesswork; the link may be healthy while a route or rule for the new service is the problem.
D=Packet Mirroring everywhere: captures traffic only after it enters instances, costs effort and storage, and cannot show a packet that never reaches a VM because a route or rule dropped it.
T: To find where a network path breaks, test the path with Connectivity Tests before changing any configuration.
V: Network Intelligence Center, Cloud Interconnect

@ GCP-PCA D4 T4.1 applied troubleshooting
S: A team puts a new external Application Load Balancer in front of a managed instance group. Opening a VM's service port from inside the VPC returns the right page, yet every backend is reported unhealthy and users receive error responses. The instances were created in a VPC that has no custom firewall rules yet. What is the most likely cause?
A: The load balancer needs a static external IP address attached to each instance before health checks can succeed
B: The health check must use the same protocol as client traffic, so a TCP check cannot be used with an HTTPS frontend
C: The instance group was created as zonal, and zonal groups cannot receive health check probes from the load balancer
D: No ingress allow rule permits the Google Cloud health check probe ranges, so the implied deny rule blocks the probes
K: D
G: ## How health checks reach a backend
Load balancer health checks are sent by Google-operated probers from documented IP ranges, not from your VPC. A backend is healthy only when probes succeed. Google Cloud requires you to create ingress allow firewall rules that permit those probe ranges to the health check port; otherwise the implied deny ingress rule blocks them and the backends become unhealthy.
- A request from a VM inside your own VPC takes a different source address, so it can succeed while probes fail. This is why "it works from inside" does not prove the load balancer can reach it.
- Limit the rule to the protocols and ports that the health check uses, and use target tags or service accounts so it applies only to those instances.
## Troubleshooting order
1. Read the backend health state in the load balancer. 2. Compare the health check port and path with what the service listens on. 3. Check the firewall rules for the probe ranges.
W: Missing probe-range allow rule: the implied deny ingress rule drops the prober traffic, so every backend is unhealthy even though the service answers normally from inside the VPC.
X: A=External IP per instance: backends of an external load balancer do not need external addresses; probes and traffic use internal addresses and Google's paths.
B=Matching protocols: a health check protocol can differ from the traffic protocol as long as it targets the right port and the service answers; this is not what blocks probes here.
C=Zonal group: zonal and regional managed instance groups are both valid backends and receive probes; the group type does not explain all backends failing.
T: All backends unhealthy while the app works locally: allow the health check probe ranges in an ingress firewall rule.
V: Cloud Load Balancing, VPC firewall

@ GCP-PCA D4 T4.1 applied troubleshooting
S: Batch worker VMs in a private subnet have no external IP addresses. Security policy forbids any route from them to the public internet. After a new subnet is created, jobs that read from Cloud Storage and call Google APIs time out, while the same code worked in the older subnet. What should the architect check and fix first?
A: Add a Cloud NAT gateway for the subnet so workers can reach the storage endpoint over the public internet
B: Check that Private Google Access is on for the new subnet, since VMs without external IPs need it to reach Google APIs
C: Attach an external IP to each worker VM, then limit outbound traffic with firewall rules so that only the storage service is allowed
D: Move the workers to the default network where Google APIs are reachable without a subnet setting
K: B
G: ## Reaching Google APIs without the internet
VMs that have only internal IP addresses can reach the external IP addresses of Google APIs and services when Private Google Access is enabled. It is a per-subnet setting. If it is disabled, such VMs can send traffic only within the VPC network, which fits the symptom: the older subnet had it enabled, the new one did not.
- Private Google Access has no effect on VMs that have external IPs.
- Cloud NAT gives access to the public internet. That might make the job work, but it breaks the stated rule of no internet route.
## Why the symptom points at a subnet setting
Same code, new subnet, timeouts on Google APIs only: a difference in subnet configuration is a stronger hypothesis than an application bug.
W: Private Google Access: enabling it on the new subnet lets internal-only workers reach Google APIs and Cloud Storage while keeping them off the internet, as the security policy requires.
X: A=Cloud NAT: it provides outbound internet access, which the policy forbids, and it is unnecessary when Google APIs can be reached privately.
C=External IPs: giving workers public addresses contradicts the no-internet-route rule and widens the attack surface; firewall rules do not remove the public route.
D=Default network: this abandons the designed network, and it would not remove the need for the subnet setting; a default network is also not a production recommendation.
T: Internal-only VMs cannot call Google APIs until Private Google Access is on for their subnet.
V: VPC, Cloud Storage

@ GCP-PCA D4 T4.1 advanced troubleshooting
S: After a marketing event, a GKE Standard cluster with node autoscaling enabled leaves new Pods in Pending state for hours, although the node pool maximum is far above the current node count. Which TWO actions most directly reveal the root cause? (Select TWO)
A: Read the cluster autoscaler visibility events in Cloud Logging, especially noScaleUp entries, which state why scale-up was blocked
B: Double the CPU requests on all Deployments so the scheduler places the Pods on the nodes that already exist
C: Check project quotas for the machine type and the free IP addresses left in the Pod range of the subnet
D: Disable the autoscaler and add nodes by hand, then see whether the Pods start without further investigation
E: Delete the Pending Pods and recreate the Deployments, since stuck scheduling state is usually cleared by this
K: A,C
G: ## Why Pending Pods persist even though the maximum allows more nodes
The cluster autoscaler adds nodes when Pods cannot be scheduled and would fit on a new node. A node pool maximum is only a ceiling; many other limits can block a scale-up before it is reached: Compute Engine quota for the machine type or region, no free IP addresses in the subnet's Pod range, a Pod request larger than any node shape, or a resource not available in the zone.
- GKE writes visibility events to Cloud Logging. A noScaleUp event is emitted when there are unschedulable Pods and the autoscaler cannot scale the cluster up, with details of the Pods and node pools.
- Cloud Monitoring metrics show trends such as failed provisioning attempts and quota exhaustion.
## Evidence first
The two correct actions read what the system says about the block (logs) and check the usual external limits (quota and address space). Changing requests, bypassing the autoscaler or recreating objects treats the symptom or makes it worse.
W: A=Visibility events: noScaleUp events name the unschedulable Pods and the reason the autoscaler did not add nodes, which is the direct evidence of the root cause.
C=Quota and Pod IP space: exhausted machine-type quota or a full Pod secondary range are common reasons a scale-up fails even below the node pool maximum, so checking them confirms or rules out an external limit.
X: B=Higher CPU requests: raising requests makes Pods harder to place and needs even more capacity; it does not explain why scale-up is blocked.
D=Manual nodes: if quota or IP space is the limit, manual node creation fails for the same reason, and it hides the autoscaling fault for the next spike.
E=Recreate Deployments: new Pods have the same requests and hit the same block, so they return to Pending.
T: Pending Pods with room under the maximum: read noScaleUp events, then check quota and Pod address space.
V: GKE, Cloud Logging

@ GCP-PCA D4 T4.1 applied use-case
S: A platform team stores Terraform for production networks and databases in Git. After an incident caused by a misconfigured public database, the CISO wants infrastructure changes tested and validated before they reach production. Which TWO controls best provide this? (Select TWO)
A: Evaluate the plan of each pull request against policy-as-code rules, such as no public database addresses, before a merge is allowed
B: Review the changed Terraform files by eye during a monthly meeting and apply them in bulk after the meeting
C: Preview each deployment to see what resources will change, and require approval of that preview before the pipeline applies it
D: Apply changes straight to production and rely on Cloud Audit Logs afterwards to show whether anything unsafe was created by the change
E: Run every change in a developer project with relaxed organization policies so errors surface where they cost little
K: A,C
G: ## Shift validation left
Infrastructure as Code makes infrastructure testable like software. Useful layers:
- Static and policy checks: evaluate the plan output (the actual proposed changes) against rules that encode the security baseline. A rule such as "databases must not have public IP addresses" fails the pull request before anything is created.
- Preview: Terraform's plan, or an Infrastructure Manager preview deployment, shows how a change would affect resources without applying it, so a human approver reviews the real diff.
- Enforcement backstop: organization policies reject non-compliant resources even if a check was missed.
## What does not validate
Reviews held after the fact, audit logs read later, or testing in a differently governed project all detect problems too late or in a setting that differs from production.
W: A=Policy checks on the plan: an automated gate evaluates exactly what would be created and blocks the public-database pattern before merge, so the validation is repeatable.
C=Preview with approval: a preview shows the real resource diff, and requiring approval puts a human decision before the apply step.
X: B=Monthly bulk review: delays changes, reviews files rather than effects, and gives no consistent, automated gate.
D=Audit logs after apply: logs record what happened; the insecure database already exists, which is the incident to prevent.
E=Relaxed dev project: tests under rules unlike production's, so a change that passes there can still violate production policy.
T: Validate infrastructure changes by policy-checking the plan and approving a preview before apply.
V: Infrastructure Manager, Terraform, Cloud Build

@ GCP-PCA D4 T4.1 applied use-case
S: KnightMotives wants regional sales managers, who are not engineers and must hold no infrastructure permissions, to request a standard dealer-portal environment on demand. Today every request is a ticket that waits days for the platform team. Which design gives self-service without handing out broad rights?
A: Grant each sales manager the Editor role on a shared sandbox project and share a written checklist for building the environment in the console
B: A request form that starts a pipeline applying an approved, versioned Terraform blueprint through a dedicated service account that holds only the roles it needs
C: Email the platform team a copy of the template with edited values for each request, so that an engineer applies it by hand from a laptop
D: Give every sales manager the Owner role on the dealer-portal project so that each can run the deployment tool directly and change settings as needed
K: B
G: ## A catalog of approved building blocks
A service catalog in the architectural sense is a curated set of pre-approved, versioned building blocks that people consume instead of building from scratch. Google Cloud's Deployment Manager has ended, so the common implementation is Infrastructure as Code: Terraform modules and blueprints for Google Cloud encode network, logging and security baselines, and Infrastructure Manager or a CI pipeline deploys them as tracked deployments.
- The requester supplies only inputs (dealer name, region, size); the baseline is not negotiable.
- The pipeline runs under its own service account with just the roles the blueprint needs, so the requester needs no infrastructure permissions at all.
- A central team updates the blueprint once, and the next request uses the new version.
## Self-service is not self-privilege
Delegating the action is different from delegating the rights. Organization policies still reject non-compliant resources, so the catalog is the paved road and the policies are the guardrails.
W: Request form plus pipeline with a scoped service account: non-engineers get on-demand environments from one reviewed definition, while the permissions stay with the pipeline identity, which is auditable and least-privilege.
X: A=Editor on a sandbox: broad rights for non-engineers, and a console checklist produces environments that differ from the standard baseline.
C=Emailed template: still a manual, engineer-dependent step, so the days-long wait and the laptop-based, unrecorded deployments remain.
D=Owner for everyone: a large over-grant of rights that lets every manager change security settings and bypass the baseline.
T: Offer self-service through versioned Terraform blueprints deployed by a pipeline identity, so requesters need no direct permissions.

@ GCP-PCA D4 T4.1 applied tradeoff
S: A growing company opens a new Google Cloud project for every new product team by raising a ticket. The central cloud team needs several days per ticket, and projects come out with inconsistent labels, budgets and API settings. The company wants speed without losing control. Which approach is best?
A: Allow all engineers to create projects anywhere in the organization and ask them to follow a naming guideline and add labels when they remember
B: Move every team into one shared project so that no new projects need to be created at all
C: Automate creation with a Terraform project factory that sets folder, billing link, labels, budget and enabled APIs
D: Keep the manual ticket process but hire more people for the cloud team to shorten the time per request
K: C
G: ## Provisioning as a product
Project creation is a repeatable, rule-based task, so it suits automation. A project factory is Infrastructure as Code that takes a few inputs (team, environment, cost center) and creates a project with a standard result: placement in the folder that carries the right organization policies and IAM, billing account link, labels for cost allocation, a budget with alerts, an approved list of enabled APIs, and baseline IAM groups.

Unrestricted creation is fast but ungoverned. A single shared project removes isolation of IAM, quotas and billing attribution. More staff still leaves a manual process that produces inconsistent output.
W: Project factory: it turns a slow manual task into a reviewed, repeatable one with standard labels, budget, billing and API settings, giving both speed and governance.
X: A=Unrestricted creation: fast, but naming guidelines are not enforced, so labels, budgets and placement remain inconsistent and cost attribution stays poor.
B=One shared project: mixes teams in a single IAM, quota and billing boundary, which defeats isolation and cost attribution.
D=More people: scales cost linearly, still depends on human steps and does not fix inconsistent results.
T: Automate repeatable provisioning, such as new projects, with code that embeds the guardrails.

@ GCP-PCA D4 T4.1 applied troubleshooting
S: Batch workers in a private subnet, with no external IP addresses, reach a partner's API through a Cloud NAT gateway. Each night, when many workers start at once, some calls fail with connection errors, while the same calls succeed during the day. Which action most directly finds the cause?
A: Read the Cloud NAT gateway logs and metrics for dropped connections, then compare the ports per VM with the simultaneous connections
B: Replace the private subnet with one that gives every worker an external IP address, so that no translation limit can apply to them
C: Increase the machine type of the batch workers so that each VM can open more outbound connections to the partner at the same time
D: Open the partner's address range in an egress firewall rule, because nightly failures are normally caused by a missing allow rule
K: A
G: ## Cloud NAT has finite capacity
Cloud NAT translates the outbound traffic of VMs that have no external addresses. Each NAT IP address offers a limited number of ports, and each VM gets a share of them. When many VMs open many connections to the same destination at once, the gateway can run out of ports, and new connections are dropped, which fits an error pattern tied to load and time of day.
- Cloud NAT logging and monitoring metrics show dropped packets and allocation failures per gateway, so the evidence is already available.
- Typical fixes are more NAT IP addresses, more ports per VM, or fewer short-lived connections through reuse.
## Reading the symptom
Failures only under burst load, with success at quiet times, point to a capacity limit, not to a missing rule, which would fail every call.
W: NAT logs and metrics: they show dropped connections and allocation failures, and comparing the ports per VM with the simultaneous connections confirms or rules out port exhaustion before anything is changed.
X: B=External IPs on workers: this removes the private design and the security benefit, and it is a change made before any evidence shows what is failing.
C=Larger machine type: VM size does not change how many ports the NAT gateway grants, so the translation limit remains.
D=Egress rule for the partner: a missing allow rule would block the calls every time, including during the day, not only under burst load.
T: Intermittent outbound failures at peak from private VMs point to Cloud NAT port exhaustion; read the gateway logs and metrics.
V: Cloud NAT, VPC

@ GCP-PCA D4 T4.1 advanced use-case
S: A company has written disaster recovery runbooks for its order system, backed by replication to a second region. It has never failed over. Which practice best confirms that the plan will really meet the recovery objectives?
A: Keep a dashboard of replication job status in the monitoring tool and treat a continuous healthy status as proof that recovery will succeed
B: Review the written plan and runbooks with senior management in a yearly meeting and have them sign it off as the approved plan
C: Schedule failover exercises that bring up the order system in the second region, with the people who would operate it, and measure the achieved recovery time and data loss
D: Restore backups into an isolated environment each quarter and count the test as passed whenever the restore job reports that it has finished
K: C
G: ## An untested plan is a hypothesis
Disaster recovery guidance stresses a well-tested plan. Recovery objectives (RTO and RPO) are only claims until measured. Tests expose missing permissions, stale runbooks, configuration that exists only in the primary region, and dependencies nobody listed.
- Failover exercises (game days): run the actual procedure in the recovery region with the real operators, including identity access, DNS or load balancer changes and the application checks. Measure how long it took and how much data was lost.
- Restore tests: a backup that has never been restored is not known to be usable. Restoring into an isolated environment verifies integrity and the time needed.
- Include access: users must be able to sign in to the DR environment before a disaster, and DR should be included in routine security tests.
## Why status lights are not enough
Healthy replication shows data is moving, not that the application starts and serves requests from it.
W: Failover exercises: they run the real procedure with the real operators in the recovery region and produce measured RTO and RPO to compare with the targets.
X: D=Restore job status only: a finished restore job does not show that the application starts and serves correct data from it, or how long the whole recovery takes; restore tests are valuable only with application checks against the targets.
A=Dashboard health: replication status says nothing about whether the application and configuration in the second region work.
B=Annual sign-off: reviewing a document finds no runtime problems such as missing permissions or stale steps.
T: Prove DR with measured failover exercises and regular restore tests, not with documents or status lights.
V: Backup and DR Service, Cloud Monitoring

@ GCP-PCA D4 T4.1 applied tradeoff
S: Altostrat Media still runs its content ingestion system in one on-premises data center. A disaster there could be tolerated for up to four hours, and the budget is limited. The business wants a recovery site in Google Cloud. Which design fits best?
A: Pilot light: replicate ingestion data to Google Cloud continuously, keep the infrastructure as code, and start compute only after a disaster is declared
B: Hot standby: run a full-size copy of the ingestion system in Google Cloud at all times, send half of live traffic to it, and keep it patched in step
C: Cold backup: copy files to Cloud Storage monthly and build the whole environment manually from documents after a disaster
D: Active-active across two on-premises sites, which removes the dependency on Google Cloud entirely
K: A
G: ## Matching the DR pattern to the objective
DR patterns are described as cold, warm or hot, according to how readily the system recovers. The choice follows the RTO and RPO and the budget: a hot pattern costs the most because capacity runs all the time; a cold pattern is cheapest but slow.
- A pilot light keeps the critical core, usually the continuously replicated data, running in the recovery site, with the rest defined as code ready to launch. In the cloud, idle compute costs nothing, so you pay mainly for storage and replication.
- Recovery in a few hours is realistic when automation creates the infrastructure and attaches the replicated data.
## Reading the stem
A four-hour tolerance with limited budget rules out paying for hot capacity and rules out a manual rebuild from monthly copies, which would be both slow and lose up to a month of data.
W: Pilot light: continuous replication keeps data loss low, infrastructure as code lets compute start in minutes after declaration, and idle capacity costs nothing, so a four-hour objective is met at low cost.
X: B=Hot standby: it gives near-zero downtime the business does not require and doubles the running cost.
C=Monthly cold copy: the data loss could reach a month and a manual rebuild from documents is unlikely to finish in four hours.
D=Two on-premises sites: it needs new sites and hardware, leaves the cloud goal unmet and requires more capital spending than a cloud recovery site.
T: Choose the cheapest DR pattern that still meets RTO and RPO; a pilot light fits a few hours of tolerance.
V: Cloud Storage, Compute Engine

@ GCP-PCA D4 T4.1 applied use-case
S: A software vendor runs stateful applications with persistent volumes on a regional GKE cluster. To prepare for the loss of an entire region, the team needs to restore Kubernetes resources and persistent data into a cluster elsewhere. Which approach fits?
A: Rely on the regional cluster's multiple zones, since zones in the same region protect against a regional outage
B: Use Backup for GKE with scheduled plans that capture configuration and volume snapshots, then restore into a cluster in another region
C: Take a snapshot of the control plane datastore and import it into a new cluster in another region, because GKE exposes it for this purpose
D: Back up only the container images in Artifact Registry, since images contain all of the application state

A regional GKE cluster spreads the control plane and nodes over several zones, which protects against a zone failure. It does not protect against the loss of the region, a bad deployment that corrupts data, or a deleted namespace.

You can schedule backups, choose whole clusters or specific namespaces or applications, and restore a backup into another cluster, which supports disaster recovery and cloning.
## Design notes
- Choose the backup frequency from the RPO.
- Keep cluster definitions in code so a target cluster can be created quickly.
- Test restores regularly; restoring is where the problems appear.
W: Backup for GKE: scheduled plans capture resources and volume snapshots, and a restore can target a cluster in another region, so the stateful workloads return with their data.
X: A=Multiple zones: zones protect against a zone failure only; a regional outage takes the cluster with them.
C=Control plane datastore: GKE manages the control plane, and customers do not get its datastore for export and import.
D=Images only: images hold code, not Kubernetes configuration or the data in persistent volumes.
T: Region-level protection for stateful GKE workloads needs backup and restore across regions, such as Backup for GKE.
V: GKE, Backup for GKE

@ GCP-PCA D4 T4.1 advanced troubleshooting
S: A hospital group's patient portal on Cloud Run often returns errors during traffic spikes. Logs show the Cloud SQL for MySQL database rejecting new connections with "too many connections", although CPU and memory on the database stay low. What is the most likely root cause and fix?
A: Each scaled-out instance opens its own connections: cap them per instance, use pooling, and limit maximum instances to what the database can serve
B: The database has too little storage, so increasing disk size will release the connection slots currently in use
C: Read traffic is too high, so adding a cross-region replica will let write requests succeed
D: Cloud Run is the wrong platform for databases, so the portal must move back to virtual machines, which have no connection limit at all
K: A
G: ## Connections are a finite resource
A database accepts a limited number of simultaneous connections. A serverless service scales out by adding instances, and each instance may open several connections. A spike that multiplies instances multiplies connections, so the limit is reached while CPU and memory still look idle. This is the clue in the stem: errors about connections, not about resources.
- Cap the pool size per instance and the instances the service may create, so total demand stays below the database limit.
- Use pooling so that many requests share few connections. Cloud SQL offers Managed Connection Pooling on the Enterprise Plus edition; a pooling layer in the application or a proxy does the same job.
- Reduce hold time by closing connections promptly.
## Root cause versus symptom
Bigger machines or replicas help only if the diagnosed constraint is the one they change.
W: Connection fan-out: scale-out multiplies connections, so limiting per-instance connections, pooling, and bounding maximum instances aligns demand with what the database can serve.
X: B=More disk: storage size does not govern the number of connections, and the errors name connections, not disk space.
C=Cross-region replica: replicas serve reads and do not raise the primary's connection limit; writes still go to the primary.
D=Back to VMs: VMs would also open connections and scale by instance count; the platform is not the cause and a move adds work without a fix.
T: "Too many connections" with idle CPU during spikes points to connection fan-out from autoscaling: pool and cap.
V: Cloud Run, Cloud SQL

@ GCP-PCA D4 T4.1 applied use-case
S: Cymbal Retail has piloted generative AI that creates product attributes and descriptions from supplier data, and wants to expand to all verticals. Before expansion the architect must define how the output is tested and validated. Which approach is best?
A: Have the merchandising lead read about ten generated items and approve the expansion if they look good
B: Build a labeled evaluation set per vertical from known-good entries, set acceptance thresholds, and keep human review before catalog updates
C: Publish generated content directly to the live catalog and watch conversion and return rates after launch to find the content that is wrong
D: Ask the model to rate its own outputs and approve any item with a high self-score
K: B
G: ## Testing a non-deterministic component
Generative AI output varies, so a handful of spot checks does not show quality. Validate like any critical component, with a representative, repeatable test.

- Metrics tied to the requirement: the technical requirement is attributes aligned to the catalog structure, so measure schema validity, correct values and hallucinated attributes.

- Human-in-the-loop: reviewers see output before it updates the catalog, and their corrections feed back into the evaluation set.
## Why other approaches fall short
Sampling by one person is unrepresentative, post-launch monitoring lets customers find errors, and self-scoring by the same model is not independent evidence.
W: Evaluation set with thresholds and review: it measures quality per vertical against known answers, can be repeated after every change, and a human check protects the live catalog.
X: A=Ten items: too small and too subjective to represent verticals, and it cannot detect regressions later.
C=Test in production: customers receive wrong product information first, which harms trust, returns and compliance.
D=Self-rating: the model can be confidently wrong, and a score from the same system is not an independent measure of accuracy.
T: Validate generative output with a labeled, repeatable evaluation set and agreed thresholds, and keep human review before publishing.

@ GCP-PCA D4 T4.2 applied use-case
S: In a design review for a new customer data platform, the security lead insists on private-only access and a lengthy approval flow, while the product owner demands a launch in six weeks for a customer commitment. The two cannot agree. What should the architect do?
A: Side with the product owner, because revenue commitments outweigh internal controls, and fix security gaps after launch
B: Tell the product owner the launch must slip until every security preference is met, because the architect has no right to weigh them against dates
C: Ask the two to settle it between themselves and attend later only if they ask for a ruling
D: Clarify each side's underlying requirement, present options with risk, cost and timing, and bring the choice to the accountable executive

G: ## Positions versus requirements

@ GCP-PCA D4 T4.2 advanced tradeoff
