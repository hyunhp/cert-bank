@ GCP-PCA D6 T6.1 applied tradeoff
S: EHR Healthcare's past outages were prolonged because alert emails were ignored and nobody was sure who should lead the response. The operations lead is writing the incident process for the new Google Cloud platform that serves hospitals and insurers. Which approach best follows the operational excellence pillar?
A: Define incident roles such as commander, investigators and communicators, document escalation paths in a runbook, and track every incident in one central incident management system
B: Let the engineer who first notices an issue handle it alone from start to finish, and keep the notes in a personal document so they can be summarized later
C: Rely on a large group chat where everyone is invited and the most senior person on the thread decides on actions as the incident goes on
D: Remove paging and rely on a weekly review of all alerts, so that engineers are not distracted from planned feature work by minor problems
K: A
G: ## Incident management in the operational excellence pillar
The pillar's principle "manage incidents and problems" asks for a process that is prepared before the incident, not improvised during it. The recommended building blocks are:
- **Clear roles and expectations**: an incident commander who coordinates, investigators, a communicator for stakeholders, and technical experts.
- **Communication and escalation paths**: who is contacted, through which channel, and when the incident moves to higher management.
- **A runbook or playbook** that lists the steps for triage, investigation, communication and resolution, with the tools and contacts, reviewed regularly.
- **A centralized incident management system** so status, impact, tasks and owners are in one place instead of scattered over channels.
- **Post-incident reviews** and a knowledge base afterwards, so the same problem is not solved twice.
EHR Healthcare's two weaknesses (ignored alerts, unclear ownership) are exactly the gaps that roles, escalation and a central tracker close.
W: Roles, a runbook with escalation paths and a central incident system: they give every responder a defined job, make sure an alert reaches someone accountable, and keep status visible to stakeholders, which is the pillar's recommended foundation.
X: B=Single owner, personal notes: one person carries triage, fixes and communication at once, nothing is shared while the incident runs, and no one else can take over.
C=Open group chat: with no defined roles or tracked tasks, decisions and context are lost in the thread and responders duplicate or contradict each other.
D=Weekly alert review: this removes the fast response entirely. Real customer-facing failures would wait days, which breaks the 99.9% availability need.
T: Prepare incident response with defined roles, a runbook with escalation paths and one central incident system.
V: Cloud Monitoring, Cloud Logging

@ GCP-PCA D6 T6.1 applied use-case
S: A retailer's platform team releases changes in large quarterly batches that need a weekend freeze, manual approvals by email and hand-run scripts. Each batch tends to break something, and recovery means patching production by hand. Which TWO changes best align with the pillar's guidance on automating and managing change? (Select TWO)
A: Keep infrastructure and configuration definitions in version control and apply them through a CI/CD pipeline that runs automated tests, with a defined rollback path
B: Move to small, frequent changes that are released through the pipeline and use controlled deployment so that a bad change can be reversed quickly
C: Extend the weekend freeze to two weekends and add a second manual approval email, so each large batch gets more review before it goes live
D: Let on-call engineers edit production resources directly in the console when an incident occurs, and sync the definitions later when there is time
E: Replace testing before release with heavier monitoring after release, because production gives the only realistic validation of a change
K: A,B
G: ## Change is the main source of incidents
The operational excellence pillar's "automate and manage change" principle rests on four elements: change governance, risk assessment, testing and validation, and controlled deployment with the ability to roll back. In practice:
- **Infrastructure as code and version control** make each change reviewable, repeatable and attributable, and let you return to an earlier version.
- **CI/CD** (for example Cloud Build for build and test, Cloud Deploy for delivery) runs automated unit, integration and end-to-end tests before anything reaches production.
- **Small batches** shrink the blast radius: when a change fails, there is little to inspect and little to reverse.
Large quarterly batches do the opposite: many changes interact, nobody knows which one broke production, and manual steps vary from run to run.
W: A=Version control, pipeline and rollback: it makes every change consistent, tested and reversible, replacing hand-run scripts with a repeatable path.
B=Small frequent controlled releases: small changes are easier to test and diagnose, and controlled deployment shortens recovery when one fails.
X: C=Longer freezes and more emails: this adds manual process to the same big batch. It delays value, and the change stays large and risky.
D=Console edits during incidents: they create drift between production and the definitions, so the next pipeline run can overwrite or hide the fix, and no review happens.
E=Monitoring instead of testing: monitoring is needed but detects failures after customers are affected. The pillar asks for testing and validation before release as well.
T: Reduce change risk with version-controlled definitions, automated tests, rollback and small frequent releases.
V: Cloud Build, Cloud Deploy

@ GCP-PCA D6 T6.2 applied comparison
S: Cymbal Retail runs its Kubernetes workloads with an open source monitoring stack of Prometheus servers and Grafana dashboards, and the team's PromQL alerts and dashboards represent years of work. Operating and scaling the Prometheus servers across clusters takes too much effort, and the team wants one global view of metrics. Which approach should the architect recommend?
A: Adopt Google Cloud Managed Service for Prometheus with managed collection, and keep the existing PromQL queries, Grafana dashboards and alert rules working against its global store
B: Rewrite every dashboard and alert as a native Cloud Monitoring chart or condition first, and only then retire the Prometheus servers
C: Keep self-managed Prometheus servers but run them on larger machines, and copy their data into BigQuery nightly for cross-cluster questions
D: Replace metrics with log-based counters only, because logs already carry the required information and no collectors would have to be run
K: A
G: ## Prometheus on Google Cloud without running Prometheus servers
Google Cloud Managed Service for Prometheus is a managed, Prometheus-compatible service built on Monarch, the same global datastore behind Cloud Monitoring. Collectors (managed collection through an operator in Kubernetes is the recommended mode, or self-deployed collection, the OpenTelemetry Collector or the Ops Agent) scrape exporters and send data to Monarch. You query with PromQL, Grafana connects to the global store instead of individual servers, and PromQL alerts can be evaluated in Cloud Monitoring.
- No Prometheus servers to scale, shard or patch.
- A global view across clusters, projects and even other clouds.
- Existing Grafana dashboards, PromQL alerts and workflows keep working, which protects the team's investment.
W: Managed Service for Prometheus with managed collection: it removes the servers to operate and scale, gives one global query view in Monarch, and the PromQL queries and Grafana dashboards remain usable, so migration effort is small.
X: B=Rewrite first: this throws away working PromQL assets and delays the benefit, although the managed service is compatible with them.
C=Bigger self-managed servers plus BigQuery copy: the operational burden grows with scale, and nightly copies give stale answers instead of a live global view.
D=Log-based counters only: logs do not replace time-series metrics such as saturation and latency distributions, and the team would lose its alert logic.
T: Managed Service for Prometheus keeps PromQL and Grafana while Google runs storage and global querying.
V: Managed Service for Prometheus, Cloud Monitoring

@ GCP-PCA D6 T6.2 applied use-case
S: A checkout service writes a log line with the text PAYMENT_GATEWAY_TIMEOUT each time a call to the card processor times out. The team cannot change the application code before the next release, yet wants a chart of timeouts per minute and a page when the rate rises. What should the architect recommend?
A: Create a counter log-based metric that matches those log entries, chart it in Cloud Monitoring and attach an alerting policy to it
B: Export all logs to Cloud Storage every hour and have an engineer count the matching lines with a script, then email the result
C: Add custom instrumentation with a metrics client library to the service and deploy it, then build the chart after the release
D: Enable Data Access audit logs on the project, because audit entries record the timeouts that the application experienced
K: A
G: ## Turning logs into metrics
A log-based metric is a Cloud Monitoring metric derived from the content of log entries. A **counter** metric counts entries that match a filter in a period, a **distribution** metric extracts a value such as latency from the entries. The result can be charted and used in alerting policies like any other metric, and it can be scoped to a project or to a log bucket.
- Use it when the application already logs the signal but does not emit a metric.
- No code change or redeploy is required.
- Counters fit "how often did X happen", distributions fit "how long did X take".
W: Counter log-based metric with chart and alert: it converts the existing log line into a time series per minute without touching the application, and an alerting policy can page when the rate rises.
X: B=Hourly export and script: the signal arrives an hour late and relies on a manual step, so it cannot page when the rate rises.
C=New instrumentation: this works but needs a code change and release, which the stem rules out for now. Log-based metrics deliver the same signal immediately.
D=Data Access audit logs: audit logs record API calls on Google Cloud resources, not an application's own timeouts to an external processor.
T: A counter log-based metric turns an existing log line into a chart and an alert without code changes.
V: Cloud Logging, Cloud Monitoring

@ GCP-PCA D6 T6.3 applied tradeoff
S: Cymbal Retail runs its storefront on GKE and wants to avoid surprises from automatic cluster upgrades during its two-week holiday sales peak, while still receiving upgrades and security patches the rest of the year. Which approach should the architect advise?
A: Enroll the clusters in a release channel for managed upgrades, and set a maintenance exclusion over the peak period plus a recurring maintenance window outside business hours
B: Disable auto-upgrade permanently on all clusters and have the team upgrade each cluster by hand once a year
C: Pin the clusters to a static version outside any release channel, so GKE never touches the clusters and no policy is needed
D: Subscribe production clusters to the Rapid channel, so upgrades arrive first and the team spends less time on patching during the holidays
K: A
G: ## Controlling when GKE upgrades happen
GKE keeps clusters current with automatic upgrades. You control the pace and the timing:
- **Release channels** (Rapid, Regular, Stable, Extended) set how quickly new versions reach your clusters. Regular is the default and balances features with stability; Stable favors stability; Rapid is recommended for testing newer versions on pre-production.
- **Maintenance windows** are recurring periods in which automatic maintenance may run.
- **Maintenance exclusions** are non-repeating periods in which automatic maintenance is forbidden, such as a sales peak.
Not everything respects these policies: GKE can override them for critical security vulnerabilities, and some control plane repairs still happen. A release channel with windows and exclusions gives managed upgrades with predictable timing.
W: Release channel plus a maintenance exclusion over the peak and a recurring window off hours: it keeps upgrades and patches flowing, yet blocks automatic maintenance during the holiday peak.
X: B=Auto-upgrade off and yearly manual upgrades: security patches and supported versions are missed for most of the year, and a once-a-year big jump is itself risky.
C=Static version outside a channel: clusters eventually reach end of support and lose patches, and the workload cannot take advantage of managed upgrade policy features.
D=Rapid channel for production: it receives new versions soonest, so it increases upgrade frequency and risk. Rapid is meant for pre-production testing.
T: Use a release channel for managed upgrades, with maintenance windows and exclusions to schedule around business peaks.
V: GKE

@ GCP-PCA D6 T6.3 applied use-case
S: Altostrat Media runs Kubernetes clusters both on premises and in Google Cloud, and central operations wants each cluster to carry the same namespaces, network policies and role bindings. Manual changes with kubectl have caused differences between clusters. Which approach best meets the need?
A: Store the desired configuration in a Git repository and use Config Sync to reconcile each cluster to it, so manual differences are detected and reverted
B: Give every cluster administrator a shared script that applies the configuration, and ask them to run it after each change in the repository
C: Back up each cluster's configuration nightly into Cloud Storage and compare the files by hand when an incident suggests a difference
D: Keep all clusters in one namespace-free design so no per-cluster policy is needed, and rely on application teams to follow conventions
K: A
G: ## GitOps for fleets of clusters
GitOps treats a Git repository as the single source of truth for desired state. Config Sync, a GitOps service included with GKE, continuously syncs configurations and policies from a central source such as Git to many clusters, so a fleet is managed centrally and **configuration drift** is prevented rather than discovered. Changes then follow the same review, approval and rollback path as code: a revert in Git is a rollback in every cluster.
- Works across clusters in Google Cloud and registered clusters elsewhere, which fits hybrid estates.
- Manual edits that diverge from Git are reverted by reconciliation.
- Auditability: who changed what is the Git history.
W: Git as the source of truth with Config Sync reconciliation: all clusters converge to the same declared state, drift from manual changes is corrected automatically, and every change is reviewed and reversible in Git.
X: B=Shared script: it depends on people remembering to run it everywhere, nothing reverts later manual edits, and scripts diverge across teams.
C=Nightly backups compared by hand: this finds differences after the fact, slowly and manually, and does not correct anything.
D=One namespace-free design: the stem's need is consistent namespaces, network policies and roles. Removing them weakens isolation and does not solve drift.
T: Config Sync reconciles clusters to a Git source of truth, preventing drift and making rollback a revert.
V: GKE, Config Sync

@ GCP-PCA D6 T6.3 applied troubleshooting
S: A web tier runs on a regional managed instance group of 12 VMs behind a load balancer. When the team rolls out a new instance template, the group briefly serves errors because too many VMs are replaced at once and some new VMs receive traffic before the application is ready. Which action best fixes the rollout?
A: Use a proactive rolling update with a lower maxUnavailable and a surge allowance, and attach an application-based health check so that new VMs get traffic only when healthy
B: Delete all VMs in the group at once and let autoscaling create new ones from the new template, which is the fastest rollout method
C: Update the template in place on each VM by connecting over SSH and changing the package version, one VM at a time during off hours
D: Raise the load balancer's idle timeout so that in-flight requests are not interrupted when VMs are replaced by the update
K: A
G: ## Rolling updates in managed instance groups
A MIG applies a new instance template to existing VMs with a proactive (automatic) update. You tune the speed and the disruption:
- **maxSurge** is how many extra VMs the group may create above target size during the update.
- **maxUnavailable** is how many VMs may be offline at the same time. Defaults are 1 per affected zone.
- An **application-based health check** with autohealing marks a VM unhealthy if the application does not respond, and the group repairs it; the load balancer uses health checks to send traffic only to healthy backends.
- A **canary update** (two template versions) applies the new template to a subset first.
Tight unavailability limits keep capacity during the rollout, surge keeps full capacity while new VMs start, and the health check keeps unready VMs out of service.
W: Rolling update with lower maxUnavailable, surge and an application-based health check: capacity stays close to full during the update, and a new VM receives traffic only once the application responds.
X: B=Delete all VMs at once: this removes the entire tier's capacity together, which is the opposite of a controlled rollout and causes an outage.
C=SSH edits per VM: manual and unrepeatable, creating VMs that no longer match the template and breaking immutable-infrastructure consistency.
D=Longer idle timeout: this affects connection handling in the load balancer, but not how many VMs are replaced at once or whether new VMs are ready.
T: Control MIG rollouts with maxSurge, maxUnavailable and health checks so capacity and readiness are protected.
V: Compute Engine, Cloud Load Balancing

@ GCP-PCA D6 T6.3 applied tradeoff
S: A product team merges code to the main branch daily, but a large new pricing feature will take six weeks to complete and must be switched on for customers only on a marketing date. The team wants to avoid a long-lived feature branch that is hard to merge. Which practice fits best?
A: Merge the unfinished feature behind a feature flag in small increments, deploy continuously with the flag off, and turn it on for users on the launch date
B: Keep the work on a separate branch for six weeks, and merge and deploy everything on the launch date together
C: Deploy a separate copy of the whole application with the new feature, and switch every customer to it on the launch date by changing DNS
D: Hold all other teams' releases until the pricing feature is complete, so that the release train contains only complete features
K: A
G: ## Separate deployment from release
Deploying code (putting a new version into production) and releasing a feature (making it visible to users) are different decisions. A **feature flag** lets unfinished or scheduled functionality ship in small increments, dark, while a configuration switch decides who sees it and when. This supports trunk-based development, which DORA research associates with higher delivery performance: short-lived branches, frequent integration and small batches.
- A flag can be turned off instantly if the feature misbehaves, without a rollback deploy.
- Exposure can be gradual (internal users, a percentage, a region).
- Remove flags after launch to avoid accumulating complexity.
W: Small merges behind a feature flag: integration stays continuous, deployments stay routine, and the business launches on its date by flipping the flag, with an instant off switch if needed.
X: B=Six-week branch: the merge grows more conflicting each day, and everything lands in one large, risky deployment on launch day.
C=Duplicate whole application with DNS switch: this doubles infrastructure and data-sync problems for one feature, and all customers move at once with slow reversal through DNS caching.
D=Block other releases: it penalizes unrelated teams, batches changes into a larger release and reintroduces the big-bang risk.
T: Use feature flags with trunk-based development to deploy continuously and release on the business schedule.
V: Cloud Build

@ GCP-PCA D6 T6.3 advanced use-case
S: Altostrat Media wants the exact container image that passed testing in staging to be the one running in production, and wants production clusters to refuse images that did not go through the pipeline. Which design achieves this?
A: Build the image once, store it in Artifact Registry, promote the same image by digest through environments, and enforce Binary Authorization on production so only images with the pipeline's attestation are admitted
B: Rebuild the image from source in each environment so that every environment gets a fresh build with the latest base image packages
C: Let developers push images by tag from their laptops to the production registry, and rely on a code review of the Dockerfile before they push
D: Copy the container files into each production node by script after tests pass, and restart the pods so that they use the copied files
K: A
G: ## Build once, promote, and verify at admission
Release management relies on one rule: what you tested is what you run. Building separately per environment produces different artifacts, because base images, dependencies and timing differ, so a passing test in staging says little about production.
- **Build once**: store the image in Artifact Registry and reference it by immutable **digest** (tags can move).
- **Promote** that same digest through dev, staging and production, using a delivery pipeline.
- **Binary Authorization** is a deploy-time control for GKE and Cloud Run: policy requires attestations from trusted attestors (signed by the pipeline after tests) before an image is admitted, so images that skipped the pipeline are refused.
W: Build once, promote the digest and enforce attestations with Binary Authorization: the artifact in production is identical to the one tested, and unattested images cannot be deployed.
X: B=Rebuild per environment: each build can differ, so the tested artifact and the production artifact are no longer the same.
C=Laptop pushes with Dockerfile review: a reviewed Dockerfile says nothing about the image that was pushed, and no technical control refuses untested images.
D=Script copying files to nodes: this bypasses the registry and the orchestrator, leaves nodes and pods inconsistent and leaves no verifiable artifact.
T: Build once, promote by digest, and enforce pipeline attestations at deploy time.
V: Artifact Registry, Binary Authorization, GKE

@ GCP-PCA D6 T6.3 applied tradeoff
S: A company patches its stateless web VMs by connecting to each VM and running package updates. Over time VMs differ in versions and some patches fail halfway, so rollbacks are uncertain. The team wants a safer approach on managed instance groups. What should the architect advise?
A: Build a new, tested VM image with the patches, create a new instance template from it and roll it out through the MIG, keeping the previous template for rollback
B: Keep patching in place but extend the maintenance window and add more engineers so that all VMs are patched in a single night
C: Take a snapshot of one patched VM and restore the snapshot over all other VMs in the group through a script, replacing their boot disks
D: Stop patching the stateless VMs entirely, because replacing instances during autoscaling will eventually bring them up to date
K: A
G: ## Immutable infrastructure for stateless tiers
With **mutable** servers, each VM accumulates changes and ends up unique, so a failed patch leaves it in an unknown state. With **immutable** infrastructure you never patch a running instance: you build a new image once, test it, and replace instances with ones created from it.
- A new instance template references the new image; a MIG rolling update replaces VMs with controlled surge and unavailability.
- Rollback is a roll forward to the previous template, which still exists.
- Every VM in the group is identical, so behaviour is predictable.
This removes the half-patched servers the team has now.
W: New tested image, new template and a MIG rollout with the old template kept: all VMs end up identical, the patch is validated before it touches production, and rollback is straightforward.
X: B=Longer window, more engineers: manual in-place patching remains error-prone, and more people produce more variation.
C=Disk replacement from a snapshot by script: it is an uncontrolled mass change that skips the MIG's rolling controls, health checks and template record.
D=No patching until autoscaling replaces VMs: new VMs still use the old template and image, and scaling in and out does not bring them current.
T: For stateless VMs, patch by replacing instances from a new tested image through a rolling MIG update.
V: Compute Engine

@ GCP-PCA D6 T6.4 applied troubleshooting
S: EHR Healthcare's availability dropped after a firewall rule was changed in a production project. The security team wants to know who changed it and when, and the platform team asks whether this information may have been missing if no one enabled logging beforehand. What is the correct answer?
A: Admin Activity audit logs record configuration changes such as firewall updates, are always written and cannot be disabled, so the change can be found in Cloud Logging
B: The change can be found only if Data Access audit logs were enabled for Compute Engine before the change was made
C: Configuration changes are recorded only if the team had created a log sink to Cloud Storage before the change was made
D: Google Cloud does not record who changes resources, so the team should rely on screenshots of the console taken by administrators

G: ## Audit logs answer "who did what, where, and when?"
Cloud Audit Logs writes several log types for each project, folder and organization:
- **Admin Activity** audit logs record user-driven API calls that modify the configuration or metadata of resources (creating VMs, changing IAM, changing firewall rules). They are **always written; you can't configure, exclude or disable them**.

W: Admin Activity audit logs: firewall rule changes are configuration modifications, which are always recorded and not optional, so the who and when are available in Cloud Logging.
X: B=Data Access needed: those logs cover reads and user data access; configuration changes are Admin Activity, which needs no enabling.
C=Sink required first: a sink only routes copies for retention or analysis; the entries exist in the project's logs without one.
D=No record exists: Google Cloud records administrative actions, so screenshots are neither needed nor reliable evidence.
T: Admin Activity audit logs always record configuration changes; Data Access logs are off by default except in BigQuery.
V: Cloud Audit Logs, Cloud Logging

@ GCP-PCA D6 T6.4 applied use-case
S: A support team investigating slow orders must count, for the last week, how many requests exceeded two seconds per customer tier and per hour, across several million log entries, and then join the result with trace data. The Logs Explorer cannot aggregate this way. What should the architect recommend?
A: Enable analytics on the log bucket and use Observability Analytics to run SQL queries that group and aggregate the entries and chart the results
B: Download the matching entries from Logs Explorer as files and aggregate them in a spreadsheet each time a question comes up
C: Create one log-based counter metric for each customer tier and hour combination, so the answer is available on a chart
D: Reduce the log retention to one day so that the number of entries to review is small enough for Logs Explorer to handle
K: A
G: ## Searching versus analyzing logs
Logs Explorer is built to find and read entries with the Logging query language; it does not support aggregate operations such as counting entries that match a pattern. For aggregation, enable analytics on the log bucket and use Observability Analytics: it runs SQL over the log data, groups and aggregates (for example average latency per hour for a URL), shows results as tables or charts, and can join log and trace data to produce trends and insights.
- Use Logs Explorer to inspect the entries of a specific incident.
