@ GCP-PCA D6 T6.1 applied tradeoff
S: EHR Healthcare's past outages were prolonged because alert emails were ignored and nobody was sure who should lead the response. The operations lead is writing the incident process for the new Google Cloud platform that serves hospitals and insurers. Which approach best follows the operational excellence pillar?
A: Define incident roles, document escalation paths in a runbook, and track every incident in one central incident management system
B: Let the engineer who first notices an issue handle it alone from start to finish, keeping the notes in a personal document for a later summary
C: Rely on one large group chat that everyone is invited to, where the most senior person on the thread decides on actions as the incident goes on
D: Remove paging altogether and hold a weekly review of all alerts, so that engineers are not distracted from planned feature work by minor problems
K: A
G: ## Incident management in the operational excellence pillar
The pillar's principle "manage incidents and problems" asks for a process that is prepared before the incident, not improvised during it. The recommended building blocks are:
- **Clear roles and expectations**: an incident commander who coordinates, investigators, a communicator for stakeholders, and technical experts.
- **Communication and escalation paths**: who is contacted, through which channel, and when the incident moves to higher management.
- **A runbook or playbook** that lists the steps for triage, investigation, communication and resolution, with the tools and contacts, reviewed regularly.
- **A centralized incident management system** so status, impact, tasks and owners are in one place instead of scattered over channels.
- **Post-incident reviews** and a knowledge base afterwards, so the same problem is not solved twice.
EHR Healthcare's two weaknesses (ignored alerts, unclear ownership) are exactly the gaps that roles, escalation and a central tracker close.
W: Roles, a runbook with escalation paths and a central incident system: they give every responder a defined job, make sure an alert reaches someone accountable, and keep status visible to stakeholders, which is the pillar's recommended foundation.
X: B=Single owner, personal notes: one person carries triage, fixes and communication at once, nothing is shared while the incident runs, and no one else can take over.
C=Open group chat: with no defined roles or tracked tasks, decisions and context are lost in the thread and responders duplicate or contradict each other.
D=Weekly alert review: this removes the fast response entirely. Real customer-facing failures would wait days, which breaks the 99.9% availability need.
T: Prepare incident response with defined roles, a runbook with escalation paths and one central incident system.
V: Cloud Monitoring, Cloud Logging

@ GCP-PCA D6 T6.1 applied use-case
S: Cymbal Retail's on-call engineers are paged several times a week for the same condition: a queue-consumer deployment stops pulling messages, and the fix is always the same documented, safe restart. The team wants to remove this toil and shorten recovery without losing sight of the underlying problem. Which design best follows the operational excellence pillar?
A: Route the alert to a Pub/Sub notification channel that triggers an automation running the documented restart, and still log each event for later root cause review
B: Silence the alert and let engineers restart the consumers by hand whenever customers complain, because a restart needs no judgement and pages add noise
C: Extend the wiki page with the restart steps and keep paging a human for every occurrence, so that every recovery stays under direct human control
D: Restart all consumer deployments every hour on a fixed schedule whatever their state, so that the stalled condition can no longer appear in practice
K: A
G: ## Automate repeatable response, keep the learning
The operational excellence pillar asks teams to automate and orchestrate operations so that people spend time on problems that need judgement. A response that is always the same, safe and documented is a candidate for automation, which is the same logic as automating change.
- In Cloud Monitoring, an alerting policy can notify a **Pub/Sub** topic or a webhook. The documentation recommends these two channel types when automation tools act on notifications, because other formats may change.
- A subscriber (for example a Cloud Run function) performs the documented step. Give it least-privilege permissions and make it idempotent.
- Keep the incident record: automation shortens recovery but the recurring cause still goes into the problem backlog (post-incident review, fix the consumer).
Silencing or blind scheduled restarts remove the signal instead of removing the toil.
W: Pub/Sub-triggered automation with logging and follow-up: the known restart happens in seconds without a page, and the recurring defect stays visible for a permanent fix.
X: B=Silence and wait for complaints: customers become the detection system and recovery waits for them, which is slower and loses the alert.
C=Longer wiki and still paging: the humans keep executing a mechanical step, so the toil and the night pages stay, only better documented.
D=Hourly restarts of everything: healthy consumers are restarted too, in-flight work can be interrupted and the underlying defect is hidden, not resolved.
T: Automate repeatable, safe responses from alerts and keep recording events so the root cause is still fixed.
V: Cloud Monitoring, Pub/Sub, Cloud Run functions

@ GCP-PCA D6 T6.2 applied comparison
S: Cymbal Retail runs its Kubernetes workloads with an open source monitoring stack of Prometheus servers and Grafana dashboards, and the team's PromQL alerts and dashboards represent years of work. Operating and scaling the Prometheus servers across clusters takes too much effort, and the team wants one global view of metrics. Which approach should the architect recommend?
A: Adopt Managed Service for Prometheus with managed collection, keeping the existing PromQL queries, Grafana dashboards and alert rules
B: Rewrite every dashboard and alert as a native Cloud Monitoring chart or condition first, and only then retire the Prometheus servers from service
C: Keep self-managed Prometheus servers on larger machines, and copy their data into BigQuery nightly to answer questions across clusters
D: Replace metrics with log-based counters only, because logs already carry the required information and no collectors would have to be operated
K: A
G: ## Prometheus on Google Cloud without running Prometheus servers
Google Cloud Managed Service for Prometheus is a managed, Prometheus-compatible service built on Monarch, the same global datastore behind Cloud Monitoring. Collectors (managed collection through an operator in Kubernetes is the recommended mode, or self-deployed collection, the OpenTelemetry Collector or the Ops Agent) scrape exporters and send data to Monarch. You query with PromQL, Grafana connects to the global store instead of individual servers, and PromQL alerts can be evaluated in Cloud Monitoring.
- No Prometheus servers to scale, shard or patch.
- A global view across clusters, projects and even other clouds.
- Existing Grafana dashboards, PromQL alerts and workflows keep working, which protects the team's investment.
W: Managed Service for Prometheus with managed collection: it removes the servers to operate and scale, gives one global query view in Monarch, and the PromQL queries and Grafana dashboards remain usable, so migration effort is small.
X: B=Rewrite first: this throws away working PromQL assets and delays the benefit, although the managed service is compatible with them.
C=Bigger self-managed servers plus BigQuery copy: the operational burden grows with scale, and nightly copies give stale answers instead of a live global view.
D=Log-based counters only: logs do not replace time-series metrics such as saturation and latency distributions, and the team would lose its alert logic.
T: Managed Service for Prometheus keeps PromQL and Grafana while Google runs storage and global querying.
V: Managed Service for Prometheus, Cloud Monitoring

@ GCP-PCA D6 T6.2 applied use-case
S: A checkout service writes a log line with the text PAYMENT_GATEWAY_TIMEOUT each time a call to the card processor times out. The team cannot change the application code before the next release, yet wants a chart of timeouts per minute and a page when the rate rises. What should the architect recommend?
A: Create a counter log-based metric that matches those log entries, chart it in Cloud Monitoring and attach an alerting policy to it
B: Export all logs to Cloud Storage every hour, have an engineer count the matching lines with a script and email the result to the team
C: Add custom instrumentation with a metrics client library to the service, deploy it with the next release and build the chart afterwards
D: Enable Data Access audit logs on the project, because the audit entries record the timeouts that the application experienced with the processor
K: A
G: ## Turning logs into metrics
A log-based metric is a Cloud Monitoring metric derived from the content of log entries. A **counter** metric counts entries that match a filter in a period, a **distribution** metric extracts a value such as latency from the entries. The result can be charted and used in alerting policies like any other metric, and it can be scoped to a project or to a log bucket.
- Use it when the application already logs the signal but does not emit a metric.
- No code change or redeploy is required.
- Counters fit "how often did X happen", distributions fit "how long did X take".
W: Counter log-based metric with chart and alert: it converts the existing log line into a time series per minute without touching the application, and an alerting policy can page when the rate rises.
X: B=Hourly export and script: the signal arrives an hour late and relies on a manual step, so it cannot page when the rate rises.
C=New instrumentation: this works but needs a code change and release, which the stem rules out for now. Log-based metrics deliver the same signal immediately.
D=Data Access audit logs: audit logs record API calls on Google Cloud resources, not an application's own timeouts to an external processor.
T: A counter log-based metric turns an existing log line into a chart and an alert without code changes.
V: Cloud Logging, Cloud Monitoring

@ GCP-PCA D6 T6.3 applied troubleshooting
S: Cymbal Retail's checkout runs six replicas on GKE. During node upgrades, drains sometimes evict several checkout Pods at almost the same moment, capacity drops and shoppers see errors until the Pods are rescheduled. Which change best protects availability during upgrades?
A: Define a PodDisruptionBudget for checkout that keeps a minimum number of replicas available, so node drains evict its Pods gradually
B: Disable node auto-upgrades for the cluster, so that maintenance never evicts any Pods and the team upgrades when it has time
C: Raise the CPU limit of each checkout Pod, so that the replicas remaining after a drain can absorb the load of the evicted ones
D: Reduce the checkout deployment to two replicas, so that each node drain has fewer Pods to evict and the process finishes faster
K: A
G: ## Keeping capacity while nodes are drained
A node upgrade replaces nodes: GKE cordons a node, drains it (evicting its Pods so they restart elsewhere) and deletes it. Eviction during a drain is a **voluntary disruption**, and a **PodDisruptionBudget (PDB)** is the Kubernetes object that limits it.
- A PDB states the minimum number (or percentage) of replicas that must stay available, or the maximum that may be unavailable.
- GKE respects the PDB and the Pod's termination grace period during node drains for up to an hour, after which remaining Pods can be evicted so that the upgrade proceeds. Set realistic values: a budget that allows zero disruption can stall upgrades.
- Surge settings (`maxSurge`, `maxUnavailable`) control how many nodes are upgraded at once; the PDB protects the application on top of that.
- A PDB does not protect against involuntary failures such as a node crash.
W: PodDisruptionBudget: it tells the drain to keep enough checkout replicas serving, so upgrades proceed node by node without losing capacity.
X: B=Auto-upgrade off: the cluster stops receiving security patches and supported versions, and manual upgrades will drain nodes the same way.
C=Higher CPU limits: limits do not stop several Pods being evicted at once, and the surviving Pods are not guaranteed to absorb the load of lost ones.
D=Fewer replicas: this lowers capacity and redundancy permanently, and evicting one of two Pods is a bigger share of traffic than evicting one of six.
T: Use PodDisruptionBudgets so that node drains during upgrades keep enough replicas running.
V: GKE

@ GCP-PCA D6 T6.3 applied use-case
S: Altostrat Media runs Kubernetes clusters both on premises and in Google Cloud, and central operations wants each cluster to carry the same namespaces, network policies and role bindings. Manual changes with kubectl have caused differences between clusters. Which approach best meets the need?
A: Store the desired configuration in a Git repository and use Config Sync to reconcile each cluster to it, reverting manual differences
B: Give every cluster administrator a shared script that applies the configuration, and ask them to run it after each change in the repository
C: Back up each cluster's configuration nightly into Cloud Storage, and compare the files by hand whenever an incident suggests a difference
D: Design all workloads for one namespace so that no per-cluster policy is needed, and rely on application teams to follow conventions
K: A
G: ## GitOps for fleets of clusters
GitOps treats a Git repository as the single source of truth for desired state. Config Sync, a GitOps service included with GKE, continuously syncs configurations and policies from a central source such as Git to many clusters, so a fleet is managed centrally and **configuration drift** is prevented rather than discovered. Changes then follow the same review, approval and rollback path as code: a revert in Git is a rollback in every cluster.
- Works across clusters in Google Cloud and registered clusters elsewhere, which fits hybrid estates.
- Manual edits that diverge from Git are reverted by reconciliation.
- Auditability: who changed what is the Git history.
W: Git as the source of truth with Config Sync reconciliation: all clusters converge to the same declared state, drift from manual changes is corrected automatically, and every change is reviewed and reversible in Git.
X: B=Shared script: it depends on people remembering to run it everywhere, nothing reverts later manual edits, and scripts diverge across teams.
C=Nightly backups compared by hand: this finds differences after the fact, slowly and manually, and does not correct anything.
D=One namespace-free design: the stem's need is consistent namespaces, network policies and roles. Removing them weakens isolation and does not solve drift.
T: Config Sync reconciles clusters to a Git source of truth, preventing drift and making rollback a revert.

@ GCP-PCA D6 T6.3 applied troubleshooting
S: A web tier runs on a regional managed instance group of 12 VMs behind a load balancer. When the team rolls out a new instance template, the group briefly serves errors because too many VMs are replaced at once and some new VMs receive traffic before the application is ready. Which action best fixes the rollout?
A: Use a proactive rolling update with low maxUnavailable and a surge allowance, plus an application-based health check for new VMs
B: Delete all VMs in the group at once and let autoscaling create new ones from the new template, which is the fastest rollout method available
C: Update each VM in place by connecting over SSH and changing the package version, one VM at a time during off-peak hours
D: Raise the load balancer's idle timeout so that in-flight requests are not interrupted while VMs are being replaced by the update
K: A
G: ## Rolling updates in managed instance groups
A MIG applies a new instance template to existing VMs with a proactive (automatic) update. You tune the speed and the disruption:
- **maxSurge** is how many extra VMs the group may create above target size during the update.
- **maxUnavailable** is how many VMs may be offline at the same time. Defaults are 1 per affected zone.
- An **application-based health check** with autohealing marks a VM unhealthy if the application does not respond, and the group repairs it; the load balancer uses health checks to send traffic only to healthy backends.
- A **canary update** (two template versions) applies the new template to a subset first.
Tight unavailability limits keep capacity during the rollout, surge keeps full capacity while new VMs start, and the health check keeps unready VMs out of service.
W: Rolling update with lower maxUnavailable, surge and an application-based health check: capacity stays close to full during the update, and a new VM receives traffic only once the application responds.
X: B=Delete all VMs at once: this removes the entire tier's capacity together, which is the opposite of a controlled rollout and causes an outage.
C=SSH edits per VM: manual and unrepeatable, creating VMs that no longer match the template and breaking immutable-infrastructure consistency.
D=Longer idle timeout: this affects connection handling in the load balancer, but not how many VMs are replaced at once or whether new VMs are ready.
T: Control MIG rollouts with maxSurge, maxUnavailable and health checks so capacity and readiness are protected.
V: Compute Engine, Cloud Load Balancing

@ GCP-PCA D6 T6.3 applied tradeoff
S: A product team merges code to the main branch daily, but a large new pricing feature will take six weeks to complete and must be switched on for customers only on a marketing date. The team wants to avoid a long-lived feature branch that is hard to merge. Which practice fits best?
A: Merge the unfinished feature in small increments behind a feature flag, deploy continuously with it off, and switch it on at launch
B: Keep the work on a separate long-lived branch for six weeks, then merge and deploy everything together on the launch date
C: Deploy a separate full copy of the application containing the feature, and switch every customer to it on the launch date by changing DNS
D: Hold all other teams' releases until the pricing feature is complete, so that the release train only ever contains finished features
K: A
G: ## Separate deployment from release
Deploying code (putting a new version into production) and releasing a feature (making it visible to users) are different decisions. A **feature flag** lets unfinished or scheduled functionality ship in small increments, dark, while a configuration switch decides who sees it and when. This supports trunk-based development, which DORA research associates with higher delivery performance: short-lived branches, frequent integration and small batches.
- A flag can be turned off instantly if the feature misbehaves, without a rollback deploy.
- Exposure can be gradual (internal users, a percentage, a region).
- Remove flags after launch to avoid accumulating complexity.
W: Small merges behind a feature flag: integration stays continuous, deployments stay routine, and the business launches on its date by flipping the flag, with an instant off switch if needed.
X: B=Six-week branch: the merge grows more conflicting each day, and everything lands in one large, risky deployment on launch day.
C=Duplicate whole application with DNS switch: this doubles infrastructure and data-sync problems for one feature, and all customers move at once with slow reversal through DNS caching.
D=Block other releases: it penalizes unrelated teams, batches changes into a larger release and reintroduces the big-bang risk.
T: Use feature flags with trunk-based development to deploy continuously and release on the business schedule.
V: Cloud Build

@ GCP-PCA D6 T6.3 advanced tradeoff
S: Altostrat Media runs a highly available metadata service on a GKE Standard node pool. A previous node upgrade changed the node configuration, the workloads misbehaved on the new nodes, and returning to the old nodes took hours. The team accepts a temporary cost increase if it can validate the workloads on new nodes and go back quickly. Which node upgrade strategy fits?
A: Configure the node pool for blue-green upgrades with a soak time, so the original nodes remain available for rollback until the workloads are validated
B: Keep the default surge upgrade with maxUnavailable set to zero, because it restores the previous nodes automatically whenever the new Pods fail
C: Disable auto-upgrade and rebuild the node pool from scratch after each release, deleting the old nodes first so that no stale capacity is kept
D: Upgrade only the control plane and leave the nodes on their older version indefinitely, because nodes may run any older version without limit
K: A
G: ## Choosing a GKE node upgrade strategy
For Standard node pools GKE offers two generally available strategies.
- **Surge upgrades** (default) roll through nodes: new surge nodes are created and old nodes are cordoned, drained and deleted, with `maxSurge` and `maxUnavailable` controlling speed and disruption. After the upgrade has completed you cannot roll the pool back; you would have to downgrade by other means.
- **Blue-green upgrades** first create a full set of new ("green") nodes, then move workloads, and keep the original ("blue") nodes during a **soak time** so that you can roll back if the workloads do not tolerate the change. The price is roughly double the node resources during the upgrade.
Choose blue-green for highly available production workloads where quick rollback matters more than temporary cost. Autopilot clusters use surge upgrades only.
W: Blue-green with soak time: the old nodes stay available for rollback while the new nodes are validated, which trades temporary extra cost for fast recovery.
X: B=Surge with zero unavailable: this controls pace, but old nodes are deleted as they are replaced and a completed upgrade cannot be rolled back automatically.
C=Delete first and rebuild: removing the old nodes before validation gives up exactly the rollback capacity the team wants and risks an outage.
D=Control plane only: nodes may lag the control plane only within supported version skew limits, and unpatched nodes lose security fixes.
T: Use blue-green node pool upgrades with a soak time when fast rollback matters more than temporary extra capacity.
V: GKE

@ GCP-PCA D6 T6.3 applied tradeoff
S: Altostrat Media's CI pipeline pushes a new image to Artifact Registry on every commit, and the repository grows without limit. Images that run in production and the most recent releases must never be deleted, but old untagged and test images should go. Which approach fits?
A: Configure cleanup policies with keep rules for release-tagged images and the most recent versions plus a delete rule by age, and test them with a dry run
B: Delete images by hand every quarter after asking each team which tags they still use, because only people can know what is deployed in production
C: Apply a delete rule by age alone to the whole repository, because images older than one month are never needed for a rollback of a release
D: Stop pushing images from CI and rebuild them from source at deploy time in each cluster, so that the registry holds nothing that needs cleaning
K: A
G: ## Retention for build artifacts
Artifact Registry **cleanup policies** automate retention and removal in a repository and reduce storage cost.
- **Delete policies** remove artifacts that match conditions such as minimum or maximum age, tag state or tag prefix.
- **Keep policies** protect artifacts, either by conditions (for example a release tag prefix) or by keeping a number of most recent versions. A single keep policy uses conditions or most-recent-versions, not both, so use separate policies.
- If an artifact matches both a delete and a keep policy, it is **kept**.
- A **dry run** shows what would be deleted before the policy is enforced.
Production images should also be referenced by digest and tagged for releases, so the keep rules can recognise them. Rebuilding at deploy time breaks the principle that the tested artifact is the one that runs.
W: Keep rules for release tags and recent versions, a delete rule by age and a dry run: unused images are removed automatically, protected images always survive and the effect is checked first.
X: B=Quarterly manual deletion: slow, error-prone and dependent on memory, so storage keeps growing and a needed image can be deleted by mistake.
C=Age-only delete rule: it deletes long-lived production or rollback images that are still in use, because a keep rule overrides deletion only when it exists.
D=Rebuild at deploy time: each cluster would build a different artifact from the tested one, so reliability suffers and nothing is verified.
T: Use cleanup policies with keep rules and a dry run to control registry growth safely.
V: Artifact Registry
