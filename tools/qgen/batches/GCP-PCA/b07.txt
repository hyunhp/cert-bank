@ GCP-PCA D3 T3.2 applied use-case
S: EHR Healthcare will store protected health information in Google Cloud and wants a technical guardrail so that engineers cannot use a Google Cloud service outside the ones covered by its Business Associate Agreement (BAA). Which approach best supports this goal?
A: Pin all health data to a single region, because the BAA is valid only for services running in the region where the agreement was signed
B: Rely on the BAA alone, because it automatically blocks any service that is not covered, so engineers cannot reach an unsupported service by mistake
C: Accept the BAA, apply an organization policy limiting which services the health-data folder can use, and keep pre-GA offerings away from that data
D: Request a HIPAA certificate from the regulator for the Google Cloud project, since certification of the project is what makes every service in it acceptable
K: C
G: ## What a BAA does and does not do
In the United States, HIPAA applies to covered entities and their business associates. When a cloud provider handles protected health information (PHI) for you, a Business Associate Agreement (BAA) is the contract that sets out its obligations. Google's HIPAA guidance says the U.S. Department of Health and Human Services offers no certification program for HIPAA, that compliance is a shared responsibility, and that the Google Cloud BAA covers the whole Google Cloud infrastructure (all regions) but only a listed set of products.
## Staying inside the covered products
- The guidance tells customers to disable unsupported services for PHI, and not to use pre-GA offerings with PHI unless the terms say so.
- The preventive control is an organization policy: the `gcp.restrictServiceUsage` constraint limits which service APIs a folder or project may use, so a mistake cannot happen by accident.
- Assured Workloads has a Healthcare and Life Sciences control package (HIPAA and HITRUST) that adds data boundary controls; it is an extra guardrail, not a legal prerequisite for HIPAA.
This is an architecture pattern, not legal advice; the compliance team still evaluates the obligations.
W: Accepting the BAA and then restricting allowed services at the folder level with an organization policy turns the "covered products only" rule into an enforced guardrail, and excluding pre-GA features follows the HIPAA guidance.
X: B=BAA blocks services: a BAA is a contract, not a technical control. It does not stop anyone from enabling a service, so without a policy an engineer can send PHI to an uncovered product.
D=Regulator certificate: HHS does not certify HIPAA compliance, so no such certificate exists for a project. Compliance is shown through your own controls and the shared responsibility model.
A=Single region: the Google Cloud BAA covers the entire infrastructure, all regions and zones. Tying PHI to one region is a separate residency choice, not a condition of the BAA.
T: A BAA is a contract; enforce "covered services only" with organization policy and keep pre-GA features away from PHI.
V: Organization Policy, Assured Workloads

@ GCP-PCA D3 T3.2 advanced tradeoff
S: EHR Healthcare needs consistent logging and retention across many projects. Auditors want admin and data-access records kept for seven years, and security staff in individual projects must not be able to shorten that period. An architect proposes a central design. Which design satisfies the requirement?
A: Raise the retention period on the log buckets that exist at the organization level, because folder and organization buckets can be extended without limit
B: Leave each project on its default log bucket and ask project owners to raise the retention period when their team has a compliance need
C: Increase retention on the required log bucket in every project, so that all admin activity logs are held for seven years by default
D: Create an aggregated sink at the organization routing audit logs to a log bucket in a dedicated logging project, then set retention there and lock it
K: D
G: ## Where log retention can be set
Cloud Logging stores logs in log buckets. Every project has a `_Required` bucket (Admin Activity and System Event audit logs, fixed 400-day retention that cannot be changed) and a `_Default` bucket (default 30 days, configurable). Retention is configurable per user-defined bucket, between 1 and 3650 days.
## Centralizing and protecting it
- The docs state that you cannot extend the retention period of a log bucket that lives in a folder or organization. The supported pattern is a log sink routing those entries to a bucket in a project, then setting that bucket's retention.
- An aggregated sink at the organization or a folder routes logs from all child projects to one destination, giving one retention rule for all of them.
- Locking a bucket locks its retention policy: it can no longer be shortened, and the bucket cannot be deleted until every entry has met retention. Add a lien on the project to prevent accidental project deletion.
W: An aggregated sink to a dedicated project's log bucket gives one consistent retention setting for all projects, and locking the bucket stops anyone, including administrators of source projects, from reducing the period.
X: A=Extend org-level buckets: the docs say the retention of a bucket in a folder or organization cannot be extended; the retention must be set on a bucket in a project that the sink targets.
B=Per-project owners: leaving the choice to each team is the opposite of consistent retention, and project-level administrators could also shorten it later. Nothing enforces seven years.
C=Required bucket: the retention of the `_Required` bucket is fixed at 400 days and cannot be changed, so it can never be stretched to seven years.
T: Central, consistent retention: aggregated sink to a log bucket in a project, set retention there, then lock it.
V: Cloud Logging

@ GCP-PCA D3 T3.2 advanced use-case
S: Cymbal Retail records calls from its IVR and call-center agents, who key in customer orders, and plans to send the transcripts to BigQuery for analytics and gen AI summaries. Callers read out payment card numbers, so the card data would spread into analytics datasets. What is the best design to keep card data out of those systems?
A: Encrypt the transcript files with a customer-managed key and keep the card numbers in the text, so only key holders can read the content
B: Store transcripts unchanged and rely on the BigQuery dataset permissions to keep analysts from reading the card numbers in the text
C: Delete the transcripts after the analytics job finishes and leave the raw call recordings in the original bucket indefinitely
D: Run the transcripts through Sensitive Data Protection to detect and redact card numbers before they are stored in the analytics datasets
K: D
G: ## Reducing the scope of cardholder data
PCI DSS applies to all systems, networks and applications that store, process or transmit cardholder data, plus systems that secure and log access to them. The less cardholder data spreads, the smaller that scope. Google Cloud's PCI-compliant services give a base to build on, but the customer remains responsible for its application's compliance.
## Removing the data early
Sensitive Data Protection can inspect text for infoTypes such as credit card numbers and de-identify them. Its transformations include redaction (delete the value), replacement, masking, crypto-based tokenization, bucketing and date shifting. For card numbers in transcripts, redaction or masking before storage means the analytics layer never holds the primary account number, so those systems stay out of the card environment.
The same idea applies to the original recordings: keep audio containing spoken card data in a tightly controlled location, or avoid capturing it at all.
W: Detecting and redacting card numbers with Sensitive Data Protection before storage removes the data from analytics and gen AI summaries, which keeps those systems out of the cardholder data scope.
X: B=Dataset permissions only: access control limits who can read, but the card numbers still sit in every analytics table, so all those systems remain in PCI scope and any over-broad grant exposes them.
A=Encrypt and keep the text: encryption at rest protects the stored files but the data is still decrypted for every query and summary, so the downstream services still process cardholder data.
C=Delete transcripts later: leaving the raw recordings with card data in the bucket indefinitely keeps cardholder data in scope, and the data still flowed through the analytics job.
T: Reduce PCI scope by removing card data early: detect and redact it with Sensitive Data Protection before it reaches analytics.
V: Sensitive Data Protection, BigQuery

S: A language-learning company is launching a mobile app for children under 13 and runs it on Google Cloud. The legal team cites the U.S. children's privacy law (COPPA). Which architectural approach best supports the privacy obligations without claiming that the platform alone makes the company compliant?
A: Store child data in the same wide analytics tables as adult users and tag the rows, because separate storage makes deletion requests harder to run
B: Collect as much usage data as possible now and decide later which records the team is allowed to keep, because large datasets are easier to anonymize afterward

@ GCP-PCA D3 T3.2 advanced use-case
S: A car maker wants to combine vehicle owner records from several systems so analysts can count and join a single owner's data across tables, but analysts must not see names or e-mail addresses. A privacy engineer must choose a Sensitive Data Protection transformation. Which choice fits?
A: Replacement with one fixed text value, because a single shared surrogate keeps every owner's records distinguishable for counting and joining
B: Deterministic tokenization of the identifiers: identical inputs give identical tokens that still join across tables, and the key allows authorized reversal
C: Redaction of the identifiers, because removing the values still lets analysts join one owner's records across tables by the same remaining value
D: Fixed-size bucketing of the identifiers, because grouping them into ranges keeps all of one owner's data together across the different systems
K: B
G: ## Matching the transformation to the need
Sensitive Data Protection groups de-identification into redaction, replacement, masking, crypto-based tokenization, bucketing, date shifting and time extraction. Two properties decide the choice:
- **Reversible** (can re-identify with the key) and
- **Referential integrity** (the same input and context give the same output, so records still join).
Deterministic encryption (AES-SIV) and the format-preserving variant are tokenization methods that provide both; a cryptographic hash keeps referential integrity but cannot be reversed. Redaction, replacement and bucketing keep neither of them.
For analysts who must count and join per owner but not see identities, tokenization with a key held by a small group is the match. Under privacy law this is pseudonymization, still personal data, so access to the key stays tightly controlled.
W: Deterministic tokenization maps the same identifier to the same token everywhere, so counts and joins work, while analysts see only tokens; the key allows authorized re-identification when needed.
X: C=Redaction: removing the value deletes the link as well, so records of one owner can no longer be joined or counted.
D=Fixed-size bucketing: bucketing replaces a value with a range, so many different owners share a bucket and one owner's records cannot be told apart.
A=Single replacement value: every owner receives the same value, so all owners look identical and counting or joining per owner is impossible.
T: To hide identity yet keep joins, use deterministic tokenization (same input, same token, reversible with the key).
V: Sensitive Data Protection

@ GCP-PCA D3 T3.2 advanced use-case
S: A health research team trains a model on patient visit records that contain exact ages and visit dates. The privacy officer wants to reduce re-identification risk while keeping the data useful: the order and spacing of each patient's visits must be preserved. Which TWO Sensitive Data Protection transformations fit this? (Select TWO)
A: Cryptographic hashing of the dates, which keeps the intervals between visits available for analysis and for the model
B: Bucketing, which replaces exact ages with age ranges so that individual patients are harder to single out
C: Redaction of all the date columns, which still keeps the sequence of visits available to the model during training
D: Date shifting, which moves dates by a random amount, consistent per patient, so the order and intervals between visits stay intact
E: Replacement of every date with the same fixed value, which preserves the order of visits for each patient
K: B,D
G: ## Generalizing and shifting
- **Bucketing** generalizes a value into a range (for example 34 becomes 30-39), so a person is harder to single out by exact age.
- **Date shifting** moves dates by a random number of days; with a context such as a patient ID the shift is consistent, so sequences and durations are preserved even though the absolute dates are hidden.
- Redaction and replacement remove or flatten the values, so the analytic signal is lost. Hashing a date produces a string, not a date, so intervals can no longer be computed.
W: D=Date shifting: preserves sequence and duration for each patient while hiding real dates, which the model needs.
B=Bucketing: turns exact ages into ranges, reducing re-identification risk while staying useful for analysis.
X: C=Redaction of dates: deletes the dates, so the order and spacing of visits cannot be known at all.
A=Hashing dates: a hash is an opaque string; it cannot be subtracted to produce intervals or ordered by time.
E=Same value for all dates: every visit looks simultaneous, so order and spacing are destroyed.
T: Generalize attributes with bucketing and keep time structure with consistent date shifting.
V: Sensitive Data Protection

@ GCP-PCA D3 T3.2 applied use-case
S: A hospital software vendor must be able to show auditors who read patient files held in Cloud Storage buckets. The team finds that Admin Activity logs exist but cannot find entries for object reads. What should the architect do?
A: Enable audit logging on the Cloud Logging API itself, because that setting writes a record each time an object in a bucket is read by a user
B: Grant the audit team the Logs Viewer role so they can see Data Access audit logs, which are stored in the same required bucket as Admin Activity logs
C: Enable Data Access audit logs for Cloud Storage on the file projects, give Private Logs Viewer only to auditors, and route the logs to a protected archive

Cloud Audit Logs provides Admin Activity, Data Access, System Event and Policy Denied logs.
