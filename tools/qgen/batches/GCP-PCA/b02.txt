@ GCP-PCA D1 T1.2 applied tradeoff
S: EHR Healthcare is moving a customer-facing records portal to Google Cloud. The stateless web tier must keep serving users if one zone of the region fails, and the MySQL database behind it must fail over without anyone restoring a backup. The company accepts a few minutes of database interruption during a zonal failure but wants to avoid the cost of running in several regions. Which design fits?
A: A regional managed instance group behind a load balancer, plus Cloud SQL for MySQL in a high-availability configuration with a standby in a second zone
B: A zonal managed instance group with a fast snapshot schedule, plus a Cloud SQL for MySQL instance with a single zone and a nightly export to a Cloud Storage bucket
C: Two regional managed instance groups in different regions behind a load balancer, plus a Spanner multi-region instance for every table in the application database
D: A single large Compute Engine VM in one zone that relies on live migration for host maintenance, plus a self-managed MySQL server on a persistent disk of that VM
K: A
G: ## Designing for zone failure within one region
A region contains several zones, which are separate failure domains. The reliability pillar of the Well-Architected Framework says to "build highly available systems through resource redundancy": every tier must have capacity in more than one zone, and a failure must be handled automatically instead of by a person.
- **Stateless tier**: a regional managed instance group (MIG) spreads identical VMs over multiple zones in one region. If a zone is lost, the instances in the remaining zones keep serving, and a load balancer stops sending traffic to unhealthy backends.
- **Stateful tier**: Cloud SQL high availability (HA) creates a primary and a standby in two zones of the same region. Writes are replicated synchronously to the disks in both zones before they are committed, and if the instance or zone fails the standby becomes the new primary and users are rerouted (a failover) with a short interruption. The standby is not used for reads.
## Matching the requirement to the cost
The requirement is zone-level resilience with a tolerated interruption of minutes. Multi-region is a separate, more expensive step that buys protection against the loss of an entire region, which this company did not ask for.
W: Regional MIG plus Cloud SQL HA: both tiers span two or more zones, so a zonal outage is absorbed automatically, with no restore step. The database failover is automatic and causes only a short interruption, which is within the stated tolerance, and everything stays in one region to keep cost down.
X: B=Zonal MIG with snapshots and exports: a single zone is a single failure domain, so a zonal outage stops the web tier and the database until someone restores from a snapshot or an export, which is exactly the manual recovery the company wants to avoid.
C=Two regions with Spanner multi-region: it would survive a regional loss, but the requirement only covers a zone, so this adds cost and rework to the application for protection that nobody requested.
D=Single large VM with live migration: live migration only handles host maintenance events, not the loss of a zone, and one VM with a self-managed database remains a single point of failure.
T: Spread each tier over multiple zones (regional MIG, Cloud SQL HA) to survive a zone failure automatically; go multi-region only when a regional outage must be survived.

@ GCP-PCA D1 T1.2 applied comparison
S: A logistics company has classified its order-management system as needing a recovery time objective of 4 hours and a recovery point objective of 15 minutes if the primary region is lost. The business will not fund a full second production environment. The database is MySQL. Which disaster recovery pattern fits best?
A: Cold pattern, with nightly backups restored into an empty second region only after a disaster has been declared by the incident team
B: Hot pattern, with two fully scaled production stacks serving live production traffic in two regions at all times
C: Warm standby: a cross-region database replica plus a scaled-down copy of the stack, scaled up on failover
D: No separate pattern: a single regional deployment, since zone redundancy covers a regional outage
K: C
G: ## Cold, warm and hot disaster recovery
The disaster recovery (DR) planning guide ties the pattern to the recovery objectives:
- **RTO** is the longest acceptable outage; **RPO** is the longest window of data that may be lost. Smaller values mean higher cost and complexity.
- **Cold**: minimal resources in the DR location. Recovery means provisioning and restoring, so RTO is long and RPO equals the age of the last backup.
- **Warm standby**: data is continuously replicated and a reduced-size environment is already running or ready. On failover you scale it up, so RTO is shorter without paying for full capacity.
- **Hot**: both environments serve production traffic, which gives the smallest RTO and RPO and the highest cost.
## Reading the numbers
A 15-minute RPO is far smaller than any nightly backup interval, so data must be replicated continuously, for example with a cross-region read replica that is promoted on failover. A 4-hour RTO leaves time to scale out a prepared stack, so a full hot environment is unnecessary.
W: Warm standby: a cross-region replica keeps data within minutes of the primary (meeting the 15-minute RPO), and the scaled-down stack can be expanded within the 4-hour RTO without funding a second full production environment.
X: A=Cold pattern with nightly backups: a nightly backup means up to a day of data loss, which breaks the 15-minute RPO, and building an empty region from scratch is risky for a 4-hour RTO.
B=Hot pattern: it would meet the objectives, but it duplicates the whole production cost, which the business explicitly refused to fund.
D=Single region with zone redundancy: zones are inside one region, so losing the region takes every zone with it and the stated regional-loss scenario is not covered.
T: Pick the cheapest DR pattern whose replication meets the RPO and whose recovery steps fit inside the RTO; continuous cross-region replication plus a scaled-down stack is warm standby.

@ GCP-PCA D1 T1.2 advanced use-case
S: A company runs a Cloud SQL for MySQL instance with high availability enabled and a cross-region read replica. A script run by an administrator drops a production table by mistake, and ransomware protection is also a board concern for the backup copies. The team learns that the standby and the replica both already show the table as gone. Which TWO measures protect against this kind of logical damage? (Select TWO)
A: Enable automated backups with point-in-time recovery so the database can be restored to a moment just before the faulty statement
B: Add a second cross-region read replica so that one more copy of the data exists in another location
C: Use Backup and DR with a backup vault, whose write-once-read-many immutability keeps protected backups from being altered or deleted
D: Switch the instance to a multi-region Cloud Storage bucket for its data files, so objects are stored in several locations
E: Raise the instance to a larger machine type, so that a failover to the standby completes faster after such an error
K: A,C
G: ## Redundancy is not backup
High availability and replicas protect against the loss of infrastructure (a zone, an instance, a region). They copy every change, including a wrong one: a dropped table, a bad UPDATE or an encrypting attacker is replicated to every copy within seconds. Protection against logical errors and malicious deletion needs **point-in-time history** and **protected backup copies**.
## Tools
- **Backups plus point-in-time recovery (PITR)** in Cloud SQL: restore to a chosen timestamp before the error, so little data is lost within the retained window.
- **Backup and DR** with a **backup vault**: policy-based backups kept in a vault with write-once-read-many (WORM) immutability and indelibility, so a compromised account or ransomware cannot remove them.
## Applying it
Both the accidental drop and the ransomware worry are about data that is valid in form but wrong in content. The answers are the ones that keep older, protected states of the data.
W: A=Backups with point-in-time recovery: it lets the team restore to the moment before the faulty statement, which is the only way to undo a replicated logical change.
C=Backup and DR vault: immutable, indelible backups survive deletion attempts and ransomware, giving a clean copy that does not depend on the production instance.
X: B=Another read replica: a replica applies the same writes as the primary, so it would also show the table as dropped; more copies do not mean older copies.
D=Multi-region bucket for data files: Cloud SQL manages its own storage and does not run on a bucket you pick, and object replication would copy corrupted content anyway.
E=Larger machine type: failover speed addresses infrastructure failure, and the standby already contains the same damaged data, so a faster failover restores nothing.
T: HA and replicas keep up with mistakes as well as with data; only PITR and immutable backups give you an earlier, safe state to return to.

@ GCP-PCA D1 T1.2 applied use-case
S: Cymbal Retail expects holiday traffic several times higher than normal for a few days. Its web tier stores each shopper's cart in the memory of the VM that served the first request, so the load balancer is configured with session affinity and the team can only grow capacity by buying larger VMs. Which change best prepares the tier for the peak?
A: Keep the design, order the largest available machine type, and let each VM hold more carts in its memory
B: Move cart state to Memorystore for Redis, make the web VMs stateless, and run them in an autoscaled managed instance group
C: Move to a spot-VM fleet of identical size, because the lower price per VM allows the team to over-provision all year
D: Move the web tier into a single zone on high-CPU VMs, so all requests reach machines in one network location
K: B
G: ## Horizontal scalability needs stateless tiers
The reliability and performance pillars both recommend scaling out (more instances) rather than only scaling up (bigger instances). Scaling up has a ceiling and a restart cost, and it leaves one machine as a single point of failure. Scaling out works only if any instance can serve any request.
- **Externalize state**: store sessions and carts in a shared service such as Memorystore for Redis (Cymbal already uses Redis) or a database, so that no VM holds data that others need.
- **Autoscale**: a managed instance group can add instances when load grows and remove them when it falls, which also reduces cost after the peak.
## Result for the holiday peak
With stateless VMs, the load balancer can send any request to any instance, a lost VM does not lose carts, and the group follows demand automatically.
W: External cache with stateless autoscaled MIG: carts survive instance loss, session affinity is no longer needed, and capacity grows and shrinks with traffic instead of being sized for the worst case by hand.
X: A=Largest machine type: scaling up has a hard upper limit, keeps carts tied to individual VMs and leaves each VM as a single point of failure during the peak.
C=Spot fleet for all-year over-provisioning: spot VMs can be reclaimed at any time, which loses in-memory carts on exactly the busiest days, and over-provisioning all year wastes money.
D=Single zone with high-CPU VMs: it concentrates the load in one failure domain and does nothing about carts living in VM memory.
T: Scale out, not up: make tiers stateless by moving session data to a shared store, then let autoscaling follow demand.

@ GCP-PCA D1 T1.2 applied use-case
S: Altostrat Media serves podcasts and documentaries to viewers on several continents. Media files are in Cloud Storage and the origin application is in one region. Viewers far from the region see slow start times for popular episodes, while the origin is lightly loaded. Which change most directly reduces latency for these viewers?
A: Move the origin application to a machine type with more vCPUs, to shorten the processing time of each request
B: Create a second Cloud Storage bucket in the same region and split the objects between the two buckets
C: Increase the replication of the media archive to a dual-region location and keep serving viewers from the same two regions
D: Put a global external Application Load Balancer in front, with Cloud CDN enabled so popular objects are cached close to the viewers
K: D
G: ## Latency is mostly distance
The performance pillar says to plan resource allocation around where users are. Round-trip time over long distances cannot be bought away with faster servers: the content must be closer to the user.
- **Cloud CDN** caches cacheable responses at Google edge locations. A cache hit is served near the viewer without reaching the origin, which cuts start-up time and offloads the origin.
- It works together with a global external Application Load Balancer, which gives one anycast front end for users everywhere.
## Diagnosing the case
The origin is lightly loaded, so compute is not the bottleneck. The distance between viewers and the one serving region is. Popular episodes are exactly the repeated, cacheable requests a CDN serves best.
W: Global load balancer with Cloud CDN: popular episodes are cached at edge locations near viewers on every continent, so start-up delay falls while the origin load falls too.
X: A=More vCPUs at the origin: the origin is already lightly loaded, so processing time is not the delay; the delay is network distance.
B=Second bucket in the same region: splitting objects within a region neither moves data closer to viewers nor reduces distance-related delay.
C=Dual-region bucket: it improves durability and availability for the archive, but viewers would still fetch from the same two regions, so far-away viewers see little change.
T: When latency comes from distance and content is repeatedly requested, cache at the edge with Cloud CDN behind a global load balancer instead of scaling the origin.

S: A retailer sees its monthly Google Cloud bill jump in the middle of the month. Finance wants to know which products, SKUs and resources caused the change, and the platform team would like the explanation to appear without someone starting an investigation each time. Which capability fits best?
A: Gemini Cloud Assist cost anomaly analysis, which runs when an anomaly is detected and explains the change behind it
B: Gemini Cloud Assist natural language design, which helps create a new and cheaper architecture for the application

@ GCP-PCA D1 T1.2 advanced use-case
S: Cymbal Retail's product page calls a recommendation service to show "you may also like" items. When that service is slow or fails, the whole page fails and shoppers cannot buy the product they came for. The business says recommendations are nice to have, and the checkout is the revenue. Which design change best follows reliability guidance?
A: Raise the availability target of the recommendation service to equal checkout, and keep the page dependent on it
B: Remove recommendations from the site, because any optional dependency lowers the availability of the page
C: Add a short timeout and a circuit breaker to the recommendation call, and show the page without it on failure
D: Retry the recommendation call repeatedly until it succeeds, so the page always shows the complete content to every shopper
K: C
G: ## Design for graceful degradation
The reliability pillar lists "design for graceful degradation" as a principle: when a non-essential dependency fails, the system should lose that feature, not the whole function. Technical tools are:
- **Timeouts and circuit breakers**: stop waiting for a failing dependency and stop calling it for a while, so slow calls do not pile up and exhaust threads.
- **Fallbacks**: serve cached, default or reduced content.
- **Classify dependencies**: hard (checkout, payment) versus soft (recommendations, banners), and give hard dependencies the stricter targets.
## Why the other directions fail
Raising everything to the highest target is costly; endless retries amplify load on a struggling service and make the page slower. Removing features loses business value that can be kept safely with a fallback.
W: Timeout, circuit breaker and fallback: the page degrades to a version without recommendations, so a failure of the soft dependency no longer blocks the revenue-critical purchase path.
X: A=Equal availability target: it makes a non-essential service as expensive as checkout, and the page remains coupled, so any residual failure still breaks it.
B=Remove recommendations: it gives up a business feature to avoid a risk that a fallback removes at a much smaller cost.
D=Retry until success: unbounded retries add load on an already struggling service and make the page slower, which can turn a partial failure into a full outage.
T: Classify dependencies as critical or optional and let optional ones fail softly with timeouts, circuit breakers and fallbacks.

@ GCP-PCA D1 T1.2 applied comparison
S: A hospital group runs a patient-scheduling application whose database is read-heavy: about 90% of queries are lookups and reports, and writes come from one region. At peak, the single Cloud SQL primary reaches its CPU limit, although the team does not want to rewrite the application or change database engines. Which approach scales the workload with the least change?
A: Migrate the database to a globally distributed Spanner instance, and rewrite the schema and queries for the new engine
B: Add Cloud SQL read replicas, and route read-only queries and reports to them while writes continue to go to the primary
C: Disable high availability on the primary, because the standby consumes CPU that the primary needs for queries
D: Move all report queries into the primary's maintenance window, so that they no longer compete with lookups during peak hours
K: B
G: ## Scaling relational reads
Relational databases scale reads more easily than writes. Cloud SQL **read replicas** receive changes asynchronously from the primary and can serve read-only queries, so reads are spread across several instances while the primary keeps handling writes. The application needs only to send read traffic to a replica endpoint.
- Fits when reads dominate and slightly stale data is acceptable.
- Does not increase write throughput, which remains with the primary.
- A cache in front of the database is another option for repeated lookups.
## Alternatives
Spanner scales writes horizontally and across regions, but it is another engine with schema and query work. Changing HA settings or moving queries around does not add capacity.
W: Read replicas with read/write splitting: they take the lookups and reports off the primary, relieving its CPU with only a connection-routing change in the application.
X: A=Spanner migration: it scales writes and regions, but the workload is read-heavy with writes in one region, and the team explicitly does not want a rewrite or a new engine.
C=Disable high availability: the standby does not run queries and does not consume the primary's CPU, and removing it would drop zone resilience for no gain.
D=Run reports in the maintenance window: maintenance windows are for updates, and reports are demand-driven, so postponing them does not add capacity for the peak.
T: For read-heavy relational workloads, add read replicas (or a cache) and split read and write traffic before considering a new database engine.

@ GCP-PCA D1 T1.2 advanced troubleshooting
S: An application is deployed in two regions, each with a managed instance group behind its own regional load balancer. Users reach it through a DNS name that points to the primary region, and operators change the DNS record manually if that region fails. During a recent regional outage some users kept reaching the failed region for more than an hour because resolvers cached the old record. What design change gives the fastest automatic fail-over?
A: Lower the DNS record's time-to-live to one second and keep the manual process for changing the record when needed
B: Add a third regional load balancer in the primary region, giving users more entry points into the failed region
C: Use a global external Application Load Balancer with health-checked backends in both regions
D: Add more instances to the managed instance group in the primary region before the next outage occurs, to hold more load
K: C
G: ## Where fail-over decisions are made
If the fail-over decision depends on DNS answers, clients and resolvers that cache records keep using the old address for as long as their cache lasts, and a person must also notice and act. A **global external Application Load Balancer** has a single anycast IP address and health-checks its backends in every region. When a region's backends are unhealthy, it routes requests to healthy backends in other regions automatically, with no client-side change.
## Design points
- Health checks decide when a backend is out; they must reflect the application's real readiness.
- Remaining regions need capacity to absorb the traffic (see capacity planning for DR).
- Data layers must also fail over; the load balancer solves only the entry point.
W: Global load balancer with multi-region backends: one stable address, automatic health-based routing away from the failed region, no dependency on cached DNS answers or an operator.
X: A=One-second TTL with manual changes: many resolvers ignore or floor very low TTLs, and a person must still detect the outage and edit the record, so recovery stays slow.
B=Third load balancer in the primary region: more entry points inside the failed region fail together with it and do not change how clients are directed.
D=More instances in the primary region: capacity does not help when the whole region is unavailable.
T: Use a global load balancer with health-checked multi-region backends for automatic fail-over instead of relying on DNS changes.

@ GCP-PCA D1 T1.2 applied troubleshooting
S: A warm-standby disaster recovery design replicates data to a second region and keeps only a few VMs running there. During a rehearsal, scaling up the standby stack to production size failed in the recovery region because the required machine type was temporarily unavailable in the chosen zone, and the RTO was missed. What should the architect add to the design?
A: Reservations for the required Compute Engine capacity in the recovery region, so resources are available when failover starts
B: A shorter health check interval on the primary region, so that the failure is detected sooner than it is now
C: A larger boot disk for the standby VM image, so that the machine starts faster after the failover begins
D: A second storage bucket in the primary region for the VM images, so the images are available if the first bucket fails
K: A
G: ## Capacity is part of a DR plan
The DR planning guide warns that a recovery environment must have its resources available at the time of the disaster. On-demand VMs depend on available capacity at that moment, and in a regional event many customers may try to start resources at once. If an RTO depends on starting large numbers of VMs, the design must secure that capacity.
- **Reservations** let you reserve Compute Engine resources in a specific zone, so the capacity is guaranteed to be there when you create VMs that match the reservation.
- You pay for reserved resources while they are reserved, so reserve what the RTO needs and keep the rest elastic.
- Rehearsals find these gaps before a real incident does.
## Reading the scenario
Data replication worked and failure was detected. The failure was the inability to obtain compute in the recovery region.
W: Reservations in the recovery region: they hold the machine capacity needed for the scale-up, so the failover can reach production size within the RTO.
X: B=Faster detection on the primary: detection was not the problem; the delay came from not obtaining capacity after detection.
C=Larger boot disk: disk size does not create unavailable machine types in the zone, so the scale-up would still fail.
D=Second image bucket in the primary region: it sits in the region that is assumed to be lost and does nothing about compute capacity in the recovery region.
T: A DR plan must secure compute capacity in the recovery region, for example with reservations, and be proven in rehearsals against the RTO.

@ GCP-PCA D1 T1.2 applied definition
S: A broadcaster stores newly produced footage in a Cloud Storage dual-region bucket for a production tool that must continue after a regional outage. The business sets a recovery point objective of 15 minutes for newly written objects across both regions, and default replication targets are too slow for that. What should the architect enable?
A: Object Versioning on the bucket, keeping older versions of overwritten or deleted objects in the bucket
B: The Archive storage class, which stores each object in colder storage that costs less for long-term retention
C: A retention policy on the bucket, which prevents any object from being deleted or replaced before a set age
D: Turbo replication on the dual-region bucket, designed to copy new objects to both regions within 15 minutes
K: D
G: ## Replication targets for dual-region buckets
Cloud Storage writes an object to one region across zones and then replicates it asynchronously to the other region of a dual-region bucket.
- **Default replication** targets 99.9% of newly written objects within one hour and 100% within 12 hours (most finish in minutes).
- **Turbo replication** is an optional, premium feature of dual-region buckets, designed to replicate 100% of newly written objects between the two regions within a recovery point objective of 15 minutes.
## Other features solve other problems
Versioning and retention protect against deletion or overwrite, and storage classes affect cost and access pattern. None of them changes how fast data reaches the second region. Note that replication is not a full BCDR plan on its own.
W: Turbo replication: it is designed for a 15-minute RPO across the two regions of a dual-region bucket, which is the stated requirement for newly written footage.
X: A=Object Versioning: it protects older object generations against overwrites and deletes, and it does not speed up copying to the second region.
B=Archive storage class: this class lowers storage cost for rarely read data and has no effect on replication time, and it would make a production tool's reads slower and costlier.
C=Retention policy: it blocks deletion for a period, which supports compliance, not a replication time objective.
T: To tighten the RPO of a dual-region Cloud Storage bucket, enable turbo replication; versioning, retention and classes address other needs.

@ GCP-PCA D1 T1.2 applied use-case
S: An e-commerce company has a user-facing Cloud Run service that runs a heavy framework. After periods without traffic, the first visitors wait several seconds for a response while a new instance starts, which violates the latency target for the first request. Costs for always running the service on VMs are not acceptable. Which change best fits the performance and cost goals?
A: Set a minimum number of instances so a warm one is always ready, with autoscaling for bursts above it
B: Rebuild the service on Compute Engine VMs with fixed capacity, because serverless platforms cannot meet a latency target
C: Increase the request timeout of the service so the first visitor can wait for the instance to start
D: Disable autoscaling and set the maximum number of instances to one, so no new instances are started during traffic bursts
K: A
G: ## Cold starts and warm capacity
Serverless platforms such as Cloud Run scale to zero when idle. The next request must wait for a new instance to start, which is a **cold start**. For latency-sensitive services the performance pillar's answer is to keep a small amount of warm capacity.
- **Minimum instances** keeps a set number of instances ready, trading a small continuous cost for fast first responses; scaling above the minimum still follows demand.
- Startup time can also be reduced by lighter images and faster initialization, but that is a code change.
## Trade-off
You pay for the idle warm instance only, not for peak capacity all day, which is much cheaper than a fixed fleet sized for bursts.
W: Minimum instances: one or more warm instances answer the first requests immediately, and autoscaling still adds instances for bursts, so cost stays far below a fixed VM fleet.
X: B=Fixed VMs: Cloud Run can meet latency goals when warm capacity is configured; moving to VMs brings back the always-on cost and the management work the company wants to avoid.
C=Longer timeout: the first visitor still waits the same startup time, and a longer timeout only allows the wait to continue without improving the latency target.
D=Maximum of one instance: it caps throughput so that bursts queue or fail, and it does not remove the cold start after idle periods.
T: For cold-start latency on serverless services, keep minimum instances warm; keep autoscaling for bursts.

@ GCP-PCA D1 T1.4 applied use-case
S: EHR Healthcare must leave its colocation facility because the lease ends in about ten months. It has a few hundred servers, documentation of its applications is thin, and several are tied to on-premises insurer integrations. What is the best first step in the migration plan?
A: Start moving servers in alphabetical order so the project shows progress, and rewrite the documentation in parallel
B: Use Migration Center discovery and assessment to inventory servers, map dependencies and decide which workloads must move together
C: Re-architect every application into microservices before moving anything, so the whole estate is cloud-native on arrival at Google Cloud
D: Renew the lease for three more years, since applications with unknown dependencies cannot be moved safely at all
K: B
G: ## Assess before you move
A migration plan starts from facts: what exists, how it is used, and what depends on what. **Migration Center** supports this with:
- **Discovery**: automatic or uploaded inventory of servers and databases.
- **Assessment**: dependency mapping at the application and network level (which components must move together), technical fit assessment with suggested target products, and total cost of ownership reports based on your migration preferences.
- **Planning**: best practices and prescriptive recommendations on what to migrate and how; the dependency results show which assets must be moved together, which is the basis for grouping them into waves.
## Using it against a deadline
A fixed lease end makes ordering decisive. Moving things without dependency information risks breaking integrations (the insurer links must keep working), while a full redesign of every application cannot fit in ten months. Most estates rehost first and modernize later.
W: Discovery and assessment with Migration Center: it gives the inventory and dependency map that the thin documentation lacks, so the move can be planned in waves that keep tightly coupled systems and insurer integrations together before the lease ends.
X: A=Alphabetical order: it ignores dependencies and risk, so systems could be split from the ones they call, causing outages and rework.

@ GCP-PCA D1 T1.4 applied definition
S: Which TWO situations point to a rehost (lift and shift) as the most suitable migration approach for a workload? (Select TWO)
A: The workload is packaged vendor software whose code cannot be changed and which cannot be retired yet
B: The business wants to remove technical debt and move a monolith to independent services that scale separately
C: A hard exit date is close and the workload can run in the target environment as it is, with minimal changes

G: ## Migration types
The migration guide describes these approaches, ordered from least to most change:
- **Rehost (lift and shift)**: move with minor or no modifications. It is quickest and uses existing skills, but the workload does not use cloud features such as horizontal scaling and managed services.
- **Replatform (lift and optimize)**: move and adopt some cloud capabilities, for example containers or a managed database.

@ GCP-PCA D1 T1.4 applied use-case
S: A retailer plans to connect its data center, which uses 10.0.0.0/8 addresses in many sites, to a new Google Cloud environment with Cloud VPN and Interconnect. Network planning is still open. Before creating subnets, which action avoids a routing problem that is hard to fix later?

B: Define an IP plan giving Google Cloud subnets ranges that do not overlap with on-premises or other connected networks

D=Public addresses for all VMs: this exposes the migrated systems to the internet and breaks the private-connectivity goal without removing the need to coordinate private ranges.
T: Plan non-overlapping IP ranges with the on-premises network before building subnets or connectivity; overlaps are costly to fix later.

@ GCP-PCA D1 T1.4 advanced troubleshooting
S: KnightMotives moved the web front end of its build-to-order system to Google Cloud while the mainframe ERP stayed on premises. Each page now makes dozens of sequential calls to the ERP over the hybrid link, and dealers report very slow pages even though the link has plenty of bandwidth. What should the migration plan have used to prevent this?
A: Dependency mapping, to move chatty components in one wave or add an API layer or cache that cuts cross-link calls
B: A larger Interconnect capacity, because slow pages in hybrid designs are always caused by too little bandwidth
C: A plan that moves each tier in its own wave, starting with whichever tier is the easiest for the team
D: A switch of the front end to Spot VMs, so that its compute is less expensive while it waits for the ERP responses
K: A
G: ## Latency, not bandwidth, between dependent components
Bandwidth is how much data can travel at once; latency is how long each round trip takes. An application that makes many sequential calls pays the round-trip time for every call. Latency across a hybrid link is far higher than inside a data center, so a chatty design that was fine on one network becomes slow when split across two.
## What dependency analysis gives
Network and application dependency mapping (as in Migration Center assessments) shows call patterns and which components must move together. Options to plan for:
- Move tightly coupled components in the same wave, or keep them together on the same side.
- Reduce chatter with an API layer that batches calls, asynchronous messaging, or caching of reference data.
- Test latency-sensitive paths before cutover.
## Applying it
The link was not saturated; adding capacity would not shorten round trips.
W: Dependency mapping and wave design: it exposes the chatty front end and ERP calls in advance, so the plan can move them together or add an API layer or cache that cuts the number of calls across the link.
X: B=Larger Interconnect: the problem is round-trip latency from sequential calls, not capacity, and the link already has spare bandwidth.
C=Separate waves by easiest tier: it ignores coupling and creates the split-tier situation that caused the problem.
D=Spot VMs for the front end: they lower compute price but do not shorten round trips to the ERP, and they can be reclaimed at any time.
T: Map dependencies to keep chatty components together or reduce cross-link calls; hybrid slowness often comes from latency and call patterns, not bandwidth.
