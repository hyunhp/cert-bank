@ GCP-PCA D2 T2.1 applied troubleshooting
S: A company links its on-premises network to one VPC network through HA VPN, with a Cloud Router in us-central1. The VPC network has subnets in us-central1 and europe-west1, and the VPC network uses its default dynamic routing mode. On-premises routers learn the us-central1 subnets only, so servers cannot reach the europe-west1 VMs over the tunnels. What is the correct fix?
A: Add an ingress firewall rule that allows the on-premises ranges to reach the europe-west1 subnets, since the firewall is dropping the traffic
B: Change the dynamic routing mode of the VPC network to global, so the Cloud Router advertises and learns routes for all regions
C: Create a second pair of HA VPN tunnels in europe-west1 that use static routes, because BGP can only cover one region per network
D: Increase the number of tunnels in us-central1 to four, so that the extra capacity lets the Cloud Router announce more subnets
K: B
G: ## Dynamic routing mode
Cloud Router exchanges routes with on-premises (or other cloud) routers over BGP. What it advertises and which routes it installs is controlled by the **dynamic routing mode** of the VPC network.
- **Regional** (the default) dynamic routing: a Cloud Router advertises only the subnets in its own region and installs learned routes only for resources in its own region.
- **Global** dynamic routing: a Cloud Router advertises the subnets of all regions in the VPC network, and learned on-premises routes apply to all regions.
The mode is a property of the VPC network, not of one router or tunnel. A hybrid design that spans regions should decide on the mode deliberately, because it also determines which regions can use a learned route. Keep in mind that firewalls act only after a route exists: a missing route looks like a connectivity failure but no firewall change will fix it.
## Example
A VPC network with `us-central1` and `europe-west1` subnets and one Cloud Router in `us-central1`: with regional mode, on-premises learns only the `us-central1` ranges; with global mode it learns both.
W: Global dynamic routing: the symptom (only the router's own region is advertised) is exactly how regional mode behaves, and switching the VPC network to global mode makes the same Cloud Router advertise every region's subnets without new tunnels.
X: A=Firewall rule: firewall rules filter packets that already have a route. On-premises routers never learned the europe-west1 prefixes, so the traffic is not even sent into the tunnels.
C=Static-route tunnels in europe-west1: BGP is not limited to one region; the limit comes from the routing mode. A second set of tunnels with static routes adds cost and loses dynamic route exchange without fixing the cause.
D=More tunnels in us-central1: extra tunnels add throughput and redundancy, not extra advertised prefixes. The prefixes announced depend on the routing mode.
T: When on-premises sees only one region's subnets, check the VPC network's dynamic routing mode: global lets one Cloud Router serve all regions.

@ GCP-PCA D2 T2.1 advanced use-case
S: A security team must block exploit attempts and command-and-control traffic between application VMs that sit in the same VPC network, inspecting the packets inline rather than only raising alerts, and it wants a Google-managed service instead of running virtual appliances. Which configuration achieves this?
A: Enable Cloud IDS with an IDS endpoint and packet mirroring policy, so that every detected threat is blocked at the VM before it spreads
B: Add VPC firewall deny rules for the IP ranges of known attackers, and refresh the list manually each week from threat reports
C: Create zonal Cloud NGFW firewall endpoints, a threat-prevention security profile group, and firewall policy rules that apply that group
D: Place Cloud Armor with a managed rule set in front of the workloads so that east-west traffic is filtered by web rules
K: C
G: ## Detection versus prevention in the network
Google Cloud offers two intrusion services with different positions in the traffic path.
- **Cloud IDS** mirrors traffic with Packet Mirroring to Google-managed inspection VMs. It detects and alerts, but it does not take action to prevent an attack.
- **Cloud NGFW intrusion prevention service** (Cloud NGFW Enterprise) intercepts matching traffic and sends it to a Google-managed, zonal **firewall endpoint** that scans it against threat signatures. If a threat is found, the action set in the security profile (for example alert or deny) is applied to that packet.
## Building blocks
- A **firewall endpoint** per zone where workloads run, associated with the VPC network.
- A **security profile** of type `threat-prevention` collected in a **security profile group**.
- **Firewall policy rules** whose action references the security profile group, so only matching traffic is intercepted for Layer 7 inspection.
Because it is a firewall policy rule, it covers east-west traffic inside the network, unlike a control that only sits on an external load balancer.
W: Cloud NGFW with endpoints, a threat-prevention profile group and policy rules: traffic that matches the rule is intercepted and inspected inline by a managed endpoint, and the profile action can drop it, which meets both the inline and the no-appliance requirement.
X: A=Cloud IDS: it inspects mirrored copies out of band and only alerts. It helps detection, but it does not block anything, so it fails the prevention requirement.
B=Manual deny lists: IP-based rules cannot match exploit signatures or command-and-control behavior, and a weekly refresh is always behind, while attackers also use compromised internal hosts.
D=Cloud Armor: it protects traffic that enters through supported load balancers and does not see VM-to-VM traffic inside the VPC network, so it cannot cover east-west inspection.
T: Block threats inline in the VPC with Cloud NGFW Enterprise (firewall endpoints plus security profile groups); Cloud IDS only detects.

@ GCP-PCA D2 T2.1 advanced comparison
S: A platform team lets many developers edit VM settings in shared development projects. Firewall rules currently permit database access only from VMs that carry the network tag "web". An audit finds that any developer who can edit an instance can add that tag and reach the database. The team wants rules keyed to a workload label that only a security group can assign. What should it change?
A: Keep network tags but add a naming convention for tags, and ask developers to document every tag they apply in the ticket system
B: Replace the tag rule with one based on the web subnet range, since instance editors cannot change a subnet range assignment
C: Move the database VMs to a separate zone, because firewall rules are evaluated per zone and developers cannot cross it
D: Use secure tags in network firewall policy rules as sources and targets, and grant the permission to bind them only to the security group
K: D
G: ## Network tags versus secure tags
- **Network tags** are strings on a VM. Anyone who can edit the instance metadata can add or remove them, so a firewall rule keyed to a tag is only as strong as the edit permission on every VM.
- **Secure tags** are Resource Manager tags governed by IAM. Creating the tag and binding it to a resource need explicit permissions, so a security team can keep that power to itself. Cloud NGFW network firewall policies use secure tags as sources and targets.
Using identity-based match criteria means rules follow workloads when IP addresses change and cannot be changed by simply editing a VM.
## Why not just use ranges
IP ranges are a coarse control: any VM placed in the subnet gets the same access, and ranges must be updated when workloads move.
W: Secure tags with restricted binding permission: the rule matches a workload attribute that only the security group can bind, which closes the gap that network tags leave open.
X: A=Tag naming conventions: documentation does not stop a developer with edit rights from adding a tag, so the control remains advisory.
B=Subnet range rule: it grants access to every VM in that range regardless of its role, and it is not a statement about who can alter a workload's identity. It also does not follow workloads that move.
C=Separate zone: firewall rules are VPC-wide and not scoped by zone, so zone placement does not limit who can reach the database.
T: Use IAM-governed secure tags in firewall policies when the rule must not be bypassable by anyone with VM edit rights.

@ GCP-PCA D2 T2.1 applied comparison
S: An online game studio runs UDP game servers on Compute Engine VMs in one region. The servers must see each player's original source IP address for anti-cheat checks, the load balancer should not terminate the player traffic, and the studio wants high throughput without a proxy layer. Which load balancer configuration fits?
A: A regional external passthrough Network Load Balancer with a backend service and a UDP forwarding rule
B: A global external Application Load Balancer with a URL map, to terminate connections near players
C: A global external proxy Network Load Balancer, because TCP proxying lets the servers choose the source address they see
D: An internal passthrough Network Load Balancer with a regional forwarding rule, so that players reach it through a private address
K: A
G: ## Passthrough versus proxy load balancers
- **Passthrough Network Load Balancers** do not terminate connections. Packets reach the backend VMs with the original client source IP, and the backend answers the client directly (direct server return). They handle TCP, UDP and other IP protocols, and external ones are regional.
- **Proxy load balancers** (Application Load Balancers and proxy Network Load Balancers) terminate the client connection and open a new one to the backend. The backend sees the proxy's address unless a header (for HTTP) or PROXY protocol carries the client address, and they are limited to the protocols they support.
## Selection logic
Start from the protocol and the requirements: UDP plus preserving client IP plus no termination points to a regional external passthrough Network Load Balancer. Choose a global Application Load Balancer for HTTP(S) needing global anycast, URL routing, Cloud CDN or Cloud Armor.
W: Regional external passthrough Network Load Balancer: it forwards UDP packets without terminating them, the servers see the real source IP, and no proxy sits in the data path.
X: B=Global external Application Load Balancer: it only carries HTTP(S)-family traffic, and it terminates the client connection, so UDP game traffic and original source addresses do not fit.
C=Global external proxy Network Load Balancer: it proxies TCP and terminates the connection, which is not UDP and not a way to expose the source address natively.
D=Internal passthrough Network Load Balancer: it is only reachable from inside a VPC network or connected networks, so internet players could not use it.
T: UDP with preserved client IP and no termination: regional external passthrough Network Load Balancer; HTTP(S) needs an Application Load Balancer.

@ GCP-PCA D2 T2.1 advanced tradeoff
S: EHR Healthcare runs an internal eligibility API used by application tiers in two regions, and the service must stay available if a whole region fails. The API must not be reachable from the internet, and clients should use a single DNS name no matter where they run, without manual switching. Which load balancer fits?
A: A regional internal Application Load Balancer with global access enabled, with all backends placed in the closest region
B: A cross-region internal Application Load Balancer with backend instance groups in both regions behind one backend service
C: A regional external Application Load Balancer restricted by firewall rules to the two regions' NAT addresses
D: An internal passthrough Network Load Balancer in each region, with clients switching to the other address by hand during an outage
K: B
G: ## Internal load balancing across regions
- A **regional internal Application Load Balancer** has backends in a single region. Enabling **global access** lets clients from other regions connect to it, but if that region fails the backends go with it.
- A **cross-region internal Application Load Balancer** is a multi-region, Envoy-based managed load balancer. Its backend service can hold backends in several regions, traffic goes to the backend closest to the client's forwarding rule, and if one region's backends are down, traffic fails over to another region.
- **Internal passthrough Network Load Balancers** are regional: backends and failover stay in one region, so a regional outage needs a manual switch to another load balancer's address.
## Fit to the EHR requirement
The case calls for at least 99.9% availability for customer-facing systems and had past outages from misconfiguration and spikes. Each region's VIP is allocated from a subnet in that region, so VIPs from several regions share the same global backend service and DNS routing policies steer clients to a responding VIP. Automatic cross-region failover removes a manual step in an incident.
W: Cross-region internal Application Load Balancer: one backend service with backends in both regions, automatic failover to healthy backends, VIPs from each region published under one DNS name with a DNS routing policy, and no internet exposure.
X: A=Regional internal ALB with global access: global access only changes who can connect. All backends sit in one region, so a regional outage still takes the API down.
C=Regional external ALB: it has a public address, which violates the not reachable from the internet requirement; firewall filtering does not make the front end internal.
D=Per-region passthrough balancers: each is regional with no cross-region failover, so clients must switch addresses by hand, which slows recovery and depends on a person during the incident.
T: Internal service that must survive a regional failure without manual switching: cross-region internal Application Load Balancer.

@ GCP-PCA D2 T2.1 applied use-case
S: A company will connect a new VPC network to on-premises networks and to a partner network through VPC Network Peering. It wants control over which regions receive subnets and which address ranges are used. Which TWO reasons support creating the VPC network in custom mode instead of auto mode? (Select TWO)
A: Custom mode lets the team choose non-overlapping ranges, which avoids conflicts with on-premises and peered networks
B: Custom mode is the only mode that supports Cloud Router, so hybrid connectivity cannot be configured on auto mode
C: Custom mode is the only mode that can host Private Google Access for subnets in several regions
D: Custom mode creates subnets only in the regions the team chooses, so unused regions get no subnet and no address space
E: Custom mode removes the implied deny-ingress rule, so peered networks can reach every VM
K: A,D
G: ## Auto mode versus custom mode
- **Auto mode** VPC networks automatically create one subnet in every region from a predefined block, and add subnets for new regions. The default network is auto mode.
- **Custom mode** VPC networks start with no subnets; you create subnets in chosen regions with ranges you specify.
Auto mode is convenient for experiments. For production the ranges matter: Cloud VPN, Interconnect and VPC Network Peering all need non-overlapping subnet ranges between connected networks, and auto mode's predefined block can collide with on-premises or other VPC networks. An auto mode network can be converted to custom mode, but never back.
## Common misconceptions
Hybrid connectivity, Private Google Access and firewall behavior are available in both modes.
W: A=Choose ranges: custom mode lets you plan non-overlapping addressing across on-premises, peering and other VPC networks, which hybrid and peering designs require.
D=Chosen regions only: you create subnets only where workloads run, which keeps address space tidy and limits where resources can be placed.
X: B=Cloud Router claim: Cloud Router and its BGP sessions work with auto mode networks as well; the mode is not a hybrid prerequisite.
C=Private Google Access claim: Private Google Access is a per-subnet setting available in both modes.
E=Implied rules claim: the implied deny-ingress rule exists in both modes. Access between peered networks is granted by firewall rules, not by the network mode.
T: Production, hybrid and peered networks need planned, non-overlapping ranges, so use custom mode VPC networks.

@ GCP-PCA D2 T2.1 applied use-case
S: A data-science team runs a large analytics workload on another cloud provider and must exchange tens of gigabits of data with Google Cloud privately. The team does not want to deploy its own network equipment in a colocation facility, and it wants a physical link between the two clouds that Google provisions. Which connectivity should it choose?
A: HA VPN tunnels across the public internet between a Google Cloud Cloud Router and a virtual gateway of the other cloud
B: Direct Peering at a Google edge location, which allows the two clouds' traffic to be exchanged without using the internet
C: Cross-Cloud Interconnect, where Google provisions a dedicated link to the other provider's network
D: Partner Interconnect through a carrier, where the team orders the circuits and the other cloud's connection separately
K: C
G: ## Multicloud connectivity options
- **HA VPN** is quick to build and encrypted but crosses the public internet, with per-tunnel bandwidth limits and variable latency.
- **Cross-Cloud Interconnect** is a dedicated physical connection between the Google network and the network of a supported cloud provider. Google provisions and supports the connection up to the point where it reaches the other provider's network, so the customer does not install equipment in a colocation facility. The VPC network is peered with the network hosted by the other provider.
- **Dedicated Interconnect** or **Partner Interconnect** can also reach another cloud, but the customer then orders and operates the routing and cross-connects at a facility or provider.
## Caveat
Google does not guarantee the other provider's uptime, so a support case must also be opened with that provider.
W: Cross-Cloud Interconnect: Google-provisioned dedicated capacity to the other cloud, private traffic, and no customer-owned equipment at a colocation facility.
X: A=HA VPN: traffic crosses the internet and per-tunnel throughput is limited, which does not suit tens of gigabits of sustained private exchange.
B=Direct Peering: it exchanges traffic with Google's public edge for Google services and is not a private path between the VPC network and another cloud.
D=Partner Interconnect: it relies on carrier circuits the team arranges, adding operational work that the requirement for a Google-provisioned link is meant to avoid.
T: Private, high-bandwidth VPC-to-other-cloud links without your own colocation gear point to Cross-Cloud Interconnect.

@ GCP-PCA D2 T2.1 advanced use-case
S: Cymbal Retail's catalog service runs on a private GKE cluster whose nodes have no external IP addresses. Suppliers will let the service call their APIs only from a fixed set of public IP addresses that Cymbal must give them in advance. Which configuration meets this?
A: A Cloud NAT gateway in the cluster's region that uses reserved static external IP addresses for the node and Pod ranges
B: An ephemeral external IP address on each node, with the supplier allowlist updated whenever autoscaling adds a node
C: Private Google Access on the subnet, so that all outbound connections leave through Google's own address blocks
D: Cloud Router custom route advertisements that announce the supplier IP ranges into the VPC network
K: A
G: ## Controlled outbound internet access
Private VMs and nodes need a way to reach the internet without exposing inbound access.
- **Cloud NAT** (public NAT) translates outbound traffic to IP addresses held by the NAT gateway. It is software-defined: no proxy VMs, and it works on a gateway attached to a Cloud Router in one region for chosen subnet ranges.
- With **automatic** address allocation, Cloud NAT adds addresses as needed, so the set can change. With **manual** allocation you reserve static external addresses, which gives suppliers a stable set to allowlist.
- For GKE private clusters, include the Pod secondary range if Pods must reach the internet.
## What does not help
**Private Google Access** only reaches Google APIs and services, not third-party endpoints, and route advertisements affect routing, not the source address seen by suppliers.
W: Cloud NAT with reserved static addresses: outbound supplier calls come from a small stable address set, nodes stay private, and scaling does not change what suppliers see.
X: B=Ephemeral node IPs: addresses change with node replacement and autoscaling, the nodes would become directly internet-addressable, and the allowlist would need constant edits.
C=Private Google Access: it provides access to Google APIs without external IPs, not to supplier endpoints on the internet.
D=Custom advertisements: they influence which prefixes a Cloud Router announces to peers and do not change the source address of outbound internet traffic.
T: Fixed, allowlistable egress for private workloads means Cloud NAT with manually allocated static IP addresses.

@ GCP-PCA D2 T2.1 applied use-case
S: A company runs Active Directory DNS on premises for corp.example and uses Cloud DNS for the private zone gcp.corp.example in a VPC network connected by Cloud Interconnect. On-premises servers must resolve names in gcp.corp.example, and Compute Engine VMs must resolve names in corp.example. What should be configured?
A: A public Cloud DNS zone for both names, with on-premises servers and VMs resolving them over the internet
B: A secondary zone on the on-premises DNS servers, with the VMs configured manually to use the Active Directory servers' addresses
C: A hosts file distributed to every VM and server, refreshed from a script when names change
D: An inbound server policy for on-premises queries, and a Cloud DNS forwarding zone for corp.example that targets the on-premises servers
K: D
G: ## Hybrid DNS in Cloud DNS
Name resolution must work in both directions, and both directions are configured with Cloud DNS features on the VPC network.
- **Inbound server policy**: creates inbound entry points, which are internal IP addresses in the VPC network. On-premises resolvers forward queries for the cloud zone to those addresses, so on-premises systems can resolve private Cloud DNS records.
- **Forwarding zone** (outbound forwarding): Cloud DNS forwards queries for a given domain to target name servers, such as the on-premises DNS servers, so VMs resolve on-premises names with no per-VM changes.
Routes and firewall rules must allow the DNS traffic between the networks across the hybrid link.
## Why a public zone is wrong
Internal names should not be published publicly, and public resolution would not reach private addresses.
W: Inbound server policy plus a forwarding zone: each side forwards the other's domain to the right resolver over the private link, with no changes on individual VMs.
X: A=Public zone: it would publish internal names and addresses on the internet, and the private records in the Cloud DNS private zone would not be used.
B=Secondary zone and manual VM settings: pointing VMs at on-premises servers manually creates per-VM configuration and bypasses Cloud DNS, so the private zone is no longer resolved from the VMs.
C=Hosts files: the record sets drift out of date, and this does not scale or support dynamic names.
T: Use an inbound server policy for on-premises-to-cloud and a forwarding zone for cloud-to-on-premises resolution.

@ GCP-PCA D2 T2.1 advanced tradeoff
S: KnightMotives connects a plant to Google Cloud with Dedicated Interconnect for real-time analytics and keeps an HA VPN as a backup. Both paths advertise the same on-premises prefixes through Cloud Router. The network team sees traffic spread across both, and VPN latency is hurting real-time workloads. How should it make the Interconnect the preferred path and the VPN a standby?
A: Give both BGP sessions the same advertised route priority so that the Cloud Router balances traffic equally between them
B: Give the Interconnect session a lower priority value than the VPN session, so the VPN carries traffic only if Interconnect routes disappear
C: Delete the VPN tunnels and rely on the two Interconnect VLAN attachments only, to keep the routing table simple
D: Give the Interconnect session a higher priority number than the VPN session, since larger values mean higher preference in Cloud Router
K: B
G: ## Steering traffic between hybrid paths
Cloud Router learns routes over BGP and installs them in the VPC network. When multiple paths exist for the same prefix, route priority decides which is used.
- Cloud Router sessions have a **base route priority** (the MED sent for advertised routes); for learned routes it is the priority of the installed dynamic route. **Lower values are preferred.**
- Equal priorities on equal-prefix routes allow ECMP-style distribution across paths.
## Design rule
For an active/standby design, give the primary path the lower number and the backup the higher number. The VPN then takes traffic only when the Interconnect routes are withdrawn. Never remove the backup: it protects from the failure of the primary, and Google's redundancy guidance for critical workloads keeps independent paths.
W: Lower priority value on the Interconnect: the Interconnect routes win while they exist, and the VPN routes become active only when they fail, which gives low-latency primary and resilient standby.
X: A=Equal priority: this lets the VPN carry a share of the traffic, which is the symptom the team is complaining about.
C=Deleting the VPN: removing the backup reduces resilience, so one fault in the Interconnect topology could cut off the plant.
D=Higher number on the Interconnect: lower values win, so this would prefer the VPN, which makes the latency problem worse.
T: In Cloud Router, the lower priority value (MED) wins; give the primary path the lower value and keep the backup at a higher value.

@ GCP-PCA D2 T2.1 applied use-case
S: Altostrat Media is modernizing in steps. Its on-premises ingestion API stays in the data center for now, while new services run in GKE. The team wants one public hostname and one global external Application Load Balancer, with the ingest path sent to the on-premises servers over the existing Cloud Interconnect. What backend configuration does this require?
A: A serverless network endpoint group pointing to the on-premises servers, because it can reference any reachable endpoint
B: An internet network endpoint group with the data center's public hostname, so that requests travel across the public internet
C: A hybrid connectivity network endpoint group holding the on-premises IP:port endpoints, used as a backend and routed by the URL map
D: A managed instance group whose template defines on-premises servers, kept in sync by the autoscaler
K: C
G: ## Hybrid load balancing
Cloud Load Balancing treats on-premises and other-cloud services like any other backend, but it needs an endpoint definition that points outside Google Cloud.
- A **hybrid connectivity NEG** holds endpoints as valid `IP:port` combinations that the load balancer can reach over Cloud VPN, Cloud Interconnect or router appliance VMs. It works with global external Application Load Balancers among others.
- An **internet NEG** instead references a public FQDN or IP and sends traffic over the internet.
- A **serverless NEG** points to Cloud Run, Cloud Run functions or App Engine.
## Why it fits modernization
A URL map can route `/ingest` to the hybrid NEG while other paths go to GKE backends, so users see one hostname while services move over time. Health checks must be able to reach the on-premises endpoints, so the firewall there must allow Google's health check probes.
W: Hybrid connectivity NEG: private on-premises IP:port endpoints become a normal backend, the URL map splits paths between GKE and the data center, and traffic stays on the Interconnect.
X: A=Serverless NEG: it targets Cloud Run, Cloud Run functions or App Engine services, not arbitrary on-premises servers.
B=Internet NEG: it sends requests across the public internet to a public name, which ignores the requirement to use the Interconnect.
D=Managed instance group: instance groups contain Compute Engine VMs, so on-premises servers cannot be members.
T: To put on-premises backends behind a Google Cloud load balancer over Interconnect or VPN, use a hybrid connectivity NEG.

@ GCP-PCA D2 T2.1 advanced troubleshooting
S: A security architect needs to detect lateral movement between VMs in the same subnets, including intra-subnet traffic. Production traffic must not be placed in the data path of the inspection engine, and the team wants to act on the findings later. Which TWO elements belong in the design? (Select TWO)
A: A Cloud IDS endpoint in each region that holds monitored VMs, with packet mirroring policies that select the VMs or subnets to inspect
B: Cloud IDS findings used to drive follow-up action through Cloud NGFW, because Cloud IDS alerts but does not block
C: A policy that makes Cloud IDS drop malicious packets inline, so that it stops threats without any other control
D: A single IDS endpoint in one region that inspects mirrored traffic for every region by default
E: A Cloud Armor policy on the VPC network, because Cloud Armor inspects subnet traffic between VMs
K: A,B
G: ## How Cloud IDS works
Cloud IDS creates a Google-managed peered network with inspection VMs. A zonal **IDS endpoint** receives mirrored traffic (from any zone in its region), and **Packet Mirroring policies** attached to it choose which VMs, subnets or tags are copied, optionally filtered by protocol, address range or direction. Inspection uses Palo Alto Networks threat technologies.
- Because it works on copies, it is out of band: no latency or failure risk for production traffic.
- It sees north-south and east-west traffic, including intra-subnet traffic that routing controls never touch.
- It detects and alerts but takes no action. Prevention is done with a control such as Cloud NGFW.
## Scale
Plan an endpoint per region to monitor, and more than one where throughput is high, since each has a finite inspection capacity.
W: A=Endpoint with mirroring policies: mirroring copies the chosen traffic, including intra-subnet flows, to a regional endpoint for inspection without being inline.
B=Follow-up with Cloud NGFW: Cloud IDS only alerts, so blocking or other action comes from a separate control such as Cloud NGFW policies.
X: C=Inline dropping by Cloud IDS: it inspects mirrored copies, so it cannot drop live packets.
D=One endpoint for all regions: an endpoint inspects traffic from zones in its own region, and you create endpoints for each region you want to monitor.
E=Cloud Armor: it protects traffic at supported load balancers and does not see VM-to-VM traffic inside subnets.
