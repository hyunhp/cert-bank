@ GCP-PCA D2 T2.2 advanced use-case
S: EHR Healthcare keeps scanned claim attachments for many medical-office tenants in one Cloud Storage bucket, under one prefix per tenant. Each tenant's service account must read and write only its own prefix. The platform team wants to manage this without touching individual objects, and wants no legacy object ACL to be able to grant surprise access. Which configuration fits?
A: Keep fine-grained access on the bucket and set an object ACL on every attachment as the tenant's upload job writes it
B: Create one bucket per tenant and grant each tenant's service account Storage Admin on the project so that it can manage its own bucket
C: Grant all tenant service accounts Storage Object Viewer on the project and filter by tenant prefix in the application code
D: Turn on uniform bucket-level access, create a managed folder for each tenant prefix and grant that tenant's service account Storage Object User on its folder
K: D
G: ## Two access systems in Cloud Storage
Cloud Storage has two parallel ways to grant access: IAM and Access Control Lists (ACLs). A request succeeds if either system allows it, so a stray ACL can open data that IAM never intended.
- **Uniform bucket-level access** disables ACLs on the bucket. Only IAM decides access, which removes the "surprise grant" path and makes audits simple.
- **Managed folders** are resources inside a bucket on which you can set an IAM policy. The policy applies to every object whose name starts with the folder path, so one grant covers a whole tenant prefix, including objects written later. They can only be created in buckets that use uniform bucket-level access.
## Choosing the granularity
A bucket per tenant gives strong separation but multiplies buckets to administer. Project-level grants are far too broad for prefix-level separation. Managed folders sit in between: one bucket, one IAM policy per prefix, no per-object work.
W: Uniform bucket-level access with a managed folder per tenant: ACLs are gone, each tenant's service account gets Storage Object User only on its own prefix, and new objects under the prefix are covered automatically with no per-object administration.
X: A=Object ACLs: this is per-object administration, which the team wants to avoid, and ACLs are exactly the second access system that can grant surprise access.
B=Bucket per tenant with project Storage Admin: a project-level admin role lets every tenant's account manage every bucket in the project and is far broader than reading and writing one prefix.
C=Project-level Storage Object Viewer plus code filtering: it grants read access to all tenant data and gives no write access, and enforcement would depend on application code instead of IAM.
T: For prefix-level isolation in one bucket, enable uniform bucket-level access and grant IAM on managed folders.

@ GCP-PCA D2 T2.2 advanced troubleshooting
S: Cymbal Retail's suppliers overwrite their catalog feed file in Cloud Storage several times a day. Object Versioning is enabled so that a bad feed can be rolled back, but noncurrent versions have piled up and storage cost keeps growing. Rollback is only ever needed within 30 days, and the current (live) feed objects must never be removed automatically. Which change fits?
A: Add a lifecycle rule with the Delete action and a condition on days since the version became noncurrent set to 30
B: Add a lifecycle rule with the Delete action and an age condition of 30 days, applied to all objects in the bucket
C: Add a lifecycle rule that moves every noncurrent version to Archive storage so that the stored bytes become cheaper
D: Disable Object Versioning on the bucket so that overwritten feeds no longer create noncurrent versions
K: A
G: ## Versioning and lifecycle together
With Object Versioning on, replacing or deleting a live object keeps the old data as a **noncurrent version**, identified by its generation number. Noncurrent versions are billed like any other data until removed.
Object Lifecycle Management evaluates conditions on objects and then applies an action (`Delete` or `SetStorageClass`). Conditions that fit versioned buckets are:
- `daysSinceNoncurrentTime`: days since the version stopped being live.
- `numNewerVersions`: how many newer versions exist.
- `isLive`: whether the object is the live version.
Plain `age` counts from object creation and is not reset when an object becomes noncurrent, so it targets live objects too. When a lifecycle rule deletes a live object in a versioned bucket, the object only becomes noncurrent, and deleting a noncurrent version removes that version.
W: A Delete rule keyed on days since noncurrent: it bounds the rollback window to 30 days, removes only versions that are no longer live and leaves current feed files untouched.
X: B=Age-based delete for all objects: age is measured from creation, so a feed file that has not been replaced for 30 days would be targeted as a live object, which breaks the rule that live feeds are never removed automatically.
C=Move noncurrent versions to Archive: the versions would still accumulate forever, and Archive has a minimum storage duration and retrieval charges, so the growth is not bounded and rollback becomes more costly.
D=Disable versioning: it removes the rollback ability the business wants, instead of bounding the history to the 30 days that are actually needed.
T: Bound noncurrent history with a lifecycle Delete rule on noncurrent age or newer-version count, never with a plain age rule.

@ GCP-PCA D2 T2.2 advanced tradeoff
S: A health insurer must keep adjudicated claim records unaltered for seven years. Auditors require evidence that no one, including project owners, can delete or replace a record before it is seven years old or shorten that period. Which design satisfies the requirement?
A: A bucket retention policy of seven years that is then locked with Bucket Lock, tested first on a non-production bucket
B: A bucket with soft delete retention raised to the maximum, so that any deleted claim record can be restored
C: Object Versioning on the bucket plus an IAM deny policy so that no principal can delete noncurrent versions
D: A lifecycle rule that never deletes claim records, combined with a restricted set of administrators
K: A
G: ## Retention is different from recovery
- **Soft delete** keeps deleted or overwritten objects recoverable for a retention duration (7 to 90 days). It is a safety net, not a guarantee that data cannot be deleted.
- **A bucket retention policy** prevents deleting or replacing an object until its age exceeds the retention period. Attempts fail with a `retentionPolicyNotMet` error.
- **Bucket Lock** locks the retention policy: once locked, the policy cannot be reduced or removed, and the bucket cannot be deleted until every object has met the retention period. Locking is permanent, so teams test the period first. The period can still be increased.
Together with detailed audit logging, a locked policy is the Cloud Storage answer to WORM-style compliance requirements.
W: A locked seven-year retention policy: it blocks deletion and replacement of every record for seven years for all principals, cannot be shortened by anyone, and the test on a non-production bucket guards against locking a wrong period permanently.
X: B=Maximum soft delete: soft delete lets deleted data be restored for at most 90 days, and it does not stop a deletion or an overwrite from happening, so it cannot prove records stay unaltered for seven years.
C=Versioning plus an IAM deny policy: IAM policies can be changed by administrators with enough rights, so this is not an irreversible control, and a live object could still be replaced.
D=Lifecycle rule that never deletes: the absence of a rule is not a control. Anyone with delete permission could still remove records, and nothing prevents changing the configuration.
T: Immutability with an audit-proof guarantee means a locked bucket retention policy, not soft delete, versioning or procedure.

@ GCP-PCA D2 T2.2 advanced comparison
S: A software vendor's licensed database must stay on Compute Engine VMs. It holds about 500 GB, but peak load needs far more IOPS than the team's current SSD Persistent Disk delivers at that size, and the demand changes through the year. The team wants to raise or lower performance while the VM runs without paying for capacity it does not need. Which storage choice fits?
A: Enlarge the SSD Persistent Disk to several terabytes so that it inherits the higher IOPS limits that come with size
B: Move the data files to Local SSD attached to the VM, which has the lowest latency of all block options
C: Use a Hyperdisk Balanced volume with IOPS and throughput provisioned separately from its size and adjusted in use
D: Switch to standard Persistent Disk and raise the vCPU count of the VM so that it can issue more requests
K: C
G: ## Performance and capacity on block storage
With Persistent Disk, performance is tied to the size of the disk, so reaching a high IOPS target can mean buying capacity you never use.
Google Cloud Hyperdisk separates the two:
- You choose the IOPS or throughput of each Hyperdisk volume, independent of its capacity.
- You can increase or decrease a volume's performance while it is in use.
- Hyperdisk Storage Pools let you buy capacity and performance in bulk and share them across disks to avoid over-provisioning.
- Hyperdisk Balanced High Availability replicates synchronously across two zones, and asynchronous replication covers regional outages.
Local SSD is physically attached and very fast, but its data does not survive the VM being stopped or the host failing, so it is for caches and scratch data, not the system of record.
W: Hyperdisk Balanced with provisioned performance: IOPS and throughput are set per volume and change while the VM runs, so seasonal peaks are met without buying terabytes of unused capacity.
X: A=Bigger Persistent Disk: it works technically but pays for terabytes the 500 GB database does not need, and performance cannot be tuned independently when the seasonal demand drops.
B=Local SSD: its data is lost when the VM stops or the host fails, which is unacceptable for the database files, and its capacity is not adjusted online.
D=Standard Persistent Disk plus vCPUs: standard (HDD-backed) disks have the lowest IOPS, and adding vCPUs does not raise the limits of the disk itself.
T: When IOPS needs and capacity needs differ, provision performance independently with Hyperdisk instead of oversizing a disk.

@ GCP-PCA D2 T2.2 advanced use-case
S: A machine-learning team trains models on accelerators in a single zone. Checkpoints and training shards are read and written constantly, and object latency from a regular bucket leaves the accelerators idle. The team still wants Cloud Storage semantics and lowest latency, close to the VMs. Which TWO configuration decisions apply? (Select TWO)
A: Create a zonal bucket in the same zone as the accelerator VMs, which uses the Rapid storage class
B: Enable hierarchical namespace and uniform bucket-level access, which Rapid Bucket requires
C: Create a dual-region bucket with turbo replication so that a copy of the data sits near the VMs
D: Enable Autoclass on a regional bucket so that hot checkpoints are promoted to the Rapid storage class
E: Set the default storage class of a regional bucket to Nearline so that reads are served from a cache
K: A,B
G: ## Rapid Bucket
Rapid storage is a Cloud Storage class available only in **zonal buckets** (a bucket whose location is a single zone). Putting the bucket in the same zone as the compute gives significantly lower latency and higher throughput than other classes, which suits AI training and checkpointing. Other zones and regions can still access the bucket, with performance depending on network distance.
- Prerequisites: the bucket must have hierarchical namespace and uniform bucket-level access enabled.
- Trade-off: the data lives in one zone. Keep the authoritative copy of valuable data, such as final model artifacts, in a regional, dual-region or multi-region bucket.
- Rapid has no minimum storage duration and no retrieval fee, unlike the colder classes.
W: A=Zonal bucket in the accelerators' zone: colocation is what delivers the latency and throughput gain, and the Rapid class exists only for zonal buckets.
B=Hierarchical namespace plus uniform access: these are mandatory settings on a bucket that uses Rapid, so they must be part of the design.
X: C=Dual-region with turbo replication: turbo replication shortens replication lag between two regions for resilience; it does not place data in the training zone or reduce read latency.
D=Autoclass promotion to Rapid: Autoclass moves objects among the location-flexible classes and cannot promote data to Rapid, which is available only with zonal buckets.
E=Nearline default class: Nearline is a cold class with a minimum storage duration and retrieval fees, and it does not add a cache or speed up reads.
T: For lowest object latency next to accelerators, use a zonal Rapid bucket in the same zone, with hierarchical namespace and uniform access.

@ GCP-PCA D2 T2.2 advanced use-case
S: A healthcare software vendor runs SQL Server and MySQL on Compute Engine VMs while it migrates. Leadership fears a ransomware attack in which stolen administrator credentials are used to delete backups. Which TWO design points best address this? (Select TWO)
A: Send backups to a Backup and DR backup vault that enforces a minimum retention period and is immutable and indelible
B: Define a backup plan with backup rules that set the frequency and retention for the VMs, using application-consistent backups
C: Take disk snapshots in the same project as the VMs and rely on a small Owner group to prevent deletions
D: Export database dumps to a Standard bucket in the same project and enable Object Versioning on that bucket
E: Attach a second persistent disk to each VM and copy the data nightly with a cron job
K: A,B
G: ## Backups that survive a compromised admin
Backup and DR Service protects Compute Engine VMs (and their disks), Filestore, VMware Engine VMs and managed databases such as Cloud SQL and AlloyDB.
- **Backup vaults** are Google-managed, isolated storage that is the security boundary for backups. They enforce write-once-read-many immutability and indelibility, and an optional minimum retention period (up to 99 years) prevents early deletion or tampering, even by privileged users in the workload project.
- **Backup plans** link workloads to a vault and hold **backup rules** that define frequency (hourly to yearly), windows and retention.
- Compute Engine backups can be crash-consistent or application-consistent, which matters for databases that must restore to a clean state.
Backups that live in the same project, with the same credentials as the workload, are only as safe as those credentials.
W: A=Backup vault with enforced retention: backups cannot be modified or deleted before the retention period ends, which defeats an attacker using stolen administrator credentials.
B=Backup plan with application-consistent backups: scheduled, policy-driven backups with defined frequency and retention give restorable, clean database states.
X: C=Same-project snapshots: a compromised administrator or Owner can delete them, and relying on a small group is a process control, not an immutable one.
D=Bucket dumps with versioning: versioning in the same project is deletable by whoever holds the credentials, and dumps are manual, with no policy-based retention enforcement.
E=Second disk plus cron: the copy sits inside the same VM trust boundary, so ransomware or stolen credentials can encrypt or erase both copies.
T: Ransomware-resilient backups combine policy-driven backup plans with an immutable, retention-enforced backup vault outside the workload's reach.

@ GCP-PCA D2 T2.2 applied
S: A publisher's organization enforces public access prevention on all projects. A partner without any Google account must download one finished episode file for the next 48 hours, and the publisher does not want to copy the file elsewhere or make the bucket public. Which approach fits?
A: Grant allAuthenticatedUsers the Storage Object Viewer role on the object so that any person with a Google account can read it
B: Create Google accounts for the partner's staff and grant Storage Object Viewer on the project containing the bucket
C: Make the object public with allUsers read access for 48 hours and then remove the grant
D: Generate a V4 signed URL for the object with a 48-hour expiry, using a service account that can read the object
K: D
G: ## Time-limited access without an account
- **Public access prevention** blocks granting access to public principals (`allUsers`, `allAuthenticatedUsers`). Enforce it at the organization, folder or project with the `storage.publicAccessPrevention` constraint.
- **Signed URLs** carry a signature and an expiration in the query string. Anyone holding the URL can perform the allowed action on that one resource until it expires, without a Google account. They are created with a service account (or a user account with an HMAC key), and public access prevention does not affect them.
Signed URLs are the standard pattern for sharing a specific object temporarily with outside parties. The signer needs permission on the object, and the URL is a bearer credential, so it should be sent only to the intended recipient.
W: A V4 signed URL: it gives the partner one object for 48 hours with no account, works even though public access prevention blocks public grants, and needs no copy or bucket change.
X: A=allAuthenticatedUsers: public access prevention blocks it, and it would expose the object to anyone with any Google account, not just the partner.
B=Accounts plus project-level role: the partner has no accounts, a project-level viewer role exposes every object in the project, and it takes administrative effort for a single file.
C=Temporary allUsers grant: public access prevention rejects public grants, and even if allowed, the file would be open to the whole internet, not only to the partner.
T: To share one object temporarily with outsiders under public access prevention, hand out a signed URL.

@ GCP-PCA D2 T2.2 advanced tradeoff
S: A team enabled Object Versioning on forty buckets only to recover from accidental or malicious deletions and overwrites. Nobody ever restores a specific older version, but storage cost has grown because every overwrite keeps a full copy. The team wants time-bounded recovery of deleted or overwritten objects without a growing pile of versions. What should the architect recommend?
A: Keep versioning and add a lifecycle rule to move all noncurrent versions to Coldline
B: Rely on soft delete with a longer retention duration for these buckets, and keep versioning only where specific older versions are needed
C: Apply a locked retention policy to every bucket so that no object can be deleted or overwritten
D: Enable Autoclass on all buckets so that older copies are cheaper to keep
K: B
G: ## Soft delete or versioning
- **Soft delete** keeps deleted or overwritten objects in a hidden soft-deleted state for a retention duration (default 7 days, configurable from 7 to 90 days, or 0 to disable). Objects can be restored during that time, and the data is then permanently removed without extra rules. Google recommends soft delete rather than versioning for protection against accidental or malicious loss.
- **Object Versioning** keeps noncurrent versions until you delete them. It fits cases that need specific earlier generations, such as rollback of a published file, and then needs a lifecycle rule to bound growth.
- **Retention policies** block deletion and overwrite altogether, which is a compliance control and would also block normal updates.
W: Soft delete with a longer retention: it gives time-bounded recovery for deletions and overwrites that expires automatically, and versioning stays only where specific older versions matter.
X: A=Versioning plus Coldline: all versions are still kept forever, Coldline has a minimum storage duration and retrieval charges, and growth is not bounded.
C=Locked retention on every bucket: it blocks legitimate overwrites and deletions for the whole period and cannot be undone, which is far beyond a recovery requirement.
D=Autoclass: it moves objects among storage classes by access pattern, but it does not bound how long versions are kept or provide a recovery window.
T: For plain accident protection, use soft delete; reserve versioning, with lifecycle limits, for workloads that need specific older versions.

@ GCP-PCA D2 T2.4 advanced troubleshooting
S: A team schedules a nightly retraining pipeline on Agent Platform Pipelines. The ingest step reads a BigQuery table through a query string that never changes, and the run finishes in minutes but the model never reflects new rows. The team still wants costly feature-engineering steps to be skipped when their inputs are unchanged. What is the best fix?
A: Turn off caching for the entire pipeline job on every run, so that every step recomputes each night
B: Pass the run date to the ingest step as an input parameter, or turn off caching for that task only, and keep caching on for the other steps
C: Compile the pipeline with the TFX SDK instead of Kubeflow Pipelines so that ingest steps are rerun automatically
D: Increase the machine type of the training step so that it picks up the newest rows in the table
K: B
G: ## How pipeline execution caching works
Before a step runs, Agent Platform Pipelines looks in ML Metadata for an earlier execution with the same **interface**: the step's input values or artifact IDs, its output definition and its component specification (image, command, arguments, environment). Only pipelines with the same name share the cache. If a match exists, the earlier outputs are reused and the step is skipped.
- A step that reads external, changing data through an unchanging query has an unchanged interface, so the cache cannot tell the data changed.
- Fix it by making the changing fact part of the interface (pass a date or snapshot ID as a parameter), or turn caching off for that task (`set_caching_options(False)`).
- Caching can also be turned off for a whole `PipelineJob`, which fixes staleness but also reruns every costly step.
W: Run-date parameter or per-task caching off: the ingest step re-executes each night, while unchanged feature-engineering steps keep their cached outputs, so cost stays low.
X: A=Caching off for the whole job: it solves staleness but reruns every expensive step each night, which the team explicitly wants to avoid.
C=Switch to the TFX SDK: the SDK used to define the pipeline does not change how the cache key is calculated, so the ingest step would still be skipped.
D=Larger training machine: the training step was not the problem. It receives the cached ingest output, and more compute does not change what data it receives.
T: A stale pipeline step with an unchanged interface is a caching issue: add a changing input or disable caching for just that task.

@ GCP-PCA D2 T2.4 advanced use-case
S: Altostrat Media requires its recommendation models to be auditable and explainable. For any model in production, reviewers must be able to show which datasets, parameters and pipeline run produced it. Training is currently run from individual notebooks. Which approach best meets this?
A: Keep training in notebooks and record the dataset names and parameters in a shared team spreadsheet

This is what makes a model traceable for auditors, and it supports explainability reviews that need to know the exact training inputs.
W: Pipelines with ML Metadata and Model Registry: every dataset, parameter and run that produced a model is recorded as lineage by the platform, giving a verifiable, repeatable audit trail.

@ GCP-PCA D2 T2.4 advanced comparison
S: A pipeline's preprocessing task currently loads 8 TB of clickstream data into one container, joins it with warehouse tables in memory and often runs out of memory. The team wants the pipeline to stay the single orchestrator of the ML workflow. What should the architect recommend?
A: Let pipeline tasks submit the SQL joins to BigQuery and large-scale parsing to Dataflow, then pass the resulting tables or files to later tasks

@ GCP-PCA D2 T2.4 advanced use-case
S: A research group is picking accelerators for two training workloads. Which TWO workloads are the best candidates for Cloud TPUs? (Select TWO)
A: A large transformer written in JAX whose training loop is dominated by dense matrix computations, with no custom operations in the main loop
B: A model with a large number of custom TensorFlow operations written in C++ that must run on the host CPU
C: A model dominated by large matrix multiplications that must be trained with large batches and scale across many chips with little code change
D: A model with many custom PyTorch operations inside the main training loop that must run at least partly on CPUs
E: A model that uses TensorFlow operations that are not available on Cloud TPU
K: A,C
G: ## When TPUs fit
TPUs are designed for large matrix operations. They have on-chip high-bandwidth memory (HBM), which allows larger models and batch sizes, and chips can be connected in groups called **slices** that scale a workload with little to no code change. Documentation lists what suits and what does not:
- Suitable: models dominated by matrix computations, and models with no custom PyTorch/JAX operations inside the main training loop.
- Poor fit: models with many custom TensorFlow operations written in C++, models with a significant number of custom PyTorch/JAX operations that must run at least partly on CPUs, and models that use TensorFlow operations unavailable on Cloud TPU.
GPUs remain the flexible choice for workloads with custom kernels or operations that TPUs do not support, and Agent Platform training supports both. A TPU VM training job on Agent Platform takes one worker pool with one replica.
W: A=JAX transformer with matrix-dominated loop: this is the textbook TPU workload, with no host-side custom operations to slow the chips.
C=Matrix-heavy, large-batch model scaled over slices: HBM and slices were built for exactly this, and scaling needs little code change.
X: B=Custom C++ TensorFlow ops: custom operations that run on the CPU do not benefit from TPUs and leave the chips waiting, so GPUs or CPUs suit the model better.
D=Custom PyTorch ops on CPUs in the loop: host-side work in the main loop leaves TPUs idle; documentation lists this as a poor fit.
E=Unavailable TensorFlow ops: if an operation is not available on Cloud TPU, the model cannot run there as written.

@ GCP-PCA D2 T2.4 advanced tradeoff
S: A team fine-tunes a model on an 8-GPU VM for two to three days per run. The job has no checkpointing, so a preemption would lose all progress. The job may wait several hours for capacity to start, and the team wants a discount compared with on-demand without buying a reservation. Which consumption option fits?
A: Spot VMs, which give the deepest discount and are started immediately based on availability
B: Flex-start, which waits for capacity, runs for up to seven days and is not preemptible
C: Standard on-demand VMs, requested again on a loop until the capacity is available

K: B
G: ## Matching consumption to workload
AI Hypercomputer offers several ways to obtain GPU capacity:
- **On-demand:** best-effort capacity, no discount, no assurance.
- **Spot:** deeply discounted, immediate if available, but can be preempted at any time, so only fault-tolerant jobs belong here.
- **Flex-start:** short-duration (up to seven days) workloads that can wait for capacity; best-effort, discounted on supported series, and not preemptible. Suited to fine-tuning, small pre-training, batch inference and HPC simulation.
- **Reservations:** standard reservations for critical general GPU workloads, and future reservations (capacity blocks, or calendar mode up to 90 days) for large clustered GPU training. They give very high capacity assurance but need planning, and often commitments.

C=Repeated on-demand requests: this has no discount, no capacity assurance, and requires custom retry automation.
D=Future reservation with commitment: it is designed for large, planned, long-running clusters, and paying for reserved capacity that sits idle between occasional runs is not cost-effective.
