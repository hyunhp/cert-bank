@ GCP-PCA D5 T5.2 applied comparison
S: A consulting firm brings in 30 short-term contractors who must edit and run infrastructure scripts against a client's Google Cloud projects for six weeks. Contractor laptops cannot be managed by the client, and the client wants no local installation of tools and no source files left on personal machines. The security team also wants to control the machine image, the machine size and the network the environments attach to. Which approach fits best?
A: Give each contractor a Cloud Shell session, since its pre-configured VM image, machine size and network can be fixed by the client's administrators in every project
B: Define Cloud Workstations configurations with the image, machine type, network and persistent home, and let each contractor create a workstation from them
C: Ask each contractor to install the Google Cloud CLI locally and run every script from the laptop with a long-lived service account key stored in a file
D: Create one shared Compute Engine VM and give all contractors the same SSH account, so that one machine holds every script and every credential
K: B
G: ## Two managed ways to work without local tools
Both options keep tools off the personal laptop and are reached from a browser, but they answer different needs.
- **Cloud Shell** gives every user a free, pre-configured environment: an ephemeral Debian-based VM owned and managed by Google (it does not appear in your project) with the gcloud CLI, Git, Docker, Terraform and editors. The VM is discarded after an hour of inactivity; a 5 GB persistent `$HOME` survives across sessions and cannot be enlarged. You cannot choose its machine type, image or network. The Cloud Shell Editor (a Code OSS based editor) and Cloud Code run inside it.
- **Cloud Workstations** gives managed development environments that run on Compute Engine VMs in your own project. An administrator defines a workstation configuration (VM type, container image, IDE, persistent disk, idle timeout) and the workstation cluster is attached to your VPC network. Developers each create a workstation from the template, so every contractor gets an identical, centrally governed environment.
## Reading the requirement
The decisive phrases are "control the machine image, the machine size and the network". That is exactly what a workstation configuration offers and Cloud Shell does not. Cloud Shell is the right answer when the need is simply "no install, quick, free, personal".
W: Cloud Workstations: configurations let the client fix the image, machine type, network attachment and persistent storage, run in the client's project, and need only a browser on the contractor side, so no source code or tool installation is left on personal laptops.
X: A=Cloud Shell: the environment is Google-managed and per user; administrators cannot set its machine image, machine size or VPC attachment, so the security requirement of controlling those three is not met.
C=Local CLI with a key file: it contradicts the requirement of no local tools and no files on personal machines, and a long-lived key on an unmanaged laptop is the weakest credential practice.
D=One shared VM and SSH account: all 30 people share one identity, so audit trails and least privilege are lost, and the single machine becomes a single point of failure for every credential.
T: Use Cloud Shell for quick personal, no-install access and Cloud Workstations when administrators must control the image, size and network of developer environments.
V: Cloud Shell, Cloud Workstations

@ GCP-PCA D5 T5.2 applied use-case
S: Altostrat Media runs its recommendation and transcoding services on GKE and its event tasks on Cloud Run. Its developers currently build container images by hand, write Kubernetes YAML in a text editor, and wait for a pipeline run to see whether a change works. The platform lead wants a faster inner loop from the developers' own IDEs: run and debug the application against a cluster, and get help with Kubernetes and Skaffold configuration. Which tool should the architect recommend?
A: Cloud Code in the developers' IDEs, which provides run and debug against Kubernetes and Cloud Run, sample templates and YAML and Skaffold editing support
B: Cloud Deploy for each developer, because its release pipelines can replace the need to run and debug the application from the IDE
C: A Terraform module that creates a new GKE cluster per developer, so that each developer edits the same YAML files in a plain text editor
D: The Google Cloud console's workload pages, which let developers edit deployed Kubernetes resources directly in the production cluster for fast feedback
K: A
G: ## Cloud Code in the development loop
Cloud Code is a set of extensions for VS Code, IntelliJ and Cloud Shell. It supports the full development cycle for Kubernetes and Cloud Run applications: run-ready and debug-ready sample applications, continuous build and run (it uses Skaffold under the hood), advanced Kubernetes YAML support, Skaffold configuration editing, log streaming, resource browsing, Secret Manager and Cloud Storage browsing, and debugging of the application running in a cluster. It also bundles Gemini Code Assist extensions for code help.
## Where it fits among delivery tools
- **IDE tooling (Cloud Code)** shortens the inner loop on the developer's machine or in Cloud Shell.
- **Delivery pipelines (Cloud Build, Cloud Deploy)** promote an already-built release through dev, staging and production with approvals and rollbacks; they are the outer loop.
- **IaC (Terraform)** provisions the platform, not the application code loop.
W: Cloud Code puts run, debug, log streaming and Kubernetes or Skaffold editing help inside the IDE for both GKE and Cloud Run, which shortens the exact inner loop the platform lead describes.
X: B=Cloud Deploy: it is a promotion and release tool for the outer loop; it does not give developers an IDE-based run, debug or YAML-editing experience.
C=Cluster per developer with Terraform: this adds cost and provisioning work yet does nothing for editing assistance, debugging or fast rebuilds, and developers would still use a plain text editor.
D=Editing in the console: changing live workloads in production bypasses review and version control, and offers no local debugging, so it is both unsafe and not an inner-loop tool.
T: Cloud Code is the inner-loop IDE tool for Kubernetes and Cloud Run; Cloud Deploy and Cloud Build are the outer-loop delivery tools.
V: Cloud Code, GKE, Cloud Run

@ GCP-PCA D5 T5.2 applied use-case
S: A team builds a service on Spanner and wants fast, free tests that run on every commit in a CI job, without creating Spanner instances or credentials for the job. Which TWO statements correctly describe how to use, and what to expect from, the Spanner emulator? (Select TWO)
A: Run the emulator in the CI job and point the client library at it, accepting that data, schema and configuration are lost on restart
B: Treat a green run on the emulator as proof of production performance, because the emulator reproduces production throughput and latency
C: Keep an additional test stage against a real Spanner instance, because error messages and checks such as whether a statement is partitionable can differ from production
D: Use the emulator as a low-cost production database for small tenants, because it offers the same APIs as the Spanner service
E: Run the emulator in a shared long-lived container so that schemas created in one commit are guaranteed to still exist for the next
K: A,C
G: ## What a local emulator is for
The Spanner emulator, shipped with the Google Cloud CLI, is a local, in-memory implementation of the Spanner APIs. The same client library code runs against it, so tests need neither a project nor billing. It listens on local gRPC and REST endpoints and is intended only for development and tests, not for production.
## What it does not promise
- It stores data only in memory: data, schema and configuration disappear when it restarts, so each test run creates what it needs.
- Its performance and scalability do not compare to the production service.
- Error messages can differ, and it does not verify whether a Partitioned DML or `partitionQuery` statement is really partitionable, so a statement that passes locally can fail in production.
## Architect's rule
Use emulators for fast, isolated functional tests, and keep a smaller stage against the real service for performance, quotas, IAM and behaviors the emulator does not check.
W: A=Emulator in CI: starting it per run and creating the schema each time gives fast, free, credential-free tests, and the loss of state on restart is expected behavior rather than a defect.
C=Real-instance stage: because messages and partitionability checks can differ from production, a later stage against actual Spanner catches what the emulator cannot.
X: B=Production performance: the emulator's performance and scalability are explicitly not comparable to the service, so load or latency results from it prove nothing.
D=Emulator as a database: it is in-memory, loses all data on restart and is intended only for development and testing.
E=Long-lived shared emulator: its state is not durable, and relying on leftovers from earlier commits makes tests order-dependent and fragile.
T: Emulators give fast, free functional tests with in-memory state; validate performance, quotas and production-only checks on the real service.
V: Spanner

@ GCP-PCA D5 T5.2 applied troubleshooting
S: A developer follows a tutorial for the Pub/Sub emulator. The application, built with a Cloud Client Library, now publishes messages locally as expected after the PUBSUB_EMULATOR_HOST environment variable is set. The developer then tries to inspect the emulator's topics with a gcloud pubsub command and with the Google Cloud console, but neither shows any topic. What is the correct understanding?
A: The emulator did not start correctly, so the developer must reinstall the Google Cloud CLI before topics can be created or displayed
B: The emulator creates topics in a hidden project, so the developer should grant the Pub/Sub Viewer role on that project to see them
C: The emulator is reached through the client libraries' environment variable only, and it does not support the console or gcloud pubsub commands
D: The emulator keeps topics only for 60 seconds, so the developer should republish and run the gcloud command before they expire
K: C
G: ## How an application finds the emulator
The Pub/Sub emulator runs locally (started with the Google Cloud CLI). Resources and messages exist for the lifetime of the emulator session. Cloud Client Libraries check the `PUBSUB_EMULATOR_HOST` environment variable (set from the output of the emulator's `env-init` command) and, when it is set, send API calls to that host instead of Google Cloud. The project ID used does not have to be a real project.
## What does not work with it
The emulator is for applications built with Cloud Client Libraries. The console and `gcloud pubsub` commands talk to the real service and are not supported with the emulator, so the real service shows nothing, and no IAM role applies to the emulator.
## Takeaway for design
Make tests create their own topics and subscriptions through the client library, and inspect them through the same library.
W: Environment-variable routing and no console or gcloud pubsub support: the library is redirected to the local emulator, while the console and gcloud pubsub commands address the real service, which has no such topics.
X: A=Reinstall the CLI: publishing already works against the emulator, which shows it is running; the missing topics are caused by where the other tools look.
B=Hidden project and Viewer role: the emulator does not run in a Google Cloud project, and its project ID need not exist, so no IAM role is involved.
D=60-second expiry: resources live for the emulator session, not a short timer.
T: The Pub/Sub emulator is for Cloud Client Library code through PUBSUB_EMULATOR_HOST; gcloud pubsub and the console do not work with it.
V: Pub/Sub

@ GCP-PCA D5 T5.2 applied definition
S: A team designs tests for a service that stores time-series data in Bigtable and wants to use the Bigtable emulator in its test suite. Which statement about what the emulator offers is correct?
A: Data is kept only in memory, and a test can connect with any project and instance name, then create the tables and data it needs on every run
B: The emulator provides administrative APIs for creating and managing instances and clusters, which tests can call to build a production-like topology
C: The emulator encrypts traffic with TLS and enforces IAM, so security configuration can be validated end to end on a developer machine
D: Data written to the emulator is replicated to a second local node, so failover behavior of a multi-cluster instance can be tested
K: A
G: ## The Bigtable emulator in short
The Google Cloud CLI provides a local, in-memory Bigtable emulator for development and testing. It prints the host and port it uses (by default `localhost:8086`), and clients connect to that address.
- **No persistence**: data does not survive across runs.
- **No instance administration**: it does not provide administrative APIs to create or manage instances and clusters; you connect with any project and instance name and create tables and data.
- **No secure connection**: it does not support a secure connection, so it is not a place to validate transport security or IAM.
- It is not a production deployment and does not model cluster replication or failover.
## Design consequence
Tests of data access code are a good fit. Tests about topology, replication, authorization or capacity belong on a real test instance.
W: In-memory emulator with arbitrary names: because nothing persists and any project and instance name is accepted, each run creates its own tables and data, which keeps tests independent and credential-free.
X: B=Administrative APIs: the emulator does not offer APIs to create or manage instances and clusters, so a topology cannot be built through it.
C=TLS and IAM: the emulator does not support a secure connection, so it cannot validate transport security or access control.
D=Replication to a second node: the emulator is a single local process and does not model replication or failover; use a real multi-cluster test instance for that.
T: The Bigtable emulator is an in-memory data-access test tool: no persistence, no instance administration, no TLS, any project or instance name.
V: Bigtable

S: A team writes integration tests for an application that uses the Firestore server client library. The tests must never touch production data, must run on developer laptops and in CI without any Google Cloud credentials, and the team does not want test-only branches in the application code. What is the best design?
A: Start the Firestore emulator in the test environment and set FIRESTORE_EMULATOR_HOST, so the unchanged client library connects to it
B: Add a configuration flag in the application that, in test mode, swaps the Firestore client for a hand-written in-memory fake class
C: Create a separate Firestore database in the production project, prefix all test document paths with "test_", and delete them after each run

Firestore has an in-memory emulator in the Google Cloud CLI, usable with all Firestore client libraries and meant only for local testing. - Application code is identical in test and production; only the environment differs.
- No credentials, no billing and no shared state between runs.

T: Point unchanged client code at an emulator with the library's environment variable, and keep production data and credentials out of tests.

@ GCP-PCA D5 T5.2 applied use-case
S: EHR Healthcare is moving from its colocation data center and expects to create several nearly identical environments (development, test, per-region production) for its containerized platform, with differences only in names, sizes and network ranges. Past outages came from misconfiguration. The architect wants repeatable, reviewable provisioning that a new region can reuse. Which approach is best?
A: Write reusable Terraform modules in version control and have each environment call them with its own values via a reviewed plan
B: Document the build steps in a wiki, let each regional team follow them in the console, and then verify the result with a checklist
C: Clone the production project's resources into each new environment by hand, then edit names, sizes and ranges directly in each copy
D: Write one large shell script of gcloud commands per environment and run it from an engineer's workstation whenever a new region is needed

G: ## Why modules plus review reduce misconfiguration
Terraform lets you declare the desired end state, generate an execution plan to preview changes, and package common patterns as **modules** with standard inputs and outputs. Deploying the same configuration several times produces reproducible development, test and production environments. Google's Terraform best practices add that modules follow the standard structure (`main.tf`, a `README.md`), that every variable has a description, that environment-specific variables such as `project_id` have **no default** so callers must supply a value, and that useful outputs are exposed.

Version control, review of the plan and an automated pipeline give accountability (who changed what and when), consistency regardless of who applies, and easy rollback. C=Hand cloning: copies carry hidden differences and leftover settings, and editing each copy by hand creates the inconsistencies EHR wants to avoid.
D=Workstation script: imperative scripts do not track state or preview changes, depend on one person's machine and are hard to review or rerun safely.
T: Declarative modules in version control, parameterized per environment and applied after a reviewed plan, give repeatable, auditable environments.

@ GCP-PCA D5 T5.2 advanced troubleshooting
S: A company manages production with Terraform, but an incident review finds that several firewall rules and a machine type were changed by hand in the console during earlier incidents. The next terraform apply would silently revert some of those changes. Which TWO measures best prevent configuration drift from recurring while still letting on-call engineers act quickly? (Select TWO)
A: Run terraform plan on a schedule and on every pipeline run, and treat any unexpected difference as a finding to import into the code or revert
B: Give every engineer the Admin basic role in production so that urgent console fixes are never blocked and later get written back to the code
C: Restrict write permissions in production to the CI/CD service account, and give people break-glass access with auditing, so emergency changes are rare, visible and backported to the code
D: Delete the Terraform state after each incident so that the next apply starts from a clean picture of production
E: Stop using the Terraform plan step and apply directly, so differences are corrected immediately without waiting for a review
K: A,C
G: ## Drift and how to control it
Terraform's state maps the configuration to real resources. When someone changes a resource outside Terraform, the real world differs from state and code, which is **drift**. The plan compares them and shows what an apply would change, so regularly running plan detects drift before an apply surprises anyone.
## Operational excellence practices
- Make the pipeline the normal path to production: IaC in version control with CI/CD gives accountability and consistency.
- Grant routine write access to the pipeline identity only; use time-bound, audited break-glass access for emergencies, then update the code so the fix is not lost.
- Treat a plan difference as a finding: either import or write the change into the code, or revert it.
W: A=Scheduled and per-run plan: the plan shows differences between code, state and reality, so drift is found early and resolved deliberately rather than by a surprise apply.
C=CI/CD-only writes plus break-glass: this keeps routine changes in reviewed code, still allows fast, audited emergency action, and the follow-up backport closes the drift.
X: B=Admin for everyone: broad write access is what produced the hand changes, and a basic Admin role in production violates least privilege.
D=Deleting state: without state Terraform loses its mapping to real resources and may try to recreate or conflict with existing ones; it hides drift rather than managing it.
E=Skipping plan: the preview is the control that lets people see unexpected changes; removing it makes surprising reverts more likely, not less.
T: Prevent drift by making the pipeline the default write path, detecting differences with regular plans, and backporting audited emergency changes.
V: Terraform, IAM

@ GCP-PCA D5 T5.2 applied tradeoff
S: Cymbal Retail manages its Cloud SQL for MySQL order database with Terraform. During a refactor an engineer renames the resource block in the configuration. The plan output shows the existing database instance would be destroyed and a new one created. Reviewers almost approved the plan because the pipeline summary only reported "1 to add, 1 to destroy". Which change best protects the architect's stateful resources in the future?
A: Enable deletion protection on databases, have reviewers read destroy lines in the plan, and use a state move for renames
B: Remove the database from Terraform so nobody can destroy it by accident, and manage it by hand in the console
C: Disable plan output in the pipeline so that reviewers focus on code diffs instead of tool output that they may misread
D: Add a post-apply script that restores the latest backup when a database disappears, so a destroyed instance is recreated automatically
K: A
G: ## Stateful resources need extra guards
Terraform identifies resources by their address in state. If the block name changes, Terraform sees one resource gone and one new, and plans a destroy and create. For stateless things this is harmless; for a database it is data loss.
Google's Terraform best practices say: for stateful resources, such as databases, ensure that deletion protection is enabled. Combine this with:
- plan review that looks specifically for destroy and replace actions;
- state refactoring (a `moved` block or a state move) so that a rename maps the old address to the new one without replacing the resource;
- backups and tested restores as the last line of defense.
## What not to do
Managing the database by hand removes the benefits of IaC; hiding the plan removes the preview; restoring after a destroy means downtime and possible data loss.
W: Deletion protection blocks destruction of the instance, the plan review catches destroy actions before approval, and a move for renames preserves the existing resource, so the refactor is safe and the database stays in code.
X: B=Hand-managed database: this gives up version control, review and reproducibility for the most important resource, and manual changes are error-prone.
C=Hiding plan output: the plan is the preview that exposed the problem; removing it hides destroys from reviewers.
D=Restore script: a restore recovers an older copy after the damage, with downtime and loss of newer writes; prevention is far better than automatic recovery.
T: Protect stateful resources with deletion protection, read destroy actions in the plan, and use moves instead of replace for renames.
V: Terraform, Cloud SQL

@ GCP-PCA D5 T5.2 advanced use-case
S: A company runs an order service on Cloud Run and a batch job on Compute Engine. Developers also test locally. Which TWO practices follow Google Cloud's recommendations for authenticating these workloads to Google APIs? (Select TWO)
A: Create a user-managed service account for each workload, grant it only the roles it needs, and attach it to the Cloud Run service or VM so that the client library finds credentials automatically
B: Download a key file for the Compute Engine default service account, store it in the repository and read it from GOOGLE_APPLICATION_CREDENTIALS in every environment
C: Have the production applications use developers' personal user credentials, since these are always the most traceable identity for audit
D: Use Application Default Credentials in the code, so that the same code uses the attached service account in production and local credentials during development
E: Hardcode a long-lived access token in the application's configuration file and refresh it by hand every few months
K: A,D
G: ## Application Default Credentials (ADC)
ADC is a strategy used by the authentication libraries to find credentials from the environment, so the same code works in development and production without changes. It searches in order: the `GOOGLE_APPLICATION_CREDENTIALS` environment variable (a credential configuration file for workforce or workload identity federation, or a service account key), a credential file created by `gcloud auth application-default login`, and the **attached service account** returned by the metadata server.
## Preferred production method
The attached service account is the preferred method in production on Google Cloud: create a user-managed service account, grant the least privileged roles, and attach it to the resource where the code runs. Service account keys are a security risk and not recommended, because a leaked key can be used without any further information.
## Local development
Developers run `gcloud auth application-default login` to give ADC a local credential file; the code is unchanged.
W: A=Attached user-managed service account: it follows least privilege per workload, needs no key to manage, and is the preferred production method.
D=ADC in code: libraries pick the right credential for each environment, so no environment-specific authentication code exists.
X: B=Key for the default service account: a downloaded key in a repository is a leak waiting to happen, and the default account typically carries broad roles shared by many workloads.
C=Personal credentials in production: production would depend on an individual's access and lifecycle, and break when the person leaves; workloads should run as service accounts.
E=Hardcoded access token: tokens are short-lived, and manual refresh means outages, plus a secret stored in a file.
T: Use ADC in code and an attached least-privilege service account in production; avoid keys and personal credentials.
V: IAM, Cloud Run, Compute Engine

@ GCP-PCA D5 T5.2 applied use-case
S: Altostrat Media's legacy content-ingestion systems stay on premises for now. They run in a data center whose identity provider supports OpenID Connect. These servers must upload objects to Cloud Storage and call other Google Cloud APIs. The security team forbids downloading service account keys. Which approach should the architect choose?
A: Create one service account key per ingestion server and rotate the key files every 90 days with a scheduled job
B: Open the buckets to allUsers write access from the data center's public IP range, so the servers need no credentials at all
C: Make a single Google user account for the ingestion team and let the servers sign in with its stored password through a script
D: Set up Workload Identity Federation with the on-premises OIDC provider and let client libraries use its configuration file via ADC
K: D
G: ## Credentials for workloads outside Google Cloud
Workloads outside Google Cloud cannot use an attached service account. Instead of a downloaded key, **Workload Identity Federation** lets a workload exchange a credential from an external identity provider (OIDC, SAML, or cloud and Kerberos-based providers) for short-lived Google Cloud access. You create a workload identity pool and provider, then generate a **credential configuration file**; ADC can read it through `GOOGLE_APPLICATION_CREDENTIALS`, so Cloud Client Libraries and gcloud use it without code changes.
## Why it is better than keys
Service account keys are long-lived and a compromised key works for anyone who holds it. Federation uses short-lived tokens tied to the external identity, so there is nothing to download or rotate.
W: Workload Identity Federation with the OIDC provider issues short-lived credentials, needs no key download, and works with the client libraries via ADC and the credential configuration file.
X: A=Keys per server: keys are exactly what the security team forbids; rotation reduces but does not remove the risk of a long-lived secret on each server.
B=Public write access: anyone on the internet could spoof the IP range or use the open permission, and public write access fails any security review.
C=Shared user account password: interactive user identities are not for workloads, passwords in scripts are poor secrets, and multi-factor and audit traceability break.
T: For workloads outside Google Cloud, use Workload Identity Federation instead of service account keys, and let ADC consume the configuration file.
V: IAM, Cloud Storage

@ GCP-PCA D5 T5.2 applied comparison
S: A new team will build a Python service that publishes to Pub/Sub, writes to Cloud Storage and calls other Google Cloud APIs. A senior developer proposes writing REST calls by hand with a generic HTTP library and managing OAuth tokens in the application. Another proposes the older Google API Client Libraries because "they cover every API". What should the architect recommend?
A: Hand-written REST calls, because only they allow complete control of retries and authentication across all Google Cloud services
B: The Google API Client Libraries for all new code, because they are the newer model and support gRPC for the highest throughput
C: Cloud Client Libraries, which handle authentication and can use gRPC, with the older libraries only where a Cloud library is missing
D: A single in-house wrapper over raw HTTP, so that every team shares one custom client and the company avoids vendor-provided libraries
K: C
G: ## Three ways to call Google Cloud APIs
- **Cloud Client Libraries** are the recommended option. They provide idiomatic code per language, a consistent style across services, handle low-level communication including authentication, install with package managers such as `pip` and `npm`, and in some cases use gRPC under the hood, which can raise throughput per CPU substantially over JSON over REST.
- **Google API Client Libraries** are an older type of library, auto-generated, REST only (no gRPC) and less idiomatic. Use them if a Cloud Client Library is not available for your language or API, or when upgrading a project that already uses them.
- **Your own client code** (REST/HTTP or generated gRPC clients) is for experienced developers whose needs the libraries do not meet.

E=No alerts in business hours: customers become the monitoring system, and detection time grows.

@ GCP-PCA D6 T6.2 applied use-case
S: A company promises its enterprise customers 99.9% availability for a public HTTPS API on Google Cloud. Internal metrics show healthy servers, yet a regional DNS problem recently made the API unreachable for some customers without any internal error. The operations lead wants an independent view of availability from the customers' perspective, with an alert when the API cannot be reached. What should the architect add?
A: A public uptime check that probes the API endpoint from multiple world locations, with an alerting policy on failures
B: A CPU utilization alert on the backend instances, because high CPU is always the first sign of an unreachable API
C: A log-based metric on the application logs, because requests that never reach the application are still logged by it
D: A weekly manual test by an engineer from the office network, recorded in a spreadsheet
K: A
G: ## Measuring from the outside
Public uptime checks test the availability of publicly accessible URLs and Google Cloud resources by sending periodic HTTP, HTTPS or TCP requests from multiple locations around the world; an uptime check uses at least three checkers, and a check fails when no response arrives within the timeout from more than one location. You can attach an alerting policy and notification channels, ideally of more than one type. Private uptime checks exist for endpoints that are not public.
## Why internal signals miss this
Metrics and logs from the servers only describe requests that arrive. If DNS, a network path or a load balancer problem stops requests reaching the service, the servers look healthy. An external probe measures the customer's path and gives a direct availability measurement for SLO and SLA reporting.
W: A public uptime check from several locations tests what customers experience, including DNS and network paths, and its alerting policy notifies the team when the endpoint cannot be reached.
X: B=CPU alert: an unreachable API receives no traffic, so CPU would drop rather than rise, and the alert would not fire.
C=Log-based metric: requests that never arrive are never logged by the application, so the logs show nothing wrong.
D=Weekly manual test: it is infrequent, from one location, and cannot support a 99.9% availability promise or timely alerts.
T: Use uptime checks for an external, customer-view availability measurement; internal metrics cannot see requests that never arrive.
