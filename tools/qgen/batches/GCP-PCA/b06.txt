@ GCP-PCA D3 T3.1 advanced comparison
S: A healthcare analytics company stores patient-derived datasets in BigQuery and Cloud Storage. A recent penetration test showed that an engineer with valid IAM permissions, or an attacker holding that engineer's stolen credentials, could copy a dataset to a bucket in an unrelated external project and read it there. The architect must close this path without removing the engineer's legitimate roles. Which control addresses it?
A: Remove the engineer's data roles and re-grant them at the dataset and bucket level only, so that no principal holds a project-wide data role
B: Place the projects in a VPC Service Controls service perimeter so that calls to BigQuery and Cloud Storage cannot move data to resources outside it
C: Add an IAM Conditions expression to every data role that limits access to the corporate IP address range of the engineer's office network
D: Require customer-managed encryption keys on both services so that data copied to an outside project stays unreadable without the key
K: B
G: ## IAM answers "who", perimeters answer "from where and to where"
IAM allow policies decide whether a principal may call an API. A principal who passes that check can still copy data anywhere the API allows, including a bucket in another organization's project. Credentials that are valid but stolen pass the same check.
**VPC Service Controls** adds a second, independent layer around Google-managed services. Projects placed in a **service perimeter** cannot have protected services read from or written to resources outside the perimeter, even by principals with the right IAM roles.
- It stops exfiltration through the service APIs, for example copying to a public bucket or to an external BigQuery table.
- Ingress and egress rules open exactly the exchanges that the business needs.
- Google recommends using it together with IAM for defense in depth, not instead of it.
W: Service perimeter: VPC Service Controls blocks the copy to the outside project at the API layer even though the caller's IAM roles allow reading the data, which is the gap the penetration test found.
X: A=Narrower IAM scope: tightening grants reduces how much data one identity can reach, but an identity with legitimate access to a dataset can still copy it to an outside project. IAM does not control the destination.
C=IAM Conditions on IP range: a condition on the caller's address helps against credentials used from other networks, but it does not stop an allowed user in the office from writing to an external bucket, and it does not govern the destination.
D=CMEK: customer-managed keys protect data at rest in the owning project. A copy written to another project's bucket is encrypted there under that project's own key, which the receiving party controls, so the control does not prevent exfiltration.
T: Valid IAM access plus an unwanted destination = exfiltration risk; a VPC Service Controls perimeter limits where protected services can send data, on top of IAM.
V: VPC Service Controls, IAM, BigQuery, Cloud Storage

@ GCP-PCA D3 T3.1 applied use-case
S: A bank wants to wrap its 40 production analytics projects in a VPC Service Controls perimeter. These projects serve nightly reports, a partner data feed and several internal tools, and the team cannot list every legitimate caller. Enforcing immediately could break business-critical jobs. What is the best rollout?
A: Enforce the perimeter on a single project first, keep the other 39 outside, and add the rest one at a time after each project has run without incident
B: Create the perimeter in dry run mode, review the audit log entries for would-be violations, add ingress and egress rules for legitimate flows, then enforce it
C: Enforce the perimeter and include every service in the restricted services list, then ask teams to open support tickets for each blocked job and add exceptions afterwards
D: Create the perimeter with only the partner feed's service account as a member, so the partner flow is covered first and all other projects stay unaffected
K: B
G: ## Dry run: see the blocked traffic before it is blocked
A VPC Service Controls perimeter can be configured in **dry run mode**. Requests that would violate the perimeter are allowed but written to Cloud Audit Logs, so the team sees the exact callers, services and methods that enforcement would block.
- Use the logs to learn real traffic: batch jobs, partner integrations, CI systems, on-premises callers.
- Model the legitimate flows as **ingress rules** (outside callers coming in) and **egress rules** (protected resources reaching outside).
- Enforce only when the dry run log shows no unexplained violations.
Perimeters also hold whole projects as members, not individual service accounts, and you choose which services are restricted.
W: Dry run first: the team observes violations without breaking jobs, translates the legitimate ones into ingress and egress rules, and enforces once the log is clean, which is the safe migration path for an unknown caller population.
X: A=One project at a time: this would leave 39 projects unprotected for a long time and does not reveal cross-project dependencies, because the first project's callers and neighbours are unknown. Dry run covers all projects at once without risk.
C=Enforce immediately: it protects the data from day one but breaks unknown flows in production and turns an architecture task into an outage. The requirement was to avoid breaking critical jobs.
D=Service account as member: a perimeter protects projects, with identities handled in ingress and egress rules and access levels. Listing one service account as a member does not protect the datasets in the other projects.
T: Roll out a perimeter in dry run, read the audit logs, add ingress/egress rules, then enforce.
V: VPC Service Controls, Cloud Audit Logs

@ GCP-PCA D3 T3.1 advanced definition
S: A security architect is designing VPC Service Controls for a company that keeps regulated data in two separate perimeters, one owned by research and one by finance, and sometimes needs controlled sharing between them. Which TWO statements describe the correct design? (Select TWO)
A: Ingress and egress rules let the two perimeters exchange only specified identities, services and methods, so the sharing path is explicit and narrow
B: Putting a project in a perimeter makes IAM unnecessary for it, because the perimeter now decides every access decision for the protected services
C: VPC Service Controls complements IAM, so a request needs both a matching IAM permission and to satisfy the perimeter boundary rules to succeed
D: Perimeters replace Cloud NGFW rules, so VPC firewall rules and firewall policies can be removed from the protected projects once the perimeter is enforced
E: Any metadata about a protected resource, such as bucket names, is always blocked from callers outside the perimeter without exceptions
K: A,C
G: ## What a perimeter is and is not
VPC Service Controls is a boundary around Google-managed services, enforced independently of IAM. It controls the movement of data across the boundary.
- **Both checks apply.** A request succeeds only if IAM allows it and the perimeter allows it.
- **Cross-perimeter exchange** uses ingress and egress rules, which name identities, source or destination resources, services and methods.
- **Network firewalls are different.** Firewall rules govern VM traffic to and from IP addresses; perimeters govern calls to Google APIs. They protect different paths.
- **Metadata.** Google states the primary goal is controlling data, and some metadata may still be accessible in some scenarios.
W: A=Ingress and egress rules: sharing between the research and finance perimeters is expressed as explicit rules naming who can do what, so nothing else crosses.
C=Defense in depth: IAM and the perimeter are independent layers, and a request must pass both, which is why Google recommends using them together.
X: B=Perimeter replaces IAM: the perimeter has no notion of least privilege per user or role, so IAM remains necessary for identity-based decisions.
D=Perimeter replaces firewalls: a perimeter controls Google API access, not traffic between VMs or to the internet, so firewall rules and policies stay in place.
E=Metadata always blocked: the service controls data movement and may still expose some metadata in certain scenarios, so a design must not assume none leaks.
T: Perimeter plus IAM, with explicit ingress/egress rules between perimeters; it does not replace IAM or firewalls.
V: VPC Service Controls, IAM

@ GCP-PCA D3 T3.1 applied use-case
S: A group of 300 projects across several folders must use customer-managed encryption keys for Compute Engine disks, BigQuery datasets and Cloud Storage buckets. The security team wants keys to be created on demand in a central key project, with key administration separated from the developers, and developers and Terraform pipelines must not need Cloud KMS admin rights. Which design fits?
A: Pre-create a key ring and key for every service in every project, and give each team Cloud KMS Admin on its own keys so it can attach them
B: Use Cloud KMS Autokey with dedicated-project key storage: each folder's Autokey config names the central key project, and keys appear as developers create resources
C: Keep Google-managed encryption for all services and rely on a single shared key in the central project for the few datasets that auditors ask about
D: Create one Cloud KMS key in the central project and share it with all 300 projects so key administration stays in one place
K: B
G: ## Autokey: CMEK without handing out KMS admin
**CMEK** means encrypting a service's data with a Cloud KMS key you control. The manual process is slow: someone plans key rings, creates keys, grants each service agent the encrypt/decrypt role, and developers wait.
**Cloud KMS Autokey** automates that. An administrator enables an **Autokey config** on a folder (or project). When a developer creates a protected resource, a **key handle** triggers on-demand creation of a key in the designated **key project**, and service agents get the needed roles.
- Developers need only the permissions in the default roles that create resources, which supports least privilege and Terraform pipelines.
- Keys follow recommended practice for protection level, rotation, location and specificity, and key administrators keep full control and visibility.
- Google calls it the recommended choice when its keys meet your requirements.
W: Autokey with dedicated key project: keys appear on demand in the central project, key administration stays with the security team, and developers and pipelines do not need KMS admin rights.
X: A=Pre-created keys per project: this is the slow manual model, and it gives each team Cloud KMS Admin, which breaks the separation between key administration and key use.
C=Google-managed encryption: the requirement is CMEK for all three services. A single key for a few datasets would not meet it for 300 projects.
D=One shared key: one key for every project and service makes blast radius and rotation coupled, and removes key specificity. Autokey creates appropriately specific keys.
T: Many projects, CMEK, separation of duties, no KMS admin for developers → Cloud KMS Autokey with a central key project.
V: Cloud KMS, Autokey, CMEK

@ GCP-PCA D3 T3.1 advanced tradeoff
S: KnightMotives Automotive has suffered past data breaches and must meet EU data protection rules for its new data management platform. Its security team wants the guarantee that no new Compute Engine disk, BigQuery dataset or Cloud Storage bucket in the organization can be created without a customer-managed key, and that the keys can only come from the central key project. Which TWO organization policy settings meet this? (Select TWO)
A: Set the constraint gcp.restrictNonCmekServices on the organization, listing the services that must always use CMEK for newly created resources
B: Set the constraint gcp.restrictCmekCryptoKeyProjects on the organization, allowing only the central key project as source of CMEK keys
C: Grant the Organization Policy Administrator role to every project owner so each team can enforce encryption on its own projects
D: Set gcp.restrictCmekCryptoKeyProjects to deny the central key project, so that Cloud KMS keys become unusable from any project of the organization
E: Enable Data Access audit logs on Cloud KMS, which blocks resource creation whenever no key is specified
K: A,B
G: ## Two org policy constraints for CMEK
Organization policies are guardrails inherited down the hierarchy. For encryption keys Google Cloud offers two constraints:
- `constraints/gcp.restrictNonCmekServices` **requires** CMEK: listed services refuse to create resources without a customer-managed key.
- `constraints/gcp.restrictCmekCryptoKeyProjects` **limits** which projects may supply those keys.
Both apply only to newly created resources of supported services, so existing resources need separate remediation.
W: A=Require CMEK: the first constraint makes the listed services reject creation without a CMEK key, which covers disks, datasets and buckets.
B=Limit key projects: the second constraint allows only keys from the central key project, which is the "keys only from there" requirement.
X: C=Policy admin for everyone: delegating the ability to set or relax policies to project owners defeats a guardrail that should be controlled centrally.
D=Deny the key project: this reverses the intent by blocking the project that is supposed to hold the keys.
E=Audit logs block creation: logs record activity, they do not enforce anything or reject a request.
T: Require CMEK with gcp.restrictNonCmekServices, restrict key origin with gcp.restrictCmekCryptoKeyProjects, set at the organization.
V: Organization Policy, Cloud KMS

@ GCP-PCA D3 T3.1 advanced comparison
S: A European insurer's regulator requires that encryption keys for its core claims data stay outside the cloud provider's infrastructure under the insurer's own custody, and that the insurer can make the data unreadable at any moment by withdrawing key access. The workloads run on Google Cloud services that support CMEK. Which key design meets this?
A: Cloud KMS software keys in a key ring in the same region as the data, with automatic rotation, a separate administrator group and disabled key export
B: Cloud HSM keys in the same region, whose key material lives in hardware security modules that Google operates for the insurer
C: Cloud External Key Manager (Cloud EKM) keys held in a partner's external key manager, with Google's access granted by the insurer and revocable
D: Customer-supplied encryption keys sent in each API request, which makes every client application responsible for key transport
K: C
G: ## Where does the key material live
- **Software keys** and **Cloud HSM keys** live in Google's infrastructure; Cloud HSM protects them in hardware modules. You control permissions, not the physical location of the material.
- **Cloud EKM** keeps the key material in an external key manager that you manage outside Google Cloud. Cloud KMS refers to the external key; Google cannot use it unless you grant access, and you can revoke that access at any time. If the key becomes unavailable, operations that need it fail.
## The trade-off
Control costs availability: the external manager is now in the critical path for the data, and if you lose keys you manage outside Google Cloud, Google cannot recover the data.
W: Cloud EKM: the key stays in the insurer's external key manager, access can be withdrawn at will, and encrypted data becomes unreadable until it is restored, which matches the two regulator requirements.
X: A=Software keys in Cloud KMS: strong control over permissions, but the key material is inside Google Cloud, so the "outside the provider" requirement is not met.
B=Cloud HSM: hardware protection raises assurance, but Google operates the HSMs and the key stays in Google's infrastructure.
D=Customer-supplied keys: this model exists only for a few services and puts keys in every request; it is not the CMEK pattern the services need, and it adds operational burden without an external manager.
T: Key must stay outside Google and be revocable → Cloud EKM; accept that availability of the external manager becomes a dependency.
V: Cloud KMS, Cloud EKM, Cloud HSM

@ GCP-PCA D3 T3.1 applied use-case
S: Two firms want to pool sensitive customer records for joint fraud analysis on Compute Engine VMs. Each firm already encrypts data at rest and in transit, but a firm's risk team worries that an administrator of the hypervisor or a compromised host could read the data while it is being processed in memory. Which design addresses that specific risk?
A: Move the analysis to Confidential VMs, which keep data encrypted in memory and isolate it from the host and hypervisor
B: Add a second layer of customer-managed encryption keys to the persistent disks that hold the records
C: Enable VPC Flow Logs on the subnets so that any unexpected host access to the VMs is recorded for review
D: Require TLS 1.3 between the two firms' systems and restrict connections with firewall rules to the partner's IP ranges
K: A
G: ## Three states of data
Data at rest (disks, buckets) and data in transit (TLS) are covered by standard encryption. **Data in use**, while the CPU processes it in memory, is the third state.
**Confidential VMs** use hardware-based confidential computing to keep memory contents encrypted and isolated from the host and hypervisor, so even privileged infrastructure software cannot read them. The workload usually needs no code changes.
W: Confidential VMs: they address data in use by encrypting VM memory and isolating it from the hypervisor, which is the exact threat.
X: B=Extra disk keys: this strengthens data at rest. The records are decrypted in memory during processing, so the hypervisor risk remains.
C=Flow logs: logs observe network flows and detect, but they neither prevent nor see memory access by a host.
D=TLS and firewalls: they protect data in transit between the firms, not data inside a VM's memory.
T: At rest, in transit, in use: only confidential computing (Confidential VMs) protects memory from the host.
V: Confidential VM, Compute Engine

@ GCP-PCA D3 T3.1 applied use-case
S: Cymbal Retail is moving its web catalog services and batch integrations to GKE and Cloud Run. Today the MySQL and Redis passwords sit in container environment files and in config repositories, and nobody can say who has read them. The security team wants central storage, per-service access, an access trail, and the ability to rotate credentials without rebuilding images. Which design fits?
A: Store the credentials in Secret Manager, grant each workload's service account access to only its own secrets, and read the current version at runtime
B: Encrypt the environment files with a Cloud KMS key and commit the encrypted files, so that only holders of decrypt rights can read them
C: Keep the passwords in Kubernetes Secrets in each cluster, and give platform engineers the cluster-admin role to rotate them
D: Move the passwords into a private Cloud Storage bucket with uniform bucket-level access, mount the bucket into each container as a file system, and rely on object versioning for rotation history
K: A
G: ## Secret Manager as the source of truth
**Secret Manager** stores API keys, passwords and certificates as versioned secrets with IAM on each secret.
- **Per-secret IAM**: the Secret Manager Secret Accessor role is granted to the one service account that needs it.
- **Versions**: add a new version for rotation; workloads that read the latest version pick it up without a rebuild.
- **Audit**: access can be written to Data Access audit logs, answering who read what.
This replaces credentials embedded in images, repositories or environment files, which are copied to every place the file goes.
W: Secret Manager: central, versioned storage with per-secret access for each workload identity, auditable access, and rotation by adding a new version.
X: B=Encrypted files in a repository: it protects the file at rest but spreads copies of the secret, offers no per-secret access trail, and rotation still means new commits and releases.
C=Kubernetes Secrets in each cluster: duplicated per cluster, readable by anyone with cluster-wide access, and unified rotation and audit across clusters and Cloud Run would be missing.
D=Bucket of password files: a general object store is not a secrets manager; it lacks versioned secret semantics and secret-level access trails, and file mounting exposes the values broadly.
T: Credentials shared by many services → Secret Manager with per-secret IAM, versions for rotation and audit logs.
V: Secret Manager, GKE, Cloud Run

@ GCP-PCA D3 T3.1 advanced use-case
S: A company encrypts its data warehouse with a key in a dedicated key project. The auditor asks for a design in which no single group can both manage keys and use them to decrypt data. Which TWO assignments achieve this? (Select TWO)
A: Grant the security team's key administrators Cloud KMS Admin on the key project, a role that manages keys but cannot encrypt or decrypt with them
B: Grant the data engineers Cloud KMS Admin on the key ring so they can rotate and disable keys as they ingest data
C: Grant the BigQuery service agent the Cloud KMS CryptoKey Encrypter/Decrypter role on only the key it protects
D: Grant the security team's key administrators Cloud KMS CryptoKey Encrypter/Decrypter on all keys so they can verify that rotation works
E: Grant every data engineer Owner on the key project so any incident can be resolved without waiting for the security team
K: A,C
G: ## Key administration and key use are different permissions
Cloud KMS separates **managing** a key (create, rotate, disable, set IAM) from **using** it (encrypt, decrypt). The Cloud KMS Admin role manages keys but has no encrypt or decrypt permission. The CryptoKey Encrypter/Decrypter role allows use but not management.
A common design keeps keys in a **separate key project** owned by the security team; the service agent of each data service gets the use role on exactly the key it needs. Access is granted at the key or key ring, not on key versions.
W: A=Key admins manage only: the security team administers the keys without being able to decrypt data, which satisfies the separation.
C=Service agent uses only: the service decrypts at runtime with narrow, per-key rights, and no human principal needs the use role.
X: B=Data engineers as key admins: the people who handle the data would also control the key lifecycle, and they could disable or destroy keys.
D=Admins also decrypt: giving key administrators the use role removes the separation the auditor requires.
E=Owner for everyone: Owner contains both management and use permissions, which defeats separation of duties.
T: Separation of duties: KMS Admin for security team, Encrypter/Decrypter for the service agent only, in a dedicated key project.
V: Cloud KMS, IAM

@ GCP-PCA D3 T3.1 advanced use-case
S: EHR Healthcare must be able to answer, for each medical office tenant, who read patient files stored in Cloud Storage and when. Today only the default audit logs exist. The logs must be tamper-resistant and viewable by the security team but not by the engineers who operate the platform. Which design meets this?
A: Rely on Admin Activity audit logs, which already record every read of a patient file, and route them to the engineers' project for convenience
B: Enable Data Access audit logs for Cloud Storage on the folder, and route them with an aggregated sink to a locked log bucket in a separate security project
C: Enable VPC Flow Logs on the clusters, which record the object names and users for each file read through the Cloud Storage API
D: Enable Data Access audit logs only on the platform projects, and store them in the log bucket of each project, so that each engineering team can review its own access
K: B
G: ## Which audit logs exist by default
Cloud Audit Logs has several types. **Admin Activity** logs (configuration changes) are always on. **Data Access** logs record reads of resource data and metadata, and they are disabled by default except for some BigQuery services, so they must be turned on explicitly for Cloud Storage.
## Making them trustworthy
- Configure them at the organization or folder so new projects are included.
- Route them with an **aggregated sink** to a log bucket in a separate security project, with IAM that excludes the people whose actions are logged. Retention can be locked so the logs cannot be shortened.
W: Data Access logs plus aggregated sink to a locked bucket: reads of objects become auditable, and logs live outside the engineers' reach, so they cannot alter their own trail.
X: A=Admin Activity only: they cover configuration changes, not object reads, and putting logs in the engineers' project exposes them to the people being audited.
C=VPC Flow Logs: flow logs record network flows between IPs; they do not identify the user or the object read through the Cloud Storage API.
D=Per-project review by engineers: the logs would sit in projects the engineers control, which allows tampering and violates the separation requirement.
T: Reads need Data Access logs enabled; make them tamper-resistant with an aggregated sink to a restricted, locked security project.
V: Cloud Audit Logs, Cloud Logging, Cloud Storage

@ GCP-PCA D3 T3.1 advanced tradeoff
S: A company blocks creation of service account keys across the organization with an organization policy, but one legacy folder runs a vendor product that cannot yet use keyless authentication. The exception must be limited to that folder, with every other folder staying blocked. What is the right design?
A: Set the policy at the organization to enforce the restriction, and override it with a policy on the legacy folder that does not enforce it
B: Remove the policy from the organization and set it separately on each of the other folders, so the legacy folder simply has none
C: Keep the policy enforced everywhere and grant the vendor's service account the Organization Policy Administrator role so that it can create its own keys
D: Enforce the policy at the organization and create an IAM deny policy on the legacy folder that allows key creation for the vendor's account
K: A
G: ## Inheritance and overrides in Organization Policy
An organization policy attached to a node applies to all descendants. A policy set on a lower node can **override** or merge with an inherited one, depending on the constraint type and settings, so you can set a strict default high up and carve out one exception.
- Setting policy at the organization gives new folders and projects the guardrail automatically.
- Removing it and re-applying per folder risks gaps for each new folder.
- Organization policies restrict what resources may be configured; they are different from IAM, which grants or denies principals.
W: Override on the legacy folder: the organization-level policy covers everyone, including future folders, while the one folder that needs an exception states it explicitly.
X: B=Per-folder policies: every future folder would start unprotected until someone remembers to add the policy, which inverts the safe default.
C=Policy Administrator for the vendor: that role lets the holder change constraints, not just create keys, and gives an external product control over guardrails.
D=Deny policy to allow: IAM deny policies only block permissions. They cannot allow what an organization policy forbids.
T: Strict organization-level default, explicit override on the single exception folder; never invert it.
V: Organization Policy, IAM

@ GCP-PCA D3 T3.1 advanced use-case
S: A platform team grants project owners broad rights to run their own environments. The CISO now wants a rule that nobody, including project owners and organization administrators, can delete the central audit log buckets or disable log sinks, except a small break-glass group. Allow policies on thousands of projects are managed by many teams. Which control is the most robust?
A: Add an IAM deny policy at the organization that denies those logging permissions to everyone, with the break-glass group as an exception
B: Remove the logging roles from every project owner by editing each project's allow policy in turn, and have a script re-check all of the policies each month
C: Create a custom role named logging-readonly and ask teams to use it instead of the basic roles
D: Set an organization policy constraint that forbids owners from signing in to the Google Cloud console outside business hours
K: A
G: ## Deny policies as guardrails
IAM **allow policies** grant roles; with many teams editing them, any project owner can re-grant access. IAM **deny policies** set guardrails that override allow: a deny rule names principals, the permissions they cannot use, an optional condition, and exceptions. Deny is evaluated before allow, and it can be attached to the organization, a folder or a project so all descendants inherit it.
Using exception principals lets a break-glass group keep access without weakening the rule for everybody else.
W: Org-level deny with exception: it applies to every project regardless of what local allow policies say, and the break-glass group keeps the ability to act in an emergency.
X: B=Edit each allow policy: owners can re-grant themselves roles, and a monthly check leaves long windows of exposure across thousands of projects.
C=Custom read-only role: it only helps for principals who adopt it voluntarily, and does nothing about existing owners who already hold broader roles.
D=Console sign-in constraint: organization policy constraints govern resource configuration, not when users sign in, and API access would remain open.
T: Non-negotiable "nobody may" rules across the organization → IAM deny policy at the org, with exception principals for break-glass.
V: IAM deny policies, Cloud Logging

@ GCP-PCA D3 T3.1 advanced use-case
S: EHR Healthcare is moving several Kubernetes environments to Google Cloud and wants a central rule that SSH and RDP from the internet are denied on every VM network in the organization, with no project administrator able to override it. Application teams still need to define their own allow rules for service ports. Which design applies?
A: Create a hierarchical firewall policy at the organization with a deny rule for SSH and RDP from the internet and goto_next for all other traffic
B: Create VPC firewall rules in each project that deny the SSH and RDP ports, and publish the standard rule in a runbook for teams to copy
C: Create a global network firewall policy in one shared project and attach it to the networks of that project, then ask the other teams to copy the same rules
D: Place a Cloud NAT gateway in front of each network so that inbound SSH and RDP can never reach a VM from the internet
K: A
G: ## Hierarchical firewall policies
**Hierarchical firewall policies** attach to the organization or folders. Their rules are evaluated before VPC-level rules, top down through the hierarchy. Lower-level rules cannot override a rule from a higher level.
- An organization-level rule can **deny** or **allow** a connection definitively.
- A **goto_next** action hands evaluation to the next level, so folders and VPC firewall rules (set by app teams) decide everything else.
That gives the security team the mandatory deny and the application teams their own freedom.
W: Organization hierarchical policy: the deny is inherited by all networks and cannot be removed by project administrators, while goto_next leaves everything else to local rules.
X: B=Per-project VPC rules: each administrator can edit or delete the copy, so the rule is not enforced and depends on convention.
