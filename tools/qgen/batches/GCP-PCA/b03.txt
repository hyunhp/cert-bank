@ GCP-PCA D1 T1.3 advanced tradeoff
S: Altostrat Media must move large volumes of newly recorded audio and video from legacy on-premises ingestion systems into Cloud Storage every day. Reliability is a top priority, the transfers must not cross the public internet, and the team wants predictable throughput for sustained bulk traffic. Which connectivity design best fits?
A: A Dedicated Interconnect topology with redundant connections in two metropolitan areas, so that ingestion keeps running if one path or one metro is lost
B: A single Dedicated Interconnect connection in one metro with a Classic VPN tunnel as the backup path, so that the redundant path stays cheap to run
C: One HA VPN gateway pair over the public internet, with Cloud Router sharing routes, so that encryption is the only protection the traffic needs
D: Direct Peering with Google at an edge location, so that the ingestion servers reach the Cloud Storage buckets over private IP addresses
K: A
G: ## Choosing hybrid connectivity
Google Cloud offers several ways to link an on-premises network to a VPC network. The choice is driven by throughput, latency stability, availability target and whether traffic may use the public internet.
- **HA VPN** builds IPsec tunnels over the public internet. It is quick to set up and encrypted, but throughput per tunnel is limited and latency varies with internet conditions.
- **Dedicated Interconnect** is a physical connection between your network and Google's at a colocation facility. Traffic stays off the internet and capacity is dedicated, which suits sustained bulk transfers.
- **Partner Interconnect** reaches Google through a service provider when you cannot be in a Google colocation facility.
## Availability is a topology decision
Interconnect availability depends on how many connections you order and where they sit. The documented 99.99% (critical production) pattern uses at least four Dedicated Interconnect connections: two in one metro and two in another, with the pair in each metro placed in different edge availability domains. Maintenance windows are coordinated inside one metro but not across metros, so a two-metro design keeps one path alive.
W: Dedicated Interconnect with redundancy across two metros: it keeps the daily bulk ingest off the public internet, gives dedicated capacity for sustained traffic, and follows the topology that carries the highest availability level, which matches the stated reliability priority.
X: B=Single connection plus Classic VPN: one connection in one metro is a single point of failure and does not follow any Interconnect availability topology. A VPN backup over the internet cannot carry the same bulk volume, so a failure would degrade ingestion badly.
C=HA VPN over the internet: it is encrypted, but the traffic still crosses the public internet and per-tunnel throughput is limited, which conflicts with the requirement and with predictable sustained bulk transfers.
D=Direct Peering: it exchanges public traffic with Google's edge for Google public services and is not a private connection to your VPC network. It carries no Interconnect SLA and is not the recommended design for production hybrid traffic.
T: Sustained, private, reliable hybrid traffic means Dedicated (or Partner) Interconnect, and the availability level comes from a redundant multi-metro topology rather than from a single link.

@ GCP-PCA D1 T1.3 advanced comparison
S: A retail group has about forty product teams, each in its own project. A central network team must own subnets, routes and firewall rules, while product teams only deploy workloads into approved subnets. All workloads must talk to each other over internal IP addresses. Which design fits?
A: Shared VPC with a host project owned by the network team and each product project attached as a service project
B: VPC Network Peering between every pair of product-team VPC networks, with each team writing its own firewall rules
C: One VPC network per project joined by Cloud VPN tunnels, with the network team reviewing every team's tunnel settings
D: A single project for all teams, with Identity and Access Management roles limited to the instances each team creates
K: A
G: ## Shared VPC versus peering
- **Shared VPC** lets an organization connect resources from several projects to one VPC network in a host project. Service projects use subnets of that network, and the network administration (subnets, routes, firewall rules) stays with the host project's administrators. Workload owners get only permission to use specific subnets.
- **VPC Network Peering** connects two separate VPC networks so they exchange routes privately. Each network keeps its own administration, peering is not transitive, and subnet ranges must not overlap.
Peering is a good fit when different organizations or independently run networks must connect. Shared VPC is the fit when one organization wants central network control with delegated workload deployment.
W: Shared VPC: the host project concentrates subnets, routes and firewalls under the network team, service projects attach to it and use internal IP addresses on the same network, which is the separation of duties described.
X: B=Pairwise peering: with forty networks this is a mesh of hundreds of non-transitive peerings, each team would administer its own firewall rules, and ranges would have to be kept non-overlapping. That is the opposite of central control.
C=VPN between projects: tunnels between VPC networks inside one organization add cost and failure points, and every team still controls its own network, so the central team cannot own subnets and firewall rules.
D=Single project: it removes the project boundary that product teams, billing and quotas rely on, and IAM on individual instances does not give the network team separate control of subnets and firewall rules.
T: One organization, central network ownership, many workload projects: use Shared VPC; use peering to link independently administered networks.

@ GCP-PCA D1 T1.3 advanced comparison
S: A software vendor hosts a managed analytics service in its own VPC network on Google Cloud. Hundreds of customers, each with its own VPC network, must consume it privately. Many customer networks use overlapping private ranges, and the vendor does not want customers to reach anything except the service. Which TWO design points fit this requirement? (Select TWO)
A: Publish the service behind an internal load balancer through a Private Service Connect service attachment
B: Have each customer create a Private Service Connect endpoint with an internal IP address from its own VPC network
C: Create a VPC Network Peering connection from the vendor network to every customer network
D: Merge the vendor and all customer subnets into one Shared VPC network owned by the vendor
E: Give the service an external IP address and let each customer allowlist the vendor's firewall rules
K: A,B
G: ## Service-oriented private access
Private Service Connect (PSC) lets a service producer host a service in its own VPC network and offer it to consumers through a service attachment. A consumer creates an endpoint, which is an internal IP address in the consumer's own VPC network that forwards traffic to the producer's service.
- Traffic stays on Google's network and consumers use their own internal addresses.
- Access is service-to-service: the consumer reaches the published service, not the producer's network.
- Consumer and producer networks do not need to coordinate IP ranges, so overlapping ranges are not a problem.
VPC Network Peering and Shared VPC, in contrast, make whole networks reachable and need non-overlapping address plans.
W: A=Service attachment: publishing the service behind an internal load balancer with a PSC service attachment is how a producer exposes it to many consumers while keeping its VPC network private.
B=Consumer endpoint: each customer gets an internal IP address in its own range that reaches the service, so overlapping customer ranges never meet and nothing else in the vendor network is reachable.
X: C=Peering with every customer: peering exchanges routes between whole networks and requires non-overlapping ranges, which the customers do not guarantee, and it opens network-level reachability instead of one service.
D=One Shared VPC network: customers are separate organizations with their own networks, and putting everyone in one network would expose workloads to each other and force a single address plan.
E=External IP address: it takes the traffic off the private path the customers asked for, and allowlisting by firewall rules does not provide private consumption through their own VPC networks.
T: To expose one service privately to many consumers with possibly overlapping ranges, publish it with Private Service Connect rather than connecting whole networks.

@ GCP-PCA D1 T1.3 advanced use-case
S: A manufacturer has four plants, each with its own site network connected to Google Cloud by Cloud Interconnect or HA VPN, and a VPC network holds shared services. The plants also need to exchange data with each other, and the team wants to use the Google network for this instead of buying a separate private WAN. Which approach fits?
A: Network Connectivity Center as a hub, with each plant's hybrid connection attached as a spoke and site-to-site data transfer enabled
B: A full mesh of VPC Network Peering connections between each plant's VPC network and every other plant's network
C: Cloud NAT gateways in each region so that plants translate their addresses and reach each other through the internet
D: A Private Service Connect endpoint in every plant, so that each site publishes its whole network as a service
K: A
G: ## Using Google's network as a site-to-site backbone
Network Connectivity Center (NCC) is a hub-and-spoke service for managing network connectivity. You create a hub, then attach spokes such as VLAN attachments (Cloud Interconnect), HA VPN tunnels, router appliances or VPC networks. With site-to-site data transfer, on-premises sites attached as spokes can exchange traffic through Google's network, not just reach the VPC network.
This replaces a mesh of point-to-point links with one central hub and keeps routing manageable as sites are added.
## What does not fit
Peering joins VPC networks, not physical sites. Cloud NAT lets resources without external IP addresses make outbound connections; it is not a way to link sites. Private Service Connect publishes services, not entire site networks.
W: Network Connectivity Center: the hub treats each plant's Interconnect or VPN connection as a spoke and, with site-to-site data transfer, carries plant-to-plant traffic over Google's network, which replaces a separate WAN.
X: B=Peering mesh: peering connects VPC networks and is not transitive, so it cannot link the physical plant networks to each other, and a mesh grows quadratically.
C=Cloud NAT: it provides outbound address translation for private resources in a VPC network. It does not route between on-premises sites and would not use the Google backbone as a WAN.
D=PSC endpoints: Private Service Connect exposes individual services, not whole site networks, and it is not a general routing fabric between plants.
T: Many on-premises sites that should talk through Google's backbone use a Network Connectivity Center hub with the hybrid connections as spokes.

@ GCP-PCA D1 T1.3 advanced use-case
S: Altostrat Media stores a huge, growing archive of audio and video in Cloud Storage. Some episodes become popular years later, so access is unpredictable, and the team does not want to maintain lifecycle rules that guess which objects are cold. Storage cost must fall without lowering availability. Which design fits best?
A: A bucket with Autoclass enabled, which moves each object between storage classes automatically according to how it is accessed
B: A bucket in the Archive storage class, so that every object gets the lowest storage price regardless of how it is read
C: Lifecycle rules that move every object to Coldline after 30 days, so that cost falls on a fixed and predictable schedule
D: A Filestore instance mounted on the editing servers, so that frequently read files stay on high-performance disks
K: A
G: ## Matching storage class to access pattern
Cloud Storage classes trade lower storage price against higher retrieval cost and minimum storage durations (Standard, Nearline, Coldline, Archive).
- **Lifecycle rules** move or delete objects on age or other conditions you define. They work well when access patterns are predictable.
- **Autoclass** automatically transitions objects to colder classes when they are not accessed, and moves objects that are read back to Standard to optimize future accesses. It removes the need to predict access, and for objects handled by Autoclass it avoids retrieval fees tied to manual class changes.
The class of a bucket does not change availability by itself: availability follows the bucket location (region, dual-region or multi-region).
W: Autoclass: access patterns are unpredictable, so letting the service move objects to colder classes when idle and back to Standard when read lowers cost without hand-tuned rules, and the bucket location keeps its availability.
X: B=Archive for everything: it has the lowest storage price but the highest retrieval cost and a long minimum duration, which is costly for archive items that suddenly become popular.
C=Fixed Coldline rule: a 30-day age rule assumes content cools down. Episodes that become popular later would stay in a class with retrieval fees and minimum durations, which is the guess the team wants to avoid.
D=Filestore: it provides managed NFS file shares on provisioned capacity, which costs more per GB than object storage and is not a storage-cost reduction for a large media archive.
T: Unpredictable object access plus cost goals points to Cloud Storage Autoclass; use lifecycle rules when the access pattern is known.

@ GCP-PCA D1 T1.3 advanced tradeoff
S: A financial reporting service stores regulatory documents in Cloud Storage. Compliance requires that data stay in two specific European regions, the application must keep working without any path changes if one region fails, and the recovery point objective for new writes should be short and predictable. Which bucket design fits?
A: A dual-region bucket in the two required regions, with turbo replication turned on
B: A multi-region bucket in the EU location, because it spreads objects across several European regions
C: A regional bucket in one required region, with a nightly copy job to a regional bucket in the second region
D: A regional bucket plus Object Versioning, so that earlier versions of objects can be restored after a failure
K: A
G: ## Bucket location types
- **Regional**: data stored in one region; lowest cost, no cross-region protection by itself.
- **Dual-region**: data stored redundantly in a specific pair of regions you choose. It gives higher availability than a region, asynchronous replication, and automatic failover and failback with no change to storage paths (RTO of zero as documented).
- **Multi-region**: data spread over a large geographic area (such as the EU) with locations chosen by Google, which you cannot restrict to two named regions.
Replication between the dual-region pair is asynchronous. Turbo replication is a premium option that targets replication of new objects within 15 minutes for a short, predictable RPO.
W: Dual-region with turbo replication: the two named regions satisfy the residency rule, failover needs no path changes, and turbo replication gives the short predictable recovery point.
X: B=EU multi-region: Google chooses the locations inside the EU, so the data may not stay in the two specific regions that compliance requires, and turbo replication is a dual-region feature.
C=Nightly copy: a custom job leaves up to a day of data at risk and failover needs the application to switch bucket names, so neither the RPO nor the no-path-change requirement is met.
D=Regional with versioning: versioning protects against overwrites and deletes inside one region. It does not protect against the loss of that region or keep the application running.
T: Two named regions plus automatic failover and a short RPO means a dual-region bucket with turbo replication; multi-region does not let you pick the regions.

@ GCP-PCA D1 T1.3 advanced tradeoff
S: A growing software-as-a-service team runs its customer data on SQL Server on premises and wants to move to Google Cloud with the lowest administration effort. The application uses T-SQL features and needs a high-availability setup with automatic failover inside one region, but does not need global writes or horizontal scaling beyond a single primary. Which database choice fits?
A: Cloud SQL for SQL Server with a high availability configuration, which fails over to a standby in another zone
B: Spanner, because it replicates across regions and removes the need to think about the database engine
C: Bigtable, because it scales writes by adding nodes and removes the need for a relational schema
D: SQL Server on Compute Engine VMs in a managed instance group, so that the team controls the operating system
K: A
G: ## Choosing a database service by workload
- **Cloud SQL** is a managed relational service for MySQL, PostgreSQL and SQL Server. Google handles patching, backups and failover; a high availability (HA) configuration keeps a standby in another zone of the region and fails over automatically.
- **AlloyDB** is a managed PostgreSQL-compatible service for demanding transactional and analytical workloads.
- **Spanner** is a horizontally scalable relational database with strong consistency across regions; it uses GoogleSQL or PostgreSQL dialects, not T-SQL, so applications need changes.
- **Bigtable** is a wide-column NoSQL store for very high throughput key-based access, not relational queries.
- **Compute Engine VMs** give full control but you own patching, backups and failover.
The deciding facts here are engine compatibility, zonal fail-over in a region and minimal operations.
W: Cloud SQL for SQL Server with HA: it keeps the SQL Server engine and T-SQL, automates backups, patching and zonal failover, and cuts administration compared with self-managed VMs.
X: B=Spanner: it is built for global scale and multi-region writes that the workload does not need, and the application would need to be rewritten from T-SQL, adding migration effort.
C=Bigtable: it is a NoSQL wide-column store without relational joins or T-SQL, so the application would need a full redesign.
D=Self-managed SQL Server on VMs: it works technically but leaves patching, backups and fail-over setup with the team, which contradicts the lowest-administration goal.
T: Keep the engine and cut operations with Cloud SQL; pick Spanner only when you need horizontal scale or global consistency.

@ GCP-PCA D1 T1.3 advanced definition
S: A global ticketing platform stores orders in a relational schema and must accept writes from users in North America, Europe and Asia at the same time. Orders need strong consistency and ACID transactions across regions, and the platform must keep serving during a regional outage without manual failover. Which database fits?
A: Spanner in a multi-region configuration, which provides strongly consistent transactions across regions with synchronous replication
B: Cloud SQL for PostgreSQL with cross-region read replicas, which serve reads close to users while one primary takes the writes
C: Bigtable with multi-cluster replication, which keeps clusters in several regions eventually consistent with one another
D: Firestore in Datastore mode with one regional location, which scales automatically for key-based reads and writes
K: A
G: ## Where relational databases stop scaling
Most relational services have a single writable primary. Cloud SQL scales reads with replicas, but all writes go to the primary in one region, so users far from it see higher latency and a regional outage needs a failover or promotion.
**Spanner** is designed for this problem: it is relational, offers SQL and ACID transactions, and splits data across servers. In multi-region configurations it replicates synchronously across regions with strong consistency, and it keeps serving when a region is lost without manual intervention.
**Bigtable** replicates asynchronously between clusters (eventual consistency) and has no multi-row relational transactions. **Firestore** is a document database.
W: Spanner multi-region: it combines a relational model with ACID transactions, accepts writes in several regions and fails over automatically, which is the full set of requirements.
X: B=Cloud SQL with cross-region replicas: replicas are read-only copies, so all writes still travel to one primary, and promotion after a regional outage is a manual or scripted step.
C=Bigtable replication: replication between clusters is eventually consistent and Bigtable offers no relational schema or cross-row ACID transactions for orders.
D=Single-region Firestore: one regional location does not survive a regional outage, and a document store does not match the relational schema.
T: Relational plus multi-region writes plus strong consistency plus automatic failover is Spanner's niche.

@ GCP-PCA D1 T1.3 advanced use-case
S: An automotive supplier collects sensor readings from millions of connected devices, each sending a small record every second. The team needs single-digit-millisecond lookups by device and time range, sustained write rates in the hundreds of thousands per second and no complex joins. Which storage service fits?
A: Bigtable, with a row key that starts with the device identifier and ends with a time component
B: Cloud SQL for MySQL, with one table per device and an index on the timestamp column
C: Cloud Storage Standard, with one object per reading and a prefix per device
D: Memorystore for Redis, holding all readings in memory with a persistence snapshot
K: A
G: ## Wide-column storage for time series
**Bigtable** is a managed wide-column NoSQL database built for very high read and write throughput with low latency. Data is sorted by row key, so key design is the main design decision. A row key that starts with a device identifier and adds a timestamp keeps a device's readings together for range scans, and spreads load across devices.
Services such as Cloud SQL scale vertically around a single primary and do not sustain this write volume cheaply. Cloud Storage is an object store without millisecond lookups of small records, and Memorystore is an in-memory cache whose capacity is bounded by memory.
W: Bigtable: it handles sustained very high write throughput and millisecond lookups, and a device-then-time row key supports the per-device time-range queries.
X: B=Cloud SQL: relational features are not needed, and a single writable primary cannot comfortably absorb hundreds of thousands of writes per second for millions of devices.
C=Cloud Storage objects: one object per reading would create billions of tiny objects and would not support millisecond range lookups over readings.
D=Memorystore: holding the entire telemetry history in memory is expensive and bounded by instance size, and a cache is not a system of record for years of readings.
T: High-throughput, key-and-time-range access without joins is the Bigtable pattern; design the row key around the query.

@ GCP-PCA D1 T1.3 advanced troubleshooting
S: A team lifts and shifts a legacy application to Compute Engine. The application expects a shared POSIX file system mounted by several VMs, uses file locking and cannot be changed. The first design stored the files in a Cloud Storage bucket, but the application fails on file semantics. What is the best storage design?
A: A Filestore instance, exported as an NFS share and mounted by all application VMs
B: A Cloud Storage bucket mounted through Cloud Storage FUSE, with the application writing files in place
C: A single Persistent Disk attached read-write to every VM in the instance group
D: Local SSD on each VM, with a scheduled rsync job copying files between the machines
K: A
G: ## Object, file and block storage
- **Object storage** (Cloud Storage) stores immutable objects accessed through APIs. Cloud Storage FUSE can mount a bucket as a file system, but it does not provide full POSIX semantics, so applications that rely on in-place edits and locking can behave differently.
- **File storage** (Filestore) offers managed NFS shares with POSIX file semantics that many VMs mount at the same time.
- **Block storage** (Persistent Disk, Hyperdisk, Local SSD) attaches to VMs. Standard disks are normally read-write on one VM; read-write multi-attach is limited to specific disk types and needs a cluster-aware file system.
An application that cannot change and needs shared file semantics points to managed NFS.
W: Filestore: it exports a shared NFS file system with POSIX semantics, so all VMs see the same files and locks without changing the application.
X: B=Cloud Storage FUSE: it makes a bucket look like a directory but does not offer full POSIX behavior such as in-place edits and locking, so the same failures would likely continue.
C=One Persistent Disk on every VM: a standard disk cannot be attached read-write to many instances, and a regular file system on it would corrupt without cluster-aware coordination.
D=Local SSD with rsync: each VM would have its own copy, so writes made on one machine appear later on others and locks do not span machines. The data is also lost when the VM stops.
T: Shared POSIX files with locking for unchanged applications mean managed NFS (Filestore), not object storage.

S: Altostrat Media needs a small piece of code that runs whenever a new video lands in a Cloud Storage bucket. It extracts metadata and writes it to the warehouse, runs for a few seconds per file, and the team wants no servers or clusters to operate and no cost while idle. Which compute choice fits?
A: Cloud Run functions triggered by the bucket event
B: A GKE Standard cluster with a Deployment that polls the bucket every minute
C: Compute Engine VMs in a managed instance group that scale on CPU utilization
D: A Cloud Run job scheduled hourly by Cloud Scheduler, regardless of when files arrive
K: A
G: ## Matching compute to workload shape
- **Cloud Run functions** run single-purpose code in response to events (a Cloud Storage object change, a Pub/Sub message, an HTTP call). You provide the function; Google runs the infrastructure and scales, including to zero.
- **Cloud Run** runs any stateless container as a service or job, also scaling to zero, when you need a custom runtime or an entire web application.
- **GKE** runs Kubernetes for complex, multi-service platforms that need cluster-level control.
- **Compute Engine** gives VMs and OS-level control.
The more of the stack the platform runs, the less to operate. A short event-triggered task with no idle cost is the textbook serverless-function case.
W: Cloud Run functions: the bucket event invokes the code directly, the platform scales it and charges nothing while idle, and nobody operates servers.
X: B=GKE polling: a cluster means node pools and Deployments to manage and nodes run while idle, plus polling adds latency and wasteful requests for a simple event reaction.
C=Instance group: VMs have to be patched and run while idle, and CPU-based scaling does not react to storage events.
D=Hourly Cloud Run job: it is serverless, but it does not react to each upload, so metadata appears up to an hour late and the job needs its own logic to find new files.
T: Short, event-driven, idle-most-of-the-time tasks fit Cloud Run functions; move up to Cloud Run, GKE or VMs only when you need more control.

@ GCP-PCA D1 T1.3 advanced use-case
S: KnightMotives builds a simulation environment to test autonomous-driving software. Thousands of independent simulation runs, each lasting minutes, are queued in batches overnight. A failed run can simply be restarted, and the team wants the lowest compute cost. Which compute choice fits?
A: Spot VMs in a managed instance group or a batch service, with jobs written to restart when a VM is preempted
B: Standard on-demand VMs sized for peak load and kept running around the clock, so that no run is ever interrupted
C: Sole-tenant nodes reserved for the simulation project, so that other customers never share the hardware
D: A single very large VM running all simulations in sequence, so that only one machine ever needs patching
K: A
G: ## Spot VMs and fault-tolerant work
Spot VMs are excess Compute Engine capacity sold at a large discount. In exchange, Compute Engine can preempt (stop or delete) them at any time, they carry no SLA and availability varies. They suit workloads that tolerate interruption, such as batch processing, rendering, simulation and CI jobs.
Design rules for using them well:
- Make jobs short and idempotent, or checkpoint progress, so a preempted run restarts.
- Use a managed instance group or a batch scheduler so replacements are created automatically.
- Allow several machine types so capacity is easier to find.
Stateful or latency-critical services should not run only on Spot VMs.
W: Spot VMs with restartable jobs: the simulations are independent and restartable, so preemption only slows a run, and the discount gives the lowest cost for overnight batch capacity.
X: B=On-demand VMs at peak size: they avoid interruption that the workload tolerates anyway, and running at peak all day wastes money on idle capacity.
C=Sole-tenant nodes: they isolate hardware for licensing or compliance needs, which are not stated here, and they cost more rather than less.
D=One large VM in sequence: it serializes thousands of runs into a very long job, creates a single point of failure and does not take advantage of parallelism.
T: Fault-tolerant, restartable batch work belongs on Spot VMs; keep SLA-bound or stateful services on standard VMs.

@ GCP-PCA D1 T1.3 advanced tradeoff
S: A team moves a legacy application to Compute Engine. The vendor says it needs 6 vCPUs and 40 GB of memory; none of the predefined machine types matches closely, and the memory-heavy sizing would waste money on unused vCPUs. The workload will run for several years at steady load. Which TWO actions reduce cost best? (Select TWO)
A: Create a VM with a custom machine type that has the exact vCPU and memory ratio the vendor needs
B: Buy resource-based or flexible committed use discounts for the steady, predictable usage
C: Run the application only on Spot VMs, since a long-running legacy application restarts cleanly
D: Select the largest predefined memory-optimized machine type to leave headroom for future growth
E: Place the VM in a dual-region location to reduce its hourly price through regional pricing
K: A,B
G: ## Right-size, then commit
Cost optimization for steady compute follows two steps.
1. **Right-size the shape.** Predefined machine types come in fixed vCPU-to-memory ratios. A **custom machine type** lets you pick the vCPU count and memory amount within allowed ratios for supported machine series, so you pay for what the application needs.
2. **Commit for predictable usage.** Committed use discounts trade a one-year or three-year commitment for lower prices on usage you will certainly consume.
Spot VMs suit interruptible work. Oversizing for growth wastes money because you can resize later.
W: A=Custom machine type: exact vCPU and memory sizing avoids paying for a larger predefined shape the legacy application cannot use fully.
B=Committed use discounts: the application runs steadily for years, so committing to that baseline usage lowers the price compared with on-demand.
X: C=All Spot VMs: a legacy application with long-running state is likely to be interrupted at an unpredictable time, and Spot VMs carry no SLA, so this trades reliability for savings.
D=Largest memory-optimized type: it pays for much more capacity than needed today; growth can be handled by resizing the VM later.
E=Dual-region location: dual-region is a Cloud Storage bucket location, not a Compute Engine placement, and it has no effect on VM prices.
T: For steady workloads, right-size with custom machine types and commit to the baseline; keep Spot for interruptible batch work.

@ GCP-PCA D1 T1.3 advanced troubleshooting
S: EHR Healthcare must ingest claims and clinical updates from new provider partners. Which processing design fits?
A: Pub/Sub to receive events, a streaming Dataflow pipeline to transform them, and BigQuery as the destination
B: A Managed Service for Apache Spark cluster that is created manually each morning and sized for the expected peak
C: A nightly batch export of all partner files to Cloud Storage, followed by a scheduled BigQuery load job
D: Compute Engine VMs running a self-written consumer, with a fixed number of instances behind a load balancer

G: ## Streaming ingestion on Google Cloud
A common streaming architecture has three parts.
- **Pub/Sub** decouples producers from consumers. Publishers send messages to a topic and it absorbs bursts.
- **Dataflow** is a fully managed service for Apache Beam pipelines (batch and streaming). It autoscales workers and handles windowing, retries and exactly-once-style processing semantics so you do not size a cluster.
- **BigQuery** is the analytics warehouse; streaming inserts or the Storage Write API make rows queryable in seconds.
**Managed Service for Apache Spark** (formerly Dataproc) fits when you already have Spark or Hadoop jobs to migrate. For new continuous pipelines without cluster management, Pub/Sub plus Dataflow is the managed answer.
W: Pub/Sub, Dataflow and BigQuery: the topic absorbs unpredictable spikes, autoscaling Dataflow transforms events within seconds without cluster sizing, and BigQuery stores the results for analytics.
X: B=Daily Spark cluster: the cluster is sized by hand for an expected peak, so unpredictable spikes either overload it or waste capacity, and it does not deliver results within seconds.
C=Nightly batch load: results would be up to a day late, which conflicts with the within-seconds processing goal.
D=Self-written consumers on VMs: a fixed instance count cannot follow spikes, and the team would own scaling, retries and deduplication that Dataflow provides.
T: Continuous, spiky event data with no cluster to manage maps to Pub/Sub plus Dataflow into BigQuery; use Spark services mainly for existing Spark code.

@ GCP-PCA D1 T1.3 advanced tradeoff
S: Altostrat Media wants a 24/7 support chat assistant that answers viewer questions using only the company's own program guides and policies, cites the source of each answer, and does not invent shows that do not exist. Which TWO design choices fit this goal? (Select TWO)
A: Build the assistant with Conversational Agents or an agent on the Agent Platform, using a foundation model such as Gemini
B: Ground the model's answers in the company's documents using a managed retrieval-augmented generation setup, such as Agent Search over the guides
C: Fine-tune a model once on a snapshot of the guides and expect it to know every later schedule change

K: A,B
G: ## Grounding reduces hallucination
Foundation models generate plausible text from patterns learned in training; they do not know a company's current catalog and can invent details (hallucinate). **Grounding** supplies trusted data at answer time: the system retrieves relevant passages from your own documents (retrieval-augmented generation, RAG) and the model answers from them, often with citations.
On Google Cloud, you can assemble this from managed parts: a foundation model from the Gemini Enterprise Agent Platform or Model Garden, Agent Search for retrieval over your content, and Conversational Agents or an agent runtime for the chat interface.

W: A=Conversational agent on a foundation model: a managed agent with Gemini provides the 24/7 natural-language chat without building model infrastructure.
B=Grounding in company documents: retrieval over the program guides makes answers rely on current, owned content and supports source citations, which limits invented shows.
X: C=One-time fine-tuning: the knowledge freezes at the snapshot date, so schedule changes are missing, and fine-tuned models still do not provide reliable citations.
D=No grounding and high temperature: higher randomness increases the chance of invented content, the opposite of the requirement.
E=Training from scratch: it needs enormous data, accelerators and time, and a custom model would still need grounding to stay current.
T: To keep a gen AI assistant factual, use a managed foundation model with grounding in your own content (RAG); do not rely on fine-tuning or training from scratch for facts.

@ GCP-PCA D1 T1.3 advanced definition
S: A company runs batch analytics on private Compute Engine VMs and on-premises servers. G: ## Reaching Google APIs privately
- **Private Google Access** lets VM instances in a subnet that have only internal IP addresses reach the external IP addresses of Google APIs and services.
- **Private Google Access for on-premises hosts** lets on-premises systems, with or without external IPs, reach Google APIs through a Cloud VPN tunnel or Cloud Interconnect VLAN attachment by using special Private Google Access domains and virtual IPs, with DNS and routes pointing to them.

C=Per-server VPN tunnels: tunnels terminate on a Cloud VPN gateway for a VPC network, not on a Cloud Storage endpoint, and per-server tunnels would be unmanageable.
D=Peering with an API network: VPC Network Peering connects VPC networks and there is no peering to Google's API network that provides this access.
