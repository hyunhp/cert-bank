@ GCP-PCA D1 T1.1 advanced use-case
S: A logistics company spends a steady amount on compute every hour across Compute Engine in three regions, a GKE cluster and a few Cloud Run services. Over the next year it will move several VM fleets from N2 to C4 machines and shift some services from VMs to Cloud Run. Finance wants a three-year discount on the steady baseline that will not be stranded when machine series, regions or services change. Which commitment approach is MOST cost-effective under these constraints?
A: Purchase a compute flexible committed use discount sized to the steady hourly spend, so the discount follows eligible usage across regions, machine series and Cloud Run
B: Purchase resource-based hardware commitments for N2 vCPUs and memory in each of the three regions, sized to today's VM fleets, and renew them as C4 when migration finishes
C: Run the whole steady baseline on Spot VMs and add standard VMs only when Spot capacity is preempted, accepting brief interruptions to keep the hourly spend as low as possible
D: Avoid commitments for three years and rely only on automatic discounts for long-running VMs, because any commitment would lock the company into its current machine series
K: A
G: ## Two kinds of committed use discounts
Compute Engine offers two commitment models:
- **Resource-based (hardware) commitments**: you commit to an amount of vCPUs, memory, GPUs or Local SSD of a specific machine series **in one region**. They give the deepest discount but are bound to that series and region.
- **Compute flexible CUDs**: spend-based. You commit to a minimum **hourly spend**. For Compute Engine, they apply across the Cloud Billing account "regardless of the project or region", across many machine series (N2, C4, E2 and others), and also to GKE and Cloud Run spend.
## Choosing
When the baseline is steady in money but its shape will change (new machine series, new regions, VMs moving to serverless), a spend-based flexible commitment keeps receiving the discount after each change. A hardware commitment would keep billing for N2 resources the company no longer uses.
W: Compute flexible CUD: it commits to hourly spend rather than to a machine series or region, and it covers Compute Engine, GKE and Cloud Run, so the planned N2-to-C4 and VM-to-Cloud Run moves keep consuming the commitment.
X: B=Regional N2 hardware commitments: they are tied to N2 resources in each region; after the move to C4 and Cloud Run they keep billing for capacity that is no longer used, until the term ends.
C=Spot baseline: Spot VMs can be preempted at any time and do not cover Cloud Run or steady GKE services; interruptions on the production baseline are not a cost decision finance can make alone.
D=No commitment: it avoids lock-in but gives up the commitment discount on spend that is known to be steady for three years, so it is not the most cost-effective choice.
T: For a steady spend whose machine series, region or service will change, choose a compute flexible (spend-based) CUD over resource-based commitments.
V: Compute Engine, GKE, Cloud Run, committed use discounts

@ GCP-PCA D1 T1.1 advanced tradeoff
S: An insurer is moving a MySQL 8.4 claims database to Cloud SQL. Its contract with hospitals promises 99.99% monthly availability and explicitly counts planned maintenance as downtime. The application team will not change the schema or rewrite queries, and the operations team is small, so a managed service is required. Which design meets the contractual availability target with the LEAST change to the application?
A: Cloud SQL Enterprise edition with high availability and a maintenance window set to Sunday night, so that the published availability target covers all remaining hours of the month
B: Cloud SQL Enterprise Plus edition with high availability, whose published 99.99% availability SLA includes maintenance, keeping MySQL so the schema and queries stay as they are
C: Spanner in a regional configuration with a 99.99% availability SLA, migrating the schema and queries to Spanner's GoogleSQL dialect to remove the maintenance downtime
D: Self-managed MySQL on two Compute Engine VMs in different zones with synchronous replication, so that the team decides itself when patches and restarts are applied
K: B
G: ## Cloud SQL editions and their SLA
Cloud SQL for MySQL comes in two editions. The editions page states the availability SLA of each:
- **Enterprise Plus**: **99.99%, including maintenance**. It also adds near-zero downtime planned maintenance and advanced disaster recovery.
- **Enterprise**: **99.95%, excluding maintenance**.
A maintenance window only chooses *when* maintenance happens; with the Enterprise edition those minutes are still outside the SLA, and the edition's target is 99.95% anyway.
## Reading the constraints
The contract counts maintenance as downtime and asks for 99.99%. The team will not change schema or queries (so MySQL stays) and wants a managed service. Enterprise Plus with HA meets all three.
W: Enterprise Plus with HA: it is the Cloud SQL edition whose 99.99% SLA includes maintenance, and it keeps the MySQL engine, so the contract target is met with no application change.
X: A=Enterprise with a maintenance window: the edition's SLA is 99.95% and excludes maintenance, so neither the number nor the maintenance clause of the contract is covered.
C=Regional Spanner: its 99.99% SLA would fit, but moving to Spanner means schema and query changes, which the application team refused.
D=Self-managed MySQL on VMs: no managed SLA backs the database, and the small operations team would own replication, failover and patching.
T: When planned maintenance counts as downtime, Cloud SQL Enterprise Plus (99.99% including maintenance) is the managed MySQL choice; Enterprise is 99.95% excluding maintenance.
V: Cloud SQL

@ GCP-PCA D1 T1.2 advanced use-case
S: A payments company runs its MySQL ledger on a Cloud SQL Enterprise Plus primary in europe-west1 with high availability. A new continuity plan requires recovery in europe-west4 within minutes if europe-west1 fails, without editing connection strings in about 40 services, and a return to europe-west1 afterwards with no data loss. The design should rely on built-in Cloud SQL features rather than custom scripts. Which TWO design elements meet these requirements? (Select TWO)
A: Designate a cross-region read replica in europe-west4 as the DR replica, so a replica failover promotes it and a later switchover restores the original roles
B: Point every service at the write endpoint, a DNS name that Cloud SQL moves to the new primary after a replica failover or switchover
C: Enable high availability with the standby placed in another zone of europe-west1, so that the standby takes over automatically if the region becomes unavailable
D: Schedule automated backups to a multi-region location and restore the latest backup in europe-west4 during a regional outage, then rebuild the primary later by hand
E: Store the primary's IP address in a Cloud DNS private zone and run a script after an outage that updates the record and recreates replicas in the original region
K: A,B
G: ## Advanced disaster recovery in Cloud SQL Enterprise Plus
Cloud SQL Enterprise Plus adds **advanced DR**:
- You designate a cross-region read replica as the **DR replica**.
- During a regional outage you run a **replica failover**: the DR replica becomes primary immediately. When the old primary comes back, it stays in the replication topology and becomes a replica of the new primary.
- A **switchover** then returns the deployment to its original roles **with zero data loss**: the current primary goes read-only until the DR replica has caught up.
## The write endpoint
A **write endpoint** is a global DNS name that always resolves to the current primary. Cloud SQL updates it after a replica failover or switchover, so applications that connect by that name need no connection-string changes. Without it, applications must be pointed at the new primary's IP.
W: A=Designated DR replica: replica failover recovers in europe-west4 within minutes, and switchover brings the primary back to europe-west1 with no data loss, as the plan requires.
B=Write endpoint: the 40 services use a DNS name that Cloud SQL repoints to whichever instance is primary, so no connection string is edited during failover or fallback.
X: C=HA standby in the same region: HA protects against a zone failure only; the standby is in europe-west1 and is lost with the region.
D=Backup restore in europe-west4: restoring a backup takes far longer than minutes, loses changes since the backup, and the fallback has to be rebuilt by hand.
E=Script-updated private DNS: it re-creates by hand what the write endpoint does, adds a fragile runbook step, and recreating replicas is not a zero-data-loss fallback.
T: Cloud SQL Enterprise Plus advanced DR = designated DR replica (replica failover, then switchover back) plus the write endpoint so apps never change connection strings.
V: Cloud SQL, Cloud DNS

@ GCP-PCA D1 T1.2 advanced use-case
S: A ride-sharing company stores driver location profiles in Bigtable, read and written with single-digit millisecond latency by services in us-east1. The business now requires that reads and writes continue automatically if the us-east1 cluster becomes unavailable, with no operator action, and accepts that a write may take a short time to appear in other regions. Which design meets the availability requirement with the LEAST operational effort?
A: Add a cluster in us-central1 to the instance and give the services an app profile with single-cluster routing to us-east1, failing over by editing the profile during outages
B: Export the table to Cloud Storage every hour with a scheduled job and import it into a standby instance in us-central1 when the primary cluster becomes unavailable
C: Add a cluster in us-central1 and give the services an app profile with multi-cluster routing, which sends traffic to the nearest available cluster automatically
D: Keep one cluster but turn on autoscaling for its nodes, so that the cluster adds nodes and keeps serving when zones in us-east1 fail or load rises suddenly
K: C
G: ## Bigtable replication and routing
A Bigtable instance can hold clusters in several zones or regions; data written to one cluster is replicated to the others. Replication normally gives **eventual consistency**.
**App profiles** decide where a client's requests go:
- **Single-cluster routing** sends everything to one cluster. If that cluster is unavailable you must **fail over manually**. It is the only policy that allows single-row transactions and can give read-your-writes consistency.
- **Multi-cluster routing** sends each request to the nearest available cluster and **fails over automatically**. It gives eventual consistency.
## Reading the stem
"No operator action" rules out manual failover. "A write may take a short time to appear elsewhere" accepts eventual consistency. Multi-cluster routing over two regional clusters fits both.
W: Second cluster plus multi-cluster routing: replication keeps the us-central1 cluster current, and the app profile moves traffic to it automatically when us-east1 is unavailable, with the eventual consistency the business accepted.
X: A=Single-cluster routing: the second cluster holds the data, but failover means editing the app profile during the outage, which breaks the no-operator-action rule.
B=Hourly export and import: recovery needs a manual import, takes long for a large table and can lose up to an hour of writes.
D=Autoscaling one cluster: it adds nodes for load, but a single cluster lives in one zone and cannot protect against the loss of the cluster or the region.
T: For automatic Bigtable failover across regions, use a replicated instance with a multi-cluster routing app profile (eventual consistency).
V: Bigtable

@ GCP-PCA D1 T1.2 advanced use-case
S: A booking service runs as stateless containers on Cloud Run in us-central1, and its data is already in a multi-region database. Users in North America and Europe should reach the nearest healthy deployment through one public IP address and one certificate, and traffic must move to the other region automatically if one region's service fails. The team wants no VMs to manage. Which design meets these requirements?
A: Deploy the service in us-central1 and europe-west1, add a serverless NEG for each region to one backend service, and front it with a global external Application Load Balancer
B: Deploy the service in us-central1 and europe-west1, put a regional external Application Load Balancer in front of each, and publish both IP addresses as round-robin DNS records
C: Keep one deployment in us-central1, raise its maximum number of instances, and enable Cloud CDN on a global external Application Load Balancer to serve European users from cache
D: Deploy the service in both regions behind proxy-based NGINX VMs in a managed instance group per region, and send users to the VMs with a geolocation DNS routing policy
K: A
G: ## Multi-region serverless behind one anycast IP
A **global external Application Load Balancer** runs on Google Front Ends, exposes a **global anycast IP address** and can reach **backends in multiple regions**. Cloud Run services join a backend service through **serverless network endpoint groups (NEGs)**, one per region.
The load balancer sends each user to the closest region with healthy capacity; if one region's service fails, requests go to the other region. One certificate is attached to the load balancer.
## What the alternatives miss
- A **regional** external Application Load Balancer serves from one region only.
- Round-robin DNS has no health awareness: clients keep resolving and using a failed region's address.
- Cloud CDN caches cacheable responses; it does not make a dynamic booking API multi-region.
W: Two regions, serverless NEGs, global external ALB: one anycast IP and certificate, nearest-region routing and automatic failover between regions, with Cloud Run and no VMs to manage.
X: B=Regional load balancers plus round-robin DNS: two IP addresses, and DNS keeps sending users to a failed region because it does not check backend health.
C=Single region with Cloud CDN: dynamic booking requests still go to us-central1, and a regional failure takes the whole service down.
D=NGINX VMs with geolocation DNS: it adds VM fleets to patch and scale, which the team wants to avoid, and uses separate addresses instead of one anycast IP.
T: Cloud Run in several regions behind one global external Application Load Balancer with serverless NEGs gives one IP, nearest-region routing and regional failover.
V: Cloud Run, Cloud Load Balancing

@ GCP-PCA D1 T1.3 advanced comparison
S: A media group has 30 VPC networks in different projects, one per business unit, and every unit must reach every other unit's private services. Today the networks are joined by a growing web of VPC Network Peering connections that a two-person network team maintains by hand. Units must be able to choose which subnets they share. Which design reduces the operational effort MOST while keeping full private connectivity?
A: Replace the peerings with HA VPN tunnels between each pair of VPC networks, so that every unit controls its own routes through Cloud Router advertisements
B: Merge all business units into one Shared VPC host project, delete the unit networks and recreate every workload in subnets of the central host network
C: Keep the peerings but add a central hub VPC peered to all 30 networks, so that traffic between units passes through the hub without further peering
D: Attach each VPC network as a VPC spoke to one Network Connectivity Center hub, exporting only the subnet ranges each unit chooses to share
K: D
G: ## Inter-VPC connectivity at scale
**VPC Network Peering** connects two networks at a time and is **not transitive**: A peered with B and B peered with C does not let A reach C. A full mesh of n networks needs n(n-1)/2 peerings (435 for 30 networks).
**Network Connectivity Center (NCC) VPC spokes** replace pair-wise peerings with a hub: every VPC spoke exports its subnet routes to the hub and imports the others', which gives full connectivity between all spokes. The docs list these advantages over peering: centralized management, and control over which IPv4 and IPv6 subnet routes each spoke exports. Spokes can be in other projects or organizations.
W: NCC hub with VPC spokes: one attachment per network gives full mesh connectivity with central management, and export filters let each unit share only the subnets it chooses.
X: A=Pair-wise HA VPN: it still needs a connection for every pair, now with tunnels, gateways and BGP sessions, which raises the effort instead of lowering it.
B=One Shared VPC: it would centralize the network, but recreating all workloads is a large migration and removes each unit's own network.
C=Peered hub VPC: peering is not transitive, so units peered only to the hub still cannot reach each other.
T: For many VPC networks that all need each other, use NCC VPC spokes on one hub instead of a non-transitive peering mesh.
V: Network Connectivity Center, VPC

@ GCP-PCA D1 T1.3 advanced use-case

The team has no Kubernetes experience and no job scheduler it wants to keep, and finance asks for the lowest compute cost. Results must be ready by the start of the next working day. Which approach meets these needs with the LEAST operational overhead?
A: Build a GKE Standard cluster with a Spot node pool and a Kubernetes job controller, and train the team to operate node upgrades and cluster autoscaling
B: Submit the tasks as a Batch job that runs on Spot VMs with automatic task retries, letting Batch provision and delete the VMs for each run
C: Create a managed instance group of standard VMs sized for the full nightly load and run an open source scheduler on a separate always-on controller VM
D: Run each task as a Cloud Run functions invocation triggered by a Pub/Sub message, so that capacity scales to zero between the nightly runs

No Kubernetes skills, no scheduler to keep, lowest cost, restartable multi-hour tasks: Batch on Spot VMs with retries matches each point.
W: Batch on Spot VMs with retries: Batch provisions and removes the VMs, Spot lowers cost, and retries rerun preempted tasks from their checkpoints, with nothing for the team to operate.

D=Cloud Run functions: a single invocation cannot run for two to four hours with 16 vCPUs, so the tasks do not fit the function model.

@ GCP-PCA D1 T1.3 advanced comparison
S: A retailer needs about 2 Gbps of private connectivity from its data center to Google Cloud, and traffic must not cross the public internet. The data center has no presence in any colocation facility where Google meets customers, and the network team wants an availability SLA from Google without buying and operating its own equipment in a new facility. Which connectivity choice fits BEST?
A: Dedicated Interconnect with two 10-Gbps connections in a colocation facility near the data center, leased and cabled by the retailer's own network team
B: HA VPN over the internet with two tunnels to two on-premises VPN gateways, giving a 99.99% SLA with dynamic routing through Cloud Router
C: Partner Interconnect through a supported service provider, with redundant VLAN attachments in two edge availability domains of one metro for an SLA
D: Direct Peering at a Google edge location, exchanging routes with Google's network so that traffic reaches the VPC network without the public internet
K: C
G: ## Choosing a hybrid connection
- **Dedicated Interconnect**: physical connections between your router and Google in a **colocation facility**. You need equipment there, and connections are 10 or 100 Gbps.
- **Partner Interconnect**: a **supported service provider** connects your network to Google. Good when you are not in a Google colocation facility or need less than a full 10-Gbps connection. Redundant attachments in both edge availability domains of a metro give the 99.9% topology; four attachments across two metros give 99.99%.
- **HA VPN**: IPsec tunnels **over the internet**; 99.99% SLA with the right topology.
- **Direct Peering**: connects to Google's edge for Google Workspace and Google APIs; it is not a private path into VPC networks.
## Deciding constraint
"Not over the public internet" removes HA VPN; "no colocation presence, no new equipment" removes Dedicated Interconnect.
W: Partner Interconnect: a service provider supplies the private path from the existing data center, sized to about 2 Gbps, and redundant attachments in both edge availability domains qualify for an availability SLA.
X: A=Dedicated Interconnect: it needs the retailer's own equipment in a colocation facility and 10-Gbps connections, which is the effort the team wants to avoid.
B=HA VPN: it has a strong SLA, but its tunnels cross the public internet, which the requirement forbids.
D=Direct Peering: it reaches Google's public services at the edge, not private VPC addresses, so it does not provide private connectivity to workloads.
T: No colocation presence and no internet path means Partner Interconnect with redundant attachments.
V: Cloud Interconnect, Cloud VPN

@ GCP-PCA D1 T1.4 advanced tradeoff
S: A manufacturer will migrate 120 applications to Google Cloud over 9 months. The migration team is new to Google Cloud, the first production cutover is in 6 weeks, and leadership wants early proof that the landing zone, tooling and runbooks work before high-risk systems move. The ERP and plant-control systems have the most dependencies. How should the first migration wave be planned to reduce overall project risk MOST?
A: Move the ERP and plant-control systems first, because their dependencies are the hardest problem and finishing them early leaves easier work for later waves
B: Move all 120 applications in one coordinated weekend, so that cross-application dependencies never span the data center and Google Cloud at the same time
C: Start with a pilot wave of low-risk applications with few dependencies, then refine runbooks and tooling from its lessons before harder waves
D: Let each application team pick its own date and tool, since teams know their systems best and parallel moves finish the 120 applications sooner
K: C
G: ## Wave planning in a migration
Google's migration guidance plans work in **waves**: groups of workloads that move together. The first wave is usually a **pilot**: applications that are low in business risk, have few dependencies and are representative enough to exercise the landing zone, network, identity, migration tooling and cutover runbooks.
Lessons from the pilot (missing firewall rules, slow transfers, unclear rollback steps) are fixed before complex, dependent systems move. Systems with many dependencies are grouped with those dependencies in later waves, so that chatty components are not split across the data center and the cloud for long.
W: Low-risk pilot wave first: it proves the landing zone, tools and runbooks on systems where mistakes are cheap, which is what a new team needs before the ERP and plant systems move.
X: A=High-risk systems first: an inexperienced team would discover gaps in tooling and process on the systems with the most dependencies and the highest business impact.
B=Big-bang weekend: all risk lands in one event with no chance to learn, and a rollback of 120 applications at once is very hard.
D=Teams choose freely: uncoordinated dates and tools ignore dependencies between applications and give no shared, tested process.
T: Start a migration with a low-risk pilot wave to validate landing zone, tools and runbooks, then move dependent, critical systems in later waves.
V: Migration Center

@ GCP-PCA D1 T1.5 advanced use-case
S: A travel start-up launches a booking service in the United States only, using a relational schema with strong consistency. Its roadmap adds European and Asian customers in about 18 months, at which point reads must be fast in those regions and the database must survive a regional outage. The company wants to pay for a single region until then and avoid a second database migration later. Which choice BEST supports this roadmap?
A: Start on Spanner in a regional configuration and later move the instance to a multi-region one, which Spanner does without downtime
B: Start on Cloud SQL for PostgreSQL and add cross-region read replicas in Europe and Asia later, promoting one of them if the United States region fails
C: Start on Firestore in a single region and copy the data to a new multi-region Firestore database when international customers arrive in about 18 months
D: Start on Spanner directly in the largest multi-region configuration now, so that nothing has to change when the European and Asian launches happen
K: A
G: ## Planning a database for future growth
A Spanner instance has an **instance configuration**: regional, dual-region or multi-region. The Spanner docs state that you can **move an instance from any configuration to any other**, including from regional to multi-region, and that the move **does not cause downtime** while Spanner keeps its transaction guarantees and strong consistency.
So a team can start with a cheaper regional configuration and switch to multi-region (or a custom configuration with read-only replicas) when the business expands, without a migration to a new database product.
## Comparing paths
Cloud SQL cross-region replicas are asynchronous read replicas: promoting one is a manual failover with possible data loss, and writes stay in one region. Firestore cannot change the location of an existing database, so a later copy is a migration.
W: Regional Spanner now, move later: the company pays for one region today, and the documented instance move to a multi-region configuration adds global reads and regional resilience without downtime or a second migration.
X: B=Cloud SQL with later replicas: replicas are asynchronous and read-only; promoting one is a manual failover that can lose data, so the "survive a regional outage" target is weaker.
C=Firestore copied later: a new multi-region database means another data migration, which the company wants to avoid, and the relational schema does not fit Firestore.
D=Multi-region from day one: it works, but the company pays for multiple regions 18 months early, against its explicit cost wish.
T: Spanner can move an instance from a regional to a multi-region configuration without downtime, so start regional and grow later.
V: Spanner

@ GCP-PCA D2 T2.1 advanced troubleshooting
S: A hospital links its data center to Google Cloud with HA VPN. To save time, the engineer configured only interface 0 of the HA VPN gateway, with one tunnel to one on-premises router, and the link works. An audit now notes that the connection has no availability SLA, and the hospital needs 99.99% for its claims traffic without buying Cloud Interconnect. What should the architect change?
A: Replace the HA VPN gateway with a Classic VPN gateway using static routes, because Classic VPN gives the stronger SLA for single-tunnel topologies
B: Add a second tunnel on interface 0 to the same on-premises router, so that two tunnels share the single external IP address of the configured interface
C: Increase the tunnel's bandwidth by lowering the MTU and adding more BGP sessions on the existing Cloud Router, so that failover becomes faster
D: Use both interfaces of the HA VPN gateway with tunnels to the on-premises peer gateway devices, following an HA VPN topology documented for 99.99%
K: D
G: ## HA VPN and its SLA
An **HA VPN gateway** has **two interfaces**, each with its own external IP address from a separate pool. The Cloud VPN overview says HA VPN can provide **99.99% or 99.9%** depending on the topology, and that a gateway configured with **only one active interface and one external IP address provides no availability SLA**.
To reach 99.99%, you create tunnels from **both interfaces** to the peer gateway (for example, two on-premises routers or one router with two interfaces) as described in the HA VPN topologies page, with dynamic routing through Cloud Router.
**Classic VPN** offers 99.9% at most and uses static routing only.
W: Use both interfaces: tunnels from both HA VPN interfaces to the peer devices form a supported 99.99% topology, which a single active interface can never provide.
X: A=Classic VPN: its SLA is 99.9%, below the 99.99% the hospital needs, and it gives up dynamic routing.
B=Second tunnel on interface 0: both tunnels still depend on one interface and IP address, which is the configuration the docs say has no SLA.
C=MTU and BGP tuning: these change performance or convergence, not the topology on which the SLA depends.
T: HA VPN gets its 99.99% SLA only when both gateway interfaces carry tunnels to the peer; one active interface has no SLA.
V: Cloud VPN, Cloud Router

@ GCP-PCA D2 T2.1 advanced use-case
S: A German bank publishes a customer portal on Compute Engine in europe-west3. Its regulator requires that customer TLS sessions be terminated only in that region, so decrypted traffic is never handled elsewhere. The bank still wants a managed proxy load balancer with Cloud Armor and weighted traffic splitting for releases. Which load balancer meets the residency rule while keeping these features?
A: A global external Application Load Balancer with backends only in europe-west3, since the backend location decides where TLS sessions are terminated
B: A regional external Application Load Balancer in europe-west3, which terminates TLS and serves content in the configured region only
C: A classic Application Load Balancer in Premium Tier with backends in europe-west3, using a certificate map to keep TLS sessions inside Germany
D: An external passthrough Network Load Balancer in europe-west3, with TLS terminated on the backends and Cloud Armor applied at the forwarding rule
K: B

G: ## DORA metrics
Google Cloud's DevOps research (DORA) uses four key measures of software delivery performance:
- **Deployment frequency**: how often code reaches production.
- **Lead time for changes**: time from commit to running in production.
- **Change failure rate**: share of deployments that cause a failure in production.
- **Time to restore service**: how long it takes to recover from a failure.
The first two measure **speed (throughput)**, the last two **stability**. They come from pipeline and incident data, and they are comparable across teams because they measure outcomes rather than activity.
W: The four DORA metrics: two measure delivery speed and two measure stability, all from pipeline and incident records, which is exactly what the director asked to compare.
X: A=Commits, lines of code, story points, coverage: activity measures that vary by team and language and say nothing about stability in production.
C=CPU, spend, tickets, alert counts: operational and cost signals, not measures of delivery speed or change stability.
D=Approvals, meeting hours, manual tests: they measure process effort, often the overhead that automation was meant to remove.
T: Measure delivery performance with the four DORA metrics: deployment frequency, lead time, change failure rate and time to restore.
V: Cloud Build, Cloud Deploy

@ GCP-PCA D6 T6.6 advanced use-case
S: A ticket marketplace expects ten times its normal traffic at a launch in six weeks. Its architecture is Cloud Run, Memorystore and Cloud SQL, and a previous peak failed because a database connection limit and a project quota were hit at the same time. Leadership wants confidence that the launch peak will be handled, without risking the production database before the event. Which approach fits BEST?
A: Raise all autoscaling maximums to the highest allowed values in production and watch the dashboards on launch day, reacting to errors as they appear
B: Run a short load test against production during business hours, since only production has the real quotas and data volumes that matter for the launch
C: Test each service alone with unit and integration tests, since load problems appear only when individual components contain inefficient code
D: Load test a production-like environment at the expected peak, find limits such as connections and quotas, and request increases early
K: D
G: ## Load testing for a known peak
The reliability pillar recommends **testing for scale before peaks**: run load tests that reach the expected peak (and beyond) in an environment that **mirrors production** (same services, sizes, configuration, realistic data), observe where it breaks, and fix it before the event.
Typical findings are **limits outside the code**: database connection caps, per-project **quotas** for instances or API calls, connection pools and autoscaling maximums. Quota increases take time, so they are requested **well before** the event.
Testing in a production-like environment protects the real database and customers.
W: Production-like load test at peak: it reveals connection limits and quotas, like those that broke the last peak, early enough to request increases, without touching the production database.
X: A=Raise limits and watch: it discovers bottlenecks during the launch itself, and quotas cannot be raised instantly on launch day.
B=Load test production: it risks the production database and customers, which leadership explicitly ruled out.
C=Unit and integration tests only: they do not exercise connection limits, quotas or the system as a whole under load.
T: Before a known peak, load test a production-like environment at peak load and request quota and limit increases early.
V: Cloud Run, Cloud SQL, Memorystore
