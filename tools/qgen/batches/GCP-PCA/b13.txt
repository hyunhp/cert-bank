@ GCP-PCA D1 T1.1 expert tradeoff
S: Corvane Health sells a scheduling API to clinics with a contractual 99.9% monthly availability, and the contract counts planned maintenance as downtime. Every request passes through a global external Application Load Balancer (SLA 99.99%), a Cloud Run service in one region (SLA 99.95%) and a Cloud SQL for MySQL Enterprise edition instance with high availability (SLA 99.95%, excluding maintenance). Treat the SLAs as independent and the chain as serial; the Cloud Run service is stateless. The architect must close the gap with the smallest design change. Which change makes the composite design meet the contract?
A: Keep Cloud SQL Enterprise with high availability and deploy Cloud Run in a second region behind the same load balancer, so that the compute tier becomes redundant
B: Keep Cloud SQL Enterprise with high availability, set a weekend maintenance window and deny periods, so that maintenance falls outside the contract's busiest hours
C: Keep Cloud SQL Enterprise with high availability and add a cross-region read replica, so that reads continue from another region if the primary is unavailable
D: Upgrade the database to Cloud SQL Enterprise Plus with high availability, whose 99.99% SLA includes maintenance, and keep one Cloud Run region
K: D
G: ## Composite availability of a serial chain
When every request needs all components, the composite availability is the **product** of the parts.
- Today: 0.9999 x 0.9995 x 0.9995 = **0.99890**, about **99.89%**, already under 99.9%. Worse, the Enterprise edition SLA **excludes maintenance**, while the contract counts it, so the real exposure is larger than the number shows.
- With **Cloud SQL Enterprise Plus** (SLA **99.99% including maintenance**): 0.9999 x 0.9995 x 0.9999 = **0.99930**, about 99.93%, and maintenance is inside the SLA.
## Parallel redundancy and its limit
Two Cloud Run regions in parallel give 1 - (0.0005)^2, about 0.99999975, so on paper 0.9999 x 0.99999975 x 0.9995 is about 99.94%. But the database term still excludes maintenance; the weakest, uncovered link stays the database.
W: Enterprise Plus with HA: it lifts the database term to 99.99% with maintenance included, giving about 99.93% end to end, which meets the contract with one change.
X: A=Second Cloud Run region: the arithmetic improves, but the database SLA still excludes maintenance that the contract counts, so the gap where it matters remains.
B=Maintenance window and deny periods: they move maintenance in time but do not remove it, and the composite stays at about 99.89%.
C=Cross-region read replica: a read replica does not take writes, so the scheduling API still fails when the primary is down; the serial product is unchanged.
T: Multiply serial SLAs, and check what each SLA excludes: a component whose SLA omits maintenance cannot back a contract that counts it.
V: Cloud SQL, Cloud Run, Cloud Load Balancing

@ GCP-PCA D1 T1.2 expert use-case
S: Hallström Versicherung, a German insurer, runs its policy database on Spanner in the regional-europe-west3 configuration, created last year on the Standard edition. Its regulator now requires that all replicas, including any witness, stay in Germany, that the database survive the loss of an entire region with no committed data lost, and that failover need no manual promotion. Write traffic is a few thousand transactions per second, reads come mostly from Frankfurt and Berlin offices, and the team wants no application rewrite or second database product. Which change meets every requirement?
A: Move the instance to the eur6 multi-region configuration, whose read-write regions are the Netherlands and Frankfurt with an automatic witness in Zurich
B: Keep regional-europe-west3 and add a read-only replica in europe-west10 through a custom instance configuration, promoting it if Frankfurt becomes unavailable
C: Move the instance to the dual-region-germany1 configuration while staying on the Standard edition, because a move between configurations never changes the edition
D: Upgrade the instance to the Enterprise Plus edition and move it to the dual-region-germany1 configuration, whose replicas are all in Berlin and Frankfurt
K: D
G: ## Spanner configurations and residency
- **Regional**: replicas in zones of one region, 99.99% SLA. It cannot survive the loss of the region.
- **Multi-region** (for example `eur3`, `eur6`): two read-write regions plus a **witness region**; 99.999%. `eur6` uses the Netherlands and Frankfurt with a witness in **Zurich**, so data leaves Germany (and the EU).
- **Dual-region**: all replicas in **two regions of one country**, 99.999%. Spanner offers `dual-region-germany1` with **Berlin (`europe-west10`) and Frankfurt (`europe-west3`)**. Dual-region configurations are **available in the Enterprise Plus edition**.
Quorum replication means a committed write is already in both regions, so a regional loss loses no committed data and failover is automatic.
## Read-only replicas are not DR
Read-only replicas do not vote in write quorums and, per the docs, "don't function as a standalone disaster recovery (DR) solution".
## Moving
Spanner can move an instance to another configuration without downtime, so the application is not rewritten.
W: Enterprise Plus and dual-region-germany1: every replica stays in Berlin or Frankfurt, quorum writes survive a regional loss with no data lost and automatic failover, and the instance move needs no rewrite.
X: A=eur6: the witness in Zurich and the Netherlands region put replicas outside Germany, which the regulator forbids.
B=Read-only replica in europe-west10: it does not take part in write quorums and is not a DR solution, so a Frankfurt outage still stops writes.
C=dual-region-germany1 on Standard: dual-region configurations are offered in the Enterprise Plus edition; the detail that the instance runs Standard makes this move impossible as described.
T: For single-country residency with regional failover in Spanner, use a dual-region configuration (Enterprise Plus), not a multi-region with a foreign witness or a read-only replica.
V: Spanner

@ GCP-PCA D1 T1.2 expert tradeoff
S: Brightmoor Retail runs order processing on a managed instance group and Cloud SQL for PostgreSQL in us-east1. The continuity plan for a regional outage sets RTO 10 minutes and RPO 5 minutes at the lowest cost; serving 20% of normal capacity during the first hour is acceptable. Drills measured: cross-region replica lag below 40 seconds, replica promotion 2 minutes, a new VM ready to serve 9 minutes after creation, and a restore from the daily backup about 3 hours. The global load balancer already lists a backend in us-west1. Which DR design fits BEST?
A: Hot: run the full application in both regions behind the load balancer and move the database to a multi-writer design, so that either region serves all traffic
B: Warm: keep a cross-region replica and a small always-running autoscaled group in us-west1, so traffic shifts as soon as the replica is promoted
C: Cold with replica: keep a cross-region replica in us-west1 and an instance template, creating the group in us-west1 only after the outage is declared
D: Cold: keep only the daily backups in a multi-region location and an instance template, recreating both the database and the group in us-west1 after an outage
K: B
G: ## DR patterns: cold, warm, hot
Google's DR planning guide describes **cold** (recreate from backups or templates when needed), **warm** (a scaled-down copy running and receiving replicated data) and **hot** (full capacity running in both locations) patterns. Cost rises from cold to hot; recovery time falls.
## Working the numbers
- **Cold**: restore takes about 3 hours (RTO fails) and loses up to a day of data (RPO fails).
- **Cold with replica**: RPO is fine (lag < 40 s), but recovery is promotion 2 min + **9 min** for new VMs = **11 min > 10 min**.
- **Warm**: promotion 2 min; the small group already serves 20% of capacity through the existing backend, so recovery is about **2-3 minutes**, and autoscaling adds the rest. RPO < 1 min.
- **Hot**: meets both targets but runs double capacity and needs a database redesign; not the lowest cost.
W: Warm standby: the running small group and the replica give about 2-3 minutes of recovery and under a minute of data loss, meeting 10/5 minutes at much lower cost than hot.
X: A=Hot: it meets the targets but doubles running capacity and forces a multi-writer database redesign, so it is not the lowest-cost fit.
C=Cold with replica: the 9-minute VM start after a 2-minute promotion gives 11 minutes, just over the 10-minute RTO.
D=Cold from backups: a 3-hour restore and up to 24 hours of lost data miss both targets.
T: Pick the cheapest DR pattern whose measured recovery steps add up within RTO and whose replication lag fits RPO; one slow step can rule out cold.
V: Cloud SQL, Compute Engine, Cloud Load Balancing

@ GCP-PCA D1 T1.3 expert use-case
S: Ostrava Steel must copy 18 TB of plant data from its data center to Google Cloud every night inside a 6-hour window, and security forbids any path over the public internet. Only one metropolitan area with two colocation facilities is within reach, and the facilities offer both edge availability domains. The business requires the 99.99% Cloud Interconnect availability topology, and the nightly window must still be met if one connection fails. All workloads that receive the data run in the metro's low-latency region. Which Dedicated Interconnect design meets all requirements?
A: Two 10-Gbps connections, one in each edge availability domain of the metro, with two VLAN attachments on one Cloud Router in the metro's low-latency region
B: Four 10-Gbps connections in one facility and edge availability domain, with four VLAN attachments on two Cloud Routers in the metro's low-latency region
C: Four 10-Gbps connections, two in each facility and edge availability domain pair, with four VLAN attachments in the metro's low-latency region
D: Four 10-Gbps connections, two in each edge availability domain, with two VLAN attachments in the low-latency region and two in a distant second region
K: C
G: ## Bandwidth first
18 TB in 6 hours = 18 x 10^12 x 8 bits / 21,600 s, about **6.7 Gbps** sustained. One 10-Gbps connection could carry it, but the window must hold **with one connection down**, so at least two healthy connections are needed after a failure.
## The 99.99% single-metro topology
The Dedicated Interconnect guide allows 99.99% in **one region** when:
- there are **at least four connections**, two in each of a pair of **facility and edge availability domain** combinations in the metro (ordered through a connection group with the `PRODUCTION_CRITICAL` topology);
- there are **at least four VLAN attachments, all in one region**: the **low-latency region of the metro**, each on a unique connection;
- at least one Cloud Router in that region (more routers add no reliability).
Two connections in one metro give only the **99.9%** topology. A multi-region 99.99% topology needs connections in **two metros**, which the company does not have.
W: Four connections across both facility/domain combinations with four attachments in the low-latency region: it is the documented single-metro 99.99% topology, and three remaining connections still carry 6.7 Gbps after a failure.
X: A=Two connections: it matches the 99.9% topology only, and one failure leaves a single connection with no redundancy.
B=All four in one facility and domain: maintenance or failure of that domain removes every connection, so it does not qualify for 99.99%.
D=Attachments split into a distant region: the single-region topology needs all attachments in the metro's low-latency region, and a multi-region topology needs a second metro.
T: Single-metro 99.99% Dedicated Interconnect = four connections across two facility/edge-domain combinations and four VLAN attachments in the metro's low-latency region.
V: Cloud Interconnect, Cloud Router

@ GCP-PCA D1 T1.4 expert troubleshooting
S: Fenwick Logistics migrates a PostgreSQL database to Cloud SQL with a Database Migration Service continuous job over a 200-Mbps VPN that also carries other production traffic using about 140 Mbps from 08:00 to 18:00. During those hours the source writes about 45 GB of WAL per hour; at night it writes far less. Replication lag grows almost linearly every business day and shrinks overnight, while Cloud SQL CPU stays near 15%. Cutover must happen on a Thursday at 17:00 when store staff are on site. What should the architect do before cutover?
A: Raise the Cloud SQL instance to a larger machine type, so that the destination applies the replicated changes faster during business hours
B: Restart the migration job each morning with a fresh full dump, so that the day starts with zero lag and the 17:00 cutover finds the copy current
C: Raise the dump parallelism of the migration job, so that more connections pull changes from the source and the lag stops building up
D: Add bandwidth for replication, such as Cloud Interconnect or more VPN capacity, so the link carries over 100 Mbps of daytime changes
K: D
G: ## Change rate versus link capacity
45 GB per hour = 45 x 8 x 10^9 bits / 3,600 s = **100 Mbps** of change data in business hours. The VPN has 200 Mbps, of which other traffic uses about 140 Mbps, leaving **about 60 Mbps**. The job falls behind by about 40 Mbps every business hour:
- by 17:00 (9 hours) the backlog is about 40 Mbps x 32,400 s, roughly **1.3 Tb (about 160 GB)**;
- at night, with little traffic and few changes, it drains.
That matches the evidence: linear growth by day, shrinking at night, an idle destination. The bottleneck is the **network**, so destination size or job restarts do not help.
## Cutover needs lag near zero
Cutover stops writes and waits for the job to catch up. At Thursday 17:00 the backlog would take hours to drain, so the cutover window would be blown unless capacity for replication exceeds the change rate.
W: More bandwidth: once the path carries more than 100 Mbps for replication, the job keeps up during business hours and lag is near zero at 17:00.
X: A=Bigger Cloud SQL: the destination is idle at 15% CPU; it is waiting for data, not struggling to apply it.
B=Daily fresh dump: a full dump each morning adds more traffic on the same link, and changes during the day still outrun 60 Mbps.
C=More dump parallelism: parallelism speeds the initial load, but ongoing change data still has to cross a link with about 60 Mbps free.
T: Compare the source change rate with the bandwidth actually free for replication; if it is lower, migration lag grows no matter how large the target is.
V: Database Migration Service, Cloud SQL, Cloud VPN

@ GCP-PCA D2 T2.1 expert troubleshooting
S: Talvik Bank has four Dedicated Interconnect connections in two metros. VLAN attachments are two in us-east4 and two in us-central1, each region with its own Cloud Router, and the VPC network uses the regional dynamic routing mode. In a drill, both us-east4 attachments were disabled: VMs in us-central1 kept reaching the data center, but VMs in us-east4 lost all on-premises connectivity, and on-premises hosts could no longer reach us-east4 subnets. On-premises routers advertise the same prefixes on all four BGP sessions, and the drill must pass before the bank can claim the 99.99% topology. What should the architect change?
A: Add custom route advertisements for the us-east4 subnet ranges to the Cloud Router in us-central1, so that the data center learns a path to those subnets
B: Change the VPC network to the global dynamic routing mode, so that routes learned in each region are programmed in every region of the network
C: Add two more VLAN attachments in us-east4 on the existing connections, so that the region keeps attachments when two of them are disabled
D: Create static routes in us-east4 for the on-premises prefixes with the us-central1 Cloud Router as the next hop, so that traffic follows the other region
K: B
G: ## Dynamic routing mode
A VPC network's **dynamic routing mode** decides where Cloud Router routes apply:
- **Regional**: routes learned by a Cloud Router are programmed only in **its own region**, and the router advertises only subnets of its region.
- **Global**: learned routes are programmed in **all regions**, and routers can advertise subnets of all regions.
The 99.99% multi-region Dedicated Interconnect topology **requires global dynamic routing** "to ensure that Cloud Router learned routes are programmed as dynamic routes in all regions".
## The drill
With regional mode, us-east4 VMs had on-premises routes only from the us-east4 router. With its attachments down, they have no route out, and the us-central1 router never advertised us-east4 subnets. Global mode fixes both directions.
W: Global dynamic routing: us-east4 VMs get the routes learned in us-central1, and the us-central1 router can advertise us-east4 subnets, so failover works in both directions.
X: A=Custom advertisement on the us-central1 router: on-premises hosts would learn a path in, but us-east4 VMs still have no learned route back, so traffic fails one way.
C=More attachments in us-east4: they do not help when the region's attachments or its metro are lost, and the topology still depends on regional routing.
D=Static routes to a Cloud Router: a Cloud Router is not a valid next hop for static routes; dynamic routing mode is the documented fix.
T: Multi-region Interconnect failover needs the VPC in global dynamic routing mode; regional mode keeps learned routes inside each region.
V: Cloud Interconnect, Cloud Router, VPC

@ GCP-PCA D2 T2.1 expert use-case
S: Marisol Foods connects its data center to Google Cloud with HA VPN over the internet; two on-premises VPN devices exist so that each can be patched monthly. Peak traffic is 2.4 Gbps from Google Cloud and 0.6 Gbps toward it, with an average packet size of 1,000 bytes. Each Cloud VPN tunnel supports up to 250,000 packets per second for ingress plus egress combined. Peak traffic must flow without congestion even while one device is being patched. The bank's policy rules out Cloud Interconnect for this site until next year. Which design meets this requirement?
A: One HA VPN gateway with one tunnel from each interface to a different device, active/active with equal route priorities, so traffic is shared over both tunnels
B: One HA VPN gateway with both interfaces' tunnels to the same device, so that the second device is held in reserve and takes over during patching
C: One HA VPN gateway with one tunnel per interface, using a jumbo MTU on the tunnels, so that each tunnel carries more bytes in every packet sent
D: Two HA VPN gateways, each with one tunnel per interface to the two devices, giving two tunnels per device that share traffic with ECMP
K: D
G: ## Tunnel capacity is a packet budget
Each Cloud VPN tunnel supports **250,000 packets per second for ingress plus egress combined**, which is 1-3 Gbps depending on packet size.
- Peak = 2.4 + 0.6 = **3.0 Gbps** in both directions together.
- At 1,000-byte packets: 3.0 x 10^9 / (1,000 x 8) = **375,000 packets per second**.
- One tunnel: 250,000 pps, about **2 Gbps** at this packet size.
So at least **two tunnels** must carry traffic, and **two must remain** while one device is patched.
## Topology
With one gateway (two interfaces, one tunnel to each device), patching a device leaves **one** tunnel: 2 Gbps for 3 Gbps of traffic. Two HA VPN gateways (or more tunnels) give **two tunnels per device**; Cloud Router spreads traffic over tunnels with equal routes (ECMP), so with one device down two tunnels (about 4 Gbps) remain.
W: Two gateways, two tunnels per device: during patching two tunnels with about 4 Gbps of packet budget remain, above the 3 Gbps (375,000 pps) peak.
X: A=One tunnel per device: normal capacity is fine, but patching one device leaves one tunnel of about 2 Gbps for 3 Gbps of traffic.
B=Both tunnels to one device: patching that device drops both tunnels at once, and the idle device carries nothing until reconfigured.
C=Jumbo MTU: Cloud VPN tunnels do not carry jumbo frames, and the limit is in packets per second, so the patching case still has one tunnel.
T: Size Cloud VPN by packets per second (ingress plus egress, 250,000 per tunnel) and keep enough tunnels when a peer device is down.
V: Cloud VPN, Cloud Router

@ GCP-PCA D2 T2.2 expert use-case
S: Quillon Payments runs a Bigtable instance with clusters in us-east1 and us-west1. The card-serving service uses an app profile with multi-cluster routing for high availability. A new fraud service must write a risk flag with a conditional (check-and-mutate) write and immediately read it back, seeing its own writes. A nightly analytics scan of the whole table slows the card-serving service, whose traffic lands mostly on us-east1. The fraud service runs in us-east1 and tolerates a manual failover. Which TWO changes meet these needs while keeping card serving highly available? (Select TWO)
A: Give the fraud service its own app profile with single-cluster routing to us-east1 and single-row transactions allowed, so its writes and reads hit one cluster
B: Switch the card-serving app profile to single-cluster routing to us-east1, so that every service reads its own writes from the same cluster in the instance
C: Give the fraud service an app profile with multi-cluster routing and row-affinity routing, so its conditional writes run on the nearest cluster with stronger consistency
D: Run the nightly analytics scan through an app profile with single-cluster routing to us-west1, so the scan stays away from the cluster that serves most card traffic
E: Add a third cluster in us-central1 and enable strong consistency for the instance, so that every app profile reads its own writes across all three clusters
K: A,D
G: ## App profiles route each workload
In a replicated Bigtable instance, replication is **eventually consistent**. Each workload uses an **app profile**:
- **Multi-cluster routing**: nearest available cluster, automatic failover, eventual consistency. **Single-row transactions cannot be enabled** with it. Row-affinity routing raises the *rate* of read-your-writes for single-row work but does not allow transactions.
- **Single-cluster routing**: everything goes to one cluster, failover is manual. It is the **only policy that allows single-row transactions** (such as check-and-mutate), and sending reads and writes to the same cluster gives **read-your-writes** consistency.
## Isolating workloads
Different app profiles can send different workloads to different clusters, so a heavy scan can be routed to the cluster that serving traffic uses least. There is no instance-wide "strong consistency" switch.
W: A=Fraud profile with single-cluster routing: conditional writes need single-row transactions, which only single-cluster routing allows, and reading from the same cluster returns its own writes.
D=Analytics profile pinned to us-west1: the scan's load lands on the cluster that card serving uses least, while card serving keeps multi-cluster failover.
X: B=Card serving to single-cluster routing: it gives up automatic failover, which the card-serving service needs for high availability.
C=Multi-cluster with row affinity: it improves the read-your-writes rate but still cannot enable the single-row transactions that check-and-mutate needs.
E=Third cluster and strong consistency: Bigtable has no instance-wide strong consistency setting; another cluster adds cost and replication paths only.
T: Use one Bigtable app profile per workload: single-cluster routing for transactions and read-your-writes, multi-cluster for HA, and pinning to isolate heavy scans.
V: Bigtable

@ GCP-PCA D2 T2.3 expert use-case
S: Lindqvist Travel serves its booking web tier from a regional managed instance group in europe-west1 spread evenly over three zones behind a global external Application Load Balancer. Load tests show that the peak needs 30 VMs, and new VMs take about 8 minutes to become healthy. The business requires that losing any one zone at peak cause no capacity shortfall at all, and finance wants the lowest number of running VMs that achieves this. The region offers exactly three zones for this machine type, and quota is not a constraint. How should the group be sized?
A: Set the autoscaler minimum to 30 VMs with even distribution, relying on autoscaling to replace the lost zone's 10 VMs in the remaining two zones
B: Set the autoscaler minimum to 36 VMs with even distribution, so that 12 VMs per zone leave 24 serving VMs when any one zone is lost
C: Set the autoscaler minimum to 45 VMs with even distribution, so that 15 VMs per zone leave 30 serving VMs when any one zone is lost
D: Set the autoscaler minimum to 60 VMs in only two zones, so that each zone alone holds the full 30 VMs needed at peak if the other zone fails
K: C
G: ## N+1 capacity across zones
A regional managed instance group with an **even** target distribution spreads VMs across its zones. To lose a zone **without any shortfall**, the remaining zones must already hold peak capacity:
- per-zone VMs x (zones - 1) >= peak
- with 3 zones: per-zone x 2 >= 30, so **15 per zone, 45 in total**.
Autoscaling can replace lost VMs, but here they take **8 minutes** to become healthy, so relying on it means a shortfall for those minutes.
## Comparing
- 30 VMs: losing a zone leaves 20 (a 33% shortfall for at least 8 minutes).
- 36 VMs: leaves 24, still short.
- 45 VMs over 3 zones: leaves 30, no shortfall; overhead 50%.
- 60 VMs over 2 zones: also leaves 30, but runs 15 more VMs (overhead 100%).
Using more zones lowers the N+1 overhead: with n zones the overhead is 1/(n-1).
W: 45 VMs over three zones: any surviving pair of zones holds 30 VMs, so a zone loss causes no shortfall, with fewer running VMs than any two-zone layout.
X: A=Minimum 30 and autoscale: the lost 10 VMs need about 8 minutes to come back healthy, which is a capacity shortfall at peak.
B=Minimum 36: a zone loss leaves 24 VMs, 6 short of the 30 needed.
D=60 VMs in two zones: it meets the rule but runs 15 more VMs than the three-zone design.
T: For zone-loss tolerance without shortfall, size per-zone capacity so that the remaining zones carry peak; more zones means less spare capacity.
V: Compute Engine, Cloud Load Balancing

S: At Renwick Insurance, the Cloud Run service quote-engine is set to ingress "internal" and requires authentication. The Cloud Run service portal, in the same project, calls quote-engine's run.app URL with a Google-signed ID token and holds the Cloud Run Invoker role on it. Portal uses Direct VPC egress on a subnet with the default "route only requests to private IPs" setting, and its calls to quote-engine are rejected. Security insists that quote-engine never be reachable from the internet, and no load balancer may be added. Which TWO changes make the calls succeed? (Select TWO)
A: Change portal's Direct VPC egress setting to route all traffic through the VPC network, so that requests to the run.app URL leave through the subnet
B: Enable Private Google Access on the subnet that portal's Direct VPC egress uses, so that requests to the run.app URL reach Cloud Run over the VPC network
C: Change quote-engine's ingress to "all" and rely on the ID token alone, since IAM authentication already rejects every caller without the Invoker role
D: Grant the Cloud Run Invoker role on quote-engine to allUsers, so that the internal ingress check is skipped for calls coming from other Cloud Run services
E: Change quote-engine's ingress to "internal and Cloud Load Balancing", so that calls from other Cloud Run services in the project are accepted as internal

G: ## When is a request "internal" for Cloud Run?
With ingress **internal**, Cloud Run accepts requests from VPC networks in the same project, internal Application Load Balancers, VPC Service Controls perimeters and some Google services. **Calls from another Cloud Run service count as internal only if they travel through a VPC network.**

- use **Direct VPC egress** (or a connector), **and**
- **route all traffic** through the VPC network and **enable Private Google Access** on that subnet (alternatives: Private Service Connect or an internal Application Load Balancer in front).
With the default "private IPs only" egress, requests to the `run.app` URL (a public Google address) bypass the VPC and arrive as external, so they are rejected even with a valid ID token.
W: A=Route all traffic through the VPC: the run.app request now leaves portal through its subnet instead of directly to Google.
B=Private Google Access on that subnet: traffic from the subnet reaches the Cloud Run endpoint over Google's network as VPC traffic, so quote-engine treats it as internal.
X: C=Ingress "all": IAM would still check tokens, but quote-engine becomes reachable from the internet, which security forbids.
D=Invoker for allUsers: it removes authentication and does not change how ingress classifies the request; the call is still external.
E=Internal and Cloud Load Balancing: it adds external Application Load Balancers as sources, not Cloud Run callers that bypass the VPC.
T: A Cloud Run caller reaches an "internal" Cloud Run service only through the VPC: route all egress through the VPC and enable Private Google Access (or use PSC or an internal load balancer).

S: Selkie Photo stores customer images in a Cloud Storage bucket. Under data protection law, an image must be unrecoverable within 30 days of an erasure request.
