@ GCP-PCA D6 T6.6 applied use-case
S: KnightMotives is rebuilding its unreliable online build-to-order system, which pulls stock and supply data from an older mainframe-based ERP. Dealers' traffic spikes when a new model opens for orders. Before launch, the architect plans load testing. Which plan is most valuable?
A: Skip load testing and rely on autoscaling of the managed services to absorb the dealer spike as traffic arrives on launch day
B: Replay realistic order mixes in a production-like environment, ramp past the launch peak, and watch autoscaling, latency and ERP load
C: Send a constant light load of identical requests to the web tier for ten minutes, and declare success if no errors occur
D: Test the new application with the ERP dependency replaced by a fast stub, so the results isolate the cloud components' performance
K: B
G: ## What a useful load test shows
Load testing finds the limits and bottlenecks of a system before real users do. A good test:
- **Models real behaviour**: realistic mix of operations, data and think time, not one repeated request.
- **Uses a production-like environment** (same configuration and dependencies), or tests carefully in production with safety measures.
- **Ramps up** gradually past the expected peak (and combined with failure scenarios), to see where latency or errors start.
- **Watches the whole path**: autoscaling reaction time, database and cache saturation, quotas and, importantly here, **dependencies** such as the mainframe ERP that cannot scale like the cloud tier.
Replacing a slow dependency with a fast stub hides the likeliest bottleneck. Autoscaling reacts with delay and cannot scale a legacy backend.
W: Realistic, production-like load beyond peak: replaying real order mixes, ramping past the launch peak and watching autoscaling, latency and ERP load reveals where the real path saturates and how autoscaling reacts to a dealer spike.
X: A=No test, rely on autoscaling: autoscaling has reaction time, and quotas and the mainframe ERP set limits it cannot raise, so a launch spike can still cause failures nobody measured.
C=Light constant load on the web tier: no stress, no variety and no downstream view, so it cannot show capacity limits.
D=Stubbed ERP: the stub removes the dependency most likely to limit throughput, so a good result would be misleading.
T: Load test with realistic traffic, in a production-like setup, beyond peak, with dependencies included.
V: Cloud Load Balancing, Cloud Monitoring

@ GCP-PCA D6 T6.5 applied use-case
S: A team deploys through a Cloud Deploy delivery pipeline to staging and then production. After each staging deployment, an engineer clicks through the application by hand and promotes the release if it looks fine. Last month a broken release was promoted because the check was skipped. Which change makes the quality check consistent?
A: Add a longer written checklist for the engineer to follow after each staging deployment, with a second engineer initialling it before promotion
B: Configure deployment verification on the staging target with a test container whose non-zero exit code fails the rollout
C: Promote to production with no check once the staging deployment finishes, and rely on production monitoring to notice a broken release
D: Run the same smoke tests on developer laptops before merging, and keep the manual click-through on staging as the release gate
K: B
G: ## Automated verification as a quality gate
Quality control in delivery means a check that runs every time and does not depend on memory. Cloud Deploy can run **verification** after a deployment to a target: you supply a container image with your tests and configure it in the pipeline.
- The tests run in the Cloud Deploy execution environment after the deployment finishes.
- The exit code decides: `0` is success, a non-zero code is failure, and when several containers run all must succeed.
- If verification fails, the rollout fails, so the problem is visible in the pipeline instead of in the judgement of a person; a failed verification can be retried or ignored deliberately.
- Combine with approval on the production target for a gate that is both automated and accountable.
W: Automated verification on the staging target: the same tests run after every deployment and a failing result fails the rollout, so a broken release no longer depends on someone remembering to check.
X: A=Longer checklist with second initials: it is still a manual step that can be skipped or done carelessly, only slower.
C=Promote without a check: this removes the gate and lets customers find the defect first.
D=Laptop tests plus the manual gate: laptop runs cannot catch problems in the deployed environment, and the staging gate stays the same manual click-through that was skipped last month.
T: Use Cloud Deploy verification so each deployment is tested the same way and failing tests fail the rollout.
V: Cloud Deploy

@ GCP-PCA D3 T3.2 applied use-case
S: EHR Healthcare will store protected health information in Google Cloud and wants a technical guardrail so that engineers cannot use a Google Cloud service outside the ones covered by its Business Associate Agreement (BAA). Which approach best supports this goal?
A: Pin the health data to a single region, because the BAA covers services running in the region where the agreement was signed
B: Request a HIPAA certificate from the regulator for the Google Cloud project, since a certified project makes its services acceptable
C: Accept the BAA, restrict the health-data folder's allowed services with an organization policy, and keep pre-GA offerings off PHI
D: Rely on the BAA by itself, because accepting it disables the services it does not cover across the whole Google Cloud organization
K: C
G: ## What a BAA does and does not do
In the United States, HIPAA applies to covered entities and their business associates. When a cloud provider handles protected health information (PHI) for you, a Business Associate Agreement (BAA) is the contract that sets out its obligations. Google's HIPAA guidance says the U.S. Department of Health and Human Services offers no certification program for HIPAA, that compliance is a shared responsibility, and that the Google Cloud BAA covers the whole Google Cloud infrastructure (all regions) but only a listed set of products.
## Staying inside the covered products
- The guidance tells customers to disable unsupported services for PHI, and not to use pre-GA offerings with PHI unless the terms say so.
- The preventive control is an organization policy: the `gcp.restrictServiceUsage` constraint limits which service APIs a folder or project may use, so a mistake cannot happen by accident.
- Assured Workloads has a US Data Boundary for Healthcare and Life Sciences control package (in-scope services are on Google's HIPAA and HITRUST lists) that adds data boundary controls; it is an extra guardrail, not a legal prerequisite for HIPAA.
This is an architecture pattern, not legal advice; the compliance team still evaluates the obligations.
W: BAA plus an organization policy on allowed services: accepting the BAA and then restricting allowed services at the folder level turns the "covered products only" rule into an enforced guardrail, and excluding pre-GA features follows the HIPAA guidance.
X: A=Single region: the Google Cloud BAA covers the entire infrastructure, all regions and zones. Tying PHI to one region is a separate residency choice, not a condition of the BAA.
B=Regulator certificate: HHS does not certify HIPAA compliance, so no such certificate exists for a project. Compliance is shown through your own controls and the shared responsibility model.
D=BAA disables services: a BAA is a contract, not a technical control. It does not stop anyone from enabling a service, so without a policy an engineer can send PHI to an uncovered product.
T: A BAA is a contract; enforce "covered services only" with organization policy and keep pre-GA features away from PHI.
V: Organization Policy, Assured Workloads

S: Altostrat Media manages CI/CD for containers that run on GKE clusters in Google Cloud and on-premises. After a supply chain scare, the architect must ensure that only images built by the approved Cloud Build pipeline and that passed vulnerability checks are deployed to production clusters. Which design enforces this?

X: A=Written policy and audits: it is detective and depends on people, which is the weakness exposed by the incident.

@ GCP-PCA D4 T4.2 applied use-case
S: A company's cloud bill is growing, and 40 teams share a few projects. Finance cannot tell which product or team causes the growth, and engineers suspect many oversized and idle VMs. Which TWO actions give finance and engineering the data to attribute and reduce the spend? (Select TWO)
A: Apply consistent resource labels, one project per team or product, and export detailed billing data to BigQuery for reporting by team
B: Ask each team to estimate its own monthly usage in a spreadsheet and send it to finance at the end of the quarter
C: Move the workloads into one large shared project so that a single total appears on the invoice each month
D: Buy committed use discounts for the full current spend first, and look at which resources are idle or oversized after the commitment
E: Review the idle and rightsizing recommendations that Google Cloud generates from observed usage and resize or remove the flagged resources

G: ## Two steps of cost optimization
Cost control starts with attribution (who spends what) and continues with removal of waste (what is not needed).

- **Waste removal**: the Recommender service analyses utilization and suggests actions such as resizing over-provisioned VMs or deleting idle resources. Acting on these is the fastest saving that needs no commitment.
- **Commitments** (CUDs) come after this: you commit only for load you know is needed, not for the waste.

E=Rightsizing and idle recommendations: they use measured utilization to identify oversized or idle VMs, so engineering can cut cost without changing the architecture.

C=One large project: a single total hides who spends what and weakens the separation of access and quotas. It removes the attribution that is missing.
D=Commit first: a commitment on the current spend locks in a discount on resources that may be waste, so the company pays for idle capacity for one or three years.
T: Attribute with labels, project structure and billing export, then cut waste with recommendations, and only then commit with CUDs.
V: Cloud Billing, BigQuery, Recommender

@ GCP-PCA D4 T4.2 applied tradeoff
S: A manufacturing company is closing two data centers and moving its workloads to Google Cloud. The finance director welcomes the end of large hardware purchases but worries that monthly bills will now vary and could surprise the business. As the architect, which advice best addresses both the benefit and the concern?
A: Explain that cloud costs are fixed once a project is created, so the monthly bill matches the first estimate and tagging can wait
B: Explain the move from capital purchases to usage-based costs, and add budgets with alerts, labels and CUDs for the steady baseline
C: Recommend buying the maximum expected capacity up front for three years on each service, so the bill stays as predictable as before
D: Recommend moving the cheapest workloads first and delaying cost reporting until the migration is complete and usage has stabilized
K: B
G: ## CapEx versus OpEx in the cloud
On premises, hardware is a capital expense (CapEx): money is spent up front for capacity that must cover the peak, and it depreciates over years. In Google Cloud most services are an operating expense (OpEx): you pay for what you use, when you use it, and you can add or remove capacity quickly. The cost optimization pillar of the Well-Architected Framework treats this as a change of discipline, not just of accounting.
## Keeping variable spend under control
- **Budgets and alerts** tell the owners when spend crosses chosen thresholds.
- **Labels, folders and projects** let finance attribute spend to teams and products (showback or chargeback).
- **Committed use discounts (CUDs)** trade a one-year or three-year commitment for a lower rate on the steady part of the load. They exist as spend-based and resource-based commitments.
- Variable or spiky load stays on demand, so the company does not pay for idle peak capacity.
W: CapEx to OpEx with budgets, labels and CUDs: naming the shift to usage-based spending and pairing it with budgets and alerts, labels for attribution and CUDs for the predictable baseline answers both points; the director keeps the benefit (no up-front hardware) and gains visibility and a lower rate where demand is stable.
X: A=Fixed costs: cloud bills follow consumption, so they change when usage changes. Believing in a fixed bill removes the monitoring and labels that prevent surprises.
C=Maximum capacity for three years: committing to peak capacity recreates the over-provisioning of a data center. CUDs fit the steady baseline, not the peak.
D=Delay cost reporting: cost visibility is easiest to set up at the start, and delaying it is exactly how unexpected bills arise. Moving the cheapest workloads first is also unrelated to the stated concern.
T: Cloud moves spend from CapEx to usage-based OpEx; control it with budgets, labels and CUDs for the steady baseline.
V: Cloud Billing, committed use discounts

@ GCP-PCA D1 T1.3 advanced comparison
S: A retail group has about forty product teams, each in its own project. A central network team must own subnets, routes and firewall rules, while product teams only deploy workloads into approved subnets. All workloads must talk to each other over internal IP addresses. Which design fits?
A: One VPC network per project joined by Cloud VPN tunnels, with the network team reviewing each team's tunnel settings
B: A single shared project for the forty teams, with IAM roles limited to the instances each team creates
C: Shared VPC with a host project owned by the network team and each product project attached as a service project
D: VPC Network Peering between each pair of product-team VPC networks, with each team writing its own firewall rules
K: C
G: ## Shared VPC versus peering
- **Shared VPC** lets an organization connect resources from several projects to one VPC network in a host project. Service projects use subnets of that network, and the network administration (subnets, routes, firewall rules) stays with the host project's administrators. Workload owners get only permission to use specific subnets.
- **VPC Network Peering** connects two separate VPC networks so they exchange routes privately. Each network keeps its own administration, peering is not transitive, and subnet ranges must not overlap.
Peering is a good fit when different organizations or independently run networks must connect. Shared VPC is the fit when one organization wants central network control with delegated workload deployment.
W: Shared VPC: the host project concentrates subnets, routes and firewalls under the network team, service projects attach to it and use internal IP addresses on the same network, which is the separation of duties described.
X: A=VPN between projects: tunnels between VPC networks inside one organization add cost and failure points, and every team still controls its own network, so the central team cannot own subnets and firewall rules.
B=Single project: it removes the project boundary that product teams, billing and quotas rely on, and IAM on individual instances does not give the network team separate control of subnets and firewall rules.
D=Pairwise peering: with forty networks this is a mesh of hundreds of non-transitive peerings, each team would administer its own firewall rules, and ranges would have to be kept non-overlapping. That is the opposite of central control.
T: One organization, central network ownership, many workload projects: use Shared VPC; use peering to link independently administered networks.

S: KnightMotives, an EU car maker, will process driver personal data on Google Cloud. Its legal team asks how the GDPR roles and contract fit together. Which statement is most accurate?
A: Signing up for Google Cloud makes Google the controller of the drivers' data, so the car maker has no GDPR duties left for the data held there
B: The customer is the controller and Google the processor under the Google Cloud data processing terms, acting on the customer's instructions
C: Google's GDPR page certifies the car maker's applications, so no assessment of its own processing purposes or legal basis is needed
D: Data processing terms are optional for GDPR, because the regulation places the processing duties on the provider rather than on cloud customers
K: B
G: ## Roles and responsibility under GDPR
GDPR distinguishes the data controller, who decides the purposes and means of processing, from the processor, who processes personal data on its behalf. Controllers must use processors with appropriate technical and organizational measures.
- For customer data on Google Cloud, Google's GDPR page describes the customer as controller and Google as processor: data is processed only according to the customer's instructions in the data processing terms (Google Cloud Data Processing and Security Terms, with EU standard contractual clauses for transfers outside the EU where needed).
- Google publishes information on subprocessors and offers admin functionality that helps controllers answer data subject requests (access, rectification, restriction, deletion).
- The legal basis, purposes, retention and the application design remain the customer's responsibility.
This is an architecture-level summary, not legal advice; counsel confirms the obligations.
W: Customer as controller, Google as processor: under the Google Cloud data processing terms Google acts on the customer's instructions, so the customer still decides purposes and answers for its own processing.
X: A=Google as controller: Google processes customer data on the customer's instructions; the customer keeps the controller duties.
C=Page as certification: the page explains Google's commitments; it does not assess any customer application, and the car maker must still document its own purposes and legal basis.
D=Terms optional: controllers must use processors with appropriate measures, and the data processing terms are the contract that documents them, so they are central, not optional.
T: GDPR on Google Cloud: customer is controller, Google is processor under the data processing terms; the customer keeps its own duties.

@ GCP-PCA D5 T5.1 applied tradeoff
S: An insurer exposes claims APIs to partners. A new contract states that API traffic must be processed in the insurer's own facilities, where it already runs a Kubernetes platform, but the insurer still wants Google-hosted API management, analytics and a developer portal. Which Apigee approach fits best?
A: A custom gateway on virtual machines in the insurer's own facilities, built and maintained by the insurer's team without Apigee
B: Apigee with a fully Google-hosted runtime, because data processed inside Google Cloud counts as the insurer's own facilities
C: Apigee for the partner developer portal and analytics, while API traffic goes unmanaged directly to the backend services
D: Apigee hybrid, running the runtime plane on the existing on-premises cluster while Apigee hosts the management plane in the cloud
K: D
G: ## Where does the runtime run?
Apigee API management has a management plane (configuration, analytics, developer portal) and a runtime plane that processes API calls.
- With the fully managed offering, Google hosts both planes.
- With **Apigee hybrid**, the management plane is hosted by Apigee in the cloud, and the runtime plane is installed and managed by the customer on a supported Kubernetes platform. This suits compliance or security rules that require API traffic to be processed on premises or in the customer's own environment, using existing governance.
The trade-off is operations: in hybrid the customer manages the runtime cluster; in the managed model Google does.
W: Apigee hybrid: the runtime plane that processes API calls runs on the insurer's existing Kubernetes platform, meeting the contract, while the cloud-hosted management plane gives the managed analytics and developer portal the insurer wants.
X: A=Custom gateway: building it forfeits the managed analytics, policies and developer portal the insurer wants, and adds a large engineering cost.
B=Fully Google-hosted runtime: the contract asks for processing in the insurer's own facilities, and a Google-hosted runtime is not that.
C=Portal and analytics only: calls would bypass Apigee's authentication, quota and analytics, so the insurer loses control of the API traffic it wanted to govern and the analytics have no traffic to report.
T: Need API processing in your own environment plus managed API management: Apigee hybrid.
V: Apigee hybrid
