@ AIF-C01 D4 T4.2 applied definition
S: A company explains to customers which factors most influenced an individual loan decision. Which responsible AI concept does this represent?
A: Explainability
B: Controllability
C: Veracity and robustness
D: Privacy and security
K: A
G: ## Explainability in responsible AI
Explainability means being able to describe why a model produced a specific output in terms people understand.
- **Global** explanations describe the model overall, for example "income and debt ratio matter most across all applications".
- **Local** explanations describe one decision, for example "this application was declined mainly because of a high debt-to-income ratio and a short credit history".
## Why it matters for lending
Customers and regulators often expect a reason for an adverse credit decision. Local explanations help customers understand what to change, help staff check that the model relied on legitimate factors, and support audits.
On AWS, SageMaker Clarify produces feature attributions for individual predictions and for the model as a whole.
W: Explainability: telling a customer which factors drove their own loan decision is a local explanation of the model's output, the core of explainability, which AWS describes as understanding and evaluating system outputs.
X: B=Controllability: this dimension is about having mechanisms to monitor and steer the AI system's behavior, for example the ability to intervene or override; it does not tell a customer why a decision was made.
C=Veracity and robustness: this dimension is about producing correct outputs even with unexpected or adversarial inputs; it concerns how reliable a decision is, not the reasons given for it.
D=Privacy and security: this dimension is about appropriately obtaining, using and protecting data and models; sharing decision factors with the applicant is not a data protection measure.
T: Explaining why an individual decision was made is explainability; controllability, veracity and robustness, and privacy and security cover steering, correctness and data protection.

@ AIF-C01 D4 T4.1 applied use-case
S: A company fine-tunes a model on customer chat logs. Which responsible AI step should happen before training?
A: Duplicate the longest chats so the training set is larger
B: Keep just the chats that customers rated most positively
C: Remove or mask personal data the model should not learn
D: Translate the chats into English so the data is consistent
K: C
G: ## Personal data in fine-tuning data
Customer chat logs often contain names, emails, phone numbers, addresses, account or card numbers. If such text is used to fine-tune a model, the model can **memorize** it and later reproduce it to other users, which is a privacy and compliance failure.
## Preparing the data
- **Detect** personal data (PII). **Amazon Comprehend** can detect PII entities in text and redact them; Amazon Macie can find sensitive data in S3.
- **Remove or mask** it, for example replace "Call Jane Doe at 555-0100" with "Call [NAME] at [PHONE]", so the model learns the conversation pattern without the personal details.
- Keep only data you are permitted to use for training, and restrict access to raw logs.
This step must happen **before** training: once personal data is in the model's weights, it cannot be reliably removed without retraining.
W: Remove or mask personal data: stripping or masking PII before training prevents the model from memorizing it and exposing it to other users later.
X: A=Duplicate the longest chats: duplication adds no new information and makes the model over-weight repeated examples, which even increases memorization risk. It does nothing for privacy.
B=Keep top-rated chats: filtering by rating can skew the model toward certain topics or customers, and the kept chats still contain personal data.
D=Translate into English: translation may be unnecessary for the use case, can lose nuance, and leaves the names and numbers in the text, so it does not address privacy.
T: Before fine-tuning on customer data, remove or mask personal data so the model cannot memorize and reveal it.

@ AIF-C01 D2 T2.1 advanced use-case
S: Which TWO statements about tokens are accurate for business planning? (Select TWO)
A: Token counts equal word counts, so a 750-word prompt uses 750 tokens
B: Response length changes cost per request but has no effect on latency
C: Tokens are counted for image generation models but not for text chat models
D: A model's context window is measured in tokens, covering prompt and output
E: Longer prompts and responses use more tokens and so cost more per request
K: D,E
G: ## What a token is
A **token** is the unit a language model reads and writes. Tokenizers split text into common chunks: a short word may be one token, while a long or rare word may be split into several. As a rough rule for English, one token is about three quarters of a word, and other languages can use more tokens per word.
## Why tokens matter to the business
- **Cost:** on-demand text model pricing is per input token and per output token, so longer prompts, retrieved context and longer answers cost more.
- **Limits:** a model's **context window**, for example 200,000 tokens, caps the prompt plus output. Long documents or chat histories must fit inside it.
- **Latency:** output is generated token by token, so longer responses take longer, and very long inputs also add processing time.
## Example
A 3,000-token prompt with a 500-token answer costs roughly twice as much as a 1,500-token prompt with a 250-token answer on the same model.
W: D=Context window in tokens: the maximum amount of text a model can handle in one request is defined as a number of tokens, covering both input and output.
E=More tokens cost more: billing is per token processed, so longer prompts and longer responses directly raise the cost of each request.
X: A=Tokens equal words: tokenizers often split words into subword pieces, and punctuation can be separate tokens, so a 750-word English prompt is usually around 1,000 tokens, not 750.
B=No latency effect: models generate one token at a time, so more output tokens mean a longer response time, and longer inputs also take more processing.
C=Image models but not chat models: tokens are the core unit for text and chat models, which is where token-based pricing and context windows apply most directly. Image generation is often priced per image instead.
T: Tokens determine cost, context window limits and latency; a token is often only part of a word, and text models count them for every request.

A: Predictive ML runs on premises, while generative AI runs in the cloud

G: ## Predictive ML versus generative AI
- **Traditional predictive ML** maps an input to a label or number. Examples: a classifier outputs "fraud" or "not fraud", a regression model predicts next month's sales of 12,400 units, a recommender outputs a ranked list of product IDs.
- **Generative AI** produces new content that did not exist before: text, images, audio or code. Example: given "write a product description for a waterproof hiking boot", a foundation model writes a new paragraph.
## What they share
- Both learn from data. Generative foundation models are pre-trained on huge, mostly unlabeled datasets using self-supervised learning.
- Both run in the cloud, on premises or at the edge, depending on the model size and hardware.
- Both can be deterministic or random depending on settings; generative models add randomness through sampling parameters such as temperature.

D=Generative repeats, predictive varies: the opposite is closer to true for many setups, since generative sampling adds randomness through settings such as temperature, while most trained predictive models return the same output for the same input.

@ AIF-C01 D4 T4.1 advanced use-case
S: Which TWO actions reduce the environmental impact of generative AI workloads? (Select TWO)
A: Choose the smallest model that still meets the quality needs
B: Run each request on two models and compare answers for safety
C: Pick the largest available model to reduce the number of retries
D: Retrain the model from scratch whenever a small update is needed
E: Use energy-efficient accelerators such as AWS Inferentia chips
K: A,E
G: ## Where generative AI energy goes
Energy use scales roughly with the compute each request needs and the number of requests. Bigger models have more parameters to compute for every token, and training from scratch consumes far more compute than inference or light fine-tuning.
## Practical levers
- **Right-size the model**: if a small model answers an FAQ just as well as a very large one, each request uses much less compute. Techniques like distillation and quantization shrink models further.
- **Efficient hardware**: purpose-built chips such as AWS Inferentia (inference) and AWS Trainium (training) are designed to deliver more performance per watt than general-purpose GPU instances for supported workloads.
- **Avoid waste**: cache repeated answers, batch non-urgent work and reuse existing models through fine-tuning instead of full retraining.
These choices also usually lower cost, so sustainability and cost goals tend to align.
W: A=Smallest adequate model: a model that meets quality needs with fewer parameters needs less compute and therefore less energy per request.
E=Energy-efficient accelerators: Inferentia is built for high-throughput inference with better performance per watt, reducing energy for the same workload.
X: B=Two models per request: running each request twice roughly doubles compute and energy with no quality requirement behind it; safety is handled with guardrails and evaluation, not duplication.
C=Largest available model: larger models use more compute per token, and fewer retries rarely offset that; for a task a small model handles, the extra compute is wasted energy.
D=Retrain from scratch for small updates: full retraining is the most compute-intensive step; small updates are handled with fine-tuning, retrieval of new data or prompt changes.
T: Reduce environmental impact by using the smallest model that meets quality needs on efficient hardware, not by adding more compute.

S: Which TWO statements about training data and inference are correct? (Select TWO)
A: Inference updates the model's weights with each new request it gets
B: A model must be retrained before each single prediction is made
C: Inference can be real-time or batch depending on the use case
D: Batch inference returns each prediction faster than a real-time endpoint
E: Training builds the model from data; inference uses it to predict
K: C,E
G: ## Two phases of the ML lifecycle
- **Training** is where the model learns. An algorithm reads historical examples (for example 100,000 past transactions labeled fraud or not fraud) and adjusts its internal parameters until its predictions match the labels well. Training is expensive and happens occasionally.
- **Inference** is where the trained model is used. New data goes in, a prediction comes out, and the parameters do not change.
## Real-time versus batch inference
- **Real-time** inference answers one request at a time with low latency, such as scoring a card payment while the customer waits. On AWS this is a SageMaker AI real-time endpoint or a serverless endpoint.
- **Batch** inference scores a large dataset offline, such as ranking every customer's churn risk overnight. On AWS this is SageMaker batch transform, or batch inference jobs in Amazon Bedrock.
The same model can serve both styles; the choice depends on how fast the answer is needed and how much data arrives at once.
W: C=Real-time or batch inference: the business need decides the mode. Latency-sensitive requests use an online endpoint, while large offline datasets are scored in batch jobs that are cheaper per prediction.
E=Training builds, inference predicts: training learns parameters from data once or periodically; inference applies those fixed parameters to new inputs to produce predictions.
X: A=Inference updates weights: inference only reads the learned parameters. Retraining is a separate, deliberate step, usually triggered by new labeled data or detected drift, not by each request.
B=Retrain before each prediction: retraining per prediction would be slow and costly; a model is trained once and then serves many predictions until it is retrained on a schedule or when quality drops.
D=Batch is faster per prediction: batch inference scores a large dataset offline and returns results when the job finishes; it is chosen for volume and lower cost, while low-latency answers for single requests come from a real-time endpoint.
T: Training creates the model and inference uses it without changing it; inference can run in real time or in batch depending on latency and volume needs.

@ AIF-C01 D2 T2.2 applied comparison
S: Which statement about the knowledge of a foundation model is accurate?
A: It searches the web before it answers, so its replies reflect the latest published information
B: It updates its weights after each conversation, so it keeps learning from the users it talks to
C: It has a training cutoff, so it may not know recent events unless it is given current information
D: It knows the company's internal documents, because these were part of its public training data
K: C
G: ## Where a model's knowledge comes from
A foundation model learns from a large training dataset collected up to a certain date, the **training cutoff**. After training, its knowledge is frozen in its weights.
- It does not know events after the cutoff unless the application supplies them in the prompt.
- It does not change its weights while chatting. Within one conversation it can use what is in its context window, but that is forgotten when the context ends.
- It only knows what was in its training data. A company's private documents were not included, so the model cannot know them.
## How applications add current or private knowledge
- **Retrieval-augmented generation (RAG)**: search a knowledge base or recent data and put the results into the prompt.
- **Tools or agents**: let the application call a search API or an internal system and pass the result to the model.
Example: to answer "what is today's exchange rate?" the app must fetch the rate and include it; the model alone can only offer an outdated guess.
W: Training cutoff: the model's knowledge stops at its training data, so recent or private facts must be provided in the prompt, for example through retrieval or tools.
X: A=Searches the web: a model only reads its prompt; web search happens only if the application adds a search tool and passes the results in.
B=Updates weights after each conversation: inference does not update weights; changing the model requires a separate training or fine-tuning job.
D=Knows internal documents: internal documents are private and not part of public training data, which is why RAG over company data is needed.
T: A foundation model's knowledge is frozen at its training cutoff; current or private information must be supplied at request time.

@ AIF-C01 D3 T3.2 advanced definition
S: A malicious actor deliberately inserts corrupted or biased examples into a dataset that will later be used to fine-tune an FM, intending to manipulate the model's future behavior. This risk is known as:
A: Prompt injection (hijacking)
B: Zero-shot context leakage
C: Training data poisoning
D: Model weights exposure
K: C
G: ## Where poisoning happens
A model learns whatever patterns are in its training data. **Data poisoning** is an attack in which someone deliberately adds corrupted, mislabeled or biased examples to that data so the trained model behaves the way the attacker wants.
Example: an attacker slips hundreds of fake support tickets into a fine-tuning dataset in which a competitor's product is always described as unsafe. After fine-tuning, the model repeats that bias to every user.
- Poisoning is dangerous because it is baked into the weights: it persists after training and is hard to spot by looking at single outputs.
- A related term, **prompt poisoning**, covers malicious content planted in data the model reads at inference time (for example documents retrieved by RAG).
## Defenses
- Control and audit who can write to training data sources (for example Amazon S3 bucket policies and logging).
- Track data lineage and validate or sample data before training.
- Evaluate the fine-tuned model for unexpected behavior before deployment.
W: Training data poisoning: the attacker tampers with the data the model learns from, which is exactly what inserting corrupted or biased examples into a fine-tuning dataset does. The same tampering with data read at inference time, such as RAG documents, is called prompt poisoning.
X: A=Prompt injection (hijacking): overrides the instructions of a single request at inference time; it does not change the training data or the model's weights for future use.
B=Zero-shot context leakage: is not a recognized security risk category; zero-shot only describes prompting a model without examples.
D=Model weights exposure: describes a model or its weights being made accessible to unauthorized parties, a confidentiality issue, not the manipulation of its training data.
T: Tampering with training data to change future model behavior is poisoning; hijacking or injection manipulates one prompt at inference time.

@ AIF-C01 D1 T1.3 advanced definition
S: A team deployed a model straight after training and it failed in production due to untested edge cases and changing data. Which pipeline order would have prevented this?
A: Collect, train, prepare, deploy, evaluate, monitor
B: Prepare, collect, train, deploy, monitor, evaluate
C: Collect, prepare, deploy, train, evaluate, monitor
D: Collect, prepare, train, evaluate, deploy, monitor

G: ## The machine learning lifecycle
Each step feeds the next, so the order matters:
- **Collect**: gather raw data relevant to the business problem.
- **Prepare**: clean it (missing values, duplicates, formats) and engineer features.
- **Train**: fit the model on the prepared data.
- **Evaluate**: test on held-out data and on edge cases, compare against the business goal, and only then approve release.
- **Deploy**: serve the approved model for predictions.
- **Monitor**: watch prediction quality and incoming data in production. When data drifts (for example customer behavior changes), retrain with fresh data and repeat.
## What went wrong in the scenario
The team skipped **evaluate** (edge cases were never tested) and had no **monitor** step (changing data went unnoticed). SageMaker AI supports these steps with tools such as Model Monitor for detecting drift.
W: Collect, prepare, train, evaluate, deploy, monitor: evaluation before deployment catches untested edge cases, and monitoring after deployment detects changing data so the model can be retrained.
X: A=Train before prepare, evaluate after deploy: training on raw, uncleaned data skips preparation, and evaluating only after deployment repeats the original mistake of releasing a model whose edge cases were never tested.
B=Prepare before collect, evaluate last: there is nothing to prepare before data is collected, and evaluation comes after the model is already deployed and monitored, so untested edge cases still reach production.
C=Deploy before train: a model cannot be deployed before it is trained, and evaluation again happens only after release, so the pipeline still lets untested behavior into production.
T: Evaluate before you deploy and monitor after you deploy; data collection and preparation always come before training.

CLV estimates the total revenue (or profit) a customer will generate over their whole relationship with the company, not just one purchase. A simple version:

Loyalty initiatives aim at repeat purchases and longer relationships. Their effect shows up over time in retention and frequency, which a single-transaction metric misses. Companies usually compare CLV (or its leading indicators, such as retention rate) between customers who use the chatbot and those who do not.

C=Average single transaction value: this captures one purchase at a time. The question explicitly asks for value over the whole relationship, not a single transaction.
T: Long-term, whole-relationship revenue is CLV; single-transaction value is short-term and token or cost metrics are technical.

- Example: a user uploads a profile photo to Amazon S3, an event triggers a function that calls Rekognition, and any image with a moderation label above 80 percent confidence is hidden and sent for human review.
- Thresholds are set by the application, so a children's platform can be stricter than a general forum.
- Custom Moderation lets you adapt the model with your own examples if needed, but the base capability works without training.
## Other pre-trained services and what they read
- **Amazon Comprehend** analyzes text: entities, key phrases, sentiment and personal data in documents.
- **Amazon Textract** reads printed and handwritten text, forms and tables from scanned documents.
- **Amazon Polly** turns text into speech.
W: Amazon Rekognition: its built-in content moderation detects unsafe or inappropriate content in images and video out of the box, so no model training is needed.
X: B=Amazon Comprehend: Comprehend is a natural language processing service that finds insights such as entities, sentiment and PII in text documents; it does not judge whether a picture shows explicit or violent content.
C=Amazon Polly: Polly converts text into lifelike speech; it produces audio and has no image analysis capability.
D=Amazon Textract: Textract extracts printed and handwritten text, forms and tables from scanned documents; it reads text in documents rather than judging whether image content is inappropriate.

G: ## Activity versus configuration
- **AWS CloudTrail** records API activity: who called which API, when, from where and with which parameters. Log file integrity validation lets you prove the delivered log files were not changed, and logs can be kept in S3 (with Object Lock) or CloudTrail Lake for forensics.
- **AWS Config** records the configuration state of resources over time and uses rules to evaluate whether they are compliant, for example `s3-bucket-server-side-encryption-enabled`.
## Using them together
Example: the policy requires SSE-KMS, and the managed rule `s3-default-encryption-kms` marks a bucket non-compliant after its default encryption is changed back to SSE-S3. CloudTrail shows the `PutBucketEncryption` call, the role that made it and the time. Config tells you what the state is; CloudTrail tells you who changed it.
W: CloudTrail for API activity, Config for compliance: CloudTrail gives the tamper-evident record of Bedrock API calls for forensics, and Config rules continuously evaluate the S3 buckets against the encryption policy.
X: B=Config rules for both: Config evaluates resource state; it does not record every API call with the caller identity, such as Bedrock invocations, so it cannot provide the forensic record.
C=Trusted Advisor merges both: Trusted Advisor runs best-practice checks. It neither stores an API history nor evaluates your own custom compliance rules, and it does not replace CloudTrail or Config.
D=Config for API calls, CloudTrail for encryption checks: this swaps the roles. CloudTrail does not evaluate compliance, and Config does not log every API call.
T: CloudTrail answers "who did what and when"; Config answers "is this resource configured correctly now and over time".

S: A company wants to explain to non-technical users why a recommendation was made. Which approach helps most?
A: Show the model's parameter count, architecture and training duration
B: Show a confidence score for the recommendation without other context

K: D
G: ## Explainability for end users
Explainability means people can understand why a model produced a particular output. What counts as a good explanation depends on the audience:
- A data scientist may want feature attributions, such as SHAP values from Amazon SageMaker Clarify.
- A non-technical user needs a short, plain-language reason tied to their own situation.
## Turning model factors into plain language
A recommendation model typically weighs signals such as past purchases, viewed items and what similar customers liked. The app can surface the top one or two factors:
- "Recommended because you bought a tent and hiking boots."
- "Popular with customers who watched the same series."
This helps users judge whether to trust the recommendation, correct wrong assumptions, and feel the system is not arbitrary. Internal details such as architecture or code do not answer the user's real question: "why me, why this?"
W: Main factors in plain language: telling users which of their own signals drove the recommendation, in everyday words, directly answers why it was made and is understandable without technical knowledge.
X: A=Parameter count, architecture and training time: these describe the model's size, design and cost, not the reasons behind any single recommendation. They mean nothing to a typical user.
B=Confidence score alone: a number such as 87% says how sure the model is, but not why it chose this item, so the user still has no reason to trust or question it.
C=Source code and weights: code and millions of numeric weights are unreadable to non-technical users, and they do not show which of the user's signals led to a particular recommendation.
T: Explain an individual decision to non-technical users with its main factors in plain language, not with model statistics, bare scores or code.

G: ## Estimating cost before you build
Before deployment there is no bill to analyze yet, so you need a planning tool that models expected usage.
## AWS Pricing Calculator
- Free web tool at `calculator.aws` for estimating the monthly cost of AWS services.
- You add services and enter expected usage. For an Amazon Bedrock app that might be: model, number of requests per month, average input and output tokens per request, plus supporting services such as AWS Lambda, Amazon S3, and a vector store for a knowledge base.
- Estimates can be grouped, saved and shared as a link or exported.
Example: 1 million requests/month × 1,000 input tokens × 300 output tokens with a chosen model gives a token cost you can compare against a smaller model or batch inference.
After launch, tools such as AWS Cost Explorer and AWS Budgets track real spend.
W: AWS Pricing Calculator: it estimates costs of AWS services, including Bedrock, from planned usage before anything is deployed.
X: A=AWS Cost Anomaly Detection: it uses machine learning to detect and alert on unusual spend in services that are already deployed. With no application running yet, there is no spend for it to analyze.
C=AWS Trusted Advisor: Trusted Advisor inspects resources already running in your account and suggests cost, security and performance improvements. It cannot estimate an application that does not exist yet.
D=AWS CloudTrail Lake: CloudTrail Lake stores and queries API activity logs with SQL. It answers "who did what", not "what will this cost".
T: For pre-deployment cost estimates use AWS Pricing Calculator; Cost Anomaly Detection, Trusted Advisor and CloudTrail Lake work on resources and activity that already exist.
