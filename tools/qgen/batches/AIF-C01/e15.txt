@ Q000090 explain
G: ## Knowledge in the weights versus knowledge in the prompt
Fine-tuning stores knowledge in the model's weights. Anything that changes after training, like today's stock count, is outdated until you train again, and each fine-tuning run costs time and money.
**Retrieval Augmented Generation (RAG)** keeps the model unchanged and fetches current data at request time:
- The user asks "Is the blue jacket in stock in size M?"
- The app queries the inventory source (a database, API or a vector index of documents).
- The retrieved facts are added to the prompt, and the FM answers from them.
When inventory changes, only the data source is updated; the next question already sees the new values. Amazon Bedrock Knowledge Bases provides managed RAG over documents and can also query structured data sources, and an agent can call APIs for live values.
Note: Amazon Bedrock Agents was renamed Bedrock Agents Classic and closed to new customers on 2026-07-30; existing customers can keep using it, and AWS points new agent builds to Amazon Bedrock AgentCore. Exam questions may still name Bedrock Agents.
W: Retrieval Augmented Generation (RAG): it supplies the latest data at query time without retraining, so daily changes are reflected immediately at a fraction of the cost of repeated fine-tuning.
X: A=Fine-tuning: bakes information into the weights, so daily-changing inventory would need a new training job every day, which is exactly what the company cannot afford.
C=Model distillation: produces a smaller copy of a larger model to cut inference cost; the student still only knows what it was trained on and goes stale the same way.
D=Full pretraining: builds a model from scratch with massive data and compute, the most expensive option, and its knowledge is frozen at training time as well.
T: Frequently changing facts belong in retrieval (RAG), not in the weights; any training-based method goes stale as soon as the data changes.

@ Q000093 explain
G: ## Amazon Bedrock model evaluation
Picking the right FM means comparing candidates on your own prompts. Amazon Bedrock includes a managed evaluation feature so you do not have to build scripts, scoring logic and reviewer tools yourself.
Evaluation options:
- **Automatic (programmatic)**: runs the prompts through each model and computes metrics such as accuracy, robustness and toxicity, using built-in datasets or your own prompt dataset in Amazon S3.
- **Model as a judge**: another FM scores responses on criteria like correctness, completeness and helpfulness.
- **Human evaluation**: human reviewers from your own work team rate or compare responses.
Results are stored as reports, so you can compare models side by side, for example three models on 500 support questions, and pick the best one for cost and quality.
Note: Amazon Bedrock Agents was renamed Bedrock Agents Classic and closed to new customers on 2026-07-30; existing customers can keep using it, and AWS points new agent builds to Amazon Bedrock AgentCore. Exam questions may still name Bedrock Agents.
W: Model Evaluation in Amazon Bedrock: it is the built-in feature for comparing FMs on the same prompts with automatic metrics or human evaluators, without custom tooling.
X: B=Knowledge Bases for Amazon Bedrock: provides managed RAG by connecting models to your documents; it does not run evaluation jobs comparing models.
C=Agents for Amazon Bedrock: orchestrates multi-step tasks and tool calls for an application; it is for building workflows, not scoring model outputs (and it is now Bedrock Agents Classic, closed to new customers, with AgentCore as the successor for new agents).
D=Guardrails for Amazon Bedrock: filters and restricts inputs and outputs for safety; it enforces policies but does not compare model quality.
T: Comparing FMs with metrics or human reviewers is Bedrock model evaluation; Knowledge Bases, Agents and Guardrails are building blocks of the application itself.

@ Q000128 explain
G: ## Agents act with an IAM role
An Amazon Bedrock agent calls tools through action groups, often AWS Lambda functions that in turn call internal APIs. Every call runs with the permissions of an IAM role, so the role, not the prompt, decides what the agent can actually do.
## Least privilege
Least privilege means granting only the actions and resources a job needs.
- For an order-status lookup, allow only read actions such as a `GetOrderStatus` API on the order resources.
- Leave out write actions like `CancelOrder` or `UpdateOrder`, so even a manipulated or confused agent cannot perform them.
- Prompt instructions are not a security boundary: prompt injection or model mistakes can make an agent try actions it was told to avoid.
The same rule applies to agents built on Amazon Bedrock AgentCore: each tool call should run with narrowly scoped permissions.
Note: Amazon Bedrock Agents was renamed Bedrock Agents Classic and closed to new customers on 2026-07-30; existing customers can keep using it, and AWS points new agent builds to Amazon Bedrock AgentCore. Exam questions may still name Bedrock Agents.
W: Least privilege, read-only actions: if the role can only read order status, modification or cancellation is impossible regardless of what the model generates.
X: A=Full access plus prompt instructions: prompts can be bypassed by prompt injection or ignored by the model, and the full permissions would then let the agent change or cancel orders.
B=Shared IAM user credentials: long-term keys shared across agents are hard to rotate, cannot be scoped per agent and make it impossible to tell which agent made a call. Agents should use their own roles with temporary credentials.
D=AdministratorAccess: this grants every action on every resource in the account, the opposite of the requirement, and turns any agent mistake into a possible account-wide incident.
T: Control what an agent can do with narrowly scoped IAM permissions, never with prompt instructions or broad access.

@ Q002471 explain
G: ## Why generative models are not calculators
A foundation model produces text by sampling tokens from probabilities. It has learned patterns of arithmetic, but it does not execute exact calculations.
- Multi-step arithmetic on large numbers can go wrong, for example a digit carried incorrectly in a total.
- With sampling settings above zero, the same prompt can return different answers, so results may not be reproducible.
## A better design
Let the model handle language and let deterministic code handle numbers.
- The model extracts values or decides which calculation to run.
- A tool, such as a Lambda function called by an agent (Bedrock Agents or Amazon Bedrock AgentCore) or a code interpreter, computes the exact result.
- The model then explains the result in plain language.
Example: the model reads a request for quarterly revenue, calls a function that sums ledger entries, and reports the exact figure returned.
Note: Amazon Bedrock Agents was renamed Bedrock Agents Classic and closed to new customers on 2026-07-30; existing customers can keep using it, and AWS points new agent builds to Amazon Bedrock AgentCore. Exam questions may still name Bedrock Agents.
W: Probabilistic outputs and arithmetic errors: exact, reproducible financial calculations need deterministic results, and a generative model cannot guarantee them on its own.
X: A=Numbers must become images: models read numbers as text tokens directly; converting statements to images would add a step, not solve a real limitation.
C=Models always refuse financial tasks: there is no universal built-in refusal of financial work. Models commonly summarize and analyze financial text; the problem is exactness, not refusal.
D=A year of training on company data: using a foundation model needs no training at all, and customization such as fine-tuning takes far less than a year. Training would not make arithmetic exact anyway.
T: Generative AI is probabilistic, so exact and reproducible numbers should come from deterministic tools that the model calls, not from generated text.

@ Q002486 explain
G: ## What Amazon Bedrock Agents do
A plain model can only produce text. An **agent** can also take actions: it reads the user's request, plans the steps, calls external APIs, and uses the results to finish the task.
## Action groups
An **action group** describes what the agent is allowed to do:
- The operations are defined with an OpenAPI schema or function details (name, description, parameters such as `room`, `date`, `startTime`).
- Each action is fulfilled by an AWS Lambda function, or the agent can return control to your application to run it.
Example: "Book a room for 6 people tomorrow at 10 am." The agent calls `checkAvailability`, picks a free room, then calls `createBooking` and confirms the result to the user.
Agents can also use knowledge bases and guardrails, but the API calls are what make booking possible.
## Availability note
Amazon Bedrock Agents was renamed Bedrock Agents Classic and closed to new customers on 2026-07-30; existing customers can keep using it, and AWS points new agent builds to Amazon Bedrock AgentCore (for example, AgentCore Gateway exposes existing APIs as tools). Exam questions may still name Bedrock Agents.
W: Agents with action groups: action groups let the agent call the internal booking APIs with parameters taken from the user's request, turning a conversation into a completed task. It remains the answer the exam expects, even though new customers would now build the same agent on AgentCore.
X: A=Knowledge Bases: they retrieve document passages to ground answers; they can explain the booking policy but cannot call an API to reserve a room.
B=Guardrails: Guardrails filter harmful content, denied topics and sensitive data in prompts and responses; they add safety, not the ability to take actions.
D=Model evaluation: evaluation jobs compare and score models on test prompts before choosing one; they play no part in serving user requests.
T: When the assistant must do something (call APIs) rather than just answer, use an agent with tools (Bedrock Agents action groups, or AgentCore for new builds); knowledge bases only retrieve information.

@ Q002534 explain
G: ## Human-in-the-loop for ML predictions
Even good models are unsure about some inputs. A common pattern is to accept confident predictions automatically and send uncertain ones to people.
## Amazon Augmented AI (A2I)
Amazon A2I provides managed human review workflows for ML predictions. You define:
- A **flow definition** with conditions, such as "send to review when confidence is below 0.80".
- A **worker task template** that shows reviewers the input and the model's prediction.
- A **work team**: your own employees (a private workforce) or a vendor workforce.
A2I integrates directly with Amazon Textract and Amazon Rekognition, and works with any custom model through the `StartHumanLoop` API. Reviewer answers are stored in Amazon S3 and can also feed retraining.
Example: an invoice-processing app accepts extracted totals above 0.9 confidence and routes the rest to accounts staff for a human check before payment.
Note: Amazon Mechanical Turk reached end of support on 2026-09-29, and the Mechanical Turk (public) workforce option in A2I ended with it; private and vendor workforces still work.
W: Amazon Augmented AI (A2I): it is built to route low-confidence predictions to human reviewers based on rules you set, and to collect their decisions before the result is used.
X: B=CloudWatch Logs: it stores and searches log data for monitoring and troubleshooting; it has no reviewer task interface or routing of predictions to people.
C=Amazon SNS: SNS can notify someone that something happened, but it provides no review interface, no task assignment and no way to capture the reviewer's decision.
D=Step Functions Express workflows: Express workflows are for short, high-volume runs (up to five minutes) and do not support the callback pattern needed to wait for a person; they would also require building the whole review UI yourself.
T: For human review of uncertain ML predictions, use A2I; notifications, logs and generic workflows do not give reviewers a task queue.

G: ## Getting labeled training data
Supervised models need labeled examples, and labeling thousands of images by hand is a large workflow problem: distributing tasks, managing workers, checking quality.
**Amazon SageMaker Ground Truth** manages this:
- Built-in task templates for bounding boxes, image classification, semantic segmentation, text and more.
- A choice of workforce: your own **private** team or a **vendor** workforce.
- Features such as combining answers from several workers to improve quality, and optional **automated data labeling** that uses a model to label easy items so humans handle the hard ones.
## Availability notes
- Amazon Mechanical Turk reached end of support on 2026-09-29, and the Mechanical Turk (public) workforce option in Ground Truth ended with it.
- **SageMaker Ground Truth Plus**, the turnkey option where AWS ran the labeling project with an expert workforce, reached end of support on 2026-06-30.
W: SageMaker Ground Truth: it is the SageMaker service for creating labeled datasets with human workers, including task templates, workforce management and quality controls.
X: A=SageMaker Clarify: detects bias in data and models and explains predictions; it does not create labels.
C=SageMaker Model Monitor: watches deployed endpoints for data and quality drift after deployment, long after labeling is done.
D=SageMaker Neo: compiles trained models to run efficiently on specific hardware, such as edge devices; it plays no role in labeling data.

@ Q002603 explain
G: ## Why a model forgets between sessions
A foundation model is stateless. Each API call sees only what is inside that request: the system prompt, the conversation turns the application sends, and any retrieved context. When the session ends and a new one starts, nothing from the old conversation is inside the model's weights.
## Adding memory from the outside
To remember a user, the application stores facts in a store it controls and puts the relevant ones back into the prompt next time.
- **Short-term memory** keeps the turns of the current conversation.
- **Long-term memory** keeps extracted facts, such as "prefers answers in Korean" or "uses the `eu-west-1` Region", keyed by a user id.
- On AWS, Amazon Bedrock AgentCore Memory provides both kinds as a managed service, and Amazon Bedrock Agents can keep session summaries across sessions. A custom store such as DynamoDB also works.
Example: the user says "always show prices in euros". The agent saves that preference; days later a new session loads it and adds it to the context before the model answers.
Note: Amazon Bedrock Agents was renamed Bedrock Agents Classic and closed to new customers on 2026-07-30; existing customers can keep using it, and AWS points new agent builds to Amazon Bedrock AgentCore, so AgentCore Memory is the managed choice for new agents. Exam questions may still name Bedrock Agents.
W: Persistent memory stored outside the model: preferences saved in a memory store survive the end of a session and are injected into later prompts, which is the only way a stateless model can "remember" a user.
X: A=Higher temperature: temperature only changes how random the token sampling is. It adds no information about the user, so the new session still starts with no knowledge of past preferences.
B=New model version every session: swapping models changes capabilities, not state. Any model version is equally stateless, and constant switching would make behavior less consistent, not more personal.
C=Longer max token limit: the maximum output tokens caps how long one reply can be. It does not store anything between sessions, so earlier preferences are still lost.
T: Models are stateless; cross-session memory lives in an external store that the agent writes to and reads back into the prompt, not in sampling or output settings.

@ Q002614 explain
G: ## What an AI agent needs
An AI agent uses a foundation model to plan steps and then acts by calling tools. For a task such as "create a support ticket, check the customer's order status and issue a refund", the agent calls a ticketing API, an order system and a payment system in sequence.
## Tools
Tools are defined functions or APIs the model can request. In Amazon Bedrock Agents they are action groups, described by an OpenAPI schema or function details and fulfilled by a Lambda function or returned to the application; Amazon Bedrock AgentCore Gateway can expose existing APIs as tools.
## Guardrails on actions
Because an agent changes real systems, it needs:
- Least-privilege IAM permissions for each tool.
- Limits such as allowed actions, spending caps or human confirmation for risky steps (Bedrock Agents supports user confirmation and return of control).
- Logging and tracing (agent traces, CloudTrail, CloudWatch) so every action can be audited.
Note: Amazon Bedrock Agents was renamed Bedrock Agents Classic and closed to new customers on 2026-07-30; existing customers can keep using it, and AWS points new agent builds to Amazon Bedrock AgentCore. Exam questions may still name Bedrock Agents.
W: C=Controls that limit and log actions: permissions, limits and audit logs keep an autonomous agent from taking harmful actions and make every step reviewable.
E=Ability to call tools or APIs: an agent can only act on internal systems through tools; without them it can only produce text.
X: A=Larger image generation model: the task is multi-step work across internal systems, which needs tool calls and reasoning, not image generation.
B=Higher temperature: more randomness makes planning and tool-call arguments less predictable, which is the opposite of what reliable multi-step execution needs.
D=Remove all instructions: instructions define the agent's role, rules and limits; removing them makes behavior unpredictable and unsafe rather than more capable.
T: Agents act through tools and must be constrained by permissions, limits and logging; creativity or fewer rules do not make them capable or safe.
