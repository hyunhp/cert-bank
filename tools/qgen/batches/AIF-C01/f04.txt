@ AIF-C01 D1 T1.1 applied troubleshooting +AIB-C01:D1
S: A team trains a classification model that achieves 99% accuracy on the training dataset but only 62% accuracy on a held-out test dataset. What does this gap most likely indicate?
A: The training data must have been unlabeled, so the model did not learn the target.
B: The model is overfitting: it memorized the training examples and generalizes poorly.
C: The model has achieved perfect fairness across the customer groups in the data.
D: The model is underfitting because it is too simple to capture the real pattern.
K: B
G: ## Why we keep a held-out test set
Data is split before training: the model learns from the **training set**, and a separate **test set** that it never sees measures how well it will do on new data. The goal is **generalization**, performing well on data the model has not seen.
## Reading the accuracy gap
- **Overfitting**: very high training accuracy, much lower test accuracy. The model has memorized noise and specific details of the training examples. 99% versus 62% is a classic sign.
- **Underfitting**: low accuracy on both sets, because the model is too simple to capture the pattern.
- **Good fit**: training and test accuracy are both good and close to each other.
Common remedies for overfitting include more (or more varied) training data, regularization, a simpler model, fewer features and early stopping.
W: Overfitting: the model fits the training data almost perfectly but fails on unseen data, so the large gap shows poor generalization.
X: A=Unlabeled training data: accuracy can only be measured when labels exist, and the team reports accuracy on both sets, so the data must be labeled. Label type does not create a train/test gap.
C=Perfect fairness: fairness concerns how outcomes differ across groups. Nothing in two overall accuracy numbers says anything about fairness, and a 37-point drop is a warning sign, not an achievement.
D=Underfitting: an underfit model would also score poorly on the training set. A 99% training accuracy rules out underfitting.
T: High training accuracy with much lower test accuracy means overfitting; underfitting shows poor accuracy on both.

@ AIF-C01 D3 T3.3 advanced tradeoff
S: A company needs its FM responses to reflect information that changes daily, such as current inventory levels, and cannot afford to retrain the model every day. Compared to fine-tuning, which customization approach is MOST cost-effective and appropriate for this requirement?
A: Fine-tuning the model again on each day's inventory
B: Retrieval Augmented Generation (RAG) at query time
C: Model distillation into a smaller student model
D: Full pretraining of a new model on company data
K: B
G: ## Knowledge in the weights versus knowledge in the prompt
Fine-tuning stores knowledge in the model's weights. Anything that changes after training, like today's stock count, is outdated until you train again, and each fine-tuning run costs time and money.
**Retrieval Augmented Generation (RAG)** keeps the model unchanged and fetches current data at request time:
- The user asks "Is the blue jacket in stock in size M?"
- The app queries the inventory source (a database, API or a vector index of documents).
- The retrieved facts are added to the prompt, and the FM answers from them.
When inventory changes, only the data source is updated; the next question already sees the new values. Amazon Bedrock Knowledge Bases provides managed RAG over documents and can also query structured data sources, and an agent can call APIs for live values.
Note: Amazon Bedrock Agents was renamed Bedrock Agents Classic and closed to new customers on 2026-07-30; existing customers can keep using it, and AWS points new agent builds to Amazon Bedrock AgentCore. Exam questions may still name Bedrock Agents.
W: Retrieval Augmented Generation (RAG): it supplies the latest data at query time without retraining, so daily changes are reflected immediately at a fraction of the cost of repeated fine-tuning.
X: A=Fine-tuning: bakes information into the weights, so daily-changing inventory would need a new training job every day, which is exactly what the company cannot afford.
C=Model distillation: produces a smaller copy of a larger model to cut inference cost; the student still only knows what it was trained on and goes stale the same way.
D=Full pretraining: builds a model from scratch with massive data and compute, the most expensive option, and its knowledge is frozen at training time as well.
T: Frequently changing facts belong in retrieval (RAG), not in the weights; any training-based method goes stale as soon as the data changes.

@ AIF-C01 D5 T5.2 applied use-case
S: A company wants to continuously verify that every Amazon S3 bucket used for storing AI training data remains encrypted and never becomes publicly accessible, and to automatically flag any bucket that drifts out of compliance. Which AWS service should they use to implement this ongoing configuration compliance check?
A: Amazon GuardDuty with S3 Protection
B: AWS Config with managed compliance rules
C: AWS CloudTrail with S3 data events logged
D: Amazon Inspector with automated scanning
K: B
G: ## Configuration compliance
AWS Config records the configuration of supported resources, such as S3 buckets, and keeps a history of changes. **Config rules** evaluate each resource against a desired setting and mark it `COMPLIANT` or `NON_COMPLIANT`.
## Managed rules for S3
AWS provides ready-made managed rules, for example:
- `s3-bucket-server-side-encryption-enabled` checks that default encryption is set.
- `s3-bucket-public-read-prohibited` and `s3-bucket-public-write-prohibited` check that buckets do not allow public access.
Rules run when a resource changes or on a schedule, so a bucket that drifts is flagged soon after the change. You can add automatic remediation with Systems Manager Automation documents, and conformance packs group rules for many accounts.
W: AWS Config with managed rules: it continuously evaluates bucket settings against the encryption and public access requirements and flags any bucket that falls out of compliance.
X: A=GuardDuty with S3 Protection: GuardDuty, including S3 Protection, detects threats from activity, such as unusual API calls or suspicious data access patterns. It is not a tool for checking that bucket settings match a required baseline.
C=CloudTrail with S3 data events: CloudTrail, even with S3 data events logged, records who called which API. It shows that a bucket policy changed, but it does not evaluate whether the result is compliant.
D=Inspector automated scanning: Inspector scans compute workloads for software vulnerabilities and network exposure; it does not check S3 bucket encryption or public access settings.
T: Is this resource configured the way it should be, continuously? That is AWS Config rules, not threat detection or API logging.

@ AIF-C01 D3 T3.1 advanced tradeoff
S: A company currently uses a very large, general-purpose FM to classify short product reviews as positive or negative. Inference is slow and expensive for this simple task. Which change would MOST directly reduce cost and latency while likely maintaining acceptable accuracy for this narrow task?
A: Raise the maximum output token limit so long responses are not cut off
B: Increase the temperature parameter to make responses more varied
C: Switch to a smaller model that is sized appropriately for the task
D: Add more few-shot examples to each prompt to improve label accuracy
K: C
G: ## Model size, cost and speed
A model's size (roughly, its number of parameters) drives how much compute every token needs. Larger models cost more per token and generate more slowly.
## Simple tasks rarely need the biggest model
Classifying a short review as positive or negative is a narrow task. A smaller model, or even a classic ML classifier, can often do it with similar accuracy.
- Example: a large model at 2 seconds and a higher token price versus a small model at 0.3 seconds and a fraction of the price, both scoring about the same on a labeled test set.
- The right approach is to evaluate a smaller model on sample reviews and switch if accuracy is acceptable.
- Other ways to save cost, such as shorter prompts, help less than changing the model itself.
W: Right-size the model: a smaller model uses less compute per token, which directly lowers cost and latency, and is usually accurate enough for simple binary classification.
X: A=Higher max output tokens: allowing longer outputs can only increase cost and time; a positive or negative label needs only a few tokens.
B=Higher temperature: temperature changes randomness in token selection, not compute cost, and more randomness can make labels less consistent.
D=More few-shot examples: every example adds input tokens to every request, raising cost and latency even if accuracy improves slightly.
T: For a narrow task, the biggest lever on cost and latency is choosing a smaller model that is still accurate enough.

@ AIF-C01 D3 T3.1 applied tradeoff
S: A financial trading firm needs an FM-powered assistant that returns responses well under 200 milliseconds to support real-time decisions, even if it means using a smaller or less capable model. Which FM characteristic is the firm prioritizing, and what is it trading off?
A: Context window size, trading off latency to fit longer inputs
B: Multilingual support, trading off cost for wider language coverage
C: Modality, trading off accuracy to accept image and audio inputs
D: Latency, trading off some model capability and response quality
K: D
G: ## Common FM selection dimensions
When choosing a foundation model you balance several characteristics:
- **Latency**: time until the response starts and finishes
- **Capability or quality**: reasoning depth and accuracy
- **Cost** per token
- **Context window**: how much text fits into one request
- **Modality**: text, image, audio or video input and output
- **Language support**
## The latency versus quality tradeoff
Smaller models generate tokens faster and respond sooner, but they usually reason less deeply than the largest models. A system that must answer in well under 200 ms, such as a trading assistant, cannot wait for a large model's slower generation.
Example: a small model that classifies a news headline as bullish or bearish in 80 ms is more useful for live trading than a larger model that writes a better analysis in 3 seconds.
W: Latency over quality: the firm explicitly accepts a smaller or less capable model to guarantee fast responses, so it prioritizes latency and gives up some capability.
X: A=Context window, trading off latency: the requirement is about response speed, not how much text fits in a request, and the firm is prioritizing low latency, not trading it away.
B=Multilingual support, trading off cost: nothing in the scenario involves languages, and the tradeoff described is capability, not cost.
C=Modality, trading off accuracy: modality means input or output types such as text or images; the firm is not changing modality, it is choosing a faster model.
T: A hard response-time limit makes latency the priority, and the usual price is a smaller, less capable model.

@ AIF-C01 D4 T4.2 applied use-case +AIB-C01:D3
S: A team wants to understand which input features most heavily influenced a specific model's prediction for an individual customer record, in order to explain the decision to that customer. Which AWS capability is best suited for this?
A: Amazon SageMaker Clarify feature attribution
B: AWS Cost Explorer with resource-level data
C: AWS Trusted Advisor best-practice checks
D: CloudWatch Logs Insights on inference logs
K: A
G: ## Feature attribution
Feature attribution explains a model's output by showing how much each input feature contributed to it.
- **Global** attribution ranks which features matter most across the whole dataset.
- **Local** attribution explains one individual prediction.
## SageMaker Clarify and SHAP
Amazon SageMaker Clarify computes feature attributions using a SHAP-based method (Kernel SHAP). SHAP values show, for a given record, how each feature pushed the prediction up or down from a baseline.
- Example: for a customer flagged as likely to churn, Clarify might show `support_tickets_last_30_days` contributed most, followed by `contract_months_remaining`.
Clarify can run these explanations in processing jobs, provide online explainability for endpoints, and monitor attribution drift over time with SageMaker Model Monitor.
## Availability
Amazon SageMaker Clarify is no longer open to new customers (AWS documentation, as of 2026-11). Existing customers can keep using it as normal; AWS keeps it secure and available but plans no new features, and points new customers to the SHAP library, standard bias-metric code and Amazon Bedrock Evaluations. The exam guide still lists Clarify, so exam questions treat it as the SageMaker AI capability for bias detection and explainability.
W: SageMaker Clarify feature attribution: it computes SHAP-based per-record attributions that show which features most influenced that customer's prediction, which is what is needed to explain the decision.
X: B=Cost Explorer with resource-level data: Cost Explorer analyzes AWS spending and usage trends, even per resource; it has no view into how a model weighed input features.
C=AWS Trusted Advisor: Trusted Advisor checks an account against best practices in areas such as cost optimization, security, performance and service quotas; it does not explain model predictions.
D=Logs Insights on inference logs: Logs Insights queries log data you already wrote, such as logged requests and responses; it cannot compute feature contributions for a model's prediction.
T: To explain why a model made a specific prediction, use SageMaker Clarify feature attribution (SHAP).
V: Amazon SageMaker

@ AIF-C01 D3 T3.1 advanced comparison
S: A company is comparing ways to customize an FM for its use case. Ordering the following approaches from LOWEST to HIGHEST typical cost and implementation complexity, which sequence is correct?
A: Fine-tuning < Prompt engineering < RAG < Full pretraining
B: Prompt engineering < RAG < Fine-tuning < Full pretraining
C: RAG < Full pretraining < Prompt engineering < Fine-tuning
D: Full pretraining < Fine-tuning < RAG < Prompt engineering
K: B
G: ## The customization ladder
From cheapest and simplest to most expensive and complex:
- **Prompt engineering (in-context learning)**: change only the prompt, for example add instructions or examples. Minutes of work, no infrastructure.
- **RAG**: add a retrieval system (embeddings, a vector store, a sync process) that inserts relevant data into prompts. More moving parts, but no model training.
- **Fine-tuning**: train an existing model further on labeled examples. Needs curated data, training jobs, evaluation and usually paid hosting for the custom model.
- **Full pretraining**: train a model from scratch on massive datasets with large GPU clusters for weeks or months. Only a few organizations do this.
Rule of thumb: start at the bottom of the ladder and move up only if the cheaper step cannot meet your needs.
W: Prompt engineering < RAG < fine-tuning < full pretraining: each step adds more data preparation, infrastructure and expertise, and pretraining from scratch is by far the costliest.
X: A=Fine-tuning first: fine-tuning needs training data and compute, so it cannot be cheaper than editing a prompt, which needs neither.
C=RAG cheapest, pretraining second: prompt engineering is simpler than RAG, and full pretraining is the most expensive option, not the second cheapest.
D=Reversed order: this lists the ladder from most to least expensive; full pretraining is the costliest, not the cheapest.
T: Customization gets more expensive from prompts to RAG to fine-tuning to pretraining; start with the cheapest step that works.

@ AIF-C01 D5 T5.1 applied use-case
S: A company building a RAG-based application needs to track which source documents and versions were used to build and update its embeddings, so it can trace a given model output back to its original data sources for compliance reviews. Which AWS capability most directly supports this data lineage and cataloging need?
A: Amazon CloudWatch Logs Insights queries
B: Amazon Bedrock Guardrails with contextual grounding
C: AWS Glue Data Catalog with custom metadata
D: AWS KMS customer managed keys with key policies
K: C
G: ## Why RAG needs data lineage
In a retrieval-augmented generation (RAG) app, source documents are split into chunks, turned into embeddings and stored in a vector index. When an answer is questioned in a compliance review, you need to know which document, and which version of it, produced the chunk the model used.
## Catalogs and metadata
A data catalog stores metadata about datasets: where they live, their schema, owners, versions and custom properties.
- The AWS Glue Data Catalog holds table and dataset definitions, including their Amazon S3 locations and schemas, and crawlers can keep them up to date as data changes.
- You can add custom properties such as source system, document version and ingestion date to catalog entries, and record the same identifiers as metadata on each chunk in the vector store.
- Example: a chunk tagged `doc=policy-17, version=4` can be matched to the catalog entry that describes the source dataset and its S3 location used for the embedding run.
For end-to-end lineage graphs, AWS also offers lineage features in Amazon SageMaker Catalog (Amazon DataZone), which build on catalog metadata; among the listed options, only the Glue Data Catalog addresses cataloging at all.
W: Glue Data Catalog with metadata tracking: it is the AWS service built to catalog datasets and their metadata, so recording source and version details there gives reviewers a record of which sources fed each embedding build.
X: A=CloudWatch Logs Insights: it queries log events such as application or invocation logs. It can show that a request happened, but it does not keep a catalog of source datasets and their versions.
B=Guardrails with contextual grounding: guardrails filter prompts and responses for harmful content, denied topics or sensitive information, and contextual grounding checks whether a response is supported by the supplied source text. They do not record where training or retrieval data came from.
D=KMS customer managed keys: KMS keys and their key policies control who can encrypt and decrypt data. It says nothing about which documents or versions a dataset contains.
T: Tracing outputs back to source data is a metadata and cataloging problem (Glue Data Catalog), not logging, content filtering or encryption.
V: AWS Glue

@ AIF-C01 D3 T3.2 applied use-case
S: A developer wants an FM to solve multi-step math word problems more accurately by having it explicitly work through intermediate reasoning steps before giving a final answer. Which prompting technique should the developer use?
A: Chain-of-thought prompting
B: Negative prompting (exclusions)
C: Reusable prompt templating
D: Zero-shot instruction prompting
K: A
G: ## Chain-of-thought prompting
Multi-step problems go wrong when a model jumps straight to an answer. **Chain-of-thought (CoT)** prompting asks the model to write out intermediate steps first, for example with "Think step by step" or by showing a worked example that includes reasoning.
Because each step is generated before the next, later steps can build on correct earlier ones.
## Example
"A store sells pens at 3 for $2. How much do 12 pens cost? Show your reasoning, then give the final answer."
- 12 pens is 12 / 3 = 4 groups
- 4 groups x $2 = $8
- Final answer: $8
CoT often improves accuracy on math, logic and planning tasks, at the cost of more output tokens.
W: Chain-of-thought prompting: it makes the model work through intermediate reasoning steps before the final answer, which is exactly what improves multi-step math accuracy.
X: B=Negative prompting: negative prompts list things to exclude, mainly in image generation; they do not make a model reason through steps.
C=Prompt templating: templates standardize prompt structure and fields across requests; a template alone does not ask for step-by-step reasoning.
D=Zero-shot prompting: zero-shot means asking the task with no examples; it does not by itself make the model show intermediate steps.
T: When a task needs several reasoning steps, ask the model to show them: that is chain-of-thought prompting.

@ AIF-C01 D3 T3.2 applied use-case
S: A team uses an FM to generate marketing images and wants to prevent the model from including any text or watermarks in the generated images. Which prompt engineering technique should they use?
A: A negative prompt naming the elements to exclude
B: Few-shot prompting with example captions
C: Chain-of-thought prompting before generation
D: Increasing the temperature (randomness) setting
K: A
G: ## Negative prompts in image generation
Image generation models accept a text prompt describing what to draw. Many also accept a **negative prompt**: a list of things the image should not contain.
- On Amazon Bedrock, image models such as Amazon Nova Canvas take a `negativeText` field next to the main prompt text.
- The model steers away from the concepts in the negative prompt while generating.
## Why a separate field works better
Writing "no text" inside the main prompt can backfire because the word "text" itself becomes part of what the model pays attention to. A dedicated negative prompt tells the model to exclude it.
Example: prompt "A cozy coffee shop interior with warm lighting", negative prompt "text, watermark, logo, letters".
W: Negative prompt: listing text and watermarks as elements to exclude directly steers the image model away from generating them.
X: B=Few-shot prompting: few-shot adds example input and output pairs to teach a pattern, mainly for text tasks; it is not a way to exclude specific visual elements.
C=Chain-of-thought prompting: chain of thought asks a model to reason step by step before answering; it helps with logic problems, not with keeping objects out of an image.
D=Higher temperature: increasing randomness makes outputs more varied, which could make unwanted elements more likely, not less.
T: To keep something out of a generated image, name it in a negative prompt.

@ AIF-C01 D4 T4.1 applied comparison
S: A legal team is reviewing risks associated with deploying a generative AI writing assistant. Risk 1: the company is sued for using copyrighted text without authorization. Risk 2: customers lose confidence after the assistant repeatedly invents nonexistent product features. Which option correctly matches Risk 1 and Risk 2, respectively, to their underlying cause?
A: Risk 1 = hallucinated citations; Risk 2 = biased outputs
B: Risk 1 = biased outputs; Risk 2 = intellectual property infringement
C: Risk 1 = trust loss; Risk 2 = intellectual property infringement
D: Risk 1 = intellectual property infringement; Risk 2 = hallucination
K: D
G: ## Two distinct generative AI risks
- **Intellectual property (IP) infringement**: a model trained on, or reproducing, copyrighted material without permission can expose the company to legal claims. The harm is legal and financial, and the cause is how content was sourced or reproduced.
- **Hallucination**: the model generates plausible but false statements, such as describing a product feature that does not exist. Repeated hallucinations lead to **loss of trust**: customers stop believing anything the assistant says.
## Matching cause to effect
Trust loss is an outcome, not a root cause, and bias is a different problem again (systematically unfair outputs for certain groups).
- Risk 1 (a lawsuit over copyrighted text) is caused by IP infringement.
- Risk 2 (customers losing confidence because features are invented) is caused by hallucination that leads to trust loss.
Mitigations differ: IP risk is handled with licensed data, provenance review and output filtering; hallucination with grounding (RAG), guardrails and human review.
W: IP infringement, then hallucination leading to trust loss: using copyrighted text without authorization is an IP problem, and inventing nonexistent features is hallucination whose consequence is lost customer confidence.
X: A=Hallucinated citations, then biased outputs: a copyright lawsuit comes from unauthorized use of protected text, not from invented citations, and inventing product features is fabrication, not bias against a group.
B=Biased outputs, then IP infringement: bias concerns unfair treatment of groups, not unauthorized use of copyrighted text, and made-up features do not infringe anyone's IP.
C=Trust loss, then IP infringement: trust loss is the effect of Risk 2, not the cause of a copyright suit, and invented features are hallucinations rather than IP violations.
T: Copyright misuse is an IP risk; invented facts are hallucinations whose consequence is lost trust.

S: A company plans to use AI services from AWS and wants published documentation describing the intended use cases, limitations and responsible AI design choices of each service before approving them. Which resource provides this?
A: AWS AI Service Cards, transparency documents that AWS publishes for individual AI services and models, with deployment guidance.

@ AIF-C01 D5 T5.1 advanced use-case
S: A company's AI app retrieves documents from S3. It wants only this app's role to read the bucket. Which control enforces this at the bucket level?
A: An S3 event notification that triggers on each upload
B: An S3 lifecycle rule that archives objects after a day
C: An S3 storage class change to S3 Glacier Flexible Retrieval
D: A resource policy on the bucket that admits one principal
K: D
G: ## Who may read an S3 bucket
Access to Amazon S3 is decided by policies. Two kinds matter here:
- **Identity-based policies** are attached to an IAM user or role and say what that identity may do.
- A **bucket policy** is a resource-based policy attached to the bucket itself. It names the principals (accounts, roles, users) that may act on the bucket and its objects.
## Locking a bucket to one role
Because the bucket policy lives on the bucket, it applies to every request, whoever sends it. A common pattern for a RAG or document-retrieval app:
- Allow `s3:GetObject` and `s3:ListBucket` for the app's role, for example `arn:aws:iam::111122223333:role/doc-retriever`.
- Add a `Deny` for all other principals using a condition such as `aws:PrincipalArn` not equal to that role (usually with an exception for administrators).
- Keep S3 Block Public Access on so no public grant can slip in.
Now even an IAM user with broad S3 permissions in the same account cannot read the documents, because an explicit deny in the bucket policy always wins.
W: Bucket policy for the app's role: it is attached to the bucket and names the allowed principal, so it enforces "only this role may read" at the bucket level regardless of what permissions other identities carry.
X: A=Event notification: notifications send a message to Lambda, SQS, SNS or EventBridge when objects are created or deleted. They react to changes; they never allow or block a read request.
B=Lifecycle rule: lifecycle rules move objects to cheaper storage classes or expire them over time. They manage storage cost and retention, not which principal can call `GetObject`.
C=Glacier Flexible Retrieval: changing the storage class only changes price and retrieval time (objects must be restored before reading). Anyone with permission can still restore and read them, so it is not an access control.
T: Access to a bucket is controlled by policies such as a bucket policy naming the allowed role; notifications, lifecycle rules and storage classes only affect events, retention and cost.
