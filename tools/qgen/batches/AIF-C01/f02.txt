S: A pharmaceutical company has millions of unlabeled internal research papers and wants a foundation model that better understands its domain terminology across many later tasks. It has no labeled question-answer data. Which approach fits best?
A: Prompt engineering with a longer system prompt that defines the company's key terms on every single request
B: Continue pre-training the model on the unlabeled domain documents so its weights absorb terminology
C: Fine-tuning the model on a few hundred labeled question-answer pairs written by the research staff
D: Lowering the temperature setting so the model uses the terminology it already knows more consistently
K: B
G: ## Continued pre-training
**Pre-training** is how a foundation model first learns language: it reads huge amounts of unlabeled text and learns to predict the next token. **Continued pre-training** repeats that process on a new, domain-specific corpus, starting from an existing model.
- Input: **unlabeled** text, such as research papers, lab reports or manuals. No question-answer pairs are needed.
- Result: the model's weights absorb the domain's vocabulary and concepts, for example drug compound names, assay types or regulatory terms.
## Compared with other approaches
- **Fine-tuning** needs **labeled** prompt-completion pairs and teaches a specific task or style.
- **Continued pre-training** needs large volumes of raw domain text and teaches general domain understanding.
- **Prompt engineering** and **inference settings** change a single request, not the model.
## Availability
Amazon Bedrock's model customization page currently lists supervised fine-tuning, reinforcement fine-tuning and distillation, so whether continued pre-training is available depends on the platform and model (for example Amazon Nova customization); check the current documentation.
W: Continued pre-training: millions of unlabeled domain papers are exactly the input it is designed for, and it teaches the model domain terminology that carries over to all later tasks without any labeling effort.
X: A=Longer system prompt: a system prompt can define a few terms per request but cannot convey a whole field's vocabulary, and it consumes tokens on every call.
C=Fine-tuning on a few hundred pairs: fine-tuning needs labeled data and targets a specific task; a few hundred pairs would ignore the millions of unlabeled papers that carry the terminology.
D=Lower temperature: temperature only controls randomness in token selection; it cannot add knowledge of terms the model does not understand.
T: Large amounts of unlabeled domain text call for continued pre-training; labeled task examples call for fine-tuning.
