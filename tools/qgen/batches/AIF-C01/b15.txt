@ AIF-C01 D1 T1.3 expert troubleshooting
S: A payments company tests a new fraud classifier on 100,000 card transactions from last month, of which 400 were confirmed fraud. The model flags 500 transactions, and 300 of the flagged ones turn out to be confirmed fraud. The product manager wants to tell the board that the model reached "99.7 percent accuracy". The fraud team can investigate up to 600 alerts a month, and the chargeback team points out that every missed fraud case costs far more than one wasted investigation. Which assessment of these results is correct?
A: Accuracy is 99.7 percent, yet always predicting "legitimate" scores 99.6; recall is 0.75, precision 0.60 and F1 about 0.67, so report those instead
B: Accuracy is 99.7 percent, which shows the model is ready; precision is 0.75 and recall is 0.60, so it misses 40 percent of the fraud cases
C: Recall is 0.75 and precision 0.60, and F1 is their simple average of 0.675, so accuracy remains the better single number for such imbalanced data
D: Precision is 0.60 and recall 0.75, and because 500 alerts already fit the 600-alert capacity, the next step is raising the threshold to lift precision
K: A
G: ## Build the confusion matrix first
From the numbers in the stem:
- **True positives (TP)**: flagged and really fraud = `300`
- **False positives (FP)**: flagged but legitimate = `500 - 300 = 200`
- **False negatives (FN)**: fraud the model missed = `400 - 300 = 100`
- **True negatives (TN)**: everything else = `100,000 - 300 - 200 - 100 = 99,400`
## Work out each metric
- **Accuracy** = (TP + TN) / all = `99,700 / 100,000 = 0.997`
- **Baseline**: a "model" that always says legitimate is right on `99,600` of `100,000` transactions = `0.996`. On data this imbalanced, accuracy barely separates a useful model from a useless one.
- **Precision** = TP / (TP + FP) = `300 / 500 = 0.60` (how many alerts are real)
- **Recall** = TP / (TP + FN) = `300 / 400 = 0.75` (how much fraud is caught)
- **F1** = harmonic mean = `2 x 0.60 x 0.75 / (0.60 + 0.75) = 0.90 / 1.35 = 0.67`
## Reading the business constraints
Missed fraud is the expensive error, so recall matters most, and the team still has room for about 100 more alerts a month. That argues for a lower threshold (more alerts, higher recall), not a higher one.
W: Accuracy versus baseline: 99.7 percent sounds impressive but beats the always-legitimate baseline by only 0.1 points. Recall 0.75 (300 of 400 frauds caught), precision 0.60 (300 of 500 alerts real) and F1 of about 0.67 describe the model honestly for imbalanced data.
X: B=Swapped precision and recall: 300 of 500 alerts is precision 0.60 and 300 of 400 frauds is recall 0.75, so the model misses 25 percent of fraud, not 40, and high accuracy alone does not show readiness.
C=F1 as a simple average: F1 is the harmonic mean, about 0.67, not the arithmetic mean, and accuracy is exactly the metric that misleads when 99.6 percent of records are one class.
D=Raise the threshold: the metric values are right, but a higher threshold trades recall for precision. Missed fraud is the costly error and the team has spare review capacity, so lowering the threshold is the better direction.
T: On imbalanced data compare accuracy with the majority-class baseline, and report precision, recall and F1, choosing the threshold by which error costs more.
V: Amazon SageMaker AI

@ AIF-C01 D1 T1.2 expert use-case
S: A travel company records about 20,000 customer support calls a week. Each language has its own phone line, so every recording is known to be US English, US Spanish or Brazilian Portuguese. Managers who read only English want each call's transcript in English together with a label saying whether the call was positive, negative, neutral or mixed. Card numbers that callers read aloud must never appear in any stored transcript. The team has no data scientists and wants pretrained AWS AI services only, with no model training. Which THREE services together meet these requirements? (Select THREE)
A: Amazon Transcribe batch jobs with the line's language code and PII redaction enabled, turning each recording into a redacted text transcript
B: Amazon Translate, converting the Spanish and Portuguese transcripts into English text so managers can read every transcript in one language
C: Amazon Comprehend sentiment analysis, labeling each English transcript as positive, negative, neutral or mixed for the managers' report
D: Amazon Polly, converting each call recording into written text in its original language so it can be searched and analyzed later
E: Amazon Lex, reading each completed recording after the call and returning the caller's overall sentiment as a positive or negative intent
F: Amazon SageMaker AI, training a custom multilingual sentiment classifier on a year of transcripts that the support team labels by hand
K: A,B,C
G: ## Match each requirement to a pretrained service
The pipeline has three steps, and each has a managed AWS AI service that needs no training:
- **Speech to text**: Amazon Transcribe. For batch jobs it can redact PII, replacing each detected item with `[PII]`. Batch redaction supports English, US Spanish (`es-US`) and Brazilian Portuguese (`pt-BR`), among others.
- **Text to another language**: Amazon Translate translates unstructured text on demand.
- **Text to sentiment**: Amazon Comprehend returns Positive, Negative, Neutral or Mixed for a document.
## The detail that matters
Transcribe can identify the language of a recording automatically, but the documentation states that **redaction is not compatible with language identification**. Here each language has its own phone line, so the job can pass the known language code and keep redaction on.
## The look-alikes
- **Amazon Polly** goes the other way: text to lifelike speech.
- **Amazon Lex** builds conversational bots (voice or text) and manages the dialog; it is not a post-call sentiment service.
W: A=Transcribe with redaction: it converts the recordings to text and masks card numbers in the transcript, and passing the known language code is what lets redaction run.
B=Translate: it turns the Spanish and Portuguese transcripts into English, which the English-only managers need.
C=Comprehend sentiment: it returns exactly the four labels the report needs (positive, negative, neutral, mixed) from pretrained models.
X: D=Polly: Polly converts text into speech, the opposite direction, so it cannot produce transcripts from call recordings.
E=Lex: Lex builds chatbots that recognize intents during a live conversation; it does not analyze finished recordings for overall sentiment.
F=SageMaker custom classifier: training a model breaks the no-training rule and needs the data-science skills the team does not have, while Comprehend already provides sentiment.
T: Chain pretrained services for speech analytics: Transcribe (speech to text, PII redaction) then Translate then Comprehend (sentiment).
V: Amazon Transcribe, Amazon Translate, Amazon Comprehend

@ AIF-C01 D1 T1.1 expert use-case
S: A hospital network has trained a computer vision model in SageMaker AI that analyzes 3D scan files of about 400 MB each, and each scan needs 8 to 12 minutes of GPU processing. Radiologists upload scans one at a time during the day and expect each result within about 20 minutes, while no scans arrive at night or on weekends. Finance does not want to pay for GPU instances that sit idle, and developers want each scan submitted as soon as it is uploaded. Which inference option fits best?
A: An asynchronous inference endpoint that queues each request with its payload in Amazon S3 and scales the instance count to zero when idle
B: A serverless inference endpoint that launches compute on demand for each request and scales down to zero when no scans are waiting
C: A real-time inference endpoint on GPU instances with automatic scaling that adds instances whenever many scans are uploaded together
D: A batch transform job each evening that reads the whole day's scans from Amazon S3 and writes all of the results back without an endpoint
K: A
G: ## Four ways to get predictions from a SageMaker AI model
- **Real-time inference**: a persistent endpoint for interactive, low-latency requests. The model container must answer each `InvokeEndpoint` call within 60 seconds.
- **Serverless inference**: no instances to choose, scales to zero, tolerates cold starts. It does **not** support GPUs, and memory tops out at 6 GB.
- **Asynchronous inference**: requests are queued, the payload sits in S3, and the result is written back to S3 (optionally with an SNS notification). Built for payloads up to 1 GB, processing up to one hour and near real-time latency, and it can scale the instance count to zero when the queue is empty.
- **Batch transform**: a job that runs over a whole dataset with no persistent endpoint.
## Fit the numbers
400 MB payload, 8 to 12 minutes per scan, GPU required, result in about 20 minutes, idle nights: every number lands inside asynchronous inference's envelope and none fits the others.
W: Asynchronous inference: it accepts large payloads through S3, allows processing times up to an hour, returns results in near real time and scales to zero instances when no scans are queued, so idle GPUs cost nothing.
X: B=Serverless inference: it scales to zero, but it does not support GPUs and is meant for short requests with cold starts, so a GPU-bound 10-minute scan cannot run there.
C=Real-time endpoint: it is designed for interactive requests that answer within 60 seconds, and keeping GPU instances provisioned through nights and weekends is the idle cost finance rejected.
D=Nightly batch transform: it needs no endpoint, but waiting until evening breaks the 20-minute result target and the submit-on-upload requirement.
T: Large payloads, minutes of processing and near real-time results with scale-to-zero point to SageMaker asynchronous inference.
V: Amazon SageMaker AI

@ AIF-C01 D1 T1.2 expert tradeoff
S: A regional bank wants to automate approval of small-business credit-line increases using 40 structured fields such as revenue, payment history and existing debt, and it holds eight years of labeled outcomes. Regulators require that every declined applicant receives the specific reasons for the decision and that the same application always gets the same result. The scoring call runs inside the online banking flow with a 100-millisecond latency budget and peaks of 2,000 requests per second. Which approach is MOST appropriate?
A: Train a supervised classifier such as gradient-boosted trees on the labeled tabular history, and derive reason codes from per-decision feature attributions
B: Send each application's fields to a large language model on Amazon Bedrock with a prompt that asks for a decision and a written list of reasons
C: Fine-tune a foundation model on the eight years of outcomes so it learns the bank's lending policy and writes its reasons in natural language
D: Train an unsupervised clustering model on past applications and approve each applicant whose cluster had the highest historical approval rate
K: A
G: ## Traditional ML or a foundation model?
The exam guide asks when a traditional ML model is more appropriate than a foundation model, based on regulation, explainability and operational constraints. Work through the three constraints:
- **Data**: 40 structured fields with eight years of labeled outcomes is a classic **supervised classification** problem on tabular data.
- **Explainability and consistency**: a trained classifier returns the same score for the same input, and feature-attribution methods can rank which fields pushed a given decision toward decline, which becomes the reason codes. An LLM's free-text "reasons" are generated text, not a faithful account of how the decision was made, and sampling can change the answer.
- **Latency and scale**: a compact tree model scores tabular input in milliseconds; a large generative model processing a prompt per request is much heavier for a 100 ms budget at 2,000 requests per second.
## When an FM would fit
Foundation models shine on unstructured text, images or open-ended generation. Here they add cost and risk without adding value.
W: Supervised classifier: labeled tabular data is exactly what supervised classification learns from, the model gives repeatable scores at low latency, and feature attributions per decision supply the specific reasons regulators demand.
X: B=LLM prompt per application: the generated reasons are not a reliable explanation of how the decision was reached, outputs can vary between runs, and a large model per request strains a 100 ms budget at 2,000 requests per second.
C=Fine-tuned foundation model: fine-tuning makes the FM more familiar with the data, but it keeps the same problems of unfaithful text explanations, possible variation and heavy inference, at extra training cost.
D=Clustering: clustering ignores the labeled outcomes the bank already has and gives group membership, not an individual decision with specific reasons for one applicant.
T: For structured, labeled data with strict explainability, consistency and latency needs, a traditional supervised model usually beats a foundation model.
V: Amazon SageMaker AI, Amazon Bedrock

@ AIF-C01 D2 T2.1 expert tradeoff
S: An insurer's support assistant on Amazon Bedrock sends every request the same fixed 9,000-token block of product terms, followed by about 500 tokens of conversation and question, and receives about 400 output tokens. It handles 200,000 requests a month, spread evenly across the business day. Assume illustrative prices of $3 per million input tokens, $15 per million output tokens and $0.30 per million tokens read from the prompt cache. Legal requires the full terms in every prompt, and answers must not get shorter. Which change lowers the monthly bill the most?
A: Turn on prompt caching for the fixed 9,000-token prefix, which lowers the bill from about $6,900 to about $2,040 once those tokens are read from cache
B: Retrieve only the three most relevant 500-token sections of the terms, which cuts input to about 2,000 tokens and the bill to about $2,400
C: Cap the maximum output length at 200 tokens instead of 400, which halves the output spend and lowers the bill from about $6,900 to about $6,300
D: Move the assistant to batch inference so all requests share one job, which caches the terms once for the whole batch and lowers input spend
K: A
G: ## Token-based pricing
On-demand inference bills input tokens and output tokens separately, usually with output tokens priced higher. Cost per month = tokens per request x requests x price.
## Work out the baseline
- Input: `9,500 x 200,000 = 1.9 billion` tokens x $3 per million = **$5,700**
- Output: `400 x 200,000 = 80 million` tokens x $15 per million = **$1,200**
- Total: **about $6,900**
## Prompt caching
Bedrock prompt caching stores a long, repeated prompt prefix so later requests do not reprocess it. Tokens read from cache are billed at the model's lower cache-read rate (cache writes can cost more on some models, so the result is approximate). The cache has a time to live, often 5 minutes, that resets on each hit, so steady traffic keeps it warm.
- Cached prefix: `9,000 x 200,000 = 1.8 billion` x $0.30 per million = $540
- Uncached input: `500 x 200,000 = 100 million` x $3 per million = $300
- Output unchanged: $1,200, so the total is about **$2,040**
Prompt caching works only with on-demand inference, not with the batch inference API.
W: Prompt caching: the 9,000-token terms are identical in every request, so caching them moves 1.8 billion tokens a month to the cache-read rate. The bill falls to about $2,040 while the full terms stay in every prompt and answers keep their length.
X: B=Retrieve three sections: about $2,400 is also lower, but it is still higher than caching and it drops most of the terms from each prompt, which breaks the legal requirement.
C=Halve the output cap: it saves only $600 because output is the smaller part of the bill, and it makes answers shorter, which is not allowed.
D=Batch inference: the assistant is interactive, batch jobs return results asynchronously in Amazon S3, and prompt caching is not supported with the batch inference API.
T: Work token costs as tokens x requests x price; for a long, repeated prompt prefix, prompt caching is the largest saving that keeps the prompt intact.

@ AIF-C01 D2 T2.2 expert troubleshooting
S: A compliance team tests a general-purpose text model on Amazon Bedrock with its default inference settings. Running the identical prompt about a vendor contract three times returns three different risk ratings, and one response confidently cites "Section 14.3" of a regulation that has no such section. The team wants the same rating every time for the same input, needs every regulatory claim tied to the regulation text the company actually licenses, and cannot fund any model training this quarter. Which explanation and plan are correct?
A: The changing ratings come from sampling during generation, so a lower temperature reduces them; the fake section is a hallucination, so supply the licensed text through retrieval
B: Both behaviours come from sampling randomness, so setting temperature to its lowest value makes outputs repeatable and also stops the model from inventing citations
C: Both behaviours mean the model is overfitted to its training data, so fine-tuning it on the company's licensed regulations fixes both the ratings and the citations
D: Both behaviours mean the context window overflowed, so raising the maximum output length gives the model room to finish its reasoning and quote real sections
K: A
G: ## Two different limitations of generative AI
- **Nondeterminism**: for each next token the model has a probability distribution and samples from it. Temperature, Top P and Top K shape that sampling. A lower temperature makes high-probability tokens more likely and responses more deterministic; a higher one flattens the distribution.
- **Hallucination**: the model generates fluent, plausible text from patterns, not from a lookup of facts. A made-up section number can be the single most likely continuation, so it appears even with sampling turned down.
## Matching the fix to the cause
- Consistency is a sampling problem: lower temperature (and Top P).
- Factual grounding is a knowledge problem: give the model the real regulation text at inference time with Retrieval Augmented Generation, for example through Amazon Bedrock Knowledge Bases, so claims can be checked against a source. No training is needed.
W: Sampling plus hallucination: lowering temperature makes the model favour high-probability tokens and gives more consistent ratings, while retrieving the licensed regulation text grounds claims in a real source, which addresses the invented section without any training.
X: B=Temperature fixes both: low temperature narrows the sampling, but it does not give the model knowledge it lacks. The most probable continuation can still be an invented citation.
C=Overfitting and fine-tuning: overfitting describes a model that memorizes training data and fails on new data, not run-to-run variation; fine-tuning also costs training money the team does not have this quarter.
D=Context overflow: the prompt is short, and the maximum output length only limits how long the response may be. It does not change sampling or the model's knowledge.
T: Lower temperature for consistency; ground with retrieved sources for accuracy. They are separate problems with separate fixes.
V: Amazon Bedrock

D=Hourly batch jobs: shoppers are waiting for answers in a live conversation, and batch inference returns results asynchronously in S3; it is also not supported for provisioned models.

@ AIF-C01 D2 T2.1 expert troubleshooting
S: An engineering firm loads 3,000 long maintenance manuals into an Amazon Bedrock knowledge base with default chunking of about 300 tokens. Engineers report that search finds the right sentence, but answers miss the safety conditions stated two paragraphs later in the same section. Raising fixed-size chunks to 1,500 tokens gave the model more context, but retrieval became noticeably less precise. The firm wants precise matching and broad context together, without rewriting or splitting the manuals by hand. Which chunking strategy should it choose?
A: Hierarchical chunking, which searches small child chunks for a precise match and then hands their larger parent chunks to the model as context
B: Semantic chunking, which splits text where its meaning changes so each chunk covers one topic, and returns that same chunk to the model as context
C: Fixed-size chunking at 1,500 tokens with a high overlap percentage, so neighbouring chunks share text and every match carries extra surrounding context
D: No chunking, so that each manual becomes a single chunk and every retrieval returns one complete manual with all of its conditions and procedures
K: A
G: ## Why chunk size is a tradeoff
A knowledge base splits documents into chunks, turns each chunk into an embedding (a vector), and searches those vectors for the user's question.
- **Small chunks** give precise embeddings: one chunk is about one thing, so the best match is accurate. But the model then sees only that small piece.
- **Large chunks** carry more context, but each embedding blends several ideas, so matching gets fuzzier.
## Hierarchical chunking resolves it
You set a parent chunk size and a child chunk size. Retrieval searches the **child** chunks (precise), then **replaces** them with their **parent** chunks so the model receives the wider passage. Because several children can share one parent, fewer results may come back than requested.
## The other strategies
- **Fixed-size** (with overlap) and **default** (about 300 tokens) pick one size for both matching and context.
- **Semantic** chunking splits where meaning changes and focuses on semantic content, but the chunk that is matched is the chunk that is returned.
- **No chunking** treats each document as a single chunk.
W: Hierarchical chunking: small child chunks keep matching precise, and swapping in the parent chunk gives the model the surrounding paragraphs where the safety conditions live, which is exactly the combination the firm asked for.
