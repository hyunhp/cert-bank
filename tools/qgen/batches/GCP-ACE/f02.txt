@ GCP-ACE D2 T2.2 applied troubleshooting
S: An analyst runs bq load to load CSV files from gs://acme-sales-us/2026/*.csv into the table sales.daily. The bucket is in the US multi-region, and the sales dataset was created in the europe-west1 region. The load job fails before reading any rows. What is the most likely cause and fix?
A: The locations of source and target differ; copy the objects to storage colocated with the target, or use a US dataset
B: A wildcard in a Cloud Storage URI is rejected by bq load; list the CSV files by name in a comma-separated set of URIs
C: CSV loads need an explicit schema because auto-detection reads JSON files alone; pass a local JSON schema file to the job
D: bq load needs Storage Transfer Service to move objects from a bucket into BigQuery; create a transfer job for the files
K: A
G: ## Location rules for BigQuery load jobs
A BigQuery dataset lives in one location (a region such as `europe-west1` or a multi-region such as `US` or `EU`). When you load from Cloud Storage, the docs require that **the Cloud Storage bucket be in the same location as the dataset** that contains the table. A mismatch makes the job fail.
## Fixes
- copy the files into a bucket colocated with the dataset (for example with `gcloud storage cp` or Storage Transfer Service), then load
- or create the dataset in the bucket's location
## Other `bq load` facts
- the source can be one URI, a comma-separated list, or URIs with a `*` wildcard (one wildcard per URI)
- schema can be inline, a JSON schema file, or `--autodetect` for CSV and JSON
- `--location` sets the location where the job runs
W: Colocate bucket and dataset: loading from Cloud Storage requires the bucket in the same location as the dataset, so moving the files to a bucket in `europe-west1` or using a dataset in the `US` multi-region fixes it.
X: B=Wildcard rejected: `bq load` accepts URIs with a wildcard, for example `gs://mybucket/mydata*.csv`, so the wildcard is not the problem.
C=Explicit schema needed: schema auto-detection works for CSV as well as JSON, and an existing table's schema is used when none is given, so the schema is not why the job fails.
D=Transfer job needed: `bq load` reads directly from Cloud Storage URIs; Storage Transfer Service moves files between storage systems, not into BigQuery tables.
T: For a BigQuery load from Cloud Storage, the bucket must be in the same location as the dataset.
V: BigQuery, Cloud Storage

@ GCP-ACE D1 T1.2 advanced tradeoff
S: To stop costs from an unused test environment, an administrator plans to disable billing on the project `net-host`. That project is the Shared VPC host for three service projects that run production VMs. What will be the effect?
A: Billing stops in `net-host`, and VMs in attached projects whose interfaces use its networks are shut down as well
B: Billing stops in `net-host`, while the service projects keep running because each is linked to its own billing account
C: Billing stops in `net-host` once its committed use discounts expire, and its resources keep running normally until then
D: Billing stops in `net-host` for new resources, while its existing VMs and disks keep running without accruing charges
K: A
G: ## What disabling billing does
Billing is disabled on a project when it is unlinked from its billing account (or the account is closed or suspended). Then:
- all Google Cloud services in the project **stop**, and billing on the project stops;
- some resources may be **deleted and not recoverable**, so back up data first;
- you remain responsible for charges already incurred.
## Shared VPC side effect
In Shared VPC, a **host project** owns the network and **service projects** attach VMs to it. If billing is disabled on the host project, services in the service projects that depend on the Shared VPC are disabled too: every Compute Engine instance whose network interface uses the Shared VPC is shut down, in all attached service projects.
## Other limits
You cannot disable billing on a project that has active or pending committed use discounts, or one whose billing link is locked.
## Safer plan
Delete or stop the unused test resources in `net-host` instead of unlinking the whole host project.
W: Service projects affected: the docs state that disabling billing on a Shared VPC host shuts down the Compute Engine instances that use the Shared VPC as their network interface, across the attached service projects.
X: B=Service projects keep running: the service projects' own billing link does not help, because their VMs depend on the host project's network, which goes down with the host.
C=Waits for CUDs to expire: a project with active or pending CUDs cannot have billing disabled at all; the action is blocked, not delayed until expiry.
D=New resources blocked: disabling billing stops the project's services, existing ones included, and some resources may even be deleted.
T: Disabling billing stops everything in the project, and on a Shared VPC host it also takes down service-project VMs that use that network.
V: Cloud Billing, VPC

@ GCP-ACE D1 T1.1 applied use-case
S: A company runs VMs in two projects, shop-staging and shop-prod. The operations team wants one place in Cloud Monitoring to chart and alert on the metrics of both projects, without having to filter out unrelated resources. What should they configure?
A: Create an empty project such as shop-monitoring and add both projects to the metrics scope of that new scoping project
B: Add shop-staging to the metrics scope of shop-prod and build the charts and alerting policies in shop-prod, next to its VMs
C: Create a log sink in each project that routes metrics to a shared BigQuery dataset, and build charts and alerts on that dataset
D: Create a folder holding both projects and enable Cloud Monitoring at the folder level, so it charts the metrics of its projects
K: A
G: ## Metrics scopes in Cloud Monitoring
- A **resource container** (a project) stores the time-series data of its own resources.
- The **metrics scope** of a project lists the resource containers whose data that project can chart and monitor. By default it includes only the project itself.
- The project that hosts a metrics scope is its **scoping project**; it stores the alerting policies, dashboards, uptime checks and groups you create. In the console, the scoping project is the one selected in the project picker.
## Best practice
To monitor several projects together, Google recommends a **new project or one without resources** as the scoping project. If the scoping project has its own VMs, every chart and alert must filter them out, which adds complexity and room for error.
## Setting it up
In Monitoring **Settings > Metric Scope**, add projects to the scope. Changes take about 60 seconds to propagate. A metrics scope can include 375 projects by default (the quota can be raised).
W: Dedicated scoping project: an empty project whose metrics scope includes both projects can chart and alert on their data, and since it stores no metrics itself, nothing needs filtering out.
X: B=Use shop-prod as scoping project: it works technically, but production's own VMs then mix with staging data, the exact filtering problem the team wants to avoid.
C=Log sink to BigQuery: log sinks route log entries, not Monitoring time series, and charts and alerting policies don't run on a BigQuery dataset.
D=Folder-level Monitoring: there is no Monitoring switch on a folder; a metrics scope belongs to a scoping project (even app-enabled folders use a management project's metrics scope).
T: For multi-project monitoring, use an empty scoping project and add the monitored projects to its metrics scope.
V: Cloud Monitoring, Google Cloud Observability
