# GCP-ACE explanation rewrites: Owner/Editor/Viewer are now "legacy basic roles"; the basic roles are

@ Q008153 explain
G: ## Two sides of a project's billing link
A project is linked to exactly one Cloud Billing account at a time. Changing the link is an action on **both** resources:
- On the **project**: `resourcemanager.projects.createBillingAssignment` (and `deleteBillingAssignment` to remove the old link). Project Billing Manager and Project Owner have these.
- On the **target billing account**: `billing.resourceAssociations.create`. Billing Account User and Billing Account Administrator have it.
## Why Project Billing Manager
Project Billing Manager lets someone attach the project to a billing account **without** granting rights over the project's resources. The docs say Project Owners can use it to let someone else manage billing for the project. The docs' full role list for this task also adds Project Browser and Service Usage Viewer on the project, plus Billing Account Viewer on the accounts for listing links.
## Basic and legacy basic roles
IAM's basic roles are now Admin (`roles/admin`), Writer (`roles/writer`) and Reader (`roles/reader`); Owner (`roles/owner`), Editor (`roles/editor`) and Viewer (`roles/viewer`) are the **legacy basic roles**. Both sets contain thousands of permissions across all services, so neither fits a "no access to resources" requirement.
## The command
`gcloud billing projects link web-prod --billing-account=0X0X0X-0X0X0X-0X0X0X` moves the project to the new account if it is already linked to another one.
W: C=Project Billing Manager: it holds the project-side permissions to create and delete the billing assignment while giving no access to the project's resources.
E=Billing Account User: it holds `billing.resourceAssociations.create` on the new account, which is required to link any project to that account.
X: A=Billing Account Viewer only: it can list which projects are linked, but it cannot create a new link, so the move would fail on the billing account side.
B=Project Editor: Editor is a legacy basic role that can modify most resources in the project, which the owner wants to avoid, and it is not the role the docs list for billing links.
D=Billing Account Creator: it lets a user create new self-serve billing accounts; it gives no permission to link a project to the existing new account.
T: Linking a project needs a project-side role (Project Billing Manager or Owner) and a billing-account-side role (Billing Account User or Administrator).

@ Q008204 explain
G: ## IAM answers "who", Organization Policy answers "what"
- **IAM** authorizes **who** can act on which resources, based on permissions in roles.
- **Organization Policy** restricts **what** configurations are allowed on resources, for everyone, regardless of their roles.
A project Owner has every permission in the project, so IAM alone can't stop an Owner from choosing an external IP. An organization policy can.
## Owner is a legacy basic role
Owner (`roles/owner`), Editor and Viewer are IAM's **legacy basic roles**; the current basic roles are Admin (`roles/admin`), Writer (`roles/writer`) and Reader (`roles/reader`). Role bindings for legacy basic roles can't carry IAM Conditions, so the Owner grant can't be narrowed with a condition.
## The external IP constraint
`constraints/compute.vmExternalIpAccess` is a list constraint naming the VM instances (`projects/PROJECT_ID/zones/ZONE/instances/INSTANCE`) that may use external IPv4 addresses. A policy that denies all values means no VM may have one. It doesn't restrict IPv6 addresses.
## Where to set it
Setting it at the organization makes every folder and project inherit it.
W: Organization policy on external IPs: the constraint restricts the VM configuration itself, so the Compute Engine API rejects external IPv4 addresses whoever makes the request, project Owners included.
X: A=Remove Instance Admin: Owners keep full permissions and can still create VMs with external IPs, so the requirement fails for exactly the group it names.
B=Deny-all egress firewall rule: VMs still receive external addresses; the rule blocks traffic, not the IP assignment, and Owners can delete the rule.
D=IAM Condition on Owner: Owner is a legacy basic role, and IAM doesn't accept conditions on role bindings for legacy basic roles; even where conditions are allowed, they can't inspect a VM's requested network configuration.
T: Use organization policy constraints to restrict resource configuration for everyone; use IAM to decide who can act.

@ Q008205 explain
G: ## Granting a role on a project
Access to a project is defined in the project's **allow policy**, a list of role bindings. Each binding links principals to one role, and the role applies to the project and every resource inside it.
## The add command
`gcloud projects add-iam-policy-binding PROJECT_ID --member=PRINCIPAL --role=ROLE` adds one binding and leaves the rest of the policy as it is.
- `--member` needs a type prefix: `user:`, `group:`, `serviceAccount:` or `domain:`.
- `--role` needs the full role name, such as `roles/viewer` or `roles/logging.viewer`; custom roles use `projects/PROJECT_ID/roles/ROLE_ID` or `organizations/ORG_ID/roles/ROLE_ID`.
## set-iam-policy is different
`gcloud projects set-iam-policy PROJECT_ID policy.json` replaces the **whole** policy with the contents of a file. It takes no `--member` or `--role` flags and can remove existing grants if the file is incomplete.
## Basic and legacy basic roles
`roles/viewer` (Viewer) is a **legacy basic role** that gives broad read access. The current basic roles are Admin (`roles/admin`), Writer (`roles/writer`) and Reader (`roles/reader`); Reader gives similar broad read-only access and, unlike Viewer, its bindings can carry IAM Conditions. For production, predefined roles are preferred where they fit; the grant mechanics are the same for every role.
W: add-iam-policy-binding with group: prefix: it adds one binding for the group with the full role name and keeps all other bindings unchanged.
X: A=user: prefix for a group: the principal type must match the identity; a group address with `user:` doesn't identify the group and the grant fails or targets the wrong principal.
B=set-iam-policy: this command replaces the entire policy from a JSON or YAML file; it doesn't take member and role flags and risks wiping existing grants.
C=Short role name: the role must be given as its full name such as `roles/viewer`; a bare `viewer` isn't a valid role identifier.
T: Grant project roles with `gcloud projects add-iam-policy-binding PROJECT --member=group:... --role=roles/...`; `set-iam-policy` replaces the whole policy.
