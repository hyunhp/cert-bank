@ GCP-ACE D3 T3.1 applied use-case
S: An operator must open SSH sessions to a Compute Engine VM named db-admin-01 that has no external IP address. Policy forbids bastion hosts and VPNs for administrative access, so the team will use Identity-Aware Proxy (IAP) TCP forwarding. Which two configurations are specifically required for the IAP tunnel to work? (Select TWO)
A: A VPC firewall rule that allows ingress on TCP port 22 to the VM from the IAP source range 35.235.240.0/20
B: The IAP-secured Tunnel User role (roles/iap.tunnelResourceAccessor) granted to the operator on the project or on the VM
C: An ephemeral external IP address attached to the VM's nic0 for the length of each SSH session, removed afterwards
D: A Cloud NAT gateway on the VM's subnet so that the IAP proxy can reach the VM's primary internal IPv4 address
E: The Compute Network Admin role (roles/compute.networkAdmin) granted to the operator on the VPC network of the VM
K: A,B
G: ## What IAP TCP forwarding does
Identity-Aware Proxy (IAP) TCP forwarding builds an encrypted tunnel from your workstation to a VM through Google's IAP proxies. The VM needs **no external IP address**: the proxies connect to the primary internal IPv4 address of `nic0`.
Two separate checks must pass before a tunnel opens:
- **Network**: the IAP proxies send the traffic from the range `35.235.240.0/20` (IPv6: `2600:2d00:1:7::/64`). A VPC firewall rule must allow ingress from that range on the port you forward, for example TCP 22 for SSH or 3389 for RDP.
- **Identity**: the user needs the **IAP-secured Tunnel User** role (`roles/iap.tunnelResourceAccessor`), granted on the project for all VMs or on one VM only. IAM Conditions can narrow it further, for example to one destination port.
## Example
`gcloud compute firewall-rules create allow-ssh-from-iap --network=prod-vpc --direction=INGRESS --action=allow --rules=tcp:22 --source-ranges=35.235.240.0/20`, then grant the role and run `gcloud compute ssh db-admin-01 --tunnel-through-iap`. The operator still needs the usual Compute Engine permissions to look up the VM and push an SSH key, but those are not specific to IAP.
W: A=Firewall rule from 35.235.240.0/20: IAP proxies reach the VM from this fixed range, so without an ingress rule for port 22 from it the tunnel is opened but the connection to the VM is dropped by the VPC firewall.
B=IAP-secured Tunnel User: this role carries the permission to open a tunnel through IAP; without it IAP refuses the request before any traffic reaches the VM.
X: C=Temporary external IP: IAP TCP forwarding exists precisely so that VMs without external IP addresses can be administered. Adding one would expose the VM and is not used by the tunnel at all.
D=Cloud NAT gateway: Cloud NAT gives VMs outbound internet access. IAP traffic arrives as inbound connections from Google's proxy range to the internal address, so NAT plays no part in it.
E=Compute Network Admin: this role lets someone manage networks, subnets and firewall rules. It does not include the permission to tunnel through IAP, and it gives the operator far more than least privilege.
T: IAP TCP forwarding needs two things: a firewall rule allowing the port from 35.235.240.0/20, and roles/iap.tunnelResourceAccessor for the user; the VM needs no external IP.
V: Identity-Aware Proxy, Compute Engine, VPC firewall rules

@ GCP-ACE D3 T3.1 applied use-case
S: A Windows Server VM named win-app-01 has no external IP address, and a firewall rule already allows TCP 3389 from the IAP range. An administrator wants to use the Remote Desktop client installed on her laptop, without adding an external IP or a VPN. Which approach works?
A: Run `gcloud compute start-iap-tunnel win-app-01 3389 --local-host-port=localhost:3389 --zone=ZONE`, then RDP to localhost:3389
B: Run `gcloud compute ssh win-app-01 --tunnel-through-iap --zone=ZONE`, then connect the RDP client to the VM's internal IP on port 3389
C: Run `gcloud compute instances add-access-config win-app-01 --zone=ZONE`, then connect the RDP client to the new address on port 3389
D: Run `gcloud compute start-iap-tunnel win-app-01 22 --local-host-port=localhost:3389 --zone=ZONE`, then connect RDP to localhost:3389
K: A
G: ## Forwarding any TCP port through IAP
`gcloud compute ssh --tunnel-through-iap` is a convenience for SSH only. For any other protocol, such as RDP on port 3389 or a database port, you open the tunnel yourself with `gcloud compute start-iap-tunnel`:
- The first argument is the VM, the second is the **port on the VM** (`3389` for RDP).
- `--local-host-port=localhost:LOCAL_PORT` binds a local listener on your laptop; `0` picks a free port automatically.
- While the command runs, anything that connects to the local port is carried through IAP to the VM's port.
Your RDP client then simply connects to `localhost:LOCAL_PORT`. The VM keeps no external IP, and access is still controlled by the IAP-secured Tunnel User role and the firewall rule from `35.235.240.0/20`.
W: start-iap-tunnel to port 3389: this opens a local listener on the laptop and forwards it through IAP to the VM's RDP port, which is exactly what a local RDP client needs.
X: B=SSH with --tunnel-through-iap: this opens an SSH session through IAP, not a port forward for RDP. The laptop still has no route to the VM's internal IP, so pointing the RDP client at it fails.
C=add-access-config: this attaches an external IP to the VM. RDP would then travel over the internet, which the administrator was told not to do, and it bypasses IAP entirely.
D=Tunnel to port 22: the tunnel's remote port decides where traffic goes on the VM. Forwarding to port 22 sends the RDP client's traffic to SSH (normally not even listening on Windows), so the session fails.
T: For non-SSH protocols through IAP, run `gcloud compute start-iap-tunnel VM REMOTE_PORT --local-host-port=localhost:LOCAL_PORT` and connect the client to the local port.
V: Identity-Aware Proxy, Compute Engine

@ GCP-ACE D3 T3.1 applied definition
S: Before a maintenance window, an engineer needs a list of only the Compute Engine VMs that are currently running, across every zone of the project, to paste into a change ticket. Which command produces that list?
A: gcloud compute instances list --filter="status=RUNNING"
B: gcloud compute instances describe --filter="status=RUNNING"
C: gcloud compute instances list --zones=all --running-only
D: gcloud compute zones list --filter="status=UP"
K: A
G: ## Listing resources with gcloud
Most resource types have a `list` command that shows every resource of that type in the project. `gcloud compute instances list` lists VMs in **all zones** by default; `--zones=ZONE,...` narrows it to certain zones.
## Filtering
Every `list` command accepts `--filter=EXPRESSION`, a Boolean expression evaluated per resource; only matching items are printed. A VM's `status` field holds values such as `RUNNING`, `STOPPING` or `TERMINATED` (stopped VMs show `TERMINATED`). So:
- `gcloud compute instances list --filter="status=RUNNING"` shows only running VMs.
- `--filter="name~'^web-'"` matches names by regular expression.
- `--format` and `--sort-by` shape the output, for example a table of name and zone for a ticket.
`describe` is the opposite of `list`: it prints every field of one named resource.
W: instances list with a status filter: `list` covers all zones by default and `--filter="status=RUNNING"` keeps only the VMs whose status field is RUNNING.
X: B=instances describe: `describe` shows the full configuration of a single named VM. It needs an instance name and does not produce a filtered inventory of the project.
C=--zones=all --running-only: `--zones` expects real zone names and there is no `--running-only` flag; filtering is done with the generic `--filter` flag.
D=zones list: this lists the zones available to the project and whether each zone is UP. It says nothing about which VMs are running.
T: List resources with `gcloud ... list` and narrow the output with `--filter`; running VMs are `--filter="status=RUNNING"`.
V: Compute Engine, Google Cloud CLI

@ GCP-ACE D3 T3.1 advanced troubleshooting
S: A team attached a daily snapshot schedule with a 14-day maximum retention to the data disks of its Compute Engine VMs. Months later, the cost review shows scheduled snapshots of a disk that was deleted in spring, and engineers ask how retention really behaves. Which two statements are correct? (Select TWO)
A: By default, scheduled snapshots of a deleted source disk are kept until someone deletes them, unless the schedule's source disk deletion rule applies the retention policy
B: After the maximum retention period, Compute Engine deletes a scheduled snapshot only when a newer snapshot of the same disk already exists
C: The retention policy also removes snapshots that engineers created by hand from the same disk once they are older than the configured 14 days
D: A snapshot schedule can create archive snapshots for long-term compliance retention if its storage location is set to a multi-region
E: A snapshot schedule created in one project can be attached to disks in other projects of the same organization to share one retention policy
K: A,B
G: ## Snapshot schedules
A snapshot schedule is a **resource policy** that creates standard snapshots of zonal or regional Persistent Disk and Hyperdisk volumes hourly, daily or weekly. It lives in a region and in one project; you attach it to disks, for example:
`gcloud compute resource-policies create snapshot-schedule daily-14d --region=us-central1 --start-time=02:00 --daily-schedule --max-retention-days=14`
`gcloud compute disks add-resource-policies data-disk-1 --resource-policies=daily-14d --zone=us-central1-a`
## Retention policy
- Applies **only to snapshots the schedule created**, never to manual snapshots.
- After the maximum retention period, Compute Engine deletes a snapshot **only if a newer snapshot of that disk exists**, so you are never left without any backup.
## Source disk deletion rule
When the source disk is deleted, scheduled snapshots are by default **kept permanently** (`--on-source-disk-delete=keep-auto-snapshots`) whatever the retention policy says. Set `apply-retention-policy` to keep ageing them out. The old disk in this scenario stopped producing newer snapshots and fell under the default keep rule, so its snapshots stay and keep costing until someone deletes them.
## Limits worth knowing
- Schedules create standard snapshots only, not archive or instant snapshots.
- A schedule can be used only in the project where it was created.
W: A=Source disk deletion rule: the default keeps automatic snapshots of a deleted disk forever; only the `apply-retention-policy` rule keeps the retention window running after the disk is gone.
B=Newer snapshot required: automatic deletion after the maximum retention period happens only when a newer snapshot of the disk exists, so the last backup of a disk is never removed by age alone.
X: C=Manual snapshots too: the retention policy covers only the snapshots generated by the schedule. Snapshots that people create by hand stay until someone deletes them.
D=Archive snapshots from a schedule: snapshot schedules can't create archive or instant snapshots. The storage location only sets where the standard snapshots are kept.
E=Shared across projects: a snapshot schedule applies only in the project that it was created in; other projects need their own schedules.
T: Schedule retention affects only scheduled snapshots, waits for a newer snapshot, and stops at source disk deletion unless the deletion rule applies the retention policy.
V: Compute Engine, Persistent Disk, snapshot schedules

@ GCP-ACE D3 T3.1 applied comparison
S: A VM runs a self-managed database with a boot disk and two data disks. Before an operating system upgrade, the team wants one backup that captures the instance's configuration, metadata and all three disks consistently at the same point in time, so the whole VM can be restored or cloned. What should they create?
A: A machine image of the VM, which captures its properties, metadata and every attached disk with one consistent timestamp
B: A standard snapshot of each of the three disks, started one after another with `gcloud compute disks snapshot`
C: A custom image of the boot disk, created with `gcloud compute images create --source-disk` after stopping the VM
D: An instance template created from the VM, which records its machine type, network settings and disk layout
K: A
G: ## Four ways to save a VM's state
Compute Engine has several resources that look alike but answer different needs:
- **Standard disk snapshot**: incremental, geo-redundant backup of **one disk**. Good for regular disk backups and snapshot schedules.
- **Custom image**: a bootable copy of one disk, used as a base image to create many VMs (often grouped into an image family).
- **Instance template**: the configuration of a VM (machine type, network, disk definitions, metadata) without the data on the disks; used by managed instance groups.
- **Machine image**: all the configuration, metadata, permissions and data from **multiple disks** of one instance. Disks are captured crash-consistently with globally consistent timestamps.
## Choosing
- Back up one disk regularly: snapshot (snapshot schedule).
- Golden image for many VMs: custom image.
- Back up or clone a whole VM with several disks: machine image.
W: Machine image: it is the only resource that backs up every disk of the instance together with its configuration and metadata, with a crash-consistent point in time across disks, and it can restore or clone the VM.
X: B=One snapshot per disk: each snapshot covers one disk and is taken at its own moment, so the three disks are not captured at the same point in time, and the VM's configuration and metadata are not saved.
C=Custom image of the boot disk: an image is a base for new VMs built from one disk. The two data disks and the VM's configuration are left out.
D=Instance template: a template stores how to build a VM but none of the data on its disks, so it cannot restore the database.
T: Snapshot = one disk; custom image = reusable boot disk; instance template = configuration only; machine image = the whole VM with all its disks.
V: Compute Engine, machine images, snapshots

@ GCP-ACE D3 T3.1 advanced troubleshooting
S: A managed instance group's instance template boots from the custom image family web-base. The build pipeline just published web-base-v8, and new VMs created from it fail health checks, while web-base-v7 worked. The team needs new VMs to boot v7 again right away, without editing the instance template. What should they do?
A: Deprecate the web-base-v8 image, so the web-base family resolves to web-base-v7 again as long as v7 is not deprecated
B: Rename web-base-v8 to web-base-v8-broken, so the family lookup skips it and selects the previous image by its name
C: Delete web-base-v7 and recreate it from its source disk, so it becomes the newest image and the family's default
D: Remove the family label from web-base-v8 with `gcloud compute images update`, so it no longer belongs to web-base
K: A
G: ## Image families
An **image family** groups versions of an image, for example `web-base-v6`, `web-base-v7`, `web-base-v8`. Anything that references the family (`--image-family=web-base`, or an instance template that points to the family) gets the **most recent non-deprecated image** in it at the moment a VM is created. Pipelines can keep publishing new versions with `gcloud compute images create ... --family=web-base` without anyone changing templates.
## Rolling back
To roll a family back, **deprecate the newest image**. The family then points to the previous image, provided that image is not deprecated itself. When a fixed `v9` is published, the family moves forward again.
## Why this is safer than editing templates
Instance templates can't be changed after creation; pointing the group at a specific image would mean creating a new template and updating the group. Deprecating one image fixes every template and script that uses the family at once.
W: Deprecate the newest image: a family always resolves to its latest image that is not deprecated, so deprecating v8 makes every new VM from the family boot v7 immediately, with no template change.
X: B=Rename the image: Compute Engine images can't be renamed, and the family choice is not based on names anyway, so this does not change what the family returns.
C=Delete and recreate v7: deleting a working image to rebuild it is risky and slow, and it needs the original source disk, which may no longer exist. Deprecation is the built-in rollback.
D=Remove the family label: the family is a property of the image, not a resource label, and the documented rollback method is deprecation. Labels have no effect on which image a family returns.
T: To roll back an image family, deprecate the newest image; the family then returns the previous non-deprecated version.
V: Compute Engine, custom images, image families

S: In a GKE Standard cluster, one replica of the Deployment checkout is in CrashLoopBackOff. Before cordoning a node, the operator wants to see, in one command, every Pod with its status, its Pod IP address and the name of the node it is running on. Which command should she run?

Two tools look at a cluster from different sides:
- `gcloud container ...` talks to the GKE API and shows **infrastructure**: clusters (`clusters list/describe`), node pools (`node-pools list/describe`), versions, machine types.

- `kubectl get services` lists Services with their type, cluster IP and external IP.
- `kubectl describe pod NAME` shows events, such as image pull errors or failed probes, for one Pod.

C=kubectl describe service: this shows a Service's selector, ports and endpoints. It does not show Pod status or the node each Pod is scheduled on.

@ GCP-ACE D3 T3.1 applied troubleshooting
S: A GKE Standard cluster in project app-prod uses the Compute Engine default service account for its nodes. Container images are stored in an Artifact Registry repository in another project, shared-artifacts. New Pods fail with ImagePullBackOff and a 403 permission error. What is the least-privilege fix?
A: Grant the Artifact Registry Reader role (roles/artifactregistry.reader) on the repository in shared-artifacts to the service account used by the nodes
B: Grant the Artifact Registry Writer role (roles/artifactregistry.writer) on the shared-artifacts project to the developers who deploy the Pods
C: Grant the Storage Object Viewer role on the artifacts bucket of shared-artifacts to the service account used by the nodes
D: Create an imagePullSecret holding a JSON key of the Owner service account of shared-artifacts, and add it to every Pod spec
K: A
G: ## Who pulls the image
When a Pod starts on a GKE node, the **node** pulls the container image, using the node's service account. By default that is the Compute Engine default service account, unless the node pool was created with a user-managed service account.
- Same project: granting that service account the **Artifact Registry Reader** role (`roles/artifactregistry.reader`) lets GKE pull images. Depending on organization policy, the default account may hold the basic Editor role automatically; Google recommends disabling that automatic grant and granting narrow roles instead.
- Different project: the node service account needs Artifact Registry permissions **in the project or on the repository that holds the images**. Being Editor in app-prod gives nothing in shared-artifacts.
## Example
`gcloud artifacts repositories add-iam-policy-binding app-images --project=shared-artifacts --location=us-central1 --member=serviceAccount:PROJECT_NUMBER-compute@developer.gserviceaccount.com --role=roles/artifactregistry.reader`
W: Reader for the node service account: the node's identity performs the pull, and read access on the repository in the other project is exactly what it lacks; nothing more is granted.
X: B=Writer for the developers: developers do not pull images when Pods start; the node service account does. Writer is also more than a pull needs.
C=Storage Object Viewer on a bucket: storage buckets were how the retired Container Registry served images. Artifact Registry repositories are controlled through Artifact Registry roles, not bucket permissions.
D=imagePullSecret with an Owner key: exporting a key of a highly privileged account into every Pod spec breaks least privilege and creates a long-lived secret to protect. An IAM grant to the node identity needs no key.
T: GKE nodes pull images with the node service account; for another project's repository, grant it roles/artifactregistry.reader there.

@ GCP-ACE D3 T3.1 applied definition
S: A GKE Standard node pool named batch uses e2-standard-4 nodes, and its jobs now run out of memory. An engineer runs `gcloud container node-pools update batch --cluster=prod --location=us-central1 --machine-type=e2-highmem-8`. What happens to the running nodes?
A: GKE recreates the nodes with the new machine type using the node pool's upgrade strategy, so Pods are rescheduled onto replacement nodes
B: GKE changes the machine type of each node in place by live migrating its VM, so running Pods keep running without any restart
C: Only nodes that the cluster autoscaler adds later get the new machine type, while existing nodes stay on e2-standard-4
D: The command is rejected, because a node pool's machine type is fixed and the node pool must be deleted and created again
K: A
G: ## Changing node machine attributes
A node pool's machine type, boot disk type and boot disk size can be changed with `gcloud container node-pools update POOL --machine-type=... --disk-type=... --disk-size=...` (at least one of them). This is vertical scaling of the nodes.
## How GKE applies it
The change needs **new nodes**: GKE recreates them with the new configuration using the **upgrade strategy** configured for the pool:
- **Surge upgrade**: a few nodes at a time are drained and replaced.
- **Blue-green upgrade**: a new set of nodes is created, workloads move, and the old nodes can be kept for rollback until the soak time ends.
Pods on a node being replaced are evicted and rescheduled, so plan for disruption (replicas, PodDisruptionBudgets).
## The alternative
You can also create a second node pool with the new machine type, move the workloads (for example with node selectors), and delete the old pool. That gives full control over timing.
W: Recreate with the upgrade strategy: changing the machine type requires new VMs, so GKE replaces the nodes following the pool's surge or blue-green settings, and Pods move to the new nodes.
X: B=In-place live migration: live migration moves a VM to another host during maintenance; it never changes a VM's machine type. The nodes must be recreated.
C=Only new nodes: the update changes the whole node pool's configuration, and GKE replaces the existing nodes; it does not wait for autoscaling to add nodes.
D=Rejected, fixed machine type: the machine type, disk type and disk size of a node pool can be updated; deleting and recreating the pool is an option, not a requirement.
T: Updating a node pool's machine type recreates its nodes using the pool's upgrade strategy, so expect Pods to be rescheduled.
V: Google Kubernetes Engine

@ GCP-ACE D3 T3.1 advanced troubleshooting
S: A GKE Standard node pool has cluster autoscaling enabled with a maximum of 10 nodes and currently runs 4. Monitoring shows node CPU near 95%, and latency is rising, but no Pods are Pending and the autoscaler adds no nodes. The Deployment's containers have no resource requests. What explains this?
A: The cluster autoscaler acts on Pod requests and Pending Pods, not on measured CPU, so busy nodes alone never trigger a scale-up
B: The Compute Engine autoscaler of the node pool's managed instance group must also be turned on, because GKE's autoscaler only removes nodes
C: The balanced autoscaling profile scales up only after nodes stay above 90% CPU for one hour; switching to optimize-utilization fixes it
D: The node pool spans more than one zone, and the cluster autoscaler adds nodes only to single-zone node pools of a Standard cluster
K: A
G: ## What triggers the cluster autoscaler
The GKE cluster autoscaler resizes a node pool by adding or removing VMs in its managed instance group, between the pool's minimum and maximum. Its decisions are based on **resource requests**, not actual usage:
- **Scale up** when Pods are **unschedulable** (Pending) because no node has enough unrequested capacity for their requests.
- **Scale down** when nodes are underutilized by requests and their Pods can fit elsewhere.
If containers request nothing, the scheduler can keep placing Pods on existing nodes, nothing is ever Pending, and the autoscaler sees no reason to add nodes, even at 95% CPU.
## Fix
- Set realistic CPU and memory **requests** on every container (VPA recommendations help find them).
- Scale the Pods with a horizontal Pod autoscaler; when new replicas don't fit, they become Pending and the cluster autoscaler adds nodes.
## Don't mix autoscalers
Never enable Compute Engine autoscaling on the node pool's managed instance group: it conflicts with GKE's cluster autoscaler.
W: Requests drive the autoscaler: without requests nothing becomes unschedulable, so the autoscaler has no signal to add nodes, however busy the existing ones are.
X: B=Compute Engine MIG autoscaler: GKE's cluster autoscaler scales up and down by itself, and Google warns not to enable Compute Engine autoscaling on node MIGs because the two conflict.
C=Balanced profile delay: autoscaling profiles change how aggressively nodes are removed. Neither profile waits for an hour of high CPU, because CPU usage is not the scale-up signal.
D=Multi-zone pools: the cluster autoscaler works with multi-zonal and regional node pools and balances them across zones during scale-up.
T: The GKE cluster autoscaler reacts to Pending Pods and requests, not CPU usage; set requests and let an HPA create the Pods that trigger scale-up.
V: Google Kubernetes Engine, cluster autoscaler

@ GCP-ACE D3 T3.1 advanced use-case
S: An engineer creates a new node pool in a regional GKE Standard cluster whose nodes run in three zones. The pool must autoscale and never have fewer than 3 or more than 9 nodes in total across all zones. Which two sets of flags meet the requirement? (Select TWO)
A: --enable-autoscaling --min-nodes=1 --max-nodes=3
B: --enable-autoscaling --total-min-nodes=3 --total-max-nodes=9
C: --enable-autoscaling --min-nodes=3 --max-nodes=9
D: --num-nodes=3 --max-nodes=9, without --enable-autoscaling
E: --enable-autoscaling --total-min-nodes=1 --total-max-nodes=3
K: A,B
G: ## Autoscaling limits per zone or in total
When you enable cluster autoscaling on a node pool (`--enable-autoscaling`), you give it bounds in one of two ways:
- `--min-nodes` / `--max-nodes`: limits **per zone**. In a pool that spans three zones, `--min-nodes=1 --max-nodes=3` means 3 to 9 nodes in total.
- `--total-min-nodes` / `--total-max-nodes`: limits for the **whole node pool** across all zones (GKE 1.24 and later).
The same per-zone logic applies to `--num-nodes`: in regional or multi-zonal clusters, it is the number of nodes **in each zone**.
## Example

W: A=Per-zone 1 to 3: with three zones, one to three nodes per zone gives exactly 3 to 9 nodes in total.
B=Total 3 to 9: the total flags set the bounds for the whole pool across all zones directly.
X: C=Per-zone 3 to 9: these flags are per zone, so three zones give 9 to 27 nodes, three times what was asked.
D=No --enable-autoscaling: without the flag the pool does not autoscale at all; `--max-nodes` is ignored, and `--num-nodes=3` per zone creates a fixed 9 nodes.
E=Total 1 to 3: these total bounds allow only 1 to 3 nodes in the whole pool, below the required minimum of 3 and maximum of 9.
T: `--min-nodes`/`--max-nodes` (and `--num-nodes`) count per zone; `--total-min-nodes`/`--total-max-nodes` count across all zones of the pool.

G: ## Vertical Pod autoscaling
Vertical Pod autoscaling (VPA) analyzes historical usage and recommends **CPU and memory requests and limits** for containers. Its `spec.updatePolicy.updateMode` decides what it does with them:

G: ## Agent Platform Workbench
**Agent Platform Workbench** (formerly Vertex AI Workbench) instances are JupyterLab environments for data science on a Compute Engine VM, with TensorFlow and PyTorch preinstalled, optional GPUs, and integrations for Cloud Storage and BigQuery. To save cost, instances **shut down after a period of idleness** by default (configurable).
## The executor
The **executor** runs a notebook file as a one-time execution or **on a recurring schedule**:
- You choose the environment and hardware; the code runs on **Agent Platform custom training**, not on your instance.
- **Parameters** change each run, for example a date, a dataset or a learning rate.
- It runs **even while your instance is shut down**, and executed notebooks are saved in a **Cloud Storage** bucket you can share.
(Executor runs are not supported in instances that use VPC Service Controls.)
W: Scheduled executor run: the schedule runs on managed training infrastructure independent of the instance, takes parameters per run, and saves output to Cloud Storage, so it works while the instance is off.
X: B=Cron inside the instance: a cron job only runs while the VM is running; with idle shutdown the instance is off at night, so nothing would start.
C=Disable idle shutdown: this keeps the VM running and billing all day and night just to wait, which defeats the cost goal; the executor exists for exactly this case.
D=Cloud Workstations timeout: Cloud Workstations are developer environments, and their idle or running timeouts stop workstations; they are not a notebook scheduler.
T: To run a Workbench notebook on a schedule while the instance is off, use the executor; runs execute on custom training and results land in Cloud Storage.

@ GCP-ACE D3 T3.1 advanced troubleshooting
S: A platform team changed the machine type in a Cloud Workstations configuration on Monday. On Wednesday, developers whose workstations never stopped still run on the old machine type, and a developer who stopped hers lost tools she had installed under /opt, while files in her home directory survived. Which explains both observations?
A: Configuration changes apply when each workstation next starts, and only the persistent home directory disk survives a stop because the VM is recreated
B: Configuration changes apply only to workstations created after the change, and data outside the home directory is removed by a weekly cleanup job
C: Machine type changes need each developer to edit her own workstation, and /opt is erased because it lies outside the configured container image
D: Configuration changes apply at the workstation cluster's next maintenance window, and stopping a workstation resets every directory to the image
K: A
G: ## How Cloud Workstations is organized
- A **workstation cluster** groups workstations in one region and VPC network (unrelated to GKE clusters).
- A **workstation configuration** is the template: VM machine type, container image with the tools, IDE, persistent storage, timeouts and IAM access.
- A **workstation** is one developer's environment created from a configuration, reached through a browser IDE, local IDEs such as VS Code or JetBrains, or SSH.
## Lifecycle and storage
Workstations run on **ephemeral Compute Engine VMs**. When a workstation stops, its VM is deleted along with all runtime data. Only the **persistent home directory**, a persistent disk attached at start and detached at stop, keeps data between sessions. Tools that every developer needs belong in the configuration's container image, not in ad hoc installs under `/opt`.
## Configuration updates
Changes to a configuration apply to each workstation **the next time it starts**. Idle timeouts and running timeouts make workstations restart regularly, so they pick up changes within a bounded time.
W: Applied on next start, home persists: the running workstations haven't restarted, so they still use the old machine type, and the stopped one lost /opt because its VM was discarded while the home directory disk was kept.
X: B=New workstations only: existing workstations do pick up configuration changes at their next start, and there is no weekly cleanup job; data outside home is lost because the VM is ephemeral.
C=Developers edit their own: the machine type is set centrally in the configuration, and developers don't change it per workstation; the loss of /opt comes from the VM being recreated at stop.
D=Cluster maintenance window: updates are not tied to a maintenance window but to each workstation's next start. A stop does not reset the home directory, which is persistent.
T: Cloud Workstations apply configuration changes on the next start, and only the persistent home directory survives a stop.
V: Cloud Workstations
