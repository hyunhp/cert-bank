@ GCP-ACE D2 T2.4 applied comparison
S: An engineer works in Cloud Shell on a Git repository of Terraform files. She wants an AI agent in the terminal that reads the local files, proposes and edits code for a new subnet, and runs commands such as terraform plan, without installing anything extra. Which tool fits best?
A: Application Design Center, opening the repository's Terraform files on the design canvas to edit them with Gemini assistance
B: Agent Runtime on Gemini Enterprise Agent Platform, deploying a custom coding agent that she then calls from Cloud Shell
C: Gemini Cloud Assist investigations, which analyze logs, metrics and configurations to trace the root cause of an issue in the project
D: Gemini CLI, the open source reason-and-act assistant preinstalled in Cloud Shell, with built-in file editing and shell tools
K: D
G: ## Where Gemini helps with infrastructure work
- **Gemini CLI**: an open source AI agent that brings Gemini into a local or **Cloud Shell** terminal. It works in a reason-and-act loop with built-in tools (such as reading and editing files and running shell commands) and MCP servers. It is available in Cloud Shell without additional setup.
- **Gemini Cloud Assist**: the assistant in the Google Cloud console (Cloud Assist panel). It answers questions with project context, generates gcloud commands, kubectl manifests and Terraform in chat or App Design Center, and runs **investigations** that troubleshoot issues from logs and metrics.
- **Application Design Center**: designs applications from governed templates and components.
- **Agent Runtime**: a managed runtime for deploying your own agents, not a developer tool.
W: Gemini CLI: it runs right in the Cloud Shell terminal with no install, reads and edits the repository's files, and can run commands such as terraform plan as part of its reason-and-act loop.
X: A=Application Design Center: it works with its own components and templates on a design canvas, not as an editor for an arbitrary Git repository inside Cloud Shell.
B=Agent Runtime: building and deploying a custom agent is a large project, and Agent Runtime hosts agents rather than giving the engineer a ready coding assistant in the terminal.
C=Cloud Assist investigations: investigations diagnose issues from logs, metrics and configuration; they do not edit files in a local repository.
T: AI agent in the terminal that edits local files and runs commands → Gemini CLI (preinstalled in Cloud Shell); console-side help and investigations → Gemini Cloud Assist.
V: Gemini CLI, Gemini Cloud Assist, Cloud Shell

@ GCP-ACE D2 T2.2 applied comparison
S: A logistics company runs dozens of services that produce and consume events with Apache Kafka client libraries and Kafka Connect, on a self-managed cluster. They want Google Cloud to run the cluster for them without rewriting producers or consumers. Which service should they choose?
A: Memorystore for Redis, whose streams store the events and accept the existing Kafka producer calls with no code changes
B: Managed Service for Apache Kafka, which provisions and patches open source clusters behind private bootstrap URLs
C: Pub/Sub, whose topics and subscriptions receive the existing Kafka producer and consumer calls with no code changes
D: Dataflow, whose streaming jobs act as Kafka brokers that the existing Kafka clients connect to as their bootstrap servers
K: B
G: ## Two messaging options on Google Cloud
- **Pub/Sub** is Google's own serverless, asynchronous messaging service. It uses its own API with **per-message** leasing instead of Kafka-style partitions. Moving Kafka applications to it means changing the producer and consumer code.
- **Google Cloud Managed Service for Apache Kafka** runs real **open source Apache Kafka** clusters for you. You set the total vCPU and memory, the service provisions brokers, handles patching and storage (tiered storage), and exposes private bootstrap URLs in your VPCs through Private Service Connect. Clients authenticate with SASL (IAM principals) or mTLS.
## Choosing
If code already uses Kafka APIs and tools, the managed Kafka service keeps them unchanged. If you are building new event-driven services and want no cluster to size, Pub/Sub is usually simpler.
W: Managed Service for Apache Kafka: it runs genuine Apache Kafka clusters managed by Google, so existing Kafka clients and tooling keep working while the team stops operating brokers.
X: A=Redis streams: Memorystore is an in-memory store with the Redis protocol; it does not speak the Kafka protocol and is not a durable event log for Kafka clients.
C=Pub/Sub without code changes: Pub/Sub has its own API and per-message delivery model; Kafka producers and consumers must be rewritten or bridged to use it.
D=Dataflow as brokers: Dataflow runs Apache Beam processing pipelines; it can read from and write to Kafka but is not a Kafka broker that clients connect to.
T: Keep Kafka APIs but drop cluster operations = Managed Service for Apache Kafka; new Google-native messaging = Pub/Sub.
V: Managed Service for Apache Kafka, Pub/Sub

@ GCP-ACE D2 T2.1 applied troubleshooting
S: A new engineer installed the Google Cloud CLI on her laptop, ran gcloud components install kubectl, and fetched credentials for a GKE cluster. Every kubectl command now fails with an error saying that gke-gcloud-auth-plugin is not found. What should she do?
A: Add the auth plugin binary through the gcloud component manager, then retry; the existing kubeconfig entry stays valid
B: Download a static service account key for the cluster and point the KUBECONFIG variable at the downloaded JSON file
C: Recreate the cluster with legacy client certificate authentication enabled so kubectl no longer needs any plugin
D: Ask an administrator to grant her roles/container.admin on the project so kubectl may use her gcloud credentials
K: A
G: ## How kubectl talks to GKE
`kubectl` is the standard Kubernetes command-line tool. You can install it as a Google Cloud CLI component (`gcloud components install kubectl`); Cloud Shell already has it.
kubectl does not log in to GKE by itself. It relies on an **authentication plugin**, `gke-gcloud-auth-plugin`, which uses the client-go credential plugin framework to hand kubectl short-lived tokens based on your gcloud identity. Without the plugin, kubectl and other Kubernetes clients cannot talk to GKE clusters and show an error.
## Setup on a new machine
- `gcloud components install kubectl`
- `gcloud components install gke-gcloud-auth-plugin` (or the `google-cloud-cli-gke-gcloud-auth-plugin` package with apt or yum); check with `gke-gcloud-auth-plugin --version`
- `gcloud container clusters get-credentials CLUSTER --location=LOCATION` to write the kubeconfig entry
W: Install gke-gcloud-auth-plugin: the error names a missing binary, and the plugin is what turns her gcloud credentials into tokens for kubectl. Running `gcloud components install gke-gcloud-auth-plugin` adds it, and the kubeconfig entry that get-credentials already wrote then works without being fetched again.
X: B=Service account key file: a key file is not a kubeconfig, and long-lived keys are a security risk to avoid; the fix is the auth plugin, not another credential.
C=Recreate with client certificates: rebuilding a cluster to work around a missing local binary is disruptive, and the supported path for GKE is the auth plugin.
D=Grant roles/container.admin: an IAM role adds permissions, but kubectl still cannot obtain any token without the plugin, so the same "not found" error remains.
T: kubectl on a new machine needs two gcloud components, kubectl and gke-gcloud-auth-plugin, plus get-credentials for each cluster.
V: GKE, Google Cloud CLI

@ GCP-ACE D2 T2.2 advanced tradeoff
S: A retailer's order application runs on PostgreSQL. Managers want reports that run heavy analytical queries directly on the live order data, without a nightly export, and without slowing down the order transactions. The team wants to keep using standard PostgreSQL clients. Which service should the team choose?
A: Bigtable, with the order data copied into it so that reports can scan wide rows by order date with low latency
B: Memorystore for Redis, with report results cached in memory so that repeated analytical queries return quickly
C: Cloud SQL for PostgreSQL, with a scheduled export to Cloud Storage and a BigQuery load job that runs every night
D: AlloyDB for PostgreSQL, whose columnar engine and read pool instances serve report scans beside the OLTP primary
K: D
G: ## Transactional and analytical work on one database
Online transaction processing (OLTP) means many small reads and writes; analytics means large scans and aggregations. Running both on one ordinary PostgreSQL server makes them compete for the same resources, so teams often copy data to a warehouse every night, and reports are then a day old.
## AlloyDB for PostgreSQL
AlloyDB is a fully managed, **PostgreSQL-compatible** database designed for demanding workloads, including **Hybrid Transactional and Analytical Processing (HTAP)**: analytical queries against live transactional data without hurting performance.
- A **columnar engine** accelerates analytical queries.
- **Read pool instances** add load-balanced read nodes, so reports run away from the primary.
- Applications connect with standard PostgreSQL protocols and tools such as `psql` and pgAdmin.
W: AlloyDB with columnar engine and read pools: it runs analytics on current transactional data with the columnar engine, isolates the report load on read pools, and stays PostgreSQL-compatible for the existing clients.
X: A=Copy into Bigtable: Bigtable has no SQL joins or PostgreSQL compatibility, and copying data into it adds a pipeline instead of querying the live order data.
B=Memorystore cache: a cache only speeds up results that were already computed; it does not run analytical queries, and the first run still loads the database.
C=Nightly export to BigQuery: it works for reporting, but the data is up to a day old, which is exactly the nightly export the managers want to avoid.
T: PostgreSQL workload that needs fast analytics on live transactional data (HTAP) = AlloyDB.
V: AlloyDB for PostgreSQL

@ GCP-ACE D4 T4.1 applied use-case
S: All employees of the company use Cloud Identity accounts in the domain `example.com`. The company wants every employee to be able to view the contents of one Cloud Storage bucket `gs://acme-handbook`, and nobody outside the company. Which principal should receive the Storage Object Viewer role on the bucket?
A: `allUsers`, which is restricted to members of the organization when public access prevention is off
B: The project's `default` service account, which employees can use to open the bucket
C: `allAuthenticatedUsers`, which means all signed-in accounts of the company
D: `domain:example.com`, which covers every user account registered under that managed Workspace domain
K: D
G: ## Principal types in an allow policy
A role binding connects a role to **principals**. The common types are:
- `user:alice@example.com`, a single account;
- `group:team@example.com`, a Google group (preferred for people with the same job);
- `serviceAccount:...`, a workload identity;
- `domain:example.com`, **all users in a Cloud Identity or Google Workspace domain**;
- `allUsers`, **anyone on the internet**, with or without authentication;
- `allAuthenticatedUsers`, **anyone with any Google Account**, including personal Gmail accounts, and service accounts.
## Example
`gcloud storage buckets add-iam-policy-binding gs://acme-handbook --member="domain:example.com" --role="roles/storage.objectViewer"`
The two `all...` types are not limited to the company, so they are almost never the right choice for internal content.
W: Domain principal: it covers every user of `example.com`, matching "all employees and nobody else".
X: A=allUsers: it means anyone on the internet and is not restricted to the organization; it makes the bucket public.
B=Default service account: a service account is an identity for workloads, and sharing its credentials with employees would break accountability.
C=allAuthenticatedUsers: it includes any person with a Google Account, such as personal Gmail users, so outsiders could read the handbook.
T: `domain:example.com` addresses everyone in the domain; `allUsers` and `allAuthenticatedUsers` reach beyond the company.
V: IAM, Cloud Storage

@ GCP-ACE D3 T3.4 applied use-case
S: A DevOps team manages an application defined in App Hub whose resources span two projects. They want one console view for that application with its open Cloud Monitoring alerts, active Google Cloud incidents, quotas above 90% usage and upcoming maintenance. What should they use?
A: The Logs Explorer of each project, with saved queries for alert, incident, quota and maintenance entries written by each service
B: A custom Cloud Monitoring dashboard in each of the two projects, with one widget per alert policy and a separate quota chart for every service
C: Cloud Asset Inventory exports for both projects to BigQuery, joined with alerting data from the Monitoring API in a scheduled query
D: Cloud Hub with that application selected as scope, which combines operational data for its resources across projects on dedicated pages
K: D
G: ## Cloud Hub
**Cloud Hub** gives a centralized view of operations data for a selected **project** or an **App Hub application** (whose resources can span projects). Its pages include:
- **Health & troubleshooting**: open Cloud Monitoring alerts, active Google Cloud incidents, health and performance metrics.
- **Quotas & reservations**: quotas and system limits above 90% usage, Compute Engine usage and reservations.
- **Maintenance**: upcoming, in-progress and completed maintenance and the affected resources.
- **Optimization**, **Security & compliance**, **Deployments** and **Support**.
You can also start Gemini Cloud Assist investigations from Health & troubleshooting.
W: Cloud Hub by application: Cloud Hub shows operations data per App Hub application, so one view covers alerts, Google Cloud incidents, high quota usage and maintenance for resources in both projects.
X: A=Logs Explorer queries: searching logs per project is manual and fragmented, and alert states and quota usage are not log entries that each service writes.
B=Dashboards per project: two dashboards are not one view, and Monitoring dashboards don't list Google Cloud incidents or upcoming maintenance events.
C=Asset Inventory to BigQuery: this is custom data engineering; asset metadata says nothing about incidents or maintenance, and it would not be a ready-made view.
T: For one operational view (alerts, incidents, quotas, maintenance) of a project or App Hub application, use Cloud Hub.
V: Cloud Hub, App Hub, Cloud Monitoring

@ GCP-ACE D2 T2.2 applied use-case
S: A start-up is building a mobile and web app that stores user profiles and posts as JSON-like documents. The team wants a serverless database that scales automatically without capacity planning, charges for actual use, and works with the Firebase SDKs. Which database should they pick?
A: Bigtable, a wide-column database whose cluster nodes are sized up front and adjusted when traffic changes
B: Memorystore for Redis, an in-memory store whose hashes hold each profile and post as a set of key fields
C: Firestore, a fully managed NoSQL document store with pay-per-use billing and native Firebase client libraries
D: Cloud SQL for MySQL, a relational instance with a JSON column type and storage that grows automatically
K: C
G: ## Document databases
A document database stores each record as a self-describing document (fields, nested maps, arrays) grouped in collections, close to how apps hold JSON objects in memory.
## Firestore
Firestore is Google Cloud's fully managed, **serverless** document database:
- no pre-provisioning: it **auto scales** compute and storage to the load, with a pay-per-use model
- strongly consistent queries, transactions, and multi-region replication options
- integration with **Firebase** for mobile and web apps (Firebase SDKs and console), plus a MongoDB-compatible API for MongoDB applications
W: Firestore: it is a serverless document database that scales without capacity settings, bills by use, and plugs into the Firebase SDKs the team wants.
X: A=Bigtable: Bigtable requires provisioned clusters with nodes and is built for very large key-value and time-series workloads, not as a serverless document backend for mobile apps.
B=Memorystore hashes: Memorystore is an in-memory cache for fast access, not the primary durable document store for user data, and it has no Firebase SDK integration.
D=Cloud SQL with JSON columns: Cloud SQL runs on an instance with chosen CPU and memory, so it is not serverless and needs capacity planning; it also has no Firebase integration.
T: Serverless, auto-scaling document database for mobile and web apps (Firebase) = Firestore.
V: Firestore
