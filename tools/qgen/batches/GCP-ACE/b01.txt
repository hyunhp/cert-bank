@ GCP-ACE D1 T1.1 applied troubleshooting
S: The Cloud Identity super admin at a retail company granted Priya the Organization Administrator role (roles/resourcemanager.organizationAdmin) on the organization. Priya can grant IAM roles to other users, but her attempt to create a top-level folder named Marketing fails with a permission error. What should be done so that Priya can create folders?
A: Grant Priya the Folder Creator role (roles/resourcemanager.folderCreator) on the organization, because Organization Administrator does not include folder creation
B: Make Priya a Cloud Identity super admin, because only super admins can create the first level of folders directly under an organization resource
C: Grant Priya the Project Creator role (roles/resourcemanager.projectCreator), because folder creation permissions are bundled with project creation
D: Grant Priya the Organization Policy Administrator role, because folders are created by enabling the folder constraint in an organization policy
K: A
G: ## Two admin roles at the top of the hierarchy
An organization resource is the root of the Google Cloud resource hierarchy. Two different roles control it:
- The **Google Workspace or Cloud Identity super admin** verifies the domain, is the recovery contact, and by default can assign IAM roles. Its main Google Cloud job is to hand out the Organization Administrator role.
- The **Organization Administrator** (`roles/resourcemanager.organizationAdmin`) defines allow and deny policies, grants roles to other users and can see the structure of the hierarchy.
## Least privilege on purpose
Google designed Organization Administrator around access management only. The docs say that the role does **not** include permissions to create folders or projects; an Organization Administrator who needs them must grant additional roles, for example to their own account.
## Roles that create things
- `roles/resourcemanager.folderCreator`: browse the hierarchy and create folders.
- `roles/resourcemanager.folderAdmin`: all folder permissions (create, move, delete, set folder IAM).
- `roles/resourcemanager.projectCreator`: create projects.
## Example
`gcloud organizations add-iam-policy-binding 123456789012 --member="user:priya@example.com" --role="roles/resourcemanager.folderCreator"` lets Priya run `gcloud resource-manager folders create --display-name=Marketing --organization=123456789012`.
W: Folder Creator: the Organization Administrator role is limited to managing access, so folder creation needs a separate role such as Folder Creator (or Folder Admin) granted on the organization.
X: B=Super admin: super admin status is about the Workspace or Cloud Identity account; folder creation in Google Cloud is controlled by IAM roles, and a super admin who is not granted a folder role is in the same position.
C=Project Creator: this role contains `resourcemanager.projects.create` only; it does not contain the folder creation permission.
D=Organization Policy Administrator: organization policies restrict how resources may be configured; there is no constraint that turns on folder creation, and the role grants no folder permissions.
T: Organization Administrator manages IAM, not resources: grant Folder Creator or Folder Admin to anyone who must build the folder structure.
V: Resource Manager, IAM

@ GCP-ACE D1 T1.1 applied use-case
S: A media company is setting up its Google Cloud organization. It has three departments (News, Sports, Studio), each with development and production workloads. Each department head must administer only their own department's projects, and the central security team must apply guardrails to everything. Which structure meets these requirements?
A: Create a folder per department under the organization with dev and prod subfolders, grant each head an admin role on their department folder, and set guardrail policies at the organization
B: Create one project per department and separate dev from prod with resource labels, then grant each department head the Owner role on that department's single project
C: Create a separate Cloud Identity account and organization per department, then give the security team an Organization Administrator role in each of the three organizations
D: Create one project per environment for the whole company and place a folder per department inside each project, granting heads an admin role on their own folder there
K: A
G: ## Organization, folders, projects
The Google Cloud resource hierarchy has the **organization** at the root, optional **folders** for grouping, and **projects** that hold the actual resources (VMs, buckets, databases). Every resource except the organization has exactly one parent.
- Folders can contain projects and other folders, nested up to **10 levels**, with up to 300 direct child folders per folder.
- Folders model departments, teams or legal entities, and can model environments below them.
- Allow policies, deny policies and organization policies attached to a node apply to everything below it.
## Delegation with folders
Granting a department head an admin role on the department folder gives them control of every project created in that folder and nothing outside it. Guardrails such as organization policies set once at the organization reach every folder and project.
## Why not several organizations
Google recommends folders under one organization for most cases. Multiple organizations mean no central visibility by default, and common policies have to be copied into each one.
## Example
`organizations/1234` -> `folders/News` -> `folders/News-prod` -> `projects/news-web-prod`.
W: Department folders with environment subfolders: each head gets an admin role on one folder subtree, while organization-level policies give the security team one place to set guardrails for all departments.
X: B=One project per department with labels: labels don't create a permission boundary, so dev and prod resources share the same IAM policy and the Owner role on a shared project is far more than least privilege.
C=One organization per department: this removes central control, forces the security team to duplicate every guardrail three times, and is the pattern Google suggests only for fully isolated entities.
D=Folders inside projects: projects are the lowest container and can't hold folders; folders always sit above projects in the hierarchy.
T: Model departments and environments with nested folders under one organization and grant roles on the folder each team owns.
V: Resource Manager

@ GCP-ACE D1 T1.1 applied definition
S: An engineer must create a new project for the payments team under folder 834512776120 by using the gcloud CLI. Which command creates the project in the right place with a valid project ID?
A: gcloud projects create acme-payments-dev --folder=834512776120
B: gcloud projects create Acme_Payments_Dev --folder=834512776120
C: gcloud resource-manager folders create acme-payments-dev --folder=834512776120
D: gcloud projects create acme-payments-dev --organization=5550001 --folder=834512776120
K: A
G: ## Creating a project from the CLI
`gcloud projects create PROJECT_ID` creates a project. To place it in the hierarchy, add **one** parent flag:
- `--organization=ORGANIZATION_ID` puts it directly under the organization.
- `--folder=FOLDER_ID` puts it inside a folder.
A resource can have only one parent, so the two flags can't be combined.
## Project ID rules
The project ID is globally unique and **permanent** after creation. It must:
- be 6 to 30 characters long
- start with a lowercase letter
- contain only lowercase letters, digits and hyphens (and not end with a hyphen)
- avoid restricted strings such as `google` or `ssl`
The project **name** (display name) is different: it can contain spaces and capitals and can be changed later.
## Example
`gcloud projects create acme-payments-dev --folder=834512776120` creates the project with ID `acme-payments-dev` as a child of that folder.
W: projects create with --folder: the ID uses only lowercase letters and hyphens, starts with a letter, and the single `--folder` flag sets the parent folder.
X: B=Capitals and underscores: project IDs must start with a lowercase letter and may only contain lowercase letters, digits and hyphens, so this ID is rejected.
C=folders create: this command creates a folder, not a project; the payments team would get a subfolder and still no project to hold resources.
D=Both parent flags: a project has exactly one parent, so `--organization` and `--folder` are mutually exclusive in `gcloud projects create`.
T: Use `gcloud projects create ID --folder=FOLDER_ID` (or `--organization`), with a lowercase, permanent project ID.

@ GCP-ACE D1 T1.1 advanced tradeoff
S: After an acquisition, a project is migrated from the acquired company's organization into the parent company's organization, directly under a folder named Acquired. The team wants to know what changes for the project at the moment of the move. Which TWO statements are correct? (Select TWO)
A: Roles that were granted to users on the source organization or source folders no longer apply to the project after the move
B: The organization policies of the destination organization and folder now apply instead of the source organization's policies
C: The project receives a new project ID in the destination organization, so scripts and API calls that use the old ID must be updated
D: The project is automatically relinked to the destination organization's billing account during the move, ending source billing
E: All VM instances and databases in the project are stopped during the move and must be restarted once the migration is complete
K: A,B
G: ## A migration changes the parent, not the data
Moving a project between organizations updates the project's **parent** in the resource hierarchy. It is not a data copy: VMs, buckets and databases stay online with no downtime.
## What stays and what changes
- **Stays the same**: project ID and number, the data and resources, roles granted **directly on the project**, project-level quotas, and the **billing account** link.
- **Changes**: roles **inherited** from the source organization or folders are lost; the source organization policies are replaced by the destination's; inherited organization-level quotas are lost.
## Things to prepare
- Custom roles defined at the source organization don't exist in the destination; recreate them first.
- Discounts and support tiers of the source organization might not carry over.
- Cloud Asset Inventory can take a few days to show the full resource list after the move.
## Example
A group had Compute Admin on the acquired company's `folders/eng`. After the move, that group has no access to the project unless the destination grants it.
W: A=Inherited roles lost: roles from the source organization or folders came from the old ancestors, so they stop applying once the project has a new parent; only roles granted directly on the project move with it.
B=Destination organization policies: organization policies are inherited from ancestors, so the destination organization and folder constraints replace the source ones immediately.
X: C=New project ID: the project ID and project number stay the same, so API keys, scripts and resource names keep working.
D=Automatic billing relink: the project stays linked to its original billing account; changing billing is a separate post-migration step.
E=Resources stopped: migration is a metadata change to the parent, and services, VMs and databases keep running throughout.
T: Moving a project keeps its ID, resources, direct roles and billing link, but swaps everything it inherits: IAM roles and organization policies.
V: Resource Manager

@ GCP-ACE D1 T1.1 applied use-case
S: A company has just signed up for Cloud Identity, and its Google Cloud organization resource was created automatically. The new Organization Administrator notices that every employee can still create projects in the organization. Only the platform-team group should be able to create projects. What should the administrator do?
A: Remove the domain-wide Project Creator grant on the organization and grant Project Creator on the organization to the platform-team group
B: Remove the Owner role from each user on every existing project, because the project owners are the users who are allowed to create new projects
C: Grant the platform-team group the Organization Administrator role, because only Organization Administrators are allowed to create new projects there
D: Delete the Billing Account Creator grant from the domain, because a user who can't create billing accounts is also unable to create projects
K: A
G: ## Default grants on a new organization
When an organization resource is created, its initial allow policy grants two roles to the **entire domain** at the organization level:
- Project Creator (`roles/resourcemanager.projectCreator`)
- Billing Account Creator (`roles/billing.creator`)
This keeps existing users working without disruption when the organization appears. Nothing else is created.
## Taking control
Once the Organization Administrator is ready to lock things down, they remove these organization-level grants and grant narrower access instead, for example Project Creator only to a platform group, or roles on specific folders. Because allow policies are inherited, a grant to the whole domain at the organization lets everyone create projects anywhere below it.
## Example
`gcloud organizations remove-iam-policy-binding 1234 --member="domain:example.com" --role="roles/resourcemanager.projectCreator"`, then `gcloud organizations add-iam-policy-binding 1234 --member="group:platform-team@example.com" --role="roles/resourcemanager.projectCreator"`.
W: Replace the domain grant: the ability to create projects comes from the default Project Creator binding for the whole domain, so removing it and granting the role to the group limits creation to the platform team.
X: B=Remove project Owner roles: owning an existing project doesn't let a user create new projects; the permission comes from Project Creator on the organization.
C=Organization Administrator for the group: this role manages IAM and does not even include project creation, and it would also give the group far more control than needed.
D=Remove Billing Account Creator: creating billing accounts and creating projects are separate permissions, so the domain would still hold Project Creator.
T: A new organization grants Project Creator and Billing Account Creator to the whole domain; remove those grants and give narrower ones when you take control.

@ GCP-ACE D1 T1.1 applied use-case
S: A bank's compliance team requires that new location-based Google Cloud resources in the organization be created only in European Union locations, including any EU regions that Google adds in the future. What should the Organization Policy administrator configure at the organization?
A: The gcp.resourceLocations constraint with the allowed value in:eu-locations, so that every location in the Google-curated EU value group is permitted
B: The gcp.resourceLocations constraint with the allowed value eu, so that the eu multi-region and every individual European region below it are permitted
C: The compute.vmExternalIpAccess constraint with a list of EU instances, so that only virtual machines located in European zones are allowed to start
D: An IAM deny policy on all users for location permissions outside the EU, so that creating resources in other regions fails with a permission error
K: A
G: ## The resource locations constraint
`constraints/gcp.resourceLocations` is a list constraint that defines where **location-based** resources can be created. By default, resources can be created anywhere.
## Value groups
Google curates **value groups**, collections of locations used with the `in:` prefix:
- `in:eu-locations`: all EU locations
- `in:us-locations`: all locations within the US
- `in:us-east1-locations`: one region and its zones
A value group grows automatically when Google adds a location, so the policy covers future regions without edits. Google recommends value groups.
## Multi-region values are not groups
Allowing or denying a multi-region such as `eu` or `us` applies only to multi-region resources (for example some storage services). It doesn't include the regions inside it: denying `us` still allows `us-east1`.
## Example policy
```
name: organizations/1234/policies/gcp.resourceLocations
spec:
  rules:
  - values:
      allowedValues:
      - in:eu-locations
```
W: in:eu-locations value group: the `in:` prefix with the curated EU group allows every EU region, zone and multi-region now and in the future, and implicitly denies everything else.
X: B=Plain eu value: a multi-region value only covers multi-region resources; it does not imply the regions inside it, so regional resources in EU regions would be blocked.
C=External IP constraint: `compute.vmExternalIpAccess` controls which VMs may have external IPv4 addresses and has nothing to do with resource location.
D=IAM deny on locations: IAM decides who may call an API, not where a resource may be created; location rules are the job of an organization policy constraint.
T: Restrict locations with `gcp.resourceLocations` and `in:` value groups such as `in:eu-locations`, not with multi-region names.

@ GCP-ACE D1 T1.1 advanced troubleshooting
S: A Google Cloud organization was created in 2025. A project owner tries to grant the Viewer role on her project to an external consultant who uses a personal gmail.com account, and the grant fails with an error that the member doesn't belong to a permitted customer. No one in the company remembers configuring such a rule. What is the most likely cause?
A: The Domain restricted sharing constraint (iam.allowedPolicyMemberDomains) is enforced on the organization as part of the Google Cloud security baseline
B: The project's IAM policy already contains the maximum number of role bindings, so new members can only be added after unused bindings are removed
C: The Viewer role is a basic role, and basic roles can't be granted to accounts outside the organization unless an IAM Condition is attached to the grant
D: The consultant must first accept a Cloud Identity invitation, because personal Google accounts are rejected until they join the company's domain
K: A
G: ## Google Cloud security baseline
Organizations created on or after **May 3, 2024** get a bundle of organization policies enforced automatically at creation (the security baseline). Examples:
- `iam.allowedPolicyMemberDomains` (Domain restricted sharing): only identities from allowed organizations or Workspace customer IDs can be added to IAM policies.
- `iam.managed.disableServiceAccountKeyCreation`: no new service account keys.
- `storage.uniformBucketLevelAccess`: no per-object ACLs.
## Domain restricted sharing
The constraint lists the principal sets or Google Workspace customer IDs whose principals may be added to allow policies. Everyone else, including personal `gmail.com` accounts, is rejected when someone tries to add them.
## Checking and changing it
- `gcloud resource-manager org-policies list --organization=ORGANIZATION_ID` shows which constraints are set.
- An Organization Policy Administrator can add the partner's customer ID, or create a project-level exception, if sharing with outsiders is truly needed.
W: Security baseline domain restriction: an organization created after May 2024 enforces Domain restricted sharing by default, which blocks adding principals from other domains such as personal Gmail accounts to IAM policies.
X: B=Binding limit: the error names a disallowed customer, not a policy size limit, and a project with a few bindings is nowhere near the size limit.
C=Basic role restriction: IAM has no rule tying basic roles to the caller's domain; Conditions can't be used with basic roles at all in `add-iam-policy-binding`, so they're no workaround either.
D=Cloud Identity invitation: IAM accepts any Google account unless an organization policy restricts it; joining the company domain is not a general requirement.
T: New organizations enforce baseline constraints such as Domain restricted sharing; check organization policies when outside identities are rejected.

@ GCP-ACE D1 T1.1 advanced troubleshooting
S: The Platform folder has an organization policy for the list constraint compute.trustedImageProjects that denies projects/legacy-images. A project under that folder sets its own policy with inheritFromParent set to true and allows projects/legacy-images. A developer in the project still can't create a VM from an image in legacy-images. Why?
A: The policies are merged because the project inherits from its parent, and for list rules a denied value always takes precedence over an allowed value
B: The project's policy takes up to 24 hours to replace the folder's policy, and until then the folder's denial of the image project stays in effect for it
C: A project-level policy can only add values to the deny list, because projects are not allowed to override any constraint set by an ancestor folder
D: The allowed value must use the under: prefix instead of the plain project path, because list values without a prefix are silently ignored
K: A
G: ## How list constraints are evaluated
A policy set on a resource replaces its parent's policy **unless** it sets `inheritFromParent: true`. With inheritance on, the parent's effective policy and the child's policy are **merged and reconciled**.
## Deny wins
For constraints with list rules, a `DENY` value always takes precedence during reconciliation. If a folder denies `projects/123` and a project below it allows `projects/123`, the effective policy still denies it. Google recommends not listing the same value in both allowed and denied lists, because the result is hard to read.
## Getting an exception
To let one project use the value, the project's policy would have to stop inheriting (`inheritFromParent: false`) and set its own values, or the folder policy has to change.
## Example
- Folder denies `projects/legacy-images`.
- Project inherits and allows `projects/legacy-images`.
- Effective policy at the project: `projects/legacy-images` denied.
W: Merged list with deny precedence: because the project inherits, its allow is merged with the folder's deny, and a denied value always beats an allowed one for list rules.
X: B=24-hour propagation: there is no day-long replacement delay; the result is the documented merge outcome, not a timing issue.
C=Projects can only add denies: a project can override an inherited list policy by setting `inheritFromParent: false`, so this limit doesn't exist.
D=under: prefix needed: values without a prefix are treated like `is:` (exact match); `under:` is for including child resources and wouldn't change the deny precedence.
T: For list constraints with inheritance, values are merged and DENY always wins; stop inheriting to make a real exception.

@ GCP-ACE D1 T1.1 advanced troubleshooting
S: The Production folder enforces the boolean constraint compute.disableSerialPortAccess. During an audit, the security team finds that one project in the folder has VMs with serial port access enabled, created after the policy was set. Organization policies for that project show a policy for the same constraint. What explains the finding?
A: The project has its own policy that sets enforce to false for the constraint, and for boolean rules the project's own value replaces the inherited one
B: Boolean constraints are evaluated by merging all ancestors, and a single enforce true anywhere above the project should have blocked these VMs
C: The folder's policy only applies to projects created after it was set, so projects that already existed in the folder are never covered by it
D: The VMs were created by a service account, and organization policy constraints apply only to requests that human users make in the console
K: A
G: ## Boolean rules don't merge
A constraint with a boolean rule is either enforced or not enforced. Unlike list rules, boolean rules are **not merged and reconciled** across the hierarchy: if a policy is specified on a resource, that resource's `true` or `false` value decides the effective policy.
## Example from the docs
- A folder sets `enforced: true`.
- A project below it sets `enforced: false`.
- The folder's value is ignored for that project, and the constraint is **not enforced** there.
## Keeping guardrails in place
Only principals with Organization Policy Administrator (`roles/orgpolicy.policyAdmin`) can set policies, so limiting that role is how you stop projects from overriding a folder. `gcloud org-policies describe CONSTRAINT --project=PROJECT_ID --effective` shows what is actually applied.
## Not retroactive
Separately, new policies generally don't change existing resources; but here the VMs were created after the folder policy, so the project-level override is the explanation.
W: Project-level override: the project's own policy for the boolean constraint sets enforce to false, and a boolean value on a resource replaces the inherited value instead of merging with it.
X: B=Merging ancestors: that is how list rules with inheritance behave; boolean rules use the policy closest to the resource when one is set there.
C=Only new projects covered: inheritance applies to all descendants of the folder, existing or new; the age of the project is not the deciding factor.
D=Service accounts exempt: constraints are enforced by the service on the API request, whoever the caller is, including service accounts and the CLI.
T: For boolean constraints, a policy set on the project wins outright; restrict who holds Organization Policy Administrator to keep folder guardrails.

@ GCP-ACE D1 T1.1 applied troubleshooting
S: On Monday, an administrator enforces the gcp.resourceLocations constraint at the organization to allow only in:europe-west1-locations. On Tuesday, the team finds that Cloud Storage buckets created last month in us-central1 still exist and still serve data. What is the reason?
A: The constraint restricts the creation of new resources at runtime and does not remove or block resources that existed before the policy
B: Organization policies need 72 hours to propagate across all projects, after which the existing buckets in us-central1 will be deleted
C: The constraint only applies to Compute Engine resources, so Cloud Storage buckets are never evaluated against the allowed locations list
D: The buckets are protected by uniform bucket-level access, which exempts a bucket from any organization policy set at a higher level
K: A
G: ## Organization policies prevent, they don't clean up
Google Cloud services enforce constraints when resources are created or updated. The application of a new organization policy is **usually not retroactive**: if a resource is already in a state that the new policy forbids, it is in violation, but the service keeps working as before. Google designed it this way so a new policy can't shut down a running business.
## Resource locations specifically
The docs say the resource locations constraint restricts resource **creation**; it helps prevent violations but does not identify or remediate existing ones. To find them, use tools such as Security Health Analytics in Security Command Center or Cloud Asset Inventory searches, then move or recreate the resources yourself.
## Testing first
Google advises testing a new location policy on non-production folders and rolling it out gradually, and dry-run mode can log violations before enforcement.
W: Not retroactive: the location constraint is checked when resources are created, so existing buckets are violations that keep running until someone remediates them.
X: B=72-hour propagation and deletion: no organization policy deletes existing resources, and there is no multi-day delay that ends in deletion.
C=Compute Engine only: the resource locations constraint covers many location-based services, Cloud Storage buckets included.
D=Uniform bucket-level access exemption: uniform bucket-level access only switches a bucket from object ACLs to IAM; it doesn't exempt the bucket from organization policies.
T: New organization policies stop future violations; existing non-compliant resources must be found and fixed separately.

@ GCP-ACE D1 T1.1 applied use-case
S: The security team wants to enforce a new organization policy that blocks external IPv4 addresses on VMs across the organization, but first wants to see which current workflows would break, without blocking anyone yet. What should they do?
A: Create the organization policy in dry-run mode, then review the audit logs for violations that would have been denied before switching it to enforced
B: Run gcloud org-policies describe with the --effective flag for each project, which lists every API call that the proposed policy would reject
C: Enforce the policy with inheritFromParent set to false at the organization, which logs the violations for a week before denials actually start
D: Grant all developers the Organization Policy Viewer role so that each team receives an email listing its own resources that break the policy
K: A
G: ## Dry-run mode
An organization policy can be created in **dry-run mode**, in active (enforced) mode, or both. In dry-run mode the policy is evaluated like an enforced one and **violations are written to audit logs**, but the violating actions are **not denied**.
This lets you watch how a change would affect real workflows before you enforce it.
## Other tools and what they do
- `gcloud org-policies describe CONSTRAINT --effective` shows the effective policy at a resource after inheritance; it doesn't simulate API calls.
- `inheritFromParent` controls whether a child merges its parent's list policy; it has nothing to do with logging.
## Example rollout
1. Set `compute.vmExternalIpAccess` with a deny-all rule as a dry-run policy at the organization.
2. Review the audit log entries for a few weeks and fix or except the workloads that need external IPs.
3. Enforce the policy.
W: Dry-run mode: the policy is evaluated and violations are audit-logged while nothing is denied, which is exactly the "see what breaks first" requirement.
X: B=describe --effective: it shows how policies combine at a resource, not which API calls would be rejected by a policy that isn't in place yet.

@ GCP-ACE D1 T1.1 advanced tradeoff
S: A company is creating projects for production workloads that will connect to its on-premises network, which uses 10.128.0.0/16 among other ranges. The network team wants every new production project to start with no network, so that they can create custom mode VPCs with planned ranges. What should be configured?
A: Enforce the compute.skipDefaultNetworkCreation constraint on the Production folder, so that new projects there are created without the default network
B: Keep the default network in each project, because its auto mode subnets can be peered with on-premises networks that use overlapping ranges
C: Delete the default firewall rules after each project is created, because the default network only becomes an auto mode network through those rules
D: Convert each project's custom mode default network to auto mode after creation, so that the subnet ranges are then chosen by the network team
K: A
G: ## The default network
Unless disabled, every new project starts with a **default network**: an **auto mode** VPC network with one subnet per region and pre-populated IPv4 firewall rules (such as `default-allow-internal`, SSH and RDP).
- Auto mode subnets use predefined ranges inside `10.128.0.0/9`, and new regions get subnets automatically.
- That range is part of RFC 1918 space and often overlaps with on-premises networks. Auto mode networks also can't be connected to each other with VPC Network Peering or Cloud VPN, because their ranges are the same.
## Custom mode for production
Custom mode networks create no subnets automatically; you choose regions and ranges. Google calls them more flexible and better suited to production. You can convert auto mode to custom mode, but not the reverse.
## Skipping the default network
The boolean constraint `compute.skipDefaultNetworkCreation` skips creating the default network and its related resources when a project is created. Set on a folder, it applies to every project created below it.
W: skipDefaultNetworkCreation on the folder: projects created in the Production folder start with no network, so the team builds custom mode VPCs with ranges that don't collide with 10.128.0.0/16.
X: B=Keep and peer the default network: overlapping ranges can't be routed between networks, and the default network's 10.128.0.0/9 subnets collide with the on-premises range.
C=Delete default firewall rules: firewall rules don't define the network type; the auto mode network and its overlapping subnets would remain.
D=Convert to auto mode: the default network is already auto mode, and conversion only goes from auto mode to custom mode, never the reverse.
T: Use `compute.skipDefaultNetworkCreation` so production projects start without the auto mode default network, then build custom mode VPCs.
V: Virtual Private Cloud, Organization Policy Service

S: A company's employees and contractors already sign in to all company apps through Okta. The company wants them to access the Google Cloud console and gcloud with single sign-on through Okta, without creating or synchronizing user accounts in Cloud Identity. Which approach meets this requirement?

- **Allow policies**: grant roles to pool principals.

## Not to be confused with
**Workload** Identity Federation federates **workloads** (applications, CI pipelines), not people.
W: Workforce Identity Federation: a workforce pool with an Okta provider gives users SSO to the console and gcloud while keeping identities in Okta, with no accounts synced into Cloud Identity.
X: B=GCDS plus SAML SSO: this is a valid design, but it creates and synchronizes Cloud Identity accounts, which the company wants to avoid.
C=Workload Identity Federation: it is meant for workloads, and sharing one service account among people removes per-user identity and audit trails.
D=Manual Cloud Identity accounts: this creates the accounts the company wants to avoid, and 2-Step Verification doesn't make Google reuse Okta passwords.
T: For people signing in with an external IdP without syncing accounts, use Workforce Identity Federation; Workload Identity Federation is for applications.

S: A company federates its users through a workforce identity pool named corp-pool. Its IdP sends a groups claim mapped to google.groups. The admin must grant the Compute Viewer role on project ops-tools to every federated user in the IdP group sre-team. Which principal identifier should the role binding use?

C: principalSet://iam.googleapis.com/locations/global/workforcePools/corp-pool/*

G: ## Principals from a workforce pool
Federated users have no Google Account email, so allow policies refer to them by **principal identifiers** based on the pool:
- One user: `principal://iam.googleapis.com/locations/global/workforcePools/POOL_ID/subject/SUBJECT` (the value mapped to `google.subject`).
- All users in an IdP group: `principalSet://iam.googleapis.com/locations/global/workforcePools/POOL_ID/group/GROUP_ID` (from `google.groups`).
- All users with an attribute value: `principalSet://.../workforcePools/POOL_ID/attribute.ATTRIBUTE/VALUE`.
- Everyone in the pool: `principalSet://.../workforcePools/POOL_ID/*`.
## Group access caution
Every member of a mapped group gets the access, so only authorized people should be able to change membership of those groups in the IdP.
## Example
`gcloud projects add-iam-policy-binding ops-tools --member="principalSet://iam.googleapis.com/locations/global/workforcePools/corp-pool/group/sre-team" --role="roles/compute.viewer"`.
W: principalSet with /group/: the group form of the identifier matches every federated user whose `google.groups` attribute contains sre-team, exactly the required audience.
X: B=principal with /subject/: this names a single user whose subject is the literal value sre-team, not the members of a group.
C=Whole pool wildcard: this grants the role to every identity in corp-pool, far more than the SRE team.
D=group: email: workforce pool groups aren't Google groups with email addresses, and `iam.gserviceaccount.com` is the service account domain.
T: Grant roles to federated groups with `principalSet://iam.googleapis.com/locations/global/workforcePools/POOL/group/GROUP`.
