@ GCP-ACE D4 T4.1 applied use-case
S: Before a quarterly access review, a cloud engineer must save every role binding on the project web-prod, including any conditions, to a file that the security team can read. Which gcloud command should the engineer run?
A: gcloud iam roles list --project=web-prod --format=json > ~/policy.json
B: gcloud projects describe web-prod --format=json > ~/policy.json
C: gcloud projects get-iam-policy web-prod --format=json > ~/policy.json
D: gcloud iam policies list --attachment-point=cloudresourcemanager.googleapis.com/projects/web-prod --kind=denypolicies --format=json > ~/policy.json
K: C
G: ## What an allow policy is
In Google Cloud, access is granted through an **allow policy** attached to a resource (organization, folder, project, or a resource such as a bucket or topic). Each resource has exactly one allow policy. The policy is a list of **role bindings**; each binding ties one role to one or more principals and can carry an optional **condition**. The policy also has metadata: an `etag` for concurrency control and a `version` (`3` when conditions are present).
## Reading the policy of a project, folder or organization
The `get-iam-policy` command returns the whole allow policy of one resource:
- Project: `gcloud projects get-iam-policy PROJECT_ID`
- Folder: `gcloud resource-manager folders get-iam-policy FOLDER_ID`
- Organization: `gcloud organizations get-iam-policy ORG_ID`
Adding `--format=json` (or yaml) and redirecting the output gives a file you can review, diff or edit for a later `set-iam-policy`.
## What other commands show
- `gcloud iam roles list --project=...` lists role definitions (custom roles), not who holds them.
- `gcloud projects describe` shows project metadata such as ID, number, parent and lifecycle state.
- `gcloud iam policies list --kind=denypolicies` lists **deny** policies, a separate policy type.
W: get-iam-policy: it returns the project's allow policy with every role binding, its members, any conditions and the etag, and --format=json writes it in a reviewable form.
X: A=gcloud iam roles list: it lists the custom role definitions available in the project, which describe permissions but say nothing about which principals hold them.
B=gcloud projects describe: it prints project metadata such as the project number, parent and lifecycle state; role bindings are not part of that output.
D=gcloud iam policies list for deny policies: it lists the deny policies attached to the project, which are separate from the allow policy that holds the role bindings.
T: To see who has which role on a project, folder or organization, read its allow policy with get-iam-policy.
V: IAM, Resource Manager

@ GCP-ACE D4 T4.1 advanced troubleshooting
S: Two automation pipelines manage the allow policy of project data-hub. Each one runs gcloud projects get-iam-policy, edits the file, and then runs gcloud projects set-iam-policy. One night, one pipeline's set-iam-policy call fails with HTTP 409 Conflict, while the other pipeline's change succeeded a few seconds earlier. What should the failing pipeline do?
A: Delete the etag field from its edited file and run set-iam-policy again, so the update is no longer checked against the stored policy version
B: Read the current policy again, apply its change to that fresh copy with the new etag, and then call set-iam-policy once more
C: Change the version field in its edited file from 1 to 3 before retrying, because a version mismatch is the cause of the 409 Conflict error
D: Wait until the other pipeline's change has propagated through IAM, then resubmit exactly the same edited file without any modifications
K: B
G: ## Read-modify-write and the etag
Allow policies are updated with a **read-modify-write** pattern: read the whole policy, change it locally, write the whole policy back. If two writers do this at the same time, the second write could silently erase the first writer's change.
IAM prevents that with the `etag` field. Every allow policy has an etag, and its value changes each time the policy is updated. When you write a policy that includes the etag you read, IAM compares it with the stored one:
- Same etag: nobody changed the policy in between, so the write succeeds.
- Different etag: someone changed it after you read it, so the write fails (REST API: `409 Conflict`).
## The correct reaction
Start over from a fresh read: get the policy again (which now contains the other pipeline's change and a new etag), reapply your edit, and write it back. Removing the etag would turn the write into a blind overwrite and lose the other change.
## Related tip
For single grants, `add-iam-policy-binding` and `remove-iam-policy-binding` change one binding without your script handling the whole file.
W: Re-read and reapply: the fresh copy contains the other pipeline's binding and the current etag, so the retried write succeeds and both changes survive, which is exactly what etag concurrency control is designed for.
X: A=Delete the etag: without the etag IAM can no longer detect the conflict, so the stale file would overwrite the policy and silently remove the other pipeline's change.
C=Bump version to 3: the version field only declares the schema (3 is needed for conditional bindings); the conflict comes from a stale etag, which a version change does not fix.
D=Wait and resubmit the same file: the file still carries the old etag and lacks the other change, so it keeps failing; propagation delay is not what the 409 response means.
T: A 409 on set-iam-policy means a stale etag: read the policy again, reapply the change, and write it back.
V: IAM

@ GCP-ACE D4 T4.1 applied troubleshooting
S: Maria belongs to the sre-team group, which holds Compute Instance Admin (v1) on the Platform folder. She was also granted the same role directly on the project billing-api, which sits under Platform. To stop her from managing VMs in billing-api, an admin removed her project-level binding, but Maria can still stop VMs there. What explains this?
A: Changes to an allow policy take effect only after the project's resources are restarted, so her existing VMs still honor the old project binding
B: Removing a binding from a project policy is ignored while the same role is still granted on the folder, so the removal must be repeated there first
C: Project-level bindings override folder-level bindings, so the admin must also add an explicit binding with no role to block inherited access
D: Her effective access is the union of the project's policy and its ancestors' policies, so the folder grant to her group still applies there
K: D
G: ## Effective policy is a union
Allow policies are inherited down the resource hierarchy: organization, then folders, then projects, then resources in the project. The **effective policy** for a resource is the **union** of:
- the allow policy attached to the resource itself, and
- the allow policies of all its ancestors.
An access request is allowed if **any** of those bindings grants the needed permission. A lower level can add access but cannot take away access granted higher up; allow policies have no "remove" or "override" entry.
## Example
`group:sre-team@example.com` has `roles/compute.instanceAdmin.v1` on `folders/Platform`. Every project under Platform, and every VM in those projects, inherits that grant. Removing a direct grant from one project changes nothing while the folder grant remains.
## Ways to really remove the access
- Remove Maria from the group, or remove or narrow the folder-level grant.
- Keep the folder grant and attach an IAM **deny policy** to the project that denies the specific permissions to her.
W: Union of policies: IAM grants access if any binding in the project or an ancestor allows it, so the folder-level grant to sre-team keeps giving Maria the role in billing-api after her direct grant is gone.
X: A=Restart required: IAM changes do not depend on restarting resources; the access remains because another binding still grants it, not because the removal is pending.
B=Removal ignored: the project binding was really removed; it just was never her only source of access, and nothing requires changing the folder first.
C=Project overrides folder: allow policies only add permissions, a binding with no role does not exist, and a lower-level policy cannot cancel an inherited grant.
T: Allow policies add up down the hierarchy; to block inherited access, change the higher-level grant or use a deny policy.
V: IAM, Resource Manager

@ GCP-ACE D4 T4.1 advanced use-case
S: The sre-team group needs Compute Instance Admin (v1) in all 12 projects under the Platform folder, and new projects will be added there. In one of them, payments-prod, the group must never be able to delete VMs, although every other permission of the role should still work there. What is the simplest setup?
A: Grant the role on the Platform folder and attach a deny policy to payments-prod that denies compute.googleapis.com/instances.delete to the group
B: Grant the role on the Platform folder and add a role binding on payments-prod that grants the group the Compute Viewer role to replace it
C: Grant the role on the Platform folder with a condition that excludes payments-prod, so the binding never applies to VM deletion requests there
D: Grant the role separately on each of the 11 other projects and grant a custom role without delete permission on payments-prod by hand
K: A
G: ## Granting broadly, then carving out exceptions
Granting a role on a folder is the least effort way to cover all current and future projects in it. Allow policies cannot subtract access lower down, so exceptions need a different tool: an **IAM deny policy**.
## How deny policies work
- A deny policy contains **deny rules**: denied principals, denied permissions, optional exception principals and permissions, and an optional condition.
- It is attached to an **organization, folder or project** and inherited by everything below.
- IAM checks deny policies **before** allow policies, so a denied permission can't be used regardless of granted roles.
- Denied permissions use the v2 format `SERVICE_FQDN/RESOURCE.ACTION`, for example `compute.googleapis.com/instances.delete`.
## Example
```
deniedPrincipals: principalSet://goog/group/sre-team@example.com
deniedPermissions: compute.googleapis.com/instances.delete
```
attached to `cloudresourcemanager.googleapis.com/projects/payments-prod`. The folder grant still gives every other permission of the role in that project.
W: Folder grant plus deny policy: the folder grant covers all projects including new ones, and the deny rule on payments-prod blocks only VM deletion there, because deny rules are checked before any allow binding.
X: B=Add Compute Viewer on the project: an extra allow binding only adds permissions; the inherited admin role is still part of the effective policy, so deletion still works.
C=Conditional folder grant excluding the project: excluding the project would drop every permission of the role there, not only deletion, which breaks the requirement to keep the other permissions.
D=Per-project grants and a custom role: this is more work, misses future projects added to the folder, and creates a custom role the team must keep up to date.
T: Grant high in the hierarchy and use a deny policy on the exception; allow policies alone cannot remove an inherited permission.
V: IAM

@ GCP-ACE D4 T4.1 applied use-case
S: A billing service running on a VM in project shop-prod uses a dedicated identity that only needs to publish messages to the Pub/Sub topic orders. The project also contains 15 other topics with sensitive data. Following least privilege, how should the identity be granted access?
A: Grant the Pub/Sub Publisher role on the shop-prod project, so the identity can publish to orders and to any topic created later in the project
B: Grant the Pub/Sub Publisher role on the orders topic only, so the identity can publish to that topic and to no other topic in the project
C: Grant the Pub/Sub Editor role on the orders topic, so the identity can publish and also fix the topic's settings without asking an admin
D: Grant the legacy Editor basic role (roles/editor) on the shop-prod project, then rely on the application code to publish only to orders
K: B
G: ## Least privilege has two dimensions
Least privilege means a principal gets only the permissions it needs, **on only the resources** it needs them for:
- **Which role**: pick the predefined role whose permissions match the task. Pub/Sub Publisher (`roles/pubsub.publisher`) contains only `pubsub.topics.publish`.
- **Where to grant it**: grant at the **smallest scope**. Roles granted on a project apply to every resource in it through inheritance. Many services accept grants on individual resources: the lowest level for Pub/Sub Publisher is a **topic**.
## Example
A grant on `projects/shop-prod/topics/orders` lets the identity publish to `orders` only. The same role on the project would let it publish to all 16 topics, now and in the future.
## Why basic roles are a poor fit
Basic roles, both the current Admin, Writer and Reader roles and the legacy Owner, Editor and Viewer roles, contain thousands of permissions across all services. Google recommends not granting any of them in production unless there is no alternative.
W: Publisher on the topic: the role has only the publish permission and the topic is the smallest resource the task needs, so the identity can't touch the 15 sensitive topics.
X: A=Publisher on the project: the right role at too wide a scope, because a project grant is inherited by every topic, including the sensitive ones and any new ones.
C=Pub/Sub Editor on the topic: the scope is right but the role is too broad, adding permissions to change and delete the topic that the service never needs.
D=Legacy Editor basic role on the project: it grants write access to almost every service in the project, and application code is not a security control.
T: Least privilege = narrowest role at the smallest resource that still lets the task work.
V: Pub/Sub, IAM

@ GCP-ACE D4 T4.1 applied use-case
S: A group of analysts must run SQL queries against the tables of the BigQuery dataset sales in project data-hub, and their query jobs must run in data-hub. They must not change data or see the project's other datasets. Which TWO role grants together meet this requirement with least privilege? (Select TWO)
A: BigQuery Data Viewer (roles/bigquery.dataViewer) granted on the sales dataset
B: BigQuery Data Editor (roles/bigquery.dataEditor) granted on the data-hub project
C: BigQuery Job User (roles/bigquery.jobUser) granted on the data-hub project
D: BigQuery Admin (roles/bigquery.admin) granted on the sales dataset only
E: Viewer (roles/viewer) granted on the data-hub project for the group
K: A,C
G: ## Querying needs two kinds of permission
In BigQuery, running a query needs:
- permission to **read the data**: `bigquery.tables.getData` and related permissions on the tables being queried, and
- permission to **create a job** in a project: `bigquery.jobs.create`, because every query runs as a job in some project.
These live in different predefined roles granted at different levels:
- **BigQuery Data Viewer** (`roles/bigquery.dataViewer`) can be granted on a dataset (or a table or view) and lets principals read table data and metadata in that dataset only.
- **BigQuery Job User** (`roles/bigquery.jobUser`) can only be granted on projects, folders or organizations; it contains `bigquery.jobs.create` and no data access.
## Example
Data Viewer on `data-hub:sales` plus Job User on `data-hub` lets analysts run `SELECT` queries on sales tables. Other datasets in data-hub stay invisible because no read role was granted on them.
W: A=Data Viewer on the dataset: it gives read access to the sales tables only, without write permissions and without reaching other datasets in the project.
C=Job User on the project: queries run as jobs, and this role adds the job creation permission in data-hub without granting any data access.
X: B=Data Editor on the project: it lets analysts change table data and reaches every dataset in data-hub, breaking both restrictions.
D=BigQuery Admin on the dataset: far more than reading, including deleting tables and changing the dataset's access, so it violates least privilege.
E=Viewer basic role: a legacy basic role with read access across all services in the project, which exposes the other datasets and is discouraged in production.
T: BigQuery queries = read access on the data (Data Viewer, on the dataset) + job creation on the project (Job User).
V: BigQuery, IAM

@ GCP-ACE D4 T4.1 applied use-case
S: An audit found 40 principals holding the Editor role on production projects. The security lead wants to reduce these grants with evidence: which permissions each principal actually used recently, and a suggested smaller role to replace or remove each grant. Which feature should the lead use?
A: Policy Troubleshooter, run once for each principal and production project to check whether that principal can still use the Editor role there
B: Role recommendations from the IAM recommender, which compare granted permissions with the permissions each principal used in the last 90 days
C: The Security Reviewer role granted to the lead on the organization, which lists each principal's unused permissions next to its allow policies
D: Cloud Asset Inventory searches of every production allow policy, filtered to role bindings that grant roles/editor on production projects
K: B
G: ## Finding excess permissions
Basic roles such as the legacy Editor role (`roles/editor`) contain thousands of permissions, so most holders use only a small part of them. To shrink these grants safely you need usage data.
## Role recommendations
The **IAM recommender** (part of Policy Intelligence) produces:
- **Policy insights**: ML-based findings that compare a principal's granted permissions with the permissions it used during the observation period (at most the last 90 days).
- **Role recommendations**: suggestions to **remove** a role the principal does not need or **replace** it with a smaller predefined role, an existing custom role, or a new project-level custom role.
Insights and recommendations exist for roles granted on organizations, folders, projects, Cloud Storage buckets and BigQuery datasets, and not for conditional role bindings.
## Other tools and what they answer
- **Policy Troubleshooter**: can principal X use permission Y on resource Z, and which policies decide that?
- **Cloud Asset Inventory**: which bindings exist where (search and analysis), not which permissions were used.
W: Role recommendations: they are built from each principal's real permission usage and suggest a removal or a smaller replacement role, which is exactly the evidence-based clean-up of Editor grants the lead needs.
X: A=Policy Troubleshooter: it explains whether a given principal can use a given permission on a resource, but it does not measure usage or suggest smaller roles.
C=Security Reviewer role: it lets the lead list resources and allow policies but contains no usage data, so it cannot show which granted permissions are unused.
D=Cloud Asset Inventory search: it finds who holds Editor, which the audit already knows, but has no information about which permissions those principals used.
T: To right-size over-broad grants with usage evidence, use IAM role recommendations (IAM recommender).
V: IAM, Recommender

@ GCP-ACE D4 T4.1 applied comparison
S: A platform team designs a custom role named vmOperator. It must be grantable in every project under the Engineering folder, including projects created later. A teammate already created a project-level vmOperator in project eng-tools. Which TWO statements are correct? (Select TWO)
A: The team should create vmOperator as an organization-level custom role, which can be granted on the Engineering folder and on resources inside the organization
B: The team should create vmOperator as a folder-level custom role on Engineering, so only projects under that folder can grant it to their principals
C: The vmOperator role created in eng-tools can be granted only on eng-tools and its resources, not on other projects in the folder
D: The vmOperator role created in eng-tools becomes grantable in sibling projects once it is granted on the Engineering folder
E: An organization-level vmOperator can also be granted in another organization the company owns, as long as the role ID is identical
K: A,C
G: ## Where custom roles live
A **custom role** is a list of permissions you define. When you create it you choose its container, and only two containers exist:
- **Organization-level** custom roles: name `organizations/ORG_ID/roles/ROLE_ID`. They can be granted on the organization and on any resource inside it: folders, projects and their resources.
- **Project-level** custom roles: name `projects/PROJECT_ID/roles/ROLE_ID`. They can be granted only on that project and its resources.
There are **no folder-level custom roles**. A custom role can't be granted in another project or organization than the one it was created in. Each organization and each project can hold up to 300 custom roles.
## Practical rule
If several projects need the same custom role, create it once at the organization level and grant it where needed (for example on a folder). Create project-level roles only when a role is really specific to one project.
Note that project-level custom roles can't include permissions that work only at the folder or organization level.
W: A=Organization-level role: it is defined once for the whole organization and can be granted on the Engineering folder, so all current and future projects there inherit it.
C=Project-level role stays in its project: custom roles can be granted only within the project or organization where they were created, so the eng-tools role can't be used in other projects.
X: B=Folder-level custom role: custom roles can be created only in an organization or a project; folders cannot hold role definitions.
D=Granting it on the folder: a project-level role can't be granted on the folder at all, because the folder is outside the project that defines it.
E=Reuse in another organization: custom roles cannot be granted in other organizations; a matching role ID there would be a separate role defined in that organization.
T: Custom roles exist only at organization or project level and can be granted only inside their own container.
V: IAM

@ GCP-ACE D4 T4.1 applied use-case
S: A security engineer is drafting a custom role for project media-prod and wants a list of the permissions that can actually be included in a custom role there, leaving out those that are not supported in custom roles. Which command gives this list?
A: gcloud iam roles describe roles/editor --format=json, filtered for permissions whose names contain the services used in media-prod
B: gcloud iam list-testable-permissions //cloudresourcemanager.googleapis.com/projects/media-prod --filter="customRolesSupportLevel!=NOT_SUPPORTED"

D: gcloud iam roles list --project=media-prod --show-deleted, which includes the permissions of every custom role created in the project
K: B
G: ## Not every permission fits in a custom role
Each IAM permission has a **support level** for custom roles:
- `SUPPORTED`: fully supported.
- `TESTING`: can be included but might behave unexpectedly; not recommended for production.
- `NOT_SUPPORTED`: can't be used in custom roles.
Availability also depends on where the role is created. A project-level role can't include permissions that work only on folders or organizations, and a permission may not appear if its service's API isn't enabled.
## Listing usable permissions
`gcloud iam list-testable-permissions FULL_RESOURCE_NAME` returns the permissions available for custom roles in a project or organization, with each one's support level. The resource uses its full name, for example `//cloudresourcemanager.googleapis.com/projects/media-prod`. Filtering on `customRolesSupportLevel!=NOT_SUPPORTED` drops the ones that can't be used.
## Then create the role
`gcloud iam roles create ROLE_ID --project=media-prod --permissions=...` (or `--file=role.yaml`) fails if the list includes an unsupported permission.
W: list-testable-permissions: it is the command that returns the permissions usable in custom roles for a given project, and the filter removes those marked NOT_SUPPORTED.
X: A=Describe roles/editor: it lists the permissions of one basic role, without support levels, so it can't tell which ones custom roles accept.
C=Get the project's allow policy: the policy holds role bindings, not permission lists, and it says nothing about custom role support.
D=List project roles with deleted ones: it shows existing custom role definitions, not the catalog of permissions that new roles may include.
T: Use gcloud iam list-testable-permissions on the project or organization to see which permissions a custom role can contain there.

An **IAM condition** is a CEL expression on a role binding; the binding applies only while the expression is true. Date/time attributes work with all Google Cloud services, so a condition on `request.time` is the standard way to make access **expire**:
