@ GCP-ACE D2 T2.1 applied troubleshooting
S: A new engineer installed the Google Cloud CLI on her laptop, ran gcloud components install kubectl, and fetched credentials for a GKE cluster. Every kubectl command now fails with an error saying that gke-gcloud-auth-plugin is not found. What should she do?
A: Install the missing component with gcloud components install gke-gcloud-auth-plugin, then run the kubectl command again
B: Ask an administrator to grant her roles/container.admin on the project so kubectl may use her gcloud credentials
C: Download a static service account key for the cluster and point the KUBECONFIG variable at the downloaded JSON file
D: Recreate the cluster with legacy client certificate authentication enabled so kubectl no longer needs any plugin
K: A
G: ## How kubectl talks to GKE
`kubectl` is the standard Kubernetes command-line tool. You can install it as a Google Cloud CLI component (`gcloud components install kubectl`); Cloud Shell already has it.
kubectl does not log in to GKE by itself. It relies on an **authentication plugin**, `gke-gcloud-auth-plugin`, which uses the client-go credential plugin framework to hand kubectl short-lived tokens based on your gcloud identity. Without the plugin, kubectl and other Kubernetes clients cannot talk to GKE clusters and show an error.
## Setup on a new machine
- `gcloud components install kubectl`
- `gcloud components install gke-gcloud-auth-plugin` (or the `google-cloud-cli-gke-gcloud-auth-plugin` package with apt or yum); check with `gke-gcloud-auth-plugin --version`
- `gcloud container clusters get-credentials CLUSTER --location=LOCATION` to write the kubeconfig entry
W: Install gke-gcloud-auth-plugin: the error names a missing binary, and the plugin is what turns her gcloud credentials into tokens for kubectl; once it is installed the existing kubeconfig entry works.
X: B=Grant roles/container.admin: an IAM role adds permissions, but kubectl still cannot obtain any token without the plugin, so the same "not found" error remains.
C=Service account key file: a key file is not a kubeconfig, and long-lived keys are a security risk to avoid; the fix is the auth plugin, not another credential.
D=Recreate with client certificates: rebuilding a cluster to work around a missing local binary is disruptive, and the supported path for GKE is the auth plugin.
T: kubectl on a new machine needs two gcloud components, kubectl and gke-gcloud-auth-plugin, plus get-credentials for each cluster.
V: GKE, Google Cloud CLI

@ GCP-ACE D2 T2.1 applied use-case
S: A three-person startup wants to run a dozen containerized microservices on Kubernetes. Nobody on the team wants to size, upgrade or repair nodes, and the founders want general-purpose workloads billed for the resources the Pods request rather than for whole VMs. Which GKE setup fits?
A: A zonal GKE Standard cluster with node auto-repair and auto-upgrade enabled on a single e2-standard-4 node pool
B: A regional GKE Standard cluster with the cluster autoscaler enabled on three node pools of different machine types
C: A GKE Autopilot cluster, where Google manages the nodes and general-purpose Pods use the Pod-based billing model
D: A Compute Engine managed instance group running the containers with Container-Optimized OS and a startup script
K: C
G: ## Two modes of GKE
- **Autopilot**: Google manages the infrastructure, including nodes, scaling, security settings and upgrades. You deploy Kubernetes manifests and GKE provisions compute to fit them. Autopilot clusters are always **regional** and always enrolled in a release channel. It is the recommended way to use GKE.
- **Standard**: you create and manage nodes in **node pools** (machine types, autoscaling, upgrades), with full control and optional zonal or regional placement.
## Billing in Autopilot
General-purpose Autopilot Pods use a **Pod-based billing model**: you pay for the resources your Pods request. Pods that select specific hardware (a machine series, GPUs) use a node-based model instead, paying for the hardware plus a management premium.
## Choosing
Small team, no wish to manage nodes, pay for what Pods ask for → Autopilot. Need for direct control of node pools and node configuration → Standard.
W: GKE Autopilot: Google creates, scales, upgrades and repairs the nodes, and general-purpose Pods are billed on the resources they request, which matches both of the founders' wishes.
X: A=Zonal Standard with auto-repair: auto-repair and auto-upgrade help, but the team still sizes and owns the node pool and pays for the node VMs whether Pods use them or not.
B=Regional Standard with autoscaler: three node pools are more node management, not less, and billing is still for node VMs rather than Pod requests.
D=MIG with Container-Optimized OS: this drops Kubernetes altogether, so the team would build its own scheduling, service discovery and rollouts on VMs it manages.
T: No node management + pay for what Pods request → GKE Autopilot; full control of node pools → GKE Standard.
V: GKE

@ GCP-ACE D2 T2.1 applied definition
S: A platform team is writing an internal guide on GKE Autopilot clusters. Which statements belong in it? (Select TWO)
A: Every Autopilot cluster is regional, with control plane replicas across multiple zones of the region you choose
B: Autopilot clusters can be zonal to save cost, and a zonal cluster can be converted to a regional one later on
C: Google creates and manages the worker nodes, so you never add node pools to an Autopilot cluster yourself
D: Autopilot clusters can opt out of release channels so that the team decides when the control plane is upgraded
E: Autopilot bills every Pod, including Pods that select GPUs, only for the CPU and memory that the Pod requests
K: A,C
G: ## Autopilot at a glance
GKE Autopilot is a mode of operation in which Google manages the infrastructure configuration: nodes, scaling, security settings and upgrades.
- **Location**: pre-configured as regional. A regional cluster runs multiple control plane replicas in several zones of the region.
- **Nodes**: Google provisions nodes from your manifests; you request special hardware through ComputeClasses instead of creating node pools.
- **Upgrades**: every Autopilot cluster is enrolled in a release channel (Rapid, Regular or Stable).
- **Billing**: general-purpose Pods use Pod-based billing; Pods that select specific hardware such as GPUs or a machine series use node-based billing (hardware plus a management premium).
## Not changeable later
The availability type is fixed at creation: a zonal cluster can't become regional, and a regional cluster can't become zonal.
W: A=Always regional: Autopilot's location setting is pre-configured as regional, so the control plane is replicated across zones in the chosen region.
C=Google manages nodes: in Autopilot, Google provisions worker nodes for your workloads; you state hardware needs in ComputeClasses rather than building node pools.
X: B=Zonal and convertible: Autopilot has no zonal option, and no GKE cluster can switch between zonal and regional after creation.
D=Opt out of release channels: all Autopilot clusters are enrolled in a release channel; you can pick Rapid, Regular or Stable and use maintenance windows, not opt out.
E=Pod-based billing for GPUs: Pods that select specific hardware such as GPUs use node-based billing, paying for the hardware plus a node management premium.
T: Autopilot: always regional, Google-managed nodes, always in a release channel; Pod-based billing for general-purpose Pods only.

@ GCP-ACE D2 T2.1 applied tradeoff
S: Six months ago a team created a zonal GKE Standard cluster in us-central1-a for its checkout service. Leadership now requires that the cluster's control plane stay available during the loss of a single zone. What must the team do?
A: Update the existing cluster with gcloud container clusters update and a --region flag so it becomes regional
B: Add a second node pool in us-central1-b, because spreading nodes across zones also replicates the control plane
C: Enable node auto-repair on the existing pool, which recreates the control plane in another zone if its zone fails
D: Create a new regional cluster in us-central1 and migrate the workloads, since zonal clusters can't become regional
K: D
G: ## Zonal and regional control planes
- A **zonal cluster** has a single control plane in one zone. If that zone has an outage, you cannot manage the cluster (deploy, scale, change config) until it returns, even if nodes in other zones keep running.
- A **regional cluster** has multiple control plane replicas spread across zones in one region, so it survives a zone loss. By default each node pool is also replicated across three zones.
Google's guidance: use regional clusters for production; for development, a regional control plane with zonal node pools costs the same as a zonal cluster.
## Fixed at creation
The availability type cannot be updated: a zonal cluster can't become regional and the reverse. Changing it means a new cluster and a workload migration.
W: New regional cluster and migration: only a regional cluster replicates the control plane across zones, and because the type is fixed at creation the team must build one and move the workloads.
X: A=Update with --region: there is no in-place conversion; the docs state that a zonal cluster can't become a regional cluster.
B=Node pool in another zone: multi-zonal nodes keep workloads running, but the single zonal control plane still has no replica outside us-central1-a.
C=Node auto-repair: auto-repair replaces unhealthy nodes; it does nothing for the control plane and never moves it to another zone.
T: Control plane must survive a zone loss → regional cluster; zonal vs regional is chosen at creation and cannot be changed.
V: GKE

@ GCP-ACE D2 T2.1 applied use-case
S: Security policy says GKE nodes must not have external IP addresses. The workloads pull some images from a public registry on the internet and call a partner's public HTTPS API. Which cluster setup meets both needs?
A: Create the cluster with --enable-private-nodes and set up Cloud NAT for the cluster's subnet so nodes get outbound internet access
B: Create the cluster with --enable-private-nodes and rely on Private Google Access, which also routes traffic to internet hosts
C: Create the cluster with --no-enable-private-nodes and add a firewall rule that denies all ingress traffic to the node VMs
D: Create the cluster with --enable-private-nodes and add authorized networks, which give nodes a path to internet hosts
K: A
G: ## Private nodes
With `--enable-private-nodes`, GKE creates nodes with **only internal IP addresses**. Nodes then have limited access to Google Cloud APIs and services and no route to the internet by themselves.
- **Private Google Access** is enabled automatically (unless you use Shared VPC), so nodes can still reach Google APIs such as Artifact Registry.
- For **outbound internet access** (public registries, partner APIs) you add **Cloud NAT**, which lets VMs without external IPs open connections out without accepting inbound ones.
## Other controls that sound similar
- **Authorized networks** limit which source IP ranges may reach the cluster's **control plane** IP-based endpoint. They do not affect node egress.
- `--no-enable-private-nodes` provisions nodes with external IP addresses.
W: Private nodes plus Cloud NAT: private nodes have no external IPs, which satisfies the policy, and Cloud NAT gives them the outbound path to the public registry and the partner API.
X: B=Private Google Access alone: it lets internal-only VMs reach Google APIs and services, not arbitrary internet hosts, so the public registry and partner API stay unreachable.
C=Public nodes with deny ingress: --no-enable-private-nodes gives every node an external IP, which the policy forbids no matter what firewall rules are added.
D=Authorized networks: they restrict who can reach the control plane endpoint; they give nodes no route to the internet.
T: No external IPs on nodes → private nodes; outbound internet from them → Cloud NAT; Google APIs → Private Google Access.
V: GKE, Cloud NAT

@ GCP-ACE D2 T2.1 applied use-case
S: An engineer has an Autopilot cluster and a container image in Artifact Registry. The web app in the image listens on port 8080. She wants the app running and reachable from the internet on port 80 with as few steps as possible. Which kubectl commands should she run?
A: kubectl run web --image=IMAGE --port=80, then kubectl expose pod web --type ClusterIP --port 80 --target-port 8080
B: kubectl create deployment web --image=IMAGE, then kubectl expose deployment web --type LoadBalancer --port 80 --target-port 8080
C: kubectl create deployment web --image=IMAGE, then kubectl expose deployment web --type ClusterIP --port 8080 --target-port 80
D: kubectl apply -f with a Deployment whose containerPort is 80, then kubectl port-forward deployment/web 80:8080 on her laptop
K: B
G: ## Deploying an image to GKE
1. **Deployment**: `kubectl create deployment NAME --image=IMAGE` creates a Deployment whose Pods run the image. The Deployment keeps the desired number of Pods running and replaces failed ones.
2. **Service**: Pods are not reachable from outside the cluster by default. `kubectl expose deployment NAME --type LoadBalancer --port 80 --target-port 8080` creates a Service of type `LoadBalancer`; GKE provisions a Google Cloud load balancer with an external IP.
- `--port` is the port clients use on the Service (80 here).
- `--target-port` is the port the container listens on (8080 here).
3. `kubectl get service NAME` shows the external IP once the load balancer is ready.
## Service types
- `ClusterIP` (default): a stable internal IP reachable only from inside the cluster.
- `NodePort`: a port on every node's IP.
- `LoadBalancer`: a network load balancer IP in front of the Service.
W: Deployment plus LoadBalancer Service: create deployment runs and maintains the Pods, and expose with --type LoadBalancer maps public port 80 to container port 8080 through an external load balancer.
X: A=Bare Pod with ClusterIP: a single Pod is not recreated if it fails, and a ClusterIP Service is reachable only inside the cluster, not from the internet.
C=ClusterIP with ports swapped: the Service is internal only, and the ports are reversed, sending traffic to port 80 where nothing listens.
D=port-forward from a laptop: port-forward tunnels traffic to her own machine for debugging; it does not publish the app to internet users.
T: Run an image on GKE with a Deployment; publish it with a LoadBalancer Service, --port for clients and --target-port for the container.
V: GKE, kubectl

@ GCP-ACE D2 T2.1 applied use-case
S: A developer has a small Node.js web service in a local folder with no Dockerfile, and Docker isn't installed on his workstation. He wants to deploy it to Cloud Run with one command and no manual image build. What should he run, and what happens?
A: gcloud run deploy --source . so Cloud Build and Google Cloud's buildpacks build an image, store it in Artifact Registry, and deploy it
B: gcloud run deploy --image . so Cloud Run reads the local folder as an image and starts the code with the Node.js runtime directly
C: gcloud builds submit --tag first, because Cloud Run accepts only images built by the user and pushed to Artifact Registry by hand
D: gcloud run deploy --source . so the source is copied into a Cloud Storage bucket and Cloud Run runs the files without any image
K: A
G: ## Deploying from source
`gcloud run deploy SERVICE --source .` deploys a Cloud Run service straight from a source folder:
- If the folder has a **Dockerfile**, it is used for the build.
- If not, **Google Cloud's buildpacks** detect the language (Node.js, Python, Go, Java, .NET, Ruby, PHP), fetch dependencies and build a production-ready image on a Google-managed base image.
- The build runs on **Cloud Build**, so Docker is not needed locally and you don't run `gcloud builds submit` yourself.
- The image is stored in an **Artifact Registry** repository named `cloud-run-source-deploy` in the deploy region, created automatically if missing.
## When to build yourself
Deploying from source is a convenience feature and allows limited build customization. For full control, build with `gcloud builds submit` and deploy with `gcloud run deploy --image`.
W: gcloud run deploy --source: one command uploads the folder, Cloud Build builds it with buildpacks (no Dockerfile or local Docker needed), the image lands in Artifact Registry, and the service is deployed.
X: B=--image with a folder: --image expects a container image URL; Cloud Run always runs container images and does not treat a local folder as one.
C=Mandatory manual build: building with gcloud builds submit is an option for more control, but source deploy already runs Cloud Build for him.
D=Runs files without an image: the source upload is only the build input; Cloud Run still runs a container image built from it.
T: No Dockerfile, no Docker → gcloud run deploy --source . (buildpacks + Cloud Build + Artifact Registry repo cloud-run-source-deploy).
V: Cloud Run, Cloud Build, Artifact Registry

@ GCP-ACE D2 T2.1 advanced troubleshooting
S: A marketing team must publish a public landing page on Cloud Run. When the engineer runs gcloud run services add-iam-policy-binding with --member=allUsers and --role=roles/run.invoker, the command fails because the organization enforces the domain restricted sharing constraint. What is the recommended way to make the service public?
A: Grant roles/run.invoker to allAuthenticatedUsers instead, because that principal type is exempt from domain restricted sharing
B: Ask for a project-level exception to domain restricted sharing and then retry the allUsers binding on the service again
C: Put an external Application Load Balancer in front of the service, which removes the need for any invoker authorization
D: Disable the Cloud Run Invoker IAM check on the service, for example with gcloud run services update SERVICE --no-invoker-iam-check
K: D
G: ## Two ways to make a Cloud Run service public
By default, Cloud Run checks that every caller has `run.routes.invoke` (the Cloud Run Invoker role). To allow anonymous callers you can:
- **Disable the Invoker IAM check** (recommended): `gcloud run deploy SERVICE --no-invoker-iam-check` for a new service, or `gcloud run services update SERVICE --no-invoker-iam-check` for an existing one. Re-enable with `--invoker-iam-check`. This is the documented choice when the project is subject to the **domain restricted sharing** organization policy.
- **Grant `roles/run.invoker` to `allUsers`** (the `--allow-unauthenticated` flag does this). Domain restricted sharing blocks grants to principals outside the allowed domains, so this fails in such organizations.
## Keeping control
Administrators can stop people from disabling the check with the managed constraint `constraints/run.managed.requireInvokerIam` (not enforced by default). Changing the setting needs `run.services.setIamPolicy`, included in Cloud Run Admin.
W: Disable the Invoker IAM check: Cloud Run then lets every request through without an IAM binding, which is the documented recommended method and works under domain restricted sharing.
X: A=allAuthenticatedUsers: this is also a principal outside the organization's domain, so the constraint blocks it, and it would not let anonymous visitors in anyway.
B=Policy exception: weakening an organization-wide security control for one page is heavier than needed when Cloud Run offers a setting made for this case.
C=Load balancer in front: a load balancer forwards requests to the service, but Cloud Run still enforces the Invoker check, so anonymous requests are still refused.
T: Public Cloud Run service under domain restricted sharing → --no-invoker-iam-check, not an allUsers binding.
V: Cloud Run, IAM, Organization Policy Service

@ GCP-ACE D2 T2.1 applied troubleshooting
S: A Flask app runs fine on a developer's laptop, where it listens on 127.0.0.1:5000. Deployed to Cloud Run with default settings, the revision never becomes ready and the logs say the container failed to listen on the expected port. What should the developer change in the app?
A: Keep 127.0.0.1 but change the port to 443 and add a TLS certificate, since Cloud Run sends requests to containers over HTTPS
B: Listen on 0.0.0.0 on the port given by the PORT environment variable, which is 8080 unless the service sets another port
C: Keep port 5000 and add EXPOSE 5000 to the Dockerfile, because Cloud Run sends traffic to the first port the image exposes
D: Listen on 127.0.0.1:8080, since Cloud Run's front end connects to the container through its loopback interface only
K: B
G: ## The Cloud Run container contract for services
A Cloud Run instance has one **ingress container** that receives requests:
- It must listen on **`0.0.0.0`**, not `127.0.0.1`, on the port requests are sent to.
- The default port is **8080**. You can configure another port; Cloud Run injects it as the **`PORT`** environment variable, so reading `PORT` keeps code and config in step.
- Requests arrive as plain HTTP/1 or gRPC: **TLS is terminated by Cloud Run**, and the container should not implement TLS itself.
## Why the laptop setup fails
`127.0.0.1` accepts connections only from inside the container, and port 5000 is not where Cloud Run sends traffic. The startup check never sees the port open, so the revision fails.
W: 0.0.0.0 on $PORT: binding to all interfaces on the injected PORT (8080 by default) is exactly what the contract requires, so the startup probe succeeds and requests reach Flask.
X: A=Port 443 with TLS: Cloud Run terminates TLS and forwards plain HTTP to the container, and a loopback-only listener is still unreachable.
C=EXPOSE 5000: Cloud Run does not pick the port from EXPOSE; it sends requests to 8080 or the port configured on the service.
D=127.0.0.1:8080: the right port on the wrong interface; the contract says the ingress container should not listen on 127.0.0.1.
T: Cloud Run services: listen on 0.0.0.0:$PORT (default 8080), plain HTTP; Cloud Run handles TLS.
V: Cloud Run

@ GCP-ACE D2 T2.1 applied definition
S: A team is moving a legacy web app into a container for Cloud Run. Which statements about the runtime environment of a Cloud Run service are correct? (Select TWO)
A: Files the app writes to the container's file system live in memory, count against the instance's memory, and are lost when the instance stops
B: TLS is terminated by Cloud Run, so the container receives requests without TLS and doesn't need to manage certificates itself
C: The container can mount an NFS or Filestore share by running a mount command in its startup script, as on a Compute Engine VM
D: Data written to /tmp is kept on a persistent disk shared by all instances of the revision, so instances can exchange files that way
E: The app can use sudo inside the container to install packages at startup, because Cloud Run allows privilege escalation on demand
K: A,B
G: ## What a Cloud Run container can rely on
- **File system**: writable, but it is an **in-memory** file system. Writes use the instance's memory (and can exhaust it), and data does not persist when the instance stops. Instances do not share it.
- **TLS**: terminated by Cloud Run for HTTPS and gRPC; requests reach the container without TLS.
- **Mounts**: the supported way to attach file systems is Cloud Run's managed **volume mounts** in the service configuration. Running a mount process inside the container (NFS, Filestore, SMB/CIFS) is not supported.
- **Privileges**: privilege escalation is disabled; `sudo` and setuid binaries are not supported.
## Design consequence
Keep instances stateless: put durable data in Cloud Storage, a database or a mounted volume, and install packages at image build time, not at startup.
W: A=In-memory file system: the contract says writes use the instance's memory and don't persist when the instance stops, so it suits scratch data only.
B=TLS at Cloud Run: Cloud Run terminates TLS and proxies plain HTTP/1 or gRPC to the container, so the app needs no certificates.
X: C=mount command in startup: mounting NFS, Filestore or SMB from inside the container is unsupported; network file systems are attached through Cloud Run volume mounts.
D=Shared persistent /tmp: /tmp is part of each instance's in-memory file system; nothing is shared between instances or kept after an instance stops.
E=sudo at startup: privilege escalation is disabled in Cloud Run containers, so sudo and setuid binaries don't work; install packages in the image.
T: Cloud Run instances are stateless: in-memory scratch disk, TLS handled by Cloud Run, no privilege escalation, volumes only through managed volume mounts.
V: Cloud Run

@ GCP-ACE D2 T2.1 applied use-case
S: Each night a team must convert 2,000 image files in a Cloud Storage bucket. The work has no HTTP endpoint, each file can be handled independently, and the run should finish faster by working on many files at once. The team already has a container image that converts one slice of the files. What should they deploy?
A: A Cloud Run service with a minimum of 50 instances and a script that sends one HTTP request per file to the service URL
B: A Cloud Run function with an HTTP trigger that loops over all 2,000 files in a single invocation with a raised timeout
C: A Cloud Run job created with --tasks set to split the work, where each task uses CLOUD_RUN_TASK_INDEX to pick its slice
D: A GKE Standard cluster with a CronJob, adding a node pool sized for the peak and keeping it running between nightly runs
K: C
G: ## Services versus jobs on Cloud Run
- A **Cloud Run service** runs code that answers HTTP requests at an endpoint.
- A **Cloud Run job** runs code that does its work and then exits. A job is not a web server and should not listen on a port.
## Parallel tasks
A job can run as one task or as many independent tasks (up to 10,000), executed in parallel by default:
- `--tasks` sets how many tasks each execution runs.
- Each task gets `CLOUD_RUN_TASK_INDEX` (0 to count-1) and `CLOUD_RUN_TASK_COUNT`; your code uses them to choose its share of the data.
- `--parallelism` caps how many run at once; `--max-retries` (default 3) retries failed tasks; `--task-timeout` defaults to 10 minutes.
Run it with `gcloud run jobs execute`, on a schedule (Cloud Scheduler) or from a workflow.
W: Cloud Run job with tasks: a job fits finite work without an endpoint, and splitting it into parallel tasks that read CLOUD_RUN_TASK_INDEX shortens the nightly run with no servers to manage.
X: A=Service with 50 minimum instances: it forces the batch into an HTTP shape and keeps 50 instances allocated all day for a short nightly run.
B=One long function call: a single invocation processes files one after another and gains no parallelism, so it is the slowest choice.
D=GKE CronJob with a standing pool: it works but leaves the team managing a cluster and paying for idle nodes between runs.
T: Run-to-completion batch on Cloud Run → Cloud Run job; parallelize with --tasks and CLOUD_RUN_TASK_INDEX.
V: Cloud Run

@ GCP-ACE D2 T2.1 applied use-case
S: A developer wrote a Python HTTP function named handle_webhook in main.py and wants it deployed as a Cloud Run function in europe-west1, built from the current directory on a Google-managed Python runtime base image. Which command matches the current Cloud Run documentation?
A: gcloud run deploy webhook --image . --function handle_webhook --region europe-west1, with the folder used as the image
B: gcloud run jobs deploy webhook --source . --function handle_webhook --region europe-west1 and a Python base image
C: gcloud run deploy webhook --source . --function handle_webhook --base-image with a Python runtime --region europe-west1

K: C
G: ## Cloud Run functions
**Cloud Run functions** (formerly Cloud Functions) let you deploy a single function from source; it runs as a Cloud Run service. The current docs deploy it with `gcloud run deploy`:
```
gcloud run deploy FUNCTION --source . --function ENTRYPOINT --base-image BASE_IMAGE --region REGION
```
- `--source .`: build from the folder.
- `--function`: the **entry point**, the function or fully-qualified class name in your code that Cloud Run executes.
- `--base-image`: the runtime base image (for example a Python runtime image), which receives automatic security updates.
- `--allow-unauthenticated` only if the function must be public (a webhook from outside); event-triggered functions omit it.
Existing functions created with `gcloud functions deploy` (the Cloud Functions v2 API) are still supported for backward compatibility. After deployment you can attach Eventarc triggers to the function.
W: run deploy with --function and --base-image: it builds from source, names handle_webhook as the entry point, picks the managed Python runtime and deploys to europe-west1, exactly as the docs show.
X: A=--image with a folder: --image takes a container image URL; source-based function deployment uses --source.
B=run jobs deploy: jobs run to completion without serving HTTP, so a webhook function cannot be deployed as a job.
D=Entry point from the service name: Cloud Run does not infer the entry point from the service name; the --function flag (and a base image) is what turns a source deploy into a function.
T: Cloud Run function = gcloud run deploy NAME --source . --function ENTRYPOINT --base-image RUNTIME --region R.

S: A team deployed a Cloud Run function and is creating an Eventarc trigger so the function runs when objects are created in a Cloud Storage bucket. The trigger's service account has the Eventarc Event Receiver role and permission to invoke the function, yet trigger creation fails with a permission error about publishing to Pub/Sub. G: ## How direct Cloud Storage events reach Eventarc
Eventarc Standard receives **direct events** from Cloud Storage (object finalized, deleted, archived, metadata updated). Cloud Storage publishes them through Pub/Sub, so the **Cloud Storage service agent** (a Google-managed identity of the project) must be allowed to publish.
## Roles to set up before creating the trigger
- **Cloud Storage service agent**: `roles/pubsub.publisher` on the project.
- **Trigger service account**: `roles/eventarc.eventReceiver` (so the trigger can receive events) and permission to invoke the target (for authenticated Cloud Run targets, `roles/run.invoker`).
- **Pub/Sub service agent**: `roles/iam.serviceAccountTokenCreator`, only if it was enabled on or before April 8, 2021 (granted by default otherwise).
## Example
```

  --event-filters="bucket=my-bucket" --service-account=SA_EMAIL
```
W: Publisher for the Cloud Storage service agent: the docs require this grant before creating a trigger for direct Cloud Storage events, because that agent publishes the events through Pub/Sub.
X: B=Storage Object Admin for the trigger account: the error is about publishing events, and the trigger account doesn't read objects; the function's own identity reads them if needed.
C=Subscriber for the user: Eventarc creates and manages the transport subscription itself; the failing identity is the one that publishes, not one that subscribes.
D=Cloud Run Admin for the Eventarc agent: Eventarc does not redeploy the function; it delivers events to it, so admin rights on Cloud Run are not needed.
T: Cloud Storage → Eventarc trigger: grant roles/pubsub.publisher to the Cloud Storage service agent; the trigger account needs eventReceiver plus invoke rights.

The trigger shows as active and objects are being uploaded, but the service never receives an event. What is the most likely cause?

G: ## Eventarc triggers from Cloud Audit Logs
Besides direct events, Eventarc can trigger on **Cloud Audit Logs** entries: event type `google.cloud.audit.log.v1.written`, filtered by `serviceName` (for example `storage.googleapis.com`) and `methodName` (for example `storage.objects.create`). ## The log must exist first
An audit log trigger can only fire when the matching audit log entry is written.
- **Admin Activity** logs are always written.

Object reads and writes in Cloud Storage are Data Access operations, so the docs' quickstart enables them first by adding an `auditConfigs` block for `storage.googleapis.com` to the project IAM policy (`gcloud projects get-iam-policy`, edit, `gcloud projects set-iam-policy`); configuring this at project level needs `roles/owner`.
W: Data Access logs not enabled: without them Cloud Storage writes no audit entry for storage.objects.create, so the trigger has nothing to match even though uploads happen.
X: A=Admin Activity only: Eventarc audit log triggers work with Data Access entries too, and the official quickstart uses exactly this storage.objects.create filter.
C=HTTP verb as methodName: methodName holds the API method recorded in the audit log entry, such as storage.objects.create, not an HTTP verb.
D=Public service needed: Eventarc delivers to Cloud Run with the trigger's service account identity, so the service can stay private when that account can invoke it.
T: Audit-log trigger silent on data operations → enable the service's Data Access audit logs first.

@ GCP-ACE D2 T2.1 applied use-case
S: A private Cloud Run service (Invoker IAM check enabled) must process every message published to the Pub/Sub topic orders. The team wants Pub/Sub to call the service directly over HTTPS without making the service public. What should they configure?
A: A pull subscription on orders, with the Cloud Run service polling the subscription in a loop every few seconds for new messages

K: D
G: ## Pub/Sub push to Cloud Run
A **push subscription** makes Pub/Sub send each message as an HTTPS POST to an endpoint. For a private Cloud Run service:
1. Create a service account to represent the subscription, for example `cloud-run-pubsub-invoker`.
2. Grant it **`roles/run.invoker`** on the Cloud Run service.
3. Create the subscription with `--push-endpoint=SERVICE-URL/` and `--push-auth-service-account=SA_EMAIL`. Pub/Sub then attaches a token for that account to each request.
Cloud Run checks that the token is valid and that the account may invoke the service.
## Acknowledgement
The service's HTTP response acknowledges the message: success codes such as 200 or 204 ack it; error codes such as 400 or 500 make Pub/Sub retry.
W: Authenticated push with invoker role: Pub/Sub signs each request as the push service account, and roles/run.invoker on the service lets Cloud Run accept it while staying private.
X: A=Pull subscription with polling: a polling loop needs an always-running instance and doesn't use Cloud Run's request-driven model, which push provides directly.
B=Unauthenticated push: with the Invoker IAM check on, requests without a valid identity token are rejected, and Cloud Run has no setting to trust Pub/Sub IP ranges.
C=Subscriber role on the topic: it lets the account pull messages, but Cloud Run checks the invoker permission on the service, which this account lacks.
T: Pub/Sub → private Cloud Run: push subscription with --push-auth-service-account, and that account gets roles/run.invoker on the service.

@ GCP-ACE D2 T2.1 applied comparison
S: A company has several teams publishing events from apps in different projects. The platform team wants one central bus that collects them, lets consuming teams subscribe through enrollments, can filter on any event attribute and can transform payloads before delivery. Which option fits?
A: Eventarc Standard, with one trigger per producer project that routes each event to every consumer's Cloud Run service
B: Eventarc Advanced, which publishes events to a central bus and uses enrollments with filtering and CEL transformations
C: A Cloud Storage bucket per team, where producers write JSON files and consumers react through object finalized triggers
D: A single Cloud Run function per producer that calls every consumer's HTTPS endpoint in turn and rewrites the payloads
K: B
G: ## Two editions of Eventarc
Both are fully managed, deliver events in CloudEvents format and integrate with Cloud Logging and Cloud Monitoring.
- **Eventarc Standard**: **triggers** filter Google, custom or third-party events by type and specific attributes and route them from **one provider to one destination** (Cloud Run, Cloud Run functions, GKE services, Workflows, HTTP endpoints). Cross-project delivery is not supported; failed events can go to a Pub/Sub dead letter topic.
- **Eventarc Advanced**: events are published to a central **bus**; consumers create **enrollments**. It filters on any attribute, routes **many providers to many destinations**, supports **cross-project** delivery and can **transform** messages with CEL expressions and convert schemas.
## Choosing
Simple "this event → that service" routing → Standard. A shared event backbone across teams and projects with filtering and transformation → Advanced. You can move from Standard to Advanced as needs grow; the data model is the same.
W: Eventarc Advanced: its central bus, enrollments, filtering on any attribute, cross-project delivery and CEL transformations match every requirement.
X: A=Eventarc Standard triggers: Standard routes provider to destination, does not support cross-project delivery, and cannot transform events.
C=Buckets as a message bus: writing files to trigger events adds storage latency and cost and provides no enrollment, attribute filtering or transformation.
D=Fan-out function per producer: hand-written fan-out hard-codes consumers in code and puts retries, filtering and transformation on the teams to build.
T: Simple source-to-target routing → Eventarc Standard; central multi-team bus with enrollments, cross-project delivery and transformation → Eventarc Advanced.
V: Eventarc

@ GCP-ACE D2 T2.1 applied use-case
S: A team runs an event-driven Cloud Run service that must react to messages that another team already publishes to an existing Pub/Sub topic named billing-events. They want delivery managed by Eventarc in CloudEvents format and do not want Eventarc to create a new topic. How should they create the trigger?
A: gcloud eventarc triggers create with --event-filters="type=google.cloud.pubsub.topic.v1.messagePublished" and --transport-topic=billing-events
B: gcloud eventarc triggers create with --event-filters="type=google.cloud.audit.log.v1.written" and serviceName=pubsub.googleapis.com
C: gcloud pubsub subscriptions create with --push-endpoint set to the Eventarc API so Eventarc forwards each message to the service
D: gcloud eventarc triggers create with --event-filters="type=google.cloud.pubsub.topic.v1.messagePublished" and --channel=billing-events
K: A
G: ## Pub/Sub events in Eventarc Standard
A message published to a Pub/Sub topic is a **direct event** of type `google.cloud.pubsub.topic.v1.messagePublished`. Eventarc delivers it to the destination as a CloudEvent over HTTP.
- `--transport-topic=TOPIC` (ID or full name such as `projects/PROJECT_ID/topics/TOPIC_ID`) names the **existing** topic the trigger listens on; it must be in the same project as the trigger. Producers keep publishing where they already do.
- The type filter `messagePublished` is required and can't be changed later; a different event type needs a new trigger.
Eventarc creates and manages the subscription that pushes to the destination; the trigger's `--service-account` needs permission to invoke the Cloud Run service.
## Not to be confused with
- `--channel` names an Eventarc channel (used for events from third-party providers), not a Pub/Sub topic.
- Audit log triggers (`google.cloud.audit.log.v1.written`) fire on API calls recorded in Cloud Audit Logs, which is a different and slower path than message delivery.
W: messagePublished with --transport-topic: this event type represents published messages, and --transport-topic binds the trigger to the existing billing-events topic instead of a new one.
X: B=Audit log trigger on Pub/Sub: audit entries record API calls, not the message payloads, so the service would not receive the billing events themselves.
C=Push subscription to the Eventarc API: Eventarc is not a push endpoint for subscriptions; triggers are created through gcloud eventarc triggers create.
D=--channel: it takes the ID of an Eventarc channel, used for third-party provider events; an existing Pub/Sub topic is set with --transport-topic.
T: Eventarc trigger on an existing Pub/Sub topic → type=google.cloud.pubsub.topic.v1.messagePublished with --transport-topic=TOPIC.
