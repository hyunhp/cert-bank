@ GCP-ACE D2 T2.3 applied use-case
S: A team is building its first production network in a new project that has no VPC network yet. It needs one subnet in us-central1 using 10.20.0.0/20 and one subnet in europe-west1 using 10.30.0.0/20, and no subnets in any other region, now or when Google adds new regions. Which approach meets these requirements?
A: Create one auto mode network, then add the two subnets with the planned ranges, because auto mode only creates subnets in the regions where you add subnets yourself
B: Create two VPC networks, one per region, because a VPC network is a regional resource and each network can hold subnets from only one Google Cloud region
C: Create one custom mode network with gcloud compute networks create --subnet-mode=custom, then create each subnet with --network, --range and --region
D: Create one custom mode network, then create each subnet with --zone=us-central1-a and --zone=europe-west1-b, because subnets belong to a single zone
K: C
G: ## VPC networks are global, subnets are regional
A Google Cloud **VPC network** is a global resource: one network, with its routes and firewall rules, can hold subnets in any number of regions. Each **subnet** is a regional resource with its own primary IPv4 range, and VMs in any zone of that region can use it.
## Auto mode versus custom mode
- **Auto mode**: Google creates one subnet in every region from predefined ranges inside `10.128.0.0/9`, and adds a subnet automatically whenever a new region launches. The `default` network of a new project is an auto mode network.
- **Custom mode**: no subnets are created for you. You choose the regions and ranges. Google recommends custom mode for production. You can convert auto mode to custom mode, but never back.
## Commands
```
gcloud compute networks create prod-net --subnet-mode=custom
gcloud compute networks subnets create prod-usc1 --network=prod-net --range=10.20.0.0/20 --region=us-central1
gcloud compute networks subnets create prod-euw1 --network=prod-net --range=10.30.0.0/20 --region=europe-west1
```
W: Custom mode network plus two regional subnets: custom mode starts with no subnets, so the team creates exactly the two subnets it planned, with its own ranges, and nothing appears in other regions when Google adds them.
X: A=Auto mode network: auto mode immediately creates a subnet in every region from `10.128.0.0/9` and keeps adding subnets for new regions, which is exactly what the team wants to avoid.
B=One network per region: VPC networks are global, so a single network can hold subnets in both regions; splitting them would also need peering or VPN just to let the two halves talk.
D=Zonal subnets: subnets are regional, not zonal; the subnets create command takes --region, and VMs in every zone of that region can use the subnet.
T: Choose your own regions and ranges with no automatic subnets → one global custom mode VPC network plus regional subnets.
V: VPC

@ GCP-ACE D2 T2.3 applied use-case
S: A central network team keeps all subnets, routes and firewall rules in one project. Three departments each run VMs in their own project of the same organization. Department A must be able to create VMs only in subnet-a, while the network team keeps sole control over network changes. Which two actions should be taken? (Select TWO)
A: Peer each department project's own VPC network with the network team's VPC network, and let each department create its own subnets and firewall rules
B: Have a Shared VPC Admin enable the network team's project as a host project and attach the three department projects to it as service projects
C: Grant Department A's administrators the Compute Network User role (roles/compute.networkUser) on subnet-a only, not on the whole host project
D: Grant Department A's administrators the Compute Network Admin role (roles/compute.networkAdmin) on the host project so they can pick subnet-a
E: Grant Department A's administrators the Compute Network User role (roles/compute.networkUser) on the whole host project, including future subnets
K: B,C
G: ## How Shared VPC splits the work
**Shared VPC** lets one **host project** own the VPC network while other projects in the same organization, the **service projects**, run resources in its subnets.
- A **Shared VPC Admin** (`roles/compute.xpnAdmin`) enables the host project and attaches service projects.
- Service Project Admins get **Compute Network User** (`roles/compute.networkUser`) either on the whole host project (all current and future subnets) or only on selected subnets. They create VMs in their own project but cannot change the network.
- Network Admins (`roles/compute.networkAdmin`) and Security Admins (`roles/compute.securityAdmin`) in the host project manage the network and the firewall rules.
## Billing stays with the departments
Resources are billed to the service project they live in, so each department still sees its own VM costs.
W: B=Host and service projects: enabling a host project and attaching the department projects lets their VMs use the central network while subnets, routes and firewall rules stay in the network team's project.
C=Subnet-level Network User: a grant of `roles/compute.networkUser` on subnet-a lets Department A create VMs in that subnet and nothing else, without any right to change the network.
X: A=VPC Network Peering per department: each department would own a separate network with its own subnets and firewall rules, which removes the central control the network team needs.
D=Network Admin on the host project: Compute Network Admin lets Department A change networks, subnets and routes, so the network team would lose sole control.
E=Network User on the whole host project: a project-level grant covers every subnet in the host project, including subnets added later, not only subnet-a.
T: Central network, departments deploy into it → Shared VPC; limit a team to some subnets by granting Compute Network User on those subnets only.
V: VPC, Shared VPC, IAM

@ GCP-ACE D2 T2.3 advanced troubleshooting
S: A Shared VPC Admin attached an existing project to a host project as a service project and granted its admins Compute Network User on a shared subnet. A week later the project's existing VMs still use the project's own local VPC network, not the shared subnet. What should the team do to move the workload onto the shared subnet?
A: Detach the project from the host project and attach it again, because the attachment only migrates existing VMs to shared subnets when it is first created
B: Grant Compute Network User to the VMs' attached service account as well, because existing VMs move to the shared subnet only when their identity holds the role
C: Peer the project's local VPC network with the Shared VPC network, because peering is the step that moves existing VM interfaces into the shared subnets
D: Create new VMs (for example from an updated instance template) that select the shared subnet, because existing VMs cannot be reconfigured to use it
K: D
G: ## What attaching a service project does
Attaching a project to a Shared VPC host project only **allows** its resources to use shared subnets. It does not change anything that already exists:
- Existing resources keep using whatever network they were created in.
- To use a Shared VPC network, a Service Project Admin creates a new eligible resource and selects a shared subnet.
- The docs give the example directly: an existing instance in a service project cannot be reconfigured to use a Shared VPC network; a new instance can be created in an available shared subnet.
## Doing it with little disruption
For a managed instance group, create a new instance template whose network interface points at the shared subnet (`projects/HOST_PROJECT/regions/REGION/subnetworks/SUBNET`) and roll the group to it. Using a Shared VPC network is optional, so the old local network keeps working until it is removed.
W: Recreate the VMs on the shared subnet: existing VMs cannot switch to a Shared VPC network, so new VMs that select the shared subnet, for example through a new instance template, are how the workload moves.
X: A=Detach and reattach: the attachment never migrates existing resources, whether it is new or old; reattaching only repeats the same permission step.
B=Network User for the service account: the role lets principals create resources in the shared subnet; granting it to a VM's identity does not move an existing network interface anywhere.
C=Peering with the host network: peering exchanges routes between two separate networks; it does not move VM interfaces into the host project's subnets and is not part of Shared VPC.
T: Attaching a service project grants access only; existing VMs stay where they are, so create new resources on the shared subnet.
V: VPC, Shared VPC, Compute Engine

@ GCP-ACE D2 T2.3 advanced troubleshooting
S: A hub VPC network is peered with spoke-a and with spoke-b, and all three use non-overlapping ranges. VMs in each spoke can reach VMs in the hub, but VMs in spoke-a cannot reach VMs in spoke-b. The team wants direct private connectivity between the two spokes. What should the team do?
A: Enable --export-custom-routes on both hub peerings so that the hub re-exports the subnet routes it learned from one spoke to the other spoke
B: Create a VPC Network Peering connection between spoke-a and spoke-b, configured in both networks so that its state becomes ACTIVE
C: Create an ingress firewall rule in the hub network that allows traffic from the spoke-a range to the spoke-b range on all protocols and ports
D: Change the dynamic routing mode of the hub network to global so that routes learned from each spoke are advertised to the other spoke
K: B
G: ## VPC Network Peering is not transitive
Peering connects exactly two VPC networks. Each side exports its routes and the other side imports them, but a network never passes on routes that it imported from a third network. With `hub ↔ spoke-a` and `hub ↔ spoke-b`, the spokes know the hub's subnets and the hub knows both spokes' subnets, yet spoke-a has no route to spoke-b.
## Creating a peering
A peering works only after **each** network has a peering configuration that references the other:
```
gcloud compute networks peerings create a-to-b --network=spoke-a --peer-network=spoke-b
gcloud compute networks peerings create b-to-a --network=spoke-b --peer-network=spoke-a
```
The state then changes to `ACTIVE` in both networks. Subnet routes with private ranges are always exchanged; custom (static and dynamic) routes are exchanged only with `--export-custom-routes` and `--import-custom-routes`.
Remember that peering never shares firewall rules: each spoke still needs ingress allow rules for the other spoke's range.
W: Peer the two spokes directly: because peering is not transitive, the only way for spoke-a and spoke-b to exchange routes through peering is a peering between them, created on both sides.
X: A=Export custom routes on the hub: those flags control static and dynamic routes; the hub still never re-exports routes it imported over peering, so the spokes would still have no route to each other.
C=Firewall rule in the hub: firewall rules filter traffic that has a route; they do not create routes, and a rule in the hub does not apply to VMs in either spoke.
D=Global dynamic routing mode: the routing mode controls how Cloud Router learned routes spread across regions of one network; it does not make peering transitive.
T: VPC Network Peering is one-to-one and non-transitive; spokes that must talk need their own peering (configured on both sides).
V: VPC, VPC Network Peering

@ GCP-ACE D2 T2.3 applied definition
S: A company plans to connect its analytics VPC network to a partner's VPC network with VPC Network Peering. Which statements about VPC Network Peering are correct? (Select TWO)
A: The two VPC networks can be in different projects and even in different organizations, and they remain administratively separate after peering
B: The VPC firewall rules and network firewall policies of each network are copied into the peered network, so both share one rule set automatically
C: Only one side needs to create the peering; the other network accepts it automatically and the connection becomes ACTIVE in both networks right away
D: Google Cloud checks for overlapping subnet ranges, and the peering fails if a subnet range in one network matches or contains a range in the other
E: When the partner network is itself peered with a third network, the analytics network can also reach the third network through the partner network
K: A,D
G: ## What peering connects
VPC Network Peering connects two VPC networks so their resources communicate with internal IP addresses. The networks can be in the same project, in different projects of one organization, or in projects of **different organizations**. They stay **administratively separate**: only routes are exchanged.
## Rules to remember
- **Both sides configure it**: the connection works after each network has a peering configuration that references the other; then the state is `ACTIVE` on both sides.
- **No overlapping subnets**: no subnet range can match, contain or fit inside a subnet range of the peered network. Google Cloud checks this when you create the peering and rejects the peering on a conflict.
- **No transitive routing**: if A peers with B and B peers with C, A and C are not connected.
- **Firewall stays local**: peering does not exchange VPC firewall rules or firewall policies. Each side writes its own ingress allow rules, using the peer's ranges as sources.
W: A=Different projects and organizations: peered networks can live in projects of different organizations, and each side keeps managing its own network.
D=Overlap check: Google Cloud checks subnet ranges at peering time and fails the peering when a range matches, contains or fits within a range of the other network.
X: B=Shared firewall rules: peering exchanges only routes; firewall rules and policies stay in their own network, so each side must allow the other's ranges itself.
C=One-sided setup: the connection becomes active only after both networks have a peering configuration that references the other.
E=Transitive reach: peering is not transitive, so a third network peered with the partner stays unreachable from the analytics network.
T: Peering: works across projects and organizations, needs config on both sides, non-overlapping ranges, no transitive routing and no shared firewall rules.
V: VPC, VPC Network Peering

@ GCP-ACE D2 T2.3 advanced tradeoff
S: Frontend VMs run as frontend-sa and backend VMs run as backend-sa, both in one VPC network. Developers hold Compute Instance Admin and often edit VMs, including their network tags. Security wants a VPC firewall rule that allows TCP 8443 only from frontend VMs to backend VMs, which developers cannot widen by editing VMs. How should the rule be defined?
A: An ingress allow rule for tcp:8443 with target service account backend-sa and source service account frontend-sa, both created in the rule's project
B: An ingress allow rule for tcp:8443 with target network tag backend and source network tag frontend, applied to the VMs through their instance templates
C: An ingress allow rule for tcp:8443 with target service account backend-sa and source network tag frontend, so that only the target side depends on identity
D: An ingress allow rule for tcp:8443 with target network tag backend and the frontend subnet's IP range as the source, to avoid depending on any VM metadata
K: A
G: ## Two ways to pick VMs in a VPC firewall rule
VPC firewall rules select targets (and, for ingress rules, sources) by **network tags** or by **service accounts**:
- A **network tag** is a free-form string. Anyone who can edit the VM, such as a principal with Compute Instance Admin, can add or remove tags while the VM runs, which changes the rules that apply to it.
- A **service account** is the VM's identity. A VM has one, changing it requires stopping the VM, and attaching it requires the Service Account User role on that account, which you control through IAM.
The docs therefore recommend service accounts when you need **strict control** over which VMs a rule applies to.
## Combinations that are not allowed
You cannot use target service accounts and target tags in one rule, and with target service accounts the source cannot be network tags (and with target tags the source cannot be service accounts). The service accounts should exist in the rule's project, or the rule is not enforced.
```
gcloud compute firewall-rules create allow-fe-be --network=prod-net --direction=INGRESS --action=ALLOW --rules=tcp:8443 \
  --source-service-accounts=frontend-sa@PROJECT.iam.gserviceaccount.com --target-service-accounts=backend-sa@PROJECT.iam.gserviceaccount.com
```
W: Service accounts on both sides: identities cannot be changed by simply editing tags, so developers cannot pull extra VMs into the rule as sources or targets unless IAM lets them use those service accounts.
X: B=Tags on both sides: any Compute Instance Admin can add the backend or frontend tag to another VM while it runs, which silently widens the rule.
C=Target service account with source tag: this combination is invalid for ingress rules; a rule with target service accounts cannot use source network tags.
D=Target tag with subnet range source: developers can still add the backend tag to other VMs, and the subnet range admits every VM in that subnet, not only frontend VMs.
T: Need strict, IAM-controlled firewall targeting → target and source service accounts instead of network tags.
V: Cloud NGFW, VPC, IAM

@ GCP-ACE D2 T2.3 advanced use-case
S: A platform team is replacing VPC firewall rules with a global network firewall policy. Application teams must decide which of their own VMs receive the policy's allow-db-access rule, but must not be able to edit any firewall rule. Which design meets this?
A: Use network tags as rule targets in the global network firewall policy, and let the application teams add the db-client network tag to their VMs as needed
B: Create a secure tag key with purpose GCE_FIREWALL for the VPC network, use its value as the rule target, and grant application teams the Tag User role
C: Create a secure tag key with purpose GCE_FIREWALL for the VPC network, use its value as the rule target, and grant application teams Compute Security Admin
D: Use network tags as rule targets in a hierarchical firewall policy on the folder, and grant application teams Compute Instance Admin on their own projects
K: B
G: ## Secure tags versus network tags
Cloud NGFW supports two kinds of tags in firewall rules:
- **Network tags**: plain strings on a VM with no access control. They work only in **VPC firewall rules**.
- **Secure tags**: IAM-governed tags created in Resource Manager as a tag key with tag values. They work in **hierarchical, global network and regional network firewall policies**, not in VPC firewall rules.
## Setting up secure tags for firewalls
1. A Tag Administrator (`roles/resourcemanager.tagAdmin`) creates a tag key with `purpose` `GCE_FIREWALL` and `purpose-data` naming a VPC network (or the whole organization), plus tag values.
2. A Compute Security Admin writes policy rules that use those values as source or target secure tags.
3. Principals with **Tag User** (`roles/resourcemanager.tagUser`) bind tag values to VMs.
The docs describe exactly this split: operations teams with Tag User control which rules apply to their VMs without being able to change the rules.
W: Secure tag plus Tag User: rules in network firewall policies target secure tag values, and Tag User lets application teams bind the value to their VMs while the rules themselves stay editable only by Security Admins.
X: A=Network tags in a network firewall policy: network firewall policies do not support network tags at all; they use secure tags only.
C=Compute Security Admin: that role can add, change and delete policy rules, which breaks the requirement that application teams cannot edit firewall rules.
D=Network tags in a hierarchical policy: hierarchical policies also cannot use network tags, and Compute Instance Admin does not grant permission to bind secure tags.
T: Firewall policies select VMs with IAM-governed secure tags (purpose GCE_FIREWALL); Tag User binds them, Security Admin writes the rules.
V: Cloud NGFW, Resource Manager, IAM

@ GCP-ACE D2 T2.3 advanced comparison
S: The security team must block inbound RDP (TCP 3389) from the internet to every VM in all projects under the Production folder. Project owners must not be able to override the block with their own firewall rules, but they should still decide all other traffic. What should the security team create?
A: A VPC firewall rule with priority 0 that denies tcp:3389 from 0.0.0.0/0 in every VPC network, created and kept in place by a scheduled script
B: A global network firewall policy with a deny rule for tcp:3389 from 0.0.0.0/0, associated directly with the Production folder for all projects
C: A hierarchical firewall policy with a deny rule for tcp:3389 from 0.0.0.0/0, associated with the Production folder, leaving other traffic to lower levels
D: A regional network firewall policy in each region with a deny rule for tcp:3389, associated with every project in the folder through its project ID
K: C
G: ## Where each firewall construct lives
- **Hierarchical firewall policies** are created and associated at the **organization or a folder**, never at a project. Every VPC network below inherits the rules.
- **Global and regional network firewall policies** are created in a project and associated with VPC networks in that same project.
- **VPC firewall rules** belong to one VPC network.
## Evaluation order
Rules from the organization's policy are evaluated first, then those of folders, and only then network-level rules. A hierarchical rule can `allow`, `deny`, or `goto_next`, which hands the decision to the next level. Lower-level rules **cannot override** a higher-level allow or deny, so a folder-level deny is final. Traffic that matches no hierarchical rule falls through to lower levels, where project teams keep control.
W: Hierarchical policy on the folder: it applies to every VM in every project under Production, a deny rule there cannot be overridden by project rules, and all other traffic falls through to the projects' own policies and VPC firewall rules.
X: A=Priority 0 VPC rule in each network: project owners can delete or change rules in their own networks, so a script only restores the block after a gap; it is not enforced from above.
B=Global network policy on a folder: global network firewall policies attach to VPC networks in their own project; they cannot be associated with a folder.
D=Regional network policies per project: regional policies attach to a region of a VPC network in their own project, and project teams with Security Admin could change them.
T: Org-wide or folder-wide rules that projects cannot override → hierarchical firewall policy (allow, deny or goto_next) on the organization or folder.
V: Cloud NGFW, Resource Manager

@ GCP-ACE D2 T2.3 applied use-case
S: A small company must connect a branch office to its VPC network this week. Expected traffic is a few hundred Mbps, the office has an ordinary internet connection, traffic must be encrypted, and the company wants a 99.99% availability SLA for the connection. Which option should it choose?
A: Dedicated Interconnect with two connections in the same metropolitan area, because it is the only option that can carry a few hundred Mbps with an SLA
B: Partner Interconnect through a supported service provider, because its VLAN attachments add IPsec encryption to all traffic by default
C: HA VPN with two tunnels from both gateway interfaces to the office's peer VPN gateway, using Cloud Router and BGP for dynamic routes
D: Classic VPN with a single tunnel and static routes, because a single tunnel already carries the 99.99% SLA when the peer gateway is redundant
K: C
G: ## Hybrid connectivity options
- **Cloud VPN** builds IPsec tunnels over the internet. Google recommends it for lower cost, lower bandwidth needs, or experiments with migration. **HA VPN** gateways have two interfaces with their own external IP addresses; with tunnels on both interfaces in a supported topology they offer a **99.99%** SLA. Routing uses **Cloud Router** with BGP.
- **Dedicated Interconnect** is a direct physical link to Google in a colocation facility, on 10-Gbps, 100-Gbps or 400-Gbps circuits; you must install routing equipment there.
- **Partner Interconnect** reaches Google through a supported service provider, with VLAN attachments from 50 Mbps to 50 Gbps.
Interconnect traffic does not cross the public internet, but it is not IPsec-encrypted by itself; for that you deploy HA VPN over Cloud Interconnect.
## Reading the scenario
A few hundred Mbps, an ordinary internet line, a one-week deadline and mandatory encryption all point to HA VPN.
W: HA VPN with two tunnels: IPsec encrypts the traffic over the existing internet line, it can be set up in days, the bandwidth fits, and two tunnels from both interfaces give the 99.99% SLA.
X: A=Dedicated Interconnect: it needs routing equipment in a Google colocation facility and 10-Gbps or larger circuits, which a branch office on an ordinary internet line cannot provide this week, and it adds no IPsec encryption.
B=Partner Interconnect: provisioning depends on a service provider, and VLAN attachments do not encrypt traffic by default; encryption needs HA VPN over Cloud Interconnect.
D=Classic VPN single tunnel: a single tunnel has no redundant path, and the 99.99% SLA comes from HA VPN topologies, not from a Classic VPN tunnel.
T: Encrypted, quick, modest bandwidth over the internet → HA VPN (two tunnels, Cloud Router, 99.99% SLA); high bandwidth private links → Cloud Interconnect.
V: Cloud VPN, Cloud Router, Cloud Interconnect

S: A company needs about 5 Gbps of private connectivity from its data center to Google Cloud, and traffic must not cross the public internet. A: Dedicated Interconnect, ordering a 10-Gbps circuit and installing a router in the nearest Google colocation facility to terminate the cross connect
B: HA VPN with several tunnels in an active/active configuration, because enough tunnels together can carry 5 Gbps over the data center's internet link

Both keep traffic off the public internet:

@ GCP-ACE D2 T2.3 applied use-case
S: A game studio runs its multiplayer servers on Compute Engine VMs in one region. Players connect from the internet over UDP, and the servers must see each player's real source IP address for anti-cheat checks. Which load balancer should the team deploy in front of the VMs?
A: A global external Application Load Balancer, because its single anycast IP address brings players to the nearest Google Front End
B: A regional external passthrough Network Load Balancer, because it forwards UDP packets to the VMs with the client source address unchanged
C: A global external proxy Network Load Balancer, because it terminates player connections close to them and supports UDP game traffic
D: An internal passthrough Network Load Balancer, because passthrough load balancers are the only ones that keep the original client IP address
K: B
G: ## Three families of load balancers
Start from the traffic type:
- **Application Load Balancers**: HTTP and HTTPS, proxy-based, with features such as URL maps.
- **Proxy Network Load Balancers**: TCP (optionally with SSL offload). They terminate the client connection and open a new one to the backend.
- **Passthrough Network Load Balancers**: TCP, UDP, ESP, GRE, ICMP and ICMPv6. They do not terminate connections: backends receive packets with the original source and destination, and reply directly to clients (direct server return).
## Then external versus internal
External load balancers take traffic from the internet; internal ones serve clients in the VPC network or networks connected to it by peering, Cloud VPN or Cloud Interconnect.
## The scenario
UDP plus "see the real client IP" means passthrough, and internet players mean external. With backends in one region, the regional external passthrough Network Load Balancer fits.
W: Regional external passthrough NLB: it accepts UDP from the internet and hands packets to the VMs with the client address intact, so anti-cheat logic sees each player's real IP.
X: A=Global external Application Load Balancer: it handles only HTTP and HTTPS, so UDP game traffic cannot use it at all.
C=Global external proxy NLB: proxy Network Load Balancers handle TCP, not UDP, and as proxies they terminate client connections, so backends do not see packets from the client's address.
D=Internal passthrough NLB: it preserves source IPs, but it serves clients inside the VPC network or connected networks, not players on the internet.

@ GCP-ACE D2 T2.3 advanced tradeoff
S: A retailer's users are all in one country near its Google Cloud region. To cut internet egress costs, the team wants new VM external IPs and new load balancers in the project to use Standard Tier by default, and accepts lower performance. Which statements about Network Service Tiers are correct? (Select TWO)
A: Running gcloud compute project-info update --default-network-tier=STANDARD changes the default for new resources but does not change the tier of existing ones
B: The tier is a property of each VPC network, so the team should create a new VPC network in Standard Tier and recreate every VM inside that network
C: A global external Application Load Balancer can run in Standard Tier, so the team can keep its single anycast IP while paying the lower Standard Tier rates

E: Standard Tier traffic is carried on Google's backbone to the edge point of presence closest to each user, exactly like Premium Tier but at lower cost

G: ## Premium Tier and Standard Tier
**Network Service Tiers** decide how internet traffic reaches your resources:
- **Premium Tier** (the default): traffic enters and leaves Google's global backbone at a point of presence as close as possible to the user. It supports every networking feature, including global external IP addresses.
- **Standard Tier**: traffic enters and leaves Google's network near the **region of the IP address** and travels over regular peering and transit networks the rest of the way. It costs less and supports a foundational set of features with **regional** external IP addresses, such as regional external Application Load Balancers, regional external passthrough Network Load Balancers, VMs and Cloud NAT.
## Where the tier is set
You choose the tier per resource (for example a VM's external IP or a load balancer's IP) or set a **project default**:
```
gcloud compute project-info update --default-network-tier=STANDARD
```
The default applies to new resources created without an explicit tier; existing resources keep their tier.
## Premium-only features
The global external Application Load Balancer and global external proxy Network Load Balancer need global IPs and work only in Premium Tier; Cloud CDN is always Premium Tier; Cloud VPN gateways need Premium Tier IP addresses.
W: A=Project default tier: the project-info update command sets the tier that new eligible resources get when none is specified, and leaves existing resources unchanged.
D=Regional routing: Standard Tier hands traffic to peering or transit networks at points of presence close to the region of the IP address, which suits users who are near that region.
X: B=Tier per VPC network: tiers are chosen per resource or as a project default, not per VPC network, so no new network or VM rebuild is needed.
C=Global ALB in Standard Tier: global external Application Load Balancers need a global IP address and run only in Premium Tier; Standard Tier needs regional load balancers.
E=Backbone to the nearest PoP: that is the Premium Tier behavior; Standard Tier leaves Google's network near the resource's region instead.
T: Standard Tier = regional entry and exit, lower cost, regional resources only; set it per resource or as the project default for new resources.
V: Network Service Tiers, Cloud Load Balancing

@ GCP-ACE D2 T2.4 applied troubleshooting
S: Three engineers run terraform apply for the same Google Cloud environment from their own laptops. Each laptop keeps its own terraform.tfstate, and runs keep trying to recreate resources that a colleague already created. What should the team change?
A: Commit terraform.tfstate to the Git repository and pull before each run, so every engineer works from the latest local copy of the state file
B: Move the configuration to Cloud Deployment Manager, which keeps deployment state on the Google Cloud side and needs no state file at all
C: Configure a gcs backend that stores the state in a Cloud Storage bucket with Object Versioning, and migrate the existing state into it
D: Run terraform plan with the -refresh=false option before each apply, so that Terraform stops comparing the configuration with the real resources
K: C
G: ## What Terraform state is
Terraform describes the desired end state in configuration files. `terraform plan` shows what will change; `terraform apply` calls the Google Cloud APIs and records the result in a **state file**, a JSON mapping from resources in the configuration to real resources. On the next apply Terraform compares configuration, state and reality to decide what to create, update or leave alone.
## Why local state breaks teams
By default the state lives in a local `terraform.tfstate`. When several people run Terraform, each machine has its own idea of what exists, so one engineer's run tries to recreate what another already built.
## Remote state in Cloud Storage
Google's docs show storing state in a **Cloud Storage bucket** through Terraform's `gcs` backend:
```
terraform {
  backend "gcs" {
    bucket = "my-tf-state"
    prefix = "prod"
  }
}
```
Enable **Object Versioning** on the bucket to keep earlier state versions, then run `terraform init` to migrate the local state into the bucket.
W: Remote state in Cloud Storage: every engineer reads and writes the same state in the bucket, so Terraform knows what already exists, and Object Versioning keeps a history of earlier states.
X: A=State in Git: copies still diverge between pulls, two people can apply from stale copies at once, and the state file can hold sensitive values that do not belong in a repository.
B=Cloud Deployment Manager: it reached end of support on 2026-03-31; Google points to Infrastructure Manager or Terraform instead.
D=Plan without refresh: skipping the refresh only hides drift between state and reality; each laptop still has a different state file.
T: Teams share Terraform state remotely, on Google Cloud in a Cloud Storage bucket via the gcs backend with Object Versioning.
V: Terraform, Cloud Storage

- `us-west1-docker.pkg.dev/my-project/my-repo/charts`
Helm authenticates to Artifact Registry and pushes with `helm push` to an `oci://` address.
