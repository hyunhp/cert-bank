@ GCP-ACE D2 T2.1 applied use-case
S: A logistics company is moving a legacy inventory application to Google Cloud. The application runs on a commercial Linux distribution, loads a vendor-supplied kernel driver at boot, and the vendor supports it only when it runs unmodified on a full operating system. The team wants to change as little as possible. Where should the team run the application?
A: On Compute Engine VMs built from an image of that distribution, so the team controls the operating system, kernel modules and installed packages
B: On Cloud Run, after packaging the application and its kernel driver into a container image that loads the driver when each instance starts
C: On a GKE Autopilot cluster, running the application as a Deployment with the vendor driver installed through an init container in each Pod
D: On Cloud Run functions, splitting the application into event-driven functions that call the vendor driver through a shared library at runtime
K: A
G: ## Matching the workload to the compute service
Google Cloud offers several places to run code, and they differ mainly in how much of the stack you control:
- **Compute Engine**: virtual machines. You pick the image, the machine type and the disks, and you control the whole guest operating system, including kernel modules, drivers and system services. This is the natural fit for lift-and-shift moves of software that expects a full OS.
- **GKE**: managed Kubernetes for containerized workloads. Containers share the node's kernel; in Autopilot mode Google manages the nodes and restricts privileged workloads.
- **Cloud Run** and **Cloud Run functions**: serverless containers and functions. Google runs the infrastructure; your code sees a sandboxed container, not a kernel you can modify.
- **Agent Runtime** (Gemini Enterprise Agent Platform): a managed runtime for AI agents.
## Reading the scenario
Two phrases decide it: "loads a vendor-supplied kernel driver" and "supported only when it runs unmodified on a full operating system". Anything container-based or serverless changes how the app is packaged and denies kernel access.
W: Compute Engine VMs: a VM gives the team full control of the guest OS, so the vendor driver loads at boot exactly as on premises and the application runs unmodified, which is what a minimal-change migration needs.
X: B=Cloud Run container: Cloud Run instances run in a managed sandbox; a container cannot load its own kernel modules, and repackaging also breaks the vendor's "unmodified" support condition.
C=GKE Autopilot with init container: containers share the node kernel and Autopilot does not let workloads modify the nodes, so a custom kernel driver cannot be installed this way; it is also a full re-platforming.
D=Cloud Run functions: rewriting the app as functions is the opposite of minimal change, and functions have no access to kernel drivers either.
T: Needs control of the OS or kernel, or must run unmodified → Compute Engine; containers and serverless trade that control for less management.
V: Compute Engine, Cloud Run, GKE

@ GCP-ACE D2 T2.1 applied use-case
S: A small team has a stateless REST API packaged as a container image. It receives traffic only during office hours and none at night or on weekends. The team does not want to manage VMs or clusters and does not want to pay for compute while the API is idle. Which compute option should the team choose?
A: A regional managed instance group of small VMs running the container, autoscaled on average CPU utilization with a minimum of zero
B: A GKE Standard cluster with the cluster autoscaler enabled on its node pool, running the image as a Deployment behind a Service
C: A Cloud Run service deployed from the image, letting it scale to zero instances when no requests arrive
D: An Agent Runtime deployment on Gemini Enterprise Agent Platform, which runs the image in a fully managed environment
K: C
G: ## Serverless containers and scale to zero
A **Cloud Run service** runs stateless containers that respond to HTTP requests at a stable endpoint. Cloud Run adds instances as requests arrive and removes them as traffic drops. When no requests arrive, even the last instance is removed: this is called **scale to zero**. Without minimum instances configured, an unused service costs nothing for CPU and memory.
## Why the others need more work
- A **managed instance group (MIG)** runs VMs that the team patches and sizes. An autoscaler based on average CPU utilization cannot scale a MIG in to zero instances.
- **GKE** runs containers on clusters: the team still owns cluster and node pool configuration (in Standard mode) and pays for nodes while they run.
- **Agent Runtime** is built to deploy and scale AI agents, not general REST APIs.
W: Cloud Run service: it runs the existing container without servers or clusters to manage, autoscales with request load and scales to zero overnight, so idle hours cost nothing for compute.
X: A=CPU-autoscaled MIG: the team would manage VM images and patching, and a MIG that scales on average CPU utilization cannot scale in to zero instances, so at least one VM always runs.
B=GKE Standard with cluster autoscaler: this is exactly the cluster management the team wants to avoid, and node VMs are billed whenever they run.
D=Agent Runtime: it is the managed runtime for AI agents built for Gemini Enterprise Agent Platform, not a general hosting service for an arbitrary REST container.
T: Stateless container + no infrastructure to manage + nothing to pay when idle → Cloud Run service (scale to zero).
V: Cloud Run, Compute Engine, GKE

@ GCP-ACE D2 T2.1 applied comparison
S: A developer has built a customer-support AI agent and now needs to run it in production. The team wants a fully managed environment that deploys and scales the agent, keeps conversation state across turns, can store long-term memories about users, and provides tracing and logging, without the team operating servers. Which option fits best?
A: Package the agent as a container and run it on a Compute Engine managed instance group, storing session state in a Cloud SQL database the team manages
B: Deploy the agent to Agent Runtime on Gemini Enterprise Agent Platform and use Agent Platform Sessions and Memory Bank for state
C: Split each agent tool into a separate Cloud Run function and keep the conversation history in the instance memory of each function
D: Run the agent on a GKE Standard cluster with a StatefulSet that stores each conversation on the Persistent Disk of its Pod
K: B
G: ## Where AI agents run
Gemini Enterprise Agent Platform (formerly Vertex AI) includes **Agent Runtime** (formerly Vertex AI Agent Engine): a fully managed runtime that deploys, operates and scales agents without infrastructure for the team to manage, with built-in observability (Cloud Trace, Cloud Logging, monitoring).
Around the runtime the platform adds:
- **Agent Platform Sessions**: keep the state of continuous conversations.
- **Memory Bank**: stores and retrieves persistent, long-term memories, so the agent can personalize answers.
## The general rule
You *can* host an agent on any compute service (Compute Engine, GKE, Cloud Run), but then you build session storage, memory and tracing yourself. When the requirement says "fully managed agent runtime with sessions and memory", Agent Runtime is the decision.
W: Agent Runtime: it is the managed runtime made for agents, and Sessions plus Memory Bank give conversation state and long-term memory out of the box, with tracing and logging built in.
X: A=Managed instance group plus Cloud SQL: it works, but the team now operates VMs, images and a database for session state, which contradicts "without the team operating servers".
C=Cloud Run functions with in-memory history: function instances are stateless and can be removed at any time, so conversation history kept in instance memory is lost between requests.
D=GKE StatefulSet: this means operating a cluster and building session storage yourself, and per-Pod disks give no long-term memory search across users.
T: Production AI agent that needs a managed runtime, sessions and memory → Agent Runtime on Gemini Enterprise Agent Platform.
V: Gemini Enterprise Agent Platform, Agent Runtime

@ GCP-ACE D2 T2.1 applied troubleshooting
S: An engineer created a reporting VM with a script copied from an old wiki that included --maintenance-policy=TERMINATE and --no-restart-on-failure. Last night Google performed host maintenance, and this morning the VM is in the TERMINATED state and nobody restarted it. The VM uses a general-purpose machine type with no GPUs. How should the engineer change the VM's host maintenance policy?
A: Enable deletion protection on the VM so that Compute Engine can no longer stop or terminate it during host maintenance events
B: Recreate the VM as a Spot VM so that Compute Engine moves it to another host automatically whenever maintenance is scheduled
C: Add a snapshot schedule to the boot disk so that the VM is recreated from the latest snapshot after each maintenance event
D: Set the maintenance behavior to migrate (live migration) and turn automatic restart back on so host errors also restart the VM
K: D
G: ## The host maintenance policy
Every VM has a host maintenance policy with two main settings:
- **Maintenance behavior** (`onHostMaintenance`): `MIGRATE` live-migrates the running VM to another host during maintenance, so it keeps running with at most a brief slowdown. `TERMINATE` stops the VM instead. Most machine types default to live migration; VMs with GPUs and some other configurations cannot live migrate.
- **Restart behavior** (`automaticRestart`): when true (the default), Compute Engine restarts a VM that was terminated by a host error, a crash or a terminate-on-maintenance event. `--no-restart-on-failure` turns this off.
## The scenario
`--maintenance-policy=TERMINATE` made Compute Engine stop the VM during maintenance, and `--no-restart-on-failure` meant nothing brought it back. Both flags override safe defaults. You can update the host maintenance policy of an existing VM at any time.
W: Migrate plus automatic restart: live migration keeps the VM running through maintenance events, and automatic restart brings it back after a host error, which restores the default availability behavior the script removed.
X: A=Deletion protection: it only blocks deleting the VM; it does not change what happens during host maintenance, so the VM would still be terminated.
B=Spot VM: Spot VMs cannot live migrate or be set to restart automatically on host events, and they can be preempted at any time, which makes availability worse.
C=Snapshot schedule: snapshots protect disk data; they do not restart or recreate the VM, and restoring from the last snapshot would also lose recent changes.
T: Keep a VM running through maintenance with onHostMaintenance=MIGRATE and keep automaticRestart=true; TERMINATE plus no restart leaves it down.
V: Compute Engine

@ GCP-ACE D2 T2.1 applied definition
S: A data team plans to use Spot VMs to cut the cost of a nightly transcoding fleet. Which statements about Spot VMs are correct? (Select TWO)
A: Compute Engine can preempt a Spot VM at any time to reclaim capacity, and its termination action decides whether the VM is stopped or deleted
B: Spot VMs keep running for at most 24 hours, after which Compute Engine always stops them, even when spare capacity is still available
C: Spot VMs are covered by the Compute Engine SLA at a reduced uptime percentage, so short outages caused by preemption earn service credits
D: Spot VMs cannot live migrate during host maintenance and cannot be configured to restart automatically when a host event occurs
E: Spot VMs are priced by bidding: you set a maximum hourly bid, and the VM is preempted whenever the market price rises above your bid
K: A,D
G: ## What a Spot VM is
A Spot VM uses the **spot provisioning model**: it runs on excess Compute Engine capacity at a large discount, and in exchange Compute Engine may **preempt** it at any time to reclaim that capacity. Spot VMs are the latest version of preemptible VMs.
- **Termination action**: on preemption, Compute Engine either stops the VM (the default, `STOP`) or deletes it (`DELETE`), as you choose when you create it.
- **No minimum or maximum runtime** unless you set one yourself (for example with a maximum run duration).
- **Limitations**: Spot VMs cannot live migrate to become standard VMs and cannot be set to restart automatically after a host event. For these reasons they are excluded from the Compute Engine SLA.
## Spot VMs and preemptible VMs
The older **preemptible VMs** share the price model, but Compute Engine always stops a preemptible VM after it has run for 24 hours. Spot VMs removed that limit.
## Good fits
Fault-tolerant, restartable work such as batch processing: if some VMs are preempted, the job slows down but does not fail.
W: A=Preemption and termination action: preemption can happen at any time, and the termination action set at creation (stop by default, or delete) controls what happens to the VM.
D=No live migration or auto restart: Spot VMs cannot live migrate or restart automatically on host events, which is one reason they carry no SLA.
X: B=24-hour limit: the 24-hour cap belongs to the older preemptible VMs; Spot VMs have no maximum runtime unless you set one.
C=Reduced SLA: Spot VMs are excluded from the Compute Engine SLA entirely; there is no reduced tier and no service credit for preemption.
E=Bidding: Google Cloud Spot VMs have no bids; they are billed at the current Spot price and preemption is driven by capacity needs, not by a price you set.
T: Spot VMs: deep discount, preemptible at any time (stop or delete), no live migration, no auto restart, no SLA, and unlike preemptible VMs no 24-hour limit.
V: Compute Engine, Spot VMs

@ GCP-ACE D2 T2.1 applied use-case
S: A media startup renders video frames pulled from a work queue. Each frame is independent and can simply be retried, and the goal is the lowest compute cost. When Compute Engine reclaims a worker VM, the team wants a replacement worker created automatically from the same configuration without anyone stepping in. What should the team set up?
A: An unmanaged instance group of Spot VMs, each created by hand, with a load balancer health check pointed at the group
B: Standard VMs on a sole-tenant node group, with the automatic restart policy enabled so that crashed workers come back
C: A managed instance group whose instance template uses the Spot provisioning model, so the group recreates preempted VMs
D: One large Spot VM with automatic restart turned on, so that Compute Engine restarts it on another host after preemption
K: C
G: ## Spot VMs inside a managed instance group
A **managed instance group (MIG)** keeps a set of identical VMs created from an **instance template**. One of its built-in services is automatic repair: if a VM in the group stops, crashes, **gets preempted (Spot VMs)** or is deleted by something other than the MIG, the MIG recreates it from the template.
Putting the Spot provisioning model in the template therefore gives two things at once:
- the Spot discount on every worker;
- self-healing capacity: preempted workers come back as soon as Compute Engine has capacity again.
## Why this fits queue workers
Work pulled from a queue is naturally retryable: a frame that was in progress on a preempted VM goes back to the queue and another worker picks it up.
W: MIG with a Spot template: the template makes every worker a discounted Spot VM, and the MIG's automatic repair recreates preempted VMs from that template, so the fleet refills itself without manual action.
X: A=Unmanaged instance group: unmanaged groups have no instance template, autohealing or autoscaling, and a load balancer health check only steers traffic; nobody would recreate preempted workers.
B=Sole-tenant standard VMs: dedicated hosts cost more than shared standard VMs, which goes against the lowest-cost goal, and automatic restart does not help with scaling a worker fleet.
D=Single Spot VM with auto restart: Spot VMs cannot be configured to restart automatically on host events, and one large VM is a single point of failure for the whole render job.
T: Cheap, self-healing batch workers → a MIG whose instance template uses Spot VMs; the MIG recreates preempted instances.
V: Compute Engine, managed instance groups, Spot VMs

@ GCP-ACE D2 T2.1 applied troubleshooting
S: A team creates Spot VMs each night with gcloud compute instances create ... --provisioning-model=SPOT. After preemptions, dozens of VMs remain in the TERMINATED state, and their boot disks keep adding to the bill. The team wants preempted VMs to disappear on their own. Which change should they make to the create command?
A: Add --no-restart-on-failure so that Compute Engine does not try to bring the Spot VM back after it is preempted
B: Add --instance-termination-action=DELETE so that Compute Engine deletes each Spot VM when it preempts it
C: Add --maintenance-policy=TERMINATE so that preempted VMs are terminated permanently instead of only stopped
D: Replace --provisioning-model=SPOT with --preemptible so that preempted VMs are removed after 24 hours of running
K: B
G: ## What happens to a preempted Spot VM
When Compute Engine preempts a Spot VM, it applies the VM's **termination action**:
- `STOP` (default): the VM moves to `TERMINATED`. You are not charged for the VM itself while it is stopped, but its disks remain and are billed until deleted.
- `DELETE`: the VM is deleted. Boot disks created with the VM are auto-deleted with it by default.
The action is set at creation, for example:
`gcloud compute instances create worker-1 --provisioning-model=SPOT --instance-termination-action=DELETE`
## Other flags that look related
- `--maintenance-policy` sets what happens during host maintenance (migrate or terminate), not during preemption.
- `--restart-on-failure` / `--no-restart-on-failure` control automatic restart after host errors; Spot VMs cannot restart automatically anyway.
W: Termination action DELETE: preemption then deletes the VM instead of stopping it, and auto-delete boot disks go with it, so nothing is left behind to bill.
X: A=--no-restart-on-failure: Spot VMs never restart automatically anyway; turning restart off does not change the default stop action, so stopped VMs and their disks still pile up.
C=--maintenance-policy=TERMINATE: this flag governs host maintenance events, and "terminate" there still means the VM is stopped, not deleted.
D=--preemptible: preemptible VMs are also stopped (TERMINATED) when preempted, and the 24-hour cap only adds another forced stop; nothing is deleted.
T: To have preempted Spot VMs removed automatically, create them with --instance-termination-action=DELETE (default is STOP).
V: Compute Engine, Spot VMs

@ GCP-ACE D2 T2.1 applied use-case
S: A finance team runs a third-party risk engine licensed per vCPU; they own licenses for exactly 6 vCPUs. Load tests show the engine needs 6 vCPUs and about 30 GB of memory. The closest predefined type, n2-standard-8, would need 8 licenses. What should the cloud engineer create?
A: A VM with an N2 custom machine type of 6 vCPUs and 30 GB of memory
B: A VM with a C3 custom machine type of 6 vCPUs and 30 GB of memory
C: A VM with the predefined n2-highmem-4 machine type and 32 GB of memory
D: A VM on a sole-tenant node with 8 vCPUs, reserving 2 vCPUs for later
K: A
G: ## Predefined and custom machine types
A **predefined machine type** has a fixed number of vCPUs and amount of memory, such as `n2-standard-8` (8 vCPUs, 32 GB). When none fits, you can create a VM with a **custom machine type** and choose the vCPU count and memory yourself.
- Custom machine types are available only for the general-purpose **N and E** series (for example N4, N2, N2D, E2, N1); the **C** and Tau series (C3, C4, T2D and others) do not support them.
- Each series has limits. For N2: 2 to 80 vCPUs (multiples of 2 up to 32), and 0.5 to 8 GB of memory per vCPU in 256 MB steps.
- Custom types cost slightly more than an equivalent predefined type, but can save much more when software is licensed per vCPU.
## Example
6 vCPUs and 30 GB is 5 GB per vCPU, inside the N2 range. With gcloud: `--custom-vm-type=n2 --custom-cpu=6 --custom-memory=30GB`.
W: N2 custom 6 vCPU / 30 GB: it matches the measured need exactly, stays within the N2 per-vCPU memory range, and uses 6 vCPUs, so the team needs only the 6 licenses it owns.
X: B=C3 custom: the C machine series does not offer custom machine types, so this configuration cannot be created.
C=n2-highmem-4: it has enough memory but only 4 vCPUs, below the 6 vCPUs the load tests showed the engine needs.
D=Sole-tenant node: a dedicated host does not shrink the VM; an 8-vCPU VM still exposes 8 vCPUs to license, and sole tenancy adds cost.
T: Per-vCPU licensing or an awkward size → custom machine type on an N or E series (not C series), within that series' memory-per-vCPU range.
V: Compute Engine, custom machine types

@ GCP-ACE D2 T2.1 advanced tradeoff
S: An in-memory analytics product is licensed per vCPU, and the team has budgeted for 4 vCPUs. The data set needs 64 GB of RAM on a single VM, and CPU usage is low. The team plans to use the N2 machine series. Which configuration meets both constraints?
A: An N2 custom machine type with 4 vCPUs and 32 GB of memory, the most memory a 4-vCPU custom type allows
B: The predefined n2-highmem-8 type with 8 vCPUs and 64 GB, then license only 4 of the vCPUs in the product
C: An N2 custom machine type with 4 vCPUs and 64 GB of memory, created with the extended memory feature
D: An E2 custom machine type with 4 vCPUs and 64 GB of memory, since E2 has no memory-per-vCPU limit
K: C
G: ## Memory per vCPU limits
Custom machine types let you choose vCPUs and memory, but each series has a **default memory-per-vCPU range**. For N2 it is 0.5 to 8 GB per vCPU; for E2 it is 0.5 to 8 GB per vCPU as well, and E2 does not support extended memory. So 4 vCPUs normally allow at most 32 GB.
## Extended memory
The **extended memory** feature lifts that ratio: instead of the default memory size based on vCPUs, you specify more memory, up to the limit of the machine series. Google's machine family docs name this use case: getting more than 8 GB per vCPU while avoiding per-CPU software licensing costs. With gcloud this is the `--custom-extensions` flag together with `--custom-cpu` and `--custom-memory`.
## Example
4 vCPUs and 64 GB is 16 GB per vCPU: invalid as a plain N2 custom type, valid with extended memory.
W: N2 custom with extended memory: extended memory allows more than 8 GB per vCPU, so the VM gets 64 GB while exposing only the 4 licensed vCPUs.
X: A=4 vCPUs / 32 GB: it respects the default ratio but provides only half of the 64 GB the data set needs.
B=n2-highmem-8: the VM exposes 8 vCPUs; per-vCPU licensing counts the vCPUs the VM has, so this doubles the license requirement.
D=E2 custom: E2 also caps memory at 8 GB per vCPU and does not offer extended memory, so 64 GB on 4 vCPUs is not a valid E2 custom type.
T: Need more than 8 GB per vCPU on N-series custom types (often to save per-vCPU licenses) → enable extended memory.
V: Compute Engine, custom machine types

@ GCP-ACE D2 T2.1 advanced use-case
S: A team runs a self-managed PostgreSQL server on one Compute Engine VM in us-central1-a. Management now requires that the database survive the loss of that zone with no loss of committed data, and a standby VM can be kept stopped in us-central1-b. Which storage design meets the requirement?
A: Keep the data on a zonal Hyperdisk Balanced volume with a snapshot schedule every hour, and create a new disk in us-central1-b from the latest snapshot
B: Keep the data on a Hyperdisk Balanced High Availability or regional Persistent Disk volume replicated to both zones, and attach it to the standby VM on failover
C: Keep the data on Local SSD disks in RAID 0 for speed, and copy the database files to a Cloud Storage bucket in the same region every fifteen minutes
D: Keep the data on a zonal Hyperdisk Balanced volume with Asynchronous Replication to europe-west1, and fail over to a VM created in that region
K: B
G: ## Synchronous disk replication
**Regional Persistent Disk** and **Hyperdisk Balanced High Availability** synchronously replicate every write to two zones in the same region. A write is acknowledged only after both replicas have it, so a zone failure loses no acknowledged data: a recovery point objective (RPO) of zero.
- The disk can be a boot or a data disk.
- It can be attached only to VMs in the two zones that hold its replicas.
- On a zone failure you attach the disk to a VM in the surviving zone (force-attach if the old VM cannot release it) and start the database there.
## Other protection tools and their RPO
- **Snapshots** are point-in-time copies: everything written since the last snapshot is lost (RPO up to the schedule interval).
- **Asynchronous Replication** copies Hyperdisk data to another *region* for regional disasters; being asynchronous, it has an RPO above zero.
- **Local SSD** is temporary storage on the host; its data is lost when the VM stops or fails.
W: Regional disk across both zones: synchronous replication to us-central1-a and us-central1-b gives zero data loss for one zone failure, and the standby VM in the second zone can attach the same disk and take over.
X: A=Hourly snapshots: restoring from a snapshot loses up to an hour of committed transactions, which violates "no loss of committed data".
C=Local SSD plus copies: Local SSD data is lost if the VM or zone fails, and files copied every fifteen minutes still leave up to fifteen minutes of lost data.
D=Asynchronous Replication to another region: it protects against regional outages but replicates asynchronously, so recent writes can be lost, and failover means moving the database to another region instead of the nearby standby zone.
T: Zone failure with RPO 0 on VMs → regional Persistent Disk or Hyperdisk Balanced High Availability (synchronous across two zones).
V: Compute Engine, Hyperdisk, Persistent Disk

@ GCP-ACE D2 T2.1 applied tradeoff
S: A MySQL VM keeps 400 GB of data on a balanced Persistent Disk and is limited by disk IOPS. To get the IOPS it needs, the team would have to grow the disk to several terabytes it will never fill. The VM's machine series supports Hyperdisk. Which option raises IOPS without paying for unused capacity?
A: Move the data to a Hyperdisk Throughput volume and raise its IOPS level separately from its size
B: Move the data to a Hyperdisk Balanced volume and set the provisioned IOPS independently of its size
C: Move the data to Local SSD disks, which deliver higher IOPS than any network-attached disk type
D: Resize the balanced Persistent Disk to several terabytes, since disk IOPS scale with its capacity
K: B
G: ## Persistent Disk vs Hyperdisk performance
- **Persistent Disk** performance depends on provisioned capacity: to get more IOPS or throughput you make the disk bigger, and you pay for the extra GB.
- **Hyperdisk** lets you configure performance and size **independently**. You can raise or lower a Hyperdisk volume's provisioned IOPS or throughput without changing its size, even while it is in use. Google recommends Hyperdisk when the machine series supports it.
## Hyperdisk types
- **Hyperdisk Balanced**: the default for most workloads, including MySQL and PostgreSQL; you set both IOPS and throughput.
- **Hyperdisk Extreme**: highest IOPS, for SAP HANA and high-end databases; you set IOPS only.
- **Hyperdisk Throughput**: for throughput-heavy, IOPS-light work such as Hadoop or Kafka and cold disks; you set throughput only, and IOPS follow from it.
- **Hyperdisk ML**: very high read-only throughput shared by many VMs.
W: Hyperdisk Balanced with provisioned IOPS: the team keeps a 400 GB volume and provisions the IOPS it needs separately, so it pays for that performance, not for terabytes of empty space.
X: A=Hyperdisk Throughput: you cannot set an IOPS level on Hyperdisk Throughput; it is designed for throughput-bound workloads that do not need high IOPS.
C=Local SSD: Local SSD is temporary storage; the database files would be lost if the VM stops or fails, which is unacceptable for MySQL data.
D=Grow the Persistent Disk: it works technically, but it is exactly the paying-for-unused-capacity outcome the team wants to avoid.
T: Persistent Disk performance grows with size; Hyperdisk performance is provisioned separately from size (Hyperdisk Balanced for typical databases).
V: Compute Engine, Hyperdisk, Persistent Disk

@ GCP-ACE D2 T2.1 applied use-case
S: An inference fleet of 400 Compute Engine VMs must load the same 150 GB of model weights at startup. The weights never change between releases, and startup time matters. The team wants one copy of the data that every VM reads directly as a disk. Which disk type should they use?
A: A Hyperdisk Extreme volume, attached in read-write mode to every VM in the fleet for the highest IOPS
B: A Hyperdisk Balanced volume in multi-writer mode, attached to every VM in the fleet at the same time
C: A Hyperdisk Throughput volume, attached to one VM that copies the weights to the others over the network
D: A Hyperdisk ML volume, loaded once and then attached in read-only mode to every VM in the fleet
K: D
G: ## Sharing one disk across many VMs
Most disks are attached to one VM. Some Hyperdisk types support sharing:
- **Hyperdisk Balanced** and **Hyperdisk Balanced High Availability** support simultaneous read-write access from **up to 8 instances**.
- **Hyperdisk ML** is built for machine learning and AI inference or training: one volume can be attached **read-only to up to 2,500 instances**, and it offers the highest read-only throughput of any Hyperdisk type. You write the data once, then attach the volume read-only everywhere.
## Example
Load model weights into a Hyperdisk ML volume, switch it to read-only, and reference it from the instance template of the inference MIG: every new VM mounts the same weights immediately, without downloading or copying.
W: Hyperdisk ML read-only: it is designed for this pattern, one volume of model data attached read-only to up to 2,500 VMs with very high read throughput, so 400 VMs load the weights quickly from a single copy.

@ GCP-ACE D2 T2.1 applied definition
S: A team plans to add Local SSD to a Microsoft SQL Server VM. Which statements about Local SSD are correct? (Select TWO)

G: ## Temporary and durable block storage
Compute Engine has two kinds of block storage:
- **Temporary (ephemeral)**: **Local SSD**, including Titanium SSD. The disks are physically attached to the server that hosts the VM. They are the fastest option, but the data is lost if you stop, suspend or restart the VM, or if it crashes or fails (Compute Engine tries to recover it after host errors, but does not guarantee it). C=Detach and reattach: Local SSD is physically attached to the host; portability between VMs is a property of network-attached Hyperdisk and Persistent Disk.
D=Replicated to a second zone: two-zone synchronous replication is offered by regional Persistent Disk and Hyperdisk Balanced High Availability, not by Local SSD.

G: ## Instance templates are immutable
An **instance template** saves a VM configuration: machine type, boot disk image, labels, startup script, network and more. A managed instance group (MIG) **must** be created from one, and it builds and repairs every VM from it.
You **can't update an instance template after it is created**. To change something you:
1. create a new template (from scratch, from an existing VM, or based on the existing template with the property changed);
2. point the MIG at the new template and roll it out, for example with a rolling update, so VMs are replaced gradually.

The MIG recreates VMs from its template whenever it repairs, autoscales or updates them. A change made by hand on one VM is lost the next time that VM is recreated.

D=Delete and recreate with the same name: Compute Engine does not let you delete a template that a MIG still references, and reusing a template name is what Google advises against (reference templates by ID).

@ GCP-ACE D2 T2.1 advanced troubleshooting
S: A managed instance group autoscales on average CPU utilization with a 60% target. Each new VM spends about 4 minutes installing packages at boot, with high CPU, before the app serves traffic. During every spike the group overshoots and adds far more VMs than needed. Which autoscaler setting should be adjusted?
A: Set the stabilization period to 4 minutes, so that the autoscaler waits that long before it adds any new VMs to the group
B: Configure scale-in controls with a small maximum allowed reduction, so that the group adds fewer VMs during each spike
C: Raise the target CPU utilization to 95%, so that the high CPU of booting VMs no longer triggers additional scale-out
D: Set the initialization period to about 240 seconds, so that scale-out ignores data from VMs that are still starting up
K: D
G: ## How the autoscaler uses time settings
- **Initialization period** (formerly cool down period): how long your app takes to initialize on a new VM, 60 seconds by default. For **scale-out** decisions the autoscaler ignores usage data from VMs still inside this period, because a booting VM's CPU does not reflect real load. For scale-in it still counts them.
- **Stabilization period** (default 10 minutes): used only for **scale-in**; the autoscaler keeps enough capacity for the peak load seen in this window before deleting VMs.
- **Scale-in controls** (maximum allowed reduction over a trailing time window): limit how fast the group shrinks.
## The scenario
With a 60-second initialization period, new VMs busy installing packages report high CPU for minutes. The autoscaler counts that as load, adds more VMs, which also boot with high CPU, and so on. Setting the initialization period to the real start-up time (about 4 minutes) breaks that loop.
W: Initialization period of about 240 seconds: the autoscaler stops using CPU data from VMs that are still installing packages for scale-out decisions, so boot-time CPU no longer triggers extra VMs.
X: A=Stabilization period: it only delays scale-in decisions; it does not change how the autoscaler reads CPU from booting VMs when it scales out.
B=Scale-in controls: they limit how quickly the group shrinks after a peak; they have no effect on overshooting during scale-out.
C=95% target: the group would run hot all the time and react late to real load, while booting VMs at 100% CPU could still trigger overshoot.
T: New VMs that are busy starting up distort scale-out → set the initialization period to the real app start-up time.
V: Compute Engine, autoscaler, managed instance groups

@ GCP-ACE D2 T2.1 advanced troubleshooting
S: Workers in a managed instance group process messages from a Pub/Sub subscription. The group autoscales on average CPU utilization, and the team set the minimum number of instances to 0 so it would be empty overnight when the queue is empty, yet at least one VM always keeps running. How should the team reach zero instances when there is no work?
A: Lower the CPU utilization target to 1%, so that the autoscaler sees even one idle VM as over target and removes it
B: Scale on a Cloud Monitoring metric for the subscription's backlog of undelivered messages instead of CPU, keeping minimum at 0
C: Add a scaling schedule with a capacity of 0 instances every night, which forces the group to delete all of its VMs
D: Switch the signal to HTTP load balancing serving capacity, which reports zero usage once all requests have stopped
K: B
G: ## Which autoscaling signals can reach zero
An autoscaling policy uses one or more signals. If a group autoscales on any of these, it **cannot scale in to zero**:
- average CPU utilization;
- HTTP load balancing serving capacity;
- Cloud Monitoring metrics that come from each VM in the group.
That makes sense: with zero VMs there is nothing to measure, so the group could never scale out again.
A Cloud Monitoring metric that does **not** come from the VMs, such as the number of undelivered messages in a Pub/Sub subscription, can drive the group down to zero, as long as `minNumReplicas` is `0`. When messages arrive the metric rises and the autoscaler adds VMs again.
## Schedules
A scaling schedule sets a **minimum** capacity for a time window ("at least 10 VMs from 08:00"). It guarantees capacity; it does not force a group down.
W: Backlog metric with minimum 0: the undelivered-messages metric is measured on the subscription, not on the VMs, so the group can scale to zero when the queue is empty and scale out again when work arrives.
X: A=1% CPU target: CPU utilization is one of the signals that can never scale a MIG in to zero, whatever target value is set.
C=Schedule with capacity 0: a schedule sets a minimum number of VMs while it is active; it never forces the group below what the other signals recommend.
D=Load balancing serving capacity: this signal also prevents scaling in to zero, and queue workers that pull from Pub/Sub receive no HTTP traffic for it to measure anyway.
T: To let a MIG scale to zero, drive it with a metric that does not come from its own VMs (e.g., Pub/Sub backlog) and set the minimum to 0.
