@ GCP-ACE D1 T1.1 advanced use-case
S: An organization enforces the boolean constraint `compute.requireOsLogin` in a policy at the organization node. Lab projects are spread over many folders and must stay where they are, and each lab project has the tag `env=lab` bound at project level. The security team wants OS Login enforcement turned off for lab projects only, including lab projects created next month, without maintaining a policy on each project. What is the approach with the LEAST operational effort?
A: Add a tag condition to the organization-level policy that turns enforcement off for resources tagged env=lab and keeps it on for everything else
B: Move every lab project into a new Lab folder and set a folder-level policy there that turns enforcement of the constraint off for that folder
C: Set a project-level policy with enforcement off on each existing lab project, and add the same step to the runbook for new lab projects
D: Add the lab teams to an IAM deny policy exception for the constraint, so that OS Login is not required when they work in lab projects
K: A
G: ## Conditional organization policies with tags
An organization policy can carry **conditions** that test tags. Tags are bound to the organization, folders or projects (and some service resources), and a tag binding is **inherited** by everything below it. A single policy can contain a conditional rule plus a default rule, for example:
- rule 1: condition `resource.matchTag('ORG_ID/env', 'lab')` with `enforce: false`
- rule 2: no condition, `enforce: true`
Any project that carries `env=lab` (or inherits it) gets the conditional rule; every other resource keeps enforcement.
## Why this scales
The policy is set once, at the organization. A lab project created next month only needs its tag, and the policy follows the tag wherever the project sits in the folder tree. Changing a tag binding is controlled by IAM roles on the tag, so developers cannot simply opt out.
W: Tag condition at the organization: the policy itself decides per tag, so every current and future project tagged env=lab is exempt and nothing has to be edited per project or per folder.
X: B=Lab folder: a folder-level policy would work, but the stem says the projects must stay in their current folders, so moving them breaks a stated constraint.
C=Per-project policies: this exempts the projects, but it is exactly the per-project maintenance the team wants to avoid and relies on a manual runbook step for every new project.
D=Deny policy exception: IAM deny policies control permissions of principals; they cannot switch an organization policy constraint on or off for anyone.
T: To scope an organization policy to some projects without moving them, use a tag-based condition in one policy at a higher level.
V: Organization Policy Service, Resource Manager tags

@ GCP-ACE D1 T1.1 advanced use-case
S: The platform team must stop anyone in the organization from creating GKE node pools that have node auto-upgrade turned off. No predefined constraint covers this field, the request must be refused before the node pool exists, and the rule must cover every current and future project. A proposal for a scheduled job that deletes non-compliant node pools after the fact has already been rejected by security. What should the team do?
A: Define a custom organization policy constraint with a CEL condition on the node pool's auto-upgrade field, and enforce it in a policy at the organization
B: Attach an IAM deny policy at the organization that denies the node pool create permission to every principal except the members of the platform group
C: Create a Cloud Asset Inventory real-time feed for node pool changes and notify the security team through Pub/Sub whenever auto-upgrade is turned off
D: Remove the Kubernetes Engine Admin role from all developers, and let only the platform team create node pools after reviewing each request by hand
K: A
G: ## Custom constraints
Managed (predefined) constraints cover common settings. When a field is not covered, an administrator can write a **custom constraint**:
- It is defined in YAML with `resourceTypes` (for example a GKE node pool), the `methodTypes` it applies to (such as `CREATE`), a **CEL** `condition` such as `resource.management.autoUpgrade == false`, and an `actionType` (`DENY` or `ALLOW`).
- After it is set up, it is enforced like any other constraint, through an organization policy at the organization, a folder or a project.
## Preventive versus detective
An organization policy is evaluated when the API request arrives, so a non-compliant node pool is never created. Feeds, alerts and clean-up jobs only react after the resource exists, which the security team ruled out here.
W: Custom constraint: it targets exactly the auto-upgrade field, blocks the create request in the API, and an organization-level policy covers every current and future project.
X: B=Deny policy on create: it stops almost everyone from creating any node pool, compliant or not, instead of blocking only the setting that is not allowed.
C=Asset feed: a feed reports changes after they happen; it never refuses the request, so non-compliant node pools would still be created.
D=Manual review: it narrows who can create node pools but still lets a reviewer approve a pool with auto-upgrade off; nothing technical enforces the rule.
T: When no managed constraint covers a field, write a custom organization policy constraint with a CEL condition and enforce it.
V: Organization Policy Service, Google Kubernetes Engine

@ GCP-ACE D1 T1.1 advanced use-case
S: A data team of 25 analysts queries BigQuery in project `ana-prod` with on-demand pricing. Finance wants each analyst limited to 2 TiB of data processed per day and the whole project to 30 TiB per day, with queries over a limit failing instead of only sending a notification. Analysts run many small queries, so a cap on each single query is not enough. Which TWO settings should the engineer configure? (Select TWO)
A: A custom quota override on ana-prod for Query usage per day, set to 30 TiB, so the project as a whole stops processing above that amount
B: A custom quota override on ana-prod for Query usage per day per user, set to 2 TiB, so each analyst and service account is limited separately
C: A maximum bytes billed of 2 TiB in each analyst's query settings, so that any analyst who processes more than that in a day is refused
D: A Cloud Billing budget scoped to the BigQuery service with thresholds at 50% and 90%, sending alerts to the data lead and the analysts
E: A BigQuery reservation with a fixed number of slots assigned to ana-prod, so that the project can never process more than 30 TiB a day
K: A,B
G: ## Custom query quotas in BigQuery
Under on-demand pricing, cost follows the bytes a query processes. BigQuery offers two **custom quotas** that cap processed data per day:
- `QueryUsagePerDay`: a project-level limit for all users combined.
- `QueryUsagePerUserPerDay`: applied separately to each user and service account in the project. The project total can never exceed the project-level limit, whatever the per-user value.
When a limit is reached, further queries fail with a `quotaExceeded` error that names the quota.
## Other controls
- **Maximum bytes billed** is a per-query setting: a query that would process more fails before it runs, but many small queries still add up.
- **Budgets** compare spend with an amount and send notifications; they do not stop queries.
- **Reservations** move a project to capacity (slot) pricing; they limit compute capacity, not bytes per day.
W: A=Query usage per day: the project-level custom quota enforces the 30 TiB daily ceiling for everyone together.
B=Query usage per day per user: the per-user custom quota enforces the 2 TiB daily limit for each analyst, however many queries they run.
X: C=Maximum bytes billed: it limits a single query only, so an analyst could run many 1.9 TiB queries and pass the daily amount.
D=Budget alerts: budgets notify people about spend; queries keep running, which fails the requirement that over-limit queries fail.
E=Reservation: slots cap processing capacity at any moment, not the bytes processed per day, and they change the pricing model the team uses.
T: Use BigQuery custom quotas (per project and per user per day) to make on-demand queries fail beyond a daily amount.
V: BigQuery, Cloud Quotas

@ GCP-ACE D1 T1.1 advanced troubleshooting
S: On Monday an engineer ran `gcloud projects delete web-stage` by mistake; today is Thursday. The project held VMs, a Cloud SQL instance and some Cloud Storage buckets, and it was linked to the company's billing account. The team wants the project back under the same project ID as quickly as possible and wants to know what to expect afterwards. Which TWO statements are correct? (Select TWO)
A: Within the 30-day recovery period, a principal with the project undelete permission can run `gcloud projects undelete web-stage` to restore it
B: After the restore, the project must be linked to the billing account again, because shutdown disconnects billing and restore does not reinstate it
C: The project ID is released at shutdown, so the team must create a new project named web-stage and rebuild its resources from backups
D: Restoring brings back every Cloud Storage object and Pub/Sub resource exactly as it was, because all services keep data for 30 days
E: Only Cloud Customer Care can restore a deleted project, so the team must open a support case and wait for Google to restore it
K: A,B
G: ## What happens when a project is shut down
`gcloud projects delete` does not erase a project at once. The project moves to the `DELETE_REQUESTED` state for a **30-day recovery period**:
- it becomes unusable immediately and all billing and resource usage stop;
- its Cloud Billing account is **disconnected**, and this link is not reinstated automatically on restore;
- after 30 days the project and its data are deleted permanently.
## Restoring
A principal with `resourcemanager.projects.undelete` runs `gcloud projects undelete PROJECT_ID`. The project keeps its ID. Some services can take up to 36 hours to resume fully, and a few (the docs name Cloud Storage and Pub/Sub) may delete resources much sooner than 30 days, so not everything is guaranteed to come back.
W: A=Undelete within 30 days: the project is only in the recovery state, and `gcloud projects undelete` restores it with the same ID.
B=Relink billing: shutdown removed the billing link, so resources that need billing stay unusable until the project is linked again.
X: C=ID released: the ID stays reserved during the recovery period and comes back with the restored project; a rebuild is unnecessary.
D=Everything returns: the docs warn that services such as Cloud Storage and Pub/Sub may delete resources sooner, so full recovery is not guaranteed.
E=Support only: project owners can restore the project themselves; support is only needed if resources are still missing long after the restore.
T: A deleted project can be undeleted for 30 days, but its billing link must be set again and some data may already be gone.
V: Resource Manager, Cloud Billing

@ GCP-ACE D1 T1.1 advanced comparison
S: A company wants every project under the Prod folder, including projects created later, to be marked as production so that an IAM allow policy condition can grant the on-call group extra roles only on production resources. The marker must be set once on the folder and flow down automatically, and changing it must require a dedicated IAM role rather than ordinary edit rights on the project. What should the engineer use?
A: A tag key env with the value prod bound to the Prod folder, referenced with resource.matchTag in the conditional role binding
B: A label env=prod set on the Prod folder, referenced in the binding's condition through resource.labels so that new projects inherit it
C: A label env=prod added to each project by the project creation script, referenced by a condition that reads the project's labels
D: A network tag prod added to all VMs through their instance templates, referenced by the IAM condition through each VM's resource name
K: A
G: ## Tags versus labels
Both are key-value metadata, but they serve different purposes:
- **Tags** are resources of their own. Creating and attaching them needs dedicated IAM roles, tag bindings are **inherited** by child resources, and they can be referenced in **allow and deny policy conditions** and in organization policy conditions.
- **Labels** annotate individual resources, are **not inherited**, have no IAM or organization policy support, and are mainly used to filter and break down costs in Cloud Billing.
- **Network tags** on VMs are yet another thing: they select targets for firewall rules and routes.
## Example
Bind `env=prod` to the Prod folder; every project in it inherits the tag. A binding with the condition `resource.matchTag('ORG_ID/env', 'prod')` then grants the on-call group its extra role only where the tag applies.
W: Tag on the folder: tags are inherited by every project below the folder, IAM conditions can test them, and attaching or changing them needs tag-specific roles.
X: B=Folder label: labels are not inherited by child resources and IAM conditions cannot reference them, so nothing would flow down or be evaluated.
C=Labels per project: labels are not supported in IAM conditions, and anyone allowed to edit the project could change them.
D=Network tags: they only select VMs for firewall rules and routes; IAM conditions cannot use them, and they do not mark projects.
T: Use tags (inherited, IAM-controlled, usable in conditions) for policy decisions and labels for cost reporting.
V: Resource Manager tags, IAM Conditions

S: A startup runs a public demo on Cloud Run in project `demo-web`, which also hosts a VM and a Cloud SQL instance used by other teams. If the month's Cloud Run spend in the project goes past an agreed amount, new Cloud Run usage must stop automatically until someone reviews it, while the VM and the database keep running. Nobody on the team wants to write or maintain automation code. What should the engineer configure?
A: A spend cap budget scoped to the demo-web project and the Cloud Run service, with the monthly amount set to the agreed limit
B: An alerts-only budget on demo-web with a Pub/Sub topic and a Cloud Run function that disables billing on the project above the amount
C: An alerts-only budget scoped to the Cloud Run service with thresholds at 90% and 100% of actual spend, emailing the project owners
D: A lower Cloud Run request quota in demo-web, sized from the monthly amount so that the service can never cost more than the limit
K: A
G: ## Two kinds of budgets
- **Alerts-only budgets** compare actual or forecasted cost with an amount and send emails or Pub/Sub messages. They never stop anything by themselves; automatic action needs your own code (for example a function that disables billing).
- **Spend cap budgets** pause usage of **one eligible service in one project** when the gross, estimated cost passes 100% of the amount in the monthly period. Eligible services are the Gemini API, Gemini Enterprise Agent Platform, Cloud Run and Cloud Run functions. The cap stays enforced until it is lifted manually or the next month starts.
## What a spend cap does not touch
Persistent resources such as VMs and storage keep running and keep accruing charges, and other services in the project are not affected.
W: Spend cap budget: it is built for exactly this case, pausing only Cloud Run usage in demo-web once the monthly amount is passed, with no code to maintain.
X: B=Disable billing function: it needs custom code, and disabling billing stops every paid service in the project, including the VM and database other teams rely on.
C=Alerts-only budget: it only sends emails; Cloud Run keeps serving and costing money until someone acts by hand.
D=Lower quota: quotas limit request rates, not money per month, so they cannot track a spend amount and they would throttle traffic even when spend is low.
T: To pause one eligible service in one project at a spend limit, use a spend cap budget; alerts-only budgets only notify.

Finance wants a monthly SQL report in BigQuery that splits the cluster's cost by namespace, based on the CPU and memory each team's Pods request. The billing account already exports standard usage cost data to BigQuery, and finance does not want to maintain any agents or scripts on the cluster. Which TWO actions are required? (Select TWO)
A: Enable GKE cost allocation on the cluster, so the cluster name and each namespace appear as labels on the cost rows in the billing export
B: Enable the detailed usage cost export for the billing account, because GKE cost allocation data is not part of the standard export
C: Enable the pricing export for the billing account, because namespace costs are calculated from the list price of the SKUs Pods use
D: Add a team label to every node pool, because Cloud Billing splits node costs only by the labels set on the node pools of the cluster
E: Install the Ops Agent on every node, so that it reports each Pod's measured CPU and memory usage to Cloud Billing for the split

D=Node pool labels: labels on node pools split costs by node pool, not by namespace; teams share the same nodes here.
E=Ops Agent: the agent sends metrics and logs to Cloud Observability, not cost data to Cloud Billing, and the team wants no agents.
T: For per-namespace GKE costs, enable GKE cost allocation and query the detailed usage cost export.

@ GCP-ACE D2 T2.1 advanced use-case
S: A legacy order-processing application runs on one Compute Engine VM and keeps its queue files on an attached data disk. The application cannot scale out to more VMs. The team wants the VM recreated automatically whenever an application health check fails, and the data disk, its contents and the VM's name must survive every recreation and every later template update. What should the engineer set up?
A: A managed instance group of size one with autohealing and a stateful policy that preserves the data disk, so recreated VMs keep the disk and name
B: A managed instance group of size one with autohealing, and the queue files moved onto the boot disk that the instance template creates
C: A standalone VM with automatic restart in its availability policy, plus a daily snapshot schedule attached to the data disk
D: An unmanaged instance group behind an internal load balancer whose health check restarts the VM whenever the application stops answering
K: A
G: ## Stateless and stateful managed instance groups
A managed instance group (MIG) recreates VMs during autohealing, updates and repairs. In a normal (stateless) MIG every recreated VM gets fresh disks from the template, a new name in some operations, and any data on it is lost.
A **stateful MIG** preserves each VM's unique state across recreation, autohealing and updates:
- attached persistent disks listed in the stateful policy or per-instance configuration,
- the instance name, and optionally IP addresses and metadata.
## Why a size-one MIG
Even for a single VM, a MIG adds **autohealing** based on an application health check: if the app hangs, the MIG recreates the VM. With a stateful disk, the recreated VM reattaches the same data disk, so the queue files remain.
W: Stateful MIG of one: autohealing replaces a VM whose application fails its health check, and the stateful policy keeps the data disk and instance name through recreations and template updates.
X: B=Stateless MIG: when the group recreates the VM it builds a new boot disk from the template, so queue files on that disk are lost.
C=Automatic restart: it restarts a VM only after a host event or crash, not when the application fails a health check, and snapshots restore data only after manual work.
D=Unmanaged group: unmanaged instance groups have no autohealing; a load balancer health check only stops sending traffic, it never restarts or recreates a VM.
T: Use a stateful MIG to get autohealing for a single stateful VM while keeping its disks and name.
V: Compute Engine

@ GCP-ACE D2 T2.1 advanced use-case
S: A zonal managed instance group runs 8 web VMs in `us-east1-b`. The project's CPU quota in us-east1 has no room for even one more VM of this type, and a quota increase will take weeks. The team must roll out a new instance template today while at least 7 VMs keep serving at every moment of the update. Which TWO update settings should the engineer use? (Select TWO)
A: Set maxSurge to 0, so the group never tries to create an extra VM above the target size while it replaces VMs during the update
B: Set maxUnavailable to 1, so the group takes only one VM out of service at a time and at least 7 of the 8 keep serving
C: Keep the default maxSurge for a zonal group, which creates one new VM before an old one is removed and needs no extra quota
D: Set maxUnavailable to 0, so no VM ever stops serving and the update replaces each VM only after its replacement is running
E: Set the minimal action to RESTART, so the VMs pick up the new template by rebooting in place without being replaced at all
K: A,B
G: ## Rolling updates in a MIG
A proactive update replaces VMs that do not match the new template. Two settings control the pace:
- `maxSurge`: how many VMs the group may create **above** its target size during the update. The default for a zonal MIG is `1`. Surge VMs need quota, and the docs note surge only works if you have enough quota.
- `maxUnavailable`: how many VMs may be out of service at once. The default for a zonal MIG is `1`.
## Updating without spare quota
With no quota headroom, surge VMs cannot be created. Setting `maxSurge=0` and `maxUnavailable=1` makes the group delete one old VM, create its replacement from the new template, and move on: 7 of 8 VMs serve at every moment.
`gcloud compute instance-groups managed rolling-action start-update web-mig --version=template=web-v2 --max-surge=0 --max-unavailable=1 --zone=us-east1-b`
W: A=maxSurge 0: no extra VM is needed, so the update does not depend on quota the project lacks.
B=maxUnavailable 1: only one VM is replaced at a time, which keeps 7 of 8 serving as required.
X: C=Default surge: the zonal default creates one extra VM above target size, which needs CPU quota that is not available.
D=maxUnavailable 0: with surge also at 0, the group could never replace a VM; zero unavailability only works when surge VMs can be created.
E=Minimal action RESTART: a new instance template (new image or machine type) cannot be applied by a restart, so the updater still replaces the VMs.
T: Without quota for surge VMs, update a MIG with maxSurge 0 and a small maxUnavailable.

@ GCP-ACE D2 T2.1 advanced troubleshooting
S: An engineer creates an instance schedule in `europe-west1` that stops dev VMs at 19:00 and starts them at 07:00 in the team's time zone, and attaches it to five VMs in that region that use only standard persistent disks. The next morning all five VMs are still running from the day before, and nobody started them by hand. The engineer holds Compute Instance Admin (v1) on the project. What is the most likely cause?
A: The project's Compute Engine Service Agent lacks a role with the start and stop permissions, which the schedule needs to act on the VMs
B: Instance schedules act only on VMs created after the schedule exists, so the five existing VMs must be recreated from their template
C: Instance schedules always run in UTC and ignore the selected time zone, so the stop operation will simply happen hours later than planned
D: The engineer needs Compute Instance Admin (v1) at the organization level, because schedules are checked against organization policies
K: A
G: ## How instance schedules run
An instance schedule is a resource policy that starts and stops attached VMs at set times in a chosen time zone. The operations are carried out by the **Compute Engine Service Agent** of the project, not by the person who created the schedule. That service agent needs `compute.instances.start` and `compute.instances.stop`, for example through Compute Instance Admin (v1) on the project.
## Other rules
- VMs must be in the **same region** as the schedule.
- VMs with **Local SSD** cannot be stopped by a schedule.
- Operations can start up to 15 minutes late, and start and stop should be at least 15 minutes apart.

B=Disable first: a disabled account stops working at once and is switched back on in minutes if a job breaks, so the cleanup is safely reversible.

S: A cleanup script removed the Editor role from every principal in project `web-prod` and granted narrower roles to the users and service accounts it recognized. B: The service account attached to VMs in the template, because the group creates additional VMs with the identity of its running VMs
C: The Compute Engine default service account, PROJECT_NUMBER-compute@developer.gserviceaccount.com, which the autoscaler uses whenever it resizes the group
D: The engineer who created the group, because a managed instance group keeps acting with the credentials of the principal that created it

G: ## Who creates the VMs of a MIG
Projects that use Compute Engine have a **Google APIs Service Agent**, `PROJECT_NUMBER@cloudservices.gserviceaccount.com`. It holds Editor on the project by default, and **managed instance groups and autoscaling use its credentials to create, delete and manage instances**. The docs warn that revoking its permissions, or changing them so it can no longer create instances, stops MIGs and autoscaling from working.
## Lesson for clean-up scripts
Service agents are Google-managed identities that services rely on. A script that removes Editor from "every principal" should skip them, or the role they need should be restored right away.
W: Google APIs Service Agent: the MIG acts through this service agent, so removing its Editor role stops the group from creating VMs even though nothing else changed.
X: B=VM's service account: the attached account is what code on the VM uses; the group does not create VMs with it.
C=Compute Engine default service account: it is a user-managed default account used by VMs and some services, not the identity that MIGs use to manage instances.
D=Creator's credentials: MIGs act through the service agent, not the human who created them, and that person's roles did not change.
T: MIGs and autoscaling act through the Google APIs Service Agent; never strip its Editor role in clean-ups.

K: A
G: ## Key expiry with an organization policy
Service account keys never expire by default. The constraint `constraints/iam.serviceAccountKeyExpiryHours` sets an expiry time for **newly created keys** in the project, folder or organization where the policy applies. It accepts fixed `ALLOW` values: `1h`, `8h`, `24h`, `168h` (7 days), `336h` (14 days), `720h`, `1440h` and `2160h`. After that time the key expires and can no longer be used.
## Scope and timing
- Setting it on the project affects only that project.
- It applies to keys created after the policy is in place, so it must be set first.
- The docs recommend expiry for temporary access like a pilot, not for production workloads.
W: Project policy with 336h before creation: any key created in vendor-pilot afterwards expires after 14 days by itself, and other projects are untouched.
X: B=Time condition on bindings: it removes permissions after 14 days for one account's bindings only; keys on other service accounts in the project would keep working forever.
C=Organization-wide after creation: it would change key expiry in every project, and the key created earlier would get no expiry.
D=Secret Manager rotation: Secret Manager rotates secret versions it stores; it does not disable the service account key itself, which stays valid.
T: Use iam.serviceAccountKeyExpiryHours on a project, set before keys are created, to make its keys expire automatically.
V: IAM, Organization Policy Service
