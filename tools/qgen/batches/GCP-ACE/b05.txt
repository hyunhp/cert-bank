@ GCP-ACE D2 T2.2 applied use-case
S: A ticketing company is building an order system for customers in North America, Europe and Asia. It needs a relational schema with SQL, transactions that are strongly consistent everywhere, and write capacity that grows by adding resources rather than by moving to a bigger single primary server. Which database should the team choose?
A: Spanner with a multi-region instance configuration, which shards data automatically and keeps transactions strongly consistent
B: Cloud SQL for PostgreSQL with cross-region read replicas, which serve reads close to users while one primary takes all writes
C: Bigtable with clusters in three regions and replication, which spreads reads and writes across clusters in every continent
D: AlloyDB for PostgreSQL with read pool instances, which add read nodes on demand while the cluster stays in a single region
K: A
G: ## Scaling reads versus scaling writes
Most managed relational databases scale **reads** easily (add replicas) but send every **write** to one primary server. When that primary is full, the only option is a bigger machine.
## What Spanner adds
Spanner is Google Cloud's relational database with **horizontal read and write scalability**:
- data is sharded automatically across many servers, so adding capacity adds write throughput
- transactions are **strongly consistent**: every read reflects the most recent committed write, wherever the data lives
- instance configurations can be single-region, dual-region or multi-region, with up to 99.999% availability
It speaks SQL (GoogleSQL or a PostgreSQL interface), so the application keeps a relational schema.
## Example
Orders from Tokyo and Frankfurt write to the same multi-region Spanner database. Both see the same committed seat inventory, so the same seat is never sold twice.
W: Spanner multi-region: it is the managed relational database that scales writes horizontally and keeps strong transactional consistency across regions, which is exactly the combination the requirements describe.
X: B=Cloud SQL with cross-region replicas: replicas only serve reads; all writes still go to one primary instance, so write capacity is limited by that single machine.
C=Bigtable with replication: Bigtable is a NoSQL wide-column store keyed by row key, without a relational schema or multi-row SQL transactions, and its replication between clusters is eventually consistent.
D=AlloyDB read pools: read pools scale reads only, and an AlloyDB cluster lives in one region, so it does not give globally consistent writes that scale out.
T: Relational + strongly consistent + horizontally scalable writes across regions = Spanner; Cloud SQL and AlloyDB scale reads, not writes.
V: Spanner, Cloud SQL, AlloyDB, Bigtable

@ GCP-ACE D2 T2.2 applied use-case
S: An energy company collects a reading every few seconds from two million smart meters. The application writes very high volumes of small records and reads them back by meter ID and time range with single-digit millisecond latency. The developers already use the Apache HBase API. Which service fits best?
A: Bigtable, with a row key that starts with the meter ID followed by a timestamp so each meter's readings sit together
B: BigQuery, with a table partitioned by day and clustered by meter ID so that range scans on recent readings stay quick
C: Firestore, with one document per reading stored in a collection per meter and a composite index on the timestamp field
D: Cloud SQL for MySQL, with a table indexed on meter ID and timestamp and several read replicas for the dashboard queries
K: A
G: ## What Bigtable is built for
Bigtable is a sparse, wide-column NoSQL database that scales to billions of rows and petabytes of data. It is ideal for **large amounts of single-keyed data with low latency** and high read and write throughput.
- Typical data: time series (sensor and server metrics), IoT, financial ticks, marketing events.
- Throughput grows with the number of nodes in the cluster, and clusters can be resized without downtime.
- It offers a supported extension of the **Apache HBase** client library for Java, so HBase applications move over with little change.
## Row key design
Bigtable has one index: the **row key**, and rows are stored sorted by it. A key such as `meter12345#20261030T0815` keeps one meter's readings next to each other, so "meter X between 08:00 and 09:00" is a fast range scan, while many meters writing at once still spread across the cluster.
W: Bigtable: it is designed for massive write throughput of small keyed records with low-latency reads by key range, it is a classic fit for time-series and IoT data, and it is compatible with the HBase API the team already uses.
X: B=BigQuery partitioned table: BigQuery is an analytics warehouse for SQL scans over large data sets; it is not meant to serve millisecond lookups to an application from a continuous stream of tiny writes.
C=Firestore documents per reading: Firestore is a document database for application data and has no HBase API; billions of tiny time-series documents are a poor fit compared with a wide-column store sized for this volume.
D=Cloud SQL with read replicas: a single MySQL primary takes every write, so millions of readings every few seconds would exceed what one instance can absorb, and replicas only help reads.
T: High-volume time-series or IoT data read by key with low latency, or an HBase workload, points to Bigtable.
V: Bigtable

@ GCP-ACE D2 T2.2 applied use-case
S: A firm is moving an internal finance application from its data center to Google Cloud. The application uses Microsoft SQL Server, and the team wants Google to handle backups, patching and high availability failover without changing the database engine. Which service should they use?
A: Cloud SQL for SQL Server, a managed instance that keeps the same engine and adds automated backups and a standby for failover
B: AlloyDB for PostgreSQL, a managed cluster whose engine takes SQL Server queries after the schema is imported unchanged
C: Spanner with the GoogleSQL dialect, a managed database whose schema accepts SQL Server tables after a direct backup restore
D: BigQuery with a dataset per database, a managed warehouse that runs the application's T-SQL transactions without changes
K: A
G: ## Managed relational engines on Google Cloud
- **Cloud SQL**: fully managed **MySQL, PostgreSQL and SQL Server**. Google runs the VM, storage, backups, maintenance and updates, and the high availability option adds a standby VM in another zone with automatic failover.
- **AlloyDB for PostgreSQL**: a PostgreSQL-compatible engine built by Google for demanding and analytical workloads.
- **Spanner**: a horizontally scalable relational database with its own GoogleSQL dialect or a PostgreSQL interface.
## Lift and shift
When the goal is "same engine, less administration", pick the managed service that runs that engine. Cloud SQL is the managed choice for an existing SQL Server database; you still manage schemas, users and data yourself with tools such as SQL Server Management Studio.
W: Cloud SQL for SQL Server: Cloud SQL is Google Cloud's managed service for SQL Server, so the engine stays the same while backups, maintenance and HA failover become Google's job.
X: B=AlloyDB for PostgreSQL: AlloyDB is PostgreSQL-compatible only; moving a SQL Server application to it is an engine migration with schema and query rewrites, not an unchanged move.
C=Spanner GoogleSQL: Spanner offers GoogleSQL and PostgreSQL dialects, not SQL Server compatibility, and it cannot restore a SQL Server backup.
D=BigQuery dataset: BigQuery is an analytics data warehouse; it does not run an application's T-SQL transactional workload and is not a SQL Server replacement.
T: Managed MySQL, PostgreSQL or SQL Server with the same engine = Cloud SQL.
V: Cloud SQL

@ GCP-ACE D2 T2.2 advanced tradeoff
S: A retailer's order application runs on PostgreSQL. Managers want reports that run heavy analytical queries directly on the live order data, without a nightly export, and without slowing down the order transactions. The team wants to keep using standard PostgreSQL clients. Which service should the team choose?
A: AlloyDB for PostgreSQL, using its columnar engine and read pool instances to run the analytical queries on live data
B: Cloud SQL for PostgreSQL, with a scheduled export to Cloud Storage and a BigQuery load job that runs every night
C: Bigtable, with the order data copied into it so that reports can scan wide rows by order date with low latency
D: Memorystore for Redis, with report results cached in memory so that repeated analytical queries return quickly
K: A
G: ## Transactional and analytical work on one database
Online transaction processing (OLTP) means many small reads and writes; analytics means large scans and aggregations. Running both on one ordinary PostgreSQL server makes them compete for the same resources, so teams often copy data to a warehouse every night, and reports are then a day old.
## AlloyDB for PostgreSQL
AlloyDB is a fully managed, **PostgreSQL-compatible** database designed for demanding workloads, including **Hybrid Transactional and Analytical Processing (HTAP)**: analytical queries against live transactional data without hurting performance.
- A **columnar engine** accelerates analytical queries.
- **Read pool instances** add load-balanced read nodes, so reports run away from the primary.
- Applications connect with standard PostgreSQL protocols and tools such as `psql` and pgAdmin.
W: AlloyDB with columnar engine and read pools: it runs analytics on current transactional data with the columnar engine, isolates the report load on read pools, and stays PostgreSQL-compatible for the existing clients.
X: B=Nightly export to BigQuery: it works for reporting, but the data is up to a day old, which is exactly the nightly export the managers want to avoid.
C=Copy into Bigtable: Bigtable has no SQL joins or PostgreSQL compatibility, and copying data into it adds a pipeline instead of querying the live order data.
D=Memorystore cache: a cache only speeds up results that were already computed; it does not run analytical queries, and the first run still loads the database.
T: PostgreSQL workload that needs fast analytics on live transactional data (HTAP) = AlloyDB.
V: AlloyDB for PostgreSQL

@ GCP-ACE D2 T2.2 applied use-case
S: A start-up is building a mobile and web app that stores user profiles and posts as JSON-like documents. The team wants a serverless database that scales automatically without capacity planning, charges for actual use, and works with the Firebase SDKs. Which database should they pick?
A: Firestore, a serverless document database that scales automatically and integrates with the Firebase platform
B: Bigtable, a wide-column database whose cluster nodes are sized up front and adjusted when traffic changes
C: Cloud SQL for MySQL, a relational instance with a JSON column type and storage that grows automatically
D: Memorystore for Redis, an in-memory store whose hashes hold each profile and post as a set of key fields
K: A
G: ## Document databases
A document database stores each record as a self-describing document (fields, nested maps, arrays) grouped in collections, close to how apps hold JSON objects in memory.
## Firestore
Firestore is Google Cloud's fully managed, **serverless** document database:
- no pre-provisioning: it **auto scales** compute and storage to the load, with a pay-per-use model
- strongly consistent queries, transactions, and multi-region replication options
- integration with **Firebase** for mobile and web apps (Firebase SDKs and console), plus a MongoDB-compatible API for MongoDB applications
W: Firestore: it is a serverless document database that scales without capacity settings, bills by use, and plugs into the Firebase SDKs the team wants.
X: B=Bigtable: Bigtable requires provisioned clusters with nodes and is built for very large key-value and time-series workloads, not as a serverless document backend for mobile apps.
C=Cloud SQL with JSON columns: Cloud SQL runs on an instance with chosen CPU and memory, so it is not serverless and needs capacity planning; it also has no Firebase integration.
D=Memorystore hashes: Memorystore is an in-memory cache for fast access, not the primary durable document store for user data, and it has no Firebase SDK integration.
T: Serverless, auto-scaling document database for mobile and web apps (Firebase) = Firestore.
V: Firestore

@ GCP-ACE D2 T2.2 applied use-case
S: Analysts at a media company need to run ad hoc SQL queries over several hundred terabytes of clickstream data and connect a BI tool to the results. The team does not want to provision, patch or scale any database servers. Which service should hold the data?
A: BigQuery, a serverless data warehouse that separates storage from compute and runs SQL queries without servers
B: Cloud SQL for PostgreSQL, with the largest machine type and read replicas added for each group of analysts
C: Spanner, with a regional instance configuration whose compute capacity is raised before the reporting runs
D: Bigtable, with an instance cluster sized for the full data set and its nodes scaled out during peak query hours
K: A
G: ## Data warehouse versus operational database
Operational databases (Cloud SQL, Spanner, Bigtable) serve applications: many small reads and writes. A **data warehouse** is built for large analytical scans and aggregations over huge data sets.
## BigQuery
BigQuery is a fully managed, **serverless** data platform:
- storage and compute are separated and scale independently, so you **do not provision or manually scale** resources
- you query with SQL (and Python); it can scan terabytes in seconds and petabytes in minutes
- it connects to BI tools through ODBC/JDBC drivers and client libraries
W: BigQuery: it is the serverless warehouse for ad hoc SQL over hundreds of terabytes, with no servers to provision, patch or scale.
X: B=Cloud SQL with large instances: Cloud SQL is an instance-based OLTP database that you size and manage; hundreds of terabytes of analytics scans would exceed what it is designed for.
C=Spanner regional instance: Spanner is a transactional database whose compute capacity you configure; it is not the tool for warehouse-style analytics, and capacity planning is still the team's job.
D=Bigtable cluster: Bigtable is a NoSQL key-value store read by row key; ad hoc SQL analytics for BI tools is BigQuery's role, and Bigtable nodes must be sized and scaled.
T: Ad hoc SQL analytics over large data with no infrastructure to manage = BigQuery.
V: BigQuery

@ GCP-ACE D2 T2.2 applied use-case
S: A web application on Compute Engine stores user sessions in a Cloud SQL database, and page loads slow down under heavy traffic. The developers already use an open source Redis client library and want a managed in-memory store that answers in under a millisecond, reached over a private IP in their VPC. What should they use?
A: Memorystore for Redis, a managed Redis-protocol store that the existing client can use with no code changes
B: Bigtable with an SSD cluster, a managed wide-column store that the existing client reaches through its HBase API
C: Firestore in Native mode, a managed document store that the existing client reaches through its MongoDB API
D: A Cloud SQL read replica, a managed copy of the database that the existing client reaches over the same private IP
K: A
G: ## Why caches help
A cache keeps frequently read data such as sessions in memory, so the application no longer goes to a disk-based database for every page. In-memory stores answer in well under a millisecond.
## Memorystore
Memorystore provides fully managed in-memory data stores:
- **Memorystore for Redis** is fully Redis-protocol compliant, so applications that use open source Redis move over **without code changes**; typical uses are caching and session management.
- Instances are reached on **private IPs** from an authorized VPC network, and the Standard Tier replicates across zones with automatic failover.
- Memorystore for Valkey and Memorystore for Memcached are other engines in the same family.
W: Memorystore for Redis: it is the managed Redis-compatible in-memory store, reachable on a private IP, and the team's existing Redis client works unchanged for sub-millisecond session reads.
X: B=Bigtable SSD cluster: Bigtable is a disk-based NoSQL database reached through its own or HBase clients, not through a Redis client, and it is not an in-memory session cache.
C=Firestore MongoDB API: Firestore is a durable document database with single-digit millisecond reads, and its MongoDB-compatible API does not accept Redis clients.
D=Cloud SQL read replica: a replica moves some read load but is still a disk-based relational database reached with SQL, not a Redis-compatible in-memory store.
T: Managed in-memory cache with Redis compatibility for sessions and hot data = Memorystore.
V: Memorystore for Redis

@ GCP-ACE D2 T2.2 applied comparison
S: A logistics company runs dozens of services that produce and consume events with Apache Kafka client libraries and Kafka Connect, on a self-managed cluster. They want Google Cloud to run the cluster for them without rewriting producers or consumers. Which service should they choose?
A: Google Cloud Managed Service for Apache Kafka, which runs Kafka clusters that the existing Kafka clients connect to
B: Pub/Sub, whose topics and subscriptions receive the existing Kafka producer and consumer calls with no code changes
C: Dataflow, whose streaming jobs act as Kafka brokers that the existing Kafka clients connect to as their bootstrap servers
D: Memorystore for Redis, whose streams store the events and accept the existing Kafka producer calls with no code changes
K: A
G: ## Two messaging options on Google Cloud
- **Pub/Sub** is Google's own serverless, asynchronous messaging service. It uses its own API with **per-message** leasing instead of Kafka-style partitions. Moving Kafka applications to it means changing the producer and consumer code.
- **Google Cloud Managed Service for Apache Kafka** runs real **open source Apache Kafka** clusters for you. You set the total vCPU and memory, the service provisions brokers, handles patching and storage (tiered storage), and exposes private bootstrap URLs in your VPCs through Private Service Connect. Clients authenticate with SASL (IAM principals) or mTLS.
## Choosing
If code already uses Kafka APIs and tools, the managed Kafka service keeps them unchanged. If you are building new event-driven services and want no cluster to size, Pub/Sub is usually simpler.
W: Managed Service for Apache Kafka: it runs genuine Apache Kafka clusters managed by Google, so existing Kafka clients and tooling keep working while the team stops operating brokers.
X: B=Pub/Sub without code changes: Pub/Sub has its own API and per-message delivery model; Kafka producers and consumers must be rewritten or bridged to use it.
C=Dataflow as brokers: Dataflow runs Apache Beam processing pipelines; it can read from and write to Kafka but is not a Kafka broker that clients connect to.
D=Redis streams: Memorystore is an in-memory store with the Redis protocol; it does not speak the Kafka protocol and is not a durable event log for Kafka clients.
T: Keep Kafka APIs but drop cluster operations = Managed Service for Apache Kafka; new Google-native messaging = Pub/Sub.
V: Managed Service for Apache Kafka, Pub/Sub

@ GCP-ACE D2 T2.2 applied use-case
S: A game studio wants to collect gameplay events from thousands of game servers, enrich and aggregate them in near real time, and write the results into BigQuery. The team wants fully managed services with no clusters to run. Which TWO services should they combine? (Select TWO)
A: Pub/Sub, to receive the events asynchronously from the game servers and buffer them for downstream processing
B: Dataflow, to run a streaming Apache Beam pipeline that reads the events, transforms them and writes to BigQuery
C: Memorystore for Redis, to hold the raw events in memory and run the enrichment and aggregation step in the cache
D: Cloud SQL for MySQL, to stage every raw event in a table and run scheduled stored procedures that load BigQuery
E: Filestore, to collect the events as files on a shared NFS share that BigQuery reads directly as the source table
K: A,B
G: ## The common streaming pipeline on Google Cloud
A classic pattern is **Pub/Sub → Dataflow → BigQuery**:
- **Pub/Sub** decouples producers from consumers. Publishers send messages to a topic without waiting for anyone to process them; subscribers receive them asynchronously. It ingests events from many clients at once.
- **Dataflow** is the fully managed runner for **Apache Beam** pipelines. One programming model covers batch and streaming; it provisions and autoscales worker VMs itself, processes each record exactly once by default, and writes to sinks such as BigQuery.
- **BigQuery** stores the results for SQL analysis.
## Example
Game servers publish `match_finished` events to a topic. A streaming Dataflow job reads the subscription, joins player data, computes per-minute aggregates and appends them to a BigQuery table.
W: A=Pub/Sub: it is the managed, asynchronous ingestion layer that accepts events from thousands of servers and decouples them from the processing step.
B=Dataflow: it runs the streaming Beam pipeline that enriches and aggregates the events and writes to BigQuery, with workers managed and autoscaled by the service.
X: C=Memorystore for enrichment: Memorystore is a cache for fast key lookups; it does not run pipelines, and holding raw events in memory is not a durable ingestion design.
D=Cloud SQL staging: an instance-based relational database adds a bottleneck and batch delays, and stored procedures in Cloud SQL do not load BigQuery; this is neither near real time nor serverless.
E=Filestore share: Filestore is an NFS file server for VMs and GKE; BigQuery does not use an NFS share as a table source, and files on a share are not a streaming pipeline.
T: Streaming ingestion and transformation into BigQuery = Pub/Sub for events plus Dataflow for processing.
V: Pub/Sub, Dataflow, BigQuery

@ GCP-ACE D2 T2.2 applied use-case
S: A media team runs a rendering application on a managed instance group of Linux VMs and on a GKE cluster. All VMs and Pods must read and write the same POSIX file tree at the same time over NFS, with file locking. Which storage should the team provision?
A: A Filestore instance, whose NFS file share every VM and Pod can mount read-write at the same time
B: A zonal Persistent Disk attached to every VM, which mounts it read-write as a shared POSIX file system
C: A Cloud Storage bucket mounted with Cloud Storage FUSE, which provides file locking and full POSIX semantics
D: A Memorystore for Redis instance, whose keys each hold one file so that every VM and Pod reads the same data
K: A
G: ## Block, file and object storage
- **Block storage** (Persistent Disk, Hyperdisk) is a disk attached to a VM. Its options for several writers at once are limited.
- **Object storage** (Cloud Storage) stores whole objects through an API. Cloud Storage FUSE can mount a bucket as a file system but lacks some file-system behavior.
- **File storage** (Filestore) is a managed NFS file server that many clients share at once.
## Filestore
Filestore instances are fully managed file servers that Compute Engine VMs, GKE clusters, Cloud Run services and on-premises machines can mount over **NFSv3** (all tiers) or **NFSv4.1**. It supports **multiple readers and writers**, so GKE PersistentVolumes can be mounted read-write by many nodes. Unlike Cloud Storage FUSE, it offers **POSIX compliance, hard links and file locking**.
W: Filestore: it is the managed NFS file server that many VMs and GKE Pods can mount read-write at once, with POSIX semantics and file locking.
X: B=Shared zonal Persistent Disk: a Persistent Disk is block storage with only limited multi-writer options; it is not a file share that many VMs and Pods mount read-write together.
C=Cloud Storage FUSE: FUSE gives some file-system semantics over a bucket, but the docs list POSIX compliance, hard links and file locking as things it lacks compared with Filestore.
D=Memorystore keys as files: an in-memory key-value cache is not a file system; applications cannot mount it over NFS or lock files in it.
T: Many VMs or Pods sharing one read-write POSIX file system over NFS = Filestore.
V: Filestore

@ GCP-ACE D2 T2.2 applied comparison
S: An engineering firm is moving Windows file servers to Google Cloud. Users on Windows desktops map the shares as network drives over SMB, and Linux build servers mount other volumes over NFS. The firm wants one fully managed service that provides both protocols. Which service should they choose?
A: Google Cloud NetApp Volumes, which provides managed volumes over SMB and NFS protocols with snapshots and backups
B: Filestore, using the regional tier for continuous availability and mounting the shares from Windows over SMB
C: Cloud Storage with Cloud Storage FUSE, mounting each bucket as a network drive on the Windows desktops over SMB
D: Google Cloud Managed Lustre, mounting its parallel file system on both the Windows desktops and the build servers
K: A

- **Filestore**: managed NFS file servers (NFSv3 on all tiers, NFSv4.1 on zonal, regional and enterprise tiers). No SMB.
- **Google Cloud NetApp Volumes**: fully managed file and block storage with built-in **NFSv3/v4.1/v4.2, SMB, iSCSI** and other protocols, plus automated snapshots, backups, auto-tiering and volume replication. It helps move enterprise and Windows workloads without re-architecting.

Protocol is often the first filter: Windows file shares mapped as network drives use **SMB**, so the service must offer SMB.
W: NetApp Volumes: it is the managed service that offers SMB for the Windows desktops and NFS for the Linux servers, with enterprise features such as snapshots and backups.
X: B=Filestore regional tier: Filestore supports NFS protocols only, so Windows clients cannot map its shares over SMB.

@ GCP-ACE D2 T2.2 applied use-case

Google Cloud Managed Lustre is a fully managed **parallel file system optimized for AI and HPC**, built with DDN:

@ GCP-ACE D2 T2.2 applied use-case
S: A finance team continuously uploads transaction exports to a bucket and runs an analysis job on them about once a month. The files must stay online with fast access, and the team wants to lower at-rest storage cost without paying for retrievals more often than needed. Which storage class should the bucket use by default?
A: Nearline storage, which is meant for data read or modified about once a month and has a 30-day minimum storage duration
B: Standard storage, which is meant for data read less than once a year and has a 365-day minimum storage duration
C: Coldline storage, which is meant for data read or modified several times every week and has no minimum storage duration
D: Archive storage, which is meant for data read about once a month and has offline retrieval that takes several hours
K: A
G: ## Cloud Storage classes
Every object has a storage class. The colder the class, the lower the at-rest cost, but the higher the access cost and the longer the **minimum storage duration**:
- **Standard**: hot data, frequent access; no minimum storage duration, no retrieval fees
- **Nearline**: about once a month or less; 30-day minimum; retrieval fees
- **Coldline**: at most once a quarter; 90-day minimum; retrieval fees
- **Archive**: less than once a year; 365-day minimum; retrieval fees
These four classes keep data online with millisecond access and the same durability; only availability, cost model and these trade-offs differ. (A fifth class, Rapid storage, is a high-performance class for zonal buckets only, aimed at I/O-intensive AI and analytics work, not at lowering storage cost.)
## Example from the docs
Continuously adding files and analyzing them once a month is the docs' own example of a good fit for Nearline.
W: Nearline storage: monthly access is exactly its intended pattern, it lowers at-rest cost compared with Standard, and its 30-day minimum suits files kept at least a month.
X: B=Standard for yearly reads: Standard is the class for frequently accessed hot data and has no minimum storage duration; the yearly-access, 365-day description belongs to Archive.
C=Coldline weekly with no minimum: Coldline is for data accessed at most once a quarter and has a 90-day minimum; frequent weekly reads would add retrieval fees.
D=Archive with offline retrieval: Archive is for data accessed less than once a year, and its data is available in milliseconds; Cloud Storage has no offline retrieval delay.

@ GCP-ACE D2 T2.2 applied troubleshooting
S: A bucket holds 2 TB of log files in Standard storage. An engineer changes the bucket's default storage class to Coldline to save money, but a week later every existing object still shows the Standard class. What explains this, and how can the engineer change the existing objects?
A: The default class applies only to objects added later; rewrite the existing objects with gcloud storage objects update and --storage-class

G: ## Default class versus object class
Storage class is **object metadata**. A bucket's **default storage class** is only what new objects get when the upload does not specify a class.
- Changing the bucket's default **does not affect objects that already exist**.
- To change existing objects, **rewrite** them with the new class, for example `gcloud storage objects update gs://BUCKET/OBJECT --storage-class=COLDLINE`, or let **Object Lifecycle Management** change them by age.
- Autoclass is a bucket feature that manages transitions automatically.
## Cost note
A rewrite replaces the object, so early-deletion charges apply if the old class had a minimum duration. Lifecycle-driven class changes do not trigger them.
W: Default applies to new objects only: existing objects keep their class, and rewriting them with `gcloud storage objects update --storage-class` (or a lifecycle rule) changes them.
X: B=Background conversion: Cloud Storage never converts existing objects when the default changes; waiting changes nothing.
C=Uniform bucket-level access: that setting controls permissions (IAM only instead of ACLs) and has nothing to do with storage classes.
D=Multi-region without Coldline: Coldline is available in multi-regions, dual-regions and regions; location type is not the reason.
T: Changing a bucket's default class affects only new uploads; existing objects need a rewrite or a lifecycle rule.

Google's guidance for transfers into Cloud Storage:

## `gcloud storage cp`

D=buckets create with --placement: this creates a bucket; `--placement` lists the regions of a custom dual-region and copies no data.

@ GCP-ACE D2 T2.2 applied use-case
S: Each night a job drops a CSV file with one header row into gs://acme-orders/daily/. An engineer writes a bq load command that adds the file's rows to the existing table orders.history, which has a schema and holds years of data that must not be lost. Which TWO choices must the command make? (Select TWO)
A: Use --skip_leading_rows=1 so that the header row is not loaded as a data row into the table
B: Append the rows, by passing --noreplace or by leaving out --replace, so that existing rows stay
C: Pass --replace so that the existing schema is kept and new rows are written alongside the old data
D: Pass --time_partitioning_type=DAY on each run so that the existing table is converted to daily partitions
E: Pass --source_format=NEWLINE_DELIMITED_JSON so that the header line is read as the names of the columns
K: A,B
G: ## Writing into an existing table
A load into an existing table either **appends** or **overwrites**:
- **Append** (the default): `--noreplace` or `--replace=false`, or no flag at all (`WRITE_APPEND`)
- **Overwrite**: `--replace` or `--replace=true` (`WRITE_TRUNCATE`)
Overwriting erases all existing data in the table before writing and also deletes the table schema, row-level security and any Cloud KMS key.
## Header rows
`--skip_leading_rows` sets how many header rows to skip at the top of a CSV file. The default is `0`, so a header would otherwise be loaded as data (or fail type conversion).
## Example
`bq load --source_format=CSV --skip_leading_rows=1 --noreplace orders.history gs://acme-orders/daily/2026-10-30.csv`
W: A=--skip_leading_rows=1: it skips the single header line, which would otherwise be treated as data because the default is 0.
B=Append: `--noreplace` (or omitting `--replace`, since append is the default) adds the new rows and keeps the years of history.
X: C=--replace: `--replace` overwrites the table, erasing all existing data and even the schema, which is exactly what must not happen.
D=--time_partitioning_type on each run: the partitioning specification of an existing table cannot be changed, and partitioning has nothing to do with appending one file.
E=JSON source format: the file is CSV, so declaring newline-delimited JSON would make the parse fail; header handling for CSV is `--skip_leading_rows`.
T: Nightly CSV into an existing table: `--skip_leading_rows=1` for the header, append (default or `--noreplace`); `--replace` truncates.

@ GCP-ACE D2 T2.2 advanced tradeoff
S: A payments company stores transaction receipts in Cloud Storage. The bucket must keep serving reads and writes with the same bucket name if one region goes down, the data must stay in two regions the company chooses, and newly written objects must be copied to the second region within 15 minutes. Which TWO settings meet these needs when the bucket is created? (Select TWO)
A: A dual-region location, either a predefined pair or a configurable dual-region whose two regions are set with --placement
B: The recovery point objective set to ASYNC_TURBO, which turns on turbo replication for the dual-region bucket
C: A multi-region location such as EU, with turbo replication enabled so that copies reach a second region in minutes
D: A single-region location, with Object Versioning enabled so that earlier versions of objects can be restored later
E: A single-region location, with Autoclass enabled so that objects move to colder classes in a second region over time
K: A,B
G: ## Bucket location types
- **Region**: redundancy across zones in one region (synchronous); lowest storage price; a regional outage affects it
- **Dual-region**: a specific **pair of regions** (asynchronous); you choose the regions, as a predefined pair such as `NAM4` or a configurable pair set with `--placement`
- **Multi-region**: a large area such as `US`, `EU` or `ASIA` (asynchronous); Google picks the data centers inside the area
Dual-regions and multi-regions are active-active: on a regional outage the same bucket keeps serving data with no change of storage path (RTO of zero).
## Replication speed
- **Default replication** targets 99.9% of new objects within one hour and 100% within 12 hours.
- **Turbo replication** targets 100% of new objects within **15 minutes**, and is **only available for dual-region buckets**. On the CLI it is `--recovery-point-objective=ASYNC_TURBO` (alias `--rpo`).
## Example
`gcloud storage buckets create gs://acme-receipts --location=EU --placement=europe-west1,europe-north1 --rpo=ASYNC_TURBO` (the regions must form a valid pair for that location code).
W: A=Dual-region location: it stores the data in two regions the company picks and keeps the same bucket serving through a regional outage.
B=ASYNC_TURBO: turbo replication is the setting that targets replication of all new objects within 15 minutes; the default only targets 12 hours for 100%.
X: C=Multi-region with turbo: turbo replication is only available for dual-region buckets, and in a multi-region the company cannot choose the specific regions.
D=Regional with Object Versioning: a regional bucket keeps data in one region, so a regional outage stops it; versioning protects against overwrites and deletes, not outages.
E=Regional with Autoclass: Autoclass changes storage classes inside the same bucket location; it never copies objects to another region.
T: Chosen pair of regions + 15-minute RPO = dual-region bucket with turbo replication (`--rpo=ASYNC_TURBO`); turbo is dual-region only.
V: Cloud Storage
