@ GCP-ACE D4 T4.2 applied use-case
S: A team in project shop-prod needs an identity for a new invoice-export job and wants to create it from Cloud Shell with a friendly name and a note saying who owns it. Which command creates the service account, and what email address will it have?
A: gcloud iam service-accounts create invoice-export --display-name="Invoice export" --description="Owner: finance-eng"; the email is invoice-export@shop-prod.iam.gserviceaccount.com
B: gcloud iam service-accounts keys create invoice-export --display-name="Invoice export" --description="Owner: finance-eng"; the email is invoice-export@shop-prod.iam.gserviceaccount.com
C: gcloud projects add-iam-policy-binding shop-prod --member=serviceAccount:invoice-export --role=roles/iam.serviceAccountUser; the email is invoice-export@shop-prod.gserviceaccount.com
D: gcloud iam service-accounts create invoice-export --display-name="Invoice export" --description="Owner: finance-eng"; the email is invoice-export@developer.gserviceaccount.com
K: A
G: ## Creating a user-managed service account
A **service account** is an account for a workload rather than a person. You create one in a project with:
`gcloud iam service-accounts create SA_NAME --description="..." --display-name="..."`
- `SA_NAME` is the **service account ID**: 6 to 30 characters, lowercase letters, digits and dashes. It cannot be changed after creation.
- `--display-name` is a friendly name and `--description` is an optional note; both are good places to record the purpose or an owner, as the best practices recommend.
- The email address is always `SA_NAME@PROJECT_ID.iam.gserviceaccount.com`.
## Example
In project `shop-prod`, the ID `invoice-export` gives `invoice-export@shop-prod.iam.gserviceaccount.com`. Creating the account grants it nothing: you then grant it roles on the resources it needs.
Different domains belong to other kinds of accounts: `PROJECT_NUMBER-compute@developer.gserviceaccount.com` is the Compute Engine default service account, created automatically when the Compute Engine API is enabled.
W: Service-accounts create: this is the command that creates a user-managed service account, the display name and description record its purpose and owner, and the email follows the SA_NAME@PROJECT_ID.iam.gserviceaccount.com pattern.
X: B=Keys create: `gcloud iam service-accounts keys create` downloads a key for an existing account into a file; it does not create the account and has no display-name or description flags.
C=Project policy binding: adding a binding only grants a role to an existing principal; it cannot create the account, and user-managed accounts use the iam.gserviceaccount.com domain, not gserviceaccount.com alone.
D=Developer domain: the command is right but the email is wrong; developer.gserviceaccount.com is used by the Compute Engine default service account, whose local part is the project number followed by -compute.
T: Create with `gcloud iam service-accounts create ID`; the email is ID@PROJECT_ID.iam.gserviceaccount.com, and the ID cannot be renamed later.

@ GCP-ACE D4 T4.2 applied troubleshooting
S: A deployment script runs gcloud iam service-accounts create and, on the very next line, grants the new service account a role on a Cloud Storage bucket. About half of the runs fail at the second step with an error saying the service account does not exist, and a manual rerun a minute later always works. What is the best fix?
A: Grant the role on the whole project instead of on the bucket, because project-level bindings accept service accounts that are still being provisioned
B: Create a service account key right after creating the account, because the account becomes active only after its first key has been generated
C: Retry the role grant with exponential backoff, because a new service account can take 60 seconds or more to become visible to other requests
D: Run the script with the Owner role instead of Service Account Admin, because only owners can grant roles to an account in the same minute it was created
K: C
G: ## Eventual consistency after creation
IAM read operations are **eventually consistent**. The docs say that after you create a service account you might need to wait **60 seconds or more** before you use it: until then, other requests may not see it yet and fail with a not-found error.
The documented fix is to **retry with exponential backoff** (wait a little, retry, wait longer, retry) rather than fail the whole run.
## What this is not
- It is not a permission problem: the same command works a minute later with the same caller.
- Nothing has to be "activated": a new service account is enabled as soon as it exists; it just needs time to propagate.
- Broadening the grant to the project only adds privilege; the new principal is just as invisible to the project policy as to the bucket policy.
W: Retry with backoff: the failure is caused by the documented delay before a new service account becomes visible, so retrying with exponential backoff makes the script reliable without changing any permissions.
X: A=Project-level grant: project policies are subject to the same visibility delay, and granting at project level gives the account far more access than the bucket it needs.
B=Create a key first: a service account is usable without any key, and creating long-lived keys adds risk; the docs recommend avoiding keys whenever possible.
D=Owner role: the error is a timing problem, not missing permissions, and using a legacy basic role like Owner for automation breaks least privilege without fixing the delay.
T: A newly created service account may take 60+ seconds to be usable; retry with exponential backoff instead of failing.
V: IAM

@ GCP-ACE D4 T4.2 applied definition
S: While reviewing project analytics-dev, an engineer sees three identities in IAM: etl-runner@analytics-dev.iam.gserviceaccount.com, 4815162342-compute@developer.gserviceaccount.com and service-4815162342@gcp-sa-pubsub.iam.gserviceaccount.com. How should each be classified?
A: All three are service agents, because every service account that Google Cloud creates or uses for a project is created and managed by Google on the customer's behalf
B: A user-managed service account; the Compute Engine default service account, which the team must manage; and a service agent that Google creates and manages for Pub/Sub
C: A service agent for an ETL product; a user-managed account the team created for Compute Engine; and the default service account that Pub/Sub attaches to subscriptions
D: A user-managed service account; a service agent that Google manages for Compute Engine; and a default service account that the Pub/Sub API attaches to the team's push endpoints
K: B
G: ## Three kinds of service accounts
- **User-managed service accounts**: you create them; email `NAME@PROJECT_ID.iam.gserviceaccount.com`. You control their roles, keys and lifecycle.
- **Default service accounts**: user-managed accounts that a service creates automatically when you enable it, for example the **Compute Engine default service account** `PROJECT_NUMBER-compute@developer.gserviceaccount.com` and the App Engine default `PROJECT_ID@appspot.gserviceaccount.com`. Google creates them, but **you are responsible for managing them** (roles, disabling).
- **Service agents**: Google-created and Google-managed accounts that let a service act on your resources, usually `service-PROJECT_NUMBER@gcp-sa-SERVICE.iam.gserviceaccount.com`. They live outside your project, so they do not appear in the project's Service Accounts list, and the IAM page hides their grants unless you choose to include Google-provided role grants.
## Reading the emails
The `gcp-sa-pubsub` domain marks the Pub/Sub service agent; `-compute@developer` marks the Compute Engine default account; the plain `iam.gserviceaccount.com` address with the project ID is one the team created.
W: User-managed, default, service agent: the project-ID address is user-managed, the -compute@developer address is the Compute Engine default service account (user-managed, created automatically), and the gcp-sa-pubsub address is the Pub/Sub service agent that Google manages.
X: A=All service agents: only Google-managed accounts that act for a service are service agents; the team created etl-runner itself, and the default account is managed by the customer.
C=Swapped roles: etl-runner uses the user-managed email pattern, the developer.gserviceaccount.com account is the Compute Engine default, and Pub/Sub has no default service account of its own.
D=Compute default as service agent: the Compute Engine default service account is a user-managed default account that the team manages, and the gcp-sa-pubsub identity is a Google-managed service agent, not a default account.
T: NAME@PROJECT_ID.iam = user-managed; NUMBER-compute@developer = Compute Engine default (you manage it); service-NUMBER@gcp-sa-* = service agent (Google manages it).
V: IAM, Compute Engine, Pub/Sub

@ GCP-ACE D4 T4.2 advanced tradeoff
S: A security review finds that in several older projects the Compute Engine default service account holds the Editor role, and new projects keep getting the same grant. The organization was created in 2022. What should the cloud engineer do to stop the automatic grant and fix the existing projects?
A: Delete the Compute Engine default service account in every project, because a new default account without the Editor role is created the next time a VM starts
B: Disable the Compute Engine API in each project and enable it again, which recreates the default service account with only the roles that its VMs need
C: Enforce iam.automaticIamGrantsForDefaultServiceAccounts on each existing project, which also removes the Editor role from accounts that already hold it
D: Enforce iam.automaticIamGrantsForDefaultServiceAccounts at the organization, then replace Editor on existing default accounts with narrower roles
K: D
G: ## Why the default account is risky
When the Compute Engine API is enabled, Google creates the **Compute Engine default service account**. Depending on the organization policy, it may automatically receive the **Editor** role (`roles/editor`, a legacy basic role) on the project, and every VM created without an explicit service account uses it. Editor can read and modify almost everything in the project, which is far more than most VMs need.
## The organization policy constraint
`constraints/iam.automaticIamGrantsForDefaultServiceAccounts` stops the automatic Editor grant to default service accounts in new projects.
- Set it at the **organization or a folder** to cover many projects at once.
- It is **enforced by default** only for organizations created after **May 3, 2024**; older organizations must enforce it themselves.
- Applying it **does not remove Editor** from default accounts that already have it: for those, grant narrower roles and revoke Editor (Policy Simulator helps you preview the impact).
W: Constraint plus manual cleanup: enforcing the constraint at the organization stops future automatic grants everywhere, and replacing Editor with narrower roles fixes the existing accounts, which the constraint does not touch.
X: A=Delete the default account: a deleted default service account is not recreated, so VMs and services relying on it break; the docs suggest disabling rather than deleting when in doubt.
B=Disable and enable the API: this does not create a fresh, least-privilege account; the roles and the risk stay with the existing account, and disabling the API can disrupt running resources.
C=Constraint removes existing Editor: the constraint only affects automatic grants from now on; existing Editor bindings stay until you remove them yourself, and per-project enforcement misses new projects.
T: Enforce iam.automaticIamGrantsForDefaultServiceAccounts high in the hierarchy, then replace Editor on existing default accounts by hand.
V: IAM, Organization Policy Service, Compute Engine

@ GCP-ACE D4 T4.2 applied use-case
S: Three applications in project retail-prod (a web API on Cloud Run, a batch job on a Compute Engine VM and a reporting service) all run as the Compute Engine default service account. The security team wants least privilege and wants audit logs to show which application made each change. What should the cloud engineer do?
A: Keep the shared default service account but replace its Editor role with the union of the predefined roles that the three applications need between them
B: Create a dedicated user-managed service account for each application, grant each only the roles its application needs, and attach it to that workload
C: Create one new user-managed service account for all three applications, so that the default service account can be disabled without changing any application code
D: Keep the default service account and add a distinct access scope on each workload, so that audit logs record which scope each application request used
K: B
G: ## Single-purpose service accounts
The IAM best practices recommend **one service account per application** instead of a shared account:
- **Least privilege**: each account gets only the roles its application needs. A shared account accumulates the union of every app's needs, so any one compromised app can do everything the others can.
- **Traceability**: Cloud Audit Logs record the *service account* that made a call, not the application. If three apps share one account, you cannot tell which one changed a resource.
- **Lifecycle**: when an app is retired, its dedicated account can be disabled and deleted safely.
Avoid the default service accounts for this reason: they are shared by default by every VM or Cloud Run service that does not name another account.
## How to do it
Create `api-sa`, `batch-sa` and `report-sa`, grant each narrow roles on the specific resources, and attach them when deploying (for example `gcloud run deploy --service-account` or `gcloud compute instances create --service-account`).
W: Dedicated account per application: separate accounts let each app have only its own roles, and audit log entries name the account, which now identifies the application.
X: A=Shared default with union of roles: removing Editor helps, but every app still holds the other apps' permissions, and audit logs still show one identity for all three applications.
C=One new shared account: replacing one shared account with another keeps the same problems: combined permissions and no way to tell the applications apart in the logs.
D=Access scopes per workload: scopes are a coarse legacy limit on VMs, not identities; audit logs record the authenticated principal, and Cloud Run does not use access scopes at all.
T: One dedicated, minimally privileged service account per application: least privilege plus audit logs that identify the app.
V: IAM, Cloud Audit Logs, Cloud Run, Compute Engine

@ GCP-ACE D4 T4.2 applied use-case
S: An engineer is creating a VM that must read and write objects in one Cloud Storage bucket. Following Google's recommended practice, the engineer created vm-uploader@media-prod.iam.gserviceaccount.com. How should the VM be created and authorized?
A: Create it with --service-account=vm-uploader@media-prod.iam.gserviceaccount.com --scopes=cloud-platform, then grant that account Storage Object User on the bucket only
B: Create it with the default service account and --scopes=storage-rw, then rely on the read-write storage scope to limit the VM to Cloud Storage access only
C: Create it with --service-account=vm-uploader@media-prod.iam.gserviceaccount.com --scopes=storage-rw, then grant that account Storage Admin on the project
D: Create it with --no-service-account, then copy a key file for vm-uploader onto the boot disk so the application can authenticate when it starts
K: A
G: ## Two controls on a VM's access
An application on a Compute Engine VM authenticates as the **service account attached to the VM**. Its effective access is limited by two things, and both must allow a call:
- **IAM roles** granted to the service account (fine-grained: a role on one bucket).
- **Access scopes** set on the VM (coarse, legacy OAuth limits per API, such as read-only Cloud Storage).
## The recommended pattern
Set the full `cloud-platform` scope and control access with IAM roles only:
`gcloud compute instances create VM --service-account=SA_EMAIL --scopes=cloud-platform`
Then grant the account a role on the specific resource, for example Storage Object User (`roles/storage.objectUser`) on the bucket. Scopes cannot restrict access to a single bucket; IAM can.
Attaching the account also means no key files: the VM's metadata server hands out short-lived tokens automatically.
W: Dedicated account, cloud-platform scope, bucket role: the attached account gives the VM an identity without keys, the full scope leaves authorization to IAM as recommended, and a role on the one bucket keeps privilege minimal.
X: B=Default account with storage scope: scopes are coarse and cannot limit access to one bucket, and the default account may hold Editor on the project, so the VM gets far more than it needs.
C=Storage Admin on the project: a project-wide admin role lets the VM manage every bucket and its policies, which breaks least privilege; the narrow scope does not make up for the broad role.
D=No service account plus key file: a key copied onto a disk is a long-lived secret that can leak with an image or snapshot; attaching the account avoids keys entirely.
T: Attach a dedicated service account with the cloud-platform scope, and do the real restriction with IAM roles on specific resources.
V: Compute Engine, IAM, Cloud Storage

@ GCP-ACE D4 T4.2 applied troubleshooting
S: A VM was created with the default access scopes and a dedicated service account. The account was later granted Storage Object Admin on a bucket, yet the application on the VM still gets 403 errors when it uploads objects with the client library, while reads work. What should the engineer do?
A: Grant the service account the Storage Admin role on the project, because Storage Object Admin on a bucket does not include permission to create new objects
B: Re-create the service account with the same name, because role changes do not reach an account that is already attached to a running VM
C: Stop the VM, set its access scopes to cloud-platform while keeping the same service account, and start the VM again
D: Add a firewall rule allowing egress to storage.googleapis.com on port 443, because the default scopes block outbound writes to Cloud Storage
K: C
G: ## Scopes can block what IAM allows
On a Compute Engine VM, requests made through gcloud and the client libraries use OAuth **access scopes** set on the VM. A call succeeds only if **both** the service account's IAM roles and the VM's scopes allow it.
The **default scopes** of a new VM include **read-only Cloud Storage** (`devstorage.read_only`), plus a few logging and monitoring scopes. With those defaults, even an account with Storage Object Admin cannot write objects from that VM: the docs give exactly this example.
## Fixing it
Changing a VM's service account or scopes requires the VM to be **stopped**:
`gcloud compute instances stop VM`
`gcloud compute instances set-service-account VM --service-account=SA_EMAIL --scopes=cloud-platform`
then start the VM. Afterwards IAM roles alone decide access, which is the recommended practice.
W: Stop, set cloud-platform, start: the read-only storage scope is what blocks uploads; scopes can be changed only on a stopped VM, and with cloud-platform the existing Storage Object Admin role takes effect.
X: A=Storage Admin on the project: Storage Object Admin already includes creating objects; the block comes from the scope, so a broader role changes nothing except adding excess privilege.
B=Re-create the account: IAM changes apply to the existing account without re-creating it, and a re-created account with the same name is a new identity that loses the existing bindings.
D=Egress firewall rule: reads already reach Cloud Storage over the same path, and access scopes are an authorization limit, not a network control.
T: Default VM scopes make Cloud Storage read-only; stop the VM and set the cloud-platform scope, then let IAM roles decide.
V: Compute Engine, Cloud Storage, IAM

@ GCP-ACE D4 T4.2 applied troubleshooting
S: Developer Mina has the Cloud Run Developer role on project api-prod. Her deployment with gcloud run deploy orders --image=IMAGE_URL --service-account=orders-sa@api-prod.iam.gserviceaccount.com fails with a permission error mentioning iam.serviceAccounts.actAs. What is the least-privilege fix?
A: Grant Mina the Service Account Token Creator role on the project, so that she can create tokens for any service account she deploys with
B: Grant Mina the Service Account Admin role on orders-sa, so that she can manage the account's settings and attach it to services
C: Grant orders-sa the Cloud Run Admin role on the project, so that the service identity can deploy revisions of itself on Mina's behalf
D: Grant Mina the Service Account User role on orders-sa only, which contains the actAs permission needed to attach that account to a service
K: D
G: ## Attaching a service account needs actAs
When you deploy a Cloud Run service (or create a VM, a Dataflow job, and so on) that runs **as** a service account, you are letting that resource use the account's permissions. IAM therefore checks that *you* hold `iam.serviceAccounts.actAs` on that service account.
- The predefined role with this permission is **Service Account User** (`roles/iam.serviceAccountUser`).
- Grant it **on the specific service account** (the account is a resource with its own allow policy), not on the project, which would cover every service account in it.
Example:
`gcloud iam service-accounts add-iam-policy-binding orders-sa@api-prod.iam.gserviceaccount.com --member=user:mina@example.com --role=roles/iam.serviceAccountUser`
## Two separate sets of permissions
The deployer needs actAs on the account; the account itself needs roles for whatever the service calls at runtime.
W: Service Account User on orders-sa: this role contains actAs, the exact permission in the error, and granting it on the one account lets Mina attach only orders-sa and no other service account.
X: A=Token Creator on the project: it lets Mina impersonate every service account in the project, which is far broader, and it is not the role the Cloud Run docs require for attaching a service identity.
B=Service Account Admin: it is meant for managing accounts (edit, disable, delete, change policies) and gives more control than deployment needs; the role documented for attaching is Service Account User.
C=Cloud Run Admin for the account: the error concerns the deployer's permission over the account; granting the runtime identity admin rights adds privilege and does not give Mina actAs.
T: Deploying a resource that runs as a service account requires actAs on that account: grant Service Account User on the account itself.

@ GCP-ACE D4 T4.2 advanced tradeoff
S: Twelve service accounts live in project shared-identities. An on-call engineer must be able to impersonate only one of them, incident-sa, during incidents. A colleague proposes granting the Service Account Token Creator role on project shared-identities to keep things simple. Why should the engineer grant the role on incident-sa instead?
A: A grant on the project lets the engineer impersonate all twelve accounts and reach everything they can access, while a grant on incident-sa limits it to that account
B: A grant on the project is ignored for impersonation, because Token Creator takes effect only when it appears in the allow policy of the service account itself
C: A grant on the project is converted by IAM into twelve separate service account grants that cannot later be revoked one at a time without recreating them
D: A grant on the project also gives the engineer the Owner role on shared-identities, because Token Creator on a project includes full resource management
K: A
G: ## Service accounts are also resources
A service account is a **principal** (you grant it roles) and a **resource** (other principals get roles on it). Access to a service account can be granted on:
- the individual service account,
- the project that contains it,
- a folder above that project, or the organization.
Policies are inherited, so a role granted on the project applies to **every service account in the project**.
## Why the level matters for impersonation
The Service Account Token Creator role (`roles/iam.serviceAccountTokenCreator`) lets a principal create short-lived credentials for a service account, that is, act as it. Granted on the project, it lets the holder impersonate every account there and reach every resource those accounts can access, possibly in other projects too. The best practices say: **do not grant access to service accounts at the project or folder level**; manage it per service account.
W: Per-account grant: inheritance makes a project-level Token Creator grant cover all twelve accounts and everything they can reach, while a grant on incident-sa's own policy gives exactly the one identity the on-call engineer needs.
X: B=Project grant ignored: project-level grants are inherited by the service accounts in the project, so it would work, which is exactly why it is too broad.
C=Converted into separate grants: IAM does not copy bindings into child resources; the project binding stays one binding that you can remove at any time.
D=Includes Owner: Token Creator contains only token-related permissions such as getAccessToken; the risk is indirect access through the accounts, not an Owner grant.
T: Grant roles on service accounts (Token Creator, Service Account User) on the individual account, never on the project or folder.
V: IAM

@ GCP-ACE D4 T4.2 applied troubleshooting
S: Dev lead Arjun has the Service Account User role on deployer-sa. He runs gcloud storage buckets list --impersonate-service-account=deployer-sa@ops-prod.iam.gserviceaccount.com and gets a permission error saying iam.serviceAccounts.getAccessToken is denied. What should the administrator grant?
A: The Service Account Admin role on deployer-sa, because only administrators of an account can request tokens for it from the command line
B: The Service Account Token Creator role on deployer-sa, because impersonation with gcloud requires creating short-lived access tokens for that account
C: The Storage Admin role to Arjun on the project, because impersonation still checks the caller's own roles on every bucket before using the account's
D: The Service Account Key Admin role on deployer-sa, because gcloud impersonation works by creating a temporary key for the account and deleting it afterwards
K: B
G: ## Two roles that sound alike
- **Service Account User** (`roles/iam.serviceAccountUser`): contains `iam.serviceAccounts.actAs`. It lets you **attach** the account to a resource (a VM, a Cloud Run service) so that code on the resource runs as it. The docs state that it does **not** let you create short-lived credentials or use `--impersonate-service-account`.
- **Service Account Token Creator** (`roles/iam.serviceAccountTokenCreator`): contains `iam.serviceAccounts.getAccessToken` (and getOpenIdToken, signBlob, signJwt). It lets you **impersonate** the account: get short-lived credentials for it and act as it yourself.
## How gcloud impersonation works
With `--impersonate-service-account=SA_EMAIL`, gcloud uses your own login to request a short-lived access token for the account from the Service Account Credentials API, then runs the command with it. The API must be enabled, and your login needs Token Creator on the account; after that, the account's roles decide what the command can do.
W: Token Creator on deployer-sa: the denied permission getAccessToken belongs to this role, and granting it on the one account lets Arjun impersonate only deployer-sa.
X: A=Service Account Admin: it manages accounts (view, edit, disable, delete, change policies) but is not the role that provides getAccessToken for impersonation.
C=Storage Admin to Arjun: during impersonation the request is authorized with the service account's permissions; the error is about creating the token, not about bucket access.
D=Key Admin: gcloud impersonation never creates keys; it requests short-lived tokens, and granting key creation would add a long-lived credential risk.
T: Attach an account to a resource = Service Account User (actAs); impersonate it yourself = Service Account Token Creator (getAccessToken).
V: IAM

@ GCP-ACE D4 T4.2 applied use-case
S: An operator runs many gcloud commands as terraform-sa@infra-prod.iam.gserviceaccount.com during a maintenance window and already holds Service Account Token Creator on that account. She wants every command to impersonate it without adding a flag each time, and to switch back afterwards. What should she do?
A: Run gcloud auth activate-service-account with a newly created key for terraform-sa, then run gcloud auth revoke for that key when the window is over
B: Run gcloud iam service-accounts keys create for terraform-sa, then set GOOGLE_APPLICATION_CREDENTIALS to the key file and unset it when the window is over
C: Run gcloud config set auth/impersonate_service_account terraform-sa@infra-prod.iam.gserviceaccount.com, then gcloud config unset auth/impersonate_service_account afterwards
D: Run gcloud config set account terraform-sa@infra-prod.iam.gserviceaccount.com, then gcloud config set account with her own user address afterwards
K: C
G: ## Impersonation for one command or for all of them
- **One command**: add `--impersonate-service-account=SA_EMAIL` to the command.
- **Every command**: set the gcloud property once:
`gcloud config set auth/impersonate_service_account SA_EMAIL`
gcloud then requests short-lived credentials for the account for each command, using the operator's own login as the authenticated principal. To stop: `gcloud config unset auth/impersonate_service_account`.
## Why not a key
Impersonation needs a prior authenticated identity, and its credentials do not persist; audit logs show both the operator and the service account. A key file needs no prior login and lives until someone deletes it, so if it leaks anyone can use it.
W: Set and unset the impersonation property: the property makes every gcloud command impersonate the account with short-lived credentials, and unsetting it returns gcloud to the operator's own identity.

The job still fails, although the bindings that granted the old account roles on two buckets are still listed in the bucket policies. Which statements are correct? (Select TWO)
A: The new account has a different unique ID, so the bindings left by the deleted account do not apply to it even though the email address is the same
B: The new account inherits the old account's role bindings automatically after about 24 hours, once IAM finishes propagating the email address
C: After the new same-named account is deleted, the original can still be undeleted because it was deleted under 30 days ago, and it keeps its role bindings
D: Deleted service accounts are kept for 90 days, but they can be restored only through a support case and lose all their role bindings on restore
E: Lee could have disabled the account instead, but a disabled account loses its role bindings in the same way as a deleted one
K: A,C
G: ## Identity is the unique ID, not the email
Each service account gets a **unique numeric ID** at creation. IAM stores role bindings by that ID, so after deletion the old bindings show as `deleted:serviceAccount:...?uid=NUMERIC_ID` until they are purged (at most 60 days). A **new account with the same name** is a different identity: none of the old bindings apply, and it is not attached to resources the old one was attached to.
## Undelete
You can **undelete** a service account for **30 days** after deletion with its numeric ID (from the policy's `?uid=` suffix or the DeleteServiceAccount audit log). Its identity does not change, so its role bindings work again. After 30 days it is permanently removed and Google cannot recover it.
Undelete fails while an account with the **same name** exists: delete the new account first, then undelete the original.
## Disable first
Best practice: **disable** an account you think is unused (`gcloud iam service-accounts disable SA_EMAIL`) and delete it only later. Disabling keeps all bindings intact, and `enable` brings it back instantly.
W: A=New unique ID: bindings are recorded against the deleted account's numeric ID, so the same-named new account is a different principal they do not cover.
C=Undelete within 30 days: at twelve days the original can still be undeleted once the same-named new account is removed, and because its identity is unchanged its existing bindings apply again.
X: B=Inherited after propagation: same-name accounts never inherit bindings; the docs say the old bindings do not apply to the new account.
D=90 days via support: the undelete window is 30 days and self-service; an undeleted account keeps its roles, and after 30 days even support cannot recover it.
E=Disabled loses bindings: disabling keeps every binding intact, which is why the docs recommend disabling before deleting.
T: Recreating a service account with the same name creates a new identity; delete the new one and undelete the original within 30 days, and disable before you delete.
V: IAM

@ GCP-ACE D4 T4.2 applied use-case
S: A project has more than 60 user-managed service accounts and nobody knows which are still used. The team wants to find accounts that have not authenticated recently and retire them safely. What approach matches Google's recommendations?
A: Delete every account that has no keys, because accounts without keys cannot authenticate and are therefore guaranteed to be unused by any workload
B: Use service account insights and Activity Analyzer to find unused accounts, disable them first, and delete them only after a waiting period
C: Remove all role bindings from every service account at once, then re-grant roles only to the accounts whose workloads report errors over the next week
D: Rename each unused account with an "old-" prefix so that workloads using it fail with clear errors, then delete those that nobody reports within a month
K: B
G: ## Finding unused service accounts
Unused service accounts are a risk: they can be abused for lateral movement or privilege escalation. Google provides:
- **Service account insights**: list accounts in a project that have **not authenticated in the past 90 days**.
- **Activity Analyzer**: shows when a service account or key was **last used**.
- **Service account usage metrics**: track authentication over time.
## Retiring them safely
1. **Disable** the account. Workloads that still need it fail, but you can **re-enable** it instantly with all role bindings intact.
2. After a waiting period with no problems, **delete** it. A deleted account can be undeleted for 30 days; a new account with the same name is a different identity.
W: Insights, Activity Analyzer, disable then delete: these tools show which accounts have not authenticated, and disabling before deleting gives a reversible test before the irreversible step.
X: A=No keys means unused: most workloads authenticate without keys (attached accounts, impersonation, federation), so keyless accounts are often the busiest ones.
C=Strip every binding: this breaks all workloads at once and relies on outages to rebuild access, instead of using the usage data Google provides.
D=Rename with a prefix: a service account ID cannot be changed after creation, and causing deliberate failures is not a safe retirement process.
T: Find unused accounts with service account insights and Activity Analyzer; disable first, delete later.
V: IAM, Recommender

@ GCP-ACE D4 T4.2 advanced use-case
S: An organization keeps all service accounts in project central-ids. A team wants to attach ingest-sa from central-ids to a Pub/Sub subscription in project app-prod, but the attempt fails. Which two actions are required for this cross-project attachment? (Select TWO)
A: Ensure the iam.disableCrossProjectServiceAccountUsage boolean constraint is not enforced on project central-ids, which holds the service account
B: Enforce the iam.disableServiceAccountCreation constraint on project app-prod, so that the team cannot work around the policy with a local account
C: Grant the Pub/Sub service agent of app-prod the Service Account Token Creator role on ingest-sa in central-ids
D: Move ingest-sa from central-ids into app-prod with gcloud iam service-accounts move, then attach it locally without changing any policy
E: Disable iam.disableCrossProjectServiceAccountUsage at the organization node, the only level where that boolean constraint can be configured
K: A,C
G: ## Centralized service accounts
Keeping service accounts in a few dedicated projects makes them easier to manage, but attaching them to resources in **other projects** needs extra setup. A service account cannot be moved between projects after creation.
## What to configure
1. **Organization policy on the service account's project**: the boolean constraint `iam.disableCrossProjectServiceAccountUsage` must **not be enforced** for the project that contains the service accounts. It is enforced by default and can be set **only at the project level**. Turning it off adds a project lien that prevents the project from being deleted.
2. **Service agent permission**: find the service agent of the service that owns the resource (here, Pub/Sub in the resource's project) and grant it **Service Account Token Creator** on the account, for example:
`gcloud iam service-accounts add-iam-policy-binding ingest-sa@central-ids.iam.gserviceaccount.com --member=serviceAccount:SERVICE_AGENT_EMAIL --role=roles/iam.serviceAccountTokenCreator`
As always, the person attaching the account also needs Service Account User on it.
W: A=Constraint off on the account's project: the cross-project usage constraint is enforced by default and must be relaxed on central-ids, where the account lives.
C=Token Creator for the service agent: the Pub/Sub service agent must be able to create tokens for ingest-sa to act as it for the subscription.
X: B=Block account creation in app-prod: it may fit the central model but does nothing to allow the cross-project attachment.
D=Move the account: service accounts cannot be moved to another project after they are created, and there is no move command.
E=Organization level: the docs state this constraint can be configured only at the project level, and it must be relaxed on the project holding the account.
T: Cross-project attachment: relax iam.disableCrossProjectServiceAccountUsage on the account's project and give the resource's service agent Token Creator on the account.
V: IAM, Organization Policy Service, Pub/Sub

@ GCP-ACE D4 T4.2 applied use-case
S: A security team wants every service account in project 735102468813, including accounts created in the future, to have the Logs Writer role, without maintaining a Google group or updating bindings for each new account. Which member should the engineer use in a single binding?
A: serviceAccount:*@project-735102468813.iam.gserviceaccount.com, which matches any service account email in the project
B: principal://iam.googleapis.com/projects/735102468813/serviceAccounts/all, which names every service account in the project
C: group:service-accounts@735102468813.iam.gserviceaccount.com, which Google maintains for each project automatically
D: principalSet://cloudresourcemanager.googleapis.com/projects/735102468813/type/ServiceAccount, the principal set of all its service accounts
K: D
G: ## Service account principal sets
When all service accounts in a scope share a requirement, IAM lets you name them as one **principal set** instead of listing each account or managing a custom group:
- All service accounts in a project: `principalSet://cloudresourcemanager.googleapis.com/projects/PROJECT_NUMBER/type/ServiceAccount`
- In all projects of a folder: `.../folders/FOLDER_NUMBER/type/ServiceAccount`
- In all projects of an organization: `.../organizations/ORGANIZATION_NUMBER/type/ServiceAccount`
The set includes accounts created later, so the binding never needs updating. The IAM docs recommend principal sets over custom groups for this case.
A single account is written `serviceAccount:SA_EMAIL`, with one exact email address; the documented way to name every service account in a scope is the principal set.
W: Project ServiceAccount principal set: this documented identifier covers all current and future service accounts in the project, so one binding meets the requirement.
X: A=Wildcard email: the serviceAccount: identifier names one exact account by its email address; IAM member identifiers do not accept wildcard patterns.
B=principal:// with "all": principal:// identifies one principal; groups of identities use principalSet://, and this path is not a documented identifier.
C=Automatic group: Google does not create a group of a project's service accounts; principal sets exist so you do not need groups for this.
T: All service accounts in a project, folder or organization: principalSet://cloudresourcemanager.googleapis.com/.../type/ServiceAccount.
V: IAM, Cloud Logging
