@ GCP-ACE D3 T3.2 applied troubleshooting
S: A team enabled uniform bucket-level access on the existing bucket gs://acme-reports to simplify permissions. The next day, an auditor from another team, who had read access to three objects through object ACLs, gets 403 errors, and an engineer's attempt to add the ACL again fails with 400 Bad Request. How should the team restore the auditor's access in line with the new setting?
A: Disable uniform bucket-level access, re-add the auditor's object ACLs, and enable the setting again so the ACLs are carried over
B: Grant the auditor an IAM role such as Storage Object Viewer on the bucket, or on a managed folder that holds only those objects
C: Set a default object ACL on the bucket that names the auditor, so the three objects inherit the grant from the bucket default
D: Make the auditor the owner of the three objects with an object update, since object ownership overrides bucket-level settings
K: B
G: ## Two permission systems in Cloud Storage
Cloud Storage can grant access in two parallel ways:
- **IAM**: roles granted on the project, the bucket or a managed folder (for example `roles/storage.objectViewer`).
- **ACLs**: an older, Cloud Storage-only system that can grant access object by object.
## What uniform bucket-level access changes
When you enable **uniform bucket-level access** on a bucket, ACLs are disabled for the bucket and every object in it. Access then comes only from IAM:
- Requests to set, read or change bucket or object ACLs fail with `400 Bad Request`.
- Access granted by existing object ACLs, and by object ownership, is revoked.
- Cloud Storage keeps the old ACLs, so you can still turn the setting off, but only until it has been on for 90 consecutive days.
**Managed folders** need uniform bucket-level access and let you grant IAM roles on a prefix, which replaces most per-object ACL use cases.
## The scenario
The auditor's three ACL grants stopped working by design. The fix is an IAM grant at the right scope: the bucket if reading everything is acceptable, or a managed folder holding only the allowed objects.
W: IAM role on bucket or managed folder: with ACLs disabled, IAM is the only way to grant access, and a managed folder lets the team keep the grant as narrow as the old per-object ACLs.
X: A=Disable, re-add ACLs, re-enable: re-enabling uniform bucket-level access disables ACLs again, so the re-added grants stop working immediately; the toggling only creates confusion.
C=Default object ACL: default object ACLs are ACLs too; setting them fails while uniform bucket-level access is on, and they would only apply to new objects anyway.
D=Object ownership: individual object ownership no longer exists under uniform bucket-level access, so it cannot grant anything.
T: Uniform bucket-level access turns ACLs off; grant access with IAM on the bucket or on a managed folder instead.
V: Cloud Storage, IAM

@ GCP-ACE D3 T3.2 applied use-case
S: A support engineer must let a customer who has no Google account download one diagnostics archive from a private bucket. The link must stop working after two hours, and the bucket must stay private. The engineer can impersonate a service account that is allowed to read the object. What should she do?
A: Grant allUsers the Storage Object Viewer role on the bucket for two hours and remove the binding with a scheduled job afterwards
B: Add the customer's email address to the bucket's IAM policy with Storage Object Viewer and an IAM condition that expires in two hours
C: Run gcloud storage sign-url on the object with --duration=2h and --impersonate-service-account, then send the customer the URL
D: Copy the archive into a new bucket configured for static website hosting and delete that bucket after the customer downloads it
K: C
G: ## Signed URLs
A **signed URL** carries authentication data in its query string, so anyone who has it can perform one specific action (for example `GET` on one object) until it expires, without a Google account.
- It is signed with the credentials of an account that has permission for the action; in most cases a service account.
- You choose the expiry when you create it. With V4 signing the longest possible expiry is 7 days.
- Typical use: temporary downloads or uploads for users outside your organization, while the bucket stays private.
## Creating one with the gcloud CLI
`gcloud storage sign-url gs://BUCKET/OBJECT --duration=2h --impersonate-service-account=SA_EMAIL`
- `--duration` sets the lifetime (default 1 hour). When the URL is signed through impersonation, the maximum is 12 hours; with a service account key file it is 7 days.
- `--impersonate-service-account` signs without downloading a service account key, which is the safer choice.
W: Signed URL: the customer gets a link that works without any Google identity, only for that object and only for two hours, and the bucket's IAM policy never changes.
X: A=allUsers for two hours: this makes every object in the bucket public to anyone during that window, and public access prevention, if enforced, blocks it anyway.
B=IAM grant to an email: an IAM role only helps a principal that can authenticate to Google Cloud (a Google account or a federated identity); the customer has neither, so the grant cannot be used.
D=Static website bucket: this publishes the archive to the whole internet, which breaks the privacy requirement, and adds a bucket to manage.
T: Temporary access for someone without a Google account → signed URL (`gcloud storage sign-url --duration`), signed by a service account.
V: Cloud Storage

@ GCP-ACE D3 T3.2 applied definition
S: A security admin enforces the organization policy constraint storage.publicAccessPrevention on the folder that holds the analytics projects. One bucket there already has an IAM binding that grants allUsers the Storage Object Viewer role, and its own public access prevention setting is inherited. Which TWO statements describe the result? (Select TWO)
A: Anonymous requests to that bucket now fail, although the existing allUsers binding stays in its IAM policy and is overridden
B: Cloud Storage deletes the allUsers binding from the bucket's IAM policy and records the removal in the Admin Activity audit log
C: Signed URLs created for objects in that bucket stop working, because they authorize requests that are not tied to an identity
D: Signed URLs for objects in that bucket keep working, because public access prevention does not apply to signed URLs
E: New buckets in those projects can still receive allUsers bindings until each bucket's own setting is changed to enforced
K: A,D
G: ## Public access prevention
**Public access prevention** stops data from being exposed to the public through the principals `allUsers` and `allAuthenticatedUsers`. It can be set:
- On a single bucket (setting `enforced`).
- Through the organization policy constraint `storage.publicAccessPrevention` on a project, folder or organization. A bucket whose setting is `inherited` follows the nearest value in the hierarchy.
## Behavior when it applies
- Requests authorized only through `allUsers` or `allAuthenticatedUsers` fail with `401` or `403`.
- Existing IAM bindings and ACLs for those principals **stay in place** but are overridden; if prevention is later removed, they take effect again.
- Attempts to add such bindings fail with `412 Precondition Failed`.
- **Signed URLs are not affected**: they are time-limited and narrowly scoped, so they still work.
- Enforcement can take up to 10 minutes, and cached copies may be served for their `Cache-Control` lifetime.
W: A=Requests fail, binding remains: public access prevention overrides the allUsers grant without deleting it, so anonymous reads fail while the binding is still visible in the policy.
D=Signed URLs keep working: the docs state that signed URLs are not affected by public access prevention, so time-limited sharing still works.
X: B=Binding deleted and logged: Cloud Storage does not edit the policy; the binding stays and simply has no effect while prevention applies.
C=Signed URLs stop: signed URLs are explicitly exempt from public access prevention because they are signed by an account that has permission.
E=New buckets still public: buckets with the inherited setting follow the folder's constraint, so adding allUsers to them fails with 412.
T: Public access prevention overrides (does not delete) allUsers/allAuthenticatedUsers grants and leaves signed URLs working.
V: Cloud Storage, Organization Policy Service

@ GCP-ACE D3 T3.2 applied use-case
S: Application logs land in gs://acme-app-logs as Standard objects. Logs are read often in their first 30 days, rarely until day 90, almost never after that, and must be deleted after one year. The engineer wants Cloud Storage to handle this automatically. What should she configure?
A: A bucket retention policy of 365 days together with the Coldline default storage class, so objects are cheaper and expire after a year
B: Autoclass with Archive as the terminal storage class, which moves objects through colder classes and deletes them after a year
C: A Cloud Scheduler job that runs gcloud storage objects update --storage-class every night and then gcloud storage rm for old objects
D: Lifecycle rules: SetStorageClass to Nearline at age 30, to Coldline at age 90, and Delete at age 365, set with --lifecycle-file
K: D
G: ## Object Lifecycle Management
A **lifecycle configuration** is a set of rules on a bucket. Each rule has one **action** and one or more **conditions**; Cloud Storage checks objects regularly and applies the action asynchronously when all conditions of a rule match.
- Actions: `Delete`, `SetStorageClass`, `AbortIncompleteMultipartUpload`.
- Common conditions: `age` (days since creation), `matchesPrefix`/`matchesSuffix`, `matchesStorageClass`, `isLive`, `numNewerVersions`, `daysSinceNoncurrentTime`.
- `SetStorageClass` only moves objects to colder classes (Standard → Nearline → Coldline → Archive).
- When several rules match at once, `Delete` wins over `SetStorageClass`.
## Applying it
Write the rules in a JSON file and run `gcloud storage buckets update gs://acme-app-logs --lifecycle-file=lifecycle.json`. Changes can take up to 24 hours to take effect.
## Cost note
A lifecycle class change does not rewrite the object: there is no retrieval or early deletion fee for the change, and the time already spent in the old class counts toward the new class's minimum storage duration.
W: Lifecycle rules: age-based SetStorageClass and Delete rules match the access pattern exactly and run without any scripts, applied with gcloud storage buckets update --lifecycle-file.
X: A=Retention policy plus Coldline: a retention policy prevents deletion before 365 days, it does not delete anything, and Coldline from day one charges retrieval fees on the frequent early reads.
B=Autoclass: Autoclass moves objects between classes by access, but it never deletes objects, so the one-year deletion still needs a lifecycle rule.
C=Scheduled script: it works only as long as the script and scheduler are maintained, and rewriting objects to change class incurs retrieval and early deletion charges that lifecycle rules avoid.
T: Age-based class changes and expiry in a bucket → lifecycle rules (SetStorageClass + Delete) set with --lifecycle-file.
V: Cloud Storage

@ GCP-ACE D3 T3.2 advanced use-case
S: Object Versioning is enabled on gs://acme-config, and storage keeps growing because every overwrite leaves a noncurrent version behind. The team wants to keep at most two noncurrent versions of each object and also remove any noncurrent version 30 days after it became noncurrent, without touching live objects. Which TWO lifecycle rules meet this? (Select TWO)
A: A Delete rule with only the condition age: 30, which removes each object version 30 days after that version was created
B: A Delete rule with isLive: false and numNewerVersions: 3, which removes a version once three newer versions, live one included, exist
C: A SetStorageClass rule to Archive with isLive: false, which stops all storage charges for noncurrent versions once they move
D: A Delete rule with isLive: true and numNewerVersions: 2, which keeps only the two newest live versions of each object name
E: A Delete rule with isLive: false and daysSinceNoncurrentTime: 30, removing a version 30 days after it was replaced or deleted
K: B,E
G: ## Versions and lifecycle conditions
With **Object Versioning**, overwriting or deleting an object turns the old data into a **noncurrent version**; only one version per name is **live**. Lifecycle conditions made for versioned buckets:
- `isLive`: `false` matches noncurrent versions, `true` matches the live version.
- `numNewerVersions: N`: matches a version that has at least N newer versions, **counting the live version**. The live version has 0 newer versions; the newest noncurrent version has 1.
- `daysSinceNoncurrentTime: N`: matches N days after the version became noncurrent.
## Worked example
Live v5, noncurrent v4, v3, v2. With `numNewerVersions: 3`, v2 matches (v3, v4 and v5 are newer) and is deleted, so the two newest noncurrent versions (v4, v3) remain.
W: B=numNewerVersions 3 on noncurrent: a version with three newer versions (the live one plus two noncurrent) is the third noncurrent one, so deleting it keeps at most two noncurrent versions.
E=daysSinceNoncurrentTime 30: this condition counts from the moment a version became noncurrent, and isLive: false keeps the rule away from live objects.
X: A=age 30: age counts from creation and also matches live objects, so live configuration files older than 30 days would be deleted (made noncurrent).
C=SetStorageClass to Archive: moving versions to Archive lowers the rate but does not stop charges, keeps every version, and adds a 365-day minimum storage duration.
D=isLive true with numNewerVersions 2: a live version always has 0 newer versions, so this rule never matches, and there is only one live version per name.
T: Trim versioned buckets with Delete + isLive:false and numNewerVersions (counts the live version) or daysSinceNoncurrentTime.
V: Cloud Storage

@ GCP-ACE D3 T3.2 applied tradeoff
S: A news site stores millions of images in one bucket. Some are read every day, others not for months, and nobody can predict which, because an old image can suddenly become popular again. The team wants untouched objects to get cheaper at rest, objects that are read again to return to Standard automatically, and no retrieval or early deletion fees. What should they enable?
A: Autoclass on the bucket, so objects move to colder classes when not accessed and move back to Standard when they are read
B: Lifecycle rules that move objects to Nearline, Coldline and Archive by age, plus a rule that returns read objects to Standard
C: Nearline as the bucket's default storage class, so every object starts cheaper and is rewritten to Standard after each read
D: Archive as the default storage class with soft delete disabled, so idle objects cost the least and reads carry no early fees
K: A
G: ## Autoclass
**Autoclass** manages storage classes per object based on access:
- New objects start in Standard.
- Objects that are not read move to progressively colder classes: Nearline after 30 days without access, then (if the terminal class is Archive) Coldline and Archive. The default terminal class is Nearline.
- When an object's data is read, it moves back to Standard.
- Objects smaller than 128 KiB stay in Standard.
## Pricing differences
Autoclass buckets pay a management fee and a one-time enablement charge, but **no retrieval fees and no early deletion fees** (except as part of enablement).
## When to use it
Good when access patterns are mixed, unknown or unpredictable. Not recommended when you already know which data belongs in which class, or when other services scan the whole bucket regularly (every read would pull objects back to Standard).
W: Autoclass: it cools down objects that are not read, warms them back to Standard on access, and waives retrieval and early deletion fees, which matches unpredictable popularity.
X: B=Lifecycle with a return rule: SetStorageClass only moves objects to colder classes; lifecycle has no condition for "was read" and cannot move objects back to Standard.
C=Nearline default: every read of a Nearline object pays a retrieval fee, and nothing moves an object to Standard unless someone rewrites it, which also adds early deletion charges.
D=Archive default: Archive charges the highest retrieval fees and has a 365-day minimum storage duration, which is the opposite of what daily-read images need.
T: Unknown or changing access patterns → Autoclass (moves objects down and back up, no retrieval or early deletion fees).

@ GCP-ACE D3 T3.2 applied troubleshooting
S: A team writes nightly build artifacts into a bucket whose default class is Coldline and deletes each artifact after 30 days with a lifecycle rule. Soft delete is disabled on the bucket. The bill shows more storage-related charges per artifact than the 30 days of Coldline storage they had estimated. What explains the difference?
A: Lifecycle Delete actions are Class A operations billed at the Archive operation rate, which is far above the Coldline storage rate
B: Coldline objects are first billed for 30 days of Standard storage before the lower Coldline storage rate starts to apply to them
C: Coldline has a 90-day minimum storage duration, so each artifact deleted at day 30 incurs an early deletion charge for 60 more days
D: Deleted Coldline objects are moved to Archive storage and kept there for 365 days before Cloud Storage removes them for good
K: C
G: ## Minimum storage durations
Colder storage classes trade a lower at-rest rate for access costs and a **minimum storage duration**:
- Standard: none
- Nearline: 30 days
- Coldline: 90 days
- Archive: 365 days
- Rapid (zonal buckets only): none
If you delete, replace or rewrite an object before its minimum duration, you pay an **early deletion charge** as if it had been stored for the rest of that duration. Nearline, Coldline and Archive also charge **retrieval fees** when data is read.
## Applying the concept
An artifact that lives 30 days in Coldline is billed for 30 days of storage plus 60 days of early deletion. For data that lives about a month, Standard (no minimum) or Nearline (30-day minimum) avoids that charge; the Pricing Calculator can compare the options with your own numbers.
W: Early deletion charge: deleting before Coldline's 90-day minimum makes Cloud Storage bill the remaining 60 days, which is exactly the extra charge per artifact.
X: A=Delete billed at Archive rate: deletes are free operations, and Archive is not involved; the extra cost is storage-duration based.
B=30 days of Standard first: Coldline objects are billed at the Coldline rate from the start; there is no Standard phase.
D=Moved to Archive for a year: deleted objects are not moved to another class; with soft delete disabled they are removed, and the charge comes from the minimum duration.
T: Deleting before the minimum storage duration (Nearline 30, Coldline 90, Archive 365 days) adds an early deletion charge; match short-lived data to Standard.
V: Cloud Storage

G: ## What drives Cloud Storage cost
A Cloud Storage bill is made of several parts:
- **At-rest storage**: data volume × the rate for the storage class and location.
- **Operations**: Class A (for example uploads, listing) and Class B (for example reads) requests.
- **Retrieval fees and early deletion**: for Nearline, Coldline and Archive.
- **Network**: data sent out to the internet or to other regions, and replication for dual- and multi-region buckets.
## Estimating before you build
The **Google Cloud Pricing Calculator** lets you enter these inputs for a planned resource and returns an estimate, so you can compare classes or locations before anything exists. Tools that read actual usage (billing export, budgets, cost reports) only help after resources run.
W: Pricing Calculator: it estimates planned usage from the inputs that drive storage cost (class, location, volume, operations, retrievals, egress) before any resource exists.
X: A=Billing export to BigQuery: it exports charges that already happened; with nothing deployed there is no Cloud Storage usage to project from.
C=Budget with forecast: budgets alert on actual and forecasted spend based on existing usage; they do not calculate the cost of a bucket that does not exist.
D=BigQuery dry run: a dry run estimates the bytes a query would process in BigQuery; it says nothing about Cloud Storage storage or egress charges.
T: Estimating cost before deployment → Pricing Calculator with class, location, volume, operations, retrieval and egress inputs.

@ GCP-ACE D3 T3.2 applied troubleshooting
S: On Tuesday a script ran gcloud storage rm on everything under gs://acme-contracts/2026/q3/ by mistake. Object Versioning is off, and the bucket still has the default soft delete policy. On Thursday the team needs the objects back. What should they do?

G: ## Soft delete
**Soft delete** keeps deleted or overwritten objects (and deleted buckets) in a soft-deleted state for a retention duration, during which they can be restored.
- It is on by default for new buckets with a **7-day** retention; you can set 7 to 90 days, or 0 to disable it. Zonal buckets that use Rapid storage do not support it.
- Soft-deleted objects cannot be read or modified, only listed and restored, and they keep accruing storage charges until the retention ends.
- It works with or without Object Versioning.
## Commands
- `gcloud storage ls --soft-deleted gs://acme-contracts/2026/q3/**` lists the soft-deleted objects.
- `gcloud storage restore gs://acme-contracts/2026/q3/**` restores the latest soft-deleted version of each matching object as a new live object (in the Standard class). Large restores can run asynchronously (`--async`).
## The scenario
Two days is well inside the default 7-day window, so the objects can still be restored.
W: Soft delete restore: the default 7-day soft delete policy retained the objects, so listing them with --soft-deleted and restoring them with gcloud storage restore brings them back as live objects.
X: A=Accept the loss: that was true before soft delete existed; today deleted objects are retained for the soft delete duration even when versioning is off.
B=Enable versioning now: versioning only affects deletions made after it is enabled; it cannot recreate objects deleted earlier.
C=Support case: restoring soft-deleted objects is a self-service operation within the retention window; no support case is needed.
T: Accidental deletes in Cloud Storage → restore from soft delete (7 days by default) with gcloud storage restore.

@ GCP-ACE D3 T3.2 applied use-case
S: Compliance requires that objects in a new bucket in europe-west3 be encrypted with a key the company controls in Cloud KMS. An engineer plans to set that key as the bucket's default encryption key. Which TWO steps are required for uploads to succeed? (Select TWO)
A: Create the Cloud KMS key ring and key in europe-west3, the same location as the bucket

G: ## Customer-managed encryption keys (CMEK)
Cloud Storage always encrypts data at rest. With **CMEK** you use a symmetric key that you manage in **Cloud KMS**, so you control its location, rotation, access and lifecycle.
## Who uses the key
The encryption is done by the project's **Cloud Storage service agent** (a Google-managed service account), not by the user who uploads. It needs `roles/cloudkms.cryptoKeyEncrypterDecrypter` on the key. `gcloud storage service-agent --authorize-cmek=KEY` grants it for you. If the service agent loses access or the key is disabled or destroyed, reads and writes of those objects fail.
## Location rule
The key ring must be in the **same location as the bucket**: a bucket in `europe-west3` needs a key ring in `europe-west3`. (For configurable dual-regions, the key ring must be in the matching multi-region.)
## Setting the default key
`gcloud storage buckets update gs://BUCKET --default-encryption-key=projects/P/locations/europe-west3/keyRings/R/cryptoKeys/K`
W: A=Same location: Cloud Storage requires the key ring to be in the bucket's location, so a europe-west3 bucket needs a europe-west3 key.
C=Service agent role: the Cloud Storage service agent performs the encryption and decryption, so it must hold the CryptoKey Encrypter/Decrypter role on the key.
X: B=Global key: a global key ring does not match a regional bucket's location, so Cloud Storage cannot use it.
D=Cloud KMS Admin for users: uploaders never call Cloud KMS themselves, and an admin role would grant far more than needed; the service agent does the key operations.
E=Autoclass: Autoclass manages storage classes and has nothing to do with encryption; any bucket can have a default CMEK.
T: CMEK for a bucket: key ring in the bucket's location + Encrypter/Decrypter role for the Cloud Storage service agent.

@ GCP-ACE D3 T3.2 applied use-case
S: A developer wants to run a few ad hoc SELECT statements against the Cloud SQL for MySQL instance orders-db, which has a public IP address and no authorized networks. She is working in Cloud Shell and does not want to change the instance's network settings permanently. What is the simplest approach?
A: Add 0.0.0.0/0 to the instance's authorized networks, then connect with the mysql client to the instance's public IP address
B: Run gcloud sql connect orders-db --user=root, which allowlists the Cloud Shell IP address briefly and opens the mysql client
C: Export the database with gcloud sql export sql to Cloud Storage and load the dump into BigQuery to run the SELECT statements
D: Create a read replica with a private IP address and connect to it from Cloud Shell, which is already attached to the project VPC
K: B
G: ## Connecting to Cloud SQL for a quick query
`gcloud sql connect INSTANCE --user=USER` is the quickest way to get a SQL prompt from Cloud Shell or a workstation with the gcloud CLI and the database client installed:
- It adds the client's public IP address to the instance's authorized networks **for 5 minutes**, then starts the `mysql` (or `psql`) client.
- It needs the instance to have a public IP address.
For long-lived application connections, the Cloud SQL Auth Proxy or the language connectors are the recommended path; for private IP instances, connect from a client inside the VPC.

G: ## Cloud NAT (Public NAT)
**Public NAT** lets resources without external IPv4 addresses open outbound connections to the internet using shared external addresses:
- A Cloud NAT gateway belongs to one VPC network, one region and one **Cloud Router**. It is a control-plane configuration: packets do not pass through a proxy VM.
- It allows outbound connections and their responses only; **unsolicited inbound connections are never allowed**, even if firewall rules would permit them.
- It serves the subnet ranges you choose (`--nat-all-subnet-ip-ranges` or `--nat-custom-subnet-ip-ranges`).
## NAT IP addresses
- **Automatic allocation** (`--auto-allocate-nat-external-ips`): Google adds or removes addresses as needed, so the set can change.
- **Manual assignment** (`--nat-external-ip-pool=ip-1,ip-2`): you name reserved static external addresses in the same region, so the egress addresses stay fixed for allowlists.
Example: `gcloud compute routers nats create nat-eu --router=router-eu --region=europe-west1 --nat-external-ip-pool=nat-ip-1,nat-ip-2 --nat-custom-subnet-ip-ranges=batch-subnet`

C=Automatic allocation: Google can add or change NAT addresses as demand grows, so a fixed two-address allowlist could break.
D=Route to internet gateway: a default route exists already; without an external IP or NAT, a VM still cannot reach the internet through it.
T: Private VMs need internet egress from fixed source IPs → Cloud Router + Public NAT with manually assigned reserved IPs.

G: ## How VPC firewall rules are chosen
- Each rule has a **priority** from 0 to 65535; **lower numbers win**. The default is 1000.
- For a packet, the **highest-priority matching rule** decides; target specificity does not matter. A broad rule at 1000 beats a narrow rule at 65534.
- A `deny` beats an `allow` **only when both have the same priority**.
- Rules are stateful: allowed connections automatically allow their return traffic.
## The scenario
`deny-all-ingress` (1000) matches the health check probes before `allow-hc` (65534) is ever considered. Updating the priority is a single command:
`gcloud compute firewall-rules update allow-hc --priority=900`
This keeps the deny-everything baseline and carves out a narrow, higher-priority allow, which is the least-privilege pattern.
W: Lower priority number: at 900 the allow rule is evaluated before the deny rule at 1000, so health check probes on TCP 80 to web VMs are allowed while everything else stays denied.
X: A=Egress rule: health check probes arrive as ingress traffic to the backends, so an ingress allow is required; egress rules do not admit them.
B=Second allow rule: rules are not counted or weighed against each other; the single highest-priority match decides, and the deny at 1000 still matches first.
C=Allow beats deny on the same tag: it is the reverse; at equal priority deny wins, and allow-hc would still be at a lower priority anyway.
T: VPC firewall: lowest priority number wins regardless of how specific the rule is; deny beats allow only at equal priority.

S: In vpc-ops, rule ops-ssh allows ingress tcp:22 from 10.0.0.0/8 to VMs tagged ops at priority 1000, and rule allow-internal allows all protocols from 10.0.0.0/8 at priority 2000. Security now requires that SSH from 10.0.0.0/8 to the ops VMs be blocked. The engineer's gcloud compute firewall-rules update ops-ssh --action=deny fails. What should she do?
A: Create a new ingress rule that denies tcp:22 from 10.0.0.0/8 to tag ops at priority 900, then delete ops-ssh, because a rule's action cannot be updated
B: Update ops-ssh with --disabled so that it is no longer enforced, which lets the implied deny ingress rule block the SSH connections to the ops VMs
C: Update ops-ssh with --priority=65535 so the implied deny ingress rule, which wins ties at that priority, blocks SSH to the VMs tagged ops instead
D: Update ops-ssh with --direction=EGRESS so the rule stops matching inbound SSH, while keeping its name, tags and ranges for any later rollback
K: A
G: ## What you can change on a VPC firewall rule
You can update many parts of an existing rule with `gcloud compute firewall-rules update`: protocols and ports, source and destination ranges, targets, priority, logging and the enforcement state (`--disabled` / `--no-disabled`).
You **cannot** modify a rule's **name**, **network**, **action** (allow or deny) or **direction** (ingress or egress). To change any of those, create a new rule and delete the old one.
## How the rules interact
- The matching rule with the lowest priority number decides; at equal priority a deny beats an allow.
- The implied deny ingress rule (priority 65535) only applies when **no** other rule matches.
- Disabling a rule keeps it defined but removes it from evaluation, so traffic falls through to the next matching rule, not straight to the implied rule.
## The scenario
SSH from `10.0.0.0/8` matches `ops-ssh` (1000) and `allow-internal` (2000). Removing or weakening `ops-ssh` alone leaves `allow-internal` allowing SSH. A new deny rule with a number below 2000 is needed:
`gcloud compute firewall-rules create deny-ops-ssh --network=vpc-ops --direction=INGRESS --action=deny --rules=tcp:22 --source-ranges=10.0.0.0/8 --target-tags=ops --priority=900`
then `gcloud compute firewall-rules delete ops-ssh`.
W: New deny rule then delete: the action of an existing rule cannot be changed, so a new deny rule is required, and at priority 900 it is evaluated before allow-internal at 2000, blocking SSH to the ops VMs.
X: B=Disable ops-ssh: with ops-ssh disabled, SSH still matches allow-internal at priority 2000, so the traffic is allowed and the implied deny rule is never reached.
C=Priority 65535: allow-internal at 2000 still matches SSH first, and the implied deny only applies when no explicit rule matches, so nothing is blocked.
D=Change direction: a rule's direction cannot be updated any more than its action, and even an egress rule would leave allow-internal allowing inbound SSH.
T: A VPC firewall rule's name, network, action and direction cannot be updated; create a new rule with the right priority and delete the old one.

K: C
G: ## Where firewall rules live
Cloud NGFW evaluates several kinds of rules for a VM:
- **Hierarchical firewall policies**, attached to the organization or folders, managed centrally.
- **Global and regional network firewall policies** and **VPC firewall rules**, managed in the project.
- The **implied rules** at the very end.
## Evaluation order
Hierarchical policies are evaluated first (organization, then folders from the top down), before VPC firewall rules and network firewall policies. Within a policy the rule with the lowest priority number that matches decides. Each policy rule action:
- `allow` / `deny`: decides and stops evaluation of everything below.
- `goto_next`: stops evaluating this policy and passes the decision to the next level.
So a priority 0 VPC rule cannot override an organization-level deny: the packet never reaches the VPC rules.
## The fix
An organization (or folder) admin changes the hierarchical rule, for example to `goto_next` for the office range, or adds a higher-priority allow for `203.0.113.0/24`, so the project's rule can take effect.
W: Hierarchical first: the organization's deny matches before any VPC rule is evaluated, so only changing the hierarchical rule (for example to goto_next or a scoped allow) lets the project's allow rule apply.
X: A=Priority 0 reserved: 0 is a valid, user-settable priority for VPC rules; priority within the VPC does not matter when a higher-level policy already decided.
B=Service account target: targeting by service account or tag does not change the order between hierarchical policies and VPC rules.
D=Deny always wins: deny only beats allow at the same priority within the same evaluation step, and organization policies (constraints) do not create firewall exceptions.
T: Hierarchical firewall policies are evaluated before VPC rules; a deny there can only be relaxed at that level (goto_next or allow).
