@ GCP-ACE D3 T3.4 applied use-case
S: A team runs a web application on a few Compute Engine VMs. They want the on-call engineer to receive an email and a message in the team's Slack channel whenever the CPU utilization of any of these VMs stays above 85% for 10 minutes. What should they configure in Cloud Monitoring?
A: An uptime check against each VM's external IP address, with a 10-minute check frequency and a failure threshold of 85% of the checking regions
B: A metric-threshold alerting policy on the VMs' CPU utilization with a 10-minute retest window, and email and Slack notification channels attached to it
C: A log-based metric that counts entries mentioning high CPU in the VMs' system logs, charted on a custom dashboard that the on-call engineer watches
D: A metric-absence alerting policy on the VMs' CPU utilization metric, so that a notification is sent when the metric exceeds 85% for 10 minutes
K: B
G: ## How Cloud Monitoring alerting works
An **alerting policy** has three parts:
- A **condition**: the data to watch and when it is met. A **metric-threshold** condition is met when a metric is above (or below) a threshold for a whole **retest window**, for example CPU utilization above 0.85 for 10 minutes.
- One or more **notification channels**: how people are told, such as email, Slack, SMS, PagerDuty, Pub/Sub or webhooks. One policy can notify several channels at once.
- Optional **documentation**: text and links (for example a runbook) included in the notification.
When the condition is met, Monitoring creates an **alert** (an incident record) and notifies every channel; when the condition is no longer met, it closes the alert and notifies again.
## Other condition types
- **Metric-absence**: met when a time series has *no data* for the retest window (a silent job or a dead agent).
- **Forecasted metric-value**: met when the metric is predicted to cross the threshold within a forecast window.
- Uptime checks probe availability from outside; they test whether a URL or port answers, not CPU load.
W: Metric-threshold policy with two channels: a threshold condition on CPU utilization with a 10-minute retest window matches the requirement exactly, and attaching both an email and a Slack notification channel sends each alert to both places.
X: A=Uptime check: uptime checks test whether an endpoint answers HTTP, HTTPS or TCP requests from several locations; they do not measure CPU utilization, so a busy but responsive VM would never fail them.
C=Log-based metric on a dashboard: CPU utilization is already a built-in metric, a dashboard notifies no one, and system logs do not reliably contain CPU readings to count.
D=Metric-absence policy: an absence condition fires when the time series stops reporting data, not when its values are high, so it cannot express "above 85%".
T: Alert on a metric value with a metric-threshold condition plus a retest window, and attach one notification channel per destination (email, Slack, ...).
V: Cloud Monitoring

@ GCP-ACE D3 T3.4 advanced use-case
S: A payment service on GKE writes one structured JSON log entry per request, with fields `endpoint`, `status` and `latency_ms`. The team wants Cloud Monitoring charts and alerting policies for the number of failed requests per endpoint and for the latency distribution, without changing the application code. Which log-based metrics should they create? (Select TWO)
A: A counter log-based metric whose filter matches failed requests, with a label extracted from the `endpoint` field so each endpoint gets its own time series
B: A boolean user-defined log-based metric on `status`, which Monitoring converts automatically into a failure count per endpoint and per minute
C: A counter log-based metric that reads past log entries from the last 30 days when it is created, so the new charts start with a full history
D: A distribution log-based metric that extracts the `latency_ms` value from each matching entry into histogram buckets for percentile charts
E: A system-defined log-based metric named `logging.googleapis.com/user/latency`, created by editing the predefined labels of the built-in metric
K: A,D
G: ## Metrics derived from logs
**Log-based metrics** are Cloud Monitoring metrics computed from log entries that match a filter. You can chart them and use them in alerting policies like any other metric. User-defined log-based metrics come in two types:
- **Counter**: counts the entries that match the filter in each interval. Use it for "how many errors".
- **Distribution**: extracts a numeric value from each matching entry (for example a latency field) and accumulates it into histogram buckets, giving count, mean and percentiles.
## Labels
A user-defined metric can have **labels** whose values are extracted from fields of the entry. Each combination of label values becomes its own time series, so a label on `endpoint` gives one error series per endpoint.
## Things that surprise people
- Data comes only from entries received **after** the metric is created: it is not backfilled.
- User-defined metrics are named `logging.googleapis.com/user/NAME`; system metrics have predefined labels you cannot change.
- Boolean is a type used by some *system* metrics only; user-defined log-based metrics are counters or distributions.
Example: `gcloud logging metrics create failed_requests --log-filter='jsonPayload.status>=500'` creates a counter (labels are added in the console or a config file).
W: A=Counter with endpoint label: a counter counts the failed-request entries, and a label extracted from `endpoint` splits the count into one time series per endpoint, ready for charts and a threshold alert.
D=Distribution on latency_ms: a distribution metric extracts the numeric latency from each entry into histogram buckets, which is how log-based latency percentiles are charted and alerted on.
X: B=Boolean user-defined metric: user-defined log-based metrics can only be counters or distributions; the boolean type appears only among some system-defined metrics.
C=Backfilled counter: log-based metrics are not retroactive; a new metric gets data only from entries received after it is created.
E=Edited system metric: system-defined metrics have predefined labels that cannot be changed, and the `logging.googleapis.com/user/` prefix marks user-defined metrics, not system ones.
T: Count matching log entries with a counter (labels split the series), extract numbers such as latency with a distribution; neither is backfilled.
V: Cloud Logging, Cloud Monitoring, GKE

@ GCP-ACE D3 T3.4 applied comparison
S: An order service on Compute Engine keeps the number of jobs waiting in an in-memory queue. That value is never written to any log. The team wants to chart it and alert when it grows above 500, following Google's recommended way to instrument code. What should they do?
A: Create a counter log-based metric with a filter on the service's log name, and alert when the counter for the queue rises above 500 entries
B: Enable Data Access audit logs on the project, so that every read of the queue by the service is recorded and can be counted as a metric
C: Instrument the service with OpenTelemetry to export a user-defined metric for queue length, collected by the Ops Agent, and alert on it
D: Create a forecasted metric-value alerting policy on the VM's built-in CPU metric, since queue growth is always reflected in rising CPU use
K: C
G: ## Built-in, log-based and user-defined metrics
- **Built-in metrics** come from Google Cloud services (CPU, disk, request counts). They know nothing about values inside your program.
- **Log-based metrics** are derived from log entries. They help only when the value appears in logs.
- **User-defined metrics** (also called custom metrics) capture application-specific values. Google recommends instrumenting code with **OpenTelemetry**; the Prometheus libraries or the Cloud Monitoring API can also write them. User-defined metric types use prefixes such as `custom.googleapis.com/` or `workload.googleapis.com/`.
## Getting the data out of a VM
On Compute Engine, the **Ops Agent** includes an OpenTelemetry Protocol (OTLP) receiver: the instrumented app sends metrics to the local agent, which forwards them to Cloud Monitoring. Once there, a user-defined metric is charted and alerted on exactly like a built-in one.
W: OpenTelemetry user-defined metric: the queue length exists only in the program's memory, so the app itself must report it; OpenTelemetry is the recommended instrumentation, the Ops Agent's OTLP receiver forwards it, and a threshold policy on the new metric alerts above 500.
X: A=Counter log-based metric: the value is never logged, so there are no entries to count; a counter would also count log entries, not report the queue's current size.
B=Data Access audit logs: audit logs record calls to Google Cloud APIs, not reads of an in-memory structure inside your own program.
D=Forecast on CPU: CPU use is at best an indirect hint; a long queue can sit behind a slow downstream service while CPU stays low, so the alert would miss the real condition.
T: Values that live only inside your code need a user-defined metric, preferably instrumented with OpenTelemetry.
V: Cloud Monitoring, Ops Agent, Compute Engine

@ GCP-ACE D3 T3.4 advanced definition
S: A security lead is writing the team's audit logging runbook. Which statements about Cloud Audit Logs are correct? (Select TWO)
A: Admin Activity audit logs, such as a record of who deleted a VM, are always written and cannot be disabled or excluded
B: Data Access audit logs are enabled by default for every service, and you turn them off per service to reduce log volume
C: A principal with only the Logs Viewer role can read the Data Access audit logs that are stored in the `_Default` bucket
D: Entries in the `_Required` bucket are kept for 400 days, and the retention period of that bucket cannot be changed
E: System Event audit logs can be excluded with an exclusion filter on the `_Required` sink to lower storage costs
K: A,D
G: ## Four kinds of audit logs
- **Admin Activity**: API calls that change configuration or metadata (create a VM, change IAM). Always written; cannot be configured, excluded or disabled.
- **System Event**: changes made by Google Cloud systems, such as an autoscaler adding VMs. Always written; cannot be disabled.
- **Data Access**: calls that read configuration or metadata, or read/write user data. **Disabled by default except for BigQuery**, because they can be very large; you enable them per service (`ADMIN_READ`, `DATA_READ`, `DATA_WRITE`).
- **Policy Denied**: written when a security policy denies access. Written by default; can be excluded from storage.
## Where they are stored
- `_Required` bucket: Admin Activity and System Event logs. Retention is **400 days** and not configurable; the `_Required` sink cannot be modified or deleted.
- `_Default` bucket: enabled Data Access logs and Policy Denied logs (default 30 days, configurable).
## Who can read them
`roles/logging.viewer` (Logs Viewer) reads Admin Activity, System Event and Policy Denied logs. Reading Data Access logs in `_Default` needs `roles/logging.privateLogViewer` (Private Logs Viewer).
W: A=Admin Activity always on: these logs answer "who changed what" (for example who deleted a VM) and are always written; even disabling the Cloud Logging API does not stop them.
D=_Required 400 days: the `_Required` bucket keeps Admin Activity and System Event logs for 400 days, and its retention is not configurable.
X: B=Data Access on by default: the opposite is true; Data Access logs are off by default for every service except BigQuery and must be enabled explicitly.
C=Logs Viewer reads Data Access: Logs Viewer cannot see Data Access logs in `_Default`; that needs Private Logs Viewer.
E=Excluding System Event logs: System Event logs cannot be disabled, and the `_Required` sink cannot be modified, so no exclusion filter can be added to it.
T: Admin Activity and System Event logs are always kept 400 days in `_Required`; Data Access logs are opt-in (except BigQuery) and need Private Logs Viewer to read.
V: Cloud Audit Logs, Cloud Logging

@ GCP-ACE D3 T3.4 applied troubleshooting
S: After a suspected data leak, an auditor searches Logs Explorer for records of who downloaded objects from a Cloud Storage bucket last week. She finds Admin Activity entries for bucket changes but no entries for object reads. Nobody has changed the project's audit configuration. What explains this, and what should be done for the future?
A: Object reads are logged only in the Cloud Storage bucket's own access log file; enable the bucket's object versioning so the access log is kept
B: Object reads are recorded as System Event audit logs, which are visible only at the organization level, so she should search from the organization
C: Data Access audit logs for Cloud Storage are disabled by default; enable `DATA_READ` audit logs for the Cloud Storage service in the project
D: The entries expired because the `_Default` bucket keeps logs for 24 hours by default; increase its retention period to 30 days to keep them
K: C
G: ## Data Access audit logs are opt-in
Reading object data is a **Data Access** operation. Except for BigQuery, Data Access audit logs are **disabled by default**, because they can be very large. You enable them per service, and per permission type:
- `ADMIN_READ`: reading configuration or metadata.
- `DATA_READ`: reading user-provided data, such as downloading an object.
- `DATA_WRITE`: writing user-provided data.
You configure them on the IAM **Audit Logs** page or in the `auditConfigs` of the IAM policy, at project, folder or organization level, and you can exempt principals (for example test accounts).
## Consequences
- Logs are not retroactive: once enabled, reads are recorded from then on, but last week's downloads were never logged.
- Enabled Data Access logs go to the `_Default` bucket (30 days by default) and add log volume.
W: Enable DATA_READ for Cloud Storage: object reads generate Data Access audit logs, which are off by default for Cloud Storage; enabling `DATA_READ` for the service records future downloads with the caller's identity.
X: A=Bucket access log and versioning: object versioning keeps older object generations, it has nothing to do with logging who read an object; audit trails for reads come from Data Access audit logs.
B=System Event logs: System Event logs record actions by Google Cloud systems, not user downloads, and project-level audit logs are visible in the project itself.
D=24-hour retention: the `_Default` bucket keeps logs for 30 days by default; the entries are missing because they were never written, not because they expired.
T: "Who read this data?" needs Data Access audit logs, which you must enable per service (BigQuery is the only exception).
V: Cloud Audit Logs, Cloud Storage

@ GCP-ACE D3 T3.4 advanced tradeoff
S: A network team enabled VPC Flow Logs on a busy subnet for forensics and capacity planning. The volume of flow log entries is now much higher than they expected. Which changes reduce the volume of flow logs while keeping flow visibility for the subnet? (Select TWO)
A: Lower the primary packet sampling rate of the subnet, which controls how many packets each host samples before flows are aggregated
B: Increase the aggregation interval from the default 5 seconds to a longer interval, such as 1 minute, so more packets merge into each entry
C: Enable TCP connection logging for the subnet, so that connections are recorded once instead of being sampled packet by packet
D: Move the subnet's VMs to a legacy network, where VPC Flow Logs records only flows that are blocked by firewall rules
E: Lower the secondary sampling rate of the flow log configuration, so that only a fraction of the generated flow log entries is kept
K: B,E
G: ## How VPC Flow Logs produces entries
VPC Flow Logs samples packets sent and received by VMs (including GKE nodes), serverless resources using Direct VPC egress, VLAN attachments and Cloud VPN tunnels. Processing happens in stages:
1. **Primary sampling**: dynamic, depends on host load. You **cannot** control or adjust it.
2. **Filtering** (optional): keep only flows that match criteria, such as one VM.
3. **Aggregation**: sampled packets of one connection (5-tuple) within the **aggregation interval** become one entry. Interval: 5 s (default), 30 s, 1 min, 5 min, 10 min or 15 min.
4. **Secondary sampling**: keep only a fraction of the generated entries (configurable, from 1.0 down).
5. **Metadata**: annotations such as VM names or geography; can be trimmed or turned off.
## Levers for volume and cost
Longer aggregation intervals, a lower secondary sampling rate, filters and fewer metadata fields all cut volume. Flow logs go to Cloud Logging, where retention is 30 days by default.
W: B=Longer aggregation interval: each entry summarizes one connection per interval, so moving from 5 seconds to 1 minute merges many short-interval entries into one and greatly reduces volume.
E=Lower secondary sampling: secondary sampling keeps only a configurable share of the generated entries, directly trading some detail for less volume.
X: A=Primary sampling rate: the primary sampling rate is dynamic and set by Google; you cannot control or adjust it.
C=TCP connection logging: this optional feature adds entries for connection attempts that sampling may miss; it increases volume, it does not replace sampling.
D=Legacy network: VPC Flow Logs works only with VPC networks, not legacy networks, so the subnet would lose flow logs entirely.
T: To shrink VPC Flow Logs volume, lengthen the aggregation interval, lower the secondary sampling rate, filter or trim metadata; primary sampling is not adjustable.
V: VPC Flow Logs, Cloud Logging

@ GCP-ACE D3 T3.4 advanced troubleshooting
S: A VPC network has three ingress allow rules with logging enabled and no deny rules of its own. A partner reports that their connection attempts on TCP port 8443 to a VM are rejected, and the team wants a log of each rejected attempt with its source address. Nothing about 8443 appears in the firewall logs. What should the team do?
A: Enable logging on the implied deny ingress rule of the network, which currently drops the partner's packets without writing connection records
B: Enable VPC Flow Logs on the subnet, because flow logs record every ingress packet that a firewall rule denies, including packets on port 8443
C: Enable Data Access audit logs for the Compute Engine API, which records each inbound connection that is refused at the VM's network interface
D: Create an ingress deny rule for all sources at priority 65534 with logging enabled, so the traffic that the implied rule would drop is logged
K: D
G: ## What firewall rules logging covers
Firewall rules logging writes a **connection record** each time a rule *with logging enabled* allows or denies a TCP or UDP connection. Each record contains source and destination IPs, protocol, ports, time and a reference to the rule. Logging is switched on **per rule** (`--enable-logging`).
## The implied rules
Every VPC network has two implied rules at the lowest priority (65535): **deny all ingress** and **allow all egress**. They have no logging option: firewall rules logging is not supported for the implied rules.
## The standard workaround
Create your own catch-all rule just above the implied one, for example an ingress deny rule for `0.0.0.0/0` at priority `65534` with logging enabled. It denies exactly what the implied rule would deny, but now each blocked attempt is logged (a denied connection is logged and repeated every 5 seconds while packets keep arriving).
## Why flow logs don't help here
VPC Flow Logs samples ingress packets *after* ingress firewall rules, so packets an ingress rule denies are not sampled as normal flows.
W: Logged catch-all deny rule: a deny-all ingress rule at priority 65534 with logging enabled matches before the implied deny, blocks the same traffic and writes a connection record with the source address for every rejected attempt.
X: A=Log the implied rule: implied rules cannot be edited, and firewall rules logging is not supported for the implied deny ingress and allow egress rules.
B=VPC Flow Logs: flow logs sample packets and see ingress traffic only after ingress firewall rules, so they do not give a reliable record of every attempt that a rule denied.
C=Data Access audit logs: audit logs record calls to Google Cloud APIs; network connections to a VM are not API calls and never appear there.
T: To log traffic that the implied deny ingress rule drops, add your own deny-all rule at priority 65534 with logging on.
V: Cloud NGFW, VPC, Cloud Logging

@ GCP-ACE D3 T3.4 applied use-case
S: A company's security team runs a third-party SIEM outside Google Cloud. It must receive the project's Admin Activity audit logs within seconds of them being written, through an integration that pulls messages from Google Cloud. What should the cloud engineer set up?
A: A log sink with a filter on the activity log whose destination is a Pub/Sub topic, with the SIEM subscribed to the topic
B: A log sink with a filter on the activity log whose destination is a Cloud Storage bucket, with the SIEM reading new files
C: A daily scheduled job that runs `gcloud logging read` and uploads the results to the SIEM through its HTTPS ingestion API
D: A linked BigQuery dataset on the `_Required` log bucket, with the SIEM running a SQL query against it once per minute
K: A
G: ## Choosing a sink destination
A **log sink** routes the log entries that match its filter to a destination. Each destination has its purpose:
- **Log bucket**: store and analyze in Cloud Logging (Logs Explorer, Observability Analytics).
- **BigQuery dataset**: join log data with other business data in SQL.
- **Cloud Storage bucket**: long-term storage of log files as JSON. Sinks to Cloud Storage are processed hourly, so new sinks may take hours before the first files appear.
- **Pub/Sub topic**: streaming export to third-party tools such as Splunk or Datadog. Each entry is published as a JSON message.
## Example
`gcloud logging sinks create siem-sink pubsub.googleapis.com/projects/sec-proj/topics/siem --log-filter='LOG_ID("cloudaudit.googleapis.com/activity")'`, then grant the sink's writer identity Pub/Sub Publisher on the topic.
W: Sink to Pub/Sub: Pub/Sub is the destination meant for streaming logs to third-party tools; each matching entry is published as a message within seconds, and the SIEM pulls them through a subscription.
X: B=Sink to Cloud Storage: Cloud Storage sinks write files in hourly batches, so entries arrive far later than "within seconds"; this destination is for long-term storage.
C=Daily gcloud logging read job: a daily batch misses the latency requirement entirely and is fragile custom tooling compared with a managed sink.
D=Linked BigQuery dataset: Admin Activity logs could be queried this way, but polling with SQL is not a streaming feed, and a linked dataset is meant for analysis rather than export to outside tools.
T: Stream logs to an external tool through a sink to Pub/Sub; use Cloud Storage for archives and BigQuery or log buckets for analysis.
V: Cloud Logging, Pub/Sub

@ GCP-ACE D3 T3.4 applied troubleshooting
S: An engineer in project app-prod creates a log sink whose destination is a BigQuery dataset in the project analytics-hub. The sink is created without errors, but after an hour no tables have appeared in the dataset, and Logging reports a sink configuration error. What is the most likely fix?
A: Enable the Cloud Logging API in analytics-hub, because a sink can only write to a dataset in a project where Logging is enabled
B: Grant the sink's writer identity the BigQuery Data Editor role on the dataset, so the sink's service account can create tables and write rows
C: Grant the engineer's own user account BigQuery Data Owner on the dataset, because a sink writes with the credentials of the user who created it
D: Recreate the destination as a linked BigQuery dataset on a log bucket, because sinks can route logs only into linked datasets
K: B
G: ## Sinks write with their own identity
When a sink's destination is anything other than a log bucket in the same project, Cloud Logging writes through a service account: the sink's **writer identity** (`writerIdentity`). Creating the sink does not grant that account access to the destination; the person who owns the destination must grant it.
## Roles per destination
- BigQuery dataset: **BigQuery Data Editor** (`roles/bigquery.dataEditor`).
- Cloud Storage bucket: **Storage Object Creator** (`roles/storage.objectCreator`).
- Pub/Sub topic: **Pub/Sub Publisher** (`roles/pubsub.publisher`).
- Log bucket in another project: **Logs Bucket Writer** (`roles/logging.bucketWriter`).
Find it with `gcloud logging sinks describe SINK_NAME` and look for `writerIdentity`.
## What a misconfigured sink does
It routes nothing: Logging writes error entries about the problem and emails the resource's Essential Contacts. Sinks are not retroactive, so entries from before the fix are not delivered.
W: Grant BigQuery Data Editor to the writer identity: the sink writes through its writer identity service account, which needs BigQuery Data Editor on the dataset to create one table per log name and stream entries into it.
X: A=Enable Logging API in the destination: a BigQuery destination needs a write-enabled dataset and permissions for the writer identity; enabling Logging in the destination project does not grant write access.
C=Grant the creator's account: sinks do not write with the creator's credentials; they use the writer identity service account, so the engineer's own roles do not help.
D=Linked dataset destination: the opposite is true; linked BigQuery datasets are read-only and must not be used as a sink destination.
T: A sink writes through its writer identity; grant that service account the destination's writer role (BigQuery Data Editor for datasets).

@ GCP-ACE D3 T3.4 applied use-case
S: An organization has about 200 projects in several folders, and new projects are created every week. The security team needs the audit logs of every current and future project collected in one log bucket in the project sec-logs, without configuring each project. What should the engineer create?
A: A sink in sec-logs with an inclusion filter that lists the project IDs of all 200 projects, updated by a script each time a project is created
B: A project-level sink in each project, created by a startup script stored in an organization policy that runs when the project is created
C: An aggregated sink at the organization with `--include-children` and an audit log filter, routing to the log bucket in sec-logs
D: A multi-project metrics scope in sec-logs that lists all projects, which makes their audit logs searchable from the sec-logs project
K: C
G: ## Aggregated sinks
A normal sink belongs to one project and sees only that project's logs. An **aggregated sink** is created on an **organization or folder** and routes logs from that resource **and all its children**, including projects created later.
- `gcloud logging sinks create SINK DEST --organization=ORG_ID --include-children --log-filter='logName:"cloudaudit.googleapis.com"'`
- **Non-intercepting** (default): routes a copy; child projects still store their own logs.
- **Intercepting** (`--intercept-children`, destination must be a project): stops matching entries from reaching child sinks, except the `_Required` sink.
As with any sink to another project, grant the writer identity write access to the destination (Logs Bucket Writer for a log bucket).
## Not to confuse with metrics scopes
A metrics scope lets one project chart *metrics* of others in Cloud Monitoring. It does not move or share logs.
W: Organization aggregated sink: created once on the organization with `--include-children`, it routes matching audit logs from every child project, present and future, into the central log bucket.
X: A=Project ID list in one sink: a sink in sec-logs only sees log entries that arrive in sec-logs; filtering on other project IDs does not pull their logs in, and the script would be brittle anyway.
B=Per-project sinks from an org policy: organization policies set constraints on resources; they do not run scripts at project creation, and per-project sinks are the manual work the team wants to avoid.
D=Metrics scope: metrics scopes share Monitoring metrics between projects; they do not route or store any log entries.
T: Central logs for a whole organization or folder = one aggregated sink with `--include-children` at that level.

@ GCP-ACE D3 T3.4 applied use-case
S: An application team's logs land in the `_Default` log bucket of their project. A new internal policy requires application logs to be searchable in Logs Explorer for 90 days. What is the simplest change?
A: Change the retention of the `_Required` bucket to 90 days, since that bucket keeps the project's application logs alongside its audit logs
B: Update the retention of the project's `_Default` log bucket to 90 days with `gcloud logging buckets update _Default --location=global --retention-days=90`
C: Create a sink to a Cloud Storage bucket with a 90-day lifecycle rule, since log buckets cannot keep log entries for longer than 30 days
D: Enable Data Access audit logs on the project, which raises the retention of every log entry in the `_Default` bucket to 400 days
K: B
G: ## Log bucket retention
Each project has two system buckets:
- `_Required`: Admin Activity, System Event and Access Transparency logs; **400 days**, not configurable.
- `_Default`: everything else that the `_Default` sink routes, including application logs; **30 days by default**, configurable.
For `_Default` and user-defined log buckets in projects, retention can be set from **1 to 3650 days**. Shortening retention has a 7-day grace period during which you can undo it. You can also **lock** a bucket's retention policy for compliance (`--locked`); after that, the bucket cannot be deleted until every entry has met its retention.
## Example
`gcloud logging buckets update _Default --location=global --retention-days=90`
W: Update _Default retention: the application logs already live in `_Default`, whose retention is configurable from 1 to 3650 days; setting 90 days keeps them searchable in Logs Explorer with one command.
X: A=_Required retention: `_Required` holds only Admin Activity, System Event and Access Transparency logs, and its 400-day retention cannot be changed.
C=Cloud Storage sink: log buckets can keep entries up to 3650 days, and files in Cloud Storage are not searchable in Logs Explorer as the policy requires.
D=Data Access logs: enabling them adds more log entries to `_Default`; it does not change any bucket's retention period.
T: Keep logs longer in Logging by raising the retention of `_Default` or a user-defined bucket (1-3650 days); `_Required` is fixed at 400 days.

@ GCP-ACE D3 T3.4 applied use-case
S: A load balancer health check hits every backend VM every few seconds, and the web server logs each probe as an INFO entry. These entries make up most of the project's log storage and are never used. The team wants to stop storing them while keeping every other log. What should they configure?
A: An exclusion filter on the project's `_Default` sink that matches the health-check entries, so the Log Router does not store them
B: Disabling the Cloud Logging API on the project, which stops all application entries while audit logs continue to be stored in `_Required`

D: A shorter retention period on the `_Required` bucket, so that the health-check entries stored there are deleted after one day
K: A
G: ## Inclusion and exclusion filters
Every sink has one **inclusion filter** and can have several **exclusion filters**. An entry is routed when it matches the inclusion filter and **no** exclusion filter. The `_Default` sink routes everything except the `_Required` logs into the `_Default` bucket; you can edit it and add exclusions.
## What exclusions do and don't do
- Excluded entries are not stored in the bucket, which cuts storage.
- Exclusions apply after the Logging API receives the entries, so they do not reduce `entries.write` calls or quota.
- User-defined log-based metrics still count excluded entries (system metrics count only included ones).
Example exclusion: `resource.type="gce_instance" AND httpRequest.userAgent:"GoogleHC"`.
W: Exclusion on the _Default sink: an exclusion filter matching the probe entries stops the `_Default` sink from routing them to storage, while all other entries still match the sink and are stored as before.
X: B=Disable the Logging API: this would stop all application logs, not just the probes, which breaks the "keep every other log" requirement.
C=Log-based metric: a metric counts matching entries; it does not delete or prevent storage of the entries themselves.
D=Shorter _Required retention: application entries are not in `_Required`, and its retention cannot be changed in any case.
T: Drop noisy logs from storage with an exclusion filter on the sink (usually `_Default`); exclusions don't reduce API write volume.

@ GCP-ACE D3 T3.4 applied comparison
S: An analyst wants to know, for each hour of the last week, the average latency of HTTP requests to `/checkout` recorded in the project's request logs. G: ## Logs Explorer vs Observability Analytics
- **Logs Explorer** uses the Logging query language to find and inspect individual entries, with a histogram of counts. It does **not** support aggregate operations such as grouping or averaging.

@ GCP-ACE D3 T3.4 applied troubleshooting
S: An engineer needs to see entries from Compute Engine VMs with severity ERROR or higher whose text payload contains the word "timeout", in Logs Explorer. Which query returns exactly these entries?
A: `resource.type="gce_instance" OR severity>=ERROR OR textPayload:"timeout"`
B: `resource.type="gce_instance" AND severity="ERROR" AND textPayload="timeout"`
C: `resource.type="gce_instance" AND severity>=ERROR AND textPayload:"timeout"`
D: `resource.type="gce_instance" and severity>=ERROR and textPayload:"timeout"`
K: C
G: ## Logging query language basics
A query is a set of comparisons `FIELD OP VALUE`, combined with Boolean operators:
- `=` equal, `!=` not equal, `>` `<` `>=` `<=` ordering, `:` **has** (substring match), `=~` regular expression.
- `severity` is ordered: `severity>=ERROR` matches ERROR, CRITICAL, ALERT and EMERGENCY.
- `AND`, `OR`, `NOT` must be **uppercase**; lowercase `and`, `or`, `not` are treated as search terms. `AND` may be omitted between comparisons.
- String comparisons are not case sensitive. Mix `AND` and `OR` only with parentheses.
The same language is used by Logs Explorer, `gcloud logging read`, sink filters and log-based metric filters.
W: AND with >= and has: `severity>=ERROR` includes every level from ERROR upward, `textPayload:"timeout"` matches the word anywhere in the text, and uppercase `AND` requires all three conditions.
X: A=OR between comparisons: `OR` returns entries that match any one condition, so it would include every VM entry and every error from any resource.
B=Equality operators: `severity="ERROR"` drops CRITICAL and higher, and `textPayload="timeout"` matches only entries whose entire text is exactly that word.
D=Lowercase and: lowercase `and` is parsed as a search term, not an operator, so the query looks for the literal word "and" instead of joining the conditions.
T: Use uppercase AND/OR/NOT, `>=` on severity for "this level or worse", and `:` for substring matches.
V: Cloud Logging
