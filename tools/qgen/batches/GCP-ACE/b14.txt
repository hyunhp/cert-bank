@ GCP-ACE D1 T1.1 expert troubleshooting
S: Priya is the Owner of projects `team-a-dev` and `team-a-prod`, which both carry the tag `team=a` at project level. She must manage organization policies on these projects herself, for example to allow an external IP on one bastion VM. Running `gcloud org-policies set-policy policy.yaml` against team-a-dev fails with PERMISSION_DENIED for `orgpolicy.policies.create`. An organization administrator then tried to grant her Organization Policy Administrator directly on the two projects, and the grant was rejected. Security insists that she must not be able to change policies on any other team's projects, and team A will get more projects with the same tag next year. What should the organization administrator do?
A: Grant her Organization Policy Administrator at the organization with an IAM condition that matches the tag team=a, so it applies only to tagged resources
B: Grant her Organization Policy Administrator on the folder that holds team A's projects, since the folder is the lowest level this role accepts
C: Grant her Organization Policy Administrator at the organization without a condition, and use audit logs to detect changes to other teams' projects
D: Make her Organization Administrator on the organization, because that role includes managing organization policies on every project in it
K: A
G: ## Who can set organization policies
Managing organization policies needs `orgpolicy.policies.create`, `update` and `delete`, which come with **Organization Policy Administrator** (`roles/orgpolicy.policyAdmin`). The role reference lists its lowest grantable level as **Organization** only, which is why a grant on a project or a folder is rejected. Project Owner does not include these permissions.
## Delegating safely
The documented way to delegate is a **conditional role binding at the organization**, for example the condition `resource.matchTag('ORG_ID/team', 'a')`. The binding then applies only to resources that carry or inherit the tag, so Priya can manage policies on team A's projects, including future ones that get the tag, and nowhere else.
W: Conditional grant at the organization: the role can only be granted at the organization, and a tag condition limits it to team A's tagged projects, now and later.
X: B=Folder grant: like the project grant, it is rejected, because Organization Policy Administrator cannot be granted below the organization.
C=Unconditional grant plus logs: she could change policies anywhere in the organization; audit logs only show it afterwards, which security does not accept.
D=Organization Administrator: it is far broader (IAM on the whole organization) and still not limited to team A's projects.
T: Organization Policy Administrator is granted only at the organization; scope it to some projects with a tag-based IAM condition.

D=Net costs: spend caps use gross, estimated costs precisely so that they act quickly; there is no credit delay to wait for.

Creating a second Cloud SQL instance with a private IP in europe-west1 now fails with an error saying there is no free address range for the instance in the allocated ranges. Private services access connects your VPC network to Google's service producer network over VPC Network Peering. C=Release and recreate: releasing a range that is in use affects the existing instance, which must not be interrupted, and changing a range is a disruptive procedure.

X: B=Egress rule for responses: firewall rules are stateful, so replies to allowed connections are allowed, and the proxies, not clients, are the peers.
C=Forwarding rule IP as source: backend connections come from proxy-only subnet addresses, not from the frontend IP of the load balancer.
D=Global access: it only matters for clients in other regions; these clients are in us-central1 with the load balancer.

This morning the CI pipeline's `terraform plan` reports `Plan: 42 to add, 0 to change, 0 to destroy`, although all 42 resources exist and nobody changed the configuration. `gcloud storage ls --all-versions -l gs://acme-tfstate/prod/` shows `default.tfstate#1763370000` at 183 KB from yesterday 18:02 and `default.tfstate#1763452000` at 1 KB from today 08:15. Audit logs show the 08:15 write came from a script on an engineer's laptop that overwrote the object by mistake. Production must not be changed, and the team wants the fastest safe fix. What should the engineer do?
A: Copy the 18:02 generation over the live object with gcloud storage cp of default.tfstate#1763370000 to default.tfstate, then rerun terraform plan
B: Run terraform apply from the CI pipeline, so Terraform recreates the 42 resources and writes a complete new state file to the bucket
C: Run terraform import for each of the 42 resources from the CI pipeline, so that the empty state slowly learns about every existing resource
D: Delete the 08:15 generation with gcloud storage rm of default.tfstate#1763452000, so that the 18:02 generation becomes the live version again
K: A
G: ## State in a versioned bucket
Terraform maps configuration to real resources through its **state**. With a Cloud Storage backend and **Object Versioning** on, every write of `default.tfstate` keeps the previous version as a **noncurrent generation** (`object#GENERATION`), which is why Google's guide enables versioning on the state bucket.
## Restoring a generation
In Cloud Storage, restoring a noncurrent version means **copying it** over the live name:
`gcloud storage cp gs://acme-tfstate/prod/default.tfstate#1763370000 gs://acme-tfstate/prod/default.tfstate`
The copy becomes the live version and the bad 1 KB version becomes noncurrent. A new `terraform plan` should then show no changes.
## Why not delete
Deleting the live version does not promote an older generation; noncurrent versions stay noncurrent until one is copied back.
W: Copy the good generation back: it restores the full state in one command without touching any production resource, so the next plan shows no changes.
