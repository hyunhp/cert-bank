@ GCP-ACE D1 T1.2 applied use-case
S: A product manager wants a quick chart of last month's cost of everything labeled `team=mobile` across all projects on the billing account, grouped by service. Nobody wants to set up exports or write SQL. What should the manager use?
A: A budget scoped to the label `team=mobile`, because budgets chart past spending per service
B: Cloud Billing Reports with the label filter set to `team=mobile` and the grouping set to service
C: A detailed usage cost export to BigQuery, followed by a SQL query that sums cost by service
D: A Cloud Monitoring dashboard that plots the billing metrics of every project carrying the label
K: B
G: ## Reports, budgets and exports
Cloud Billing offers three different tools for cost data, and each answers a different question:
- **Reports** (Billing > Reports): a built-in chart and table of usage cost for the whole billing account. You choose a time range, filters (projects, services, SKUs, locations, **labels**) and a **Group by** (project, service, SKU, location). No setup is needed beyond access to the billing account.
- **Budgets and alerts**: compare spend with a target amount and notify people; they are not a reporting tool.
- **Billing export to BigQuery**: row-level data for SQL analysis, dashboards and long-term history. It must be enabled first and only fills from the moment it is turned on.
## Example
Open Reports for the billing account, set the date range to last month, add the filter Labels `team:mobile` and Group by Service. The chart and table show the answer immediately.
W: Cloud Billing Reports: it already supports label filters and grouping by service for all projects on the account, so the question is answered with no setup.
X: A=Budget: a budget watches spend against a threshold and sends alerts; it does not provide a historical breakdown chart per service.
C=BigQuery export: it would work for deeper analysis, but it needs to be enabled first, only holds data from then on, and the requirement says to avoid exports and SQL.
D=Monitoring dashboard: Cloud Monitoring tracks resource metrics such as CPU, not the cost data of the billing account.
T: For a quick, no-setup look at costs by label, project or service use Cloud Billing Reports; use BigQuery export for SQL-level analysis.
V: Cloud Billing

@ GCP-ACE D1 T1.2 applied troubleshooting
S: Last week an engineer added the label `cost-center=4711` to all Compute Engine VMs of a project. Today finance runs a query on the BigQuery billing export for the previous month, grouped by that label, and gets no rows with the label. The export has been running for a year. Why?
A: Labels can only be exported by the detailed usage cost export
B: The billing export is delayed, and labels from the previous month appear after the next invoice is finalized
C: New labels appear only in usage exported after the change; old rows are not rewritten
D: Labels on VMs are not exported at all; only labels set on the project are included in billing data
K: C
G: ## Billing export reflects the past as it was
Rows in the billing export tables record the state of resources **at the time the usage happened**. Google Cloud does not go back and rewrite them. The documentation spells out two examples: adding new labels to a project, and changing a project's hierarchy (which changes `project.ancestors`). Both show up only in future exports of usage data.
## What this means in practice
- Decide on a labeling scheme **before** you need it, and apply labels early.
- Labels can be used to group costs from the day they are applied, in Reports and in the export.
- To attribute older costs, join on other fields that existed back then, such as project or service.
W: Labels added later: previously exported records stay as they were, so last month's rows carry no `cost-center` label, while usage after the change will.
X: A=Detailed export required: labels appear in both the standard and the detailed usage cost export; the missing rows are caused by timing, not by the export type.
B=Delayed month-end: export data arrives continuously within a day or so and is never rewritten after an invoice; waiting would not add labels to old rows.
D=Only project labels: resource labels on VMs and other resources are part of the exported rows; the VMs simply had no label during last month.
T: Billing export records are not rewritten, so new labels or hierarchy changes affect only usage recorded afterwards.

@ GCP-ACE D1 T1.2 applied use-case
S: A team wants its monthly budget to follow its actual spending pattern: each calendar month the target amount should automatically equal what the project spent in the previous calendar month, with alert thresholds at 90% and 100%. Which budget setting fits?
A: Budget type "Last period's spend", which updates the target amount each budget period from the previous period's spend
B: Budget type "Specified amount", re-entered by an administrator at the start of each month with the earlier total
C: A custom date range budget that is edited at the end of each month to move the range forward by one month
D: A forecasted-spend threshold rule, which sets the target amount to the projected total of the current month
K: A
G: ## Two budget amount types
When you create a Cloud Billing budget you choose the **target amount**:
- **Specified amount**: a fixed value you enter; actual spend is compared with it. It works for calendar periods and custom date ranges.
- **Last period's spend**: a dynamic amount; the target updates automatically each budget calendar period from the previous calendar period's spend. It needs a calendar period (monthly, quarterly, yearly), not a custom range.
## Thresholds
Threshold rules (for example 90% and 100%) are percentages of the target and can be based on **actual** or **forecasted** spend. They do not change the target.
W: Last period's spend: the target is recalculated automatically every calendar month from the previous month's cost, and the 90% and 100% rules apply to that moving target.
X: B=Specified amount re-entered monthly: it can reproduce the number, but it is manual work that is easy to forget, while a built-in type does it automatically.
C=Custom date range edited monthly: custom ranges still need a specified amount and a manual edit every month, and they do not use the previous period's spend.
D=Forecasted threshold: a forecast-based rule triggers an alert when projected spend would reach a percentage of the target; it never sets the target itself.
T: A budget whose target should track last month's spend uses the "Last period's spend" amount type.
V: Cloud Billing

@ GCP-ACE D1 T1.2 applied definition
S: Which TWO statements about Cloud Billing accounts and projects are correct? (Select TWO)
A: A project can be linked to only one Cloud Billing account at a time, and its costs go to that account
B: A project can be linked to several billing accounts, and each service's cost goes to the account chosen for it
C: Unlinking a project keeps its paid services running until the end of the month, and the old account is billed for them
D: One Cloud Billing account can pay for the usage of many projects, so teams do not need an account each
E: A Cloud Billing account must be created inside the project it pays for and is deleted along with that project
K: A,D
G: ## Billing accounts and projects
A **Cloud Billing account** is a separate resource that defines who pays for usage. **Projects** use paid Google Cloud services only while they are linked to an active billing account.
- Many projects can be linked to the same billing account (a typical company has one or a few accounts and hundreds of projects).
- A project has **at most one** billing account at a time. Moving it means linking it to another account, after which new costs go to that account.
- If a project has no active billing account, its paid services stop working (free-tier-only usage aside); resources are not billed to anyone else.
- Billing accounts are not children of projects; they have their own IAM roles and live next to the resource hierarchy.
## Example
Fifty projects of a company link to `01A2B3-C4D5E6-F7A8B9`; the finance team manages budgets and invoices in one place.
W: A=One account per project: the project-to-account relationship is one account at a time; costs go to the account the project is linked to.
D=Many projects per account: a billing account can be linked to many projects, so one account can cover a whole company's projects.
X: B=Several accounts per project: a project cannot split its services across billing accounts; only one link exists at a time.
C=Services keep running after unlinking: once billing is disabled for a project, its paid services stop, and nothing keeps charging the old account.
E=Account created inside a project: billing accounts are independent resources with their own IAM, not children of a project, so deleting a project does not delete the account.
T: One project links to one billing account at a time; one billing account can serve many projects.
V: Cloud Billing

@ GCP-ACE D1 T1.2 applied use-case
S: Finance wants budget alerts for the production projects to be based on the real cost before any committed use discounts and promotional credits are subtracted, so that the team sees the full gross consumption. The default budget calculation subtracts them. What should be configured on the budget?
A: A custom date range that starts before the first credit was applied to the billing account, so credits are left out
B: A forecasted threshold, which always measures gross usage before credits and discounts
C: Billing export to BigQuery, since budgets read their data from it

G: ## Budgets and credits
When you create a budget, the **Savings** setting decides which discounts and credits are subtracted from the spend the budget measures. By default all savings types are selected, so actual spend is **total cost minus applicable discounts and credits**. Savings include committed use discounts, promotional credits, sustained use discounts, free tier credits and similar grants.
- If you want to monitor spend **before** discounts and credits, deselect the savings options.
- If credits exceed usage, the calculated spend can even become negative.
## Example
A team with a large promotional credit sees a budget at 0% all month. Deselecting all Savings shows gross spend and lets the alerts trigger on real consumption.
W: Savings settings: with no savings types selected, the budget measures the cost before discounts and credits, which is exactly the gross consumption finance asked for.
X: A=Custom date range: the range sets the period measured, not whether discounts and credits are subtracted, so credits would still be applied.
B=Forecasted threshold: forecasts project future totals using the same spend definition; they do not change whether savings are included.
C=Export with pricing table: budgets are evaluated by Cloud Billing itself and need no BigQuery export; exports are for analysis, not for budget settings.
T: To make a budget measure gross spend, deselect the Savings types in the budget's scope.

@ GCP-ACE D2 T2.3 applied troubleshooting
S: Two teams each use the `default` network in their own project. They want the VMs of both projects to talk over internal IPs and try to set up VPC Network Peering between the two default networks, but it cannot be created. What is the correct way forward?
A: Convert both default networks to custom mode with one command, then create the peering connection between them
B: Create a custom mode VPC network in each project with non-overlapping ranges, move the workloads there, and peer those
C: Create the peering from one project only; the other side is created automatically
D: Add a Cloud Router to each default network so that the peering exchanges its routes dynamically
K: B
G: ## Auto mode networks cannot be peered together
A new project starts with the `default` network, which is an **auto mode** VPC network: it has one automatically created subnet per region, all taken from the same predefined block `10.128.0.0/9`. Peered networks always exchange subnet routes, so their subnet ranges must not overlap. Because every auto mode network uses the same block, **two auto mode networks cannot be peered**.
## Why converting does not help
You can switch auto mode to custom mode (a one-way change with `gcloud compute networks update NETWORK --switch-to-custom-subnet-mode`), but the existing subnets keep their ranges, which still overlap.
## Fix
Create new custom mode networks with chosen, non-overlapping ranges, migrate the workloads and peer them. A custom network can peer with an auto mode one only if it has no range inside `10.128.0.0/9`.
W: New custom mode networks: with ranges you choose and no overlap, the peering can be created; this is the documented way around the auto mode restriction.
X: A=Convert to custom mode: the conversion is one-way and leaves the same overlapping `10.128.0.0/9` subnets in place, so the peering would still be refused.
C=One-sided peering: each side of a peering must be created separately in its own network, and it only becomes active when both exist; nothing is created automatically.
D=Cloud Router: peering exchanges subnet routes through its own mechanism; Cloud Router is used with VPN and Interconnect, and does not fix overlapping ranges.
T: Auto mode VPC networks cannot be peered with each other; use custom mode networks with non-overlapping ranges.
V: VPC, VPC Network Peering

@ GCP-ACE D2 T2.3 applied use-case
S: A batch team creates a new subnet `batch-subnet` in a custom mode VPC network for VMs that have no external IP addresses. The VMs must read and write Cloud Storage buckets without sending traffic to a NAT device. The network still has its default route to the default internet gateway and default egress rules. What should the engineer do?
A: Create the subnet with the `--enable-private-ip-google-access` option
B: Create a VPC Network Peering connection to the Google-managed network that hosts Cloud Storage
C: Create a private Cloud DNS zone for `googleapis.com`, since the names need it
D: Attach the subnet to a Shared VPC host project, so it can reach Google APIs
K: A
G: ## Private Google Access
VMs without external IP addresses can normally only reach internal destinations. **Private Google Access** is a **per-subnet** setting that lets VMs in the subnet, which have no external IP on the interface, reach the external IPs of Google APIs and services such as Cloud Storage, without a NAT device and without leaving Google's network.
## Requirements
- The VM interface is in a subnet where Private Google Access is on.
- The interface has no external IP address (VMs with one do not need it).
- The VPC meets the network requirements: for the default domains (`storage.googleapis.com`) that means a route to the API IP ranges (the default route to `default-internet-gateway`) and egress firewall rules that allow it; the default allow-egress rule does.
Enable it when creating the subnet (`--enable-private-ip-google-access`) or later with `gcloud compute networks subnets update`.
W: Private Google Access on the subnet: the default route and the default allow-egress rule already satisfy the network requirements, so enabling this one setting is all that is missing.
X: B=Peering to a Google network: there is no such peering for public APIs; Private Google Access is the feature built for this, and VPC peering connects customer VPCs.
C=Private zone for googleapis.com: with the default domains the public API names resolve without any special DNS; custom zones are only needed for private.googleapis.com or restricted.googleapis.com.
D=Shared VPC: it shares subnets across projects and has no relationship to reaching Google APIs; it does not enable access for VMs without external IPs.
T: VMs without external IPs reach Google APIs through Private Google Access, enabled per subnet.
V: VPC, Cloud Storage

@ GCP-ACE D2 T2.3 applied use-case
S: A team will create a VPC-native GKE cluster in a custom mode VPC network and wants full control over the IP ranges used for Pods and Services instead of letting GKE pick them. How should the subnet be prepared?
A: Create a subnet with two secondary IP ranges, one for Pods and one for Services, and select them when creating the cluster
B: Create three subnets in the region: one for nodes, one for Pods and one for Services, and attach all three to the cluster as primary ranges
C: Reserve a /16 range in a private Cloud DNS zone so that Pods and Services resolve inside the VPC network
D: Create the cluster in the default network, because custom mode networks assign Pod and Service ranges only by external IP
K: A
G: ## VPC-native clusters and alias IPs
A VPC-native GKE cluster uses **alias IP ranges**. The subnet has a **primary range** for node (VM) IPs and **secondary ranges** for Pod IPs and Service (cluster IP) IPs. Because the ranges are part of the VPC subnet, Pod IPs are natively routable inside the VPC and, with Cloud VPN or Cloud Interconnect through Cloud Router, also from on premises.
## Options
- Let GKE create secondary ranges automatically.
- Use **user-managed secondary ranges** you create beforehand on the subnet, which gives you control over sizes and avoids overlaps with other networks.
## Example
`gcloud compute networks subnets create gke-subnet --network=prod-vpc --region=us-central1 --range=10.0.0.0/22 --secondary-range=pods=10.4.0.0/14,services=10.8.0.0/20`
W: Subnet with secondary ranges: the cluster takes Pod and Service IPs from named secondary ranges on the node subnet, which is exactly the control the team wants.
X: B=Three subnets: primary ranges of other subnets cannot be used as Pod or Service ranges; the cluster needs secondary ranges on the node subnet.
C=Private DNS zone: DNS zones resolve names and never allocate IP ranges, so a zone cannot provide Pod or Service address space.
D=Default network: a cluster can use any network and subnet, and ranges have nothing to do with external IPs; custom mode is the right place to choose them.
T: VPC-native GKE clusters take Pod and Service IPs from secondary ranges on the node subnet.

@ GCP-ACE D2 T2.4 applied use-case
S: Three Cloud Storage buckets and a Pub/Sub topic were created by hand in the console last year. The team now manages new resources with Terraform and wants Terraform to manage these existing resources as well, without deleting and recreating them or losing data. What should the engineer do?
A: Write matching resource blocks and import each existing resource into the Terraform state, for example with `terraform import`
B: Run `terraform apply` with matching resource blocks, which takes over resources of the same name
C: Delete the resources and let Terraform recreate them after the data is copied elsewhere
D: Copy the resource names into a `terraform.tfvars` file, which tells Terraform that they already exist
K: A
G: ## Bringing existing resources under Terraform
Terraform manages only the resources recorded in its **state**. A resource created outside Terraform is unknown to it: if the configuration describes it, `terraform apply` tries to **create** it, which fails or duplicates it.
- **Import** attaches an existing real resource to a resource block in the state. Options: `terraform import ADDRESS ID` one at a time, an `import` block in the configuration (Terraform 1.5 or later) for bulk imports, or a Google Cloud bulk export that generates configuration.

W: Import into state: it links the existing buckets and topic to the resource blocks without recreating them, so data and settings stay, and later changes go through Terraform.
X: B=Apply alone: Terraform has no state entry for the resources, so it plans to create them; names alone are not enough to adopt them.
C=Delete and recreate: it works only after risky data copying and causes downtime, while importing needs neither.
D=tfvars file: variable files only provide input values; they do not change the state.
T: Existing resources enter Terraform management through import (command or import block), followed by plan to check for drift.

@ GCP-ACE D3 T3.3 applied troubleshooting
S: Users report that VM `app-1` in subnet `web` cannot connect to TCP port 5432 on VM `db-1` in subnet `data` of the same VPC network. The engineer wants to find out which firewall rule or route blocks the traffic, without logging in to either VM or generating real traffic first. Which tool fits best?
A: Connectivity Tests, with `app-1` as source, `db-1` as destination, TCP and port 5432
B: Cloud Trace, which follows the request from `app-1` to `db-1` and marks the slowest network hop
C: Cloud Profiler, which samples the CPU usage of the database process to show why connections fail and where
D: Cloud Asset Inventory, which lists the firewall rules and shows which of them is applied last
K: A
G: ## Connectivity Tests
**Connectivity Tests** (part of Network Intelligence Center) is a diagnostics tool for checking connectivity between network endpoints such as VMs, GKE clusters, load balancer forwarding rules or internet IPs. It **analyzes your configuration**: it simulates the expected forwarding path of a packet through the VPC network (routes, firewall rules, peering, VPN tunnels, VLAN attachments) and reports where the packet would be delivered or **dropped**, naming the responsible rule or route. For some scenarios it also performs a **live data plane analysis** that sends packets.
## Example
`gcloud network-management connectivity-tests create app-to-db --source-instance=app-1 --destination-instance=db-1 --protocol=TCP --destination-port=5432`
The result may say the packet is dropped by an ingress firewall rule on `db-1`.
W: Connectivity Tests: it simulates the path from the source to the destination for the protocol and port and shows the rule or route that drops the packet, without logging in to the VMs.
X: B=Cloud Trace: it traces latency of application requests that are instrumented with trace data, not the network path or firewall verdicts.
C=Cloud Profiler: it profiles CPU and memory use inside running applications and says nothing about firewall rules or routes.
D=Cloud Asset Inventory: it lists resources and their configuration, but it does not evaluate whether a particular flow would be allowed.
T: Use Connectivity Tests to find which firewall rule or route blocks traffic between two endpoints.

@ GCP-ACE D3 T3.3 applied use-case
S: VMs in the VPC network `prod-vpc` must resolve names under `corp.example.com.` using the company's on-premises DNS server at 10.200.0.53. The data center is connected to the VPC network with HA VPN. Names in other domains should still be resolved by Google Cloud as before. What should be configured?
A: An inbound server policy on `prod-vpc`, so that the on-premises server is queried first for every name in the VPC network
B: A public Cloud DNS managed zone for `corp.example.com.` with an NS record that points to 10.200.0.53
C: A private Cloud DNS forwarding zone for `corp.example.com.` authorized for `prod-vpc`, with 10.200.0.53 as the forwarding target
D: A Cloud NAT gateway with a rule that translates DNS queries for `corp.example.com.` to 10.200.0.53
K: C
G: ## Cloud DNS zone types for hybrid name resolution
- **Private managed zone**: records are stored in Cloud DNS and visible only to authorized VPC networks.
- **Forwarding zone**: a private zone that sends queries for a domain to other name servers, such as on-premises DNS. RFC 1918 targets must be reachable in your VPC or in an on-premises network connected by **Cloud VPN or Cloud Interconnect**.
- **Peering zone**: queries are answered using the resolution order of another VPC network.
- **Inbound server policy**: lets on-premises hosts resolve Google Cloud private names; the opposite direction.
## Example
`gcloud dns managed-zones create corp-fwd --description="on-prem" --dns-name=corp.example.com. --networks=prod-vpc --visibility=private --forwarding-targets=10.200.0.53`
Only queries for `corp.example.com.` go to the on-premises server; all other names keep their normal resolution.
W: Private forwarding zone: it sends only that domain's queries to 10.200.0.53 across the HA VPN and leaves all other resolution untouched.
X: A=Inbound server policy: it makes VPC resolvers reachable from on premises (on-premises to Google Cloud), not the other way around, and does not redirect queries to an on-premises server.
B=Public zone with NS record: public zones answer internet queries; VMs would not use it to reach a private on-premises server through the VPN.
D=Cloud NAT: NAT translates IP addresses of VM traffic to the internet and has no DNS rules.
T: To resolve an on-premises domain from a VPC, create a private forwarding zone that targets the on-premises DNS server.
V: Cloud DNS, Cloud VPN

@ GCP-ACE D3 T3.3 applied use-case
S: A cost review suggests that the project `legacy-apps` contains reserved static external IP addresses that are not attached to anything. An engineer wants to list them and release those no longer needed. Which approach is correct?
A: Run `gcloud compute addresses list`, keep status RESERVED, and release the unneeded ones with `delete`
B: Run `gcloud compute instances list` and delete every VM that has no external IP address attached to it
C: Ephemeral addresses are released only when the project is deleted, so the engineer should delete the entire project
D: Reserved addresses expire automatically after 30 days without use, so the engineer only needs to wait
K: A
G: ## Static external IP addresses are project resources
A **static external IP address** is a resource of your project that stays reserved until you release it, whether or not a VM uses it. An address that is reserved but not attached is shown with status **RESERVED**; an attached one is **IN_USE**. Google Cloud bills for reserved addresses that are not in use, so they are worth cleaning up. Do not confuse them with **ephemeral** addresses, which are released automatically when the resource is deleted.
## Commands
- `gcloud compute addresses list --filter="status=RESERVED"`: unused addresses (add `--global` for global ones).
- `gcloud compute addresses delete NAME --region=REGION`: release a regional address; first make sure nothing, such as an allowlist at a partner, still depends on it.
W: List and delete reserved addresses: filtering for RESERVED finds the unattached static addresses, and deleting them releases the reservation.
X: B=Delete VMs without external IP: VMs without an external address have nothing to release, and deleting VMs would destroy workloads instead of releasing reserved addresses.
C=Delete the project: ephemeral addresses go away with their VM automatically, and deleting the whole project is far more destructive than needed.
D=Wait 30 days: nothing expires a reservation; a reserved static address remains yours until someone releases it.
T: Reserved but unused static IPs show status RESERVED; list them and delete the ones not needed.
V: VPC, Compute Engine

@ GCP-ACE D3 T3.3 applied troubleshooting
S: The VPC network `hub-vpc` has a custom static route to the on-premises range 192.168.0.0/16 through a VPN tunnel. `spoke-vpc` is peered with `hub-vpc` and cannot reach 192.168.0.0/16, although VMs in the two networks reach each other. The engineer wants spoke VMs to use that route. What is needed?
A: Enable export of custom routes on the hub side and import of custom routes on the spoke side of the peering
B: Create a second peering from `spoke-vpc` to the on-premises network, because routes are shared through peering of data centers
C: Add a firewall rule in `spoke-vpc` that allows egress to 192.168.0.0/16, which makes the route appear in its route table
D: Recreate the peering as a Shared VPC attachment, because peered networks never exchange any routes
K: A
G: ## What peering exchanges
VPC Network Peering always exchanges **subnet routes** between the peered networks. It does **not** share your custom static routes or dynamic routes unless you configure it:
- the network that owns the route enables **export custom routes**;
- the peer network enables **import custom routes**.
(`gcloud compute networks peerings update NAME --network=hub-vpc --export-custom-routes`, and `--import-custom-routes` on the other side.)
## Also remember
- Peering is **not transitive**: spokes reach the hub but not each other.
- The route still needs a firewall and an on-premises return path to work; routes alone do not allow traffic.
W: Export and import of custom routes: the hub exports its custom route and the spoke imports it, so spoke VMs can send traffic to 192.168.0.0/16 through the hub's tunnel.
X: B=Peering to on premises: peering connects VPC networks and has no relation to data centers; the on-premises path is the existing VPN.
C=Egress firewall rule: firewall rules allow or deny traffic and do not add routes to a route table; the route is missing, not blocked.
D=Shared VPC: it is a different design (shared subnets in a host project); peered networks do exchange subnet routes, and custom routes can be exchanged by configuration.
T: Custom routes cross a VPC peering only when one side exports and the other side imports them.
V: VPC Network Peering, Cloud VPN

@ GCP-ACE D3 T3.2 applied use-case
S: A regulator requires that audit exports in `gs://acme-audit` cannot be deleted or overwritten for seven years, and that even project owners cannot shorten or remove this rule once it is in place. Which TWO actions meet the requirement? (Select TWO)
A: Set a bucket retention policy with a retention period of seven years
B: Lock the retention policy, which permanently prevents reducing or removing it

D: Set a lifecycle rule that moves objects to Archive after seven years

G: ## Retention policies and Bucket Lock
A **retention policy** on a bucket sets a retention period: objects can be deleted or replaced only once their age is greater than that period. On its own the policy can still be changed or removed by someone with the right permissions.
**Bucket Lock** locks the retention policy: the policy is **permanently** set, and the retention period can only be increased, never reduced or removed. Locking is irreversible, so check the period first. Together they provide immutable storage for compliance needs.

X: C=Versioning with lifecycle: versioning keeps older copies but allows live and noncurrent objects to be deleted by users who have permission; lifecycle rules delete data, they do not protect it.
D=Move to Archive: a storage class change lowers cost and does not stop deletion or overwrites.
E=Storage Object Admin for the audit team: an IAM role grants access, and holders of that role can delete objects; owners could also change the roles.
T: Immutable retention needs a bucket retention policy plus Bucket Lock to make it permanent.

@ GCP-ACE D3 T3.2 applied definition
S: A data team sets a default table expiration of 7 days on the existing BigQuery dataset `staging`, which already contains 20 tables with no expiration. Which TWO statements about this setting are correct? (Select TWO)
A: Tables already in the dataset keep their current expiration settings and do not expire because of the new default
B: All 20 existing tables are scheduled to be deleted exactly seven days after the setting is saved
C: New tables created in the dataset after the change get a 7-day expiration unless the table is created with its own expiration
D: A table created with its own expiration still expires after 7 days, because the dataset default always wins

G: ## Table expiration in BigQuery
A **default table expiration** can be set on a dataset. It applies automatically to **new tables** created in that dataset; the table is deleted when the time passes.
- If a table is created with its own expiration time, the dataset default is ignored for that table.
- Changing the dataset default from `Never` to a value does **not** affect tables that already exist; they expire only if an expiration was set on the table itself.

D=Dataset default always wins: an expiration specified on the table at creation overrides the dataset default.
E=Whole-dataset restore only: BigQuery lets you restore individual deleted tables within the time travel window.
T: A dataset default table expiration applies only to tables created later, and a table's own expiration overrides it.

@ GCP-ACE D3 T3.2 applied troubleshooting
S: The Cloud SQL for MySQL instance `orders-db` has automatic storage increases turned off, and writes now fail because the disk is full. The team wants the writes to work again, and wants the instance to avoid this problem in the future without regular manual resizing. What should the engineer do?
A: Enlarge the disk and run `gcloud sql instances patch orders-db --storage-auto-increase`
B: Recreate the instance with a smaller disk after exporting the data, which frees up space
C: Enable high availability, because the standby instance adds extra storage capacity to the primary

G: ## Cloud SQL storage
Cloud SQL storage capacity can be **increased but not decreased**. Two ways to grow it:
- Manually, by editing the instance and entering a larger size.
- Automatically: with **automatic storage increases** on, Cloud SQL adds storage when the instance gets close to the limit (it is on by default). You can set an upper limit; the default is no limit apart from the maximum for the instance.

D=Point-in-time recovery: it needs logs to be kept and does not reduce the size of the database files.
T: Cloud SQL storage can only grow; turn on automatic storage increases to avoid a full disk.
