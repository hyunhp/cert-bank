@ GCP-ACE D1 T1.2 applied use-case
S: A platform team lets developers create their own projects. Each new project must be paid for by the company's central Cloud Billing account, but developers must not see invoices, change payment methods or manage who has access to that billing account. Which role should the developers get on the billing account, in addition to Project Creator on their folder?
A: Billing Account User (`roles/billing.user`), which allows linking projects to the account and has very restricted permissions
B: Billing Account Administrator (`roles/billing.admin`), which allows linking projects and also manages the account's settings
C: Billing Account Viewer (`roles/billing.viewer`), which allows reading cost data and transactions recorded on the billing account
D: Billing Account Creator (`roles/billing.creator`), which allows creating new self-serve billing accounts at the organization level
K: A
G: ## Who pays for a project
A **Cloud Billing account** defines who pays for a set of projects. A project uses paid services only while it is linked to an active billing account. Linking needs permissions on **both sides**: on the project (`resourcemanager.projects.createBillingAssignment`) and on the billing account (`billing.resourceAssociations.create`).
## The predefined billing roles
- **Billing Account Creator** (`roles/billing.creator`): create new self-serve billing accounts; granted at the organization.
- **Billing Account Administrator** (`roles/billing.admin`): the owner role of a billing account: payment methods, exports, costs, link and unlink projects, and manage other users' roles.
- **Billing Account Costs Manager** (`roles/billing.costsManager`): budgets, cost views and cost export, no project linking.
- **Billing Account Viewer** (`roles/billing.viewer`): read costs and transactions, usually for finance.
- **Billing Account User** (`roles/billing.user`): link projects to the account. Its permissions are very restricted, so it can be granted broadly.
- **Project Billing Manager** (`roles/billing.projectManager`): on a project, link and unlink it, without access to its resources.
## Example
Granting Billing Account User on the billing account plus Project Creator on a folder lets a developer run `gcloud projects create` and then link the new project to the central account, and nothing more on the billing side.
W: Billing Account User: the docs describe exactly this pairing: Billing Account User together with Project Creator lets users create new projects linked to the billing account, while the role itself carries no rights over payments, invoices or account IAM.
X: B=Billing Account Administrator: it can link projects, but it is the owner role of the account, including payment methods, exports and managing other users' roles, which breaks least privilege.
C=Billing Account Viewer: it is read-only for costs and transactions and does not include the permission to link a project to the account, so new projects would stay without billing.
D=Billing Account Creator: it creates new self-serve billing accounts, which leads to untracked spend outside the central account and does not link projects to the existing one.
T: Let people attach projects to a billing account with Billing Account User; keep Billing Account Administrator for the few who own the account.

@ GCP-ACE D1 T1.2 applied use-case
S: The finance department wants two analysts to see the costs, transactions and payment documents of the company's Cloud Billing account. They must not be able to link or unlink projects, create budgets or change any account settings. Which predefined role on the billing account fits this best?
A: Billing Account Viewer, which gives read access to cost and payment information without managing the billing account
B: Billing Account Costs Manager, which shows cost information and also lets the analysts create, edit and delete budgets
C: Billing Account User, which lets the analysts attach projects to the account while hiding its payment information
D: Project Billing Manager, which is granted on each project and lets the analysts view that project's invoices directly
K: A
G: ## Matching billing roles to jobs
Cloud Billing roles separate duties so that each team gets only what it needs:
- **Viewing** costs and transactions: Billing Account Viewer (`roles/billing.viewer`). The docs note it is usually granted to finance teams.
- **Managing cost tools** such as budgets and cost exports: Billing Account Costs Manager (`roles/billing.costsManager`).
- **Attaching projects**: Billing Account User on the account plus Project Billing Manager (or Project Owner) on the project.
- **Owning the account**: Billing Account Administrator.
## Where to grant
Billing roles are granted on the **billing account** (or on the organization to apply to all its billing accounts). Costs for one project only can be viewed with project-level cost permissions such as `billing.resourceCosts.get`, but invoices and payment information belong to the billing account, not a project.
W: Billing Account Viewer: it provides read access to cost and payment information and explicitly does not allow linking or unlinking projects or managing account properties, which is exactly the finance analysts' need.
X: B=Billing Account Costs Manager: it shows costs, but it also creates, edits and deletes budgets and manages cost exports, which the analysts must not be able to do.
C=Billing Account User: its purpose is linking projects to the account, the very action the analysts must not perform, and it is not meant for reading costs and payment documents.
D=Project Billing Manager: it only links and unlinks a project to a billing account; it grants no view of invoices, which live on the billing account rather than on a project.
T: Read-only access to billing costs and transactions is Billing Account Viewer; anything that changes budgets, links or settings needs a stronger role.

@ GCP-ACE D1 T1.2 advanced comparison
S: A FinOps engineer must create and edit budgets for every project on the billing account and set up the usage cost export to BigQuery. Security policy says the engineer must not link or unlink projects or manage who has access to the billing account. Which role should be granted on the billing account?
A: Billing Account Costs Manager, which manages budgets and the export of cost data but cannot link projects or manage account properties
B: Billing Account Administrator, which manages budgets and the export of cost data and also controls the account's role assignments
C: Billing Account Viewer, which reads cost data and transactions and can edit budgets that other administrators already created
D: Project Billing Costs Manager, which manages budgets and the cost export for every project linked to the billing account without project roles
K: A
G: ## Costs Manager versus Administrator
Both roles can work with budgets and cost exports, but they differ in what else they allow:
- **Billing Account Costs Manager** (`roles/billing.costsManager`): create, edit and delete budgets, view cost information and transactions, and manage the export of billing **cost** data to BigQuery. It does **not** allow linking or unlinking projects or managing the account's properties, and it cannot export pricing data.
- **Billing Account Administrator** (`roles/billing.admin`): everything above plus payment methods, pricing export, project links and `setIamPolicy` on the account.
## Project-scoped variant
**Project Billing Costs Manager** (`roles/billing.projectCostsManager`) gives billing information scoped to projects, and only when combined with cost view permissions on those projects. It is meant for project teams, not for a central engineer covering the whole account.
## Export permissions
To set up the standard or detailed usage cost export you need Costs Manager or Administrator on the billing account, plus BigQuery User on the project that holds the dataset.
W: Billing Account Costs Manager: it covers budgets and the cost export to BigQuery for the whole billing account while excluding project links and account administration, the exact split the security policy asks for.
X: B=Billing Account Administrator: it can do the work, but it is the owner role that also links projects and manages other users' roles, which the policy forbids.
C=Billing Account Viewer: it is read-only; it cannot create or edit budgets and cannot configure the export of billing data to BigQuery.
D=Project Billing Costs Manager: it only shows billing information for projects where the user also has cost view permissions, and it is not the role that manages the account-wide cost export.
T: Budgets and cost export without control of project links or account IAM = Billing Account Costs Manager.

G: ## Two sides of a project's billing link
A project is linked to exactly one Cloud Billing account at a time. Changing the link is an action on **both** resources:
- On the **project**: `resourcemanager.projects.createBillingAssignment` (and `deleteBillingAssignment` to remove the old link). Project Billing Manager and Project Owner have these.
- On the **target billing account**: `billing.resourceAssociations.create`. Billing Account User and Billing Account Administrator have it.

Project Billing Manager lets someone attach the project to a billing account **without** granting rights over the project's resources. The docs say Project Owners can use it to let someone else manage billing for the project. The docs' full role list for this task also adds Project Browser and Service Usage Viewer on the project, plus Billing Account Viewer on the accounts for listing links.

`gcloud billing projects link web-prod --billing-account=0X0X0X-0X0X0X-0X0X0X` moves the project to the new account if it is already linked to another one.

B=Billing Account User: it holds `billing.resourceAssociations.create` on the new account, which is required to link any project to that account.
X: C=Project Editor: Editor is a basic role that can modify most resources in the project, which the owner wants to avoid, and it is not the role the docs list for billing links.
D=Billing Account Viewer only: it can list which projects are linked, but it cannot create a new link, so the move would fail on the billing account side.
E=Billing Account Creator: it lets a user create new self-serve billing accounts; it gives no permission to link a project to the existing new account.
T: Linking a project needs a project-side role (Project Billing Manager or Owner) and a billing-account-side role (Billing Account User or Administrator).

@ GCP-ACE D1 T1.2 applied use-case
S: A company has used a self-serve Cloud Billing account paid by credit card for two years. Finance now wants a single monthly invoice paid by wire transfer within agreed payment terms. What should the company do?
A: Have a Billing Account Administrator of the current account apply for monthly invoiced billing and check eligibility
B: Change the charging cycle of the self-serve account from Postpay to monthly invoice on the Payment settings page
C: Create a second self-serve billing account and choose wire transfer as its payment instrument during sign-up
D: Switch the self-serve account to the Prepay charging cycle and top it up each month with one wire transfer
K: A
G: ## Two types of Cloud Billing account
- **Self-serve (online)**: created online by anyone allowed to create billing accounts. The payment instrument is a credit or debit card, or ACH direct debit where available. Costs are charged automatically, either monthly or when a threshold amount is reached.
- **Invoiced (offline)**: Google sends a monthly invoice (by mail or electronically); you pay by **check or wire transfer** within the payment terms you agreed with Google.
## How you get an invoiced account
Every new billing account starts as self-serve. Invoiced accounts are configured by Google: you apply, and Google checks eligibility, which includes being a registered business for at least one year, expected spend levels and availability in your country. To apply, you must be a **Billing Account Administrator** of the organization's current billing account.
## What you cannot do yourself
For self-serve accounts the charging cycle is assigned automatically; you cannot choose or edit the Postpay cycle type.
W: Apply for invoiced billing: invoiced accounts are set up by Google after an eligibility check, the result is a monthly invoice payable by check or wire transfer, and the application must come from a Billing Account Administrator.
X: B=Change charging cycle: the charging cycle of a self-serve account is assigned automatically and cannot be edited, and no setting turns a self-serve account into an invoiced one.
C=New self-serve account with wire transfer: self-serve accounts pay with cards or direct debit charged automatically; wire transfer against an invoice is a feature of invoiced accounts only.
D=Switch to Prepay: Prepay is a charging cycle for specific services such as the Gemini API in AI Studio, not a general way to pay all Google Cloud usage by monthly invoice.
T: Monthly invoices paid by check or wire need an invoiced Cloud Billing account, which you apply for as a Billing Account Administrator; you cannot convert one yourself.

@ GCP-ACE D1 T1.2 applied use-case
S: An engineer must move the project `analytics-dev` to the Cloud Billing account `01A2B3-C4D5E6-F7A8B9` from the command line, without a gap during which billing is disabled. Which command does this?
A: `gcloud billing projects link analytics-dev --billing-account=01A2B3-C4D5E6-F7A8B9`
B: `gcloud projects update analytics-dev --billing-project=01A2B3-C4D5E6-F7A8B9`
C: `gcloud billing projects unlink analytics-dev` and then `gcloud projects create` again

G: ## Billing commands for projects
The `gcloud billing projects` group manages the link between a project and a billing account:
- `gcloud billing projects describe PROJECT_ID`: shows the project's billing info, including which account it uses and whether billing is enabled.
- `gcloud billing projects link PROJECT_ID --billing-account=ACCOUNT_ID`: sets **or updates** the billing account. If the project is already linked to another account, the command moves it.
- `gcloud billing projects unlink PROJECT_ID`: removes the link, which **disables billing** and stops paid services.
Billing account IDs look like `0X0X0X-0X0X0X-0X0X0X`; `gcloud billing accounts list` shows the ones you can use.
## Moving without downtime
Switching a project to another billing account should not interrupt services. Charges incurred before the move stay on the old account; later charges go to the new one.
W: gcloud billing projects link: it sets or updates the billing account of a project, so on an already linked project it moves the link in one step without disabling billing in between.
X: B=gcloud projects update --billing-project: `gcloud projects update` only changes the project name, and `--billing-project` is a global flag that picks the project used for API quota and billing of the request, not the project's billing account.
C=Unlink then recreate: unlinking disables billing and stops paid services, and creating a new project does not move the existing project's resources to another account.
D=gcloud billing budgets create: it creates a budget on the billing account; it does not change which account pays for the project.
T: `gcloud billing projects link` both links and moves a project between billing accounts; `unlink` disables billing.

- Charges incurred **before** the move are billed to the **former** account, including charges that had not yet appeared in the transaction history (some services take up to two days to report).
- Charges incurred **after** the move are billed to the **new** account.

## Other things to check before moving
- Resource-based committed use discounts from the moved project apply in the destination account only.
- Some costs belong to the billing account, not a project (for example Support); review them under "Charges not specific to a project".
- Cloud Marketplace purchases must be transferred before the project can move.

X: B=Linked to both accounts: a project is linked to only one billing account at a time; there is no half-finished state with double billing that needs an unlink.
C=Billing mistake needing support: the split is documented behavior, not an error, and nothing reassigns the earlier usage to the new account.
D=Old account keeps the whole month: costs move with the change date, not at the end of the month, so seeing May 16 to 31 on account B shows the move worked.

@ GCP-ACE D1 T1.2 advanced tradeoff
S: To stop costs from an unused test environment, an administrator plans to disable billing on the project `net-host`. That project is the Shared VPC host for three service projects that run production VMs. What will be the effect?
A: Billing stops in `net-host`, and VMs in the three service projects that use its Shared VPC networks are shut down too
B: Billing stops in `net-host` only, while the service projects keep running because they are linked to their own billing account
C: Billing stops in `net-host` after its committed use discounts expire, and until then all of its resources keep running normally
D: Billing stops in `net-host` for new resources only, while existing VMs and disks in the project keep running and accrue no charges
K: A
G: ## What disabling billing does
Billing is disabled on a project when it is unlinked from its billing account (or the account is closed or suspended). Then:
- all Google Cloud services in the project **stop**, and billing on the project stops;
- some resources may be **deleted and not recoverable**, so back up data first;
- you remain responsible for charges already incurred.
## Shared VPC side effect
In Shared VPC, a **host project** owns the network and **service projects** attach VMs to it. If billing is disabled on the host project, services in the service projects that depend on the Shared VPC are disabled too: every Compute Engine instance whose network interface uses the Shared VPC is shut down, in all attached service projects.
## Other limits
You cannot disable billing on a project that has active or pending committed use discounts, or one whose billing link is locked.
## Safer plan
Delete or stop the unused test resources in `net-host` instead of unlinking the whole host project.
W: Service projects affected: the docs state that disabling billing on a Shared VPC host shuts down all Compute Engine instances that use the Shared VPC as their network interface, across every attached service project.
X: B=Only the host stops: the service projects' own billing link does not help, because their VMs depend on the host project's network, which goes down with the host.
C=Waits for CUDs to expire: a project with active or pending CUDs cannot have billing disabled at all; the action is blocked, not delayed until expiry.
D=Only new resources blocked: disabling billing stops all of the project's services, existing ones included, and some resources may even be deleted.
T: Disabling billing stops everything in the project, and on a Shared VPC host it also takes down service-project VMs that use that network.

@ GCP-ACE D1 T1.2 applied use-case
S: Last quarter a production project was accidentally moved to a test billing account and later unlinked, causing an outage. The billing administrator wants any future change to that project's billing link to require a deliberate extra step. What should the administrator do?
A: Lock the link between the project and its Cloud Billing account, so it must be unlocked before any move or unlink
B: Place a lien on the production project, so it cannot be moved to another billing account until the lien is removed

A project can use Google Cloud services only while it is linked to an active billing account. An unintended move or unlink can stop every paid service in it.
## Locking the link
Cloud Billing lets you **lock the link** between a project and its billing account. While locked:
- the project cannot be moved (linked) to a different billing account;
- the link cannot be deleted, so billing cannot be disabled by unlinking.
To change anything, someone must first **unlock** the link, which turns a one-click mistake into an intentional two-step process. Locking requires the same pair of roles as linking (Project Billing Manager or Owner on the project, Billing Account User or Administrator on the account).

- A **lien** protects a project from deletion.
- A budget setting **Read-only for project users** protects the budget's configuration, not the project's billing link.

C=Read-only single-project budget: this setting stops project users from editing that budget; it has no effect on linking or unlinking the project.
D=Pub/Sub relink function: it would react after the outage has already started, and it adds a fragile automation instead of preventing the change in the first place.
T: To guard a critical project's billing, lock its link to the billing account; changes then need an explicit unlock first.

G: ## Who receives budget alert emails
Budget **threshold rules** trigger alert emails. Recipients come from these options:

A **Pub/Sub topic** connected to a budget receives JSON messages for code to process (for example, forwarding to Slack). Pub/Sub delivers messages to subscribers such as push endpoints or pull clients; it does not email people by itself.

C=Project Owners option: it is only available for single-project budgets and would email project owners, not these two managers who may not own any project.
D=Pub/Sub topic: Pub/Sub carries machine-readable messages to subscribers such as functions; it does not send email to people's addresses on its own.

@ GCP-ACE D1 T1.2 advanced use-case
S: A team has a monthly budget for its project. Leadership wants a warning in the first half of the month if current usage trends mean the spend will exceed the budget by month end, rather than finding out only after the money is spent. Which threshold rule meets this?
A: A threshold rule triggered on forecasted spend at 100% of the monthly budget amount
B: A threshold rule triggered on actual spend at 100% of the monthly budget amount
C: A budget amount type of last period's spend with the default actual spend thresholds
D: A budget with a custom date range for the first half of each month on actual spend
K: A
G: ## Actual versus forecasted thresholds
A budget compares spend with a target amount. Each **threshold rule** has a percentage and a basis:
- **Actual**: fires when the cost accrued so far in the period exceeds the threshold. A 50% actual rule on a 100 unit budget fires once 50 units are spent.
- **Forecasted**: fires when the cost **forecast to the end of the current calendar period** exceeds the threshold. A 110% forecasted rule fires as soon as the forecast passes 110 units, possibly early in the month.
New budgets get default thresholds of 50%, 90% and 100% on **actual** spend.
## Limits
- Forecasted rules need a calendar period (monthly, quarterly, yearly); budgets with a custom time range cannot trigger on forecasted costs.
- In `gcloud billing budgets create`, `--threshold-rule=percent=1.0,basis=forecasted-spend` sets such a rule.
W: Forecasted spend at 100%: it alerts when the end-of-month forecast passes the budget, so leadership hears about it while there is still time to act.
X: B=Actual spend at 100%: it fires only once the budget has already been spent, which is the late warning leadership wants to avoid.
C=Last period's spend amount: it changes the target amount to last month's spend, but with actual thresholds it still reports only money already spent.
D=Custom date range: custom-range budgets cannot alert on forecasted costs, and tracking half a month of actual spend does not predict the month-end total.
T: To be warned before the budget is exceeded, use a forecasted threshold rule on a calendar-period budget; actual rules report spend already incurred.

@ GCP-ACE D1 T1.2 advanced troubleshooting

T: Forecast alerts need a calendar-period budget; custom date range budgets only alert on actual spend.

S: A university gives each student a sandbox project with a fixed budget. When a sandbox's costs reach its budget, all paid services in that project must stop automatically, and the team accepts that the project may be shut down. Which steps should the team take? (Select TWO)
A: Connect a Pub/Sub topic to each project's budget so that budget status messages are published programmatically
B: Deploy a Cloud Run function on that topic that compares cost with budget and unlinks billing through the Cloud Billing API
C: Set the alerts-only budget's 100% actual threshold rule, which pauses every service in the project when the amount is reached
D: Lower the project's Compute Engine quotas to the budget amount so that resource creation stops when the money runs out
E: Add a Cloud Monitoring email channel to the budget so that the alert email disables the project's billing link on delivery
K: A,B
G: ## Alerts-only budgets do not stop spending
An alerts-only budget only **notifies**: emails at threshold rules and, optionally, messages to a **Pub/Sub topic**. To act on spend, you automate the response.
## The documented pattern
1. Create a Pub/Sub topic (the docs suggest a FinOps admin project for billing topics) and **connect it to the budget**.
2. Deploy a **Cloud Run function** triggered by the topic. It decodes the message, compares `costAmount` with `budgetAmount`, and if the cost is over, calls the Cloud Billing API (`updateProjectBillingInfo` with an empty `billingAccountName`) to **disable billing** on the project.
3. Give the function's service account permission to change the project's billing link (the sample grants Billing Account Administrator on the billing account).
## Caveats
- Disabling billing stops **all** services in the project, and some resources may be deleted.
- Cost data arrives with a delay, so spend can exceed the budget a little; set the budget below the real limit.
- A project whose billing link is locked cannot have billing disabled.
## Spend cap budgets are narrower
Cloud Billing also offers **spend cap budgets**, which pause usage automatically, but only for a single project and a single eligible API-based service (Gemini API, Gemini Enterprise Agent Platform, Cloud Run, Cloud Run functions), and they do not pause persistent resources such as VMs and disks. They cannot stop every paid service in a project, so the documented way to do that is still disabling billing from a budget notification.
W: A=Pub/Sub topic on the budget: programmatic notifications are how a budget hands its current status to code; without a connected topic there is nothing for automation to react to.
B=Cloud Run function that disables billing: the documented example reads the budget message and unlinks the project's billing account through the Cloud Billing API, which stops all paid services in the project.
X: C=Threshold pauses services: threshold rules of an alerts-only budget trigger notifications only; reaching 100% does not stop any service by itself.
D=Quotas as a spending cap: quotas limit amounts of resources, not money, so they cannot track a cost amount and do not stop usage of resources that already exist.
E=Email channel disables billing: an email notification is delivered to people's inboxes; it cannot change the project's billing link.
T: Alerts-only budgets only notify; to cut spend automatically, connect a Pub/Sub topic and let a function disable billing (accepting delays and shutdown).
V: Cloud Billing, Pub/Sub, Cloud Run functions

@ GCP-ACE D1 T1.2 advanced troubleshooting
S: A team's Cloud Run function subscribes to a budget's Pub/Sub topic and shuts down a project's dev VMs whenever a message arrives. The VMs are stopped several times a day, even though spend is far below the budget and no threshold has been crossed. What is the cause?
A: Budgets publish status messages to the topic several times a day, so the function must compare `costAmount` with `budgetAmount` first
B: Pub/Sub retries every message until the function stops the VMs, so each retry is seen as a new alert from the budget on the topic
C: Budgets publish to the topic only when a threshold is crossed, so the extra messages must come from another budget sharing the topic
D: The forecasted thresholds on the budget fire once per hour by default, so the function must ignore messages that carry the forecast key
K: A
G: ## Two notification cadences
- **Email alerts** are sent only when a threshold rule is crossed.
- **Pub/Sub notifications** are sent to the topic **multiple times per day** with the current status of the budget, even when nothing has been crossed and even if the account has no usage.
## What a message contains
Attributes: `billingAccountId`, `budgetId`, `schemaVersion`. Data (base64-encoded JSON): `budgetDisplayName`, `costAmount`, `budgetAmount`, `costIntervalStart`, `currencyCode`, and, only when exceeded, `alertThresholdExceeded` and `forecastThresholdExceeded`.
## Writing the subscriber
- Decide from the data, for example `if costAmount > budgetAmount`, or check whether `alertThresholdExceeded` is present.
- Pub/Sub delivery is **at least once** and can be out of order, so the action should be idempotent (stopping an already stopped VM does no harm).
W: Status messages several times a day: Pub/Sub budget notifications are periodic status updates, not threshold events, so code that acts on every message reacts to routine updates; it must check the cost against the budget or thresholds first.
X: B=Retries until success: Pub/Sub redelivers unacknowledged messages, but the function succeeds when it stops the VMs; the frequent messages are new status updates from the budget.
C=Only on threshold crossing: that is the email cadence; the docs state Pub/Sub notifications arrive multiple times per day regardless of thresholds.
D=Hourly forecast messages: there is no hourly forecast firing; `forecastThresholdExceeded` is present only when a forecasted threshold has actually been exceeded.
T: Budget Pub/Sub messages are periodic status reports; subscriber code must decide from `costAmount`, `budgetAmount` or the exceeded-threshold fields.
V: Cloud Billing, Pub/Sub, Cloud Run functions

@ GCP-ACE D1 T1.2 advanced troubleshooting
S: All production projects carry the project label `env=prod`. An engineer creating a budget wants to scope it with that label, but `env=prod` does not appear in the budget's label filter, while resource labels such as `app=checkout` do. How should the engineer scope the budget to the production projects?
A: Select the production projects in the budget's project scope, or place them in one folder and scope the budget to that folder
B: Wait until the label shows usage in the next billing cycle, because new project labels appear in budget filters only after one month
C: Grant the engineer Billing Account Administrator, because only administrators can see project labels in budget scope filters
D: Copy the project label into a tag binding on each project, because budget scopes filter on tags instead of on project labels
K: A
G: ## Budget scope options
An alerts-only budget can cover the whole billing account or a subset:
- one or more **organizations, folders or projects** paid by the billing account;
- one or more **services**, such as Compute Engine or BigQuery;
- **resources with a specific label**;
- with or without **savings** (credits and discounts).
## The label catch
The label filter only lists **user labels applied to resources** that have usage. **Labels applied to a project are not available** as a budget scope.
## Folder scope
Scoping to a folder includes its projects, but only those paid by this billing account; projects in the folder that use another billing account are not covered.
## gcloud
`gcloud billing budgets create` offers `--filter-projects=projects/PROJECT_ID`, `--filter-resource-ancestors=folders/FOLDER_ID` and `--filter-labels=KEY=VALUE` (one label pair).
W: Project or folder scope: project labels are not selectable as a budget scope, so the reliable way to cover exactly the production projects is to list them in the project scope or group them in a folder and scope to the folder.
X: B=Wait a billing cycle: the label is missing because project labels are never offered as a budget scope, not because it lacks usage; waiting will not change that.
C=More billing permissions: the role does not change which labels are offered; project labels are excluded for every user.
D=Use tags instead: the budget scope offers projects, folders, services, resource labels and savings; the docs do not list tags as a budget scope filter.
T: Budget label filters use resource labels only; to budget for a set of projects, scope by projects or by their folder.

@ GCP-ACE D1 T1.2 applied comparison
S: A cost analyst must find which individual Compute Engine VMs and persistent disks are driving a rise in costs, using SQL over billing data in BigQuery. Which Cloud Billing export should be enabled?
A: Detailed usage cost export, which adds resource-level cost data to everything in the standard usage cost export
B: Standard usage cost export, which lists cost by service, SKU, project and label without the individual resources
C: Pricing data export, which lists each SKU's list and contract prices for the billing account, without any usage
D: Cost table report download, which saves the invoice month's costs as a CSV file grouped by project and service
K: A
G: ## Cloud Billing export to BigQuery
Billing data can be exported automatically throughout the day to a BigQuery dataset. Each export type is enabled separately and writes its own table:
- **Standard usage cost** (`gcp_billing_export_v1_<BILLING_ACCOUNT_ID>`): account ID, invoice month, services, SKUs, projects, labels, locations, cost, usage, credits. Good for broad trends.
- **Detailed usage cost** (`gcp_billing_export_resource_v1_<BILLING_ACCOUNT_ID>`): everything in standard **plus resource-level cost data**, such as a VM or SSD that generates usage. Good for finding which resources drive costs.
- **Pricing** (`cloud_pricing_export`): prices of services and SKUs for the billing account, no usage.
## Notes
- GKE cluster cost breakdowns in the detailed export also need **GKE cost allocation** enabled.
- Storing and querying exported data incurs normal BigQuery charges; the detailed table has more rows, so use standard for trends and detailed for resource-level digging.
W: Detailed usage cost export: it is the export with resource-level cost data, so the analyst can group by individual VM or disk and find the ones behind the increase.
X: B=Standard usage cost export: it shows costs by service, SKU, project and label, which reveals the trend but not which individual resources caused it.
C=Pricing data export: it contains prices per SKU, not usage or costs, so it cannot show which resources consumed money.
D=Cost table CSV: it is a manual report download, not a continuous BigQuery export, and it does not give resource-level rows for SQL analysis.
T: Need costs per individual resource in BigQuery = detailed usage cost export; trends only = standard export.
V: Cloud Billing, BigQuery

@ GCP-ACE D1 T1.2 advanced tradeoff
S: A company is about to enable the standard usage cost export to BigQuery for a billing account it has used for several months. Finance wants the new dataset to start with the current month and the previous month's costs, not only costs from the day the export is enabled. How should the dataset be created?
A: In the US or EU multi-region, because multi-region datasets receive the current and previous month retroactively
B: In a single supported region close to the analysts, because regional datasets receive the past twelve months
C: In any location, because every export type backfills all costs since the billing account was first created
D: In a single supported region, and then change the dataset's location to a multi-region once the backfill ends
K: A
G: ## Where to put the billing dataset
Exported billing data lives in a BigQuery dataset inside a project that you choose. The docs recommend a separate **FinOps or billing administration project** linked to the same billing account.
## Location decides the backfill
- **Multi-region (US or EU)**: the dataset gets billing data from the **start of the previous month** when you first enable the export, so the current and previous month are added retroactively. The initial backfill can take up to five days.
- **Supported single region**: standard and detailed cost data only start from the day you enable the export; nothing earlier is added.
- **Pricing export**: never retroactive, whatever the location.
## Location is permanent
A BigQuery dataset's location is set at creation and cannot be changed. If you later switch the export to another dataset, earlier data is not copied there; you join the old and new datasets yourself.
W: US or EU multi-region: for the standard and detailed usage cost exports, a multi-region dataset receives data from the start of the previous month, which gives finance the current and previous month.
X: B=Single region with twelve months: regional datasets receive no retroactive data at all; costs only appear from the day the export is enabled.
C=Any location, full history: the backfill covers at most the current and previous month, and only for multi-region datasets.
D=Change location later: a dataset's location cannot be changed after creation, and switching the export to a new dataset does not copy the earlier data.
T: Create the billing export dataset in the US or EU multi-region to get the previous month backfilled; regional datasets start from the enable date.
V: Cloud Billing, BigQuery

@ GCP-ACE D1 T1.2 advanced use-case
S: A FinOps lead wants to export the billing account's pricing data to a BigQuery dataset in the project `finops-admin`, which is linked to the same billing account. The first attempt failed. Which requirements apply to the pricing export? (Select TWO)
A: The BigQuery Data Transfer Service API must be enabled in the `finops-admin` project that holds the dataset
B: The person setting it up needs Billing Account Administrator, because Costs Manager cannot export pricing
C: The dataset must be in a single region, because the pricing export does not accept US or EU multi-regions
D: The `finops-admin` project must be linked to another billing account than the one whose prices are exported
E: The person setting it up needs Project Billing Manager on `finops-admin` instead of any role on BigQuery
K: A,B
G: ## Pricing export is different from cost exports
The pricing export writes the billing account's prices for services and SKUs into the `cloud_pricing_export` table. Compared with the standard and detailed usage cost exports it has extra requirements:
- the **BigQuery Data Transfer Service API** must be enabled in the same project as the dataset (the BigQuery API is needed for every export);
- **Billing Account Administrator** on the billing account (Costs Manager can manage cost exports but not pricing);
- **BigQuery Admin** on the dataset's project and `resourcemanager.projects.update` on it.
## Common to all exports
- The dataset's project must have billing enabled and be linked to the **same** billing account whose data is exported; pricing data is specific to the account linked to that project.
- Dataset location: US or EU multi-region, or a supported region.
- Pricing data is never added retroactively.
W: A=BigQuery Data Transfer Service API: the pricing export uses it, and the docs require it to be enabled in the same project that contains the dataset.
B=Billing Account Administrator: setting up the pricing export needs Administrator on the billing account; Costs Manager explicitly does not confer the right to export pricing data.
X: C=Single region only: billing exports support both multi-region (US, EU) and a set of single regions; multi-regions are actually recommended.
D=Different billing account: the dataset project must be linked to the same billing account, and the pricing data reflects the account linked to that project.
E=Project Billing Manager instead of BigQuery roles: that role only links and unlinks the project; the export needs BigQuery Admin on the project for pricing data.
T: Pricing export = Billing Account Administrator + BigQuery Data Transfer Service API in the dataset's project, which is linked to the same billing account.
V: Cloud Billing, BigQuery
