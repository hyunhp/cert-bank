@ GCP-ACE D3 T3.3 applied use-case
S: A cost review suggests that the project `legacy-apps` contains reserved static external IP addresses that are not attached to anything. An engineer wants to list them and release those no longer needed. Which approach is correct?
A: Wait 30 days, because a reserved address left unattached for that long is returned to Google's pool and its charges stop
B: Delete the stopped VMs that once used the addresses, because a static address is released when its last VM is deleted
C: Run `gcloud compute addresses list`, keep those with status RESERVED, and release the unneeded ones with `addresses delete`
D: Run `gcloud compute instances list` and remove the external IP access config from each VM to release the reserved addresses
K: C
G: ## Static external IP addresses are project resources
A **static external IP address** is a resource of your project that stays reserved until you release it, whether or not a VM uses it. An address that is reserved but not attached is shown with status **RESERVED**; an attached one is **IN_USE**. Google Cloud bills for reserved addresses that are not in use, so they are worth cleaning up. Do not confuse them with **ephemeral** addresses, which are released automatically when the resource is deleted.
## Commands
- `gcloud compute addresses list --filter="status=RESERVED"`: unused addresses (add `--global` for global ones).
- `gcloud compute addresses delete NAME --region=REGION`: release a regional address; first make sure nothing, such as an allowlist at a partner, still depends on it.
W: List and delete reserved addresses: filtering for status RESERVED finds the static addresses that are not attached to anything, and `gcloud compute addresses delete` releases each reservation so its charge stops.
X: A=Wait 30 days: nothing expires a reservation; a reserved static address remains in the project, and keeps being billed, until someone releases it.
B=Delete the old VMs: deleting a VM releases only an ephemeral address. A static address stays reserved after the resource that used it is deleted, so the addresses in question are already detached and stay billed.
D=Remove access configs from VMs: the addresses in question are not attached to any VM, and removing an external IP from a VM only unassigns it; a static address stays reserved in the project after it is unassigned.
T: Reserved but unused static IPs show status RESERVED; list them and delete the ones not needed, since neither time nor VM deletion releases them.
V: VPC, Compute Engine

@ GCP-ACE D2 T2.3 advanced comparison
S: The security team must block inbound RDP (TCP 3389) from the internet to every VM in all projects under the Production folder. Project owners must not be able to override the block with their own firewall rules, but they should still decide all other traffic. What should the security team create?
A: A hierarchical firewall policy with a deny rule for tcp:3389 from 0.0.0.0/0, associated with the Production folder, leaving other traffic to lower levels
B: A global network firewall policy with a deny rule for tcp:3389 from 0.0.0.0/0, associated directly with the Production folder for its projects
C: A VPC firewall rule with priority 0 that denies tcp:3389 from 0.0.0.0/0 in each VPC network, created and kept in place by a scheduled script
D: A regional network firewall policy in each region with a deny rule for tcp:3389, associated with each project in the folder through its project ID
K: A
G: ## Where each firewall construct lives
- **Hierarchical firewall policies** are created and associated at the **organization or a folder**, never at a project. Every VPC network below inherits the rules.
- **Global and regional network firewall policies** are created in a project and associated with VPC networks in that same project.
- **VPC firewall rules** belong to one VPC network.
## Evaluation order
Rules from the organization's policy are evaluated first, then those of folders, and only then network-level rules. A hierarchical rule can `allow`, `deny`, or `goto_next`, which hands the decision to the next level. Lower-level rules **cannot override** a higher-level allow or deny, so a folder-level deny is final. Traffic that matches no hierarchical rule falls through to lower levels, where project teams keep control.
W: Hierarchical policy on the folder: it applies to each VM in each project under Production, a deny rule there cannot be overridden by project rules, and other traffic falls through to the projects' own policies and VPC firewall rules.
X: B=Global network policy on a folder: global network firewall policies attach to VPC networks in their own project; they cannot be associated with a folder.
C=Priority 0 VPC rule in each network: project owners can delete or change rules in their own networks, so a script only restores the block after a gap; it is not enforced from above.
D=Regional network policies per project: regional policies attach to a region of a VPC network in their own project, not to a project ID, and project teams with Security Admin could change them.
T: Folder-wide rules that projects cannot override belong in a hierarchical firewall policy (allow, deny or goto_next) on the organization or folder.

@ GCP-ACE D1 T1.1 advanced tradeoff
S: To reduce clutter, an administrator plans to disable APIs that look unused in an old project: Cloud Storage, Cloud Run and Kubernetes Engine. Before doing so, she checks what disabling each API does to existing resources. Which TWO statements are correct? (Select TWO)
A: Disabling the Kubernetes Engine API suspends running clusters, and suspended clusters are deleted after 30 days unless the API is re-enabled
B: Disabling the Cloud Run API keeps existing Cloud Run services serving traffic and just blocks new deployments and revisions until it is re-enabled
C: Disabling the Cloud Storage API deletes the project's buckets after a 7-day grace period, so the data must be exported beforehand
D: Disabling an API immediately cancels the pending fees and billable usage of that service, so it is a safe way to stop its costs at once
E: Disabling the Cloud Storage API leaves the stored objects in place, so storage charges continue until the data itself is deleted
K: A,E
G: ## Disabling an API is not a cleanup
You can disable an API for a project at any time with the console or `gcloud services disable SERVICE`. What happens to existing resources depends on the service:
- **Cloud Storage and BigQuery**: data is **not deleted**, and storage keeps being billed. To stop charges, delete the data before disabling the API.
- **Cloud Run**: disabling the API **deletes** the associated Cloud Run resources.
- **Kubernetes Engine**: running clusters become **suspended**; after **30 days** suspended clusters are deleted. Re-enabling the API reactivates them, which can take up to 24 hours.
Pending fees and billable use already incurred are still charged.
## Best practice
Take an inventory of the resources that belong to a service before disabling its API (for example with Cloud Asset Inventory), and delete or migrate them deliberately.
W: A=GKE clusters suspended then deleted: running clusters are suspended when the Kubernetes Engine API is disabled and are deleted after 30 days if it stays disabled.
E=Storage data stays and is billed: disabling the Cloud Storage API does not touch the objects, so storage costs continue until the data is deleted.
X: B=Cloud Run keeps serving: the docs warn that disabling the Cloud Run API deletes its resources, so the services do not keep running.
C=Buckets deleted after 7 days: there is no automatic bucket deletion; the data stays and keeps generating storage charges.
D=Cancels pending fees: pending fees and billable usage already incurred are still charged after an API is disabled.
T: Disabling an API can keep data (and its bill), delete resources (Cloud Run) or suspend them (GKE); inventory first.
V: Service Usage, Cloud Storage, Cloud Run, Google Kubernetes Engine

@ GCP-ACE D1 T1.1 applied use-case
S: A company has just signed up for Cloud Identity, and its Google Cloud organization resource was created automatically. The new Organization Administrator notices that every employee can still create projects in the organization. Only the platform-team group should be able to create projects. What should the administrator do?
A: Delete the Billing Account Creator grant from the domain, because creating a project in an organization requires the billing account creation permission
B: Remove the domain-wide Project Creator grant on the organization and grant Project Creator on the organization to the platform-team group
C: Remove the Owner role from each user on the existing projects, because project owners are the users who are allowed to create new projects
D: Grant the platform-team group the Organization Administrator role, because that role is what lets a group create new projects in the organization
K: B
G: ## Default grants on a new organization
When an organization resource is created, its initial allow policy grants two roles to the **entire domain** at the organization level:
- Project Creator (`roles/resourcemanager.projectCreator`)
- Billing Account Creator (`roles/billing.creator`)
This keeps existing users working without disruption when the organization appears. Nothing else is created.
## Taking control
Once the Organization Administrator is ready to lock things down, they remove these organization-level grants and grant narrower access instead, for example Project Creator only to a platform group, or roles on specific folders. Because allow policies are inherited, a grant to the whole domain at the organization lets everyone create projects anywhere below it.
## Example
`gcloud organizations remove-iam-policy-binding 1234 --member="domain:example.com" --role="roles/resourcemanager.projectCreator"`, then `gcloud organizations add-iam-policy-binding 1234 --member="group:platform-team@example.com" --role="roles/resourcemanager.projectCreator"`.
W: Replace the domain grant: the ability to create projects comes from the default Project Creator binding for the whole domain, so removing it and granting the role to the group limits project creation to the platform team.
X: A=Remove Billing Account Creator: creating billing accounts and creating projects are separate permissions, so the domain would still hold Project Creator and employees could keep creating projects.
C=Remove project Owner roles: owning an existing project does not let a user create new projects; that permission comes from Project Creator on the organization.
D=Organization Administrator for the group: this role manages IAM on the organization and does not include project creation, and it would give the group far more control than needed while the domain-wide grant stays in place.
T: A new organization grants Project Creator and Billing Account Creator to the whole domain; remove those grants and give narrower ones when you take control.

@ GCP-ACE D2 T2.2 applied use-case
S: A research lab trains large machine learning models on hundreds of GPU VMs and GKE nodes. Training needs a shared POSIX file system that delivers very high aggregate throughput and IOPS to all nodes at once, and data sets are staged from Cloud Storage. Which storage service is designed for this?
A: Google Cloud Managed Lustre, a fully managed parallel file system for AI and HPC with transfers to and from Cloud Storage
B: Cloud Storage with the Nearline storage class, a bucket that each GPU node reads through the JSON API during training
C: Filestore with the basic tier, a legacy managed NFS share for basic file sharing that the GPU nodes mount at once
D: Memorystore for Redis with five replicas, an in-memory store whose keys hold the training files for the GPU nodes
K: A
G: ## Why HPC and AI need parallel file systems
Large training and simulation jobs run on many nodes that read the same data at the same time. A single file server becomes the bottleneck; a **parallel file system** spreads files across many storage servers so throughput grows with the system.
## Managed Lustre
Google Cloud Managed Lustre is a fully managed **parallel file system optimized for AI and HPC**, built with DDN:
- multi-petabyte capacity and very high throughput, IOPS and low latency
- **POSIX compliance**, so existing tools and code work
- integration with Compute Engine and GKE
- high-speed managed transfers into and out of **Cloud Storage**
W: Managed Lustre: it is the managed parallel file system aimed at exactly this case, giving many GPU nodes a shared POSIX namespace with very high throughput and moving data sets in from Cloud Storage.
X: B=Nearline bucket: Nearline is meant for data read about once a month and adds retrieval fees; it is object storage through an API, not a shared POSIX file system.
C=Filestore basic tier: the docs place the legacy basic tiers at basic file sharing and software development; they are not built for hundreds of GPU nodes demanding parallel throughput.
D=Memorystore with replicas: an in-memory cache is not a file system for training data sets, and the nodes cannot mount it as one.
T: AI or HPC jobs that need a shared, very high-throughput POSIX file system point to Managed Lustre.
V: Google Cloud Managed Lustre

@ GCP-ACE D2 T2.4 applied use-case
S: Three Cloud Storage buckets and a Pub/Sub topic were created by hand in the console last year. The team now manages new resources with Terraform and wants Terraform to manage these existing resources as well, without deleting and recreating them or losing data. What should the engineer do?
A: List the resource names in a `terraform.tfvars` file so that Terraform records them as existing resources in its state
B: Copy the data elsewhere, delete the resources, let Terraform recreate them from new resource blocks, then copy the data back
C: Write matching resource blocks and import each existing resource into the Terraform state, for example with `terraform import`
D: Write resource blocks with matching names and run `terraform apply`, which adopts existing resources of the same name
K: C
G: ## Bringing existing resources under Terraform
Terraform manages only the resources recorded in its **state**. A resource created outside Terraform is unknown to it: if the configuration describes it, `terraform apply` tries to **create** it, which fails or duplicates it.
- **Import** attaches an existing real resource to a resource block in the state. Options: `terraform import ADDRESS ID` one at a time, an `import` block in the configuration (Terraform 1.5 or later) for bulk imports, or a Google Cloud bulk export that generates configuration.
- After importing, run `terraform plan` to see differences between the configuration and the real resource, then adjust the configuration until the plan shows no unwanted changes.
W: Import into state: it links the existing buckets and topic to the resource blocks without recreating them, so data and settings stay, and later changes go through Terraform.
X: A=tfvars file: variable files only provide input values to the configuration; they do not add anything to the state.
B=Delete and recreate: it is exactly what the team wants to avoid; it needs risky data copying and causes downtime, while importing needs neither.
D=Apply alone: Terraform has no state entry for the resources, so it plans to create them; matching names are not enough to adopt them.
T: Existing resources enter Terraform management through import (command or import block), followed by plan to check for drift.
V: Terraform, Cloud Storage, Pub/Sub

@ GCP-ACE D4 T4.2 applied use-case
S: A GKE workload in namespace billing using Kubernetes ServiceAccount billing-ksa calls an API that does not support federated identities, so it must act as the IAM service account billing-sa@fin-prod.iam.gserviceaccount.com. Which two steps link the identities? (Select TWO)
A: Create a key for billing-sa and store it as a Kubernetes Secret in namespace billing, then mount it into the Pods that use billing-ksa
B: Grant roles/iam.workloadIdentityUser on billing-sa to the member serviceAccount:fin-prod.svc.id.goog[billing/billing-ksa]
C: Add the nodeSelector iam.gke.io/gcp-service-account: billing-sa to the Pod spec, so that GKE schedules the Pods onto nodes running as billing-sa
D: Grant roles/iam.serviceAccountUser on billing-sa to the member principal://iam.googleapis.com/projects/PROJECT_NUMBER/locations/global/workloadIdentityPools/fin-prod.svc.id.goog/subject/ns/billing/sa/billing-ksa
E: Add the annotation iam.gke.io/gcp-service-account to billing-ksa, with the full email address of billing-sa as its value
K: B,E
G: ## Linking a Kubernetes ServiceAccount to an IAM service account
Some APIs have limitations with the federated tokens that Workload Identity Federation for GKE issues. For those, GKE can exchange the federated token for an access token of an **IAM service account**. Two pieces are required:
1. **IAM allow policy on the service account**: grant Workload Identity User (`roles/iam.workloadIdentityUser`) to the Kubernetes identity:
`gcloud iam service-accounts add-iam-policy-binding billing-sa@fin-prod.iam.gserviceaccount.com --role roles/iam.workloadIdentityUser --member "serviceAccount:fin-prod.svc.id.goog[billing/billing-ksa]"`
2. **Annotation on the Kubernetes ServiceAccount**, so GKE knows which account to impersonate:
`kubectl annotate serviceaccount billing-ksa --namespace billing iam.gke.io/gcp-service-account=billing-sa@fin-prod.iam.gserviceaccount.com`
The docs state both the binding and the annotation are required. Then grant billing-sa the roles it needs for the API.
## Not a node setting
The only nodeSelector involved is `iam.gke.io/gke-metadata-server-enabled: "true"` in Standard clusters, which places Pods on node pools with the GKE metadata server; it never names an IAM account.
W: B=Workload Identity User binding: this role on billing-sa lets the Kubernetes identity get tokens for it; the member uses the PROJECT_ID.svc.id.goog[NAMESPACE/KSA] format.
E=Annotation on the KSA: the iam.gke.io/gcp-service-account annotation, set to the service account's email, tells GKE which IAM service account Pods using billing-ksa should impersonate.
X: A=Key in a Secret: storing keys in the cluster is the insecure practice that Workload Identity Federation for GKE exists to remove.
C=nodeSelector with the account: nodes do not run as per-Pod IAM accounts; the identity comes from the KSA annotation and the IAM binding.
D=Service Account User: actAs is for attaching an account to resources, not for getting tokens, so the Kubernetes identity still could not impersonate billing-sa.
T: Link the identities with Workload Identity User on the IAM service account for serviceAccount:PROJECT_ID.svc.id.goog[NS/KSA], plus the iam.gke.io/gcp-service-account annotation on the KSA.
V: GKE, IAM
