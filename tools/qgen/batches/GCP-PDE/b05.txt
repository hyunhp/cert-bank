@ GCP-PDE D3 T3.1 applied tradeoff
S: A genomics lab keeps raw sequencer output in a Cloud Storage bucket. Researchers reopen runs unpredictably, sometimes after months, so the team wants Autoclass to manage storage classes. Enabling it on the bucket fails, because the bucket already has lifecycle rules that move objects to Nearline after 30 days and to Coldline after 90 days, plus a rule that deletes objects after 5 years. What should the data engineer do?
A: Keep both configurations by raising the bucket's default storage class to Coldline, so Autoclass can start from a colder class
B: Move the age-based rules to a second bucket and copy every object there, so Autoclass bucket receives only new uploads
C: Remove the storage-class transition rules, keep the delete rule, and then enable Autoclass on the bucket
D: Disable object versioning on the bucket first, because versioning is what blocks Autoclass from accepting lifecycle rules
K: C
G: ## Two ways to change storage class automatically
Cloud Storage can move objects between Standard, Nearline, Coldline and Archive in two ways.
- **Object Lifecycle Management** applies rules you write, usually on object age. It suits access patterns you can predict.
- **Autoclass** watches actual access: an object that is read returns to Standard, and an object that is not read for 30 days moves to Nearline. The terminal class is Nearline by default and can be Archive.
## How they interact
A bucket cannot have Autoclass enabled together with a lifecycle rule that uses the `SetStorageClass` action or the `matchesStorageClass` condition; the request fails. Rules that only delete objects, for example by age, are allowed, so retention can stay in place.
## Applying it here
Reopening runs "unpredictably" is exactly the case Autoclass targets, because an age-based schedule would leave a hot run in Coldline. The blocking items are the two transition rules only.
W: Remove transitions, keep delete, enable Autoclass: the transition rules use `SetStorageClass`, which conflicts with Autoclass, while the 5-year delete rule is still allowed, so retention is preserved and storage-class management moves to access-based logic.
X: A=Raise default class to Coldline: a bucket default class does not remove the conflicting lifecycle rules, so enabling Autoclass would still be rejected, and Coldline as a starting point would add retrieval fees for hot data.
B=Second bucket with copies: this moves data needlessly and splits the lab's data across two buckets; the conflict is solved by removing two rules, not by duplicating objects.
D=Disable versioning: versioning is not what blocks Autoclass; the documented restriction is on `SetStorageClass` rules and `matchesStorageClass` conditions, so this changes nothing.
T: Autoclass and lifecycle `SetStorageClass` rules cannot coexist on a bucket; delete-only lifecycle rules can.

@ GCP-PDE D3 T3.1 applied comparison
S: A media-analytics team stores clickstream exports in a Cloud Storage bucket where some days of data are queried again and again and other days are never touched. The team enables Autoclass on the bucket. Which TWO statements describe how Autoclass will manage these objects? (Select TWO)
A: An object that is read is moved back to Standard storage, even if it had already reached a colder class
B: Objects not accessed for 30 days move to Nearline, which is the default terminal class unless Archive is chosen
C: Every read of an object in a colder class adds a retrieval fee to the bill, as it does with manual Coldline
D: Objects move to colder classes at fixed ages that the owner must list in a lifecycle configuration on the bucket
E: Objects stay in the class chosen at upload, and Autoclass only reports which objects could be moved
K: A,B
G: ## What Autoclass does
Autoclass is a bucket-level setting that manages the storage class of each object from its own access history, so the owner does not have to forecast access.
- An object whose data is accessed transitions to **Standard**.
- An object not accessed for **30 days** transitions to **Nearline**. Nearline is the default terminal class: objects stay there until they are accessed.
- If the terminal class is set to **Archive**, unused objects keep moving to Coldline and then Archive.
## Cost behaviour
Retrieval fees and early deletion fees are not charged on Autoclass buckets (apart from the enablement charge), but a management fee applies. It is the opposite of a manual cold class, where retrieval and minimum-duration charges punish a wrong guess.
W: A=Access returns objects to Standard: a read promotes the object, so a day of clickstream data that suddenly becomes hot is served from Standard without any action by the team.
B=30 days to Nearline, terminal class: Autoclass demotes untouched objects after 30 days and by default stops at Nearline, unless Archive is configured as the terminal class.
X: C=Retrieval fee per read: Autoclass buckets do not charge retrieval fees; that charge applies to manually assigned Nearline, Coldline and Archive objects.
D=Owner lists ages in lifecycle: moving objects by fixed age is Object Lifecycle Management; Autoclass decides from access, and its transition rules cannot coexist with `SetStorageClass` rules.
E=Report only: Autoclass actually changes the class of objects; it is not a recommendation tool.
T: Autoclass promotes read objects to Standard, demotes untouched ones after 30 days, and removes retrieval and early-deletion fees.

@ GCP-PDE D3 T3.1 applied use-case
S: A bank must keep payment-audit exports for 7 years. The files are read by dashboards daily during the first 30 days, are opened a few times in the following year for investigations, and after that are almost never read. Access depends only on object age, and the auditors want the transition dates to be exactly predictable. Which storage design fits best?
A: Enable Autoclass with Standard as the starting class and rely on object reads to decide when each file should move
B: Store every export in Archive storage from the first day, because the data must be kept for such a long period
C: Upload to Coldline storage and add a rule that deletes each object after exactly 7 years from its creation
D: Upload to Standard, add age-based rules to Nearline after 30 days and Archive after 365 days, and delete at 7 years
K: D
G: ## Predictable pattern: use lifecycle rules
When the access pattern follows object age, **Object Lifecycle Management** is the more exact tool. Each rule has a condition (such as `age`) and an action (`SetStorageClass` or `Delete`), and Cloud Storage evaluates it for every object.
## Match the class to the access
- Standard has no minimum storage duration or retrieval fee, so it suits daily reads.
- Nearline (30-day minimum) suits data read about once a month or less.
- Coldline has a 90-day minimum and Archive a 365-day minimum; both charge retrieval fees.
Putting hot data in a cold class from day one wastes money on retrieval fees; leaving cold data in Standard wastes money on storage.
## Here
Standard for the first month, Nearline for investigations, Archive for the long tail, and deletion at the end of retention gives the dates the auditors want.
W: Age-based lifecycle tiering: it keeps the daily-read month in Standard, places occasional investigation reads in Nearline, parks the long tail in Archive and deletes at 7 years, all on predictable dates.
X: A=Autoclass: transitions follow reads, not a calendar, so the auditors' requirement for exactly predictable dates is not met, and the pattern is already known by age so the extra management fee buys nothing.
B=Archive from day one: the dashboards read the files daily for 30 days, so retrieval fees would apply on every read, and Archive is intended for data accessed rarely, not daily.
C=Coldline plus delete: the first-month daily reads would incur retrieval fees in a cold class, and the data would never reach the cheaper long-tail class during the remaining years.
T: When access depends on age, lifecycle rules give exact, predictable class transitions; Autoclass is for unpredictable access.

@ GCP-PDE D3 T3.1 applied definition
S: A retail data team exports a weekly snapshot of its product catalog to Cloud Storage. Each snapshot is read about once in the first quarter for reconciliation, then deleted by a lifecycle rule 200 days after creation. The team wants the lowest at-rest cost without paying for time it will not use. Which storage class is the best fit?
A: Archive, because it has the lowest at-rest storage rate of the four standard classes and the data is rarely read
B: Coldline, because its 90-day minimum storage duration is shorter than the 200 days the data is kept
C: Nearline, because the snapshots are read a few times and the class has no retrieval fees
D: Standard, because data that is deleted by a lifecycle rule never qualifies for a colder class
K: B
G: ## Minimum storage duration
Each colder class has a **minimum storage duration**: Nearline 30 days, Coldline 90 days, Archive 365 days. If an object is deleted or moved before that period, you pay as if it had stayed the full period (an early deletion charge).
## How to choose
1. Estimate how long the object lives.
2. Estimate how often it is read.
3. Pick the coldest class whose minimum duration is no longer than the object lifetime and whose retrieval fee is acceptable for the read frequency.
Objects kept 200 days and read about once fit Coldline: the lifetime exceeds 90 days, and a single read costs little.
W: Coldline: objects live 200 days, which is beyond its 90-day minimum, so no early deletion charge applies, and a single read in the quarter suits a class intended for data accessed at most about once a quarter.
X: A=Archive: its 365-day minimum duration is longer than the 200-day lifetime, so deletion at 200 days would be billed as if the data had stayed for 365 days, wiping out the saving.
C=Nearline: it does suit monthly access, but the claim that it has no retrieval fees is wrong; Nearline charges retrieval fees too, and it costs more to store than Coldline for data read this rarely.
D=Standard: lifecycle deletion does not stop an object from being in a colder class; the minimum duration only matters if the object is removed before it ends.
T: Choose a storage class whose minimum duration fits the object's lifetime, otherwise early-deletion charges cancel the saving.

@ GCP-PDE D3 T3.1 applied tradeoff
S: A telecom's BigQuery dataset holds several hundred terabytes of highly repetitive call-detail records. The records compress very well. The dataset uses the default storage billing, the storage bill is the largest line item, and the team wants to lower it with no change to queries, tools or data layout. What should the data engineer do?
A: Compare the logical and physical bytes of the tables, then switch the dataset to the physical storage billing model if it is cheaper
B: Export all tables to Cloud Storage as Parquet files and delete the BigQuery tables, so only the compressed files are billed
C: Set the physical storage billing model on each table, because the model can only be chosen per table and not per dataset
D: Rewrite every table into a new compressed format, because BigQuery stores data uncompressed by default and bills accordingly
K: A
G: ## Two storage billing models
BigQuery always stores data in a compressed, columnar physical format. What differs is how the bytes are **metered**.
- **Logical billing** (default): you are billed on the uncompressed size of the data.
- **Physical billing**: you are billed on the compressed size on disk.
The model is set per **dataset**, changing it only changes metering, and it does not alter performance or require data migration. A changed dataset cannot be switched again for 14 days.
## What to check first
With highly compressible data, physical bytes are much smaller than logical bytes, which favours physical billing. But under physical billing, time travel and fail-safe bytes are charged separately at active rates, whereas logical billing includes them in its rate. Compare using the `INFORMATION_SCHEMA.TABLE_STORAGE` views, which show logical, physical and time travel bytes and support a rough forecast.
W: Compare then switch the dataset billing model: highly compressible data has far fewer physical than logical bytes, and the change affects only metering, so queries, tools and layout stay untouched.
X: B=Export to Parquet: this removes data from BigQuery storage and its query features and adds an export and external-table project; it is not a change that leaves queries and tools untouched.
C=Per-table setting: the storage billing model is configured at the dataset level, so a per-table choice does not exist.
D=Rewrite to a new format: BigQuery already stores data in its own compressed physical format; the billing choice is a metering setting, not a stored-format change.
T: Compressible data may be cheaper under physical storage billing; decide per dataset using the TABLE_STORAGE logical and physical byte counts.

@ GCP-PDE D3 T3.1 applied troubleshooting
S: A dataset on physical storage billing holds staging tables that are fully rewritten every night. The storage bill is much higher than the size of the live tables suggests, and INFORMATION_SCHEMA.TABLE_STORAGE shows large time travel byte counts. The team does not need to restore staging data older than two days. What should the data engineer do?
A: Set the fail-safe period of the dataset to zero, because fail-safe bytes are the part that can be shortened
B: Set the time travel window on the dataset to the 2-day minimum, which reduces the time travel bytes that are billed
C: Switch the dataset back to logical billing, which makes time travel bytes free of charge for every dataset
D: Disable time travel on the dataset, which removes the retained bytes of every rewritten table at once
K: B
G: ## Time travel and fail-safe cost
BigQuery keeps changed or deleted data for recovery: the **time travel** window (seven days by default, configurable from 2 to 7 days at dataset or project level), followed by a fixed fail-safe period.
- Under **logical** billing these bytes are included in the base rate, so shortening the window does not save money.
- Under **physical** billing they are charged separately at active storage rates, so a shorter window directly reduces the bill.
- The fail-safe window cannot be modified.
## Why nightly rewrites hurt
Fully rewriting a table moves the old version into time travel, so tables rewritten daily keep roughly a week of old copies. A short window limits that.
W: Shorten time travel to 2 days: the dataset is on physical billing, where time travel bytes are billed separately, and two days is the minimum the platform allows and covers the stated recovery need.
X: A=Fail-safe to zero: the fail-safe window cannot be modified, so this setting does not exist.
C=Back to logical billing: logical billing includes time travel in its base rate rather than making it free, and the data's compressibility may make logical billing more expensive overall.
D=Disable time travel: the window cannot be set below two days, so time travel cannot be turned off.
T: On physical billing, shorten the dataset time travel window (minimum 2 days) to cut costs for heavily rewritten tables; the fail-safe window is fixed.

@ GCP-PDE D3 T3.1 applied use-case
S: A clickstream table in BigQuery is partitioned by day on its ingestion time. Compliance allows analysts to see only the most recent 90 days of raw events. The table must stay in place with its schema, and other datasets must not be affected. Which configuration keeps storage from growing without limit?
A: Set a default table expiration of 90 days on the dataset so older rows are removed from the table
B: Set a partition expiration of 90 days on the table so each partition is deleted when it is that old
C: Schedule a weekly query that selects the latest 90 days and overwrites the table with the result
D: Set a table expiration of 90 days on the table, so that only the oldest partitions are removed first
K: B
G: ## Partition expiration versus table expiration
- **Table expiration** deletes the whole table (all data and the table itself) at a given time.
- A dataset **default table expiration** is applied to every new table created in the dataset. A dataset can also carry a separate default partition expiration, but it too reaches only tables created later.
- **Partition expiration** is set on one partitioned table: BigQuery deletes each partition once the partition time is older than the setting, calculated independently for each partition. The table itself stays, even if it becomes empty.
## Choosing
A rolling retention window on a single partitioned table calls for partition expiration. Dataset-wide defaults would affect every table created later in that dataset, so they are the wrong scope when other tables must not be touched.
W: Partition expiration of 90 days: each daily partition is removed when it ages beyond 90 days, the table and schema remain, and nothing else in the dataset is changed.
X: A=Dataset default table expiration: this applies to all newly created tables in the dataset, so it would affect tables the team did not mean to limit, and it does not target one existing table.
C=Weekly overwrite query: it works but rewrites the data on a schedule, scans data and creates time travel bytes, when a built-in setting does the same declaratively.
D=Table expiration: that deletes the entire table including its schema when it expires; it does not remove old partitions one by one.
T: Use partition expiration for a rolling retention window on one partitioned table; table expiration drops the whole table.

@ GCP-PDE D3 T3.1 advanced use-case
S: An IoT platform stores billions of per-second sensor readings in BigQuery. Engineers need the detail for the last 60 days, while the business needs only hourly averages and maxima for the following five years. The storage cost of raw rows is growing quickly. What approach keeps long-term metrics while limiting cost?
A: Keep all raw rows indefinitely and use clustering on the sensor identifier to reduce the stored bytes
B: Build a scheduled aggregation into an hourly summary table, then expire the raw partitions after 60 days
C: Move all raw rows to a Coldline bucket after 60 days and delete the BigQuery table afterwards
D: Replace the raw table with monthly snapshots that are created on a schedule and kept for five years
K: B
G: ## Aggregate long-term data
Row-level data is often useful for a short time, while the business keeps asking for the same metrics for years. The recommended pattern is to compute the metrics with aggregation queries, store them in a summary table, and use table or partition expiration to remove the row-level data automatically. The metrics stay available, and storage charges shrink.
## What does not help
- Clustering sorts blocks to cut bytes scanned; it does not reduce the data stored.
- Copying to another store trades cost for convenience but does not give the business its aggregates.
- Snapshots preserve full data; they are not summaries.
W: Hourly summary plus partition expiry: the summary table keeps the five-year metrics at a tiny fraction of the size, and expiring raw partitions after 60 days removes the costly detail on schedule.
X: A=Clustering the raw table: clustering improves query pruning, but every row is still stored, so the storage cost keeps growing.
C=Coldline plus drop the table: the business loses ready aggregates, and queries over the old data would require external tables over raw files; Coldline would also add retrieval fees to every recomputation.
D=Monthly snapshots: a snapshot preserves a table's contents; it does not summarize them and holds the same raw rows the team wants to stop paying for.
T: Store aggregates for long-term metrics and let partition or table expiration delete the raw row-level data.

@ GCP-PDE D3 T3.1 applied use-case
S: A nightly pipeline rewrites a BigQuery table called ledger_daily. A defect was discovered 12 days after a faulty run changed many rows, and the team could not restore from time travel. Auditors now want an end-of-month copy of the table that can be queried 6 months later, at the lowest storage cost, without a full duplicate of the data. What should the data engineer use going forward?
A: Table snapshots created at month end, with an expiration of about 6 months
B: A full copy job each month into a new table, kept until the retention period ends
C: Raise the time travel window to 30 days so each month end can be queried from the base table
D: Export each month to Avro files in Archive storage and recreate tables only when requested
K: A
G: ## Time travel versus table snapshots
Time travel lets you query or restore a table as it was within the dataset's window of two to seven days. Anything older is gone, so a defect found after 12 days cannot be fixed with it.
**Table snapshots** preserve a table at a chosen time as a read-only table. They can have an expiration, can be queried like any table, and can be restored into a standard table. Storage is billed only for bytes that differ from the base table, so a snapshot typically costs far less than a full copy.
## Here
A snapshot at each month end, with an expiration of about 6 months, gives queryable history with minimal incremental storage.
W: Month-end table snapshots: they retain the table beyond the seven-day time travel limit, remain directly queryable, expire on their own, and charge only for data that differs from the base table.
X: B=Full copy each month: it is queryable but stores a complete duplicate every month, which is the cost the auditors wanted to avoid.
C=30-day time travel: the window is capped at 7 days, so it cannot be raised to 30.
D=Avro export to Archive: this is cheap to store but the data is not directly queryable, and rebuilding tables on demand fails the requirement to query the copy later.
T: Table snapshots keep queryable history beyond the 7-day time travel limit and bill only changed bytes.

@ GCP-PDE D3 T3.2 applied tradeoff
S: A ride-sharing company loads trip events into BigQuery from devices that sometimes upload data up to a week late. Analysts always filter by the event timestamp recorded on the device (a TIMESTAMP column named event_ts), usually over a few days. Which partitioning choice gives pruning that matches how the data is queried?
A: Partition by ingestion time at daily granularity, because it assigns each row to the partition of its load time
B: Partition by the event_ts column at daily granularity, so late rows still land in the partition of their event date
C: Leave the table unpartitioned and cluster by event_ts, because clustering gives an exact cost estimate
D: Partition by an integer range on a derived hour-of-day number, so queries can filter on event time ranges
K: B
G: ## Choosing the partition column
BigQuery offers three ways to partition: by a **time-unit column** (DATE, TIMESTAMP or DATETIME), by **ingestion time**, and by **integer range**.
- **Time-unit column partitioning** places each row in the partition of its own column value, so late data lands in the day it belongs to. Queries that filter on that column prune partitions.
- **Ingestion-time partitioning** uses load time (the `_PARTITIONTIME` pseudocolumn). A row that arrives a week late sits in the wrong partition for event-based questions.
## Rule of thumb
Partition on the column analysts filter by most. Partitioning also supports partition-level management (expiration, delete, loads into a partition) and gives a cost estimate before a query runs.
W: Partition by event_ts: late rows go to the partition for their event date, and the analysts' event-time filters prune partitions as intended.
X: A=Ingestion time: late-arriving rows are stored under their load date, so a filter on event_ts across a few days would still have to read extra partitions or miss the logic.
C=Unpartitioned plus clustering: clustering does not give an exact estimate before the query runs, so the claim is false; the cost can only be determined after the run.
D=Integer range on hour of day: this groups different days together in the same range, so date filters could not prune by day.
T: Partition by the time column that queries filter on; ingestion-time partitions suit queries about load time.

@ GCP-PDE D3 T3.2 applied use-case
S: A utility stores 20 billion meter readings in one BigQuery table. Each reading has an integer region_id between 1 and 500, and dashboards nearly always filter on a range of region_id values. No column is a date that the dashboards filter on. Which design reduces the data scanned by these queries?
A: Partition the table by time unit on the load date, so that every region is found in one particular daily partition
B: Cluster the table by a string column that holds the region name, with no partitioning at all
C: Partition by integer range on region_id, with start 1, end 501 and an interval that groups regions
D: Create one table per region and query them through a wildcard table with a name suffix filter
K: C
G: ## Integer-range partitioning
When the natural filter is a range of integer values rather than a date, a table can be partitioned by an `INTEGER` column. You provide the column, the start and end of the range, and the interval for each partition. Values outside the range go to an `__UNPARTITIONED__` partition and NULLs to `__NULL__`.
A query that filters the partitioning column to a range reads only the matching partitions, and BigQuery can estimate its cost before it runs.
## Why not the other choices
- Date partitioning only helps queries that filter on the date.
- Clustering sorts data inside blocks and helps filtering, but its savings cannot be estimated up front and it is not specific to ranges on the integer column used here.
- Sharding tables by name is an older pattern; it adds metadata and permission overhead and BigQuery recommends partitioning instead.
W: Integer-range partitioning on region_id: the dashboards' range filters map directly to partitions, so only the needed ranges are read and costs can be estimated up front.
X: A=Load-date partitions: dashboards do not filter by date, so every query would scan all daily partitions.
B=Clustering by region name: it ignores the integer column the dashboards actually filter on and gives no up-front cost estimate.
D=One table per region: sharded tables add many tables to manage and each query must reference them by name; partitioning achieves pruning inside a single table.
T: Use integer-range partitioning when the dominant filter is a range on an integer column.

@ GCP-PDE D3 T3.2 applied use-case
S: A BigQuery orders table is partitioned by order_date. Reports filter on order_date plus one or more of status and country, and sometimes on status and country alone (without a date range limit). The team wants to cluster the table by status, country and customer_id. Which statement about the clustering column order is accurate?
A: Order does not matter, because BigQuery sorts all clustered columns together and reads blocks
B: Put the columns in alphabetical order, because BigQuery uses the clustering order as a name index
C: Put the column with the fewest distinct values last, because high-cardinality columns must be listed first
D: Order by the filters the queries use, because queries gain most from the leading clustered columns
K: D
G: ## How clustering sorts data
Clustered tables sort the data in storage blocks by the values in the user-defined clustered columns, in the order listed. A query that filters or aggregates on those columns reads only the relevant blocks.
## Column order matters
The first column is the primary sort, the second sorts within it, and so on. A query that filters on the first column and then the second benefits; a query that filters only on later columns is not optimized as well. The order should therefore follow the filters used most.
## Combining with partitioning
Data is first split into partitions; clustering is then maintained within each partition. BigQuery reclusters in the background automatically.
W: Order by the filters the queries use: the leading clustered columns decide how well blocks can be skipped, so list first the columns that most queries filter on.
X: A=Order does not matter: it does, since the sort is hierarchical and a query filtering only on later columns is not optimized the same way.
B=Alphabetical order: the order is a sort priority for pruning blocks and has nothing to do with name lookup.
C=Fewest distinct values last: there is no rule that high-cardinality columns must come first; the order depends on query filters.
T: Cluster column order is sort priority; put first the columns that queries filter on most often.

@ GCP-PDE D3 T3.2 applied comparison
S: A team compares partitioning and clustering for a 40 TB BigQuery fact table queried by date and customer. They plan to partition by order date and cluster by customer_id. Which TWO statements about this combination are correct? (Select TWO)
A: A dry run on a query that prunes partitions can show a close estimate of the bytes processed before the query runs
B: BigQuery automatically maintains the clustering of new data within each partition, using background reclustering
C: Clustering guarantees that queries need fewer slots, so a smaller reservation will always be enough
D: The estimate for a clustered column filter is exact before the run, so no maximum bytes billed setting is needed
E: Clustering only works on tables that are not partitioned, so the two features cannot be used together
K: A,B
G: ## Partitioning and clustering together
- **Partitioning** divides a table into segments, for example by day. It keeps metadata that lets BigQuery estimate query cost accurately after pruning, so a dry run gives a useful estimate before the query executes. It also enables partition-level management such as expiration.
- **Clustering** sorts data within storage blocks on chosen columns. Queries filtering on those columns scan only relevant blocks, but the number of blocks is known only when the query runs, so the pre-run estimate is an upper bound.
- You can combine them: split by partition first, then cluster within each partition. Automatic reclustering in the background maintains the sort for new data, and it works within each partition.
## Caveats
Clustering does not guarantee a reduction in slots.
W: A=Dry run after pruning: partitioned tables keep sort-property metadata so BigQuery can estimate bytes after partition pruning, which supports cost checks before running.
B=Automatic reclustering: BigQuery maintains clustering in the background as data changes, and for partitioned tables it does this within each partition.
X: C=Fewer slots guaranteed: clustering can reduce bytes read but is documented as not guaranteeing a reduction in the slots needed.
D=Exact estimate for clustered filters: for clustered tables the estimate is an upper bound and the real figure is known only after execution, so cost controls remain useful.
E=Cannot be combined: combining partitioning and clustering is a documented and common design.
T: Partitioning gives pre-run estimates, clustering gives block-level pruning maintained by automatic reclustering, and the two work together.

@ GCP-PDE D3 T3.2 applied use-case
S: Analysts at a retailer keep running queries on a 15 TB partitioned BigQuery table without a date filter, and each such query scans every partition. Finance wants the platform to stop these queries from running at all, without telling analysts which columns to remember. What should the data engineer configure?
A: Set the Require partition filter option so queries must include a predicate on the partitioning column
B: Reduce the table's partition expiration to a single day, so that queries cannot reach older partitions in the table at all, and so none can scan them
C: Cluster the table by the date column, so that every query is forced to read fewer blocks
D: Enable a materialized view on the table, because it blocks queries that do not use the view
K: A
G: ## Forcing efficient queries
Partitioning saves money only when queries filter on the partitioning column. Teams often forget the filter, which produces a full scan.
The table option **Require partition filter** makes every query on the table include at least one predicate that references only the partitioning column; queries without it fail with an error instead of scanning the table. It can be set when the table is created or updated later.
## Related controls
- Partition expiration controls how long data is kept; it does not control how queries read it.
- Clustering helps skip blocks but does not stop a full scan.
- Maximum bytes billed limits the cost of a single query on on-demand pricing.
W: Require partition filter: queries that lack a predicate on the partitioning column are rejected, so no analyst can accidentally scan all partitions.
X: B=One-day partition expiration: this deletes data, harming analysis, and does not stop a query that omits a filter.

@ GCP-PDE D3 T3.2 applied use-case
S: An e-commerce company has three tables for its BigQuery warehouse: orders, order_lines and shipments. G: ## Denormalization in BigQuery
