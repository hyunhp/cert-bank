@ GCP-PDE D1 T1.3 advanced use-case
S: A media analytics company writes its batch and streaming transformations today on Dataflow. Its architects want a contractual exit path: if pricing or strategy changes, the same pipeline logic should be able to run on Apache Flink or Apache Spark clusters without a rewrite. Which design choice best supports this?
A: Write the pipelines with the Apache Beam SDK and keep business logic out of Dataflow-specific service calls
B: Build the transformations as BigQuery stored procedures and call them from scheduled queries on a fixed timetable
C: Convert the pipelines into Cloud Data Fusion visual graphs and export the graph definitions as JSON files
D: Rewrite the logic as Dataflow templates and store the template files in a Cloud Storage bucket for reuse
K: A
G: ## Portability at the pipeline layer
Portability is decided by the programming model, not by where the job runs today. Dataflow is a managed runner for pipelines written with the open source **Apache Beam** SDKs (Java, Python, Go and multi-language pipelines). Beam separates the pipeline definition from the runner that executes it, so the same code can be submitted to Dataflow, Apache Flink or Apache Spark.
## What helps and what binds you
- Keep transformation logic in Beam `DoFn`s and composite transforms, and use Beam I/O connectors where they exist.
- Service-specific glue (templates, console settings, runner options) is thin and replaceable; business logic in it is not.
- Logic written in another engine's dialect (SQL procedures, a visual tool's node types) has to be rewritten to move.
W: Apache Beam SDK: the Dataflow docs state that a Beam pipeline can later run on Apache Flink or Apache Spark without rewriting pipeline code, so the exit path is built into the programming model.
X: B=BigQuery stored procedures: they run only inside BigQuery and are written in its SQL dialect, so moving to Flink or Spark would be a rewrite.
C=Data Fusion graphs: a graph is a design for Data Fusion's own execution model; exporting it as JSON does not make it a Beam pipeline that other runners accept.
D=Dataflow templates: templates package a Beam pipeline for repeatable launch on Dataflow; they are a deployment convenience on one service and not a portability mechanism by themselves.
T: Write once in Apache Beam and Dataflow becomes a replaceable runner rather than a dependency.

@ GCP-PDE D1 T1.3 applied use-case
S: A retailer's clickstream data sits in Amazon S3 buckets in an AWS region. Its contract requires that the raw files must not leave that region. Analysts already work in BigQuery and want to join the clickstream with BigQuery sales tables using SQL, without a recurring copy job. What should the data engineer design?
A: Create BigLake tables over the S3 data using BigQuery Omni, and join them with BigQuery tables
B: Schedule a nightly Storage Transfer Service job that copies the S3 objects into a Cloud Storage bucket
C: Ship the S3 data to a Transfer Appliance and load the files into a partitioned BigQuery table
D: Use Datastream to replicate the S3 objects as change events into a BigQuery dataset each hour
K: A
G: ## Querying data where it lives
Sometimes the constraint is that data cannot be copied: residency contracts, egress cost or sheer volume. **BigQuery Omni** runs BigQuery compute in AWS or Azure regions, and **BigLake tables** over Amazon S3 or Azure Blob Storage let BigQuery query that data in place through a connection. BigQuery Omni joins can then combine BigLake tables from several clouds with BigQuery tables in one `SELECT`, so nothing needs to be copied first.
## Why copy-based designs fail the requirement
Transfer tools (Storage Transfer Service, Transfer Appliance) move the bytes out of the region by definition. Datastream captures database changes, not object-store files.
W: BigLake tables with BigQuery Omni: the data stays in S3 in the AWS region, queries run next to it, and Omni joins let analysts combine it with BigQuery tables without a copy job.
X: B=Storage Transfer Service copy: it would move the objects into Cloud Storage and break the rule that raw files stay in the AWS region.
C=Transfer Appliance: it is an offline shipping device for bulk uploads into Cloud Storage, so it also relocates the data and is not a recurring or in-place approach.
D=Datastream: it replicates changes from databases and a few SaaS sources; it does not read objects from S3 buckets.
T: When data may not move, bring BigQuery to it with BigLake tables and BigQuery Omni.

@ GCP-PDE D1 T1.3 applied comparison
S: A data science group runs Apache Spark on its own clusters, while the BI team uses BigQuery. Both want to read and update the same sales tables stored in buckets the company owns, keeping one copy of the data and the open Iceberg format. Which BigQuery capability fits?
A: Apache Iceberg managed tables, with data in your buckets and Iceberg metadata open engines can read
B: Native BigQuery storage tables, which Spark reads through a nightly export into Parquet files
C: External tables over CSV files, which BigQuery reads while Spark keeps its own working copy
D: Materialized views over native tables, which Spark queries through the BigQuery console
K: A
G: ## Open table formats and one copy of data
An open table format such as Apache Iceberg defines tables (schema, snapshots, metadata) on top of files in object storage so that several engines can share them. **Apache Iceberg managed tables** in BigQuery give the managed BigQuery experience (GoogleSQL DML, streaming writes through the Storage Write API, schema evolution, automatic storage optimisation) while the data stays in buckets you own and Iceberg V2 snapshots are exported and refreshed on each mutation, so Spark and other third-party engines can query a single copy.
## Trade-off
The alternative designs create copies (exports, working sets) that drift out of date and must be reconciled.
W: Iceberg managed tables: data lives in your buckets in an open format, BigQuery keeps full DML support, and refreshed Iceberg snapshots let Spark read the same single copy.
X: B=Native storage plus nightly export: this keeps two copies and Spark sees data that is up to a day old, with no path for Spark to update the table.
C=CSV external tables: a second working copy for Spark is exactly what the team wants to avoid, and CSV has no table metadata or DML support.
D=Materialized views: they are a BigQuery query-acceleration object over native tables and are not an open-format sharing mechanism for Spark.
T: Iceberg managed tables give BigQuery behaviour on one open-format copy that other engines can read.

@ GCP-PDE D1 T1.3 applied definition
S: A company keeps Parquet files in Cloud Storage and exposes them to analysts through BigLake tables instead of plain external tables. Which TWO benefits does this design provide? (Select TWO)
A: Analysts are granted access to the table only, because a connection's service account reads the files on their behalf
B: Row-level and column-level security can be enforced on the table without granting access to the bucket
C: Parquet files are rewritten automatically into BigQuery native storage the first time they are queried
D: Queries read the bucket files with each analyst's own Cloud Storage permissions, so bucket roles stay the control point
E: Streaming inserts into the table are supported, so Pub/Sub messages can be written to the files directly
K: A,B
G: ## BigLake tables and access delegation
BigLake tables query structured data in Cloud Storage (and Amazon S3 or Azure Blob Storage via BigQuery Omni) with **access delegation**. A connection resource has a service account that reads the files; users receive permission on the BigLake table only. Because users never touch the underlying objects, BigQuery can apply fine-grained security (row-level, column-level and, for Cloud Storage, dynamic data masking) at table level. The data stays in the lake in its open format.
## Governance impact
The lake owner controls one service account's access to the bucket and the data owner controls who sees which rows and columns, instead of managing per-user bucket permissions.
W: A=Access delegation: a connection service account retrieves the data, so only the table needs to be shared and the bucket remains private.
B=Fine-grained security: with access delegated, BigQuery can enforce row-level and column-level security on the table, which plain external tables cannot guarantee.
X: C=Automatic conversion: BigLake tables read the files where they are; they do not copy them into BigQuery native storage.
D=Analyst bucket permissions: that is how plain external tables behave; BigLake deliberately decouples table access from bucket access.
E=Streaming inserts: BigLake tables over files are read-oriented lake tables, and Pub/Sub messages are not written to them directly.
T: BigLake tables delegate file access to a connection service account, which makes table-level row and column security possible on lake data.

@ GCP-PDE D1 T1.3 advanced tradeoff
S: A bank is designing a new analytics platform and wants to limit lock-in without giving up managed services. Which TWO design decisions best support portability of its data and processing? (Select TWO)
A: Store curated datasets in open file formats such as Parquet or Avro in Cloud Storage with schemas documented
B: Implement transformations with the Apache Beam SDK so the pipeline code is not tied to one runner
C: Place every dataset only in the warehouse's proprietary native storage and expose it through its SQL dialect alone
D: Encode business rules inside the configuration screens of a single orchestration product rather than in code
E: Use cloud-specific serialisation formats for messages so that consumers must use the same client libraries
K: A,B
G: ## Portability through open interfaces
Lock-in comes from proprietary formats and proprietary programming models. Two choices keep the exit cost low without giving up managed services:
- **Open data formats** (Avro, Parquet, ORC, Iceberg) can be read by BigQuery, Spark, Trino and other engines, so data can be moved or shared without conversion.
- **Open programming models** such as Apache Beam keep logic independent from the runner that executes it.
## Reading the distractors
Anything that hides logic or data inside one product's configuration or encoding forces a rewrite or re-export later.
W: A=Open file formats: Parquet and Avro in Cloud Storage can be consumed by many engines and carry schema information, so data stays usable if the processing platform changes.
B=Beam SDK: pipeline logic written once runs on Dataflow today and on other Beam runners later without a rewrite.
X: C=Proprietary native storage only: this is the lock-in the bank wants to avoid, because the data and queries are tied to one engine and dialect.
D=Business rules in one orchestrator's screens: rules held in a tool's configuration cannot be exported or version-controlled as code and must be recreated on exit.
E=Proprietary message encoding: forcing consumers to use matching client libraries ties every producer and consumer to one vendor's serialisation.
T: Open data formats plus open programming models are the two levers that keep data and pipelines portable.

@ GCP-PDE D1 T1.3 applied tradeoff
S: A logistics company ingests partner shipment files, cleans them, and loads curated tables into BigQuery. The cleaning rules change several times a year, and auditors sometimes ask to re-derive a table as it was a year ago. Which staging design best meets these needs?
A: Land every incoming file unchanged in a Cloud Storage raw zone, then build curated tables from it
B: Apply cleaning in the ingestion step and keep only cleaned rows so that storage use stays small
C: Load files straight into the final BigQuery tables and use table snapshots as the only record of history
D: Keep raw files on the partners' servers and re-request them whenever the rules change
K: A
G: ## Staging zones as a design pattern
A common data lake or lakehouse layout has layers: a **raw (landing) zone** that keeps source data exactly as received, a **curated/clean zone** with validated, standardised data, and serving tables for consumers. The raw zone is cheap object storage and is the system of record for reprocessing.
## Why it matters here
- When business rules change, the curated layer is rebuilt from raw without asking partners to resend anything.
- For audits, the same raw input plus versioned transformation code reproduces a historical table.
- Cleaning that discards information at ingest makes both impossible.
W: Immutable raw zone in Cloud Storage: keeping the original files lets the team re-run changed rules and reproduce an older table from the same input.
X: B=Clean at ingest and keep only cleaned rows: discarded or modified source data cannot be re-derived when rules change, and auditors cannot see the original.
C=Load directly and rely on snapshots: snapshots capture the already-loaded state and do not retain the original files, so rule changes cannot be replayed from source.
D=Re-request from partners: it depends on third parties retaining and resending files, which is neither reliable nor auditable.
T: Keep a raw, unmodified landing zone so curated data can always be rebuilt and audited.

@ GCP-PDE D1 T1.3 applied use-case
S: A ticketing company needs a dashboard that shows sales within a few seconds of each purchase. Traffic is mostly quiet but jumps by orders of magnitude when popular events go on sale. The team is small and does not want to size or patch clusters. Which architecture maps best to these requirements?
A: Publish purchase events to Pub/Sub, process them with a Dataflow streaming pipeline, and write to BigQuery
B: Write purchases to a Cloud SQL instance and refresh a spreadsheet extract at the top of each hour
C: Collect events in a Dataproc cluster sized for the peak and run a Spark batch job every few minutes
D: Save events as files in Cloud Storage and run a scheduled BigQuery load job once per day
K: A
G: ## Mapping requirements to components
Start from the quantified requirements and map each to a property of the architecture:
- **Seconds of latency** points to streaming ingestion and processing, not periodic batch.
- **Spiky, unpredictable volume** points to services that absorb bursts (Pub/Sub buffers) and autoscale workers (Dataflow).
- **Small team, no cluster management** points to serverless components.
- **Analytical dashboards** point to BigQuery as the sink.
Windowing and delivery semantics are streaming-pipeline design details covered elsewhere; here the point is that the three requirements together select this pattern.
W: Pub/Sub, Dataflow and BigQuery: Pub/Sub decouples and buffers spikes, Dataflow streams and autoscales without cluster sizing, and BigQuery serves the dashboard with seconds-level freshness.
X: B=Cloud SQL with hourly extract: hourly refresh misses the seconds target, and a single instance is not built for order-of-magnitude bursts.
C=Peak-sized Dataproc cluster with batch jobs: a few-minute cycle misses the latency target and a fixed cluster sized for peak is idle most of the time and needs operations work.
D=Daily load jobs: one-day freshness cannot support a live dashboard.
T: Translate each requirement (latency, burstiness, operating effort) into a property, then pick the serverless pipeline that has all of them.

@ GCP-PDE D1 T1.3 applied comparison
S: A company has about 200 existing Spark jobs on an on-premises Hadoop cluster. The jobs use custom JARs and Spark libraries and run nightly. The company wants them in Google Cloud within a quarter, with minimal code change, and plans to modernise later. Which service should the data engineer choose?
A: Dataproc, which runs Spark and Hadoop jobs largely unchanged on managed clusters
B: Dataflow, after rewriting each job as an Apache Beam pipeline
C: BigQuery, after translating every job into scheduled SQL queries
D: Cloud Data Fusion, after rebuilding each job as a visual pipeline from scratch
K: A
G: ## Lift-and-shift versus re-platform for data processing
Choosing a processing service depends on how much existing code you must keep. **Dataproc** (documentation now calls it Managed Service for Apache Spark) runs open source Spark and Hadoop, so existing jobs, JARs and libraries move with few or no changes. **Dataflow**, **BigQuery SQL** and **Cloud Data Fusion** are better targets for a later modernisation, but each requires rewriting the logic into a different model.
## Applying it
A quarter's timeline and the "minimal code change" requirement make the compatible runtime the right first step; modernisation can follow job by job.
W: Dataproc: it executes the existing Spark and Hadoop code with custom libraries, which meets the deadline and the minimal-change requirement.
X: B=Dataflow with Beam rewrites: it is a good long-term target, but rewriting 200 jobs conflicts with the quarter deadline and the minimal-change constraint.
C=BigQuery SQL translation: custom JARs and Spark library logic do not translate mechanically into SQL queries, so this is a large redevelopment.
D=Cloud Data Fusion rebuild: rebuilding every job visually from scratch is again a full rewrite.
T: When code reuse is the priority, pick the runtime that already runs the code, and modernise afterwards.

@ GCP-PDE D1 T1.3 advanced use-case
S: A company is moving a Hadoop cluster to Google Cloud. Its HDFS holds 300 TB that is mostly cold between monthly jobs, and the team wants to stop paying for always-on disks and to run Spark on temporary clusters. Which design decouples storage from compute?
A: Keep the data in Cloud Storage and read it from Spark and Hadoop jobs through the Cloud Storage connector
B: Rebuild an HDFS cluster on persistent disks in the cloud and keep it running between monthly jobs
C: Copy the data into each temporary cluster's local disks at startup and delete it when the cluster shuts down
D: Load the data into a Memorystore instance shared by all clusters and read it over the network
K: A
G: ## Separating storage from compute
In on-premises Hadoop, HDFS ties data to the cluster: to keep the data you keep the machines. On Google Cloud the common pattern is to store data in **Cloud Storage** and use the open source **Cloud Storage connector**, which lets Hadoop and Spark jobs read and write `gs://` paths directly. Clusters become disposable, created for a job and deleted afterwards, while the data persists and can also be read by BigQuery and other services.
## Trade-off
Object storage has higher per-operation latency than local HDFS, which is acceptable for batch jobs that run monthly.
W: Cloud Storage with the connector: durable storage independent of clusters, and temporary Spark clusters read it directly, so there are no always-on disks.
X: B=Rebuilt HDFS on persistent disks: it reproduces the coupling and the always-on cost the team wants to remove.
C=Copying into local disks at startup: every run pays to re-copy 300 TB, and anything not written back is lost when the cluster is deleted.
D=Memorystore: it is an in-memory cache service for small, hot data and is not designed to hold hundreds of terabytes for batch analytics.
T: Put the data in Cloud Storage and make compute temporary; the connector keeps Spark and Hadoop code working.

@ GCP-PDE D1 T1.3 applied comparison
S: A team lands event data from many producers into Cloud Storage for later loading to BigQuery and Spark. Producers' schemas gain new optional fields every few months. Which file format best fits the landing zone?
A: Avro, because files carry their schema and support adding fields, and both BigQuery and Spark read it
B: CSV, because every tool can open it and the header row documents each column's type
C: Plain text log lines, because the parser can be changed later without touching stored files
D: Proprietary binary dumps from each producer's database, because no conversion happens at write time
K: A
G: ## Choosing a landing format
For a shared lake zone, prefer **self-describing, typed, splittable formats**. Avro (row-oriented) and Parquet/ORC (columnar) embed their schema in the file, retain data types, compress well and are read natively by BigQuery, Dataflow and Spark. Avro handles schema evolution (adding optional fields) and suits write-heavy landing; Parquet suits analytical scans.
## Weak choices
CSV and text carry no types or nested structures and break when columns change. Producer-specific binary dumps need that producer's software to read.
W: Avro: it embeds the schema, preserves types, supports adding fields with defaults, and is read by BigQuery and Spark, so evolving producers do not break consumers.
X: B=CSV: a header gives column names, not types, and inserting or reordering columns can silently break loaders.
C=Plain log text: schema is implicit in parsing code, which creates ambiguity and slows every consumer.
D=Proprietary dumps: they can be read only with the source database's tooling, which defeats sharing across engines.
T: Use self-describing formats such as Avro or Parquet in a shared landing zone to absorb schema change and stay engine-neutral.

@ GCP-PDE D1 T1.4 applied use-case
S: A company runs a 2 TB MySQL database on premises that backs an order system. It wants to move to Cloud SQL for MySQL and can tolerate only a few minutes of downtime at cutover. Which approach fits?
A: Database Migration Service continuous migration: initial load, ongoing replication, then promotion
B: A one-time Database Migration Service dump and load started during business hours while writes continue
C: Datastream to Cloud Storage, followed by a manual import of the files into Cloud SQL after hours
D: BigQuery Data Transfer Service scheduled MySQL transfers into a BigQuery dataset, then export to Cloud SQL
K: A
G: ## Database Migration Service migration types
**Database Migration Service (DMS)** migrates databases into Cloud SQL and AlloyDB for PostgreSQL. A **continuous** migration performs an initial dump and load, then keeps replicating changes using change data capture (CDC) while the source stays live. When the destination is in sync, you finalise (promote) it into a standalone primary, so downtime is limited to the switch.
A **one-time** migration is a single point-in-time snapshot; applications cannot write to the source while it runs.
## Choosing
Tight downtime allowance plus a live source means continuous migration.
W: Continuous Database Migration Service migration: the source remains writable during the load and replication, and promoting the in-sync Cloud SQL instance keeps downtime to minutes.
X: B=One-time dump and load during business hours: it is a snapshot, so writes during the run are lost or must be blocked, which means long downtime.
C=Datastream to files then manual import: Datastream replicates into destinations such as BigQuery or Cloud Storage; building a Cloud SQL cutover from files is manual and has no managed promotion.
D=BigQuery Data Transfer Service: it loads data into BigQuery for analytics and cannot transfer data out of BigQuery to Cloud SQL.
T: For minimal-downtime database moves into Cloud SQL, use continuous Database Migration Service and promote at sync.

@ GCP-PDE D1 T1.4 applied comparison
S: An insurer wants its Oracle operational database on premises to stay in place, but analysts need the data in BigQuery within seconds of each change, without adding noticeable load to the source. Which service fits this requirement?
A: Datastream, a serverless change data capture and replication service with BigQuery as destination
B: Database Migration Service, because it replicates Oracle data into a BigQuery dataset
C: BigQuery Data Transfer Service scheduled queries that re-read the full Oracle tables every few minutes
D: Transfer Appliance, shipping an Oracle export to Google and loading it into BigQuery
K: A
G: ## Replication versus migration
Three tools are easily confused:
- **Datastream** is serverless CDC and replication. It reads database logs (Oracle, MySQL, PostgreSQL, SQL Server and others) with minimal source impact, takes an initial backfill, then streams changes to BigQuery or Cloud Storage. Source stays the system of record.
- **Database Migration Service** moves a database into Cloud SQL or AlloyDB and makes it the new primary.
- **BigQuery Data Transfer Service** automates scheduled loads into BigQuery from supported sources.
## Applying it
Continuous near-real-time analytics from an operational source that stays in place is the Datastream pattern.
W: Datastream: it captures changes from Oracle logs with low impact on the source and writes them to BigQuery for near real-time analytics.
X: B=Database Migration Service: its destinations are Cloud SQL and AlloyDB for PostgreSQL, so it migrates operational databases and does not feed BigQuery.
C=Repeated full reads: re-reading entire tables loads the production database heavily and cannot reach seconds-level freshness.
D=Transfer Appliance: it is a one-time offline bulk transfer into Cloud Storage and offers no ongoing change capture.
T: Use Datastream when an operational database must keep running and its changes must flow continuously to BigQuery.

@ GCP-PDE D1 T1.4 advanced tradeoff
S: A compliance team wants a BigQuery table that records every insert, update and delete made to a PostgreSQL table on premises, so that it can reconstruct the state of a row at any past moment. The analytics team separately wants a current-state copy. How should the data engineer configure Datastream for the compliance copy?
A: Use append-only write mode, which keeps each change event as a row with metadata for ordering
B: Use merge write mode, which keeps only the latest version of each row in the destination table
C: Skip Datastream and run a nightly full export, because change history cannot be captured by replication
D: Use merge write mode and rely on BigQuery time travel to see each past version indefinitely
K: A
G: ## Datastream write modes for BigQuery
When Datastream writes to BigQuery you choose between:
- **Merge mode**: the destination table mirrors the source's current state; updates and deletes are applied to the existing rows (needs a primary key; tables without one are written append-only).
- **Append-only mode**: every change event is appended as a new row, with a `datastream_metadata` column that carries source timestamps and identifiers to order events.
## Choosing
History and audit use cases need the events themselves, so append-only. A current-state view can be built on the history or fed by a second stream in merge mode. BigQuery time travel is a short-term recovery window, not an audit log.
W: Append-only write mode: it preserves every change event with metadata, so the compliance team can rebuild a row's state at any time.
X: B=Merge write mode: it overwrites rows to match the latest source state, so intermediate versions are lost.
C=Nightly full export: snapshots miss the changes made between exports and cannot show every intermediate change.
D=Merge plus time travel: time travel covers only a limited recent window, so it is not a durable history for audits.
T: Merge mode gives current state, append-only gives history; pick by whether the consumer needs the events.

@ GCP-PDE D1 T1.4 applied tradeoff
S: A school district must move a 40 GB PostgreSQL database to Cloud SQL for PostgreSQL. The system is used only during school hours, and the district accepts a full weekend of downtime. It wants the simplest migration with the fewest moving parts. Which Database Migration Service approach is best?
A: A one-time migration, taking a snapshot while the application is stopped
B: A continuous migration, kept running for several weeks before the cutover
C: Datastream replication to BigQuery, then export the tables into Cloud SQL
D: A Transfer Appliance shipment of database files, then a restore on a Compute Engine VM
K: A
G: ## Do not buy more than you need
Continuous migration exists to reduce downtime. If the business accepts a maintenance window, the snapshot-based **one-time migration** is simpler: Database Migration Service takes a point-in-time snapshot and loads it, and the destination is ready as soon as the load finishes. The cost is that no new writes may reach the source during the migration, which a stopped application guarantees.
## Judging the options
A longer-running replication adds monitoring and cutover steps that the district does not need. A 40 GB database does not justify offline shipping.
W: One-time Database Migration Service migration: a weekend window and a small database make a snapshot dump and load the simplest managed option, with the application stopped to prevent writes.
X: B=Continuous migration for weeks: it supports near-zero downtime the district did not ask for, and adds replication to monitor and a promotion step.
C=Datastream to BigQuery: it feeds analytics and cannot restore data into Cloud SQL, so it does not complete the migration.
D=Transfer Appliance: it is built for very large data volumes at remote sites, and 40 GB can simply be transferred over the network.
T: Match the migration type to the downtime budget: one-time for windows, continuous for near-zero downtime.

@ GCP-PDE D1 T1.4 applied use-case
S: A manufacturer wants to copy 600 TB of files from an on-premises NAS to Cloud Storage and then keep new and changed files synchronised every night. A 10 Gbps Cloud Interconnect link exists, and the network team wants to cap the bandwidth that the transfer uses during working hours. Which service should be used?
A: Storage Transfer Service with agents installed in the data centre to read the file system
B: Transfer Appliance, because the link is shared and appliances never use the network
C: A BigQuery Data Transfer Service transfer from the file share into a staging dataset
D: Datastream with the NAS as a source, writing change events to Cloud Storage

G: ## Online transfers from file systems
**Storage Transfer Service** moves data at scale, optimised for more than 1 TiB, between object and file storage: on-premises to Cloud Storage, Amazon S3 or Azure Blob Storage to Cloud Storage, HDFS to Cloud Storage and more. For on-premises sources you run **self-hosted agents** that read the file system, which gives you control over network routing and bandwidth use. Transfers can be scheduled to repeat, copying only new or changed data, and the service validates data integrity.
## Fit
A fast private link, recurring sync and a bandwidth cap are the signals for an online managed transfer rather than shipping hardware.
W: Storage Transfer Service with agents: it handles large file transfers from on-premises storage, supports recurring runs for changed files, and lets agents control the bandwidth used.
X: B=Transfer Appliance: it is an offline, one-time bulk upload option and cannot keep synchronising nightly; with a 10 Gbps link, the online route is practical.
C=BigQuery Data Transfer Service: it loads supported sources into BigQuery tables, not files from a NAS into Cloud Storage.
D=Datastream: its sources are databases and SaaS applications, not network file shares.
T: Recurring or large online file transfers, including bandwidth control, are the job of Storage Transfer Service with agents.

@ GCP-PDE D1 T1.4 applied tradeoff
S: A genomics lab at a remote site has 800 TB of sequencing files and a shared 200 Mbps internet connection. It needs the data in Cloud Storage within the next two months. Which approach is the best fit?
A: Order Transfer Appliance units, copy the data locally, and ship them to a Google upload facility
B: Use Storage Transfer Service agents over the 200 Mbps link and let it run until it finishes
C: Run a parallel copy script from several workstations on the same internet connection
D: Stream the files through Pub/Sub topics, which scale elastically beyond the link
K: A
G: ## Online versus offline transfer
Time to transfer is roughly data size divided by usable bandwidth. At 200 Mbps, even with the full link dedicated, 800 TB would take years, far beyond a two-month deadline, and the link is shared. When data size and bandwidth make an online transfer impractical, use an offline device.
**Transfer Appliance** is a high-capacity storage device. You request it, copy data to it (NFS, SMB, SCP or SSH), ship it back to a Google upload facility, and Google uploads the data to your Cloud Storage bucket and then wipes the appliance. The appliance is tamper-resistant and encrypted.
W: Transfer Appliance: shipping hardware bypasses the bandwidth limit, and the data lands in Cloud Storage within the deadline.
X: B=Storage Transfer Service over 200 Mbps: it is an online service and cannot exceed the link capacity, so the transfer would run for years.
C=Parallel copy scripts: more workstations still share the same 200 Mbps connection, so throughput does not improve.
D=Pub/Sub streaming: Pub/Sub is a messaging service, not a bulk file transfer method, and the traffic would cross the same link.
T: When size divided by bandwidth exceeds the deadline, ship the data with Transfer Appliance instead of sending it over the network.

@ GCP-PDE D1 T1.4 applied troubleshooting
