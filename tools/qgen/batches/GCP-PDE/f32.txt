@ GCP-PDE D5 T5.2 advanced use-case
S: A Cloud Composer DAG loads one day of sales into BigQuery with an append task. Operations often re-run failed days from the Airflow UI, and finance has found doubled revenue on re-run days. The engineer wants the DAG to be safe to re-run for any date. Which change achieves that?
A: Make the load task write to that run's date partition with overwrite semantics, so a re-run replaces the same data
B: Add a second task that appends the same rows again to a backup table, then compare the two tables each morning
C: Put the extract, transform and load code in a single PythonOperator task so a failed day restarts from the top
D: Set the task retries to zero so Airflow does not attempt a failed day a second time on its own after an error
K: A
G: ## Idempotent tasks
Composer documentation advises that each task be an idempotent unit of work. An idempotent task produces the same end state however many times it runs for the same logical date.
- Append-only loads are not idempotent: a re-run adds the day again.
- Loading to the **partition of the run date** with a truncate/overwrite disposition, or using `MERGE` on a key, is idempotent.
- Using the DAG run's logical date (a templated value) rather than the wall-clock time makes a re-run target the same data.
## What does not help
Disabling retries removes resilience without fixing re-runs started by people. Bundling work into one task makes the failure unit larger and partial reruns harder, which the docs advise against.
W: Partition overwrite for the run date: re-running the task for a given day rewrites that day's partition, so the result is the same however often it runs.
X: B=Second append plus comparison: it doubles the duplicate rows and adds a manual reconciliation step instead of preventing duplicates.
C=Single large task: a multi-step script inside one operator is discouraged; it still appends on re-run and restarts the whole job on any failure.
D=Zero retries: this removes automatic recovery from transient errors, and manual re-runs from the Airflow UI would still double the data.
T: Make each DAG task idempotent, for example by overwriting the run-date partition, so retries and manual re-runs are safe.

@ GCP-PDE D2 T2.3 applied use-case
S: An analytics engineering team builds SQL transformations in Dataform inside a Git repository. They need production runs of the compiled code every morning at 06:00 from the main branch, while developers continue to edit in separate workspaces. How should this be set up?
A: A Cloud Composer environment that copies the SQL files of each developer workspace into production each morning before the run
B: A BigQuery scheduled query for each file in the repository, set to 06:00 and created in the order the files were added
C: A manual run at 06:00 by whoever is on duty, started from their own workspace and executing the code on that workspace's branch
D: A release configuration that compiles the main branch, plus a workflow configuration that executes the result on a 06:00 schedule
K: D
G: ## Dataform CI/CD concepts
Dataform develops SQL workflows (SQLX files, with dependencies declared through `ref()`) in a Git-connected repository.
- **Workspaces** are isolated development areas, each on its own branch.
- A **release configuration** compiles a chosen Git branch or tag into a *compilation result* on a schedule or on demand.
- A **workflow configuration** executes selected actions from a compilation result, on a cron schedule, using a chosen service account.
This separates development from production: only reviewed, merged code on the production branch is compiled and run.
## Why other approaches fail
Copying developer workspaces mixes unreviewed code into production; one scheduled query per file loses dependency ordering; manual runs are not repeatable.
W: Release plus workflow configurations: the release configuration compiles the main branch and the workflow configuration runs the compiled result at 06:00 with dependency order kept.
X: A=Composer copying workspaces: it moves unreviewed developer code into production and adds an orchestrator Dataform already provides.
B=One scheduled query per file: this loses the dependency graph Dataform builds from `ref()`, and Dataform can schedule runs itself.
C=Manual workspace runs: they depend on people and on unreviewed branches, so they are neither repeatable nor safe.
T: In Dataform, release configurations compile the production branch and workflow configurations schedule execution of that compiled code.

@ GCP-PDE D1 T1.1 applied tradeoff
S: A retailer is building a new analytics platform. Raw files come from partners, curated data feeds finance reports, and a data science group experiments with copies of curated tables. Auditors want to prove that experiments cannot change finance data, and developers need freedom in a non-production space. Which layout best meets these goals?
A: Keep the environments in one project with a single dataset, and give analysts the project-level BigQuery Data Editor role to keep management simple
B: Use one project per analyst so that each person has full control, and copy the curated tables into each of those projects nightly
C: Use separate projects for raw, curated and sandbox data, with dev and prod split too, and grant roles to groups at the dataset or bucket level
D: Put the datasets and buckets in one shared project and separate teams by naming prefixes, relying on people to avoid touching other teams' tables
K: C
G: ## Projects as the governance boundary
In Google Cloud the project is the unit for IAM scope, quotas, billing, audit logs and organization-policy inheritance. For data platforms the common pattern is to separate **zones** (raw, curated, consumption, sandbox) and **environments** (dev, test, prod) into separate projects, grouped in folders so that policies apply by inheritance.
## Why it works for audits
- IAM granted on a prod project or dataset does not leak into the sandbox, so an experiment cannot write to finance tables by accident.
- Granting roles to groups at the dataset or bucket level keeps access reviews short and explainable.
- Cost and audit logs separate naturally per project.
W: Separate projects per zone and environment with group-based, resource-level roles: finance data lives in a project that experimenters cannot write to, and sandbox work has no effect on production.
X: A=Single project and dataset: project-level Data Editor lets any analyst change finance tables, so experiments and production share one blast radius.
B=A project per analyst: it multiplies copies of curated data, loses central control and leaves nobody accountable for freshness or access.
D=One shared project with prefixes: names are not an access boundary, so a role granted at project level reaches each team's data, which an auditor cannot accept.
T: Separate projects by data zone and environment, and grant group roles at the narrowest resource, so governance follows the resource hierarchy.

@ GCP-PDE D3 T3.3 applied definition
S: A lake team keeps an Apache Iceberg table in Cloud Storage and queries it from BigQuery as an Iceberg external table. A colleague suggests enabling metadata caching to speed up planning on this table. What should the data engineer say?
A: Enable it, but convert the table to CSV first, since the cache needs a file format that carries per-file statistics
B: Enable it, because Iceberg tables keep no file manifests, so the cache is where BigQuery gets its list of data files
C: Do not enable it, because metadata caching is a feature of native BigQuery tables rather than of external tables
D: Do not enable it, because BigQuery already uses the metadata Iceberg captures in its manifest files
K: D
G: ## Metadata caching and Iceberg
Metadata caching helps tables whose file metadata must be discovered by listing objects. **Apache Iceberg** tables already carry their own metadata: manifest files record the data files and statistics. BigQuery reads that metadata directly, so the cache cannot be used with Iceberg external tables and adds nothing.
## Where the cache does apply
BigLake tables over Cloud Storage and object tables, especially those with a large number of files and Hive partition filters.
## Take-away for lake design
Table formats that keep their own metadata (such as Iceberg) reduce the listing problem at the format level; plain Parquet folders rely on the cache.
W: Not needed for Iceberg: manifests already tell BigQuery which files and statistics apply, and the BigLake docs state that cached metadata can't be used with Iceberg external tables.
X: A=Convert to CSV: there is no such requirement, and CSV would lose the efficient columnar format.
B=No manifests: Iceberg's manifest files are the metadata, which is the reason caching is unnecessary.
C=Native tables: the cache is for object tables and BigLake tables over Cloud Storage or Amazon S3, not for native BigQuery tables.
T: Iceberg external tables use Iceberg manifest metadata, so BigQuery metadata caching does not apply.

@ GCP-PDE D4 T4.1 applied comparison
S: A team using column-level security finds that analysts' existing queries break with an error whenever the queries read a protected column through SELECT *. They want existing queries to keep working while the raw values stay hidden. What change achieves this?
A: Attach a data policy with a masking rule to the policy tag and grant analysts Masked Reader, so queries return masked values
B: Grant analysts the Fine-Grained Reader role on the policy tag, so their queries stop failing and read the column as stored
C: Remove the policy tag from the column and rely on dataset-level roles to hide the raw values from the analysts' queries
D: Rewrite each existing query to name its columns explicitly and leave out the protected ones, as column-level control expects
K: A
G: ## Error versus masked value
Plain column-level access control denies queries that read a protected column. The user must edit queries to exclude it.
With data masking, no query changes are needed: BigQuery applies the rule based on the roles the user has. Masking is optional and layered on column-level access control, so the same policy tag can serve raw readers, masked readers and denied users.
## Best practice
Grant the Masked Reader role at the data policy level; assigning it at project level or above gives access to all data policies in the project.
W: Masking plus Masked Reader: queries run unchanged and analysts see masked values instead of an error, because masking is layered on the same policy tag.
X: B=Fine-Grained Reader: this returns the raw values, so the protection is lost.
C=Removing the tag: dataset roles cannot hide a single column, so the value would become visible.
D=Rewriting queries: this is the approach masking was designed to avoid, and it leaves a heavy maintenance burden for each new query.
T: Data masking lets protected columns appear as masked values for unprivileged users, with no query rewrites.

@ GCP-PDE D4 T4.3 applied comparison
S: A reporting dataset contains 35 views that all read from a central sales dataset. Analysts hold access only to the reporting dataset. New views are added every week, and the team is tired of authorizing each new view on the sales dataset one by one. What should the data engineer configure?
A: Make the sales dataset a public exchange listing so that views in other datasets can query it without further setup
B: Grant the analysts the BigQuery Data Viewer role on the sales dataset so that the views run with their own credentials
C: Replace the views with a table copy of each query result and refresh those tables with scheduled queries each hour
D: Add the dataset holding the views as an authorized dataset on the source, which covers current and future views
K: D
G: ## Authorized datasets
An **authorized dataset** lets you authorize all views in a specified dataset to read the data of a second dataset. This replaces the need to configure individual authorized views.
- The dataset that holds the views is the authorized dataset.
- The dataset it reads from is the shared dataset (the source).
- Principals are given access to the dataset with the views, or to individual views in it, as needed.
## Applying it
With 35 views and weekly additions, authorizing the reporting dataset once covers existing and future views, while analysts still cannot read the sales dataset.
W: Authorized dataset: one authorization lets each current and future view in the dataset that holds the views read the source data, and analysts stay out of the source.
X: A=Public exchange listing: listings share data with subscribers and do not authorize views, and a public exchange exposes data to all authenticated users.
B=Data Viewer on the sales dataset: it exposes the tables to analysts directly, which defeats the point of reporting views.
C=Copies refreshed by scheduled queries: it duplicates data, adds latency and needs a scheduled query for each of the views.
T: Authorize the dataset that contains the views once on the source dataset instead of authorizing each view separately.
