@ GCP-PDE D1 T1.1 advanced use-case
S: A hospital network shares three years of patient encounter records with an external research group that studies how long patients wait between referral, first visit and surgery. Privacy officers require that no real calendar date leaves the network, but the researchers must still measure intervals and event order for each patient accurately. The data sits in BigQuery and the extract runs monthly. Which de-identification approach in Sensitive Data Protection meets the requirement with the least loss of analytic value?
A: Generalize every date to its year with a bucketing transformation, so no exact calendar date can be read and yearly trends remain available for the research group
B: Shift all dates by a random amount that is chosen per patient through a context field, so each patient's intervals and event order stay intact
C: Replace each date with a format-preserving encrypted token, so the column keeps its shape while the real value can be recovered by the hospital later
D: Redact every date column completely before export, so the research extract contains no calendar information at all and carries no re-identification risk
K: B
G: ## Date shifting in Sensitive Data Protection
Sensitive Data Protection (formerly Cloud DLP) offers several transformations for dates:
- **Bucketing / generalization** replaces a date with a coarser value such as the year. It hides the date, but the documentation notes that it can remove the order of events inside the bucket.
- **Redaction** removes the value altogether.
- **Date shifting** moves every date by a random number of days while **preserving the sequence and duration** of a period of time. Shifting is normally done in the context of an individual: with a context field such as `patient_id`, each patient's dates are shifted by the same amount, unique to that patient.
## Why the context field matters
If patient 17's referral is on 3 March and surgery on 20 April, a per-patient shift of -41 days moves both dates, so the 48-day wait is unchanged. Another patient gets a different shift, so dates cannot be lined up across patients to recover real calendar days.
W: B=Per-patient date shifting: one random offset per patient hides the real dates while keeping every interval and the order of that patient's events, which is exactly what the wait-time study needs.
X: A=Year bucketing: it hides exact dates, but intervals measured in days and the order of events inside a year are lost, so the waiting-time analysis breaks.
C=Format-preserving encryption: the ciphertext looks like a value but is not a date, so researchers cannot compute intervals from it, and keeping reversibility is not a stated need.
D=Full redaction: no dates at all means no intervals and no ordering, which destroys the analytic value the research group needs.
T: When analysts need intervals and sequence but not real dates, use date shifting with a per-entity context field.
V: Sensitive Data Protection, BigQuery

@ GCP-PDE D1 T1.1 advanced use-case
S: A subscription platform stores events for all of its business customers in shared BigQuery tables, and each table also has time travel and table snapshots for recovery. Contracts say that when a customer leaves, all of its data must become unreadable within one day, including copies held in snapshots, and the team cannot rewrite every snapshot. Which design should the data engineer implement from now on?
A: Encrypt each customer's sensitive values with AEAD functions and a keyset per customer, then destroy that customer's keyset when the contract ends
B: Protect the whole dataset with one customer-managed Cloud KMS key, then disable that key whenever any single customer asks for its data to go away
C: Run a DELETE statement for the departing customer's rows and shorten the dataset's time travel window to its minimum value of two days
D: Store each customer's rows in separate partitions and set a partition expiration so that the customer's partitions expire one day after offboarding
K: A
G: ## Crypto-deletion with AEAD in BigQuery
BigQuery encrypts all data at rest, and a **CMEK** key protects whole tables or datasets. For per-tenant control inside a shared table, GoogleSQL offers **AEAD encryption functions** (`KEYS.NEW_KEYSET`, `AEAD.ENCRYPT`, `AEAD.DECRYPT_STRING` and others).
- A **keyset** holds the keys that encrypt and decrypt values.
- You can keep one keyset per customer and encrypt that customer's values with it.
- The documentation describes **crypto-deletion (crypto-shredding)**: deleting the key renders every value encrypted with it unreadable, wherever the ciphertext lives.
## Why it fits copies
Snapshots, clones and time travel hold the ciphertext, not plaintext. Once the keyset is gone, none of those copies can be decrypted, so nothing has to be rewritten.
W: A=Per-customer AEAD keysets: destroying one customer's keyset makes that customer's ciphertext unreadable in the live table, in time travel and in every snapshot, without touching other tenants.
X: B=One CMEK key for the dataset: the key covers every tenant, so disabling it makes all customers' data unreadable, not just the departing customer's.
C=DELETE plus a short time travel window: the rows stay readable in existing table snapshots, and deleted data still passes through time travel and fail-safe, so the one-day promise fails.
D=Partition expiration: expiring partitions removes live data only; snapshots taken earlier keep their copy, and partitions are by date or range, not a clean per-tenant boundary.
T: To make one tenant's data unreadable everywhere at once, encrypt it with its own AEAD keyset and crypto-delete the keyset.
V: BigQuery, Cloud KMS

@ GCP-PDE D1 T1.1 advanced use-case
S: A brokerage lands daily trade-confirmation files in a Cloud Storage bucket. A regulator requires that every file be kept unchanged for six years, that nobody, including project owners, can shorten that period once it is approved, and that the data engineers can show this control to auditors. New files arrive every night, and older files must also be covered by the rule from the day it is applied. Which configuration should the data engineer use?
A: Enable Object Versioning and a lifecycle rule that deletes noncurrent versions after six years, so every overwritten file keeps an older copy for the auditors
B: Add a six-year retention policy to the bucket and lock it, so objects cannot be deleted or replaced early and the period can never be shortened
C: Set soft delete to its longest duration and let only two administrators delete objects, so removed files can be restored and deletions stay rare
D: Grant only the Storage Object Viewer role to every user of the bucket and alert on IAM policy changes, so nobody gets write access to the files
K: B
G: ## Bucket Lock for write-once storage
A **retention policy** on a Cloud Storage bucket says objects can be deleted or replaced only after they reach a given age. It applies retroactively to objects already in the bucket and to every new object.
**Locking** the policy makes it permanent:
- the policy cannot be removed and its retention period cannot be reduced (it can still be increased),
- the bucket cannot be deleted until every object has met the retention period.
Together with detailed audit logging, Bucket Lock is the documented way to meet regulations such as FINRA, SEC and CFTC rules for immutable records.
## What the other features do
Object Versioning keeps older generations but anyone with delete rights can still remove them. Soft delete lets you restore objects for a limited time after deletion. IAM roles can be changed by an owner at any time.
W: B=Locked retention policy: objects younger than six years cannot be deleted or replaced, the rule covers existing files too, and once locked nobody can shorten or remove it, which is the evidence auditors want.
X: A=Versioning with a lifecycle rule: noncurrent versions can still be deleted by a user with permission, and a lifecycle rule can be edited, so nothing is immutable.
C=Soft delete with few deleters: soft delete keeps deleted objects only for a limited window measured in days, it does not stop deletion or replacement, and administrators can change both settings.
D=Viewer-only IAM: a project owner can grant write access again at any time, so this is not a control that cannot be reversed.
T: For regulator-grade immutability in Cloud Storage, set a bucket retention policy and lock it.
V: Cloud Storage

@ GCP-PDE D1 T1.2 advanced tradeoff
S: A team runs a long-lived Dataproc cluster that keeps intermediate data in HDFS and serves Spark jobs submitted all day through the Dataproc Jobs API. A master VM reboot last month made HDFS unavailable until the NameNode recovered and failed every running job. The team plans to recreate the cluster in high availability mode with three masters. Which TWO limitations should the reliability plan still account for? (Select TWO)
A: All nodes of the HA cluster stay in a single zone, so an outage of that whole zone still takes down the cluster and its HDFS data
B: A job whose driver runs on the master node that fails is still terminated, because Jobs API drivers are not themselves highly available
C: The number of masters can be changed later on a running cluster, so the cluster must be watched to stop it from shrinking back to one master
D: HA mode moves HDFS to a regional Persistent Disk shared by the masters, so HDFS write throughput drops for every job on the cluster
E: HA mode removes YARN from the cluster and schedules work through ZooKeeper, so existing Spark jobs must be rewritten before migration
K: A,B
G: ## Dataproc high availability mode
Dataproc (named Managed Service for Apache Spark in current docs) supports two master configurations, chosen only at **cluster creation**: one master (default) or **three masters** (Hadoop HA).
In HA mode:
- HDFS and YARN high availability are configured with ZooKeeper on the masters, so a single master failure or reboot does not stop HDFS or YARN.
- **Job drivers** remain a single point of failure: jobs submitted through the Dataproc Jobs API are terminated if the master that runs their driver fails, unless the driver runs inside YARN and is written to be restartable.
- **Zonal failure**: every node of a Dataproc cluster, HA or not, is in one zone, so a zone-wide failure is not mitigated.
## Design consequence
HA mode protects against node failures, not zone loss. Keep durable data in Cloud Storage and make jobs restartable for the remaining gaps.
W: A=Single zone: HA spreads roles across three masters but all of them, and all workers, live in one zone, so a zone outage still stops the cluster.
B=Driver on the failed master: the documentation states that Jobs API drivers are not highly available; a master failure still ends those jobs unless drivers run restartably in YARN.
X: C=Changing master count later: the number of masters can be set only when the cluster is created, so it cannot shrink back by itself.
D=Shared regional disk: HA mode configures HDFS NameNode high availability across the masters; it does not move HDFS onto a shared regional disk.
E=YARN removed: HA mode keeps YARN and adds ResourceManager high availability; ZooKeeper coordinates failover, it does not replace the scheduler.
T: Dataproc HA mode survives a master failure, but drivers on that master and whole-zone outages still need separate protection.
V: Dataproc

@ GCP-PDE D1 T1.2 advanced troubleshooting
S: Two nightly ELT procedures run multi-statement transactions on the same date-partitioned BigQuery table. One updates yesterday's partition, the other deletes rows in a partition from last year. They overlap for a few minutes, and one of them sometimes fails with a concurrent update error and is rolled back. The engineer believed partitions isolate the work. The table must stay consistent and both jobs must finish before 06:00. What should the data engineer do?
A: Move each procedure into its own reservation, so slot isolation keeps the two transactions from touching the same table locks at the same time
B: Rewrite both procedures to run their DML outside transactions, because each statement then locks only the partition that it actually modifies
C: Keep the transactions, retry a failed one with exponential backoff after at least a minute, or stop the two jobs from overlapping
D: Split the table into two tables, one for current data and one for history, and rejoin them with a view for every report that reads the data
K: C
G: ## How BigQuery locks tables in transactions
When a multi-statement transaction **updates or deletes** rows, BigQuery takes a **table-level** lock, not a partition lock. Another transaction or DML statement that mutates the same table cannot run concurrently, **even if it targets different partitions**. BigQuery cancels conflicting transactions; conflicting DML outside a transaction is queued instead.
Reads and appends can run alongside a transaction, because `INSERT` statements do not conflict with each other.
## Recommended handling
The documentation advises retrying a failed transaction with exponential backoff and waiting **at least 60 seconds** before the first retry, because the lock can take seconds to release in the metadata layer. Avoiding overlapping schedules removes the conflict entirely.
W: C=Backoff retry or separate schedules: the conflict comes from a table-level lock, so a retry after the lock is released, or simply not overlapping the jobs, lets both finish while keeping atomicity.
X: A=Separate reservations: reservations isolate compute slots, not table locks; the two transactions still mutate the same table and still conflict.
B=DML outside transactions: individual DML statements are queued rather than cancelled, but each one still locks the table, and dropping the transactions gives up atomicity the jobs rely on.
D=Two tables plus a view: it is a large redesign of a working model to avoid a lock that a retry or a schedule change already handles.
T: BigQuery transactions that update or delete lock the whole table, not one partition; retry with backoff or avoid overlap.
V: BigQuery

@ GCP-PDE D1 T1.3 advanced comparison
S: A gaming studio collects events from 40 titles into one BigQuery table. Each title sends its own set of attributes, game teams add new attributes almost every week, and the platform team cannot schedule a schema change for each release. Analysts usually read two or three attributes per query and want to address them as fields in SQL instead of parsing a text blob in every query. Events with a brand-new attribute must still load. Which column design should the data engineer choose for the attributes?
A: A STRING column that holds the raw attribute text, with analysts calling JSON_VALUE on that text in each query that needs one of the attributes
B: A JSON column that holds the attributes as loaded, so new attributes need no schema change and queries address each field with dot notation
C: A STRUCT column with one typed field per known attribute, extended by an ALTER TABLE statement whenever a game team ships new attributes
D: A separate table for each game title with its own attribute columns, combined through a wildcard table query when analysts compare titles
K: B
G: ## Semi-structured data in BigQuery
BigQuery offers three common ways to store attributes whose shape varies:
- **`JSON` data type**: a schema-on-read column. Any valid JSON object loads without a schema change, and GoogleSQL addresses fields directly, for example `attrs.level` or `JSON_VALUE(attrs.boss_name)`. The documentation says it lets you process each field individually and write cost-efficient queries without enforcing a rigid `STRUCT` schema.
- **`STRUCT`**: a fixed schema enforced for every value in the column; new fields need a schema update first.
- **`STRING` with JSON text**: flexible to load, but each query parses the text with JSON functions, and nothing tells BigQuery that the value is structured.
## Applying it
Weekly new attributes rule out a fixed schema, and the analysts' wish to address fields instead of parsing text in every query rules out a string column. A `JSON` column gives both flexibility and field access.
W: B=JSON column: schema-on-read accepts new attributes with no table change, and analysts address the two or three fields they need directly in SQL.
X: A=STRING with JSON text: loading stays flexible, but every query parses the whole text to extract a field, which is the per-query parsing the analysts want to avoid.
C=STRUCT with ALTER TABLE: typed fields are convenient, but every new attribute needs a schema change first, which the platform team cannot schedule weekly.
D=Table per title with a wildcard query: each title's table still needs a schema change for new attributes, and cross-title queries must reconcile different schemas.
T: For attributes whose shape changes often, store them in a BigQuery JSON column (schema-on-read) rather than a STRUCT or a text string.
V: BigQuery

@ GCP-PDE D1 T1.3 advanced use-case
S: A media company runs Apache Spark on Managed Service for Apache Spark, a streaming team uses Apache Flink, and analysts use BigQuery. Today each engine keeps its own Hive metastore and its own copy of the same Iceberg tables, and schemas drift apart. Leadership wants one catalog that all three engines use for the same Iceberg tables in Cloud Storage, without the team running a metastore service. What should the data engineer propose?
A: A Cloud SQL database that hosts a shared Hive metastore schema, with every engine pointed at its JDBC connection string and the team managing upgrades
B: A self-managed Iceberg REST catalog service on GKE, sized for peak load and backed by a Cloud SQL database that the platform team operates
C: Knowledge Catalog entries for each engine's tables, so analysts can search them, while every engine keeps writing to its own Iceberg copy as today
D: The BigLake metastore, now called the Lakehouse runtime catalog, with each engine connecting through its Iceberg REST catalog endpoint

G: ## A shared serverless catalog for open tables
The **BigLake metastore**, renamed the **Lakehouse runtime catalog** in April 2026 (APIs and IAM names still say BigLake), is a fully managed, serverless metastore. It keeps table metadata in one place so that **Spark, Flink, Hive and BigQuery** share the same tables without duplicating files.

W: D=BigLake metastore (Lakehouse runtime catalog): one serverless catalog that Spark, Flink and BigQuery all use for the same Iceberg tables, so there is one copy and one schema with nothing to operate.

B=Self-managed REST catalog on GKE: it gives a shared catalog, but it is a service the team must size, patch and keep available.
C=Knowledge Catalog entries only: discovery metadata does not make the engines share tables, so the duplicate copies and schema drift remain.

@ GCP-PDE D1 T1.4 advanced tradeoff
S: Datastream replicates a busy PostgreSQL order database into BigQuery in merge mode. Finance only needs the tables to be no more than one hour behind the source, but the BigQuery bill for background CDC merge jobs is far higher than expected, and the jobs run on demand. The tables were created with a max_staleness of a few minutes. Which TWO changes lower the cost while still meeting the freshness need? (Select TWO)
A: Raise max_staleness on the replicated tables toward one hour, so BigQuery applies the changes less often
B: Assign the background CDC jobs to a slot reservation, so the merges use fixed capacity rather than on-demand pricing
C: Switch the stream to append-only mode and point finance's reports directly at the change log rows written by Datastream
D: Pause the Datastream stream every hour and resume it, so changes arrive in one large batch that BigQuery merges at once
E: Lower max_staleness to zero, so BigQuery never has to merge a backlog and each change is applied as soon as it arrives
K: A,B
G: ## How Datastream writes to BigQuery
In **merge mode** Datastream writes change records and BigQuery's CDC feature applies them to the table in **background merge jobs**.
- `max_staleness` on the table is a direct trade-off: a **lower** value means more frequent merges, fresher data and **higher cost**; a higher value means fewer merges and lower cost.
- Background CDC jobs that are not assigned to a reservation (assignment type `BACKGROUND` or `BACKGROUND_CHANGE_DATA_CAPTURE`) are billed **on demand**. Datastream's documentation recommends a slot reservation to cap and predict this cost.
## Applying it
Finance accepts one hour, so a max staleness near one hour plus a reservation for the background work cuts cost without breaking the requirement.
W: A=Higher max_staleness: merges run less often, so less background compute is billed, while data stays within the one-hour freshness limit.
B=Reservation for CDC background jobs: the merge work runs on fixed slot capacity instead of on-demand pricing, which the documentation recommends to control CDC cost.
X: C=Append-only mode: it avoids merges but gives finance a change log with many versions per order, so every report must deduplicate rows itself.
D=Hourly pause and resume: pausing does not change how BigQuery merges and adds an operational task without lowering the merge cost.
E=Staleness of zero: a lower staleness makes merges more frequent, which raises the cost instead of lowering it.
T: For Datastream to BigQuery, tune max_staleness to the freshness actually needed and run CDC background jobs on reserved slots.
V: Datastream, BigQuery

Which approach should the data engineer use?

@ GCP-PDE D2 T2.1 advanced use-case
S: Point-of-sale terminals publish about 30,000 small JSON messages per second to a Pub/Sub topic. Besides the existing streaming pipeline, compliance wants every raw message archived in Cloud Storage as batched files within about five minutes, with no transformation, no extra servers or jobs to run, and failed writes kept for inspection. What is the simplest design that meets these needs?
A: Add a Cloud Run service behind a push subscription that buffers messages in memory and writes a file to the bucket every five minutes
B: Add a second streaming Dataflow job from a Google template that reads the topic, windows the messages and writes files to the bucket
C: Add a Cloud Storage subscription to the topic with time and size batch limits, and configure a dead-letter topic on that subscription
D: Turn on topic message retention for the maximum period and export the retained messages to Cloud Storage once a day with a scheduled job
K: C
G: ## Export subscriptions to Cloud Storage
A **Cloud Storage subscription** is an export subscription: Pub/Sub itself writes messages to an existing bucket, so no subscriber client or Dataflow job is needed.
- Messages are written in **batches**; each batch becomes one object. You configure batching by **object size** and by **time elapsed** since the object was created.
- A message becomes visible only after its object is finalized.
- If writes fail, messages are negatively acknowledged and retried; with a **dead-letter topic** configured, messages that fail repeatedly move there.
The documentation says the overhead of a Dataflow job is unnecessary when messages need no processing before landing in Cloud Storage.
W: C=Cloud Storage subscription: Pub/Sub writes batched files on its own within the configured time limit, there is nothing to run, and the dead-letter topic keeps messages that cannot be written.
X: A=Cloud Run with push: it works but adds custom buffering code and a service to operate, and an instance restart can lose its in-memory batch.
B=Second Dataflow job: a template removes coding, but it is still a job with workers to pay for and monitor, which the documentation calls unnecessary for plain archiving.
D=Retention plus daily export: topic retention is not an archive feed, and a daily job misses the five-minute target.
T: To land raw Pub/Sub messages in Cloud Storage without processing, use a Cloud Storage subscription with batching and a dead-letter topic.
V: Pub/Sub, Cloud Storage

@ GCP-PDE D2 T2.1 advanced use-case
S: A payments team streams card authorizations into a BigQuery table with the Storage Write API. Its SQL-only analysts want each new row scored with a fraud rule and suspicious rows published to Pub/Sub within seconds, so that a case-management app can react. They want to stay in SQL and avoid running a separate stream processing engine. The project currently uses on-demand pricing. Which TWO steps are required? (Select TWO)
A: Write a continuous query that filters new rows and uses EXPORT DATA to publish suspicious rows to the Pub/Sub topic
B: Create an Enterprise or Enterprise Plus edition reservation and give the project an assignment of the CONTINUOUS job type
C: Schedule a query every minute that selects rows from the last minute and writes them to a Pub/Sub topic through a remote function
D: Create a Standard edition reservation with autoscaling, because continuous queries only need any reservation instead of on-demand
E: Turn on BI Engine for the table, so that its in-memory cache detects new rows and sends them to Pub/Sub without delay
K: A,B
G: ## BigQuery continuous queries
**Continuous queries** are SQL statements that keep running and process rows as they arrive in a table, for example from the Storage Write API.
- They can `INSERT` into BigQuery tables or `EXPORT DATA` to **Pub/Sub** topics (and to Bigtable or Spanner), which makes them an event-driven engine in SQL.
- Exports to Pub/Sub must run as a service account.
## Capacity requirement
Continuous queries do **not** support on-demand billing. You need an **Enterprise or Enterprise Plus** edition reservation with a reservation assignment of job type `CONTINUOUS`. A reservation used for that assignment cannot also hold assignments of other job types.
W: A=Continuous query with EXPORT DATA: it reads new rows as they are written, applies the SQL rule and publishes matches to Pub/Sub within seconds.
B=Enterprise reservation with a CONTINUOUS assignment: continuous queries only run on Enterprise or Enterprise Plus capacity assigned for the CONTINUOUS job type.
X: C=Scheduled query each minute: it adds a minute or more of delay, can miss or repeat rows at the boundaries, and a remote function is extra code to run.

- **Recover the whole database**: back up or export at a past timestamp and restore or import into a **new** database. This suits wide corruption, takes hours and cannot overwrite the existing database.
## Applying it
Only one column of known rows is wrong, and later valid writes must survive. A stale read of those rows at 14:09 plus a write-back repairs them online.
W: B=Stale read and write-back: it reads exactly the damaged rows as they were before 14:10 and restores them, keeping every valid later write and keeping the service online.
X: A=Restore last night's backup: restores cannot overwrite an existing database, and going back to last night would lose valid changes since then.
C=Export at a past time into a new database: it loses every valid write after 14:10 and needs a cutover for a problem limited to some rows.
D=Automatic undo: Spanner keeps old versions for reading but never reverses committed writes by itself.
T: For a surgical Spanner fix inside the retention window, stale-read the old values and write them back.

@ GCP-PDE D5 T5.5 advanced use-case
S: A platform team runs critical DAGs in a Cloud Composer environment. Last month an update that installed new PyPI packages broke many DAGs, and recovery took a day of manual work while finance reports waited. The team also plans to move to a newer Composer version later this year with minimal risk and no duplicate DAG runs. Which TWO practices should the team adopt? (Select TWO)
A: Save environment snapshots on a schedule, so a bad update such as new PyPI packages can be rolled back by loading a snapshot
B: Copy the DAG folder to a second bucket every night, because DAG files hold the full state of the environment including configuration
C: For the upgrade, pause DAGs, save a snapshot, create a new environment on the newer version and load the snapshot into it
D: Enable Object Versioning on the environment bucket, so Airflow database contents and Airflow configuration can be restored from it
E: Upgrade the existing environment in place on a Monday morning, so that any problems are found during working hours
K: A,C
G: ## Composer environment snapshots
An **environment snapshot** stores the state of a Cloud Composer (Managed Service for Apache Airflow) environment: Airflow configuration overrides, PyPI packages, environment variables, DAGs and a backup of the Airflow database.
- **Rollback**: load a snapshot to restore an earlier state, for example after an update that installed PyPI packages or changed configuration. Snapshots can be saved on a schedule.
- **Side-by-side upgrades**: save a snapshot, create a new environment with the same or a later version, and load the snapshot. **Pause DAGs** before saving to avoid duplicate DAG runs.
- Snapshots are stored in the environment's bucket (or a custom location) and are kept when the environment is deleted.
W: A=Scheduled snapshots: loading a snapshot rolls back packages and configuration, which turns last month's day of manual repair into a short restore.
C=Snapshot-based side-by-side upgrade: the new version runs next to the old one with the same state, and pausing DAGs first prevents duplicate runs.
X: B=Nightly DAG copy: DAG files do not include packages, configuration overrides or the Airflow database, so a restore would still be manual.
D=Bucket versioning: the Airflow database is not stored as files in the bucket, so versioning cannot restore it or the configuration.
E=In-place Monday upgrade: timing does not reduce risk, and an in-place upgrade gives no ready fallback environment.
T: Use Composer environment snapshots for rollbacks and side-by-side upgrades, pausing DAGs before saving.
V: Cloud Composer
