@ GCP-PDE D1 T1.1 advanced use-case
S: A media company runs a nightly Dataflow pipeline that reads from a Cloud Storage bucket in the ingest project and writes aggregates to one BigQuery dataset in the analytics project. Today the job runs as the project's Compute Engine default service account, which also holds a broad project-level editor role used by other workloads. The security team wants the pipeline to be able to do only what it needs. What should the data engineer do?
A: Create a dedicated user-managed worker service account with the Dataflow Worker role, read access on the one bucket and BigQuery data editing on the one dataset
B: Keep the default service account and remove its editor role, then rely on the submitting engineer's own permissions to cover all data access at run time
C: Create a service account key for the pipeline, store it in the bucket next to the input files, and grant that account the project-level BigQuery Admin role
D: Grant the Dataflow Admin role to the default service account at the organization level so that the pipeline can reach every project it might ever need
K: A
G: ## Which identity does a Dataflow job use?
A Dataflow job involves several identities. The submitting user (or service account) needs permission to create the job. The **worker service account** is what the worker VMs use to read sources and write sinks after the job starts. By default that is the Compute Engine default service account, which is often shared and over-privileged. Google recommends a **user-managed worker service account**, one per pipeline or per pipeline family, holding only the roles the pipeline needs.
## Least privilege for data
- The account needs `roles/dataflow.worker` so workers can talk to the Dataflow service.
- Data roles are granted on the narrowest resource that works: the single bucket for reads and the single dataset for writes (not the project).
- Long-lived keys are avoided; the account is attached to the job instead.
W: Dedicated worker service account: it separates this pipeline from other workloads, carries the Dataflow Worker role plus resource-level data roles on only the bucket and the dataset, and uses no downloadable key.
X: B=Default account without editor: removing the role breaks the job, and the worker account does not borrow the submitting engineer's permissions; the workers' own identity must hold the data access.
C=Key stored in the bucket: a downloadable key next to the data is a long-lived credential anyone with bucket access can copy, and BigQuery Admin at project level is far broader than a single dataset write.
D=Dataflow Admin at organization level: Dataflow Admin manages jobs rather than granting data access, and an organization-wide grant to a shared account is the opposite of least privilege.
T: Run each pipeline under its own user-managed worker service account with Dataflow Worker plus resource-level data roles.
V: Dataflow, IAM, BigQuery, Cloud Storage

@ GCP-PDE D1 T1.1 applied tradeoff
S: A retailer is building a new analytics platform. Raw files come from partners, curated data feeds finance reports, and a data science group experiments with copies of curated tables. Auditors want to prove that experiments cannot change finance data, and developers need freedom in a non-production space. Which layout best meets these goals?
A: Use separate projects for raw, curated and sandbox data, with dev and prod split too, and grant roles to groups at the dataset or bucket level
B: Put all datasets and buckets in one shared project and separate teams by naming prefixes, relying on the people to avoid touching other teams' tables
C: Use one project per analyst so that every person has full control, and copy curated tables into each of those projects every night
D: Keep every environment in one project with a single dataset, and give analysts the project-level BigQuery Data Editor role to keep management simple
K: A
G: ## Projects as the governance boundary
In Google Cloud the project is the unit for IAM scope, quotas, billing, audit logs and organization-policy inheritance. For data platforms the common pattern is to separate **zones** (raw, curated, consumption, sandbox) and **environments** (dev, test, prod) into separate projects, grouped in folders so that policies apply by inheritance.
## Why it works for audits
- IAM granted on a prod project or dataset does not leak into the sandbox, so an experiment cannot write to finance tables by accident.
- Granting roles to groups at the dataset or bucket level keeps access reviews short and explainable.
- Cost and audit logs separate naturally per project.
W: Separate projects per zone and environment with group-based, resource-level roles: finance data lives in a project that experimenters cannot write to, and sandbox work has no effect on production.
X: B=One shared project with prefixes: names are not an access boundary, so any role granted at project level reaches every team's data, which an auditor cannot accept.
C=A project per analyst: it multiplies copies of curated data, loses central control and leaves nobody accountable for freshness or access.
D=Single project and dataset: project-level Data Editor lets any analyst change finance tables, so experiments and production share one blast radius.
T: Separate projects by data zone and environment, and grant group roles at the narrowest resource, so governance follows the resource hierarchy.
V: BigQuery, Cloud Storage, IAM, Resource Manager

@ GCP-PDE D1 T1.1 applied definition
S: A European bank creates a BigQuery dataset in the EU multi-region and wants every table in it protected with a customer-managed encryption key in Cloud KMS. In which location should the key ring be created?
A: In a multi-regional key ring in the matching location, which is europe for an EU dataset
B: In the global location, because a global key can protect datasets in every BigQuery location
C: In any single region inside the EU, because a regional key ring is allowed to protect a multi-region dataset in that geography
D: In the us multi-region, because key rings are always kept in the United States for tables
K: A
G: ## CMEK location rules
With CMEK, BigQuery encrypts the data encryption keys with a Cloud KMS key you control. A Cloud KMS key lives in exactly one key ring tied to a location and cannot be moved later. BigQuery requires that the key ring location **matches the dataset location**. A multi-regional dataset uses a multi-regional key ring from a matching location: a dataset in `US` uses key ring location `us`, and a dataset in `EU` uses `europe`.
## Residency angle
Choosing the key location is part of the residency design. A mismatch is rejected when the table is created, so plan key rings with dataset locations.
W: Matching multi-regional key ring: the dataset in the EU multi-region needs a key ring in the europe location, which keeps key and data in the same geography.
X: B=Global key ring: a global location is not accepted as a match for a dataset in a specific location, and it would also undermine a residency argument.
C=Single EU region: a regional key does not match a multi-regional dataset, so the table could not be created with it.
D=us multi-region: this does not match an EU dataset and would place the key outside the geography the bank chose for compliance reasons.
T: Create the Cloud KMS key ring in a location that matches the BigQuery dataset: europe for EU, us for US.
V: Cloud KMS, BigQuery

@ GCP-PDE D1 T1.1 advanced tradeoff
S: A payments company copies customer and order tables into BigQuery. Analysts must join the two tables on customer ID, but they must never see the real IDs. A small fraud service must be able to recover the real ID for flagged customers. Which TWO design choices meet these needs? (Select TWO)
A: Replace the ID with a deterministic encryption token (AES-SIV) produced by Sensitive Data Protection using a Cloud KMS-wrapped key
B: Hash the ID in each table with a different random salt, so that a stolen table cannot be matched to another table
C: Allow only the fraud service's service account to use the key for decryption and re-identification
D: Replace the ID with the fixed text REDACTED in both tables, then keep the originals in a separate dataset for the fraud service
E: Allow every analyst group to use the key, because tokens are only useful together with the original tables
K: A,C
G: ## Pseudonymization with Sensitive Data Protection
Pseudonymization replaces a sensitive value with a cryptographic token. Sensitive Data Protection offers three methods: **deterministic encryption (AES-SIV)**, **format-preserving encryption (FPE-FFX)** and **cryptographic hashing (HMAC-SHA-256)**. The first two are **two-way**: the same key reverses the token. Hashing is one-way.
## Two properties this scenario needs
- **Consistency**: the same input and key give the same token, so joins and aggregations across tables still work and referential integrity is preserved.
- **Authorized reversibility**: because the key sits in Cloud KMS, only principals allowed to use it can re-identify values, so decrypt access is the control point.
W: A=Deterministic encryption with a KMS-wrapped key: identical IDs map to identical tokens, so the join works, and the key can reverse the token for authorized use.
C=Decrypt rights only for the fraud service: IAM on the key decides who can re-identify, so analysts keep tokens while the fraud service can recover the originals.
X: B=Random salt per table: different salts give different hashes for the same ID, which breaks the join, and a hash is one-way anyway, so the fraud service could not recover IDs.
D=Fixed text REDACTED: every row would carry the same value, so the join collapses, and keeping originals elsewhere adds a second copy to secure.
E=Key access for every analyst: anyone allowed to decrypt could reverse all tokens, which defeats the requirement that analysts never see real IDs.
T: Use two-way deterministic tokens for joinable pseudonyms and keep decryption permission on the Cloud KMS key limited to the re-identification service.
V: Sensitive Data Protection, Cloud KMS, BigQuery

@ GCP-PDE D1 T1.1 applied use-case
S: A bank refreshes its test environment nightly from production. The test application validates 16-digit card numbers with a length and digit check, and testers must not see real card numbers. The team also wants the same card number to map to the same replacement across tables. Which de-identification approach fits?
A: Format-preserving encryption with a Cloud KMS-wrapped key, applied to the card number column during the copy
B: Cryptographic hashing, which always returns a value of fixed length regardless of the input and is not reversible
C: Redact the whole card number column and let the test application fill in random numbers when it needs them
D: Replace each card number with a mask of asterisks while keeping only the last four digits visible in test
K: A
G: ## Choosing among the pseudonymization methods
Sensitive Data Protection documents safeguarding test and development environments as a typical use of tokenization: production data is replicated to a lower tier with tokenized fields so developers keep realistic data structures.
- **Format-preserving encryption (FPE-FFX)** keeps the character set and the length of the input, so a 16-digit number stays a 16-digit number, and equal inputs give equal tokens under the same key.
- **Deterministic encryption (AES-SIV)** gives a base64 token that does not keep length or character set.
- **Cryptographic hashing** gives a fixed-length digest and cannot be reversed.
## Fit here
The application checks length and digit format, so a format-preserving token passes validation while hiding the real value.
W: Format-preserving encryption: output is still 16 digits, so format validation in the test application passes, equal cards map to equal tokens across tables, and real numbers are not visible.
X: B=Cryptographic hashing: a fixed-length digest that is not 16 digits would fail the application's format check, so tests would break.
C=Redact and random fill: the same card would get different values in different tables, losing referential integrity across tables.
D=Asterisk mask with last four: a masked string is no longer a valid 16-digit number, and keeping the last four digits reveals part of real data.
T: When tests need the original format and consistent mapping, use format-preserving encryption with a Cloud KMS key.
V: Sensitive Data Protection, Cloud KMS, BigQuery

@ GCP-PDE D1 T1.1 applied troubleshooting
S: A team creates a BigQuery dataset in the EU multi-region to satisfy a residency rule. Parquet files for it are in a Cloud Storage bucket in the us-central1 region, and the load job fails with a location error. The files must not be stored outside the EU. What is the right fix?
A: Place the files in a Cloud Storage bucket in an EU location that matches the dataset, then load from that bucket
B: Recreate the dataset in the US multi-region so that it matches the bucket, and let the load job continue
C: Add a second copy of the dataset in the US and make the load job write to both datasets
D: Keep the bucket as it is and run the load job in a US location, which can write into an EU dataset
K: A
G: ## Co-location of load sources and datasets
A BigQuery dataset has a location fixed at creation. A load job reading from Cloud Storage requires the bucket to be **in the same location as the dataset**. For an EU multi-region dataset the bucket can be in a single EU region (for example Netherlands) or a dual-region that includes it. The same idea applies to external tables.
## Residency
Residency rules are about where the data is stored. Moving the dataset to the US would break the rule that the files must not leave the EU, so the bucket moves to a matching EU location instead (for example with Storage Transfer Service) and the pipeline reads from there.
W: Matching EU bucket: the load job and dataset are then in the same location, and the data stays within the EU as the rule requires.
X: B=Dataset in the US: this satisfies the match but sends data to the US, violating the residency rule.
C=Duplicate dataset in the US: it still copies EU data to the US and doubles the governance burden without fixing the original mismatch.
D=Run the job in the US: a job runs in the location of the dataset it targets, so a US job cannot write an EU dataset.
T: Keep Cloud Storage buckets in the same geography as the BigQuery dataset, so loads work and residency holds.
V: BigQuery, Cloud Storage, Storage Transfer Service

@ GCP-PDE D1 T1.1 advanced use-case
S: A health-data company must keep patient data in the EU. Platform teams create projects freely, so the architects want a guardrail and a pipeline design that keep processing in the EU too. Which TWO actions help? (Select TWO)
A: Set the resource locations organization policy with an EU value group at the organization or folder, so datasets and buckets cannot be created elsewhere
B: Run Dataflow jobs in an EU region, because the Dataflow region stores job metadata and deploys and controls the workers
C: Rely on the Dataflow job name containing the text eu, because naming is how Google Cloud picks the processing location
D: Enforce the policy only in the production project, since development projects never hold copies of real patient records
E: Use the global Cloud KMS location for the keys, because the global location is treated as inside every geography

Data residency has two parts: where data is stored and where it is processed.

Organization policies set at an organization or folder inherit down to projects, so the guardrail covers projects teams create later.

V: Organization Policy, Dataflow, Cloud Storage, BigQuery

@ GCP-PDE D1 T1.1 advanced use-case
S: A finance team has granted analysts BigQuery Data Viewer on the curated dataset. A compliance review finds that an analyst could run a query and save the results into a BigQuery dataset in a personal project outside the company. IAM alone cannot stop this because the analyst has legitimate read access. Which control addresses it?
A: A VPC Service Controls perimeter around the projects with BigQuery, with egress rules that allow only approved destinations
B: A Cloud KMS key on the curated dataset, because encryption at rest prevents authorized readers from saving results elsewhere
C: A shorter time travel window on the dataset, because history on tables is what lets analysts take results out
D: A BigQuery slot reservation for the analysts, since capacity limits reduce how much data can leave
K: A
G: ## Perimeter controls versus IAM
IAM answers "who may act on this resource". It cannot express "this data must not leave this boundary" for someone who is allowed to read it. **VPC Service Controls** creates a **security perimeter** around Google Cloud resources (BigQuery is a supported service). Requests that cross the perimeter, such as a copy to a project outside it, are blocked unless an **ingress or egress rule** allows them. Perimeters are independent of IAM, which makes them a defence against data exfiltration, misconfigured access and compromised credentials.
## Why other controls miss
Encryption protects stored bytes, not who can read them after authorization. Time travel and slots affect recovery and capacity.
W: VPC Service Controls perimeter with egress rules: even a user with valid read access cannot move the data to a project outside the perimeter, except to destinations explicitly allowed.
X: B=CMEK on the dataset: BigQuery decrypts data transparently for authorized readers, so the saved results are readable in the other project.
C=Shorter time travel: time travel is about recovering older table states, not about where query results can be written.
D=Slot reservation: capacity affects speed and cost, and a small query can still copy sensitive rows out.
T: Use VPC Service Controls to stop exfiltration by authorized users; IAM alone cannot do it.
V: VPC Service Controls, BigQuery, IAM

@ GCP-PDE D1 T1.1 applied comparison
S: An auditor asks for evidence of which users queried a sensitive BigQuery table in the last quarter, and wants the evidence kept for years outside the project. What should the data engineer propose?
A: Use BigQuery Data Access audit logs and route them to a sink with long retention
B: Rely on Admin Activity audit logs alone, because they record every query a user runs against table data
C: Ask each analyst to record their own queries in a shared spreadsheet, then sign the sheet each quarter
D: Enable Data Access audit logs on Cloud Storage only, because BigQuery tables are stored in Cloud Storage objects
K: A
G: ## Audit log types
Cloud Audit Logs has several types:
- **Admin Activity** logs record API calls that change configuration or metadata. They are always written and cannot be disabled.
- **Data Access** logs record reads and writes of user data. They are disabled by default for most services, but BigQuery is the exception and writes Data Access audit logs by default.
## Retention and export
Log buckets have their own retention, so for multi-year evidence a **log sink** exports entries to a BigQuery dataset, Cloud Storage bucket or a log bucket in a separate audit project. Doing this outside the data project also guards the evidence against changes by project admins.
W: BigQuery Data Access audit logs routed through a sink: they show who ran which job on which resource, and an external destination keeps them as long as required.
X: B=Admin Activity only: these logs cover configuration changes such as creating a table, not the reading of its contents.
C=Spreadsheet: self-reported, editable evidence is not accepted by auditors and misses queries from service accounts.
D=Cloud Storage Data Access logs: BigQuery managed storage is not exposed as customer-visible Cloud Storage objects, so those logs would not show queries.
T: BigQuery Data Access audit logs show who read what; export them with a sink for long-term, separate retention.
V: Cloud Audit Logs, Cloud Logging, BigQuery

@ GCP-PDE D1 T1.1 applied definition
S: A company's on-premises scheduler sometimes pushes data into Google Cloud, and security has found service account JSON keys in old repositories. Which TWO measures best reduce this risk for the on-premises workloads? (Select TWO)
A: Enforce the organization policy that disables creation of service account keys, so unmanaged long-term keys cannot be issued
B: Move the keys to a private bucket and rotate them every year, so that the key lifetime stays within the audit period
C: Let the on-premises workloads authenticate with Workload Identity Federation, which exchanges the identity from their own provider for short-lived credentials
D: Give the scheduler's account the basic Admin role, so that it never needs a second account that could have its keys leaked
E: Copy the keys onto every build server so that a missing key never stops a pipeline
K: A,C
G: ## Keyless authentication
A service account key is a long-lived credential. If it leaks, it works from anywhere until it is deleted. Google's guidance is to avoid keys where possible:
- **Workload Identity Federation** lets workloads outside Google Cloud (on-premises or other clouds) use their own identity provider to obtain short-lived Google credentials, with no key stored.
- The organization policy constraint `iam.managed.disableServiceAccountKeyCreation` (and the legacy `iam.disableServiceAccountKeyCreation`) blocks new external keys in the projects it covers, so the old pattern cannot return.
## Why partial fixes fail
Rotating or relocating keys keeps a long-lived secret to protect, and broader roles only raise the damage of a leak.
W: A=Disable key creation by policy: the control is enforced centrally, so new unmanaged keys cannot appear in covered projects.
C=Workload Identity Federation: the on-premises scheduler trades its own identity for short-lived credentials, so no key exists to leak.
X: B=Private bucket and yearly rotation: a key remains valid for a year and anyone with bucket access can copy it, so the risk is only reduced a little.
D=Basic Admin role: more privilege on the account makes a leaked credential more damaging, and it does not remove keys.
E=Keys on every build server: this multiplies the places where a key can leak.
T: Remove long-lived keys with Workload Identity Federation and block new ones with the organization policy.
V: IAM, Workload Identity Federation, Organization Policy

@ GCP-PDE D1 T1.1 applied use-case
S: A security policy says Dataflow workers must not have public IP addresses, and the organization policy blocks external IP addresses on VMs. The pipeline reads from Pub/Sub and writes to BigQuery, and does not call any internet service. How should the data engineer configure the job's network?
A: Run workers in a subnet that has Private Google Access enabled and turn off external IP addresses for the workers
B: Keep external IP addresses on the workers and ask the security team to add an exception for the pipeline project
C: Create a Cloud NAT gateway and attach a public IP to every worker so that traffic still reaches the Google APIs
D: Move the pipeline to a laptop with a public address, because Pub/Sub and BigQuery can only be reached from the public internet
K: A
G: ## Dataflow workers without external IPs
By default Dataflow assigns both external and internal IP addresses to workers. When external IPs are turned off, the job can only reach resources on the same VPC, a Shared VPC, or a peered network, and cannot reach the internet. To reach Google APIs such as Pub/Sub, BigQuery and Cloud Storage, the worker subnet needs **Private Google Access**, which lets VMs with only internal addresses use Google API IP addresses.

This meets the policy without exceptions. A pipeline that must call an internet service would additionally need Cloud NAT, but this one does not.
