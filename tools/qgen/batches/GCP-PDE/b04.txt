@ GCP-PDE D2 T2.2 applied tradeoff
S: A manufacturer runs nightly Spark and Hive jobs on an on-premises Hadoop cluster that holds 300 TB in HDFS and sits idle about 18 hours a day. The team wants to move to Google Cloud with minimal code change and lower cost. Which design best meets this?
A: Copy the data to Cloud Storage, change paths to gs:// through the Cloud Storage connector, and create a Dataproc cluster for each nightly run, deleting it after
B: Create one large persistent Dataproc cluster sized for the nightly peak and copy all 300 TB into its HDFS on persistent disks, keeping it running all day
C: Rewrite every Spark and Hive job as an Apache Beam pipeline on Dataflow and load all 300 TB into Bigtable tables for the jobs to read
D: Run the existing Hadoop distribution on a managed instance group of Compute Engine VMs that stays at full size, with HDFS replicated across zones
K: A
G: ## Separating storage from compute for Hadoop and Spark
On-premises Hadoop couples storage (HDFS) to the compute nodes, so the cluster must stay up to keep data available. On Google Cloud the usual pattern is to keep data in **Cloud Storage** and treat Dataproc clusters as disposable compute.
- The **Cloud Storage connector** lets Hadoop and Spark jobs read and write `gs://` paths as if they were HDFS, so existing Spark and Hive code needs little change.
- Because the data survives outside the cluster, a cluster can be created for a job run and deleted when it finishes (an **ephemeral cluster**), so you pay only for the hours the job runs.
- Dataproc (now branded Managed Service for Apache Spark) also offers workflow templates and Composer operators to create, run and delete clusters automatically.
## Applying it here
Nightly jobs and 18 idle hours are the signal for ephemeral clusters; an unchanged Spark/Hive code base is the signal for Dataproc rather than a rewrite.
W: Cloud Storage plus ephemeral Dataproc clusters: data stays durable in Cloud Storage, jobs keep Spark and Hive code through the connector, and compute is paid for only during the nightly run.
X: B=Persistent cluster with HDFS: you pay for peak-sized VMs all day, and data held in HDFS on cluster disks ties storage to compute, which is the on-premises problem the move should remove.
C=Rewrite on Dataflow and Bigtable: this abandons the minimal-change goal, and Bigtable is a low-latency key-value store, not a file store for batch Spark and Hive jobs.
D=Self-managed Hadoop on Compute Engine: it keeps full-size VMs running all day and adds operations work that managed Dataproc removes, so it saves neither cost nor effort.
T: For batch Hadoop and Spark, keep data in Cloud Storage and use ephemeral Dataproc clusters so compute cost follows job runtime.

@ GCP-PDE D2 T2.2 advanced definition
S: A Dataproc cluster runs fault-tolerant Spark batch jobs and the team wants to add cheap extra capacity during the nightly peak. Which TWO statements about secondary workers are correct? (Select TWO)
A: Secondary workers act only as processing nodes and do not store HDFS data, so they scale compute without scaling storage
B: Secondary workers host HDFS DataNodes, so adding them is the way to scale the cluster's HDFS storage capacity
C: Secondary workers can be Spot VMs, which lowers cost for batch work that can tolerate a node being reclaimed
D: Secondary workers must always be non-preemptible, because the loss of any one worker aborts the running Spark job
E: Secondary workers replace the master node during failures, so a cluster using them does not need a high availability setup
K: A,C
G: ## Primary and secondary workers in Dataproc
A Dataproc cluster has **primary workers** (standard VMs that run HDFS DataNodes and the node manager) and optional **secondary workers**.
- Secondary workers **only process**: they hold no HDFS data, only a local cache on their disks.
- They can be **Spot VMs**, standard preemptible VMs or non-preemptible VMs. Because a reclaimed node loses no stored data, Spark can reschedule its tasks.
- They are managed through managed instance groups, so they may appear a little after the scale-up call returns.
## Design guidance
Use stable primary workers for data and master roles, and add secondary workers for elastic, interruptible compute. Keep data in Cloud Storage when possible so even primary-worker loss is harmless.
W: A=Processing only: secondary workers add CPU and memory but no HDFS storage, so compute scales independently from storage.
C=Spot VMs: secondary workers can be Spot VMs, which suits fault-tolerant batch work because lost tasks are rescheduled on other nodes.
X: B=Scaling HDFS: secondary workers do not run DataNodes, so they add no HDFS capacity; primary workers or Cloud Storage provide storage.
D=Always non-preemptible: preemptible and Spot types are explicitly supported, and Spark retries lost tasks, so a single reclaimed worker does not abort the job.
E=Replacing the master: secondary workers have no master role at all; cluster high availability is configured through multiple master nodes.
T: Secondary workers are interruptible, storage-free compute for Dataproc; keep durable data on primary workers or in Cloud Storage.

@ GCP-PDE D2 T2.2 applied use-case
S: A Spark job on Dataproc must read a 4 TB BigQuery fact table, join it with files in Cloud Storage and write the result back to BigQuery. The team wants parallel reads without a manual export step. What should the data engineer use?
A: The Spark BigQuery connector, which reads table data in parallel through the BigQuery Storage Read API and writes results back to BigQuery
B: A scheduled query that exports the table each night to CSV files in Cloud Storage, which Spark then reads as a separate input directory
C: A JDBC driver pointed at BigQuery so each Spark executor pages through the table with a single long-running SELECT statement
D: The BigQuery REST API jobs.getQueryResults method called from the Spark driver, which collects the rows and distributes them to executors
K: A
G: ## Reading BigQuery from Spark
BigQuery is not an HDFS-style store, so Spark needs a connector. The **Spark BigQuery connector** reads through the **BigQuery Storage Read API**, which splits the table into streams that Spark executors read in parallel, applying column projection and filter pushdown. Writing back uses load jobs or the Storage Write API.
## Why exports and drivers lose
- A manual or scheduled export adds a copy, a delay and a cleanup job, and the data is stale.
- A single driver or single result stream becomes a bottleneck at multi-terabyte sizes.
W: Spark BigQuery connector: it reads in parallel using the Storage Read API, pushes down column and filter selection, and writes results back, with no export step.
X: B=Nightly CSV export: it adds a stale copy and a pipeline stage, and CSV loses types, which is the manual export step the team wants to avoid.
C=JDBC with one SELECT: a single result stream pages the whole table through one connection and cannot use parallel reads from many executors.
D=jobs.getQueryResults on the driver: collecting results on one driver node bottlenecks at 4 TB and defeats the purpose of distributed processing.
T: Use the Spark BigQuery connector so Dataproc jobs read and write BigQuery in parallel through the Storage APIs without exports.

S: A retail finance team of analysts with little programming experience must build batch pipelines that pull tables from an on-premises Oracle database, apply joins and cleansing, and load BigQuery. They want a visual interface, prebuilt connectors and no cluster administration. Which service fits best?
A: Cloud Data Fusion, which offers a drag-and-drop pipeline designer with plugins and runs pipelines on ephemeral Dataproc clusters it provisions
B: Dataproc with hand-written PySpark jobs, because this gives the analysts direct control of executors, partitions and cluster sizing for every run
C: Dataflow with custom Apache Beam Java code, because a code-first pipeline is the only way to read relational sources in batch mode
D: Cloud Composer with Python DAGs, because orchestration code is the main tool for extracting, transforming and loading the tables
K: A
G: ## Cloud Data Fusion
Cloud Data Fusion is a managed, code-free data integration service built on the open-source CDAP project. Users design pipelines on a canvas by connecting **plugins** (sources, transforms, aggregates, sinks) and can use Wrangler for interactive cleansing.
- Instances come as Developer, Basic or Enterprise editions.
- At run time Data Fusion provisions an **ephemeral Dataproc cluster** in the customer project, runs the pipeline with Spark and deletes the cluster, so the user does not administer clusters.
## Choosing against the others
Choose it when users prefer a visual tool and prebuilt connectors; choose Dataflow or Dataproc when engineers want code-level control; Composer orchestrates work and does not itself transform data.
W: Cloud Data Fusion: visual designer, prebuilt database and BigQuery plugins, and managed ephemeral Dataproc execution match analysts who want no code and no cluster work.
X: B=Hand-written PySpark: it requires programming skill and cluster tuning, the opposite of a visual, no-administration requirement.
C=Custom Beam code: Beam batch pipelines can read relational data through connectors, so code is not the only way; it also needs developers the team lacks.

@ GCP-PDE D2 T2.2 applied definition
S: A data engineer maintains a nightly BigQuery job with several steps: declare a date variable, delete a partition, insert recomputed rows, check a row count and, if it is zero, raise an error. Several teams in other datasets must run the same logic with different dates. Which TWO benefits do BigQuery SQL stored procedures give here? (Select TWO)
A: The logic can be defined once in a dataset and called by teams using different input arguments
B: The routine runs automatically each night once created, because a procedure carries its own built-in schedule
C: The multi-statement body can use variables and control flow such as IF and loops, including raising an error
D: The routine runs on a Dataproc cluster that BigQuery creates, which gives the steps access to Spark libraries
E: Each caller must copy the procedure body into its own dataset, because a procedure cannot be referenced from another dataset
K: A,C
G: ## SQL stored procedures in BigQuery
A stored procedure is a named, reusable collection of SQL statements saved in a dataset. It can accept **IN, OUT and INOUT arguments**, declare variables, and use procedural language such as `IF`, `WHILE` and `RAISE`. Callers invoke it with `CALL project.dataset.procedure(args)`, including from other datasets if they have access.
## Limits to remember
- A procedure has **no schedule of its own**. Run it from a scheduled query, Cloud Composer, Workflows or Dataform.
- SQL procedures execute inside BigQuery; there is also a separate type, procedures for Apache Spark, which is not what a plain SQL procedure uses.
W: A=Reuse with arguments: one definition in a dataset is called by many teams with different parameters, so logic is not copied.
C=Control flow: variables, IF logic and raising an error let a multi-statement job validate its own result.
X: B=Built-in schedule: procedures never run on their own; a scheduled query, Composer or Workflows must call them.
D=Dataproc execution: a SQL procedure runs in BigQuery itself; Spark-based procedures are a different routine type.
E=Copy per dataset: procedures can be called across datasets by qualified name, which is why they centralise logic.
T: A stored procedure packages multi-statement, parameterised SQL logic for reuse, but something else must trigger it.

@ GCP-PDE D2 T2.2 applied use-case
S: Each night a BigQuery staging table receives a change feed of customers: new customers, changed addresses and flagged deletions. The data engineer must apply the feed to the production customer table in one atomic statement without rewriting the whole table. What should be used?
A: A MERGE statement that joins staging to production, with WHEN MATCHED clauses for updates and deletes and WHEN NOT MATCHED for inserts
B: A CREATE OR REPLACE TABLE statement that reselects every production row plus the staged changes to rebuild the table each night
C: Three separate load jobs for inserts, updates and deletes, run one after another with the Cloud Storage files exported from staging
D: A scheduled query with INSERT only, appending the whole change feed and relying on analysts to pick the latest row per customer
K: A
G: ## Applying change data in BigQuery SQL
BigQuery supports DML, including **MERGE**, which combines `INSERT`, `UPDATE` and `DELETE` in one statement driven by a join condition between a source and a target table. It is atomic: either all of the changes apply or none do.
- `WHEN MATCHED THEN UPDATE` or `DELETE` handles changed and deleted keys.
- `WHEN NOT MATCHED THEN INSERT` handles new keys.
## Why alternatives are weaker
Rebuilding the table touches all rows; separate steps are not atomic; append-only shifts deduplication to every reader. MERGE can be wrapped in a stored procedure and run by a scheduled query.
W: MERGE: one atomic statement updates, deletes and inserts only the affected rows from the staging table.
X: B=CREATE OR REPLACE rebuild: it rewrites and rescans all rows each night, which is slow and costly when only a few change.
C=Three load jobs: load jobs append files, they do not update or delete existing rows, and separate steps could leave the table half-updated.
D=Insert only: this leaves stale and deleted customers in the table and pushes deduplication into every report.
T: Use MERGE to apply inserts, updates and deletes from a staging table to a target in one atomic statement.

@ GCP-PDE D2 T2.2 applied use-case
S: A logistics company runs Apache Kafka in its own data center. Events must land in BigQuery for reporting, the team wants to avoid writing and operating a custom consumer, and the data center is linked to the VPC network by Cloud Interconnect. Which approach fits?
A: Run the Dataflow Apache Kafka to BigQuery template, with workers in the connected VPC network reaching the brokers over Cloud Interconnect
B: Use Datastream with the on-premises Kafka brokers as a change source, so changes are captured and written to BigQuery without any pipeline job
C: Create a Storage Transfer Service job that polls the topics each hour and writes batches of files to Cloud Storage
D: Write a custom consumer on a Compute Engine VM that polls brokers and inserts rows one at a time with BigQuery jobs
K: A
G: ## Kafka into Google Cloud
Kafka clusters outside Google Cloud can feed Google Cloud through **Dataflow**. Beam's `KafkaIO` reads topics, and Google provides a ready-to-run **Apache Kafka to BigQuery template**, so no pipeline code is needed. The Dataflow workers need network reach to the brokers, so private connectivity (Cloud VPN or Cloud Interconnect, with firewall rules and name resolution) is part of the design.
## What does not apply
- **Datastream** captures changes from databases (such as MySQL, PostgreSQL, Oracle), not from Kafka.
- **Storage Transfer Service** moves objects, not message streams.
- A hand-written consumer works but gives you the operations load you wanted to avoid.
W: Dataflow Kafka to BigQuery template: it is managed, scalable and needs no code, and workers reach the on-premises brokers over the existing private link.
X: B=Datastream: it reads database logs, not Kafka topics, so it cannot take brokers as a source.
C=Storage Transfer Service: it copies objects between stores and cannot consume a streaming topic.
D=Custom VM consumer: it is code you must operate, scale and make fault tolerant, and per-row insert jobs are inefficient.
T: Use the Dataflow Kafka template over private connectivity to move Kafka topics into BigQuery without custom consumers.

@ GCP-PDE D2 T2.2 applied comparison
S: An internal platform team already has Java services that use the Apache Kafka client libraries and consumer groups. They are moving to Google Cloud and want brokers run by Google, but they must not rewrite client code. Which choice fits?
A: Google Cloud Managed Service for Apache Kafka, which runs Kafka clusters and keeps the standard Kafka client protocol
B: Pub/Sub topics and subscriptions, because the services can switch to Pub/Sub client libraries and its model without changes to the client code
C: A Kafka cluster that the team installs on Compute Engine VMs, which Google patches and scales automatically for them
D: Dataproc with Kafka as an optional component, because Dataproc is the managed service that hosts Kafka brokers

G: ## Managed Kafka versus Pub/Sub
- **Google Cloud Managed Service for Apache Kafka** provides Kafka clusters operated by Google while applications keep using open-source Kafka clients, APIs and tools. It suits teams with existing Kafka code, connectors or stream-processing libraries.
- **Pub/Sub** is Google's native messaging service with its own API and client libraries. It is serverless and scales without cluster sizing, but moving to it means changing producers and consumers.
## Rule of thumb
Existing Kafka code that must not change: managed Kafka. New workloads without Kafka dependencies: Pub/Sub is usually simpler.
W: Managed Service for Apache Kafka: brokers are operated by Google and clients keep the Kafka protocol, so no rewrite is needed.

@ GCP-PDE D2 T2.2 applied use-case
S: An analytics team stores 5 million support tickets in a BigQuery table. They want to label each ticket with a sentiment and a short list of topics, keep the results in a new table, and avoid exporting data or building a custom ML model. What is the most direct approach?
A: Create a BigQuery remote model over a Gemini model and call it with AI.GENERATE_TEXT in a SQL query that writes the results to a table
B: Export the table to Cloud Storage, write a Python script that calls a Gemini API per ticket, then load the labelled output back
C: Train a custom text classification model from scratch with BigQuery ML after hand-labelling several hundred thousand tickets
D: Use Dataflow to stream each ticket to a third-party sentiment API and write the labels to a separate Bigtable table

G: ## Generative AI enrichment inside BigQuery
BigQuery can call Gemini models from SQL. You create a **remote model** that references a Gemini endpoint through a BigQuery connection, then call the table-valued function `AI.GENERATE_TEXT` in a query (the scalar `AI.GENERATE` function can also call Gemini directly, without a remote model). Prompt text can be built from table columns, and inference happens in Google Cloud while the results are written to a BigQuery table.
## Why this is the direct path
- No export or movement of the data to another system.
- No labelled training set is needed, because a foundation model follows the prompt.
- It is plain SQL, so analysts can run and schedule it like any other transform.
Cost still depends on token counts, so test on a sample first.
W: Remote model with AI.GENERATE_TEXT: the labels are produced in SQL by a Gemini model, with no export, no training data and results stored in a BigQuery table.
X: B=Export and script: it works but adds an export, custom code and a reload step for a task SQL can do in place.
C=Custom BigQuery ML classifier: it needs a large hand-labelled set and training effort that a prompt-driven foundation model avoids.
D=Third-party API through Dataflow: it sends data outside Google Cloud and puts labels in Bigtable, which is a poor store for analytical joins.
T: Use BigQuery remote models and AI functions to enrich table data with Gemini in SQL, without exporting data or training a model.

@ GCP-PDE D2 T2.2 advanced use-case
S: A claims team keeps 200,000 scanned PDF claim forms in a Cloud Storage bucket. They need fields such as claimant name, claim date and amount extracted into typed BigQuery columns, with the work done from SQL. Which design fits?
A: Reference the files from BigQuery as ObjectRef values and call AI.GENERATE with an output schema, so the model returns typed fields for each document
B: Create a BigLake table over the PDFs in the bucket and run SELECT, because BigQuery parses PDF page layouts into typed columns automatically
C: Load each PDF into a BYTES column with a load job and apply REGEXP_EXTRACT, which interprets the scanned page images
D: Copy the PDFs to Bigtable rows and use a column filter to read name, date and amount fields from the stored objects
K: A
G: ## Structured extraction from unstructured files
BigQuery can treat objects in Cloud Storage as **ObjectRef** values (created with `OBJ.MAKE_REF` from a URI or taken from an object table). Generative AI functions accept them, so a query can send a PDF or image to Gemini together with a prompt.
- `AI.GENERATE` with an **output schema** returns typed fields (strings, numbers, booleans) in a `STRUCT` that can be stored in columns.
- Single-field cases have helpers such as `AI.GENERATE_INT` or `AI.GENERATE_DOUBLE`; `AI.GENERATE_TABLE` is the table-valued variant over a remote model.
## Things that do not extract
A table definition over PDFs exposes only object metadata or raw bytes; regular expressions cannot read scanned images; Bigtable does not parse content.
W: ObjectRef with AI.GENERATE and an output schema: the model reads each document and returns typed values that SQL can insert into columns.
X: B=BigLake table over PDFs: external tables read structured file formats such as Parquet or CSV; they do not interpret PDF layouts into fields.
C=BYTES and REGEXP_EXTRACT: regex works on text, and scanned images contain no text for it to match.
D=Bigtable rows: Bigtable stores and returns cell values; it has no capability to read or understand document content.
T: Combine ObjectRef values with AI.GENERATE and an output schema to turn documents in Cloud Storage into typed BigQuery columns.

S: An order process must call a Cloud Run service, wait for a callback, call two REST APIs in sequence, and then start a BigQuery job. No data is processed in the workflow itself, there are no Airflow-specific dependencies, and the team wants a serverless service with no idle cost. Which service should orchestrate it?
A: Workflows, which chains HTTP calls and connectors, holds state while waiting, and has no charge while idle
B: Cloud Composer, because every sequence of API calls requires an Airflow environment that stays running with its own cluster
C: Dataproc workflow templates, because they are the Google Cloud service for sequencing calls to REST APIs

**Workflows** is a serverless orchestrator for service calls. You write steps in YAML or JSON; steps can call HTTP endpoints, use connectors for Google Cloud APIs, branch, loop, retry, wait for callbacks and keep state for up to a year. It bills per step and costs nothing while idle.

@ GCP-PDE D2 T2.3 applied tradeoff
S: A finance analyst needs one SQL statement, a MERGE into a reporting table, to run every night at 02:00. Nothing depends on it and no other tasks need coordination. Which option is the best fit?
A: A BigQuery scheduled query that runs the statement on a schedule, with no extra infrastructure to maintain
B: A new Cloud Composer environment with one DAG, because Composer is the required way to schedule any BigQuery work
C: A Dataproc cluster kept running with a cron job on the master node that calls the bq command each night
D: A Dataflow streaming job that sleeps all day and wakes at 02:00 to submit the SQL by using the BigQuery API
K: A
G: ## Match the scheduler to the complexity
Scheduling choices form a ladder:
- A single recurring SQL statement: **BigQuery scheduled queries** (built on BigQuery Data Transfer Service), with notifications on failure.
- A few dependent SQL steps in BigQuery: Dataform workflow configurations or a stored procedure called by a scheduled query.
- Calls across services without Airflow needs: Workflows triggered by Cloud Scheduler.
- Many dependent tasks across services, retries, backfills: Cloud Composer.
## Why it matters
Operational effort and idle cost grow with each rung. A one-statement job should sit on the lowest rung that meets requirements.
W: Scheduled query: BigQuery runs the statement on a schedule natively, with nothing to provision, patch or pay for while idle.
X: B=New Composer environment: Composer is not required for scheduling BigQuery, and an environment for one statement adds cost and operations.
C=Always-on Dataproc cluster with cron: it pays for a running cluster and a hand-maintained script to do what a built-in feature does.
D=Idle streaming job: Dataflow is a data processing engine, and a job that sleeps most of the day wastes resources and is not designed for scheduling.
T: Pick the simplest scheduler that meets the need: scheduled queries for one statement, Workflows or Composer only when coordination is required.

@ GCP-PDE D2 T2.3 advanced use-case
S: A DAG in Cloud Composer waits for a partner file to arrive in Cloud Storage, which may take from minutes to many hours. During busy mornings, many waiting tasks have used up all the worker slots and other DAGs are delayed. What is the best fix?
A: Use a deferrable version of the sensor, so the waiting is handed to the triggerer and the task frees its worker slot until the file appears
B: Set the sensor's timeout to a few seconds so that the task fails fast and the scheduler never has long-running tasks to hold
C: Replace the sensor with a loop of time.sleep calls in a PythonOperator, which uses fewer worker resources than the built-in sensors
D: Add a Dataproc cluster to run the waiting tasks in place of the environment's workers, so the slots are no longer in short supply
K: A
G: ## Sensors and worker slots in Airflow
A **sensor** is an Airflow task that waits for a condition, such as a file in Cloud Storage. In the default `poke` mode it holds a worker slot for the entire wait, so many sensors can starve other tasks.
- **Deferrable operators** (and sensors) hand the wait to the Airflow **triggerer**, an asynchronous component that watches many conditions cheaply. The task releases its worker slot and resumes when the trigger fires.
- `reschedule` mode also frees the slot between checks, but a deferrable sensor is the modern approach.
In Cloud Composer the environment must run at least one triggerer before deferrable operators work.
## Why other fixes fail
Short timeouts break the business need; `sleep` still occupies a slot; Dataproc does not run Airflow task slots.
W: Deferrable sensor: the triggerer handles the wait asynchronously, so no worker slot is held while the file is missing.
X: B=Tiny timeout: the file may take hours, so the task would fail before it arrives and the DAG would not meet its purpose.
C=time.sleep loop: the PythonOperator still occupies a worker slot for the full sleep, so it is the same problem with worse behavior.
D=Dataproc for waiting: Airflow task slots belong to the Composer environment's workers; a Dataproc cluster does not take them over.
T: In Cloud Composer, use deferrable operators or sensors so long waits do not consume worker slots.

@ GCP-PDE D2 T2.3 applied use-case
S: A team develops Cloud Composer DAGs in a Git repository. They want changes to be validated automatically before production and want the production environment to pick up only reviewed code. Which TWO practices fit? (Select TWO)
A: Run unit and DAG-integrity tests, such as import checks, in a build step like Cloud Build whenever a pull request is opened
B: Let developers edit DAG files directly in the production environment's bucket, because Composer rejects any file that has errors
C: Promote reviewed code by copying the DAG files to the dags folder of the production environment's Cloud Storage bucket after tests pass
D: Test only in production using a copy of the DAG that has a different name, because test environments cannot run the same code
E: Install every DAG as a Python package on the environment's Pods one by one with SSH sessions to each node
K: A,C
G: ## CI/CD for Composer DAGs
A Composer environment reads DAG files from the **dags/ folder of a Cloud Storage bucket** it owns, and picks up changes by sync. A sound pipeline therefore is:
1. Developers work in Git with pull requests.
2. A build service (**Cloud Build**, or GitHub Actions and similar) runs checks: Python import tests ("DAG integrity" to catch syntax and cycle errors), unit tests of custom operators, and optionally a run in a separate test environment.
3. After merge, a deploy step syncs the files into the dags/ folder of the production bucket.
## Why direct edits fail
