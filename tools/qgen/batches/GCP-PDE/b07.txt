@ GCP-PDE D4 T4.2 applied comparison
S: A compliance team stores 150,000 contract-clause embeddings in a BigQuery table and runs a few similarity searches per day. Reviewers must always see the true closest clauses, because a missed clause is a legal risk, and the latency of each search is not important. How should the data engineer run the searches?
A: Create a vector index and rely on approximate nearest neighbor results, since index-backed search always returns the same clauses as an exhaustive scan
B: Run VECTOR_SEARCH without a vector index, or force brute force, so every stored vector is compared and results are exact
C: Replace the stored embeddings with lower-dimension vectors so approximate search becomes exact on the smaller table
D: Export the embeddings to a spreadsheet and ask reviewers to sort the clauses by similarity score manually
K: B
G: ## Exact versus approximate vector search
`VECTOR_SEARCH` in BigQuery compares a query embedding with the vectors in a table and returns the nearest ones by a distance measure.
- **Without a vector index** the function uses brute force: it measures the distance to every record, so the result is exact.
- **With a vector index** (`CREATE VECTOR INDEX`, using inverted file indexing and the ScaNN algorithm) the function uses approximate nearest neighbor search. It is faster on large tables, with the trade-off of lower recall, so some true neighbors can be missed.
- Even when an index exists, a query can ask for brute force to get exact results.
## Choosing
Pick approximate search when scale and latency matter and a small recall loss is acceptable (recommendations, semantic search). Pick exact search when the table is modest, searches are infrequent and a miss is costly, as here.
W: B=Brute force: with no index, or with brute force forced, every vector is compared, so the closest clauses are guaranteed. At 150,000 vectors and a few queries per day the extra compute is acceptable.
X: A=Index with approximate search: an index trades recall for speed, so it can miss true neighbors; the claim that results always match an exhaustive scan is wrong.
C=Lower-dimension vectors: shrinking dimensions changes the embedding and loses information; it does not turn approximate search into exact search.
D=Spreadsheet sorting: it moves a similarity workload out of the warehouse, does not scale and adds governance risk for contract data.
T: Vector search without an index (or forced brute force) is exact; a vector index gives approximate results with lower latency and cost at scale.

@ GCP-PDE D4 T4.2 applied definition
S: A retailer generated product embeddings in BigQuery with a text embedding model that Google has announced will be retired. The team moves the pipeline to the replacement model. Which TWO actions keep similarity search results meaningful? (Select TWO)
A: Regenerate the embeddings already stored in the table with the replacement model, then rebuild any vector index on that column
B: Keep the stored vectors and embed only new rows with the replacement model, because the vector length is unchanged
C: Generate each search query's embedding with the same replacement model that produced the stored table embeddings
D: Apply L2 normalization to the old vectors so they share an embedding space with the replacement model's vectors
E: Keep embedding search queries with the retiring model until its retirement date, then switch only the table
K: A,C
G: ## Embeddings from different models do not mix
An embedding is a position in a space learned by one specific model. Vectors from different models, or different versions of one model, live in separate embedding spaces and are generally mathematically incompatible, even when they have the same number of dimensions. Comparing them gives inaccurate search and similarity results.
## Migration steps for a deprecated embedding model
- Regenerate the embeddings in existing tables with the replacement model so all stored vectors share one space.
- Update any query or pipeline that generates embeddings at search time to use the same replacement model.
- After regeneration, recreate or rebuild the vector index on the embedding column, because the index was built on the old vectors.
W: A=Regenerate and rebuild: re-embedding every stored row puts the whole table in one embedding space, and the index must be rebuilt over the new vectors.
C=Same model at query time: a query vector is only comparable with stored vectors from the same model, so search-time embedding must use the replacement model.
X: B=Mixed table: new and old rows would sit in different spaces; the equal vector length does not make them comparable, so ranking becomes unreliable.
D=Normalization: scaling a vector changes its length, not the space it was learned in, so it cannot align two models.
E=Old model for queries: queries embedded by the retiring model would be compared with vectors from the replacement model, and they stop working after retirement.
T: Keep every stored embedding and every query embedding on one model; after a model change, regenerate the table and rebuild the vector index.

@ GCP-PDE D4 T4.2 applied definition
S: An insurer wants an assistant that answers questions from 20,000 long policy PDFs. A data engineer is preparing the corpus in BigQuery for retrieval-augmented generation (RAG). Which preparation step is most important before generating embeddings?
A: Concatenate all PDFs into one very long text row per product line so each embedding carries the whole context
B: Split extracted text into passage-sized chunks, one row per chunk with a document identifier and metadata, then embed each chunk
C: Embed only the title of each PDF, because titles are short and always describe the full document content accurately, then pass whole PDFs to the model
D: Convert the PDF text into one-hot encoded word columns, which can then be searched with vector search directly
K: B
G: ## Retrieval-augmented generation in BigQuery
RAG grounds a generative model in your own data. The usual flow in BigQuery is: parse documents, generate embeddings, optionally create a vector index, run `VECTOR_SEARCH` with the question's embedding, and pass the top matches to a Gemini model as context for the answer.
## Why chunking matters
- An embedding is a single vector for the text it was given. A whole document averages many topics, so a question about one clause matches poorly.
- Passage-sized chunks give precise matches and keep the prompt small enough to pass to the model.
- Each chunk row should keep a document identifier and metadata (product, date, access group), so answers can cite sources and filters can restrict the search.
W: B=Chunk rows with metadata: each passage gets its own embedding, so retrieval returns the relevant clause, and the identifier and metadata allow citation and filtering.
X: A=One huge row per product line: a single vector for a large amount of text blurs the meaning, retrieval loses precision, and the text may exceed what an embedding model or prompt can accept.
C=Titles only: titles do not contain the answers, so the assistant would retrieve documents but never the content that answers the question.
D=One-hot word columns: sparse word-presence columns are not embeddings, and vector search needs dense embedding vectors that capture semantics.
T: For RAG, split documents into chunk rows with identifiers and metadata, embed each chunk, then retrieve the nearest chunks with vector search.

@ GCP-PDE D4 T4.2 applied comparison
S: A media company has precomputed embeddings for 8 million catalog items. Every night a job must find the 20 most similar items for each of 400,000 newly added items, and finish within the batch window. Which BigQuery capability fits best?
A: AI.SIMILARITY called in a cross join between new and catalog items, computing a cosine similarity for every pair
B: VECTOR_SEARCH over the embeddings, with a vector index on the catalog table to speed up the nearest neighbor lookups
C: A LIKE predicate on item titles, ordered by the number of shared words, to approximate semantic similarity
D: A scheduled query that exports all embeddings to Cloud Storage so a spreadsheet macro can rank neighbors
K: B
G: ## Choosing among the similarity functions
BigQuery offers several ways to compare embeddings:
- `AI.SIMILARITY` computes the cosine similarity between two inputs, and it works well for a small number of comparisons when you have not precomputed embeddings.
- `VECTOR_SEARCH` should be used when performance is critical and the number of embeddings is large. With a vector index it uses approximate nearest neighbor search.
## Applying it
400,000 queries against 8 million precomputed vectors is a large nearest neighbor workload. Pairwise comparison of every combination is far too much work, while an indexed `VECTOR_SEARCH` returns only the top neighbors per query.
W: B=VECTOR_SEARCH with vector index: it is built for many lookups over large embedding tables, and the approximate index avoids scanning every vector for each new item.
X: A=AI.SIMILARITY cross join: it suits few comparisons, and a cross join of this size computes trillions of pairs, which is slow and costly.
C=LIKE on titles: lexical matching misses items that are similar in meaning but use different words, which is the point of embeddings.
D=Spreadsheet macro: this cannot process millions of vectors in a batch window and leaves the managed analytics platform.
T: Use AI.SIMILARITY for a few ad hoc comparisons and VECTOR_SEARCH with a vector index for large-scale nearest neighbor lookups.

@ GCP-PDE D4 T4.2 advanced tradeoff
S: A team plans to add semantic search over 500 million embeddings in BigQuery and wants to forecast cost. Which TWO statements about the cost of vector search are accurate? (Select TWO)
A: With on-demand pricing, a vector search is charged for bytes scanned in the base table, the index and the search query
B: A vector index adds no storage cost, because index data is kept in a hidden system area
C: Active vector indexes incur storage costs, and the index size is visible in INFORMATION_SCHEMA.VECTOR_INDEXES
D: Vector search queries are accelerated by BI Engine, which removes the slot or scan charge for repeated searches
E: Index building is billed per row indexed at a fixed rate, whatever the total size of the indexed data
K: A,C
G: ## Cost model for embeddings and vector search
Vector search is billed as ordinary BigQuery compute plus storage:
- `VECTOR_SEARCH` and `AI.SEARCH` use on-demand pricing (bytes scanned in the base table, the index and the query) or editions pricing (slots needed in your reservation).
- `CREATE VECTOR INDEX` has no processing charge while the indexed table data stays below a per-organization limit. Beyond that limit you must supply your own reservation for index management jobs.
- Embedding columns and active vector indexes are billed as storage. The index size and its coverage are visible in `INFORMATION_SCHEMA.VECTOR_INDEXES`.
- Queries with `VECTOR_SEARCH` or `AI.SEARCH` are not accelerated by BI Engine.
W: A=On-demand bytes: scan charges cover the base table, the index and the query, so large tables or poorly pruned searches cost more.
C=Index storage: an active index is billed as storage, and the view shows its size and coverage, so it belongs in the forecast.
X: B=Free index storage: indexes are charged as active storage, and there is no hidden free area.
D=BI Engine acceleration: queries that contain vector search functions are not accelerated by BI Engine.
E=Per-row index billing: index building has no processing charge below the organization limit, not a per-row rate.
T: Forecast vector search as query cost (bytes or slots) plus storage for embeddings and active indexes; index builds are free below a limit and BI Engine does not help.

@ GCP-PDE D4 T4.2 advanced use-case
S: A bank holds 60 million customer records from three systems, with names and addresses typed differently in each. Exact joins miss many duplicates. The data engineer wants to prepare a deduplication step in BigQuery with the least custom infrastructure. What is the best approach?
A: Embed a normalized text form of each record, use vector search for nearest-neighbor candidates, and review matches above a threshold
B: Hash every record with a cryptographic hash and join on equal hashes, since identical meaning always gives identical hashes for names and addresses typed in several formats
C: Export records to a self-managed server that runs a fuzzy matching service, then load the match results back into BigQuery
D: Delete every record that shares a postal code with another record, since records that live close together are duplicates
K: A
G: ## Embeddings for entity resolution
Entity resolution finds records that refer to the same real-world entity. Because embeddings place semantically similar text close together, they can match "12 Main St." with "12 Main Street" where an exact join fails. BigQuery documents entity resolution and deduplication (for example, deduplicating personally identifiable information records) as a vector search use case.
## Pattern
- Build a normalized text string per record and generate embeddings with `AI.GENERATE_EMBEDDING`.
- Run `VECTOR_SEARCH` to retrieve each record's nearest neighbors as candidate pairs.
- Apply a distance threshold and business rules, and send borderline pairs to review. Keep the records governed like any other PII.
W: A=Embeddings plus vector search: it finds fuzzy matches inside the warehouse, needs no extra servers, and the threshold and review step control false merges.
X: B=Cryptographic hash: any one-character difference gives a totally different hash, so it is no better than the exact join that already misses duplicates.
C=Self-managed matcher: it adds infrastructure, data movement and governance burden that the in-warehouse approach avoids.
D=Delete by postal code: many different customers share a postal code, so this destroys valid records.
T: Embeddings with VECTOR_SEARCH give fuzzy candidate matching inside BigQuery; combine with thresholds and review to deduplicate records.

@ GCP-PDE D4 T4.2 advanced troubleshooting
S: A vector search runs against a 4 TB table of embeddings that holds ten years of support tickets, and analysts always want only the last 30 days. Queries scan far more data than expected, even with the vector index in place. The table is partitioned by ticket date. Which change reduces the scanned data most directly?
A: Pre-filter on the partitioned date column in the VECTOR_SEARCH call so only recent partitions are read
B: Drop the vector index so that the function compares only the vectors returned by a later WHERE clause
C: Cluster the table on an unrelated column and filter on it in a subquery without storing that column in the vector index
D: Switch the embedding column to a string type so that BigQuery can prune data with its text search index
K: A
G: ## Pre-filtering in vector search
A pre-filter restricts which rows of the base table are candidates before the nearest neighbor search.
- Pre-filtering data pruning is only optimized when the filter is on **partitioned columns** or **stored columns** of the vector index.
- A pre-filter on a non-stored clustered column causes a full table scan.
## Applying it
The table is partitioned by ticket date and the question needs only 30 days, so a date pre-filter lets BigQuery read only those partitions. Under on-demand pricing this also reduces the bytes billed.
W: A=Pre-filter on the partition column: only matching partitions are read, so the search scans a small part of the 4 TB table.
X: B=Dropping the index: without an index the search is brute force and a later WHERE clause does not shrink the search, so cost and latency rise.
C=Non-stored clustering column: a pre-filter on a clustered column that is not stored in the index results in a full table scan.
D=String embeddings: embeddings must be numeric vectors for distance functions, and converting them to text would break the search.
T: Pre-filter vector search on a partitioned (or stored) column to prune data; filters on non-stored clustered columns do not prune.

BigQuery supports both authorized views (for logical views) and **authorized materialized views**. A materialized view is a precomputed view that periodically caches the results of a query, which improves performance and efficiency when a view relies on a large or expensive query.

- BigQuery refreshes materialized views automatically as base data changes, so analysts get current results without each query recomputing the aggregation.
## Applying it
Both requirements are met: restricted access to the raw events and reduced repeated computation.

X: B=Logical view plus Data Viewer on raw data: analysts would see the raw events, and a logical view recomputes the aggregation on every query.
C=Per-minute scheduled append: it creates duplicated aggregate rows and needless runs, and opening a table to all authenticated users exposes it widely.
D=PDF export: it is static, loses queryability and moves data out of governed storage.

@ GCP-PDE D5 T5.1 advanced tradeoff
S: A Dataproc cluster for a recurring Spark batch ETL must be cheaper. Input and output are in Cloud Storage and a few failed tasks are tolerable if they are retried. Which TWO actions reduce cost while keeping jobs reliable? (Select TWO)

B: Put all workers on secondary Spot VMs, including the nodes that host HDFS data, to reach the lowest hourly rate

G: ## Secondary workers for lower cost
Dataproc has primary workers and secondary workers. Secondary workers can be Spot VMs, standard preemptible VMs or non-preemptible VMs, and they scale compute cheaply because they do not store HDFS data.

@ GCP-PDE D5 T5.1 advanced troubleshooting

@ GCP-PDE D5 T5.2 applied definition
S: A data engineer wrote a Cloud Composer DAG whose single task, a PythonOperator, extracts data from an API, cleans it, loads it into BigQuery and sends a notification. When the load step fails, the whole task reruns and the data is duplicated. How should the DAG be redesigned?
A: Split the work into separate idempotent tasks, so a failed step can be retried alone
B: Keep one task but add a long sleep before the notification, so the load has time to finish properly

G: ## DAG design in Cloud Composer
Cloud Composer runs Apache Airflow. A DAG is a graph of tasks with dependencies.
- Each task should be an **idempotent unit of work**: running it twice produces the same end state, for example by writing to a partition with overwrite instead of appending.
- Avoid encapsulating a multi-step workflow in a single task, such as a complex program in one PythonOperator.
- Separate tasks let Airflow retry, monitor and alert on each step, and show where a run stopped.
## Applying it
Extract, clean, load and notify become four tasks, and the load is made idempotent so a retry cannot duplicate rows.
W: A=Small idempotent tasks: failures are isolated to one step, retries are safe, and the DAG shows which step failed.

C=Maximum retries: rerunning a non-idempotent combined task repeats side effects, so duplicates multiply.
D=Top-level code in the DAG file: code outside tasks runs at every parse, slows the scheduler and is not task execution.
T: Design Composer DAG tasks as small idempotent steps so retries are safe and failures are easy to locate.
