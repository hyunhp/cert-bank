@ GCP-PDE D1 T1.2 applied use-case
S: The data platform team runs about two hundred Airflow DAGs in Cloud Composer. Nightly DAG failures are only discovered when business users complain in the morning. The team wants to be told as failures happen and to see the environment's health in one place. What should they do?
A: Build alerting policies in Cloud Monitoring on Composer metrics and logs that notify the on-call engineers
B: Add a sleep task at the end of each DAG so that an operator notices when the run ends and checks it by hand
C: Export the task logs to a spreadsheet each morning and review failed entries during the daily stand-up
D: Turn off task retries so that each failure appears on the first attempt and the DAG halts the pipeline
K: A
G: ## Observing the orchestrator
Cloud Composer (Managed Airflow in current product pages) integrates with **Cloud Monitoring** and **Cloud Logging**. Monitoring collects metrics from the environment (scheduler, workers, database and DAG-run statistics) for dashboards and charts, and Logging captures the scheduler and worker logs. **Alerting policies** on these metrics or on log-based metrics notify people through email, chat or paging channels.
## Why this is an operations design choice
Alerts turn an invisible overnight failure into an immediate notification, and a dashboard gives one health view across DAGs. Viewing logs requires the monitoring and logging viewer roles.
W: Cloud Monitoring metrics, logs and alerting policies: failures page the on-call team as they happen and dashboards show the health of the DAGs in one place.
X: B=Sleep task: it adds delay and does not notify anyone; an operator would still check manually.
C=Daily spreadsheet: failures are found hours later, which is the problem that triggered the request.
D=No retries: transient failures would then become permanent failures and still would not alert anyone.
T: Monitor Composer with Cloud Monitoring dashboards and alerting policies instead of waiting for users to find failures.
V: Cloud Composer, Cloud Monitoring, Cloud Logging

@ GCP-PDE D2 T2.1 applied use-case
S: A Cloud Data Fusion pipeline must read from an on-premises database that is reachable only through a VPN into a VPC network. The security team forbids the instance from using public endpoints. How should the instance be planned?
A: Create a private instance and connect its tenant project's VPC network to the customer VPC through peering
B: Create a public instance and publish the database under a public DNS name that the pipelines resolve
C: Create a public instance and open an SSH tunnel on each Dataproc worker that the pipelines start at runtime
D: Replace the database connection with a Cloud Storage bucket that a DBA fills with an export each night
K: A
G: ## Cloud Data Fusion networking
Cloud Data Fusion runs a **tenant project** that holds the resources it manages for you, and runs pipelines on Dataproc (Managed Service for Apache Spark) clusters in your customer project. A **private instance** is reached through VPC peering between its own tenant VPC and your VPC, keeping traffic off the public internet. From your VPC, sources reachable over Cloud VPN or Interconnect can then be used by pipelines.
## Planning point
Choose private versus public at creation time, since the access model and the network design depend on it.
W: Private instance with VPC peering: it keeps design and execution traffic on private networks and lets pipelines use sources reachable through the VPN.
X: B=Public instance with public DNS: this exposes the database path publicly, which the security team forbids.
C=SSH tunnels on each worker: this keeps a public instance, is fragile and hard to audit, and contradicts the managed model.
D=Nightly bucket export: it removes the live pipeline and adds a manual dependency rather than solving connectivity.
T: Use a private Cloud Data Fusion instance with VPC peering for sources behind a private network.
