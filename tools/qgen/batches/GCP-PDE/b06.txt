@ GCP-PDE D3 T3.3 applied troubleshooting
S: A company has Cloud Storage buckets, BigQuery datasets and Cloud SQL instances spread over 60 projects. Analysts complain that they cannot find out which tables hold customer orders, and a few say they can see a table in search results that a colleague cannot. What explains the second complaint, and what is the right way to improve discovery?
A: Dataplex Catalog search results are scoped by each user's read permission on the underlying asset, so improve discovery by enriching metadata and keeping permissions correct
B: Dataplex Catalog search returns every indexed asset in the organization to all users, so the colleague is missing a catalog role and needs the administrator role granted
C: Dataplex Catalog indexes only the assets of the project where search runs, so the colleague must run the same search from the project that owns the table
D: Dataplex Catalog search is limited to assets a user has starred earlier, so the team should ask each analyst to star the tables they want to see
K: A
G: ## Discovery in the catalog
Dataplex Catalog (documented today as Knowledge Catalog, formerly Dataplex Universal Catalog; API and IAM names are unchanged) automatically indexes technical metadata for Google Cloud sources such as BigQuery, Cloud Storage, Cloud SQL and Pub/Sub, so a single search box can cover many projects.
## Search respects source permissions
- Search scope defaults to the whole organization, but can be narrowed to the current project or starred assets.
- Search results are scoped to the user's access: to find a BigQuery table the user needs read access to its metadata (for example BigQuery Metadata Viewer). Two users can therefore see different results for the same query.
## Making assets findable
Beyond automatic technical metadata, stewards add business context (descriptions, aspects, glossary terms) so that a query such as "customer orders" matches the right tables.
W: Permission-scoped search plus richer metadata: the catalog hides entries the user cannot read in the source system, which explains the difference, and enriching entries with business context fixes the findability problem.
X: B=Everyone sees everything: search is not a global listing; a user without read permission on the underlying asset does not see it, and no catalog administrator role changes that.
C=Only the project that runs the search: the default scope is the organization, so assets in all 60 projects can be found from one place.
D=Only starred assets: starring is an optional scope filter, not a requirement for results to appear.
T: Catalog search spans projects but only returns assets the caller may read; add business metadata to make assets findable.

@ GCP-PDE D3 T3.4 advanced tradeoff
S: A retailer wants a data mesh. Sales, logistics and finance each own their BigQuery data and want to publish curated datasets that other teams can find, evaluate and request access to without waiting on the central platform team. The security office still wants one place to see what is published. Which design fits best?
A: Domain teams publish Dataplex data products with owners, documentation and access groups, and the central team governs the shared catalog
B: Move all domain tables into one central BigQuery project owned by the platform team, who answer every access request through tickets
C: Let each domain publish datasets in its own project with no common catalog, and ask consumers to find owners via a wiki
D: Replace domain ownership with one shared data lake bucket where every team writes files and the platform team curates them afterwards
K: A
G: ## Data mesh and federated governance
A data mesh treats data as a product: the domain that knows the data owns it, publishes it in a consumable form, and a central function sets shared standards and visibility. This is federated governance: policies are central, ownership and curation are distributed.
## Data products in Dataplex
Data products (documented in Knowledge Catalog, formerly Dataplex Universal Catalog) package related catalog assets, such as BigQuery tables and views, into one curated unit. A data product has:
- an owner or producer responsible for quality, access and documentation;
- context such as description, documentation and aspects;
- a contract stating expectations such as refresh cadence;
- access groups that map friendly roles (Reader, Analyst) to Google Groups, giving consumers a self-service way to request access.
W: Domain-owned data products in the shared catalog: producers keep ownership and speed, consumers discover and request access themselves, and the catalog gives the security office one place to see what is published.
X: B=Central project and tickets: this centralizes ownership again, recreating the bottleneck the domains want to remove and giving the central team knowledge of data it does not own.
C=No common catalog: without shared discovery and metadata there is no single view for security and consumers depend on word of mouth.
D=Single shared bucket: it removes domain ownership and curation, and a flat set of files lacks the per-product context, contracts and access model.
T: A data mesh puts ownership in domains and publishes data products into a shared catalog that central governance oversees.

@ GCP-PDE D3 T3.4 advanced use-case
S: A bank has about 400 tables with personal data across eight business domains. The central governance team wants a consistent classification (for example High, Medium and Low sensitivity) that can be applied to columns, can be re-tiered later without relabeling each column, and can drive access control. Which TWO design choices follow Google's guidance for BigQuery policy tags? (Select TWO)
A: Build a hierarchical taxonomy of a few data classes, with leaf policy tags such as credit card or government ID under tiered parents
B: Create a separate taxonomy per table so that each table owner can use tag names of their own choosing
C: Grant the Fine-Grained Reader role on a parent tier so that principals receive access to the whole group of tags beneath it
D: Create one policy tag per column name so that each column has a unique tag and can be restricted individually
E: Assign policy tags through broad project-level roles and skip the taxonomy so that no hierarchy needs to be maintained
K: A,C
G: ## Policy tags in a taxonomy
Policy tags classify BigQuery columns; access control on a tag then applies to every column carrying it. Google's best-practice guide says to describe a small number of data classes (PII, financial data, order history) and apply one tag to many columns, so a few tags manage many columns.
## Why a hierarchy
- Group tags in a tree, for example High, Medium and Low parents with leaf tags such as credit card, government ID and address.
- Access can be granted on a parent tier once to cover all leaves beneath it.
- A leaf can be moved to another tier (address from Low to Medium) to tighten its access without reclassifying every column that uses it.
W: A=Hierarchical taxonomy: a small tree of data classes lets many columns share a few tags, and re-tiering a leaf changes access for all its columns at once.
C=Fine-Grained Reader on a tier: granting the role on a parent covers all tags under it, which keeps access management small and consistent.
X: B=Taxonomy per table: it fragments the classification and makes consistent organization-wide governance impossible.
D=Tag per column name: this multiplies tags, defeating the purpose of abstracting to data classes, and makes re-tiering costly.
E=Project-level roles with no taxonomy: policy tags exist precisely to give column-level control; project roles would not provide it.
T: Use a small hierarchical taxonomy of data classes, and manage access at the tier level.

@ GCP-PDE D4 T4.1 applied use-case
S: A Looker dashboard queries a 2 TB fact table joined with a few small dimension tables, filtering on the last 30 days. Queries take several seconds, and 200 users refresh at the start of the working day. The team wants sub-second response without changing the BI tool. What should they do?
A: Reserve BI Engine capacity in the table's region and set the fact and dimension tables as preferred tables
B: Export the fact table to Cloud Storage as CSV files and point the dashboard at those files
C: Move the dimension tables to Cloud SQL so that the joins execute in a relational database
D: Convert the fact table to an external table so that every dashboard query runs against Cloud Storage objects
K: A
G: ## BI Engine
BI Engine is an in-memory analysis layer that accelerates BigQuery SQL for dashboards. It integrates through the BigQuery API (so BI tools work unchanged), uses a vectorized runtime, caches only the queried parts of columns and partitions, and works with authorized views, column-level security and data masking.
## Using it well
- Reserve capacity (in GiB, per project and region) with a supported edition.
- Designate preferred tables so that important dashboards are accelerated and other traffic does not use the memory.
- It works best for a large fact table joined to small dimension tables, and for pre-joined or pre-aggregated data.
W: BI Engine with preferred tables: it caches the hot columns in memory with no tool changes, and the fact-plus-small-dimensions pattern is the one it handles best.
X: B=CSV in Cloud Storage: the dashboard would lose BigQuery's engine and BI Engine acceleration, and file scans are slower.
C=Dimensions in Cloud SQL: this splits the join across systems and adds data movement, not speed.
D=External table: BI Engine does not accelerate external tables, and reads from object storage are slower than native storage.
T: For sub-second BigQuery dashboards, reserve BI Engine capacity and mark the hot tables as preferred.

@ GCP-PDE D4 T4.1 applied troubleshooting
S: A team reserved BI Engine capacity, but dashboards that query a BigLake table over Parquet files in Cloud Storage see no acceleration. They need responsive dashboards on this data and can tolerate hourly freshness. What should they do?

BI Engine does not accelerate external tables, including BigLake tables, nor some features: JavaScript UDFs, JSON or RANGE types, row-level security, search and vector search, recursive queries and BigQuery ML queries, and results larger than 1 GiB. Unsupported stages fall back to normal slots.

@ GCP-PDE D4 T4.1 advanced tradeoff
S: A large events table receives inserts all day, and a dashboard repeatedly runs the same aggregation grouped by country and day. Users must always see current numbers, and the team wants the lowest compute cost for repeated queries. Which design fits?
A: An incremental materialized view of the aggregation, which combines its cached results with new base table data at query time
B: A scheduled query that rebuilds a summary table every six hours and a dashboard that reads that table
C: A standard logical view over the events table, because views store the computed results of the aggregation
D: A BI Engine reservation alone, because it recomputes aggregates over all rows less expensively than caching
K: A
G: ## Materialized views
A materialized view precomputes and stores query results, and BigQuery keeps it up to date. Incremental materialized views support a limited set of SQL, can reduce the cost of frequently used queries, and return fresh results even when base tables changed since the last refresh, because BigQuery combines the cached data with new rows.
## Compared with scheduled queries
A scheduled query reruns in full each time, pays the full compute cost and is stale between runs; it suits workloads with a high tolerance for staleness. Google's guideline: use materialized views whenever you are not running arbitrarily complex calculations.
W: Incremental materialized view: repeated aggregation cost falls because stored results are reused, and results stay current as new rows arrive.
X: B=Scheduled rebuild: each rebuild pays the whole aggregation and results can be up to six hours old, which conflicts with current numbers.
C=Logical view: it saves the query text only, so every read recomputes from the base table.
D=BI Engine alone: it speeds up reads from memory but is not a stored aggregate, and it does not remove the need for the repeated work.
T: For repeated aggregations needing fresh data, prefer incremental materialized views to periodic rebuilds.

@ GCP-PDE D4 T4.1 advanced troubleshooting
S: A materialized view over a sales table was fast for weeks. After the source team started running UPDATE and DELETE statements that rewrite historical rows in the base table, queries on the view became slow and expensive until the next refresh. Why?
A: Updates or deletions to base table data stop incremental updates, so BigQuery cannot use the view's cached data until the view is refreshed
B: Materialized views are removed automatically when any base table row is changed, so queries read the base table directly until it is recreated
C: BI Engine invalidates the view each time historical rows change, and the reservation must be recreated before the view is used again
D: Smart tuning permanently disables any materialized view when its base table receives DML statements
K: A
G: ## How freshness works
Queries on a materialized view are always consistent with the base table. For appended rows BigQuery adds the new data to the cached result (an incremental update). If the base table had updates or deletions since the last refresh, incremental updates are not possible; BigQuery reverts to the original query, so the cached data is not used until the view is automatically or manually refreshed.
## Design implications
- Append-mostly tables suit materialized views well.
- For tables with frequent rewrites, partitioned views limit the damage because the behavior applies to each partition independently.
- If staleness is acceptable, the `max_staleness` option allows cached data to be used for a stated interval.
W: Incremental updates need an unchanged base: UPDATE and DELETE statements mean the cached result cannot be combined with new data, so queries fall back to the full computation until refresh.
X: B=Automatic removal: the view is not deleted; it remains and refreshes, and results stay correct.
C=BI Engine invalidation: BI Engine is a separate memory cache and has no role in how a materialized view is maintained.
D=Smart tuning disables the view: smart tuning is query rewriting to use a view and does not disable views.
T: Updates and deletions on a base table prevent incremental use of a materialized view until it refreshes; favor append-only sources.

@ GCP-PDE D4 T4.1 applied use-case
S: A product has several dashboards that all group the same 5 billion row table by region and month, and developers write queries against the base table in many places. The team wants those queries to get faster without changing any query text. Which feature does this?
A: A materialized view, because smart tuning can rewrite base table queries to use its results
B: A BI Engine preferred-table list, because it rewrites queries to read precomputed aggregates
C: A scheduled query that writes a summary table, because BigQuery redirects matching base-table queries to it
D: A clustered base table, because clustering stores aggregated results for each cluster key
K: A
G: ## Smart tuning
If any part of a query against a base table can be resolved by an incremental materialized view, BigQuery automatically reroutes the query to the view for better performance and efficiency. Developers need no changes in queries (the query needs access to the view and base table, so permissions matter). Non-incremental views do not support smart tuning. Materialized views thus work like a pseudo-index.
## Other options do not rewrite
Summary tables you manage yourself must be referenced explicitly; BI Engine accelerates scanning, and clustering sorts storage.
W: Materialized view with smart tuning: matching queries on the base table are rerouted to the stored result with no text change.
X: B=BI Engine preferred tables: they decide which tables are cached in memory and do not rewrite queries to use aggregates.
C=Scheduled summary table: BigQuery never redirects queries to such tables, so every query must be rewritten to use one.
D=Clustering: it organizes data to prune reads and does not store aggregates.
T: Smart tuning lets incremental materialized views speed up base table queries without code changes.

@ GCP-PDE D4 T4.1 advanced troubleshooting
S: In the execution details of a slow BigQuery query, a join stage outputs far more rows than it receives as input, and the later stages spend most of their time on those rows. What is the most effective change?
A: Filter or pre-aggregate the inputs before the join, and check that the join keys match the intended relationship
B: Raise the LIMIT value of the query so that each slot processes more rows at a time and the stage finishes sooner
C: Convert the query to SELECT * so that BigQuery can choose the best columns to scan itself
D: Add more BI Engine memory, because join row explosion is caused by a shortage of cache
K: A
G: ## Reading the query plan
The query plan shows stages with input and output rows and a timeline of slot use. A JOIN stage that generates far more output rows than input rows suggests a many-to-many or non-unique join key, and it is a signal to filter earlier.
## Common remedies
- Reduce data before the join by aggregating or filtering (Google's compute guidance recommends reducing data before JOIN).
- Verify that the join keys are unique where one-to-many was intended.
- Project only the needed columns; LIMIT does not reduce bytes read for SELECT *.
W: Filter or aggregate before the join and check keys: reducing the rows entering the join and fixing the key relationship removes the explosion.
X: B=Raising LIMIT: LIMIT applies after the work is done and does not make the join cheaper.
C=SELECT *: reading all columns increases I/O and materialization.
D=More BI Engine memory: row explosion comes from the query logic, not cache size.
T: A join that outputs many more rows than it reads means filter or aggregate earlier and verify the join keys.

@ GCP-PDE D4 T4.1 applied troubleshooting
S: An hourly BigQuery report normally takes 40 seconds under on-demand pricing. Today it takes several minutes. The query plan timeline shows the number of active units staying low while the amount of queued units of work stays high, and nothing in the query text changed. What does this point to, and what should be done?
A: Slot contention with other queries, so reduce concurrent load or move the workload to reserved capacity
B: A partitioning mistake in the table, so the table should be recreated with clustering on all columns
C: A BI Engine cache miss, so the reservation size should be increased until the miss rate is zero
D: A data skew in the first stage only, so the query should add ORDER BY to even out the work
K: A
G: ## Slow in isolation or because of contention?
Query execution details include a timeline. If active units stay limited while queued units stay high, the query is waiting for slots rather than being inefficient, and contention is the cause. Remedies are to lower concurrency or provide more dedicated slots: under on-demand pricing, queries share a pool, while capacity-based pricing with reservations gives dedicated slots (and shuffle capacity).
## Query insights
Query performance insights can flag slot contention, insufficient shuffle quota, high-cardinality joins and partition skew.
W: Slot contention: high queued work with low active work is the documented signature, and the fix is less competing load or reserved capacity.
X: B=Partitioning mistake: bad layout would show up as more data scanned in every run, and the query text and data are unchanged.
C=BI Engine miss: a cache miss would change how input stages run but would not produce queued work waiting for slots.
D=Skew in the first stage with ORDER BY: skew is a different insight, and adding a sort increases work.
T: Low active and high queued units mean contention for slots, not a slow query; manage concurrency or reserve capacity.

S: A data engineer opens BigQuery's query performance insights for a slow query. Which TWO kinds of findings can the insights report? (Select TWO)

BigQuery can attach insights to a query. Documented examples are slot contention, insufficient shuffle quota, high-cardinality joins and partition skew. @ GCP-PDE D4 T4.1 applied use-case
S: Analysts must query a customers table in BigQuery. Compliance says the national ID column must be visible only to the fraud team, and analysts should still be able to run SELECT * queries on the table. Which design satisfies both?
A: Tag the national ID column with a policy tag, grant the fraud team Fine-Grained Reader, and give analysts masked access through a data policy
B: Tag the national ID column with a policy tag and give analysts no further access, so that their SELECT * queries run on the remaining columns
C: Move the national ID column to a separate Cloud Storage bucket and ask the fraud team to join the data by hand
D: Create a logical view without the national ID column and give analysts access to both the view and the base table
K: A
G: ## Column-level access control and masking
Column-level security uses policy tags: a user without the Data Catalog Fine-Grained Reader role on the tag cannot read the column, and a SELECT * returns an error that lists the columns to exclude.
Dynamic data masking is built on top of that. A data policy maps a masking rule (for example nullify, default value, hash or last four characters) to a policy tag and to principals who hold the BigQuery Masked Reader role. Existing queries need no change: users with masked access see masked values.
## Combining them
Fine-Grained Reader users see the original data, Masked Reader users see masked values and others are denied.
W: Policy tag with fraud access and masked analyst access: fraud sees raw values, analysts' SELECT * works and returns masked values.
X: B=Policy tag with no masked access: without a data policy and the Masked Reader role, SELECT * fails for analysts because they lack access to the tagged column.
C=Manual join from a bucket: this loses BigQuery governance and adds manual steps for the fraud team.
D=View plus base table access: giving analysts the base table defeats the restriction, since they could read the column directly.
T: Combine policy tags with a data policy: raw for privileged groups, masked for others, denied for the rest.

@ GCP-PDE D4 T4.1 advanced use-case
S: Analysts must join the orders table to a customer table on the email column to count repeat buyers, but must not see actual addresses. Joins must still work across both tables. Which masking rule should the data engineer apply for analysts?
A: Hash (SHA-256), which returns a type-preserving hash so equal values stay equal and can be joined
B: Nullify, which returns NULL and hides the value so that the join still finds matching rows
C: Default masking value, which returns the same constant for every email so that rows still match uniquely
D: Last four characters, which returns the last four characters so that matching is still unique
K: A
G: ## Choosing a masking rule
BigQuery data masking rules differ in how much they reveal and in how useful the result is:
- **Nullify** returns NULL, hiding the value and the data type; it is not useful in joins.
- **Default masking value** returns a constant per data type, hiding the value but revealing the type.
- **Hash (SHA-256)** returns a type-preserving hash; use it when users need to join on the column. The same input always gives the same hash.
- **Email mask** replaces the username with XXXXX but leaves the domain visible.
- **First four / last four characters** keep part of the value (hashed if it is four characters or fewer).
- **Random hash** is salted per query, so joins work only within one query and only for data policies in the same project.
W: SHA-256 hash: deterministic output means equal emails get equal hashes in both tables, so the join counts repeat buyers.
X: B=Nullify: NULL never matches in an equality join, so no rows would match.
C=Default value: all emails collapse to one constant, so every row would match every other row and counts would be wrong.
D=Last four: many emails share the same last four characters, so matches would be false positives.
T: Pick hash masking when masked users must still join on the column.

@ GCP-PDE D4 T4.2 advanced troubleshooting
S: A churn model built in BigQuery ML scored well in evaluation, but its predictions are poor in production, where requests arrive as raw rows. The training query computed scaled and bucketed features in a separate SELECT that is not reused at prediction time. What is the most robust fix?
A: Move the feature logic into the TRANSFORM clause of CREATE MODEL, so the same preprocessing is applied at evaluation and prediction
B: Retrain with more rows from the same table and keep the preprocessing in a separate query
C: Disable automatic preprocessing and rely on prediction callers to scale values correctly
D: Create a materialized view with the bucketing logic and ask callers to read from it per prediction request, while the model keeps its own features
K: A
G: ## Training-serving skew
When training features are transformed in a query that the prediction path does not repeat, the model sees different distributions at prediction time (training-serving skew). Fixes:
- Put preprocessing inside the model with the `TRANSFORM` clause of CREATE MODEL. The preprocessing is automatically applied when you use the model with ML.EVALUATE and ML.PREDICT, and callers pass raw columns.
- Manual preprocessing functions can also be used outside TRANSFORM to prepare training data, but then the same logic has to be reproduced at serving time.
W: TRANSFORM clause: preprocessing is stored with the model, so prediction takes raw rows and gets the same features as training.
X: B=More rows: more data does not fix a mismatch between how features are made in training and serving.
C=Disabling automatic preprocessing: this removes protection and puts the burden on each caller, which increases inconsistency.
D=Materialized view: callers could skip it or use a stale definition, and it does not tie preprocessing to the model.
T: Use TRANSFORM so that feature engineering travels with the model and avoids training-serving skew.

@ GCP-PDE D4 T4.2 applied tradeoff
S: A team forecasts demand from three years of weekly data with a BigQuery ML regression model. One feature is the average discount of the week being predicted, and rows were split randomly into training and evaluation sets. Evaluation accuracy is very high, but real accuracy is low. Which TWO data preparation problems explain this? (Select TWO)
A: Data leakage, because a feature uses information from the period being predicted that is unavailable at prediction time
B: Too few distinct columns, because BigQuery ML cannot compute feature statistics unless many columns exist
C: Weekly granularity, because BigQuery ML models cannot train on data that has been aggregated by period
D: A random split of time-ordered rows, because evaluation rows then mix in periods that lie close to or before training rows
E: Automatic preprocessing, because it always standardizes numeric inputs in a way that inflates evaluation scores
K: A,D
G: ## Leakage and splits
Data leakage occurs when training features contain information that would not be available when the prediction is made, such as the discount of the week being predicted. Evaluation looks excellent because the model is effectively seeing the answer; production predictions lack that information.
## Time-ordered data
For time-dependent data, evaluation rows should come after training rows. A random split puts neighbouring weeks in both sets, which flatters the score. BigQuery ML's CREATE MODEL has a `DATA_SPLIT_METHOD` option (AUTO_SPLIT, RANDOM, CUSTOM, SEQ, NO_SPLIT) that controls how input data is divided into training and evaluation sets, and custom splits can be prepared in SQL.
W: A=Leakage: a future-looking feature inflates evaluation accuracy and is unavailable in production.
D=Random split: mixing time periods across the sets makes evaluation optimistic compared with predicting genuinely later weeks.
X: B=Too few columns: BigQuery ML computes statistics for whatever columns exist, and the symptom here is inflated evaluation, not missing statistics.
C=Weekly granularity: aggregated data is a normal input, and coarse grain would not produce very high evaluation accuracy.
E=Automatic preprocessing: it prepares features consistently for training and prediction and does not inflate evaluation scores.
T: Build each feature only from data available at prediction time, and evaluate on periods later than training.
