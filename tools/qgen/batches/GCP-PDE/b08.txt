@ GCP-PDE D5 T5.2 applied comparison
S: Every night a data engineer must call a partner REST API, wait for a Cloud Run job to finish, run one BigQuery load and then post a status message. The steps are strictly sequential, need no Python code, and the team wants no environment to size or patch. Which scheduling design fits best?
A: Cloud Scheduler triggering a Workflows workflow that calls each service in order and waits for the result
B: A Cloud Composer environment with a DAG for the four steps, kept running around the clock for this one job
C: A BigQuery scheduled query that tries to call the REST API and the Cloud Run job from inside the SQL text
D: A cron job on a Compute Engine VM that runs a shell script and is restarted by hand when the VM fails
K: A
G: ## Picking an orchestrator for a repeatable job
Three Google Cloud tools cover most scheduling needs:
- **Cloud Scheduler** is a managed cron service. It starts something on a schedule but does not model steps or dependencies.
- **Workflows** is a serverless orchestrator for sequences of service and HTTP calls, with retries, conditions and waiting on long-running operations. A Cloud Scheduler job can trigger a workflow on a schedule.
- **Cloud Composer** (the managed Apache Airflow service, now named Managed Service for Apache Airflow in the docs) fits data pipelines with many dependent tasks, backfills, sensors and Python-defined DAGs. It is an always-on environment you pay for and operate.
## Applying it here
Four ordered calls with no custom code is the textbook Workflows case. Heavy Airflow features (backfill, DAG-to-DAG dependencies, hundreds of tasks) are not needed, so a whole Composer environment is overkill.
W: A=Cloud Scheduler plus Workflows: the scheduler fires the workflow each night and Workflows sequences the HTTP, Cloud Run and BigQuery calls with built-in waiting and retries. Nothing is provisioned or patched.
X: B=Always-on Composer environment: it would work, but it carries standing cost and operations for one short linear job and brings Airflow features the team does not need.
C=Scheduled query as orchestrator: scheduled queries run GoogleSQL statements on a schedule; they cannot call a partner REST API or wait for a Cloud Run job.
D=Cron on a VM: this puts patching, availability and restarts on the team, the opposite of the stated requirement, and gives no step-level retry or visibility.
T: For a short, linear, code-free sequence use Cloud Scheduler with Workflows; keep Cloud Composer for dependency-heavy data DAGs.

@ GCP-PDE D5 T5.2 applied troubleshooting
S: A BigQuery scheduled query appends the previous hour's aggregates to a reporting table with INSERT. It is set to run at exactly the top of every hour. Occasionally the same hour's rows appear twice. What should the data engineer do?
A: Move the schedule off the exact hour, such as a few minutes past, and make the statement safe to repeat
B: Keep the schedule and add a larger destination table so duplicate inserts are absorbed without any effect
C: Change the query to run as a batch priority job so BigQuery guarantees it executes exactly one time
D: Replace the schedule with a Cloud Monitoring alert that reruns the query whenever a duplicate is detected
K: A
G: ## Scheduled queries and repeat runs
BigQuery scheduled queries are built on BigQuery Data Transfer Service. The documentation warns that a scheduled query configured to run exactly on the hour (for example 09:00) might trigger more than once, which can duplicate rows when the statement is an `INSERT`. The recommended mitigation is an off-the-hour time such as 08:58 or 09:03.
## Make repeats harmless
Any scheduled pipeline should be **idempotent**: running it twice for the same time window leaves the same result. For a reporting table this means overwriting the hour's partition or using `MERGE` on a natural key, instead of blind appends.
## Why other fixes fail
Capacity or priority settings change when a job runs, not how many times a schedule fires, and monitoring only reports the symptom.
W: A=Off-the-hour schedule plus idempotent write: it avoids the documented hour-boundary double trigger and, with a partition overwrite or `MERGE`, a rare repeat can no longer duplicate rows.
X: B=Larger table: table size has nothing to do with duplicate triggers; the extra rows are still inserted and still counted twice.
C=Batch priority: priority controls queueing behaviour when slots are scarce; it does not give exactly-once scheduling.
D=Alert-driven rerun: an alert detects a duplicate after the fact, and rerunning an append would add yet another copy.
T: Schedule queries off the hour and design each run to be idempotent so a repeated trigger cannot duplicate data.

@ GCP-PDE D5 T5.2 advanced use-case
S: A Cloud Composer DAG loads one day of sales into BigQuery with an append task. Operations often re-run failed days from the Airflow UI, and finance has found doubled revenue on re-run days. The engineer wants the DAG to be safe to re-run for any date. Which change achieves that?
A: Make the load task write to that run's date partition with overwrite semantics, so a re-run replaces the same data
B: Set the task retries to zero so a failed day is never attempted a second time by Airflow or by operators
C: Add a second task that appends the same rows again to a backup table, then compare the two tables every morning
D: Put the whole extract, transform and load code in a single PythonOperator task so only one task can fail
K: A
G: ## Idempotent tasks
Composer documentation advises that each task be an idempotent unit of work. An idempotent task produces the same end state however many times it runs for the same logical date.
- Append-only loads are not idempotent: a re-run adds the day again.
- Loading to the **partition of the run date** with a truncate/overwrite disposition, or using `MERGE` on a key, is idempotent.
- Using the DAG run's logical date (a templated value) rather than the wall-clock time makes a re-run target the same data.
## What does not help
Disabling retries removes resilience without fixing re-runs started by people. Bundling work into one task makes the failure unit larger and partial reruns harder, which the docs advise against.
W: A=Partition overwrite for the run date: re-running the task for a given day rewrites that day's partition, so the result is the same however often it runs.
X: B=Zero retries: this removes automatic recovery from transient errors, and manual re-runs would still double the data.
C=Second append plus comparison: it doubles the duplicate rows and adds a manual reconciliation step instead of preventing duplicates.
D=Single large task: a multi-step script inside one operator is explicitly discouraged; it still appends on re-run and restarts everything on any failure.
T: Make every DAG task idempotent, for example by overwriting the run-date partition, so retries and manual re-runs are safe.

@ GCP-PDE D5 T5.2 applied troubleshooting
S: A team's Cloud Composer DAGs set `email_on_failure` to True, yet nobody has ever received a failure email, and the team also wants to hear at once if the whole environment stops being healthy, not just a single task. Which TWO actions address this? (Select TWO)
A: Configure the environment to send email through SendGrid so the failure emails can actually be delivered
B: Create a Cloud Monitoring alerting policy on the environment health metric that is driven by the liveness DAG
C: Edit the liveness DAG in the dags folder to run every minute so health is reported more often
D: Raise the default task retries to a large number so failures never surface to the notification path
E: Grant the DAG authors the Monitoring editor role so each author can see every environment metric
K: A,B
G: ## Notifications in Cloud Composer
- Setting `email_on_failure` makes Airflow send mail when an operator fails, but Composer documents that to send email from an environment you must **configure it to use SendGrid**. Without that, the setting has nowhere to send.
- Task-level mail does not tell you the platform is unhealthy. Composer runs a liveness DAG named `airflow_monitoring` on a schedule and publishes the result as the `composer.googleapis.com/environment/healthy` metric: True when the run succeeds, False when it fails. Alert on that metric in Cloud Monitoring.
## Cautions
The liveness DAG's frequency and contents are immutable, and changes to it do not persist. Retries are valuable for transient errors but are not a monitoring tool.
W: A=SendGrid email: the documented requirement for `email_on_failure` mails to leave a Composer environment; once configured, task failures reach the recipients.
B=Environment health alert: an alerting policy on the healthy metric fires when the liveness DAG fails, which covers scheduler or environment trouble that task emails cannot.
X: C=Editing the liveness DAG: its schedule and code are fixed by the service and any edit is discarded, so health reporting cannot be sped up this way.
D=Large retries: retries recover from transient faults but hide nothing useful from monitoring; they do not deliver any email or alert.
E=Monitoring editor for authors: write access to metrics is not what is missing; no alert or mail is created by simply viewing metrics.
T: Failure emails from Cloud Composer need SendGrid, and environment-level problems are caught by alerting on the health metric.

@ GCP-PDE D5 T5.2 applied troubleshooting
S: After a team added forty new DAGs, Cloud Composer tasks start late and the scheduler seems busy even when few tasks run. The new DAG files query BigQuery and read a configuration table at the top of the file, outside any task. What is the most likely cause and fix?
A: The DAG files do heavy work whenever they are parsed, so move the queries inside tasks and keep file-level code light
B: The workers are too small to run tasks, so add worker nodes without changing how the DAG files are written
C: The tasks need an Airflow pool of size one for every DAG so the scheduler is never asked to run two at once
D: BigQuery is rate limiting the environment, so schedule all forty DAGs at the same minute to share one connection
K: A
G: ## DAG parse time
Airflow's scheduler repeatedly parses every file in the `dags/` folder to discover DAGs. Code at the top level of a DAG file runs on every parse, not only when a task executes. Network calls such as BigQuery queries, API requests or database reads at file level therefore run constantly, slow parsing and load the scheduler. The Composer guidance is to verify that new DAGs do not increase parse time too much.
## Fix
Keep top-level code to imports and DAG/task definitions, and perform queries and heavy computation in tasks or in templated fields evaluated at run time.
W: A=Move work into tasks: file-level queries run at every parse; relocating them to task execution removes the constant scheduler load and restores on-time scheduling.
X: B=More workers: workers run tasks, but the symptom is scheduler load from parsing, so extra worker capacity does not help.
C=Pool of size one: pools limit concurrent task slots; they would slow work further and do nothing about parse-time queries.
D=Same-minute schedules: stacking all DAGs at one time makes scheduling contention worse and is unrelated to parse behaviour.
T: Do not run queries or heavy code at the top level of a DAG file; the scheduler executes it on every parse.

@ GCP-PDE D5 T5.3 applied tradeoff
S: A media analytics team runs BigQuery on the on-demand model. Monthly cost swings widely because of occasional very large queries, and finance wants predictable spend with some headroom for peaks. Utilisation is fairly steady during working hours. What should the data engineer propose?
A: Move to a BigQuery Editions reservation with a baseline for steady load and autoscaling for the peaks
B: Stay on on-demand and ask users to run every query as a batch job so bytes processed stay constant
C: Buy a very large fixed baseline sized for the worst peak ever seen and leave autoscaling switched off
D: Create one reservation per analyst project with no baseline and no autoscaling to share costs evenly
K: A
G: ## On-demand versus capacity-based pricing
- **On-demand** bills by TiB processed per query. Usage and bills are variable, so large queries create spikes.
- **Capacity-based** (BigQuery Editions) bills slot-hours. You create a reservation and choose a **baseline** (always allocated and always billed) and optionally an **autoscaling** maximum (extra slots added when needed, billed while scaled). This gives centralized, predictable billing.
You can use both models together and switch at any time.
## Sizing idea
Cover the steady, predictable load with baseline slots and let autoscaling absorb peaks. Sizing the baseline for the worst peak wastes money all the time; zero capacity leaves jobs without slots.
W: A=Editions reservation with baseline plus autoscale: the baseline matches steady working-hour usage at a known cost, and autoscaling gives headroom for peaks without paying peak capacity around the clock.
X: B=Batch priority on on-demand: batch changes queueing priority, not the bytes a query scans or the bill, so the swings remain.
C=Worst-case baseline, no autoscaling: this makes spend predictable but pays for peak capacity at all times, which wastes budget when utilisation is steady.
D=Per-project reservations with zero slots: a reservation with no baseline, no autoscaling and no idle sharing gives its projects nothing to run on.
T: Use a reservation with a baseline for steady load and autoscaling for peaks to make BigQuery spend predictable.

@ GCP-PDE D5 T5.3 applied troubleshooting
S: A team created a Standard edition reservation, assigned a project to it and later decided the workload needs another edition's capabilities. They try to change the edition on the existing reservation and cannot. What does the documentation say they must do?
A: Delete the reservation and create a new one in the other edition, then assign the project again
B: Open a support case so Google changes the edition field on the reservation in place
C: Move the project to the on-demand model first, because editions can be changed only from there
D: Edit the capacity commitment, because the commitment alone decides the edition of its reservations
K: A
G: ## Editions are fixed per reservation
BigQuery has three editions (Standard, Enterprise, Enterprise Plus) that differ in capabilities, SLO and compute model. You pick an edition when you create a reservation or a capacity commitment. The Understand BigQuery editions page states that to change the edition associated with a reservation you must **delete and recreate** it.
## Practical consequences
- Plan the edition from requirements (features, availability target) before creating reservations.
- Do not use edition tiers to restrict access to features, because the features per edition can change over time.
- After recreating, assign projects (or folders and the organization where the edition supports it) to the new reservation.
W: A=Delete and recreate: this is the documented way to move capacity to another edition, followed by new assignments.
X: B=Support case: there is no in-place edit of the edition; support would give the same delete and recreate answer.
C=Go on-demand first: on-demand is a separate billing model and is not a stepping stone for changing editions.
D=Edit the commitment: a commitment is edition-bound too, but changing it does not alter an existing reservation's edition.
T: A reservation's edition cannot be edited; delete and recreate the reservation in the target edition.

@ GCP-PDE D5 T5.3 applied troubleshooting
S: Finance questions a bill. A reservation autoscales, and the data engineer compares the autoscaled slots billed for a day with the slot usage summed from INFORMATION_SCHEMA.JOBS. The billed number is clearly higher. Which explanation is correct?
A: Autoscaled slots are charged for the slots scaled up, with a minimum scale-down window, not the slots used by jobs
B: The jobs view is rounded down to the nearest hour, so small jobs are missing from the total that is shown
C: Only queries that failed are billed at the autoscaling rate, so successful queries never appear on the invoice
D: Autoscaled slots are charged only while a query is actively reading data, so shuffle stages are billed double
K: A
G: ## How autoscaling is billed
When a reservation autoscales, BigQuery adds slots in multiples of 50 up to the configured maximum. You are charged for the number of **scaled** slots, not the number of slots actually used, and capacity is retained for at least a 60-second scale-down window (by default billing is per second with a one-minute minimum; fluid scaling is an opt-in without the minimum). The charge applies even if the job that caused scaling fails.
## Consequence
`INFORMATION_SCHEMA.JOBS` reports per-job slot usage, so summing it will not match the autoscaling bill. The docs say not to use the jobs information schema to reconcile billing and point to the information schema views that monitor autoscaling instead.
W: A=Scaled slots, not used slots: billing follows scaled capacity and the scale-down window, so job-level usage sums come out lower than the charge.
X: B=Hourly rounding: the jobs view records slot milliseconds per job; it does not round to hours, and rounding is not the documented reason.
C=Failed queries only: billing is for scaled slots whether jobs succeed or fail; failures are just one case that still incurs the charge.
D=Double shuffle billing: slot capacity is billed per scaled slot, not by data-read phases of a query.
T: Autoscaling bills scaled slots with a scale-down window, so job-level slot usage never reconciles exactly with the bill.

@ GCP-PDE D5 T5.3 advanced use-case
S: A nightly financial close runs in a reservation that has no baseline and no autoscaling and relies on idle slots borrowed from other reservations. When other teams are busy the close misses its deadline. Which TWO changes make the close dependable? (Select TWO)
A: Give the close's reservation baseline slots sized to its normal need so some capacity is always allocated
B: Enable autoscaling on that reservation with a maximum large enough for the close's peak demand
C: Set the reservation to ignore idle slots, so it stops borrowing and therefore cannot be preempted
D: Run the close as a batch priority job, because batch jobs are protected from slot preemption
E: Assign the close project to a folder instead, since folder assignments always bypass slot contention
K: A,B
G: ## Idle slots are best effort
Within a capacity-based setup, slots unused by one reservation are shared by default with others in the same administration project. Documentation warns not to rely solely on idle slots for production workloads with strict time requirements: idle slots can be preempted at any time. Such jobs must use **baseline** or **autoscaled** slots.
- A reservation with no baseline and no autoscaling that loses its borrowed slots has none, and its queries pause or queue until slots become free.
- `ignore_idle_slots` only stops a reservation from *borrowing*; it can still lend. Used alone it removes the only capacity this reservation has.
## Fix
Provide guaranteed capacity (baseline) for the usual need and autoscaling for the peak.
W: A=Baseline slots: baseline capacity is always allocated to the reservation, so the close always has slots irrespective of what other teams do.
B=Autoscaling maximum: autoscaled slots are added when demand rises, which covers peaks above the baseline.
X: C=Ignore idle slots: this stops the reservation from borrowing, which for a reservation with no baseline or autoscaling leaves it with nothing.
D=Batch priority: batch jobs are lower priority and more likely to queue when slots are scarce, so this makes the deadline risk worse.
E=Folder assignment: where a project is assigned decides which reservation it uses, not whether the reservation has capacity.
T: Strict-deadline jobs need baseline or autoscaled slots; idle slots are only opportunistic.

@ GCP-PDE D5 T5.3 applied troubleshooting
S: An admin assigns the project of a new ETL team to a reservation named etl. The reservation has zero baseline slots, zero autoscaling slots and is set to ignore idle slots. The console shows the assignment as pending, and the team's queries show no reservation. What is happening?
A: The reservation has no capacity source, so the assignment stays pending and the project runs as on-demand
B: The assignment works, but queries are routed to the organization's default reservation automatically
C: The project is blocked from running any queries until the administrator buys a slot commitment
D: BigQuery splits the project's jobs across all reservations in the region until the assignment completes
K: A
G: ## Requirements for an assignment
An assignment links a project, folder or organization (folders and organizations are not available to Standard edition reservations) to a reservation. A reservation can take an assignment only if at least one of these holds:
- it has a non-zero baseline;
- it has non-zero autoscaling slots; or
- it is configured to use idle slots and idle slots are available.
If none is true you see `Assignment is pending, your project will be executed as on-demand.` Jobs of a project with no effective assignment use the on-demand model, so their `reservation_id` in INFORMATION_SCHEMA is empty.
## Fix
Add baseline or autoscaling slots, or allow idle slot use, and the assignment becomes effective.
W: A=Pending, on-demand: with zero baseline, zero autoscaling and no idle use, the reservation cannot back the assignment, so queries run (and are billed) on-demand.
X: B=Default reservation: BigQuery has no automatic default reservation to catch these jobs; the fallback is on-demand.
C=Blocked until a commitment: commitments are optional and do not gate assignments; the project keeps running on-demand.
D=Spread across reservations: a project uses a single most specific reservation, not a shared pool of all of them.
T: A reservation needs baseline, autoscaling or idle-slot access to accept an assignment; otherwise the project stays on-demand.

@ GCP-PDE D5 T5.3 applied definition
S: In a reservation shared by dashboards and nightly data-quality scans, the scans are not time critical but sometimes slow dashboard queries when all slots are busy. What should the data engineer do for the scans?
A: Run them as batch query jobs so they queue behind interactive queries when the reservation is fully used
B: Run them as interactive jobs so BigQuery always executes them first and dashboards wait their turn
C: Keep them interactive and disable query result caching for them so they release slots earlier
D: Create a second project for the scans without assigning it to any reservation to get dedicated slots
K: A
G: ## Interactive versus batch query jobs
- **Interactive** (default) jobs are intended to start executing as soon as possible.
- **Batch** jobs have lower priority. When a project or reservation is using all of its available compute, batch queries are more likely to be queued and stay queued. Once running, a batch query behaves like an interactive one.
Choose batch for work with no human waiting (scans, reports, backfills) so it does not compete with interactive dashboards.
## Related controls
Reservations can also keep workloads apart entirely: separate reservations per workload, assigned at project level.
W: A=Batch priority: the scans yield to interactive dashboard queries when slots run out, which matches non-urgent scans in a shared reservation.
X: B=Interactive priority: this makes the scans start immediately and compete with dashboards, which is the problem described.
C=Disable result caching: caching is unrelated to slot priority, and disabling it only adds work.
D=Unassigned project: an unassigned project runs on-demand, which is separate billing, not dedicated slots.
T: Send non-urgent work as batch queries so interactive queries get slots first in a shared reservation.

@ GCP-PDE D5 T5.3 advanced use-case
S: A retailer expects a one-off, unusually heavy analytics load during a sales event in three weeks. Its reservation has a modest baseline and an autoscaling maximum that has been enough so far. What does BigQuery guidance recommend?
A: Raise the baseline well before the event, because autoscaled capacity depends on availability at that moment
B: Rely on autoscaling alone, because autoscaled slots are reserved in advance exactly like baseline slots
C: Move the load to batch jobs only, because batch jobs are guaranteed capacity during peak periods
D: Switch off idle slot sharing for every reservation in the organization on the day of the event
K: A
G: ## Baseline versus autoscaled capacity
- **Baseline** slots are always allocated to the reservation, and you always pay for them.
- **Autoscaled** slots are not reserved in advance. They are drawn when needed and depend on current system availability, so during periods of high demand capacity constraints might delay scaling up.
BigQuery documents that baseline and autoscaling are meant to track *recent* workload. For an unusually large event, it recommends increasing baseline capacity well in advance, because raising a baseline also depends on available capacity and needs lead time.
## Commitments
Slot commitments (optional) lower the price of capacity that is needed steadily, and cannot be reduced during their term.
W: A=Raise baseline early: baseline is dedicated capacity; planning ahead gives BigQuery time to provide it, instead of hoping autoscaling finds capacity during peak demand.
X: B=Autoscaling alone: autoscaled slots are explicitly not reserved ahead and scale-up can be delayed under high demand.
C=Batch only: batch is lower priority, not guaranteed, and would delay the event's reports.
D=Disable sharing everywhere: ignore-idle settings affect borrowing, not guaranteed capacity, and would waste idle slots for others.
T: Plan for a known surge by raising baseline slots in advance; autoscaling is not pre-reserved capacity.

@ GCP-PDE D5 T5.3 applied tradeoff
S: An enterprise uses about 1,000 slots every hour of every day, with brief peaks to about 1,600. It expects this for years and wants the lowest effective cost with peak coverage. Which design is most appropriate?
A: A slot commitment covering the steady 1,000 slots, with baseline set to match and autoscaling for the peaks
B: No commitment and a 1,600-slot baseline, so peaks are covered at the standard pay-as-you-go slot rate
C: Pure autoscaling with zero baseline, so the steady 1,000 slots are bought minute by minute
D: Several one-slot reservations, one per user, so cost is split down to the individual analyst

G: ## Commitments, baseline and autoscaling together
- A **capacity commitment** gives a discounted rate for slots used consistently. It is optional, and a commitment cannot be reduced during its term, so commit only to the steady floor.
- **Baseline** slots allocate that capacity to a reservation; commitments provide the discount for the baseline.
- **Autoscaling** covers demand above baseline and is charged at the autoscaling rate for scaled slots.
For a flat 1,000-slot floor with rare peaks, commit to about the floor, set baseline to it and autoscale for the gap. Autoscaling slots work without commitments, but steady use is cheaper under commitments.
W: A=Commitment, matching baseline and autoscaling: the discount applies to the constant base, and only the occasional peak is bought at the autoscaling rate.
X: B=Large baseline without commitment: baseline of 1,600 pays for peak capacity constantly and without the commitment discount.
C=Pure autoscaling: steady load billed as scaled capacity forgoes the discount that a commitment gives for predictable use.
D=One-slot reservations: slots are allocated in meaningful capacity units for workloads; fragmenting per user would leave most reservations starved.
T: Commit to the steady floor, set baseline to it and let autoscaling absorb peaks.

@ GCP-PDE D5 T5.4 applied use-case
S: A streaming Dataflow job feeds a live dashboard. The on-call team wants a page when the pipeline falls behind by minutes, and a separate alert when any batch Dataflow job finishes in a failed state. Which approach uses Dataflow's Cloud Monitoring integration?
A: Alerting policies on the system lag metric for the streaming job and on the failed-job metric for batch jobs
B: Alerting policies on the element count metric of each PCollection, which are available at job level for alerting
C: A Cloud Logging sink to BigQuery with a nightly SQL query that checks for lag and failures
D: A Cloud Scheduler job that restarts the pipeline every hour so lag cannot build up
K: A
G: ## Dataflow metrics in Cloud Monitoring
Dataflow publishes job metrics to Cloud Monitoring, so you can chart them and create alerting policies. Among them:
- **System lag**: the maximum lag across the pipeline for streaming jobs, in seconds; alert on it for slow pipelines.
- **Failed**: set to 1 when a job exits with a failure; alert on it to detect failed pipelines.
- **Job status** enum values cannot be charted or used for alerts; use the Failed metric instead.
- **Element count** and estimated byte count are per-PCollection, not job level, so they are not available for alerting.
W: A=System lag and Failed metrics: both are job-level metrics that an alerting policy can evaluate, giving a prompt page for a lagging stream and a failure alert for batch.
X: B=Element count alerts: element count is per PCollection and the docs say it is not yet available for alerting.
C=Sink and nightly query: a daily check detects problems hours late, not when the pipeline falls behind.
D=Hourly restart: restarting does not diagnose or fix lag, risks losing state, and gives no failure alert.
T: Alert on Dataflow's system lag metric for streaming delay and on the Failed metric for failed jobs.

@ GCP-PDE D5 T5.4 applied troubleshooting
S: A batch Dataflow job processing partner files fails after running for an hour. Worker logs in Cloud Logging show the same exception on a few malformed records, repeated across several attempts, before the pipeline fails. What does this indicate and what is the right fix?
A: A bundle with a failing element was retried four times in batch mode; handle bad records in code, for example with a dead-letter output
B: Batch mode retries a failing bundle indefinitely, so the job should have recovered by itself if given more time
C: Workers ran out of quota, so the job needs a higher compute quota rather than any change to element handling
D: The job failed because its template version is out of date, so recreating the job from the same template will always clear the error
K: A
G: ## Retries in Dataflow
Dataflow processes elements in bundles and retries the whole bundle when an error is thrown for any element in it.
- In **batch** mode, a bundle with a failing item is retried **four times**; when one bundle fails four times the pipeline fails completely.

A persistent exception on specific records is a data-quality or code-handling problem, not a transient one.
## Fix

X: B=Infinite retry in batch: indefinite retry is the streaming behaviour; batch fails after four attempts.
C=Quota exhaustion: quota problems show distinct quota errors and are not tied to the same exception on malformed records.
D=Old template: a template version does not cause record-specific exceptions, and a recreated job would hit the same records.
T: Batch Dataflow fails after four retries of a bundle, so route malformed records to a dead-letter output.
