@ GCP-PDE D1 T1.1 expert troubleshooting
S: A bank's data-prod project sits inside a VPC Service Controls perimeter that restricts BigQuery, Cloud Storage and Dataflow. A nightly Dataflow job in data-prod, running as the service account etl-runner, must write a small aggregate table into a BigQuery dataset in the reporting-share project, which belongs to another business unit and is in no perimeter. The job fails at the write step, and the audit log shows violationReason RESOURCES_NOT_IN_SAME_SERVICE_PERIMETER on a BigQuery method. The security team will not add reporting-share to the perimeter, and its exfiltration policy requires every exception to name the identity, the service and the target project. What should the data engineer request?
A: An ingress rule on the data-prod perimeter that allows the reporting-share project to call the BigQuery API on data-prod resources for any identity
B: An egress rule on the data-prod perimeter that allows etl-runner to call the BigQuery API on resources in the reporting-share project only
C: An access level on the data-prod perimeter that matches the IP ranges of the Dataflow worker subnet, so the workers' requests are trusted
D: An egress rule on the data-prod perimeter that allows any identity to call any service on any project outside, limited to the job's time window
K: B
G: ## Ingress and egress in VPC Service Controls
A **service perimeter** blocks API requests that cross its boundary unless a rule allows them.
- **Ingress** is access by a client from outside the perimeter to resources inside it.
- **Egress** is access that involves a client or resource inside the perimeter and a resource **outside** it. A Dataflow job inside the perimeter writing to a dataset outside it is egress.
The violation `RESOURCES_NOT_IN_SAME_SERVICE_PERIMETER` means one request touched resources on both sides; the troubleshooting guide's fix is an **egress rule**.
## Scoping the rule
An egress rule has a `from` block (identities or identity types) and a `to` block (services, methods, and resources such as `projects/NUMBER`). Naming the service account, `bigquery.googleapis.com` and the one target project gives the narrowest exception, which is what the exfiltration policy asks for.
W: B=Scoped egress rule: the write is egress from the perimeter, and a rule naming etl-runner, the BigQuery service and only reporting-share allows exactly this flow and nothing else.
X: A=Ingress rule: the request does not come from outside into the perimeter; it leaves it, so an ingress rule does not match, and allowing any identity breaks the policy.
C=Access level on worker IPs: access levels are evaluated for requests coming into the perimeter from outside; they do not authorize calls from inside to a project outside.
D=Wide egress rule: it would let the write succeed, but any identity, service and project is the opposite of the named exception the policy requires, and rules have no time window.
T: Calls from inside a perimeter to a project outside need an egress rule scoped to identity, service and target project.
V: VPC Service Controls, Dataflow, BigQuery

@ GCP-PDE D1 T1.2 expert tradeoff
S: An audit consumer reads a Pub/Sub subscription with the default seven-day message retention. Its processor was stopped five days ago for a database migration, so the backlog's oldest unacknowledged message is now five days old. On Thursday the team will restart the consumer with a new parsing version and then validate output for three days. If validation fails they want to seek the subscription back to the moment just before the new version started and reprocess with the old one. They plan to rely on a snapshot for that rollback and must not lose any message. Which TWO statements are correct? (Select TWO)
A: A snapshot created right now would expire about two days later, which is before the three-day validation period could finish
B: A snapshot created right now would last the full seven days, because its lifetime starts counting only from its creation time
C: Creating a snapshot right now fails, because Pub/Sub refuses snapshots of any subscription whose backlog is older than one hour
D: If the old version first clears the backlog, a snapshot taken just before the switch lasts close to seven days and covers validation
E: Raising the acknowledgement deadline to 600 seconds before creating the snapshot extends the snapshot's lifetime to the full seven days
K: A,D
G: ## How long a Pub/Sub snapshot lives
A snapshot captures the acknowledgment state of a subscription so you can later **seek** to it and replay messages. Its lifetime depends on the backlog:
- lifetime = **7 days minus the age of the oldest unacknowledged message** in the subscription,
- the maximum lifetime is seven days,
- a snapshot that would expire in **less than one hour** cannot be created.
## Working the numbers
- Oldest unacked message is 5 days old, so a snapshot made now lives about 7 - 5 = **2 days**.
- Validation needs 3 days after Thursday, so that snapshot expires first and the rollback point is lost.
- If the old processor catches up first, the oldest unacked message becomes minutes old, and a snapshot taken right before the switch lives close to **7 days**.
W: A=About two days: seven days minus the five-day-old backlog leaves roughly two days, shorter than the three-day validation.
D=Clear the backlog first: with no old unacked messages, a snapshot taken just before the new version starts lives nearly seven days, enough to seek back after validation.
X: B=Full seven days: the lifetime is reduced by the age of the oldest unacked message, so an old backlog shortens it.
C=Refused when older than an hour: creation fails only if the snapshot would expire within one hour; a two-day lifetime is allowed.
E=Longer ack deadline: the deadline controls redelivery timing for leased messages; it does not change message age or snapshot lifetime.
T: A Pub/Sub snapshot lives seven days minus the oldest unacked message's age, so clear old backlog before taking a rollback snapshot.

@ GCP-PDE D1 T1.4 expert troubleshooting
S: Datastream replicates a self-managed MySQL 8 primary, which has one replica, into BigQuery with binlog-based replication; binary logs are kept for two days. Two incidents occurred this quarter. During planned maintenance the DBA promoted the replica to primary and repointed the stream, which then failed and needed a full backfill of 4 TB. Later a three-day VPN outage left the stream unable to resume because the positions it needed were gone. The business wants planned failovers to work without backfill and wants the stream to survive network outages of up to five days. Which TWO changes should the data engineer make? (Select TWO)
A: Increase the source's binary log retention to seven days, which is the retention Datastream's MySQL guide asks for
B: Switch to GTID-based replication by creating a GTID stream and pausing the binlog-based stream, avoiding a new backfill
C: Change binlog_format from ROW to MIXED, so that each log file is smaller and the same disk keeps logs for more days
D: Change binlog_row_image from FULL to MINIMAL, so the logs shrink and the two-day setting effectively covers five days
E: Point the binlog-based stream at the replica permanently, so that a failover of the primary no longer affects its positions
K: A,B
G: ## Binlog versus GTID replication in Datastream
Datastream can read MySQL changes in two ways:
- **Binlog-based**: it tracks positions in binary log files. Each node keeps its **own** binlog files and positions, so after a failover the new primary's positions do not match.
- **GTID-based**: every transaction has a global transaction identifier that is the same across the replication topology. GTID replication **supports failovers** and keeps working when the cluster changes. You can switch without a backfill by creating a GTID stream, pausing the binlog stream and starting the new one from the right point.
## Source configuration
The MySQL guide asks for `binlog_format=ROW` (MIXED and STATEMENT are not supported), `binlog_row_image=FULL`, and a **7-day** binary log retention. If logs are purged before Datastream reads them, the stream cannot resume. A 7-day retention covers a 5-day outage; 2 days does not.
W: A=Seven-day retention: logs then outlive a five-day outage, so the stream can resume from where it stopped.
B=GTID-based replication: transaction IDs are shared by primary and replica, so a planned failover no longer breaks the stream, and the documented switch avoids a backfill.
X: C=MIXED format: Datastream supports only ROW format, so the stream would stop working.
D=MINIMAL row image: Datastream requires FULL row images to reproduce changes, and smaller logs do not change a time-based retention setting.
E=Binlog stream on the replica: the replica's binlog positions are its own; if the replica is promoted or replaced, the same mismatch happens.
T: For MySQL sources, keep binlogs seven days and use GTID-based replication so Datastream survives outages and failovers.

@ GCP-PDE D2 T2.2 expert troubleshooting
S: A payments service writes settled transactions to a BigQuery table through the Storage Write API using an application-created committed-type stream. It sends AppendRows requests without offsets. During a network incident the client logged DEADLINE_EXCEEDED for several requests and retried them, and reconciliation later found about 3,000 rows stored twice. Finance needs rows queryable within seconds of settlement, forbids duplicates in the table, and does not allow a downstream deduplication job. The team can change the client code but not the table schema or its partitioning. Which change meets all three requirements?
A: Switch the client to the default stream with the same retry logic, because the default stream deduplicates rows within a short window
B: Keep the committed-type stream and send every AppendRows request with an offset, so a retry is accepted only at the next position
C: Switch to a pending-type stream and commit it every few minutes, so that rows from failed requests are discarded before the batch commit
D: Switch to legacy streaming inserts with an insertId per row, so that BigQuery removes rows that are retried within its deduplication window
K: B
G: ## Exactly-once writes with the Storage Write API
Stream types differ in visibility and delivery guarantees:
- **Default stream**: rows visible immediately, **at-least-once**; retries can duplicate rows.
- **Committed type**: rows visible as soon as they are written. With **client-supplied offsets**, the write happens only if the offset matches the next append offset, so a retried request that already succeeded is rejected instead of duplicated: **exactly-once**. Without offsets, rows are appended at the current end, and a retry can store them twice.
- **Pending type**: rows become visible only when the stream is committed, which suits batch loads.
## Matching the requirements
Queryable within seconds rules out pending streams that commit every few minutes. No duplicates and no downstream job require exactly-once at write time: committed type with offsets.
W: B=Committed type with offsets: rows stay visible within seconds, and the offset check turns a retried, already-written append into a rejected duplicate instead of a second copy.
X: A=Default stream: it gives at-least-once delivery, so retries after timeouts can still store rows twice.
C=Pending stream every few minutes: rows would wait minutes for the commit, breaking the within-seconds rule, and without offsets retried appends can still duplicate.
D=Legacy insertId: deduplication with insertId is best effort, so duplicates are still possible, which finance forbids.
T: For exactly-once streaming into BigQuery, use a committed-type stream with client-supplied offsets.
V: BigQuery
