@ Q010380 explain
G: ## Export subscriptions
Pub/Sub has three subscription families. **Pull** and **push** subscriptions hand messages to a subscriber application you run. **Export subscriptions** (BigQuery, Cloud Storage) make the Pub/Sub service itself write each message to a Google Cloud resource, with automatic flow control and load balancing.
## When no processing is needed
Docs state that without an export subscription you need a subscriber such as Dataflow to read and write messages, and that the overhead of a Dataflow job is not necessary when messages need no additional processing before storage. A BigQuery subscription can also use the topic schema, and failed writes can go to a dead-letter topic.
## Applying it here
Plain JSON into a table with no transformation is the exact case the export subscription targets: nothing to deploy, scale or monitor.
Current name: Dataproc is now documented as Managed Service for Apache Spark. The exam guide and this question keep the older name.
W: BigQuery subscription: the Pub/Sub service writes directly to the table, so there is no job or service to run, and cost and latency are lower than with a processing pipeline.
X: A=Push to Cloud Run: it delivers one message per request and needs custom insert code, retries and scaling that the service would otherwise handle for you.
B=Spark Structured Streaming on Dataproc: a cluster must be sized, patched and monitored, which is the heaviest option for a pass-through load.
C=Streaming Dataflow job: it works, but a continuously running job with workers adds cost and operations that are unnecessary when nothing is transformed.
T: When messages need no processing before storage, an export subscription replaces a Dataflow job.

@ Q010426 explain
G: ## Scheduled deletion
Cluster Scheduled Deletion removes a cluster automatically so inactive clusters stop incurring charges. It can delete a cluster:
- after a specified idle period,
- at a specified future time, or
- after a specified duration from the time of the creation request.
Idle time starts counting when the cluster has no running jobs (by default both the Jobs API and YARN activity must be idle).
## Applying it
For ad hoc queries or externally scheduled workloads, a cluster idle period is the matching control, because the jobs have no fixed schedule that a workflow template could encode.
Current name: Dataproc is now documented as Managed Service for Apache Spark. The exam guide and this question keep the older name.
W: A=Scheduled deletion with idle period: forgotten clusters are removed automatically once jobs stop, which fits unpredictable usage.
X: A=Autoscaling to minimum: a cluster always keeps its primary workers and master, and autoscaling is not recommended for shrinking an idle cluster; deleting and recreating is preferred.
B=Workflow template for ad hoc jobs: workflows suit a known job graph, but this usage is interactive and externally triggered.
D=Manual Friday cleanup: it depends on people remembering and misses idle periods during the week.
T: Use Cluster Scheduled Deletion with an idle period for ad hoc Dataproc clusters so forgotten clusters stop billing automatically.

@ Q010427 explain
G: ## Secondary workers for lower cost
Dataproc has primary workers and secondary workers. Secondary workers can be Spot VMs, standard preemptible VMs or non-preemptible VMs, and they scale compute cheaply because they do not store HDFS data.
- Preemptible workers lower per-hour cost for non-critical processing or to build very large clusters cheaply. For best results keep their number below 50% of all workers.
- Expect more transient single-worker task failures. To tolerate them, raise task retry limits, similar to the defaults of autoscaling clusters.
- Savings are not guaranteed, because preemptions can lengthen jobs. Short jobs fit better, and Enhanced Flexibility Mode helps.
Current name: Dataproc is now documented as Managed Service for Apache Spark. The exam guide and this question keep the older name.
W: A=More task retries: transient failures from preempted workers are retried, which avoids failing the job.
E=Secondary Spot workers under half: cheaper compute for a batch job, with enough stable primary workers to keep the cluster healthy.
X: B=All Spot including HDFS nodes: HDFS data is hosted on primary workers, and a cluster with only preemptible capacity risks job instability.
C=Intermediate data on secondary workers: losing the workers loses shuffle data and forces recomputation; Enhanced Flexibility Mode exists to avoid this.
D=Non-preemptible secondary only: these are priced like regular VMs, so there is no discount relative to the cost goal.
T: Add Spot or preemptible secondary workers (under about 50% of workers) and raise task retries; keep primary workers for stable capacity.

@ Q010428 explain
G: ## What autoscaling is for
The Dataproc autoscaling policy sets boundaries, frequency and aggressiveness for scaling workers. It suits clusters that store data in external services (Cloud Storage, BigQuery), clusters that process many jobs, and single-job clusters that need to scale up.
It is **not recommended** for:
- scaling an idle cluster down to a minimum size: creating a cluster is about as fast as resizing one, so delete idle clusters and recreate them (workflows, Cloud Composer or scheduled deletion);
- on-cluster HDFS, because HDFS utilization is not a scaling signal;
- Spark Structured Streaming, which autoscaling does not support.
Current names: Dataproc is now documented as Managed Service for Apache Spark; Cloud Composer is now documented as Managed Service for Apache Airflow (Managed Airflow). The exam guide and this question keep the older names.
W: A=Delete and recreate: an idle cluster keeps its minimum workers and master billing, so removing it entirely is the cost control, using workflows, Composer or scheduled deletion.
X: B=Higher maximum: the maximum only matters under load and does nothing about idle-time cost.
C=Structured Streaming: Dataproc autoscaling does not support Spark Structured Streaming.
D=HDFS utilization signal: autoscaling is not intended for scaling on-cluster HDFS, as HDFS utilization is not a scaling signal.
T: Do not use autoscaling to shrink idle Dataproc clusters; delete and recreate ephemeral clusters instead.

G: ## Mixed-size workloads and graceful scale-down
Autoscaling scale-down uses graceful decommissioning: workers are removed after the work on them finishes. When small and large jobs share a cluster, the scale-down waits for the large job, so one long-running job delays the release of resources that the smaller jobs no longer need.
Dataproc guidance: group similarly sized smaller jobs together on a cluster, and isolate each long-duration job on a separate cluster.
Current name: Dataproc is now documented as Managed Service for Apache Spark. The exam guide and this question keep the older name.
W: Separate clusters by job size: the long job no longer holds the shared cluster's capacity, so that cluster can scale down once the short jobs finish, and the long job's cluster is deleted after it ends.
X: A=Longer cooldown: it makes scale-down slower, which worsens the problem.
C=No graceful decommissioning: it risks killing running tasks and failing the long job, so it is unsafe.
D=Pin short jobs to HDFS nodes: it does not remove the dependency on the long job, and autoscaling is not intended to scale around HDFS.
T: Isolate long-running Dataproc jobs on their own clusters and group similar short jobs so autoscaling can scale down.

@ Q010432 explain
G: ## Auto Zone placement
When you create a Dataproc cluster you give a region. If you omit the zone, **Auto Zone** chooses a zone in that region for you, and all nodes are deployed in that one zone.
- Auto Zone prioritizes a zone that has resource reservations covering the request, using reserved plus on-demand resources when needed.
- If no zone can be fully satisfied from reservations plus on-demand capacity, it chooses the zone most likely to satisfy the request with on-demand resources.
- Zones can be excluded from the selection if at least two non-excluded zones remain (CLI and REST).
## Applying it
Letting Dataproc pick the zone removes the dependency on one zone's capacity and uses the reserved capacity first.
Current name: Dataproc is now documented as Managed Service for Apache Spark. The exam guide and this question keep the older name.
W: A=Auto Zone: the region is fixed, the zone is chosen per request, and zones with matching reservations come first, which raises the chance of success.
X: A=Autoscaling later: the failure is at creation, so no cluster exists to autoscale.
C=Always-on cluster in another region: duplicating a running cluster doubles cost and may break data residency.
D=Pinned cheapest zone: pinning keeps the dependency on a single zone's capacity, and retrying does not create capacity.
T: Omit the zone so Dataproc Auto Zone placement selects a zone with available capacity, preferring zones with matching reservations.

@ Q010521 explain
G: ## Primary and secondary workers in Dataproc
A Dataproc cluster has **primary workers** (standard VMs that run HDFS DataNodes and the node manager) and optional **secondary workers**.
- Secondary workers **only process**: they hold no HDFS data, only a local cache on their disks.
- They can be **Spot VMs**, standard preemptible VMs or non-preemptible VMs. Because a reclaimed node loses no stored data, Spark can reschedule its tasks.
- They are managed through managed instance groups, so they may appear a little after the scale-up call returns.
## Design guidance
Use stable primary workers for data and master roles, and add secondary workers for elastic, interruptible compute. Keep data in Cloud Storage when possible so even primary-worker loss is harmless.
Current name: Dataproc is now documented as Managed Service for Apache Spark. The exam guide and this question keep the older name.
W: B=Spot VMs: secondary workers can be Spot VMs, which suits fault-tolerant batch work because lost tasks are rescheduled on other nodes.
E=Processing only: secondary workers add CPU and memory but no HDFS storage, so compute scales independently from storage.
X: A=Scaling HDFS: secondary workers do not run DataNodes, so they add no HDFS capacity; primary workers or Cloud Storage provide storage.
C=Replacing the master: secondary workers have no master role at all; cluster high availability is configured through multiple master nodes.
D=Always non-preemptible: preemptible and Spot types are explicitly supported, and Spark retries lost tasks, so a single reclaimed worker does not abort the job.
T: Secondary workers are interruptible, storage-free compute for Dataproc; keep durable data on primary workers or in Cloud Storage.

G: ## Reading BigQuery from Spark
BigQuery is not an HDFS-style store, so Spark needs a connector. The **Spark BigQuery connector** reads through the **BigQuery Storage Read API**, which splits the table into streams that Spark executors read in parallel, applying column projection and filter pushdown. Writing back uses load jobs or the Storage Write API.
## Why exports and drivers lose
- A manual or scheduled export adds a copy, a delay and a cleanup job, and the data is stale.
- A single driver or single result stream becomes a bottleneck at multi-terabyte sizes.
Current name: Dataproc is now documented as Managed Service for Apache Spark. The exam guide and this question keep the older name.
W: Spark BigQuery connector: it reads in parallel using the Storage Read API, pushes down column and filter selection, and writes results back to BigQuery, with no export step.
X: A=Nightly export to Cloud Storage: it adds a stale copy and a pipeline stage, which is the manual export step the team wants to avoid.
B=JDBC with one long SELECT: a single result stream pages the whole table through one connection and cannot use parallel reads from many executors.
D=jobs.getQueryResults on the driver: collecting results on one driver node bottlenecks at 4 TB and defeats the purpose of distributed processing.
T: Use the Spark BigQuery connector so Dataproc jobs read and write BigQuery in parallel through the Storage APIs without exports.

@ Q010524 explain
G: ## SQL stored procedures in BigQuery
A stored procedure is a named, reusable collection of SQL statements saved in a dataset. It can accept **IN, OUT and INOUT arguments**, declare variables, and use procedural language such as `IF`, `WHILE` and `RAISE`. Callers invoke it with `CALL project.dataset.procedure(args)`, including from other datasets if they have access.
## Limits to remember
- A procedure has **no schedule of its own**. Run it from a scheduled query, Cloud Composer, Workflows or Dataform.
- SQL procedures execute inside BigQuery; there is also a separate type, procedures for Apache Spark, which is not what a plain SQL procedure uses.
Current names: Dataproc is now documented as Managed Service for Apache Spark; Cloud Composer is now documented as Managed Service for Apache Airflow (Managed Airflow). The exam guide and this question keep the older names.
W: C=Reuse with arguments: one definition in a dataset is called by many teams with different parameters, so logic is not copied.
E=Control flow: variables, IF logic and raising an error let a multi-statement job validate its own result.
X: A=Dataproc execution: a SQL procedure runs in BigQuery itself; Spark-based procedures are a different routine type.
B=Copy per dataset: procedures can be called across datasets by qualified name, which is why they centralise logic.
D=Built-in schedule: procedures never run on their own; a scheduled query, Composer or Workflows must call them.
T: A stored procedure packages multi-statement, parameterised SQL logic for reuse, but something else must trigger it.

@ Q010532 explain
G: ## Sensors and worker slots in Airflow
A **sensor** is an Airflow task that waits for a condition, such as a file in Cloud Storage. In the default `poke` mode it holds a worker slot for the entire wait, so many sensors can starve other tasks.
- **Deferrable operators** (and sensors) hand the wait to the Airflow **triggerer**, an asynchronous component that watches many conditions cheaply. The task releases its worker slot and resumes when the trigger fires.
- `reschedule` mode also frees the slot between checks, but a deferrable sensor is the modern approach.
In Cloud Composer the environment must run at least one triggerer before deferrable operators work.
## Why other fixes fail
Short timeouts break the business need; `sleep` still occupies a slot; Dataproc does not run Airflow task slots.
Current names: Dataproc is now documented as Managed Service for Apache Spark; Cloud Composer is now documented as Managed Service for Apache Airflow (Managed Airflow). The exam guide and this question keep the older names.
W: Deferrable sensor: the triggerer handles the wait asynchronously, so no worker slot is held while the file is missing.
X: B=Tiny timeout: the file may take hours, so the task would fail before it arrives and the DAG would not meet its purpose.
C=Dataproc for waiting: Airflow task slots belong to the Composer environment's workers; a Dataproc cluster does not take them over.
D=time.sleep loop: the PythonOperator still occupies a worker slot for the full sleep, so it is the same problem with worse behavior.
T: In Cloud Composer, use deferrable operators or sensors so long waits do not consume worker slots.

@ Q010541 explain
G: ## Trigger rules in Airflow
By default a task uses the trigger rule `all_success`: it runs only when all upstream tasks succeeded, otherwise it is skipped as `upstream_failed`. For cleanup tasks you want the opposite: the task must run **regardless of upstream result**.
- `all_done` runs after all upstream tasks finish, whatever their state.
- Trigger rules are an Apache Airflow feature that Cloud Composer runs unchanged. The ephemeral-cluster pattern is create cluster, run job, **delete cluster with `all_done`**.
- A Dataproc cluster can additionally be created with an idle-delete or maximum-age (scheduled deletion) setting as a safety net.
## Why not the others
Endless retries hide real bugs and cost money; clusters are not removed automatically unless a deletion setting is configured; a weekly sweep still leaves a week of cost.
Current names: Dataproc is now documented as Managed Service for Apache Spark; Cloud Composer is now documented as Managed Service for Apache Airflow (Managed Airflow). The exam guide and this question keep the older names.
W: all_done trigger rule: the cleanup task runs even after a failed Spark job, so the cluster is always deleted.
X: B=Weekly cleanup DAG: it leaves failed clusters billing for days and could delete clusters other teams still use.
C=Relying on defaults: Dataproc clusters stay up until deleted unless idle or age-based deletion is set, so nothing removes it.
D=100 retries: a job with a real bug never succeeds, so this burns cluster time and still may not reach the delete task.
T: Give cleanup tasks in an ephemeral-cluster DAG the all_done trigger rule so they run even when the job fails.

G: ## Idempotent tasks
Composer documentation advises that each task be an idempotent unit of work. An idempotent task produces the same end state however many times it runs for the same logical date.
- Append-only loads are not idempotent: a re-run adds the day again.
- Loading to the **partition of the run date** with a truncate/overwrite disposition, or using `MERGE` on a key, is idempotent.
- Using the DAG run's logical date (a templated value) rather than the wall-clock time makes a re-run target the same data.
## What does not help
Disabling retries removes resilience without fixing re-runs started by people. Bundling work into one task makes the failure unit larger and partial reruns harder, which the docs advise against.
Current name: Cloud Composer is now documented as Managed Service for Apache Airflow (Managed Airflow). The exam guide and this question keep the older name.
W: Partition overwrite for the run date: re-running the task for a given day rewrites that day's partition, so the result is the same however often it runs.
X: B=Zero retries: this removes automatic recovery from transient errors, and manual re-runs from the Airflow UI would still double the data.
C=Single large task: a multi-step script inside one operator is discouraged; it still appends on re-run and restarts the whole job on any failure.
D=Second append plus comparison: it doubles the duplicate rows and adds a manual reconciliation step instead of preventing duplicates.
T: Make each DAG task idempotent, for example by overwriting the run-date partition, so retries and manual re-runs are safe.

G: ## Catchup in Airflow
For each DAG, the Airflow scheduler creates a run for every schedule interval between `start_date` and now that has not run yet. This is **catchup**. If catchup is enabled (the Airflow default unless changed) and the start date is far in the past, hundreds of runs are created at once.
Composer's scheduler troubleshooting guide recommends:
- a **static** `start_date` (a dynamic one is evaluated on every parse and causes unpredictable scheduling),
- `catchup=False` to stop runs for past dates.
## Side effects of a flood
Many runs fill queues, starve other DAGs and multiply calls to external systems.
Current name: Cloud Composer is now documented as Managed Service for Apache Airflow (Managed Airflow). The exam guide and this question keep the older name.
W: C=Static start_date and catchup False: the scheduler creates runs only from now on, so no historical backfill floods the environment or the partner API.
X: B=Dynamic start_date: the guide warns against it because it is re-evaluated at every parse, which leads to unpredictable or missing runs.
C=One active run with catchup: runs execute one at a time, but the scheduler still processes two years of unwanted runs and calls.
D=More workers: it finishes the unwanted backfill faster and sends the partner API even more calls in a shorter time.
T: For DAGs that should not backfill, use a static start_date and set catchup to False.

G: ## Concurrency limits in Airflow on Composer
Several settings cap how many tasks run at once; the lowest one wins.
- `[celery]worker_concurrency` x number of workers = how many tasks workers can execute: 16 x 6 = **96**.
- `[core]parallelism` = how many tasks the scheduler can queue to the executor at once. Composer's guide says it is usually set to the product of maximum workers and worker concurrency.
- **Pool size**: Composer environments use one pool; if it is too small, the scheduler cannot queue tasks even when the other limits allow it.
- `max_active_tasks` per DAG and `max_active_runs_per_dag` cap one DAG.
## Reading the evidence
Exactly 32 running tasks matches `parallelism = 32`. Once parallelism is raised, the 64-slot pool becomes the next cap below 90. Workers are mostly idle, so more workers or higher worker concurrency would not help.

W: A=Parallelism to 96: the scheduler can then queue up to 96 tasks, matching what 6 workers x 16 slots can execute.

X: B=More workers: the existing 96 worker slots are mostly empty; the cap of 32 comes from the scheduler side, not from worker capacity.
