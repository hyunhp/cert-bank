@ TF-IEP002 D4 T4.1 applied use-case
S: A pull-request pipeline runs on shared runners that hold no cloud credentials. Which TWO Terraform steps can still run there and give useful feedback? (Select TWO)
A: terraform fmt -check -recursive, to fail the build when any file is not in canonical style
B: terraform plan with the default refresh, to show reviewers the changes against the live resources
C: terraform init -backend=false followed by terraform validate, to catch syntax and type errors
D: terraform plan -refresh-only, to confirm that no one changed the live resources outside Terraform
E: terraform apply on a plan file produced earlier, to prove that the plan can be executed
K: A,C
G: ## What needs credentials
A CI pipeline is a sequence of gates, and a good design puts the cheap, credential-free gates first so that most mistakes fail in seconds.
- **Style**: `terraform fmt -check` reads only local files. Its exit status is 0 when the input is properly formatted and non-zero otherwise.
- **Static checks**: `terraform validate` checks syntax and internal consistency, regardless of variables or state. It needs an initialized directory with providers and modules installed, and `terraform init -backend=false` prepares that without touching the backend.
- **Anything that reads real objects**: a normal plan, a refresh-only plan and an apply must call the backend and the provider APIs, so they need credentials.
Ordering the stages as format, validate, plan, approval, apply keeps expensive and privileged work at the end.
W: A=terraform fmt -check -recursive: it only parses local files, needs no network or credentials, and returns a non-zero status for unformatted files so the build fails.
C=init -backend=false plus validate: initialization without the backend still installs providers and modules, and validate then checks the configuration without calling provider APIs or remote state.
X: B=Default plan: planning refreshes every resource through provider APIs and reads state from the backend, so it fails without credentials.
D=Refresh-only plan: this mode exists to read live objects and compare them with state, which requires credentials for both the backend and the provider.
E=Applying a saved plan: apply changes real infrastructure, needs backend and provider access, and is the last stage of a pipeline, not a credential-free check.
T: Put fmt -check and init -backend=false plus validate first; anything that touches state or providers needs credentials.
V: Terraform

@ TF-IEP002 D4 T4.1 applied definition
S: A pipeline step runs terraform fmt -check in the repository root. It passes, yet a module in modules/network/ is badly formatted and reaches main. What change makes the step catch it?
A: Add -recursive, because by default fmt processes only the current directory unless told to descend into subdirectories
B: Add -diff, because the exit status becomes non-zero whenever a diff would be produced for any nested file
C: Run terraform validate first, because validation also enforces canonical formatting of every file in all modules
D: Add -write=false, because without it the command silently reformats the files and then reports success
K: A
G: ## fmt scope and exit status
`terraform fmt` has one job: rewrite configuration to the canonical style. In automation it is used in check mode.
- By default it scans only the current directory; `-recursive` also processes subdirectories.
- `-check` reports whether input is formatted: exit 0 when properly formatted, non-zero with a list of file names otherwise. `-check` implies no writing.
- `-diff` only displays the changes; `-write=false` only stops overwriting.
A pipeline that should fail on any unformatted file in the tree therefore uses `terraform fmt -check -recursive`.
W: Without -recursive the command never looks into modules/network, so the badly formatted file is invisible to the check. Adding -recursive extends the scan, and -check turns findings into a failing status.
X: B=-diff: it prints differences but is not the switch that controls the exit status; scope is still limited to the current directory.
C=validate: it verifies syntax, attribute names and types, not style, and a badly indented but valid file passes.
D=-write=false: -check already implies no overwrite, and the missing piece is directory scope, not file writing.
T: In CI use terraform fmt -check -recursive; check controls the exit status and recursive controls the scope.

@ TF-IEP002 D4 T4.1 advanced troubleshooting
S: A pipeline's validate stage passes for a change that sets instance_type to a value no provider API accepts, and the plan stage fails later. What explains the gap?
A: validate checks syntax and internal consistency only, not remote services, so accepted values of provider APIs are not tested
B: validate runs against the backend state and aborts only when the state holds a resource with a conflicting attribute

G: ## What validate does and does not do
`terraform validate` verifies that configuration is syntactically valid and internally consistent: correct attribute names, value types, references. It does so regardless of provided variables or existing state, and it does not validate remote services such as remote state or provider APIs.
## Consequence for pipelines
- A string such as an unknown instance size has the right type, so validate passes. Only the provider API rejects it, usually at plan or apply time.

C=Missing var-file: validate is designed to work regardless of the variables supplied and does not need values to be set.
D=Root only: validate checks the configuration in the directory including the module calls it contains; the gap is the remote API, not module depth.
T: validate catches structural errors only; provider-side acceptance shows up at plan, so use validation blocks to shift checks left.

@ TF-IEP002 D4 T4.1 advanced use-case
S: Two CI jobs run on separate runners: a plan job writes tfplan and uploads it, and an apply job downloads it later. Which TWO statements about handling that artifact are accurate? (Select TWO)
A: The file holds the full configuration and variable values, so sensitive values sit in cleartext and it needs protected storage
B: The apply job must run terraform init with the same lock file and Terraform version, since the plan file does not carry providers
C: The file is a standard JSON document, so reviewers can safely grep it for secrets and then share it on a public bucket for audit
D: The apply job can add -var="size=large" to adjust a value after review without invalidating the approval
E: The apply job needs -auto-approve, because a saved plan otherwise waits for an interactive confirmation prompt
K: A,B
G: ## What a saved plan is
`terraform plan -out=tfplan` writes the plan in an opaque, non-standard file format. The docs state that it contains your full configuration, all values associated with planned changes and all plan options including input variables. Sensitive data, even if obscured on screen, is saved in cleartext. Treat the file as a sensitive artifact.
## Applying it elsewhere
- `terraform apply tfplan` performs the saved operations without prompting; passing the plan file is the approval, and `-auto-approve` is ignored.
- You cannot add planning modes or options to a saved-plan apply, because the plan already holds the final decisions.
- The plan file is not a replacement for initialization: the working directory must be initialized with the same provider versions (lock file) and a compatible Terraform version.
- `terraform show tfplan` renders the plan for review.
W: A=Sensitive artifact: the plan stores configuration and variables in cleartext, so artifact storage needs access control and short retention.
B=Initialized directory: the apply job needs a working directory prepared by init with the same lock file and a compatible Terraform version, because providers are installed by init and not embedded in the plan file.
X: C=Standard JSON: the format is opaque and not meant for other software; use terraform show -json for review and treat the file as secret either way.
D=Adding -var: a saved plan cannot be combined with extra planning options; the values were fixed at plan time, and the apply would be rejected.
E=Needs -auto-approve: passing a saved plan counts as approval, and the flag is ignored in that mode.
T: A saved plan is a secret-bearing, opaque artifact applied in an initialized directory; no new options and no extra approval flag.
V: Terraform

@ TF-IEP002 D4 T4.1 advanced tradeoff
S: A pipeline plans on merge, a reviewer approves, and a later job runs terraform apply -auto-approve with a fresh plan. Last week the apply deleted a database that the reviewed plan did not mention. Which change best closes the gap?
A: Apply the exact plan file that the reviewer saw, using terraform apply tfplan after the approval gate
B: Require two reviewers on the pull request, so that a second person also reads the plan output once
C: Run the plan twice before approval and compare the outputs, then continue with the second one
D: Add -refresh=false to the apply, so the apply cannot notice new differences in live resources
K: A
G: ## Approval gates and what is approved
A gate is only meaningful if the thing that was reviewed is the thing that runs. In a pipeline with a separate `plan` and `apply`, the approval is attached to a human-readable plan, but a second `terraform apply` without a plan file creates a **new** plan at apply time. Anything that changed between the two moments (a merge, a console edit, another pipeline) can appear in the second plan without anyone having approved it.
## The fix
Save the plan with `-out`, review it (for example with `terraform show`), put the manual approval after it, and apply that same file. If the state changed in between, Terraform refuses the stale plan instead of silently doing something else. Treat the file as sensitive and keep it as the artifact bound to the approval.
W: Applying the saved plan binds the approval to the exact change set. Differences discovered at apply time cause a failure, not an unreviewed deletion.
X: B=Two reviewers: more reading of an output that no longer matches the later apply does not stop the second, unreviewed plan from running.
C=Plan twice: both plans are throwaway, and the apply still creates a third plan, so nothing ties approval to execution.
D=-refresh=false: skipping refresh hides drift and uses possibly outdated state, which makes surprises more likely rather than less.
T: Approve a saved plan and apply that file; a fresh plan at apply time makes the approval meaningless.
V: Terraform

@ TF-IEP002 D4 T4.1 advanced troubleshooting
S: After a team adds -detailed-exitcode to its plan step, the pipeline starts failing on every run that has pending changes, though the plans are valid. What explains this?
A: Exit code 2 means success with changes present, and a step that treats any non-zero status as failure reads it as an error
B: The flag makes Terraform return 1 for a non-empty plan, which signals a partial failure that the job must retry automatically
C: The flag requires -out, and without a saved plan file the command ends with an unspecified error status
D: The flag adds an interactive prompt, which cannot be answered in CI and therefore aborts the step
K: A
G: ## Exit codes of plan
Without the flag, plan returns 0 on success (whether or not changes exist) and non-zero on error. With `-detailed-exitcode` the meanings become:
- `0` success, empty diff (no changes)
- `1` error
- `2` success, non-empty diff (changes present)
## Pipeline use
The flag lets a pipeline branch: exit 0 skips the approval and apply stages, exit 2 raises the approval gate, exit 1 fails the build. The shell step must therefore capture the status and treat 2 explicitly, rather than relying on the default "non-zero is failure" behavior.
W: Exit code 2 is the documented success-with-changes result, so a naive step that fails on non-zero marks every plan with changes as failed. The script should map 0, 1 and 2 separately.
X: B=Return 1: 1 remains an error status; changes present is distinct as 2.
C=Needs -out: the flag works without a plan file; -out only decides whether the plan is saved.
D=Interactive prompt: plan never prompts for approval, and the flag changes only the exit status.
T: With -detailed-exitcode, 0 means no changes, 1 error, 2 changes; handle 2 explicitly in the pipeline.

@ TF-IEP002 D4 T4.2 advanced use-case
S: A team runs a web tier on two identical stacks, blue and green, behind one load balancer. They want the cutover and the rollback to be a small, low-risk apply. Which design fits?

Terraform does not ship a deployment engine; it applies the desired state you declare. Blue/green is therefore a **modeling choice**: two complete stacks coexist and one object (a load balancer listener, a DNS weight, a routing rule) decides which one receives traffic.
- Create green while blue serves traffic; test it directly.
- Cutover is a plan that changes only the routing object, so the diff is tiny and reviewable.
- Rollback is the same one-line change back, because blue is still running.
- Remove the old stack later, in a separate apply, when confidence is high.

C=In-place AMI change: an in-place update has no parallel environment, and -replace after a failure means rebuilding under pressure.
D=Disposable green: removing the standby immediately after release eliminates the quick rollback path that blue/green exists to give.
T: Model blue and green as coexisting stacks and flip one routing value; remove the old stack in a later apply.

@ TF-IEP002 D4 T4.2 advanced tradeoff
S: A team wants a canary release: 5 percent of traffic to the new version, then 25, then 100. What does a Terraform-based design need to supply that Terraform does not do on its own?
A: A pipeline gate between applies that checks metrics and decides whether the weight variable moves on
B: A provisioner on the listener that sleeps and raises the weight on a timer with no external check of application health
C: A lifecycle setting that makes the provider observe error rates and revert the weight when failures increase
D: A single apply with count increasing by one each minute so that the weight grows continuously while it runs
K: A
G: ## Terraform and progressive traffic shifting
Terraform computes and applies a diff; it does not watch application health after the apply completes. Canary rollouts therefore combine two parts:
- **Configuration**: a variable (for example `canary_weight`) feeding a weighted target group, DNS record or routing rule, so each step is a small, reviewable change.
- **Orchestration**: the pipeline applies step one, waits, evaluates metrics from a monitoring system, and only then runs the next apply with a higher value. Failing the gate stops the rollout or applies the previous value.
Provisioner sleeps and timers are fragile and do not look at health, and no lifecycle argument performs automatic reversal.
W: Terraform lacks feedback from running traffic, so the pipeline must evaluate metrics between applies and decide whether to move the weight forward or back.
X: B=Provisioner timer: it moves traffic regardless of health and provisioners are a last resort; a timer is not a canary analysis.
C=Lifecycle revert: lifecycle arguments control creation, replacement and drift handling, not monitoring-driven rollback.
D=Count over time: a single apply is one graph walk to a final state; it does not pace itself over minutes and cannot pause for analysis.
T: Canary with Terraform means a weight variable plus a pipeline gate on metrics between small applies.

@ TF-IEP002 D4 T4.2 advanced use-case
S: A change to the AMI would replace all twelve instances of one resource in a single apply, and the service cannot lose them together. Which approach gives a batched rollout with plain Terraform?
A: Split the instances into groups keyed in a for_each map and roll the new AMI through one group per apply

D=-target on the block: the block address covers every instance, and -target is for exceptional use, not release control.

@ TF-IEP002 D4 T4.2 applied comparison
