@ TF-IEP002 D1 T1.5 expert troubleshooting
S: A tenant module builds `for_each = { for k, v in local.tenants : k => regex("^(?P<env>dev|prod)-(?P<app>[a-z]+)$", k) }`, where `local.tenants = yamldecode(file("tenants.yaml"))`. The YAML file is owned by a self-service portal that the platform team cannot edit, and it recently gained the key `prod-Billing`. Every plan now stops with: Call to function "regex" failed: pattern did not match any part of the given string. Requirements: valid tenants must keep deploying, invalid keys must be skipped rather than block everyone, and the platform team wants each skipped key reported on every run without failing it. Which TWO changes meet these requirements? (Select TWO)
A: Add `if can(regex("^(dev|prod)-[a-z]+$", k))` to the for expression, so keys that do not match are left out of the for_each map entirely
B: Add a `check` block whose `assert` lists keys failing `can(regex(...))`, so Terraform reports them as a warning on every plan and apply
C: Wrap the value in `try(regex(...), {})`, so keys that do not match get an empty object and their tenant resources are still created with defaults
D: Add a `validation` block to the module's tenant input that rejects keys failing the pattern, so invalid tenants stop the plan with a clear message
E: Replace `regex` with `regexall`, so keys that do not match return an empty list and the for_each map no longer raises an error for them
K: A,B
G: ## Why the plan stops
`regex(pattern, string)` returns the captures (here a map with the keys `env` and `app`, because the groups are named) when it matches, and **raises an error** when the pattern does not match. `prod-Billing` contains an uppercase letter, so the call fails, and one failing key stops the whole plan.
## Filtering with can
`can(expression)` evaluates the expression and returns `true` if it succeeds and `false` if it produces an error. Used as an `if` clause in the for expression, it drops the invalid key before `regex` is ever called for it, so only valid tenants enter `for_each`.
## Reporting without failing
A `check` block runs its `assert` conditions on every plan and apply and reports failures as **warnings**; the run continues. An assert such as `length([for k in keys(local.tenants) : k if !can(regex(...))]) == 0`, with an `error_message` listing those keys, gives the platform team the report they asked for.
## Why the other options fail a requirement
- `try(..., {})` keeps the bad key in `for_each`, so resources for an invalid tenant are created.
- A `validation` block (or any error) blocks every tenant, which the requirement forbids.
- `regexall` returns an empty list for a non-match, but the key stays in the map and its resources are still created with an empty value.
W: A=Filter with can: the if clause removes keys that do not match before regex runs, so valid tenants deploy and the bad key creates nothing.
B=check block warning: check assertions report failures as warnings on every run without stopping it, which is exactly the requested reporting.
X: C=try with an empty object: the invalid key stays in the map, so its tenant resources are created with empty values instead of being skipped.
D=validation block: a failed validation is an error that stops the plan for every tenant, the outcome the requirements rule out.
E=regexall: it avoids the error, but the key remains in for_each and its resources are created with an empty capture list.
T: Filter invalid keys with `can()` in the for expression's if clause, and report them with a check block, which warns without failing the run.

D=state push: it would work technically, but the runbook explicitly forbids writing state with state push.

X: B=Root constraint overrides: constraints are combined, not overridden; the network module's `~> 1.12.0` still rejects 1.15.

`.terraform.lock.hcl` records the exact version selected for each provider and the checksums that verify it. W: Upgrade locally, lock both platforms, commit: the new selection and its checksums for macOS and Linux arrive with the constraint change, and CI keeps verifying in read-only mode.
X: B=Commit as written: an entry first installed from a mirror holds checksums for the installing platform only, so the Linux runners could not verify their packages; providers lock adds them.
C=-upgrade with readonly in CI: the two flags conflict, and the requirement is that CI never writes the lock file.
D=Delete the lock file: CI would then choose and trust versions on its own, so nothing is verified against a reviewed file.
T: When a provider constraint moves past the locked version, run init -upgrade and providers lock for every platform locally, and commit the lock file.

HCP Terraform resolves conflicting values in a documented order: priority sets first, then command-line and local `TF_VAR_` values in CLI runs, then **workspace-specific variables**, then non-priority variable sets, with more specific scopes winning over broader ones.
## Ties between workspace-scoped sets
When two **workspace-scoped** variable sets conflict, HCP Terraform compares the **set names** and uses the one with lexical precedence (sorted by Unicode code points). The documentation example: with `A_Variable_Set` and `B_Variable_Set`, the value from `A_Variable_Set` wins, **regardless of which set was edited most recently**.
Ownership is compared first: workspace-scoped sets owned by a project beat organization-owned sets with the same scope. Here both are organization-owned, so the names decide.
