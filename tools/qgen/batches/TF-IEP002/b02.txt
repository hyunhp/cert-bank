@ TF-IEP002 D1 T1.5 applied use-case
S: A network module carves one subnet per tier out of `10.1.0.0/16`. A planner needs the CIDR for the fourth block (index 3) when every block is a /20. What does `cidrsubnet("10.1.0.0/16", 4, 3)` return?
A: `10.1.12.0/20`
B: `10.1.48.0/20`
C: `10.1.3.0/20`
D: `10.1.48.0/16`
K: B
G: ## How cidrsubnet slices a prefix
`cidrsubnet(prefix, newbits, netnum)` extends the prefix length by `newbits` and picks the subnet with number `netnum`, counting from zero.
- `/16` plus 4 new bits gives `/20`, and there are 2^4 = 16 such subnets.
- A /20 holds 4,096 addresses, which is 16 steps of 256 in the third octet, so subnet number N starts at third octet `N * 16`.
- Subnet 0 is `10.1.0.0/20`, subnet 1 is `10.1.16.0/20`, subnet 3 is `10.1.48.0/20`.
Counting new bits as the step size in the octet (3 x 4 = 12) is the classic mistake.
W: `10.1.48.0/20`: four new bits make a /20, each one spans 16 values of the third octet, and netnum 3 starts at 3 x 16 = 48.
X: A=`10.1.12.0/20`: multiplies netnum by the number of new bits (3 x 4) instead of by the 16-value octet step a /20 occupies.
C=`10.1.3.0/20`: treats netnum as the raw third octet; the network address of a /20 must fall on a multiple of 16, and 3 is not.
D=`10.1.48.0/16`: cidrsubnet always returns the extended prefix length (/20 here); the result keeps the original /16 only when newbits is 0.
T: cidrsubnet adds newbits to the prefix; netnum N starts at N times the size of one block.
V: Terraform

@ TF-IEP002 D1 T1.5 applied use-case
S: A module computes a static IP for a bastion with `cidrhost("10.0.8.0/22", 260)`. What does the function return?
A: `10.0.9.4`
B: `10.0.8.260`
C: `10.0.12.4`
D: An error, because the host number exceeds 255
K: A
G: ## cidrhost counts addresses, not octets
`cidrhost(prefix, hostnum)` returns the address at position `hostnum` inside the prefix, counting from the network address as number 0. Negative numbers count backward from the end of the range.
- `10.0.8.0/22` covers `10.0.8.0` to `10.0.11.255`, which is 1,024 addresses.
- Host number 260 is 256 + 4, so it spills into the next third octet: `10.0.9.4`.
- Only a number larger than the range (here above 1,023) is an error.
W: `10.0.9.4`: position 260 is one full 256-address block (moving 8 to 9 in the third octet) plus 4 more.
X: B=`10.0.8.260`: an IPv4 octet cannot exceed 255, so the function carries the overflow into the previous octet rather than printing it.
C=`10.0.12.4`: that address lies outside the /22 (which ends at `10.0.11.255`) and would need a host number of 1,028.
D=Error: the /22 has 1,024 addresses, so 260 is well inside the range; only host numbers beyond the range fail.
T: cidrhost returns the Nth address of the prefix and carries overflow into higher octets; it errors only past the end of the range.
V: Terraform

@ TF-IEP002 D1 T1.5 applied troubleshooting
S: A module merges default tags with caller tags: `merge({ tags = { env = "prod", team = "net" } }, { tags = { env = "dev" } }).tags`. What is the result?
A: `{ env = "dev", team = "net" }`
B: `{ env = "prod", team = "net" }`
C: `{ env = "dev" }`
D: `{ env = ["prod", "dev"], team = "net" }`
K: C
G: ## merge is shallow
`merge` combines maps or objects from left to right. For each top-level key, the value from the last argument that has the key wins, and the whole value is replaced.
- Here the top-level key is `tags`. Both arguments have it, so the second `tags` value replaces the first as a unit.
- Nothing inside the nested object is combined, so `team` disappears.
To combine nested maps you merge them explicitly, for example `{ tags = merge(a.tags, b.tags) }`.
W: `{ env = "dev" }`: the later `tags` value overwrites the earlier one completely because `merge` does not descend into nested maps.
X: A=Deep merge result: it would be correct only if `merge` combined nested objects key by key, which it never does.
B=Left side wins: later arguments take precedence over earlier ones, so the first value is the one overwritten.
D=List of conflicting values: `merge` never builds lists; a conflicting key simply takes the last value.
T: merge is shallow and last-wins; merge the nested maps yourself to keep both.
V: Terraform

@ TF-IEP002 D1 T1.5 advanced troubleshooting
S: A module has `local.cfg = { db = { port = null } }` and the expression `try(local.cfg.db.port, 5432)`. A teammate expects 5432. What value does the expression produce?
A: `5432`, because `try` replaces null values with the fallback
B: An error, because a null attribute cannot be read
C: `null`, because the attribute exists and evaluating it raised no error
D: `"5432"`, converted to a string to match the null type
K: C
G: ## try catches errors, not nulls
`try(expr1, expr2, ...)` evaluates its arguments in order and returns the first one that does not produce an error. The docs recommend using it sparingly, because it also hides typos in attribute names.
- If `local.cfg.db.port` were missing, evaluating it would raise "Unsupported attribute", and `try` would return the fallback.
- Here the attribute exists and its value is `null`. Reading it is not an error, so `try` returns `null` as is.
- To treat null as "unset", use `coalesce(local.cfg.db.port, 5432)`, or combine them: `coalesce(try(local.cfg.db.port, null), 5432)`.
W: `null`: the attribute is present, so no error occurs and `try` hands back the first argument unchanged, including a null.
X: A=Replaces nulls: `try` has no null handling; that is the job of `coalesce` or a conditional.
B=Error: reading an attribute whose value is null is valid, and `try` would hide an error anyway.
D=String conversion: no conversion happens; the result is the first argument as evaluated, and a number fallback is never converted.
T: try falls back on errors only; a present attribute holding null is returned as null (use coalesce for that).
V: Terraform

@ TF-IEP002 D1 T1.5 applied comparison
S: Which TWO expressions evaluate to the list `["a", "b", "c"]`? (Select TWO)
A: `flatten([["a"], ["b", ["c"]]])`
B: `concat(["a"], [["b", "c"]])`
C: `distinct(["a", "b", "a", "c"])`
D: `compact(["a", "", "b"])`
E: `slice(["a", "b", "c", "d"], 1, 3)`
K: A,C
G: ## Shape-changing list functions
- `flatten` removes all levels of nesting from a list of lists, however deep, and keeps element order.
- `concat` joins lists end to end but does not flatten: a list given as an element stays a nested list.
- `distinct` drops duplicates, keeping the first occurrence of each element and the original order.
- `compact` removes empty strings (and nulls) from a list of strings.
- `slice(list, start, end)` returns elements from `start` up to but not including `end`.
W: A=`flatten`: recursion removes both nesting levels, giving `["a", "b", "c"]`.
C=`distinct`: the second `"a"` is dropped and order is kept, giving `["a", "b", "c"]`.
X: B=`concat` with a nested list: the second argument contributes the single element `["b", "c"]`, so the result is `["a", ["b", "c"]]`.
D=`compact`: drops the empty string and returns `["a", "b"]`; there is no `"c"`.
E=`slice` from 1 to 3: starts at the second element and stops before index 3, so it returns `["b", "c"]`.
T: flatten is recursive, concat is not; distinct keeps first occurrences in order; slice's end index is exclusive.
V: Terraform

@ TF-IEP002 D1 T1.5 advanced troubleshooting
S: An engineer builds a lookup of words by first letter with `{ for s in ["ab", "cd", "ae"] : substr(s, 0, 1) => s }` and plan fails with a duplicate object key error for `"a"`. Which change gives `{ a = ["ab", "ae"], c = ["cd"] }`?
A: Wrap the list in `distinct()` so that duplicate first letters are removed
B: Append `...` after the value expression, as in `substr(s, 0, 1) => s...`
C: Replace the braces with brackets so the expression returns a list of the values
D: Add `if s != "ae"` so that only one word per letter is produced
K: B
G: ## Object for expressions need unique keys
A `for` expression in braces builds an object (or map). Each iteration produces one key and one value, and two iterations producing the same key is an error: Terraform cannot decide which value should win.
- Adding `...` after the value expression switches on grouping mode: values with the same key are collected into a list.
- Without grouping, every value is a scalar; with it, every value is a list, even for keys that occur once (`c = ["cd"]`).
- Brackets instead of braces produce a tuple of results with no keys at all.
W: Grouping with `...`: values that share the key `"a"` are collected into `["ab", "ae"]`, and `"c"` gets `["cd"]`.
X: A=`distinct()`: the three strings are already distinct, so nothing is removed and the keys still collide.
C=Brackets: that yields a tuple like `["ab", "cd", "ae"]` with no keys, so the lookup shape is lost.
D=Filtering with `if`: it hides a word to avoid the collision; the requirement is to keep every word, which grouping does.
T: Duplicate keys in a for-object are an error unless you group with `...`, which turns every value into a list.
V: Terraform

@ TF-IEP002 D1 T1.5 applied troubleshooting
S: `templatefile("${path.module}/user_data.tftpl", { name = var.name })` fails at plan time. The template contains `${region}` and `${name}`. The module also declares `var.region`. What is the cause?
A: The template engine only reads files in the root module, not in child modules
B: Template files must use the `.tpl` suffix, so `.tftpl` is rejected as a template
C: The template needs `var.region`, but a template can read module variables directly
D: The template references `region`, but only keys in the vars object are visible
K: D
G: ## What a template can see
`templatefile(path, vars)` renders the file with the string-template syntax (`${ }` interpolation and `%{ }` directives). The only variables available inside are the keys of the `vars` object.
- Module input variables, locals and resources are not visible unless you pass them in.
- A missing key is an error at plan time ("vars map does not contain key"), which is helpful, because a wrong script never reaches an instance.
- The file extension is only a naming convention: `*.tftpl` is the recommended pattern.
- A template cannot call `templatefile` itself recursively.
Fix: pass `{ name = var.name, region = var.region }`.
W: Only keys in vars are visible: `region` is not a key in the object, so evaluation fails even though a variable of the same name exists in the module.
X: A=Root-only files: `path.module` locates files in whichever module calls the function; child modules can use it.
B=Suffix rule: the extension is only a convention, and `.tftpl` is the name the documentation recommends.
C=Direct variable access: this is the false premise; templates see only what is passed, which is the reason for the error.
T: A template sees only the keys of the vars object; pass every value you reference.
V: Terraform

@ TF-IEP002 D1 T1.5 applied use-case
S: A module must upload a `.zip` artifact and a PKCS#12 certificate bundle as Base64 strings. Using `file("${path.module}/bundle.p12")` fails with an invalid UTF-8 error. Which function fixes this?
A: `base64encode(file("${path.module}/bundle.p12"))`
B: `templatefile("${path.module}/bundle.p12", {})`
C: `filebase64("${path.module}/bundle.p12")`
D: `textdecodebase64("${path.module}/bundle.p12", "UTF-8")`
K: C
G: ## Text versus binary file functions
- `file(path)` reads a file as UTF-8 text and returns the string. A binary file is not valid UTF-8, so the call fails.
- `filebase64(path)` reads the raw bytes and returns them Base64-encoded, which is the correct way to carry binary data such as archives, keystores or images in an argument.
- `base64encode(string)` encodes a string you already have. Wrapping `file()` in it does not help, because the failure happens inside `file`, before encoding.
- `filebase64sha256` gives the digest, for change detection of such files.
W: `filebase64`: it reads bytes directly and returns Base64, so no UTF-8 decoding is attempted.
X: A=`base64encode(file(...))`: `file` runs first and raises the same UTF-8 error, so the encode step is never reached.
B=`templatefile`: it also reads the file as UTF-8 text and renders it as a template, so it fails on binary content.
D=`textdecodebase64`: it decodes a Base64 string into text; it does not read files and takes the data as its first argument.
T: Use filebase64 for binary files; file and templatefile require UTF-8 text.
V: Terraform

@ TF-IEP002 D1 T1.5 applied definition
S: A variable holds `["b", "a", "b"]`. What does `tolist(toset(["b", "a", "b"]))` return?
A: `["b", "a", "b"]`
B: `["b", "a"]`
C: `["a", "b"]`
D: An error, because a set cannot be converted back to a list
K: C
G: ## Sets drop duplicates and have no order
`toset` converts a list to a set: duplicates are removed, and the original order is not kept. A set of strings is stored in lexical (sorted) order.
- `tolist` of a set produces a list in that sorted order, so converting through a set is a common way to get a unique, sorted list.
- Use `distinct` instead when you want unique elements in their original order.
- Conversion from set to list is always allowed.
W: `["a", "b"]`: the set holds `a` and `b` once each, and the resulting list follows the set's lexical order.
X: A=Original list: the duplicate `"b"` is removed by the set stage.
B=First-seen order: that would be the result of `distinct`; a set does not remember insertion order.
D=Error: conversion from a set to a list is valid for any element type.
T: toset removes duplicates and sorts strings; distinct removes duplicates but keeps order.
V: Terraform

@ TF-IEP002 D1 T1.5 applied use-case

@ TF-IEP002 D1 T1.5 advanced comparison
S: Which TWO statements about `try` and `can` are accurate? (Select TWO)
A: `can(expr)` returns true when the expression evaluates without error and false otherwise
B: `try(a, b)` returns the value of the first argument that evaluates without error
C: `try` also catches provider API failures that happen during apply
D: `can(expr)` returns the value of the expression when it succeeds
E: `try` works only inside a variable `validation` block
K: A,B
G: ## Two error-handling helpers
- `try(expr, fallback...)` evaluates arguments in order and returns the first that does not raise an error. It suits optional attributes of a loosely typed object.
- `can(expr)` returns a boolean: does this expression evaluate without error? It is mainly used in a variable `validation` condition, such as `can(regex("^[a-z]+$", var.name))`.
Both only deal with errors while evaluating the expression. They do not intercept provider failures, which happen later, during plan or apply operations on resources. Heavy use of `try` hides typos, so use it for genuinely optional data.
W: A=`can`: it converts "this expression errors" into a boolean, which is why it pairs with validation conditions.

D=`can` returning a value: it returns only true or false; use `try` when you need the value.
E=Validation only: `try` is usable anywhere an expression is allowed, such as locals and arguments.
T: try returns the first working value; can returns true or false; neither handles provider API errors.
