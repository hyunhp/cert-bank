@ TF-IEP002 D2 T2.1 applied use-case
S: A team on Terraform 1.12 stores state in S3 and locks it with a DynamoDB table. They want to retire the table and keep locking. Which change to the `s3` backend block achieves this?
A: Set `use_lockfile = true` and allow the pipeline role to read, write and delete the lock object stored beside the state key
B: Enable versioning on the bucket and remove `dynamodb_table`, since versioned writes make concurrent applies fail safely
C: Set `encrypt = true` with a customer managed KMS key, because encrypted state objects can only be written by one caller
D: Point `dynamodb_table` at the bucket name and add a `LockID` tag to the state object so S3 handles lock rows itself
K: A
G: ## How the S3 backend locks state
Locking stops two runs from writing the same state at once. The `s3` backend supports locking only if you opt in, and it offers two mechanisms.
- **S3 native locking**: `use_lockfile = true` makes Terraform create a lock object named like the state key plus `.tflock`, using S3 conditional writes. The lock exists while a run holds it and is deleted afterwards.
- **DynamoDB locking**: `dynamodb_table` names a table whose partition key is `LockID` (string). The docs mark this method deprecated and due for removal in a future minor version. Both can be set together during migration.
## Permissions follow the mechanism
The role needs `s3:GetObject`, `s3:PutObject` and `s3:DeleteObject` on the `.tflock` key, in addition to access to the state key. Missing delete rights leave the lock behind and the next run reports a held lock.
W: Native S3 locking: `use_lockfile = true` replaces the DynamoDB table, and the role needs get, put and delete on the lock object next to the state key.
X: B=Versioning only: versioning keeps old object versions for recovery, but it does not stop two runs from overwriting each other, so concurrent applies would still corrupt state.
C=Encryption: `encrypt` protects the object at rest; it has nothing to do with serializing writers, and KMS does not limit writes to one caller.
D=Table named after the bucket: a DynamoDB table is a separate service, and the backend never stores lock rows in S3 objects or tags.
T: To drop DynamoDB for S3 backend locking, set `use_lockfile = true` and grant object delete on the `.tflock` key.
V: Terraform, Amazon S3

@ TF-IEP002 D2 T2.1 applied troubleshooting
S: An engineer changes the `bucket` value in the `s3` backend block to a new bucket. `terraform init` stops with "Backend configuration changed". The state must move to the new bucket. Which command does that?
A: `terraform init -reconfigure`, which re-reads the block and copies the old state to the new location
B: `terraform init -migrate-state`, which copies the existing state to the newly configured backend
C: `terraform init -upgrade`, which refreshes the backend definition along with provider selections
D: `terraform state push` run before init, which writes the local file into the bucket named in the block
K: B
G: ## Changing a backend is a state decision
Terraform remembers the initialized backend in `.terraform/`. When the block no longer matches, `init` refuses until you say what should happen to the state: `-reconfigure` or `-migrate-state` must be supplied.
- **`-migrate-state`** copies existing state to the new backend, and may prompt to confirm each workspace. `-force-copy` answers yes to the prompts and implies `-migrate-state`.
- **`-reconfigure`** ignores the previous configuration and does not migrate anything. The new location starts empty, so the next plan proposes creating every resource again.
Back up the state first. The docs strongly recommend copying `terraform.tfstate` aside before migrating.
W: `-migrate-state`: it is the option that copies the existing state into the new backend, so the next plan shows no changes.
X: A=`-reconfigure`: it discards the old backend settings without copying, so the bucket would be empty and plan would want to recreate resources that already exist.
C=`-upgrade`: this only re-selects provider and module versions within constraints; it does not handle a changed backend.
D=`state push` first: push writes to the backend that is already initialized, which is the old one here, and it is not how a backend change is processed.
T: Changed backend settings need `init -migrate-state` to carry state over; `-reconfigure` starts with nothing.

@ TF-IEP002 D2 T2.1 advanced use-case
S: Four environments share one `s3` backend block in Git. Bucket and key differ per environment, and the repository must not hold them. Which TWO statements about a partial configuration are accurate? (Select TWO)
A: The block keeps `backend "s3" {}` and each pipeline run passes `terraform init -backend-config=prod.s3.tfbackend`
B: Backend arguments cannot use input variables, so a partial configuration is the way to vary them per run
C: Values from `-backend-config` stay in memory and are never written to the working directory
D: Terraform needs no backend block at all if every argument arrives through `-backend-config` options
E: Credentials passed by `-backend-config` are safer than environment variables because they are never saved in plan files
K: A,B
G: ## Why partial configuration exists
The `backend` block is read before variables are evaluated, so it cannot reference `var.` values. To keep environment-specific or sensitive arguments out of version control, you leave them out and supply them at `init`.
- A **file**: `-backend-config=PATH`, a file of `key = "value"` lines that fills the empty arguments.
- **Key/value pairs**: `-backend-config="key=value"` (shell history keeps these).
- Interactive prompts for missing values.
Terraform requires at least an empty `backend "s3" {}` in a root file to name the backend type. The merged result is written in plain text under `.terraform/`, and also into plan files, which is why HashiCorp recommends environment variables for credentials.
W: A=Partial configuration with a file: the empty block names the type and the per-environment file supplies bucket and key at init.
B=No variables in backends: backend settings are needed before variable evaluation, so per-run values must come through init options.
X: C=Memory only: the merged configuration is stored on disk in `.terraform/` in plain text, so that directory must stay out of version control.
D=No block needed: at least an empty backend block is required to select the backend type.
E=Safer than environment variables: the docs warn the opposite, because `-backend-config` values land in `.terraform/` and in plan files.
T: A partial backend block names only the type; init options fill in the rest, and the merged result sits in plain text under `.terraform/`.
V: Terraform

@ TF-IEP002 D2 T2.1 applied comparison
S: A root module declares `cloud { organization = "acme" workspaces { tags = ["app:web"] } }`. Three HCP Terraform workspaces carry that tag. An engineer runs `terraform init` then `terraform plan`. What is the expected behavior?
A: Terraform plans all three workspaces in one run and merges their results into a single plan
B: Plan fails because tags may only be used with a workspace `name`, so one workspace must be chosen
C: Terraform works in one workspace at a time, chosen with `terraform workspace select` or `TF_WORKSPACE`
D: Terraform creates a new workspace per tag value on every plan and runs there, leaving the existing ones untouched
K: C
G: ## Name versus tags in the cloud block
The `cloud` block links a working directory to HCP Terraform workspaces.
- `workspaces { name = "..." }` ties the directory to one workspace.
- `workspaces { tags = [...] }` ties it to every workspace in the organization with those tags (optionally limited with `project`). The CLI then maps its own workspace commands onto them: `terraform workspace list` shows the matches and `terraform workspace select` picks one. If no workspace has the tags, init offers to create one.
`name` and `tags` cannot be combined. Each run still targets exactly one workspace, with its own state and variables.
W: One workspace at a time: with tags, the CLI picks among matching workspaces via `workspace select` or `TF_WORKSPACE`, and each run uses that workspace's own state.
X: A=Merged plan: a run belongs to a single workspace and a single state, so there is no cross-workspace plan.
B=Tags need a name: the two settings are alternatives, and combining them is what is rejected.
D=Workspace per tag value: init may offer to create a workspace when none match, but plan never creates workspaces on its own.
T: A tags-based `cloud` block exposes many workspaces to the CLI; you work in one selected workspace per run.
V: HCP Terraform

@ TF-IEP002 D2 T2.1 advanced use-case
S: A project keeps state in an `s3` backend and now moves it to an HCP Terraform workspace. The team edits the configuration. Which approach moves the state with the fewest manual steps?
A: Keep the `backend "s3"` block and add a `cloud` block, so both receive every state write
B: Replace the `backend` block with a `cloud` block and run `terraform init`, accepting the prompt to copy existing state
C: Replace the block, run `terraform init -reconfigure`, then re-import each resource into the new workspace
D: Run `terraform state pull`, upload the JSON to the workspace's variables page and then remove the old backend
K: B
G: ## Moving state into HCP Terraform
A configuration can have one state storage setting: either a `backend` block or a `cloud` block, not both. Switching is a backend change, so `terraform init` detects the previous backend and offers to copy the existing state into the HCP Terraform workspace, matching the `-migrate-state` flow.
- Back up the state first.
- If the `cloud` block uses tags, init asks which workspace name to create or use for each existing workspace.
- Afterwards runs can execute remotely with state, locks and history handled by the service.
`-reconfigure` would skip the copy, leaving an empty workspace.
W: Replace and init: init sees the backend changed and offers to copy the state into the workspace, so no resources need to be re-imported.
X: A=Both blocks: a configuration can use only one of `backend` or `cloud`, and Terraform reports an error rather than dual-writing.
C=Reconfigure and re-import: `-reconfigure` discards the old state link, which forces needless imports of resources that are already tracked.
D=Upload as a variable: workspace variables are inputs to runs, not a state store, and state would not become a state version.
T: Switch to HCP Terraform by swapping `backend` for `cloud` and answering the migration prompt in `init`.

@ TF-IEP002 D2 T2.1 applied tradeoff
S: A shared state bucket for production is updated by a pipeline. Last week a mistaken `terraform state push` replaced the production state with an older snapshot. Which bucket setting lets the team restore the previous snapshot?
A: `use_lockfile = true`, because a lock object keeps the last written state in a sibling key
B: `encrypt = true`, because server-side encryption retains the prior ciphertext of each overwritten object
C: Bucket versioning, which keeps earlier versions of the state object so a known-good version can be restored
D: A `-backup` path on `terraform apply`, because the backup option copies remote state before each write
K: C
G: ## Locking is not backup
Three different protections get confused.
- **Locking** (`use_lockfile`) serializes writers. It holds no copy of state.
- **Encryption** (`encrypt`) protects data at rest. Overwriting still replaces the object.
- **Versioning** keeps earlier versions of the same S3 key. The S3 backend docs highly recommend enabling bucket versioning so state can be recovered after accidental deletion or human error.
After a bad overwrite you restore the earlier object version, then run `terraform plan` to see what differs from the real infrastructure. The `-backup` option is a legacy option for local state files, not remote backends.
W: Versioning: each overwrite creates a new object version, so the correct earlier state can be copied back as the current one.
X: A=Lock file: it exists only while a run holds the lock and holds no state content.
B=Encryption: it does not retain previous contents; an overwrite replaces the object.
D=`-backup`: the legacy backup options work with local state, so they do not snapshot an S3 backend before writes.
T: Recover from overwritten or deleted remote state with bucket versioning; locking only prevents concurrent writes.
V: Amazon S3, Terraform

@ TF-IEP002 D2 T2.2 applied use-case
S: `aws_instance.web` has no `count`. A developer adds `count = 2` to the block, and the plan wants to destroy `aws_instance.web` and create `aws_instance.web[0]` and `aws_instance.web[1]`. How do they keep the existing instance as the first one?
A: Add `moved { from = aws_instance.web to = aws_instance.web[0] }` so the existing state entry is retargeted to index 0
B: Add `lifecycle { ignore_changes = [count] }` so Terraform keeps the unindexed address and adds one more instance
C: Run `terraform apply -refresh-only`, which rewrites state addresses to match the new count automatically
D: Add `moved { from = aws_instance.web to = aws_instance.web }` so Terraform reads the single address as index 0
K: A
G: ## Addresses change when count is added
State tracks an instance by its full address. A resource without `count` has the address `aws_instance.web`; with `count` the instances are `aws_instance.web[0]` and `aws_instance.web[1]`. Terraform does not guess that the old object is the new first instance, so the plan destroys one address and creates two.
- A `moved` block states the mapping in code: `from` is the old address and `to` the new one. The next plan then shows the object as moved, and only the second instance is created.
- The same applies when switching between `count` and `for_each`, or adding `for_each` to a resource.
- `terraform state mv` achieves the same once per state, with no review in the plan.
W: `moved` to index 0: the old state entry is retargeted to `aws_instance.web[0]`, so only the second instance is created.
X: B=`ignore_changes` on count: `count` is not an attribute and cannot be listed; lifecycle rules do not map old addresses.
C=Refresh-only: it reads real objects and updates attribute values; it never renames addresses in state.
D=Moved to itself: both addresses are the same, so the block maps nothing and the bare address stays without state.
T: Adding count or for_each changes addresses; record the mapping with a `moved` block to avoid destroy and create.
V: Terraform

@ TF-IEP002 D2 T2.2 applied troubleshooting
S: An operator terminated `aws_instance.web` in the console. The configuration and state are unchanged, and the team runs `terraform plan`. What does the plan show?
A: A note that objects changed outside Terraform, then a proposal to create `aws_instance.web` again to match the configuration
B: An error that state refers to an instance the provider cannot find, so state must be repaired with `terraform state rm` first
C: No changes, because the plan compares configuration with state and skips reading real objects unless `-refresh-only` is set
D: A note that objects changed outside Terraform, then a proposal to destroy the old instance and create a replacement
K: A
G: ## Drift when an object disappears
A normal plan first refreshes state by reading each tracked object from the provider. If the object is gone, the provider reports it as not found, and Terraform drops it from the in-memory state before comparing.
- Plan output lists it under "Objects have changed outside of Terraform", so reviewers see the drift.
- The configuration still declares the resource and the refreshed state has none, so the plan proposes a **create**, not a replacement.
- Nothing is changed until apply. `terraform apply -refresh-only` would instead record the deletion in state without recreating anything.
The reverse case, an object edited in place, shows up as an in-place update back to the configured value.
W: Refresh then create: the missing instance is detected during the plan's refresh, reported as drift, and recreated because the configuration still wants it.
X: B=Error: a missing remote object is an expected drift case that plan handles; no manual state repair is needed.
C=No refresh: a normal plan refreshes by default; `-refresh-only` just limits the proposal to state updates.
D=Destroy and create: there is nothing left to destroy, since the refresh found the instance already gone, so only a create is planned.
T: A normal plan refreshes first; an object deleted outside Terraform is reported as drift and planned as a create.
V: Terraform

@ TF-IEP002 D2 T2.2 advanced comparison
S: A module is used by 30 workspaces. A maintainer renames `aws_s3_bucket.logs` to `aws_s3_bucket.audit` in the module. How should the rename ship so every workspace keeps its bucket?
A: Add a `moved` block from the old address to the new one in the module, so each workspace's next plan updates its state address
B: Run `terraform state mv` manually in only one workspace, because other workspaces learn the address through the registry
C: Rename the resource and rely on the provider to detect the same bucket name and update the state automatically
D: Add a `removed` block for the old address and an `import` for the new one in each of the 30 workspaces
K: A
G: ## Refactoring addresses safely
Terraform tracks objects in state by address. If you rename a resource block, the old address has no configuration and the new address has no state, so a plan proposes destroy and create.
- A **`moved` block** (`from = aws_s3_bucket.logs`, `to = aws_s3_bucket.audit`) records the rename in code. On the next plan, each workspace that has state at the old address shows the object as moved and retargets its state, with no infrastructure change.
- **`terraform state mv`** does the same by hand, once per state. With 30 workspaces that is 30 manual, unreviewed, error-prone operations.
Because the block ships with the module, consumers get the move as they upgrade. Keep it long enough for all consumers to apply once.
W: `moved` block: it travels with the module and each consumer applies the address change on its next run, with the change visible in the plan.
X: B=One manual `state mv`: each workspace has its own state, and nothing teaches the others the new address.
C=Provider detection: providers know nothing about Terraform addresses; the plan would destroy the old bucket and create a new one.
D=`removed` plus `import`: removed with destroy false and a new import would work per workspace but multiplies manual effort and is not a rename mechanism.
T: Ship a rename with a `moved` block so every state retargets itself on its next plan.
V: Terraform

@ TF-IEP002 D2 T2.2 applied troubleshooting
S: A team deletes the `aws_db_instance.legacy` block from the configuration. They want Terraform to forget the database while the database keeps running. The plan currently shows a destroy. What fixes it?
A: Add `lifecycle { prevent_destroy = true }` to the block and keep applying, since the destroy then only warns
B: Run `terraform plan -refresh=false`, so the missing block cannot cause the database to be destroyed
C: Add `removed { from = aws_db_instance.legacy }` with `lifecycle { destroy = false }` in place of the block
D: Add `moved { from = aws_db_instance.legacy to = null }` so the address is dropped from state quietly
K: C
G: ## Removing from management without destroying
A resource in state but not in configuration is planned for destroy. To stop managing it, state the intent in code with a **`removed` block**.
- `removed { from = aws_db_instance.legacy  lifecycle { destroy = false } }` tells Terraform to drop the object from state and leave the real database alone.
- `destroy = true` (the default) would destroy it, which is the same as deleting the block.
- The block is reviewed in the plan and travels with the code, unlike a one-off `terraform state rm`.
W: `removed` block with `destroy = false`: Terraform removes the address from state at apply time and does not call the delete API.
X: A=`prevent_destroy`: this makes the plan fail with an error, and it needs the resource block that was deleted.
B=`-refresh=false`: skipping refresh only avoids reading remote objects; the plan still compares state with configuration and proposes the destroy.
D=`moved` to null: `to` must be a valid resource address, so the block is invalid and cannot discard state.
T: Use a `removed` block with `destroy = false` to stop managing a resource without deleting it.
V: Terraform

@ TF-IEP002 D2 T2.2 advanced use-case
S: The security team wants to catch out-of-band changes to production early, without applying anything. Which TWO approaches serve that goal? (Select TWO)
A: A scheduled `terraform plan -refresh-only -detailed-exitcode` job that raises an alert when it exits with code 2
B: A scheduled `terraform validate` job that fails when a resource attribute differs from the cloud API
C: A scheduled `terraform plan -refresh-only -out=drift.tfplan` followed by `terraform show -json drift.tfplan` and a check for `resource_drift` entries
D: A nightly `terraform fmt -check` job that reports resources edited outside the pipeline
E: A pipeline step that runs `terraform state list` and compares the address count with the previous day
K: A,C
G: ## Detecting drift
Drift is real infrastructure differing from what state records. Only a command that reads the remote objects can see it.
- `terraform plan -refresh-only` compares state against real objects and proposes only state changes. With `-detailed-exitcode`, the exit code is 0 for no changes and 2 when changes exist (1 is an error), which suits a scheduled job.
- Saving the refresh-only plan and reading it with `terraform show -json` exposes a `resource_drift` list, which a script can inspect and alert on.
## What does not detect drift
`validate` checks syntax and internal consistency offline. `fmt` checks style. `state list` only prints addresses already in state.
W: A=Scheduled refresh-only plan: exit code 2 signals that remote objects differ from state, with no apply involved.
C=Saved refresh-only plan: the JSON plan lists resource_drift for objects that changed outside Terraform, and nothing is applied.
X: B=`validate`: it never contacts the cloud API, so it cannot compare attributes with reality.
D=`fmt -check`: it inspects file formatting only and knows nothing about resources.
E=`state list` counts: addresses in state do not change when someone edits an attribute in the console.
T: Detect drift with refresh-only plans (exit code 2 or the JSON resource_drift list); validate, fmt and state list cannot see it.

@ TF-IEP002 D2 T2.2 applied troubleshooting
S: An engineer runs `terraform state rm aws_instance.app` for a tracked instance, then runs `terraform plan`. The configuration still contains the `aws_instance.app` block. What does the plan show?
A: A plan to destroy the instance, because it is running but no longer recorded in state
B: A plan to create a new `aws_instance.app`, while the original instance keeps running outside management
C: No changes, because the plan reads the real instance by its configuration arguments
D: An error that the address was removed from state, which must be restored with `terraform state push`
K: B
G: ## What `state rm` does
`terraform state rm` deletes the binding between an address and its real object in state. It never calls the provider to delete anything: the object keeps running.
- Config still declares `aws_instance.app`, state has nothing for it, so Terraform plans a **create**.
- Applying that plan builds a second instance, and the first becomes unmanaged and may cost money or hold an IP or name.
- If the goal is to stop managing the object, remove the resource block too, or use a `removed` block. If the goal is to adopt it again, use `import`.
W: Create: with no state entry, Terraform sees a missing resource and proposes a new one, leaving the original untouched.
X: A=Destroy: destroy needs a state entry for an object to delete, so an object absent from state cannot be destroyed by Terraform.
C=No changes: Terraform matches configuration to state by address, not by searching the cloud for a lookalike.
D=Error: removal is valid; the plan runs normally and just differs from before.
T: After `state rm` with the block still in code, the next plan creates a duplicate.

@ TF-IEP002 D2 T2.3 applied use-case
S: Before changing a shared networking module, an engineer wants a picture of which resources depend on which, including the order Terraform will use. Which command gives this?

Terraform builds a directed graph of resources and data sources, and walks it so independent nodes run in parallel and dependent ones wait. An edge comes from a reference to another object's attribute (implicit) or from `depends_on` (explicit).
- `terraform graph` prints the simplified graph in Graphviz DOT format, for example `terraform graph | dot -Tsvg > graph.svg`.

Reading the graph before a refactor shows what changes ripple into.

C=`validate -json`: it reports diagnostics, not a list of dependency edges.

@ TF-IEP002 D2 T2.3 advanced use-case
S: Which TWO things create a dependency edge, so Terraform orders operations accordingly? (Select TWO)
A: A resource argument that references an attribute of another resource, such as `subnet_id = aws_subnet.a.id`
B: A `depends_on = [aws_iam_role_policy.p]` meta-argument listing another resource
C: The order in which resource blocks appear within a `.tf` file
D: The alphabetical order of the file names in the working directory
E: A shared `tags` value that both resources read from the same local
K: A,B
G: ## Implicit and explicit dependencies
- **Implicit**: referencing `aws_subnet.a.id` tells Terraform the instance needs the subnet first, so it creates the subnet first and destroys it last.
- **Explicit**: `depends_on` is for hidden dependencies, where one resource needs another to exist but no attribute is referenced, such as an instance whose boot script needs an IAM policy to be attached.
Position in files does not matter: Terraform loads all `.tf` files in a directory as one module. A shared local value creates a reference to the local, not an ordering between the two resources.
W: A=Attribute reference: it creates an implicit edge from the referencing resource to the one it uses.
B=`depends_on`: it creates an explicit edge for dependencies Terraform cannot see in the arguments.
X: C=Block order in a file: configuration is declarative, so layout in the file has no effect on ordering.
D=File names: all files in the directory are merged into one module, and name order is not an ordering signal.
E=Shared local: both resources depend on the local value, but that does not make one wait for the other.
T: Edges come from references and `depends_on`; file order and naming do not matter.
