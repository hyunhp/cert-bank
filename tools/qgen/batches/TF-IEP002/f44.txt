@ TF-IEP002 D4 T4.3 advanced troubleshooting
S: A platform team creates the AWS role trust policy for HCP Terraform with one condition on the token's aud claim and nothing on sub. A reviewer says the setup is unsafe. Why?
A: The condition covers plan-phase tokens alone, so apply-phase runs fall outside it and need a second role with its own trust policy
B: The aud claim is a secret value, so writing it into the trust policy discloses the audience to each user who can read the role
C: Matching aud with StringEquals rejects tokens that carry extra audience values, so StringLike with a wildcard is required instead
D: Any workspace in any HCP Terraform organization presenting a token with that audience could assume the role, so sub must be checked
K: D
G: ## Trust policy conditions
The OIDC identity provider in AWS trusts tokens from HCP Terraform's issuer. The **role trust policy** then decides which tokens may assume the role. HCP Terraform tokens carry:
- `aud`: the audience, default `aws.workload.identity` (or the value of `TFC_AWS_WORKLOAD_IDENTITY_AUDIENCE`).
- `sub`: a subject of the form `organization:ORG:project:PROJECT:workspace:WORKSPACE:run_phase:PHASE`.
The docs warn that you should always check, at minimum, the audience and the organization name, to prevent unauthorized access from other HCP Terraform organizations. The default audience is public knowledge, so it is not a secret that protects the role.
## Narrowing further
Match the project and workspace too, and use separate roles for plan and apply when permissions differ.
W: Other organizations can assume the role: the default audience `aws.workload.identity` is public knowledge and every HCP Terraform organization's tokens come from the same issuer, so a condition on aud alone admits runs from other organizations. The documentation warns to check, at minimum, the audience and the organization name in sub.
X: A=Plan phase alone: a condition without sub does not select a run phase at all; it matches plan and apply tokens alike, which is part of why it is too broad.
B=Secret audience: aud is not a secret and does not have to be; it names the intended consumer of the token, and its default value is published in the documentation.
C=StringLike required for aud: the documented trust policy matches aud with `StringEquals` against the single audience value; `StringLike` with a wildcard is used only on sub when one role should serve both run phases. A wildcard on aud would loosen the check further, not fix it.
T: Always restrict sub (at least the organization) in the trust policy; the audience alone does not identify your organization.

@ TF-IEP002 D5 T5.5 advanced tradeoff
S: Which TWO controls help stop accidental destruction of a production database? (Select TWO)
A: `lifecycle { ignore_changes = all }` on the database resource, so Terraform stops proposing destructive changes to it
B: A mandatory policy that inspects the plan's `resource_changes` for delete actions on database types and fails the run
C: Marking the database identifier variable `sensitive`, so plans that touch the database wait for a separate approval
D: `lifecycle { create_before_destroy = true }` on the database resource, so a replacement keeps the old instance in place
E: `lifecycle { prevent_destroy = true }` on the database resource, so plans that would destroy it fail with an error
K: B,E
G: ## Layers of protection
- **In configuration**: `prevent_destroy` makes Terraform reject plans that destroy the object, whether it is a destroy, a replacement, or a plan for `terraform destroy`. It does not cover removal of the whole resource block.
- **In the platform**: a mandatory-level Sentinel or OPA policy reads the plan (`tfplan.resource_changes` or `input.plan.resource_changes`) and fails when a protected type has a delete action. It also covers the block-removal case that `prevent_destroy` misses.
## What does not help
- `create_before_destroy` only changes the order of a replacement.
- `ignore_changes = all` stops update proposals; the docs state Terraform can still create and destroy the object.
- `sensitive` hides values, and has no approval role.
W: B=Mandatory policy on the plan: a Sentinel or OPA policy at a mandatory level reads `resource_changes`, finds delete actions on protected database types and fails the run in the platform, so the control remains even if someone removes the block or its lifecycle rule.
E=prevent_destroy: Terraform rejects any plan that would destroy the object, whether by destroy, replacement or `terraform destroy`, giving an immediate guardrail close to the code.
X: A=ignore_changes all: Terraform stops proposing updates for the arguments, but the docs state it can still create and destroy the object, so deletion is not prevented.
C=Sensitive identifier: `sensitive` only redacts the value in output; it adds no approval step and prevents no action, and it leaves reviewers with less information.
D=create_before_destroy: it only changes the order of a replacement; the old object is still destroyed after the new one exists.
T: Combine prevent_destroy in code with a mandatory plan-inspecting policy; ordering, ignore and sensitive settings do not prevent deletion.

S: A CI job runs `terraform plan -out=tfplan`, then uploads `tfplan` as a build artifact so another job can apply it after approval. A reviewer worries about secrets. Which statement is accurate?
A: The saved plan holds the configuration, planned values and input variables, and sensitive data is stored in cleartext

G: ## What a saved plan contains
`terraform plan -out` writes an opaque file with the full configuration, all values associated with planned changes, and the plan options including **input variables**. The documentation states that sensitive data, even if obscured in terminal output, is saved in **cleartext** in the plan file.
## Consequences for pipelines
- Treat the plan artifact exactly like state: restrict who can download it, set a short retention and keep it in an access-controlled artifact store.
- Do not publish it to a place broader than the people allowed to see the secrets it might hold.
- Ephemeral values are the exception: Terraform omits them from state **and** plan files, which is another reason to prefer them for credentials.
W: Cleartext saved plan: `terraform plan -out` writes the configuration, all values of the planned changes and the plan options including input variables, and the documentation states that sensitive data is saved in cleartext even when it is hidden in terminal output. The artifact must be guarded like state, with tight access and short retention.
X: B=Hashed variables: the file keeps the values, not hashes of them, and a saved plan is applied as is; hashes could not be applied without the values.
C=Runner-bound encryption: Terraform does not encrypt plan files with any key tied to a runner, so anyone who can read the file can extract the values.
D=Stripped values: only ephemeral values are left out of plan files. Sensitive values and the input variables still appear, and the apply needs them.
T: A saved plan file holds sensitive values in cleartext, so guard the artifact like state.

S: A module has variables `min_size` and `max_size`. The author wants a plan to fail whenever max_size is smaller than min_size, on Terraform 1.15. Which implementation works?
A: A default on max_size equal to the default of min_size, so callers who omit max_size get a valid pair
B: A check block asserting var.max_size >= var.min_size, which fails the plan when the assertion is false

G: ## Validation can look at other values

A `check` block is different: when its assertion fails, Terraform reports a warning and continues the plan or apply, so it cannot stop a bad pair of inputs.
W: Cross-variable validation: on the tested version a `validation` condition may read other input variables, so `condition = var.max_size >= var.min_size` on `max_size` rejects the bad pair during plan with a clear error message next to the input that is wrong.
X: A=Matching default: a default applies only when the caller omits the variable; it does not stop a caller from passing a max_size smaller than min_size.
B=check block assertion: a failing `check` assertion makes Terraform report a warning and continue the operation; the check block is the one validation that does not block plan or apply.
C=Local as a guard: a local is just a named value; when it evaluates to false nothing happens, because only validations, preconditions and postconditions stop a plan.
T: In current Terraform versions, variable validation can reference other variables; check blocks only warn and locals never fail a plan.

S: Which TWO statements about `try` and `can` are accurate? (Select TWO)

X: A=Validation only: `try` is usable anywhere an expression is allowed, such as locals and resource arguments; it is `can` that is mainly used in validation.
B=can returning a value: `can` returns only true or false; use `try` when you need the value itself.
C=Provider failures: they occur when the provider calls the remote API, long after expression evaluation, and are not caught by `try`.

D=depends_on on the module: this is also not allowed on a module with a nested provider configuration, and there is no `provider.aws` object to reference in `depends_on`.
