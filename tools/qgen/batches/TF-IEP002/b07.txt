@ TF-IEP002 D5 T5.1 applied troubleshooting
S: A module declares `variable "db_password" { type = string, sensitive = true }` and passes it to `aws_db_instance`. Plan output shows `(sensitive value)`, yet an auditor who downloaded the state file reads the password in cleartext. What explains this?
A: The sensitive flag only redacts the value in CLI and UI output; Terraform still writes the value to state and plan files
B: The sensitive flag was ignored because the variable is consumed by a managed resource instead of by an output block
C: The remote backend decrypts the state when it is downloaded, which makes every sensitive marker disappear from the file
D: The sensitive flag only applies to variables that have no default; set the default to null so redaction covers the state
K: A
G: ## What `sensitive` does and does not do
Marking a variable or output `sensitive = true` changes how Terraform **displays** values. Terraform redacts them in CLI output and the HCP Terraform UI, and any expression that references a sensitive value is treated as sensitive too.
It does not change what Terraform **stores**. State and plan files still contain the real value, so anyone who can read those files can read the secret. `terraform output -raw` and `-json` also print sensitive outputs in plain text.
## Keeping the value out of state
Only ephemeral values (the `ephemeral` argument on variables, the `ephemeral` block, write-only arguments) are omitted from state and plan files. Otherwise, secure the state: remote storage, encryption at rest, access control and audit logs.
W: The sensitive argument is a display control. The password still lands in state because the resource argument is a normal, persisted attribute, so protecting state access or switching to an ephemeral value plus a write-only argument is the real fix.
X: B=Resource consumption: sensitivity propagates to every expression that references the variable, which is why the plan shows a redacted value. The redaction is the same for outputs and resources, and neither stores less.
C=Decryption on download: encryption at rest protects the stored object, but the file content itself is not changed by sensitive markers. Even a perfectly encrypted state holds the secret once someone with access reads it.
D=Default value: the sensitive argument has no relation to defaults, and setting a default of null would only make the variable required or empty. It would not change what Terraform writes to state.
T: sensitive hides values on screen only; state and plan files still hold them, so use ephemeral values and write-only arguments or lock down state access.
V: Terraform

@ TF-IEP002 D5 T5.1 applied use-case
S: A config uses `resource "random_password" "db"` and passes `random_password.db.result` to the `password` argument of `aws_db_instance`. Security wants the password in neither resource's state entry. Which change achieves this?
A: Mark the `result` reference with `sensitive()` and enable server-side encryption on the state bucket that holds both entries
B: Use an `ephemeral "random_password"` block and pass its result to the instance's `password_wo` argument, with `password_wo_version` set
C: Move `random_password` into a child module and expose the value through an output block that has `sensitive = true`
D: Add `lifecycle { ignore_changes = [password] }` on the instance so Terraform stops tracking the password attribute in state
K: B
G: ## Two pieces work together
- An **ephemeral resource** (`ephemeral "random_password" "db" {}`) exists only during the current operation. Terraform never writes it to state or plan files.
- A **write-only argument** (such as `password_wo` on `aws_db_instance`) accepts a value for the provider to use and then Terraform discards it, so the managed resource's state entry has no password.
## Version argument
Because Terraform cannot store the write-only value, providers add a version argument such as `password_wo_version`. Terraform stores that number in state, so changing it is the way to tell the provider to send a new value.
## Reading it later
The generated value is not kept anywhere by Terraform. If it must be recoverable, write it to a secrets store in the same configuration (for example with a write-only secret argument) and read it back with another ephemeral resource.
W: The ephemeral block never persists, and the write-only argument hands it to the provider without storing it. Neither the random_password nor the database entry holds the secret, which a regular resource and argument pair cannot guarantee.
X: A=sensitive() plus encryption: sensitive only hides the value on screen and encryption protects the file at rest. The secret is still written to state, so anyone who can read the state reads the password.
C=Sensitive output via a child module: the random_password resource still saves its result in state, and a sensitive output is also stored in state. Moving the resource into a module changes only where the address lives.
D=ignore_changes: this setting stops Terraform from proposing updates to the attribute. It does not remove the attribute from state, and the value written on creation remains there.
T: To keep a secret out of state, generate it with an ephemeral block and consume it through a write-only argument and its version argument.
V: Terraform

@ TF-IEP002 D5 T5.1 applied troubleshooting
S: A CI job runs `terraform plan -out=tfplan`, then uploads `tfplan` as a build artifact so another job can apply it after approval. A reviewer worries about secrets. Which statement is accurate?
A: The saved plan encrypts every sensitive value with a key that only the approving job's runner can use
B: Terraform strips sensitive and ephemeral values from the file, so the artifact only holds non-secret planned changes
C: The saved plan holds the configuration, planned values and input variables, and sensitive data is stored in cleartext
D: The saved plan stores only a hash of each variable, so the apply job must receive all the secret values again
K: C
G: ## What a saved plan contains
`terraform plan -out` writes an opaque file with the full configuration, all values associated with planned changes, and the plan options including **input variables**. The documentation states that sensitive data, even if obscured in terminal output, is saved in **cleartext** in the plan file.
## Consequences for pipelines
- Treat the plan artifact exactly like state: restrict who can download it, set a short retention and keep it in an access-controlled artifact store.
- Do not publish it to a place broader than the people allowed to see the secrets it might hold.
- Ephemeral values are the exception: Terraform omits them from state **and** plan files, which is another reason to prefer them for credentials.
W: The saved plan is not encrypted and is not redacted. Sensitive values appear in cleartext, so the artifact must be protected as a secret store with tight access and short retention.
X: A=Runner-bound encryption: Terraform does not encrypt plan files with any key tied to a runner. Anyone who can read the file can extract the values.
B=Stripped values: only ephemeral values are left out of plan files. Sensitive values and the input variables still appear, and the apply needs them.
D=Hashed variables: the file keeps the values, not hashes of them, and a saved plan is applied as is. Hashing would make the plan impossible to apply without recalculating.
T: A saved plan file holds sensitive values in cleartext, so guard the artifact like state.

@ TF-IEP002 D5 T5.1 applied troubleshooting
S: Reviewers find a `prod.auto.tfvars` containing `db_password = "..."` committed to the main branch two weeks ago. Which remediation is most complete?
A: Delete the file in a new commit and add it to `.gitignore`, because the latest commit no longer exposes the password
B: Rotate the exposed password, remove the file and ignore it, then supply the new value through a secrets source or sensitive variable
C: Mark `db_password` as `sensitive = true` in the variable block, which redacts the committed value in the repository
D: Encrypt the committed file with base64 and decode it in the pipeline, so the stored copy is no longer readable at a glance
K: B
G: ## Secrets in version control
Terraform variable files are plain text, and Git keeps history. Once a secret is committed, deleting the file does not remove it from earlier commits, clones or forks, so the secret must be treated as compromised.
## A complete fix has three parts
- **Rotate** the credential so the leaked value is useless.
- **Remove and ignore** the file (and rewrite history only as an extra clean-up, not as a substitute for rotation).
- **Re-supply** the value from outside the repository: environment variables, an HCP Terraform sensitive variable, or an ephemeral read from a secrets manager.
The variables documentation also says to ignore variable definition files with sensitive values in your VCS.
W: Rotation is mandatory because history still holds the old value. Removing and ignoring the file stops a repeat, and moving the new value to a secrets source keeps it out of the repository.
X: A=Delete and ignore only: older commits still contain the password, so anyone with a clone or fork can read it. Without rotation the secret stays valid.
C=Sensitive flag: sensitive changes how Terraform displays values and does not touch a file already in Git. The committed text stays readable.
D=Base64: base64 is an encoding, not encryption; anyone can decode it in one command. It also leaves the secret in history.
T: A committed secret is a leaked secret: rotate it, remove and ignore the file, and inject the new value from outside the repository.
V: Terraform

@ TF-IEP002 D5 T5.1 applied use-case
S: A root module must read a short-lived token created by a child module and use it to configure a provider, without the token reaching state. Which child module declaration allows this?
A: `output "token" { value = ephemeral.auth.main.token, ephemeral = true }` in the child module
B: `output "token" { value = ephemeral.auth.main.token, sensitive = true }` in the child module
C: `output "token" { value = ephemeral.auth.main.token, ephemeral = true }` in the root module, read by the child
D: `variable "token" { default = ephemeral.auth.main.token }` in the child module, set from the root
K: A
G: ## Ephemeral outputs
The `ephemeral` argument on an `output` block omits that output from state. Terraform only allows it on **child module** outputs: root module outputs cannot be ephemeral. This is how a module passes a credential to its caller during one run.
## Where the caller may use it
An ephemeral value can only be referenced in ephemeral contexts: another ephemeral output or variable, locals, an `ephemeral` block, a write-only argument, a `provider` block and provisioner or connection blocks. A provider configuration is therefore a valid consumer of the token.
## Sensitive is a different control
`sensitive = true` hides the value on screen. A sensitive child output still reaches state.
W: An ephemeral child module output omits the token from state and plan, and the root can consume it in a provider block, which is an allowed ephemeral context.
X: B=Sensitive output: this redacts the display but the value is still persisted, so the token would reach state. It also is not accepted in a provider block unless the value is ephemeral.
C=Ephemeral root output: the ephemeral argument cannot be used on root module outputs, and the token comes from the child module in this design anyway.
D=Variable default: defaults must be constants, so a reference to an ephemeral resource there is invalid. Ephemeral values flow in through ephemeral variables or outputs.
T: Pass transient credentials between modules with ephemeral = true on a child module output; root outputs cannot be ephemeral.
V: Terraform

@ TF-IEP002 D5 T5.1 applied definition
S: A team reads a secret with `ephemeral "aws_ssm_parameter" "api"` and wants to use `.value`. Which TWO usages of `ephemeral.aws_ssm_parameter.api.value` are valid? (Select TWO)
A: As the value of a write-only argument such as `secret_string_wo` on a managed resource
B: As an argument of a regular, non-write-only attribute such as `tags` on a managed resource
C: As the value of a root module `output` block that has `sensitive = true`
D: As an argument inside a `provider` block that configures a provider
E: As an argument of a `data` block that reads another object from the cloud API
K: A,D
G: ## Where ephemeral values may appear
Terraform restricts ephemeral references to places where the value cannot be persisted. Valid contexts are: `locals`; `variable` blocks with `ephemeral`; child module `output` blocks with `ephemeral`; managed resource **write-only** arguments; other `ephemeral` blocks; `provider` blocks; and provisioner and connection blocks.
Anywhere else, such as an ordinary resource argument, a data source or a root output, Terraform returns an error when it plans, because the value would be written to state or plan files.
W: A=Write-only argument: the provider receives the value and Terraform discards it, so it is an allowed ephemeral context.
D=Provider block: provider configuration is evaluated at run time and never stored in state, which is why ephemeral credentials may configure providers.
X: B=Regular attribute: tags is stored in state, so Terraform rejects an ephemeral value there to avoid persisting it.
C=Root output: sensitive does not make it ephemeral, and root module outputs cannot be ephemeral. The value would be written to state.
E=Data block argument: data sources store their configuration and results in state, and the block is not on the list of ephemeral contexts, so the reference is rejected.
T: Ephemeral values may flow only into write-only arguments, provider blocks, locals, ephemeral blocks, and ephemeral variables or child outputs.

@ TF-IEP002 D5 T5.2 applied troubleshooting
S: A database uses `password_wo = var.new_password` and `password_wo_version = 1`. Security rotated the secret and the pipeline passes the new value, but `terraform plan` reports no changes and the database keeps the old password. Why?
A: Terraform stores the write-only value in state, and it only compares the stored hash on a later apply
B: Terraform cannot diff a write-only value it never stored; only a changed version argument produces a planned update
C: Terraform treats write-only arguments as immutable, so a password change requires destroying and recreating the instance
D: The plan only shows password changes when `sensitive = true` is set on the variable that feeds the write-only argument
K: B
G: ## Why a rotation can be invisible
Terraform sends write-only arguments to the provider on every operation, but it does not keep them in state or in plan files. With no stored prior value, Terraform has nothing to compare against, so a new value alone creates no plan diff.
## The version argument
Providers add a sibling such as `password_wo_version`. Terraform **does** store that number. Increment it in the same change that supplies the new value and the plan shows an update, so the provider applies the new write-only value.
## Practice
Tie the version to the secret's own version metadata (for example a version output of the secrets manager) so rotation in the store drives the update.
W: The version argument is the only trackable signal. Raising it makes the plan include an in-place update, and the provider then uses the current write-only value.
X: A=Stored hash: Terraform keeps no copy or hash of write-only values. That is the reason a version argument exists.
C=Immutable: write-only arguments are updated in place by the provider when the version changes; a replacement is not required for a password change.
D=Sensitive on the variable: sensitivity only changes display. It has nothing to do with whether a change appears in the plan.
T: A write-only argument is invisible to plan diffs, so bump its _version argument to apply a rotated secret.
V: Terraform

@ TF-IEP002 D5 T5.2 applied use-case
S: A configuration reads a Vault secret with an `ephemeral` block that obtains a dynamic credential lease. The security team asks what happens to that lease once the run is over. Which behavior matches the documented lifecycle?
A: Terraform stores the lease ID in state so the next run can renew the same credential
B: Terraform leaves the lease untouched, and Vault revokes the credential when its TTL expires
C: Terraform opens the resource, renews it if needed, and closes it, ending the lease so Vault revokes the credentials
D: Terraform opens the resource at the start of every run and closes it only when `terraform destroy` runs
K: C
G: ## Ephemeral resource lifecycle
An `ephemeral` block has three steps in each run phase:
- **Open**: when Terraform needs the result. For a Vault secret, the Vault provider obtains a lease and returns the secret.
- **Renew**: if the operation outlasts the remote expiration time, Terraform asks the provider to renew, for example by calling Vault's lease renewal API.
- **Close**: after the dependent providers have finished their work in that phase, Terraform closes the resource. For Vault that explicitly ends the lease, so Vault revokes the credentials immediately.
## Why it helps
Credentials are alive only as long as the run needs them and never appear in state, so a leaked state or plan contains no usable secret.
W: Terraform manages the full open, renew and close cycle, and closing the Vault resource ends the lease, which makes the credentials stop working right after the phase completes.
X: A=Lease ID in state: ephemeral resources are never recorded in state or plan files, so nothing carries over to the next run. Each run opens its own new lease.
B=Wait for TTL: Terraform closes the resource and ends the lease explicitly. It does not leave short-lived credentials alive until they time out.
D=Close only at destroy: the resource is closed after the dependent providers finish their work for the current run phase, not at the end of the infrastructure's lifetime.
T: Ephemeral resources are opened, renewed and closed within the run; for Vault, closing ends the lease and revokes the credentials.
V: Terraform

@ TF-IEP002 D5 T5.2 applied troubleshooting
S: One config creates `aws_secretsmanager_secret_version.db` and, in the same run, reads it through `ephemeral "aws_secretsmanager_secret_version"` to feed `password_wo`. On a first plan, the ephemeral block shows no result yet. What does Terraform do?
A: It fails the plan, because ephemeral resources must read objects that already exist before planning starts
B: It reads the secret during plan using the previous run's state, then verifies the value during apply
C: It skips the ephemeral block and sets `password_wo` to null so the database is created without a password
D: It defers opening the ephemeral resource to the apply stage, once the secret version's `secret_id` is known
K: D
G: ## Unknown inputs and ephemeral resources
If an input argument of an ephemeral resource references something Terraform cannot know until apply (such as the ID of an object created in the same run), Terraform **defers** executing the ephemeral resource until the apply stage. The dependency graph still orders it after the secret version is created.
## Why a data source is the wrong tool
A normal `data` block that reads the secret would store `secret_string` in state. The ephemeral read gives the same data without persisting it, and the dependent write-only argument receives it at apply time.
## Pattern from the docs
Generate with an ephemeral `random_password`, store with `secret_string_wo` and `secret_string_wo_version`, read back with an ephemeral secret version, and pass the result to `password_wo` with the version taken from the secret.
W: Deferral lets the first apply create the secret and then read it in the same run, so the database password comes from the secrets manager without ever being stored in state.
X: A=Plan failure: unknown input values do not cause an error; Terraform postpones the work until apply.
B=Previous state: an ephemeral resource is not in state, so there is no previous result to read. It is opened in the run itself.
C=Null password: Terraform does not substitute null for a missing ephemeral result. The write-only argument receives the real value at apply.
T: An ephemeral resource with unknown inputs is deferred to apply, which allows create-then-read of a secret in one run.
V: Terraform

@ TF-IEP002 D5 T5.2 applied definition
S: Which TWO statements about write-only arguments are accurate? (Select TWO)
A: Terraform sends the write-only argument to the provider on every operation, because it has no stored value to compare

@ TF-IEP002 D5 T5.2 applied tradeoff
S: A workspace stores an AWS access key as a Terraform variable marked Sensitive, and the config assigns it to the provider's `access_key`. A reviewer asks for the key to be passed as an environment variable instead. What is the strongest reason?
A: Only environment variables can be marked sensitive in HCP Terraform, so Terraform variables are always stored in readable form
B: Environment variables can be read back through the API by workspace admins, which simplifies key rotation
C: Terraform variables cannot hold strings longer than the maximum length for environment variable values
D: Terraform variables reach the configuration and may leak to logs or state; environment variables stay outside it
K: D
G: ## Where a secret can leak
An HCP Terraform sensitive variable is write-only in the UI and API: nobody can read it back. But a Terraform variable is part of the configuration's inputs. The documentation warns that Terraform runs receive the full text of all Terraform variable values, including sensitive ones, and may print them in logs or state if the configuration sends the value to an output or a resource parameter.
## Environment variables
Provider credentials supplied as environment variables are read by the provider process and are not referenced from the configuration, so there is no path to an output or resource argument. Both categories can be marked sensitive.
## Better still
Use dynamic provider credentials so no long-lived key is stored at all.
W: Keeping credentials out of the configuration's variables removes the chance that a reference carries them into logs, outputs or state, which is why the documentation prefers environment variables when possible.
X: A=Environment variables encrypted: both categories can be marked sensitive and are handled the same way once sensitive. Encryption is not the difference.
B=Readable through the API: sensitive values cannot be read back by anyone, including admins. Only new values can be written.
C=Length limit: no such limit makes Terraform variables unsuitable for credentials. The concern is exposure, not size.
T: Prefer environment variables for provider credentials: Terraform variables travel through the configuration and can reach logs or state.

@ TF-IEP002 D5 T5.2 applied use-case
S: A company self-hosts Terraform Enterprise with no public OIDC metadata endpoint. Cloud providers cannot reach it to verify workload identity tokens, yet runs need short-lived AWS credentials. Which approach fits?
A: Vault-backed dynamic credentials, where Vault authenticates the run's token and issues short-lived AWS credentials
B: Long-lived IAM user keys stored as sensitive environment variables and rotated each quarter by an administrator
C: A shared variable set that holds the AWS root account keys, applied to every workspace in the organization
D: Embedding the AWS access key in the provider block, with the configuration repository set to private
K: A
G: ## Two forms of dynamic credentials
- **Dynamic provider credentials**: the cloud trusts HCP Terraform or Terraform Enterprise's OIDC identity and verifies tokens through the platform's public metadata endpoints.
- **Vault-backed dynamic credentials**: the run's token authenticates to **Vault**, whose secrets engines (AWS, GCP, Azure) generate short-lived credentials.
## Why Vault-backed here
The documentation positions Vault-backed credentials for teams that want a central place to manage cloud credentials and want to avoid exposing the platform's OIDC metadata endpoints publicly. Vault itself must reach `/.well-known/openid-configuration` and `/.well-known/jwks`, but those can stay on a private network.
W: Vault verifies the run's token over the private network and uses its AWS secrets engine to mint short-lived credentials, so no public OIDC endpoint and no long-lived key is needed.
X: B=Static IAM user keys: long-lived keys defeat the goal of short-lived credentials, and stored keys can leak through logs or state.
C=Root keys in a variable set: this gives every workspace full account power, which is the opposite of least privilege, and the keys never expire.
D=Key in the provider block: a private repository is still a repository; the key sits in cleartext in configuration and state. Access control on the repo is not a secrets mechanism.
T: No public OIDC endpoint but need short-lived cloud credentials: use Vault-backed dynamic credentials.
V: Terraform

@ TF-IEP002 D5 T5.3 advanced troubleshooting
S: An AWS role trusts HCP Terraform with the condition `StringLike` on `sub` of `organization:acme:project:*:workspace:*:run_phase:*`. The role grants admin access to a production account. What is the risk?
A: Only the plan phase can assume the role, so applies fail with an authentication error
B: Any workspace in any project of the acme organization can assume the production role
C: The token audience is no longer checked, so a Vault token could assume the AWS role
D: The wildcard makes the role usable by any organization on HCP Terraform, not only acme
K: B
G: ## The subject claim identifies the caller
A workload identity token's `sub` claim reads `organization:ORG:project:PROJECT:workspace:WS:run_phase:PHASE`. The cloud trust policy compares it with a pattern. The narrower the pattern, the fewer workspaces can assume the role.
## What the wildcards allow
With `*` for both project and workspace, every workspace in the `acme` organization, including a sandbox workspace any developer can run, can assume the production role. Use the exact project and workspace, and wildcard only the run phase when plan and apply need the same access.
## Where wildcards hurt more
The documentation notes that unless you match at least the organization name, any organization on HCP Terraform could reach your cloud resources. Here the organization is pinned, so the exposure is every workspace in it.
W: The organization is fixed, but project and workspace are wildcards, so any workspace in acme is trusted by the admin role. A sandbox workspace could act in production.
X: A=Plan-only: the run_phase wildcard matches both plan and apply, so both phases can assume the role.
C=Audience: the audience is a separate condition (aud). A pattern on sub does not remove it, and changing sub does not affect the aud check.
D=Any organization: the pattern starts with organization:acme, so tokens from other organizations do not match. That risk appears only when the organization is not matched.
T: Pin the trust policy to the exact organization, project and workspace; wildcards on those parts let every workspace assume the role.
V: Terraform

@ TF-IEP002 D5 T5.3 applied use-case
S: Plans in a workspace should only read AWS resources, while applies need write access. The workspace uses dynamic credentials. Which configuration implements least privilege?
A: One role with write access, and a policy set that blocks destructive changes during the plan phase
B: One role with read access for both phases, and the pipeline grants write access to a person on approval
C: Two roles with trust policies matching run_phase plan and apply, set through plan and apply role ARN variables
D: One role whose trust policy uses a `run_phase:*` wildcard, restricted by a longer session duration
K: C
G: ## Separate identity per run phase
The `sub` claim ends in `run_phase:plan` or `run_phase:apply`, so a trust policy can tell the phases apart. When different permissions are wanted, create **two roles**, each trusting one phase, and set the environment variables `TFC_AWS_PLAN_ROLE_ARN` and `TFC_AWS_APPLY_ROLE_ARN`. The plan role can be read-only. If the plan variable is absent, `TFC_AWS_RUN_ROLE_ARN` is used.
## Why a wildcard is not enough
