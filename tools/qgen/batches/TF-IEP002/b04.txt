@ TF-IEP002 D3 T3.1 advanced tradeoff
S: One root module holds networking, a database tier and 40 application services. Every plan takes 25 minutes and a typo in a service change once put the database in the same plan. Which restructuring best addresses both problems?
A: Split it into configurations along ownership and change-frequency lines, each with its own state, sharing values via outputs
B: Keep one configuration and always run plans with -target for the service being changed, so only that service is refreshed and planned
C: Convert the services to CLI workspaces inside the same directory so that each service gets a separate state file under the one backend
D: Raise -parallelism to a much higher value so the graph walk finishes sooner, and keep a single state for easier cross-references
K: A
G: ## Why large root modules hurt
A configuration and its state form one unit: every plan refreshes every resource in the state and every apply can touch any of them. Two costs follow.
- **Time**: refresh and graph walking grow with resource count, and API rate limits make raising concurrency a poor fix.
- **Blast radius**: one mistake in a frequently changed part can show up in the same plan as a rarely changed, critical part such as a database.
## What the docs recommend
The `-target` documentation says to prefer breaking large configurations into several smaller ones that can be applied independently, using data sources to read objects from other configurations. Typical boundaries are ownership (network team, platform team, app team) and change frequency (foundation changes rarely, services change daily).
W: Splitting by ownership and change frequency gives each part its own state, so plans refresh only that part, a service change cannot include database changes, and access can be granted per configuration. Shared values flow through published outputs or data sources.
X: B=Routine -target: the plan documentation reserves -target for exceptional cases; used routinely it hides drift and leaves the state unrelated to the configuration, and the single state still holds everything.
C=CLI workspaces: workspaces are copies of the same configuration with different state, not separate components. They would multiply the same 40 services, not divide the system, and all share one backend and credentials.
D=Higher parallelism: concurrency only helps up to provider API rate limits, and it does nothing for blast radius because one state and one plan still cover everything.
T: Split big configurations at ownership and change-frequency boundaries; -target and workspaces do not decompose a system.

@ TF-IEP002 D3 T3.1 applied comparison
S: A network configuration exposes its VPC ID as a root output, and an application configuration in another state reads it with a terraform_remote_state data source. A security reviewer objects. Which concern is accurate?
A: The consumer needs read access to the entire state snapshot of the network configuration, which may hold sensitive values beyond the one output
B: The data source copies the network outputs into the application state, so any later change to the output is never seen by the consumer
C: The data source can only read outputs from a state stored locally, so the setup silently fails once the network state is moved to a remote backend
D: The data source takes a lock on the network state during the read, so every application plan blocks all network changes
K: A
G: ## What terraform_remote_state exposes
The data source reads the latest state snapshot from a backend and returns only the root module **output values**. But to read it, the caller's credentials need access to the whole state file, and state often contains secrets such as generated passwords or connection strings.
## Alternatives
- Publish the value to a dedicated store (a parameter store, DNS record, key/value store) with its own access controls, then read it with a matching data source.
- Look the object up by tags with the provider's data source.
- In HCP Terraform, the `tfe_outputs` data source is recommended because it does not require full access to workspace state.
W: The data source exposes only outputs, but the consumer must be allowed to read the full state snapshot. That access exposes any sensitive data in state, which is why explicitly published data or tfe_outputs is recommended.
X: B=Copied outputs: the data source reads the latest snapshot each time it is evaluated. A changed output appears at the next plan of the consumer, nothing is stored permanently in its state.
C=Local only: the data source is designed for remote backends such as S3, azurerm or HCP Terraform; it takes the backend type in its configuration.
D=Locking: reading a snapshot does not hold the producing configuration's lock, so consumer plans do not block producer changes.
T: terraform_remote_state returns only outputs but needs access to the whole state; prefer published data or tfe_outputs for sensitive setups.

@ TF-IEP002 D3 T3.1 advanced troubleshooting
S: A team uses CLI workspaces named dev and prod with one S3 backend. Auditors find that engineers with dev credentials can run terraform workspace select prod and apply. What is the underlying design flaw?
A: CLI workspaces within a directory share one backend and its credentials, so they do not provide access separation between environments
B: The prod workspace was created with terraform workspace new, which grants every user of the backend write access to it by default
C: CLI workspaces store state in the .terraform directory on each laptop, which any engineer can overwrite with a copy of dev state
D: The default workspace is always mapped to production, and selecting any other workspace therefore inherits its permissions
K: A
G: ## What a CLI workspace is
A CLI workspace is a separate instance of state inside the same working directory and backend. The documentation describes workspaces as technically equivalent to renaming the state file. The same configuration, backend settings and credentials are used for all of them.
## Consequence for environments
The docs say that organizations commonly want strong separation between deployments for different stages or teams, where each backend often has different credentials and access controls. CLI workspaces are not a suitable isolation mechanism for that. The alternative is one small root module per environment, each instantiating shared modules with its own backend.
W: Because both workspaces live in one backend reachable with one credential set, selecting prod needs no extra permission. Separate configurations with separate backends and credentials are the documented alternative.
X: B=Default access: workspace creation grants nothing; access comes from the backend and cloud IAM, which are shared by all workspaces here.
C=State on laptops: with a remote backend, workspace states live in the backend. Only the selected workspace name is cached locally in .terraform.
D=Default maps to production: the default workspace is just the one that exists in every directory; it has no special link to production and no permission model.
T: CLI workspaces share backend and credentials, so use separate configurations and backends when environments need different access.

@ TF-IEP002 D3 T3.1 advanced use-case
S: A shared VPC was created in the monolith state, and it must move to a new network configuration without destroying it. Which sequence achieves this?
A: Add an import block in the new configuration for the VPC, apply it, then drop the object from the old state without destroying it
B: Delete the VPC resource block from the old configuration and apply, then recreate it in the new configuration under the same name
C: Copy terraform.tfstate into the new directory and delete the VPC block from the old one, which makes the new state authoritative
D: Add replace_triggered_by in the new configuration, which transfers the VPC object from the old state during the next plan
K: A
G: ## Moving ownership between states
Terraform ties a real object to exactly one state entry. Moving ownership means: first make the destination state adopt the object, then make the source state forget it, and never let both plan changes to it at once.
- **Adopt**: an `import` block (`to` = new resource address, `id` = the cloud ID) with a matching `resource` block in the destination.
- **Forget**: a `removed` block with `lifecycle { destroy = false }` in the source, or `terraform state rm`. Simply deleting the resource block would plan a destroy.
## Ordering
Import first, then remove from the source, so the object always has an owner and nothing is destroyed.
W: Importing into the new state gives it ownership, and removing the object from the old state without destroying (removed block with destroy set to false) stops the old configuration from managing or deleting it.
X: B=Delete and recreate: deleting the block makes the old apply destroy the real VPC, taking every dependent resource with it; the recreation is a new object.
C=Copying the state file: it would hold the whole monolith, so both states claim the same objects, and each configuration would plan to destroy what the other manages.
D=replace_triggered_by: it only forces replacement of a resource when another changes. It cannot transfer objects between states.
T: Move an object between states by importing it into the new one and removing it, without destroy, from the old one.

@ TF-IEP002 D3 T3.1 advanced use-case
S: Which TWO situations justify splitting a Terraform project into separate configurations with separate states? (Select TWO)
A: A team owns the shared network and must grant others only read access to its outputs, never write access to its state
B: Plan times are growing and the stable foundation resources are refreshed on every application release for no reason
C: Two engineers want to avoid editing the same file, so the project is divided into a main.tf and a network.tf per person
D: A module call is repeated three times, so each repetition must be stored in its own state to keep names unique
E: A variable has become long, so its default is moved to a separate state to shorten the code
K: A,B
G: ## What a state boundary buys
A separate state means a separate plan scope, lock, access policy and apply history. Splitting is a runtime and governance decision, not a file layout decision.
- **Different owners or permissions**: each configuration can have its own backend access.
- **Different change rates**: stable foundations are not refreshed on each application release.
- **Smaller blast radius**: a failed or mistaken apply affects only that scope.
Splitting adds coupling work (outputs, remote state, ordering), so it is not free.
W: A=Ownership and access: a separate state and backend lets the network team control who can modify it and share only outputs.
B=Change frequency: the stable foundation does not have to be refreshed and planned with each release when it has its own state.
X: C=Files per engineer: files in one directory belong to the same module and state; splitting files changes nothing about plans or locking.
D=Repeated module calls: repeated calls with different names or for_each keys coexist in one state without conflict, and splitting them is not needed for naming.
E=Long variable: code readability is unrelated to state boundaries, and defaults cannot live in a state.
T: Split states for ownership, access and change-rate reasons, not for file organisation or naming.

@ TF-IEP002 D3 T3.2 advanced use-case
S: An instance is healthy in the console but its disk is corrupted and the team wants a fresh one with the same configuration. Which command plans exactly that without changing the code?
A: terraform plan -replace=aws_instance.web
B: terraform plan -refresh-only
C: terraform plan -target=aws_instance.web
D: terraform plan -destroy
K: A
G: ## Forcing replacement
`-replace=ADDRESS` plans a **replace** action (destroy and create, or create then destroy if create_before_destroy is set) for that instance even when the configuration and refreshed state show no difference. It is the successor of `terraform taint` (docs: use taint before v0.15.2) and fits immutable-infrastructure patterns when a remote object is degraded.
## Why the others differ
- `-refresh-only` updates state and outputs to match reality and never changes infrastructure.
- `-target` only narrows scope; with no diff it plans nothing.
- `-destroy` plans removal of everything, and cannot combine with `-replace`.
W: -replace tells Terraform to plan replacement of the specified instance regardless of configuration drift, which gives a fresh resource with identical configuration.
X: B=-refresh-only: only reconciles state with reality, so the corrupted disk, which Terraform cannot see, changes nothing.
C=-target: restricts the scope, but a resource with no differences yields no action, so nothing is replaced.
D=-destroy: removes all managed resources, not one instance, and it cannot be used together with -replace.
T: Use plan -replace=ADDRESS to rebuild one healthy-looking resource without editing code.

@ TF-IEP002 D3 T3.3 advanced troubleshooting
S: During apply, 30 resources are planned. After 12 succeed, the 13th fails with a provider API error and Terraform stops. What is the state of the project?

D=Everything tainted: tainting is per resource and applies only where creation failed partway, not to the whole configuration.
T: Apply is not transactional: successes stay in state, and the next plan finishes the rest.

@ TF-IEP002 D3 T3.5 advanced use-case
S: A load balancer name must be unique, and a change forces replacement of the load balancer that a listener depends on. Which setting gives zero-downtime replacement, and what happens to the listener?
A: create_before_destroy on the load balancer; Terraform carries the same ordering to the listener that depends on it
B: prevent_destroy on the load balancer; the dependent listener is updated in place while the old load balancer stays
C: ignore_changes on the load balancer name; the listener keeps pointing at the old load balancer until replaced manually
D: replace_triggered_by on the listener; the listener is created first and the load balancer after
K: A
G: ## Replacement order
By default Terraform destroys the old object and then creates the new one. With `create_before_destroy = true` it creates the replacement first and destroys the old one afterwards, so there is no gap, provided the two can exist at the same time (names must differ, for example through a `name_prefix` or random suffix).
## Propagation
Terraform applies create_before_destroy to dependencies too. If resource A has it and depends on B, B implicitly gets it and the state records it; you cannot set it to false on B because that would form a dependency cycle. When the dependent is replaced, the same ordering applies.
W: create_before_destroy builds the new load balancer before removing the old one, and the replacement order is carried through the dependency chain so the listener is replaced consistently.
X: B=prevent_destroy: it rejects plans that would destroy the object with an error; it does not produce a replacement.
C=ignore_changes on name: the name change would not be planned, so the load balancer would not be replaced at all, which defeats the intent.
D=replace_triggered_by: it forces replacement when another resource changes; it does not alter the order of create and destroy.
T: create_before_destroy replaces without a gap and propagates to dependencies; the name must allow two objects at once.
