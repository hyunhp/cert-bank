@ TF-IEP002 D1 T1.5 advanced use-case
S: A platform team keeps access data as `var.team_roles = { data = ["reader", "analyst"], ops = ["admin", "reader"] }`. The IAM module, owned by another team and frozen for this quarter, expects a map from each role name to the list of teams that hold it. The map must be derived automatically so that adding a team needs no second edit. The author writes `transpose(var.team_roles)`. Which value does the frozen module receive?
A: `{ admin = ["ops"], analyst = ["data"], reader = ["data", "ops"] }`, a map keyed by role with the teams for each role in a list
B: `{ data = ["analyst", "reader"], ops = ["admin", "reader"] }`, the original team keys with each team's list of roles sorted lexically
C: `{ admin = "ops", analyst = "data", reader = "ops" }`, a map of single strings in which the last team listed wins for a shared role
D: An error, because `transpose` requires every role string to appear in only one list, and `reader` appears under both of the teams
K: A
G: ## What transpose does
`transpose` takes a **map of lists of strings** and swaps keys and values: every string found in any list becomes a key of the result, and its value is the list of original keys whose lists contained it.
## Working the example
- `data` holds `reader` and `analyst`; `ops` holds `admin` and `reader`.
- `admin` appears only under `ops`, so it maps to `["ops"]`.
- `analyst` appears only under `data`, so it maps to `["data"]`.
- `reader` appears under both, so it maps to `["data", "ops"]`.
A string that appears in several lists is the normal case: collecting those keys into one list is exactly what the function is for. The documentation example `transpose({"a" = ["1", "2"], "b" = ["2", "3"]})` returns `"2" = ["a", "b"]` for the same reason.
## Why this suits the constraint
Because the inverted map is computed from `var.team_roles`, a new team added to that one variable automatically appears under each of its roles, so the frozen module needs no second edit.
W: Role-keyed map of team lists: transpose turns each role string into a key and lists every team whose list contained it, so `reader` maps to both teams.
X: B=Original keys sorted: this is just the input with each list sorted. transpose changes which side is the key; it does not keep team names as keys.
C=Map of single strings: transpose always returns a map of lists of strings, so a role held by two teams keeps both rather than letting one overwrite the other.
D=Error on repeats: repeated strings are expected input; they are grouped under one key. transpose does not require the lists to be disjoint.
T: transpose inverts a map of lists of strings, grouping every original key under each string it contained.

@ TF-IEP002 D1 T1.5 advanced use-case
S: Security groups in the target account accept at most 60 inbound rules each, a quota the cloud team will not raise. A module receives 130 partner CIDR blocks in `var.partner_cidrs` and must spread them over as few groups as possible, with the number of groups following the list size automatically. The author writes `locals { batches = chunklist(var.partner_cidrs, 60) }` and sets `count = length(local.batches)` on the group. What does the first plan create?
A: Three security groups: the first two take 60 rules each, and the third takes the remaining 10 CIDR blocks from the end of the list
B: Two security groups of 65 rules each, because `chunklist` divides the list into equally sized chunks that stay close to the given limit
C: Three security groups holding 44, 43 and 43 rules, because `chunklist` balances the remainder evenly across every chunk that it returns
D: An error, because `chunklist` requires the length of the list to be an exact multiple of the chunk size passed as its second argument
K: A
G: ## How chunklist splits a list
`chunklist(list, chunk_size)` cuts a list into consecutive pieces of **at most** `chunk_size` elements and returns a list of lists. It fills each chunk in order; only the last chunk can be shorter. The documentation example `chunklist(["a", "b", "c", "d", "e"], 2)` returns `[["a", "b"], ["c", "d"], ["e"]]`.
## Working the numbers
- 130 / 60 = 2 full chunks (120 elements) with 10 left over.
- The result is three lists of 60, 60 and 10 elements, so `length(local.batches)` is `3`.
- Each group instance can then use `local.batches[count.index]` as its rule source.
## A caveat worth knowing
Because chunks are positional, inserting a CIDR near the start of the list shifts later entries into different chunks, so several groups change at once. Sorting the input (or keying groups another way) keeps changes small.
W: Two full chunks and a short tail: chunklist fills chunks of the given size in order and leaves the remainder in a final, shorter chunk, so 130 entries make 60, 60 and 10.
X: B=Equal halves: chunklist never resizes chunks to be equal. The second argument is the exact size of every chunk except possibly the last.
C=Balanced remainder: there is no balancing step. Elements go into chunks in order until each reaches the chunk size.
D=Exact multiple required: a list that does not divide evenly is fine; the last chunk simply holds the leftover elements.
T: chunklist returns consecutive chunks of the given size and puts any remainder in a shorter final chunk.

@ TF-IEP002 D1 T1.6 advanced troubleshooting
S: A network module receives `var.subnets`, a map such as `{ app-a = { az = "eu-west-1a", id = "subnet-1" }, db-a = { az = "eu-west-1a", id = "subnet-2" } }`. A load balancer module needs one list of subnet IDs per availability zone, and adding a subnet must not require code changes. The author writes `{ for k, s in var.subnets : s.az => s.id }`, and planning fails with a duplicate object key error. Which TWO expressions fix it while keeping every subnet? (Select TWO)
A: `{ for k, s in var.subnets : s.az => s.id... }`, which puts the for expression in grouping mode and returns a list of IDs for each zone key
B: `{ for k, s in var.subnets : s.az => s.id if s.az != "" }`, which filters the input entries so that only one subnet remains for each zone key
C: `merge([for k, s in var.subnets : { (s.az) = s.id }]...)`, which merges one single-entry map per subnet and collects every ID under its zone
D: `zipmap(values(var.subnets)[*].az, values(var.subnets)[*].id)`, which pairs zones with IDs and gathers the IDs of repeated zones into lists
E: `{ for z in distinct([for s in values(var.subnets) : s.az]) : z => [for s in values(var.subnets) : s.id if s.az == z] }`
K: A,E
G: ## Why the original expression fails
A `for` expression that builds an object needs **unique keys**. Two subnets in `eu-west-1a` produce the key `eu-west-1a` twice, so Terraform stops with a duplicate key error instead of silently dropping one.
## Two ways to group
- **Grouping mode**: put `...` after the value expression. Terraform then collects every value for a key into a list, giving `{ "eu-west-1a" = ["subnet-1", "subnet-2"] }`. The documentation shows the same pattern to invert users by role.
- **Distinct keys, nested for**: first build the list of unique zones with `distinct`, then for each zone collect the IDs whose `az` matches. The result has the same shape.
## What loses data
Functions that build maps from pairs keep **one** value per key: `merge` lets later maps override earlier ones, and `zipmap` uses the value with the highest index when a key repeats. Both hide subnets instead of grouping them.
W: A=Grouping mode: the trailing `...` tells Terraform that keys may repeat and makes each value a list, so both subnets stay under eu-west-1a.
E=Distinct zones with a nested for: each unique zone becomes one key, and the inner for collects every subnet ID in that zone, so nothing is lost and new subnets are picked up automatically.
X: B=Filter clause: the `if` condition removes entries that fail it; it never makes keys unique, and here every subnet passes the filter, so the duplicate error stays.
C=merge of single-entry maps: merge keeps the last value for a repeated key, so one of the two eu-west-1a subnet IDs is overwritten rather than collected.
D=zipmap: when a key repeats, zipmap keeps the value with the highest index, so it returns one ID per zone and drops the rest.
T: To collect several values under one key, use grouping mode (`...`) or a distinct-keys outer loop; merge and zipmap keep only one value per key.

@ TF-IEP002 D1 T1.7 advanced troubleshooting
S: A shared module `modules/audit` checks a role's account with `provider::aws::arn_parse(var.role_arn).account_id`. Its resources use the default AWS provider configuration inherited from the root, and the module has no `terraform` block of its own. The root module declares `hashicorp/aws` in `required_providers`. `terraform validate` reports an unknown provider function inside the module. The check must stay inside the module. What fixes the error?
A: Add a `terraform { required_providers { aws = { source = "hashicorp/aws" } } }` block to the module, so the `aws` local name resolves there
B: Pass `providers = { aws = aws }` in the module call, because provider functions only exist for provider configurations that are passed explicitly
C: Rewrite the call as `provider::hashicorp::aws::arn_parse(...)`, because function calls in child modules must spell out the full provider source address
D: Add a `provider "aws"` block inside the module, because a provider function needs a provider configuration declared in the same module that calls it
K: A
G: ## How provider-defined functions are named
Providers can ship functions. A call uses the form `provider::<local-name>::<function>(...)`, and the documentation states that `<local-name>` must correspond to an entry in the **`required_providers` block** of the module making the call.
## Why the child module fails
- Each module resolves local names on its own. The root's `required_providers` entry does not cover the child.
- A module can manage `aws_*` resources without declaring the provider, because Terraform infers `hashicorp/aws` for them, but function calls look up the local name in the module's own requirements.
- Adding `required_providers` with `aws = { source = "hashicorp/aws" }` (ideally with a minimum version that has the function) makes `provider::aws::...` resolvable while the module still receives the root's default configuration.
## What does not matter
Function calls do not need a configured `provider` block in the module, and the call syntax always uses the local name, never the full source address.
W: required_providers in the module: declaring `aws` as a local name inside the module is what lets `provider::aws::arn_parse` resolve there, and the inherited default configuration keeps working unchanged.
X: B=Explicit providers map: passing configurations decides which provider configuration the resources use; it does not declare a local name in the module's requirements, which is what the function lookup needs.
C=Full source in the call: provider function syntax is `provider::<local-name>::<function>`; there is no form that embeds the namespace and type.
D=provider block in the module: a child module does not need its own configuration to call a function, and putting provider blocks in shared modules is discouraged because it blocks count, for_each and depends_on on the module call.
T: A module that calls `provider::<name>::...` must list `<name>` in its own required_providers block.

@ TF-IEP002 D1 T1.6 advanced use-case
S: A module declares `variable "site" { type = object({ name = string, cdn = optional(object({ enabled = optional(bool, true), ttl = optional(number, 300) }), {}) }) }` and creates its CDN only when `var.site.cdn.enabled` is true. Callers must not need extra arguments in the common case. One caller passes `{ name = "docs" }` and another passes `{ name = "blog", cdn = { ttl = 60 } }`. What does each caller get?
A: Both get a CDN: docs uses the nested default `ttl = 300`, and blog keeps `ttl = 60` with `enabled` defaulted to true
B: Only blog gets a CDN, because an omitted `cdn` becomes `{}` and nested defaults are never applied to a value that came from an outer default
C: Only docs gets a CDN, because passing any `cdn` attribute replaces the whole default object and leaves `enabled` set to null for blog
D: Neither gets a CDN until `enabled` is set explicitly, because optional attributes nested inside an optional object always default to null
K: A
G: ## Optional attributes with defaults
In an object type constraint, `optional(type, default)` lets a caller omit an attribute; Terraform inserts the default. A non-null default is also used when the caller sets the attribute to `null`.
## Defaults are applied top-down
The documentation states that Terraform applies object attribute defaults **top-down** in nested types: it first applies the default given in the outer `optional` modifier, then applies the nested defaults to that attribute.
## Working both callers
- `docs` omits `cdn`, so it first becomes `{}` (the outer default). The nested defaults then fill in `enabled = true` and `ttl = 300`.
- `blog` passes `cdn = { ttl = 60 }`. `enabled` is missing, so the nested default `true` is inserted, and `ttl` keeps 60.
Both objects end with `enabled = true`, so both callers get a CDN without writing extra arguments.
W: Both get a CDN: the outer default `{}` is applied first and the nested defaults then fill `enabled` and `ttl`; a partially supplied object also receives defaults for its missing attributes.
X: B=Outer default skips nested ones: Terraform applies the outer default first and the nested defaults after it, so `{}` becomes a complete object.
C=Partial object loses defaults: optional attributes are filled per attribute, so supplying only `ttl` still gives `enabled = true`.
D=Nested optionals default to null: only attributes without a declared default become null; here both nested attributes declare non-null defaults.
T: Nested optional defaults are applied top-down: the outer default first, then the inner defaults fill every missing attribute.

@ TF-IEP002 D2 T2.1 advanced use-case
S: A team stores state with `backend "s3" { bucket = "acme-tf" key = "app/terraform.tfstate" use_lockfile = true }` and uses the CLI workspaces dev and prod. Security requires the prod pipeline role to reach only the prod state and its lock in that bucket, and the backend block may not change this sprint. Besides `s3:ListBucket` on the bucket, which object ARNs must the role's object-level statement cover?
A: `arn:aws:s3:::acme-tf/env:/prod/app/terraform.tfstate` and the same path ending in `.tflock`, covering state reads, writes and lock handling
B: `arn:aws:s3:::acme-tf/app/prod/terraform.tfstate` and the same path ending in `.tflock`, because the workspace name is inserted just before the file name
C: `arn:aws:s3:::acme-tf/app/terraform.tfstate` only, because the backend keeps every workspace as a separate object version under the configured key
D: `arn:aws:s3:::acme-tf/prod/app/terraform.tfstate` and the same path ending in `.tflock`, because the default workspace prefix is the workspace name itself
K: A
G: ## Where the S3 backend writes workspace state
- The `default` workspace uses the `key` exactly: `app/terraform.tfstate`.
- Every other workspace uses `<workspace_key_prefix>/<workspace_name>/<key>`.
- `workspace_key_prefix` defaults to `env:`, so workspace `prod` lives at `env:/prod/app/terraform.tfstate`.
## What locking adds
With `use_lockfile = true`, Terraform creates a lock object next to the state with `.tflock` appended. The documentation lists `s3:GetObject`, `s3:PutObject` and `s3:DeleteObject` on that lock file, for example `arn:aws:s3:::mybucket/<workspace_key_prefix>/*/path/to/my/key.tflock`.
## A least-privilege prod role
- `s3:ListBucket` on `arn:aws:s3:::acme-tf`.
- `s3:GetObject` and `s3:PutObject` on `arn:aws:s3:::acme-tf/env:/prod/app/terraform.tfstate`.
- `s3:GetObject`, `s3:PutObject` and `s3:DeleteObject` on `arn:aws:s3:::acme-tf/env:/prod/app/terraform.tfstate.tflock`.
Nothing under `env:/dev/` is granted, so the role cannot read or lock dev state.
W: env:/prod path plus lock: non-default workspaces live under the `env:` prefix followed by the workspace name and the key, and the lock file is that path with `.tflock` appended.
X: B=Workspace before file name: the backend does not splice the workspace into the key; it prefixes the whole key with `env:/<workspace>/`.
C=Object versions: workspaces are separate objects, not versions of one object. S3 versioning protects history but does not separate workspaces.
D=Prefix equals workspace name: the default prefix is `env:`, so the path starts with `env:/prod/`, not `prod/`, unless `workspace_key_prefix` is changed.
T: In the S3 backend, workspace state lives at `env:/<workspace>/<key>` by default, and its lock is the same path plus `.tflock`.

@ TF-IEP002 D2 T2.1 advanced use-case
S: Eight pipelines share an `s3` backend that locks with `dynamodb_table`. Over six weeks the platform team moves them to Terraform 1.15, but two legacy pipelines must stay on Terraform 1.9 until the final week. Upgraded pipelines must start using S3 lock files as soon as they move, no run may write state without a lock that every other pipeline honours, and the table is retired at the end. Which backend setting should upgraded pipelines use during the transition?
A: Keep `dynamodb_table` and also set `use_lockfile = true`, so upgraded runs take both locks while legacy runs still see the DynamoDB lock
B: Replace `dynamodb_table` with `use_lockfile = true` right away, since older releases detect the `.tflock` object in the bucket and wait for it
C: Keep only `dynamodb_table` for all eight pipelines until the final week, then switch everyone to `use_lockfile = true` in a single change
D: Give the legacy pipelines a separate `key` until they upgrade, so the two lock mechanisms never guard the same state object at the same time
K: A
G: ## Two locking mechanisms in the S3 backend
- `use_lockfile = true` writes a `.tflock` object next to the state in the bucket. This is the current mechanism.
- `dynamodb_table` stores the lock in a DynamoDB item. The documentation marks DynamoDB locking as **deprecated**, to be removed in a future minor version.
## Running both during a migration
The documentation says the S3 and DynamoDB arguments **can be configured simultaneously** to support migration from older Terraform versions that only support DynamoDB locking. A run configured with both acquires both locks.
## Applying it to mixed versions
- Terraform 1.9 does not know `use_lockfile`; it only takes and checks the DynamoDB lock.
- An upgraded run with both settings takes the DynamoDB lock too, so a legacy run that holds it blocks the upgraded run, and the reverse.
- When the last legacy pipeline upgrades, remove `dynamodb_table` everywhere and delete the table.
W: Both settings together: dual locking keeps a lock that legacy releases honour while the upgraded runs already use S3 lock files, which is the documented migration path.
X: B=Lock file only: a release without lock file support never checks the `.tflock` object, so legacy runs could write state while an upgraded run holds only the S3 lock.
C=Wait until the end: it keeps everyone safe but breaks the requirement that upgraded pipelines use S3 lock files as soon as they move.
D=Separate key: a different key is a different state, so the legacy pipelines would no longer manage the same infrastructure state at all.
T: To migrate from DynamoDB to S3 lock files with mixed Terraform versions, configure both arguments until every pipeline is upgraded.

@ TF-IEP002 D2 T2.2 advanced use-case
S: During an incident an engineer raised `instance_type` of `aws_instance.api` from `m5.large` to `m5.xlarge` in the console; the configuration still says `m5.large`. Management wants the larger size kept permanently, recorded through a reviewed pull request, and no restart or stop of the instance caused by any later Terraform run. The team runs `terraform apply -refresh-only` and approves it. Which TWO statements describe what happens next? (Select TWO)
A: State now records `m5.xlarge`, but the next normal plan still proposes changing the instance back to `m5.large`
B: The refresh-only apply also rewrites the configuration file, so `instance_type` in the code matches the value read from the console
C: The drift is closed only once the pull request sets `m5.xlarge` in the configuration, after which a normal plan reports no changes
D: The refresh-only apply marks `instance_type` as ignored in state, so later plans skip that attribute until a new refresh happens
E: Approving the refresh-only plan restarts the instance once, so the provider can confirm the new size before writing it to state
K: A,C
G: ## What refresh-only mode does
`terraform plan -refresh-only` and `terraform apply -refresh-only` compare state with the real infrastructure and propose **updating state only**. Approving it writes the observed values into state; it changes no infrastructure and never touches configuration files.
## Why that is not the end of the story
After the refresh-only apply, state says `m5.xlarge` but the configuration still says `m5.large`. A normal plan compares configuration with state, sees a difference, and proposes an in-place update back to `m5.large` (which, for an instance type, means a stop and start).
## Accepting drift permanently
To keep an out-of-band change, update the configuration to the observed value. Once the pull request sets `m5.xlarge`, configuration, state and reality agree and the plan shows no changes. The refresh-only step is useful to record reality and review the drift, but the configuration change is what makes it permanent.
W: A=State updated, config unchanged: refresh-only only syncs state, so the next normal plan sees the configuration's `m5.large` and proposes reverting the drift.
C=Configuration change closes it: once the code declares `m5.xlarge`, the desired value matches state and reality, so the plan is empty and no restart happens.
X: B=Rewrites configuration: Terraform never edits `.tf` files during refresh or apply; only the team can change the declared value.
D=Marks attribute ignored: ignoring attributes is done with `lifecycle { ignore_changes }` in configuration. A refresh-only apply records values; it does not add ignore rules to state.
E=Restarts the instance: refresh-only operations read infrastructure and write state; they make no changes to the instance.
T: Refresh-only accepts drift into state, but only a matching configuration change stops the next plan from reverting it.

@ TF-IEP002 D2 T2.3 advanced troubleshooting
S: A root module calls `module "app"` with `depends_on = [module.network]`. Inside `app`, `data "aws_ami" "base"` selects an image used by several instances. Whenever anything in `network` changes, the plan shows the AMI data as known after apply and proposes replacing every instance, although no new image exists. The team must keep `app` ordered after the subnets it uses, and a genuinely new AMI must still replace instances. What should they change?
A: Remove the module-level `depends_on` and pass `module.network.subnet_ids` into `app` as an input, so real references order the work
B: Add `lifecycle { ignore_changes = [ami] }` to the instances, so a deferred data source read can no longer produce a replacement plan for them
C: Move the `depends_on` from the module call onto the `data "aws_ami"` block inside `app`, so only that one lookup waits for the network module
D: Run `terraform apply -target=module.network` before every full apply, so the AMI lookup is read after the network changes have finished
K: A
G: ## Why module-level depends_on is costly
`depends_on` on a module call makes **every** resource and data source in that module wait for **all** actions on the dependency. The documentation warns that this produces more conservative plans: Terraform treats more values as `(known after apply)` because it cannot be sure what the upstream change will do, and this is "especially likely when you use depends_on for modules".
## What happens here
- `network` has a pending change, so every data source in `app` must wait until apply.
- `data.aws_ami.base` is read at apply time, so its `id` is unknown during the plan.
- Each instance's `ami` argument becomes unknown, and because `ami` forces replacement, Terraform plans to replace every instance.
## The fix: depend on data, not on the whole module
Pass the values `app` really needs (subnet IDs) as module inputs. References create precise dependency edges: instances still wait for the subnets, but the AMI lookup is independent and is read during the plan, so replacements happen only when the image really changes.
W: Pass outputs as inputs: a reference to `module.network.subnet_ids` orders the instances after the subnets without forcing every data source in `app` to defer to apply.
X: B=ignore_changes on ami: it suppresses the false replacements but also hides a genuinely new AMI, which breaks the requirement that a new image still replaces instances.
C=depends_on on the data block: the data source would still wait for every pending change in `network`, so it is still read at apply time and still shows an unknown image ID.
D=-target first: the documentation reserves targeting for exceptional cases, and it turns every rollout into two partial applies instead of fixing the dependency design.
T: Prefer references over module-level depends_on; module dependencies defer data sources and cause needless known-after-apply replacements.

@ TF-IEP002 D2 T2.4 advanced tradeoff
S: A company runs dev, staging and prod on Terraform 1.12 with versioned S3 state and is moving to 1.15. Change policy says prod must be able to return to the 1.12 binary at any point during a ten-day staging soak, and auditors reject hand-edited or rolled-back state files. Shared modules will not use any 1.15 language feature until the soak ends. Which rollout meets the policy?
