@ TF-IEP002 D7 T7.1 applied troubleshooting
S: A workspace is set to Local execution mode. Cloud credentials live in a global variable set that applies to every workspace, yet `terraform plan` on an engineer's laptop fails with "no valid credential sources". What explains this?
A: Global variable sets reach only workspaces whose latest run was started from a VCS commit, and a laptop run does not qualify
B: The variable set must be marked as a priority set before local runs can read environment variables stored in it
C: In Local mode the run happens on the workstation, and HCP Terraform does not evaluate workspace variables or variable sets there
D: The workspace needs a team token before HCP Terraform will inject variable set values into any run started with the CLI
K: C
G: ## Execution modes decide where a run happens
A workspace has an execution mode that says which machine runs Terraform:
- **Remote**: HCP Terraform runs the plan and apply on its own disposable workers. Variables, variable sets, policies, cost estimation, notifications and VCS integration all work.
- **Agent**: the same run lifecycle, but a `tfc-agent` in your own network executes the work.
- **Local**: Terraform runs on your machine and the workspace only stores state.
- **Project Default**: the workspace inherits the mode set on its project.
## What Local mode gives up
Because the Terraform process is on the workstation, HCP Terraform has nothing to inject into it. Workspace variables and variable sets are **not evaluated**, so credentials must come from the engineer's own environment, or the workspace must move to Remote or Agent mode.
W: Local execution keeps the run outside HCP Terraform, so variable sets (global or otherwise) are never evaluated. The fix is to supply credentials locally or switch the execution mode to Remote or Agent.
X: A=VCS-only reach: scope decides which workspaces receive a variable set, not how a run started. A global set targets every workspace, and what blocks it here is the execution mode.
B=Priority flag: the priority setting only decides which value wins when keys conflict. It does not make values available to a run that HCP Terraform does not control.
D=Team token: a team token authenticates API calls. It plays no part in variable injection, and no token makes Local mode evaluate variables.
T: In Local execution mode HCP Terraform does not evaluate workspace variables or variable sets, so the workstation must supply credentials.

@ TF-IEP002 D7 T7.1 applied use-case
S: A company must provision vSphere resources in a data center that accepts no inbound connections from the internet. Which design lets HCP Terraform runs reach that environment?
A: Open an inbound HTTPS port on the data center firewall for HCP Terraform's published IP ranges so the runs can connect to vCenter
B: Run HCP Terraform agents in the data center, put the workspace in Agent execution mode, and allow only outbound connections to HCP Terraform
C: Switch the workspace to Local execution mode and give every engineer a VPN account so they can start each run from a laptop
D: Build a site-to-site VPN from HCP Terraform's managed workers into the data center network and keep the workspace in Remote mode
K: B
G: ## Agents bring execution to the private network
An **HCP Terraform agent** (`tfc-agent`) is a lightweight process you run inside a private network. It belongs to an **agent pool** and polls HCP Terraform for work. A workspace whose execution mode is **Agent** sends its plan and apply jobs to an available agent in the chosen pool.
## Why this fits a closed network
- The agent only needs **outbound** TCP connections: to the HCP Terraform APIs, to the module registry, to `releases.hashicorp.com` for Terraform binaries, and to the providers' own APIs (here vCenter, which is local).
- No inbound firewall rule is needed, so the data center stays closed.
- Runs keep every HCP Terraform feature: variables, policies, run tasks, notifications and the run UI.
W: Agent execution moves the Terraform process next to vCenter while the agent initiates the connection outward. No inbound exposure is required and the full run workflow remains.
X: A=Inbound firewall rule: this reverses the requirement, because the data center accepts no inbound traffic. Agents exist so that HCP Terraform never has to connect in.
C=Local mode with laptops: it works technically but gives up remote execution, variable sets, policy enforcement and a shared audit of runs, and it ties provisioning to individual laptops.
D=Site-to-site VPN from managed workers: HCP Terraform's disposable workers are not customer-networked appliances, so there is no supported way to place them on your private network.
T: For private networks, run agents inside them and set the workspace to Agent mode; agents need only outbound connectivity.

@ TF-IEP002 D7 T7.1 applied troubleshooting
S: A team changes a busy workspace from Remote to Agent execution mode. Right afterwards, two runs that had already finished planning fail with errors when confirmed. How could the team have avoided this?
A: Raise the workspace to a newer Terraform version first, because plans from the old version cannot be applied by an agent
B: Delete the stale configuration versions from the workspace, so the agent downloads fresh configuration before applying
C: Mark the workspace as ephemeral before the change, which cancels pending plans and creates new ones on the agent
D: Disable auto-apply, finish runs that are past the pending stage, lock the workspace, and only then change the mode
K: D
G: ## A plan belongs to the execution platform that made it
A planned run carries data produced where it was planned. If the execution mode changes after the plan, the apply would run on a different platform and **errors**. Runs that are still queued behind the current run have not planned yet, so they are not affected.
## Safe sequence for changing execution mode
- Disable auto-apply so finished plans do not start applying during the change.
- Complete (apply or discard) any run that is no longer pending.
- Lock the workspace to stop new runs from being queued.
- Change the execution mode (and pick the agent pool).
- Re-enable auto-apply if it was on, then unlock.
The same ordering applies when you move a workspace from an agent pool back to Remote.
W: Draining and locking first leaves no planned run to be applied on a different platform. That is the documented order for switching execution mode with minimal errors.
X: A=Newer Terraform version: the agent can run any Terraform release the workspace selects. Version has nothing to do with plans failing after the mode switch.
B=Deleting configuration versions: configuration versions are not why the applies fail. The planned runs are tied to the platform that planned them, and removing sources would not help.
C=Ephemeral workspace: there is no such setting that cancels pending plans. Ephemeral usually means auto-destroy for inactivity, which is unrelated.
T: Before changing a workspace's execution mode, disable auto-apply, finish non-pending runs and lock the workspace.

@ TF-IEP002 D7 T7.1 applied definition
S: Which TWO statements about HCP Terraform agent hooks are accurate? (Select TWO)
A: A hook that exits with a non-zero code makes the Terraform run fail immediately
B: A workspace can define several `pre-plan` hooks, and the agent runs them in alphabetical order
C: Hooks run on HCP Terraform's managed workers too, as long as the script is stored in the workspace configuration
D: A hook can set environment variables for later Terraform commands by writing `KEY=value` lines to the file named in `TFC_AGENT_ENV`
E: The `pre-plan` hook runs after `terraform init`, so it can inspect the downloaded providers and modules
K: A,D
G: ## What hooks are
Agent hooks are executables the agent runs at fixed points of a run: `pre-plan`, `post-plan`, `pre-apply` and `post-apply`. They let you install tools, fetch data or call an external system on your own infrastructure.
## Rules to remember
- The file name must be one of the four hook names, so an agent has **at most one hook per type**.
- Each hook must be executable and has a timeout (60 seconds by default, with a maximum of 10 minutes).
- `pre-plan` and `pre-apply` run **before** `terraform init` in their operation.
- A non-zero exit code, or a timeout, fails the run.
- Environment variables do not carry between hooks. To pass a variable to the next Terraform command, append `KEY=value` to the file in `$TFC_AGENT_ENV`.
- Hooks exist only on self-managed agents.
W: A=Non-zero exit: hooks are part of the run, so a failing hook stops it right away, which is useful for failing fast on missing prerequisites.
D=TFC_AGENT_ENV: writing KEY=value lines to the file in that variable is the supported way to hand variables from a hook to the Terraform commands that follow.
X: B=Several pre-plan hooks: names are fixed, so there can be only one hook of each type per agent. There is no ordering to configure.
C=Managed workers: hooks are an agent feature. Managed workers have no hook mechanism, and a script in the repository is not run as one.
E=After terraform init: pre-plan and pre-apply run before init, so providers and modules are not yet downloaded when they run.
T: Agent hooks fail the run on non-zero exit, exist once per type, run before init, and pass environment variables through the TFC_AGENT_ENV file.
V: HCP Terraform

@ TF-IEP002 D7 T7.1 applied troubleshooting
S: A mandatory post-plan run task calls an external scanner. The scanner's service is down, so it never answers HCP Terraform's request. What happens to runs that reach this stage?
A: The run ends in an errored state, because a timeout or remote error counts as a failure and mandatory failures stop the run
B: The run continues to the apply stage with a warning, because only a task that explicitly returns failed can block a run
C: The run waits in the post-plan stage until the scanner comes back, because the plan result cannot be released without a verdict
D: The run skips the task and records it as passed, because tasks are optional once the plan has completed successfully
K: A
G: ## How a run task reaches a decision
Run tasks send a payload (with a callback URL) to an external service at a chosen stage: pre-plan, post-plan, pre-apply or post-apply. The service must acknowledge with `200 OK` and then answer with `passed`, `running` or `failed`. The request errors if no progress update arrives within 10 minutes, and HCP Terraform treats a timeout or unexpected remote error as **failed**.
## Enforcement level turns the result into an action
- **Advisory**: a failed task shows a warning, and the run goes on.
- **Mandatory**: a failed task, **including a timeout or unexpected remote error**, stops the run (Plan Errored).
When a run has several tasks, the most restrictive result wins: one failing mandatory task fails the run even if several advisory tasks pass.
W: A timeout is a failure and the task is mandatory, so the run stops in an errored state. The team can change the task's enforcement to advisory if a scanner outage must not block deployments.
X: B=Warning only: the warning-and-continue behavior belongs to advisory tasks. A mandatory task that fails or times out blocks the run.
C=Waits indefinitely: the stage has a time limit. When it expires, HCP Terraform assumes failure instead of holding the run open.
D=Skipped as passed: nothing marks an unanswered task as passed. It counts as failed.
T: A run task that times out counts as failed, and when mandatory it errors the run; advisory tasks only warn.
V: HCP Terraform

@ TF-IEP002 D7 T7.1 applied comparison
S: A team's pipeline generates Terraform configuration from an internal service catalog and keeps no Git repository for it. Its tooling must decide when runs happen. Which HCP Terraform workflow fits?
A: The VCS-driven workflow, with the generated files committed by a bot to a repository that webhooks watch
B: The CLI-driven workflow with `terraform apply` on the laptop of whoever owns the catalog entry
C: The API-driven workflow, where the tooling uploads a `.tar.gz` configuration version and creates runs
D: The UI-driven workflow, where an operator uploads a ZIP archive in the browser before every run
K: C
G: ## Three ways to drive runs
- **UI/VCS-driven**: the workspace is linked to a branch of a repository. Webhooks queue a run on each merge, and pull requests get speculative plans. The code always comes from version control.
- **CLI-driven**: engineers run `terraform plan` or `terraform apply` with a `cloud` block, and the run executes in the workspace. Workspaces without a linked repository can run remote applies and saved plans this way.
- **API-driven**: no repository is linked. Your tooling decides when a run should happen, packages the configuration as a `.tar.gz` (the configuration directory at the root of the archive), creates a configuration version through the API, uploads the archive and creates the run.
## Choosing
API-driven is the flexible workflow for unsupported version control, generated configuration or custom CI. It requires you to build the tooling.
W: The API-driven workflow lets existing tooling push generated configuration as configuration versions and trigger runs, which matches a setup with no repository and an external decision about when to run.
X: A=Bot commits to Git: it works, but adds a repository and webhook layer just to carry files the tooling already has. The case is built for the API workflow.
B=CLI on a laptop: the run would depend on one person's machine and does not let the pipeline decide when to run.
D=Upload in the browser: this describes a manual step per run. The UI workflow starts from VCS or from an existing configuration version, not from browser uploads of ZIP files.
T: When your own tooling owns configuration and timing, use the API-driven workflow: upload a configuration version and create the run.
V: HCP Terraform

@ TF-IEP002 D7 T7.1 applied troubleshooting
S: A monorepo holds `envs/prod` and `modules/`. The workspace has working directory `envs/prod`, and VCS runs trigger only for changes under that directory. A change that edits a shared module under `modules/` starts no run. What fixes this?
A: Clear the working directory so the workspace watches the whole repository for every push
B: Add `modules` as a trigger prefix or a trigger pattern like `/modules/**/*.tf` on the workspace

D: Change the workspace's tracked branch to a tag so any repository change creates a run

G: ## Default filtering with a working directory
When a VCS-backed workspace sets a **working directory**, HCP Terraform assumes only changes inside that directory matter and uses it as the default filter. Edits to shared code outside it, such as `modules/`, do not start runs.
## Automatic Run Triggering options
- **Always trigger runs**: any change to the repository. Easy, but queues unnecessary runs in a monorepo.
- **Only trigger runs when files in specified paths change**: trigger **patterns** (globs, recommended) or **prefixes** (directories, including the working directory). The same filter applies to speculative plans on pull requests.
- **Trigger on git tags**: runs start when a matching tag is published.
Adding the shared directory as a pattern or prefix keeps the workspace narrow but makes it react when its modules change.
W: A trigger prefix or pattern for `modules` adds the shared code to what the workspace watches, while the working directory still scopes the configuration itself.

C=Auto-apply: auto-apply only decides whether a finished plan applies without confirmation. It does not start runs for files outside the filter.
D=Tracking a tag: tag triggers start runs only when a tag matching the chosen format is published. They do not make module edits start runs.
T: A working directory narrows VCS triggers; add trigger patterns or prefixes for shared directories such as modules.

@ TF-IEP002 D7 T7.2 applied definition
S: A workspace's state holds `aws_instance.web` created with `count = 4`, a module called with `for_each` over three keys that contains two `aws_sqs_queue` resources, one `aws_s3_bucket`, and two data sources. How many managed resources does HCP Terraform count for it?

G: ## How the managed resource count works
HCP Terraform reads the state files of all workspaces (and Stack deployments) and counts the entries with `mode` equal to `managed`. The total appears on the organization's **Usage** page.

- Each **resource instance** in state is one managed resource. A resource with `count = 4` is four.

- **Data sources** (`mode` is `data`) are not counted.

- `aws_instance.web`: 4
- Module with three instances, each with two queues: 3 x 2 = 6
- `aws_s3_bucket`: 1
- Data sources: 0
Total: 4 + 6 + 1 = **11**.
W: Instances are counted individually, including those inside module instances, while data sources are excluded: 4 + 6 + 1 = 11.
X: A=Includes data sources: that adds the two data sources to the total. Data sources have mode data and are not part of the managed resource count.
C=Module call counts once: each module instance created by for_each has its own copies of the resources in state, so the three instances contribute six, not two.
D=Count of blocks: state records instances, not blocks. A block with count 4 appears four times, and the same goes for module-created resources.
T: Managed resource count equals managed resource instances in state, across modules and count or for_each, and excludes data sources.

A run trigger connects a **downstream** workspace to one or more **source** workspaces. @ TF-IEP002 D7 T7.3 applied tradeoff
S: Three teams (payments, search, data) each deploy dev, staging and prod workspaces. Each team must administer only its own workspaces and use its own cloud credentials, while the platform team manages the shared setup. Which layout fits best?
A: One project holds all nine workspaces, with a variable set per team applied to its three workspaces
B: One project per environment, with each team granted access workspace by workspace in every project
C: One project per team holding its three workspaces, team access set on the project, and a project-scoped variable set for its credentials
D: One organization per team, with a shared parent organization that links them for common policies and variables
K: C
G: ## Projects are the unit of delegation
A **project** is a folder for workspaces (and Stacks) inside an organization. Team permissions can be granted on the project and apply to every workspace in it, including workspaces created later. Variable sets can be **project-scoped**, so one set (such as cloud credentials) applies to all workspaces of the project automatically.
## Matching the requirement
- Teams must manage only their own workspaces: project per team, team access at project level.
- Different credentials per team: a project-scoped variable set per project.
