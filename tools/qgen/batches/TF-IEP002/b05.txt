@ TF-IEP002 D3 T3.6 applied use-case
S: Three environment directories (dev, stage, prod) each call the shared module `app` from one Git repository. Prod must keep running the reviewed release while dev tests the next release. Which setup supports this?
A: Pin the module source in each environment directory to its own Git tag with a `ref`, and move the prod tag forward only after dev and stage pass
B: Point all three directories at one local path to the module folder and let prod apply less often than dev, so its resources change rarely
C: Copy the module code into every environment directory so each team may edit its copy and promote changes by hand when it is ready
D: Run `terraform init -upgrade` in dev only, because the upgrade flag keeps the other directories on whatever module source they installed first
K: A
G: ## Directory-per-environment with shared modules
The CLI workspaces documentation names this pattern as the alternative to workspaces: reusable modules hold the common elements, and each environment is a separate configuration whose root module is only a backend configuration plus a few `module` blocks with environment-specific arguments. Every environment then has its own state, backend and credentials.
## Promotion by version
Because each root module chooses its own module version, a release moves through environments one at a time. For a Git source the version is a `ref` (tag or commit) in the `source` URL. For registry modules it is the `version` constraint. Dev points at the new tag first; stage and prod keep the old one until the change is reviewed.
W: Separate roots with separately pinned Git tags let dev consume the new release while prod stays on the reviewed one, and promotion is a one-line change in the next environment's `source`.
X: B=Shared local path: all directories read the same files, so the moment the folder changes every environment's next plan sees it. Applying prod less often only delays the surprise.
C=Copied module code: copies drift apart, fixes must be re-applied by hand in each, and the review of one version no longer proves anything about the other copies.
D=Upgrade flag in dev only: `-upgrade` refreshes modules and providers of the directory where it runs, but it does not pin anything for the other directories, so it is no release mechanism.
T: One root per environment, each pinning its own module version, is the promotion path that workspaces cannot give.

@ TF-IEP002 D3 T3.6 advanced troubleshooting
S: A shared module names a bucket `"${terraform.workspace}-logs"`. A root module calls it twice, as `module.audit` and `module.access`, and the second apply fails because the bucket name already exists. What is the correct fix?
A: Add a `name_prefix` input to the module and let the root module compute each value, using `terraform.workspace` only in the root
B: Replace `terraform.workspace` with `path.module`, which is unique for every call and therefore yields two distinct bucket names
C: Add a `depends_on` between the two module calls so that the second call waits and picks a different workspace name
D: Select a second workspace before the second module call, because a workspace is selected per module rather than per directory

G: ## terraform.workspace inside a shared module
`terraform.workspace` is the name of the currently selected workspace, and it is the same for every module call in one run. The references documentation warns that these context values can hurt the portability or composability of a module. Using `terraform.workspace` as a name prefix inside a shared module makes it impossible to call the module more than once with distinct names.
## The recommended pattern
The module declares an input variable (for example `name_prefix`). The calling module passes `"${terraform.workspace}-audit"` and `"${terraform.workspace}-access"`, or any other values. The module stays reusable, and the root decides how environment names appear.
W: A prefix input makes the module's naming a caller decision, so both calls get distinct names while the root still derives them from the workspace.
X: B=path.module: this is the filesystem path of the module source and is identical for both calls of the same module, so it would not separate the names. It is also not meant for resource naming.
C=Added depends_on: ordering changes only when the calls run, not the string `terraform.workspace` evaluates to, so both calls still request the same bucket name.
D=Second workspace: only one workspace can be selected for a working directory at a time, and the choice applies to the whole run, not to a single module call.

S: `variable "size"` has `default = "tiny"`. The directory holds `terraform.tfvars` (small) and `prod.auto.tfvars` (large). The pipeline exports `TF_VAR_size=xlarge` and runs `terraform apply -var-file=ci.tfvars`, where that file sets medium. Which size is used?
A: medium
B: large
C: xlarge

G: ## Order of precedence for root module variables
When a root module variable gets values from several sources, Terraform uses this order, highest first:
- `-var` and `-var-file` options on the command line (in the order provided) and variables from HCP Terraform
- `*.auto.tfvars` and `*.auto.tfvars.json` files, in lexical order
- `terraform.tfvars.json`
- `terraform.tfvars`
- environment variables (`TF_VAR_name`)
- the `default` in the variable block
## Applying it
Here every source sets a value: default (tiny), the environment variable (xlarge), `terraform.tfvars` (small), the auto-loaded file (large) and the explicit `-var-file` (medium). The command-line file sits at the top, so medium wins.

X: B=Large: the auto-loaded `*.auto.tfvars` file beats `terraform.tfvars`, environment variables and the default, but not an explicit command-line variable file.
C=Xlarge: environment variables are one of the lowest-precedence sources, beaten by every variable definition file and by the command line.
D=Small: `terraform.tfvars` is loaded automatically, but both `*.auto.tfvars` files and `-var-file` override it.

@ TF-IEP002 D3 T3.6 applied definition
S: A directory holds `10-base.auto.tfvars` and `2-team.auto.tfvars`, both defining `tier`, with `tier = "base"` and `tier = "team"` respectively. No other source sets it. What value does the root module use?
A: team, because the files load in lexical order and the later file wins
B: base, because the file whose name starts with the lower number is loaded last
C: An error is raised, because two auto-loaded files may not set the same variable
D: The value of the variable's default, because competing auto-loaded files cancel each other
K: A
G: ## Lexical order, not numeric order
Terraform loads every `*.auto.tfvars` and `*.auto.tfvars.json` file in lexical order, and a later file overrides an earlier one for the same variable. Lexical means character by character, like a dictionary sort:
- `10-base.auto.tfvars` compares `1` against `2` at the first character and sorts first.
- `2-team.auto.tfvars` sorts after it.
So `2-team` is applied last. Teams that layer files (`00-`, `10-`, `20-`) must zero-pad numbers, otherwise `100-` sorts before `20-`.
## Duplicates
The restriction is only that one variable cannot be assigned twice in the same file. Across files, later overrides earlier.
W: Lexical sorting puts `10-base` before `2-team`, the last file loaded wins, so the variable resolves to team.
X: B=Numeric reading: file names are compared as text, not as numbers, so the file starting with 10 is first, not last, and loses to the later one.
C=Error on duplicates: Terraform reports a duplicate only when the same variable is assigned twice inside one file, not across different files.
D=Default value: overrides are layered, never cancelled; any definition file beats the variable's default.
T: Auto-loaded tfvars apply in lexical order and the last one wins, so zero-pad numeric prefixes.
V: Terraform

CLI workspaces are separate instances of state inside one working directory and backend. @ TF-IEP002 D3 T3.7 applied troubleshooting
S: A CI job was cancelled in the middle of `terraform apply`. The next run stops with "Error acquiring the state lock" and prints a lock ID and the earlier run's metadata. No other run is active. What is the correct action?
A: Confirm the earlier run is really dead, then release the lock with `terraform force-unlock` and the printed lock ID
B: Add `-lock=false` to every future command so that locks left by cancelled jobs no longer block the pipeline
C: Delete the state object from the backend so that the lock disappears together with the file that it protects
D: Run `terraform init -reconfigure`, which clears locks left behind by earlier runs when it reinitializes the backend
K: A
G: ## Why the lock stays
Terraform locks state for every operation that can write it. When a process is killed, it cannot release the lock, so the next run fails to acquire it and prints a lock ID.
## Safe recovery
`terraform force-unlock LOCK_ID` removes the lock for the current configuration without modifying infrastructure. The ID acts as a nonce so that you unlock the right lock. The docs warn that unlocking a lock held by someone else can lead to multiple writers, so use it to release your own lock after automatic unlocking failed, once you have verified the holder is gone.
## What not to do
Disabling locking (`-lock=false`) is not recommended: concurrent writers can corrupt state. Removing state objects destroys the record of managed resources.
W: Verifying that no run holds the lock and then using `force-unlock` with the reported ID releases only the orphaned lock and leaves state and infrastructure untouched.
X: B=Disabling locks permanently: the docs do not recommend `-lock=false`; two concurrent applies could write the state at once and corrupt it.
C=Deleting state: this loses the mapping between configuration and real resources, so the next plan would try to create everything again. The lock is a separate concern.
D=Reconfigure: `-reconfigure` ignores earlier backend configuration settings; it does not release a lock held on the state.
T: After a killed run, verify nobody holds the lock, then use terraform force-unlock with the lock ID.
V: Terraform

@ TF-IEP002 D3 T3.7 applied troubleshooting
S: Two pipelines apply different changes to the same state. When both start together, the second fails at once with a lock error although the first finishes within minutes. Which change makes the second run wait instead of failing?
A: Add `-lock-timeout=10m` to the plan and apply commands
B: Add `-lock=false` to the second pipeline only
C: Lower `-parallelism` to 1 on the first pipeline so it holds the lock for less time
D: Run `terraform init -upgrade` in the second pipeline before applying
K: A
G: ## Lock acquisition
By default Terraform tries to take the state lock once. The default for `-lock-timeout` is `0s`, which means it fails immediately if the lock is held. With `-lock-timeout=DURATION` (a number with a unit such as `30s` or `10m`) Terraform retries until the duration passes, and only then returns the error.
## Choosing the timeout
Set it a bit above the normal run length of competing pipelines. Serializing the runs in the CI system (a concurrency group) is better still, because it also avoids applying out of order.
W: A lock timeout makes the second run retry for up to ten minutes, which covers the first run's few minutes, so no manual intervention is needed.
X: B=Disabling the lock: the second run would write state at the same time as the first, which is the corruption that locking prevents.
C=Lower parallelism: fewer concurrent operations make the first run slower, not shorter, and the second run would still fail at once.
D=Upgrading in init: `-upgrade` refreshes providers and modules; it has no effect on how the state lock is taken.
T: -lock-timeout makes Terraform wait for a held lock; the default of 0s fails immediately.

@ TF-IEP002 D3 T3.7 advanced troubleshooting

@ TF-IEP002 D3 T3.7 applied definition

D=Apply only: the docs list plan, apply and destroy as accepting the flag, since all three walk the graph.
E=Zero as a fix: the docs describe no unlimited value and no rate-limit remedy; unlimited concurrency would make throttling worse.
T: -parallelism caps concurrent graph nodes (default 10) on plan, apply and destroy; rate limits are mostly handled by provider retries.

C=Sharing prerequisite: the docs say remote state access controls do not apply to tfe_outputs; the token's permissions govern it instead.
D=Complete state: the data source returns output values only, which is why it is considered more secure than full state access.
