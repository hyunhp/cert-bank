# AZ-900 D3 T3.3 (infrastructure as code, Azure Resource Manager, ARM templates, Bicep) and T3.4 (Advisor, Service Health, Azure Monitor)

@ AZ-900 D3 T3.3 applied troubleshooting
S: A company deployed staging and production a year ago. Since then, engineers fixed production issues by changing settings in the portal, and new releases now pass in staging but fail in production. Which practice prevents this kind of problem?
A: Infrastructure as code: keep the environment definition in source control, change the file, and redeploy it to every environment
B: Resource locks: put a ReadOnly lock on the staging environment so that it can never drift away from the production settings
C: Azure Advisor: review its recommendations weekly so that every environment follows the same best-practice configuration
D: Management groups: move both subscriptions under one management group so that their settings are always kept in sync
K: A
G: ## What infrastructure as code solves
When each environment is changed by hand, it slowly becomes a unique "snowflake" that nobody can rebuild exactly. Microsoft's DevOps guidance calls this **environment drift**: staging and production stop matching, so a release that works in one fails in the other.
**Infrastructure as code (IaC)** means describing the infrastructure in code or templates instead of configuring it manually.
- The definition lives in a source repository and is versioned like application code.
- To make a change, the team edits the source, not the target, and redeploys.
- The same definition produces the same environment every time it is deployed.
## IaC on Azure
Azure supports IaC natively through Azure Resource Manager: you write declarative **ARM templates** (JSON) or **Bicep** files. Third-party tools such as Terraform also work through Azure providers.
## Example
A production fix that raises an App Service plan's instance count is made in `main.bicep`, reviewed in a pull request, and deployed to staging and production, so both keep the same configuration.
W: Infrastructure as code: one versioned definition deployed to every environment removes manual, one-off changes, so staging and production stay identical and every change is reviewable in source control.
X: B=ReadOnly lock on staging: a lock blocks changes to staging but does nothing about the manual edits in production, which caused the drift. It also blocks legitimate updates to staging.
C=Azure Advisor reviews: Advisor suggests improvements to deployed resources but does not define or apply a single configuration to several environments.
D=Common management group: a management group lets policy and access apply to several subscriptions, but it does not copy resource settings from one environment to another or undo manual edits.
T: Infrastructure as code keeps environments identical by changing the versioned definition and redeploying, never the live environment by hand.
V: Azure Resource Manager, ARM templates, Bicep

@ AZ-900 D3 T3.3 advanced definition
S: A team deploys an ARM template that creates a storage account. A week later it deploys the same template again, unchanged, and the storage account still has exactly the properties the template defines. What happens?
A: Resource Manager sees the storage account already matches the template, so the resource is left in that same state
B: Resource Manager deletes the storage account and creates a new, empty one, because each deployment starts over
C: The deployment fails, because a template can create a resource only once and must be edited before it runs again
D: A second storage account is created with a generated suffix, because each deployment adds a new set of resources
K: A
G: ## Idempotent deployments
ARM templates and Bicep files are **idempotent**: you can deploy the same file many times and get the same resource types in the same state. The template describes the desired end state, not a list of steps, so Resource Manager compares that state with what exists:
- a resource that does not exist yet is created
- a resource that differs from the template is updated to match it
- a resource that already matches is left as it is
Because of this, one template can represent the desired state for the whole lifecycle; you do not write separate "create" and "update" templates.
## Example
Microsoft's own example is a template with one `Microsoft.Storage/storageAccounts` resource: if the storage account with the specified properties already exists, deploying the template again makes no changes.
W: Same state, nothing changed: idempotence means a repeated deployment of an unchanged template ends in the same state. The existing storage account already matches the desired state, so it keeps its data and settings.
X: B=Delete and recreate: redeploying does not start from scratch. Resource Manager updates or leaves resources to match the template; it does not wipe an existing storage account.
C=Create only once: templates are designed to be deployed repeatedly through the development lifecycle. A second run of the same template is a normal, supported operation.
D=Extra copy each time: the template names the resource, and the same name in the same scope means the same resource. Redeploying does not add duplicates.
T: ARM templates and Bicep files are idempotent: deploying the same file again results in the same resources in the same state.
V: ARM templates, Azure Resource Manager

@ AZ-900 D3 T3.3 applied use-case
S: An organization has one management group with several subscriptions. An admin wants a setting to apply to every resource group in the Sales subscription, including groups created later, without affecting the other subscriptions. At which Azure Resource Manager scope should it be applied?
A: The Sales subscription, because settings applied there are inherited by all of its resource groups and their resources
B: The management group, because settings applied there reach only the resource groups that already exist at that time
C: Each existing resource group in Sales, because resource groups created later copy the settings of an existing group
D: Each resource in Sales, because Resource Manager applies settings only at the level of individual resources
K: A
G: ## Management scopes in Azure Resource Manager
Resource Manager has four levels of management scope, from broadest to narrowest:
- **management groups** (containers for subscriptions)
- **subscriptions**
- **resource groups**
- **resources**
You can apply management settings, such as Azure Policy assignments or role assignments, at any of these levels. The level you choose decides how widely the setting applies, because **lower levels inherit settings from higher levels**.
## Example
A policy assigned to the subscription applies to all resource groups and resources in that subscription, including ones created later. The same policy assigned to one resource group applies only to that group and its resources; a second resource group does not get it.
W: Sales subscription: the subscription is the narrowest scope that covers every resource group in Sales, and inheritance means new resource groups get the setting automatically while other subscriptions stay unaffected.
X: B=Management group: settings at the management group are inherited by every subscription under it, so the other subscriptions would be affected too. Inheritance also covers new resources, not only existing ones.
C=Each resource group: a setting on one resource group applies only to that group. New resource groups do not copy settings from other groups, so they would be missed.
D=Each resource: settings can be applied at any of the four scopes, not only resources. Setting each resource one by one would also miss resources created later.
T: Apply settings at the narrowest Resource Manager scope that covers everything you need; lower scopes inherit from higher ones.
V: Azure Resource Manager, Azure Policy

@ AZ-900 D3 T3.3 applied comparison
S: A team writes its Azure infrastructure in ARM template JSON and finds the files long and hard to read. It is considering Bicep. Which TWO statements about Bicep are correct? (Select TWO)
A: A Bicep file is converted into an ARM JSON template during deployment, and Resource Manager deploys it as usual
B: Bicep has no state file for the team to store, because Azure keeps track of the state of the deployed resources
C: Bicep supports only resource types that are generally available, so newer preview types still need a JSON template
D: Bicep is an imperative scripting language that runs each command in order, unlike the declarative JSON templates
E: Bicep deployments go straight to each resource provider, so they skip the Azure RBAC checks done by Resource Manager
K: A,B
G: ## Bicep and ARM templates
**ARM templates** are JSON files that declare the resources to deploy. JSON works, but it is verbose and needs bracketed expressions such as `[parameters('location')]`.
**Bicep** is a domain-specific, declarative language for the same job. Microsoft describes it as a transparent abstraction over ARM JSON templates:
- During deployment, Bicep converts the file into an ARM JSON template, so Resource Manager handles it exactly like any other template.
- Anything valid in an ARM template (resource types, API versions, properties) is valid in Bicep, including new preview and GA resource types as soon as a provider adds them.
- There are **no state files** to manage: Azure stores the state.
- Bicep is idempotent, orchestrated by Resource Manager, and supports reuse through modules.
## Example
`resource sa 'Microsoft.Storage/storageAccounts@2023-05-01' = { name: 'stdemo' ... }` in Bicep replaces a longer JSON block with the same meaning.
W: A=Converted to ARM JSON: Bicep is a layer over ARM templates. The Bicep tooling turns the file into JSON, and Resource Manager validates and deploys it like any template.
B=No state file: unlike tools that keep their own state, Bicep relies on Azure for the current state of resources, so there is no state file to store, lock or share.
X: C=GA types only: Bicep immediately supports all preview and GA resource types and API versions; you do not have to fall back to JSON for new types.
D=Imperative scripting: Bicep is declarative, like JSON templates. You describe the resources you want, and Resource Manager decides the order.
E=Skips RBAC: Bicep deployments go through Resource Manager, which authenticates and authorizes every request. Nothing bypasses Azure RBAC.
T: Bicep is a simpler declarative language over ARM templates: it compiles to ARM JSON, is deployed by Resource Manager and needs no state file.
V: Bicep, ARM templates, Azure Resource Manager

@ AZ-900 D3 T3.3 advanced troubleshooting
S: An engineer splits a large ARM template into a main template plus linked network and compute templates. The main template references the linked files by a path on the engineer's laptop, and the deployment fails. What is the cause?
A: Resource Manager must download linked templates from an HTTP or HTTPS address it can reach, not from a local file
B: ARM templates cannot be split; every resource of a deployment must be defined in one single template file
C: Linked templates work only when every linked template targets a different subscription than the main one
D: Linked templates are allowed only in Bicep, so a JSON main template has to define every resource inline
K: A
G: ## Modular templates
You do not have to put a whole solution into one template. ARM templates support **modular files**: you break the deployment into smaller, reusable templates and combine them from a **main template**.
- A **nested template** is template syntax embedded inside the main template.
- A **linked template** is a separate file that the main template references by URI.
Bicep offers the same idea through **modules**.
## Where linked templates must live
Resource Manager itself fetches linked templates during the deployment, so the URI must be downloadable over HTTP or HTTPS. It cannot be a local file or a file available only on your local network. Common options:
- a storage account (it can stay private, with a SAS token in the URI)
- a **template spec**, which packages the main and linked templates as an Azure resource shared through Azure RBAC
## Example
`main.json` links `https://<account>.blob.core.windows.net/templates/network.json?<sas>` instead of `C:\templates\network.json`.
W: Reachable URI: linked templates are retrieved by Resource Manager in Azure, which cannot read a laptop's disk. Storing them in a storage account (with a SAS token) or packaging them as a template spec fixes the deployment.
X: B=Single file only: ARM templates explicitly support breaking a deployment into reusable linked and nested templates; modularity is one of their listed benefits.
C=Different subscription: linked templates can deploy to the same resource group as the main template or to other scopes; there is no rule that they must target another subscription.
D=Bicep only: linked and nested templates are features of JSON ARM templates. Bicep provides the same idea through modules.
T: Split large templates into linked templates or Bicep modules, and store linked files where Resource Manager can download them (storage account or template spec).
V: ARM templates, template specs, Azure Resource Manager

@ AZ-900 D3 T3.3 applied definition
S: A developer deploys an ARM template that contains a syntax error. Resource Manager rejects the deployment before creating any resource, so nothing is left half-built. Which ARM template feature explains this?
A: Built-in validation: Resource Manager checks the template first and starts the deployment only after it passes
B: Azure Policy deny effect: a built-in policy blocks every template that contains an error before it is deployed
C: Resource locks: a CanNotDelete lock on the resource group rolls back any template that contains an error
D: Azure Advisor checks: Advisor reviews each template against best practices and stops those with problems
K: A
G: ## What happens when you deploy a template
When Resource Manager receives an ARM template (or a Bicep file, already converted to JSON), it does not start creating resources immediately:
- **Validation**: Resource Manager checks the template before the deployment starts, to make sure it can succeed. A template that fails validation is not deployed, so a deployment is less likely to stop in a half-finished state.
- **Orchestration**: after validation, Resource Manager creates interdependent resources in the right order and runs independent ones in parallel.
- **Tracking**: the deployment history records the template, parameter values and outputs.
Before deploying, teams can also run the **what-if** operation to preview which resources would be created, changed or deleted.
## Example
A typo in a property name or a missing bracket makes validation fail, and the error is returned before any VM or network is created.
W: Built-in validation: Resource Manager validates every template before it begins the deployment, so a broken template is rejected up front instead of failing midway.
X: B=Policy deny: Azure Policy evaluates resource properties against organisational rules such as allowed regions. It does not check templates for syntax errors.
C=Resource lock: locks only prevent deleting or changing existing resources. They do not inspect templates or roll back deployments.
D=Advisor checks: Advisor gives recommendations about resources that are already deployed. It is not part of the deployment pipeline and cannot stop a template.
T: Resource Manager validates an ARM template before deploying it, then orchestrates resource creation in the correct order.
V: ARM templates, Azure Resource Manager

S: Users report that one VM is unreachable. The admin wants to know whether Azure has detected a platform problem with that VM, such as an unexpected host reboot, or whether the cause is a user action like stopping it. Which tool should they use first?
A: Azure Resource Health for the VM, which shows its health status and whether a platform or a non-platform event caused it

G: ## Resource Health: one resource, one status
**Azure Resource Health** reports the current and past health of individual resources, such as a specific VM, web app or SQL database. Each resource shows a status:
- **Available**: no events affecting its health.
- **Unavailable**: an ongoing event affects it. Resource Health distinguishes **platform events** (triggered by Azure infrastructure, for example planned maintenance or an unplanned host reboot) from **non-platform events** (triggered by user actions, for example stopping the VM).
- **Degraded**: still available, but with reduced performance.
- **Unknown**: no information for more than 10 minutes, common when a VM is deallocated.
For platform problems, Resource Health explains what Microsoft is doing and lets you contact support even without a support plan.
## Example
`vm-web-01` shows Unavailable with a platform event "unexpected host reboot": the problem is on Azure's side, not caused by an admin.
W: Resource Health: it focuses on one resource and says whether its unavailability comes from Azure (platform event) or from a user action (non-platform event), which is exactly the admin's question.
X: B=Azure status page: the status page covers only broad, Azure-wide incidents. It never lists individual customer VMs.
C=Azure Advisor: Advisor gives recommendations about configuration, cost and security. It does not report a resource's live health or the cause of an outage.
D=Application Insights: Application Insights monitors application performance and usage from telemetry. It is not the Azure view of a VM's platform health.
T: Use Resource Health to see whether a specific resource is healthy and whether a problem comes from Azure or from your own actions.
V: Azure Resource Health

S: Right after a Windows VM is created, its CPU and disk charts appear in Azure Monitor with no setup. An admin also wants the VM's Windows event logs in a Log Analytics workspace, but none arrive. What is missing?

Azure Monitor gets data about a VM from two places:

## Example

C=Service Health alert: Service Health alerts notify you about Azure service issues. They have nothing to do with collecting data from a VM.
D=Resource Health: Resource Health reports whether a resource is available. It does not collect or forward the guest operating system's logs.
T: Platform metrics come automatically from the host; guest OS logs and counters need the Azure Monitor Agent and a data collection rule.

A: Kusto Query Language (KQL), a read-only language for filtering and aggregating data in Azure Monitor Logs
B: Transact-SQL (T-SQL), the language of Azure SQL Database, which Log Analytics uses to query every log table

G: ## Querying Azure Monitor Logs
Azure Monitor Logs is built on Azure Data Explorer and uses the same **Kusto Query Language (KQL)**. A KQL query is a read-only request: it filters, aggregates and joins data and returns results, and it can scan millions of records quickly.
- **Log Analytics** is the tool in the Azure portal for writing and running log queries. It also has a Simple mode for users who do not know KQL yet.
- The same queries are reused in **log search alert rules**, workbooks and dashboards.
## Example
`Event | where EventLevelName == "Error" and TimeGenerated > ago(1h) | summarize count() by Computer`
This counts error events per machine for the last hour.
W: KQL: Azure Monitor Logs and Log Analytics use Kusto Query Language, and the same KQL query can power a log search alert or a workbook.
X: B=T-SQL: T-SQL queries relational databases such as Azure SQL Database. Log Analytics workspaces are not queried with T-SQL.
C=PromQL: PromQL is used for Prometheus metrics stored in an Azure Monitor workspace, not for log tables in a Log Analytics workspace.
D=Bicep: Bicep is an infrastructure-as-code language for deploying resources. It does not query any data.
T: Log Analytics queries, log search alerts and workbooks over Azure Monitor Logs all use KQL.
V: Log Analytics, Azure Monitor Logs

@ AZ-900 D3 T3.4 advanced use-case
S: An app writes the text "Payment gateway timeout" to its logs, which are collected into a Log Analytics workspace from 12 VMs. The team wants an alert when this message appears more than 5 times in 15 minutes across all VMs. Which alert type fits?
A: A log search alert rule that runs a KQL query on the workspace on a schedule and checks the count of matches
B: A metric alert rule on each VM's CPU percentage, because a high CPU value shows that the timeouts are happening
C: A Service Health alert for the region of the VMs, because timeouts are reported as Azure service issues
D: An activity log alert on the VMs, because each logged message is written as an administrative operation
K: A
G: ## Choosing an Azure Monitor alert type
An alert rule combines the resources to monitor, a signal and a condition; when the condition is met it fires and runs an action group. The signal decides the alert type:
- **Metric alerts**: evaluate numeric metrics at regular intervals (CPU above 80%).
- **Log search alerts**: run a Log Analytics (KQL) query on a schedule and evaluate the results, so they can match text patterns across many resources.
- **Activity log alerts**: fire on new activity log events, such as an administrative operation, or Service Health and Resource Health events.
## Example
`AppLogs_CL | where Message has "Payment gateway timeout"`
A log search alert runs this every 5 minutes over the last 15 minutes and fires when the count is greater than 5, then calls an action group.
W: Log search alert: the condition is about specific text in log records from many VMs, which only a scheduled KQL query over the workspace can count.
X: B=CPU metric alert: CPU is an indirect signal. Timeouts can happen at normal CPU, and a metric cannot tell you that a specific message was logged.
C=Service Health alert: Service Health alerts report Azure's own service issues and maintenance. Messages written by your application are not Service Health events.
D=Activity log alert: the activity log records control-plane operations such as creating or deleting resources. Application log messages are not written there.
T: Alert on numbers with metric alerts, on log content with log search alerts (KQL), and on Azure operations and health events with activity log alerts.
V: Azure Monitor alerts, Log Analytics

@ AZ-900 D3 T3.4 advanced comparison
S: An operations team is designing Azure Monitor action groups to use with several alert rules. Which TWO can an action group do when an alert fires? (Select TWO)
A: Notify people by email, SMS, voice call or Azure mobile app push notification
B: Start automation such as a runbook, an Azure Function, a Logic Apps workflow or a webhook
C: Raise the alert rule's threshold automatically so that the same alert does not fire again
D: Decide which resources and signals the alert rule watches and the condition that fires it
E: Fix the cause of the alert by itself, for example by resizing the VM without any automation
K: A,B
G: ## Alert rules and action groups
An **alert rule** says *what* to watch: the resources, the signal (metric, log query, activity log event) and the condition. An **action group** says *what happens* when an alert fires.
Action groups contain:
- **Notifications**: email, SMS, voice call, Azure mobile app push, email to an Azure Resource Manager role.
- **Actions**: Automation runbook, Azure Functions, Logic Apps, webhook or secure webhook, ITSM, Event Hubs.
Action groups are reusable: one group can serve many alert rules, and the same groups are used by Service Health alerts and Azure Advisor alerts.
## Example
`ag-oncall` texts the on-call engineer and calls a webhook that opens a ticket. Three alert rules (CPU, disk, failed logins) all point to `ag-oncall`, so contacts are changed in one place.
W: A=Notify people: email, SMS, voice and push notifications are the notification types an action group offers.
B=Start automation: action groups can trigger runbooks, Functions, Logic Apps workflows and webhooks, for example to open a ticket or restart a service.
X: C=Raise the threshold: an action group never edits the alert rule. Thresholds are part of the rule's condition and change only when someone updates the rule.
D=Define what is watched: resources, signal and condition belong to the alert rule. The action group only defines the response.
E=Fix the cause by itself: an action group has no built-in remediation. Any fix, such as resizing a VM, must be done by automation you attach (for example a runbook).
T: Alert rules decide when to fire; reusable action groups decide who is notified and which automation runs.
V: Azure Monitor alerts, Azure Monitor action groups

@ AZ-900 D3 T3.4 applied use-case
S: An online shop has almost no visitors between 1 a.m. and 6 a.m., so outages at night go unnoticed until morning. The team wants its public checkout URL tested every few minutes from several locations, with an alert if it fails. What should it use?
A: Application Insights standard availability tests, which send synthetic web requests from several locations
B: Azure Resource Health for the web app, which sends test requests to the public URL from several regions
C: A metric alert on the web app's request count, which fires when the number of user requests falls to zero
D: Azure Advisor performance recommendations, which test the public URL at night and report response times
K: A
G: ## Why synthetic monitoring
Request telemetry only exists when users visit. With no traffic at night, there is nothing to measure, so a broken site looks the same as a quiet one.
**Availability tests** in Application Insights fix this by sending requests themselves:
- They call any HTTP or HTTPS endpoint reachable from the public internet, at a set frequency, from several test locations around the world (Microsoft recommends at least five).
- They need no change to the application.
- A **standard test** measures whether the endpoint responds and how fast, and can also check the validity and remaining lifetime of the TLS/SSL certificate.
- An alert fires when tests fail from a chosen number of locations, and an action group sends the notification.
## Example
A standard test calls `https://shop.example.com/checkout` every 5 minutes from 5 locations and alerts when 3 of the 5 report failures.
W: Standard availability test: it generates its own traffic from multiple locations, so the team learns about failures at any hour, even when there are no real users.
X: B=Resource Health: Resource Health reports Azure's view of a resource's platform health. It does not send requests to your URL, so an application error would go unnoticed.
C=Request count alert: zero requests at 3 a.m. is normal for this shop, so the alert would fire every night or be useless; it cannot tell a broken site from a quiet one.
D=Advisor performance: Advisor makes configuration recommendations. It does not probe URLs or measure response times on a schedule.
T: Use Application Insights availability tests to check that an endpoint responds, from several locations, even when no users are active.
V: Application Insights, Azure Monitor alerts

@ AZ-900 D3 T3.4 applied use-case
S: A company runs a web application on servers in its own datacenter and another in a different public cloud. Developers want request rates, failure rates and dependency performance in Azure, ideally without changing code. What should they use?
A: Application Insights, enabled through its agent or an SDK; it monitors apps in Azure, on-premises or other clouds
B: Azure Resource Health, which tracks request and failure rates for any web application after it is registered
C: Azure Advisor, which collects request and dependency data from web applications both inside and outside Azure
D: Azure Service Health, which reports the failure rates of applications that run in the regions the company uses
K: A
G: ## Application Insights
**Application Insights** is the application performance monitoring (APM) feature of Azure Monitor. It monitors web applications wherever they run: in Azure, on-premises or in another cloud.
You can enable it in two ways:
- add an SDK (or OpenTelemetry instrumentation) to the application code, or
- enable the **Application Insights agent**, which needs no code changes.
It collects request rates, response times and failure rates, dependency calls and their performance, page load times, user and session counts, and server performance counters, and shows them in views such as the application map, failures and performance.
## Example
An app on an on-premises IIS server and another in a different cloud both send telemetry to Application Insights; the application map shows that slow responses come from calls to one database.
W: Application Insights: it is built for application telemetry, works for apps outside Azure, and can be enabled with an agent so no code changes are needed.
X: B=Resource Health: Resource Health reports the platform health of Azure resources. It does not measure request or failure rates and does not cover servers outside Azure.
C=Azure Advisor: Advisor makes best-practice recommendations for Azure resources. It does not collect telemetry from applications.
D=Service Health: Service Health reports Azure service incidents and maintenance. It knows nothing about your application's requests or failures.
T: Application Insights monitors application performance in Azure, on-premises and other clouds, through an SDK or a no-code agent.
V: Application Insights, Azure Monitor
