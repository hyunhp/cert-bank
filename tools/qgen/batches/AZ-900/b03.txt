# AZ-900 D3 Describe Azure management and governance (T3.1-T3.4), 5 questions per task

@ AZ-900 D3 T3.1 applied use-case
S: A small company plans to move a web app to Azure next quarter. Before anything is deployed, the owner wants a monthly cost estimate for an App Service plan, a managed database and storage, compared across two regions. Which tool should they use?
A: The Azure pricing calculator, which models the planned services and options without deploying anything
B: Cost analysis in Microsoft Cost Management, which breaks down the charges of resources already running
C: Azure Advisor cost recommendations, which find underused resources in an existing subscription
D: A Cost Management budget, which sends an alert when actual spending passes a set threshold
K: A
G: ## Estimating versus tracking cost
Azure cost tools fall into two groups, and the key question is whether the resources exist yet.
- **Before deployment**: the **pricing calculator** estimates what a planned set of services would cost. You add services, choose options such as region, tier, storage type and redundancy, and get an estimate. Nothing is provisioned and nothing is charged; the result is an estimate, not a quote.
- **After deployment**: **Microsoft Cost Management** works on real usage data. Cost analysis shows where money is spent, budgets and alerts warn when spending grows, and Azure Advisor points out resources you could shrink or remove.
## Example
A team modelling "one App Service plan + one database + blob storage" can switch the region in the pricing calculator and compare the two monthly estimates side by side, then use the figure as a baseline for budget approval.
W: Pricing calculator: it is built for planning. It estimates the cost of services you have not deployed yet, lets you compare regions, tiers and redundancy options, and provisions nothing.
X: B=Cost analysis: it analyses the actual charges of resources that already exist. With nothing deployed there is no cost data to break down.
C=Azure Advisor: Advisor evaluates deployed resources and suggests changes such as resizing an idle VM. It cannot price a design that exists only on paper.
D=Budget: a budget tracks real spending against a limit you set and alerts when thresholds are reached. It does not produce an estimate for planned services.
T: Estimate planned resources with the pricing calculator; analyse, budget and optimise real spending with Cost Management and Advisor.
V: Azure pricing calculator, Microsoft Cost Management, Azure Advisor

@ AZ-900 D3 T3.1 advanced troubleshooting
S: A team created a monthly budget in Microsoft Cost Management for its dev subscription with an alert at 100%. Spending passed the budget, the team received an email, but every VM kept running. What explains this?
A: A budget only notifies when thresholds are reached; resources keep running unless an action group runs automation
B: The budget failed because budgets apply only to resource groups and cannot be scoped to a whole subscription
C: Budgets stop resources only for production subscriptions, so the dev subscription was treated as exempt
D: The VMs kept running because a resource lock on the subscription overrides the budget's stop action
K: A
G: ## What a budget does
A **budget** in Microsoft Cost Management is a spending target for a scope such as a subscription or resource group, reset monthly, quarterly or yearly. You attach alert thresholds (for example 80% and 100%) based on actual or forecasted cost.
When a threshold is met, Azure sends notifications (email, and the alert shows in cost alerts). Microsoft's documentation is explicit: resources aren't affected and consumption isn't stopped.
## Adding automation
If you want something to happen, you can have the budget trigger an **action group**. The action group can call automation, for example a runbook or function that shuts down non-production VMs. That shutdown is your own automation, not built-in budget behaviour.
## Example
Dev budget alert at 90% → action group → automation stops all VMs tagged `Environment=Dev`.
W: Notify only: budgets are evaluated against cost data and send alerts when thresholds are met, but they never stop or delete resources by themselves. To act automatically, connect the budget to an action group that runs automation.
X: B=Subscription scope: budgets can be created at subscription scope as well as resource group and other scopes, and the alert email shows the budget did work.
C=Production-only stop: there is no built-in stop action for any subscription type. The behaviour is the same everywhere: notification only.
D=Lock overrides stop: a lock blocks deletes or changes, but the budget never tried to stop anything, so there was nothing for a lock to override.
T: A Cost Management budget alerts; it does not stop spending unless you wire an action group to automation.
V: Microsoft Cost Management, Azure Monitor action groups

@ AZ-900 D3 T3.1 applied comparison
S: A company compares two deployment options and sees different monthly costs for what looks like the same workload. Which TWO factors can change the cost of Azure resources? (Select TWO)
A: The region where the resources are deployed, because prices can differ between regions
B: Outbound data transfer leaving Azure datacenters, which is priced by billing zone
C: How many resource groups the same resources are spread across in the subscription
D: Tags attached to each resource for cost reporting and ownership tracking
E: Management groups placed above the subscriptions to organise policy and access
K: A,B
G: ## What drives Azure cost
Azure is pay-as-you-go: you pay for what you consume. The Learn module on cost lists these factors:
- **Resource type and settings**: VM size and cores, OS licensing, storage type, access tier and redundancy.
- **Consumption**: more usage costs more; reservations, savings plans and Spot VMs lower the rate.
- **Maintenance**: leftover disks or IP addresses from deleted VMs keep costing money.
- **Geography**: power, labour, taxes and fees differ, so the same resource can cost more in one region than another.
- **Network traffic**: some inbound transfers are free; outbound transfers are priced by billing zone (a grouping of regions for data transfer pricing).
- **Subscription type** (free allowances) and **Azure Marketplace** (third-party vendor charges).
## What does not add cost
Organising tools such as resource groups, management groups and tags are not on that list. They are containers and metadata that organise and describe resources; the bill comes from the resources themselves. They help you report on cost, but they do not change it.
W: A=Region: the same VM or storage account can have a different price in different regions because local costs differ.
B=Outbound data transfer: data leaving Azure datacenters is billed based on billing zones, so moving data between continents or to the internet adds cost.
X: C=Resource groups: a resource group is a logical container; the charges come from the resources inside it. Ten groups or one group holding the same resources cost the same.
D=Tags: tags are metadata (name-value pairs). They make costs easier to report on but do not change what the resources consume.
E=Management groups: management groups only organise subscriptions for policy and access. The bill comes from the resources in those subscriptions, not from the hierarchy.
T: Cost depends on what you run, how much, where, and how much data leaves Azure; organising constructs like resource groups, tags and management groups do not drive the bill.
V: Microsoft Cost Management

@ AZ-900 D3 T3.1 applied use-case
S: Several departments share one resource group that holds a single application, and the resources cannot be split up. Finance wants monthly cost reports per department. What is the simplest approach?
A: Apply a CostCenter tag to each resource and group the costs by that tag in Cost Management cost analysis
B: Place a resource lock on each department's resources so their charges appear on a separate invoice
C: Create a management group for each department and move the shared resource group under all of them
D: Assign an Azure Policy initiative per department so that compliance reports also show each team's spending
K: A
G: ## Tags as cost metadata
A **tag** is a name-value pair, such as `CostCenter=Sales` or `Environment=Prod`, attached to a resource, resource group or subscription. Tags add no cost and do not change how a resource works.
Because Cost Management can **group and filter costs by tag**, tags let you report on spending along lines that do not match your resource groups or subscriptions:
- allocate costs to internal cost centres
- track budgets for a team or workload
- find owners of expensive resources
## Example
`app-db` tagged `CostCenter=Sales` and `app-web` tagged `CostCenter=Marketing` live in the same resource group. In cost analysis, grouping by the `CostCenter` tag shows each department's share. Azure Policy can require the tag on new resources so reports stay complete.
W: CostCenter tag: tags work at resource level, so resources inside one shared resource group can still be attributed to different departments, and cost analysis can group costs by tag.
X: B=Resource lock: locks only prevent deletion or modification. They have nothing to do with billing or invoices.
C=Management group per department: management groups contain subscriptions, not resource groups, and each subscription sits under only one parent, so this cannot split one resource group's costs.
D=Policy initiative: Azure Policy reports whether resources meet rules. Compliance results are not cost reports, although a policy can require the tag that cost reports use.
T: Use tags (with cost analysis) to report costs by department, owner or environment when the resource structure does not match how you need to bill.
V: Microsoft Cost Management, Azure Resource Manager tags

@ AZ-900 D3 T3.1 advanced troubleshooting
S: An admin tagged a resource group with Environment=Prod. Later, cost analysis grouped by the Environment tag shows the VMs and disks inside that group as untagged. What is the reason?
A: Resources do not inherit resource group tags, so tag each resource, for example by using Azure Policy
B: Tags on a resource group appear in cost analysis only after a resource lock is also applied to that group
C: Tag values are case-sensitive, so cost analysis ignores any tag whose name begins with an uppercase letter
D: Tags take effect only on resources created by ARM templates, so resources made in the portal stay untagged
K: A
G: ## Tags do not flow downward
You can tag subscriptions, resource groups and individual resources, but **resources don't inherit the tags you apply to a resource group or a subscription**. A tag on the group describes the group itself.
To get the group's tag onto every resource, you can:
- add the tag to each resource (portal, Azure CLI, Azure PowerShell, templates), or
- assign an **Azure Policy** definition with the Modify effect, such as "Inherit a tag from the resource group", which adds the tag to new resources and, through remediation, to existing ones.
For cost reports only, Cost Management also has an optional **tag inheritance** setting (for EA, MCA and MPA billing accounts) that copies resource group and subscription tags onto child usage records, not onto the resources themselves. It is off unless someone enables it.
## Example
`rg-shop` has `Environment=Prod`. `vm-shop-01` inside it has no tags, so cost analysis grouped by `Environment` lists its cost as untagged until the tag is added to the VM itself.
W: No inheritance: tags apply only where they are set. Azure Policy can copy the resource group's tag to its resources so cost reports by tag become complete.
X: B=Lock required: locks protect against deletion or change and have no link to tagging or cost reporting.
C=Case-sensitivity: tag values are case-sensitive and tag names are not, but that never hides a tag because of an uppercase letter. The resources simply have no tag.
D=Templates only: tags can be added with the portal, Azure CLI, PowerShell, templates and the REST API; how a resource was created does not matter.
T: Tags are not inherited: tag resources directly or use Azure Policy to apply the resource group's tag to them.
V: Azure Policy, Microsoft Cost Management

@ AZ-900 D3 T3.2 applied use-case
S: Admins of a production storage account must keep changing its settings, but nobody, including Owners, should be able to delete it by accident. Which control fits best?
A: A Delete (CanNotDelete) resource lock on the storage account, which blocks deletion but allows changes
B: A ReadOnly resource lock on the storage account, which blocks deletion and keeps the settings editable
C: An Azure Policy assignment with the Allowed locations rule set to the storage account's current region
D: The Reader role for every admin on the storage account, so they can view it but not remove it
K: A
G: ## Resource locks
A **resource lock** protects a subscription, resource group or resource from accidental changes. Locks apply to **all users and roles**, even Owners; to do the blocked action you must remove the lock first.
There are two lock types (portal name / command-line name):
- **Delete / CanNotDelete**: users can read and modify the resource but cannot delete it.
- **Read-only / ReadOnly**: users can read but cannot modify or delete; it works much like giving everyone the Reader role.
Locks set on a parent scope are inherited by everything inside it.
## Locks versus RBAC and Policy
RBAC decides who may do what; a lock overrides those permissions for delete or change. Azure Policy checks resource properties (region, SKU, tags), not whether someone deletes a resource.
W: Delete lock: it blocks deletion for every user, including Owners, while still letting admins change settings, which is exactly the requirement.
X: B=ReadOnly lock: ReadOnly blocks updates as well as deletes, so admins could no longer change the settings.
C=Allowed locations: this policy only restricts where new resources may be created. It does nothing to stop the account being deleted.
D=Reader role: Reader would stop deletion but also stop the admins from changing any setting, and it does not protect against an Owner.
T: Prevent deletion but allow changes → Delete (CanNotDelete) lock; prevent both → ReadOnly lock.
V: Azure Resource Manager locks

@ AZ-900 D3 T3.2 advanced troubleshooting
S: A user with the Owner role tries to resize a VM and gets an error. The VM's resource group has a ReadOnly lock. What must happen before the resize can succeed?
A: The lock must be removed first, because locks apply to every user regardless of their role assignment
B: The user must also be given the User Access Administrator role, which allows actions on locked resources
C: An Azure Policy remediation task must run, because locks are released when a policy marks resources compliant
D: Microsoft support must approve the change, because only support can modify resources under a ReadOnly lock
K: A
G: ## Locks override permissions
A resource lock restricts all users and roles. Even if your role allows an action, a lock that blocks it wins. Learn describes changing a locked resource as a two-step process: remove the lock, then do the action you have permission for.
## Inheritance
A lock on a resource group applies to every resource in it, including resources added later, and the most restrictive lock in the chain applies. A ReadOnly lock blocks management updates such as resizing a VM or changing its configuration.
## Example
`rg-prod` has a ReadOnly lock → resizing `vm-app-01` fails for everyone → an authorised admin removes the lock (or replaces it with a Delete lock), resizes, and decides whether to restore it.
W: Remove the lock: locks restrict all users and roles, so even an Owner must remove the lock before performing the blocked change.
X: B=User Access Administrator: that role manages role assignments. No role bypasses a lock; adding roles does not change the result.
C=Policy remediation: Azure Policy and resource locks are separate features. Remediation fixes noncompliant resources; it never removes or relaxes locks.
D=Microsoft support: locks are your own control. Anyone with permission to manage locks can remove one; support is not involved.
T: A resource lock beats RBAC: even an Owner must remove the lock before deleting or changing what it protects.
V: Azure Resource Manager locks, Azure RBAC

@ AZ-900 D3 T3.2 applied use-case
S: A European company must make sure that no team can create Azure resources outside two approved EU regions, in every subscription. Which service should enforce this?
A: Azure Policy, assigning the Allowed locations definition at a scope above the subscriptions
B: Resource locks of type ReadOnly on each subscription, so that resources cannot be placed in other regions
C: Microsoft Purview, scanning the subscriptions and classifying data stored outside the approved regions
D: Microsoft Defender for Cloud, which builds the approved region list from the subscription's secure score
K: A
G: ## Azure Policy
**Azure Policy** lets you create, assign and manage rules about resource properties. A policy definition has a condition and an **effect**:
- **Deny** blocks a create or update request that breaks the rule.
- **Audit** allows it but marks the resource noncompliant.
- **Modify** or **DeployIfNotExists** fix the resource automatically.
Policies are assigned at a scope (management group, subscription, resource group) and are inherited by everything below it. Related policies can be grouped into an **initiative**.
## Built-in examples
- **Allowed locations** (Deny): restricts the regions where new resources may be created.
- **Allowed virtual machine size SKUs** (Deny): limits VM sizes.
- **Add a tag to resources** (Modify): adds a required tag when it is missing.
Assigning Allowed locations at a management group covers all subscriptions under it.
W: Azure Policy: the built-in Allowed locations definition denies deployments to any region not on the list, and assigning it high in the hierarchy applies it to every subscription.
X: B=ReadOnly locks: a ReadOnly lock blocks all changes in the subscription, so teams could not create resources anywhere, and locks have no notion of regions.
C=Microsoft Purview: Purview discovers and classifies data for governance and compliance. It reports on data, it does not block resource deployments.
D=Defender for Cloud: Defender assesses security posture and gives recommendations; it does not maintain region allow-lists or block deployments by location.
T: Enforce rules about how resources are configured (regions, SKUs, tags) with Azure Policy.
V: Azure Policy

@ AZ-900 D3 T3.2 applied use-case
S: A retailer keeps data in Azure SQL Database, in on-premises SQL Server and in Amazon S3. Compliance staff need one map of where sensitive data is, with classification and lineage. Which service should they use?
A: Microsoft Purview, for automated data discovery, classification and lineage across the whole estate
B: Azure Policy, which inspects the rows in each database and assigns a sensitivity label to each table
C: Azure Monitor Log Analytics, which collects data from all three sources into one workspace for queries
D: Azure Arc, which projects the S3 buckets and SQL servers into Azure and labels the sensitive columns
K: A
G: ## Microsoft Purview
**Microsoft Purview** is a family of data governance, risk and compliance solutions. It gives a unified view of data that lives on-premises, in multiple clouds and in SaaS services.
Two solution areas:
- **Unified data governance**: automated data discovery, sensitive data classification and end-to-end lineage. It can map data in Azure, SQL and Hive databases, on-premises stores and other clouds such as Amazon S3.
- **Risk and compliance**: built on Microsoft 365 services (Teams, OneDrive, Exchange) to protect sensitive data and manage regulatory requirements.
## Purview versus Azure Policy
Azure Policy governs **resources** (where they run, which SKU, which tags). Purview governs **data** (what it contains, how sensitive it is, where it came from).
W: Microsoft Purview: it discovers data across Azure, on-premises and other clouds, classifies sensitive content and shows lineage, giving compliance staff a single map.
X: B=Azure Policy: Policy evaluates resource properties such as region or SKU. It does not read the contents of databases or classify data.
C=Log Analytics: it stores and queries monitoring logs and metrics, not an inventory of business data and its sensitivity.
D=Azure Arc: Arc brings servers, Kubernetes clusters and data services under Azure management. It does not classify the data stored in them or build lineage.
T: Data discovery, classification and lineage across clouds → Microsoft Purview; rules about resource configuration → Azure Policy.
V: Microsoft Purview

@ AZ-900 D3 T3.2 applied definition
S: A company assigns a new Azure Policy that allows only certain VM sizes. Some VMs created last year use a size not on the list. How does Azure Policy treat those existing VMs?
A: It evaluates them and reports them as noncompliant; they keep running unless the company remediates them
B: It deletes them automatically, because Deny policies remove every resource that breaks the rule
C: It ignores them permanently, because a policy only ever applies to resources created after assignment
D: It applies a ReadOnly lock to them, so that nobody can change them until they meet the new rule
K: A
G: ## New rules, existing resources
When a policy is assigned, Azure Policy evaluates **all resources in scope**, including ones created before the assignment, and shows the results on its compliance dashboard.
- For **new** create or update requests, a Deny effect blocks anything that breaks the rule. Resizing an existing VM to a size not on the list is also blocked.
- **Existing** noncompliant resources are not deleted or stopped. They are flagged as noncompliant so you can act on them.
- For some effects (Modify, DeployIfNotExists) you can run a **remediation task** to fix existing resources automatically, for example adding a missing tag.
## Example
Policy "Allowed virtual machine size SKUs" assigned to a subscription → three old VMs show as noncompliant → the team plans to resize them in the next maintenance window; new VMs of a forbidden size are denied immediately.
W: Evaluate and report: Azure Policy evaluates existing resources too and marks them noncompliant without deleting them. Fixing them is a separate remediation step.
X: B=Automatic deletion: the Deny effect blocks requests; no policy effect deletes existing resources that break a rule.
C=New resources only: Azure Policy also evaluates resources that existed before the assignment, which is how the compliance dashboard finds them.
D=Automatic lock: Azure Policy does not create resource locks. Locks and policies are separate governance features.
T: Azure Policy flags existing noncompliant resources and blocks new violations; it never deletes resources on its own.
V: Azure Policy

@ AZ-900 D3 T3.3 applied use-case
S: An administrator works from a shared kiosk PC where installing software is blocked. They need to run a few Azure CLI commands against their subscription today. What should they use?
A: Azure Cloud Shell, a browser-based shell that is already authenticated and ships with the Azure CLI
B: Azure PowerShell installed locally on the kiosk PC, which provides the same commands as the Azure CLI

- **Azure portal**: a web-based graphical console for building, managing and monitoring resources, with custom dashboards.

**Azure Arc** extends Azure management and governance to resources running outside Azure: on-premises, at the edge or in other clouds. It works with Azure Resource Manager by **projecting** those resources into Azure, so they appear as Azure resources you can organise, tag, govern and monitor.
Resource types Arc can manage outside Azure:
- servers (Windows and Linux)

- Azure data services and SQL Server

@ AZ-900 D3 T3.3 applied definition
S: A team notices that a VM created in the Azure portal, with the Azure CLI or with Azure PowerShell behaves the same and obeys the same permissions. Why is that?
A: Every request from these tools goes to Azure Resource Manager, which authenticates and authorizes it
B: Every request runs inside Azure Cloud Shell, which converts portal clicks into the same Azure CLI commands
C: Every request is first stored in Azure Monitor, which replays it to the resource in the same order
D: Every request is approved by Azure Advisor, which checks it against best practices before deployment
K: A
G: ## Azure Resource Manager (ARM)
**Azure Resource Manager** is the deployment and management service for Azure. Whatever tool you use (portal, Azure CLI, Azure PowerShell, REST API, SDKs), the request goes to the same ARM API:
1. ARM authenticates and authorizes the request.
2. ARM sends it to the right Azure service, which performs the action.
Because all tools share one layer, results and capabilities are consistent.
## What ARM adds
- deploy and manage resources as a group
- declarative templates (JSON or Bicep) for repeatable deployments
- dependencies so resources deploy in the right order
- RBAC built into the management platform, plus tags for organisation and cost reporting
W: Azure Resource Manager: all management tools call the same ARM API, so the same authentication and RBAC checks apply no matter which tool sent the request.
X: B=Cloud Shell: Cloud Shell is just one place to run the CLI or PowerShell. The portal does not route requests through it.
C=Azure Monitor: Monitor collects metrics and logs; it does not process or replay management requests.
D=Azure Advisor: Advisor produces recommendations after resources exist. It does not approve requests.
T: Portal, CLI, PowerShell, REST and SDKs all go through Azure Resource Manager, which gives consistent results and access control.
V: Azure Resource Manager

@ AZ-900 D3 T3.3 applied use-case
S: A team must build identical dev, test and production environments many times a year. They want to describe the desired end state in files kept in source control and let Azure handle deployment order. What should they use?
A: Bicep files deployed through Azure Resource Manager as declarative infrastructure as code
B: Step-by-step portal instructions in a wiki that each engineer follows for every new environment
C: Azure Advisor recommendations exported to source control and replayed for each new environment
D: Resource locks set on the dev environment and copied to test and production by Azure Policy
K: A
G: ## Infrastructure as code (IaC)
**Infrastructure as code** means managing infrastructure through code and templates instead of manual steps. In Azure, IaC can start with Azure CLI or PowerShell scripts and grows into declarative templates:
- **ARM templates**: JSON files that declare the resources you want.
- **Bicep**: a declarative language that also deploys through Azure Resource Manager, with simpler, more concise syntax than JSON.
## Why declarative
You describe **what** should exist, not the step-by-step **how**. ARM validates the file, works out dependencies (create the virtual network before the VM that uses it), deploys in parallel where possible, and gives the same result every time you redeploy (idempotent).
## Example
`main.bicep` with a parameter `env` set to `dev`, `test` or `prod` and deployed three times gives three matching environments.
W: Bicep with ARM: Bicep files declare the desired end state, live in source control, and ARM orchestrates dependency order, so each environment is deployed the same way every time.
X: B=Portal instructions: manual steps are slow and error-prone, and they are not code that Azure deploys for you.
C=Advisor exports: Advisor recommendations describe improvements to existing resources. They cannot be replayed to create an environment.
D=Locks copied by Policy: locks prevent deletion or change; they do not create any resources, so no environment would be built.
T: Repeatable, declarative environments → infrastructure as code with Bicep or ARM templates deployed by Azure Resource Manager.
V: Bicep, Azure Resource Manager templates

@ AZ-900 D3 T3.3 applied comparison
S: A company moves from scripted, step-by-step deployments to ARM templates. Which TWO benefits of ARM templates should it expect? (Select TWO)
A: Declarative syntax: the template states which resources should exist instead of listing commands to run
B: Orchestration: Azure Resource Manager works out dependency order and deploys resources in parallel where it can
C: Isolation: each template can contain only one resource, which keeps every deployment small and simple
D: Enforcement: after deployment the template blocks every manual portal change to the deployed resources
E: Scope: a template can deploy only to the region of the subscription that the deploying user signed in from
K: A,B
G: ## Imperative scripts versus declarative templates
A script is **imperative**: "create this, then that, then configure the other". If a step fails or is run twice, you must handle it yourself.
An **ARM template** (JSON) or **Bicep** file is **declarative**: it states the end result. Azure Resource Manager then:
- validates the template before deploying
- creates resources in the right order based on dependencies, in parallel where possible
- gives repeatable results across environments
- supports modularity (nested templates or Bicep modules) and deployment scripts when extra setup is needed
## Limits to know
A template describes what to deploy; it is not a guard rail afterwards. Preventing later changes is the job of Azure Policy, RBAC or resource locks.
W: A=Declarative syntax: you define what to deploy, not each command, which removes most step-by-step scripting.
B=Orchestration: ARM handles dependency order and parallel creation automatically, so you do not script the sequence.
X: C=One resource per template: a single template can define many resources and whole solutions; modularity is optional, not a limit.
D=Blocks manual changes: a deployed template does not watch or block later edits. Use Azure Policy, RBAC or locks for that.
E=Signed-in region only: templates choose regions through parameters and resource definitions; the user's sign-in location does not restrict where resources go.
T: ARM templates and Bicep are declarative and let Azure Resource Manager handle ordering and parallel deployment for repeatable results.
V: Azure Resource Manager templates, Bicep

@ AZ-900 D3 T3.4 applied use-case
S: A startup wants personalized suggestions to reduce spending on underused VMs and to improve the reliability and security of its existing Azure resources. Which service should it check?
A: Azure Advisor, which evaluates existing resources and recommends changes for cost, reliability and more
B: Azure Service Health, which reports outages and planned maintenance for the Azure services and regions in use
C: The Azure pricing calculator, which estimates the cost of resources and options before they are deployed
D: Microsoft Purview, which scans the subscriptions and recommends cheaper storage tiers for classified data
K: A
G: ## Azure Advisor
**Azure Advisor** evaluates your deployed Azure resources and makes personalized best-practice recommendations. The dashboard covers all your subscriptions and can be filtered by subscription, resource group or service. Recommendations fall into five categories:
- **Reliability**: configuration risks to keeping apps running
- **Security**: threats and vulnerabilities
- **Performance**: changes that speed up applications
- **Operational excellence**: workflow and deployment improvements
- **Cost**: ways to reduce spending, for example resizing or shutting down underused VMs
Each recommendation has a suggested action you can take, postpone or dismiss, and you can be notified of new ones.
## Example
Advisor sees a VM with very low CPU use for weeks and recommends a smaller size or shutting it down.
W: Azure Advisor: it analyses the startup's own resources and gives cost, reliability, security, performance and operational excellence recommendations with suggested actions.
X: B=Service Health: it reports Azure-side incidents, maintenance and advisories, not how to configure or size your own resources.
C=Pricing calculator: it estimates planned costs and knows nothing about how existing VMs are used.

G: ## Three views of Azure health

@ AZ-900 D3 T3.4 advanced use-case
S: An admin wants an SMS sent to the on-call engineer whenever a VM's CPU stays above 80% for 10 minutes. Which TWO Azure Monitor components are needed? (Select TWO)
A: An alert rule with a metric condition on the VM's CPU percentage over the 10-minute period
B: An action group that defines who is notified, such as the on-call engineer's phone number
C: A Service Health alert that fires when Azure reports maintenance on the VM's host in the region
D: A Cost Management budget with a threshold based on the VM's forecasted compute spending
E: A Delete resource lock on the VM, so that Azure Monitor can read its CPU metrics continuously
K: A,B
G: ## Azure Monitor alerts
An Azure Monitor alert has two parts:
- **Alert rule**: what to watch and when to fire. It has a target (the VM), a signal and a condition. Rules can be **metric-based** (CPU above 80% over 10 minutes) or **log-based** (a query finds a specific error pattern).
- **Action group**: what happens when the rule fires. It lists notifications (such as email or SMS) and actions such as calling a webhook or automation. Action groups are reusable across Azure Monitor, Service Health and Azure Advisor.
## Example
Rule `cpu-high-vm01`: Percentage CPU > 80, averaged over 10 minutes → action group `oncall` → SMS to the on-call phone.
W: A=Metric alert rule: the rule defines the signal (CPU), the threshold (80%) and the time window (10 minutes) that make the alert fire.
B=Action group: it holds the notification targets, here the on-call engineer's phone for SMS.
X: C=Service Health alert: it notifies about Azure incidents and maintenance, not about your VM's CPU load.
D=Budget: budgets track spending, not performance metrics, and would never fire on CPU usage.
E=Delete lock: locks only prevent deletion. Azure Monitor collects platform metrics without any lock.
T: Azure Monitor alert = alert rule (condition) + action group (who is notified and what runs).
V: Azure Monitor
