# AZ-900 D3 Describe Azure management and governance: T3.2 Azure Policy and resource locks (9), T3.3 portal, Cloud Shell, CLI, PowerShell and Azure Arc (11)

@ AZ-900 D3 T3.2 applied use-case
S: A security team wants to track about twenty related security rules as one compliance goal. It wants to assign them to each subscription as a single item and add more rules later without creating new assignments. What should it create?
A: A policy initiative that groups the related policy definitions and is assigned as one unit
B: A management group that holds the twenty rules and applies them to each subscription below it
C: A custom Azure RBAC role that contains the twenty rules as permissions for the security team
D: A policy exemption that bundles the twenty rules so they can be tracked together on one report
K: A
G: ## Definitions, initiatives and assignments
Azure Policy has three main objects:
- **Policy definition**: one business rule written in JSON, with a condition and an **effect** (for example "storage accounts must not allow public access", effect Deny or Audit).
- **Initiative definition** (called a *policySet* in the Azure CLI and Azure PowerShell): a collection of policy definitions grouped toward one overarching goal, such as a security baseline.
- **Assignment**: a definition or initiative applied to a scope (management group, subscription, resource group or single resource).
## Why group into an initiative
An initiative is assigned and tracked as **one item**, and its compliance is reported as one overall state with per-policy detail. Microsoft recommends creating initiatives even when you start with one policy: when you later add a definition to the initiative, it automatically becomes part of the existing initiative assignments, so you do not multiply assignments.
## Example
Initiative `Security baseline` = "no public storage" + "require HTTPS" + "allowed VM SKUs" + ... → one assignment per subscription → one compliance view.
W: Policy initiative: an initiative groups related policy definitions toward one goal, is assigned as a single item, and definitions added later become part of the existing assignments automatically.
X: B=Management group: a management group is a container for subscriptions. It is a scope you assign policies to, not something that holds or groups policy rules.
C=Custom RBAC role: roles define which actions identities may perform. They cannot express rules about how resources must be configured or report compliance against them.
D=Policy exemption: an exemption removes a resource or scope from evaluation of an assignment. It is the opposite of grouping rules to enforce them.
T: Group related policy definitions into an initiative to assign and track them as one compliance goal.
V: Azure Policy

@ AZ-900 D3 T3.2 applied tradeoff
S: A company plans a rule that storage accounts must not allow public blob access. Before blocking anything, it wants to see which existing and new accounts break the rule while teams keep deploying normally. Which policy effect should it use first?
A: Audit, which marks noncompliant resources and logs a warning but lets every request continue
B: Deny, which rejects noncompliant requests and lists every blocked account on the dashboard
C: Modify, which changes the public access setting on each account as it is created or updated
D: DeployIfNotExists, which deploys a private endpoint for every account that allows public access
K: A
G: ## Policy effects
Every policy definition has one **effect** that decides what happens when a resource matches the rule:
- **Audit**: creates a warning event in the activity log and marks the resource noncompliant, but does not stop the request.
- **Deny**: fails the create or update request (HTTP 403 Forbidden). Existing resources that match are marked noncompliant.
- **Modify**: adds, updates or removes properties or tags during create or update; existing resources can be fixed with a remediation task.
- **DeployIfNotExists**: deploys a related resource (through a template) when it is missing.
## Start with Audit
Microsoft's guidance is to begin with an audit effect instead of an enforcement effect (deny, modify, deployIfNotExists). You learn how many resources the rule would affect, and nothing breaks existing deployments or automation. When the results look right, you switch the effect to Deny.
## Example
Week 1: assign the rule with Audit → dashboard shows 14 noncompliant accounts → owners fix them → week 4: change the effect to Deny.
W: Audit: it reports which resources break the rule and logs a warning event, but never blocks a deployment, which is exactly a "measure first" rollout.
X: B=Deny: Deny rejects noncompliant create and update requests immediately, so teams would no longer deploy normally.
C=Modify: Modify changes the resource during deployment. That alters what teams deploy instead of only reporting on it.
D=DeployIfNotExists: it deploys extra resources when a related resource is missing. It is an enforcement action, not a report-only check.
T: Roll out a new rule with the Audit effect to see its impact, then switch to Deny to enforce it.
V: Azure Policy

@ AZ-900 D3 T3.2 advanced use-case
S: Finance requires a CostCenter tag on every resource. New resources missing the tag should get a default value automatically, and hundreds of existing untagged resources should be fixed as well. What should the company use?
A: An Azure Policy with the Modify effect that adds the tag, plus a remediation task for existing resources
B: An Azure Policy with the Audit effect, which adds the missing tag during the daily compliance evaluation
C: A Delete lock on each resource group, which requires every resource to carry the tag before changes
D: An Azure Policy with the Deny effect, which blocks untagged resources and retags existing ones in bulk
K: A
G: ## Fixing resources with Azure Policy
Some effects change resources instead of only reporting on them:
- **Modify** adds, replaces or removes tags (and certain properties) on a resource **while it is created or updated**. The built-in definition "Add a tag to resources" uses it.
- **DeployIfNotExists** deploys a missing related resource.
## Remediation of existing resources
Effects act when a request is made. Resources that already exist and break the rule are only marked noncompliant during evaluation. To bring them into line you create a **remediation task**, which applies the Modify operations (or the DeployIfNotExists template) to existing resources.
Remediation runs under a **managed identity** attached to the policy assignment, which needs an Azure role that allows the change.
## Example
Assign "Add a tag to resources" with `CostCenter=Unassigned` → new resources get the tag at creation → a remediation task tags the 300 older resources.
W: Modify with remediation: Modify adds the tag to new or updated resources automatically, and a remediation task applies the same change to resources that already exist.
X: B=Audit: Audit only marks resources noncompliant and logs a warning. It never adds or changes a tag, during evaluation or at any other time.
C=Delete lock: a lock blocks deletion of resources. It has no notion of tags and cannot require or add them.
D=Deny: Deny blocks new untagged requests but cannot add a default value, and it does not retag existing resources; they are only reported as noncompliant.
T: To add a missing setting automatically, use the Modify (or DeployIfNotExists) effect, and run a remediation task to fix resources that already exist.
V: Azure Policy

@ AZ-900 D3 T3.2 advanced troubleshooting
S: A policy that blocks networking resource types is assigned at a subscription. One resource group in it must be allowed to hold network resources. An admin assigned a more permissive policy on that group, but deployments there are still denied. What should be done instead?
A: Exclude that resource group from the subscription-level assignment, then grant the network team access to it
B: Assign the more permissive policy to the subscription as well, so the newer assignment overrides the older one
C: Give the network team the Owner role on the resource group, because Owners are not evaluated by Azure Policy
D: Place a ReadOnly lock on the resource group, which pauses policy evaluation for the resources inside it
K: A
G: ## Inheritance of assignments
A policy assignment applies to its scope and everything below it: an assignment on a subscription covers every resource group and resource in that subscription.
## Azure Policy is an explicit deny system
Assignments are evaluated **independently** and the result is cumulative, most restrictive. A more permissive assignment lower in the hierarchy does not cancel a Deny from above: if any assignment denies a resource, it is denied. The only way to allow it is to change the denying assignment.
## Excluding a scope
An assignment can list **excluded scopes** (`notScopes`): child resource groups or resources that the assignment does not evaluate. Microsoft's own example: assign "no networking resources" at the subscription, exclude the resource group intended for networking infrastructure, then give trusted users access to that group.
## Policy and RBAC are separate
RBAC controls who can act; Azure Policy controls what the resulting resource may look like. Even if a user may perform an action, Azure Policy still blocks a noncompliant create or update.
W: Exclude the resource group: the subscription-level Deny keeps applying until that group is listed as an excluded scope of the assignment; access for the network team is then controlled with RBAC.
X: B=Newer assignment overrides: assignments do not override each other by age or scope. Each one is evaluated, and any Deny still blocks the request.
C=Owner role: Azure Policy evaluates the request regardless of the caller's role, so an Owner is denied just like anyone else.
D=ReadOnly lock: a lock does not pause policy evaluation. It would block all changes in the group, including the deployments the team needs.
T: Azure Policy denies are cumulative; to allow a child scope, exclude it from the denying assignment rather than adding a looser policy below it.
V: Azure Policy

@ AZ-900 D3 T3.2 applied troubleshooting
S: A developer with the Owner role on a subscription tries to create a premium storage account and gets a "disallowed by policy" error. Which statement explains the error?
A: An assigned Azure Policy with a Deny effect blocks the request, regardless of the role of the person making it
B: The Owner role cannot create storage accounts, because only the Storage Account Contributor role is able to
C: A resource lock on the subscription blocks every new storage account until the lock owner approves it
D: The subscription's spending budget was exceeded, so Azure blocks any new premium storage account request
K: A
G: ## How a request is checked
When someone creates or updates a resource, Azure Resource Manager checks the request in two separate ways:
- **Azure RBAC**: is this identity allowed to perform the action at this scope? Owner passes for almost everything.
- **Azure Policy**: does the resulting resource meet the assigned rules? This check ignores who is asking.
If a policy with the **Deny** effect matches, the request fails with HTTP 403 (Forbidden) and the error names the policy assignment that blocked it. Built-in definitions such as **Allowed storage account SKUs** work this way.
## RBAC plus Policy
Learn describes the two as complementary: RBAC manages user actions, Azure Policy manages resource state, and together they give full control. Holding a powerful role never exempts you from policy.
## Fixing it
Choose a permitted SKU, or ask the policy owner to change the assignment, add an exemption or exclude the scope.
W: Deny policy: a Deny effect rejects noncompliant create requests for everyone, including Owners, because Azure Policy evaluates the resource, not the caller's permissions.
X: B=Storage Account Contributor only: Owner has full rights to create and manage all resources in its scope, including storage accounts, so the role is not the cause.
C=Lock approval: locks block deletes or changes for everyone and have no approval workflow; the error message points to a policy, not a lock.
D=Budget exceeded: Cost Management budgets only send alerts. They never block resource creation, whatever the SKU.
T: A "disallowed by policy" error comes from an Azure Policy Deny assignment, which applies to every caller, even an Owner.
V: Azure Policy, Azure RBAC

@ AZ-900 D3 T3.2 applied comparison
S: An administrator is planning resource locks for a production environment. Which TWO statements about Azure resource locks are correct? (Select TWO)
A: A lock on a resource group is inherited by its resources, including resources added after the lock was set
B: Users with the Owner or User Access Administrator role can create and delete resource locks by default
C: A lock can be set on a management group so that every subscription below it inherits the same lock
D: A ReadOnly lock on a database server also stops applications from writing rows into its databases
E: A lock is removed automatically after its expiry date, which is set when the lock is first created
K: A,B
G: ## Lock scopes and inheritance
Resource locks can be applied to a **subscription**, a **resource group** or a **single resource**. They cannot be added to management groups.
A lock on a parent scope is inherited by everything inside it, even resources created later, and the most restrictive lock in the chain wins.
## Who manages locks
Creating or deleting a lock needs the `Microsoft.Authorization/locks/*` permissions. The built-in **Owner** and **User Access Administrator** roles include them; a custom role can grant them too. A lock stays until someone with those permissions removes it.
## Control plane only
Locks protect the resource itself from changes made through Azure Resource Manager (`management.azure.com`), the **control plane**. They do not restrict **data plane** operations that go to the service, so a ReadOnly lock on a SQL logical server stops it being changed or deleted but still lets applications create, update and delete data in its databases.
W: A=Inherited by new resources: locks on a parent apply to all child resources, including ones created after the lock was set.
B=Owner and User Access Administrator: these built-in roles hold the lock management permissions, so they can add and remove locks.
X: C=Management group lock: locks can be applied to subscriptions, resource groups and resources, but not to management groups.
D=Blocks data writes: locks apply to control plane operations only; reading and writing data inside the databases continues normally.
E=Automatic expiry: locks have no expiry date. A lock stays in place until a user with permission removes it.
T: Locks are inherited from subscription or resource group down, can be managed by Owners and User Access Administrators, and protect the resource, not the data inside it.
V: Azure Resource Manager locks

@ AZ-900 D3 T3.2 advanced troubleshooting
S: A test resource group holds twelve resources. Only one VM in it has a Delete lock. An admin deletes the whole resource group to clean up. What happens?
A: The entire delete operation is blocked, so none of the twelve resources or the group are deleted
B: The eleven unlocked resources are deleted, and the group remains with only the locked VM inside it
C: Everything is deleted, because a lock on a single resource is ignored when its parent group is deleted
D: The locked VM is moved to a new resource group automatically, and then the original group is deleted
K: A
G: ## Locks and resource group deletion
Deleting a resource group deletes everything in it. Azure Resource Manager checks locks on the group **and on every resource inside it** before doing anything.
Learn is explicit: if one resource has a Delete lock and you try to delete its resource group, the whole delete operation is blocked, even if the group and the other resources are unlocked. **A partial deletion isn't possible.**
## What to do
- Remove the lock from the VM (it needs `Microsoft.Authorization/locks` permissions, such as Owner or User Access Administrator), then delete the group, or
- Move the VM to another resource group first if it must survive, then delete the group.
## Related behaviour
A Delete lock on a resource or resource group also stops role assignments on it from being deleted, and a Delete lock on a group stops Resource Manager from cleaning up old deployment history.
W: Whole operation blocked: Resource Manager refuses the group deletion if any resource inside carries a Delete lock, and it never performs a partial delete.
X: B=Partial delete: Learn states that partial deletion isn't possible; nothing is deleted when one resource is locked.
C=Lock ignored: a resource-level lock is exactly what stops the parent group from being deleted. It is not bypassed by deleting the parent.
D=Automatic move: Azure never moves resources on its own to work around a lock; moving the VM would be a manual step by the admin.
T: One Delete lock on any resource blocks deletion of its whole resource group; Azure never deletes part of the group.
V: Azure Resource Manager locks

@ AZ-900 D3 T3.2 advanced definition
S: An admin puts a ReadOnly lock on the logical server that hosts an Azure SQL database. The ordering application keeps inserting and updating rows without errors. Why does the lock not stop these writes?
A: Locks apply only to control plane operations on the resource; data plane writes to the database are not restricted
B: ReadOnly locks take effect only after the next daily compliance evaluation cycle, so writes continue until it runs
C: The application signs in with an identity that holds the Owner role, and Owners can write through any ReadOnly lock
D: A ReadOnly lock on a logical server covers only its firewall rules, while each database needs its own separate lock
K: A
G: ## Control plane and data plane
Azure separates two kinds of operations:
- **Control plane**: managing the resource itself, sent to Azure Resource Manager at `https://management.azure.com` (create the server, change its settings, delete it).
- **Data plane**: using the service, sent to the service instance itself (run SQL statements against a database, upload a blob to `https://myaccount.blob.core.windows.net`).
## What locks protect
Resource locks apply **only to control plane operations**. They protect a resource from being changed or deleted, but they do not restrict how the resource performs its function. Learn's own example: a ReadOnly lock on a SQL Database logical server protects it from deletion or modification, while data in the databases can still be created, updated and deleted.
The same applies to storage: a lock on a storage account does not protect the blobs, files, queues or tables inside it from data plane deletes.
## Protecting data
To protect data, use data-level features (permissions in the database, backups, soft delete, immutability) rather than locks.
W: Control plane only: the lock stops changes to the server resource through Resource Manager, but SQL inserts and updates are data plane operations and are not affected.
X: B=Daily evaluation: locks are not evaluated on a schedule. They take effect as soon as they are created; that delay describes Azure Policy compliance scans.
C=Owner bypass: locks apply to every user and role, Owners included. The writes succeed because they are data operations, not because of a role.
D=Firewall rules only: a lock on the server covers the server and its child resources at the control plane; it is not limited to firewall rules.
T: Resource locks guard the resource (control plane), not the data inside it (data plane).
V: Azure Resource Manager locks, Azure SQL Database

@ AZ-900 D3 T3.2 applied definition
S: A governance team relies on the Azure Policy compliance dashboard. Which TWO events cause Azure Policy to evaluate resources and update their compliance state? (Select TWO)
A: A policy or initiative is newly assigned to a scope that contains the resources
B: The standard compliance evaluation cycle, which reevaluates assignments once every 24 hours
C: A user with the Reader role opens the resource's overview page in the Azure portal
D: A resource lock is added to the resource group that contains the evaluated resources
E: The subscription's monthly invoice is generated and the charges are posted in Cost Management
K: A,B
G: ## When Azure Policy evaluates
Azure Policy does not check resources continuously in real time. Evaluation is triggered by specific events:
- a resource is **created or updated** in a scope that has an assignment
- a policy or initiative is **newly assigned** to a scope
- an assignment or its definition is **updated**
- the **standard compliance evaluation cycle**, which reevaluates all assignments once every 24 hours
- an **on-demand scan** started with Azure CLI, Azure PowerShell, REST or other tooling
Large scopes can take time to finish, so compliance results appear after evaluation completes, not instantly.
## What does not trigger evaluation
Reading or viewing a resource, adding a lock, or billing events do not change the resource's properties, so they do not start a policy evaluation.
W: A=New assignment: assigning a policy or initiative to a scope starts an evaluation of all resources in that scope, including existing ones.
B=24-hour cycle: every assignment is automatically reevaluated once every 24 hours, which keeps compliance data current.
X: C=Viewing a resource: reads in the portal do not change the resource and are not an evaluation trigger.
D=Adding a lock: locks are a separate feature and adding one does not start a policy compliance scan.
E=Invoice generation: billing events in Cost Management have no link to Azure Policy evaluation.
T: Azure Policy evaluates on resource changes, new or changed assignments, a 24-hour cycle and on-demand scans.
V: Azure Policy

@ AZ-900 D3 T3.3 applied use-case
S: A new operations manager has no scripting experience. She wants to create a few resources with guided forms and build a personal dashboard that shows the health of her team's key resources. Which tool should she use?
A: The Azure portal, a web-based graphical console with custom dashboards for an organized view
B: Azure PowerShell, a set of cmdlets that return objects and can be combined into reusable scripts

Azure offers several ways to manage the same resources:

@ AZ-900 D3 T3.3 applied use-case
S: A Windows server team already automates its on-premises work with PowerShell scripts that pass objects between commands. It now wants to manage Azure resources with the least learning effort. Which tool fits best?
A: Azure PowerShell, the Az module whose verb-noun cmdlets return objects in a PowerShell session
B: The Azure CLI, whose commands follow Bash-style syntax and feel most natural on Linux systems
C: The Azure portal, whose graphical blades can be recorded as PowerShell scripts for later reuse
D: Azure Arc, which runs the existing on-premises PowerShell scripts against Azure resources
K: A
G: ## Azure CLI and Azure PowerShell
Both tools create and manage Azure resources, both are cross-platform (Windows, macOS, Linux), and both are available in Azure Cloud Shell. Learn calls them functionally equivalent; the main difference is the language.

Learn's advice: pick the tool that uses your existing experience and shortens your learning curve. Teams working mostly with Windows and PowerShell → Azure PowerShell; teams working mostly with Linux and Bash → Azure CLI.
W: Azure PowerShell: it matches the team's PowerShell skills, uses familiar verb-noun cmdlets and returns objects, so existing habits and scripts carry over.
X: B=Azure CLI: it would work, but its Bash-like syntax suits Linux-focused teams and means more to learn for a PowerShell team.
C=Portal recording: the portal is a graphical console; it does not record blade actions as reusable PowerShell scripts.
D=Azure Arc: Arc manages servers and clusters outside Azure. It is not a way to run scripts against Azure resources.
T: Choose Azure PowerShell for PowerShell and Windows-focused teams, and Azure CLI for Bash and Linux-focused teams; both manage the same resources.
V: Azure PowerShell, Azure CLI

@ AZ-900 D3 T3.3 applied use-case
S: An administrator uses Azure Cloud Shell every day and keeps helper scripts and SSH keys in her home directory. She wants those files to still be there in tomorrow's session. What makes this possible?
A: An Azure Files share in a storage account that Cloud Shell mounts and uses to persist her $HOME directory
B: The Cloud Shell host VM, which Microsoft keeps running for each user between sessions indefinitely
C: The browser's local storage, which keeps a copy of the Cloud Shell file system on her own computer
D: An Azure Arc-enabled server, which syncs the Cloud Shell home directory to her on-premises machine
K: A
G: ## How Cloud Shell works
**Azure Cloud Shell** is an interactive, authenticated, browser-accessible terminal with **Bash** or **PowerShell**. Microsoft manages it, and it comes with the Azure CLI, Azure PowerShell and other common tools preinstalled.
Each session runs on a **temporary host** provided per session and per user. When the session ends (including after a period without activity), that host goes away.
## Persisting files
To keep files between sessions, Cloud Shell uses an **Azure Files share** in a storage account you choose or create on first use:
- your `$HOME` directory (scripts, SSH keys, profile settings) is saved in a disk image stored in that share and synced automatically
- the share is also mounted as `clouddrive` inside `$HOME`
Use of the Cloud Shell host is free; the storage account is billed at normal storage rates. If you start Cloud Shell without a storage account, files do not survive the session.
W: Azure Files share: Cloud Shell stores the $HOME disk image in a mounted Azure Files share, so scripts and keys are available again in every new session.
X: B=Host kept running: the host is temporary and created per session; it is not kept running between sessions.
C=Browser local storage: Cloud Shell files live in Azure, not in the browser; that is why the same files appear from any device.
D=Arc-enabled server: Azure Arc manages machines outside Azure and has no role in storing Cloud Shell files.
T: Cloud Shell sessions run on temporary hosts; files persist only through the Azure Files share mounted for $HOME.
V: Azure Cloud Shell, Azure Files

@ AZ-900 D3 T3.3 applied troubleshooting
S: An auditor has only the Reader role on a subscription. She opens Azure Cloud Shell from the portal and runs an Azure CLI command to stop a VM, but the command fails with an authorization error. Why?
A: Cloud Shell signs in as her own account, so commands are limited to the permissions her roles grant
B: Cloud Shell runs read-only commands only, so stopping a VM requires installing the Azure CLI locally
C: Cloud Shell can stop VMs only from its PowerShell experience, so the Bash experience was the problem
D: Cloud Shell needs Azure Arc enabled on the VM before any command can change the machine's state

G: ## Cloud Shell identity
Azure Cloud Shell is **authenticated with your Azure credentials**. When you open it, it already knows who you are and what permissions you have; there is no separate service account with extra rights.
Every Azure CLI or Azure PowerShell command in Cloud Shell is sent to Azure Resource Manager as **you**, so Azure RBAC applies exactly as it does in the portal or on a local workstation.

**Reader** allows viewing resources but not changing them. Starting, stopping or restarting a VM is an action (a POST request to Resource Manager) that Reader does not include, so the request is refused with an authorization error.
## Both shells are equal
Bash (with the Azure CLI) and PowerShell (with Azure PowerShell) in Cloud Shell manage the same resources; switching shells changes the syntax, not the permissions.

C=PowerShell only: both Cloud Shell experiences can manage VMs; the shell choice changes syntax, not permissions.
D=Arc required: Azure VMs are already Azure Resource Manager resources. Azure Arc is for machines outside Azure and is not needed here.
T: Cloud Shell acts with the signed-in user's own permissions; it never grants more than their Azure RBAC roles.

@ AZ-900 D3 T3.3 applied tradeoff
S: Every Monday an engineer performs the same fifteen portal steps to create a test resource group, a storage account and a VM. Mistakes are common, and colleagues need to repeat the task the same way. What is the best improvement?
A: Capture the steps in an Azure CLI or Azure PowerShell script that anyone can rerun the same way
B: Pin the three resources to a custom portal dashboard so each step is easier to find the next time
C: Connect the test machines to Azure Arc so the portal remembers and replays the previous week's steps
D: Place a Delete lock on the resource group so the engineer can reuse it instead of creating it each week
K: A
G: ## Portal versus command-line tools
The **Azure portal** is ideal for exploring, one-off tasks and visual monitoring. For tasks repeated often, clicking through the same steps is slow and error-prone.
Learn's comparison of command-line tools makes the point: every portal action translates to code that reads, creates, modifies or deletes resources, and **sharing a script is much easier than a lengthy wiki page with time-consuming screenshots**.
## Scripting with the CLI or PowerShell
Azure CLI commands or Azure PowerShell cmdlets can be run once for a quick change, or captured in a **script** to make a process **repeatable and automatable**: the routine setup, teardown and maintenance of one or several connected resources.
## Example
Save `az group create --name rg-test --location westeurope` and the storage account and VM commands in one script file; anyone can then run it from a workstation or Cloud Shell and get the same result.
W: CLI or PowerShell script: a script captures the steps once, removes manual mistakes and lets any colleague repeat the task identically.

S: A company plans to connect forty physical Linux and Windows servers in its datacenter to Azure Arc. What must happen on each server for it to appear and be managed in Azure?

G: ## Azure Arc-enabled servers
Azure Arc-enabled servers let you manage **Windows and Linux physical servers and virtual machines hosted outside Azure**, on a corporate network or with another cloud provider. Azure calls them **hybrid machines**.
## Connecting a machine
- Install the **Azure Connected Machine agent** on each machine, manually or at scale with a deployment method that suits you. The agent communicates **outbound** to Azure over TCP port 443; no inbound ports are needed.
- Each connected machine becomes a resource with an **Azure resource ID**, so it can sit in a resource group next to native Azure resources, carry tags and receive RBAC assignments.
- The agent sends a regular heartbeat to the service; if the heartbeats stop, the machine shows as Disconnected.
## What you can do then
Govern with Azure Policy machine configuration, protect with Microsoft Defender for Cloud, manage updates with Azure Update Manager and monitor with Azure Monitor, much as for native Azure VMs, while the server keeps running where it is.
W: Connected Machine agent: installing the agent connects the server to Azure Arc, and it then appears as a hybrid machine with its own resource ID that can be grouped, tagged and governed.
X: B=Migrate to Azure: Arc manages machines where they already run; moving them into Azure VMs is migration, not Arc.
C=VPN per server: Arc does not need a VPN tunnel per server or inbound ports; the agent connects from the server to Azure.
D=Azure Stack hardware: Arc works with your existing physical servers and VMs; no hardware replacement is required.
T: Install the Azure Connected Machine agent to turn an on-premises server into an Azure Arc hybrid machine with an Azure resource ID.
V: Azure Arc

S: An admin plans to onboard the company's existing Azure VMs to Azure Arc so that Azure Policy and tags can be applied to them. A colleague says this is unnecessary. Why is the colleague right?

G: ## What Azure Arc is for
Azure Arc **projects non-Azure resources into Azure Resource Manager**, so that servers, Kubernetes clusters and data services running on-premises, at the edge or in another cloud can use Azure governance and management.

An Azure VM is created through Azure Resource Manager in the first place. It already has a resource ID and can be placed in resource groups, tagged, covered by Azure Policy assignments, controlled with RBAC and monitored with Azure Monitor.

@ AZ-900 D3 T3.3 applied definition
S: In a briefing, an architect says Azure Arc "projects" on-premises servers into Azure Resource Manager. What does this mean for those servers?
A: Each server appears as an Azure resource that can be organized, tagged and governed while it keeps running on-premises
B: Each server is copied into an Azure region as a standby replica that takes over if the on-premises server fails
C: Each server's disks are uploaded to Azure Storage so that its data is backed up and stored inside Azure
D: Each server is converted into an Azure virtual machine, and the on-premises copy becomes a read-only image
K: A
G: ## Projection into Azure Resource Manager
Azure Resource Manager is the management layer for everything in Azure. Azure Arc "projects" non-Azure resources into it: it creates an Azure **representation** of the server, cluster or data service, while the actual workload keeps running where it is.
## What the projection gives you
- a resource in a resource group with its own Azure resource ID
- organisation with management groups, resource groups and tags
- search and inventory with Azure Resource Graph
- access control with Azure RBAC and governance with Azure Policy
- monitoring, security and updates through Azure services (Azure Monitor, Microsoft Defender for Cloud, Azure Update Manager)
Learn's summary: Azure Arc lets you manage resources outside Azure **as if they are running in Azure**, using familiar Azure tools wherever they live.
## What it is not
Arc does not move, copy, replicate or back up the workload; disaster recovery and backup are separate services such as Azure Site Recovery and Azure Backup.
W: Azure representation: projection gives each server an Azure resource that can be organised, tagged, secured and governed with Azure tools, while the server itself stays on-premises.
X: B=Standby replica: replicating machines for failover is disaster recovery (Azure Site Recovery), not Arc projection.
C=Disk upload: Arc does not copy server data into Azure; backing up data is the job of Azure Backup.
D=Converted to Azure VM: conversion into Azure VMs is migration. With Arc the server keeps running on its own hardware.
T: Azure Arc projection = an Azure Resource Manager representation of an outside resource, managed with Azure tools while it runs where it is.
V: Azure Arc, Azure Resource Manager
