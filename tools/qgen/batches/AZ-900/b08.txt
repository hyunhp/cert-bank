G: ## Geo-replication and the secondary region
With **GRS** and **GZRS**, Azure Storage copies your data asynchronously to a **secondary region** hundreds of miles away. **Microsoft Entra Conditional Access** is Microsoft's Zero Trust policy engine. It runs after the first authentication factor and works like an if-then statement:

@ AZ-900 D2 T2.4 advanced troubleshooting
S: A developer has the Reader role assigned at the subscription scope. An administrator also assigns the developer the Contributor role on the resource group rg-app in that subscription. What can the developer now do?
A: Create and change resources in rg-app, and only view resources in the subscription's other resource groups
B: Only view resources in rg-app, because the Reader role on the subscription is more restrictive and wins
C: Create and change resources in every resource group, because Contributor spreads up to the subscription
D: Nothing in rg-app until the Reader assignment is removed, because two assignments on one scope conflict
K: A
G: ## Azure RBAC is additive
Azure role-based access control uses an **allow model**. Each role assignment adds permissions; the effective permissions on a resource are the **union** of all role assignments that apply to it, directly or through inheritance. If one assignment grants read and another grants write on the same resource group, the user has both.
## Inheritance flows down, not up
Scopes form a hierarchy: management group > subscription > resource group > resource. A role assigned at a parent scope is inherited by every child scope, but an assignment at a child scope never spreads up to the parent or across to siblings.
## What actually blocks access
- With no applicable allow assignment, the action is not allowed (access is denied by default).
- A **deny assignment** blocks actions even when a role allows them.
Example: Reader at `/subscriptions/<id>` plus Contributor at `/subscriptions/<id>/resourceGroups/rg-app` = read everywhere in the subscription, read and write in rg-app.
W: Write in rg-app, read elsewhere: Reader inherited from the subscription gives view access everywhere, and the Contributor assignment adds manage rights only within rg-app; RBAC combines both.
X: B=Reader wins: Azure RBAC does not pick the most restrictive role; permissions from all assignments add together, so Contributor's rights apply in rg-app.
C=Contributor spreads up: inheritance flows from parent to child scopes only; a resource group assignment does not reach the subscription or other resource groups.
D=Assignments conflict: multiple role assignments are normal and simply combine; only a deny assignment would block an action that a role allows.
T: Azure RBAC permissions are the union of all applicable role assignments, and assignments inherit downward, never upward.
V: Azure RBAC

S: A team lead has the Contributor role on the resource group rg-sales. She can create and delete VMs and storage accounts there, but when she tries to give a new colleague the Reader role on rg-sales, the role assignment fails. What is the cause?

G: ## Owner, Contributor, Reader
The three fundamental built-in roles of Azure RBAC:
- **Owner**: full access to manage all resources, **including assigning roles** to others.
- **Contributor**: full access to manage all resources, but **cannot assign roles** in Azure RBAC.
- **Reader**: can view all resources but make no changes.

Example: to let the team lead onboard colleagues to rg-sales, an owner assigns her Role Based Access Control Administrator (or Owner) on rg-sales.

B=Global Administrator approval: Azure RBAC assignments need no approval by a Microsoft Entra directory role; anyone with role-assignment permission at the scope can make them.
D=Conditional Access first: Conditional Access controls how users sign in; it is not a prerequisite for receiving an Azure role assignment.
T: Contributor can manage everything in its scope except access; granting roles needs Owner, User Access Administrator or Role Based Access Control Administrator.

@ AZ-900 D2 T2.4 applied use-case
S: A company has 12 subscriptions under one management group and plans to add more next year. External auditors must be able to view all resources in every current and future subscription under that management group, but must not change anything. What is the simplest approach?
A: Assign the Reader role to the auditors' group separately in each of the 12 subscriptions and repeat it for new ones
B: Assign the Reader role to the auditors' group once at the management group that contains all the subscriptions
C: Assign the Contributor role to the auditors' group at the management group and apply a read-only resource lock
D: Assign the Reader role to the auditors' group on every resource group, because subscriptions cannot be a scope
K: B
G: ## Choosing the scope of a role assignment
An Azure RBAC role assignment applies at one of four scopes:
- **Management group**: a collection of subscriptions (and nested management groups).
- **Subscription**.
- **Resource group**.
- **Single resource**.
Access granted at a parent scope is **inherited** by all child scopes, including children created later. Assigning a role at the highest scope that matches the requirement keeps administration simple.
## Pick the role, then the scope
- **Reader** lets the auditors view every resource without making changes, which fits "view but not change".
- Assigning it once at the **management group** covers all 12 subscriptions and every subscription that is later moved or created under it.
Example: assign Reader to the group `grp-external-auditors` at `/providers/Microsoft.Management/managementGroups/mg-corp`.
W: Reader at the management group: one assignment is inherited by every subscription, resource group and resource below it, including subscriptions added later, and Reader allows viewing only.
X: A=Reader per subscription: it works today but means 12 assignments plus one more for every new subscription, which is the opposite of the simplest approach and easy to miss.
C=Contributor with a lock: Contributor grants write access, and relying on a lock to undo that is fragile; the requirement is simply read-only access, which Reader gives directly.
D=Reader per resource group: subscriptions and management groups are valid scopes, and assigning per resource group would multiply the work and miss new resource groups.
T: Give the right role at the highest scope that matches the need; inheritance carries it to every current and future child.
V: Azure RBAC, Azure management groups

@ AZ-900 D2 T2.4 applied definition
S: A company redesigns its network so that each application sits in its own segment, traffic between application tiers is encrypted end to end, and analytics watch for unusual movement between systems. The security architect says the design must limit the damage of an attacker who is already inside. Which Zero Trust principle is this?
A: Verify explicitly, which authenticates and authorizes every request using identity, location and device signals
B: Use least privilege access, which grants just-in-time and just-enough access through risk-based policies
C: Assume breach, which segments access to limit impact, verifies encryption, and uses analytics to detect threats
D: Shared responsibility, which divides the security tasks for a cloud service between the customer and Microsoft
K: C
G: ## The three Zero Trust principles
Zero Trust assumes the worst case and protects resources with that expectation. It does not treat any network as safe:
- **Verify explicitly**: always authenticate and authorize based on all available data points.
- **Use least privilege access**: limit access with just-in-time and just-enough access (JIT/JEA), risk-based adaptive policies and data protection.
- **Assume breach**: limit the potential impact by **segmenting** access, **verify end-to-end encryption**, and use **analytics** for visibility and threat detection.
## Spotting assume breach
Assume breach is about the *blast radius*: if an attacker gets in, segmentation keeps them from moving freely, encryption keeps intercepted traffic useless, and analytics notice the lateral movement. Verify explicitly and least privilege, by contrast, are about how each request is checked and how much access is granted.
Example: a compromised web server in the `web` segment cannot open connections to the payroll database segment, and an analytics rule alerts on its attempts.
W: Assume breach: segmenting applications, encrypting traffic end to end and using analytics to spot unusual movement are the exact practices of this principle, aimed at limiting an attacker already inside.
X: A=Verify explicitly: it is about checking every request with all available signals, not about segmenting networks and limiting the impact of an intruder.
B=Use least privilege access: it limits how much access a verified user or app receives; the scenario is about containing damage, not about sizing permissions.
D=Shared responsibility: it is a cloud model that divides security duties between provider and customer, not one of the Zero Trust principles.
T: Segmentation, end-to-end encryption and threat analytics to contain an intruder: the Zero Trust principle assume breach.
V: Zero Trust

@ AZ-900 D2 T2.4 applied comparison
S: A company is mapping its Azure security controls to the defense-in-depth model. Which TWO controls belong to the perimeter layer? (Select TWO)
A: Azure DDoS Protection that filters large-scale attacks before they affect service availability
B: Network security group rules that allow only required traffic between subnets inside a VNet

G: ## Defense in depth
Defense in depth protects data with several layers, so that if one layer is breached the next one is already in place. Each layer slows the attack and gives security teams alerts to act on. From the outside in:
- **Physical security**: securing buildings and datacenter hardware.
- **Identity and access**: SSO, multifactor authentication, auditing of sign-ins and changes.
- **Perimeter**: **DDoS protection** to filter large-scale attacks, and **perimeter firewalls** to identify and alert on malicious attacks against the network.

The perimeter layer faces the outside world (traffic arriving at the edge). The network layer limits traffic between your own resources once inside.

C=Endpoint protection and patching: securing virtual machines against malware and unpatched systems is the compute layer.
E=Secrets in Azure Key Vault: keeping secrets out of code is an application layer practice.
T: In defense in depth, DDoS protection and edge firewalls form the perimeter layer; controls between internal resources belong to the network layer.

S: A company uses Microsoft Entra Domain Services so legacy apps on Azure VMs can use Kerberos. An administrator creates a new user account directly in the managed domain with Active Directory admin tools. The user can sign in to the legacy app but cannot sign in to Microsoft 365 or the Azure portal. What is the reason?
A: Accounts created in a managed domain are kept for a trial period and appear in Microsoft Entra ID only after seven days
B: The managed domain's two domain controllers must first be patched by the administrator before accounts can sync out

D: The managed domain syncs one way from Microsoft Entra ID, so accounts created in it are not synced back to the cloud

G: ## How Microsoft Entra Domain Services gets its identities
**Microsoft Entra Domain Services** provides a **managed domain**: domain join, Group Policy, LDAP and Kerberos/NTLM authentication, with Azure deploying and maintaining two Windows Server domain controllers (a replica set), including patching and backups.
Synchronization is **one way**: users, groups and credential hashes flow **from Microsoft Entra ID into the managed domain**. You can create objects directly in the managed domain, but they are **not synchronized back** to Microsoft Entra ID.
## Hybrid chain
With on-premises Active Directory, **Microsoft Entra Connect** syncs on-premises accounts to Microsoft Entra ID, which then syncs them to the managed domain: on-premises AD > Microsoft Entra ID > managed domain.
## Practical rule
Create cloud users in Microsoft Entra ID (or on-premises AD in a hybrid setup) so they exist everywhere; create objects directly in the managed domain only when they are needed just there, such as service accounts for a legacy app.
Example: `svc-legacyapp` created in the managed domain works for the app's Kerberos sign-in but never appears in Microsoft Entra ID.
W: One-way sync from Microsoft Entra ID: the managed domain receives identities from Microsoft Entra ID but does not send any back, so an account created only in the managed domain does not exist for Microsoft 365 or the Azure portal.
X: A=Seven-day trial delay: there is no delayed sync from the managed domain; objects created there are never synchronized to Microsoft Entra ID at all.
B=Administrator patches the DCs: Azure manages, patches and backs up the domain controllers of the managed domain, and no patching would make sync run in the other direction.
C=Device join required: device identity can be a Conditional Access signal, but the user's problem is that the account itself does not exist in Microsoft Entra ID.
T: Microsoft Entra Domain Services syncs one way, from Microsoft Entra ID into the managed domain; create users in Microsoft Entra ID.
