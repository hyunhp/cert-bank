# AZ-900 D3 T3.1 cost management (16) and T3.2 Microsoft Purview (4)

@ AZ-900 D3 T3.1 applied troubleshooting
S: A developer deleted a test VM last month. This month, cost analysis still shows charges in the same resource group for a managed disk and a public IP address. What is the most likely reason?
A: Deleting a VM can leave its disks, IP addresses and other network resources behind, and they keep billing until removed
B: Azure keeps billing a deleted VM's disk and IP address for a fixed retention period and then removes them automatically
C: The resource group itself carries a monthly charge that cost analysis splits across the disk and IP address meters
D: Cost analysis shows the deleted VM's final compute charges under its disk and IP meters until the billing cycle closes
K: A
G: ## Maintenance as a cost factor
Microsoft lists **maintenance** as one of the factors that affect Azure cost. When you create a VM, Azure also creates supporting resources: an OS disk (and maybe data disks), a network interface, and often a public IP address.
These are separate resources with their own meters. When you delete the VM, those extra resources may not be deleted at the same time, either on purpose (you want to keep the disk) or by accident.
## Why it matters
Anything that still exists can still be billed. A forgotten disk or IP address quietly adds cost every month until someone removes it.
## Example
A resource group `rg-test` once held `vm-test01`. After the VM was deleted, `vm-test01_OsDisk` and `vm-test01-ip` are still listed. Cost analysis grouped by resource shows exactly these two lines, and deleting them (or the whole resource group, if nothing else is needed) stops the charges.
W: Leftover resources: a VM's disks, network interface and public IP address are separate resources. Deleting the VM does not always delete them, and each one that remains keeps its own charges, which is why cleaning up regularly is part of controlling cost.
X: B=Fixed retention period: Azure does not hold and later auto-delete a deleted VM's leftovers. They stay until someone removes them, so waiting will not stop the charges.
C=Resource group charge: a resource group is a free logical container. The charges come from the resources inside it, here the disk and the IP address.
D=Final compute charges: compute for a deleted VM stops when the VM is gone; Cost Management reports meters per resource and does not relabel compute as disk or IP usage.
T: Deleting a VM may leave disks and IP addresses behind; regular cleanup of unused resources is part of cost control.
V: Microsoft Cost Management, Azure Virtual Machines

**Azure Marketplace** lets you buy Azure-based solutions from third-party vendors: a preconfigured web server, a VM with specialised software installed, a managed backup service and so on. Marketplace solutions are certified against Azure policies and standards.

D=Mandatory reservation: Marketplace VMs can run pay-as-you-go. Reservations are an optional discount you choose, not a requirement of Marketplace images.

@ AZ-900 D3 T3.1 applied definition
S: An architect reads that outbound data transfer prices depend on "zones" and assumes this means the availability zones inside a region. What is a billing zone in Azure?
A: A geographical grouping of Azure regions used for data transfer pricing, which is different from an availability zone
B: A physically separate group of datacenters inside one region, each with its own power, cooling and networking
C: A pair of regions in the same geography that Microsoft uses to order platform updates and regional recovery
D: A logical container inside a subscription that groups resources so their costs show up on one invoice line
K: A
G: ## Two different kinds of "zone"
Azure uses the word *zone* in two unrelated ways.
- **Availability zone**: physically separate datacenters within one region, each with independent power, cooling and networking. It is a resiliency concept.
- **Billing zone**: a geographical grouping of Azure regions used only for **data transfer pricing**. It is a billing concept.
## How billing zones affect cost
Bandwidth is data moving in and out of Azure datacenters. Some inbound transfers are free, while outbound transfers are priced by billing zone. That is why moving data within Europe costs less than moving it from Europe to Asia or South America.
## Example
Copying backups from a West Europe resource to North Europe stays within one geography and costs less than sending the same data to a region in another continent.
W: Billing zone: Microsoft defines it as a geographical grouping of regions for data transfer pricing, and states that billing zones are different from availability zones.
X: B=Availability zone: this describes an availability zone, a resiliency feature inside one region. It plays no part in how outbound data transfer is priced.
C=Region pair: this describes paired regions, which relate to update sequencing and recovery planning, not to data transfer price groups.
D=Resource group: a container that groups resources is a resource group. It organises resources and does not define bandwidth prices.
T: A billing zone groups regions for data transfer pricing; it is unrelated to availability zones.
V: Azure bandwidth (data transfer)

**Bandwidth** in Azure means data moving into and out of Azure datacenters.

C=Included in storage price: data transfer is its own cost factor. Downloads out of Azure can appear as bandwidth charges in addition to storage charges.
D=Availability zone pricing: transfer prices are based on billing zones, which group regions. Availability zones are a resiliency feature and do not remove bandwidth charges.
T: Data going into Azure is often free; data leaving Azure is what is priced by billing zone.

@ AZ-900 D3 T3.1 advanced use-case
S: A project manager wants to be warned before the project's monthly spending actually passes its budget, based on where spending is trending. What should be configured in Microsoft Cost Management?
A: A budget with a forecasted alert, which fires when projected cost is expected to exceed the set threshold
B: A budget with an actual-cost alert at 100%, which fires early whenever daily spending rises faster than usual
C: A credit alert, which warns at fixed percentages before the subscription's spending passes its budget amount
D: An Azure Advisor cost recommendation, which warns when month-to-date spending is trending above the budget
K: A
G: ## Actual versus forecasted budget alerts
A **budget** in Cost Management sets a spending amount for a scope (such as a subscription or resource group) and a reset period (monthly, quarterly or annual). Each alert condition has a type:
- **Actual**: fires when the money already spent reaches the threshold, for example 80% of the budget.
- **Forecasted**: fires when Cost Management's cost **projection** for the period is expected to exceed the threshold. This gives advance notice while there is still time to act.
Either way the budget only notifies (and can call an action group); it does not stop resources by itself.
## Example
A monthly budget for `rg-project` with a forecasted alert at 100%: on day 10, spending is only 40% of the budget, but the trend projects 115% by month end, so the manager is warned on day 10 instead of on day 27.
W: Forecasted alert: forecasted budget alerts use cost predictions and fire when the projected spend for the period passes the threshold, so the manager hears about the trend before the money is actually spent.
X: B=Actual alert at 100%: an actual-cost alert fires only when real spending reaches the threshold. At 100% the budget has already been spent, which is too late for this requirement.
C=Credit alert: credit alerts track an Enterprise Agreement's Azure Prepayment balance. They are not tied to a project budget or its trend.
D=Advisor recommendation: Advisor suggests savings such as resizing idle VMs. It does not compare month-to-date spending with a budget or send budget warnings.
T: Use a forecasted budget alert to be warned before spending actually exceeds a budget.
V: Microsoft Cost Management

G: ## Designing a tag schema
A **tag** is a name and a value, such as `Impact=Mission-critical` or `CostCenter=4100`. You can assign one or more tags to each resource, and you can add, change or delete them at any time through the portal, PowerShell, the Azure CLI, ARM templates or the REST API.

X: B=Same tag names everywhere: Azure has no rule that all resources share one tag set. Requiring a tag is something you choose to enforce, for example with Azure Policy.
C=Tags only at creation: tags can be added, modified or removed on existing resources at any time, so no redeployment is needed.
D=Higher service level: tags are descriptive metadata. They do not change a resource's service level or price, so a tag on a test resource costs nothing extra.
T: Tags are optional per resource: apply a tag such as Impact only where it is meaningful, and use Azure Policy only for tags that must be everywhere.

@ AZ-900 D3 T3.1 advanced tradeoff
S: A studio renders animation frames in nightly batch jobs. Each job saves its progress and simply restarts if its VM is stopped partway. The VMs are not needed during the day, and the studio wants the lowest compute cost. Which pricing option fits best?
A: Azure Spot Virtual Machines, which run on unused Azure capacity at a lower price but can be evicted when Azure needs it
B: Reservations for the render VM size, which commit to that specific capacity for every hour of a one- or three-year term
C: An Azure savings plan for compute, which commits to a fixed hourly spend on eligible compute for one or three years
D: Pay-as-you-go pricing with no commitment, which bills each hour the render VMs run at the standard on-demand rate
K: A
G: ## Ways to buy compute
The **consumption** cost factor is about how much you use and also how you pay for it.
- **Pay-as-you-go**: no commitment; each hour of use is billed at the standard rate. Most flexible, no discount.
- **Reservations**: commit to specific resources (for example a VM size in a region) for one or three years. Best for stable workloads that run continuously.
- **Azure savings plan for compute**: commit to an **hourly spend amount** on eligible compute for one or three years. Suits steady spend that moves between VM types or services. Unused commitment in an hour does not roll over.
- **Azure Spot Virtual Machines**: use **unused Azure capacity** at lower prices. Azure can **evict** them when it needs the capacity back, and there is no SLA, so they suit work that tolerates interruption, such as batch processing and dev/test.
## Matching the workload
Commitments pay off when usage is steady around the clock. A job that runs only at night and can restart after an interruption gets the most from Spot.
## Example
A render job checkpoints every frame. Overnight two Spot VMs are evicted; the scheduler starts new ones and the job resumes from the last saved frame, at a fraction of the on-demand cost.
W: Spot Virtual Machines: Microsoft recommends Spot for workloads that can handle interruptions, such as batch jobs. The render jobs checkpoint and restart, so eviction only delays them, and the studio pays the lower Spot price instead of the standard rate.
X: B=Reservations: a reservation is a commitment for continuous use of specific capacity. VMs that sit idle all day would waste most of the reserved hours.
C=Savings plan: the hourly commitment applies to every hour of the term, and unused commitment does not roll over, so a night-only workload leaves much of it unused.
D=Pay-as-you-go: it fits the part-time schedule but charges the full on-demand rate, so it costs more than Spot for interruptible work.
T: Interruptible, restartable work such as batch rendering fits Azure Spot Virtual Machines; commitments fit steady around-the-clock usage.
V: Azure Spot Virtual Machines, Azure Reservations, Azure savings plan for compute

G: ## Resource type and settings
Microsoft lists **resource type** first among cost factors: the type of resource, **its settings**, and the region all change the price.
For a VM, settings that affect cost include:
- **licensing** for the operating system or other software;
- processor and number of cores (the VM size);
- attached storage;
- network interface.
For a storage account, settings include the type of data, access speed (tier), how many copies to keep (redundancy) and region.
## Isolating the factor
When size, region, subscription and running time are all the same, the remaining difference is a setting of the resource itself. Here, that setting is the operating system and its licence.
## Example

X: B=Geography: both VMs are in the same region. The operating system does not move a VM to a more expensive location.
C=Consumption: both VMs run around the clock, so they are metered for the same hours. Windows is not billed for extra time.
D=Subscription type: both VMs are in the same subscription, and operating systems do not have their own subscription offers.
T: A resource's settings, such as VM size and operating system licensing, are a direct cost factor even when region and usage are the same.
