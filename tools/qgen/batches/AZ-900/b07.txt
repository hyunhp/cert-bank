X: A=Blob Storage: blobs hold unstructured objects; one JSON blob per device gives no table-style properties or key queries, so every lookup means downloading and parsing whole files.
B=Queue Storage: a queue delivers messages for processing and removes them after use; it is not a store for looking up persistent records by key.
C=Azure Files: spreadsheets in a share are hard to query and update concurrently for millions of devices; file shares are for file-based access, not record lookups.
T: For low-cost, schemaless structured data accessed by key, use Azure Table Storage.
V: Azure Table Storage

@ AZ-900 D2 T2.3 applied use-case
S: A manufacturer is moving a legacy application to Azure without changing its code. The application expects a shared network folder that several Windows VMs in Azure and two servers still in the factory mount at the same time over SMB. The company does not want to build or patch a file server. Which Azure service should it use?
A: Azure Files, creating an SMB file share that the Azure VMs and factory servers mount concurrently
B: Azure Blob Storage, storing the application files as blobs in a container that each server lists
C: Azure Disk Storage, attaching a managed disk to one VM and sharing its folder with the others
D: Azure Table Storage, keeping each file's contents as an entity that the servers read and write
K: A
G: ## Azure Files
**Azure Files** offers fully managed file shares in the cloud, reachable through the industry-standard **SMB** and **NFS** protocols.
- Shares can be **mounted concurrently** by cloud and on-premises clients.
- SMB shares work from Windows, Linux and macOS; NFS shares from Linux.
- **Fully managed**: no hardware, no OS patching, no disks to replace.
- Typical uses: replace or supplement on-premises file servers, and **lift and shift** applications that expect shared file storage, **without code changes**.
## Why not the other storage services?
Blob storage is object storage reached by URL and API, not a mounted SMB share. Managed disks are volumes for VMs. Tables store structured entities.
Example: the share `\\contosoapp.file.core.windows.net\appdata` is mapped as drive `S:` on the Azure VMs and on the factory servers.
W: Azure Files: it provides a managed SMB share that Azure VMs and on-premises servers can mount at the same time, so the legacy app keeps working without code changes or a file server.
X: B=Blob Storage: blobs are accessed through URLs, REST APIs and SDKs; an application that expects a mounted SMB folder would need code changes to use them.
C=Shared managed disk folder: sharing a folder from one VM recreates a self-managed file server, with an OS to patch and a single VM as a point of failure.
D=Table Storage: tables store structured entities with properties, not files; an application that reads and writes files on a share cannot use them without a rewrite.
T: For shared folders mounted over SMB or NFS by many machines, in Azure or on-premises, use Azure Files.
V: Azure Files

@ AZ-900 D2 T2.3 applied tradeoff
S: A hospital keeps scanned patient consent forms in Blob Storage for at least five years. After the first few months a form is opened only a few times a year, but when a nurse needs one it must open within seconds, not hours. The hospital wants the lowest storage cost that still meets this need. Which access tier should it use for the older forms?
A: Hot tier, because it has the lowest storage cost of all the tiers when data is kept for years
B: Archive tier, because it has the lowest storage cost and forms can be read straight from it
C: Cool tier, because it is the only online tier meant for data stored for 30 days or longer
D: Cold tier, because it is an online tier with lower storage cost than cool for rarely read data
K: D
G: ## Blob access tiers
Access tiers balance **storage cost** against **access cost and speed**:
- **Hot** (online): frequently accessed data; no minimum storage period.
- **Cool** (online): infrequently accessed data; store for at least 30 days.
- **Cold** (online): rarely accessed data that still needs fast retrieval; at least 90 days.
- **Archive** (**offline**): rarely accessed data where a latency of hours is acceptable; at least 180 days.
- Going from hot to archive, **storage cost falls** and **access cost rises**.
- Hot, cool and cold are **online**: data is readable immediately, with the same retrieval latency.
- Archive is **offline**: a blob must first be **rehydrated** to an online tier, which can take up to 15 hours.
- Deleting or moving a blob before its minimum period causes a prorated early deletion charge.
Example: forms older than 90 days are moved to cold; they open instantly when needed.
W: Cold tier: it is online, so a form opens immediately, and it costs less to store than cool for data that is rarely read and kept well beyond 90 days.
X: A=Hot tier: hot has the highest storage cost and the lowest access cost; it suits data in active use, not forms opened a few times a year.
B=Archive tier: archive has the lowest storage cost, but it is offline; a blob must be rehydrated first, which can take hours and breaks the "within seconds" requirement.
C=Cool tier: cool is online, but it is not the only online tier for older data; cold is also online and has a lower storage cost for data this rarely read.
T: For rarely read data that must still open instantly, the cold tier is the cheapest online option; archive is cheaper but offline.
V: Azure Blob Storage, access tiers

@ AZ-900 D2 T2.3 applied use-case
S: A marketing agency stores campaign assets in Blob Storage. Assets are used heavily for 30 days, rarely after that, and must be deleted after three years. Today someone moves old blobs between tiers by hand and often forgets. The agency wants Azure to move blobs to cooler tiers and delete them automatically based on their age. What should it configure?
A: A lifecycle management policy on the storage account with rules that change the tier and delete blobs by age
B: An Azure Policy assignment that denies uploads to the hot tier after 30 days and audits blobs older than three years

D: Geo-redundant storage on the account, so older blobs are moved to the secondary region and expire there

G: ## Blob lifecycle management
**Lifecycle management** is a set of **rules in a JSON policy** on a storage account. Each rule has:
- **Filters**: which blobs (by container or name prefix, or by blob index tags).
- **Conditions**: based on creation time, last modified time or last accessed time.
- **Actions**: move to a cooler tier (cool, cold, archive) or **delete** current versions, previous versions or snapshots.
Rules run automatically; you can also move a blob back from cool to hot when it is accessed. The policy itself is free; you pay for the tier-change operations.
## Default account access tier
A storage account has a default access tier for new blobs: **hot, cool or cold**. **Archive can't be the account default**; it is set per blob.
Example rule: for `campaign/` blobs, move to cool 30 days after last modification, to archive after 180 days, and delete after 1,095 days.
W: Lifecycle management policy: rules based on blob age move assets to cooler tiers and delete them after three years automatically, removing the forgotten manual step.
X: B=Azure Policy: Azure Policy governs how resources are configured; it doesn't move individual blobs between access tiers or delete blob data on a schedule.
C=Archive as account default: archive can't be set as the account's default tier, and storing new assets offline would block the heavy use in the first 30 days.
D=Geo-redundant storage: redundancy copies data to a secondary region for durability; it does not tier or expire blobs by age.
T: Use a blob lifecycle management policy to move blobs to cooler tiers and delete them automatically by age.

@ AZ-900 D2 T2.3 applied troubleshooting
S: An auditor asks a company for an invoice PDF that was moved to the archive tier last year. A support engineer finds the blob in the container listing and can see its properties, but every attempt to download it fails. What must the engineer do to make the file readable?
A: Change the storage account's redundancy from locally redundant to zone-redundant storage, then retry the download
B: Generate a new shared access signature with read permission for the blob, then retry the download from the browser
C: Rehydrate the blob by changing its tier to hot, cool or cold, wait for rehydration to finish, then download it
D: Change the storage account's default access tier to hot, which immediately moves all archived blobs back online
K: C
G: ## Why archived blobs can't be read
The **archive tier** is **offline**. While a blob is in archive:
- Its **metadata stays readable**, so it appears in listings and you can see its properties.
- Its **content can't be read or modified**.
## Rehydration
To read an archived blob, first **rehydrate** it to an online tier (**hot, cool or cold**), either by changing its tier or by copying it to a new blob in an online tier.
- **Standard priority** can take **up to 15 hours** for objects under 10 GB.
- **High priority** might finish in under an hour for objects under 10 GB, at a higher cost.
Moving a blob out of archive before 180 days triggers a prorated early deletion charge.
## Account default tier
The default access tier applies only to blobs without an explicitly set tier. A blob moved to archive has an explicit tier, so changing the default does not bring it back.
Example: set `invoices/2025/INV-0412.pdf` to the cool tier with standard priority, then download it once rehydration completes.
W: Rehydrate the blob: archived content is offline, so the blob must be moved back to an online tier and the rehydration must complete before the download can succeed.
X: A=Change redundancy: redundancy controls how many copies exist and where; it does not make offline data readable. Archive is also not supported for zone-redundant accounts, so this change would require rehydration first anyway.
B=New SAS token: a shared access signature grants permission, but the failure is not about permission; an archived blob can't be read by anyone until it is rehydrated.
D=Default tier to hot: the account default affects only blobs whose tier is inferred; a blob explicitly set to archive stays archived until it is rehydrated individually.
T: Archived blobs are offline; rehydrate them to hot, cool or cold (which can take hours) before reading them.
V: Azure Blob Storage, access tiers
