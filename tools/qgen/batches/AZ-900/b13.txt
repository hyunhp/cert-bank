@ AZ-900 D1 T1.1 expert comparison
S: A biotech company is reviewing how it pays for three Azure workloads. Its SQL Server VMs use one size in West Europe, run around the clock, and will not change for three years. Its web tier is being modernized, so over the next year it will move between VM families and into a second region, while total hourly compute use stays steady. A nightly genomics pipeline saves checkpoints and can resume after an interruption, and finance wants it as cheap as possible. The customer payment API, however, must never be interrupted. Which THREE purchasing decisions fit these workloads? (Select THREE)
A: Buy an Azure reservation for the SQL Server VMs, because their size, region and round-the-clock use stay fixed for the whole term.
B: Buy an Azure savings plan for compute for the web tier, because it commits to an hourly spend that applies across VM families and regions.
C: Run the genomics pipeline on Azure Spot Virtual Machines, because its checkpoints let a job resume after Azure evicts the VMs to reclaim capacity.
D: Run the payment API on Azure Spot Virtual Machines with the maximum price set to -1, because that setting stops Azure from ever evicting them.
E: Buy an Azure reservation for the web tier, because a reservation automatically follows the VMs when they move to another region and VM family.
F: Keep the SQL Server VMs on pay-as-you-go pricing, because one- and three-year commitments cannot apply to VMs that run around the clock all year.
K: A,B,C
G: ## Four ways to pay for Azure compute
Azure compute can be bought in several ways, and each one trades flexibility for price:
- **Pay-as-you-go**: no commitment; you pay for what you use in each billing cycle. Most flexible, highest unit price.
- **Reservations**: you commit for one or three years to a specific resource configuration, for example a D2v4 VM in Japan East. When fully used on a stable workload, Microsoft says reservations can give greater savings than savings plans.
- **Savings plan for compute**: you commit to a fixed hourly spend for one or three years, and the discount applies to eligible compute usage across services and regions. Microsoft recommends it for workloads that are "dynamic or evolving".
- **Azure Spot Virtual Machines**: unused Azure capacity at a large discount, with **no SLA**. Azure can evict a Spot VM with about 30 seconds' notice whenever it needs the capacity back, so only interruptible work (batch jobs, dev/test) belongs there.
## The max price trap
Setting a Spot VM's maximum price to `-1` only means the VM is never evicted **for price reasons**. Azure can still evict it when it needs the capacity, so the setting never makes Spot safe for a workload that must not stop.
## Matching the scenario
Fixed size, region and 24/7 use for three years points to a reservation; changing families and regions with a steady spend points to a savings plan; a checkpointed batch job points to Spot. The payment API, the detail at the end, must stay on capacity that Azure does not reclaim.
W: A=Reservation for the SQL Server VMs: a reservation commits to a specific configuration such as VM size and region. These VMs never change and run continuously, which is exactly the stable workload where Microsoft says a fully used reservation saves the most.
B=Savings plan for the web tier: a savings plan commits to an hourly amount, not a configuration, and its discount applies to eligible compute in any region. Moving between VM families and adding a region does not waste the commitment, while the steady total spend keeps it fully used.
C=Spot VMs for the genomics pipeline: Spot capacity is the cheapest option and can be reclaimed at any time, which this job tolerates because it resumes from its checkpoints after an eviction.
X: D=Spot for the payment API with max price -1: the -1 setting only removes evictions caused by price. Azure still evicts Spot VMs when it needs the capacity back, and Spot has no SLA, so an API that must never be interrupted cannot run there.
E=Reservation for the web tier: a reservation is tied to attributes such as instance family and region. When the web tier changes family and region, the reservation stops matching, which is why Microsoft points evolving workloads to savings plans instead.
F=Pay-as-you-go for the SQL Server VMs: continuous, unchanging use is the best case for a one- or three-year commitment, not a reason against it. Staying on pay-as-you-go pays the highest unit price for a predictable workload.
T: Fixed configuration for years: reservation; steady spend that moves between families and regions: savings plan; interruptible work: Spot, and -1 never protects Spot from capacity eviction.
V: Azure Reservations, Azure savings plan for compute, Azure Spot Virtual Machines

@ AZ-900 D1 T1.1 expert use-case
S: A regional hospital group must keep its patient records system on servers it owns in its own datacenter, under a contract with the state health authority. Every winter it also runs a flu-forecasting model on anonymized data for about ten weeks, which needs ten times the compute it has. Its three-person IT team cannot manage more physical hardware, and the board will not pay for servers that sit idle for the other forty-two weeks of the year. Which cloud model best meets all of these requirements?
A: A private cloud, built by buying enough extra servers for the hospital's own datacenter to cover the winter forecasting peak each year
B: A public cloud only, moving the records system to an Azure region in the same state and running the forecasting model next to it
C: A hybrid cloud, keeping the records system on the hospital's own servers and running the winter forecasting model in Azure on demand
D: A public cloud only, moving the records system onto Azure Dedicated Host so that no other customer shares the physical servers with it
K: C
G: ## Three cloud models
- **Private cloud**: cloud-style self-service on infrastructure used by one organization, usually in its own datacenter. It gives the most control, but the organization buys, runs and maintains the hardware, so capacity must be bought for the peak.
- **Public cloud**: the provider owns and runs the infrastructure; customers rent what they need and pay only while they use it. No upfront hardware and near-unlimited capacity on demand.
- **Hybrid cloud**: private and public combined in one interconnected environment. Workloads that must stay on owned hardware stay there, while other workloads use public cloud capacity, for example to handle a seasonal peak.
## Reading the constraints
- The records must stay on **servers the hospital owns**. That rules out every public-cloud-only design, whatever region or isolation level it uses.
- The forecasting peak is short and ten times larger than current capacity, and the board will not pay for idle servers. That rules out buying the peak capacity for a private cloud.
- The tiny IT team cannot run more hardware, which again favours renting the peak from a public cloud.
## Example
The hospital keeps its records database in its datacenter, sends anonymized data to Azure each November, runs the model on rented VMs for ten weeks, and deletes them in February.
W: Hybrid cloud: the records stay on hospital-owned servers, which satisfies the contract, while the short winter peak runs on public cloud capacity that is paid for only during those ten weeks and needs no new hardware.
X: A=Private cloud with extra servers: this keeps everything on owned hardware, but the hospital would buy and maintain ten times its capacity for a ten-week job. The board refuses to pay for servers idle most of the year, and the small team cannot run them.
B=Public cloud in an in-state region: staying in the same state may help with data location, but the contract requires servers the hospital owns. Azure regions run on Microsoft's hardware, so the records cannot move there.
D=Public cloud on Azure Dedicated Host: a dedicated host gives the hospital a physical server no other customer shares, but Microsoft still owns that server in its datacenter. Isolation is not ownership, so the contract is still broken.
T: When some data must stay on owned hardware and a peak needs elastic capacity, a hybrid cloud keeps the first on premises and rents the second.
V: Azure Virtual Machines, Azure Dedicated Host

@ AZ-900 D1 T1.2 expert tradeoff
S: A team is checking the availability of its online ordering flow before launch. Customers place orders through a web app that calls one database; for this exercise, assume the web app's SLA is 99.95% and the database's SLA is 99.99%. A separate storage account, assumed at 99.9%, receives a nightly export that the finance team's reporting job reads the next morning; customers never wait on it. The business target for the ordering flow is 99.9%, and the team wants the number it reports to describe what customers actually experience. Which assessment is correct?
A: Only the web app and database sit on the customer flow, so its composite is about 99.95% × 99.99% ≈ 99.94%, which meets the 99.9% target
B: All three services must be multiplied, so the composite is about 99.84%, below target, and the export storage needs redundancy before launch
C: A composite SLA equals the lowest SLA in the chain, so the flow sits at exactly 99.9% and meets the target with no margin left at all
D: A composite SLA equals the highest SLA in the chain, because the database holds every order, so the flow reaches 99.99% and beats the target
K: A
G: ## How composite availability works
When a request needs several components and **every one of them** must be up, the chance that the whole flow works is the product of their individual availabilities. Microsoft's reliability guidance says a composite value "is a product distribution of the contributing factors". Two consequences:
- The composite is always **lower** than the weakest component, never equal to it and never the highest.
- Every component you add in series pulls the number down a little more.
## Which components count
The same guidance says flows can have components "you deem as noncritical", and you can omit them when their brief unavailability does not affect the customer's experience. You include a dependency when it directly affects the critical flow.
## Worked numbers
- Customer flow: `0.9995 × 0.9999 = 0.99940005`, about **99.94%**.
- If the nightly export storage were wrongly included: `0.99940005 × 0.999 ≈ 0.9984`, about 99.84%.
The SLA values here are assumptions for the exercise; real SLAs depend on the service, tier and configuration.
W: Customer flow only, about 99.94%: the export storage is used only by a next-morning reporting job, so customers never depend on it. Multiplying the two components on the ordering path gives about 99.94%, above the 99.9% target, and that number describes what customers experience.
X: B=Multiply all three, about 99.84%: the multiplication itself is correct, but it includes a component that is not on the customer flow. The result understates the ordering flow's availability and would trigger redundancy work the target does not require.
C=Equals the lowest SLA: a series of dependencies is less available than its weakest part, because a failure of any one of them stops the flow. The composite is a product, not the minimum.
D=Equals the highest SLA: the most important component does not set the flow's availability. If the web app is down, orders fail even though the database is up.
T: Multiply the availabilities of the components a flow really depends on; the result is below the weakest one, and noncritical side paths can be left out.
V: Azure App Service, Azure SQL Database, Azure Storage

@ AZ-900 D1 T1.2 expert comparison
S: An online retailer is preparing a cloud business case. The operations lead wants customers to get consistent response times during unannounced flash sales, when traffic can jump fivefold within minutes. The CFO wants to know each month roughly what the next month will cost, without surprises. Before anything is migrated, the CFO also wants a first estimate of the monthly Azure spend for the planned design, including its storage redundancy choices. Which statement correctly matches these goals to Microsoft's description of predictability in the cloud?
A: Performance predictability through autoscaling and load balancing; cost predictability through real-time usage tracking and forecasts, with a pricing calculator estimate before migration
B: Performance predictability through region pairs that move traffic automatically; cost predictability through SLA service credits that cap any overspending each month
C: Performance predictability through resource locks that keep VM sizes fixed; cost predictability through Azure Policy assignments that limit monthly spending in Cost Management
D: Performance predictability through larger VMs bought for the peak in advance; cost predictability through Azure Advisor reports that generate the first estimate before migration
K: A
G: ## Two kinds of predictability
Microsoft's Azure Fundamentals material splits predictability into two parts, both shaped by the Azure Well-Architected Framework:
- **Performance predictability** is about having the resources needed for a good customer experience. Autoscaling adds resources when demand rises and removes them when it falls; load balancing spreads traffic away from overloaded instances; high availability keeps the service running.
- **Cost predictability** is about forecasting cloud spend. You track resource use in real time, monitor efficiency, analyse trends to plan future deployments, and use tools such as the **Azure pricing calculator** to estimate spend before anything is deployed.
## Reading the scenario
Flash sales that arrive without warning need resources that follow demand automatically (autoscaling, load balancing). Monthly forecasts come from tracking and analysing actual usage. A pre-migration estimate that includes redundancy options is exactly what the pricing calculator is for: Learn notes it can model storage type, access tier and redundancy, and nothing is provisioned.
W: Autoscaling and load balancing, plus tracking, forecasts and the pricing calculator: these are the mechanisms Microsoft lists for performance and cost predictability. Autoscaling absorbs the unannounced surge, usage data drives the monthly forecast, and the calculator gives the first estimate before migration.
X: B=Region pairs and SLA credits: deploying into a region pair does not automatically shift traffic or provide failover, and SLA credits compensate for missed availability; they do not cap or forecast spending.
C=Locks and Azure Policy: a lock prevents changes or deletion and would stop VMs from scaling, the opposite of handling a surge. Azure Policy enforces resource rules; it does not set a monthly spending limit.
D=Peak-sized VMs and Advisor: buying for the peak in advance is the capacity guessing the cloud is meant to remove, and it wastes money on normal days. Advisor recommends improvements for deployed resources; it does not estimate a design before migration.
T: Performance predictability comes from autoscaling and load balancing; cost predictability comes from tracking, forecasting and pricing-calculator estimates.
V: Azure Virtual Machine Scale Sets, Azure Load Balancer, Azure pricing calculator, Microsoft Cost Management

S: A company moves its customer portal from Windows virtual machines (IaaS) to Azure App Service (PaaS). On the VMs, its team patched the operating system, configured the firewall rules and network segmentation, and managed the app's settings. After the move, the security architect updates the responsibility matrix. She notes that her team will still restrict which IP ranges can reach the portal and will keep managing who may deploy code. According to Microsoft's shared responsibility model, which change is correct for this move?
A: The operating system moves to Microsoft, network controls become shared, and configurations and settings stay with the customer
B: The operating system and network controls both move entirely to Microsoft, and configurations and settings become a shared responsibility
C: The operating system becomes shared, network controls stay entirely with the customer, and identities and users become a shared responsibility
D: The operating system and network controls both move to Microsoft, and client devices that reach the portal become a shared responsibility
K: A
G: ## Microsoft's responsibility matrix
Microsoft's shared responsibility page lists who owns each area in each service model:
- **Always the customer** (on premises, IaaS, PaaS, SaaS): customer data, configurations and settings, identities and users. Client devices are the customer's in IaaS and PaaS and become shared only in SaaS.
- **Shared in PaaS**: applications and network controls. In PaaS, Microsoft provides baseline network security, but the customer configures application-level network controls.
- **Microsoft in PaaS**: the operating system, physical hosts, physical network and physical datacenter.
## IaaS to PaaS
Moving from VMs to App Service takes the operating system (patching included) off the customer's list. It does not hand over everything: the customer still configures app-level network rules such as access restrictions, still owns the app's settings, and still decides who has access.
## Example
After the move, the team stops patching Windows, keeps an access restriction that allows only its partners' IP ranges, and still controls which engineers can deploy to the app.
W: OS to Microsoft, network controls shared, configurations with the customer: in PaaS Microsoft manages the operating system, network controls are shared (Microsoft's baseline plus the team's IP restrictions), and configurations and settings remain the customer's in every service model.
X: B=OS and network controls entirely Microsoft's: network controls become fully Microsoft's only in SaaS. In PaaS the team still configures app-level rules such as the IP restrictions it mentioned, and configurations never become shared.
C=OS shared, network controls customer-only: in PaaS the operating system is Microsoft's, not shared, and network controls are shared, not the customer's alone. Identities and users stay with the customer in every model.
D=Client devices shared: client devices become a shared area only in SaaS. For a PaaS portal the devices that reach it remain the customer's responsibility, and network controls are shared, not Microsoft's.
T: Going from IaaS to PaaS moves the operating system to Microsoft and makes network controls and applications shared, while data, configurations and identities always stay with the customer.
V: Azure App Service, Azure Virtual Machines

@ AZ-900 D2 T2.2 expert tradeoff
S: A manufacturer runs an order-routing application on two Windows VMs in an Azure region it must use for data residency. The two VMs exchange messages constantly, so the team wants the lowest possible VM-to-VM latency. The application must keep running when Azure restarts hosts for planned maintenance and when a single rack loses power. When the team reviewed the region's deployment options in the portal, it found that this region does not support availability zones. Which configuration best meets these requirements?
A: Place both VMs in an availability set, so Azure spreads them across fault domains and update domains inside the region's datacenter
B: Place each VM in a different availability zone of the region, so the loss of one datacenter never stops the whole application
C: Place one VM in the region and the second in its paired region, so the pair's sequential updates keep one VM running
D: Place both VMs on one larger VM size with premium SSD disks, so a single host gives the lowest possible latency between them
K: A
G: ## VM availability options side by side
- **Availability set**: a logical grouping of two or more VMs. Azure gives each VM a **fault domain** (shared power source and network switch, up to 3) and an **update domain** (VMs restarted together during planned maintenance, up to 20). Only one update domain is restarted at a time, so at least one VM keeps running during maintenance, and a rack failure hits only one fault domain. VMs stay physically close, so latency between them is lower than across zones. It is especially useful in regions without availability zones, and the set itself costs nothing.
- **Availability zones**: physically separate datacenters within a region with their own power, cooling and networking. Highest resiliency inside a region, but only in regions that support zones, and VM-to-VM latency is higher than in an availability set.
- **Region pairs**: Microsoft staggers planned updates across a pair, but deploying into a pair does not by itself give high availability or failover, and data placed in another region may break residency rules.
## Reading the constraints
Residency fixes the region, the region has no zones (the detail in the stem), and the app wants minimum latency and survival of maintenance and rack failures. That is the textbook case for an availability set.
W: Availability set: the two VMs land in different fault domains and update domains, so a rack power loss or a host restart affects only one of them. They stay close together for low latency, and the option works in a region that has no availability zones.
X: B=Different availability zones: zones would protect against a whole datacenter failure, but this region does not support availability zones, and cross-zone placement also adds latency between the VMs.
C=VM in the paired region: the paired region may break the data residency requirement, the distance adds latency to constant messaging, and a region pair alone does not make a deployment highly available.
D=One larger VM: a single VM is a single point of failure. Planned host maintenance or a rack power loss takes the whole application down, whatever its size or disk type.
T: In a region without availability zones, an availability set spreads VMs across fault and update domains for high availability with low latency.
V: Azure Virtual Machines, availability sets, availability zones

@ AZ-900 D2 T2.1 expert definition
S: A company with 40 Azure subscriptions is designing a management group hierarchy so that one allowed-locations policy and one Reader role assignment for auditors reach every subscription, including subscriptions created next year. The architect also wants a deep tree that mirrors the company's eight-level reporting structure. The company has just acquired a smaller firm whose subscriptions trust that firm's own Microsoft Entra tenant, and the architect hopes to place them under the same management groups right away. Which THREE statements about management groups are correct? (Select THREE)
A: A management group tree supports up to six levels of depth, not counting the root level or the subscription level, so eight levels will not fit
B: Every management group and subscription in a directory folds up to a single root management group, which can hold directory-wide assignments
C: All subscriptions within a single management group must trust the same Microsoft Entra tenant as the management group hierarchy itself
D: A subscription can sit under two management groups at once, so it receives the policies and role assignments of both parent groups
E: A policy assigned at a management group reaches only the subscriptions that were already in the group when the assignment was created
F: A subscription owner can override a policy inherited from a parent management group by assigning a conflicting policy at the subscription
K: A,B,C
G: ## What management groups do
Management groups are a governance scope **above** subscriptions. Policies and Azure role assignments applied to a management group **cascade by inheritance** to every nested management group, subscription and resource, including ones added later. That is why one assignment can replace dozens of per-subscription assignments.
## Rules worth knowing
- One directory can hold 10,000 management groups.
- A tree supports up to **six levels of depth**; the root level and the subscription level are not counted.
- Each management group and subscription has **only one parent**.
- Every directory has one **root management group** (display name "Tenant root group"); all management groups and subscriptions fold up to it, and it allows directory-level policies and role assignments.
- All subscriptions within a management group must trust the **same Microsoft Entra tenant**.
- An inherited policy cannot be altered by the subscription or resource owner, which is what makes it useful for governance.
## Applying it to the scenario
The eight-level design is too deep and must be flattened, and the acquired firm's subscriptions cannot join the hierarchy while they trust another tenant.
W: A=Six levels of depth: Learn states a tree supports up to six levels, excluding the root and subscription levels, so an eight-level copy of the org chart must be simplified.
B=Single root management group: every directory has one root management group to which all management groups and subscriptions fold up, and it can carry global policies and role assignments.
C=Same Microsoft Entra tenant: all subscriptions within a single management group must trust the same tenant, so the acquired firm's subscriptions cannot be placed in the hierarchy while they trust their own tenant.
X: D=Two parents: each management group and subscription supports only one parent, so a subscription inherits along exactly one path.
E=Only existing subscriptions: inheritance is continuous. A subscription moved or created under the group later receives the group's policies and role assignments too, which is what the company wants for next year's subscriptions.
F=Owner overrides inherited policy: Microsoft notes that the resource or subscription owner cannot alter a policy applied at a parent management group, which is the point of assigning it there.
T: Management groups pass policies and roles down a single-parent tree up to six levels deep under one root, and only for subscriptions in the same Microsoft Entra tenant.
V: Azure management groups, Azure Policy, Azure RBAC

@ AZ-900 D2 T2.2 expert use-case
S: A startup has chosen the brand name for its new public website but has not yet registered the domain anywhere. It wants its DNS records managed in Azure, so that only the platform team can change them through Azure role-based access control, every change appears in the activity log, and a lock can stop the zone from being deleted by accident. Visitors worldwide should get DNS answers from a nearby name server. The team has no budget to run or patch its own DNS servers. Which plan meets these requirements?
A: Buy the domain through App Service domains or a third-party registrar, host the zone in Azure Public DNS, and delegate the domain to its Azure name servers
B: Create the zone in Azure Public DNS, which registers the brand-new domain name automatically and bills the yearly registration on the Azure invoice
C: Create an Azure Private DNS zone for the brand name and link it to the website's virtual network, so internet visitors can resolve the site
D: Run DNS server software on two Azure virtual machines in different regions, and grant the platform team access to those VMs through Azure RBAC
K: A
G: ## Hosting a domain versus buying it
**Azure Public DNS** hosts DNS zones: it stores and answers the records of a domain you already own. Its name servers sit on Azure's global network and use **anycast**, so each query is answered by the closest available server. Because Azure DNS is built on Azure Resource Manager, zones get Azure RBAC, activity logs and resource locks like any other resource.
What Azure Public DNS does **not** do is sell domain names. Learn says you buy a domain through **App Service domains** or a third-party registrar, then host it in Azure DNS by **delegating** it: at the registrar you set the domain's name server records to the Azure name servers assigned to your zone.
**Azure Private DNS** is a different service: it resolves names inside virtual networks and is not reachable from the internet.
## Example
The startup buys `contoso-brand.com` from a registrar, creates the zone in Azure Public DNS, copies the four Azure name server names into the registrar's settings, and from then on manages records with RBAC and a CanNotDelete lock on the zone.
W: Buy the domain, host it in Azure Public DNS, delegate it: registration happens at App Service domains or a registrar, while the zone in Azure Public DNS gives RBAC, activity logs, locks and anycast name servers with no servers to run.
X: B=Azure Public DNS registers the name: Azure DNS cannot buy domain names. Creating a zone does not register anything, and queries reach the zone only after the domain is bought and delegated to Azure's name servers.
C=Azure Private DNS zone: a private zone answers only resources in linked virtual networks. Internet visitors cannot resolve names from it, so a public website would be unreachable by name.
D=DNS servers on VMs: the team would have to run and patch the servers, which it has no budget for, and two VMs do not give the anycast network that answers each query from the nearest server. It also still needs the domain to be bought.
T: Azure Public DNS hosts and manages zones with RBAC, logs, locks and anycast, but the domain itself must be bought elsewhere and delegated to Azure.
V: Azure DNS, App Service domains

@ AZ-900 D2 T2.2 expert comparison
S: A media company runs a render farm in a virtual network in East US and its asset catalog in a virtual network in West Europe. Render nodes must reach the catalog over private IP addresses, and the security team forbids any path over the public internet. The network team is small and does not want to deploy or manage VPN gateways for this link. After reading the design, an engineer claims that connecting virtual networks in different regions always requires extra infrastructure. Which TWO statements about connecting these virtual networks are correct? (Select TWO)
A: Global virtual network peering can connect the two virtual networks across regions, and the traffic stays on the Microsoft backbone network
B: Traffic between peered virtual networks needs no gateway, public internet routing or encryption configuration between the two networks
C: Virtual network peering works only between virtual networks in the same region, so a VPN gateway connection is needed between the regions
D: Peered traffic between regions is routed through VPN gateways that Azure deploys automatically in both virtual networks when peering is created
E: Peering across regions first requires an ExpressRoute circuit between East US and West Europe so that the traffic avoids the public internet
K: A,B
G: ## Virtual network peering
**Virtual network peering** connects two or more Azure virtual networks so they appear as one for connectivity. There are two kinds:
- **Virtual network peering**: virtual networks in the same Azure region.
- **Global virtual network peering**: virtual networks in different Azure regions.
In both cases, traffic between the networks is **private** and stays on Microsoft's backbone. Learn states that no public internet, gateways or encryption are required for the communication between the peered networks, and in the same region the latency between VMs in peered networks equals the latency inside one network.
## Where gateways and ExpressRoute fit
- **VPN Gateway** sends encrypted traffic, typically to on-premises sites, and is a resource you deploy and manage.
- **ExpressRoute** is a private connection from your own network into Microsoft's network through a connectivity provider. It is for on-premises connectivity, not a prerequisite for connecting two Azure virtual networks.
## Example
The East US render network peers with the West Europe catalog network; render nodes reach the catalog at `10.20.1.4` without any gateway in either network.
W: A=Global peering on the Microsoft backbone: global virtual network peering is the cross-region form of peering, and its traffic never leaves Microsoft's private backbone, which satisfies the no-internet rule.
B=No gateway, internet or encryption setup: peered traffic flows directly between the networks, so the small team has no VPN gateways to deploy or manage.
X: C=Same region only: that limit does not exist; global virtual network peering exists precisely to connect virtual networks in different regions.
D=Automatic VPN gateways: peering creates no gateways. Traffic between peered networks is routed directly over the backbone, not through a gateway.
E=ExpressRoute first: ExpressRoute links on-premises networks to Microsoft's network through a provider. Two Azure virtual networks can be peered without any circuit.
T: Global virtual network peering privately links virtual networks across regions over Microsoft's backbone, with no gateways, internet path or ExpressRoute needed.

G: ## Two common causes of surprise cloud costs
**Leftover resources.** When you provision a VM, Azure also creates resources such as disks and networking (a network interface and often a public IP). Microsoft's cost guidance warns that when you deprovision the VM, those additional resources "may not deprovision at the same time". They keep costing money until someone deletes them.
**Data transfer by geography.** Some inbound transfers into Azure datacenters are free; **outbound** transfers are priced by **billing zones**, geographical groupings of regions used for data-transfer pricing (not availability zones). Microsoft's example: moving data within Europe is cheaper than moving it from Europe to Asia or South America.
## What does not reduce cost
- A **budget** in Microsoft Cost Management sends alerts at actual or forecasted thresholds; resources are not affected and consumption is not stopped.
- A **resource lock** prevents deletion or changes; it has no effect on billing.
## Example
Deleting 20 orphaned disks and 20 unused public IPs ends their charges, and running the log job in West Europe removes the daily Europe-to-Asia egress.
W: A=Remove leftover disks and public IPs: these resources outlived the deleted VMs and are still billed; deleting them, after checking that nothing on the disks is needed, ends the charges.
B=Keep the log processing in West Europe: the daily 2 TB leaving Europe for Asia is outbound transfer between billing zones, which costs more than moving data within Europe; processing it in the same region removes that egress.
X: C=Stop inbound uploads: some inbound transfers into Azure are free, and the stem says inbound uploads did not change, so they are not the cause of the rise.
D=Budget that stops charges: Cost Management budgets only notify; Learn states that resources are not affected and consumption is not stopped when a threshold is reached.
E=ReadOnly lock to stop billing: a lock prevents changes or deletion; locked resources are billed exactly as before, and it would even stop the cleanup.
T: Delete resources that outlive a VM and keep large data transfers within a region or geography; budgets and locks do not cut costs by themselves.
