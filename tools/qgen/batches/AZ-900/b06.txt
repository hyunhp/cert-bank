@ AZ-900 D2 T2.2 applied troubleshooting
S: To save money overnight, an administrator signs in to a Windows virtual machine every evening and shuts it down from the Start menu. At month end, the VM's compute charges are almost the same as if it had run all day. What explains this, and what should the administrator do instead?
A: A shutdown inside the guest OS leaves the VM in the Stopped (allocated) state; stopping it from Azure deallocates the VM and ends its compute charges
B: Windows VMs are billed for compute at a flat monthly rate regardless of state; switching the VM to a Linux image is the only way to save money
C: The VM's operating system disk keeps the compute meter running; detaching the OS disk every evening before shutting down ends the charges
D: Compute charges stop only when the VM is deleted; the administrator should delete and recreate the VM from its image every evening
K: A
G: ## VM power states and billing
A virtual machine's compute charge depends on whether Azure still holds hardware for it:
- **Running**: billed.
- **Stopped** (also called Stopped (allocated) or PoweredOff): the VM is still **allocated on a host** but not running. This happens when you shut down from **inside the guest OS** or call the PowerOff operation. **Still billed** for compute.
- **Deallocated** (Stopped (deallocated)): the VM has released the underlying hardware. **Not billed** for compute.
Some related resources, such as **disks** and **networking** (for example a public IP), keep incurring charges in every state.
## How to stop paying for compute
Stop the VM through Azure (portal Stop button, CLI or an automated schedule) so it is deallocated. Partial hours are billed by the minute, so deallocating overnight saves real money.
Example: an auto-shutdown schedule deallocates a dev VM at 19:00 every day.
W: Stopped (allocated) versus deallocated: a guest-OS shutdown keeps the VM allocated on its host, which is still billed; stopping it from Azure deallocates it so compute billing stops (disks are still billed).
X: B=Flat monthly rate: VMs are billed by usage based on size and OS, with partial hours charged per minute; a deallocated Windows VM does not incur compute charges.
C=OS disk keeps the meter running: disks have their own storage charge, but they do not cause compute charges, and detaching an OS disk is not a normal way to stop a VM.
D=Delete to stop billing: deallocation already stops compute charges, so deleting and recreating the VM each day adds risk and work for no benefit.
T: Only a deallocated VM stops compute billing; a shutdown from inside the OS leaves it allocated and billed.

@ AZ-900 D2 T2.2 applied definition
S: A new engineer is reviewing the resources that were created together with a Linux virtual machine. Which resource connects the VM to a subnet of the virtual network and holds the VM's private IP address?
A: The network interface (NIC), which attaches the VM to a subnet and carries its private and any public IP configuration
B: The network security group (NSG), which filters the traffic to and from the VM by port, protocol and source address

G: ## What a VM is made of
Creating a VM also creates (or uses) several supporting resources, by default in the same resource group as the VM:
- **Virtual network** and **subnet**: the private network the VM communicates on.

- **OS disk** and optional **data disks** (managed disks).

@ AZ-900 D2 T2.2 applied use-case
S: A small company runs an internal web portal on one Azure VM. The portal is idle most of the day, with CPU usage usually under 10%, but it needs more CPU for short bursts when employees sign in each morning. Which type of VM size fits this pattern at a low cost?
A: A B-series burstable size, which builds up CPU credits while usage is low and spends them during short peaks
B: A memory-optimized size, which provides a high memory-to-CPU ratio for large in-memory databases and caches
C: A GPU-accelerated size, which adds graphics processors for rendering, visualization and model training work
D: A storage-optimized size, which provides high disk throughput and I/O for big data and large databases
K: A
G: ## VM sizes
The **size** of a VM sets its processing power, memory, storage capacity and network bandwidth, and it largely decides the price. Azure groups sizes into families:
- **General purpose**: balanced CPU-to-memory ratio, good for dev/test, small to medium databases and low to medium traffic web servers. This includes the **B-series**.
- **Compute optimized**: high CPU-to-memory ratio.
- **Memory optimized**: high memory-to-CPU ratio, for in-memory analytics and large databases.
- **Storage optimized**: high disk throughput and I/O.
- **GPU accelerated** (and FPGA accelerated): specialized hardware for graphics, visualization and AI.
## Burstable B-series
B-series VMs use a **CPU credit** model: while the workload runs below the base CPU performance, the VM accumulates credits; when it needs more, it spends them to burst above the base. When credits run out it is throttled back to the base level. That suits workloads that are usually quiet but occasionally busy.
Example: a portal that idles all day and spikes at 9:00 runs on a small B-series size instead of a larger fixed-performance size.
W: B-series burstable: credits earned while the portal is idle pay for the morning bursts, so a small, inexpensive size can handle occasional peaks.
X: B=Memory optimized: these sizes target memory-hungry workloads; the portal's problem is short CPU bursts, not memory.
C=GPU accelerated: graphics processors are for rendering and AI work and cost much more; a web portal does not need them.
D=Storage optimized: these sizes are built for heavy disk I/O, which does not match a mostly idle portal with brief CPU peaks.
T: Choose a VM size family by workload shape; B-series burstable sizes suit low average CPU with occasional bursts.
V: Azure Virtual Machines

@ AZ-900 D2 T2.2 advanced troubleshooting
S: A company runs four identical web VMs in an availability set behind a load balancer. The team asks what happens to the VMs when Microsoft performs planned maintenance on the underlying hosts that requires a reboot. Which statement is accurate?
A: The VMs are grouped into update domains, and only one update domain is restarted at a time, so the other VMs keep serving traffic
B: The VMs are grouped into fault domains, and all fault domains are restarted together so that the maintenance window ends quickly
C: The availability set moves the VMs to another availability zone before maintenance starts, so no VM is ever restarted
D: All four VMs restart at the same time, because availability sets protect only against hardware failures and not against maintenance
K: A
G: ## Availability sets
An **availability set** is a logical grouping of VMs that reduces the chance of correlated failures taking them all down. It costs nothing extra; you pay only for the VMs. Azure assigns every VM in the set an **update domain** and a **fault domain** (up to 3 fault domains and 20 update domains; these counts cannot be changed after the set is created).
## Two kinds of domain
- **Fault domain**: VMs that share a common **power source and network switch**. Spreading VMs across fault domains limits the impact of hardware, power or network failures in the datacenter.
- **Update domain**: VMs and hardware that **can be restarted at the same time**. During planned maintenance only **one update domain is restarted at a time**, and a restarted update domain gets 30 minutes to recover before maintenance moves on.
## Limits
Availability sets keep VMs physically close (low latency) but do not protect against a whole datacenter failing. For that, use availability zones.
Example: four VMs spread across update domains 0-3; when update domain 1 is rebooted, the other three VMs keep handling requests.
W: Update domains: planned maintenance restarts one update domain at a time, so the VMs in the other update domains keep running behind the load balancer.
X: B=Fault domains restarted together: fault domains describe shared power and network hardware, not maintenance order, and Azure does not restart them all at once for maintenance.
C=Move to another zone: availability sets do not use availability zones and do not migrate VMs; they control placement inside a datacenter.
D=All restart together: protecting against planned maintenance is exactly what update domains are for, so the VMs are not all restarted at once.
T: Fault domains separate shared power and network; update domains make planned maintenance restart one group of VMs at a time.
V: Azure Virtual Machines, availability sets

@ AZ-900 D2 T2.2 applied comparison
S: A team runs three web VMs in an availability set. At every month end, traffic doubles and the site slows down, and the team had assumed the availability set would add VMs automatically when demand rose. Which statement correctly compares availability sets with Virtual Machine Scale Sets?
A: An availability set only spreads the VMs you create across fault and update domains; a scale set can add and remove VMs automatically with autoscale

G: ## Availability sets
An **availability set** improves availability by distributing a fixed group of VMs that **you create** across fault domains (shared power and network) and update domains (planned maintenance groups). It has no extra cost, and it does **not** change the number of VMs.
## Virtual Machine Scale Sets
A **scale set** manages a group of load-balanced VMs as one resource:
- **Autoscale**: adds VMs as demand rises and removes them when it falls, based on metrics or a schedule, which also cuts cost when demand is low.
- **High availability**: spreads instances across fault domains or availability zones.
- **Central management**: VM instances are configured and updated centrally.
- Works with Azure Load Balancer (layer 4) or Application Gateway (layer 7).
- No extra charge for the scale set itself; you pay for the VMs, storage and networking it uses.
Microsoft now recommends scale sets with Flexible orchestration for high availability with the widest range of features.
Example: a scale set keeps 3 instances normally and grows to 6 when average CPU stays above 70%.
W: Placement versus scaling: an availability set only controls where the VMs you created are placed, while a scale set can automatically change the number of instances with demand.
X: B=Availability set adds VMs: an availability set never adds VMs, and scale set autoscale runs on rules or schedules without manual approval.
C=Both autoscale: availability sets do not autoscale, and they do spread VMs across fault domains; that is their main purpose.
D=Autoscale depends on zones: availability sets do not autoscale in any region, and scale sets can autoscale whether or not they use availability zones.
T: Availability sets place a fixed set of VMs for resilience; scale sets add and remove identical VMs automatically.
V: Azure Virtual Machines, Virtual Machine Scale Sets, availability sets
