@ AZ-900 D1 T1.2 applied definition
S: A CTO tells the board that cloud platforms "naturally support a reliable and resilient infrastructure." Which explanation of this claim matches how Microsoft describes cloud reliability?
A: The cloud's decentralized design lets resources run in regions around the world, so a disaster in one region leaves others running.
B: The cloud provider contractually guarantees that no service will ever go down, so the customer never needs to plan for failure.
C: The pay-as-you-go model lets the company stop paying for resources during an outage, so failures cost the business nothing.
D: The cloud's preconfigured templates deploy every resource the same way, so configuration mistakes can never take a system down.
K: A
G: ## Reliability as a cloud benefit
Microsoft defines **reliability** as the ability of a system to recover from failures and continue to function. It is also one of the pillars of the Azure Well-Architected Framework.
## Why the cloud helps
- The cloud has a **decentralized design**: you can deploy resources in regions around the world instead of in one building.
- Because of this global scale, a catastrophic event in one region does not stop the other regions.
- You can design applications to take advantage of this, for example by running copies of a workload in more than one region.
## What reliability does not mean
Reliability is not a promise that nothing fails. Hardware, software and whole sites can still fail; a reliable design expects failure and recovers from it. Microsoft notes that in some cases the cloud environment shifts to another region for you, but in general you design your applications to take advantage of the extra regions.
## Example
A booking service runs in two Azure regions. When a storm takes one region offline, users are served from the other region while the first one recovers.
W: Decentralized, global design: Microsoft ties cloud reliability to the ability to deploy resources in regions around the world, so that one region's catastrophic event does not stop the others.
X: B=No-outage guarantee: no provider promises that nothing ever fails. Reliability is about recovering from failures, so customers still design for them.
C=Pay-as-you-go during outages: consumption pricing is a cost benefit (operational expenditure), not a reason the infrastructure recovers from failures.
D=Preconfigured templates: templates support consistent deployments (governance and manageability), but they do not make a system resilient to a regional disaster.
T: Cloud reliability comes from a decentralized, global design: resources in many regions let a system recover and keep working when one location fails.

@ AZ-900 D1 T1.2 applied use-case
S: An accounting firm runs its reporting app on one Azure virtual machine. At month-end the reports run out of memory, and the app cannot be split across several machines. The extra capacity is not needed the rest of the month. What should the firm do?
A: Scale out horizontally by adding identical virtual machines for month-end and removing them again once the reports are finished.
B: Scale up vertically by giving the virtual machine more CPU and RAM for month-end, then scale it back down once the reports finish.
C: Reserve a larger virtual machine size for three years, so that the extra memory is always available and paid for at a lower rate.
D: Put a load balancer in front of the virtual machine, so that the month-end report requests are spread more evenly across its memory.
K: B
G: ## Scalability as a cloud benefit
**Scalability** is the ability to adjust resources to meet demand. Because the cloud is a consumption-based model, you only pay for what you use: when demand drops, you reduce resources and so reduce costs.
## Two directions of scaling
- **Vertical scaling** changes the **capabilities** of a resource. Scale **up** to add CPUs or RAM to a virtual machine; scale **down** by lowering the CPU or RAM specifications when you over-specified it.
- **Horizontal scaling** changes the **number** of resources. Scale **out** by adding virtual machines or containers when demand jumps; scale **in** by removing them when demand drops. It can be automatic or manual.
## Choosing
Horizontal scaling only helps if the work can be shared across instances. An app that must run on one machine needs a bigger machine: vertical scaling.
## Example
On the 28th the firm resizes its VM to a size with twice the memory; on the 3rd of the next month it resizes back to the original size and pays the higher rate only for those days.
W: Vertical scaling: Microsoft describes scaling up as adding CPUs or RAM to a virtual machine and scaling down as lowering them again, which suits an app that must stay on one machine and needs more memory only at month-end.
X: A=Horizontal scale-out: adding instances only helps when the work can be spread across machines, and this app cannot be split, so the extra VMs would sit idle.
C=Three-year reservation: a reservation is a pricing commitment, not scaling; it keeps paying for the larger size all month, the opposite of reducing resources when demand drops.
D=Load balancer: load balancing spreads requests across several resources; with a single VM there is nothing to spread to, and it does not add memory.
T: Vertical scaling changes the size (CPU, RAM) of a resource; horizontal scaling changes the number of resources.

A: Autoscaling, which adds resource instances automatically when demand rises and removes them again once the demand drops.

Consumption-based pricing does not have to mean unpredictable bills. Microsoft describes **cost predictability** as the ability to predict or forecast cloud spend, and lists how the cloud supports it:

- Apply **data analytics** to find patterns and trends that help plan resource deployments.
- Estimate potential spend with tools such as the **Azure Pricing Calculator**.

- Autoscaling and load balancing support **performance** predictability: they keep the user experience steady.
- Running in several regions supports **reliability**: the system keeps working when one region fails.

After three months of tracking, the director sees that storage grows about 5% a month and that compute peaks every quarter-end, so she builds next year's budget from those trends.
W: Usage tracking and analytics: seeing consumption in real time and analyzing its patterns lets the company forecast future spend and adjust resources, which is how Microsoft describes cost predictability.

@ AZ-900 D1 T1.2 applied use-case
S: A small online shop hosts its website on two servers in a rented rack. Floods of traffic from thousands of compromised machines keep knocking the site offline, and its two-person IT team cannot build defenses at that scale. Which cloud benefit addresses this most directly?
A: Security, because cloud providers are typically well suited to handle these large-scale attacks, which makes the shop's network more robust.
B: Cost predictability, because real-time tracking of resource use shows what each traffic flood costs, so the shop can forecast its spend.
C: Management in the cloud, because the team can reach the website's resources through the portal, the CLI, APIs or PowerShell at any time.

G: ## Distributed denial of service (DDoS)
A DDoS attack tries to exhaust an application's resources, making it unavailable to legitimate users. It can target any endpoint that is publicly reachable through the internet, and the traffic usually comes from many machines at once, so a small team with a few servers cannot absorb it.
## The security benefit of the cloud
Microsoft lists DDoS among the security benefits of the cloud: cloud providers are typically well suited to handle things like DDoS attacks, making your network more robust and secure. A provider operates at a scale and with expertise that a small company cannot match.
## The Azure service
**Azure DDoS Protection**, combined with application design best practices, provides enhanced DDoS mitigation for resources in a virtual network. It protects at network layers 3 and 4; web applications add layer 7 protection with a web application firewall (WAF).
## Example
The shop moves its site to Azure, enables DDoS protection on the virtual network and adds a WAF in front of the web tier; attack traffic is absorbed before it reaches the site.
W: Security: Microsoft says cloud providers are typically well suited to handle distributed denial of service attacks, making the customer's network more robust and secure, which is exactly the problem the small team cannot solve alone.
X: B=Cost predictability: tracking usage forecasts the bill; it does nothing to stop attack traffic from taking the site offline.
C=Management in the cloud: the portal, CLI, APIs and PowerShell are ways to manage resources, not defenses against attack traffic.
D=High availability and SLAs: an SLA states the uptime Microsoft commits to for a service; it is not a defense, and nothing guarantees that a site can never be taken offline.
T: Handling DDoS attacks at a scale a small company cannot match is part of the security benefit of the cloud.

**Management of the cloud** is about managing your cloud resources themselves, often automatically. In the cloud you can:

- Deploy resources from a preconfigured template, removing manual configuration.
- Monitor the health of resources and automatically replace failing resources.

C=Azure portal: using a web portal is a management in the cloud example, describing the tool rather than what happens to the resources.
D=Azure APIs: calling APIs is another management in the cloud method, alongside the portal, CLI and PowerShell.
T: Management of the cloud = autoscaling, templates, self-healing and alerts; management in the cloud = portal, CLI, APIs and PowerShell.

- **IaaS** is the most flexible category and provides the maximum amount of control. It places the most responsibility on the customer: the provider covers physical security, power and connectivity, and the customer manages the operating system, network configuration and more.
- **PaaS** is a middle ground. The provider also maintains the operating systems, middleware, development tools and analytics services, and responsibility is spread between provider and customer.
- **SaaS** is the most complete model from a product perspective. It is the least flexible but the easiest to start with; the provider manages almost all of the application stack.
## The trade-off
More control means more management effort. Moving from IaaS to PaaS to SaaS, you give up control and gain less work and faster adoption.

B=SaaS first: this reverses the spectrum; SaaS is the least flexible model and leaves the fewest decisions to the customer.
C=IaaS, SaaS, PaaS: in SaaS the customer does not manage any runtime; the provider manages almost the whole application stack, so SaaS comes last.
T: Customer control and responsibility decrease from IaaS to PaaS to SaaS, while ease of use increases.

@ AZ-900 D1 T1.3 advanced tradeoff
S: A team runs a standard .NET web app on five Azure virtual machines and spends many hours each month on operating system patches and server maintenance. The app needs no custom OS changes. Which move reduces this effort, and what is the trade-off?
A: Move to SaaS by rebuilding the app inside Microsoft 365, giving up the ability to choose which features the company's customers see.
B: Move to a private cloud in the company's own datacenter, giving up the pay-as-you-go pricing model while keeping full OS control.
C: Stay on IaaS but add more virtual machines, giving up some budget so that each VM carries less load and needs fewer OS patches.
D: Move to PaaS with Azure App Service, giving up direct control of the operating system in exchange for Microsoft maintaining it.
K: D
G: ## Flexibility versus management effort
Each service type trades control for convenience:
- **IaaS** gives maximum flexibility and control, and the largest operational responsibility: the customer installs, configures and patches the operating system.
- **PaaS** removes the operating system and middleware from the customer's list. You do not have to worry about licensing or patching operating systems; you focus on code, data and access controls. The price is that you can no longer customize the OS.
- **SaaS** is the least flexible: you use a finished application rather than running your own code.
## Choosing
If an application needs custom OS changes, IaaS is justified. If it is a standard web app that runs on a supported runtime, PaaS removes most of the patching work.
## Example
After moving to App Service, the team's monthly patch window disappears; it now deploys code and manages app settings, scaling rules and access.
W: PaaS with App Service: Microsoft maintains the operating system and platform, removing the patching work, and the cost of that convenience is losing direct control of the OS, which this app does not need.
X: A=SaaS in Microsoft 365: Microsoft 365 is a productivity suite, not a platform for hosting a company's own web app, so the app cannot be moved there.
B=Private cloud: running the servers in the company's own datacenter keeps all OS patching and adds hardware maintenance, so the effort grows instead of shrinking.
C=More IaaS VMs: every extra VM has its own operating system to patch; load per VM does not change how often patches are needed.
T: Moving a standard web app from IaaS to PaaS trades OS control for far less patching and maintenance.

S: A company runs an application on Azure virtual machines (IaaS). After a change, the VMs can no longer reach an external partner service, because a network security rule that the company's own admins created blocks the traffic. Who must fix it?
A: Microsoft, because in IaaS the provider is responsible for network connectivity to the internet, including every rule that controls it.
B: The company, because in IaaS the customer is responsible for network configuration, including the security rules it created.
C: Microsoft, because the physical network is always the provider's job, and every network rule in Azure runs on the physical network.

K: B
G: ## Network responsibilities in IaaS
In IaaS, the cloud provider maintains the **hardware, network connectivity to the internet and physical security**. The customer is responsible for everything else, including:
- operating system installation, configuration and maintenance,
- **network configuration** (virtual networks, subnets, firewall and security rules),
- database and storage configuration.
Microsoft's responsibility matrix marks **network controls** as the customer's in IaaS: you configure all network security, including firewalls and segmentation.
## Physical versus logical network
The **physical network** (cables, switches, the datacenter's internet links) is always Microsoft's. The **logical rules** you place on your virtual networks and VMs are configuration you own. A rule you wrote that blocks traffic is a configuration problem for you to fix.
W: Customer fixes network configuration: in IaaS network configuration and network controls belong to the customer, so the admins must correct the rule they created.
X: A=Microsoft for internet connectivity: Microsoft keeps the datacenter connected to the internet, but the rules that allow or block a VM's traffic are customer configuration.
C=Physical network: the physical network is always Microsoft's, but the blocking rule is logical configuration the customer created, not a physical fault.
D=The partner: the traffic never leaves Azure because the company's own rule blocks it, and a destination service does not manage another customer's outbound rules.
T: In IaaS Microsoft owns the physical network and internet connectivity; the customer owns network configuration and the security rules on its VMs.
