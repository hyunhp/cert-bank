@ AI-901 D2 T2.4 applied use-case
S: A small accounting firm receives supplier invoices as PDFs in many different layouts. A developer must return the vendor name, invoice total and line items as JSON this week, and nobody has time to design or label a schema. Which Content Understanding analyzer should the first version of the app call?
A: The prebuilt-invoice analyzer, which already has a tuned invoice field schema
B: The prebuilt-read analyzer, which returns the words and paragraphs of each page
C: The prebuilt-document base analyzer, called directly without any field schema
D: The prebuilt-imageSearch analyzer, which writes a one-paragraph file description
K: A
G: ## Analyzers are the unit of work in Content Understanding
Every Content Understanding request names an **analyzer**: a reusable configuration that says what kind of content is processed, what is extracted and how the output is structured. There are several families:
- **Content extraction analyzers** such as `prebuilt-read` and `prebuilt-layout` return text, layout and tables only. They have no field schema.
- **Base analyzers** (`prebuilt-document`, `prebuilt-image`, `prebuilt-audio`, `prebuilt-video`) are parents you build custom analyzers from.
- **RAG analyzers** such as `prebuilt-documentSearch` or `prebuilt-imageSearch` produce Markdown and summaries for search indexes.
- **Domain-specific analyzers** such as `prebuilt-invoice`, `prebuilt-receipt`, `prebuilt-idDocument` and `prebuilt-contract` come with a field schema tuned for that document type.
## Start with a prebuilt when one exists
Learn's guidance is to start with a prebuilt analyzer whenever one covers your document type, and only build a custom analyzer when you need fields it does not return. For invoices, `POST .../analyzers/prebuilt-invoice:analyze` returns fields such as the vendor, totals and a `LineItems` array, each with a confidence score.
W: prebuilt-invoice: it is a domain-specific analyzer whose ready-made schema already covers vendor, totals and line items across many invoice layouts, so the app gets structured JSON with no schema design or labeling.
X: B=prebuilt-read: it performs OCR and returns words, paragraphs, formulas and barcodes, but it has no field schema, so the developer would still have to find the vendor and total in raw text.
C=prebuilt-document alone: the base document analyzer is meant to be the parent of a custom analyzer. Without a field schema written by the team, it does not know which invoice fields to return.
D=prebuilt-imageSearch: it is a RAG analyzer for images that generates a description for search. It does not return invoice fields such as totals or line items.
T: When a domain-specific prebuilt analyzer such as prebuilt-invoice covers the document type, call it first; build a custom analyzer only for fields it lacks.

@ AI-901 D2 T2.4 applied definition
S: An insurer builds a custom document analyzer for claim letters. It needs three fields: ClaimNumber (printed in the letter), DamageSummary (a short summary written from the whole letter) and ClaimType (one of Auto, Home or Travel). Which field methods should the schema use?
A: ClaimNumber extract, DamageSummary generate, ClaimType classify with an enum of the three types
B: ClaimNumber generate, DamageSummary extract, ClaimType classify with an enum of the three types
C: ClaimNumber extract, DamageSummary classify, ClaimType generate with a description of the types
D: ClaimNumber classify, DamageSummary generate, ClaimType extract with a description of the types
K: A
G: ## Three ways a field gets its value
Each field in an analyzer's `fieldSchema` can set a `method`:
- **extract**: the value is taken as it appears in the content, such as an invoice number or a date. This method is supported for document analyzers only.
- **generate**: the model produces the value freely from the content, such as a summary, a risk level or a scene description.
- **classify**: the model picks one value from a fixed list given in `enum`, such as a document type or a sentiment.
If you leave `method` out, the service chooses one based on the field type and description, but Learn's best practice is to set it explicitly.
## Example
```
"ClaimType": {"type": "string", "method": "classify", "enum": ["Auto", "Home", "Travel"]}
```
W: extract, generate, classify: the claim number is literal text in the letter (extract), the damage summary must be written by the model (generate), and the claim type must be one of three known values (classify with an enum).
X: B=Generate the number, extract the summary: a summary does not appear word for word in the letter, so it cannot be extracted, and generating an identifier invites the model to invent one instead of copying it.
C=Classify the summary: classify chooses from a fixed list of categories, which cannot hold free-form summaries, while generating the claim type allows values outside Auto, Home and Travel.
D=Extract the claim type: the type is a decision about the letter, not a value printed in it, and classify is meant for picking from fixed categories rather than copying an identifier.
T: Extract copies values that appear in a document, generate writes values such as summaries, and classify picks one value from an enum.

@ AI-901 D2 T2.4 advanced troubleshooting
S: A developer's custom analyzer uses baseAnalyzerId prebuilt-document. The field PolicyNumber has "method": "extract", and the analyzer config sets estimateFieldSourceAndConfidence to false to keep responses small. Creating the analyzer fails on that field. What should the developer change?
A: Set estimateSourceAndConfidence to true for PolicyNumber, because extract fields need source and confidence
B: Change baseAnalyzerId to prebuilt-read, because only content extraction analyzers allow the extract method
C: Set returnDetails to false in the config, because detailed output conflicts with fields that use extract
D: Change the field type to array, because the extract method only returns values found in repeating tables
K: A
G: ## Extract relies on grounding
A field with `"method": "extract"` copies a value exactly as it appears in the document. Content Understanding ties that value to its location, so Learn states that **extract requires `estimateSourceAndConfidence` to be true for the field**.
Two settings control this:
- `estimateFieldSourceAndConfidence` in the analyzer `config` turns source (page and bounding region) and confidence on for all fields of a document analyzer.
- `estimateSourceAndConfidence` on a single field overrides the analyzer-level setting for that field.
So a team that wants small responses can leave the analyzer-level switch off and turn it on only for the fields that use extract.
## Example
```
"PolicyNumber": {"type": "string", "method": "extract", "estimateSourceAndConfidence": true}
```
W: Per-field source and confidence: turning `estimateSourceAndConfidence` on for the extract field meets its requirement, while the rest of the analyzer can keep the analyzer-level setting off.
X: B=Switch to prebuilt-read: prebuilt-read is a content extraction analyzer with no field schema, and custom analyzers can only derive from the four base analyzers such as prebuilt-document.
C=Turn off returnDetails: returnDetails only controls how much extra detail the response carries; it has nothing to do with the requirement that extract fields return source and confidence.
D=Make it an array: extract works for simple values such as strings and dates; the field type does not cause the error, and a single policy number is not a list.
T: A field that uses the extract method must have source and confidence estimation turned on, either for that field or for the whole document analyzer.

@ AI-901 D2 T2.4 applied tradeoff
S: A logistics company uses a document analyzer to read delivery notes and wants to send only doubtful results to a human reviewer. TotalCharge drives billing, while DriverComments is rarely used. How should the app use the confidence scores Content Understanding returns?
A: Apply a stricter confidence threshold to TotalCharge than to DriverComments and tune both values on sample delivery notes
B: Apply one fixed threshold of 0.5 to every field, because the service calibrates all scores to make 0.5 the correct cut-off
C: Ignore confidence for TotalCharge and review every total by hand, because confidence is returned only for generated fields
D: Treat any returned value as correct, because the analyzer leaves out every field that has a confidence lower than 0.9
K: A
G: ## Confidence scores enable straight-through processing
For document analyzers, Content Understanding can return a **confidence score from 0 to 1** for each field value (with source estimation turned on). The goal is straight-through processing: high-confidence values flow straight into the business system, and low-confidence ones go to a person.
## Thresholds per field
Learn's best practices suggest setting **different thresholds by field criticality**, for example:
- critical fields such as totals or termination dates: a high threshold (around 0.90)
- important fields such as vendor names: a medium threshold (around 0.80)
- non-critical fields such as comments: a lower threshold (around 0.70)
These numbers are only an illustration; the right values are found experimentally on your own documents. Currently only document analyzers return confidence scores.
W: Field-specific thresholds: a mistake in TotalCharge costs money and a mistake in comments costs little, so the total gets a higher bar, and testing on real delivery notes sets the actual numbers.
X: B=One fixed 0.5 cut-off: Learn does not define a universal cut-off; it recommends thresholds that depend on how critical the field is and that you determine experimentally.
C=Confidence only for generated fields: confidence scores in document analyzers apply to extract, classify and generate fields alike, so the total does get a score the app can check.
D=Low-confidence fields are dropped: the service returns the value with its score and leaves the decision to the app; it does not hide values below a built-in limit.
T: Use confidence scores to route only doubtful values to people, with stricter thresholds for critical fields, tuned on your own documents.

@ AI-901 D2 T2.4 applied use-case
S: In a review screen, clerks check each value that a document analyzer extracted from scanned lease agreements. They want the app to highlight the exact spot on the page where each value was found. Which part of the analysis result should the app use?
A: The source and spans returned with each field, which locate the value on its page
B: The markdown string of the document, searched for the first match of each value
C: The analyzerId and createdAt values in the result, which identify the page region
D: The warnings array of the result, which lists the page coordinates of each field
K: A
G: ## Grounding: where did this value come from?
**Grounding** links each extracted or generated value back to the place in the content it came from. For document analyzers it is turned on with `estimateFieldSourceAndConfidence` (or per field with `estimateSourceAndConfidence`). Each field in the result then carries:
- `source`: the page number and the bounding polygon of the value, written like `D(1, x1,y1, ...)` for page 1
- `spans`: the offset and length of the value inside the result's Markdown text
- `confidence`: the score from 0 to 1
A review UI can draw a box at the `source` coordinates so a clerk confirms the value at a glance instead of reading the whole lease.
W: Field source and spans: they are the grounding information for each value, giving the page and bounding region (and the text offset), which is exactly what a highlight needs.
X: B=Search the markdown: a value such as a date or an amount can appear several times in a lease, so the first text match may point to the wrong place; the result already says where each value came from.
C=analyzerId and createdAt: these describe which analyzer ran and when the result was created; they carry no location information for individual fields.
D=Warnings array: warnings report problems such as guardrail detections during analysis; field locations are not stored there.
T: Grounding returns each field's page and bounding region (source) and text offset (spans), so reviewers can verify values against the original document.

@ AI-901 D2 T2.4 applied troubleshooting
S: A custom analyzer reads purchase orders from many suppliers. The field DeliveryDate is often empty because suppliers label it "Ship Date", "Expected Delivery" or "Arrival". The team wants better results before adding labeled samples. Which two changes follow Learn's best practices? (Select TWO)
A: List the alternative labels and where the date usually appears in the field description
B: Write the field name and description in the same language as the purchase orders
C: Describe the field mainly by what it is not, such as "not the order date or invoice date"
D: Create a separate category for every supplier layout so each gets its own analyzer

K: A,B
G: ## The field description is a mini-prompt
In Content Understanding, the model reads each field's `description` as a small prompt. Learn's best practices for field schemas:
- **Be detailed**: say where the value usually is and what format it has.
- **Include all aliases**: list the different labels documents use for the same thing.
- **Use affirmative language**: describe what the field is, not what it isn't.
- **Match the language of the content**: Italian invoices get Italian field names and descriptions.
- **Use structured types** (arrays of objects) for repeated data instead of strings that hold JSON.
## Descriptions before examples
Learn recommends refining descriptions first; clear descriptions often fix accuracy without more data. Only if confidence stays low do you add labeled training examples.
W: A=Aliases and location hints: listing "Ship Date", "Expected Delivery" and "Arrival" tells the model that all of these labels mean the delivery date.
B=Same language as the documents: Learn notes that a mismatch between the schema language and the file language can significantly reduce accuracy.
X: C=Negative wording: Learn advises describing what a field is; telling the model what the field is not is less clear and less effective.
D=One category per layout: Content Understanding handles visual template variations itself; Learn advises semantic categories, not one per visual template.
E=String holding JSON: Learn advises proper structured types instead of strings that request JSON, and the problem here is recognizing the label, not the format.
T: Improve fields first with clear, affirmative descriptions that list aliases and match the document language; add labeled examples only if that is not enough.

@ AI-901 D2 T2.4 applied definition
S: A custom analyzer must return every product row from a packing list, each with a product code, quantity and weight. How should the developer define this in the field schema?
A: An array field whose items are objects with ProductCode, Quantity and Weight properties
B: A string field whose description asks the model to write the rows as a JSON text block
C: Three separate array fields of strings, one each for codes, quantities and weights
D: A classify field whose enum lists the product codes the company currently ships
K: A
G: ## Structured types in a field schema
A Content Understanding field has a `type`: `string`, `number`, `boolean`, `date`, `object` or `array`.
- `object` groups named sub-fields under `properties`, for example an address with street and city.
- `array` holds a list; its `items` describe each entry, and an entry can itself be an object.
For repeated data such as invoice line items, Learn's best practice is an **array of objects**, not a string field that asks for JSON. Typed fields are also normalized by the service, for example numbers come back as numbers.
## Example
```
"Rows": {"type": "array", "items": {"type": "object",
  "properties": {"ProductCode": {"type": "string"}, "Quantity": {"type": "number"}, "Weight": {"type": "number"}}}}
```
Learn also advises not to nest more than two or three levels deep.
W: Array of objects: each row becomes one object with typed properties, so the code, quantity and weight of a row always stay together in the result.
X: B=String with JSON: Learn advises against strings that request JSON output; the app would have to parse free text, and numbers would not be typed or normalized.
C=Three parallel arrays: nothing ties the third code to the third quantity, so one missed value shifts every later row out of line.
D=Classify with product codes: classify picks one value from a fixed list; it cannot return a list of rows with quantities and weights.
T: Model repeated rows as an array of objects with typed properties, not as text that contains JSON.

@ AI-901 D2 T2.4 advanced use-case
S: A finance team scans each day's mail into one PDF that mixes invoices and receipts in random order. The app must split the PDF, process every invoice with prebuilt-invoice and every receipt with prebuilt-receipt. How should the developer configure the custom document analyzer?
A: Set enableSegment to true and define contentCategories for invoice and receipt, each with its own analyzerId
B: Set enableSegment to false and define contentCategories so the whole file is routed to prebuilt-invoice
C: Set segmentPerPage to true and add one array field to the schema for all invoice and receipt values
D: Call prebuilt-procurement on every single page and then merge the pages back into one result file
K: A
G: ## Classification and segmentation in one analyzer
A document analyzer can route content to other analyzers through `contentCategories`. Each category has:
- a `description` that acts as a prompt for recognizing that kind of content, and
- an optional `analyzerId` of the analyzer that processes content in that category.
`enableSegment` decides what happens with the file:
- `true`: the file is split into segments based on the category descriptions, each segment gets one category, and segments with an `analyzerId` are analyzed by it. The result has the segment list plus extra content objects for routed segments.
- `false`: the whole file is classified into one category and routed as a whole.
## Example
```
"config": {"enableSegment": true, "contentCategories": {
  "invoice": {"description": "...", "analyzerId": "prebuilt-invoice"},
  "receipt": {"description": "...", "analyzerId": "prebuilt-receipt"}}}
```
W: Segment and route: with segmentation on, the PDF is cut into logical documents, each is classified as invoice or receipt, and each segment is sent to the analyzer named in its category.
X: B=enableSegment false: the whole PDF would be classified as a single document into one category, so a mixed file would not be split into separate invoices and receipts.
C=segmentPerPage with one array: one segment per page only helps when segmentation and categories are defined, and a single array field cannot apply two different prebuilt schemas.
D=prebuilt-procurement page by page: a multi-page invoice would be broken into pages analyzed separately, and splitting and merging by hand rebuilds what segmentation already does.
T: For a file that mixes document types, turn on enableSegment and route each contentCategory to its own analyzer with analyzerId.

@ AI-901 D2 T2.4 advanced troubleshooting
S: A classifier analyzer defines two contentCategories, "invoice" and "receipt". Sometimes users upload delivery notes, and the result labels each one as an invoice, which sends it into the invoice workflow. What is the simplest fix?
A: Add an "other" category with a description, so content that matches neither type has somewhere to go
B: Lower the confidence threshold in the app, so that a delivery note gets a score below the invoice type
C: Change the invoice category to use the generate method, so the model can return a new category name
D: Set enableSegment to true, so the analyzer returns an empty result for content it cannot categorize
K: A
G: ## Classification always chooses one category
When an analyzer uses `contentCategories`, every file or segment is assigned to **exactly one** of the listed categories. Learn warns that if no "other" or "default" category exists, content is **forced** into one of the listed ones, even when it fits none of them.
## The fix
Add a catch-all category:
```
"other": {"description": "Any document that is not an invoice or a receipt"}
```
A category without an `analyzerId` is only labeled, not processed further, so delivery notes are recognized and simply not sent to the invoice analyzer. Learn also suggests semantic categories with clear distinguishing descriptions.
W: Catch-all category: once "other" exists, a delivery note has a valid category to land in, so it stops being forced into the invoice category.
X: B=Lower a threshold: the forced choice happens inside the analyzer; a threshold in the app does not create a category for documents that are neither invoices nor receipts.
C=Generate method on a category: methods belong to fields in the field schema; content categories are a fixed list, and generate would not stop the forced choice.
D=Turn on segmentation: segmentation splits a file into parts, but each part is still classified into one of the listed categories, so the delivery note would still land in invoice.
T: Classification always picks one listed category, so add an "other" category to catch content that matches none of them.

E=Contracts with inferred fields: the guide recommends Content Understanding's prebuilt-contract for mostly unstructured agreements that need reasoning.

@ AI-901 D2 T2.4 advanced troubleshooting
S: A developer creates a new Microsoft Foundry resource and calls prebuilt-invoice with the REST API. The analysis fails because no model is available, yet prebuilt-layout works on the same resource. What must the developer set up?
A: Deploy the required models and set them as the resource's default model deployments
B: Assign the Cognitive Services User role to the PDF file in the storage account first
C: Switch the analyzer to prebuilt-read, because invoices can only be analyzed with OCR
D: Enable an Azure AI Search index, because prebuilt analyzers write their results there

G: ## Content Understanding uses your model deployments
Generative features in Content Understanding (fields, figure analysis, segmentation, summaries) run on **Foundry model deployments in your resource**. You pay for the tokens of those deployments, plus the Content Understanding meters. Before such analyzers work, you must:
1. Deploy the supported chat completion and embedding models in the Foundry resource.
2. Connect them as **defaults**, either in Content Understanding Studio (settings, add resource, optionally auto-deploy) or with `PATCH /contentunderstanding/defaults` and a `modelDeployments` map.
You can also pass `modelDeployments` in an individual analyze request, which overrides the defaults for that call.
## Why layout still worked
`prebuilt-read` and `prebuilt-layout` don't need a language model or an embedding model, so they run even when no defaults exist. `prebuilt-invoice` does need them.
W: Default model deployments: prebuilt-invoice uses generative models for its fields, so the resource needs deployed models mapped as defaults (or passed per request) before the analyzer can run.
X: B=Role on the file: an access problem would also break prebuilt-layout on the same file; the difference here is that only the invoice analyzer needs a model.
C=Switch to prebuilt-read: read returns text but no invoice fields, and invoices are not limited to OCR; the missing model setup is the real problem.

So the app reads `contents[0].fields.AmountDue.valueObject.Amount.valueNumber` to get 610, and the matching currency from `CurrencyCode.valueString`.
W: Nested valueNumber: AmountDue is an object, its Amount sub-field has type number, and number fields keep their value in valueNumber.
X: B=valueString on the object: an object field holds its data in valueObject; the amount is a number sub-field, not a string on the parent.
C=result.warnings: warnings carry issues found during analysis, such as guardrail detections, not extracted values.
D=result.usage: usage reports consumption such as tokens and processed units for billing, not values from the invoice.
T: In the REST result, each field stores its value in a type-named property; objects nest sub-fields under valueObject and numbers use valueNumber.
