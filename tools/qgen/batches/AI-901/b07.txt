@ AI-901 D2 T2.2 applied comparison
S: A clinic stores patient feedback forms in a database. Before the text is copied to an analytics team, every phone number, email address and patient name must be masked, and the job must give the same result every time it runs. Which approach fits best?
A: Call recognize_pii_entities from the Azure Language client library and store the redacted_text value it returns
B: Send each form to a deployed gpt-4.1-mini model with a prompt asking it to replace any personal details with asterisks
C: Call extract_key_phrases from the Azure Language client library and delete every returned phrase from the stored text
D: Call recognize_entities from the Azure Language client library and mask every entity that it labels as a Person entity
K: A
G: ## Two ways to analyze text in Foundry
Microsoft Foundry gives you two kinds of tools for text analysis:
- A **general-purpose model** (for example a deployed GPT model) follows a natural-language prompt. It is flexible, but it generates text probabilistically, so two calls with the same prompt can return different wording or formatting.
- **Azure Language in Foundry Tools** has purpose-built features that return structured, predictable output for one task, such as a language code with a confidence score, or a redacted copy of the text.
## PII detection
PII (personally identifiable information) detection is an Azure Language **core** feature. It finds entities such as `Person`, `PhoneNumber` and `Email` and returns both the list of entities (category, confidence score, offset, length) and the **redacted text**.
In the Python library (`azure-ai-textanalytics`) the call is `client.recognize_pii_entities(documents)`; each result has `redacted_text` and `entities`. By default each detected character is replaced with `*`.
## Example
`Call our office at 312-555-1234` becomes `Call our office at ************`.
W: PII detection with redacted_text: the PII feature is built for exactly this job. It detects names, phone numbers and emails, returns a ready-made masked copy of each document, and gives the same structured result for the same input, which suits an automated pipeline.
X: B=Prompt a GPT model: a model can often do this, but its output is generated text that can vary between runs and is not guaranteed to catch every value or keep the rest of the text unchanged, which is weak for a privacy control.
C=Key phrase extraction: key phrases are the main concepts of the text (such as "appointment delay"), not personal data. Deleting them would remove useful content and leave phone numbers and emails in place.
D=Prebuilt NER on Person: general entity recognition finds people, places and dates but is not a redaction feature; masking only `Person` would leave phone numbers and email addresses visible.
T: To mask personal data consistently, use Azure Language PII detection and keep its redacted text; a prompt to a general model gives variable output.

@ AI-901 D2 T2.2 applied tradeoff
S: A product team wants a quick prototype that reads each customer review, sorts it into one of their own five categories (such as "billing" or "delivery"), and writes a one-line English summary even when the review is in German. They have no labeled training data. What should they use?
A: A general-purpose model deployed in the Foundry project, called through the Responses API with a prompt that lists the categories
B: Azure Language custom text classification, trained on a labeled set of reviews for each of the five categories they defined
C: Azure Language key phrase extraction, then a lookup table that maps each returned phrase to one of the five categories
D: Azure Language language detection, then route each German review to a separate project that holds a translated copy
K: A
G: ## When a general-purpose model is the better tool
A general-purpose language model can follow instructions to classify, summarize, translate and extract information **without any configuration or training**. Because everything is driven by the prompt, you can combine tasks freely in one request: "Assign one of these categories: billing, delivery, ... Then summarize the review in one English sentence."
In code you deploy a model in your Foundry project and call it with the OpenAI library, for example `client.responses.create(model=deployment_name, input=prompt)`.
## When Azure Language is the better tool
Azure Language features return fixed, structured output for a single task. Its custom features (custom text classification, custom NER) need you to **label training data** and train a model first.
## Trade-off
- Prompted model: fastest to prototype, flexible, but results can vary slightly between calls.
- Azure Language: predictable, structured results, but each feature does one job and custom ones need training.
W: Prompted general-purpose model: one prompt can classify into the team's own categories, translate and summarize in a single call with no training data, which is exactly what a quick prototype needs.
X: B=Custom text classification: this feature can classify into custom classes, but only after the team labels and trains on example reviews, which they don't have; it also doesn't write summaries.
C=Key phrases plus a lookup table: key phrases are words from the review, not categories, and a hand-built mapping would be brittle; it also produces no English summary of German text.
D=Language detection and routing: detection only names the language; it doesn't classify, translate or summarize anything, so the core tasks are still not done.
T: Use a prompted general-purpose model for flexible, combined text tasks without training data; use Azure Language when you need fixed, structured, repeatable output.

@ AI-901 D2 T2.2 applied use-case
S: A support portal receives tickets in many languages and must send each ticket to a queue named after its ISO 639-1 language code, such as "es" or "fr". The developer already has an authenticated TextAnalyticsClient named client. Which code gets the value to use as the queue name?
A: client.detect_language([text])[0].primary_language.iso6391_name
B: client.recognize_entities([text])[0].entities[0].category
C: client.extract_key_phrases([text])[0].key_phrases[0]
D: client.detect_language([text])[0].primary_language.confidence_score
K: A
G: ## Language detection in Azure Language
Language detection is an Azure Language **core** feature. It evaluates a piece of text and returns the **primary language** with:
- `name`: the language name, for example `Spanish`
- `iso6391_name`: the ISO 639-1 code, for example `es`
- `confidence_score`: a value between 0 and 1
## Calling it from Python
The Python client library is `azure-ai-textanalytics`. You create a `TextAnalyticsClient` with the endpoint and an `AzureKeyCredential`, then pass a **list** of strings. The method returns one result per input document, so `[0]` picks the first one.
```
result = client.detect_language([text])[0]
print(result.primary_language.name, result.primary_language.iso6391_name)
```
For "¡Hola! Me llamo Josefina y vivo en Madrid, España." the result is `Spanish`, `es`, `1.00`.
W: iso6391_name of the primary language: `detect_language` returns the detected language for each document, and `iso6391_name` is the two-letter code such as `es`, exactly the queue name the portal needs.
X: B=Entity category: `recognize_entities` returns categories such as `Location` or `Person` for things mentioned in the text; it says nothing about which language the ticket is written in.
C=First key phrase: key phrase extraction returns the main topics of the ticket, such as "refund request", not a language code.
D=Confidence score: this is a number between 0 and 1 that shows how sure the service is; it is useful for a fallback rule but is not the code to route on.
T: `detect_language` returns `primary_language` with `name`, `iso6391_name` and `confidence_score`; route on the ISO code.

S: A recruiting app uses Azure Language PII detection on candidate notes. The hiring team wants only phone numbers and email addresses redacted, while names, cities and dates stay readable. What should the developer change in the PII request?

G: ## What PII detection returns by default
Without extra settings, Text PII detects every entity category that is enabled by default for the input language (people, phone numbers, emails, addresses, IDs and many more) and redacts all of them in `redactedText`.
## Choosing the categories
The request accepts an optional `piiCategories` parameter. When you list categories such as `PhoneNumber` and `Email`, the service returns **only those categories** (unless you also include `default`), so only they are redacted. The same parameter can also turn on categories that are not enabled by default for a language.
## Other tuning options
- A **value exclusion policy** keeps specific terms (for example "police officer") from being redacted even if they fall into a detected category.
- **Redaction policies** decide how detected text is masked (a mask character such as `*`, the entity type, or no mask).
W: Limit piiCategories: listing only the phone number and email categories tells the service to detect and redact just those, so names, cities and dates stay in the text without any extra code.
X: B=Value exclusion list: exclusions are meant for a few known terms, not every candidate's name and city; maintaining a list of all personal values defeats the purpose of automatic detection.
C=Document-based PII: document PII handles native files such as .pdf and .docx. It is chosen by input format, not because it is the only way to pick entity types.
D=Filter sentences with NER first: dropping whole sentences would lose the very notes the team wants to read, and it adds a second call for something one parameter already does.
T: Use the `piiCategories` parameter to restrict PII detection (and redaction) to the categories you name.

G: ## Sentiment analysis levels
Azure Language sentiment analysis labels text as `positive`, `negative`, `neutral` or `mixed`, with confidence scores:
- at the **document** level (one label for the whole review)
- at the **sentence** level (one label per sentence)
## Opinion mining (aspect-based sentiment)
Opinion mining goes one step further. It finds **targets** (the thing being talked about, such as "breakfast") and the **assessments** about them (such as "cold"), each with its own sentiment. In the Python library you turn it on with `show_opinion_mining=True` on `analyze_sentiment`.
## Example
"The room was spotless but the breakfast was cold." gives a `mixed` document sentiment, target `room` = positive (assessment "spotless") and target `breakfast` = negative (assessment "cold").
Sentiment analysis and opinion mining are listed by Microsoft as **legacy** Azure Language capabilities: fully supported for existing and established use, while new investment goes to core features.

C=Key phrases: key phrase extraction lists topics such as "breakfast" without saying whether the guest liked them.
D=Entity categories: NER labels things such as locations or dates; it has no sentiment information at all.
T: For likes and dislikes per aspect, call `analyze_sentiment` with opinion mining turned on; document sentiment alone only gives one overall label.

G: ## Named entity recognition (NER)
NER finds items in text and assigns each one a **category** (and sometimes a subcategory). Azure Language offers two versions, both listed as core features:
- **Prebuilt NER** uses predefined types such as `Person`, `Location` (subcategory `GPE`), `Organization`, `DateTime` and `Quantity`. You just send text; there is nothing to train.
- **Custom NER** lets you define your own entity categories (for example "contract clause"), but you must label example documents and train a model.
## Example
"On May 2nd, 2017, John Smith visited New York to attend a conference hosted by Microsoft." returns `John Smith` (Person), `New York` (Location), `Microsoft` (Organization) and `May 2nd, 2017` (DateTime, Date).
In Python the call is `client.recognize_entities(documents)`, and each entity has `text`, `category`, `subcategory` and `confidence_score`.
W: Prebuilt NER: it already knows standard types such as Person, Organization, Location and DateTime, so the startup can tag articles immediately with no training data.
X: B=Custom NER: it is for categories you invent and needs labeled training documents, which the startup doesn't have and doesn't need for standard types.
C=Key phrase extraction: key phrases are uncategorized topics; the output doesn't say which phrase is a person and which is a place.
D=Text analytics for health: it is designed for clinical text (medications, diagnoses, dosages), not general news entities.
T: Use prebuilt NER for standard entity types with no training; use custom NER only when you need your own categories and have labeled data.

@ AI-901 D2 T2.2 advanced tradeoff
S: A law firm wants short summaries of long case notes. Its compliance rule says a summary may only contain sentences that appear word for word in the original notes. Which approach should the developer use?
A: Azure Language extractive summarization, which selects the most important sentences from the notes and keeps their original wording
B: Azure Language abstractive summarization, which writes new and concise sentences that capture the main ideas found in the notes

G: ## Two kinds of text summarization
Azure Language summarization condenses long text and supports two approaches:
- **Extractive**: picks key sentences from the document and returns them as they are, in their original positions, with a rank score.
- **Abstractive**: generates new, concise sentences that are not copied directly from the document.
A general-purpose model asked to "summarize" also writes new sentences, like abstractive summarization.
## Calling it from code
Summarization is a long-running operation. In the Python library you start it with `client.begin_analyze_actions(documents, actions=[ExtractiveSummaryAction(max_sentence_count=4)])` and read the results from the returned poller.
Summarization is listed by Microsoft as a **legacy** Azure Language capability: fully supported for existing and established use.
W: Extractive summarization: it returns sentences copied from the notes, so every sentence in the summary can be found word for word in the original, which satisfies the compliance rule.
X: B=Abstractive summarization: by design it produces new sentences that aren't copied from the source, which the firm's rule forbids.
C=Prompted general-purpose model: the model rewrites the content in its own words and may vary between calls, so verbatim sentences are not guaranteed.
D=Joined key phrases: key phrases are short fragments, not sentences, so a comma list is neither a readable summary nor verbatim sentences.
T: Extractive summarization keeps original sentences; abstractive summarization and prompted models write new ones.

G: ## One Foundry resource, two kinds of endpoint
A Foundry resource gives access to deployed models **and** to Foundry Tools such as Azure Language and Azure Speech. Different client libraries expect different endpoints of that resource:
- The **OpenAI library** (chat or Responses API on a deployed model) uses an endpoint like `https://<resource>.openai.azure.com/openai/v1/` plus a **model deployment name**.

C=Deploy a detection model: language detection is a prebuilt Azure Language feature with nothing to deploy, and `TextAnalyticsClient` does not take a deployment name.
D=Deployment name as credential: Azure Language authenticates with a key (or Microsoft Entra ID); a deployment name is not a credential and isn't used by this library.
T: The OpenAI library uses the `openai.azure.com/openai/v1/` endpoint and a deployment name; `TextAnalyticsClient` uses the `cognitiveservices.azure.com` endpoint and a key.

An agent's model can understand language, but on its own it gives generated, variable answers. When a task needs structured, deterministic analysis (a language code with a confidence score, an exact redacted text), the agent should call a purpose-built tool.
## Model Context Protocol (MCP)
MCP is an open standard for connecting agents to external tools. The agent is the MCP client; an MCP server exposes tools that the agent can discover and call without custom integration code.
## Azure Language MCP server
The **Azure Language MCP server** exposes Azure Language features (PII detection, language detection, NER, sentiment analysis, summarization, key phrases and more) through MCP. It is available as a remote server in the Foundry tool catalog and as a local server. In the Foundry portal you add it as a tool on the agent and configure the connection with your **Foundry resource name**; no separate Azure Language resource is needed.

C=Low-temperature second model: lower temperature makes output less random but it is still a generative model, not a detection and redaction service.
D=File search with a code list: a reference document can't scan new tickets for PII or detect their language; it only lets the agent look things up.
T: Give an agent deterministic text analysis by adding the Azure Language MCP server as a tool.

@ AI-901 D2 T2.2 applied use-case
S: A developer deployed gpt-audio-mini in a Foundry project. The app records a user's spoken question as a WAV file and must send it to the model in a chat completions request. How should the audio be included in the message?
A: Base64-encode the file and add it to the user content as an input_audio part with the data and a format of wav

G: ## Audio-capable models
Some models in Foundry accept **audio as input** (and can produce audio as output) through the normal `/chat/completions` API. Examples are `gpt-audio` and `gpt-audio-mini`. Supported input and output combinations include audio in with text out (for example, transcribe or answer a spoken question) and audio in with text plus audio out (a spoken reply).
## Sending audio in a message
The user message content becomes a list of parts. Next to an optional `text` part you add an `input_audio` part whose `data` is the **base64-encoded** audio and whose `format` names the encoding:
```
{"type": "input_audio", "input_audio": {"data": encoded_string, "format": "wav"}}
```
In Python you read the file in binary mode and encode it with `base64.b64encode(...)`.
Note: the Learn quickstart for audio completions calls the API with a preview API version (`2025-01-01-preview`).
W: input_audio with base64 data: the chat completions API carries audio inside the message as an `input_audio` content part holding base64 data and its format, so the model hears the user's question directly.
X: B=image_url part: `image_url` is the content type for images; the audio model doesn't download audio from a URL given as an image.
C=Local file path as text: the path is just text to the model; the client library doesn't open local files referenced in a prompt.
D=File ID as deployment name: the deployment name identifies the model to call; it can't be replaced by a file ID, and audio is passed inline in the message.
T: Send spoken prompts to an audio-capable model as an `input_audio` content part with base64 data and a format such as `wav`.

G: ## What a resource key is
When you create a Foundry (or Azure Language) resource you get two **keys** and an **endpoint**. A key works like a password: anyone who has it can call the service and run up charges on your subscription, from anywhere unless you add network restrictions.
## Microsoft's guidance
- Never put a key directly in code or post it publicly.
- For development, the quickstarts read it from environment variables (for example `LANGUAGE_KEY` and `LANGUAGE_ENDPOINT`, or a `.env` file loaded with `python-dotenv`); keep that file out of source control.
- For production, store keys in **Azure Key Vault**, rotate them regularly, and restrict access.
- Better still, use **Microsoft Entra ID** authentication (for example with managed identities), so there is no key to protect.
W: Keep the key out of the repository: loading it from the environment or Key Vault keeps it secret, and Entra ID removes the key altogether, which is Microsoft's recommended approach.
X: B=Key as a constant: keys are full credentials, not read-only, and hard-coding them is exactly what the guidance forbids.
C=Commit .env: keys are not tied to the developer's IP by default; a published key can be used by anyone until it is regenerated.
D=Base64-encode the key: base64 is reversible encoding, not encryption, and the service expects the plain key value, so this protects nothing.
T: Treat resource keys as passwords: keep them out of code and repos, use environment variables or Key Vault, and prefer Microsoft Entra ID.
