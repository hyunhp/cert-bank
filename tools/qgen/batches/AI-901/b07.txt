@ AI-901 D2 T2.2 applied use-case
S: A clinic's Python script uses the Azure Language client library (TextAnalyticsClient). Before feedback text is copied to an analytics team, the script must save a copy in which patient names, phone numbers and email addresses are masked. Which call and result value should the script use?
A: Call recognize_pii_entities, then save the redacted_text value of each result
B: Call detect_language, then save the primary_language value of each result
C: Call recognize_entities, then save the text of each entity labeled Person
D: Call extract_key_phrases, then save the key_phrases list of each result
K: A
G: ## PII detection in Azure Language
PII (personally identifiable information) detection is an Azure Language **core** feature. It finds personal details in text, such as names, phone numbers, email addresses and street addresses, and can redact them. It returns two things for each document:
- the **redacted text**: a copy of the input with each detected value masked
- the list of **entities** it found, each with its text, category (for example `Person` or `PhoneNumber`) and confidence score
## Calling it from Python
The Azure Language Python library is `azure-ai-textanalytics`. You create a `TextAnalyticsClient` with your Foundry resource endpoint and key, then pass a **list** of strings; `[0]` picks the result for the first one:
```
result = client.recognize_pii_entities([text])[0]
print(result.redacted_text)
for entity in result.entities:
    print(entity.text, entity.category, entity.confidence_score)
```
## Example
For "Maria Garcia called from 020 7946 0958 ..." the service finds `Maria Garcia` (Person) and `020 7946 0958` (Phone number), and `redacted_text` holds the same sentence with those values masked.
W: recognize_pii_entities and redacted_text: PII detection is the feature built for this job, and `redacted_text` is the ready-made masked copy of each document, so the script can save it directly.
X: B=detect_language and primary_language: language detection only names the language of the text (for example Spanish, `es`); it does not find or mask any personal data.
C=recognize_entities and Person entities: general entity recognition is not a redaction feature, and saving only the names it found would lose the feedback itself while phone numbers and emails are never handled.
D=extract_key_phrases: key phrases are the main topics of the text (such as "appointment delay"), not personal data, and the list is not a masked copy of the feedback.
T: For a masked copy of text, call Azure Language PII detection (`recognize_pii_entities`) and keep its `redacted_text`.

@ AI-901 D2 T2.2 applied tradeoff
S: A product team wants a quick prototype that reads each customer review, sorts it into one of their own five categories (such as "billing" or "delivery"), and writes a one-line English summary even when the review is in German. They have no labeled training data. What should they use?
A: A general-purpose model deployed in the Foundry project, called through the Responses API with a prompt that lists the categories
B: Azure Language custom text classification, trained on a labeled set of reviews for each of the five categories they defined
C: Azure Language key phrase extraction, then a lookup table that maps each returned phrase to one of the five categories
D: Azure Language language detection, then route each German review to a separate project that holds a translated copy
K: A
G: ## When a general-purpose model is the better tool
A general-purpose language model can follow instructions to classify, summarize, translate and extract information **without any configuration or training**. Because everything is driven by the prompt, you can combine tasks freely in one request: "Assign one of these categories: billing, delivery, ... Then summarize the review in one English sentence."
In code you deploy a model in your Foundry project and call it with the OpenAI library, for example `client.responses.create(model=deployment_name, input=prompt)`.
## When Azure Language is the better tool
Azure Language features return fixed, structured output for a single task. Its custom features need you to **label training data** and train a model first; custom text classification is also listed by Microsoft as a **legacy** capability (supported for existing use, while new investment goes to core features).
## Trade-off
- Prompted model: fastest to prototype, flexible, but results can vary slightly between calls.
- Azure Language: predictable, structured results, but each feature does one job and custom ones need training.
W: Prompted general-purpose model: one prompt can classify into the team's own categories, translate and summarize in a single call with no training data, which is exactly what a quick prototype needs.
X: B=Custom text classification: this feature can classify into custom classes, but only after the team labels and trains on example reviews, which they don't have; it also doesn't write summaries.
C=Key phrases plus a lookup table: key phrases are words from the review, not categories, and a hand-built mapping would be brittle; it also produces no English summary of German text.
D=Language detection and routing: detection only names the language; it doesn't classify, translate or summarize anything, so the core tasks are still not done.
T: Use a prompted general-purpose model for flexible, combined text tasks without training data; use Azure Language when you need fixed, structured, repeatable output.
V: Microsoft Foundry, Foundry Models, Responses API

@ AI-901 D2 T2.2 applied troubleshooting
S: A support portal routes tickets by the language that Azure Language detects. The team now wants a ticket sent to a person for checking whenever the service is unsure which language it is written in. The code runs result = client.detect_language([text])[0]. Which value should the check use?
A: result.primary_language.confidence_score, compared with a threshold such as 0.8
B: result.primary_language.iso6391_name, compared with the codes of existing teams
C: result.redacted_text, checked for masked characters that hide the ticket's language
D: result.key_phrases, counted to see whether the ticket has enough phrases to analyze
K: A
G: ## What language detection returns
Language detection is an Azure Language **core** feature. For each document it returns the **primary language** with three values:
- `name`: the language name, for example `Spanish`
- `iso6391_name`: the ISO 639-1 code, for example `es`
- `confidence_score`: a number between 0 and 1 that shows how sure the service is
## Example
```
result = client.detect_language(["¡Hola! Me llamo Josefina y vivo en Madrid, España."])[0]
print(result.primary_language.name, result.primary_language.iso6391_name, result.primary_language.confidence_score)
```
prints `Spanish es 1.0`. A short or mixed-language text gets a lower score.
## Using the score
Route on the code, and use the score as a safety check: below a threshold you choose, send the item to a person instead of trusting the detected language.
W: confidence_score: it measures how sure the service is about the detected language, so comparing it with a threshold is exactly the "unsure" test the team needs.
X: B=iso6391_name: the code is the detected answer itself; it is present even when the service is unsure, so it can't show how reliable the detection was.
C=redacted_text: this value belongs to PII detection results, not language detection, and masking personal data says nothing about the language.
D=key_phrases: key phrases come from key phrase extraction, a different call; the number of phrases is not a measure of detection certainty.
T: Language detection returns `name`, `iso6391_name` and a 0-1 `confidence_score`; route on the code and use the score to catch uncertain results.
V: Azure Language in Foundry Tools, language detection

@ AI-901 D2 T2.2 applied troubleshooting
S: A developer prompts a deployed GPT model to list the people, organizations and places in each news article. The parser that reads the reply keeps breaking because the wording and layout of the list change between runs. What should the developer do?
A: Call Azure Language prebuilt named entity recognition, which returns each entity with a fixed category field
B: Call Azure Language key phrase extraction, which returns the main concepts of each article as a plain list
C: Train an Azure Language custom NER model on labeled articles before it can find any people or places
D: Send the same prompt to the model twice and keep only the entities that appear in both of the replies
K: A
G: ## Why the model's reply keeps changing
A general-purpose model generates text probabilistically, so two calls with the same prompt can return slightly different wording or formatting. That is fine for a person reading the answer but fragile for code that parses it.
## Structured output from Azure Language
Azure Language features return **structured, deterministic** results. Prebuilt named entity recognition (NER) returns a list of entities, and each entity always has the same fields: its `text`, a `category` such as `Person`, `Organization` or `Location`, an optional subcategory and a confidence score.
## Example
"On May 2nd, 2017, John Smith visited New York to attend a conference hosted by Microsoft." returns `John Smith` (Person), `New York` (Location), `Microsoft` (Organization) and `May 2nd, 2017` (DateTime, Date).
In Python the call is `client.recognize_entities(documents)`.
W: Prebuilt NER: it already knows standard types such as Person, Organization and Location and returns them in a fixed structure, so the parser gets the same format on every run.
X: B=Key phrase extraction: key phrases are uncategorized topics; the output doesn't say which phrase is a person and which is a place.
C=Custom NER first: custom NER is for categories you invent and needs labeled training data; people, organizations and places are already covered by prebuilt NER.
D=Prompt twice and intersect: two variable replies are still variable, the layout problem remains, and it doubles the cost of every article.
T: When code must parse entities reliably, use Azure Language prebuilt NER, which returns a fixed structure, instead of a prompted model's free-form text.

@ AI-901 D2 T2.2 applied troubleshooting
S: A developer reuses the .env file from a chat app for a new language-detection script. The file has AZURE_OPENAI_ENDPOINT=https://contoso-ai.openai.azure.com/openai/v1/ and the code passes this value to TextAnalyticsClient. The call fails. What should the developer do?
A: Pass the resource's Azure AI services endpoint, such as https://contoso-ai.cognitiveservices.azure.com/, to TextAnalyticsClient
B: Create a separate Azure Language resource, because a Foundry resource cannot be used to call Azure Language features at all
C: Deploy a language detection model in the Foundry project first, and then pass that model's deployment name to the client
D: Replace AzureKeyCredential with the model deployment name, because Azure Language calls authenticate by using deployments
K: A
G: ## One Foundry resource, two kinds of endpoint
A Foundry resource gives access to deployed models **and** to Foundry Tools such as Azure Language and Azure Speech. Different client libraries expect different endpoints of that resource:
- The **OpenAI library** (Responses API on a deployed model) uses an endpoint like `https://<resource>.openai.azure.com/openai/v1/` plus a **model deployment name**.
- The **Azure Language client library** (`TextAnalyticsClient`) uses the resource endpoint like `https://<resource>.cognitiveservices.azure.com/` plus the key (`AzureKeyCredential`). Azure Language features are prebuilt, so there is **no deployment name**.
## Keep the names straight
Store both values in `.env` under clear names, for example `AZURE_OPENAI_ENDPOINT` and `AZURE_LANGUAGE_ENDPOINT`, and make sure each name in code matches the file exactly.
W: Use the cognitiveservices endpoint: `TextAnalyticsClient` talks to Azure Language through the resource endpoint, not the OpenAI `/openai/v1/` path, so switching the value fixes the call while the same key keeps working.
X: B=Separate Language resource: a Foundry resource already includes access to Azure Language, so no extra resource is needed; the problem is only the endpoint string.
C=Deploy a detection model: language detection is a prebuilt Azure Language feature with nothing to deploy, and `TextAnalyticsClient` does not take a deployment name.
D=Deployment name as credential: Azure Language authenticates with a key (or Microsoft Entra ID); a deployment name is not a credential and isn't used by this library.
T: The OpenAI library uses the `openai.azure.com/openai/v1/` endpoint and a deployment name; `TextAnalyticsClient` uses the `cognitiveservices.azure.com` endpoint and a key.
V: Microsoft Foundry, Azure Language in Foundry Tools

An agent's model can understand language, but on its own it gives generated, variable answers, and whatever is in its input has already been read. When a rule says data must be masked **before** the model sees it, and with repeatable results, the masking has to happen in a deterministic step first.

With a tool, the agent decides when to call it after it has read the input, so it doesn't by itself guarantee masking before the model reads the ticket.
W: PII detection before the agent: redacting each ticket in the app with Azure Language gives the same structured result every time, and the model only ever receives the masked text, which is exactly what compliance asks for.
X: B=System instruction: the model has already read the personal data, and an instruction only shapes generated output; it doesn't give deterministic masking.
C=Lower temperature: it makes output less random, but the model still reads the raw ticket and is not a detection and redaction service.
D=File search with a list: a reference document can't scan new tickets or mask anything; it only lets the agent look information up.

D=Low temperature on a text model: temperature only controls randomness; a model that doesn't support audio input can't be made to accept it.
E=Per-user voice training: the model is pretrained and works for any speaker; custom training of this kind is not required to respond.

Each model supports specific input and output **modalities**. A text model such as `gpt-4.1-mini` accepts text (and images) but can't process audio. ## Two ways to answer spoken prompts

SSML is an XML format that gives fine control over text to speech output. Every document has a `speak` element. Inside it:
