@ AI-901 D1 T1.1 expert troubleshooting
S: A bank audits its small-business loan model before renewing it. Overall accuracy is 92 percent, but applicants over 60 are wrongly declined three times as often as younger applicants with similar finances. Every declined applicant already receives the three main reasons for the decision, and applicant data is minimized, encrypted and deleted on schedule. The audit also finds that a data scientist pushed the current model version to production without any sign-off, and nobody can say who approved the two earlier versions or who handles appeals. Which TWO responsible AI principles does the audit show are not being met? (Select TWO)
A: Fairness, because applicants with similar finances face very different error rates depending on the age group they belong to
B: Accountability, because nobody owns model releases or appeals, and new versions reach production without any approval
C: Transparency, because declined applicants cannot find out which factors led the model to decline their loan applications
D: Privacy and security, because applicant data is processed by a model whose handling of personal data has never been reviewed
E: Inclusiveness, because the bank never tested its online application form with screen readers and other assistive technologies
K: A,B
G: ## Read the evidence, not the topic
Every principle can sound relevant to a loan model. An expert answer uses only what the audit actually shows:
- **Fairness**: similar people should get similar outcomes. A false-decline rate three times higher for one age group with similar finances is a fairness failure (high overall accuracy hides it).
- **Accountability**: people must be answerable for the system, and AI must not be the final authority on decisions that affect lives. Releases without sign-off, no record of approvers and no owner for appeals are accountability failures.
## Details that rule principles out
- Declined applicants already get their main reasons, so **transparency** (interpretability) is addressed.
- Data is minimized, encrypted and deleted on schedule, so the audit gives no evidence of a **privacy** gap.
- Nothing in the audit concerns accessibility, so **inclusiveness** is not shown to fail.
W: A=Fairness: a three-times-higher false-decline rate for over-60 applicants with similar finances is unequal treatment of similar people.
B=Accountability: unapproved releases, unknown approvers and no owner for appeals mean no person is answerable for the model's decisions.
X: C=Transparency: the stem states that every declined applicant already receives the main reasons, so this principle is being addressed.
D=Privacy and security: minimized, encrypted data deleted on schedule is evidence of good practice; the audit found no privacy gap.
E=Inclusiveness: assistive-technology testing is never mentioned in the audit, so there is no evidence either way.
T: Name a principle as failing only when the evidence shows it: unequal error rates mean fairness, missing ownership and approvals mean accountability.

@ AI-901 D1 T1.1 expert troubleshooting
S: A procurement team's Python app sends each inbound supplier email to a chat model deployment in Microsoft Foundry and lets the model call a create_order function. In a red-team test, an email contains hidden white text telling the model to order 500 units from an unknown supplier, and the model emits the function call. The deployment uses the default guardrail, and the team notes that jailbreak attempts typed directly by users are already being blocked. The app pastes the email body straight into the user message. The team wants a control in the safety system, not only a prompt change. What should it do?
A: Enable document attack detection in a custom guardrail for the deployment, and mark each email in the prompt as a document that the shield should scan
B: Keep the default guardrail, because its user prompt attack detection already scans emails pasted into user messages for hidden instructions
C: Raise the Violence and Hate blocking levels to High in a custom guardrail, so that any email containing manipulative content is blocked
D: Move the email body into the system message, because the safety system treats system message content as trusted and ignores instructions there
K: A
G: ## Two kinds of prompt attack
Prompt Shields in Foundry guardrails detect two attack types:
- **User prompt attacks** (jailbreaks): a user tries to bypass the system instructions. Detection is **on by default** in DefaultV2.
- **Document attacks** (indirect attacks): "Hidden instructions embedded in document content (documents, emails, web pages) that try to hijack the model session." Detection is **off by default and must be enabled** in the guardrail for the deployment.
## The hidden detail
Blocking typed jailbreaks proves only that user prompt attack detection works. Emails are third-party content; to have them scanned as documents, the app should identify them as documents in the prompt (Learn shows a `<documents> ... </documents>` delimiter for Chat Completions) and the guardrail must have document attack detection enabled.
## Defense in depth
Also validate tool calls in the app (for example, require approval for orders from unknown suppliers).
W: Document attack detection on, emails marked as documents: this is the safety-system control for instructions hidden in third-party content, and it is off by default, which explains why the attack got through.
X: B=Rely on the default: the default only covers user prompt attacks; document attack detection must be enabled separately for hidden instructions in emails.
C=Higher harm blocking levels: Violence and Hate filters look for harmful content, not for instructions that hijack the model; an ordering instruction is neither violent nor hateful.
D=Email in the system message: giving untrusted text system-level authority makes injection more dangerous, and it is not a safety-system control.
T: Instructions hidden in emails or documents are document (indirect) attacks; enable document attack detection, which is off by default, and mark that content as documents.

@ AI-901 D1 T1.2 expert troubleshooting
S: A help desk app calls a chat model deployment that has 30,000 tokens per minute (TPM) assigned. Each request carries about 1,000 input tokens, sets max_tokens to 4,000, and actually receives replies of about 150 tokens. The app needs 20 requests a minute, which is only about 23,000 real tokens, yet it starts receiving HTTP 429 responses after about six requests in each minute. The team cannot get more quota this month. Which change fixes the problem?
A: Lower max_tokens to about 300, because the rate limiter counts each request's input plus its max_tokens setting before the reply exists
B: Wait for billing to catch up, because 429 responses occur only when the monthly invoice shows more tokens than the TPM assignment
C: Send all 20 requests in the first second of each minute, because the limiter resets its counter at the start of every minute
D: Raise max_tokens to 8,000, so that each request reserves enough capacity and the service stops returning 429 responses
K: A
G: ## How the TPM limit is enforced
Learn: "TPM rate limits are based on the maximum number of tokens that are estimated to be processed by a request at the time the request is received. It isn't the same as the token count used for billing." The estimate includes the prompt text and **the `max_tokens` setting** (and `best_of`). The estimates are added to a running count that resets each minute; when the TPM limit is reached, further requests get **429** until the counter resets.
## Worked numbers
- Estimated per request now: 1,000 + 4,000 = 5,000 tokens. 30,000 / 5,000 = **6 requests per minute**, matching the symptom.
- With `max_tokens` = 300: 1,000 + 300 = 1,300. 20 x 1,300 = **26,000** < 30,000, so 20 requests fit.
Learn's guidance: "Set `max_tokens` to the minimum value that serves your scenario ... if you expect responses of about 200 tokens, don't set `max_tokens` to 4,000."
## RPM too
Requests should also be spread evenly; the service checks request rate over short periods such as 1 or 10 seconds.
W: Lower max_tokens: the limiter reserves input plus max_tokens per request, so cutting max_tokens from 4,000 to about 300 drops the estimate to 1,300 tokens and lets 20 requests fit in 30,000 TPM.
X: B=Billing lag: 429s come from the per-minute rate limiter, which uses an estimate at request time, not from the monthly invoice.
C=Burst at the start of each minute: bursts make things worse, because request rates are evaluated over short intervals and uneven traffic triggers 429s.
D=Raise max_tokens: a larger max_tokens increases each request's estimate, so even fewer requests fit per minute.
T: The TPM limiter counts estimated tokens (input plus max_tokens) at request time, so an oversized max_tokens causes 429s long before real usage reaches the limit.

X: C=Global Standard: it fits the traffic pattern, but processing may happen in any region, which breaks the EU-only clause.
D=Global Batch: same discount, but the global scope breaks the EU-only clause.
E=Data Zone Provisioned: it meets residency, but reserved PTUs are paid for continuously, a poor fit for traffic that is often near zero.

Which request change fits ALL of these facts?
A: Remove temperature, replace max_tokens with max_completion_tokens of about 3,000, and set reasoning_effort to low
B: Remove temperature, replace max_tokens with max_completion_tokens of 800, and set reasoning_effort to low

Learn's reasoning models page lists parameters these models (other than the newest exception) do **not** support: `temperature`, `top_p`, `presence_penalty`, `frequency_penalty`, `logprobs`, `top_logprobs`, `logit_bias` and **`max_tokens`**. Instead:

- A cap of 800 would cut the response off during reasoning, giving empty or truncated answers.
- A cap of about 3,000 leaves headroom; low effort reduces reasoning tokens and latency.
## Hidden detail
The answer must satisfy the error, the completeness requirement and the speed requirement at the same time.
W: Remove temperature, max_completion_tokens about 3,000, effort low: it drops the unsupported parameters, sets a budget that covers reasoning plus the answer, and lowers effort for faster replies.
X: B=Cap of 800: the cap counts reasoning tokens too, so about 2,100 tokens of work cannot fit and answers would be cut off.
C=Keep temperature and max_tokens, effort high: both parameters are unsupported, and high effort makes the model think longer, so answers get slower.
D=Keep max_tokens and ask to skip reasoning: max_tokens is still unsupported, and a prompt request does not replace the reasoning_effort control.
T: For reasoning models drop temperature and max_tokens, size max_completion_tokens for reasoning plus answer, and tune reasoning_effort for latency.

@ AI-901 D1 T1.3 expert comparison
S: A bridge-maintenance company sends drones to photograph steel girders. Engineers need two numbers from each photo: the percentage of the girder surface covered by rust, which must follow the irregular edge of each rust patch, and the number of bolts still in place, with the location of each one so that a robot can torque it later. A third team already reads the serial plates printed on each girder with its own OCR system, and no whole-photo labels are needed. Which combination of computer vision techniques fits BEST?
A: Semantic segmentation for the rust, which labels each pixel so the covered area can be measured, plus object detection for the bolts
B: Object detection for the rust, which draws a rectangle around each patch to measure its area, plus image classification for the bolts
C: Image classification for the rust, which labels each photo as rusty or clean, plus semantic segmentation to count and place the bolts
D: Semantic segmentation for the rust, plus optical character recognition, which reads each bolt's markings and returns the bolt's position
K: A
G: ## Match the output to the measurement
- **Image classification**: one label for the whole image. Good for "is there rust?", useless for "how much?" or "how many?".
- **Object detection**: a class and a **bounding box** per object, so you can count objects and locate them. Rectangles do not follow irregular shapes, so areas computed from them are overestimates.
- **Semantic segmentation**: a class for **every pixel**, so the exact area of an irregular region can be measured. Pixels of one class are not separated into countable items.
- **OCR**: reads text and its position.
## Worked example
A girder photo has 2,000,000 girder pixels; segmentation labels 180,000 of them as rust: 9% coverage. Detection finds 46 bolts, each with a box for the robot.
## Hidden detail
The serial plates are already handled by another team, so OCR adds nothing here.
W: Segmentation plus detection: pixel-level labels measure the irregular rust area, and bounding boxes count each bolt and give its location.
X: B=Detection for rust, classification for bolts: rectangles overstate irregular rust areas, and a whole-image label cannot count or locate bolts.
C=Classification for rust, segmentation for bolts: a rusty/clean label gives no percentage, and class-per-pixel output does not separate individual bolts into a count with positions.
D=Segmentation plus OCR: bolts carry no text to read, and the only text in the photos is already handled by another team.
T: Use semantic segmentation to measure irregular areas and object detection to count and locate items; choose classification only for whole-image labels.

@ AI-901 D1 T1.3 expert use-case

Several product names are misrecognized, and the team has a few hours of call audio with human-made reference transcripts. The workload is file-based, not live. Which approach fits BEST?
A: Batch transcription that uses a custom speech model trained on the reference transcripts, with no hosted custom endpoint needed
B: Fast transcription with a phrase list of the product names, because it returns each file's transcript synchronously and faster than real time
C: Batch transcription with a phrase list of the product names attached to each nightly job, which avoids having to train any model
D: Real-time transcription with the Speech SDK and a phrase list, streaming every stored file through continuous recognition each night
K: A
G: ## Three processing options, different outputs
- **Real-time** transcription: live audio with intermediate results.
- **Fast transcription**: synchronous file transcription. Learn: "Unlike the batch transcription API, fast transcription API only produces transcriptions in the display (not lexical) form."
- **Batch transcription**: asynchronous processing of large volumes of stored audio; its results include the lexical form as well as the display form.
## Two ways to improve accuracy
- **Phrase list**: runtime boost, no training. Supported with real-time and fast transcription, LLM Speech and Voice Live; "The Batch transcription API doesn't support phrase lists."

## Putting the constraints together
Lexical output rules out fast transcription; nightly file volume points to batch; batch rules out phrase lists, so accuracy must come from a custom model, for which the team has data.
W: Batch plus custom speech: batch handles the nightly file volume and returns the lexical form, and a custom model trained on the reference transcripts fixes product names without needing a hosted endpoint.
X: B=Fast transcription with phrase list: phrase lists work there, but fast transcription returns only the display form, not the lexical form compliance needs.
C=Batch with phrase list: batch transcription does not support phrase lists, so the names would still be misrecognized.
D=Real-time over stored files: streaming 5,000 recordings through real-time recognition is the wrong tool for file volume, and it is the batch API that is designed for this workload.
T: For nightly file volume with lexical output use batch transcription, and improve its vocabulary with a custom speech model because batch does not accept phrase lists.
