@ AI-901 D2 T2.1 applied definition
S: A developer already calls a deployed GPT model from a Python script with a single request and prompt. A colleague suggests turning it into an agent in Foundry Agent Service instead. What does an agent add that the plain model call does not have?
A: A saved, versioned definition that combines a model, instructions and tools, so every request gets the same behavior and the model can call tools
B: A larger context window than the deployed model offers, because the agent splits long prompts across several deployments of the same model
C: A fine-tuned copy of the deployed model that is trained automatically on the instructions and on the files the developer attaches to it
D: A cheaper billing model, because agents are charged a flat monthly rate per agent instead of for the input and output tokens they use
K: A
G: ## Model call versus agent
A plain model call (a chat completion or a single Responses API call) sends some input to a deployed model and gets text back. Every call has to carry its own system prompt, and the model can only produce text: it cannot look anything up or act.
An **agent** in Foundry Agent Service is a persisted definition that combines:
- a **model** from the Foundry model catalog,
- **instructions** that set its role, tone and rules,
- **tools** it may call, such as file search, code interpreter, web search, OpenAPI or function tools.
Foundry stores agents as **named, versioned assets**. Your app only names the agent; the same instructions and tools are applied to every request, and the model can decide to call a tool, read the result and then answer.
## Example
A support bot defined as an agent always follows the support instructions and can search the product manuals with file search, instead of each app re-sending a long system prompt and having no access to the manuals.
W: Persisted model + instructions + tools: Learn describes an agent as a persisted definition that combines a model, instructions and tools and is stored as a named, versioned asset, which gives consistent behavior and lets the model use tools.
X: B=Larger context window: an agent uses the context window of the model it is configured with; it does not split prompts across deployments or extend the model's limits.
C=Automatic fine-tuning: creating an agent does not train or fine-tune anything. Instructions are sent to the model at run time and attached files are searched with tools, not used as training data.
D=Flat monthly price: prompt agents are billed per call for model inference plus any tool usage, not with a flat per-agent rate.
T: An agent is a saved, versioned combination of model, instructions and tools; a plain model call is a single request that has none of these.
V: Microsoft Foundry, Foundry Agent Service

@ AI-901 D2 T2.1 applied comparison
S: A small HR team wants an assistant that answers questions about leave policies. They want to set it up in the Foundry portal, test it there, and avoid writing or hosting any agent code or containers. Which kind of agent in Foundry Agent Service fits best?
A: A prompt agent, defined only by a model, instructions and tools, which Foundry runs for them on a fully managed runtime
B: A hosted agent, packaged as a container image of their own code, which Foundry runs with a managed endpoint and scaling
C: An ephemeral agent, defined inside their own application code on every Responses API call, with nothing saved in Foundry
D: A voice-based prompt agent, connected through Voice Live, which Foundry runs over a real-time WebSocket audio session
K: A
G: ## The ways to build an agent in Foundry
Foundry Agent Service offers several paths, from least to most code:
- **Prompt agent**: defined entirely by configuration (model, instructions, tools). You can author it in the Foundry portal or with the SDK/REST API, and Foundry runs it. No application code, containers or compute to manage. Learn calls it the fastest path and suggests it for a first agent.
- **Voice-based prompt agent**: a prompt agent for real-time spoken conversations through Voice Live (preview).
- **Hosted agent**: your own code (Agent Framework, LangGraph and others) shipped as a container or a .zip; Foundry hosts it.
- **Ephemeral agent**: your app calls the Responses API directly and passes the instructions, model and tools in each call; nothing is saved in Foundry.
## Picking one
"No code, set it up and test it in the portal" points to a prompt agent: create it in the portal, chat with it in the agents playground, and call it from an app later if needed.
W: Prompt agent: it is defined only by configuration in the portal or SDK, and Foundry runs it with no code, containers or compute for the team to maintain, exactly what the HR team asked for.
X: B=Hosted agent: hosted agents exist for teams that bring their own code and framework; the team would have to write, package and maintain that code.
C=Ephemeral agent: the definition lives in application code that the team would write and run; there is no saved agent to set up and test in the portal.
D=Voice-based prompt agent: it is built for spoken, real-time conversations and is in preview; the HR team asked for a text assistant, not a voice experience.
T: For a no-code agent that Foundry runs for you, create a prompt agent (model + instructions + tools) in the Foundry portal.
V: Foundry Agent Service, prompt agents

@ AI-901 D2 T2.1 applied use-case
S: A travel agency builds an agent in the Foundry portal. It must always answer in a friendly tone, only discuss the agency's tours, and politely refuse other topics. Where should the developer put these rules so they apply to every conversation without users repeating them?
A: In the agent's instructions, which Foundry stores with the agent and applies to every response the agent generates
B: In the first user message of each conversation, which the agent keeps in its history and treats as its rules
C: In a file attached to the file search tool, which the agent reads as its behavior rules at the start of every response
D: In the model deployment's content filter settings, which add the tone and topic rules to every request automatically
K: A
G: ## What instructions do
Every prompt agent has **instructions**: the text that tells the model who it is, how to behave and what it must not do. They play the role of a system message, but they are saved as part of the agent definition, so:
- every conversation and every response uses them automatically,
- users never see or need to type them,
- changing them creates a new version of the agent that you can test and roll back.
## Writing good instructions
- State the role and audience: "You are a booking assistant for Contoso Tours."
- Set limits: "Only answer questions about Contoso tours. Politely decline other topics."
- Describe the tools and when to use them: "Use file search for tour details."
## Example
`instructions="You are a friendly assistant for Contoso Tours. Only discuss our tours and politely refuse other topics."`
W: Agent instructions: instructions are part of the saved agent definition and steer the model on every response, so the tone and topic rules apply to all conversations without anyone repeating them.
X: B=First user message: user messages are input, not configuration. Each new conversation would need the rules again, and a later user message could easily override them.
C=File search document: file search retrieves passages that look relevant to a question to ground answers in facts; it is not a reliable place for behavior rules, which belong in the instructions.
D=Content filter settings: content filters block harmful categories such as hate or violence; they cannot set a friendly tone or restrict the agent to a company's own topics.
T: Put an agent's role, tone and limits in its instructions; they are stored with the agent and applied to every response.
V: Foundry Agent Service

@ AI-901 D2 T2.1 advanced troubleshooting
S: A developer adds the code interpreter tool to a prompt agent. When she tests it, Foundry returns a "tool not supported" error, although the documentation says the model she picked supports code interpreter. What should she check first?
A: Whether the project's region also supports code interpreter, because a tool runs only when both the model and the region support it
B: Whether the agent's instructions mention code interpreter by name, because a tool is disabled until the instructions refer to it
C: Whether she has uploaded a CSV file to the agent, because code interpreter can be enabled only after at least one file is attached
D: Whether the model deployment has a high enough temperature, because code interpreter needs creative sampling to write its code
K: A
G: ## Tool availability depends on two things
A tool in Foundry Agent Service can run only when **both** of these support it:
- the **model** the agent uses, and
- the **region** of the Foundry project (and of the model deployment).
Learn's troubleshooting guidance says: if either the region table or the model table shows "No", the tool can't run, even if the other shows "Yes". For example, code interpreter doesn't run in regions that show no for it, whatever model you choose.
## How to fix it
- Check the tool support by region and model tables on Learn.
- Confirm the model is really deployed in the project and region you are using.
- Use a different region or a model deployment that supports the tool.
W: Region support: the error appears when the region (or the actual deployment) does not support the tool, even though the model does; both must support it.
X: B=Instructions naming the tool: describing tools in the instructions helps the model choose when to call them, but it does not enable or disable a tool, and it would not cause an unsupported error.
C=Uploaded CSV file: code interpreter can run Python and do calculations without any uploaded file; files are optional input, not a prerequisite for enabling the tool.
D=Temperature setting: temperature changes how varied the model's text is; it has nothing to do with whether a tool is supported in a region or by a model.
T: A Foundry agent tool runs only when both the model and the project's region support it; check both tables when you get a "tool not supported" error.
V: Foundry Agent Service, code interpreter

@ AI-901 D2 T2.1 applied use-case
S: A bicycle maker wants its support agent to answer questions using about 200 PDF repair manuals that are not on the public internet. Answers should be based on the manuals rather than on the model's general knowledge. Which tool should the developer add to the agent?
A: File search, after uploading the manuals so they are indexed in a vector store that the agent can query
B: Code interpreter, after uploading the manuals so the agent can write Python that opens and reads each PDF
C: Web search, so the agent finds repair pages on the public web that match the manuals' content and models
D: Function calling, so the agent sends each question to the developer's app, which returns the matching manual
K: A
G: ## Grounding an agent in your own documents
A model only knows what it learned in training. To make an agent answer from **your** documents, you give it a retrieval tool. In Foundry Agent Service the simplest one is **file search**:
1. Upload the files and add them to a **vector store** (the files are split into chunks and indexed by meaning).
2. Wait for ingestion to finish.
3. Attach file search with that vector store to the agent.
4. When a user asks something, the agent searches the store, gets the most relevant passages and answers from them.
This pattern is retrieval-augmented generation (RAG). File search is GA; it has charges on top of the model's token fees. With the standard agent setup the files stay in your own storage and your Azure AI Search resource ingests them.
## Tip
In the instructions, tell the agent to use file search for product questions and to say when the manuals don't contain the answer.
W: File search: it indexes the uploaded manuals in a vector store and lets the agent retrieve the relevant passages for each question, so answers come from the company's private documents.
X: B=Code interpreter: it runs Python in a sandbox for data analysis and charts. It is not a search index; reading 200 PDFs with code on every question would be slow and would not find the relevant passages by meaning.
C=Web search: the manuals are not public, so a web search cannot return them, and answers would come from other websites instead of the company's own content.
D=Function calling: the developer would have to build and run their own search over the manuals and return the results; file search already provides that retrieval without custom code.
T: To ground an agent in private documents, upload them to a vector store and attach the file search tool.
V: Foundry Agent Service, file search

@ AI-901 D2 T2.1 applied use-case
S: A sales manager uploads a CSV of monthly revenue to an agent and asks it to calculate the growth rate per region and draw a bar chart. The model on its own often gets the arithmetic wrong. Which tool lets the agent do this reliably?
A: Code interpreter, which lets the model write and run Python in a sandbox to compute the numbers and create the chart file
B: File search, which indexes the CSV in a vector store so the model can quote the rows that match each region's name
C: Web search, which looks up published regional revenue figures and returns them with inline citations to the sources
D: OpenAPI tool, which sends the CSV to a charting web service that is described by an OpenAPI 3.0 specification file
K: A
G: ## Why models need a calculator
Large language models predict text; they are not reliable at exact arithmetic over many rows. **Code interpreter** solves this by letting the agent's model write Python, run it in a **sandboxed environment**, look at the result and try again if needed.
## What code interpreter can do
- Read uploaded files such as CSV or Excel.
- Calculate exact results (sums, growth rates, statistics).
- Produce files such as PNG charts that the app can download.
## Things to know
- It has charges beyond the model's token fees.
- Each conversation that uses it gets its own session; a session is active for up to one hour, with a 30-minute idle timeout.
- The sandbox is Microsoft-managed and isolated, so the generated code cannot touch your systems.
W: Code interpreter: the model writes Python that computes the growth rates exactly and draws the chart, and the code runs in an isolated sandbox, so the arithmetic is done by code instead of guessed by the model.
X: B=File search: retrieval returns passages of text that match a question; it does not perform calculations across all rows or produce charts.
C=Web search: the data is the manager's own CSV, so public web results would be irrelevant, and searching does not compute anything.
D=OpenAPI tool: it would need an external charting service the company doesn't have, and it still would not compute the growth rates; code interpreter does both with no extra service.
T: Use code interpreter when an agent must calculate, analyze data files or generate charts; it runs model-written Python in a sandbox.
V: Foundry Agent Service, code interpreter

@ AI-901 D2 T2.1 applied definition
S: A retailer wants its agent to report a customer's order status, which only the retailer's own app can read from an internal database. The developer adds a function tool named get_order_status. When a customer asks about an order, who runs the function?
A: The developer's application runs the function when the model requests it, then sends the output back so the agent can finish its answer
B: Foundry Agent Service runs the function in a managed sandbox, using Python code that the developer pastes into the agent's portal page
C: The model runs the function itself inside the deployment, because a function tool compiles the code into the model's own weights
D: Foundry calls the function as a web endpoint, using the URL and operationId that the developer lists in an OpenAPI specification
K: A
G: ## How function calling works
A **function tool** describes a function to the model: its name, a description and its parameters (a JSON schema). The model never runs code. Instead:
1. The user asks "Where is order 1042?"
2. The model decides the function is needed and returns a **function call** item, for example `get_order_status` with `{"order_id": "1042"}`.
3. **Your application** runs the real function (here, a database lookup).
4. Your app sends the result back as a `function_call_output` item in the same conversation.
5. The agent uses the result to write the final answer.
This is client-side execution: the data and code stay in your app.
## Limits worth knowing
- Learn warns that runs expire 10 minutes after creation, so submit tool outputs in time.
- The Foundry portal can run agents that have function tools, but you add or change function definitions with the SDK or REST API, not in the portal.
W: Client-side execution: with function calling the model only asks for the call with arguments; the developer's app executes it against the internal database and returns the output for the agent to use.
X: B=Managed sandbox: that describes code interpreter, which runs model-written Python. Function tools are executed by your application, and the portal doesn't edit function definitions.
C=Model runs the code: a model only generates text, including the structured request for a call; it cannot execute code or reach the retailer's database.
D=Web endpoint from a spec: that is the OpenAPI tool, where Foundry calls an HTTP API described by a specification. A function tool is executed by the client application instead.
T: With a function tool, the model requests the call and your app executes it and returns the output; Foundry never runs your function.
V: Foundry Agent Service, function calling

@ AI-901 D2 T2.1 advanced comparison
S: A logistics company already exposes a shipment-tracking REST API with an OpenAPI 3.0 specification. It wants its agent to call this API on the server side, without the client app having to execute any calls itself. What should the developer use, and what does it need?
A: The OpenAPI tool, with the specification (each operation needs an operationId) and a project connection for the chosen authentication
B: A function tool, with the API's operations copied in as function names, so Foundry calls the HTTPS endpoint on the app's behalf
C: The file search tool, with the specification uploaded to a vector store, so the agent can look up and call the right operation
D: The code interpreter tool, with the API key placed in the agent's instructions, so model-written Python can call the endpoint
K: A
G: ## Two ways to let an agent call your systems
- **Function calling**: the model asks for a call and **your app** executes it. Good when the logic lives in the client.
- **OpenAPI tool**: you give the agent an **OpenAPI 3.0 or 3.1 specification**, and Foundry Agent Service calls the HTTP API **itself**. Good when an API already exists and the client should not run the calls.
## What the OpenAPI tool needs
- A specification in which each operation has an `operationId` (letters, `-` and `_`) and a clear description, so the model can choose the right operation.
- A **project connection**, even for anonymous APIs. Supported authentication: anonymous, API key, or the project's managed identity.
- Credentials stored in the connection, never in the specification, the prompt or source code.
## Example
An operation `getShipmentStatus` with a parameter `trackingNumber` lets the agent answer "Where is parcel 7781?" by calling the tracking API directly.
W: OpenAPI tool: it lets the agent call an existing HTTP API described by an OpenAPI 3.0/3.1 spec on the server side; each operation needs an operationId, and the tool uses a project connection for anonymous, key or managed identity authentication.
X: B=Function tool: Foundry never executes function tools; the client app would have to run every call, which the company wants to avoid.
C=File search: indexing the specification only lets the agent quote it; file search cannot make HTTP requests to the API.
D=Code interpreter with key in instructions: putting credentials in instructions is unsafe, and code interpreter runs in a sandbox for data analysis, not as a way to call company APIs.
T: To have an agent call an existing REST API itself, use the OpenAPI tool with a spec that has operationIds and a project connection for authentication.
V: Foundry Agent Service, OpenAPI tool

@ AI-901 D2 T2.1 advanced troubleshooting
S: A developer tests a prompt agent in the Foundry agents playground. It has a web search tool and a function tool, and it should always call the order-lookup function before answering. Sometimes it answers without calling any tool. Which two changes address this? (Select TWO)
A: Set tool_choice to required for the requests that must call a tool, so the model has to call at least one
B: State in the instructions that order questions must always use the order-lookup function before replying
C: Set tool_choice to none, so the model stops calling web search and is left with only the function tool
D: Lower max output tokens, so the model has too little room to answer directly and calls a tool instead
E: Remove the instructions entirely, so the model relies on the tool descriptions alone to choose a tool

Two levers decide how reliably an agent uses its tools:

Use traces to confirm whether the model produced a tool call and to inspect inputs and outputs. In the agents playground you can repeat the same question after each change and compare.

D=Lower max output tokens: this only truncates the answer; the model may still skip tools and simply return a cut-off reply.
E=Remove instructions: instructions are where the decision rules live; removing them makes tool use less predictable, not more.
T: Use clear instructions to guide tool use and tool_choice required when a tool call must happen.

@ AI-901 D2 T2.1 applied definition
S: A developer changes the instructions of a prompt agent named support-bot in the Foundry portal and saves. The previous instructions worked better, so she wants to go back. How do agents in Foundry Agent Service handle this?
A: Each saved change creates a new version of support-bot; agents are identified by name and version, so she can roll back to an earlier version
B: Each save overwrites support-bot in place, so she must retype the old instructions because Foundry keeps no history of earlier definitions

- Creating or changing the agent (for example with `project.agents.create_version(...)` in the SDK, or saving in the portal) produces a **new version**.
- Agents are identified by **name and version**; they no longer have a GUID "agent ID".

- Apps that refer to the agent by name get the current version, and publishing gives a stable endpoint.
## Why this matters
Versioning lets you try new instructions, model choices or tools in the agents playground, compare results, and go back if quality drops, without breaking apps that call the agent by name.

D=Session-only changes: saving persists the definition in the project as a version; no export is needed to keep it.
T: Foundry agents are named, versioned assets: each change makes a new version you can compare with or roll back to.

In Foundry Agent Service, three runtime pieces work together:
- **Agent**: reusable model, instructions and tools.
- **Conversation**: persisted input and output items, so later turns have server-side history.
- **Response**: one unit of execution that runs the agent against the input (and the conversation) and appends output items.

G: ## Classic agents versus current agents
The **classic** Foundry Agent Service (Agents API v1, Azure AI Projects 1.x) used:
- **Thread**: a conversation session that stored messages.
- **Message**: a user or agent entry in the thread.
- **Run**: invoking the agent on the thread; the app polled its status (`queued`, `in_progress`, `requires_action`, `completed`).

- **Agent**: named, versioned definition (model, instructions, tools).
- **Conversation**: persisted history items, the successor to the thread.
- **Response**: one call that takes the input, runs the agent against the conversation and returns the output items.
W: Conversation and response: conversations persist the history across turns like threads did, and a response combines adding the input and running the agent in a single call.

S: An agent has a function tool get_weather. The client sends a question, and the response contains a function_call item for get_weather instead of text. The developer's code only prints response.output_text, which is empty. What should the client do next?
A: Run get_weather with the requested arguments, then send a function_call_output item with the result in the same conversation

D: Call conversations.create to open a new conversation, because a function call ends the current one and it can't continue
K: A
G: ## The function calling loop in a client
With function tools, the conversation pauses until **your app** supplies the result:
1. Your app sends the user's input with `responses.create(...)`.
2. The model decides it needs `get_weather` and the response contains a **function call** item with the arguments (for example `{"city": "Seoul"}`), not final text.
3. Your app runs its own `get_weather` function.
4. Your app sends a follow-up request containing a `function_call_output` item with the result, in the **same conversation**.
5. The agent uses the result and returns the final answer in `output_text`.
## Common mistakes
- Only reading `output_text` and ignoring function call items.
- Asking the same question again, which just produces another function call.
- Waiting too long: Learn warns that runs expire 10 minutes after creation, so submit tool outputs promptly.
W: Return the function output: the model asked the client to run get_weather; after the app runs it and sends a function_call_output item in the same conversation, the agent can produce the final text answer.
X: B=Ask again and wait: Foundry never executes function tools, so repeating the question only produces another function call request.
C=Remove the tool: a function_call item is the normal, successful step of function calling, not a failure; removing the tool would lose the weather capability.
D=New conversation: the call does not end the conversation, and a new conversation would lose the pending function call and the context it belongs to.
T: When a response contains a function call, run the function in your app and send a function_call_output in the same conversation to get the final answer.

@ AI-901 D2 T2.1 advanced definition
S: A developer is deciding how an agent client should keep multi-turn context in Foundry Agent Service. Which two statements about conversations and responses are correct? (Select TWO)
A: A conversation persists the input and output items of earlier turns on the service side, so later responses can use that history
B: Without a conversation, a client can chain turns by referencing a previous stored response with previous_response_id

G: ## Three ways to carry context between turns
Foundry Agent Service builds multi-turn chats from agents, conversations and responses:
- **Conversation**: the service stores the items of each turn. Pass the same `conversation` ID to every `responses.create` call.
- **Previous response**: by default responses are stored server-side, so a new call can reference `previous_response_id` and continue from it, with no conversation object.
- **Client-managed history**: with `store=False` the service doesn't persist the response at all; the client resends earlier output items as input to the next request. Useful when you want full control over state, to minimize stored data, or for zero data retention.
## What is not true
The agent definition never stores chat history; it is shared configuration (model, instructions, tools). History lives in conversations or stored responses.
W: A=Conversation persists history: Learn describes a conversation as the component that supplies persisted input and output items to responses so later turns have server-side history.
B=previous_response_id: because responses are stored by default, a client can continue from an earlier response by its ID instead of using a conversation.
X: C=Responses added to the agent: agents hold only the reusable definition; chat history is never written into it or shared across users.
D=store false hides from traces: with `store=False` the service does not persist the response, so the client must carry the context forward itself.
E=One call per conversation: a conversation is meant to be reused across many turns; that reuse is what makes follow-up questions work.
T: Carry context with a conversation ID, with previous_response_id on stored responses, or yourself with store=False; the agent definition never holds chat history.
