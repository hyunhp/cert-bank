S: A developer is moving a feature to a reasoning model and reads about reasoning tokens. Which TWO statements about reasoning tokens are correct? (Select TWO)
A: Reasoning tokens appear in the message content that the model returns, so users can read the model's step-by-step internal thinking in each answer.
B: Reasoning tokens occupy space in the context window and count toward the output token limit set by max_completion_tokens.
C: Reasoning tokens are produced while the model is trained rather than at inference, so a deployed model adds no tokens to a request.
D: Reasoning tokens are stored on the server as the model's long-term memory and are reused by later requests from other users of the deployment.
E: Reasoning tokens are billed as output tokens, so a request can cost more even when the visible answer is short.
K: B,E
G: ## How reasoning models think
**Reasoning models** generate **reasoning tokens** in addition to the usual input and output tokens. The model uses them to work through the prompt: breaking the problem apart, weighing approaches, and abandoning paths that do not hold up.
## Facts to remember
- Reasoning tokens **never appear in the message content** returned to you. The response usage details report how many were used (for example `completion_tokens_details.reasoning_tokens`).
- They **occupy space in the context window**.
- They are **billed as output tokens**, so a request that thinks longer costs more even if the visible answer is short.
- `max_completion_tokens` (Chat Completions) or `max_output_tokens` (Responses API) caps **reasoning plus visible output** together. If the cap is too low, the response can come back incomplete before any visible text appears.
- `reasoning_effort` controls how much the model thinks; supported values vary by model.
## Example
A question uses 20 input tokens and returns a 150-token answer, but the usage shows 1,800 completion tokens: about 1,650 of them were reasoning tokens.
W: B=Context window and output limit: reasoning tokens take up context window space and are included in the max completion tokens cap along with the visible answer.
E=Billed as output: reasoning tokens are charged as output tokens, so a short visible answer can still produce a large output token count.
X: A=Visible thinking: reasoning tokens never appear in the message content; only a count (and, where supported, a summary) is available.
C=Produced during training: reasoning tokens are generated at inference time for each request, which is why they show up in usage and cost.
D=Long-term memory: reasoning tokens belong to a single request and are not stored as shared memory for other users of the deployment.
T: Reasoning tokens are invisible, use context window space, count toward the output cap and are billed as output.

A: A video analyzer fed the photo as a one-frame clip, so its frame sampling reads the label
B: prebuilt-imageSearch, because its one-paragraph description lists the numbers it can see

G: ## Image analyzer or document analyzer?
Content Understanding image analyzers are built to understand **visual** content: chart types, defects, products on a shelf, scene descriptions. Learn's image overview adds a note: image analyzers are **not optimized for scenarios where analysis is based primarily on extracted text**. If the main goal is to extract and analyze text from images, use a **document field extraction schema** instead.
Document analyzers accept image files as well as PDFs, run OCR, and support the extract method with confidence and grounding, which is what a serial number needs.
## Example
A photo of a label saying `SN 48-2219-X` analyzed with a document analyzer whose `SerialNumber` field uses extract returns the exact string plus its confidence and location.
W: Document analyzer for text: Learn recommends a document field extraction schema when the goal is text in an image, and document analyzers add OCR, the extract method and confidence scores.
X: A=Video analyzer with a one-frame clip: video analysis samples frames resized to 512 by 512 pixels, which loses small text, and it is not the tool Learn recommends for reading printed text.
B=prebuilt-imageSearch: it writes a general description for search; nothing guarantees that every printed number appears in it, and it returns no named serial number field.
D=Image analyzer with generate fields: a photo is not a reason to pick an image analyzer, because document analyzers accept image files too. Learn notes image analyzers are not optimized for text-based analysis, and generated values carry no confidence score to catch a misread digit.

@ AI-901 D2 T2.1 applied comparison
S: A developer is starting a new Python chat app that uses the OpenAI-compatible client from get_openai_client(). It calls a gpt-4.1 deployment now and might later switch to a Foundry direct model such as Microsoft Phi. The developer wants the chat API that Microsoft recommends for new projects. Which choice fits, and why?
A: The Responses API, but after the deployment is first saved as an agent, because responses.create sends prompts to agents rather than to models
B: The Responses API, because it's recommended for most new development, supports stateful multi-turn chats, and also works with Foundry direct models
C: The ChatCompletions API, because the Responses API lacks a system prompt setting, so the rules would have to be repeated in each user input
D: The ChatCompletions API, because Foundry direct models such as Phi accept chat.completions calls but reject calls made with responses.create
K: B
G: ## Two chat APIs on the same client
The OpenAI-compatible client (from the Foundry SDK's `get_openai_client()` or from the OpenAI SDK) supports two chat APIs:
- **Responses API** (`responses.create`): combines the capabilities of Chat Completions and the Assistants API. It supports stateful multi-turn conversations, takes an `instructions` parameter as the system prompt, and works with Azure OpenAI models and Foundry direct models (such as Microsoft Phi or DeepSeek). Learn calls it the recommended approach for most new development.
- **ChatCompletions API** (`chat.completions.create`): takes a `messages` list with system, user and assistant roles. It's well established and compatible across many models and platforms, so it's useful for existing code and cross-platform work, but the app must track conversation history itself.
## Example
`openai_client.responses.create(model="gpt-4.1", instructions="You are a helpful assistant.", input="What is Microsoft Foundry?")`
Switching to Phi later only changes the `model` value to the Phi deployment name.
W: Responses API: Microsoft recommends it for new projects; it handles multi-turn state, accepts instructions, and works with Foundry direct models as well as Azure OpenAI models.
X: A=Save as agent first: `responses.create` sends prompts straight to a model deployment named in `model`; an agent is optional.
C=No system prompt in Responses: the Responses API has an `instructions` parameter that acts as the system prompt for every call.
D=Direct models reject Responses: both APIs can call Foundry direct models through the project endpoint; that isn't a reason to choose the older API.
T: For new Foundry chat apps use the Responses API (recommended, stateful, works with Azure OpenAI and Foundry direct models); ChatCompletions remains for existing or cross-platform code.
V: Microsoft Foundry, Foundry SDK

@ AI-901 D1 T1.1 applied use-case
S: A government benefits agency uses an AI model that recommends whether to stop a household's housing support payments. Which design best reflects the accountability principle?
A: Retrain the model each week on the newest cases so that its recommendations reflect the latest patterns.
B: Let the model stop payments on its own, and publish its overall accuracy figures on the agency's public website.
C: Have a qualified caseworker make the final decision on each stoppage and record the reasons for the decision.
D: Encrypt the case data at rest and in transit so that household details are protected from unauthorized access.
K: C
G: ## Accountability
The people and organizations that design and deploy AI systems are accountable for how those systems operate. Microsoft's guidance says accountability norms should ensure that AI systems are **not the final authority** on decisions that affect people's lives, and that humans keep **meaningful control** over highly autonomous systems.
## Human oversight
For high-impact decisions, such as stopping a family's housing support, a common pattern is **human-in-the-loop**: the AI recommends, and a qualified person reviews and decides. Recording who decided and why creates a trail that an auditor, regulator or the affected person can follow.
## Governance
Accountability also means a framework of governance inside the organization: clear owners, review processes, documentation of decisions and a way to act when something goes wrong.
## Example
The model flags a household for stopping payments with a short explanation. A caseworker reads the file, overrides the recommendation because a recent change of income was not yet recorded, and records the reason. The agency, not the model, made and owns the decision.
W: Human final decision with recorded reasons: keeping a qualified person as the final authority on high-impact stoppages, and recording why, is the human oversight and traceability the accountability principle calls for.
X: A=Weekly retraining: fresh data may improve accuracy, but it does not establish who is responsible for each decision.
B=Automatic stoppages with published accuracy: publishing accuracy adds some transparency, but letting the model make final stoppages removes human control over decisions that affect people's homes.
D=Encryption: protecting household data supports privacy and security. It does not put a responsible person in charge of the outcome.
T: Accountability means humans and organizations stay answerable for AI decisions, with people keeping meaningful control over high-impact outcomes.

@ AI-901 D2 T2.1 applied definition
S: A developer is learning the three runtime pieces of Foundry Agent Service: agents, conversations and responses. Which two statements about them are correct? (Select TWO)
A: A conversation persists the input and output items of earlier turns on the service side, so later responses can use that history
B: A response must be created through a saved agent, so the service rejects a plain model call that has no agent definition
C: Each response is written into the agent's saved definition, so users who call that agent share one common chat history
D: A conversation keeps the users' text messages but drops the tool calls and tool outputs of earlier turns once a turn ends
E: A response is one unit of execution that runs a model or an agent against the input and produces output items such as the reply
K: A,E
G: ## Agents, conversations and responses
Learn describes three runtime components that work together:
- **Agent**: a reusable definition (model, instructions, tools). Use it when many requests need the same behavior.
- **Conversation**: a durable object that stores **items**: user and assistant messages, tool calls, tool outputs and other data. Use it when later turns need server-side history.
- **Response**: one unit of execution. It runs a model or an agent against the input (and the conversation, if one is given) and produces output items, including the text in `output_text`.
## How they fit together
A support app picks an agent, creates a conversation for the customer, and sends each question as a response in that conversation; the response's output is appended to the same conversation, so the next question is answered in context.
A response doesn't need an agent: you can call a model directly and pass everything in the request. Without a conversation, an app can still chain turns by referencing a previous stored response (`previous_response_id`).
## What is not true
The agent definition never stores chat history; it is shared configuration. History lives in conversations or stored responses.
W: A=Conversation persists history: Learn describes a conversation as the component that supplies persisted input and output items to responses, so later turns have server-side history.
E=Response as execution: Learn defines a response as running a model or agent against input and producing output items; every interaction is one response.
X: B=Agent required: Learn shows responses created directly against a model with no agent, which is the plain model call of a chat client.
C=Responses written into the agent: agents hold only the reusable definition; chat history is never written into it or shared across users.
D=Text messages only: conversations store items, including tool calls and tool outputs, so the next turn can reuse that context.
T: An agent is the reusable definition, a conversation holds the history items, and a response is one run that produces output.

@ AI-901 D1 T1.2 applied use-case
S: A bank in Germany must ensure that prompts and responses for its chat model are processed only inside the EU data zone. Its traffic is moderate and varies through the day. Which deployment type meets this need most directly?
A: Global Provisioned, because reserving dedicated throughput units restricts processing to the region where the bank created its resource.
B: Data Zone Standard, a pay-per-token type whose inference stays inside a Microsoft-defined group of regions, here the European Union.
C: Global Batch, because asynchronous jobs are processed in the region where the input file is stored rather than routed to other regions.
D: Global Standard, because data stored at rest stays in the chosen geography, so inference processing in any Azure region still meets the rule.
K: B
G: ## Where your data is processed
Every deployment type keeps **data stored at rest** in the designated Azure geography. What differs is where **inference** (processing prompts and responses) can happen:
- **Global** types (Global Standard, Global Provisioned, Global Batch): may be processed in **any Azure region**.
- **Data Zone** types (Data Zone Standard, Data Zone Provisioned, Data Zone Batch): processed only within a **Microsoft-specified data zone**: the United States, the European Union or Asia Pacific. The EU data zone follows the Azure EU Data Boundary.
- **Standard** and **Regional Provisioned**: processed within the customer-specified **Azure geography**.
## Picking within the data zone
Data Zone Standard bills per token and suits variable traffic. Data Zone Provisioned adds reserved throughput for consistent high volume. Both keep processing in the zone.
## Example
The bank deploys its model as Data Zone Standard in an EU region. A request from Frankfurt may be processed in another EU region inside the data zone, but never outside it.
W: Data Zone Standard: it restricts inference processing to the chosen data zone (here the EU) and bills per token, which matches a residency rule with moderate, variable traffic.
X: A=Global Provisioned: reserving capacity changes billing and latency, not location; global provisioned deployments can still process data in any Azure region.
C=Global Batch: batch changes timing and cost, and as a global type its processing may happen in any Azure region, not only where the input file is stored.
D=Global Standard: data at rest stays in the geography, but global types may process prompts and responses in any Azure region, which breaks the EU-only processing rule.
T: Data at rest always stays in your geography; to keep inference inside the EU, US or APAC zone, choose a Data Zone deployment type.
