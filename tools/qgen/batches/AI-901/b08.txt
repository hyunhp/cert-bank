@ AI-901 D2 T2.3 applied use-case
S: A developer writes a small Python app that sends shelf photos stored on her laptop to a vision-enabled GPT model deployed in Microsoft Foundry. The photos are not hosted anywhere on the web. How should the app include each photo in the request?
A: Read the file bytes, base64-encode them, and pass a data URL such as data:image/jpeg;base64,... as the image input
B: Put the local file path, such as C:\photos\shelf.jpg, in the image URL field so the service opens the file directly
C: Paste the raw binary bytes of the file into the text part of the message so the model reads them as ordinary tokens
D: Attach the photo to the deployment's details page in the Foundry portal so that every later request includes it
K: A
G: ## Two ways to give a model an image
A vision-enabled model in Foundry accepts images as part of a normal chat or Responses API request. Each image is one part of the user message, next to the text part, and can be supplied as:
- a **public URL** (`https://...`): the service downloads the image itself;
- a **base64 data URL** (`data:image/jpeg;base64,<data>`): the image bytes travel inside the request.
Base64 turns binary bytes into plain ASCII text, which is what lets an image sit inside a JSON request body.
## Example
```
with open("shelf.jpg", "rb") as f:
    b64 = base64.b64encode(f.read()).decode("utf-8")
{"type": "input_image", "image_url": f"data:image/jpeg;base64,{b64}"}
```
The Learn quickstarts show exactly this pattern for local images, plus a small helper that guesses the MIME type from the file extension.
W: Base64 data URL: when an image is not reachable at a public URL, encoding its bytes as a data URL puts the image inside the request, so nothing has to be fetched from the laptop.
X: B=Local file path: the model runs in Azure, not on the laptop. A path such as `C:\photos\shelf.jpg` means nothing to the service, which can only fetch public HTTP or HTTPS URLs.
C=Raw bytes as text: binary data is not valid text, and the text part is treated as words, not as an image. The image must go in an image part, encoded as base64.
D=Attach to the deployment: a deployment has no place to store images for later prompts. Every request must carry its own image input.
T: For images that aren't publicly hosted, send them as base64 data URLs inside the image part of the message.

@ AI-901 D2 T2.3 advanced troubleshooting
S: A team stores product images in a storage account that has public network access disabled and a private endpoint in their virtual network. Their app, in the same virtual network, passes blob URLs to a vision-enabled model in Foundry, and the images are never processed. What should they do?
A: Send the image bytes as base64 data, because the service fetches image URLs from Microsoft-managed infrastructure outside the network
B: Peer the app's virtual network with the Foundry resource's network so the model can download the images through the existing private endpoint
C: Set the image detail setting to high so the model retries the download with a full-resolution request against the private endpoint address
D: Add a Foundry project connection to the storage account so that the deployed model can read private blob URLs on the next request
K: A
G: ## Who downloads an image URL?
When you pass an image URL to a vision-enabled model, the model does not receive your app's network position. The service fetches the image from **Microsoft's managed infrastructure**, not from inside your virtual network.
Learn states it directly: image URLs must be publicly accessible. Private endpoint, VNet-restricted and firewall-restricted URLs are not supported, even when the storage account sits in the same or a peered virtual network.
## Your options
- Send the image as **base64 data** in the request body. Your app reads the blob over the private endpoint (it can), encodes it, and the model never needs to download anything.
- Or make the image reachable at a public URL, which this team has deliberately ruled out.
Learn's troubleshooting table lists "Image not processed: verify URL is publicly accessible or base64 encoding is correct" for exactly this symptom.
W: Base64 instead of URL: the app can read the blob privately, and inline base64 data removes the need for the service to reach the storage account at all.
X: B=Network peering: Learn says private and VNet-restricted URLs fail even for storage in the same or a peered network, because the fetch happens from Microsoft-managed infrastructure.
C=High detail: `detail` only controls how finely the model looks at an image it already has. It has no effect on whether the image can be downloaded.
D=Project connection: connections let Foundry tools and agents reach data sources, but the image URL in a model request is still fetched as a public URL and fails behind a private endpoint.
T: Vision models fetch image URLs from outside your network, so private images must be sent as base64 data.

The AI-901 Learn module says it directly: "Images can be provided as URLs or as base64-encoded image data."

@ AI-901 D2 T2.3 advanced tradeoff
S: A maintenance app sends wide photos of whole machines to a vision-enabled model and asks for the serial number printed on a small label in one corner. The model often misreads the digits. Which change is most likely to improve accuracy?
A: Send a closer or cropped photo in which the label fills more of the frame, so the printed text is larger, while keeping all of its digits visible
B: Raise the temperature setting of the request, so the model considers more possible readings of each digit before it settles on an answer

D: Rename each photo file to include the expected serial number, so the model can compare the digits it reads with the name of the file

G: ## What vision-enabled models find hard
Learn lists known limitations of vision-enabled models. Several are about how readable the image is:
- **Small text**: "Enlarge text within an image to improve readability, but avoid cropping out important details."
- **Rotation**: rotated or upside-down text and images can be misread.
- **Low resolution**: processing a lower-resolution version is faster and uses fewer tokens, but can reduce the accuracy of object and text recognition.
- **Metadata**: the model doesn't process original file names or metadata.
## Fixing the input, not the answer settings
When the model misreads something in a picture, improve what it sees: a closer shot, a crop around the area that matters, an upright image, enough resolution. Settings that shape the answer (temperature, output length) can't add detail the model never saw.
W: Larger text in the photo: small text is a documented weakness, and Learn's advice is to enlarge the text while keeping important details in the frame, which a closer or cropped photo does.
X: B=Higher temperature: temperature makes the wording more random. It doesn't make small digits easier to see and can make answers less consistent.
C=More output tokens: the output limit controls how long the answer may be. The problem is that the digits are too small in the image, not that the answer is cut short.
D=Serial number in the file name: the model doesn't process file names, and putting the expected answer in the input would defeat the purpose of reading the label.
T: When a vision model misreads small text, make the text larger in the image (closer shot or crop) without cutting off the details.

G: ## Reading finish_reason
Every chat completion response includes `finish_reason`:
- `stop`: the model finished its answer normally.
- `length`: the output was cut off by the `max_tokens` (or `max_completion_tokens`) value or the model's token limit.
- `content_filter`: content was omitted because the content filters flagged it.
## Why vision samples set a token limit
The Learn quickstarts for vision-enabled models remind you to set `max_tokens` or `max_completion_tokens`, "or the return output will be cut off". Reasoning models use `max_completion_tokens`. The troubleshooting table on the same page lists "Output truncated: increase max_tokens or max_completion_tokens value".
W: Raise the token limit: finish_reason `length` means the output limit was reached, so a higher `max_tokens` or `max_completion_tokens` value lets the descriptions finish.
X: B=Relax content filter: a filtered answer reports `content_filter`, not `length`. Nothing about the response points to a safety block.
C=Smaller image files: an image that can't be accepted fails as input; image size doesn't make the model stop mid-sentence, and `length` refers to the output limit.
D=Lower temperature: temperature changes how varied the wording is. It doesn't set where the answer ends; the output token limit does.
T: finish_reason "length" means the output limit was hit: raise max_tokens or max_completion_tokens.

@ AI-901 D2 T2.3 applied definition
S: A beginner writes a Responses API call to a vision-enabled model in Foundry and must ask one question about one photo. How should the input be structured?
A: One user message whose content list holds an input_text part with the question and an input_image part with the photo
B: A system message that holds the photo, followed by a separate user message that holds only the text of the question
C: Two separate API requests, one sending the photo and one the question, which the service links by matching their IDs
D: A single input_text part whose text contains the question followed by the public URL of the photo written in plain words
K: A
G: ## A multi-part user message
Vision-enabled models take text and images **in the same request**. In the Responses API, the user message has a `content` list with several parts:
```
input=[{"role": "user", "content": [
  {"type": "input_text", "text": "What is in this image?"},
  {"type": "input_image", "image_url": image_url}]}]
```
The image part can hold a public URL or a base64 data URL. The model reads both parts together and replies; `response.output_text` contains the answer. The Chat Completions API uses the same idea with `text` and `image_url` parts.
## Why structure matters
The part type tells the service how to treat each piece. A URL typed inside a text part is only characters; an `input_image` part is fetched and processed as an image.
W: Text part plus image part: one user message with an `input_text` and an `input_image` part is the documented multimodal request shape, so the model sees the question and the photo together.
X: B=Image in system message: the samples put images in the user message's content list; splitting the photo into the system message is not the documented pattern and separates it from the question it belongs to.
C=Two linked requests: a plain request has no memory of another request, and no ID matching joins an image from one call to a question in another.
D=URL inside text: inside a text part the URL is just characters. Without an image part, the service never downloads or analyzes the photo.
T: Put the question and the image in one user message as separate text and image parts.
