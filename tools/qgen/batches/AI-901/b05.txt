@ AI-901 D2 T2.1 applied definition
S: A bicycle shop is building a chat assistant on a deployed model. Every conversation must follow the same rules: the assistant is a friendly repair advisor, it answers only questions about bicycles, and it says so politely when a question is out of scope. Where should the developer put these rules?
A: In a system message at the start of the message list, which sets the assistant's role, boundaries and fallback behavior for the whole conversation
B: In the first user message of every conversation, so the customer's own question and the shop's rules reach the model as one combined request
C: In an assistant message at the end of the message list, so the model reads the rules as its own last reply and repeats that behavior
D: In the deployment's guardrail configuration, which stores the role description and topic list and applies them to every request to the model
K: A
G: ## Message roles in a chat request
A chat request to a generative model is a list of messages, each with a **role**:
- **system**: instructions and context from the developer. It usually comes first and acts as the highest-level set of instructions for the conversation.
- **user**: what the person typed (the question, the text to summarize).
- **assistant**: replies the model gave earlier, or example replies the developer writes.
## What belongs in a system message
Learn's system message guidance lists the typical uses:
- define the assistant's **role and boundaries** (what it is, what topics it may cover)
- set **tone** and style
- specify an **output format**, for example JSON
- make the **fallback behavior** explicit: what to do when a request is out of scope or information is missing
## Example
`{"role": "system", "content": "You are a friendly bicycle repair advisor. Only answer questions about bicycles. If asked about anything else, politely say you can only help with bicycles."}`
W: System message: the developer's standing instructions belong in the system role at the start of the list, where they steer every turn of the conversation, including what to do with out-of-scope questions.
X: B=Rules in the user message: the user role carries the customer's input. Mixing developer rules into it makes them look like part of the customer's request and means rebuilding that message for every question.
C=Rules as an assistant message: assistant messages hold earlier model replies or example answers. A trailing assistant message also leaves no user turn for the model to answer.
D=Guardrail configuration: a guardrail is a set of safety controls (risks such as hate or violence, where to scan, block or annotate). It doesn't hold a persona, topic list or fallback wording.
T: Put the assistant's role, scope, tone and fallback rules in the system message; user messages carry what the person asks.

@ AI-901 D2 T2.1 applied use-case
S: A help desk app asks a deployed chat model to label each incoming ticket as Hardware, Access or Billing. The labels come back inconsistent, for example "Login problem" or "Account". The team wants the model to copy an exact pattern without retraining it. What should the developer add to the request?
A: A fine-tuning job that trains the deployed model on a few hundred labeled tickets, so the labels become part of the model's weights before the app sends any request
B: A few example user messages, each followed by an assistant message with the correct label, placed after the system message and before the new ticket
C: A higher temperature value in the request, so the model explores more possible label words and settles on the expected three categories more often
D: A longer user message that repeats the new ticket text several times, so the model has more context about the ticket and picks a better label
K: B
G: ## Zero-shot, one-shot and few-shot prompts
- **Zero-shot**: the prompt only describes the task.
- **One-shot / few-shot**: the prompt also includes one or more **examples** of input and the desired output.
Few-shot learning isn't training: the model's weights don't change. The examples only exist in this request and show the model the pattern to follow, which makes outputs more consistent.
## How to add examples in a chat request
In a chat request, examples are written as **pairs of messages**: a `user` message with a sample input followed by an `assistant` message with the exact output you want. The real input comes last as a `user` message:
- system: "Classify each support ticket as Hardware, Access or Billing. Reply with the label only."
- user: "My laptop screen flickers" / assistant: "Hardware"
- user: "I can't sign in to the portal" / assistant: "Access"
- user: (the new ticket)
W: Few-shot message pairs: example user/assistant pairs in the request show the model the exact label set and the reply format, so it copies the pattern for the new ticket without any training.
X: A=Fine-tuning job: fine-tuning changes the model with training data and is far more work than this problem needs; the team explicitly wants consistency without retraining.
C=Higher temperature: temperature controls randomness. Raising it makes wording more varied, which is the opposite of consistent labels.
D=Repeating the ticket: repeating the input adds tokens but no information about which labels are allowed or how the reply should look.
T: To make a model copy a pattern, add a few example user/assistant message pairs (few-shot) before the real input; the model learns from them only within that request.

@ AI-901 D2 T2.1 applied troubleshooting
S: A Python app sends support emails to a deployed model and parses the reply with json.loads(). The system message says "Extract the customer name, order number and issue from the email." Some replies start with a sentence such as "Sure, here are the details:" and parsing fails. What is the most direct fix?
A: Increase the maximum output tokens for the request, so the model has enough room to finish the full JSON object after its opening sentence
B: Move the extraction instruction from the system message into the user message, because the model only follows formatting rules that the user writes
C: State an output contract in the system message: return only JSON with the fixed keys name, order_number and issue, and nothing else
D: Assign a custom guardrail to the deployment that blocks every reply that isn't JSON, so only parseable replies ever reach the application code
K: C
G: ## Output format is part of the prompt
A model produces the format you ask for. If a prompt only says *what* to extract, the model may add friendly sentences, bullet points or Markdown around the data. When code consumes the answer, the prompt must state the format plainly. Learn's system message guidance calls this an **output contract**: "If your app needs structured output, specify an output contract (for example, JSON with fixed keys). Keep the contract small and stable."
## Example system message
`You extract entities from support emails. Return only JSON, using this schema: {"name": "", "order_number": "", "issue": ""}`
Learn lists *hidden requirements* as a common pitfall: "if the output format matters, state it explicitly." Showing the schema (or a few-shot example of the exact output) is the simplest fix, and the app should still validate what it receives.
W: Output contract in the system message: stating "return only JSON" with the exact keys removes the ambiguity that made the model add a lead-in sentence, so the reply parses.
X: A=More output tokens: the replies aren't cut off; they contain extra prose before the JSON. More room doesn't stop the model from adding it.
B=Move to the user message: system messages are where formatting rules usually go. The problem is that no format was stated, not which role stated the task.
D=Guardrail for non-JSON: guardrails detect safety risks such as hate, violence or prompt attacks. They don't check output syntax or enforce JSON.
T: When code parses the reply, spell out the exact output format (for example "return only JSON with these keys") in the system message.

@ AI-901 D2 T2.1 applied tradeoff
S: A small museum wants a chat assistant that answers visitor questions using its one-page list of opening hours, ticket prices and accessibility facts. The page changes a few times a year. Answers must come only from that page. What is the simplest suitable approach?
A: Fine-tune the model on the page, then redeploy the fine-tuned model each time the hours or ticket prices change during the year
B: Index the page in Azure AI Search with vector embeddings and add a retrieval step that searches the index before every request
C: Ask visitors to paste the relevant part of the page into each question, so the assistant always has the facts in the user message
D: Put the page text in the system message as context and instruct the model to answer only from it, or say it doesn't know
K: D
G: ## Grounding data
Generative models answer from patterns learned during training, which can be outdated or wrong for your organization. **Grounding** means giving the model the facts to draw its answer from, in the prompt itself. Learn calls this "one of the most effective ways to provide reliable answers."
## Small data versus large data
Learn's chat guidance draws the line clearly:
- **Small amount of information**: hard-code it in the system message, for example `Only answer questions using the following context. If the context doesn't contain the answer, say 'I don't know.' Context: ...`
- **Large amount of data**: use embeddings or a product like **Azure AI Search** to retrieve the most relevant pieces at query time (retrieval augmented generation, RAG).
## Example
The museum pastes its page under a `Context:` heading in the system message. When the prices change, the developer updates the text; no redeployment or index is needed.
W: Grounding in the system message: a single page fits easily in the prompt, so including it with an "answer only from this context" rule keeps answers factual and is updated by editing text.
X: A=Fine-tuning: fine-tuning needs training data, a training run and a new deployment, and that whole cycle would repeat for every change of hours or prices; grounding gives the same facts by editing text.
B=Azure AI Search index: retrieval is the right design when the data is too large for a prompt. For one page it adds an index, embeddings and a retrieval step with no benefit.
C=Visitors paste the facts: this pushes the work onto users, and visitors don't know which part of the page answers their question.
T: Ground small, stable reference data directly in the system message with an "answer only from this context" rule; use retrieval such as Azure AI Search for large data.

@ AI-901 D2 T2.1 applied troubleshooting
S: A system message gives a model the text of a company's travel policy and tells it to answer employee questions from that text. When an employee asks about something the policy doesn't cover, the model invents a plausible rule. Which change to the prompt is most likely to reduce this?
A: Tell the model what to do when the answer isn't in the text, for example to reply "The travel policy doesn't cover this."
B: Remove the policy text from the system message and rely on the model's general training knowledge about common travel policies
C: Raise the temperature in the request so that the model considers more candidate answers before it settles on a rule
D: Move the policy text into an assistant message so that the model treats the policy as something it has already said
K: A
G: ## Why models invent answers
A generative model predicts the most likely next words. If the prompt implies "always answer," the model produces a fluent answer even when the source text has no answer. That is how grounded assistants still produce fabricated details.
## Give the model an "out"
Learn's prompt engineering best practices include: **Give the model an "out."** Give it an alternative path if it can't complete the task, for example "respond with 'not found' if the answer isn't present." This "can help the model avoid generating false responses."
The system message guidance says the same thing as a design step: add a **"when unsure" policy** that tells the model what to do when the request is out of scope or it lacks information.
## Example
`Answer only from the policy below. If the policy doesn't cover the question, reply exactly: "The travel policy doesn't cover this. Please contact HR."`
W: Explicit fallback: giving the model a permitted answer for missing information removes the pressure to produce a rule, so it says the policy doesn't cover the question.
X: B=Rely on training knowledge: removing the grounding text makes fabrication more likely, because the model then answers from generic patterns instead of the company's policy.
C=Higher temperature: temperature increases randomness in word choice. It makes invented details more varied, not less frequent.
D=Policy as an assistant message: the role of the text doesn't fix the missing instruction. The model still has no allowed response for uncovered questions.
T: Reduce fabricated answers by giving the model an explicit "out", such as a fixed reply when the source text doesn't contain the answer.

@ AI-901 D2 T2.1 advanced tradeoff
S: A team has written a system message for an internal HR assistant and tried three friendly questions in the Foundry model playground. The answers looked right, and they plan to release the app next week. Which TWO statements about this plan reflect Microsoft's guidance on system messages? (Select TWO)
A: Saving the system message in the playground stores it on the deployment, so every app that calls the deployment gets the same rules automatically
B: Making the system message as long and detailed as possible is the most reliable way to guarantee the model follows every one of the rules
C: The system message steers the model but doesn't guarantee compliance, so it should be layered with other mitigations such as guardrails and evaluation
D: The team should test with realistic and adversarial prompts, such as off-topic or rule-breaking requests, and keep refining the system message
E: Once the answers look right in the playground, the same system message produces identical behavior on any other model or model version
K: C,D
G: ## What a system message can and can't do
A system message is a strong influence on the model, not a guarantee. Learn's system message article states it directly: "A system message influences the model, but it doesn't guarantee compliance. You still need to test and iterate, and you should layer system messages with other mitigations (for example, filtering and evaluation)." It also notes that responses "can vary across models and versions."
## Test, measure and iterate
The design checklist ends with **test, measure, and iterate**: test with realistic *and adversarial* prompts, because system messages can overfit to a few examples or fail on edge cases. The playground is the place to do this: change the system message, rerun the same prompts, and compare.
## Common pitfalls
- conflicting instructions ("be brief" and "be comprehensive")
- overly long system messages, which consume the context window and leave less room for user content
- hidden requirements, such as an output format that is never stated
## Where the system message lives
The system message is part of each request. The playground's **Code** tab shows it inside the generated sample; the app must send it on every call.
W: C=Influence, not guarantee: Microsoft states that a system message doesn't guarantee compliance and should be combined with filtering (guardrails) and evaluation.
D=Realistic and adversarial testing: three friendly questions don't show how the assistant handles off-topic or rule-breaking requests; testing those and iterating is the documented practice.
X: A=Stored on the deployment: a deployment doesn't keep a system message. Each client request carries its own system message, which is why the playground's code sample includes it.
B=Longer is more reliable: Learn lists overly long system messages as a pitfall, because they use context window space and can contain conflicting rules.
E=Identical on any model: responses vary across models and versions, so a prompt tuned on one deployment has to be retested on another.
T: A system message steers but doesn't guarantee behavior: test it with realistic and adversarial prompts, iterate, and layer it with guardrails and evaluation.

@ AI-901 D2 T2.1 applied troubleshooting
S: A developer's prompt starts with "Summarize the key points as a bulleted list," followed by a long meeting transcript. The model often returns a paragraph instead of bullets. Using techniques from Microsoft's prompt engineering guidance, what should the developer try first?
A: Split the transcript into many separate requests, one sentence per request, and then join the individual replies together in the app
B: Repeat the instruction after the transcript and end the prompt with a cue such as "Key points:" followed by a first "- " bullet
C: Remove the instruction entirely and rely on the transcript's structure, because models format summaries as lists by default
D: Set the temperature to its maximum value, because a more random model is more likely to try other output formats such as lists
K: B
G: ## Order matters: recency bias
Learn's prompt engineering guidance notes that models can show **recency bias**: information at the end of a prompt can influence the output more than information at the beginning. With a long transcript in the middle, an instruction at the very top can lose its effect. Two documented techniques help:
- **Repeat instructions at the end**: give the instruction before and after the primary content ("double down").
- **Use a cue**: end the prompt with a few words the model builds on. Learn's example is a cue like `Here's a bulleted list of key points:\n- `, which "can help make sure the output is formatted as a list of bullet points."
## Prompt parts in Microsoft's terms
- **Instructions**: what to do.
- **Primary content**: the text to process (the transcript).
- **Cue**: the jump-start for the output.
- **Supporting content**: extra context such as the current date.
W: Repeat plus cue: restating the instruction after the long transcript counters recency bias, and a bulleted cue gives the model the start of the format it should continue.
X: A=One sentence per request: summarizing single sentences loses the overall meaning of the meeting and multiplies requests, and it doesn't address the format problem.
C=Remove the instruction: without any instruction the model has even less reason to use bullets; nothing makes lists the default format.
D=Maximum temperature: temperature adds randomness to word choice. It doesn't steer the model toward a specific format and can make the output less coherent.
T: When a long input buries the instruction, repeat the instruction after the content and end with a cue that starts the desired format.

@ AI-901 D2 T2.1 advanced troubleshooting
S: A developer tries to create a second deployment of a model in a Foundry resource. The deployment fails, and the troubleshooting guidance points to a quota exceeded error for that model in the region. Which TWO actions resolve the problem? (Select TWO)
A: Submit a quota increase request for that model in the region, so more tokens-per-minute (TPM) can be assigned to deployments
B: Lower the TPM assigned to the existing deployment of that model, which frees quota that the new deployment can use
C: Switch the application from API key authentication to Microsoft Entra ID, which raises the quota available to the resource
D: Assign a custom guardrail to the new deployment, because the default guardrail counts its scans against the model's quota
E: Accept the Azure Marketplace terms for the model again, because quota is only granted with an active Marketplace subscription
K: A,B
G: ## How deployment quota works
Deploying a model and running inference consume **quota**, which Azure assigns to your subscription **per region and per model** in units of **tokens per minute (TPM)**. When you create a deployment you assign it some TPM, which reduces the quota left for that model. You can keep creating deployments until the quota is used up.
## When the quota is used up
Learn lists exactly two ways to create more deployments of that model:
- **Request more quota** by submitting a quota increase form.
- **Adjust the quota allocated to other deployments** of the model in the Foundry portal to free tokens for the new one.
## Example
The region has 50K TPM for the model and the first deployment holds all 50K. Lowering it to 30K leaves 20K for the new deployment; alternatively, request an increase.
W: A=Quota increase request: asking for more TPM for that model and region raises the limit so the new deployment can be assigned capacity.
B=Reallocate TPM: reducing the TPM held by the existing deployment returns quota to the pool, which the new deployment can use.

G: ## Guardrails (content filters) in Foundry
Microsoft Foundry applies **guardrails** to model deployments and agents. A guardrail is a named collection of **controls**; each control defines:
- a **risk** to detect, such as hate, sexual, self-harm, violence, or user prompt attacks
- **intervention points**: for models, *user input* (the prompt) and *output* (the completion)
- an **action**: annotate, or annotate and block

G: ## Where content filtering shows up in the API
Guardrails scan both the **prompt** and the **completion**. Your code sees the result in two different ways:
- **Prompt filtered**: prompts classified at a filtered category and severity level return an **HTTP 400** error with the code `content_filter`.
- **Completion filtered**: the call succeeds, but the choice's `finish_reason` is `content_filter` and no (or only partial) content is returned.
## Other finish_reason values
- `stop`: the model finished its output.
- `length`: output stopped at the max tokens setting or the token limit.
- `tool_calls`: the model called a tool.
## What the app should do
Check `finish_reason` on every response, and catch the 400 `content_filter` error to show the user a friendly message (for example "I can't help with that request") instead of crashing.

X: A=Context window exceeded: a request that's too long fails because of token limits, not with a content_filter code, and it would affect long conversations rather than one message's content.
B=Cut off at max tokens: a reply that hits the token limit is returned successfully with `finish_reason` set to `length`, not as an HTTP 400 error.
D=TPM throttling: running past the rate limit is a throttling response that asks the client to retry later; it isn't tied to content and doesn't use the content_filter code.
T: A blocked prompt returns HTTP 400 with code `content_filter`; a blocked completion returns `finish_reason: content_filter`, so apps should handle both.
