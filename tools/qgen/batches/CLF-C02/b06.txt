# CLF-C02 b06: D2 T2.1 The AWS shared responsibility model (x20)

@ CLF-C02 D2 T2.1 applied troubleshooting
S: An online retailer discovers that customer invoices stored in an Amazon S3 bucket were downloaded by strangers. Investigation shows an employee had turned off S3 Block Public Access and added a bucket policy that allows public reads. Under the shared responsibility model, whose responsibility was this exposure?
A: The retailer's, because deciding who can read objects, through bucket policies and Block Public Access settings, is security in the cloud.
B: AWS's, because Amazon S3 is a fully managed service, so AWS must review every new bucket policy before it takes effect on stored objects.
C: AWS's, because S3 should reject any bucket policy that grants public read access to objects that contain personal information.
D: Both equally, because access to S3 objects is a shared control that AWS and the customer must approve together for each bucket.
K: A
G: ## Managed does not mean "access is managed for you"
Amazon S3 is a fully managed service: AWS runs the storage hardware, the software that stores objects, and the facilities. What AWS does **not** decide is who is allowed to read your data. That choice is always part of **security in the cloud**, the customer's side of the model.
## The customer's access tools in S3
- **S3 Block Public Access**: account-level and bucket-level switches that override any policy or ACL that would make data public. It is turned on by default for new buckets, but a user with enough permissions can turn it off.
- **Bucket policies and IAM policies**: decide which principals may call actions such as `s3:GetObject`.
- **Encryption and logging choices**: for example SSE-KMS keys and server access logs.
Example: a bucket policy with `"Principal": "*"` and `s3:GetObject` lets anyone on the internet download every object, and S3 will serve those requests exactly as configured.
W: The retailer: S3 does what its configuration says. Turning off Block Public Access and writing a public-read policy are customer configuration decisions, so the resulting exposure sits on the customer side of the model.
X: B=AWS reviews every bucket policy: AWS does not approve or review customer policies before they take effect. Tools such as IAM Access Analyzer can warn about public access, but acting on the warning is the customer's job.
C=S3 rejects public policies: public access is a legitimate configuration (for example, for static websites), and S3 has no way of knowing which objects contain personal data. Classifying data and choosing access is the customer's job.
D=Access is a shared control: AWS lists patch management, configuration management, and awareness and training as shared controls. Granting access to customer data is customer-specific, and there is no joint approval step.
T: Even on a fully managed service like S3, who can access the data is always the customer's responsibility.
V: Amazon S3, S3 Block Public Access

@ CLF-C02 D2 T2.1 advanced troubleshooting
S: A company encrypted its Amazon S3 objects with a customer managed key in AWS KMS. An administrator scheduled the key for deletion, the waiting period ended, and now the objects cannot be decrypted. The company opens a support case asking AWS to restore the key. What is the expected outcome?
A: AWS cannot restore it, because the key lifecycle, including deletion of a customer managed key, is the customer's responsibility and the deletion is final.
B: AWS restores it from its own backup of KMS key material, because AWS is responsible for the durability of every key stored in the KMS service.
C: AWS restores it after verifying account ownership, because AWS keeps a recovery copy of each deleted customer managed key for one more year.
D: AWS decrypts the objects with its own master key instead, because S3 always keeps a second encrypted copy of each object under an AWS owned key.
K: A
G: ## Who controls an encryption key
AWS KMS splits the work like this:
- **AWS (security of the cloud)**: runs the hardware security modules, keeps key material durable and available while the key exists, and makes sure no AWS employee can use your plaintext keys.
- **Customer (security in the cloud)**: creates customer managed keys, writes key policies, decides who may use them, enables rotation, and decides when to disable or delete them.
## Deleting a key is a customer decision with permanent effect
Because deletion is so dangerous, KMS never deletes a key immediately. You must schedule deletion with a waiting period, and during that window you can cancel it. Once the waiting period ends, the key material is gone, and anything encrypted only under that key can no longer be decrypted.
Safer practice: disable a key first and watch for failed requests (for example in AWS CloudTrail) before scheduling deletion.
W: No restore: managing a customer managed key's lifecycle is customer responsibility. KMS gives a waiting period to cancel the deletion, but after it ends the key material is destroyed and AWS cannot bring it back.
X: B=AWS keeps a KMS backup: AWS keeps keys durable only while they exist. A deletion the customer requested is carried out completely, so there is no hidden backup to restore from.
C=One-year recovery copy: there is no recovery period after the waiting period ends. The only chance to undo the deletion is to cancel it while the deletion is still pending.
D=Second copy under an AWS key: S3 stores the object encrypted under the key the customer chose. It does not keep a parallel copy under another key that AWS could use instead.
T: AWS keeps KMS running and keys durable, but the customer decides who uses a key and when it is deleted, and a completed deletion cannot be undone.
V: AWS Key Management Service (AWS KMS), Amazon S3

@ CLF-C02 D2 T2.1 applied comparison
S: A logistics company runs its containers on Amazon ECS with a cluster of EC2 instances that it manages. It plans to switch the same tasks to AWS Fargate. Which security task moves from the company to AWS after the switch?
A: Patching the operating system and container agent on the hosts that run the containers.
B: Scanning the company's own container images for vulnerable software packages before deploy.
C: Writing the IAM task role policies that decide which AWS resources each task may call.
D: Choosing which ports the tasks' security groups allow from the company's load balancer.
K: A
G: ## Two ways to run Amazon ECS tasks
- **EC2 launch type**: your containers run on EC2 instances in your account. You choose the AMI, patch the operating system, update the ECS container agent and Docker or containerd, and scale the instances.
- **AWS Fargate**: a serverless compute engine for containers. AWS provisions and patches the underlying hosts, operating system and container runtime. You never see or log in to those hosts.
## What stays with the customer on Fargate
Fargate removes the host layer, not your application layer:
- The **container image** and everything inside it, including libraries with known vulnerabilities.
- **IAM task roles** and task execution roles.
- **Network rules**: security groups and which subnets the tasks use.
- Secrets, data and logging choices.
Example: an old `openssl` package baked into your image is still yours to fix on Fargate, even though the host OS is AWS's.
W: Host OS and agent patching: with Fargate, AWS runs and patches the hosts, their operating system and the container runtime, so the company no longer maintains that layer.
X: B=Image scanning: the contents of a container image are the customer's code and dependencies. Fargate does not patch what is inside your image, so scanning and rebuilding images stays with the company.
C=Task role policies: IAM permissions are always customer configuration. Fargate runs whatever role the company assigns, so least privilege remains the company's job.
D=Security group ports: Fargate tasks still use security groups, and the customer writes their rules just as it did with EC2 instances.
T: Fargate moves host and OS patching to AWS; images, IAM roles and network rules stay with the customer.
V: AWS Fargate, Amazon ECS

@ CLF-C02 D2 T2.1 applied definition
S: A school district is learning which parts of security AWS handles for workloads that run on Amazon EC2. Which items are AWS responsibilities under the shared responsibility model? (Select TWO)
A: Maintaining the routers, switches and fiber links that connect AWS data centers and Regions.
B: Providing power, cooling and fire suppression in the facilities that host the EC2 servers.
C: Writing the security group rules that decide which traffic can reach the district's instances.
D: Configuring the firewall software running inside the guest operating system of each instance.
E: Installing TLS certificates on the district's web servers so that student logins are encrypted.
K: A,B
G: ## Security OF the cloud
AWS owns everything you cannot see or touch as a customer:
- **Facilities**: buildings, guards, badge systems, power, cooling, fire detection and suppression.
- **Hardware**: servers, storage devices, and their secure decommissioning.
- **Network infrastructure**: the routers, switches and cabling inside data centers and the global network that links Availability Zones and Regions.
- **Virtualization**: the hypervisor that isolates one customer's instances from another's.
## Security IN the cloud
For EC2 (Infrastructure as a Service) the customer owns everything it configures:
- Security groups and network ACLs.
- The guest operating system, its firewall (for example `iptables` or Windows Firewall) and patches.
- Applications, TLS certificates and the data they handle.
A quick test: if you can configure it in your account or log in to it, it is yours. If you could only reach it by walking into an AWS building, it is AWS's.
W: A=Network infrastructure: the physical network devices and links between AWS facilities are part of the infrastructure AWS runs for all customers.
B=Environmental controls: power, cooling and fire suppression in data centers are physical and environmental controls that customers fully inherit from AWS.
X: C=Security group rules: AWS provides security groups as a feature, but the district writes the rules, so they are on the customer side.
D=Guest OS firewall: on EC2 the guest operating system is the customer's, including any firewall software running inside it.
E=TLS certificates on web servers: encrypting application traffic is a customer choice. AWS offers tools such as AWS Certificate Manager, but the district decides to use them and configures its servers.
T: Facilities, hardware, network infrastructure and the hypervisor are AWS's; anything configured in the account or inside the instance is the customer's.
V: Amazon EC2

@ CLF-C02 D2 T2.1 applied use-case
S: A financial analytics firm runs sensitive calculations on Amazon EC2. Its risk officer worries that another AWS customer whose instances run on the same physical server could read the firm's instance memory. Under the shared responsibility model, who is responsible for preventing that?
A: AWS, because isolating instances from each other through the hypervisor and host hardware is part of security of the cloud.
B: The firm, because it must install memory encryption software in each guest operating system to block other tenants on that host.
C: The firm, because it must add security group rules that deny all traffic coming from other AWS customers' instances on the host.
D: The other customer, because each tenant must sign an agreement with AWS that forbids reading memory owned by neighboring tenants.
K: A
G: ## Multi-tenancy and the hypervisor
Most EC2 instances share physical servers with instances from other customers. The **hypervisor** is the layer that divides one physical server into separate virtual machines. On modern instance types this is the **AWS Nitro System**, which moves virtualization functions to dedicated hardware and gives AWS operators no interactive access to customer instances.
## Whose job is isolation?
Keeping one tenant's memory, CPU state and storage away from another tenant is part of the infrastructure AWS runs, so it sits under **security of the cloud**. The customer cannot see or configure the hypervisor at all.
If a company has its own compliance reasons to avoid sharing hardware, it can choose **Dedicated Instances** or **Dedicated Hosts**, but that is a placement choice, not a requirement for isolation.
W: AWS: tenant isolation is enforced by the hypervisor and host hardware, which AWS designs, operates and patches as part of security of the cloud.
X: B=Install memory encryption in the guest: software inside a guest OS cannot control what the hypervisor below it does. Isolation between tenants is not something the customer can or must build.
C=Security groups against other tenants: security groups filter network traffic to an instance's network interfaces. They have nothing to do with memory sharing on the physical host.
D=Tenant agreements: isolation is a technical control AWS operates, not a promise each neighboring customer makes. A customer cannot even see who shares its host.
T: Isolation between customers on shared hardware is provided by the AWS hypervisor (Nitro), which is security of the cloud.
V: Amazon EC2, AWS Nitro System

@ CLF-C02 D2 T2.1 applied use-case
S: A design agency stores client artwork in Amazon S3. Which tasks are the agency's responsibility under the shared responsibility model? (Select TWO)
A: Classifying which artwork files are confidential and deciding who in the agency may access each bucket.
B: Turning on S3 Versioning if the agency wants to recover files that staff overwrite or delete by mistake.
C: Replacing failed disks in the S3 storage fleet so that the stored artwork files remain durable over time.
D: Applying security patches to the servers and software that run the Amazon S3 service in each Region.
E: Destroying storage media that leaves the AWS data center so that deleted artwork cannot be read again.
K: A,B
G: ## What AWS does for S3
Amazon S3 is an abstracted (fully managed) storage service. AWS runs:
- The storage hardware and its replacement when disks fail.
- The software and servers behind the S3 API, including patching.
- Redundant storage across multiple Availability Zones for most storage classes, which is where S3's high durability comes from.
- Secure handling and destruction of storage media at the end of its life.
## What the customer still decides
- **Data classification and access**: which data is sensitive and who may read or write it (IAM policies, bucket policies, Block Public Access).
- **Data protection features**: S3 Versioning, replication, Object Lock and lifecycle rules are options the customer chooses to turn on.
- **Encryption choices**: for example, whether to use SSE-KMS with a customer managed key.
Durability protects against hardware failure, not against a user deleting the wrong file. Recovering from human mistakes needs features such as Versioning, which only the customer can enable.
W: A=Classification and access: AWS does not know which files are confidential. Classifying data and granting access to it is always the customer's job.
B=Enabling Versioning: Versioning is off until the customer turns it on. Protecting data against accidental overwrite or deletion is a customer configuration choice.
X: C=Replacing failed disks: hardware maintenance in the S3 fleet is invisible to customers and is done by AWS as part of the service's durability design.
D=Patching S3 servers: S3 is fully managed. Customers have no access to its servers, so AWS patches them.
E=Destroying storage media: media sanitization and destruction is a physical control that AWS performs inside its facilities.
T: For S3, AWS runs and protects the storage; the customer classifies data, controls access and turns on protection features such as Versioning.
V: Amazon S3

@ CLF-C02 D2 T2.1 applied definition
S: A company stores documents in Amazon S3. Which statement about encryption at rest best fits the shared responsibility model?
A: AWS supplies the encryption features and encrypts new objects with SSE-S3 by default, and the company decides if it needs another option such as SSE-KMS.
B: AWS selects the most suitable encryption key type for each object automatically, so the company has no encryption decisions left to make for its bucket.
C: The company must encrypt every object in its own application before upload, because Amazon S3 stores all objects without any encryption at rest at all.
D: AWS encrypts objects only when the company signs a separate data protection addendum, because encryption at rest is outside the standard S3 service.
K: A
G: ## Encryption is a feature from AWS and a choice for the customer
AWS builds and runs the encryption capabilities, and the customer chooses how to use them. In Amazon S3:
- **SSE-S3** (S3 managed keys): since January 2023, S3 encrypts all new objects with SSE-S3 by default, at no extra cost.
- **SSE-KMS**: uses keys in AWS KMS. With a customer managed key the customer writes the key policy, controls who can decrypt, and every use of the key appears in AWS CloudTrail.
- **Client-side encryption**: the customer encrypts data before sending it, keeping full control of keys outside AWS.
## Why the choice matters
Regulations or internal policies may require separate control of keys or an audit trail of key use. SSE-S3 alone does not give the customer its own key policy, so the customer must decide whether SSE-KMS or client-side encryption is needed. That decision, and the management of any customer managed keys, is security in the cloud.
W: Default SSE-S3 plus customer choice: AWS provides the encryption capabilities and a secure default, while choosing a stronger or more controllable option such as SSE-KMS stays with the customer.
X: B=AWS picks the key type: S3 applies a default (SSE-S3), but it does not judge what each object needs. Choosing SSE-KMS, a specific key or client-side encryption is the company's decision.
C=S3 stores data unencrypted: this was never a requirement and is outdated now. New objects are encrypted at rest with SSE-S3 by default, and client-side encryption is optional.
D=Separate addendum needed: encryption at rest is a standard S3 feature available to every customer. No extra agreement is needed to use it.
T: AWS provides encryption features and secure defaults; the customer decides which encryption option and keys its data requires.
V: Amazon S3, AWS Key Management Service (AWS KMS)

@ CLF-C02 D2 T2.1 applied comparison
S: A travel booking company uses Amazon Aurora MySQL for its reservations database. Which task does AWS perform for the company under the shared responsibility model?
A: Detecting and repairing failed storage segments in the cluster volume that is spread across Availability Zones.
B: Creating database accounts for each booking application and granting each account only the privileges it needs.
C: Deciding which VPC security groups and subnets may send connections to the cluster's endpoint and database port.
D: Choosing whether to encrypt the cluster with an AWS KMS key when the database cluster is being created.
K: A
G: ## Aurora is a managed relational database
Amazon Aurora is part of Amazon RDS, and like other RDS engines it moves the infrastructure layers to AWS:
- **AWS**: hardware, the operating system, database engine patching in maintenance windows, and the distributed **cluster volume**. Aurora stores copies of the data across multiple Availability Zones and automatically detects and repairs failed storage segments.
- **Customer**: what happens inside and around the database.
## The customer side for Aurora
- Database users, passwords and privileges (for example `GRANT SELECT` on one schema).
- Network placement: VPC, subnets, security group rules, and whether the cluster is publicly accessible.
- Encryption at rest, chosen when the cluster is created, and requiring TLS from clients.
- Backup retention settings, snapshots the customer takes, and the data itself.
W: Storage repair: the Aurora storage layer is part of the managed service. AWS replicates data across Availability Zones and repairs failed segments without customer action.
X: B=Database accounts: Aurora does not know which application should read which tables. Creating users and applying least privilege is the customer's job.
C=Security groups and subnets: AWS provides the network controls, but the customer chooses which sources can connect to the database.
D=Encryption choice: AWS supplies KMS-based encryption, but the customer decides to enable it at creation and controls the key.
T: With Aurora, AWS runs and heals the storage and engine; the customer controls users, network access, encryption choices and data.
V: Amazon Aurora, Amazon RDS

@ CLF-C02 D2 T2.1 applied definition
S: A compliance team is mapping its controls to the AWS shared responsibility model. Which controls does AWS describe as shared controls? (Select TWO)
A: Configuration management, where AWS configures its infrastructure devices and the customer configures its own guest operating systems, databases and applications.
B: Awareness and training, where AWS trains AWS employees and the customer trains its own employees on how to use and secure its workloads.
C: Physical and environmental protection, where the customer relies fully on the safeguards that AWS builds and audits in every data center.
D: Service and communications protection, where the customer routes and segments its own data into security zones inside its environment.
E: Host isolation on shared servers, where the hypervisor keeps one customer's virtual machines separated from other customers' instances.
K: A,B
G: ## Three kinds of controls
The shared responsibility model sorts IT controls into three groups:
- **Inherited controls**: the customer gets them entirely from AWS. Physical and environmental controls are the standard example.
- **Shared controls**: the same control applies in both layers, and each party carries it out in its own context. AWS names three: **patch management**, **configuration management**, and **awareness and training**.
- **Customer-specific controls**: only the customer is responsible, for example service and communications protection, or zone security, where the customer routes and segments its own data.
## Shared means "each does its own part"
In configuration management, AWS maintains the configuration of its own infrastructure devices, while the customer configures its own guest operating systems, databases and applications. In awareness and training, AWS trains its staff, and the customer trains its own people. Neither party does the other's part.
W: A=Configuration management: one of the three controls AWS lists as shared, with AWS configuring infrastructure and the customer configuring what it runs.
B=Awareness and training: also listed as shared; each party is responsible for training its own employees.
X: C=Physical and environmental protection: customers fully inherit these from AWS, which makes them inherited controls, not shared ones.
D=Service and communications protection: segmenting and routing the customer's own data is customer-specific; AWS has no part in it.
E=Host isolation: separating tenants on shared hardware is done only by AWS through the hypervisor, so it is purely on the AWS side.
T: The three shared controls are patch management, configuration management, and awareness and training; each party does its own part.
V: AWS shared responsibility model

@ CLF-C02 D2 T2.1 applied use-case
S: A payments startup is preparing for an audit of its workloads that run on Amazon EC2. Its auditor asks which controls the startup can document as fully inherited from AWS, with no action required by the startup. Which control fits?
A: Physical and environmental controls of the data centers, such as access badges, guards, power and climate control.
B: Hardening the configuration of each instance's guest operating system against the startup's security baseline.
C: Reviewing every quarter which IAM users and roles can stop, start or terminate the startup's EC2 instances.
D: Applying operating system patches to the instances in a monthly maintenance window that the startup has chosen.
K: A
G: ## What "inherited" means
An **inherited control** is a control that AWS fully operates and the customer benefits from automatically. The customer does nothing to implement it, but can show auditors that it exists by pointing to AWS audit reports (for example SOC reports downloaded from AWS Artifact).
The standard example is **physical and environmental protection**: data center access control, security staff, video surveillance, power, cooling and fire suppression.
## What cannot be inherited
- **Shared controls**: patch management, configuration management, and awareness and training. AWS handles its layer, but the startup must still do its own part on its instances.
- **Customer-specific controls**: things only the customer can do, such as access reviews for its own IAM identities or segmenting its own network.
W: Physical and environmental controls: AWS fully operates data center security and environmental safeguards, so the startup inherits them and documents them using AWS's audit reports.
X: B=Guest OS hardening: configuration management is a shared control. AWS configures its infrastructure, but the startup must harden the operating systems it runs.
C=IAM access reviews: deciding and reviewing who may act on the startup's resources is purely the customer's responsibility.
D=OS patching on EC2: patch management is shared. AWS patches hosts and the hypervisor, but the guest OS on EC2 is patched by the customer.
T: Physical and environmental data center controls are inherited from AWS; patching, configuration and access reviews still need customer action.
V: AWS shared responsibility model, AWS Artifact

@ CLF-C02 D2 T2.1 applied definition
S: Under the AWS shared responsibility model, which example is a customer-specific control, one that AWS has no part in for the customer's workload?
A: Zone security, where the customer segments its own VPC into tiers and routes data between them according to its own rules.
B: Patch management, where updates are applied to infrastructure by AWS and to guest systems by the customer for each service.
C: Awareness and training, where both AWS and the customer make sure their own staff understand secure cloud practices.
D: Media sanitization, where storage devices are wiped and destroyed before they leave the secured AWS data center sites.
K: A
G: ## Where each control sits
- **AWS only (security of the cloud)**: physical security, media sanitization and destruction, hypervisor, network infrastructure.
- **Shared controls**: patch management, configuration management, awareness and training. Both parties perform the control, each in its own layer.
- **Customer-specific controls**: only the customer can decide or perform them because they depend on the customer's own design and data.
## Example: zone security
A hospital might put web servers in public subnets, application servers in private subnets and databases in isolated subnets, with security groups and network ACLs allowing only specific traffic between tiers. AWS provides the building blocks (VPCs, subnets, security groups), but how data is segmented and routed is entirely the customer's design. AWS calls this service and communications protection, or zone security.
W: Zone security: segmenting and routing the customer's own data inside its environment depends entirely on the customer's design, so AWS lists it as a customer-specific control.
X: B=Patch management: it is a shared control, because AWS patches its infrastructure and the customer patches its own guest systems and applications.
C=Awareness and training: also a shared control, since each party trains its own staff.
D=Media sanitization: wiping and destroying storage devices happens only inside AWS facilities, so it is an AWS-only control the customer inherits.
T: Customer-specific controls, such as zone security, depend only on the customer's own design; AWS supplies the tools but has no part in the control.
V: AWS shared responsibility model, Amazon VPC

@ CLF-C02 D2 T2.1 applied troubleshooting
S: A game studio's Amazon EC2 instance was taken over by attackers. The security group allowed SSH on port 22 from 0.0.0.0/0, and the Linux user had a weak password. The studio asks why AWS did not prevent the attack. Which explanation is correct?
A: Security group rules and operating system credentials are customer configuration, so securing them is the studio's responsibility.
B: AWS should have blocked the traffic, because AWS is responsible for filtering all attack traffic before it reaches any EC2 instance.
C: AWS should have rejected the weak password, because AWS enforces password strength for every user account inside guest operating systems.
D: The studio's ISP is responsible, because security for internet traffic arriving at a VPC belongs to the provider that delivers it.
K: A
G: ## AWS gives you the controls; you set them
On Amazon EC2, the customer configures every layer that decides who can log in:
- **Security groups**: virtual firewalls on each instance's network interfaces. A rule allowing port 22 from `0.0.0.0/0` lets the whole internet attempt SSH logins.
- **Guest OS authentication**: Linux users, passwords, SSH keys and the `sshd` configuration live inside the instance, which AWS cannot see.
## Safer patterns
- Allow SSH only from known addresses, or remove inbound SSH entirely and use AWS Systems Manager Session Manager.
- Use key pairs instead of passwords and keep the OS patched.
AWS does protect the infrastructure (for example, AWS Shield Standard defends against common network-layer DDoS attacks for all customers), but it does not override the access rules a customer chooses.
W: Customer configuration: the security group rule and the weak OS password are both settings the studio controls, so preventing this break-in was part of security in the cloud.
X: B=AWS filters attack traffic: AWS protects its infrastructure, but it does not second-guess traffic that a customer's own security group explicitly allows. An open port 22 is a customer choice.
C=AWS enforces OS password strength: AWS has no access to user accounts inside a guest operating system. Password policies there are set by the customer.
D=The ISP is responsible: the internet provider only carries traffic. Which traffic reaches the instance is decided by the studio's security group.
T: On EC2, open ports and OS credentials are customer configuration; AWS protects the infrastructure, not the access rules you choose.
V: Amazon EC2, AWS Systems Manager

@ CLF-C02 D2 T2.1 applied troubleshooting
S: A developer at a marketing agency pushed an IAM user's access key to a public code repository. Within hours, unknown parties used the key to launch resources in the agency's account. Under the shared responsibility model, who is responsible for protecting that access key?
A: The agency, because managing IAM credentials, including storing, rotating and revoking access keys, is the customer's responsibility.
B: AWS, because AWS issues every access key and must therefore detect and block any request made with a key that has been leaked.
C: AWS, because IAM is a global service and global services fall entirely under security of the cloud in the shared responsibility model.
D: The code hosting provider, because it accepted the file and is responsible for preventing secrets in its repositories from being used.
K: A
G: ## Identity is always on the customer side
AWS runs the IAM service itself (the infrastructure, the authentication systems and their availability). Everything about **your identities** is security in the cloud:
- Which users and roles exist and what their policies allow.
- How credentials are stored, rotated and revoked.
- Whether MFA is required.
## Long-term keys are risky
An access key for an IAM user works until someone deactivates or deletes it. If it leaks, anyone can call AWS APIs as that user. Better practice:
- Prefer temporary credentials: IAM roles for workloads and IAM Identity Center for people.
- Never put keys in code; use a secrets store such as AWS Secrets Manager when a secret is unavoidable.
- If a key leaks, deactivate it immediately, review AWS CloudTrail for what it did, and remove any resources created.
AWS may notify you when it detects an exposed key, but that is a courtesy; the responsibility stays with the customer.
W: The agency: protecting, rotating and revoking its own IAM credentials is customer responsibility, so a key published in a public repository is the agency's security failure to fix.
X: B=AWS must block leaked keys: a valid key is accepted because AWS cannot tell an attacker from the real owner. Revoking a compromised key is the customer's job.
C=Global services are AWS's: whether a service is global or Regional does not change the model. AWS runs IAM, but the identities and credentials in it belong to the customer.
D=The code host is responsible: the hosting provider stores what users upload. The agency chose to put the secret there and remains responsible for it in AWS.
T: AWS runs IAM, but creating, protecting, rotating and revoking credentials is always the customer's job.
V: AWS Identity and Access Management (IAM), AWS Secrets Manager

@ CLF-C02 D2 T2.1 applied tradeoff
S: A small nonprofit with no operations staff is building a donation API. It wants to keep its share of security work under the shared responsibility model as small as possible. Which design meets this goal best?
A: Amazon API Gateway with AWS Lambda functions and Amazon DynamoDB tables, so no servers or operating systems exist for it to manage.
B: Amazon EC2 instances running a web server and a database the nonprofit installs, with patches applied by a scheduled script.
C: Amazon ECS on a cluster of EC2 instances that the nonprofit manages, running both the API container and a database container.
D: Amazon EC2 instances behind a load balancer and Amazon RDS for the database, so only the web tier's operating system is its job.
K: A
G: ## Responsibility shrinks as abstraction grows
The shared responsibility model applies to every service, but the line moves:
- **Infrastructure services** (Amazon EC2, ECS on EC2): the customer manages the guest OS, patches, runtime software and scaling.
- **Container services with managed hosts** (AWS Fargate) and **managed databases** (Amazon RDS): AWS takes over hosts, OS and engine patching.
- **Serverless services** (AWS Lambda, Amazon API Gateway, Amazon DynamoDB): AWS runs the servers, operating systems and runtimes. The customer manages code, data, configuration and IAM permissions.
## What still remains in a serverless design
Even with no servers, the nonprofit must write secure code, keep bundled libraries updated, set least-privilege IAM roles, configure API authentication, and protect donor data. Those tasks never move to AWS.
W: Serverless stack: with API Gateway, Lambda and DynamoDB, there are no operating systems or servers for the customer to patch or harden, which leaves the smallest customer share of the work.
X: B=Self-managed EC2: the nonprofit would patch the OS, web server and database software itself, which is the largest share of responsibility.
C=ECS on self-managed EC2: containers help packaging, but the nonprofit still patches and scales the EC2 hosts and runs its own database in a container.
D=EC2 plus RDS: RDS removes database patching, but the web tier's EC2 instances still leave an operating system for the nonprofit to patch and harden.
T: The more serverless and managed the services, the less infrastructure security the customer handles; code, data and permissions always remain.
V: AWS Lambda, Amazon API Gateway, Amazon DynamoDB

@ CLF-C02 D2 T2.1 advanced tradeoff
S: A research lab must run a custom kernel module and a specialized monitoring agent inside the operating system of its compute servers. It is choosing between Amazon EC2 and AWS Lambda. Which statement describes the trade-off under the shared responsibility model?
A: EC2 gives the lab the operating system access it needs, but the lab then becomes responsible for patching and hardening that operating system.
B: Lambda gives the lab root access to the execution environment for kernel modules, and AWS still keeps full responsibility for patching it.
C: EC2 and Lambda carry the same customer responsibilities, because the shared responsibility model applies equally to every AWS compute service.
D: EC2 moves operating system patching to AWS once a custom kernel module is installed, because AWS must then certify the modified kernel.
K: A
G: ## Control and responsibility move together
Choosing a service is also choosing where the shared responsibility line falls:
- **Amazon EC2** gives full control of the guest operating system: root or Administrator access, custom kernels and modules, any agent. With that control comes responsibility for patching, hardening and monitoring the OS.
- **AWS Lambda** hides the operating system. AWS patches and operates the execution environment, but customers cannot load kernel modules or log in as root on the host.
## Choosing deliberately
If a requirement truly needs OS-level access, EC2 (or another service that exposes the OS) is the right choice, and the team should plan for patching, for example with AWS Systems Manager Patch Manager. If it does not, a managed or serverless service removes that work.
W: Control means responsibility: EC2 lets the lab load kernel modules and agents, and in exchange the lab owns patching and hardening of that operating system.
X: B=Lambda allows kernel modules: Lambda functions run in an execution environment the customer cannot modify at the kernel level, so this requirement rules Lambda out.
C=Same responsibilities everywhere: the model applies to all services, but the split differs. EC2 leaves the OS with the customer, while Lambda moves it to AWS.
D=AWS patches modified kernels: AWS never takes over a customer's guest OS on EC2, and installing custom modules makes OS maintenance even more clearly the lab's job.
T: More control over the operating system (EC2) means more security responsibility; less control (Lambda) means AWS carries more of it.
V: Amazon EC2, AWS Lambda

@ CLF-C02 D2 T2.1 applied use-case
S: An insurance company in Germany must keep customer data inside the European Union. It plans to store the data in Amazon S3 and Amazon DynamoDB. Under the shared responsibility model, who decides in which geographic location the data is stored?
A: The company, because it chooses the AWS Regions for its resources, and AWS does not move content out of a Region unless the customer acts to do so.
B: AWS, because AWS places each customer's data in the Region with the most spare capacity and moves it between continents to balance usage.
C: AWS, because AWS determines the customer's legal obligations from its billing address and stores data in a Region that satisfies those laws.
D: The local regulator, because European authorities assign each company an approved AWS Region when it registers to process personal data.
K: A
G: ## Customer data belongs to the customer
Under the shared responsibility model, **customer content** (the data you store) and decisions about it are security in the cloud. That includes:
- **Where it lives**: the customer selects the AWS Region for each resource, for example `eu-central-1` (Frankfurt).
- **Who can access it**: IAM and resource policies.
- **How it is protected**: encryption, backups and retention.
## Region choice and data residency
AWS does not move customer content out of the Region the customer selected unless the customer does it (for example by setting up cross-Region replication) or it is needed to comply with law or a binding legal order. Tools such as service control policies in AWS Organizations can also deny actions outside approved Regions, which helps enforce a residency rule.
Note that global features, such as IAM, store some configuration data outside a single Region, but the content you put in S3 or DynamoDB stays in the Region you chose.
W: The company: choosing Regions for its resources is the customer's decision, and AWS keeps content in that Region unless the customer moves it, so meeting the EU residency rule is in the company's hands.
X: B=AWS balances data across continents: AWS does not relocate customer content between Regions for capacity reasons. Content stays where the customer put it.
C=AWS decides from the billing address: AWS does not interpret a customer's legal obligations or pick Regions for it. Understanding and meeting regulations is the customer's responsibility.
D=Regulator assigns a Region: regulators set rules, but they do not assign AWS Regions. The company must pick Regions that satisfy the rules.
T: Customers choose the Regions where their data lives, and AWS does not move content out of them without customer action, so data residency is a customer decision.
V: Amazon S3, Amazon DynamoDB, AWS Organizations

@ CLF-C02 D2 T2.1 applied comparison
S: A media company runs Kubernetes workloads on Amazon Elastic Kubernetes Service (Amazon EKS) with worker nodes that are EC2 instances in its own account. Which task is AWS's responsibility?
A: Operating, scaling and patching the Kubernetes control plane, including the API server and its etcd data store.
B: Updating the worker nodes to newer Amazon Machine Images (AMIs) that contain the latest operating system patches.
C: Configuring Kubernetes role-based access control so that each team can deploy only to its own namespaces.
D: Scanning the container images that the teams deploy for vulnerable libraries before they run in production.
K: A
G: ## Two halves of a Kubernetes cluster
- The **control plane** runs the Kubernetes API server, the scheduler and the `etcd` database that stores cluster state.
- The **data plane** is the set of worker nodes where pods (containers) actually run.
## How Amazon EKS splits the work
- **AWS**: runs the control plane across multiple Availability Zones, scales it, patches it and keeps it available. Customers cannot log in to control plane instances.

@ CLF-C02 D2 T2.1 applied use-case
S: A ride-sharing company stores trip records in Amazon DynamoDB. Which tasks does AWS handle for this table under the shared responsibility model? (Select TWO)
A: Patching and maintaining the servers and software that run the DynamoDB service.
B: Storing the table's data redundantly across multiple Availability Zones in the Region.
C: Writing IAM policies that limit which applications can read or write trip records.
D: Turning on point-in-time recovery so a table can be restored to an earlier second.
E: Deciding which trip record fields are personal data that need extra protection.
K: A,B
G: ## DynamoDB is a serverless database
Amazon DynamoDB has no servers for customers to see. AWS handles:
- The hardware, operating systems and database software, including patching.
- Partitioning and scaling the table.
- Storing data redundantly across multiple Availability Zones in the Region.
- Encryption at rest, which is always on (the customer can choose which kind of key to use).
## What the customer still controls
- **Access**: IAM policies, for example allowing an application to call `dynamodb:PutItem` only on one table.
- **Data protection features**: point-in-time recovery (PITR), on-demand backups and global tables are options the customer turns on.

W: A=Servers and software: DynamoDB is fully managed and serverless, so AWS patches and maintains everything that runs the service.

@ CLF-C02 D2 T2.1 advanced tradeoff
S: An Amazon EC2 instance at a logistics firm received a scheduled retirement event because AWS detected a problem with the underlying host hardware. Which statement correctly splits the responsibilities?
A: AWS repairs or retires the faulty hardware, and the firm is responsible for moving the workload and for designing it to tolerate instance failures.
B: AWS automatically moves the instance and all instance store data to healthy hardware, so the firm has no action to take before the event date.
C: The firm must open a ticket for an AWS engineer to replace the faulty host part, because hardware fixes start only after a customer request.
D: The firm must replace the faulty host part itself during its maintenance window, because EC2 hosts are part of the customer's infrastructure.
K: A
G: ## Hardware is AWS's, availability design is shared work
AWS owns the physical servers. When AWS detects a problem with a host, it can schedule an **instance retirement**, and the customer sees the event in the AWS Health Dashboard and in the EC2 console.
What the customer controls is how its workload reacts:
- Stopping and starting an EBS-backed instance moves it to healthy hardware. Data on **instance store** volumes is lost when that happens.
- Backups, such as EBS snapshots, are the customer's choice.
- A resilient architecture uses several instances across Availability Zones, for example behind a load balancer with Auto Scaling, so one host failure does not cause an outage.
## Why this matters
"AWS is responsible for the hardware" does not mean "AWS guarantees my application stays up". Resilience of the customer's workload is a customer design decision; AWS provides the building blocks.
W: Hardware versus workload design: AWS handles the faulty host, while the firm must act on the event and is responsible for backups and a multi-instance, multi-AZ design that survives a lost instance.
X: B=AWS moves everything automatically: if the firm does not act, AWS stops or terminates the instance at retirement, and instance store data does not survive the move to new hardware.
C=Customer requests the fix: AWS monitors and maintains its hardware on its own; the retirement notice shows AWS already found the problem.
D=Customer replaces host parts: customers never touch physical hosts. Hardware in AWS data centers is purely AWS's responsibility.
T: AWS fixes the hardware; the customer acts on events, backs up data and designs workloads to survive instance failures.
V: Amazon EC2, AWS Health Dashboard

@ CLF-C02 D2 T2.1 applied use-case
S: A hotel chain runs its booking database on Amazon RDS for PostgreSQL in a single Availability Zone. Management wants the database to keep running if that Availability Zone fails. How are the responsibilities divided?
A: The hotel chain must enable a Multi-AZ deployment, and AWS then keeps the standby updated and performs the failover automatically.
B: AWS must move every RDS database to a second Availability Zone on its own when a failure happens, without any customer setting.
C: The hotel chain must build its own replication between two RDS instances and write scripts that switch the application during a failure.
D: AWS must enable a Multi-AZ deployment for every production database, because availability of managed databases is never a customer setting.
K: A
G: ## Managed service, customer choices
With Amazon RDS, AWS runs the infrastructure and the database engine. But many protection features are **options the customer selects**, because they change cost and architecture:
- **Multi-AZ deployment**: RDS keeps a standby copy in another Availability Zone, replicates data synchronously and fails over automatically if the primary or its AZ fails.
- **Automated backups**: retention period chosen by the customer.
- **Encryption at rest**: chosen at creation.
## Who does what for Multi-AZ
- **Customer**: decides the database needs high availability and turns on Multi-AZ (at a higher cost).
- **AWS**: creates and maintains the standby, keeps replication running, detects failures and switches the DNS endpoint to the standby.
A single-AZ database stays single-AZ. AWS does not quietly upgrade it, because that changes the bill and the design.
W: Customer enables, AWS operates: the hotel chain decides to use Multi-AZ, and after that AWS handles the standby, replication and automatic failover.
X: B=AWS moves databases on its own: a single-AZ instance has no standby. Without Multi-AZ, recovery means restoring from backups, not an automatic move.
C=Build your own replication: RDS already provides Multi-AZ as a managed feature, so the hotel chain does not need to build replication or failover scripts.
D=AWS enables Multi-AZ for everyone: Multi-AZ is a customer setting with extra cost, not something AWS turns on for every database.
T: In managed services AWS operates the high-availability machinery, but the customer must choose to turn it on.
V: Amazon RDS
