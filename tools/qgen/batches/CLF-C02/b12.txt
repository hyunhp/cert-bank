# CLF-C02 D3 Cloud Technology and Services (24 questions: T3.5 network services x12, T3.6 storage services x12)

@ CLF-C02 D3 T3.5 applied use-case
S: An insurance company runs its claims database on Amazon EC2 instances in a private subnet. The instances must download operating system patches from the internet, but nothing on the internet may start a connection to them. What should the company add?
A: An internet gateway attached to the VPC, with the private subnet's route table sending `0.0.0.0/0` directly to that gateway.
B: A NAT gateway in a public subnet, with the private subnet's route table sending internet-bound traffic to that NAT gateway.
C: An egress-only internet gateway, with the private subnet's route table sending all IPv4 internet traffic through it.
D: A gateway VPC endpoint, with the private subnet's route table sending the patch repository traffic through the endpoint.
K: B
G: ## Outbound-only internet access for private subnets
Instances in a **private subnet** have no route to an internet gateway, which protects them from inbound connections. They often still need to reach the internet, for example to download patches.
- A **NAT gateway** is a managed AWS service placed in a **public subnet**. It has a public IP address (an Elastic IP).
- The private subnet's route table gets a route like `0.0.0.0/0 -> nat-0abc`.
- When an instance opens a connection, the NAT gateway forwards it to the internet using its own public address and sends the replies back. Connections that start on the internet cannot reach the instances.
## Related gateways
- **Internet gateway**: two-way internet access for subnets that route to it; this is what makes a subnet public.
- **Egress-only internet gateway**: the outbound-only idea, but for **IPv6** traffic only.
- **Gateway VPC endpoint**: private access to Amazon S3 or DynamoDB only, not to the general internet.
## Example
Database instances in `10.0.2.0/24` send patch downloads to the NAT gateway in the public subnet `10.0.1.0/24`, which sends them on through the internet gateway.
W: NAT gateway: it lets instances in the private subnet start outbound connections to the internet through a public subnet while blocking any connection that starts from the internet.
X: A=Internet gateway route: sending the private subnet's traffic straight to an internet gateway turns it into a public subnet, so instances with public IPs could be reached from the internet.
C=Egress-only internet gateway: it provides outbound-only access for IPv6 traffic only, so it does not handle the IPv4 patch downloads.
D=Gateway VPC endpoint: gateway endpoints reach only Amazon S3 and DynamoDB privately. They do not give access to patch servers on the public internet.
T: Private subnet needs outbound internet only = NAT gateway in a public subnet plus a route to it.
V: Amazon VPC, NAT gateway

@ CLF-C02 D3 T3.5 applied use-case
S: A streaming service has licensing deals that allow some films only in certain countries. It runs one copy of its site in Europe and another in North America, and every viewer in Germany must always be sent to the European copy. Which Amazon Route 53 routing policy should it use?
A: Latency-based routing, which answers each DNS query with the Region that gives the viewer the lowest measured network latency.
B: Weighted routing, which splits DNS answers between the two copies of the site in proportions that the administrator sets.
C: Geolocation routing, which answers each DNS query based on the country or continent from which the query originates.
D: Multivalue answer routing, which returns several healthy IP addresses at random so the client can choose any one of them.
K: C
G: ## Route 53 routing policies
Amazon Route 53 is AWS's DNS service. When a user types a domain name, Route 53 answers with an address. A **routing policy** decides which answer each user gets:
- **Simple**: one answer for everyone.
- **Weighted**: split traffic by percentages, for example 90/10 for testing a new version.
- **Latency-based**: send each user to the Region with the lowest latency for them.
- **Failover**: send everyone to a primary site and switch to a standby when a health check fails.
- **Geolocation**: answer based on where the user is (country, continent or US state).
- **Multivalue answer**: return several healthy addresses.
## Why location matters for licensing
Latency usually sends German users to Europe, but not always: network conditions change, and the policy optimizes speed, not borders. When a contract or law depends on the user's country, geolocation routing gives a guaranteed, rule-based answer.
W: Geolocation routing: it chooses the answer from the location the DNS query comes from, so every query from Germany can be mapped to the European copy of the site, as the licensing rules require.
X: A=Latency-based routing: it picks the fastest Region for each user. That is usually Europe for German viewers but is not guaranteed, so it cannot enforce country-based licensing.
B=Weighted routing: it splits traffic by fixed percentages without regard to where the viewer is, so German viewers would sometimes reach the North American copy.
D=Multivalue answer routing: it returns several healthy addresses for availability, with no control over which country is sent to which copy.
T: Route users by their country or continent (licensing, legal rules, localization) = Route 53 geolocation routing.
V: Amazon Route 53

@ CLF-C02 D3 T3.5 applied use-case
S: A travel agency runs its booking site in one AWS Region and keeps a static "we will be back soon" page in Amazon S3 in another Region. When the main site stops responding, users should be sent to the backup page automatically. Which Route 53 feature meets this need?
A: Failover routing with a health check on the main site, so DNS answers switch to the backup page when the check fails.
B: Weighted routing with equal weights on both records, so half of all users always reach the backup page during normal operation.
C: Simple routing with both addresses in one record, so client browsers pick one of them at random each time they connect.
D: Geoproximity routing with a bias toward the main site, so users are drawn to whichever site lies closest to their location.
K: A
G: ## Active-passive failover with Route 53
Route 53 can check the health of an endpoint by sending it requests from many locations. A **health check** is marked unhealthy when the endpoint stops answering correctly.
**Failover routing** uses two records for the same name:
- a **primary** record (the main site), returned while its health check is healthy;
- a **secondary** record (the backup), returned only when the primary is unhealthy.
## Example
`book.example.com` normally points to the load balancer in the main Region. When the health check fails, Route 53 starts answering with the S3 static website instead, with no manual change. When the main site recovers, answers switch back.
This is an **active-passive** design: the backup receives no traffic until it is needed.
W: Failover routing with a health check: Route 53 returns the main site while it is healthy and automatically returns the backup page once the health check marks the main site as failed.
X: B=Weighted routing with equal weights: it would send half of all users to the static backup page even when the main site is working perfectly.
C=Simple routing with two addresses: simple routing does not use health checks, so users can still be sent to the failed site.
D=Geoproximity routing: it routes by the distance between users and resources, not by whether the main site is healthy, so it does not provide failover to a standby page.
T: Send traffic to a standby only when the primary fails = Route 53 failover routing with health checks.
V: Amazon Route 53

@ CLF-C02 D3 T3.5 applied comparison
S: An online multiplayer game uses UDP and runs on servers in two AWS Regions. Players' home routers and corporate firewalls must allow a fixed set of IP addresses, and traffic should move to the healthy Region within seconds if one fails. Which service fits best?
A: Amazon CloudFront, which caches game assets at edge locations and serves each player's HTTP requests from a nearby location.
B: Amazon Route 53 latency-based routing, which returns DNS answers that point each player to the closest Region it measures.
C: Elastic Load Balancing with an Application Load Balancer, which spreads HTTP and HTTPS requests over targets in one Region.
D: AWS Global Accelerator, which gives two static anycast IP addresses and routes TCP and UDP traffic to healthy Regional endpoints.
K: D
G: ## What AWS Global Accelerator does
Global Accelerator gives an application **two static anycast IP addresses**. The same addresses are announced from AWS edge locations worldwide.
- A player's traffic enters the AWS network at the nearest edge location and then travels over the AWS global network, which is usually faster and more stable than the public internet.
- It works for **TCP and UDP**, so it suits games, voice and IoT, not just websites.
- It checks the health of endpoints (for example load balancers or instances in two Regions) and shifts traffic to a healthy Region within seconds, without waiting for DNS caches to expire.
- Because the IP addresses never change, they can be put on allow lists.
## Global Accelerator compared with CloudFront
- **CloudFront** caches HTTP(S) content at the edge.
- **Global Accelerator** does not cache; it speeds up and protects the network path for any TCP/UDP application.
W: Global Accelerator: it provides fixed anycast IP addresses that firewalls can allow, supports UDP traffic, and moves traffic between Regional endpoints based on health checks in seconds.
X: A=CloudFront: it caches and delivers HTTP(S) content. It does not carry the game's UDP traffic to game servers or shift that traffic between Regions based on server health.
B=Route 53 latency-based routing: it works through DNS answers, so the IP addresses behind the name can change, and failover waits for clients' cached DNS answers to expire.
C=Application Load Balancer: it handles HTTP and HTTPS in a single Region. It cannot balance UDP traffic or fail over between Regions.
T: Static IPs, TCP/UDP, fast multi-Region failover over the AWS network = AWS Global Accelerator.
V: AWS Global Accelerator

@ CLF-C02 D3 T3.5 applied tradeoff
S: A retail group has 35 VPCs across several accounts in one Region and a Site-to-Site VPN to its head office. Managing dozens of one-to-one connections between VPCs has become error-prone. It wants one central hub that connects all VPCs and the VPN. Which service fits best?
A: VPC peering, which creates a private connection between two VPCs and must be set up separately for every pair that talks.
B: AWS Transit Gateway, which acts as a regional hub that VPCs and VPN connections attach to and route traffic through.
C: AWS PrivateLink, which exposes one specific service in a VPC to consumers through interface endpoints in their own VPCs.
D: An internet gateway, which connects each VPC to the internet so the VPCs and the office can reach each other over the internet.
K: B
G: ## Connecting many networks
- **VPC peering** links exactly two VPCs. It is simple and cheap for a few VPCs, but it is **not transitive**, so every pair that must talk needs its own peering connection. With 35 VPCs, a full mesh would need hundreds of connections and route table entries.
- **AWS Transit Gateway** is a **hub-and-spoke** router. Each VPC, VPN connection or Direct Connect gateway attaches once to the hub, and route tables on the transit gateway decide who can reach whom.
## Example
35 VPCs + 1 VPN = 36 attachments to one transit gateway, instead of 595 peering connections for a full mesh of 35 VPCs (35 x 34 / 2) plus separate VPN connections to each VPC.
## When peering is still fine
Two or three VPCs that need to talk to each other, with no on-premises connection to share: peering is simpler and has no hourly attachment charge.
W: Transit Gateway: every VPC and the VPN attach once to the same regional hub, which replaces the mesh of one-to-one connections and centralizes routing.
X: A=VPC peering: this is the approach that has become unmanageable. Peering connects only two VPCs at a time, is not transitive, and cannot carry the head office VPN traffic between VPCs.
C=PrivateLink: it publishes a single service to consumers, not full network routing between whole VPCs and an on-premises network.
D=Internet gateway: it sends traffic over the public internet, which does not create a private, centrally routed network between the VPCs and the office.
T: Many VPCs plus on-premises networks through one central hub = AWS Transit Gateway; a few VPC pairs = VPC peering.
V: AWS Transit Gateway, VPC peering

@ CLF-C02 D3 T3.5 applied troubleshooting
S: A university connects its research VPC to a shared-services VPC with VPC peering, and the shared-services VPC is also peered with a library VPC. Researchers find that instances in the research VPC cannot reach the library VPC. What is the reason?
A: VPC peering connections work only between VPCs in the same AWS account, so the library VPC must be moved into the research account.
B: VPC peering is not transitive, so traffic cannot pass through the shared-services VPC to reach a VPC peered only with it.
C: VPC peering carries only IPv6 traffic between VPCs, so the IPv4 instances in each VPC must first be given IPv6 addresses.
D: VPC peering requires an internet gateway in every VPC involved, and the shared-services VPC does not have one attached yet.
K: B
G: ## VPC peering basics
A **VPC peering connection** links two VPCs so their instances can talk using private IP addresses, as if they were on the same network.
- The VPCs can be in the same or different AWS accounts, and in the same or different Regions.
- Their IP address ranges must not overlap.
- Traffic stays on the AWS network; no internet gateway is needed.
## No transitive routing
Peering connects exactly two VPCs. If A is peered with B and B is peered with C, A **cannot** reach C through B.
Example: research `10.1.0.0/16` <-> shared `10.2.0.0/16` <-> library `10.3.0.0/16`. Research and library are not connected.
## Fixes
- Create a direct peering connection between the research and library VPCs, or
- Use **AWS Transit Gateway**, which does route between everything attached to it.
W: Not transitive: each peering connection links only its two VPCs, so the shared-services VPC cannot pass traffic on from the research VPC to the library VPC.
X: A=Same account only: peering works across AWS accounts (and Regions), so the accounts are not the cause.
C=IPv6 only: peering carries IPv4 and IPv6 traffic between private addresses, so no IPv6 change is needed.
D=Internet gateway required: peering traffic goes directly between the VPCs over the AWS network and does not use internet gateways.
T: VPC peering is one-to-one and not transitive; use a direct peering or Transit Gateway for more VPCs.
V: VPC peering

@ CLF-C02 D3 T3.5 applied use-case
S: A logistics company runs batch jobs on EC2 instances in a private subnet. The jobs read and write large files in Amazon S3. The company wants this traffic to stay on the AWS network without going through a NAT gateway or the internet. What should it use?
A: A gateway VPC endpoint for Amazon S3, added as a target in the private subnet's route table for S3 traffic.
B: An internet gateway attached to the VPC, with S3 traffic from the private subnet routed through it directly.
C: AWS Direct Connect, ordered from the VPC to a Direct Connect location close to the AWS Region of the S3 bucket.
D: S3 Transfer Acceleration, enabled on the bucket so uploads enter AWS through the nearest CloudFront edge location.
K: A
G: ## VPC endpoints
A **VPC endpoint** lets resources in a VPC reach an AWS service privately, without an internet gateway, NAT gateway or public IP address. There are two main kinds:
- **Gateway endpoints**: for **Amazon S3 and Amazon DynamoDB** only. You add the endpoint as a target in a route table. There is no extra charge for gateway endpoints.
- **Interface endpoints** (powered by **AWS PrivateLink**): an elastic network interface with a private IP in your subnet for many AWS services and partner services. These are billed per hour and per GB.
## Why it helps here
Without an endpoint, the private instances would reach S3 through a NAT gateway, which charges for every GB it processes. With a gateway endpoint, S3 traffic goes straight from the VPC to S3 on the AWS network.
W: Gateway VPC endpoint for S3: it gives the private subnet a route to S3 that stays on the AWS network, needs no NAT gateway or internet path, and has no added charge.
X: B=Internet gateway: routing the private subnet to an internet gateway makes it public and sends the traffic out the internet path the company wants to avoid.
C=Direct Connect: it links an on-premises network to AWS. It is not used to connect a VPC to a service in the same Region.
D=Transfer Acceleration: it speeds up uploads from distant clients over the internet via edge locations, the opposite of keeping VPC traffic off the internet.
T: Private access from a VPC to S3 or DynamoDB without NAT or internet = gateway VPC endpoint.
V: Amazon VPC, Amazon S3

@ CLF-C02 D3 T3.5 advanced use-case
S: A payments SaaS provider wants hundreds of customers to call its API from their own VPCs using private IP addresses. It must not open its VPC to customers' networks or deal with overlapping IP ranges. Which AWS capability is designed for this?
A: VPC peering between the provider's VPC and each customer's VPC, with routes to the API servers added on both sides.
B: AWS Transit Gateway shared with every customer account, with each customer VPC attached to the provider's hub.
C: AWS PrivateLink, with the API published as an endpoint service that customers reach through interface endpoints.
D: AWS Site-to-Site VPN from each customer VPC to the provider's VPC, with tunnels terminated on a virtual private gateway.
K: C
G: ## Sharing one service privately: AWS PrivateLink
PrivateLink connects a **consumer** to a single **service**, not one network to another.
- The provider puts the service behind a load balancer (usually a Network Load Balancer) and creates an **endpoint service**.
- Each consumer creates an **interface VPC endpoint** in its own VPC. It appears as a network interface with a private IP address from the consumer's subnet.
- Traffic flows only from consumer to service, over the AWS network. The two VPCs are not routed together, so overlapping CIDR ranges do not matter.
## Compared with network-level connections
- **VPC peering** and **Transit Gateway** join whole networks: every peer can potentially reach every address, and IP ranges must not overlap.
- PrivateLink exposes **one service** only, which is why SaaS providers and AWS services (through interface endpoints) use it.
W: PrivateLink: customers reach the API through interface endpoints in their own VPCs, with no network routing between the VPCs, so the provider's VPC stays closed and overlapping ranges are not a problem.
X: A=VPC peering: it joins whole networks, fails when CIDR ranges overlap, and would mean hundreds of peering connections and route updates.
B=Transit Gateway: it also routes whole networks together and needs non-overlapping ranges, exposing more than the single API.
D=Site-to-Site VPN: each tunnel connects networks, not a single service, and also requires non-overlapping address ranges and per-customer tunnel management.
T: Expose one service privately to many VPCs, even with overlapping IPs = AWS PrivateLink (endpoint service + interface endpoints).
V: AWS PrivateLink

@ CLF-C02 D3 T3.5 applied use-case
S: A logistics company runs an SFTP server on one EC2 instance in a public subnet. A partner's firewall accepts only IP addresses, but the server's public IPv4 address changes whenever the instance is stopped and started. What is the simplest fix?
A: Allocate an Elastic IP address and associate it with the instance, so the same public IPv4 address stays with it across stops and starts.
B: Turn on auto-assign public IPv4 for the subnet, so the instance receives the same public address from AWS each time it is started.
C: Place a NAT gateway in the public subnet, so the partner's connections arrive at the instance through the NAT gateway's fixed address.
D: Create a Route 53 record for the instance, so the partner's firewall rule can use the server's domain name instead of its address.
K: A
G: ## Public IPv4 addresses on EC2
An instance in a public subnet can get an **auto-assigned public IPv4 address** from Amazon's pool. That address is not yours:
- it is released when the instance is stopped, hibernated or terminated;
- a new, different address is assigned at the next start.
An **Elastic IP address** is a static public IPv4 address that you allocate to your account:
- you associate it with an instance (or network interface), and it stays there across stop and start;
- you can move it to a replacement instance, so partners and allow lists never need to change;
- it remains yours until you release it. Like all public IPv4 addresses on AWS, it is billed per hour.
## Example
The Elastic IP address `203.0.113.25` is associated with the SFTP instance. The partner allows `203.0.113.25/32` once. After a stop and start, or even after the instance is replaced, the address is the same.
## Related ideas
- A **NAT gateway** also uses an Elastic IP, but only for outbound connections from private subnets; it never accepts inbound connections.
- **DNS names** (Route 53) help users, but a firewall that accepts only IP addresses still needs a fixed address.
W: Elastic IP address: it is a static public IPv4 address owned by the account, so it stays associated with the instance through every stop and start and the partner's allow list keeps working.
X: B=Auto-assign public IPv4: auto-assigned addresses come from Amazon's shared pool and are replaced by a different address after each stop and start, which is the problem the company already has.
C=NAT gateway: it lets private instances start outbound connections. It does not accept connections that start on the internet, so the partner could not reach the SFTP server through it.
D=Route 53 record: a DNS name does not help a firewall that accepts only IP addresses, and the record itself would still have to be updated whenever the address changed.
T: A public IPv4 address that must never change for an EC2 instance = Elastic IP address.
V: Amazon EC2, Elastic IP address

@ CLF-C02 D3 T3.5 applied troubleshooting
S: A developer launches a web server on EC2 in a public subnet whose route table already sends `0.0.0.0/0` to an internet gateway, but users cannot load the site over HTTPS from the internet. Which TWO issues could cause this? (Select TWO)
A: The instance has no public IPv4 address or Elastic IP address, so the internet has no address it can use to reach it.
B: The subnet has no NAT gateway, which every instance needs before it can accept connections arriving from the internet.
C: The instance's security group has no inbound rule that allows TCP port 443 from the internet address range.
D: The VPC has no gateway endpoint for Amazon S3, which is required for any instance to answer requests on the internet.
E: The instance is not registered in AWS Transit Gateway, which provides the path between public subnets and the internet.
K: A,C
G: ## What an instance needs to be reachable from the internet
Think of it as a checklist; every item must be true:
- **Route**: the subnet's route table sends `0.0.0.0/0` to an **internet gateway** (here already done).
- **Address**: the instance has a **public IPv4 address** or an **Elastic IP address**. A private address such as `10.0.1.25` cannot be reached from the internet.
- **Security group**: an inbound rule allows the traffic, for example TCP `443` from `0.0.0.0/0`. Security groups deny all inbound traffic by default.
- **Network ACL**: the subnet's ACL allows the traffic in and the replies out (the default ACL allows everything).
## What is not needed
- A **NAT gateway** only provides outbound access for private subnets; it never accepts inbound connections.
- **VPC endpoints** and **Transit Gateway** connect to AWS services or other networks, not to internet users.
W: A=No public IP address: without a public IPv4 or Elastic IP address, the instance has only a private address that internet users cannot reach, even in a public subnet.
C=No inbound rule for 443: security groups deny inbound traffic unless a rule allows it, so HTTPS requests are dropped at the instance.
X: B=Missing NAT gateway: a NAT gateway gives private instances outbound access only. Instances in a public subnet accept internet traffic through the internet gateway without one.
D=Missing S3 gateway endpoint: a gateway endpoint provides private access to S3 and has nothing to do with serving web requests from internet users.
E=Not attached to Transit Gateway: Transit Gateway connects VPCs and on-premises networks; internet access for a public subnet comes from the internet gateway.
T: Internet-reachable instance = route to internet gateway + public IP + security group (and network ACL) rule allowing the traffic.
V: Amazon VPC, Amazon EC2

@ CLF-C02 D3 T3.5 applied definition
S: A startup that is new to AWS asks what Amazon Route 53 can do for its website, beyond answering DNS queries for its domain. Which TWO capabilities does Route 53 provide? (Select TWO)
A: Registering new domain names, such as the startup's own .com name, and renewing them, all from within the AWS account.
B: Caching copies of the website's images and pages at edge locations so that distant visitors receive them faster.
C: Checking the health of the website's endpoints and sending DNS answers only to endpoints that are currently healthy.
D: Issuing and renewing public TLS certificates for the domain so that the website can serve its pages over HTTPS.
E: Inspecting web requests and blocking SQL injection and cross-site scripting attempts before they reach the website.
K: A,C
G: ## What Amazon Route 53 is
Route 53 is AWS's highly available **Domain Name System (DNS)** service. It has three main jobs:
- **Domain registration**: buy and renew domain names such as `example.com` directly in AWS.
- **DNS routing**: host the domain's records (in a **hosted zone**) and answer queries, for example `www.example.com -> the load balancer`. Routing policies (simple, weighted, latency, failover, geolocation and others) decide which answer each user gets.
- **Health checks**: test endpoints from many locations and stop returning unhealthy ones, which enables automatic failover.
## Services that are often confused with it
- **Amazon CloudFront** caches content at edge locations.
- **AWS Certificate Manager (ACM)** issues and renews public TLS certificates.
- **AWS WAF** filters malicious web requests such as SQL injection.
## Example
A startup registers `shopnow.com` in Route 53, points `www` at its load balancer, and adds a health check so a backup site is returned if the main site fails.
W: A=Domain registration: Route 53 is also a domain registrar, so the startup can register and renew its domain name in the same AWS account.
C=Health checks: Route 53 monitors endpoints and, combined with routing policies such as failover, returns only healthy endpoints in its DNS answers.
X: B=Edge caching: caching content at edge locations is the job of Amazon CloudFront, not of a DNS service.
D=TLS certificates: public certificates are issued and renewed by AWS Certificate Manager; Route 53 can hold the DNS record ACM uses for validation but does not issue certificates.
E=Blocking SQL injection: inspecting request contents is done by AWS WAF. DNS only answers which address to connect to and never sees the web requests.
T: Route 53 = domain registration + DNS routing + health checks; caching is CloudFront, certificates are ACM, request filtering is WAF.
V: Amazon Route 53

@ CLF-C02 D3 T3.5 applied use-case
S: A recipe website runs on EC2 instances behind an Application Load Balancer in one Region. Its pages, photos and videos are viewed worldwide. The company plans to put Amazon CloudFront in front of the load balancer. Which TWO benefits will this bring? (Select TWO)
A: The website's EC2 instances and database will be copied automatically to every AWS Region where viewers are located.
B: Photos and videos will be stored permanently at the edge, so the copies at the origin can be deleted to cut storage costs.
C: Cached copies of photos and videos at edge locations will let distant viewers load them with lower latency.
D: Requests answered from the edge caches will no longer reach the load balancer and instances, which reduces their load.
E: The VPC will no longer need security groups, because CloudFront filters every request before it can reach the instances.
K: C,D
G: ## What a CDN in front of a website changes
**Amazon CloudFront** sits between viewers and the **origin** (here the Application Load Balancer). Viewers connect to the nearest of hundreds of **edge locations**.
- For content that can be cached (photos, videos, CSS, often whole pages for a while), the edge location keeps a copy. Later viewers nearby get it from the edge, which cuts latency.
- Every cache hit is a request the origin does not have to serve, so the load balancer, instances and database handle less traffic, which can also lower costs.
- Dynamic requests that cannot be cached still travel from the edge to the origin over the AWS network.
- CloudFront also includes AWS Shield Standard DDoS protection at the edge and can work with AWS WAF.
## What CloudFront does not do
- It does not copy the application or database to other Regions.
- It does not store content permanently: edge copies expire or are evicted, and every cache miss is fetched again from the origin.
- It does not replace security groups or network ACLs in the VPC.
W: C=Edge caching for lower latency: photos and videos are served from edge locations near the viewers, so pages load faster around the world.
D=Less load on the origin: every request answered from an edge cache never reaches the load balancer and instances, so the origin serves less traffic.
X: A=Copies the application to every Region: CloudFront caches responses at the edge; the instances and database stay in their one Region unless the company deploys them elsewhere.
B=Permanent storage at the edge: edge caches hold temporary copies that expire or are evicted. The origin must keep the content, because CloudFront fetches it from there on every cache miss.
E=No more security groups: security groups still protect the instances inside the VPC. CloudFront adds edge protection but does not replace VPC controls.
T: CloudFront in front of an origin = lower latency for viewers worldwide and fewer requests hitting the origin.
V: Amazon CloudFront, Elastic Load Balancing

@ CLF-C02 D3 T3.6 applied troubleshooting
S: A data analyst stored intermediate results on the local disk of an EC2 instance. After the instance was stopped overnight to save costs and started again, the files were gone, although the boot volume was intact. What is the most likely explanation?
A: The files were on an Amazon EBS volume, and EBS volumes are erased each time the instance that they are attached to is stopped.
B: The files were in Amazon S3, and S3 removes objects automatically when the instance that uploaded them is stopped.
C: The files were on an Amazon EFS file system, and EFS deletes files when the last instance that mounted it is stopped.
D: The files were on an instance store volume, which loses its data when the instance is stopped, hibernated or terminated.
K: D
G: ## Instance store: fast but temporary
Some EC2 instance types come with **instance store** volumes: disks physically attached to the host server that runs the instance.
- They are very fast and are included in the instance price.
- The data lives only as long as the instance runs on that host. It **survives a reboot**, but is **lost when the instance is stopped, hibernated or terminated**, or if the underlying disk fails. After a stop and start, the instance usually lands on a different host.
- Good uses: caches, buffers, scratch space, and data that is replicated elsewhere.
## Persistent options
- **Amazon EBS** volumes keep their data across stop and start (the boot volume in this scenario is an example).
- **Amazon S3** and **Amazon EFS** keep data until someone deletes it, regardless of any instance.
W: Instance store: it is temporary storage on the host's own disks, so stopping the instance released those disks and the intermediate files with them, while the EBS boot volume kept its data.
X: A=EBS volume erased on stop: EBS volumes persist independently of the instance's running state; the intact boot volume itself shows that.
B=S3 removes objects: objects in S3 stay until they are deleted or expired by a lifecycle rule; they are not tied to any instance.
C=EFS deletes files: an EFS file system keeps its data whether or not any instance has it mounted.
T: Data that disappears after stop/start lived on instance store; use EBS, EFS or S3 for data that must persist.
V: Amazon EC2 instance store, Amazon EBS

@ CLF-C02 D3 T3.6 applied use-case
S: An engineer needs to move the data on an Amazon EBS volume in Availability Zone A to a new EC2 instance in Availability Zone B of the same Region. EBS volumes cannot be attached across zones. What is the standard way to do this?
A: Create a snapshot of the volume, then create a new volume from that snapshot in Availability Zone B and attach it there.
B: Turn on EBS Multi-Attach for the volume, so the instance in Availability Zone B can mount it alongside the original one.
C: Enable S3 Cross-Region Replication on the volume, so its blocks are copied automatically to Availability Zone B.
D: Change the volume's Availability Zone setting in the console, which moves the volume while it stays attached to the instance.
K: A
G: ## EBS volumes are zonal, snapshots are regional
An EBS volume exists in one Availability Zone and can attach only to instances in that zone. An **EBS snapshot** is a point-in-time copy of the volume, stored by AWS in Amazon S3 and available across the whole Region.
## Typical uses of snapshots
- **Backup and restore**: take snapshots on a schedule; restore by creating a volume from one.
- **Move between AZs**: create a volume from the snapshot in any AZ of the same Region.
- **Move between Regions or accounts**: copy or share the snapshot, then create a volume there.
Snapshots are **incremental**: after the first full copy, only changed blocks are stored, which keeps costs down.
## Example
Snapshot `vol-0a1` in `us-east-1a` -> `snap-0b2` -> create `vol-0c3` from it in `us-east-1b` -> attach to the new instance.
W: Snapshot and restore: a snapshot is regional, so a new volume created from it can be placed in Availability Zone B and attached to the new instance with the same data.
X: B=Multi-Attach: it lets some volume types attach to several instances in the same Availability Zone only, so it cannot reach an instance in another zone.
C=Cross-Region Replication: it is a feature of S3 buckets that copies objects between buckets, not a way to copy EBS volumes between zones.
D=Change the zone setting: a volume's Availability Zone is fixed when it is created; there is no setting that moves it to another zone.
T: Move or copy EBS data to another AZ (or Region) = snapshot, then create a new volume from it.
V: Amazon EBS

@ CLF-C02 D3 T3.6 applied use-case
S: A media company writes application logs to Amazon S3. Logs are read often in the first 30 days, rarely for the next year, and must then be deleted. The company wants this handled automatically without moving objects by hand. What should it configure?
A: S3 Versioning on the bucket, which keeps every earlier version of each log and removes older versions after one year.
B: An S3 Lifecycle configuration that transitions logs to a cheaper storage class after 30 days and expires them later.
C: S3 Cross-Region Replication to a second bucket, which stores the replicated logs in a cheaper Region after 30 days.
D: S3 Transfer Acceleration on the bucket, which uploads new logs through edge locations to reduce the cost of storing them.
K: B
G: ## S3 Lifecycle configuration
A lifecycle configuration is a set of rules on a bucket (optionally filtered by prefix or tag) with two kinds of actions:
- **Transition actions** move objects to another storage class after a number of days, for example from S3 Standard to S3 Standard-IA or to an S3 Glacier storage class.
- **Expiration actions** delete objects after a number of days.
## Example rule for these logs
- Day 0-30: S3 Standard (frequent reads, no retrieval fees).
- Day 30: transition to S3 Standard-IA or S3 Glacier Instant Retrieval (cheaper storage, rare reads).
- Day 395: expire (delete).
## Lifecycle rules versus Intelligent-Tiering
Lifecycle rules work best when the access pattern is **known and age-based**, as here. When the pattern is unknown, S3 Intelligent-Tiering moves each object based on real access instead.
W: Lifecycle configuration: its transition action moves logs to a cheaper class once they are rarely read, and its expiration action deletes them when the retention period ends, all automatically by object age.
X: A=Versioning: it keeps older copies of objects that are overwritten or deleted. It does not change storage classes for current objects and would increase storage, not reduce it.
C=Cross-Region Replication: it copies every log to another bucket, which doubles storage. Replication is for compliance and disaster recovery, not age-based cost reduction.
D=Transfer Acceleration: it speeds up uploads from distant clients and adds a per-GB charge. It has no effect on storage class or deletion.
T: Known, age-based access pattern in S3 = lifecycle rules (transition to cheaper classes, then expire).
V: Amazon S3

@ CLF-C02 D3 T3.6 applied use-case
S: Employees of an architecture firm sometimes overwrite or delete drawings stored in an Amazon S3 bucket by mistake. The firm wants to be able to restore the earlier version of any drawing after such an accident. Which S3 feature should it enable?
A: S3 Transfer Acceleration, which routes each upload through an edge location so that the drawings arrive at the bucket faster.
B: S3 Intelligent-Tiering, which moves each drawing between access tiers automatically depending on how often it is read.
C: S3 Versioning, which keeps every version of an object so an earlier version can be retrieved after an overwrite or delete.
D: S3 Inventory, which produces a scheduled report listing the objects in the bucket together with their size and metadata.
K: C
G: ## How S3 Versioning works
With versioning **enabled** on a bucket, S3 keeps every version of every object:
- Uploading `plan.dwg` again does not replace the old file; it adds a new version and keeps the old one with its own **version ID**.
- Deleting an object without a version ID only adds a **delete marker**. The object looks deleted, but its earlier versions remain and can be restored by removing the marker or copying an old version back.
## Things to know
- Once enabled, versioning can be suspended but not turned off.
- Every stored version is billed, so it is common to add a lifecycle rule that expires **noncurrent versions** after, for example, 90 days.
- Versioning is required for S3 replication and S3 Object Lock.
W: Versioning: overwrites create new versions and deletes create delete markers, so the previous version of any drawing stays in the bucket and can be restored.
X: A=Transfer Acceleration: it speeds up uploads over long distances but keeps no earlier copy of an overwritten or deleted drawing.
B=Intelligent-Tiering: it reduces storage cost by moving objects between tiers based on access; an overwrite still replaces the object.
D=S3 Inventory: it reports what objects exist and their metadata. It is a listing, not a copy of earlier versions that can be restored.
T: Recover from accidental overwrite or deletion in S3 = enable S3 Versioning (and manage old versions with lifecycle rules).
V: Amazon S3

@ CLF-C02 D3 T3.6 applied tradeoff
S: A bank must keep scanned loan documents for ten years for regulators. The documents are almost never read, and if an auditor requests one, waiting up to 48 hours is acceptable. The bank wants the lowest possible storage cost in Amazon S3. Which storage class fits best?
A: S3 Glacier Instant Retrieval, which offers low-cost archive storage with retrieval in milliseconds for data read about once a quarter.
B: S3 Standard-Infrequent Access, which offers lower-cost storage with millisecond access for data read less than once a month.
C: S3 Glacier Flexible Retrieval, which offers archive storage with restores that complete in minutes to hours after a request.
D: S3 Glacier Deep Archive, which offers the lowest-cost S3 storage for long-term archives restored within about 12 to 48 hours.
K: D
G: ## The S3 Glacier storage classes
All three Glacier classes are storage classes inside S3, used for archives. They differ in how fast data comes back and what it costs to store:
- **S3 Glacier Instant Retrieval**: milliseconds access, for archives read about once a quarter.
- **S3 Glacier Flexible Retrieval**: a **restore** request is needed; data comes back in minutes to hours.
- **S3 Glacier Deep Archive**: the **lowest storage price in S3**; restores take within 12 hours (standard) or up to 48 hours (bulk). Designed for data kept 7-10 years or more for compliance.
## The trade-off
The cheaper the storage, the slower and the more expensive the access. Archive classes also have minimum storage durations, which is no problem for data kept ten years.
## Example
Ten years of loan scans that an auditor might request a few times a year: Deep Archive, with a restore requested when needed.
W: Glacier Deep Archive: it has the lowest storage price of any S3 class and is designed for long-term regulatory archives, and its restore time fits the 48-hour tolerance.
X: A=Glacier Instant Retrieval: millisecond access costs more per GB stored than Deep Archive, and the bank does not need instant access.
B=Standard-IA: it is meant for data read occasionally with instant access, and its storage price is far higher than an archive class.
C=Glacier Flexible Retrieval: it restores faster than needed but stores data at a higher price than Deep Archive, so it is not the lowest-cost choice.
T: Long-term compliance archives with hours-to-days retrieval acceptable = S3 Glacier Deep Archive (lowest S3 storage cost).
V: Amazon S3, S3 Glacier Deep Archive

@ CLF-C02 D3 T3.6 applied comparison
S: A radiology clinic keeps older X-ray images in Amazon S3. Each image is opened only a few times a year, but when a doctor needs one it must appear in milliseconds. The data must survive the loss of an Availability Zone. Which storage class is most cost-effective?
A: S3 Glacier Flexible Retrieval, which charges less to store the images but returns each one only after a restore job finishes.
B: S3 Glacier Instant Retrieval, which charges a low archive storage price yet returns each image in milliseconds when read.
C: S3 One Zone-Infrequent Access, which charges less to store the images by keeping a single copy set in one Availability Zone.

G: ## Archive data that still needs instant access
Some data is cold (rarely read) but cannot wait for a restore when it is needed: medical images, news photo archives, user-generated content from past years.

@ CLF-C02 D3 T3.6 applied definition
S: A team that is new to AWS is comparing Amazon EBS with Amazon S3 for a project. Which TWO statements correctly describe Amazon EBS? (Select TWO)
A: An EBS volume is created in one Availability Zone and is attached to EC2 instances in that same zone.
B: An EBS volume is reached directly from any web browser through a unique HTTPS URL for each stored file.
C: An EBS volume keeps its data when the instance it is attached to is stopped, because it persists separately.
D: An EBS volume automatically keeps copies in every AWS Region so the data survives the loss of a whole Region.
E: An EBS volume grows and shrinks automatically as files are written and deleted, with no size set in advance.
K: A,C
G: ## Amazon EBS in a few facts
- **Block storage** for EC2: the operating system sees a volume as a disk, formats it with a file system and reads or writes individual blocks.
- **Zonal**: a volume lives in one Availability Zone and is replicated within that zone to protect against hardware failure. It attaches to instances in the same zone.
- **Persistent**: its lifetime is independent of the instance. It survives stop and start, and it can be detached and attached to another instance.
- **Provisioned size**: you choose the size (and for some types the performance) when you create the volume and pay for what you provision. You can increase it later, but it does not grow by itself.
- **Backups**: snapshots, which can be copied to other Regions when you choose to.
## Compared with S3
Amazon S3 is object storage: virtually unlimited, pay for what you store, data spread across multiple AZs in a Region, and each object reached through an API or HTTPS URL.
W: A=Zonal: an EBS volume is created in a specific Availability Zone and can only be attached to instances in that zone.
C=Persistent: EBS volumes exist independently of the instance, so their data stays intact when the instance is stopped and started again.
X: B=HTTPS URL per file: that describes objects in Amazon S3. An EBS volume is a disk attached to an instance, not something browsers access over HTTPS.
D=Copies in every Region: EBS replicates data within one Availability Zone. Copies in other Regions exist only if you copy snapshots there yourself.
E=Grows and shrinks automatically: that describes Amazon EFS or S3. You provision an EBS volume's size and pay for it whether it is full or not.
T: EBS = zonal, persistent, provisioned block storage for EC2; S3 = regional object storage accessed by API.
V: Amazon EBS, Amazon S3

@ CLF-C02 D3 T3.6 applied definition
S: A marketing agency plans to store campaign images and videos in Amazon S3. Its staff are used to traditional file servers. Which TWO statements about Amazon S3 are correct? (Select TWO)
A: Each bucket must be given a fixed storage capacity when it is created, and the bucket rejects uploads once that capacity is full.
B: Data is stored as objects in buckets, and each object is identified by a key and holds the data together with its metadata.

G: ## Object storage, the S3 way
- A **bucket** is a container for objects, created in one AWS Region.
- An **object** is the data (a file of any type) plus **metadata**, identified by a **key** such as `campaigns/2026/spring/hero.jpg`. The slashes only look like folders; the namespace is flat.
- Applications use the S3 **API** (or HTTPS) to put, get, list and delete whole objects.

## What S3 is not
- It is not a block device: you cannot boot an instance from a bucket or format it with a file system (that is Amazon EBS).
- Objects are not edited in place: to change an object, you upload a new version of the whole object.
## Example

E=Virtually unlimited, pay for use: S3 needs no capacity planning; the agency is billed for what it stores, not for space reserved in advance.
X: A=Fixed capacity per bucket: S3 buckets have no provisioned size and do not fill up, so no capacity is set at creation.
C=Mounted as a boot disk: block devices used as boot volumes are Amazon EBS or instance store. S3 is accessed through an API, not formatted as a disk.
D=Edit bytes in place: S3 objects are replaced as a whole when changed; partial in-place writes are a property of block and file storage.
T: S3 = object storage: data + metadata + key in buckets, unlimited capacity, whole-object writes, pay for what you store.
V: Amazon S3
