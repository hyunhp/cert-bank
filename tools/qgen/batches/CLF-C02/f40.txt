@ CLF-C02 D1 T1.4 advanced tradeoff
S: An executive team is preparing the business case for moving to AWS. The draft counts only the expected drop in infrastructure spending. A consultant says the case misses other value. Which additional factors should the business case include?
A: Resale income from the existing servers, counted as a yearly saving that keeps growing for as long as the company keeps its workloads on AWS.
B: Improvements in staff productivity, operational resilience and business agility, such as less time on routine tasks, fewer outages and faster product releases.
C: The higher unit prices of managed services, counted as a pure loss on the assumption that they bring no reduction in the staff effort that is needed.
D: The one-time cost of the migration project, with the drop in infrastructure spending then treated as the whole long-term value of the cloud.
K: B
G: ## Cloud economics is more than a smaller bill
AWS describes the value of moving to the cloud along several dimensions (the AWS Cloud Value Framework):
- **Cost savings**: lower infrastructure spending, the part most business cases start with.
- **Staff productivity**: less time on undifferentiated tasks such as hardware upkeep and patching, so people work on higher-value projects.
- **Operational resilience**: better availability and security, which means fewer and shorter outages and less lost revenue.
- **Business agility**: faster experiments and releases, so new products reach customers sooner.
## Why it matters
A business case that counts only infrastructure savings may undervalue the move, or even make it look unattractive when infrastructure costs are similar. Measuring productivity, resilience and agility gives a complete picture.
W: Productivity, resilience and agility: these are the value dimensions beyond infrastructure savings. Time freed from routine work, fewer outages and faster releases all carry business value that a cost-only case ignores.
X: A=Server resale as a yearly saving: selling old hardware is a one-time item, not a recurring saving, and it says nothing about the ongoing value of the cloud.
C=Managed service prices as a pure loss: managed services can have higher unit prices, but they also reduce staff effort. Counting only their price gives a one-sided view.
D=Migration cost plus infrastructure savings: migration costs belong in the case, but treating infrastructure savings as the whole long-term value is exactly the gap the consultant points out; it leaves out productivity, resilience and agility.
T: A complete cloud business case adds staff productivity, operational resilience and business agility to the infrastructure cost savings.

@ CLF-C02 D1 T1.4 advanced tradeoff
S: A team proposes moving an API service from Amazon EC2 to AWS Lambda to save money. The service handles a high, steady volume of requests around the clock, and its rightsized EC2 instances stay busy all day. What is the best assessment of the cost claim?
A: Pay-per-use saves most when capacity would sit idle; for steady, busy capacity Lambda can cost more, so compare both options with the real usage.
B: Lambda will lower the bill because it does not charge for idle time, and that saving applies just as much to steady, busy traffic as to quiet traffic.
C: Lambda bills the same rate as EC2 for equal memory and CPU, so the move changes who manages the servers but leaves the monthly cost as it is.
D: Lambda bills each invocation for at least one full minute, so it costs more than EC2 for any service that gets more than a few requests a day.
K: A
G: ## Where pay-per-use saves money
**AWS Lambda** charges for the number of requests and for compute duration (measured in milliseconds, priced by the memory configured). When no requests arrive, there is no compute charge. That is why Lambda is so economical for **intermittent or spiky** work: an EC2 instance would be billed for all the idle time in between.
## Where it may not
If a service is busy all the time, there is little idle time to save. A rightsized EC2 fleet running near full use, especially with a Savings Plan, can then cost less per request than paying Lambda's per-request and per-millisecond charges for the same constant load.
## How to decide
- Estimate both options with the **AWS Pricing Calculator** using real request counts, durations and memory sizes.
- Include operations in the total: Lambda removes server patching and scaling work, which has value of its own.
- Compute Savings Plans can apply to Lambda as well as to EC2.
W: Compare with real usage: Lambda's advantage is not paying for idle time. A service that is busy around the clock has little idle time, so Lambda may cost more, and only an estimate with actual traffic shows which is cheaper.
X: B=Idle-time saving applies to steady traffic: removing idle cost helps only when there is idle time. For constant heavy load, per-request and per-duration charges can exceed the cost of busy, rightsized instances.
C=Same rate as EC2: the two services use different pricing models (per request and duration versus per instance running time), so the cost of the same workload usually differs.
D=One-minute minimum: Lambda bills duration in 1 ms increments, not per minute. The real question is the usage pattern, not a minimum charge.
T: Serverless pay-per-use pricing saves the most for idle-heavy workloads; for steady, high utilization, compare Lambda and EC2 with real usage before moving.
V: AWS Lambda, Amazon EC2, AWS Pricing Calculator

@ CLF-C02 D1 T1.1 advanced definition
S: A startup with no infrastructure team stores files in Amazon S3 Standard and runs its web servers on Amazon EC2. It asks which high availability it gets automatically from AWS and which it must design itself. Which TWO statements are correct? (Select TWO)
A: Edge locations hold a standby copy of each EC2 instance, so the web servers keep answering users from the edge when their Availability Zone fails.
B: Each EC2 instance has a standby copy in a second Availability Zone, and AWS restarts it there whenever its original zone has a power problem.
C: Objects stored in Amazon S3 are copied by AWS to a second Region by default, so the startup's files stay available if its own Region has a problem.
D: Objects in the S3 Standard storage class are stored redundantly across multiple Availability Zones in the Region, with no extra work by the customer.
E: Each EC2 instance lives in one Availability Zone, so spreading the web servers across several zones is work that is left to the customer.
K: D,E
G: ## Built-in versus designed availability
Some AWS services are **Regional** and spread data across Availability Zones (AZs) for the customer. Others give the customer a resource that lives in **one AZ**, and the customer decides how many copies to run and where.
## Built in: Amazon S3
S3 Standard, and most other S3 storage classes, store each object redundantly across a minimum of three AZs in the Region. The startup does nothing extra for this. (One Zone classes such as S3 One Zone-IA are the deliberate exception: cheaper, but stored in a single AZ.) Other services, such as Amazon DynamoDB, also replicate across AZs automatically.
## Designed by the customer: Amazon EC2
An EC2 instance is launched into a subnet, and a subnet is in exactly one AZ. EC2 can recover an instance onto new hardware after a host problem, but it stays in the same AZ. To survive the loss of a whole AZ, the customer runs instances in several AZs, for example with an Auto Scaling group and a load balancer.
## Not automatic
- Copying data to another Region happens only if the customer configures it.
- Edge locations cache content; they do not run standby servers.
W: D=S3 Standard across AZs: S3 itself stores each object in several AZs of the Region, so the files survive the loss of one zone without any design work by the startup.
E=EC2 is zonal: an instance lives in one AZ, so redundancy across zones exists only if the startup launches instances in several AZs behind a load balancer.
X: A=Edge standby servers: edge locations cache content for CloudFront and serve DNS for Route 53; they do not run copies of EC2 instances.
B=Standby copy in a second AZ: EC2 does not keep a standby copy of an instance in another AZ. Recovery after a host problem stays in the same AZ.
C=Copied to a second Region by default: S3 keeps objects in the Region the customer chose. Copies in other Regions exist only if the customer sets up replication.
T: Regional services such as Amazon S3 spread data across Availability Zones by design, while EC2 instances are zonal and the customer designs multi-AZ redundancy.
V: Amazon S3, Amazon EC2

D=MFA on the user: MFA is a recommended security control, but billing access does not require it unless a company writes its own policy conditions that do.

A: The company must encrypt each object in its own application before upload, because Amazon S3 stores new objects unencrypted unless told otherwise.
B: AWS encrypts objects at rest when the company signs a separate data protection addendum, because encryption is an add-on to the standard S3 service.
C: AWS picks the most suitable key type for each object by inspecting its content, so the company has no encryption decisions left for its bucket.

B=Separate addendum needed: encryption at rest is a standard S3 feature available to every customer. No extra agreement is needed to use it.
C=AWS picks the key type from content: S3 applies a default (SSE-S3), but it does not inspect objects to judge what each one needs. Choosing SSE-KMS, a specific key or client-side encryption is the company's decision.

@ CLF-C02 D3 T3.6 applied use-case
S: Employees of an architecture firm sometimes overwrite or delete drawings stored in an Amazon S3 bucket by mistake. The firm wants to be able to get back any drawing as it was before such an accident. Which S3 feature should it enable?
A: S3 Transfer Acceleration, which routes each upload through an edge location so that the drawings arrive at the bucket faster.
B: S3 Inventory, which produces a scheduled report listing the objects in the bucket together with their size and metadata.
C: S3 Intelligent-Tiering, which moves each drawing between access tiers depending on how often it is read.
D: S3 Versioning, which keeps the prior copies of an object under their own version IDs in the same bucket.
K: D
G: ## How S3 Versioning works
With versioning **enabled** on a bucket, S3 keeps every version of every object:
- Uploading `plan.dwg` again does not replace the old file; it adds a new version and keeps the old one with its own **version ID**.
- Deleting an object without a version ID only adds a **delete marker**. The object looks deleted, but its earlier versions remain and can be restored by removing the marker or copying an old version back.
## Things to know
- Once enabled, versioning can be suspended but not turned off.
- Every stored version is billed, so it is common to add a lifecycle rule that expires **noncurrent versions** after, for example, 90 days.
- Versioning is required for S3 replication and S3 Object Lock.
W: Versioning: overwrites create new versions and deletes create delete markers, so the previous version of any drawing stays in the bucket and can be restored.
X: A=Transfer Acceleration: it speeds up uploads over long distances but keeps no earlier copy of an overwritten or deleted drawing.
B=S3 Inventory: it reports what objects exist and their metadata. It is a listing, not a copy of earlier versions that can be restored.
C=Intelligent-Tiering: it reduces storage cost by moving objects between tiers based on access; an overwrite still replaces the object.
T: Recover from accidental overwrite or deletion in S3 = enable S3 Versioning (and manage old versions with lifecycle rules).

@ CLF-C02 D3 T3.4 applied use-case
S: A software company runs MySQL on its own servers. It wants a managed database that is compatible with MySQL, offers higher performance, and stores data durably by keeping copies across three Availability Zones with storage that grows automatically. Which service meets these needs?
A: Amazon DynamoDB, a serverless key-value and document database that replicates its tables across three zones in a Region.
B: Amazon DocumentDB, a managed document database that is compatible with MongoDB applications and drivers.
C: Amazon Aurora, a managed relational engine whose high-performance distributed cluster volume grows as data is added.
D: Amazon RDS for MariaDB, a managed open-source relational engine that stores data on EBS volumes attached to the instance.
K: C
G: ## Amazon Aurora
Aurora is a relational database built by AWS for the cloud and offered through Amazon RDS.
- **Compatible** with MySQL or PostgreSQL, so most existing applications, drivers and tools work with little or no change.
- **Higher performance** than standard MySQL or PostgreSQL on similar hardware, because AWS redesigned the storage engine.
- **Storage** is a shared, distributed volume that keeps six copies of the data across three Availability Zones and grows automatically as data is added.
- Up to 15 low-latency read replicas, and Aurora Serverless can adjust capacity automatically.
## Compare
- Standard RDS engines (MySQL, MariaDB, PostgreSQL and others) store data on EBS volumes attached to the DB instance. Storage autoscaling can grow a volume up to a limit you set, but copies in other zones come only from a Multi-AZ deployment that you turn on (for MariaDB, one standby in a second zone).
- DynamoDB and DocumentDB are non-relational, so a MySQL application would have to be rewritten.
W: Amazon Aurora: it is MySQL-compatible (and PostgreSQL-compatible), delivers higher throughput than stock MySQL on similar hardware, and its cluster volume keeps copies of the data across three Availability Zones and grows automatically.
X: A=DynamoDB: it is durable across zones, but it is a NoSQL database, so a MySQL application would need its data model and queries rewritten.
B=DocumentDB: it is compatible with MongoDB, not MySQL, so the application's SQL would not run on it.
D=RDS for MariaDB: it is a managed MySQL-family engine and storage autoscaling can grow its volume, but it runs at standard engine performance and its storage is not a shared volume copied across three zones; even Multi-AZ adds only one standby in a second zone.
T: MySQL or PostgreSQL compatible, faster, with storage replicated across three AZs that grows on its own = Amazon Aurora.
V: Amazon Aurora, Amazon RDS

G: ## Storage optimized instances
Some workloads read and write huge amounts of data on disk all the time. Storage optimized instances (such as the `I` and `D` types) include large, fast local disks, often NVMe SSDs, attached directly to the host.
- Typical uses: NoSQL databases such as Cassandra or MongoDB that you run yourself, data warehousing, log and stream processing, and distributed file systems.
- The local disks are **instance store** volumes: very fast, but the data is lost if the instance stops or fails, so these applications replicate data across several nodes.
## Compare
- General purpose instances are a good default but are not built for the highest disk I/O.
- Compute optimized and accelerated computing instances speed up calculations, not storage access.
W: Storage optimized: these instances are built for tens of thousands of low-latency, random I/O operations per second on large local datasets, which is what a self-managed NoSQL cluster needs.
X: A=Compute optimized: extra processor power does not help when the database is limited by how fast it can read and write its disks.
B=General purpose: they balance resources for typical workloads, but they do not provide the large, very fast local disks that heavy database I/O needs.
C=Accelerated computing: GPUs and other accelerators help with machine learning and graphics, not with reading and writing data on disk.
T: Heavy read and write I/O on large local datasets (NoSQL, data warehousing) = storage optimized instances.

G: ## Generative AI and foundation models
A **foundation model (FM)** is a very large model trained on huge amounts of data. It can summarize, answer questions, write drafts and more, guided by a text **prompt**. Training one costs far too much for most companies, so they use existing models.
