# CLF-C02 b08: D2 T2.3 AWS access management capabilities (21 questions, 4 multi-answer)

@ CLF-C02 D2 T2.3 applied troubleshooting
S: An administrator at an online bookstore added a bucket policy to an Amazon S3 bucket that accidentally denies every action to all principals. Now even IAM administrators cannot read or change the policy. What is the AWS-documented way to recover?
A: Ask AWS Support to remove the bucket policy, because AWS staff can override customer bucket policies on request.
B: Sign in as the account's root user and delete or correct the bucket policy, which is a task reserved for the root user.
C: Attach the AdministratorAccess managed policy to another IAM user, because full IAM permissions override a bucket deny.
D: Wait for the bucket policy to expire automatically, since S3 bucket policies are reset to defaults after 24 hours.
K: B
G: ## Tasks only the root user can do
The root user is meant to be locked away, but AWS keeps a short list of tasks that require it. Well-known examples:
- Changing the root user's own password or other root credentials.
- Editing or deleting an Amazon S3 bucket policy that was misconfigured to deny all principals.
- Restoring IAM permissions when the only IAM administrator has accidentally removed their own access.
## Why IAM administrators are stuck
In a bucket policy, an explicit `Deny` with `"Principal": "*"` applies to every IAM user and role in the account, including ones with `AdministratorAccess`. An explicit deny always beats any allow, so no IAM identity can fix it. The root user is the documented way back in. (In AWS Organizations, the management account can also run this privileged root task on a member account when centralized root access is turned on.)
Example: a policy meant to deny `s3:DeleteObject` to everyone is written as `"Action": "s3:*"`. The fix is to sign in as root, delete the policy and write a correct one.
W: Root user deletes the policy: removing a bucket policy that denies all principals is one of the documented root-only tasks, because no IAM identity can get past that explicit deny.
X: A=AWS Support removes it: AWS Support does not change customer resource policies for you; the account owner recovers access through the root user.
C=AdministratorAccess overrides the deny: an explicit deny in a bucket policy wins over any allow, including allows in AdministratorAccess, so another admin is blocked the same way.
D=Policy expires after 24 hours: bucket policies have no expiry. The deny stays in place until someone with enough authority removes it.
T: A bucket policy that denies all principals can be fixed only by the root user, one of the few tasks reserved for it.
V: AWS Identity and Access Management (IAM), Amazon S3

@ CLF-C02 D2 T2.3 applied definition
S: A logistics company is enabling multi-factor authentication (MFA) for its IAM users. Which MFA types does AWS support for IAM users? (Select TWO)
A: One-time codes sent to the user's mobile phone as SMS text messages each time the user signs in.
B: A virtual authenticator app on a smartphone that generates time-based one-time passcodes for sign-in.
C: A one-time link sent to the user's registered email address that must be opened before sign-in completes.
D: A FIDO2 security key or passkey that the user confirms with a touch or a fingerprint during sign-in.
E: An automated voice call to the user's desk phone that reads out a six-digit code for each new sign-in.
K: B,D
G: ## What MFA adds
Multi-factor authentication means a sign-in needs something you know (the password) plus something you have (a device). A stolen password alone is no longer enough.
## MFA types AWS supports for IAM users and the root user
- **Passkeys and security keys** (FIDO2/WebAuthn): a hardware key such as a YubiKey, or a passkey built into a phone or laptop and unlocked with a fingerprint, face or PIN. These resist phishing because they are bound to the real AWS sign-in site.
- **Virtual authenticator apps**: smartphone apps such as Google Authenticator that generate time-based one-time passwords (TOTP).
- **Hardware TOTP tokens**: small physical devices that show a changing six-digit code.
## What is not supported
AWS no longer offers SMS-based MFA for IAM users, and there is no email-link or voice-call MFA option.
W: B=Virtual authenticator app: TOTP apps on a phone are a supported and very common MFA type for IAM users and the root user.
D=FIDO2 security key or passkey: AWS supports FIDO2 security keys and passkeys, which are also the most phishing-resistant choice.
X: A=SMS text codes: AWS ended SMS-based MFA for IAM users, so text messages are not a supported MFA type.
C=Email sign-in link: email is not an MFA factor in IAM; a compromised mailbox would otherwise defeat the second factor.
E=Voice call codes: IAM has no voice-call MFA; the supported types are passkeys or security keys, authenticator apps and hardware TOTP tokens.
T: IAM MFA works with passkeys or FIDO2 security keys, virtual authenticator apps and hardware TOTP tokens, not SMS, email or voice calls.
V: AWS Identity and Access Management (IAM)

@ CLF-C02 D2 T2.3 applied definition
S: Which statement correctly describes a resource-based policy in AWS?
A: A policy attached to an IAM user, group or role that lists which actions that identity may perform on which resources.
B: A policy set in AWS Organizations that limits the maximum permissions available to every account in an organizational unit.
C: A policy attached directly to a resource, such as an S3 bucket, that names which principals may access that resource.
D: A policy that defines firewall rules on a network interface to control which IP addresses can reach a resource.
K: C
G: ## Two places to write permissions
AWS lets you grant access from two directions:
- **Identity-based policies** are attached to an IAM user, group or role. They answer "what can this identity do?" Example: a role may `s3:GetObject` on `arn:aws:s3:::invoices/*`.
- **Resource-based policies** are attached to a resource. They answer "who can use this resource?" and must include a `Principal` element naming the account, user, role or service allowed in.
## Common resource-based policies
- Amazon S3 bucket policies
- AWS KMS key policies
- Amazon SQS queue policies and Amazon SNS topic policies
- AWS Lambda function resource policies and IAM role trust policies
Resource-based policies are especially useful for cross-account access, because the resource owner can name a principal from another account directly.
W: Attached to a resource and names principals: that is the definition of a resource-based policy; an S3 bucket policy is the best-known example, and its `Principal` element states who is allowed in.
X: A=Attached to a user, group or role: that describes an identity-based policy, the other half of IAM permissions.
B=Organizations limit on accounts: that is a service control policy (SCP), a guardrail that caps permissions in member accounts and grants nothing by itself.
D=Firewall rules on a network interface: that describes a security group, which filters network traffic rather than authorizing API actions.
T: Identity-based policies attach to users, groups and roles; resource-based policies attach to a resource and name the principals that may use it.
V: AWS Identity and Access Management (IAM), Amazon S3

@ CLF-C02 D2 T2.3 applied use-case
S: An insurance company's external audit firm has its own AWS account. The auditors need read-only access to resources in the insurer's account for two weeks, without receiving any long-term credentials from the insurer. What should the insurer do?
A: Create IAM users for each auditor in the insurer's account and email them their passwords and access keys.
B: Share the root user's email address and password with the audit firm and change the password when the audit ends.
C: Make the resources the auditors need publicly readable for two weeks and switch them back to private afterwards.
D: Create an IAM role with read-only permissions whose trust policy allows the audit firm's account to assume it.
K: D
G: ## Cross-account access with roles
An IAM role has two policies:
- A **trust policy** says who may assume the role, for example the AWS account `111122223333`.
- A **permissions policy** says what the role can do once assumed, for example the AWS managed `ReadOnlyAccess` or `SecurityAudit` policy.
When an auditor in the trusted account assumes the role, AWS Security Token Service (STS) returns **temporary credentials** that expire after a set time (one hour by default). No password or access key from the insurer's account ever leaves it.
## Ending access
To end the engagement, delete the role or remove the audit firm's account from the trust policy. Every action the auditors take is recorded in AWS CloudTrail with the role session name, so activity stays traceable.
W: Cross-account read-only role: the audit firm's identities assume the role and receive short-lived credentials, the permissions policy keeps them read-only, and access ends cleanly when the role is removed.
X: A=IAM users with emailed keys: these are long-term credentials, exactly what the insurer wanted to avoid, and sending them by email adds a leak risk.
B=Shared root credentials: the root user has unrestricted access, so sharing it gives auditors far more than read-only and destroys accountability.
C=Public resources: making data public lets anyone on the internet read it, not just the auditors, and is a serious exposure for an insurer.
T: For cross-account access, create a role the other account can assume; it hands out temporary credentials scoped by the role's permissions.
V: AWS Identity and Access Management (IAM), AWS Security Token Service (AWS STS)

@ CLF-C02 D2 T2.3 applied definition
S: When a user or an application assumes an IAM role, which AWS service issues the temporary security credentials that the role session uses?
A: AWS Security Token Service (AWS STS), which returns an access key, a secret key and a session token that expire.
B: AWS Key Management Service (AWS KMS), which generates encryption keys that applications use to sign their AWS API calls.
C: AWS Secrets Manager, which stores long-term access keys for each role and hands a copy to the caller on every request.
D: AWS Certificate Manager (ACM), which issues short-lived TLS certificates that applications present when calling AWS APIs.
K: A
G: ## Long-term versus temporary credentials
- **Long-term**: an IAM user's password or access keys. They stay valid until someone rotates or deletes them.
- **Temporary**: issued for a session and expire on their own, typically after minutes to hours.
## AWS STS
AWS Security Token Service is the service behind every role session. Calls such as `AssumeRole` (cross-account and service roles), `AssumeRoleWithSAML` and `AssumeRoleWithWebIdentity` (federation) return three values:
- an access key ID
- a secret access key
- a session token
The AWS SDKs and CLI use them like normal keys until they expire, then request new ones. EC2 instance roles, Lambda execution roles and IAM Identity Center sign-ins all rely on STS under the hood.
W: AWS STS: it issues the temporary access key, secret key and session token that a role session uses, and they expire automatically.
X: B=AWS KMS: KMS creates and manages encryption keys for data; it does not issue the credentials used to sign AWS API requests.
C=AWS Secrets Manager: Secrets Manager stores application secrets such as database passwords. Roles have no stored access keys to hand out.
D=AWS Certificate Manager: ACM issues TLS certificates for websites and load balancers; AWS API authentication does not use them.
T: AWS STS is the service that issues temporary credentials whenever a role is assumed or a user is federated.
V: AWS Security Token Service (AWS STS), AWS Identity and Access Management (IAM)

@ CLF-C02 D2 T2.3 applied tradeoff
S: A media company grants developers broad permissions while a new project starts. After three months it wants a least-privilege policy based on the actions the developers' role has actually used. Which AWS capability helps produce that policy?
A: AWS Trusted Advisor, which reviews each role's attached policies and rewrites them automatically to remove unused permissions.
B: IAM Access Analyzer policy generation, which reviews the role's activity in AWS CloudTrail logs and drafts a matching policy.
C: Amazon Inspector, which scans the role's permissions for known software vulnerabilities and suggests replacement policies.
D: AWS Config conformance packs, which compare each role against the CIS benchmark and create a new policy for the role.
K: B
G: ## Least privilege in practice
Least privilege means granting only the permissions a task needs. In real projects, teams often start broad because they do not yet know what will be needed, then tighten later. The hard part is knowing which actions are really used.
## IAM Access Analyzer policy generation
IAM Access Analyzer can generate a policy from activity:
- You pick an IAM user or role, a CloudTrail trail and a time range (for example the last 90 days).
- Access Analyzer reads the logged API calls and drafts a policy listing the services and actions used.
- You review it, add resource ARNs where needed, and replace the broad policy with it.
The other Access Analyzer features also support least privilege: external access findings, unused access findings and policy validation checks.
W: IAM Access Analyzer policy generation: it builds a draft policy from the role's real activity recorded in CloudTrail, which is exactly the input needed to shrink broad permissions to what is used.
X: A=Trusted Advisor rewriting policies: Trusted Advisor runs best-practice checks and recommendations; it does not analyze a role's API activity or rewrite IAM policies.
C=Amazon Inspector: Inspector finds software vulnerabilities and network exposure in EC2, container images and Lambda code, not unused IAM permissions.
D=Config conformance packs: conformance packs bundle AWS Config rules to evaluate compliance; they report on resources but do not author least-privilege policies for a role.
T: To shrink broad permissions, let IAM Access Analyzer generate a policy from the actions recorded in CloudTrail, then review and apply it.
V: IAM Access Analyzer, AWS CloudTrail

The team then archives findings for intended sharing and fixes the rest.

@ CLF-C02 D2 T2.3 applied use-case
S: A bank's security standard says IAM user passwords must have at least 14 characters, include numbers and symbols, expire after 90 days and not reuse recent passwords. How can the bank enforce these rules for its IAM users?
A: Create an AWS Config rule that checks password strength, which blocks IAM users from choosing a weak password.
B: Store every IAM user's password in AWS Secrets Manager and turn on automatic rotation every 90 days for each user.
C: Set an IAM account password policy with the required length, character types, expiration and reuse prevention.
D: Attach a service control policy to the account that lists the minimum password length and complexity required.
K: C
G: ## IAM account password policy
Each AWS account has one password policy that applies to its **IAM users**. Settings include:
- minimum length and required character types (upper case, lower case, numbers, symbols)
- password expiration after a set number of days
- preventing reuse of a number of previous passwords
- whether users may change their own password, and whether an expired password needs an administrator reset
Most settings take effect the next time a user changes a password; some, such as expiration, apply right away.
## What it does not cover
- The **root user** password is not governed by the IAM password policy.
- Users in IAM Identity Center or an external identity provider follow that directory's own password rules.
## Checking versus enforcing
The AWS Config managed rule `iam-password-policy` can report whether the account's password policy meets your standard, but it is the password policy itself that enforces the rules when users set passwords.
W: IAM account password policy: it is the built-in setting that enforces length, character, expiration and reuse rules whenever IAM users set passwords.
X: A=Config rule blocks weak passwords: AWS Config evaluates and reports compliance; its password rule checks the account's policy settings but cannot stop a user from picking a password.
B=Secrets Manager rotation per user: Secrets Manager rotates application secrets such as database credentials; it has no built-in rotation for IAM console passwords and cannot enforce length, character or reuse rules on passwords users choose.
D=SCP with password rules: service control policies limit which API actions accounts may use; they have no settings for password length or complexity.
T: Enforce IAM user password rules with the account password policy; it does not apply to the root user.

@ CLF-C02 D2 T2.3 applied troubleshooting
S: A developer at a gaming studio accidentally pushed an IAM user's access key ID and secret access key to a public code repository. What should the studio do first?
A: Change the IAM user's console password, because a new password also invalidates any access keys that the user owns.
B: Make the repository private, because removing public access to the file stops anyone from using the copied keys.
C: Enable MFA on the IAM user, because API calls signed with access keys then require an MFA code to succeed.
D: Deactivate the exposed access key, then replace it with a new one and review CloudTrail for unauthorized activity.
K: D
G: ## Why leaked access keys are urgent
An access key (access key ID plus secret access key) is a long-term credential for programmatic access. Anyone who has a copy can call AWS APIs as that user until the key is deactivated or deleted. Automated scanners find keys in public repositories within minutes.
## Responding to a leak
1. **Deactivate** the exposed key right away (and delete it once nothing legitimate depends on it).
2. Create a new key for the workload if still needed, or better, move the workload to an IAM role with temporary credentials.
3. Review **AWS CloudTrail** for calls made with the key, and check for unexpected resources such as new EC2 instances or IAM users.
4. Remove the secret from the repository history, knowing that copies may already exist elsewhere.
AWS may also notify you and apply a quarantine policy when it detects an exposed key, but the account owner must still act.
W: Deactivate, replace and investigate: disabling the key stops any further use of the leaked secret at once, and CloudTrail shows whether it was already misused.
X: A=Change the console password: passwords and access keys are separate credentials; changing the password leaves the leaked key fully working.
B=Make the repository private: the key may already have been copied, and hiding the file does nothing to invalidate it.
C=Enable MFA: MFA protects console sign-in. API calls signed with access keys do not need MFA unless a policy explicitly requires it, so the leaked key keeps working.
T: When an access key leaks, deactivate it immediately, rotate to a new credential or role, and check CloudTrail for misuse.
V: AWS Identity and Access Management (IAM), AWS CloudTrail

@ CLF-C02 D2 T2.3 applied tradeoff
S: A data analytics company still uses IAM user access keys for several scripts. Which practices reduce the risk from these long-term credentials? (Select TWO)
A: Replace access keys with IAM roles and temporary credentials wherever the workload can assume a role.
B: Create root user access keys as a backup in case an IAM user's access key stops working unexpectedly.
C: Share one IAM user's access key among all scripts so there are fewer keys to track in the account.
D: Embed the keys in the script source code so they are versioned and backed up with the repository.
E: Rotate the keys that must remain on a regular schedule and remove keys that are no longer used.
K: A,E
G: ## Long-term access keys are a standing risk
An IAM user access key works until someone deactivates it. The longer it lives and the more places it is copied, the more likely it is to leak.
## AWS guidance
- **Prefer temporary credentials**: workloads on AWS (EC2, Lambda, ECS) should use IAM roles; workloads outside AWS can use IAM Roles Anywhere or federation; people should use IAM Identity Center. Temporary credentials expire on their own.
- **When keys must stay**: give each workload its own key with least-privilege permissions, rotate keys regularly (an IAM user can have two keys so you can rotate without downtime), and delete unused keys. The credential report and the key's "last used" information show which keys are idle.
- **Never** create root user access keys, and keep keys out of source code.
W: A=Move to roles and temporary credentials: credentials that expire on their own remove the long-lived secret that can leak, which is AWS's first recommendation.
E=Rotate and remove unused keys: for keys that cannot be replaced yet, regular rotation shortens the useful life of a leaked key and deleting idle keys removes needless risk.
X: B=Root access keys as backup: root keys have unlimited permissions and cannot be restricted by IAM policies; AWS recommends having none.
C=One shared key for all scripts: sharing widens the damage of a single leak, breaks least privilege and makes CloudTrail unable to tell which script did what.
D=Keys in source code: repositories are copied, cloned and sometimes made public, which is one of the most common ways access keys leak.
T: Use roles and temporary credentials instead of access keys; where keys must remain, rotate them and delete unused ones.
V: AWS Identity and Access Management (IAM)

S: An application on AWS Lambda connects to an Amazon RDS database. The security team wants the database password removed from the code and changed automatically on a schedule. Which service meets these requirements?
A: AWS Secrets Manager, which stores the password encrypted and can rotate it automatically on a schedule.

W: AWS Secrets Manager: the function retrieves the password at run time with its IAM role, and Secrets Manager rotates the RDS password automatically, meeting both requirements.

C=IAM access keys for the function: Lambda functions get AWS permissions from an execution role, so access keys only add another long-term secret to protect; they do not store or rotate the database password the application still uses.
D=Encrypted S3 object: the password is out of the code, but nothing rotates it and the database would not be updated when it changes.

A: The delete succeeds, because the group policy allows all S3 actions and group policies take precedence over user policies.
B: The delete succeeds, because AWS applies whichever policy was attached most recently to the user or to the group.
C: The delete is denied, because an explicit deny in any applicable policy overrides any allow from other policies.

K: C
G: ## How AWS decides allow or deny
For a request inside one account, AWS gathers every policy that applies (the user's own policies, its groups' policies, and any resource-based policy) and evaluates them together. In simplified form:
1. **Default deny**: everything starts denied.
2. **Explicit deny**: if any applicable policy has a `Deny` that matches the request, the answer is deny. Nothing can override it.
3. **Explicit allow**: otherwise, if some policy has a matching `Allow`, the request is allowed.
Order of attachment and whether a policy comes from a group or the user directly make no difference. Guardrails such as service control policies and permissions boundaries can further limit an allow, but they never turn a deny into an allow.
## Using explicit deny on purpose
Teams use this behavior as a safety net: grant broad access through a group, then add a narrow explicit deny for dangerous actions such as deleting objects or disabling CloudTrail.
W: Explicit deny wins: the user-attached deny matches `s3:DeleteObject`, and an explicit deny overrides the group's allow regardless of where each policy is attached.
X: A=Group policy takes precedence: group and user policies are evaluated together with equal standing; there is no group-first rule.
B=Most recent policy wins: IAM evaluation does not use attachment time; all applicable policies are combined on every request.
D=Users in groups cannot have own policies: users can have directly attached policies and group memberships at the same time; the deny comes from evaluation logic, not from a restriction on attaching.
T: In IAM policy evaluation, an explicit deny anywhere always overrides any allow.

@ CLF-C02 D2 T2.3 applied definition
S: In an IAM policy statement, which element lists the API operations, such as s3:GetObject or ec2:StartInstances, that the statement allows or denies?
A: The Effect element, which lists each operation that the statement covers with its permission setting.
B: The Resource element, which names the operations that may be performed on the listed resource ARNs.
C: The Condition element, which names the operations along with the circumstances under which they apply.
D: The Action element, which names the service prefix and the operations that the statement covers.
K: D
G: ## Anatomy of a policy statement
IAM policies are JSON documents made of one or more statements. The main elements:
- **Effect**: `Allow` or `Deny`.
- **Action**: the API operations, written as `service:Operation`, for example `s3:GetObject` or `dynamodb:Query`. Wildcards such as `s3:Get*` are allowed.
- **Resource**: the ARNs the actions apply to, for example `arn:aws:s3:::payroll-reports/*`.
- **Condition** (optional): extra checks, such as requiring MFA or a source IP range.
- **Principal**: only in resource-based policies, to name who is allowed.
## Example
`{"Effect": "Allow", "Action": "s3:GetObject", "Resource": "arn:aws:s3:::payroll-reports/*"}` lets the identity read objects in one bucket and nothing else.
W: Action element: it lists the operations in `service:Operation` form, so it is where `s3:GetObject` or `ec2:StartInstances` appears.
X: A=Effect element: Effect holds only `Allow` or `Deny`; it does not list operations.
B=Resource element: Resource holds the ARNs of the resources the statement applies to, not the operations.
C=Condition element: Condition adds optional circumstances, such as a required source IP, but the operations themselves go in Action.
T: In an IAM policy, Effect says allow or deny, Action lists operations, Resource lists ARNs and Condition adds optional limits.

@ CLF-C02 D2 T2.3 applied tradeoff
S: A nonprofit needs to give its volunteers view-only access to its AWS account today. It has no IAM expertise and wants the permissions kept up to date as AWS releases new services. Which type of policy fits best?
A: An AWS managed policy for the job function, which AWS creates and updates when new services and actions are added.
B: A customer managed policy written from scratch, which the nonprofit must update itself whenever new services are added.
C: An inline policy embedded in each volunteer's IAM identity, which is deleted automatically when that identity is deleted.
D: A service control policy in AWS Organizations, which grants view-only permissions to every principal in the account.
K: A
G: ## Three kinds of identity-based policies
- **AWS managed policies**: created and maintained by AWS. Examples include job-function policies such as `ViewOnlyAccess` and `ReadOnlyAccess`. AWS updates them when services add new actions. You can attach them but not edit them.
- **Customer managed policies**: written by you, reusable across many identities, versioned. Best for precise least privilege, but you must maintain them.
- **Inline policies**: embedded in a single user, group or role and deleted with it. Useful for a strict one-to-one relationship, hard to manage at scale.
## The trade-off
AWS managed policies are quick and low-maintenance but are often broader than a specific job needs. A common path: start with an AWS managed policy, then move to a customer managed policy once you know what is really used.
W: AWS managed job-function policy: it is ready to attach today, needs no IAM expertise, and AWS keeps it current as new services and actions appear.
X: B=Customer managed policy from scratch: it allows tight least privilege, but it needs the IAM skills the nonprofit lacks and manual updates for every new service.
C=Inline policy per identity: copies embedded in each identity must be written and maintained one by one, which is the hardest option to keep current.
D=Service control policy: SCPs only limit the maximum permissions in member accounts; they never grant permissions to anyone.
T: AWS managed policies are quick and AWS-maintained; customer managed policies give tighter control at the cost of maintenance.

@ CLF-C02 D2 T2.3 applied comparison
S: Which statement best describes how an IAM role differs from an IAM user?
A: A role is a collection of IAM users that share one password, while a user is an individual identity with its own password.
B: A role has no long-term password or access keys; trusted entities assume it and receive temporary credentials.
C: A role can be used only by AWS services, while a user can be used by people, applications and AWS services alike.
D: A role always has full administrator permissions, while a user has only the permissions attached to it directly.
K: B
G: ## IAM user
An IAM user represents one specific person or application in one account. It can have long-term credentials: a console password and up to two access keys. Those credentials stay valid until changed or deleted.
## IAM role
An IAM role is an identity with permissions but **no long-term credentials**. Instead, a trusted entity **assumes** it and gets temporary credentials from AWS STS. Who can assume it is set by the role's trust policy, and that can be:
- an AWS service, such as EC2 or Lambda
- a user or role in the same or another AWS account
- federated users from an identity provider (IAM Identity Center uses roles this way)
Roles have exactly the permissions their policies grant, from read-only to administrator.
W: No long-term credentials, assumed for temporary ones: that is the defining difference; roles hand out short-lived credentials to whoever the trust policy allows.

C=Roles only for AWS services: roles are also assumed by people, federated users and identities in other accounts, not only by services.
D=Roles always have admin rights: a role has only the permissions its policies grant, which can be as narrow as one action on one resource.
T: An IAM user has long-term credentials; an IAM role has none and gives temporary credentials to whoever is trusted to assume it.

E=AdministratorAccess on the function: full permissions mean any bug or compromise in the function can affect the entire account, the opposite of least privilege.
T: Give Lambda functions AWS permissions through a least-privilege execution role and keep third-party secrets in Secrets Manager.

The credential report is a CSV snapshot of IAM users in one account. It shows when passwords and keys were last used, but it does not cover roles or individual permissions.
