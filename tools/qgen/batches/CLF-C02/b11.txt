@ CLF-C02 D3 T3.3 applied use-case
S: A financial analytics firm runs an application on Amazon EC2 that loads a very large dataset into RAM so that analysts can query it in real time. The current instances run out of memory long before they run out of CPU. Which EC2 instance family should the firm choose?
A: Compute optimized instances, which offer a high ratio of vCPUs to memory for processor-bound work such as batch processing.
B: Memory optimized instances, which offer a high ratio of memory to vCPUs for workloads that process large datasets in RAM.
C: Storage optimized instances, which offer fast local disks for workloads with heavy sequential reads and writes to local storage.
D: Accelerated computing instances, which add GPUs or other hardware accelerators for parallel math such as model training.
K: B
G: ## EC2 instance families
Every EC2 instance type belongs to a family designed for a certain balance of CPU, memory, storage and networking. The letter at the start of the type name hints at the family.
- **General purpose** (for example `M` and `T` types): a balance of CPU, memory and networking for web servers, small databases and development environments.
- **Compute optimized** (`C` types): many fast vCPUs per GB of memory for CPU-bound work.
- **Memory optimized** (`R`, `X` types): a lot of memory per vCPU for data held in RAM.
- **Storage optimized** (`I`, `D` types): fast, large local instance storage for heavy disk I/O.
- **Accelerated computing** (`P`, `G`, `Inf`, `Trn` types): GPUs or AI chips for machine learning and graphics.
## How to pick
Find the resource that runs out first. If memory is full while CPU is idle, a bigger compute optimized instance would waste money on cores you do not use; a memory optimized instance gives more RAM per dollar.
W: Memory optimized: these instances are built for in-memory databases, caches and real-time analytics on large datasets, and they give the most memory per vCPU, which is exactly the resource this workload runs short of.
X: A=Compute optimized: they add processing power, but the application is limited by memory, not CPU, so the extra cores would sit idle while RAM is still too small.
C=Storage optimized: they speed up local disk I/O. The data is queried from RAM, so faster disks do not fix the memory shortage.
D=Accelerated computing: GPUs help with highly parallel calculations such as training models. They do not add the main memory the analytics application needs.
T: Data that must fit in RAM (in-memory analytics, caches, large databases) = memory optimized instances.
V: Amazon EC2

A game server simulating physics for 64 players at 60 ticks per second keeps its CPU near 90% all day. A burstable instance would run out of credits and slow down; a compute optimized instance keeps steady full-speed CPU.

@ CLF-C02 D3 T3.3 applied use-case
S: A development team at an insurance company writes a Java web application. It wants to upload the code and have AWS set up and run the environment, while keeping access to the underlying resources. Which TWO tasks does AWS Elastic Beanstalk handle for the team automatically? (Select TWO)
A: Provisioning the EC2 capacity and the load balancer that the application runs behind.
B: Writing unit tests for the application code and fixing any defects that the tests find.
C: Scaling the number of instances up and down with traffic and monitoring application health.

AWS Elastic Beanstalk is a platform as a service (PaaS) for web applications. You upload code (Java, .NET, Node.js, Python, PHP, Ruby, Go or a Docker container) and Beanstalk builds the environment for it:
- **Capacity provisioning**: EC2 instances on a managed platform (operating system plus language runtime).

D=Schema design and query tuning: the data model and SQL performance belong to the team, whether the database is created with Beanstalk or separately.
E=Access decisions: who may change the application is an IAM decision the company makes. Beanstalk uses roles but does not decide permissions for people.
T: Elastic Beanstalk = upload code; AWS provisions capacity, load balancing, scaling and health monitoring, and you keep control of the resources.

@ CLF-C02 D3 T3.3 applied use-case
S: A genomics institute must run tens of thousands of independent analysis jobs each week. It wants AWS to queue the jobs, choose and launch the right amount of compute for them, and release that compute when the queue is empty. Which service is designed for this?
A: AWS Lambda, which runs short functions in response to events and scales the number of concurrent copies automatically.
B: AWS Batch, which queues batch jobs and provisions and scales compute resources based on the jobs' requirements.

Batch work is a large set of jobs that run to completion without a user waiting: genome analysis, financial risk models, image rendering, simulations.

@ CLF-C02 D3 T3.3 applied comparison
S: An online travel agency runs one website on Amazon EC2. Requests whose path starts with /flights must go to one group of instances and requests for /hotels to another group, all behind one endpoint. Which load balancer type supports this?
A: Network Load Balancer, which forwards TCP and UDP connections at Layer 4 with very low latency and a static IP per zone.
B: Gateway Load Balancer, which sends traffic through a fleet of third-party virtual appliances such as firewalls for inspection.
C: Application Load Balancer, which inspects HTTP and HTTPS requests at Layer 7 and routes them by path or host name.
D: Amazon Route 53 weighted routing, which answers DNS queries with different endpoints in proportions set by the company.
K: C
G: ## Elastic Load Balancing types
Elastic Load Balancing (ELB) spreads traffic across targets such as EC2 instances, containers and Lambda functions. It offers several types:
- **Application Load Balancer (ALB)**, Layer 7: understands HTTP and HTTPS. It can route on the URL path (`/flights/*`), host name (`api.example.com`), headers or query strings, and send each rule to a different target group.
- **Network Load Balancer (NLB)**, Layer 4: forwards TCP, UDP and TLS connections with very high throughput and low latency, and can have a static IP address per Availability Zone.
- **Gateway Load Balancer (GWLB)**: places third-party virtual network appliances (firewalls, intrusion detection) transparently in the traffic path.
- Classic Load Balancer: the previous generation, kept for older applications.
## Example
Listener rule 1: path `/flights/*` -> target group "flights". Rule 2: path `/hotels/*` -> target group "hotels". One DNS name serves both.
W: Application Load Balancer: it reads each HTTP request and its listener rules route by URL path, so /flights and /hotels traffic can go to different target groups behind one endpoint.
X: A=Network Load Balancer: it works at the connection level and does not read HTTP paths, so it cannot send /flights and /hotels to different groups.
B=Gateway Load Balancer: it is for inserting inspection appliances into the traffic path, not for routing web requests by URL.
D=Route 53 weighted routing: DNS chooses an endpoint for a whole host name by weight. It never sees the URL path, so it cannot split traffic by /flights and /hotels.
T: Routing HTTP requests by path or host name = Application Load Balancer (Layer 7).
V: Elastic Load Balancing, Application Load Balancer

@ CLF-C02 D3 T3.3 applied use-case
S: An online retailer's EC2 traffic always jumps every Monday at 08:00 when a weekly sale starts, and occasionally an instance becomes unhealthy and stops responding. Which TWO capabilities of Amazon EC2 Auto Scaling address these needs? (Select TWO)
A: Scheduled scaling actions that raise the group's capacity shortly before 08:00 each Monday and lower it later.
B: Vertical scaling that changes each running instance to a larger instance type in place without a restart.
C: Health checks that detect an unhealthy instance, terminate it and launch a replacement automatically.
D: Cross-Region copying that moves running instances to a less busy AWS Region whenever demand rises.
E: Automatic operating system patching of every instance in the group during the busy Monday morning hours.
K: A,C
G: ## What EC2 Auto Scaling does
An Auto Scaling group keeps a number of EC2 instances between a minimum and a maximum. It changes that number in several ways:
- **Dynamic scaling**: follows a metric, for example target tracking that keeps average CPU near 50%.
- **Scheduled scaling**: changes capacity at set times, useful when the pattern is known in advance.
- **Predictive scaling**: forecasts recurring patterns from past traffic and scales ahead of them.
It also keeps the group healthy: with **health checks** (EC2 status checks, and optionally load balancer health checks), an instance that fails is terminated and replaced.
## Horizontal, not vertical
Auto Scaling adds or removes instances (horizontal scaling). It does not resize a running instance, move instances between Regions or patch operating systems.
W: A=Scheduled scaling: the spike happens at a known time, so a scheduled action can add capacity before 08:00 and remove it later, instead of waiting for metrics to react.
C=Health check replacement: Auto Scaling terminates instances that fail health checks and launches new ones, keeping the desired capacity without manual work.
X: B=In-place vertical scaling: Auto Scaling changes the number of instances, not their size. Changing an instance type requires stopping the instance and is not an Auto Scaling feature.
D=Cross-Region copying: an Auto Scaling group works within one Region. It does not move running instances between Regions.
E=Automatic OS patching: Auto Scaling does not patch instances; patching is done with tools such as Systems Manager Patch Manager or by updating the launch template's image.
T: EC2 Auto Scaling = scale horizontally on metrics, schedules or forecasts, and replace unhealthy instances.
V: Amazon EC2 Auto Scaling

@ CLF-C02 D3 T3.3 applied troubleshooting
S: A team moved a nightly data export to AWS Lambda. Small exports succeed, but large exports that need about 40 minutes always fail when the function reaches its maximum duration. The team still wants to avoid managing servers. What is the best solution?
A: Increase the function's memory to the maximum, because Lambda allows a longer timeout for functions with more memory.
B: Turn on provisioned concurrency, so that pre-initialized execution environments can keep running past the time limit.
C: Run the export as a container task on Amazon ECS with AWS Fargate, which has no 15-minute limit and no servers to manage.
D: Deploy the function as Lambda@Edge, so that it runs at CloudFront edge locations closer to the database it exports from.
K: C
G: ## The Lambda time limit
A single AWS Lambda invocation can run for at most **15 minutes** (900 seconds). This is a fixed service limit. More memory makes code run faster (CPU grows with memory) but never raises the 15-minute ceiling.
## Options for long jobs without servers
- Split the work into smaller pieces that each finish within 15 minutes, for example with AWS Step Functions.
- Run the job as a container on **AWS Fargate** (through Amazon ECS or EKS). Fargate tasks can run for hours, and there are still no EC2 instances to manage.
- For many queued jobs, AWS Batch can schedule them on Fargate or EC2.
## Other Lambda features
- **Provisioned concurrency** keeps execution environments initialized to remove cold-start delay. It does not change the timeout.
- **Lambda@Edge** runs small functions at CloudFront locations to change web requests and responses; its limits are stricter, not looser.
W: ECS with Fargate: a Fargate task can run the 40-minute export to completion, and AWS still manages the underlying compute, so the team keeps its no-servers goal.
X: A=More memory: memory raises the CPU share and can shorten run time, but the maximum timeout stays 15 minutes whatever the memory size.
B=Provisioned concurrency: it reduces start-up delay by keeping environments warm. Each invocation is still limited to 15 minutes.
D=Lambda@Edge: it customizes CloudFront requests and responses with even tighter time limits, so it makes long-running exports less possible, not more.
T: Lambda stops at 15 minutes per invocation; long-running serverless work belongs on Fargate (or split it up with Step Functions).
V: AWS Lambda, AWS Fargate, Amazon ECS

@ CLF-C02 D3 T3.4 applied use-case

A: Create a read replica and point the reporting tool at it, so that the read-only queries run on a separate copy.
B: Convert to a Multi-AZ DB instance deployment, so that the standby in another zone answers the reporting queries.
C: Take a manual DB snapshot every afternoon and let the finance team query the snapshot file directly from Amazon S3.
D: Move the database to a Dedicated Host, so that no other customer's workloads share the physical server with it.
K: A
G: ## Two RDS features that are often confused
- **Read replicas** are copies kept up to date asynchronously from the primary. Applications can send read-only queries to them, which takes that load off the primary. They are for **read scaling**.
- **Multi-AZ DB instance deployments** keep a synchronous standby in another Availability Zone. If the primary fails, RDS fails over to the standby automatically. The standby does **not** serve queries; it is for **high availability**. (The newer Multi-AZ DB cluster option has readable standbys, but its purpose is still availability.)
## Example
The order application keeps writing to the primary. The reporting tool connects to the replica endpoint. Heavy afternoon reports now run on the replica, and order processing stays fast.
W: Read replica: it serves read-only queries from a separate copy, so moving the reports there removes their load from the primary that handles customer orders.
X: B=Multi-AZ standby: in a Multi-AZ DB instance deployment the standby exists for automatic failover and does not accept queries, so it cannot take the reporting load.
C=Snapshot in S3: snapshots are backups used to restore a database. They cannot be queried directly as files, and a restore would take time every afternoon.
D=Dedicated Host: RDS does not run on Dedicated Hosts, and isolation from other customers would not reduce the load that the finance reports put on the database.
T: Offload read-heavy work = read replicas; survive an AZ failure with automatic failover = Multi-AZ.
V: Amazon RDS

@ CLF-C02 D3 T3.4 applied use-case
S: A news website stores articles in Amazon RDS. The same popular articles are read thousands of times per minute, and the database is overloaded by these repeated queries. The company wants faster responses and less database load with a managed service. What should it add?
A: Amazon Redshift, which loads the articles into a columnar warehouse that runs analytical SQL queries in parallel.
B: Amazon ElastiCache, which keeps frequently read results in memory so the application can serve them in microseconds.
C: Amazon Neptune, which stores the articles as connected nodes and edges so related content can be found quickly.
D: An Amazon RDS Multi-AZ deployment, which keeps a synchronous standby of the database in a second Availability Zone.
K: B
G: ## Caching in front of a database
When many users ask for the same data, running the same query against the database each time wastes capacity. A **cache** stores the result in memory after the first request.
- **Amazon ElastiCache** is a managed in-memory cache compatible with Valkey, Redis OSS and Memcached.
- Reads from memory take microseconds, far faster than a disk-based database query.
## Cache-aside pattern
1. The application looks for `article:5821` in ElastiCache.
2. On a hit it returns the cached article at once.
3. On a miss it queries RDS, returns the result and stores it in the cache with an expiry time.
Popular articles are served almost entirely from memory, and the database handles only misses and writes.
W: ElastiCache: an in-memory cache answers repeated reads in microseconds and absorbs most of the identical queries, so the RDS database is no longer overloaded.
X: A=Redshift: it is a data warehouse for analytics on large datasets, not a low-latency layer for serving individual articles to website visitors.
C=Neptune: it is a graph database for relationship queries. Moving articles there would not reduce repeated identical reads or speed up serving popular pages.
D=Multi-AZ: it improves availability with a standby copy, but the standby does not serve reads, so the primary still handles every query.
T: Repeated reads overloading a database = add an in-memory cache with Amazon ElastiCache.
V: Amazon ElastiCache, Amazon RDS

@ CLF-C02 D3 T3.4 advanced comparison
S: A fintech startup needs a Redis-compatible database to be its primary data store for account balances. It needs microsecond read latency, but it cannot accept losing recent writes if a node fails. Which AWS service is the best fit?
A: Amazon ElastiCache, a managed in-memory cache that is usually placed in front of another database that holds the source data.
B: Amazon MemoryDB, a durable in-memory database that stores every write in a Multi-AZ transaction log before acknowledging it.
C: Amazon DynamoDB Accelerator, an in-memory cache that sits in front of DynamoDB tables to speed up repeated item reads.
D: Amazon RDS for MySQL with read replicas, which serves read traffic from asynchronous copies kept in other Availability Zones.
K: B
G: ## In-memory speed, two different jobs
- **Amazon ElastiCache** is a cache. It speeds up reads in front of a primary database. It can replicate, but it is designed so that the system of record lives elsewhere.
- **Amazon MemoryDB** is a durable, in-memory **primary database** compatible with Valkey and Redis OSS. Each write is stored in a distributed transaction log across multiple Availability Zones before it is acknowledged, so data survives node failures. Reads come from memory in microseconds; writes take single-digit milliseconds because of the durable log.
## How to choose
- Need a faster layer in front of an existing database: ElastiCache.
- Need Redis-style data structures and microsecond reads as the main, durable store of data: MemoryDB.
W: Amazon MemoryDB: it gives Redis-compatible microsecond reads and is built as a primary database, writing each change to a Multi-AZ transaction log so acknowledged writes are not lost when a node fails.
X: A=ElastiCache: it is designed as a cache for data that is also kept in another database, so using it as the only store of balances risks losing recent writes.
C=DynamoDB Accelerator: DAX only caches DynamoDB reads. It is not Redis-compatible and is not a database on its own.
D=RDS for MySQL: it is durable, but it is a disk-based relational engine with millisecond reads, and it is not Redis-compatible.
T: In-memory cache in front of a database = ElastiCache; durable, Redis-compatible in-memory primary database = MemoryDB.
V: Amazon MemoryDB, Amazon ElastiCache

@ CLF-C02 D3 T3.4 applied use-case
S: A bank wants to detect fraud rings by following connections between accounts, devices, phone numbers and transactions several hops away in real time. Which AWS database service is purpose-built for this type of query?
A: Amazon Redshift, which runs complex SQL across billions of historical rows stored in a columnar format.
B: Amazon DocumentDB, which stores each customer as a flexible JSON document with nested fields and arrays.
C: Amazon Neptune, which stores data as nodes and relationships and quickly traverses many connections.
D: Amazon Aurora, which stores data in relational tables and links accounts to transactions with foreign keys.
K: C
G: ## Graph databases
Some questions are about **relationships**: who is connected to whom, and through what. A graph database stores:
- **Nodes** (vertices): an account, a device, a phone number.
- **Edges**: the links between them, such as "logged in from" or "sent money to".
Following edges (traversal) is fast even across many hops. In a relational database each hop is another join, and queries slow down sharply as hops grow.
## Amazon Neptune
A fully managed graph database supporting the Gremlin, openCypher and SPARQL query languages. Typical uses: fraud detection, social networks, recommendation engines, knowledge graphs and network security.
## Example
"Find every account that shares a device or phone number with a known fraudulent account, up to three hops away" is a short graph query in Neptune.
W: Amazon Neptune: it is a graph database built to store relationships and traverse many hops quickly, which is the core of finding fraud rings across accounts, devices and transactions.
X: A=Redshift: it analyzes large historical datasets with SQL, but multi-hop relationship searches in real time are not what a columnar warehouse is designed for.
B=DocumentDB: it stores self-contained JSON documents. Following links between many documents across several hops is slow and complex in a document model.
D=Aurora: relational tables can model links, but each hop needs another join, so deep relationship queries become slow and hard to write.
T: Highly connected data and multi-hop relationship queries (fraud rings, social networks, recommendations) = Amazon Neptune.
V: Amazon Neptune

C: Amazon DocumentDB, a managed document database that is compatible with MongoDB application code and drivers.

@ CLF-C02 D3 T3.4 applied use-case
S: A chain of pharmacies wants business analysts to run complex SQL queries across five years of sales, inventory and customer data from many systems, and to feed dashboards. The operational databases must not slow down. Which AWS service is designed for this?
A: Amazon RDS for SQL Server, a managed relational engine for transactional workloads such as point-of-sale and order entry.
B: Amazon Redshift, a managed data warehouse that stores data in columns and runs analytical queries in parallel.
C: Amazon DynamoDB, a key-value database that returns individual items by key in single-digit milliseconds at scale.
D: Amazon ElastiCache, an in-memory cache that serves frequently requested results to applications in microseconds.
K: B
G: ## OLTP versus OLAP
- **OLTP** (online transaction processing): many small reads and writes, such as recording a sale. RDS, Aurora and DynamoDB are built for this.
- **OLAP** (online analytical processing): fewer but huge queries that scan and aggregate millions or billions of rows, such as "sales by region by month for five years".
Running OLAP queries on the OLTP database slows down the business. The usual pattern is to copy data from many sources into a separate **data warehouse**.
## Amazon Redshift
- Managed, petabyte-scale data warehouse using standard SQL.
- **Columnar storage** and **massively parallel processing** make large scans and aggregations fast.
- Works with BI tools such as Amazon Quick Sight; Redshift Serverless removes cluster management.
W: Amazon Redshift: it is a data warehouse built for complex analytical SQL over large historical data from many sources, and it keeps that work off the operational databases.
X: A=RDS for SQL Server: it is optimized for transactions. Running five-year analytical scans on it would compete with the workloads it serves.
C=DynamoDB: it excels at fast lookups by key but is not designed for ad hoc SQL joins and aggregations over years of data.
D=ElastiCache: it caches small, frequently used results in memory. It is not a store for years of history or an engine for analytical SQL.
T: Analytics and BI over large historical data from many sources = Amazon Redshift (data warehouse, OLAP).
V: Amazon Redshift

@ CLF-C02 D3 T3.4 applied tradeoff
S: A company runs a commercial database that needs a third-party extension installed in the operating system and administrator access to the host for tuning. Amazon RDS does not allow this level of access. What is the most suitable approach on AWS?
A: Use Amazon RDS anyway and ask AWS Support to install the extension and grant operating system access to the company.
B: Run the database on Amazon EC2 and manage the operating system, the database software, backups and high availability itself.
C: Move the data to Amazon DynamoDB, which accepts operating system extensions because it is fully serverless.
D: Use Amazon Redshift, which gives full host access to its nodes so administrators can install any database extension.
K: B
G: ## Managed database or database on EC2
**Amazon RDS** is a managed service: AWS handles the host, operating system, database installation, patching, backups and failover. In exchange, you do not get operating system access, and you can use only the engines, versions and options RDS supports.
**A database on Amazon EC2** gives you full control:
- Root access to the operating system and any engine, version, extension or setting.
- But you take on everything RDS would do: patching the OS and database, configuring backups, replication and failover, monitoring and scaling.
## How to choose
- Default to a managed service when it supports what you need: less work and fewer mistakes.
- Choose EC2 when a hard requirement (OS-level access, an unsupported engine or extension, special licensing) rules the managed service out.
W: Database on EC2: it gives the company OS-level and administrator access for the extension and tuning, at the cost of managing patching, backups and availability itself.
X: A=Ask AWS Support: RDS is managed by design without customer OS access, and AWS Support does not grant host access or install arbitrary software on RDS instances.
C=DynamoDB: it is a serverless NoSQL service with no operating system for customers to reach, and it cannot run a commercial relational engine's extension.
D=Redshift: it is a managed data warehouse without customer host access, and it does not run the company's commercial database engine.
T: Managed (RDS) = less work but no OS access; self-managed on EC2 = full control and full responsibility.
V: Amazon EC2, Amazon RDS

@ CLF-C02 D3 T3.4 applied use-case
S: Before moving a Microsoft SQL Server database to Amazon RDS for PostgreSQL, a team wants an assessment of how much of its schema and stored procedures can be converted automatically, and then wants that code converted. Which AWS capability is designed for this step?
A: AWS DMS Schema Conversion, which assesses the source and converts its schema and database code to the target engine.
B: AWS DataSync, which copies large sets of files and objects from on-premises storage systems into AWS storage services.
C: AWS Application Migration Service, which replicates entire source servers so they launch unchanged on Amazon EC2.
D: Amazon RDS Performance Insights, which shows the database load and the SQL statements that consume the most time.
K: A
G: ## Two parts of a heterogeneous migration
Moving between different engines (for example SQL Server to PostgreSQL) needs two steps:
1. **Convert the schema and code**: tables, indexes, views, functions and stored procedures are written in each engine's own dialect and must be translated.
2. **Move the data**: copy the rows, then keep them in sync until cutover.
## AWS tools for each step
- **DMS Schema Conversion** (inside AWS DMS) and the downloadable **AWS Schema Conversion Tool (SCT)** produce an **assessment report** showing what converts automatically and what needs manual work, then convert the schema and code.
- **AWS DMS replication** moves the data with full load and ongoing change data capture.
For a homogeneous migration (for example MySQL to RDS for MySQL), no conversion is needed and native tools or DMS can move the data directly.
W: DMS Schema Conversion: it produces an assessment of how much can be converted automatically and converts the schema, views, functions and stored procedures from SQL Server to PostgreSQL.
X: B=DataSync: it moves files and objects between storage systems. It does not understand database schemas or translate stored procedures.
C=Application Migration Service: it rehosts whole servers on EC2 as they are, so the database would stay SQL Server and nothing would be converted.
D=Performance Insights: it helps tune a running RDS database by showing load and top SQL. It does not assess or convert a source schema.
T: Different source and target engines = convert schema and code with DMS Schema Conversion (or SCT), then move data with DMS.
V: AWS Database Migration Service

@ CLF-C02 D3 T3.4 applied comparison
S: A company currently runs MySQL itself on an Amazon EC2 instance and plans to move it to Amazon RDS for MySQL. Which TWO tasks will RDS take over that the company had to set up and run itself on EC2? (Select TWO)
A: Automated daily backups with transaction logs that allow restoring the database to a point in time.
B: Designing the tables and indexes so that the application's most frequent queries run efficiently.
C: Maintaining a synchronous standby in another Availability Zone with automatic failover, enabled by one setting.
D: Deciding which application users may read or change each table and creating their database accounts.
E: Choosing which customer data the company is legally allowed to store and for how long it is retained.
K: A,C
G: ## What changes when a database becomes managed
On EC2 the company installs and runs everything above the hardware. On Amazon RDS, AWS takes over the undifferentiated operational work:
- **Automated backups**: daily snapshots plus transaction logs, so you can restore to any second within the retention period (**point-in-time recovery**).
- **High availability**: a **Multi-AZ** deployment keeps a synchronous standby in another Availability Zone and fails over automatically. On EC2 you would build replication and failover yourself.
- Provisioning, OS and database engine patching, monitoring metrics and storage scaling.
## What stays with the customer
The data itself and how it is modeled: schema design, indexes and query tuning, database users and permissions, and decisions about which data to keep and for how long. RDS makes running the database easier; it does not decide what is in it.
W: A=Automated backups with point-in-time recovery: RDS takes the daily snapshots and keeps the transaction logs, replacing the backup scripts and storage the company ran on EC2.
C=Multi-AZ standby: RDS builds and maintains the synchronous standby and handles failover automatically once Multi-AZ is turned on, instead of the company configuring replication itself.
X: B=Table and index design: the data model depends on the application, so schema and index design stay with the company on RDS just as on EC2.
D=Database users and permissions: RDS provides the means to create users and grants, but deciding who may access which tables is still the company's job.
E=Data retention decisions: what data may be stored and for how long is a legal and business decision that remains with the customer.
T: RDS takes over backups, failover, patching and provisioning; schema, queries, access decisions and data governance stay with you.
V: Amazon RDS, Amazon EC2

@ CLF-C02 D3 T3.4 applied comparison
S: An online ticketing company is building an order system. Orders, customers, events and payments are related tables that must be joined in SQL reports, and a payment and its seat reservation must succeed or fail together. Which type of database fits best?
A: A key-value database such as Amazon DynamoDB, which looks up single items by key with predictable low latency.
B: A graph database such as Amazon Neptune, which stores entities as nodes and follows the relationships between them.
C: A relational database such as Amazon Aurora, which supports SQL joins across tables and multi-statement transactions.
D: An in-memory cache such as Amazon ElastiCache, which keeps frequently read values in memory for fast retrieval.
K: C
G: ## When a relational database is the right choice
Relational databases store data in tables with a fixed schema and links between tables (foreign keys). They shine when:
- Data is **structured** and related: customers place orders for events, orders have payments.
- You need **SQL joins** for flexible queries and reports across tables.
- You need **ACID transactions** across several statements: reserve the seat and record the payment, or do neither.
## Purpose-built alternatives
- **Key-value** (DynamoDB): massive scale for simple access by key; access patterns must be designed up front.
- **Graph** (Neptune): deep relationship traversal such as social networks.
- **In-memory** (ElastiCache): a speed layer, usually not the system of record.
## Example
`BEGIN; UPDATE seats SET status='sold' WHERE id=42; INSERT INTO payments ...; COMMIT;` Either both changes are saved or neither is.
W: Relational database (Aurora): structured, related data with SQL joins for reports and transactions that commit or roll back several changes together is exactly what relational engines are designed for.
X: A=Key-value (DynamoDB): it is excellent for fast lookups by key, but it does not support SQL joins across tables, so flexible relational reports would be hard to build.
B=Graph (Neptune): it is optimized for traversing many-hop relationships, not for tabular SQL reports and order-processing transactions.
D=In-memory cache (ElastiCache): it speeds up reads of hot data, but it is not meant to be the durable system of record for orders and payments.
T: Structured, related data with joins and multi-statement transactions = relational database (RDS or Aurora).
V: Amazon Aurora, Amazon RDS
