# CLF-C02 b02: D2 Security and Compliance (T2.1 x4, T2.2 x4, T2.3 x4, T2.4 x3)

@ CLF-C02 D2 T2.1 applied use-case
S: A company runs its web application on Amazon EC2 instances that use a Linux operating system the company chose. A new security patch for that operating system has been released. Under the AWS shared responsibility model, who must apply the patch?
A: The company, because the guest operating system on an EC2 instance is part of what the customer configures and maintains.
B: AWS, because every operating system running on AWS hardware is patched automatically during the scheduled host maintenance.
C: AWS and the company equally, because each patch must be approved by both parties before it can be applied to any instance.
D: Neither party, because EC2 instances are rebuilt from a fresh AWS image every night, which removes the need to patch them.
K: A
G: ## The shared responsibility model
AWS splits security work into two layers:
- **Security of the cloud** (AWS): the data centers, physical hosts, the network between them and the virtualization layer (hypervisor) that runs your instances.
- **Security in the cloud** (customer): everything you put on top, such as the operating system you install, your applications, your data, your firewall rules and who can access what.
## Where EC2 sits
Amazon EC2 is Infrastructure as a Service (IaaS). AWS hands you a virtual server; from the guest operating system upward it is yours. That means you install OS patches, update application software and configure security groups. Tools such as AWS Systems Manager Patch Manager can automate patching, but the decision and the responsibility stay with you.
Example: a critical OpenSSL fix comes out for Amazon Linux. AWS patches the hosts and hypervisor underneath, but the copy of OpenSSL inside your instance is updated only when you (or your automation) run the update.
W: Company patches the guest OS: with EC2 the customer controls the operating system, so the customer is responsible for keeping it patched, by hand or with automation such as Systems Manager Patch Manager.
X: B=AWS patches every OS automatically: AWS patches its own hosts and hypervisor, not the guest operating system inside your instance. Managed services such as Amazon RDS are where AWS takes over OS patching.
C=Both must approve each patch: there is no joint approval process. Patch management is a shared control only in the sense that each party patches its own layer.
D=Instances rebuilt nightly: EC2 instances keep running until you stop or replace them. AWS does not reimage them, so an unpatched OS stays unpatched.
T: On EC2, AWS secures the hardware and hypervisor; the customer patches and secures the guest operating system and everything above it.
V: Amazon EC2, AWS Systems Manager

@ CLF-C02 D2 T2.1 applied comparison
S: A company moves its self-managed MySQL database from an Amazon EC2 instance to Amazon RDS for MySQL. Which security task does the company no longer need to perform itself after the move?
A: Installing operating system and database engine patches on the database server.
B: Creating database user accounts and granting each account only the privileges it needs.
C: Configuring security group rules that limit which clients can reach the database port.
D: Deciding whether the database storage should be encrypted with an AWS KMS key.
K: A
G: ## How responsibility shifts with managed services
The more AWS manages, the more of the stack moves to the AWS side of the shared responsibility model.
- **Database on EC2**: you own the operating system, the MySQL installation, its patches, backups, users and network rules.
- **Amazon RDS**: AWS manages the host, the operating system and the database engine software. It applies OS patches and, with automatic minor version upgrades turned on (the default), minor engine patches during a maintenance window you choose; major version upgrades still need your approval.
## What stays with the customer on RDS
- Database users, passwords and privileges inside MySQL.
- Network access: which subnets the DB runs in, whether it is publicly accessible and which security group rules allow connections.
- Encryption choices: enabling encryption at rest with an AWS KMS key and requiring TLS from clients.
- The data itself and how it is classified.
W: OS and engine patching: on Amazon RDS, AWS patches the underlying operating system and the database engine during the maintenance window, so the company stops doing that work itself.
X: B=Database users and privileges: RDS does not know which application or person should read which tables. Creating users and granting least privilege stays with the customer.
C=Security group rules: AWS provides the security group feature, but the customer writes the rules that decide which clients can connect to the database.
D=Encryption decision: AWS supplies encryption at rest with AWS KMS, but the customer decides to turn it on (it is chosen when the DB instance is created; an existing unencrypted instance can only be encrypted by restoring from an encrypted copy of a snapshot) and controls access to the key.
T: Moving from EC2 to RDS hands OS and engine patching to AWS; data, users, network access and encryption choices stay with the customer.
V: Amazon RDS, Amazon EC2

@ CLF-C02 D2 T2.1 applied use-case
S: A team deploys an application as AWS Lambda functions that use an AWS managed runtime. Under the shared responsibility model, which tasks are the team's responsibility? (Select TWO)
A: Fixing security flaws in the function code and in the third-party libraries packaged with it.
B: Granting the function's execution role only the permissions the function actually needs.
C: Patching the operating system of the servers that run the Lambda execution environments.
D: Applying security updates to the managed language runtime that executes the function.
E: Controlling physical access to the data centers that host the Lambda service fleet.
K: A,B
G: ## Serverless moves most of the stack to AWS
With AWS Lambda you upload code and configuration; AWS runs it. That shifts even more work to AWS than Amazon RDS does.
- **AWS manages**: data centers, servers, the operating system of the execution environment, and the managed runtimes (for example Python or Node.js). By default AWS rolls out runtime security updates automatically.
- **Customer manages**: the function code, the libraries you bundle with it, the function's configuration (environment variables, network settings) and its permissions.
## Permissions are always the customer's job
Every Lambda function runs with an **execution role**, an IAM role whose policies decide what the function may do, such as reading one DynamoDB table. Giving it `*` permissions is a customer mistake that AWS cannot fix for you. Least privilege means granting only the actions and resources the function needs.
W: A=Code and bundled libraries: AWS never inspects or patches your application code. A vulnerable package you include in the deployment package is yours to update.
B=Execution role permissions: IAM permissions are always on the customer side, so scoping the execution role to the minimum actions and resources is the team's job.
X: C=Host operating system: Lambda is serverless; AWS operates and patches the servers and operating systems underneath, and customers have no access to them.
D=Managed runtime updates: for managed runtimes AWS publishes the security updates and, in the default mode, applies them to functions automatically. Only custom runtimes or container images make runtime patching the customer's job.
E=Physical data center access: physical security is always part of security of the cloud, which AWS owns for every service.
T: With Lambda, AWS handles servers, OS and managed runtimes; the customer still owns code, bundled libraries, configuration and IAM permissions.
V: AWS Lambda, AWS Identity and Access Management (IAM)

@ CLF-C02 D2 T2.1 applied definition
S: The AWS shared responsibility model describes some controls as "shared controls". Which example best matches a shared control?
A: Patch management, where AWS patches its infrastructure and the customer patches its own guest operating systems and applications.
B: Physical and environmental protection, where the customer fully inherits the data center safeguards that AWS operates and audits.
C: Destruction of failed storage devices, where AWS wipes and physically destroys drives before they leave a secure facility.
D: Routing traffic between security zones inside a customer VPC, where only the customer designs and maintains the network layout.
K: A
G: ## Three kinds of controls
AWS sorts security controls into three groups:
- **Inherited controls**: the customer gets them fully from AWS, with nothing to do. Physical and environmental controls in AWS data centers are the classic example.
- **Shared controls**: the same control applies to both layers, and each party does it for its own part. AWS lists patch management, configuration management, and awareness and training.
- **Customer-specific controls**: only the customer is responsible, such as protecting data inside its own services or segmenting its own network into zones.
## Why "shared" does not mean "joint"
A shared control is not done together. In patch management AWS patches hosts and the hypervisor, and the customer patches guest operating systems and applications. Each party works in its own context.
W: Patch management: it is one control that exists in both layers, with AWS patching the infrastructure and the customer patching what it runs, which is exactly how AWS defines a shared control.
X: B=Physical and environmental protection: customers inherit this entirely from AWS and do nothing themselves, so it is an inherited control, not a shared one.
C=Destruction of failed drives: media sanitization and destruction happen only inside AWS facilities and are done only by AWS, so they sit purely on the AWS side.
D=Routing between security zones: segmenting a VPC is something only the customer designs and runs, which makes it a customer-specific control.
T: Shared controls (patching, configuration management, training) apply to both layers, with AWS and the customer each handling its own part.
V: AWS shared responsibility model

@ CLF-C02 D2 T2.2 applied use-case
S: An external auditor asks a company for the AWS SOC 2 report and the AWS PCI DSS Attestation of Compliance to review how AWS secures its infrastructure. Where can the company download these documents?
A: AWS Artifact, which offers on-demand access to AWS security and compliance reports and to select online agreements.
B: AWS Config, which records resource configurations over time and checks them against rules the company defines.
C: AWS Audit Manager, which collects evidence about the company's own AWS usage and maps it to compliance frameworks.
D: AWS Trusted Advisor, which inspects the company's account and recommends improvements for security and cost.
K: A
G: ## Proving that AWS itself is compliant
Under the shared responsibility model, a company's auditor needs two kinds of evidence:
- Evidence about **AWS's layer**: independent audit reports showing that AWS data centers and services meet standards such as SOC 1/2/3, ISO 27001 and PCI DSS.
- Evidence about the **customer's layer**: how the company configured its own accounts and workloads.
## AWS Artifact
AWS Artifact is a self-service portal in the AWS Management Console for the first kind. It offers:
- **Artifact Reports**: downloadable third-party audit reports and certifications, such as SOC reports, PCI DSS attestations and ISO certificates.
- **Artifact Agreements**: online agreements such as the Business Associate Addendum (BAA) for HIPAA workloads.
The company can pass these documents to its auditor without opening a support case.
W: AWS Artifact: it is the AWS service for downloading AWS's own third-party audit reports and attestations, including SOC and PCI DSS documents, on demand.
X: B=AWS Config: Config tracks and evaluates the company's resource settings. It produces evidence about the customer's configuration, not AWS's audit reports.
C=AWS Audit Manager: it gathers evidence about the customer's own usage, not AWS's reports, and it has been closed to new customers since 2026-04-30, so a company that does not already use it cannot turn it on.
D=AWS Trusted Advisor: it gives best-practice recommendations for the company's account. It does not provide third-party audit reports about AWS.
T: AWS compliance reports (SOC, PCI, ISO) and agreements such as the BAA come from AWS Artifact.
V: AWS Artifact

@ CLF-C02 D2 T2.2 applied troubleshooting
S: An Amazon EC2 instance in a production account was terminated yesterday, and nobody admits to doing it. Which AWS service lets the administrator find which identity made the termination request and when?
A: AWS CloudTrail, which records API calls in the account, including the caller identity, time and source IP address.
B: Amazon CloudWatch, which collects metrics such as CPU use and can raise alarms when a value crosses a threshold.
C: VPC Flow Logs, which capture information about IP traffic going to and from network interfaces in the VPC.
D: Amazon Inspector, which scans EC2 instances and container images for software vulnerabilities and network exposure.
K: A
G: ## Every AWS action is an API call
Whether someone clicks in the console, runs the AWS CLI or uses an SDK, the action becomes an API call such as `TerminateInstances`. AWS CloudTrail records these calls.
## What a CloudTrail event shows
- **Who**: the IAM user, role or root user that made the call.
- **What**: the API action and the resources involved.
- **When and from where**: the timestamp and source IP address.
CloudTrail **event history** keeps the last 90 days of management events in each Region at no extra cost, so a termination from yesterday is already there. To keep events longer, create a trail that delivers them to an Amazon S3 bucket.
Example: filtering event history for event name `TerminateInstances` shows the role `ops-admin` called it at 22:14 from a specific IP address.
W: AWS CloudTrail: it logs account activity as API events with the caller identity and time, which is exactly what is needed to answer "who terminated this instance".
X: B=Amazon CloudWatch: CloudWatch metrics would show the instance stopped reporting, but they do not record which identity made the API call.
C=VPC Flow Logs: flow logs describe network traffic only (addresses, ports, protocol, accept or reject). They hold no API action names and no IAM identity, so they cannot show who requested the termination.
D=Amazon Inspector: Inspector finds vulnerabilities in workloads. It does not track who performed actions in the account.
T: "Who did what, and when" in an AWS account is answered by AWS CloudTrail.
V: AWS CloudTrail

@ CLF-C02 D2 T2.2 applied comparison
S: A company's security policy says every Amazon EBS volume must be encrypted. The security team wants to be told automatically when a non-compliant volume appears and to see how each volume's settings have changed over time. Which AWS service meets these needs?
A: AWS Config, using a rule that evaluates whether EBS volumes are encrypted and its record of configuration history.
B: AWS CloudTrail, using its record of API calls to list every volume that a user created in the account today.
C: AWS Artifact, using its compliance reports to confirm that the EBS service supports encryption of all volumes.
D: Amazon Inspector, using its vulnerability scans to detect operating systems that were installed on unencrypted disks.
K: A
G: ## Two questions an auditor asks
- **Who changed something?** That is an activity question, answered by AWS CloudTrail.
- **What does the resource look like now, and does it follow our rules?** That is a configuration question, answered by AWS Config.
## How AWS Config works
AWS Config records the configuration of supported resources and keeps a **configuration history**, so you can see what a volume, security group or bucket looked like at any point. **Config rules** evaluate those configurations against a desired state and mark each resource compliant or non-compliant.
- AWS provides many **managed rules**, for example `encrypted-volumes`, which checks that attached EBS volumes are encrypted.
- Non-compliant results can trigger notifications through Amazon EventBridge or Amazon SNS, and some rules can run automatic remediation.
W: AWS Config: a managed rule flags any EBS volume that is not encrypted, and the configuration history shows how each volume's settings changed, which covers both requirements.
X: B=AWS CloudTrail: CloudTrail shows the API call that created a volume, but it does not evaluate whether the resulting volume follows a rule or keep a per-resource configuration timeline.
C=AWS Artifact: Artifact proves that AWS meets its own compliance programs. It says nothing about whether this company's volumes are encrypted.
D=Amazon Inspector: Inspector scans workloads for software vulnerabilities and network exposure. It does not evaluate EBS encryption settings against a policy.
T: Continuous checks of resource settings against rules, plus configuration history, is the job of AWS Config.
V: AWS Config, Amazon EBS

@ CLF-C02 D2 T2.2 applied use-case
S: A healthcare company in Japan must keep patient records stored only in Japan and must encrypt them at rest. The records will be stored in Amazon S3. Which actions meet these requirements? (Select TWO)
A: Create the S3 bucket in an AWS Region located in Japan, because AWS does not move content out of the Region the customer chooses.
B: Configure the bucket's default encryption to use server-side encryption with an AWS KMS key that the company manages.
C: Put Amazon CloudFront in front of the bucket so the records are cached at edge locations near patients worldwide.
D: Download a Japanese compliance report from AWS Artifact, which then restricts all of the account's data to Japan.
E: Enable AWS Shield Advanced on the bucket so the records are encrypted while they travel across the internet.
K: A,B
G: ## Data residency on AWS
Data residency means content must be stored in a particular country or jurisdiction. On AWS the customer controls this by choosing the **Region**. AWS commits not to move or replicate customer content outside the chosen Regions without the customer's agreement. Japan has the Asia Pacific (Tokyo) and Asia Pacific (Osaka) Regions.
Features that copy data elsewhere, such as S3 Cross-Region Replication or caching at CloudFront edge locations around the world, are choices the customer makes and must avoid if the data has to stay put.
## Encryption at rest and in transit
- **At rest**: data stored on disk is encrypted. S3 encrypts every new object by default with S3 managed keys (SSE-S3); choosing SSE-KMS with an AWS KMS key gives the company control over key policies and an audit trail of key use in CloudTrail.
- **In transit**: data moving over the network is protected with TLS (HTTPS), for example by requiring secure transport in a bucket policy.
W: A=Bucket in a Japan Region: the customer picks where content lives, and AWS keeps it in that Region, which satisfies the residency requirement.
B=SSE-KMS default encryption: it encrypts every stored object at rest with a KMS key the company controls, which satisfies the encryption requirement.
X: C=CloudFront edge caching: CloudFront copies content to edge locations in many countries, which works against keeping the records only in Japan.
D=Artifact report restricts data: Artifact only provides compliance documents to download. Reading a report does not change where any data is stored.
E=Shield Advanced encrypts traffic: Shield protects against DDoS attacks and does not encrypt anything. Encryption in transit comes from TLS.
T: Data residency is controlled by the Region you choose; encryption at rest on S3 is a bucket setting, with SSE-KMS adding key control.
V: Amazon S3, AWS Key Management Service (AWS KMS)

@ CLF-C02 D2 T2.3 applied use-case
S: A startup has just created a new AWS account using the founder's email address. Which action follows AWS best practices for protecting the root user?
A: Enable multi-factor authentication on the root user and use separate identities with limited permissions for everyday work.
B: Create access keys for the root user so administrators can run automation scripts with full permissions from their laptops.
C: Share the root user password with every administrator through a password manager so the account is never locked out.
D: Keep using the root user for daily administration, but change its password every month and choose a longer passphrase.
K: A
G: ## What the root user is
The root user is the identity created with the account, signed in with the account email address and password. It has complete, unrestricted access to every resource and setting, and IAM policies cannot limit it within its own account (only AWS Organizations service control policies can, for member accounts).
## Protecting it
- Turn on **MFA** for the root user, so a stolen password alone is not enough to sign in.
- Do **not** create root access keys; delete any that exist.
- Use the root user only for the few tasks that require it, such as changing some account settings or restoring locked-out IAM permissions.
- For daily work, use IAM Identity Center users or IAM roles that have only the permissions each person needs.
W: Root MFA plus separate everyday identities: MFA blocks sign-in with a stolen password, and doing routine work with limited identities keeps the all-powerful root credentials out of daily use.
X: B=Root access keys for automation: long-term root keys can do anything in the account if leaked, and they cannot be restricted by IAM policies. AWS recommends having no root access keys at all.
C=Shared root password: sharing one credential removes accountability (no one can tell who did what) and multiplies the chances of it leaking.
D=Daily root use with rotation: a long, rotated password still leaves the most powerful identity in constant use, and the plan adds no MFA. Rotation does not replace MFA or least privilege.
T: Lock away the root user: enable MFA, create no access keys, and use limited identities for everyday tasks.
V: AWS Identity and Access Management (IAM)

@ CLF-C02 D2 T2.3 applied use-case
S: An application on an Amazon EC2 instance must read objects from one Amazon S3 bucket. The security team wants no long-term credentials stored on the instance and wants to follow least privilege. Which solution meets these requirements?
A: Attach an IAM role to the instance with a policy that allows only reading objects from that one bucket.
B: Create an IAM user with full S3 access and save its access keys in the application's configuration file.
C: Generate access keys for the root user and pass them to the instance through environment variables at boot.
D: Make the S3 bucket public so the application can read objects without needing any AWS credentials.
K: A
G: ## IAM identities and policies
- An **IAM user** has long-term credentials (a password and/or access keys) that stay valid until someone rotates or deletes them.
- An **IAM role** has no long-term credentials. Whoever assumes it receives **temporary credentials** that expire automatically.
- A **policy** is a JSON document that lists allowed or denied actions on resources, for example `s3:GetObject` on `arn:aws:s3:::reports-bucket/*`.
## Roles for EC2
When you attach a role to an EC2 instance (through an instance profile), the instance metadata service hands temporary credentials to the application, and the AWS SDKs pick them up automatically and refresh them before they expire. Nothing secret is written into code or files.
## Least privilege
Grant only the actions and resources needed. Read access to one bucket means `s3:GetObject` on that bucket, not `s3:*` on every bucket.
W: IAM role with a read-only policy for one bucket: the instance gets automatically rotated temporary credentials, and the policy limits it to reading that single bucket, which meets both requirements.
X: B=IAM user keys in a config file: these are long-term credentials stored on disk, and full S3 access is far more than the application needs.
C=Root access keys at boot: root credentials have unlimited power, cannot be scoped by IAM policies and should never be created, let alone placed on a server.
D=Public bucket: it removes the need for credentials by letting anyone on the internet read the data, which breaks least privilege completely.
T: Give AWS workloads permissions through IAM roles (temporary credentials) with the narrowest policy that works.
V: AWS Identity and Access Management (IAM), Amazon EC2, Amazon S3

@ CLF-C02 D2 T2.3 applied comparison
S: An administrator must give eight new IAM users in one AWS account the same set of permissions, and expects those permissions to change several times over the next year. What is the most manageable way to assign them?
A: Create an IAM group, attach the required policies to the group, and add all eight users as members.
B: Attach a separate copy of the same inline policy to each of the eight users and edit every copy on change.
C: Create one shared IAM user for the team and give its password to all eight people who need the access.
D: Add the eight users to the account's root user so they inherit its permissions while their work is reviewed.
K: A
G: ## IAM groups
An IAM group is a collection of IAM users. Policies attached to the group apply to every member, so you manage permissions in one place:
- A new team member is added to the group and receives the same permissions immediately.
- A permission change is made once on the group policy and applies to everyone.
- Someone who changes jobs is removed from the group and loses those permissions.
Groups only contain users; a group cannot contain another group and cannot be used to sign in.
## A note on current best practice
For people who sign in to AWS, AWS now recommends AWS IAM Identity Center with permission sets, which applies the same "manage permissions for a set of people in one place" idea across many accounts. Inside a single account with IAM users, groups are the tool.
W: IAM group with attached policies: every member gets the group's permissions, and later changes are made once instead of eight times, while each person keeps an individual identity.
X: B=Inline policy per user: it works on day one, but every change must be repeated on eight separate policies, which invites drift and mistakes.
C=One shared IAM user: shared credentials hide who did what in CloudTrail and make it impossible to remove one person's access without affecting everyone.
D=Users under the root user: IAM users cannot be placed under the root user or inherit its permissions; root access is never a way to grant routine permissions.
T: Give the same permissions to several IAM users by attaching policies to an IAM group, not to each user.
V: AWS Identity and Access Management (IAM)

@ CLF-C02 D2 T2.3 applied use-case
S: A company has 30 AWS accounts in AWS Organizations. Employees should sign in once with their existing corporate identity provider and then reach only the accounts and permissions their job needs. Which AWS service is designed for this?
A: AWS IAM Identity Center, which connects to the identity provider and assigns permission sets to users for each account.
B: Amazon Cognito user pools, which let customers of a web or mobile app sign up and sign in with social identity providers.
C: IAM users created separately in each of the 30 accounts, with the same user names and passwords in every account.
D: AWS Directory Service, which runs managed Microsoft Active Directory domain controllers for Windows workloads in a VPC.
K: A
G: ## Workforce access across many accounts
When a company runs many AWS accounts, creating IAM users in each one quickly becomes unmanageable: people have many passwords, and removing a leaver means visiting every account.
## AWS IAM Identity Center
IAM Identity Center (the successor to AWS Single Sign-On) is the recommended way for people in an organization to access AWS.
- It connects to an existing identity source such as Microsoft Entra ID or Okta, or uses its own built-in directory.
- **Permission sets** define what a user can do (for example read-only or developer access). Identity Center creates matching IAM roles in the accounts you assign.
- Users sign in once to an access portal and choose an account and role; they receive temporary credentials.
Disabling the user in the corporate directory removes access to every account at once.
W: AWS IAM Identity Center: it provides single sign-on with the corporate identity provider and assigns permission sets per account across AWS Organizations, which matches the requirement exactly.
X: B=Amazon Cognito user pools: Cognito manages sign-up and sign-in for an application's end users, such as shoppers in a mobile app. It does not grant employees access to AWS accounts.
C=IAM users in every account: 30 separate sets of long-term credentials are hard to keep in sync and to remove, and they do not give single sign-on with the corporate directory.
D=AWS Directory Service: it provides an Active Directory for workloads to use. It can serve as an identity source, but on its own it does not assign people to AWS accounts and permissions.
T: Employee sign-in across many AWS accounts with permission sets and an existing identity provider is the job of IAM Identity Center.
V: AWS IAM Identity Center, AWS Organizations

@ CLF-C02 D2 T2.4 applied comparison
S: A security team sees malicious traffic coming from one specific IP address and wants to block that address from reaching every instance in a subnet. Which control can do this directly?
A: A network ACL on the subnet with a deny rule for that IP address, since network ACLs support both allow and deny rules.
B: A security group on each instance with a deny rule for that IP address, since security groups evaluate deny rules first.
C: A route table entry that sends the attacker's IP address to the internet gateway, so its packets are returned unanswered.
D: An IAM policy with an explicit deny for that IP address, attached to the subnet so the address cannot send traffic to it.
K: A
G: ## Two VPC firewalls
- **Security groups** act at the level of an instance's network interface. They contain **allow rules only**: anything not allowed is denied. They are **stateful**, so return traffic for an allowed connection is allowed automatically.
- **Network ACLs** act at the **subnet** boundary. They contain numbered **allow and deny** rules evaluated in order, lowest number first. They are **stateless**, so return traffic must be allowed by its own rule.
## Blocking one address
Because security groups cannot express "deny", the built-in VPC control for blocking a single IP address while allowing everyone else is a network ACL rule such as rule 90 `DENY 203.0.113.25/32`, placed before a broader allow rule. For web applications, AWS WAF IP set rules are another option at the load balancer or CloudFront, and AWS Network Firewall can do it for larger network designs.
W: Network ACL deny rule: network ACLs protect the whole subnet and support explicit deny rules, so a low-numbered rule can block that one address for every instance in the subnet.
X: B=Security group deny rule: security groups have allow rules only. There is no way to write a deny entry, so a single address cannot be blocked while others stay allowed.
C=Route to the internet gateway: route tables decide where outbound traffic from the subnet goes. They cannot filter inbound packets by source address.
D=IAM policy on the subnet: IAM policies control who can call AWS APIs, not which packets reach an instance, and they are not attached to subnets.
T: Security groups: instance-level, stateful, allow only. Network ACLs: subnet-level, stateless, allow and deny.
V: Amazon VPC

@ CLF-C02 D2 T2.4 applied use-case
S: A public web application runs behind an Application Load Balancer. Logs show SQL injection attempts, and the company also wants enhanced DDoS protection with access to an AWS response team during attacks. Which services should the company use? (Select TWO)
A: AWS WAF, with rules that inspect web requests and block common SQL injection patterns.
B: AWS Shield Advanced, which adds DDoS detection, mitigation and Shield Response Team support.
C: Amazon GuardDuty, which analyzes account logs to find compromised instances and credentials.
D: Amazon Macie, which discovers and reports sensitive data such as personal information in S3.
E: AWS Secrets Manager, which stores database passwords and rotates them on a regular schedule.
K: A,B
G: ## Protecting a web application at the edge
- **AWS WAF** is a web application firewall. You attach a web ACL to an Application Load Balancer, Amazon CloudFront distribution, Amazon API Gateway API and similar resources. Rules inspect HTTP requests and can block SQL injection, cross-site scripting, bad IP addresses or excessive request rates. AWS Managed Rules, such as the SQL database rule group, give ready-made protections.
- **AWS Shield Standard** protects every AWS customer from common network and transport layer DDoS attacks at no extra cost.
- **AWS Shield Advanced** is a paid subscription that adds enhanced detection and mitigation for resources such as load balancers and CloudFront, attack visibility, cost protection for scaling during an attack and access to the **Shield Response Team (SRT)** (engaging the SRT requires a business-level or higher paid AWS Support plan).
## Detection is not blocking
Services such as GuardDuty and Macie find problems and report them; they do not sit in front of the application to stop requests.
W: A=AWS WAF: its rules inspect requests reaching the load balancer and block SQL injection patterns before they reach the application.
B=AWS Shield Advanced: it provides enhanced DDoS protection and access to the Shield Response Team, which the company specifically asked for.
X: C=Amazon GuardDuty: GuardDuty detects threats from logs and reports findings. It does not inspect or block HTTP requests to the load balancer and offers no DDoS response team.
D=Amazon Macie: Macie classifies data stored in S3. It has nothing to do with web requests or DDoS attacks.
E=AWS Secrets Manager: it protects credentials such as the database password, but it does not stop injection requests or absorb DDoS traffic.
T: Block web exploits such as SQL injection with AWS WAF; add DDoS response team support and cost protection with AWS Shield Advanced.
V: AWS WAF, AWS Shield, Elastic Load Balancing

@ CLF-C02 D2 T2.4 applied comparison
S: A security team wants a managed service that continuously analyzes AWS CloudTrail events, VPC Flow Logs and DNS query logs to detect threats such as compromised credentials or instances communicating with known malicious IP addresses. Which service should the team enable?

G: ## The AWS security services, by question they answer
- **Amazon GuardDuty**: "Is something malicious happening in my account?" It analyzes CloudTrail management events, VPC Flow Logs and DNS logs (plus optional sources such as S3 data events and EKS audit logs) with threat intelligence and machine learning. Example findings: an EC2 instance talking to a known command-and-control server, or access keys used from an unusual location.
- **Amazon Inspector**: "Which of my workloads have known software vulnerabilities (CVEs) or unintended network exposure?"
- **Amazon Macie**: "Where is sensitive data, such as personal information, stored in S3?"
- **Amazon Detective**: "What led up to this finding?" It helps investigate findings after detection.
- **AWS Security Hub CSPM**: "How do all these findings and best-practice checks look in one place?"
GuardDuty's foundational data sources need no agents or log pipelines; you enable it and it reads them itself (only optional features such as Runtime Monitoring use an agent).
W: Amazon GuardDuty: it is the threat detection service that continuously analyzes CloudTrail, VPC Flow Logs and DNS logs and reports findings such as compromised credentials or contact with malicious IP addresses.
X: B=Amazon Inspector: Inspector looks for vulnerable software packages and network reachability in workloads. It does not watch account activity or network logs for active threats.
C=Amazon Macie: Macie finds and classifies sensitive data in S3. It does not analyze flow logs or DNS logs for attacks.
D=Amazon Detective: Detective helps investigate a finding after it is raised, often a GuardDuty finding. It is not the service that detects the threat in the first place.
T: Threat detection from CloudTrail, VPC Flow Logs and DNS logs is Amazon GuardDuty; Inspector finds vulnerabilities, Macie finds sensitive data, Detective investigates.
V: Amazon GuardDuty, Amazon Inspector, Amazon Macie, Amazon Detective
