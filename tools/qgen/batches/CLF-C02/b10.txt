# CLF-C02 D3 Cloud Technology and Services (22 questions: T3.1 x11, T3.2 x11)

@ CLF-C02 D3 T3.1 applied use-case
S: A logistics company is writing a Python application that must upload delivery photos to Amazon S3 and write tracking records to Amazon DynamoDB as part of its normal code. Which way of interacting with AWS fits this best?
A: The AWS Management Console, where an operator opens the S3 and DynamoDB pages and adds each photo and record through the web forms.
B: An AWS SDK for Python (Boto3), which lets the application code call the S3 and DynamoDB APIs directly with signed requests.
C: AWS CloudFormation, which declares the S3 bucket and the DynamoDB table in a template and creates them together as one stack.
D: The AWS Console Mobile Application, which lets staff view resources and perform selected tasks from a phone while away from a desk.
K: B
G: ## Four ways to work with AWS
Every action on AWS, whether it creates a server or stores a file, is an **API call** to an AWS service. The tools differ only in who or what makes that call.
- **AWS Management Console**: a website. Good for exploring, learning and one-time tasks done by a person.
- **AWS CLI**: commands typed in a terminal or put in shell scripts, for example `aws s3 cp photo.jpg s3://my-bucket/`.
- **AWS SDKs**: libraries for programming languages (Python, Java, JavaScript, Go, .NET and others). Application code calls AWS services as part of its own logic. The SDK signs each request with the application's credentials and retries temporary errors.
- **Infrastructure as code** (CloudFormation, AWS CDK): describes the resources that should exist, such as the bucket and the table, not the data the application puts into them.
## Example
With Boto3 the app runs `s3.put_object(Bucket="photos", Key="d123.jpg", Body=data)` each time a driver finishes a delivery. No person needs to be involved.
W: AWS SDK (Boto3): the application itself must store photos and records while it runs, and an SDK is the tool built for calling AWS service APIs from program code in a familiar language.
X: A=Management Console: it is a web interface for people. Adding every photo and record by hand cannot keep up with an application and is not part of its code.
C=CloudFormation: it creates and manages the bucket and the table as infrastructure. It does not upload photos or write items while the application runs.
D=Console Mobile Application: it lets people check resources and do a limited set of tasks from a phone. It is not a way for application code to call AWS.
T: Application code that calls AWS services = AWS SDK; people clicking = Console; terminal and scripts = CLI; resource definitions = CloudFormation or CDK.
V: AWS SDKs, Amazon S3, Amazon DynamoDB

@ CLF-C02 D3 T3.1 applied comparison
S: A software team wants to define its AWS infrastructure in TypeScript, the language it already uses, so it can use loops, classes and its usual code editor to build many similar resources. The result should still be deployed as CloudFormation stacks. Which service should it use?
A: AWS Elastic Beanstalk, which takes the team's application code and deploys it on a managed platform with capacity and load balancing.
B: AWS Systems Manager, which runs commands and automation documents across fleets of instances to configure them after launch.
C: AWS Cloud Development Kit (AWS CDK), which turns infrastructure code written in common programming languages into CloudFormation templates.
D: AWS CloudFormation StackSets, which deploy one existing CloudFormation template to many AWS accounts and Regions in one operation.
K: C
G: ## Infrastructure as code in a programming language
AWS CloudFormation reads templates written in JSON or YAML. Templates are clear, but long ones repeat a lot, and they have limited logic.
The **AWS Cloud Development Kit (AWS CDK)** lets developers write infrastructure in TypeScript, JavaScript, Python, Java, C# or Go.
- You combine ready-made building blocks called **constructs**, for example a VPC or a load-balanced container service.
- You can use loops, functions, classes and unit tests like in any other code.
- `cdk synth` turns the code into a CloudFormation template, and `cdk deploy` deploys it as a CloudFormation stack.
## Example
A loop `for (const name of ["orders", "billing", "users"])` can create three queues with the same settings, instead of copying the same YAML block three times.
W: AWS CDK: the team writes infrastructure in TypeScript with normal programming features, and the CDK synthesizes CloudFormation templates and deploys them as stacks, which is exactly what was asked.
X: A=Elastic Beanstalk: it deploys and runs application code on a managed platform. It is not a way to describe general infrastructure in a programming language.
B=Systems Manager: it manages and configures servers that already exist, for example by running commands or patching. It does not define infrastructure as code that becomes CloudFormation stacks.
D=StackSets: they spread an existing template across accounts and Regions, but the template is still JSON or YAML. They do not let the team write the infrastructure in TypeScript.
T: Infrastructure as code in a familiar programming language that deploys through CloudFormation = AWS CDK.
V: AWS CDK, AWS CloudFormation

@ CLF-C02 D3 T3.1 applied tradeoff
S: An operations team does most of its AWS work in the Management Console. Which TWO tasks would benefit most from being moved into infrastructure as code templates? (Select TWO)
A: Opening the billing dashboard once to check whether last month's charges look reasonable before a budget meeting.
B: Creating an identical test environment for every release branch and removing it after testing ends a few days later.
C: Browsing the list of instance types once to compare memory sizes while drafting an early design for a new project.
D: Keeping a standby copy of the production environment in a second Region that must match production after every change.
E: Viewing a single CloudWatch graph once to see how CPU use changed during an incident that happened earlier today.
K: B,D
G: ## One-time versus repeatable operations
Not every task needs automation. A useful rule:
- **One-time or exploratory tasks** (looking at a bill, reading a graph, trying a service for the first time) are fine in the **Management Console**. Writing code for them costs more time than it saves.
- **Repeatable tasks** (building the same environment again and again, keeping two environments identical) belong in **infrastructure as code** (CloudFormation or AWS CDK).
## Why IaC helps with repeatable work
- The same template always builds the same resources, so there is no "someone forgot a setting" drift.
- Templates are kept in version control, so every change is reviewed and can be rolled back.
- A whole environment can be created or deleted as one stack in minutes.
## Example
A team that creates a test environment per branch runs `deploy` when the branch opens and `delete` when it merges. Doing that by hand in the console ten times a month would be slow and error-prone.
W: B=Per-branch test environments: the same environment is built and torn down many times, so a template guarantees each copy is identical and removing it deletes every resource at once.
D=Standby copy in a second Region: the copy must keep matching production, and deploying the same template in both Regions after each change keeps them in step without manual rework.
X: A=Checking last month's bill: this is a one-time look at information. There is nothing to build or repeat, so the console is the right tool.
C=Browsing instance types: comparing options while sketching a design is exploration. It creates no resources, so there is nothing to describe in a template.
E=Viewing one graph: reading a CloudWatch metric after an incident is a single investigation step, not infrastructure that needs to be recreated.
T: One-time or exploratory work = console; repeated or must-stay-identical environments = infrastructure as code.
V: AWS CloudFormation, AWS CDK

@ CLF-C02 D3 T3.1 applied use-case
S: An insurance company has 300 employees working from home on their own internet connections. They need secure access to internal applications that run on private IP addresses in an Amazon VPC. Which AWS service meets this need?
A: AWS Site-to-Site VPN, which connects an on-premises network router to a virtual private gateway or transit gateway with two IPsec tunnels.
B: AWS Direct Connect, which provides a dedicated physical link from a colocation facility to AWS that bypasses the public internet.
C: VPC peering, which connects two Amazon VPCs so their resources can reach each other using private IP addresses.
D: AWS Client VPN, a managed service that lets each user's device open an encrypted VPN session into the VPC over the internet.
K: D
G: ## Connecting people versus connecting networks
- **AWS Client VPN** connects **individual users**. Each employee installs an OpenVPN-based client on a laptop, signs in (for example with Active Directory or SAML single sign-on), and gets an encrypted tunnel to the VPC from wherever they are.
- **AWS Site-to-Site VPN** connects a **whole network**, such as an office or a data center, through its router.
- **AWS Direct Connect** is a **dedicated line** from a data center or colocation facility to AWS.
- **VPC peering** connects **two VPCs** to each other. It does not involve users outside AWS.
## Example
An employee at home starts the VPN client, signs in, and can then open `http://10.0.2.15` (an internal app in the VPC). Without the VPN, that private address cannot be reached from the internet.
W: Client VPN: it is a managed, scalable VPN for individual devices, so 300 remote employees can reach private VPC applications securely over their home internet connections.
X: A=Site-to-Site VPN: it joins a network with its own VPN router to AWS. Employees at home do not sit behind a shared company router, so each would have no tunnel.
B=Direct Connect: it needs a physical circuit to a fixed location. It cannot serve hundreds of people working from different homes.
C=VPC peering: it links one VPC to another VPC. The employees' laptops are not in a VPC, so peering gives them no access.
T: Individual remote users into a VPC = Client VPN; an office or data center network = Site-to-Site VPN or Direct Connect.
V: AWS Client VPN

@ CLF-C02 D3 T3.1 applied tradeoff
S: A retail chain is starting a three-month pilot that sends small amounts of sales data from one store's network to an Amazon VPC. The link must be encrypted, working within a day, and cheap. Which connectivity option fits best?
A: AWS Site-to-Site VPN, which builds encrypted IPsec tunnels between the store's router and AWS over the store's existing internet link.
B: AWS Direct Connect, which orders a dedicated private circuit from the store's network to a Direct Connect location near the Region.
C: AWS Client VPN, which installs a VPN client on each store employee's laptop so every person opens a tunnel into the VPC.
D: An internet gateway in the VPC, which lets the store's servers send the sales data to public IP addresses of the VPC instances.
K: A
G: ## Picking a network connection for a hybrid setup
When an on-premises network must reach a VPC, weigh speed of setup, cost, performance and encryption.
- **Site-to-Site VPN**: uses the internet link you already have. You create the VPN connection in AWS, download a configuration for your router, and the IPsec tunnels can be up within hours. You pay per connection-hour plus data transfer. Traffic is encrypted. Performance depends on the internet.
- **Direct Connect**: a dedicated circuit. Consistent performance and high bandwidth, but ordering and installing it often takes weeks, and it costs more. It is not encrypted by default.
- **Client VPN**: for individual users, not a network-to-network link.
## Typical pattern
Many companies start with a Site-to-Site VPN for a pilot and add Direct Connect later if traffic grows.
W: Site-to-Site VPN: it reuses the store's internet connection, can be configured in hours, costs little for small volumes, and encrypts the traffic with IPsec, which matches every requirement of the pilot.
X: B=Direct Connect: provisioning a physical circuit usually takes weeks and costs more, which is out of proportion for a short pilot with small data volumes.
C=Client VPN: it gives individual users tunnels from their devices. The requirement is to connect the store's network systems, not each employee's laptop.
D=Internet gateway: it lets instances use public IP addresses on the internet. It does not create an encrypted private link, so the data would travel unprotected unless the app added its own encryption.
T: Quick, cheap and encrypted over the existing internet link = Site-to-Site VPN; consistent, dedicated and slower to set up = Direct Connect.
V: AWS Site-to-Site VPN

@ CLF-C02 D3 T3.1 applied definition
S: A manufacturing company keeps its plant-floor control systems in its own data center, runs its new online ordering website on AWS, and connects the two so orders flow to the plant. Which cloud deployment model is this?
A: A cloud (all-in) deployment, because the online ordering website and its data run entirely on AWS managed services.
B: A hybrid deployment, because workloads run both on premises and in the AWS Cloud and the two environments are connected.
C: An on-premises (private cloud) deployment, because the plant control systems stay on servers in the company's own data center.
D: A multi-Region deployment, because the company uses more than one physical location to run its business applications.
K: B
G: ## The three cloud deployment models
- **Cloud (all-in)**: every part of the application runs in the cloud. There is no company data center in the design.
- **Hybrid**: some workloads stay on premises and others run in the cloud, and the two are connected (for example with Site-to-Site VPN or Direct Connect) so they work together.
- **On-premises (private cloud)**: everything runs in the company's own data center, often with virtualization and self-service tools that feel cloud-like, but on hardware the company owns.
## Why companies choose hybrid
- Some systems cannot move yet: they depend on local machines, need very low latency to equipment, or run on old hardware.
- New projects can still use AWS for elasticity and speed.
Note that "multi-Region" describes where AWS resources are placed. It is an architecture choice inside the cloud, not a deployment model.
W: Hybrid deployment: part of the business runs in the company's own data center and part runs on AWS, and the two environments are connected to work as one system.
X: A=Cloud deployment: the ordering site is in the cloud, but the control systems remain on premises, so the whole design is not all-in cloud.
C=On-premises deployment: the plant systems are local, but the website runs on AWS, so not everything is in the company's data center.
D=Multi-Region deployment: this term means placing AWS resources in several AWS Regions. It is not a deployment model, and the company uses only one cloud location.
T: Some workloads on premises + some in AWS + connected = hybrid deployment.
V: AWS global infrastructure

@ CLF-C02 D3 T3.1 applied definition
S: A national research agency runs all of its applications on servers it owns in its own facility. It uses virtualization and a self-service portal so teams can request virtual machines, and it uses no public cloud provider. Which deployment model describes this setup?
A: A hybrid deployment, because the agency's self-service portal gives teams a cloud-like experience for requesting new virtual machines.
B: A cloud deployment, because teams can create virtual machines on demand without waiting for new physical servers to be purchased.
C: An on-premises deployment, also called a private cloud, because all resources run on the agency's own hardware in its own facility.

An **on-premises** deployment, also called a **private cloud**, uses hardware the organization owns or leases in its own facility.

- The organization still buys, powers, cools, patches and replaces all hardware itself, and total capacity is limited to what it has bought.

@ CLF-C02 D3 T3.1 applied definition
S: A new cloud engineer asks how the AWS Management Console, the AWS CLI and the AWS SDKs differ in the way they reach AWS services. Which statement is correct?
A: All three send authenticated requests to the AWS service APIs, so IAM permissions apply the same way whichever tool is used.
B: The CLI and SDKs bypass IAM policies because they use access keys, while only the Management Console checks user permissions.
C: The Management Console changes resources directly on AWS hardware, so its actions are not recorded by AWS CloudTrail as API calls.
D: The SDKs can only be used by code that runs on Amazon EC2, while the CLI is required for any automation from outside AWS.
K: A
G: ## Everything is an API call
Each AWS service exposes an **API**: a set of operations such as `RunInstances` for Amazon EC2 or `PutObject` for Amazon S3.
- The **Management Console** is a web interface that calls these APIs for you when you click.
- The **AWS CLI** turns commands like `aws ec2 run-instances` into the same API calls.
- The **AWS SDKs** let program code make the same calls in Python, Java, JavaScript and other languages.
## Why it matters
- **One permission model**: every request is signed with credentials and checked by IAM. A user who is denied `ec2:TerminateInstances` is denied in the console, the CLI and the SDK alike.
- **One audit trail**: AWS CloudTrail records API calls no matter which tool made them.
- **Freedom to automate**: something you learned to do by clicking can usually be scripted with the CLI or built into an application with an SDK.
W: Same APIs, same IAM checks: the console, CLI and SDKs are different front ends for the same signed API requests, so IAM evaluates permissions identically in each case.
X: B=CLI and SDKs bypass IAM: access keys are just another kind of credential. Every request signed with them is still checked against the caller's IAM policies.
C=Console not logged by CloudTrail: the console works by calling the service APIs, and CloudTrail records those calls just like calls from the CLI or SDKs, including the console sign-in itself.
D=SDKs only on EC2: SDKs run anywhere the code runs, such as laptops, on-premises servers, containers or Lambda functions, as long as it has credentials and network access.
T: Console, CLI and SDKs all call the same AWS APIs, so the same IAM permissions and CloudTrail logging apply to each.
V: AWS Management Console, AWS CLI, AWS SDKs, AWS IAM

@ CLF-C02 D3 T3.1 applied troubleshooting
S: An administrator sees five EC2 instances in the Europe (Ireland) Region in the Management Console. Running `aws ec2 describe-instances` in the AWS CLI on a laptop with valid credentials for the same account returns an empty list. What is the most likely cause?
A: The AWS CLI can list only instances that were launched with the CLI, so instances created in the console never appear in its output.
B: The CLI default Region on the laptop is different from Europe (Ireland), so the command lists instances in another Region.
C: The instances are in the stopped state, and the CLI returns only running instances unless a special license is enabled.
D: The IAM user needs a separate CLI access policy, because console permissions do not include the right to call EC2 APIs.
K: B
G: ## Most AWS resources live in one Region
EC2 instances, VPCs, RDS databases and most other resources belong to one Region. The console shows the Region in the top bar; the CLI and SDKs use whichever Region they are configured for.
## How the CLI picks a Region
- The `--region` option on the command, for example `aws ec2 describe-instances --region eu-west-1`.
- Otherwise the `AWS_REGION` or `AWS_DEFAULT_REGION` environment variable.
- Otherwise the `region` setting in the CLI profile, written by `aws configure`.
If the laptop's profile says `us-east-1`, the command correctly reports that there are no instances in us-east-1.
## How to fix
Add `--region eu-west-1`, or run `aws configure` to change the default Region.
W: Different default Region: EC2 is a Regional service, and the CLI queries only the Region it is configured for, so an empty list from a different Region is the expected result.
X: A=Only CLI-launched instances: the CLI calls the same EC2 API as the console and lists every instance in the Region, however it was created.
C=Stopped instances hidden: `describe-instances` returns instances in every state, including stopped ones, and no license is involved.
D=Separate CLI policy: IAM permissions apply to API actions, not to tools. If the user can view instances in the console, the same permissions let the CLI call the same action.
T: Regional resources "missing" in the CLI or SDK usually mean the tool is pointed at a different Region; check `--region` and the profile.
V: AWS CLI, Amazon EC2

@ CLF-C02 D3 T3.1 applied comparison
S: A company is building a hybrid architecture and must connect its entire on-premises corporate network to an Amazon VPC so that servers in both locations can communicate privately. Which TWO AWS options can provide this network-to-network connection? (Select TWO)
A: AWS Site-to-Site VPN, which links the corporate network's VPN device to AWS through encrypted IPsec tunnels over the internet.
B: AWS Client VPN, which gives each employee's laptop its own encrypted session into the VPC from any internet connection.
C: AWS Direct Connect, which links the corporate network to AWS through a dedicated private connection at a Direct Connect location.
D: An internet gateway, which attaches to the VPC so that instances with public IP addresses can send and receive internet traffic.
E: Amazon CloudFront, which delivers the company's web content to users through a worldwide network of edge locations.

A hybrid architecture needs a link between the data center network and the VPC so that private IP addresses on both sides can reach each other.

@ CLF-C02 D3 T3.2 applied definition
S: A student preparing for a cloud certification asks what an AWS Availability Zone is. Which description is correct?
A: A worldwide site where Amazon CloudFront caches copies of content so that viewers in nearby cities receive it with lower latency.
B: A geographic area such as a country or large metro area that contains several fully independent AWS Regions for data residency.
C: One or more discrete data centers with redundant power, networking and connectivity, physically separated from others in a Region.
D: An AWS-managed rack of servers installed in a customer's own building that connects back to a parent Region for management.
K: C
G: ## Regions and Availability Zones
- An **AWS Region** is a separate geographic area, such as Europe (Frankfurt) or Asia Pacific (Seoul).
- Each Region is made of multiple **Availability Zones (AZs)**. An AZ is one or more discrete data centers with its own redundant power, networking and connectivity.
- AZs in a Region are physically separated by a meaningful distance, so a fire, flood or power failure at one is unlikely to affect another, yet they are close enough to be linked by high-bandwidth, low-latency networking.
## Why AZs matter
Running copies of an application in two or more AZs lets it keep working if one AZ has a problem. Names like `eu-central-1a` identify AZs inside the Region `eu-central-1`.
## Related terms
- **Edge locations**: sites used by CloudFront, Route 53 and Global Accelerator, not AZs.
- **Outposts**: AWS hardware in your own building.
W: Availability Zone: it is one or more isolated data centers with redundant power and networking inside a Region, separated from the other AZs so failures stay contained.
X: A=Edge location: that describes CloudFront's caching sites, which are separate from Availability Zones and far more numerous.
B=Area containing Regions: the hierarchy runs the other way. A Region contains several Availability Zones, not the reverse.
D=On-premises rack: that describes AWS Outposts, which runs in the customer's facility, not an Availability Zone inside an AWS Region.
T: Region = geographic area; Availability Zone = isolated data center group inside a Region; several AZs per Region.
V: AWS global infrastructure

@ CLF-C02 D3 T3.2 applied troubleshooting
S: An online pharmacy runs its web application on four Amazon EC2 instances, all in one Availability Zone, behind an Application Load Balancer. A power problem in that zone took the whole site offline for two hours. What change would best prevent this kind of outage?
A: Replace the four instances with two larger instance types in the same Availability Zone so each instance has more spare capacity.
B: Move all four instances into a cluster placement group in the same Availability Zone so they share faster networking hardware.
C: Spread the instances across at least two Availability Zones in the Region and have the load balancer route to healthy ones.
D: Add Amazon CloudFront in front of the load balancer so that edge locations keep serving the dynamic pages when the origin fails.
K: C
G: ## High availability with multiple AZs
Availability Zones are designed to fail independently. An event in one AZ, such as a power or cooling problem, should not affect the others.
- If all instances are in **one AZ**, that AZ is a single point of failure.
- If instances are spread over **two or more AZs**, the others keep serving while one is impaired.
## How the pieces work together
- An **Application Load Balancer** is enabled in several AZs and sends requests only to instances that pass health checks.
- An **EC2 Auto Scaling group** spanning those AZs replaces failed instances and keeps the desired number running.
## Example
Two instances in `us-east-1a` and two in `us-east-1b`: if `us-east-1a` loses power, the load balancer sends all traffic to the instances in `us-east-1b`, and Auto Scaling can launch more there.
W: Multiple Availability Zones: zones fail independently, so instances in a second zone keep serving while the load balancer stops sending traffic to the impaired zone.
X: A=Larger instances in one AZ: bigger instances add capacity, but they sit in the same zone and go down together in the next zone-wide event.
B=Cluster placement group: it packs instances close together for low-latency networking inside one zone, which concentrates risk instead of spreading it.
D=CloudFront in front: CloudFront caches content at edge locations, but a dynamic pharmacy site still needs a working origin to process orders.
T: To survive the loss of one data center, run across at least two Availability Zones behind a load balancer.
V: Elastic Load Balancing, Amazon EC2, Amazon EC2 Auto Scaling

@ CLF-C02 D3 T3.2 advanced use-case
S: A payment processor already runs across three Availability Zones. Its regulator now requires a plan to restore service if an entire AWS Region becomes unavailable. Which TWO actions support this disaster recovery requirement? (Select TWO)
A: Copy Amazon EBS snapshots and Amazon Machine Images on a regular schedule to a second AWS Region so servers can be rebuilt there.
B: Turn on Amazon RDS Multi-AZ so a standby database in another Availability Zone of the same Region takes over automatically.
C: Enable Amazon S3 Cross-Region Replication so new objects are copied automatically to a bucket in a different AWS Region.
D: Increase the size of the EC2 Auto Scaling group so it keeps more instances running across the existing three zones.
E: Add a fourth Availability Zone in the same Region to the load balancer so that traffic can be shifted to more locations.
K: A,C
G: ## High availability versus disaster recovery
- **High availability (HA)** keeps an application running when a component or one **Availability Zone** fails. You get it by spreading resources across AZs in one Region.
- **Disaster recovery (DR)** restores service after a much larger event, such as the loss of a whole **Region**. You need copies of data, and a way to rebuild the application, in **another Region**.
AWS Regions are isolated from each other by design, and data you store in a Region stays there unless you copy it. So DR across Regions only works if you set up the copies yourself.
## Common building blocks for cross-Region DR
- Copy **EBS snapshots** and **AMIs** to a second Region (AWS Backup can schedule cross-Region copies).
- Use **S3 Cross-Region Replication** for object data.
- Use cross-Region replicas for databases, such as Aurora global databases or RDS cross-Region read replicas.
- Keep infrastructure as code so the environment can be recreated quickly in the recovery Region.
W: A=Cross-Region snapshot and AMI copies: with server images and volume backups already in the second Region, the company can rebuild its instances there if the primary Region is lost.
C=S3 Cross-Region Replication: it keeps a copy of object data in another Region automatically, so the data survives a Region-wide outage.
X: B=RDS Multi-AZ: the standby lives in the same Region. It protects against a zone failure, not against the whole Region being unavailable.
D=Larger Auto Scaling group: more instances in the same three zones still depend on the same Region, so they would all be lost together.
E=Fourth Availability Zone: an extra zone in the same Region improves zone-level resilience but gives nothing to fail over to if the Region is down.
T: Multi-AZ = high availability inside a Region; surviving a Region outage needs data and images copied to another Region.
V: Amazon EBS, Amazon S3, Amazon RDS, AWS Backup

@ CLF-C02 D3 T3.2 applied comparison
S: A company learns that AWS edge locations are far more numerous than AWS Regions. Which TWO AWS services use edge locations to serve their customers? (Select TWO)
A: Amazon RDS, which runs managed relational database instances in subnets inside Availability Zones of a chosen Region.
B: Amazon CloudFront, which caches and delivers web content and APIs to viewers from locations close to them around the world.
C: Amazon EBS, which provides block storage volumes attached to EC2 instances within a single Availability Zone of a Region.
D: Amazon Route 53, which answers DNS queries for a company's domain names from a worldwide network of servers.
E: Amazon EFS, which provides a shared file system for instances that is stored redundantly across zones of one Region.
K: B,D
G: ## What edge locations are
Edge locations are AWS sites in many cities worldwide, many more than there are Regions. They are not places where you launch EC2 instances or databases. Instead, certain services use them to get closer to end users:
- **Amazon CloudFront** caches content at edge locations so viewers download it from nearby.
- **Amazon Route 53** answers DNS queries from its global network of servers at edge locations, which keeps lookups fast and resilient.
- **AWS Global Accelerator** gives users static IP addresses at the edge and carries their traffic over the AWS network.
- **AWS WAF** and **AWS Shield** can protect traffic at the edge when used with CloudFront.
## Regional services
RDS, EBS and EFS store data inside one Region (and one or more of its AZs). They do not run at edge locations.
W: B=CloudFront: it is the content delivery network built on edge locations, serving cached copies of content close to viewers.
D=Route 53: its authoritative DNS servers run across AWS edge locations worldwide, so users get fast, highly available answers to DNS queries.
X: A=Amazon RDS: database instances run in subnets in a chosen Region's Availability Zones, not at edge locations.
C=Amazon EBS: volumes exist in one Availability Zone and attach to instances in that zone. They are not distributed to edge locations.
E=Amazon EFS: the file system is stored within one Region. Edge locations play no part in serving its data.
T: Edge locations serve CloudFront, Route 53 and Global Accelerator; databases and storage volumes stay in Regions and AZs.
V: Amazon CloudFront, Amazon Route 53

@ CLF-C02 D3 T3.2 applied use-case
S: A sports broadcaster is building an augmented reality app for fans in the stadium. The app runs on phones connected to a mobile carrier's 5G network and needs ultra-low latency to the game-state servers. Which AWS infrastructure option fits this best?
A: AWS Local Zones, which place AWS compute and storage in a large metropolitan area for users who connect through ordinary networks there.
B: Amazon CloudFront edge locations, which cache the app's static files close to fans in cities around the world for faster downloads.
C: AWS Outposts, which deliver AWS-managed racks to the broadcaster's own facility so the servers can run inside its building.
D: AWS Wavelength Zones, which place AWS compute and storage inside a telecommunications carrier's 5G network at the edge.
K: D
G: ## AWS Wavelength
AWS Wavelength embeds AWS compute and storage in the data centers of telecommunications carriers, at the edge of their **5G networks**.
- Traffic from a phone on that carrier's 5G network reaches the application without leaving the carrier's network for the internet.
- That removes network hops and gives very low latency for mobile devices.
- A Wavelength Zone is tied to a parent Region; you extend a VPC into it with a subnet and launch EC2 instances there.
## Typical uses
Augmented and virtual reality, live video analysis, connected vehicles and interactive games on mobile devices.
## How the options differ
- **Wavelength Zones**: mobile devices on a carrier's 5G network.
- **Local Zones**: users and systems in a large city on ordinary networks.
- **Outposts**: inside your own building.
- **Edge locations**: caching and routing, not general-purpose servers.
W: Wavelength Zones: compute inside the carrier's 5G network lets phone traffic reach the game-state servers without leaving the mobile network, giving the ultra-low latency the AR app needs.
X: A=Local Zones: they bring compute close to a city, but traffic from phones still has to leave the carrier's mobile network to reach it. Wavelength is designed for the 5G case.
B=CloudFront edge locations: they speed up delivery of cached files. They do not run the live game-state servers that the app talks to constantly.
C=Outposts: they run AWS in the customer's own facility. Phones on the carrier's 5G network would still have to travel out of the mobile network to reach them.
T: Ultra-low latency for mobile devices on 5G = AWS Wavelength Zones.
V: AWS Wavelength

@ CLF-C02 D3 T3.2 applied troubleshooting
S: A developer in a company that uses a newer AWS Region cannot find a recently launched AWS service in the Management Console, although a colleague using a different Region sees it. What is the most likely reason?
A: The service is offered only to accounts that have purchased Reserved Instances, so it stays hidden until a commitment is made.
B: The service is not yet available in the developer's Region, because new services and features are rolled out to Regions over time.
C: The developer's IAM user lacks permission to view the service, because AWS hides services from users who cannot use them.
D: The console caches its service list for each browser, so the developer must clear the browser history before new services appear.
K: B
G: ## Service availability differs by Region
AWS launches a new service or feature in some Regions first and expands to others over time. Newer Regions may lack some services for a while, and a few services are offered in only a limited set of Regions.
## How to check
- The **AWS Regional Services** list on the AWS website shows which services are available in each Region.
- Each service's documentation lists its supported Regions and endpoints.
## How this affects Region choice
Service availability is one of the four factors in choosing a Region, together with compliance, latency and pricing. If a workload depends on a service, confirm the service is in the Region before building there; otherwise pick a Region that has it, or design around it.
## Note on IAM
IAM controls whether you can call a service's actions. Missing permissions cause "access denied" errors; they do not make a service disappear from the console.
W: Not available in that Region: AWS rolls services out Region by Region, so the colleague's Region can offer a service that the developer's newer Region does not have yet.
X: A=Reserved Instance purchase: there is no rule that makes services visible only after a pricing commitment. Reserved Instances are a billing discount for steady usage.
C=IAM hides services: IAM does not hide services from the console. A user without permissions sees the service but gets access denied errors when acting on it.
D=Browser cache: availability is decided by the Region, not by the browser. Clearing the history will not make a service appear in a Region that does not offer it.
T: A service missing in one Region but present in another usually means it is not yet available there; check the Regional services list before choosing a Region.

@ CLF-C02 D3 T3.2 applied tradeoff
S: A research lab runs large overnight batch simulations on Amazon EC2. Results are downloaded the next morning, the data has no residency rules, and nobody needs fast interactive responses. The required services exist in every Region it considers. Which factor should most influence its Region choice?
A: The price of the needed EC2 instances and storage, because prices for the same resources can differ from one AWS Region to another.
B: The distance to the lab's researchers, because the lowest possible latency is always the most important factor for any workload.
C: The number of CloudFront edge locations in each country, because batch output can only be downloaded through the nearest edge.
D: The Region the lab's AWS account was created in, because an account's resources must all run in that original home Region.
K: A
G: ## The four factors for choosing a Region
1. **Compliance**: laws or contracts that require data to stay in a place.
2. **Latency**: distance to the users or systems that interact with the workload.
3. **Service availability**: whether the services and features you need are offered there.
4. **Pricing**: the same instance type, storage or data transfer can cost different amounts in different Regions.
## Weighing them
When a factor does not apply, the others decide. Here:
- No residency rules: compliance does not narrow the choice.
- Overnight batch with next-morning downloads: a few extra milliseconds of latency make no difference.
- All services available everywhere considered: availability is not a constraint.
That leaves **price**. Choosing a lower-priced Region can noticeably cut the bill for large, compute-heavy jobs. Remember that moving data out of AWS or between Regions has its own transfer charges.
W: Price per Region: with compliance, latency and service availability ruled out as constraints, the lab can pick the Region where its instances and storage cost the least.
X: B=Latency always first: latency matters for interactive users, but these jobs run overnight and results are collected later, so milliseconds do not change anything here.
C=Edge locations per country: downloads do not have to pass through an edge location, and CloudFront's network serves viewers worldwide regardless of Region, so this is not a factor.
D=Account creation Region: an AWS account can use any enabled Region at any time. Where the account was first created does not limit where resources run.
T: When compliance, latency and service availability do not constrain the choice, pick the Region with the best price.
V: Amazon EC2, AWS global infrastructure

@ CLF-C02 D3 T3.2 applied definition
S: A legal firm stores client contracts in an Amazon S3 bucket in the Europe (Paris) Region. A partner asks whether AWS might move or copy those files to another Region for its own operational reasons. Which statement is correct?
A: AWS automatically copies all S3 data to at least one other Region on the same continent to protect it against Region-wide outages.
B: AWS moves data between Regions when one Region is busy, so the customer cannot guarantee where the contracts are stored at a given time.
C: Data stays in the Region where the customer stores it, and it moves to another Region only if the customer copies or replicates it.
D: S3 data is stored at edge locations worldwide by default, so copies of the contracts exist wherever CloudFront has an edge location.
K: C
G: ## Regions and data residency
AWS Regions are designed to be isolated from each other. Content you store in a Region stays in that Region unless you take an action to move it, for example:
- turning on **S3 Cross-Region Replication**,
- copying snapshots or backups to another Region,
- serving the objects through a service such as CloudFront, which caches copies at edge locations because you set it up.
## Durability inside one Region
S3 Standard already stores objects redundantly across multiple Availability Zones within the Region, so durability does not depend on copying data to other Regions.
## Why this helps with compliance
A firm with a rule that client data must remain in France can choose the Paris Region and know that AWS will not move it elsewhere by itself. The firm controls any cross-Region copies.

D=Stored at edge locations by default: edge locations hold cached copies only for content a customer chooses to serve through CloudFront. S3 data does not go there by default.
T: Customer data stays in the Region where it is stored unless the customer moves or replicates it, which is why Region choice supports data residency.

@ CLF-C02 D3 T3.2 applied definition
S: A gaming company in Dallas plans to use an AWS Local Zone for low-latency game servers. A teammate asks how a Local Zone relates to the rest of AWS. Which statement is correct?
A: A Local Zone is a separate, independent Region with its own full set of AWS services, IAM users and a separate billing account.
B: A Local Zone is an extension of a parent Region; you enable it and create a subnet there in a VPC that belongs to that Region.
C: A Local Zone is a group of CloudFront edge locations that can also run EC2 instances when content caching capacity is unused.
D: A Local Zone is AWS hardware installed in the customer's own data center that the customer orders, powers and connects locally.
K: B
G: ## What a Local Zone is
An AWS Local Zone places AWS compute, storage and selected services in a large metropolitan area, closer to users than the nearest Region.
- Each Local Zone is **tied to a parent Region**. It is managed through that Region's console and APIs.
- You **opt in** to the Local Zone, then **extend a VPC** from the parent Region by creating a subnet in the Local Zone.
- You launch resources such as EC2 instances and EBS volumes in that subnet. They talk to the rest of the VPC in the parent Region over AWS's network.
- Only a subset of services is offered in a Local Zone; the rest stay in the parent Region.
## Compare
- **Region**: full set of services, multiple AZs.
- **Outposts**: AWS hardware in your own building.
- **Edge locations**: CloudFront and Route 53 sites, not for general-purpose compute.
W: Extension of a parent Region: a Local Zone is enabled from its parent Region and used by adding a subnet to a VPC of that Region, so it shares the Region's account, IAM and management.
X: A=Separate independent Region: a Local Zone has a limited set of services and depends on its parent Region. It is not a Region of its own, and it uses the same account and IAM.
C=Group of edge locations: edge locations serve CloudFront and Route 53. A Local Zone is a distinct infrastructure type where you run EC2 instances in your VPC.
D=Hardware in your own data center: that describes AWS Outposts. A Local Zone is an AWS-operated facility, so the customer installs nothing.
T: Local Zone = AWS-run extension of a parent Region in a metro area; enable it and add a VPC subnet there.
V: AWS Local Zones

@ CLF-C02 D3 T3.2 applied troubleshooting
S: An administrator switches the Management Console from US East (N. Virginia) to Asia Pacific (Seoul). The EC2 instances she created disappear from view, but all IAM users and roles still appear. What explains this?
A: The EC2 instances were deleted when the console Region changed, while IAM users are protected from deletion by a default policy.
B: IAM data is copied to each Region once a day, while EC2 instances are copied only when cross-Region replication is enabled.
C: EC2 instances are Regional resources shown only in their own Region, while IAM is a global service that is the same in all Regions.
D: The administrator lacks permission to view EC2 in Seoul, because EC2 permissions are granted Region by Region in the console.
K: C
G: ## Regional versus global services
Most AWS services are **Regional**: their resources live in one Region and the console shows only the Region currently selected in the top bar.
- Examples: EC2 instances, VPCs, RDS databases, Lambda functions.
A few services are **global**: their configuration is not tied to one Region.
- **AWS IAM**: users, groups, roles and policies apply across all Regions of the account. The console shows "Global" for IAM.
- Other examples include Amazon Route 53 and Amazon CloudFront configuration.
## Example
An instance launched in `us-east-1` exists only there. Switching the console to `ap-northeast-2` shows Seoul's (empty) list. Switching back shows the instances again. The IAM user who launched it can sign in and work in any Region.
W: Regional EC2, global IAM: the console lists EC2 instances only for the selected Region, so they vanish from view in Seoul, while IAM identities are global and look the same in every Region.
X: A=Instances deleted on Region change: changing the console Region only changes what is displayed. Nothing is deleted, and switching back shows the instances again.
B=Daily IAM copy to Regions: IAM is a single global service for the account, not a set of Regional copies, and EC2 instances are never copied between Regions automatically.
D=Missing permission for Seoul: a missing permission causes an access denied message, not an empty list. Here the instances simply live in another Region.
T: Regional resources show only in their own Region; IAM is global and is the same in every Region.
V: AWS IAM, Amazon EC2

@ CLF-C02 D3 T3.2 advanced tradeoff
S: An online travel booking site has large customer groups in Western Europe and Southeast Asia. Users in Asia complain that pages generated from the single Europe-based deployment are slow, and the data has no residency limits. Which approach best reduces latency for both groups?
A: Move the whole application to a Region halfway between the two groups so that each group is roughly the same distance away.
B: Deploy the application in a Region near each group and use Amazon Route 53 latency-based routing to send users to the nearest one.
C: Add more Availability Zones to the existing European deployment so that Asian users have more data centers to connect to.
D: Upgrade the European EC2 instances to larger sizes so that each page is generated faster and the distance matters less.
K: B
G: ## Latency and distance
Network latency grows with physical distance. A request from Singapore to a server in Europe crosses many thousands of kilometers each way, and a dynamic page may need several round trips. Faster servers cannot remove that delay.
## Using several Regions to serve global users
- Run the application in a Region close to each main user group, for example one in Europe and one in Southeast Asia.
- Use **Amazon Route 53 latency-based routing**: for each DNS query, Route 53 returns the endpoint in the Region that gives that user the lowest latency.
- **CloudFront** can also help by caching static content at edge locations, but dynamic pages still need a nearby origin to be fast.
## Things to plan for
Running in two Regions means keeping data in step (for example, with a global database feature) and paying for two deployments. Because the data has no residency limits, it is allowed to exist in both Regions.
W: Region near each group with latency-based routing: each user group is served by a nearby deployment, and Route 53 directs every user to the Region with the lowest latency for them.
X: A=Region halfway between: both groups would still be far from the servers, so Europe gets slower while Asia improves only a little.
C=More Availability Zones: AZs are inside the same European Region. They improve availability, not the distance to users in Asia.
D=Larger instances: they shorten processing time, but most of the delay is the long network path, which instance size cannot change.
T: To cut latency for users on different continents, deploy in Regions near each group and route users to the closest one.
V: Amazon Route 53, AWS global infrastructure
