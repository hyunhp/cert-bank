@ CLF-C02 D2 T2.2 applied use-case
S: A digital health startup will store protected health information (PHI) on AWS and must have a Business Associate Addendum (BAA) with AWS before it starts. How can the startup put the BAA in place?
A: Download the AWS HIPAA certification from the reports section of AWS Artifact and attach it to the startup's records.
B: Review and accept the BAA in the agreements section of AWS Artifact for the account or for the whole organization.
C: Deploy the AWS Config conformance pack for HIPAA, which signs the BAA automatically once every rule is compliant.
D: Open a support case asking AWS to mail a signed paper BAA, which is the only way AWS enters into this agreement.
K: B
G: ## HIPAA and the Business Associate Addendum
In the United States, the HIPAA law says that a company handling protected health information (PHI) must sign a **Business Associate Addendum (BAA)** with any provider that stores or processes that information for it. AWS acts as a business associate when PHI sits in an AWS account, so a BAA is needed before PHI goes in.
## AWS Artifact has two parts
- **Artifact Reports**: downloadable third-party audit reports and certifications about AWS, such as SOC reports, ISO certificates and PCI DSS attestations.
- **Artifact Agreements**: online legal agreements that a customer reviews and accepts in the console, such as the AWS BAA. A single account can accept it, or the management account of AWS Organizations can accept it for every account in the organization.
## Things to remember
- There is no government "HIPAA certification" that a cloud provider can hold. HIPAA compliance is shown through the BAA plus the customer's own controls.
- After accepting the BAA, the customer must still use only HIPAA eligible services for PHI and configure them securely (encryption, access control, logging).
W: Accept the BAA in Artifact Agreements: AWS Artifact lets a customer review and accept the BAA online for one account or an entire organization, with no paperwork exchange needed.
X: A=HIPAA certification in Artifact Reports: HIPAA has no official certification for cloud providers, and a downloaded report is evidence about AWS, not a legal agreement between the startup and AWS.
C=Config conformance pack signs the BAA: conformance packs only evaluate resource settings against a set of Config rules. They have no legal function and cannot create an agreement with AWS.
D=Mailed paper BAA through support: the standard AWS BAA is handled self-service through AWS Artifact, so a support case and paper copy are not the way to put it in place.
T: Compliance reports come from Artifact Reports; legal agreements such as the HIPAA BAA are accepted in Artifact Agreements.
V: AWS Artifact

@ CLF-C02 D2 T2.2 applied use-case
S: A legal services company keeps client documents in an Amazon S3 bucket. Its policy says every request to the bucket must be encrypted in transit, and any request sent over plain HTTP must be rejected. What should the company do?
A: Add a bucket policy statement that denies every request in which the condition key `aws:SecureTransport` is false.
B: Enable default encryption with an AWS KMS key on the bucket so that every request sent to it is encrypted in transit.
C: Turn on S3 Object Lock in compliance mode so that objects cannot be read or written over an unencrypted connection.
D: Turn on S3 Block Public Access for the bucket so that it accepts only encrypted requests from the company's network.
K: A
G: ## In transit versus at rest for Amazon S3
- **Encryption at rest** protects objects while they are stored. Amazon S3 encrypts every new object at rest by default (SSE-S3), and a bucket can use AWS KMS keys instead.
- **Encryption in transit** protects data while it travels between a client and S3. It comes from **TLS**, which is what HTTPS uses.
S3 endpoints accept both HTTPS and plain HTTP. The AWS SDKs, the AWS CLI and the console use HTTPS by default, but a custom script or old tool could still send a request over HTTP, and the at-rest settings would not stop it.
## Requiring HTTPS with a bucket policy
Every request to S3 carries the global condition key `aws:SecureTransport`, which is true only when the request used TLS. A bucket policy statement with `"Effect": "Deny"` for all principals and actions, and the condition `"Bool": {"aws:SecureTransport": "false"}`, rejects every HTTP request, whoever sends it. Security posture checks such as the AWS Foundational Security Best Practices standard flag buckets that lack this rule.
Example: a script uploads to `http://` instead of `https://` and receives "Access Denied"; switching to HTTPS fixes it.
W: Bucket policy denying requests without `aws:SecureTransport`: the condition is false for any request not sent over TLS, so the explicit deny rejects all plain HTTP requests and only encrypted connections reach the bucket.
X: B=Default encryption with a KMS key: this encrypts objects when S3 stores them (at rest). It does not affect how requests travel, so an HTTP request is still accepted.
C=S3 Object Lock in compliance mode: Object Lock stops objects from being deleted or overwritten for a retention period. It has nothing to do with whether connections use TLS.
D=S3 Block Public Access: it stops public access through ACLs and bucket policies. Requests from authorized users over plain HTTP are still accepted.
T: To require encryption in transit for an S3 bucket, deny requests where `aws:SecureTransport` is false in the bucket policy; default encryption covers only data at rest.
V: Amazon S3

@ CLF-C02 D2 T2.2 applied comparison
S: A payments processor must store its encryption keys in dedicated hardware security modules (HSMs) that no other customer shares, where the company alone manages the users and keys inside the device. Which AWS service meets this requirement?
A: AWS Key Management Service (AWS KMS) using AWS managed keys, which AWS creates for each service in the account.
B: AWS Secrets Manager, which stores database passwords and API keys and can rotate them on a regular schedule.
C: AWS CloudHSM, which provides single-tenant HSMs in the customer's VPC that only the customer can administer.
D: AWS Key Management Service (AWS KMS) using customer managed keys with a key policy written by the company.
K: C
G: ## Two ways to manage keys on AWS
Both AWS KMS and AWS CloudHSM keep keys inside hardware security modules (HSMs), tamper-resistant devices built to protect keys. The difference is who owns and operates the HSM.
- **AWS KMS** is a fully managed, **multi-tenant** service. AWS runs the HSM fleet; customers create keys and control them through key policies and IAM. It integrates with most AWS services (S3, EBS, RDS and more) with a few clicks.
- **AWS CloudHSM** gives the customer **dedicated, single-tenant** HSMs inside its own VPC. AWS handles the hardware, but the customer creates the HSM users and manages the keys; AWS has no access to them. The customer also handles more of the work, such as scaling the cluster and integrating applications.
## When to choose which
- Most workloads: AWS KMS, because it is simpler and integrated everywhere.
- A rule that demands dedicated hardware under the customer's exclusive control: AWS CloudHSM.
W: AWS CloudHSM: it gives the company dedicated HSMs that no other customer shares, and the company itself manages the HSM users and keys, which is exactly what the rule demands.
X: A=KMS with AWS managed keys: AWS creates and manages these keys on shared KMS infrastructure, so the company neither owns dedicated hardware nor controls the keys.
B=AWS Secrets Manager: it stores and rotates secrets such as passwords. It is not a dedicated HSM for managing cryptographic keys.
D=KMS with customer managed keys: the company controls the key policy, but the keys still live in the shared, AWS-operated KMS HSM fleet rather than in single-tenant hardware the company administers.
T: AWS KMS is managed and multi-tenant; AWS CloudHSM is dedicated, single-tenant hardware where the customer alone manages the keys.
V: AWS CloudHSM, AWS Key Management Service (AWS KMS)

@ CLF-C02 D2 T2.2 applied comparison
S: A media company encrypts its Amazon S3 data with AWS KMS. The security team wants to write its own key policy, decide which roles can use the key, and be able to disable the key at any time. Which type of KMS key should it use?
A: A customer managed key, which the company creates and whose key policy, rotation and status the company controls.
B: An AWS managed key, which AWS creates for the S3 service in the account and whose key policy the company can edit.
C: An AWS owned key, which AWS keeps in its own account and shares across many customers with no visibility to them.
D: An S3 managed key (SSE-S3), which S3 creates for each bucket and which the company can disable from the S3 console.
K: A
G: ## Who manages the key?
Encryption is only as strong as control over the key. AWS offers several levels of key ownership:
- **SSE-S3 (S3 managed keys)**: S3 handles everything. Encryption is on by default for new objects, but the customer has no key to manage or audit.
- **AWS owned keys**: keys that AWS uses across many accounts for some services. Customers cannot see, manage or audit them.
- **AWS managed keys**: KMS keys that an AWS service creates in your account, named like `aws/s3`. You can see them and their use is logged, but you cannot change their key policy, disable them or delete them. AWS rotates them automatically.
- **Customer managed keys**: KMS keys you create. You write the key policy, grant access, turn on automatic rotation, disable the key or schedule it for deletion.
## Why control matters
Disabling a customer managed key makes the data it protects unreadable until the key is enabled again, which is a powerful emergency control.
W: Customer managed key: only this key type lets the company write its own key policy, choose who may use the key, set rotation and disable it whenever it wants.
X: B=AWS managed key: these keys are visible in the account, but their key policy is set by AWS and cannot be edited, and they cannot be disabled by the customer.
C=AWS owned key: these keys sit in AWS accounts and are invisible to customers, so the company could not write policies for them or disable them.
D=S3 managed key (SSE-S3): S3 manages these keys entirely; there is no key policy for the company to write and no option to disable the key.
T: Need your own key policy and the power to disable or rotate the key? Use a KMS customer managed key.
V: AWS Key Management Service (AWS KMS), Amazon S3

@ CLF-C02 D2 T2.2 applied use-case
S: An insurance company is reviewing how it protects data while it moves between systems. Which TWO measures provide encryption in transit? (Select TWO)
A: Turning on Amazon EBS encryption for the volumes attached to the claims processing EC2 instances.
B: Using an AWS Site-to-Site VPN connection, which sends traffic through IPsec tunnels to the VPC.
C: Requiring clients to call the company's API over HTTPS, which protects each connection with TLS.
D: Setting default encryption with an AWS KMS key on the S3 bucket that stores scanned claim forms.
E: Enabling Amazon Macie to discover and classify the sensitive data stored in the company's buckets.
K: B,C
G: ## At rest versus in transit
- **Encryption at rest** protects stored data: EBS volumes, S3 objects, RDS databases, snapshots and backups. It defends against someone reading the storage media or the stored copy.
- **Encryption in transit** protects data moving across a network: between users and applications, between services, or between a data center and AWS. It defends against eavesdropping and tampering on the way.
## Common in-transit protections on AWS
- **TLS (HTTPS)** for web traffic and APIs. AWS service endpoints accept TLS, and S3 bucket policies can deny any request that does not use it.
- **IPsec** in AWS Site-to-Site VPN, which encrypts traffic between an on-premises network and a VPC over the internet.
Example: branch offices send claim files to AWS over a Site-to-Site VPN, and mobile apps call the claims API over HTTPS. Once the files land, S3 encrypts them at rest with a KMS key.
W: B=Site-to-Site VPN: the VPN carries traffic inside encrypted IPsec tunnels, so data is protected while it crosses the internet between the office network and AWS.
C=HTTPS for the API: TLS encrypts each client connection, which is the standard way to protect data in transit to an application.
X: A=EBS encryption: this protects data stored on the volumes and their snapshots, which is encryption at rest, not protection on the network.
D=S3 default encryption with KMS: objects are encrypted once they are stored, which is encryption at rest; uploads must still use TLS to be protected on the way.
E=Amazon Macie: Macie finds and classifies sensitive data in S3. It reports where data is, but it does not encrypt anything.
T: Encryption in transit on AWS means TLS (HTTPS) or IPsec (VPN); EBS and S3 encryption protect data at rest.
V: AWS Site-to-Site VPN, AWS Key Management Service (AWS KMS)

@ CLF-C02 D2 T2.2 applied use-case
S: A logistics company runs its tracking application on 40 Amazon EC2 instances. Operators want the application's log files collected in one place, kept for one year, and an alarm when the word "ERROR" appears too often. Which AWS service should they use?
A: AWS CloudTrail, which records the API calls made in the account and can deliver its event log files to an S3 bucket.
B: AWS Config, which records the configuration of each EC2 instance and keeps a timeline of every change to its settings.
C: AWS Trusted Advisor, which checks the account for best practices and lists the instances that have high error rates.
D: Amazon CloudWatch Logs, with the CloudWatch agent sending log files, a retention setting and a metric filter with an alarm.
K: D
G: ## Different logs answer different questions
- **AWS CloudTrail**: who called which AWS API (for example, who stopped an instance).
- **AWS Config**: what a resource's configuration looked like over time.
- **Amazon CloudWatch Logs**: what your applications, operating systems and some AWS services wrote to their logs.
## How CloudWatch Logs works
- The **CloudWatch agent** on each EC2 instance sends log files to a **log group**.
- Each log group has a **retention setting** (from one day up to ten years, or never expire).
- **Metric filters** turn matching log lines into a metric, for example counting lines with `ERROR`. A **CloudWatch alarm** on that metric can notify operators through Amazon SNS.
- **CloudWatch Logs Insights** lets operators search and analyze the logs with a query language.
W: CloudWatch Logs with agent, retention and metric filter: the agent centralizes the files, retention keeps them for a year, and a metric filter counts "ERROR" lines so an alarm can fire.
X: A=AWS CloudTrail: CloudTrail logs AWS API activity, not the text that the tracking application writes to its own log files.
B=AWS Config: Config tracks resource configuration changes. It does not collect application log lines or count error messages.
C=AWS Trusted Advisor: it checks the account against best practices for cost, security and more. It does not read application logs or report error counts.
T: Application and OS log files go to CloudWatch Logs; metric filters and alarms turn log patterns into notifications.
V: Amazon CloudWatch

@ CLF-C02 D2 T2.2 applied use-case
S: A bank with 25 AWS accounts in AWS Organizations must keep a record of API activity from every account for seven years, protected from changes by account administrators. Which approach meets this requirement?
A: Rely on the CloudTrail event history in each account, which automatically keeps every management event for seven years.
B: Create a CloudTrail organization trail that delivers logs from all accounts to an S3 bucket in a separate log archive account.
C: Turn on VPC Flow Logs in every account and send them to Amazon CloudWatch Logs with a retention period of seven years.
D: Enable AWS Config in every account and keep its configuration history, which records each API call and its caller.
K: B
G: ## Event history versus trails
- **CloudTrail event history** is on by default and shows the last **90 days** of management events in each Region of an account. It cannot be extended.
- A **trail** delivers events continuously as log files to an Amazon S3 bucket, where they can be kept as long as needed with S3 lifecycle rules.
## Organization trails
In AWS Organizations, an **organization trail** created in the management account (or a delegated administrator account) logs events for every account in the organization, including accounts added later. Member account administrators can see the trail but cannot change or delete it.
## Protecting the logs
Good practice is to send the logs to a bucket in a dedicated **log archive account** that few people can access. Extra protections include CloudTrail log file integrity validation, which detects changes to delivered files, and S3 Object Lock, which stops objects from being deleted or overwritten for a set period.
W: Organization trail to a log archive bucket: one trail captures API activity from all 25 accounts, member administrators cannot alter it, and the S3 bucket in a separate account can keep the files for seven years.
X: A=CloudTrail event history: event history covers only the last 90 days in each Region, far short of seven years, and it is per account rather than central.
C=VPC Flow Logs: flow logs capture network traffic metadata such as IP addresses and ports. They do not record API calls or the identity that made them.
D=AWS Config history: Config records how resource configurations changed, not every API call with its caller; that is CloudTrail's job.
T: For long-term, central API logs across an organization, use a CloudTrail organization trail delivering to a protected S3 bucket.
V: AWS CloudTrail, AWS Organizations, Amazon S3

@ CLF-C02 D2 T2.2 applied comparison
S: A new cloud auditor asks which AWS service answers each question: (1) Who deleted a security group yesterday? (2) Which rules did that security group have last month? (3) How high was the web server's CPU use last night? Which option matches them correctly?
A: (1) AWS Config, (2) AWS CloudTrail, (3) Amazon CloudWatch, because Config records callers and CloudTrail records settings.
B: (1) Amazon CloudWatch, (2) AWS Config, (3) AWS CloudTrail, because CloudWatch records callers and CloudTrail stores metrics.
C: (1) AWS CloudTrail, (2) AWS Config, (3) Amazon CloudWatch, matching API activity, configuration history and metrics.
D: (1) AWS CloudTrail, (2) Amazon CloudWatch, (3) AWS Config, because CloudWatch keeps settings and Config stores metrics.
K: C
G: ## Three monitoring services, three questions
- **AWS CloudTrail** records **activity**: every API call, with the identity, time, source IP and parameters. "Who did what, and when?"
- **AWS Config** records **configuration state**: what each supported resource looked like at each point in time, and whether it complies with rules. "What did this look like, and is it allowed?"
- **Amazon CloudWatch** records **performance and operational data**: metrics such as CPU use, plus logs and alarms. "How is it behaving?"
## Using them together
Example: an alarm shows a web server's CPU spiked (CloudWatch). The configuration timeline shows its security group gained a rule allowing port 22 from anywhere (Config). The event behind that change shows which role called `AuthorizeSecurityGroupIngress` (CloudTrail).
W: CloudTrail, Config, CloudWatch: deletions are API calls recorded by CloudTrail, earlier security group rules are in Config's configuration history, and CPU use is a CloudWatch metric.
X: A=Config for callers, CloudTrail for settings: this swaps the two services. Config does not record who made a call, and CloudTrail does not keep a per-resource configuration timeline.
B=CloudWatch for callers, CloudTrail for metrics: CloudWatch does not record which identity made an API call, and CloudTrail does not store CPU metrics.
D=CloudWatch for settings, Config for metrics: CloudWatch does not keep security group rule history, and Config does not collect performance metrics such as CPU use.
T: CloudTrail = who did what; Config = what the configuration was and whether it complies; CloudWatch = how resources perform.
V: AWS CloudTrail, AWS Config, Amazon CloudWatch

@ CLF-C02 D2 T2.2 applied use-case
S: A retail group uses AWS Organizations. The security team must make sure that no one in any member account, including administrators, can stop or delete the CloudTrail trails. What should the team use?
A: An IAM policy attached to the security team's own users that denies the actions for stopping and deleting trails.
B: An AWS Config rule in each account that reports a trail as non-compliant after it has been stopped or deleted.
C: A Trusted Advisor check that lists accounts without logging enabled and sends a weekly email to the security team.
D: A service control policy (SCP) attached to the organization root that denies the actions for stopping and deleting trails.
K: D
G: ## Service control policies (SCPs)
An SCP is a policy in AWS Organizations that sets the **maximum permissions** for accounts in the organization. It is attached to the organization root, an organizational unit (OU) or an account, and it applies to every IAM user and role in the affected member accounts, including their root users.
- If an SCP denies an action, no IAM policy in the account can allow it.
- SCPs do not affect the management account itself, which is one reason AWS recommends running no workloads there.
## A typical guardrail
An SCP that denies `cloudtrail:StopLogging` and `cloudtrail:DeleteTrail` keeps audit logging running even if an attacker or careless administrator gains full admin rights in a member account. The action is blocked before it happens, which makes the control **preventive**.
W: SCP denying trail changes: an SCP at the root applies to every principal in every member account, including administrators, so the actions are blocked before they can run.
X: A=IAM policy on the security team's users: it limits only the users it is attached to. Other administrators in the member accounts would still be able to stop the trails.
B=AWS Config rule: a Config rule is detective. It reports the problem after the trail is stopped, but it does not prevent the action.
C=Trusted Advisor check: Trusted Advisor gives recommendations about account settings. It cannot block an administrator from stopping a trail.
T: To stop an action in every member account, even for administrators, use a deny statement in an SCP.
V: AWS Organizations, AWS CloudTrail

@ CLF-C02 D2 T2.2 applied use-case
S: A German bank's regulator requires that the bank's workloads run only in AWS Regions inside the European Union. The bank has 40 accounts in AWS Organizations. How can it enforce this centrally?
A: Attach a service control policy that denies actions when the requested Region is outside the approved EU Regions.
B: Ask AWS Support to delete all Regions outside the EU from the bank's accounts so that they no longer appear there.
C: Set the default Region in each employee's AWS CLI profile to an EU Region so that commands go there by default.
D: Download the EU compliance report from AWS Artifact, which limits all of the organization's accounts to EU Regions.
K: A
G: ## Data residency is the customer's choice
AWS stores customer content in the Regions the customer chooses and does not move it elsewhere without the customer's action. The risk, then, is that someone in the company creates resources in the wrong Region. Governance tools turn the residency policy into a rule that cannot be bypassed.
## Region restriction with an SCP
A service control policy can deny actions when the condition key `aws:RequestedRegion` is not one of an approved list, such as `eu-central-1` and `eu-west-1`. Because SCPs apply to every principal in the member accounts, nobody can create resources in other Regions.
- Global services such as IAM are usually exempted in the policy, because their API calls are handled in a fixed Region.
- AWS Control Tower offers a ready-made control to deny access to Regions you have not selected, built on the same SCP mechanism.
W: SCP that denies other Regions: the `aws:RequestedRegion` condition blocks requests to non-approved Regions in every member account, which enforces the regulator's rule centrally.
X: B=Support deletes Regions: AWS does not remove Regions from accounts on request. Some newer Regions are opt-in, but restricting use across an organization is done with policies.
C=Default Region in CLI profiles: a default is only a convenience. Anyone can name another Region in a command or pick one in the console, so it enforces nothing.
D=Artifact report limits Regions: Artifact only supplies compliance documents to download. Reading a report does not change what accounts can do.
T: Enforce data residency across an organization with an SCP that denies requests outside the approved Regions.
V: AWS Organizations, AWS Control Tower

@ CLF-C02 D2 T2.2 applied troubleshooting
S: An organization's member account has an SCP that allows only Amazon S3 and Amazon EC2 actions. A new developer in that account has no IAM policies attached and receives an "access denied" error when listing S3 buckets. Why?
A: The SCP allows S3 and therefore grants the permission, so the error must come from a temporary outage of the S3 service.
B: SCPs only set the maximum permissions; the developer also needs an IAM policy that allows the S3 actions.
C: SCPs apply only to the root user of a member account, so the developer must sign in as the root user to use S3.
D: The SCP must be attached to the developer's IAM user directly, because SCPs on the account are ignored for IAM users.
K: B
G: ## SCPs are a boundary, not a grant
A service control policy never gives anyone permissions. It defines the **largest set of actions** that IAM users and roles in an account could be allowed. Actual permissions come from IAM policies.
An action is allowed only if **both** of these are true:
- The SCPs on the account (and its OUs and the root) allow it.
- An identity-based or resource-based policy allows it.
## The example
The SCP says S3 and EC2 actions are possible in this account. The developer has no IAM policy, so nothing allows `s3:ListAllMyBuckets`, and the default is deny. Attaching an IAM policy (directly or through a group or role) that allows the S3 actions fixes the error. An IAM policy allowing DynamoDB would still not work, because the SCP rules it out.
W: SCPs set maximum permissions only: the SCP makes S3 possible, but without an IAM policy that allows the action, the default deny applies and the request fails.
X: A=SCP grants the permission: SCPs never grant permissions, so the error is expected behavior, not an outage.
C=SCPs apply only to root: SCPs apply to all IAM users and roles in a member account as well as its root user, and AWS advises against using root for daily work.
D=Attach the SCP to the IAM user: SCPs attach to the organization root, OUs or accounts, never to individual IAM users, and they already affect every user in the account.
T: Access needs both an SCP that permits the action and an IAM policy that allows it; SCPs alone grant nothing.
V: AWS Organizations, AWS Identity and Access Management (IAM)

@ CLF-C02 D2 T2.2 advanced comparison
S: A governance team wants controls that stop non-compliant actions before they happen in member accounts, rather than reporting them afterward. Which TWO options are preventive controls? (Select TWO)
A: A service control policy that denies making Amazon EBS snapshots public in any member account of the organization.
B: An AWS Config rule that marks any S3 bucket without default encryption as non-compliant in the compliance dashboard.
C: An AWS Control Tower preventive control, enforced through organization policies such as SCPs on the OUs it is enabled for.
D: A CloudTrail trail that records every API call so the team can review the non-compliant actions in its weekly meeting.
E: An AWS Trusted Advisor security check that flags security groups which allow unrestricted access to specific ports.
K: A,C
G: ## Preventive versus detective controls
- **Preventive controls** block an action before it happens. The request fails, and the non-compliant resource is never created.
- **Detective controls** find a problem after it exists and report it, so someone (or an automated remediation) can fix it.
Good governance uses both: prevent what you can, and detect the rest.
## On AWS
- **Preventive**: service control policies (SCPs) in AWS Organizations; AWS Control Tower preventive controls, which are implemented as SCPs (and some as resource control policies).
- **Detective**: AWS Config rules; Control Tower detective controls (built on Config rules); Trusted Advisor checks; Security Hub CSPM findings.
- **Records for investigation**: CloudTrail logs, which show what happened but neither block nor evaluate anything by themselves.
W: A=SCP denying public snapshots: an SCP deny blocks the request in every affected account before the snapshot can be shared, so it is preventive.
C=Control Tower preventive control: these controls are enforced with organization policies (mostly SCPs, some resource control policies) on the enabled OUs, so disallowed actions fail before they take effect.
X: B=AWS Config rule: a Config rule evaluates a bucket after it has been created and reports non-compliance, which makes it a detective control.
D=CloudTrail trail: CloudTrail records what happened for later review. It does not stop any action from running.
E=Trusted Advisor security check: the check flags open security groups that already exist, so it detects rather than prevents.
T: SCPs (and Control Tower preventive controls built on them) prevent actions; Config rules, Trusted Advisor and Security Hub CSPM detect problems after the fact.
V: AWS Organizations, AWS Control Tower, AWS Config

@ CLF-C02 D2 T2.2 applied troubleshooting
S: A company turned on AWS Security Hub CSPM with the AWS Foundational Security Best Practices standard in a new account. A week later, Amazon GuardDuty findings appear in Security Hub CSPM, but most of the standard's controls still have no results. What is the most likely cause?
A: AWS Config is not enabled and recording resources in the account, and most of the standard's controls rely on Config rules.
B: The company has not accepted the Security Hub CSPM agreement in AWS Artifact, which must happen before any control runs.
C: Amazon Inspector has not finished scanning every EC2 instance, and the standard's controls only start once those scans end.
D: The account is not a member of AWS Organizations, and Security Hub CSPM runs its controls only in organization accounts.
K: A
G: ## Two jobs, two data sources
AWS Security Hub CSPM (cloud security posture management) does two things, and each needs different input:
- **Findings aggregation**: it receives findings that other services send to it, such as Amazon GuardDuty, Amazon Inspector and Amazon Macie. This works as soon as those services are on.
- **Security standards**: it runs automated **controls** against your resources for standards such as the AWS Foundational Security Best Practices (FSBP) and the CIS AWS Foundations Benchmark, and calculates a security score.
## Controls depend on AWS Config
Most controls are evaluated through **service-linked AWS Config rules** that Security Hub CSPM creates in the account. AWS Config must therefore be **enabled and recording** the relevant resource types in each account and Region where the standard is enabled. Without the recorder, those rules have nothing to evaluate, so the controls produce no results and the score stays incomplete.
Example: an administrator turns on the AWS Config recorder for the Region; within hours the FSBP controls begin to show passed and failed checks, such as an S3 bucket that allows HTTP requests.
W: AWS Config not recording: Security Hub CSPM evaluates most controls with AWS Config rules, so without the Config recorder those controls have no resource data, while findings sent by GuardDuty still arrive normally.
X: B=Agreement in AWS Artifact: Artifact holds AWS's compliance reports and legal agreements such as the BAA. Security Hub CSPM needs no Artifact agreement before its controls run.
C=Waiting for Inspector scans: Inspector is a separate findings source. The FSBP controls check resource configurations and do not wait for Inspector scans to finish.
D=Requires AWS Organizations: Security Hub CSPM works in a standalone account. Organizations only adds central management of many accounts through a delegated administrator.
T: Security Hub CSPM security standard controls need AWS Config enabled and recording; findings from other services arrive without it.
V: AWS Security Hub CSPM, AWS Config

@ CLF-C02 D2 T2.2 applied use-case
S: A small nonprofit has one AWS account and no security staff. It plans to use the security checks in AWS Trusted Advisor for a quick review of common risks. Which TWO issues can these checks flag? (Select TWO)
A: Amazon S3 buckets whose permissions allow open access to anyone, including list or upload access for everyone.
B: Amazon EBS snapshots that are shared publicly, so that any AWS account in the world could copy them and read their data.
C: Malware hidden in files on the EBS volumes attached to EC2 instances, found by scanning the volume contents.
D: Known software vulnerabilities (CVEs) in packages installed inside the container images stored in Amazon ECR.
E: Personal data such as passport numbers inside S3 objects, found by reading and classifying each object's contents.
K: A,B
G: ## AWS Trusted Advisor
Trusted Advisor inspects an AWS account and gives **recommendations** based on AWS best practices in categories such as cost optimization, performance, security, fault tolerance, service limits and operational excellence. It looks at **account and resource settings**, not at what is inside files, images or objects.
Security checks include:
- **S3 bucket permissions**: buckets that allow open access.
- **Amazon EBS public snapshots** and **Amazon RDS public snapshots**: snapshots whose sharing setting makes them available to every AWS account.
- **Security groups**: rules that allow unrestricted access (`0.0.0.0/0`) to specific ports.
- **MFA on root account**: whether the root user has multi-factor authentication.
- **IAM use** and exposed access keys.
A basic set of core security checks is available in every account; the full set of checks depends on the support plan.
## Which tool looks inside the content
- Malware in EBS volumes: Amazon GuardDuty Malware Protection.
- Software vulnerabilities in instances and container images: Amazon Inspector.
- Sensitive data such as personal information in S3 objects: Amazon Macie.
W: A=Open S3 bucket permissions: the S3 bucket permissions check flags buckets whose ACLs or policies allow open access.
B=Publicly shared EBS snapshots: the EBS public snapshots check flags snapshots whose permissions let any AWS account create a volume from them.
X: C=Malware in EBS volumes: scanning volume contents for malware is done by GuardDuty Malware Protection; Trusted Advisor does not read file contents.
D=CVEs in container images: finding vulnerable packages in images is the job of Amazon Inspector, not a best-practice settings check.
E=Personal data in S3 objects: discovering sensitive data inside objects is what Amazon Macie does; Trusted Advisor only looks at bucket settings.
T: Trusted Advisor security checks flag risky settings such as open buckets, public snapshots and open ports; content scanning belongs to GuardDuty, Inspector and Macie.
V: AWS Trusted Advisor, Amazon GuardDuty, Amazon Inspector, Amazon Macie

@ CLF-C02 D2 T2.2 applied troubleshooting
S: A Brazilian retailer must keep customer data only in the South America (Sao Paulo) Region. An internal audit finds copies of one S3 bucket's objects in a US Region. What is the most likely cause?
A: Amazon S3 automatically copies every object to a second Region on another continent to achieve its durability design.
B: AWS moves customer content between Regions during routine maintenance and copies it back when the work is finished.
C: Someone in the company configured S3 Cross-Region Replication or a cross-Region backup copy for that bucket.
D: The bucket was encrypted with an AWS KMS key, and KMS stores a copy of all encrypted objects in a US Region.
K: C
G: ## Where AWS keeps your data
When a customer stores content in a Region, AWS keeps it in that Region. AWS does not move or replicate customer content outside the Regions the customer chose unless the customer takes an action that does so (or it is needed to comply with law).
- **S3 durability** comes from storing data redundantly across multiple Availability Zones **within** the Region (for most storage classes), not from copying it to other Regions.
## Customer actions that copy data to other Regions
- **S3 Cross-Region Replication (CRR)** rules on a bucket.
- **AWS Backup** plans with a cross-Region copy step.
- Copying snapshots or AMIs to another Region, or caching content worldwide through Amazon CloudFront.
To keep data residency rules, these features must be avoided or limited to approved Regions, and an SCP can block resource creation outside them.
W: Customer-configured cross-Region copy: data leaves its Region only through a customer action, such as a CRR rule or a cross-Region backup copy, so that is the likely cause to investigate and remove.
X: A=S3 copies objects to another Region: S3 achieves durability by storing data across Availability Zones within the Region, not by copying to other continents.
B=AWS moves data during maintenance: AWS does not move customer content out of the chosen Region for maintenance or any other routine reason.
D=KMS stores object copies: AWS KMS manages encryption keys only. It never stores copies of the data that the keys protect.
T: AWS keeps content in the Region you choose; data in another Region usually means someone set up replication or cross-Region copies.
V: Amazon S3, AWS Backup

@ CLF-C02 D2 T2.2 applied use-case
S: A pharmaceutical company encrypts research data with an AWS KMS customer managed key. Auditors want a record of every time an application used that key to decrypt data, including which role made the request and when. Where can the company find this?
A: In AWS Artifact, which publishes a monthly report of key usage for each KMS key that is used in the customer's account.
B: In AWS Trusted Advisor, which lists each decryption request made with a key as part of its security recommendations.
C: In the KMS key policy, which keeps a history of every principal that has used the key since the key was first created.
D: In AWS CloudTrail, which records each KMS API call such as Decrypt with the calling identity, time and key used.
K: D
G: ## Every key use is an API call
Applications use AWS KMS keys by calling KMS APIs such as `Encrypt`, `Decrypt` and `GenerateDataKey`. AWS services that encrypt data for you (S3, EBS, RDS) also call KMS on your behalf.
## CloudTrail records KMS activity
AWS CloudTrail logs these KMS calls as management events, showing:
- the identity (user or role) that made the request,
- the time and source,
- the KMS key used and the encryption context.
This is one of the main reasons to use KMS keys for sensitive data: auditors can see exactly who used which key and when. Keep the events beyond the 90-day event history by delivering them to S3 with a trail.
Example: an auditor filters events for `Decrypt` on the research key and sees the role `research-etl` used it 1,200 times last week, all from the expected application.
W: AWS CloudTrail: KMS operations are API calls, and CloudTrail logs each one with the caller, time and key, which is exactly the audit record requested.
X: A=Artifact key usage report: Artifact provides AWS's own compliance documents. It contains nothing about how a customer's keys are used.
B=Trusted Advisor: Trusted Advisor gives best-practice recommendations. It does not log individual cryptographic requests.
C=Key policy history: a key policy defines who may use the key. It is a permissions document, not a log of who actually used it.
T: Use of AWS KMS keys is audited through AWS CloudTrail, which records every KMS API call with its caller.
V: AWS Key Management Service (AWS KMS), AWS CloudTrail

@ CLF-C02 D2 T2.2 applied definition
S: An online ticket seller plans to accept card payments in an application on AWS. A manager says that because AWS holds a PCI DSS attestation, the application is automatically PCI DSS compliant. Which statement is correct?
A: The manager is right, because the AWS attestation covers every application that customers build on any of the in-scope services.
B: AWS's attestation covers its infrastructure and services, but the seller must still make and prove its own setup compliant.
C: The manager is right only if the seller downloads the attestation from AWS Artifact, which then extends it to the account.
D: PCI DSS cannot be met on a public cloud, so the seller must process cards in its own data center to stay compliant.
K: B
G: ## Compliance follows the shared responsibility model
AWS is assessed against many programs, including PCI DSS. Its attestation shows that the AWS infrastructure and the in-scope services meet the standard **for the parts AWS controls**.
The customer is responsible for the parts it controls:
- how the application handles card data,
- network design, access control, encryption and logging in its accounts,
- its own processes, staff and assessments.
## How AWS's attestation helps
A customer builds on in-scope services and uses AWS's Attestation of Compliance and responsibility documents (from AWS Artifact) as evidence for the AWS layer. The customer's own assessor then evaluates the customer's environment. This is sometimes described as **inheriting** controls: the customer does not have to re-audit the data centers, but it still owns everything above them.
W: AWS covers its layer, the seller covers its own: the AWS attestation proves the infrastructure meets PCI DSS, while the seller must build, run and have its own cardholder data environment assessed.
X: A=Attestation covers every application: AWS cannot see or control how customers build their applications, so its attestation does not extend to them.
C=Downloading extends the attestation: downloading a report gives the seller evidence about AWS; it does not change the scope of the attestation or the seller's duties.
D=PCI DSS impossible on public cloud: many companies run PCI DSS compliant workloads on AWS using in-scope services, so moving back on premises is not required.
T: AWS compliance covers AWS's layer; customers inherit those controls but must still make their own workloads compliant.
V: AWS Artifact

@ CLF-C02 D2 T2.2 advanced tradeoff
S: A law firm will store case files in Amazon S3. Its policy says plaintext must never leave the firm's network and AWS must never hold the encryption keys. Which approach meets this policy?
A: Use server-side encryption with Amazon S3 managed keys (SSE-S3), which encrypts every object as S3 writes it to disk.
B: Use server-side encryption with customer-provided keys (SSE-C), sending the firm's key with each upload request.
C: Use client-side encryption with keys kept on premises, so files are encrypted before upload and S3 stores only ciphertext.
D: Use server-side encryption with keys stored in AWS CloudHSM, which the firm administers inside its own AWS VPC.
K: C
G: ## Where encryption happens
- **Server-side encryption**: you send plaintext to the service over TLS, and the service encrypts it before writing it to disk. The service must see the plaintext at some point.
- **Client-side encryption**: you encrypt data on your own systems before sending it. AWS only ever receives and stores ciphertext.
## Who holds the keys
- **SSE-S3**: AWS manages the keys entirely.
- **SSE-KMS**: keys live in AWS KMS; the customer controls policies.
- **SSE-C**: the customer supplies the key with each request; S3 uses it to encrypt and then discards it, but the key and plaintext do reach AWS during the request.
- **AWS CloudHSM**: the customer administers the keys exclusively, but the HSMs are in AWS.
- **Client-side with on-premises keys**: neither plaintext nor keys ever reach AWS.
Trade-off: client-side encryption gives the most control but puts all key management and data recovery on the customer. If the firm loses its keys, AWS cannot help recover the data.
W: Client-side encryption with on-premises keys: files are encrypted inside the firm's network, and only ciphertext travels to S3, so neither plaintext nor keys ever reach AWS.
X: A=SSE-S3: S3 receives the plaintext and encrypts it with keys that AWS manages, which breaks both parts of the policy.
B=SSE-C: AWS does not keep the key, but both the key and the plaintext are sent to S3 with each request, so plaintext leaves the firm's network.
D=CloudHSM keys with server-side encryption: the firm controls the keys, but they are stored in HSMs inside AWS and the plaintext is still sent to AWS to be encrypted.
T: If AWS must never see plaintext or keys, encrypt on the client side with keys kept outside AWS.
V: Amazon S3, AWS CloudHSM

@ CLF-C02 D2 T2.2 applied definition
S: A security lead is explaining AWS Security Hub CSPM to a new team. Which TWO statements correctly describe what it does? (Select TWO)
A: It runs automated checks of the account against security standards such as the AWS Foundational Security Best Practices.
B: It provides the third-party audit reports that show AWS's own infrastructure meets programs such as SOC 2 and ISO 27001.
C: It collects findings from services such as Amazon GuardDuty and Amazon Inspector into one view in a standard format.
D: It inspects and filters incoming web requests to block attacks such as SQL injection before they reach the application.
E: It creates and stores the encryption keys that services such as Amazon S3 and Amazon EBS use to protect data at rest.
K: A,C
G: ## Two jobs of Security Hub CSPM
AWS Security Hub CSPM (cloud security posture management) does two things:
- **Posture checks**: it continuously runs automated **security controls** against your resources, grouped into standards such as the AWS Foundational Security Best Practices (FSBP), the CIS AWS Foundations Benchmark, PCI DSS and NIST SP 800-53. Results roll up into a security score. Most controls rely on AWS Config being enabled and recording.
- **Findings aggregation**: it receives findings from AWS services (GuardDuty, Inspector, Macie, IAM Access Analyzer, Firewall Manager and others) and partner products, normalizes them in the AWS Security Finding Format (ASFF), and lets you filter, prioritize and act on them in one place.
## What it does not do
It is not a firewall, an encryption key store or a source of AWS's own audit reports. Those are AWS WAF, AWS KMS and AWS Artifact.
W: A=Automated standards checks: Security Hub CSPM evaluates resources against standards such as FSBP and the CIS benchmark and reports a security score.
C=Findings aggregation: it pulls findings from GuardDuty, Inspector and other services into one normalized view so teams can prioritize them.
X: B=Third-party audit reports: AWS's SOC and ISO reports are downloaded from AWS Artifact, not produced by Security Hub CSPM.
D=Filtering web requests: blocking SQL injection in HTTP requests is the job of AWS WAF, not a posture management service.
E=Creating encryption keys: encryption keys are created and stored in AWS KMS or AWS CloudHSM; Security Hub CSPM does not manage keys.
T: Security Hub CSPM checks resources against security standards and aggregates findings from many services into one view.
V: AWS Security Hub CSPM, AWS Config
