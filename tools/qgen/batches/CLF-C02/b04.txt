@ CLF-C02 D1 T1.1 applied definition
S: A regional chain of veterinary clinics runs its appointment system on one server in a back-office room. Twice last year a power failure in that building took the system offline for a full day. The owners want the system to keep working for staff when one server or facility fails. Which cloud concept describes this goal?
A: High availability, which keeps a system running with little or no downtime by placing redundant resources in separate locations, such as several Availability Zones.
B: Elasticity, which adds resources automatically when demand rises and removes them again when demand falls, so that capacity closely follows the actual load.
C: Economies of scale, which lets AWS lower its prices over time because it buys and runs hardware for a very large number of customers at the same time.
D: Agility, which lets teams create and delete resources within minutes, so that they can try new ideas quickly and drop the ones that do not work out.
K: A
G: ## Single points of failure
A system that lives in one room depends on everything in that room: one power feed, one network uplink, one cooling unit. If any of them fails, the whole system stops. Each of these is a **single point of failure**.
## High availability
**High availability** is the property of a system that keeps working, with little or no downtime, when individual components fail. It is achieved with redundancy: more than one copy of each critical part, placed where one failure cannot hit all copies at once.
## How AWS makes it practical
Every AWS Region contains several **Availability Zones (AZs)**. Each AZ is one or more discrete data centers with redundant power, networking and connectivity, physically separated from the other AZs in the Region.
- Run copies of the application in two or more AZs.
- Put a load balancer in front so traffic goes only to healthy copies.
- If a power problem hits one AZ, the copies in the other AZ keep serving users.
A small business gets this protection without building and running a second server room of its own.
## Do not confuse it with
- **Elasticity** and **scalability** are about handling changing or growing load, not failures.
- **Agility** is about how fast teams can provision and experiment.
W: High availability: the owners want the appointment system to stay usable when a server or a building has a problem. That is the definition of high availability, which AWS customers achieve by running redundant copies in more than one Availability Zone.
X: B=Elasticity: elasticity matches capacity to changing demand. The clinics' problem is a failure that stops the only server, not a rise or fall in the number of users.
C=Economies of scale: this explains why AWS prices can fall over time. It says nothing about keeping a system running when a facility loses power.
D=Agility: agility is about creating resources and trying ideas quickly. Fast provisioning does not by itself keep a running system online through a power failure.
T: Keeping a system running when a component or facility fails is high availability, which on AWS is built with redundant resources across Availability Zones.
V: AWS Global Infrastructure, Elastic Load Balancing

@ CLF-C02 D1 T1.1 advanced comparison
S: A news website gets a sudden surge of visitors when a major story breaks. Its AWS environment adds web servers within minutes during the surge and removes them automatically once traffic returns to normal a few hours later. Which cloud concept does this behavior describe?
A: Fault tolerance, the ability of a system to keep running without interruption when one of its components fails, by using redundant copies of that component.
B: Elasticity, the ability to acquire resources automatically as demand rises and release them as demand falls, so capacity closely follows the actual load.
C: Durability, the ability of a storage service to keep data intact over long periods by storing redundant copies of each object across several devices.
D: Economies of scale, the lower unit cost that AWS achieves by running very large amounts of hardware for many customers and passing on the savings.
K: B
G: ## Words that sound alike
The exam often offers several cloud terms that all sound positive. Each one describes a different property:
- **Elasticity**: resources grow *and shrink* automatically with demand. The key detail is the release of capacity when it is no longer needed.
- **Scalability**: the system can handle more load by adding resources. It says nothing about giving them back.
- **Fault tolerance / high availability**: the system keeps working when a part fails.
- **Durability**: stored data is not lost over time (for example, Amazon S3 is designed for very high durability).
- **Economies of scale**: AWS's size lowers its costs and therefore its prices.
## Example
A news site normally needs 4 web servers. When a story breaks, Amazon EC2 Auto Scaling raises the count to 20; three hours later it returns to 4. The site paid for 20 servers only for those three hours. That round trip, up and back down, is elasticity.
W: Elasticity: the environment adds servers when the surge arrives and removes them when the surge ends, so the capacity tracks real demand in both directions. The automatic scale-in is what separates elasticity from simple growth.
X: A=Fault tolerance: this is about surviving the failure of a component. Nothing in the scenario fails; the servers are added because of more visitors, not because something broke.
C=Durability: durability describes how safely stored data is kept over time. Adding and removing web servers has nothing to do with protecting stored objects.
D=Economies of scale: this explains why AWS can charge low prices. It does not describe how a single customer's environment reacts to a traffic surge.
T: Capacity that automatically grows with demand and shrinks again afterward is elasticity.
V: Amazon EC2 Auto Scaling

@ CLF-C02 D1 T1.1 applied use-case
S: A sporting goods retailer wants to test a new product recommendation feature for one month. If customers do not use it, the team will drop the idea. On premises, such a test would require buying servers that might never be used again. Which AWS Cloud benefit makes this test low risk?
A: Massive economies of scale, because AWS buys hardware for millions of customers and can therefore offer the retailer a lower price on servers it buys outright.
B: Go global in minutes, because the team can launch the feature in several Regions on different continents at once and compare customer reactions in each one.
C: High durability, because the data the feature creates is copied across several devices and Availability Zones, so nothing is lost if the test is abandoned.
D: Increase speed and agility, because the team can create the resources in minutes, run the test, and delete everything afterward with nothing left to pay for.
K: D
G: ## The cost of failing on premises
Experiments fail often. On premises, a failed experiment still leaves the company with servers it bought, licensed, racked and must now depreciate or resell. Because a failed test is expensive, teams run fewer tests and innovate more slowly.
## The cost of failing on AWS
On AWS, resources are created when needed and deleted when they are not. A one-month test costs one month of usage. If the idea fails, the team deletes the resources and the charges stop.
AWS lists this under the advantage **increase speed and agility**: because the cost and time of trying something are low, the organization can experiment more often and bring successful ideas to market faster.
## Example
A team launches a few EC2 instances and a small database for 30 days. Customers ignore the feature, so the team deletes the stack on day 31. No hardware remains on the books.
W: Speed and agility: the team provisions the test environment in minutes and removes it when the month ends, so a failed experiment costs only the short period it ran. Low-cost, fast experiments are exactly what this advantage describes.
X: A=Economies of scale: AWS's scale does lower prices, but it does not sell servers for customers to own. The low risk comes from being able to delete resources, not from a cheaper purchase.
B=Go global in minutes: launching the test in many Regions adds cost and complexity. The scenario is about the risk of buying hardware for a short test, not about reaching distant customers.
C=High durability: durability protects stored data from loss. It does nothing to reduce the financial risk of buying hardware for a test that may be dropped.
T: Being able to create resources for a short test and delete them afterward makes experiments cheap; this is the speed and agility benefit.
V: Amazon EC2

@ CLF-C02 D1 T1.1 applied definition
S: A student asks why AWS has been able to lower the prices of many of its services repeatedly over the years, even though customers did not negotiate for those reductions. Which AWS Cloud benefit explains this?
A: Stop guessing capacity, because customers can scale their resources up and down with demand and so avoid paying for idle servers they bought for peak traffic.
B: Trade fixed expense for variable expense, because customers pay only for the resources they consume instead of paying for data centers before they use them.
C: Benefit from massive economies of scale, because aggregated usage from many customers lets AWS lower its own costs and pass the savings on as lower prices.
D: Go global in minutes, because AWS operates Regions on many continents, which allows customers to deploy closer to users without building any facilities.
K: C
G: ## Economies of scale
When a company buys and runs a few servers, it pays retail prices for hardware, power and network capacity. AWS buys and runs hardware for hundreds of thousands of customers. At that size it can:
- negotiate better prices for hardware, power and bandwidth;
- design its own efficient servers, networking and chips;
- automate operations so each person runs far more equipment.
These lower costs are passed on to customers as lower pay-as-you-go prices. AWS calls this advantage **benefit from massive economies of scale**.
## How to spot it in a question
Look for wording about *price levels* and *why AWS can be cheaper*, rather than about how much a single customer uses. Questions about paying only for what you use describe variable expense; questions about lower unit prices that come from AWS's size describe economies of scale.
W: Economies of scale: the combined usage of a very large customer base lowers AWS's own costs per unit, and AWS passes those savings to every customer as price reductions, with no negotiation needed.
X: A=Stop guessing capacity: this saves money by avoiding idle capacity, but it changes how much a customer uses, not the price AWS charges per unit.
B=Fixed to variable expense: this describes how customers pay (per use instead of up front). It does not explain why the price of each unit drops over time.
D=Go global in minutes: global Regions help customers reach users quickly. Geographic reach is not the reason prices fall.
T: Lower unit prices that come from AWS's size and combined customer usage are economies of scale.
V: AWS Global Infrastructure

@ CLF-C02 D1 T1.1 applied definition
S: An insurance company runs its claims system in one AWS Region and its reporting system in a different Region. A serious service problem affects several services in the first Region for some hours, while the reporting system keeps working normally. Which design property of the AWS global infrastructure explains this?
A: Edge locations, which keep a standby copy of every workload in the account and take over automatically whenever a service problem affects the Region it runs in.
B: AWS Regions, which are designed to be isolated from one another, so a problem in one Region is contained there and does not spread to workloads in other Regions.
C: Availability Zones, which are each located in a different country, so the zones used by the two systems were too far apart to be affected by the same problem.
D: Automatic cross-Region failover, which AWS turns on in every account so that any affected workload moves to another Region without action by the customer.
K: B
G: ## Regions are isolated by design
An **AWS Region** is a separate geographic area that contains several Availability Zones. AWS designs each Region to be **isolated from the other Regions**: Regional services run independently in each Region. This limits the **blast radius** of a problem: an issue in one Region is meant to stay in that Region.
## What isolation means for customers
- A workload in Region A is not affected by most problems in Region B.
- AWS does **not** move a customer's workloads or data to another Region on its own. If a company wants to recover in a second Region, it must copy its data and be ready to run there itself (for example with AWS Backup copies or S3 Cross-Region Replication).
## Two levels of separation
- **Availability Zones** protect against the failure of a data center inside one Region. All AZs of a Region are in the same general area.
- **Regions** protect against problems that affect a whole Region.
W: Isolated Regions: each Region runs its services independently of the other Regions, so the problem in the first Region did not reach the reporting system running in the second one.
X: A=Edge locations: edge locations cache content for services such as Amazon CloudFront and answer DNS queries for Route 53. They do not hold standby copies of customer workloads.
C=One country per AZ: the Availability Zones of a Region are all in the same geographic area, and both systems here are in different Regions anyway, not just different zones.
D=Automatic cross-Region failover: AWS does not move customer workloads between Regions by itself. Multi-Region recovery is something the customer designs and sets up.
T: AWS Regions are isolated from each other, so a problem in one Region stays there; recovering in a second Region is the customer's own design choice.
V: AWS Global Infrastructure

@ CLF-C02 D1 T1.1 applied use-case
S: A fitness app startup has 5,000 users today and expects millions within two years if marketing succeeds, but it cannot predict how quickly that growth will happen. Which AWS Cloud benefit removes the need to buy servers now for the users it may have later?
A: High availability, because the app can run in several Availability Zones, which ensures that the growing number of users never sees an outage during a release.
B: Durability, because data stored in Amazon S3 is copied across several facilities, which lets the startup keep the records of millions of users without loss.
C: Scalability, because the startup can add compute, storage and database capacity as the user base grows, paying for that capacity only once it is needed.
D: Security, because AWS manages the physical protection of its data centers, which means the startup does not have to hire guards for its own server rooms.

G: ## Planning for growth on premises
A startup that owns its servers must decide today how much hardware to buy for next year. If it buys too much, cash sits idle in unused servers. If it buys too little, the app slows down or fails just when growth arrives, and new hardware takes weeks to install.
## Scalability on AWS
**Scalability** is the ability to handle more load by adding resources. On AWS, a team can:
- add more EC2 instances or larger ones;
- let managed services such as Amazon DynamoDB or Amazon S3 grow with the data;
- move to bigger database instances when needed.
Capacity is added in minutes, when growth actually arrives, and billed from that point on. This connects to the AWS advantage **stop guessing capacity**.
W: Scalability: the startup provisions what 5,000 users need today and adds capacity step by step as real growth arrives, so it never has to bet money on a forecast it cannot make.
X: A=High availability: running across several AZs keeps the app online during failures, but it does not decide how much capacity to buy for future growth.
B=Durability: S3 durability protects stored data from loss. It does not address buying compute capacity ahead of uncertain growth.
D=Security: AWS's physical security is a real benefit, but it has nothing to do with matching capacity to an unpredictable number of users.
T: Uncertain future growth points to scalability: add capacity on AWS when demand arrives instead of buying it in advance.
V: Amazon EC2, Amazon DynamoDB

@ CLF-C02 D1 T1.1 applied definition
S: A manager new to cloud computing asks for a description of the cloud model that AWS offers. Which TWO statements are characteristics of cloud computing on AWS? (Select TWO)
A: Customers provision resources themselves on demand, through the console, CLI or API, without needing a person at AWS to process each request.
B: Customers must sign a contract of at least one year before they can launch their first resource, so that AWS can plan the hardware it will reserve.
C: Customers pay as they go for the resources they use, metered by measures such as hours, requests or gigabytes, instead of paying up front for hardware.
D: Customers receive dedicated physical servers by default, so that no other AWS customer's workload ever shares the same hardware as their instances.
E: Customers send their own servers to an AWS facility for installation, and AWS then charges them a monthly fee for rack space, power and cooling.
K: A,C
G: ## What cloud computing means
AWS defines cloud computing as the **on-demand delivery of IT resources over the internet with pay-as-you-go pricing**. Instead of buying, owning and maintaining physical data centers and servers, customers use compute, storage and databases from a cloud provider as they need them.
## Key characteristics
- **On-demand self-service**: customers create and delete resources themselves through the console, the AWS CLI or the API. No ticket to AWS staff is required.
- **Pay as you go / measured service**: usage is metered (per second or hour of compute, per GB stored, per request) and billed accordingly.
- **Rapid elasticity**: capacity can grow and shrink quickly.
- **Resource pooling**: many customers share large pools of infrastructure, isolated from one another by the virtualization layer.
- **Broad network access**: resources are reached over the network from anywhere.
## What it is not
Cloud computing is not colocation (bringing your own servers to someone else's building), and long-term contracts are optional discounts, not a requirement.
W: A=On-demand self-service: customers create resources themselves at any time with the console, CLI or API, and they are available in minutes without a manual request to AWS.
C=Pay as you go: usage is metered and billed by measures such as compute time, storage and requests, so there is no up-front hardware purchase.
X: B=Mandatory one-year contract: no commitment is needed to start. Commitments such as Savings Plans are optional and exist only to earn a discount.
D=Dedicated servers by default: by default instances run on shared, multi-tenant hardware with isolation provided by the hypervisor. Dedicated Instances and Dedicated Hosts are optional and cost more.
E=Shipping your own servers: that describes colocation. With cloud computing the provider owns and runs the hardware and the customer rents capacity from it.
T: Cloud computing on AWS means on-demand, self-service resources over the internet with pay-as-you-go pricing.
V: AWS Management Console, AWS CLI

@ CLF-C02 D1 T1.1 advanced troubleshooting
S: A company moved its web application to Amazon EC2 by copying its on-premises setup: 12 large instances run around the clock, sized for the busiest week of the year. Six months later the CFO asks why the expected cloud savings have not appeared. What is the most likely reason?
A: The company has not used elasticity: the fleet stays at its peak size all year, so it keeps paying for capacity that is idle most of the time, just as it did on premises.
B: The company chose a Region that is too far from its users, and AWS charges a higher hourly price for every instance that serves traffic to users on another continent.
C: The company did not enable AWS Shield Advanced, and without it AWS automatically adds a surcharge to every EC2 instance that receives traffic from the internet.
D: The company runs its instances in a single Availability Zone, and AWS bills single-AZ instances at a higher rate than instances that are spread across two zones.
K: A
G: ## Lift and shift copies the old habits too
Moving servers to AWS unchanged (rehosting) is quick, but it also copies the old capacity plan. On premises, the company had to buy for the peak. If it keeps the same peak-sized fleet running 24 hours a day on AWS, it now *rents* the idle capacity instead of owning it, and the savings never arrive.
## Using elasticity
The cost benefit of the cloud comes from matching capacity to demand:
- use Amazon EC2 Auto Scaling to add instances during busy periods and remove them afterward;
- rightsize instances to the load they really carry;
- stop non-production resources when nobody uses them.
Example: if the busy week needs 12 instances but a normal week needs 4, an Auto Scaling group that runs 4 most of the year and 12 for one week costs far less than 12 instances all year.
W: Unused elasticity: a fleet fixed at its yearly peak pays for idle capacity on most days. The savings appear only when capacity follows demand, for example with Auto Scaling scaling in after busy periods.
X: B=Distance-based pricing: EC2 prices differ somewhat between Regions, but AWS does not add a surcharge based on where users are. Distance affects latency, not the instance rate.
C=Shield Advanced surcharge: AWS Shield Standard protection is included at no extra cost, and AWS does not add a surcharge to EC2 instances that lack Shield Advanced.
D=Single-AZ premium: EC2 instances are not priced higher for running in one AZ. Spreading across AZs improves availability, not the hourly rate.
T: Moving to AWS saves money only when capacity follows demand; a fleet kept at peak size all year wastes the same idle capacity as before.
V: Amazon EC2 Auto Scaling

@ CLF-C02 D1 T1.1 advanced tradeoff
S: A manufacturer's disaster recovery plan relies on a second data center that it owns and keeps fully equipped, although that equipment sits idle almost all the time. The company wants to keep a recovery site in a distant location but stop paying for idle capacity. How does the AWS Cloud help?
A: The company keeps an up-to-date copy of its data and a small set of core systems in a second AWS Region, and adds full capacity there only during a disaster.
B: The company buys three-year Reserved Instances in a second AWS Region for its full production size, so the idle recovery capacity is billed at a lower rate.
C: The company relies on AWS to copy its workloads to another Region during a disaster, because recovery between Regions is included in every account at no charge.
D: The company keeps its recovery copy in a second Availability Zone of the same Region, because zones are hundreds of kilometers apart and count as a distant site.
K: A
G: ## The cost of a traditional recovery site
On premises, a recovery site is a second building full of servers, storage and network gear. It must be bought, powered, cooled and maintained, yet it does useful work only during a disaster. Most of its cost pays for capacity that waits.
## Disaster recovery on AWS
AWS lets a company keep the *ability* to recover without keeping the full *capacity* running:
- Data is copied continuously or on a schedule to a second **Region** far from the primary site (for example with AWS Backup cross-Region copies or S3 Cross-Region Replication).
- Only a small core runs there all the time, such as a database replica, or nothing but the data and the templates to rebuild servers.
- During a disaster the company launches or scales up the rest, and pays for full capacity only while it is used.
Patterns such as **backup and restore**, **pilot light** and **warm standby** trade recovery speed against standing cost; services such as AWS Elastic Disaster Recovery can automate the replication and recovery.
## Example
A plant's systems need 40 servers. The recovery Region keeps only the replicated data and two small instances. In a disaster, an Auto Scaling group or a template launches the other servers within minutes.
W: Small standby, scale on demand: storing data and a minimal core in a distant Region costs a fraction of a second data center, and elasticity lets the company add full capacity only when a disaster actually happens.
X: B=Reserved Instances at full size: a commitment lowers the rate but still pays for the whole recovery fleet every hour, which keeps the idle-capacity cost the company wants to remove.
C=Free automatic cross-Region recovery: AWS does not copy workloads to another Region on its own, and there is no free built-in recovery. The customer sets up replication and pays for what it uses.
D=Second AZ as distant site: Availability Zones are separated from each other but sit in the same Region's area. A zone is not a distant site for an event that affects that whole area.
T: On AWS a recovery site can be mostly data plus a small core in a second Region, with full capacity added only during a disaster, so idle hardware disappears.
V: AWS Backup, AWS Elastic Disaster Recovery, Amazon EC2 Auto Scaling

@ CLF-C02 D1 T1.1 advanced definition
S: A startup with no infrastructure team stores files in Amazon S3 Standard and runs its web servers on Amazon EC2. It asks which high availability it gets automatically from AWS and which it must design itself. Which TWO statements are correct? (Select TWO)
A: Objects in the S3 Standard storage class are stored redundantly across multiple Availability Zones in the Region, with no extra design work by the startup.
B: Each EC2 instance runs in a single Availability Zone, so any redundancy across zones for the web servers is something the startup must set up itself.
C: Each EC2 instance is copied automatically to a second Availability Zone, and AWS restarts it there whenever its original zone has a power problem.
D: Objects stored in Amazon S3 are copied automatically to every AWS Region, so the startup's files stay available even if its own Region has a problem.
E: Edge locations keep a standby copy of every EC2 instance, so the web servers keep answering users from the edge when their Availability Zone fails.
K: A,B
G: ## Built-in versus designed availability
Some AWS services are **Regional** and spread data across Availability Zones (AZs) for the customer. Others give the customer a resource that lives in **one AZ**, and the customer decides how many copies to run and where.
## Built in: Amazon S3
S3 Standard, and most other S3 storage classes, store each object redundantly across a minimum of three AZs in the Region. The startup does nothing extra for this. (One Zone classes such as S3 One Zone-IA are the deliberate exception: cheaper, but stored in a single AZ.) Other services, such as Amazon DynamoDB, also replicate across AZs automatically.
## Designed by the customer: Amazon EC2
An EC2 instance is launched into a subnet, and a subnet is in exactly one AZ. EC2 can recover an instance onto new hardware after a host problem, but it stays in the same AZ. To survive the loss of a whole AZ, the customer runs instances in several AZs, for example with an Auto Scaling group and a load balancer.
## Not automatic
- Copying data to another Region happens only if the customer configures it.
- Edge locations cache content; they do not run standby servers.
W: A=S3 Standard across AZs: S3 itself stores each object in several AZs of the Region, so the files survive the loss of one zone without any design work by the startup.
B=EC2 is zonal: an instance lives in one AZ, so redundancy across zones exists only if the startup launches instances in several AZs behind a load balancer.
X: C=Automatic copy to a second AZ: EC2 does not keep a standby copy of an instance in another AZ. Recovery after a host problem stays in the same AZ.
D=Copied to every Region: S3 keeps objects in the Region the customer chose. Copies in other Regions exist only if the customer sets up replication.
E=Edge standby servers: edge locations cache content for CloudFront and serve DNS for Route 53; they do not run copies of EC2 instances.
T: Regional services such as Amazon S3 spread data across Availability Zones automatically, while EC2 instances are zonal and the customer designs multi-AZ redundancy.
V: Amazon S3, Amazon EC2

@ CLF-C02 D1 T1.1 applied use-case
S: A software company's testers wait several days each time they need a fresh copy of the full staging environment, because administrators build networks, servers and databases by hand. Which approach uses an AWS Cloud benefit to solve this?
A: Buy Reserved Instances for the staging servers, so that the capacity for every new staging copy is already paid for and waiting for the testers when they need it.
B: Ask AWS Support to build each new staging copy, because AWS engineers create customer environments on request as part of every account's support plan.
C: Move the staging environment to a larger Region, so that more instance types are available and administrators can build the servers by hand more quickly.
D: Describe the environment once as code with AWS CloudFormation, so testers can create an identical copy in minutes and delete it when testing ends.
K: D
G: ## Manual builds are slow and inconsistent
Building an environment by hand means clicking through dozens of settings: networks, security groups, servers, databases. It takes days, and two copies built by two people rarely match exactly.
## Infrastructure as code
On AWS, every resource can be created through an API. **AWS CloudFormation** uses this: the team writes a template (YAML or JSON) that describes the whole environment. CloudFormation then creates all the resources as one **stack**, in the right order.
- A new copy of staging is one command or one click away.
- Every copy is identical, because it comes from the same template.
- When testing ends, deleting the stack removes every resource, and the charges stop.
This is a practical form of the **increase speed and agility** advantage: environments become disposable and fast to create.
W: CloudFormation templates: the environment is defined once in code and recreated on demand as a stack. Testers get an identical copy in minutes instead of days, and deleting the stack removes it cleanly.
X: A=Reserved Instances: Reserved Instances are a billing discount for steady usage. They do not build networks, servers or databases, so the manual work and its delays remain.
B=AWS Support builds it: AWS Support gives guidance and troubleshooting help. Building and maintaining customer environments is the customer's job, not a support plan service.
C=Larger Region: the problem is the manual process, not a shortage of instance types. Building by hand in another Region is just as slow.
T: Defining infrastructure as code with AWS CloudFormation turns a days-long manual build into a repeatable copy created in minutes.
V: AWS CloudFormation

@ CLF-C02 D1 T1.1 advanced tradeoff
S: A German healthcare provider must keep patient records inside Germany and wants its records system to keep running if one data center fails. It plans to use the Europe (Frankfurt) Region. Which design meets both requirements?
A: Run the system in one Availability Zone of the Frankfurt Region and replicate the records to a Region in the United States, so a failure in Germany cannot stop it.
B: Run the system across several Availability Zones of the Frankfurt Region, because those zones are separate data centers that all belong to that one Region in Germany.
C: Run the system in the Frankfurt Region and keep a standby copy of the records at CloudFront edge locations across Europe, which take over if a data center fails.
D: Run the system in one Availability Zone of the Frankfurt Region and rely on that zone's redundant power supply, which prevents any of its data centers from failing.
K: B
G: ## Two requirements, one Region
Data residency rules say *where* data may be stored. High availability says the system must survive a failure. On AWS both can often be met inside one Region.
- The customer chooses the **Region** for its resources. The Europe (Frankfurt) Region (`eu-central-1`) is in Germany, and AWS does not move customer content out of it unless the customer configures that.
- Every Region has several **Availability Zones (AZs)**. They are separate data centers with independent power and networking, but they are all part of the same Region and in the same area.
## Putting it together

W: Multiple AZs in Frankfurt: the zones are independent data centers, so one can fail while the others keep the system running, and because they all belong to the Frankfurt Region the records never leave Germany.
X: A=Replicate to the United States: this adds protection, but it moves patient records out of Germany and breaks the residency requirement.
C=Standby at edge locations: edge locations cache content for delivery. They do not run a standby records system, and caching across Europe would place copies outside Germany.

Cleaning up orphaned resources is a basic cloud cost practice: on AWS you pay for what you provision, even if nothing uses it.
W: B=Unattached data volumes: volumes not set to delete on termination survive the instance and keep being billed for their provisioned size until someone deletes them.
D=Leftover snapshots: backup snapshots are independent of the instances and volumes they came from, so they stay and are billed for their stored data until deleted.
X: A=Extra month of compute: EC2 compute charges stop when an instance is terminated. AWS does not add a month of compute, and it would not appear as an EBS charge.
C=Fixed EBS account fee: EBS has no account-level fixed fee. Charges come from resources that still exist, such as volumes (with any provisioned performance) and snapshots.
E=Hidden 90-day copy: AWS does not keep and bill a hidden copy of terminated instances' disks. Data remains only in volumes and snapshots the customer still has (deleted snapshots are kept in the Recycle Bin only if the customer created a retention rule).
T: After terminating instances, delete unattached EBS volumes and unneeded snapshots, because provisioned storage is billed even when nothing uses it.
V: Amazon EBS

@ CLF-C02 D1 T1.4 applied use-case
S: A publishing company pays commercial license fees for the database engine behind its content system and wants to reduce long-term licensing costs on AWS. Which approach addresses this most directly?
A: Move the database to Amazon Aurora PostgreSQL-Compatible Edition, which is based on an open source engine and has no separate database license fee to pay.
B: Move the database to a larger EC2 instance with the same commercial engine, so that fewer database instances are needed and fewer licenses must be bought.
C: Move the database to a Region with lower EC2 prices, so that the savings on compute balance the commercial license fees that stay exactly the same as before.
D: Move the database files to Amazon S3 Glacier storage classes, so that the commercial engine reads its tables from low-cost archive storage instead of disks.
K: A
G: ## Licensing is part of cloud economics
Commercial database engines often charge license and support fees per core or per server. These can be a large share of a database's total cost. Moving to the cloud gives a chance to change engines.
## Open source compatible engines
**Amazon Aurora** offers MySQL-compatible and PostgreSQL-compatible editions. Customers pay for the database instances or capacity, storage and I/O, with no separate engine license fee. Tools such as AWS Database Migration Service and AWS DMS Schema Conversion help convert schemas and code from commercial engines.
## Trade-off
Changing engines is a **replatform or refactor** step: SQL code, stored procedures and application queries may need changes. The licensing savings must be weighed against that migration effort.
W: Aurora PostgreSQL-Compatible: moving to an engine based on open source removes the commercial license fee entirely. The company pays for Aurora usage only, which directly lowers long-term licensing cost.
X: B=Bigger instance, same engine: fewer servers may help a little, but commercial engines are commonly licensed per core, so a bigger instance can need just as many licenses or more.
C=Cheaper Region: compute prices change slightly, while the license fees, the cost the company wants to cut, remain unchanged.
D=Database files in Glacier: Glacier storage classes are for archives with retrieval delays. A live database engine cannot run its tables from archive storage.
T: Switching from a commercial database engine to an open source compatible engine such as Aurora PostgreSQL removes license fees, at the cost of some migration work.
V: Amazon Aurora, AWS Database Migration Service

@ CLF-C02 D1 T1.4 advanced use-case
S: A company runs commercial software on Amazon EC2 under a BYOL agreement that is licensed per CPU core. The workload needs the memory of a large instance type but only a fraction of its cores. Which EC2 feature can lower the license cost?
A: Detailed monitoring, which reports CPU use every minute so that the software vendor bills the company only for the cores that show activity during each hour.
B: Elastic IP addresses, which attach a fixed public address to the instance so that the license is tied to the address instead of the number of CPU cores used.
C: Optimize CPUs, which lets the company launch the instance with fewer active CPU cores or one thread per core, so fewer cores need to be licensed.
D: Instance hibernation, which saves memory to disk when the instance stops so that the license counts only the cores that are running at any given moment.
K: C
G: ## Per-core licensing on the cloud
Many commercial products are licensed per CPU core or per vCPU. Large EC2 instance types have many vCPUs, so a workload that needs a lot of **memory** but little **CPU** can end up paying for licenses on cores it hardly uses.
## Optimize CPUs
Amazon EC2 lets customers **optimize CPU options** for supported instance types, usually when the instance is launched:
- set a **custom number of CPU cores** lower than the default;
- set **threads per core** to 1 to turn off simultaneous multithreading.
The instance keeps the same memory, but exposes fewer vCPUs. The EC2 price stays the same; the saving comes from the BYOL license count. AWS presents this specifically as a way to reduce per-core software licensing costs.
## Related tools
- AWS License Manager tracks license usage against the rules.
- Dedicated Hosts give visibility into physical sockets and cores for socket-based licenses.
W: Optimize CPUs: the instance keeps its large memory but runs with fewer active cores or threads, so the per-core BYOL license covers fewer cores and costs less.
X: A=Detailed monitoring: more frequent CloudWatch metrics do not change how a software vendor counts licensed cores. The cores still exist and are counted.
B=Elastic IP addresses: a static public IP address has nothing to do with per-core licensing, and licenses tied to cores are not moved to an address.
D=Hibernation: hibernation stops the instance and saves memory to disk. When it runs, all of its cores are active and counted.
T: When per-core licenses dominate cost, use EC2 Optimize CPUs to run a large-memory instance with fewer licensed cores.
V: Amazon EC2, AWS License Manager

@ CLF-C02 D1 T1.4 applied use-case
S: A software company runs its Linux-based Java web services on x86 EC2 instances. It wants better price performance without changing its purchasing model or rewriting the application logic. Which option should it evaluate first?
A: Move the web services to AWS Graviton-based instances, which use AWS-designed Arm processors that often deliver better price performance for such workloads.
B: Move the web services to Dedicated Instances, which run on hardware reserved for one customer and therefore offer a lower hourly rate than shared instances.
C: Move the web services to instances with the most vCPUs available, because the largest instance size always gives the lowest cost for each request served.
D: Move the web services to AWS Outposts racks in the company's own data center, because on-premises AWS hardware is billed at a lower hourly rate than a Region.
K: A
G: ## Price performance
Price performance means how much work you get for each dollar. Two instances with the same hourly price can deliver very different amounts of work, so choosing a better-suited instance family is one form of cost optimization.
## AWS Graviton
**AWS Graviton** processors are Arm-based chips designed by AWS. Graviton instance families (for example `m7g`, `c7g`, `r7g`) are generally priced lower than comparable x86 instances and often deliver better price performance for workloads such as web services, containers and many databases.
- Interpreted or JIT-compiled languages such as Java, Python and Node.js usually run with little or no code change.
- Compiled native code and some third-party software need an Arm build.
- Testing is still needed, so the move is usually tried on one service first.
## Fit with the economics
This optimization lowers cost per request without a new commitment, and it combines with existing Savings Plans: Compute Savings Plans apply to Graviton instances too.
W: Graviton-based instances: Java runs on the JVM, so the services usually move to Arm with little change, and Graviton families commonly provide more work per dollar than comparable x86 instances.
X: B=Dedicated Instances: single-tenant hardware costs more, not less, than default shared tenancy. It is chosen for isolation or licensing needs, not price performance.
C=Largest instance size: cost scales with size, and an oversized instance wastes capacity. The largest size is not automatically the cheapest per request.
D=Outposts on premises: Outposts brings AWS infrastructure to a customer site for latency or local data needs. It is not a cheaper way to run web services that already run well in a Region.
T: For workloads that can run on Arm, AWS Graviton-based instances are a common way to improve price performance with little or no code change.
V: AWS Graviton, Amazon EC2

@ CLF-C02 D1 T1.4 advanced use-case
S: A company runs hundreds of Amazon EBS volumes of the older General Purpose SSD gp2 type as boot and data volumes. It wants to lower its block storage bill while keeping the performance its applications need, without downtime. Which action fits best?
A: Change the volumes to the gp3 type with Elastic Volumes, because gp3 costs less per GB and lets IOPS and throughput be set separately from the volume size.
B: Change the volumes to Provisioned IOPS SSD (io2), because io2 costs less per GB than the General Purpose types and also gives more consistent performance.
C: Change all the volumes to Cold HDD (sc1), because it has the lowest price per GB and works for boot volumes as well as for frequently accessed data.
D: Move the data to the instance store of each EC2 instance, because instance store has no separate charge and keeps its data when an instance is stopped.
K: A
G: ## How EBS is billed
Amazon EBS volumes are billed for the **provisioned size** per GB-month, and some types also for provisioned performance. Choosing the right volume type is a simple, ongoing cost lever.
## gp2 versus gp3
- **gp2** (older General Purpose SSD): performance is tied to size, about 3 IOPS per GB with bursting for small volumes. To get more IOPS, teams often had to buy more GB than they needed.
- **gp3** (current General Purpose SSD): a lower price per GB than gp2, with a baseline of 3,000 IOPS and 125 MiB/s at any size. Extra IOPS and throughput can be provisioned separately from capacity.
With **Elastic Volumes**, a volume's type can be changed while it stays attached and in use, so the move needs no downtime. Very large gp2 volumes may have a baseline above 3,000 IOPS, so check their needs and provision extra gp3 IOPS where required. AWS Compute Optimizer also gives EBS volume recommendations.
## Other types
- **io2** (Provisioned IOPS SSD): for the most demanding databases; costs more.
- **st1 / sc1** (HDD): cheap, throughput-oriented storage for large sequential data; they cannot be boot volumes.
- **Instance store**: temporary disks on the host; data is lost when the instance stops or terminates.
W: Move to gp3: gp3 has a lower price per GB, its baseline performance does not depend on size, and Elastic Volumes changes the type while volumes stay in use, so cost falls without downtime.
X: B=io2: Provisioned IOPS volumes are the premium SSD type and cost more than General Purpose volumes. They suit the most demanding databases, not a cost cut.
C=Cold HDD (sc1): sc1 is cheap but is designed for infrequently accessed sequential data and cannot be used as a boot volume, so it does not keep the needed performance.
D=Instance store: instance store is included in some instance types, but it is temporary storage and its data is lost when the instance is stopped or terminated.
T: Changing gp2 EBS volumes to gp3 with Elastic Volumes lowers the price per GB and separates performance from size, without downtime.
V: Amazon EBS, AWS Compute Optimizer

@ CLF-C02 D1 T1.4 advanced tradeoff
S: An online learning company's monthly AWS bill has doubled over the past year. In the same period, its number of active students tripled. The CFO wants to know whether cloud spending is under control. Which measure gives the most useful view?
A: The total monthly AWS bill alone, because any increase in total spending shows that the company's cloud costs are rising out of control and must be cut.
B: The number of EC2 instances running at the end of each month, because fewer instances always means the company is using the AWS Cloud more efficiently.
C: The percentage of the bill covered by Savings Plans, because high commitment coverage proves that every resource the company runs is sized correctly.
D: A unit cost such as AWS spend per active student, which shows whether the cost of serving each customer is falling even while the total bill rises.
K: D
G: ## Total cost versus unit cost
In the cloud, spending is supposed to grow with the business. A rising total bill is not bad by itself; it may simply mean more customers. The useful question is whether each unit of business costs more or less than before.
## Unit metrics
A **unit cost** divides cloud spend by a business measure:
- cost per active user or student;
- cost per order or transaction;
- cost per gigabyte processed.
Example: last year the bill was 100,000 for 50,000 students (2.00 per student). This year it is 200,000 for 150,000 students (about 1.33 per student). Total spend doubled, but the cost of serving each student fell by about a third, which shows improving efficiency.
## Tools
Cost allocation tags, AWS Cost Explorer and AWS Cost and Usage Reports provide the cost side; the business system provides the unit count.
W: Unit cost per student: spend divided by active students shows that each student costs less to serve than before, even though the bill grew, so the CFO can see efficiency rather than raw growth.
X: A=Total bill alone: the total grows naturally with a growing customer base. Without relating spend to business volume, it cannot show whether costs are under control.
B=Instance count: fewer instances can mean larger, more expensive ones, and the count says nothing about how much business they support.
C=Savings Plans coverage: coverage shows how much usage gets a commitment discount. It does not show whether resources are rightsized or whether each student costs less.
T: Judge cloud spending with unit costs, such as spend per customer, because a growing business should see total spend rise while unit cost falls.
V: AWS Cost Explorer

@ CLF-C02 D1 T1.4 advanced tradeoff
S: A company plans to buy a three-year Compute Savings Plan sized to its current EC2 spending. A review shows that many of its instances are much larger than their workloads need. What should the company do first to get the most value from the commitment?
A: Commit to the full current spending right away, because a Savings Plan discount is larger when the hourly commitment is based on oversized instances.
B: Rightsize the oversized instances first and then size the commitment to the smaller usage, so the company does not lock in payment for capacity it does not need.
C: Buy Reserved Instances for the oversized instances as well, so that both discounts apply to the same usage and the instance sizes stop mattering for the cost.
D: Move the oversized instances to Dedicated Hosts before committing, because a Savings Plan only covers instances on dedicated hardware at its highest discount.
K: B
G: ## Commit after you optimize
A **Savings Plan** is a commitment to spend a fixed amount per hour (for example 10 USD/hour) on compute for one or three years, in exchange for lower rates. The commitment is paid whether or not the usage is there.
## The right order
1. **Rightsize** first: shrink or change oversized instances (AWS Compute Optimizer helps), and turn off what is not needed.
2. **Measure** the new, lower steady usage.
3. **Commit** with a Savings Plan or Reserved Instances sized to that steady baseline.
If the company commits first, the hourly commitment is based on waste. After rightsizing later, usage falls below the commitment and the company pays for the unused part anyway.
## Example
Current usage costs 20 USD/hour On-Demand; rightsizing would bring it to 12 USD/hour. A plan sized to today's spend leaves a large share of the commitment unused for three years.
W: Rightsize, then commit: rightsizing lowers the steady usage first, and a commitment sized to that lower baseline gets the discount without paying for capacity the company will later remove.
X: A=Commit to current spending: the discount rate does not improve because instances are oversized. A bigger commitment only locks in payments for waste that rightsizing would remove.
C=Stack Reserved Instances on top: Reserved Instances and Savings Plans do not both discount the same usage hour, and oversized instances still waste money at any rate.
D=Dedicated Hosts first: Savings Plans are not limited to dedicated hardware. Dedicated Hosts usually cost more and would add to the waste, not reduce it.
T: Rightsize resources before buying Savings Plans or Reserved Instances so the commitment matches real, steady usage.
V: Savings Plans, AWS Compute Optimizer
