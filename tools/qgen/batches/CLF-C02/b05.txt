@ CLF-C02 D1 T1.2 applied use-case
S: A retail company protects its web application only with a firewall at the edge of its network. Once traffic passes the firewall, servers, subnets and the database trust each other completely. A Well-Architected review flags this. Which security pillar design principle should the company adopt?
A: Apply security at all layers, adding controls such as security groups, network ACLs and per-tier rules so that each layer is protected, not only the edge.
B: Scale horizontally to increase aggregate availability, spreading the application across many small servers so one breach affects fewer customers.
C: Stop spending money on undifferentiated heavy lifting, handing the network firewall to AWS so the team no longer has to manage it at the edge.
D: Use serverless architectures, removing the servers behind the firewall so there is no operating system left that an attacker could reach.
K: A
G: ## Defense in depth
A single perimeter control is a single point of failure for security. If an attacker gets past it, through a stolen credential, a vulnerable web page or a misconfigured rule, nothing else stands in the way.
The security pillar of the AWS Well-Architected Framework answers this with the design principle **apply security at all layers** (defense in depth). Every layer gets its own controls:
- the network edge (for example AWS WAF or AWS Shield in front of a load balancer);
- the VPC and subnets (network ACLs, route tables);
- each instance or tier (security groups that allow only the traffic that tier needs);
- the operating system and application (patching, input validation);
- the data itself (encryption, access policies).
## Example
A three-tier application can allow HTTPS from the internet only to the load balancer, traffic from the load balancer only to the web tier, and database connections only from the application tier. An attacker who compromises one web server still cannot reach the database directly.
W: Apply security at all layers: the review found that everything behind one firewall is trusted. Adding controls at the subnet, instance, application and data layers means one failed control no longer exposes the whole workload, which is exactly what this security principle asks for.
X: B=Scale horizontally: this reliability principle reduces the impact of a component failure on availability. Many small servers that all trust each other are no harder to attack than one large server.
C=Undifferentiated heavy lifting: this is a cost optimization principle about letting AWS run work that does not set the company apart. Handing over the edge firewall still leaves every internal layer unprotected.
D=Serverless architectures: serverless is a performance efficiency principle. It changes who manages servers, but data, identities and application code still need their own controls at each layer.
T: Relying on one perimeter control is fixed by the security principle "apply security at all layers" (defense in depth).
V: AWS Well-Architected Framework

@ CLF-C02 D1 T1.2 applied use-case
S: At an insurance company, support engineers often log in to the production database and run queries by hand to look up and correct customer records. Auditors are worried about mistakes and misuse. Which Well-Architected security design principle addresses this concern most directly?
A: Implement observability, collecting metrics and logs from the database so engineers can see when their manual queries slow it down.
B: Keep people away from data, giving engineers tools and automated processes so they no longer need direct access to customer records.
C: Measure overall efficiency, comparing the business output of the support team with the cost of the database to justify the access.
D: Anticipate failure, running exercises in which the database is taken offline so engineers practice restoring customer records quickly.
K: B
G: ## Why direct access to data is risky
Every time a person handles sensitive data by hand, there is a chance of a typing mistake, a wrong `UPDATE` without a `WHERE` clause, accidental exposure or deliberate misuse. Broad human access also makes it harder to prove to auditors who saw what.
## The security principle
The security pillar of the Well-Architected Framework includes **keep people away from data**: use mechanisms and tools that reduce or remove the need for direct access to or manual processing of data. Examples:
- a support dashboard or internal application that shows only the fields an engineer needs and logs every action;
- automated runbooks that apply common corrections with tested code;
- read-only reports instead of direct database sessions.
Direct access can remain as a controlled break-glass process for rare cases, with approval and logging.
W: Keep people away from data: replacing manual database sessions with purpose-built tools and automation lowers the risk of human error and misuse and gives auditors a clear, limited set of actions to review.
X: A=Implement observability: this operational excellence principle helps teams understand how workloads behave. Watching the effect of manual queries does nothing to reduce the number of people touching customer records.
C=Measure overall efficiency: this cost optimization principle relates business output to cost. It says nothing about who may handle sensitive data.
D=Anticipate failure: this operational excellence principle is about finding and testing failure scenarios. Practicing restores does not remove the risk of everyday manual edits to customer records.
T: Engineers handling sensitive data by hand points to the security principle "keep people away from data": use tools and automation instead.

@ CLF-C02 D1 T1.2 applied use-case
S: A software company keeps its development and test environments running 24 hours a day, every day, but developers use them only about 50 hours a week. Which Well-Architected cost optimization design principle should guide the fix?
A: Analyze and attribute expenditure, tagging each environment with its owner so the finance team can charge each development team for its usage.
B: Use serverless architectures, rewriting the test environments as functions so they no longer need servers that the team has to manage.
C: Adopt a consumption model, paying only for what is used by stopping the environments outside working hours and starting them when needed.
D: Scale horizontally to increase availability, splitting each environment across several smaller instances in different Availability Zones.
K: C
G: ## Paying for idle resources
On premises, a server costs the same whether it is busy or idle, so leaving it on is free. In the cloud, most compute is billed while it runs. A non-production environment that runs 168 hours a week but is used for about 50 pays for more than 100 idle hours every week.
## Adopt a consumption model
The cost optimization pillar lists **adopt a consumption model**: pay only for the computing resources you need, and increase or decrease usage with business requirements. The pillar uses this very example: stopping development and test environments outside business hours can cut their cost by around 75 percent (40 of 168 hours).
Ways to do it include instance scheduling with automation (for example AWS Systems Manager or Amazon EventBridge Scheduler with a stop/start action) and choosing services that charge per request.
W: Adopt a consumption model: stopping the environments when nobody uses them and starting them again for the working week means the company pays for roughly the hours developers actually need, which is the essence of this principle.
X: A=Analyze and attribute expenditure: tagging and chargeback show who spends the money, which is useful, but the environments would still run idle for most of the week.
B=Use serverless architectures: this performance efficiency principle can lower cost for some workloads, but rewriting whole test environments is a large project and not the direct fix for resources left running.
D=Scale horizontally: this reliability principle adds availability by using several smaller resources. It does nothing about paying for environments during hours when nobody uses them.
T: Resources that run around the clock but are used only part of the time point to "adopt a consumption model": pay only while you use them.
V: AWS Well-Architected Framework, AWS Systems Manager

@ CLF-C02 D1 T1.2 applied definition
S: A finance team is learning the Well-Architected Framework. Which TWO of the following are design principles of the cost optimization pillar? (Select TWO)
A: Measure overall efficiency, by relating the business output of a workload to the costs of delivering it and tracking gains over time.
B: Stop spending money on undifferentiated heavy lifting, letting AWS do work such as racking servers so the team can focus on customers.
C: Experiment more often, using virtual resources to run comparative tests of different instance types and configurations quickly.
D: Anticipate and adopt new, more efficient hardware and software offerings to reduce the environmental impact of each workload.
E: Manage change through automation, applying infrastructure changes with tested code so changes are predictable and reversible.
K: A,B
G: ## The five cost optimization principles
The cost optimization pillar of the Well-Architected Framework is about delivering business value at the lowest price point. Its design principles are:
- **Implement Cloud Financial Management**: build the people, processes and tools to manage cloud spending.
- **Adopt a consumption model**: pay only for what you use.
- **Measure overall efficiency**: measure business output against the cost of delivering it, so you can see whether changes really help.
- **Stop spending money on undifferentiated heavy lifting**: let AWS run data centers and managed services so the team can focus on its own product.
- **Analyze and attribute expenditure**: identify the cost of each workload and owner so you can measure return on investment.
## Telling pillars apart
Many principles sound like they save money, but belong elsewhere. Experimenting cheaply is a performance efficiency principle; adopting more efficient hardware is a sustainability principle; automating change is a reliability principle.
Example of measuring efficiency: a team tracks "cost per 1,000 orders processed" instead of only the monthly bill, so growth in orders is not mistaken for waste.
W: A=Measure overall efficiency: it ties spending to business output, such as cost per transaction, so the team can tell whether an optimization actually improves value for money.
B=Undifferentiated heavy lifting: AWS takes on data center operations and the operational work of managed services, so money and staff time go to what differentiates the business.
X: C=Experiment more often: running comparative tests on virtual resources is a performance efficiency principle, aimed at finding the best-performing configuration.
D=Adopt new, efficient hardware: this is a sustainability principle; it may also lower cost, but the pillar it belongs to is about environmental impact.
E=Manage change through automation: this reliability principle makes infrastructure changes safe and repeatable, not cheaper.
T: Cost optimization principles: Cloud Financial Management, consumption model, measure overall efficiency, stop undifferentiated heavy lifting, analyze and attribute expenditure.

@ CLF-C02 D1 T1.2 applied use-case

A: Consider mechanical sympathy, choosing the database and storage engines that best match the access patterns of the application's data.

Some technologies, such as machine learning, NoSQL at massive scale or media transcoding, need deep specialist knowledge to build and run well. Few small companies can hire that expertise.
The performance efficiency pillar of the Well-Architected Framework names the design principle **democratize advanced technologies**: let the cloud provider carry the complexity, and consume the technology as a service so the team can focus on product development.

- Amazon Rekognition detects objects and text in images through an API call.
- Amazon Translate translates text between languages through an API call.
The logistics company sends images and text to these services and gets results back, with no models to train, host or tune.

C=Experiment more often: comparing configurations helps tune performance, but the company has no model to compare; it needs the capability delivered as a service.

@ CLF-C02 D1 T1.2 advanced use-case
S: A team stores user session data that is always read and written by a single session ID, yet it uses a relational database with complex joins designed for reporting. Responses are slow under load. Which Well-Architected performance efficiency design principle points the team to a better choice?
A: Democratize advanced technologies, asking AWS to run the relational database as a managed service so that the team no longer needs to tune it.
B: Consider mechanical sympathy, using the technology approach that fits the data access pattern, such as a key-value store for lookups by session ID.
C: Go global in minutes, copying the relational database to several Regions so that each user reads sessions from the nearest copy of the data.
D: Automatically recover from failure, adding a standby database that takes over when the primary becomes slow or stops responding to queries.
K: B
G: ## Fit the tool to the access pattern
"Mechanical sympathy" comes from racing: a driver who understands how the car works drives it better. In the Well-Architected Framework, the performance efficiency principle **consider mechanical sympathy** means: use the technology approach that aligns best with your goals, and consider data access patterns when you choose a database or storage service.
## Example access patterns
- Get or put one item by a known key, at high request rates: a key-value store such as Amazon DynamoDB, or an in-memory cache such as Amazon ElastiCache.
- Join many tables for ad hoc reports: a relational database such as Amazon RDS or Amazon Aurora.
- Scan large volumes for analytics: a data warehouse such as Amazon Redshift.
Session data read and written by one session ID is a textbook key-value pattern, so a relational engine optimized for joins is a poor fit.
W: Mechanical sympathy: the workload only ever reads and writes by one key, so a key-value store or cache matches the access pattern and serves these requests fast at scale, unlike a relational design built for reporting joins.
X: A=Democratize advanced technologies: a managed relational database removes operational work, but it is still the wrong kind of engine for simple key lookups at high volume.
C=Go global in minutes: more copies in more Regions add cost and complexity while every copy keeps the same mismatch between engine and access pattern.
D=Automatically recover from failure: a standby is a reliability measure for outages. Slowness caused by the wrong engine is not a failure that failover fixes.
T: Choosing a database or storage service that matches how the data is accessed is the performance efficiency principle "consider mechanical sympathy".
V: Amazon DynamoDB, Amazon ElastiCache, Amazon RDS

@ CLF-C02 D1 T1.2 applied use-case
S: A company has set a goal to reduce the environmental impact of its AWS workloads. Which TWO actions follow the design principles of the Well-Architected sustainability pillar? (Select TWO)
A: Consolidate many lightly used instances onto fewer, well-utilized ones, so less provisioned hardware sits idle for the same amount of work.
B: Move suitable workloads to newer, more energy-efficient instance types, such as AWS Graviton-based instances, as they become available.
C: Keep a full, always-running copy of every environment in a second Region, so that each workload can fail over instantly after an outage.
D: Size each instance for the busiest hour of the year, so that performance stays the same during peaks and nothing ever needs to be resized.
E: Keep every log file and backup in the highest-performance storage tier forever, so analysts never wait for any data to be retrieved.
K: A,B
G: ## The sustainability pillar
The sixth pillar of the Well-Architected Framework focuses on minimizing the environmental impact of running cloud workloads. AWS is responsible for the sustainability **of** the cloud (efficient data centers, renewable energy); customers are responsible for sustainability **in** the cloud (how efficiently they use resources).
## Design principles
- **Understand your impact**: measure the footprint of the workload.
- **Establish sustainability goals**: set long-term goals and model return on investment.
- **Maximize utilization**: right-size and remove idle resources; two hosts at 30 percent use more energy than one host at 60 percent.
- **Anticipate and adopt new, more efficient hardware and software offerings**: for example, Graviton-based instances use less energy for the same performance.
- **Use managed services**: shared services run at higher utilization than many small dedicated setups.
- **Reduce the downstream impact of your cloud workloads**: lower the energy customers need to use your service.
## Trade-offs
Over-provisioning, idle standby copies and keeping all data in the fastest tier can serve other goals, but each one consumes more resources than the work requires.
W: A=Maximize utilization: consolidating lightly used instances does the same work with less idle hardware, which lowers the energy and resources consumed.
B=Adopt efficient hardware: newer instance types such as Graviton-based instances deliver the same work with less energy, which is a named sustainability principle.
X: C=Always-running copy in a second Region: it can improve recovery times, but it doubles the resources that run all the time, which works against the sustainability goal.
D=Size for the busiest hour: provisioning for the yearly peak leaves most capacity idle most of the time, the opposite of maximizing utilization.
E=Highest tier forever: keeping rarely used data in high-performance storage uses more resources than needed; the sustainability pillar recommends lifecycle policies that move or delete data.
T: Sustainability in the cloud means using fewer resources for the same work: maximize utilization and adopt newer, more efficient hardware.
V: AWS Well-Architected Framework, AWS Graviton

A: Always maximize reliability first, because the framework ranks reliability above every other pillar and requires multi-Region designs for all workloads.

K: C
G: ## Pillars can pull in different directions
The six Well-Architected pillars sometimes conflict. More redundancy improves reliability but raises cost and resource use (cost optimization, sustainability). Extra encryption or inspection may add latency (performance efficiency).
The framework does not rank one pillar above all others for every workload. It asks teams to make **informed trade-offs based on business context**. Security and operational excellence are generally not traded away, while reliability, performance, cost and sustainability are balanced against each other.

Recovery requirements are usually expressed as:
- **RTO** (recovery time objective): how long the workload may be down.
- **RPO** (recovery point objective): how much data loss is acceptable.

W: Trade-offs against business needs: the framework expects architects to balance pillars using business requirements. With a one-day tolerance for downtime, an always-on second Region adds cost and resource use that buys little, so a simpler recovery approach fits better.
X: A=Reliability always first: the framework does not require multi-Region designs for all workloads; reliability targets should come from the business's recovery objectives.
B=Cost always first: the framework does not mandate single-Region designs or put cost above everything; some workloads justify multi-Region spending.
D=Highest score on every pillar: reviews identify risks to address in light of business priorities, not a score to maximize; a medium or accepted risk can be the right decision.
T: The Well-Architected Framework asks for informed trade-offs between pillars based on business requirements, not maximum effort on every pillar.

@ CLF-C02 D1 T1.3 applied tradeoff

G: ## Refactor (re-architect)
**Refactor** means changing how an application is architected and developed, usually by adopting cloud-native features such as microservices, containers, serverless functions and managed databases. - managed and serverless services reduce operational work.
Rehost and replatform are faster but keep the monolith's limits. Many companies rehost first to leave the data center and refactor the most important applications later.
W: Refactor: the problems are architectural (a monolith that cannot scale and slows releases), and the business accepts the cost and time. Re-architecting into cloud-native services is the strategy that removes these limits.
X: A=Rehost: lift and shift is fast, but the same monolith on EC2 keeps the same scaling and release problems.
C=Replatform: a managed database helps operations, but the core monolithic architecture, the source of the problems, stays the same.
D=Retain: more on-premises hardware postpones the scaling issue for a while and does nothing about slow feature releases.
T: Architecture-level problems with scale or agility, and a business willing to invest, point to refactor (re-architect).

@ CLF-C02 D1 T1.3 applied use-case
S: A publisher must copy 300 TB of files from its on-premises NFS and SMB file servers to Amazon S3 and Amazon EFS over its network connection before a migration. Which TWO capabilities make AWS DataSync a good fit? (Select TWO)
A: It automates and schedules online transfers between on-premises storage and AWS storage services, copying only changed data on later runs.
B: It encrypts data in transit and verifies data integrity during the transfer, so the publisher can trust that the copies match the source.
C: It converts the schemas and stored procedures of relational databases so they can run on a different database engine in AWS.
D: It continuously replicates entire servers at block level and launches them as Amazon EC2 instances at cutover with short downtime.
E: It provides managed SFTP and FTPS endpoints that business partners use to upload files directly into Amazon S3 buckets.
K: A,B
G: ## What AWS DataSync does
AWS DataSync is an online data transfer service that moves files and objects between storage systems:
- **sources and destinations**: NFS and SMB file servers, HDFS, object storage, other clouds, and AWS services such as Amazon S3, Amazon EFS and Amazon FSx;
- **automation**: an agent connects to on-premises storage; tasks can run on a schedule, and later runs transfer only data that changed;
- **trust**: data is encrypted in transit, and DataSync verifies integrity during and after the transfer;
- **efficiency**: parallel transfers and bandwidth throttling so the network link is used well without starving other traffic.
## Which migration service for which job
- Files and objects: **AWS DataSync**.
- Whole servers to EC2: **AWS Application Migration Service**.
- Databases: **AWS DMS** with **DMS Schema Conversion** for engine changes.
- Partner file exchange over SFTP/FTPS/FTP/AS2: **AWS Transfer Family**.
W: A=Automated, scheduled transfers: DataSync connects to the NFS and SMB shares, moves the data online into S3 and EFS and, on later scheduled runs, copies only what changed, which suits a large pre-migration copy.
B=Encryption and integrity checks: DataSync encrypts data in transit and validates that what arrives matches the source, which matters for 300 TB of files.
X: C=Schema conversion: converting database schemas and code is the job of DMS Schema Conversion, not a file transfer service.
D=Block-level server replication: this describes AWS Application Migration Service, which moves whole servers, not file shares.
E=Managed SFTP endpoints: this describes AWS Transfer Family, built for ongoing file exchange with partners, not bulk migration of file servers.
T: AWS DataSync automates online, scheduled, verified and encrypted transfers of files and objects into AWS storage services.

@ CLF-C02 D1 T1.3 applied troubleshooting
S: A team used AWS DMS to move data from an on-premises Oracle database to Amazon RDS for PostgreSQL. The data copied, but the stored procedures and some table definitions were missing or did not work on PostgreSQL. What step did the team skip?
A: Converting the source schema and code objects to PostgreSQL first with DMS Schema Conversion or the AWS Schema Conversion Tool.
B: Turning on change data capture in the DMS task, so ongoing changes from Oracle keep replicating to PostgreSQL until the cutover.
C: Replicating the Oracle database server at block level with AWS Application Migration Service and launching it on Amazon EC2.
D: Copying the Oracle data files to Amazon S3 with AWS DataSync, so that PostgreSQL could import them in a later loading step.
K: A
G: ## Homogeneous and heterogeneous migrations
- A **homogeneous** migration keeps the same engine (for example Oracle to Oracle, or MySQL to Amazon RDS for MySQL). The schema and code work on the target as they are.
- A **heterogeneous** migration changes engine (for example Oracle to PostgreSQL). Data types, SQL dialects, and procedural code such as PL/SQL stored procedures differ, so the schema and code must be converted.
## Two tools, two jobs
- **AWS DMS** moves the data: a full load, plus change data capture (CDC) to keep the target in sync until cutover. It creates basic tables when needed, but it does not convert stored procedures, functions or other code objects.
- **DMS Schema Conversion** (in the DMS console) or the **AWS Schema Conversion Tool** (a desktop application) converts the schema and code objects to the target engine and produces an assessment report showing what needs manual work.
Typical order: assess and convert the schema, apply it to the target, then run DMS to load and replicate the data.
W: Schema conversion: in a heterogeneous migration the schema and code objects must be converted to PostgreSQL before the data is loaded. DMS moves data, so without DMS Schema Conversion or AWS SCT the stored procedures and engine-specific definitions are missing or broken.
X: B=Change data capture: CDC keeps ongoing data changes flowing until cutover. It affects how current the data is, not whether stored procedures and table definitions work on PostgreSQL.
C=Application Migration Service: rehosting the Oracle server on EC2 keeps the Oracle engine, which does not produce a working PostgreSQL schema on Amazon RDS.
D=DataSync: copying data files to S3 moves bytes, not a converted schema. PostgreSQL cannot use Oracle data files or run Oracle stored procedures.
T: Changing database engines needs schema and code conversion (DMS Schema Conversion or AWS SCT) in addition to AWS DMS data migration.
V: AWS Database Migration Service, AWS Schema Conversion Tool, Amazon RDS

@ CLF-C02 D1 T1.3 applied use-case
S: After assessing 200 applications, a company finds that 25 are no longer used by anyone and 15 must stay in its data center for now because of a pending hardware dependency. Which TWO migration strategies describe the decisions for these 40 applications? (Select TWO)
A: Retire, switching off the applications that are no longer used so that they do not need to be migrated, maintained or paid for.
B: Retain, keeping the applications that cannot move yet in the source environment and revisiting them in a later migration wave.
C: Relocate, moving the applications at the hypervisor level to a cloud-based virtualization platform without changing them.

E: Repurchase, replacing the applications with software as a service products and migrating the existing data into those products.

G: ## Not every application moves
A migration program starts with a portfolio assessment, and for each application the team chooses one of the 7 Rs. Two of them mean the application does **not** move in this program:
- **Retire**: decommission applications that are no longer useful. Assessments regularly find applications nobody uses; switching them off saves migration effort and running costs, and reduces the attack surface.
- **Retain** (revisit): keep applications in the source environment, for example because of a dependency on other systems or hardware, a recent upgrade, compliance requirements, or no business case for moving yet. They are revisited later.

Rehost, relocate, replatform, repurchase and refactor all move the workload, or replace it with a new product.
W: A=Retire: the 25 unused applications are switched off instead of migrated, which removes their migration effort and their ongoing costs.

D=Rehost: lift and shift would move the applications to EC2, including the unused ones that should simply be switched off.
E=Repurchase: replacing applications with SaaS is still a move to a new platform; unused applications need no replacement at all.
T: In the 7 Rs, unused applications are retired and applications that must stay for now are retained.
V: AWS Application Migration Service

@ CLF-C02 D1 T1.3 applied use-case
S: A gaming company runs 120 virtual machines on another public cloud provider and wants to move them to Amazon EC2 as they are, with continuous replication and a short cutover window. Which AWS service should it use?
A: AWS DataSync, which copies files and objects from the other cloud's storage into Amazon S3 buckets on a recurring schedule.
B: AWS Database Migration Service, which copies databases into AWS and keeps them in sync until the applications switch over.
C: AWS Application Migration Service, which replicates source servers at block level and launches them as Amazon EC2 instances.
D: AWS Transfer Family, which provides managed SFTP endpoints that the company can use to upload disk images to Amazon S3.
K: C
G: ## Rehosting from anywhere
AWS Application Migration Service (AWS MGN) is the main AWS service for rehosting (lift and shift). It works with source servers on physical hardware, on virtualization platforms such as VMware vSphere and Microsoft Hyper-V, and on **other public clouds**, as long as the replication agent can run on the server and reach AWS.
## How it works
1. Install the AWS Replication Agent on each source server.
2. MGN continuously replicates the disks at block level into a staging area in the target AWS account.
3. Launch test instances without affecting the source, to check that everything works.
4. At cutover, stop the source workload, let the final changes replicate, and launch the cutover instances on EC2.
Because data is replicated continuously, the downtime at cutover is typically minutes, not hours.
W: Application Migration Service: it replicates the 120 virtual machines continuously from the other cloud at block level and launches them as EC2 instances at cutover, which is exactly a rehost with short downtime.
X: A=DataSync: it moves files and objects between storage services; it cannot turn running virtual machines into bootable EC2 instances.
B=Database Migration Service: it migrates databases only; the company needs whole virtual machines moved.
D=Transfer Family: uploading disk images over SFTP would be manual, would not replicate changes continuously and would not create EC2 instances on its own.
T: Lift-and-shift of servers from on premises or another cloud to EC2, with continuous replication and short cutover, is AWS Application Migration Service.
V: AWS Application Migration Service, Amazon EC2
