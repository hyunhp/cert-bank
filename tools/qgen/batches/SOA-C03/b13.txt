@ SOA-C03 D1 T1.1 advanced use-case
S: A media company sends about 30 TB of debug logs per month to existing Standard-class log groups in CloudWatch Logs. Engineers only run ad hoc CloudWatch Logs Insights queries on them during incidents. A separate audit log group feeds a metric filter that drives a paging alarm and a subscription filter that streams to Amazon Data Firehose. Finance wants the ingestion bill reduced with the LEAST operational overhead, without losing Insights queries or the audit alarm. What should the CloudOps engineer do?
A: Create new log groups in the Essentials log class for the debug logs, repoint the agents to them, and keep the audit group Standard
B: Switch the existing debug log groups to the Essentials log class in place, and keep the audit log group and its filters as they are
C: Move every log group, including the audit group, to the Essentials log class, and recreate the audit metric and subscription filters there
D: Stream the debug logs to Amazon S3 through Firehose instead, and query them with Amazon Athena during incidents instead of Logs Insights
K: A
G: ## Two log classes, one price difference
CloudWatch Logs has a **Standard** class and an **Essentials** class (formerly called Infrequent Access). They differ in **ingestion price only**: storage and Logs Insights query charges are the same.
Essentials keeps the core features: managed ingestion and storage, KMS encryption, cross-account analytics, export to S3 and **Logs Insights queries**. It drops the real-time features:
- metric filters and embedded metric format
- subscription filters
- Live Tail and log anomaly detection
- `GetLogEvents` / `FilterLogEvents` (use Logs Insights instead)
## The class is fixed at creation
After a log group is created, its log class **can't be changed**. Moving data to the cheaper class therefore means creating new log groups and sending the logs there.
## Applying it here
The debug logs are only searched ad hoc, so Essentials fits them. The audit group needs a metric filter and a subscription filter, which only Standard supports.
W: A=New Essentials groups for debug logs: the cheaper ingestion applies to the 30 TB of debug data, Logs Insights still works on them, and the audit group keeps the metric and subscription filters that need Standard.
X: B=Switch in place: a log group's class is chosen at creation and can't be changed afterward, so the existing groups cannot simply be switched.
C=Everything to Essentials: Essentials supports neither metric filters nor subscription filters, so the audit alarm and the Firehose stream would stop working.
D=S3 and Athena: it can cut cost, but it replaces Logs Insights with a new pipeline, tables and queries, which is far more operational work and breaks the requirement to keep Insights queries.
T: Put logs you only query ad hoc into new Essentials log groups; keep anything that needs metric filters, subscriptions or Live Tail in Standard.
V: Amazon CloudWatch Logs

@ SOA-C03 D1 T1.1 advanced use-case
S: An Orders platform runs on EC2 instances in four Auto Scaling groups plus a few standalone instances, all tagged Application=Orders. Teams add and remove groups every month, and instances are replaced daily. Operations needs one alarm that fires when any single Orders instance runs above 90% CPU for 10 minutes. The solution must keep covering new groups and instances without anyone editing alarms, with the LEAST ongoing effort. What should the CloudOps engineer configure?
A: Turn on resource tags for telemetry, then create one alarm on a Metrics Insights query that takes MAX(CPUUtilization) where tag.Application is Orders
B: Create one alarm per Auto Scaling group on the group's aggregated CPUUtilization metric with the Maximum statistic, and add an alarm for each new group
C: Use an EventBridge rule on instance launch to invoke a Lambda function that creates a per-instance CPU alarm and deletes it when the instance ends
D: Create a composite alarm that combines one CPU alarm for every current instance, and rebuild the composite rule whenever the instance list changes
K: A
G: ## Alarms that follow the fleet
A normal metric alarm watches one metric with fixed dimensions, such as one `InstanceId`. When instances are replaced every day, those alarms go stale.
An alarm on a **CloudWatch Metrics Insights query** evaluates a SQL-like query instead. The query is re-run at each evaluation, so it **automatically includes new resources** and drops old ones.
## Filtering by tags
After you turn on **resource tags on telemetry** in the CloudWatch settings, a Metrics Insights query can filter and group by AWS resource tags, for example:
`SELECT MAX(CPUUtilization) FROM "AWS/EC2" WHERE tag.Application = 'Orders'`
Using `MAX` makes the alarm react when any single matching instance is hot, regardless of which Auto Scaling group (or none) launched it.
W: A=Metrics Insights alarm on the tag: one alarm keeps evaluating every instance that carries the tag, including standalone instances and groups added later, with no alarm maintenance.
X: B=Per-group alarms: the Maximum statistic does catch one hot instance, but standalone instances are missed and every new group needs another alarm, which is the editing the team wants to avoid.
C=Lambda per-instance alarms: it works, but it is custom code to build, test and maintain, and orphaned alarms appear whenever a deletion event is missed.
D=Composite of instance alarms: the composite must be rebuilt whenever instances change, which happens daily, so it fails the no-editing requirement.
T: To alarm on a changing set of resources, alarm on a Metrics Insights query filtered by tags rather than maintaining one alarm per resource.
V: Amazon CloudWatch, Amazon EC2, Amazon EC2 Auto Scaling

@ SOA-C03 D1 T1.1 advanced use-case
S: A multi-tenant API writes one JSON log line per request, including tenantId and status, to a CloudWatch Logs log group in the Standard class. Operations wants a dashboard of the 10 tenants causing the most HTTP 429 responses, updated continuously, and an alarm when the single largest tenant exceeds 5,000 throttled requests in 5 minutes, whoever that tenant is. The team wants no custom code and the LEAST operational overhead. Which approach meets these requirements?
A: Create a Contributor Insights rule keyed on tenantId and filtered to status 429, and alarm on INSIGHT_RULE_METRIC with MaxContributorValue
B: Create a metric filter with tenantId as a dimension for status 429 lines, and alarm on the sum of the filter's metric across all tenant dimension values
C: Schedule a Logs Insights query every 5 minutes that counts 429 lines by tenantId, and have a Lambda function publish the top count as a custom metric
D: Add an anomaly detection band to the log group's IncomingLogEvents metric, and alarm when the request volume leaves the band for 5 minutes
K: A
G: ## Top-N contributors without code
**Contributor Insights** rules read structured log events (JSON or space-delimited) from a log group and keep time series for the top-N contributors of a key, for example `tenantId`. A rule can filter events (only `status = 429`) and count or sum them. The console graphs the top contributors continuously.
## Alarming on whoever is on top
The metric math function `INSIGHT_RULE_METRIC(ruleName, metricName)` turns rule data into a metric that can be graphed and alarmed. Useful metric names:
- `MaxContributorValue`: the value of the top contributor in each period, whoever that contributor is
- `UniqueContributors`: how many distinct contributors there are
- `Sum`: the total of all contributors
An alarm on `MaxContributorValue > 5000` with a 5-minute period fires when any one tenant crosses the line.
W: A=Contributor Insights rule: it ranks tenants by 429 count without code, feeds the top-10 dashboard, and `MaxContributorValue` alarms on the single largest tenant without naming it in advance.
X: B=Metric filter with dimension: summing all tenant dimension values alarms on total throttling, not on the largest single tenant, and a dimension per tenant creates a metric for every tenant ID.
C=Scheduled query plus Lambda: it can approximate the result, but it adds a Lambda function and custom metric publishing, which the team wanted to avoid.
D=Anomaly detection on IncomingLogEvents: that metric counts log events of every kind, so it says nothing about which tenant is throttled or how many 429 responses one tenant receives.
T: For "which key contributes most" questions on structured logs, use a Contributor Insights rule and alarm through INSIGHT_RULE_METRIC.
V: Amazon CloudWatch, Amazon CloudWatch Logs

@ SOA-C03 D1 T1.2 advanced use-case
S: An Aurora PostgreSQL DB cluster still has Performance Insights settings from 2025, and the DBA team must now investigate slow statements. They need per-query statistics, slow SQL query analysis and execution plans, with at least three months of history, and the company wants no separate charge for that retention. Performance Insights reached end of life on July 31, 2026. Which TWO actions should the CloudOps engineer take? (Select TWO)
A: Turn on the Advanced mode of CloudWatch Database Insights for the DB cluster, which includes 1 to 24 months of retention at no extra cost
B: Export the Aurora PostgreSQL logs to CloudWatch Logs, because the slow SQL query analysis in Database Insights reads the exported logs
C: Keep Database Insights in Standard mode and buy three months of paid retention, because Standard mode shows execution plans and per-query statistics
D: Raise the Performance Insights retention period to three months on the DB instances, so the existing dashboards keep their history after the change
E: Turn on Enhanced Monitoring with a 1-second granularity, which records each SQL statement with its execution plan for the instance's processes
K: A,B
G: ## From Performance Insights to Database Insights
AWS announced end of life for Performance Insights on **July 31, 2026** and migrated its users to **CloudWatch Database Insights**. Database Insights has two modes for RDS and Aurora:
- **Standard** (default): top contributors to DB load, alarms on database metrics, 7 days of detailed metrics free, and **paid** retention of 1 to 24 months.
- **Advanced**: everything in Standard plus per-query statistics, slow SQL query analysis, SQL execution plans (Aurora PostgreSQL, RDS for Oracle and RDS for SQL Server; lock analysis for PostgreSQL engines), fleet views and on-demand analysis, with **1 to 24 months of retention included at no additional cost**.
Execution plan analysis is engine-specific: Aurora PostgreSQL has it, RDS for PostgreSQL does not, so check the engine before promising plans.
## Prerequisite for slow SQL
Slow SQL query analysis and the consolidated dashboard need the **database logs exported to CloudWatch Logs**. Without the export the feature has nothing to analyze.
W: A=Advanced mode: per-query statistics, slow SQL analysis and plan analysis are Advanced-only features, and Advanced mode includes long retention without a separate retention charge.
B=Export logs: Database Insights builds slow SQL analysis from the database logs, so the Aurora PostgreSQL logs must be exported to CloudWatch Logs.
X: C=Standard plus paid retention: Standard mode does not offer per-query statistics, slow SQL analysis or execution plan analysis, and its long retention is billed.
D=Performance Insights retention: Performance Insights is past its end of life, so configuring it is not a path forward; its users were moved to Database Insights.
E=Enhanced Monitoring: it collects operating-system metrics per process, not SQL statements or execution plans.
T: After the Performance Insights end of life, use Database Insights Advanced mode plus log export for query-level analysis with included long retention.
V: Amazon CloudWatch, Amazon RDS

@ SOA-C03 D1 T1.3 advanced use-case
S: A self-managed database on a current-generation EC2 instance uses a 1 TiB io2 volume provisioned at 32,000 IOPS, and monitoring shows it needs about 30,000 IOPS and 500 MiB/s at peak. Finance asks to cut the volume cost. The database must stay online with no detach, restore or downtime, and the team wants the LEAST operational effort. Which change meets these requirements?
A: Modify the volume in place to gp3 with Elastic Volumes, specifying 32,000 IOPS and 500 MiB/s of throughput in the same modification request
B: Create a snapshot, restore it as a gp3 volume with 32,000 IOPS and 500 MiB/s, and swap the volumes during a short maintenance window
C: Attach two new gp3 volumes at 16,000 IOPS each, build a RAID 0 stripe in the operating system, and migrate the data files online to the stripe
D: Keep the io2 volume and reduce its provisioned IOPS to 16,000, because the gp3 volume type cannot reach 30,000 IOPS on a single volume
K: A
G: ## gp3 limits today
gp3 includes a baseline of **3,000 IOPS and 125 MiB/s**. You can provision more independently of size:
- IOPS up to **80,000**, at up to **500 IOPS per GiB** (maximum reached at 160 GiB)
- throughput up to **2,000 MiB/s**, at up to **0.25 MiB/s per provisioned IOPS**
A 1 TiB volume can therefore have 32,000 IOPS (well under 500 x 1,024), and 500 MiB/s needs only 2,000 IOPS of ratio headroom.
## Elastic Volumes
On current-generation instances, Elastic Volumes changes the type, IOPS and throughput of an attached, in-use volume **without detaching it**. The volume stays usable while the modification runs (it can take hours for large volumes). After a modification completes, the volume can be modified again, up to four times in a rolling 24-hour period.
W: A=In-place change to gp3: gp3 can deliver 32,000 IOPS and 500 MiB/s on a 1 TiB volume, usually at a lower price than io2, and Elastic Volumes makes the change while the database keeps running.
X: B=Snapshot and restore: it reaches the same end state but needs a volume swap, which means downtime and more steps than an online modification.
C=RAID 0 of two gp3 volumes: a single gp3 volume now reaches 80,000 IOPS, so striping only adds data migration and two volumes to manage.
D=Lower io2 IOPS: cutting to 16,000 IOPS starves a workload that needs 30,000, and the premise about gp3 is outdated.
T: gp3 now scales to 80,000 IOPS and 2,000 MiB/s; move io2 volumes that do not need io2 durability to gp3 online with Elastic Volumes.
V: Amazon EBS, Amazon EC2

@ SOA-C03 D1 T1.3 advanced troubleshooting
S: A 200 GiB Amazon EFS file system in Bursting throughput mode serves a build farm. Every afternoon BurstCreditBalance falls to zero and builds slow down sharply. Throughput is idle most of the day and spikes for about one hour, so the average-to-peak ratio is about 3%. The team wants consistent performance at the LOWEST cost, and does not want to store dummy data or track throughput settings. What should the CloudOps engineer do?
A: Switch the file system to Elastic throughput mode, so EFS scales throughput with the spikes and bills only for the throughput that is used
B: Switch the file system to Provisioned throughput sized for the afternoon peak, so the full peak rate is always available all day long
C: Write about 2 TiB of padding files into the Standard storage class, so the higher storage size raises the baseline and earns credits faster
D: Recreate the file system in Max I/O performance mode and copy the data, so the build farm gets a higher aggregate throughput ceiling
K: A
G: ## EFS throughput modes
- **Bursting**: baseline grows with storage in the Standard class (50 KiBps per GiB). Credits accrue below baseline and are spent above it. A 200 GiB file system has a tiny baseline, so a daily spike drains `BurstCreditBalance`.
- **Elastic** (recommended default): throughput scales up and down automatically, and you pay for the throughput used. AWS recommends it for spiky or unpredictable workloads, or an **average-to-peak ratio of 5% or less**.
- **Provisioned**: you pay for a fixed throughput level whether used or not. AWS recommends it when the ratio is 5% or more and the requirement is known.
## Switching rules
After switching to Provisioned or changing the provisioned amount, you can't switch back to Elastic or Bursting, or decrease the amount, for 24 hours.
W: A=Elastic throughput: with a 3% average-to-peak ratio the workload is the textbook case for Elastic, which removes the credit problem and charges only for the throughput used during spikes.
X: B=Provisioned for the peak: it fixes the slowdown but bills the peak rate around the clock for a file system that is idle most of the day, so it is not the lowest cost.
C=Padding files: raising storage does raise the Bursting baseline, but it costs storage every month and the team explicitly ruled out dummy data.
D=Max I/O: Max I/O is a previous-generation performance mode with higher latency that targets parallel operations, not throughput credits, and AWS recommends General Purpose for all file systems.
T: Bursting EFS that runs out of credits during short spikes should move to Elastic throughput; choose Provisioned only for steady, known throughput.
V: Amazon EFS, Amazon CloudWatch

@ SOA-C03 D1 T1.3 advanced use-case
S: Every night a test environment is rebuilt by creating a database volume from the latest production snapshot, which holds about 600 GiB of data. Testing starts one hour later and needs the volume fully initialized by then, but with default lazy loading the first queries are slow for hours. A new snapshot is taken each night, and the team wants a predictable completion time at the LOWEST cost. What should the CloudOps engineer do?
A: Create the volume with an EBS Provisioned Rate for Volume Initialization of 300 MiB/s, which finishes about 600 GiB of data in roughly 35 minutes
B: Create the volume with an EBS Provisioned Rate for Volume Initialization of 100 MiB/s, which is the cheapest rate and finishes well inside the hour
C: Enable fast snapshot restore on each nightly snapshot in the test Availability Zone, and keep it enabled so every restore is instantly fully performant
D: Create the volume normally and run a script that reads every block with dd after attach, so the volume is fully initialized before testing starts
K: A
G: ## Why restored volumes start slow
A volume created from a snapshot loads its blocks from Amazon S3 lazily; the first access to each block is slow until the block has been fetched. The default initialization rate also **fluctuates**, so completion time is unpredictable.
## Two ways to get a fully performant volume
- **Provisioned Rate for Volume Initialization**: when you create the volume, you specify a rate from **100 to 300 MiB/s**. Blocks are downloaded at that rate, so the volume is fully initialized in a predictable time. You are charged based on the snapshot data size and the rate, per volume creation.
- **Fast snapshot restore (FSR)**: volumes from an FSR-enabled snapshot are fully initialized at creation, but FSR is billed for every hour it is enabled per snapshot and Availability Zone.
## Working the numbers
600 GiB = 614,400 MiB. At 300 MiB/s that is about 2,048 seconds (about 34 minutes). At 100 MiB/s it is about 6,144 seconds (about 1.7 hours).
W: A=300 MiB/s initialization rate: about 34 minutes fits the one-hour window with a predictable finish, and the charge is per volume creation rather than per hour.
X: B=100 MiB/s rate: about 6,144 seconds, or 1.7 hours, misses the one-hour deadline.
C=Fast snapshot restore: it does give instant performance, but it is billed per snapshot per Availability Zone for every hour it is enabled and must be set up on a new snapshot each night.
D=dd read script: reading all blocks works but uses the fluctuating default rate, so completion time is unpredictable and the script adds operational work.
T: For a deadline after restoring from a snapshot, use a provisioned volume initialization rate (100 to 300 MiB/s) sized from the snapshot data and the time available.
V: Amazon EBS, Amazon EC2

@ SOA-C03 D1 T1.2 advanced troubleshooting
S: Web instances in an Auto Scaling group use ELB health checks. Twice this month a volume impairment left instances hanging on disk I/O while the health endpoint, served from memory, still returned HTTP 200. CloudWatch showed StatusCheckFailed_AttachedEBS at 1 on those instances, but they stayed in service for hours. The group runs on m5 instances. The team wants such instances replaced automatically with the LEAST custom work. What should the CloudOps engineer do?
A: Set the Auto Scaling group health check type to include EBS together with ELB, so instances that fail the attached EBS status check are replaced
B: Create a CloudWatch alarm on StatusCheckFailed_System for each instance with the EC2 recover action, so impaired volumes trigger a host recovery
C: Change the target group health check path to a deep check that writes a file to the data volume, and keep the group's health check type at ELB only
D: Create an EventBridge rule for EBS volume events that invokes a Lambda function to call SetInstanceHealth Unhealthy for the attached instance
K: A
G: ## Three kinds of EC2 status checks
- **System** status checks: problems with the AWS host or network.
- **Instance** status checks: problems inside the instance (OS, network configuration).
- **Attached EBS** status checks: whether the attached EBS volumes are reachable and can complete I/O. The metric is `StatusCheckFailed_AttachedEBS`.
## Auto Scaling health checks
An Auto Scaling group always uses EC2 status checks; you can add **ELB**, **VPC Lattice**, **EBS** and custom checks. With the **EBS** health check type, the group marks an instance unhealthy when its attached EBS status check fails and replaces it. EBS health checks are available only for instances built on the **Nitro System**, which includes M5.
Example: `--health-check-type "EBS,ELB" --health-check-grace-period 60`.
W: A=EBS health check type: the group starts acting on `StatusCheckFailed_AttachedEBS`, so an instance whose volume cannot complete I/O is replaced without any custom code, and M5 is a Nitro type that supports it.
X: B=Recover on system check: the system status check covers host and network problems, not attached-volume I/O, so this alarm would not fire for these events.
C=Deep health check only: a check that writes to disk could detect the hang, but it requires application changes and still depends on the probe timing out rather than on the AWS-reported volume status.
D=EventBridge plus Lambda: it can work, but it is custom code to build and maintain when the group already has a built-in health check for this status.
T: When instances hang on impaired EBS volumes, add the EBS health check type to the Auto Scaling group (Nitro instances only).
V: Amazon EC2 Auto Scaling, Amazon EBS, Amazon CloudWatch

@ SOA-C03 D1 T1.1 advanced use-case
S: Every Sunday from 02:00 to 06:00 UTC, a team patches a fleet, and 60 CloudWatch alarms fire SNS pages and EC2 reboot actions while the hosts are intentionally down. The team wants those actions muted only during that window, the alarms still evaluated, and, if a problem is still present when the window ends, the actions to run then without anyone re-triggering them. Which approach meets these requirements with the LEAST overhead?
A: Create an alarm mute rule with a cron expression for Sunday 02:00 and a four-hour duration that targets the 60 alarms by name
B: Use EventBridge Scheduler to call DisableAlarmActions on the 60 alarms at 02:00 and EnableAlarmActions on them again at 06:00
C: Wrap each alarm in a composite alarm with a maintenance alarm as its actions suppressor, and move every SNS and EC2 action to the composites
D: Set each alarm's missing data treatment to ignore and raise its evaluation periods to 240 one-minute periods during the maintenance window
K: A

A **mute rule** mutes the **actions** of target alarms during a time window, while the alarms keep evaluating and changing state.

No workload needs private NAT to other networks. The team wants highly available outbound internet access with the LEAST operational overhead. What should the CloudOps engineer do?
A: Create a regional NAT gateway in automatic mode, and point every private subnet's default route at that single NAT gateway ID
B: Keep zonal NAT gateways and add an EventBridge rule that creates a NAT gateway and route table whenever a subnet appears in a new zone
C: Replace the NAT gateways with one zonal NAT gateway in a single public subnet, and route every private subnet's default route to it
D: Attach an egress-only internet gateway to the VPC and route every private subnet's default route through it instead of NAT gateways
K: A
G: ## Regional NAT gateways
A **zonal** NAT gateway lives in one public subnet in one Availability Zone, so high availability means one per zone plus per-zone route tables, repeated whenever workloads move into a new zone.
A **regional NAT gateway** is created for the VPC, not a subnet:
- It **needs no public subnet**; it is a standalone resource with its own route table that AWS creates with a route to the internet gateway.
- It **expands automatically** into Availability Zones where your network interfaces appear (this can take up to 60 minutes, during which traffic is processed from another zone) and contracts where they disappear.
- Every private subnet can use the **same NAT gateway ID** as its default route.
- In automatic mode AWS manages the IP addresses; up to 32 IPs per zone are supported.
- It does **not support private NAT**; use zonal NAT gateways for that.
W: A=Regional NAT gateway: one NAT ID serves every zone, follows workloads into new zones without new gateways or route tables, and removes the need for public subnets.
X: B=EventBridge automation: it keeps zonal gateways and public subnets and adds custom code to maintain, the opposite of least overhead.
C=Single zonal NAT gateway: it is cheap but a zone failure stops outbound access for every subnet, and it still needs a public subnet.
D=Egress-only internet gateway: it provides outbound access only for IPv6 traffic, so IPv4 workloads lose internet access.
T: For multi-AZ outbound IPv4 without public subnets or per-zone NAT plumbing, use a regional NAT gateway (zonal remains for private NAT).
V: Amazon VPC

@ SOA-C03 D5 T5.1 advanced use-case
S: A security team turned on VPC Block Public Access for an account in ingress-only mode. Private subnets still reach the internet through NAT gateways, but an internet-facing Application Load Balancer in two public subnets of one VPC no longer receives traffic. Only that ALB may accept inbound internet traffic, and its targets must stay unreachable from the internet otherwise. What should the CloudOps engineer do?
A: Create bidirectional exclusions for both of the ALB's public subnets, and keep the targets in private subnets that have no exclusion
B: Create an exclusion for only one of the ALB's public subnets, and keep the second subnet blocked to reduce the exposed surface
C: Switch the account's Block Public Access mode to bidirectional, which allows inbound load balancer traffic through the internet gateway
D: Create an egress-only exclusion for the whole VPC, so the ALB can answer internet clients while new inbound connections stay blocked
K: A
G: ## VPC Block Public Access
VPC BPA blocks traffic through internet gateways in a Region, overriding route tables and security groups:
- **Bidirectional** mode: blocks all traffic to and from internet gateways and egress-only internet gateways (except exclusions).
- **Ingress-only** mode: blocks inbound internet traffic; traffic through NAT gateways and egress-only internet gateways still works because they only allow outbound-initiated connections.
## Exclusions
You can exclude VPCs or subnets:
- **Bidirectional** exclusion: all internet traffic to and from the excluded resource is allowed.
- **Egress-only** exclusion: only outbound is allowed; it applies only when BPA is in bidirectional mode.
Internet-facing ALBs and NLBs need the internet gateway, so their subnets must be excluded. If you exclude only some of a load balancer's subnets, it can still receive public traffic there and route it privately to targets in non-excluded subnets.
W: A=Bidirectional exclusions for the ALB subnets: the ALB again accepts internet traffic in both zones, while targets in non-excluded private subnets stay blocked from direct internet access.
X: B=Exclude one subnet: the ALB would receive traffic only in the excluded zone, losing the second zone's availability without making targets any safer.
C=Bidirectional mode: it is stricter than ingress-only and would also break the NAT gateway outbound traffic; it does not allow inbound load balancer traffic.
D=Egress-only exclusion: it only allows outbound traffic and only in bidirectional mode, so internet clients still could not reach the ALB.
T: Under VPC Block Public Access, exclude every subnet of an internet-facing load balancer with a bidirectional exclusion and keep targets in non-excluded subnets.

@ SOA-C03 D5 T5.2 advanced use-case
S: A company has 150 VPCs in 40 accounts in one Region. Each VPC must resolve three private hosted zones, use the same Resolver forwarding rules to on-premises DNS, and apply the same DNS Firewall rule groups. Today engineers associate each zone, rule and rule group with every new VPC by hand, and new VPCs are often missed. The team wants one place to manage these settings with the LEAST operational overhead. What should the CloudOps engineer do?
A: Add the zones, forwarding rules and rule groups to a Route 53 Profile, share it with AWS RAM, and associate it with each VPC
B: Share the Resolver rules and DNS Firewall rule groups with AWS RAM, and authorize each private hosted zone for each VPC by account
C: Build a central DNS VPC with Resolver inbound endpoints, and set every VPC's DHCP options set to use those endpoint IP addresses
D: Use AWS Firewall Manager DNS Firewall policies for the rule groups, and let each team associate the zones and rules on its own
K: A
G: ## Route 53 Profiles
A **Route 53 Profile** groups DNS settings and applies them to many VPCs at once:
- private hosted zones
- Resolver rules (forwarding and system)
- DNS Firewall rule groups
- VPC endpoints, plus settings such as reverse DNS lookup and DNSSEC validation
You share a Profile with other accounts in the same Region through **AWS RAM** and associate it with their VPCs (up to two Profiles per VPC, ordered by priority). When you change the Profile, the change **propagates to every associated VPC**.
## Without Profiles
Each zone must be associated with each VPC (cross-account associations need authorization), each rule shared and associated separately, and each rule group associated separately.
W: A=Route 53 Profile shared with RAM: one object carries all three kinds of DNS settings, and associating it with a VPC applies them all, with later edits propagating automatically.
X: B=RAM sharing plus per-VPC authorization: it still requires a separate association per zone, rule and rule group for each new VPC, which is the manual work causing misses.
C=Central inbound endpoints via DHCP: it adds endpoint costs and routes every query across VPCs, and DNS Firewall rule groups associated with the central VPC do not filter traffic resolved elsewhere in the same way.
D=Firewall Manager for rule groups only: it centralizes DNS Firewall but leaves the hosted zones and forwarding rules to manual association.
T: To apply the same private zones, Resolver rules and DNS Firewall rule groups to many VPCs across accounts, use a Route 53 Profile shared with AWS RAM.

@ SOA-C03 D5 T5.2 advanced use-case
S: A web application uses CloudFront in front of an internet-facing Application Load Balancer. Security found that clients can bypass CloudFront by calling the ALB directly, and now requires that the ALB have no public exposure at all, while CloudFront keeps serving the same paths. The team wants the LEAST operational overhead and no changes to the application code. What should the CloudOps engineer do?
A: Make the ALB internal in private subnets, create a CloudFront VPC origin for it, and allow CloudFront origin-facing traffic in its security group
B: Keep the internet-facing ALB, allow only the CloudFront managed prefix list in its security group, and require a secret custom header in a listener rule
C: Keep the internet-facing ALB, and attach an AWS WAF web ACL that blocks requests whose source IP is not one of the CloudFront edge address ranges
D: Replace the ALB with an API Gateway private integration through a VPC link, and point CloudFront at the API Gateway regional endpoint instead
K: A
G: ## CloudFront VPC origins
With **VPC origins**, CloudFront delivers content from an **ALB, NLB or EC2 instance in a private subnet**. CloudFront reaches it through a service-managed elastic network interface over a private connection, so the origin needs **no public IP and no internet-facing scheme**, and CloudFront becomes the single entry point.
Requirements and details:
- The VPC must have an internet gateway attached (it is not used for routing to the origin), and the private subnet needs a free IP address.
- The origin's security group must allow CloudFront: either the managed prefix list `com.amazonaws.global.cloudfront.origin-facing`, or the service-managed security group `CloudFront-VPCOrigins-Service-SG` for a tighter rule.
- NLBs used as VPC origins need a security group and cannot use TLS listeners.
W: A=Internal ALB as a VPC origin: the ALB loses all public exposure, CloudFront reaches it privately, and nothing in the application changes.
X: B=Prefix list plus custom header: it blocks most direct access but the ALB is still internet-facing, so it fails the no-public-exposure rule, and the header secret must be rotated.
C=WAF IP filtering: the ALB stays public, and maintaining CloudFront ranges in a web ACL is ongoing work that the managed prefix list was meant to replace.
D=API Gateway in the middle: it adds a new service, new routing and likely application changes, which is more overhead than moving the ALB behind a VPC origin.
T: To remove an origin's public exposure behind CloudFront, make it internal and use a CloudFront VPC origin.
V: Amazon CloudFront, Elastic Load Balancing, Amazon VPC

@ SOA-C03 D5 T5.2 advanced use-case
S: A video platform serves HLS segments through CloudFront from an S3 bucket in us-east-1, with a replica bucket in us-west-2. During a recent S3 issue, viewers saw errors for several minutes. The team wants CloudFront to send GET requests to the replica automatically when the primary returns 5xx errors or does not respond, and to give up on the primary within a few seconds instead of the default 30. Which TWO actions should the CloudOps engineer take? (Select TWO)
A: Create an origin group with the us-east-1 bucket as primary and the us-west-2 bucket as secondary, failing over on 500, 502, 503 and 504
B: Lower the primary origin's connection timeout and connection attempts, so CloudFront abandons an unresponsive primary within seconds
C: Create a Route 53 failover record for the origin domain name with health checks on both buckets, and set the record's TTL to 60 seconds
D: Turn on Origin Shield in us-east-1, so the regional caching layer keeps serving segments to viewers while the primary bucket is unavailable
E: Add a Lambda@Edge viewer request function that rewrites every request to the us-west-2 bucket whenever an alarm marks us-east-1 unhealthy
K: A,B
G: ## Origin failover
An **origin group** has a primary and a secondary origin. CloudFront fails over to the secondary when the primary is unavailable or returns one of the status codes you choose (400, 403, 404, 416, 429, 500, 502, 503, 504). Failover applies only to **GET, HEAD and OPTIONS** requests (OPTIONS only if it is a cached method).
## How fast CloudFront gives up
By default CloudFront tries the primary for up to **30 seconds**: **3 connection attempts** of **10 seconds** each. You can lower the **connection timeout** (1 to 10 seconds) and **connection attempts** (1 to 3); for custom origins you can also lower the response timeout. For example, 2 seconds and 1 attempt fails over in about 2 seconds.
W: A=Origin group on 5xx codes: CloudFront automatically retries failed GET requests against the replica bucket per request, with no DNS changes.
B=Shorter timeout and fewer attempts: an unresponsive primary is abandoned after a few seconds instead of the default 30.
X: C=Route 53 failover: it depends on health check intervals and DNS caching, so failover takes minutes, and the S3 origin domain names are AWS-owned, not records the team controls.
D=Origin Shield: it adds a caching layer that improves hit ratio, but cache misses still go to the failing primary.
E=Lambda@Edge rewrite on an alarm: it is custom code driven by alarm latency, and the per-request origin group already does this.
T: For per-request origin failover in CloudFront, use an origin group with failover status codes and tune connection timeout and attempts.

@ SOA-C03 D5 T5.3 advanced use-case
S: A company has 60 VPCs across many accounts. Compliance requires continuous proof that no network path exists from any internet gateway to any network interface in subnets tagged Tier=database, except through approved ALBs, and the evidence must show the full path for any violation it finds in a VPC. The team wants the LEAST operational effort. Which approach should the CloudOps engineer use?
A: Create a Network Access Analyzer scope for paths from internet gateways to the database interfaces, excluding approved ALBs, and analyze it on a schedule
B: Run Reachability Analyzer between the internet gateway and each database instance in every VPC whenever any route table or security group in that VPC changes
C: Enable VPC Flow Logs on every database subnet and alarm on any accepted inbound record whose source address is outside the private ranges
D: Use AWS Config managed rules that check for security groups with unrestricted inbound access attached to the database instances
K: A
G: ## Two analyzers, two questions
- **Reachability Analyzer** answers "**can traffic get from A to B?**" for one source and one destination at a time, with hop-by-hop detail.
- **Network Access Analyzer** answers "**does any path exist that violates my requirements?**" across many resources. You define a **Network Access Scope** with:
  - `MatchPaths`: paths you consider violations, for example from internet gateways to network interfaces with the tag `Tier=database`
  - `ExcludePaths`: legitimate exceptions, for example paths through approved load balancers
  An analysis returns findings that show each unintended path in detail.
Both analyze configuration (route tables, security groups, NACLs, gateways, load balancers); neither sends packets.
W: A=Network Access Analyzer scope: one scope covers all matching interfaces, excludes the approved ALB paths, and reports any violating path with its details.
X: B=Reachability Analyzer per pair: it checks one source and destination per analysis, so covering every database instance in 60 VPCs after each change is heavy manual work.
C=Flow logs and alarms: they show traffic that already happened, not whether a path exists, so they cannot prove that no path is open.
D=Config rules on security groups: they look at one control in isolation and miss paths created by routes, NACLs or other components.
T: To prove no unintended network paths exist across many resources, use Network Access Analyzer scopes; use Reachability Analyzer for one source and destination.
V: Amazon VPC, Network Access Analyzer

@ SOA-C03 D5 T5.1 advanced use-case
S: Dev, test and prod VPCs, plus a shared-services VPC, attach to one transit gateway that today uses a single default route table, so dev can reach prod. Every application VPC must reach shared services, and shared services must reach all of them, but dev and test must never reach prod. New attachments are added often. Which TWO actions should the CloudOps engineer take? (Select TWO)
A: Associate the dev, test and prod attachments with one route table that has only a propagation from the shared-services attachment
B: Associate the shared-services attachment with a second route table that has propagations from the dev, test and prod attachments
C: Keep the default route table for all attachments and add blackhole routes for the prod CIDR on the dev and test attachments
D: Add network ACL rules in the prod VPC subnets that deny the dev and test CIDR ranges, and keep the single default route table
E: Replace the transit gateway with VPC peering between each application VPC and the shared-services VPC, and none between applications
K: A,B
G: ## How transit gateway routing works
- Each attachment is **associated** with exactly one transit gateway route table. That table decides where traffic **from** that attachment can go.
- An attachment can **propagate** its routes into one or more route tables, which makes it a **destination** for traffic from attachments associated with those tables.
## Segmentation pattern
- **Application route table**: associate dev, test and prod; propagate only shared services. Application VPCs can reach shared services but have no routes to each other.
- **Shared-services route table**: associate shared services; propagate dev, test and prod. Shared services can reach every application VPC.
New application attachments just need the same association and propagation, so the design scales without per-CIDR rules.
W: A=Application route table: dev, test and prod learn only the shared-services routes, so they cannot reach one another.
B=Shared-services route table: shared services learn every application VPC's routes, so it can reach all of them.
X: C=Blackhole routes in the default table: a single table is shared by every attachment, so a blackhole for prod would also cut shared services off from prod, and each new VPC needs more static routes.
D=NACLs in prod: it can block traffic, but routing still allows it, NACL rule limits are low, and each new CIDR means more rules.
E=VPC peering: it can isolate traffic, but it abandons the transit gateway, needs a peering connection per VPC, and scales poorly as attachments are added.
T: Segment transit gateway traffic with separate route tables: associations decide where traffic comes from, propagations decide where it can go.
V: AWS Transit Gateway, Amazon VPC
