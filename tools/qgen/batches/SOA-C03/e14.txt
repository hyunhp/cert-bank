G: ## Distributed tracing with X-Ray
**AWS X-Ray** follows one request through several services.
- Each service records a **segment**; calls it makes, such as a DynamoDB `GetItem`, become **subsegments** with their own timing.
- A **trace ID** passed in the `X-Amzn-Trace-Id` header ties the pieces together.
- The **trace map** (service map) shows each node with average latency and error rate, and single traces show a timeline of where time was spent.
To set it up, enable active tracing on the API Gateway stage and the Lambda function, and instrument the AWS SDK in the function (X-Ray SDK or OpenTelemetry) so DynamoDB calls appear. Traces are viewed in the CloudWatch console.
Example: a 900 ms request shows 20 ms in API Gateway, 80 ms of Lambda code, and 780 ms in a DynamoDB `Scan` subsegment, which points directly to the fix.
Note: the AWS X-Ray SDKs and the X-Ray daemon entered maintenance mode on 2026-02-25 (security fixes only), and AWS recommends OpenTelemetry (AWS Distro for OpenTelemetry) for new instrumentation. X-Ray itself, active tracing and the trace console are unchanged, and exam questions may still name the X-Ray SDK.
W: AWS X-Ray: it traces a request across API Gateway, Lambda and DynamoDB and breaks the latency into segments, showing which hop is slow.
X: B=AWS Batch: it schedules and runs batch computing jobs; it provides no request tracing.
C=AWS Config: it records resource configurations and compliance, not per-request timing.
D=Amazon Macie: it discovers sensitive data such as PII in S3 and has nothing to do with latency.
T: Finding which service in a request chain adds latency is distributed tracing, which is AWS X-Ray.
