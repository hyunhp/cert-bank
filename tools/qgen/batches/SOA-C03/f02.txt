# SOA-C03 fixes: Performance Insights reached end of life on 2026-07-31 (now CloudWatch Database Insights)

@ SOA-C03 D1 T1.3 advanced use-case
S: A database administrator notices intermittent slow query performance on an Amazon RDS for PostgreSQL instance but cannot determine which specific SQL statements or wait events are driving the load during those periods. Which tool should be used to diagnose this without installing any additional software on the instance?
A: AWS X-Ray traces of the application's database calls
B: CloudWatch Database Insights (formerly Performance Insights)
C: VPC Flow Logs for the DB instance's network interface
D: Basic Amazon CloudWatch RDS metrics such as CPU and IOPS only
K: B
G: ## Performance Insights is now Database Insights
Amazon RDS Performance Insights reached **end of life on July 31, 2026**, and AWS migrated its users to **Amazon CloudWatch Database Insights**. The default **Standard mode** keeps the Performance Insights features (DB load, top SQL, wait events); the **Advanced mode** adds longer included retention, per-query statistics, lock and execution plan analysis.
## Database load and wait events
Database Insights measures **DB load** as average active sessions (AAS): how many sessions are working or waiting at each moment. You can slice load by:
- **Wait events** (for PostgreSQL, for example `IO:DataFileRead`, `Lock:transactionid`, `LWLock` types): what sessions are waiting for.
- **Top SQL**: which statements contribute most load.
- Hosts, users and databases.
It is turned on for the RDS instance with no software to install. Zooming into the slow periods shows, for example, one query spending its time on `IO:DataFileRead`, which suggests a missing index.
W: CloudWatch Database Insights: it shows which SQL statements and wait events drive database load at any moment, which directly answers the question for intermittent slow periods, without installing agents.
X: A=AWS X-Ray: it traces requests through application code and can show that a database call was slow, but not the database's internal wait events or top SQL across all sessions.
C=VPC Flow Logs: they record network connection metadata (IPs, ports, bytes) and contain no SQL text or database wait information.
D=Basic CloudWatch RDS metrics only: CPU, IOPS and connections show that the instance is busy but not which statements or waits are responsible.
T: To find which queries and waits cause database slowness, use CloudWatch Database Insights (the successor of Performance Insights); host metrics only show that the database is busy.
V: Amazon CloudWatch Database Insights, Amazon RDS

@ SOA-C03 D1 T1.3 advanced troubleshooting
S: An RDS for PostgreSQL instance shows high CPU during business hours. The DBA needs to see which SQL statements and wait events contribute most to database load. Which tool fits BEST?
A: The CloudWatch CPUUtilization metric for the DB instance.
B: RDS Enhanced Monitoring of OS processes on the DB host.
C: AWS Trusted Advisor performance and cost optimization checks.
D: CloudWatch Database Insights (formerly Performance Insights).
K: D
G: ## Measuring database load
Amazon RDS Performance Insights reached **end of life on July 31, 2026**; AWS migrated its users to **Amazon CloudWatch Database Insights**, whose default **Standard mode** keeps the same DB load, top SQL and wait event analysis (the **Advanced mode** adds per-query statistics, execution plans and fleet views).
Database Insights measures database load as **average active sessions (AAS)**: how many sessions are running or waiting at each moment. The load can be sliced by dimension:
- **SQL statements**: which queries contribute most of the load.
- **Wait events**: what sessions are waiting on, for example CPU, I/O (`IO:DataFileRead`), or locks (`Lock:transactionid`).
- Users, hosts and databases.
Example: load exceeds the vCPU count at 10:00, and the top SQL is one query mostly waiting on CPU; it probably needs an index.
## Compared with other tools
- The `CPUUtilization` metric tells you CPU is high, not why.
- **Enhanced Monitoring** collects OS metrics from an agent on the host, including a process list, at up to one-second granularity, but not per-SQL load.
W: CloudWatch Database Insights: it attributes database load to specific SQL statements and wait events, which is exactly what the DBA asked for.
X: A=CPUUtilization metric: it confirms the CPU is high but gives no breakdown by query or wait event.
B=Enhanced Monitoring: it shows OS-level metrics and processes on the DB host, not which SQL statements and wait events drive database load.
C=Trusted Advisor: it runs account-level best-practice checks (cost, security, limits, some idle or underused RDS findings) and has no query-level performance analysis.
T: CPU metrics and Enhanced Monitoring show that the database is busy; Database Insights (formerly Performance Insights) shows which SQL and waits make it busy.
V: Amazon CloudWatch Database Insights, Amazon RDS

@ SOA-C03 D1 T1.3 applied use-case
S: An RDS for MySQL database is slow, and the team wants to identify which SQL statements consume the most database load. Which feature helps?
A: CloudWatch Database Insights (formerly Performance Insights)
B: RDS Multi-AZ deployment with a synchronous standby instance
C: RDS automated backups with point-in-time recovery enabled
D: The RDS read replica lag (ReplicaLag) metric in CloudWatch
K: A
G: ## Finding what loads a database
The main question for a slow database is "what is the database busy with?". Amazon RDS Performance Insights answered it until its **end of life on July 31, 2026**; AWS migrated its users to **Amazon CloudWatch Database Insights**, which answers it with the same **DB load** metric: the average number of active sessions, broken down by dimension.
- **Top SQL** shows which statements contribute the most load.
- **Wait events** show what those sessions wait on, such as CPU, I/O or locks.
- You can also slice load by host, user or database.
The default **Standard mode** keeps these Performance Insights features with 7 days of free retention; the **Advanced mode** adds 1-24 months of included retention, per-query statistics and deeper analysis.
Example: DB load averages 12 while the instance has 4 vCPUs; Top SQL shows one `SELECT` without an index causing most of it, waiting on I/O. That points to adding an index rather than a bigger instance.
W: CloudWatch Database Insights: it breaks database load down by SQL statement and wait event, which directly identifies the queries consuming the most load.
X: B=Multi-AZ deployment: Multi-AZ adds a standby for failover; it does not analyze queries, and the standby of a Multi-AZ instance deployment does not serve reads.
C=Automated backups: backups provide point-in-time recovery; they give no insight into which SQL uses resources.
D=Read replica lag metric: `ReplicaLag` shows how far a replica is behind its source; it says nothing about which statements load the primary.
T: To see which SQL drives database load, use CloudWatch Database Insights (the successor of Performance Insights); availability and backup features do not diagnose performance.
V: Amazon CloudWatch Database Insights, Amazon RDS
I: Q002659
