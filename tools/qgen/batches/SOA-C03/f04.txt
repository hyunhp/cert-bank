@ SOA-C03 D4 T4.2 advanced use-case
S: A team wants to know which EC2 instances have critical CVEs AND are reachable from the internet, to fix those first. Which service fits?
A: Amazon GuardDuty Runtime Monitoring findings
B: VPC Reachability Analyzer path analyses
C: Amazon Inspector EC2 scanning findings
D: AWS Trusted Advisor security checks
K: C
G: ## Prioritizing vulnerabilities by exposure
**Amazon Inspector** continuously scans EC2 instances (and container images and Lambda functions) for software vulnerabilities (CVEs) and, for EC2, for **network reachability**: open paths from outside the VPC to ports on the instance, based on security groups, network ACLs, route tables and gateways.
Inspector combines these into an **Inspector score** for each finding. A critical, network-exploitable CVE on an instance with an open path from the internet is scored higher than the same CVE on an isolated instance.
- Example: two instances share a critical OpenSSL CVE; only the one behind a security group open to `0.0.0.0/0` on port 443 is internet-reachable, so it rises to the top of the list.
- Findings can be filtered by severity and by network exposure to build a fix-first list.
W: Amazon Inspector EC2 scanning: it finds critical CVEs on the instances and, for EC2, evaluates network reachability from the internet, raising the Inspector score of exposed vulnerable instances so they are fixed first.
X: A=GuardDuty Runtime Monitoring: GuardDuty detects threats from activity such as runtime events, flow logs, DNS logs and CloudTrail; it does not inventory installed software or report CVEs.
B=Reachability Analyzer: it checks whether a path exists between a source and a destination you name, but it knows nothing about installed software, so it cannot say which reachable instances carry critical CVEs.
D=Trusted Advisor security checks: they can flag security groups with unrestricted ports, but there is no CVE scanning, so they cannot tell which exposed instances are also vulnerable.
T: Vulnerability plus exposure in one score is Inspector; GuardDuty detects attacks and Trusted Advisor checks configuration, neither lists CVEs.
V: Amazon Inspector

@ SOA-C03 D2 T2.3 advanced use-case
S: Backups of EC2, EBS, and RDS must be copied to another Region and another account, and must be protected so that no one, including administrators, can delete them before the retention period ends. Which solution fits BEST?
A: EBS snapshots tagged do-not-delete and copied by Data Lifecycle Manager rules
B: Backup plan copies to another Region and account in a compliance-mode Vault Lock vault
C: S3 Versioning plus Cross-Region Replication to a bucket in a separate account
D: Manual snapshots copied to another Region and account by a nightly Lambda script
K: B
G: ## AWS Backup building blocks
- A **backup plan** defines schedules, retention and **copy rules** for resources such as EC2, EBS and RDS, selected by tags or ARNs.
- Copy rules can send each recovery point to a vault in another Region and, with AWS Organizations, to a vault in another account.
- A **backup vault** stores recovery points and has its own access policy and encryption key.
## Vault Lock
**AWS Backup Vault Lock** in compliance mode enforces minimum and maximum retention on a vault. After the grace (cooling-off) period ends, the lock cannot be removed and recovery points cannot be deleted early by anyone, including the root user and administrators. Governance mode can still be changed by users with sufficient permissions.
Example: production account backs up nightly, copies to a locked vault in a separate backup account in another Region with 35-day minimum retention. Even a compromised production admin cannot delete those copies.
W: Backup plan copies to a locked vault: AWS Backup copy rules handle the cross-Region and cross-account copies for EC2, EBS and RDS, and Vault Lock in compliance mode prevents anyone, including administrators and the root user, from deleting recovery points before retention ends.
X: A=Tagged snapshots copied by Data Lifecycle Manager: a tag is just metadata, so anyone with delete permissions can still delete the snapshots and their copies; it also covers only EBS-backed resources, not RDS.
C=S3 Versioning and replication: they protect objects in S3 buckets, not EC2, EBS or RDS backups, and privileged users can still delete object versions.
D=Nightly copy script: it can copy snapshots, but it is fragile to maintain and provides no immutability; an administrator can still delete the copies.
T: For cross-account, cross-Region backups nobody can delete early, use AWS Backup copy rules into a compliance-mode Vault Lock vault.
V: AWS Backup

@ SOA-C03 D1 T1.3 applied use-case
S: A team wants recommendations on whether its EC2 instances are over- or under-provisioned based on utilization. Which service provides this?
A: AWS Artifact reports
B: AWS Compute Optimizer
C: Amazon Inspector scans
D: AWS Backup Audit Manager
K: B
G: ## Right-sizing with AWS Compute Optimizer
Compute Optimizer uses machine learning on CloudWatch utilization history (CPU, network, disk and, if the CloudWatch agent publishes it, memory) to judge whether each resource is sized well.
- Each EC2 instance is classified as **Under-provisioned**, **Over-provisioned** or **Optimized**.
- It recommends alternative instance types with projected utilization, performance risk and estimated price difference.
- It also covers Auto Scaling groups, EBS volumes, Lambda functions, ECS services on Fargate and other resources.
Example: an `m5.2xlarge` that never exceeds 15% CPU might be flagged over-provisioned with an `m5.large` or Graviton option recommended.
You opt in at the account or organization level, and it needs a minimum amount of metric history (at least about 30 hours for EC2) before recommendations appear.
W: AWS Compute Optimizer: it analyzes actual utilization and recommends instance types and sizes, labeling instances as under- or over-provisioned.
X: A=AWS Artifact reports: Artifact is a portal for downloading AWS compliance reports and agreements; it knows nothing about your instances' utilization.
C=Inspector scans: Inspector scans EC2 instances, container images and Lambda functions for software vulnerabilities and exposure, not for sizing.
D=Backup Audit Manager: it audits whether backups comply with your backup policies; it does not evaluate performance or capacity.
T: Right-sizing recommendations based on utilization come from Compute Optimizer; Inspector covers vulnerabilities, not size.
V: AWS Compute Optimizer

@ SOA-C03 D3 T3.2 advanced use-case
S: An engineer must restart a service on 300 instances tagged Role=web, at most 10% at a time, and stop if more than 5 instances fail. Which approach fits BEST?
A: An SSH loop script that works through the hosts 30 at a time
B: Edit user data on the tagged instances, then stop and start them
C: Systems Manager Run Command with concurrency and error limits
D: Reboot the tagged instances from the EC2 console in small groups
K: C
G: ## Run Command at fleet scale
AWS Systems Manager Run Command runs an SSM document, for example `AWS-RunShellScript` with `systemctl restart nginx`, on managed instances without SSH.
- **Targets**: choose instances by tag (`tag:Role` = `web`), resource group or instance IDs.
- **Concurrency** (`MaxConcurrency`): a number or percentage of targets running at once, for example `10%` = 30 of 300.
- **Error threshold** (`MaxErrors`): with `5`, Systems Manager stops sending the command to new targets once the sixth failure is reported; invocations already running finish.
Output can go to S3 or CloudWatch Logs, the command history keeps per-instance status, and the `SendCommand` API call is recorded in CloudTrail.
W: Run Command with rate controls: targeting the `Role=web` tag with a maximum concurrency of 10% and a maximum error count of 5 implements the rolling restart and the automatic stop exactly, with no SSH access and a central record of every invocation.
X: A=SSH loop in batches: it needs open SSH access and key management, its batching and failure handling must be written and maintained by hand, and it leaves no central record.
B=User data and stop/start: user data runs at instance launch, not as an on-demand command on running instances, and stopping instances to apply it is far more disruptive than restarting one service, with no failure threshold.
D=Console reboots in groups: it restarts whole instances rather than one service, depends on someone clicking through the groups and has no automatic stop after a number of failures.
T: For controlled, auditable commands across many instances, use Run Command with tag targeting, max concurrency and max errors.
V: AWS Systems Manager Run Command

@ SOA-C03 D4 T4.2 applied use-case
S: An internet-facing Application Load Balancer created several years ago still uses the ELBSecurityPolicy-2016-08 security policy on its HTTPS listener. An audit requires that clients can connect only with TLS 1.2 or TLS 1.3 and strong ciphers. What should the CloudOps engineer change?
A: Add an AWS WAF rule to the web ACL on the ALB that blocks every request whose TLS protocol version is lower than 1.2 before it reaches the targets
B: Add a listener rule that redirects every HTTP request on port 80 to HTTPS on port 443 so that all clients are forced to use a secure TLS connection
C: Replace the ACM certificate on the listener with a new certificate that uses a 4096-bit RSA key so that older TLS versions are no longer negotiated
D: Switch the listener to ELBSecurityPolicy-TLS13-1-2-2021-06 so the handshake offers only newer protocol versions and modern ciphers
K: D
G: ## What an ELB security policy is
A security policy is a named set of TLS protocol versions and cipher suites that an HTTPS (ALB) or TLS (NLB) listener offers during the handshake.
## Old versus current policies
- `ELBSecurityPolicy-2016-08`: allows TLS 1.0, 1.1 and 1.2. It was the default for many years.
- `ELBSecurityPolicy-TLS13-1-2-2021-06`: TLS 1.2 and 1.3 with modern ciphers; a recommended general-purpose policy.
- `ELBSecurityPolicy-TLS13-1-2-Res-2021-06`: a more restricted cipher set. FIPS variants exist for workloads that need FIPS-validated cryptography.
## Checking the result
Change it with `aws elbv2 modify-listener --ssl-policy ...`. Test with `openssl s_client -tls1_1 -connect host:443`; the handshake should now fail. Before switching, check ALB access logs, which record the TLS protocol of each request, to find clients that still use TLS 1.0 or 1.1.
W: Newer listener security policy: the ALB security policy decides which TLS protocol versions and ciphers the listener negotiates. `ELBSecurityPolicy-2016-08` still allows TLS 1.0 and 1.1; switching to `ELBSecurityPolicy-TLS13-1-2-2021-06` (or a stricter TLS13 variant) limits handshakes to TLS 1.2 and 1.3 with modern ciphers, with no downtime.
X: A=WAF rule on TLS version: WAF inspects HTTP requests only after the TLS handshake has completed, so clients could still negotiate TLS 1.0 or 1.1 with the listener. Only the security policy controls which versions are offered.
B=HTTP to HTTPS redirect: this moves plain HTTP clients to HTTPS but does not change which TLS versions the HTTPS listener negotiates.
C=Bigger certificate key: the key size affects the certificate, not which protocol versions the listener allows, so TLS 1.0 and 1.1 handshakes would still succeed.
T: TLS versions and ciphers on an ALB are set by the listener's security policy; certificates, redirects and WAF do not control the handshake.
V: Elastic Load Balancing, AWS Certificate Manager

@ SOA-C03 D2 T2.1 applied comparison
S: An API fleet behind an ALB is limited by calls to a downstream service, not by CPU. Load tests show each instance handles about 500 requests per minute before latency rises, while CPU stays under 30%. A CPU-based target tracking policy therefore never scales out. Which policy fits best?
A: Target tracking on average NetworkIn per instance, with a target taken from the inbound bytes seen in load tests
B: Target tracking on ALBRequestCountPerTarget, set a little under the measured per-instance limit
C: Scheduled scaling that adds instances during business hours and removes them in the evening each weekday
D: Target tracking on average CPUUtilization with the target value lowered from 50 percent to 20 percent
K: B
G: ## Choosing a scaling metric
Target tracking keeps one metric near a target value. It only works well when the metric grows in proportion to load **and** reflects what actually saturates the instance.
## Request-bound workloads
Some services spend their time waiting on a database or downstream API. Their CPU stays low while latency climbs, so CPU never tells Auto Scaling that more capacity is needed.
## ALBRequestCountPerTarget
- Predefined metric for EC2 Auto Scaling target tracking, tied to one ALB target group.
- Value = requests to the target group per minute divided by healthy targets.
- Example: capacity found in testing is 500 per instance; set the target to about 400 to keep headroom. At 4,000 requests per minute the group aims for 10 instances.
Other load-proportional choices are SQS backlog per instance for queue workers or a custom metric such as active connections.
W: ALBRequestCountPerTarget: this predefined metric divides the target group's request count by the number of healthy targets, which is exactly the per-instance limit found in testing. With a target of about 400, target tracking adds instances when the per-target count rises and removes them when it falls.
X: A=Target tracking on NetworkIn: inbound bytes depend on request size, not on request count, so the same byte rate can mean very different numbers of downstream calls. It tracks the real limit poorly.
C=Scheduled scaling: it follows the clock, not demand, so load outside the expected pattern still overloads the fleet.
D=Lower CPU target: CPU is only loosely related to this workload's real bottleneck, so a 20% target scales at the wrong times, too early at some loads and too late at others.
T: Scale on the metric that represents the bottleneck; for request-bound web fleets that is requests per target, not CPU.
V: Amazon EC2 Auto Scaling, Elastic Load Balancing

@ SOA-C03 D5 T5.3 advanced troubleshooting
S: An ALB returns intermittent HTTP 502 errors. Target logs show the application server closes idle keep-alive connections after 5 seconds, while the ALB idle timeout is 60 seconds. What should the engineer do?
A: Turn on ALB access logs to capture every 502 response.
B: Register more targets so each one holds fewer connections.
C: Have the web server keep sockets open for over a minute.
D: Shorten the target group's health check interval to 5 seconds.
K: C
G: ## How an ALB reuses backend connections
An Application Load Balancer keeps TCP keep-alive connections open to its targets and reuses them for later requests. Two timers matter:
- The **ALB idle timeout** (default `60` seconds) says how long the ALB keeps an idle connection before closing it.
- The **application keep-alive timeout** (set in the web server, for example Node.js `keepAliveTimeout` or Apache `KeepAliveTimeout`) says how long the target keeps it.
## The race that causes 502s
Here the target closes idle connections after 5 seconds, but the ALB still considers them usable for 60 seconds. When the ALB sends a new request on a connection the target just closed, the target resets it and the ALB returns **HTTP 502 Bad Gateway**. The errors are intermittent because they only hit requests that land on a connection idle for more than 5 seconds.
The fix is to make the target keep connections longer than the ALB does, for example a keep-alive of 65 seconds, so the ALB is always the side that closes first.
W: Server keep-alive above 60 seconds: when the application keeps idle connections longer than the ALB idle timeout (for example 65 seconds), the ALB never reuses a connection the target has already closed, which removes the reset-induced 502s.
X: A=Access logs: access logs record the 502s and their target status, which helps confirm the cause, but they do not change either timeout, so the errors continue.
B=More registered targets: each additional target has the same 5-second keep-alive, so connections still go stale and the ALB still reuses closed ones.
D=Shorter health check interval: health checks decide whether a target is healthy; the targets are healthy here, and faster checks do not affect how idle connections are closed.
T: When the backend closes idle connections before the ALB does, the ALB reuses dead connections and returns 502, so set the backend keep-alive above the ALB idle timeout.
V: Application Load Balancer
