@ SOA-C03 D1 T1.1 applied use-case
S: A team running workloads on both Amazon ECS and Amazon EKS wants to collect CPU and memory performance metrics at the cluster, service, task, and container level, viewable in automatically generated dashboards. Which feature should they enable?
A: AWS Trusted Advisor performance checks
B: AWS X-Ray tracing with a service map
C: VPC Flow Logs published to CloudWatch
D: CloudWatch Container Insights
K: D
G: ## CloudWatch Container Insights
Container Insights collects, aggregates and summarizes performance data from containerized workloads on Amazon ECS, Amazon EKS and Kubernetes on EC2.
- It reports CPU, memory, network and storage at several levels: cluster, service, task and container on ECS; cluster, node, namespace, pod and container on EKS.
- Data is sent as structured performance log events (embedded metric format) and turned into CloudWatch metrics, with ready-made automatic dashboards in the CloudWatch console.
- The enhanced observability mode adds finer-grained metrics and curated views.
## How you turn it on
On ECS, enable it at the account or cluster level. On EKS, install the Amazon CloudWatch Observability add-on, which deploys the CloudWatch agent as a DaemonSet on the nodes.
W: CloudWatch Container Insights: it is built for ECS and EKS and provides CPU and memory metrics at cluster, service, task and container level along with automatically generated dashboards.
X: A=Trusted Advisor performance checks: they flag best-practice issues such as over-utilized instances or service limits; they do not collect per-container performance metrics.
B=X-Ray tracing with a service map: it follows individual requests across services to show latency and errors, not resource utilization of clusters, tasks or containers.
C=VPC Flow Logs in CloudWatch: they record IP traffic metadata for network interfaces (source, destination, ports, accept or reject), not CPU or memory usage, even when delivered to CloudWatch Logs.
T: Container resource metrics with prebuilt dashboards for ECS and EKS come from Container Insights, not from tracing, advisory checks or network logs.
V: Amazon CloudWatch, Amazon ECS, Amazon EKS

@ SOA-C03 D1 T1.3 applied comparison
S: A company is migrating a line-of-business application that requires an SMB share with NTFS access control lists and integration with Microsoft Active Directory. Which AWS storage service is the BEST fit?
A: Amazon EFS with access points
B: Amazon FSx for Windows File Server
C: Amazon FSx for Lustre with an S3 link
D: Amazon S3 with S3 Access Points
K: B
G: ## Picking a file service by protocol
- **Amazon FSx for Windows File Server** is a fully managed Windows Server file system. It serves shares over **SMB**, stores data on NTFS with Windows **ACLs**, and joins your **Microsoft Active Directory** (AWS Managed Microsoft AD or self-managed), so users and groups authenticate as they do on-premises. It also supports DFS namespaces, shadow copies and Multi-AZ deployments.
- **Amazon EFS** provides NFS file systems for Linux clients and POSIX permissions.
- **Amazon FSx for Lustre** is a high-performance parallel file system for Linux compute clusters.
- **Amazon S3** is object storage accessed through an HTTP API, not a mounted file share.
## Example
A lift-and-shift of an app that maps `\\fs01\finance` with AD group permissions maps directly to an FSx for Windows share with the same ACLs.
W: Amazon FSx for Windows File Server: it natively provides SMB shares, NTFS ACLs and Active Directory integration, which is what the application expects.
X: A=Amazon EFS with access points: EFS uses NFS and POSIX permissions; access points enforce a POSIX user and root directory, but there is still no SMB access or NTFS ACL support.
C=FSx for Lustre linked to S3: it is built for high-throughput Linux HPC and ML workloads using the Lustre client; linking it to an S3 bucket does not add SMB shares or Windows ACLs.
D=Amazon S3 with Access Points: it is object storage governed by IAM and access point policies; applications cannot mount it as an SMB share with NTFS permissions.
T: SMB plus NTFS ACLs plus Active Directory points to FSx for Windows File Server; EFS and Lustre are for Linux clients.
V: Amazon FSx for Windows File Server, Amazon EFS, Amazon S3

@ SOA-C03 D5 T5.3 advanced troubleshooting
S: One instance in a public subnet with a public IPv4 address can't reach the internet, while others in the same subnet can. The subnet routes to an IGW. What should be checked first?
A: Whether a new VPC peering connection replaced the default route
B: Whether Shield Advanced protections are dropping its outbound traffic
C: Whether an S3 gateway endpoint route is capturing its internet traffic
D: Its security groups, host firewall, and operating system routing table
K: D
G: ## Subnet-wide versus instance-specific causes
Internet access from a public subnet depends on several layers. Some apply to the whole subnet, others to a single instance:
- **Subnet-wide**: the subnet route table (`0.0.0.0/0` to an internet gateway) and the network ACL associated with the subnet.
- **Per instance**: the security groups attached to its network interface, the public IPv4 address mapped to that interface, and everything inside the OS (host firewall such as `iptables`/`firewalld` or Windows Firewall, OS routing table, proxy settings).
## Troubleshoot by comparison
When other instances in the same subnet reach the internet, the route table and the NACL are already proven to work for that subnet. Compare the failing instance with a working one: which security groups it has, whether its outbound rules were tightened, whether the OS firewall blocks outbound traffic, and whether its OS routes send traffic somewhere unexpected. VPC Flow Logs on its ENI and Reachability Analyzer can confirm whether packets are rejected at the security group.
W: Instance-level checks: the difference between a working and a failing instance in the same subnet must be something attached to that instance, so its security groups, host firewall and OS routes are the right place to start.
X: A=VPC peering replacing the default route: a peering connection only adds routes to another VPC's CIDR. It cannot be the target of the default route to the internet, and any route table change would affect every instance in the subnet, not one instance.
B=Shield Advanced: it is a DDoS protection subscription for resources such as load balancers, CloudFront and Elastic IPs. It does not block an instance's own outbound internet traffic.
C=S3 gateway endpoint route: it only adds a prefix-list route for Amazon S3 to the route tables. Internet destinations still use the internet gateway, and the route applies subnet-wide anyway.
T: If neighbors in the same subnet work, skip the subnet-wide layers (routes, NACL) and look at what is unique to the failing instance: security groups and the OS.
V: Amazon VPC, Amazon EC2

@ SOA-C03 D4 T4.1 advanced use-case
S: A company needs to ensure that EC2 instances can only be launched with approved AMIs and required tags. Which TWO controls help? (Select TWO)
A: A shared administrator password so engineers launch from one account
B: A CloudWatch dashboard that shows instance counts by Region and type
C: Config rules that flag instances on unlisted images or lacking tag keys
D: Turning off CloudTrail data events to cut log volume and storage cost
E: IAM conditions on ec2:ImageID and aws:RequestTag for RunInstances
K: C,E
G: ## Preventive and detective controls
Governance works best in two layers:
- **Preventive** controls stop a non-compliant action before it happens.
- **Detective** controls find anything that got through, for example resources created before the policy existed or by a path the policy did not cover.
## Preventive: IAM condition keys
An IAM policy (or an SCP) on `ec2:RunInstances` can allow only specific AMIs with the `ec2:ImageID` condition key, or deny launches unless `aws:RequestTag/CostCenter` is present and `aws:TagKeys` includes the required keys. A launch that breaks the condition fails with an access denied error.
## Detective: AWS Config rules
AWS managed Config rules such as `approved-amis-by-id` (or `approved-amis-by-tag`) and `required-tags` evaluate each instance and mark any violation as `NON_COMPLIANT`. Results can trigger an SSM Automation remediation or an alert.
W: C=Config rules for images and tags: they continuously detect instances running unapproved AMIs or missing required tags, catching anything the preventive policy missed.
E=IAM conditions on image ID and request tags: conditions on `ec2:ImageID` and `aws:RequestTag` block non-compliant launches at the `RunInstances` API call itself.
X: A=Shared administrator password: sharing credentials removes individual accountability and does not restrict which AMIs or tags are used.
B=Instance count dashboard: counts by Region and type reveal nothing about which AMI an instance uses or whether its tags are present.
D=Turning off CloudTrail data events: this removes audit records and enforces nothing; it weakens governance and does not restrict which AMIs or tags are used.
T: Pair preventive IAM conditions on AMI IDs and tags with detective Config rules to enforce approved launches.
V: AWS IAM, AWS Config

@ SOA-C03 D1 T1.3 advanced use-case
S: A company runs a steady-state fleet of EC2 instances 24/7 for three years and wants to cut compute cost without changing instances often. Which option fits?
A: On-Demand Instances, since commitments raise long-term cost for steady use
B: Spot Instances for the production fleet without interruption handling
C: A Compute Savings Plan or Reserved Instances sized to the baseline
D: Dedicated Hosts for the fleet so costs can be shared with other accounts
K: C
G: ## Paying for steady compute
EC2 has several purchase models, and the right one depends on how predictable the usage is.
- **On-Demand**: pay per second or hour with no commitment. Most flexible, highest unit price.
- **Savings Plans**: commit to a dollar amount of compute per hour (for example `$10/hour`) for 1 or 3 years. **Compute Savings Plans** apply automatically across instance families, sizes, Regions, operating systems, and also to Fargate and Lambda. **EC2 Instance Savings Plans** give a deeper discount but are tied to one instance family in one Region.
- **Reserved Instances**: a 1- or 3-year commitment to a specific instance configuration (Standard or Convertible).
- **Spot**: spare capacity at a large discount that AWS can reclaim with a two-minute notice.
## Example
A fleet that runs 24/7 for three years uses the same baseline every hour. A 3-year Compute Savings Plan sized to that baseline turns most of the On-Demand spend into discounted committed spend, and any burst above the commitment is simply billed On-Demand.
W: Savings Plan or Reserved Instances sized to the baseline: long-running, predictable usage is exactly what commitment discounts are for. The company pays much less per hour than On-Demand, and a Compute Savings Plan still lets it change instance types later without losing the discount.
X: A=On-Demand because commitments cost more: the claim is false. On-Demand has the highest unit price, and a 1- or 3-year commitment on a steady 24/7 baseline is the standard way to lower long-term cost.
B=Spot without interruption handling: Spot capacity can be reclaimed at any time with two minutes of notice, so running production on it with no handling risks outages. It suits fault-tolerant work, not a steady fleet that must stay up.
D=Dedicated Hosts shared with other accounts: a Dedicated Host is a whole physical server reserved for you, used for per-socket or per-core licensing or compliance isolation. It can be shared with other accounts through AWS RAM, but the owner still pays for the whole host, and putting the fleet on hosts generally costs more than shared tenancy.
T: Steady, predictable 24/7 usage belongs on Savings Plans or Reserved Instances; Spot is for interruptible work, and On-Demand only for unpredictable or short-lived usage.
V: Savings Plans
