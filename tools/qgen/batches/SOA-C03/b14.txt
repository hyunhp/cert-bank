@ SOA-C03 D1 T1.3 expert troubleshooting
S: A reporting database runs on an m5.large instance with a single gp3 data volume provisioned at 16,000 IOPS and 500 MiB/s. A nightly job needs about 11,000 IOPS of 16 KiB random reads for three hours. CloudWatch shows about 18,000 IOPS for the first 30 minutes, then a sudden drop to about 3,600 IOPS for the rest of the run. At the drop, EBSIOBalance% reaches 0 and InstanceEBSIOPSExceededCheck turns to 1, while VolumeIOPSExceededCheck stays at 0. CPU never exceeds 40%. Finance asks for the smallest change that sustains the job. What should the CloudOps engineer do?
A: Resize the instance to m5.2xlarge, whose 12,000 IOPS baseline EBS performance holds for the entire run
B: Resize the instance to m5.xlarge, whose maximum EBS performance of 18,750 IOPS is twice what the nightly job needs
C: Raise the gp3 volume to 24,000 IOPS, so the volume keeps enough headroom above the job's demand after the initial burst ends
D: Add a second gp3 volume at 16,000 IOPS and stripe both in RAID 0, so the job's reads are spread across two volumes
K: A
G: ## Two limits on EBS performance
An EBS workload is capped by **both** the volume and the instance:
- The **volume** limit: here 16,000 IOPS. `VolumeIOPSExceededCheck = 1` would mean the app is asking for more than the volume provides.
- The **instance** limit: each EBS-optimized instance type has a dedicated EBS bandwidth. `InstanceEBSIOPSExceededCheck = 1` means the app hit the instance's EBS IOPS limit.
## Burstable EBS performance on smaller sizes
Many instance types up to 4xlarge have a **baseline** and a **maximum** EBS performance. They can run at the maximum for **30 minutes at least once every 24 hours**, then fall back to baseline. `EBSIOBalance%` and `EBSByteBalance%` show the remaining burst credits.
## Working the numbers (16 KiB I/O)
- m5.large: baseline 3,600 IOPS, maximum 18,750 IOPS
- m5.xlarge: baseline 6,000 IOPS, maximum 18,750 IOPS
- m5.2xlarge: baseline 12,000 IOPS, maximum 18,750 IOPS
The evidence matches m5.large exactly: about 18,000 IOPS for 30 minutes, then 3,600. A three-hour run at 11,000 IOPS needs an instance whose **baseline** is at least 11,000, and m5.2xlarge is the smallest m5 size that qualifies.
W: A=m5.2xlarge: its 12,000 IOPS baseline covers 11,000 IOPS for the full three hours, so the job no longer depends on the 30-minute burst.
X: B=m5.xlarge: its 18,750 IOPS is only the burst maximum; after 30 minutes it falls to a 6,000 IOPS baseline, about half of what the job needs.
C=More volume IOPS: VolumeIOPSExceededCheck stayed at 0, so the volume was never the limit; the instance throttled the I/O.
D=RAID 0 of two volumes: the instance limit applies to all attached EBS volumes together, so striping adds volume capacity the instance still cannot use.
T: When InstanceEBSIOPSExceededCheck is 1 and EBSIOBalance% hits 0 after 30 minutes, size the instance by its baseline EBS performance, not its burst maximum.

@ SOA-C03 D1 T1.2 expert troubleshooting
S: An order processor is a Lambda function triggered by an SQS standard queue through an event source mapping with batch size 10. The function's reserved concurrency is 20 because the database allows only 20 connections, and its timeout is 60 seconds. The queue's visibility timeout is 60 seconds and its redrive policy sends messages to a dead-letter queue after maxReceiveCount 1. During traffic spikes the Throttles metric rises and thousands of messages land in the dead-letter queue, yet the function logs show no errors for any of those message IDs. Which THREE changes should the CloudOps engineer make? (Select THREE)
A: Set MaximumConcurrency on the event source mapping to 20, so it never drives more invocations than the reserved concurrency allows
B: Raise the queue's visibility timeout to at least 360 seconds, six times the function timeout, so throttled batches get retried first
C: Raise maxReceiveCount on the redrive policy to at least 5, so a message gets several delivery attempts before it moves to the dead-letter queue
D: Set MaximumConcurrency on the event source mapping to 40, so the pollers have extra concurrency headroom above the function's reserved concurrency
E: Remove the reserved concurrency from the function, so it can scale with the queue and the throttles that move messages to the DLQ disappear
F: Raise the function timeout to 360 seconds and keep the queue's visibility timeout at 60 seconds, so each batch gets more processing time
K: A,B,C
G: ## Why throttled messages end up in the DLQ
With an SQS event source, Lambda pollers receive a batch, which makes those messages invisible for the **visibility timeout**, and then invoke the function. If the invoke is **throttled** (here by reserved concurrency 20), the batch is not processed; the messages become visible again and count another **receive**. With `maxReceiveCount = 1`, one throttled receive sends the message to the DLQ, even though the code never failed.
## The three documented settings
- **Maximum concurrency** on the event source mapping (2 to 1,000) limits how many concurrent invocations the queue can drive. AWS advises keeping it **at or below the function's reserved concurrency**; otherwise Lambda may throttle messages.
- **Visibility timeout** of at least **six times the function timeout** (plus any batching window), so Lambda has time to retry throttled batches.
- **maxReceiveCount of at least 5**, so messages get several chances before they are moved to the DLQ.
Lambda also validates that the function timeout is not longer than the queue's visibility timeout.
W: A=MaximumConcurrency 20: the mapping stops trying to run more than 20 invocations, so it no longer generates throttles against the reserved concurrency.
B=Visibility timeout 360 seconds: a batch that is throttled stays hidden long enough for Lambda to retry it instead of reappearing as a new receive.
C=maxReceiveCount 5: a single throttled or retried receive no longer sends a healthy message to the DLQ.
X: D=MaximumConcurrency 40: a value above the reserved concurrency of 20 keeps producing throttles, which is the documented misconfiguration.
E=Remove reserved concurrency: throttles stop, but the function could open far more than 20 database connections and overload the database.
F=Function timeout 360 with visibility 60: Lambda rejects a mapping whose function timeout exceeds the queue's visibility timeout, and the longer timeout does nothing for throttling.
T: For Lambda on SQS with a concurrency cap, set event source maximum concurrency at or below reserved concurrency, visibility timeout at least 6x the function timeout, and maxReceiveCount at least 5.
V: AWS Lambda, Amazon SQS, Amazon CloudWatch

G: ## Connection tracking allowances
Security groups are stateful: each tracked connection uses an entry in the instance's connection tracking table, and every instance type has a maximum. When it is full, new packets are dropped. The ENA metrics show it:

- `conntrack_allowance_available`: entries still free

Flows allowed by `0.0.0.0/0` rules in both directions are normally **untracked**, but connections through some services are **always tracked**, including **Network Load Balancers**, NAT gateways, Global Accelerator and interface endpoints. So opening rules does not help behind an NLB.

C=Open all ports: connections through a Network Load Balancer are always tracked, so wider rules leave the table just as full.
D=NACLs with an empty security group: an empty security group allows no inbound traffic, and NLB connections are still tracked regardless of rules.

G: ## How auto-pause decides
With a minimum capacity of **0 ACUs**, an Aurora Serverless v2 instance pauses after `SecondsUntilAutoPause` (300 to 86,400 seconds) **with no connections initiated by user activity**. While paused, `ServerlessDatabaseCapacity` reports **0** and instance capacity is not billed.

- An associated **RDS Proxy**: the proxy maintains an open connection to each DB instance, so instances in that cluster **never auto-pause**.
- The cluster being the primary or a secondary of an **Aurora global database**.

X: B=300-second interval: the instances never become idle at all because the proxy's connections stay open, so a shorter interval changes nothing.
C=Reader to tier 0: tiers 0 and 1 matter only with replication features, and tier 0 would make the reader less likely to pause in that case, not more.
D=0.5 to 1 ACU: a nonzero minimum turns auto-pause off entirely and keeps charging for capacity overnight.

G: ## How a VPC combines Profile and local settings
For each query, VPC Resolver takes the **first associated Profile in priority order** (100 to 9900; lower is higher priority) that has a matching private hosted zone or Resolver rule, then compares that Profile's match with the VPC's **local** settings:
- the **most specific** domain name wins;
- when both are **equally specific**, the **local VPC settings take precedence**.
## Applying it
The Profile zone and the local zone are both `corp.example.com`, equally specific, so the **local legacy zone wins** and returns 10.0.9.9. Priority only orders Profiles among themselves; it never puts a Profile above local settings. Removing the local association leaves the Profile's zone as the only match.
W: A=Disassociate the legacy zone: with no equally specific local zone, the query is answered from the Profile's zone with 10.1.5.10.
X: B=Priority 100: priority only decides which Profile is consulted first; local settings still win a tie in specificity.
C=Second Profile copy: it is the same zone at the same specificity, so the local zone still takes precedence, and duplicate associations add confusion.
D=TTL 0: the answer is not cached; it comes from the local zone every time, so a lower TTL in the Profile's zone changes nothing.
T: With Route 53 Profiles, an equally specific locally associated zone or rule beats the Profile; remove the local association to let the Profile answer.
