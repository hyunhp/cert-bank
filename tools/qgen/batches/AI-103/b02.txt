# AI-103 D1 T1.2 Set up AI solutions in Foundry (17 questions: infrastructure design x6, deployment options x4, model and agent deployment configuration x4, CI/CD integration x3)

@ AI-103 D1 T1.2 advanced tradeoff
S: A retailer runs three production AI workloads in Microsoft Foundry: a customer support agent, an invoice extraction pipeline and an internal HR assistant. Security requires independent access control for each workload, and finance requires that one workload exhausting its quota or budget can never throttle the others. How should the platform team lay out the Foundry resources for production?
A: Create one Foundry resource with a project for each workload, and rely on project-level RBAC and separate project connections to keep the three workloads' quota and cost apart.
B: Create one Foundry resource per production workload, each with its own primary project, so every workload gets its own access boundary, quota and cost scope.
C: Create one AI hub with three hub-based projects, so the hub shares one managed network while each hub-based project receives its own model quota and budget limit.
D: Create one Foundry resource with three model deployments named after the workloads, and use Azure Policy to stop each team from calling another team's deployment.
K: B
G: ## Resource and project: two different boundaries
In Microsoft Foundry the **Foundry resource** (`Microsoft.CognitiveServices/accounts`, kind `AIServices`) is the top-level Azure resource. It holds governance settings such as networking, security and **model deployments**. A **Foundry project** (`Microsoft.CognitiveServices/accounts/projects`) is a development boundary inside it: agents, files, evaluations and indexes are scoped to the project, while deployments and parent-level connections are shared by every project in the resource.
## Choosing a topology
Microsoft's rollout guidance gives two patterns:
- **Co-located workloads**: one Foundry resource with many projects (often one per use case). Best for experimentation and prototypes that benefit from shared deployments; the trade-off is a **shared blast radius** for incidents, quota exhaustion and misconfiguration.
- **Fully isolated workloads**: one Foundry resource per production workload boundary, usually with one primary project. Gives independent access control and **independent quota and cost boundaries**, at the cost of more resources to manage.
For production, the guidance is to treat isolation as the default and use co-location only as a deliberate exception.
## Example
`contoso-support-prod`, `contoso-invoices-prod` and `contoso-hr-prod` are three Foundry resources. A spike in the support agent's traffic uses up only that resource's deployments, and each team's Entra group is assigned roles on its own resource only.
V: Microsoft Foundry
W: One resource per workload: separate Foundry resources give each workload its own RBAC scope, its own deployments and quota allotment, and its own cost line, which is the isolated pattern Microsoft recommends for production.
X: A=Projects in one resource: projects share the resource's model deployments, so one workload can still exhaust the capacity the others depend on; Microsoft lists this shared blast radius as the trade-off of co-location.
C=Hub-based projects: hubs are the classic project type, and no project type receives its own model quota or budget limit; projects under one parent share its settings, so this layout does not give per-workload isolation.
D=Named deployments with policy: separate deployments do get their own TPM allotments, but Azure Policy governs resource configuration, not which caller sends inference requests, so all three teams still share one resource-level access scope, cost line and incident blast radius.
T: Use projects in one Foundry resource for co-located experimentation, and a separate Foundry resource per production workload when access, quota and cost must be independent.

@ AI-103 D1 T1.2 advanced use-case
S: A company is designing a Foundry deployment for agents that must never use public endpoints. The plan uses a Foundry resource with public network access disabled, the standard agent setup with its own Azure Storage, Azure AI Search and Azure Cosmos DB accounts, and virtual network injection for agent traffic. Which TWO statements must the design account for? (Select TWO)
A: Virtual network injection and its delegated subnet must be chosen when the Foundry resource is created, because outbound networking can't be added afterwards.
B: Private endpoints for the Storage, Azure AI Search and Cosmos DB accounts must be created separately on those resources, because Foundry does not create them automatically.
C: Nothing beyond the Foundry private endpoint, because creating the Foundry resource also creates private endpoints for every connected resource it references.
D: Public network access left enabled on the Foundry resource, because the injected agent subnet reaches the resource only through its public endpoint address.
E: All connected resources placed in the same resource group as the Foundry resource, so that they inherit its network rules and need no separate configuration.
K: A,B
G: ## Three directions of network isolation
Learn splits Foundry network isolation into three areas:
- **Inbound** to the Foundry resource: controlled by the public network access (PNA) flag; set it to *Disabled* and add a **private endpoint** so clients reach the resource privately.
- **Outbound** from the Foundry resource to other Azure services: PaaS dependencies are reached through **Private Link**.
- **Outbound from the Agent client**: Foundry uses **virtual network injection**. The platform injects the agent runtime into a subnet in your virtual network (bring-your-own VNet), or uses a Microsoft-managed virtual network as the simpler alternative.
## What you must build yourself
- The injection subnet must be **delegated to `Microsoft.App/environments`** and be **/27 or larger**, and you select it **when you create the Foundry resource**. Learn lists as a limitation that outbound networking can't be updated later: you can't add virtual network injection to an existing Foundry resource or switch to a different delegated subnet; you must redeploy.
- Connected resources such as Storage, Azure AI Search and Cosmos DB are **independent Azure resources with their own governance boundaries**. Learn states that their private endpoints are **not** auto-created when you deploy the Foundry resource; create them on each resource.
- DNS must resolve each endpoint to its private IP from inside the network.
## Example
`snet-agents` (10.20.4.0/26, delegated to `Microsoft.App/environments`) hosts the injected agent runtime, and `snet-pe` holds private endpoints for `contosofoundry`, `contososearch`, `contosostore` and `contosocosmos`.
V: Microsoft Foundry, Foundry Agent Service, Azure Private Link, Azure AI Search, Azure Cosmos DB
W: A=Decide injection at creation: the delegated subnet is selected when the resource is created, and Learn states outbound networking can't be added to an existing resource or moved to a new subnet without redeploying.
B=Separate private endpoints: connected resources keep their own network settings, and Foundry does not create their private endpoints, so the design must add them on each resource.
X: C=Automatic private endpoints: Learn explicitly warns that private endpoints to Azure AI Search, Storage and Cosmos DB are not auto-created with the Foundry resource.
D=Public access left on: the injected subnet reaches the Foundry resource through its private endpoint; enabling public access contradicts the requirement and is not needed.
E=Shared resource group: resource groups do not pass network rules between resources; each connected resource keeps its own firewall and private endpoint settings.
T: In a network-isolated Foundry design, choose virtual network injection at creation time and create private endpoints for every connected resource yourself.

@ AI-103 D1 T1.2 advanced use-case
S: A company plans for a regional outage of its Foundry-based chat application. Microsoft Foundry does not support automatic cross-region failover. Which TWO design decisions follow Microsoft's guidance? (Select TWO)
A: Deploy a separate Foundry resource in each target region and handle request routing and any data synchronization between regions in the application layer.
B: Confirm before rollout that the required models, deployment types and features such as agents and evaluations are available in every target region.

K: A,B
G: ## Foundry and regions
Foundry stores data at rest in the resource's Azure geography, and inferencing is processed according to the deployment type (global, data zone or regional). What Foundry **does not** do is fail a resource over to another region. Learn's architecture guidance says: if you need multi-region availability, **deploy separate Foundry resources in each target region** and manage data synchronization and routing at the **application layer**.
## Regional differences
Model availability, deployment type options and features such as agents or evaluations **differ across regions**. Validating that every target region supports the required capabilities is on Learn's pre-rollout checklist.
## Global and Data Zone Standard are not failover
Learn notes that with Global Standard and Data Zone Standard deployments, if the primary region has a service interruption, **all traffic initially routed to that region is affected**. Dynamic routing improves capacity; it is not a disaster recovery design.

B=Validate regional availability: models, deployment types and features vary by region, so a secondary region is useful only if it can run the same deployments.
X: C=Paired-region failover: region pairing does not fail Foundry resources over, and Foundry has no automatic cross-region failover of any kind.
D=Data Zone Standard failover: Learn states that an interruption in the primary region affects all traffic initially routed there for Global and Data Zone Standard deployments.
E=Second project: a project is a child of its Foundry resource and does not create an independent deployment in another region.
T: Foundry has no automatic regional failover; build multi-region availability with a resource per region, application routing and a checked region capability list.

@ AI-103 D1 T1.2 applied use-case
S: A European insurer is deploying a chat model in Microsoft Foundry. Prompts and responses must be processed only inside the EU, traffic is bursty and unpredictable, and the team prefers pay-per-token billing with higher default quota than a single-region deployment offers. Which deployment type fits?
A: Global Standard, because it gives the highest default quota and routes requests to the closest EU datacenter whenever the resource is created in an EU region.
B: Regional Provisioned, because reserved throughput units keep processing inside the region and suit traffic whose volume rises and falls without warning.
C: Data Zone Standard in an EU region, because it processes data only within the EU data zone and bills per token with higher quota than geography types.
D: Data Zone Batch in an EU region, because it keeps processing inside the EU data zone and bills per token for each interactive chat request sent.
K: C
G: ## Deployment types decide where data is processed and how you pay
Every Serverless API deployment in Foundry has a **deployment type** (SKU):
- **Global** types (`GlobalStandard`, `GlobalProvisionedManaged`, `GlobalBatch`) may process prompts in **any Azure region**.
- **Data Zone** types (`DataZoneStandard`, `DataZoneProvisionedManaged`, `DataZoneBatch`) process data only within a Microsoft-defined data zone: **US, EU or APAC**. The EU zone follows the Azure EU Data Boundary.
- **Geography** types (`Standard`, `ProvisionedManaged`) process within the resource's Azure geography.
Data at rest stays in the resource's geography for every type; the choice governs **inferencing**.
## Standard, provisioned or batch
- *Standard* types bill **per token** and suit variable, bursty traffic.
- *Provisioned* types reserve capacity in provisioned throughput units (PTUs) for predictable, high-volume traffic.
- *Batch* types run large **asynchronous** jobs with a target turnaround of 24 hours.
Learn notes Data Zone Standard has **higher default quotas than geography-based types** while keeping data in the zone.
## Example
The insurer creates its Foundry resource in Germany West Central and deploys the model with SKU `DataZoneStandard`.
V: Microsoft Foundry Models
W: Data Zone Standard: it keeps inferencing inside the EU data zone, bills per token for bursty traffic, and offers higher default quota than the single-geography Standard type.
X: A=Global Standard: global types may process data in any Azure region; creating the resource in the EU does not restrict where inferencing happens.
B=Regional Provisioned: reserved PTUs suit consistent high volume; for unpredictable bursts the insurer would pay for idle reserved capacity and lose pay-per-token billing.
D=Data Zone Batch: batch deployments process asynchronous files of requests with a 24-hour target; they are not for interactive chat requests.
T: For zone-level data residency with bursty pay-per-token traffic, choose Data Zone Standard in a region inside that zone.

**Global Batch** (`GlobalBatch`) and **Data Zone Batch** (`DataZoneBatch`) are deployment types for large, non-urgent workloads. Instead of sending one request at a time, you upload a file containing many requests and the service processes it asynchronously.

- Global Standard: interactive pay-per-token traffic; the default starting point.
- Global Provisioned: reserved PTUs for predictable, latency-sensitive volume.
- Global Batch: big asynchronous jobs where next-day results are fine.

@ AI-103 D1 T1.2 applied use-case
S: A team pins a chat deployment to a specific model version so it can validate each new version before switching. It does not want automatic upgrades when Microsoft changes the default version, but if it misses a retirement date, the deployment must keep working rather than stop. Which `versionUpgradeOption` value should the deployment use?
A: `OnceNewDefaultVersionAvailable`, which upgrades the deployment to the new default version within two weeks of the default version changing.
B: `OnceCurrentVersionExpired`, which keeps the pinned version until its retirement date and then upgrades the deployment to the current default version.
C: `NoAutoUpgrade`, which keeps the pinned version until its retirement date and then upgrades the deployment to the latest preview version available.
D: `NoAutoUpgrade`, which never upgrades the deployment and moves it to the next available model family after its version reaches retirement.
K: B
G: ## Version upgrade policy
Each Azure OpenAI model deployment has a **model version** and, for models that support automatic updates, a **version upgrade policy** (`versionUpgradeOption`):
- `OnceNewDefaultVersionAvailable` (*Auto-update to default*): when a new version becomes the default, the deployment upgrades within two weeks. Good for early testing.
- `OnceCurrentVersionExpired`: the deployment stays on its version until the **retirement date**, then upgrades to the current default. A null value behaves the same way.
- `NoAutoUpgrade`: the deployment never upgrades; at retirement it **stops working**, and code must be pointed at a non-expired deployment.
Learn notes automatic updates apply to standard deployment types; provisioned deployments use their own migration practices.
## Setting it
The property lives on the deployment and can be set in the portal, REST or Azure PowerShell. A REST `PUT` on `.../accounts/{account}/deployments/{name}` with `"versionUpgradeOption": "OnceCurrentVersionExpired"` in `properties` sets it.
## Example
The team tests each new version on a separate test deployment, then updates `model.version` on production by hand; `OnceCurrentVersionExpired` is the safety net if a retirement date slips past.
V: Azure OpenAI in Foundry Models
W: OnceCurrentVersionExpired: the pinned version stays until the team upgrades it manually, and at retirement the deployment moves to the default version instead of failing.
X: A=OnceNewDefaultVersionAvailable: this upgrades automatically whenever the default version changes, which is the behavior the team wants to avoid.
C=NoAutoUpgrade to preview: NoAutoUpgrade never upgrades at all, to preview or otherwise; at retirement the deployment stops working.
D=NoAutoUpgrade to next family: NoAutoUpgrade does not move deployments to another model family; once the version retires, requests to the deployment fail.
T: Pin versions with `OnceCurrentVersionExpired` to control upgrades yourself while avoiding an outage at retirement; `NoAutoUpgrade` stops working when the version retires.

A: Lower `sku.capacity` on one of the existing `GlobalStandard` deployments of the same model in East US, or request a quota increase for that model, region and deployment type.
B: Move the new deployment into a different Foundry resource in East US, because each Foundry resource receives its own separate quota for every model it deploys.
C: Lower `sku.capacity` on the deployment of the different model in East US, because capacity released by any model goes back to one shared quota pool for the region.
D: Set a `rateLimits` value in the deployment properties of the template, because an explicit rate limit lets the deployment run outside the subscription's model quota.
K: A
G: ## How standard deployment quota works
Quota for standard deployment types is assigned to the **subscription**, **per region, per model and per deployment type**, in tokens per minute (TPM). Each time you create a deployment you assign part of that quota to it, and the available quota for that model shrinks by the same amount. Learn's example: with 240,000 TPM of a model in East US you can create one 240K deployment, two 120K deployments, or any number of deployments **in one or multiple resources** as long as the total stays within the quota.
## The capacity property
In ARM, Bicep and REST the assignment is the deployment's **`sku.capacity`**, counted in **capacity units**. Each unit maps to a model-specific amount of TPM and requests per minute (RPM); for many chat models one unit is 1,000 TPM, but some models use a different ratio, so check the quota table for the model. The rate limits the service enforces are derived from the capacity you assign.
## When quota runs out
Once the quota for a model, region and deployment type is used up, you can only create new deployments of that model by **reducing the capacity assigned to other deployments of the same model** or by **requesting a quota increase**.
## Example
Quota for the model in East US is fully assigned to `chat-prod` and `chat-test`. Lowering `chat-test` from 100 to 40 units frees 60 units, and the template's new deployment with `capacity: 50` then succeeds.
V: Azure OpenAI in Foundry Models, Bicep
W: Free or raise the same quota: quota is shared by all deployments of that model, region and deployment type in the subscription, so capacity must come from another deployment of the same model or from an approved increase.
X: B=Different resource: quota belongs to the subscription and region, not to a Foundry resource; deployments in one or many resources draw from the same total.
C=Different model: quota is assigned per model, so capacity released by another model's deployment does not become available to this model.
D=rateLimits value: rate limits are derived by the service from the assigned capacity; they are not an input that bypasses the subscription quota.
T: Standard deployment quota is per subscription, region, model and deployment type; free capacity from deployments of the same model or request an increase.

G: ## Connections in Foundry
A **connection** stores the endpoint and authentication details that let a Foundry project use another resource, such as Azure AI Search, Azure Storage or an external API, without each developer configuring it again. The connected resources themselves remain separate Azure resources with their own governance.
## Two scopes
Learn's rollout guidance states that connections can be created at both the **parent Foundry resource level** and the **child project level**, depending on the isolation scope you want:
- A connection on the **Foundry resource** is available to **all projects** in that resource. Use it for shared data and tools.
- A connection on a **project** belongs to that project. Use it for data that only one team should reach.
Projects otherwise share common settings from their parent, such as network security and model deployments, so choosing the connection scope is one of the main ways to separate what each team can use.

W: Resource-level plus project-level: a parent-level connection is shared with every project, and a project-level connection keeps the payroll Storage connection inside the finance project.
X: B=Both on the resource: connections can also be created on a project, and a resource-level connection is available to every project, which exposes the payroll connection to all five teams.
C=Search in every project: repeating the same connection five times is unnecessary work, and the resource-level Storage connection would be available to all projects, not only to administrators.

G: ## Agent identities
In Foundry Agent Service, an agent can call tools such as Azure AI Search using an **Entra agent identity**. Which identity it uses depends on how the agent was created:
- **Legacy agents** (created before the newer agent object model) use the **project's shared** agent identity and blueprint.
- **New agents** receive their **own unique** Entra agent identity and blueprint when they are created, along with a stable agent endpoint.
In the older publishing flow, publishing an agent created an Agent Application with its own identity, and the same rule applied.
## Permissions follow the identity
Azure RBAC assignments belong to a principal. When the identity behind an agent changes, **permissions don't transfer**. Learn's migration guidance says you must reassign roles on downstream resources to the new identity; otherwise tool calls that worked in development fail with authorization errors. Apply least privilege and remove assignments that are no longer needed.
Note: the new agent endpoint and publishing APIs shown in Learn's migration guide use preview API versions (`2025-11-15-preview`); the rule that role assignments follow the identity is plain Azure RBAC and does not depend on them.
## Example
The team grants the new agent's identity the search data role it needs on `contososearch` and removes the role from the project's shared identity once no legacy agents use it.
V: Foundry Agent Service, Azure AI Search, Microsoft Entra ID
W: Roles on the new identity: the recreated agent runs as its own agent identity, which has no role assignments yet, so the search roles must be granted to it.
X: A=Restore old definition: the definition already matches; the failure comes from the identity that calls Azure AI Search, not from the tool configuration.
C=Foundry User for developers: agent tool calls use the agent identity, not the developer's identity, so developer roles do not authorize the search tool.
D=Search admin key: the tool is set to authenticate with agent identity, and switching to shared keys weakens security instead of fixing the missing role assignment.
T: When an agent gets a new identity (new agent model or publishing), reassign the roles its tools need to that identity.
