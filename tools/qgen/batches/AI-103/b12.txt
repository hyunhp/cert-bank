@ AI-103 D1 T1.2 expert use-case
S: A Swedish insurer sizes a provisioned gpt-4.1 deployment for a claims assistant. Peak traffic is 600 requests per minute, with an average prompt of 2,000 tokens and an average response of 250 tokens. The shared system prompt makes about 40 percent of input tokens prompt cache hits. For gpt-4.1, Learn lists 3,000 input TPM per PTU and an output-to-input ratio of 4; Global and Data Zone Provisioned deploy from 15 PTUs in steps of 5, Regional Provisioned from 50 PTUs in steps of 50. The architecture review adds one more fact: the works council agreement requires prompts and responses to be processed only within the Azure geography of the deployment. Which deployment should the team request?
A: Regional Provisioned with 600 PTUs, from 1,200,000 input TPM with no cache deduction plus 600,000 weighted output TPM
B: Data Zone Provisioned with 440 PTUs, from 720,000 cached-adjusted input TPM plus 600,000 weighted output TPM
C: Regional Provisioned with 300 PTUs, from 720,000 cached-adjusted input TPM plus 150,000 output TPM without any weighting
D: Regional Provisioned with 450 PTUs, from 720,000 cached-adjusted input TPM plus 600,000 weighted output TPM
K: D
G: ## Sizing a provisioned deployment by hand
Learn's method converts the workload into **normalized TPM** and divides by the model's **Input TPM per PTU**:
- Input TPM = peak RPM x average prompt tokens
- Output TPM = peak RPM x average response tokens
- Normalized TPM = input TPM x (1 - cache rate) + output-to-input ratio x output TPM (for models before GPT-6 Astra, cached tokens are fully deducted)
- PTUs = normalized TPM / Input TPM per PTU, rounded **up** to the deployment type's scale increment or minimum
## Worked numbers
- Input TPM = 600 x 2,000 = 1,200,000; after 40% cache hits: 720,000
- Output TPM = 600 x 250 = 150,000; weighted x 4 = 600,000
- Normalized TPM = 1,320,000; / 3,000 = **440 PTUs**
- Regional Provisioned scales in steps of 50, so 440 rounds up to **450**.
## The residency detail
Global types may process anywhere; Data Zone types stay in the US, EU or APAC zone; **Standard and Regional Provisioned keep processing within the customer-specified Azure geography**. "Only within the Azure geography" therefore rules out Data Zone Provisioned even though its 440 PTUs would be a valid size.
W: Regional Provisioned, 450 PTUs: the normalized 1,320,000 TPM needs 440 PTUs, Regional Provisioned rounds to steps of 50, and it is the provisioned type that keeps processing in the deployment's geography.
X: A=600 PTUs without cache deduction: for gpt-4.1, cached input tokens are deducted 100% and don't consume PTU capacity, so 600 oversizes the deployment.
B=Data Zone Provisioned, 440 PTUs: the math is right, but a data zone spans many countries, which breaks the works council's geography rule.
C=300 PTUs without output weighting: one gpt-4.1 output token counts as four input tokens, so leaving 150,000 output TPM unweighted undersizes the deployment by about a third.
T: PTUs = (input TPM x (1 - cache rate) + ratio x output TPM) / input TPM per PTU, rounded up to the step of the deployment type that meets residency.
V: Provisioned throughput, Microsoft Foundry

@ AI-103 D1 T1.3 expert troubleshooting
S: A help desk routes tickets with an o4-mini Global Standard deployment that has 200,000 TPM assigned. The subscription's regional quota for o4-mini Global Standard is 500,000 TPM, and only this deployment uses it. Traffic is steady at about 350 requests per minute, spread evenly, and each request is small: about 250 prompt tokens with max_completion_tokens set to 100. About 40 percent of calls fail with HTTP 429 "Rate limit is exceeded", while Azure Monitor shows only about 90,000 processed tokens per minute. Learn's quota table lists one o4-mini capacity unit as 1 RPM and 1,000 TPM. What should the developer do?
A: Raise the deployment to at least 350,000 TPM, because o4-mini gets 1 RPM per 1,000 TPM and 350 requests per minute need 350 units
B: Keep 200,000 TPM and pace requests within each second, because 200,000 TPM already allows 1,200 requests per minute for o4-mini
C: Lower max_completion_tokens to 50, because the limiter counts prompt plus maximum output, which pushes the estimate over 200,000 TPM
D: Submit a quota increase request for o4-mini, because a 429 that names the rate limit means the regional quota has been used up
K: A
G: ## RPM follows TPM, and the ratio depends on the model
Assigning TPM to a deployment also sets its **requests-per-minute (RPM)** limit, in fixed units of capacity. Learn's table:
- Older chat models: 1 unit = **6 RPM** and 1,000 TPM
- o4-mini and o3: 1 unit = **1 RPM** and 1,000 TPM
- o3-mini, o1-mini, o3-pro: 1 unit = 1 RPM and 10,000 TPM
"Changes in RPM/TPM ratio can result in accidental misallocation of quota", especially for programmatic deployments.
## Worked numbers
- 200,000 TPM on o4-mini = 200 units = **200 RPM**.
- Demand is 350 RPM, so about 150 of 350 requests a minute (about 43%) are rejected, matching the evidence.
- Token demand is tiny: 350 x (250 + 100) = 122,500 estimated TPM, well under 200,000. The token limit isn't the bottleneck.
- 350 RPM needs 350 units = **350,000 TPM**; the regional pool has 500,000, so no quota request is needed.
W: Raise to 350,000 TPM or more: on o4-mini each 1,000 TPM gives only 1 RPM, so 350 requests per minute need 350 units, which fit inside the unused regional quota.
X: B=1,200 RPM: 6 RPM per 1,000 TPM applies to older chat models; for o4-mini, 200,000 TPM gives 200 RPM.
C=Lower max_completion_tokens: the estimated 122,500 TPM is already under 200,000, so the token limit isn't what is being hit; the RPM limit is.
D=Quota increase: 300,000 TPM of regional quota is unassigned, so the fix is a larger assignment, not more quota.
T: For o-series models check the RPM-per-unit ratio: o4-mini gets 1 RPM per 1,000 TPM, so request-heavy, token-light workloads hit the RPM limit first.

Which TWO statements are correct? (Select TWO)

G: ## Two ways to turn on spillover
- **Deployment level**: set `spilloverDeploymentName` on the provisioned deployment; all requests can spill.
- **Request level**: send `x-ms-spillover-deployment: <standard deployment>`; only those requests can spill.
Learn: "If the spillover capability is enabled for the deployment using the `spilloverDeploymentName` property and also enabled at the request level ..., the system defaults to the setting of the deployment property. If you want to ensure that spillover is only enabled on a per-request basis, don't set the `spilloverDeploymentName` property."
## When spillover triggers
Spillover starts on specific non-200 results from the provisioned deployment:
- 429 when PTUs are fully used
- **400 for long context**: "when you use gpt 4.1 series models, PTU supports only context lengths less than 128K and returns HTTP 400"
- 500 or 503 server errors
Spilled responses carry `x-ms-spillover-from-deployment` and `x-ms-spillover-error` (the provisioned deployment's status code).
## Applying it
Omitting the header doesn't help while the deployment property is set. The 150,000-token contracts exceed the 128K PTU limit, so they correctly spill and are billed at standard rates.
W: C=Long-context 400: gpt-4.1 PTU deployments reject prompts of 128K tokens or more with 400, which triggers spillover to the standard deployment.
D=Property overrides header: with spilloverDeploymentName set, every request can spill; removing the property and sending the header only on interactive calls keeps the nightly job on PTU.
X: A=Always on for Global Provisioned: spillover is optional per deployment or per request; moving to Regional Provisioned isn't needed.
B=Guardrail 400: a guardrail block returns a content_filter error, and the stem states no filter fired; standard deployments also apply guardrails.
E=Only on 429: Learn lists 429, 500, 503 and the long-context 400 as triggers (the 400 header here proves it); more PTUs can reduce spills but can't guarantee none while the deployment property lets every request spill.
T: The deployment-level spillover setting wins over the request header, and gpt-4.1 PTU requests of 128K tokens or more spill over with a 400.

@ AI-103 D1 T1.1 expert tradeoff

Each night carries about 30 million tokens in total (prompt plus output), max_tokens is set close to real output sizes, and the work can be spread evenly through the night by a queue. G: ## Deadlines versus batch turnaround
Batch deployments (Global Batch, Data Zone Batch) bill at a 50% discount, but Learn describes their processing as a **24-hour target**: "The service aims to process batch requests within 24 hours, but it doesn't expire jobs that take longer." - Required rate: 30,000,000 / 720 = about **41,700 tokens per minute**.

- A 50,000 TPM deployment leaves about 20% headroom for the rate limiter, which counts prompt plus max_tokens at request time.
## Residency
Data Zone types keep processing in the EU zone; Global Standard may process in any Azure region.
W: Data Zone Standard at 50,000 TPM: it keeps prompts in the EU zone, and 50,000 TPM over 720 minutes covers the 41,700 TPM average with headroom, so the deadline is met at pay-per-token cost.
X: A=Global Standard: the rate is sufficient, but Global types may process data outside the EU data zone.
C=Data Zone Batch: it is cheaper and in-zone, but its 24-hour target doesn't guarantee completion within the 12-hour contractual window.
D=30,000 TPM: 30,000 x 720 = 21.6 million tokens, so about 8 million tokens would miss the 07:00 deadline.
T: Batch offers a 24-hour target, not a deadline; size a standard deployment from tokens / minutes in the window, and pick the data zone type when residency applies.

G: ## Each tool evaluator isolates one step
GA process evaluators for agents:
- **Tool Selection**: chose the needed tools without unnecessary ones.
- **Tool Input Accuracy**: parameters correct (types, formats, required fields, values).

## Reading the evidence

G: ## Model aliases in prebuilt analyzers
Prebuilt analyzers reference **model aliases** instead of model names so the service can upgrade models without changing analyzer definitions:
- `prebuilt-analyzer-completion`: default for most prebuilt analyzers
- `prebuilt-analyzer-completion-mini`: default for selected prebuilt analyzers, **for example `prebuilt-*Search`**
- `prebuilt-analyzer-embedding`: analyzers that need embeddings
You map aliases to your deployments in the resource's default `modelDeployments` (or per request). A GET on an analyzer returns `supportedModels` (completion and embedding lists) and its `models` aliases.
## Reading the evidence
Custom analyzers use the two mapped aliases and work. prebuilt-documentSearch needs `prebuilt-analyzer-completion-mini`, which has no mapping, so it fails. The fix is to add that mapping to a supported mini completion deployment (cheapest fit), not to change prebuilt definitions.
## Also note
12-page PDFs sent asynchronously are within limits (async handles up to 2,000 pages); synchronous calls would process only the first five pages.
