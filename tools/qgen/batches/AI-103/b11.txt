@ AI-103 D1 T1.1 advanced use-case
S: A media group plans three gpt-4.1-mini workloads in Microsoft Foundry. A customer assistant for German users has steady, high traffic, needs consistent latency, and its prompts must stay inside the EU. A nightly job labels 2 million archived articles; it has no residency rule and results are needed within a day. A data scientist must also score three fine-tuned checkpoints for a few hours each at the lowest cost. Which THREE deployment choices fit? (Select THREE)
A: Data Zone Provisioned for the assistant, which reserves dedicated throughput and keeps processing inside the EU data zone
B: Global Batch for the labeling job, which offers a 24-hour target turnaround at a discount and uses separate enqueued token quota
C: Developer deployments for the checkpoints, built for short fine-tuned model evaluation with per-token billing and no hosting fee
D: Global Provisioned for the assistant, which gives the widest capacity choice plus dedicated throughput and predictable latency
E: Regional Provisioned for the labeling job, which reserves capacity in one region so that the archive finishes at a steady pace
F: Global Standard deployments for each checkpoint, which keep every candidate online with an availability SLA for the evaluation
K: A,B,C
G: ## Three questions decide a deployment type
Every Foundry deployment type answers three questions: **where** data is processed, **how** you pay, and **what latency behavior** you get.
- **Where**: Global types may process in any Azure region; Data Zone types stay inside a Microsoft-defined zone (US, EU or APAC); Standard and Regional Provisioned stay in the chosen Azure geography.
- **How you pay**: Standard types bill per token; Provisioned types bill per PTU per hour (or through a reservation); Batch types bill per token at a 50% discount.
- **Latency**: Provisioned types give reserved capacity and low latency variance; Standard and Batch are best effort.
## Fine-tuned model evaluation
The **Developer** type exists for evaluating fine-tuned models: per-token billing, **no hourly hosting fee**, a **24-hour lifetime**, no SLA and no residency guarantee. Other deployment types for fine-tuned models can add fine-tuned hosting charges.
## Mapping the example
Steady, latency-sensitive EU traffic needs reserved capacity **and** zone residency: Data Zone Provisioned. A large job with a one-day window and no residency rule is the textbook Global Batch case. A few hours of checkpoint scoring fits inside Developer's 24-hour lifetime.
W: A=Data Zone Provisioned: it is the documented choice for data residency plus reserved throughput, giving the assistant consistent latency while prompts stay in the EU zone.
B=Global Batch: large asynchronous jobs that can wait up to a day are its purpose, at 50% lower cost, and its enqueued token quota doesn't compete with online traffic.
C=Developer: it is the lowest-cost way to evaluate fine-tuned models, and a few hours per checkpoint fits within its 24-hour lifetime.
X: D=Global Provisioned: it can route traffic to any Azure region, which breaks the rule that the assistant's prompts stay inside the EU.
E=Regional Provisioned: paying hourly for reserved PTUs for a job that only needs results within a day costs far more than the discounted batch rate.
F=Global Standard per checkpoint: an SLA isn't needed for a few hours of scoring, and fine-tuned deployments outside Developer can add hosting charges, so it isn't the lowest-cost choice.
T: Match residency, billing and latency needs: Data Zone Provisioned for EU steady traffic, Global Batch for day-long bulk jobs, Developer for short fine-tuned evaluations.

@ AI-103 D1 T1.1 advanced comparison
S: A travel company is building multilingual retrieval over 3 million help-article chunks in English, Spanish, Japanese and Korean. Users often ask in one language while the best article is written in another. The search team's memory budget allows at most 1,024 float dimensions per vector, and the architect wants one embedding deployment for both indexing and queries. Which embedding approach best meets these constraints?
A: Deploy text-embedding-3-large and request 1,024-dimension vectors with the dimensions parameter for both chunks and queries
B: Deploy text-embedding-ada-002 and request 1,024-dimension vectors with the dimensions parameter for the chunks and the queries
C: Deploy text-embedding-3-large, keep 3,072 dimensions for chunks, and request 1,024 dimensions only for queries to save memory
D: Deploy text-embedding-3-small at its default 1,536 dimensions, because the smaller model already returns vectors within the budget
K: A
G: ## Third-generation embeddings and the `dimensions` parameter
Foundry offers `text-embedding-3-large` (3,072 output dimensions), `text-embedding-3-small` (1,536) and `text-embedding-ada-002` (1,536).
- Learn reports that both third-generation models score clearly better than ada-002 on **multi-language retrieval** (MIRACL average 54.9 for large, 44.0 for small, 31.4 for ada-002).
- The third-generation models support a **`dimensions` parameter** that shortens the returned vector. Learn notes that even below 1,536 dimensions they still perform slightly better than ada-002.
- ada-002 has a fixed 1,536-dimension output and no `dimensions` parameter.
## Vectors must live in the same space
A query vector is compared with document vectors by similarity, so both must come from the **same model with the same dimension count**. A vector field in Azure AI Search has one `dimensions` value; queries with another length don't match it.
## Example
`text-embedding-3-large` with `dimensions=1024` for every chunk and every query: 1,024 floats per vector (inside the budget) and the strongest cross-language retrieval.
W: text-embedding-3-large at 1,024 dimensions: it has the best multilingual retrieval quality, and the dimensions parameter trims every vector to the 1,024-float budget while keeping queries and documents in the same space.
X: B=ada-002 with dimensions: ada-002 doesn't support the dimensions parameter, always returns 1,536 dimensions, and is weaker on multi-language retrieval.
C=3,072 for chunks, 1,024 for queries: vectors of different lengths can't be compared in one vector field, and 3,072-dimension chunks break the memory budget.
D=text-embedding-3-small at 1,536: 1,536 dimensions exceeds the 1,024 budget, and the small model is also weaker than the large one on multilingual retrieval.
T: Use a text-embedding-3 model with the dimensions parameter to fit a vector budget, and embed documents and queries with the same model and size.

@ AI-103 D1 T1.1 advanced tradeoff
S: A SaaS vendor keeps 4 million document chunks for 300 customers in one Azure AI Search index with an HNSW vector profile and a filterable tenantId field. Every vector query is filtered to one tenant, and small tenants own only a few hundred chunks. Queries for these tenants are slow and use a lot of CPU. The vendor must keep full recall and tenant isolation without restructuring the index. What should the developer do?
A: Keep the tenantId filter in preFilter mode and set exhaustive to true on vector queries for small tenants, so only their vectors are scanned
B: Switch vectorFilterMode to postFilter, so HNSW traversal runs first on each shard and results from other tenants are removed afterward
C: Switch vectorFilterMode to strictPostFilter, so the global top k is found first and the tenant filter is applied to that final list
D: Drop the tenantId filter for small tenants and instruct the chat model to ignore any retrieved chunks that belong to another customer
K: A
G: ## Where a vector filter is applied
Azure AI Search offers three `vectorFilterMode` values:
- **preFilter** (default for indexes created after about October 2023): the filter is applied during HNSW traversal. It maximizes recall and guarantees `k` results if they exist, but a **highly selective** filter forces the engine to traverse much more of the graph, raising CPU and latency.
- **postFilter**: traversal runs first, then results are filtered per shard. Highly selective filters or small `k` can produce **false negatives**.
- **strictPostFilter** (preview): finds the unfiltered global top `k`, then filters; the highest false-negative risk.
## Learn's advice for very selective filters
"If your filter is highly selective (has very few matches), consider using `exhaustive: true` to perform exhaustive search." Exhaustive KNN scans the vectors that pass the filter instead of navigating the graph, which suits a tenant with a few hundred chunks out of 4 million.
W: preFilter plus exhaustive: the filter keeps tenant isolation, and the exhaustive scan over the few hundred matching vectors avoids the expensive graph traversal while returning every true nearest neighbor.
X: B=postFilter: filtering after traversal is exactly the case Learn warns about; with a tenant that owns 0.01% of the vectors, most candidates are discarded and relevant chunks go missing.
C=strictPostFilter: it is preview and has the highest false-negative risk for selective filters, because the unfiltered global top k rarely contains a small tenant's chunks.
D=Drop the filter: sending other customers' chunks to the model breaks tenant isolation, and an instruction is not a security boundary.
T: For highly selective vector filters keep preFilter and use exhaustive search; post-filtering trades recall for speed and loses matches.

@ AI-103 D1 T1.2 advanced troubleshooting
S: A bank will run a Data Zone Provisioned deployment of 300 PTUs in Sweden Central for at least a year. Finance plans to buy an Azure reservation now and create the deployment next month, after a vendor contract is signed, and assumes the reservation holds the capacity until then. The AI engineer must keep the discounted rate and avoid a failed rollout. What should the engineer advise?
A: Create the deployment first to confirm that capacity is available, then buy a Data Zone Provisioned reservation that covers those PTUs
B: Buy a Global Provisioned reservation now, because one reservation discounts every provisioned deployment type in the subscription
C: Buy the Data Zone reservation now, because a reservation holds regional PTU capacity until a matching deployment is created later
D: Create the deployment now on hourly billing, then scale it down to zero PTUs until the contract is signed so the capacity stays held
K: A
G: ## Quota, capacity and reservations are three different things
- **PTU quota**: a policy limit per subscription, region and deployment type. It costs nothing and does not guarantee capacity.
- **Capacity**: the PTUs actually available for a model in a region. It is allocated **when you create the deployment** and held for its lifetime. Deleting or scaling down releases it, with no guarantee you get it back.
- **Azure Reservation**: a **financial discount** on the PTU billing meter for a 1-month or 1-year term. Reservations are bought **per deployment type** (Global, Data Zone or Regional) and are loosely coupled to deployments.
## The documented order
Learn says reservations "don't guarantee capacity. First create deployments to confirm that capacity is available, then purchase the reservation to lock in the discounted rate." Buying first risks paying for a discount that no deployment can use.
## Example
Create `DataZoneProvisionedManaged` with 300 PTUs in Sweden Central. When it succeeds, buy a 1-year Data Zone Provisioned reservation for 300 PTUs scoped to that subscription.
W: Deploy first, then reserve: creating the deployment is what secures capacity, and a Data Zone reservation then applies the discount to the same deployment type's meter.
X: B=Global reservation: reservations are purchased per deployment type, so a Global reservation doesn't discount a Data Zone Provisioned deployment.
C=Reservation holds capacity: a reservation is only a billing discount; capacity may be gone next month and the reservation would sit unused.
D=Scale to zero: scaling a deployment down releases its capacity back to the region pool, so the capacity is not held, and provisioned deployments have a minimum size.
T: An Azure reservation for PTUs is a discount, not a capacity hold: create the provisioned deployment first, then buy a reservation of the same deployment type.

@ AI-103 D1 T1.2 advanced troubleshooting
S: A retailer regenerates 250,000 product summaries each weekend with Global Batch. It has two Global Batch deployments, gpt-4.1-mini for standard items and gpt-4.1 for premium items. The developer builds one JSONL file with all 250,000 lines, mixing both deployment names in the model field, and the results are written back to the catalog by line position. Which TWO changes are required for the job to work correctly? (Select TWO)
A: Split the work into separate files per deployment, each with at most 100,000 requests and the same model value on every line
B: Match each result to its product by its custom_id value, because batch output isn't returned in the order of the input file
C: Set completion_window to 72h for the larger file, because jobs with more than 100,000 lines need a longer processing window
D: Send the file to a Global Standard deployment with a batch header, because Global Batch deployments accept only files under 1 MB
E: Enable spillover from the batch deployments to a Global Standard deployment, so lines that exceed enqueued quota run online
K: A,B
G: ## How a Global Batch job is built
A batch job is a `.jsonl` file of requests, uploaded through the Files API (or from Blob Storage) and submitted as one job.
- **One deployment per file**: the `model` attribute must name the Global Batch deployment, and "the same Global Batch model deployment name must be present on each line". To target another deployment, use a separate file and job.
- **Limits**: at most **100,000 requests per file** and 200 MB per input file (1 GB with bring-your-own storage).
- **Order**: "Responses won't be returned in identical order to the order defined in the `.jsonl` batch file", which is why every line needs a unique `custom_id`.
- **Window**: `completion_window` must be `24h`; any other value makes the job fail. Jobs that take longer keep running until canceled.
- **Quota**: tokens in submitted files count against an **enqueued token** limit until the job finishes; Learn recommends **dynamic quota** on batch deployments to avoid failures from insufficient enqueued quota.
## Example
150,000 standard items become two files of 75,000 lines for `gpt-41-mini-batch`; 100,000 premium items become one file for `gpt-41-batch`. The writer joins results on `custom_id` such as `sku-48213`.
W: A=Separate files per deployment: each file may target only one Global Batch deployment and hold at most 100,000 requests, so the mixed 250,000-line file is invalid.
B=Join on custom_id: batch results come back in a different order, so line position would attach summaries to the wrong products.
X: C=72h window: completion_window must be 24h; other values make the job fail, and there is no longer window for large files.
D=Batch header on Global Standard: batch work runs on Global Batch deployments, and input files can be up to 200 MB, not 1 MB.
E=Spillover: spillover routes overflow from provisioned deployments to standard ones; it is not a batch feature, and enqueued token limits are handled with dynamic quota or queued jobs.
T: A batch file targets one Global Batch deployment with up to 100,000 lines, and results must be matched by custom_id, not by order.

@ AI-103 D1 T1.3 advanced troubleshooting
S: A Global Standard deployment has 300,000 TPM allocated. Since this morning, a steady workload of about 120,000 tokens per minute gets intermittent HTTP 429 responses. The allocation and regional quota are unchanged, max_tokens matches real reply sizes, and requests are spread evenly over each minute. Response headers show x-ratelimit-limit-tokens of 90,000. The product owner wants to file a quota increase. What is the most appropriate response?
A: Treat it as a temporary rate limit adjustment on the shared pool: honor retry-after-ms, spread traffic, and consider PTU for steady throughput
B: File the quota increase, because x-ratelimit-limit-tokens below the allocation shows that the regional quota for the model is exhausted
C: Lower max_tokens further on every call, because the header reports the prompt estimate plus max_tokens counted against the TPM limit
D: Raise the deployment's TPM allocation to 600,000, because a larger allocation prevents temporary adjustments on Global Standard
K: A
G: ## Not every 429 is a quota problem
Learn lists several kinds of 429 and warns that "many customers misinterpret capacity-related 429s as quota problems".
- **Rate limit exceeded**: traffic exceeds the deployment's TPM or RPM allocation.
- **Token budget exceeded by request parameters**: a large `max_tokens` inflates the per-request estimate.
- **Burst patterns**: RPM is checked in 1 to 10 second windows.
- **Temporary rate limit adjustment**: Standard (pay-as-you-go) deployments share a resource pool. When demand nears capacity, the service **temporarily lowers a deployment's effective limit**. The tell-tale sign is `x-ratelimit-limit-tokens` **lower than the configured TPM** while the quota is unchanged. It typically resolves within a few hours.
## The documented response
Retry with backoff that honors `retry-after-ms`, spread traffic across deployments or regions, ramp workloads gradually, and consider **Provisioned Throughput** when the workload needs consistent throughput without shared-pool variability.
W: Temporary adjustment: the header shows a 90,000 effective limit against a 300,000 allocation with nothing else changed, which is the documented sign of a protective, temporary adjustment that backoff and traffic spreading handle.
X: B=Quota increase: the allocation and regional quota are unchanged and only partly used; a quota request treats a shared-pool capacity event as a quota shortage.
C=Lower max_tokens: max_tokens already matches reply sizes, and x-ratelimit-limit-tokens reports the effective limit, not each request's estimated token count.
D=Allocate 600,000 TPM: temporary adjustments come from shared-pool demand, so a bigger Standard allocation doesn't prevent them; only provisioned capacity avoids that variability.
T: A 429 with x-ratelimit-limit-tokens below the configured TPM means a temporary shared-pool adjustment: back off and spread traffic, or move steady workloads to PTU.

G: ## Replicas and partitions do different jobs
- **Replica**: a copy of the index used to load-balance queries. More replicas = more query throughput and **availability**.

- **Two or more replicas** satisfy query (read) SLAs.
- **Three or more replicas** satisfy query (read) **and** indexing (write) SLAs.
- "The number of partitions doesn't affect SLAs."
## Example

W: A=At least three replicas: three or more replicas is the documented threshold for both read and write SLAs on dedicated tiers.

X: C=Add partitions: partitions provide storage and indexing throughput, not redundancy, so adding them never creates SLA coverage.
D=Two replicas: two replicas cover only the query SLA; the indexing SLA needs three replicas, not more partitions.
E=Six partitions: each partition holds a slice of the index, not a full copy, so partitions can't take over queries for each other.
T: SLA coverage in Azure AI Search comes from replicas: two for queries, three for queries plus indexing; partitions add storage, not availability.

@ AI-103 D5 T5.1 advanced tradeoff
S: A search team must cut the memory used by an HNSW vector field of 1,536-dimension float32 embeddings by about four times. Search quality must stay close to today's, so results should be rescored with full-precision vectors, and the team accepts that disk usage will not shrink much. Which compression configuration fits these constraints?
A: Scalar quantization to int8 with rescoring enabled and rescoreStorageMethod set to preserveOriginals, plus oversampling at query time
B: Scalar quantization to int8 with rescoreStorageMethod set to discardOriginals, so rescoring uses the dot product of the stored codes
C: Binary quantization with discardOriginals and no oversampling, because binary codes keep full precision for the rescoring step
D: Exhaustive KNN with scalar quantization and oversampling, because exhaustive search rescores every candidate with original vectors
K: A
G: ## Quantization options in Azure AI Search
- **Scalar quantization** (`int8`): each float becomes an 8-bit code, about **4x** smaller vector index.
- **Binary quantization**: each component becomes 1 bit, up to about **28x** smaller (up to 96% reduction); best above 1,024 dimensions.
## Rescoring and what it needs
Rescoring offsets lossy compression: the query **oversamples** (`k x oversampling` candidates), then rescores them.
- Scalar quantization rescoring "requires the availability of the original full precision vectors": `rescoreStorageMethod: preserveOriginals`.
- Binary quantization can rescore with originals (`preserveOriginals`) **or** with the binary dot product (`discardOriginals`).
- Setting `discardOriginals` with scalar quantization prevents `enableRescoring` and `defaultOversampling`.
- Only **HNSW** allows rescoring; exhaustive KNN scans all vectors, so oversampling and rescoring don't apply.
## Example
`"kind": "scalarQuantization", "rescoringOptions": {"enableRescoring": true, "defaultOversampling": 10, "rescoreStorageMethod": "preserveOriginals"}`; a query with `k=5` considers 50 candidates.
W: int8 with preserveOriginals: int8 gives the fourfold memory cut, and keeping the originals allows full-precision rescoring of oversampled candidates, at the cost of disk space the team accepts.
X: B=int8 with discardOriginals: scalar rescoring needs the original vectors; discardOriginals disables rescoring for scalar quantization.
C=Binary with discardOriginals: binary codes are 1-bit approximations, not full precision, and the memory cut far exceeds the target with more quality risk.
D=Exhaustive KNN: exhaustive search doesn't support rescoring or oversampling, and it doesn't use the in-memory HNSW index the team is shrinking.
T: Scalar int8 quantization cuts vector memory about fourfold; keep preserveOriginals when you want full-precision rescoring.
