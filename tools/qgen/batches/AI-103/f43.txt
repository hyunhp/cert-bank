@ AI-103 D3 T3.3 advanced troubleshooting
S: An insurer runs a custom Content Understanding analyzer based on prebuilt-image on accident-scene photos. For some photos with injured people, the operation status is Succeeded but several generated fields are empty, and result.warnings contains HarmfulContentFiltered. How should the developer interpret and handle these results?
A: Image analyzers filter photos of injuries by design; rebuild the analyzer on prebuilt-document so guardrails stop applying to these accident-scene photos
B: Succeeded means the fields were evaluated and the photos simply lack the values; mark the empty fields as not applicable and pass the results to the claims workflow
C: The analyzer's own safety setting in its fieldSchema rejected the photos; add a safetyLevel property set to off on the affected fields so the model fills them again
D: The guardrail on the analyzer's model deployment suppressed field values for content at or above its blocking level, so route these photos to human review
K: D
G: ## Guardrails inside Content Understanding
Content Understanding uses generative models through **model deployments in your Foundry resource**. The **guardrails assigned to those deployments** check the content, and depending on the action and severity threshold they can:
- add a **warning** to `result.warnings`,
- **suppress** generated field values (fields empty or absent),
- or stop the operation, with a top-level `error`.
## Warning codes
- `HarmfulContentDetected`: potentially harmful content was found; route the result to human review.
- `HarmfulContentFiltered`: fields were filtered because of harmful content; don't assume all requested fields are present.
`Succeeded` doesn't guarantee that every field has a value, so always inspect warnings, and don't parse the warning `message` as a stable contract (use `code` and `target`).
## Changing the behavior
- Raise the blocking threshold of the relevant control in the deployment's guardrail (for example block only High), or
- with modified-guardrails approval, set the control to **Annotate** so warnings are kept but fields aren't suppressed, combined with human review.
## Example
`{"status": "Succeeded", "result": {"warnings": [{"code": "HarmfulContentFiltered", "target": "Result.Contents[0]"}]}}` -> send the claim photo to an adjuster queue.
W: Deployment guardrail suppressed fields: Learn states that guardrails on the analyzer's model deployment can suppress field values while the operation still succeeds, and that HarmfulContentFiltered means fields were filtered, so these results need human review.
X: A=Switch to prebuilt-document: the guardrail belongs to the model deployment, so every analyzer type that calls it is checked, and a document base analyzer is the wrong base for photos.
B=Trust Succeeded: Learn warns that Succeeded doesn't guarantee every field has a value, and HarmfulContentFiltered says the empty fields were suppressed, not missing from the photo.
C=Safety setting in the fieldSchema: analyzers have no per-field safety switch; the controls live in the guardrail assigned to the Foundry model deployment the analyzer calls.
T: In Content Understanding, check result.warnings even when the status is Succeeded: HarmfulContentFiltered means the deployment's guardrail suppressed fields, so route the item to review.

@ AI-103 D2 T2.3 applied use-case
S: A newsroom tool asks a non-reasoning model, in one prompt, to fact-check a 2,000-word article and propose search queries. Results are vague and skip many claims. Using techniques from Microsoft's prompt engineering guidance, how should the developer restructure the work?
A: Ask the model to pick the three most interesting claims, because models fact-check best when they choose their own scope
B: Raise the maximum output tokens and keep the single prompt, because vague results mean the model ran out of room
C: Summarize the article into a short bulleted list first and fact-check that summary so each request uses fewer tokens
D: Break the task down: first have the model list each factual claim, then generate one search query per listed claim
K: D
G: ## Break the task down
Learn's prompt engineering article states that LLMs often perform better when a task is **broken into smaller steps**. Its example is exactly this scenario: instead of "fact-check this paragraph," the prompt first asks the model to **extract factual claims**, then to **issue search queries** to verify them, using clear section headers such as `FACTUAL CLAIMS` and `QUERIES` to separate the steps.
## Why it works
Each step has one clear job and a defined output. The extraction step produces a list the next step can work through, so claims aren't skipped. The guidance notes that for "a larger piece of text with many factual claims, breaking the task down can make a significant difference."
## Related techniques
- **Clear syntax**: separators and headings make intent explicit and outputs easier to parse.
- **Affordances**: pass the real search results back into the next prompt so the model checks claims against evidence.
- **Chain of thought**: a variation where the model works step by step within one reply (non-reasoning models only).
W: Break the task down: separating claim extraction from query generation gives each step a clear, checkable output and stops the model from skipping claims in a long article.
X: A=Let the model choose three claims: narrowing scope by the model's preference leaves most claims unchecked, which defeats a fact-checking tool.
B=More output tokens: the replies aren't truncated, they're unfocused; more room doesn't add structure.
C=Summarize first: a summary drops detail, so specific claims (numbers, names, dates) can disappear before they are checked.
T: For multi-part tasks, split the work into steps with defined outputs, each feeding the next.

@ AI-103 D2 T2.3 applied definition
S: A team moves a ticket-triage app from the Chat Completions API to the Responses API in Microsoft Foundry. In the old code, the JSON Schema for structured outputs was passed in response_format. Where does the schema go in a Responses API request?
A: Under text.format, with type, name, schema and strict set as sibling properties of format in the Responses API request body
B: In the deployment's guardrail settings in the Foundry portal, which apply the schema to requests made to that model deployment
C: In a tools entry of type function with strict set to true, because the Responses API takes output schemas as function definitions
D: In the instructions string as a pasted JSON Schema, because the Responses API reads output formats from the instructions text
K: A
G: ## Same feature, two request shapes
Both the Chat Completions API and the Responses API support structured outputs, but they put the schema in different places:
- **Chat Completions**: `response_format` → `{"type": "json_schema", "json_schema": {..., "strict": true}}`
- **Responses API**: `text.format` → `{"type": "json_schema", "name": "ticket", "schema": {...}, "strict": true}`
Learn's Responses example says to "set type, name, schema, and strict as sibling properties of format."
## Why it matters when migrating
Copying the old `response_format` block into a Responses request doesn't apply the schema, because that API reads it from `text.format`. Function calling is a separate use: a function tool with `strict: true` constrains the **arguments** the model generates for your tool, not the final reply.
W: text.format: the Responses API defines the JSON Schema under text.format with type, name, schema and strict as siblings, which is the direct replacement for response_format.
X: B=Guardrail settings: guardrails hold safety controls for harm categories and attacks. A deployment has no setting that stores an output schema.
C=Function tool: strict function tools constrain tool-call arguments. Using a fake tool to shape the final answer is a workaround, not where the Responses API expects an output schema.
D=Schema in instructions: putting a schema in the prompt is only guidance; it doesn't switch on schema enforcement, and the API has a dedicated field for it.
T: Structured outputs: response_format in Chat Completions, text.format in the Responses API.

- `tool_choice` set to a named function forces that function; `"none"` forces a user-facing message.

G: ## The default guardrail

@ AI-103 D1 T1.1 applied use-case
S: A manufacturer's search team already maintains an Azure AI Search index of 200,000 maintenance manuals with vector fields, a semantic configuration and filterable plant and model fields that a nightly indexer refreshes. A new Foundry agent must answer technicians' questions from this content with citations. Which integration should the developer choose?
A: The function calling tool, with the client app downloading the manuals into the prompt so the model reads their full text on each turn.
B: The code interpreter tool, loading the manuals into a sandbox session so the agent scans the files with Python code on each question.
C: The file search tool, re-uploading the manuals into a new vector store so the agent owns a separate copy of the manual content.
D: The Azure AI Search tool, connected through a project connection to the existing index, so the agent queries it and cites the results.
K: D
G: ## Reuse the index you already have
The **Azure AI Search tool** in Foundry Agent Service connects an agent to an **existing** Azure AI Search index. The agent's model generates answers with **inline citations** from the retrieved documents.
- You connect the index through a **project connection**; for private networking, use the project's managed identity (key-based authentication is not supported with private virtual networking).
- The tool's `query_type` defaults to `vector_semantic_hybrid`; it also supports `simple`, `vector`, `semantic` and `vector_simple_hybrid`, so it can use the vectors and semantic configuration the search team already built.
- Filters and index design stay under the search team's control.
## When file search is better
File search is for documents users bring into a conversation or small sets you upload; it creates its own vector store. Duplicating a curated 200,000-document index into it would lose the team's schema, filters and refresh process.
W: Azure AI Search tool: it queries the index the search team already maintains, uses its hybrid and semantic setup, keeps the nightly refresh and returns cited answers, with no second copy of the content.
X: A=Function calling with manuals in the prompt: no context window holds 200,000 manuals, and stuffing text into prompts replaces retrieval with cost and truncation.
B=Code interpreter: it runs Python in a sandbox for analysis and charts; scanning 200,000 manuals per question is slow and costly, and it is not a retrieval service.
C=File search with re-uploaded manuals: copying the corpus into a separate vector store duplicates storage and cost, loses the curated fields and filters, and drifts from the index the nightly indexer refreshes.
T: When a maintained Azure AI Search index already exists, connect the agent to it with the Azure AI Search tool instead of copying content into file search.
