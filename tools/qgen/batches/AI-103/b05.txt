S: A Python service calls a gpt-5-mini deployment through the v1 endpoint with keyless authentication. It creates the client once at startup with `OpenAI(base_url="https://contoso-ai.openai.azure.com/openai/v1/", api_key=token_provider())`. Requests succeed for a while, then every call returns 401 Unauthorized until the service restarts. What should the developer change?
A: Pass the token provider function itself as `api_key=token_provider`, so the OpenAI client requests a fresh Microsoft Entra token whenever the old one expires
B: Switch the client class to `AzureOpenAI()` with a dated `api_version`, because the plain `OpenAI()` client can't send Microsoft Entra tokens to Azure
C: Change the token scope in `get_bearer_token_provider` from `https://ai.azure.com/.default` to the resource's own endpoint URL with `/.default` added
D: Assign the service's managed identity the Foundry Account Owner role, because the Foundry User role only issues tokens that last a few minutes
K: A
G: ## Keyless authentication with the v1 endpoint
With the v1 Azure OpenAI API you use the standard `OpenAI()` client and point `base_url` at `https://<resource>.openai.azure.com/openai/v1/`. For Microsoft Entra ID (keyless) authentication, Learn shows this pattern:
`token_provider = get_bearer_token_provider(DefaultAzureCredential(), "https://ai.azure.com/.default")`
`client = OpenAI(base_url=..., api_key=token_provider)`
## Function versus string
`get_bearer_token_provider` returns a **function**. Learn's v1 article says to set `api_key` to `token_provider` "to enable automatic retrieval and refresh of an authentication token instead of using a static API key". The v1 API added automatic token refresh to the `OpenAI()` client, which previously needed the `AzureOpenAI()` client.
- `api_key=token_provider`: the client calls the function when it needs a token, so expired tokens are replaced.
- `api_key=token_provider()`: the function runs once at startup and the client keeps that single token string. Entra access tokens expire, and every later call fails with 401 until a restart gets a new token.
## Example
A service started at 08:00 works until its token expires, then fails on every request. Passing the callable fixes it without any role or endpoint change.
W: Pass the callable: handing the client the provider function lets it fetch and refresh Entra tokens on demand, which is exactly what stops the 401 errors that begin once the first token expires.
X: B=Go back to AzureOpenAI(): the v1 API was designed so the plain `OpenAI()` client handles Entra tokens and refresh; returning to dated API versions doesn't address the static token string.
C=Change the scope: Learn's samples use the `https://ai.azure.com/.default` scope for this endpoint. The first calls succeed, which shows the scope is accepted; the failure starts later because the token isn't refreshed.
D=Bigger role: role assignments decide what an identity may do, not how long its tokens live. Foundry User is the role Learn recommends for day-to-day development, and a higher role wouldn't refresh a cached string.
T: For keyless auth with the OpenAI client, pass `api_key=token_provider` (the function), not `token_provider()` (a single token that expires).

@ AI-103 D2 T2.1 applied troubleshooting
S: A research tool's privacy policy sets `store=False` on every Responses API request so that the service keeps no response data. A developer adds `background=True` to a multi-minute o3 analysis request, and the request is rejected. Which change lets the task run in background mode while keeping stored data to a minimum?
A: Send this request with `store=True`, then delete the stored response by its ID as soon as the app has retrieved the final output
B: Keep `store=False` and also set `stream=True`, because a streamed background request can report progress without a stored response
C: Keep `store=False` and pass `previous_response_id`, so the service rebuilds the background task from an earlier stored turn
D: Keep `store=False` and move the request to a Global Batch deployment, because background mode runs only on batch deployments
K: A
G: ## Background mode needs a stored response
Background mode runs long Responses API tasks asynchronously: the request returns at once with a response ID and a `queued` status, and the app polls that ID until the task reaches a terminal state. Polling only works if the service keeps the response object, so Learn lists this limitation: "Background mode requires store=true. Stateless requests are not supported."
## Keeping stored data small
- By default, stored response data is retained for 30 days.
- Learn shows how to delete a stored response by ID.
- A privacy-minded design therefore stores only the background requests, retrieves the result, and deletes the response right away. Interactive turns can keep using `store=False`.
## Example flow
1. `job = client.responses.create(model="o3-analysis", input=task, background=True, store=True)`
2. Poll `client.responses.retrieve(job.id)` while the status is `queued` or `in_progress`.
3. Save the output in the app, then delete the stored response by its ID.
W: store=True, then delete: background mode can't run statelessly, so the request must be stored; deleting the response by ID after retrieval keeps the data held by the service as short-lived as possible.
X: B=Add streaming: streaming a background response also needs `background` and a stored response; the store requirement applies whether or not the request streams.
C=previous_response_id: chaining reads an earlier stored response and doesn't lift the rule that the background request itself must be stored.
D=Global Batch deployment: batch is a separate deployment type for large asynchronous job files; background mode is a request option of the Responses API with reasoning models such as o3.
T: Background mode requires `store=true`; to limit retained data, delete the stored response by ID once the result has been collected.

G: ## One endpoint, two inference APIs
The v1 endpoint of a Foundry resource (`https://<resource>.openai.azure.com/openai/v1/`) serves Azure OpenAI models **and** other Foundry Models sold by Azure. It exposes two inference APIs:
- **Responses API** (`client.responses.create`): the newer API with the latest features such as stateful chaining and built-in tools.

Learn's endpoint article notes that the Responses API works with Azure OpenAI models and with models sold by Azure that support it (it names DeepSeek, Llama and Grok). W: Chat Completions on the same client: the error is specific to the Responses API, and Learn's documented fallback is Chat Completions on the same v1 endpoint, which most models sold by Azure support.

B=Add api-version: the v1 route uses implicit versioning, and no version string adds Responses support to a model that lacks it.
D=Project endpoint: the project endpoint adds Foundry features such as agents and evaluations; Learn's fix for 400 Model not supported is Chat Completions on the same v1 endpoint, not a different route.
T: If a deployment returns 400 Model not supported on the Responses API, call it with Chat Completions on the same v1 endpoint.

@ AI-103 D2 T2.1 applied use-case
S: A support chatbot uses the Responses API. After the first turn, the developer wants the model to keep the earlier context while sending as little data as possible on each later request. How should the second request be built?
A: Send the full transcript again in `input` and also set `previous_response_id`, so the model receives the history twice and weights it more strongly
B: Store the transcript in a project connection and pass the connection name in `instructions`, which the service reads before generating the reply

K: C
G: ## State in the Responses API
Learn describes the Responses API as producing **stateful, multi-turn responses**. Responses are stored by the service (by default for 30 days), so a later request can refer to an earlier one.
## Two ways to carry context
- **`previous_response_id` chaining**: "Chain turns by passing the previous response ID to `previous_response_id`." Each later request sends only the new user input; the service supplies the earlier turns.
- **Manual chaining**: the app keeps a list of input items, appends `response.output` and the next user message, and sends the whole list each time.
## Example
`first = client.responses.create(model="support-chat", input="My router keeps rebooting.")`
`second = client.responses.create(model="support-chat", previous_response_id=first.id, input="It started after the firmware update.")`
Learn's compaction section repeats the rule for this pattern: with `previous_response_id`, "pass only the new user message on each turn and carry the latest response ID forward."
W: New message plus previous_response_id: the service already holds the earlier response, so linking to its id preserves context while each request carries only the new turn.
X: A=Transcript and id together: this duplicates history the service already has, raising token use without improving recall, which is the opposite of the goal.
B=Transcript in a connection: connections store how a project authenticates to other resources; the Responses API doesn't read conversation history from them.
D=Bigger first output: output token limits cap how much the model writes; they don't create memory for later requests.
T: With the Responses API, continue a conversation by sending only the new input and `previous_response_id` set to the last response's id.

@ AI-103 D2 T2.1 applied use-case
S: An insurer's claims assistant calls the Responses API. The architects don't want later turns to depend on responses held by the service, so the app keeps the conversation itself. Which approach carries context to the next turn correctly?
A: Append the items in `response.output` to the app's input list, add the new user message, and send the whole list as `input` on the next request
B: Copy only `response.output_text` into the `instructions` field of the next request, because instructions are the only place earlier turns are read
C: Send the new user message alone, because the model keeps a private memory of each caller's earlier requests for the life of the deployment
D: Pass the earlier response id as `previous_response_id` and leave `input` empty, so the service rebuilds the conversation on its side
K: A
G: ## Manual chaining
Learn shows two ways to chain Responses API turns. Besides `previous_response_id`, you can "manually carry forward output items in the next request":
`inputs = [{"type": "message", "role": "user", "content": "..."}]`
`response = client.responses.create(model=deployment, input=inputs)`
`inputs += response.output`
`inputs.append({"role": "user", "type": "message", "content": "next question"})`
`second = client.responses.create(model=deployment, input=inputs)`
## Why choose it
- The app owns the full history, so it can trim, redact or persist it in its own store.
- Later turns don't rely on the service's stored response objects.
- Learn's compaction guidance calls this **stateless input-array chaining**, the alternative to `previous_response_id` chaining.
## What a model doesn't do
The model itself has no memory between calls. Anything it should know about earlier turns must be in the request or linked through a stored response.
W: Append output items and the new message: the app sends the full item history each time, so the model has the earlier turns without relying on stored responses.
X: B=Output text in instructions: instructions carry developer guidance; copying just the final text loses the earlier user turns and any tool call items in the output.
C=Model memory: models are stateless between requests; without history in the input or a linked response, the next turn starts from nothing.
D=previous_response_id with empty input: this is the service-side chaining the architects want to avoid, and a turn still needs the new user message.
T: For app-managed state, append `response.output` and the next user message to the input list and send the list every turn.

G: ## How tool_choice works
When a request defines function tools, `tool_choice` decides whether the model may, must or must not call them. Learn's function calling article describes three settings:
- `"auto"` (the default): "the model decides on its own if it should call a function and if so which function to call". A plain-text answer is allowed.

C: The `deployment_name` of a GPT model deployment to act as the LLM judge, which AI-assisted evaluators require and F1 doesn't
D: A higher pass threshold than the default of 3, because coherence can't start when its threshold is lower than the F1 threshold
K: C
G: ## Two kinds of built-in evaluators
- **AI-assisted (LLM-as-judge)**: Coherence, Fluency, Relevance, Groundedness, Retrieval, Similarity. A judge model reads the inputs and scores them on a 1-5 scale. Learn lists `deployment_name` as a **required parameter**; general-purpose evaluator guidance suggests gpt-5-mini as a good balance of performance and cost.
- **Algorithmic**: F1, BLEU, GLEU, ROUGE, METEOR. They compute token or n-gram overlap and need no judge model; F1, BLEU, GLEU and METEOR list no required parameters (ROUGE only needs a `rouge_type`).
## Cloud evaluation setup
The cloud evaluation article sets shared variables: `AZURE_AI_PROJECT_ENDPOINT` and `AZURE_AI_MODEL_DEPLOYMENT_NAME` ("the model deployment used by AI-assisted evaluators"), then creates `AIProjectClient` and its OpenAI client. A criterion for an AI-assisted evaluator looks like:
`{"type": "azure_ai_evaluator", "name": "coherence", "evaluator_name": "builtin.coherence", "initialization_parameters": {"deployment_name": model_deployment}, "data_mapping": {"query": "{{item.query}}", "response": "{{item.response}}"}}`
## Why F1 still worked
F1 only needs `ground_truth` and `response`, so it ran without a judge.
W: Judge deployment name: coherence is scored by an LLM judge, and without `deployment_name` in its initialization parameters the evaluator has no model to call.
X: A=ground_truth column: coherence needs query and response (or messages); ground truth is for Similarity and the NLP metrics.
B=Application Insights: connecting it lets results flow to monitoring, but it isn't required for an evaluator to run.
D=Threshold: thresholds decide pass or fail after scoring; they don't prevent an evaluator from starting.
T: AI-assisted evaluators need a judge model `deployment_name`; algorithmic metrics such as F1 and BLEU don't.

G: ## What a connection is
Learn: "Connections let you authenticate to Microsoft and other resources within your Foundry projects." Azure AI Search, Azure Storage, Application Insights, Azure Key Vault and other services can be connected. Connection details are stored in a managed Key Vault unless you bring your own.
## Reading connections from code
The Azure AI Projects client library (part of the Foundry SDK) lets you "enumerate connected Azure resources in your Foundry project using `.connections` operations", alongside `.deployments`, `.datasets` and `.indexes`. Learn's SDK overview places "listing connections" among the project client's Foundry-native operations.
## Example flow
1. Configure only `FOUNDRY_PROJECT_ENDPOINT` per environment.
2. `project = AIProjectClient(endpoint=..., credential=DefaultAzureCredential())`
3. Use `project.connections` to find the Azure AI Search connection and read its target endpoint.
4. Create the `SearchClient` with that endpoint and a keyless credential.
Each environment's project points to its own search service, so the code stays the same.
W: Project connections: the project client's connections operations expose the connected search resource, so the app needs only the project endpoint per environment.
X: B=models.list on v1: that lists models available to the resource; search services aren't models and aren't returned.
C=Deployments list: deployments describe models (name, version, capacity, guardrails), not search indexes.
D=Resource Manager query: picking the first search service in a subscription is fragile and ignores which service the project actually uses.
T: Let apps discover connected resources such as Azure AI Search through `AIProjectClient` connections operations, configured with just the project endpoint.

S: A developer moves a Python app from the `AzureOpenAI()` client with a dated `api_version` to the v1 Azure OpenAI API, keeping API key authentication. Which TWO changes are part of this move? (Select TWO)

E: Send the API key as a project connection secret, because the v1 API no longer accepts keys passed directly to the client
K: A,B
G: ## The v1 Azure OpenAI API
Since August 2025, you can opt in to the **v1** API. Learn lists what it changes:
- "`OpenAI()` client is used instead of `AzureOpenAI()`."
- "Pass the Azure OpenAI endpoint to `base_url` and append `/openai/v1` to the endpoint address."
- "`api-version` is no longer a required parameter with the v1 GA API."
Preview features are opted into with feature-specific headers or path segments instead of changing API versions.
## Before and after
Before: `AzureOpenAI(azure_endpoint=..., api_key=..., api_version="2024-xx-xx")`
After: `OpenAI(api_key=os.getenv("AZURE_OPENAI_API_KEY"), base_url="https://<resource>.openai.azure.com/openai/v1/")`
The request still names the **deployment** in `model`. Keys still work; with Entra ID you pass a token provider as `api_key` instead.
W: A=OpenAI() client: the v1 API is designed for the standard OpenAI client, so `AzureOpenAI()` isn't needed anymore.
B=/openai/v1/ and no api_version: the v1 route uses implicit versioning, so the base URL changes and the dated version parameter goes away.
X: C=Catalog model name: the `model` field still takes the deployment name on the v1 endpoint.
D=Project endpoint: the v1 API lives on the resource endpoint `https://<resource>.openai.azure.com/openai/v1/`; the project endpoint is for the Foundry SDK.
E=Key as connection secret: the v1 examples pass the API key straight to `OpenAI(api_key=...)`; connections aren't involved.
T: Moving to v1 means `OpenAI()` with `base_url=https://<resource>.openai.azure.com/openai/v1/` and no `api_version`, still naming the deployment in `model`.
