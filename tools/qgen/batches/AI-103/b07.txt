@ AI-103 D2 T2.3 applied comparison
S: A legal team uses a non-reasoning chat model deployment in Microsoft Foundry to draft clause summaries for contracts. Reviewers complain that the same clause gets differently worded summaries on every run, sometimes with invented qualifiers. The developer currently sends temperature 1.2 and top_p 0.9. Following Microsoft's prompt engineering guidance, what should the developer change?
A: Lower the temperature to a small value such as 0.2 and leave top_p at its default, changing only one of the two sampling parameters at a time
B: Lower both temperature and top_p to 0 at the same time, because the two parameters must always be moved together to have any effect on output
C: Raise top_p to 1.0 while keeping temperature at 1.2, so the model considers every possible token and settles on the most likely wording
D: Keep the sampling values and raise the maximum output tokens instead, because short output limits are what make the summaries vary between runs
K: A
G: ## Two knobs that control randomness
For non-reasoning chat models, two request parameters change how the next token is sampled:
- **temperature** (0 to 2): higher values such as 0.7 make output more random and divergent; lower values such as 0.2 make it more focused and concrete.
- **top_p** (nucleus sampling): also controls randomness, but by limiting sampling to the most probable tokens whose probabilities add up to the given share.
## Microsoft's guidance
Learn's prompt engineering article recommends a high temperature for creative work such as fiction and "a much lower temperature" for something like a legal document. It also gives a general rule: **alter one of these two parameters at a time, not both**, so you can tell which change produced which effect.
## Example
`temperature: 0.2` with top_p left at its default gives repeatable, concrete summaries; a story generator might use 0.9.
W: Lower temperature only: 1.2 is a creative setting. Dropping temperature to a low value makes summaries focused and consistent, and changing one parameter at a time follows the documented recommendation.
X: B=Both to 0 together: the guidance is the opposite, change one parameter at a time. The two are not required to move together; each affects sampling on its own.
C=Raise top_p to 1.0: a higher top_p widens the pool of candidate tokens, which adds variety. Combined with a high temperature it makes the drift worse, not better.
D=More output tokens: the maximum token setting only limits length and can truncate a reply. It doesn't change how random the wording is.
T: For factual or legal text, lower the temperature (or top_p, but not both at once); keep high values for creative tasks.

@ AI-103 D2 T2.3 applied comparison
S: A procurement team wants a Foundry solution that assesses each new supplier application from four angles: financial health, security posture, legal terms and sustainability. Each check uses its own specialist agent and tools, no check needs another check's output, and the combined verdict is needed within minutes. Which orchestration pattern fits best?
A: Sequential orchestration that passes the application through the four agents in a fixed order, so each agent refines the previous agent's finished assessment
B: Concurrent orchestration that sends the same application to all four agents in parallel and then aggregates their independent results into one verdict
C: Handoff orchestration in which the financial agent starts and transfers full control to whichever specialist it decides should handle the application next
D: Magentic orchestration in which a manager agent builds and keeps adapting a task ledger, because the four checks have no predetermined solution path
K: B
G: ## Multiagent orchestration patterns
Microsoft's AI agent orchestration patterns guide (Azure Architecture Center) describes five patterns:
- **Sequential**: a linear pipeline; each agent processes the previous agent's output.
- **Concurrent**: agents work **independently and in parallel on the same input**; also called fan-out/fan-in or scatter-gather.
- **Group chat**: agents contribute to a shared thread run by a chat manager (including maker-checker loops).
- **Handoff**: one active agent at a time; agents decide when to transfer control.
- **Magentic**: a manager agent builds and adapts a task ledger for open-ended problems.
## When concurrent orchestration fits
Learn lists tasks that can run in parallel, tasks that benefit from **multiple independent perspectives or specializations**, and **time-sensitive scenarios where parallel processing reduces latency**. Its example sends one stock ticker to fundamental, technical, sentiment and ESG agents at the same time and combines their results into one recommendation.
## Aggregating the results
Choose an aggregation strategy that fits the task: voting or majority rule for classification, weighted merging for scored recommendations, or a model-written summary that reconciles the findings. Plan for contradictory results, and remember that parallel agents use more model quota at once.
## Applied here
Financial, security, legal and sustainability checks are independent views of the same application, so they run side by side and an aggregator produces the verdict.
W: Concurrent with aggregation: the four checks are independent specialist views of the same input, and running them in parallel cuts total run time, which is exactly the documented use of concurrent orchestration.
X: A=Sequential: it suits stages that build on each other; here no check needs another's output, so a fixed chain only adds the four run times together.
C=Handoff: it gives full control to one agent at a time and suits cases where the right specialist emerges during processing; every application needs all four checks.
D=Magentic: it is for open-ended problems without a predetermined plan; four known checks don't need a manager that keeps replanning, which adds cost and time.
T: Independent analyses of the same input that must finish quickly call for concurrent (fan-out/fan-in) orchestration with a defined aggregation step.

S: A developer sends a JSON Schema with strict set to true for structured outputs. The object has properties name, email and phone; only name and email are listed in "required" because phone is optional, and the object doesn't set additionalProperties. The request is rejected as an invalid schema. Which TWO changes make the schema valid for structured outputs? (Select TWO)
A: Set "additionalProperties": false on the object, because structured outputs need every object to forbid keys that the schema doesn't define
B: List phone in "required" as well and give it the type ["string", "null"], so the model can return null when no phone number exists
C: Replace the object with an anyOf at the root level, because a root anyOf lets the model choose freely between a version with and without phone
D: Add "minLength": 7 and a "pattern" regular expression to phone, because strict mode needs every string property to have explicit limits
E: Remove strict from the request and keep the schema as it is, because strict mode is only supported for function calling and not response formats
K: A,B
G: ## Structured outputs use a subset of JSON Schema
Learn's "JSON Schema support and limitations" section lists the rules a strict schema must follow:
- **All fields must be required.** Every property goes in `required`. To make a field effectively optional, use a union with null: `"type": ["string", "null"]`.
- **Always set `additionalProperties: false`** on objects, so the model can't add keys that aren't defined.
- **Root objects can't be `anyOf`.** anyOf is allowed in nested schemas only.
- Some keywords are **unsupported**, for example `minLength`, `maxLength`, `pattern` and `format` for strings, and `minimum`/`maximum` for numbers.
- Nesting is limited (up to 100 object properties in total and five levels).
## Example
`{"type":"object","properties":{"name":{"type":"string"},"email":{"type":"string"},"phone":{"type":["string","null"]}},"required":["name","email","phone"],"additionalProperties":false}`
W: A=additionalProperties false: Learn says to set it to false on every object to use structured outputs; leaving it unset makes the schema invalid.
B=Required plus null union: every property must be listed as required; the documented way to model an optional value is a type union with null, so phone comes back as null when missing.
X: C=Root anyOf: the limitations explicitly say root objects can't be of the anyOf type, so this creates a new error.
D=minLength and pattern: these string keywords are on the unsupported list for structured outputs; adding them makes the schema fail rather than pass. Validate such rules in application code.
E=Drop strict: strict is supported for response formats as well as function calling, and removing it gives up the schema guarantee the team wants.
T: Strict structured outputs need every property in required (nullable for optional) and additionalProperties false on every object.

Reasoning models generate hidden **reasoning tokens** before the visible answer. Learn's reasoning article lists parameters they don't support (all except one specific model): `temperature`, `top_p`, `presence_penalty`, `frequency_penalty`, `logprobs`, `top_logprobs`, `logit_bias` and `max_tokens`.

D=Think step by step: reasoning models already reason internally; Learn notes chain-of-thought prompting applies only to non-reasoning models.
E=Penalty parameters: presence_penalty and frequency_penalty are themselves unsupported on reasoning models; sending them adds errors.
T: On reasoning models, drop temperature/top_p/penalties and max_tokens; use max_completion_tokens (or max_output_tokens) and reasoning_effort.

Learn's prompt engineering article notes that models can be **susceptible to recency bias**: information at the end of the prompt can influence the output more than information at the beginning. D=One-word instruction: being less specific contradicts the "be specific" practice; the problem is the instruction's position, not its length.
T: When a long input buries the instruction, repeat it after the content and prime the output with a cue.

S: Every request in a support app starts with the same 3,000-token system message and product policy, followed by the customer's question. What should the developer do?

G: ## How prompt caching works
Prompt caching reduces latency and cost for longer prompts that have **identical content at the beginning**. The service keeps a temporary cache of processed input token computations, so a matching prefix isn't reprocessed. It doesn't change the model's output.
## Requirements from Learn
- The prompt is at least **1,024 tokens** long.
- The **first 1,024 tokens must be identical** across requests.
- Cache hits appear as `cached_tokens` under `prompt_tokens_details` in the response usage.
For supported models, cache reads are billed at a discount on input tokens.
## The common mistake
A value that changes per request (timestamp, user name, request ID) at the top of the prompt makes every prefix different, so the cache never matches. Put stable content first and variable content last.

B=Separate policy request: each request is independent; a model doesn't remember an earlier call, so the policy must still be in the prompt.
D=Short max_completion_tokens: caching depends on the input prefix, not on the output limit.

@ AI-103 D2 T2.3 advanced use-case
S: A marketing app generates product descriptions that must pass brand rules (tone, banned claims, length). The team adds a second model call that reviews each draft and sends specific feedback back to the generator, which revises it. In testing, some drafts bounce back and forth for dozens of rounds. Which design matches the maker-checker pattern that Microsoft describes?
A: Let the generator review its own draft in the same call and approve it, because one model judging its own work avoids the extra review calls
B: Remove the review step and raise the generator's temperature instead, so later drafts differ enough from earlier ones to satisfy the rules

K: D
G: ## The maker-checker loop
Microsoft's AI agent orchestration patterns guide describes the **maker-checker loop**, also known as evaluator-optimizer, generator-verifier, critic loop or **reflection loop**:
- the **maker** creates or proposes something
- the **checker** evaluates it **against defined criteria**
- if there are gaps, the checker sends **specific feedback** back to the maker, which revises and resubmits
- the cycle repeats **until the checker approves the result or the orchestration reaches a maximum iteration limit**
## Why the limit matters
Without a cap, a draft that can't satisfy the checker loops forever and keeps consuming tokens. The same guide recommends iteration limits for single agents that loop through tool calls. Human reviewers can also act as checkers when a decision needs oversight.
## Example
Maker: "Write a 60-word description." Checker: "Fails rule 3: 'clinically proven' is a banned claim; 74 words." Loop stops after approval or, say, three rounds, then escalates.

X: A=Self-approval in one call: the pattern separates the roles so the checker evaluates independently against criteria; approving its own draft in the same call removes the check.
B=Higher temperature, no checker: randomness doesn't make drafts follow brand rules, and nothing verifies them anymore.
C=Always approve after round one: approval must depend on the criteria; auto-approval lets drafts that still break rules through.
T: Reflection (maker-checker) loops need explicit acceptance criteria, specific feedback and a maximum iteration limit.

G: ## Chain-of-thought prompting (non-reasoning models)
Learn's prompt engineering article describes **chain of thought** as a variation of breaking the task down: the prompt tells the model to proceed **step by step** and present all the steps. This "reduces the possibility of inaccuracy of outcomes and makes assessing the model response easier." Learn's example ends with a fixed format, `ANSWER is: <name>`, so code can pick out the final answer while reviewers read the steps.

G: ## Evaluate model router against your baseline
Model router is a drop-in deployment that picks an underlying model per request. Learn says "evaluation remains important": before production traffic, **benchmark it against your current model for response quality, estimated cost, and latency**, then decide whether to keep the configuration, change one routing lever (routing mode or model subset), or keep a direct deployment for part of the workload.
## See which model answered
- The standard response includes a **`model`** field that identifies the underlying model that served the request (for example a mini model for a simple prompt).
- In the playground, each response shows which model the router selected.
- Optional per-request metadata with the routing trace, attempts and fallback (`model_selection_details`) is a **preview** feature enabled with a feature header.
## Why quality can differ
Balanced mode considers models within a small quality range of the best model for that prompt and chooses the most cost-effective one, so quality is comparable, not identical; that is why evaluation is needed.
