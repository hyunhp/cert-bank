@ AI-103 D5 T5.1 applied troubleshooting
S: A team built a chunked index in Azure AI Search with an indexer, a Text Split skill and an AzureOpenAIEmbedding skill. Indexing succeeds and the vector field is populated. When the app sends a vector query with "kind": "text" and the user's question, the request fails because the text can't be converted to a vector. What must the team add?
A: A vectorizer in the index's vectorSearch section that calls the same embedding deployment, referenced by a vector profile that is assigned to the vector field
B: A second AzureOpenAIEmbedding skill in the skillset that runs at query time and writes the embedded question into a temporary field of the index
C: A semantic configuration that lists the vector field as its content field, so the semantic ranker converts the query text into an embedding first
D: An indexer field mapping from the chunk text field to the vector field, so the search engine can look up a stored vector for the query string
K: A
G: ## Integrated vectorization has two halves
Integrated vectorization in Azure AI Search covers both directions of the pipeline:
- **Indexing**: an indexer runs a skillset. A chunking skill (Text Split or the Azure Content Understanding skill) splits content, and an **embedding skill** (for example AzureOpenAIEmbedding) turns each chunk into a vector.
- **Querying**: a **vectorizer** defined in the index schema turns the text of a query into a vector at query time.
Skills only run during indexing. Nothing in a skillset touches a query.
## How a vectorizer is wired in
1. Define the vectorizer in `vectorSearch.vectorizers` (for example `kind: azureOpenAI` with the deployment).
2. Reference it from a **vector profile** in `vectorSearch.profiles`, together with the algorithm (for example HNSW).
3. Set `vectorSearchProfile` on the vector field.
A query then sends `{"kind": "text", "text": "...", "fields": "contentVector"}` and the engine reads the vectorizer from the field's profile automatically. Learn's rule: the vectorizer must use the same embedding model as the skill that built the vectors.
W: Vectorizer on the field's profile: the vectorizer is the query-time counterpart of the embedding skill. Once the profile that references it is assigned to the vector field, text queries are vectorized by the service.
X: B=Second embedding skill: skills run only inside an indexer pipeline during indexing. A skill never runs for a search request, so it can't embed the user's question.
C=Semantic configuration: the semantic ranker reranks text results with language models and only reads text fields. It doesn't create embeddings and can't list a vector field as content.
D=Field mapping to the vector field: field mappings move source values into index fields during indexing. They don't give the query engine a way to turn new query text into a vector.
T: Embedding skills vectorize content at indexing time; a vectorizer on the field's vector profile vectorizes text queries at query time.

@ AI-103 D5 T5.1 advanced troubleshooting
S: A search index was built with chunks embedded by text-embedding-3-small through the AzureOpenAIEmbedding skill. To improve quality, a developer changes only the index's Azure OpenAI vectorizer to a text-embedding-3-large deployment. Vector queries now return errors or unrelated chunks. What is the correct fix?
A: Keep the new vectorizer and switch the vector algorithm from HNSW to exhaustive KNN, so every chunk is compared with the query vector and recall improves
B: Keep the new vectorizer and enable semantic ranker on the queries, so the reranking step promotes the relevant chunks to the top of the vector results
C: Use the same model on both sides: either point the vectorizer back to the small model, or change the skill and field dimensions and re-run indexing
D: Keep the new vectorizer and add the large model to the semantic configuration's keyword fields, so the two embedding spaces are aligned at query time
K: C
G: ## Vectors are only comparable inside one embedding space
An embedding model maps text to a point in its own vector space. Two models, even from the same family, produce vectors that are not comparable: they can differ in **dimensions** (text-embedding-3-small defaults to 1536, text-embedding-3-large to 3072) and in what each dimension means.
## Skill and vectorizer come as a pair
Azure AI Search pairs each embedding skill with a vectorizer:
- AzureOpenAIEmbedding skill and the Azure OpenAI vectorizer
- Custom Web API skill and the Custom Web API vectorizer
- AML skill and the Foundry model catalog vectorizer
Learn states that you must use the same embedding model for both, because the vectorizer creates query vectors that are compared with the vectors the skill stored.
## Changing models
To move to a new model, update the embedding skill, the vector field's `dimensions` and the vectorizer together, then rebuild the index so every chunk is re-embedded.
W: Same model at indexing and query time: the query vector must come from the model that produced the stored vectors. Either revert the vectorizer, or move the skill, field dimensions and vectorizer to the new model and re-index.
X: A=Exhaustive KNN: exhaustive search compares more vectors, but comparing vectors from two different models is meaningless no matter how many are scanned, and a dimension mismatch still fails.
B=Semantic ranker: semantic ranking reorders an initial result set. If the vector step returns the wrong chunks or errors out, the reranker has nothing useful to promote.
D=Model in the semantic configuration: a semantic configuration lists text fields (title, content, keywords) for the reranker. It has no setting that maps one embedding space to another.
T: Index and query vectors must come from the same embedding model; changing models means changing the skill, the field dimensions and the vectorizer together and re-indexing.

When a blob indexer opens a file (document cracking), it extracts the text layer into `/document/content`. A scanned PDF is just page images, so the text layer is empty and every downstream skill (chunking, embedding) receives nothing.
## Built-in OCR in an AI enrichment pipeline

E=Larger maximumPageLength: chunk size only matters once text exists. The chunks are empty because no text was extracted, not because they were cut too small.

@ AI-103 D5 T5.1 applied use-case
S: A parts distributor enriches product sheets in an Azure AI Search skillset. G: ## Built-in, custom and utility skills
Azure AI Search groups skills into three kinds:
- **Built-in skills** wrap a well-understood Azure capability (OCR, entity recognition, Azure OpenAI Embedding, GenAI Prompt, Azure Content Understanding).
- **Custom skills** run your own code outside the search service. The **Custom Web API** skill calls any HTTPS endpoint (often an Azure function); the **AML** skill calls a model in Foundry or Azure Machine Learning.
- **Utility skills** run inside the service (Text Split, Text Merge, Shaper, Conditional).
## The Custom Web API contract
The skill posts JSON with a top-level `values` array, at most `batchSize` records per call:
`{"values": [{"recordId": "0", "data": {"text": "..."}}]}`
The endpoint must answer with the same structure: one entry per `recordId` with a `data` object (plus optional `errors` and `warnings`). Outputs named in the skill definition then become enrichment nodes that later skills or output field mappings can use.
W: Custom Web API skill: this is the documented way to plug your own HTTPS code into a skillset; the indexer sends batches of records and maps the returned data back into the enrichment tree.
X: A=GenAI Prompt skill: this skill sends a prompt to a chat completion model. The model doesn't call the company's endpoint, so the deterministic lookup logic never runs.
B=Custom Entity Lookup: this skill matches text against a user-defined list of words and phrases. It can't execute normalization code that already lives in a function app.
C=Vectorizer pointing to the function: vectorizers turn query text into vectors at query time. They don't add enrichment fields to documents during indexing.
T: To run your own logic during indexing, call it from a Custom Web API skill that follows the values/recordId/data contract.

@ AI-103 D5 T5.1 applied use-case
S: A skillset splits each manual into chunks and embeds them. The team wants one search index where every search document is a chunk, and each chunk repeats the parent manual's title and URL so the RAG app can cite it. Parent-only documents must not appear in the index. How should they configure the skillset?

K: C
G: ## One-to-many indexing with index projections
Chunking turns one source document into many chunks. **Index projections**, defined in the skillset, control how those chunks become search documents:
- **Single index, repeating parent fields** (recommended for RAG): parent fields such as title and URL are copied into every chunk document, so all documents have one shape.
- **Single index, mixed shapes**: parents and chunks live side by side (default `includeIndexingParentDocuments`).
- **Separate indexes**: parents in one index, chunks in another; there are no query-time joins.
## Required pieces
- A chunk index with a key field (`Edm.String`, keyword analyzer) and a filterable `parent_id` string field.
- `indexProjections.selectors`: `targetIndexName`, `parentKeyFieldName`, `sourceContext` (for example `/document/pages/*`) and `mappings` for chunk text, vector and parent fields.
- `parameters.projectionMode: skipIndexingParentDocuments` so only chunk documents are written.
W: Index projections with skipIndexingParentDocuments: the projection writes one search document per chunk with the parent's title and URL copied in, and the projection mode stops the parent document itself from being indexed.
X: A=Shaper into a complex collection: shaping keeps the chunks inside one parent document, so the index still has one document per manual instead of one per chunk.
B=Two indexers and a query-time join: Azure AI Search doesn't join documents at query time, and two indexers duplicate the work that index projections do in one pass.
D=parsingMode jsonArray: parsing modes split source files (such as JSON arrays) before enrichment. They don't apply to chunks that a skill creates inside the pipeline.
T: To index chunks as their own search documents with parent fields repeated, use index projections with projectionMode skipIndexingParentDocuments.

@ AI-103 D5 T5.1 applied troubleshooting
S: A RAG app answers questions from policy documents chunked by the Text Split skill (textSplitMode pages, maximumPageLength 2000, pageOverlapLength 0). Answers often miss a condition that starts at the end of one chunk and finishes in the next. Which change addresses this most directly?
A: Switch textSplitMode to sentences, so each chunk holds a single sentence and no condition is ever divided between two consecutive chunks
B: Set pageOverlapLength to about a quarter of the chunk size, so the end of each chunk is repeated at the start of the next one
C: Set maximumPagesToTake to 1, so the skill keeps only the first and most complete chunk of each document and discards the fragments
D: Raise maximumPageLength above the embedding model's input limit, so that each policy document always ends up as one single chunk
K: B
G: ## Why chunks lose context
Fixed-size chunking cuts text at a length limit. A sentence or rule that crosses that boundary ends up half in one chunk and half in the next, and retrieval may return only one half.
## Text Split skill settings
- `textSplitMode`: `pages` (default; chunks of several sentences) or `sentences` (one sentence per chunk).
- `maximumPageLength`: maximum characters per chunk; the splitter avoids breaking sentences.
- `pageOverlapLength`: characters from the end of the previous chunk repeated at the start of the next. It must be less than half of `maximumPageLength`.
- `maximumPagesToTake`: how many chunks to keep (`0` = all).
## Learn's starting point
Learn suggests starting around 512 tokens (about 2,000 characters) with **25% overlap**, then tuning for the content. Overlap keeps continuity between neighbouring chunks without large duplication. Chunks must also stay under the embedding model's input limit (8,191 tokens for text-embedding-3-small).
W: Overlap between chunks: repeating the tail of one chunk at the head of the next keeps a rule that crosses a boundary complete in at least one chunk.
X: A=Sentences mode: single-sentence chunks cut a multi-sentence condition into even more pieces and give the embedding very little context.
C=maximumPagesToTake 1: keeping only the first chunk throws away the rest of every policy document, so later conditions can't be retrieved at all.
D=Chunks above the model limit: input beyond the embedding model's token limit can't be embedded as one vector, which is the reason chunking exists in the first place.
T: When information is split across chunk boundaries, add overlap (Learn's starting point is about 25%), keeping it under half the chunk length.

@ AI-103 D5 T5.1 applied use-case
S: Users of a support assistant search both by exact error codes such as "E-4471" and by vague descriptions such as "the printer stops after warming up". The index has a searchable text field and a vector field with a vectorizer. Which query design returns good matches for both kinds of question in one request?
A: A hybrid query that sends the text in search and in a vectorQueries entry, so full-text and vector results are merged with Reciprocal Rank Fusion
B: A vector-only query with exhaustive set to true, so every chunk is compared with the question and exact codes are found by vector similarity
C: A full-text query with queryType full and fuzzy matching on every term, so vague descriptions match the documents through spelling variants
D: Two separate requests, one full-text and one vector, with the app keeping the result list whose top score is higher for each question asked
K: A
G: ## Keyword and vector search find different things
- **Full-text (BM25)** search is precise for exact tokens: product codes, error codes, names, dates, specialized jargon.
- **Vector** search finds content that is *conceptually* similar, even with no shared words.
Each alone misses what the other finds.
## Hybrid search in Azure AI Search
A hybrid query is **one request** with both `search` (text) and `vectorQueries` parameters:
`{"search": "printer stops after warming up", "vectorQueries": [{"kind": "text", "text": "printer stops after warming up", "fields": "contentVector", "k": 50}], "top": 10}`
The engine runs both queries in parallel and merges the ranked lists with **Reciprocal Rank Fusion (RRF)** into one result set. Filters, facets and semantic ranking still apply. Learn notes that hybrid retrieval with semantic ranker gives significant relevance gains in benchmarks, which is why it's the common choice for RAG grounding.
W: Hybrid query merged with RRF: one request runs keyword search (strong on exact codes) and vector search (strong on paraphrases) and fuses the rankings, so both question styles get relevant results.
X: B=Exhaustive vector-only query: exhaustive KNN improves vector recall, but embeddings don't reliably match exact codes such as "E-4471"; keyword search is the precise tool for those.
C=Full Lucene with fuzzy terms: fuzzy search tolerates misspellings, not paraphrases. A vague description shares few words with the right document, so it still won't match.
D=Two requests, keep the higher top score: BM25 scores and vector similarity scores are on different scales, so comparing them is meaningless; RRF exists to merge rankings instead.
T: Use a hybrid query (text plus vector in one request, merged with RRF) when users mix exact identifiers and natural-language descriptions.

@ AI-103 D5 T5.1 applied troubleshooting
S: A team enables semantic ranker for hybrid queries over a chunk index. The semantic configuration lists title as the title field and a long keywords field first, then the chunk text field, under content. Reranking ignores parts of the chunk text, and captions rarely come from it. What should the developer change?
A: Raise the vector query's k to 1,000, so the semantic ranker receives more candidate chunks and finds the passages in the chunk text field

D: Add the vector field to the semantic configuration's content fields, so reranking uses the embedding of the chunk instead of its text
K: C
G: ## What the semantic ranker reads
Semantic ranker is an L2 reranker. It takes the top **50** results of a BM25 or RRF ranked query and rescores them with Microsoft's language models, returning `@search.rerankerScore` (0 to 4), captions and optional answers.
## Inputs are summarized and trimmed
For each document the ranker builds a summary string of up to 2,048 tokens from the fields in the **semantic configuration**:
- title field: up to 128 tokens
- keywords fields: up to 128 tokens
- content fields: the remaining tokens, **in the order listed**
Anything past the limit is ignored, so Learn advises listing fields in priority order. Only text fields can be used; the reranking uses text only.
## Practical settings
- Put the main chunk text first in `prioritizedContentFields`.
- Keep keywords short.
- For hybrid or vector queries, set `k` to 50 so the ranker gets its full input.
W: Chunk text first in the content fields: the ranker trims inputs in the listed order, so moving the chunk text up (and dropping low-value fields) makes its passages part of what is scored and used for captions.
X: A=k of 1,000: the semantic ranker only reranks the top 50 results; a larger k doesn't change how much of each document's text it reads.
B=queryType full: full selects the Lucene query syntax for the text query. Semantic ranking still reads only the fields in the semantic configuration.
D=Vector field in the configuration: semantic configurations accept text fields only, and the ranker works on text, not on stored embeddings.
T: The semantic ranker reads a trimmed summary built from the semantic configuration's fields in priority order, so list the main chunk text first.

@ AI-103 D5 T5.1 applied definition
S: A product owner reviews a design that adds semantic ranker to an Azure AI Search hybrid query used for grounding a chat model. Which two statements about the semantic ranker are correct? (Select TWO)
A: It reranks only the top results of the initial BM25 or RRF ranked result set, at most 50, rather than scoring every document in the index
B: Its captions and semantic answers are verbatim text taken from the indexed documents, not new text composed by a generative model
C: It replaces the vector search step of a hybrid query, so the index no longer needs a vectorizer once semantic ranking is turned on
D: It writes a generated summary of each document into the index during indexing, and queries later return that stored summary as the caption
E: It needs the chat model's deployment name in the query request, because it calls that model to compose a direct answer for the user
K: A,B
G: ## Semantic ranker in the query pipeline
Semantic ranker is a **query-side** feature of Azure AI Search:
1. The query runs as usual: BM25 for text, RRF for hybrid or vector queries.
2. The top 50 results go to the semantic ranker, which builds a summary string per document from the semantic configuration's fields.
3. Microsoft-hosted language models (adapted from Bing) rescore the documents (`@search.rerankerScore`, 0 to 4) and extract **captions** and, when requested, **answers**.
## What it doesn't do
Learn is explicit: "Captions and answers are always verbatim text from your index. There's no generative AI model in this workflow that creates or composes new content." It doesn't touch the index at indexing time and doesn't replace vector or keyword retrieval; it only reorders what retrieval returned. Query rewrite, which generates query variants, is a separate preview capability.
## Why it matters for grounding
Reranking improves which chunks reach the chat model. The chat model, not the ranker, writes the final answer.
W: A=Reranks the top 50: semantic ranking is a second-stage (L2) step over the first-stage results, limited to the top 50.
B=Verbatim captions and answers: captions and answers are extracted from indexed text by reading-comprehension models; nothing is generated.
X: C=Replaces vector search: the ranker works on the results retrieval already produced. Without the vector step (and its vectorizer), conceptual matches never reach it.
D=Summary written at indexing time: the summary string is built per query, in memory, from the configured fields. Nothing is stored in the index during indexing.
E=Needs a chat deployment: the semantic ranker uses Microsoft-hosted ranking models. It doesn't call your chat model and doesn't compose answers.
T: Semantic ranker reorders the top 50 retrieved results and extracts verbatim captions and answers; it never generates text or replaces retrieval.

Content Understanding uses your Foundry model deployments for generative steps, and it **inherits the guardrails** (formerly content filters) applied to those deployments. Learn explains the effect on analysis:

- **Guardrails can restrict field generation while preserving extracted source content.**
- Analysis can therefore **succeed with warnings** even when some field values aren't returned.
- Blocking can limit field extraction or stop analysis; with the required approval, annotate-only behavior keeps detections for human review instead of blocking.
## What to do
Review warnings before using results in automated workflows. Decide whether the content should be blocked, or whether an approved annotate-only configuration plus human review is more appropriate for the use case.
W: Guardrail restricting field generation: this matches the documented behavior exactly: extraction succeeds and content is preserved, while flagged content stops some generated fields and produces warnings.
X: B=File size limit: a size problem would show up as a failed request or truncated content, but here the Markdown content is complete.
C=Source and confidence off: that setting only adds confidence and location to fields; leaving it off doesn't remove field values.
D=Deleted deployment: a missing model deployment would break every generative step for every file, not drop a few fields only on some flagged documents.
