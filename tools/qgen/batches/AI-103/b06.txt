@ AI-103 D2 T2.2 applied troubleshooting
S: An HR prompt agent has two tools: file search over a vector store that holds the company handbook, and web search. When employees ask "How many days of parental leave do I get?", the agent sometimes answers with figures from public websites instead of the handbook. What should the developer change first?
A: Set tool_choice to required on every request, so the model must call a tool before it answers and therefore reads the handbook vector store first
B: Add a decision rule to the agent instructions: use file search for company policy questions, and use web search only for public, non-company information
C: Raise max_num_results on the file search tool, so the handbook returns more chunks per query and outweighs the web results when both tools are called
D: Move the handbook files into a second vector store attached to the conversation, so file search gives them priority over web search on every turn
K: B
G: ## Instructions define the agent's role and tool policy
A prompt agent in Foundry Agent Service is a model plus **instructions** plus **tools**. The instructions describe the agent's role, goals, boundaries and expected output, and they are where you tell the model *which tool to use when*.
Learn's tool best-practice guidance says:
- tell the model what each tool is for
- when tools overlap, add a **decision rule**, for example "Use File Search before Web Search for internal content"
- say what to do when a tool fails or returns nothing (explain, then ask a follow-up question)
## Why overlap causes wrong answers
Both tools can return something for "parental leave". Without a rule, the model may pick the public web result, which describes statutory or other companies' leave, not this company's policy.
## Example
`Instructions: You answer HR questions for Contoso employees. For any question about Contoso policy, benefits or leave, use File Search over the handbook. Use Web Search only for public information such as national holidays. If the handbook has no answer, say so and suggest contacting HR.`
W: Decision rule in instructions: the problem is tool choice between two overlapping tools, and Learn's recommended fix is to state in the instructions which tool serves which kind of question, so policy questions go to the handbook.
X: A=tool_choice required: this forces the model to call some tool, but it doesn't say which one; web search still satisfies the requirement, so the wrong source can still win.
C=More file search results: more handbook chunks don't stop the model from also calling web search and preferring that answer; the selection problem stays.
D=Conversation vector store: attaching the files at conversation level changes where the vector store lives, not how the model chooses between file search and web search.
T: When an agent has overlapping tools, put a clear decision rule in its instructions that says which tool to use for which kind of request.
V: Foundry Agent Service, file search, web search

@ AI-103 D2 T2.2 applied troubleshooting
S: A Python chat app calls a Foundry prompt agent with openai.responses.create(input=user_text) for each message the user types. Single questions work, but a follow-up such as "And what about the second option?" gets a reply that ignores the earlier turns. How should the developer track the conversation?
A: Attach the memory search tool to the agent, so every turn is stored as long-term memory and recalled on the next request from the same user
B: Create a new agent version for each user session and copy the previous turns into its instructions before sending the next message
C: Create a conversation once per chat session with openai.conversations.create(), and pass conversation=conversation.id on every responses.create call
D: Set tool_choice to auto on each request, so the agent can decide on its own whether it needs to look back at the earlier messages in the session
K: C
G: ## Conversations and responses
The current Foundry Agent Service API uses three objects:
- **Agent** (a versioned definition: model, instructions, tools)
- **Conversation**: a durable container that stores the items of a multi-turn exchange (user messages, agent replies, tool calls)
- **Response**: one invocation of the agent, created with `responses.create`
A response created without a conversation is a single, independent turn. To keep history, create a conversation and reference it on each call; Foundry appends the response items to it, so the next turn sees the earlier ones.
## Example
`conversation = openai.conversations.create()`
`openai.responses.create(conversation=conversation.id, input="Compare the two plans")`
`openai.responses.create(conversation=conversation.id, input="And what about the second option?")`
## Short-term versus long-term memory
The conversation is the agent's short-term, in-session memory. Memory in Foundry Agent Service (currently **preview**) is a separate long-term store that extracts user preferences and summaries across sessions; it doesn't replace passing the conversation.
W: Conversation per session: a conversation object stores every item of the exchange, and passing its id on each responses.create call gives the agent the earlier turns, which is how Learn's quickstart keeps multi-turn history.
X: A=Memory search tool: Foundry memory is a preview, long-term store that distills preferences and summaries across sessions; it isn't the mechanism for replaying the turns of the current chat.
B=Agent version per session: versions are immutable snapshots of the agent definition. Rewriting instructions with chat history every turn misuses versioning and still loses tool-call items.
D=tool_choice auto: tool_choice controls whether the model calls tools. It has nothing to do with conversation history, which the app must pass explicitly.
T: Keep multi-turn context in Foundry Agent Service by creating a conversation and passing its id on every responses.create call.
V: Foundry Agent Service, Responses API

G: ## Classic agents versus the current API
Classic Foundry agents (and the OpenAI Assistants API) used **assistants**, **threads**, **messages** and **runs**. The classic threads, messages and runs model is deprecated (retirement 2027-03-31). Learn's migration guide lists the minimum steps:
- compare tools with the new tool availability and pick replacements for tools that don't carry over
- migrate the agent definition (assistant or classic agent becomes an agent with versions)
- **replace threads with conversations and runs with responses**
- verify state, tool calls, outputs and error handling
## Mapping
- assistant / classic agent -> agent (versioned definition)
- thread -> conversation
- message -> conversation item (input and output items)
- run -> response (`responses.create`)

B=Run to response: a response is one invocation of the agent; creating it with the conversation id replaces creating a run on a thread.
X: C=Thread to vector store: vector stores hold uploaded files for the file search tool; they don't store chat history.
D=Run to agent version: an agent version is an immutable snapshot of the definition, created when the definition changes, not once per user turn.
E=Message to toolbox: a toolbox groups tools behind one MCP-compatible endpoint; it has nothing to do with chat messages.
T: Migrating to the current Foundry Agent Service API means threads become conversations and runs become responses.

@ AI-103 D2 T2.2 advanced troubleshooting
S: A retail prompt agent has a function tool create_return with the parameters order_id and reason. Traces show the model sometimes calls it without order_id, and sometimes adds an extra refund_amount argument that the backend rejects. Which TWO changes to the function definition address both problems? (Select TWO)
A: Add "required": ["order_id", "reason"] to the parameters schema, so the definition states which arguments every call must include
B: Set strict to true and "additionalProperties": false, so the model's arguments must follow the schema exactly with no extra fields
C: Set tool_choice to none for requests that might create a return, so the model describes the return in text and the app collects the fields
D: Remove the parameters schema and describe order_id and reason in the agent instructions, so the model reads the rules from the system prompt
E: Rename the function to createReturnWithOrderIdAndReason, so the function name itself tells the model which arguments it has to send
K: A,B
G: ## A function tool is a JSON schema contract
With function calling, you describe each function with a **name**, a **description** and a **parameters** JSON schema. The model never runs the function: it returns a `function_call` item with arguments, your app executes the function and sends back a `function_call_output`.
The schema is what keeps arguments valid. Learn's troubleshooting table for function calling says:
- "Required fields are missing" -> the schema doesn't enforce required properties; add a `"required": [...]` array and, where supported, set `strict: true`
- "Function called with wrong parameters" -> improve the description and parameter descriptions
## Example
`"parameters": {"type": "object", "properties": {"order_id": {"type": "string"}, "reason": {"type": "string"}}, "required": ["order_id", "reason"], "additionalProperties": false}` with `strict=True`.
Note: the Microsoft Copilot harness (preview) for prompt agents rejects `strict: true`; for default prompt agents strict mode is supported.
W: A=required array: listing order_id and reason as required tells the model that every call must include them, which fixes the missing-argument calls.
B=strict with no additional properties: strict mode makes the generated arguments follow the schema, and additionalProperties false rules out invented fields such as refund_amount.
X: C=tool_choice none: this stops the model from calling any tool, so returns could no longer be created through the function at all.
D=Rules in instructions only: removing the schema takes away the structured contract; prose instructions are weaker than a validated schema for argument shape.
E=Longer function name: a descriptive name helps tool selection, but it doesn't enforce required arguments or block extra ones.
T: Enforce function arguments in the schema itself: a required array plus strict mode with additionalProperties false.
V: Foundry Agent Service, function calling

@ AI-103 D2 T2.2 applied troubleshooting
S: A developer adds a function tool get_order_status to a prompt agent. The first response's output contains an item of type function_call with call_id and arguments, but the app prints response.output_text, which is empty, and the user never gets an answer. What is missing?
A: An mcp_approval_response item that approves the function call, sent in the same conversation with approve set to true and the call's id

C: A project connection for the function tool, so that Foundry can reach the order system and run get_order_status on the server side
D: Running get_order_status in the app and sending a function_call_output item with the same call_id in a new responses.create call
K: D
G: ## Function calling is a client-side loop
Function tools run in **your** application, not in Foundry. Learn describes the pattern:
1. Define function tools (name, description, parameters).
2. Create the agent with those definitions.
3. Send a prompt; the model may return `function_call` items.
4. **Execute and return**: your app runs the function and submits the output back.
5. The agent uses the output to produce the final answer.
## What the follow-up call looks like
`input_list.append(FunctionCallOutput(type="function_call_output", call_id=item.call_id, output=json.dumps(result)))`
`openai.responses.create(input=input_list, conversation=conversation.id)`
If the model asked for several functions in one response, handle each item and return all the outputs in a single `responses.create` call. Learn also notes that outputs must be submitted promptly (runs expire 10 minutes after creation).
W: Execute and return output: Learn's troubleshooting row "agent returns function call but no final answer" is caused by not returning tool output; the app must run the function and send a function_call_output with the matching call_id to continue.
X: A=MCP approval response: approval requests and responses belong to the MCP tool. A function call isn't waiting for approval; it's waiting for your app to run it.
B=tool_choice required: this forces the model to call a tool, which it already did. It can't make Foundry execute code that only exists in your app.
C=Project connection: connections store credentials for server-side tools such as OpenAPI or MCP. Function tools are executed by the client, so no connection runs them.
T: With function tools, your app runs the function and sends a function_call_output with the same call_id; only then does the agent produce its final answer.

@ AI-103 D2 T2.2 applied comparison
S: A manufacturer's data team already maintains an Azure AI Search index of two million product manuals with vector fields, a semantic configuration and nightly updates. A new Foundry agent must answer engineers' questions from that content with source citations. Which retrieval approach should the developer use?
A: Download the manuals again, upload them to a vector store in the project, and attach the file search tool to the agent with that vector store

G: ## Two retrieval tools in Foundry Agent Service
- **File search**: you upload files; Foundry parses, chunks, embeds and stores them in a **vector store** (Microsoft-managed in basic setup, your own Azure AI Search and Blob Storage in standard setup). Best for documents you upload directly or that users provide.
- **Azure AI Search tool**: connects the agent to an **existing** Azure AI Search index through a project connection. The agent queries the index and answers with inline citations.
Learn's file search page states it directly: to "search existing Azure AI Search indexes", use the Azure AI Search tool.
## Azure AI Search tool settings
- `project_connection_id` and `index_name` (required)
- `query_type` (default `vector_semantic_hybrid`; also `simple`, `vector`, `semantic`, `vector_simple_hybrid`)
- `top_k` (default 5) and `filter` (applied to every query)
The index needs searchable text fields, vector fields, a retrievable content field and a retrievable URL (and optionally title) field for citation links.
W: Azure AI Search tool: the content already lives in a maintained index with vectors and semantic ranking, and this tool queries that index directly with citations, so nothing has to be copied or re-indexed.
X: A=File search re-upload: this duplicates two million manuals into a separate vector store that the data team's nightly updates would never reach.
C=Web search: public web results depend on what Bing has indexed and bypass the team's curated index, its semantic configuration and its update schedule.
D=Code interpreter over an export: code interpreter runs Python in a sandbox; it isn't a search engine and a static export goes stale after the next nightly update.
T: Use the Azure AI Search tool for content already in an Azure AI Search index, and file search for files you upload to a vector store.

File search reads from **vector store** objects. You can attach vector stores to the **agent** (shared content such as a handbook) or to a **conversation** (files a user brings to one chat).

- maximum file size 512 MB, up to 5,000,000 tokens per file
- up to 10,000 files per vector store

A trace records one request as nested **spans**; each span has start and end times and **attributes**. G: ## How an agent-targeted evaluation works
When you run an evaluation against an agent, the service sends each test query from your dataset to the agent, captures the response and applies the selected evaluators. Each evaluator entry uses **data_mapping** to say which fields it receives:
- `{{item.X}}`: fields from your test data, such as `{{item.query}}`
- `{{sample.output_items}}`: the **full agent response, including tool calls**
- `{{sample.output_text}}`: **just the response message text**
- `initialization_parameters={"deployment_name": ...}`: the judge model for LLM-based evaluators
## Why the mapping matters
Process evaluators (Tool Call Accuracy, Tool Selection, Tool Input Accuracy, Tool Call Success...) judge the tool calls themselves. If they only receive the final text, there are no tool calls to judge.
## Building datasets
Test data is a JSONL file with a `query` per line; you can also generate a synthetic dataset or convert agent traces into an evaluation dataset.
W: Map output_items: tool evaluators need the tool call items, and output_items is the mapping that includes them, while output_text carries only the final message.
X: B=Map item.query: the query is the input; the evaluator would see no agent behavior at all, so tool calls still couldn't be judged.
C=Remove the judge model: LLM judge evaluators typically require the deployment_name parameter; removing it breaks the evaluator without exposing tool calls.
D=CSV dataset: Learn's agent evaluation uses a JSONL dataset of queries; file format doesn't decide whether tool calls reach the evaluator.
T: In agent evaluations, map tool-focused evaluators to {{sample.output_items}}, which includes tool calls, not {{sample.output_text}}.
