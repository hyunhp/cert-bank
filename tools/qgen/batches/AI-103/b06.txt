@ AI-103 D2 T2.2 applied troubleshooting
S: An HR prompt agent has two tools: file search over a vector store that holds the company handbook, and web search. When employees ask "How many days of parental leave do I get?", the agent sometimes answers with figures from public websites instead of the handbook. What should the developer change first?
A: Set tool_choice to required on every request, so the model must call a tool before it answers and therefore reads the handbook vector store first
B: Add a decision rule to the agent instructions: use file search for company policy questions, and use web search only for public, non-company information
C: Raise max_num_results on the file search tool, so the handbook returns more chunks per query and outweighs the web results when both tools are called
D: Move the handbook files into a second vector store attached to the conversation, so file search gives them priority over web search on every turn
K: B
G: ## Instructions define the agent's role and tool policy
A prompt agent in Foundry Agent Service is a model plus **instructions** plus **tools**. The instructions describe the agent's role, goals, boundaries and expected output, and they are where you tell the model *which tool to use when*.
Learn's tool best-practice guidance says:
- tell the model what each tool is for
- when tools overlap, add a **decision rule**, for example "Use File Search before Web Search for internal content"
- say what to do when a tool fails or returns nothing (explain, then ask a follow-up question)
## Why overlap causes wrong answers
Both tools can return something for "parental leave". Without a rule, the model may pick the public web result, which describes statutory or other companies' leave, not this company's policy.
## Example
`Instructions: You answer HR questions for Contoso employees. For any question about Contoso policy, benefits or leave, use File Search over the handbook. Use Web Search only for public information such as national holidays. If the handbook has no answer, say so and suggest contacting HR.`
W: Decision rule in instructions: the problem is tool choice between two overlapping tools, and Learn's recommended fix is to state in the instructions which tool serves which kind of question, so policy questions go to the handbook.
X: A=tool_choice required: this forces the model to call some tool, but it doesn't say which one; web search still satisfies the requirement, so the wrong source can still win.
C=More file search results: more handbook chunks don't stop the model from also calling web search and preferring that answer; the selection problem stays.
D=Conversation vector store: attaching the files at conversation level changes where the vector store lives, not how the model chooses between file search and web search.
T: When an agent has overlapping tools, put a clear decision rule in its instructions that says which tool to use for which kind of request.
V: Foundry Agent Service, file search, web search

@ AI-103 D2 T2.2 applied troubleshooting
S: A Python chat app calls a Foundry prompt agent with openai.responses.create(input=user_text) for each message the user types. Single questions work, but a follow-up such as "And what about the second option?" gets a reply that ignores the earlier turns. How should the developer track the conversation?
A: Upload each finished turn as a text file to a vector store on the agent, so file search retrieves the earlier turns on the next request
B: Create a new agent version for each user session and copy the previous turns into its instructions before sending the next message
C: Create a conversation once per chat session with openai.conversations.create(), and pass conversation=conversation.id on every responses.create call
D: Set tool_choice to auto on each request, so the agent can decide on its own whether it needs to look back at the earlier messages in the session
K: C
G: ## Conversations and responses
The current Foundry Agent Service API uses three objects:
- **Agent** (a versioned definition: model, instructions, tools)
- **Conversation**: a durable container that stores the items of a multi-turn exchange (user messages, agent replies, tool calls)
- **Response**: one invocation of the agent, created with `responses.create`
A response created without a conversation is a single, independent turn. To keep history, create a conversation and reference it on each call; Foundry appends the response items to it, so the next turn sees the earlier ones.
## Example
`conversation = openai.conversations.create()`
`openai.responses.create(conversation=conversation.id, input="Compare the two plans")`
`openai.responses.create(conversation=conversation.id, input="And what about the second option?")`
W: Conversation per session: a conversation object stores every item of the exchange, and passing its id on each responses.create call gives the agent the earlier turns, which is how Learn's quickstart keeps multi-turn history.
X: A=Turns in a vector store: file search retrieves chunks that look relevant, not the ordered turns of this chat, and an agent-level vector store is shared by every user's conversations.
B=Agent version per session: versions are immutable snapshots of the agent definition. Rewriting instructions with chat history every turn misuses versioning and still loses tool-call items.
D=tool_choice auto: tool_choice controls whether the model calls tools. It has nothing to do with conversation history, which the app must pass explicitly.
T: Keep multi-turn context in Foundry Agent Service by creating a conversation and passing its id on every responses.create call.
V: Foundry Agent Service, Responses API

@ AI-103 D2 T2.2 applied comparison
S: A team is migrating a support bot from the classic Foundry agents API, which uses assistants, threads, messages and runs, to the current Foundry Agent Service API. Which TWO replacements should the team make in its code? (Select TWO)
A: Replace each thread with a conversation, which stores the user messages, agent replies and tool call items of a multi-turn exchange
B: Replace each run with a response, created with responses.create against the agent and, for multi-turn chats, the conversation id
C: Replace each thread with a vector store, which keeps the message history of a session searchable for the agent on later turns
D: Replace each run with a new agent version, because the new API executes every user turn by snapshotting the agent definition
E: Replace each message with a toolbox, which groups the messages of one session behind a single managed MCP endpoint for the agent
K: A,B
G: ## Classic agents versus the current API
Classic Foundry agents (and the OpenAI Assistants API) used **assistants**, **threads**, **messages** and **runs**. The classic threads, messages and runs model is deprecated (retirement 2027-03-31). Learn's migration guide lists the minimum steps:
- compare tools with the new tool availability and pick replacements for tools that don't carry over
- migrate the agent definition (assistant or classic agent becomes an agent with versions)
- **replace threads with conversations and runs with responses**
- verify state, tool calls, outputs and error handling
## Mapping
- assistant / classic agent -> agent (versioned definition)
- thread -> conversation
- message -> conversation item (input and output items)
- run -> response (`responses.create`)
W: A=Thread to conversation: a conversation is the new container for the items of a multi-turn exchange, which is the role a thread played.
B=Run to response: a response is one invocation of the agent; creating it with the conversation id replaces creating a run on a thread.
X: C=Thread to vector store: vector stores hold uploaded files for the file search tool; they don't store chat history.
D=Run to agent version: an agent version is an immutable snapshot of the definition, created when the definition changes, not once per user turn.
E=Message to toolbox: a toolbox groups tools behind one MCP-compatible endpoint; it has nothing to do with chat messages.
T: Migrating to the current Foundry Agent Service API means threads become conversations and runs become responses.
V: Foundry Agent Service, Responses API

@ AI-103 D2 T2.2 advanced troubleshooting
S: A prompt agent has a function tool generate_audit_report. The app runs the function whenever the model asks for it, but the report job takes about 25 minutes, and submitting the function_call_output afterward fails because the run has expired. Short functions on the same agent work. What should the developer change?
A: Make generate_audit_report start the job and return a job ID and status right away, and add a second function that the agent can call to check the job
B: Set tool_choice to required on the follow-up request, so that the expired run is reopened and accepts the late function_call_output for the report
C: Send the request with streaming turned on, so that the run stays connected while the report job runs and the late function output is still accepted
D: Create a new agent version with a longer timeout setting on the function tool, so that the agent keeps the run open until the audit report is ready
K: A
G: ## Function tools run in your app, on the run's clock
With function calling, the model returns a `function_call` item, your app runs the function, and the app submits a `function_call_output` so the agent can finish its answer. That loop has a time limit. Learn's function calling page warns: "Runs expire 10 minutes after creation. Submit your tool outputs before they expire."
## Learn's troubleshooting row
- Symptom: tool outputs fail due to expiration
- Cause: the run expired
- Resolution: "Return tool outputs promptly. For slow operations, return a status and poll separately."
## The start-and-check pattern
Split the slow work into two quick functions:
- `start_audit_report(period)` starts the job in your backend and returns at once, for example `{"job_id": "rpt-881", "status": "running"}`
- `get_report_status(job_id)` returns `running`, or `done` with a link to the report
The agent can tell the user the report is being prepared, and a later turn (or the app itself) checks the status. Every function output is then submitted well within the run's lifetime.
W: Start and check: Learn's fix for expired runs is to return outputs promptly and, for slow operations, return a status and poll separately, so a job ID now and a status function later keep every output inside the run's lifetime.
X: B=tool_choice required: tool_choice only says whether the model must call a tool; it can't revive an expired run or extend its lifetime.
C=Streaming: streaming changes how output is delivered to the client, not how long a run accepts tool outputs, so the late output still fails.
D=Timeout on the function tool: a function tool definition has a name, description, parameters and strict flag; there's no per-tool timeout that keeps a run open for 25 minutes.
T: Function outputs must be submitted before the run expires; for slow work, return a job ID and status at once and check the job with a separate call.
V: Foundry Agent Service, function calling

A function tool is defined by a name, a description and a parameters schema, but the code behind it lives in **your application**. Foundry never executes it: the model returns a `function_call` item, and your app runs the function and submits a `function_call_output`.
Learn's function calling page states two portal limits:
- "You can run agents with function tools in the Microsoft Foundry portal. However, the portal doesn't support adding, removing, or updating function definitions on an agent. Use the SDK or REST API to configure function tools."

2. Test with a small script that sends a prompt, runs `lookup_warranty` when the model asks for it, and returns the output.

W: SDK or REST, test from code: Learn says the portal can't add, remove or update function definitions and doesn't execute function calls, so the change and the test both belong in code.

C=Hosted agents only: prompt agents support function tools (Learn's samples create prompt agents with FunctionTool); the limit is the portal, not the agent type.
D=tool_choice required: this only forces the model to request a tool call; the portal still has no code to execute lookup_warranty.

@ AI-103 D2 T2.2 applied use-case
S: A benefits agent uses file search over an HR handbook. Employees should also be able to upload their own payslips during a chat and ask questions about them, and one employee's payslip must never be searchable in another employee's chat. How should the developer organize the vector stores?
A: Keep the handbook in a vector store attached to the agent, and put each chat's uploaded payslips in a vector store attached to that conversation
B: Add every uploaded payslip to the agent's handbook vector store, and add an instruction that tells the model to use only the current user's payslip
C: Attach a second vector store that holds all payslips to the agent next to the handbook store, so that handbook and payslip searches stay apart
D: Create a new agent version per employee whose vector store holds the handbook and that employee's payslips, and route each chat by employee
K: A
G: ## Where file search looks
File search reads from **vector stores**. Adding a file parses, chunks, embeds and stores it for hybrid (keyword plus semantic) search. Learn: "You can attach vector stores to both agents and conversations. Currently, you can attach at most one vector store to an agent and at most one vector store to a conversation."
- **Agent-level vector store**: content every conversation should see, such as a handbook
- **Conversation-level vector store**: files a user brings to one chat; other conversations don't search it
## Lifecycle details worth knowing
- Conversation vector stores created with conversation helpers expire by default seven days after they were last active; requests on that conversation then fail until you recreate and reattach the store.
- If a conversation's vector store still has files processing, the run waits up to 60 seconds for them; that fallback doesn't apply to the agent's vector store, so poll new agent-level files until processing completes.
- Limits: up to 10,000 files per vector store, 512 MB per file.
## Example
Handbook store `vs_handbook` on the agent; when an employee uploads a payslip, the app creates `vs_chat_4711` with that file and attaches it to the employee's conversation.
W: Agent store plus conversation store: the handbook is shared through the agent's vector store, while each conversation's own vector store keeps a payslip searchable only in the chat where it was uploaded.
X: B=Everything in the agent store: every conversation searches the agent's vector store, so payslips would be retrievable in other chats; an instruction doesn't enforce isolation.
C=Second agent store: an agent can have at most one vector store attached, and a shared payslip store would still be searchable from every employee's chat.
D=Agent version per employee: versions snapshot the agent definition; one per employee duplicates the handbook everywhere and is far more work than the conversation store built for this.
T: Attach shared content to the agent's vector store and per-chat uploads to the conversation's vector store; each can hold one vector store.
V: Foundry Agent Service, file search

@ AI-103 D2 T2.2 applied use-case
S: A multinational's Azure AI Search index holds HR policies for every country, with a filterable country field. A new agent for German employees must only ever retrieve documents where country is 'DE', whatever the user asks. How should the developer configure the Azure AI Search tool?
A: Set top_k to 1 on the tool, so the agent only reads the single best-matching document, which should be the German policy for most questions
B: Set the filter parameter on the tool to country eq 'DE', which the tool applies to every query that the agent sends to the index
C: Set query_type to vector on the tool, so the agent matches documents by meaning and German questions find the German documents first
D: Add "Only use German policies" to the agent instructions, so the model discards results from other countries before writing the answer

G: ## Azure AI Search tool parameters
When you attach the Azure AI Search tool to a Foundry agent you can set:
- `project_connection_id` (required): the project connection to the search service
- `index_name` (required)
- `top_k` (optional, default 5): number of results per query
- `query_type` (optional, default `vector_semantic_hybrid`)
- `filter` (optional): an OData filter that "applies to all queries the agent makes to the index"
## Enforce scope in the query, not in the prompt
A filter is applied by Azure AI Search before results reach the model, so documents from other countries are never retrieved. Instructions are only guidance to the model: results from other countries would still enter the context and could leak into an answer.
## Example
Learn's C# sample uses `Filter = "category eq 'sleeping bag'"`. For this agent: `filter = "country eq 'DE'"` (the field must be filterable in the index).
W: Tool filter: an OData filter on the tool is applied by the search service to every query, so the agent can only ever retrieve German documents, which is a hard guarantee rather than a request to the model.
X: A=top_k of 1: fewer results doesn't restrict them to Germany; the single top match could easily be another country's policy.
C=Vector query type: semantic similarity between a question and documents doesn't encode the country; French and German leave policies are close in meaning.
D=Instruction only: the other countries' documents are still retrieved and placed in context, and the model may still use them; instructions don't enforce scope.
T: Use the Azure AI Search tool's filter parameter to restrict every agent query to a subset of the index.

Workflows run in **supersteps**. Learn: "Checkpoints are created at the end of each superstep", and a checkpoint captures the whole workflow state:

- pending messages for the next superstep
- **pending requests and responses** (such as a waiting human approval)

Foundry's built-in agent evaluators work like unit tests for agentic systems: they take agent messages (including tool calls) and return Pass/Fail results. Learn groups them by best practice:
## System evaluation (end-to-end outcome)
Task Completion, Customer Satisfaction, Task Adherence, Intent Resolution (several of these are marked **preview**), and Task Navigation Efficiency.
## Process evaluation (each step)
- **Tool Call Accuracy**: right tool calls with correct parameters
- **Tool Selection**: correct and necessary tools, no unnecessary ones
- **Tool Input Accuracy**: strict checks on parameters
- **Tool Output Utilization**: correct use of tool results
- **Tool Call Success**: calls succeeded rather than ending in technical errors
## Matching problems to evaluators
Wrong tool -> Tool Selection. Tool ran but errored -> Tool Call Success. Right tool with bad arguments -> Tool Input Accuracy or Tool Call Accuracy. Ignored instructions -> Task Adherence (preview).
W: A=Tool Selection: calling search_flights instead of get_booking is a tool-choice error, which is exactly what Tool Selection measures.
B=Tool Call Success: HTTP 500 responses from the airline API are technical failures in tool execution, which Tool Call Success detects.
X: C=Intent Resolution: it's a system-level (preview) evaluator for understanding the user's intent; it doesn't measure whether tool calls fail technically.
D=Fluency: it scores language quality of the final text and has no view of which tools ran or failed.
E=Groundedness: it checks support in the context for the response; it doesn't diagnose tool choice or name a better tool.
T: Use process evaluators for tool problems: Tool Selection for wrong tools, Tool Call Success for failed calls, Tool Input Accuracy for bad arguments.

@ AI-103 D2 T2.2 advanced troubleshooting
S: A customer reports that a returns agent promised a refund of 500 instead of 50. The developer opens the trace for that request: an invoke_agent span contains a model call and two execute_tool spans. How should she find where the wrong amount came from?
A: Open the Monitor tab's run success rate chart for the day of the request, because a failed run marks the step that produced the wrong refund amount
B: Run a red teaming scan against the agent, because the scan replays the customer's request and reports which tool returned the incorrect amount
C: Inspect the execute_tool spans' gen_ai.tool.call.arguments and gen_ai.tool.call.result attributes to see whether the tool got or returned the wrong amount
D: Compare the token usage of the two execute_tool spans, because the span that consumed more tokens is the one that introduced the wrong refund amount
K: C
G: ## Error analysis with traces
A trace records one request as nested **spans**; each span has start and end times and **attributes**. Learn: tracing lets you "view the inputs and outputs of each primitive involved in a particular agent run, displayed in the order they were invoked", which answers "Where did this response come from?" and "Which step introduced an error or latency spike?"
## OpenTelemetry GenAI spans used by Foundry
- `invoke_agent`: an agent invocation (child `invoke_agent` spans for sub-agents)
- `execute_tool`: a tool execution, with attributes `gen_ai.tool.call.arguments` (what the agent sent) and `gen_ai.tool.call.result` (what came back)
- `gen_ai.tool.definitions` on the agent span lists available tools
## Reasoning through this case
- arguments already say 500 -> the model misread the order, so fix instructions or the tool's parameter descriptions
- arguments say 50 but the result says 500 -> the backend or tool is wrong
- both say 50 -> the model changed the number while writing the reply
W: Tool span attributes: the arguments and result recorded on each execute_tool span show whether the wrong value entered at the tool input, came back from the tool, or appeared only in the final reply.
X: A=Run success rate: this run succeeded technically; an aggregate rate can't locate a wrong value inside a single successful request.
B=Red teaming scan: red teaming probes for safety and security risks with adversarial prompts; it doesn't replay and diagnose a specific production request.
D=Token usage: tool spans with more tokens aren't more likely to be wrong; token counts measure cost, not correctness.
T: For error analysis, walk the trace spans and compare each execute_tool span's arguments and result to find where a wrong value first appears.

@ AI-103 D2 T2.2 advanced troubleshooting
S: A team runs an agent-targeted evaluation in Foundry with a tool-focused evaluator. The data_mapping sends {{sample.output_text}} as the agent response, and every result says the agent made no tool calls, although traces show it called its tools. What should the team change?
A: Map the response to {{sample.output_items}}, which contains the full agent response including tool calls, instead of only the response message text
B: Map the response to {{item.query}}, so the evaluator reads the original test query and infers from it which tool calls the agent should have made
C: Remove initialization_parameters from the evaluator, because a judge deployment makes the evaluator ignore tool calls and look only at text
D: Convert the test dataset from JSONL to CSV, because agent-targeted evaluations only read tool calls from datasets uploaded in CSV format
K: A
G: ## How an agent-targeted evaluation works
When you run an evaluation against an agent, the service sends each test query from your dataset to the agent, captures the response and applies the selected evaluators. Each evaluator entry uses **data_mapping** to say which fields it receives:
- `{{item.X}}`: fields from your test data, such as `{{item.query}}`
- `{{sample.output_items}}`: the **full agent response, including tool calls**
- `{{sample.output_text}}`: **just the response message text**
- `initialization_parameters={"deployment_name": ...}`: the judge model for LLM-based evaluators
## Why the mapping matters
Process evaluators (Tool Call Accuracy, Tool Selection, Tool Input Accuracy, Tool Call Success...) judge the tool calls themselves. If they only receive the final text, there are no tool calls to judge.
## Building datasets
Test data is a JSONL file with a `query` per line; you can also generate a synthetic dataset or convert agent traces into an evaluation dataset.
W: Map output_items: tool evaluators need the tool call items, and output_items is the mapping that includes them, while output_text carries only the final message.
X: B=Map item.query: the query is the input; the evaluator would see no agent behavior at all, so tool calls still couldn't be judged.
C=Remove the judge model: LLM judge evaluators typically require the deployment_name parameter; removing it breaks the evaluator without exposing tool calls.
D=CSV dataset: Learn's agent evaluation uses a JSONL dataset of queries; file format doesn't decide whether tool calls reach the evaluator.
T: In agent evaluations, map tool-focused evaluators to {{sample.output_items}}, which includes tool calls, not {{sample.output_text}}.
