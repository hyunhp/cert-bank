# AI-103 D1 T1.1 Choose the appropriate Foundry services for generative AI and agents (17 questions: model choice x6, Foundry service choice x3, retrieval and indexing x4, agent memory/tools/knowledge x4)

@ AI-103 D1 T1.1 applied use-case
S: A legal-tech startup is building a feature in Microsoft Foundry that compares two versions of a 40-page supplier contract and explains which changed clauses shift liability, citing the clause numbers. Accuracy on subtle differences matters far more than response time, and each comparison is requested a few dozen times a day. Which kind of model should the team deploy for this feature?
A: A small language model such as Phi-4-mini-instruct, because its lower cost per token allows many comparisons to run in parallel cheaply.
B: An embedding model such as text-embedding-3-large, because cosine similarity between the two versions shows which clauses changed.
C: A reasoning model from the Foundry model catalog, because it spends extra processing on multi-step analysis such as comparing documents.
D: A realtime audio model such as gpt-realtime, because its low-latency streaming returns the clause differences while the user waits.
K: C
G: ## Matching the model family to the task
Microsoft Foundry Models offers several families, and AI-103 expects you to pick by the shape of the task rather than by brand name:
- **Reasoning models** spend more time processing a request before answering. Microsoft Learn lists their strengths as complex code generation, advanced problem solving and **complex document comparison** ("analyzing contracts, case files, or legal documents to identify subtle differences").
- **General chat LLMs** answer quickly and handle broad conversation, drafting and summarization.
- **Small language models (SLMs)** such as the Phi family trade breadth for lower cost and latency on narrow, well-defined tasks.
- **Embedding models** return vectors, not text; they power similarity search.
## Trade-offs to remember
Reasoning models cost more time and tokens per request and do not accept every chat parameter (for example, sampling settings such as `temperature` are not supported on many of them; you tune a reasoning effort instead). That cost is acceptable when requests are few and correctness is the priority.
## Example
"Clause 12.3 now caps liability at fees paid in the prior 12 months instead of uncapped, which moves risk to the customer" is a multi-step judgment: align clauses, detect the change, then reason about its legal effect.
W: Reasoning model: the task is a low-volume, accuracy-first comparison of long legal text, which is exactly the "complex document comparison" strength Microsoft Learn names for reasoning models; the extra processing time is acceptable here.
X: A=Small language model: an SLM is the right choice for cheap, high-volume narrow tasks, but the requirement here is depth of analysis on subtle legal changes, and cost is not the constraint at a few dozen requests a day.
B=Embedding model: similarity scores can flag that a clause differs, but an embedding model produces vectors only; it cannot explain how a change shifts liability or write cited explanations.
D=Realtime audio model: realtime models are built for low-latency speech conversations, while this feature is a text analysis job where response time explicitly matters less than accuracy.
T: When a task needs multi-step analysis of long documents and accuracy matters more than latency, choose a reasoning model.
V: Microsoft Foundry, Foundry Models

@ AI-103 D1 T1.1 applied tradeoff
S: A telecom company receives about two million short customer chat messages per day and must tag each one with one of eight fixed intent labels in under a second, at the lowest practical cost. Tests show the task needs no world knowledge beyond the message itself and no tool calls. Which model choice in Microsoft Foundry best fits these requirements?
A: A small language model such as Phi-4-mini-instruct, prompted with the eight labels, because the narrow task does not need a larger model.
B: A reasoning model with high reasoning effort, because spending more time per message gives the most reliable label for each chat.
C: A multimodal model that accepts images and text, because customers might attach screenshots that change the intent of a message.
D: A model router deployment in Quality mode, because it always sends every message to the highest-rated model for that prompt.
K: A
G: ## Why small language models exist
A **small language model (SLM)** has far fewer parameters than a frontier LLM. It knows less about the world and handles open-ended reasoning less well, but for a **narrow, well-defined task** (classify, extract a short value, rewrite in a fixed style) it can be accurate enough while costing less and answering faster.
In the Foundry model catalog, Microsoft's Phi models are the typical SLM example: `Phi-4-mini-instruct` takes text input and returns text. Meta also lists 1B and 3B Llama models as SLMs.
## How to decide
- High volume plus tight latency plus a closed set of outputs points to an SLM.
- Open-ended analysis, long documents or multi-step planning point to a larger LLM or a reasoning model.
- Always confirm with an evaluation on your own labeled sample before switching production traffic.
## Example
Prompt: "Classify into one of: billing, outage, upgrade, cancel, roaming, device, password, other. Message: 'my bill doubled this month'" returns `billing`.
W: Small language model: eight fixed labels, short inputs, no tools and no outside knowledge make this a narrow task, and an SLM meets the sub-second, low-cost target at two million requests a day.
X: B=Reasoning model with high effort: extra reasoning adds latency and tokens to every one of two million requests, which breaks both the sub-second and the lowest-cost requirements for a simple labeling job.
C=Multimodal model: the messages are short text and nothing in the scenario says images matter, so paying for image input capability adds cost without improving the eight-way classification.
D=Model router in Quality mode: Quality mode ignores cost and picks the highest-rated model for each prompt, which is the opposite of the lowest-practical-cost goal stated here.
T: For a high-volume, latency-sensitive, narrow task with a closed set of outputs, a small language model is usually the right first choice.
V: Foundry Models, Phi

@ AI-103 D1 T1.1 applied use-case
S: An IT service desk wants to show agents the five most similar past tickets whenever a new ticket arrives, so they can reuse proven fixes. Tickets describe the same problem in different words ("VPN drops", "remote connection keeps disconnecting"). The team plans to store the results in an Azure AI Search index. Which Foundry model should produce the representation of each ticket that the index compares?
A: A chat completion model such as gpt-4.1-mini, asked to write a one-line summary of each ticket for the index to compare word by word.
B: An embedding model such as text-embedding-3-small, which converts each ticket into a vector so similar meanings land close together.
C: A reasoning model such as Phi-4-mini-reasoning, which writes step-by-step reasoning that the index stores as a searchable text field.
D: An image generation model, which renders each ticket as a picture so a vision model can measure visual similarity between tickets.
K: B
G: ## What an embedding model does
An **embedding model** turns a piece of text into a fixed-length array of numbers (a vector). Texts with similar meaning produce vectors that are close together, even when they share no words. Azure AI Search stores these vectors in vector fields and finds the nearest neighbors of a query vector.
Microsoft Learn's example: "dog" and "canine" are conceptually similar but linguistically distinct, so keyword matching misses the link while vector search finds it.
## Embedding models in Foundry
- `text-embedding-3-small` and `text-embedding-3-large` (Azure OpenAI in Foundry Models); `text-embedding-3-large` is the most capable.
- Partner options such as `Cohere-embed-v3-multilingual`.
- They are called only through the embeddings API and return vectors, never prose.
Important: you cannot mix models. Index vectors and query vectors must come from the same embedding model, and switching models means re-embedding the content.
## Example
"VPN drops" and "remote connection keeps disconnecting" become two vectors whose cosine similarity is high, so the older ticket ranks in the top five.
W: Embedding model: similarity of meaning across different wording is exactly what vector embeddings capture, and Azure AI Search can run nearest-neighbor queries over those vectors to return the five closest past tickets.
X: A=Chat summary compared word by word: rewriting tickets into summaries still leaves the index matching words, so two summaries that use different vocabulary would still fail to match.
C=Reasoning text stored as a field: step-by-step text is more words to keyword-match, not a numeric representation of meaning, and it adds model cost to every ticket without enabling similarity search.
D=Image generation for visual similarity: rendering text as pictures throws away meaning and adds two unnecessary models; vector search over text embeddings is the direct way to compare meaning.
T: When you need "find items that mean the same thing", generate vectors with an embedding model and query them with vector search.
V: Foundry Models, Azure AI Search

@ AI-103 D1 T1.1 applied comparison
S: A parcel carrier is building an internal assistant. Depot staff upload a photo of a damaged parcel together with a short typed question such as "Is this crush damage or water damage, and which claim form applies?" and expect a text answer. The team is choosing between two Phi models from the Foundry model catalog. Which model fits, and why?
A: Phi-4-mini-instruct, because its long text context window can hold a detailed written description of the parcel damage from the staff.
B: Phi-4-mini-reasoning, because the claim-form decision is a reasoning step that only a reasoning model can perform reliably.
C: Phi-4-multimodal-instruct, because it accepts images as well as text in the same request and returns a text answer to the user.
D: Phi-4, because the larger base model reads image files that are attached to a chat completion request without extra configuration.
K: C
G: ## What makes a model multimodal
A **multimodal model** accepts more than one type of input in a single request, typically text plus images and sometimes audio. A text-only model can only work with what the user types, so it would never "see" the photo.
## Reading the catalog entry
The Foundry model catalog lists each model's input and output types. Microsoft Learn shows, for example:
- `Phi-4-mini-instruct`: input **text**, output text.
- `Phi-4-multimodal-instruct`: input **text, images and audio**, output text.
- `Phi-4` and `Phi-4-reasoning`: input text, output text.
Many Azure OpenAI chat models are also multimodal ("text and image input with text output"). Checking the input modalities in the catalog is the first filter when a scenario involves photos, scans or audio.
## Example
Request: an image of a parcel with a torn, wet corner plus "crush or water damage?" A multimodal model answers "The staining and warped cardboard indicate water damage; use form WD-2."
W: Phi-4-multimodal-instruct: the request contains a photo and a text question, and this model's catalog entry lists text, image and audio input with text output, so it can look at the parcel and answer in text.
X: A=Phi-4-mini-instruct: its catalog entry lists text input only, so the assistant would depend on staff describing the damage in words and the uploaded photo would be ignored.
B=Phi-4-mini-reasoning: reasoning helps with the decision, but this model also takes text input only, so it cannot inspect the photo that the whole scenario depends on.
D=Phi-4: the catalog lists Phi-4 as text in and text out; model size does not add image input, so the photo still could not be processed.
T: When users send images or audio, first filter the catalog by input modality and pick a multimodal model that accepts them.
V: Foundry Models, Phi

@ AI-103 D1 T1.1 applied comparison
S: A health insurer is designing a call-center solution in Microsoft Foundry. For which TWO requirements is a Foundry Tool a better fit than prompting a general-purpose chat model? (Select TWO)
A: Turning live phone audio into a text transcript while the call is still in progress, so the transcript can feed the rest of the solution.
B: Writing an empathetic first-draft reply to a member who complained in an email about a delayed claim payment last month.
C: Detecting and redacting names, phone numbers and policy numbers in transcripts with a fixed set of entity categories before storage.
D: Answering an open-ended member question by combining several retrieved policy passages into one clear, well-structured explanation.
E: Rewriting a long, technical internal policy note into plain language that a new call-center employee can understand on day one.
K: A,C
G: ## Foundry Tools versus models
**Foundry Tools** (formerly Azure AI services) are prebuilt, task-specific APIs: Azure Speech, Azure Language, Azure Translator, Azure Content Understanding, Azure Vision, Content Safety and others. You send data and receive a specific, predictable result without designing prompts.
**Generative models** in Foundry Models are general-purpose: they write, explain and reason, which makes them flexible but less predictable for a narrow, well-defined job.
## A practical rule
- Use a **Foundry Tool** when the task has a fixed output contract (a transcript, a list of PII entities with categories and offsets, a translation) and the service is designed for it, such as streaming audio.
- Use a **model** when the output is new, open-ended language: drafting, explaining, combining sources.
## The two tools here
- **Azure Speech in Foundry Tools**: speech to text, including real-time transcription of streaming audio.
- **Azure Language in Foundry Tools**: PII detection returns entities with categories and can return redacted text. PII detection is part of Language's core features (some other Language features, such as summarization and sentiment, are marked legacy).
W: A=Live transcription: streaming audio to text during a call is the core job of Azure Speech, which handles the audio stream directly; a chat model would still need a transcript before it could do anything.
C=PII redaction: Azure Language PII detection returns a consistent, category-based result with redacted text, which is more predictable for compliance than asking a chat model to find and mask personal data.
X: B=Empathetic draft reply: writing new, tone-aware prose from a complaint is a generative task that a chat model handles well, and no prebuilt Foundry Tool writes customer replies.
D=Combining retrieved passages: synthesizing several sources into one explanation is the generation step of a RAG pattern, which is what a chat model is for.
E=Plain-language rewrite: rewriting for a new audience is open-ended generation where a chat model's flexibility helps; a prebuilt API would not adapt style and level of detail this way.
T: Pick a Foundry Tool for narrow jobs with a fixed output contract (speech to text, PII detection); pick a generative model for open-ended writing and synthesis.
V: Azure Speech in Foundry Tools, Azure Language in Foundry Tools

@ AI-103 D1 T1.1 applied use-case
S: A mortgage lender receives application packs that mix scanned PDFs, phone photos of payslips and short recorded voice statements. It must turn each pack into the same JSON schema (applicant name, employer, monthly income and so on) with a confidence score and source location for every field, so low-confidence values go to human review. Which Foundry service should be the core of this pipeline?
A: A general chat model prompted to return JSON for each file, because structured outputs guarantee that every field value is correct.
B: Azure AI Search with integrated vectorization, because indexing the pack makes every field searchable for the reviewers afterwards.
C: Azure Translator in Foundry Tools, because converting every file to one language first is the step that produces consistent fields.
D: Azure Content Understanding in Foundry Tools, using an analyzer with a field schema that returns values with confidence and grounding.
K: D
G: ## Azure Content Understanding
**Azure Content Understanding in Foundry Tools** uses generative AI to process documents, images, video and audio into a **user-defined output format**. You define a schema of fields; an **analyzer** extracts, classifies or generates each value.
Key points from Microsoft Learn:
- It returns **confidence scores and grounding** for extracted values, so automation can route uncertain fields to people ("straight-through processing").
- It handles several modalities in one service, including audio.
- It offers prebuilt analyzers (for example for procurement documents, contracts and call analytics) and classification to route documents to the right analyzer.
- API version `2025-11-01` is GA; later preview versions add extra features.
## Why not just prompt a model?
A chat model with structured outputs guarantees the JSON **shape**, not the correctness of each value, and it gives no per-field confidence or source location. Content Understanding is built for exactly that audit trail.
## Example
A payslip photo returns `MonthlyIncome: 4,250.00` with confidence `0.93` and the bounding region where it was read; a blurry value at `0.41` goes to a reviewer.
W: Content Understanding: one service ingests documents, images and audio into a defined field schema and returns confidence and grounding per field, which is exactly what the lender needs to automate high-confidence values and review the rest.
X: A=Chat model with JSON output: structured outputs enforce the format of the response, not the accuracy of each value, and they provide no per-field confidence or source location for routing to reviewers.
B=Azure AI Search with integrated vectorization: indexing makes content findable by query, but it does not extract named fields such as monthly income into a schema with confidence scores.
C=Azure Translator: translation changes the language of the text but extracts nothing; the packs would still need a separate service to produce the fields.
T: To turn mixed documents, images and audio into a fixed field schema with confidence and grounding, choose Azure Content Understanding.
V: Azure Content Understanding in Foundry Tools

@ AI-103 D1 T1.1 applied use-case
S: A travel company's Foundry agent must answer questions such as "Are there strikes affecting Paris airports today?" using information published in the last few hours on public websites, with citations the user can follow. Which grounding option should the developer add to the agent?
A: The file search tool with a vector store of travel advisories, because uploaded files give the agent a curated and citable source of truth.

G: ## The knowledge cutoff problem
Every Foundry model has a **knowledge cutoff**: it cannot know about events after its training data ends. For "what is happening today" questions, the agent needs a tool that fetches fresh public information at query time.
## Web grounding in Foundry Agent Service
The **web search tool** lets the agent's model retrieve real-time information from the public web before answering and return **inline citations**. It uses Grounding with Bing Search, and Grounding with Bing Custom Search when results must come only from domains you configure.
Things to know before choosing it:
- It incurs extra cost.
- Microsoft Learn notes that the Microsoft Data Protection Addendum does not apply to data sent to Grounding with Bing, and that data transfers can occur outside compliance and geographic boundaries. Admins can manage access to it.

- Your own curated documents: file search or Azure AI Search.
- Current public web content: web search (Grounding with Bing).

D=Azure AI Search over crawled pages: an index is only as fresh as its last indexer run and covers only the pages you chose, so breaking news elsewhere on the web would be missed.

@ AI-103 D1 T1.1 applied use-case
S: A university runs five assistant applications (admissions, finance, housing, IT and library) that must all ground answers on the same content: policy PDFs in Azure Blob Storage, a curated Azure AI Search index and selected public web pages. The team wants to define this content once as a reusable retrieval resource that every assistant calls, which returns source passages with citations and can be shared across assistants without copying data. Which option fits best?
A: A separate file search vector store for each assistant, each holding its own uploaded copy of the policy PDFs and saved web pages.
B: A Foundry IQ knowledge base with Blob Storage, search index and web knowledge sources, which all five assistants query for retrieval.
C: Memory in Foundry Agent Service shared by all assistants, so facts learned from one student conversation are reused by the others.
D: Fine-tuning one model on all policy content and deploying it to every assistant, so the knowledge is built into the model weights.

G: ## What Foundry IQ is
**Foundry IQ** is a managed knowledge layer for agents and apps. You create a **knowledge base** that references one or more **knowledge sources** (connections to indexed or remote content) and set retrieval parameters. Azure AI Search provides the indexing and retrieval underneath.
- **Multiple agents can share the same knowledge base**, and any custom application can call it through the knowledge base REST API or the Azure AI Search SDKs.
- For indexed sources such as Blob Storage it automates chunking, vector embedding and indexer refresh.
- It returns **extractive content with citations** so the caller can trace each answer to its source document.
## GA versus preview
Some Foundry IQ features are GA and others are preview, depending on the Search REST API version:
- GA in `2026-04-01`: knowledge bases with `searchIndex`, `azureBlob`, `indexedOneLake` and `web` knowledge sources, and a retrieve call that returns extractive grounding content with references.
- Still preview: LLM query planning (non-minimal reasoning effort), answer synthesis, multi-turn messages, query-time ACL enforcement, SharePoint and other source types, and connecting a knowledge base to a Foundry Agent Service agent through its MCP endpoint. The Foundry and Azure portals expose agentic retrieval through preview schemas.
## Example
The housing assistant sends "Can I defer my housing deposit?" to the shared knowledge base; it searches the policy PDFs, the curated index and the web source and returns cited passages that the assistant's model uses to answer.
W: Foundry IQ knowledge base: one knowledge base combines Blob, search index and web knowledge sources (all GA source types in the `2026-04-01` API), is defined once and called by all five assistants, and returns extractive passages with citations.
X: A=Separate file search stores: five uploaded copies drift apart whenever a policy changes, duplicate storage and give no single place to manage the shared content.
C=Shared memory: memory (preview) stores user-specific context learned from conversations; it is not a governed store of university policy, and sharing one student's details with other assistants would be a privacy problem.
D=Fine-tuning on policy content: fine-tuning does not reliably teach facts, cannot cite sources and must be redone whenever a policy changes.
T: When many agents or apps need the same multi-source, cited knowledge defined once, use one Foundry IQ knowledge base.

@ AI-103 D1 T1.1 applied tradeoff
S: An online parts retailer's search in Azure AI Search must handle two kinds of queries: exact part numbers such as "XR-2210-B" and natural questions such as "pump that keeps losing pressure". Today pure vector queries miss many part numbers, and users complain that the best match is often not in the top three results. Which TWO choices address both problems? (Select TWO)
A: Send hybrid queries that run full-text and vector search in one request and merge the two result lists with Reciprocal Rank Fusion.
B: Enable semantic ranker so the top results are reranked by a language understanding model that scores how well they match the query.
C: Replace the embedding model with a larger one, because larger vectors also match exact part numbers as reliably as keyword search does.
D: Add suggesters for autocomplete to the index, because type-ahead suggestions reorder the result list by meaning when the query runs.
E: Switch the vector fields from HNSW to exhaustive KNN, because exact neighbor search fixes the ranking of keyword-style part numbers.
K: A,B
G: ## Keyword, vector and hybrid search
- **Full-text (keyword) search** ranks with BM25 and excels at **exact matches**: product codes, jargon, dates and names.
- **Vector search** compares embeddings and excels at **conceptual similarity**, even with no shared words.
- **Hybrid search** is one request with both `search` and `vectorQueries`. Azure AI Search runs both in parallel and merges results with **Reciprocal Rank Fusion (RRF)** into one result set.
## Semantic ranker
Semantic ranker is a premium, usage-billed feature that adds **secondary (L2) ranking** over the initial BM25 or RRF results, using multilingual deep learning models adapted from Microsoft Bing. It reranks up to the top 50 results, returns `@search.rerankerScore` and can return captions and answers. Microsoft Learn notes that hybrid retrieval with semantic ranker gives significant relevance benefits in benchmark testing.
## Example
"XR-2210-B" is found by the keyword half of a hybrid query; "pump that keeps losing pressure" is found by the vector half; semantic ranker then promotes the most relevant documents into the top three.
W: A=Hybrid queries: adding the full-text side brings back exact matches for part numbers that vector search misses, while the vector side still handles natural-language questions, and RRF merges both into one list.
B=Semantic ranker: L2 reranking over the merged results uses language understanding to push the most relevant documents to the top, which addresses the "best match is not in the top three" complaint.
X: C=Larger embedding model: a bigger embedding model improves conceptual matching but still does not provide the exact-token matching that part numbers need; that is what keyword search is for.
D=Suggesters for autocomplete: suggesters power type-ahead as the user types; they do not change how executed queries are ranked, and autocomplete is not part of vector queries.
E=Exhaustive KNN: exhaustive search returns exact nearest neighbors in vector space, but part numbers still fail as vectors, and exact KNN is slower without adding keyword matching.
T: Use hybrid search to cover both exact terms and meaning, and add semantic ranker to improve the order of the top results.
V: Azure AI Search

@ AI-103 D1 T1.1 applied use-case
S: A global HR team stores policy documents written in English, German and Japanese in one Azure AI Search index. Employees ask questions in their own language and expect to find the relevant policy even when it is written in another language and uses different wording. Which retrieval approach should the developer choose?
A: Full-text search with a language analyzer per field, because stemming in each language matches the same policy across all three languages.
B: A scoring profile that boosts recent documents, because the newest version of each policy is the one employees most likely want to see.
C: Faceted navigation on a language field, because employees can filter to their own language and then browse the matching policies.
D: Vector search with a multilingual embedding model applied to both the content and the query, so matching is based on meaning across languages.

G: ## Why vectors cross language boundaries
Vector search matches on numeric representations of meaning. Microsoft Learn lists the scenarios this enables:
- **Semantic likeness**: "dog" and "canine".
- **Multilingual content**: "dog" in English and "hund" in German.
- **Multiple content types**: text and images with a multimodal embedding model.
For cross-language retrieval the **same multilingual embedding model** must embed both the indexed chunks and the query, so a German question and an English policy land near each other in vector space.
## Where keyword search still helps
Language analyzers improve keyword search **within** one language (stemming, stop words). They do not translate, so a German query term never matches an English document by keywords. You can still combine both in a hybrid query.
## Example
Query: "Wie viele Urlaubstage habe ich?" returns the English "Annual leave entitlement" policy because both vectors express the same meaning.
W: Vector search with a multilingual embedding model: matching on meaning rather than words lets a query in one language retrieve a policy written in another language with different wording.
X: A=Language analyzers: analyzers improve keyword matching within a single language, but they do not translate, so a German query term still cannot match an English or Japanese document.
B=Freshness scoring profile: boosting recent documents changes the order of results that already matched; it does nothing to match queries and documents across languages.
C=Facets on a language field: filtering to the user's own language hides exactly the documents written in other languages, which is the opposite of the requirement.
T: For "same meaning, different language or wording" retrieval, use vector search with one multilingual embedding model for both content and queries.

G: ## Short-term and long-term memory
Microsoft Learn separates two categories:
- **Short-term memory** tracks the **current session's** conversation. Agent orchestration manages it as session context.
- **Long-term memory** keeps distilled knowledge **across sessions**, which needs a persistent system that extracts and consolidates facts.
## How Foundry Agent Service handles each
- Current agents use **agents + conversations + responses**: a **conversation** is a durable object that stores the items (messages, tool calls) of a chat and is passed with each response so the model sees earlier turns. It persists until you delete it (`conversations.delete`), so the app removes it when the chat ends. (The classic threads/messages/runs model is deprecated.)
- **Memory in Foundry Agent Service** is a managed long-term memory store (user profile, chat summary and procedural memory) for continuity across sessions. It is currently in **public preview**.
## Choosing
If context must last only for this chat, keep it in the conversation. Use long-term memory only when personalization across sessions is a requirement and allowed by policy.
W: Conversation object: it holds the current chat's turns so the agent can use earlier details on every response, nothing is extracted into a cross-session store, and the app deletes the conversation when the chat ends, which fits the no-retention policy.
X: A=Memory with user profile memory: long-term memory deliberately persists extracted facts across sessions, which violates the bank's no-retention policy (and the feature is still in preview).
B=Foundry IQ over transcripts: a knowledge base is a curated, shared organizational source; indexing chat transcripts would retain customer data and is far more than needed for in-session context.
D=File search vector store of messages: writing messages to a vector store creates a persistent copy and adds retrieval steps, when the conversation already carries the earlier turns.
T: Keep in-session context in the conversation; use long-term memory only when information must deliberately persist across sessions.

D=File search over the spec: retrieving text about the endpoints lets the agent describe the API, but it never actually calls it to get a shipment status.

@ AI-103 D1 T1.1 applied tradeoff
S: A software company's in-product assistant receives a mix of requests: many simple ones ("rename this file") and some hard ones ("why does this query deadlock under load?"). The team wants one deployment that sends simple prompts to cheaper models and hard prompts to stronger or reasoning models, without writing its own routing code. Which Foundry option should it choose?
A: Two separate deployments, one small and one large, with a keyword rule in the app that sends prompts containing "why" to the large one.
B: A single reasoning model deployment with maximum reasoning effort for every request, so hard prompts are always handled correctly.
C: Model router, deployed as one model in Balanced mode, which picks a suitable underlying model per prompt based on complexity and cost.
D: A fine-tuned small model trained on past hard prompts, so that one inexpensive model learns to answer both simple and hard requests.
K: C
G: ## What model router does
**Model router** is a trained language model that you deploy like any other Foundry model. For each request it analyzes the prompt (complexity, reasoning needs, task type) and routes it to a suitable underlying LLM. Smaller, cheaper models handle easy prompts; larger or **reasoning** models handle complex ones.
## Routing modes
- **Balanced** (default): considers models within a small quality range of the best model for that prompt and picks the most cost-effective.
- **Cost**: allows a larger quality band to save more.
- **Quality**: always picks the highest-rated model, ignoring cost.
You can also restrict routing to a **model subset**. Note that the effective context window is limited by the smallest underlying model, and you should evaluate the router against your current baseline.
## Example
"Rename this file" is routed to a small, cheap model; "Why does this query deadlock under load?" is routed to a reasoning model, all through one deployment name in your code.
W: Model router: one deployment analyzes each prompt and routes simple ones to cheaper models and complex ones to stronger or reasoning models, which is exactly the managed, no-custom-code routing the team wants.
X: A=Keyword rule across two deployments: this is the custom routing code the team wants to avoid, and a word like "why" is a poor proxy for how hard a prompt actually is.
B=Reasoning model with maximum effort for everything: hard prompts are handled, but every simple request also pays reasoning latency and tokens, which defeats the cost goal.
D=Fine-tuned small model: fine-tuning cannot give a small model the reasoning capacity of a much larger one, and the team would still have one model for all prompt difficulties.
T: To match each prompt to a cheaper or stronger model automatically behind one deployment, choose model router.
