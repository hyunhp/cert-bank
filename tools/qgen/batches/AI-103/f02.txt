@ AI-103 D1 T1.2 advanced tradeoff
S: Two business units share one Foundry resource and each has its own Foundry project. Both projects call the Translator API. Compliance now requires that users in one unit must not be able to use the other unit's Translator access. What should the architect do?
A: Assign the Foundry User role on each project only, because the Translator API is served from the project endpoint and inherits project-level role assignments.
B: Give each team a separate Foundry resource, because Translator is served only at resource scope and Learn lists no project-level RBAC isolation for it.
C: Create a project connection to Translator in each project, because project connections give each unit a private Translator endpoint scoped to its own project.
D: Add a private endpoint for each project in a separate subnet, because network paths per project keep each unit's Translator requests apart from the other unit.
K: B
G: ## Not every API is project-scoped
Most newer, agent-centric Foundry APIs (agents, responses, evaluations, datasets, indexes, files) support **project-scope** permissions, so one Foundry resource with a project per team gives real isolation. Some APIs inherited from the older Foundry Tools accounts work only at the **Foundry resource** scope.
Learn names **Translator** as an example: it is available only from the Foundry resource level, not at the project scope. The rollout guidance's capability table lists Translator with no project organization, no project-level RBAC isolation, and the advice *"Use separate Foundry resource if isolation is a must."*
## Design rule
Before choosing a topology, list the APIs each workload needs. If a required API only works at resource scope, either assign roles at that scope (accepting shared access) or isolate the workloads into separate Foundry resources.
## Example
Unit A keeps `contoso-foundry-a` and Unit B moves to `contoso-foundry-b`. Each unit's Entra group gets roles only on its own resource, so neither can call the other's Translator endpoint.
W: Separate Foundry resource: Translator is reachable only at the resource level, so the only way to keep one unit from using the other's Translator access is a resource boundary between them.
X: A=Project-scoped roles: Translator is not served at project scope, so project role assignments cannot separate the two units' Translator usage.
C=Project connections: connections reference other resources for a project's tools and data; they do not turn the resource-level Translator API into a project-isolated one.
D=Per-project private endpoints: private endpoints control network paths to the resource, not which authenticated users may call a resource-level API.
T: Check API scope before sharing a Foundry resource: resource-level-only APIs such as Translator need a separate Foundry resource when isolation is required.
V: Microsoft Foundry, Azure Translator in Foundry Tools

@ AI-103 D2 T2.3 applied use-case
S: A high-volume FAQ bot sends simple and occasionally complex prompts. The team wants one Foundry deployment that sends easy prompts to cheaper models and hard prompts to stronger ones, while only ever using three models approved by their compliance team. What should they deploy?
A: A single deployment of the largest approved model with temperature set low, because a stronger model makes routing between models unnecessary
B: A model router deployment using Custom deploy with the Cost routing mode and a model subset restricted to the cleared list
C: Three separate model deployments with a load balancer that spreads requests evenly across them, so each model receives a third of the traffic
D: A model router deployment using Custom deploy with the Quality routing mode and every supported model left in the routing pool
K: B
G: ## What model router does
**Model router** is a trained language model, deployed like any other Foundry model, that routes each prompt **in real time** to the most suitable underlying LLM based on complexity, reasoning needs and task type. Smaller, cheaper models handle easy prompts; larger or reasoning models handle hard ones, all behind **one deployment**.
## Custom deploy options
- **Routing mode**: **Balanced** (default) picks the most cost-effective model within a small quality band; **Cost** widens the band for more savings (high-volume, budget-sensitive workloads); **Quality** picks the highest-quality model regardless of cost.
- **Model subset**: choose which underlying models may be used. New models aren't added unless you include them, which supports compliance. The subset also acts as the fallback set, so include at least two models to benefit from automatic failover.
## Example
Custom deploy → routing mode Cost → subset: the three approved models. The app calls the router deployment name like any chat model.
W: Model router with Cost mode and a model subset: the router picks a model per prompt, Cost mode favors cheaper models for a high-volume bot, and the subset keeps every request on the three approved models.
X: A=One large model: it works but pays large-model prices for every simple FAQ, which is what the team wants to avoid.
C=Even load balancing: spreading traffic by thirds ignores prompt difficulty, so easy prompts still hit expensive models and hard prompts hit weak ones.
D=Quality mode with every model: Quality mode picks the highest-quality model regardless of cost, and leaving every model in the pool lets the router use models outside the approved list.
T: Model router = per-prompt model choice behind one deployment; tune it with routing mode (Balanced, Cost, Quality) and a model subset.

@ AI-103 D1 T1.2 applied comparison
S: A team is starting a new agent solution and plans to use the Responses API, the unified `azure-ai-projects` 2.x client and the new Foundry portal. A colleague suggests creating an AI hub because an older tutorial did so. Which project type should the team create?
A: A Foundry project under a Foundry resource, because Microsoft's current investment and the GA Agent Service are focused on that kind of project.
B: A hub-based project and a separate Foundry resource, because the hub stores agent definitions while the Foundry resource only hosts model deployments.
C: A standalone Azure OpenAI resource with no project, because agents and evaluations run directly on the Azure OpenAI endpoint and need no project scope.
D: A hub-based project under an AI hub, because hubs are still required to host agents and to connect a project to Azure OpenAI model deployments.
K: A
G: ## Two project types
Foundry has had two project types:
- **Foundry project**: a child resource of a Foundry resource (`Microsoft.CognitiveServices/accounts/projects`). It works with the new Foundry portal, the Responses-based Agent Service (agents, conversations, responses, agent versions) and one project endpoint used by the `azure-ai-projects` 2.x client and the OpenAI client.
- **Hub-based project**: hosted by a Foundry **hub** (the older resource model of hub + Azure OpenAI + Azure AI Services). Hub-based projects are reached through the **Foundry (classic)** portal, which Learn suggests when you need features not yet in the current portal, such as prompt flow.
## Which one to start with
Learn states that **new investments are focused on Foundry projects** in the new portal, and that new agents and model-centric capabilities, including Foundry Agent Service in general availability, are **only available on Foundry projects**. The architecture guidance names a Foundry resource with one project as the recommended default, and the deployments overview notes that Serverless API deployments on a Foundry resource require **no AI hub**.
## Example
The team creates `contoso-foundry` (Foundry resource) with project `support-agents`, deploys a model on the resource and builds its agent against `https://contoso-foundry.services.ai.azure.com/api/projects/support-agents`.
W: Foundry project: the new portal, the current Agent Service with the Responses API and the unified project client all work against a Foundry project, which needs no AI hub.
X: B=Hub plus Foundry resource: agent definitions are project assets in a Foundry project; splitting the work across a hub and a separate resource recreates the older multi-resource model.
C=Standalone Azure OpenAI: Learn notes a standalone Azure OpenAI resource might suffice for completions only; agents, evaluations and project assets need a Foundry resource and project.
D=Hub-based project: hubs are not required for agents or model deployments; the current Agent Service is available only on Foundry projects, and hubs remain the classic option for features such as prompt flow.
T: New agent work starts with a Foundry resource and a Foundry project; hub-based projects are the classic option for features the new portal does not yet offer.
V: Microsoft Foundry, Foundry Agent Service
