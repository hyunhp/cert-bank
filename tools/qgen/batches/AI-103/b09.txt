@ AI-103 D4 T4.1 applied troubleshooting
S: A retailer routes customer reviews from its France-only web shop to reviewers by language with Azure Language language detection. Very short reviews such as "Communication" or "Excellent" are often returned as English with a low confidence score. The reviews are almost always French. What should the developer change?
A: Send countryHint set to "fr" with each document, so ambiguous text is resolved with France as the origin
B: Set the language field of each document to "fr", because language detection needs the input language first
C: Run key phrase extraction first and send only the returned phrases to language detection for a better score
D: Transliterate each review to Latin script with Translator first, so the detector can recognize French words
K: A
G: ## How language detection decides
Language detection is a **core** Azure Language capability. For each document it returns one predominant language with its name, **ISO 639-1** code (`iso6391Name`), a **confidence score** between 0 and 1, and the script name and ISO 15924 script code.
## Ambiguous content and countryHint
Some words exist in several languages: Learn's example is "communication", which is both English and French. With little context the model uses a **country hint**, and by default the API uses **"US"**, which pushes ambiguous text toward English.
- `countryHint` takes an ISO 3166-1 alpha-2 code, for example `"fr"`, to tell the model where the text comes from.
- Setting `countryHint` to an empty string removes the default US preference.
- Learn notes the hint only matters when confidence is below 0.8, which is exactly the short, ambiguous case.
## Example
```
{"kind": "LanguageDetection", "analysisInput": {"documents": [{"id": "1", "text": "Communication", "countryHint": "fr"}]}}
```
Other outputs to handle: text that can't be parsed (for example only numbers) returns `(Unknown)`, and mixed-language text returns the language with the largest share at a lower score.
W: countryHint fr: the default US hint tips ambiguous words toward English; telling the model the text comes from France resolves the short reviews to French.
X: B=Declare the language first: language detection is the feature that finds the language, so documents carry a countryHint, not a declared language; a known language would make the call pointless.
C=Key phrases first: extracting phrases makes the input even shorter and adds a legacy feature, so the ambiguity gets worse, not better.
D=Transliterate first: French is already written in Latin script, so changing script does nothing to the English versus French ambiguity.
T: For short or ambiguous text, pass countryHint to language detection, because the API otherwise assumes US origin.
V: Azure Language in Foundry Tools, language detection

@ AI-103 D4 T4.1 applied use-case
S: A scheduling assistant reads meeting request emails and must pull out dates, times and money amounts such as "next Friday at 3 pm" or "eighty euros" with character offsets and in a consistent machine-readable form. There is no labeled data, and the team wants a core, non-generative Azure Language feature. Which feature should it call?
A: Prebuilt named entity recognition, which returns DateTime and Currency entities with offsets and resolved metadata
B: Custom named entity recognition, which returns DateTime and Currency entities once labeled emails are used to train it
C: Key phrase extraction, which returns phrases such as "next Friday" as a plain list without categories or values
D: Entity linking, which links every date and amount found in an email to its Wikipedia article to resolve its value
K: A
G: ## Prebuilt NER
**Prebuilt named entity recognition** is a core Azure Language capability. It identifies entities in unstructured text and assigns them to a preset list of types, including `Person`, `Organization`, `Location`, `DateTime` (with `Date`, `Time`, `DateRange` and similar), `Currency`, `Number`, `Quantity`-style types and more. Each entity comes back with its `type`, `offset`, `length` and `confidenceScore`; no training is needed.
## Entity metadata
For numeric and temporal entities, NER can add a **metadata** object with a standardized resolution. Learn's examples: "eighty" and "80" both resolve to the integer 80, and date and time entities can be resolved for "integration with a meeting scheduling system". Currency metadata includes the value, unit and ISO 4217 code.
## Choosing among Language features
- No training data and standard categories: **prebuilt NER**
- Your own categories with labeled data: **custom NER**
- Main concepts as a list: key phrase extraction (legacy, no categories)
W: Prebuilt NER: its predefined DateTime and Currency types cover these values without training, and it returns offsets plus metadata resolutions that turn "eighty" into 80.
X: B=Custom NER: it is for categories you define and requires labeled training data, which the team doesn't have; the needed categories already exist in prebuilt NER.
C=Key phrase extraction: it returns main concepts as plain strings with no entity type, offsets or resolved values, and it is a legacy capability.
D=Entity linking: it disambiguates well-known entities against Wikipedia; dates and amounts have no Wikipedia article and get no resolved value.
T: Use prebuilt NER for standard entity types such as dates and currencies; its metadata gives normalized values without any training.

G: ## Core and legacy capabilities in Azure Language
Learn's Azure Language overview splits features into two groups:
- **Core capabilities**: "recommended for new development and long-term planning" and still receiving feature investment. They are **PII detection**, **language detection**, **named entity recognition** (prebuilt NER and custom NER) and **Text analytics for health**.
- **Legacy capabilities**: "supported for existing implementations". These legacy features are scheduled to retire on 2029-03-31.
## What this means for design
For tasks such as summaries, topics or sentiment in a new solution, the usual path is generative prompting on a Foundry model (with structured outputs), while core Language features remain the choice for deterministic PII, NER and health extraction with offsets and confidence scores.

D=Sentiment and opinion mining: also a legacy capability; new sentiment and tone work is usually done with generative prompting instead.
E=Conversational language understanding: CLU sits in the legacy group together with orchestration workflow and question answering.
T: Azure Language core capabilities are PII detection, language detection, NER (prebuilt and custom) and Text analytics for health; sentiment, key phrases, summarization and CLU are legacy.

@ AI-103 D4 T4.1 applied use-case
S: A software company wants every piece of customer feedback tagged with one or more topics from its own fixed list of 12 product areas, such as Billing, Onboarding and Mobile app. The tags feed a dashboard, so only values from the list are allowed. This is a new solution. Which approach fits best?
A: Prompt a Foundry chat model with the 12 areas and a strict output schema whose topics array uses an enum of those areas
B: Call Azure Language key phrase extraction and use the returned phrases directly as the topic labels on the dashboard
C: Call Azure Language entity linking and map each linked Wikipedia article to the nearest of the 12 product areas
D: Call Azure Language language detection first and assign each detected language to one of the 12 product areas
K: A
G: ## Topics are a classification problem
"Topics" can mean two different things:
- **Open-ended phrases** that appear in the text (for example "late invoice email"). Key phrase extraction returns these, but it is a **legacy** Azure Language capability and its output is free text, not your categories.
- **Labels from a fixed taxonomy** (Billing, Onboarding...). That is classification into known values.
## Generative prompting with an enum
A chat model can read the feedback, understand paraphrases ("I was charged twice" means Billing) and choose labels. Putting the allowed values in a JSON Schema `enum` inside a strict structured output guarantees the reply only contains valid labels:
```
"topics": {"type": "array", "items": {"type": "string", "enum": ["Billing", "Onboarding", "Mobile app", "..."]}}
```
Include short definitions of each area in the system message so borderline cases are labeled consistently, and evaluate on a labeled sample before release.
W: Chat model with an enum schema: the model maps paraphrased feedback to the company's own areas, and the strict schema enum makes values outside the list impossible, which the dashboard requires.
X: B=Key phrase extraction: it returns phrases taken from each text, not labels from the company list, and it is a legacy capability rather than one recommended for new solutions.
C=Entity linking: it links named entities to Wikipedia articles, which says nothing reliable about product areas such as Billing or Onboarding, and it is also a legacy feature.
D=Language detection: it identifies which language the text is written in; a language code is unrelated to the product area the customer is writing about.
T: To tag text with topics from a fixed taxonomy, prompt a chat model and enforce the allowed values with an enum in a strict output schema.

@ AI-103 D4 T4.1 applied use-case
S: A help desk stores ticket text in a data lake. Compliance wants only credit card numbers and phone numbers masked; names must stay readable for agents. The team uses Azure Language PII detection with the generally available API. How should the request be configured?
A: Set piiCategories to the credit card and phone number categories so only those entities are detected and masked in redactedText
B: Leave the categories at their default and remove person names from redactedText afterwards by copying them back from the original text
C: Set the language parameter to an unsupported value so the service skips person detection and returns only numeric entities
D: Send each ticket to Text analytics for health, because it masks financial and contact identifiers while leaving names untouched
K: A
G: ## How PII detection redacts
The `PiiEntityRecognition` task returns, for each document:
- `entities`: each detected item with `category`, `offset`, `length` and `confidenceScore`
- `redactedText`: the input with detected entities masked. With the default **character mask**, each character of an entity is replaced by `*`, so length and offsets are preserved.
## Choosing what is detected
By default the API looks for all categories enabled for the input language. The optional **`piiCategories`** parameter restricts detection to the categories you list (and can enable categories that are off by default). Learn's tip: if you don't include `default` in the list, only the listed categories are returned.
## GA versus preview parameters
Newer controls such as `redactionPolicies` (entity mask, synthetic replacement), `confidenceScoreThreshold` and `disableEntityValidation` were introduced with preview API versions; synthetic replacement is explicitly a preview feature. Production code should use the GA API version and only GA parameters.
W: piiCategories filter: listing only the needed categories means only card and phone numbers are detected, so redactedText masks exactly those and leaves names readable.
X: B=Post-processing names back: this undoes masking by hand from the original text, which is fragile and still sends names through detection when the API can simply be told which categories to look for.
C=Unsupported language value: an invalid language code causes errors or poor detection for every category; it is not a way to choose entity types.
D=Text analytics for health: it extracts medical concepts such as medications and diagnoses from clinical text; it is not a PII masking service for help desk tickets.
T: Use the piiCategories parameter to limit Azure Language PII detection, and therefore redaction, to the entity types compliance asks for.

@ AI-103 D4 T4.1 applied comparison
S: A law firm must share signed contracts (PDF and DOCX) with an external auditor after removing personal data, and the auditor needs files that keep the original layout plus a machine-readable list of what was removed. Which Azure Language PII feature type fits?

G: ## Three PII feature types
Azure Language PII detection is a core capability with three feature types, chosen by the shape of the input:
- **Text PII**: synchronous, for raw strings such as prompts, logs and tickets.
- **Conversation PII**: asynchronous jobs over turn-based chat or call transcripts, using conversational context.
- **Document-based PII**: asynchronous, storage-based processing of **native files** (`.pdf`, `.docx`, `.txt`). It returns redacted files that keep document fidelity, plus JSON metadata about the detected entities. Learn lists "compliance workflows and document sharing" as its best fit.
## Why not extract text first?
Converting a PDF to plain text and using Text PII loses layout, so the auditor would get text, not the contract. The document feature keeps the structure.
W: Document-based PII: it works on native PDF and DOCX files and returns redacted documents that preserve layout together with machine-readable metadata, exactly what the auditor needs.
X: B=Text PII: it is built for strings; the firm would have to flatten the contracts to text and would lose the original document layout.
C=Conversation PII: it is tuned for multi-turn transcripts and chat, not for contract files.
D=Prebuilt NER: it labels entities in text but does not produce redacted files; PII detection is the feature designed for redaction.
T: Pick the PII feature type by input: Text PII for strings, Conversation PII for transcripts, Document-based PII for native files that must keep their layout.

@ AI-103 D4 T4.1 applied tradeoff
S: An insurer must extract internal entity types (policy rider codes, coverage clause names, adjuster IDs) from claim notes. Auditors require each entity's character offset and a confidence score, and the label set must stay stable across releases. The team has 400 labeled notes. Which approach meets these requirements best?
A: Train an Azure Language custom NER model on the labeled notes and call it for the predicted entities with offsets

G: ## Custom NER in Azure Language
**Custom named entity recognition** (a core capability) lets you define your own entity categories, label example documents, train a model and deploy it. At runtime it returns each entity with its category, **offset**, **length** and **confidence score**, the same shape as the prebuilt NER output.
## Comparing with generative extraction
A chat model with structured outputs is a strong option when there is no labeled data or the categories change often. Its trade-offs for this scenario:
- It does not return character offsets or calibrated confidence scores by itself.
- Model updates can change behavior, so stability depends on pinning versions and re-evaluating.
With labeled data already available and an audit requirement for offsets and scores, the trained model is the closer fit.
W: Custom NER: it learns the insurer's own entity types from labeled notes and returns offsets and confidence scores per entity from a versioned, deployed model.

C=Chat model in prose then search: prose output has no offsets or scores, and searching for phrases afterwards can match the wrong occurrence in a long note.
D=Key phrase extraction then filtering: it returns main concepts without entity categories, so the team would guess types from the text, and it is a legacy feature.

@ AI-103 D4 T4.1 applied use-case
S: A logistics company receives customer names and street addresses in Cyrillic from its Russian web shop. Courier labels must show the same names and streets in Latin letters so that drivers can read them, and the words must not be translated into English. Which Azure Translator operation fits?
A: Transliterate with language ru, fromScript Cyrl and toScript Latn, which changes only the script and keeps the words

K: A
G: ## Translation versus transliteration
Azure Translator text translation (latest GA version `2026-06-06`) has three core operations: **Languages**, **Translate** and **Transliterate**.
- **Translate** changes the *meaning* into another language: "улица Ленина" becomes "Lenin Street".
- **Transliterate** maps text from one **script** to another without translating it. Learn: "Unlike translation, transliteration doesn't return the meaning, only the way the text is written." The same street becomes "ulitsa Lenina".
## Request parameters
Transliterate takes `language` (the language of the input, for example `ru`), `fromScript` (for example `Cyrl`) and `toScript` (for example `Latn`):
```
POST https://api.cognitive.microsofttranslator.com/transliterate?api-version=2026-06-06&language=ru&fromScript=Cyrl&toScript=Latn
{"inputs": [{"text": "улица Ленина"}]}
```
The Languages operation lists which language and script pairs support transliteration.
W: Transliterate Cyrl to Latn: it rewrites names and streets in Latin letters while keeping the original Russian words, which is what couriers and the delivery address need.
X: B=Translate to English: translation changes the words themselves, so street names would no longer match the real address the courier must find.
C=notranslate markup: it tells Translator to leave the wrapped text exactly as it is, so the names would stay in Cyrillic.
D=Document translation of a template: it translates document content into another language while keeping layout; it is not a script conversion tool and adds file handling for short strings.
T: Use Translator Transliterate (language, fromScript, toScript) to change the writing system without translating; use Translate to change the language.

- `add_target_language("fr")`: each call adds one **target** language; results contain a `translations` dictionary keyed by language.
- `voice_name`: the voice for **event-based synthesis** of translated audio.
`TranslationRecognizer` uses this config and raises `recognizing`, `recognized` and `synthesizing` events.
## The single-language limit
Learn states: "The event-based synthesis works only with a single translation. Do not add multiple target translation languages," and the voice should match the target language (for example `de` with `de-DE-Hedda`). For several targets, use **manual synthesis**: iterate over `result.translations` and synthesize each one with a `SpeechSynthesizer` whose `speech_synthesis_voice_name` fits that language.
W: Manual synthesis per language: event-based synthesis supports a single target, so each translation must be synthesized separately with a matching voice.
X: B=One multilingual voice_name: event-based synthesis still produces one translation's audio; a voice setting does not add synthesis for other targets.
C=Change speech_recognition_language: it describes the input speech; changing it would make recognition of the speaker fail.
D=Translator text API with audio: the text API translates text and returns text; it does not take or produce audio.
T: In Speech SDK translation, event-based synthesis works for one target language only; synthesize multiple targets manually with SpeechSynthesizer.

G: ## Speech translation options
- **Real-time speech translation** (Speech SDK `TranslationRecognizer`): streams audio in a source language and returns translated text, **synthesized speech** or both, with interim results. It is for live audio. (Live Interpreter extends it for conversations with automatic language switching.)
- **Azure LLM Speech** (enhanced mode of the **fast transcription** API): a multimodal LLM-powered model for **pre-recorded audio**. Its tasks are `transcribe` and `translate`; for translate, `targetLanguage` is required (a language code such as `en`).

## What Translator and Language do not do
Translator text and document APIs translate **text and files**, not audio. Language detection identifies the language of text. Custom Translator trains NMT on parallel **text** documents.

X: C=Document translation for live audio: it translates document files and does not accept audio streams or return speech.
D=Custom Translator on audio: it trains on parallel text documents and cannot read audio files.
E=Language detection to speech: it returns which language a text is in; it neither translates nor synthesizes speech.
T: Use Speech SDK speech translation for live audio and Azure LLM Speech translate (fast transcription enhanced mode) for recorded files.

G: ## Input customization versus output customization
Voice Live separates the two sides of a conversation:
- **Speech input** (recognition): `phrase_list` and **custom speech** models.
- **Speech output** (synthesis): **custom lexicon**, **custom voice** (professional voice or personal voice, both limited access) and custom avatar.
## Custom lexicon
A custom lexicon (same format used with SSML) defines pronunciations for words, and Voice Live accepts it through `custom_lexicon_url` in the voice settings. It works with standard Azure voices and custom voices.
```
"voice": {"name": "en-US-Ava:DragonHDLatestNeural", "type": "azure-standard", "custom_lexicon_url": "<lexicon url>"}
```
Here recognition is already correct, so the fix belongs on the output side.
W: Custom lexicon: it changes how the synthesized voice pronounces specific words and is set through custom_lexicon_url in the Voice Live voice configuration.
X: B=Phrase list: it helps the recognizer catch words in user speech; it has no effect on how the agent's voice pronounces them.
C=Custom speech: it trains recognition of incoming audio; the synthesized voice does not learn from it.
D=Semantic VAD: turn detection decides when the user has finished speaking; it does not change pronunciation.
T: Fix recognition with phrase lists or custom speech, and fix spoken pronunciation with a custom lexicon on the output voice.
