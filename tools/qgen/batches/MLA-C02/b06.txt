@ MLA-C02 D1 T1.2 expert tradeoff
S: A legal-research company is building its own RAG index of 30 million chunks with Amazon Titan Text Embeddings V2, stored as 32-bit floats in an Amazon OpenSearch Service domain. The raw vector data must fit in the 40 GB of memory budgeted for vectors (ignore index overhead). On 2,000 labeled queries, recall@5 is 0.94 at 1,024 dimensions, 0.93 at 512 and 0.90 at 256; the product requires at least 0.88. Half of the corpus has already been embedded at the default 1,024 dimensions into an index whose knn_vector field is 1,024. The team wants the cheapest design that meets both limits. What should the ML engineer do?
A: Request 256-dimension embeddings, create a new index with a 256-dimension knn_vector field, and embed the whole corpus again, including the half already done
B: Request 512-dimension embeddings, which keep recall at 0.93, create a new 512-dimension index, and embed only the half of the corpus that is not done yet
C: Keep the existing 1,024-dimension vectors but store only their first 256 values in a new index, so the half already embedded is reused without more model calls
D: Request 256-dimension embeddings for the remaining half only, and keep the 1,024-dimension index so that the knn_vector field pads the shorter vectors with zeros
K: A
G: ## Titan Text Embeddings V2 output sizes
Titan Text Embeddings V2 returns vectors of **1,024 (default), 512 or 256** dimensions. Smaller vectors cost less to store and search, with some loss of retrieval quality that you measure on your own queries.
## Working the numbers
Raw size = chunks x dimensions x 4 bytes (float32):
- 1,024 dims: 30,000,000 x 1,024 x 4 = about 122.9 GB
- 512 dims: about 61.4 GB, still above the 40 GB budget
- 256 dims: about 30.7 GB, which fits; recall 0.90 is above the 0.88 floor
## Why everything must be embedded again
Vectors are only comparable when they come from the same model with the same output size, and a vector index field has one fixed dimension. The 1,024-dimension half cannot be mixed with 256-dimension vectors or cut down, so the whole corpus is embedded again into a new 256-dimension index.
W: 256 dimensions, new index, full re-embed: it is the only size that fits 40 GB while meeting the recall floor, and one consistent vector space requires embedding the first half again.
X: B=512 dimensions: about 61.4 GB of raw vectors exceeds the 40 GB budget, and mixing a 1,024-dimension half with a 512-dimension half is not possible in one field anyway.
C=First 256 values of 1,024-dimension vectors: the model's 256-dimension output is requested from the model; slicing stored vectors is not a documented equivalent, and its recall was never measured.
D=Pad 256-dimension vectors into a 1,024 field: a knn_vector field requires vectors of its declared dimension, and padded vectors would not be comparable with real 1,024-dimension ones.
T: Size vector storage as chunks x dimensions x 4 bytes, choose the smallest Titan V2 output that meets the measured recall, and re-embed everything when the dimension changes.

@ MLA-C02 D1 T1.1 expert troubleshooting
S: A manufacturer syncs an S3 data source of 18,000 files into an Amazon Bedrock knowledge base that uses multimodal parsing, so that answers can cite both text and wiring diagrams. The ingestion job finishes with 212 failed documents. The failure list shows 140 scanned service-manual PDFs of 60 to 90 MB each and 72 PNG wiring diagrams of 5 to 8 MB each; all DOCX and smaller PDF files succeeded. The team must keep the parsing strategy, keep every manual page searchable, and keep the diagrams retrievable as images. Which TWO actions will let all 212 documents ingest? (Select TWO)
A: Split each failing manual into several PDF files under 50 MB, for example one file per chapter, and upload the parts to the data source
B: Recompress or downscale each wiring diagram to a JPEG or PNG file of no more than 3.75 MB, and replace the original images in the bucket
C: Increase the maximum chunk size of the data source, because the chunk size quota is what limits how large a source file can be
D: Convert each manual to plain .txt files with an OCR tool, because text files have no size limit in a knowledge base data source
E: Zip the diagrams of each product line into one archive, so that the knowledge base unpacks every archive and indexes each image inside it separately
K: A,B
G: ## Source file limits for knowledge base data
For Amazon S3 (and custom) data sources, each source file must be a supported format and:
- **each file must not exceed 50 MB**;
- multimodal **JPEG and PNG files** are limited to **3.75 MB**.
Supported document formats include .txt, .md, .html, .doc/.docx, .csv, .xls/.xlsx and .pdf. Archives such as .zip are not on the list.
## Chunk size is something else
The maximum chunk size quota applies to the text chunks produced **after** a document is split by the chunking strategy. It does not limit the size of the source file; large documents are simply split into more chunks.
W: A=Split manuals under 50 MB: each part is within the per-file limit, and every page is still ingested and parsed.
B=Images at 3.75 MB or less: the diagrams stay images that multimodal parsing can index, now within the image size limit.
X: C=Larger chunk size: the chunk size quota limits chunks after splitting, not the size of the source file.
D=OCR to .txt: plain text loses the scanned layout and figures, and every file still has to respect the 50 MB limit.
E=Zip archives: .zip is not a supported source format, so the archives would fail instead of being unpacked.
T: Bedrock knowledge base source files must be 50 MB or less, and JPEG/PNG images 3.75 MB or less; chunk size settings do not change these limits.

@ MLA-C02 D1 T1.3 expert use-case
S: A lender that opened its first AWS account this year must report two pre-training bias metrics for every credit training set, using the standard definitions Clarify documents, with applicants under 60 as facet a and applicants 60 or older as facet d. Limits: absolute class imbalance (CI) at most 0.5 and absolute difference in proportions of labels (DPL) at most 0.1. The current set has 100,000 rows: 78,000 in facet a with 46,800 approved, and 22,000 in facet d with 9,900 approved. The SageMaker pipeline must stop before training when a limit is broken. Which statement is correct?
A: CI is 0.56 and DPL is 0.15, so both limits are broken; compute them in a Processing step with the lender's own pandas code and stop before training
B: CI is 0.56 and DPL is 0.15, so both limits are broken; compute them with a ClarifyCheckStep using a data bias config and stop before training
C: CI is 0.28 and DPL is 0.15, so only the DPL limit is broken; compute them in a Processing step with the lender's own pandas code and stop before training
D: CI is 0.56 and DPL is -0.15, so only CI is broken because a negative DPL favors facet d; compute both with the lender's own pandas code
K: A
G: ## Two pre-training bias metrics
- **Class imbalance**: `CI = (na - nd) / (na + nd)`, range -1 to 1. Positive means facet a has more samples.
- **Difference in proportions of labels**: `DPL = qa - qd`, where `qa = na(1)/na` and `qd = nd(1)/nd` are the shares of positive labels. Positive means facet a gets more positive outcomes.
## Working the numbers
- CI = (78,000 - 22,000) / 100,000 = **0.56** (above 0.5)
- qa = 46,800 / 78,000 = 0.60; qd = 9,900 / 22,000 = 0.45; DPL = 0.60 - 0.45 = **0.15** (above 0.1)
## Who computes them
SageMaker Clarify is **no longer open to new customers**. AWS notes that these metrics are standard arithmetic on label counts that you can reproduce with pandas and scikit-learn in your own pipeline code, for example in a Processing step followed by a Condition step and a Fail step.
W: Both metrics broken, own code: the arithmetic gives CI 0.56 and DPL 0.15, and a new customer computes them with its own code because Clarify is closed to new customers.
X: B=ClarifyCheckStep: the numbers are right, but a company that is new this year cannot start using Clarify.
C=CI of 0.28: 0.28 is (78,000 - 22,000) / 200,000 or a similar slip; the normalized formula divides by na + nd = 100,000.
D=DPL of -0.15: DPL is qa - qd = 0.60 - 0.45, which is positive because facet a has the higher approval rate.
T: CI = (na - nd)/(na + nd) and DPL = qa - qd; new customers compute them in their own pipeline code because Clarify is closed to new customers.

@ MLA-C02 D1 T1.1 expert troubleshooting
S: Before a cutover in 6 hours, a team must re-embed 1.8 million chunks with Amazon Titan Text Embeddings V2 on demand. An AWS Glue job with 40 parallel workers sends one chunk of about 300 tokens per InvokeModel call. The chunk boundaries are fixed by an evaluated chunking strategy. The job gets many ThrottlingException errors and projects about 15 hours. CloudWatch shows InputTokenCount peaking near 600,000 per minute; an approved increase of the model's tokens-per-minute quota to 5,000,000 changed nothing. Service Quotas shows 2,000 requests per minute for this model. What should the ML engineer do?
A: Request a further tokens-per-minute increase to 10,000,000, because each embedding call reserves its input tokens plus a large default max_tokens from the quota
B: Request a requests-per-minute increase to at least 5,000 for the model, because 1.8 million calls in 6 hours need 5,000 calls every minute
C: Raise the Glue job from 40 to 120 parallel workers, so that more InvokeModel calls run at the same time inside the current per-minute request quota
D: Concatenate about 27 chunks into each request up to the 8,192-token input limit, so that one call returns the embeddings for many chunks at once
K: B
G: ## How embedding models are throttled
AWS documents that **embedding models on Amazon Bedrock are throttled by requests per minute (RPM), not tokens per minute (TPM)**, and that capacity planning and quota increases for them should use the RPM quota.
Titan Text Embeddings V2 takes one input text (up to 8,192 tokens or 50,000 characters) and returns **one** vector for it.
## Working the numbers
- At 2,000 RPM: 1,800,000 / 2,000 = 900 minutes = **15 hours**, exactly the projection.
- To finish in 6 hours (360 minutes): 1,800,000 / 360 = **5,000 requests per minute**.
- Token volume (about 600,000 per minute) was never the limit, which is why the TPM increase changed nothing.
W: RPM increase to 5,000 or more: requests per minute is the limit for embedding models, and 5,000 per minute is the rate the deadline requires.
X: A=More TPM: TPM is not what throttles embedding models, as the unchanged result after the first increase already shows; embeddings also have no max_tokens to reserve.
C=More workers: the account still gets 2,000 requests per minute, so more workers only produce more throttling errors.
D=Concatenate chunks: Titan returns one vector per input text, so 27 chunks would become one vector and break chunk-level retrieval.
T: Bedrock embedding models are throttled by requests per minute; size the RPM quota as items to embed divided by minutes available.

@ MLA-C02 D1 T1.1 expert use-case
S: A fraud team moves an online feature group to Provisioned throughput mode because its traffic is predictable. Each record holds 400 features and is about 6 KB. At peak the model calls GetRecord 1,500 times per second, asking for only 25 features (about 0.4 KB) each time. Streaming jobs call PutRecord with full records at up to 400 per second. Next month the team will backfill two years of historical records into the same feature group. The team wants the smallest capacity that avoids throttling, set in advance. Which capacity plan should the ML engineer set?
A: About 1,500 RCU and 4,800 WCU, because a 25-feature read of about 0.4 KB consumes one read unit, and writes double the peak for the backfill
B: About 3,000 RCU and 4,800 WCU, because each read is charged for the full 6 KB record and backfill writes need twice the recent peak
C: About 3,000 RCU and 2,400 WCU with auto scaling on write capacity, so that WCU rises by itself when the backfill of historical records starts
D: About 3,000 RCU and 2,400 WCU, because writing historical records consumes the same write capacity per KB as current records
K: B
G: ## Provisioned throughput for Feature Store
In `Provisioned` mode you set read and write capacity units (RCU, WCU) and pay for them even if unused; exceeding them throttles requests.
- **Reads**: a `GetRecord` of a record up to 4 KB consumes at least 1 RCU; larger records take more. Retrieving **only a subset of features still consumes RCU for the entire record.**
- **Writes**: a 1 KB `PutRecord` consumes at least 1 WCU, rounded up to the nearest KB.
- **Backfills**: writing historical records consumes extra write capacity, so AWS recommends provisioning **2x the recent peak** for backfills or bulk ingestion.
- **No auto scaling** in Provisioned mode; you raise capacity with `UpdateFeatureGroup` (decreases are limited per day).
## Working the numbers
- Reads: a 6 KB record needs two 4 KB read units -> 1,500 x 2 = **3,000 RCU**.
- Writes: 6 KB -> 6 WCU x 400 = 2,400 WCU; doubled for the backfill = **4,800 WCU**.
W: 3,000 RCU and 4,800 WCU: reads are charged for the whole record, and the backfill needs twice the peak write capacity, set manually ahead of time.
X: A=1,500 RCU: asking for 25 features does not reduce the read units; the whole 6 KB record is charged.
C=Auto scaling on WCU: Provisioned mode has no auto scaling, so the backfill would be throttled at 2,400 WCU.
D=No backfill headroom: historical writes consume additional write capacity, which is why AWS recommends 2x the peak.
T: Feature Store Provisioned mode charges reads for the full record, needs 2x write capacity for backfills and has no auto scaling.

@ MLA-C02 D2 T2.2 expert troubleshooting
S: A team trains a custom PyTorch model with managed Spot training, writing checkpoints every 30 minutes to /opt/ml/checkpoints with a CheckpointConfig. Last week's job reported TrainingTimeInSeconds 36,000 and BillableTimeInSeconds 10,800, but its wall-clock time was 15 hours because of two interruptions and waits for capacity. New rules: each run must cost at most 40 percent of on-demand and must stop within 18 hours of starting. Separately, the team wants to move a 2.5-hour job that uses a built-in algorithm without checkpoint support to managed Spot as well. Which THREE conclusions are correct? (Select THREE)
A: Last week's job saved 70 percent against on-demand, (1 - 10,800 / 36,000) x 100, so it already meets the 40 percent cost rule
B: Set MaxWaitTimeInSeconds to 64,800 and MaxRuntimeInSeconds to a clearly smaller value, because the wait limit covers Spot waiting plus running time
C: The 2.5-hour built-in job cannot finish as managed Spot, because built-in algorithms without checkpointing are limited to a 3,600-second wait
D: If Spot capacity is still missing close to the 18-hour limit, SageMaker moves the job to on-demand instances, so the deadline is always met
E: The 15 hours of wall-clock time are what was billed, so the real saving was only about a third compared with a 10-hour on-demand run
F: Set MaxWaitTimeInSeconds below MaxRuntimeInSeconds, so that the job stops waiting for Spot capacity early and runs the rest on on-demand capacity
K: A,B,C
G: ## Managed Spot training rules
- Savings formula: `(1 - BillableTimeInSeconds / TrainingTimeInSeconds) x 100`.
- `TrainingTimeInSeconds` is productive training time; **only `BillableTimeInSeconds` is billed**. Wall-clock time includes interruptions and waits and is not what you pay for.
- `MaxWaitTimeInSeconds` is the time spent waiting for Spot capacity **plus** running time, and must not be smaller than `MaxRuntimeInSeconds` (set it clearly larger to stay valid).
- Managed Spot **does not fall back to on-demand**: if capacity is missing, the job waits until `MaxWaitTimeInSeconds` and then stops.
- Built-in and Marketplace algorithms that do not checkpoint are limited to a `MaxWaitTimeInSeconds` of **3,600 seconds**.
## Working the numbers
- Saving: 1 - 10,800 / 36,000 = 0.70, so the job cost 30 percent of on-demand, under the 40 percent rule.
- 18 hours = 64,800 seconds for MaxWaitTimeInSeconds.
- A 2.5-hour (9,000-second) job cannot finish inside a 3,600-second wait limit.
W: A=70 percent saving: billable time is 30 percent of training time, inside the 40 percent rule.
B=MaxWait 64,800: the wait limit bounds total elapsed time including Spot waits, which enforces the 18-hour rule; a smaller MaxRuntimeInSeconds keeps the pair valid.
C=3,600-second limit for non-checkpointing built-ins: a 9,000-second job cannot complete under it, so it should run on-demand.
X: D=Fallback to on-demand: managed Spot never switches to on-demand; it stops when the wait limit is reached.
E=Wall-clock billing: only BillableTimeInSeconds is billed, not the hours spent waiting or recovering from interruptions.
F=MaxWait below MaxRuntime: MaxWaitTimeInSeconds may not be smaller than MaxRuntimeInSeconds, and there is no switch to on-demand anyway.
T: For managed Spot, bill = BillableTimeInSeconds, MaxWait (wait + run) above MaxRuntime, no on-demand fallback, and non-checkpointing built-ins are capped at a 3,600-second wait.

@ MLA-C02 D2 T2.2 expert troubleshooting
S: A team runs Amazon Bedrock reinforcement fine-tuning on a supported model to extract 14 fields from invoices into JSON. The reward Lambda function returns 1 only when all 14 fields match the reference values and 0 otherwise; for each response it also calls an external tax-ID validation API, and its logs show about 25 seconds per invocation. After two epochs, the average training reward has stayed at 0.00 from the first step, and the baseline model scored 0 on a 200-example pre-check as well. Which TWO changes are MOST likely to make the next run effective? (Select TWO)
A: Run supervised fine-tuning on labeled invoices first, so the model produces some correct outputs before reinforcement fine-tuning starts
B: Make the reward function return within seconds, for example by validating tax IDs from a local lookup table instead of calling the external API
C: Increase the number of epochs to six, because rewards in reinforcement fine-tuning usually start rising only after the third epoch of the training run
D: Replace the Lambda grader with a model-as-a-judge grader, because rule-based Lambda graders cannot compare JSON outputs with reference values
E: Remove the validation dataset, so that every example goes into training and the model sees more invoices that can earn a reward of 1
K: A,B
G: ## How Bedrock RFT learns
For each prompt the model generates several responses, a **reward function** scores them, and Bedrock trains on the scored pairs with GRPO. Learning needs differences in reward between responses.
## AWS best practices that apply here
- **Pre fine-tuning evaluation**: if rewards are consistently 0 percent, use **supervised fine-tuning first** to establish basic capabilities (and if rewards are above 95 percent, RFT may be unnecessary).
- **Reward functions** should execute **within seconds, not minutes**, minimize external API calls and take advantage of Lambda's parallel scaling.
- Watch average rewards; rewards plateauing near zero means the signal is not working.
## Reading the evidence
The baseline scores 0 and training reward never moves from 0.00: every sampled response gets the same reward, so there is nothing to learn from. The 25-second external call makes each step slow and fragile.
W: A=SFT first: the model must produce some correct invoices before reward differences can guide it, exactly as the guidance for 0 percent rewards says.
B=Fast reward function: removing the slow external call follows the seconds-not-minutes guidance and keeps training steps quick.
X: C=More epochs: with every reward at 0 there is no signal to accumulate, so more epochs only spend more money.
D=Judge instead of Lambda: rule-based Lambda graders are the documented choice for objective checks such as exact field matches.
E=Remove validation data: it removes the way to detect overfitting and does nothing about a model that never earns a reward.
T: In Bedrock RFT, constant zero rewards call for supervised fine-tuning first, and reward functions must run in seconds without slow external calls.

@ MLA-C02 D2 T2.3 expert tradeoff
S: A card issuer picks a decision threshold for a fraud model using 100,000 validation transactions that contain 500 frauds. A missed fraud costs $400 and a false alert costs $15 of review time. Results: at 0.3, 450 frauds caught with 6,000 false alerts; at 0.5, 420 caught with 1,800 false alerts; at 0.7, 370 caught with 600 false alerts; at 0.9, 300 caught with 150 false alerts. The review team can handle at most 1,500 alerts per 100,000 transactions, true and false together. Which threshold should the ML engineer choose?
A: 0.5, because its expected cost of $59,000 per 100,000 transactions is the lowest of the four thresholds that were evaluated
B: 0.7, because its expected cost of $61,000 is the lowest among thresholds whose 970 total alerts stay within the review capacity
C: 0.9, because it has the highest F1 score of the four thresholds, about 0.63, and therefore balances precision and recall best
D: 0.3, because it catches 90 percent of fraud, and recall is the metric that matters most when a missed fraud costs over 26 times a review
K: B
G: ## Choosing a threshold by cost
Expected cost = missed frauds x $400 + false alerts x $15. Alerts = caught frauds + false alerts.
- 0.3: 50 missed, 6,000 false -> $20,000 + $90,000 = **$110,000**; 6,450 alerts
- 0.5: 80 missed, 1,800 false -> $32,000 + $27,000 = **$59,000**; 2,220 alerts
- 0.7: 130 missed, 600 false -> $52,000 + $9,000 = **$61,000**; 970 alerts
- 0.9: 200 missed, 150 false -> $80,000 + $2,250 = **$82,250**; 450 alerts
## The capacity constraint
Only thresholds with at most 1,500 alerts are feasible: 0.7 and 0.9. Of those, 0.7 costs less.
## Why F1 is not the deciding metric
F1 = 2PR/(P+R) weighs precision and recall equally. At 0.9, precision 300/450 = 0.67 and recall 0.60 give F1 of about 0.63, the highest, but it ignores the 27-to-1 cost ratio and costs $21,250 more than 0.7.
W: 0.7: at $61,000 per 100,000 transactions with 970 alerts, it is the cheapest threshold that the review team can actually work through, so every alert it raises gets reviewed.
X: A=0.5: the cheapest on paper, but 2,220 alerts exceed the 1,500-alert capacity, so the reviews would not happen.
C=0.9 for F1: F1 treats precision and recall as equally valuable, which this cost structure does not.
D=0.3 for recall: recall alone ignores the cost of 6,000 false alerts and breaks the capacity limit four times over.
T: Pick thresholds by expected business cost under operational limits, not by a single metric such as F1 or recall.
