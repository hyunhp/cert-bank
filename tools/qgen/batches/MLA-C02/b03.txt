@ MLA-C02 D3 T3.1 applied use-case
S: A retailer must generate marketing summaries for about two million product records every night with a foundation model on Amazon Bedrock. Results are needed by the next morning, nobody waits on an individual response, and the team wants the lowest cost per token. Which deployment option fits best?
A: Submit a Bedrock batch inference job that reads the records as JSONL files from Amazon S3 and writes the model outputs to an S3 output prefix.
B: Buy Bedrock Provisioned Throughput with a one-month commitment and send the records through InvokeModel calls from a fleet of Lambda functions.
C: Call the model on demand through a cross-Region inference profile so that the nightly burst of requests is spread over Regions without throttling.
D: Deploy the model to a SageMaker AI real-time endpoint with auto scaling and loop through all the records from one EC2 instance during the night.
K: A
G: ## Three ways to consume a model on Amazon Bedrock
- **On-demand**: you call `InvokeModel` or `Converse` and pay per input and output token. Capacity is shared and limited by per-account quotas (requests and tokens per minute).
- **Provisioned Throughput**: you buy model units for a model for a term and pay per hour whether or not you send traffic. You get dedicated throughput for steady, predictable load.
- **Batch inference**: you put many prompts in JSONL files in Amazon S3 and call `CreateModelInvocationJob`. Bedrock processes them asynchronously and writes the results to an S3 output location. For supported models, batch is priced lower than on-demand.
## Matching the option to the workload
The deciding question is "does someone wait for each answer?". An interactive chatbot needs on-demand or provisioned capacity. A nightly job over millions of records only needs all results by a deadline, so the cheaper asynchronous batch path fits.
Example: the nightly export writes `records-0001.jsonl` ... `records-0200.jsonl` (each line has a `recordId` and a `modelInput`), the job is submitted at 22:00, and the morning process reads the `.jsonl.out` files.
W: Bedrock batch inference: it is built for large offline workloads. Records go in as JSONL in S3, results come back to S3, nobody needs a real-time response, and batch is the lower-priced way to run the same model, with no client fleet to manage or throttle.
X: B=Provisioned Throughput with Lambda: you pay for model units every hour of the commitment even though the work runs only at night, and you still have to build and throttle a Lambda fan-out yourself. It buys dedicated capacity, not the lowest cost per token.
C=Cross-Region inference profile: a profile helps absorb bursts of real-time traffic by routing across Regions, but every call is still billed at on-demand prices and the client must still drive two million synchronous calls.
D=SageMaker AI real-time endpoint: you would pay for GPU instances while they run and write the driver loop and retries yourself. A real-time endpoint is for low-latency requests, not for a cheap overnight batch of an already available Bedrock model.
T: Large, non-interactive Bedrock workloads with a deadline instead of a latency target belong in batch inference jobs (JSONL in S3, results to S3, lower price).
V: Amazon Bedrock, Amazon S3

@ MLA-C02 D3 T3.1 applied troubleshooting
S: A US healthcare analytics company calls an Anthropic Claude model on Amazon Bedrock in us-east-1 with on-demand throughput. During afternoon peaks some requests are throttled. Compliance requires that inference stays inside the United States, and the team does not want to commit to reserved capacity. What should the ML engineer change?
A: Set the modelId to the US geographic cross-Region inference profile, so Bedrock can route requests to other US Regions in the profile during peaks.
B: Set the modelId to the global cross-Region inference profile, so Bedrock can route requests to any commercial Region that has spare capacity.
C: Buy Provisioned Throughput with a six-month commitment in us-east-1 sized for the afternoon peak and send all traffic to the provisioned model.
D: Deploy a second copy of the application in us-west-2 and add client-side logic that switches Regions after every throttling error it receives.
K: A
G: ## What a cross-Region inference profile does
An inference profile is an ID you pass as `modelId` instead of a plain model ID. A **system-defined cross-Region inference profile** lists a model and a set of Regions. You still call Bedrock in your source Region, but Bedrock may serve the request in another Region of the profile when your Region is busy. This raises the throughput you can reach without any reserved capacity.
## Geographic versus global profiles
- **Geographic profiles** (for example a `us.` prefix for United States Regions, `eu.` for Europe) keep processing inside that geography. They fit data-residency rules.
- **Global profiles** (a `global.` prefix) can route to supported commercial Regions worldwide for the most capacity, so they do not fit a "stay in the US" rule.
Example: changing `anthropic.claude-...` to `us.anthropic.claude-...` in the request is the whole code change; the IAM policy must also allow the profile and the model in the destination Regions.
W: US geographic inference profile: Bedrock spreads peak traffic across the US Regions listed in the profile, which reduces throttling, keeps inference in the United States, and needs no commitment or extra infrastructure.
X: B=Global inference profile: it gives the most capacity, but requests may be processed outside the United States, which breaks the stated compliance requirement.
C=Six-month Provisioned Throughput: it would remove the throttling but is exactly the long-term reserved capacity the team does not want, and it is paid for all day to fix an afternoon peak.
D=Second Region with client failover: it adds a whole deployment to operate and reacts only after a request has already been throttled. The managed profile already routes across US Regions for the team.
T: On-demand throttling at peaks with a data-residency rule → use the matching geographic cross-Region inference profile, not the global one and not reserved capacity.
V: Amazon Bedrock

@ MLA-C02 D3 T3.1 advanced comparison
S: An ML team hosts four fine-tuned 8B-parameter open-weight LLMs, each on its own SageMaker AI real-time endpoint with a 4-GPU instance. Each model needs only one GPU and gets little traffic. Two models use a different serving container than the others. The team wants one endpoint where each model keeps its own resources and scales on its own. What should they use?
A: Deploy each model as an inference component on one endpoint, giving each component its own accelerator and memory allocation and its own copy-count scaling policy.
B: Deploy the models on one multi-model endpoint, which loads each model from Amazon S3 on demand and scales the copies of each model with its own target-tracking policy.
C: Deploy the models as a multi-container endpoint with direct invocation, where each container receives its own GPU and an independent auto scaling policy per container.
D: Move the models to SageMaker Serverless Inference endpoints, which share one pool of GPU capacity and charge only for the time each model is processing a request.
K: A
G: ## Inference components
An **inference component** is a model deployment that lives on a SageMaker AI endpoint but is managed separately from it. For each component you set:
- the model and its container image,
- the compute it reserves on an instance: number of accelerators (GPUs), CPU cores and memory,
- the number of copies, with its own auto scaling policy.
SageMaker AI places the copies on the endpoint's instances, so several models share the same GPUs and instances. Endpoint-level instance scaling can add or remove instances as components need more or less room.
## Why this fits underused GPU endpoints
Four endpoints with 4-GPU instances and one busy GPU each means 12 idle GPUs. With components, one 4-GPU instance can host the four models (one GPU each), different containers are allowed, and a busier model can scale its own copies without scaling the others.
W: Inference components on one endpoint: each model gets its own accelerator and memory reservation, can use its own container, and scales its copy count independently, which is exactly the packing the team needs.
X: B=Multi-model endpoint: all models share one serving container and are loaded and evicted dynamically. There is no per-model scaling policy, and the two models with a different container cannot be served by the same endpoint.
C=Multi-container endpoint: containers on one endpoint run on every instance and scale together with the endpoint. There is no per-container GPU reservation or per-container auto scaling policy.
D=Serverless Inference: serverless endpoints do not offer GPUs at all, so they cannot run these LLMs. There is no shared GPU pool.
T: Several models, different containers, one GPU endpoint, independent scaling → SageMaker AI inference components.
V: Amazon SageMaker AI

@ MLA-C02 D3 T3.1 applied troubleshooting
S: A legal-tech company serves an open-weight LLM on a SageMaker AI asynchronous inference endpoint. Requests carry document bundles of up to 200 MB and take 5 to 15 minutes each. To save cost, the auto scaling minimum is 0 and a target-tracking policy uses the backlog size per instance. After a quiet night at zero instances, new requests stay queued and no instance starts. What should the ML engineer change?
A: Add a step scaling policy driven by a CloudWatch alarm on the endpoint's backlog-without-capacity metric, so that queued requests start the first instance.
B: Set the minimum instance count back to 1, so that one GPU instance stays running through the night and picks up the first requests in the morning.
C: Lower the target value of the target-tracking policy to one queued request per instance, so that a single waiting request triggers a scale-out.
D: Increase the invocation timeout of the asynchronous endpoint to its maximum, so that the queued requests are kept long enough for an instance to start.
K: A
G: ## Asynchronous inference and scaling to zero
Asynchronous inference puts each request in an internal queue, reads the input from Amazon S3 (payloads up to 1 GB), allows long processing, writes the output to S3 and can notify through Amazon SNS. Because work waits in the queue, the endpoint may scale down to **zero instances** when idle, which is the main cost advantage over a real-time endpoint for bursty, long-running LLM jobs.
## Why target tracking alone does not wake the endpoint
The usual scaling metric is `ApproximateBacklogSizePerInstance`: queued requests divided by the number of instances. It works well for adding and removing instances while at least one is running. At zero instances there is nothing to divide by, so a target-tracking policy on this metric does not start the first instance.
## The scale-from-zero pattern
SageMaker AI publishes `HasBacklogWithoutCapacity` for asynchronous endpoints: it is 1 when requests are queued and no instance is running. The documented pattern is:
- a CloudWatch alarm on `HasBacklogWithoutCapacity` greater than or equal to 1,
- a **step scaling** policy, triggered by that alarm, that adds the first instance,
- the existing target-tracking policy on backlog per instance, which then scales further out and back in to 0.
Example: at 08:00 the first request lands in the queue, the alarm fires within a few minutes, one GPU instance starts, and the backlog policy adds more instances if the morning burst grows.
W: Step scaling on the backlog-without-capacity alarm: this metric reports queued work while no instance runs, so the alarm and step policy start the first instance; target tracking then handles further scaling, and the endpoint can still return to zero when idle.
X: B=Minimum of 1: it removes the symptom by keeping a GPU instance running all night, which is the idle cost the team set the minimum to 0 to avoid.
C=Lower target value: any per-instance metric is undefined at zero instances, so changing the target value does not let target tracking start the first instance.
D=Longer invocation timeout: the timeout limits how long a request may be processed once it runs. It does not add capacity, so requests would still wait with no instance to run them.
T: An asynchronous endpoint that scales to zero also needs a step scaling policy on HasBacklogWithoutCapacity to start the first instance; backlog-per-instance target tracking cannot scale out from zero.
V: Amazon SageMaker AI, Amazon CloudWatch, Application Auto Scaling

@ MLA-C02 D3 T3.1 advanced use-case
S: An ML engineer must host a 70B-parameter open-weight LLM on SageMaker AI. In 16-bit precision the weights need about 140 GB, more than the memory of any single GPU on the chosen ml.p4d.24xlarge instance (eight GPUs with 40 GB each). What is the most direct way to serve the model?
A: Use a SageMaker AI large model inference (LMI) container and set the tensor parallel degree to 8, so the model's layers are split across all eight GPUs.
B: Use the generic PyTorch inference container with an initial instance count of 4, so the endpoint spreads the model's weights across four instances.
C: Use a SageMaker Serverless Inference endpoint with its largest memory setting, so the weights are paged in from Amazon S3 as each layer is needed.
D: Use the SageMaker distributed data parallel library at inference time, so each request batch is split across the eight GPUs of the instance.
K: A
G: ## When a model does not fit on one GPU
A model's weights must sit in GPU memory to run fast. In 16-bit precision each parameter takes 2 bytes, so 70 billion parameters need about `70e9 x 2 = 140 GB`, plus room for the KV cache. One 40 GB GPU cannot hold that, but eight of them (320 GB) can if the model is **sharded**.
## Tensor parallelism and LMI containers
- **Tensor parallelism** splits each layer's weight matrices across several GPUs; the GPUs compute their parts of every token together.
- **SageMaker AI large model inference (LMI) containers** package serving engines such as vLLM and TensorRT-LLM with settings such as `option.tensor_parallel_degree`, continuous batching and quantization. You point the container at the model in S3 or on Hugging Face and set the degree to the number of GPUs.
- **Data parallelism** is different: it puts a full copy of the model on each device and splits the requests or data. It helps throughput only when one copy already fits.
W: LMI container with tensor parallel degree 8: the serving engine shards every layer across the eight GPUs of one instance, so the 140 GB of weights fit in 320 GB of combined GPU memory and the model serves normally.
X: B=Four instances with a generic container: adding instances adds full copies of the model behind the endpoint; the generic container does not shard weights across instances, so each copy still fails to load on a 40 GB GPU.
C=Serverless Inference: serverless endpoints have no GPUs and a small memory ceiling. Paging weights from S3 layer by layer is not something they do, and a 70B model could not be served this way.
D=Data parallel library: data parallelism replicates the whole model on each GPU, so every replica still needs 140 GB. The library is a training feature, not a way to fit a large model for inference.
T: A model larger than one GPU → shard it with tensor parallelism in a SageMaker AI LMI container (tensor parallel degree = GPUs per instance).
V: Amazon SageMaker AI

@ MLA-C02 D3 T3.1 applied comparison
S: A support chatbot has two back ends: a Claude model on Amazon Bedrock and a fine-tuned open model on a SageMaker AI real-time endpoint that uses an LMI container with streaming enabled. Users complain that each reply appears only after the whole answer is generated. Which TWO API calls should the application use so tokens appear as they are produced? (Select TWO)
A: ConverseStream on the Bedrock Runtime API, which returns the model output as a stream of events while the text is still being generated.
B: InvokeEndpointWithResponseStream on the SageMaker AI Runtime API, which returns the container's output in parts as the model generates it.
C: InvokeEndpointAsync on the SageMaker AI Runtime API, which returns the generated tokens through an Amazon SNS topic while the model is running.
D: CreateModelInvocationJob on the Bedrock API, which streams the output of each record to the client as soon as the job has processed that record.
E: StartAsyncInvoke on the Bedrock Runtime API, which keeps the HTTP connection open and pushes partial output to the client until generation ends.
K: A,B
G: ## Why streaming matters for LLMs
An LLM generates text one token at a time. Without streaming, the API returns only when the last token is ready, so a 400-token answer may show nothing for many seconds. With streaming, the first words appear almost at once (low time to first token) even though total generation time is the same.
## Streaming APIs on AWS
- **Amazon Bedrock**: `ConverseStream` (one interface for all supported models) and `InvokeModelWithResponseStream` (model-native request body) return an event stream of content deltas, then metadata such as token usage.
- **SageMaker AI**: `InvokeEndpointWithResponseStream` returns the response in parts, provided the container streams (LMI and other LLM serving containers support this).
- **Not streaming**: asynchronous APIs (`InvokeEndpointAsync`, Bedrock `StartAsyncInvoke`) and batch jobs (`CreateModelInvocationJob`) write results to Amazon S3 later.
W: A=ConverseStream: the Bedrock Runtime streaming call sends content deltas as the Claude model produces them, so the chat window can render text immediately.
B=InvokeEndpointWithResponseStream: the SageMaker AI streaming call relays the LMI container's partial output to the client while the fine-tuned model is still generating.
X: C=InvokeEndpointAsync: asynchronous inference queues the request and writes the complete output to S3; SNS only reports that the result is ready. It makes the wait longer, not shorter.
D=CreateModelInvocationJob: this starts a batch inference job over JSONL files in S3. Results land in S3 when the job processes them; nothing is streamed to a chat client.
E=StartAsyncInvoke: this Bedrock call starts a long-running asynchronous invocation (used for example for video generation) and writes the output to S3. It returns an invocation ARN, not a token stream.
T: Tokens on screen as they are generated → ConverseStream (or InvokeModelWithResponseStream) on Bedrock and InvokeEndpointWithResponseStream on SageMaker AI.
V: Amazon Bedrock, Amazon SageMaker AI

@ MLA-C02 D3 T3.1 applied tradeoff
S: An insurance company runs a claims-triage assistant on Amazon Bedrock around the clock. Traffic is steady and well forecast for the next year, and the business requires a guaranteed level of throughput for this model instead of shared on-demand capacity. Which option meets the requirement?
A: Purchase Provisioned Throughput for the model with a commitment term, sized in model units for the forecast load, and invoke it through the provisioned model ARN.
B: Use on-demand invocation through a cross-Region inference profile, which reserves a fixed share of capacity in each Region of the profile for the account.
C: Run Bedrock batch inference jobs every few minutes, which reserve dedicated capacity for the account while the records of each job are being processed.
D: Raise the on-demand tokens-per-minute quota through Service Quotas, which turns the shared on-demand capacity into capacity dedicated to the account.
K: A
G: ## Shared versus dedicated capacity on Bedrock
- **On-demand** traffic uses capacity shared by many customers. Quotas cap what you may send; they do not promise that capacity is free when you send it, so peaks can still be throttled.
- **Provisioned Throughput** buys **model units** for one model. Each model unit delivers a defined throughput, and you pay per hour for the term you chose. You invoke it with the ARN of the provisioned model instead of the model ID.
## When the commitment pays off
Provisioned Throughput suits steady, forecastable, business-critical traffic: the hourly charge is paid whether or not you use it, so it is wasteful for spiky or uncertain workloads and sensible for a 24/7 assistant with a known load. Longer commitment terms lower the hourly price.
Example: load tests show the assistant needs N model units at the daily peak; the team buys N units for the model and changes the `modelId` in its configuration to the provisioned model ARN.
W: Provisioned Throughput: it is the Bedrock option that dedicates throughput to the account. Sized in model units for the forecast and bought for a term, it gives the guaranteed capacity the business asked for at a predictable hourly cost.
X: B=Cross-Region inference profile: a profile routes on-demand requests across Regions to absorb bursts, but nothing is reserved for the account; it is still shared capacity.
C=Batch inference: batch jobs are asynchronous and process files from S3 with no latency promise, so they cannot serve an interactive assistant and do not reserve capacity.
D=Quota increase: a higher quota lets the account send more, but the requests still run on shared on-demand capacity with no guarantee of throughput.
T: Steady, forecastable traffic that needs guaranteed Bedrock throughput → Provisioned Throughput (model units, commitment term, provisioned model ARN).
V: Amazon Bedrock

@ MLA-C02 D3 T3.2 applied troubleshooting
S: A team deploys a Bedrock knowledge base with AWS CloudFormation: an AWS::Bedrock::KnowledgeBase resource with an Amazon OpenSearch Serverless vector store, and an AWS::Bedrock::DataSource resource for an S3 bucket that already holds the documents. The stack creates successfully, but Retrieve calls return no results. What is the most likely cause and fix?
A: The data source has never been synchronized; add a pipeline step or custom resource that calls StartIngestionJob after the stack deploys.
B: The embedding model needs Provisioned Throughput before it can embed documents; buy model units and reference them in the knowledge base.
C: CloudFormation cannot attach S3 data sources to knowledge bases; recreate the data source by hand in the console after every stack deployment.
D: The vector index stays empty until OpenSearch Serverless copies it to a standby collection; wait for that replication and then query again.
K: A
G: ## What creating a knowledge base does and does not do
A Bedrock knowledge base has three parts:
- the **knowledge base** itself (embedding model, vector store configuration, service role),
- one or more **data sources** (for example an S3 prefix, with chunking settings),
- the **vectors** in the vector store, which exist only after an **ingestion job** has read, chunked and embedded the documents.
Creating the knowledge base and data source, in the console or with CloudFormation, only sets up configuration. Documents are read when a sync runs: `StartIngestionJob` (the console's Sync button). Later changes in S3 also need a new sync.
## Infrastructure as code plus a sync step
A common pattern: CloudFormation or the CDK creates the vector index, knowledge base and data source; then a pipeline step (CodeBuild, a Step Functions task) or a custom resource calls `StartIngestionJob` and waits for status `COMPLETE` before the application is tested.
W: Never-synced data source: the stack created only configuration. Running an ingestion job after deployment chunks and embeds the S3 documents into the vector index, after which Retrieve finds them.
X: B=Provisioned Throughput for embeddings: knowledge bases embed documents with on-demand embedding models, so no model units are required. Capacity is not the problem; no ingestion job has ever run.
C=CloudFormation cannot attach data sources: the AWS::Bedrock::DataSource resource exists precisely to define S3 data sources in a template, and the stack created it successfully.
D=Standby replication: OpenSearch Serverless does not keep an index empty until a copy to another collection completes. The index is empty because nothing was ever written to it.
T: Creating a knowledge base and data source does not load documents: run StartIngestionJob (as a pipeline step or custom resource) after deploying and after every content change.

@ MLA-C02 D3 T3.2 applied use-case
S: A team's production application calls Amazon Bedrock with a guardrail but references the guardrail's working draft. An engineer tuned a content filter in the console for a test, and the change affected production at once. The team wants guardrail changes reviewed in Git and production to change only when a release is deployed. What should they do?
A: Define the guardrail with AWS::Bedrock::Guardrail and publish AWS::Bedrock::GuardrailVersion resources in CloudFormation, and have production reference a specific version.
B: Define the guardrail in CloudFormation and enable stack termination protection, so console edits to the draft are blocked while the application keeps using it.
C: Copy the guardrail to a second AWS Region for production and call it through a cross-Region inference profile, so edits in the first Region never reach it.
D: Attach the guardrail to an application inference profile and tag the profile with a version, so the profile freezes the guardrail settings at the tagged time.
K: A
G: ## Guardrail drafts and versions
A Bedrock guardrail always has a **working draft** (`DRAFT`) that you edit. Creating a **version** takes an immutable snapshot of the draft and gives it a number (`1`, `2`, ...). Calls pass both `guardrailIdentifier` and `guardrailVersion`:
- `guardrailVersion = DRAFT` means "whatever the draft says right now", so any edit takes effect immediately.
- `guardrailVersion = 3` means exactly the configuration snapshotted as version 3, no matter how the draft changes later.
## Guardrails as code
CloudFormation and the CDK can define the guardrail (`AWS::Bedrock::Guardrail`) and publish versions (`AWS::Bedrock::GuardrailVersion`). The template lives in Git, changes go through pull requests, and the release that publishes a new version also updates the version number the application uses (for example a parameter in AWS Systems Manager Parameter Store).
W: Guardrail versions in CloudFormation: the guardrail definition is reviewed in Git, each release publishes an immutable version, and production pinned to that version is unaffected by later draft edits until the next release changes the pin.
X: B=Termination protection: it only prevents the stack from being deleted. It does not block edits to the guardrail draft, and production would still follow every draft change.
C=Second Region via inference profile: inference profiles route model invocations; they do not carry guardrails between Regions or freeze them. It also doubles the configuration to keep in sync by hand.
D=Tagged application inference profile: application inference profiles track usage and cost with tags. Tags do not snapshot or freeze guardrail settings.
T: Production should call a numbered guardrail version, never DRAFT; manage the guardrail and its versions as code so changes reach production only through a release.
V: Amazon Bedrock Guardrails, AWS CloudFormation

@ MLA-C02 D3 T3.2 applied use-case
S: A startup is building its first production AI agent with the open-source LangGraph framework and a model on Amazon Bedrock. It wants managed, serverless hosting in which each user session runs isolated from other sessions, sessions can run long multi-step tasks, and the team keeps its framework code. Which service should host the agent?
A: Amazon Bedrock AgentCore Runtime, which hosts agent code built with any framework and runs each user session in its own isolated environment.
B: Amazon Bedrock Agents (Classic), which imports LangGraph graphs as action groups and runs them on managed capacity separately for each session.
C: Amazon SageMaker AI Serverless Inference, which hosts the agent's container and keeps each session's state on the endpoint between invocations.
D: Amazon Bedrock Flows, which converts LangGraph code into a flow definition and runs each user session through a separate alias of that flow.
K: A
G: ## Amazon Bedrock AgentCore at a glance
AgentCore is a set of managed services for running agents in production, independent of the agent framework (Strands Agents, LangGraph, CrewAI and others) and of the model provider:
- **Runtime**: serverless hosting for agent code or containers. Each session runs in its own isolated environment, and sessions can run long, multi-step tasks.
- **Gateway**: turns APIs and Lambda functions into tools the agent can call over MCP.
- **Memory**: short-term and long-term memory for conversations.
- **Identity**, **Observability**, **Code Interpreter**, **Browser**: authentication, tracing, sandboxed code execution, web browsing.
## Where the older options stand
Amazon Bedrock Agents is now **Bedrock Agents Classic** and closed to new customers, so new agents are built on AgentCore. A model endpoint or a workflow service is not an agent host: it has no session isolation or agent loop of its own.
Example: the team wraps its LangGraph graph with the AgentCore Runtime SDK entry point, builds a container, and deploys it as an agent runtime; each `InvokeAgentRuntime` call carries a session ID.
W: AgentCore Runtime: it hosts existing framework code without rewrites, isolates each session, supports long-running agent tasks and is serverless, matching every requirement of a new agent build.
X: B=Bedrock Agents Classic: it is closed to new customers, so a startup building its first agent cannot adopt it, and it never imported LangGraph graphs; action groups describe APIs or Lambda functions.
C=Serverless Inference: it serves model predictions and keeps no session state between invocations. It offers no per-session isolation or agent loop, and its request duration is limited.
D=Bedrock Flows: Flows is a visual workflow builder with its own node types. It does not convert LangGraph code, and aliases select flow versions, not user sessions.
T: New agents built with any framework that need serverless, session-isolated hosting → Amazon Bedrock AgentCore Runtime.
V: Amazon Bedrock AgentCore

@ MLA-C02 D3 T3.2 applied comparison
S: An agent hosted on Amazon Bedrock AgentCore Runtime must call a company's existing REST APIs and AWS Lambda functions as tools through the Model Context Protocol (MCP) without writing an MCP server for each one. It must also remember each customer's preferences across separate conversations. Which TWO AgentCore capabilities meet these needs? (Select TWO)
A: AgentCore Gateway, which turns existing APIs and Lambda functions into MCP-compatible tools that the agent can discover and call.
B: AgentCore Memory, which stores conversation events as short-term memory and extracts long-term memory such as user preferences.
C: AgentCore Code Interpreter, which wraps existing REST APIs in generated code so that the agent can call them as MCP tools.
D: AgentCore Identity, which stores each customer's preferences together with the user identity so that the agent can read them later.
E: AgentCore Browser, which caches each customer's earlier conversations in a managed browser profile that the agent reopens later.
K: A,B
G: ## Tools and memory are separate building blocks
An agent needs two things beyond a model and a loop: **tools** to act, and **memory** to carry context forward.
## AgentCore Gateway
Gateway exposes existing services as tools over MCP. You register targets such as an OpenAPI specification of a REST API, a Smithy model, or a Lambda function; Gateway presents them as MCP tools with a single endpoint, handles inbound authorization and outbound credentials, and can offer semantic search over many tools. Writing one MCP server per API is not required.
## AgentCore Memory
Memory stores the events of a session (short-term memory) and runs strategies that extract long-term records such as user preferences, facts or summaries. A later session for the same user can retrieve them.
Example: on Monday the customer says "I prefer email, not phone calls"; the preference strategy stores it, and on Friday the agent retrieves it before replying.
## Other AgentCore services
**Identity** manages who can call the agent and the credentials the agent uses for other services. **Code Interpreter** runs code in a sandbox. **Browser** gives the agent a managed web browser.
W: A=AgentCore Gateway: it converts the existing REST APIs and Lambda functions into MCP tools behind one endpoint, so no per-API MCP server is needed.
B=AgentCore Memory: its long-term memory extracts and stores preferences per user, which the agent retrieves in later, separate conversations.
X: C=Code Interpreter: it executes code the agent writes in an isolated sandbox. It does not publish existing APIs as MCP tools.
D=Identity: it handles inbound authentication and outbound credentials (OAuth tokens, API keys). It is not a store for conversation content or preferences.
E=Browser: it provides a cloud browser for the agent to use websites. It does not keep conversation history or user preferences.
T: Existing APIs and Lambda functions as MCP tools → AgentCore Gateway; preferences remembered across sessions → AgentCore Memory.

@ MLA-C02 D3 T3.2 applied troubleshooting
S: An ML application in private subnets calls InvokeModel on Amazon Bedrock. Security requires this traffic to use AWS PrivateLink instead of the NAT gateway. The team created an interface VPC endpoint for the bedrock-runtime service, but VPC Flow Logs show the calls still leave through the NAT gateway. The application uses the default SDK endpoint. What is the most likely fix?
A: Enable private DNS on the interface endpoint, so the default bedrock-runtime hostname resolves to the private IP addresses of the endpoint in the VPC.
B: Add a gateway VPC endpoint for Bedrock to the private route tables, because interface endpoints for Bedrock carry only control-plane API calls.

D: Attach an endpoint policy that allows bedrock:InvokeModel, because an interface endpoint without a policy sends its traffic through the NAT gateway.
K: A
G: ## How interface endpoints receive traffic
An interface VPC endpoint (AWS PrivateLink) places network interfaces with private IP addresses in your subnets. Traffic uses them only if the client connects to those IPs. There are two ways:
- **Private DNS enabled**: the normal public hostname, for example `bedrock-runtime.us-east-1.amazonaws.com`, resolves inside the VPC to the endpoint's private IPs. SDKs need no change. The VPC must have DNS support and DNS hostnames turned on.
- **Private DNS disabled**: the public hostname still resolves to public IPs (so traffic follows the route table to the NAT gateway), and only clients configured with the endpoint-specific DNS name use PrivateLink.
## Bedrock endpoint services
- `bedrock`: control plane (for example creating Provisioned Throughput or customization jobs).
- `bedrock-runtime`: model invocation (`InvokeModel`, `Converse`).
- `bedrock-agent` and `bedrock-agent-runtime`: building and using knowledge bases, agents and flows.
Bedrock has no gateway endpoints; those exist only for Amazon S3 and DynamoDB.
W: Private DNS on the endpoint: with it enabled, the default bedrock-runtime hostname resolves to the endpoint's private IPs, so InvokeModel traffic stays on PrivateLink without any code change.
X: B=Gateway endpoint for Bedrock: gateway endpoints exist only for Amazon S3 and DynamoDB. The bedrock-runtime interface endpoint is exactly the one that carries model invocations.
C=Control-plane endpoint: the bedrock endpoint serves management APIs. InvokeModel is a runtime call and belongs on bedrock-runtime, which the team already created.
D=Endpoint policy: a missing policy means the default policy, which allows full access through the endpoint. Policies control what is allowed, not which route traffic takes; DNS decides that.
T: An interface endpoint that traffic ignores usually means private DNS is off: enable it so the default service hostname resolves to the endpoint's private IPs.
V: AWS PrivateLink, Amazon VPC, Amazon Bedrock

@ MLA-C02 D3 T3.3 applied use-case
S: An ML team fine-tunes a model on Amazon Bedrock each month. A workflow must start the model customization job, wait for it to finish (which can take many hours), then run an evaluation and notify the team. The team does not want to write custom polling code. Which design fits?

B: An AWS Lambda function that starts the customization job and loops on GetModelCustomizationJob with a sleep between checks until the job reports completion.
C: An Amazon EventBridge Scheduler schedule that starts the job, plus a second schedule a fixed 24 hours later that starts the evaluation whatever the job status.

G: ## Service integration patterns in Step Functions
A Task state can call an AWS service in three ways:
- **Request Response** (default): call the API and move on as soon as it returns, for example right after a job is started.
- **Run a Job (`.sync`)**: start a job and wait until it finishes, then continue with its final status. Step Functions does the waiting.
- **Wait for Callback (`.waitForTaskToken`)**: pause until some other component returns a task token.
## Bedrock in Step Functions
Step Functions has optimized integrations for Amazon Bedrock, including `InvokeModel` and `CreateModelCustomizationJob`, which supports `.sync`. A Catch block handles a failed job, and the next states can run the evaluation and publish to Amazon SNS.
W: Step Functions with the .sync integration: the state machine starts the customization job, waits for it however long it runs, and continues to evaluation and notification only after a real success, with failures routed to a Catch.
X: B=Lambda polling loop: a Lambda function can run for at most 15 minutes, so it cannot wait for a job that takes hours, and the loop is the custom polling code the team wants to avoid.
C=Two fixed schedules: a fixed 24-hour gap ignores the job's real status. A slow job means evaluating a model that does not exist yet, and a failed job is never noticed.
D=SageMaker Pipelines training step: a training step runs a SageMaker AI training job. It does not run Bedrock model customization jobs by model ID.
T: Long-running Bedrock jobs in a workflow → Step Functions optimized integration with .sync, so the service waits and handles failure without custom polling.

@ MLA-C02 D3 T3.3 applied tradeoff
S: A team builds a document-classification workflow with Amazon Bedrock Flows. Releases must move from test to production without code changes in the calling application, and a bad release must be rolled back within minutes. How should the application call the flow?
A: Invoke the flow through a production alias, and at each release point the alias to a newly created immutable flow version, or back to the previous version.

@ MLA-C02 D3 T3.3 advanced use-case
S: A CodePipeline pipeline promotes a new prompt version and a new guardrail version of a Bedrock-based assistant from staging to production. The team wants the pipeline to block promotion automatically when answer quality or safety regresses. Which TWO stages should be added before the production deployment? (Select TWO)
A: A CodeBuild action that runs an Amazon Bedrock evaluation job, for example LLM-as-a-judge, on a golden prompt set and fails the stage if scores fall below agreed thresholds.
B: A CodeBuild action that sends a red-team prompt set through the ApplyGuardrail API with the new guardrail version and fails the stage if any harmful content is not blocked.
C: A manual approval action in which a reviewer reads the change summary of the pipeline and approves the release when the commit messages say the changes were tested.
D: A CloudWatch alarm on the invocation errors of the production application that rolls back the stack if errors rise during the first hour after the deployment.
E: A CodeBuild action that runs cfn-lint on the templates and fails the stage if the guardrail or prompt resources contain syntax errors or unknown property names.
K: A,B
G: ## What an evaluation gate is
A gate is a pipeline step that measures the candidate release and **fails the pipeline** when a measurement misses a threshold, so a regression never reaches production. For generative AI, a prompt or guardrail change can break quality or safety without any code error, so the gates must test model behavior.
## Two kinds of gates
- **Quality gate**: run the candidate prompt over a golden dataset of representative inputs and score the outputs. Amazon Bedrock evaluation jobs can do this with automatic metrics or with a judge model (LLM-as-a-judge) for criteria such as correctness, completeness and helpfulness. A CodeBuild script starts the job, waits, reads the scores and exits non-zero below the threshold.
- **Safety gate**: send a red-team set (prompt attacks, denied topics, PII) through the `ApplyGuardrail` API with the new guardrail version. `ApplyGuardrail` evaluates text against a guardrail without calling a model, so the test is quick and cheap. Any input that should be blocked but is not fails the build.
## What is not a gate
Human approval based on commit messages, syntax linting and post-deployment alarms all have value, but none measures the new release's behavior before promotion.
W: A=Evaluation job gate: scoring the candidate prompt on a golden set and failing below threshold blocks quality regressions automatically before production.
B=ApplyGuardrail red-team gate: replaying known harmful inputs against the new guardrail version proves the safety controls still block them, and fails the stage if they do not.
X: C=Manual approval on commit messages: it is neither automatic nor a measurement. A reviewer trusting "tested" in a commit message cannot see a drop in answer quality.
D=Production error alarm: it acts after the release is already live, and quality or safety regressions do not raise invocation errors at all.
E=cfn-lint: it catches template syntax and property mistakes. A perfectly valid template can still contain a worse prompt or a weaker guardrail.
T: Gate GenAI releases on behavior: an evaluation job on a golden set for quality and ApplyGuardrail red-team tests for safety, both failing the build below threshold.

@ MLA-C02 D3 T3.3 applied troubleshooting
S: A team deploys an AI agent to Amazon Bedrock AgentCore Runtime from a container image. Its CodePipeline currently rebuilds the image separately in the staging stage and in the production stage. A production failure was traced to a dependency version that changed between the two builds. What should the team change?
A: Build the image once, push it to Amazon ECR, and deploy that same image digest to staging and then, after the staging tests pass, to production.
B: Keep separate builds but pin the base image to the latest tag in both stages, so staging and production always pull the same newest base layers.
C: Rebuild the image in production with the CodeBuild cache enabled, so that the dependency layers are reused from the staging build automatically.
D: Deploy production directly from the source repository with a separate CodeBuild project that runs the same build commands as the staging stage.
K: A
G: ## Build once, promote the same artifact
A release pipeline should test exactly what it ships. If each stage rebuilds from source, anything resolved at build time (a `pip install` without pinned versions, a base image tag such as `latest`) can differ between builds, so the tested artifact is not the deployed one.
## How it looks for container-based agents
- The build stage creates the image once and pushes it to Amazon ECR.
- Every later stage refers to the image by its **digest** (`repo@sha256:...`), which identifies the exact bytes; tags can be moved, digests cannot.
- Staging deploys the digest and runs the agent tests and evaluations; production deploys the same digest after the gate passes.
Pinning dependency versions (a lock file) is good practice too, but promoting one artifact is what guarantees staging and production match.
W: Build once and promote the digest: staging tests and production run byte-for-byte the same image, so a dependency cannot change between the tested build and the released one.
X: B=Pin to the latest tag: latest is a moving tag, so two builds at different times can still pull different base layers, and application dependencies can still drift.
C=Production rebuild with cache: the cache is an optimization that may or may not be hit; it is not a guarantee, and it is still a second, untested build.
D=Separate production build from source: running the same commands again is exactly how the drift happened; it creates a new, untested artifact.
T: Build the agent image once and deploy the same immutable ECR digest to every stage, so what was tested is what ships.
V: AWS CodePipeline, AWS CodeBuild, Amazon ECR, Amazon Bedrock AgentCore
