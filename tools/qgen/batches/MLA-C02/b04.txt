# MLA-C02 b04: D4 generative-AI additions (T4.1 FM/agent monitoring, T4.2 FM cost, T4.3 FM security)

@ MLA-C02 D4 T4.1 applied use-case
S: An insurer runs a claims-summary feature on an Amazon Bedrock model through the Converse API. Auditors require every prompt and model response to be kept for one year, and engineers want to search the last two weeks of requests interactively while debugging. Nothing is recorded today. What should the ML engineer do?
A: Turn on AWS CloudTrail data events for the Bedrock runtime API and query the trail with Athena, because each event stores the full prompt and the model's response text
B: Enable Bedrock model invocation logging in the Region with both an S3 bucket and a CloudWatch Logs log group as destinations, and set retention on each destination
C: Enable data capture on the model, the same way as on a SageMaker endpoint, so that the request and response payloads are written to an S3 prefix for the audit team
D: Create a high-resolution CloudWatch dashboard on the AWS/Bedrock namespace so that every invocation, with its prompt and response, can be searched for one year
K: B
G: ## Two kinds of Bedrock telemetry
Amazon Bedrock produces two very different signals:
- **CloudWatch metrics** in the `AWS/Bedrock` namespace: numbers such as `Invocations`, `InvocationLatency`, `InputTokenCount`, `OutputTokenCount` and `InvocationThrottles`, per model ID. They tell you how much and how fast, never what was said.
- **Model invocation logging**: an opt-in, account-level setting per Region. When it is on, Bedrock writes a log record for each invocation with the request metadata, the input (prompt) and the output (response), plus token counts.
## Destinations
Invocation logging can deliver to Amazon S3, to CloudWatch Logs, or to both:
- S3 suits long retention and cheap storage; lifecycle rules can move old logs to colder classes, and Athena can query them later.
- CloudWatch Logs suits interactive search with Logs Insights, metric filters and alarms. Set a retention period on the log group so the cost does not grow forever.
Bedrock needs an IAM role (for CloudWatch Logs) and a bucket policy (for S3) that allow it to write. Logging is off by default.
W: Model invocation logging to S3 and CloudWatch Logs: it is the feature that captures full prompts and responses; S3 gives the one-year audit copy and CloudWatch Logs gives Logs Insights search for recent debugging.
X: A=CloudTrail data events: CloudTrail records who called which API, when and from where, not the prompt and response bodies, so it cannot satisfy a content audit.
C=SageMaker-style data capture: data capture is a setting of SageMaker AI real-time endpoints; on-demand Bedrock models are called through the Bedrock runtime and have no data capture option.
D=Dashboard on AWS/Bedrock metrics: metrics are numeric counts and latencies, so no dashboard built on them can show or search the text of a prompt.
T: Bedrock prompts and responses are recorded only by model invocation logging (to S3 and/or CloudWatch Logs); CloudWatch metrics and CloudTrail carry numbers and API activity, not content.
V: Amazon Bedrock, Amazon CloudWatch, Amazon S3

@ MLA-C02 D4 T4.1 applied troubleshooting
S: A retail chatbot calls an Amazon Bedrock model on demand. Every weekday between 12:00 and 13:00, some users get errors. CloudWatch shows that `InvocationThrottles` for the model ID rises sharply in that hour, while `InvocationServerErrors` stays at zero and `InvocationLatency` is normal. What should the ML engineer do FIRST?
A: Switch the chatbot to a larger model in the same family, because a model with more parameters is allocated a higher request quota for on-demand use in each Region
B: Increase the `maxTokens` inference parameter so that each answer completes in one call and the client sends fewer follow-up requests during the busy lunch hour
C: Add retries with exponential backoff and jitter, and route the calls through a cross-Region inference profile or request a higher quota for the peak hour
D: Open a support case about a service fault, because server-side errors in the Bedrock runtime cause intermittent failures that only appear at certain hours
K: C
G: ## Reading the Bedrock runtime metrics
The `AWS/Bedrock` namespace splits failures by cause, per `ModelId`:
- `InvocationThrottles`: requests rejected because the account went over its requests-per-minute or tokens-per-minute quota for that model (a `ThrottlingException`).
- `InvocationClientErrors`: bad requests, for example an invalid parameter or an access problem.
- `InvocationServerErrors`: faults on the service side.
- `InvocationLatency`: how long successful calls took.
## What the pattern means
Throttles that rise only at a predictable peak, with no server errors and normal latency, mean demand is above the on-demand quota for that hour. The service is healthy; the account is asking for more than it is allowed.
## Fixes for throttling
- Retry with **exponential backoff and jitter** so short bursts are smoothed instead of retried in waves.
- Use a **cross-Region inference profile**, which spreads requests across several Regions and so gives more throughput for the same model.
- Request a **service quota increase**, or for steady high volume consider Provisioned Throughput.
W: Backoff plus more capacity: throttling is a quota limit, so the client must retry politely and the workload needs more headroom, which a cross-Region inference profile or a quota increase provides.
X: A=Larger model: quotas are set per model, and bigger models do not get higher quotas (they often get lower ones); a larger model also costs more per token and does not address the quota that is being exceeded.
B=Larger maxTokens: raising the output limit makes each call consume more tokens, which uses up a tokens-per-minute quota faster and can increase throttling.
D=Service fault: `InvocationServerErrors` is zero, so the metrics already show the service is healthy; the failures are throttles caused by the account's own peak traffic.
T: Rising `InvocationThrottles` with no server errors means quota pressure: add backoff with jitter and more capacity (cross-Region inference profile or quota increase).
V: Amazon Bedrock, Amazon CloudWatch

@ MLA-C02 D4 T4.1 advanced troubleshooting
S: A support agent built with an open-source framework runs on Amazon Bedrock AgentCore Runtime and calls four tools. Some answers come back incomplete, and the team suspects that tool calls fail silently. They need step-level visibility into each request. Which TWO actions should the ML engineer take? (Select TWO)
A: Enable CloudWatch Transaction Search and instrument the agent with AWS Distro for OpenTelemetry so AgentCore Observability records a trace with a span for each model and tool call
B: Enable SageMaker Model Monitor model quality monitoring for the agent so that each failed tool call is reported as a constraint violation in the next monitoring run
C: Turn on CloudTrail data events for the agent's Region so that the reasoning steps and tool inputs of each conversation turn are stored in the trail for later review
D: Open the CloudWatch generative AI observability view, filter traces by session, and inspect tool spans that have an error status or unusually long duration
E: Raise the agent's model temperature so that the model retries a failed tool with different arguments instead of returning the partial result to the user
K: A,D
G: ## Why agents need tracing
A single agent request is a chain: the model plans, calls a tool, reads the result, maybe calls another tool, then answers. If one tool call times out or returns an error that the agent then ignores, the final answer is incomplete but the request still "succeeds". Request-level metrics cannot show which step went wrong.
## AgentCore Observability
Amazon Bedrock AgentCore Observability is built on Amazon CloudWatch and OpenTelemetry:
- Agents hosted in AgentCore Runtime publish runtime metrics automatically.
- For detailed **traces and spans**, enable **CloudWatch Transaction Search** once per account and instrument the agent code with **AWS Distro for OpenTelemetry (ADOT)**. Popular agent frameworks emit OpenTelemetry spans for model calls and tool calls.
- The CloudWatch **generative AI observability** pages show sessions, traces and spans, with latency, token usage and errors for each step.
## Example
A trace for session `s-81f2` shows four spans: model call, `lookup_order` tool (ok), `refund_status` tool (error: timeout after 10 s), model call that wrote the answer. The broken step is now obvious.
W: A=Transaction Search plus ADOT instrumentation: this turns on the trace pipeline so every model and tool call becomes a span that AgentCore Observability stores in CloudWatch.
D=Generative AI observability view: once traces exist, filtering by session and looking at tool spans with error status or long duration shows exactly which tool failed and how often.
X: B=SageMaker Model Monitor: Model Monitor analyzes data captured from SageMaker endpoints against a baseline; it has no knowledge of an agent's tool calls in AgentCore Runtime.
C=CloudTrail data events: CloudTrail records API activity, not the agent's internal reasoning steps or tool arguments, so it cannot rebuild the step chain of a request.
E=Higher temperature: temperature changes how random the generated text is; it does not add retries, and it hides the failure instead of making it visible.
T: For step-level agent debugging, enable Transaction Search and OpenTelemetry instrumentation so AgentCore Observability records spans per tool call, then inspect failing spans in CloudWatch.
V: Amazon Bedrock AgentCore, Amazon CloudWatch, AWS Distro for OpenTelemetry

@ MLA-C02 D4 T4.1 applied troubleshooting
S: A web chat streams answers from an Amazon Bedrock model with the ConverseStream API. Users say some answers stop in the middle of a sentence, but every stream finishes without an error and `InvocationClientErrors` is zero. The ML engineer needs a production metric that shows how often answers are cut off. What should the engineer do?
A: Create an alarm on the `InvocationClientErrors` metric for the model ID, because every truncated answer is counted there as a rejected request from the chat client
B: Read the stop reason in the stream's final message event and publish a custom CloudWatch metric each time it is `max_tokens`, then alarm on that rate
C: Alarm on the average `OutputTokenCount` metric for the model ID, because a falling average shows exactly which responses were cut off before they were finished
D: Enable the contextual grounding check in a guardrail, because it flags responses that end early and reports them as interventions in the guardrail metrics
K: B
G: ## How a streamed answer ends
With `ConverseStream`, the model sends text in small events. The stream ends with a `messageStop` event that carries a **stop reason**, followed by a metadata event with token usage and latency. Common stop reasons:
- `end_turn`: the model finished its answer normally.
- `max_tokens`: the answer reached the `maxTokens` limit and was cut off.
- `stop_sequence`, `tool_use`, `guardrail_intervened`, `content_filtered`: other ways the turn ended.
## Why the usual metrics miss it
A truncated answer is still a successful call: no exception, no client error, no server error. Bedrock's built-in metrics count invocations and tokens but do not report how often each stop reason occurs.
## Making truncation measurable
The application already receives the stop reason, so it can publish a custom metric, for example `TruncatedResponses` with a dimension for the feature, using `PutMetricData` or the CloudWatch embedded metric format in its logs. An alarm on the share of truncated answers then shows when a prompt change or a too-small `maxTokens` setting starts cutting answers.
W: Custom metric from the stop reason: the `max_tokens` stop reason is the exact signal of truncation, and publishing it as a metric turns individual cut-offs into a rate that can be graphed and alarmed.
X: A=InvocationClientErrors alarm: a truncated stream is a successful call, so it never increments client errors; that is exactly why the metric is zero here.
C=Average OutputTokenCount: an average mixes complete and cut answers and changes for many reasons, such as shorter questions; it cannot say which responses hit the limit.
D=Contextual grounding check: grounding compares the answer with source text for unsupported claims and relevance; it does not detect that an answer ended early.
T: Truncation is not an error: capture the `max_tokens` stop reason in the application and publish it as a custom CloudWatch metric to monitor it.
V: Amazon Bedrock, Amazon CloudWatch

@ MLA-C02 D4 T4.1 advanced troubleshooting
S: A travel company runs a supervisor agent and three specialist agents on Amazon Bedrock AgentCore Runtime. A few requests a day pass work back and forth between two specialists until the request times out, and token spend for those sessions is very high. Today each agent's logs are viewed separately. How should the ML engineer detect these coordination failures?
A: Alarm on the average `InvocationLatency` of the model ID that the agents share, because a handoff loop shows up as a slower average latency across all model calls
B: Add a denied topic to the agents' guardrail that describes repeated delegation, so that a loop between two specialists is blocked and counted as an intervention
C: Raise the session timeout of the supervisor agent so that looping requests have time to finish, and compare the final answers with those of normal requests
D: Propagate one session ID and trace context through every agent so each request is one trace, and alarm on a custom metric of handoffs or tokens per session
K: D
G: ## Coordination failures in multi-agent systems
In a multi-agent design, a supervisor delegates to specialists, and specialists may hand work to each other. Typical failures are not crashes but bad coordination:
- **Handoff loops**: agent A sends the task to agent B, which sends it back to A.
- **Lost context**: a specialist receives the task without the facts it needs and asks again.
- **Runaway cost**: each hop adds model calls, so token use per session explodes.
## Seeing the whole request
When each agent logs alone, nobody sees the chain. The fix is **trace context propagation**: the supervisor starts a trace for the session and passes the session ID and OpenTelemetry trace context to each agent it calls. AgentCore Observability then shows the whole request as one trace, with a span for every agent hop, model call and tool call.
## Alarming on the pattern
From the trace data or from application logs, publish per-session counts such as `handoffs` and `tokens`. An alarm when a session exceeds, for example, 8 handoffs or 200,000 tokens catches loops early. A hard cap on handoffs in the supervisor code then stops them.
W: Shared session and trace context with a per-session metric: one end-to-end trace makes the back-and-forth handoffs visible, and a handoff or token count per session turns the loop into an alarmable signal.
X: A=Average model latency: a few looping sessions a day hardly move the average latency of all model calls, and latency does not show which agents passed work to each other.
B=Denied topic for delegation: denied topics classify the meaning of user prompts and model responses; they do not see the control flow between agents, so a loop cannot be detected that way.
C=Longer timeout: a longer timeout lets loops run longer and spend more tokens, and it adds no visibility into why the specialists keep returning work.
T: Detect multi-agent coordination failures with end-to-end traces (one session ID and trace context across agents) and per-session metrics such as handoffs and tokens.
V: Amazon Bedrock AgentCore, Amazon CloudWatch

@ MLA-C02 D4 T4.1 advanced use-case
S: A bank's FAQ assistant on Amazon Bedrock was approved after an offline evaluation. Since then, the document set and user questions have changed, and the team worries that answer quality is drifting. Model invocation logs are already delivered to Amazon S3. The team wants a weekly, automated quality signal without human labeling. What should the ML engineer build?
A: A SageMaker Model Monitor data quality schedule that compares this week's prompts with the training baseline of the foundation model and reports drifted features
B: A CloudWatch alarm on the weekly sum of `OutputTokenCount` for the model, because answers that become shorter or longer indicate that answer quality has dropped
C: A weekly job that samples logged prompts and responses, runs a Bedrock LLM-as-a-judge evaluation job on them, and publishes the scores as CloudWatch metrics
D: A guardrail word filter containing the phrases that bad answers usually contain, with a weekly report of the number of words that the filter blocked in responses
K: C
G: ## Quality drift in LLM output
A generative model does not change by itself, but its inputs do: new documents, new kinds of questions, a changed prompt template or a new model version. Answer quality can drift even when latency, errors and token counts look normal, because those metrics say nothing about whether the answer is correct or helpful.
## Evaluating production traffic
Amazon Bedrock evaluations can score responses with an **LLM-as-a-judge**: a separate evaluator model rates each response on metrics such as correctness, completeness, helpfulness, faithfulness and harmfulness. You can **bring your own inference responses**, so the job scores responses that the application already produced instead of generating new ones.
## A weekly pipeline
- An Amazon EventBridge Scheduler schedule starts a job each week.
- The job samples, for example, 500 prompt/response pairs from the invocation logs in S3 and writes them in the evaluation dataset format.
- It starts a Bedrock evaluation job; when it completes, it reads the scores and publishes them as custom CloudWatch metrics.
- An alarm fires when, for example, the average correctness score falls below the approved baseline.
W: Sampled logs scored by an LLM-as-a-judge evaluation: it measures answer quality directly on real production traffic every week without human labels, and the published scores give a trend that alarms can watch.
X: A=Model Monitor data quality: Model Monitor compares tabular features from SageMaker endpoint captures with a baseline; it does not score free-text answers, and there is no training baseline of a Bedrock foundation model to compare with.
B=Output token sum: answer length changes with traffic volume and question mix; it is not a measure of correctness, so a constant token count can hide a real drop in quality.
D=Word filter report: word filters block exact words and phrases; a wrong but polite answer contains none of them, so the count says little about quality.
T: Track LLM output quality over time by sampling production logs and scoring them with Bedrock LLM-as-a-judge evaluations, then alarm on the published scores.
V: Amazon Bedrock, Amazon S3, Amazon CloudWatch, Amazon EventBridge

@ MLA-C02 D4 T4.1 applied troubleshooting
S: An internal assistant uses an Amazon Bedrock model. The CloudWatch dashboard shows the Average statistic of `InvocationLatency` at about 1.8 seconds, which meets the 3-second target, yet many users report waits of 8 seconds or more. How should the ML engineer change the monitoring?
A: Switch the dashboard to the Sum statistic of `InvocationLatency`, because the total latency per minute shows how long the slowest users waited for answers
B: Graph and alarm on the p90 and p99 percentile statistics of `InvocationLatency`, so the slow tail that users notice is measured against the target
C: Replace the latency metric with the `Invocations` metric, because the number of calls per minute shows directly how long each user had to wait
D: Enable model invocation logging and remove the latency widget, because the logged response text also gives the wait time that each user experienced
K: B
G: ## Averages hide the tail
Latency is rarely normally distributed. Most calls may be fast while a minority (long prompts, long answers, retries after throttling) take much longer. An average of 1.8 seconds can hide one call in ten taking 8 seconds.
## Percentile statistics in CloudWatch
CloudWatch can compute **percentiles** for metrics such as `InvocationLatency`:
- `p50` is the median: half of the calls are faster.
- `p90` and `p99`: 90 or 99 percent of calls are faster; the rest are the slow tail.
Service level objectives are usually written on percentiles ("p95 under 3 seconds") because users remember the slow requests.
## What to do next
Once the tail is visible, split it by cause: compare `OutputTokenCount` (long answers take longer), check `InvocationThrottles` (retries add delay) and consider streaming so users see text sooner.
W: Percentile statistics: p90 and p99 show the latency of the slowest calls, which is what users complain about, and an alarm on them tests the real experience against the target.
X: A=Sum statistic: summing latency adds up all calls in a period, so it grows with traffic and says nothing about how slow any single call was.
C=Invocations count: the number of calls measures load, not how long each call took.
D=Invocation logs instead of metrics: logs hold prompts, responses and metadata for investigation, but removing the latency metric leaves nothing to graph or alarm on.
T: Monitor FM latency with percentiles (p90/p99), not averages, so the slow tail that users notice is visible and alarmable.
V: Amazon Bedrock, Amazon CloudWatch

@ MLA-C02 D4 T4.2 applied use-case
S: Each quarter, a compliance team classifies about 5 million archived customer emails with an Amazon Bedrock model. Today a fleet of Lambda functions calls InvokeModel on demand for each email; the run hits throttling and costs more than planned. Results are needed within a few days. Which approach reduces cost MOST?
A: Buy Provisioned Throughput with no commitment for the week of the run, because reserved model units are always billed at a lower rate per token than on-demand calls
B: Route the Lambda calls through a cross-Region inference profile, because spreading the requests across Regions lowers the price charged for each input and output token
C: Write the emails as JSONL records to Amazon S3 and run a Bedrock batch inference job, which is priced lower than on-demand and writes the results back to S3
D: Raise the reserved concurrency of the Lambda functions so the run finishes in fewer hours, because Bedrock bills on-demand inference by the hour of model use
K: C
G: ## On-demand versus batch inference
- **On-demand** inference (`InvokeModel`, `Converse`) answers each request right away and is billed per input and output token. It is limited by per-minute request and token quotas.
- **Batch inference** takes a file of records in Amazon S3 (JSONL, one request per line), processes them asynchronously and writes the outputs to an S3 location. For supported models it is priced lower than on-demand inference, and a job is governed by job-level quotas (records per job, jobs in progress) instead of the per-minute request and token quotas that throttle a client fleet.
## When batch fits
Batch fits large, non-interactive jobs where results can wait hours: quarterly classification, nightly enrichment, backfills. It also removes the client-side fleet: no Lambda retries, no throttling logic.
## Example
`CreateModelInvocationJob` with `inputDataConfig` = `s3://archive-jobs/q3/input/` and `outputDataConfig` = `s3://archive-jobs/q3/output/`; an EventBridge rule on the job state change starts the next step.
W: Batch inference job: the workload is large and not time-critical, so the discounted batch price and the absence of per-request throttling cut both cost and operational effort.
X: A=Provisioned Throughput: it is billed per model unit per hour for the whole term whether or not it is used, and sizing it for a one-week burst seldom beats the batch discount.
B=Cross-Region inference profile: it raises available throughput by spreading requests over Regions; tokens are still billed at on-demand prices, so it fixes throttling, not cost.
D=More Lambda concurrency: on-demand Bedrock is billed per token, not per hour, and more parallel callers make throttling worse while the token bill stays the same.
T: For large, delay-tolerant FM workloads, use Bedrock batch inference from S3: lower price than on-demand and no per-request throttling.
V: Amazon Bedrock, Amazon S3, AWS Lambda

@ MLA-C02 D4 T4.2 applied comparison
S: An ML engineer is deciding where Amazon Bedrock prompt caching will lower cost and latency. Which workload benefits MOST from enabling it?
A: A nightly job that summarizes 20,000 different contracts, where each request contains one contract and a short instruction of about 40 words
B: A sentiment classifier for short social media posts, where each request contains only a 30-word instruction followed by the text of one post
C: A monthly report generator that sends a long finance glossary once on the first business day and otherwise makes no calls during the month
D: An agent that sends the same long system prompt and tool definitions on every turn, with users making several turns within a few minutes
K: D
G: ## How prompt caching works
With Amazon Bedrock prompt caching, you mark a **cache checkpoint** in the prompt. The first request writes the prefix up to the checkpoint to a cache; later requests that start with exactly the same prefix read it from the cache instead of processing it again. Cached reads are billed at a much lower rate than normal input tokens and reduce time to first token.
## What it needs to pay off
- **A long, identical prefix**: system prompt, tool definitions, a reference document. Models set a minimum number of tokens per checkpoint, so a 30-word instruction is too small to cache.
- **Reuse within the cache lifetime**: entries expire after a short time without use (5 minutes by default; some models offer a longer option). Traffic once a month never finds a warm cache.
- **Static content first, changing content last**: anything different in the prefix, such as a different contract, is a cache miss.
## Example
An agent with a 3,000-token system prompt and 2,000 tokens of tool schemas sends those 5,000 tokens on every turn. With a checkpoint after the tool definitions, turns two, three and four of a session read them from the cache.
W: Agent with a repeated long prefix: the same large system prompt and tool definitions are sent on every turn within minutes, so most input tokens become cheap, fast cache reads.
X: A=Different contracts each request: the long part of each prompt is unique, so there is no shared prefix to reuse, and the short instruction is too small to be worth caching.
B=Short instruction plus a post: the repeated part is far below the minimum size of a cache checkpoint, and the post itself changes every time.
C=Monthly reuse: cache entries expire within minutes of inactivity, so a prefix sent once a month is always a cache write, never a read.
T: Prompt caching pays off for a long identical prompt prefix that is reused within minutes, such as an agent's system prompt and tool definitions.
V: Amazon Bedrock

@ MLA-C02 D4 T4.2 applied comparison
S: A team is comparing on-demand inference and Provisioned Throughput for a new Amazon Bedrock workload and asks the ML engineer to confirm how each is billed. Which TWO statements are correct? (Select TWO)
A: Provisioned Throughput is billed for each model unit per hour for the whole term, whether or not the workload sends any requests during that time
B: Provisioned Throughput bills per token like on-demand, but at a lower rate per token, and it scales its model units to zero automatically at night
C: On-demand inference is billed for the input and output tokens that each request processes, with no capacity commitment and no charge while idle
D: On-demand inference requires a one-month or six-month commitment, which in return guarantees that requests are never throttled in busy hours
E: Provisioned Throughput is free for the first model unit, and only additional model units beyond the first one are charged per hour of usage
K: A,C
G: ## Two ways to pay for a Bedrock model
- **On-demand**: pay per use. Text models are billed per input token and per output token (output tokens usually cost more). Nothing is charged when no requests arrive. Throughput is shared and limited by account quotas, so peaks can be throttled.
- **Provisioned Throughput**: buy a number of **model units**, each giving a fixed amount of throughput for one model. It is billed **per model unit per hour**, with no commitment or with a 1-month or 6-month commitment that lowers the hourly rate. The charge runs for as long as the capacity exists, used or not.
## How to choose
- Spiky, low or unpredictable traffic: on-demand, because idle time costs nothing.
- Steady, high, predictable traffic that needs guaranteed throughput: Provisioned Throughput, sized so that the units are well used.
## Example
A chatbot busy only during office hours, using 10 percent of a model unit on average, would pay for 24 hours of capacity every day with Provisioned Throughput; on-demand charges only for the tokens it actually uses.
W: A=Hourly model units: Provisioned Throughput reserves capacity, so the bill is per model unit per hour for the term regardless of usage.
C=Per-token on-demand: on-demand charges only for tokens processed, with no commitment, so idle periods cost nothing.
X: B=Per-token Provisioned Throughput with scale to zero: Provisioned Throughput is not billed per token and does not scale down by itself; the units are charged while they exist.
D=Commitment for on-demand: commitment terms belong to Provisioned Throughput; on-demand has none and remains subject to quotas and throttling.
E=Free first model unit: there is no free model unit; every unit of Provisioned Throughput is billed per hour.
T: On-demand bills tokens with no commitment; Provisioned Throughput bills model units per hour for the term, used or not.
V: Amazon Bedrock

@ MLA-C02 D4 T4.2 applied use-case
S: Three product teams in one AWS account call the same Amazon Bedrock model. Finance wants each team's Bedrock spend shown separately in AWS Cost Explorer and an email when a team's forecast spend for the month reaches 80 percent of its budget. What should the ML engineer do?
A: Have each team call the model through its own application inference profile tagged `team`, activate the tag for cost allocation, and set tag-filtered budgets
B: Add a `team` tag to the shared foundation model's ARN and activate it for cost allocation, because tags on the model ID split its token charges between the calling teams
C: Enable model invocation logging and build a CloudWatch dashboard of each team's prompts, because Cost Explorer reads the logged token counts to split the charges by team
D: Create a separate Provisioned Throughput for each team and tag it, because on-demand Bedrock usage in an account cannot be divided between teams in any way
K: A
G: ## The problem with shared model IDs
When everyone calls the same model ID on demand, the bill shows one line for that model. Cost allocation tags only work on resources that can carry tags, and a foundation model ID is not one of your resources.
## Application inference profiles
An **application inference profile** is a resource you create in your account that points to a model (or to a cross-Region system profile). It has an ARN and can carry **tags**. Applications call `InvokeModel` or `Converse` with the profile ARN in place of the model ID, and the usage is recorded against that profile.
## From tags to budgets
- Create profiles such as `search-team-profile` with tag `team=search`.
- Activate `team` as a **cost allocation tag** in the Billing console (tags appear in cost data only after activation, and only from then on).
- In **Cost Explorer**, group Bedrock costs by `team`.
- In **AWS Budgets**, create one cost budget per team filtered on its tag, with a forecast alert at 80 percent sent to an email address or SNS topic.
CloudWatch metrics for the profile also give per-team token counts.
W: Tagged application inference profiles: they turn shared model usage into taggable resources, so cost allocation tags flow into Cost Explorer and AWS Budgets can alert per team on forecast spend.
X: B=Tags on the foundation model: a base foundation model is provided by AWS and is not a resource in your account, so you cannot tag it; even if you could, one shared resource with one `team` value cannot split usage between three teams.
C=Invocation logging dashboard: logs and dashboards show usage, but Cost Explorer and Budgets work from billing data and tags, not from log contents, so no budget alert results.
D=Provisioned Throughput per team: on-demand usage can be split with application inference profiles, and buying hourly capacity for each team would raise cost for teams with light or spiky traffic.
T: To split shared Bedrock spend by team, call the model through tagged application inference profiles and use the activated cost allocation tags in Cost Explorer and AWS Budgets.
V: Amazon Bedrock, AWS Cost Explorer, AWS Budgets

@ MLA-C02 D4 T4.2 advanced tradeoff
S: A logistics company extracts 12 fields from delivery notes with a large Amazon Bedrock model. Accuracy is 97 percent on a labeled test set of 800 notes, and the business requires at least 95 percent. Monthly cost is too high, and a smaller model from the same family costs a fraction as much per token. What should the ML engineer do?
A: Keep the large model and lower the temperature to zero, because deterministic sampling reduces the price that is charged for each output token of the response
B: Evaluate the smaller model on the same 800 labeled notes with a Bedrock evaluation job and switch if it reaches 95 percent, keeping that test set for later checks
C: Move the large model to Provisioned Throughput with a 6-month commitment, because committed capacity always costs less than on-demand calls for any traffic level
D: Fine-tune the large model on the 800 labeled notes, because a customized model is billed at a lower per-token rate than the base model that it was trained from
K: B
G: ## Right-sizing the model
Model price grows with model size. Many production tasks, such as field extraction, classification or routing, do not need the largest model in a family. If a smaller model meets the quality bar, it is usually cheaper per token and faster.
## Decide with data, not guesses
The team already has what it needs: a labeled test set and an explicit threshold (95 percent).
- Run the smaller model on the same 800 notes. A Bedrock model evaluation job with the team's own prompt dataset and ground truth, or a simple script, produces comparable scores.
- If it meets the threshold, switch, and keep the test set as a regression check for future prompt or model changes.
- If it falls just short, prompt changes or a few examples in the prompt often close the gap before considering customization.
## Trade-off
The smaller model saves money on every call; the cost is an evaluation run and the risk of slightly lower accuracy, which the threshold keeps within bounds.
W: Evaluate then switch: measuring the smaller model on the same labeled set proves whether it meets the 95 percent requirement, and switching to it cuts the per-token price for every future call.
X: A=Temperature zero: temperature controls randomness, not price; tokens cost the same at any temperature.
C=Six-month Provisioned Throughput: committed capacity is billed per hour whether used or not and is only cheaper when utilization is high; it keeps the most expensive model.
D=Fine-tune the large model: customization adds training and hosting cost and does not make the large model cheaper per token than the smaller one.
T: Cut FM cost by testing a smaller model on your own labeled set and switching when it meets the quality bar.

@ MLA-C02 D4 T4.2 applied troubleshooting
S: A team's Amazon Bedrock knowledge base indexes 300,000 product documents from Amazon S3; about 500 change each day. Embedding costs are far higher than expected. The nightly job deletes the data source, recreates it, and starts an ingestion job. How should the ML engineer reduce the embedding cost?
A: Keep the nightly job but switch to an embedding model with a larger vector dimension, because larger vectors need fewer embedding calls for each document that is ingested
B: Move the documents to a second S3 bucket every night before the job, because a knowledge base ingests only the objects that are new in a bucket it has not seen yet
C: Replace the nightly job with a weekly full rebuild, because a knowledge base charges embedding cost only once per week for each document regardless of how often it changes
D: Keep the data source and only start an ingestion job on it each night, because a sync processes just the documents that were added, changed or deleted since the last one
K: D
G: ## How a knowledge base sync works
An Amazon Bedrock knowledge base reads documents from a **data source** (for example an S3 prefix), splits them into chunks, calls an embedding model for each chunk, and stores the vectors in a vector store.
A **sync** (`StartIngestionJob`) on an existing data source is **incremental**: it compares the source with what was ingested before and processes only new, modified and deleted documents.
## Why the cost exploded
Embedding is billed per input token sent to the embedding model. Deleting and recreating the data source throws away that history, so every night all 300,000 documents are chunked and embedded again, although only about 500 changed.
## Example
With incremental sync, the nightly job embeds roughly 500 documents instead of 300,000, a reduction of more than 99 percent in embedding tokens, and the job also finishes much sooner.
W: Incremental sync on the existing data source: only changed documents are embedded again, so nightly embedding tokens drop from the whole corpus to the daily changes.
X: A=Larger vector dimension: the number of embedding calls depends on the number of chunks, not on vector size; larger vectors also raise vector store cost.
B=Copy to a new bucket: a new bucket or data source has no ingestion history, so everything is embedded again, which is the same problem in a different place.
C=Weekly full rebuild: a full rebuild re-embeds every document each time; doing it less often lowers cost but leaves the index up to a week out of date and still wastes most of the tokens.
T: Keep knowledge base data sources and run incremental syncs so only added, changed or deleted documents are embedded again.

@ MLA-C02 D4 T4.3 applied use-case
S: An HR assistant on Amazon Bedrock must refuse questions about planned layoffs and must never show employees' US Social Security numbers that appear in retrieved HR records. Which TWO Amazon Bedrock Guardrails settings should the ML engineer configure? (Select TWO)
A: A denied topic for workforce reductions, with a clear definition and sample phrases, so related questions and answers are blocked
B: A contextual grounding check with a high grounding threshold, so answers about layoffs that the documents do not support are blocked
C: A sensitive information filter for the US Social Security number type, set to mask or block it in model responses for every user
D: A prompt attack filter at HIGH strength, so that questions about layoffs and requests for ID numbers are classified as jailbreaks
E: A content filter for the misconduct category at HIGH strength, so that any message mentioning layoffs or ID numbers is filtered
K: A,C
G: ## The building blocks of a guardrail
Amazon Bedrock Guardrails combines several policies, each for a different kind of risk:
- **Content filters**: harmful categories (hate, insults, sexual, violence, misconduct) and **prompt attacks**, each with a strength.
- **Denied topics**: subjects the application must not discuss, described in natural language with a definition and sample phrases.
- **Word filters**: exact words or phrases, plus a managed profanity list.
- **Sensitive information filters**: built-in PII types (such as `US_SOCIAL_SECURITY_NUMBER`, email, phone) and custom regular expressions, with the action **block** or **mask** (anonymize).
- **Contextual grounding check**: scores whether a response is supported by the source text and relevant to the query.
## Matching policy to requirement
"Do not discuss subject X" is a denied topic. "Never reveal identifier Y" is a sensitive information filter. Content filters cover harmful content, not business-confidential topics.
## Example
Denied topic `Workforce reductions`: "Questions or statements about planned layoffs, redundancies or job cuts at the company." Sample phrase: "Is my team on the layoff list?"
W: A=Denied topic: it blocks a business subject described in natural language, whatever words the user chooses, in both prompts and responses.
C=Sensitive information filter for SSNs: the built-in US SSN type detects the numbers in responses and masks or blocks them before they reach the user.
X: B=Contextual grounding check: it blocks unsupported or irrelevant answers; an answer about layoffs that is supported by an HR document would pass, so the topic is not refused.
D=Prompt attack filter: it detects jailbreaks and injected instructions, not ordinary questions about a sensitive subject or data type.
E=Misconduct content filter: it targets content about criminal or harmful activity; questions about layoffs or ID numbers are not misconduct, so they would not be caught reliably.
T: Use denied topics for subjects the assistant must refuse and sensitive information filters (block or mask) for identifiers such as SSNs.

@ MLA-C02 D4 T4.3 applied comparison
S: A developer created a long-term Amazon Bedrock API key while trying out models and now wants to put the same key into the environment variables of a production Lambda function that calls the Converse API. What should the ML engineer recommend?
A: Keep the long-term API key but store it in AWS Secrets Manager, because a key read from a secret at run time is the AWS recommended credential for production workloads
B: Generate a short-term API key once during deployment and place it in the environment variables, because short-term keys never expire while the function is unchanged
C: Grant Bedrock permissions to the function's execution role and call with the SDK, so it uses temporary credentials, and keep API keys for exploration only
D: Create an IAM user with an access key for the function, because an access key that is rotated every 90 days is safer than any role for production Bedrock calls
K: C
G: ## Bedrock API keys
Amazon Bedrock API keys let a caller authenticate with a bearer token instead of signing requests with AWS credentials. They make quick experiments easy. There are two kinds:
- **Short-term keys**: generated from existing credentials, valid for a limited time (up to 12 hours, or less if the session ends sooner) and limited to the permissions of the identity that created them.
- **Long-term keys**: tied to an IAM user as a service-specific credential, with an expiry you choose. Anyone who obtains the key can use it until it expires or is revoked.

A Lambda function already has an **execution role**. The SDK picks up its temporary credentials automatically, they rotate without any code, and permissions can be scoped to `bedrock:InvokeModel` on specific model or inference profile ARNs. No secret is stored anywhere.

B=Short-term key in environment variables: short-term keys expire after hours at most, so the function would start failing, and the token still sits in plain configuration.
D=IAM user access key: long-term access keys are exactly what roles replace; rotation reduces but does not remove the risk of a leaked static credential.
T: In production, call Bedrock with an IAM role's temporary credentials; keep Bedrock API keys (prefer short-term) for exploration.

D=VPC peering to Bedrock: AWS services are not peered into customer VPCs; private connectivity to Bedrock is provided through PrivateLink interface endpoints.

G: ## Why prompt injection is hard to stop at the prompt
Prompt injection hides instructions in content the model reads: an email, a web page, a retrieved document. The model cannot reliably tell "data to process" from "instructions to follow". C=KMS encryption of emails: encryption protects data at rest; the agent must decrypt the text to read it, so the model still sees the injected instructions.
E=Invocation logging: logs record what happened for later review; they do not inspect or block anything before the tool runs.
T: Assume prompt injection will sometimes succeed: limit tool permissions and parameters, and require human approval for high-impact actions.
