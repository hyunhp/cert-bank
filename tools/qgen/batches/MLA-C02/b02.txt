# MLA-C02 D2 generative-AI additions: modeling approach (T2.1), FM customization (T2.2), FM/RAG/agent evaluation (T2.3)

@ MLA-C02 D2 T2.1 applied tradeoff
S: A manufacturer has five years of labeled sensor readings (about 40 numeric features per row) and wants to predict pump failures. Predictions run on millions of rows per hour and must cost very little per prediction and return in milliseconds. A stakeholder suggests sending each row to a large language model on Amazon Bedrock. What should the ML engineer recommend?
A: Train a gradient-boosted tree model such as XGBoost on the labeled tabular data with SageMaker AI and serve it from an endpoint or batch job
B: Send each row to a Bedrock text model with a few-shot prompt that lists example rows and their failure labels before the new row
C: Fine-tune a Bedrock text model on the five years of rows serialized as prompt and completion pairs so it learns the failure labels
D: Store the historical rows in a Bedrock knowledge base and have a model retrieve similar past rows before it predicts a failure label
K: A
G: ## Foundation model or custom model?
A foundation model (FM) is a large model pre-trained on broad data, mostly text, images or code. It shines when the task is open-ended language or vision work and labeled data is scarce.
A **custom model** (for example XGBoost, a linear model or a small neural network) is trained from scratch on your own labeled data for one narrow prediction.
## Signals that point to a custom model
- The data is **structured and numeric** (tabular rows), not natural language.
- There is plenty of **labeled history** for exactly the target you want to predict.
- The workload needs **very high volume, millisecond latency and a tiny cost per prediction**.
An LLM would have to read each row as text tokens and generate a label; that costs orders of magnitude more per prediction and is slower, and LLMs are not designed for precise numeric pattern learning over 40 features.
Example: a SageMaker AI built-in XGBoost model on a small CPU instance can score thousands of rows per second, at a tiny fraction of the cost of sending each row to an LLM as tokens.
W: XGBoost on SageMaker AI: tabular, labeled, high-volume, latency-sensitive prediction is the classic case for a purpose-built supervised model, which is cheaper, faster and usually more accurate here than any FM.
X: B=Few-shot prompting a Bedrock model: every prediction pays for the example rows plus the new row as input tokens, latency is far above milliseconds, and a handful of examples cannot capture five years of failure patterns.
C=Fine-tuning a Bedrock text model on serialized rows: this spends GPU training on a model built for language, still leaves per-token inference cost and latency at millions of rows per hour, and gains nothing over a tree model on numeric features.
D=Knowledge base of historical rows: retrieval-augmented generation adds documents as context for text answers; nearest-row lookup plus an LLM is a slow, costly and unreliable replacement for a trained classifier.
T: Labeled tabular data with high-volume, low-latency, low-cost needs points to a custom supervised model, not a foundation model.
V: Amazon SageMaker AI, Amazon Bedrock

@ MLA-C02 D2 T2.1 applied comparison
S: An ML team wants to fine-tune an open-weight text model with its own training script and then host it in its own account on a GPU instance type it chooses, with control over the inference container and auto scaling settings. Which service fits these requirements?
A: Amazon Bedrock, invoking the open-weight model on demand through the Converse API and paying only per input and output token
B: Amazon SageMaker JumpStart, deploying the open-weight model to a SageMaker AI endpoint on an instance type that the team selects
C: Amazon Bedrock Provisioned Throughput, buying model units for the base model so that capacity is reserved for the team's traffic
D: Amazon Bedrock Knowledge Bases, attaching the open-weight model as the generator so that it can be served without infrastructure
K: B
G: ## Two ways to get a foundation model on AWS
- **Amazon Bedrock** is a fully managed, serverless API. You pick a model by ID and pay per token (or buy Provisioned Throughput). You never see instances, containers or weights, and customization is limited to the job types Bedrock offers with the hyperparameters it exposes.
- **Amazon SageMaker JumpStart** is a model hub inside SageMaker AI. A model from it is deployed to a **SageMaker AI endpoint in your account**: you choose the instance type (for example a GPU instance), the container, the scaling policy and the VPC, and you can fine-tune it with JumpStart's training recipes or with your own script in a SageMaker AI training job.
## How to choose
- Want no infrastructure and pay-per-use access to many models → Bedrock.
- Want control over hardware, container, training code or scaling → JumpStart and SageMaker AI.
Example: a team that must run a model on a specific GPU instance inside a private subnet with a custom inference handler picks JumpStart.
W: SageMaker JumpStart: JumpStart deploys the model to a SageMaker AI endpoint where the team chooses instance type, container and scaling, and its models can be fine-tuned with SageMaker training jobs and custom scripts.
X: A=Bedrock on-demand invocation: on-demand Bedrock is serverless; the team cannot choose instances, change the inference container or tune scaling, which are explicit requirements.
C=Bedrock Provisioned Throughput: model units reserve throughput for a Bedrock model but still hide instances and containers, and they do not let the team run its own training script.
D=Bedrock Knowledge Bases: a knowledge base adds retrieval to a Bedrock model; it is not a hosting option and gives no control over hardware or containers.
T: Need control of instances, containers, scaling or training code → SageMaker JumpStart on SageMaker AI; want a managed per-token API → Amazon Bedrock.
V: Amazon SageMaker JumpStart, Amazon Bedrock

@ MLA-C02 D2 T2.1 applied use-case
S: A legal team wants to send scanned contract pages (images) together with typed questions to a model and get answers in one request. Some contracts are several hundred pages long and must be analyzed in a single pass. Which criteria should drive the choice of foundation model on Amazon Bedrock?
A: Pick the model with the highest parameter count in the catalog, since larger models always accept every input type and any document size
B: Pick the cheapest text-only model per input token and send each page as extracted text in a separate request to keep the cost lowest
C: Pick an embedding model with the largest vector dimension, since it can encode the entire contract and the question into one vector
D: Pick a model whose supported input modalities include images and text and whose context window fits the full contract and the question
K: D
G: ## Selection criteria for foundation models
When choosing a model on Amazon Bedrock or SageMaker JumpStart, compare the models against the workload:
- **Modality**: which input types (text, image, document, video, audio) and output types the model supports. A text-only model cannot read a scanned page image.
- **Context window**: the maximum number of tokens (input plus output) the model can handle in one request. A long document analyzed in one pass needs a window big enough for all of it.
- **Latency and throughput**: smaller models usually respond faster.
- **Cost**: price per input and output token, or per hour for hosted models.
- **Customization support**: whether the model can be fine-tuned, continued-pre-trained or distilled.
The model catalog and model cards list modality and context length for each model.
Example: "images + text in, long documents, single pass" narrows the list to multimodal models with long context windows; cost and latency then decide among them.
W: Modalities and context window: the requirements are image plus text input and very long documents in one request, so the model must accept both modalities and have a context window large enough for the full contract.
X: A=Highest parameter count: size does not determine which input types or how many tokens a model accepts; many large models are text-only or have modest context windows.
B=Cheapest text-only model per page: a text-only model cannot read the scanned images, and splitting the contract into page-by-page requests breaks the single-pass analysis across the whole document.
C=Largest embedding model: embedding models turn input into vectors for search; they do not generate answers, and vector dimension says nothing about how much text they can take in.
T: Match the model's supported modalities and context window to the input first; then trade off latency and cost among the models that qualify.
V: Amazon Bedrock

@ MLA-C02 D2 T2.1 advanced tradeoff
S: A company is building an internal assistant on Amazon Bedrock. Answers must come from about 20,000 HR policy documents that are updated every week and must cite the source document. Answers must also follow a fixed three-part layout and a formal tone. Which TWO approaches meet these requirements with the least effort? (Select TWO)
A: Use retrieval-augmented generation with a Bedrock knowledge base over the policy documents so answers use current text and return citations
B: Run a continued pre-training job every week on the updated policy documents so the model learns the latest wording of every policy
C: Use prompt engineering with a system prompt and a few examples that show the three-part layout and the required formal tone
D: Fine-tune a model on question and answer pairs generated from the policies so it answers policy questions without any retrieval
E: Raise the temperature and the maximum output tokens so the model writes longer, more complete answers that cover each policy
K: A,C
G: ## Four ways to adapt a foundation model, from lightest to heaviest
- **Prompt engineering**: instructions, a system prompt and few-shot examples. No training, changes take effect instantly. Good for format, tone and task framing.
- **Retrieval-augmented generation (RAG)**: at query time, search a document store and put the relevant passages in the prompt. Best for knowledge that changes often or must be cited, because updating the documents updates the answers.
- **Fine-tuning**: train the model further on labeled prompt/response pairs. Good for teaching a consistent behavior, style or narrow task that prompting cannot reach. Knowledge baked in this way goes stale and cannot be cited.
- **Continued pre-training**: train on large amounts of unlabeled domain text so the model learns vocabulary and domain knowledge. The heaviest option.
## Rules of thumb
- Facts that change, or answers that need sources → RAG.
- Output shape and tone → prompt engineering first; fine-tune only if prompting cannot get there.
Example: after each weekly update, a sync (ingestion job) of the Amazon Bedrock knowledge base re-indexes the documents from S3, and RetrieveAndGenerate returns citations with each generated answer.
W: A=RAG with a knowledge base: retrieval pulls the current policy text at question time, so weekly updates only need a data source sync, and the response includes citations to the source documents.
C=Prompt engineering: a system prompt with the layout and a few examples controls structure and tone with no training at all, the lowest-effort way to shape output.
X: B=Weekly continued pre-training: retraining every week is costly and slow, the model can still mix old and new wording, and a trained model cannot cite which document a statement came from.
D=Fine-tuning on generated Q&A pairs: knowledge baked into weights goes stale after the next weekly update and cannot produce citations, so the requirements for currency and sources fail.
E=Higher temperature and more tokens: temperature adds randomness and maximum tokens limits length; neither supplies current policy facts, citations or a fixed layout.
T: Changing facts with citations → RAG; layout and tone → prompt engineering; reach for fine-tuning or continued pre-training only when these are not enough.
V: Amazon Bedrock, Amazon Bedrock Knowledge Bases

@ MLA-C02 D2 T2.1 applied comparison
S: A specialty chemicals company finds that a Bedrock model misreads its internal product codes and process jargon. The company has several gigabytes of unlabeled internal technical reports but almost no labeled question and answer pairs. It wants the model itself to understand this vocabulary. Which customization approach fits best?
A: Fine-tuning, supplying the technical reports as prompt and completion pairs so the model learns each product code as a labeled answer
B: Model distillation, using a larger teacher model to label the reports so that a smaller student model learns the company vocabulary
C: Continued pre-training on Amazon Bedrock, supplying the unlabeled technical reports so the model adapts to the company's domain language
D: Prompt caching on Amazon Bedrock, storing the technical reports as a cached prompt prefix so that every request includes the full vocabulary
K: C
G: ## Fine-tuning versus continued pre-training
Both are model customization jobs in Amazon Bedrock, and both produce a custom model, but they learn from different data:
- **Fine-tuning** is supervised. Each training record is a labeled pair: an input (prompt) and the desired output (completion or assistant reply). It teaches the model how to respond to a kind of task.
- **Continued pre-training** is unsupervised (self-supervised). Each record is plain domain text. The model keeps doing what it did in pre-training, predicting the next token, but on your corpus, so it absorbs your terminology and domain knowledge.
## Picking one
- Lots of raw domain text, few labels, model "does not speak our language" → continued pre-training.
- Good labeled examples of the exact task → fine-tuning.
- A common path is both: continued pre-training for vocabulary, then fine-tuning for the task.
Example: a continued pre-training record in Bedrock is a JSON line such as `{"input": "Reactor R-12 uses catalyst CX-4 at ..."}`.
W: Continued pre-training: it learns from unlabeled domain text, which is exactly what the company has, and adapts the model to the company's product codes and jargon.
X: A=Fine-tuning with reports as pairs: fine-tuning needs meaningful input and output pairs; raw reports are not labeled examples, and inventing pairs from them is effort the company wants to avoid.
B=Model distillation: distillation transfers a large model's behavior on a set of prompts to a smaller model; the teacher does not know the company jargon either, so the student cannot learn it.
D=Prompt caching of the reports: caching reuses a repeated prompt prefix to cut cost and latency, but gigabytes of reports do not fit in any context window and caching does not change the model itself.
T: Unlabeled domain text to teach vocabulary → continued pre-training; labeled input/output pairs to teach a task → fine-tuning.
V: Amazon Bedrock

@ MLA-C02 D2 T2.1 advanced use-case
S: A support chatbot uses a large, high-quality model on Amazon Bedrock. Its answers are good, but cost and latency are now too high at production volume. Prompts are short and varied, and Bedrock model invocation logging has stored months of production prompts. The team wants a smaller, faster model that keeps most of the large model's quality for this use case. What should the ML engineer do?
A: Buy Provisioned Throughput model units for the large model so that every request gets reserved capacity and the per-request cost drops
B: Enable prompt caching on the large model so that repeated prompt prefixes are reused across requests and the generation step runs faster
C: Fine-tune the smaller model on a new dataset of answers written by the support agents, labeling thousands of prompts by hand first
D: Create a Bedrock model distillation job with the large model as teacher, a smaller model as student, and the logged prompts as input
K: D
G: ## What model distillation does
Model distillation trains a smaller **student** model to imitate a larger **teacher** model on your use case.
In **Amazon Bedrock Model Distillation**:
- You choose a teacher model and a smaller student model that Bedrock supports for distillation (typically from the same model family).
- You supply prompts, either as a dataset in S3 or by pointing to your **model invocation logs**.
- Bedrock has the teacher generate responses (synthetic data generation), then fine-tunes the student on them.
- The result is a custom model that is faster and cheaper to run, and that keeps much of the teacher's quality for this specific task.
## When it fits
- A big model already gives the right answers, but cost and latency are too high.
- You have representative production prompts and little or no labeled data.
Example: months of logged support prompts become the training input, so the student learns how the teacher answers real customer questions.
W: Bedrock model distillation: the teacher labels the logged production prompts, and the student learns to reproduce those answers, giving a smaller, faster, cheaper model with no manual labeling.
X: A=Provisioned Throughput on the large model: reserved model units guarantee capacity, but they are an hourly commitment that pays off only at steady high use, and the large model generates no faster per token, so the latency problem and the cost of running a large model remain.
B=Prompt caching: caching helps when many requests share a long identical prefix; short, varied prompts gain little, and output generation from the large model stays as slow and costly.
C=Fine-tuning on hand-labeled answers: this can work but needs thousands of human-written answers, which is slow and costly when the large model already produces the desired answers.
T: When a big model's quality is right but its cost or latency is not, distill it into a smaller student model using representative prompts.
V: Amazon Bedrock

@ MLA-C02 D2 T2.1 applied use-case
S: A company wants to route incoming support emails into eight intent categories within two weeks. It has no labeled emails today, the volume is a few thousand emails per day, and the category list may change next quarter. Which modeling approach should the ML engineer start with?
A: Train a custom text classifier with SageMaker AI built-in BlazingText after a labeling team tags enough emails for every one of the categories
B: Use a foundation model on Amazon Bedrock with a prompt that lists the eight categories and gives a short description and example for each
C: Run continued pre-training on the company's archived email text so that the model learns the support vocabulary before classifying any email
D: Train a transformer model from scratch on the archived emails with SageMaker AI distributed training so that it fits the categories exactly
K: B
G: ## Why a foundation model is often the right first step
A custom classifier needs **labeled examples** of each class before it can learn anything. A foundation model already understands language, so it can do **zero-shot or few-shot classification**: you describe the categories in the prompt and it picks one.
## Signals that favor a prompted FM
- No labeled data yet, and a short deadline.
- Moderate volume, where per-request token cost is acceptable.
- Categories that may change: with prompting you edit the prompt; a custom model needs new labels and retraining.
## When to switch later
Once the FM's predictions are reviewed and corrected, they become labeled data. If volume grows a lot or latency must drop, that data can train a small custom classifier or fine-tune a smaller model.
Example: a prompt such as "Classify the email into one of: billing, shipping, returns, ... Reply with the category name only" with one example per category.
W: Prompted foundation model: it needs no labels, can launch in days, handles a few thousand emails a day at modest cost, and new categories only require a prompt change.
X: A=BlazingText after labeling: a supervised classifier needs a labeled dataset first, which the team does not have and cannot build reliably in two weeks for every category.
C=Continued pre-training first: adapting vocabulary with a training job is slow and costly, and the model would still need a prompt or labels to classify, so it adds effort without meeting the deadline.
D=Transformer from scratch: training a language model from scratch needs huge data, compute and time, and with no labels it cannot learn the intent categories at all.
T: No labels, a short deadline and changing classes favor a prompted foundation model; move to a custom model later when labels and volume justify it.
V: Amazon Bedrock, Amazon SageMaker AI

@ MLA-C02 D2 T2.2 applied troubleshooting
S: An ML engineer starts an Amazon Bedrock fine-tuning job using a CSV file in Amazon S3 with two columns, question and answer. The job fails during data validation. What should the engineer change?
A: Convert the CSV file to Apache Parquet with a Snappy codec and register it in the AWS Glue Data Catalog for the customization job to read
B: Convert the data to JSON Lines, one JSON record per line in the prompt and response schema the chosen base model expects, and upload it to S3
C: Split the CSV file into one small text file per question and answer pair and upload all of the text files under a single S3 prefix
D: Keep the CSV file and raise the number of epochs and the batch size so that the job has more passes to parse each training record
K: B
G: ## Training data for Bedrock model customization
Bedrock customization jobs read training (and optional validation) data from Amazon S3 as **JSON Lines** (`.jsonl`): one complete JSON object per line.
The record schema depends on the job type and the base model:
- **Fine-tuning, prompt/completion style**: `{"prompt": "What is our refund window?", "completion": "30 days from delivery."}`
- **Fine-tuning, conversational style** (used by many newer chat models): a record with a `messages` list of user and assistant turns, sometimes with a system prompt.
- **Continued pre-training**: unlabeled text, for example `{"input": "..."}`.
The Bedrock documentation lists the format for each model; records in the wrong shape fail validation before training starts.
## Other job inputs
- An IAM service role that Bedrock assumes to read the data and write outputs.
- An S3 output location for training and validation metrics.
- Hyperparameters such as epochs, batch size and learning rate.
W: JSON Lines in the expected schema: Bedrock customization jobs accept `.jsonl` training files whose records match the base model's format, so converting each question and answer row into such a record fixes the validation failure.
X: A=Parquet in the Glue Data Catalog: Bedrock customization does not read Parquet or Glue tables; it reads JSON Lines files from S3.
C=One text file per pair: many small text files do not provide the required JSON records with prompt and response fields, so validation still fails.
D=More epochs and larger batches: hyperparameters control training once the data is valid; they do not make Bedrock accept a CSV file.
T: Bedrock fine-tuning and continued pre-training read JSON Lines from S3, with the record schema set by the job type and base model.
V: Amazon Bedrock, Amazon S3

@ MLA-C02 D2 T2.2 advanced troubleshooting
S: A team fine-tuned a model with an Amazon Bedrock customization job, and the job completed successfully. The application still calls InvokeModel with the base model's ID, and the responses show none of the fine-tuned behavior. What must the team do to use the custom model?
A: Wait for the custom model to propagate to the base model ID, because Bedrock replaces the base model for the account after each completed job
B: Add the custom model's name to the request body as a model variant field while the application keeps calling the same base model ID as before
C: Give the custom model serving capacity, through an on-demand custom model deployment where supported or Provisioned Throughput, and invoke that ARN
D: Download the custom model weights from the job's S3 output location and load them into the application, which then runs the model locally
K: C
G: ## A custom model is a separate resource
A Bedrock customization job (fine-tuning, continued pre-training or distillation) creates a **custom model** resource with its own ARN. The base model is never changed: calling the base model ID always returns base model behavior.
## How a custom model gets serving capacity
A newly created custom model cannot just be invoked; you first set up how it is served:
- **On-demand custom model deployment**: for base models that support it, you create a deployment and pay per token without buying capacity.
- **Provisioned Throughput**: you buy model units for the custom model, which reserves dedicated throughput. This has long been the way to serve Bedrock custom models and is still required for those that do not support on-demand deployment.
The application then passes the deployment ARN or the Provisioned Throughput ARN as the `modelId` in InvokeModel or Converse.
## What you never get
Bedrock does not hand you the custom model's weights; the model stays inside Bedrock.
W: Deployment or Provisioned Throughput ARN: the custom model is a separate resource that needs serving capacity, and requests must target the deployment or provisioned throughput ARN, not the base model ID.
X: A=Propagation to the base model ID: Bedrock never overwrites a base model; the base ID keeps serving the original model for every customer, so waiting changes nothing.
B=Model variant field in the body: there is no request-body field that redirects a base model call to a custom model; the model is selected only by the model ID or ARN.
D=Download the weights: Bedrock custom models cannot be downloaded; the output location receives training metrics, not model weights.
T: A Bedrock custom model is invoked through its own on-demand deployment or Provisioned Throughput ARN; the base model ID never serves customized behavior.
V: Amazon Bedrock

@ MLA-C02 D2 T2.2 advanced troubleshooting
S: An ML engineer fine-tunes an open-weight 13-billion-parameter model with a SageMaker AI training job on a single-GPU instance. Full fine-tuning in 16-bit precision fails with CUDA out-of-memory errors before the first step. The budget allows only this instance type. Which change most directly lets the job fit in GPU memory?
A: Use QLoRA, loading the frozen base weights in 4-bit precision and training only small low-rank adapter matrices on top of them
B: Raise the per-device batch size so that each step processes more samples and the GPU memory is used more efficiently per sample
C: Switch the weights from 16-bit to 32-bit floating point so that the optimizer states stay numerically stable during each training step
D: Add data parallel training across several copies of the same instance so that each instance processes a smaller share of the batches
K: A
G: ## Why full fine-tuning runs out of memory
Full fine-tuning updates every weight. GPU memory must hold the weights, their gradients and the optimizer states (Adam keeps two extra values per weight), plus activations. For a 13B model in 16-bit that is roughly 26 GB of weights alone, and several times more with gradients and optimizer states, far beyond a single GPU.
## Parameter-efficient fine-tuning (PEFT)
- **LoRA** (low-rank adaptation) freezes the original weights and adds small trainable low-rank matrices to selected layers. Only those matrices get gradients and optimizer states, often well under 1% of the parameters.
- **QLoRA** adds quantization: the frozen base weights are loaded in **4-bit**, cutting their memory about fourfold versus 16-bit, while the LoRA adapters train in higher precision.
Together they let a 13B model fine-tune on one GPU that could never hold full fine-tuning.
## On AWS
SageMaker AI training jobs (for example with the Hugging Face PEFT library) and many SageMaker JumpStart models support LoRA or QLoRA fine-tuning.
W: QLoRA: quantizing the frozen base model to 4-bit shrinks the largest memory consumer, and training only small adapters removes most gradient and optimizer memory, so the job fits on the single GPU.
X: B=Larger batch size: more samples per step means more activation memory, which makes the out-of-memory error worse, not better.
C=32-bit weights: full precision doubles the memory for weights, gradients and optimizer states compared with 16-bit, so the job needs even more memory.
D=Data parallel copies: plain data parallelism places a full copy of the model and its optimizer states on every GPU, so each instance still runs out of memory, and the budget rules out more instances anyway.
T: When full fine-tuning does not fit in GPU memory, use parameter-efficient fine-tuning: LoRA trains small adapters, and QLoRA also quantizes the frozen base to 4-bit.
V: Amazon SageMaker AI

@ MLA-C02 D2 T2.2 applied definition
S: A company plans to adapt one open-weight model to six business units, each with its own task, using LoRA on SageMaker AI instead of full fine-tuning. Which TWO statements correctly describe the benefits of LoRA in this plan? (Select TWO)
A: LoRA trains only small low-rank matrices while the base weights stay frozen, so training needs far less GPU memory and compute
B: LoRA extends the base model's context window for each business unit so that every adapter can process much longer input prompts
C: Each LoRA adapter is a small artifact, so six adapters can share one copy of the base model instead of storing six full models
D: LoRA updates every weight of the base model at a lower learning rate, so it avoids overfitting while still changing the whole model
E: LoRA removes the need for a validation dataset because the frozen base weights prevent the adapters from overfitting the training set
K: A,C
G: ## How LoRA works
Low-rank adaptation (LoRA) keeps the pre-trained weight matrix `W` frozen and learns a small update `ΔW = B × A`, where `A` and `B` are thin matrices of a low rank `r` (for example 8 or 16). Only `A` and `B` are trained.
## What this buys you
- **Less compute and memory**: gradients and optimizer states exist only for the adapter matrices, a tiny fraction of the model.
- **Small artifacts**: an adapter is typically megabytes to a few hundred megabytes, while the base model is many gigabytes.
- **Many tasks, one base**: several adapters can be stored and served on top of one shared base model, swapping or loading adapters per task. SageMaker AI inference components, for example, can host LoRA adapters on a shared base model.
## What it does not change
- The base model's architecture and context window stay the same.
- You still need validation data to catch overfitting and pick hyperparameters such as rank, learning rate and epochs.
W: A=Frozen base, small trainable matrices: only the low-rank adapters receive gradients and optimizer states, so memory and compute drop sharply compared with full fine-tuning.
C=Small adapters on a shared base: each business unit gets a compact adapter, and all six can run on top of one copy of the base model rather than six full model copies.
X: B=Longer context window: LoRA does not change the architecture or positional limits, so the context window stays exactly as the base model defines it.
D=All weights at a lower learning rate: that describes full fine-tuning with a cautious learning rate; LoRA leaves the original weights untouched.
E=No validation data needed: adapters can still overfit a small training set, so a validation set is still needed to tune and stop training.
T: LoRA freezes the base model and trains small adapters: cheaper training and small per-task artifacts that share one base model.
V: Amazon SageMaker AI

@ MLA-C02 D2 T2.2 applied troubleshooting
S: An ML engineer uses the SageMaker Python SDK to fine-tune a Meta Llama model from SageMaker JumpStart on an instruction dataset in Amazon S3. The training job fails right away with an error saying the end-user license agreement was not accepted. What should the engineer do?

Some JumpStart models, such as Meta Llama models, are **gated**: their license requires each user to accept an end-user license agreement (EULA) before training or deploying.

W: Accept the EULA: gated JumpStart models require explicit license acceptance in the fine-tuning or deployment request, and the error says exactly that it is missing.
X: A=Service quota increase: a quota problem returns a resource limit error when the job requests instances, not a license error.
B=AWS Marketplace subscription and role tag: JumpStart's gated open-weight models use EULA acceptance in the request, not a Marketplace subscription attached to the role.
C=Copying the weights: copying the artifacts does not change the license terms, and JumpStart fine-tuning is meant to use its managed model artifacts with the acceptance flag.

@ MLA-C02 D2 T2.2 applied troubleshooting
S: An Amazon Bedrock fine-tuning job fails with an access denied error when reading its training data. The data sits in an S3 bucket encrypted with a customer managed AWS KMS key. The service role passed to the job has s3:GetObject and s3:ListBucket on the bucket. What is the most likely fix?
A: Attach the S3 read permissions to the IAM role of the engineer who starts the job, because Bedrock reads training data with the caller's credentials
B: Allow the job's service role to use the KMS key, for example kms:Decrypt, in the key policy or in the role's policy where the key policy permits it
C: Create an S3 gateway VPC endpoint in the account's default VPC so that the customization job can reach the training bucket over a private network
D: Turn off default encryption on the bucket and copy the training data again so that the job can read the objects without any KMS permission check
K: B
G: ## How a Bedrock customization job reads data
A model customization job runs as the **service role** you pass to it. Bedrock assumes that role (its trust policy names `bedrock.amazonaws.com`) to:
- read training and validation data from S3,
- write output metrics to S3,
- use KMS keys if the data or the output is encrypted with a customer managed key.
## Why KMS matters
An object encrypted with a customer managed key (SSE-KMS) can only be read by a principal that has S3 read permission **and** permission to use the key (`kms:Decrypt`). The key policy controls who may use the key; a key policy that does not allow the role (directly, or by delegating to IAM policies) blocks access even when the S3 permissions are correct.
Example: add a key policy statement that allows the job's service role `kms:Decrypt` on the key, or delegate to IAM and add it to the role's policy.
W: KMS key permission for the service role: the role can list and get the objects, but SSE-KMS objects also need key usage permission, so granting the role `kms:Decrypt` on the customer managed key removes the access denied error.
X: A=Permissions on the engineer's role: the job reads data as the service role it was given, not with the caller's credentials, so changing the engineer's role does not help.
C=S3 gateway endpoint: a VPC endpoint gives a private network path; the error is an authorization failure, and the job does not even need a VPC to reach S3 by default.
D=Turning off encryption: this weakens a security control the company chose, and it is unnecessary when one missing key permission is the real cause.
T: Bedrock customization jobs act through their service role, which needs S3 access and, for SSE-KMS data, permission to use the KMS key.

@ MLA-C02 D2 T2.3 advanced troubleshooting
S: A team runs an Amazon Bedrock retrieve-and-generate evaluation on its knowledge base. Context relevance scores are high, but faithfulness scores are low: answers often contain details that do not appear in the retrieved passages. Where is the problem, and what should the team adjust first?
A: In the retrieval step: change the chunking strategy and embeddings model so that the knowledge base returns more relevant passages
B: In the data source: sync the knowledge base again because the vector index is likely missing the most recently uploaded documents
C: In the evaluation itself: switch to a larger evaluator model, because a low faithfulness score means the judge cannot read the passages

G: ## RAG has two stages, so measure both
A retrieval-augmented generation (RAG) system first **retrieves** passages, then **generates** an answer from them. Amazon Bedrock RAG evaluations (for Knowledge Bases) can score each stage:
- **Retrieve-only metrics**: *context relevance* (are the retrieved passages relevant to the question?) and *context coverage* (do they contain the information the reference answer needs?).
- **Retrieve-and-generate metrics**: for example *correctness*, *completeness*, *helpfulness* and *faithfulness*.
## What faithfulness means
**Faithfulness** (also called groundedness) checks whether the answer's claims are supported by the retrieved context. Low faithfulness means the model is adding information from its own training or inventing it, which is hallucination relative to the sources.
## Reading the pattern
- Low context relevance → fix retrieval (chunking, embeddings, metadata filters, number of results).
- High context relevance, low faithfulness → retrieval is fine; fix generation (prompt instructions, model choice, a guardrail contextual grounding check).

B=Re-sync the data source: a missing document would show up as low context relevance or coverage, not as answers that add facts absent from relevant passages.
C=Larger evaluator model: nothing suggests the judge is failing; low faithfulness with high relevance is a consistent pattern pointing at the generator.
T: High context relevance with low faithfulness means retrieval works and the generator is not grounded: fix the prompt, model or grounding checks, not the retriever.

@ MLA-C02 D2 T2.3 applied definition

A: ROUGE, which counts overlapping words and n-grams between the generated summary and the reference summary

G: ## Reference-based text metrics
When you have human-written reference outputs, you can score a generated text by comparing it with the reference:
- **ROUGE** (Recall-Oriented Understudy for Gisting Evaluation) counts overlapping units. ROUGE-1 uses single words, ROUGE-2 uses word pairs, ROUGE-L uses the longest common subsequence. It is the classic summarization metric, but it gives no credit for synonyms or paraphrases.
- **BLEU** is a similar n-gram overlap metric, precision-oriented and common for translation.
- **BERTScore** embeds every token of both texts with a BERT-style model and matches tokens by cosine similarity. "The car was fast" and "The vehicle was quick" score well even with little word overlap.
## On AWS
SageMaker Clarify foundation model evaluations report ROUGE, METEOR and BERTScore for summarization accuracy, and Bedrock automatic evaluations use similar algorithmic metrics.

X: B=RMSE: it is a regression metric for numeric predictions and cannot compare two pieces of text.
D=AUC-ROC: it evaluates how a binary classifier ranks scores, not the similarity of a generated summary to a reference.
E=Perplexity: it reflects how predictable a text is to a language model and uses no reference summary, so it cannot measure overlap or meaning match.
T: Compare generated text with a reference using ROUGE (or BLEU) for word overlap and BERTScore for semantic similarity.

S: An agent built on Amazon Bedrock AgentCore handles warranty claims by calling tools to check orders, verify warranties, and issue replacements. G: ## Why agents need more than answer scoring

- **Task completion**: did the agent achieve the goal?

## How to build it
- Keep a fixed **test set** of scenarios with the expected tool sequence or required checks for each.
- Capture **traces** of every run (AgentCore Observability emits OpenTelemetry-compatible traces and spans for tool calls).
- Compare the traces with the expectations in code, and optionally add an LLM-as-a-judge score for the final answer.
Run it before and after every prompt, model or tool change.
W: Trace-based trajectory tests: comparing the traced tool calls and arguments with the expected sequence for each fixed test case directly catches a replacement issued before a warranty check, whatever the final message says.
X: A=ROUGE on the final message: a polite final reply can match the reference closely even when a required tool call was skipped, so overlap scoring misses the failure.
B=Customer thumbs ratings after release: this is not a pre-change regression test, customers cannot see skipped internal steps, and the damage is done before ratings fall.
D=Temperature zero: lower temperature reduces randomness but does not prove the tool sequence is correct; a deterministic agent can still skip the warranty check every time.
T: Evaluate agents on their trajectory (tool calls, order and arguments from traces) against a fixed test set, not only on the final answer.
