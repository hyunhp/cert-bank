@ MLA-C02 D3 T3.3 applied use-case
S: Several teams upload policy documents during the day to an S3 bucket that backs a Bedrock knowledge base. The ML engineer must refresh the knowledge base every night after the upload window closes, then run a retrieval quality check and alert on failure. Which design fits best?
A: An S3 event notification invokes a Lambda function for each uploaded object, and each invocation calls StartIngestionJob and runs the quality check right after the call returns.
B: An EventBridge Scheduler schedule starts a Step Functions workflow that calls StartIngestionJob, polls GetIngestionJob in a Wait and Choice loop until it completes, then runs the check.
C: A SageMaker AI Processing job re-embeds the documents each night and writes the resulting vectors into the knowledge base's S3 data source bucket, then runs the quality check.
D: A nightly schedule redeploys the CloudFormation stack of the knowledge base, on the assumption that updating the AWS::Bedrock::DataSource resource re-embeds the bucket's documents.
K: B
G: ## Keeping a knowledge base in step with its documents
A Bedrock knowledge base does not watch its S3 data source. New, changed or deleted documents are picked up by an **ingestion job** (`StartIngestionJob`), which processes the changes and updates the vector store. The job runs asynchronously: the call returns a job ID, and `GetIngestionJob` reports `STARTING`, `IN_PROGRESS`, `COMPLETE` or `FAILED`.
## Orchestrating the nightly refresh
- **Trigger**: an EventBridge Scheduler schedule at a fixed time after the upload window (a cron expression in the right time zone).
- **Workflow**: a Step Functions state machine calls `StartIngestionJob` through the AWS SDK integration, then loops: Wait 60 seconds, `GetIngestionJob`, Choice on the status.
- **Check and alert**: when the status is `COMPLETE`, a task runs a set of test questions with `Retrieve` and compares results with expected sources; a `FAILED` status or a failed check publishes to Amazon SNS.
W: Scheduled Step Functions workflow: it starts one sync after the uploads finish, waits for the asynchronous ingestion job to reach `COMPLETE`, and only then runs the quality check and alerts, with managed retries and a visible execution history.
X: A=Lambda per uploaded object: hundreds of uploads would start hundreds of overlapping sync attempts during the day, and the check runs as soon as the start call returns, long before the ingestion job has finished.
C=Processing job writing vectors: the data source bucket holds source documents, not vectors. Vectors written there would be treated as new documents, and the knowledge base's own ingestion job still does not run.
D=Nightly stack redeploy: an unchanged stack update changes nothing, and updating a data source resource changes its configuration only. CloudFormation does not start an ingestion job, so no document is re-embedded.
T: Refresh a knowledge base on a schedule with an orchestrated StartIngestionJob that waits for completion before the quality checks run.
V: Amazon Bedrock, AWS Step Functions, Amazon EventBridge

@ MLA-C02 D4 T4.2 applied comparison
S: A team is comparing on-demand inference and Provisioned Throughput for a new Amazon Bedrock workload and asks the ML engineer to confirm how each is billed. Which TWO statements are correct? (Select TWO)
A: Provisioned Throughput is free for the first model unit, and each additional model unit beyond the first one is charged per hour of usage
B: Provisioned Throughput bills per token like on-demand, but at a lower rate per token, and it scales its model units down to zero at night
C: On-demand inference requires a one-month or six-month commitment, which in return reserves capacity so that busy-hour requests are not throttled
D: On-demand inference is billed for the input and output tokens that each request processes, with no capacity commitment and no charge while idle
E: Provisioned Throughput is billed for each model unit per hour for the whole term, whether or not the workload sends any requests during that time
K: D,E
G: ## Two ways to pay for a Bedrock model
- **On-demand**: pay per use. Text models are billed per input token and per output token (output tokens usually cost more). Nothing is charged when no requests arrive. Throughput is shared and limited by account quotas, so peaks can be throttled.
- **Provisioned Throughput**: buy a number of **model units**, each giving a fixed amount of throughput for one model. It is billed **per model unit per hour**, with no commitment or with a 1-month or 6-month commitment that lowers the hourly rate. The charge runs for as long as the capacity exists, used or not.
## How to choose
- Spiky, low or unpredictable traffic: on-demand, because idle time costs nothing.
- Steady, high, predictable traffic that needs guaranteed throughput: Provisioned Throughput, sized so that the units are well used.
## Example
A chatbot busy only during office hours, using 10 percent of a model unit on average, would pay for 24 hours of capacity every day with Provisioned Throughput; on-demand charges only for the tokens it actually uses.
W: D=Per-token on-demand: on-demand charges for the input and output tokens processed, with no commitment, so idle periods cost nothing.
E=Hourly model units: Provisioned Throughput reserves capacity, so the bill is per model unit per hour for as long as the units exist, regardless of usage.
X: A=Free first model unit: there is no free model unit; each unit of Provisioned Throughput is billed per hour.
B=Per-token Provisioned Throughput that scales to zero: Provisioned Throughput is not billed per token and does not scale its units down by itself; the units are charged while they exist.
C=Commitment for on-demand: the 1-month and 6-month terms belong to Provisioned Throughput; on-demand has no term and stays subject to account quotas and throttling.
T: On-demand bills tokens with no commitment; Provisioned Throughput bills model units per hour for the term, used or not.
