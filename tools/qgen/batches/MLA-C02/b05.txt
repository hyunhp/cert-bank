@ MLA-C02 D1 T1.1 advanced use-case
S: A payments company serves a fraud model that reads 30 features per request from SageMaker Feature Store and wants the lowest online read latency it can get. The same feature group must keep full history in the offline store for monthly retraining, and the security team requires every store that holds card features to be encrypted with a customer managed AWS KMS key. Which online store configuration meets ALL of these requirements?
A: Create the feature group with the InMemory online tier, enable the offline store, and set the customer managed KMS key in both the online and offline store configurations
B: Create the feature group with the Standard online tier plus the offline store, encrypt both with the customer managed key, and read through a PrivateLink endpoint
C: Create an InMemory online-only feature group for serving, then copy each record to S3 with a nightly AWS Glue job that encrypts the copy with the managed key
D: Create a Standard online-only feature group, then rebuild the training history each month by replaying the raw event stream through a SageMaker Processing job
K: B
G: ## Online store storage types
A Feature Store online store comes in three storage types:
- `Standard` (default): a managed low-latency store.
- `Standard_V2`: like Standard, plus partial updates with `UpdateRecord`.
- `InMemory`: powered by Amazon ElastiCache (Redis OSS) for very low-latency, high-throughput reads.
## The limits of the InMemory tier
The docs list two limits that matter here:
- InMemory supports **online-only** feature groups, so there is no replication to an offline store.
- InMemory does **not** support customer managed KMS keys.
## Cutting network latency instead
Much of the read latency is the network path. An interface VPC endpoint (PrivateLink) for `com.amazonaws.region.sagemaker.featurestore-runtime` with private DNS keeps calls inside the VPC and shortens that path, without giving up the offline store or the key requirement.
W: Standard tier with offline store and PrivateLink: Standard supports online plus offline stores with a customer managed key, and the PrivateLink endpoint lowers network latency, so every constraint holds.
X: A=InMemory with offline store and CMK: the InMemory tier supports neither an offline store nor customer managed keys, so this configuration cannot be created as described.
C=InMemory plus nightly Glue copy: the online store itself would not use the customer managed key, and the extra Glue copy is not Feature Store history with event times.
D=Online-only Standard plus replay: there is no offline store in the feature group, which breaks the stated requirement and adds a costly monthly rebuild job.
T: The Feature Store InMemory tier is online-only and has no customer managed key support; when you need offline history or a CMK, use Standard and reduce network latency with PrivateLink.
V: Amazon SageMaker Feature Store, AWS KMS, AWS PrivateLink

@ MLA-C02 D1 T1.1 advanced troubleshooting
S: A recommendation service keeps session features in a Feature Store online-only feature group. Two weeks ago an engineer called UpdateFeatureGroup to set a TtlDuration of 2 hours so stale sessions disappear. New sessions now expire as expected, but GetRecord still returns millions of sessions written before the change, and the online store keeps growing. The team must remove the old sessions without recreating the feature group. What should the ML engineer do?
A: Wait a few more days, because TTL runs as a background process that can take several days to delete records that were written before the setting was applied
B: Call UpdateFeatureGroup again with a shorter TtlDuration, because a new group-level value is applied retroactively to every record already in the online store
C: Remove the old sessions with DeleteRecord in hard delete mode, or rewrite them with PutRecord carrying a record-level TtlDuration so that each one expires
D: Enable an offline store on the feature group so that the online store moves records older than the TtlDuration to Amazon S3 and then deletes them automatically
K: C
G: ## How Feature Store TTL works
`TtlDuration` hard deletes a record from the online store when `EventTime + TtlDuration` is reached (`ExpiresAt`). It can be set:
- at the **feature group level** with `CreateFeatureGroup` or `UpdateFeatureGroup`, as the default for records added afterwards;
- at the **record level** with `PutRecord`, overriding the group default for that record.
## The trap: no retroactive TTL
When the group default is set with `UpdateFeatureGroup`, it does **not** become the TTL of records created before the call. Those records have no `ExpiresAt` and stay until they are overwritten or deleted.
## Cleaning up
For the old records, either delete them with `DeleteRecord` (hard delete removes them from the online store) or write them again with a record-level `TtlDuration` so the normal expiry applies. TTL deletion itself is a background process that can take a few days, but only for records that actually have an expiry.
W: DeleteRecord or rewrite with record-level TTL: the old records never received an expiry, so they must be deleted explicitly or rewritten with their own TtlDuration.
X: A=Wait for background TTL: the delay of a few days applies to expired records; records written before the update have no ExpiresAt, so waiting never removes them.
B=Shorter group-level TTL: a group-level value set by UpdateFeatureGroup only becomes the default for records added after the call, never for existing ones.
D=Enable offline store: TTL hard deletes are added to the offline store, but an offline store does not give old records an expiry or delete anything from the online store.
T: A feature group TTL set later applies only to new records; old online records need DeleteRecord or a rewrite with a record-level TtlDuration.
V: Amazon SageMaker Feature Store

@ MLA-C02 D1 T1.2 advanced use-case
S: A data science team computes 90-day aggregate features, such as average transaction value per customer, from Parquet files in Amazon S3 with PySpark and writes them to an existing feature group. Today an engineer runs the notebook by hand each night. The team wants a scheduled, repeatable job with lineage that traces features back to their source data, and it does not want to run Spark clusters or write ingestion code. Which approach has the LEAST operational overhead?
A: Run the PySpark code on a long-running Amazon EMR cluster with a cron step, and write each output row to the feature group with PutRecord calls from the Spark executors
B: Wrap the transformation in a Feature Processor definition with the S3 source and the feature group as output, promote it with to_pipeline, and schedule it
C: Convert the notebook to an AWS Glue job that writes rows with the boto3 PutRecord API, and start the job every night with a scheduled AWS Glue trigger
D: Move the logic into an AWS Lambda function that reads the Parquet files with pandas every night and writes the computed aggregates with the PutRecord API
K: B
G: ## Feature Store Feature Processing
Feature Processing gives you a **Feature Processor SDK**: you write a transformation function and declare its **sources** (for example Parquet in S3) and its **sink** (a feature group). Feature Store then provisions the compute and handles ingestion.
- `to_pipeline` promotes the definition into a fully managed SageMaker Pipelines pipeline (an upsert).
- `schedule` runs that pipeline with an EventBridge Scheduler `at`, `rate` or `cron` expression; pipelines can also be chained on events.
- Because it is a pipeline, executions are tracked with SageMaker lineage, so you can trace features back to their data sources.
## Why the alternatives cost more effort
Every other design needs a cluster or a function to operate and custom code that calls `PutRecord` row by row, and none of them records lineage for you.
W: Feature Processor pipeline: Feature Store runs the Spark compute, ingests the results, schedules the pipeline through EventBridge Scheduler and records lineage, so the team writes only the transformation.
X: A=EMR cluster with cron: a long-running cluster must be patched, sized and paid for, and the PutRecord ingestion code is exactly what the team wants to avoid.
C=Glue job with PutRecord: Glue removes cluster management, but the team still writes and maintains row-by-row ingestion code and gets no feature-to-source lineage.
D=Lambda with pandas: a 90-day aggregation over many Parquet files can exceed Lambda's memory and 15-minute limits, and ingestion code is still hand-written.
T: Scheduled batch features into a feature group with lineage and no clusters → a Feature Processor definition promoted with to_pipeline and run with the schedule API.
V: Amazon SageMaker Feature Store, Amazon SageMaker Pipelines, Amazon EventBridge Scheduler

@ MLA-C02 D1 T1.1 advanced use-case
S: A SaaS company streams JSON usage events for 300 tenants through an existing Amazon Data Firehose stream into a single S3 prefix. Each tenant's churn model is retrained weekly on that tenant's data only, and the Athena queries that build each training set scan every tenant's files, which is slow and costly. The company wants files grouped by tenant at delivery time, with no partitioning job after the data lands. Which THREE steps should the ML engineer take? (Select THREE)
A: Create a new Firehose stream with dynamic partitioning enabled and point the producers at it, because the setting cannot be turned on for the existing stream
B: Turn on dynamic partitioning for the existing Firehose stream in place, so that the producers keep writing to the same stream name without any change
C: Use inline parsing with a jq expression that extracts tenant_id from each JSON record as the partitioning key, with no Lambda function to maintain
D: Set the S3 bucket prefix to a hive-style expression such as tenant_id=!{partitionKeyFromQuery:tenant_id}/ so each tenant's records land under their own prefix
E: Keep the single prefix and add Athena partition projection on tenant_id to the Glue table, so that queries skip other tenants' files without moving any of the data
F: Run a nightly AWS Glue job that reads the new objects and rewrites them into one prefix per tenant, then deletes the original unpartitioned objects
K: A,C,D
G: ## Firehose dynamic partitioning
Dynamic partitioning groups records in transit by keys taken from the data (for example `customer_id`) and delivers each group to its own S3 prefix, so Athena scans only the partitions a query needs.
- **Partitioning keys** come from **inline parsing** (a built-in jq 1.6 parser for JSON) or from a Lambda function.
- The **S3 prefix** uses `!{partitionKeyFromQuery:key}` (or `partitionKeyFromLambda`), and can be hive style, for example `tenant_id=!{partitionKeyFromQuery:tenant_id}/`.
## The detail that changes the plan
Dynamic partitioning can be enabled **only when a Firehose stream is created**. It cannot be enabled on an existing stream that was created without it, and once enabled it cannot be disabled. So the producers must move to a new stream.
W: A=New stream with dynamic partitioning: the existing stream cannot gain the feature, so a new stream is required.
C=Inline jq parsing: the tenant ID is a plain JSON field, so the built-in parser extracts it with no function to run.
D=Hive-style prefix with partitionKeyFromQuery: each tenant's records are delivered under their own prefix that Athena can treat as a partition.
X: B=Enable in place: Firehose does not allow dynamic partitioning to be enabled on an existing stream that was created without it.
E=Partition projection only: projection describes partitions that must already exist in the S3 layout; with one flat prefix there is nothing to prune.
F=Nightly Glue rewrite: it works, but it is the post-delivery partitioning job that the company wants to avoid, and it adds cost and delay.
T: Firehose dynamic partitioning (inline jq keys + !{partitionKeyFromQuery:...} prefix) partitions data at delivery, and it can only be enabled when the stream is created.
V: Amazon Data Firehose, Amazon S3, Amazon Athena

@ MLA-C02 D1 T1.2 advanced troubleshooting
S: A SageMaker Processing job tokenizes 24,000 compressed text files, about 50 MB each, under one S3 prefix. To cut the 16-hour runtime, the engineer raised the instance count from 1 to 8. The job now takes about as long, costs eight times as much, and the output contains every tokenized file eight times. The script processes every file it finds in /opt/ml/processing/input. What should the engineer change to get the expected speedup?
A: Set the input's S3InputMode to Pipe so that every instance streams the files from Amazon S3 instead of copying the whole prefix to its local volume first
B: Set the input's S3DataDistributionType to ShardedByS3Key so that each of the 8 instances downloads and processes about 3,000 different files
C: Keep FullyReplicated and change the script to read the host list from the resource config and skip files whose hash does not match its own host index
D: Replace the 8 general purpose instances with one larger instance type that has more vCPUs, because Processing jobs do not split a single input channel
K: B
G: ## How a Processing job hands S3 data to instances
Each `ProcessingS3Input` has an `S3DataDistributionType`:
- `FullyReplicated` (the default behavior people often keep): **every** instance downloads **all** the data from the S3 prefix.
- `ShardedByS3Key`: the objects are split by S3 key, and each instance downloads **one shard**.
## Working the numbers
With 8 instances and `FullyReplicated`, all 8 copy all 24,000 files (about 1.2 TB) and run the same script on them, so each instance does the full 16 hours of work and writes the same outputs. With `ShardedByS3Key`, each instance receives roughly 24,000 / 8 = 3,000 files, so the work, and roughly the runtime, drops to about one eighth.
W: ShardedByS3Key: splitting the input by key gives each instance a different subset of files, which removes the duplicate work and the duplicate outputs.
X: A=Pipe input mode: Pipe changes how data is delivered, not which data each instance gets; with full replication every instance still processes all 24,000 files.
C=FullyReplicated plus host filtering: it can remove duplicate outputs, but each instance still downloads the full 1.2 TB, so time and transfer costs stay high.
D=One larger instance: Processing jobs can split an input channel with ShardedByS3Key; one bigger instance also caps the speedup at what a single machine can do.
T: For parallel Processing over many S3 objects, use ShardedByS3Key; FullyReplicated gives every instance all the data and all the work.
V: Amazon SageMaker Processing, Amazon S3

@ MLA-C02 D1 T1.3 advanced troubleshooting
S: An AWS Glue job builds the daily training table for a demand model and evaluates a Glue Data Quality ruleset with completeness and range rules. Last week an upstream change silently dropped one store region, so the table held 40 percent fewer rows, yet every rule passed and the data quality score stayed at 100 percent. The team wants to catch such unexpected shifts without writing a rule for every possible threshold. What should the ML engineer do?
A: Add RowCount and AllStatistics analyzers for key columns and enable anomaly detection, then review anomaly observations, which do not change the score
B: Add a RowCount rule with a fixed minimum taken from last month's average volume, and fail the job whenever the daily row count falls under that number
C: Raise the threshold of every completeness rule to 100 percent, so that the evaluation fails whenever any column contains null values for the missing region
D: Lower the minimum data quality score that the job accepts, so that a single failing rule stops the job before the training table is written to S3
K: A
G: ## Rules versus analyzers
AWS Glue Data Quality has two ways to look at data:
- **Rules** in DQDL express expectations you already know, such as `IsComplete "store_id"`. If no rule covers a problem, nothing fails.
- **Analyzers** such as `RowCount`, `AllStatistics "column"` or `DistinctValuesCount "column"` only gather statistics, without a pass or fail threshold.
## Anomaly detection
Glue Data Quality keeps those statistics over time and, with anomaly detection enabled, uses an ML model to predict the expected range of each statistic. When an actual value falls outside it, Glue creates an **anomaly observation** and recommends rules.
- It needs at least three data points to start.
- Anomalies do **not** change the data quality score, so they must be reviewed or acted on.
- An anomalous value is treated as normal for later runs unless you exclude it.
W: Analyzers plus anomaly detection: the learned range catches a sudden 40 percent drop in row count or a shift in a column's statistics without a hand-written threshold for each case.
X: B=Fixed RowCount rule: it catches only this one known failure, and a fixed threshold breaks as volume grows or follows seasons.
C=Completeness at 100 percent: dropped rows do not create nulls in the remaining rows, so completeness rules still pass.
D=Lower score threshold: the score was already 100 percent because no rule failed; changing the accepted score cannot detect what no rule measures.
T: Glue Data Quality rules catch known problems; analyzers with anomaly detection catch unexpected shifts, and anomalies do not affect the score.
V: AWS Glue Data Quality, AWS Glue

@ MLA-C02 D1 T1.2 advanced use-case
S: An analyst built a Data Wrangler flow in SageMaker Canvas on a 50,000-row sample of a 40-million-row table. It imputes missing income with the median and one-hot encodes region. The model was trained on the exported full dataset, but the production app sends raw records, and an engineer re-implemented the transforms in AWS Lambda using the sample's median. Live predictions now differ from offline results. With the least custom code, what should the team do?
A: Keep the Lambda function but have it read the median from the analyst's flow file at start-up, so that the same sample-based value is used for every live request

When training data is transformed by one tool and live requests by hand-written code, small differences (a median from a sample, a different category order) make the model see different inputs in production than in training.

D=Exported Python in Lambda: it copies the code but still uses sample-fitted values and leaves two copies of the logic to keep in step.
T: To avoid training-serving skew from a Data Wrangler flow, refit the transforms on the full data and serve them with the model as a serial inference pipeline.

@ MLA-C02 D1 T1.1 advanced use-case
S: A media company's online feature group stores 400 features per user. Two separate streaming jobs update it: one changes only last_login and session_count thousands of times per second, the other rewrites watch-history aggregates every hour. Each job reads the full record and writes it back, so write costs are high, and sometimes a delayed write from one job overwrites newer values from the other. What should the ML engineer change?
A: Recreate the feature group with the InMemory tier, because an ElastiCache-backed store merges concurrent writes from different jobs automatically by feature name
B: Split the 400 features into two feature groups, one per job, and join them in the application for every inference request to rebuild the full record
C: Add a DynamoDB table with conditional writes in front of Feature Store, and copy the merged record into the feature group from a stream every minute
D: Migrate the feature group in place to Standard_V2 and have both jobs call UpdateRecord with only their changed features and the event time of the change
K: D
G: ## Partial updates with Standard_V2
The `Standard_V2` online store type supports the **UpdateRecord** operation:
- You send only the features you want to change; Feature Store keeps the rest. No read-modify-write is needed.
- Writing only changed features lowers write cost and latency for wide records where a few values change often.
- Each update's `EventTime` is used to detect and reject out-of-order writes, so a slow, stale update cannot overwrite newer values.
## Migrating
An existing `Standard` feature group can be migrated in place by calling `UpdateFeatureGroup` with `StorageType` set to `Standard_V2`, without recreating the group or reingesting data. The migration is one way.
W: Standard_V2 with UpdateRecord: each job writes only its own features, and EventTime checks stop stale writes from overwriting newer values, which fixes both cost and correctness.
X: A=InMemory tier: InMemory gives lower read latency, but it is not described as merging partial writes; full-record writes would still overwrite each other.
B=Two feature groups joined at request time: it avoids overwrites but adds a second lookup to every inference request and more application code.
C=DynamoDB in front: it builds a second store and a sync process that Feature Store now provides natively, and adds up to a minute of staleness.
T: For wide feature records with frequent partial updates, use the Standard_V2 online store and UpdateRecord, which also rejects out-of-order writes by EventTime.

@ MLA-C02 D1 T1.1 advanced use-case

The images are a working copy; the source of truth stays in an S3 Standard bucket, so losing the copy would only mean recopying it. The team wants faster data access and lower request costs without managing a file system. Which storage choice fits BEST?
A: Copy the working set to an S3 Express One Zone directory bucket in the same Availability Zone as the training instances and read tiles from it
B: Move the working copy to S3 Standard-Infrequent Access, because its lower storage price offsets the larger number of requests that every epoch sends

S3 Express One Zone is a single-Availability Zone storage class stored in **directory buckets**:
- consistent single-digit millisecond access, up to 10x faster than S3 Standard;
- request costs 80 percent lower than S3 Standard;
- you choose the Availability Zone, so you can co-locate data with compute;

W: S3 Express One Zone in the same AZ: low-latency, lower-cost requests next to the training instances, with no file system to run, and the single-AZ storage is fine for a re-creatable copy.

D=Transfer Acceleration: it speeds up long-distance transfers through edge locations; it does nothing for in-Region reads from a training instance.
T: Latency-bound training reads of a re-creatable copy → an S3 Express One Zone directory bucket in the same AZ as the compute.

@ MLA-C02 D1 T1.3 advanced use-case
S: A health insurer prepares claims tables for model training with AWS Glue. Member IDs follow an internal format (two letters and nine digits) and appear in free-text notes as well as in the ID column. Policy requires that no raw member ID reaches the training bucket, yet the data scientists must still join claims and pharmacy tables on member. Which TWO Glue Detect PII settings meet these requirements? (Select TWO)
A: Create a custom detection entity with a regular expression for the member ID format plus context words, and scan each cell of the notes and ID columns
B: Detect PII at the column level with a 10 percent detection threshold, so that the whole notes column is dropped whenever enough member IDs appear in it
C: Use the global action that applies a cryptographic SHA-256 hash to detected member IDs, so the same member gets the same value in both tables
D: Use the redact action with the default replacement string, so every detected member ID in both tables becomes the same string of asterisks
E: Rely on the built-in HIPAA category of entities, which already includes the insurer's member ID format along with names and addresses
K: A,C
G: ## Glue Detect PII transform
The Detect PII transform scans data for sensitive entities and then applies an action.

@ MLA-C02 D4 T4.3 advanced use-case
S: An internal agent on Amazon Bedrock AgentCore Runtime summarizes each employee's Jira tickets and Google Drive files. The team wants to avoid building OAuth flows itself. What should the ML engineer use?

G: ## AgentCore Identity
Amazon Bedrock AgentCore Identity manages identities and credentials for agents:

@ MLA-C02 D3 T3.3 advanced use-case
S: A SageMaker pipeline evaluates each new fraud model and registers it only if AUC is at least 0.90, using a Condition step with an empty else branch. When AUC is too low, the execution still ends as Succeeded with no model registered, so the on-call EventBridge rule, which matches only failed executions, stays silent. The team wants low-AUC runs to show as failed, with the AUC value in the reason. What should the ML engineer do?
A: Raise an exception in the evaluation script whenever AUC is under 0.90, so that the evaluation Processing step fails and stops the whole execution
B: Add a Lambda step in the else branch that publishes the AUC to an SNS topic, so that on-call receives a message although the execution succeeds
C: Add a retry policy to the evaluation step, so that a low AUC is evaluated again and the execution fails only after the last retry attempt
D: Put a Fail step in the Condition step's else branch, with an error message built with Join from the evaluation step's AUC property
K: D
G: ## Ending a pipeline on purpose
A Condition step chooses between branches; if the else branch is empty, the execution simply ends, and its status is **Succeeded**.
A **Fail step** stops the execution with status **Failed** when a desired condition is not met, with a **custom error message**. The message can be static or built from pipeline parameters, a `Join` operation or other step properties, such as the AUC from the evaluation report.
Limits: a Fail step is always the last step, other steps cannot reference it or list it in `DependsOn`, and an execution that ended in a Fail step cannot be retried.
Because the status is Failed, EventBridge rules for failed executions fire as usual.
W: Fail step with a Join message: low-AUC runs end as Failed with a readable reason that includes the AUC, and the existing on-call rule picks them up.
X: A=Exception in the evaluation script: the failure then looks like a broken script, and the evaluation outputs that explain the low AUC may never be written.
B=Lambda plus SNS: on-call gets a message, but the execution is still marked Succeeded, which hides the problem from status-based tooling.
C=Retry policy: retry policies repeat steps after errors; re-evaluating the same model returns the same AUC and still does not fail the execution.
T: To make a SageMaker pipeline end as Failed with a reason when a check is not met, route the Condition step's false branch to a Fail step.
V: Amazon SageMaker Pipelines, Amazon EventBridge

@ MLA-C02 D4 T4.2 advanced troubleshooting
S: An endpoint hosts three inference components on ml.g5.12xlarge instances (4 GPUs, 22 GiB each) with managed instance scaling. Each component copy sets NumberOfAcceleratorDevicesRequired to 2, although each model needs about 12 GiB of GPU memory. CloudWatch shows GPUReservation at 100 percent on all six instances, while GPUMemoryUtilizationNormalized stays near 25 percent. The team wants the same number of copies on fewer instances. What should the ML engineer change?
A: Update each inference component to require one accelerator per copy, so each instance holds four copies and managed scaling removes instances
B: Replace the instances with ml.g5.48xlarge (8 GPUs), so that more two-GPU copies fit on each instance and the endpoint runs on fewer, larger instances
C: Lower the target value of each component's copy-count scaling policy, so that fewer copies run and GPUReservation drops below 100 percent
D: Move the three models to a multi-model endpoint, because inference components always reserve whole instances and cannot share GPUs between models
K: A
G: ## Reservation versus utilization
With inference components, each copy **reserves** resources on an instance: `NumberOfAcceleratorDevicesRequired`, `NumberOfCpuCoresRequired`, `MinMemoryRequiredInMb`. SageMaker AI places copies only where the reservation fits.
CloudWatch shows both sides:
- **GPUReservation**: the share of GPUs reserved by containers (4 GPUs, 2 reserved = 50%).
- **GPUUtilizationNormalized** and **GPUMemoryUtilizationNormalized**: what the containers actually use, normalized to 0-100%.
## Working the numbers
Six instances x 4 GPUs = 24 GPUs; at 2 GPUs per copy that is 12 copies. Each model needs about 12 GiB, which fits in one 22 GiB GPU. With 1 GPU per copy, 12 copies need 12 GPUs, that is 3 instances instead of 6, and managed instance scaling can release the rest.
W: One accelerator per copy: the reservation matches what each model needs, so the same 12 copies fit on half the instances.
X: B=Larger instances: two-GPU copies still waste half of every reservation; it only moves the waste to bigger, pricier machines.
C=Lower scaling target: it reduces copies and capacity for traffic, which is not the goal; the waste per copy remains.
D=Multi-model endpoint: inference components already share instances between models; the issue is the size of each reservation, not the hosting type.
T: When GPUReservation is high but normalized GPU memory use is low, shrink each inference component's accelerator reservation so more copies share each instance.
V: Amazon SageMaker AI, Amazon CloudWatch
