@ MLA-C02 D1 T1.1 applied troubleshooting
S: An ML engineer creates an Amazon Bedrock knowledge base that uses Amazon Titan Text Embeddings V2 with 1,024 output dimensions. The vector index in the Amazon OpenSearch Serverless collection was created from an older template whose knn_vector field has dimension 1536. Every ingestion job fails for all documents. What should the engineer do?
A: Turn on normalization for Titan Text Embeddings V2 so each 1,024-value vector is padded to the 1536 values the index expects
B: Build a replacement index whose vector size matches the model output, switch the data source to it and load the documents again
C: Change the knn_vector field's engine from faiss to lucene, which accepts vectors shorter than the dimension in the mapping
D: Raise the OpenSearch Serverless indexing capacity so the collection can accept the knowledge base's ingestion jobs again
K: B
G: ## The dimension contract
An embedding model always returns vectors of a fixed length (its **dimension**). Titan Text Embeddings V2 lets you choose 256, 512 or 1,024 values; the older Titan Text Embeddings G1 model returned 1,536.
A vector index stores vectors in a field such as `"type": "knn_vector", "dimension": 1024`. Every vector written to that field must have exactly that many values, and every query vector must too. A mismatch is not a quality problem: the write is rejected.
## Fixing a mismatch
The dimension of an existing field cannot be changed in place. You create a new index (or a new field) with the right dimension, point the application or knowledge base at it, and re-ingest. The same rule applies to pgvector (`vector(1024)`) and to S3 Vectors indexes, where the dimension is fixed when the index is created.
W: Replacement index sized to the model output: matching the vector field to the model's 1,024 values is the only fix, and since the mapping cannot be edited in place, the index is recreated, the knowledge base is pointed at it and the documents are ingested again.
X: A=Normalize to pad vectors: normalization scales a vector to unit length; it never changes the number of values, so the vectors still have 1,024 dimensions.
C=Switch the engine to lucene: every k-NN engine requires vectors to match the field dimension exactly; the engine choice affects the index algorithm, not the length check.
D=Raise indexing capacity: capacity units control throughput and cost, and the failure is a mapping rejection that more capacity cannot change.
T: The vector field dimension must equal the embedding model's output dimension; a mismatch means recreating the index and re-ingesting.
V: Amazon Bedrock Knowledge Bases, Amazon OpenSearch Serverless, Amazon Titan Text Embeddings

@ MLA-C02 D2 T2.2 applied troubleshooting
S: An ML engineer uses the SageMaker Python SDK to fine-tune a Meta Llama model from SageMaker JumpStart on an instruction dataset in Amazon S3. The training job fails right away with an error saying the end-user license agreement was not accepted. What should the engineer do?
A: Subscribe to the model in AWS Marketplace to accept its license, then tag the execution role with the subscription ARN
B: Request a higher service quota for the GPU training instance type, and then start the same training job again unchanged
C: Copy the model weights into the team's own S3 bucket, where the license agreement no longer applies to the training run
D: Review the model's license terms and pass the explicit acceptance flag in the SDK fine-tuning call before running it again
K: D
G: ## Gated models in SageMaker JumpStart
Some JumpStart models, such as Meta Llama models, are **gated**: their license requires each user to accept an end-user license agreement (EULA) before training or deploying.
- In SageMaker Studio, you accept the EULA in the model's page before fine-tuning or deploying.
- In the SageMaker Python SDK, you pass an explicit acceptance flag (for example `accept_eula=True`) when you call fine-tuning or deployment. Without it the job is rejected immediately.
## Other JumpStart fine-tuning basics
- `JumpStartEstimator` takes a model ID, the instance type and hyperparameters; `fit()` takes the S3 location of the training data.
- Depending on the model, JumpStart supports domain adaptation (unlabeled text) or instruction tuning (prompt and response records), and many models support parameter-efficient fine-tuning such as LoRA.
W: Explicit acceptance flag after reviewing the license: gated JumpStart models require explicit EULA acceptance in the fine-tuning or deployment request (for example `accept_eula=True` in the SDK), and the error says exactly that it is missing.
X: A=AWS Marketplace subscription and role tag: JumpStart's gated open-weight models use EULA acceptance in the request, not a Marketplace subscription attached to the role.
B=Service quota increase: a quota problem returns a resource limit error when the job requests instances, not a license error.
C=Copy the weights: copying the artifacts does not change the license terms, and JumpStart fine-tuning is meant to use its managed model artifacts with the acceptance flag.
T: Gated JumpStart models such as Llama require explicit EULA acceptance in Studio or the SDK before fine-tuning or deployment.

@ MLA-C02 D1 T1.2 applied use-case
S: A bank loads 12,000 FAQ files into a Bedrock knowledge base. Each file holds exactly one short question and its answer of about 120 words. With fixed-size chunking at 60 tokens, retrieved chunks often contain only the question or only the answer. Which chunking setting fits this content best?
A: Semantic chunking with a low breakpoint percentile threshold, so each question and answer sentence gets its own chunk
B: Hierarchical chunking with 60-token child chunks for each question and a larger parent chunk that holds the answer
C: No chunking at all, since every file is already a small, self-contained unit that can be retrieved as it is
D: Fixed-size chunking at 60 tokens with higher overlap, so each chunk repeats much of the previous question or answer
K: C
G: ## Chunking options in Bedrock Knowledge Bases
- **Default / fixed-size**: split text into chunks of a set token count, with an optional overlap percentage.
- **Hierarchical**: small child chunks are matched, and their larger parent chunk is returned for context.
- **Semantic**: split where the meaning changes, using embedding similarity between neighboring sentences.
- **No chunking**: each file is one chunk. You pre-split the content yourself.
- **Custom**: a Lambda function does the splitting.
## Match the strategy to the document shape
Chunking exists to cut long documents into retrievable pieces. When each file is already one small, self-contained unit (a FAQ entry, a product card, a ticket summary), cutting it again only separates parts that belong together. Example: "Can I close my account online?" in one chunk and "Yes, from the settings page..." in another means neither chunk answers the question.
W: No chunking: each file is already a natural, short unit, so keeping it whole as one chunk guarantees that the question and its answer are retrieved together.
X: A=Semantic chunking with a low threshold: a low threshold splits more often, so a 120-word entry would be cut into even smaller pieces that separate the question from the answer.
B=Hierarchical chunking: parents and children are formed by size, not by question and answer roles, and the documents are too short to benefit from a hierarchy.
D=Larger overlap at 60 tokens: overlap duplicates text between neighbors but the chunks stay too small to hold a full question and answer, and the index grows.
T: If every file is already one small, self-contained unit, use no chunking instead of splitting it further.
V: Amazon Bedrock Knowledge Bases
