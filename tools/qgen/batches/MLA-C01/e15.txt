@ Q000985 explain
G: ## Data drift versus concept drift
A model learns a mapping from inputs X to a target y.
- **Data drift** (covariate shift): the distribution of X changes, for example customers suddenly come from a new region. Input distribution checks detect it without labels.
- **Concept drift**: the relationship between X and y changes while X can look the same. The same inputs now lead to different outcomes.
Example: a competitor enters the market. Store traffic, prices and seasonality features still look normal, but for the same inputs actual demand is lower because some customers go to the competitor. The model keeps predicting the old demand.
## How to detect it
Because inputs look unchanged, input monitoring stays quiet. The problem only appears when predictions are compared with real outcomes (ground truth). SageMaker Model Monitor **model quality monitoring** merges captured predictions with ground truth labels and tracks metrics such as MAE or RMSE for regression, alerting when they degrade.
Availability note: Amazon SageMaker Model Monitor is no longer open to new customers. Existing customers keep using it as normal (AWS adds no new features), and AWS points new customers to open-source monitoring with Amazon CloudWatch. The exam guide still names Model Monitor, so exam questions treat it as the SageMaker AI monitoring capability.
W: Concept drift detected with model quality monitoring: the input distributions are stable but accuracy falls, which means the input-to-target relationship changed; only comparing predictions with ground truth labels can reveal that.
X: A=Data drift via input checks: data drift means the input distributions change, but the stem says they look unchanged, so input distribution checks would not flag anything.
B=Latency drift: adding instances addresses slow responses, not a gradual loss of accuracy caused by a changed market.
D=Hardware drift: instance type affects speed and cost; the model computes the same predictions on any hardware, so changing it cannot restore accuracy.
T: Same inputs, different outcomes is concept drift, caught by model quality monitoring against ground truth, not by input distribution checks.

@ Q000995 explain
G: ## How the baseline drives violations
Model Monitor judges production data against a **baseline**: `statistics.json` (distributions of each feature) and `constraints.json` (rules such as data types, completeness and drift thresholds). The baseline is suggested by a baselining job, usually `suggest_baseline()` run on a dataset.
If that dataset is tiny or unrepresentative, the baseline describes a narrow slice of reality. Normal production traffic then looks like drift on every run.
Example: the baseline came from 500 records from one week in July. In production, `order_value` covers a much wider range and categories that never appeared in the sample, so every hourly run reports `baseline_drift_check` and categorical violations.
## Fix
- Rerun baselining on the full, representative training dataset (the data the model actually learned from).
- Review the suggested constraints and adjust thresholds or completeness requirements that are too strict.
- Update the monitoring schedule to use the new baseline files.
Availability note: Amazon SageMaker Model Monitor is no longer open to new customers. Existing customers keep using it as normal (AWS adds no new features), and AWS points new customers to open-source monitoring with Amazon CloudWatch. The exam guide still names Model Monitor, so exam questions treat it as the SageMaker AI monitoring capability.
W: Re-baseline on representative data: violations are only meaningful when the baseline reflects normal data, so regenerating statistics and constraints from the full training set stops the false alarms while keeping real drift detection.
X: B=Disable monitoring: the model has not changed and retraining would not fix a bad baseline, while turning monitoring off leaves the endpoint unmonitored in the meantime.
C=Delete all constraints: with no constraints nothing is checked, so real drift would go unnoticed along with the false alarms.
D=Run every minute: running more often only produces the same false violations more often; it does not change what they are compared against.

G: ## How Model Quality monitoring gets its labels
Model Quality monitoring compares predictions with **ground truth**, which arrives later and separately. Each run has a merge step:
- Captured request and response records are joined with ground truth records by an **inference ID**. The application supplies it when it calls the endpoint (the `InferenceId` parameter), and the ground truth records carry the same ID.

@ Q004628 explain
G: ## Distributions and attributions are different things
- **Data quality monitoring** looks at the inputs: statistics such as mean, min, max, missing values and data types, compared with baseline constraints.
- **Feature attribution drift monitoring** (SageMaker Clarify with Model Monitor) looks at **why the model predicts what it does**. It computes SHAP-based attributions for live inference data and ranks the features by importance.
## The comparison
The monitor compares the live ranking with the baseline ranking using the **normalized discounted cumulative gain (NDCG)** score. If the score falls below the constraint, a violation is reported, meaning the features driving predictions have changed in importance.
This can happen even when each input distribution looks the same, for example when the relationship between two features and the label has shifted, so the model leans on different features than at training time.

Existing customers keep using it as normal (AWS adds no new features), and AWS points new customers to open-source monitoring with Amazon CloudWatch. W: NDCG on SHAP-based rankings: the monitor detects a change in which features drive predictions, which is invisible to input distribution checks.
X: A=Missing values and data types: this is also a data quality check, and it does not involve model explanations.

D=Column statistics with a statistical test: this describes the checks that data quality monitoring performs on inputs, and it would not explain a violation when the inputs match.

G: ## Drift is a signal, not proof of harm
Data drift says the inputs changed. Model quality says whether the predictions are still correct. Inputs can drift in ways that do not matter to the model, so retraining on every drift alarm pays for runs that add nothing.
## Composite alarms
A CloudWatch **composite alarm** evaluates a rule expression over other alarms, for example `ALARM(feature-drift) AND ALARM(model-quality)`. It triggers its actions (SNS notification, EventBridge event that starts a SageMaker Pipeline) only when the rule is true, which reduces noisy notifications.
## Trade-off
The design waits for labeled evidence, so it reacts more slowly than a drift-only trigger. Add a rule for severe drift alone, for example `OR ALARM(severe-drift)`, if waiting is too risky.

Existing customers keep using it as normal (AWS adds no new features), and AWS points new customers to open-source monitoring with Amazon CloudWatch. The exam guide still names Model Monitor, so exam questions treat it as the SageMaker AI monitoring capability.
W: Composite alarm on drift and model quality: retraining starts only when the inputs moved and measured quality actually dropped.
X: A=Lower thresholds: a more sensitive alarm fires even more often, which increases unneeded retraining.
C=Dropping model quality monitoring: this removes the only signal of actual harm, and slow labels are handled by scheduling the monitor accordingly.
D=Retrain on every drift alarm: this repeats a $3,000 run several times a month without evidence that forecasts got worse.
T: Combine drift and model quality alarms in a CloudWatch composite alarm so retraining requires evidence of both changed inputs and degraded predictions.

G: ## What Model Monitor expects
Data Quality monitoring works on **tabular** records. For an endpoint that accepts CSV or flat JSON lines, the built-in analyzer can read the captured data directly. When the payload is nested or in a custom format, the monitor cannot map it to the baseline's columns, so it produces missing or unexpected features.
## Preprocessing script
The schedule accepts a **record preprocessor script** (`record_preprocessor_script`), a Python function that runs on each captured record and returns a flat dictionary or list of feature values with the same names as in the baseline. There is a matching **post-analytics processor script** for custom checks after analysis.
Example: the function extracts `customer.age`, `customer.tenure` and the summary of `events` into columns, so live data is compared with the training statistics column by column.

W: Record preprocessor script: it converts each nested captured record into the tabular feature layout that the baseline and constraints use.
X: A=100 percent sampling: sampling changes how many records are captured and does not alter their structure.
B=Larger instance: the failure is a format mismatch and not a lack of memory or CPU, so more capacity yields the same wrong columns.
C=CSV-only container: this forces a change to the model container and all clients to fix a monitoring problem that a script solves without touching the endpoint.
T: For nested or custom payloads, give the Model Monitor schedule a record preprocessor script that flattens records into the baseline's feature columns.

G: ## One place to see model risk
A large set of models needs a portfolio view, not 40 separate reports. The **SageMaker Model Dashboard** is a centralized portal in SageMaker AI that shows the models in an account and Region together with their details. It combines information from model cards, endpoints, batch transform jobs and **Model Monitor** schedules.
## What it shows
- Which models have monitoring schedules for data quality, model quality, bias drift and feature attribution drift, and which have none.
- Whether monitoring has found **violations** and their status, so reviewers can go from a model to the report.
- Endpoint status and links to model cards, plus the model risk rating that governance records in the card.
It reads the resources that already exist, so there is nothing to build; alarms and notifications are still set separately with CloudWatch and EventBridge.

Existing customers keep using it as normal (AWS adds no new features), and AWS points new customers to open-source monitoring with Amazon CloudWatch. The exam guide still names Model Monitor, so exam questions treat it as the SageMaker AI monitoring capability.
W: SageMaker Model Dashboard: it gathers monitoring status, violations, endpoints and model cards for all models in one managed view.

B=AWS Config aggregator: Config evaluates resource configuration against rules and does not read Model Monitor violations or model quality results.

T: Use the SageMaker Model Dashboard for a single view of monitoring status and violations across all production models.
