@ MLA-C01 D1 T1.1 applied definition
S: A team needs to compute rolling window aggregations (such as a 5-minute moving average) directly on a Kinesis Data Stream to generate real-time features for a fraud-scoring model, with exactly-once processing semantics. Which AWS-managed processing framework is purpose-built for this kind of stateful stream processing?
A: AWS Glue DataBrew scheduled recipe jobs
B: Amazon Managed Service for Apache Flink
C: Amazon Athena scheduled SQL queries
D: AWS Batch jobs submitted every minute
K: B
G: ## Stateful stream processing
A rolling feature such as "average transaction amount over the last 5 minutes per card" needs **state**: the processor must remember recent events per key and update the result as new events arrive.
## Amazon Managed Service for Apache Flink
This service (formerly Kinesis Data Analytics for Apache Flink) runs Apache Flink applications without managing servers.
- Flink supports tumbling, sliding and session **windows**, keyed state and event-time processing with watermarks for late data.
- **Checkpoints** save state regularly so a failed application restarts where it left off, giving exactly-once state consistency; with transactional sinks, end-to-end exactly-once output is possible.
- It has a native connector for Kinesis Data Streams as a source.
Example: `SELECT card_id, AVG(amount) ... GROUP BY card_id, HOP(event_time, INTERVAL '1' MINUTE, INTERVAL '5' MINUTE)` in Flink SQL emits a 5-minute moving average every minute.
W: Managed Service for Apache Flink: it runs stateful windowed aggregations on a Kinesis stream in real time and uses checkpoints for exactly-once state consistency.
X: A=Glue DataBrew recipe jobs: DataBrew runs visual recipe jobs on data at rest in batches, so even on a schedule it cannot keep continuous windows and per-key state over a live stream.
C=Athena scheduled queries: Athena runs SQL on data already stored in S3 and other sources, so results arrive only when a query runs, not as a continuous per-event computation with exactly-once state.
D=AWS Batch every minute: Batch schedules finite containerized jobs; a stream needs a long-running application that keeps state between events, and minute-by-minute jobs lose that state between runs.
T: Real-time windows with exactly-once state on a stream call for Managed Service for Apache Flink; batch and query tools only work on data at rest.
V: Amazon Managed Service for Apache Flink, Amazon Kinesis Data Streams

@ MLA-C01 D4 T4.2 advanced use-case
S: Endpoint traffic rises fivefold during business hours. The team wants instance count to follow load automatically. Which configuration is standard?
A: Target tracking on the variant's SageMakerVariantInvocationsPerInstance metric
B: A scheduled action that sets the variant to a fixed peak instance count each weekday
C: Step scaling on the variant's average disk utilization, adding one instance per alarm
D: A larger instance type for the variant, sized once for the business-hours peak load
K: A
G: ## Auto scaling SageMaker endpoints
SageMaker endpoints scale through Application Auto Scaling. You register the production variant as a scalable target (dimension `sagemaker:variant:DesiredInstanceCount`) with a minimum and maximum instance count, then attach a scaling policy.
- **Target tracking** is the standard policy: you pick a metric and a target value, and Auto Scaling adds or removes instances to keep the metric near it.
- The usual metric is the predefined `SageMakerVariantInvocationsPerInstance`, the average number of requests per minute each instance receives.
Example: if load tests show one instance handles about 1,000 invocations per minute comfortably, set a target of 700. When business-hours traffic rises fivefold, Auto Scaling adds instances; when traffic falls, it removes them after a cooldown.
Step scaling and scheduled scaling also exist, but they are used for special cases.
W: Target tracking on SageMakerVariantInvocationsPerInstance: it adjusts the variant's instance count automatically to keep requests per instance near a target, so capacity follows the daily traffic curve.
X: B=Scheduled fixed count: it changes capacity by the clock, not by load, so an unexpected peak or a quiet business day still gets the wrong number of instances.
C=Step scaling on disk utilization: disk use on an inference instance does not rise with request volume, so the alarms do not fire when traffic grows; it is not a meaningful load signal.
D=Larger instance type: a bigger instance raises fixed capacity but the instance count never changes, so the variant is oversized at night and may still be short at an unusual peak.
T: Endpoint capacity that follows load is achieved with target tracking on invocations per instance, not with manual or unrelated metrics.
V: Amazon SageMaker AI, Application Auto Scaling

@ MLA-C01 D4 T4.1 applied use-case
S: A team wants to automatically detect when the statistical distribution of input features sent to a real-time SageMaker endpoint diverges significantly from the training data baseline, and raise a CloudWatch alarm when this happens. Which capability should they use?
A: Model Monitor data quality monitoring
B: SageMaker Autopilot candidate evaluation
C: SageMaker Ground Truth labeling jobs
D: SageMaker Debugger built-in rules
K: A
G: ## Model Monitor data quality monitoring
SageMaker Model Monitor watches a deployed endpoint on a schedule. **Data quality monitoring** focuses on the input features.
- **Baseline**: a baselining job runs on the training dataset and writes `statistics.json` (per-feature distributions, missing values) and `constraints.json` (expected types, completeness and drift thresholds).
- **Data capture**: the endpoint saves a sample of requests and responses to S3.
- **Monitoring schedule**: for example hourly, a job compares the captured inputs with the baseline and writes a violations report (such as `baseline_drift_check` when a feature's distribution distance exceeds its threshold).
- **Alerting**: with CloudWatch metrics enabled, the job publishes per-feature metrics, and CloudWatch alarms on them notify the team.
No ground truth labels are needed, because only inputs are compared.
Availability note: Amazon SageMaker Model Monitor is no longer open to new customers. Existing customers keep using it as normal (AWS adds no new features), and AWS points new customers to open-source monitoring with Amazon CloudWatch. The exam guide still names Model Monitor, so exam questions treat it as the SageMaker AI monitoring capability.
W: Model Monitor data quality monitoring: it compares live input feature distributions from data capture with a training baseline, reports drift violations, and publishes metrics that CloudWatch alarms can watch.
X: B=Autopilot candidate evaluation: Autopilot is AutoML that builds, tunes and ranks candidate models from a training dataset; it does not monitor a deployed endpoint's inputs.
C=Ground Truth labeling jobs: Ground Truth produces labeled data with human or automated labeling; it does not compare production input distributions with a baseline.
D=Debugger built-in rules: Debugger rules inspect tensors and system resources during training jobs (for example vanishing gradients); they do not run on live endpoint traffic.
T: Input feature drift at an endpoint is detected by Model Monitor data quality monitoring against a training baseline, alarmed through CloudWatch.
V: SageMaker, Amazon CloudWatch

@ MLA-C01 D1 T1.3 applied use-case
S: A dataset used for training contains customer names and full credit card numbers that are not needed as predictive features. Before storing the data for ML use, the team wants to irreversibly remove or obscure this sensitive information rather than merely restrict access to it. Which technique should be applied?
A: Restricting reads with IAM and S3 bucket policies
B: Encrypting the objects with SSE-KMS keys
C: Enabling Amazon Macie discovery on the bucket
D: Masking, removing or anonymizing the fields
K: D
G: ## Restricting access versus removing the data
Access controls (IAM, bucket policies) decide who can read a file, but the sensitive values are still inside it. If a policy is misconfigured, a copy is made, or the data is used to train a model, the values are exposed.
## De-identification techniques
- **Masking**: replace part or all of a value, for example `4111 **** **** 1111` or `XXXX`.
- **Redaction or removal**: drop the column entirely. Best when the field is not a useful feature, like a name.
- **Anonymization**: transform data so it cannot be linked back to a person, for example generalizing or aggregating.
- **Tokenization or hashing**: replace values with surrogates; useful when a join key is needed, but reversible or guessable schemes need care.
Tools such as AWS Glue's sensitive data detection, Glue DataBrew transforms or Amazon Macie (to find PII in S3) help.
Example: drop `customer_name`, remove `card_number`, keep `transaction_amount` and `merchant_category` as features.
W: Masking, removing or anonymizing: it irreversibly removes or obscures names and card numbers before the data is stored for ML, so the sensitive values no longer exist in the dataset.
X: A=IAM and bucket policies: they restrict who can read the data but leave the names and card numbers intact, which the question explicitly says is not enough.
B=SSE-KMS encryption: encryption protects the stored objects, but anyone allowed to use the key reads the original names and card numbers, so the values are still present and recoverable.
C=Macie discovery: Macie finds and reports sensitive data such as card numbers in S3, but it does not change the objects, so the values stay in the dataset.
T: Sensitive fields not needed as features → mask, anonymize or drop them; access controls only restrict who sees them.
V: Amazon S3

@ MLA-C01 D1 T1.2 applied comparison
S: A data scientist is preparing numeric features for a model sensitive to feature scale. One feature ranges from 0 to 1,000,000 while another ranges from 0 to 1. The scientist wants to transform features to have zero mean and unit variance. Which technique should be applied?
A: Standardization (z-score scaling)
B: Min-max normalization to [0, 1]
C: Quantile binning into ten buckets
D: Log transformation of the values
K: A
G: ## Why scale features
Models that use distances or gradients, such as k-NN, SVM, linear or logistic regression with regularization, and neural networks, are **scale-sensitive**. A feature ranging to 1,000,000 dominates one ranging to 1 simply because of its units.
## Standardization (z-score)
Each value is transformed as `z = (x - mean) / std`, using the mean and standard deviation from the training data.
- The result has mean 0 and standard deviation 1, which is exactly the requirement in the question.
- Values are not bounded: a value 3 standard deviations above the mean becomes 3.
Example: with mean 50,000 and standard deviation 20,000, an income of 90,000 becomes 2.0.
## How it differs from min-max normalization
Min-max scaling maps values to a fixed range such as 0 to 1 with `(x - min) / (max - min)`. It does not give zero mean and unit variance, and a single extreme value changes `max` for every row.
W: Standardization (z-score): subtracting the mean and dividing by the standard deviation produces features with zero mean and unit variance, putting both features on a comparable scale.
X: B=Min-max normalization: it rescales to a fixed range such as 0 to 1, but the result does not have zero mean and unit variance, and it is strongly affected by extreme values.
C=Quantile binning: binning replaces values with bucket labels, losing detail within each bucket, and it does not produce a zero-mean, unit-variance feature.
D=Log transformation: taking logarithms compresses large values, but the transformed feature has neither a mean of 0 nor a standard deviation of 1, so the stated requirement is not met.
T: "Zero mean and unit variance" means z-score standardization; min-max gives a bounded range instead.

@ MLA-C01 D4 T4.2 applied use-case
S: An SRE wants a way to express the percentage of successful invocations versus total invocations for a SageMaker endpoint over the last hour, to track availability. Which pair of metrics should be combined?
A: CPUUtilization and MemoryUtilization
B: Invocations and Invocation5XXErrors
C: ModelLatency and OverheadLatency
D: GPUUtilization and DiskUtilization
K: B
G: ## Availability from invocation metrics
SageMaker publishes per-endpoint invocation metrics to CloudWatch:
- `Invocations`: number of requests sent to the model.
- `Invocation4XXErrors`: requests that failed because of the client (for example bad input).
- `Invocation5XXErrors`: requests that failed on the server side (the model container or SageMaker).
Availability as a success rate is usually computed from server-side failures, because client errors are not the service's fault:
`availability = 1 - (Invocation5XXErrors / Invocations)`
In CloudWatch you do this with **metric math**: add both metrics with the `Sum` statistic over a 1-hour period and define an expression such as `100 * (1 - m2/m1)`. The result can be graphed on a dashboard, alarmed on or used as a service level indicator.
Example: 120,000 invocations and 60 5XX errors in an hour gives 1 - 60/120,000 = 99.95% availability.
W: Invocations and Invocation5XXErrors: the server error count divided by total invocations gives the failure ratio, and one minus that ratio is the percentage of successful invocations over the hour.
X: A=CPU and memory utilization: they measure how busy the instances are, not how many requests succeeded or failed.
C=ModelLatency and OverheadLatency: they measure how long requests take, and a request can be fast and still fail, so they cannot give a success rate.
D=GPU and disk utilization: these are resource usage figures and contain no count of successful or failed requests.
T: Endpoint availability is 1 minus 5XX errors divided by invocations, computed with CloudWatch metric math.
V: Amazon CloudWatch, SageMaker

@ MLA-C01 D4 T4.2 applied troubleshooting
S: A Lambda function that pre-processes features before invoking a SageMaker endpoint is intermittently timing out. The team wants a fast way to see the function's memory usage, cold start counts, and CPU usage without writing custom metrics code. Which tool should they enable?
A: AWS Config managed rules
B: SageMaker Debugger profiling
C: AWS Trusted Advisor checks
D: CloudWatch Lambda Insights
K: D
G: ## CloudWatch Lambda Insights
By default, Lambda publishes basic metrics such as `Invocations`, `Duration`, `Errors` and `Throttles`. They do not show memory or CPU use inside the function.
**Lambda Insights** adds that detail. You enable it on the function (in the console or by adding the Lambda Insights extension layer and the `CloudWatchLambdaInsightsExecutionRolePolicy` managed policy to the role). The extension then collects system-level metrics per invocation, with no code changes:
- `memory_utilization` and `used_memory_max`
- `cpu_total_time`
- `init_duration`, which shows cold starts
- network and `/tmp` usage
CloudWatch provides ready-made dashboards for a single function and across functions.
Example: timeouts coincide with `used_memory_max` near the configured 512 MB and high CPU time, so raising memory (which also raises CPU share) fixes them. Or they coincide with long `init_duration`, pointing to cold starts from a heavy dependency load.
W: CloudWatch Lambda Insights: it collects memory, CPU and cold start (init duration) metrics for the function automatically once enabled, so no custom metrics code is needed to diagnose the timeouts.
X: A=Config managed rules: Config checks whether resource configurations comply with rules; it records settings, not runtime memory or CPU use per invocation.
B=Debugger profiling: Debugger profiles SageMaker training jobs (tensors and system resources); it does not instrument Lambda functions.
C=Trusted Advisor checks: they give account-level recommendations on cost, security and limits and do not provide per-invocation performance metrics.
T: For memory, CPU and cold start detail on a Lambda function, enable CloudWatch Lambda Insights instead of writing custom metrics.
V: Amazon CloudWatch, AWS Lambda

@ MLA-C01 D4 T4.2 applied use-case
S: Before deploying a new model to production, a team wants an automated, data-driven recommendation for the most cost-effective instance type and endpoint configuration that meets a specific latency SLA, based on load testing against their actual model artifact. Which SageMaker feature should they use?
A: SageMaker Clarify explainability
B: SageMaker Ground Truth labeling
C: SageMaker Data Wrangler flows
D: SageMaker Inference Recommender
K: D
G: ## SageMaker Inference Recommender
Inference Recommender helps choose how to host a model before it goes to production. You register the model (for example in the Model Registry) and start a job:
- A **default** job runs quick load tests on a set of recommended instance types and returns cost, latency and throughput for each.
- An **advanced** job runs a custom load test, with your traffic pattern and your constraints such as a maximum P95 latency, and reports configurations that meet the target along with their cost per hour and per inference.
## Example
A team needs P95 latency under 100 ms at 200 requests per second. Inference Recommender tests the actual model artifact on several instance types and shows that a certain GPU type meets the SLA at the lowest cost, while a CPU type misses the latency target.
W: Inference Recommender: it load-tests the real model artifact on candidate instance types and endpoint settings and recommends the most cost-effective configuration that meets the stated latency requirement.
X: A=Clarify explainability: SageMaker Clarify measures bias in data and models and explains predictions with feature attributions; it does not benchmark hosting configurations.
B=Ground Truth labeling: Ground Truth creates labeled datasets with human or automated labeling; it plays no role in choosing instance types.
C=Data Wrangler flows: Data Wrangler imports, explores and transforms data for training; it does not load-test deployed models.
T: "Which instance meets my latency target at the lowest cost?" is answered by Inference Recommender load tests, not by data preparation or bias tools.
V: SageMaker

@ MLA-C01 D4 T4.3 applied use-case
S: A company wants only a small, designated group of ML engineers to be able to approve a model version in SageMaker Model Registry for production deployment, while data scientists can register new model versions but not approve them. How should this be implemented?
A: Give everyone the same admin role and rely on team communication
B: Disable versioning in the Model Registry to prevent unauthorized changes
C: IAM policies that split CreateModelPackage from UpdateModelPackage
D: Track approval decisions in a shared spreadsheet outside AWS
K: C
G: ## Model Registry approval flow
In the SageMaker Model Registry, each model version is a **model package** in a model package group. Every version has an approval status: `PendingManualApproval`, `Approved` or `Rejected`. CI/CD pipelines commonly deploy to production only when a version becomes `Approved`, often triggered by an EventBridge rule on the status change.
## Separating the permissions with IAM
The actions behind each step are separate IAM permissions:
- Registering a version uses `sagemaker:CreateModelPackage`.
- Changing its approval status uses `sagemaker:UpdateModelPackage`.
Data scientists get a policy allowing `CreateModelPackage` on their model package groups but not `UpdateModelPackage`; ML engineers who approve get `UpdateModelPackage`. Because `CreateModelPackage` can also set an initial approval status, teams make sure new versions are registered as `PendingManualApproval` (for example in the registration pipeline), and CloudTrail records who approved each version.
W: Split IAM permissions: data scientists get `sagemaker:CreateModelPackage` but not `sagemaker:UpdateModelPackage`, and only the designated engineers can change a version's approval status, so separation of duties is enforced inside AWS.
X: A=Same admin role for everyone: everyone could approve any model, so nothing enforces that only the designated engineers approve, and the audit trail cannot distinguish the roles.
B=Disable versioning: versions are the core of the Model Registry; without them there is no version history to register and approve, and it does nothing to separate who may approve.
D=Shared spreadsheet: a spreadsheet records decisions but enforces nothing; anyone with SageMaker permissions could still approve a version in AWS.
T: Separation of duties in the Model Registry is enforced with IAM permissions on the register and approve actions, not with shared roles or off-platform records.
V: SageMaker, AWS IAM

@ MLA-C01 D2 T2.2 applied troubleshooting
S: A SageMaker hyperparameter tuning job runs a custom PyTorch script. Every training job completes, but the tuning job shows no objective metric values. The metric definition uses the regex `val_loss=([0-9\.]+)`, and the script's log lines look like `epoch 5 validation loss: 0.2310`. What should the engineer do?
A: Enable SageMaker Debugger on the training jobs so that it collects the validation loss tensors and passes them to the tuner
B: Increase MaxRuntimeInSeconds for each training job so the script has enough time to write its final validation metric line
C: Change the tuning strategy from Bayesian to random search so that the objective metric does not need to be read from the logs
D: Align the regular expression with the printed text, editing either one so every epoch's output line yields a captured number
K: D
G: ## How SageMaker finds your metrics
For training scripts that you write yourself, SageMaker does not know what "validation loss" is. It reads the job's log stream in CloudWatch Logs and applies each `MetricDefinitions` entry, a name plus a regular expression with one capture group.
- Every log line that matches produces a data point for that metric name.
- A hyperparameter tuning job reads its objective metric from exactly one of these definitions.
If the regex never matches, the metric is empty, and the tuner has nothing to compare between jobs.
## Example
Log line: `epoch 5 validation loss: 0.2310`
Working definition: `{"Name": "validation:loss", "Regex": "validation loss: ([0-9\\.]+)"}`
The regex `val_loss=([0-9\.]+)` expects different text, so it never matches.
W: Align the pattern and the output: the objective metric is parsed from the logs with the metric definition regex, so making the pattern match the printed line (or printing what the pattern expects) gives the tuner its values.
X: A=Debugger: Debugger saves tensors for analysis and rules; it does not feed values to the tuner's objective metric, which comes from the metric definitions.
B=Longer runtime: the jobs already complete and print the loss lines. The problem is that the pattern does not match them, not that they are missing.
C=Random search: every tuning strategy, including random search, still needs the objective metric to rank the training jobs and report the best one.
T: An empty objective metric in a tuning job usually means the metric definition regex does not match the script's log lines.
V: Amazon SageMaker, Amazon CloudWatch Logs
