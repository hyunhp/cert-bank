Example: a baseline says `vehicle_age` has mean 6.1; a night with mean 9.8 produces a drift violation.
Availability note: Amazon SageMaker Model Monitor is no longer open to new customers. @ MLA-C01 D2 T2.1 applied tradeoff
S: A company wants an internal assistant on Amazon Bedrock that answers employee questions from 40,000 policy documents. About 200 documents change every day, answers must cite the source document, and the team has no labeled question-answer pairs. Which approach fits BEST?
A: Create an Amazon Bedrock knowledge base over the documents and answer with retrieval-augmented generation that returns citations
B: Fine-tune a Bedrock foundation model each night on the full document set so that the model memorizes the newest policy wording
C: Run continued pre-training weekly on the changed documents so the model absorbs the new policy text before users ask about it
D: Paste as many complete policy documents as fit into each prompt so the model can read the relevant text directly for each question
K: A
G: ## Two ways to give a model company knowledge
- **Customization** (fine-tuning or continued pre-training) changes the model's weights. It is good for style, tone and task format, but facts learned this way are frozen at training time, cannot be traced back to a source, and every refresh is a new training job.
- **Retrieval-augmented generation (RAG)** leaves the model unchanged. At question time, relevant passages are retrieved from an index and inserted into the prompt, so the answer is based on the current text.
## Amazon Bedrock Knowledge Bases
A knowledge base connects a data source such as an S3 bucket, splits documents into chunks, creates embeddings and stores them in a vector store. A sync job picks up added or changed documents. The `RetrieveAndGenerate` API returns the answer plus citations that point to the source chunks.
Example: a policy changes on Monday, the sync runs, and the next answer quotes the new wording with a link to that document.
W: Knowledge base with RAG: daily changes are handled by syncing the data source instead of retraining, answers come with citations to the retrieved documents, and no labeled training data is needed.
X: B=Nightly fine-tuning: fine-tuning needs labeled prompt-response pairs, which the team does not have, it does not produce citations, and retraining every night is slow and costly.
C=Weekly continued pre-training: the model would be up to a week out of date, it still cannot say which document a fact came from, and each run is an expensive training job.
D=Stuffing whole documents into prompts: only a tiny fraction of 40,000 documents fits in a context window, so without retrieval the model usually sees the wrong ones, and very long prompts are slow and costly.
T: Frequently changing facts that need citations call for RAG with a knowledge base; fine-tuning changes behavior, not up-to-date, traceable knowledge.
V: Amazon Bedrock, Amazon Bedrock Knowledge Bases, Amazon S3

@ MLA-C01 D2 T2.3 advanced use-case
S: A classifier outputs probabilities that are poorly calibrated, and downstream systems depend on accurate probabilities. What should the team do?
A: Train for more epochs until the training loss approaches zero on the training data
B: Apply probability calibration, such as Platt scaling or isotonic regression
C: Remove the validation set so that the calibration error is no longer measured
D: Send downstream systems the predicted class label instead of a probability
K: B
G: ## What calibration means
A classifier is well calibrated when its predicted probabilities match observed frequencies: among cases scored 0.8, about 80% should be positive. Many models, such as boosted trees or deep networks, rank cases well but produce probabilities that are too extreme or too flat.
## Calibration methods
Calibration fits a small mapping from raw scores to corrected probabilities on a held-out set, without retraining the main model.
- **Platt scaling**: fits a logistic regression on the model's scores; simple and works with little data.
- **Isotonic regression**: fits a monotonic step function; more flexible but needs more data.
Quality is checked with a reliability diagram or metrics such as the Brier score or expected calibration error.
## Example
A fraud model scores 0.9 for transactions that turn out fraudulent only 60% of the time. After isotonic regression on validation data, those cases score about 0.6, so downstream cost rules act on correct risk estimates.
W: Platt scaling or isotonic regression: these methods remap scores so predicted probabilities match observed frequencies, which is what downstream systems relying on probabilities need.
X: A=Train until training loss is near zero: driving training loss toward zero overfits and typically makes predictions more overconfident, worsening calibration on new data.
C=Remove the validation set: without held-out data you can neither measure calibration nor fit a calibrator, so the problem is hidden, not fixed.
D=Class label instead of a probability: downstream systems explicitly depend on probabilities, so removing them breaks those consumers instead of fixing their accuracy.
T: When probabilities drive decisions, fix them with a calibration step on held-out data rather than longer training or discarding probabilities.

@ MLA-C01 D2 T2.3 applied use-case
S: A medical screening model must miss as few positive cases as possible. Which metric should be prioritized?
A: Overall accuracy
B: Specificity (true negative rate)
C: Recall (sensitivity)
D: Precision (positive predictive value)
K: C
G: ## Precision and recall from the confusion matrix
For a binary classifier, predictions fall into four cells: true positives (TP), false positives (FP), true negatives (TN) and false negatives (FN).
- **Recall (sensitivity)** = TP / (TP + FN): of all real positives, how many did the model catch?
- **Precision** = TP / (TP + FP): of everything flagged positive, how many really were positive?
- **Specificity** = TN / (TN + FP): of all real negatives, how many were correctly cleared?
- **Accuracy** = (TP + TN) / all predictions.
Example: 1,000 patients, 10 with the disease. A model that always says "healthy" is 99% accurate and 100% specific but has 0% recall: it misses every sick patient.
In screening, a missed case (FN) is the costly error, so the model is tuned to maximize recall, accepting more false alarms that later tests can rule out.
W: Recall (sensitivity): it directly measures the share of actual positive cases that the model identifies, so maximizing it minimizes missed diagnoses.
X: A=Overall accuracy: with rare positives, accuracy is dominated by the many negatives and can look excellent while most positive cases are missed.
B=Specificity: it measures how well healthy people are cleared; false negatives do not appear in its formula, so a model can be highly specific while missing many sick patients.
D=Precision: precision penalizes false positives (false alarms), not false negatives, so a model can have high precision while still missing many sick patients.
T: When missing a positive is the worst error, prioritize recall; precision and specificity matter when false alarms are the costly error.

@ MLA-C01 D1 T1.2 advanced use-case
S: A model uses a date feature. Which transformation typically helps a tree model capture weekly and monthly patterns?
A: One-hot encode each unique timestamp value
B: Extract components such as day of week and month
C: Drop the date column, since trees split on numbers
D: Convert the date into a single epoch-seconds integer
K: B
G: ## Why raw dates are hard for models
A timestamp like `2025-11-14 18:32:05` is almost unique per row. Weekly or monthly patterns (weekend spikes, month-end payments) are hidden inside it.
## Extracting calendar components
Split the date into features that repeat:
- `day_of_week` (0-6), `is_weekend`
- `month` (1-12), `day_of_month`, `is_month_end`
- `hour`, `quarter`, `is_holiday` (from a holiday calendar)

Example: an electricity demand model gains accuracy once `hour` and `day_of_week` are added, because consumption follows daily and weekly cycles.
W: Calendar components: day of week and month repeat across rows, so they expose weekly and monthly cycles directly and tree splits can capture them.
X: A=One-hot each unique timestamp: each timestamp becomes its own column with a single 1, so no two rows share a value and nothing generalizes to new dates.
C=Drop the date column: a raw date string is not usable as is, but dates are very informative once converted into numeric calendar features, so dropping them discards useful signal.
D=Single epoch integer: an epoch number increases steadily, so the model can learn a trend but cannot see that every Monday or every December is similar.
T: Turn dates into calendar components so repeating patterns become visible; unique timestamps or a single epoch value hide periodicity.

@ MLA-C01 D1 T1.1 applied use-case
S: Which storage option is most cost-effective for keeping large raw training datasets that are read occasionally?
A: EC2 instance store NVMe disks
B: Amazon ElastiCache in-memory nodes
C: Amazon EBS io2 Block Express volumes
D: Amazon S3 with lifecycle rules

G: ## Where raw training data should live
Raw datasets are often very large, written once, and read only when a model is retrained. The ideal store is durable, cheap per GB and readable by many services.
## Amazon S3 with lifecycle rules

@ MLA-C01 D1 T1.3 applied use-case
S: Which data split is appropriate for tuning hyperparameters without biasing the final performance estimate?
A: Training and validation sets, reporting the validation score as the final estimate
B: One combined dataset that is used for training, tuning and the final score
C: Training and test sets, with hyperparameters tuned on the test set
D: Separate training, validation, and held-out test sets
K: D
G: ## Three splits, three jobs
- **Training set**: the model learns its parameters (weights) from it.
- **Validation set**: you compare hyperparameter choices (learning rate, depth, regularization) and pick the best.
- **Test set**: used once, at the end, to estimate how the chosen model will perform on new data.
## Why tuning on the test set is a problem
Every time you look at test results and change a setting, you are fitting the model to the test data. After 50 tuning trials, the best test score is optimistic because you picked it for being high. The same applies to the validation score of the winning trial: it was selected for being high, so it is not an unbiased final estimate.
Example: 70% training, 15% validation, 15% test. SageMaker automatic model tuning optimizes an objective metric computed on the validation channel; the test set is scored only after the final model is chosen. With small datasets, k-fold cross-validation on the training data can replace a fixed validation split, but the test set is still kept separate.
W: Separate training, validation and test sets: hyperparameters are chosen on validation data, so the untouched test set gives an unbiased final performance estimate.
X: A=Validation score as final estimate: the hyperparameters were picked because they scored best on the validation set, so that score is optimistic; a separate test set is needed for the final estimate.
B=One dataset for everything: the model is trained, tuned and scored on the same rows, so the score measures memorization and says little about new data.
C=Tuned on the test set: selecting hyperparameters by test score leaks test information into model choice, so the final test estimate is biased upward.
T: Tune on validation and touch the test set once at the end; a score used for selection is optimistic as a final estimate.

@ MLA-C01 D1 T1.3 applied comparison
S: A team runs SageMaker Clarify twice: once on the raw training dataset before any model is built, and once after evaluating a trained model's predictions. What is the key difference between these two analysis phases?
A: Pre-training metrics check the dataset; post-training metrics check the model's predictions
B: Post-training bias metrics need a separate tool outside SageMaker to be computed
C: Pre-training metrics analyze image data, while post-training metrics analyze tabular data
D: Both phases compute the same bias metrics, just at different points in the project
K: A
G: ## Two phases of Clarify bias analysis
- **Pre-training bias** looks only at the dataset: the facet (for example gender or age group) and the labels. It asks "is the data itself skewed?". Metrics include Class Imbalance (CI), Difference in Proportions of Labels (DPL) and KL divergence. No model is needed.
- **Post-training bias** looks at a trained model's predictions compared with labels across facet groups. It asks "does the model treat groups differently?". Metrics include Difference in Positive Proportions in Predicted Labels (DPPL), Disparate Impact (DI) and differences in accuracy or recall between groups. Clarify runs the model (or a shadow endpoint) to get predictions.
## Why run both
Biased data can produce a biased model, but a model can also amplify or reduce bias present in the data. Comparing the two runs shows where a disparity comes from, and post-training bias can be monitored in production through Model Monitor.
W: Dataset versus predictions: pre-training metrics measure imbalance in the data and labels before any model exists, while post-training metrics measure how the trained model's predictions differ across groups.
X: B=Separate tool for post-training: Clarify computes post-training bias metrics itself as a processing job, and they can also be monitored in production.
C=Images versus tabular: the two phases differ in what they analyze (data versus predictions), not in data type; Clarify's bias metrics are designed for tabular data in both phases.
D=Same metrics at two times: each phase has its own metric set, such as CI and DPL before training and DPPL and DI after it.
T: Pre-training bias = skew in the data; post-training bias = skew in the model's predictions.

@ MLA-C01 D2 T2.2 advanced use-case
S: A 30-billion-parameter model does not fit into the memory of a single GPU, even with batch size 1. Which training approach is required?
A: Distributed data parallelism across more GPU instances.
B: Model parallelism or fully sharded data parallelism.
C: Increasing the EBS volume size of the training instance.
D: Using a larger learning rate with gradient clipping.
K: B
G: ## Why a large model does not fit on one GPU
Training memory is much more than the weights. For each parameter you also store gradients and optimizer state. A common rule of thumb for Adam in mixed precision is about 16 bytes per parameter (16-bit weights and gradients plus 32-bit master weights and two Adam moments). A 30-billion-parameter model therefore needs on the order of 480 GB before activations, far more than the memory of any single GPU.
## Two families of parallelism
- **Data parallelism** copies the full model to every GPU and gives each a different slice of the batch. It speeds up training but each GPU must still hold the entire model.
- **Model parallelism** splits the model itself: pipeline parallelism places different layers on different GPUs, and tensor parallelism splits individual layers.
- **Fully sharded data parallelism** (FSDP, or sharded data parallelism in the SageMaker model parallelism library) shards parameters, gradients and optimizer state across GPUs and gathers them only when needed.
W: Model parallelism or FSDP: both spread the model's memory across many GPUs, which is what makes training possible when one full copy of the model does not fit even at batch size 1.
X: A=Plain data parallelism: every worker still needs a full replica of the model, so adding instances does not solve an out-of-memory error for the model itself.
C=Larger EBS volume: EBS is disk storage for data and checkpoints; it does not add GPU memory, which is where the model must live during training.
D=Larger learning rate with clipping: these settings change optimization speed and stability, not memory usage, so the model still cannot be loaded.
T: When the model itself is too big for one GPU, split the model (model parallel or sharded data parallel); plain data parallelism splits only the data.

@ MLA-C01 D2 T2.3 advanced tradeoff
S: A delivery-time model is evaluated for a business where large errors (late by hours) are far more costly than many small errors. Which evaluation metric best reflects this preference?
A: Mean absolute error (MAE).
B: Root mean squared error (RMSE).
C: Mean absolute percentage error (MAPE).
D: F1 score.
K: B
G: ## How regression error metrics weigh mistakes
MAE, MAPE and RMSE all measure how far predictions are from actual values, but they treat large errors differently.
- **MAE** (mean absolute error) averages the absolute errors. An error of 60 minutes counts exactly six times as much as an error of 10 minutes.
- **MAPE** (mean absolute percentage error) averages each absolute error divided by the actual value. It is still linear in the size of each error, and it weighs a miss on a short delivery more than the same miss on a long one.
- **RMSE** (root mean squared error) squares each error before averaging and then takes the square root. Squaring makes large errors dominate.
Example: two models each have total absolute error of 60 minutes across six deliveries. Model 1 is off by 10 minutes on every delivery (MAE 10, RMSE 10). Model 2 is perfect on five and off by 60 minutes on one (MAE 10, RMSE about 24.5). MAE cannot tell them apart; RMSE clearly penalizes the model with the single large miss.
W: RMSE: squaring errors makes a few hours-late predictions weigh much more than many small errors, matching a business where big misses are far more costly.
X: A=MAE: it weights all errors linearly, so it treats one large error the same as several small ones that add up to the same total and does not reflect the higher cost of big misses.
C=MAPE: it is also linear in each error, only scaled by the actual delivery time, so one large miss does not dominate and short deliveries get extra weight instead.
D=F1 score: F1 combines precision and recall for classification and has no meaning for a continuous time prediction.
T: When large errors hurt disproportionately, choose RMSE, which squares errors; MAE and MAPE weigh each unit of error linearly.

@ MLA-C01 D1 T1.2 applied use-case
S: Two features are highly correlated and cause unstable coefficients in a linear model. Which approach helps?
A: Convert both features into categorical text strings
B: Increase the learning rate so the optimizer converges faster
C: Remove one feature, combine them, or apply regularization
D: Duplicate both features to strengthen the shared signal
K: C
G: ## Multicollinearity
Two features are collinear when one is nearly a linear function of the other, for example `house_size_sqft` and `house_size_m2`, or `total_spend` and `num_orders x average_order`.
In a linear model, the effect can be split between them in countless ways: 10 and 0, 5 and 5, or 100 and -90 all give similar predictions. Small data changes then swing the coefficients wildly and they become hard to interpret, even if overall predictions look fine.
## Remedies
- **Drop one** of the pair (check with a correlation matrix or variance inflation factor, VIF).
- **Combine** them into one feature (a ratio, a sum, or a principal component from PCA).
- **Regularize**: L2 (ridge) shrinks correlated coefficients toward similar, small values; L1 (lasso) tends to keep one and zero the other. SageMaker Linear Learner supports both through `wd` (L2) and `l1` hyperparameters.
W: Remove, combine or regularize: each removes the redundancy or penalizes large offsetting coefficients, so the estimates become stable.
X: A=Convert to text strings: turning numbers into strings discards their numeric meaning and would require encoding again; it does not address the correlation.
B=Increase the learning rate: the learning rate changes how fast the optimizer moves; collinearity is a property of the data, and a higher rate can even make training unstable.
D=Duplicate both features: exact copies are perfectly collinear, which makes the coefficient instability worse, not better.
T: Fix collinear features by dropping, combining or regularizing them; optimizer settings and duplication do not change the redundancy.

@ MLA-C01 D1 T1.2 advanced tradeoff
S: A dataset feature contains a small number of extreme outliers alongside mostly well-behaved values. The team applies min-max normalization and finds that most values are compressed into a very narrow range near 0, reducing the feature's discriminative power for modeling. What is the best explanation and remedy for this issue?
A: The outliers set the global min and max, so use standard or robust scaling instead
B: Min-max isn't affected by outliers, so the outliers must be data entry errors
C: This is the expected result, since normalization compresses values toward zero
D: The issue comes from too many decimal places and is fixed by rounding the values
K: A
G: ## Why outliers break min-max scaling
Min-max uses `(x - min) / (max - min)`, so the entire scale is set by the two most extreme values.
Example: most values are between 10 and 100, but one value is 100,000. After scaling, 10 becomes about 0 and 100 becomes about 0.0009, while the outlier becomes 1. Almost all the data now sits in a tiny band near 0, and the model can barely tell those values apart.
## Remedies
- **Standardization** (`(x - mean) / std`) is not bounded, so outliers do not force all other values into a fixed range, though they still affect the mean and standard deviation.
- **Robust scaling** uses the median and the interquartile range, `(x - median) / IQR`, which outliers barely influence.
- **Clipping or winsorizing** caps extreme values (for example at the 1st and 99th percentiles) before scaling, and a **log transform** can reduce heavy right skew.
W: Outliers set the min and max: a few extreme values stretch the range, compressing everything else near 0, so switching to standard or robust scaling (or clipping first) restores useful spread.
X: B=Min-max is not affected by outliers: min-max depends directly on the minimum and maximum, so it is the scaler most affected by outliers, and outliers are not necessarily entry errors.
C=Expected compression toward zero: with well-behaved data min-max spreads values evenly across 0 to 1; the compression happens here because of the extreme values.
D=Too many decimal places: precision is not the cause; rounding would actually merge the compressed values further and lose even more information.
T: Min-max scaling is dominated by extreme values; use robust scaling, standardization or clipping when a feature has outliers.

@ MLA-C01 D3 T3.2 applied use-case
S: A team needs Pipelines steps to reuse results when inputs have not changed, to save time. Which feature fits?
A: S3 lifecycle rules on pipeline outputs
B: Endpoint auto scaling policies
C: Step caching with CacheConfig
D: CloudWatch alarm actions
K: C
G: ## Step caching in SageMaker Pipelines
A SageMaker pipeline is a graph of steps such as processing, training and evaluation. Rerunning the whole graph after a small change repeats work that has not changed.
With **step caching**, you attach a `CacheConfig` to a step, for example `CacheConfig(enable_caching=True, expire_after="P30D")`. When the pipeline runs, SageMaker looks for an earlier successful run of the same step with the same arguments (inputs, parameters, image, instance settings) within the expiry window.
- **Cache hit**: the step is skipped and its previous outputs are reused.
- **Cache miss**: the step runs normally, for example because the input data location or a hyperparameter changed.
Example: you change only the evaluation threshold. The expensive data preparation and training steps hit the cache, and only evaluation runs again.
W: Step caching: it reuses earlier outputs when a step's arguments have not changed, saving both time and compute.
X: A=S3 lifecycle rules: they move or expire objects between storage classes over time; they do not decide whether a pipeline step needs to run.
B=Endpoint auto scaling: it changes the number of inference instances behind an endpoint based on load and has no effect on pipeline execution.
D=CloudWatch alarm actions: they react when a metric crosses a threshold; they cannot detect unchanged inputs or skip pipeline steps.
T: To skip unchanged work in SageMaker Pipelines, enable step caching; storage, scaling and alarm features do not affect which steps run.

G: ## Feature attribution drift
Feature attribution explains how much each feature contributes to predictions. SageMaker Clarify computes this with SHAP values.
**Feature attribution drift monitoring** (a Model Monitor job type using Clarify) works like this:

- On a schedule, attributions are computed on captured live traffic.
- The rankings are compared (Clarify uses an NDCG score), and a large drop is reported as a violation and can be published as a CloudWatch metric.
Example: after a marketing change, `age` becomes the most important feature. The data may still pass data quality checks, but the model is now relying on different signals, which is worth investigating.
W: Feature attribution drift monitoring: it compares live feature importance with the baseline ranking and reports when the drivers of predictions change.

C=IAM Access Analyzer: it finds resources shared outside the account and helps validate policies; it has no view of model behavior.
