@ MLA-C01 D1 T1.1 advanced comparison
S: An organization already operates a self-managed Apache Kafka cluster on-premises for streaming ingestion and wants to move this workload to AWS with minimal operational overhead for cluster management while retaining the Kafka API. Which AWS service should they choose over building a new solution on Kinesis Data Streams?
A: Amazon Redshift streaming ingestion
B: Amazon Data Firehose streams
C: AWS Glue Data Catalog tables
D: Amazon MSK provisioned clusters
K: D
G: ## Managed Kafka on AWS
**Amazon Managed Streaming for Apache Kafka (Amazon MSK)** runs open-source Apache Kafka for you.
- **MSK provisioned** manages brokers, KRaft or ZooKeeper nodes, patching and failure replacement; you choose broker size and count.
- **MSK Serverless** removes capacity planning entirely.
- The Kafka API is unchanged, so existing producers, consumers, Kafka Connect connectors and Kafka Streams apps only need new bootstrap broker addresses (and authentication settings).
## Why not rebuild on Kinesis
Kinesis Data Streams is a different API (shards, `PutRecords`, KCL). Moving Kafka workloads to it means rewriting every producer and consumer. When the goal is "keep the Kafka API, drop the cluster operations", MSK is the direct fit; tools such as Kafka MirrorMaker 2 can copy topics from the on-premises cluster during migration.
W: Amazon MSK: Amazon Managed Streaming for Apache Kafka provides managed Apache Kafka that keeps the Kafka API, so the on-premises producers and consumers move with minimal change while AWS runs the brokers.
X: A=Redshift streaming ingestion: this lets Redshift consume from Kinesis or MSK into materialized views; it is a destination for a stream, not a Kafka cluster that producers can write to.
B=Data Firehose streams: Amazon Data Firehose delivers streams to destinations such as S3 or Redshift, but it does not expose the Kafka protocol, so Kafka clients cannot produce to or consume from it.
C=Glue Data Catalog tables: the catalog stores table metadata for data lakes and does not ingest or transport any streaming data.
T: Existing Kafka plus low operations means Amazon MSK; Kinesis or Firehose would force a rewrite of every Kafka client.
V: Amazon MSK, Amazon Kinesis Data Streams

@ MLA-C01 D1 T1.3 applied use-case
S: Rather than simply duplicating existing minority-class records, a data scientist wants to generate new, synthetic minority-class examples by interpolating between existing minority-class data points and their nearest neighbors in feature space. Which well-known technique does this describe?
A: Principal component analysis
B: Random undersampling
C: SMOTE oversampling
D: One-hot encoding
K: C
G: ## SMOTE step by step
SMOTE (Synthetic Minority Over-sampling Technique) adds new minority examples instead of copying existing ones:
- Pick a minority example `x`.
- Find its k nearest minority-class neighbors (k is often 5) and pick one, `x_nn`.
- Create a new point on the line between them: `x_new = x + λ × (x_nn - x)`, with `λ` random between 0 and 1.
Example: minority points at (1, 2) and (3, 6) with `λ = 0.5` give a new point (2, 4).
## Why this helps
The synthetic points fill the region around the minority class, so the classifier learns a broader decision region instead of memorizing a few duplicated rows. SMOTE is applied to training data only, and works on numeric features; variants such as SMOTE-NC handle categorical ones.
W: SMOTE: the Synthetic Minority Over-sampling Technique generates synthetic minority examples by interpolating between existing minority points and their nearest neighbors in feature space, exactly as described.
X: A=PCA: principal component analysis reduces the number of features by projecting data onto directions of highest variance; it does not create new rows or change class balance.
B=Random undersampling: it balances classes by removing majority examples, the opposite of generating new minority examples.
D=One-hot encoding: it converts categorical values into 0/1 columns; it changes how features are represented, not how many examples each class has.
T: Interpolate between minority neighbors to create new samples: SMOTE; remove majority samples: undersampling.

@ MLA-C01 D4 T4.2 applied use-case
S: A ML platform team wants to break down and visualize monthly SageMaker costs by individual project team, using cost allocation tags applied to training jobs and endpoints. Which service should they use to analyze this cost data over time?
A: SageMaker Model Registry
B: Amazon CloudWatch metrics
C: AWS Cost Explorer reports
D: AWS X-Ray service maps
K: C
G: ## Cost allocation tags
A tag is a key-value pair on a resource, such as `project=fraud-detection`. SageMaker training jobs, endpoints, notebooks and other resources can be tagged. To use a tag in billing data, an administrator **activates** it as a cost allocation tag in the Billing and Cost Management console. From then on, usage carries that tag in cost data; earlier months are not tagged unless a backfill is requested.
## AWS Cost Explorer
Cost Explorer shows cost and usage over time, by day or month, with filters and groupings. Grouping by the `project` tag and filtering by the service SageMaker gives a chart and a table of monthly SageMaker spend per project team.
- Example: `project=churn` spent a certain amount on training this month while `project=search` spent most of its budget on endpoints.
- Untagged spend appears as its own group, which helps find resources missing tags.
W: AWS Cost Explorer: once the project tag is activated for cost allocation, Cost Explorer can group SageMaker spend by that tag and chart it month by month.
X: A=Model Registry: the Model Registry catalogs model versions, their metadata and approval status; it does not hold any billing or cost data.
B=CloudWatch metrics: CloudWatch tracks operational metrics such as invocations, latency and CPU use; it does not break down dollar costs by cost allocation tag.
D=X-Ray service maps: X-Ray traces requests through distributed applications to find latency and errors; it has no view of billing or project-level spend.
T: Cost per team needs activated cost allocation tags plus a billing tool such as Cost Explorer; operational tools like CloudWatch and X-Ray do not see costs.
V: AWS Cost Explorer, SageMaker

@ MLA-C01 D4 T4.3 applied use-case
S: A healthcare company must ensure that data stored in a SageMaker Feature Store and all training job output artifacts are encrypted at rest using a customer-managed key they control, rather than an AWS-managed default key. Which service or feature should they configure?
A: AWS Secrets Manager with scheduled rotation
B: AWS KMS keys passed in each job's KmsKeyId
C: AWS Certificate Manager certificates
D: Amazon Macie sensitive data discovery
K: B
G: ## Encryption keys in SageMaker
SageMaker encrypts data at rest by default, using AWS managed keys. When a company must control the key itself (its key policy, rotation, and the ability to disable it), it creates an AWS KMS **customer managed key** and passes its ID or ARN in the resource configuration.
- **Feature Store**: `KmsKeyId` in the offline store's S3 storage configuration and in the online store's security configuration.
- **Training jobs**: `KmsKeyId` in `OutputDataConfig` for model artifacts, and `VolumeKmsKeyId` in `ResourceConfig` for the attached storage volumes.
- Endpoints and processing jobs have similar key settings.
## Key policy matters
The execution role that runs the job must be allowed to use the key (for example `kms:Decrypt` and `kms:GenerateDataKey`), and every use of the key is logged in CloudTrail.
W: KMS customer managed keys in SageMaker settings: specifying the company's own KMS key in the Feature Store and training job settings (`KmsKeyId`) encrypts the feature data and output artifacts with a key the company controls.
X: A=Secrets Manager rotation: Secrets Manager stores and rotates secrets such as database passwords; it does not encrypt Feature Store data or training artifacts.
C=Certificate Manager: ACM issues and manages TLS certificates for encryption in transit, not the at-rest keys used for stored data.
D=Macie data discovery: Macie discovers and reports sensitive data in S3; it does not encrypt anything.
T: Encryption at rest with a key you control means a KMS customer managed key set in each SageMaker resource's configuration; ACM and Secrets Manager solve other problems.
V: AWS KMS, SageMaker

@ MLA-C01 D4 T4.3 applied use-case
S: Applications in a VPC must call a SageMaker endpoint without traversing the internet. Which feature fits?
A: An AWS PrivateLink interface endpoint for the SageMaker Runtime API
B: A public IP address on each instance that calls the SageMaker endpoint
C: A NAT gateway route for the subnets that call the SageMaker endpoint
D: An internet gateway route from the VPC subnets to the SageMaker API
K: A
G: ## Invoking an endpoint privately
Applications call a SageMaker endpoint through the **SageMaker Runtime** API (`InvokeEndpoint`). By default that API is reached at a public regional address, so instances in private subnets would need an internet path.
An **interface VPC endpoint** (AWS PrivateLink) for the service `com.amazonaws.<region>.sagemaker.runtime` places network interfaces with private IPs in your subnets.
- With private DNS enabled, the normal runtime hostname resolves to those private IPs, so application code does not change.
- Security groups on the endpoint control which clients can connect.
- An endpoint policy, or an IAM condition such as `aws:SourceVpce`, can restrict which endpoints may be invoked or require that calls come through the VPC endpoint.
Example: a Lambda function in private subnets invokes a fraud model with no NAT gateway or internet gateway in the VPC.
W: Interface VPC endpoint for SageMaker Runtime: it gives the VPC a private path to `InvokeEndpoint`, so calls never need an internet route.
X: B=Public IPs on clients: this makes the instances reachable from the internet and sends calls to the public API address, increasing exposure.
C=NAT gateway route: a NAT gateway forwards traffic to the public service address through an internet gateway, which is the internet path the requirement wants to avoid.
D=Internet gateway route: routing subnets to an internet gateway turns them into public subnets and sends the calls over the internet rather than keeping them private.
T: Private calls to SageMaker endpoints use an interface VPC endpoint for SageMaker Runtime; NAT, internet gateways and public IPs all rely on internet routing.
V: AWS PrivateLink

@ MLA-C01 D4 T4.3 applied use-case
S: Which feature restricts a SageMaker training container from making any outbound network calls, even inside a VPC?
A: Warm pools kept for the training cluster
B: Network isolation (EnableNetworkIsolation)
C: Managed Spot Training for the job
D: Checkpointing of job state to Amazon S3
K: B
G: ## Network isolation for SageMaker jobs
Setting `EnableNetworkIsolation` to true on a training job (or model) stops the container from making any outbound network calls: no internet, no calls to AWS services, and no calls to other hosts in the VPC.
- SageMaker itself still copies the training input from S3 into the container and uploads the model artifacts to S3 afterward, so the job works without the container needing network access.
- This matters when running third-party or untrusted algorithm code (for example from AWS Marketplace): even if the code tries to send data out, it has no network.
## Difference from a VPC configuration
Putting a job in a VPC controls **where** traffic can go (subnets, security groups, endpoints). Network isolation removes the container's network access entirely.
## Example
A partner's proprietary training container processes sensitive data. With network isolation enabled, any attempt from the code to reach an external server fails, while training data still arrives in `/opt/ml/input/data`.
W: Network isolation: it blocks all outbound connections from the container, even inside a VPC, while SageMaker handles input download and artifact upload for it.
X: A=Warm pools: warm pools keep provisioned instances alive after a job so the next job starts faster. They change startup time, not network access.
C=Managed Spot Training: spot training runs on spare capacity to cut cost and may be interrupted. It has no effect on what the container can reach on the network.
D=Checkpointing to S3: checkpoints save training progress so jobs can resume after interruption. Writing checkpoints actually uses a data path to S3 rather than restricting it.
T: To stop a training container from calling out anywhere, enable network isolation; a VPC alone only shapes where traffic may go.
V: Amazon SageMaker AI

@ MLA-C01 D1 T1.3 applied use-case
S: A company has 400 S3 buckets from many teams and plans to reuse their data for ML training. Nobody knows which buckets contain personal data such as passport numbers or credit card numbers. The security team wants an automated, managed way to find and report sensitive data across the buckets. Which service fits BEST?
A: Amazon GuardDuty S3 Protection turned on for each account's buckets
B: Amazon Macie scans that use managed data identifiers on the objects
C: Amazon Inspector scans configured for the accounts that own the buckets
D: AWS Config managed rules that evaluate each bucket's configuration
K: B
G: ## Finding sensitive data before training
Before data is used for ML, you need to know whether it contains personal or regulated data, so you can remove, mask or protect it. Checking hundreds of buckets by hand does not scale.
## What Amazon Macie does
Macie inspects the contents of S3 objects with managed data identifiers (for example credit card numbers, passport numbers, bank account numbers, names and addresses in many countries) and custom identifiers you define with regular expressions.
- **Automated sensitive data discovery** samples objects across all buckets continuously and gives each bucket a sensitivity score.
- **Sensitive data discovery jobs** do a targeted, deeper scan of chosen buckets.
- Findings go to the Macie console, EventBridge and Security Hub, so they can trigger remediation.
Macie also reports bucket-level risks such as public access or missing encryption.
W: Amazon Macie: automated sensitive data discovery and discovery jobs scan S3 object contents for personal and financial data with managed identifiers and report which buckets hold it, which is exactly the discovery task.
X: A=GuardDuty S3 Protection: it detects suspicious access patterns to S3 from CloudTrail data events, such as unusual API calls. It does not read object contents to find personal data.
C=Amazon Inspector: it scans EC2 instances, container images and Lambda functions for software vulnerabilities, not S3 objects for personal data.
D=AWS Config rules: they check resource configuration, such as whether encryption or versioning is on, not what data the objects contain.
T: To discover personal data inside S3 objects use Macie; GuardDuty watches access behavior, Config checks settings, Inspector finds vulnerabilities.
V: Amazon Macie, Amazon S3
