@ SC-900 D1 T1.1 advanced comparison
S: A manufacturer runs a legacy app on Azure virtual machines, a new API on Azure App Service and its email on Microsoft 365. The board wants a single list of the security duties the company keeps in all three, so that no budget line is cut by mistake after the move. According to the shared responsibility model, which THREE responsibilities stay with the company in every one of these service models? (Select THREE)
A: Classifying and protecting the company's own data, including deciding what is sensitive and how it must be encrypted.
B: Securing the laptops, tablets and phones that employees use to connect to the cloud services and the company's data.
C: Managing user accounts, authentication methods and access permissions, such as requiring MFA and removing leavers' access.
D: Patching the operating system of the servers that run each workload, because the company deploys the code that runs there.
E: Protecting the physical hosts and datacenter network, because the company still chooses the Azure region that holds the workloads.
F: Maintaining the web server and runtime middleware under each application, because the company chose which language framework to use.
K: A,B,C
G: ## What moves to the provider, and what never does
The shared responsibility model splits security duties between the customer and the cloud provider. As a workload moves from on-premises to **IaaS**, then **PaaS**, then **SaaS**, the provider takes on more layers:
- In **IaaS** (Azure VMs) the provider runs the physical datacenter, hosts and network; the customer still patches the guest operating system, middleware and applications.
- In **PaaS** (App Service) the provider also runs the operating system and runtime; the customer owns the code, configuration, identities and data.
- In **SaaS** (Microsoft 365) the provider runs almost everything, including the application.
## Responsibilities you always retain
Learn lists duties that stay with the customer **regardless of the model**: data (classification, protection, encryption decisions), endpoints (laptops, phones, desktops), identities and access (accounts, authentication methods, permissions), and configuration choices in the tenant.
## Example
Even if all mail moves to Microsoft 365, a stolen password on a user's phone still exposes the mailbox: the account and the device are the company's job.
W: A=Data classification and protection: data is listed by Learn as a responsibility the customer always retains, in IaaS, PaaS and SaaS alike.
B=Endpoints: the client devices that reach the cloud services are always secured by the customer, whatever the service model.
C=Accounts and access: managing identities, authentication methods and permissions stays with the customer in every model.
X: D=Operating system patching: the customer patches the guest OS only in IaaS; in App Service and Microsoft 365 the provider manages the operating system.
E=Physical hosts and datacenter network: physical security is the provider's job in every cloud model; choosing a region does not move it to the customer.
F=Web server and runtime middleware: in PaaS and SaaS the provider runs the runtime; only the IaaS workload leaves middleware to the customer.
T: Data, endpoints and identities/access stay with the customer in IaaS, PaaS and SaaS; physical infrastructure never does, and OS and runtime shift to the provider.
V: Shared responsibility model

@ SC-900 D1 T1.1 advanced use-case
S: An insurer already has strong MFA for all staff and a firewall at its internet edge. A penetration test shows that once the testers controlled one web server, they could connect directly to every database server in the same flat network. The security lead wants to close this gap at the layer the testers exploited, without rewriting the applications. Which defense-in-depth control addresses that specific layer?
A: Divide the network into separate zones for web and database servers and allow only the required ports between those zones.
B: Add DDoS protection in front of the public endpoints so that large floods of attack traffic are filtered before they arrive.
C: Require phishing-resistant authentication methods for every administrator who signs in to the web or database servers.
D: Turn on encryption at rest for every database file so that stolen disks or backups cannot be read by anyone outside the company.
K: A
G: ## Layers of defense in depth
Defense in depth stacks several independent controls so that one failure does not expose everything. Learn describes these layers from the outside in:
- **Physical security**: buildings, badges, cameras.
- **Identity and access**: MFA, RBAC, Conditional Access.
- **Perimeter**: DDoS protection that filters large-scale attacks at the network boundary.
- **Network**: segmentation into isolated zones and rules that limit communication between them.
- **Compute**: patched VMs and containers, closed ports.
- **Application**: secure code and input validation.
- **Data**: access controls and encryption for the information itself.
## Which layer failed here?
The testers moved **sideways inside** the network: from a web server to the database servers. That is lateral movement, and the layer that limits it is **network** security. Segmentation means a compromise in one zone does not open every other zone.
W: Network segmentation between zones: splitting web and database servers into zones with only required ports open is the network-layer control that stops a compromised web server from reaching every database.
X: B=DDoS protection: this is the perimeter layer and stops volumetric floods from outside; it does nothing about an attacker already inside moving between servers.
C=Phishing-resistant admin sign-in: this strengthens the identity layer, but the testers did not sign in; they connected over an open network path.
D=Encryption at rest: this protects stored data on disks and backups, yet a live connection from a compromised server can still query the database.
T: Lateral movement inside a flat network is a network-layer gap, closed by segmentation that limits traffic between zones.
V: Defense in depth

@ SC-900 D1 T1.1 advanced use-case
S: A retailer rewrites its access rules. First, every request to a business app must be evaluated using the user's identity, location and device health, even when the device is on the office network. Second, contractors will receive access to only the one app their contract covers, and only until the contract ends. Which TWO Zero Trust guiding principles do these two rules apply? (Select TWO)
A: Verify explicitly, because every access decision is based on all available data points instead of on the network the request came from.
B: Use least privilege access, because users get just-in-time and just-enough access that is limited both in scope and in time.
C: Assume breach, because the company minimizes blast radius by segmenting access and using analytics to detect threats as they happen.
D: Trust the corporate network, because devices that are already on the office network have passed the perimeter and need fewer checks.
E: Defense in depth, because the company adds a second firewall layer at the perimeter to stop contractors from reaching other apps.
K: A,B
G: ## The three guiding principles of Zero Trust
Zero Trust replaces "trust everything inside the network" with "never trust, always verify". Microsoft describes three guiding principles:
- **Verify explicitly**: always authenticate and authorize based on all available data points, such as user identity, location, device health, service or workload, data classification and anomalies.
- **Use least privilege access**: limit user access with just-in-time and just-enough-access (JIT/JEA), risk-based adaptive policies and data protection.
- **Assume breach**: minimize blast radius and segment access, verify end-to-end encryption, and use analytics to gain visibility and drive threat detection.
## Mapping rules to principles
A rule that checks identity, location and device health on every request, **regardless of network**, is verify explicitly. A rule that limits contractors to one app and to the contract period is just-enough and just-in-time access, which is least privilege.
W: A=Verify explicitly: evaluating identity, location and device health for every request, even on the office network, is the definition of verifying explicitly.
B=Use least privilege access: one app only (just enough) and only until the contract ends (just in time) is least privilege.
X: C=Assume breach: segmentation and threat analytics are a real principle, but neither rule describes limiting blast radius or detecting threats.
D=Trust the corporate network: this is the old perimeter model that Zero Trust rejects; the first rule explicitly checks devices on the office network too.
E=Defense in depth: it is a layered security strategy, not one of the three Zero Trust guiding principles, and neither rule adds a firewall.
T: Checking every request against all signals is verify explicitly; limiting access in scope and time is least privilege.
V: Zero Trust

@ SC-900 D1 T1.2 advanced comparison
S: A hospital's security team reviews five controls that protect its patient portal. It wants to label each one correctly before an audit, because the auditor will test proof-of-identity controls separately from controls that decide what a proven identity may do. Which TWO of the following are authorization controls rather than authentication controls? (Select TWO)
A: A role assignment that gives the billing team read access to invoices in the portal's database and nothing else in it.
B: A SharePoint permission level that lets ward managers edit staffing documents but only view the policy documents.
C: A FIDO2 security key that a nurse touches after typing her user name, which proves she holds the registered key.
D: A one-time code from the Microsoft Authenticator app that a doctor enters after his password at each new sign-in.
E: A password complexity rule that requires long passwords so that the identity proof at sign-in is harder to guess.
K: A,B
G: ## Authentication versus authorization
- **Authentication (AuthN)** proves that someone is who they claim to be. Passwords, one-time codes, security keys, biometrics and certificates are all ways to authenticate.
- **Authorization (AuthZ)** happens after authentication and decides **what level of access** the authenticated identity has: which data it can read, which actions it can take.
## A simple test
Ask: "Does this control help prove who the user is, or does it decide what the user may do?" Anything a user presents at sign-in is authentication. Anything that grants or limits permissions on a resource (roles, permission levels, access control lists) is authorization.
## Example
A doctor signs in with a password and an Authenticator code (authentication). The portal then lets him read his own patients' records but not edit billing (authorization).
W: A=Role assignment for billing: it decides what the authenticated billing team can do (read invoices only), which is authorization.
B=SharePoint permission level: edit versus view rights on documents are permissions granted after sign-in, so this is authorization.
X: C=FIDO2 security key: touching a registered key proves the nurse's identity during sign-in, which is authentication.
D=Authenticator one-time code: a code entered after the password is a second authentication factor, not a permission.
E=Password complexity rule: it makes the identity proof harder to guess; it does not decide what the user can access.
T: Anything presented to prove identity is authentication; anything that grants or limits what an identity can do is authorization.
V: Authentication, Authorization

@ SC-900 D1 T1.2 advanced use-case
S: A biotech firm gives researchers from a partner university access to its lab-results web app. The university insists that its staff keep using their own university credentials, and the firm's legal team insists that the firm must never store or reset those people's passwords. When a researcher leaves the university, access must end without the firm doing anything. Which approach meets both demands?
A: Set up federation so the firm's app trusts sign-in tokens issued by the university's identity provider for its own staff.
B: Create local accounts in the firm's directory for each researcher and copy their current university passwords into them.
C: Synchronize the university's directory into the firm's on-premises Active Directory every night and let researchers sign in there.
D: Issue one shared service account to the university's research group and rotate its password whenever a researcher leaves.
K: A
G: ## What federation does
**Federation** is a trust relationship between identity providers. The resource side (the firm's app or identity provider) agrees to accept tokens that a **different** identity provider (the university's) issues after it authenticates its own users.
- The user authenticates at the **home** identity provider with home credentials.
- The resource side never sees or stores the password; it receives a signed token with claims.
- When the home organization disables the account, the user can no longer get tokens, so access ends at the resource too.
## Why the alternatives fail
Copying or synchronizing accounts creates a second set of credentials or objects the firm must manage, and shared accounts break individual accountability.
W: Federation with the university's identity provider: researchers authenticate at the university, the firm only receives tokens, and a disabled university account stops access automatically.
X: B=Local accounts with copied passwords: the firm would store passwords, which legal forbids, and the copies stay valid after a researcher leaves.
C=Nightly directory synchronization: this copies university accounts into the firm's own directory, which the firm then manages, and access can linger until the next sync.
D=Shared service account: no one is individually identified, the firm must manage its password, and every rotation affects all remaining researchers.
T: Federation lets a resource trust another organization's identity provider, so users keep home credentials and lose access when the home account is disabled.
V: Federation, Identity provider

@ SC-900 D2 T2.1 advanced use-case
S: A dev team's GitHub Actions workflow deploys infrastructure to Azure several times a day. Today it signs in with a client secret stored in the repository's secrets, and auditors flagged that the secret has not been rotated in two years. The team wants no long-lived secret anywhere and does not want to run its build agents inside Azure. Which Microsoft Entra capability meets these needs?
A: Configure workload identity federation so an app registration or user-assigned managed identity trusts tokens that GitHub issues to the workflow.
B: Assign a system-assigned managed identity to the GitHub repository so that Azure issues tokens to the workflow without any secret.
C: Replace the client secret with a certificate credential on the app registration and store the private key as a repository secret.
D: Create a dedicated user account for the pipeline, exclude it from MFA, and store its password in an Azure Key Vault that the workflow reads.
K: A
G: ## Workload identities and their credentials
A **workload identity** is an identity for software: an application, service or script. In Microsoft Entra these are app registrations (service principals) and managed identities.
- **Managed identities** remove secrets for code running **on Azure resources**; Azure handles the credential.
- Code that runs **outside Azure** (GitHub Actions, Kubernetes elsewhere, AWS, Google Cloud) traditionally used a client secret or certificate, which must be stored and rotated.
## Workload identity federation
With **workload identity federation** you configure a user-assigned managed identity or an app registration to **trust tokens from an external identity provider**, such as GitHub. The workflow presents its GitHub-issued token, exchanges it for a Microsoft Entra access token, and no secret is stored anywhere. Learn lists GitHub Actions as a supported scenario.
W: Workload identity federation: the identity trusts GitHub's tokens for that workflow, so the pipeline gets Entra access tokens without any stored secret and without running in Azure.
X: B=System-assigned managed identity on the repository: system-assigned identities are tied to an Azure resource; a GitHub repository is not an Azure resource and cannot hold one.
C=Certificate credential stored as a repository secret: a certificate is still a long-lived credential that sits in the repository and must be rotated.
D=Pipeline user account excluded from MFA: this adds a password-based human-style account with weakened protection, the opposite of removing long-lived secrets.
T: For workloads outside Azure, workload identity federation replaces stored secrets with trust in the external platform's tokens.
V: Microsoft Entra Workload ID, Managed identities

@ SC-900 D2 T2.1 advanced use-case
S: A logistics startup opens a new branch with forty corporate-owned Windows laptops. It has no on-premises servers or domain controllers anywhere, and IT wants staff to sign in to the laptops with their Microsoft Entra work accounts and get single sign-on to cloud apps. Devices must be manageable by the organization rather than personally owned. Which device identity option fits?
A: Microsoft Entra joined, which joins organization-owned devices directly to Microsoft Entra ID so users sign in with their work accounts.
B: Microsoft Entra hybrid joined, which joins the laptops to an on-premises domain first and then registers them with Microsoft Entra ID.
C: Microsoft Entra registered, which adds a work account to a personally owned device so the user can reach company apps and email.
D: Microsoft Entra Domain Services, which hosts managed domain controllers in Azure that the laptops must join over a site-to-site VPN.
K: A
G: ## Three ways a device gets an identity in Microsoft Entra
- **Microsoft Entra registered**: for bring-your-own-device. A user adds a work account to a personal device; the device is known but not owned by the organization.
- **Microsoft Entra joined**: for **organization-owned** devices joined **only** to Microsoft Entra ID. Users sign in to Windows with their Entra work account and get SSO to cloud (and, on the network, on-premises) resources. Learn calls it suitable for both cloud-only and hybrid organizations.
- **Microsoft Entra hybrid joined**: devices joined to an **on-premises Active Directory** domain and also registered with Microsoft Entra ID. This requires on-premises domain controllers.
## Example
A cloud-only branch with no domain controllers cannot hybrid join; Entra join is the natural choice for its corporate laptops.
W: Microsoft Entra joined: it is designed for organization-owned devices in cloud-only organizations, with Windows sign-in using Entra work accounts and SSO to cloud apps.
X: B=Microsoft Entra hybrid joined: hybrid join requires an on-premises Active Directory domain, which this startup does not have.
C=Microsoft Entra registered: registration is for personally owned devices, while these laptops are corporate-owned and must be organization-managed.
D=Microsoft Entra Domain Services: it provides managed domain services for legacy apps in Azure, not the standard way to give laptops a cloud identity, and adds a VPN dependency.
T: Corporate devices in a cloud-only organization are Microsoft Entra joined; hybrid join needs on-premises AD, and registration is for personal devices.
V: Microsoft Entra ID, Device identity

@ SC-900 D2 T2.1 advanced comparison
S: An engineering firm and a supplier both use Microsoft Entra ID and Microsoft Teams. They want to collaborate in a Teams shared channel where each side signs in with its own home account. The firm's identity team has one firm rule: supplier staff must not be added as guest user objects in the firm's directory. Which external collaboration capability fits?
A: B2B direct connect, a mutual two-way trust for Teams shared channels in which external users are not added as guests.
B: B2B collaboration, which invites supplier staff as guest users so they can sign in to the firm's apps with their own credentials.
C: Microsoft Entra External ID for customers, which creates a separate external tenant for consumer sign-up to public-facing applications.
D: Cross-tenant synchronization, which automatically creates and updates supplier users as members of the firm's own Microsoft Entra tenant.
K: A
G: ## Ways to work with people outside your organization
Microsoft Entra External ID covers several scenarios:
- **B2B collaboration**: invite external users; they sign in with their own credentials but appear in your directory as **guest users**.
- **B2B direct connect**: a **mutual, two-way trust** between two Microsoft Entra organizations, used for **Teams Connect shared channels**. Users authenticate in their home organization and receive a token from the resource organization, and **they are not added as guests** to your directory.
- **External ID for customers**: a separate external tenant for consumer and business customers of your public-facing apps.
- **Cross-tenant synchronization**: automates creating users from one tenant in another, typically for organizations under one company.
## Deciding detail
The requirement "no guest objects" plus "Teams shared channel" points straight to B2B direct connect. Both organizations must enable it in their cross-tenant access settings.
W: B2B direct connect: it is built for Teams shared channels between two Entra organizations, with home-account sign-in and no guest objects in the firm's directory.
X: B=B2B collaboration: it meets the home-credential need, but each supplier user becomes a guest object, which breaks the firm's rule.
C=External ID for customers: it is for customer-facing apps with consumer sign-up, not for Teams collaboration with a business partner.
D=Cross-tenant synchronization: it creates supplier users inside the firm's tenant, which is the opposite of keeping them out of the directory.
T: Teams shared channels without guest accounts use B2B direct connect; B2B collaboration always creates guest users.
V: Microsoft Entra External ID

@ SC-900 D2 T2.2 advanced use-case
S: A design agency uses Microsoft Entra ID Free with security defaults turned on, so every user gets MFA prompts. Staff complain about prompts at the office. Management wants MFA required only for sign-ins from outside the office's public IP range, while keeping costs as low as possible. Which change meets the requirement with the LEAST extra licensing?
A: License users for Microsoft Entra ID P1, turn off security defaults, and create a Conditional Access policy that requires MFA outside a named office location.
B: Keep security defaults and add the office IP range as an exclusion inside the security defaults settings so office sign-ins skip MFA.
C: License users for Microsoft Entra ID P2 and create a sign-in risk policy that requires MFA only when ID Protection rates the sign-in as risky.
D: Turn off security defaults and require users to register Windows Hello for Business, which removes MFA prompts from every sign-in at once.
K: A
G: ## Security defaults versus Conditional Access
**Security defaults** are free preconfigured settings: they require all users to register for MFA, protect administrators, and block legacy authentication. They are all-or-nothing: you cannot add exclusions or location rules.
**Conditional Access** is the policy engine for "if this, then that" decisions: for example, if a sign-in comes from outside a named location, require MFA. Learn's licensing table lists Conditional Access in **Microsoft Entra ID P1** (and P2). Risk-based Conditional Access needs **P2**.
## Switching
You must turn off security defaults before you enable Conditional Access policies; the two are not used together.
## Example
A named location "Office" with the agency's public IP range, and a policy "All users, all cloud apps, exclude Office location, grant: require MFA".
W: Entra ID P1 with a location-based Conditional Access policy: P1 is the lowest tier that includes Conditional Access, and a named-location condition requires MFA only away from the office.
X: B=Security defaults with an IP exclusion: security defaults cannot be customized with exclusions or locations; they apply the same way to everyone.
C=Entra ID P2 sign-in risk policy: it costs more than needed and keys on risk, not location, so risky office sign-ins would prompt and safe remote ones would not.
D=Windows Hello for Business everywhere: it changes how users authenticate on their devices but is not a way to apply MFA only to sign-ins outside the office.
T: Location-based MFA needs Conditional Access, which starts at Microsoft Entra ID P1; security defaults cannot be tuned.
V: Microsoft Entra Conditional Access, Security defaults

@ SC-900 D2 T2.2 advanced use-case
S: A semiconductor plant bans personal and company phones on its clean-room floor. Operators sign in to shared terminals whose USB ports and NFC readers are disabled for contamination and security reasons, and each sign-in must still use a second factor. The security team wants a method that Microsoft Entra ID supports natively. Which second-factor method fits these constraints?
A: OATH TOTP hardware tokens that display a new six-digit code every 30 or 60 seconds for the operator to type in.
B: FIDO2 security keys that operators insert into the terminal and touch to complete a phishing-resistant sign-in.
C: Microsoft Authenticator push notifications that operators approve by entering the number shown on the terminal screen.
D: SMS text messages with a one-time code sent to a mobile number that each operator registers during onboarding.
K: A
G: ## Matching an MFA method to the environment
Microsoft Entra ID supports many authentication methods. The right one depends on what the user can carry and what the device can accept:
- **Microsoft Authenticator** and **SMS** need a phone.
- **FIDO2 security keys / passkeys** connect over USB, NFC or Bluetooth to the device.
- **OATH TOTP hardware tokens** are small standalone devices that show a code which changes every 30 or 60 seconds. The user types the code; nothing connects to the computer. Learn says Microsoft Entra ID supports OATH-TOTP SHA-1 and SHA-256 tokens that refresh every 30 or 60 seconds.
## Applying the constraints
No phones rules out Authenticator and SMS. Disabled USB and NFC rules out plugging in or tapping a key. A code you read and type needs no phone and no port.
W: OATH TOTP hardware tokens: they need neither a phone nor a USB/NFC connection, and Microsoft Entra ID supports them as a second factor.
X: B=FIDO2 security keys: they would be the strongest choice normally, but they must connect over USB, NFC or Bluetooth, and the ports and readers are disabled.
C=Authenticator push with number matching: it runs on a phone, and phones are banned on the floor.
D=SMS one-time codes: SMS also requires a phone, and it is one of the weaker methods.
T: When phones are banned and ports are disabled, OATH hardware tokens still provide a supported second factor.
V: Microsoft Entra multifactor authentication

@ SC-900 D2 T2.2 advanced use-case
S: A school district synchronizes staff accounts from on-premises Active Directory to Microsoft Entra ID. Teachers who forget their passwords call the help desk, which is overwhelmed in September. The district wants teachers to reset their own password from a browser at home, and the new password must also work the next morning on domain-joined classroom PCs. Which capability meets both requirements?
A: Self-service password reset with password writeback, which writes the new password back to on-premises Active Directory.
B: Self-service password reset in cloud-only mode, which updates the password in Microsoft Entra ID for the synchronized account.
C: Microsoft Entra Password Protection with the on-premises agent, which blocks weak passwords when teachers change them.
D: A Temporary Access Pass issued by the help desk, which lets teachers sign in once and then register a new password themselves.
K: A
G: ## SSPR for hybrid users
**Self-service password reset (SSPR)** lets users reset or change their password after proving their identity with registered methods, without calling the help desk.
For **synchronized** users, the password of record lives in **on-premises Active Directory**. A reset done only in the cloud would not reach the domain-joined PCs. **Password writeback** (configured with Microsoft Entra Connect Sync or Cloud Sync) writes the new password back to AD DS so it works on premises right away. Learn's licensing table lists "SSPR with writeback" under Microsoft Entra ID P1 and P2.
## Related but different
- **Password Protection** enforces banned password lists; it does not reset passwords.
- **Temporary Access Pass** is a time-limited passcode for onboarding or recovery, issued by an admin.
W: SSPR with password writeback: teachers reset in the browser, and writeback updates on-premises AD so the password works on domain-joined PCs the next day.

Learn: **insider risk analytics** lets you evaluate potential insider risks in your organization **without configuring any insider risk policies**. It helps identify areas of higher user risk and decide the type and scope of policies to configure.
## Policy templates come next
Templates such as Data theft by departing users, Data leaks, and Security policy violations are used once the organization decides to create policies.
W: Insider risk analytics: it gives an organization-level view of potential insider risk before any policy exists, guiding which templates and scope to choose.
X: B=Departing users template: it is a policy, so it is exactly what the works council wants to avoid until need is shown, and it targets departing users only.
C=eDiscovery (Premium) cases: collecting everyone's content is a legal investigation tool and far more intrusive than an aggregate risk view.
D=Activity explorer: it reports labeling activity on content; it is not an insider risk assessment.
T: Insider risk analytics shows where insider risk may be higher before you create any Insider Risk Management policy.
