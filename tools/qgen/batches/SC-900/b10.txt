@ SC-900 D1 T1.1 expert use-case
S: An engineering firm must send CAD archives of several gigabytes each to a manufacturing partner over the internet. The two firms have never exchanged a secret key and cannot meet to do so. The partner must be able to confirm that each archive really came from the engineering firm and was not altered in transit. The firm's architect adds that asymmetric algorithms are far slower than symmetric ones on large amounts of data, and transfers must stay fast. Which THREE steps together meet all of these requirements? (Select THREE)
A: Encrypt each archive with a newly generated symmetric key, because symmetric encryption is fast on large amounts of data.
B: Encrypt that symmetric key with the partner's public key, so only the partner's private key can recover the archive key.
C: Hash the archive and sign the hash with the firm's private key, so the partner can check it with the firm's public key.
D: Encrypt each whole archive with the partner's public key, because asymmetric encryption is the only way to avoid exchanging a key first.
E: Encrypt the symmetric key with the engineering firm's own public key, so the partner can decrypt it later with that same public key.
F: Hash the archive and send only the hash value, because the partner can reverse the hash to rebuild any archive content that was changed.
K: A,B,C
G: ## Symmetric, asymmetric and hashing working together
- **Symmetric encryption** uses one key to encrypt and decrypt. It is fast, so it suits large data, but both sides need the same key.
- **Asymmetric encryption** uses a key pair. Data encrypted with a **public** key can be decrypted only with the matching **private** key. It solves key exchange but is much slower.
- **Hashing** turns data into a fixed-length value. The same input always gives the same hash, and a hash cannot be reversed to get the data back. Any change to the file changes the hash.
## The usual combination
1. Encrypt the big file with a random symmetric key (speed).
2. Encrypt that small key with the **recipient's public key** (no prior key exchange).
3. Hash the file and **sign the hash with the sender's private key** (a digital signature). The recipient verifies it with the sender's public key: a valid signature proves origin, and a matching hash proves integrity.
## The hidden constraint
Speed rules out encrypting multi-gigabyte archives asymmetrically, even though that alone would solve key exchange.
W: A=Symmetric key for the archive: it gives fast bulk encryption, which the speed requirement demands for multi-gigabyte files.
B=Wrap the key with the partner's public key: only the partner's private key can unwrap it, so no secret ever has to be exchanged beforehand.
C=Sign the hash with the firm's private key: verification with the firm's public key proves origin, and a matching hash proves the archive was not altered.
X: D=Whole archive with the partner's public key: it avoids key exchange but is the slow asymmetric bulk encryption the architect ruled out.
E=Key wrapped with the firm's own public key: only the firm's private key could decrypt it, so the partner could not recover the archive key.
F=Send only a hash and reverse it: hashes are one-way and cannot rebuild content; a bare hash without a signature does not prove who sent it either.
T: Encrypt bulk data with a symmetric key, protect that key with the recipient's public key, and sign a hash with the sender's private key.
V: Encryption, Hashing

@ SC-900 D1 T1.1 expert comparison
S: A payments startup designs three data stores. Customer passwords must be checked at every sign-in but must never be recoverable, not even by the company's own administrators. Card numbers must be stored so that the refunds service can later read the full number and send it to the card network. Archived log files must let auditors prove that a file has not changed since it was archived. In a design review, the security architect adds that two customers who happen to choose the same password must never produce the same stored value. Which design meets every requirement?
A: Salted hashes for the passwords, encryption with a managed key for the card numbers, and a stored hash of each archived log file.
B: Encryption with a managed key for the passwords, salted hashes for the card numbers, and encryption of each archived log file instead.
C: Unsalted hashes for the passwords, salted hashes for the card numbers, and a digital certificate attached to each of the archived log files.
D: Salted hashes for the passwords, salted hashes for the card numbers, and encryption of each log file so that nobody can read the archive later.
K: A
G: ## Reversible versus one-way protection
- **Encryption is reversible**: with the right key, the original data comes back. Use it when a system must read the data again later.
- **Hashing is one-way**: a hash cannot be turned back into the original. Use it to **verify** data (a password at sign-in, a file's integrity) without storing the data itself.
- **Salting** adds a random value to each password before hashing, so two users with the same password get different hashes and precomputed lookup tables stop working.
## Mapping each store
- Passwords: verify, never recover, and different users must not share a stored value -> **salted hash**.
- Card numbers: the refunds service needs the full number again -> **encryption**, with the key protected in a key management service.
- Log archives: prove nothing changed -> store a **hash** and recompute it later; any change gives a different hash.
## The hidden constraint
The rule about identical passwords is what makes plain (unsalted) hashing wrong, even though it is one-way.
W: Salted hash, encryption, file hash: passwords are verifiable but unrecoverable and unique per user, card numbers are recoverable for refunds, and log hashes prove integrity.
X: B=Encrypt passwords and hash card numbers: encrypted passwords can be decrypted by key holders, and hashed card numbers can never be read back for refunds.
C=Unsalted password hashes: identical passwords would give identical stored values, which the architect forbids, and hashed card numbers cannot be recovered.
D=Hash the card numbers: the refunds service could never retrieve the full number, and encrypting logs hides content but does not by itself prove they were unchanged.
T: Hash what you only need to verify (salt passwords), encrypt what you must read again, and keep file hashes to prove integrity.
V: Encryption, Hashing

@ SC-900 D2 T2.1 expert comparison
S: A distributor licenses every employee for Microsoft Entra ID P1 and reviews six security requirements before its budget meeting. Finance wants to know which requirements force an upgrade of some users to Microsoft Entra ID P2 or Microsoft Entra ID Governance, and which the current licenses already cover. The requirements protect administrators, guests, and hybrid employees who still sign in to on-premises PCs with passwords synchronized from Active Directory, so several features look advanced but are not. Which THREE requirements need capabilities that Microsoft Entra ID P1 does not include? (Select THREE)
A: Block sign-ins automatically when ID Protection rates the sign-in risk as high, by using a risk-based Conditional Access policy.
B: Make administrators only eligible for Global Administrator and require approval and MFA every time one of them activates it.
C: Have managers recertify every quarter whether each guest still needs membership in the project groups, removing those who do not.
D: Require MFA for every user who signs in from outside the company's named locations, by using a Conditional Access policy for all apps.
E: Let hybrid employees reset forgotten passwords themselves and write each new password back to on-premises Active Directory at once.
F: Require guests to accept a terms of use document through a Conditional Access grant control before they can open shared SharePoint sites.
K: A,B,C
G: ## What P1 adds and what needs P2
Learn's licensing tables show:
- **Microsoft Entra ID P1**: Conditional Access (including named locations), SSPR with on-premises **writeback**, terms of use attestation in Conditional Access, application proxy, dynamic groups and more.
- **Microsoft Entra ID P2**: everything in P1 plus **risk-based Conditional Access** (ID Protection), **Privileged Identity Management**, and the access review and entitlement management capabilities that were previously generally available in P2. **Microsoft Entra ID Governance** adds more governance features on top.

Three requirements sound advanced but are P1 features: location-based MFA, SSPR writeback for hybrid users, and terms of use. The three that are not in P1 are risk-based sign-in blocking, eligible role assignments with approval (PIM), and recurring access reviews.
W: A=Risk-based Conditional Access: the licensing table lists it only under P2, because it uses ID Protection risk scores.
B=Eligible Global Administrator with approval: this is Privileged Identity Management, which needs P2 or Microsoft Entra ID Governance.
C=Quarterly guest membership reviews: Learn lists access reviews under ID Governance, with the capabilities previously generally available in P2 still working with P2; P1 has none.
X: D=Location-based MFA: Conditional Access with named locations is included in P1.
E=SSPR with writeback: the licensing table lists SSPR with writeback under P1 and P2.
F=Terms of use in Conditional Access: Learn lists terms of use attestation as available with P1.
T: Conditional Access, SSPR writeback and terms of use come with P1; risk-based policies, PIM and access reviews need P2 or ID Governance.
V: Microsoft Entra ID P1, Microsoft Entra ID P2

@ SC-900 D2 T2.3 expert comparison
S: A hospital's identity team writes three rules. Clinicians may open the electronic health record app only from devices that Intune reports as compliant. Any sign-in that Microsoft rates as coming from an anonymous IP address or with unfamiliar sign-in properties must be challenged with MFA, while ordinary sign-ins are not. The four engineers who manage Microsoft Entra settings must not hold the Privileged Role Administrator role between tasks; each use must be approved by the CISO and end automatically four hours later. The hospital has Microsoft Entra ID P2. Which combination of features fits all three rules?
A: Conditional Access requiring a compliant device, a sign-in risk condition from ID Protection that requires MFA, and PIM eligible assignments with approval.
B: Conditional Access requiring a compliant device, a user risk policy from ID Protection that forces a password change, and permanent active role assignments.
C: PIM for the health record app, a Conditional Access named location that lists anonymous IP addresses, and quarterly access reviews of the role.
D: An Intune compliance policy alone for the app, security defaults for the risky sign-ins, and an entitlement management access package containing the role.
K: A
G: ## Three tools that are easy to mix up
- **Conditional Access** is the policy engine at sign-in: if conditions match (user, app, device state, location, risk), then grant with requirements (MFA, compliant device) or block.
- **Microsoft Entra ID Protection** calculates **sign-in risk** (this sign-in probably isn't the owner: anonymous IP address, unfamiliar sign-in properties) and **user risk** (the account is probably compromised: leaked credentials). These risks become conditions in Conditional Access.
- **Privileged Identity Management (PIM)** manages privileged roles: **eligible** assignments that users activate just in time, with **approval**, MFA, justification and a limited activation duration.
## Hidden detail
"End automatically four hours later" is an activation duration, which only PIM provides; Conditional Access does not remove role assignments.
W: Compliant device, sign-in risk with MFA, PIM with approval: each rule maps to the tool designed for it, and PIM's time-limited activation ends the role after four hours.
X: B=User risk policy and permanent roles: anonymous IP and unfamiliar properties are sign-in risk, not user risk, and permanent assignments break the between-tasks rule.
C=PIM for an app and named locations for anonymous IPs: PIM governs roles, not app sign-ins, and Microsoft's anonymous IP detection is a risk signal, not a list you maintain.
D=Intune alone, security defaults, access package: compliance must be enforced through Conditional Access, security defaults cannot target risk, and packages don't time-box role activation with CISO approval.
T: Conditional Access enforces sign-in conditions, ID Protection supplies sign-in and user risk, and PIM gives time-limited, approved privileged roles.
V: Microsoft Entra Conditional Access, Microsoft Entra ID Protection, Microsoft Entra Privileged Identity Management

@ SC-900 D2 T2.3 expert use-case
S: A retailer's platform team must create, start and resize virtual machines in every subscription under its Retail management group, including subscriptions that will be added next year, but must not change virtual networks or grant access to anyone. Service desk members in the same team reset forgotten passwords for ordinary employees in Microsoft Entra ID, but must not create users, manage groups or reset passwords of higher-privileged administrators such as Global Administrators. The CISO insists on least privilege and on no maintenance work each time a subscription is added. Which assignments fit?
A: Virtual Machine Contributor at the Retail management group, and the Microsoft Entra Password Administrator role for the service desk.
B: Azure Contributor on each existing subscription one by one, and the Microsoft Entra User Administrator role for the service desk members.
C: Azure Owner at the Retail management group scope, and the Microsoft Entra Global Administrator role for each of the service desk members.
D: Virtual Machine Contributor assigned as a Microsoft Entra role at tenant scope, and the Azure Reader role on users for password resets.
K: A
G: ## Two RBAC systems with different scopes
- **Azure RBAC** roles apply to Azure resources at a scope: **management group**, subscription, resource group or resource. Assignments **inherit** downward, so a role at a management group also applies to subscriptions added to it later.
- **Microsoft Entra roles** apply to directory objects at tenant scope, an administrative unit, or a single object.
## Picking least-privilege roles
- **Virtual Machine Contributor** (Azure): create and manage virtual machines, but it does not grant management access to the virtual network or storage account the VM connects to, nor access to assign roles.
- **Password Administrator** (Entra): limited ability to manage passwords; whether it can reset a user depends on that user's role, and it cannot reset most administrators. **User Administrator** can also create users and manage groups.
## Hidden detail
"Subscriptions added next year" makes per-subscription assignments wrong even if the role itself is right.
W: VM Contributor at the management group plus Password Administrator: inheritance covers future subscriptions, the role excludes networking and access grants, and Password Administrator only resets eligible users' passwords.
X: B=Contributor per subscription and User Administrator: Contributor can change networks, per-subscription work repeats for new subscriptions, and User Administrator can create users and manage groups.
C=Owner and Global Administrator: both are the broadest roles in their systems and break least privilege outright.
D=VM Contributor as an Entra role and Reader for resets: Azure roles are not assigned as Entra roles, and Reader cannot reset any password.
T: Assign Azure roles at a management group for inherited future coverage, and choose the narrowest Entra role, such as Password Administrator, for directory tasks.
V: Azure RBAC, Microsoft Entra roles

@ SC-900 D2 T2.1 expert use-case
S: A manufacturer federates its Microsoft Entra tenant with an aging AD FS farm that it wants to retire next year to cut server and certificate maintenance. The works council requires that on-premises account policies, such as sign-in hours and disabled accounts, are enforced at the moment of each cloud sign-in. The security team wants Microsoft Entra ID Protection to report users whose passwords appear in leaked credential lists. The network team adds that, after the change, no on-premises server may accept inbound connections from the internet. Which hybrid authentication design fits?
A: Pass-through authentication with lightweight on-premises agents, plus password hash synchronization turned on for leaked credential detection.
B: Password hash synchronization as the only sign-in method, because Microsoft Entra ID enforces on-premises sign-in hours from the synchronized hashes.
C: Keep AD FS federation and add more Web Application Proxy servers, because federation is the only method that enforces on-premises account policies.
D: Pass-through authentication on its own, because its agents forward each user's password hash to Microsoft Entra ID for the leaked credential checks.
K: A
G: ## Three hybrid sign-in methods
- **Password hash synchronization (PHS)**: a hash of the password hash is synchronized; Microsoft Entra ID validates sign-ins in the cloud. Simplest, but on-premises account states like sign-in hours are not checked at sign-in time.
- **Pass-through authentication (PTA)**: lightweight agents on premises validate passwords against AD DS. Learn: PTA enforces the on-premises account policy at sign-in (disabled, locked out, expired, sign-in hours). Agents need only **outbound** internet access.
- **Federation (AD FS)**: authentication happens on premises; needs AD FS and Web Application Proxy servers with **inbound** internet access.
## Leaked credentials
Learn: "Microsoft Entra ID Protection requires Password Hash Sync regardless of which sign-in method you choose" for the leaked credentials report. PHS can run alongside PTA (and can also serve as a fallback if the agents fail).
## Hidden detail
The inbound-connection ban rules out keeping federation even if it met the policy needs.
W: PTA plus PHS: PTA enforces on-premises account policy at sign-in with outbound-only agents, and enabling PHS alongside provides the leaked credential report.
X: B=PHS alone: cloud validation does not check sign-in hours or other on-premises account states at the moment of sign-in.
C=Keep AD FS: it contradicts the plan to retire AD FS and needs inbound internet connections to Web Application Proxy servers.
D=PTA alone: PTA agents validate passwords on premises and do not synchronize hashes, so ID Protection's leaked credential report would not work.
T: Enforce on-premises account policy with pass-through authentication, and turn on password hash sync as well to get leaked credential detection.
V: Microsoft Entra Connect, Microsoft Entra ID Protection

@ SC-900 D2 T2.4 expert use-case
S: A pharmaceutical company runs clinical trials with staff from three partner research organizations, each with its own Microsoft Entra tenant. Partner staff must request one bundle that contains a Teams team, a SharePoint site and a data app, and a sponsor in the company approves each request. Access must end after 180 days unless renewed, and the company's directory must not fill up with stale guest accounts. Most partner staff who will join next year do not yet exist in the company's directory, and IT cannot invite them in advance. Which approach fits?
A: An entitlement management access package whose policy admits the partners as connected organizations, with sponsor approval and 180-day expiry.
B: Invite every partner employee in advance as a B2B guest, add each guest to a dynamic group, and review that group every 180 days.
C: Privileged Identity Management for Groups with eligible membership in one group that grants the team, the site and the data app.
D: A Conditional Access policy for the three partner tenants that grants all three of the resources and then blocks every partner sign-in after 180 days.
K: A
G: ## Entitlement management in Microsoft Entra ID Governance
**Entitlement management** bundles resources (groups, Teams, SharePoint sites, applications) into an **access package**. Each package has **policies** that say who can request, who approves, and how long assignments last.
- **Connected organizations** are external Microsoft Entra directories or domains you have a relationship with. Learn: when someone who **isn't yet in your directory** requests access and is approved, they are automatically invited and assigned access.
- Assignments **expire**; when an external user's access expires and they have no other assignments, their B2B account can be removed from your directory, which prevents stale guests.

## Hidden detail
"Not yet in the directory" and "IT cannot invite in advance" rule out designs that start from existing guest accounts.
W: Access package with connected organizations: partners request the bundle, a sponsor approves, users are invited on approval, and expiry removes access and can clean up guest accounts.

C=PIM for Groups: it time-boxes privileged group membership for existing users; it is not a self-service request flow for external people who are not yet in the directory.
D=Conditional Access for partner tenants: Conditional Access evaluates sign-ins; it does not grant resource access, approve requests or expire assignments.
T: For external users who must request bundled access with approval and expiry, use an entitlement management access package with connected organizations.
V: Microsoft Entra ID Governance

@ SC-900 D2 T2.2 expert comparison
S: After an adversary-in-the-middle phishing kit captured both passwords and Microsoft Authenticator approvals, a bank decides that its Microsoft Entra administrators must use only methods accepted by the built-in Phishing-resistant MFA authentication strength in Conditional Access. Administrators work from bank-issued Windows laptops with a TPM, and when travelling they sometimes use a tablet browser into which they can plug or tap a hardware key. The bank's architects also refuse to build or run any new certificate infrastructure for this project. Which TWO methods should administrators register to satisfy the policy in both situations? (Select TWO)
A: Windows Hello for Business on the bank-issued Windows laptops, which binds the credential to each laptop's TPM.
B: FIDO2 security keys, which the administrators plug in or tap over NFC when they work from the tablet browser.
C: Microsoft Authenticator phone sign-in, which counts as passwordless MFA and therefore also meets the phishing-resistant strength.
D: Hardware OATH tokens, which generate one-time codes away from the phone so that a phishing kit cannot capture the codes in transit.
E: Certificate-based authentication with smart cards, which needs the bank to deploy and run a new public key infrastructure for administrators.
K: A,B
G: ## Authentication strengths
An **authentication strength** in Conditional Access lists which method combinations satisfy a policy. Microsoft provides three built-in strengths: **MFA strength**, **Passwordless MFA strength** and **Phishing-resistant MFA strength**.
Learn's table shows the phishing-resistant strength accepts only:
- **FIDO2 security key** (passkeys);
- **Windows Hello for Business** or platform credential;
- **Certificate-based authentication (multifactor)**.
These methods require an interaction between the method and the sign-in surface, so a proxy site cannot replay them.
## What does not qualify
Microsoft Authenticator phone sign-in meets the MFA and passwordless strengths, but not phishing-resistant. Codes from OATH tokens, SMS or voice (password plus something you have) meet only the MFA strength.
## Hidden detail
Certificate-based authentication would qualify, but the ban on new certificate infrastructure removes it.
W: A=Windows Hello for Business: it is accepted by the phishing-resistant strength and fits the TPM-equipped bank laptops.
B=FIDO2 security keys: they are phishing-resistant and work from the tablet browser where the key can be plugged in or tapped.
X: C=Authenticator phone sign-in: Learn lists it under MFA and passwordless strengths only, not phishing-resistant.
D=Hardware OATH tokens: a typed code is "something you have" plus a password, which meets only the MFA strength and can be relayed by a phishing proxy.
E=Smart card certificate-based authentication: multifactor CBA qualifies, but it requires the new certificate infrastructure the architects refuse to build.
T: The phishing-resistant strength accepts only FIDO2 keys, Windows Hello for Business and multifactor certificate-based authentication.
V: Microsoft Entra authentication strengths, Conditional Access

@ SC-900 D3 T3.4 expert comparison
S: A law firm's analysts review three events in the Microsoft Defender portal. A lawyer clicked a link in a Microsoft Teams chat that led to a credential-harvesting page; the page was harmless when the message was sent and turned malicious later. A third-party app that a partner published received consent through OAuth to read every mailbox and is now pulling large volumes of mail. On premises, an account's NTLM hash was reused to authenticate to a file server and then to a domain controller. Which products are designed to detect or protect against these events, in this order?
A: Defender for Office 365 Safe Links, Defender for Cloud Apps app governance, and Defender for Identity.
B: Defender for Endpoint network protection, Microsoft Entra ID Protection, and Defender for Office 365 anti-phishing.
C: Defender for Office 365 Safe Attachments, Defender for Identity, and Defender for Cloud Apps session controls.
D: Defender for Cloud Apps session controls, Defender for Office 365 anti-phishing, and Microsoft Entra ID Protection.
K: A
G: ## Matching each event to its product
- **Safe Links** (Defender for Office 365) checks URLs **at the time of click** in email, Office apps and Teams. A link that was harmless at delivery and malicious later is exactly why time-of-click checking exists.
- **App governance** in **Defender for Cloud Apps** extends threat protection to **OAuth-enabled apps** that have permissions to critical data, flagging apps with risky permissions or unusual data access.
- **Defender for Identity** uses sensors on identity infrastructure to detect compromised credentials and **lateral movement**, such as pass-the-hash reuse of NTLM hashes against servers and domain controllers.
## Hidden details
"Harmless when sent" points to time-of-click, not attachment detonation; "on premises" and "domain controller" point to Defender for Identity rather than a cloud identity service.
