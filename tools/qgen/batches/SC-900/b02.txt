@ SC-900 D2 T2.1 applied definition
S: A small company has just subscribed to Microsoft 365 for email and file sharing. The owner asks whether the company must buy and set up a separate identity service before staff can sign in. What should you tell the owner?
A: The company must first deploy Active Directory Domain Services on a server, because Microsoft 365 reads its accounts from domain controllers.
B: Every Microsoft 365 tenant is already a Microsoft Entra tenant, so the company is using Microsoft Entra ID, a cloud identity service, today.
C: The company must buy Microsoft Entra ID P2 licenses, because Microsoft 365 sign-in is only available after an Entra ID edition is purchased.
D: The company must create a Microsoft Entra Domain Services managed domain, because cloud apps need Kerberos to authenticate the staff.
K: B
G: ## What Microsoft Entra ID is
Microsoft Entra ID (formerly Azure Active Directory) is Microsoft's **cloud-based identity and access management service**. It authenticates users, enforces policies and protects users, devices, apps and resources.
- Every new directory gets an initial domain such as `contoso.onmicrosoft.com`; you can add your own domain names.
- If you subscribe to **Microsoft 365, Azure or Dynamics CRM Online**, you are already using Microsoft Entra ID: every such tenant is automatically a Microsoft Entra tenant.
- The **Free** edition is included with Microsoft cloud subscriptions. Paid editions (P1, P2) add features such as Conditional Access and risk-based protection.
## What it is not
Microsoft Entra ID is not a domain controller in the cloud. It does not need on-premises servers, and it uses modern protocols (OAuth 2.0, OpenID Connect, SAML) instead of Kerberos and LDAP. **Microsoft Entra Domain Services** exists separately for legacy apps that need those older protocols.
## Example
A ten-person shop signs up for Microsoft 365, creates its users in the Microsoft 365 admin center, and those users are stored in the company's Microsoft Entra tenant from the first day.
W: Already a Microsoft Entra tenant: Microsoft 365 uses Microsoft Entra ID as its identity service, so the subscription already came with a tenant and the Free edition; staff accounts are created there.
X: A=Deploy AD DS first: Microsoft 365 needs no on-premises directory. AD DS is only involved when a company chooses hybrid identity and synchronizes existing accounts.
C=Buy P2 first: the Free edition included with the subscription handles sign-in. P2 adds advanced features like risk-based protection, which basic sign-in does not need.
D=Create a Domain Services domain: Microsoft Entra Domain Services is for legacy apps that need Kerberos, LDAP or group policy; Microsoft 365 uses modern cloud authentication.
T: Every Microsoft 365, Azure or Dynamics 365 tenant is a Microsoft Entra tenant, so Microsoft Entra ID (Free) is already in use.
V: Microsoft Entra ID

@ SC-900 D2 T2.1 applied comparison
S: A company uses only the Microsoft Entra ID edition that came with its Azure subscription. It now wants to publish an on-premises web app to remote staff through Microsoft Entra application proxy. What is the lowest edition that adds this capability?
A: Microsoft Entra ID P1, because application proxy requires a P1 or P2 license and P1 is the first paid edition above Free.
B: Microsoft Entra ID P2, because application proxy is only included in the edition that also contains risk-based protections.
C: Microsoft Entra ID Free, because application proxy is part of the edition that every Azure and Microsoft 365 tenant already has.
D: Microsoft Entra ID Governance, because publishing on-premises apps to users is part of the identity lifecycle governance features.
K: A
G: ## Microsoft Entra ID editions
Microsoft Entra ID comes in several licensing options:
- **Free**: included with Microsoft cloud subscriptions such as Azure and Microsoft 365. Covers user and group management, cloud authentication, SSO to apps, security defaults and basic reports.
- **P1**: sold standalone and included in Microsoft 365 E3, E5 and Business Premium. Adds features such as Conditional Access, password writeback for hybrid users, dynamic groups and **application proxy** for on-premises web apps.
- **P2**: everything in P1 plus advanced protection such as Microsoft Entra ID Protection (risk-based Conditional Access) and Privileged Identity Management.
- **Microsoft Entra ID Governance** and **Microsoft Entra Suite** are further products that build on P1.
## Reading a requirement
Find the lowest edition that lists the feature. Learn states that Microsoft Entra application proxy requires P1 or P2 licenses, so P1 is enough.
## Example
A firm moves from Free to P1 so field staff can open the on-premises timesheet site from home without a VPN, published through application proxy.
W: Microsoft Entra ID P1: application proxy is licensed with P1 or P2, and P1 is the cheaper of the two, so it is the lowest edition that adds the feature.
X: B=Microsoft Entra ID P2: P2 also includes application proxy, but it is not required; P2 is aimed at extras like risk-based protection and PIM.
C=Microsoft Entra ID Free: Free is what the company already has, and application proxy is not part of it; it needs a P1 or P2 license.
D=Microsoft Entra ID Governance: Governance covers access requests, reviews and lifecycle workflows for identities, not publishing on-premises web apps.
T: Microsoft Entra ID Free comes with cloud subscriptions; P1 adds features such as application proxy and Conditional Access; P2 adds risk-based protection.
V: Microsoft Entra ID

@ SC-900 D2 T2.1 applied use-case
S: A company is moving an old line-of-business app to Azure virtual machines. The app can only authenticate users with Kerberos and query LDAP, and the company does not want to deploy or patch its own domain controllers in Azure. Which service fits?
A: Microsoft Entra ID application registrations, because registering the app lets it accept Kerberos tickets from Microsoft Entra sign-in.
B: Microsoft Entra Cloud Sync, because its provisioning agent turns the Microsoft Entra tenant into an LDAP directory for the virtual machines.
C: Microsoft Entra Domain Services, because Microsoft deploys and maintains a managed domain that provides Kerberos, LDAP and group policy.
D: Microsoft Entra External ID, because an external tenant offers legacy protocol support for apps that cannot use modern authentication.
K: C
G: ## Modern versus legacy authentication
Microsoft Entra ID uses modern, web-based protocols such as OAuth 2.0, OpenID Connect and SAML. Many older applications were written for Windows Server Active Directory and expect:
- **Kerberos or NTLM** authentication
- **LDAP** queries against a directory
- **Group policy** applied to domain-joined servers
## Microsoft Entra Domain Services
Microsoft Entra Domain Services provides **managed domain services** (group policy, LDAP, Kerberos/NTLM authentication) for legacy applications in the cloud. Microsoft deploys and maintains the domain controllers; you do not patch or back them up.
- Users can sign in with their existing Microsoft Entra credentials.
- For hybrid users, password hash synchronization is required so their credentials reach the managed domain.
## Example
A payroll app running on Azure VMs joins a managed domain called `aadds.contoso.com` and authenticates staff with Kerberos, while the IT team never touches a domain controller.
W: Microsoft Entra Domain Services: it is designed for legacy cloud apps that cannot use modern authentication, giving them Kerberos, LDAP and group policy from a domain that Microsoft runs.
X: A=Application registration: registering an app lets it use OAuth 2.0 or OpenID Connect with Microsoft Entra ID; it does not make Microsoft Entra ID issue Kerberos tickets or answer LDAP.
B=Cloud Sync: Cloud Sync copies users and groups from Active Directory into Microsoft Entra ID; it does not expose the tenant as an LDAP directory to servers.
D=External ID: External ID manages partner and customer identities for apps; it adds no Kerberos or LDAP support for legacy workloads.
T: Legacy cloud apps that need Kerberos, NTLM, LDAP or group policy without self-managed domain controllers point to Microsoft Entra Domain Services.
V: Microsoft Entra Domain Services

@ SC-900 D2 T2.1 applied use-case
S: Employees want to read work email on their personal Android phones. The company does not own these phones but wants each phone to have a device identity in Microsoft Entra ID so it can be considered in access decisions. Which option fits?
A: Microsoft Entra hybrid join, because personal phones are joined to on-premises Active Directory and then registered in Microsoft Entra ID.
B: Microsoft Entra join, because personal phones are joined directly to the tenant and must be signed in with an organizational account.
C: Microsoft Entra registration, because it gives personal and mobile devices an identity without requiring an organizational sign-in to the device.
D: Microsoft Entra Domain Services join, because personal phones join a managed domain so Kerberos can be used for their email access.
K: C
G: ## Device identities
A **device identity** is an object in Microsoft Entra ID, like a user or an app. It gives administrators information to use in access or configuration decisions, and it is a prerequisite for device-based Conditional Access and for device management with Microsoft Intune. There are three ways to get one:
- **Microsoft Entra registered** (also called workplace joined): for **bring your own device (BYOD)** and mobile phones and tablets. The user signs in to the device with a personal account; ownership can be the user or the organization. Supports Windows, macOS, iOS, Android and some Linux editions.
- **Microsoft Entra joined**: organization-owned Windows 10/11 devices (and Windows Server VMs in Azure) whose users sign in with their organizational account. No on-premises AD needed.
- **Microsoft Entra hybrid joined**: organization-owned Windows devices joined to on-premises AD **and** registered in Microsoft Entra ID; they need periodic line of sight to domain controllers. Seen as an interim step toward Entra join.
## Example
A nurse registers her own iPhone so the hospital can see it in the directory, while hospital-owned laptops are Microsoft Entra joined.
W: Microsoft Entra registration: it is the option for BYOD and mobile devices, giving the phone a device identity while the owner keeps signing in to it with a personal account.
X: A=Hybrid join: hybrid join is for organization-owned Windows computers joined to on-premises Active Directory; Android phones are not joined to on-premises AD.
B=Entra join: join is for organization-owned Windows devices where users sign in with a work account, not for personal phones that the company does not own.
D=Domain Services join: Microsoft Entra Domain Services provides managed domains for legacy server apps; it is not a way to give personal phones a device identity.
T: Personal (BYOD) and mobile devices are Microsoft Entra registered; company Windows devices are Entra joined or, with on-premises AD, hybrid joined.
V: Microsoft Entra ID

@ SC-900 D2 T2.1 applied definition
S: A company wants consultants from a partner firm to open its SharePoint sites by using Microsoft Entra B2B collaboration. Which TWO statements describe how B2B collaboration works? (Select TWO)
A: The consultants sign in with their own work, school or social identities, so the company does not manage passwords for them.
B: The company must first synchronize the partner's on-premises accounts into its own tenant by using Microsoft Entra Connect Sync.
C: After a consultant redeems the invitation, the consultant appears in the company's directory as a user object, typically a guest.
D: The partner firm must have its own Microsoft Entra tenant, because B2B invitations can only be redeemed by Entra work accounts.
E: The company must create a separate external tenant for the consultants, because guests cannot be added to a workforce tenant.
K: A,C
G: ## External identities in Microsoft Entra
Microsoft Entra External ID covers people outside your organization. It has two main scenarios:
- **B2B collaboration** in your **workforce tenant**: share your apps and resources with business partners and guests.
- **CIAM** (customer identity and access management) in a separate **external tenant**: sign-up and sign-in for consumer and business-customer apps.
## How B2B collaboration works
- You invite a partner user (or let them use self-service sign-up). The partner **uses their own credentials**, whether or not they have Microsoft Entra ID: a work account, a Microsoft account, Google, or an email one-time passcode.
- After redemption the person is represented in your directory as a **user object**, usually with the user type **Guest**.
- You don't manage the partner's passwords, sync their accounts or manage their account lifecycles; you control what they can reach with cross-tenant access and external collaboration settings.
## Example
A consultant at Fabrikam receives an invitation, signs in with her Fabrikam account, and shows up in Contoso's tenant as a guest who can open one SharePoint site.
W: A=Their own identities: B2B lets partners bring their own work, school or social identities, so the inviting company never handles their passwords.
C=Guest user object: once the invitation is redeemed, the partner is represented in the inviting directory as a user object whose user type is typically Guest.
X: B=Synchronize partner accounts: Connect Sync synchronizes your own on-premises directory; B2B removes any need to sync or manage partner accounts.
D=Partner needs a tenant: B2B works whether or not the partner has Microsoft Entra ID; guests can use other identities or an email one-time passcode.
E=Separate external tenant: an external tenant is for consumer-facing CIAM apps; B2B guests are added to the company's existing workforce tenant.
T: B2B collaboration: partners sign in with their own identities and appear as guest user objects in your workforce tenant.
V: Microsoft Entra External ID

@ SC-900 D2 T2.1 applied use-case

A: Microsoft Entra B2B collaboration in the workforce tenant, inviting each customer as a guest user before their first purchase.
B: Microsoft Entra External ID in an external tenant, which provides customer sign-up, sign-in and branding separate from the workforce.
C: Microsoft Entra Connect Sync, which copies customer accounts from the retailer's on-premises customer database into Microsoft Entra ID.
D: Microsoft Entra Domain Services, which creates a managed domain where customer accounts can be stored apart from employee accounts.

G: ## Two kinds of external users
Microsoft Entra External ID handles people outside the organization in two ways:
- **Workforce tenant + B2B collaboration**: business partners and guests get access to the company's internal apps, usually by invitation.
- **External tenant (CIAM)**: a separate Microsoft Entra tenant in an **external configuration** for apps that the company publishes to **consumers and business customers**.
## What an external tenant offers
- **Self-service sign-up flows** with email and password, one-time passcodes, or social accounts such as Google or Facebook.
- **Custom branding** (logos, colors, background images) on sign-in pages.
- Collecting built-in or custom attributes at sign-up and analyzing user activity.
- Separation: customer accounts live apart from employees and organizational resources.

A ticketing site lets visitors create an account with their Google identity; the accounts sit in the site's external tenant, while staff accounts stay in the workforce tenant.
W: External ID in an external tenant: this is Microsoft's CIAM solution for consumer apps, with self-service sign-up, social identity providers and branding in a tenant kept separate from the workforce.

C=Connect Sync: Connect Sync synchronizes an on-premises Active Directory into Microsoft Entra ID; it is not a customer sign-up service and does not read customer databases.

T: Consumer-facing app sign-up with social accounts in a tenant separate from staff = Microsoft Entra External ID in an external tenant.
V: Microsoft Entra External ID

@ SC-900 D2 T2.1 applied definition
S: A security team is listing every workload identity in its Microsoft Entra tenant so that each one can be reviewed. Which TWO object types count as workload identities in Microsoft Entra? (Select TWO)
A: Guest user accounts that partner staff created by redeeming B2B collaboration invitations from the company.
B: Service principals, which are the local instances of an application object inside a specific tenant.
C: Device objects that are created when company laptops are Microsoft Entra joined or hybrid joined.
D: Managed identities, which are a special type of service principal that removes the need to manage credentials.
E: Dynamic security groups whose membership rules automatically add and remove members based on attributes.
K: B,D
G: ## Human and machine identities
Microsoft divides identities into two broad kinds:
- **Human identities** represent people: employees, frontline workers, partners and customers. Guest users are human identities.
- **Machine (non-human) identities** are of two kinds: **device identities** (laptops, phones, IoT devices) and **workload identities** (software).
## Workload identities in Microsoft Entra
A workload identity is an identity assigned to software (an app, service, script or container) so it can authenticate to other services. In Microsoft Entra, workload identities are:
- **Applications**: the application object is the global template that describes how tokens are issued and what the app needs.
- **Service principals**: the local representation of an application in a specific tenant; it defines what the app can do there and what it can access.
- **Managed identities**: a special type of service principal whose credentials Azure manages, so developers don't handle secrets.
## Example
A CI/CD pipeline that deploys from GitHub to Azure App Service uses a service principal; a web app reading Azure Key Vault uses a managed identity.
W: B=Service principals: a service principal is the tenant-local instance of an application and one of the workload identity types Microsoft Entra lists.
D=Managed identities: a managed identity is a special service principal for Azure resources, and Microsoft Entra counts it as a workload identity.
X: A=Guest users: B2B guests are people, so they are human identities even though they come from another organization.
C=Device objects: devices are machine identities, but Microsoft places them in the separate device identity group, not among workload identities.
E=Dynamic groups: a group is a container that grants access to its members; it is not an identity that software uses to authenticate.
T: Workload identities in Microsoft Entra are applications, service principals and managed identities; devices are a separate kind of machine identity.
V: Microsoft Entra Workload ID

@ SC-900 D2 T2.1 applied use-case
S: A developer's web app runs in Azure App Service and must read secrets from Azure Key Vault. The security team forbids storing any password, key or certificate for that access in code or configuration. What should the developer use?
A: A guest user account created through B2B collaboration, whose password the app reads from an environment variable at startup.
B: A service principal with a client secret that the developer copies into the app settings and rotates by hand every few months.
C: A shared administrator user account whose sign-in is protected by multifactor authentication on the developer's phone.
D: A managed identity for the App Service app, so Azure manages its credentials and the app gets tokens from Microsoft Entra ID.
K: D
G: ## Why apps need identities
When one Azure service calls another, the caller must prove who it is. The classic approach gives the app a service principal with a **client secret** or certificate, which someone must store, protect and rotate. Leaked secrets are a common cause of breaches.
## Managed identities for Azure resources
A managed identity is an **automatically managed identity in Microsoft Entra ID** for apps running on Azure resources that support it.
- Developers **don't manage any credentials**; Azure handles them.
- The app asks for a token and uses it with any resource that supports Microsoft Entra authentication, such as Key Vault or Azure Storage.
- There is no extra cost and no special license.
- Two types exist: **system-assigned** (tied to one resource) and **user-assigned** (a standalone resource you can attach to several).
## Example
A function app enables a system-assigned managed identity, the team grants that identity permission to read secrets in one key vault, and the code calls Key Vault with no secret anywhere in its settings.
W: Managed identity: Azure manages the identity's credentials, so the app gets Microsoft Entra tokens for Key Vault without anyone storing a password, key or certificate.
X: A=Guest user account: guest accounts represent people from other organizations, and reading a password from a variable still stores a credential.
B=Service principal with a secret: this works technically, but the copied client secret is exactly the stored credential the team forbids, and manual rotation adds risk.
C=Shared admin account: apps should not use human accounts, sharing an admin account breaks least privilege, and the app can't complete phone-based MFA.
T: Apps on Azure that must reach other Azure services without stored secrets should use a managed identity.
V: Managed identities for Azure resources, Azure Key Vault

@ SC-900 D2 T2.1 applied comparison
S: A team runs twelve Azure virtual machines that all need the same access to one storage account. VMs are often deleted and rebuilt, and the team wants the identity and its permissions to survive those rebuilds. Which managed identity type fits?
A: A system-assigned managed identity on each VM, because it is shared automatically by every VM in the same resource group.
B: A user-assigned managed identity, because it is a standalone resource that several VMs can share and that is deleted only on request.
C: A system-assigned managed identity on the storage account, because the storage account then grants itself access to every VM.
D: A user-assigned managed identity per VM, because user-assigned identities are deleted together with the VM they are attached to.
K: B
G: ## Two types of managed identity
**System-assigned**
- Enabled directly on one Azure resource, such as a VM.
- Microsoft Entra creates a special service principal tied to **that resource's lifecycle**: when the resource is deleted, the identity is deleted too.
- It cannot be shared with other resources, and its name always matches the resource.
**User-assigned**
- Created as a **standalone Azure resource**, then assigned to one or more resources.
- Has an **independent lifecycle**: it must be deleted explicitly.
- The **same identity can be associated with more than one resource**, so permissions are granted once.
- Microsoft recommends user-assigned identities for Microsoft services.
## Example
A team creates one user-assigned identity called `id-reports`, gives it read access on a storage account, and attaches it to every VM; when a VM is rebuilt, the new VM gets the same identity attached and works at once.
W: User-assigned managed identity: one identity is shared by all twelve VMs and lives independently of them, so its storage permission survives every rebuild.
X: A=System-assigned per VM: each system-assigned identity belongs to one resource only and is deleted with it, so rebuilt VMs would need new identities and new permissions.
C=System-assigned on storage: an identity on the storage account would let the storage account call other services; it does not authenticate the VMs.
D=User-assigned per VM, deleted with the VM: user-assigned identities are not deleted with a VM; their lifecycle is independent, and one identity can serve all twelve.
T: System-assigned = one resource, same lifecycle; user-assigned = standalone, shareable across resources, independent lifecycle.
V: Managed identities for Azure resources, Azure Virtual Machines

@ SC-900 D2 T2.1 applied definition
S: A software vendor publishes one multitenant app that customers add to their own Microsoft Entra tenants. A customer admin asks which object in the customer's tenant defines what the vendor's app may do there and who can use it. Which object is it?
A: The application object, which is the single global definition of the app and lives in the vendor's home tenant.
B: A managed identity, which Azure creates in each customer tenant when the vendor's app is first signed in to.
C: A service principal, which is the local instance of the app in each tenant and holds that tenant's permissions.
D: A guest user object, which represents the vendor in each tenant and is invited through B2B collaboration.
K: C
G: ## Application object versus service principal
An app that uses Microsoft Entra ID has two related objects:
- **Application object**: the **global representation** of the app, used across all tenants. It is a template that describes how tokens are issued, the resources the app needs and the actions it can take. It lives in the tenant where the app was registered.
- **Service principal**: the **local representation, or application instance**, of the application object in a specific tenant. A service principal is created from the template in **every tenant where the app is used**. It defines what the app can actually do in that tenant, who can access it and which resources it can reach.
## Managed identities
A managed identity is a special type of service principal for Azure resources whose credentials Azure manages. It is not created for third-party SaaS apps.
## Example
Contoso registers a project-tracking app once. When Fabrikam and Northwind consent to it, each gets its own service principal for the app, and each admin controls its permissions in their own tenant.
W: Service principal: it is the app's local instance in the customer's tenant, and it carries the permissions, user assignments and resource access that apply in that tenant.
X: A=Application object: the application object is the global template in the vendor's tenant; it does not hold permissions inside the customer's tenant.
B=Managed identity: managed identities are for Azure resources whose credentials Azure manages; they are not created for third-party multitenant apps.
D=Guest user: a guest represents a person invited through B2B; software uses a service principal, not a guest account.
T: An application object is the global template; a service principal is the app's local instance and permissions in each tenant.
V: Microsoft Entra ID

@ SC-900 D2 T2.1 applied use-case
S: After a merger, a company has two Active Directory forests that have no network trust between them. It wants both synchronized into one Microsoft Entra tenant with lightweight agents and configuration managed from the cloud. Which tool fits?
A: Microsoft Entra Connect Sync, because a single on-premises server must hold the full synchronization configuration for both forests.
B: Microsoft Entra Connect Health, because its agents copy users and groups from each forest into the tenant every two minutes.
C: Microsoft Entra Domain Services, because the managed domain joins both forests together before their accounts reach the cloud.
D: Microsoft Entra Cloud Sync, because its provisioning agents bridge each forest while configuration is stored and managed in the cloud.
K: D
G: ## Hybrid identity
**Hybrid identity** means a common user identity for authentication and authorization to resources both on-premises and in the cloud. It is achieved through **provisioning and synchronization**: making sure the identity information for on-premises users and groups matches the cloud.
## Two synchronization tools
- **Microsoft Entra Connect Sync**: an on-premises Microsoft application installed on a server. It handles sync, password hash sync, pass-through authentication and federation integration.
- **Microsoft Entra Cloud Sync**: a cloud-managed sync service. A **lightweight provisioning agent** (outbound connections only, automatic updates) runs on-premises, and all configuration lives in Microsoft Entra ID. It natively supports **multiple disconnected forests**, for example after mergers and acquisitions, and multiple active agents for high availability.
Learn describes Cloud Sync as the future of synchronization for Microsoft that replaces Microsoft Entra Connect; organizations whose scenario the migration tooling doesn't yet cover keep using Connect Sync.
## Example
After buying a rival, a company installs one provisioning agent in each forest and synchronizes both into its tenant without building trust between them.
W: Cloud Sync: its lightweight agents connect each forest outbound to the cloud, all settings are managed in Microsoft Entra ID, and disconnected forests are supported natively.
X: A=Connect Sync: Connect Sync is a full on-premises server application whose configuration lives on that server, which the company specifically wants to avoid.
B=Connect Health: Connect Health monitors sync, AD FS and AD DS health and shows alerts; it does not synchronize any objects.
C=Domain Services: a managed domain gives legacy cloud apps Kerberos and LDAP; it does not merge on-premises forests or feed them into the tenant.
T: Disconnected forests, lightweight agents and cloud-managed configuration point to Microsoft Entra Cloud Sync.
V: Microsoft Entra Cloud Sync, Microsoft Entra Connect

@ SC-900 D2 T2.1 applied comparison
S: A company synchronizes its on-premises users to Microsoft Entra ID. It wants them to sign in to Microsoft 365 with their usual password, using the least extra on-premises infrastructure. Which sign-in method fits?
A: Pass-through authentication, because software agents on several on-premises servers validate each password against domain controllers.
B: Federation with AD FS, because a farm of on-premises federation servers checks each password before Microsoft Entra ID issues a token.
C: Password hash synchronization, because a hash of each password hash is synchronized and Microsoft Entra ID validates the sign-in itself.
D: Microsoft Entra Domain Services, because a managed domain in Azure validates passwords for synchronized users who sign in to Microsoft 365.
K: C
G: ## Three hybrid sign-in methods
When users exist in on-premises Active Directory and are synchronized to Microsoft Entra ID, you choose how their passwords are checked:
- **Password hash synchronization (PHS)**: a hash of the password hash is synchronized to Microsoft Entra ID, which validates sign-ins in the cloud. It needs **the least effort and infrastructure**; it runs as part of the Connect Sync process. Passwords are never stored in clear text or with reversible encryption.
- **Pass-through authentication (PTA)**: lightweight agents on on-premises servers validate passwords directly against Active Directory, so validation doesn't happen in the cloud. Microsoft recommends three agents for availability.
- **Federation**: Microsoft Entra ID hands authentication to a separate trusted system such as AD FS, which you deploy and run.
PHS and PTA are **cloud authentication**; federation is **federated authentication**.
## Example
A 300-person firm turns on PHS in its existing sync tool; staff sign in to Teams with their domain password and no new servers are deployed.
W: Password hash synchronization: Microsoft Entra ID checks passwords in the cloud using the synchronized hashes, so users keep the same password and no extra servers are needed.
X: A=Pass-through authentication: PTA needs agents on on-premises servers with access to domain controllers, which adds infrastructure that PHS avoids.
B=Federation with AD FS: federation needs its own server farm to deploy and maintain, the most on-premises infrastructure of the three methods.
D=Domain Services: a managed domain serves legacy apps with Kerberos and LDAP; it is not a sign-in method for Microsoft 365.
T: Password hash synchronization is the simplest hybrid sign-in method with the least on-premises infrastructure.
V: Microsoft Entra Connect

G: ## Public key sign-in
Passkeys are built on the **FIDO** (Fast Identity Online) standards and use **origin-bound public key cryptography**:
- At registration, a key pair is created. The **private key is stored on the user's device**; the **public key is stored with the app or website**.
- At sign-in, Microsoft Entra ID sends a **challenge**. The user unlocks the private key with a **biometric or PIN gesture**, the authenticator signs the challenge, and Microsoft Entra ID **verifies the signature with the public key**.
- The key pair only works for the site it was created for, so a look-alike phishing site can't use it.
## Local unlock
The biometric or PIN check happens **on the device**; the fingerprint or face data is not sent to the service. Because the user must be present at the device, an attacker can't trick them into signing in on a device the attacker controls.
## Types of passkey
- **Device-bound**: the private key never leaves one device (FIDO2 security keys, passkeys in Microsoft Authenticator).
- **Synced**: the key is synced through a passkey provider such as Apple iCloud Keychain or Google Password Manager.
W: Private key on the device: the service holds only a public key, which can't be used to sign in, and the private key is unlocked locally to sign each challenge.
X: B=Stored random password: a passkey is not a password at all; there is no shared secret on the service that a breach or phishing page could steal.
C=Email one-time code: email OTP is a separate, phishable method; passkeys sign a challenge with a private key instead of sending codes.
D=Fingerprint uploaded: biometrics only unlock the key locally; no fingerprint or face image is sent to Microsoft Entra ID.
T: A passkey keeps the private key on the device and gives the service only the public key, so nothing reusable can be stolen or phished.

G: ## The hybrid reset problem
When a user's password is **managed on-premises** (the tenant uses password hash sync, pass-through authentication or federation), a reset in Microsoft Entra ID is useless unless the on-premises directory also gets the new password. ## Password writeback
**Password writeback** writes password changes made in the cloud **back to the on-premises directory** in real time.
- Supported with **PHS, PTA and AD FS**.
- Configured through Microsoft Entra Connect Sync or Cloud Sync.
- **Enforces on-premises AD DS password policies** (history, complexity, age, filters) before committing.
- **Zero-delay feedback**: it's synchronous, so users learn at once if the password is rejected.
- SSPR with writeback needs **Microsoft Entra ID P1 or P2**.

D=Smart lockout: smart lockout locks out brute-force attempts in the cloud; it doesn't update on-premises passwords.

S: A company named Northwind finds that staff keep choosing passwords like Northwind1! and Seattle#1. It wants Microsoft Entra ID to reject passwords built from its brand and city names when users change or reset passwords. What should it configure?

G: ## Microsoft Entra Password Protection
Password Protection **detects and blocks known weak passwords and their variants** when users change or reset passwords.
- **Global banned password list**: built by Microsoft from security telemetry about weak and commonly attacked passwords. It applies **automatically to all users**, can't be disabled, and its contents aren't published. You can't edit it.
- **Custom banned password list**: your own **organization-specific terms**, such as brand names, product names, locations (for example headquarters city), internal terms and abbreviations. Its entries are **combined with the global list** when passwords are checked.
## Block base terms, not variants
The checker **normalizes** passwords (lower-case, common substitutions such as `0`->`o`, `$`->`s`) and uses fuzzy and substring matching, so listing `northwind` and `seattle` also catches `N0rthw1nd!` and `Seattle#1`. A password containing a banned term may still be accepted if the rest of it is strong enough.

C=Smart lockout: smart lockout limits repeated failed sign-ins; it doesn't check the content of new passwords.
D=Security defaults: security defaults turn on MFA registration and block legacy authentication; they don't ban organization-specific password terms.
T: Organization-specific weak terms go in the custom banned password list, which works together with Microsoft's global list.

G: ## Where the global list comes from
The Microsoft Entra ID Protection team analyzes **Microsoft Entra security telemetry**, looking for commonly used weak or compromised passwords and especially the **base terms** that weak passwords are built on. Those terms go on the global banned password list.
- It is **not based on third-party data sources**, including compromised-password lists from breaches.
- Its **contents aren't published**, because attackers use similar lists.

- The global list is **automatically applied to all users** in a Microsoft Entra tenant when they change or reset their password.
- There is **nothing to enable or configure, and it can't be disabled**.
- Organizations can add their own terms in a **custom banned password list**, which is combined with the global list.

Password spray attacks try a few of the most common weak passwords against many accounts. A list sourced from real attacks, plus normalization and fuzzy matching, blocks millions of weak variants without needing a huge list.

G: ## Extending Password Protection to AD DS
Microsoft Entra Password Protection works for cloud password changes by default. To protect **on-premises Active Directory Domain Services**, you install two components:
- **Proxy service**: runs on a domain-joined machine in the forest and forwards password policy download requests from domain controllers to Microsoft Entra ID.
- **DC agent**: installed on **domain controllers**. Its password filter receives password-validation requests from Windows and checks them against the locally stored policy (the global and custom banned lists downloaded through the proxy).
## Behavior to know
- The policy is only enforced on DCs **where the DC agent is installed**, so partial deployments leave gaps.
- The DC agent never listens on the network, and the proxy never calls the DC agent.
- It isn't real-time: policy changes in the cloud take a while to reach every DC.
## Example

D=Pass-through authentication: PTA validates sign-ins against AD; it doesn't check new passwords against banned lists.
T: To enforce banned passwords for on-premises AD DS changes, deploy the Password Protection proxy service and the DC agent on domain controllers.

S: Attackers keep guessing passwords against employee accounts. The company wants the guessers blocked while employees signing in from their usual places can keep working, without locking everyone out. Which built-in capability provides this?
A: Self-service password reset, because it automatically resets the password of any account that receives too many failed sign-ins.

K: C
G: ## Brute force and password guessing
Attackers try many passwords against an account (brute force) or a few common passwords against many accounts (password spray). A simple lockout rule stops them but also locks out the real user, which attackers can abuse.
## Smart lockout
Microsoft Entra **smart lockout** locks out bad actors who guess passwords while trying to keep genuine users working:
- It recognizes sign-ins from **valid users and treats them differently** from attackers and unknown sources.
- By default it locks an account after 10 failed attempts in Azure Public tenants; the lockout period starts at one minute and grows with further failures.
- It tracks recent bad password hashes, so the same wrong password typed again doesn't keep counting.
- It is **always on** for all Microsoft Entra customers; customizing its settings needs P1 or higher.
Smart lockout reduces but doesn't guarantee against locking out a genuine user.
## Example
A spray tool from an unfamiliar country hits a sales rep's account; the tool gets locked out, while the rep signing in from the office keeps working.
W: Smart lockout: it locks out repeated failed sign-ins from attackers while recognizing the valid user's sign-ins, and it is on by default for every tenant.
X: A=SSPR: SSPR lets users reset their own passwords; it doesn't react to failed sign-ins or block attackers.
B=Password Protection: Password Protection checks new passwords when they're set or changed; it doesn't evaluate or lock out sign-in attempts.
D=Temporary Access Pass: a TAP is issued by an admin for onboarding or recovery; it isn't triggered by failed sign-ins.
T: Smart lockout blocks password-guessing attackers while trying to keep genuine users signed in, and it's always on.
