@ SC-900 D2 T2.3 applied use-case
S: A company wants a rule that says: if a sales employee opens Microsoft 365 from a network outside the office IP ranges, then the employee must complete multifactor authentication first. Which Microsoft Entra capability is designed to enforce this kind of rule?
A: Microsoft Entra Privileged Identity Management, which asks users to activate their roles before they can open Microsoft 365.
B: Microsoft Entra Conditional Access, which evaluates signals such as group and IP location and then applies an access decision.
C: Microsoft Entra ID Protection risk reports, which list the users and sign-ins that Microsoft has flagged as possibly compromised.
D: Microsoft Entra entitlement management, which bundles Microsoft 365 access into a package that users request and managers approve.
K: B
G: ## Conditional Access in one sentence
Microsoft Entra Conditional Access is Microsoft's **Zero Trust policy engine**. It brings signals together, makes a decision, and enforces the organization's policy every time someone signs in to a resource.
## If-then statements
At their simplest, Conditional Access policies are **if-then statements**:
- **If** a user (the assignment: users, groups, the app they are opening, the network location, the device, the risk level) ...
- **then** apply an access control (block access, or grant access only after something such as multifactor authentication).
## Example
`If` a member of the Sales group opens Microsoft 365 `and` the sign-in comes from outside the named office IP ranges, `then` require multifactor authentication. Inside the office the same user signs in without the extra prompt, which keeps people productive while still protecting the data.
## Licensing note
Conditional Access needs Microsoft Entra ID P1 (or a plan that includes it, such as Microsoft 365 Business Premium).
W: Conditional Access: this is exactly the if-then policy engine described for Entra. It combines the user's group and the IP location signal, then grants access only when MFA is completed.
X: A=Privileged Identity Management: PIM gives just-in-time activation of privileged roles. It does not decide how an ordinary employee signs in to Microsoft 365 from different networks.
C=ID Protection risk reports: these reports help admins investigate risky users and sign-ins; they do not, by themselves, express a rule based on group membership and office IP ranges.
D=Entitlement management: access packages govern who is given access to groups, apps and sites and for how long. They do not add a sign-in requirement that depends on where the user is connecting from.
T: "If this user, app, location or device, then block or require something" is a Conditional Access policy.
V: Microsoft Entra Conditional Access

@ SC-900 D2 T2.3 applied definition
S: An administrator is designing a Conditional Access policy and lists the information it can evaluate before it reaches a decision. Which TWO items are signals that Conditional Access evaluates, rather than access decisions it enforces? (Select TWO)
A: The IP location of the sign-in, such as a named range of office addresses or a specific country or region.
B: A requirement that the device is marked as compliant before the user can open the requested application.
C: The device the user is signing in from, such as its platform or a filter that targets privileged workstations.
D: A requirement that the user accepts the organization's terms of use before reaching the requested resource.
E: A block on access to the application, which is the most restrictive outcome that a policy can enforce.
K: A,C
G: ## Signals in, decisions out
Conditional Access works in two halves:
- **Signals** describe the sign-in. Common signals are the user or group; **IP location information** (named IP ranges, countries or regions); the **device** (platform, or a device filter such as privileged access workstations); the **application** being opened; **real-time and calculated risk** from Microsoft Entra ID Protection; and Microsoft Defender for Cloud Apps session information.
- **Decisions** are what the policy does about it: **block access** (most restrictive) or **grant access**, possibly requiring one or more controls such as MFA, an authentication strength, a compliant device, a Microsoft Entra hybrid joined device, an app protection policy, a password change or terms of use.
## A quick test
Ask "is this something about the sign-in, or something the user must do?" A country is about the sign-in (signal). "Accept terms of use" is something the user must do (decision).
W: A=IP location: Conditional Access lets admins define IP ranges and whole countries or regions and use them as a signal when making policy decisions.
C=Device: the device platform, or a filter for specific devices such as privileged access workstations, is a signal the policy evaluates before deciding.
X: B=Require compliant device: this is a grant control, one of the requirements a policy can impose after it has evaluated the signals.
D=Require terms of use: accepting terms of use is a grant control that the user must satisfy, so it belongs on the decision side.
E=Block access: blocking is the most restrictive decision a policy can enforce, not an input that the policy reads.
T: Signals (user, location, device, app, risk) go in; decisions (block, or grant with requirements) come out.

@ SC-900 D2 T2.3 applied definition
S: A security lead says Conditional Access will be the company's main protection against denial-of-service floods because it checks every request before any credential is entered. What is wrong with this plan?
A: Conditional Access only evaluates sign-ins from devices enrolled in Intune, so traffic from unmanaged machines is never examined.
B: Conditional Access applies only to administrator accounts, so the sign-ins of ordinary users fall outside every policy it holds.
C: Conditional Access policies are enforced after first-factor authentication, so they are not a frontline defense against floods.
D: Conditional Access works only for applications hosted on premises, so cloud services must rely on a separate protection tool.
K: C
G: ## When Conditional Access runs
Microsoft documents that Conditional Access policies are **enforced after first-factor authentication is completed**. The user (or attacker) has already presented a first credential such as a password; Conditional Access then decides whether to block, grant, or ask for more.
## What that means for design
- Conditional Access is not intended to be the organization's **frontline defense** for scenarios such as denial-of-service attacks.
- It can still **use signals from such events** (for example risk detections) when making access decisions.
- Network-level floods are handled by network services such as Azure DDoS Protection, in front of the application.
## Scope reminder
Conditional Access policies can target any users and groups, cloud and on-premises apps, and devices whether managed or not; the device signal simply gives more or less information.
W: Enforced after first factor: because policies run once first-factor authentication completes, Conditional Access shapes access decisions but is not a frontline control that absorbs denial-of-service floods.
X: A=Only Intune-enrolled devices: policies evaluate sign-ins from managed and unmanaged devices alike; device compliance is one optional signal and requirement, not a precondition for evaluation.
B=Only administrator accounts: requiring MFA for admins is a common policy, but policies can target any users and groups in the tenant.
D=Only on-premises apps: Conditional Access protects cloud apps such as Microsoft 365 as well as on-premises applications.
T: Conditional Access runs after the first factor; it is a decision engine, not a DoS shield.
V: Microsoft Entra Conditional Access, Azure DDoS Protection

@ SC-900 D2 T2.3 applied use-case
S: Sign-in logs show password-guessing attempts against mailboxes through old protocols that use basic authentication. Users with modern Outlook clients must keep working. What should the company do with Conditional Access?
A: Create a policy that requires every user to change the password at each sign-in until the guessing attempts stop happening.
B: Create a policy that targets legacy authentication clients and blocks them, leaving modern authentication clients unaffected.
C: Create a policy that requires an app protection policy for all browser sign-ins, which turns off legacy protocols automatically.
D: Create a policy that sets sign-in frequency to every time for all users, so that each request is checked again at the source.
K: B
G: ## Legacy authentication
Older protocols (for example some POP, IMAP and SMTP clients using basic authentication) send a user name and password with each request. They **cannot perform multifactor authentication** and **do not pass device state**, which makes them a favourite route for password spray and guessing attacks.
## The client apps condition
A Conditional Access policy can be scoped with the **client apps** condition to modern authentication clients (browser, mobile apps and desktop clients) or to legacy authentication clients. Microsoft lists "blocking sign-ins for users who try to use legacy authentication protocols" as one of the commonly applied policies.
## Example
Policy: users = all, client apps = Exchange ActiveSync clients and other clients, grant = **Block access**. Outlook with modern authentication is not in scope and keeps working; a script trying passwords over basic authentication is refused.
W: Block legacy authentication clients: scoping the policy to legacy clients and blocking them shuts the password-guessing route while modern authentication clients stay out of the policy's scope.
X: A=Password change at every sign-in: forcing constant password changes disrupts every user and does nothing to stop a protocol that cannot do MFA from being used for guessing.
C=App protection policy for browsers: this grant control requires Intune app protection on supported mobile client apps; it does not switch off legacy protocols, and the guessing traffic is not browser traffic.
D=Sign-in frequency every time: this session control forces reauthentication on modern clients but does not stop a basic authentication client from trying passwords.
T: Legacy authentication cannot do MFA, so the standard answer is a Conditional Access policy that blocks legacy authentication clients.
V: Microsoft Entra Conditional Access

@ SC-900 D2 T2.3 applied use-case
S: Staff may open a finance app either from a company-compliant device or, from any other device, after completing multifactor authentication. Which grant setting in a Conditional Access policy allows either path?
A: Select both controls with "Require all the selected controls" so that the user satisfies MFA and device compliance together.
B: Select both controls with "Require one of the selected controls" so that satisfying either MFA or device compliance is enough.
C: Select "Block access" together with an exclusion for compliant devices, so that only managed devices can open the finance app.
D: Select a session control for persistent browser sessions, so that devices which completed MFA once are remembered by the app.
K: B
G: ## Combining grant controls
When a Conditional Access policy grants access, an admin can select several controls and choose how they combine:
- **Require all the selected controls**: control **and** control. The user must satisfy every one.
- **Require one of the selected controls**: control **or** control. Any one is enough.
## Block versus grant
**Block access** is the most restrictive decision and needs careful testing (report-only mode, What If). It ends the sign-in; it cannot ask the user to prove anything.
## Example
Grant: `Require multifactor authentication` + `Require device to be marked as compliant`, combined with **one of**. A laptop managed and compliant in Intune signs in directly; a personal tablet gets an MFA prompt instead.
W: Require one of the selected controls: this OR combination lets a compliant device pass on its own and lets any other device pass by completing MFA, which is the stated requirement.
X: A=Require all the selected controls: this AND combination demands MFA and a compliant device on every sign-in, so personal devices would never get in.
C=Block with compliant exclusion: blocking everything except compliant devices removes the MFA path for other devices entirely.
D=Persistent browser session: this session control only decides whether the browser session stays signed in; it does not choose between MFA and device compliance.
T: "Either X or Y" in Conditional Access = select both grant controls and choose "Require one of the selected controls".

@ SC-900 D2 T2.3 applied use-case
S: Nurses share workstations on a ward and sign in to a patient portal through the browser. Management wants them prompted to sign in again after a set number of hours, even if the browser is left open. Which Conditional Access control fits?
A: The session control sign-in frequency, which sets how long a user can stay signed in before being asked to sign in again.
B: The grant control require an app protection policy, which applies Intune data rules to the browser before the portal opens.
C: The grant control require a password change, which makes each nurse pick a new password at the start of every new shift.
D: The condition named device platform, which detects the shared workstations and limits the portal to Windows computers only.
K: A
G: ## Grant controls versus session controls
Conditional Access has two kinds of access controls:
- **Grant controls** decide whether the sign-in may continue (block, or grant with requirements such as MFA or a compliant device).
- **Session controls** shape the experience **after** access is granted, inside specific cloud apps.
## Session controls to know
- **Sign-in frequency**: how long a user can stay signed in before being prompted to sign in again. Admins set hours or days, or require reauthentication every time.
- **Persistent browser session**: whether users stay signed in after closing and reopening the browser.
- **Application enforced restrictions**: passes device information to apps such as Exchange Online and SharePoint so they can offer a limited experience.
- **Conditional Access App Control**: routes the session through Microsoft Defender for Cloud Apps for real-time monitoring and control.
## Example
Sign-in frequency set to `8 hours` for the patient portal: a session started at 07:00 asks for sign-in again around 15:00.
W: Sign-in frequency: this session control is built to limit how long a session lasts before reauthentication, which is what shared ward workstations need.
X: B=App protection policy: this grant control applies Intune app protection to supported client apps; it does not time out sessions on a shared browser.
C=Require password change: this is mainly used to remediate risky users; forcing a new password every shift would be impractical and is not a session timeout.
D=Device platform condition: a condition only decides which sign-ins the policy applies to; it does not shorten how long anyone stays signed in, and the platform value comes from the device and is not verified.
T: Need to force reauthentication after a period of time = session control "sign-in frequency".
V: Microsoft Entra Conditional Access

@ SC-900 D2 T2.3 applied use-case
S: An administrator has written a Conditional Access policy that blocks sign-ins from several countries. Before turning it on, she wants to see which real sign-ins it would have affected, without blocking anyone yet. What should she use?
A: Security defaults, which apply a preset set of protections to all users and show their impact before they are enforced.
B: Report-only mode for the policy, which evaluates real sign-ins and records the result the policy would have produced.
C: An access review of the sign-in logs, in which reviewers approve or deny each past sign-in from the listed countries.
D: Privileged Identity Management eligibility for the policy, so it is activated only for a limited time while she tests it.
K: B
G: ## Testing a policy before enforcing it
A policy that blocks access can lock out people who should get in, so Microsoft recommends testing first.
- **Report-only mode** is a policy state. The policy is evaluated on every matching sign-in and the result (would have blocked, would have required MFA, and so on) is recorded in the sign-in logs, but nothing is enforced.
- Results can be analysed in the Conditional Access insights and reporting workbook.
- The **What If** tool answers the question for one simulated sign-in; report-only mode answers it for real traffic over time.
- Report-only mode works for most policies, except those scoped to "User actions".
## Example
The country block runs in report-only mode for two weeks. The log shows that a partner's support team signs in from one of the listed countries, so the admin adds an exclusion before switching the policy on.
W: Report-only mode: it evaluates the policy against real sign-ins and logs what it would have done without enforcing anything, which is exactly a safe impact test.
X: A=Security defaults: these are a fixed baseline (such as MFA registration and blocking legacy authentication) for tenants without custom policies; they do not preview a custom country block.
C=Access review of sign-in logs: access reviews recertify memberships and assignments; they do not replay past sign-ins against a draft policy.
D=PIM eligibility for the policy: PIM makes roles and group memberships eligible and time-bound; it cannot make a Conditional Access policy eligible.
T: Test a new Conditional Access policy on live traffic without enforcing it = report-only mode.

@ SC-900 D2 T2.3 applied comparison
S: Help desk staff need to reset users' passwords and update user profiles in Microsoft Entra ID. They must not be able to manage virtual machines in the company's Azure subscriptions. Which kind of role assignment fits?
A: A Microsoft Entra role such as User Administrator, because Microsoft Entra roles manage directory objects like users.
B: An Azure role such as Contributor on the subscription, because Azure roles manage everything inside the Azure tenant.
C: An Azure role such as Reader on the subscription, because reading resources includes resetting the passwords of users.
D: The Owner role on each resource group, because owners can manage both user accounts and the resources inside the group.
K: A
G: ## Two role-based access control systems
Microsoft uses role-based access control (RBAC) in two separate places:
- **Microsoft Entra roles** control access to **Microsoft Entra resources** such as users, groups and applications, through Microsoft Graph. Examples: Global Administrator, User Administrator, Billing Administrator.
- **Azure roles** (Azure RBAC) control access to **Azure resources** such as virtual machines and storage, through Azure Resource Manager. Examples: Owner, Contributor, Reader, Virtual Machine Contributor.
By default the two do not span each other: an Azure role on a subscription gives no rights over users in the directory, and a Microsoft Entra role gives no rights over virtual machines.
## Example
User Administrator can create and manage users and groups and change passwords for users (and some other admins). Giving help desk staff this role lets them handle password resets while they still cannot start or delete a VM.
W: Microsoft Entra role: password resets and profile changes are directory tasks, so a Microsoft Entra role such as User Administrator grants them without any rights over Azure resources.
X: B=Contributor on the subscription: Contributor manages Azure resources such as VMs, which is the opposite of what is wanted, and it gives no rights over users in the directory.
C=Reader on the subscription: Reader only views Azure resources; it has nothing to do with resetting user passwords in Microsoft Entra ID.
D=Owner on resource groups: Owner is an Azure role that grants full control of the resources in its scope, including VMs, and does not manage directory users.
T: Users, groups and passwords = Microsoft Entra roles; VMs, storage and other Azure resources = Azure roles.
V: Microsoft Entra ID, Azure role-based access control

@ SC-900 D2 T2.3 applied use-case
S: A developer must create and manage virtual machines, but only in the resource group for her project, and nowhere else in the subscription. How should access be granted under the principle of least privilege?
A: Assign her the Global Administrator role in Microsoft Entra ID, which includes the rights needed to manage every subscription.
B: Assign her the Owner role on the subscription, then ask her to work only in the resource group that belongs to her project.
C: Assign her the Virtual Machine Contributor Azure role with the scope set to the project's resource group and nothing wider.
D: Assign her the User Administrator role in Microsoft Entra ID, scoped to an administrative unit containing the project's users.
K: C
G: ## Role assignment = who + what + where
Every role assignment has three parts:
- **Security principal**: the user, group, service principal or managed identity that gets the permissions.
- **Role definition**: the collection of permissions (for example Virtual Machine Contributor lets you create and manage virtual machines).
- **Scope**: where the permissions apply.
## Azure scopes
Azure roles can be scoped at several levels: **management group, subscription, resource group or a single resource**. Permissions flow down from the scope you choose, so a narrower scope means less access.
## Least privilege in practice
Choose the most specific built-in role that covers the task and the narrowest scope that covers the resources. A resource-specific role at resource group scope is far smaller than Owner on the whole subscription.
W: Virtual Machine Contributor at resource group scope: the role covers creating and managing VMs, and the resource group scope keeps those rights inside her project only.
X: A=Global Administrator: this is the most powerful Microsoft Entra role and does not by default include Azure resource access; it is the opposite of least privilege.
B=Owner on the subscription: Owner grants full access to every resource in the subscription plus the right to assign roles; asking her to stay in one group does not limit what she can do.
D=User Administrator for an administrative unit: this Microsoft Entra role manages users and groups, not virtual machines, whatever administrative unit it is scoped to.
T: Least privilege in Azure RBAC = specific role + narrowest scope (management group > subscription > resource group > resource).
V: Azure role-based access control

@ SC-900 D2 T2.3 applied definition
S: A trainer explains how access is granted in Microsoft Entra role-based access control: an administrator creates a role assignment. Which set of elements makes up a role assignment?
A: A security principal, a role definition that lists permissions, and a scope that limits where those permissions apply.

D=Risk levels and remediation: these come from Microsoft Entra ID Protection and risk-based Conditional Access, not from role assignments.
T: Role assignment = who (security principal) + what (role definition) + where (scope).

## Why MFA alone is not enough here
The password itself is known to attackers. Passing MFA proves the person signing in now is the owner, but the exposed password remains; changing it removes the cause.
W: Secure password change: a user risk policy can require it, and once the user completes it the leaked credential is no longer valid and the user risk is remediated automatically.
X: A=Trusted named location: named locations can lower sign-in risk calculations, but they do not replace a leaked password or remediate user risk.
B=MFA once, keep the password: MFA is the typical remediation for risky sign-ins; for leaked credentials the exposed password must be changed.
D=Accept terms of use: terms of use is a grant control for acknowledging policies and has no effect on a compromised password.
T: Leaked credentials = user risk; remediate with a secure password change through a user risk-based policy.

G: ## Risk-based Conditional Access
Conditional Access has two risk conditions powered by ID Protection: **sign-in risk** and **user risk**. During each sign-in, ID Protection sends the detected risk level to Conditional Access, which applies the matching policy. This needs Microsoft Entra ID P2.
## Sign-in risk policies
Admins can configure sign-in risk-based policies to block access, allow access, **require multifactor authentication**, or require reauthentication (sign-in frequency).
- Users are prompted only when the sign-in reaches the chosen level, for example medium or high.
- If the user completes MFA, the risky sign-in event is **self-remediated**, which reduces noise for administrators.
## Example
Policy: all users, sign-in risk = medium and high, grant = require MFA. An employee signing in from a hotel on an unfamiliar network gets an MFA prompt and continues; an attacker with only the password is stopped.
W: Sign-in risk condition with MFA: this is the documented risk-based policy; the genuine user self-remediates by completing MFA while an attacker with only a password cannot.
X: B=Device platform with block: this ignores risk entirely and would block every sign-in on every platform.
C=Monthly access review: risk is evaluated in real time at sign-in; a monthly manual review cannot challenge the risky sign-in when it happens.
D=PIM approval by risk: PIM controls activation of privileged roles; it does not challenge ordinary risky sign-ins to apps.
T: Risky sign-in = Conditional Access sign-in risk condition + require MFA (self-remediation).

@ SC-900 D2 T2.4 applied definition
S: A trainer sorts Microsoft Entra ID Protection detections into user risk and sign-in risk. Which TWO of these detections are sign-in risk detections? (Select TWO)
A: Anonymous IP address, raised when a sign-in comes from an anonymizing source such as Tor or an anonymous VPN.
B: Leaked credentials, raised when the user's valid credentials have been found in a known public breach dump.
C: Atypical travel, raised for two sign-ins from distant places within too short a time to travel between them.
D: Anomalous user activity, raised when the account's directory changes look unusual compared to its baseline.
E: Suspicious sending patterns, raised when the user's mailbox shows unusual patterns of outgoing email over time.
K: A,C
G: ## Sign-in risk detections
Sign-in risk detections look at **one authentication request**:
- **Anonymous IP address**: sign-in from an anonymous IP address such as the Tor browser or an anonymous VPN (real time).
- **Atypical travel**: two sign-ins from geographically distant locations, where the time between them is shorter than the time needed to travel (real time).
- Others include unfamiliar sign-in properties, malicious IP address and password spray.
## User risk detections
User risk detections look at **the account** over time:
- **Leaked credentials**: the user's valid credentials appeared in a known breach (offline, always high).
- **Anomalous user activity**, **suspicious sending patterns**, possible attempts to access the Primary Refresh Token, and others.
## Memory hook
If it is about *where or how this sign-in happened*, it is sign-in risk. If it is about *what is happening to the account*, it is user risk.
W: A=Anonymous IP address: this detection is calculated on the sign-in itself, based on the anonymizing network it comes from, so it is a sign-in risk.
C=Atypical travel: this compares the locations and timing of sign-ins, which makes it a sign-in risk detection.
X: B=Leaked credentials: this is a user risk detection about the account's exposed password, not about a particular sign-in.
D=Anomalous user activity: this flags unusual behaviour of the account in the directory, so it is listed under user risk.
E=Suspicious sending patterns: this looks at the account's email behaviour over time and is a user risk detection.
T: Anonymous IP and atypical travel are sign-in risks; leaked credentials and anomalous account behaviour are user risks.
V: Microsoft Entra ID Protection

K: D
G: ## Investigating risk
ID Protection tracks every risk detected on an identity and gives administrators **three key reports**:
- **Risk detections**: each risk detected is reported as a risk detection.
- **Risky sign-ins**: a sign-in with one or more risk detections.
- **Risky users**: a user with one or more risky sign-ins or risk detections.
Admins can take manual actions such as dismiss user risk, confirm safe or confirm compromise.
## Making use of the data
- Risk data can be collected with **Microsoft Graph APIs** for processing in a SIEM.
- ID Protection can be connected to **Microsoft Sentinel** with a data connector.
- Diagnostic settings can send data to a Log Analytics workspace, a storage account or Event Hubs for longer retention.
W: Risk reports and export: the risky users, risky sign-ins and risk detections reports are where risk is investigated, and the data can be sent to Microsoft Sentinel for correlation.
X: A=What If tool: What If simulates which Conditional Access policies apply to one sign-in; it does not list risky accounts or send data to Sentinel.
B=Access review history: access reviews record decisions about continued access, not risk detections, and Sentinel can connect to many identity data sources.
C=PIM audit history: PIM audits privileged role assignments and activations; it is not where user risk levels are reported.
T: Investigate identity risk in ID Protection's risky users, risky sign-ins and risk detections reports; export them to a SIEM such as Sentinel.
V: Microsoft Entra ID Protection, Microsoft Sentinel
