@ SC-900 D3 T3.1 applied comparison
S: An online retailer runs its storefront on virtual machines in an Azure virtual network with public IP addresses. It has not purchased anything for DDoS defense. Management now wants access to Microsoft's DDoS rapid response team during attacks and service credits for scale-out costs caused by a documented attack. What should the retailer enable?
A: Nothing extra, because the default Azure DDoS infrastructure protection already includes rapid response support and cost protection
B: Azure DDoS Network Protection on the virtual network, which adds DDoS rapid response support and cost protection to the core mitigation
C: Azure Web Application Firewall on Application Gateway, which handles volumetric attacks and provides rapid response and cost protection
D: Azure Firewall Premium in front of the VMs, whose intrusion detection signatures include DDoS rapid response and cost guarantees
K: B
G: ## Layers of DDoS protection in Azure
A distributed denial of service (DDoS) attack tries to exhaust an application's resources so legitimate users cannot reach it. Any endpoint that is publicly reachable from the internet can be targeted.
- **DDoS infrastructure protection** is on by default at no additional cost for every Azure service that uses public IPv4 and IPv6 addresses. It defends against common network-layer attacks.
- **Azure DDoS Protection** is the paid service with two tiers that add mitigation automatically tuned to your own resources:
- **DDoS Network Protection** protects the resources in a virtual network and adds the value-added services: **DDoS rapid response (DRR)** support, **cost protection** (service credits for data transfer and scale-out costs from documented attacks) and a WAF discount.
- **DDoS IP Protection** is pay-per-protected-IP with the same core engineering features, but without rapid response support, cost protection or the WAF discount.
## Example
A retailer enables DDoS Network Protection on its storefront VNet. During a large SYN flood, its team engages the rapid response team and later claims credits for the extra VM instances the attack forced it to run.
W: DDoS Network Protection: it is the tier whose feature list includes DDoS rapid response support and cost protection, on top of always-on monitoring and automatic L3/L4 mitigation for the virtual network's resources.
X: A=Default infrastructure protection: the free platform protection defends against common network-layer attacks but is not tuned to your resources and has no rapid response team or cost protection.
C=Web Application Firewall: a WAF filters layer 7 web requests such as SQL injection; it is not a DDoS tier and does not come with rapid response support or a cost guarantee.
D=Azure Firewall Premium: its IDPS detects malicious traffic patterns for inspection and filtering, but rapid response and cost protection are services of Azure DDoS Network Protection, not of a firewall SKU.
T: Free infrastructure protection covers everyone; DDoS Network Protection adds tuned mitigation plus rapid response support and cost protection.
V: Azure DDoS Protection

@ SC-900 D3 T3.1 applied tradeoff
S: A small company exposes only two public IP addresses in Azure: one for a web server and one for a VPN endpoint. It wants DDoS mitigation tuned to these resources at the lowest cost, without creating a DDoS protection plan, and it does not need the rapid response team. Which option fits best?
A: Azure DDoS IP Protection enabled on each of the two public IP resources, billed per protected IP address
B: Azure DDoS Network Protection with a protection plan linked to the virtual network that holds both resources
C: Azure Firewall Basic deployed in front of both resources, because it includes DDoS mitigation for its public IPs
D: Network security groups with deny rules on both subnets, because they drop flood traffic before it reaches Azure
K: A
G: ## Two tiers of Azure DDoS Protection
- **DDoS Network Protection**: you create a **DDoS protection plan** and enable it on virtual networks. Everything with a public IP in those VNets is protected. One plan can be used across multiple subscriptions in a tenant. Priced per 100 protected IP addresses, and it includes rapid response support, cost protection and a WAF discount.
- **DDoS IP Protection**: a **pay-per-protected-IP** model. You enable it directly on a public IP resource; **no protection plan is needed**. It has the same core engineering features (always-on monitoring, adaptive tuning, automatic L3/L4 mitigation, metrics, alerts and reports) but not the value-added services.
## Choosing
A handful of public IPs and no need for rapid response or cost protection points to IP Protection. Many protected resources across virtual networks, or a need for the extra services, points to Network Protection.
W: DDoS IP Protection: it is enabled per public IP without a protection plan, is billed per protected IP, and gives the same core tuned mitigation, which matches two IPs and no need for rapid response.
X: B=DDoS Network Protection: it requires a protection plan and is priced for protecting a whole virtual network (per 100 IPs), which is more than the company needs and contradicts the no-plan requirement.
C=Azure Firewall Basic: Azure Firewall filters traffic with rules and threat intelligence alerts; DDoS mitigation tuned to the resources is a separate service, Azure DDoS Protection.
D=NSG deny rules: NSGs allow or deny flows by IP, port and protocol inside the virtual network; they are not a DDoS mitigation service and do not absorb volumetric floods aimed at public IPs.
T: Few public IPs, no plan, no rapid response needed: DDoS IP Protection; whole VNets plus extra services: DDoS Network Protection.
V: Azure DDoS Protection

@ SC-900 D3 T3.1 applied use-case
S: A company has eight Azure subscriptions in one Microsoft Entra tenant, each with virtual networks that host public-facing services. It wants Azure DDoS Network Protection for all of them. How should it plan the DDoS protection plans?
A: Create one DDoS protection plan in each subscription, because a plan can only protect virtual networks in its own subscription
B: Create one DDoS protection plan per virtual network, because each plan learns the traffic profile of exactly one network
C: Create a single DDoS protection plan and use it for virtual networks across the subscriptions in the tenant
D: Create no plan, because DDoS Network Protection is switched on automatically for every subscription in the tenant
K: C
G: ## How DDoS Network Protection is applied
DDoS Network Protection is configured through a **DDoS protection plan**. You enable the plan on virtual networks, and every resource with a public IP in those networks is protected immediately, with no application changes.
## One plan for the tenant
Microsoft's guidance is that under a tenant, a **single DDoS protection plan can be used across multiple subscriptions**, so there is no need to create more than one plan. The tuning is still per resource: Azure DDoS Protection applies auto-tuned mitigation policies (TCP SYN, TCP, UDP) for **each public IP** of the protected resources.
## What is automatic and what is not
DDoS infrastructure protection is automatic and free for all Azure public IPs. DDoS Network Protection is a paid tier that you choose to enable.
W: Single plan across subscriptions: one DDoS protection plan can protect virtual networks in multiple subscriptions under the same tenant, so the company needs only one.
X: A=One plan per subscription: plans are not limited to their own subscription; Microsoft states that more than one plan is not needed in a tenant.
B=One plan per virtual network: tuning happens per protected public IP, not per plan, so one plan can cover many virtual networks.
D=Automatic for every subscription: only the basic infrastructure protection is automatic; DDoS Network Protection must be enabled through a protection plan.
T: Under one tenant, a single DDoS protection plan can cover virtual networks in many subscriptions.
V: Azure DDoS Protection

@ SC-900 D3 T3.1 applied definition
S: A security lead is explaining to new staff what Azure DDoS Network Protection does once it is enabled on a virtual network. Which TWO statements are correct? (Select TWO)
A: It monitors application traffic patterns around the clock and automatically mitigates an attack as soon as it is detected
B: It learns each protected resource's traffic over time and adjusts the mitigation profile as the traffic changes
C: It inspects HTTP requests for SQL injection and cross-site scripting and blocks them at the application layer
D: It requires each protected application to be redeployed with a DDoS agent before mitigation can start working
E: It decrypts outbound TLS traffic so that malware inside encrypted sessions can be detected and blocked
K: A,B
G: ## What Azure DDoS Protection provides
Azure DDoS Protection works at **layer 3 and layer 4** (network and transport). Its key features include:
- **Always-on traffic monitoring**: traffic patterns are watched 24 hours a day, 7 days a week for signs of a DDoS attack; once detected, the attack is mitigated instantly and automatically.
- **Adaptive real-time tuning**: intelligent traffic profiling learns your application's traffic over time and updates the profile as traffic changes.
- **Analytics, metrics and alerting**: attack reports, Azure Monitor metrics and alerts at the start and stop of an attack.
- **Turnkey protection**: enabling it immediately protects all resources in the virtual network, with no application or resource changes.
## What it does not do
Layer 7 web attacks need a **web application firewall (WAF)**. Decrypting and inspecting TLS traffic is a feature of **Azure Firewall Premium**. Used together, DDoS Protection and a WAF give multilayered protection.
W: A=Always-on monitoring: traffic is monitored continuously and a detected attack is mitigated automatically, without waiting for an operator.
B=Adaptive tuning: traffic profiling learns the application's normal traffic and keeps the mitigation profile up to date as it changes.
X: C=SQL injection and XSS: those are layer 7 web exploits handled by Azure Web Application Firewall; DDoS Protection works at layers 3 and 4.
D=Redeploy with an agent: protection is simple to enable on new or existing virtual networks and requires no application or resource changes.
E=TLS decryption: outbound TLS inspection is a feature of Azure Firewall Premium, not of a DDoS mitigation service.
T: DDoS Protection gives always-on, automatically tuned L3/L4 mitigation without application changes; layer 7 needs a WAF.
V: Azure DDoS Protection

@ SC-900 D3 T3.1 applied use-case
S: A company has several spoke virtual networks in Azure. It wants one managed, stateful service that controls outbound internet traffic from all of them, allowing only approved fully qualified domain names such as an update site, and logs every allowed and denied connection. Which service should it deploy?
A: Network security groups on every subnet, with outbound rules that list the approved domain names for each spoke
B: Azure DDoS Network Protection on each spoke, with a protection plan that blocks traffic to unapproved domains
C: Azure Web Application Firewall on Application Gateway, which filters outbound requests from virtual machines
D: Azure Firewall in a central virtual network, with application rules that allow only the approved domain names
K: D
G: ## What Azure Firewall is
**Azure Firewall** is a cloud-native, intelligent network firewall security service: a **fully stateful firewall as a service** with built-in high availability and cloud scalability. It inspects both **east-west** (between networks inside Azure) and **north-south** (to and from the internet) traffic.
## Features that matter here
- **Application rules with FQDN filtering**: allow or deny outbound traffic by fully qualified domain name, for example `*.windowsupdate.com`. **FQDN tags** such as the Windows Update tag make well-known services easy to allow.
- **Network rules** filter by source, destination, port and protocol (5-tuple).
- **SNAT and DNAT**: outbound traffic leaves through the firewall's public IP; inbound traffic to that IP can be translated to private addresses.
- **Logging and SIEM integration** for every rule decision.
## Central deployment
A common design places one firewall in a hub virtual network and routes spoke traffic through it, so policy is defined once.
W: Azure Firewall: a stateful firewall as a service that can sit in a central network, filter outbound traffic with FQDN-based application rules and log the decisions for all spokes.
X: A=NSGs with domain names: NSG rules filter by IP address, CIDR, service tag or application security group, port and protocol; they cannot match fully qualified domain names.
B=DDoS Network Protection: it mitigates volumetric L3/L4 attacks against public IPs and has no rules for allowing or blocking outbound destinations.
C=WAF on Application Gateway: a WAF protects inbound web applications from exploits such as SQL injection; it is not an outbound egress filter for virtual machines.
T: Central, stateful control of outbound traffic with FQDN rules is Azure Firewall, not NSGs, WAF or DDoS Protection.
V: Azure Firewall

@ SC-900 D3 T3.1 applied comparison
S: A payment processor is moving a card-processing workload to Azure. Its auditors require the network firewall to decrypt and inspect outbound TLS traffic and to run signature-based intrusion detection and prevention. Which Azure Firewall SKU meets this?
A: Azure Firewall Basic, which includes TLS inspection and IDPS for small and medium-sized business environments
B: Azure Firewall Standard, which includes TLS inspection and IDPS alongside threat intelligence and web categories
C: Azure Firewall Premium, which adds outbound TLS inspection and fully managed IDPS to the Standard capabilities
D: Any Azure Firewall SKU, because TLS inspection and IDPS are core features that every SKU includes by default
K: C
G: ## The three Azure Firewall SKUs
- **Basic**: for small and medium-sized businesses; essential protection, throughput up to about 250 Mbps; threat intelligence in **alert mode only**.
- **Standard**: L3-L7 filtering, threat intelligence that can **alert and deny**, DNS proxy, custom DNS, web categories, autoscaling to higher throughput.
- **Premium**: everything in Standard plus advanced threat protection for highly sensitive workloads such as **payment processing**:
- **TLS inspection**: decrypts outbound traffic, inspects it and re-encrypts it.
- **IDPS**: signature-based intrusion detection and prevention that identifies known malicious patterns (malware, phishing, coin mining, Trojans).
- **URL filtering** on the full path.
## Example
A card processor uses Premium so malware hidden inside an HTTPS download is decrypted, matched against an IDPS signature and blocked.
W: Azure Firewall Premium: it is the only SKU with TLS inspection and fully managed IDPS, and Microsoft positions it for sensitive applications such as payment processing.
X: A=Basic: Basic covers essential protection with threat intelligence alerts only; it has neither TLS inspection nor IDPS.
B=Standard: Standard adds threat intelligence deny, DNS proxy and web categories, but the feature list shows TLS inspection and IDPS as not supported.
D=Any SKU: the feature comparison marks TLS inspection and IDPS for Premium only, so choosing Basic or Standard would fail the audit.
T: TLS inspection and IDPS mean Azure Firewall Premium.
V: Azure Firewall

@ SC-900 D3 T3.1 applied troubleshooting
S: A small business deployed Azure Firewall Basic and enabled threat intelligence-based filtering. A report shows that traffic to a known malicious IP address was recorded as an alert but was still allowed through the firewall. What explains this?

B: Threat intelligence in the Basic SKU runs in alert mode only; denying the traffic requires the Standard or Premium SKU

Azure Firewall can use the **Microsoft Threat Intelligence feed** to recognise traffic from or to **known malicious IP addresses and domains**. The feed updates in real time to cover new and emerging threats.

- **Standard**: alert and deny.
- **Premium**: alert and deny.

@ SC-900 D3 T3.1 applied use-case
S: A large enterprise runs dozens of Azure Firewall instances across many subscriptions and in Virtual WAN secured hubs. The security team wants to define a common set of network and application rules once and apply it to all of these firewalls. What should it use?
A: Azure Firewall Manager with firewall policies applied to the firewalls in the tenant
B: An Azure DDoS protection plan linked to every virtual network that hosts a firewall
C: A single network security group associated with the subnet of each firewall instance
D: Azure Key Vault storing the rule set as a secret that each firewall downloads at startup

G: ## Central management of many firewalls
**Azure Firewall Manager** provides a central place to manage Azure Firewalls across multiple subscriptions. It uses **firewall policies** to apply a common set of **network and application rules** and configurations to the firewalls in a tenant.
- It supports firewalls in ordinary **virtual networks** and in **Virtual WAN secured virtual hubs**.
- Secured hubs use Virtual WAN route automation, so routing traffic through the firewall takes only a few steps.

Without central policy, each firewall's rules drift apart over time. One policy, applied everywhere, keeps the organisation's rules consistent and easier to audit.
W: Firewall Manager with firewall policies: it is built to apply one common set of network and application rules to Azure Firewalls across subscriptions, in both virtual networks and secured hubs.
X: B=DDoS protection plan: a plan applies DDoS mitigation to virtual networks; it holds no firewall rules and cannot configure Azure Firewall.

@ SC-900 D3 T3.1 applied comparison
S: An architect is deciding whether to add Azure Firewall or rely only on network security groups. Which TWO capabilities does Azure Firewall provide that network security groups do not? (Select TWO)
A: Filtering of outbound traffic by fully qualified domain name in application rules, such as allowing one update site
B: Alerting on and denying traffic to known malicious IP addresses and domains using a Microsoft threat intelligence feed
C: Allowing or denying traffic based on the source IP address, destination IP address, port and protocol of each flow
D: Association directly with a virtual machine's network interface so that its rules apply to that one virtual machine
E: Default rules that let resources in the same virtual network talk to each other while denying inbound internet traffic
K: A,B
G: ## Two layers of network filtering
- A **network security group (NSG)** is a list of allow/deny rules evaluated on the **five-tuple**: source, source port, destination, destination port and protocol. Sources and destinations can be IP addresses, CIDR blocks, service tags or application security groups. An NSG is associated with a **subnet** or a **network interface** and comes with default rules (for example AllowVNetInBound and DenyAllInbound).
- **Azure Firewall** is a managed, stateful firewall service, usually deployed centrally. Besides 5-tuple network rules it adds **application-level FQDN filtering**, **threat intelligence-based filtering**, SNAT/DNAT, web categories (Standard and Premium) and, in Premium, TLS inspection and IDPS.
## Using both
They are complementary: NSGs give fine-grained filtering close to each workload, and Azure Firewall gives central control with richer inspection.
W: A=FQDN filtering: Azure Firewall application rules can allow or deny traffic by domain name; NSG rules have no domain-name field.
B=Threat intelligence: Azure Firewall can alert on and deny traffic to known malicious IPs and domains from the Microsoft Threat Intelligence feed (deny needs Standard or Premium); NSGs have no such feed.
X: C=5-tuple filtering: both services filter on source, destination, port and protocol; this is the core of every NSG rule, so it is not unique to Azure Firewall.
D=NIC association: associating rules with a subnet or a network interface is how NSGs work; Azure Firewall is a separate service deployed in its own subnet.
E=Default VNet rules: AllowVNetInBound and DenyAllInbound are the default rules every NSG gets, not features of Azure Firewall.
T: NSGs filter on the five-tuple near the workload; Azure Firewall adds FQDN filtering, threat intelligence and deeper inspection centrally.
V: Azure Firewall, network security groups

@ SC-900 D3 T3.1 applied use-case
S: A company's public web application has been hit by SQL injection and cross-site scripting attempts. The developers cannot patch every vulnerable page quickly, so the security team wants a central control that blocks these common web exploits before requests reach the app. What should it deploy?
A: Azure DDoS IP Protection on the application's public IP address, which blocks malicious HTTP payloads
B: Azure Bastion in the application's virtual network, which hides the web servers from the internet entirely
C: Azure Web Application Firewall with Application Gateway, using the managed rule set for common exploits
D: A network security group that allows only TCP port 443 inbound to the subnet that hosts the web servers
K: C
G: ## What a web application firewall does
Web applications are frequent targets of attacks that exploit well-known vulnerabilities; **SQL injection** and **cross-site scripting (XSS)** are among the most common. Fixing every one in application code needs constant patching and monitoring.
**Azure Web Application Firewall (WAF)** gives **centralized protection** of web applications from these exploits. Because it is central, a known vulnerability can be "patched" once in the WAF instead of in every application.
## Where it runs
Azure WAF is deployed with **Azure Application Gateway** (regional) or **Azure Front Door** (global edge). On Application Gateway it uses managed rule sets based on the OWASP Core Rule Set, plus custom rules you write.
## Example
A request with `' OR 1=1 --` in a query string matches a SQL injection rule, and the WAF in prevention mode returns a 403 instead of passing it to the app.
W: WAF on Application Gateway: it inspects HTTP requests at layer 7 and its managed rules block common exploits such as SQL injection and XSS centrally, without changing the application.
X: A=DDoS IP Protection: DDoS Protection mitigates L3/L4 floods; it does not read HTTP payloads, so it cannot recognise SQL injection.
B=Azure Bastion: Bastion provides secure RDP/SSH to VMs for administrators; public web traffic still has to reach the app and would not be inspected.
D=NSG allowing 443: limiting the port still lets the malicious requests in, because SQL injection and XSS travel inside normal HTTPS requests.
T: Layer 7 exploits like SQL injection and XSS are stopped by Azure Web Application Firewall, not by NSGs or DDoS Protection.
V: Azure Web Application Firewall, Azure Application Gateway

@ SC-900 D3 T3.1 applied tradeoff
S: A team is about to enable Azure Web Application Firewall on Application Gateway for a busy production site. It worries that the managed rules might block some legitimate requests. Microsoft's guidance suggests a way to start. What should the team do first?
A: Run the WAF in prevention mode from day one, because detection mode turns off the managed rule sets entirely
B: Leave the WAF disabled and rely on a network security group until the developers finish their code review
C: Run the WAF in detection mode for a short period, review the WAF logs, then add exceptions and switch to prevention
D: Delete all managed rules and write only custom rules, because managed rules cannot be tuned with exclusions
K: C
G: ## WAF modes
Azure WAF on Application Gateway can run in two modes:
- **Detection mode**: monitors and logs all threat alerts but **does not block** incoming requests. WAF logging must be turned on to see the results.
- **Prevention mode**: **blocks** intrusions and attacks that the rules detect; the attacker receives a 403 response and the connection is closed. Attacks are still recorded in the WAF logs.
## Microsoft's recommendation
Run a newly deployed WAF in **detection mode for a short period** in production. The logs show which legitimate requests would have been blocked, so you can add **exclusions** or **custom rules** before switching to prevention mode. This reduces unexpected blocked traffic.
## Rule types
A WAF policy has managed rule sets (Azure-managed, preconfigured) and custom rules (yours). Exclusion lists can omit certain request attributes from evaluation.
W: Detection mode first: the WAF logs what it would block without blocking it, so the team can tune exceptions and then move to prevention mode, exactly as Microsoft recommends for new deployments.
X: A=Prevention from day one: detection mode does not turn off the rules; it evaluates and logs them without blocking. Starting in prevention mode risks the very false positives the team fears.
B=Disable and use an NSG: an NSG filters by IP, port and protocol and cannot see web exploits, so the site would stay unprotected at layer 7.
D=Only custom rules: managed rule sets provide the common exploit protection and can be tuned with exclusions; dropping them throws away most of the protection.
T: Start a new WAF in detection mode, tune using the logs, then switch to prevention mode.
V: Azure Web Application Firewall

S: A streaming service has users on several continents and its web front end is delivered through Azure Front Door. @ SC-900 D3 T3.1 applied use-case
S: A regional bank's customer portal sits behind Azure Application Gateway with Web Application Firewall enabled. Because the bank serves customers in only one country, it wants to block requests coming from all other countries or regions. What WAF feature meets this need?
A: The Bot Manager rule set, which classifies requests from foreign countries as bad bots and blocks them
B: A custom rule that uses geo-filtering to allow the home country and block other countries or regions
C: Detection mode, which logs requests from foreign countries so administrators can block them manually later
D: The OWASP Core Rule Set, which includes a default rule that blocks traffic from outside the home country

A WAF policy contains two kinds of rules:
- **Managed rule sets**: Azure-managed, preconfigured rules (on Application Gateway, based on the OWASP Core Rule Set) for common exploits, plus the **Bot Manager rule set** for bot traffic.

## Geo-filtering
Custom rules can **geo-filter** traffic, allowing or blocking certain countries or regions, using the `Geomatch` operator. Example: a rule with priority 10 that blocks any request whose source country is not the bank's home country.
W: Geo-filtering custom rule: Azure WAF lets you create custom rules that allow or block traffic from specific countries or regions, which is exactly the bank's requirement.
X: A=Bot Manager: the bot rule set categorizes requests as bad, good or unknown bots by behaviour and reputation, not by the country a human visitor comes from.
C=Detection mode: detection mode only logs and never blocks, so foreign requests would keep reaching the portal.
D=OWASP Core Rule Set: the CRS targets exploit patterns such as SQL injection and XSS; it has no built-in country blocking, which is configured through custom rules.
T: Blocking by country is done with a WAF custom rule using geo-filtering.

@ SC-900 D3 T3.1 applied use-case
S: A company wants multilayered protection for a public web application in an Azure virtual network: resilience against volumetric network floods and protection against layer 7 attacks on the web requests themselves. Which TWO services together meet this goal? (Select TWO)
A: Azure DDoS Protection on the virtual network, which mitigates layer 3 and layer 4 attacks

G: ## How NSG rules are processed
Each NSG rule has a **priority** from 100 to 4096. Rules are processed in priority order: **lower numbers first**, because a lower number means a higher priority. **Once traffic matches a rule, processing stops**, so later rules are never evaluated for that traffic.
## Default rules
Every NSG also has default rules at the very lowest priority (65000 and above), such as `AllowVNetInBound` and `DenyAllInbound`. You cannot remove them, but you override them with your own rules at higher priority.
## Example
To let IT in while blocking everyone else, give the allow rule for the IT range priority 100 and the general deny rule priority 200, or simply rely on `DenyAllInbound`.
W: Lowest number wins: the deny rule at priority 100 matches the RDP traffic first, processing stops there, and the allow rule at 200 is never reached.
X: B=Higher numbers are outbound only: direction is a separate property of each rule; priority numbers do not decide whether a rule is inbound or outbound.
C=Allow before deny: NSGs evaluate by priority number, not by action, so a deny with a lower number is processed before an allow.
D=Rules cancel out: rules never cancel each other; the first matching rule decides, and the default inbound rule for internet traffic is a deny, not an allow.
T: NSG rules run from the lowest priority number up, and the first match decides.
