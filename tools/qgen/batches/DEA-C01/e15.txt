G: ## Distribution keys and sort keys in Redshift
A Redshift cluster spreads each table's rows across compute node slices. The **distribution style** (`AUTO`, `EVEN`, `KEY` or `ALL`) decides which slice a row lands on; the **sort key** decides the order of rows on disk inside each slice.
- `DISTKEY(customer_id)` on the fact table and on the dimension table it joins most often places matching `customer_id` values on the same slice, so the join runs locally with no network redistribution (a "collocated join"). AWS recommends distributing the fact table and one dimension table on their common column.
- `SORTKEY(order_date)` stores rows in date order. Redshift keeps min/max values for every 1 MB block (zone maps), so a filter like `WHERE order_date >= '2026-01-01'` skips whole blocks that cannot match.
## Where ALL distribution fits
`ALL` puts a full copy of a table on every node. It multiplies storage by the node count and slows loads and updates, so it suits only slow-moving tables. It helps most for a mid-sized dimension that cannot be collocated with the fact table; for a small dimension, redistributing it at query time is cheap, so `ALL` gives little benefit there. For a large, frequently loaded fact table it is the wrong choice.
## Example
An orders fact table with billions of rows joined to `customers` on `customer_id` and filtered by last month's `order_date`: with these keys, the join avoids moving rows between nodes and the scan reads only the blocks for last month.
W: DISTKEY customer_id and SORTKEY order_date: the distribution key matches the join column so joins are collocated, and the sort key matches the filter column so zone maps prune blocks during scans.
X: A=Sort on customer_id with EVEN: EVEN distribution places rows round-robin regardless of `customer_id`, so matching rows must be redistributed for every join, and sorting on the join column does little for the `order_date` filters that dominate the workload.
B=Unused sort column with ALL on the fact table: a sort key that never appears in filters prunes nothing, and ALL copies the entire large fact table to every node, multiplying storage and load time; AWS limits ALL to slow-moving tables, typically a dimension that cannot be collocated, never a big fact table.
D=No keys, decided at query time: Redshift cannot pick a physical layout per query. AUTO distribution and automatic sort keys are adjusted in the background over time, but when the join and filter columns are well known, choosing them explicitly gives the predictable win the question asks for.
T: Distribute the fact table and its main dimension on the join column to avoid shuffling rows between nodes, and sort on the filter column so zone maps skip blocks; reserve ALL for slow-moving dimensions that cannot be collocated.
