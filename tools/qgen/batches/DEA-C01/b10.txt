@ DEA-C01 D1 T1.1 expert troubleshooting
S: A manufacturer streams machine telemetry into a provisioned Kinesis data stream with 24 shards, using plant_id as the partition key. There are 12 plants and about 40,000 sensors, and the consumer computes rolling averages that need each sensor's readings in order. CloudWatch shows stream-level IncomingBytes of about 9 MB per second, yet WriteProvisionedThroughputExceeded errors occur on only three shards. The busiest plant alone sends about 2.6 MB per second, with each sensor sending under 2 KB per second. The team must stop the throttling without losing per-sensor ordering. What should the data engineer do?
A: Change the producers' partition key from plant_id to sensor_id, so the load spreads across all 24 shards while each sensor's readings stay on one shard
B: Split the three throttled shards with SplitShard until each child shard has a narrower hash key range that can absorb the busiest plant's 2.6 MB per second
C: Switch the stream to on-demand capacity mode, so Kinesis Data Streams splits hot shards automatically whenever a shard's incoming traffic exceeds its limit
D: Keep plant_id but append a random suffix from 0 to 3 to every record's partition key, so each plant's traffic is spread over four separate hash key values
K: A
G: ## How Kinesis places records on shards
Kinesis hashes each record's **partition key** (MD5) to a 128-bit value; the shard whose hash key range contains that value receives the record. Every record with the same key lands on the **same shard**, which is what preserves ordering for that key.
Each shard accepts writes of up to **1 MB per second or 1,000 records per second**.
## Working the numbers
- 24 shards give 24 MB/s of write capacity; the stream receives only 9 MB/s, so total capacity is not the problem.
- With only **12 distinct keys**, at most 12 of the 24 shards ever receive data, and two plants may even share a shard.
- One key (the busiest plant) produces 2.6 MB/s, but a single key always maps to a single shard, so that shard is asked for 2.6 times its 1 MB/s limit. This is a **hot partition key**.
## Why a finer key fixes it
With `sensor_id` (about 40,000 values, each under 2 KB/s), the hash values spread evenly over all 24 shards, about 0.375 MB/s each, and every sensor still maps to exactly one shard.
W: A=Partition key sensor_id: thousands of small keys spread 9 MB/s across all shards at roughly 0.4 MB/s each, and because one sensor always hashes to one shard, its readings stay in order.
X: B=SplitShard: a split divides a shard's hash key range, but one partition key is one hash value. All of the busiest plant's 2.6 MB/s would still land in a single child shard, which still has a 1 MB/s limit.
C=On-demand mode: on-demand mode adapts to uneven traffic only until a single partition key exceeds one shard's 1 MB/s or 1,000 records/s, and it does not isolate hot keys. The 2.6 MB/s plant key still throttles.
D=Random suffix: salting the key does spread the plant over four hash values (about 0.65 MB/s each), but one sensor's readings now land on different shards at random, so their order is lost and the rolling averages break.
T: When only a few shards throttle while total throughput is low, look for a hot partition key; choose a higher-cardinality key at the level where ordering is needed.
V: Amazon Kinesis Data Streams, Amazon CloudWatch

@ DEA-C01 D1 T1.1 expert use-case
S: A Lambda function consumes a 6-shard Kinesis data stream (24-hour retention) with the default event source mapping settings and loads orders into a database; each invocation runs for up to 60 seconds. Last week one malformed record made the function fail on every attempt, its shard stalled until the record aged out a day later, and the record was gone with no trace. New rules: a bad record may stall its shard for at most about 5 minutes, records that come before it in the same batch must not be loaded again, and the full content of every discarded record must be kept 90 days for replay. Finance will not pay for longer stream retention. Which THREE changes meet these rules? (Select THREE)
A: Add ReportBatchItemFailures to FunctionResponseTypes, and have the function return the sequence number of the first record that failed in each batch
B: Set MaximumRetryAttempts on the event source mapping to 2, so a batch that keeps failing is retried twice and then discarded before the shard stalls longer
C: Configure an Amazon S3 bucket as the on-failure destination of the event source mapping, with a lifecycle rule that expires its objects after 90 days
D: Configure an Amazon SQS queue as the on-failure destination of the event source mapping, with the queue's message retention period set to its maximum
E: Set MaximumRecordAgeInSeconds on the event source mapping to 604,800, so Lambda discards a failing record once it is a week old instead of retrying it
F: Raise the stream's retention period to 2,160 hours, so records the function discarded can be read again from the stream at any point within 90 days
K: A,B,C
G: ## Why one bad record blocks a shard
Lambda processes one batch at a time per shard. With the defaults (`MaximumRetryAttempts = -1`, `MaximumRecordAgeInSeconds = -1`) a failing batch is retried **until the records expire** from the stream, so the shard makes no progress. Here that meant 24 hours, after which the record was silently dropped.
## The three knobs
- **Retry limit**: `MaximumRetryAttempts` (0 to 10,000) or `MaximumRecordAgeInSeconds` (60 to 604,800) decides when Lambda gives up. With a 60-second invocation, 1 attempt + 2 retries is about 3 minutes.
- **Partial batch response**: with `ReportBatchItemFailures` in `FunctionResponseTypes`, the function returns the sequence number of the first failed record. Lambda checkpoints just before it and retries only from there, so the records ahead of it are not processed again.
- **On-failure destination**: when Lambda discards records it sends an invocation record. **SQS and SNS** destinations get **metadata only** (shard ID, sequence number range); the data must then be re-read from the stream. An **S3** destination receives the **entire invocation record**, including the batch content.
## Working the retention constraint
Stream retention stays at 24 hours, and SQS keeps a message at most 14 days. Only S3 can keep the actual record content for 90 days.
W: A=ReportBatchItemFailures: Lambda checkpoints at the first failed sequence number, so the successful records before the bad one are not reloaded when the batch is retried.
B=MaximumRetryAttempts 2: three attempts of up to 60 seconds each end in about 3 minutes, inside the 5-minute stall budget, after which Lambda discards the batch and moves on.
C=S3 on-failure destination: for S3, Lambda writes the whole invocation record with the failed records, and a 90-day lifecycle expiration keeps exactly the required window.
X: D=SQS on-failure destination: SQS receives only metadata that points at sequence numbers in the stream. Those records expire after 24 hours, and SQS itself keeps messages for at most 14 days.
E=Maximum record age 604,800: a week-long age limit is longer than the 24-hour retention, so a bad record would again stall the shard until it expires, exactly the failure being fixed.
F=2,160-hour retention: this keeps every record (not only discarded ones) for 90 days at extra cost, which finance rejected, and nothing records which records were discarded.
T: For Kinesis consumers, bound retries, report partial batch failures, and use an S3 on-failure destination when you need the failed records' content, because SQS/SNS get metadata only.
V: AWS Lambda, Amazon Kinesis Data Streams, Amazon S3

@ DEA-C01 D1 T1.1 expert tradeoff
S: An AWS DMS task replicates an Aurora PostgreSQL database to Amazon S3 in Parquet format with ongoing CDC, using the default S3 endpoint settings. The busiest table produces about 2 MB of changes per minute, and Athena queries over its CDC folder are slow because DMS writes a new small file every minute. Analysts accept data that is up to 30 minutes old but no older, and they want the fewest, largest files that still meet that limit. The DBA notes that higher batch intervals keep more WAL in the replication slot, which is acceptable up to 30 minutes. Which endpoint setting change BEST meets these requirements?
A: Set CdcMaxBatchInterval to 1800 seconds and CdcMinFileSize to 128000 KB, so the busiest table writes one file of about 60 MB every 30 minutes
B: Set CdcMaxBatchInterval to 3600 seconds and CdcMinFileSize to 64000 KB, so the busiest table writes a file whenever about 64 MB of changes have built up
C: Keep CdcMaxBatchInterval at its default and set MaxFileSize to 131072 KB, so the busiest table's CDC files can grow to 128 MB before DMS starts a new file
D: Set CdcMaxBatchInterval to 1800 seconds and keep CdcMinFileSize at its default 32000 KB, so the busiest table writes a file once a 30-minute batch closes
K: A
G: ## When DMS writes a CDC file to S3
For an S3 target, DMS holds changes in memory and writes a file when **either** condition is met first:
- `CdcMaxBatchInterval`: maximum time in seconds (default **60**);
- `CdcMinFileSize`: minimum size in KB (default **32000 KB**, about 32 MB).
`MaxFileSize` is a different setting: the docs describe it as the maximum size of .csv files created during full load (default 1 GB). It never holds changes back, so it cannot delay CDC writes.
## Working the numbers at 2 MB per minute
- Defaults: 60 s is reached long before 32 MB, so one file of about 2 MB per minute.
- 1800 s and 128000 KB: 128 MB would take 64 minutes, so the 30-minute interval fires first: one file of about **60 MB** every 30 minutes.
- 3600 s and 64000 KB: 64 MB is reached after about **32 minutes**, which is older than the 30-minute limit.
- 1800 s and 32000 KB: 32 MB is reached after about **16 minutes**, so files of about 32 MB, twice as many as needed.
W: A=1800 s and 128000 KB: the size threshold is out of reach in 30 minutes, so the interval closes every file at the 30-minute limit, giving the largest files the freshness rule allows.
X: B=3600 s and 64000 KB: the 64 MB size trigger fires first, after about 32 minutes of changes, so the newest data in each file can be older than the analysts' 30-minute limit.
C=MaxFileSize 128 MB: this setting only caps file size (documented for full-load .csv files) and never delays a write. With the 60-second interval still in place, DMS keeps writing a 2 MB file every minute.
D=1800 s with the default 32000 KB: the default size trigger fires first, after about 16 minutes, so files are about 32 MB and twice as many as necessary; it meets freshness but not "fewest, largest".
T: DMS writes a CDC file when CdcMaxBatchInterval or CdcMinFileSize is reached, whichever comes first; size both against the change rate and the freshness limit.

@ DEA-C01 D1 T1.1 expert troubleshooting
S: An 8-shard provisioned Kinesis data stream receives a steady 0.75 MB per second per shard. Six consumers read every record: four Lambda functions owned by different teams, each with a standard event source mapping, and two KCL 1.x applications, and every consumer polls each shard with GetRecords about once per second. After the fourth Lambda function was added, all consumers show ReadProvisionedThroughputExceeded and rising iterator age. The stream must keep its current producers unchanged, the four teams must keep deploying their functions independently, and every consumer must still receive every record within seconds. Which change resolves the throttling?
A: Register each of the four Lambda functions as an enhanced fan-out consumer and point its event source mapping at the consumer ARN, leaving the two KCL applications on shared reads
B: Double the stream to 16 shards with UpdateShardCount, so each shard carries about half as much data and the six consumers share each shard's 2 MB per second read limit
C: Switch the stream to on-demand capacity mode, so Kinesis Data Streams adds shards on its own as the consumers' shared read traffic on each shard keeps growing
D: Merge the four Lambda functions into one dispatcher function behind a single standard event source mapping, which then calls the four teams' functions for each batch
K: A
G: ## Shared read limits per shard
Consumers that use standard iterators (shared throughput) all draw from the same per-shard budget:
- **2 MB per second** of reads per shard, shared by all of them;
- **5 GetRecords calls per second** per shard, shared by all of them.
An **enhanced fan-out** consumer instead gets its own dedicated **2 MB per second per shard**, pushed over HTTP/2 with `SubscribeToShard`, and does not count against the shared budget. A stream can register up to 20 such consumers (50 in On-demand Advantage mode).
## Working the numbers
- Today: 6 consumers x 0.75 MB/s = **4.5 MB/s** demanded per shard against 2 MB/s, and 6 calls/s against 5.
- 16 shards: 0.375 MB/s x 6 = **2.25 MB/s** per shard, still over 2 MB/s, and still 6 calls/s per shard.
- One dispatcher plus two KCL apps: 3 x 0.75 = **2.25 MB/s**, still over 2 MB/s.
- Four Lambda functions on enhanced fan-out: the shared budget carries only the two KCL apps, 2 x 0.75 = **1.5 MB/s** and 2 calls/s. Each enhanced consumer needs 0.75 of its dedicated 2 MB/s.
W: A=Enhanced fan-out for the Lambda functions: moving four consumers to dedicated 2 MB/s pipes leaves 1.5 MB/s and 2 calls/s on the shared budget, inside both per-shard limits.
X: B=16 shards: halving data per shard still leaves 2.25 MB/s of shared demand per shard, and every consumer still polls every shard, so 6 calls per second still exceed the 5-call limit.
C=On-demand mode: on-demand shards have the same shared per-shard read limits; adding shards cannot fix a fan-out problem where the number of consumers, not the write rate, exceeds the budget.
D=One dispatcher: three shared consumers still need 2.25 MB/s per shard, above the 2 MB/s limit, and the four teams lose independent deployment and error handling.
T: When many consumers share a stream, the per-shard 2 MB/s and 5 GetRecords/s budgets are split among them; move consumers to enhanced fan-out instead of adding shards.

@ DEA-C01 D1 T1.2 expert troubleshooting
S: An AWS Glue 4.0 job has job bookmarks enabled and a maximum concurrency of 1. Its script calls job.init() at the start and job.commit() at the end. It reads an append-only Aurora MySQL table through a JDBC catalog table whose primary key is a random UUID; the table also has an ingest_id BIGINT column that increases with every insert. It also reads JSON files from Amazon S3 with create_dynamic_frame.from_catalog, and that call has no transformation_ctx argument. Every run reloads all rows from both sources into the target, creating duplicates. Which TWO changes will make both sources incremental? (Select TWO)
A: Add jobBookmarkKeys set to ingest_id and jobBookmarkKeysSortOrder set to asc in the JDBC source's additional options, so the bookmark tracks that column
B: Pass a unique transformation_ctx value to the from_catalog call that reads the S3 JSON source, so the bookmark state for that source is stored
C: Call reset-job-bookmark before every scheduled run, so that each run starts from a clean bookmark state and records only the newest files and rows
D: Start each run with the job bookmark option set to Pause and job-bookmark-from set to the previous run ID, so that only input after that run is read
E: Add transformation_ctx to the S3 sink as well, so the bookmark also records which objects were written to the target and skips them on later runs
K: A,B
G: ## How Glue job bookmarks remember progress
Bookmark state is saved per job when `job.commit()` runs, and it is keyed by each operator's **transformation_ctx**. Two separate conditions must hold for every source you want to be incremental:
- **S3 sources**: the read call must pass a `transformation_ctx`. Without it, bookmarks are not enabled for that DynamicFrame, and every run reads every object.
- **JDBC sources**: Glue uses one or more **bookmark keys**. By default it uses the primary key, but only if it increases or decreases **sequentially, without gaps**. A random UUID does not, so the table is reread each time. You can name your own key with `jobBookmarkKeys` (and `jobBookmarkKeysSortOrder`); a user-defined key must be strictly monotonically increasing or decreasing.
## Checking the other common causes
- Maximum concurrency above 1 can confuse bookmarks; here it is already 1.
- A missing `job.commit()` makes every source reprocess; here it is present.
- Targets are never tracked by bookmarks, only sources.
W: A=jobBookmarkKeys ingest_id: an ever-increasing BIGINT is a valid bookmark key, so each run reads only rows with an ingest_id above the last committed value.
B=transformation_ctx on the S3 read: the context name is the key under which Glue stores the S3 source's state, so the next run filters out objects it has already processed.
X: C=Reset before every run: a reset clears all bookmark state, so each run deliberately reprocesses everything, which is the opposite of incremental loading.
D=Pause with job-bookmark-from: Pause reads a range but does not update the bookmark state, and it still cannot track the UUID-keyed table or the source with no transformation_ctx.
E=transformation_ctx on the sink: bookmarks track only sources; Glue does not record or skip target objects, so this changes nothing about what is read.
T: Glue bookmarks need a transformation_ctx on each source and, for JDBC, a gap-free increasing key; set jobBookmarkKeys when the primary key is not one.
V: AWS Glue, Amazon Aurora, Amazon S3

@ DEA-C01 D1 T1.2 expert troubleshooting
S: An Amazon Data Firehose stream delivers to Amazon S3 and invokes a Lambda function to enrich each record with product attributes. To reduce invocations, the team set the Lambda processor's BufferSizeInMBs to 3. The enrichment makes each batch the function returns about 2.5 times larger than the batch it receives. Since the change, almost every batch lands under the processing-failed prefix, the function's Errors metric rises, yet the function's own logs show each handler finishing in about 8 seconds with no exception. The code must not change, and records should reach S3 within 5 minutes. What should the data engineer do?
A: Set the Lambda processor's BufferSizeInMBs to 1, so each invocation receives about 1 MB of records and returns roughly 2.5 MB of enriched output to Firehose
B: Raise the Lambda function's memory to 3,008 MB and its timeout to 5 minutes, so every invocation has more room to build the enriched batch before it returns
C: Raise the S3 destination's buffering hint to 128 MB, so Firehose collects more enriched records per object before the delivery to the bucket is attempted
D: Raise the Lambda processor's number of retries from 3 to 5, so batches that fail once get more invocation attempts before Firehose marks them failed
K: A
G: ## How Firehose calls a transformation Lambda
When data transformation is on, Firehose buffers incoming records with its own **Lambda processing buffer** (`BufferSizeInMBs` 0.2 to 3 MB, default 1 MB; interval 0 to 900 seconds, default 60) and invokes the function **synchronously** with each batch.
Synchronous invocation has a **6 MB limit on both the request and the response**. If the function's response is larger, the invocation fails even though the handler code ran without error. Firehose retries (3 times by default) and then writes the records to the `processing-failed` prefix.
## Working the numbers
- 3 MB in x 2.5 = about **7.5 MB** out, over the 6 MB response limit.
- 1 MB in x 2.5 = about **2.5 MB** out, well within the limit.
The Lambda buffer is separate from the destination's S3 buffering hints, which decide object size in S3 after transformation.
W: A=BufferSizeInMBs 1: smaller input batches keep the enriched response near 2.5 MB, under the 6 MB synchronous response limit, with no code change and little extra latency.
X: B=More memory and timeout: the handler already finishes in 8 seconds; the failure is the response payload size, which memory and timeout do not change.
C=128 MB S3 buffer: the destination buffer only groups already-transformed records into objects; the oversized Lambda response fails before records ever reach it.
D=More retries: each retry sends the same 3 MB batch and gets the same 7.5 MB response, so it fails every time and only adds delay.
T: Firehose invokes the transform Lambda synchronously, so input buffer times expansion factor must stay under the 6 MB response limit; size BufferSizeInMBs accordingly.

@ DEA-C01 D1 T1.2 expert troubleshooting
S: A nightly AWS Glue job on 10 G.1X workers copies a 180-million-row orders table from Amazon RDS for MySQL to Amazon S3 as Parquet, using spark.read.jdbc with only a URL, table name and credentials. Job metrics show one active executor whose memory climbs to the limit, then logs report "Container killed by YARN for exceeding memory limits", and the run fails after four task attempts. The DBA allows at most 8 concurrent read queries against the instance. The copy must finish within one hour. Which change BEST fixes the job?
A: Read the table as a DynamicFrame from the Data Catalog with hashfield set to order_id and hashpartitions set to 8, so eight executors stream rows with a bounded fetch size
B: Increase the job to 40 G.1X workers while keeping spark.read.jdbc, so that Spark has four times as many executors and much more total memory for the read
C: Change the worker type to G.2X while keeping spark.read.jdbc, so the single executor that reads the table has twice the memory available for the result set
D: Read the table as a DynamicFrame from the Data Catalog with hashfield set to order_id and hashpartitions set to 32, so thirty-two executors stream the rows in parallel
K: A
G: ## Why a JDBC read runs on one executor
A plain `spark.read.jdbc` call with no partitioning options issues **one query**, so one task on one executor reads the whole table. The Spark JDBC fetch size defaults to 0, meaning the driver tries to fetch all rows at once and cache them, which ends in an executor OOM ("Container killed by YARN for exceeding memory limits").
## What Glue offers instead
- Glue **DynamicFrames** use a default fetch size of **1,000 rows**, so an executor streams rows instead of caching the table.
- **Parallel reads**: set `hashfield` (any column, ideally evenly distributed) or `hashexpression`, plus `hashpartitions` (default 7). Glue generates that many non-overlapping queries and runs them in parallel.
## Fitting the constraints
The DBA's limit is 8 concurrent queries, so `hashpartitions` must be 8 or fewer. More workers alone change nothing, because the work is still a single query.
W: A=DynamicFrame with hashpartitions 8: eight parallel queries spread the read across executors within the DBA's limit, and the 1,000-row fetch size removes the memory blow-up.
X: B=40 workers: the table is still read by one query in one task, so extra executors sit idle and the single reader still runs out of memory.
C=G.2X workers: doubling one executor's memory might delay the OOM, but a fetch size of 0 still makes one task cache all 180 million rows from a single query, so the root cause stays.
D=hashpartitions 32: the parallel read would work technically, but 32 concurrent queries break the DBA's limit of 8 on the source database.
T: For large JDBC sources in Glue, use DynamicFrames with hashfield/hashpartitions sized to what the source database can take, instead of a single unpartitioned spark.read.jdbc.

- 1 at a time: 12 x 25 = **300 minutes**.

G: ## Null behavior decides these rules
DQDL rules treat `NULL` differently, and the contract has both "may be null" and "never null" columns.
- `IsPrimaryKey` checks that the values are **unique and complete (non-null)**; listing several columns checks the combination.
- `IsUnique` checks uniqueness of one column only.
- `ColumnValues ... in [...]`: rows with `NULL` **fail** (except for `!=` and `not in`). To allow nulls, list `NULL` in the set, as the DQDL examples do.
- `DataFreshness "col" <= 24 hours`: compares each value with the current time, and rows with `NULL` **fail**. The documented compound rule `(DataFreshness ...) OR (ColumnValues "col" = NULL)` exists to **allow** nulls.
## Mapping the contract
- Composite key, non-null: `IsPrimaryKey "shipment_id" "line_no"`.
- Allowed carriers or null: include `NULL` in the in-list.
- Recent and never null: plain `DataFreshness`, which already fails null rows.
W: A=IsPrimaryKey on both columns: it checks that the shipment_id and line_no pair is unique and that neither value is null, matching the composite key.
C=In-list including NULL: listing NULL lets unassigned carriers pass while any other code fails.
E=DataFreshness 24 hours: rows older than 24 hours fail, and so do rows with a null event_ts, which the contract forbids.
X: B=IsUnique on shipment_id: a shipment has many lines, so valid data repeats shipment_id and this rule would fail every day.
D=In-list without NULL: null rows fail ColumnValues rules, so every shipment without an assigned carrier would break valid data.
F=Freshness OR null: the OR branch lets null event_ts values pass, which the contract says must fail.
T: Know each DQDL rule's null behavior: ColumnValues and DataFreshness fail nulls unless you allow them, and IsPrimaryKey checks uniqueness plus completeness, also across several columns.

S: An AWS Glue 4.0 ETL job evaluates order data with Glue Data Quality. Store orders are about 40 percent of rows and usually have a NULL email, because cashiers rarely ask for one; a missing web email is also NULL. For web orders, the contract allows at most 2 percent of rows with a missing or malformed email, and the job must not fail because store orders lack emails. A missing web email must count against the 2 percent, not be skipped, and the check must be a single DQDL rule in the job's ruleset. Which rule meets the contract?
A: ColumnValues "email" matches "[^@]+@[^@]+" where "channel = 'web'" with threshold >= 0.98
B: ColumnValues "email" matches "[^@]+@[^@]+" where "channel in ('web', 'store')" with threshold >= 0.98
C: ColumnValues "email" matches "[^@]+@[^@]+" where "channel = 'web' and email is not null" with threshold >= 0.98
D: ColumnValues "email" matches "[^@]+@[^@]+" where "channel = 'web'"
K: A
G: ## Three DQDL building blocks
- **where clause** (AWS Glue 4.0): `<rule> where "<SparkSQL condition>"` evaluates the rule only on rows that match the condition. With a threshold, the where clause comes **before** `with threshold`.
- **with threshold**: for `ColumnValues` with `matches` or `in`, it sets the share of rows that must pass. Without it, **every** row must pass.
- **Null behavior**: `ColumnValues` rules (other than `!=` and `not in`) fail rows with `NULL`, so a missing email counts as a failing row, as the contract wants, unless the where clause filters those rows out first.
## Working the numbers
- Counting store orders too: about 40 percent of rows have no valid email, so at most about 60 percent can pass, and a 98 percent threshold always fails.
- Filtering to web rows with a 98 percent threshold: only web rows are counted, and up to 2 percent of them may be missing or malformed.
- Adding `email is not null` to the filter removes missing emails from the count, so a web feed where 30 percent of emails are missing could still pass.
W: A=Web rows with a 0.98 threshold: it counts only web orders, treats missing and malformed emails as failures, and passes while at least 98 percent are valid.
X: B=Web and store rows: store orders are counted too, so roughly 40 percent of rows fail and the 98 percent threshold can never be met.
C=Filter out null emails: missing emails never reach the rule, so they no longer count against the 2 percent, although the contract says they must.
D=No threshold: every web row must match, so a single malformed email fails the rule, though the contract allows up to 2 percent.
T: Combine a where clause (which rows count) with "with threshold" (what share must pass); without a threshold, ColumnValues requires every row to pass, and filtering nulls out hides them.
