@ DEA-C01 D2 T2.1 expert troubleshooting
S: A retailer runs an Amazon Redshift ra3.4xlarge cluster on reserved nodes, and finance forbids adding nodes or resizing. Every Monday from 09:00, about 300 analysts open dashboards that run plain SELECT statements, with no UDFs or temporary tables, against the web_sessions table, and those queries wait in the queue for up to 6 minutes. The cluster uses automatic WLM, the dashboard queue has concurrency scaling mode set to auto, and max_concurrency_scaling_clusters is 3. STL_QUERY shows concurrency_scaling_status = 1 for many finance queries in the same queue, but never for a dashboard query. web_sessions was created three years ago with INTERLEAVED SORTKEY(session_date, region, device), and the dashboards filter on session_date and region. Which change removes the Monday queueing?
A: Run ALTER TABLE web_sessions ALTER COMPOUND SORTKEY (session_date, region) so that dashboard queries can use the scaling clusters
B: Raise max_concurrency_scaling_clusters from 3 to 10 so that more transient clusters are available to absorb the Monday morning dashboard burst
C: Switch to manual WLM and give the dashboard queue 50 query slots so that all Monday dashboard queries start at once on the main cluster
D: Add a query monitoring rule that hops dashboard queries into a second queue that also has concurrency scaling mode set to auto
K: A
G: ## How concurrency scaling decides what to send
With concurrency scaling turned on for a WLM queue, Amazon Redshift adds transient clusters when more queries arrive than the queue can run. Only **eligible** queries are routed there; the rest keep waiting on the main cluster. The `concurrency_scaling_status` column of `STL_QUERY` shows where each query ran (`1` = a concurrency-scaling cluster).
## Documented limitations
Concurrency scaling does not support queries that:
- read tables that use **interleaved sort keys**,
- read temporary tables,
- contain Python or Lambda UDFs,
- read system tables, catalog tables or no-backup tables.
## Reading the evidence
Scaling works for finance queries in the same queue, so the queue setting, the Region, the node type and `max_concurrency_scaling_clusters` are all fine. What is unique to the dashboards is the table they read. `web_sessions` has an interleaved sort key, so none of its queries can ever be routed to a scaling cluster.
`ALTER TABLE ... ALTER COMPOUND SORTKEY` can change an interleaved sort key to a compound one (the reverse is not allowed). With `session_date` leading, the dashboards' date filter still skips blocks through min/max metadata.
W: Compound sort key: removing the interleaved sort key removes the one limitation that blocks these queries; afterwards the existing auto setting and the 3 scaling clusters absorb the burst without new nodes.
X: B=More scaling clusters: the limit is not being reached by the dashboards at all; ineligible queries never go to any scaling cluster, whether the limit is 3 or 10.
C=50 manual slots: slots only split the same main-cluster memory and CPU into smaller pieces; no capacity is added, so queries start sooner but run slower, and nothing changes the ineligibility.
D=Hop to another queue: the second queue applies the same eligibility rules, so the dashboard queries still cannot leave the main cluster.
T: Concurrency scaling silently skips queries on interleaved-sort-key tables, temporary tables or UDFs; check eligibility before adding scaling clusters.
V: Amazon Redshift

@ DEA-C01 D2 T2.1 expert use-case
S: A voting app stores one Amazon DynamoDB item per live contest, and every vote calls UpdateItem with ADD on a votes attribute. The item also holds a list of recent voter regions, so it is about 1.6 KB. During a TV final, one contest receives a steady 3,500 votes per second. The table uses on-demand mode, and updates to that item are throttled although the table is far below its table-level throughput limits. The scoreboard reads the total once per second and may be up to one second stale. The team wants the smallest change that removes the throttling and leaves some headroom. Which design meets the requirement?
A: Split the counter into 10 items keyed contest#0 to contest#9, add each vote to a random shard, and sum all 10 items with one BatchGetItem call per second
B: Split the counter into 5 items keyed contest#0 to contest#4, add each vote to a random shard, and sum all 5 items with one BatchGetItem call per second
C: Move the voter-region list into a separate item so that the counter item stays below 1 KB, and keep sending all votes to the single contest item
D: Switch the table from on-demand to provisioned mode with 8,000 write capacity units so that the contest item gets 7,000 WCUs reserved for it
K: A
G: ## The per-partition ceiling
Every DynamoDB partition delivers at most **1,000 write units** and **3,000 read units** per second, in on-demand and provisioned mode alike. One item always lives in one partition, so a single hot item can never exceed 1,000 WCUs, whatever the table's capacity.
## Working the numbers
- One write unit covers an item up to 1 KB. `UpdateItem` is charged on the larger of the item's before and after size, rounded up to the next 1 KB, even if only one attribute changes. A 1.6 KB item costs **2 WCUs** per vote.
- Demand: 3,500 votes/s x 2 WCUs = **7,000 WCUs/s** on one item.
- Shards needed: 7,000 / 1,000 = 7 at the absolute minimum.
- 10 shards: 700 WCUs each, 30% below the ceiling. 5 shards: 1,400 WCUs each, still over it.
## Write sharding
Adding a suffix (`contest#0` ... `contest#9`) spreads one logical key over several partition key values. Writes pick a random suffix; the reader fetches every shard (one `BatchGetItem` for 10 keys) and adds them up, which fits the one-second staleness allowance.
W: Ten shards: 7,000 WCUs spread over 10 keys is 700 per key, below the 1,000-unit partition limit with headroom, and one BatchGetItem per second rebuilds the total.
X: B=Five shards: 7,000 / 5 = 1,400 WCUs per shard, so every shard is still throttled at the 1,000-unit partition limit.
C=Shrink below 1 KB: each vote then costs 1 WCU, but 3,500 WCUs on one item is still 3.5 times the partition limit.
D=Provisioned 8,000 WCUs: table capacity is shared across partitions; it cannot lift the 1,000 WCU ceiling of the single partition that holds the item.
T: A single item is capped at 1,000 WCUs per second; size the number of write shards from (writes/s x WCUs per write) / 1,000 plus headroom.
V: Amazon DynamoDB

@ DEA-C01 D2 T2.1 expert use-case
S: A producer AWS account runs an encrypted Amazon Redshift RA3 cluster with sales tables. A partner team in another account of the same company wants live, read-only access through a datashare, without copying data, from its own RA3 cluster in the same Region. That consumer cluster was created years ago with encryption turned off, and it has cross-Region snapshot copy to a disaster recovery Region enabled, which must keep working afterwards. The security team will not share the producer's KMS key with any other account. Which sequence lets the consumer cluster query the datashare?
A: Disable cross-Region snapshot copy, modify the consumer cluster to KMS encryption with a key in its own account, re-enable snapshot copy with a snapshot copy grant, then associate the datashare
B: Add the consumer account to the producer key's policy, modify the consumer cluster to KMS encryption with that producer key, then associate the datashare and keep snapshot copy running
C: Keep the consumer cluster unencrypted and associate the datashare, because shared data travels under the producer's encryption schema and is never stored on the consumer
D: Modify the consumer cluster to KMS encryption with a key in its own account while cross-Region snapshot copy stays enabled, then associate the datashare once it is available
K: A
G: ## Encryption rules for data sharing
- Within one account, producer and consumer must have the **same encryption type** (both encrypted or both unencrypted).
- **Across accounts** (and for Lake Formation managed datashares), **both must be encrypted**. They do **not** need the same key.
Data in transit between them is encrypted with the producer's encryption schema, and the consumer adopts it, but that does not waive the at-rest rule.
## Encrypting an existing cluster
You can modify an unencrypted cluster to use AWS KMS encryption (AWS owned key or a customer managed key). Redshift migrates the data to a new encrypted cluster; during the migration the cluster is read-only and shows the status `resizing`.
One prerequisite is easy to miss: **if cross-Region snapshot copy is enabled, you must disable it before changing encryption**. For a KMS-encrypted cluster, copying snapshots to another Region then needs a **snapshot copy grant** in the destination Region, so re-enabling copy afterwards includes creating that grant.
W: Disable copy, encrypt, re-enable with a grant: this is the only order that both satisfies the cross-account encryption rule and keeps the disaster recovery snapshots working, using a key the consumer owns.
X: B=Producer's key: the rule needs both clusters encrypted, not the same key, so sharing the key is unnecessary and violates the security team's condition.
C=Stay unencrypted: cross-account data sharing requires an encrypted consumer; the in-transit encryption of shared data does not replace that requirement.
D=Encrypt with copy enabled: Redshift requires cross-Region snapshot copy to be disabled before cluster encryption can be changed, so this step order fails.
T: Cross-account datashares need both clusters encrypted (any keys); disable cross-Region snapshot copy before encrypting a cluster and re-enable it with a snapshot copy grant.
V: Amazon Redshift, AWS KMS

@ DEA-C01 D2 T2.2 expert troubleshooting
S: An AWS Glue Data Catalog table over s3://pos/sales/ is partitioned by dt (string, yyyy-MM-dd) and store_id (string) and has about 2.1 million partitions. A BI tool generates Athena queries such as WHERE store_id = 'S0412' AND dt LIKE '2026-%', and the team cannot change the generated SQL. Query planning takes over a minute. An engineer created a partition index on (dt, store_id); GetPartitionIndexes reports it ACTIVE, but planning time did not change. Partition projection is ruled out because store IDs are created irregularly. Which TWO actions let these queries benefit from a partition index? (Select TWO)
A: Set the table property partition_filtering.enabled to true so that Athena passes the partition predicates to the Data Catalog for index-based filtering
B: Create a second partition index on (store_id, dt) so that the first indexed key appears in every generated query with an equality predicate
C: Have the BI tool send dt BETWEEN '2026-01-01' AND '2026-12-31' instead of LIKE so that the existing (dt, store_id) index can filter partitions
D: Alter the table to reorder its partition keys as (store_id, dt) so that the existing partition index starts with the store key as well
E: Rewrite the store filter as store_id IN ('S0412') so that the Data Catalog evaluates it as an indexed set-membership lookup on the first key
K: A,B
G: ## What a partition index does
Without an index, `GetPartitions` loads every partition of the table and filters them afterwards, which is slow with millions of partitions. A partition index (up to 3 per table) lets the Data Catalog fetch only matching partitions.
## Rules that decide whether the index is used
- **The first key of the index must appear in the expression.** An index on `(dt, store_id)` is ignored when no usable `dt` predicate is present.
- Supported operators are `=`, `>`, `>=`, `<`, `<=` and `between`, joined with `AND`. Sub-expressions with `LIKE`, `IN`, `OR` or `NOT` are **ignored** for index filtering and applied afterwards.
- After an index exists, you cannot change the names, types or order of the partition keys registered with it.
- Redshift Spectrum, EMR and Glue Spark DataFrames use indexes automatically; **Athena** needs the table property `partition_filtering.enabled` = `true`.
## Applying them here
The generated filter is `store_id = 'S0412' AND dt LIKE '2026-%'`. The `LIKE` part is ignored, so the index `(dt, store_id)` sees no first key and falls back to loading everything. An index that starts with `store_id` gets an equality on its first key, and Athena must have partition filtering turned on to use any index.
W: A=partition_filtering.enabled: without this table property Athena does not use Data Catalog partition indexes at all.
B=Index on (store_id, dt): every generated query carries store_id = '...', so the first key is always present with a supported operator; the dt LIKE part is then filtered on the much smaller result.
X: C=BETWEEN instead of LIKE: it would make the existing index usable, but the stem says the BI tool's generated SQL cannot be changed.
D=Reorder partition keys: once a partition index exists, the order of keys registered with it cannot be changed, and the index order is fixed at creation anyway.
E=IN instead of equality: IN sub-expressions are ignored by index filtering, so this makes the store filter useless to the index.
T: Athena uses a Glue partition index only with partition_filtering.enabled, and only when the index's first key appears with =, <, >, <=, >= or between (not LIKE, IN, OR, NOT).
V: AWS Glue Data Catalog, Amazon Athena

@ DEA-C01 D2 T2.2 expert troubleshooting
S: To cut a nightly AWS Glue crawler from 3 hours to 10 minutes, a team set it to crawl new sub-folders only on s3://lake/orders/, where each day adds one dt=YYYY-MM-DD folder of Parquet files. Two weeks ago the producer, in a one-time change, added a discount_code column and changed quantity from int to bigint. Since then Athena shows no partitions newer than the change, and the crawler's CloudWatch log lists the new folders as schema-incompatible objects that were not added. Analysts need the new partitions and column queryable, and nightly runs must stay short afterwards. What should the team do?
A: Run one crawl of all folders with a schema change policy that updates the table, then switch the crawler back to new sub-folders only
B: Keep crawling new sub-folders only, but set the schema change policy UpdateBehavior to UPDATE_IN_DATABASE so the next incremental run updates the table schema
C: Keep the crawler as it is and run MSCK REPAIR TABLE in Athena after every crawl so that the skipped dt folders are added as partitions of the existing table
D: Keep the crawler as it is and have a nightly AWS Lambda function run ALTER TABLE ADD PARTITION for each new dt folder that the crawler skipped
K: A
G: ## Incremental crawls
With the recrawl policy `CRAWL_NEW_FOLDERS_ONLY` ("Crawl new sub-folders only"), the first run is a full crawl and every later run adds only folders that are new since the previous run. That is fast, but it has fixed side effects:
- The crawler's update and delete behaviors are **forced to `LOG`**. Objects whose schema is not compatible with the table are **not added**; the crawler only writes a CloudWatch Logs entry.
- It does not detect changes to existing partitions.
AWS's guidance: incremental crawling suits stable schemas; after a **one-time major schema change**, temporarily switch to a full crawl to capture the new schema, then switch back to incremental mode.
## Why adding partitions by hand is not enough
Partitions added with `MSCK REPAIR TABLE` or `ALTER TABLE ADD PARTITION` get the table's current schema. The table still has no `discount_code` column and still types `quantity` as `int`, so the new column stays invisible to queries.
W: One full crawl, then back to incremental: the full crawl may update the table schema (new column, wider type) and add the skipped partitions; switching back keeps later nightly runs short.
X: B=UPDATE_IN_DATABASE with incremental: while crawl-new-folders-only is on, the update and delete behaviors are forced to LOG, so this setting cannot take effect.
C=MSCK REPAIR TABLE: it registers the folders as partitions, but with the old table schema, so discount_code still cannot be queried.
D=ALTER TABLE ADD PARTITION: same gap as the repair command, plus custom code to run; the table definition never learns about the new column.
T: Incremental (new-folders-only) crawls force LOG behavior and skip schema-incompatible data; run one full crawl after a one-time schema change, then return to incremental.

@ DEA-C01 D2 T2.3 expert tradeoff
S: A company writes about 30 TB per month of Parquet log files, 200-500 MB each, to an unversioned S3 Standard bucket. Dashboards query every file daily for its first 20 days. Between day 30 and day 45 an incident team reads about 20 percent of the files once each and needs millisecond access, and policy requires deleting every file at day 45. Use these prices: Standard $0.023 per GB-month; Standard-IA $0.0125 per GB-month plus $0.01 per GB retrieved; Glacier Instant Retrieval $0.004 per GB-month plus $0.03 per GB retrieved; Intelligent-Tiering Frequent Access priced as Standard plus a per-object monitoring fee. Ignore request charges. Which lifecycle configuration is MOST cost-effective?
A: Keep the files in S3 Standard and add a lifecycle rule that only expires objects 45 days after creation, without any storage-class transition
B: Add a lifecycle rule that transitions the files to S3 Standard-IA 30 days after creation and expires them 45 days after creation
C: Add a lifecycle rule that transitions the files to S3 Glacier Instant Retrieval 30 days after creation and expires them 45 days after creation
D: Write the files directly to S3 Intelligent-Tiering and add a lifecycle rule that expires the objects 45 days after creation
K: A
G: ## Minimum storage durations
Cheaper classes bill a minimum duration. Deleting earlier adds a pro-rated charge for the rest of the minimum:
- Standard-IA and One Zone-IA: **30 days** (and 128 KB minimum billable size).
- Glacier Instant Retrieval and Glacier Flexible Retrieval: **90 days**. Glacier Deep Archive: **180 days**.
- Standard and Intelligent-Tiering: no minimum.
Intelligent-Tiering moves an object to its Infrequent Access tier only after **30 consecutive days without access**.
## Working days 30-45 per GB (all options cost the same before day 30)
- **Standard**: 15 days = 0.5 month x $0.023 = **$0.0115**.
- **Standard-IA**: 15 days stored but 30 billed = 1 x $0.0125 = $0.0125, plus 20% x $0.01 retrieval = **$0.0145**.
- **Glacier IR**: 90 days billed = 3 x $0.004 = $0.012, plus 20% x $0.03 = **$0.018**.
- **Intelligent-Tiering**: last daily read is on day 20, so the 30-day clock would end on day 50, after deletion. Every byte stays in Frequent Access at the Standard price, plus the monitoring fee: slightly **more than Standard**.
For 30 TB (30,720 GB) a month: Standard about $353, Standard-IA about $445, Glacier IR about $553.
W: Standard with expiration only: with just 15 days left before deletion, no colder class can recover its minimum-duration charge and retrieval fees, so the plain expiration rule is cheapest.
X: B=Standard-IA at day 30: the 30-day minimum bills twice the 15 days actually stored, which already costs more than Standard before the retrieval fee.
C=Glacier Instant Retrieval at day 30: the 90-day minimum bills six times the stored period, and its $0.03 per GB retrieval fee is the highest of the options.
D=Intelligent-Tiering: objects last read on day 20 would only tier down on day 50, so they never leave the Standard-priced tier, and the monitoring fee comes on top.
T: Before transitioning, compare the days left until deletion with the class's minimum duration; short remaining lives are cheapest left in Standard.

@ DEA-C01 D2 T2.3 expert use-case
S: A booking service keeps reservations in an Amazon DynamoDB table with TTL on an expires_at attribute stored in epoch seconds, set 90 days after checkout. Every expired reservation must be archived to S3 in full for 7 years. When a guest invokes the right to erasure, the app deletes the reservation with DeleteItem, and those items must never reach the archive. The mobile app must not show reservations whose expires_at time has already passed. An AWS Lambda function will write the archive files. Which TWO actions meet these requirements? (Select TWO)
A: Enable DynamoDB Streams with the OLD_IMAGE view type and add an event filter on the Lambda event source mapping that matches userIdentity type Service and principalId dynamodb.amazonaws.com
B: Enable DynamoDB Streams with the NEW_IMAGE view type and add an event filter on the Lambda event source mapping that matches userIdentity type Service and principalId dynamodb.amazonaws.com
C: Enable DynamoDB Streams with the OLD_IMAGE view type and add an event filter on the Lambda event source mapping that matches every stream record whose eventName is REMOVE
D: Add a filter expression to the app's Query and Scan calls that keeps only items whose expires_at value is greater than the current time in epoch seconds
E: Store expires_at as an ISO 8601 date-time string instead of a number so that TTL deletes each item at the exact second that its reservation expires
K: A,D
G: ## How TTL deletes appear
TTL deletes expired items **typically within a few days** of the expiry time, without consuming write throughput. Until then the item is still returned by reads, so AWS recommends filter expressions to hide expired items. The TTL attribute must be a **Number** in epoch seconds; any other type is ignored.
A TTL delete is written to DynamoDB Streams as a **service delete**: the record carries `userIdentity.type = "Service"` and `userIdentity.principalId = "dynamodb.amazonaws.com"`. A user's `DeleteItem` produces a `REMOVE` record without that identity.
## What the stream record contains
The view type decides the payload: `KEYS_ONLY`, `NEW_IMAGE` (item after the change), `OLD_IMAGE` (item before) or `NEW_AND_OLD_IMAGES`. A delete has no "after" image, so archiving the full item needs `OLD_IMAGE` or `NEW_AND_OLD_IMAGES`.
## Event filtering
A filter on the Lambda event source mapping such as `{"userIdentity": {"type": ["Service"], "principalId": ["dynamodb.amazonaws.com"]}}` invokes the function only for TTL deletes, so erasure deletes never reach it, and you are not billed for the filtered-out invocations.
W: A=OLD_IMAGE plus service-identity filter: the record holds the whole deleted item, and the filter passes only TTL deletes, keeping erasure requests out of the archive.
D=Filter expression on expires_at: expired items can linger for days before TTL removes them, so the app must filter them out itself.
X: B=NEW_IMAGE: a deleted item has no new image, so the function would receive no item data to archive.
C=eventName REMOVE: this matches the guests' DeleteItem calls as well, archiving exactly the data the erasure requirement forbids keeping.
E=ISO 8601 string: TTL only works on a Number attribute in epoch seconds; a string is ignored and nothing would ever expire, and TTL never deletes at the exact second anyway.
T: Archive TTL deletes with an OLD_IMAGE stream filtered on userIdentity (Service, dynamodb.amazonaws.com), and filter expired items in reads because TTL can lag by days.

@ DEA-C01 D2 T2.4 expert comparison
S: Analysts query two Athena tables holding the same kind of order data: orders_hive, a Hive-style Parquet table partitioned by dt with default SerDe settings, and orders_ice, an Apache Iceberg table. A data product owner asks for four changes: rename cust_ref to customer_ref, widen quantity from int to bigint, raise amount from decimal(10,2) to decimal(12,2), and change unit_price from double to decimal(12,4). Neither the roughly 40 TB of existing data files nor the 9,000 existing partition definitions of orders_hive may be modified, and old files must keep returning their current values under the new names and types. Which THREE changes can be made under these constraints? (Select THREE)
A: On orders_ice, rename cust_ref to customer_ref with ALTER TABLE CHANGE COLUMN, because Iceberg tracks every column by an ID rather than by its name
B: On orders_ice, widen quantity from int to bigint with ALTER TABLE CHANGE COLUMN as a metadata-only type promotion of the column
C: On orders_ice, change amount from decimal(10,2) to decimal(12,2) with ALTER TABLE CHANGE COLUMN, because raising decimal precision is supported
D: On orders_ice, change unit_price from double to decimal(12,4) with ALTER TABLE CHANGE COLUMN, because a decimal can store every double value
E: On orders_hive, rename cust_ref to customer_ref in the table definition, because Parquet files are matched to table columns by their column names
F: On orders_hive, set parquet.column.index.access to true in the table's SerDe properties and then rename the column, so that old files are matched by position
K: A,B,C
G: ## Iceberg schema evolution
Iceberg schema updates are **metadata-only**: no data file is rewritten. Supported changes are add, drop, rename and reorder columns, and **type promotion** limited to:
- `int` to `bigint`,
- `float` to `double`,
- increasing the precision of a `decimal`.
Rename is safe because Iceberg identifies each column by an internal ID, so old files still map to the renamed column. `double` to `decimal` is not a supported promotion.
## Hive-style Parquet tables in Athena
Athena reads Parquet **by name** by default. Renaming a column in the table definition therefore makes old files, which still carry the old name, return `NULL` for it. Reading by index (`parquet.column.index.access` = `true`) allows renames, but the SerDe property is set at table creation and is **not propagated to existing partitions**: each partition needs it set again (for example with `ALTER TABLE ADD PARTITION`), and reading by index then blocks adding columns in the middle or dropping them.

D=Default encryption change: default encryption applies only to new uploads that specify no encryption, and the partner's requests name SSE-C, so neither existing nor future partner objects change.
E=SSE-C keys in Secrets Manager: Macie has no way to use a customer-provided key; SSE-C objects remain metadata-only no matter which secrets it can read.
T: Macie analyzes SSE-KMS objects under a customer managed key only when the key policy allows its service-linked role kms:Decrypt, and never analyzes SSE-C or client-side encrypted objects.

@ DEA-C01 D4 T4.4 expert troubleshooting
S: Auditors require the SQL text of every query run on an Amazon Redshift provisioned cluster to be kept as log files in Amazon S3. An engineer turned on audit logging to an existing bucket, evidence-vault, which has default SSE-KMS encryption with a customer managed key and S3 Object Lock enabled. No log files ever arrive. A test against a new bucket with default settings and the documented bucket policy then delivered connection logs and user logs, but no user activity log. The company does not want to route these logs through CloudWatch Logs. Which combination of changes meets the requirement?
A: Deliver to a bucket with Object Lock turned off and SSE-S3 default encryption whose policy allows redshift.amazonaws.com, and set enable_user_activity_logging to true
B: Allow redshift.amazonaws.com to use the customer managed key in its key policy so evidence-vault accepts the files, and set enable_user_activity_logging to true
C: Switch evidence-vault's default Object Lock retention from compliance mode to governance mode so Redshift can write, and set enable_user_activity_logging to true
D: Deliver to a bucket with Object Lock turned off and SSE-S3 default encryption whose policy allows redshift.amazonaws.com, and leave the parameter group unchanged
K: A
G: ## Three audit logs
Redshift audit logging produces a **connection log** (authentication, connects, disconnects), a **user log** (changes to database users) and a **user activity log** (each query before it runs). The SQL text auditors want is in the user activity log.
## The extra switch for query text
Turning on audit logging enables the three logs together, but the user activity log is only written when the database parameter **`enable_user_activity_logging`** is `true` in the cluster's parameter group (default `false`). Without it you get exactly what the test showed: connection and user logs only.
## Bucket constraints for S3 delivery
- Only **SSE-S3** (AES-256) encryption is supported.
- The bucket must have **S3 Object Lock turned off**.
- A bucket policy must allow the Redshift service principal (`redshift.amazonaws.com` in most Regions) `s3:PutObject` and `s3:GetBucketAcl`.
`evidence-vault` breaks two of these rules, so nothing is ever delivered there.
W: Compliant bucket plus the parameter: SSE-S3 and no Object Lock let delivery work, and enable_user_activity_logging adds the query text log.
X: B=KMS key policy: audit log delivery to S3 supports only SSE-S3, and Object Lock would still block the bucket even with key access.
C=Governance mode: the requirement is that Object Lock be turned off on the bucket, not a different retention mode; KMS encryption would also remain unsupported.
D=Parameter unchanged: logs would now arrive, but only connection and user logs; the user activity log stays off while enable_user_activity_logging is false.
T: Redshift S3 audit logs need an SSE-S3 bucket without Object Lock, and query text needs enable_user_activity_logging = true.

@ DEA-C01 D4 T4.5 expert troubleshooting
S: In AWS Lake Formation, the database crm carries the LF-tags domain=crm and sensitivity=public, and its table customers inherits both. The columns email and ssn override the inherited value with sensitivity=restricted. Three grants exist: analyst_role has SELECT on tables matching domain=crm AND sensitivity=public; loader_role has SELECT and INSERT on tables matching the same expression; steward_role has SELECT on tables matching domain=crm AND sensitivity=restricted. The nightly job that runs as loader_role must append full rows to customers. No other grants or data filters exist on the table. What is the resulting access?
A: analyst_role reads every column except email and ssn; loader_role cannot insert, because INSERT needs a match on all columns; steward_role reads only email and ssn
B: analyst_role reads every column except email and ssn; loader_role inserts full rows, because INSERT is checked at table level; steward_role reads only email and ssn
C: analyst_role reads every column, because the table-level tags match its grant; loader_role cannot insert; steward_role reads only the email and ssn columns
D: analyst_role reads every column except email and ssn; loader_role cannot insert; steward_role reads every column, because restricted ranks above public
K: A
G: ## LF-tag inheritance and overrides
Tables inherit LF-tags from their database, and columns inherit from their table. An inherited value can be **overridden** on a lower level; a resource can hold only one value per key. Here every column of `customers` has `domain=crm`, and all columns have `sensitivity=public` except `email` and `ssn`, which have `sensitivity=restricted`.
## How a tag expression is evaluated
A grant with several tags (`domain=crm AND sensitivity=public`) matches only resources that carry **all** of them. Evaluated per column:
- `analyst_role`: every column except `email` and `ssn` matches, so SELECT covers those columns only.
- `steward_role`: only `email` and `ssn` match.
There is no ranking between tag values; `restricted` is just another value.
## Permissions that need every column
If an expression matches only a **subset** of a table's columns and the granted permission needs full column access (`ALTER`, `DROP`, `INSERT`, `DELETE`), that permission is not granted; only `DESCRIBE` is. So `loader_role` keeps SELECT on the public columns but gets **no INSERT** on `customers`, and the nightly append fails until the grant also covers the restricted columns.
W: Column-level evaluation: analysts and stewards get complementary column sets, and the loader's INSERT is dropped because its expression does not match every column.
X: B=INSERT at table level: Lake Formation withholds INSERT when the tag expression matches only part of the columns, so the full-row append is denied.
C=Analysts read everything: the column-level override takes email and ssn out of the analysts' match even though the table itself carries sensitivity=public.
D=Restricted ranks above public: tag values have no hierarchy; the steward's AND expression matches only the columns tagged restricted.
T: LF-tag grants are evaluated per column after inheritance and overrides; INSERT, DELETE, ALTER and DROP are withheld when the expression matches only some columns.
V: AWS Lake Formation, AWS Glue Data Catalog

@ DEA-C01 D4 T4.5 expert troubleshooting
S: A brokerage keeps trade records in a versioned S3 bucket with an S3 Object Lock default retention of 7 years in compliance mode and a lifecycle rule that moves objects to S3 Glacier Deep Archive after 180 days. A faulty cleanup script sent 2,000 DeleteObject requests without version IDs; each returned 200 OK, and the records vanished from listings and from Athena results. Separately, legal counsel says 300 of the records must stay immutable past their 7 years until a lawsuit ends, on a date nobody knows yet. Which TWO statements are correct? (Select TWO)
A: The protected versions still exist; each request only added a delete marker, and deleting those delete markers by version ID makes the records current again
B: A legal hold on each of the 300 object versions, set with s3:PutObjectLegalHold, keeps them immutable after retention ends until the hold is removed
C: The 200 OK responses prove the retention was never applied, so the objects were permanently removed and must be restored from a replicated copy
D: The objects that had moved to S3 Glacier Deep Archive lost their Object Lock protection during the transition, so those records cannot be recovered
E: Switching the 300 object versions from compliance mode to governance mode with a longer date, using s3:BypassGovernanceRetention, extends their protection
K: A,B
G: ## What Object Lock protects
Object Lock protects **object versions** in a versioned bucket. In **compliance mode** no user, not even the root user, can overwrite or delete a locked version or shorten its retention, and the mode cannot be changed.
## Deletes against a locked bucket
- A **permanent delete** (with a version ID) of a protected version returns `403 Access Denied`.
- A **simple delete** (no version ID) returns `200 OK` and only adds a **delete marker** as the new current version. The object looks deleted to listings and queries, but the locked version is untouched.
- Delete markers are **not** WORM-protected, so removing them (a delete that names the marker's version ID) makes the previous version current again.
## Lifecycle and storage classes
Lifecycle rules keep working on locked objects, including transitions and placing delete markers, but cannot delete a locked version. The lock stays in force in every storage class, including Glacier Deep Archive.
## Retention without a known end date
A **legal hold** has no expiry: it protects the version until someone with `s3:PutObjectLegalHold` removes it, independent of the retention period. That fits a lawsuit whose end date is unknown.
W: A=Delete markers: simple deletes on a locked bucket only hide the versions; deleting the markers restores them.
B=Legal hold: it keeps the 300 versions immutable beyond the 7-year retention until it is explicitly removed, which suits an unknown end date.
X: C=Permanently removed: a 200 OK for a delete without a version ID is the normal delete-marker response; the locked versions were never removed.
D=Lost in Deep Archive: Object Lock is maintained through lifecycle transitions and in every storage class.
E=Switch to governance mode: a compliance-mode lock cannot have its mode changed, and BypassGovernanceRetention applies only to governance-mode locks.
T: On an Object Lock bucket, a simple delete only adds a removable delete marker; use legal holds to extend immutability without a known end date.
V: Amazon S3
