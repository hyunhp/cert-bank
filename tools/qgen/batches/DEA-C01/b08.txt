@ DEA-C01 D1 T1.1 advanced troubleshooting
S: A logistics company streams GPS events from 8,000 trucks into a Kinesis data stream with 12 provisioned shards, using truck_id as the partition key. A Lambda function reads the stream, calls a slow geocoding API for each record, and writes results to DynamoDB. At peak, IteratorAge climbs to 40 minutes while shard read and write throughput stay below 30 percent. Events for each truck must stay in order, and finance will not pay for more shards. What should the data engineer do?
A: Raise ParallelizationFactor on the event source mapping to 5, so each shard feeds several concurrent invocations while records sharing a truck_id stay in order
B: Increase the stream to 48 shards with UpdateShardCount, so the existing event source mapping runs four times as many concurrent Lambda batches at peak
C: Register the function as an enhanced fan-out consumer, so it receives a dedicated 2 MB per second push connection per shard instead of polling GetRecords
D: Have the function forward every record to an SQS standard queue, and let a second function with high concurrency make the slow geocoding calls in parallel
K: A
G: ## Why a Kinesis consumer falls behind
With the default settings, Lambda processes **one batch at a time per shard**. If each batch takes a long time (here, a slow API call per record), the shard's backlog grows even though the shard itself has plenty of read capacity left. `IteratorAge` (the age of the last record in the batch Lambda just read) then rises.
## Two ways to get more parallel batches
- **More shards**: each shard gets its own batch stream. This works, but every shard is billed per hour.
- **ParallelizationFactor** (1 to 10) on the event source mapping: Lambda reads up to that many batches **from the same shard** at once. With 12 shards and a factor of 5, up to 60 invocations run concurrently.
Lambda still keeps **in-order processing at the partition-key level** when the factor is above 1, so all events for one `truck_id` are still processed in sequence.
W: ParallelizationFactor: it multiplies concurrent batches per shard without adding shards, and Lambda keeps per-partition-key ordering, so each truck's events stay in sequence while the lag drains.
X: B=More shards: resharding to 48 shards also adds concurrency, but it quadruples the shard-hour bill, which finance has ruled out. The shards are not even busy.
C=Enhanced fan-out: a dedicated 2 MB per second pipe helps when consumers compete for read throughput. Here reads are below 30 percent; the slow per-batch processing is the bottleneck, and enhanced fan-out does not add parallel batches.
D=SQS standard fan-out: a standard queue gives no ordering guarantee, so events for one truck could be geocoded and written out of sequence, breaking the ordering requirement.
T: When a Kinesis Lambda consumer lags because processing is slow (not because reads are throttled), raise ParallelizationFactor; ordering per partition key is preserved.
V: Amazon Kinesis Data Streams, AWS Lambda

@ DEA-C01 D1 T1.1 advanced use-case
S: A retailer's order service writes about 2 million messages a day to an Amazon SQS standard queue that uses the default settings, and a loader on EC2 batches them into the data warehouse. Next month the warehouse will be offline for a planned 10-day migration, and the loader will be stopped for the whole window. No order message may be lost, producers must keep using the same queue URL, and the team wants no extra storage outside SQS. What should the data engineer do before the migration?
A: Set the queue's MessageRetentionPeriod to 1,209,600 seconds, the 14-day maximum, so that unconsumed messages survive the whole outage with spare days
B: Attach a dead-letter queue with a 14-day retention period and a maxReceiveCount of 1, so waiting messages move there and are kept for the outage
C: Raise the queue's visibility timeout to the 12-hour maximum, so waiting messages stay hidden and protected from expiry until the loader starts again
D: Add a Lambda function on the queue that copies every message into S3 objects, so the loader can replay the saved orders after the warehouse returns
K: A
G: ## How long SQS keeps a message
Every queue has a **message retention period**: from 1 minute to **14 days**, default **4 days**. A message that nobody deletes is removed automatically when it is older than this period, counted from when it was sent.
With the default, a 10-day outage would silently lose every message older than 4 days.
## What does not extend a message's life
- **Visibility timeout** only hides a message for a while after a consumer receives it (maximum 12 hours). It does not change when the message expires.
- **Dead-letter queues** receive a message only after it has been *received* `maxReceiveCount` times without being deleted. Messages nobody receives never move. For standard queues the expiry is still based on the **original enqueue timestamp**, even in the DLQ.
W: 14-day retention: the retention period is a queue attribute that can be raised in place to 14 days, which covers the 10-day window with no new storage and no producer change.
X: B=DLQ with maxReceiveCount 1: with the loader stopped, nobody receives the messages, so nothing ever moves to the DLQ, and the source queue's 4-day retention still deletes them.
C=12-hour visibility timeout: visibility only applies after a receive and has no effect on expiry; unreceived messages still expire after 4 days.
D=Copy to S3 with Lambda: this would keep the data, but it adds storage outside SQS and a replay path, which the team explicitly wanted to avoid.
T: SQS retention is 4 days by default and at most 14 days; raise MessageRetentionPeriod before a planned consumer outage.
V: Amazon SQS

@ DEA-C01 D1 T1.1 advanced troubleshooting
S: A scheduled Amazon AppFlow flow runs every 15 minutes and copies changed Salesforce Opportunity records to Amazon S3 with incremental transfer on LastModifiedDate. Auditors found that some updates never reach S3. Salesforce sometimes commits records a few minutes after the LastModifiedDate it stamps on them, so those records fall before the previous run's cut-off. The fix must keep incremental transfer, must not copy full snapshots, and must not add custom code. What should the data engineer do?
A: Set an incremental transfer time offset of 10 minutes on the flow, so each run imports records changed in a window that ends 10 minutes before run time
B: Switch the flow to full transfer, so every 15-minute run copies a complete snapshot of all Opportunity records into a new S3 prefix for that run
C: Shorten the schedule to every 5 minutes, so that each incremental window is smaller and fewer late-committed records fall outside it between runs
D: Replace the flow with a Lambda function that queries the Salesforce API with an overlapping window and removes duplicate records by Opportunity Id
K: A
G: ## Incremental transfer in AppFlow
A schedule-triggered flow can use **incremental transfer**: each run copies only records added or changed since the last successful run, using a source timestamp field such as `LastModifiedDate`.
## The late-timestamp problem
If the source system commits a record *after* the time written in its timestamp, the record may become visible only after the next run has already moved its window past that time. Incremental transfer never looks back, so the record is skipped for good.
## The offset option
AppFlow lets you add a **time offset** `t` (less than 10 hours). A run at `T1` then imports records changed between `T0 - t` and `T1 - t`. The windows still join end to end, so nothing is copied twice, but each window closes `t` minutes in the past, giving late commits time to appear.
W: Time offset: shifting every incremental window back by 10 minutes lets late-committed records land inside a later window, with no duplicates, no snapshots and no code.
X: B=Full transfer: copying every record each run would catch late commits, but it creates full snapshots, which the requirements forbid.
C=Shorter schedule: a smaller window does not help. The cut-off still sits at run time, so a record committed after its timestamp still falls behind it.
D=Custom Lambda poller: an overlapping window with deduplication works, but it is custom code to write and maintain, which the team ruled out.
T: For AppFlow incremental flows that miss late-stamped records, add a time offset so each window ends a little before the run.
V: Amazon AppFlow, Amazon S3

@ DEA-C01 D1 T1.1 advanced tradeoff
S: An IoT team runs a Lambda function on a 10-shard Kinesis data stream that writes each invocation's records to S3 as one JSON object. Traffic is light overnight, so the function is often invoked for batches of only one to three records, creating millions of tiny objects that slow downstream Athena queries. The product owner accepts up to 5 minutes of extra delivery delay, the team wants no new services in the pipeline, and the function code must stay unchanged. Which change BEST meets these requirements?
A: Set MaximumBatchingWindowInSeconds to 300 and raise BatchSize on the event source mapping, so Lambda gathers larger batches before each invocation
B: Add an Amazon Data Firehose stream that reads the Kinesis stream and buffers for 300 seconds before writing larger objects to the same S3 prefix
C: Configure a 300-second tumbling window on the event source mapping and have the function return the records as state, writing one object per window
D: Reduce the stream to two shards with UpdateShardCount, so each shard accumulates more records before Lambda polls it and starts an invocation
K: A
G: ## When Lambda invokes a stream consumer
By default Lambda invokes the function **as soon as records are available**, even if the batch holds a single record. At low traffic that means many tiny invocations.
## The batching window
`MaximumBatchingWindowInSeconds` (up to 300 seconds) tells the event source mapping to keep reading until one of these happens:
- the batch reaches `BatchSize`,
- the batching window expires, or
- the payload reaches the 6 MB invocation limit.
Combined with a larger `BatchSize`, each invocation receives many more records, so a function that writes one object per invocation writes far fewer, larger objects. It is configuration only.
W: Batching window: buffering up to 300 seconds on the event source mapping makes each invocation, and therefore each S3 object, much larger while staying inside the 5-minute delay and leaving the code untouched.
X: B=Firehose buffering: this would also produce larger objects, but it adds a new service to the pipeline, which the team does not want.
C=Tumbling window: tumbling windows require the function to return a `state` object and handle `isFinalInvokeForWindow`, which means changing the code; the state is also capped at 1 MB per shard.
D=Fewer shards: Lambda still invokes as soon as any record exists, so fewer shards do not make batches bigger at low traffic, and they cut the stream's peak write capacity.
T: To get bigger batches from a Kinesis or SQS event source at low traffic, set a batching window (up to 5 minutes) and a larger batch size.

@ DEA-C01 D1 T1.1 advanced troubleshooting
S: A fleet of EC2 loader processes reads payment messages from an Amazon SQS standard queue and writes them to a ledger database. During reconciliation, the team finds payments that never reached the ledger and that are absent from both the queue and its dead-letter queue. CloudTrail data events were not enabled, so the team must reason from SQS behavior alone. Which THREE events could have removed those messages from the queue without a ledger write? (Select THREE)
A: A loader called DeleteMessage with the receipt handle before its ledger write, and the write then failed after the message was already gone
B: The loader fleet was stopped for longer than the queue's MessageRetentionPeriod, so SQS deleted the waiting messages automatically when they expired
C: An operator ran PurgeQueue on the production queue by mistake, which deletes every message in it, including messages that were in flight
D: The visibility timeout expired while a loader was still writing, so SQS discarded the messages because the loader had not deleted them in time
E: A loader process crashed right after ReceiveMessage, so SQS treated the received messages as delivered and removed them from the queue
F: A loader called ChangeMessageVisibility with a timeout of 0 seconds, which tells SQS that the message is no longer needed by any consumer
K: A,B,C
G: ## What really removes a message from SQS
A message leaves a queue only in a few ways:
- a consumer calls **DeleteMessage** with the receipt handle it got from `ReceiveMessage`;
- the message becomes older than the queue's **retention period** (default 4 days, maximum 14 days);
- someone runs **PurgeQueue**, which deletes all messages, including in-flight ones, and cannot be undone;
- a redrive policy moves it to a dead-letter queue after `maxReceiveCount` receives (ruled out here).
## What does NOT remove it
Receiving a message only hides it for the **visibility timeout**. If it is not deleted in time, because the consumer crashed, was slow, or set the visibility to 0 with `ChangeMessageVisibility`, the message becomes visible again and another consumer can receive it.
W: A=Delete before write: deleting first and writing second is a classic bug; if the write fails, the message is already gone.
B=Retention expiry: messages older than the retention period are deleted by SQS without anyone receiving them.
C=PurgeQueue: a purge deletes every message, including in-flight ones, and they cannot be retrieved.
X: D=Visibility timeout expiry: when the timeout expires the message becomes visible again; SQS does not discard it. The result is a duplicate, not a loss.
E=Crash after receive: SQS has no notion of "delivered"; without DeleteMessage the message reappears after the visibility timeout.
F=Visibility set to 0: this ends the visibility timeout early and makes the message available immediately to other consumers. It is the opposite of deleting it.
T: Only DeleteMessage, retention expiry, PurgeQueue (and DLQ redrive) remove SQS messages; visibility timeouts only hide them for a while.
V: Amazon SQS, Amazon EC2

@ DEA-C01 D1 T1.2 advanced use-case
S: A media company sends clickstream JSON to Amazon Data Firehose and stores it in S3 for Athena. Compliance now requires that the email field is replaced with a SHA-256 hash before any byte of the record lands in S3, and analysts want Parquet output that matches an existing AWS Glue Data Catalog table. Data may reach S3 up to 10 minutes late, and the team wants no servers or clusters to manage. Which TWO Firehose configurations together meet these requirements? (Select TWO)
A: A Firehose Lambda transformation function that hashes the email field and returns every record with its recordId and an Ok result for delivery
B: Firehose record format conversion with a JSON deserializer and the Parquet serializer, referencing the Glue table as the schema for the output
C: Delivery of raw JSON to a staging prefix, with a scheduled AWS Glue job every 10 minutes that hashes email and writes Parquet to a curated prefix
D: An Amazon EMR cluster with Spark Structured Streaming that reads the source data, hashes email, and writes Parquet files to S3 every few minutes
E: Parquet conversion only, plus an Athena view over the table that applies sha256 to the email column so that analysts never see the raw values
K: A,B
G: ## Firehose's in-flight processing steps
Firehose can change data before it writes to S3, in this order:
1. **Data transformation**: Firehose buffers incoming records (0.2 to 3 MB, up to 900 seconds) and invokes your Lambda function synchronously. The function returns each record with the same `recordId`, a `result` (`Ok`, `Dropped` or `ProcessingFailed`) and the new base64 data.
2. **Record format conversion**: Firehose reads JSON with a deserializer (OpenX or Hive JSON SerDe), uses a table in the **Glue Data Catalog** as the schema, and writes **Parquet or ORC** with a serializer.
Both are managed features of the stream, so there is nothing to run, and the transformed bytes are the only ones that reach the destination.
W: A=Lambda transformation: hashing happens inside Firehose before delivery, so the raw email never lands in S3.
B=Record format conversion: Firehose converts the transformed JSON to Parquet using the existing Glue table as the schema, with no cluster to manage.
X: C=Staging plus Glue job: the raw JSON with clear-text email lands in S3 first, which violates the compliance rule even if it is deleted later.
D=EMR Structured Streaming: it can hash and write Parquet, but an EMR cluster is exactly the infrastructure the team does not want to manage.
E=Athena view with sha256: the view hides the value from analysts, but the clear-text email is still stored in S3.
T: To mask fields before they land and write Parquet, chain a Firehose Lambda transformation with record format conversion against a Glue table.

@ DEA-C01 D1 T1.2 advanced troubleshooting
S: A team configured an Amazon Data Firehose stream with record format conversion to Apache Parquet, using an AWS Glue Data Catalog table that lists the columns of a partner feed. The partner sends comma-separated lines, and every record now lands in the S3 error prefix with a format conversion failure. The partner cannot change its output format, data must reach S3 within 5 minutes, and Firehose must stay the only delivery path. What should the data engineer do?
A: Add a Firehose Lambda transformation that parses each CSV line into a JSON object, so the deserializer receives JSON before the Parquet conversion step
B: Switch the deserializer from the OpenX JSON SerDe to the Apache Hive JSON SerDe, and list timestamp formats that match the partner's CSV columns
C: Turn off format conversion, deliver the CSV files to S3, and run an hourly AWS Glue job that rewrites them as Parquet files in a curated prefix
D: Change the Glue table's serialization library to OpenCSVSerDe, so Firehose reads the comma-separated lines with the same library as the table itself
K: A
G: ## What Firehose format conversion accepts
Record format conversion needs three parts: a **deserializer**, a **schema** from a Glue table, and a **serializer** (Parquet or ORC).
The only deserializers are **OpenX JSON SerDe** and **Apache Hive JSON SerDe**. In other words, Firehose converts **from JSON only**. For CSV or other text, the documented approach is to add a Lambda transformation that turns each record into JSON first; conversion then runs on the Lambda output.
## Order of operations
Lambda transformation runs before format conversion, so the conversion step never sees the original CSV.
W: Lambda CSV-to-JSON transform: Firehose's converter reads only JSON, so turning each line into a JSON object first lets the existing conversion produce Parquet inside the same stream within the latency target.
X: B=Hive JSON SerDe: both deserializers parse JSON. Switching between them changes how timestamps are read, not whether CSV can be parsed.
C=Hourly Glue rewrite: it would produce Parquet, but hourly runs break the 5-minute target and add a second processing path.
D=OpenCSVSerDe on the table: Firehose uses the Glue table only for the column schema; the deserializer is chosen in the stream and must be a JSON SerDe.
T: Firehose converts only JSON to Parquet or ORC; for CSV input add a Lambda transformation that emits JSON first.
V: Amazon Data Firehose, AWS Lambda, AWS Glue Data Catalog

@ DEA-C01 D1 T1.2 advanced tradeoff
S: An Amazon Data Firehose stream uses dynamic partitioning on customer_id, about 3,000 active customers, with a 60-second buffer interval, and writes JSON logs to S3 for a nightly AWS Glue job. The job is slow because each run opens millions of objects of a few kilobytes. Logs only have to be in S3 within 15 minutes, analysts filter by region and day rather than by customer, and the team will not run a separate compaction job. Which TWO changes help MOST? (Select TWO)
A: Raise the buffer interval to 900 seconds and the buffer size to 128 MB, so each partition accumulates data for up to 15 minutes before delivery
B: Change the dynamic partitioning keys from customer_id to region and event date, so far fewer partitions each receive a larger share of the records
C: Set the buffer interval to 0 seconds, so Firehose writes records to S3 at once and the nightly Glue job can begin reading the files earlier
D: Schedule an extra AWS Glue job before the main job that merges each customer prefix into a few large Parquet files for the main job to read
E: Lower the buffer size to 1 MB, so that Firehose flushes each partition sooner and spreads its writes more evenly across all customer prefixes
K: A,B
G: ## Where small files come from in Firehose
Firehose writes one object per buffer flush. A flush happens when the **buffer size** (1 to 128 MB for S3) or the **buffer interval** (0 to 900 seconds for S3) is reached, whichever comes first.
With **dynamic partitioning**, Firehose keeps a separate buffer per partition key value. 3,000 customers flushed every 60 seconds means up to 3,000 small objects per minute.
## Two levers
- **Longer buffers**: the interval can go up to 900 seconds (15 minutes), so each object holds more data.
- **Fewer partitions**: partition by the keys people actually filter on. Region and day give far fewer, larger partitions, and Athena or Glue can still prune by them.
Zero buffering is not available with dynamic partitioning or for S3 backup.
W: A=Longer buffers: a 900-second interval with the maximum size makes every flush roughly 15 times larger while staying within the 15-minute delivery limit.
B=Coarser partition keys: partitioning by region and date cuts the number of parallel buffers from thousands to a handful, so each object is much larger and still matches how analysts filter.
X: C=Zero buffering: it is not supported with dynamic partitioning, and if it were, it would create even more, smaller objects.
D=Compaction job: merging files would help the main job, but it is the separate compaction job the team refuses to run.
E=1 MB buffer size: a smaller size triggers flushes sooner, which produces more and smaller objects, the opposite of the goal.
T: Firehose small files: lengthen buffering hints toward 900 s / 128 MB and partition only by low-cardinality keys that queries filter on.

@ DEA-C01 D1 T1.2 advanced use-case
S: A genomics team runs a Lambda transformation that annotates sample files using a 6 GB reference index. Up to 400 concurrent invocations need the same index, and a nightly job replaces it with a new version that every invocation must see right away. Downloading the index from S3 on each cold start pushes processing past a 2-minute target, and the team wants to stay serverless without managing instances. Which TWO steps should the data engineer take? (Select TWO)
A: Store the index on an Amazon EFS file system with an access point, and add a file system configuration that mounts it under /mnt in the function
B: Connect the function to private subnets that have EFS mount targets in each Availability Zone, with security groups that allow NFS on port 2049
C: Raise the function's ephemeral storage to 10,240 MB and copy the index into /tmp during initialization, so warm invocations reuse the local copy
D: Publish the index as a new Lambda layer version each night, so every invocation of the function finds the reference files under the /opt directory
E: Serve the index from an NFS server on an Amazon EC2 instance in the same VPC, and mount it from the function code at the start of each invocation
K: A,B
G: ## Storage options inside Lambda
- **/tmp (ephemeral storage)**: 512 MB to 10,240 MB, but **private to one execution environment**. Each new environment starts empty, so a large file must be copied in again on every cold start.
- **Layers and deployment packages**: read-only and limited to **250 MB unzipped** in total.
- **Amazon EFS**: a shared, elastic NFS file system. All concurrent invocations see the same files, and a new version written by another job is visible at once.
## What mounting EFS requires
- An EFS file system with an **access point**, configured on the function with a local mount path under `/mnt`.

Athena treats source files whose names start with an underscore (`_`) or a dot (`.`) as **hidden** and skips them. Tools such as Hadoop and Spark use these prefixes for marker files (`_SUCCESS`) and temporary files. The documented fix is to **rename the files**.
## What LOCATION accepts
A table `LOCATION` must be an S3 folder path ending with a slash, such as `s3://bucket/folder/`. File names, wildcards and glob patterns are not allowed.
## Partitions are a different problem
`MSCK REPAIR TABLE` adds missing Hive-style partitions to the catalog. It does not change which files inside a location Athena reads.
W: Copy to names without the underscore: Athena reads every non-hidden file under the table location, so renamed copies become visible with no change to the table or the vendor's tool.
X: B=Wildcard LOCATION: a LOCATION cannot contain file names or glob patterns, so this is not a valid way to point a table at hidden files.
C=MSCK REPAIR TABLE: the table is not missing partitions; the files are skipped because of their names, which a partition repair does not change.
D=Crawler include pattern: crawler include and exclude patterns affect only what the crawler scans; Athena still reads the folder and still skips the underscore files.
T: Athena skips files whose names start with _ or .; rename them (for example by copying) instead of changing the table.
V: Amazon Athena, Amazon S3

@ DEA-C01 D3 T3.2 advanced troubleshooting
S: Analysts' Athena queries on a reporting table fail several times a day with HIVE_FILESYSTEM_ERROR: Incorrect fileSize or with HIVE_CURSOR_ERROR: The specified key does not exist. An hourly AWS Glue job refreshes the table by overwriting the same S3 object keys in place. Analysts query around the clock, the data must stay in the same S3 bucket, and the refresh must remain hourly. Which change resolves the errors?
A: Have the Glue job write each refresh to new object keys or a new partition and then point the table at them, never replacing files in place
B: Run the hourly Glue job only at the top of each hour, and ask analysts not to run queries during the first five minutes of every hour
C: Turn on S3 Versioning for the bucket, so Athena can keep reading the previous object version while the Glue job replaces the current file
D: Raise the query timeout in the Athena workgroup and turn on query result reuse, so that failed queries are answered from earlier cached query results
K: A
G: ## Why in-place overwrites break Athena
Athena lists the files of a table when it plans a query and reads them during execution. If a file is replaced or deleted in between:
- `HIVE_FILESYSTEM_ERROR: Incorrect fileSize` means the file changed between planning and execution (for example a `PUT` to an existing key);
- `HIVE_CURSOR_ERROR ... The specified key does not exist` means a file was removed while the query ran.
Athena does not support deleting or replacing file contents while a query is running. The documented fix is to schedule overwrites when no queries run or to **only write data to new files or partitions**.
W: Write to new keys or partitions: queries keep reading a complete, unchanging set of files while the next version is written, and the table then switches to the new data.
X: B=Quiet window for analysts: queries run around the clock, so asking people to pause conflicts with the requirement and still fails for long-running queries.
C=S3 Versioning: Athena reads the current object, not earlier versions, so replacing it mid-query still causes the same errors.
D=Longer timeout and result reuse: the errors come from changed files, not slow queries; reuse returns stale results only for repeated identical queries and fixes nothing else.
T: Never overwrite files under a live Athena table; write new files or partitions and switch the table to them.
V: Amazon Athena, AWS Glue, Amazon S3

The jobs start at midnight and usually finish within an hour, the results are needed by 8 AM, and a delayed start is acceptable. Finance asks to reduce the cost of these jobs without rewriting them and without moving them off AWS Glue. What should the data engineer do?

@ DEA-C01 D3 T3.3 advanced troubleshooting
S: An AWS Glue 4.0 Spark job on 10 G.1X workers converts 2,000 gzipped JSON files to Parquet and takes 70 minutes, but it must finish within 30 minutes. Job metrics show the maximum needed executors staying near 120 for most of the run, while active executors stay flat at the allocated maximum. Driver and executor memory use stay below 40 percent. The team wants to fix this through configuration only. Which TWO actions help? (Select TWO)
A: Enable auto scaling with a maximum number of workers well above 10, so Glue adds workers while the needed executors exceed the active ones
B: Raise the number of G.1X workers in proportion to the ratio of needed to allocated executors, because the job is under-provisioned
C: Switch to R.1X memory-optimized workers with the same worker count, because memory pressure on the executors is what makes tasks queue up
D: Set the job's execution class to FLEX, so that it receives spare capacity sooner and its 70-minute run time drops below the 30-minute target
E: Repartition the input into a single partition before the write step, so Spark creates fewer Parquet files and spends less time on small writes
K: A,B
G: ## Reading Glue job metrics for capacity
- **Maximum needed executors** = (running tasks + pending tasks) / tasks per executor: how many executors the current load could use.
- **Active executors**: how many executors are running tasks.
- **Maximum allocated executors**: the ceiling set by the number of workers.
When needed executors stay far above active executors, and active executors sit at the allocated maximum, the job is **under-provisioned**: tasks wait for executors, not for memory. The Glue capacity-planning guide scales DPUs by that ratio.
## Two ways to add capacity
- Raise the fixed number of workers.
- Enable **auto scaling** (Glue 3.0 or later, G or R worker types): Glue adds workers while executors are needed and removes idle ones, up to the maximum you set.
W: A=Auto scaling with a higher maximum: Glue adds executors while tasks are pending and releases them when they go idle, so the run speeds up without paying for idle workers.
B=More G.1X workers: the needed-to-allocated ratio of about 120 to 10 shows the job is starved of executors, so scaling workers by that ratio adds the missing parallelism.
X: C=R.1X memory-optimized workers: memory use is below 40 percent, so more memory per worker does not add executors.
D=FLEX execution class: Flex lowers cost for non-urgent jobs; it does not add capacity, and start and run times may even be longer.
E=Single partition: it removes almost all parallelism, so the job would get slower, not faster.
T: Needed executors far above active executors means under-provisioning: add workers or enable auto scaling.
V: AWS Glue, Amazon CloudWatch

@ DEA-C01 D3 T3.3 advanced troubleshooting
S: An Amazon SQS standard queue with a 4-day retention period has a redrive policy to a dead-letter queue that also uses 4-day retention. Because of long visibility timeouts, malformed messages can spend up to 3 days in the source queue before they reach the DLQ. Engineers review the DLQ once a week and will not change that schedule, yet many failed messages vanish from the DLQ within a day of arriving. Failed messages must be kept at least 7 days after they fail. What should the data engineer change?
A: Raise the DLQ's retention period to 14 days, because a message moved from a standard queue keeps its original enqueue timestamp in the DLQ
B: Lower maxReceiveCount to 1, so failing messages move to the DLQ after the first failed attempt and their retention clock restarts on the move
C: Convert both queues to FIFO queues, so the enqueue timestamp is reset when a message moves to the DLQ and the 4-day period starts again
D: Add a CloudWatch alarm on the DLQ's ApproximateNumberOfMessagesVisible metric, so engineers review failed messages on the day they arrive
K: A
G: ## Retention in a dead-letter queue
For **standard queues**, a message's expiry is always based on its **original enqueue timestamp**. Moving it to a DLQ does not reset that clock. A message that spent 3 days in a source queue arrives in a DLQ with 4-day retention with only about 1 day left.
For **FIFO queues**, the enqueue timestamp is reset when a message moves to the DLQ.
## The practical rule
Set the DLQ's retention period **longer than the source queue's**, and long enough for your review process. The maximum is 14 days.
W: 14-day DLQ retention: counted from the original send time, 14 days leaves at least 11 days after the move, well beyond the 7-day requirement and the weekly review.
X: B=maxReceiveCount 1: the clock does not restart for standard queues, and a single failed attempt sends messages with transient errors to the DLQ that a retry would have fixed.
C=Convert to FIFO: FIFO does reset the timestamp, but 4 days is still shorter than the required 7, and converting means new queues and producer changes.
D=Same-day alarm: it relies on engineers reviewing daily, which they will not do, and the messages still expire after about a day.
T: For standard SQS queues, the DLQ's retention must exceed the source queue's because messages keep their original enqueue time.
V: Amazon SQS, Amazon CloudWatch

@ DEA-C01 D3 T3.3 advanced troubleshooting
S: A Lambda function consumes a Kinesis data stream with 20 shards and a ParallelizationFactor of 4, and at peak it used to run about 70 concurrent invocations. After a security review, the function's reserved concurrency was set to 20. Since then IteratorAge has risen steadily on most shards and the Throttles metric is above zero, while Duration and Errors are unchanged. Records must be processed within 5 minutes of arrival, and the shard count must not change. What is the MOST likely fix?
A: Raise the function's reserved concurrency to at least 80, because the event source mapping can run one invocation per shard for each parallelization slot
B: Register an enhanced fan-out consumer for the function, so it gets a dedicated 2 MB per second read pipe per shard and stops sharing read throughput
C: Enable BisectBatchOnFunctionError with an on-failure destination, so that batches that keep failing are split and stop blocking their shards
D: Lower the ParallelizationFactor to 1, so the event source mapping needs only 20 concurrent invocations and matches the new reserved concurrency
K: A
G: ## How much concurrency a Kinesis consumer needs
The event source mapping runs up to **shards x ParallelizationFactor** concurrent batches, here 20 x 4 = 80.
**Reserved concurrency** caps the function. When the mapping needs more than the cap, invocations are **throttled** (`Throttles` > 0), batches wait, and `IteratorAge` rises.
## Reading the metrics together
- Throttles up, Duration and Errors flat: concurrency is capped; the code is fine.
- Errors up: a failing batch is retried and blocks its shard (bisect, retry limits, on-failure destination).
- Read throughput exceeded: consumers compete for the shard's 2 MB/s (enhanced fan-out).
W: Reserved concurrency of 80 or more: the mapping needs up to 80 concurrent invocations, and the security cap of 20 is what throttles it; raising the cap restores the throughput the stream needs.
X: B=Enhanced fan-out: it fixes read contention between consumers, but nothing shows read throttling; the throttles are Lambda concurrency throttles.
C=Bisect on error: Errors are unchanged, so no batch is failing repeatedly and splitting batches would not help.
D=ParallelizationFactor 1: throttling would stop, but the function previously needed about 70 concurrent invocations at peak, so 20 cannot keep up and the 5-minute target is still missed.
T: Rising IteratorAge with Throttles > 0 and flat errors means the function's concurrency cap is below shards x ParallelizationFactor.

@ DEA-C01 D3 T3.4 advanced tradeoff
S: A nightly AWS Glue ETL job loads partner transaction files whose volume grows about 3 percent each month. A static rule, RowCount > 500000, has started to miss partial deliveries that are still above that number but far below a normal night. The team wants the check to adjust to recent history automatically, to run inside the existing ETL job before the curated write, and to need no custom code or extra state store. Which approach fits BEST?
A: Replace the static rule with the dynamic DQDL rule RowCount >= min(last(7)) in the job's Evaluate Data Quality transform before the curated write
B: Keep the static rule, and raise its threshold every month in a scheduled ruleset update based on the previous month's average nightly row count
C: Create a Data Catalog data quality ruleset on the table with RowCount >= min(last(7)), and schedule it to run after each nightly load completes
D: Have the job write its row count to a DynamoDB table and compare it with the stored average of the last seven runs in PySpark code before writing
K: A
G: ## Dynamic rules in DQDL
DQDL rules normally compare a metric with a fixed value. **Dynamic rules** compare it with the metric's own history using `last(k)`:
- `RowCount > last()` compares with the previous run;
- with `k > 1` an aggregate is needed: `avg`, `median`, `min`, `max`, `sum`, `std`, for example `RowCount > avg(last(5))` or `RowCount >= min(last(7))`.
Glue stores the history of these metrics for you, so no table or code is needed.
## Where they run
Dynamic rules are supported **only in AWS Glue ETL**, not in Data Catalog data quality rulesets.
W: Dynamic rule in the ETL job: the threshold moves with recent history, the check runs in the job before the curated write, and Glue keeps the history itself.
X: B=Monthly threshold update: the threshold still lags behind real volume and someone or something has to update the ruleset every month; it is not automatic.
C=Data Catalog ruleset: dynamic rules are not supported for Data Catalog evaluations, and a check after the load runs too late to protect the curated data.
D=DynamoDB plus PySpark: it would work, but it is the custom code and extra state store the team wants to avoid.
T: Thresholds that should follow history call for dynamic DQDL rules with last(k), which run only in Glue ETL jobs.
V: AWS Glue
