@ DEA-C01 D4 T4.4 applied use-case
S: An organization already delivers its CloudTrail logs to a centralized Amazon S3 bucket and wants to run ad hoc SQL queries against historical logs stored as JSON/gzip files without deploying additional infrastructure. Which service is the most direct fit?
A: Amazon Kinesis Data Analytics reading the CloudTrail events as a stream
B: AWS Glue DataBrew with a project and recipe over the CloudTrail log files
C: Amazon Redshift Spectrum external tables, after provisioning a Redshift cluster
D: Amazon Athena with a table defined over the CloudTrail S3 log location
K: D
G: ## Querying CloudTrail logs in S3 with Athena
A trail delivers gzipped JSON log files to S3 under a path like `AWSLogs/<account-id>/CloudTrail/<region>/<yyyy>/<mm>/<dd>/`. **Amazon Athena** is serverless: you define a table over that location and query the files where they are.
- The CloudTrail console can generate the Athena table for you, and AWS documents a `CREATE TABLE` statement using a CloudTrail SerDe.
- **Partition projection** on Region and date lets Athena compute partitions from the path instead of loading them, which keeps queries fast and cheap.
- You pay per data scanned, with no clusters to run.
Example: `SELECT eventName, count(*) FROM cloudtrail_logs WHERE eventSource = 's3.amazonaws.com' AND timestamp >= '2026/09/01' GROUP BY eventName;`
W: Athena with a table over the CloudTrail location: it queries the existing JSON/gzip files in place with standard SQL, with no servers, clusters or pipelines to deploy.
X: A=Kinesis Data Analytics: this service (now Amazon Managed Service for Apache Flink) processes streaming data in real time; it is not meant for ad hoc queries over files already stored in S3.
B=Glue DataBrew: DataBrew is a visual tool for cleaning and preparing data with recipes; it does not provide interactive SQL querying of log archives.
C=Redshift Spectrum after provisioning a cluster: Spectrum can read the files in S3, but it requires a running Redshift cluster or workgroup, which is the additional infrastructure the requirement says to avoid.
T: Ad hoc SQL on CloudTrail files already in S3 with nothing to deploy is Athena with a CloudTrail table and partition projection.
V: Amazon Athena, AWS CloudTrail, Amazon S3

@ DEA-C01 D2 T2.1 advanced definition
S: Partners must upload files by SFTP into S3 with their existing keys, and each partner may see only its own folder. No servers should be managed. Which service fits?
A: AWS DataSync agents installed at each partner site
B: AWS Transfer Family SFTP with scoped home folders
C: S3 presigned upload URLs emailed to partners daily
D: An SFTP server on EC2 that syncs uploads to S3
K: B
G: ## AWS Transfer Family
**AWS Transfer Family** provides fully managed SFTP, FTPS, FTP and AS2 endpoints that store files directly in Amazon S3 or Amazon EFS. AWS runs, scales and patches the servers.
- Partners connect with standard SFTP clients and authenticate with their existing **SSH public keys** stored on their Transfer Family user (or with a custom identity provider).
- Each user gets an IAM role and a **logical home directory**, for example `/` mapped to `s3://partner-inbox/acme/`. With restricted logical directories, the partner cannot browse or even see other partners' folders.
- Uploaded files land as S3 objects, so S3 event notifications or EventBridge can start the next pipeline step.
## Example
User `acme` connects to `s-1234.server.transfer.us-east-1.amazonaws.com`, runs `put orders.csv`, and the file appears at `s3://partner-inbox/acme/orders.csv`.
W: AWS Transfer Family SFTP with scoped home folders: a managed SFTP endpoint backed by S3, SSH key authentication, and per-user logical home directories give each partner its own folder with no servers to run.
X: A=DataSync agents at each partner: DataSync moves data between storage systems using agents the partners would have to deploy and run; it is not an SFTP endpoint that partners log in to with their keys.
C=Presigned URLs emailed daily: presigned URLs are HTTPS links for single objects that expire; they are not SFTP, do not use the partners' SSH keys, and emailing links daily is manual and fragile.
D=EC2 SFTP server syncing to S3: this works technically but means running, patching and scaling servers yourself, which violates the no-servers requirement.
T: Managed SFTP into S3 with per-partner folder isolation is AWS Transfer Family with logical home directories.
V: AWS Transfer Family

@ DEA-C01 D2 T2.3 applied comparison
S: A team needs the ability to restore a DynamoDB table to any point in time within the last 35 days after an application bug caused unwanted writes, without needing to manually schedule backups. Which feature should be enabled?
A: DynamoDB Point-in-Time Recovery (PITR)
B: DynamoDB on-demand backups taken on request
C: DynamoDB Streams feeding a change log
D: DynamoDB global tables in a second Region
K: A
G: ## DynamoDB point-in-time recovery
With PITR enabled, DynamoDB continuously backs up a table without affecting performance or needing a schedule.
- You can restore to any second within the recovery period, which is 35 days by default and can be set from 1 to 35 days.
- A restore always creates a **new table**; you then compare data or switch the application.
Example: a bug starts writing bad data at 09:12. Restore the table to 09:11 as `orders_restored`, then copy corrected items back or repoint the app.
## How it compares
- **On-demand backups** are full backups you (or AWS Backup) create at chosen times; you can restore only to those moments.
- **Streams** is a 24-hour change log for triggers and replication, not a backup.
- **Global tables** replicate writes to other Regions, including bad writes.
W: Point-in-Time Recovery: it provides continuous backups with restore to any second in the recovery window, with no manual backup scheduling.
X: B=On-demand backups taken on request: each backup captures the table at the moment it is taken, so recovery is limited to those snapshots, and they must be created or scheduled.
C=DynamoDB Streams: stream records are kept for 24 hours and are a change feed, not a restore mechanism for a table.
D=Global tables in a second Region: they replicate each write to other Regions within seconds, so the buggy writes are copied too; they protect against Regional outages, not bad data.
T: Restoring DynamoDB to any second in the past 35 days is PITR; backups give fixed points, and replication copies mistakes.
V: Amazon DynamoDB

@ DEA-C01 D1 T1.4 advanced use-case
S: A Redshift table of 2 billion customer rows receives about 1 million new and changed rows each hour in a staging table. Changed rows must replace existing rows by customer_id and new rows must be added, without duplicates and without reloading the whole table. Which SQL approach fits?
A: Declare customer_id as the PRIMARY KEY of the target table and INSERT the staged rows so that Redshift rejects duplicates
B: INSERT the staged rows into the target table and run VACUUM afterward so that the duplicate customer_id rows are removed
C: TRUNCATE the target table each hour and reload the full customer dataset from S3 using a COPY command with a manifest
D: Run MERGE INTO the target USING the staging table ON customer_id, updating matched rows and inserting unmatched rows
K: D
G: ## Upserts in a columnar warehouse
An **upsert** updates rows that already exist and inserts rows that do not. Redshift supports the SQL `MERGE` statement for this:
- `MERGE INTO customers USING customers_stage s ON customers.customer_id = s.customer_id`
- `WHEN MATCHED THEN UPDATE SET name = s.name, tier = s.tier, updated_at = s.updated_at`
- `WHEN NOT MATCHED THEN INSERT VALUES (s.customer_id, s.name, s.tier, s.updated_at)`
Before MERGE existed, the pattern was delete-then-insert inside one transaction; MERGE does both in one statement.
## Constraints in Redshift
Redshift accepts `PRIMARY KEY` and `UNIQUE` definitions but does **not enforce** them. The optimizer uses them as hints, so inserting duplicate keys succeeds and gives wrong results later.
## Other notes
`VACUUM` reclaims space and re-sorts rows; it never removes logical duplicates. The staging table itself should have one row per key, for example deduplicated with `ROW_NUMBER()`.
W: MERGE with staging: it updates rows whose customer_id already exists and inserts the rest in one statement, touching only the hourly changes instead of the full 2 billion rows.
X: A=Primary key plus INSERT: Redshift does not enforce primary keys, so every changed row becomes a duplicate instead of being rejected.
B=INSERT then VACUUM: VACUUM re-sorts and reclaims deleted space; it has no notion of duplicate keys, so the old and new versions both remain.
C=Hourly truncate and full reload: gives correct data but rewrites 2 billion rows each hour to apply 1 million changes, and leaves the table empty during the reload.
T: Upsert into Redshift with MERGE from a staging table; primary keys are not enforced and VACUUM does not deduplicate.
V: Amazon Redshift

@ DEA-C01 D2 T2.3 applied use-case
S: Which TWO actions reduce storage cost for a versioned S3 data lake bucket? (Select TWO)
A: Abort incomplete multipart uploads with a lifecycle rule
B: Replicate the objects to three other Regions for resilience
C: Disable compression for the data files written to the bucket
D: Enable Transfer Acceleration for uploads to the bucket
E: Expire noncurrent object versions after a set period
K: A,E
G: ## Hidden storage in a versioned bucket
With versioning enabled, an overwrite or delete does not remove the old data. The previous object becomes a **noncurrent version**, and you keep paying for it. In a data lake that rewrites files daily, noncurrent versions can grow larger than the current data.
Another hidden cost is **incomplete multipart uploads**: when a large upload fails midway, the uploaded parts stay in the bucket, billed as storage, but are not visible as objects.
## Lifecycle rules clean both up
- `NoncurrentVersionExpiration` with `NoncurrentDays: 30` permanently removes versions 30 days after they became noncurrent (optionally keeping a few newest ones).
- `AbortIncompleteMultipartUpload` with `DaysAfterInitiation: 7` deletes parts of uploads that never completed.
Both run automatically with no application changes.
W: A=Abort incomplete multipart uploads: removes orphaned parts from failed uploads, which are billed as storage but serve no purpose.
E=Expire noncurrent versions: removes old versions after a retention window, which is usually the largest hidden cost in a versioned bucket.
X: B=Replicate to three Regions: each replica is a full additional copy billed in its Region, plus inter-Region transfer charges, so storage cost rises roughly fourfold.
C=Disable compression: uncompressed files are larger, so the bucket stores more bytes; it also makes Athena and Spectrum scan more data.
D=Transfer Acceleration: it speeds up long-distance uploads through edge locations and adds a per-GB transfer charge; it does not reduce the amount of data stored.
T: In versioned buckets, use lifecycle rules to expire noncurrent versions and abort incomplete multipart uploads; replication and acceleration add cost rather than removing it.
V: Amazon S3

@ DEA-C01 D2 T2.3 advanced use-case
S: A data lake must support deleting a specific customer's records within 30 days of a request (GDPR), with ACID guarantees and time travel for audits. Which table format fits BEST?
A: JSON files in S3 with Object Lock retention enabled.
B: Apache Iceberg tables queried with Athena or Glue.
C: Plain Parquet files partitioned by date in S3.
D: CSV files tracked by a manifest file per load.
K: B
G: ## Open table formats
Plain files in S3 cannot be changed row by row: deleting one customer means rewriting whole files, and readers may see half-finished rewrites. **Apache Iceberg** is a table format that adds a metadata layer on top of Parquet files.
- **ACID transactions**: each write creates a new **snapshot** atomically, so readers never see partial changes.
- **Row-level operations**: `DELETE FROM customers_events WHERE customer_id = 'c-981'` and `MERGE INTO` work directly in Athena and in Glue (Spark).
- **Time travel**: queries such as `FOR TIMESTAMP AS OF` read the table as it was at an earlier snapshot, which supports audits.
## GDPR note
Older snapshots still reference the deleted rows. To remove them physically, expire old snapshots and clean up unreferenced files (for example `VACUUM` in Athena) within the retention window, while keeping enough history for audit needs.
W: Apache Iceberg tables: they provide ACID row-level deletes that satisfy erasure requests, plus snapshot-based time travel for audits, with native support in Athena and Glue.
X: A=JSON with Object Lock: Object Lock prevents deletion or overwriting for a retention period, which directly conflicts with the requirement to erase a customer's data.
C=Plain Parquet by date: deleting one customer means finding and rewriting each affected file with custom code, with no transactions and no time travel.
D=CSV with a manifest: a manifest lists files but gives no ACID guarantees, row-level deletes or snapshots, and CSV is slow to scan.
T: Row-level deletes with ACID and time travel on S3 require an open table format such as Iceberg; plain files and Object Lock cannot do both.
V: Apache Iceberg, Amazon Athena, Amazon S3

@ DEA-C01 D4 T4.5 applied use-case
S: A multinational company must ensure that customer data belonging to European Union residents is never stored or processed outside EU AWS Regions, to comply with data sovereignty requirements. Which combination of controls best enforces this at the account/organization level?
A: A multi-Region CloudTrail trail with alerts on API calls made in non-EU Regions
B: SCPs denying actions outside approved EU Regions
C: Amazon Macie jobs that move EU data back to EU Regions when found elsewhere
D: Region checks coded into the application logic of each microservice
K: B
G: ## Preventive versus detective controls
- A **detective** control (CloudTrail logs, AWS Config rules) tells you after the fact that something happened.
- A **preventive** control stops the action from happening at all. Data sovereignty ("never stored or processed outside the EU") needs a preventive control.
## Service control policies (SCPs)
SCPs are attached in AWS Organizations to the root, an OU or an account. They set the maximum permissions for every IAM user and role in those accounts, including administrators, and cannot be bypassed from inside the member account.
A Region guardrail uses the `aws:RequestedRegion` condition key, for example a `Deny` on all actions when the Region is not `eu-central-1`, `eu-west-1` or `eu-west-3`. Global services such as IAM, Organizations or Route 53 are usually listed in a `NotAction` exception because their API calls are served from a US Region. AWS Control Tower offers the same pattern as its Region deny control.
W: SCPs denying non-EU Regions: an organization-level `Deny` on requests outside approved EU Regions prevents any principal in the member accounts from creating storage or compute elsewhere, which is the enforcement the requirement asks for.
X: A=CloudTrail with alerts: a trail records API calls and alerts fire after the fact; nothing is blocked, so the violation is seen after the data has already left the EU.
C=Macie moving data: Macie finds and classifies sensitive data in S3. It does not move or replicate data between Regions, and moving data later would not prevent it from being stored outside the EU in the first place.
D=Application checks: each microservice would have to implement the rule correctly, and anyone with console or API access could still create resources in other Regions. There is no central enforcement.
T: Sovereignty rules need a preventive guardrail that no one in the account can override: an SCP on `aws:RequestedRegion`, not logging or per-application checks.
V: AWS Organizations, IAM, AWS CloudTrail

@ DEA-C01 D2 T2.3 advanced troubleshooting
S: A company must permanently delete a customer's data from an S3 bucket that has both Versioning and Object Lock enabled in Compliance mode, to satisfy a right-to-erasure request, but discovers the objects cannot be deleted before their retention period expires. What is the correct explanation?
A: Object Lock applies to the current version and is lifted once a delete marker is added
B: Compliance mode blocks deletion by any user, including root, until retention ends
C: Turning on Versioning overrides Object Lock restrictions for erasure requests
D: An IAM administrator granted s3:BypassGovernanceRetention can bypass compliance mode
K: B
G: ## Object Lock modes
S3 Object Lock applies write-once-read-many (WORM) protection to **object versions** and requires versioning.
- **Governance mode**: most users cannot delete or change the lock, but a user with `s3:BypassGovernanceRetention` can by sending the bypass header.
- **Compliance mode**: no user, including the account root user, can delete a locked version or shorten its retention until the retain-until date passes.
- **Legal hold**: a separate flag with no end date, removed explicitly.
A delete request without a version ID only adds a delete marker; the locked version itself still exists until retention ends.
## Why this matters for erasure requests
Choosing compliance mode is a deliberate promise that data cannot be removed early. Data that may need to be erased on request should not be locked in compliance mode, or should use a retention period the policy allows.
W: Compliance mode blocks deletion by any user: that is the defining property of compliance mode, even for the root user, so the locked versions cannot be deleted until their retention period expires.
X: A=Lifted by a delete marker: Object Lock is set on individual versions, and each locked version stays protected. A delete without a version ID just adds a delete marker; the locked versions remain.
C=Versioning overrides the lock: versioning is a prerequisite for Object Lock, not an override. Turning it on does not relax any retention.
D=Bypass permission: `s3:BypassGovernanceRetention` works for governance mode. Compliance-mode retention cannot be bypassed by any IAM permission.
T: Governance mode can be bypassed with a special permission; compliance mode cannot be bypassed by anyone until retention ends.
V: Amazon S3

@ DEA-C01 D1 T1.1 applied use-case
S: A retail company wants to query live clickstream events arriving on an Amazon Kinesis Data Stream directly from Amazon Redshift using SQL, with sub-minute latency, without first landing the data in Amazon S3 or running a separate ETL job. Which Redshift capability supports this?
A: Redshift federated queries to Amazon RDS for PostgreSQL
B: Redshift Serverless snapshot restore into a namespace
C: Redshift streaming ingestion into a materialized view
D: Redshift Spectrum with an external schema and tables
K: C
G: ## Redshift streaming ingestion
Amazon Redshift can read directly from **Amazon Kinesis Data Streams** and **Amazon MSK** without staging in S3.
First you create an external schema that points at the stream source using an IAM role, for example `CREATE EXTERNAL SCHEMA kds FROM KINESIS IAM_ROLE '...'`.
Then you define a **materialized view** over the stream, for example selecting `approximate_arrival_timestamp` and parsing the JSON payload stored in the `kinesis_data` column.
- Each refresh pulls new records from the stream into the view; with `AUTO REFRESH YES`, Redshift refreshes it automatically.
- Latency from stream to query is typically seconds, and large volumes are supported.
- Analysts query the view with normal SQL and can join it with warehouse tables.
Example: a dashboard queries `clickstream_mv` for the last 5 minutes of page views.
W: Streaming ingestion into a materialized view: Redshift reads the Kinesis stream directly and refreshes the view within seconds, so SQL queries see live events without S3 or ETL.
X: A=Federated queries to RDS: federated query reads live data from RDS or Aurora PostgreSQL and MySQL databases, not from Kinesis streams.
B=Serverless snapshot restore: restoring a snapshot recovers earlier data into a namespace; it does not ingest new streaming events.
D=Redshift Spectrum external tables: Spectrum queries files stored in S3, so it requires landing the data in S3 first, which the requirement rules out.
T: Kinesis or MSK straight into Redshift means streaming ingestion with a materialized view; Spectrum needs S3 and federated query needs a database.
V: Amazon Redshift, Amazon Kinesis Data Streams

@ DEA-C01 D1 T1.1 applied troubleshooting
S: Producers writing to an Amazon Kinesis Data Stream in provisioned mode intermittently receive ProvisionedThroughputExceededException errors during traffic spikes. Which combination of actions addresses this without redesigning the application? (Select TWO)
A: Add shards, or switch the stream to on-demand capacity mode
B: Decrease the stream's data retention period to 24 hours
C: Implement exponential backoff and retry in the producer
D: Disable server-side encryption with KMS on the stream
E: Omit the partition key so records spread across shards
K: A,C
G: ## Shard limits in provisioned mode
In provisioned mode, each Kinesis shard accepts up to **1 MB per second or 1,000 records per second** of writes. When producers exceed that for a shard, `PutRecord` or `PutRecords` return `ProvisionedThroughputExceededException`.
- Traffic spikes push total writes over the shard capacity.
- A skewed **partition key** can overload one "hot" shard even when the total is fine.
## Two standard fixes
- **More capacity**: split shards or use `UpdateShardCount`, or switch to **on-demand mode**, where Kinesis scales capacity automatically based on observed traffic.
- **Handle throttling in the producer**: retry failed records with exponential backoff (for example 100 ms, 200 ms, 400 ms, plus jitter). With `PutRecords`, retry only the records marked as failed. The Kinesis Producer Library (KPL) and AWS SDKs include retry logic.
W: A=More shards or on-demand mode: raises the write capacity of the stream so spikes fit within the per-shard limits, or lets Kinesis scale it automatically.
C=Exponential backoff and retry: brief throttling during spikes becomes a short delay instead of lost records, and backing off avoids hammering the throttled shard.
X: B=Shorter retention: retention controls how long data is kept for reading; it has no effect on how fast producers can write to a shard.
D=Disable KMS encryption: server-side encryption does not reduce the write limit of a shard; turning it off lowers security without solving throttling.
E=Omit the partition key: the partition key is required on each record because it decides the shard; the API rejects records without it.
T: Write throttling in Kinesis is fixed by adding capacity (more shards or on-demand) and retrying with backoff, not by changing retention or encryption.
V: Amazon Kinesis Data Streams

@ DEA-C01 D3 T3.3 applied use-case
S: A Glue job fails intermittently, and engineers need its logs and metrics to diagnose the problem. Where should they look?
A: Route 53 Resolver query logs for the account's VPC networks
B: Amazon CloudWatch log groups and the Glue metrics namespace
C: The AWS Billing console's charges for the job this month
D: The IAM credential report covering the job's IAM users
K: B
G: ## Where AWS Glue writes diagnostic data
Glue jobs send their output to Amazon CloudWatch.
- **CloudWatch Logs**: driver and executor output goes to log groups such as `/aws-glue/jobs/output` and `/aws-glue/jobs/error`; with continuous logging enabled, near-real-time logs appear in `/aws-glue/jobs/logs-v2`.
- **CloudWatch metrics**: with job metrics enabled, Glue publishes Spark metrics (memory, elapsed time, bytes read, records processed) in the `Glue` namespace; observability metrics add views of skew and worker utilization.
- **Job run details**: the Glue console shows each run's state, error message and duration, and the Spark UI can show stages and tasks.
## Example
An intermittent failure is traced by comparing the error log of a failed run with a successful one and checking the memory metric: if driver memory spikes only on large input days, the cause is data volume, not the code.
W: Amazon CloudWatch: Glue writes driver and executor output to CloudWatch Logs and publishes job metrics in the `Glue` namespace, which hold the error messages, stack traces and resource trends needed to find why only some runs fail.
X: A=Route 53 Resolver query logs: they record DNS queries; they contain nothing about Spark stages, errors or memory inside a Glue job.
C=Billing console: it shows charges by service; cost can confirm a job ran longer, but it has no error messages or per-run diagnostics.
D=IAM credential report: it lists IAM users with the status of their passwords, access keys and MFA; it does not record job executions or failures.
T: Diagnose Glue runs with CloudWatch Logs and job metrics; billing, DNS and credential reports never contain job errors.
V: AWS Glue, Amazon CloudWatch

@ DEA-C01 D2 T2.4 advanced use-case
S: An analytics team wants Aurora transactional data available in Amazon Redshift in near real time, without building or operating an extraction and load pipeline. Which feature fits?
A: Aurora zero-ETL integration with Amazon Redshift
B: Manual SQL dumps from Aurora imported into Redshift each morning
C: Nightly CSV exports from Aurora to S3, loaded into Redshift with COPY
D: A Lambda function polling Aurora each minute and writing rows to Redshift
K: A
G: ## What zero-ETL integration means
Traditionally, getting OLTP data into a warehouse needs a pipeline: extract from the database, stage in S3, transform and load, then schedule and monitor it. Every step adds delay and operational work.
## Aurora zero-ETL integration with Amazon Redshift
You create an integration between an Aurora cluster (MySQL-compatible or PostgreSQL-compatible) and a Redshift Serverless workgroup or RA3 cluster. AWS then:
- seeds Redshift with an initial copy of the selected data,
- continuously replicates inserts, updates and deletes from Aurora's change log, typically within seconds,
- runs with minimal impact on the Aurora workload and no extraction jobs to build.
In Redshift you create a database from the integration and query the replicated tables directly, joining them with other warehouse data. Data filters can limit which databases or tables are replicated.
W: Zero-ETL integration: it delivers Aurora changes to Redshift in near real time with no pipeline to build or operate, which is exactly the stated requirement.
X: B=Manual SQL dumps: data is at least a day old and depends on a person doing the import, so it is neither near real time nor free of pipeline work.
C=Nightly CSV exports with COPY: this is a classic batch ETL pipeline with up to a day of latency, and it must be built, scheduled and maintained.
D=Lambda polling each minute: custom polling adds load on Aurora, misses deletes unless specially designed, and is a hand-built pipeline to maintain.
T: Near-real-time Aurora-to-Redshift analytics without pipelines is zero-ETL integration; dumps, nightly COPY loads and polling functions are the ETL it replaces.
V: Amazon Aurora, Amazon Redshift
