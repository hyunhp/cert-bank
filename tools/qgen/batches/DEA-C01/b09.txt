@ DEA-C01 D2 T2.1 advanced use-case
S: An online retailer keeps 40 million product items in an Amazon DynamoDB table that the catalog service updates all day. The product team now needs a storefront search box with relevance ranking, typo-tolerant matching and faceted filters on brand and price, and new or changed products must become searchable within seconds. The data platform team has no capacity to write or operate custom replication code. Which solution meets these requirements with the LEAST operational overhead?
A: Create an Amazon OpenSearch Ingestion pipeline with the DynamoDB table as its source, loading an initial export and then streaming ongoing changes into an OpenSearch Service domain
B: Enable DynamoDB Streams on the table and write an AWS Lambda function that transforms each change record and indexes it into an OpenSearch Service domain through the bulk API
C: Add global secondary indexes on brand and price, and implement the search box with Query calls that apply begins_with conditions on a lowercase copy of the product name
D: Set up a zero-ETL integration from DynamoDB to Amazon Redshift and serve the search box with SQL queries that use ILIKE predicates on the replicated product table
K: A
G: ## Key-value stores do not do search
DynamoDB finds items by key. It can match a partition key exactly and a sort key by range or prefix, but it has no notion of relevance scores, fuzzy (typo-tolerant) matching or facet counts. Those are features of a search engine with an inverted index, such as Amazon OpenSearch Service.
## Getting the data there without code
OpenSearch Ingestion is a managed pipeline service. Its DynamoDB source works in two phases:
- **Initial load**: DynamoDB uses point-in-time recovery (PITR) to export the table to S3, and the pipeline indexes that snapshot.
- **Change data capture**: the pipeline then reads DynamoDB Streams (view type `NEW_IMAGE`, or `NEW_AND_OLD_IMAGES`) and applies every insert, update and delete to the index within seconds.
The pipeline scales in OpenSearch Compute Units (OCUs) by itself; there is no consumer code to write, deploy or retry. A blueprint for DynamoDB exists, so the setup is configuration only. The table and the pipeline must be in the same account and Region.
W: OpenSearch Ingestion from DynamoDB: a managed pipeline handles both the initial export and the ongoing stream, and OpenSearch provides relevance, fuzzy matching and aggregations for facets, so every requirement is met without custom replication code.
X: B=Streams plus a Lambda indexer: this works and is a classic pattern, but it is exactly the custom replication code (transformation, batching, retries, error handling) that the team has no capacity to build and run.
C=GSIs with begins_with: GSIs give new key-based access paths, but a prefix match on a name is not relevance ranking, it cannot tolerate typos, and DynamoDB has no facet counts.
D=Zero-ETL into Redshift: the replication itself needs no code, but a data warehouse with ILIKE pattern matching gives no relevance scoring or typo tolerance and is not built to serve a storefront search box.
T: Full-text relevance, fuzzy matching and facets need OpenSearch; feed it from DynamoDB with an OpenSearch Ingestion pipeline instead of custom stream consumers.
V: Amazon DynamoDB, Amazon OpenSearch Service, Amazon OpenSearch Ingestion

@ DEA-C01 D2 T2.1 advanced tradeoff
S: A security analytics team indexes about 2 TB of application logs per day into Amazon OpenSearch Service. Analysts run interactive searches and dashboards mostly over the last 7 days, but investigators must also search any log from the past 12 months with the same OpenSearch queries and get answers in seconds. Logs are never modified after they are written, and the cost of hot data nodes keeps growing. Which approach is MOST cost-effective?
A: Keep all 12 months of indexes on hot data nodes but move the domain to larger storage-optimized instance types so that the cost per terabyte stored goes down
B: Add an Index State Management policy that migrates indexes older than 7 days to UltraWarm storage, which is backed by Amazon S3 and stays searchable read-only
C: Delete indexes older than 7 days from the domain and keep the raw log files in S3 Glacier Flexible Retrieval so they can be restored when an investigation starts
D: Export indexes older than 7 days to Amazon S3 as JSON files and have investigators search them with Amazon Athena SQL queries instead of OpenSearch queries
K: B
G: ## Storage tiers in OpenSearch Service
- **Hot** storage lives on the data nodes' local disks (EBS or instance storage). It is the fastest tier and the most expensive per GB because compute and storage scale together.
- **UltraWarm** keeps index data in Amazon S3 and uses dedicated warm nodes with a local cache to run queries. It costs much less per GB than hot storage, and indexes stay fully searchable with the same query DSL and Dashboards.
- **Cold** storage is cheaper again, but an index must be attached (moved back to warm) before it can be searched.
## Why logs fit UltraWarm
Indexes in UltraWarm are read-only: you can query and delete them but not update documents. Logs are immutable after ingestion, so this costs nothing. Index State Management (ISM) automates the move with the `warm_migration` action, for example after an index is 7 days old.
W: UltraWarm with ISM: data older than 7 days moves to S3-backed warm storage, which is far cheaper than hot nodes while investigators keep searching it with the same OpenSearch queries in seconds; immutable logs suit the read-only warm tier.
X: A=Larger hot nodes: storage-optimized instances lower the price per TB a little, but 12 months of logs on hot nodes is still the most expensive way to keep rarely searched data, which is the cost problem itself.
C=Glacier Flexible Retrieval: archive storage is cheap, but a standard restore takes hours and the data must then be re-indexed, so investigators cannot search old logs in seconds.
D=Athena over JSON exports: Athena can query the exports cheaply, but investigators must switch to a different engine and SQL instead of the same OpenSearch queries the requirement names.
T: Rarely searched but still searchable OpenSearch data belongs in UltraWarm (S3-backed, read-only), moved there automatically by an ISM policy.
V: Amazon OpenSearch Service

@ DEA-C01 D2 T2.1 advanced use-case
S: A company runs nightly and intraday ETL on an Amazon Redshift RA3 provisioned cluster. Marketing dashboards on the same cluster slow down whenever ETL runs, and finance now wants marketing's query compute billed separately from the ETL cluster. The dashboards must always show the data committed by the latest ETL run, and the platform team refuses to copy tables or maintain extra pipelines. Which solution meets these requirements?
A: Enable concurrency scaling for the dashboards' WLM queue on the ETL cluster so that transient scaling clusters absorb the bursts of marketing queries during ETL runs
B: Restore the latest automated snapshot of the ETL cluster into a separate provisioned cluster every hour and point the marketing dashboards at that restored cluster
C: Create a datashare on the ETL cluster and consume it from a separate Amazon Redshift Serverless workgroup that the marketing dashboards connect to
D: UNLOAD the reporting tables to Amazon S3 after each ETL run and let the dashboards query them through Redshift Spectrum from a second, smaller cluster
K: C
G: ## What Redshift data sharing does
A **producer** (provisioned RA3 cluster or Serverless workgroup) creates a datashare that lists schemas, tables or views. A **consumer** cluster or workgroup, in the same or another account or Region, creates a database from that datashare and queries the objects directly.
- No data is copied or moved: the consumer reads the producer's live, transactionally consistent data, so it sees every committed ETL change at once.
- The consumer runs queries on **its own compute**, so heavy ETL on the producer no longer competes with dashboard queries.
- Because each workload has its own cluster or workgroup, its cost appears separately, which AWS describes as workload isolation and chargeback.
## Why Serverless suits the consumer
Dashboards are spiky. A Redshift Serverless workgroup bills for RPU-hours only while queries run, and it can read datashares from provisioned producers.
W: Datashare to a Serverless consumer: the marketing workgroup reads the ETL cluster's live data without copies or pipelines, runs on separate compute that ETL cannot slow down, and its cost is billed to that workgroup.
X: A=Concurrency scaling: it adds transient capacity for queued queries, but the usage is charged to the ETL cluster itself and the main cluster's resources are still shared, so finance gets no separate bill for marketing.
B=Hourly snapshot restore: a separate cluster isolates compute, but its data is up to an hour old and the restore cycle is an extra process to run, which breaks both the freshness and the no-pipeline constraint.
D=UNLOAD plus Spectrum: this copies data to S3 after every run and adds a pipeline to maintain, which the platform team explicitly refuses.
T: Separate compute and cost on live Redshift data without copies = data sharing from the producer to a consumer cluster or Serverless workgroup.
V: Amazon Redshift, Amazon Redshift Serverless

@ DEA-C01 D2 T2.1 advanced use-case
S: A fitness app shows each user's weekly totals and personal records on its home screen. An Amazon Redshift job recomputes these summaries every 10 minutes from 3 billion workout rows. At peak, the app sends 60,000 requests per second, each reading one user's summary, and every read must return in under 10 milliseconds. The app team wants a fully managed store with no servers or nodes to patch. Where should the summaries be served from?
A: Point the app directly at the Redshift cluster and create a materialized view with auto refresh, so that each app request reads a single precomputed row
B: Unload the summaries to Amazon S3 as Parquet after each run and have the app read them through Amazon Athena queries filtered on the user ID column
C: Load the summaries into a self-managed Redis cluster on Amazon EC2 instances in an Auto Scaling group and have the app read each user key with GET
D: Write each user's computed summary as one item keyed by user ID into an Amazon DynamoDB table, and have the app read it with GetItem calls
K: D
G: ## Analytics stores versus serving stores
A data warehouse is built for few, large, scan-heavy queries. Every Redshift query goes through the leader node, query planning and the WLM queues, so tens of thousands of point lookups per second at single-digit millisecond latency are not what it is designed for. Athena is similar: each query is a job that starts, plans and scans, typically taking a second or more.
## The serving pattern
The common design is to compute aggregates in the warehouse and **publish** the results to an operational store that is built for key lookups:
- DynamoDB serves `GetItem` by primary key in single-digit milliseconds at virtually any request rate.
- It is serverless: no instances, patching or capacity planning (on-demand mode scales with traffic).
- The Redshift job (or a small export step) overwrites one item per user every 10 minutes.
W: DynamoDB serving table: precomputed summaries keyed by user ID are read with GetItem in single-digit milliseconds at 60,000 requests per second, and DynamoDB is fully managed with no servers to patch.
X: A=Materialized view in Redshift: the view makes each query cheaper, but every request is still a warehouse query with planning and queueing, so 60,000 lookups per second under 10 ms is not realistic.
B=Athena over Parquet: each Athena query is a separate job that typically takes seconds, so it cannot meet a 10 ms read latency for an app home screen.
C=Self-managed Redis on EC2: Redis would be fast enough, but EC2 instances are servers the team must patch and operate, which the fully managed requirement excludes.
T: Compute aggregates in the warehouse, then serve them from a key-value store such as DynamoDB when an app needs millisecond lookups at high request rates.
V: Amazon DynamoDB, Amazon Redshift

@ DEA-C01 D2 T2.2 advanced troubleshooting
S: Clickstream Parquet files land under s3://clicks/dt=YYYY-MM-DD/. The team enabled Athena partition projection on the Glue Data Catalog table and then removed the nightly crawler to save cost. Athena queries for new dates work, but the finance team's Amazon Redshift Spectrum queries on the same external table return no rows for any date after the crawler was removed. Both engines must keep sharing the same table definition. What should the team do?
A: Create a second Redshift external table without partition columns over s3://clicks/ so that the Spectrum queries scan every file and filter on dt in the query
B: Keep registering each new dt partition in the Data Catalog, for example with a daily ALTER TABLE ADD PARTITION, because Spectrum ignores projection
C: Replace the external table for finance with a local Redshift table that a nightly COPY loads from s3://clicks/, so that Spectrum is no longer involved
D: Remove the projection properties and set the table's location to s3://clicks/ with recursive listing so both engines discover new folders on their own
K: B
G: ## Projection is an Athena-only shortcut
With partition projection, the table properties in the Glue Data Catalog describe the partition pattern (for example a `date` type for `dt` with a range). Athena computes which partitions exist at query time instead of calling `GetPartitions`, and while projection is enabled Athena ignores the partitions registered in the catalog.
The Athena documentation is explicit: projection is usable only when the table is queried through Athena. Redshift Spectrum, Amazon EMR and Athena for Spark read the **standard partition metadata** in the catalog.
## What went wrong here
Removing the crawler stopped new partitions from being registered. Athena did not notice (it projects them), but Spectrum only sees partitions that exist in the catalog, so new dates look empty.
The fix is to keep the catalog's partition list current for the other engines, for example a daily `ALTER TABLE ... ADD PARTITION`, a scheduled `MSCK REPAIR TABLE`, the Glue `BatchCreatePartition` API, or the crawler. Athena keeps using projection for speed.
W: Keep registering partitions: Spectrum reads only catalog partitions, so adding each new dt partition (by DDL, API or crawler) restores the finance queries while Athena keeps projecting, and both engines share one table.
X: A=Unpartitioned second table: Spectrum would then scan every file for every query, and finance would use a different table definition, which breaks the shared-definition requirement.
C=Local table loaded by COPY: this copies the data into Redshift and gives finance a separate table, so the two engines no longer share one definition.
D=Recursive location without partitions: Hive-style tables do not discover new partitions by themselves, and dropping the partition columns would remove pruning, making every query scan the whole history.
T: Partition projection helps only Athena; Spectrum, EMR and Glue Spark still need partitions registered in the Data Catalog.
V: Amazon Athena, Amazon Redshift Spectrum, AWS Glue Data Catalog

@ DEA-C01 D2 T2.2 advanced troubleshooting
S: An AWS Glue crawler must catalog 300 tables in an Amazon RDS for PostgreSQL instance in private subnets. The crawler uses a Glue JDBC connection placed in the database's subnet with the database's security group, whose only inbound rule allows port 5432 from the application tier's security group. Every crawler run fails with a connection timeout. Security policy forbids rules that open the database to any CIDR range. Which change resolves the failure?
A: Add an inbound rule to the database security group that allows port 5432 from the VPC CIDR range, so that any Glue network interface in the subnet can connect
B: Move the database to a public subnet and enable public accessibility so that the crawler can reach the endpoint without using a VPC-based Glue connection
C: Store the database credentials in AWS Secrets Manager and reference that secret from the Glue connection instead of typing the user name and password in
D: Add a self-referencing inbound rule for all TCP ports to the database security group, so Glue network interfaces in that group can reach each other
K: D
G: ## How Glue reaches a database in a VPC
When a crawler or job uses a JDBC connection, Glue creates elastic network interfaces in the connection's subnet and attaches the connection's security group to them. Traffic between those interfaces and the database is then controlled by that security group like any other traffic in the VPC.
## The self-referencing rule
The Glue documentation requires a security group with a **self-referencing inbound rule for all TCP ports**: the source of the rule is the security group itself. This lets every resource that carries the group, the Glue interfaces and the database, talk to each other, without opening anything to an IP range.
Here the only rule allows the application tier's group, so Glue's interfaces, which carry the database's group, are not allowed in and the connection times out.
W: Self-referencing rule: with the group as its own source, Glue's network interfaces and the database can communicate on all TCP ports, which fixes the timeout without any CIDR-based rule.
X: A=VPC CIDR rule: it would probably let Glue connect, but it is a rule that opens the database to a CIDR range, which the security policy forbids.
B=Public subnet: exposing the database endpoint publicly fixes reachability by weakening security, the opposite of the policy, and the crawler would still need network access rules.
C=Secrets Manager: storing credentials in a secret is good practice, but a timeout is a network problem; the crawler never reaches the stage where it sends a password.
T: Glue JDBC connections need a security group with a self-referencing all-TCP inbound rule; timeouts point to network rules, not credentials.
V: AWS Glue, Amazon RDS, Amazon VPC

@ DEA-C01 D2 T2.2 advanced troubleshooting
S: A Spark job owned by another team writes daily Parquet output to s3://lake/orders/dt=.../ and also leaves a run-manifest JSON file and a quality-report CSV file in every dt folder. A Glue crawler over s3://lake/orders/ now produces mixed schemas and extra tables from those files, which breaks Athena queries. The Spark job cannot be changed this quarter. Which fix makes the catalog correct with the LEAST effort?
A: Ask the owning team to stop writing the manifest and report files into the dt folders and to put them under a separate prefix outside s3://lake/orders/
B: Add exclude patterns such as **/run-manifest*.json and **/quality-report*.csv to the crawler's S3 data source so the crawler skips those files
C: Replace the crawler with a Lambda function that S3 events trigger, which calls the Glue CreatePartition API for each new dt folder that the job writes
D: Run a nightly S3 Batch Operations job that deletes the manifest and report files from each dt folder before the crawler's scheduled run begins
K: B
G: ## Include paths and exclude patterns
A crawler's S3 data source has an **include path** (for example `s3://lake/orders/`) and optional **exclude patterns**: Unix-style glob patterns evaluated relative to the include path.
- `*` matches characters within one folder level; `**` crosses folder boundaries.
- `**.csv` excludes every CSV object below the include path; `**/run-manifest*.json` excludes the manifests in any dt folder.
- The patterns are stored as a property of the tables the crawler creates, so Glue readers that use the catalog also skip the excluded files.
## Why it matters
A crawler infers a schema from every file it reads. JSON and CSV files mixed with Parquet in the same folders make it create extra tables or merge incompatible schemas, which then breaks Athena.
W: Exclude patterns: two glob patterns make the crawler ignore the non-data files, so the table is built only from Parquet, with a configuration change on the crawler and nothing else.
X: A=Change the producer: this is the cleanest long-term fix, but the job cannot be changed this quarter, so it does not solve the problem now.
C=Event-driven CreatePartition: it avoids schema inference, but it means writing and running new code and maintaining the table schema by hand, which is far more effort than a crawler setting.
D=Nightly delete job: deleting files that another team writes may break their process, and a scheduled Batch Operations job is extra machinery compared with telling the crawler what to skip.
T: When non-data files pollute a crawled S3 path, use crawler exclude patterns (glob, ** crosses folders) instead of changing the data or the producer.
V: AWS Glue, Amazon Athena

@ DEA-C01 D2 T2.2 advanced troubleshooting
S: A daily AWS Glue crawler catalogs JSON exports under s3://exports/events/dt=.../, about 900 partitions so far, and typed the amount column as string. Analysts need it as double, so an engineer changed the table definition, and Athena queries now fail with HIVE_PARTITION_SCHEMA_MISMATCH. The engineer's column type must survive future crawler runs, existing and future partitions must follow the table, and nobody will write per-partition DDL. Which TWO actions should the engineer take? (Select TWO)
A: Turn on the crawler option to update all new and existing partitions with metadata from the table, so every partition inherits the table's schema on the next run
B: Set the crawler's schema change behavior for tables to add new columns only, so later runs keep the engineer's double type instead of reverting amount to string
C: Run ALTER TABLE DROP PARTITION and ADD PARTITION for each of the 900 existing partitions, so that every recreated partition takes the table's current schema
D: Change the table's SerDe to the OpenX JSON SerDe with ignore.malformed.json set to true, so that rows whose amount type differs are skipped during queries
E: Delete the table and rerun the crawler with the single schema for each S3 path option, so that it rebuilds the table and partitions with one consistent schema
K: A,B
G: ## Table schema versus partition schemas
In the Glue Data Catalog every partition stores its own column list, not only the table. A crawler writes the schema it infers into each partition it adds, and editing the table later does not touch the partitions. Athena compares the two at the start of a query:
- For Parquet and ORC it matches columns by name, so mismatches rarely matter.
- For CSV, JSON and Avro it checks by position and type, and a partition that declares `amount` as `string` while the table says `double` fails with `HIVE_PARTITION_SCHEMA_MISMATCH`.
The usual manual workaround is to drop and re-add the bad partitions, which does not scale to hundreds of them.
## Two crawler settings fix it for good
- **Update all new and existing partitions with metadata from the table** (`"Partitions": {"AddOrUpdateBehavior": "InheritFromTable"}`): partition schemas inherit from the table, for the partitions already there and for new ones.
- **Table schema change behavior**: by default a crawler updates the table to match what it infers, which would turn `amount` back into `string`. **Add new columns only** (`MergeNewColumns`) or **Ignore the change** keeps existing column types.
Both are needed: inheriting from a table that the crawler keeps reverting would just copy the wrong type into every partition.
W: A=Inherit partitions from the table: the next crawler run rewrites the 900 existing partition schemas and every new partition from the table definition, which removes the mismatch without any DDL.
B=Add new columns only: the crawler stops overwriting existing column types in the table, so the engineer's double type survives every later run while new attributes are still added.
X: C=Drop and re-add every partition: it fixes today's partitions but is exactly the per-partition DDL the team will not write, and the crawler would still revert the type and add mismatched partitions.
D=OpenX SerDe ignoring malformed JSON: that setting skips unparseable records, but Athena's schema check between table and partitions fails before any row is read, so the error remains.
E=Delete and recrawl: the crawler infers the column types from the files again, so the engineer's manual double type is lost and the same string type returns.
T: Partition schemas do not follow table edits; set the crawler to inherit partitions from the table and to add new columns only so a manual type change sticks.
V: AWS Glue, Amazon Athena

@ DEA-C01 D2 T2.3 advanced comparison
S: A media company is moving three archives out of S3 Standard. Dataset 1: dashboards read random files about once a quarter and need millisecond access. Dataset 2: the legal team asks for whole folders a few times a year and needs them within 5 hours. Dataset 3: regulators may ask for it once in 10 years and allow 48 hours. Each dataset must use the lowest-cost class that meets its window. Which THREE choices should the team make? (Select THREE)
A: Dataset 1 to S3 Glacier Instant Retrieval with a lifecycle transition, because it serves GET requests in milliseconds at a lower storage price
B: Dataset 1 to S3 Glacier Flexible Retrieval with Expedited retrievals, because urgent requests for small objects usually finish in 1 to 5 minutes
C: Dataset 2 to S3 Glacier Flexible Retrieval, with Standard retrievals that typically finish within 3 to 5 hours when the legal team asks
D: Dataset 2 to S3 Glacier Deep Archive, with Standard retrievals through S3 Batch Operations that typically finish within 9 to 12 hours
E: Dataset 3 to S3 Glacier Deep Archive, with Bulk retrievals that typically finish within 48 hours at the lowest retrieval price available
F: Dataset 3 to S3 Glacier Flexible Retrieval, with free Bulk retrievals that typically finish within 5 to 12 hours when regulators ask
K: A,C,E
G: ## Three Glacier classes, three retrieval windows
- **S3 Glacier Instant Retrieval**: objects are read with a normal `GET` in milliseconds. Storage is cheaper than Standard-IA for data read about once a quarter, with a per-GB retrieval fee and a 90-day minimum storage duration.
- **S3 Glacier Flexible Retrieval**: objects must be restored first with `RestoreObject`. Expedited takes 1-5 minutes, Standard 3-5 hours, Bulk 5-12 hours (Bulk is free). 90-day minimum.
- **S3 Glacier Deep Archive**: the cheapest storage. Standard restores finish within 12 hours (9-12 hours with Batch Operations), Bulk within 48 hours. Expedited is not available. 180-day minimum.
## Matching window to class
Pick the cheapest storage whose retrieval time still meets the window: milliseconds rules out anything that needs a restore, 5 hours rules out Deep Archive, and 48 hours allows Deep Archive.
W: A=Glacier Instant Retrieval: the only Glacier class read with a direct GET in milliseconds, and cheaper to store than Standard or Standard-IA for quarterly access.
C=Glacier Flexible Retrieval: Standard retrievals in 3-5 hours fit the 5-hour window, and its storage is cheaper than Instant Retrieval.
E=Glacier Deep Archive: the lowest storage price of all, and Bulk retrievals within 48 hours fit the regulators' window.
X: B=Flexible with Expedited: even 1-5 minutes is a restore, not millisecond access, so the dashboards' requirement fails.
D=Deep Archive for legal: 9-12 hours, even with Batch Operations, is longer than the 5-hour window.
F=Flexible for the 10-year archive: it would meet 48 hours easily, but its storage costs several times more than Deep Archive, so it is not the lowest-cost class that fits.
T: Milliseconds → Glacier Instant Retrieval; hours (3-5) → Glacier Flexible Retrieval; up to 12 or 48 hours → Glacier Deep Archive.
V: Amazon S3

@ DEA-C01 D2 T2.3 advanced troubleshooting

E: Allow s3:GetObject on arn:aws:s3:::raw-zone/*, so the job can read the sales prefix along with any new prefixes added later on
F: Allow s3:* on arn:aws:s3:::curated-zone/sales/*, so the job can write, overwrite, tag and delete its own output files freely
K: A,B,C
G: ## Bucket-level versus object-level actions
S3 actions apply to different resource types, and the ARN in a policy must match:
- **Bucket actions** such as `s3:ListBucket` apply to the bucket ARN, `arn:aws:s3:::raw-zone`. To limit what can be listed, add a condition on the `s3:prefix` key, for example `StringLike` `sales/*`.
- **Object actions** such as `s3:GetObject` and `s3:PutObject` apply to object ARNs, for example `arn:aws:s3:::raw-zone/sales/*`.
A statement that pairs `s3:ListBucket` with an object ARN never matches any request, so listing silently stays denied.
## Least privilege
Grant only the actions the job performs, only on the prefixes it uses. Wildcards on actions (`s3:*`) or on the whole bucket (`raw-zone/*`) reach other teams' data or allow deletes the job does not need.
W: A=ListBucket on the bucket ARN with an s3:prefix condition: lets the job enumerate the sales input files and nothing else in the bucket.
B=GetObject on raw-zone/sales/*: allows reading exactly the input objects.
C=PutObject on curated-zone/sales/*: allows writing output only under the sales prefix of the curated bucket.
X: D=ListBucket on an object ARN: ListBucket is a bucket-level action, so this resource never matches and the job could not list its input at all.
E=GetObject on the whole raw bucket: it works, but it also exposes other teams' prefixes, breaking least privilege.
F=s3:* on the output prefix: it adds delete, tagging and ACL actions the job does not need.
T: ListBucket goes on the bucket ARN (narrowed with s3:prefix); GetObject and PutObject go on object ARNs for the exact prefix.

@ DEA-C01 D4 T4.2 advanced use-case
S: A governance team uses Lake Formation tag-based access control and grants analysts SELECT on resources tagged domain=finance. Data engineers create about 20 new tables per week in the finance database, and analysts wait days for a data steward to tag each one. New tables never contain personal data. They must be queryable by analysts as soon as they are created, with no per-table steps, while personal data columns in existing finance tables stay hidden. Which approach fits?
A: Tag the finance database with domain=finance and pii=false for inheritance, override existing personal columns to pii=true, and grant on both tags

G: ## How LF-tags reach new tables
LF-tags can be assigned to databases, tables and columns. A table **inherits** the tags of its database, and a column inherits the tags of its table. A child can override an inherited value by assigning a new value for the same key.
## Building the grant
A tag-based grant uses an expression, for example `domain=finance AND pii=false`. Lake Formation evaluates it on every resource, including tables created later:

D=Hybrid access mode: IAM-based access to new tables gives analysts whole tables with no column restrictions, so personal data would not stay hidden.

@ DEA-C01 D4 T4.2 advanced use-case
S: Glue jobs and EMR clusters in a VPC read a sensitive S3 bucket through an S3 gateway endpoint. After a leaked access key was used from the internet, security requires that the bucket reject every request that does not arrive through that endpoint, including requests from administrators whose policies allow s3:*. The existing IAM roles and their policies must not be changed. Which control meets this requirement?
A: A VPC endpoint policy on the gateway endpoint that allows only the Glue and EMR roles to read objects from the sensitive bucket through that endpoint

G: ## Where to enforce "only through this endpoint"
- An **endpoint policy** controls what can be done **through** the endpoint. It cannot affect requests that do not use the endpoint, such as calls from the internet.
- A **bucket policy** is evaluated on every request to the bucket, whatever path it takes. An explicit `Deny` there overrides any `Allow` in identity policies, including `s3:*` for administrators.

Requests through a VPC endpoint carry the endpoint ID in `aws:SourceVpce`. A statement such as `Effect: Deny`, `Condition: StringNotEquals aws:SourceVpce vpce-...` rejects everything else. W: Deny unless aws:SourceVpce matches: the bucket policy applies to every request, the explicit deny overrides administrators' s3:* permissions, and no IAM role is touched.
X: A=Endpoint policy: it limits traffic through the endpoint only; a leaked key used from the internet never passes through it, so the bucket would still accept that request.
B=aws:SourceIp with VPC CIDRs: requests through a gateway endpoint do not present those private addresses in aws:SourceIp, so this condition does not identify the endpoint path and would block the jobs too.
D=Permissions boundaries: they would require changing every role, which is not allowed, and they do not cover other principals such as users with leaked keys.
T: To force S3 access through a VPC endpoint, deny in the bucket policy when aws:SourceVpce is not the endpoint ID.

@ DEA-C01 D4 T4.4 advanced use-case
S: A payroll bucket is written by analysts, pipelines and a nightly re-encryption job whose IAM role rewrites every object in place, about 40 million calls a night, and it is read far more often. Auditors need a CloudTrail record of every write and delete on that bucket by any principal except the re-encryption role. A trail already delivers management events to a log bucket, and CloudTrail data event charges must stay as low as possible. Which configuration meets these requirements?

G: ## Data events are opt-in and billed per event
A trail records management events (bucket configuration, IAM changes) by default. Object-level calls such as `PutObject`, `CopyObject`, `DeleteObject` and `GetObject` are **data events**: they are logged only when an event selector asks for them, and every delivered data event is charged. - `eventCategory = Data` and `resources.type = AWS::S3::Object` (required).

- `readOnly = false` keeps only write events (`true` keeps only reads; leaving the field out logs both).

Basic event selectors can choose buckets and read/write type, but they cannot filter on the caller identity.

X: B=Basic selector plus a query filter: basic selectors cannot exclude an identity, so the job's 40 million nightly writes are still logged and charged before any query filters them out.
C=Advanced selectors without readOnly: the identity exclusion works, but without readOnly false the trail also records and charges every read, which on this bucket is the larger share of calls.
D=Server access logs: delivery is best effort, so a log record can occasionally be missing, and the requirement is a CloudTrail record of every write; CloudTrail data events are the complete audit source.
T: Cut CloudTrail data event cost at collection time with advanced event selectors: resources.ARN for the bucket, readOnly for reads or writes, userIdentity.arn to exclude noisy roles.
