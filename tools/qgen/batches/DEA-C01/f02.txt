@ DEA-C01 D1 T1.2 applied use-case
S: Analysts frequently filter a large S3-based sales dataset in Athena by both year/month and country. Which S3 partitioning strategy would most improve query performance and reduce cost for these access patterns?
A: Partition by country, keeping year and month as ordinary data columns
B: Partition by year, month, and country in the S3 key structure
C: Partition by a randomly generated UUID assigned to each file
D: Store the data under a single unpartitioned prefix in the bucket
K: B
G: ## Partitioning data in S3 for Athena
A partitioned table stores data under prefixes named after column values, commonly in Hive style:
`s3://sales/year=2026/month=09/country=KR/part-0001.parquet`
Each partition value becomes a column Athena can filter on. When a query says `WHERE year = '2026' AND month = '09' AND country = 'KR'`, Athena reads only that prefix and skips everything else (**partition pruning**), which lowers both run time and bytes scanned.
## Choosing partition keys
- Use columns that appear in most `WHERE` clauses.
- Keep the number of values reasonable: too many tiny partitions create many small files and slow down planning.
- For many partitions, **partition projection** lets Athena compute partition locations from the key pattern instead of looking them up in the catalog.
W: Partition by year, month and country: these match exactly how analysts filter, so Athena prunes whole prefixes on all three predicates and reads only the relevant slice of data.
X: A=Country only, date as data columns: the country filter can prune prefixes, but every query still reads all months of that country, because year and month are ordinary columns that Athena must scan to evaluate the date filter.
C=Random UUID partitions: a random value never appears in analyst filters, so every query must scan every partition, and the huge number of partitions adds planning overhead.
D=Single unpartitioned prefix: with no partitions, every query scans the full dataset regardless of the date or country filter.
T: Partition on the columns queries actually filter by (here year, month and country) so Athena can skip everything outside the requested slice.
V: Amazon Athena, Amazon S3

@ DEA-C01 D2 T2.1 applied comparison
S: A team already has Apache Kafka producers and consumers using native Kafka client libraries and protocol. They want to move ingestion to a managed AWS service while keeping full compatibility with existing Kafka APIs and clients. Which service should they choose?
A: Amazon SQS
B: Amazon Kinesis Data Streams
C: Amazon Data Firehose
D: Amazon MSK
K: D
G: ## API compatibility when migrating streaming
Kafka producers and consumers use Kafka client libraries and the Kafka wire protocol: they connect to brokers, write to topics and partitions, and track progress with consumer group offsets.
**Amazon MSK** runs real Apache Kafka brokers, managed by AWS (provisioning, patching, broker replacement, storage). Existing clients only need new bootstrap broker addresses and security settings; the code stays the same. **MSK Serverless** removes capacity planning as well.
## Why the other streaming services differ
- **Kinesis Data Streams** has its own API (`PutRecord`, `GetRecords`, shards, KCL).
- **Amazon Data Firehose** (formerly Kinesis Data Firehose) is a delivery service that loads data into destinations such as S3 or Redshift.
- **SQS** is a message queue with its own API and no topics or partitions.
## Example
A producer configured with `bootstrap.servers=b-1.mycluster...:9098` publishes to `orders` exactly as before, and consumer groups keep committing offsets.
W: Amazon MSK: Amazon Managed Streaming for Apache Kafka runs open-source Apache Kafka, so existing native Kafka clients, APIs and tooling work without code changes.
X: A=Amazon SQS: SQS uses its own queue API (`SendMessage`, `ReceiveMessage`) with no topics, partitions or consumer offsets, so all Kafka clients would need rewriting.
B=Kinesis Data Streams: it is a managed streaming service with a different API and concepts (shards, sequence numbers), so Kafka client libraries cannot talk to it directly.
C=Amazon Data Firehose: Firehose (formerly Kinesis Data Firehose) is a delivery pipeline into destinations such as S3, not a Kafka-compatible broker that native consumers can read from.
T: Keeping native Kafka clients unchanged requires real Kafka brokers, which is Amazon MSK; Kinesis and SQS use their own APIs.
V: Amazon MSK, Amazon Kinesis Data Streams, Amazon Data Firehose, Amazon SQS

@ DEA-C01 D2 T2.3 advanced troubleshooting
S: After enabling an S3 Lifecycle rule that transitions objects to S3 Glacier Deep Archive after 30 days, a team notices that many small objects, only a few KB each, now cost more in overhead than before the transition, despite the lower per-GB Glacier price. What is the most likely explanation?
A: Deep Archive bills small objects at a higher per-GB rate than it bills large objects
B: Per-object transition requests and archive metadata outweigh the per-GB savings
C: Objects below 128 KB are rejected by the rule, and each failed transition is billed
D: The transition expires the small objects, and the team pays for their re-upload
K: B
G: ## Per-object costs of Glacier classes
S3 Glacier Deep Archive has a very low per-GB price, but small objects bring fixed per-object costs:
- **Lifecycle transition requests** are charged per 1,000 objects, so transitioning millions of tiny objects costs real money.
- About **40 KB of metadata** is added per archived object: 8 KB billed at S3 Standard rates and 32 KB at the Deep Archive rate.
- A **minimum storage duration** of 180 days applies.
Example: a 4 KB object in Deep Archive is billed a transition fee plus about 36 KB at the Deep Archive rate and 8 KB at the Standard rate, for at least 180 days, so it can cost more than the 4 KB it used in Standard.
Because of this, Lifecycle configurations created or updated since September 2024 by default do not transition objects smaller than 128 KB; a rule can override that with an object size filter (`ObjectSizeGreaterThan`). Aggregating small files (for example with tar or a compaction job) before archiving avoids the overhead.
W: Per-object transition and metadata costs: transition fees plus the roughly 40 KB of metadata added to each archived object outweigh the lower per-GB price when objects are only a few KB.
X: A=Higher per-GB rate for small objects: Deep Archive has one per-GB storage rate for all object sizes. The extra cost comes from fixed per-object charges, not from a different rate.
C=Small objects rejected and billed: 128 KB is the default minimum size for lifecycle transitions; objects below it are simply skipped and stay in their current class without a charge, and a size filter on the rule can override the default. Skipped objects would cost the same as before, not more.
D=Transition expires the objects: a transition action never deletes objects; only an expiration action does, and nothing in the scenario re-uploads data.
T: Glacier classes charge per object as well as per GB; for many tiny files the per-object fees and metadata dominate, so filter them out or bundle them first.
V: Amazon S3

@ DEA-C01 D2 T2.4 applied use-case
S: When designing tables that will be governed by AWS Lake Formation for a multi-tenant data lake, which practice best supports enforcing column-level security for sensitive fields such as national ID numbers?
A: Keep sensitive and other columns in one table and filter them in the application layer
B: Encrypt the table with one shared KMS key and grant decrypt permission to each analyst
C: Move the sensitive data to a separate account and leave it out of the Data Catalog
D: Tag the sensitive columns with LF-Tags and grant access through data cells filters
K: D
G: ## Fine-grained access in AWS Lake Formation
Lake Formation governs tables registered in the AWS Glue Data Catalog. Instead of granting access to S3 paths, you grant permissions on databases, tables and columns, and integrated engines such as Athena, Redshift Spectrum, EMR and Glue enforce them.
- **Column-level security**: grant `SELECT` on a table while including or excluding specific columns, for example everything except `national_id`.
- **Data filters**: a data cells filter combines a column list with an optional row filter expression, such as `tenant_id = 'acme'`, and can be granted to a principal like a table.
- **LF-Tags**: tag sensitive columns (for example `classification=pii`) and grant access by tag, so new tables inherit the policy.
## Example
A multi-tenant lake stores all tenants in one `customers` table. Analysts of tenant A get a data filter with `tenant_id = 'A'` and all columns except `national_id`; the compliance team gets the full column set.
W: Classify columns and use Lake Formation grants: once sensitive columns are identified and tagged, column-level grants and data cells filters make the query engines themselves hide those columns (and rows) from principals who are not entitled to them.
X: A=Application-layer filtering: any user or tool that queries the table directly bypasses the application, so the national IDs are fully exposed; nothing in the data layer enforces the restriction.
B=One shared KMS key with decrypt for each analyst: encryption at rest protects against storage-level access, but granting decrypt to every user means everyone can read every column. Encryption is not an authorization boundary per column.
C=Separate account outside the catalog: data with no Data Catalog entry cannot be governed by Lake Formation at all, and moving whole datasets to another account does not provide per-column control within a table that users still need.
T: Column-level security in a Lake Formation data lake comes from column grants, data filters and LF-Tags enforced by the query engines, not from application logic or blanket encryption.
V: AWS Lake Formation, AWS Glue

@ DEA-C01 D4 T4.2 advanced tradeoff
S: A rapidly growing organization is deciding between a purely role-based access control (RBAC) model, where a new IAM role is created for every job function and resource combination, and an attribute-based access control (ABAC) model using tags for the same access requirements. What is a key operational tradeoff of choosing RBAC over ABAC as the number of teams and resources scales?
A: RBAC roles pick up access to newly tagged resources with no policy edits
B: ABAC needs a separate IAM role per tag value, so it creates more roles than RBAC
C: RBAC policies stay fixed as resources grow, while ABAC needs edits for each tag
D: Role and policy counts climb with each team and resource, unlike tag-matched rules
K: D
G: ## RBAC and ABAC at scale
- **Role-based access control (RBAC)**: permissions are attached to a role for a job function, and resources are named explicitly in its policies. If every team and resource combination needs its own role, the number of roles and policies grows roughly as teams multiplied by resources.
- **Attribute-based access control (ABAC)**: a smaller set of policies compares tags, for example allowing access when `aws:PrincipalTag/team` equals `aws:ResourceTag/team`. New teams and resources are covered by tagging them correctly.
## Example
With 20 teams and 50 data stores, a pure RBAC design may need hundreds of roles or constant policy edits as each new store appears. With ABAC, a new store tagged `team=finance` is immediately reachable by roles tagged `team=finance`, with no policy change.
ABAC still needs governance: consistent tag keys, control over who may change tags, and sometimes tag policies in AWS Organizations.
W: RBAC sprawls, ABAC scales with tags: the key operational tradeoff is that RBAC multiplies roles and policy updates as teams and resources grow, while ABAC keeps a few tag-matching policies stable and relies on tagging discipline.
X: A=RBAC picks up tagged resources: that describes ABAC. A pure RBAC policy names roles and resources explicitly and does nothing with tags unless you add tag conditions.
B=ABAC needs a role per tag value: ABAC uses a small set of roles and policies that compare tags such as `aws:PrincipalTag/team` with `aws:ResourceTag/team`; a new tag value needs no new role, which is why it creates fewer roles, not more.
C=RBAC policies stay fixed: this reverses the tradeoff. In RBAC each new resource or job function means creating or editing roles and policies, while ABAC policies stay unchanged when correctly tagged resources are added.
T: RBAC grows by adding roles and policy edits for every new team or resource; ABAC grows by tagging, which is why it scales better in fast-growing organizations.
V: IAM

@ DEA-C01 D1 T1.2 advanced use-case
S: A nightly Glue job reprocesses all files in an S3 prefix, even though only new files arrive each day. Runtime and cost keep growing. What should the data engineer enable?
A: AWS Glue job bookmarks that track the input files earlier runs processed
B: An AWS Glue crawler that runs before each job to refresh the table partitions
C: S3 Versioning on the input bucket to keep track of each object's versions
D: Additional DPUs for the job so each run finishes the full reprocessing faster
K: A
G: ## AWS Glue job bookmarks
A **job bookmark** is state that AWS Glue keeps between runs of a job so it can process only new data.
- For S3 sources, the bookmark remembers which objects were already processed (based on their paths and modification timestamps). The next run reads only files added since the last successful run.
- Enable it with the job parameter `--job-bookmark-option job-bookmark-enable`. In the script, sources need a `transformation_ctx` name, and the run must end with `job.commit()` so the state is saved.
- A bookmark can be paused or reset, for example to reprocess everything after a bug fix.
## Example
On Monday the prefix holds 1,000 files, and the job processes all of them. On Tuesday 40 new files arrive; with bookmarks enabled the job reads only those 40, so runtime tracks the daily volume instead of the total history.
W: Job bookmarks: the job keeps state about what it has already processed and reads only new files, so runtime and cost stay proportional to each day's new data.
X: B=Crawler before each run: a crawler updates table schemas and partitions in the Data Catalog. It does not tell the job which files it has already processed.
C=S3 Versioning: versioning keeps older versions of overwritten objects. It does not stop the job from listing and reading every current object in the prefix.
D=More DPUs: more capacity may make each run faster, but the job still reads all history, so the work and cost keep growing every day.
T: Incremental processing in Glue means job bookmarks; more capacity only speeds up reprocessing data that did not need to be read again.
V: AWS Glue

@ DEA-C01 D1 T1.3 advanced use-case
S: A team already has 150 Apache Airflow DAGs orchestrating Glue, EMR, and Redshift tasks on self-managed servers. It wants a managed service with minimal rewrite. Which option fits BEST?
A: Amazon EventBridge Scheduler invoking Lambda functions
B: AWS Glue workflows with triggers
C: Amazon MWAA environments
D: AWS Step Functions state machines
K: C
G: ## Amazon MWAA
Amazon Managed Workflows for Apache Airflow (MWAA) runs open-source Apache Airflow as a managed service. AWS operates the scheduler, workers, web server and metadata database, scales workers, and patches the environment.
- You upload DAG files, a `requirements.txt` and plugins to an S3 bucket, and the environment picks them up.
- Existing DAGs keep using the same Airflow operators, such as the Amazon provider operators for Glue jobs, EMR steps and Redshift SQL, so migration is mostly about matching the Airflow version and dependencies.
- Access is controlled with IAM, and the environment runs in your VPC.
## Example
A team copies its 150 DAG files to `s3://mwaa-dags/dags/`, pins the same provider versions in `requirements.txt`, and gives the execution role permission to start Glue, EMR and Redshift work. The DAGs run largely unchanged.
W: Amazon MWAA: Amazon Managed Workflows for Apache Airflow is managed Airflow, so the existing 150 DAGs can run with little or no rewriting while AWS takes over the servers.
X: A=EventBridge Scheduler with Lambda: it schedules single targets on a timetable but has no DAG dependencies, retries across tasks or backfills. All 150 workflows would have to be rebuilt as custom code.
B=Glue workflows: Glue workflows orchestrate Glue jobs, crawlers and triggers. They are not built to run existing Airflow DAGs and would require a rewrite of each workflow.
D=Step Functions state machines: Step Functions is a capable orchestrator, but converting 150 DAGs into state machines is exactly the large rewrite the team wants to avoid.
T: Existing Airflow DAGs plus "managed, minimal rewrite" points to MWAA; other orchestrators mean rebuilding every workflow.
V: Amazon MWAA

@ DEA-C01 D4 T4.3 advanced use-case
S: Security requires that Glue ETL jobs encrypt data written to S3, CloudWatch logs, and job bookmarks with customer managed KMS keys. Which feature enforces this for the jobs?
A: SSL required on the AWS Glue connection that the ETL jobs use
B: An S3 bucket policy that denies uploads lacking SSE-KMS with the key
C: Default SSE-KMS encryption on the output bucket with the customer key
D: An AWS Glue security configuration attached to the ETL jobs
K: D
G: ## Glue security configurations
A **security configuration** in AWS Glue is a named set of encryption settings that you attach to jobs and crawlers. It covers three places data can end up:
- **S3 encryption**: data the job writes to S3 using SSE-KMS with a chosen key (SSE-S3 is also possible).
- **CloudWatch Logs encryption**: the job's log output encrypted with a KMS key.
- **Job bookmark encryption**: the bookmark state encrypted with client-side KMS encryption.
## Example
You create `sc-kms-cmk` with the customer managed key `arn:aws:kms:eu-west-1:111122223333:key/...` for all three settings and attach it to every ETL job. The job's IAM role needs permission to use the key, and the log group needs the key's policy to allow CloudWatch Logs.
W: Glue security configuration: one configuration attached to the jobs names the customer managed KMS keys for S3 output, CloudWatch Logs and job bookmarks, so all three are encrypted as required.
X: A=SSL on the connection: SSL protects data in transit between Glue and a database. It does not encrypt data at rest in S3, logs or bookmarks.
B=Bucket policy requiring SSE-KMS: it can reject S3 uploads that do not use the key, but it does nothing for CloudWatch Logs or job bookmarks.
C=Default bucket encryption: it may cover the S3 objects, but it does nothing for CloudWatch Logs or job bookmarks, and a job can still specify a different encryption setting.
T: Encrypting everything a Glue job writes (S3, logs, bookmarks) with your own KMS keys is done with a security configuration attached to the job.
V: AWS Glue, AWS KMS
