@ SCS-C03 D1 T1.1 advanced use-case
S: A partner-upload account receives supplier files into one Amazon S3 bucket, and an internal Lambda pipeline reads each new object within minutes. The account has never enabled GuardDuty, and the security team does not want to pay for GuardDuty threat detection there. Every new object must be scanned for malware, and the pipeline must be unable to read any object that has not been confirmed clean. Which TWO actions meet these requirements? (Select TWO)
A: Enable GuardDuty Malware Protection for S3 on the bucket as an independent feature, and turn on tagging of the scanned objects
B: Enable GuardDuty in the account with the S3 Protection plan, so every PutObject data event on the bucket is analyzed for malware before it is read
C: Add a bucket policy statement that denies s3:GetObject unless the object tag GuardDutyMalwareScanStatus equals NO_THREATS_FOUND
D: Turn on Amazon Macie automated sensitive data discovery for the bucket, so new objects are sampled and any malicious file is reported as a finding
E: Configure an S3 event notification that sends each new object to Amazon Inspector, and deny reads in the bucket policy until Inspector tags the object
K: A,C
G: ## Malware Protection for S3 without a detector
GuardDuty **Malware Protection for S3** scans newly uploaded objects in the buckets you select. It can be used as part of GuardDuty or **as an independent feature**: then the account has no GuardDuty detector and pays only for the scans. Because findings belong to a detector, an independent account gets no GuardDuty finding; the result goes to EventBridge, CloudWatch metrics and, if enabled, an object tag.
## Turning the scan result into an access control
With tagging on, GuardDuty adds the tag `GuardDutyMalwareScanStatus` with the scan result (for example `NO_THREATS_FOUND`). A bucket policy can then use the condition key `s3:ExistingObjectTag/GuardDutyMalwareScanStatus` to deny `s3:GetObject` for every principal except the Malware Protection service role while the tag is missing or not clean. This is tag-based access control (TBAC): an object that was never scanned or was found malicious stays unreadable.
W: A=Malware Protection for S3 (independent): scans every new object without enabling GuardDuty threat detection, and the tagging option writes the result onto each object.
C=Bucket policy on the scan tag: an object without the clean tag, including one still waiting for its scan, cannot be read by the pipeline.
X: B=S3 Protection: it analyzes S3 data events for suspicious access patterns, not file contents for malware, and it requires enabling GuardDuty threat detection, which the team refused.
D=Macie: Macie discovers sensitive data such as PII; it does not detect malware.
E=Inspector: Inspector scans EC2, ECR images and Lambda functions for vulnerabilities; it does not scan S3 objects or tag them.
T: For malware in uploaded S3 objects, use GuardDuty Malware Protection for S3 (it can run without a detector) and gate reads on the GuardDutyMalwareScanStatus tag.
V: Amazon GuardDuty, Amazon S3

@ SCS-C03 D1 T1.1 advanced use-case
S: A fintech runs Amazon Aurora PostgreSQL clusters in 12 accounts with GuardDuty already enabled across the organization. After a credential-stuffing attempt against one database, the security team wants alerts on anomalous login behavior, such as a burst of failed logins from an unusual source, for every Aurora cluster. The database team will not install extensions, change parameter groups, or accept any performance impact. Which approach meets these requirements with the LEAST operational effort?
A: Enable GuardDuty RDS Protection from the delegated administrator for all member accounts, and route its findings to the on-call team with EventBridge
B: Export Aurora PostgreSQL logs to CloudWatch Logs in every account, then create metric filters and alarms on repeated password authentication failures per cluster
C: Turn on Database Activity Streams for every Aurora cluster and send each stream to a SIEM that builds its own per-user baseline of normal logins
D: Activate Amazon Inspector in every account so that it profiles database login events against a learned baseline and opens a finding for each anomalous burst
K: A
G: ## What RDS Protection watches
GuardDuty **RDS Protection** analyzes and profiles **login activity** for Aurora (MySQL- and PostgreSQL-compatible), RDS for PostgreSQL, RDS for MySQL and RDS for MariaDB, and data activity for Aurora PostgreSQL and RDS for PostgreSQL. It builds a baseline per database and raises findings for anomalous logins, such as a successful login after many failures from an unusual source.
- It needs no agent, extension or parameter change, and it is designed not to affect database performance.
- In an organization, the GuardDuty delegated administrator enables the protection plan for member accounts.
## Static alarms versus anomaly detection
A metric filter counts a pattern against a fixed threshold. It knows nothing about what is normal for a given user or source, and getting failed-login lines into the logs at all usually means changing logging parameters on every cluster.
W: A=RDS Protection: managed, baseline-driven login anomaly detection for Aurora with no change to the databases, enabled centrally for all accounts that already run GuardDuty.
X: B=Log export with metric filters: it needs logging settings on each cluster (a parameter change the database team refuses) and a static threshold is not anomaly detection.
C=Database Activity Streams: each cluster must be modified and the team must build and run its own baselining in the SIEM, which is far more effort.
D=Amazon Inspector: Inspector finds software vulnerabilities and network exposure; it does not analyze database login events.
T: For anomalous logins to Aurora and RDS without touching the databases, enable GuardDuty RDS Protection.
V: Amazon GuardDuty, Amazon Aurora, Amazon EventBridge

@ SCS-C03 D1 T1.1 advanced tradeoff
S: A media company stores 900 TB in Amazon S3 across 40 buckets. The security team wants detection of suspicious object-level activity, such as a sudden mass download by a role from an unusual network location. A cost review rejected a CloudTrail trail that logs S3 data events for all buckets, and the team will not write or tune its own detection rules. GuardDuty foundational threat detection is already enabled in the account. What should the team do?
A: Enable the GuardDuty S3 Protection plan, which monitors S3 data events by itself without a trail logging them and raises findings for anomalous access
B: Create a trail with advanced event selectors for GetObject only, and build CloudWatch anomaly detection alarms on download volume for each role
C: Enable S3 server access logging on all 40 buckets and run scheduled Athena queries that flag unusual download volumes for each requester
D: Enable CloudTrail Insights on the existing management events trail, so that unusual rates of object-level API calls raise Insights events automatically
K: A
G: ## Two different S3 data sources for GuardDuty
- **Foundational threat detection** analyzes CloudTrail **management** events, such as bucket policy changes.
- **S3 Protection** adds monitoring of CloudTrail **data events for S3** (GetObject, PutObject, DeleteObject and so on) and generates findings such as anomalous data access or exfiltration patterns.
To use S3 Protection you do not need to enable or configure S3 data event logging in CloudTrail: GuardDuty consumes that stream itself. You pay for the GuardDuty plan, not for a trail that delivers billions of data events to S3.
## Insights is not object-level
CloudTrail Insights looks for unusual API call rates or error rates in the events a trail already logs. A management events trail contains no object-level calls, so Insights on it can never see a mass download.
W: A=S3 Protection: managed anomaly detection on object-level activity, with no data event trail to pay for and no rules to maintain.
X: B=GetObject data event trail: this is exactly the data event logging the cost review rejected, and the team would still have to build and tune the alarms.
C=Server access logs with Athena: the team would write and tune its own detection queries, which it refused to do.
D=Insights on management events: object-level calls are data events, so they are not in that trail and Insights cannot evaluate them.
T: GuardDuty S3 Protection analyzes S3 data events without a CloudTrail data event trail.
V: Amazon GuardDuty, Amazon S3, AWS CloudTrail

@ SCS-C03 D1 T1.2 advanced tradeoff
S: An audit found that the organization trail logs only write management events to save cost, so nobody can show who called secretsmanager:GetSecretValue on production secrets. Auditors now require every GetSecretValue call to be logged. Finance objects to extra volume, pointing out that AWS KMS Encrypt, Decrypt, and GenerateDataKey calls already account for nearly all read events in these accounts. Which change to the trail satisfies the auditors while keeping that KMS volume out?
A: Add a data event selector for the Secrets Manager secret resource type with readOnly set to true, and keep management events at write-only
B: Keep write-only management events and enable CloudTrail Insights for read API activity, so unusual GetSecretValue call rates are captured for the audit
C: Log both read and write management events on the trail, and turn on the setting that excludes AWS KMS events from its management events
D: Create a second trail that logs only read management events into a cheaper bucket class, leaving the KMS events included so nothing is ever missed
K: C
G: ## Where GetSecretValue lands in CloudTrail
Secrets Manager API calls are **management events**; Secrets Manager is not among the services that offer CloudTrail data events. `GetSecretValue` (and `BatchGetSecretValue`, which produces GetSecretValue entries) is a **read** event, so a trail set to write-only skips it.
## Read events without the KMS flood
KMS `Encrypt`, `Decrypt` and `GenerateDataKey` are also read management events and usually make up more than 99% of KMS event volume. A trail can log read and write management events and, as a separate setting, **exclude AWS KMS events**. In CloudTrail terms this is an advanced event selector with `eventSource` NotEquals `kms.amazonaws.com`.
Note the trade: excluding KMS events also drops low-volume KMS write events such as `ScheduleKeyDeletion` from that trail, so many teams keep a second source (another trail or GuardDuty) for those.
W: C=Read and write, KMS excluded: GetSecretValue is a read management event, so logging reads captures it, and the KMS exclusion keeps the high-volume Decrypt and GenerateDataKey calls out.
X: A=Secrets Manager data events: Secrets Manager has no CloudTrail data events; its API calls are management events.
B=Insights: Insights records unusual activity rates, not each individual call, so it cannot prove who read which secret.
D=Second read-only trail with KMS: it does capture GetSecretValue, but it adds exactly the KMS read volume that finance objected to.
T: GetSecretValue is a read management event; log read events and exclude KMS events to keep the volume down.
V: AWS CloudTrail, AWS Secrets Manager, AWS KMS

@ SCS-C03 D1 T1.2 advanced use-case
S: A company uses Amazon Security Lake with a rollup Region for 60 accounts. Its third-party SIEM runs its own ingestion pipeline: it must copy every new OCSF object into its own storage as soon as the object is written, and the SIEM vendor will not run Athena queries against AWS. The security team wants the SIEM to see only CloudTrail and VPC Flow Logs sources. How should the team give the SIEM access?
A: Create a Security Lake subscriber with query access for those two sources, so the SIEM queries the Lake Formation tables with its own engine
B: Create a Security Lake subscriber with data access for those two sources, notified of each new object through an SQS queue or HTTPS endpoint
C: Share the Security Lake S3 bucket with the SIEM account through a bucket policy, and add an S3 event notification that invokes the SIEM endpoint
D: Create a Security Lake subscriber with query access for all sources, and add a Lake Formation filter that limits the SIEM to the two source tables
K: B
G: ## Two kinds of Security Lake subscribers
- **Data access**: the subscriber reads the source objects directly from the Security Lake S3 bucket and is **notified of new objects** as they are written, through an HTTPS endpoint it provides or an **SQS queue** it polls. This suits tools that ingest into their own storage.
- **Query access**: the subscriber queries the **Lake Formation tables** in place with services such as Athena; nothing is copied.
A subscriber is scoped to chosen sources and to the Region where it is created; with a **rollup Region**, data from contributing Regions is available there too.
## Why not hand-built sharing
Security Lake creates and manages the permissions and notifications for a subscriber. Editing the managed bucket policy and notifications yourself bypasses that and is easy to break.
W: B=Data access subscriber: the SIEM gets object-level read access to only the chosen sources and a notification for every new object, which fits an ingest-and-copy pipeline.
X: A=Query access: it lets the SIEM query tables in place, but the vendor wants to copy objects as they are written and will not run queries against AWS.
C=Hand-built bucket sharing: it bypasses Security Lake subscriber management and exposes every source in the bucket, not just the two required.
D=Query access with filters: still query-based rather than object delivery, and it grants all sources first, the opposite of least privilege.
T: Security Lake data access = object reads plus new-object notifications; query access = Lake Formation tables queried in place.
V: Amazon Security Lake, Amazon SQS, AWS Lake Formation

@ SCS-C03 D1 T1.3 advanced troubleshooting
S: To cut AWS Config cost, a platform team narrowed the configuration recorder in 30 accounts to only EC2 and IAM resource types. Since then, AWS Security Hub CSPM controls for S3 buckets, such as S3.5 and S3.8, show many findings with a compliance status of WARNING instead of PASSED or FAILED, and their control status is Unknown. The security team needs real pass or fail results for the S3 controls again. What is the cause and the fix?
A: The controls fail because the S3 buckets lack resource tags that CSPM requires; tag all buckets and wait for the next periodic evaluation cycle
B: Security Hub CSPM cannot evaluate those controls because Config no longer records S3 buckets; add AWS::S3::Bucket back to the recorder
C: Consolidated control findings is turned off in the administrator account; enable it so that each S3 control produces one PASSED or FAILED result
D: The S3 controls are disabled in the central configuration policy; re-enable them for all accounts from the delegated administrator account
K: B
G: ## Most CSPM controls run on AWS Config
Many Security Hub CSPM controls are backed by AWS Config rules (managed or service-linked). For controls with a change-triggered schedule, and some periodic ones, **AWS Config must record the resource type** the control checks.
## Reading the status
- `WARNING`: CSPM cannot tell whether the resource passes or fails, for example because Config resource recording is not turned on for that resource type.
- `NOT_AVAILABLE`: the check could not be completed (server failure, deleted resource, or a NOT_APPLICABLE Config result).
- Control status **Unknown** means at least one finding is WARNING or NOT_AVAILABLE and none failed.
When the recorder was narrowed to EC2 and IAM, the S3 controls lost their data source, which is exactly the WARNING pattern.
W: B=Record S3 buckets again: the S3 controls depend on Config recording `AWS::S3::Bucket`; once it is recorded, the checks produce PASSED or FAILED again.
X: A=Missing tags: CSPM controls do not require tags to evaluate, and a missing tag would produce FAILED, not WARNING.
C=Consolidated control findings: that setting only merges findings across standards; it does not supply the missing resource data.
D=Disabled controls: a disabled control produces no findings at all, rather than findings in WARNING status.
T: CSPM findings in WARNING usually mean AWS Config is not recording the resource type the control needs.
V: AWS Security Hub CSPM, AWS Config

@ SCS-C03 D1 T1.3 advanced troubleshooting
S: An Amazon Macie sensitive data discovery job over three finance buckets reports that many objects could not be analyzed. Bucket one uses SSE-KMS with a customer managed key whose key policy grants only the finance application role. Bucket two holds objects that a legacy uploader wrote with SSE-C. Bucket three uses SSE-S3 and was analyzed normally. The team wants Macie to inspect the contents of all three buckets. Which TWO actions are required? (Select TWO)
A: Add a statement to the customer managed key's policy that allows the Macie service-linked role to use the key
B: Attach an IAM policy granting kms:Decrypt on the customer managed key to the AWSServiceRoleForAmazonMacie role in the account
C: Upload the SSE-C encryption key to Macie as a custom data identifier, so that Macie can decrypt the bucket two objects whenever it samples them
D: Re-encrypt the bucket two objects by copying them in place with SSE-S3 or SSE-KMS, because Macie can only report metadata for SSE-C objects
E: Switch bucket one to the AWS managed key aws/s3, because Macie cannot use a customer managed key even when its key policy allows Macie
K: A,D
G: ## How Macie reads encrypted objects
Macie uses its service-linked role `AWSServiceRoleForAmazonMacie` to retrieve objects.
- **SSE-S3** and **SSE-KMS / DSSE-KMS with an AWS managed key**: Macie can decrypt them.
- **SSE-KMS / DSSE-KMS with a customer managed key**: Macie can decrypt only **if you allow Macie to use the key**, which is done in the **key policy**. A key policy that names only the application role blocks Macie.
- **SSE-C**: Macie cannot decrypt the object; it can only store and report its metadata. The key is never stored by AWS.
## Fixing the two failures
For bucket one, add a key policy statement for the Macie service-linked role. For bucket two, the content must be re-encrypted with a server-side option Macie can read, for example by copying each object in place with SSE-S3 or SSE-KMS.
W: A=Key policy allows Macie: customer managed keys are usable by Macie only when the key policy lets the Macie service-linked role use them.
D=Re-encrypt the SSE-C objects: Macie can never decrypt SSE-C content, so the objects must be rewritten with an encryption type Macie can read.
X: B=IAM policy on the service-linked role: service-linked role policies are managed by AWS and cannot be edited, and the key policy names only the application role, so IAM permissions alone would not count.
C=SSE-C key as a custom data identifier: custom data identifiers are regex patterns for finding data, not a way to supply encryption keys.
E=Switch to aws/s3: Macie can use a customer managed key when the key policy allows it, and changing the default key does not re-encrypt existing objects.
T: Macie needs a key policy grant for customer managed keys and cannot read SSE-C objects at all.
V: Amazon Macie, AWS KMS, Amazon S3

@ SCS-C03 D2 T2.1 advanced use-case
S: A security team has built an EventBridge rule that sends GuardDuty findings to a Step Functions workflow, which tags resources, opens tickets, and isolates EC2 instances. Before the quarterly audit it must prove that the rule matches every finding type the workflow claims to handle, including attack sequence findings. Policy forbids running attack tools or malware in any account. What is the MOST efficient way to test the pipeline?
A: Run the open-source GuardDuty tester in a sandbox account so that it creates real findings of each type, then check that the workflow handled every one
B: Generate GuardDuty sample findings in a test account, then check that the rule matched each finding type and that the workflow ran its steps
C: Write synthetic findings in AWS Security Finding Format with BatchImportFindings into Security Hub CSPM and check that the workflow received them
D: Temporarily lower the rule's severity filter to match all findings in production and wait for a full week of naturally occurring GuardDuty findings
K: B
G: ## Testing detection pipelines without an attack
GuardDuty can **generate sample findings**: one sample for each supported finding type, including **attack sequence** finding types. Samples carry placeholder values and are marked as samples, but they are published like real findings, so they are meant for testing EventBridge rules, filters and automation.
- Use a test account (or make the workflow skip isolation for samples) so placeholder resource IDs do not cause side effects.
- Check both halves: that the rule pattern matched each type, and that each workflow branch ran.
## Why not other approaches
Tools that create real findings work by generating real suspicious traffic or behavior, which the policy forbids. Findings imported into Security Hub CSPM are a different event source than GuardDuty's own EventBridge events.
W: B=Sample findings: one sample for every finding type, attack sequences included, delivered through the same event path, with no attack activity needed.
X: A=GuardDuty tester: it produces findings by simulating real attack behavior, which the policy forbids even in a sandbox.
C=BatchImportFindings into Security Hub CSPM: these arrive with a Security Hub event source, so they do not test a rule written for GuardDuty findings.
D=Wait for real findings in production: slow, incomplete (rare types may never occur) and it changes the production rule.
T: Use GuardDuty sample findings to test EventBridge rules and response automation for every finding type.
V: Amazon GuardDuty, Amazon EventBridge, AWS Step Functions

@ SCS-C03 D2 T2.1 advanced tradeoff
S: A ransomware recovery plan requires AWS Backup copies that no one, including the account root user and AWS, can delete or shorten before 35 days. The backup team has never run its new retention rules in production and fears that a wrong setting could lock unwanted backups in place forever. It wants a window to test the setup and remove the lock if needed, and then full immutability. Which vault configuration fits?
A: Lock the vault in governance mode with a 35-day minimum retention, and restrict the backup:DeleteBackupVaultLockConfiguration action to a break-glass role
B: Use a standard vault with a vault access policy that denies backup:DeleteRecoveryPoint to every principal, and remove that policy if testing finds a problem
C: Lock the vault in compliance mode with a 35-day minimum retention and a grace time of a few days, then review the setup before the grace time ends
D: Lock the vault in compliance mode with no grace time, and rely on AWS Support to remove the lock if the retention settings turn out to be wrong
K: C
G: ## Vault Lock modes
- **Governance mode**: users with sufficient IAM permissions can remove the lock. Good against mistakes, not against a compromised administrator.
- **Compliance mode**: after the **grace time** ends, the vault and its lock are immutable. No user, not even the root user, and not AWS, can change or delete it while it holds recovery points, and recovery points cannot be deleted before their retention ends.
## The grace time is the test window
In compliance mode you choose a cooling-off period, the **grace time**, which must be **at least 3 days (72 hours)**. During it you can still remove or change the lock. Programmatically it is `ChangeableForDays` in `PutBackupVaultLockConfiguration`; including that parameter is what makes the lock compliance mode.
Caution: recovery points with a retention of "Always" in a compliance-mode vault would be kept forever, so check retention settings during the grace time.
W: C=Compliance mode with grace time: it ends fully immutable (root and AWS cannot delete) and still gives a window of at least three days to test and undo.
X: A=Governance mode: a user with enough IAM permissions, such as an attacker with administrator access, can remove the lock, so the root-user requirement is not met.
B=Vault access policy deny: the root user or an administrator can edit or remove the access policy, so nothing is immutable.
D=Compliance with no grace time: the API requires a grace time of at least 3 days, and after it ends AWS cannot remove the lock either.
T: Backup Vault Lock in compliance mode is immutable after its grace time (minimum 3 days), which is the window to test and undo.
V: AWS Backup

@ SCS-C03 D2 T2.2 advanced use-case
S: An IAM user's access key was pushed to a public repository. Within minutes AWS attached the AWSCompromisedKeyQuarantineV3 managed policy to the user and opened a support case. The user runs a nightly reporting job that must keep working after a short break. The on-call engineer proposes detaching the policy because the key is now quarantined. Which TWO actions should the team take? (Select TWO)
A: Detach AWSCompromisedKeyQuarantineV3 right away, because AWS rotates the exposed access key automatically when it attaches the quarantine policy
B: Issue a new access key to the reporting job, deactivate and delete the exposed key, then follow the support case before removing the policy
C: Review CloudTrail for every call made with the exposed access key ID, including calls to services that the quarantine policy does not deny
D: Leave the exposed key active, because the quarantine policy denies all actions for the user until AWS Support closes the case
E: Delete the IAM user and recreate it under the same name, so that the old key and the quarantine policy are both removed at once
K: B,C
G: ## What the quarantine policy is
When AWS detects an IAM user's access key exposed publicly, it attaches the AWS managed policy **AWSCompromisedKeyQuarantineV3** and opens a support case. The policy **denies a defined list of actions** that are commonly abused for fraud (for example launching instances, creating users or access keys, and some S3, Lambda and Bedrock actions). AWS says not to remove it, and to follow the case instructions instead.
## What it does not do
- It does **not** deactivate, delete or rotate the exposed key; the key is still valid.
- It denies only the listed actions; calls to anything not on the list still succeed.
## Response
Replace the credential (new key for the workload), deactivate and delete the exposed key, then look at CloudTrail for everything that key ID did, before and after the quarantine. Only then follow the case to remove the policy.
W: B=Replace and remove the key: a new key keeps the job running, and deactivating and deleting the exposed key is what actually ends the attacker's access.
C=Review CloudTrail by access key ID: the quarantine covers only certain actions, so the team must find everything the key did, including allowed actions and anything done before quarantine.
X: A=Detach now: AWS does not rotate the key; detaching the policy would reopen the denied actions to whoever holds the leaked key.

A: Declarative policies apply only to new accounts; detach and reattach the policy so that it is enforced in the existing workload accounts as well
B: The ImageProviders list needs the value amazon; without it, the criteria are evaluated in audit mode and launches are reported but not blocked
C: Allowed AMIs never restricts AMIs owned by the account itself; also deny ec2:CreateImage and ec2:RegisterImage for developers with an SCP
D: Allowed AMIs is evaluated only at instance stop and start; enable the setting for RunInstances too, so new launches are checked at creation
K: C
G: ## What Allowed AMIs controls
**Allowed AMIs** is an account-level EC2 setting (per Region, or applied across accounts and Regions with a **declarative policy**). You define criteria, such as `ImageProviders`, `ImageNames`, `CreationDateCondition` or `MarketplaceProductCodes`; only matching AMIs are discoverable and usable. **Audit mode** previews the effect without blocking.
Important limit: it controls only **public AMIs and AMIs shared with the account**. **AMIs owned by the account are always discoverable and usable**, whatever the criteria.
## Closing the gap
Stop the creation of local AMIs: an SCP that denies `ec2:CreateImage`, `ec2:RegisterImage` and `ec2:CopyImage` (except for the image pipeline) means the only usable images are the allowed shared ones.
W: C=Own AMIs are exempt: the developer's locally created AMI is never filtered, so preventing local AMI creation is what enforces the golden-image rule.
X: A=Only new accounts: declarative policies apply to all accounts in the target and the shared-AMI filtering already works in this account.
B=Missing amazon provider: adding amazon would allow more AMIs, not fewer, and audit mode is a separate setting that the team did not choose.
D=Only at stop and start: Allowed AMIs is evaluated when instances are launched; that is why public and Marketplace AMIs are already blocked.
T: Allowed AMIs filters public and shared AMIs only; block local AMI creation to enforce golden images.

@ SCS-C03 D6 T6.2 advanced use-case
S: A CloudFormation stack deploys a payment service, including a DynamoDB table and a KMS key. Recently a pipeline change renamed the table's logical ID, and the update replaced the table and lost data. Developers must still be able to update every other resource through the same pipeline, and the guard must apply to anyone who updates the stack. What should the team add?
A: A stack policy that allows Update:* on all resources but denies Update:Replace and Update:Delete for the table and the KMS key
B: A DeletionPolicy of Retain on the table and key, so that CloudFormation keeps the original table when the update replaces it with a new one
C: Termination protection on the stack, so that CloudFormation rejects any update that would delete or replace resources inside the stack
D: An IAM policy on the pipeline role that denies cloudformation:UpdateStack whenever the change set contains replacement of the table
K: A
G: ## Stack policies
A **stack policy** is a JSON document that controls which **update actions** CloudFormation may perform on which resources during **stack updates**:
- Actions: `Update:Modify`, `Update:Replace`, `Update:Delete`, `Update:*`.
- Once a stack policy exists, every resource is protected by default; you add explicit `Allow` statements, and `Deny` statements protect specific resources.
- It applies to **every user** who updates the stack. It is a fail-safe against accidents, not an access control.
A policy that allows `Update:*` on `*` and denies `Update:Replace` and `Update:Delete` on the table and key lets the pipeline change everything else.
## Other protections
- **DeletionPolicy Retain** keeps a resource when it is removed or replaced, but the stack then points to a new, empty table.
- **Termination protection** prevents deleting the **stack**; it does not affect updates.
W: A=Stack policy denying replace and delete: CloudFormation refuses any update that would replace or delete the table or key, for anyone, while other resources update normally.
X: B=DeletionPolicy Retain: the old table survives as an orphan, but the application would be pointed at the new empty table, so the outage still happens.
C=Termination protection: it only blocks deleting the whole stack; updates that replace resources still run.
D=IAM deny on UpdateStack: IAM cannot inspect change set contents, and it would cover only the pipeline role, not everyone.
T: Use a stack policy that denies Update:Replace and Update:Delete for critical resources.
V: AWS CloudFormation

@ SCS-C03 D6 T6.3 advanced troubleshooting
S: A company enabled the AWS Foundational Security Best Practices, CIS AWS Foundations Benchmark, and PCI DSS standards in Security Hub CSPM, which was first enabled in 2022. Analysts now see three separate findings for the same check on the same resource, one per standard, and suppressing one leaves the other two open. The team wants one finding per control per resource, whichever standards include it. What should the team do?
A: Disable the CIS and PCI DSS standards, because Security Hub CSPM can evaluate a security control for only one enabled standard at a time
B: Create an automation rule that suppresses findings whose GeneratorId starts with the CIS or PCI DSS prefix, keeping only the FSBP finding
C: Turn on consolidated control findings in the administrator account, so that Security Hub CSPM generates one finding per control check
D: Configure cross-Region aggregation to a single Region, so that duplicate findings from each standard are merged into one finding there
K: C
G: ## Standard-based versus consolidated findings
Many controls belong to several standards. Without **consolidated control findings**, Security Hub CSPM creates a **separate finding for each enabled standard** that includes the control: three standards, three findings per check.
With consolidated control findings on, it creates **one finding per security control** per resource, regardless of how many standards include it. The finding lists the related standards.
- Accounts that enabled Security Hub CSPM on or after **23 February 2023** have it on automatically; older accounts must turn it on (`update-security-hub-configuration --control-finding-generator SECURITY_CONTROL`).
- With Organizations, member accounts follow the administrator account's setting.
W: C=Consolidated control findings: one finding per control check, so workflow and suppression act on a single finding.
X: A=Disable standards: a control can be part of several enabled standards; disabling them throws away the compliance views the company needs.
B=Suppress by GeneratorId: it hides findings rather than producing one per control, and it breaks when standards share controls differently.
D=Cross-Region aggregation: it collects findings from Regions into one Region; it does not merge per-standard findings.
T: Consolidated control findings gives one Security Hub CSPM finding per control check instead of one per standard.
V: AWS Security Hub CSPM

@ SCS-C03 D6 T6.3 advanced use-case
S: A gaming company's matchmaking servers must accept UDP 7777 and TCP 8443 from the internet. The Security Hub CSPM control EC2.18, which checks security groups for unrestricted inbound access on unauthorized ports, fails for these groups in 25 accounts, and analysts suppress the findings each week. The security team wants the control to treat those ports as authorized while still failing on any other open port. What should the team do?
A: Create a Security Hub CSPM automation rule that sets the workflow status of EC2.18 findings to SUPPRESSED for all security groups in the 25 accounts
B: Disable control EC2.18 in the 25 accounts with the central configuration policy, and replace it with a custom AWS Config rule for the two ports
C: Tag the matchmaking security groups with a value that Security Hub CSPM uses to exempt resources from EC2.18 during each periodic evaluation
D: Customize the EC2.18 control parameters for authorized TCP and UDP ports to include 8443 and 7777, applied through the central configuration policy
K: D
G: ## Control parameters in Security Hub CSPM
Some controls are evaluated against parameters, and for a subset you can **set custom values** instead of suppressing findings. Examples: `IAM.7` password policy settings, `CloudWatch.16` log retention, `Lambda.5` minimum Availability Zones, and **`EC2.18`**, which takes the **authorized ports** that may have unrestricted inbound access.
Changing a parameter triggers a new check, and later periodic checks use the new value. With **central configuration**, the delegated administrator sets parameters in a configuration policy for many accounts at once.
## Why not suppress
Suppression hides findings, including the ones that would reveal a newly opened, truly unauthorized port on the same group.
W: D=Custom parameters for EC2.18: the two game ports count as authorized, every other open port still fails, and central configuration applies it to all 25 accounts.
X: A=Suppress all EC2.18 findings: real violations on these groups would be hidden too.
B=Disable and rebuild: it throws away the managed control and adds a custom rule to maintain, when the control already supports the needed parameter.
C=Exemption tag: CSPM controls do not use resource tags as exemptions.
T: Customize control parameters such as EC2.18 authorized ports instead of suppressing findings.
V: AWS Security Hub CSPM, Amazon EC2
