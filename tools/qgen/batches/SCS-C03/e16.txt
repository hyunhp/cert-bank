# SCS-C03 explain-only: EBS docs (2026-11) allow sharing an aws/ebs-encrypted snapshot after associating a customer managed key; letters are the published ones
# src: https://docs.aws.amazon.com/ebs/latest/userguide/ebs-modifying-snapshot-permissions.html
# src: https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/sharingamis-explicit.html

@ Q004091 explain
G: ## Why the default key blocks a plain share
To use a shared encrypted snapshot, the other account must be able to use a KMS key for it. The AWS managed key `aws/ebs` has a key policy AWS controls, and it only allows use within your own account.
- The EBS docs state that you cannot share a snapshot encrypted under an AWS managed key by granting create-volume permission alone. That is the share the console refuses here.
- The only way such a snapshot reaches another account is through a **customer managed key** that the other account is allowed to use.
## Two ways to get a customer managed key involved
- **Re-encrypt a copy (the pattern in this question):** copy the snapshot and choose a customer managed key during the copy (copying is when you can change the key). Add the DR account to that key's policy with `kms:Decrypt`, `kms:DescribeKey`, `kms:CreateGrant` and data key permissions, then share the copy with the DR account ID.
- **Associate a key with the snapshot (newer option in the docs):** associate a customer managed key with the existing snapshot, allow the DR account in that key's policy, then share the snapshot as usual. The DR account copies it using the associated key.
- Either way, in the DR account copy the snapshot again under its own key, so it no longer depends on the source account's key.
W: Re-encrypt the copy with a customer managed key: only a key you control can be granted to another account, and a snapshot copy is the step where you change the key. Sharing the copy and allowing the DR account in the key policy gives that account everything it needs.
X: A=Make it public: encrypted snapshots cannot be made public, and public exposure of backup data would be a serious risk anyway.
B=Edit the aws/ebs key policy: AWS managed key policies cannot be changed, which is exactly why a snapshot under `aws/ebs` cannot be shared by itself; a customer managed key has to be brought in.
D=Unencrypted copy: you cannot create an unencrypted copy of an encrypted snapshot, and removing encryption would break the protection requirement.
T: A snapshot under `aws/ebs` cannot be shared on its own; bring in a customer managed key granted to the target account (re-encrypt a copy, or associate the key), never edit the AWS managed key or drop encryption.

@ Q004527 explain
G: ## Why the AWS managed key blocks sharing
An encrypted AMI is backed by encrypted snapshots. To launch from a shared encrypted AMI, the other account needs permission to use the KMS key that encrypted the snapshots.
- The **AWS managed key** `aws/ebs` has a key policy you cannot edit, and it only permits use within your own account. The EC2 docs state that you cannot share AMIs backed by snapshots encrypted with the default AWS managed key.
- For individual snapshots, the EBS docs now describe a way around this: associate a customer managed key with the snapshot, share that key, and the other account copies the snapshot using it. Granting create-volume permission alone is still not enough.
- A **customer managed key** has a key policy you control. Allow the target account (or its roles) to use the key, for example `kms:Decrypt`, `kms:DescribeKey`, `kms:CreateGrant` and `kms:ReEncrypt*`, and share the AMI as usual.
## Fix
Copy the AMI so the snapshots are re-encrypted with a customer managed key that allows the workload account, then share the copy. Image Builder distribution settings can apply this encryption during distribution.
W: Re-encrypt with a customer managed key: re-encrypting the AMI's snapshots with a customer managed key that trusts the workload account lets that account use the key and launch from (or copy) the shared AMI.
X: A=Editing the aws/ebs policy: the key policy of AWS managed keys is managed by AWS and cannot be changed by the account owner.
C=Launch and snapshot permissions: these control access to the image and snapshots, but the workload account still cannot use the `aws/ebs` key of the build account. The EBS docs say create-volume permission alone does not share a snapshot under an AWS managed key, so the launch and copy fail.
D=Encryption by default in the workload account: this encrypts new volumes there and does not give the account permission to use the build account's key.
T: Shared encrypted AMIs need a customer managed KMS key that allows the target account; the `aws/ebs` key can never be granted to another account, so permissions on the image or snapshots alone do not help.
