@ SCS-C03 D2 T2.1 applied use-case
S: A company wants an automated, repeatable process so that whenever GuardDuty generates a high-severity Backdoor or CryptoCurrency finding on an EC2 instance, the instance is automatically isolated via security group changes, and both EBS volume snapshots and a memory capture are collected into a separate, restricted forensics AWS account without requiring manual intervention. Which AWS-provided solution most directly addresses this requirement out of the box?
A: The AWS Solutions forensic orchestrator for EC2, a Step Functions workflow
B: SSM Automation runbooks that the response team starts from the console
C: AWS Config custom rules that invoke Lambda remediation functions
D: Amazon Inspector with EventBridge rules on its vulnerability findings
K: A
G: ## The requirements
The scenario lists every step of an EC2 forensic response and asks for it **automated and out of the box**:
- trigger on a specific high-severity GuardDuty finding type,
- isolate the instance by changing security groups,
- capture EBS snapshots and memory,
- store evidence in a separate, restricted forensics account.
## The Automated Forensics Orchestrator for Amazon EC2
AWS published this as an AWS Solutions reference implementation. Findings are routed through Amazon EventBridge (from Security Hub) to an AWS Step Functions state machine that runs Lambda functions and Systems Manager commands for isolation, disk snapshot, memory acquisition and transfer to the forensics account. It is deployed from AWS-provided infrastructure-as-code templates, so you do not have to build the workflow yourself.
Building the same thing from Config rules or Systems Manager documents is possible, but it is custom work, not an out-of-the-box answer.
W: AWS Solutions forensic orchestrator for EC2: the Automated Forensics Orchestrator already implements finding-driven isolation, disk and memory capture and cross-account evidence storage as an EventBridge-triggered Step Functions workflow.
X: B=SSM Automation runbooks started by the team: runbooks can perform steps, but a person must start them, which fails the "no manual intervention" requirement.
C=Config custom rules with Lambda remediation: Config evaluates resource configuration, not GuardDuty findings, and you would have to write all the forensic capture logic yourself.
D=Inspector with EventBridge rules: Inspector finds software vulnerabilities and exposures; its findings are not GuardDuty threat findings, and nothing in it captures memory and disk evidence.
T: For hands-off EC2 forensics triggered by GuardDuty, use the purpose-built orchestrator instead of assembling manual runbooks or configuration rules.
V: AWS Step Functions, Amazon EventBridge, Amazon GuardDuty, Amazon EC2

@ SCS-C03 D4 T4.1 advanced troubleshooting
S: A company enables attribute-based access control in AWS IAM Identity Center and maps a CostCenter attribute from its external identity provider to be passed as a session tag. Permission sets use policies referencing aws:PrincipalTag/CostCenter to scope access to resources tagged with the matching cost center. After enabling this, some users can still access resources from other cost centers. What should the security team check first?
A: Whether permission set conditions match resource tags to the session tag
B: Whether the affected users completed MFA when signing in to the portal
C: Whether AWS Config rules flag resources that are missing the cost tag
D: Whether the target accounts include the Organizations management account
K: A
G: ## How ABAC with Identity Center works
Attribute-based access control (ABAC) grants access by matching tags rather than listing resources.
- In IAM Identity Center, **attributes for access control** map user attributes (from the IdP or the identity store) to session tags, for example `CostCenter = 1234`.
- When the user signs in, the role session carries that tag, readable in policies as `aws:PrincipalTag/CostCenter`.
- The permission set's policy must compare it with the resource tag, for example a condition `StringEquals` on `aws:ResourceTag/CostCenter` equal to `${aws:PrincipalTag/CostCenter}`.
## Common mistakes
Passing the tag is only half of ABAC. If the permission set still contains a broad statement (such as a managed policy granting `ec2:*` on `*`) or the condition compares the wrong key, the tag is present but nothing enforces it. Some actions also do not support resource tag conditions, so those need separate handling.
W: Permission set conditions match resource tags to the session tag: ABAC enforcement lives in the permission set policies, so the first check is that every allow is conditioned on `aws:ResourceTag/CostCenter` matching `aws:PrincipalTag/CostCenter` and no broader statement grants access anyway.
X: B=MFA at sign-in: MFA strengthens authentication, but it has no effect on which cost center's resources an authenticated session can reach.
C=Config rules for missing tags: Config rules can detect missing or incorrect tags after the fact, but they do not decide whether an API request is allowed.
D=Management account: whether the account is the management account does not change how tag conditions in permission set policies are evaluated in the target accounts.
T: ABAC works only if policies actually compare the principal tag with the resource tag; passing the attribute as a session tag does nothing by itself.
V: IAM Identity Center, IAM

@ SCS-C03 D4 T4.2 advanced tradeoff
S: A security architect is weighing attribute-based access control (ABAC) against a traditional role-based access control (RBAC) approach of creating a distinct IAM role per team/project combination. Which tradeoff accurately favors ABAC as the organization scales to hundreds of teams and projects?
A: RBAC needs fewer policies than ABAC once teams and projects grow large
B: ABAC absorbs growth through tags; RBAC adds a role for each new pairing
C: ABAC requires IAM Identity Center and does not apply to plain IAM roles
D: ABAC policies are incompatible with explicit Deny statements, unlike RBAC
K: B
G: ## RBAC versus ABAC in AWS
- **RBAC**: each team/project combination gets its own role with a policy listing its resources. With 50 teams and 20 projects, that can mean hundreds of roles, and every new project means new roles and policy changes.
- **ABAC**: principals and resources carry tags (`Team`, `Project`), and a few policies compare them, for example allowing access when `aws:ResourceTag/Project` equals `${aws:PrincipalTag/Project}`.
## What ABAC changes day to day
- A new project needs tags on its resources and people, not new policies.
- Moving someone to another team means changing their tag or IdP attribute.
- Explicit Deny statements, permissions boundaries and SCPs still work with ABAC.
ABAC works with plain IAM roles and session tags, as well as with IAM Identity Center attributes for access control. Its downside is that tag governance becomes security-critical, so tag editing must be controlled.
W: ABAC absorbs growth through tags: access follows attributes, so growth is handled by tagging, while RBAC needs a new role or policy for every team/project combination.
X: A=RBAC needs fewer policies at scale: at scale RBAC needs more roles and policies, one per combination; ABAC keeps a small fixed set.
C=ABAC requires Identity Center: ABAC works with standard IAM roles, users and session tags; Identity Center is one convenient source of attributes, not a requirement.
D=ABAC incompatible with Deny: ABAC policies can include explicit Deny statements, for example to block tag changes, just like any IAM policy.
T: ABAC grows by adding tags; RBAC grows by adding roles, which is why ABAC wins at hundreds of teams and projects.
V: IAM

@ SCS-C03 D6 T6.3 applied comparison
S: An IAM administrator wants to understand the difference between IAM Access Analyzer's policy validation checks and its external access analyzer findings when reviewing a new S3 bucket policy before applying it. Which statement correctly distinguishes the two capabilities?
A: External access findings lint the policy text; validation reports outside principals
B: Validation lints the draft policy text; the analyzer reports access granted outside
C: Policy validation covers identity policies and skips resource-based bucket policies
D: Both run the same checks under two names, so either one gives the same results
K: B
G: ## Two different Access Analyzer jobs
IAM Access Analyzer has several features that look at policies from different angles.
- **Policy validation** checks a policy document before or while you write it. It returns findings of type `ERROR`, `SECURITY_WARNING`, `WARNING` and `SUGGESTION`, for example an invalid action name, a missing condition or `Principal: "*"` with no condition. It works for identity policies, resource policies, trust policies and SCPs, and is called through `ValidatePolicy` or the console editor.
- **External access findings** come from an analyzer that continuously evaluates policies already attached to resources and reports which ones grant access outside the zone of trust.
## Example
Pasting a new bucket policy into the editor shows validation warnings immediately. After the policy is saved, the analyzer reports a finding if account `444455556666` outside the organization can call `s3:GetObject`. (An access preview can show the external access result for a proposed policy before saving it.)
W: Validation lints the draft, the analyzer reports outside access: validation checks the policy text for errors and risky patterns, while external access findings describe what attached policies actually allow outside principals to do.
X: A=Roles swapped: this reverses the features; syntax and best-practice checks are policy validation, and outside principals are found by the external access analyzer.
C=Validation skips resource policies: policy validation also checks resource-based policies such as S3 bucket policies, plus trust policies and SCPs.
D=Same checks under two names: they use different APIs, run at different times and return different finding types, so they are not interchangeable.
T: Policy validation checks the policy text for mistakes; external access findings show which resources are actually reachable from outside the zone of trust.
V: AWS IAM Access Analyzer, Amazon S3

@ SCS-C03 D5 T5.3 advanced use-case
S: A company wants to discover PII across S3 buckets in all accounts and route findings to Security Hub. Which setup fits?
A: AWS Config rules on bucket encryption, with results sent to Security Hub
B: Amazon Macie with a delegated administrator, publishing to Security Hub
C: Amazon Inspector scanning in each account, with findings in Security Hub
D: GuardDuty Malware Protection for EC2 volumes, reporting to Security Hub
K: B
G: ## Finding PII in S3 with Macie
**Amazon Macie** inspects S3 objects with managed and custom data identifiers to find sensitive data such as names, credit card numbers or passport numbers. It also produces policy findings about bucket security, such as public access.
## Organization-wide setup
- In AWS Organizations, designate a **delegated administrator** account (usually the security account) for Macie.
- The administrator enables Macie for member accounts and runs automated sensitive data discovery or targeted discovery jobs across all their buckets.
- Findings go to EventBridge and can be published to Security Hub (now called AWS Security Hub CSPM), giving one view next to GuardDuty and Inspector findings. Macie's publication settings decide whether policy findings, sensitive data findings, or both are sent.
Example: the security account sees a finding `SensitiveData:S3Object/Personal` for a bucket in a member account and triages it centrally.
## Security Hub is not the deciding part
Config, Inspector and GuardDuty can also send their findings to Security Hub. What matters is which service can read S3 object contents and recognize personal data, and only Macie does that.
W: Macie with delegated administrator, publishing to Security Hub: Macie is the AWS service that discovers PII in S3, the delegated administrator covers all accounts, and the integration sends findings to Security Hub.
X: A=Config rules on bucket encryption: they report whether encryption is configured; they never read object contents, so they cannot find PII, wherever the results are sent.
C=Inspector scanning: Inspector finds software vulnerabilities and network exposure in EC2, container images and Lambda, not personal data in S3 objects.
D=GuardDuty Malware Protection for EC2: it scans EBS volumes for malware; it does not classify sensitive data in S3.
T: PII discovery across S3 in all accounts is Macie with a delegated administrator, feeding findings to Security Hub.
V: Amazon Macie
