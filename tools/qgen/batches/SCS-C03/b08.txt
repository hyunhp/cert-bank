@ SCS-C03 D1 T1.3 expert troubleshooting
S: A security team sends its organization trail to a CloudWatch Logs log group and created a metric filter with the pattern { $.errorCode = "AccessDenied" } feeding an alarm for unauthorized API calls. During a red-team exercise, the testers ran hundreds of ec2:RunInstances, ec2:DescribeInstances, and s3:GetObject calls with a role that had no permissions. The alarm fired for the S3 calls but never for the EC2 calls, although CloudTrail recorded every one of them. The team must alarm on all denied calls without adding another log group or trail. What explains the gap, and what should the filter be?
A: EC2 denials use errorCode Client.UnauthorizedOperation; use { ($.errorCode = "*UnauthorizedOperation") || ($.errorCode = "AccessDenied*") }
B: EC2 denials are recorded only as read-only events that the trail filters out; switch the trail to log read and write events and keep the existing filter
C: EC2 denials are recorded with errorCode AccessDeniedException; use { ($.errorCode = "AccessDenied") || ($.errorCode = "AccessDeniedException") }
D: EC2 denials are recorded with errorMessage only and no errorCode field; use { $.errorMessage = "*not authorized*" } instead of the errorCode test
K: A
G: ## Error codes differ by service
CloudTrail writes the service's own error code into `errorCode`. Most services that use the newer API style return `AccessDenied` or `AccessDeniedException`, but the **Amazon EC2 API returns `Client.UnauthorizedOperation`** (shown in CloudTrail as `Client.UnauthorizedOperation`). An exact match on `"AccessDenied"` therefore never sees EC2 denials.
## The pattern used by CIS and Security Hub CSPM
The CloudWatch control for unauthorized API calls (CIS) uses:
`{($.errorCode="*UnauthorizedOperation") || ($.errorCode="AccessDenied*")}`
- The leading wildcard catches `Client.UnauthorizedOperation`.
- The trailing wildcard catches both `AccessDenied` and `AccessDeniedException`.
## Reading the evidence
The S3 calls matched, so the log group, filter and alarm work. Only the EC2 calls were missed, and they were in CloudTrail, so the cause is the value of the field, not logging.
W: A=Wildcard pattern: matches EC2's Client.UnauthorizedOperation and every AccessDenied variant, so one filter on the same log group covers all denied calls.
X: B=Read-only events: RunInstances is a write event and was recorded, as the stem states; the problem is the error code value, not the event selection.
C=AccessDeniedException: EC2 does not use that code, so the EC2 calls would still be missed.
D=errorMessage only: denied EC2 calls do carry an errorCode; a free-text match on the message is fragile and not the cause.
T: EC2 denials use errorCode Client.UnauthorizedOperation; match "*UnauthorizedOperation" and "AccessDenied*".
V: Amazon CloudWatch, AWS CloudTrail, Amazon EC2

G: ## Cross-account subscriptions
A **destination** is a CloudWatch Logs resource in the **recipient** account that fronts a Kinesis Data Streams or Firehose stream:
- an IAM role that `logs.amazonaws.com` assumes to write to the stream (owned by the recipient);
- an **access policy** on the destination that lets sender accounts call `logs:PutSubscriptionFilter` (by account ID or `aws:PrincipalOrgID`).

- **The log group and the destination must be in the same Region.**
- The resource that the destination points to **can be in a different Region**.

X: B=Second stream: it works technically but breaks the requirement that the SIEM reads a single stream.

@ SCS-C03 D2 T2.2 expert use-case
S: A database password stored in Secrets Manager was pasted into a public chat at 09:00. The secret uses Lambda rotation with the alternating users strategy, and the AWSCURRENT version, which holds the credentials for app_user_clone, is the one that leaked. Applications always fetch the secret at connection time. The responder triggered RotateSecret at 09:10, rotation succeeded, and AWSCURRENT now holds app_user's new password. At 09:40 the database audit log still shows logins as app_user_clone from an unknown address. The rotation function may not be changed during the incident. What should the responder do next?
A: Nothing further, because the 09:10 rotation set a new password for app_user_clone, and the 09:40 logins are sessions that were opened before rotation
B: Rotate the secret a second time, which changes the app_user_clone password because alternating rotation updates the other user on each run
C: Call PutSecretValue with a new password for app_user_clone under the AWSCURRENT label, so that the database rejects the leaked credentials
D: Delete the AWSPREVIOUS version of the secret, because deleting the version that holds the leaked password also invalidates it in the database
K: B
G: ## Alternating users rotation
With the **alternating users** strategy, a secret holds credentials for one of two database users (`user` and `user_clone`). **Each rotation changes the password of the user that is not current** and then makes it AWSCURRENT. After rotation, **both users' credentials are valid**, which gives high availability during rotation.
## Consequence for a leak
At 09:10 the rotation changed **app_user**'s password and moved AWSCURRENT to it. The leaked app_user_clone password was untouched and is still valid in the database, which matches the 09:40 logins. A **second rotation** changes app_user_clone's password, ending the attacker's access. Applications keep working because they fetch AWSCURRENT at connect time.
## Why not edit the secret
Writing a new value into the secret changes what Secrets Manager stores; it does **not** change the password in the database. Deleting versions does not touch the database either.
W: B=Rotate again: the next alternating rotation targets app_user_clone, so its leaked password is replaced in the database while apps use AWSCURRENT.
X: A=No action: the first rotation changed app_user, not app_user_clone, and logins at 09:40 are new authentications with the leaked password.
C=PutSecretValue: it updates only the stored value; the database password for app_user_clone stays the same, and applications would get a password the database rejects.
D=Delete AWSPREVIOUS: removing a secret version does not change any database password.
T: With alternating users rotation, the previous user's password stays valid; rotate twice to retire a leaked current credential.
V: AWS Secrets Manager, Amazon RDS

@ SCS-C03 D2 T2.2 expert troubleshooting
S: At 02:14 CloudTrail recorded kms:ScheduleKeyDeletion with PendingWindowInDays 7 on the customer managed key that encrypts a production DynamoDB table and its S3 exports, called by a compromised automation role. By 02:30, application calls fail with KMSInvalidStateException. The responder has already revoked the automation role's sessions and holds an incident role with kms:* in the key policy. The S3 exports are read by an auditor's account and cannot be re-created, and the key has automatic rotation enabled, which the team wants to keep. Service must be restored within the hour without restoring the table from backup or changing the table's encryption settings. What sequence restores service?
A: Call EnableKey on the key, which cancels the pending deletion and returns the key to the Enabled state in a single step
B: Create a new customer managed key, update the table to use it, and let the old key finish deletion after the seven-day waiting period
C: Call CancelKeyDeletion on the key and wait; AWS KMS returns the key to Enabled automatically when the cancellation completes
D: Call CancelKeyDeletion on the key, then call EnableKey, because a key whose deletion is canceled is left in the Disabled state
K: D
G: ## Key states during deletion
- Scheduling deletion sets the key state to **Pending deletion** for a waiting period of 7 to 30 days (the actual time may be up to 24 hours longer). A key pending deletion **cannot be used in any cryptographic operation**, so services using it fail with `KMSInvalidStateException`.
- **CancelKeyDeletion** stops the deletion, and the key state becomes **Disabled**, not Enabled.
- **EnableKey** then makes it usable again.
EnableKey cannot be called on a key that is pending deletion.
## Why not a new key
A table encrypted with the old key needs that key to decrypt existing data when its encryption is changed. Letting the old key be deleted would lose access to anything still encrypted under it, such as the S3 exports.
W: D=Cancel then enable: cancellation leaves the key Disabled; EnableKey returns it to Enabled so DynamoDB and S3 can use it again.
X: A=EnableKey alone: it is not valid for a key in the Pending deletion state; the deletion must be canceled first.
B=New key: switching the table's key still needs the old key, and deleting the old key would make the S3 exports unreadable.
C=Cancel only: after cancellation the key stays Disabled, so applications would keep failing.
T: CancelKeyDeletion leaves a KMS key Disabled; call EnableKey afterwards.
V: AWS KMS, Amazon DynamoDB, AWS CloudTrail

A principal in another account can use a KMS key only when **both** allow it:

@ SCS-C03 D3 T3.1 expert troubleshooting
S: An API behind an Application Load Balancer uses an AWS WAF web ACL with the AWS managed SQL database rule group. A penetration test sent a JSON body of 14 KB in which the injection payload started at byte 10,000; WAF logs show the request ALLOWED by the web ACL default action, and the backend executed the injected query. The team must stop body inspection blind spots without breaking attachments. Which change should the team make?
A: Raise the web ACL body inspection size limit to 64 KB so that the managed rule group inspects the whole 14 KB request body before the default action
B: Add a rule before the rule group that blocks requests with a body larger than 16,384 bytes unless the URI path is /v1/attachments

K: D
G: ## Body inspection limits depend on the resource type
- **Application Load Balancer and AWS AppSync**: AWS WAF can inspect the **first 8 KB** of the body. This limit is fixed.
- **CloudFront, API Gateway, Cognito, App Runner, Verified Access**: 16 KB by default, configurable up to 64 KB in the web ACL.
## Oversize handling
For rules that inspect the body, oversize handling says what to do when the body is over the limit:
- **Continue**: inspect only the part within the limit (the default outside the console);
- **Match**: treat the request as matching;
- **No match**: treat it as not matching.
For rule groups you don't manage, AWS recommends a **separate rule, placed before them**, that blocks requests whose body **size is greater than** the limit: `8192` for ALB, `16384` for the CloudFront default.
## The evidence
The payload began after byte 8,192, so the SQL rules never saw it. A size rule with a scope-down for the attachments path removes the blind spot while leaving that endpoint working.
W: D=Block bodies over 8 KB except attachments: no request can carry content beyond the ALB's inspection window into the API, and the one large-body path keeps working.
X: A=Raise the limit to 64 KB: the configurable limit applies to CloudFront, API Gateway and similar resources; for an ALB it is fixed at 8 KB.
B=16,384 threshold: that is the CloudFront default; a 14 KB body still passes with its payload beyond the 8 KB the ALB lets WAF inspect.
C=Continue: Continue already means inspect only the first 8 KB, which is exactly how the payload got through.
T: For ALB web ACLs, WAF sees only the first 8 KB of a body; block larger bodies with a size rule placed before inspection rules.
V: AWS WAF, Elastic Load Balancing

@ SCS-C03 D3 T3.3 expert troubleshooting
S: An egress firewall policy in AWS Network Firewall uses strict rule order with the default action Drop all. A stateful rule group allows outbound HTTPS only to an approved domain list using TLS SNI. After cutover, every HTTPS connection from the workload subnets times out, including those to approved domains. Flow logs show TCP SYN packets leaving the instances but no SYN-ACK returning, and the firewall's alert logs show no matches for the domain rules. Traffic to unapproved domains must stay blocked, and the team does not want extra rules for TCP handshakes. What should the team change?
A: Change the default action from Drop all to Drop established, so handshake packets pass and established flows with no pass rule are dropped
B: Keep Drop all and add Alert established as a second default action, so the stateful engine logs established flows and then evaluates their SNI
C: Add a stateless rule that forwards TCP port 443 with the Pass action, so the handshake bypasses the stateful engine before the domain list applies
D: Change the policy's default action from Drop all to Alert all, so that every packet is logged and the domain allow list decides what is passed
K: A
G: ## Why Drop all breaks domain allow lists
With **strict order**, the default actions apply to packets that no rule passed. **Drop all** drops **every** packet that is not passed, including the TCP **SYN** of a new connection. The TLS ClientHello with the SNI never gets a chance to be sent, so the domain rule never matches. That is exactly the evidence: SYNs out, no SYN-ACK, no rule matches.
## Drop established
**Drop established** drops only packets of **established** connections that no rule passed. Layer 3 and 4 handshake packets go through, the ClientHello arrives, and the SNI-based pass rule can act. AWS recommends this default when you use domain list rule groups with strict order, because Network Firewall needs an established connection to evaluate domain lists. (Newer application-level variants exist for segmented ClientHello traffic.)
## Other options
A stateless Pass sends the whole flow past the stateful engine, so the domain list is never applied. Alert actions log; they do not pass or block anything.
W: A=Drop established: the handshake completes, the SNI is inspected, approved domains are passed and every other established flow is dropped.
X: B=Add Alert established: alerts only log; Drop all still drops the SYN before any SNI is seen.
C=Stateless Pass for 443: passed traffic skips stateful inspection entirely, so unapproved domains would be allowed too.
D=Alert all: it logs packets but drops nothing, so traffic to unapproved domains would no longer be blocked.
T: With strict order and SNI or HTTP host allow lists, use the Drop established default action, not Drop all.
V: AWS Network Firewall
