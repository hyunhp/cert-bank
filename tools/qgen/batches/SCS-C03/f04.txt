# SCS-C03 giveaway-cue fixes, cue pass 2 group 3 (full blocks pinned with I:; answers unchanged)

@ SCS-C03 D2 T2.2 advanced use-case
S: An IAM user's access key was accidentally committed to a public repository an hour ago. What should the security engineer do FIRST?
A: Rotate the IAM user's console password and sign out its active console sessions.
B: Delete the public repository and purge the commit holding the key from its history.
C: Deactivate the exposed key, delete it, then review CloudTrail for what it was used for.
D: Enable MFA for the IAM user so that further API calls signed with the key are refused.
K: C
G: ## How fast leaked keys are used
Automated scanners watch public repositories and try leaked AWS access keys within minutes. An hour of exposure means the key must be treated as **already compromised**.
## Response order
- **Deactivate** the access key (`UpdateAccessKey` with status `Inactive`). This stops all use at once and can be reversed if something legitimate breaks; **delete** it once a replacement key is in place.
- **Review CloudTrail** for calls made with that access key ID (for example `AKIA...EXAMPLE`): new IAM users or keys, launched instances, changed policies or data access.
- Remove anything the attacker created, and check GuardDuty findings.
- Remove the secret from the repository history too, but that alone does not revoke it.
AWS may also attach a quarantine managed policy to the user when it detects a public exposure, but you should not rely on that.
W: Deactivate then delete, then review CloudTrail: disabling the key cuts off the attacker immediately, and CloudTrail shows what was done with it so the team can clean up.
X: A=Rotate the console password: the leaked credential is the access key, which works independently of the password and of console sessions, so the attacker keeps full API access.
B=Delete the repository and purge history: the key has likely been copied already, and removing it from the repository or its history does nothing to stop API calls that use it.
D=Enable MFA: an MFA device protects console sign-in; access key API calls are not blocked by MFA unless policies explicitly require it, so the key keeps working.
T: A leaked access key must be deactivated first; cleaning up the repository or password does not revoke it.
V: AWS IAM, AWS CloudTrail

@ SCS-C03 D1 T1.2 applied use-case
S: A security group's inbound rules changed unexpectedly, opening port 22 to 0.0.0.0/0. AWS Config is enabled and recording this resource type. Which Config capability lets an analyst see exactly when the rule changed, what the previous configuration was, and, via CloudTrail integration, which principal made the API call?
A: Config's proactive compliance evaluation of the security group definition
B: A Config conformance pack holding rules that flag open SSH access
C: A Config aggregator collecting data from every account and Region
D: The resource's Config timeline, linked to the matching CloudTrail events
K: D
G: ## Configuration items and the resource timeline
When AWS Config records a resource type, it saves a **configuration item** each time the resource changes: the full configuration, relationships and capture time.
The **resource timeline** in the Config console lists these items in order for one resource, for example security group `sg-0abc...`.
- Each entry shows what changed compared with the previous item, such as a new inbound rule `22/tcp` from `0.0.0.0/0`.
- The timeline also shows compliance changes from Config rules.
- It links to the related **CloudTrail events**, such as `AuthorizeSecurityGroupIngress`, where `userIdentity` shows which principal made the call and when.
This answers "when", "what was it before" and "who" in one place.
W: Resource timeline linked to CloudTrail: it shows each configuration change with the previous state and connects it to the CloudTrail event that identifies the caller.
X: A=Proactive evaluation mode: proactive rules evaluate resource definitions before deployment; they do not show history of an existing resource.
B=Conformance packs: a conformance pack deploys a collection of rules and remediations as one unit; it reports compliance, not the change history of one security group.
C=Aggregators: aggregators collect Config data from multiple accounts and Regions into one view; the question is about a single resource's change detail, which the timeline provides.
T: To see when a resource changed, what it looked like before and who did it, use the Config resource timeline with its CloudTrail links.
V: Config, CloudTrail

@ SCS-C03 D3 T3.3 advanced troubleshooting
S: A team inserted AWS Network Firewall endpoints in front of a public ALB. The ALB subnet route table sends 0.0.0.0/0 to the firewall endpoint, and the firewall subnet routes 0.0.0.0/0 to the internet gateway. Clients now time out, and the firewall shows only one direction of each flow. What is missing?
A: A security group on the firewall endpoint that allows inbound HTTPS from 0.0.0.0/0 to reach the ALB subnets
B: A stateless rule that forwards all return traffic to the stateful engine instead of passing it to the ALB directly
C: An edge-associated table on the internet gateway steering inbound packets for the ALB subnets to the firewall
D: A route in the ALB subnet route table that sends the VPC CIDR to the firewall endpoint as well as 0.0.0.0/0
K: C
G: ## Stateful inspection needs symmetric routing
Network Firewall's stateful engine must see both directions of a connection. If only responses pass through it, it sees packets for flows it never saw start and drops them.
## The inbound path
Without special routing, the internet gateway delivers inbound packets straight to the ALB, because the VPC's local route wins. Responses then go ALB subnet, firewall endpoint, internet gateway. The firewall sees half the flow.
## Ingress routing
An **edge-associated route table** is attached to the internet gateway itself. It can hold a route like:
`10.0.1.0/24 (ALB subnet) -> vpce-firewall-endpoint`
Now inbound packets go internet gateway, firewall, ALB, and responses go ALB, firewall, internet gateway: symmetric and fully inspected.
W: Internet gateway ingress route table: it sends inbound traffic for the ALB subnets through the firewall endpoint, so both directions of each connection pass through the firewall.
X: A=Firewall endpoint security group: Network Firewall endpoints are Gateway Load Balancer-type endpoints without security groups; the problem is routing, not filtering.
B=Stateless forward rule: stateless rules act on packets the firewall already receives. The inbound packets never reach the firewall, so no rule can fix the asymmetry.
D=VPC CIDR route in the ALB subnet: a subnet route table only steers traffic leaving that subnet. Inbound internet traffic is steered by the route table associated with the internet gateway, so this route cannot pull it through the firewall.
T: Inspecting inbound traffic with Network Firewall needs an internet gateway ingress route table; otherwise routing is asymmetric and stateful rules drop flows.
V: AWS Network Firewall, Amazon VPC
