@ SCS-C03 D6 T6.1 advanced troubleshooting
S: A member account can still launch EC2 instances in ap-southeast-2 despite an SCP on its OU denying ec2:RunInstances when aws:RequestedRegion is not us-east-1. The OU also has a default FullAWSAccess SCP and a second SCP explicitly allowing ec2:RunInstances in all regions for an automation role. Why might launches still succeed, and what should the team check first?
A: Confirm the deny SCP is attached on the account's own OU path, not on another OU
B: SCPs on an OU log denied calls to CloudTrail but do not block them for member accounts
C: The Deny fails because aws:RequestedRegion is not a supported condition key in SCPs
D: The automation role's Allow SCP overrides the Deny because SCPs are combined with OR
K: A
G: ## How SCPs are evaluated
For an action in a member account to be allowed, every level from the organization root down to the account must allow it through its SCPs, and no SCP at any of those levels may deny it.
- An explicit `Deny` in any SCP on the account's path always wins; an `Allow` elsewhere cannot override it.
- An SCP only counts if it is attached to the root, an OU the account sits under, or the account itself. SCPs on a sibling OU do nothing.
- The management account is never affected by SCPs.
## Troubleshooting order
If a deny seems ignored, first confirm where the account really lives and which SCPs are attached along that path (for example with `aws organizations list-parents` and `list-policies-for-target`). Common causes: the account was moved to another OU, the deny SCP is attached to a different OU, or the call came from the management account. Then check the condition itself, for example that `aws:RequestedRegion` uses `StringNotEquals`.
W: Check the SCP attachment path: a valid explicit deny cannot be overridden, so launches that still succeed mean the deny is not actually in effect for that account, most often because it is attached to an OU the account does not sit under.
X: B=SCPs only log: SCPs are enforced authorization guardrails; a denied call fails with an access denied error, it is not merely recorded in CloudTrail.
C=No aws:RequestedRegion in SCPs: Region restriction with `aws:RequestedRegion` is one of the most common SCP patterns and is documented by AWS.
D=Allow overrides Deny: an explicit deny in any applicable SCP overrides every allow, including the second SCP that allows the automation role.
T: In SCPs an explicit Deny always wins, so a deny that seems ignored usually is not attached to the account's actual OU path.
V: AWS Organizations, Amazon EC2, AWS IAM

@ SCS-C03 D3 T3.1 advanced use-case
S: A security architect is designing centralized outbound traffic inspection using AWS Network Firewall in an inspection VPC. The requirement is to block outbound connections to known malicious domains at the TLS handshake stage without terminating or decrypting TLS traffic. Which Network Firewall capability satisfies this requirement?
A: A stateless rule group matching the destination IP ranges of those domains
B: VPC Flow Logs with a subscription filter that drops the flagged flows
C: An AWS WAF web ACL with domain match rules associated with the inspection VPC
D: A stateful domain-list rule group matching the SNI in the TLS ClientHello
K: D
G: ## Domain filtering without decryption
When a client opens a TLS connection, the first message (ClientHello) carries the **Server Name Indication (SNI)**: the host name it wants, in clear text. A firewall can read the SNI and drop the connection before any encrypted data flows, without terminating or decrypting TLS.
## Network Firewall rule groups
- **Stateless** rules look at single packets (IPs, ports, protocol). They cannot see host names.
- **Stateful** rules track connections and can inspect application fields. A **domain list** rule group lists domains (for example `.malware-c2.example`) and a type (allow list or deny list); it matches the TLS SNI for HTTPS and the `Host` header for HTTP.
Example: a deny list with `.badsite.example` drops `https://cdn.badsite.example` at the handshake, whatever IP address the domain currently resolves to.
W: Stateful domain-list rules on SNI: they identify the destination domain from the clear-text SNI in the TLS handshake and drop the connection right there, which is exactly blocking by domain without decrypting.
X: A=Stateless IP rules: stateless rules see only addresses and ports, not domain names, and malicious domains change IPs often, so an IP list is always behind.
B=Flow logs dropping flows: VPC Flow Logs only record traffic metadata after the fact; a subscription filter can forward those records but cannot drop or block traffic.
C=WAF web ACL on the VPC: a web ACL protects inbound requests to resources such as CloudFront, ALB or API Gateway; it cannot be associated with a VPC and does not see outbound traffic.
T: To block outbound domains at the TLS handshake without decryption, use Network Firewall stateful domain-list rules that match the SNI.
V: AWS Network Firewall

@ SCS-C03 D5 T5.1 applied use-case
S: An internal microservices platform running on ECS needs certificates for service-to-service TLS within a private VPC, but the organization does not want these certificates to be publicly trusted or discoverable via Certificate Transparency logs. Which ACM capability should be used to issue these certificates?
A: ACM public certificates validated through DNS records
B: ACM public certificates validated by email instead of DNS
C: Self-signed OpenSSL certificates distributed through S3
D: Private certificates issued from an AWS Private CA
K: D
G: ## Public versus private certificates
A **public certificate** from ACM chains to a publicly trusted root, so browsers trust it. Publicly trusted CAs must log every certificate they issue to **Certificate Transparency (CT) logs**, which anyone can search. That means hostnames like `payments.internal.example.com` become discoverable.
A **private certificate** is issued by your own CA, created with **AWS Private CA**. Only systems you configure to trust that CA accept its certificates, and they are not written to public CT logs.
- Private CA certificates can be issued through ACM, which can renew them automatically, or directly through the Private CA API for workloads such as ECS services or a service mesh.
- Example: a root CA and a subordinate CA in Private CA issue certificates for `orders.svc.local`; each ECS task trusts the root CA bundle.
W: AWS Private CA: it issues private certificates that are trusted only by systems configured to trust your CA and are not published to CT logs, which fits internal service-to-service TLS.
X: A=Public certificates with DNS validation: public ACM certificates are publicly trusted and logged to CT logs, exactly what the organization wants to avoid. They also need names in a public domain.
B=Email validation: the validation method only proves domain control. The result is still a public certificate that is publicly trusted and CT-logged.
C=Self-signed via S3: self-signed certificates have no managed chain of trust, revocation or renewal, and copying private keys through a bucket is a weak distribution model.
T: Internal-only TLS that must not appear in CT logs needs a private CA (AWS Private CA), not a public ACM certificate validated a different way.
V: ACM Private CA

S: AWS sent an abuse report about a member account to the account's original owner, who left the company, and nobody on the security team saw it. The organization has 250 member accounts. Which approach makes sure AWS security notifications reach the SOC for every account with the least effort?
A: Enable trusted access for AWS Account Management and call PutAlternateContact with type SECURITY for each member account from the management account
B: Subscribe the SOC's shared email distribution list to the AWS security bulletins RSS feed that announces vulnerabilities to AWS customers
C: Configure AWS User Notifications in the management account to forward high-severity Security Hub findings to the SOC email distribution list

AWS sends account-level security communications, such as abuse reports and notices of possible compromise, to the root email address and to the account's **security alternate contact**. Alternate contacts exist for BILLING, OPERATIONS and SECURITY.
## Managing contacts centrally

- from the management account or a delegated administrator, call

- loop over `organizations list-accounts` to cover all 250 accounts, and include the step in account vending for new ones.
## Example
A distribution list, not a person, keeps notices flowing when people leave.
W: Security alternate contact via Account Management: AWS sends security notices such as abuse reports to the SECURITY alternate contact, and trusted access lets one team set it for all member accounts through the API from the management account.
X: B=Security bulletins feed: bulletins are public announcements about vulnerabilities for all customers; account-specific notices such as abuse reports are not sent there.
C=User Notifications for findings: Security Hub findings are your own tools' detections; AWS abuse reports do not arrive as findings, whatever their severity.

@ SCS-C03 D4 T4.1 advanced use-case
S: An organization has 300 member accounts, each with its own root user password and MFA device stored in a safe. The security team wants to remove long-term root credentials from member accounts but still be able to fix an S3 bucket policy that accidentally denies all principals. Which approach fits?
A: Enable centralized root access management, delete member root credentials, and use sts:AssumeRoot with the S3UnlockBucketPolicy task policy
B: Keep the root passwords but replace each MFA device with a passkey stored in a shared vault that the security team controls
C: Create an IAM Identity Center permission set with AdministratorAccess and assign it in each member account to fix locked bucket policies
D: Attach an SCP that denies root user actions in member accounts, and use an administrator role to edit the locked bucket policy
K: A
G: ## Root users in member accounts
Every AWS account has a root user. In an organization, member root credentials are a large attack surface: hundreds of passwords and MFA devices to protect.
## Centralized root access management
In IAM, the management account (or a delegated administrator) can enable two features once trusted access for IAM is on:
- **Root credentials management**: delete root passwords, access keys, signing certificates and MFA from member accounts; new accounts are created without root credentials.
- **Privileged root actions**: call `sts:AssumeRoot` for a member account with a narrow task policy, getting a short root session that can do only that task.
Task policies include `S3UnlockBucketPolicy`, `SQSUnlockQueuePolicy`, `IAMDeleteRootUserCredentials`, `IAMCreateRootUserPassword` and `IAMAuditRootUserCredentials`.
## Why root is needed for a locked bucket
A bucket policy that denies all principals blocks every IAM role, including administrators. Only the root user can delete that bucket policy.
W: Centralized root access management: it removes member root credentials entirely while keeping a controlled, auditable way to perform root-only tasks such as unlocking a bucket policy through sts:AssumeRoot.
X: B=Passkeys in a vault: the long-term root passwords still exist in every account, which is exactly what the team wants to eliminate.
C=AdministratorAccess permission set: any IAM role is blocked by a bucket policy that denies all principals, so this cannot unlock the bucket, and it grants broad standing access.
D=SCP plus admin role: the SCP limits root but leaves the credentials in place, and an administrator role cannot delete a bucket policy that denies all principals.
T: Remove member root credentials and use sts:AssumeRoot task policies for root-only fixes; admin roles cannot override a deny-all bucket policy.
V: AWS IAM, AWS Organizations, AWS STS, Amazon S3

@ SCS-C03 D1 T1.1 applied use-case
S: A SOC receives many separate GuardDuty findings, such as unusual API calls, a policy change, and S3 data access, that analysts only later realize were steps of one intrusion. The team wants GuardDuty to correlate such signals into one finding with the full timeline. What should it use?
A: GuardDuty trusted IP lists that group findings from one source IP address into a single correlated finding per day
B: GuardDuty Malware Protection for EC2, which scans the instances named in related findings and merges the results
C: GuardDuty Extended Threat Detection, which produces attack sequence findings that link related signals across a timeline
D: GuardDuty suppression rules that merge findings for the same account into one archived finding each day for review
K: C
G: ## Single findings versus attack sequences
Classic GuardDuty findings each describe one suspicious behavior, for example an API call from an unusual location. Real attacks are multi-stage: credential misuse, then privilege escalation, then data access. Analysts had to correlate these manually.
## Extended Threat Detection
GuardDuty **Extended Threat Detection** correlates events and signals across data sources and over time within an account. When they form a known attack pattern it creates one **attack sequence** finding, for example `AttackSequence:IAM/CompromisedCredentials`, usually with Critical severity.
- The finding lists the signals, affected resources, and a timeline mapped to MITRE ATT&CK tactics.
- It is enabled automatically in every account that has GuardDuty turned on, at no additional cost; protection plans such as S3 Protection or EKS Protection widen the signals it can use.
W: Extended Threat Detection: it is the GuardDuty feature built to link related signals into one attack sequence finding with a timeline, which is exactly the correlation the SOC is doing by hand.
X: A=Trusted IP lists: they stop GuardDuty from generating findings for listed addresses. They do not group or correlate findings.
B=Malware Protection: it scans EBS volumes for malware when triggered. It adds findings but does not correlate multi-stage activity into one finding.
D=Suppression rules: they archive findings that match criteria so analysts do not see them. They do not merge findings or build a timeline, and hiding real signals is the opposite of the goal.
T: To see a multi-step attack as one finding, use GuardDuty Extended Threat Detection attack sequences; suppression and trusted IP lists only hide findings.
V: Amazon GuardDuty

@ SCS-C03 D1 T1.3 advanced troubleshooting
S: A team runs its whole workload in eu-west-1 and has an organization trail logging management events. It creates an EventBridge rule in eu-west-1 for "AWS API Call via CloudTrail" events with source aws.iam and eventName CreateAccessKey. Access keys are created, but the rule never matches. What is the cause?
A: EventBridge starts receiving IAM events after IAM Access Analyzer is enabled in the Region where the matching rule was created
B: The organization trail records IAM calls as data events, so CreateAccessKey does not reach EventBridge as a management event
C: IAM is a global service, so its CloudTrail events are delivered to EventBridge in us-east-1, where the rule must be created
D: CreateAccessKey is a read-only management event, which an EventBridge rule does not match unless it opts in to read-only events
K: C
G: ## How CloudTrail events reach EventBridge
EventBridge receives API calls recorded by CloudTrail as events with `detail-type` "AWS API Call via CloudTrail". Each event is delivered to the default event bus in the Region where the API call was processed.
## Global services
Some services are global: IAM, AWS STS global endpoint calls, and CloudFront, for example. Their API calls are processed in, and recorded as coming from, **us-east-1**. So a rule that watches `aws.iam` events must live in us-east-1, even if every workload runs elsewhere.
- Rule in us-east-1: `{"source": ["aws.iam"], "detail": {"eventName": ["CreateAccessKey"]}}`
- If the alert must go to a team in eu-west-1, the us-east-1 rule can forward to a bus or SNS topic in eu-west-1.
## Read-only calls
Read-only calls (Get, List, Describe) reach a rule only if it opts in with the state `ENABLED_WITH_ALL_CLOUDTRAIL_MANAGEMENT_EVENTS`, but CreateAccessKey is a write call, so that setting is irrelevant here.
W: Global service events land in us-east-1: IAM API calls are delivered to EventBridge in us-east-1, so a rule in eu-west-1 never sees them. Creating the rule in us-east-1 fixes it.
X: A=Access Analyzer required: Access Analyzer analyzes policies and access; it is not a prerequisite for EventBridge to receive CloudTrail events.
B=Data events: IAM API calls such as CreateAccessKey are management events, and the trail logs management events, so they are captured. The problem is the Region of the rule, not the trail.
D=Read-only event: CreateAccessKey changes state and is a write management event, so the read-only opt-in does not apply to it.
T: Rules for global-service API calls such as IAM belong in us-east-1; a rule in the workload Region never matches them.
V: Amazon EventBridge, AWS CloudTrail, AWS IAM

@ SCS-C03 D5 T5.3 advanced use-case
S: Which TWO actions reduce the risk of a KMS key being scheduled for deletion accidentally? (Select TWO)
A: Grant developers kms:* on the keys their applications use
B: Set the waiting period to the minimum of seven days on each key
C: Restrict kms:ScheduleKeyDeletion in key policies and SCPs
D: Record key IDs in developers' notes instead of an inventory
E: Alarm on ScheduleKeyDeletion events from CloudTrail
K: C,E
G: ## How KMS key deletion works
Deleting a KMS key is destructive: data encrypted under it can never be decrypted again. So KMS never deletes immediately. `ScheduleKeyDeletion` puts the key in **Pending deletion** for a waiting period of 7 to 30 days (default 30). During that time the key cannot be used, and `CancelKeyDeletion` restores it.
Two controls reduce the risk of an accidental or malicious deletion:
- **Prevent**: allow `kms:ScheduleKeyDeletion` only to a small key-administration role in key policies, and add an SCP that denies it to everyone else in the organization.
- **Detect**: CloudTrail records every `ScheduleKeyDeletion` call; an EventBridge rule on that event (or a CloudWatch alarm on a metric filter) notifies the security team so they can cancel in time.
## Example
A developer runs a cleanup script that schedules deletion of a production key. The SCP denies the call for that role. If an admin role makes the same mistake, the EventBridge rule pages on-call, who runs `CancelKeyDeletion` within the 30-day window.
W: C=Restrict ScheduleKeyDeletion: key policies and SCPs limit the deletion action to a few trusted administrators, so most principals cannot start a deletion at all.
E=Alarm on ScheduleKeyDeletion events: CloudTrail captures the request and an alert lets the team cancel the deletion during the waiting period.
X: A=kms:* for developers: it lets them schedule deletion, disable keys and change key policies on those keys, greatly increasing the chance of an accident.
B=Minimum seven-day waiting period: shortening the window leaves less time to notice and cancel a mistaken deletion; a longer period, such as the 30-day default, is safer.
D=Key IDs in developers' notes: where IDs are recorded has no effect on who can delete a key, and it makes keys harder to track and audit.
T: Protect KMS keys by limiting `kms:ScheduleKeyDeletion` (key policies and SCPs) and alerting on it so it can be cancelled during the waiting period.
V: AWS KMS, AWS CloudTrail

@ SCS-C03 D3 T3.3 advanced use-case
S: East-west traffic between VPCs must be inspected by IPS with centralized rules. Which design fits?
A: A VPC peering mesh with NACLs that permit the required ports between VPCs
B: A single EC2 firewall instance in one AZ that routes and inspects the flows
C: Security groups with tightly scoped rules on the instances in each connected VPC
D: Network Firewall in an inspection VPC behind a transit gateway with appliance mode
K: D
G: ## Centralized inspection with a transit gateway
East-west traffic is traffic between VPCs inside your own network. To inspect it in one place, route it all through an **inspection VPC**.
- Each spoke VPC attaches to a **transit gateway**. The spoke route table sends all traffic to the inspection VPC attachment.
- The inspection VPC holds **AWS Network Firewall** endpoints in each Availability Zone. Network Firewall supports stateful rules and Suricata-compatible IPS signatures, managed centrally (AWS Firewall Manager can push policies across accounts).
- **Appliance mode** on the inspection VPC attachment keeps both directions of a flow on the same Availability Zone, so the stateful firewall sees the request and the reply.
## Example
VPC A (`10.1.0.0/16`) talks to VPC B (`10.2.0.0/16`). The packet goes spoke to transit gateway to the firewall endpoint to the transit gateway to VPC B, and the reply returns through the same firewall endpoint thanks to appliance mode.
Network Firewall can now also attach natively to a transit gateway, so AWS manages the firewall's attachment without a separate inspection VPC. Both designs give central, managed inspection; peering, single instances and security groups do not.
W: Network Firewall in an inspection VPC with appliance mode: all inter-VPC flows pass one managed, highly available IPS with one rule set, and appliance mode keeps stateful inspection symmetric.
X: A=Peering mesh with NACLs: peering sends traffic directly between VPCs, so nothing passes a central inspection point, and NACLs filter addresses and ports without inspecting payloads.
B=One EC2 firewall in one AZ: a single instance is a single point of failure and a throughput bottleneck, and an AZ outage would cut or bypass inspection.
C=Scoped security groups: security groups are stateful allow lists on ports and addresses spread across instances; they do not inspect payloads for intrusion signatures and give no central rule set.
T: Central east-west IPS means routing every VPC through a Network Firewall inspection VPC on a transit gateway, with appliance mode for symmetric flows.
V: AWS Network Firewall, AWS Transit Gateway

@ SCS-C03 D6 T6.1 advanced troubleshooting
S: An administrator relies on the AWS Control Tower mandatory control that disallows changes to the encryption configuration of the S3 buckets Control Tower created in the Log Archive account. An engineer with an administrator role in that account nevertheless changes the default encryption of the Control Tower log bucket, even though the console shows the control as enabled on the Security OU. What is the most likely explanation?
A: Mandatory controls take effect on buckets created after the control, not on existing ones
B: The control for log bucket encryption is detective and reports changes after they occur
C: Controls on an OU apply to accounts that were enrolled after the control was enabled there
D: The account has drifted from its Control Tower baseline; repair the OU or the account
K: D
G: ## Control Tower drift
AWS Control Tower deploys its controls and baseline resources (SCPs, Config rules, roles, log buckets) and expects them to stay as it set them. When someone changes these resources outside Control Tower, the landing zone is in **drift**. Examples:
- an SCP created by Control Tower is edited or detached in the Organizations console,
- an enrolled account is moved to another OU directly in Organizations,
- a control-managed role or bucket policy is changed by hand.
The console can still show a control as enabled on the OU while the account no longer receives the policy. Drift is reported in the Control Tower console and through notifications to the Audit account.
## Scope of this control
The mandatory control is an SCP that denies `s3:PutEncryptionConfiguration` on the Control Tower-created log buckets only, for every principal except the Control Tower roles. It does not cover other buckets in other accounts; those need your own controls. Since January 2023 S3 always encrypts new objects (SSE-S3 at minimum), so such a change can switch the encryption type (for example from SSE-KMS to SSE-S3) but cannot turn encryption off.
## Fixing it
Re-register the OU, update or re-enroll the account, or reset the landing zone, depending on what drifted.
W: Account drift: the control is a preventive SCP, so if an administrator's change went through, the SCP is most likely not in effect for that account because something was changed outside Control Tower; repairing the OU or account restores it.
X: A=Only new resources: a preventive SCP evaluates each API call when it happens, so it blocks changes to existing buckets as much as to new ones.
B=Detective control: this mandatory control is preventive and denies encryption changes on the log buckets, so prevention is available and should have stopped the call.
C=Only later accounts: controls enabled on an OU apply to all enrolled accounts in it, existing and new.
T: When a preventive control seems ignored while the console says it is enabled, suspect drift: the SCP or the account placement was changed outside Control Tower.

@ SCS-C03 D5 T5.3 applied use-case
S: A security team requires that all secrets stored in AWS Secrets Manager for a regulated workload be encrypted with a customer managed KMS key that they control and can audit via CloudTrail, rather than the account's default Secrets Manager encryption key. Is this achievable, and how?
A: Not achievable; Secrets Manager encrypts secrets with the AWS managed key aws/secretsmanager
B: Achievable by editing the key policy of aws/secretsmanager so the team decides who can decrypt
C: Achievable by specifying a customer managed KMS key on the secret
D: Achievable by encrypting each value client-side with the KMS key and storing the ciphertext
K: C
G: ## How Secrets Manager encrypts secrets
Secrets Manager always encrypts the secret value with an AWS KMS key using envelope encryption. You choose which key:
- The **AWS managed key** `aws/secretsmanager` is used by default. AWS controls its key policy, so you cannot restrict or share it, and it cannot be used for secrets that other accounts must read.
- A **customer managed key** is one you create in KMS. You write its key policy, can enable or disable it, rotate it and grant cross-account access.
## Setting it up
Pass the key when creating or updating the secret, for example `aws secretsmanager create-secret --name app/db --kms-key-id alias/regulated-secrets ...`. The key policy must let the principals that read the secret use `kms:Decrypt` (usually limited with `kms:ViaService` = `secretsmanager.<region>.amazonaws.com`).
Every time Secrets Manager uses the key, a KMS event such as `Decrypt` or `GenerateDataKey` is written to CloudTrail, which gives the auditors their trail.
W: Customer managed KMS key on the secret: Secrets Manager accepts a customer managed key per secret (`KmsKeyId` on create or update), and because the team owns the key policy, they control who can decrypt and see each use in CloudTrail.
X: A=Not achievable: `aws/secretsmanager` is only the default key; the `KmsKeyId` parameter lets you pick a customer managed key.
B=Edit the AWS managed key policy: you can view the policy of an AWS managed key but cannot change it, rotate it or delete it, so the team cannot take control of `aws/secretsmanager`.
D=Client-side encryption: encrypting the value yourself adds a second, unmanaged layer and makes the secret unusable by services that read it directly; Secrets Manager already does the KMS encryption with the key you name.
T: Secrets Manager defaults to `aws/secretsmanager`, but you can name any customer managed key per secret to own its policy and audit its use.
V: Secrets Manager, KMS

@ SCS-C03 D4 T4.2 applied use-case
S: A multi-tenant SaaS platform runs on shared AWS infrastructure where each customer's resources are tagged with a project tag matching a project identifier. The platform wants engineers to only be able to access resources belonging to the project they are assigned to, without maintaining a separate IAM role per project as the number of projects grows into the hundreds. Which policy design best achieves this at scale?
A: A dedicated role and managed policy per project, created when each new project starts
B: Resource-based policies that list the assigned engineers' role ARNs on each resource
C: A few ABAC policies matching principal and resource project tags
D: One shared policy allowing access to any resource that carries a project tag
K: C
G: ## ABAC for multi-tenant isolation
In a shared environment where each customer's resources carry a tag such as `project=acme`, ABAC lets one policy enforce isolation for all tenants:
- Engineers get a principal tag for their assigned project (on the role, or as a session tag from the IdP).
- The policy allows actions only when `aws:ResourceTag/project` equals `${aws:PrincipalTag/project}`.
- Creation actions require `aws:RequestTag/project` to match the principal's tag, and tag-editing actions are denied, so nobody can move a resource into another project.
## Why it scales
Adding the 301st project means tagging its resources and the engineers assigned to it. No new roles, no policy edits. With a role per project, every new project adds a role, a policy and assignment work, and the number of roles grows without limit.
W: A few ABAC policies matching tags: principal and resource project tags are compared at request time, so isolation holds for any number of projects with a fixed, small set of policies.
X: A=Role and policy per project: this works functionally but grows linearly with projects, which is exactly the maintenance burden to avoid at hundreds of projects.
B=Resource policies listing engineers: not all resources support resource policies, size limits are reached quickly, and each assignment change requires editing many policies.
D=Shared policy on any project tag: it checks only that a tag exists, not that it matches the engineer's own project tag, so every engineer could reach every tenant's resources.
T: Multi-tenant isolation at scale comes from comparing principal and resource tags (ABAC), not from multiplying roles.

@ SCS-C03 D2 T2.2 advanced tradeoff
S: A security team is designing an automated remediation Step Functions workflow triggered by GuardDuty findings that will automatically revoke IAM credentials and isolate EC2 instances without any human approval. What is the primary risk this design introduces that a human-in-the-loop approval step would mitigate?
A: False positives could trigger disruptive actions with no human check
B: Each Step Functions execution can invoke a single Lambda function
C: GuardDuty findings must be exported to S3 before EventBridge sees them
D: Automated workflows run outside CloudTrail, which reduces auditability
K: A
G: ## Automated response and its risk
GuardDuty findings flow into EventBridge, and a rule can start a Step Functions workflow that, for example, attaches a deny-all policy to an IAM role, deactivates access keys or moves an EC2 instance into an isolation security group. These actions stop an attacker in seconds, but they also stop the real workload.
Detection is never perfect. A GuardDuty finding can be a **false positive** or benign activity, for example a new, legitimate admin tool calling unusual APIs or a vulnerability scanner the team runs itself.
## Adding a human approval
Step Functions supports a callback pattern (`.waitForTaskToken`): the workflow pauses, sends the token to an approver (by email via SNS, or a chat tool), and resumes only when someone approves or rejects.
- Collect evidence and snapshot volumes automatically.
- Ask for approval before destructive steps such as revoking production credentials or isolating a production instance.
- Auto-approve only well-understood, low-impact finding types.

G: ## The structure of a Cedar policy
Every Cedar policy has an effect and a scope:
- **Effect**: `permit` or `forbid`.
- **Scope**: `principal` (who), `action` (what) and `resource` (on what). Each can be a specific entity, such as `User::"alice"`, a group via `in`, or left open.

C=Stack name, resource type and timestamp: CloudFormation stacks and deployment times have no role in Cedar policy structure.
D=Security group, port range and route table: these are VPC network controls, unrelated to application authorization decisions.
T: A Cedar policy is permit or forbid over principal, action and resource, refined by when/unless conditions.

@ SCS-C03 D5 T5.3 applied troubleshooting
S: An application needs to encrypt a 25 MB file before storing it in S3. What is the correct pattern to encrypt data of this size using KMS?
A: Use the KMS Sign API instead of Encrypt for payloads larger than 4 KB
B: Request a Service Quotas increase for the KMS Encrypt plaintext size limit

D: Split the file into 4 KB chunks and call KMS Encrypt once for each chunk

G: ## Envelope encryption
The KMS `Encrypt` API accepts at most **4 KB** of plaintext. It is designed for small secrets and data keys, not files. For larger data, use **envelope encryption**:
- Call `GenerateDataKey` with your KMS key. KMS returns a data key in two forms: plaintext and encrypted under the KMS key.
- Encrypt the 25 MB file locally with the plaintext data key (for example AES-256-GCM), then erase the plaintext key from memory.
- Store the encrypted data key with the ciphertext, for example as object metadata or in the file header.
To decrypt, call `Decrypt` on the small encrypted data key and use the returned key locally. The AWS Encryption SDK and S3 client-side encryption libraries implement this pattern.
W: Envelope encryption: KMS protects only a small data key while the file itself is encrypted locally, so the size of the data never hits the 4 KB limit; the encrypted data key is stored with the object.
X: A=Sign API: `Sign` creates a digital signature with an asymmetric key; it does not encrypt data, and it has its own small message limit.
B=Quota increase: the 4 KB plaintext limit is a fixed limit of the API, not an adjustable quota.
D=4 KB chunks with Encrypt: roughly 6,000 KMS calls per file adds latency, cost and throttling risk, and it is not the intended pattern when a single data key would do.
T: KMS encrypts keys, not large files; use GenerateDataKey and encrypt the data locally.
