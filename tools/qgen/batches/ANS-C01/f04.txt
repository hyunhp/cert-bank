@ ANS-C01 D1 T1.2 advanced comparison
S: A company has application stacks deployed in us-east-1 and eu-west-1. They currently use geolocation routing but want to be able to gradually shift a small, controlled percentage of traffic from one Region to the other for a capacity test, without changing which physical Region actually serves which countries. Which Route 53 capability should they use instead?
A: Latency-based routing records for both Regions, each with an attached health check
B: Geoproximity routing with a bias value set on the records for each Region
C: Geolocation routing with a default record that points at the Region under test
D: Simple routing with one A record holding the IP addresses of both Regions
K: B
G: ## Route 53 routing policies that depend on location
- **Geolocation** routes by where the user is (continent, country, US state). A user in France always gets the record for France or Europe, all or nothing.
- **Latency-based** routes to the Region with the lowest measured latency for the user.
- **Geoproximity** routes by the physical distance between users and your resources. A **bias** value (from -99 to +99) grows or shrinks the area that is routed to a given Region, so you can move the boundary between Regions step by step.
Geoproximity was originally configured in Traffic Flow policies; today it can also be set directly on records.
## Shifting a small share of traffic
Raising the bias for eu-west-1 slightly moves the edge of its area outward, so a small group of users near the boundary starts going to eu-west-1. You tune the value up or down to control how much traffic moves.
W: Geoproximity with a bias: the bias moves the geographic boundary between the two Regions gradually, giving controlled, reversible shifts of traffic for a capacity test, which geolocation cannot do.
X: A=Latency-based routing with health checks: latency routing chooses the fastest Region per user, and health checks only remove unhealthy endpoints; there is no setting to move a chosen amount of traffic.
C=Geolocation with a default record: the default record only answers for locations that match no other record, so it moves users who were unmatched, not a small controlled share of the traffic.
D=Simple routing with both IP addresses: simple routing returns all values in random order with no weighting or location logic, so you cannot control how much traffic goes to each Region.
T: Gradually move the geographic line between Regions → geoproximity with bias. Split by exact percentages regardless of location → weighted routing.
V: Amazon Route 53

@ ANS-C01 D1 T1.2 advanced use-case
S: A company wants to block VPC workloads from resolving known malicious domains. Which feature fits?
A: Route 53 public DNSSEC signing
B: Route 53 traffic flow policies
C: Route 53 Resolver DNS Firewall
D: Route 53 Resolver query logging
K: C
G: ## Route 53 Resolver DNS Firewall
Every VPC has the Route 53 Resolver (the `.2` address, for example `10.0.0.2`) that answers DNS queries from workloads. DNS Firewall inspects those outbound queries before they are resolved.
- You build **domain lists**: your own (for example `*.bad-example.com`) or AWS managed lists of known malware and botnet domains.
- You put rules in a **rule group**; each rule matches a domain list and takes an action: `ALLOW`, `ALERT` or `BLOCK` (answering `NODATA`, `NXDOMAIN` or an override record).
- You associate the rule group with VPCs, directly or across accounts with Firewall Manager or AWS RAM.
Example: an instance infected with malware tries to resolve its command-and-control domain; the query matches a managed list, is blocked, and the malware cannot find its server.
W: Resolver DNS Firewall: it filters DNS queries leaving VPC workloads against domain lists, including AWS managed threat lists, and blocks the malicious ones.
X: A=Public DNSSEC signing: it signs a public hosted zone so resolvers can verify its answers were not tampered with. It protects your own domain's records, not what your workloads look up.
B=Traffic flow policies: a visual editor for routing policies (latency, geolocation, failover) for records you publish. It shapes answers for your domains; it does not filter queries to other domains.
D=Resolver query logging: it records the queries VPC workloads make, which helps find a lookup of a malicious domain afterwards, but it only logs and never blocks the resolution.
T: Blocking what VPC workloads can resolve is DNS Firewall; query logging only records lookups, and DNSSEC and traffic flow concern records you publish.
V: Amazon Route 53 Resolver

@ ANS-C01 D3 T3.1 advanced use-case
S: A company has two Direct Connect private virtual interfaces to the same VPC: a primary 10 Gbps connection and a backup 1 Gbps connection at a different location. They want traffic from the VPC toward on-premises to always prefer the primary connection, using the backup only when the primary is unavailable, without making any AWS-side configuration changes. Which technique should be applied on the customer router advertising routes over the backup virtual interface?
A: AS path prepending, repeating the on-premises ASN several extra times in those advertisements
B: A higher MED value on the advertisements that the customer router sends over the primary link
C: A lower local preference for the primary link, set in the customer router's inbound route policy
D: A more specific prefix, such as each network split into /25 halves, advertised on the 1 Gbps link
K: A
G: ## Which side controls which direction
BGP influences traffic in the opposite direction of the advertisement:
- What **you advertise** to AWS decides how AWS sends traffic **to** on-premises.
- What **AWS advertises** to you (plus your local settings) decides how you send traffic **to** AWS.
To steer VPC-to-on-premises traffic from your router alone, change the routes you send to AWS.
## AS path prepending
AWS prefers the shorter AS path when prefixes are equal. Prepending repeats your own ASN on the backup advertisement:
- primary sends `10.0.0.0/8` with AS path `65001`
- backup sends `10.0.0.0/8` with AS path `65001 65001 65001`
AWS then chooses the primary and falls back to the backup only when the primary route is withdrawn. AWS also offers local preference communities, which take priority over AS path length.
W: AS path prepending on the backup: it makes the backup route look longer to AWS, so the VPC's return traffic uses the 10 Gbps primary and moves to the backup only when the primary's routes disappear, all configured on the customer router.
X: B=Higher MED on primary: in BGP a lower MED is preferred, so raising the primary's MED would make it less attractive, the opposite of the requirement.
C=Lower local preference on primary: local preference is set on your router and only influences your own outbound choice toward AWS. It is not sent to AWS and cannot affect how the VPC routes to on-premises.
D=More specific prefix on the backup: longest-prefix match beats every other attribute, so /25 halves advertised on the backup would pull all matching traffic onto the 1 Gbps link.
T: To make AWS avoid a link, advertise a less attractive route over it (prepend or low local-preference community); a more specific prefix does the opposite.
V: Direct Connect

@ ANS-C01 D3 T3.2 applied use-case
S: An NLB-backed service intermittently fails. Which TWO data sources help diagnose connection issues? (Select TWO)
A: VPC Flow Logs on the NLB's network interfaces and on the targets
B: Route 53 change history for the public hosted zone holding the NLB alias
C: AWS Budgets forecast reports for data transfer and load balancer usage
D: The IAM credential report listing access key age for every account user
E: NLB CloudWatch metrics such as TCP reset counts and HealthyHostCount
K: A,E
G: ## Troubleshooting a Network Load Balancer
An NLB works at layer 4 and passes TCP, UDP or TLS connections to targets. When connections fail intermittently, look at two views.
- **NLB CloudWatch metrics**: `HealthyHostCount` and `UnHealthyHostCount` show targets failing health checks; `TCP_Target_Reset_Count` shows resets sent by targets, `TCP_Client_Reset_Count` resets from clients and `TCP_ELB_Reset_Count` resets generated by the NLB itself, for example after idle timeouts.
- **VPC Flow Logs** on the NLB's network interfaces and on the targets show whether flows are accepted or rejected, for example because a target's security group or a network ACL blocks the NLB or client IPs.
## Example
Failures line up with drops in `HealthyHostCount`, and flow logs show `REJECT` on the health check port for one subnet, pointing to a network ACL that was changed.
W: A=VPC Flow Logs: they reveal accepted and rejected connections on the NLB and target interfaces, which exposes filtering problems between clients, the NLB and targets.
E=NLB CloudWatch metrics: reset counts and healthy host counts show whether targets, clients or the load balancer are closing connections and when targets fail health checks.
X: B=Hosted zone change history: DNS record changes could matter only if the NLB name moved; this history shows no connection-level data about failures.
C=AWS Budgets forecasts: Budgets predicts and alerts on spend; it has no information about connections or targets.
D=IAM credential report: this lists users and the status of their passwords and access keys; it is unrelated to network connections through the NLB.
T: Diagnose NLB connection failures with its CloudWatch metrics (resets, healthy hosts) plus Flow Logs (accept/reject); billing, IAM and DNS history do not show connections.
V: Elastic Load Balancing

@ ANS-C01 D2 T2.2 advanced tradeoff
S: A company wants to share a Transit Gateway created in a central network account with 40 accounts spanning two different AWS Organizations after an acquisition, so all accounts can create attachments to it. What is a key constraint they must design around when using AWS RAM?
A: Own-organization accounts get the share automatically; acquired accounts are added by ID and must accept
B: The two Organizations must be merged into one before any RAM resource share can be created at all
C: Cross-organization RAM sharing is not supported, so each organization needs its own Transit Gateway
D: Transit Gateways cannot be shared through RAM at all; only VPC subnets support sharing with accounts
K: A
G: ## AWS RAM sharing inside and outside an organization
AWS RAM can share resources, including transit gateways, with different kinds of principals:
- **Inside your organization**: after enabling RAM sharing with AWS Organizations, you can share with the whole organization, an OU or individual accounts. No invitation is needed, and new accounts in the OU get access automatically.
- **Outside your organization**: you must list each **account ID**. Each account receives an **invitation** and must accept it before it can use the resource.
Not every resource type can be shared outside the organization (for example, subnets for VPC sharing cannot), but transit gateways can.
## After an acquisition
With two organizations, the network account can share with its own organization or OUs in one step, and must add the acquired company's accounts by ID; each of those accounts accepts the invitation and then creates its attachment.
W: Automatic inside the organization, invitations for the other one: sharing is seamless for the owner's organization, while accounts in the acquired organization must be listed by account ID and accept invitations, which the design must plan for until the organizations are merged.
X: B=Organizations must be merged first: RAM can share transit gateways with individual accounts outside the organization through invitations, so merging is not a prerequisite.
C=Cross-organization sharing not supported: transit gateways can be shared with external accounts; the only difference is the invitation and acceptance step, so a second transit gateway is not required.
D=Transit gateways cannot be shared: transit gateways are one of the most common RAM-shared resources, along with subnets, prefix lists and Route 53 Resolver rules.
T: RAM inside the organization is automatic; outside it, list account IDs and wait for each account to accept the invitation.
V: Resource Access Manager, Transit Gateway, AWS Organizations

@ ANS-C01 D3 T3.1 advanced troubleshooting
S: A Site-to-Site VPN tunnel to a branch office repeatedly drops during periods of low traffic, then re-establishes once traffic resumes. The on-premises device implements Dead Peer Detection (DPD) with aggressive timers, while AWS's side uses default DPD settings. What is the most likely cause and appropriate fix?
A: The customer gateway MTU is too large, so the DPD packets get fragmented and dropped in quiet periods
B: The device gives up on its peer too quickly when no data flows; relax its settings or send keepalives
C: Perfect forward secrecy is disabled, and AWS requires PFS to keep an idle tunnel up between rekeys
D: AWS endpoints do not answer DPD probes, so DPD should be turned off on the customer gateway entirely
K: B
G: ## Dead Peer Detection (DPD)
DPD is an IKE keepalive: when a peer has seen no traffic for a while, it sends an R-U-THERE message and expects an acknowledgment. If no reply arrives within its timeout, it declares the peer dead and clears the security associations (SAs).
- AWS endpoints support DPD. The default DPD timeout is 30 seconds, and the timeout action (clear, restart or none) is a tunnel option.
- DPD is triggered mostly during **idle periods**, because with steady traffic each side sees packets from the other.
## Why aggressive timers hurt
If the customer device probes every few seconds and gives up after one or two missed replies, a short delay or a lost UDP packet during a quiet period makes it tear down the tunnel. The tunnel comes back only when new traffic triggers renegotiation.
- Fixes: set DPD interval and retries to values compatible with AWS, adjust the AWS DPD timeout action, or keep traffic flowing (for example a periodic ping across the tunnel).
W: Device gives up too quickly when idle: the drops happen only when traffic stops, which is exactly when DPD runs, so relaxing the device's DPD interval and retries to match AWS, or keeping traffic flowing, stops the teardowns.
X: A=MTU fragments DPD: DPD messages are small IKE informational packets far below any normal MTU, so they are not fragmented. An MTU problem would also affect large packets during busy periods, not idle ones.
C=PFS required for idle tunnels: perfect forward secrecy only makes each rekey use fresh Diffie-Hellman keys. AWS supports it, but it has nothing to do with keeping an idle tunnel up.
D=AWS doesn't answer DPD: AWS endpoints do support DPD and let you configure its timeout and action; disabling it on the customer gateway would also hide real failures.
T: Tunnels that drop only when idle point to DPD mismatches; align DPD timers or keep traffic flowing instead of blaming MTU or PFS.
V: Site-to-Site VPN

@ ANS-C01 D3 T3.1 applied troubleshooting
S: A Site-to-Site VPN tunnel intermittently drops and re-establishes every 20-30 minutes, but the on-premises firewall logs show nothing unusual. The network engineer wants visibility into the IKE and IPsec negotiation phases from the AWS side to determine whether AWS is initiating the rekey or teardown. What should be enabled to get this visibility?
A: AWS CloudTrail data events for the VPN connection
B: Traffic Mirroring on the customer gateway's ENI
C: VPC Flow Logs on the virtual private gateway's ENI
D: Site-to-Site VPN logs published to CloudWatch Logs
K: D
G: ## What each logging source records
- **CloudTrail** records API calls such as `CreateVpnConnection` or `ModifyVpnTunnelOptions`: who changed configuration, not what the tunnel negotiated.
- **VPC Flow Logs** record IP traffic metadata (addresses, ports, bytes, accept/reject) on network interfaces.
- **Site-to-Site VPN logs** are published from the AWS VPN endpoints to CloudWatch Logs and record IKE and IPsec negotiation: phase 1 and phase 2 establishment, rekeys, Dead Peer Detection events, tunnel up/down reasons and error messages.
## Example
A tunnel that drops every 20-30 minutes often lines up with a rekey. With tunnel logging enabled per tunnel (in the tunnel options), the engineer can see whether AWS initiated a rekey, received a delete payload from the customer gateway, or declared the peer dead through DPD, and compare timestamps with the firewall.
W: Site-to-Site VPN logs: published from the AWS endpoints to CloudWatch Logs, they expose the AWS side of IKE and IPsec negotiation, including who initiated rekeys or teardowns, which is exactly what the engineer needs to explain periodic drops.
X: A=CloudTrail data events: CloudTrail captures API activity, and VPN connections have no data events. Tunnel negotiation happens on the data plane and never appears in CloudTrail.
B=Traffic Mirroring on the CGW: the customer gateway is an on-premises device, not an AWS network interface, so it cannot be a mirror source. Mirroring copies packets; it does not decode IKE state changes.
C=Flow Logs on the VGW: a virtual private gateway has no customer-visible network interface for flow logs, and flow logs only record traffic summaries, not IKE/IPsec negotiation events.
T: For IKE and IPsec negotiation details from AWS's side, enable Site-to-Site VPN logs; CloudTrail and flow logs record API calls and traffic, not tunnel negotiation.
V: Site-to-Site VPN, CloudWatch

@ ANS-C01 D4 T4.3 advanced use-case
S: A company needs to encrypt traffic between EC2 instances in a VPC without application changes, on supported instance types. Which fact applies?
A: Traffic between instances is encrypted only when it is sent to their public IP addresses
B: VPC traffic between instances is never encrypted, so TLS must be added to every application
C: Traffic between instances is encrypted only when it is routed through a NAT gateway
D: Their Nitro hardware encrypts those packets automatically, with nothing to configure
K: D
G: ## Encryption provided by the Nitro System
Many current EC2 instance types are built on the AWS Nitro System. When two instances of **supported types** communicate, the Nitro hardware automatically encrypts the traffic between them in transit, with no configuration and no change to the operating system or application.
- It applies to traffic between supported instances within the same VPC or across peered VPCs, as long as the traffic does not pass through a virtual network device or service such as a load balancer or transit gateway; the EC2 documentation lists the exact conditions.
- Encryption is offloaded to the Nitro hardware, so it uses no instance CPU and AWS states there is no performance impact.
- If either side is an unsupported instance type, the traffic is not covered, so check the list of supported instance types in the EC2 documentation.
## When you still need TLS
If you need end-to-end protection you control, or traffic crosses unsupported instances, a load balancer, a transit gateway or the internet, applications still add TLS or use IPsec.
W: Automatic Nitro encryption: traffic between supported Nitro-based instance types in the VPC is encrypted by the underlying hardware, which satisfies the requirement without any application change.
X: A=Only via public IP addresses: a public IP only makes an instance reachable from the internet. It does not add encryption, and Nitro encryption works on private addresses inside the VPC.
B=Never encrypted, TLS required: this ignores the automatic Nitro in-transit encryption between supported instance types; TLS remains an option but is not the only one, and it would need application changes.
C=Routing through a NAT gateway: a NAT gateway translates addresses for outbound connections; it does not encrypt traffic, and instance-to-instance traffic in a VPC does not pass through it.
T: For transparent instance-to-instance encryption without code changes, use supported Nitro instance types; NAT and public IPs never encrypt.
