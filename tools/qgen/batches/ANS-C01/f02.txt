@ ANS-C01 D4 T4.1 applied troubleshooting
S: A network engineer adds a new NACL rule with rule number 50 that denies inbound traffic from a specific malicious CIDR block. Shortly after, legitimate traffic from an unrelated, previously allowed CIDR range starts being blocked as well. The existing allow rule for that legitimate range has rule number 100. What is the most likely explanation?
A: The NACL uses the first matching entry by number, and the deny prefix overlaps that range.
B: The new entry was added to the outbound list, which also filters the partner's inbound requests.
C: Adding a deny rule switches the NACL default action for unmatched traffic from allow to deny.
D: NACLs combine the matching entries and apply the most restrictive action to the packet.
K: A
G: ## How NACL rules are evaluated
A network ACL has numbered rules for each direction. For every packet, AWS checks the rules **from the lowest number upward** and applies the **first rule that matches**; later rules are not considered. If nothing matches, the final `*` rule denies the packet.
## Why a new low-numbered deny can hit good traffic
The new deny rule 50 is checked before the allow rule 100. If its CIDR is broader than intended or overlaps the legitimate range, legitimate packets match rule 50 first and are denied; rule 100 is never reached for them.
Example: the intent was to block `203.0.113.0/26`, but the rule was entered as `203.0.0.0/16`, which also contains the partner range `203.0.200.0/24` allowed by rule 100.
Fix: correct the deny CIDR to the exact malicious range, and leave gaps in numbering (10, 20, 30) so specific rules can be placed carefully.
W: First match in ascending order: rule 50 is checked before rule 100, so any address inside the new deny prefix is dropped there; when that prefix overlaps the legitimate range, the allow at rule 100 is never reached for that traffic.
X: B=Added to the outbound list: each NACL rule belongs to one direction, and outbound rules do not filter inbound requests. An outbound rule 50 could not block the inbound traffic from the legitimate range, yet that traffic is now being blocked.
C=Default action switched: adding a deny rule changes nothing about other rules or the default `*` rule, which is always a deny and cannot be edited; the legitimate traffic also matched rule 100, so it never reached the default anyway.
D=Most restrictive match wins: NACLs do not combine matching rules; they stop at the first match by rule number. Evaluating all rules together describes security groups, which only have allow rules.
T: NACLs are first-match by rule number; a low-numbered deny whose CIDR overlaps an allowed range blocks that range.
V: Amazon VPC

@ ANS-C01 D1 T1.2 advanced use-case
S: A company must protect its public DNS zone against spoofed responses. Which feature fits?
A: DNSSEC signing on the Route 53 hosted zone
B: Route 53 Resolver DNS Firewall rule groups
C: Route 53 weighted routing across record sets
D: Moving the records to a private hosted zone
K: A
G: ## What DNSSEC protects against
In DNS spoofing or cache poisoning, an attacker gets a resolver to accept a forged answer, for example sending `www.example.com` to the attacker's IP. **DNSSEC** adds digital signatures to DNS records so validating resolvers can check that an answer really came from the zone owner and was not altered.
## How it works in Route 53
- You enable DNSSEC signing on the public hosted zone. Route 53 signs records with a zone-signing key it manages.
- You create a key-signing key (KSK) backed by an asymmetric customer managed key in AWS KMS (created in `us-east-1`).
- You add a DS record for the KSK to the parent zone (at the registrar), which builds the chain of trust from the root.
Resolvers that validate DNSSEC then reject responses whose signatures do not match.
W: DNSSEC signing: signed records let validating resolvers verify the authenticity and integrity of every answer from the public zone, which is exactly protection against spoofed responses.
X: B=DNS Firewall: DNS Firewall filters the queries that resources in your VPCs send through the Route 53 Resolver, blocking or allowing domains. It does not sign or authenticate the answers the internet receives from your public zone.
C=Weighted routing: weighted records split traffic between endpoints by ratio. They change which answer is returned, not whether a resolver can verify it is genuine.
D=Moving to a private hosted zone: private zones are resolvable only inside associated VPCs, so the public names would stop working for internet users; it removes the service instead of protecting it.
T: To prove public DNS answers are authentic, sign the zone with DNSSEC; DNS Firewall controls outbound queries from VPCs instead.
V: Amazon Route 53

@ ANS-C01 D1 T1.5 applied use-case
S: Which TWO options provide backup connectivity if a single Direct Connect connection fails? (Select TWO)
A: A larger secondary CIDR block added to the VPC
B: A second internet gateway attached to the same VPC
C: Additional NAT gateways, one in each Availability Zone
D: Another Direct Connect link at a second location
E: An IPsec Site-to-Site VPN over the internet
K: D,E
G: ## Planning for a Direct Connect failure
A single Direct Connect connection is a single point of failure: the port, the device, the location or the carrier circuit can go down. Common backups:
- **A second Direct Connect connection at another location**: keeps dedicated bandwidth and predictable latency during a failure. This is the basis of the high resiliency models.
- **A Site-to-Site VPN as backup**: IPsec over the internet to the same virtual private gateway, transit gateway or Cloud WAN. It is cheaper but a standard tunnel carries only about 1.25 Gbps.
With BGP on both paths, AWS prefers Direct Connect routes over VPN routes for the same prefix, so the VPN is used only when the Direct Connect routes disappear.
W: D=Another link at a second location: an independent connection on a different device and site keeps private dedicated connectivity when the first fails.
E=Site-to-Site VPN backup: a VPN over the internet gives a separate path that BGP falls back to automatically when the Direct Connect routes are withdrawn.
X: A=Larger secondary CIDR: it only adds address space inside the VPC; it creates no additional path between on premises and AWS.
B=Second internet gateway: a VPC can have only one internet gateway attached, and an internet gateway serves internet traffic, not private hybrid connectivity.
C=More NAT gateways: NAT gateways let private subnets start outbound connections; they do not carry on-premises traffic into the VPC or replace a Direct Connect link.
T: Back up Direct Connect with another Direct Connect connection at a different location or a Site-to-Site VPN; VPC-internal components add no hybrid path.
V: AWS Direct Connect, AWS Site-to-Site VPN

@ ANS-C01 D3 T3.2 advanced use-case
S: A network team must analyze traffic that passes through transit gateways and between Availability Zones. Which TWO logging enhancements help? (Select TWO)
A: AWS Trusted Advisor checks for networking best practices
B: CloudTrail Insights on the transit gateway API calls
C: A custom VPC flow log format with az-id and flow-direction
D: S3 Storage Lens dashboards for the bucket holding the logs
E: Flow logs created on the transit gateway resource itself
K: C,E
G: ## Richer flow logs
Default VPC Flow Log records include addresses, ports, protocol and action. Two enhancements help with transit and multi-AZ analysis.
- **Custom log formats** add fields such as `az-id` (the Availability Zone ID of the interface), `flow-direction` (`ingress` or `egress`), `traffic-path` (for example, through an internet gateway or transit gateway), `pkt-srcaddr` and `pkt-dstaddr` (original addresses behind NAT).
- **Transit Gateway Flow Logs** capture flows at the transit gateway itself, with fields for the transit gateway attachment IDs and the source and destination VPC or AZ, so you can see traffic between attachments without enabling flow logs in every VPC.
## Example
A team investigating cross-AZ data transfer costs adds `az-id` to VPC flow logs and enables TGW flow logs, then groups bytes by source and destination AZ.
W: C=Custom flow log fields such as `az-id` and `flow-direction`: these add AZ and direction context to each record, which is exactly what cross-AZ analysis needs.
E=Transit Gateway Flow Logs: they record flows passing through the transit gateway with attachment details, giving visibility into transit traffic in one place.
X: A=Trusted Advisor checks: Trusted Advisor gives best-practice recommendations on cost, security and limits; it records no traffic flows.
B=CloudTrail Insights: Insights detects unusual rates of management API calls; API activity on the transit gateway says nothing about packets crossing it.
D=S3 Storage Lens: Storage Lens reports S3 storage usage and activity metrics for buckets; it does not analyze network flows between VPCs or AZs.
T: For transit and cross-AZ traffic analysis, add custom flow log fields and enable Transit Gateway Flow Logs; the other tools report on APIs, cost advice or storage.
V: AWS Transit Gateway, Amazon VPC

@ ANS-C01 D4 T4.1 applied use-case
S: Security groups in a VPC must allow traffic from instances in a peered VPC in the same Region by referencing their security group. Is this possible?
A: No; across a peering connection, rules must use the peer VPC's CIDR ranges instead
B: Yes, but this works for inter-Region peering and not for peering within one Region
C: Yes; over an active peering connection, a rule can use the peer's group as its source
D: Yes, after the peer VPC's security group is shared with the account through AWS RAM
K: C
G: ## Referencing security groups across a peering connection
A security group rule can use another security group as its source instead of a CIDR, for example allow TCP `5432` from `sg-0abc1234`. The rule then follows whichever instances carry that group, even as their IPs change.
For **VPC peering in the same Region**, rules can reference security groups in the peer VPC, including one in another account (written as `account-id/sg-id`). The peering connection must be active and routes must exist in both route tables.
## Example
VPC A (app servers in `sg-app`) is peered with VPC B (database). The database security group in VPC B allows port `5432` from `sg-app`. New app instances with `sg-app` are allowed automatically.
For peering across Regions, security group references are not available; rules use CIDR blocks of the peer instead.
W: Same-Region peer security group references: over an active same-Region peering connection, a security group rule can use a group from the peer VPC (even in another account) as its source.
X: A=Peer CIDR ranges required: CIDR-based rules are what cross-Region peering needs, but same-Region peering supports security group references.
B=Inter-Region only: this reverses the rule; cross-Region peering does not support security group references, while same-Region peering does.
D=Share through AWS RAM first: sharing security groups with RAM is a feature for shared VPC participants. Referencing a group across a peering connection needs no RAM share, only the active peering and the group ID (with the account ID for another account).
T: Security group references work over same-Region peering; across Regions you must use CIDRs.

@ ANS-C01 D1 T1.3 applied use-case
S: An application needs WebSocket connections behind a load balancer with HTTP routing rules. Which option fits?
A: Gateway Load Balancer (GWLB)
B: Application Load Balancer (ALB)
C: VPC endpoint service (PrivateLink)
D: Classic Load Balancer (CLB)
K: B
G: ## WebSocket and load balancers
A WebSocket connection starts as an HTTP request with an `Upgrade: websocket` header and then stays open as a long-lived, two-way connection over the same TCP session. The load balancer must understand the HTTP upgrade and keep the connection open.
## Which load balancer does what
- **Application Load Balancer (ALB)**: layer 7. Natively supports WebSocket on HTTP and HTTPS listeners and routes by host header, path, HTTP headers, methods, query strings or source IP. Example: `/chat/*` to a WebSocket target group, `/api/*` to REST services.
- **Network Load Balancer**: layer 4. Can pass WebSocket traffic as TCP, but cannot inspect HTTP, so no path or host routing.
- **Gateway Load Balancer**: sends packets to third-party appliances such as firewalls using GENEVE.
- **Classic Load Balancer**: previous-generation, without listener rules for host or path routing.
W: Application Load Balancer: it handles the WebSocket upgrade natively and offers HTTP listener rules for routing, meeting both requirements in one managed load balancer.
X: A=Gateway Load Balancer: it transparently inserts virtual appliances into the traffic path at layer 3. It does not terminate HTTP or provide HTTP routing rules for applications.
C=VPC endpoint service: an endpoint service exposes a service to other VPCs through PrivateLink, fronted by a Network or Gateway Load Balancer. It is a connectivity feature, not an HTTP routing load balancer.
D=Classic Load Balancer: this legacy load balancer has no content-based routing rules, so it cannot route by path or host, and AWS recommends current-generation load balancers instead.
T: Need WebSockets plus HTTP routing rules: ALB; layer 4 or legacy load balancers cannot route on HTTP content.
V: Elastic Load Balancing

@ ANS-C01 D4 T4.3 applied use-case
S: An internal REST API in Amazon API Gateway must be callable from three specific VPCs, over private network paths and from nowhere else. Which TWO controls fit? (Select TWO)
A: An internet gateway and public subnets in each consumer VPC
B: The private endpoint type plus a resource policy on aws:SourceVpce
C: The regional endpoint type plus an IP allow list of the VPC CIDRs
D: A public Route 53 alias record that points to the API's endpoint
E: An execute-api interface endpoint in each of the consumer VPCs
K: B,E
G: ## Private REST APIs in API Gateway
An Amazon API Gateway REST API can use the **private** endpoint type. A private API has no internet-facing endpoint: it can be invoked only through an **interface VPC endpoint** for the `execute-api` service, which places network interfaces with private IPs in the consumer VPC.
## Two layers of control
- The **interface endpoint** gives a VPC a network path to API Gateway. Only VPCs with such an endpoint can reach private APIs at all.
- The API's **resource policy** decides which endpoints may call this API. A typical policy denies `execute-api:Invoke` unless `aws:SourceVpce` equals an approved endpoint ID (or `aws:SourceVpc` equals an approved VPC). A private API needs a resource policy that allows access, otherwise calls are denied.
Example: VPCs A and B each have an `execute-api` endpoint; the resource policy allows only `vpce-0aaa` and `vpce-0bbb`, so a third VPC with its own endpoint is still refused.
W: B=Private API with a resource policy: the private endpoint type removes internet exposure, and a resource policy that checks `aws:SourceVpce` limits invocation to the listed VPC endpoints, enforcing which consumers are allowed.
E=Interface endpoints for execute-api: they provide the private network path from each allowed VPC to API Gateway, which is the only way a private API can be reached.
X: A=Internet gateway and public subnets: an internet gateway gives public internet access. Private APIs are not reachable over the internet, so it adds exposure without providing the needed path.
C=Regional endpoint with an IP allow list: the API would still have an internet-facing endpoint, and requests from a VPC reach it over the internet from NAT or public IP addresses, so private VPC CIDRs never appear as the source and the allow list cannot express "only these VPCs".
D=Public alias record: DNS only maps a name to an address. It enforces no access control and cannot make a private API reachable from outside the allowed VPC endpoints.
T: Private API access is two parts: an `execute-api` interface endpoint for the network path, and a resource policy that allows only the approved endpoints or VPCs.
V: Amazon API Gateway, AWS PrivateLink

@ ANS-C01 D4 T4.1 applied use-case
S: A media company runs a public application on an Application Load Balancer and wants AWS Shield Advanced to engage the AWS Shield Response Team (SRT) proactively when an attack makes the application unhealthy, without waiting for the company to open a support case. Which TWO actions are required for proactive engagement to work? (Select TWO)
A: Grant the SRT read access to the S3 bucket that receives the AWS WAF web ACL logs
B: Turn on automatic application layer DDoS mitigation for the protected resource
C: Create an AWS Firewall Manager Shield Advanced policy that covers the resource
D: Register emergency contacts and turn on the feature for the Shield subscription
E: Associate a Route 53 health check for the application with the protected resource
K: D,E
G: ## What proactive engagement is
With **Shield Advanced proactive engagement**, the SRT contacts you when Shield detects an event that affects the availability of a protected resource, instead of waiting for you to open a case. Two things are needed for the SRT to know an event matters and to reach you.
- **Health-based detection**: the protected resource is associated with a Route 53 health check. When the health check turns unhealthy during an attack, Shield treats it as impact and can escalate.
- **Contacts**: you register emergency contacts (email, phone number, notes) and enable proactive engagement.
## What is optional
Automatic application layer mitigation, SRT access to logs or roles for support cases, and Firewall Manager management are useful, but proactive engagement does not depend on them.
W: D=Emergency contacts: with the contacts registered and proactive engagement enabled, the SRT has a way to reach you when the health check fails.
E=Health check association: without it, Shield cannot use application health to decide that an event is affecting the resource.
X: A=SRT access to WAF logs: access lets the SRT analyze traffic and write mitigations when you engage them, but it does not trigger or enable proactive contact.
B=Automatic application layer mitigation: this feature lets Shield create and manage WAF rules against layer 7 floods. It is separate from proactive engagement and is not a prerequisite.
C=Firewall Manager policy: Firewall Manager can enroll many resources at scale, but a resource protected manually in Shield Advanced can use proactive engagement without any Firewall Manager policy.
T: Proactive engagement from the SRT needs a Route 53 health check on the protected resource and registered emergency contacts with the feature enabled.
V: AWS Shield, Amazon Route 53
