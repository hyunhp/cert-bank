@ ANS-C01 D1 T1.4 advanced troubleshooting
S: Traffic between two VPC attachments on a Transit Gateway is intermittently failing, and the network team suspects packets are being dropped at the Transit Gateway itself rather than within either VPC. Which logging capability should be enabled to directly observe accepted and rejected traffic at the Transit Gateway level?
A: AWS CloudTrail management events recorded for the Transit Gateway
B: VPC Flow Logs on both VPCs, which capture TGW traffic natively
C: Transit Gateway Flow Logs delivered to CloudWatch Logs or S3
D: Route 53 Resolver query logging enabled for the TGW attachments
K: C
G: ## Why VPC flow logs are not enough for a transit gateway
VPC Flow Logs are captured on network interfaces inside a VPC. They show traffic entering or leaving the transit gateway attachment ENIs in that VPC, but not what the transit gateway itself did with a packet after it arrived.
## Transit Gateway Flow Logs
**Transit Gateway Flow Logs** are enabled on the transit gateway (or on individual attachments) and record the flows that pass through it. Besides addresses, ports, bytes and packets, records identify the source and destination attachments and include drop counters such as:
- `packets-lost-no-route` and `packets-lost-blackhole` (routing problems),
- `packets-lost-mtu-exceeded` and `packets-lost-ttl-expired`.
Logs go to CloudWatch Logs, S3 or Firehose.
Example: flows from the VPC A attachment to the VPC B attachment showing `packets-lost-blackhole` point at a blackhole route in a TGW route table.
W: Transit Gateway Flow Logs: they are captured at the transit gateway, so they show which attachment traffic entered and left through and whether the TGW dropped it, which is exactly the suspected failure point.
X: A=CloudTrail management events: these record API calls such as creating a route or attachment. They show configuration changes, not individual packets or drops.
B=VPC Flow Logs capture TGW traffic: VPC flow logs only see the interfaces in each VPC. A packet dropped inside the transit gateway after leaving VPC A never shows up as a drop in either VPC's log.
D=Resolver query logging: this records DNS queries, not IP traffic, and it is associated with VPCs, not with transit gateway attachments.
T: To see what happens inside the transit gateway, log at the transit gateway; VPC flow logs only see the edges.
V: AWS Transit Gateway

@ ANS-C01 D1 T1.1 advanced use-case
S: A game studio wants to expose thousands of backend game server instances behind a small set of static IP addresses, preserve the original client IP address end to end, and map incoming client connections directly to specific instance IP:port combinations without deploying a load balancer in front of the fleet. Which Global Accelerator feature satisfies this?
A: A standard accelerator with client affinity set to SOURCE_IP on its listener
B: A custom routing accelerator with subnet endpoints that map ports to each instance
C: A standard accelerator with Elastic IP endpoints and endpoint health checks disabled
D: A standard accelerator with a Network Load Balancer endpoint in each Region
K: B
G: ## The two kinds of Global Accelerator
AWS Global Accelerator gives you static anycast IP addresses at AWS edge locations and carries user traffic over the AWS backbone to your endpoints.
- A **standard accelerator** spreads traffic across healthy endpoints (Application or Network Load Balancers, EC2 instances, Elastic IP addresses) using weights, Region traffic dials and health checks. You do not choose which endpoint a given user reaches.
- A **custom routing accelerator** maps ranges of listener ports to specific EC2 instance IP:port destinations inside VPC subnets. Your application (for example a matchmaking service) decides which server a player should join and hands the player the static IP plus the port that maps to that server.
## Why games use custom routing
Multiplayer games need players of the same match on the same server. That needs a deterministic "this port goes to that server" mapping, not a load balancer that picks a server for you.
W: Custom routing accelerator: it maps listener port ranges to individual instance IP:port destinations, so thousands of game servers sit behind a few static IPs, each client connection goes to the exact server your matchmaker chose, and no load balancer is needed.
X: A=SOURCE_IP client affinity: affinity only keeps the same client going to the same endpoint once one has been picked. It does not let you choose which game server a player lands on.
C=Elastic IP endpoints: a standard accelerator still distributes traffic across its endpoints by weight and health. It has no way to map a port to one particular instance, so players of one match could land on different servers.
D=Network Load Balancer endpoint: the NLB picks the target itself, and the question explicitly rules out a load balancer in front of the fleet.
T: Load-balance to any healthy endpoint → standard accelerator. Send each user to one specific instance and port → custom routing accelerator.
V: AWS Global Accelerator

@ ANS-C01 D4 T4.1 advanced use-case
S: A company needs intrusion prevention with Suricata-compatible rules for traffic between VPCs. Which design fits?
A: Network Firewall in an inspection VPC with TGW routing and appliance mode
B: A single EC2 proxy instance in one AZ that forwards the inter-VPC traffic
C: Network ACLs on each subnet with stateless rules that permit the required ports
D: Security groups on each instance that reference the CIDR blocks of the other VPCs
K: A
G: ## Centralized IPS between VPCs
AWS Network Firewall supports **Suricata-compatible** stateful rules, so it can act as an intrusion prevention system that drops traffic matching attack signatures. A common design for traffic between VPCs:
- Each workload VPC attaches to a **transit gateway**.
- Transit gateway route tables send inter-VPC traffic to an **inspection VPC** that has firewall endpoints in each AZ.
- After inspection the traffic returns to the transit gateway and on to the destination VPC.
## Why appliance mode
Without appliance mode, the transit gateway may pick a different AZ for the return direction, so the reply reaches a firewall endpoint that never saw the request. A stateful firewall drops that asymmetric flow. Enabling **appliance mode** on the inspection VPC attachment keeps both directions of a flow in the same AZ.
W: Network Firewall inspection VPC with TGW and appliance mode: it runs Suricata-compatible IPS rules centrally for all inter-VPC traffic, and appliance mode keeps flows symmetric so stateful inspection works.
X: B=Single EC2 proxy in one AZ: one instance is a single point of failure and a throughput bottleneck, and a proxy is not a Suricata-based IPS.
C=Stateless NACL rules: NACLs filter only by address, port and protocol, so they cannot evaluate Suricata IPS signatures or look into payloads.
D=Security groups referencing CIDRs: security groups filter by address, port and group; they allow or deny connections but provide no intrusion detection or prevention.
T: Suricata-compatible IPS between VPCs means Network Firewall in an inspection VPC behind a transit gateway, with appliance mode for symmetric flows.

@ ANS-C01 D3 T3.1 advanced use-case
S: Traffic between an EC2 instance and the internet through an internet gateway fails with large packets after jumbo frames were enabled. What is the explanation?
A: Jumbo frames must also be enabled on the internet gateway's route table entry
B: Traffic leaving the VPC through an internet gateway is limited to 1500 bytes MTU
C: Internet gateways split outbound packets into 64-byte segments before forwarding
D: Internet gateways accept packets of up to 576 bytes and drop larger ones
K: B
G: ## MTU differs by path
An instance can use a **9001-byte** MTU with other instances in the same VPC, but not every path supports that size.
- Traffic that leaves through an **internet gateway** is limited to **1500 bytes**; Site-to-Site VPN is lower still (1446 bytes). Paths inside AWS such as inter-Region VPC peering and transit gateways allow up to 8500 bytes, so the internet path is where jumbo frames clearly break.
- If an instance sends a large packet with the Don't Fragment bit set, the path must return an ICMP "fragmentation needed" message so the sender can lower its size (path MTU discovery). If that ICMP message is blocked, for example by a security group or network ACL, large packets are silently lost.
## Example
After switching `eth0` to 9001 bytes, an instance can still ping a website but downloads stall. Allowing ICMP "destination unreachable, fragmentation needed" in, or setting the MTU to 1500 for internet-bound routes, fixes it.
W: 1500-byte limit through the internet gateway: 9001-byte frames are valid only inside the VPC and the internet path allows 1500 bytes, so large packets headed to the internet must be 1500 bytes or smaller, and the failures come from exceeding that limit.
X: A=Jumbo frames on the route entry: route tables and internet gateways have no MTU setting to enable. The path through an internet gateway supports 1500 bytes, so jumbo frames are the cause of the problem, not something missing from the route.
C=64-byte fragmentation: internet gateways do not split packets into 64-byte pieces; oversized packets with Don't Fragment set are dropped with an ICMP message instead.
D=576-byte limit: internet gateways carry normal 1500-byte packets; if 576 were the limit, almost all internet traffic from AWS would fail.
T: 9001-byte jumbo frames work only inside the VPC; anything leaving through an internet gateway must fit 1500 bytes, so keep path MTU discovery working.
V: Amazon VPC

@ ANS-C01 D3 T3.1 applied use-case
S: Within a VPC, instances exchange large data sets and the team wants to reduce packet overhead. What MTU do most current-generation instances support inside a VPC?
A: 576 bytes
B: 65,535 bytes
C: 1,024 bytes
D: 9,001 bytes
K: D
G: ## Jumbo frames in a VPC
A **jumbo frame** is an Ethernet frame larger than the standard 1500-byte payload. Most current-generation EC2 instance types support an MTU of **9001** bytes.
- A bigger MTU means fewer packets for the same data, so less header overhead and fewer per-packet operations, which helps bulk transfers.
- 9001 bytes applies to traffic **within a VPC**. Other paths have smaller limits: inter-Region VPC peering and transit gateway attachments (VPC, Direct Connect and peering, including inter-Region peering) support up to 8500 bytes, traffic through an internet gateway is limited to 1500 bytes, and Site-to-Site VPN to 1446 bytes.
## Example
Two instances in the same VPC copying a 500 GB dataset use 9001-byte packets, sending about one sixth as many packets as with 1500 bytes. You can check a Linux instance's setting with `ip link show eth0`.
W: 9001 bytes (jumbo frames): this is the MTU that most current-generation instances support for traffic inside a VPC, which reduces packet overhead for large transfers.
X: A=576 bytes: 576 is the minimum datagram size every IPv4 host must accept, not a VPC maximum; using it would greatly increase overhead.
B=65535 bytes: 65,535 is the largest possible IPv4 packet length field value, not a supported MTU on any VPC network path.
C=1024 bytes: 1024 is not an Ethernet or VPC MTU value at all; it is smaller than even the standard 1500-byte MTU.
T: Inside a VPC, current instances can use 9001-byte jumbo frames; paths leaving the VPC are smaller.

@ ANS-C01 D2 T2.2 advanced use-case
S: A company attaches 50 VPCs to a transit gateway. Production VPCs must reach shared services but not development VPCs. Which configuration fits?
A: One route table associated with each attachment and propagating the routes of each VPC
B: Separate prod and dev route tables, each propagating the shared services routes
C: Network ACLs in the shared services VPC that deny production traffic by default
D: Security groups on each instance that block the development CIDR ranges manually
K: B
G: ## Associations and propagations
Each transit gateway attachment has two independent relationships with route tables:
- **Association**: the one route table used to look up destinations for traffic arriving from that attachment.
- **Propagation**: the route tables into which the attachment's CIDRs are automatically installed.
A VPC can reach another only if the route table it is associated with contains a route to that VPC.
## A segmentation example
- `prod-rt`: associated with production VPCs; receives propagations from shared services (and production if prod must talk to prod).
- `dev-rt`: associated with development VPCs; receives propagations from shared services only.
- `shared-rt`: associated with shared services; receives propagations from both production and development so replies can return.
Production VPCs never learn development routes, so they cannot reach each other, while both reach shared services.
W: Separate route tables with shared-service propagations: associations and propagations isolate production from development at the routing layer while giving both a path to shared services.
X: A=One shared route table: every VPC learns every other VPC's routes, creating full any-to-any reachability that violates the isolation requirement.
C=NACLs denying production: denying production traffic in shared services blocks exactly the access production needs, and it does nothing to separate production from development.
D=Security groups on each instance: manual per-instance rules across 50 VPCs are fragile and easy to miss, and the routes still exist; segmentation belongs in transit gateway route tables.
T: Transit gateway segmentation is done with separate route tables and selective propagation, not with one flat table or per-instance filters.
V: AWS Transit Gateway

@ ANS-C01 D1 T1.6 advanced use-case
S: A company has 200 VPCs in one Region across many accounts and wants transitive routing with segmentation between environments. Which design fits?
A: A transit gateway with separate route tables for each environment
B: A full mesh of VPC peering connections between the 200 VPCs
C: One VPC with 200 subnets shared with the accounts through RAM

A **transit gateway** is a Regional router that VPCs, VPNs and Direct Connect gateways attach to. It is transitive: any attachment can reach any other if the route tables allow it. It can be shared with other accounts through AWS RAM and supports thousands of attachments.
