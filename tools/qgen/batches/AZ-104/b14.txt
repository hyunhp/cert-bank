@ AZ-104 D5 T5.1 applied troubleshooting
S: Users of an order-entry VM report short freezes during the busiest hour each day. In Metrics Explorer the admin charts Percentage CPU for the last 30 days with Avg aggregation, and the line never goes above 35%. What should the admin change to check whether the CPU actually hits 100% during those freezes?
A: Switch the aggregation to Max and shorten the time range so that the chart uses a finer time granularity
B: Switch the aggregation to Sum so that every CPU sample in each interval is added into a single total value
C: Switch the aggregation to Count so that the chart shows how many CPU samples arrived in each interval
D: Lock the y-axis range to 0-100 so that the small peaks on the existing Avg line become clearly visible
K: A
G: ## How Metrics Explorer draws a chart
Platform metrics are stored as time-stamped values. When you plot a chart, Metrics Explorer groups the raw values into **time grains** (time granularity) and reduces each grain to one data point with an **aggregation**. If you do not pick a granularity, it is chosen automatically from the time range, so a long range gets large grains. The smallest grain is 1 minute, and one chart can show up to 30 days.
## The five aggregations
- **Avg**: the sum divided by the count in each grain.
- **Max** / **Min**: the largest / smallest value captured in the grain.
- **Sum**: all values added together.
- **Count**: the number of measurements in the grain.
Learn's aggregation article shows that as the grain grows, Avg and Sum "lose" anomalies while Min and Max keep them: larger grains smooth out spikes. A VM that sits at 100% for 2 minutes and at 20% for the rest of a 6-hour grain still averages close to 20%.
## Example
Range: last 24 hours, granularity 5 minutes, aggregation Max. A freeze at 14:05 now shows as a point at 100% instead of disappearing into an hourly or daily average.
W: Max with a finer granularity: Max keeps the highest sample in each grain, and a shorter time range gives small grains, so short periods of 100% CPU appear on the chart instead of being averaged away.
X: B=Sum aggregation: adding CPU percentages inside a grain produces a number that depends on how many samples were taken, not a percentage. It does not answer whether the CPU reached 100%.
C=Count aggregation: Count only shows how many measurements arrived per grain. It says nothing about how high the CPU went.
D=Lock the y-axis: locking the axis helps to see small changes in a line, but the line itself is still an average over large grains. A spike that the average already removed cannot be made visible by rescaling.
T: Averages over large time grains hide short spikes; use Max (or Min) with a small time granularity to find peaks.
V: Azure Monitor Metrics, Metrics Explorer

@ AZ-104 D5 T5.1 applied use-case
S: An app writes to a storage account, and the Transactions metric looks normal in Metrics Explorer. The developers suspect that one kind of request keeps failing. How should the admin configure the chart to see which operations return errors?
A: Add a filter on the ResponseType dimension that excludes Success, then apply splitting on the ApiName dimension
B: Add a filter on the ApiName dimension that excludes Success, then apply splitting on the GeoType dimension
C: Change the aggregation of Transactions to Max, then apply splitting on the Authentication dimension instead
D: Add the Availability metric to the same chart, then apply splitting by resource ID to show each operation
K: A
G: ## Dimensions, filters and splitting
Many platform metrics carry **dimensions**: name/value pairs that describe each measurement. In Metrics Explorer:
- A **filter** keeps only the dimension values you choose (for example, only failed requests).
- **Splitting** draws one line per dimension value instead of one combined line, so you can compare segments and spot the outlier. The default limit is 10 lines (1 to 50).
Using both on the right dimensions turns a single "all is fine" line into an answer.
## Storage Transactions
The storage `Transactions` metric counts all requests, successful and failed, and has these dimensions:
- `ResponseType`: the result, such as `Success`, `ClientThrottlingError` or `ServerTimeoutError`
- `ApiName`: the operation, such as `PutBlob` or `GetBlob`
- `GeoType`, `Authentication`, `TransactionType`
## Example
Filter `ResponseType != Success`, split by `ApiName`: the chart shows one line per operation, and a steady line for `PutBlob` failures points straight at the problem.
W: Filter on ResponseType, split by ApiName: the filter removes the successful requests, and the split shows the remaining failures per operation, which is exactly "which operation fails".
X: B=Filter ApiName, split GeoType: `Success` is a value of ResponseType, not of ApiName, so the filter would not remove successful requests. GeoType only separates primary and secondary location requests, not operations.
C=Max with Authentication split: Transactions is a count metric summed per grain, and Authentication shows how requests were authorized (for example, account key or SAS), not which operation failed.
D=Availability split by resource ID: splitting by resource ID compares several resources, not operations inside one account. Availability shows a percentage, not which operation produced the errors.
T: Filter a metric's dimension to keep the values you care about, and split on another dimension to see which segment causes them.

@ AZ-104 D5 T5.1 applied troubleshooting
S: The security team must find out who read secrets from a key vault last week. In the Log Analytics workspace they find no Key Vault data at all, and the vault's activity log only shows management operations such as policy and network changes. What is the cause?
A: Resource logs aren't collected by default, so the vault needs a diagnostic setting that sends its audit logs to the workspace
B: The vault has no data collection rule, so a DCR with a Key Vault data source must be created and associated with the vault
C: The Azure Monitor Agent isn't installed on the vault, so the agent extension must be added before any data can reach the workspace
D: The workspace uses resource-context access, so the team must switch to workspace-context before Key Vault records become visible
K: A
G: ## Three kinds of platform data
Azure resources produce platform data with very different defaults:
- **Platform metrics**: collected automatically.
- **Activity log**: collected automatically. It records control-plane operations on resources (create, update, delete, configuration changes) for 90 days.
- **Resource logs**: **not collected by default**. They record data-plane operations inside a resource, such as getting a secret from a key vault or a request to a database.
## Diagnostic settings
A **diagnostic setting** on the resource selects log categories (or category groups such as `audit`) and sends them to one or more destinations: a Log Analytics workspace, a storage account, an event hub or a partner solution. Collection starts once the setting exists: Learn says data should start flowing within 90 minutes.
## Example
For a key vault, the `AuditEvent` category records every operation such as `SecretGet`, with the caller's identity and IP address. A diagnostic setting that sends `AuditEvent` to the workspace lets the team query it with KQL from then on.
W: Diagnostic setting for resource logs: reading a secret is a data-plane operation recorded only in resource logs, and resource logs are emitted only after a diagnostic setting routes them somewhere, such as the workspace.
X: B=Data collection rule on the vault: DCRs drive the Azure Monitor Agent and other DCR-based collection. Platform resource logs from a key vault are routed with a diagnostic setting, not by associating a DCR with the vault.
C=Install the Azure Monitor Agent: the agent collects guest OS data from VMs and Arc-enabled servers. A key vault is a PaaS service where nothing can be installed; its logs come from the platform.
D=Switch access mode: access mode only limits which existing records a user sees. Here no Key Vault records exist in the workspace at all, so changing the scope cannot show them.
T: Activity log and metrics arrive automatically; resource logs (data-plane operations) need a diagnostic setting before they are collected.

@ AZ-104 D5 T5.1 applied use-case
S: An Azure Firewall's resource logs must meet two needs: a copy kept as files for three years under a policy that prevents changes, and a near-real-time stream to a non-Microsoft SIEM. Which TWO destinations should the diagnostic setting include? (Select TWO)
A: A storage account in the same region as the firewall, with an immutability policy on the log container
B: An event hub in the same region as the firewall, which the SIEM reads from as a streaming consumer
C: A Log Analytics workspace with table retention raised, which the SIEM reads through scheduled exports
D: A Service Bus queue in the same region as the firewall, which the SIEM polls to read the newest entries
E: A Recovery Services vault with a long-term retention policy, which protects the log files from changes
K: A,B
G: ## Diagnostic setting destinations
A diagnostic setting can send platform logs and metrics to up to one destination of each type:
- **Log Analytics workspace**: analysis with KQL, alerts, workbooks.
- **Storage account**: low-cost archive as blobs (JSON). Can use an immutability policy so the data cannot be modified. Kept as long as you like.
- **Event Hubs**: streaming to external systems such as non-Microsoft SIEM tools.
- **Azure Monitor partner solutions**: specific third-party integrations.
## Rules worth remembering
- The destination must exist before you create the setting.
- For regional resources, storage accounts and event hubs must be in the **same region** as the monitored resource.
- Behind a firewall, enable **Allow trusted Microsoft services** on the storage account or Event Hubs namespace.
- A resource can have up to five diagnostic settings; to send to two destinations of the same type, create two settings.
## Example
One diagnostic setting on `fw-hub` sends all log categories to `stfwarchive` (with a time-based retention policy on the container) and to the event hub `eh-siem`, which the SIEM connector consumes.
W: A=Storage account with immutability: storage is the archive destination of a diagnostic setting, data is kept as files for as long as needed, and an immutability policy prevents anyone from modifying it.
B=Event hub: Event Hubs is the destination designed for streaming platform logs to non-Microsoft SIEM tools in near real time.
X: C=Log Analytics workspace: the workspace is for querying and alerting, and stores data in tables rather than as protected files; scheduled exports add delay, so this is not a near-real-time stream to the SIEM.
D=Service Bus queue: Service Bus is not a diagnostic setting destination. Streaming uses Event Hubs.
E=Recovery Services vault: Recovery Services vaults hold Azure Backup and Site Recovery data. A diagnostic setting cannot send logs to a vault.
T: Diagnostic settings: workspace to analyze, storage account to archive (optionally immutable), event hub to stream to external tools.

@ AZ-104 D5 T5.1 applied use-case
S: From now on, auditors will ask at any time for every role assignment change in the production subscription during the previous 12 months, and the team wants to search those events with KQL together with other logs. Today the team only uses the Activity log blade. What should the admin configure?
A: A diagnostic setting on the subscription's activity log that sends all categories to a Log Analytics workspace
B: A retention setting on the subscription's activity log that raises the default 90-day period to 365 days
C: A log profile on the subscription that copies all activity log categories to a Log Analytics workspace
D: An activity log alert on role assignment writes whose action group emails each event to an archive mailbox
K: A
G: ## Activity log retention
Azure collects activity log entries (control-plane operations such as `Microsoft.Authorization/roleAssignments/write`) automatically and keeps them for **90 days** at no charge. After that they are deleted, and the activity log itself has no setting to keep them longer.
## Exporting the activity log
To keep the entries longer or analyze them with other data, create a **diagnostic setting** on the activity log (portal: Monitor > Activity log > Export Activity Logs). Destinations:
- **Log Analytics workspace**: entries land in the `AzureActivity` table; you can query them with KQL, join them with other logs, create log search alerts, and keep them as long as the workspace retention allows. Activity log ingestion is free; retention past 90 days is charged.
- **Storage account**: archive for audit beyond 90 days.
- **Event hub**: stream to other systems.
The older export method, **log profiles**, is legacy; disable it when you move to diagnostic settings.
Export only copies entries the activity log still holds, so set it up early: entries already past 90 days cannot be recovered later.
## Example
`AzureActivity | where OperationNameValue has "roleAssignments" | project TimeGenerated, Caller, ActivityStatusValue`
W: Diagnostic setting on the activity log: it sends every new entry to the workspace, where the team can keep it beyond 90 days and query it with KQL alongside other tables.
X: B=Raise activity log retention: the activity log keeps entries for 90 days and has no setting to extend that; longer retention requires sending the entries to another location.
C=Log profile: log profiles are the legacy export method that Learn tells you to disable, and they are not how activity log data is routed to a workspace today.
D=Activity log alert to a mailbox: an alert notifies about events but is not an archive. Emails cannot be queried with KQL alongside other logs, and alerts are not a reliable copy of every entry.
T: The activity log keeps 90 days; for longer retention or KQL analysis, export it with a diagnostic setting to a Log Analytics workspace (or storage for archive).
V: Azure activity log, Azure Monitor diagnostic settings, Log Analytics

@ AZ-104 D5 T5.1 applied use-case
S: An admin is enabling guest monitoring for 30 Windows VMs. Memory usage, disk free space and the System event log must reach a Log Analytics workspace, and the setup must use the currently supported agent. Which TWO steps are required? (Select TWO)
A: Install the Azure Monitor Agent extension on each of the 30 VMs, once per VM regardless of how many rules apply
B: Create a data collection rule with the counters and event logs, sending to the workspace, and associate it with the VMs
C: Install the Log Analytics agent on each VM and connect it with the workspace ID and primary key of the workspace
D: Install the Dependency agent on each VM so that processes, performance counters and events are sent to the workspace
E: Create a diagnostic setting on each VM resource that sends the guest performance counters and event logs to the workspace
K: A,B
G: ## Host data versus guest data
Azure collects **host metrics** for every VM automatically (CPU, network, disk I/O seen from the host). Anything inside the operating system, such as memory used, free disk space per volume or Windows event logs, is **guest** data and needs an agent.
## Azure Monitor Agent and data collection rules
Guest monitoring takes three steps (when you create a DCR in the portal and add VMs to it, the portal installs the agent and creates the associations for you):
1. **Install the Azure Monitor Agent** on each VM (extension `AzureMonitorWindowsAgent` or `AzureMonitorLinuxAgent`). Install it once; it can use any number of DCRs.
2. **Create data collection rules (DCRs)**: each DCR lists what to collect (performance counters, Windows event logs, Syslog, text logs) and where to send it.
3. **Associate the DCRs with the VMs**: the agent downloads its associated DCRs and starts collecting.
Windows event data can only go to a Log Analytics workspace (the `Event` table).
## Agents to avoid
- The **Log Analytics agent** (MMA/OMS) is the legacy agent; it was retired on August 31, 2024, and Learn tells you to migrate to the Azure Monitor Agent.
- The **Dependency agent** only fed the VM insights Map feature; both are deprecated (retiring June 30, 2028), and Learn says not to install the agent on any more systems.
- The **Azure Diagnostics extension** (WAD/LAD), an older guest agent, was retired on March 31, 2026.
W: A=Install the Azure Monitor Agent: it is the supported agent for guest OS data; it is installed once per VM and then applies whatever DCRs are associated with it.
B=DCR associated with the VMs: the DCR defines the counters, event logs and workspace destination, and the association is what makes each agent start collecting.
X: C=Log Analytics agent: this legacy agent was retired on August 31, 2024, and Learn says to migrate to the Azure Monitor Agent, so it fails the "currently supported agent" requirement.
D=Dependency agent: it only collected process and connection data for the deprecated Map feature and requires the Azure Monitor Agent anyway; it does not send counters or event logs.
E=Diagnostic setting on the VM: an Azure Monitor diagnostic setting on a VM can only export its platform (host) metrics; it has no guest log categories, so it cannot read memory, disk space or event logs. The older Diagnostics extension that collected guest data was retired on March 31, 2026.
T: Guest monitoring = Azure Monitor Agent (installed once) + data collection rules associated with the machines.
V: Azure Monitor Agent, data collection rules, VM insights, Log Analytics

@ AZ-104 D5 T5.1 advanced troubleshooting
S: VMs send Windows events through the Azure Monitor Agent and a DCR stored in West Europe to a West Europe workspace. A new rule says System log errors must also reach a workspace in East US, but the existing DCR doesn't accept that workspace as a destination. What should the admin do?
A: Create a second DCR in East US that collects System log errors to that workspace, and associate it with the same VMs
B: Install a second Azure Monitor Agent instance on each VM and point it at the East US workspace with its own key
C: Move the East US workspace to West Europe with a resource move, then add it as a second destination in the DCR
D: Create a diagnostic setting on each VM that copies System log errors from the agent to the East US workspace
K: A
G: ## Where a DCR lives
A data collection rule is an Azure resource with its own subscription, resource group and **region**. The subscription and resource group can differ from the VMs', but Learn states that the DCR's region **must be the same region as any Log Analytics workspace or Azure Monitor workspace used as a destination**. If you have workspaces in different regions, you create multiple DCRs and associate them with the same set of machines.
## One agent, many DCRs
The Azure Monitor Agent is installed once per machine. It downloads every DCR associated with it and runs them all, so splitting collection into several DCRs (by region, by team, by data type) is normal.
## Example
- `dcr-events-weu` (West Europe): all Windows event levels to `law-weu`.
- `dcr-syserr-eus` (East US): System log, level Error only, to `law-eus`.
Both associated with the same 40 VMs; each agent runs both rules.
W: Second DCR in East US: a DCR can only send to workspaces in its own region, so a rule stored in East US is needed for the East US workspace, and the existing agents simply pick up the additional association.
X: B=Second agent instance: the agent is installed once per machine and is configured only through DCRs. There is no workspace key to point a second instance at.
C=Move the workspace: a resource move only changes a workspace's resource group or subscription, not its region; relocating means recreating it in the target region. The requirement is also for data in East US, so moving it away would defeat the purpose.
D=Diagnostic setting on each VM: an Azure Monitor diagnostic setting on a VM exports only platform (host) metrics; it cannot read or copy events that the agent collects from inside the guest.
T: A DCR must be in the same region as its workspace destinations; for workspaces in several regions, create one DCR per region and associate all of them with the machines.

@ AZ-104 D5 T5.1 applied use-case
S: An admin needs a line chart of the average Available MBytes of server APP01 for each hour of the last 7 days, using the Perf table in Log Analytics. All queries below start with `Perf | where TimeGenerated > ago(7d) | where Computer == "APP01" | where CounterName == "Available MBytes"`. Which ending produces the chart?
A: `| summarize avg(CounterValue) by bin(TimeGenerated, 1h) | render timechart`
B: `| summarize avg(CounterValue) by TimeGenerated | render timechart`
C: `| render timechart | summarize avg(CounterValue) by bin(TimeGenerated, 1h)`
D: `| summarize avg(CounterValue) by Computer, CounterName | render timechart`
K: A
G: ## The query pipeline
A KQL query starts with a table and passes rows through operators separated by `|`:
- `where` filters rows; put the time filter right after the table name.
- `summarize <aggregation> by <columns>` groups rows and computes one result per group, such as `count()` or `avg(CounterValue)`.
- `render <visualization>` draws the result.
## Grouping by time
`TimeGenerated` values are almost all unique, so `summarize ... by TimeGenerated` makes one group per timestamp, which is no aggregation at all. `bin(TimeGenerated, 1h)` rounds each timestamp down to its hour, giving one group per hour.
## render rules
- `render` **must be the last operator** in the query.
- `timechart` draws a line graph whose first column must be a `datetime` (the x-axis) and whose numeric columns become the lines.
## Example
`Perf | where TimeGenerated > ago(7d) | where Computer == "APP01" | where CounterName == "Available MBytes" | summarize avg(CounterValue) by bin(TimeGenerated, 1h) | render timechart` returns one point per hour (about 168) drawn as one line.
W: summarize by bin, then render: `bin(TimeGenerated, 1h)` creates one group per hour, `avg(CounterValue)` gives the hourly average, and `render timechart` as the last operator draws it with time on the x-axis.
X: B=Group by raw TimeGenerated: each timestamp is its own group, so nothing is averaged per hour; the chart just replays the raw samples.
C=render before summarize: `render` must be the last operator in the query, so placing `summarize` after it is not valid.
D=Group by Computer and CounterName: the filters already fixed both values, so the result is a single row with no datetime column, which a timechart cannot use as its x-axis.
T: For a trend chart in KQL: filter with where, `summarize ... by bin(TimeGenerated, <size>)`, and end with `render timechart`.
V: Log Analytics, Kusto Query Language

@ AZ-104 D5 T5.1 applied troubleshooting
S: The same KQL query on the Perf table returns data from 25 VMs when the operations lead runs it from Logs on the Log Analytics workspace's menu, but only one VM's data when a developer runs it from Logs on the APP01 VM's menu. Both use the same workspace. What explains the difference?
A: Opening Logs from a VM menu uses resource-context mode, so queries are scoped to data associated with that VM only
B: Opening Logs from a VM menu applies the VM's data collection rule as a filter, so only the rule's counters are shown
C: Opening Logs from a VM menu sets the time range to the VM's uptime, so data from the other machines is excluded
D: Opening Logs from a VM menu switches the query to simple mode, which can only read rows written by one computer
K: A
G: ## Access modes in Log Analytics
The **scope** you open Log Analytics with decides which data a query can see:
- **Workspace-context**: you open Logs with the workspace as the scope (for example, Logs on the workspace's menu). Queries cover all data in the tables you have access to in the workspace.
- **Resource-context**: you open Logs for a resource, resource group or subscription (for example, Logs on a VM's menu). Queries cover only records associated with that resource, in any workspace, through the `_ResourceId` column.
## Access control mode
The workspace's **access control mode** decides how permissions are checked. With *Use resource or workspace permissions*, a user who only has read access to some VMs can query their logs in resource-context without any permission on the workspace. That is how application teams get logs for their own resources only.
## Example
The lead sees `Perf | summarize count() by Computer` with 25 rows. The developer, starting from APP01's Logs blade, gets 1 row because the scope is `/subscriptions/.../virtualMachines/APP01`.
W: Resource-context scope: starting from a resource menu scopes every query to records whose `_ResourceId` belongs to that VM, while starting from the workspace uses all data in the workspace.
X: B=DCR as a filter: a DCR controls what the agent collects and sends, not what a query returns afterwards. Opening Logs never applies a DCR to a query.
C=Time range set to uptime: the time range picker works the same in both places and filters by time, not by machine. Other VMs' data would still appear within the range.
D=Simple mode: simple mode is a query-building interface, and it does not restrict results to one computer. The scope, not the editing mode, limits the data.
T: Logs opened from the workspace = workspace-context (all data); Logs opened from a resource = resource-context (only that resource's records).

@ AZ-104 D5 T5.1 applied comparison
S: After an accidental deletion, a company wants an email whenever anyone deletes a virtual machine in its production subscription, within minutes of the operation. Which alert rule should the admin create?
A: An activity log alert on the Delete Virtual Machine operation, scoped to the subscription, with an email action group
B: A metric alert on Percentage CPU that fires when the value drops to zero, scoped to all VMs in the subscription
C: A log search alert on the Heartbeat table that fires when a VM stops reporting for 15 minutes in the workspace
D: A Service Health alert on the Virtual Machines service in all regions, with an email action group attached
K: A
G: ## Which signal records a deletion?
Deleting a VM is a **control-plane operation** (`Microsoft.Compute/virtualMachines/delete`) and is recorded in the **activity log** of the subscription, with the caller, time and status. Activity log entries are usually available for alerting within minutes.
## Alert types in Azure Monitor
- **Metric alerts**: evaluate numeric platform or custom metrics, such as CPU above 80%.
- **Log search alerts**: run a KQL query on a Log Analytics workspace at a set frequency.
- **Activity log alerts**: fire when a specific activity log event occurs, such as a restart, a shutdown or the creation or deletion of a resource.
- **Service Health alerts**: Azure-side incidents, planned maintenance and advisories for services and regions.
## Example
Condition: signal *Delete Virtual Machine (Virtual Machines)*, scope: production subscription, event level: all. Action group `ag-ops-email`.
W: Activity log alert on Delete Virtual Machine: the deletion is written to the activity log as its own operation, so this rule fires exactly when someone deletes a VM and names the caller.
X: B=Metric alert on CPU at zero: CPU also drops when a VM is stopped or idle, and a deleted VM stops emitting metrics instead of reporting zero, so the alert is both noisy and unreliable for deletions.
C=Heartbeat log search alert: missing heartbeats also happen when a VM is shut down or the agent fails, and this needs the agent on every VM; it cannot tell a deletion from an outage.
D=Service Health alert: Service Health reports problems and maintenance on Azure's side, not operations performed by your own users.
T: "Someone did X to a resource" (create, delete, restart, change) → activity log alert; numeric thresholds → metric alert; KQL conditions → log search alert.
V: Azure Monitor alerts, Azure activity log, action groups

@ AZ-104 D5 T5.1 applied comparison
S: Twenty VMs already send their Windows Application event log to a Log Analytics workspace. The admin must be alerted whenever event ID 1000 (application crash) for the billing service appears on any of them. Which alert rule type fits?
A: A log search alert rule whose KQL query filters the Event table for that event ID and fires when rows are returned
B: A metric alert rule on the VMs' Percentage CPU that fires when the value changes suddenly on any of the VMs
C: An activity log alert rule on the VMs that fires when an Administrative event with Error level is recorded
D: A Resource Health alert rule on the VMs that fires when their health status changes from Available to Unavailable
K: A
G: ## Logs versus metrics in alerting
An alert rule watches one kind of signal:
- **Metric alert rules** evaluate numeric time series that Azure stores as metrics. They are simple and fast, but only work on data that exists as a metric.
- **Log search alert rules** run a KQL query against a Log Analytics workspace at a set frequency. They can measure the **number of rows** returned (good for events such as Windows event logs or Syslog) or a calculation on a numeric column. One rule can cover many resources by querying the whole scope and splitting by dimensions such as `Computer`.
- **Activity log alerts** react to control-plane events on Azure resources (create, delete, restart, role changes).
- **Resource Health alerts** react to platform health changes of a resource.
Windows events collected by the Azure Monitor Agent are stored in the `Event` table, which is log data, not metric data.
## Example
`Event | where EventLog == "Application" and EventID == 1000 and RenderedDescription has "billing"`; condition: number of rows greater than 0, evaluated every 5 minutes, split by `Computer`.
W: Log search alert on the Event table: the crash events exist only as log records in the workspace, and a log search rule can filter them with KQL and fire when the query returns rows.
X: B=Metric alert on CPU: CPU behaviour is not the same as an application crash event; a crash might not change CPU at all, and event IDs are not available as metrics.
C=Activity log alert: the activity log holds Azure control-plane operations on the VM resource, not events written inside the guest OS's Application log.
D=Resource Health alert: Resource Health reports whether the VM itself is available from the platform's view. An application crash inside a running VM does not change it.
T: Events from inside the guest (Windows events, Syslog) live in Log Analytics, so alert on them with a log search alert rule.

@ AZ-104 D5 T5.1 applied use-case
S: A company wants every alert in its main subscription to email all users who hold the Owner role on that subscription. Owners change often, and nobody wants to keep a list of addresses up to date. How should the action group be configured?
A: Add an Email Azure Resource Manager role notification that targets the Owner role of the subscription
B: Add an Email/SMS/Push/Voice notification with each Owner's address and update it with a monthly runbook
C: Add a Secure Webhook action that posts each alert to the Microsoft Entra group of the subscription Owners
D: Grant the Monitoring Contributor role to each Owner, so that they automatically receive all fired alerts
K: A
G: ## What an action group is
An **action group** is a reusable list of notifications and actions that alert rules (and alert processing rules) call when an alert fires:
- **Notifications**: email, SMS, voice call, Azure mobile app push, and **Email Azure Resource Manager role**.
- **Actions**: Automation runbook, Azure Function, Logic App, webhook / secure webhook, Event Hubs, ITSM.
## Email Azure Resource Manager role
This notification emails the members of a **role on the subscription**, including Microsoft Entra user and group members of the role. Action groups support these roles: Owner, Contributor, Reader, Monitoring Contributor and Monitoring Reader. The role assignment should be made at subscription level, and users need an email address in their Entra profile. Learn notes that it can take up to 24 hours before a newly added role starts receiving notifications.
## Example
Action group `ag-owners` with one notification: *Email Azure Resource Manager role = Owner*. When a new person becomes Owner of the subscription, they start receiving alerts with no change to the action group.
W: Email Azure Resource Manager role: the recipient list is resolved from the subscription's role membership, so new and removed Owners are handled automatically without maintaining addresses.
X: B=Fixed addresses plus a runbook: it works only as well as the runbook, and it is exactly the address list the company wants to avoid maintaining.
C=Secure Webhook to an Entra group: a secure webhook calls an HTTP endpoint protected by Microsoft Entra authentication; it does not send email to the members of a group.
D=Monitoring Contributor role: the role lets users manage monitoring settings and see alerts in the portal, but having a role does not cause any notification to be sent.
T: To notify whoever holds a subscription role (Owner, Contributor, Reader, Monitoring Contributor or Monitoring Reader), use the Email Azure Resource Manager role notification.

@ AZ-104 D5 T5.1 applied definition
S: Every Saturday from 22:00 to 02:00, an admin patches all VMs in resource group rg-erp. A recurring alert processing rule with the Suppression action and that resource group as its scope is in place. Which TWO statements describe what happens to an alert that fires during that window? (Select TWO)
A: The alert is still created and appears when the team lists alerts in the portal, Resource Graph or the API
B: The alert's action groups are not called, and they are not called later when the maintenance window ends
C: The alert rules covering rg-erp are disabled at 22:00 and enabled again at 02:00 by the processing rule
D: The suppressed notifications are queued and sent as one summary email to the action groups at 02:00
E: Metric and log data from rg-erp aren't collected during the window, so the alert has no data to report
K: A,B
G: ## Alert rules versus alert processing rules
- An **alert rule** decides *when an alert fires* (a metric crosses a threshold, a query returns rows).
- An **alert processing rule** changes *what happens to alerts that have already fired*. It does not touch the alert rules or the monitoring data.
## Parts of an alert processing rule
- **Scope**: specific resources, a resource group, or a whole subscription (in the same subscription as the rule), with optional **filters** such as severity, resource type, alert rule ID or monitor service.
- **Action**: **Suppression** (removes all action groups from the affected alerts) or **Apply action groups** (adds action groups). Suppression wins if both apply to one alert.
- **Schedule**: always, a one-time window, or a recurring window (daily, weekly, monthly).
## Why not just disable the alert rules?
Disabling rules works only if a rule's scope exactly matches the resources in maintenance, needs every rule updated twice per window, and cannot cover alerts that no rule created, such as Azure Backup alerts. An alert processing rule avoids all three.
## Example
Scope: `rg-erp`; action: Suppression; schedule: weekly, Saturday 22:00 to Sunday 02:00. A high-CPU alert at 23:10 shows in the Alerts list, but no email or SMS is sent, then or afterwards.
W: A=Alert still visible: suppression only removes action groups; the fired alert still exists and is listed in the portal, Azure Resource Graph, the API and PowerShell.
B=Action groups never called: suppressed alerts invoke none of their action groups, not even when the maintenance window ends.
X: C=Rules disabled and re-enabled: an alert processing rule never changes the alert rules. Disabling rules is the manual alternative that processing rules were designed to replace.
D=Queued summary at 02:00: suppressed notifications are not stored or replayed. Learn states the action groups are not invoked even at the end of the window.
E=Data collection paused: processing rules act only on fired alerts. Metrics and logs keep flowing, which is why the alert can fire at all.
T: A suppression alert processing rule silences notifications for matching fired alerts in its schedule, while the alerts themselves still fire and stay visible.
V: Azure Monitor alert processing rules, action groups

@ AZ-104 D5 T5.1 applied use-case
S: A subscription has 150 alert rules created by different teams, plus Azure Backup alerts that no alert rule creates. The operations center must be paged through its action group ag-noc for every Sev0 alert in the subscription. What should the admin create?
A: An alert processing rule at subscription scope with a Sev0 filter and the Apply action groups action set to ag-noc
B: An Azure Policy assignment at subscription scope that appends ag-noc to every alert rule whose severity is set to Sev0
C: A new log search alert rule at subscription scope that queries the alerts of severity Sev0 and calls ag-noc for each
D: A Service Health alert rule at subscription scope that covers all services and regions and calls ag-noc on every event
K: A
G: ## Managing action groups at scale
Normally each alert rule lists its own action groups. With many rules from many teams, keeping "always page the NOC for Sev0" consistent by editing each rule is slow and error-prone. Some alert sources, such as **Azure Backup alerts**, Azure Stack Edge and VM insights guest health, are not created by an alert rule at all, so there is no rule to edit.
## Apply action groups
An **alert processing rule** with the **Apply action groups** action adds one or more action groups to every fired alert in its scope that matches its filters:
- Scope: the whole subscription (or resource groups, or resources) in the rule's subscription.
- Filters (logical AND between filters): severity, monitor service, resource type, alert rule ID, alert context and more.
- Schedule: always on by default.
Note that alert processing rules don't affect Azure Service Health alerts.
## Example
Rule `apr-sev0-noc`: scope = subscription; filter = Severity equals Sev0; action = Apply action groups `ag-noc`. Every new Sev0 alert, from any rule or from Azure Backup, now also pages the NOC.
W: Alert processing rule with Apply action groups: one rule adds ag-noc to every matching Sev0 alert in the subscription, including alerts that have no alert rule such as Azure Backup alerts, without editing the 150 rules.
X: B=Azure Policy appending ag-noc: even if rules were modified this way, Azure Backup alerts have no alert rule to change, and processing rules are Azure Monitor's built-in way to add action groups to fired alerts.
C=Log search alert on alerts: this creates a second, separate set of alerts with its own delay and query costs instead of acting on the alerts that already fired.
D=Service Health alert: Service Health alerts cover Azure platform incidents and maintenance. They do not see Sev0 alerts raised by your own rules or by Azure Backup.
T: To add (or suppress) action groups across many alerts, including alerts without an alert rule, use an alert processing rule instead of editing each rule.
V: Azure Monitor alert processing rules, action groups, Azure Backup

@ AZ-104 D5 T5.1 applied troubleshooting
S: After a route table was associated with a subnet, VM01 in that subnet can no longer reach an internet API. The NSG rules haven't changed. Which Network Watcher tool shows whether traffic to the API's IP address is now sent to a network virtual appliance, and which route table causes it?
A: Next hop, which returns the next hop type, IP address and route table ID for a destination from the VM
B: IP flow verify, which returns whether the packet is allowed or denied and the rule that made the decision
C: Effective security rules, which lists all NSG rules applied to the VM's network interface and its subnet
D: Packet capture, which records the packets sent and received by the VM into a file for later analysis
K: A
G: ## Two separate questions when a VM can't connect
1. **Is the traffic allowed?** That is decided by network security group rules (and Azure Virtual Network Manager admin rules).
2. **Where is the traffic sent?** That is decided by routing: system routes, user-defined routes (UDRs) in route tables, and BGP routes.
A new route table changes the answer to question 2 without touching question 1, for example by sending `0.0.0.0/0` to a firewall appliance.
## Network Watcher diagnostic tools
- **Next hop**: for a source VM and destination IP, returns the **next hop type** (Internet, VirtualAppliance, VirtualNetworkGateway, VirtualNetwork, VirtualNetworkPeering, VirtualNetworkServiceEndpoint, MicrosoftEdge or None), the next hop IP address, and the **route table ID** when the route is a UDR (otherwise System Route).
- **IP flow verify** and **NSG diagnostics**: whether a packet is allowed or denied, and by which rule.
- **Effective security rules**: all security rules applied to a NIC.
- **Connection troubleshoot**: a point-in-time connection test.
- **Packet capture**: records traffic to and from a VM or scale set.
## Example
Next hop from VM01 to `52.x.x.x` returns: type `VirtualAppliance`, IP `10.0.100.4`, route table `/subscriptions/.../routeTables/rt-spoke`. The UDR is sending the traffic to a firewall that is not forwarding it.
W: Next hop: it answers exactly the routing question, showing that traffic goes to a VirtualAppliance and naming the route table that holds the user-defined route.
X: B=IP flow verify: it only checks NSG and admin rules, which did not change here. It would report "Access allowed" and miss the routing problem.
C=Effective security rules: it lists security rules, not routes, so it cannot show where traffic is sent.
D=Packet capture: a capture shows packets leaving the VM but not the route decision or which route table made it; it is a heavier tool for deeper analysis.
T: Routing problem (where does the packet go?) → Next hop; filtering problem (is it allowed?) → IP flow verify or NSG diagnostics.
V: Azure Network Watcher, route tables, network security groups

@ AZ-104 D5 T5.1 applied comparison
S: Three Azure VMs call a payment server in the on-premises datacenter over a site-to-site VPN. The admin needs ongoing checks every minute of reachability and round-trip time from each VM to the server's TCP port, with history and an alert when checks fail. What should the admin set up?
A: A Connection monitor in Network Watcher with the VMs as sources and the server's IP and port as the destination
B: Connection troubleshoot in Network Watcher, run from each VM against the server's IP address and TCP port
C: VPN troubleshoot in Network Watcher, run against the virtual network gateway and its site-to-site connection
D: IP flow verify in Network Watcher, run from each VM for outbound TCP traffic to the server's IP and port
K: A
G: ## Point in time versus over time
Network Watcher has tools that answer "does it work right now?" and one that answers "has it been working, and how fast?":
- **Connection troubleshoot**: a one-time test from a VM, scale set, application gateway or Bastion host to a VM, FQDN, URI or IP address.
- **Connection monitor**: end-to-end monitoring **over time** for Azure and hybrid endpoints, with checks over TCP, HTTP or ICMP at regular intervals, latency and checks-failed metrics in Azure Monitor, logs in Log Analytics, topology and alerts.
## How Connection monitor is built
- **Sources**: Azure VMs and scale sets (with the Network Watcher extension) or Azure Arc-enabled on-premises hosts (with the Azure Monitor Agent). The portal enables the extensions for you.
- **Destinations**: Azure VMs, URLs, FQDNs or IP addresses, including on-premises endpoints without any agent.
- **Test configurations**: protocol, port and frequency, plus thresholds for checks failed and round-trip time.
Network Watcher is enabled automatically in a region when you create or update a virtual network there.
## Example
Test group: sources `vm-app1..3`, destination `10.20.5.10`, TCP port 443, every 60 seconds, threshold "checks failed > 5%". A metric alert on Checks Failed notifies the team.
W: Connection monitor: it runs scheduled checks from the VMs to the on-premises IP and port, stores reachability and round-trip time history, and exposes metrics that alert rules can use.
X: B=Connection troubleshoot: it tests a connection once, at the moment you run it, so it gives no ongoing history or alerting.
C=VPN troubleshoot: it diagnoses the health of a gateway and its connections, not the reachability and latency of a specific server port from each VM.
D=IP flow verify: it only evaluates NSG and admin rules for one simulated packet; it never sends traffic, so it cannot measure reachability or round-trip time.
T: One-time connectivity test → Connection troubleshoot; continuous reachability and latency with history and alerts → Connection monitor.
V: Azure Network Watcher, Connection monitor, VPN Gateway
