# AZ-104 D4 T4.3 Configure name resolution and load balancing (15 questions: Azure DNS public zones x4, private DNS zones x3, Standard Load Balancer configuration x4, troubleshooting load balancing x4)

@ AZ-104 D4 T4.3 applied troubleshooting
S: A retailer bought `fabrikam-shop.com` from a third-party registrar and created a public DNS zone with that name in Azure DNS, then added an A record set `www`. A day later, `nslookup www.fabrikam-shop.com` from the internet still returns the old hosting provider's address. What should the administrator do?
A: At the registrar, replace the domain's name server (NS) records with all four Azure DNS name servers shown on the zone's Overview page.
B: In the Azure DNS zone, add the registrar's name servers to the NS record set at the zone apex so that both providers answer for the domain.
C: At the registrar, create an A record for `www` that points to the IP address of one of the four Azure DNS name servers assigned to the zone.
D: Transfer the domain registration from the third-party registrar to Azure DNS, which then publishes the zone's records on the internet.
K: A
G: ## Hosting a domain in Azure DNS takes two steps
Creating a zone in Azure DNS only stores records on Azure's authoritative name servers. Nobody on the internet asks those servers anything until the parent zone (here `.com`) says that Azure's name servers are responsible for the domain.
- **Step 1, create the zone**: Azure assigns four name servers from a pool, for example `ns1-37.azure-dns.com`, `ns2-37.azure-dns.net`, `ns3-37.azure-dns.org` and `ns4-37.azure-dns.info`, and creates the authoritative NS record set at the apex automatically.
- **Step 2, delegate**: at the registrar you set the domain's NS records to those Azure name servers. The registrar stores them in the parent zone. This is called delegation.
## How resolution finds the zone
A recursive resolver starts at the root, asks the `.com` servers which name servers host `fabrikam-shop.com`, and then queries those servers. If `.com` still lists the old provider, the old provider's answers win, no matter what the Azure zone contains.
## Checking the result
Microsoft recommends using all four Azure name servers and verifying with `nslookup -type=SOA fabrikam-shop.com`: the primary name server in the answer should be an Azure DNS server. Allow time for caches to expire after the change.
W: Delegate at the registrar: the parent `.com` zone learns the Azure name servers only through the registrar, so updating the NS records there (all four servers, copied with their trailing period where the registrar needs it) is what sends internet queries to the Azure zone.
X: B=Add registrar servers to the apex NS: extra servers in the Azure zone's own NS record set are for co-hosting a zone with another provider. They change nothing in the `.com` parent, which still delegates to the old provider.
C=A record for the name server: an A record maps a host name to an address for clients to connect to; it does not tell resolvers which servers are authoritative for the domain. Only NS records in the parent zone do that.
D=Transfer registration to Azure DNS: Azure DNS hosts zones but doesn't sell or register domain names; Learn says to buy domains from a third-party registrar. You keep the registration where it is and delegate the domain to Azure DNS.
T: A public Azure DNS zone answers internet queries only after the registrar's NS records for the domain point to the zone's four Azure name servers.
V: Azure DNS

@ AZ-104 D4 T4.3 applied troubleshooting
S: `contoso.com` is delegated to an Azure DNS zone in the networking subscription. A developer team created a separate public zone `dev.contoso.com` in its own subscription and added an A record `api`. Internet lookups of `api.dev.contoso.com` return NXDOMAIN. How should the administrator fix the delegation?
A: In the `contoso.com` zone, create an NS record set named `dev` that lists the four name servers assigned to the `dev.contoso.com` zone.
B: In the `contoso.com` zone, add the four `dev.contoso.com` name servers to the existing NS record set at the apex of the parent zone.
C: In the `contoso.com` zone, create a CNAME record set named `dev` whose value is the first name server assigned to the child zone.
D: At the registrar, replace the NS records of `contoso.com` with the four name servers that were assigned to the `dev.contoso.com` zone.
K: A
G: ## Child zones are delegated by the parent zone
DNS is a hierarchy of zones. A subdomain can live in the same zone as its parent (just records named `dev` or `api.dev`), or in its own **child zone**. A child zone is invisible until the parent zone contains an **NS record set with the child's name** that lists the child zone's name servers.
## What happens in this scenario
- Resolvers find `contoso.com` in Azure DNS through the registrar delegation.
- They ask the `contoso.com` zone about `api.dev.contoso.com`. That zone has no record named `api.dev` and no NS record for `dev`, so it answers NXDOMAIN.
- The `dev.contoso.com` zone exists, with its own four name servers, but nothing points to it.
## Fixing it
Look up the four name servers on the child zone's Overview page and create an NS record set `dev` in the parent zone with those values. When you create a child zone through the parent zone's **+ Child zone** button, or tick "This zone is a child of an existing zone already hosted in Azure DNS" and pick the parent zone's subscription and zone, Azure adds the delegation for you. Parent and child can sit in different subscriptions or resource groups.
W: NS record set `dev` in the parent: setting up NS records for a child zone in the parent zone is exactly what delegation means, and Azure DNS lets you create, change and delete non-apex NS record sets freely for this purpose.
X: B=Child servers in the apex NS: the apex NS record set describes who is authoritative for `contoso.com` itself. Adding the child's servers there would send some `contoso.com` queries to servers that do not host that zone, and still would not delegate `dev`.
C=CNAME to a name server: a CNAME makes one name an alias of another host name; resolvers would look up records of the name server's host name, not ask that server about the `dev` zone. Delegation needs NS records.
D=Change the registrar NS: that would re-delegate the whole `contoso.com` domain to servers that only host `dev.contoso.com`, breaking every other record of the company.
T: A child zone in Azure DNS works only after the parent zone holds an NS record set with the child's label and the child zone's name servers.
V: Azure DNS

@ AZ-104 D4 T4.3 applied use-case
S: A web shop runs behind a public Standard Load Balancer whose frontend uses the Standard public IP `pip-shop`. Customers must reach the shop at the bare domain `tailspin.com`, and the record must never keep pointing at an address the company no longer owns if `pip-shop` is deleted. What should the administrator create in the Azure DNS zone?
A: An alias A record set at the apex `@` whose target is the Azure resource `pip-shop`, so the record follows the public IP resource.
B: A CNAME record set at the apex `@` whose value is the DNS name label of `pip-shop` ending in `cloudapp.azure.com`.
C: A standard A record set at the apex `@` holding the current address of `pip-shop` and a short time-to-live of 60 seconds.
D: An NS record set at the apex `@` that delegates the bare domain to the frontend IP configuration of the load balancer.
K: A
G: ## Two problems at the zone apex
The apex (relative name `@`) is the zone name itself, `tailspin.com`. Two rules make it special:
- **No CNAME at the apex**: every zone has NS and SOA record sets at `@`, and the DNS standard forbids a CNAME next to other record sets with the same name. So you cannot "point" the bare domain at another host name with a CNAME.
- **Dangling records**: a normal A record holds a fixed address. If the public IP resource is deleted and Azure later hands that address to someone else, users would be sent to a stranger's service.
## Alias record sets
An Azure DNS **alias record set** is an A, AAAA or CNAME record set that references an Azure resource instead of literal data. Supported targets include a Standard public IP address, a Traffic Manager profile, an Azure CDN endpoint, an Azure Front Door endpoint and another record set in the same zone.
- The record set updates automatically when the referenced public IP address changes.
- If the referenced resource is deleted, the alias becomes an empty record set instead of a stale address.
- Alias A/AAAA record sets can be created at the zone apex.
In the portal you add a record set, choose **Alias record set: Yes**, alias type **Azure resource**, and pick the public IP.
W: Alias A record at the apex: it is allowed at `@`, resolves to the current address of the Standard public IP, and turns into an empty record set if that resource is deleted, which prevents a dangling record.
X: B=CNAME at the apex: Azure DNS rejects it because the apex already holds the NS and SOA record sets, and a CNAME cannot coexist with other record sets of the same name.
C=Plain A record with a short TTL: a short TTL only makes clients re-query sooner; the record itself still returns the old address after `pip-shop` is deleted until someone edits it by hand.
D=NS record at the apex: NS records name authoritative DNS servers. A load balancer frontend is not a DNS server, and the apex NS record set's Azure name servers cannot be replaced anyway.
T: Point the zone apex at an Azure resource with an alias record set; it is allowed at `@` and tracks the resource so records never dangle.
V: Azure DNS, Azure Public IP address, Azure Load Balancer

@ AZ-104 D4 T4.3 applied definition
S: An administrator is cleaning up the Azure DNS public zone `northwind.org` and documenting how record sets behave. Which TWO statements about this zone are correct? (Select TWO)
A: The time-to-live is configured on each record set, so every record inside one record set uses the same TTL value.
B: A CNAME record set cannot be created at the apex `@`, because the apex already holds the zone's NS and SOA record sets.
C: The Azure DNS name servers in the apex NS record set can be removed and replaced with the name servers of another provider.
D: A wildcard record set named `*` can be created for NS records to delegate every possible subdomain to the same name servers.
E: Two A records named `www` can be stored as separate record sets with different TTLs so that each address is cached differently.
K: A,B
G: ## Record sets in Azure DNS
Azure DNS manages records as **record sets**: all records in a zone with the same name and the same type. If `www` must return two IPv4 addresses, you add a second record to the existing `www` A record set rather than creating another record set.
## Rules worth knowing
- **TTL per record set**: the TTL is a property of the record set, so all records in it share the value.
- **CNAME limits**: a CNAME record set holds a single record and cannot coexist with other record sets of the same name. Because the apex always has NS and SOA record sets, a CNAME at `@` is impossible (use an alias record set instead).
- **Apex NS record set**: created and deleted with the zone. You can add name servers (to co-host with another provider) and change its TTL, but you cannot remove or modify the prepopulated Azure name servers. Other NS record sets, used for delegating child zones, can be changed freely.
- **Wildcards**: the name `*` (or `*.foo`) is supported for all record types except NS and SOA.
- **SOA**: created automatically; the serial number is not incremented automatically when records change.
## Example
`www  3600  A  203.0.113.10` and `www  3600  A  203.0.113.11` are one record set with one TTL of 3600 seconds.
W: A=TTL on the record set: Azure DNS specifies the TTL for the record set, not for each record, so all records in the set share it.
B=No CNAME at the apex: the NS and SOA record sets exist at `@` from the moment the zone is created, and a CNAME cannot share its name with any other record set.
X: C=Replace the apex NS servers: you may add extra name servers to the apex NS record set and change its TTL, but removing or modifying the prepopulated Azure DNS name servers is not allowed.
D=Wildcard NS record set: Azure DNS supports wildcard record sets for every record type except NS and SOA, so delegation always uses named NS record sets.
E=Two `www` A record sets: a record set is defined by name plus type, so all A records named `www` belong to one record set and share a single TTL.
T: In Azure DNS the record set (name plus type) is the unit you manage: one TTL per set, no CNAME at the apex, no wildcard NS, and the Azure apex name servers stay.
V: Azure DNS

@ AZ-104 D4 T4.3 applied troubleshooting
S: In a hub-and-spoke network, the private DNS zone `corp.fabrikam.net` is linked to the hub VNet with autoregistration enabled. The spoke VNet `vnet-spoke1` is peered with the hub, and its VMs ping hub VMs by IP, but `nslookup sql01.corp.fabrikam.net` from a spoke VM fails. Both VNets use Azure-provided DNS. What should the administrator do?
A: Create a virtual network link from `corp.fabrikam.net` to `vnet-spoke1`; registration can stay disabled because the spoke only needs to resolve names.
B: Enable **Allow forwarded traffic** on both sides of the peering so that DNS queries from the spoke are passed through to the hub VNet.
C: Enable gateway transit on the hub side of the peering and **Use remote gateways** on the spoke side so the spoke can use the hub's DNS resolution.
D: Create an NS record set named `corp` in the public `fabrikam.net` zone that points the private zone's name to the hub virtual network.
K: A
G: ## Private DNS zones resolve only in linked virtual networks
A private DNS zone is a global resource. To resolve its records from a virtual network, that virtual network must be **linked** to the zone. Each link is a child resource of the zone and comes in two flavours:
- **Registration virtual network** (autoregistration enabled): VMs in the VNet get A records in the zone automatically and can resolve the zone.
- **Resolution virtual network** (autoregistration disabled): VMs can query every record in the zone, including records registered from other VNets, but their own names are not added.
## Peering is not name resolution
Peering connects address spaces so packets can flow; it does not share private DNS zones. Learn states that forward resolution across virtual networks works for VNets linked to the zone and does not even require peering. The reverse is also true: peering alone does not let an unlinked VNet see the zone.
## Example
`az network private-dns link vnet create --zone-name corp.fabrikam.net --name link-spoke1 --virtual-network vnet-spoke1 --registration-enabled false` turns `vnet-spoke1` into a resolution virtual network for the zone.
W: Link the spoke as a resolution VNet: once `vnet-spoke1` is linked, the Azure-provided resolver used by its VMs can answer from `corp.fabrikam.net`, including the records autoregistered from the hub. This is the documented hub (registration) and spoke (resolution) pattern.
X: B=Allow forwarded traffic: this peering setting accepts traffic that a network virtual appliance forwards from outside the peered VNet. It does not make a private DNS zone visible to an unlinked VNet.
C=Gateway transit: this lets the spoke use the hub's VPN or ExpressRoute gateway to reach other networks. The Azure-provided DNS in the spoke still cannot see a zone that is not linked to it.
D=NS record in the public zone: public NS records delegate internet-facing zones to name servers. A virtual network is not a name server, and private zones are only resolvable from linked VNets.
T: Peering moves packets but not DNS: every VNet that must resolve a private DNS zone needs its own virtual network link to that zone.
V: Azure Private DNS, Azure Virtual Network

@ AZ-104 D4 T4.3 advanced troubleshooting
S: `vnet-prod` uses two domain controllers, `10.20.0.4` and `10.20.0.5`, as its custom DNS servers. The administrator links the private DNS zone `apps.contoso.net` to `vnet-prod`, where the DCs also run, but `nslookup web1.apps.contoso.net` from a VM reports server `10.20.0.4` and NXDOMAIN. What should the administrator do?
A: On the domain controllers, add a conditional forwarder for `apps.contoso.net` that sends queries to the Azure DNS address `168.63.129.16`.
B: Enable autoregistration on the existing virtual network link so that the VMs in `vnet-prod` start using the private DNS zone for name lookups.
C: Create a second virtual network link between `apps.contoso.net` and `vnet-prod` that is reserved for DNS queries coming from the domain controllers.
D: Create an NS record set for `apps` in the public `contoso.net` zone that lists the private IP addresses of the two domain controllers.
K: A
G: ## Who answers a VM's DNS query?
Each VNet (or NIC) has a DNS server setting.
- **Azure-provided DNS** (default): VMs send queries to the virtual IP `168.63.129.16`. That resolver knows the private DNS zones linked to the VNet.
- **Custom DNS servers** (here two domain controllers): VMs send every query to those servers. A custom DNS setting at the VNet or NIC level takes precedence over the linked private zone, so the zone is only used if the custom server itself asks Azure DNS.
## Making custom DNS servers see a private zone
The domain controllers run inside `vnet-prod`, which is linked to the zone. If they forward queries for `apps.contoso.net` to `168.63.129.16`, Azure DNS answers from the linked private zone. A conditional forwarder (or a general forwarder to `168.63.129.16`) is the usual design: the DCs answer their Active Directory zones and pass everything else to Azure.
## Symptom to recognise
`nslookup` shows the custom server (`10.20.0.4`) as the server and returns NXDOMAIN: the DC does not host the zone and has nowhere to send the query.
W: Conditional forwarder to `168.63.129.16`: the DCs sit in a VNet that is linked to the zone, so forwarding the zone's queries to the Azure recursive resolver returns the private zone's records to every client that uses the DCs.
X: B=Enable autoregistration: autoregistration only creates A records for VMs in the linked VNet. The clients still send their queries to the DCs, which never consult the private zone.
C=Second link to the same VNet: Azure allows only one link between a private DNS zone and a given virtual network, and a link does not change which server VMs query.
D=Public NS record to the DCs: public NS records serve internet resolvers. They have no effect on how the DCs inside the VNet resolve a name they do not host, and would publish private addresses.
T: With custom DNS servers on a VNet, private DNS zones work only if those servers forward the zone's queries to `168.63.129.16` from a linked VNet.
V: Azure Private DNS, Azure Virtual Network

@ AZ-104 D4 T4.3 applied definition
S: An administrator links the private DNS zone `int.adatum.com` to `vnet-app` with autoregistration enabled. `vnet-app` contains several VMs, some with two NICs, and an internal Standard Load Balancer. Which TWO results should the administrator expect? (Select TWO)
A: An A record for each VM's primary NIC private IP, including VMs that existed before the link was created.
B: When a VM in `vnet-app` is deleted, its autoregistered A record is removed from `int.adatum.com` automatically.
C: An A record for the frontend IP of the internal load balancer, named after the load balancer resource in the zone.
D: A records for the secondary NICs of the dual-NIC VMs, created in the zone next to the record for each primary NIC.
E: `vnet-app` can also be linked with autoregistration to a second private zone, so every VM is registered in both zones.
K: A,B
G: ## What autoregistration does
When a virtual network link has autoregistration enabled, the VNet becomes a **registration virtual network** for the zone. Azure DNS then manages A records for the VMs in that VNet:
- An A record is created for each VM, pointing to its private IP, for VMs already in the VNet and for new ones.
- Records are updated when a VM's IP changes and removed when the VM is deleted (or stopped and deallocated).
- Records come from the Azure DHCP service, so host names or static IPs set inside the guest OS are not reflected.
## Restrictions
- **VMs only**: other resources, such as an internal load balancer frontend, need records you create manually.
- **Primary NIC only**: additional NICs need manual records.
- **One registration zone per VNet**: a VNet can be a registration VNet for only one private zone, though it can be a resolution VNet for many zones, and one zone can have many registration VNets.
- No PTR records are autoregistered.
## Example
To publish the internal load balancer as `api.int.adatum.com`, add an A record set `api` with the frontend IP, for example `10.4.1.10`.
W: A=Primary NIC records, existing VMs too: Learn states that records are also created for VMs already deployed when the link is made, and autoregistration covers the primary NIC of each VM.
B=Record removed on delete: Azure DNS automatically removes the autoregistered record when the VM is deleted, so the zone does not keep stale entries.
X: C=Load balancer frontend: autoregistration works only for virtual machines. For an internal load balancer you create the A record by hand.
D=Secondary NIC records: only the primary NIC is registered automatically; records for other NICs must be created manually.
E=Second registration zone: a specific virtual network can be linked to only one private DNS zone with autoregistration enabled. It can still be linked to other zones for resolution only.
T: Autoregistration manages A records only for VM primary NICs in one registration zone per VNet; load balancers, extra NICs and PTRs need manual records.
V: Azure Private DNS

@ AZ-104 D4 T4.3 applied use-case
S: A booking app runs on four VMs behind a public Standard Load Balancer. The app keeps each user's session in the VM's memory, and users from home networks complain that they are randomly signed out when new connections land on another VM. The team can't change the app this quarter. Which setting should the administrator change on the load-balancing rule?
A: Set **Session persistence** to **Client IP**, so that requests from the same client IP address go to the same backend VM.
B: Enable **Floating IP** on the rule, so that each backend VM receives the traffic addressed to the frontend IP of the load balancer.
C: Increase the TCP **idle timeout** on the rule, so that the load balancer keeps each established flow pinned to its VM for longer.
D: Enable **TCP reset** on idle timeout, so that clients reconnect cleanly to the VM that already holds their session in memory.
K: A
G: ## How Azure Load Balancer picks a backend
By default the load balancer uses a **five-tuple hash**: source IP, source port, destination IP, destination port and protocol. One TCP connection always stays on one VM, but a new connection from the same browser uses a new source port and can land on another VM.
## Session persistence (source IP affinity)
The distribution mode is set per load-balancing rule:
- **None** (REST `Default`): five-tuple hash.
- **Client IP** (REST `SourceIP`): two-tuple hash of source and destination IP, so the same client IP goes to the same backend VM.
- **Client IP and protocol** (REST `SourceIPProtocol`): three-tuple hash that also includes the protocol.
Switching mode causes no downtime. Caveats from Learn: when backend pool members change the distribution is recomputed, and many clients behind one proxy look like a single client, which can skew load.
## Better long-term fix
Keeping session state outside the VM (for example in a cache or database) removes the need for affinity, but this team cannot change the app now.
W: Client IP session persistence: a two-tuple hash keeps every connection from the same client IP on the same healthy VM, so new connections find the in-memory session.
X: B=Floating IP: Floating IP changes the IP address mapping so the guest OS receives packets addressed to the frontend IP; it is used for port reuse such as SQL Server Always On listeners and does not keep a client on one VM.
C=Longer idle timeout: the idle timeout only decides how long an idle established flow is kept; a new connection is still hashed with its new source port and can reach another VM.
D=TCP reset on idle: this sends a TCP RST to both sides when an idle flow times out so applications notice; the following connection is still distributed by the five-tuple hash.
T: The default five-tuple hash only keeps a single connection on one VM; Client IP session persistence keeps all of a client's connections there.
V: Azure Load Balancer

@ AZ-104 D4 T4.3 advanced use-case
S: A company runs two third-party firewall VMs in the hub VNet. Spoke subnets have a user-defined route that sends all traffic to the firewalls, which must be active-active, fail over quickly, and inspect TCP and UDP on any port without one rule per port. How should the administrator front the firewall VMs?
A: An internal Standard Load Balancer with both firewall VMs in its backend pool and one HA ports rule (protocol All, port 0), used as the UDR next hop.
B: A public Standard Load Balancer with both firewall VMs in its backend pool and one HA ports rule (protocol All, port 0), used as the UDR next hop.
C: An internal Standard Load Balancer with one load-balancing rule per protocol and port in use, each with Floating IP enabled, as the UDR next hop.
D: An internal Standard Load Balancer with inbound NAT rules that map each port to one firewall VM, with the first VM as the default target.
K: A
G: ## Why network virtual appliances need a load balancer
A user-defined route can point to one next-hop IP address. With two firewall VMs you need a single, highly available address in front of them: the private frontend IP of an **internal Standard Load Balancer**. Its health probes take a failed appliance out of rotation quickly.
## HA ports rule
An **HA ports** rule is a load-balancing rule with protocol **All** and frontend and backend port **0**. One rule load-balances all TCP and UDP flows on all ports (and ICMP is supported), deciding per flow with the five-tuple hash.
- Available only on an **internal** Standard Load Balancer; public load balancers (and the retired Basic SKU) do not support it.
- Gives n-active or active-passive appliance designs without extra cluster software.
- For a single internal load balancer with one backend pool of NVAs, HA ports also provides flow symmetry for ingress and egress traffic.
## Health probe advice
Probe a port that reflects the health of the appliance itself, not a port it proxies to other VMs behind it.
W: Internal Standard Load Balancer with HA ports: the private frontend is the next hop for the UDR, the single All/0 rule covers every TCP and UDP port, and per-instance probes give fast failover across active-active appliances.
X: B=Public load balancer with HA ports: HA ports rules are available only on an internal Standard Load Balancer, and a public frontend address cannot serve as the private next hop of spoke routes.
C=One rule per port with Floating IP: rules must name a specific protocol and port, so unknown or changing ports are not covered; this is exactly the per-port rule list that HA ports replaces.
D=Inbound NAT rules per port: an inbound NAT rule forwards a frontend port to one specific backend instance, so there is no load balancing across the firewalls and no automatic failover.
T: For NVAs behind a UDR, use an internal Standard Load Balancer with an HA ports rule (All, port 0): one rule, every port, health-probed failover.
V: Azure Load Balancer, Azure Virtual Network

@ AZ-104 D4 T4.3 advanced use-case
S: Web VMs sit behind a public Standard Load Balancer whose frontend `pip-web` carries the inbound HTTPS rule. A payment partner will allowlist only a separate public IP, `pip-out`, as the source of the VMs' outbound calls. Using only this load balancer, what should the administrator configure?
A: Add `pip-out` as a second frontend, disable outbound SNAT on the HTTPS load-balancing rule, and create an outbound rule from the backend pool to the `pip-out` frontend.
B: Add `pip-out` as a second frontend and create a second load-balancing rule for TCP 443 on that frontend, so outbound connections use the most recently added frontend.
C: Add `pip-out` as a second frontend and create an inbound NAT rule on it for each backend VM, so that the VMs' outbound and return traffic leaves through `pip-out`.
D: Replace `pip-web` with `pip-out` on the existing frontend and keep the HTTPS rule's automatic outbound SNAT enabled for both directions of traffic.
K: A
G: ## Outbound connectivity from a public Standard Load Balancer
Backend VMs without their own public IP can reach the internet through the load balancer's frontend by **SNAT** (source network address translation).
- A **load-balancing rule** can program outbound SNAT automatically using its own frontend IP. Learn recommends not relying on this and disabling outbound SNAT on the rule (`disableOutboundSnat`).
- An **outbound rule** defines SNAT explicitly: which backend pool, which frontend IPs or public IP prefix, how many SNAT ports per VM, which protocols, and the idle timeout.
## Using a different IP for outbound
To make outbound flows use an address other than the inbound one, give the load balancer a frontend for that address, create an outbound rule that maps the backend pool to it, and disable automatic outbound SNAT on the load-balancing rule. If you disable outbound SNAT without any outbound rule, the VMs lose outbound connectivity.
## Notes
- Outbound rules are ignored for VMs that have an instance-level public IP.
- For large-scale outbound traffic Learn recommends Azure NAT Gateway; the scenario here limits you to the load balancer.
W: Second frontend plus outbound rule: the outbound rule translates the backend pool's outbound flows to `pip-out`, and disabling outbound SNAT on the HTTPS rule stops `pip-web` from being used for outbound, so the partner sees only `pip-out`.
X: B=Second load-balancing rule: load-balancing rules handle inbound traffic to a frontend. A rule on `pip-out` would accept inbound HTTPS there; it does not choose `pip-out` as the outbound source.
C=Inbound NAT rules: inbound NAT rules forward a frontend port to one backend VM for inbound sessions (for example RDP). Responses go back through the same frontend, but new outbound calls are not translated to `pip-out`.
D=Swap the frontend IP: moving `pip-out` onto the HTTPS frontend changes the address customers use for the shop and still mixes inbound and outbound on one IP, which breaks the separation the partner asked for.
T: Use an outbound rule on its own frontend, and disable outbound SNAT on the load-balancing rule, to control exactly which public IP backend VMs use outbound.

Minutes later, Health Probe Status for the public Standard Load Balancer fell to 0%. What is the fix?
A: Add an inbound NSG rule with a priority lower than 100 that allows the service tag `AzureLoadBalancer` as source to the health probe port.
B: Add an outbound NSG rule with a priority lower than 100 that allows traffic from the backend VMs to the destination address `168.63.129.16`.
C: Move the rule that allows TCP 443 from Internet to priority 90 so it is evaluated first, because the health probes arrive from the internet.
D: Remove the NSG from the subnet and associate it with each VM's network interface instead, where the default rules are evaluated first.
K: A
G: ## Where health probes come from
Every IPv4 health probe of Azure Load Balancer originates from `168.63.129.16`. In NSGs this source is represented by the service tag **AzureLoadBalancer**. Learn notes the tag only covers probe traffic, not the real client traffic to your backend.
## Default NSG rules and priorities
Every NSG ends with default rules, evaluated after your own rules (lower number = evaluated first, first match wins):
- `AllowVnetInBound` (65000)
- `AllowAzureLoadBalancerInBound` (65001), which normally lets probes in
- `DenyAllInBound` (65500)
A custom deny-all at priority 100 matches probe packets long before rule 65001 is reached, so every backend fails its probe. When all probes are down, a Standard Load Balancer sends no new flows to the pool.
## Fix pattern
Allow the probe explicitly above the deny, for example priority 90: source service tag `AzureLoadBalancer`, destination port = probe port, action Allow. Then confirm with the **Health Probe Status** metric in Azure Monitor.
W: Allow `AzureLoadBalancer` above the deny: this restores the probe path from `168.63.129.16`, which the custom priority-100 deny now blocks before the default allow rule at 65001 can match.
X: B=Outbound allow to `168.63.129.16`: NSGs are stateful, so replies to an allowed inbound probe are permitted automatically. The probe is dropped inbound by the deny rule, so an outbound rule changes nothing.
C=Move the Internet rule up: the `Internet` service tag covers public internet addresses, not the Azure platform address `168.63.129.16`. Client traffic would be allowed, but every probe would still hit the deny rule.
D=Move the NSG to the NICs: rule evaluation is the same on a NIC as on a subnet; default rules always come after custom rules, so the deny at priority 100 would still block the probes.
T: A custom deny-all above priority 65001 also blocks health probes; add an allow rule with source `AzureLoadBalancer` at a higher priority.

@ AZ-104 D4 T4.3 advanced troubleshooting
S: A public Standard Load Balancer uses an HTTP health probe on port 80, path `/health`, for two IIS VMs. Health Probe Status shows both VMs as down, yet browsing `http://<vm-private-ip>/health` from a jump box in the VNet works. Which TWO causes could explain the failed probes? (Select TWO)
A: The site sends an HTTP 301 redirect to HTTPS for `/health`, so the probe receives a status code other than 200 OK.
B: The Windows firewall on the VMs allows port 80 only from the VNet address space, which drops requests from `168.63.129.16`.
C: The backend VMs have no instance-level public IP addresses, so the probes sent from the internet cannot reach them at all.
D: The probe interval is left at its default, so each VM is marked down whenever two probes arrive less than one second apart.
E: The load-balancing rule has session persistence set to **Client IP**, which sends every probe to the first VM in the backend pool.
K: A,B
G: ## How an HTTP probe decides
An HTTP or HTTPS probe sends `GET` to the configured path. It marks an instance:
- **Up** when the response is HTTP 200 within the timeout.
- **Down** when the response code is anything else (301, 302, 403, 404, 500...), when nothing answers within the timeout, or when the connection is reset.
A browser follows redirects silently, so a page that "works" in a browser can still fail the probe.
## Where probes come from
Probes originate from `168.63.129.16` (service tag `AzureLoadBalancer`), not from the internet and not from your VNet range. NSGs and guest OS firewalls must allow that source on the probe port. Learn's troubleshooting steps: check the VM is healthy, check something is LISTENING on the probe port (`netstat -an`), check the guest firewall and NSGs, then capture traffic.
## Quick test
Request the probe path from another machine with a tool that does not follow redirects and look at the raw status code: anything other than 200 is what the probe sees as a failure.
W: A=Redirect instead of 200: an HTTP probe treats any status other than 200 as a failure, so a 301 to HTTPS marks the instance down even though browsers follow it.
B=Guest firewall scoped to the VNet: probe traffic comes from `168.63.129.16`, which is outside the VNet range; the firewall drops it and the instance is marked down.
X: C=No public IP on the VMs: probes come from the Azure platform address, not from the internet, and backend VMs do not need public IPs to be in a public load balancer's backend pool.
D=Default probe interval: the interval only sets how often probes are sent; probes do not fail because of their own timing, and both VMs answered the same path to the jump box.
E=Client IP persistence: distribution modes apply to client flows through load-balancing rules; each backend instance is probed individually regardless of the rule's session persistence.
T: HTTP probes need a 200 from the probe path and a firewall path open to `168.63.129.16`; redirects and VNet-only firewall scopes are classic causes of "site works, probe fails".

@ AZ-104 D4 T4.3 advanced troubleshooting
S: An order service runs on three VMs in the backend pool of an internal Standard Load Balancer with frontend `10.8.1.100`. Clients in the VNet reach the service fine, but a nightly job on one of the three backend VMs that calls `https://10.8.1.100` fails to connect. Probes are healthy. What is the cause?
A: A backend VM calling the frontend of the internal load balancer it belongs to is not supported, so the job must run from a VM outside that backend pool.
B: The internal load balancer needs an outbound rule before backend VMs can open connections, so the job fails until outbound SNAT is configured.
C: The NSG on the subnet blocks traffic from the VNet to `10.8.1.100`, because frontend addresses are covered only by the `AzureLoadBalancer` tag.
D: The session persistence setting sends the job's connection back to the same VM, which can't accept a session from its own IP address.
K: A
G: ## Internal load balancer basics
An **internal** Standard Load Balancer has a private frontend IP. Clients in the VNet, in peered VNets or on premises (over VPN or ExpressRoute) connect to that address, and load-balancing rules spread the flows across the backend pool.
## The hairpin limitation
Learn lists this limitation for Azure Load Balancer: an outbound flow from a backend VM to the frontend of the internal load balancer it sits behind fails. The FAQ asks "Can I access the frontend of my internal load balancer from the participating backend pool VM?" and answers no: the scenario is not supported.
## Practical option
Run the job on a VM that is not a member of that backend pool, so its flow to the frontend is an ordinary client flow.
## Related but different
Outbound **internet** access from behind an internal Standard Load Balancer is a separate issue: Standard internal load balancers give no default outbound access, so you add a NAT gateway, instance public IPs or an outbound rule on a public Standard Load Balancer. Here the target is a private frontend in the same VNet, so internet egress is not involved.
W: Hairpin to own frontend is unsupported: Learn documents that flows from a backend pool VM to its internal load balancer's frontend fail, which matches a failure only on the backend VM while other clients succeed.
X: B=Outbound rule required: outbound rules translate traffic to public IPs for internet access and exist only on public load balancers; they play no part in reaching a private frontend inside the VNet.
C=NSG blocks the frontend: the default `AllowVnetInBound` rule permits VNet traffic, and other clients in the same VNet connect successfully, so NSG rules are not singling out this one VM.
D=Session persistence loops back: distribution modes choose among backends for supported flows; the failure happens because the hairpin flow itself is unsupported, whatever the distribution mode.
T: A VM in an internal load balancer's backend pool cannot reach that load balancer's own frontend; call the service from a VM outside the pool.

@ AZ-104 D4 T4.3 advanced troubleshooting
S: Internet users reach an app through Azure Firewall: a DNAT rule maps the firewall's public IP `203.0.113.136` to the public IP of a Standard Load Balancer. The backend subnet's route table sends `0.0.0.0/0` to the firewall's private IP `10.0.1.4`. Probes are healthy but connections time out. What should the administrator do?
A: Add a route for `203.0.113.136/32` with next hop type Internet to the backend subnet's route table so return traffic avoids the stateful firewall.
B: Set session persistence to **Client IP and protocol** on the load-balancing rule so that the replies follow the same path back to the firewall.
C: Add an NSG rule on the backend subnet that allows the `AzureLoadBalancer` service tag on the application port for inbound user traffic.
D: Enable an HA ports rule on the public load balancer so that every protocol and port is carried symmetrically through the Azure Firewall.
K: A
G: ## Asymmetric routing
Asymmetric routing means a packet takes one path to the destination and another path back. Stateful devices such as Azure Firewall drop return packets for sessions they never saw.
## What happens here
- Inbound: client to firewall public IP, DNAT to the load balancer's public IP, then to a backend VM.
- Return: the backend subnet's default route `0.0.0.0/0` sends replies to the firewall's **private** IP `10.0.1.4`. The firewall has no matching session on that path and drops the packets, so users time out even though probes (which come from `168.63.129.16`) look healthy.
## The documented fixes
- With a public load balancer: add a specific route for the firewall's public IP with next hop **Internet**, so packets destined to `203.0.113.136` bypass the default route and return the way they came. (If a NAT gateway is on the firewall subnet, the route is for the NAT gateway's public IP instead.)
- Preferred design from Learn: use an **internal** load balancer behind the firewall, which has no asymmetric routing problem.
W: Host route for the firewall public IP: Learn's fix for a public load balancer behind Azure Firewall is a route for the firewall's public IP with next hop Internet, so return packets no longer take the default route to the firewall's private IP.
X: B=Client IP and protocol persistence: session persistence only chooses which backend VM gets a client's flows; it has no influence on the route that replies take out of the subnet.
C=Allow `AzureLoadBalancer` for user traffic: that service tag represents only the health probe source `168.63.129.16`, not user traffic, and probes are already healthy; the drop happens at the firewall.
D=HA ports on the public load balancer: HA ports rules are available only on an internal Standard Load Balancer, and they do not change the subnet's route table that causes the asymmetry.
T: A UDR default route to a stateful firewall breaks a public load balancer's return path; add an Internet route for the firewall's public IP or use an internal load balancer.

@ AZ-104 D4 T4.3 applied troubleshooting
S: A new public Standard Load Balancer has a TCP 443 rule to two web VMs. The backend subnet's NSG has only the default rules plus one rule allowing RDP from the office. Health Probe Status shows 100%, but browsers on the internet time out on the frontend IP. Which change makes the site reachable?
A: Add an inbound NSG rule that allows TCP 443 from the `Internet` service tag (or the client range) to the backend VMs on the subnet's NSG.
B: Add an inbound NSG rule that allows TCP 443 from the `AzureLoadBalancer` service tag to the backend VMs, since client traffic arrives via the load balancer.
C: Add an outbound rule to the load balancer for the backend pool so that the VMs' responses to clients can be translated back to the frontend IP.
D: Enable Floating IP on the TCP 443 rule so the VMs accept packets addressed to the frontend IP instead of packets for their own private IPs.
K: A
G: ## Standard Load Balancer is secure by default
Standard load balancers and Standard public IP addresses are **closed to inbound connections** until a network security group permits the traffic. The load balancer passes packets through to the VMs unchanged (it is a layer 4 pass-through service), so NSGs on the backend subnet or NICs see the real client source IP.
## Reading the symptoms
- Probes at 100%: the default rule `AllowAzureLoadBalancerInBound` (65001) admits probes from `168.63.129.16`, so the load balancer considers the VMs healthy.
- Clients time out: internet sources match no allow rule and fall through to `DenyAllInBound` (65500).
## Fix
Add an inbound rule such as: priority 200, source service tag `Internet` (or specific client ranges), destination port 443, protocol TCP, action Allow. Responses are allowed automatically because NSGs are stateful.
## Don't confuse
The `AzureLoadBalancer` tag stands for the probe source only; Learn says it does not include real traffic to your backend resources.
W: Allow 443 from the internet on the NSG: client packets reach the VMs with their own public source IPs, and only an explicit allow rule lets them past the default deny of a Standard deployment.
X: B=Allow from `AzureLoadBalancer`: this tag covers only the health probe address `168.63.129.16`, which is already allowed by default; client packets keep their internet source address and stay blocked.
C=Outbound rule for responses: outbound rules configure SNAT for connections the VMs start. Replies to inbound flows are handled by the load-balancing rule, and the inbound packets never reach the VMs here.
D=Floating IP: Floating IP is for port reuse designs such as SQL Server Always On listeners and needs guest OS loopback configuration; it does not open the NSG that is dropping the client packets.
T: Healthy probes but no client traffic on a Standard Load Balancer usually means the NSG lacks an inbound allow rule for the real client sources.
