# AZ-104 D3 T3.4 Create and configure Azure App Service (plans, scaling, TLS, custom domains, backups, networking, slots)

@ AZ-104 D3 T3.4 applied use-case
S: A company runs an internal web app in a Basic B1 App Service plan. The team now needs a staging deployment slot for zero-downtime releases and rule-based autoscale on CPU percentage. It wants the lowest-cost tier that provides both features. What should the administrator do?
A: Scale the plan up to the Standard tier, which adds deployment slots and rule-based autoscale on top of the Basic features
B: Keep the Basic tier and raise the instance count to three, because Basic supports slots once more than one instance runs
C: Scale the plan down to the Shared tier and enable autoscale there, since Shared apps already get CPU quotas per app
D: Scale the plan up to the IsolatedV2 tier, because slots and autoscale need an App Service Environment in a virtual network
K: A
G: ## Pricing tiers decide the features
An App Service plan's **pricing tier** sets both the size of the VMs and which App Service features the apps in it can use. Changing the tier is called **scaling up** (or down) and takes only seconds; no redeployment is needed.
- **Free and Shared**: apps run on shared VMs with CPU quotas and cannot scale out.
- **Basic**: dedicated VMs, manual scale out (up to 3 instances), custom domains, certificates, backups, VNet integration and private endpoints.
- **Standard**: everything in Basic plus **deployment slots** (up to 5) and **autoscale** (rule- and schedule-based, through Azure Monitor autoscale).
- **Premium (v2, v3, v4)**: more instances and slots, larger VMs, and the HTTP-based **automatic scaling** option.
- **IsolatedV2**: runs in an App Service Environment inside your own virtual network for network isolation.
## Example
`az appservice plan update --name plan-intranet --resource-group rg-web --sku S1` moves the plan to Standard; afterwards **Deployment slots** and **Scale out (App Service plan)** with custom autoscale rules become available.
W: Standard tier: it is the lowest tier where deployment slots and rule-based autoscale are both available, so scaling the plan up to Standard meets both needs at the lowest cost.
X: B=More Basic instances: Basic allows manual scale out only, and slots need the Standard, Premium or Isolated tier no matter how many instances run.
C=Shared tier: Free and Shared apps receive CPU minutes on shared VMs and cannot scale out at all, and they have no deployment slots.
D=IsolatedV2 tier: an App Service Environment gives network isolation, but it is not required for slots or autoscale and costs far more than Standard.
T: Deployment slots and rule-based autoscale start at the Standard tier; Basic has manual scale out only and Free/Shared cannot scale out.
V: Azure App Service, App Service plans, Azure Monitor autoscale

@ AZ-104 D3 T3.4 applied troubleshooting
S: A reporting app runs in a Standard S1 plan. Each report request loads a large dataset into memory, and single requests fail with out-of-memory errors. The administrator scaled out from 2 to 5 instances, but the same requests still fail. What should the administrator do?
A: Scale the plan up to a tier and size with more memory per instance, because each request is limited by one instance's memory
B: Scale out further to the Standard maximum of 10 instances, because spreading the requests across more VMs adds more memory
C: Enable per-app scaling on the plan, so that the reporting app gets its own VM memory separate from the other apps in the plan
D: Add a staging deployment slot and route half of the traffic to it, so that each slot handles a smaller share of the requests
K: A
G: ## Two ways to scale an App Service plan
- **Scale up** changes the pricing tier or size of the plan (for example S1 to P1v3). Every instance gets more CPU, memory and disk, and higher tiers add features.
- **Scale out** changes the number of VM instances that run the apps. More instances share the **number of requests**, but each request is still served by one instance.
## Matching the fix to the symptom
If many small requests overload the app, scaling out helps because the load balancer spreads them. If **one request** needs more memory than an instance has, adding instances changes nothing: that request still lands on a single VM with the same memory. The fix is a larger instance size.
## Example
An S1 instance has a fixed amount of memory. Moving the plan to P1v3 or P2v3 (Premium v3) gives every instance more memory; the change takes seconds and affects all apps in the plan.
W: Scale up: a larger instance size gives each VM more memory, which is what a single memory-heavy request needs. Scaling up is done by changing the plan's pricing tier and requires no code change or redeployment.
X: B=Scale out to 10: more instances share the request load, but each request still runs on one instance with the same memory limit, so the failing reports keep failing.
C=Per-app scaling: per-app scaling only limits how many of the plan's instances an app may use. It does not give an app more memory per instance.
D=Slot traffic routing: a slot runs on the same VM instances of the plan, and splitting traffic does not change the memory available to an individual request.
T: Scale out when there are too many requests; scale up when a single request needs more CPU or memory than one instance has.
V: Azure App Service, App Service plans

@ AZ-104 D3 T3.4 advanced troubleshooting
S: An App Service plan has autoscale rules: scale out by 1 if CPU > 75% or memory > 75%; scale in by 1 if CPU < 30%, and scale in by 1 if memory < 50%. Overnight, CPU stays near 20% and memory near 60%, yet the plan stays at 6 instances. Why does autoscale not scale in?
A: A scale-in action needs every scale-in rule in the profile to be met, and the memory condition below 50% is not met
B: The cooldown after the last scale-out blocks every scale-in action until the next daily profile starts the following day
C: The default instance count of the profile is 6, and autoscale never scales below the default while metrics are available
D: App Service plans support scale-out rules only, so scaling in must be done manually or by a separate scheduled runbook
K: A
G: ## How autoscale combines several rules
An Azure Monitor autoscale setting has profiles with a minimum, maximum and default instance count and a set of rules. When a profile has several rules, the engine treats the two directions differently:
- **Scale out**: runs if **any** scale-out rule is met.
- **Scale in**: runs only if **all** scale-in rules are met.
This is deliberate: removing capacity is the risky direction, so every metric must agree that the load is low.
## Example
With the rules in the scenario, CPU 20% meets the CPU scale-in rule, but memory 60% does not meet "memory < 50%". The engine does not scale in. It would scale in only when, for example, CPU is 29% and memory 49% at the same time. To get scale-in at night, the team can raise the memory scale-in threshold (keeping a margin below the scale-out threshold to avoid flapping) or add a schedule-based profile for the night.
## The default instance count
The default count is used when autoscale cannot read metrics: it scales out to the default if current capacity is lower, and it does not scale in if capacity is already higher. With metrics available, it plays no role.
W: All scale-in rules must be met: CPU 20% satisfies its rule, but memory 60% does not satisfy "below 50%", so the scale-in condition as a whole is false and the plan stays at 6 instances.
X: B=Cooldown: a cooldown is a short wait after a scale action (minutes), not a block until the next day. Once it ends, the rules are evaluated again.
C=Default instance count: the default is used only when metrics cannot be read. With metrics available, autoscale scales between the minimum and maximum.
D=Scale-out only: App Service plans support both scale-out and scale-in rules in Azure Monitor autoscale; no runbook is needed.
T: Autoscale scales out when any scale-out rule fires but scales in only when every scale-in rule is met.
V: Azure Monitor autoscale, Azure App Service

@ AZ-104 D3 T3.4 applied use-case
S: A Standard S3 App Service plan autoscales between 4 and 10 instances for a busy storefront app. A small admin app in the same plan should never run on more than 2 of those instances, while the storefront keeps using all of them. What should the administrator configure?
A: Enable per-app scaling on the plan and set the admin app's number of workers to 2, leaving the storefront app without a limit
B: Add a separate autoscale setting to the admin app with a maximum of 2 instances, since each app in a plan can autoscale alone
C: Move the admin app into a deployment slot of the storefront app, because slots run on a fixed subset of two plan instances
D: Set the admin app's Traffic % to 20 in the deployment slots page, so that it receives requests on only two of the instances
K: A
G: ## Apps share the plan's instances by default
All apps in an App Service plan run on **all** of the plan's VM instances. When the plan scales out, every app scales with it, including small apps that do not need it.
## Per-app scaling
Per-app scaling (Standard, Premium and Isolated tiers) changes this:
- On the plan, set `perSiteScaling` to `true`.
- On each app or slot that should be limited, set `siteConfig.numberOfWorkers`, the maximum number of plan instances it may use.
- Apps without a limit keep using every instance.
The limit does not change the plan's capacity or billing; you still pay for the plan's instances. It also does not react to load: it is a fixed cap within the plan's workers.
## Example
Plan capacity 10, storefront without limit, admin app `numberOfWorkers = 2`: the storefront runs on up to 10 instances, the admin app on at most 2.
W: Per-app scaling: with `perSiteScaling` enabled on the plan, `numberOfWorkers = 2` caps the admin app at two instances while the storefront continues to run on every instance the autoscale setting provides.
X: B=Autoscale per app: autoscale is configured on the App Service plan and scales the whole plan; it has no per-app instance limit.
C=Deployment slot: a slot is another live app in the same plan and runs on the same instances; it is not pinned to a subset of instances.
D=Traffic %: traffic routing sends a share of production requests to a slot. It does not limit how many instances an app runs on.
T: To keep one app on fewer instances than the plan has, enable per-app scaling on the plan and set that app's number of workers.
V: Azure App Service, App Service plans

@ AZ-104 D3 T3.4 advanced troubleshooting
S: An administrator wants to move a .NET app from its Windows App Service plan in resource group rg-legacy to an existing Linux plan in rg-web, in the same region. In the app's Change App Service plan pane, the Linux plan is not listed. What is the reason?
A: An app can move only to a plan in the same resource group and region with the same OS type, so this move is not supported
B: The Linux plan is hidden until the administrator is granted the Website Contributor role on the rg-web resource group itself
C: The Linux plan must first be scaled to the same pricing tier as the Windows plan, because moves require identical tiers
D: The Change App Service plan pane lists Linux plans only after the app's stack setting is changed to a Linux runtime version
K: A
G: ## Moving an app between plans
The region and OS of an app come from its App Service plan. You can move an app to another plan only when:
- the source and target plans are in the **same resource group** and **same region**,
- both plans have the **same OS type** (Windows to Linux, or the reverse, is not supported),
- the plans are in the same deployment unit (webspace); plans created in the same resource group, region and OS share one.
The **Change App Service plan** pane therefore lists only plans that qualify. Virtual network integration must be disconnected before a move.
## Options when the move is not possible
- To change OS or resource group combination: create a new app in the target Linux plan and deploy the code to it.
- To change region: clone the app or redeploy it, because a plan's region cannot be changed.
## Example
`app-crm` on Windows plan `plan-win` (rg-legacy) can move to another Windows plan in rg-legacy in the same region, but never to Linux plan `plan-linux` in rg-web.
W: Same resource group, region and OS: the target plan is Linux and in a different resource group, so it fails two of the conditions and the pane never offers it. The app must be recreated on the Linux plan and redeployed.
X: B=Missing role: the pane filters by plan compatibility, not by the caller's role assignments. Even an Owner sees only plans in the same resource group, region and OS.
C=Identical tiers: moves between different tiers are allowed (a lower tier can remove features). The tier is not why the plan is missing.
D=Change stack first: an app's runtime setting does not change the OS of its plan, and Windows-to-Linux moves are not supported at all.
T: An app can move only between App Service plans in the same resource group, region and OS type; changing OS means a new app and a redeploy.
V: Azure App Service, App Service plans

@ AZ-104 D3 T3.4 advanced troubleshooting
S: A Standard-tier app serves www.contoso.com and the root domain contoso.com, with access restrictions that allow only the company's office IP ranges. A free App Service managed certificate is created for www.contoso.com, but creation fails for contoso.com. What should the administrator do?
A: Secure contoso.com with a certificate from another source, such as an App Service certificate or a Key Vault certificate
B: Replace the A record for contoso.com with a CNAME record that points directly to the app's azurewebsites.net host name
C: Request the managed certificate for *.contoso.com instead, because one wildcard managed certificate covers the root domain
D: Scale the plan up to Premium v3, because free managed certificates for root domains are only issued on Premium tiers
K: A
G: ## App Service managed certificates
A free App Service managed certificate is issued by DigiCert, bound to one custom domain, and renewed automatically by App Service. It needs a Basic or higher plan and has limits:
- no wildcard certificates, not exportable, no private DNS, not available in an App Service Environment
- a **subdomain** needs a CNAME that points directly to `<app>.azurewebsites.net` (or Traffic Manager)
- a **root (apex) domain** needs an A record to the app's IP, and the app must be reachable from the internet: Microsoft states it must not have IP restrictions, because both issuance and periodic renewal depend on that
## Other certificate sources
- **App Service certificate**: bought in Azure, managed and renewable, exportable.
- **Import from Key Vault** or **upload a PFX**: your own certificate from a CA, with the full chain.
None of these depends on App Service reaching your app over the internet to issue or renew the certificate, so they work with access restrictions.
## Example
`www.contoso.com` (CNAME) got a managed certificate. For `contoso.com`, the office-only restrictions block validation, so an App Service certificate or a Key Vault certificate is bound with an SNI SSL binding instead.
W: Use another certificate source: the managed certificate for a root domain requires the app to be reachable without IP restrictions for issuance and every renewal. An App Service certificate or a Key Vault/PFX certificate secures contoso.com while the office-only access restrictions stay in place.
X: B=CNAME at the root: a CNAME at the zone apex is not allowed by DNS rules (RFC 1912), and Microsoft recommends an A record for root domains. The blocked validation would remain anyway.
C=Wildcard managed certificate: managed certificates do not support wildcards, and a wildcard does not cover the bare root domain either.
D=Premium tier: managed certificates are available from the Basic tier up. The tier is not the problem; the IP restrictions are.
T: Free managed certificates for a root domain need an internet-reachable app with no IP restrictions; otherwise use an App Service certificate or your own certificate.
V: Azure App Service, App Service managed certificate, Azure Key Vault

@ AZ-104 D3 T3.4 applied use-case
S: A company runs about 30 customer subdomains such as a.contoso.com and b.contoso.com on one App Service app and adds new ones weekly. It wants one wildcard certificate for *.contoso.com bound to these domains. Which TWO ways can provide this certificate? (Select TWO)
A: Upload a password-protected PFX file of a wildcard certificate from a CA, including the intermediate and root certificates
B: Import a wildcard certificate that the company stores in Azure Key Vault, after granting App Service read access to the vault
C: Create a free App Service managed certificate for *.contoso.com and let App Service renew it automatically each period
D: Upload the wildcard certificate as a .cer file under Public key certificates and select it in the custom domain binding
E: Bind the app's default *.azurewebsites.net certificate to the contoso.com subdomains with an IP-based SSL binding type
K: A,B
G: ## Certificate options in App Service
App Service can secure a custom domain with a **private certificate** (one with its private key) from several sources:
- **Free App Service managed certificate**: easiest, but it does **not** support wildcards and cannot be exported.
- **App Service certificate**: bought and managed in Azure.
- **Import from Key Vault**: a PKCS12 certificate kept in your vault. App Service (`Microsoft.Azure.WebSites`) needs read access, for example the **Key Vault Certificate User** role or Get permissions in an access policy.
- **Upload a private certificate**: a password-protected PFX file with all intermediate and root certificates. For a TLS binding it must have the server authentication EKU and come from a trusted CA.
**Public certificates** (.cer) hold no private key. They are for app code that calls remote resources and cannot secure a custom domain.
## Example
`*.contoso.com` is bought from a CA, exported as `wildcard.pfx` with its chain, and uploaded once; each new subdomain then gets an SNI SSL binding that uses it.
W: A=Upload a wildcard PFX: a password-protected PFX with the full chain, the server authentication EKU and a trusted CA meets the private certificate requirements and can be bound to every subdomain.
B=Import from Key Vault: once App Service has read access to the vault, a wildcard certificate stored there can be imported and bound, and App Service syncs new versions from the vault.
X: C=Managed wildcard certificate: free managed certificates do not support wildcard domains; one would be needed per subdomain.
D=Public certificate: a .cer public certificate has no private key, so it can be loaded for app code but cannot secure a custom domain in a TLS binding.
E=Default azurewebsites.net certificate: that certificate covers only Microsoft's azurewebsites.net names, so browsers would reject it for contoso.com subdomains.
T: Wildcard domains need a private certificate from your own CA (uploaded PFX or Key Vault) or an App Service certificate; the free managed certificate does not do wildcards.
V: Azure App Service, Azure Key Vault

@ AZ-104 D3 T3.4 applied use-case
S: An administrator is adding the root domain fabrikam.com as a custom domain to an App Service app. The domain's DNS is hosted at a third-party registrar. Following Microsoft's guidance, which TWO DNS records should be created at the registrar? (Select TWO)
A: An A record for the host @ whose value is the app's IP address shown in the Add custom domain dialog
B: A TXT record for the host asuid whose value is the domain verification ID shown in the Add custom domain dialog
C: A CNAME record for the host @ whose value is the app's default host name, such as fabrikam-web.azurewebsites.net
D: A TXT record for the host asuid.www whose value is the domain verification ID shown in the Add custom domain dialog
E: An MX record for the host @ whose value is the app's default host name, so that App Service can validate the domain
K: A,B
G: ## Two records per custom domain
Mapping a custom domain to App Service needs two DNS records at the domain provider:
- a **mapping record** that sends traffic to the app
- a **TXT verification record** named `asuid` (for the root) or `asuid.<subdomain>`, holding the app's **domain verification ID**. It proves ownership and protects against subdomain takeover; Microsoft says it is not strictly required but highly recommended.
## Root domain versus subdomain
- **`fabrikam.com`**: Mapping record: A `@` to the app's IP; Verification record: TXT `asuid`
- **`www.fabrikam.com`**: Mapping record: CNAME `www` to `<app>.azurewebsites.net`; Verification record: TXT `asuid.www`
DNS does not allow a CNAME at the zone apex (RFC 1912), so a root domain uses an A record. Subdomains should use a CNAME because the app's IP address can change.
The plan must be a paid tier (not Free F1), and the domain must be in a public DNS zone.
W: A=A record at @: the root domain cannot be a CNAME, so it maps to the app's IP address with an A record.
B=TXT asuid: App Service reads the `asuid` TXT record to verify that you own fabrikam.com before it accepts the domain.
X: C=CNAME at @: a CNAME at the root conflicts with the zone's other apex records and is not used for root domains; Microsoft recommends an A record there.
D=TXT asuid.www: this name verifies the www subdomain, not the root domain, so it does not prove ownership of fabrikam.com.
E=MX record: MX records route email to mail servers. App Service does not use them for mapping or verification.
T: A root domain needs an A record at `@` plus a TXT record `asuid`; a subdomain needs a CNAME plus `asuid.<subdomain>`.
V: Azure App Service, Azure DNS

@ AZ-104 D3 T3.4 applied use-case
S: An audit of a payment app finds that it accepts TLS 1.0 connections from a setting made years ago for a retired partner, and that it still answers plain HTTP requests on its custom domain. Which TWO settings fix both findings? (Select TWO)
A: Set the app's minimum inbound TLS version to 1.2 so that clients that offer only TLS 1.0 or 1.1 are rejected
B: Turn on HTTPS Only so that every HTTP request to the app is redirected to the matching HTTPS address instead
C: Set client certificate mode to Required so that browsers must present a certificate before the app answers HTTP
D: Change the custom domain's binding from SNI SSL to IP-based SSL so that the app gets a dedicated TLS address
E: Enable end-to-end TLS encryption so that traffic from the front ends to the app's workers is encrypted as well
K: A,B
G: ## Where TLS ends in App Service
Clients connect to App Service **front ends**, which terminate TLS and forward the request to the workers that run your code. Settings on the front end decide which connections are accepted:
- **Minimum inbound TLS version**: TLS 1.2 is the default for new apps; older apps or manual changes may allow 1.0/1.1. TLS 1.3 is also supported. Raising the minimum makes the front end refuse older protocol versions.
- **HTTPS Only**: redirects HTTP requests to HTTPS so content is never served over plain HTTP.
## Other TLS-related settings
- **Client certificates (mutual TLS)** make clients authenticate with their own certificate; that is identity, not protocol enforcement.
- **SNI SSL vs IP-based SSL** chooses how a certificate is bound (shared IP with SNI, or a dedicated IP for one certificate).
- **End-to-end TLS encryption** encrypts traffic between front ends and workers inside Azure.
## Example
`az webapp config set --min-tls-version 1.2` and `az webapp update --https-only true` close both audit findings.
W: A=Minimum TLS 1.2: raising the minimum inbound TLS version makes the front end reject TLS 1.0 and 1.1 handshakes, which closes the first finding.
B=HTTPS Only: with HTTPS Only on, plain HTTP requests are redirected to HTTPS, so the app no longer serves content over HTTP.
X: C=Client certificates required: mutual TLS asks clients for their own certificate. It does not change which TLS versions are allowed or redirect HTTP, and normal customers would be locked out.
D=IP-based SSL: this only gives the binding a dedicated IP address; the allowed TLS versions and HTTP handling stay the same.
E=End-to-end TLS: it encrypts the hop inside Azure from front ends to workers. Clients could still connect with TLS 1.0 or plain HTTP.
T: Use the minimum TLS version setting to block old protocols and HTTPS Only to redirect HTTP; neither is done by certificate or binding settings.

@ AZ-104 D3 T3.4 applied use-case
S: A Standard-tier app has only the automatic backups. Compliance now requires monthly backups kept for 90 days and copies that the team can download for an offline archive. What should the administrator configure?
A: Custom scheduled backups to a storage account container, with backup retention set to keep them indefinitely
B: A longer retention period on the automatic backups, and then export each one from the Backups page as a ZIP
C: A scale up to a Premium tier, because Premium extends automatic backup retention to 90 days and adds downloads
D: A second deployment slot that receives a nightly restore of production, so the slot acts as the backup copy
K: A
G: ## Automatic and custom backups
App Service has two backup types (Basic, Standard, Premium and Isolated tiers):
- **Configuration**: Automatic: none; Custom: storage account and container
- **Frequency**: Automatic: hourly, fixed; Custom: on demand or scheduled (every 2 hours at most often)
- **Retention**: Automatic: 30 days, not configurable; Custom: 0-30 days, or indefinite
- **Downloadable**: Automatic: no; Custom: yes, as blobs in your storage account
- **Size**: Automatic: 30 GB; Custom: 10 GB
Each custom backup is a ZIP file plus an XML manifest in the container; the team can download these blobs or copy them to an archive. On-demand custom backups are kept indefinitely.
## Retention beyond 30 days
The custom retention setting accepts 0-30 days or indefinite; there is no 90-day value. To keep backups for 90 days, set retention to indefinite and remove backups older than the policy requires (for example with a storage lifecycle rule or a cleanup job).
## Example
**Backups** > **Configure custom backups** > storage account `stwebbackup`, container `app-backups` > **Set schedule** with a monthly frequency and retention set to indefinite, so no backup is deleted before 90 days. Custom backups need SAS-based access to the storage account; managed identity is not supported.
W: Custom scheduled backups with indefinite retention: they are written to the team's own storage account, are not deleted after 30 days and are downloadable as blobs, which meets both requirements.
X: B=Longer automatic retention: automatic backup retention is fixed at 30 days and the backups are not downloadable.
C=Premium tier: automatic backups behave the same in every supported tier: 30-day retention and no download. A higher tier does not change that.
D=Restore into a slot: a slot is a live app, not a retained point-in-time copy, and it holds only the latest restore, not 90 days of history.
T: Automatic backups are hourly, kept 30 days and not downloadable; for longer retention or downloadable copies, configure custom backups to a storage account (retention 0-30 days or indefinite).
V: Azure App Service, Azure Storage

@ AZ-104 D3 T3.4 advanced troubleshooting
S: Custom backups of a Premium v3 web app worked until the security team set the target storage account's firewall to allow only selected virtual networks. Now every backup fails with a storage access error. Which change restores the backups while keeping the firewall?
A: Integrate the app with a VNet subnet the storage firewall allows, then enable backup and restore over virtual network integration
B: Assign the app's system-assigned managed identity the Storage Blob Data Contributor role on the backup storage account itself
C: Create a private endpoint for the web app in the virtual network that the storage firewall allows, then rerun the backup job
D: Switch the app to automatic backups and point them at the same storage account, because automatic backups use trusted access
K: A
G: ## Custom backups and network rules
A custom backup writes a ZIP to a storage account through a SAS URL. When the storage firewall allows only selected networks, App Service can still reach it if:
- the app uses **virtual network integration** (or runs in an App Service Environment v3),
- the storage account allows the integrated virtual network or subnet, and
- **Backup/restore over virtual network integration** is selected in the custom backup configuration.
After that, manual and scheduled backups and restores go through the virtual network. Deployment slots need this configured separately.
## What does not help
- Custom backups authenticate with SAS; **managed identity authentication is not supported** for App Service backup and restore.
- A private endpoint on the app handles **inbound** traffic to the app, not the app's outbound calls to storage.
## Example
App `app-sales` integrates with subnet `snet-appsvc` (delegated to `Microsoft.Web/serverFarms`); the storage account allows `snet-appsvc`; the backup setting **Backup/restore over virtual network integration** is checked.
W: VNet integration plus the backup option: the backup traffic then leaves the app from the integration subnet, which the storage firewall allows, and the backup setting tells App Service to use that path for every backup and restore.
X: B=Managed identity role: App Service backup and restore use SAS-based authorization; managed identity authentication to the storage account is not supported for backups.
C=Private endpoint on the app: a private endpoint carries only inbound traffic to the app. The backup is an outbound write to storage and still arrives from outside the allowed network.
D=Automatic backups: automatic backups are stored by the platform, not in your storage account, and they keep only 30 days and are not downloadable.
T: To back up to a firewalled storage account, use VNet integration, allow that subnet on the storage account, and enable backup over virtual network integration.

@ AZ-104 D3 T3.4 applied use-case
S: A web app in a Premium v3 plan must call a REST API on a VM at 10.20.1.4 in the VNet vnet-prod, which has no public IP address. The web app itself must stay reachable from the internet. What should the administrator configure on the app?
A: Virtual network integration with an empty subnet of vnet-prod delegated to Microsoft.Web/serverFarms for the app's outbound calls
B: A private endpoint for the app in a subnet of vnet-prod, so that the app's calls to the VM leave from a private IP in that subnet
C: An access restriction rule of type Virtual Network for the VM's subnet, with the Microsoft.Web service endpoint enabled on it
D: An IP-based SSL binding on the app, so that the app gets a dedicated IP address that the VM's network security group can allow
K: A
G: ## Inbound and outbound are separate features
App Service networking features each work in one direction:
- App calls resources in or through a VNet (outbound): **Virtual network integration**
- Clients reach the app privately (inbound): **Private endpoint**
- Filter who may call the app (inbound): **Access restrictions** (IP, service tag, VNet via service endpoints)
## Virtual network integration
- Available in Basic, Standard, Premium (v2/v3/v4) and Elastic Premium.
- Needs a **dedicated subnet** in the same region, delegated to `Microsoft.Web/serverFarms`; each plan instance uses one IP. Microsoft suggests sizing for double the maximum scale (a `/26` covers a multitenant plan's maximum).
- Private (RFC 1918) traffic goes into the VNet; with outbound internet traffic routing enabled, all outbound traffic does.
- It gives no inbound access; the app stays public unless you change that.
## Example
`az webapp vnet-integration add --name app-orders --resource-group rg-web --vnet vnet-prod --subnet snet-appsvc-int`, then the app calls `http://10.20.1.4/api`.
W: Virtual network integration: it mounts interfaces from the delegated subnet on the app's workers, so calls to 10.20.1.4 travel inside vnet-prod while inbound internet access to the app is unchanged.
X: B=Private endpoint: a private endpoint is used only for incoming traffic to the app; outgoing calls do not use it, so the VM is still unreachable.
C=Virtual Network access restriction: access restrictions filter requests coming into the app. They do not give the app a route into the VNet.
D=IP-based SSL: a dedicated inbound IP for a TLS binding does not create any network path from the app to a private address.
T: VNet integration is for the app's outbound calls into a VNet; private endpoints are for private inbound access to the app.
V: Azure App Service, Azure Virtual Network

@ AZ-104 D3 T3.4 advanced troubleshooting
S: An administrator created a private endpoint for app-hr in vnet-corp and disabled public network access. VMs in vnet-corp use Azure-provided DNS, and when they browse to app-hr.azurewebsites.net they get HTTP 403 errors. What should the administrator do?
A: Create a privatelink.azurewebsites.net private DNS zone linked to vnet-corp with an A record for app-hr pointing to the endpoint IP
B: Add an access restriction rule that allows the VM subnet of vnet-corp, because private endpoint traffic is still evaluated by those rules
C: Enable virtual network integration for app-hr in vnet-corp, because the private endpoint carries traffic only after the app joins the VNet
D: Re-enable public network access on app-hr, because a private endpoint answers only after the public endpoint has validated the client
K: A
G: ## How name resolution changes with a private endpoint
Without a private endpoint, `app-hr.azurewebsites.net` resolves through CNAMEs to a public IP. When a private endpoint is created, the public record becomes a CNAME to `app-hr.privatelink.azurewebsites.net`.
- If clients can resolve `privatelink.azurewebsites.net` to the private endpoint IP, traffic goes over Private Link.
- If not, the name still resolves to the **public** IP. With public network access disabled, that returns **403**.
## The fix
Create an **Azure DNS private zone** `privatelink.azurewebsites.net`, link it to the virtual network, and add an A record for `app-hr` (and `app-hr.scm` for the deployment site) with the private endpoint IP. A **private DNS zone group** on the endpoint adds the records automatically. On-premises clients need forwarding to Azure DNS or their own records.
## Example
After the fix, `nslookup app-hr.azurewebsites.net` on a VM returns `10.30.2.5` (the endpoint's NIC IP) instead of a public address.
W: Private DNS zone: once vnet-corp resolves app-hr through privatelink.azurewebsites.net to the endpoint IP, requests use the private endpoint and are no longer sent to the disabled public endpoint.
X: B=Access restriction rule: access restrictions are not evaluated for private endpoint traffic, and the requests here are going to the public endpoint because of DNS.
C=Virtual network integration: VNet integration handles the app's outbound calls; the private endpoint works on its own for inbound traffic.
D=Re-enable public access: this would make the app reachable from the internet again and defeats the purpose; the private endpoint does not depend on the public endpoint.
T: A private endpoint for App Service works only when clients resolve the app name through privatelink.azurewebsites.net to the endpoint IP.
V: Azure App Service, Azure Private Link, Azure DNS private zones

@ AZ-104 D3 T3.4 advanced use-case
S: A web app is published through the company's Azure Front Door profile. The administrator must make the app reject any request that does not come through that specific Front Door profile, including requests sent through other customers' Front Door profiles. Which access restriction should be added?
A: An Allow rule with the AzureFrontDoor.Backend service tag and an X-Azure-FDID header filter set to the profile's Front Door ID
B: An Allow rule with the AzureFrontDoor.Backend service tag only, because that tag lists the IP ranges of the company's own profile
C: An Allow rule of type Virtual Network for the Front Door subnet, with the Microsoft.Web service endpoint enabled on that subnet
D: An Allow rule with an X-Forwarded-Host header filter set to the app's host name and no source IP range or service tag in the rule
K: A
G: ## Access restriction basics
Access restrictions are a priority-ordered allow/deny list evaluated on the App Service front ends. Once one rule exists, an implicit **deny all** applies to unmatched requests (unless the unmatched action is set to Allow); blocked requests get **403**. Rule types:
- IPv4/IPv6 CIDR ranges
- **Service tags** (Azure-maintained IP ranges, such as `AzureFrontDoor.Backend`)
- Virtual Network subnets (through `Microsoft.Web` service endpoints)
Any rule can add **HTTP header filters** on `X-Forwarded-For`, `X-Forwarded-Host`, `X-Azure-FDID` or `X-FD-HealthProbe`; the source and the header must both match.
## Locking an app to one Front Door profile
Front Door traffic comes from the shared `AzureFrontDoor.Backend` ranges, used by **every** Front Door customer. Each profile sends its unique ID in the `X-Azure-FDID` header, so the rule combines both.
## Example
`Add-AzWebAppAccessRestrictionRule -ResourceGroupName rg-web -WebAppName app-shop -Name "Front Door only" -Priority 100 -Action Allow -ServiceTag AzureFrontDoor.Backend -HttpHeader @{'x-azure-fdid' = $afd.FrontDoorId}`
W: Service tag plus X-Azure-FDID: the tag admits only Front Door's back-end IP ranges and the header filter admits only requests carrying the company's own profile ID, so traffic through any other path or profile hits the implicit deny.
X: B=Service tag only: the AzureFrontDoor.Backend ranges are shared by all Front Door customers, so another company's profile could still reach the app.
C=Virtual Network rule: Front Door is a global edge service and does not send requests from a subnet in the company's virtual network.
D=X-Forwarded-Host only: anyone can set that header on a direct request, and it does not identify the Front Door profile at all.
T: To accept only your own Front Door, allow the AzureFrontDoor.Backend service tag and filter on your profile's X-Azure-FDID header.
V: Azure App Service, Azure Front Door

@ AZ-104 D3 T3.4 applied troubleshooting
S: An app has a staging slot whose connection string SqlDb points to the test database. After the team swapped staging into production, the production app started writing orders to the test database. How should the administrator prevent this on future swaps?
A: Mark the SqlDb connection string as a deployment slot setting in each slot, with each slot keeping its own database value
B: Use swap with preview for every release, because a preview swap keeps the production slot's own connection strings
C: Turn on auto swap for the staging slot, because an automatic swap leaves connection strings out of the swap operation
D: Move the connection string from the Connection strings section into App settings, since app settings never swap
K: A
G: ## What moves in a swap
A swap exchanges the content and most of the configuration of two slots. By default these **follow the app** across a swap:
- app settings and connection strings (unless marked as slot settings)
- language/framework versions, platform bitness, WebSockets, handler mappings, public certificates
These **stay with the slot**: custom domains, non-public certificates and TLS settings, scale settings, managed identities, VNet integration, and (by default) HTTPS Only, TLS version, IP restrictions and Always On.
## Deployment slot settings
To keep a value tied to a slot, select **Deployment slot setting** on the setting (or use `--slot-settings` in `az webapp config connection-string set`). During a swap, App Service applies the target slot's slot-specific values to the source slot before swapping, so production always keeps the production database.
## Example
Production: `SqlDb = Server=sql-prod...` (slot setting). Staging: `SqlDb = Server=sql-test...` (slot setting). After a swap, production code runs with `sql-prod` and staging with `sql-test`.
W: Slot setting: marking SqlDb as a deployment slot setting makes it stick to its slot, so each slot keeps its own database connection whatever code is swapped into it.
X: B=Swap with preview: preview pauses after applying the target's slot-specific settings, but a setting that is not marked as slot-specific still swaps when the swap completes.
C=Auto swap: auto swap triggers the same swap automatically after a deployment; it follows the same rules about which settings move.
D=App settings: app settings swap by default exactly like connection strings; only marking them as slot settings keeps them in place.
T: App settings and connection strings swap by default; mark them as deployment slot settings to keep per-environment values in their slot.
V: Azure App Service

@ AZ-104 D3 T3.4 advanced use-case
S: A pipeline swaps a staging slot into production after each deployment. The app answers / at once, before its caches are loaded. Its /health endpoint responds only after cache loading ends: 200 on success, 503 on failure. How can every swap warm up through /health and stop unless it returns 200, without a manual step?
A: Set WEBSITE_SWAP_WARMUP_PING_PATH to /health and WEBSITE_SWAP_WARMUP_PING_STATUSES to 200 on the slot
B: Turn on Always On for the staging slot, so its instances are fully loaded before the pipeline starts the swap
C: Use swap with preview in the pipeline, because its first phase checks that /health answers 200 on all instances
D: Set the staging slot's Traffic % to 100 for two minutes before the swap, so real requests fill the app's caches
K: A
G: ## Warm-up during a swap
Before switching routing, a swap restarts the source slot's instances with the target's slot-specific settings and **warms them up**. By default, App Service sends an HTTP request to `/` on each instance, and **any** HTTP response counts as warmed up. For an app that answers `/` before it is ready, that is too early.
## Custom warm-up
- `WEBSITE_SWAP_WARMUP_PING_PATH`: the path to ping, for example `/health` (default `/`).
- `WEBSITE_SWAP_WARMUP_PING_STATUSES`: the HTTP codes that count as success, for example `200,202` (by default every code is valid). If the response code is not in the list, the warm-up and the swap are stopped; production keeps running the old version.
- `applicationInitialization` in Web.config (Windows) lists initialization pages; it runs at every app start.
- `WEBSITE_WARMUP_PATH` pings a path on every restart, not only during swaps.
## Example
App settings on the slot: `WEBSITE_SWAP_WARMUP_PING_PATH=/health`, `WEBSITE_SWAP_WARMUP_PING_STATUSES=200`. The swap now waits for each instance's `/health` response; it switches routing only if every instance returns 200 and stops if any returns 503.
W: Custom warm-up path and statuses: the swap pings /health on every instance, waits for the response and continues only on a 200, so routing switches only after the caches loaded, and a 503 stops the swap, with no manual validation step.
X: B=Always On: Always On keeps an app loaded so it is not unloaded when idle; it does not make the swap wait for /health, and the swap restarts the instances anyway.
C=Swap with preview: the first phase applies the target slot settings and then pauses for a person to validate and complete the swap; it does not check a health path by itself and adds a manual step.
D=Traffic % to 100: sending real users to an unwarmed slot exposes them to the slow start, and the swap still restarts the instances afterwards.
T: Use WEBSITE_SWAP_WARMUP_PING_PATH and WEBSITE_SWAP_WARMUP_PING_STATUSES so a slot swap warms up through a health endpoint and stops unless it returns an allowed status code.
V: Azure App Service
