# AZ-104 D4 T4.2 Configure secure access to virtual networks (NSGs, ASGs, effective security rules, Azure Bastion, service endpoints, private endpoints)

@ AZ-104 D4 T4.2 applied troubleshooting
S: An administrator adds an inbound rule to the NSG on a web subnet: priority 300, Allow, TCP 443, source `Internet`. A colleague had earlier added a rule at priority 250 that denies all inbound traffic from any source on any port. HTTPS requests from the internet still fail. What should the administrator do?
A: Change the HTTPS allow rule to a priority number lower than 250, such as 200, so that it is processed before the custom deny rule
B: Add an outbound rule that allows TCP 443 to the `Internet` tag so that the responses to the HTTPS requests can leave the subnet
C: Delete the `DenyAllInbound` default rule at priority 65500, because it overrides custom rules that allow traffic from the internet
D: Change the HTTPS allow rule to priority 4000, because a higher number gives a rule more weight when two rules match one flow
K: A
G: ## How an NSG picks a rule
Every NSG rule has a **priority** between 100 and 4096. Azure processes rules in priority order, **lower numbers first**, and stops at the first rule that matches the flow (source, source port, destination, destination port, protocol). Any later rule that would also match is never looked at.
## Default rules
Each NSG also has default rules at 65000-65500, such as `AllowVNetInBound` (65000) and `DenyAllInbound` (65500). They cannot be deleted, but because their numbers are higher than any custom rule they only apply when no custom rule matched first.
## Stateful filtering
NSGs keep a flow record for each connection. When inbound traffic is allowed, the reply is allowed automatically; no matching outbound rule is needed.
## Example
- 200 Allow TCP 443 from `Internet`
- 250 Deny all from Any
An HTTPS packet matches priority 200 and is allowed; an SSH packet skips 200, matches 250 and is denied.
W: Lower priority number: the deny-all rule at 250 matches HTTPS first, so the allow rule at 300 is never evaluated. Moving the allow rule to a number below 250 makes it the first match for TCP 443 while the deny rule still blocks everything else.
X: B=Outbound rule for replies: NSGs are stateful. The flow record created for an allowed inbound connection lets the response leave without an outbound rule, and the request is being dropped on the way in anyway.
C=Delete DenyAllInbound: default rules cannot be removed, only overridden by custom rules with lower numbers. It is also not the rule blocking the traffic; the custom deny at 250 matches before 65500 is reached.
D=Priority 4000: a higher number means a lower priority. At 4000 the allow rule is processed even later than before, so the deny rule at 250 still matches HTTPS first.
T: NSG rules run from the lowest priority number up and stop at the first match, so an allow rule must have a lower number than any broader deny rule.

@ AZ-104 D4 T4.2 advanced troubleshooting
S: VM1 runs in Subnet1. NSG-Subnet is associated with Subnet1 and NSG-Nic is associated with VM1's network interface. An administrator is troubleshooting web traffic to and from VM1. Which TWO statements about how Azure evaluates these NSGs are correct? (Select TWO)
A: Inbound internet traffic to VM1 on TCP 80 reaches the VM only when both NSG-Subnet and NSG-Nic contain a rule that allows it
B: For outbound traffic from VM1, Azure processes the rules in NSG-Nic on the network interface first and then those in NSG-Subnet
C: An allow rule in NSG-Subnet is final for inbound traffic, so NSG-Nic is skipped for any flow that the subnet's NSG has allowed
D: The responses to an allowed inbound HTTP session need their own outbound allow rule in both NSG-Nic and in NSG-Subnet
E: VM1's network interface can also be associated with a second NSG, and Azure merges both of them into one list by priority
K: A,B
G: ## Two places to attach an NSG
An NSG can be associated with a **subnet**, a **network interface**, or both. On a subnet or a network interface you pick one NSG (or None) in its Network security group setting, and the same NSG can be reused on as many subnets and interfaces as you like.
## Order of evaluation
- **Inbound**: Azure processes the subnet's NSG first, then the network interface's NSG. If the subnet NSG denies the flow, the NIC NSG never sees it. If it allows the flow, the NIC NSG still has to allow it too.
- **Outbound**: the order is reversed: the NIC's NSG first, then the subnet's NSG. A deny in either one blocks the traffic.
The same order applies to traffic between VMs in the same subnet.
## Practical advice
Learn recommends choosing one level (subnet or NIC) where possible, because rules at both levels often conflict and are hard to troubleshoot. To see the combined result, open **Effective security rules** on the network interface, which lists the rules of both NSGs.
W: A=Both must allow inbound: the subnet NSG is checked first and the NIC NSG second, so an inbound flow needs an allow in each. A rule only in NSG-Subnet still ends at `DenyAllInbound` in NSG-Nic.
B=NIC first for outbound: for traffic leaving VM1, Azure evaluates the network interface's NSG and then the subnet's NSG, so a deny in NSG-Nic stops the traffic before NSG-Subnet sees it.
X: C=Subnet allow is final: an allow in the subnet NSG only passes the flow on to the next level. The NIC NSG is still processed, and its default `DenyAllInbound` rule blocks anything it does not allow.
D=Outbound rule for responses: NSGs are stateful. Once an inbound flow is allowed, its return traffic is allowed through both NSGs without extra outbound rules.
E=Second NSG on the NIC: the network interface's Network security group setting holds a single NSG (or None), so there is no second NIC-level NSG to merge. To combine rules you edit that one NSG or use the subnet-level NSG.
T: Inbound traffic passes the subnet NSG and then the NIC NSG, outbound traffic passes the NIC NSG and then the subnet NSG, and every NSG on the path must allow the flow.

@ AZ-104 D4 T4.2 applied troubleshooting
S: The NSG on a database subnet has one custom inbound rule: priority 100, Deny, TCP 1433, source `Internet`. A penetration test shows that VMs in the web subnet of the same virtual network can still connect to the database VMs on TCP 1433. What explains this, and what fixes it?
A: The default `AllowVNetInBound` rule (65000) allows all VNet sources; add a TCP 1433 deny rule from the web subnet with a lower number
B: NSGs never filter traffic between subnets of the same virtual network; deploy Azure Firewall between the two subnets to block TCP 1433
C: The default `AllowAzureLoadBalancerInBound` rule admits all sources in the network; delete it from the NSG so only custom rules decide
D: New NSG rules take effect only after the target VMs restart; restart the database VMs so that the existing deny rule starts filtering
K: A
G: ## The default rules every NSG has
Azure adds three inbound default rules to each NSG:
- `AllowVNetInBound` (65000): source and destination `VirtualNetwork`, all ports, Allow
- `AllowAzureLoadBalancerInBound` (65001): source `AzureLoadBalancer`, Allow
- `DenyAllInbound` (65500): everything else, Deny
## What the VirtualNetwork tag covers
`VirtualNetwork` is a service tag, not one subnet. It includes the whole virtual network address space, peered virtual networks, connected on-premises ranges and a few platform addresses. So by default every subnet in the virtual network can reach every other subnet on any port.
The `Internet` tag means address space outside the virtual network, so a rule with source `Internet` never matches traffic from another subnet.
## Example fix
Priority 200, Deny, TCP 1433, source `10.0.1.0/24` (web subnet), destination the database subnet. If the app tier still needs SQL, give it an allow rule with an even lower number, such as 150.
W: AllowVNetInBound plus a new deny: the web subnet's traffic does not match the `Internet` rule, so it falls through to `AllowVNetInBound` and is allowed. A custom deny rule for TCP 1433 from the web subnet, numbered below 65000, matches first and blocks it.
X: B=NSGs ignore intra-VNet traffic: NSGs do filter traffic between subnets and even inside one subnet; the default allow rule is simply permitting it here. A firewall is not needed for this.
C=AllowAzureLoadBalancerInBound: that rule only matches the `AzureLoadBalancer` tag (the health probe source), not VMs in other subnets. Default rules also cannot be deleted, only overridden.
D=Restart the VMs: NSG changes apply to new connections without restarting anything. The existing rule is working as written; it just does not match traffic from inside the virtual network.
T: The default `AllowVNetInBound` rule lets every subnet reach every other subnet, so blocking east-west traffic needs an explicit deny rule numbered below 65000.

@ AZ-104 D4 T4.2 applied use-case
S: VMs in a West US subnet must reach Azure Storage in West US over its public endpoints, and all other outbound internet access from the subnet must be blocked. The administrator does not want to maintain any IP address lists. Which outbound NSG rules meet the requirement?
A: Allow outbound to the `Storage.WestUS` service tag at priority 100, and deny outbound to the `Internet` service tag at priority 200
B: Deny outbound to the `Internet` service tag at priority 100, and allow outbound to the `Storage.WestUS` service tag at priority 200
C: Allow outbound to the `AzureCloud` service tag at priority 100, and deny outbound to the `Internet` service tag at priority 200
D: Allow outbound to the `VirtualNetwork` service tag at priority 100, and deny outbound to the `Internet` service tag at priority 200
K: A
G: ## Service tags
A service tag is a named group of IP prefixes for an Azure service, maintained by Microsoft. You use the name (for example `Storage`, `Sql`, `AzureCloud`, `Internet`) as the source or destination of an NSG rule, and Azure keeps the address list current.
Some tags can be scoped to a region: `Storage` covers Azure Storage in the whole cloud, while `Storage.WestUS` covers only the storage ranges in West US.
## Watch the Internet tag
`Internet` means all address space outside the virtual network that is reachable on the public internet, and it **includes Azure-owned public IP space**. Storage public endpoints therefore match both `Storage.WestUS` and `Internet`.
## Putting it together
Because the first matching rule wins, the narrow allow rule must have a lower number than the broad deny rule:
- 100 Allow, destination `Storage.WestUS`
- 200 Deny, destination `Internet`
The default `AllowInternetOutBound` rule (65001) is never reached for internet traffic because priority 200 matches first.
W: Storage.WestUS before Internet deny: traffic to West US storage matches the allow rule at 100 and leaves; everything else bound for public addresses matches the deny at 200. The tag is maintained by Microsoft, so no IP lists are needed.
X: B=Deny first: storage endpoints are part of the `Internet` tag, so storage traffic matches the deny at 100 and processing stops. The allow rule at 200 is never evaluated.
C=AzureCloud: `AzureCloud` covers the public IP space of all Azure services in all regions, so VMs could reach far more than West US storage, which breaks the requirement.
D=VirtualNetwork: this tag covers the virtual network, peered and connected networks, not Azure Storage public endpoints. Storage traffic would match the `Internet` deny and fail.
T: Use a regional service tag such as `Storage.WestUS` in an allow rule numbered below a deny rule for `Internet`, because the `Internet` tag includes Azure public endpoints.

@ AZ-104 D4 T4.2 applied use-case
S: A three-tier app runs web, app and database VMs in one subnet, and the web and app tiers scale in and out often. The administrator must allow TCP 1433 to the database VMs only from app-tier VMs, without editing NSG rules whenever IP addresses change. What should the administrator configure?
A: Create an application security group per tier, add each VM's network interface to its tier's group, and use the groups as rule source and destination
B: Create a custom service tag per tier, register each VM's private IP address in that tag, and use the tier tags as the NSG rule source and destination
C: Move each tier into its own virtual network and use the `VirtualNetwork` service tag in NSG rules to tell traffic from the different tiers apart
D: Create a route table per tier with user-defined routes that drop TCP 1433 traffic from every source other than the app-tier VMs' addresses
K: A
G: ## What an application security group is
An **application security group (ASG)** is a label you attach to network interfaces. NSG rules can then use the ASG as source or destination instead of IP addresses. When a VM joins or leaves a tier, you only change its NIC's ASG membership; the rules stay the same.
A rule that names an ASG applies only to NICs that are members of it, even when the NSG is associated with the whole subnet. A NIC can belong to several ASGs.
## Microsoft's three-tier example
- `AsgWeb`, `AsgLogic`, `AsgDb`: one ASG per tier
- 100 Allow TCP 80 from `Internet` to `AsgWeb`
- 110 Allow TCP 1433 from `AsgLogic` to `AsgDb`
- 120 Deny 1433 from Any to `AsgDb`
The deny rule is needed because `AllowVNetInBound` would otherwise let every VM in the virtual network reach the database.
## Constraint
All NICs in one ASG must be in the same virtual network, and a rule that uses ASGs as both source and destination needs both groups in the same virtual network.
W: Application security groups: the rules reference tiers, not addresses, so scaling only changes group membership on each NIC. App-tier NICs in the logic group can reach the database group on 1433 while a lower-priority deny blocks everyone else.
X: B=Custom service tags: a service tag represents the IP prefixes of a given Azure service, and Microsoft manages and updates those prefixes. Tags are picked from Microsoft's published list, not filled with your own VM addresses; grouping your own VMs is exactly what ASGs are for.
C=Separate virtual networks: the `VirtualNetwork` tag includes peered virtual networks, so it cannot tell tiers apart, and redesigning the network does not remove the IP-based rules the requirement wants to avoid.
D=Route tables: user-defined routes choose a next hop for destination prefixes; they do not allow or deny traffic by source and port. Filtering by port and source is an NSG job.
T: Application security groups let NSG rules target groups of NICs by role, so scaling a tier changes membership instead of rules.

@ AZ-104 D4 T4.2 applied troubleshooting
S: The `AsgApp` application security group contains network interfaces of VMs in VNet-A. An administrator tries to add the network interface of a new VM in VNet-B, which is peered with VNet-A, to `AsgApp`, and the operation fails. What is the cause?
A: All network interfaces in an application security group must be in the same virtual network as the first network interface that was assigned to it
B: An application security group can contain network interfaces from one subnet only, so the new VM must first move into the subnet of the current members
C: A network interface can be a member of only one application security group, and the new NIC already belongs to the default group created with the VM
D: Application security group membership is set on the NSG and not on the NIC, so the VM's private IP must be added to the NSG rule's address list instead
K: A
G: ## Where ASG membership lives
An application security group is assigned on a **network interface** (its IP configuration). NSG rules then reference the ASG as source or destination. You never list the member IP addresses yourself.
## Membership rules from Learn
- The first NIC added to an ASG fixes its virtual network. Every later NIC must be in that **same virtual network**; NICs from another virtual network cannot join, even if the networks are peered.
- When one rule uses ASGs as both source and destination, the NICs in both groups must be in the same virtual network.
- One NIC can be a member of **several** ASGs (within Azure limits).
- Members can sit in different subnets of that virtual network.
## Example
`AsgApp` got its first member in VNet-A. A VM in VNet-B needs its own ASG (for example `AsgApp-B`) used in rules of the NSG that protects VNet-B, or the VM must be deployed into VNet-A.
W: Same virtual network: an ASG is bound to the virtual network of its first member, so a NIC in VNet-B cannot join `AsgApp` even though the networks are peered. Create a separate ASG for VNet-B or place the VM in VNet-A.
X: B=One subnet only: ASG members can be in any subnet of the same virtual network. The limit is the virtual network, not the subnet.
C=One ASG per NIC: a network interface can belong to multiple application security groups, and Azure does not create a default ASG for new VMs.
D=Membership on the NSG: membership is configured on the network interface, and the whole point of an ASG is to avoid putting member IP addresses into rules.
T: An application security group is limited to one virtual network: every member NIC must be in the same virtual network as the first one, peering does not change that.

@ AZ-104 D4 T4.2 applied troubleshooting
S: To check which NSG rules apply to a VM, an administrator runs `az network nic list-effective-nsg --name vm-nic --resource-group test-rg`. An NSG is associated with the VM's subnet, but the command returns no rules. The VM is currently stopped (deallocated) for maintenance. What should the administrator do?
A: Start the VM and run the command again, because the effective security rules are returned only while the VM is in the running state
B: Associate an NSG directly with the network interface, because effective security rules are shown only for NSGs associated with the NIC
C: Enable virtual network flow logs on the virtual network first, because effective security rules are calculated from logged traffic records
D: Run the command against the subnet's NSG resource instead, because effective security rules are a property of each NSG and not of the NIC
K: A
G: ## What effective security rules show
The **effective security rules** of a network interface are the combined rules from the NSG on the NIC and the NSG on the NIC's subnet, including the default rules. You can view them:
- in the portal: VM > Networking > Network settings > select the NIC > Help > **Effective security rules** (a CSV download shows more than the first 50)
- with `az network nic list-effective-nsg` or `Get-AzEffectiveNetworkSecurityGroup`
## Conditions
Output is returned only when an NSG is associated with the NIC, its subnet, or both, and **the VM must be running**. A VM with several NICs can have different effective rules on each, so check each NIC.
## Reading the output
- `Association` shows whether a rule set comes from the subnet or the NIC.
- Names starting with `defaultSecurityRules/` are defaults, `securityRules/` are your own.
- For service tags, `expandedDestinationAddressPrefix` lists the real prefixes behind the tag.
W: Start the VM: effective security rules are calculated for a NIC attached to a running VM. With the VM deallocated nothing is returned, even though the subnet's NSG exists; after starting it the command shows the subnet NSG's rules.
X: B=NIC-level NSG required: effective rules include an NSG associated with the subnet as well as one on the NIC. A subnet NSG alone is enough for output, so adding a NIC NSG changes the rules instead of fixing the query.
C=Flow logs first: effective security rules come from the NSG configuration, not from traffic logs. Flow logs record IP traffic flows for later analysis; they are not a prerequisite for viewing rules.
D=Query the NSG: an NSG on its own lists only its own rules. The effective view is per network interface because it combines the subnet and NIC NSGs that apply to that NIC.
T: Effective security rules combine the subnet and NIC NSGs of one network interface and are only available while the VM is running.

@ AZ-104 D4 T4.2 applied troubleshooting
S: An administrator deploys Azure Bastion (Standard SKU) into VNet1 and has created a subnet named `BastionSubnet` with the prefix `10.0.255.0/27` for it. Validation fails. Which TWO changes must the administrator make before deploying again? (Select TWO)
A: Use a dedicated subnet named exactly `AzureBastionSubnet`, because Bastion deploys only into a subnet with that name
B: Make the dedicated subnet `/26` or larger, such as `10.0.255.0/26`, because `/27` is too small for new deployments
C: Assign a Standard public IP address to each target VM so that Bastion can forward the RDP and SSH sessions to them
D: Associate an NSG with the Bastion subnet that allows inbound TCP 3389 and 22 from the `Internet` service tag
E: Create a Basic SKU public IP address with dynamic allocation for the bastion host instead of a Standard static one
K: A,B
G: ## What Azure Bastion is
Azure Bastion is a managed PaaS service in your virtual network. Users open RDP or SSH sessions over TLS on port 443 (from the portal or, on higher SKUs, a native client), and Bastion connects to the VMs over their **private IP addresses**. The VMs need no public IP address, agent or special client software.
## Requirements for dedicated SKUs (Basic, Standard, Premium)
- A dedicated subnet named exactly `AzureBastionSubnet` in the same virtual network (and resource group) as the bastion host
- Subnet size `/26` or larger for deployments since November 2, 2021 (older `/27` deployments keep working)
- No other resources in that subnet
- A **Standard**, **Static** public IP address for the bastion host (not needed for the Developer SKU or a Premium private-only deployment)
## NSG on AzureBastionSubnet (optional)
If you add one, it must contain all the required rules, such as inbound 443 from `Internet` and from `GatewayManager`; ports 3389 and 22 are not needed inbound on this subnet.
W: A=AzureBastionSubnet name: Bastion finds its subnet by this exact name, so a subnet called `BastionSubnet` is not accepted.
B=/26 or larger: new deployments require at least `/26` (64 addresses) so that host instances can be added; a `/27` fails validation.
X: C=Public IPs on VMs: Bastion reaches VMs on their private IP addresses; removing the need for public IPs on VMs is one of its main benefits.
D=Allow 3389 and 22 from Internet: users reach Bastion on TCP 443, not on 3389 or 22. Learn states these ports are not required inbound on the Bastion subnet, and an NSG there must carry the full set of required rules.
E=Basic dynamic public IP: Bastion requires a Standard SKU public IP with static allocation, and Basic SKU public IPs are retired.
T: Dedicated Azure Bastion needs a subnet named exactly AzureBastionSubnet, sized /26 or larger, plus a Standard static public IP (except private-only Premium).

@ AZ-104 D4 T4.2 advanced use-case
S: A bank must record every administrator RDP and SSH session to its Azure VMs for auditors. Its administrators connect only over ExpressRoute, and the security team requires that the bastion host itself has no public IP address. Which Azure Bastion configuration meets these requirements?
A: The Premium SKU deployed as private-only, with session recording enabled and stored in a storage account blob container
B: The Standard SKU with shareable links and IP-based connections enabled, and an NSG limiting 443 to the bank's ranges
C: The Basic SKU with an NSG on AzureBastionSubnet that allows inbound 443 only from the bank's on-premises ranges
D: The Developer SKU, because it runs on shared infrastructure and needs no public IP address or AzureBastionSubnet

G: ## Bastion SKUs at a glance
- **Developer**: free, shared infrastructure, one VM at a time, no peering, for dev/test only.
- **Basic**: dedicated host with two fixed instances, browser connections.
- **Standard**: adds host scaling, native client, shareable links, IP-based connection, custom ports, file transfer.

## Session recording
When enabled, Bastion records the graphical RDP/SSH sessions it brokers and stores them in a blob container in your storage account (reached through a SAS URL or a managed identity). ## Private-only deployment
A normal Bastion deployment has a Standard static public IP that users connect to. A private-only deployment (Premium) has **no public IP**: users reach the bastion host only on its private IP, for example from on-premises over ExpressRoute or VPN.
W: Premium private-only with session recording: Premium is the only SKU that offers both features, so it satisfies the audit requirement and keeps the bastion host off the internet for administrators coming in over ExpressRoute.
X: B=Standard with shareable links: Standard has no session recording and always uses a public IP address. Shareable links widen access rather than restricting it.
C=Basic with an NSG: an NSG can limit who reaches the public IP, but the host still has one, and Basic cannot record sessions.
D=Developer SKU: it does avoid a dedicated subnet and public IP, but it is a shared dev/test offering with no session recording, one VM at a time and no production suitability.
T: Session recording and private-only (no public IP) deployment are Premium-only Bastion features.

@ AZ-104 D4 T4.2 applied troubleshooting
S: Azure Bastion works for VMs in Subnet-A, but sessions to VMs in Subnet-B fail. The NSG on Subnet-B has an inbound rule at priority 100 that denies TCP 3389 and 22 from any source. The NSG on AzureBastionSubnet contains all the documented rules. What should the administrator change?
A: Add an inbound allow rule to Subnet-B's NSG for TCP 3389 and 22 from the AzureBastionSubnet prefix, with a priority number below 100
B: Add an inbound allow rule to Subnet-B's NSG for TCP 443 from the `Internet` tag, because Bastion sessions reach target VMs over TLS
C: Add an inbound allow rule to Subnet-B's NSG for TCP 3389 and 22 from the `GatewayManager` tag, which Bastion uses to reach the VMs
D: Assign a Standard static public IP address to every VM in Subnet-B, because Bastion needs one for VMs in subnets that have an NSG
K: A
G: ## The two legs of a Bastion session
- **User to Bastion**: TLS on TCP 443 to the bastion host (from the internet or, for private-only, from private networks).
- **Bastion to VM**: RDP (3389) or SSH (22), or a custom port on Standard and Premium, from the bastion instances in `AzureBastionSubnet` to the VM's **private IP**.
## NSG rules on the target VM's subnet
The target subnet must allow inbound 3389/22 from Bastion. Learn recommends scoping the source to the `AzureBastionSubnet` address range, so only Bastion, not the internet, can use those ports. Without this rule Bastion cannot reach the VMs even when the bastion host itself is configured correctly.
## Example
Bastion subnet `10.0.254.0/26`, rule on Subnet-B's NSG:
`90 Allow TCP 3389,22 from 10.0.254.0/26 to Any`
Because 90 is lower than 100, it matches Bastion traffic before the existing deny rule.
W: Allow 3389/22 from AzureBastionSubnet before the deny: the Bastion-to-VM leg uses RDP/SSH on the VMs' private IPs, and the deny rule at 100 matches it first. An allow rule numbered below 100, scoped to the Bastion subnet's prefix, lets only Bastion through.
X: B=443 from Internet: 443 is the user-to-Bastion leg, which ends at the bastion host. Bastion then connects to the VM on 3389 or 22, which are still denied, and opening 443 to the internet adds exposure.
C=GatewayManager tag: `GatewayManager` is the Azure control plane that manages the bastion host; it is allowed on 443 into AzureBastionSubnet. Session traffic to VMs comes from the bastion instances in AzureBastionSubnet.
D=Public IPs on VMs: Bastion always connects to private IP addresses, and VMs do not need public IPs whether or not their subnet has an NSG.
T: Target VM subnets must allow RDP/SSH inbound from the AzureBastionSubnet range, numbered ahead of any deny rule.

S: VM `vm-report` has public IP `20.10.5.4` and queries an Azure SQL Database logical server whose firewall has one IP rule for `20.10.5.4`. After the administrator enables the `Microsoft.Sql` service endpoint on the VM's subnet, logins fail with error 40914, "Client is not allowed to access the server." What should the administrator do?
A: Add a virtual network rule for the VM's subnet on the SQL server's firewall, because the server now sees the VM's private address and subnet
B: Create a `privatelink.database.windows.net` private DNS zone and link it, because the service endpoint now resolves the server to a private IP
C: Add an inbound NSG rule from the `Sql` service tag on the VM's subnet, because service endpoint return traffic needs its own inbound rule
D: Set the server's public network access back to enabled, because enabling the service endpoint switched it off on the logical server
K: A
G: ## What a service endpoint changes
A **virtual network service endpoint** is a setting on a **subnet** (for example `Microsoft.Sql`, `Microsoft.Storage`, `Microsoft.KeyVault`). Once enabled:
- Traffic from that subnet to the service stays on the Azure backbone (the subnet's effective routes show next hop `VirtualNetworkServiceEndpoint`).
- The **source IP** the service sees switches from the VM's public IPv4 address to its **private IPv4 address**, and the request carries the subnet's identity.
- DNS does not change: the server name still resolves to the service's public IP.
- Existing TCP connections to the service are closed during the switch, so enable endpoints in a quiet window.
## Effect on firewalls
Learn warns that existing firewall rules that use public IP addresses stop working after the switch. On Azure SQL Database the two firewall errors tell you which rule type is missing:
- **40615**: the client's IP address has no IP rule.
- **40914**: the client is in a subnet with a service endpoint, but the server has no **virtual network rule** for that subnet.
## Example fix
On the logical server's networking (firewall) page, add a virtual network rule for the VM's subnet; with PowerShell, `New-AzSqlServerVirtualNetworkRule` does the same. The IP rule for `20.10.5.4` can then be removed.
W: Virtual network rule for the subnet: with the endpoint on, the request arrives from the VM's private address with the subnet's identity, so the IP rule for `20.10.5.4` no longer matches. Error 40914 is the documented signal that the server needs a virtual network rule for that subnet.
X: B=Private DNS zone: service endpoints never change DNS; the server name still resolves to its public IP. A `privatelink` zone only helps when a private endpoint exists to point it at.
C=Inbound Sql rule: NSGs are stateful, so replies to the VM's outbound connection need no inbound rule, and the default outbound rules already allow the traffic. The rejection comes from the SQL firewall, not from an NSG.
D=Public network access: enabling a service endpoint on a subnet changes nothing on the logical server, and service endpoint traffic still goes to the public endpoint. The firewall is rejecting the request because no rule matches the subnet.
T: A service endpoint makes the service see the VM's private address and subnet, so IP firewall rules stop matching and the subnet must be allowed with a virtual network rule.
V: Virtual network service endpoints, Azure SQL Database

@ AZ-104 D4 T4.2 advanced use-case
S: VMs in a finance subnet use a `Microsoft.Storage` service endpoint. To prevent data exfiltration, the security team requires that these VMs can reach only the two finance storage accounts and no other storage account, including accounts in other subscriptions. What should the administrator configure?
A: A service endpoint policy that lists the resource IDs of the two finance storage accounts, associated with the finance subnet
B: An outbound NSG rule that allows only the regional `Storage` service tag and denies the `Internet` tag for the finance subnet
C: Virtual network rules on the two finance storage accounts that allow only the finance subnet and deny all other networks
D: The `Microsoft.Storage.Global` service endpoint on the finance subnet, which limits access to accounts in its own subscription
K: A
G: ## The exfiltration gap
NSG service tags such as `Storage.WestUS` cover every storage account in a region, including accounts owned by someone else. A VM that may reach "Azure Storage" could therefore copy data to an attacker's account. Storage firewalls protect your accounts from other networks but do not control where your VMs send data.
## Service endpoint policies
A **service endpoint policy** is attached to a subnet that has the Azure Storage service endpoint enabled. It is an **allow list** of resource IDs:
- a whole subscription: `/subscriptions/<id>`
- a resource group
- a single storage account: `/subscriptions/<id>/resourceGroups/<rg>/providers/Microsoft.Storage/storageAccounts/<name>`
Once a policy is on the subnet, only the listed accounts are reachable over the endpoint; every other storage account is denied. Applying a policy also makes the storage service endpoint scope global.
## Things to watch
List every dependency your apps need, because anything not listed is blocked. Policies do not apply to traffic from on-premises and are not supported for most managed services deployed into the subnet.
W: Service endpoint policy: it filters the subnet's outbound storage traffic by account, so the finance VMs can reach the two listed accounts and are denied every other storage account, wherever it lives.
X: B=Storage service tag: the tag represents the whole Azure Storage service in that region, not specific accounts, so VMs could still write to any other account there.
C=Virtual network rules on the finance accounts: these control who can reach the finance accounts. They do nothing to stop the finance VMs from sending data to other storage accounts.
D=Microsoft.Storage.Global: the cross-region storage service endpoint extends the endpoint to storage in other regions; it does not restrict access to accounts in one subscription.
T: To restrict a subnet to specific storage accounts, attach a service endpoint policy that lists their resource IDs; service tags only work at the service and region level.
V: Virtual network service endpoints, Service endpoint policies, Azure Storage

@ AZ-104 D4 T4.2 applied troubleshooting
S: A storage account with hierarchical namespace (Data Lake Storage) has public network access disabled and one private endpoint in VNet1 with target subresource `blob`, integrated with private DNS. Analytics VMs in VNet1 can upload and download blobs, but creating directories and managing ACLs fail. What should the administrator do?
A: Create a second private endpoint for the account with target subresource `dfs`, integrated with a `privatelink.dfs.core.windows.net` zone
B: Enable the `Microsoft.Storage` service endpoint on the VMs' subnet so that Data Lake directory and ACL calls reach the account's dfs endpoint
C: Edit the existing private endpoint and add `dfs` as a second target subresource so that one network interface serves blob and dfs traffic
D: Add an A record for the account's dfs host name to the `privatelink.blob.core.windows.net` zone, pointing at the blob endpoint's private IP
K: A
G: ## One private endpoint per storage service
A private endpoint is a network interface with a private IP from your subnet, mapped to one resource and one **target subresource**. A storage account exposes several services, each with its own endpoint and private DNS zone:
- `blob`: `privatelink.blob.core.windows.net`
- `dfs` (Data Lake Storage): `privatelink.dfs.core.windows.net`
- `file`: `privatelink.file.core.windows.net`
- `queue`, `table`, `web`: their own zones
Learn says you need a **separate private endpoint for each storage service** you want to reach privately.
## Data Lake Storage needs both
With hierarchical namespace, Data Lake operations such as Create Directory, Delete Directory and Manage ACL go to the `dfs` endpoint and fail without a dfs private endpoint. Some dfs operations are redirected to the blob endpoint, so Learn recommends creating private endpoints for **both** `blob` and `dfs`.
## Connection strings and DNS
Clients keep the normal names (`<account>.blob.core.windows.net`, `<account>.dfs.core.windows.net`). Public DNS returns a CNAME into the matching `privatelink` zone, and the zone linked to the virtual network returns the private IP of that service's endpoint.
W: Second private endpoint for dfs: directory and ACL APIs use the dfs endpoint, which has no private endpoint yet and whose public path is closed. A `dfs` private endpoint with its own private DNS zone gives those calls a private IP while blob calls keep using the existing endpoint.
X: B=Service endpoint: service endpoint traffic still goes to the account's public endpoint, which is disabled, so the dfs calls would still be refused. Service endpoints also do not change DNS.
C=Add dfs to the existing endpoint: each private endpoint maps to one target subresource, and Learn requires a separate private endpoint for each storage service. There is no option to attach a second subresource to the same endpoint.
D=dfs record in the blob zone: the dfs host name resolves through the `privatelink.dfs.core.windows.net` zone, not the blob zone, and the blob endpoint's IP only serves the blob service. The Data Lake APIs need a dfs private endpoint.
T: Each storage service needs its own private endpoint and privatelink zone; Data Lake Storage accounts need both a blob and a dfs private endpoint.
V: Azure Private Link, Azure Storage, Azure Data Lake Storage

@ AZ-104 D4 T4.2 advanced comparison
S: Servers in an on-premises data center reach VNet1 over a site-to-site VPN. They must read blobs from a storage account over a private connection, and the account must stop accepting traffic from the public internet. Which TWO actions should the administrator take? (Select TWO)
A: Create a private endpoint for the blob subresource in VNet1, and make on-premises DNS resolve the account name to its private IP
B: Set the storage account's public network access to Disabled, so that it accepts traffic only through private endpoint connections
C: Enable the `Microsoft.Storage` service endpoint on the GatewaySubnet so the VPN traffic carries VNet1's identity to the account
D: Add the data center's public NAT IP address to the storage firewall, so the VPN traffic is allowed through the public endpoint
E: Associate a service endpoint policy with the GatewaySubnet that lists the account, so only this account is reachable from on-premises
K: A,B
G: ## Service endpoints vs private endpoints
- **Service endpoint**: a subnet setting. Traffic still goes to the service's public endpoint, over the Azure backbone and with the subnet's identity. DNS is unchanged (public IP). It works only for traffic that starts in that Azure subnet, never from on-premises.
- **Private endpoint**: a network interface with a private IP from your subnet, mapped to one resource and one subresource (such as `blob`). DNS resolves the name to the private IP through a `privatelink` zone. It is reachable from the same virtual network, peered virtual networks and on-premises networks over VPN or ExpressRoute.
Microsoft recommends private endpoints for secure, private access to Azure services.
## Locking down the public endpoint
On a storage account, setting **Public network access** to **Disabled** blocks all public traffic; access is then possible only through private endpoints. Traffic through an approved private endpoint is always allowed, even with public access disabled.
## DNS for on-premises clients
On-premises DNS needs a conditional forwarder for `blob.core.windows.net` (the public zone, not the privatelink one) to a DNS forwarder or Azure DNS Private Resolver in a virtual network linked to the private DNS zone.
W: A=Private endpoint with DNS: the endpoint gives the account a private IP in VNet1 that the data center reaches over the VPN, and DNS forwarding makes the normal account name resolve to that IP.
B=Public network access Disabled: this closes the public endpoint completely, while traffic arriving through the approved private endpoint is still accepted.
X: C=Service endpoint on GatewaySubnet: service endpoints cannot be used for traffic from on-premises; Learn says on-premises access to a service secured by endpoints must go through public NAT IPs instead.
D=Allow the NAT IP: this keeps using the public endpoint over the internet, which contradicts both requirements.
E=Service endpoint policy: policies filter outbound storage traffic from subnets with service endpoints and do not apply to on-premises traffic. They also cannot make the public endpoint private.
T: For private access from on-premises, use a private endpoint (with DNS forwarding) and disable public network access; service endpoints only serve traffic from Azure subnets.
V: Azure Private Link, Virtual network service endpoints, Azure Storage

@ AZ-104 D4 T4.2 advanced troubleshooting
S: A private endpoint for an Azure SQL logical server sits in the `pe-subnet`. To block a test subnet, the administrator adds a deny rule for TCP 1433 from the test subnet's prefix to the endpoint's private IP in the NSG on `pe-subnet`. Test VMs can still connect. What is the most likely cause?
A: Network policies for private endpoints are disabled on `pe-subnet`, so NSG rules are not applied to traffic sent to its private endpoints
B: The NSG must be associated with the private endpoint's network interface, because a private endpoint only honors NIC-level NSGs
C: The rule must use the `Sql` service tag as its destination, because NSG rules for private endpoints cannot match their private IP
D: The private endpoint connection is still Pending on the SQL server, and NSG rules apply only to connections in the Approved state
K: A
G: ## Network policies on a private endpoint subnet
By default, Learn states, network policies are **disabled** for private endpoints in a subnet. While they are disabled, NSG rules and user-defined routes are not applied to traffic destined for the private endpoints in that subnet (other resources in the subnet are still filtered normally).
You turn them on per subnet, for NSGs only, route tables only, or both:
- Portal: virtual network > Subnets > subnet > **Network policy for private endpoints** > Network security groups
- ARM/Bicep property `privateEndpointNetworkPolicies`: `Disabled`, `NetworkSecurityGroupEnabled`, `RouteTableEnabled` or `Enabled`
- CLI: `az network vnet subnet update --disable-private-endpoint-network-policies false ...`
The setting affects every private endpoint in the subnet.
## Other private endpoint facts
- The endpoint's network interface is created automatically and is read-only; its private IP stays the same for the endpoint's lifetime.
- Only connections in the **Approved** state can carry traffic.
- Effective security rules are not displayed for a private endpoint NIC in the portal.
W: Enable network policies: with private endpoint network policies disabled on `pe-subnet`, the NSG ignores traffic to the endpoint, so the deny rule never fires. Enabling the NSG network policy on the subnet makes the rule apply.
X: B=NIC-level NSG: the private endpoint's network interface is managed by Azure and read-only; NSG filtering for private endpoints is turned on through the subnet's network policy setting.
C=Sql service tag: the `Sql` tag represents the public Azure SQL service ranges, not your private endpoint. Rules for a private endpoint target its private IP once network policies are enabled.
D=Pending connection: a Pending connection cannot carry traffic at all, so the test VMs would not be able to connect. The successful connections show the endpoint is Approved.
T: NSG rules reach private endpoints only after network policies for private endpoints are enabled on their subnet.
V: Azure Private Link, Network security groups, Azure SQL Database
