# AZ-104 D3 T3.3 Provision and manage containers in the Azure portal: Azure Container Registry, Azure Container Instances, Azure Container Apps, sizing and scaling

@ AZ-104 D3 T3.3 applied comparison
S: A company runs a Standard tier Azure container registry in West Europe. It is opening a plant in Southeast Asia whose hosts should pull images from a local copy under the same login server, and security wants the registry reachable only through a private endpoint. What should the administrator do?
A: Change the registry's pricing plan to Premium under Properties, then add a Southeast Asia geo-replication and a private endpoint
B: Keep the Standard plan, add a Southeast Asia geo-replication, and replace the private endpoint with firewall IP access rules
C: Create a second Standard registry in Southeast Asia, import the images into it, and point a CNAME at the West Europe login server
D: Delete the Standard registry and recreate it as Premium with the same name, because a registry's tier is fixed at creation time
K: A
G: ## Azure Container Registry service tiers
Azure Container Registry (ACR) has three SKUs, also called pricing plans or service tiers: **Basic**, **Standard** and **Premium**. All three have the same data plane APIs, Microsoft Entra authentication and zone redundancy in supported regions, but they differ in included storage, throughput and features.
- **Basic**: cost-optimized entry point for learning and low usage.
- **Standard**: more storage and throughput; fits many production workloads.
- **Premium**: the most storage and concurrency, plus features only this tier has, including **geo-replication**, **private link with private endpoints**, public IP network rules (IP access rules), customer-managed keys and connected registries.
## Changing the tier
The tier is not fixed. You change it in the portal (registry > **Settings > Properties > Pricing plan**), with `az acr update --sku Premium`, or with `Update-AzContainerRegistry`. Learn states there is **no downtime or impact on registry operations** when you change the SKU. Going down from Premium requires removing Premium-only resources first, such as geo-replications.
## Geo-replication in one sentence
A geo-replicated registry is still **one** registry: one login server (`contoso.azurecr.io`), one set of credentials and role assignments, with content synced to every replica region.
## Example
`az acr update --name contosoacr --sku Premium` followed by `az acr replication create --registry contosoacr --location southeastasia` gives the plant a local replica, and a private endpoint then keeps traffic off the public internet.
W: Upgrade to Premium, then configure: geo-replication and private endpoints are both Premium-only features, and the tier can be raised in place with no downtime, so the existing registry, its login server and its images stay exactly as they are.
X: B=Standard with geo-replication: geo-replication requires Premium, and so do public IP network rules. A Standard registry can offer neither, so this plan fails on both requirements.
C=Second registry plus CNAME: a second registry is a separate resource with its own login server, credentials and role assignments. Import copies images once, and a CNAME does not merge two registries into one endpoint, so the plant would not get a synced copy under the same name.
D=Delete and recreate: the tier can be changed at any time without downtime. Deleting the registry would destroy its images, role assignments and webhooks for no reason.
T: Geo-replication and private endpoints need the Premium tier, and an existing registry can be moved to Premium in place without downtime.
V: Azure Container Registry

@ AZ-104 D3 T3.3 advanced troubleshooting
S: Policy requires the admin user on a company's Azure container registry to stay disabled. An administrator deploys a Linux container group to Azure Container Instances with a Bicep file that enables its system-assigned managed identity, which has the AcrPull role on the registry. The image pull still fails. What should she do?
A: Attach a user-assigned managed identity with AcrPull on the registry to the group, and name it in the group's imageRegistryCredentials
B: Give the system-assigned identity the AcrPush role instead, because Container Instances must write cached image layers back to the registry
C: Give the system-assigned identity a registry control plane role such as Container Registry Contributor, so that it can log in first
D: Wait for the AcrPull role assignment to replicate and redeploy, because system-assigned identity pulls work once the assignment is visible
K: A
G: ## Ways to authenticate an image pull from ACR
- **Admin user**: one shared account per registry with full push and pull rights. It is disabled by default and Learn recommends enabling it only when needed (for example some portal deployment flows); it does not support Azure RBAC.
- **Service principal**: a Microsoft Entra identity for headless pulls, governed by Azure RBAC.
- **Managed identity**: an Entra identity that Azure manages for a resource, so no password is stored anywhere. You grant it a pull role such as **AcrPull** on the registry.
## The Container Instances rule
Azure Container Instances (ACI) **does not support system-assigned managed identity for ACR image pulls**. Learn is explicit: you must use a **user-assigned** managed identity, regardless of the container group's operating system.
The pieces that must line up:
- `identity` on the container group lists the user-assigned identity.
- `imageRegistryCredentials` has `server: 'contosoacr.azurecr.io'` and `identity: '<resource ID of the user-assigned identity>'`.
- The identity has **AcrPull** on the registry (`az role assignment create --assignee <principalId> --scope <registry-id> --role acrpull`).
With the CLI the same thing is `az container create ... --acr-identity $USERID --assign-identity $USERID`.
W: User-assigned identity with AcrPull: ACI authenticates registry pulls only with a user-assigned managed identity. Granting that identity AcrPull and naming it in imageRegistryCredentials gives a password-free pull that keeps the admin user disabled.
X: B=AcrPush: ACI only needs to read images. AcrPush adds write rights the workload should not have, and the real problem, a system-assigned identity that ACI cannot use for pulls, would remain.
C=Control plane role: the Container Registry Contributor and Data Access Configuration Administrator role covers registry settings and `az acr login`, but it grants no data plane pull permission, and the identity type is still unsupported for ACI pulls.
D=Wait for replication: role assignments can take a short time to apply, but no amount of waiting helps here. ACI does not use system-assigned identities to pull from ACR at all.
T: Container Instances pulls from ACR with a managed identity only when it is user-assigned and holds AcrPull; system-assigned identities are not supported for image pulls.
V: Azure Container Instances, Azure Container Registry, managed identities

@ AZ-104 D3 T3.3 applied troubleshooting
S: A container app on the Consumption plan runs one container with 1.0 vCPU and 2.0Gi of memory. An administrator adds a log-forwarding sidecar container with 0.5 vCPU and 0.5Gi, and the new revision is rejected because of an invalid CPU and memory allocation. Which change fixes the deployment?
A: Size the sidecar at 0.5 vCPU and 1.0Gi so that the app's containers total 1.5 vCPU and 3.0Gi, one of the allowed pairs
B: Size the sidecar at 0.25 vCPU and 0.25Gi so that the app's containers total 1.25 vCPU and 2.25Gi, a smaller pair
C: Keep both sizes and raise the maximum replica count so that the platform spreads the sidecar's load over more replicas
D: Keep both sizes and add a CPU scale rule so that KEDA resizes each replica vertically when the sidecar is under load
K: A
G: ## CPU and memory in Azure Container Apps
Each container in a container app declares `resources.cpu` and `resources.memory`. On the **Consumption plan**, the **total** of all containers in the app (main containers plus sidecars) must equal one of a fixed set of pairs, in which memory is always twice the vCPU count:
- `0.25` vCPU / `0.5Gi`, `0.5` / `1.0Gi`, `0.75` / `1.5Gi`, `1.0` / `2.0Gi`
- `1.25` / `2.5Gi`, `1.5` / `3.0Gi` ... up to `4.0` / `8.0Gi`
Apps in a legacy Consumption-only environment are limited to 2 cores and 4Gi.
## Scaling is horizontal only
Container Apps scales by adding or removing **replicas** (copies of the revision), driven by scale rules based on KEDA. Learn lists **vertical scaling isn't supported**: a scale rule never changes the CPU or memory of a replica.
## Example
Main container 1.0 / 2.0Gi plus sidecar 0.5 / 0.5Gi = 1.5 vCPU / 2.5Gi, which is not on the list. Changing the sidecar to 0.5 / 1.0Gi gives 1.5 / 3.0Gi, which is.
W: Sidecar at 0.5 vCPU and 1.0Gi: the Consumption plan validates the sum across all containers. 1.5 vCPU with 3.0Gi is an allowed pair, so the revision passes validation.
X: B=0.25 vCPU and 0.25Gi: the totals become 1.25 vCPU and 2.25Gi. The allowed pair for 1.25 vCPU is 2.5Gi, so this is still rejected.
C=Raise maximum replicas: replica limits control how many copies run, not the size of each copy. The revision is rejected before any replica starts, because the per-app allocation itself is invalid.
D=CPU scale rule: scale rules add or remove replicas; vertical scaling is not supported in Container Apps, and a rule cannot repair an invalid CPU and memory total.
T: On the Consumption plan, the combined CPU and memory of all containers in a container app must match an allowed pair (memory twice the vCPU), and scaling never resizes a replica.
V: Azure Container Apps

@ AZ-104 D3 T3.3 advanced troubleshooting
S: An ACR task builds an app image from a Dockerfile whose FROM line is contosoacr.azurecr.io/base/node:20. The task has run successfully many times. The platform team now publishes patched base images as base/node:20.1, base/node:20.2 and so on, and the app image is never rebuilt. What is the cause?
A: A base-image trigger fires only when the tag the Dockerfile references is updated, so patches pushed under new version tags never reach the task
B: Base-image triggers are disabled by default on new tasks, so the administrator must turn on the trigger with the task update command
C: ACR tasks track base images only in Docker Hub and Microsoft Container Registry, so a base image in the same registry is never watched
D: Base images in a registry are checked at a random 10-to-60-minute interval, so the rebuild is still waiting in the queue for its next check
K: A
G: ## What ACR Tasks automate
ACR Tasks builds container images in Azure. A task can be triggered by a source code commit, a timer, or an **update to the image's base image**, which is how teams automate OS and framework patching without editing every application.
## How the base-image trigger works
- When a task builds an image, ACR Tasks **discovers the base image dependency** from the `FROM` line. The task must have run at least once for the dependency to be tracked.
- The base-image trigger is **enabled by default** on tasks created with `az acr task create` (`--base-image-trigger-enabled` is True).
- Tracked locations include the same registry, another Azure container registry, and public repos in Docker Hub and Microsoft Container Registry.
- Timing: a base image in an Azure container registry triggers the task **immediately**; public repos are polled at a random 10-60 minute interval.
- **Stable tag required**: the base image must be updated under a stable tag such as `node:20`. Learn states that if the base image is updated with a **new version tag**, it does not trigger a task.
## Example
The platform team re-pushes the patched layer as `base/node:20` (optionally also tagging `20.2`). The task sees the tag it depends on change and rebuilds the app image.
W: New tags are not updates: the task watches the exact tag in the FROM line. Publishing `20.1` and `20.2` creates different images, while `base/node:20` never changes, so nothing triggers. Re-pushing the stable tag fixes it.
X: B=Disabled by default: the base-image trigger is enabled by default for tasks created with `az acr task create`, and this task's dependency has been tracked for many runs.
C=Public registries only: a base image in the same registry is one of the supported locations; another Azure registry, Docker Hub and Microsoft Container Registry are also tracked.
D=Random polling interval: the 10-60 minute check applies to public repos. A base image in an Azure container registry triggers the task at once, and here the referenced tag never changes at all.
T: ACR Tasks rebuilds on a base-image update only when the tag in the FROM line is updated, so patches must be published under that stable tag.

@ AZ-104 D3 T3.3 advanced definition
S: A company upgrades its Azure container registry to Premium and adds geo-replicas in East US and Japan East; the home region is West Europe. Which TWO statements about the geo-replicated registry are correct? (Select TWO)
A: Clients in every region keep using one login server name, and Azure routes each request to a replica with good network performance, usually the closest
B: If West Europe becomes unavailable, pushes and pulls continue through the other replicas, but registry configuration changes and ACR tasks wait
C: Each replica is a separate registry resource, so role assignments and network rules must be created again in East US and in Japan East
D: Replication is primary-secondary: only West Europe accepts pushes, and the other replicas serve read-only copies of the images
E: Replication is synchronous, so an image pushed in one region can always be pulled at once from every other replica without retries
K: A,B
G: ## What geo-replication gives you
Geo-replication (Premium tier) creates replicas of one registry in the regions you choose:
- **One registry to manage**: one set of credentials, role assignments, network rules and configuration across all replicas.
- **One global endpoint**: `contoso.azurecr.io/app:1.4` works everywhere. Azure routes each request to the replica with the best network performance for the client, usually the closest one.
- **Active-active**: every replica accepts push, pull and delete, not only the home region.
- **Eventual consistency**: changes replicate in the background. A push in one region followed immediately by a pull from another can fail with `manifest unknown` until replication catches up, so pipelines should retry or wait for replication webhooks.
## The home region
The home region (where the registry was created) hosts the control plane and cannot be changed. If it goes down:
- image push, pull and delete, and authentication keep working through the other replicas
- registry configuration changes (network rules, replication settings) wait for recovery
- **ACR Tasks** are bound to the home region and do not run
## Billing note
Storage is billed per replica: an image stored in three regions is charged three times.
W: A=One login server: all replicas share the registry's single endpoint, and Azure picks a well-performing replica (usually the nearest), so deployment manifests do not change per region.
B=Home region outage: the data plane keeps working through the remaining replicas, while control plane changes and ACR Tasks, which live in the home region, pause until it recovers.
X: C=Separate resources: replicas are part of the same registry and share credentials, role assignments and network rules; nothing is configured per region.
D=Primary-secondary: ACR geo-replication is active-active, so pushes, pulls and deletes work against any replica, not only the home region.
E=Synchronous replication: replication is eventually consistent. A push followed by an immediate pull from another region can fail until the content arrives, so pipelines need retries or webhooks.
T: A geo-replicated registry is one active-active, eventually consistent registry behind one login server; a home region outage stops only management changes and ACR Tasks.

@ AZ-104 D3 T3.3 applied troubleshooting
S: An administrator runs a nightly report as a container group in Azure Container Instances, created with default settings. The container writes the report and exits with code 0, but it keeps starting again and the group is billed all night. Failed runs must still be retried automatically. What should she do?
A: Delete the container group and create it again with the OnFailure restart policy, because an update can't change the restart policy
B: Redeploy the group under the same name with the OnFailure restart policy, which updates the policy in place and reuses cached layers
C: Keep the Always policy and add a liveness probe that fails once the report is written, so that the platform stops the container group
D: Delete the container group and create it again with the Never restart policy, which retries failed runs but never restarts finished ones
K: A
G: ## Restart policies in Azure Container Instances
A container group has one of three restart policies:
- **Always** (the default when none is given): containers are always restarted, which suits long-running services such as web servers.
- **OnFailure**: containers restart only when the process exits with a nonzero code. They run at least once, and a successful run (exit code 0) leaves the group **Terminated**.
- **Never**: containers are not restarted after a successful exit. Learn notes the platform *might* still restart a container after a nonzero exit, but Never makes no promise to retry.
ACI bills by the second for the resources while containers run, so a finished task that keeps restarting under **Always** keeps costing money.
## Updating a container group
You update a group by running create again with the same name and at least one changed property. Some properties can't be updated that way and require **deleting and recreating** the group: OS type, CPU/memory/GPU resources, **restart policy**, and availability zone.
## Example
`az container delete -g rg-reports -n nightly-report` then `az container create -g rg-reports -n nightly-report --image contosoacr.azurecr.io/report:3 --restart-policy OnFailure`.
W: Recreate with OnFailure: OnFailure stops the group after a clean exit and restarts it only after a failure, which is exactly the requirement, and the restart policy is one of the properties that requires delete and recreate.
X: B=Update in place: restart policy is on the list of properties that can't be changed by redeploying an existing group. The group has to be deleted and created again.
C=Failing liveness probe: a failed liveness probe tells the platform the container is unhealthy, and with Always it is restarted again. It also does nothing to guarantee retries of genuinely failed runs.
D=Never: Never only guarantees no restart after a successful exit. It does not guarantee a retry after a failure, so the second requirement is not met.
T: Use OnFailure for run-to-completion tasks that must retry on errors, and remember that changing the restart policy means deleting and recreating the container group.

@ AZ-104 D3 T3.3 applied use-case
S: A developer deploys a container group in Azure Container Instances from a YAML file that sets DB_PASSWORD as an environment variable. Anyone with read access sees the password in the portal and in the az container show output. How should the administrator change the deployment?
A: Define DB_PASSWORD with the secureValue property instead of value, so the group's properties show only the variable's name
B: Move DB_PASSWORD into an ENV line in the Dockerfile, so the value lives in the image and no longer appears in the group
C: Give readers the Reader role instead of Contributor, because the Reader role shows container properties without their values
D: Set DB_PASSWORD at runtime with az container exec after the group starts, so the deployment file never contains its value
K: A
G: ## Environment variables in ACI
Environment variables configure a container at start, like `docker run --env`. You set them in the portal (**Advanced** tab), with `--environment-variables` in the CLI, or under `environmentVariables` in YAML or ARM templates.
A normal variable uses `value`, and anyone who can read the container group sees it.
## Secure values
For passwords and keys, ACI supports **secure values** for Linux and Windows containers. Use `secureValue` instead of `value`:
```
environmentVariables:
- name: 'DB_PASSWORD'
  secureValue: 'P@ss-from-pipeline'
```
- The value is available **inside the container** as a normal environment variable.
- Container properties in the portal and Azure CLI show only the variable's **name**, not its value.
Another supported option is a **secret volume**, which mounts secrets as files.
W: secureValue: secure environment variables are hidden from the container group's properties in the portal and CLI, while the application still reads them from its environment as before.
X: B=Dockerfile ENV: baking the password into the image exposes it to everyone who can pull the image or inspect its layers, and changing it means rebuilding the image.
C=Reader role: Reader can read the container group's properties, including normal environment variable values. Changing roles does not hide a value stored in plain `value`.
D=az container exec: exec runs a command in a running container, such as a shell. Setting a variable there affects only that session; the application process started with the group never sees it.
T: In Azure Container Instances, put secrets in secureValue environment variables (or a secret volume) so that they never appear in the group's properties.

@ AZ-104 D3 T3.3 applied definition
S: An administrator wants a container group in Azure Container Instances to keep its output after restarts by mounting an Azure file share at /data. Which TWO statements about this mount are correct? (Select TWO)
A: Only Linux containers can mount an Azure file share, so the image and the group's OS type must be Linux
B: The mount uses the storage account name, share name and account key, because a managed identity can't mount it
C: The container must run as a non-root user, because the CIFS mount refuses connections from the root account
D: Files already in the image under /data are merged with the share, so the app sees both sets of files after it starts
E: The share must be an NFS share in a premium storage account, because Azure Container Instances can't mount SMB shares
K: A,B
G: ## Why mount a volume
ACI containers are stateless: when a container restarts, crashes or stops, its local state is lost. To keep data, mount a volume from an external store, most often an **Azure file share**.
## Limitations Learn lists for Azure Files mounts
- **Linux containers only**: Windows containers can't mount Azure Files shares.
- The container must **run as root**.
- Mounts are **SMB/CIFS** only.
- Azure Storage **doesn't support SMB mounting with managed identity**, so you provide the storage account name, the share name and the **storage account key**.
## What the mount does to existing files
Mounting works like a Docker bind mount: if the image already has files in the mount path, the share **hides** them while the container runs.
## Example
```
az container create -g rg-app -n report --image contosoacr.azurecr.io/report:2 \
  --azure-file-volume-account-name stcontosodata --azure-file-volume-account-key $KEY \
  --azure-file-volume-share-name output --azure-file-volume-mount-path /data
```
W: A=Linux only: Azure Files volume mounts are supported only for Linux containers in ACI, so a Windows container group can't use this design.
B=Account key authentication: Azure Storage doesn't support SMB mounting of a file share with managed identity, so the volume definition carries the account name, share name and account key.
X: C=Non-root user: Learn states the opposite. The Azure Files volume mount requires the Linux container to run as root.
D=Merged files: the mount behaves like a bind mount and obscures anything already in /data while the container runs; the image's files are not visible.
E=NFS premium share: ACI Azure Files mounts are limited to CIFS (SMB). A standard SMB share, like the Standard_LRS account in Learn's example, is the supported option.
T: ACI mounts Azure file shares over SMB only into Linux containers running as root, authenticated with the storage account key.

@ AZ-104 D3 T3.3 applied troubleshooting
S: A partner's application calls an API that runs in a container group in Azure Container Instances with a public IP address. The partner hard-coded that IP. After the container group was deleted and recreated, the calls fail. What should the administrator do so this doesn't happen after future redeployments?
A: Set a DNS name label on the container group and have the partner use its FQDN, of the form label.region.azurecontainer.io
B: Associate a static Standard public IP address resource directly with the container group's IP address configuration
C: Change the group's restart policy to Never, because a group that never restarts always keeps the IP address it got
D: Always redeploy with az container create under the same group name, which guarantees that the group keeps its IP address
K: A
G: ## Public addresses in ACI
A container group can get a public IP address with exposed ports. That address is **not stable**:
- it can change when the container group restarts
- an update usually keeps it, but Learn says this is **not guaranteed** (internal events can move the group to another host)
- deleting the group releases its IP address and FQDN; recreating it creates the group new, so the IP can change
## The recommended fix: DNS name label
Give the group a **DNS name label**, and it is reachable at `<label>.<region>.azurecontainer.io`, for example `contoso-api.westeurope.azurecontainer.io`. The label must be unique within the region. Clients use the name, so they follow the group to whatever IP it has; after a delete, recreate the group with the same label to get the same name back.
## When a static IP is mandatory
If a partner really needs a fixed IP (for example for a firewall allow list), Learn advises putting **Application Gateway** in front of the container group and giving the gateway the static public IP.
W: DNS name label: the FQDN stays the same across restarts and updates, and a recreated group gets it back by using the same label, so the partner's calls keep working even when the underlying IP changes, which is what Learn recommends instead of hard-coding IPs.
X: B=Static public IP resource: ACI doesn't offer a setting to bind your own static public IP resource to a container group; Learn's answer when a static IP is needed is Application Gateway in front of the group.
C=Restart policy Never: the restart policy controls when containers restart; it doesn't reserve an address, and deletion and recreation, which happened here, can still change the IP.
D=Update under the same name: an update usually keeps the IP, but Learn says this isn't guaranteed, and some changes force delete and recreate anyway.
T: Don't hard-code an ACI public IP: use the DNS name label's FQDN, or put Application Gateway in front when a static IP is required.

@ AZ-104 D3 T3.3 advanced use-case
S: A container group in Azure Container Instances runs a web container that requests 1 vCPU and a log-shipping container that requests 0.5 vCPU. The web container has short CPU spikes while the log shipper is mostly idle. How is CPU allocated, and what lets the web container use the idle capacity?
A: The group gets 1.5 vCPU, the sum of the requests; set a resource limit of 1.5 vCPU on the web container so it can use idle CPU
B: The group gets 1 vCPU, the largest request, shared by both; raise the web container's request to 2 vCPU with an in-place update
C: The group gets 1.5 vCPU, the sum of the requests; set a resource limit of 3 vCPU on the web container so it can borrow host CPU
D: The group gets 1.5 vCPU, the sum of the requests; add an ACI autoscale rule that adds a web container when CPU passes 80%
K: A
G: ## Container groups
A **container group** is the top-level resource in ACI: containers scheduled on the same host that share a lifecycle, resources, a local network (they reach each other over `localhost`) and storage volumes, similar to a Kubernetes pod. Typical pairs are an app plus a logging or monitoring sidecar.
## How resources are allocated
- **Requests** are mandatory per container. The group is allocated the **sum** of its containers' requests: 1 + 0.5 = **1.5 vCPU**.
- A group gets at least 1 CPU and 1 GB of memory; single containers in it can request less.
- An optional **limit** lets one container use more than its request, up to the limit, when others leave capacity idle. The limit must be greater than or equal to the request, and the **largest limit allowed is the group's total** allocation.
- Plan a small buffer: the service uses a little of the group's resources.
## Scaling and resizing
A container group has no CPU-based autoscale rule that adds containers. Changing CPU or memory requests requires deleting and recreating the group, because those properties can't be updated in place.
W: Sum of requests, limit at group total: the group receives 1.5 vCPU. A 1.5 vCPU limit on the web container lets it burst into the CPU the idle log shipper isn't using, without redeploying a larger group.
X: B=Largest request: ACI adds the requests of all containers; it doesn't size the group by the largest one. CPU requests also can't be changed in place: that needs delete and recreate.
C=Limit of 3 vCPU: a container's limit can't exceed the resources allocated to the whole group, 1.5 vCPU here; ACI doesn't lend extra host CPU beyond the group's allocation.
D=Autoscale rule: a container group has no CPU-based autoscale rule that adds containers to it. Running more copies means deploying more container groups yourself, or choosing a service with scale rules, such as Azure Container Apps.
T: An ACI container group gets the sum of its containers' requests, and a per-container limit (at most the group total) lets one container use capacity the others leave idle.

@ AZ-104 D3 T3.3 applied use-case
S: A team runs a container app with external ingress in the default revision mode. It wants to send 10% of user traffic to a new image version for a day, keep 90% on the current revision, and roll back quickly if errors rise. What should the administrator configure?
A: Switch the app to multiple revision mode, deploy the new image as a new revision, and set the traffic weights to 90 and 10
B: Keep single revision mode and give the new revision a 10% weight, because single mode keeps the old revision until traffic moves
C: Create a staging deployment slot on the container app and set its traffic percentage to 10 in the deployment slot settings
D: Deploy the new image as a second container app with internal ingress, and set the environment to split traffic 90 to 10
K: A
G: ## Revisions
A **revision** is an immutable snapshot of a container app version. Changes in the `properties.template` section (image, container settings, scale rules, revision suffix) create a new revision; changes in `properties.configuration` (secrets, revision mode, ingress) apply to all revisions without creating one.
## Revision modes
- **Single** (default): each new revision is provisioned, becomes ready, then receives **all** traffic, and the old revision is deprovisioned automatically. No percentage split is possible.
- **Multiple**: several revisions stay active at once, you choose when to deactivate old ones, and you can **split traffic** between them.
Learn also lists a third mode, deployment labels, which is still in preview.
## Traffic splitting
Weights are percentages per revision (or per label) and must add up to 100. In the portal: **Revision management**, set the mode to Multiple, then enter the traffic per active revision. In the CLI:
`az containerapp ingress traffic set -n app-orders -g rg-apps --revision-weight app-orders--v1=90 app-orders--v2=10`
Rolling back is setting the weights back to 100 and 0. Labels can also give a revision its own URL for testers.
W: Multiple revision mode with weights: only multiple revision mode keeps two revisions active, and ingress traffic splitting sends exactly 90% and 10% to them, with rollback as simple as moving the weight back.
X: B=Single mode weight: in single revision mode the new revision takes 100% of traffic once it is ready and the old one is deprovisioned, so there is no way to hold a 90/10 split.
C=Deployment slots: deployment slots and slot traffic percentages are an Azure App Service feature. Container Apps uses revisions and traffic weights instead.
D=Second app with internal ingress: internal ingress keeps the app reachable only inside the environment, and the environment doesn't split one app's URL across two different apps by percentage.
T: In Azure Container Apps, canary and blue-green releases use multiple revision mode with ingress traffic weights that add up to 100.

@ AZ-104 D3 T3.3 advanced troubleshooting
S: An administrator deploys a container app that processes messages from an Azure Service Bus queue. Ingress is disabled, minimum replicas is 0, and no scale rule was added. Messages pile up in the queue and the app shows zero running replicas. What should the administrator do to fix this while still allowing scale to zero?
A: Add a custom scale rule of type azure-servicebus with the queue name and a message count, authenticated with a secret or managed identity
B: Add an HTTP scale rule with concurrentRequests set to 1, so that the first message that arrives in the queue starts a new replica
C: Raise the maximum number of replicas from 10 to 30, so that the platform has enough room to start replicas when messages arrive
D: Lower the KEDA polling interval to 5 seconds, so that the platform checks the queue more often and starts a replica sooner
K: A
G: ## How Container Apps scales
Container Apps scales replicas horizontally with **KEDA** (Kubernetes Event-driven Autoscaling). A scale definition has:
- **Limits**: minimum replicas (default 0) and maximum replicas (default 10).
- **Rules**: HTTP (concurrent requests), TCP (concurrent connections), or **custom** rules based on any ScaledObject KEDA scaler, such as `azure-servicebus`, `azure-queue`, Event Hubs, Kafka, CPU or memory.
- **Behavior**: for custom rules KEDA polls the source every 30 seconds by default and waits a 300-second cool-down before scaling the last replica to 0.
## The trap: no ingress, no rule
If you add no rule, the **default HTTP rule** (0-10 replicas) applies. Learn warns: if ingress is disabled and you set neither a minimum of 1 or more nor a custom rule, the app **scales to zero and has no way of starting back up**.
## A queue-driven rule
```
--scale-rule-name sb-orders --scale-rule-type azure-servicebus
--scale-rule-metadata "queueName=orders" "namespace=sb-contoso" "messageCount=5"
--scale-rule-auth "connection=sb-connection-secret"
```
Authentication uses a Container Apps secret or, for Service Bus, Queue Storage and Event Hubs, a managed identity (CLI or ARM; not in the portal). Adding or editing a scale rule creates a new revision of the app.
W: Custom azure-servicebus rule: KEDA watches the queue length, starts replicas when messages arrive (desired replicas = messages / messageCount) and returns to zero when the queue is empty, so the app processes the backlog and still costs nothing when idle.
X: B=HTTP scale rule: HTTP rules count HTTP requests reaching the app through ingress. Ingress is disabled and queue messages are not HTTP requests, so this rule never fires.
C=More maximum replicas: the maximum is an upper bound. With a minimum of 0 and no rule that reacts to the queue, nothing asks for even one replica.
D=Shorter polling interval: the polling interval applies to custom KEDA rules, and there is no queue rule here to poll. A faster check of nothing still starts nothing.
T: A container app without ingress needs a custom event-driven scale rule (or a minimum of 1 replica), otherwise it scales to zero and never wakes up.

@ AZ-104 D3 T3.3 applied use-case
S: A company is creating a new Azure Container Apps environment for an internal HR app. The app must be reachable from virtual machines in a virtual network and from on-premises users over a site-to-site VPN, but never from the internet. How should the administrator configure it?
A: Create the environment as internal in a subnet of the virtual network, and set the app's ingress to external, accepting traffic from anywhere
B: Create the environment with a public inbound IP, and set the app's ingress to internal, limited to the Container Apps environment
C: Create the environment as internal in a subnet of the virtual network, and set the app's ingress to internal, limited to the environment
D: Create the environment with a public inbound IP for testing, and change its accessibility level to internal before the app goes live
K: A
G: ## Two settings decide who can reach an app
1. **Environment accessibility level**, chosen when the environment is created. An **internal** environment (`az containerapp env create ... --internal-only true` with your own subnet) has **no public endpoint**; it is reachable only through an internal load balancer in the virtual network. This setting **can't be changed after creation**.
2. **App ingress visibility**, per app:
- **External** ("Accepting traffic from anywhere"): published at the environment's inbound endpoint. In an internal environment, that endpoint is the internal load balancer, so clients in the virtual network and connected networks can reach the app.
- **Internal** ("Limited to Container Apps Environment"): reachable directly only from other apps in the same environment. In an internal environment, requests through the internal load balancer return HTTP 404.
## The combination for private apps
Learn's pattern for "VNet only, not the internet" is: **internal environment + external app ingress**. Peered networks and on-premises networks connected by VPN or ExpressRoute reach it through the virtual network.
## Example
`az containerapp ingress enable -n app-hr -g rg-hr --target-port 8080 --type external` on an app in an environment created with `--internal-only true`.
W: Internal environment, external ingress: the internal environment removes any public endpoint, and external ingress publishes the app on the environment's internal load balancer, so VMs and VPN users can reach it while the internet can't.
X: B=Public environment, internal ingress: internal ingress makes the app reachable only from other apps in the same environment, so the virtual network VMs and on-premises users can't reach it either.
C=Internal environment, internal ingress: this hides the app from the rest of the virtual network too; requests through the internal load balancer return HTTP 404.
D=Switch to internal later: the accessibility level is fixed when the environment is created, so a public environment can't be converted. It would have to be recreated.
T: For a Container Apps app that only the virtual network and connected networks may reach, create an internal environment and give the app external ingress.
