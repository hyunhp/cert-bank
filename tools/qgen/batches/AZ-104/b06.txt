# AZ-104 D2 T2.3 Configure Azure Files and Azure Blob Storage (file shares, container access, tiers, soft delete, snapshots, lifecycle, versioning)

@ AZ-104 D2 T2.3 applied comparison
S: A small engineering firm moves its project folders to Azure Files. Designers on Windows 11 laptops and a build server running Ubuntu must open and edit the same files in one share. Which share configuration should the administrator create?
A: An SMB file share, because Windows clients mount it natively and Linux clients can mount the same share with the SMB kernel client
B: An NFS file share, because NFS is the only protocol in Azure Files that Linux clients can mount and Windows 11 also includes a client
C: One SMB share and one NFS share that point at the same data, because Azure Files exposes a single share over both protocols at once
D: An NFS file share on the HDD media tier, because NFS on standard storage gives both Windows and Linux clients a common POSIX view
K: A
G: ## Two protocols, one per share
Azure Files offers two industry-standard protocols for mounting a share: **SMB** and **NFS** (NFSv4.1). Each share uses one of them. Learn states plainly that a single Azure file share cannot be accessed with both SMB and NFS; you can create an SMB share and a separate NFS share in the same storage account, but they hold separate data.
## Which clients can use which protocol
- **SMB shares** are mounted by Windows (drive letter or UNC path), by Linux through the SMB kernel client (`mount -t cifs`), and by macOS.
- **NFS shares** are for Linux/UNIX workloads that need POSIX semantics, UID/GID permissions and case sensitivity. Learn's NFS page says NFS Azure file shares **aren't supported for Windows**, and lists "access same data from Windows and Linux client" as not supported.
- NFS also needs the SSD (premium) media tier; there is no NFS on HDD.
## Example
A share named `projects` is created as SMB. Windows laptops map it as `P:` and the Ubuntu build server mounts `//<account>.file.core.windows.net/projects` with the SMB client, so everyone works on the same files.
W: SMB share: SMB is the protocol both client families can use. Windows mounts it natively, and Learn documents mounting SMB Azure file shares on Linux with the SMB kernel client, so one share serves both groups.
X: B=NFS share for both: Azure Files NFS shares are not supported on Windows clients, and Linux can also mount SMB, so NFS is neither the only Linux option nor a path for the Windows laptops.
C=SMB and NFS over one data set: Azure Files does not let one share be accessed with both protocols. Two shares in one account are two separate data sets, so edits in one would never appear in the other.
D=NFS on HDD: NFS shares require the SSD media tier, so this configuration cannot be created, and even on SSD the Windows designers could not mount it.
T: Mixed Windows and Linux clients on the same files means an SMB share; NFS shares are Linux-only, SSD-only and never shared with SMB.
V: Azure Files

@ AZ-104 D2 T2.3 advanced troubleshooting
S: An administrator creates an NFS file share in a premium FileStorage account. To let an on-premises Linux server mount it over the internet, she adds the office's public IP address to the storage account firewall. The mount still fails. What is the cause and fix?
A: NFS shares accept no IP address network rules; reach the share through a private endpoint over the site-to-site VPN instead
B: NFS shares need TCP port 445 open outbound; ask the office ISP to unblock port 445 and then retry the same mount command
C: NFS shares authenticate with the storage account key; pass the key in the mount options so the firewall rule takes effect
D: NFS shares require identity-based access; join the Linux server to Microsoft Entra Domain Services before mounting again
K: A
G: ## How NFS shares decide who may connect
NFS Azure file shares do **not** support user-based authentication: there is no storage account key and no Kerberos/Entra identity in the NFS mount. Instead, Azure Files relies on **network-level access** to decide which clients are allowed. Learn's NFS page states that clients must connect through:
- a **private endpoint**, which gives the share a private IP address in a virtual network (reachable from peered networks and from on-premises over VPN or ExpressRoute), or
- a **service endpoint** with virtual network restrictions on the storage account.
The feature table for NFS shares lists "Grant network access to specific Azure virtual networks" as supported and "Grant network access to specific IP addresses" as **not supported**.
## Example
The firm already has a site-to-site VPN to `vnet-hub`. The admin creates a private endpoint for the `file` sub-resource in that virtual network, makes sure on-premises DNS resolves `<account>.file.core.windows.net` to the private IP, and the server mounts with `mount -t nfs ... -o vers=4,minorversion=1,sec=sys`.
W: No IP rules for NFS: an IP address firewall rule is not a supported way to admit NFS clients. A private endpoint reached over the existing VPN gives the server a supported, private network path to the share.
X: B=Port 445: TCP 445 is the SMB port. NFS uses its own port, and the failure here is that NFS never trusts an IP rule, not that a port is blocked by the ISP.
C=Account key in mount options: NFS shares have no key-based or user-based authentication at all, so there is no key to pass and the IP rule still would not admit the client.
D=Identity-based access: identity-based authentication is listed as not supported for NFS shares; it is an SMB feature, so domain-joining the server changes nothing.
T: NFS Azure file shares trust networks, not identities or IP rules: connect through a private endpoint or a service endpoint from an allowed virtual network.

@ AZ-104 D2 T2.3 applied comparison
S: A company is choosing a billing model for new Azure file shares and asks the administrator to confirm how the models work. Which TWO statements about Azure Files billing models are correct? (Select TWO)
A: With provisioned v2, you pay for the storage, IOPS and throughput you provision, whether or not the share actually uses them
B: The pay-as-you-go model is available only on the HDD media tier, and its bill depends on used storage, transactions and data transfer
C: The pay-as-you-go model is available for NFS shares on the SSD media tier, so Linux workloads can pay only for the data they store
D: A provisioned v2 share grows its provisioned storage automatically when it fills up, and the extra capacity is billed at the end of the month
E: With provisioned v2, a share's storage can be reduced again right after an increase, so admins can scale up for one hour and then back down
K: A,B
G: ## Three billing models
Azure Files offers **provisioned v2**, **provisioned v1** and **pay-as-you-go**. Microsoft recommends provisioned v2 for new deployments.
- **Provisioned v2**: you separately provision storage, IOPS and throughput, and you pay for what you provision regardless of usage. The provisioned storage is a hard limit: if you provision 2 TiB and write 2 TiB, the share is full until you raise the size or delete data. You can scale up or down, but a decrease is allowed only after 24 hours have passed since the last increase.
- **Provisioned v1**: you provision storage, and IOPS and throughput follow from it.
- **Pay-as-you-go**: you are billed for used storage, transactions and data transfer. Learn states that this model is **only available for HDD storage**, and pay-as-you-go shares support only SMB.
## Where NFS fits
NFS shares require SSD storage, so they use a provisioned model; there is no pay-as-you-go NFS share.
## Example
A 1 TiB provisioned v2 share holding 200 GiB is billed for 1 TiB plus the provisioned IOPS and throughput. The same data in a pay-as-you-go share is billed for about 200 GiB plus every read and write transaction.
W: A=Provisioned v2 bills what you provision: storage, IOPS and throughput are each provisioned, and that provisioned amount drives the bill, independent of how much the share really uses.
B=Pay-as-you-go is HDD only and usage based: Learn states the model is only available on HDD and bills for used storage, transactions and data transfer.
X: C=Pay-as-you-go NFS on SSD: pay-as-you-go exists only on HDD and supports only SMB, while NFS requires SSD; this combination does not exist.
D=Automatic growth: the provisioned size is the share's hard limit. When data reaches it, writes fail until an admin increases the provisioned storage or deletes data.
E=Immediate decrease: provisioned v2 lets you decrease a provisioned quantity only after 24 hours have passed since your last increase, so hourly up-and-down scaling is not possible.
T: Provisioned v2 = pay for what you provision (storage, IOPS, throughput); pay-as-you-go = HDD-only, SMB-only, pay for usage and transactions.

@ AZ-104 D2 T2.3 applied troubleshooting
S: A pay-as-you-go SMB file share holds about 1 TiB of scanned documents. Users now get "There is not enough space" when saving new files, although the storage account is nowhere near its capacity limit. What should the administrator check and change?
A: The share's quota, which caps how large this share can grow; raise it, which does not by itself increase the pay-as-you-go bill
B: The storage account's access tier, which limits share size; switch the account default from hot to cool to free extra capacity
C: The share snapshots, which count against the share quota; delete older snapshots so the live data has room to grow again
D: The share's soft delete retention, which reserves space for deleted files; shorten the retention period to release that space
K: A
G: ## Quota versus provisioned size
Every Azure file share has a maximum size it may grow to.
- In **provisioned** shares this value is the **provisioned size**, and you pay for it whether you use it or not.
- In **pay-as-you-go** shares the same setting is called the **quota**. Learn notes that the quota **does not directly affect the bill**: you still pay for the logical data stored and the transactions. If you don't set it, the quota defaults to the maximum the storage account supports.
The share's total logical size is enforced against the quota or provisioned size, so a share can be "full" long before the storage account is.
## What does not count
Learn's snapshot page says share snapshots **don't count towards the maximum share size limit**. Share soft delete works at the level of a whole deleted share, not individual files.
## Example
The share `scans` has a 1 TiB quota and holds 1 TiB of data. The admin raises its quota to 2 TiB in the share's properties; users can save again, and the bill still follows the data actually stored.
W: Share quota: the share has reached the maximum size set for it. Raising the quota removes the limit, and in the pay-as-you-go model the quota is only a cap, so a higher value does not raise the bill by itself.
X: B=Account access tier: the account default access tier (hot, cool, cold) applies to blob data, not to file share size. Pay-as-you-go file shares have their own tiers (transaction optimized, hot, cool), and none of them changes capacity.
C=Snapshots against quota: snapshots are differential and are billed, but they don't count towards the share's maximum size, so deleting them frees no room under the quota.
D=Soft delete reserving space: share soft delete keeps whole deleted shares for the retention period. It doesn't hold space inside a live share for deleted files.
T: A file share fills up at its own quota or provisioned size, not at the account limit; in pay-as-you-go the quota is a cap, not a charge.

@ AZ-104 D2 T2.3 applied troubleshooting
S: An administrator runs the portal's Connect script for an SMB file share on a laptop in a branch office. The script reports that the storage account isn't reachable, and `Test-NetConnection <account>.file.core.windows.net -Port 445` shows TcpTestSucceeded False. What is the most likely cause and a supported fix?
A: The branch ISP or firewall blocks TCP 445; connect the branch to Azure over a VPN or ExpressRoute and mount the share through it
B: The share needs a SAS token to mount; generate a file service SAS and pass it to `net use` in place of the storage account key
C: The client must use NFS for internet access; recreate the share as an NFS share and mount it with the Windows NFS client
D: The share's quota is full, so new SMB sessions are refused; raise the quota and then rerun the same Connect script
K: A
G: ## SMB needs port 445
SMB uses **TCP port 445**. Learn's Windows mount guide says connections fail if 445 is blocked, and recommends `Test-NetConnection -ComputerName <account>.file.core.windows.net -Port 445` to check. Some ISPs and corporate firewalls block outbound traffic on 445.
## Ways around a blocked port
- Open 445 outbound on the firewall, if policy allows.
- Use a **VPN or ExpressRoute** connection so the client reaches the share privately (often through a private endpoint) without exposing 445 to the internet.
Outside the share's Azure region the client must also support **SMB 3.x**, because SMB 2.1 has no encryption and is refused over the public endpoint.
## What does not help
Learn also states that SAS tokens aren't supported for mounting Azure file shares; mounting uses the storage account key or identity-based authentication.
## Example
After a point-to-site VPN to the hub virtual network is set up and the account has a private endpoint, `Test-NetConnection` succeeds against the private IP and the script maps the share as `Z:`.
W: Blocked port 445: the failed TCP test is the classic symptom of an ISP or firewall dropping 445. A VPN or ExpressRoute connection is the documented way to mount from outside Azure without opening that port.
X: B=SAS token for the mount: SAS tokens aren't supported for mounting Azure file shares, and authentication is never reached anyway because the TCP connection itself fails.
C=Switch to NFS: NFS Azure file shares aren't supported on Windows clients, and NFS shares need a private endpoint or service endpoint rather than internet access.
D=Quota full: a full quota stops writes on a mounted share. It doesn't make the TCP connection to port 445 fail before any SMB session starts.
T: When an SMB mount fails and the port 445 test fails, the network blocks SMB: open 445 or route the traffic over VPN or ExpressRoute.

@ AZ-104 D2 T2.3 applied use-case
S: A museum's storage account already allows anonymous access. Container `media` holds public product images and, under the `drafts/` prefix, unreleased images. The website must load public images by URL with no token, visitors must not list blobs, and drafts must never be readable anonymously. What should the administrator do?
A: Move the drafts into a separate container left at Private, then set the anonymous access level of `media` to Blob
B: Set `media` to the Blob level, then set the anonymous access level of the `drafts/` virtual directory to Private
C: Set `media` to the Container level, which serves blobs by URL to anonymous clients but never returns a blob list
D: Set `media` to the Blob level and rename every draft to a long random name, so visitors can't guess any draft URL
K: A
G: ## Where anonymous access is configured
Anonymous (public) read access to blob data is controlled by two settings:
- **Storage account**: *Allow Blob anonymous access* (`AllowBlobPublicAccess`). If it is disabled, no container can be anonymous. In this scenario it is already enabled.
- **Container**: the anonymous access level. Learn states that you **can't change the anonymous access level for an individual blob**; it is set **only at the container level** and applies to every blob in that container.
Because blob storage has a flat namespace, `drafts/` is just part of each blob's name, not a separate object that carries its own access level.
## The three container levels
- **Private** (default): every request must be authorized.
- **Blob**: anonymous clients can read any blob in the container if they know its URL, but can't enumerate the blobs.
- **Container**: anonymous clients can read blobs and also list the blobs in the container (but never list the account's containers).
## Example
The admin copies `media/drafts/*` into a new Private container `media-drafts` (for example with AzCopy), deletes the originals, and sets `media` to **Blob**. `https://<account>.blob.core.windows.net/media/vase.jpg` loads in a browser, while listing `media` or reading anything in `media-drafts` fails for anonymous callers.
W: Separate container, then Blob level: the access level always covers a whole container, so blobs that must stay private have to live in a different, Private container. The Blob level then serves the public images by URL without letting visitors list them.
X: B=Private level on a virtual directory: the anonymous access level exists only on containers. A prefix such as `drafts/` is part of the blob names and can't carry its own access level.
C=Container level: this level lets anonymous clients enumerate the blobs in the container, so visitors could list every image, including the drafts.
D=Random draft names: with the Blob level every blob in `media` is readable by anyone who has its URL. Hard-to-guess names hide the drafts but don't stop anonymous reads once a URL leaks.
T: Anonymous access is set per container, never per blob or folder: keep private blobs in a Private container and use Blob (read by URL, no listing) for public ones.

@ AZ-104 D2 T2.3 applied comparison
S: A general-purpose v2 account has the default access tier hot. Container `exports` holds 5,000 blobs uploaded without a tier (the portal shows Hot (inferred)) and 200 blobs an app uploaded with the tier explicitly set to hot. The administrator changes the account's default access tier to cool. What is the result?
A: The 5,000 inferred blobs move to cool and are billed as write operations, while the 200 explicitly tiered blobs stay hot
B: All 5,200 blobs move to cool, because a change of the default access tier overrides the tier explicitly set on any blob
C: No existing blob moves, because the new default applies only to blobs uploaded later, so all 5,200 blobs stay in hot
D: The 5,000 inferred blobs move to cool free of charge, because changing an account setting runs no blob operations
K: A
G: ## Default access tier
Every general-purpose v2 account has a **default access tier**: hot (the default for new accounts), cool or cold. It decides the online tier of a new blob when the upload doesn't specify one. **Archive can't be the default access tier.**
## Inferred versus explicit tiers
- A blob uploaded without a tier has an **inferred** tier: it follows the account default, and the portal shows *Hot (inferred)*, *Cool (inferred)* or *Cold (inferred)*.
- A blob whose tier was set on upload or later with Set Blob Tier has an **explicit** tier, which the account default no longer affects.
Learn states that changing the default access tier **applies to all blobs for which an access tier hasn't been explicitly set**.
## What the change costs
- Toggling the default to a **cooler** tier in a general-purpose v2 account is charged as **write operations** (per 10,000) for every blob with an inferred tier.
- Toggling to a **warmer** tier is charged as **read operations** (per 10,000) plus **data retrieval** (per GB) for those blobs.
## Example
After the change, the 5,000 inferred blobs show *Cool (inferred)* and the bill shows write operations for them; the 200 blobs still show *Hot*. To move those too, the admin would run Set Blob Tier on them or use a lifecycle rule.
W: Inferred blobs follow the default: changing the default access tier re-tiers every blob without an explicit tier, and moving to a cooler tier in a general-purpose v2 account is billed as write operations for those blobs. Explicitly tiered blobs keep their tier.
X: B=Default overrides explicit tiers: the default only applies to blobs whose tier is inferred. A tier set explicitly on a blob stays until someone changes that blob's tier.
C=Only new uploads affected: inferred blobs have no tier of their own, so they move with the account default as soon as it changes, not only blobs uploaded afterwards.
D=No charge: in a general-purpose v2 account the switch to a cooler default is charged as write operations for every inferred blob, so large containers can make the change noticeably costly.
T: Changing the account default tier moves every blob with an inferred tier (billed as tier-change operations) and leaves explicitly tiered blobs where they are.

@ AZ-104 D2 T2.3 applied use-case
S: Yesterday an administrator started a standard-priority rehydration of 400 archived blobs to the hot tier. Now legal needs one 2 GB contract from that set as soon as possible, and its rehydration is still pending. What should the administrator do?
A: Set the rehydration priority of that one blob to High while its standard rehydration is still pending
B: Cancel the pending Set Blob Tier request for that blob and start it again with High priority instead
C: Download the archived blob directly with AzCopy, which reads archive data without needing to rehydrate
D: Take a snapshot of the archived blob and read the snapshot, which is served from an online tier right away
K: A
G: ## Rehydrating from archive
A blob in the **archive** tier is offline: it cannot be read or modified until it is **rehydrated** to hot, cool or cold, either with **Set Blob Tier** on the blob itself or with **Copy Blob** to a new online blob.
## Rehydration priority
- **Standard** (default): processed in the order received; can take up to 15 hours for objects under 10 GB.
- **High**: prioritized; may finish in under an hour for objects under 10 GB, at a higher cost.
While a standard request is pending, you **can raise** a blob's priority to High (for example, bulk restore at Standard and then expedite the few urgent blobs). You **can't lower** a pending request from High to Standard, and a Set Blob Tier request **can't be cancelled** once it starts. High-priority throughput is also limited per storage account, so expedite only what is urgent.
## Example
`az storage blob set-tier --container-name contracts --name 2021/acme.pdf --tier Hot --rehydrate-priority High` updates the pending request for that blob (the target tier must match the one in the original request); the other 399 blobs continue at Standard.
W: Raise priority to High: Learn explicitly allows updating a pending standard-priority rehydration to High for individual blobs that are needed sooner, without touching the rest of the bulk job.
X: B=Cancel and restart: a Set Blob Tier request can't be cancelled after it starts. The supported path is to update the priority of the pending request.
C=AzCopy download from archive: no tool can read archived blob data; only metadata and properties are available until rehydration completes.
D=Snapshot of an archived blob: snapshots aren't supported for archived blobs, and a snapshot would still not make offline data readable.
T: A pending standard rehydration can be raised to High priority for urgent blobs; it can't be cancelled or lowered from High to Standard.

@ AZ-104 D2 T2.3 advanced troubleshooting
S: An administrator rehydrated an archived blob to the hot tier with Set Blob Tier. Two days later it is back in archive. The account's lifecycle rule has `tierToArchive` with `daysAfterModificationGreaterThan: 180`, and the blob was last modified three years ago. How should she stop this from recurring?
A: Add a `daysAfterLastTierChangeGreaterThan` condition to the rule's `tierToArchive` action, or rehydrate future blobs by copying them
B: Enable blob versioning on the account, so the rehydrated blob becomes a new current version that the archive rule doesn't evaluate
C: Change the condition to `daysAfterCreationGreaterThan: 180`, because the creation time is reset whenever a blob is rehydrated
D: Turn on `enableAutoTierToHotFromCool` in the same rule, so blobs that are read are moved back to hot instead of archive
K: A
G: ## Why rehydrated blobs get re-archived
A lifecycle rule checks each blob's age against a time condition. Learn points out that **changing a blob's tier does not change its last modified time** (nor its last access time). After rehydration, a blob modified three years ago still matches `daysAfterModificationGreaterThan: 180`, so a later policy run archives it again.
## Two documented fixes
- Add `daysAfterLastTierChangeGreaterThan` to the `tierToArchive` action. It sets the minimum number of days a rehydrated blob stays online before the rule may archive it again, and it applies only to `tierToArchive`.
- Rehydrate by **Copy Blob** to a new blob in an online tier. The copy is a new blob with a new last modified time, so the rule doesn't match it, and the archived source stays untouched.
## Example
```
"tierToArchive": { "daysAfterModificationGreaterThan": 180,
                   "daysAfterLastTierChangeGreaterThan": 30 }
```
W: Tier-change condition or copy: the extra condition keeps any rehydrated blob online for the chosen period, and copying creates a fresh blob with a new modified time; both are the remedies Learn gives for this exact behaviour.
X: B=Enable versioning: rehydration doesn't write the blob, so no new version is created, and lifecycle rules for the current version still use its old last modified time.
C=Creation time reset: a tier change works on the existing blob and doesn't create a new one, so its creation time stays three years old. The blob would still match a 180-day creation condition and be archived again.
D=Auto tier to hot: `enableAutoTierToHotFromCool` only moves cool blobs back to hot when accessed, works with the last access condition, and does nothing to stop a `tierToArchive` action.
T: Changing a blob's tier keeps its last modified time; use `daysAfterLastTierChangeGreaterThan` (or rehydrate by copy) so lifecycle rules don't re-archive rehydrated blobs.

@ AZ-104 D2 T2.3 applied troubleshooting
S: Container `app` holds blobs named `logs/2026/...` (many written in January) and `data/...`. A lifecycle rule created a week ago should delete log blobs older than 90 days, with filter `"prefixMatch": ["logs/"]` and `blobTypes: ["blockBlob"]`. No logs have been deleted. What is wrong?
A: The prefix must start with the container name, so the filter needs to be `app/logs/` instead of `logs/`
B: Prefix filters need a wildcard to match nested folders, so the filter needs to be `logs/*` instead of `logs/`
C: The rule must also have a blob index tag filter, because a prefix filter can't be used as the only filter
D: The policy needs up to 30 days before its first run, so the rule will start deleting blobs later this month
K: A
G: ## How lifecycle filters select blobs
A lifecycle rule has **filters** (which blobs), **conditions** (how old) and **actions** (what to do).
- `blobTypes` is required: `blockBlob` or `appendBlob`.
- `prefixMatch` is optional, up to 10 case-sensitive prefixes per rule. Learn states that **a prefix string must start with a container name**: to match `https://<account>.blob.core.windows.net/sample-container/blob1/...` you write `sample-container/blob1`.
- Prefixes don't support wildcards; `*` and `?` are treated as literal characters.
- `blobIndexMatch` (blob index tags) is optional. If several filters are set they are combined with AND, and filters can only include blobs, never exclude them.
## Timing
After you add or change rules, it can take up to 24 hours before the changes take effect and the first run starts; after that the policy runs periodically and evaluates each blob once per run.
## Example
```
"filters": { "blobTypes": ["blockBlob"], "prefixMatch": ["app/logs/"] },
"actions": { "baseBlob": { "delete": { "daysAfterModificationGreaterThan": 90 } } }
```
W: Container name in the prefix: `logs/` would match only blobs in a container literally named `logs`. Writing `app/logs/` matches the log blobs inside container `app`.
X: B=Wildcard: prefix strings don't support wildcard matching; `logs/*` would look for names that literally contain an asterisk and match nothing.
C=Index tag filter required: `blobIndexMatch` is optional. A rule can filter on prefix alone, or even on no prefix at all to cover the whole account.
D=30 days to start: rule changes take up to 24 hours to take effect, and the rule was created a week ago, so timing is not the reason.
T: Lifecycle `prefixMatch` values start with the container name (`container/path`) and don't support wildcards.

@ AZ-104 D2 T2.3 advanced use-case
S: A news site stores article images as block blobs. Images that nobody has read for 60 days should move to cool, and an image that is read again should return to hot automatically. Which TWO configuration steps does the administrator need? (Select TWO)
A: Enable access time tracking on the storage account so that Azure records each blob's last access time
B: Add a rule with `tierToCool` set to `daysAfterLastAccessTimeGreaterThan: 60` and `enableAutoTierToHotFromCool` set to true
C: Add a rule with `tierToCool` set to `daysAfterModificationGreaterThan: 60` and `enableAutoTierToHotFromCool` set to true
D: Change the account's default access tier to cool so that images with an inferred tier cool down when they are not used
E: Enable blob versioning on the account so that each read of an image creates a version the lifecycle rule can evaluate
K: A,B
G: ## Lifecycle conditions
Lifecycle conditions are based on three blob times:
- `daysAfterCreationGreaterThan`: creation time
- `daysAfterModificationGreaterThan`: last write
- `daysAfterLastAccessTimeGreaterThan`: last **read or write**, available only when **access time tracking** is enabled on the account
## Last access time
With tracking on, the blob property `LastAccessTime` is updated by access operations such as Get Blob and Put Blob (at most once per 24 hours per blob). Get Blob Properties, Get Blob Metadata and Get Blob Tags don't count as access. If tracking is off, the rule uses the date tracking was enabled instead of real access times, so it can't follow reads.
## Moving back to hot
`enableAutoTierToHotFromCool` moves a cool blob back to hot when it is accessed. It works only together with `daysAfterLastAccessTimeGreaterThan`, has no effect on blobs that were already in cool before the action was enabled in a rule, and moves a blob back at most once in 30 days to avoid repeated early deletion charges.
## Example
`az storage account blob-service-properties update --enable-last-access-tracking true`, then a rule with `"tierToCool": {"daysAfterLastAccessTimeGreaterThan": 60}, "enableAutoTierToHotFromCool": true`.
W: A=Access time tracking: without it the account doesn't record reads, so "not read for 60 days" can't be evaluated and the last access condition falls back to the date tracking was enabled.
B=Last access condition with auto tier: this rule cools images that haven't been read for 60 days, and the auto tier flag returns an image to hot as soon as it is accessed again.
X: C=Modification-based condition: images are written once and then only read, so modification time ignores reads; `enableAutoTierToHotFromCool` is also only available with the last access condition.
D=Cool as the default tier: changing the default re-tiers every inferred blob at once, regardless of how often each image is read, and nothing ever moves a read image back to hot.
E=Versioning: versions are created by writes, not reads, and they play no part in tracking access; this only adds storage cost.
T: To tier by reads, enable access time tracking and use `daysAfterLastAccessTimeGreaterThan`; add `enableAutoTierToHotFromCool` to bring accessed blobs back to hot.

S: A storage account has blob soft delete (14 days) and blob versioning enabled. A user deleted `budget.xlsx` yesterday. The administrator selects the blob in the portal and clicks Undelete, but `budget.xlsx` still has no current version. How does the administrator restore the file?

G: ## What a delete does when versioning is on
With **blob versioning** enabled, deleting a blob does not remove its data: the **current version becomes a previous version**, and the blob has no current version any more. Earlier previous versions persist too.

## Restoring
Learn's soft delete management page explains the difference:

G: ## How container soft delete works
When **container soft delete** is enabled, a deleted container and its contents are kept for the retention period (1 to 365 days, default 7). During that time **Restore Container** brings back the container with its blobs, versions and snapshots.
## Rules that trip admins up
- A container can be restored **only to its original name**. If a new container with that name exists, you must rename or delete it before restoring.

G: ## Share snapshots
A **share snapshot** is a read-only, point-in-time, incremental copy of an Azure file share. You can browse it and **restore individual files or folders** by copying them back to the live share or to another location. On Windows, SMB share snapshots appear in File Explorer's **Previous Versions** tab, and Robocopy can copy from the snapshot path. A share keeps up to 200 snapshots; Azure Backup can schedule them.
## Share soft delete
**Soft delete for file shares** works **only at the share level**: it protects against deleting the whole share and restores it, with its snapshots, during the retention period. Learn says that to restore deleted files you use share snapshots or Azure file share backup.
## Important detail
Snapshots are deleted together with the share; you can't delete a share and keep its snapshots. Soft delete covers that case by bringing back the share and its snapshots.
## Example
In File Explorer on the mapped drive, the admin opens Properties > Previous Versions on the share root, picks last night's snapshot, and copies `Contracts` back.

D=Promote the snapshot to the base share: snapshots aren't promoted to the base share. Restoring is done by copying data out, and the whole-share revert that exists for SMB is only a limited preview.

@ AZ-104 D2 T2.3 applied comparison
S: An insurance team keeps claim documents as block blobs. A faulty sync job sometimes overwrites blobs or changes their metadata. The team wants every prior state kept automatically, with no change to the job, and a way to roll a blob back. Which feature should the administrator enable?
A: Blob versioning, which creates a new version on each write or metadata update so a previous version can be promoted
B: Blob soft delete, which keeps a soft-deleted snapshot on every overwrite and on every metadata or property update
C: Blob snapshots, which Azure takes on each write once enabled, so the team can copy a snapshot back over the blob
D: Container soft delete, which records each overwrite of a blob in the container and lets the team restore that blob
K: A
G: ## Versions versus snapshots
- A **blob version** is automatic and system-managed. With versioning enabled, every write (Put Blob, Put Block List, Copy Blob) and every **Set Blob Metadata** creates a new version; the old state becomes a previous version with its own version ID. No application change is needed.
- A **blob snapshot** is manual: an application or admin explicitly creates a point-in-time copy, for example before a planned update. Learn recommends stopping block blob snapshots once versioning is on.
## What blob soft delete covers
Blob soft delete keeps deleted blobs, and on overwrite creates a soft-deleted snapshot of the old data. But Learn states that soft delete **doesn't protect against writes to blob metadata or properties**; it points to versioning for that.
## Rolling back
To roll back, promote a previous version: copy it over the base blob (portal: *Make current version*). Microsoft recommends combining versioning with blob soft delete and container soft delete, and using a lifecycle rule to delete old versions to control cost.
## Example
`az storage account blob-service-properties update --resource-group rg-claims --account-name stclaims --enable-versioning true`
W: Blob versioning: it captures the prior state on every overwrite and on metadata updates with no change to the job, and any previous version can be promoted to roll the blob back.
X: B=Blob soft delete: it protects deletes and overwrites, but Learn says it doesn't protect metadata or property updates, so metadata changes by the job would be lost.
C=Automatic snapshots: snapshots are manual and application-driven; Azure doesn't take them on each write, so the job would have to be changed to create them.
D=Container soft delete: it only restores a whole deleted container. It records nothing about overwrites of blobs in a container that still exists.
T: For automatic protection of every overwrite and metadata change, enable blob versioning; snapshots are manual and soft delete misses metadata updates.
