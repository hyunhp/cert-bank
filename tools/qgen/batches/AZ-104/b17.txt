@ AZ-104 D1 T1.2 expert troubleshooting
S: A Linux VM in rg-orders runs an order service under the user-assigned managed identity id-orders. The service reads the secret orders-db from kv-orders, a vault that uses the Azure RBAC permission model and whose firewall allows the VM's subnet. Last week a cleanup script rewrote role assignments to reduce privileges. Since then every getSecret call from the service returns HTTP 403 Forbidden, and the vault's logs show the requests arriving from the allowed subnet under id-orders. Access control on kv-orders now lists Key Vault Reader for id-orders at vault scope, and Key Vault Secrets User for id-orders at the scope of the secret orders-archive. Security requires least privilege and forbids access policies. What should the administrator do?
A: Assign Key Vault Secrets User to id-orders at the scope of kv-orders, so the service can read orders-db along with the other secrets in the vault
B: Assign Key Vault Secrets User to id-orders at the scope of the secret orders-db, and remove Key Vault Reader if nothing else needs it
C: Assign Key Vault Secrets Officer to id-orders at the scope of the secret orders-db, so the service can read the value and also rotate it
D: Add the VM's subnet to the vault firewall again, because a request denied by the firewall is also reported as an authorization failure
K: B
G: ## Reading the evidence
A 403 from Key Vault has two typical causes: the caller lacks **data-plane permission**, or the **firewall** rejected the caller's network. Here the logs show the request arriving from the allowed subnet, so the network side is fine; the problem is authorization.
## What the current assignments grant
- **Key Vault Reader** at vault scope: metadata of keys, secrets and certificates only. Learn: it **can't read sensitive values such as secret contents**.
- **Key Vault Secrets User** at the scope of **orders-archive**: reads that one secret's value, not orders-db.
So id-orders can see that orders-db exists but can't read its value.
## Least privilege in an RBAC vault
Data roles can be scoped to the vault or to a **single secret**. Learn suggests vault-level assignments in general, but per-secret assignments are the tool when one identity must read only specific secrets.
W: Secrets User on orders-db: it grants exactly the getSecret permission on the one secret the service needs; Reader adds nothing the service uses.
X: A=Secrets User on the vault: it works, but it lets the service read every secret in kv-orders, which breaks least privilege.
C=Secrets Officer on the secret: it allows setting and deleting the secret too, more than a read-only service needs.
D=Firewall rule: the logs already show the call arriving from the allowed subnet, and the subnet is in the firewall rules, so the network isn't the cause.
T: Key Vault Reader never returns secret values; scope Key Vault Secrets User to the exact secret a workload needs.

@ AZ-104 D2 T2.1 expert troubleshooting
S: An Azure file share uses on-premises AD DS authentication. Eight months ago the storage account was registered as a computer account in the Servers OU with the AzFilesHybrid module. This morning every user gets Access is denied when mapping the share, while mapping it with the storage account key from an admin workstation still works. Share-level roles and Windows ACLs haven't changed, and the domain controllers log Kerberos failures for the storage account's service principal name. The Servers OU enforces a 180-day maximum password age for computer accounts. Requirements: restore identity-based access today, keep the account in the Servers OU, and prevent a repeat. What should the administrator do?
A: Reset the computer account's password in Active Directory Users and Computers, so that its Kerberos key matches the storage account again
B: Regenerate key1 of the storage account in the portal, because the AD account's password is derived from the first account access key
C: Move the computer account to an OU without password expiry, and wait for the next Kerberos ticket renewal to bring access back
D: Run Update-AzStorageAccountADObjectPassword from a domain-joined client to rotate to kerb2, and schedule the rotation before each expiry
K: D
G: ## The AD principal behind Azure Files
Domain-joining a storage account for AD DS authentication creates an AD **computer account or service account**. Its password is one of the storage account's **Kerberos keys** (`kerb1` or `kerb2`), so AD and Azure Storage share the secret.
## Password expiry
If the OU's password policy expires that password and nobody rotates it, **Kerberos authentication to the share is lost**. Key-based mounts keep working because they don't use Kerberos, exactly the pattern in the evidence. Some environments even delete principals with expired passwords.
## The fix
- `Update-AzStorageAccountADObjectPassword -RotateToKerbKey kerb2` regenerates the Kerberos key and sets it as the AD password in one step; run it from a domain-joined client.
- Later, rotate back to `kerb1` so both keys are refreshed.
- Prevent repeats: rotate on a schedule shorter than the OU's maximum age, or place the principal in an OU without rotation (not allowed here).
W: Update-AzStorageAccountADObjectPassword: it rotates the Kerberos key and the AD password together, which restores Kerberos today, and a schedule under 180 days prevents a repeat without moving the account.
X: A=Reset in ADUC: AD gets a password that Azure Storage doesn't know, so the Kerberos keys still don't match.
B=Regenerate key1: account access keys and Kerberos keys are separate; regenerating key1 breaks key users and doesn't touch the AD principal.
C=Move OU and wait: it violates the Servers OU requirement, and moving the account doesn't give it a valid password again.
T: An AD DS-joined storage account has an AD password tied to its Kerberos key; rotate it with Update-AzStorageAccountADObjectPassword before the OU policy expires it.

G: ## Flapping protection
Before a **scale-in**, autoscale estimates the metric after removing instances. If the estimate would immediately trigger a **scale-out**, it skips the scale-in (or removes fewer instances) to avoid **flapping**. Scale-outs are never held back. The run history shows these skips.
## Working the numbers
- Now: 3 instances x 48% = 144% total CPU.
- After scale-in to 2: 144 / 2 = **72%**, which is above the 70% scale-out threshold, so autoscale refuses.
- With the scale-out threshold at 80%: 72% is below 80%, so the scale-in goes ahead and the set doesn't bounce back.
## The rule of thumb
Keep a wide margin between thresholds. For n instances, the scale-in threshold times n/(n-1) should stay under the scale-out threshold.
W: Scale-out at 80%: the projected 72% after removing one instance is now inside the allowed range, so the skipped scale-in runs and the set settles at 2.

B=Decrease by 2: from 3 instances that targets 1, below the minimum, and the estimate at the resulting count still exceeds 70%, so the action stays blocked.
D=Shorter cool down: re-evaluating more often repeats the same 72% estimate and the same skip.
T: Autoscale skips a scale-in whose projected metric would trigger a scale-out; widen the gap between scale-in and scale-out thresholds.
