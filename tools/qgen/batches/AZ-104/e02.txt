G: ## Internal load balancer basics
An **internal** Standard Load Balancer has a private frontend IP. Clients in the VNet, in peered VNets or on premises (over VPN or ExpressRoute) connect to that address, and load-balancing rules spread the flows across the backend pool.
## The hairpin limitation
Learn lists this limitation for Azure Load Balancer: "Outbound flow from a backend VM to a frontend of an internal load balancer fails." The FAQ asks "Can I access the frontend of my internal load balancer from the participating backend pool VM?" and answers no: the scenario is not supported.
## Practical option
Run the job on a VM that is not a member of that backend pool, so its flow to the frontend is an ordinary client flow.
## Related but different
Outbound **internet** access is a separate topic. An internal Standard Load Balancer provides no outbound connectivity of its own, and outbound rules exist only on a public Standard Load Balancer. Explicit outbound methods are:
- a NAT gateway on the subnet
- a public IP on the VM's network interface
- an outbound rule on a public Standard Load Balancer that has the VM in its backend pool
Do not count on default outbound access instead: new virtual networks created with API versions released after March 31, 2026 (and in the portal) have private subnets, where VMs get no default outbound IP. Here the target is a private frontend in the same VNet, so internet egress is not involved at all.
W: Hairpin to own frontend is unsupported: Learn documents that flows from a backend pool VM to its internal load balancer's frontend fail, which matches a failure only on the backend VM while other clients succeed.
