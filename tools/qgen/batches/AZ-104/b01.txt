# AZ-104 D1 T1.1 Manage Microsoft Entra users and groups (users, groups, dynamic rules, bulk operations, licensing, B2B, SSPR)

@ AZ-104 D1 T1.1 advanced troubleshooting
S: A marketing agency wants a dynamic security group that contains every employee in the Sales or Marketing department. B2B guests from client companies also have the department attribute filled in, and they must never be included. Which membership rule meets the requirement?
A: (user.department -in ["Sales","Marketing"]) -and (user.userType -eq "Member")
B: (user.department -eq "Sales") -or (user.department -eq "Marketing") -and (user.userType -eq "Member")
C: (user.department -in ["Sales","Marketing"]) -and (user.userType -ne "Member")
D: (user.department -eq "Sales") -or (user.department -eq "Marketing") -and (user.objectId -ne null)
K: A
G: ## How dynamic membership rules are built
A rule for a dynamic membership group is an expression that is true or false for each user: `<property> <operator> <value>`, for example `user.department -eq "Sales"`. Several expressions are joined with `-and`, `-or` and `-not`.
- `-in` compares one attribute with a list of values: `user.department -in ["Sales","Marketing"]` is true for either department.
- `user.userType` is `Member` for employees and `Guest` for B2B guests, so `user.userType -eq "Member"` keeps guests out.
## Operator precedence
Microsoft Entra evaluates `-and` before `-or`. A rule written as `X -or Y -and Z` therefore means `X -or (Y -and Z)`, not `(X -or Y) -and Z`. Use parentheses whenever the precedence does not match what you mean, or avoid the problem with `-in`.
## Example
A guest from a client company with `department = Sales` matches `user.department -eq "Sales"` on its own. Only a rule where the user-type check applies to every department keeps that guest out.
W: -in plus userType check: the department list matches either department, and the `-and (user.userType -eq "Member")` part applies to both, so only employees in Sales or Marketing become members.
X: B=-or chain without grouping: because `-and` binds tighter than `-or`, this reads as Sales OR (Marketing AND Member). Every Sales guest still matches the first expression and joins the group.
C=userType -ne "Member": this inverts the user-type check and selects the Sales and Marketing users who are not members, which are exactly the guests the agency wants to exclude.
D=objectId -ne null: `user.objectId -ne null` is true for every user, guests included, so it filters nothing; the rule also keeps the same precedence problem with Sales guests.
T: Exclude guests with `user.userType -eq "Member"` and make sure it applies to the whole expression: `-and` is evaluated before `-or`, so group with parentheses or use `-in`.
V: Microsoft Entra ID, dynamic membership groups

@ AZ-104 D1 T1.1 applied troubleshooting
S: The group GRP-Engineering uses the dynamic rule user.department -eq "Engineering". A Groups Administrator needs to add a contractor whose department is "External" and finds no way to add him on the group's Members page. What is the cause, and what should the administrator do?
A: Members of a dynamic group cannot be added by hand; set the contractor's department so the rule matches him, or give him access through a separate assigned group
B: The contractor has no Microsoft Entra ID P1 license assigned; assign one to his account, and then the Add members option appears on the Members page of the group
C: Rule processing for the group is paused; resume processing on the group's overview page, and then add the contractor manually from the group's Members page
D: Only the group owner can add members to a dynamic group; make the administrator an owner of GRP-Engineering, and then add the contractor manually as a member
K: A
G: ## Assigned and dynamic membership
A Microsoft Entra group has one of these membership types:
- **Assigned**: owners or administrators add and remove members by hand.
- **Dynamic user** or **dynamic device**: a rule decides membership. When a user's attributes change, Microsoft Entra re-evaluates the rules and adds or removes the user automatically.
Because the rule owns the membership, you **can't manually add or remove members of a dynamic membership group**, whatever your role or ownership.
## Getting an exception into the group
- Change the attribute the rule reads, for example set the user's `department` to `Engineering`, and the next evaluation adds the user.
- Change the rule itself so it covers the exception.
- Or grant the resource to a second, assigned group as well, and put the exception there.
## Licensing note
Dynamic membership needs Microsoft Entra ID P1 (or Intune for Education) licenses for each unique member, but you don't have to assign the licenses to the users. The licenses don't unlock manual adds.
W: Rule-driven membership: in a dynamic group the rule is the only way users get in or out, so the administrator either makes the contractor's attributes match the rule or uses an assigned group for the exception.
X: B=Missing P1 license: dynamic groups require enough P1 licenses in the tenant, but they don't have to be assigned to members, and no license turns on manual membership changes for a dynamic group.
C=Paused processing: pausing only stops the rule from being evaluated. Even a paused dynamic group still does not accept manually added members.
D=Owner-only membership: ownership lets someone manage an assigned group's members. For a dynamic group, owners can't add members by hand either; the rule decides.
T: A dynamic group's members come only from its rule: change the user's attributes or the rule, or use a separate assigned group for exceptions.
V: Microsoft Entra ID, dynamic membership groups

@ AZ-104 D1 T1.1 applied definition
S: A security group named APP-Payroll-Users has 40 hand-picked members and is assigned to a payroll application. An administrator changes its membership type from Assigned to Dynamic User with the rule user.department -eq "Payroll". What happens to the group?
A: It keeps its name and object ID; current members who match the rule stay, members who don't match are removed, and other matching users are added
B: It keeps all 40 current members as permanent exceptions, and from now on the rule only adds new matching users without removing any of them
C: It is recreated with a new object ID that holds only the matching users, so the app assignment must be added again for the new group
D: It keeps its object ID but is emptied first; all members are removed, then the rule adds matching users back during the next sync cycle
K: A
G: ## Changing the membership type of an existing group
In the group's **Properties** you can switch the membership type between Assigned, Dynamic User and Dynamic Device. Microsoft Entra keeps the **same group name and object ID**, so app assignments, role assignments and other references to the group keep working. Creating a new group instead would mean updating every one of those references.
## What happens to the members
When an assigned (static) group becomes dynamic:
- existing members who meet the rule **remain**
- existing members who don't meet the rule **are removed**
- other users who meet the rule **are added** automatically
If the group controls access to an app, users can lose access until the rule has been fully processed. Test the rule first (the **Validate rules** tab checks sample users against it).
## Example
Of the 40 members, 35 have `department = Payroll` and stay; 5 from Finance are removed. Two Payroll employees who were never added by hand now join automatically.
W: Same group, rule-based members: conversion keeps the identity of the group, so the payroll app assignment still points to it, while membership is recalculated from the rule.
X: B=Manual members kept: a dynamic group has no manual exceptions. Members who don't satisfy the rule are removed during conversion.
C=Recreated with new ID: the documented behaviour is that the same name and ID are kept precisely so existing references, such as the app assignment, stay valid.
D=Emptied first: matching members simply remain. The group is not cleared and rebuilt, although non-matching members do lose access once processing completes.
T: Converting a group from assigned to dynamic keeps its ID and references; matching members stay, non-matching members are removed and new matches are added.
V: Microsoft Entra ID, dynamic membership groups

@ AZ-104 D1 T1.1 applied use-case
S: An IT team wants a group that automatically contains every Windows device in the tenant, so that it can target device policies at it. New devices must join the group without anyone editing it. Which group should the team create?
A: A security group with the Dynamic Device membership type and the rule device.deviceOSType -eq "Windows" entered in the rule text box
B: A Microsoft 365 group with the Dynamic Device membership type and the rule device.deviceOSType -eq "Windows" entered in the rule text box
C: A security group with the Dynamic User membership type and a rule that selects every user who is the registered owner of a Windows device
D: A Microsoft 365 group with the Assigned membership type, and a group owner who adds each new Windows device to it after it is joined
K: A
G: ## Which groups can hold devices
Microsoft Entra ID has two group types you manage in the admin center:
- **Security groups** control access to resources. Members can be users, devices or service principals.
- **Microsoft 365 groups** are for collaboration (shared mailbox, calendar, SharePoint site). Members can **only be users**.
## Dynamic device groups
A dynamic group is either for users or for devices, never both. A device rule can reference **only device attributes**, such as `deviceOSType`, `deviceOwnership` or `deviceTrustType`; it can't be based on the attributes of the device's owner.
The rule builder in the portal supports only user rules, so a device rule is typed in the text box, for example:
`device.deviceOSType -eq "Windows"`
## Licensing
Dynamic groups need Microsoft Entra ID P1 for users, but no license is required for devices that are members of a device-based dynamic group.
W: Security group with a dynamic device rule: only security groups can contain devices, and a Dynamic Device rule on `deviceOSType` adds every Windows device, including new ones, with no manual work.
X: B=Microsoft 365 group: Microsoft 365 groups can include only users, so a dynamic device rule is not available for this group type.
C=Dynamic User rule on owners: this group would contain users, not devices, and device membership can't be derived from the owner's attributes anyway.
D=Assigned Microsoft 365 group: it can't contain devices at all, and assigned membership means someone must edit the group for every new device.
T: Device groups must be security groups; use a Dynamic Device rule on device attributes such as `deviceOSType` to keep them up to date automatically.
V: Microsoft Entra ID, security groups, dynamic membership groups

@ AZ-104 D1 T1.1 advanced troubleshooting
S: Ten days ago, a User Administrator ran a bulk delete with the wrong CSV file and removed 150 active user accounts. The accounts must be brought back with their existing settings. Which TWO statements are correct? (Select TWO)
A: Run Bulk restore from the Deleted users page with a CSV file that lists the object ID of each user to restore
B: Restored users get back the licenses they had when deleted, even if that pushes license use above the number purchased
C: Run Bulk create with the original CSV file, because deleted accounts can only be rebuilt with their UPN and an initial password
D: Restored users receive new object IDs, so every app assignment and group membership has to be added again for each of them
E: Open a support case, because deleted users can be restored by an administrator only during the first seven days after deletion
K: A,B
G: ## Soft delete for users
When a user is deleted in Microsoft Entra ID, the account is not removed at once. It stays in a **suspended (soft-deleted) state for 30 days** and appears on the **Deleted users** page. During that window it can be restored **with all its properties**; the organization information is kept.
After 30 days, permanent deletion starts automatically and can't be stopped. A permanently deleted user can't be restored by anyone, including Microsoft Support; you would have to create a new account and re-enter everything.
## Restoring many users
**Bulk restore** (on the Deleted users page) takes a CSV file whose only required column is `Object ID [objectId]`, one deleted user per row. Errors per row are listed on the Bulk operation results page.
## Licenses after a restore
Licenses that were assigned at the time of deletion are **restored even if none are available**. The tenant can then temporarily use more licenses than it bought, so check license counts afterwards.
W: A=Bulk restore with object IDs: the accounts are still in the 30-day soft-delete window, and Bulk restore takes a CSV of object IDs to bring them back in one job.
B=Licenses restored: a restored user gets back the licenses assigned at deletion even when the pool is empty, which can leave the tenant temporarily over its purchased count.
X: C=Bulk create from the CSV: this creates brand-new accounts with new IDs and none of the old properties, while the deleted accounts can still simply be restored.
D=New object IDs: a restore brings the same account back with all its properties; that is the reason to restore rather than recreate.
E=Seven-day limit: the window is 30 days and administrators restore users themselves; after permanent deletion even Microsoft Support can't restore them.
T: Deleted users stay restorable for 30 days with all their properties (Bulk restore takes object IDs), and their licenses come back even beyond the purchased count.
V: Microsoft Entra ID

Some Microsoft services aren't available in every country or region. Before a license can be assigned to a user, Microsoft needs the user's **usage location**, a two-letter country or region code such as `DE` or `US`.

C=Owner's location: the fallback documented by Microsoft is the tenant's location, not the location of a group owner.
D=No location, nearest datacenter: a license is never applied without a location; the user simply inherits the tenant's location.
T: Direct license assignment needs the user's usage location; group-based licensing falls back to the tenant location, so set the correct location when creating users.

@ AZ-104 D1 T1.1 applied troubleshooting
S: The group LIC-E5 assigns Microsoft 365 E5. After HR added 25 new hires to it, the group shows a licensing error and eight of the new members have no E5 license. The error says there aren't enough licenses for the product. Which TWO actions resolve the problem? (Select TWO)
A: Buy additional E5 licenses for the subscription, and then reprocess the affected users in the group
B: Remove E5 licenses that are assigned directly to users who also get E5 through a group, and then reprocess
C: Set the usage location on the eight users, because the error is shown whenever a member has no location

E: Convert LIC-E5 to dynamic membership, because only dynamic groups can wait for licenses to become free
K: A,B
G: ## How group-based licensing reports errors
With group-based licensing, licenses are applied in the background as members join. If a license can't be applied, the failure is recorded on the user and shown on the group (a notification lists the users in an error state) and in the admin center's **Errors & issues** view, instead of failing immediately like a direct assignment.
## The "Not enough licenses" error
The group's product has no free licenses left for the extra members. Microsoft's fixes are:
- **buy more licenses** for that product
- **remove unused direct assignments**, for example users who have E5 both directly and through a group
- **free licenses** from other groups or users that no longer need them
After fixing the cause, select **Reprocess** for the affected users or group so the assignment is attempted again with the licenses now available.
## Errors that clear by themselves
`LicenseAssignmentAttributeConcurrencyException` in the audit logs comes from several groups assigning the same license at once; it is retried automatically. A shortage of licenses is not like that: nothing changes until licenses are freed or bought.
W: A=Buy more licenses: adding E5 seats to the subscription gives the eight users licenses to take; reprocessing then applies them.
B=Remove redundant direct assignments: a user with both a direct and a group E5 assignment frees a seat when the direct one is removed, which can cover the shortfall without buying more.
X: C=Set usage location: a missing usage location produces a different error, and for group licensing users without one inherit the tenant's location.
D=Reprocess only: reprocessing retries with the same number of licenses, so the eight users fail again; it helps only after the shortage has been fixed.
E=Convert to dynamic: membership type doesn't change how many licenses exist; a dynamic group runs into the same shortage.
T: "Not enough licenses" in group-based licensing is fixed by buying or freeing licenses (such as redundant direct assignments) and then reprocessing.

Each license (product) contains **service plans**, for example Exchange Online (Plan 1) in E1 and Exchange Online (Plan 2) in E3. Some plans can't be assigned to the same user together. - remove the redundant **direct** license (here E1, since E3 includes a higher Exchange plan)
- disable one of the conflicting service plans in one of the assignments
- adjust the group license assignment

K: A
G: ## External collaboration settings
In the Microsoft Entra admin center, **External Identities > External collaboration settings** groups several separate controls:
- **Guest user access**: what guests can see in the directory.
- **Guest invite settings**: **who** in your organization may send invitations.
- **Collaboration restrictions**: **which domains** invitations may be sent to.
## Allow list or block list
Collaboration restrictions work with either an allow list or a block list, never both:
- **Deny invitations to the specified domains**: everything is allowed except the listed domains (common for blocking `gmail.com`, `outlook.com`).
- **Allow invitations only to the specified domains (most restrictive)**: only the listed domains can be invited; every other domain is blocked.
The default is to allow invitations to any domain. Domains are entered one per line, and an invitation to a blocked domain fails with a blocked-domain message.

K: A
G: ## How SSPR checks a user
When someone starts a reset at `https://aka.ms/sspr`, Microsoft Entra checks that the user is enabled for SSPR and that they have registered **at least as many methods as the policy requires**, out of the methods the administrator enabled. If not, the user is told to contact their administrator.
## Changing the required number
Microsoft documents the effect of raising the requirement from one method to two:
- 1 or more methods registered, 1 required: able to reset
- **1 method registered, 2 required: unable to reset**
- 2 or more registered, 2 required: able to reset
Changing **which** methods are allowed has a similar effect: users whose only registered method was removed from the policy can no longer reset.
## Fix
Ask affected users to register a second method (for example at `https://aka.ms/ssprsetup`), and use the registration settings to prompt users at sign-in. Plan the change and tell users before raising the requirement.

X: B=Registration reset: changing the number of required methods doesn't erase registrations; users with two or more methods can still reset.
C=Admins only: the number of methods applies to the users in scope; administrators have a separate fixed two-gate policy, so standard users are not excluded.
D=Synced users disabled: the number of methods has nothing to do with on-premises passwords; synced users depend on password writeback instead.
T: Raising SSPR's required methods from one to two blocks users who registered only one method until they add another.
