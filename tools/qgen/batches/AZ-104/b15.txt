# AZ-104 D5 T5.2 Implement backup and recovery: vaults, vault settings, policies, restores, Azure Site Recovery, alerts and reports

@ AZ-104 D5 T5.2 applied comparison
S: A small engineering firm already backs up its Azure VMs, its SQL Server databases on Azure VMs and its Azure Files shares. It now wants Azure Backup to protect two more workloads, and an administrator must decide which ones need a Backup vault instead of the existing Recovery Services vault. Which TWO workloads are protected in a Backup vault? (Select TWO)
A: Azure managed disks that need agentless, crash-consistent snapshots several times a day
B: Block blobs in a storage account that need operational and vaulted backups together
C: An Azure Files share whose snapshots and vaulted copies follow a daily backup policy
D: A SQL Server database on an Azure VM that needs log backups every 15 minutes
E: A Windows Server Azure VM that needs daily application-consistent backups
K: A,B
G: ## Two kinds of vault in Azure Backup
Azure Backup keeps recovery points and backup policies in a **vault**, and there are two vault types. Which one you create depends on the workload, not on your preference.
- **Recovery Services vault**: the original vault. It protects Azure VMs (Windows or Linux), SQL Server and SAP HANA databases running in Azure VMs, Azure Files shares, and on-premises servers through the MARS agent, Azure Backup Server or System Center DPM. Azure Site Recovery also uses this vault type.
- **Backup vault**: the vault for the newer workloads. It protects Azure managed disks (Azure Disk Backup), Azure Blobs, Azure Database for PostgreSQL, Azure Kubernetes Service and other recently added data sources.
The two vaults have separate backup policies and separate protected items; you cannot point a managed disk backup at a Recovery Services vault.
## Example
An administrator who wants hourly snapshots of one data disk creates a Backup vault, a disk backup policy with an hourly schedule, and a backup instance for that disk. The VM itself can stay protected by its daily VM backup in the Recovery Services vault: Microsoft documents this side-by-side use.
W: A=Azure managed disks: Azure Disk Backup is configured in a Backup vault. It is agentless, crash-consistent, uses incremental snapshots and supports hourly schedules.
B=Azure Blobs: blob backup (operational, vaulted or both under one policy) creates a backup instance for the storage account in a Backup vault.
X: C=Azure Files share: Azure Files backup is configured from a Recovery Services vault, which discovers the storage account and registers its shares, so the existing vault already fits.
D=SQL Server in an Azure VM: the stream-based SQL Server workload backup, including 15-minute log backups, runs in a Recovery Services vault through the AzureBackupWindowsWorkload extension.
E=Azure VM: full VM backup with application-consistent recovery points is the classic Recovery Services vault workload; a Backup vault cannot protect a whole VM.
T: Recovery Services vault: VMs, SQL/SAP HANA in VMs, Azure Files and on-premises agents (and Site Recovery). Backup vault: managed disks, blobs, PostgreSQL, AKS and other newer workloads.
V: Azure Backup, Recovery Services vault, Backup vault

@ AZ-104 D5 T5.2 applied troubleshooting
S: An administrator created a Recovery Services vault with default settings and enabled backup for four development VMs. A week later, finance asks for locally redundant storage to reduce cost, but the Storage replication type setting in the vault's Backup Configuration cannot be changed. The existing development backups do not need to be kept. What should the administrator do?
A: Stop protection and delete the backup data in this vault, then configure backup for the VMs in a new vault set to LRS
B: Turn off Cross Region Restore in the vault properties first, which unlocks the Storage replication type setting again
C: Change the redundancy of the storage account that holds the vault's backup data from GRS to LRS on its Configuration page
D: Wait until the soft-delete retention period of the first backups ends, after which the replication type can be edited
K: A
G: ## Vault storage redundancy is chosen once
Azure Backup stores vault data for you; you never see or manage a storage account. You only choose how the vault replicates it:
- **Geo-redundant (GRS)**: the default; copies data to the paired region. Required for Cross Region Restore.
- **Locally redundant (LRS)**: cheaper, three copies in one datacenter.
- **Zone-redundant (ZRS)**: copies across availability zones in one region, useful for data residency.
Microsoft's guidance is to review this setting **before** you configure the first backup: once a backup is configured in the vault, the option to change it is disabled.
## Moving to LRS afterwards
The documented workaround is to protect the workloads in a new vault that uses LRS:
- If old backups are not needed: stop protection and delete the backup data in the GRS vault, then configure backup in the LRS vault.
- If old backups must be kept: stop protection with retained data. A VM can be in only one vault at a time, so the documented path moves the VM to another resource group before protecting it in the LRS vault.
W: New LRS vault: because the replication type is locked after the first backup is configured, the supported way is to remove protection (and the unneeded data) from the GRS vault and start fresh backups in a vault created with LRS.
X: B=Turn off Cross Region Restore: Cross Region Restore cannot be reverted after protection starts, and even without it the replication type stays locked once any backup has been configured.
C=Change the storage account: the vault's backup data sits in storage that Azure Backup manages in a Microsoft-managed subscription, so there is no storage account of yours to reconfigure.
D=Wait for soft-delete retention: soft delete only governs how long deleted backup data stays recoverable; it has nothing to do with unlocking the vault's replication type.
T: Set the Recovery Services vault's storage redundancy before the first backup; afterwards the only way to change it is to protect the items in a new vault.
V: Recovery Services vault, Azure Backup

@ AZ-104 D5 T5.2 applied use-case
S: An auditor requires a retail company to prove twice a year that its production VMs can be restored from Azure Backup recovery points in the Azure paired region, at a time the company chooses. Its Recovery Services vault uses the default geo-redundant storage. What should the administrator configure on the vault?
A: Enable Cross Region Restore, then restore from the secondary-region items in Backup items to create a VM or disks in the paired region
B: Keep plain geo-redundant storage, because recovery points replicated to the paired region can be restored there whenever needed
C: Switch the vault to zone-redundant storage and use Cross Zonal Restore to restore the VMs into the zones of the paired region
D: Enable Cross Subscription Restore so that the vault can restore recovery points into a subscription linked to the paired region
K: A
G: ## Geo-redundant backups and when you can use them
With geo-redundant storage (GRS), the vault replicates backup data to the Azure paired region. That copy protects you from a regional outage, but on its own you **cannot restore from it whenever you like**: secondary-region data becomes available only when Microsoft declares an outage in the primary region.
## Cross Region Restore (CRR)
CRR is a vault property (Properties > Backup Configuration) that makes the secondary-region copy restorable **at any time**, for drills, audits or a real outage.
- Supported only on vaults that use GRS; it adds cost, and after enabling it items can take up to 48 hours to appear in the secondary region.
- Once protection has started, CRR cannot be reverted to plain GRS or LRS.
- For Azure VMs you can **create a VM** or **restore disks** in the secondary region; replacing existing disks is not supported there.
- Only vault-tier data is replicated (snapshots are not), so secondary-region restores are vault-tier restores; the secondary RPO for VM backups can be up to 36 hours in the worst case.
## Example
After enabling CRR, the administrator opens Backup items, selects **Secondary Region**, picks a VM and restores it as a new VM in the paired region for the audit.
W: Cross Region Restore: it is designed exactly for restoring in the paired region on demand, including compliance drills, without waiting for an outage declaration.
X: B=Plain GRS: the replicated data is there, but without CRR it can be restored only after Microsoft declares a disaster in the primary region, so a planned drill is impossible.
C=ZRS with Cross Zonal Restore: zone-redundant storage keeps all backup data in the primary region, so there is no paired-region copy to restore from; Cross Zonal Restore only changes the target availability zone.
D=Cross Subscription Restore: this restores to a different subscription in the same tenant; it does not make paired-region data available, and subscriptions are not tied to regions.
T: GRS alone gives secondary-region data only after a declared outage; Cross Region Restore on a GRS vault lets you restore in the paired region whenever you choose.
V: Azure Backup, Recovery Services vault, Cross Region Restore

@ AZ-104 D5 T5.2 applied troubleshooting
S: On a Monday, a help desk technician at a design studio selected Stop backup with Delete backup data for an Azure VM by mistake. On Friday, the administrator finds the item in the Recovery Services vault in a soft-deleted state; the vault uses the default soft-delete settings. How can the administrator get the recovery points back?
A: Undelete the soft-deleted backup item, which returns it to Stop protection with retain data, then restore or resume backup
B: Configure backup for the VM again in the same vault, and the soft-deleted recovery points attach to the new item automatically
C: Restore the VM from the secondary region with Cross Region Restore, because the deletion does not reach the paired-region copy
D: Nothing can be recovered, because soft delete keeps only the vault itself and not the recovery points of deleted backup items
K: A
G: ## Soft delete for backup data
Soft delete protects backups from accidental or malicious deletion. When someone stops protection and deletes backup data, the data is not purged at once: the item moves to a **soft-deleted** state and is kept for the soft-delete retention period.
- Default retention: **14 days**, at no extra cost. You can extend it up to 180 days; days beyond 14 are charged at normal backup rates.
- Soft delete is now enabled by default on new vaults and, where secure-by-default is generally available (all public regions for Recovery Services vaults), it cannot be turned off.
- Soft delete also covers recovery points lost by lowering a policy's retention.
## Getting the data back
Select the soft-deleted item and choose **Undelete**. The item returns to **Stop protection with retain data**; from there you can restore any recovery point or resume backups. Azure Backup does not let you configure backup again for an item that is still soft-deleted in the same vault.
## Example
Deleted on Monday, noticed on Friday: four days have passed, well inside the 14-day window, so undelete restores every recovery point.
W: Undelete: within the soft-delete retention period the item and all its recovery points can be undeleted, which puts the item back in Stop protection with retain data, ready for restore or resumed backups.
X: B=Reconfigure in the same vault: Azure Backup does not allow configuring backup for an item that is in a soft-deleted state in the same vault; the item must be undeleted (or protected in a different vault).
C=Cross Region Restore: nothing in the stem says CRR is enabled, and a soft-deleted item has to be undeleted before its data can be used for any restore, so undelete is the documented recovery path.
D=Nothing recoverable: soft delete exists precisely to keep deleted backup items and their recovery points for the retention period (14 days by default).
T: A deleted backup item stays soft-deleted for 14 days by default; undelete it to return to Stop protection with retain data, then restore or resume backups.
V: Azure Backup, Recovery Services vault

@ AZ-104 D5 T5.2 advanced use-case
S: After a ransomware incident at a partner, a logistics company wants its Recovery Services vault protected so that nobody, including administrators with Owner rights, can delete recovery points before they expire or lower policy retention, and so that this protection itself can never be switched off later. What should the administrator configure?
A: Enable immutability on the vault and then lock it, so that the immutable vault setting is enabled and locked and becomes irreversible
B: Enable immutability on the vault and leave it unlocked, so that the vault blocks the operations while the setting stays enabled
C: Extend the soft-delete retention of the vault to 180 days, so that any deleted recovery point can be restored for half a year
D: Enable Cross Region Restore on the vault, so that a second copy of every recovery point can always be restored in the paired region
K: A
G: ## Immutable vaults
An immutable vault blocks operations that could lose recovery points. For a Recovery Services vault these include:
- stopping protection **with deletion** of data (stopping with retained data is still allowed),
- modifying a backup policy to **reduce** retention,
- assigning an item a different policy with **lower** retention.
Increasing retention and changing the schedule remain possible. Immutability applies to all the data in the vault.
## Three states
- **Disabled**: nothing is blocked.
- **Enabled**: the operations are blocked, but anyone with the right permissions can disable immutability again.
- **Enabled and locked**: the setting can no longer be disabled; locking is irreversible (and enables WORM storage where supported).
Microsoft recommends testing with the enabled state first and locking once you are sure, because the lock cannot be undone.
W: Enabled and locked immutability: it blocks early deletion and retention reductions for everyone, and locking makes the setting irreversible, so a compromised Owner account cannot turn it off.
X: B=Enabled but unlocked: the protection works, but the setting is reversible, so an attacker or Owner could disable immutability first and then delete backups, which breaks the "never switched off" requirement.
C=180-day soft delete: soft delete lets you recover data after it is deleted; it does not stop the deletion or prevent someone from shortening policy retention.
D=Cross Region Restore: CRR makes the paired-region copy restorable; it does not block deleting recovery points or reducing retention.
T: To stop anyone from deleting or shortening backups and to make that guarantee permanent, enable vault immutability and lock it.
V: Azure Backup, Recovery Services vault

@ AZ-104 D5 T5.2 applied use-case
S: A payroll application runs on an Azure VM whose data disk is Premium SSD v2. The business requires application-consistent recovery points of the whole VM at least every four hours, and restores of the full VM from the Recovery Services vault. Which backup configuration meets the requirement?
A: An Enhanced VM backup policy with an Hourly schedule set to run every 4 hours across a 24-hour window
B: A Standard VM backup policy with a Daily schedule plus three on-demand backups that are triggered each day
C: An Azure Disk Backup policy in a Backup vault with an hourly frequency of 4 hours for each of the VM's disks
D: A Standard VM backup policy with a Weekly schedule, Instant Restore set to five days and daily retention
K: A
G: ## Standard and Enhanced VM backup policies
Azure VM backup policies in a Recovery Services vault come in two types:
- **Standard policy**: one scheduled backup per day (daily or weekly schedules). Instant Restore snapshots kept 1 to 5 days. It does not protect newer offerings such as **Premium SSD v2** and **Ultra Disks**.
- **Enhanced policy**: adds an **Hourly** schedule with backups every 4, 6, 8, 12 or 24 hours, Instant Restore snapshots kept up to 30 days, zone-redundant snapshots, and support for Trusted Launch VMs, Premium SSD v2 and Ultra Disks.
Once a VM is protected with an Enhanced policy you cannot switch it back to a Standard policy.
## Example
A policy with subtype **Enhanced**, frequency **Hourly**, start 8:00 AM, every 4 hours, duration 24 hours creates six recovery points a day. The snapshots give fast instant restores; the daily transfer to the vault gives long-term retention.
W: Enhanced policy, hourly every 4 hours: it is the only VM policy that supports both multiple scheduled backups per day and VMs with Premium SSD v2 disks, while still producing full-VM recovery points.
X: B=Standard policy with on-demand backups: the Standard policy does not support Premium SSD v2 disks, and hand-triggered extra backups are not a schedule that guarantees the four-hour objective.
C=Azure Disk Backup: disk backups are crash-consistent snapshots of individual disks, so they meet neither the application-consistency requirement nor full-VM restore.
D=Standard weekly policy: one backup a week misses the four-hour objective by far, and the Standard policy still cannot protect a Premium SSD v2 disk.
T: Several VM backups per day, or Premium SSD v2, Ultra Disk and Trusted Launch VMs, require the Enhanced backup policy.
V: Azure Backup, Recovery Services vault

@ AZ-104 D5 T5.2 applied use-case
S: A faulty update leaves a Windows Server Azure VM at a marketing agency unable to boot. The VM uses unencrypted managed disks and is backed up daily to a Recovery Services vault. The administrator wants the same VM, with its existing name, network interface and configuration, rolled back to last night's recovery point. Which restore option should be used?
A: Replace existing, which swaps the VM's disks for the disks from the selected restore point and keeps the VM object
B: Create new virtual machine, which builds a VM from the restore point that keeps the original name and settings
C: Restore disks, which attaches the restored disks to the existing VM automatically when the restore job finishes
D: File Recovery, which mounts the recovery point and lets the administrator copy back the whole operating system
K: A
G: ## VM restore options in Azure Backup
From a VM recovery point you can choose:
- **Create new virtual machine**: quickly builds a basic VM. You give it a name that does not already exist, a resource group and a VNet; it must be in the same region as the source.
- **Restore disks**: creates managed disks (and a generated ARM template) in a resource group you choose. You then deploy a customised VM from the template, attach the disks to a VM yourself, or use PowerShell.
- **Replace existing**: restores disks and swaps them onto the **existing** VM. The VM must still exist. Azure Backup first takes a snapshot of the current VM, and the replaced original disks stay in the resource group until you delete them. Supported for unencrypted managed VMs; not for generalized VMs.
- **File Recovery**: mounts a recovery point as drives so you can copy individual files and folders.
## Example
The VM `web01` is still there but will not boot. Replace existing keeps `web01`, its NIC, IP configuration and extensions, and only swaps the disks back to last night's state.
W: Replace existing: it keeps the VM resource and its configuration and only replaces the disks with those from the chosen recovery point, which is exactly an in-place rollback.
X: B=Create new virtual machine: this option needs a VM name that does not exist in the subscription and creates a separate VM with its own new NIC, so it does not roll back the existing VM.
C=Restore disks: the disks are created in a resource group, but nothing attaches them for you; you would have to swap the disks or deploy the template yourself.
D=File Recovery: it is meant for individual files and folders through mounted volumes, not for rebuilding a bootable operating system disk.
T: To roll back an existing VM in place, use Replace existing; it keeps the VM and swaps its disks for the recovery point's disks.
V: Azure Backup, Azure Virtual Machines

@ AZ-104 D5 T5.2 advanced use-case
S: A VM at an accounting firm was deleted by mistake, but its daily backups remain in the Recovery Services vault. The administrator must bring it back with a different VM size and extra settings that the quick-create restore does not offer, using the portal's restore experience. Which approach should be used?
A: Restore disks to a resource group, then open the restore job and use Deploy Template to edit the generated template and create the VM
B: Replace existing, choosing the same VM name so that Azure Backup recreates the deleted VM and applies the new size during restore
C: Create new virtual machine, then pick the new size and the extra settings on the restore pane before the job is submitted
D: File Recovery on the latest recovery point, then copy the mounted volumes onto a new VM that was created with the new size
K: A
G: ## When Create new VM is not enough
**Create new virtual machine** restores with basic settings only: name, resource group, VNet and subnet, staging location, subscription and zone. The restored VM keeps the **SKU (size) it had at the recovery point**.
**Restore disks** is for customisation. The restore job creates the managed disks in a resource group and generates an ARM template. Then:
1. Open the restore job (vault > Backup Jobs, or Resiliency > Jobs).
2. Select **Deploy Template**, then **Edit template** or **Edit parameters** to change the size, availability settings, tags and other properties.
3. Deploy, and the new VM is built from the restored disks.
You can also attach the restored disks to another VM or build a VM with PowerShell.
## Why not Replace existing
Replace existing works only while the original VM still exists; a deleted VM cannot have its disks replaced.
W: Restore disks plus the generated template: the restore creates the disks and an editable ARM template, so the administrator can set a different size and any settings before deploying the new VM.
X: B=Replace existing: the current VM must exist for this option, so it cannot be used after the VM was deleted, and it never changes the VM size.
C=Create new virtual machine: this quick restore offers only basic settings, and the restored VM keeps the size it had when the recovery point was taken.
D=File Recovery: it gives read-only access to files and folders for copying; it is not a way to rebuild a bootable VM from its disks.
T: Restore disks when you need a customised VM: deploy it from the template that the restore job generates.
V: Azure Backup, Azure Resource Manager templates

@ AZ-104 D5 T5.2 advanced troubleshooting
S: To recover one folder from an Azure VM backup, an administrator downloads the File Recovery executable and runs it on an on-premises Windows 11 workstation with a compatible OS. The script cannot connect to the recovery point. The corporate firewall allows outbound traffic only on TCP 443 through a web proxy. What should be changed?
A: Allow the workstation direct outbound TCP 3260 to the vault region's recovery service URL or AzureBackup tag
B: Allow inbound TCP 3389 from the vault region's recovery service to the workstation so that the session can attach
C: Run the executable on a VM in the same virtual network as the vault, because recovery points are reached privately
D: Choose an Instant Restore snapshot recovery point, because File Recovery cannot open recovery points in the vault tier
K: A
G: ## How File Recovery works
File Recovery (item-level recovery) does not copy a whole disk. In the VM's **Backup > File Recovery** pane you pick a recovery point and download a password-protected executable (Windows) or Python script (Linux). When you run it, it connects to the recovery point over **iSCSI** and mounts its volumes as local drives, read-only, so you can copy files out. The connection is valid for 12 hours; afterwards select **Unmount Disks**.
## Network requirements of the machine running the script
- Outbound **443** to `download.microsoft.com` (or the AzureFrontDoor.FirstParty service tag) for components.
- Outbound **3260** (iSCSI) to the recovery service URL of the vault's region, such as `https://pod01-rec2.<geo-name>.backup.windowsazure.com`, or the **AzureBackup** service tag in an NSG.
- Outbound 53 for public DNS and 443 to the Microsoft Entra ID endpoints.
Microsoft notes that proxies may not support iSCSI or port 3260 and strongly recommends running the script on a machine with direct access.
W: Outbound 3260 to the recovery service: the mount is an iSCSI session on port 3260, which a 443-only proxy blocks, so the workstation needs direct outbound access to the regional recovery URL or the AzureBackup tag.
X: B=Inbound 3389: the script opens outbound connections only; RDP into the workstation plays no part in mounting a recovery point.
C=Same virtual network as the vault: a vault is not deployed into a VNet; the script can run on any machine, in Azure or on-premises, that meets the OS and outbound access requirements.
D=Only snapshot recovery points: File Recovery works from vault recovery points too; the failure is the blocked iSCSI port, not the recovery point's tier.
T: File Recovery mounts recovery points over iSCSI: the machine running the script needs direct outbound TCP 3260 to the vault region's recovery service.
V: Azure Backup

@ AZ-104 D5 T5.2 applied tradeoff
S: A law firm backs up an Azure Files share with a Recovery Services vault policy that keeps snapshots for 30 days. A risk review asks that backups survive even if an attacker deletes the entire storage account that hosts the share. What should the administrator change?
A: Switch the share to a policy with the Vault-Standard tier, so backup data is also copied into the vault outside the account
B: Keep the snapshot policy and raise its retention to one year, so that older snapshots outlive any deletion of the account
C: Set the vault's storage replication type to geo-redundant, so that the share's snapshots are copied to the paired region
D: Enable soft delete for file shares on the storage account, so that a deleted share and its snapshots come back in 14 days
K: A
G: ## Two backup tiers for Azure Files
Azure Files backup is configured in a Recovery Services vault and offers two tiers in the backup policy:
- **Snapshot tier**: Azure Backup takes share snapshots with the File Share API. The snapshots live **in the same storage account** as the share; the vault holds only metadata. Restores are fast, but if the storage account is deleted the snapshots go with it.
- **Vault-Standard tier (vaulted backup)**: after each snapshot, changed data is copied **into the vault**, an offsite copy isolated from the source account. It gives protection "irrespective of the severity or blast radius", long-term retention and cross-region recovery.
## Notes
- The vault's storage redundancy setting does not apply to snapshot-tier backups, because nothing is stored in the vault; it applies only to vaulted backups.
- Vaulted backup currently restores only full shares; item-level restore comes from snapshots.
W: Vault-Standard tier: copying the backup data into the vault keeps recovery points outside the storage account, so they survive the deletion of that account.
X: B=Longer snapshot retention: snapshots are stored inside the same storage account, so deleting the account removes them however long their retention is.
C=Geo-redundant vault: the vault's replication setting is irrelevant for snapshot-tier backups, because the snapshots stay in the storage account and are never copied into the vault.
D=File share soft delete: it can bring back a deleted share for a period, but it is a setting of the storage account, so it does not help when the whole account is deleted.
T: Snapshot-tier Azure Files backups live in the source storage account; to survive account deletion, use the Vault-Standard (vaulted) tier.
V: Azure Backup, Azure Files

@ AZ-104 D5 T5.2 advanced troubleshooting
S: While configuring Azure Disk Backup for three data disks in a Backup vault, an administrator sees "Role assignment not done" in the Backup readiness column. The vault uses its system-assigned managed identity. Which TWO role assignments fix the error? (Select TWO)
A: Disk Backup Reader for the vault's managed identity on each source disk that is being backed up
B: Disk Snapshot Contributor for the vault's managed identity on the snapshot resource group selected
C: Backup Contributor for the administrator's own account on the Backup vault that holds the policy
D: Storage Account Backup Contributor for the vault's managed identity on each of the source disks
E: Virtual Machine Contributor for the vault's managed identity on the VM that the disks attach to
K: A,B
G: ## How Azure Disk Backup accesses your resources
Azure Disk Backup is agentless: the **Backup vault's managed identity** creates incremental snapshots of each managed disk and stores them in a **snapshot resource group** in your subscription. Because the vault acts through its identity, that identity needs Azure RBAC roles on:
- the **source disk**: the **Disk Backup Reader** role,
- the **snapshot resource group**: the **Disk Snapshot Contributor** role, so it can create, store and delete snapshots,
- at restore time, the **target resource group**: the **Disk Restore Operator** role (Microsoft suggests revoking it after the restore).
If these are missing, the configure-backup wizard shows **Role assignment not done** in the Backup readiness column; you can grant them there if you have permission, then revalidate.
## Example
`disk-data01` in `rg-app` and snapshots in `rg-snapshots`: assign Disk Backup Reader on `disk-data01` and Disk Snapshot Contributor on `rg-snapshots` to the vault's identity. The snapshot resource group cannot be changed after backup is configured.
W: A=Disk Backup Reader on the disk: the vault's identity needs this role on each source disk to read it and take its snapshots.
B=Disk Snapshot Contributor on the snapshot resource group: the identity needs this role to create and manage the incremental snapshots in that group.
X: C=Backup Contributor for the admin: the message is about the vault's managed identity, not the signed-in user, so giving the administrator more rights on the vault does not change the readiness check.
D=Storage Account Backup Contributor: this role lets a Backup vault protect blobs in a storage account; it grants nothing on managed disks.
E=Virtual Machine Contributor: disk backup works on the disks themselves, attached or not, and does not use VM permissions.
T: Azure Disk Backup needs the vault's managed identity to have Disk Backup Reader on the disks and Disk Snapshot Contributor on the snapshot resource group.
V: Azure Backup, Backup vault, Azure managed disks

@ AZ-104 D5 T5.2 applied troubleshooting
S: A hospital's Azure VMs run in East US and are backed up to a Recovery Services vault in East US. The administrator now wants Azure Site Recovery to replicate the VMs to West US, but the existing vault cannot be used to enable replication for these VMs. Where should the vault for Site Recovery be created?
A: A new Recovery Services vault in any supported region except East US, for example West US, the target region
B: A new Backup vault in West US, because Site Recovery for Azure VMs needs the newer vault type and its identity
C: A second Recovery Services vault in East US, because a vault can hold either backup items or replicated items only
D: A new Recovery Services vault in the same resource group as the VMs, because the vault must share their resource group
K: A
G: ## Where the vault goes: Backup versus Site Recovery
Both Azure Backup for VMs and Azure Site Recovery use a **Recovery Services vault**, but they place it differently:
- **Azure Backup**: the vault must be in the **same region** as the VM it protects. VMs in two regions need two vaults.
- **Azure Site Recovery (Azure to Azure)**: the vault can be in **any supported region except the source region** of the VMs. The usual choice is the target region, so that the vault and its recovery data remain usable when the source region is down.
## Setting up Azure VM disaster recovery
1. Create a Recovery Services vault outside the source region.
2. In the vault, select Enable Site Recovery, choose the source region and VMs, and the target region.
3. Site Recovery installs the Mobility service extension on each VM. Disk writes go to a cache storage account in the source region and are replicated to the target region, where recovery points are created.
W: Vault outside the source region: Site Recovery requires the Recovery Services vault to be in a different region from the replicated VMs, so a vault in West US (or another non-source region) works.
X: B=Backup vault: Site Recovery uses Recovery Services vaults; Backup vaults hold newer Azure Backup workloads such as disks and blobs and cannot replicate VMs.
C=Second vault in East US: a vault in the source region cannot be used for those VMs' disaster recovery; the problem is the region, not a split between backup and replication items.
D=Same resource group as the VMs: a vault's resource group is your choice and does not need to match the VMs; the region is what blocks the existing vault.
T: Azure Backup puts the vault in the VM's region; Azure Site Recovery needs the vault in a region other than the VMs' source region.

@ AZ-104 D5 T5.2 applied use-case
S: An insurer replicates its claims VMs from North Europe to West Europe with Azure Site Recovery. For the quarterly disaster recovery drill, the VMs must be started in West Europe and checked, while production in North Europe keeps running and replication continues. What should the administrator do?
A: Run Test Failover into an isolated non-production VNet in West Europe, check the VMs, then run Cleanup test failover
B: Run Failover with Shut down machine before beginning failover selected, check the VMs, and then select Commit at the end
C: Run Re-protect on the VMs so that they replicate from West Europe back to North Europe, and then run a full Failover
D: Run Failover to the Latest recovery point into the VNet created at enablement, then cancel the job once VMs have started
K: A
G: ## Test failover is the drill
Azure Site Recovery has two very different operations:
- **Failover**: the real thing. VMs are created in the target region from a recovery point; you can ask Site Recovery to shut down the source VMs first. After checking, you **Commit**, which deletes the other recovery points.
- **Test failover**: a disaster recovery drill. It creates VMs in the target region from a recovery point **without affecting production or ongoing replication**.
## Running a drill
1. On the replicated item (or a recovery plan), select **Test Failover** and choose a recovery point (Latest processed gives a low RTO).
2. Choose a target VNet. Microsoft recommends a **non-production network**, not the network created when replication was enabled, so IP addresses and production network components are not disturbed.
3. Check the test VMs.
4. Select **Cleanup test failover**, record notes and select Testing is complete; the test VMs are deleted.
Microsoft suggests running a test failover for each app every quarter.
W: Test Failover then cleanup: a test failover brings up copies of the VMs in the target region while production and replication carry on, and cleanup removes the test VMs afterwards.
X: B=Failover with shutdown and commit: this is a real failover that shuts down the source VMs and commits to the target region, which stops production in North Europe.
C=Re-protect then fail over: re-protect is only possible after a committed failover and reverses replication; it is a failback step, not a drill.
D=Failover into the production VNet: a real failover is not a drill, and using the network created at enablement can clash with the IP addresses and components meant for a real disaster.
T: Disaster recovery drills use Test Failover into an isolated network, followed by Cleanup test failover; production and replication keep running.

@ AZ-104 D5 T5.2 advanced use-case
S: After a regional outage, an administrator failed a manufacturing company's VMs over from UK South to UK West with Azure Site Recovery and committed the failover. UK South is healthy again, and the business wants the VMs to run in UK South once more. What must the administrator do first?
A: Re-protect the VMs from UK West so that they replicate back to UK South, and fail them over to UK South after that
B: Start the original VMs in UK South again, because Site Recovery kept them up to date in the background after failover
C: Run Test Failover from UK West to UK South, which copies the changed data back and then switches users to UK South
D: Disable replication for the VMs and enable it again from UK South, so that a fresh initial copy is sent from scratch
K: A
G: ## Failover and failback in Azure Site Recovery
After a failover, the VMs run in the secondary region in an **unprotected** state: nothing replicates them anywhere. To return home you go through two more steps.
1. **Commit** the failover (status Failover committed).
2. **Re-protect**: on the replicated item, select Re-Protect. The direction is now secondary to primary. If the original VM and disks still exist, Site Recovery compares them and sends only the differences, then keeps replicating deltas.
3. **Fail over** again, this time from the secondary to the primary region (failback). Run a test failover first if you can.
4. **Re-protect** once more so that the VMs replicate from the primary to the secondary region again.
## A detail worth knowing
After re-protecting in the secondary region, Site Recovery puts a **read-only lock** on the source machine in the primary region so that it is not deleted while it receives replication; the lock stays until failback completes.
W: Re-protect, then fail over: re-protection reverses replication so changes made in UK West reach UK South, and only then can a failover return the VMs to the primary region without losing data.
X: B=Start the original VMs: the source VMs were not kept up to date after failover, so starting them would bring back stale data and abandon the changes made in UK West.
C=Test Failover back: test failover creates throwaway VMs for a drill and does not reverse replication or move production; the failed-over VMs first need to be re-protected.
D=Disable and re-enable replication: Site Recovery supports re-protect, which reuses the existing VM data and transfers only differences; starting over discards that and is needed only when the source data is gone.
T: To fail back, commit the failover, re-protect so the VMs replicate to the primary region, then fail over again and re-protect once more.

@ AZ-104 D5 T5.2 applied use-case
S: A three-tier ticketing app replicates to a secondary region with Azure Site Recovery. During a failover, the database VM must start first, then the app servers, then the web servers, and after the web tier starts a public IP must be attached automatically. What should the administrator configure?
A: A recovery plan with three ordered groups for the tiers and an Azure Automation runbook action after the web servers group
B: A replication group with multi-VM consistency for all of the VMs, so that they fail over in dependency order with one IP
C: An availability set in the target region for each tier, so that Azure starts the sets one after another after failover
D: A backup policy for each tier in the vault, with start times one hour apart so that the restores run in the needed order
K: A
G: ## Recovery plans
A **recovery plan** groups replicated machines into units that fail over together, usually one app. It controls:
- **Order**: machines in the same group fail over in parallel; group 2 starts only after every machine in group 1 has failed over and started. A typical three-tier app puts the database in group 1, middleware in group 2 and the web front end in group 3.
- **Automation**: you can add Azure Automation runbooks or scripts before or after a group, for example to create a public IP or assign an NSG to the failed-over VM, and manual actions (pauses) for steps that cannot be automated.
- **Testing**: you can run a test failover on the whole plan.
A plan holds up to 100 protected instances, and with a recovery plan you choose from Latest processed, Latest or Latest app-consistent recovery points (Custom works only for a single VM).
W: Recovery plan with ordered groups and a runbook: groups give the database-app-web start order, and a post-group runbook automates the public IP step, which is exactly what recovery plans are for.
X: B=Multi-VM consistency: a replication group gives VMs shared crash-consistent and app-consistent recovery points; it does not set a start order or run post-failover tasks.
C=Availability sets: they spread VMs across fault and update domains for availability; they have no role in the order in which Site Recovery starts VMs.
D=Staggered backup policies: backup policies schedule Azure Backup jobs, not Site Recovery failover, and restore jobs would not give a coordinated failover.
T: Use a Site Recovery recovery plan to order failover by tier and to add runbook or manual steps around each group.

@ AZ-104 D5 T5.2 applied use-case
S: An IT team wants an email whenever a scheduled VM backup or a restore job fails in any of its Recovery Services vaults. It does not want to send data to a Log Analytics workspace or write queries, and it no longer uses the classic backup alerts. What should the administrator configure?
A: Keep the built-in Azure Monitor alerts for job failures and add an alert processing rule with an action group that sends email
B: Create an activity log alert on each vault for failed backup jobs, with an action group that sends email to the team mailbox
C: Create an Azure Service Health alert for Azure Backup in the vault regions, with an action group that emails the IT team
D: Turn on email notifications on the Backup Alerts tab of each vault, which sends the classic alerts for each failed backup
K: A
G: ## Backup alerts are Azure Monitor alerts
Azure Backup raises **built-in Azure Monitor alerts** without any setup:
- **Security alerts** (Sev 0), such as deletion of backup data or disabling soft delete. They cannot be turned off.
- **Job failure alerts** (Sev 1), such as Backup Failure and Restore Failure. They are on by default and can be turned off per vault.
The alerts appear in Azure Monitor and in Resiliency (formerly Azure Business Continuity Center). **Notifications** are a separate step: you create an **alert processing rule** that routes the alerts to an **action group**, which can send email, SMS, ITSM, webhooks, Logic Apps and more.
## Other options
- **Log search alerts** need vault diagnostics in a Log Analytics workspace and a KQL query; useful for custom logic.
- **Classic alerts** (Backup Alerts tab of the vault) were deprecated on 31 March 2026; Microsoft recommends the built-in Azure Monitor alerts as the closest replacement.
W: Built-in alerts plus an alert processing rule: job failure alerts already fire in Azure Monitor, and an alert processing rule with an email action group delivers them with no workspace or query.
X: B=Activity log alert: the activity log records user-triggered operations on the vault, such as changing a policy, not the outcome of scheduled backup and restore jobs.
C=Service Health alert: Service Health reports Azure platform incidents and maintenance, not failures of your own backup or restore jobs.
D=Classic alerts: these are the deprecated classic alerts that the team no longer uses; the forward-looking solution is Azure Monitor alerts.
T: Backup job failures already raise built-in Azure Monitor alerts; route them to email with an alert processing rule and an action group.

@ AZ-104 D5 T5.2 advanced troubleshooting
S: A new administrator opens Backup Reports to review job success and storage use across a company's Recovery Services vaults and Backup vaults, but the reports show no data for any of them. Which TWO statements describe what is needed? (Select TWO)
A: Each vault needs a diagnostic setting that sends its backup data to a Log Analytics workspace selected in the reports
B: After diagnostics are set, the first data can take up to 24 hours, and the reports never show the current partial day
C: The Log Analytics workspace must be in the same region and subscription as each vault, or the data cannot be sent
D: The vaults' data must first be exported to a storage account and opened with the Power BI template app for backup
E: Built-in Azure Monitor alerts for job failures must be turned on, because the reports are built from fired alerts
K: A,B
G: ## Where Backup Reports get their data
Backup Reports are Azure workbooks that query **Azure Monitor Logs**. A vault sends nothing to them until you configure it:
1. Create (or reuse) a **Log Analytics workspace**. Its region and subscription are independent of the vaults' location and subscription.
2. On each Recovery Services vault and Backup vault, add a **diagnostic setting** that sends the backup diagnostic data to that workspace. A built-in Azure Policy definition can configure this for all Recovery Services vaults in a scope.
3. Open Backup Reports (in Resiliency, formerly Azure Business Continuity Center, or from a vault) and select the workspace.
## Timing
- The initial data push can take up to 24 hours after diagnostics are configured.
- Reports show only completed days (UTC); the current partial day is excluded. Microsoft recommends looking at the reports two days after setup.
- The workspace keeps data for 30 days by default; raise its retention for longer history.
The older Power BI template app that read from a storage account is on a deprecation path.
W: A=Diagnostic setting per vault: the reports read Log Analytics data, which exists only once each vault's diagnostic setting sends it to the workspace.
B=Initial delay and no partial day: even after setup, data can take up to 24 hours to arrive, and the current day is never shown, so empty reports right after setup are expected.
X: C=Same region and subscription: Microsoft states that the workspace's location and subscription are independent of where the vaults are.
D=Power BI template app: that storage-account-based reporting is on a deprecation path; current reports read the Log Analytics workspace directly.
E=Job failure alerts: alerts and reports are separate features; reports come from diagnostics data in Log Analytics, not from fired alerts.
T: Backup Reports need each vault's diagnostics sent to a Log Analytics workspace; allow up to a day for the first data and expect only completed days.
V: Azure Backup, Azure Monitor Logs, Log Analytics
