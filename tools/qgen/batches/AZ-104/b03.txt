@ AZ-104 D1 T1.3 advanced troubleshooting
S: An admin used Azure CLI to assign a custom deployIfNotExists policy that deploys diagnostic settings, at subscription scope with a system-assigned managed identity. The definition lists the required roles in `roleDefinitionIds`. Every remediation deployment now fails with an authorization error. What should the admin do?
A: Re-run the remediation task while signed in with the Owner role, because remediation deployments run under the identity of the user who starts the task.
B: Grant the assignment's managed identity the roles listed in `roleDefinitionIds` at the subscription, because only the portal grants those roles automatically.
C: Replace the system-assigned identity with a user-assigned one, because deployIfNotExists remediation does not support system-assigned identities.
D: Change the assignment's enforcement mode to DoNotEnforce, because remediation tasks for deployIfNotExists run only when enforcement is disabled.
K: B
G: ## How remediation gets its permissions
Policies with the **deployIfNotExists** or **modify** effect change resources. Azure Policy does not use the admin's account for those changes; it uses a **managed identity attached to the policy assignment** (system-assigned or user-assigned, one per assignment).
- The definition says which roles that identity needs in `details.roleDefinitionIds` (full role IDs, for example the Contributor role ID).
- The identity must then actually **hold** those roles at the scope it changes.
## Portal versus everything else
- When you assign the policy **in the portal**, Azure Policy creates the identity and grants it the listed roles automatically.
- When you assign it with an SDK, Azure CLI or PowerShell, the identity is created (for example with `az policy assignment create --mi-system-assigned --location westeurope`) but **no roles are granted**. You must add the role assignments yourself, for example with `az role assignment create` or `New-AzRoleAssignment` using the identity's principal ID.
- Manual grants are also needed when the resources changed are outside the assignment scope, or when `roleDefinitionIds` is edited later.
Note that evaluation of the policy still uses the caller of each request; only the deployment or modification uses the assignment's identity.
## Example
`az policy assignment create ... --mi-system-assigned --location westeurope` returns a principal ID. Granting that principal Monitoring Contributor and Log Analytics Contributor on the subscription lets the next remediation task deploy the diagnostic settings.
W: Grant the identity its roles: the assignment was created outside the portal, so its managed identity exists but holds none of the roles in `roleDefinitionIds`. Its template deployments are therefore unauthorized until the roles are assigned to it at the subscription.
X: A=Run the task as Owner: remediation deployments run as the assignment's managed identity, not as the person who starts the task, so the admin's own Owner role does not reach the deployment.
C=Switch to user-assigned: both system-assigned and user-assigned identities are supported for remediation. A new user-assigned identity would still need the same role assignments.
D=DoNotEnforce: enforcement mode controls whether the effect runs during create and update requests. Remediation tasks can be started in either mode, and changing it does nothing about missing permissions.
T: deployIfNotExists and modify remediate through the assignment's managed identity; only portal assignments grant its roles automatically, so CLI, PowerShell and SDK assignments need manual role assignments.

@ AZ-104 D1 T1.3 applied troubleshooting
S: The built-in policy "Inherit a tag from the resource group" (tag CostCenter) has been assigned to a subscription for months with a managed identity. Finance changed the CostCenter tag on rg-crm from 1001 to 2002. A week later most resources in rg-crm still show 1001; only a VM resized yesterday shows 2002. What should the admin do?
A: Run `az policy state trigger-scan` for rg-crm so that the evaluation cycle rewrites the tags of every resource in the group without waiting for the daily scan.
B: Replace the assignment with the "Append a tag and its value from the resource group" policy, which copies resource group tag values to every resource it contains.
C: Wait for the standard 24-hour compliance evaluation cycle, which applies the modify operation to all resources whose CostCenter value differs from the group.
D: Create a remediation task for the assignment, so that its managed identity applies the modify operation to the existing resources in rg-crm right away.
K: D
G: ## Resources do not inherit tags by themselves
A tag on a resource group or subscription is not copied to the resources inside it. To make resources follow the group's tag you use Azure Policy, typically the built-in definitions "Inherit a tag from the resource group" or "Inherit a tag from the subscription", which use the **modify** effect.
## When modify acts
- **Create or update requests**: modify changes the request before it reaches the resource provider. That is why the VM that was resized yesterday now carries 2002: the resize was an update, and the policy added the current group value.
- **Existing resources**: during an evaluation cycle modify only marks non-matching resources as **non-compliant**. It never changes them on its own.
- **Remediation task**: to fix existing resources, start a remediation task on the assignment. It runs the modify operations with the assignment's managed identity on every non-compliant resource.
## The limit to remember
Changing a group's tag later does not ripple down. Every change at the group needs a new remediation run (or later updates of each resource) before resources show the new value.
W: Remediation task: the modify effect fixes existing resources only through a remediation task, which uses the assignment's managed identity to add or replace the CostCenter tag on each non-compliant resource now.
X: A=On-demand scan: `az policy state trigger-scan` starts a compliance evaluation, which only updates compliance states. Evaluation never modifies existing resources.
B=Append policy: append also acts only on create and update requests and cannot remediate existing resources; it is also not recommended for tags, where modify is preferred.
C=Wait for the daily cycle: the 24-hour cycle re-evaluates compliance and marks the stale resources non-compliant, but it does not apply the modify operations to them.
T: Tag inheritance policies use modify: they fix resources as they are created or updated, and existing resources only through a remediation task.

@ AZ-104 D1 T1.3 applied use-case
S: An initiative is assigned at the Production management group. One storage account of a legacy app breaks a single definition in it and will be retired in 90 days. The team wants that account still evaluated against the other definitions, shown in compliance reports for that one rule, and the waiver to end on its own. What should the admin create?
A: A policy exemption on the storage account, category Waiver, limited to that definition's reference ID and with an `expiresOn` date 90 days out.
B: An entry for the storage account in the `notScopes` exclusion list of the initiative assignment, removed by an admin again after 90 days.
C: A ReadOnly resource lock on the storage account, so the noncompliant setting cannot change until the account is deleted in 90 days.
D: A second assignment of the initiative on the storage account with the enforcement mode set to DoNotEnforce for the next 90 days.
K: A
G: ## Three ways to narrow a policy assignment
- **Scope (inclusion)**: the assignment applies to everything under the scope where it is assigned.
- **Exclusion (`notScopes`)**: listed child scopes or resources are **not evaluated at all** and do not count in compliance. It is part of the assignment object and covers every definition in the initiative. Microsoft recommends exclusions for broad, permanent cases, such as a test environment that does not need the same governance.
- **Exemption**: a separate object created on a resource or resource hierarchy. The resource shows as **Exempt** in compliance reports, so it stays tracked.
## What exemptions add
- `exemptionCategory`: **Waiver** (non-compliance is temporarily accepted) or **Mitigated** (the intent is met another way).
- `policyDefinitionReferenceIds`: limit the exemption to some definitions of an initiative; the others still evaluate the resource.
- `expiresOn`: after this date the exemption is no longer honoured (the object stays for record keeping).
Creating an exemption requires `Microsoft.Authorization/policyExemptions/write` on the scope and the exempt action on the assignment.
W: Exemption with expiry: an exemption scoped to the account and to the one definition reference keeps all other rules active, reports the account as Exempt for that rule, and stops being honoured automatically on the `expiresOn` date.
X: B=notScopes exclusion: an excluded resource is not evaluated by any definition in the initiative and disappears from the compliance count, and nothing removes the entry after 90 days unless someone edits the assignment.
C=ReadOnly lock: a lock blocks control-plane changes but does not change how Azure Policy evaluates the account, so it would still show as non-compliant.
D=Second assignment in DoNotEnforce: adding another assignment does not relax the original one at the management group, which still evaluates and reports the account as non-compliant.
T: Permanent, broad carve-outs use exclusions (`notScopes`); time-limited, tracked exceptions for specific definitions use exemptions with a category and `expiresOn`.

C: Assign it with every VM size listed in the allowed-sizes parameter, then narrow the list to the approved sizes after the two-week review.

Every policy assignment has an `enforcementMode`:

C=Allow every size: with all sizes allowed every VM is compliant, so the review cannot show which VMs would break the real rule.
D=Exemptions for existing VMs: exempt VMs are not evaluated, so the existing fleet gives no results, and new VMs would still be blocked by Deny.
T: To preview a Deny-only policy without blocking anything, assign it with enforcement mode DoNotEnforce (Disabled); compliance is still evaluated and reported.

G: ## Definitions, initiatives and assignments
- A **policy definition** holds the rule and the effect.
- An **initiative** (policy set) groups several definitions so they are assigned and tracked as one unit.

## Parameters pass downward
An initiative can declare its own parameter, for example `init_allowedLocations`, and pass it to the parameters of each member definition with `[parameters('init_allowedLocations')]`. The same initiative can then be assigned many times, each assignment giving a different value.
## Example

Parameters make one definition reusable: the rule references `[parameters('effect')]`, and each assignment provides the value.

D=Definitions are immutable: assigned custom definitions can be edited. A copy plus an initiative would add complexity and still leave the old assignments unchanged.
T: A parameter added to a definition that is already assigned needs a `defaultValue`; parameters can't be removed from a definition.

@ AZ-104 D1 T1.3 applied troubleshooting
S: To protect a storage account's configuration, an admin adds a ReadOnly lock to it. Afterwards a support engineer with the Contributor role can't view the access keys in the portal, and a script that runs `az storage account keys list` fails. Apps that read blobs with Microsoft Entra ID keep working. Why?
A: Applying a ReadOnly lock rotates both account keys and disables Shared Key authorization, so only Microsoft Entra ID requests are accepted afterwards.
B: The Contributor role does not include permission to list storage account keys, and the lock only exposed this missing permission in the portal.
C: Listing keys is a POST operation on the control plane, which the ReadOnly lock blocks, while data-plane requests to the blob endpoint are not affected.
D: A ReadOnly lock blocks every request that goes to the storage account, but apps keep cached tokens and fail only after those tokens expire.
K: C
G: ## What a lock protects
Resource locks apply to **control-plane** operations, the requests sent to Azure Resource Manager at `https://management.azure.com`.
- **CanNotDelete** (portal: Delete): users can read and change the resource but not delete it.
- **ReadOnly** (portal: Read-only): users can read but not update or delete, much like everyone is limited to the Reader role.
Locks override role permissions, so even Owners are affected until the lock is removed.
## Side effects of ReadOnly
ReadOnly blocks any write, and that includes **POST** operations that look like reads. Listing storage account keys is a POST (`listKeys`) because the keys give full data access. With a ReadOnly lock on a storage account:
- users can't list the account keys, in the portal or with `az storage account keys list`;
- role assignments scoped to the account or its containers can't be added;
- blob containers can't be created through the control plane.
## What keeps working
Data-plane requests go to the service endpoint, such as `https://myaccount.blob.core.windows.net/`, not to Resource Manager, so reads and writes of blob data with Microsoft Entra ID (or existing keys and SAS) still work.
W: POST blocked by ReadOnly: the key listing is a control-plane POST that the ReadOnly lock refuses, while the apps' blob traffic uses the data plane, which locks never touch.
X: A=Keys rotated and Shared Key disabled: locks don't change resource settings or rotate keys; they only block management operations.
B=Contributor lacks the permission: Contributor can list storage account keys; the failure started with the lock, and removing the lock restores it.
D=Everything blocked, tokens cached: locks don't apply to data-plane requests at all, so the apps are not running on borrowed time.
T: ReadOnly locks block control-plane writes including POST actions such as listing storage keys; data-plane access is not affected by locks.

K: B
G: ## Deployment history
Every ARM template or Bicep deployment to a resource group leaves an entry in the group's **deployment history**. The history has a limit (800 entries per scope), and Azure Resource Manager normally deletes old entries automatically as the limit approaches, so most teams never notice it.
## Side effects of CanNotDelete
A **CanNotDelete** lock lets users read and change resources but not delete anything in scope. The automatic clean-up of deployment history is a delete operation, so the lock also stops it. Learn lists this side effect explicitly: with a cannot-delete lock on a resource group, Resource Manager can't delete deployments from the history, and once 800 are reached, deployments fail.
## Other documented side effects
- A cannot-delete lock prevents deleting Azure RBAC role assignments in scope.
- On the resource group used by Azure Backup it stops restore point clean-up, and backups fail.
## Fixing it
Learn's guidance is to remove the CanNotDelete lock from the group so automatic clean-up can run again. To keep deletion protection, put CanNotDelete locks on the individual critical resources instead of on the whole group.
W: History clean-up blocked: automatic deletion of old deployment entries is a delete operation, which the CanNotDelete lock blocks, so the history fills up and new deployments to that group fail.
X: A=Resource count limit: a lock has no resource count; it only blocks delete operations in its scope.
C=Locks expire into ReadOnly: locks have no expiry and never change their level on their own; a lock stays as created until someone removes it.
D=Role removed by the lock: adding a lock never changes role assignments; locks restrict operations for everyone regardless of their roles.
T: A CanNotDelete lock on a resource group also blocks automatic deployment-history clean-up, so frequent deployments eventually hit the history limit and fail.

A ReadOnly lock acts like limiting every user, Owners included, to Reader permissions for **Azure Resource Manager operations** in its scope. It is inherited by everything in the resource group.

## Practical advice
Use CanNotDelete when the goal is only to prevent accidental deletion, and keep ReadOnly for resources that really must not change.
