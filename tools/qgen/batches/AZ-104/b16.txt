@ AZ-104 D1 T1.1 advanced use-case
S: A retailer's help desk in Germany must reset passwords and edit profile details only for the roughly 900 employees whose country attribute is DE, and it must not be able to touch users in any other country. Membership has to follow HR changes to the country attribute without manual updates, and every user already has a Microsoft Entra ID P1 license. Which TWO actions should the administrator take to grant the narrowest access? (Select TWO)
A: Create an administrative unit whose dynamic membership rule is user.country -eq "DE", so German users join and leave it automatically
B: Assign the help desk group the User Administrator role with that administrative unit, not the whole directory, as the role's scope
C: Create a dynamic security group for country DE and assign the help desk the User Administrator role scoped to that security group
D: Assign the help desk the Helpdesk Administrator role at tenant scope and add a Conditional Access policy that limits it to German users
E: Add the German users to an administrative unit from a weekly CSV export of the HR system, and remove leavers from it in the same weekly run
K: A,B
G: ## Administrative units scope Microsoft Entra roles
A Microsoft Entra role assigned at **tenant scope** applies to every user. To limit an administrator to a subset of users, put those users in an **administrative unit (AU)** and assign the role **with the AU as its scope**.
- AUs can contain users, groups and devices.
- Membership can be assigned or **dynamic**: a rule such as `user.country -eq "DE"` adds and removes users as their attributes change.
- Licensing: creating AUs needs only Free, but each AU-scoped administrator needs P1, and dynamic AU membership needs P1 for each member.
## Example
The help desk group gets User Administrator scoped to the AU "Germany users". Its members can reset passwords and edit profiles of users in the AU and nobody else.
W: A=Dynamic AU: the rule keeps membership in step with the HR-fed country attribute without anyone editing lists, and P1 is already licensed for every user.
B=User Administrator scoped to the AU: the role grants password reset and profile edits, and the AU scope confines it to German users only.
X: C=Role scoped to a security group: a Microsoft Entra directory role such as User Administrator can't be scoped to a security group's members; the documented way to scope it to a set of users is an administrative unit.
D=Tenant-wide Helpdesk Administrator: Conditional Access controls how users sign in, not which objects a role can manage, so the help desk could still reset passwords of users in every country.
E=Weekly CSV import: it works technically, but membership lags HR changes by up to a week and requires a manual job, which breaks the requirement.
T: To delegate user management for a subset of users, assign the Microsoft Entra role at an administrative unit scope; a dynamic AU keeps the subset current.
V: Microsoft Entra ID, Administrative units

@ AZ-104 D1 T1.1 advanced troubleshooting
S: Contoso synchronizes its users from on-premises Active Directory with Microsoft Entra Connect Sync. A dynamic group for the Finance department misses a user who transferred from Sales last week, and in the Microsoft Entra admin center the administrator finds that the user's Department field can't be edited. The fix must survive future sync cycles and must stay within the supported way of managing synced users. What should the administrator do?
A: Add the user to the Finance dynamic group as a direct member so that the membership holds until someone fixes the Department value later on
B: Update the Department value with Microsoft Graph PowerShell, because only the admin center blocks edits of synchronized attributes
C: Change the Department attribute of the user in on-premises Active Directory, then let the next sync cycle update the dynamic group
D: Clear the user's on-premises immutable ID so the account becomes cloud-managed, then edit the Department field in the admin center
K: C
G: ## Source of authority
A synchronized user's **source of authority** is Windows Server Active Directory. Identity, contact and job attributes (Department, Job title, Manager and so on) must be changed **on-premises**; the change reaches Microsoft Entra ID with the next sync cycle.
- A few Microsoft Entra-only attributes, such as Usage location, can be edited in the cloud.
- Microsoft notes that some synced attributes can technically be changed in Microsoft Entra ID, but that this isn't recommended except in emergencies.
## Dynamic groups follow the attribute
A dynamic group's members come only from its rule (for example `user.department -eq "Finance"`). Once the corrected Department value syncs, the rule re-evaluates and adds the user; nobody adds members by hand.
W: Change it on-premises: Active Directory is the source of authority, so the corrected value flows to Microsoft Entra ID on the next sync and the dynamic rule then picks up the user, and the next cycles keep it that way.
X: A=Direct member of a dynamic group: dynamic groups don't accept manually added members; membership comes only from the rule.
B=Graph PowerShell: the restriction is not a portal limitation; synchronized job attributes are mastered on-premises, so a cloud edit is unsupported and the next sync can overwrite it.
D=Clear the immutable ID: this breaks the link to the on-premises object, an emergency-only change that is far outside normal management of synced users.
T: For synced users, change identity and job attributes in on-premises AD and wait for the next sync; dynamic groups update from the synced value.
V: Microsoft Entra ID, Microsoft Entra Connect Sync

@ AZ-104 D1 T1.1 advanced use-case
S: A partner engineer was invited as a B2B guest two years ago with her old company email address. She now works for the partner's new subsidiary, which uses a different email domain and its own Microsoft Entra tenant. She must keep her group memberships and app assignments in your tenant, and her object ID must not change because several audit reports are keyed on it. What should the administrator do?
A: Delete the guest account, invite the new email address as a new guest, and then re-create the memberships and app assignments from a saved export
B: Change the guest's user principal name to the new domain in the admin center so that her next sign-in is sent to the subsidiary's tenant
C: Resend the original invitation from her guest profile so that she can redeem it again while signed in with her new work account instead
D: Update the guest's email to the new address and run Reset redemption status, so she redeems a fresh invitation as the same user object
K: D
G: ## Reset redemption status
When a B2B guest's sign-in account changes (new company, new email, new home tenant), you don't have to delete and reinvite the guest. **Reset redemption status** sends a new invitation while keeping:
- the user's **object ID**,
- group memberships,
- app assignments.
After the guest redeems the new invitation, the UPN in your tenant stays the same and the sign-in name becomes the new email.
## How to do it
Edit the guest's **Email** (and Other emails) to the new address, then select **Reset redemption status** on the user's Overview page. PowerShell and the Microsoft Graph invitation API can do the same. Helpdesk Administrator (least privileged) or User Administrator at directory scope can reset it.
W: Reset redemption status: it is built for exactly this case and keeps the same user object, so the object ID, memberships and assignments all survive.
X: A=Delete and reinvite: a new guest gets a new object ID, which breaks the audit reports, and memberships must be rebuilt by hand.
B=Change the UPN: the UPN is only the guest's name in your tenant; it doesn't change which identity redeems or signs in, so she would still be tied to the old account.
C=Resend the invitation: resending applies to an invitation that hasn't been redeemed; an already redeemed guest stays bound to the old identity until redemption is reset.
T: When a guest's email or home tenant changes, update the email and use Reset redemption status to keep the same object, memberships and app access.
V: Microsoft Entra External ID, B2B collaboration

@ AZ-104 D1 T1.2 advanced use-case
S: A research firm keeps documents for 40 projects in one blob container, and its upload tool already sets a Project blob index tag on every blob. Each project team's Microsoft Entra group must read only blobs of its own project. The container layout can't change, and the security team allows no SAS tokens or account keys for this access. What should the administrator configure for each project group?
A: Storage Blob Data Reader on the container with a condition that allows blob reads only when the Project tag matches the group's project
B: A service SAS for the group that references a stored access policy on the container, with the project name written into each policy's identifier
C: A custom role whose NotDataActions exclude the blob read action for blobs whose Project tag holds another project's value, assigned on the container
D: Storage Blob Data Reader scoped to a virtual folder path named after the project inside the container, created by moving blobs under that path
K: A
G: ## Azure ABAC: conditions on role assignments
Azure RBAC grants access per scope (management group, subscription, resource group, resource, and for Blob storage down to a container). When the split you need is **inside** a container, add a **condition** to the role assignment. This is Azure attribute-based access control (ABAC).
- Conditions can test resource attributes such as **blob index tags**, container name, blob path or encryption scope, and principal attributes.
- Example from Learn: Storage Blob Data Reader with a condition that allows reads only when the blob tag `Project=Cascade`.
- Adding conditions in the portal, PowerShell, CLI and REST is generally available for the documented storage combinations.
## Why not a custom role?
`NotDataActions` removes an **action** from a role; it can't look at attribute values such as a tag.
W: Condition on Storage Blob Data Reader: the tag already exists on every blob, so one conditional assignment per group gives Microsoft Entra-based read access to exactly that project's blobs without SAS or keys.
X: B=Stored access policy SAS: every SAS is a token handed to users, which the security team forbids, and it can't be tied to a group's identity.
C=Custom role with NotDataActions: NotDataActions only excludes whole data actions; it has no way to compare a blob tag value, so it can't separate projects.
D=Folder-scoped assignment: Azure RBAC scopes stop at the container; moving blobs under folder paths would also change the layout, which isn't allowed.
T: To split read access within one container by blob tags, add an ABAC condition to a Storage Blob Data role assignment instead of creating SAS or custom roles.
V: Azure RBAC, Azure ABAC, Azure Blob Storage

S: A platform team built a custom role, Blob Auditor, with only Microsoft.Storage/storageAccounts/blobServices/containers/blobs/read in DataActions and container read in Actions. Auditors must read blobs in 30 subscriptions under the Production management group but must never obtain user delegation keys to issue SAS tokens. Adding the management group to AssignableScopes fails validation. What should the team do, with the fewest assignments that meet the rules?
A: Assign the built-in Storage Blob Data Reader role once at the Production management group, since built-in data roles can be assigned there
B: Move the blob read action from DataActions into Actions so that the custom role becomes valid at the management group scope
C: Add the tenant root management group to AssignableScopes, because the root scope accepts custom roles that contain DataActions
D: List the 30 subscriptions in AssignableScopes and create one Blob Auditor assignment for the auditors' group in each subscription

G: ## Custom roles and management groups
A custom role's **AssignableScopes** say where it can be assigned. A management group can be listed (only one), but Learn adds a hard rule: **a custom role that has DataActions can't be assigned at management group scope.** So for data access across subscriptions, list the subscriptions and assign per subscription.

Built-in **Storage Blob Data Reader** has:
- Actions: `containers/read` and `generateUserDelegationKey/action`
- DataActions: `containers/blobs/read`
The second action lets the holder obtain a user delegation key and sign user delegation SAS tokens, which this scenario forbids.
W: Subscriptions in AssignableScopes: the role keeps its data action and stays free of the delegation-key action, and 30 subscription-level assignments are the fewest that the DataActions rule allows.
X: A=Built-in Storage Blob Data Reader: it could be assigned at the management group, but it includes generateUserDelegationKey/action, so auditors could create user delegation SAS tokens.
B=Data action under Actions: blob reads are data-plane operations; listed under Actions the permission is invalid for control-plane checks and grants no blob data access.
C=Tenant root group: the root is still a management group, so the DataActions restriction applies there too.
T: Custom roles with DataActions can't be assigned at management group scope; list subscriptions in AssignableScopes and assign per subscription.

@ AZ-104 D1 T1.2 advanced use-case
S: Twelve apps share the key vault kv-shared, which uses the Azure RBAC permission model. A new reporting app runs with a user-assigned managed identity and must read the value of the secret sql-report-conn only; reading any other secret in the vault must fail. Security wants no new key vault and no access policies. What should the administrator do for the identity?
A: Assign Key Vault Reader on the vault, because that role reads secret metadata and values without being able to change or delete them
B: Assign Key Vault Secrets User with its scope set to the secret sql-report-conn itself, instead of to the whole key vault
C: Add an access policy that grants only Get on secrets to the identity, while the vault keeps using the Azure RBAC permission model
D: Assign Key Vault Secrets User on the vault, and add NotDataActions to the assignment to block every secret except sql-report-conn

G: ## Azure RBAC for Key Vault data
With the Azure RBAC permission model, data-plane access to keys, secrets and certificates comes from role assignments, and the scope can be as narrow as **one secret**.
- **Key Vault Secrets User**: reads secret contents.
- **Key Vault Secrets Officer**: any action on secrets except managing permissions.

Access policies belong to the legacy model; a vault uses one permission model at a time, so access policies have no effect on a vault set to Azure RBAC.
W: Secrets User on the single secret: the role reads secret values and the per-secret scope limits it to sql-report-conn, so other secrets are denied without a new vault.
X: A=Key Vault Reader: it reads metadata only and can't return a secret's value, so the app couldn't get the connection string.
C=Access policy: the vault evaluates Azure RBAC, so the policy would be ignored, and security forbids access policies anyway.
D=NotDataActions on an assignment: NotDataActions belong to role definitions, not assignments, and they exclude actions, not individual secret names.
T: In an RBAC-model key vault, scope Key Vault Secrets User to one secret to share only that secret; Key Vault Reader can't read values.

@ AZ-104 D1 T1.3 advanced use-case
S: A software company's development subscription has spend that swings widely from month to month as projects start and stop, so finance can't set a meaningful fixed budget amount for it. The FinOps lead wants an email when daily spend departs sharply from the subscription's recent usage pattern, without writing queries and without maintaining thresholds as projects change. What should the administrator configure?
A: A monthly budget on the subscription with alert conditions at 80 and 100 percent of an amount that finance revisits every quarter
B: A Cost Management anomaly alert rule for the subscription, which compares each day's usage with a forecast from recent usage
C: An Azure Advisor alert on the subscription that sends an email whenever a new cost recommendation appears for any of its resources
D: An activity log alert on the subscription that fires when a write operation creates resources whose cost exceeds the daily average
K: B
G: ## Budgets versus anomaly detection
- A **budget** compares actual or forecast cost with a **fixed amount** you set. It suits stable spend.
- **Cost anomaly detection** in Cost Management evaluates each **subscription daily**: it compares the day's total usage with an expected range forecast from the last 60 days, so recurring patterns (such as Monday spikes) aren't flagged. It runs about 36 hours after the end of the UTC day.
- An **anomaly alert rule** emails recipients when an anomaly is detected, with the top resource group changes. You create it from Cost alerts at subscription scope; no thresholds or queries.
## When to use which
Varying spend with no sensible fixed limit is the textbook case for anomaly alerts; budgets still help where a fixed limit exists.
W: Anomaly alert: it needs no fixed amount, adapts to the subscription's own recent pattern and emails when a day falls outside the expected range.
X: A=Budget with alert conditions: it depends on a fixed amount, which finance says can't be set meaningfully, and someone would have to keep revising it.
C=Advisor alert: Advisor alerts fire on new recommendations (for example right-sizing), not on unexpected changes in daily spend.
D=Activity log alert on cost: activity log alerts match operations and their properties; they have no cost value to compare with an average.
T: For subscriptions with variable spend, use Cost Management anomaly alerts; use budgets when a fixed spending limit makes sense.
V: Microsoft Cost Management, Cost alerts

@ AZ-104 D1 T1.3 advanced use-case
S: A release pipeline must confirm that resource group rg-payments is compliant before it promotes a build. The audit policy assignment has existed for weeks, but the last standard evaluation ran 20 hours ago and several resources changed since then through other pipelines. The pipeline step must start a fresh evaluation of every resource in rg-payments and wait until it finishes, without changing any resource. Which command should the step run?
A: az policy state list --resource-group rg-payments --filter "complianceState eq 'NonCompliant'" to fetch fresh results for every resource
B: az policy remediation create --resource-group rg-payments for the assignment, which re-evaluates every resource before it remediates any of them
C: az policy state trigger-scan --resource-group rg-payments, which starts an on-demand evaluation of the group and waits for it to complete
D: az policy assignment update for the assignment with an unchanged description, so that the assignment is evaluated again from the start

G: ## When Azure Policy evaluates
Compliance results are refreshed when an assignment is created or updated, when a resource is created or updated through Resource Manager (that one resource, about 15 minutes later), once every 24 hours in the **standard evaluation cycle**, and on an **on-demand scan**.
## On-demand evaluation scan
- `az policy state trigger-scan` starts an evaluation for the current subscription, or for one resource group with `--resource-group`.
- The CLI waits for the asynchronous scan to finish by default; `--no-wait` returns immediately.
- If a scan for that scope is already running, the request joins it instead of starting another.

D=Update the assignment: an update starts the same cycle as a new assignment, with no predictable completion time and no way for the command to wait for results.
T: Use az policy state trigger-scan (subscription or resource group) to force a fresh Azure Policy evaluation outside the 24-hour cycle.
V: Azure Policy, Azure CLI

@ AZ-104 D1 T1.3 advanced troubleshooting
S: Ravi must move subscription Sub-Analytics from management group MG-Dev to MG-Prod. His Owner role on Sub-Analytics is inherited from an Owner assignment on MG-Dev, and he holds only Contributor on MG-Prod. The portal blocks the move. Neither management group is the tenant root group, and no one else should become Owner of Sub-Analytics. Which TWO changes would each, on its own, let Ravi complete the move? (Select TWO)
A: Grant Ravi Owner on MG-Prod, because inherited subscription ownership allows moves only into groups where he is also Owner
B: Assign Ravi Owner directly on Sub-Analytics, after which his Contributor role on the target MG-Prod is enough to perform the move
C: Grant Ravi Management Group Reader on the tenant root group, because every move needs read access along the entire hierarchy path above both groups
D: Grant Ravi User Access Administrator on MG-Prod, because the move needs only permission to create role assignments at the target
E: Ask a Billing Administrator to approve the change, because moving a subscription to another management group is a billing operation
K: A,B
G: ## Permissions for moving a subscription
Moving a subscription to another management group needs permissions at three layers:
- **The subscription**: management group write, role assignment write and delete, and register action (Owner has these).
- **Target parent** management group: `Microsoft.Management/managementGroups/write` (for example Contributor or Management Group Contributor).
- **Current parent** management group: the same write permission.
The root management group is an exception: no permission is needed on it.
## The inherited Owner trap
If your Owner role on the subscription is **inherited from the current management group**, you'd lose it after the move. Azure therefore lets you move the subscription only to a group where you're **Owner**. With a **direct** Owner assignment on the subscription, Contributor on the target is enough.
W: A=Owner on the target: with inherited ownership he keeps Owner after the move only if he is Owner at MG-Prod, so this unblocks it.
B=Direct Owner on the subscription: a direct assignment travels with the subscription, so Contributor on MG-Prod then satisfies the target requirement; Ravi isn't someone else, so the no-new-Owner rule holds.
X: C=Reader on the root group: read access along the path isn't a requirement; the checks are write permissions on the subscription, target and current parent.
D=User Access Administrator on the target: the target needs management group write, which this role lacks, and it doesn't fix the inherited Owner restriction.
E=Billing approval: management group placement is a Resource Manager governance operation; billing roles play no part in it.
T: With Owner inherited from the source management group you can move a subscription only where you're Owner; a direct subscription Owner needs only Contributor on the target.
V: Azure management groups, Azure RBAC

@ AZ-104 D1 T1.3 advanced comparison
S: An administrator applies a CanNotDelete lock to resource group rg-core, which holds a storage account with business documents, an NSG, several VMs and their role assignments. A pipeline deploys ARM templates to rg-core many times a day. A colleague asks what the lock will and won't do besides blocking deletion of the resources themselves. Which THREE statements are correct? (Select THREE)
A: Removing an Azure role assignment that is scoped to rg-core or to one of its resources fails while the lock is in place
B: Resource Manager can no longer prune old entries from the group's deployment history, so deployments fail once the history reaches 800
C: A user with a data role can still delete blobs through the Blob service endpoint, because locks cover only control-plane operations
D: Changing settings such as a VM size or an NSG rule in rg-core fails, because the lock blocks every write operation on the locked resources
E: Starting and restarting the VMs in rg-core fails, because these operations are POST requests that the CanNotDelete lock treats as changes
F: Creating a flow log for the NSG in rg-core fails, because the lock prevents new resources that depend on the locked network security group
K: A,B,C
G: ## Two lock levels
- **CanNotDelete** (Delete in the portal): users can read and **modify** resources but can't delete them.
- **ReadOnly**: users can read but can't update or delete, much like the Reader role; POST operations such as VM start and storage key listing are blocked too.
Locks are inherited from the parent scope and apply to every user and role.
## Side effects documented on Learn
- A CanNotDelete lock on a resource or resource group **prevents deleting Azure RBAC assignments** there.
- A CanNotDelete lock on a resource group prevents Resource Manager from **automatically deleting deployments** from the history; at 800 deployments new deployments fail.
- Locks apply **only to control-plane operations** (`management.azure.com`). Data-plane requests to the storage account endpoint can still delete blobs, files, queues and tables.
- A CanNotDelete lock on an NSG **doesn't** prevent creating or modifying its flow log (a ReadOnly lock does).
W: A=Role assignment deletion blocked: Learn lists this explicitly for CanNotDelete locks on resources and resource groups.
B=Deployment history: automatic pruning is a delete, so the 800-entry limit is reached and further deployments fail.
C=Data plane still open: the lock protects the storage account resource, not the data inside it, so blob deletes over the Blob endpoint succeed.
X: D=Settings changes fail: CanNotDelete still allows updates; blocking changes is what a ReadOnly lock does.
E=Start and restart fail: that effect belongs to a ReadOnly lock on the resource group, which blocks POST actions; CanNotDelete doesn't.
F=NSG flow log creation fails: Learn states that a cannot-delete lock on an NSG doesn't prevent creating or modifying its flow log.
T: CanNotDelete still allows changes, blocks role assignment removal and deployment-history cleanup, and never protects data-plane content.
V: Azure Resource Manager, Resource locks

@ AZ-104 D2 T2.1 advanced use-case

- **Service Health** reports Azure-wide events that can affect your subscription: **service issues**, **planned maintenance**, **health advisories** and security advisories. Notifications are stored in the activity log.
- **Resource Health** reports the availability state of **your individual resources** (Available, Unavailable, Degraded).
## Service Health alerts
A Service Health alert is an activity log alert for Service Health events. You filter it by **subscription, services, regions and event types**, and attach an **action group** for email, SMS, push, voice, webhooks and more.
W: Service Health alert: it targets exactly the platform event types, services and regions requested and notifies through one action group.
X: A=Resource Health alerts: they report the health state of individual resources, which the team explicitly doesn't want, and they don't announce planned maintenance for a service.
C=Administrative activity log alert: the Administrative category records create, update and delete operations on resources, not Azure service notifications.
D=Advisor alert: Advisor alerts fire on new best-practice recommendations, not on incidents or maintenance.
T: Use Service Health alerts (filtered by service, region and event type) for Azure incidents and maintenance; Resource Health is per resource.

D: Install the MARS agent on the VM and back up the SQL data folder, so that new database files are picked up automatically by every run
K: A
G: ## Auto-protection for SQL Server in Azure VMs
Turning on **auto-protection** for a SQL Server instance (or Always On availability group) backs up all existing databases and **automatically protects new ones** with the policy you choose.
- Discovery typically runs **every eight hours**, and auto-protection of a newly discovered database is triggered **within 32 hours**.
- To protect a new database immediately, run **Rediscover DBs** manually.
- Databases already protected keep their own policies.
## Why not other tools
SQL workload backup is stream-based, with full, differential and log backups for point-in-time restores. VM backup and file-level agents don't give database-level, policy-driven protection.
W: Auto-protection plus Rediscover DBs: future databases are covered with no manual step, and a manual rediscovery protects today's database before tonight's window.
X: B=Rely on scheduled discovery: discovery runs about every eight hours and protection may take up to 32 hours, so tonight isn't guaranteed.
C=Enhanced VM policy: VM backups don't give the SQL workload policy's database-level full, differential and log backups, so the databases aren't protected under the same policy.
D=MARS agent on the data folder: MARS doesn't use SQL Server's VSS writer, so it can't make consistent database backups.
T: Enable SQL auto-protection to cover future databases; use Rediscover DBs when a new database must be protected before the next discovery.

S: A small firm wants Azure Backup for an on-premises Windows Server file server (selected folders and the system state), an on-premises Linux web server, and two Windows Azure VMs already protected by VM backup, where finance also wants one folder backed up on its own schedule. The firm wants to use the MARS agent wherever it is supported. Which TWO uses of the MARS agent are supported? (Select TWO)

B: Install the MARS agent inside the Windows Azure VMs next to the VM backup extension and back up the finance folder separately
C: Install the MARS agent on the on-premises Linux web server and back up its configuration and content folders to a Recovery Services vault
D: Install the MARS agent on the file server and register it with a Backup vault, since Backup vaults hold the newer on-premises workloads
E: Use the MARS agent on the Azure VMs for application-consistent SQL Server backups, because the agent calls each application's VSS writer
K: A,B
G: ## The MARS agent
The Microsoft Azure Recovery Services (MARS) agent backs up **Windows** machines directly to a **Recovery Services vault**:
- **Files and folders**, whole **volumes** and the Windows **system state** (system state on server editions).
- It runs on on-premises Windows machines, on **Windows Azure VMs**, and on MABS or DPM servers.
- On an Azure VM it can run **alongside the VM backup extension** to protect specific files and folders on a separate schedule.
## Limits
- Windows only; no Linux.
- It uses only the Windows System Writer for its VSS snapshot, **not application VSS writers**, so it doesn't make app-consistent backups of SQL Server or other apps.
W: A=Windows file server: folders and system state are standard MARS scenarios, sent to a Recovery Services vault.
B=Inside Azure VMs: Learn describes installing MARS in an Azure VM next to the VM backup extension to back up specific folders.
X: C=Linux server: the MARS agent runs only on Windows machines, so a Linux web server needs another protection method.
D=Backup vault: MARS registers only with a Recovery Services vault.
E=App-consistent SQL backups: MARS doesn't use application VSS writers; SQL Server in Azure VMs uses the workload backup extension instead.
T: MARS = Windows only, files, folders, volumes and system state to a Recovery Services vault, also inside Azure VMs next to the VM backup.
V: Azure Backup, MARS agent, Recovery Services vault
