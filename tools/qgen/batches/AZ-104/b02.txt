# AZ-104 D1 T1.2 Manage access to Azure resources (built-in roles, scopes, interpreting access)

@ AZ-104 D1 T1.2 applied troubleshooting
S: An external auditor at Contoso was assigned Storage Blob Data Reader on the storage account stauditlogs. When she signs in to the Azure portal, she cannot find the storage account or open its containers to read the log blobs. What should the administrator do?
A: Also assign her the Reader role at the storage account scope or higher, so that the portal can show the account and its containers
B: Replace her role with Storage Blob Data Owner at the storage account scope, because only Owner data roles let users open containers
C: Assign her the Storage Blob Delegator role on the storage account, so that the portal can create a user delegation key on her behalf
D: Add her to the Microsoft Entra Directory Readers role, so that the portal can list the storage accounts she has data access to
K: A
G: ## Two planes, two kinds of role
Azure separates **control plane** operations (managing the resource itself, handled by Azure Resource Manager) from **data plane** operations (working with the data inside it). A role definition lists control plane permissions in `Actions` and data plane permissions in `DataActions`.
- **Storage Blob Data Reader** has `DataActions` such as `.../containers/blobs/read` and only a few container-level `Actions`. It authorizes reading blob data with a Microsoft Entra account.
- **Reader** is a control plane role (`*/read`): it lets you see resources, but on its own it gives no access to blob data.
## What the portal needs
Learn's page on authorizing blob access in the portal lists two requirements for using your Microsoft Entra account:
- a role that grants access to blob data (Storage Blob Data Reader, Contributor or Owner), and
- the Azure Resource Manager **Reader** role, at a minimum, scoped to the storage account or higher, so you can navigate to the account and its containers.
## Example
`az role assignment create --assignee auditor@contoso.com --role Reader --scope <storage account resource ID>` adds the missing control plane permission; together with the existing data role she can browse and read the blobs.
W: Add Reader at account scope or higher: the data role authorizes reading blobs, but the portal also needs the control plane Reader role (or another management role) to list the storage account and navigate to its containers.
X: B=Storage Blob Data Owner: Owner is the full-access data role, which breaks least privilege, and it still has no control plane read permission on the storage account itself, so the navigation problem would remain.
C=Storage Blob Delegator: this role only allows getting a user delegation key to create a user delegation SAS. It adds no permission to see the storage account in the portal.
D=Directory Readers: this is a Microsoft Entra role for reading directory objects such as users and groups. It grants nothing on Azure resources, so the storage account stays invisible.
T: To read blobs in the portal with a Microsoft Entra account you need a blob data role plus at least Reader on the storage account or higher.
V: Azure RBAC, Azure Blob Storage, Azure portal

@ AZ-104 D1 T1.2 advanced troubleshooting
S: Jun has the Owner role on the subscription. The storage account stfinance in that subscription has a ReadOnly resource lock. When Jun opens a container in the portal, the blob list fails, although he can view all account settings. Why does this happen?
A: The ReadOnly lock suspends his Owner role assignment on the locked account, so he keeps only read access to the account settings
B: Owner has no blob DataActions, and the ReadOnly lock blocks the List Keys call the portal would otherwise use to read blobs
C: Owner inherited from the subscription applies only to resource groups, so a role assigned directly on the storage account is needed
D: The ReadOnly lock blocks every data plane read for all users, so nobody can list blobs until the lock is deleted from the account
K: B
G: ## Control plane wildcards do not reach data
The Owner role has `Actions: *` and no `DataActions`. Learn's role definition article is explicit: a user with a wildcard at subscription scope can create and delete containers but, by default, **cannot read the blobs inside them**. Control plane access is not inherited to the data plane when the portal uses the Microsoft Entra user account.
## How the portal picks an authorization method
When you open blob data, the portal first checks whether you hold `Microsoft.Storage/storageAccounts/listkeys/action`.
- If you do, it fetches the account key and reads data with **Access Key** authorization. Owner normally has this action, which is why Owners usually "just see" blobs.
- If listing keys is not possible, it uses your **Microsoft Entra account**, which needs a data role such as Storage Blob Data Reader.
## The lock
List Keys is a POST operation, and a **ReadOnly** lock blocks every POST on the account. With the lock in place the portal cannot get the key, falls back to Entra authorization, and Jun's Owner role has no data permission to use.
## Fix
Assign Jun a data role such as Storage Blob Data Reader at the account (or container) scope; he then reads blobs with his Entra account while the lock stays.
W: No DataActions plus blocked List Keys: Owner normally reaches blobs through the account key. The ReadOnly lock blocks the List Keys POST, so the portal uses his Entra identity, and Owner grants no blob data actions.
X: A=Lock suspends the assignment: locks never change or suspend role assignments. They block write, delete and POST operations for everyone; Jun is still an Owner, as his ability to view all settings shows.
C=Inheritance stops at resource groups: role assignments at a subscription are inherited by resource groups and every resource in them. A direct assignment of Owner on the account would behave exactly the same.
D=Lock blocks all data reads: users with a blob data role can still read data with their Entra accounts while a ReadOnly lock is in place; Learn tells them to use Entra credentials for exactly this case.
T: Control plane roles such as Owner carry no DataActions; they read blobs only through account keys, so when keys are unavailable a blob data role is required.
V: Azure RBAC, Azure Blob Storage, resource locks

@ AZ-104 D1 T1.2 applied troubleshooting
S: A Windows Server VM in rg-hr has Microsoft Entra login enabled. Admin Sora holds Virtual Machine Contributor on rg-hr and can start, resize and reconfigure the VM, but RDP sign-in with her Entra account is denied. What should be assigned to fix the sign-in with least privilege?
A: The Owner role on the virtual machine, because Owner adds the login permission that Virtual Machine Contributor leaves out
B: The Virtual Machine Administrator Login or Virtual Machine User Login role on the VM or a higher scope, depending on the rights she needs
C: The User Access Administrator role on rg-hr, so that she can grant herself the sign-in rights on the VM whenever she needs them
D: The Microsoft Entra Cloud Device Administrator role, because RDP sign-in to Entra-joined VMs is authorized by directory roles
K: B
G: ## Managing a VM is not signing in to it
For VMs with Microsoft Entra login, signing in is a **data plane** action:
- `Microsoft.Compute/virtualMachines/login/action` (sign in as a regular user)
- `Microsoft.Compute/virtualMachines/loginAsAdmin/action` (sign in as administrator or root)
These appear in `DataActions` of two built-in roles:
- **Virtual Machine Administrator Login**: sign in with administrator privileges
- **Virtual Machine User Login**: sign in with regular user privileges
**Virtual Machine Contributor** manages VMs (`Microsoft.Compute/virtualMachines/*` in `Actions`) but has no `DataActions`. Learn states that Owner or Contributor alone does not grant sign-in privileges either; this keeps an audited separation between people who control VMs and people who can log on to them.
## Example
Assign Virtual Machine User Login at the VM scope if Sora only needs a normal session, or Virtual Machine Administrator Login if she must administer Windows. Assigning at rg-hr covers every VM in the group.
W: VM Administrator Login or VM User Login: only these roles carry the login data actions that Entra-based RDP checks; Virtual Machine Contributor manages the VM resource but cannot sign in to it.
X: A=Owner on the VM: Owner has `Actions: *` but no `DataActions`, and Learn says Owner or Contributor alone does not grant sign-in. It is also far broader than needed.
C=User Access Administrator: letting her assign roles to herself is a privilege escalation path, not least privilege. The role itself grants no sign-in right.
D=Cloud Device Administrator: Entra directory roles manage devices in the directory; RDP sign-in to an Azure VM is authorized by the Azure roles that contain the login data actions.
T: Entra sign-in to Azure VMs needs Virtual Machine Administrator Login or Virtual Machine User Login; Owner, Contributor and VM Contributor do not include it.
V: Azure RBAC, Azure Virtual Machines, Microsoft Entra ID

@ AZ-104 D1 T1.2 applied use-case
S: The backup lead, Dara, must assign only the Backup Contributor and Backup Reader roles, and only to the Marketing and Sales groups, on the Prod subscription. She must not be able to grant any other role or assign roles to anyone else. What should the administrator configure?
A: Assign Dara the User Access Administrator role on the Prod subscription and ask her to document each role assignment that she creates
B: Assign Dara the Backup Contributor role on the Prod subscription, because it lets her assign backup roles to the groups that she supports
C: Assign Dara the Role Based Access Control Administrator role on the subscription with a condition limiting the roles and the principals
D: Make Dara an owner of the Marketing and Sales groups in Microsoft Entra ID, so that she can manage the access of both groups herself
K: C
G: ## The problem with classic delegation
Owner and User Access Administrator can create **any** role assignment for **any** principal at their scope, including Owner for themselves. Delegating with them breaks least privilege.
## Constrained delegation
The built-in **Role Based Access Control Administrator** role was designed for delegating role assignment management. It can create and delete role assignments, read resources and open support tickets, and nothing else. When you assign it you can add an **Azure ABAC condition** (a template in the portal, or the condition editor, PowerShell, CLI, Bicep or REST) that constrains:
- which roles can be assigned or removed (for example only Backup Contributor and Backup Reader)
- which principal types can receive them (users, groups, service principals)
- which specific principals can receive them (for example only the Marketing and Sales groups)
## What happens outside the condition
If Dara tries to assign another role, or assign a backup role to a different user or group, the role assignment fails. Learn uses this exact Backup Contributor / Backup Reader example.
W: RBAC Administrator with a condition: the role grants role assignment write and delete, and the condition limits those assignments to the two backup roles and the two groups.
X: A=User Access Administrator: she could assign any role, including Owner, to anyone in the subscription. Documentation does not restrict anything.
B=Backup Contributor: Learn describes it as managing the backup service but unable to create vaults or give access to others; it has no role assignment write, so she could not assign any role.
D=Group owner in Entra ID: owning a group lets her change its membership, not create Azure role assignments; she still could not grant the backup roles to the groups.
T: Delegate role assignment safely with Role Based Access Control Administrator plus a condition that limits the roles and principals.
V: Azure RBAC, Azure ABAC conditions

@ AZ-104 D1 T1.2 applied troubleshooting
S: The only subscription Owner left Contoso. Global Administrator Mika set Access management for Azure resources to Yes, signed in again and assigned Owner on the subscription to the new lead. She now wants to give up her own extra access. What should she do?
A: Remove the Owner role assignment that she created for the new lead, because her own access ends as soon as that assignment is deleted
B: Set Access management for Azure resources back to No in Entra ID Properties, which removes her User Access Administrator role at root scope
C: Remove her Global Administrator role in Microsoft Entra ID, because the root scope access lasts only while she holds that directory role
D: Do nothing, because the elevated access granted by the toggle expires automatically eight hours after it was turned on in Entra ID Properties
K: B
G: ## Two separate role systems
- **Microsoft Entra roles** (Global Administrator, User Administrator, ...) manage directory objects: users, groups, domains, licenses.
- **Azure roles** (Owner, Contributor, Reader, ...) manage Azure resources at management group, subscription, resource group or resource scope.
By default they do not span each other: a Global Administrator has **no** access to Azure resources.
## Elevating access
The documented bridge is the **Access management for Azure resources** toggle (Microsoft Entra ID > Manage > Properties), available only to Global Administrators. Setting it to **Yes** assigns that user **User Access Administrator** at root scope (`/`), so she can view all resources and assign roles in every subscription and management group of the tenant. This is how an orphaned subscription is recovered.
## Removing it again
Microsoft says to remove the elevated access once the root-scope changes are done:
- Set the toggle back to **No**, signed in as the same user (it is a per-user setting). This removes the User Access Administrator assignment at `/`.
- Removing that assignment on the Access control (IAM) page is not possible; besides the toggle, only Azure PowerShell, Azure CLI or the REST API can remove it.
- With Privileged Identity Management, deactivating the Global Administrator role does **not** set the toggle to No, so set it to No first.
W: Toggle back to No: the toggle is what created User Access Administrator at root scope, and setting it to No removes that assignment, which is the documented way to drop elevated access.
X: A=Remove the lead's Owner role: that assignment belongs to the new lead; her own User Access Administrator at root scope is a separate assignment and stays in place.
C=Remove Global Administrator: the root-scope User Access Administrator is an Azure role assignment that stays when the directory role ends; Learn notes that even deactivating the role in PIM does not turn the toggle off.
D=Expires automatically: the elevation has no built-in expiry; it stays until the toggle is set to No or the assignment is removed with PowerShell, CLI or REST.
T: Elevated access is a standing User Access Administrator assignment at root scope; remove it by setting Access management for Azure resources back to No.
V: Microsoft Entra ID, Azure RBAC

G: ## Where each kind of role can be scoped
| | Azure roles | Microsoft Entra roles |
|---|---|---|
| Manage | Azure resources | directory objects (users, groups, apps) |
| Scopes | management group, subscription, resource group, resource | tenant, administrative unit, individual object |
User Administrator is a **Microsoft Entra role**. Users are directory objects; they do not live inside a subscription or resource group, so Azure scopes do not apply to them.
## Administrative units
An **administrative unit** is a container in Microsoft Entra ID that restricts a role's permissions to the users, groups or devices you place in it. Learn's own example is delegating help desk work to regional support staff so they manage only users in their region. Administrators scoped to an administrative unit need a Microsoft Entra ID P1 license.

W: Administrative unit scope: Entra roles can be scoped to an administrative unit, which limits User Administrator to the users placed in that unit.
X: A=Subscription scope: subscriptions are Azure resource scopes used by Azure roles. Users do not belong to subscriptions, and Entra roles cannot be assigned there.
B=Management group scope: management groups organize subscriptions for Azure RBAC and Azure Policy; they cannot scope a Microsoft Entra role.
D=Resource group scope: resource groups hold Azure resources only; Entra roles such as User Administrator are never assigned at that level.
T: Azure roles are scoped to management groups, subscriptions, resource groups or resources; Entra roles to the tenant, administrative units or single objects.

@ AZ-104 D1 T1.2 advanced troubleshooting
S: Leo has the Contributor role on resource group rg-data and the User Access Administrator role on the storage account stdata01, which is in rg-data. Which statement describes what Leo can do with role assignments?
A: He can assign roles on stdata01 and on everything in rg-data, because User Access Administrator inherits upward to the resource group
B: He cannot assign any roles, because the NotActions of Contributor on rg-data block role assignment writes everywhere below it
C: He can assign roles in rg-data but not on stdata01, because a role on a resource is overridden by the role on its resource group
D: He can assign roles on stdata01 but not on other resources in rg-data, because the NotActions of Contributor do not deny anything
K: D
G: ## Effective permissions are additive
Azure RBAC adds up every role assignment that applies to a principal at a scope. There is no "most specific wins" rule and no override between parent and child scopes.
## NotActions is not a deny
Contributor is `Actions: *` minus `NotActions` that include `Microsoft.Authorization/*/Write` and `Microsoft.Authorization/*/Delete`. Learn explains that `NotActions` only shapes the set of actions **that role** grants: if a second role grants the excluded action, the user can perform it. Only a **deny assignment** blocks an action that a role grants.
## Inheritance goes down, not up
A role assigned at a scope applies to that scope and its children. User Access Administrator on `stdata01` reaches the account and its child resources, never its parent resource group or sibling resources.
## Applying this to Leo
- On `stdata01`: Contributor (manage the account) + User Access Administrator (`Microsoft.Authorization/*`), so he can create role assignments there.
- Elsewhere in `rg-data`: only Contributor applies, which excludes role assignment writes.
W: Roles on stdata01 only: User Access Administrator adds role assignment rights at the account scope, and Contributor's NotActions cannot cancel them because NotActions is not a deny rule.
X: A=Inherits upward: assignments flow from a scope to its children only. A role on a single storage account never applies to its resource group.
B=NotActions blocks everywhere: NotActions only subtracts actions from the Contributor role itself; another role assignment that grants the action still allows it.
C=Parent overrides child: RBAC has no override between scopes; all assignments that apply are summed, so the account-level role adds rights instead of being replaced.
T: Effective access is the sum of all role assignments; NotActions only trims one role, while only deny assignments block what a role grants.
V: Azure RBAC

@ AZ-104 D1 T1.2 applied troubleshooting
S: Hana is the subscription Owner. She tries to delete a virtual network in rg-shared and gets an authorization error. Access control (IAM) for rg-shared lists a deny assignment created by a deployment stack with DenyDelete. What explains the error, and how can it be resolved?
A: Owner can delete only resources it created, so the stack owner must delete the network or transfer it to Hana as the new resource owner
B: Deny assignments override role assignments; change the stack's deny settings, or add Hana to its excluded principals, then delete it

D: Deny assignments are removed by Hana adding a second Owner role assignment for herself directly on the virtual network resource
K: B
G: ## How Azure RBAC evaluates a request
Azure Resource Manager collects every role assignment and **deny assignment** that applies to the resource. If a deny assignment matches the principal and the action, access is **blocked**, whatever roles the user holds. Only then are role assignments checked.
## Who creates deny assignments
You cannot create your own deny assignments directly. In generally available scenarios Azure creates and manages them, for example:
- **Deployment stacks** with deny settings: `DenyDelete` or `DenyWriteAndDelete` protect the stack's managed resources against everyone unless explicitly excluded. `--deny-settings-excluded-principals` lists exempt principals.
- Azure managed applications.
All such deny assignments are system protected: you change them by changing the deployment stack, not by editing the deny assignment.
## Seeing them
Access control (IAM) > **Deny assignments** shows deny assignments at the scope and inherited to it, with denied and excluded principals.
W: Deny overrides allow: a deny assignment blocks the action even for an Owner. The supported fix is to update the deployment stack's deny settings, or exclude Hana's principal, and then delete the resource.
X: A=Owner only for own resources: Azure RBAC has no concept of a creator-owner; Owner applies to every resource in scope. The block comes from the deny assignment.
C=Deny only below Owner: a deny assignment applies to the listed principals regardless of their roles, Owner included. The portal already shows a deny assignment, not a lock.
D=Second Owner assignment: adding more role assignments cannot outweigh a deny assignment, because deny assignments are evaluated first and block the action.
T: Deny assignments, created by Azure for features such as deployment stacks, block actions even for Owners; change the source (the stack) to lift them.
V: Azure RBAC, deployment stacks

## What Learn says about moves
If you move a resource that has an Azure role assigned **directly to the resource** (or to a child resource), the role assignment **is not moved** and becomes orphaned. Assignments inherited from the subscription or a management group are unaffected when the resource stays in the same subscription, because those parent scopes still contain it.

T: Role assignments set directly on a resource stay behind when the resource moves; re-create them at the new scope.

G: ## Subscriptions trust one directory
Every subscription trusts exactly one Microsoft Entra directory. Role assignments point to **object IDs** of users, groups and service principals in that directory, and every managed identity is a service principal in it.
## What a transfer does
Learn's transfer article and RBAC troubleshooting page say that when you transfer a subscription to a different Microsoft Entra directory:
- all role assignments (and custom roles) are **permanently deleted** and not migrated, so you re-create them in the target directory;
- managed identities **are not updated**, so existing system-assigned and user-assigned identities are **broken**.
## Fixing managed identities
- **System-assigned**: disable and re-enable the identity on the resource, which creates a new service principal in the target directory.
- **User-assigned**: delete, re-create and attach the identity to the resource.
- In both cases, re-create the identity's role assignments, because the new identities have new object IDs.
Run `az ad sp list` before the transfer to find the identities and `az role assignment list` to record what they were granted.
W: Re-enable, re-create and re-assign: identities are not carried to the new directory, so the system-assigned one is disabled and re-enabled, the user-assigned one is re-created and attached, and each new identity gets its roles again.
X: A=Role assignments only: managed identities are not updated by the transfer and stay broken; new assignments for the old object IDs cannot fix them.
B=Restart the resources: a restart reuses the same broken identity configuration; the service principals do not exist in the target directory.
D=Directory Readers: the identities themselves are missing from the target directory, and a directory role cannot be assigned to an identity that does not exist there.
T: After moving a subscription to another Entra directory, re-enable system-assigned identities, re-create user-assigned ones and re-create every role assignment.
V: Azure RBAC, managed identities, Microsoft Entra ID, Azure subscriptions

@ AZ-104 D1 T1.2 advanced troubleshooting
S: A pipeline signs in as a service principal that has the Owner role on the subscription. It runs `az role assignment create --assignee "ana@contoso.com" --role Reader --scope <rg ID>` and gets "Insufficient privileges to complete the operation". Which TWO actions resolve the error? (Select TWO)
A: Run the command with `--assignee-object-id` and Ana's object ID, so that Azure CLI skips the directory lookup
B: Also assign the service principal the User Access Administrator role at the scope of the subscription
C: Wait ten minutes and run the command again, because the Owner role assignment has not yet replicated
D: Assign the service principal the Directory Readers role in Microsoft Entra ID so it can read the directory
E: Change the scope of the command to the subscription, because roles cannot be assigned at a resource group
K: A,D
G: ## Two systems in one command
`az role assignment create` touches two systems:
1. **Microsoft Entra ID**: with `--assignee` and a user principal name, Azure CLI first looks up the user's object ID in the directory.
2. **Azure RBAC**: it then writes the role assignment, which needs `Microsoft.Authorization/roleAssignments/write` at the scope.
Owner covers step 2. Step 1 is a directory read, and a service principal **cannot read Microsoft Entra ID by default**. The error "Insufficient privileges to complete the operation" comes from that directory lookup, not from Azure RBAC.
## The two documented fixes
- Give the service principal permission to read the directory, for example the **Directory Readers** Entra role.
- Skip the lookup: pass `--assignee-object-id <object ID>` (and ideally `--assignee-principal-type User`), so CLI never queries Entra ID.
W: A=--assignee-object-id: with the object ID supplied, Azure CLI skips the Microsoft Entra lookup that failed, and the Owner role already allows the role assignment write.
D=Directory Readers: the lookup fails because the service principal cannot read the directory; this Entra role lets it resolve Ana's user principal name.
X: B=User Access Administrator: the service principal already holds Owner, which includes role assignment write. Another Azure role does not grant directory read access.
C=Wait for replication: the error is a missing directory permission, not a propagation delay, so it would fail again after any wait.
E=Subscription scope only: roles can be assigned at management group, subscription, resource group and resource scope; a resource group is valid.
T: "Insufficient privileges" when a service principal assigns roles by UPN means it cannot read Entra ID; use --assignee-object-id or grant Directory Readers.
V: Azure RBAC, Azure CLI, Microsoft Entra ID

@ AZ-104 D1 T1.2 applied use-case
S: The web app in rg-shop uses a system-assigned managed identity to read secrets from kv-shop, a key vault that uses the Azure role-based access control permission model. The identity has Key Vault Contributor on kv-shop but gets 403 errors reading secrets. Which role assignment fixes this with least privilege?
A: Key Vault Secrets User on kv-shop, which allows reading secret contents and nothing else that manages the vault
B: Key Vault Reader on kv-shop, which allows reading the metadata of the vault together with its secrets and keys
C: Key Vault Administrator on kv-shop, which allows all data plane operations on keys, secrets and certificates
D: Contributor on rg-shop, which adds write access to every resource in the group, including the key vault itself
K: A
G: ## Key Vault has two planes
- **Control plane**: create, delete and configure vaults (Azure Resource Manager, authorized by Azure RBAC).
- **Data plane**: work with keys, secrets and certificates (authorized by Azure RBAC in the RBAC permission model, or by legacy access policies).
Learn states that **Key Vault Contributor** is for control plane operations only: it does **not** allow access to keys, secrets and certificates.
## Built-in data plane roles (RBAC permission model)
- **Key Vault Secrets User**: read secret contents
- **Key Vault Secrets Officer**: perform any action on secrets, except manage permissions
- **Key Vault Reader**: read metadata, but **not** secret values or key material
- **Key Vault Administrator**: all data plane operations on keys, secrets and certificates
## Example
`az role assignment create --assignee-object-id <identity object ID> --assignee-principal-type ServicePrincipal --role "Key Vault Secrets User" --scope <kv-shop resource ID>`
W: Key Vault Secrets User: it grants exactly the data action to read secret values, which is what the app needs, at the scope of the one vault.
X: B=Key Vault Reader: it reads metadata only and cannot read secret values, so the 403 errors would continue.
C=Key Vault Administrator: it would work, but it also allows creating, changing and deleting keys, secrets and certificates, far more than reading secrets.
D=Contributor on the resource group: Contributor has no DataActions, so it cannot read secrets in an RBAC-model vault; it only adds broad control plane rights.
T: Key Vault Contributor manages vaults, not their contents; an app that reads secrets needs Key Vault Secrets User on the vault.
V: Azure Key Vault, Azure RBAC, managed identities

@ AZ-104 D1 T1.2 advanced comparison
S: A security review must find every built-in role that lets a user read and write all data in a storage account by retrieving the account access keys, which needs `Microsoft.Storage/storageAccounts/listkeys/action`. Which TWO of these built-in roles include that action? (Select TWO)
A: Storage Blob Data Owner, which gives full control of blob containers and the blobs that are stored inside them
B: Reader and Data Access, which lets users view everything and read or write data through the storage account keys
C: Storage Account Contributor, which permits management of storage accounts and also provides access to the account key
D: Storage Blob Delegator, which lets users get a user delegation key to create a shared access signature for blob data
E: Reader, which lets users view every resource in the scope, including the full configuration of each storage account
K: B,C
G: ## Shared Key: why listKeys matters
A storage account has two access keys. Anyone holding a key has full access to all data in the account through **Shared Key** authorization, outside Azure RBAC. Getting a key needs the control plane action `Microsoft.Storage/storageAccounts/listkeys/action`.
## Built-in roles that include it (from least to most permissions, per Learn)
- **Reader and Data Access**: view everything, cannot create or delete accounts, and has read and write access to all data via the keys.
- **Storage Account Contributor**: manage storage accounts and access the account key.
- **Contributor** and **Owner**: through their `*` actions.
## Roles that do not
- **Storage Blob Data Owner / Contributor / Reader**: blob `DataActions` plus container actions, but no listKeys; they work through Microsoft Entra authorization.
- **Storage Blob Delegator**: only `generateUserDelegationKey/action`, a different, Entra-backed key used for user delegation SAS.
- **Reader**: `*/read` only; listKeys is a POST action, not a read.
W: B=Reader and Data Access: it includes `listKeys/action` by design, so its holders can read and write all data through the keys even though the role cannot change the account.
C=Storage Account Contributor: Learn describes it as providing access to the account key, which can be used for Shared Key data access.
X: A=Storage Blob Data Owner: full blob data rights come from DataActions authorized with Entra ID; the role has no listKeys action.
D=Storage Blob Delegator: the user delegation key it returns is not an account key; it only signs user delegation SAS tokens bounded by the user's own data roles.
E=Reader: Reader allows only read operations; listing keys is a POST action, so Reader cannot retrieve the keys.
T: Roles with listKeys (Reader and Data Access, Storage Account Contributor, Contributor, Owner) give full data access through account keys; blob data roles do not.
V: Azure Storage, Azure RBAC

@ AZ-104 D1 T1.2 applied comparison
S: Contoso hires an access manager who must create and remove role assignments for other people in rg-finance. She must not be able to create, change or delete any resource in rg-finance herself. Which TWO built-in roles assigned at rg-finance meet these requirements? (Select TWO)
A: Owner, which grants full access to manage every resource and also allows her to assign roles in Azure RBAC
B: User Access Administrator, which lets her manage user access to Azure resources and read all resources
C: Contributor, which grants full access to manage every resource but does not allow assigning roles in Azure RBAC
D: Role Based Access Control Administrator, which lets her assign and remove roles and read all resources
E: Reader, which lets her view every resource and its role assignments without making any changes to them
K: B,D
G: ## The privileged administrator roles
Learn groups these built-in roles as privileged:
| Role | Manage resources | Assign roles |
|---|---|---|
| Owner | yes (`*`) | yes |
| Contributor | yes (`*` minus Authorization writes) | no |
| User Access Administrator | no (`*/read` only) | yes (`Microsoft.Authorization/*`) |
| Role Based Access Control Administrator | no (`*/read` only) | yes (role assignment write and delete) |
Reader has `*/read` only and can view role assignments, but not change them.
## Choosing between the two access roles
- **User Access Administrator** manages all of `Microsoft.Authorization`, which also includes things such as locks and policy assignments.
- **Role Based Access Control Administrator** is narrower: only role assignments, plus support tickets. It also supports conditions to limit which roles and principals she can assign, which Microsoft recommends for least privilege.
W: B=User Access Administrator: it grants `Microsoft.Authorization/*` with only read access to resources, so she can manage role assignments but not change resources.
D=Role Based Access Control Administrator: it grants role assignment write and delete with `*/read`, the least privileged built-in way to manage access without managing resources.
X: A=Owner: Owner can assign roles but also create, change and delete every resource, which the requirement forbids.
C=Contributor: Contributor manages every resource and its NotActions exclude role assignment writes, so it fails both requirements.
E=Reader: Reader can see role assignments but cannot create or remove them.
T: To manage access without managing resources, use User Access Administrator or the narrower Role Based Access Control Administrator.
V: Azure RBAC

@ AZ-104 D1 T1.2 applied use-case
S: A partner application's service principal must upload files into only the inbound container of the storage account stexchange. The account has four other containers that the partner must not be able to read or change. Which role assignment meets the requirement with least privilege?
A: Storage Blob Data Contributor at the stexchange storage account scope, which lets it write blobs in any container of the account
B: Storage Account Contributor at the stexchange storage account scope, which lets it manage the account and use its access keys
C: Storage Blob Data Contributor at the inbound container scope, which lets it read, write and delete blobs in that container only
D: Storage Blob Data Owner at the resource group scope, which lets it control all blob data in every account of that resource group
K: C
G: ## Scopes go all the way down
Azure roles can be assigned at management group, subscription, resource group or **resource** scope, and for Azure Storage the resource scope can be as narrow as a single **container**. Learn's scope examples include a container ID like:
`/subscriptions/<id>/resourceGroups/rg-x/providers/Microsoft.Storage/storageAccounts/stexchange/blobServices/default/containers/inbound`
Permissions are inherited downward only, so an assignment on `inbound` does not reach sibling containers.
## Picking the role
- **Storage Blob Data Reader**: read and list blobs (not enough to upload)
- **Storage Blob Data Contributor**: read, write and delete containers and blobs
- **Storage Blob Data Owner**: full access, including POSIX access control (more than needed)
Learn's guidance: start with the most restrictive role and the narrowest scope that meet the need.
W: Data Contributor on the container: it grants blob write at the inbound container only, so the partner can upload there while the four other containers remain out of reach.
X: A=Account scope: the same role at the account is inherited by all five containers, exposing the four the partner must not touch.
B=Storage Account Contributor: it can list the account keys, and a key gives full Shared Key access to every container in the account.
D=Blob Data Owner on the group: it is the broadest data role at a broader scope, covering every container of every account in the resource group.
T: Grant data roles at the narrowest scope that fits; for blob access that can be a single container.
V: Azure RBAC, Azure Blob Storage
