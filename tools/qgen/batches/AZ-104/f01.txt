@ AZ-104 D2 T2.1 advanced troubleshooting
S: An ad hoc account SAS signed with key1 was posted in a public code repository. Production apps use a connection string with key1, and a few batch jobs already use key2. The admin must invalidate the leaked SAS with no app outage. Which sequence should the admin follow?
A: Delete every stored access policy on the account's containers, then regenerate key2 to remove anything still valid.
B: Run `az storage account revoke-delegation-keys`, then set a key expiration policy so both keys rotate in the future.
C: Point the production connection strings at the secondary key, verify traffic, then renew the primary key.
D: Regenerate key1 right away, then update the production apps to the new key1 value as quickly as possible afterwards.
K: C
G: ## Two keys for rotation
Every storage account has two 512-bit access keys, **key1** (primary) and **key2** (secondary). Two keys exist so you can rotate without downtime:
1. Point apps to the key you are *not* regenerating.
2. Regenerate the other key (`az storage account keys renew --key primary`).
3. Move apps to the new key, and later regenerate the second key the same way.
## Keys and SAS
Learn notes that regenerating a key **revokes every SAS signed with it**, so account and service SAS created from that key must be reissued. User delegation SAS aren't affected by key rotation. An ad hoc account SAS has no stored access policy, so key regeneration is the way to revoke it.
## Example
Switch the production app settings to the key2 connection string, verify traffic, then run `az storage account keys renew -g rg-prod --account-name stprod --key primary`. The leaked token stops working; nothing goes down.
W: Move to the secondary key, then renew the primary: the apps keep running on key2 (the secondary key) while renewing key1 (the primary key) revokes every SAS signed with it, including the leaked account SAS.
X: A=Delete policies and regenerate key2: account SAS can't use stored access policies, and the leaked token was signed with key1, so regenerating key2 leaves it valid and breaks the batch jobs.
B=Revoke delegation keys: that only invalidates user delegation SAS; a key expiration policy is a reminder and doesn't revoke anything.
D=Regenerate key1 first: this does revoke the token, but the production apps fail from the moment the key changes until they're updated.
T: To revoke an account or service SAS without stored access policy, switch apps to the other key and regenerate the key that signed it.

@ AZ-104 D3 T3.2 advanced comparison
S: An auditor requires that new Linux VMs at a logistics firm encrypt the temp disk and the OS and data disk caches at rest, and that disk data travel encrypted from the host to Azure Storage. Encryption must not use the VMs' own CPU. Which option should the administrator enable on the new VMs?
A: Confidential disk encryption on a standard D-series size, so the OS disk key is bound to the VM's TPM
B: Encryption at host, a VM setting that extends server-side encryption to the server running the VM
C: Azure Disk Encryption with a key encryption key, so DM-Crypt inside each VM encrypts every volume
D: Server-side encryption with a customer-managed key in a disk encryption set for each managed disk
K: B
G: ## Four ways a managed disk can be encrypted
Azure offers several layers, and they protect different things:
- **Server-side encryption (SSE)** is always on. Azure Storage encrypts OS and data disks when it writes them to the storage clusters, with platform-managed keys or, through a **disk encryption set**, customer-managed keys. It does **not** cover the temp disk or the disk caches on the host, and data between the host and storage is not part of it.
- **Encryption at host** is a VM setting that extends SSE: the server hosting the VM encrypts the temp disk, the ephemeral OS disk and the OS/data disk caches, and the data flows encrypted to Azure Storage. It runs on the host, so it does not use the VM's CPU.
- **Azure Disk Encryption (ADE)** encrypts volumes inside the guest with BitLocker (Windows) or DM-Crypt (Linux). It uses the VM's CPU and does not work for custom Linux images. ADE is scheduled to retire on September 15, 2028, and Microsoft tells you to use encryption at host for new VMs.
- **Confidential disk encryption** binds the OS disk key to the VM's TPM (temp disk encryption is an opt-in extra) and is available only on confidential VM sizes (such as DCasv5/ECasv5).
## Example
`vm-route-01` with encryption at host on: its `/dev/disk/azure/resource` temp disk and the read cache of its data disk are encrypted on the host, and writes leave the host already encrypted.
W: Encryption at host: the server hosting the VM encrypts the temp disk and the OS and data disk caches and sends the data to storage already encrypted, without any load on the guest CPU; it is also Microsoft's recommended choice for new VMs.
X: A=Confidential disk encryption: it needs a confidential VM size such as DCasv5 or ECasv5, so a standard D-series size can't use it; it also protects the OS disk (temp disk only by opt-in) and, per Learn's comparison table, does use the VM's CPU.
C=Azure Disk Encryption: it covers temp disks and caches but encrypts inside the guest with DM-Crypt, which uses the VM's CPU, and it is scheduled for retirement in 2028.
D=Customer-managed SSE: a disk encryption set changes who controls the key for data at rest in storage, but SSE still leaves temp disks and host caches unencrypted.
T: Temp disk and cache encryption plus encrypted data flow without guest CPU cost → encryption at host; ADE is retiring.

@ AZ-104 D2 T2.3 applied use-case
S: Yesterday an administrator started a standard-priority rehydration of 400 archived blobs to the hot tier. Now legal needs one 2 GB contract from that set as soon as possible, and its rehydration is still pending. What should the administrator do?
A: Cancel the pending Set Blob Tier request for that blob and start it again with High priority instead
B: Take a snapshot of the archived blob and read the snapshot, which is served from an online tier right away
C: Call Set Blob Tier again on just that blob, with the same target tier and the priority raised to High
D: Download the archived blob directly with AzCopy, which reads archive data without needing to rehydrate
K: C
G: ## Rehydrating from archive
A blob in the **archive** tier is offline: it cannot be read or modified until it is **rehydrated** to hot, cool or cold, either with **Set Blob Tier** on the blob itself or with **Copy Blob** to a new online blob.
## Rehydration priority
- **Standard** (default): processed in the order received; can take up to 15 hours for objects under 10 GB.
- **High**: prioritized; may finish in under an hour for objects under 10 GB, at a higher cost.
While a standard request is pending, you **can raise** a blob's priority to High (for example, bulk restore at Standard and then expedite the few urgent blobs). You **can't lower** a pending request from High to Standard, and a Set Blob Tier request **can't be cancelled** once it starts. High-priority throughput is also limited per storage account, so expedite only what is urgent.
## Example
`az storage blob set-tier --container-name contracts --name 2021/acme.pdf --tier Hot --rehydrate-priority High` updates the pending request for that blob (the target tier must match the one in the original request); the other 399 blobs continue at Standard.
W: Raise that blob's priority to High: Learn explicitly allows updating a pending standard-priority rehydration to High for individual blobs that are needed sooner, as long as the target tier matches the original request, without touching the rest of the bulk job.
X: A=Cancel and restart: a Set Blob Tier request can't be cancelled after it starts. The supported path is to update the priority of the pending request.
B=Snapshot of an archived blob: snapshots aren't supported for archived blobs, and a snapshot would still not make offline data readable.
D=AzCopy download from archive: no tool can read archived blob data; only metadata and properties are available until rehydration completes.
T: A pending standard rehydration can be raised to High priority for urgent blobs; it can't be cancelled or lowered from High to Standard.

@ AZ-104 D2 T2.2 applied troubleshooting
S: A reporting app is configured to read from `contosodata-secondary.blob.core.windows.net` using the account's access key, so reports keep working during a primary outage. Requests to that host fail, while the primary endpoint works. The account's redundancy is GRS. What should the administrator change?
A: Convert the account to GZRS, because the secondary endpoint is available only when the primary region uses zones
B: Switch the replication setting to RA-GRS, which exposes a read-only copy without any change to credentials
C: Start a customer-managed failover so that the secondary region's endpoint becomes readable for the reporting app
D: Generate a separate access key for the secondary region, because the secondary endpoint doesn't accept the primary keys
K: B
G: ## Geo-redundant is not the same as readable
With **GRS** or **GZRS**, data is copied asynchronously to the secondary region, but that copy isn't readable or writable unless a failover happens.
With **RA-GRS** or **RA-GZRS**, the secondary is always available for reads:
- The secondary endpoint adds `-secondary` to the account name, for example `contosodata-secondary.blob.core.windows.net`.
- The account access keys are the same for the primary and secondary endpoints.
- The secondary can lag behind the primary; the **Last Sync Time** property shows how current it is.
## Changing it
GRS to RA-GRS is a geo/read-access change, done in the portal's Redundancy page or with `az storage account update --sku Standard_RAGRS`; no conversion is needed. Azure Files doesn't support RA-GRS or RA-GZRS.
W: Enable read access with RA-GRS: only RA-GRS or RA-GZRS exposes the `-secondary` endpoint for reads, and it accepts the same keys, so changing the setting makes the app's configuration work as designed.
X: A=Convert to GZRS: GZRS still keeps the secondary unreadable without a failover. Read access comes from the RA- options, not from zones in the primary.
C=Customer-managed failover: a failover makes the secondary the new primary through DNS updates. It's a disaster recovery action, not a way to enable read-only access, and an unplanned one would also drop geo-redundancy.
D=Separate secondary key: there's no secondary-only key. Learn states the access keys are the same for the primary and secondary endpoints.
T: GRS and GZRS secondaries can't be read until a failover; RA-GRS and RA-GZRS expose a `-secondary` endpoint that uses the same keys.

@ AZ-104 D2 T2.1 applied troubleshooting
S: An Azure file share uses AD DS authentication. Hybrid user Mia's only share-level permission is the built-in read-only Azure RBAC role for SMB access, and she has the NTFS Modify permission on folder `\Projects`. She can open files there but can't save changes. What should the admin do?
A: Give Mia the NTFS Full Control permission on `\Projects` so that her file-level rights are higher than the share-level role.
B: Assign Mia the Storage File Data SMB Share Contributor role on the file share and leave the folder ACLs as they are.
C: Assign Mia the Reader role on the storage account so her share-level and file-level permissions can be merged together.
D: Assign Mia the Storage Blob Data Contributor role on the storage account so that her write requests are authorized.
K: B
G: ## Two layers of permission
Identity-based access to Azure Files checks two things:
- **Share-level permissions** (Azure RBAC roles on the share, or a default share-level permission): the gatekeeper for the whole share.
- Storage File Data SMB Share Reader: read.
- Storage File Data SMB Share Contributor: read, write, delete.
- Storage File Data SMB Share Elevated Contributor: read, write, delete, modify ACLs.
- **Directory and file permissions** (Windows ACLs, also called NTFS permissions): fine-grained rights on folders and files.
## The most restrictive wins
When the layers differ, only the most restrictive applies. Learn's example: read/write at file level but read at share level means the user can only read. With SMB Share Reader, even NTFS Full Control yields Read only. With SMB Share Contributor and NTFS Modify, the user gets read, write and delete.
## Example
Share-level role changes usually take effect within 30 minutes, so Mia should reconnect after the new assignment propagates.
W: SMB Share Contributor role: her NTFS Modify already allows writing, and the share-level read-only role (Storage File Data SMB Share Reader) is the restrictive layer. Contributor at share level gives read, write and delete together with Modify.
X: A=NTFS Full Control: with the SMB Share Reader role, every NTFS level up to Full yields read access only, because the share level stays restrictive.
C=Reader role: Reader is a control-plane role for viewing the account; it grants no data access and permissions are never merged upward.
D=Storage Blob Data Contributor: that role covers blob data, not SMB access to Azure file shares.
T: Azure Files enforces the more restrictive of share-level RBAC and NTFS permissions; raise the share-level role when NTFS already allows the action.
