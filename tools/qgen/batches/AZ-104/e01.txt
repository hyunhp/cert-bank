@ Q006710 explain
G: ## Two records per custom domain
Mapping a custom domain to App Service needs two DNS records at the domain provider:
- a **mapping record** that sends traffic to the app
- a **TXT verification record** named `asuid` (for the root) or `asuid.<subdomain>`, holding the app's **domain verification ID**. It proves ownership and protects against subdomain takeover; Microsoft says it is not strictly required but highly recommended.
## Root domain versus subdomain
- **`fabrikam.com`**: mapping record: A `@` to the app's IP; verification record: TXT `asuid`
- **`www.fabrikam.com`**: mapping record: CNAME `www` to `<app>.azurewebsites.net`; verification record: TXT `asuid.www`
DNS does not allow a CNAME at the zone apex (RFC 1912), so a root domain uses an A record. Subdomains should use a CNAME because the app's IP address can change.
The plan must be a paid tier (not Free F1), and the domain must be in a public DNS zone.
W: A=A record at @: the root domain cannot be a CNAME, so it maps to the app's IP address with an A record.
E=TXT asuid: App Service reads the `asuid` TXT record to verify that you own fabrikam.com before it accepts the domain.
X: B=TXT asuid.www: this name verifies the www subdomain, not the root domain, so it does not prove ownership of fabrikam.com.
C=MX record: MX records route email to mail servers. App Service does not use them for mapping or verification.
D=CNAME at @: a CNAME at the root conflicts with the zone's other apex records and is not used for root domains; Microsoft recommends an A record there.
T: A root domain needs an A record at `@` plus a TXT record `asuid`; a subdomain needs a CNAME plus `asuid.<subdomain>`.

@ Q006712 explain
G: ## Automatic and custom backups
App Service has two backup types (Basic, Standard, Premium and Isolated tiers):
- **Configuration**: Automatic: none; Custom: storage account and container
- **Frequency**: Automatic: hourly, fixed; Custom: on demand or scheduled (every 2 hours at most often)
- **Retention**: Automatic: 30 days, not configurable; Custom: 0-30 days, or indefinite
- **Downloadable**: Automatic: no; Custom: yes, as blobs in your storage account
- **Size**: Automatic: 30 GB; Custom: 10 GB
Each custom backup is a ZIP file plus an XML manifest in the container; the team can download these blobs or copy them to an archive. On-demand custom backups are kept indefinitely.
## Retention beyond 30 days
The custom retention setting accepts 0-30 days or indefinite; there is no 90-day value. To keep backups for 90 days, set retention to indefinite and remove backups older than the policy requires (for example with a storage lifecycle rule or a cleanup job).
## Example
**Backups** > **Configure custom backups** > storage account `stwebbackup`, container `app-backups` > **Set schedule** with a monthly frequency and retention set to indefinite, so no backup is deleted before 90 days. Custom backups need SAS-based access to the storage account; managed identity is not supported.
W: Custom scheduled backups with indefinite retention: they are written to the team's own storage account, are not deleted after 30 days and are downloadable as blobs, which meets both requirements.
X: A=Longer automatic retention: automatic backup retention is fixed at 30 days and the backups are not downloadable.
B=Restore into a slot: a slot is a live app, not a retained point-in-time copy, and it holds only the latest restore, not 90 days of history.
C=Premium tier: automatic backups behave the same in every supported tier: 30-day retention and no download. A higher tier does not change that.
T: Automatic backups are hourly, kept 30 days and not downloadable; for longer retention or downloadable copies, configure custom backups to a storage account (retention 0-30 days or indefinite).

@ Q006714 explain
G: ## Inbound and outbound are separate features
App Service networking features each work in one direction:
- App calls resources in or through a VNet (outbound): **Virtual network integration**
- Clients reach the app privately (inbound): **Private endpoint**
- Filter who may call the app (inbound): **Access restrictions** (IP, service tag, VNet via service endpoints)
## Virtual network integration
- Available in Basic, Standard, Premium (v2/v3/v4) and Elastic Premium.
- Needs a **dedicated subnet** in the same region, delegated to `Microsoft.Web/serverFarms`; each plan instance uses one IP. Microsoft suggests sizing for double the maximum scale (a `/26` covers a multitenant plan's maximum).
- Private (RFC 1918) traffic goes into the VNet; with outbound internet traffic routing enabled, all outbound traffic does.
- It gives no inbound access; the app stays public unless you change that.
## Example
`az webapp vnet-integration add --name app-orders --resource-group rg-web --vnet vnet-prod --subnet snet-appsvc-int`, then the app calls `http://10.20.1.4/api`.
W: Virtual network integration: it mounts interfaces from the delegated subnet on the app's workers, so calls to 10.20.1.4 travel inside vnet-prod while inbound internet access to the app is unchanged.
X: A=IP-based SSL: a dedicated inbound IP for a TLS binding does not create any network path from the app to a private address.
B=Private endpoint: a private endpoint is used only for incoming traffic to the app; outgoing calls do not use it, so the VM is still unreachable.
D=Virtual Network access restriction: access restrictions filter requests coming into the app. They do not give the app a route into the VNet.
T: VNet integration is for the app's outbound calls into a VNet; private endpoints are for private inbound access to the app.

@ Q006784 explain
G: ## Where each kind of role can be scoped
- **Manage**: Azure roles: Azure resources; Microsoft Entra roles: directory objects (users, groups, apps)
- **Scopes**: Azure roles: management group, subscription, resource group, resource; Microsoft Entra roles: tenant, administrative unit, individual object
User Administrator is a **Microsoft Entra role**. Users are directory objects; they do not live inside a subscription or resource group, so Azure scopes do not apply to them.
## Administrative units
An **administrative unit** is a container in Microsoft Entra ID that restricts a role's permissions to the users, groups or devices you place in it. Learn's own example is delegating help desk work to regional support staff so they manage only users in their region. Administrators scoped to an administrative unit need a Microsoft Entra ID P1 license.
## Example
Create an administrative unit `AU-Busan`, add the Busan users to it, and assign the lead **User Administrator** scoped to `AU-Busan`.
W: Administrative unit scope: Entra roles can be scoped to an administrative unit, which limits User Administrator to the users placed in that unit.
X: A=Subscription scope: subscriptions are Azure resource scopes used by Azure roles. Users do not belong to subscriptions, and Entra roles cannot be assigned there.
B=Resource group scope: resource groups hold Azure resources only; Entra roles such as User Administrator are never assigned at that level.
D=Management group scope: management groups organize subscriptions for Azure RBAC and Azure Policy; they cannot scope a Microsoft Entra role.
T: Azure roles are scoped to management groups, subscriptions, resource groups or resources; Entra roles to the tenant, administrative units or single objects.

@ Q006795 explain
G: ## The privileged administrator roles
Learn groups these built-in roles as privileged:
- **Owner**: manage resources: yes (`*`); assign roles: yes
- **Contributor**: manage resources: yes (`*` minus Authorization writes); assign roles: no
- **User Access Administrator**: manage resources: no (`*/read` only); assign roles: yes (`Microsoft.Authorization/*`)
- **Role Based Access Control Administrator**: manage resources: no (`*/read` only); assign roles: yes (role assignment write and delete)
Reader has `*/read` only and can view role assignments, but not change them.
## Choosing between the two access roles
- **User Access Administrator** manages all of `Microsoft.Authorization`, which also includes things such as locks and policy assignments.
- **Role Based Access Control Administrator** is narrower: only role assignments, plus support tickets. It also supports conditions to limit which roles and principals she can assign, which Microsoft recommends for least privilege.
W: A=User Access Administrator: it grants `Microsoft.Authorization/*` with only read access to resources, so she can manage role assignments but not change resources.
E=Role Based Access Control Administrator: it grants role assignment write and delete with `*/read`, the least privileged built-in way to manage access without managing resources.
X: B=Contributor: Contributor manages every resource and its NotActions exclude role assignment writes, so it fails both requirements.
C=Reader: Reader can see role assignments but cannot create or remove them.
D=Owner: Owner can assign roles but also create, change and delete every resource, which the requirement forbids.
T: To manage access without managing resources, use User Access Administrator or the narrower Role Based Access Control Administrator.
