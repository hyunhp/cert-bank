# AZ-104 D2 T2.2 Configure and manage storage accounts: account settings, redundancy changes and failover,
# object replication, encryption (customer-managed keys, encryption scopes, infrastructure encryption), AzCopy

@ AZ-104 D2 T2.2 applied troubleshooting
S: An administrator created a Standard general-purpose v2 account for a telemetry app. The app now needs consistently low latency for many small block blob writes, so the team asks to switch the account to premium performance. What should the administrator do?
A: Create a premium block blob account and copy the data with AzCopy, because an account's type can't be changed after creation
B: Open the account's Configuration blade and change Performance from Standard to Premium, then wait for the change to finish
C: Start a redundancy conversion to ZRS, because a conversion moves the account onto the premium solid-state storage tier
D: Run `az storage account update --set kind=BlockBlobStorage` to upgrade the existing account in place without copying data
K: A
G: ## Account type is fixed at creation
Learn lists the recommended storage account types: **Standard general-purpose v2** (blobs, files, queues, tables) and three premium types that run on solid-state drives: **premium block blobs**, **premium file shares** and **premium page blobs**. Premium block blob accounts are meant for high transaction rates, smaller objects and consistently low latency.
The overview page states it plainly: you can't change a storage account to a different type after it's created. To move data to another type, you create a new account and copy the data.
## Moving the data
- AzCopy copies between accounts with server-to-server APIs, so the data goes directly between storage servers.
- Premium block blob accounts don't support access tiers, so Learn says to add `--s2s-preserve-access-tier=false` when copying into one.
- Storage Explorer can also copy data, but for large transfers AzCopy is the scripted, resumable choice.
## Example
`azcopy copy 'https://stdacct.blob.core.windows.net/telemetry' 'https://premacct.blob.core.windows.net/telemetry' --recursive --s2s-preserve-access-tier=false`, then point the app at the new account.
W: New premium account and copy: the account type, including standard versus premium performance, is set when the account is created and can't be changed, so the only path is a new premium block blob account plus a data copy.
X: B=Change Performance in Configuration: performance isn't an editable setting on an existing account. Standard and premium are different account types, and the type is fixed at creation.
C=Redundancy conversion to ZRS: a conversion changes only how copies are spread across availability zones. The account stays a standard general-purpose v2 account on the same performance tier.
D=Update kind in place: the documented in-place `kind` change upgrades general-purpose v1 or ZRS Classic accounts to `StorageV2`. There is no in-place change from a standard account to a premium block blob account.
T: A storage account's type and performance tier are fixed at creation; to change them, create a new account and copy the data (for example with AzCopy).
V: Azure Storage, AzCopy

@ AZ-104 D2 T2.2 advanced tradeoff
S: An analytics team asks an administrator to enable a hierarchical namespace on an existing general-purpose v2 account that holds production blob data, so Spark jobs can rename directories atomically. Which TWO statements should the administrator include in the change plan? (Select TWO)
A: The upgrade is one-way, so the account can't be turned back to a flat namespace afterward
B: Write operations are disabled while the upgrade runs, so a maintenance window is needed
C: The upgrade can be undone from the portal within 30 days if an application stops working
D: Hadoop jobs that use the WASB driver keep working unchanged and never need the ABFS driver
E: Existing object replication policies keep replicating blobs after the namespace is enabled
K: A,B
G: ## What the hierarchical namespace changes
A hierarchical namespace (the core of Azure Data Lake Storage) turns virtual folders into real directory objects. Renaming or deleting a directory becomes a single operation instead of copying and deleting every blob under a name prefix, which is why Spark and Hive jobs run faster.
You can enable it when creating an account or **upgrade** an existing account. Learn lists what to plan for:
- **One-way**: there's no way to revert the account once the upgrade is done; Microsoft recommends validating in a nonproduction environment first.
- **Downtime**: write operations are disabled during the upgrade. Reads aren't blocked, but Microsoft strongly recommends suspending them too.
- **Drivers**: Hadoop workloads that use the WASB driver must move to the ABFS driver, which calls the Data Lake Storage endpoint (`dfs.core.windows.net`).
- **Feature support**: some Blob Storage features aren't supported with a hierarchical namespace; object replication, for example, isn't supported on accounts that have one.
W: A=One-way upgrade: Learn states there's no way to revert the account after the upgrade, so the plan needs testing on a nonproduction copy first.
B=Writes disabled: write operations are disabled during the upgrade and reads should be paused as well, so the change needs a maintenance window.
X: C=Undo within 30 days: there is no rollback period. Once the namespace is enabled, the account can't return to a flat namespace.
D=WASB keeps working: Learn says Hadoop workloads that use the WASB driver must be changed to the ABFS driver, which talks to the Data Lake Storage endpoint.
E=Object replication continues: Learn states object replication isn't supported in accounts that have a hierarchical namespace, so those policies stop being an option after the upgrade.
T: Enabling a hierarchical namespace on an existing account is irreversible and blocks writes while it runs; check drivers and unsupported features first.
V: Azure Data Lake Storage, Azure Blob Storage

@ AZ-104 D2 T2.2 applied troubleshooting
S: A security baseline turned on Secure transfer required for an account. Since then, a legacy script that uploads nightly reports with a valid SAS to `http://contosorpt.blob.core.windows.net/reports` fails on every request. What should the administrator change to fix it without weakening the baseline?
A: Change the script's URL to `https://`, because the account now rejects every REST request that arrives over plain HTTP
B: Lower the account's minimum TLS version to TLS 1.0, because the script's older TLS library can't negotiate TLS 1.2
C: Allow anonymous blob access on the account, because the SAS is ignored for requests that are sent without encryption
D: Add the server's public IP to the storage firewall, because secure transfer also blocks traffic from unlisted networks
K: A
G: ## Secure transfer required
The **Secure transfer required** property (`enableHttpsTrafficOnly` in the API) makes the account accept REST requests only over secure connections. Any request made over HTTP is rejected, whatever credential it carries. Learn recommends requiring secure transfer for all accounts, and it's enabled by default for new accounts.
- It applies to Blob, Data Lake Storage, Queue and Table requests; Azure Files has its own encryption-in-transit settings that interact with it.
- It is separate from the **minimum TLS version** setting, which matters only once a client is already using HTTPS.
- It is also separate from the network firewall, which filters by source network.
## Example
`http://contosorpt.blob.core.windows.net/reports?sv=...` is rejected; the same SAS on `https://contosorpt.blob.core.windows.net/reports?sv=...` succeeds.
W: Switch the script to HTTPS: with secure transfer required, every HTTP request is rejected regardless of the SAS. Using the `https://` endpoint fixes the script and keeps the baseline in place.
X: B=Lower minimum TLS: the script isn't using TLS at all; it sends plain HTTP. Lowering the TLS floor would weaken the account and still leave HTTP requests rejected.
C=Allow anonymous access: anonymous access doesn't bypass secure transfer, and it would expose data publicly. The SAS isn't the problem; the protocol is.
D=Firewall rule: secure transfer checks the protocol, not the caller's network. A firewall rule doesn't make an HTTP request acceptable.
T: Secure transfer required rejects every HTTP request; the fix is to use HTTPS, not to loosen TLS, network or anonymous access settings.
V: Azure Storage

@ AZ-104 D2 T2.2 applied use-case
S: An account was created years ago by a script that never set its minimum TLS version. The administrator must enforce TLS 1.2 but first wants to know which client applications still connect with an older TLS version. What should the administrator do?
A: Send the blob resource logs to a Log Analytics workspace with a diagnostic setting, then query the `TlsVersion` field
B: Add a Transactions metric in Metrics Explorer filtered on Authentication equals Anonymous to list the older clients
C: Review the account's activity log, which records the TLS version and caller IP of every read and write request
D: Connect with Storage Explorer and open the account's properties, which show the TLS versions that clients used
K: A
G: ## Detect before you enforce
Setting a **minimum TLS version** makes the account fail any request that uses an older version. When an account is created with PowerShell, the Azure CLI or an ARM template, the property isn't set unless you set it; the portal sets TLS 1.2 by default for new accounts.
Learn's recommended order is detect, remediate, then enforce:
- Create a **diagnostic setting** that sends Azure Storage resource logs (for example `StorageBlobLogs`) to a Log Analytics workspace.
- After an interval, query the logs. Each entry includes `TlsVersion`, the caller IP address and the user agent, which identify the clients to update.
- When old-TLS traffic is gone or acceptable to fail, set `MinimumTlsVersion` to `TLS1_2`.
## Example
`StorageBlobLogs | where TimeGenerated > ago(7d) and TlsVersion != "TLS 1.2" | project TlsVersion, CallerIpAddress, UserAgentHeader`
W: Resource logs in Log Analytics: storage resource logs record the TLS version, caller IP and user agent of each request, so a query shows exactly which clients still use an older version before enforcement starts.
X: B=Anonymous transactions metric: that metric filter is Learn's method for finding anonymous requests before disallowing anonymous access. It counts requests and says nothing about TLS versions.
C=Activity log: the activity log records control-plane operations such as changing account settings. It doesn't log individual data requests or their TLS version.
D=Storage Explorer properties: Storage Explorer browses and manages data with your own credentials. It doesn't show which TLS versions other clients used.
T: Before enforcing a minimum TLS version, send storage resource logs to Log Analytics and query `TlsVersion` to find clients that still need updating.
V: Azure Storage, Azure Monitor, Log Analytics

@ AZ-104 D2 T2.2 applied troubleshooting
S: A public product catalog loads images from a blob container whose anonymous access level was set to Blob two years ago. This morning every image request without credentials started failing, but no one changed the container. The security team made an account-level change overnight. What explains the failures?
A: Allow Blob anonymous access was disabled on the account, and that account setting overrides the container access level
B: The Blob access level permits anonymous listing of the container but not reading individual blobs without a SAS
C: Secure transfer was enabled, and anonymous requests are always rejected when the account accepts only HTTPS
D: The minimum TLS version was raised to 1.2, and anonymous requests can only be negotiated over an older TLS version
K: A
G: ## Two settings control anonymous reads
Anonymous read access to blob data depends on two separate settings:
- **Account setting**: Allow Blob anonymous access (`AllowBlobPublicAccess`). New Azure Resource Manager accounts disallow anonymous access by default.
- **Container access level**: Private (default), Blob, or Container.
Learn's table: when anonymous access is disallowed for the account, no container accepts anonymous requests, whatever its own level says. The account setting overrides the container setting. Containers that were already configured for anonymous access stop accepting anonymous requests, and users can't configure new ones.
## Container levels when the account allows it
- **Blob**: anonymous clients can read blobs but can't list the container.
- **Container**: anonymous clients can read blobs and list the container.
## Example
Before disallowing anonymous access, Learn recommends a Metrics Explorer chart of Transactions filtered on `Authentication = Anonymous` and storage logs to find which containers are read anonymously, so a catalog like this one is found first.
W: Account setting overrides the container: disallowing anonymous access on the account makes every anonymous request fail, even for containers that still show the Blob level, which matches a failure with no container change.
X: B=Blob level reversed: the Blob level is the opposite. It allows anonymous reads of blobs and blocks listing the container, so image URLs worked until the account setting changed.
C=Secure transfer: secure transfer rejects plain HTTP requests, not anonymous ones. An anonymous request over HTTPS is still allowed when both anonymous settings permit it.
D=Minimum TLS raised: the TLS floor applies the same way to anonymous and authorized requests. Modern browsers use TLS 1.2 or later, so this wouldn't break all image loads.
T: Anonymous blob reads need both the account setting and the container level; disallowing it at the account overrides every container.

@ AZ-104 D2 T2.2 advanced use-case
S: An administrator must move a Standard general-purpose v2 account from LRS to GZRS. Applications must keep reading and writing during the change, and the region supports customer-initiated conversion. Which approach meets the requirement?
A: Change the account to GRS with the portal or `az storage account update --sku`, then start a conversion to GZRS as a separate step
B: Run one `az storage account update --sku Standard_GZRS` command, which adds zone and geo redundancy together in a single operation
C: Create a GZRS account, copy all data with AzCopy, then repoint the applications, because LRS accounts can't be converted in place
D: Initiate a planned failover to the secondary region, which recreates the account as GZRS while the applications keep running
K: A
G: ## Two kinds of redundancy change
Learn separates redundancy changes by what they touch:
- **Geo-redundancy or read access** (LRS to GRS, GRS to RA-GRS): change the SKU in the portal (**Data management > Redundancy**), with `Set-AzStorageAccount -SkuName` or `az storage account update --sku`.
- **Zone-redundancy** (LRS to ZRS, GRS to GZRS): a **conversion**, started from the same portal page, with `Start-AzStorageAccountMigration` or `az storage account migration start`.
A change that involves zone-redundancy must be done separately from a geo change, as a two-step process in either order. After a zone conversion, wait at least 24 hours before changing redundancy again.
## Conversion versus manual migration
- A conversion has no data loss and no application downtime; it typically begins within 72 hours, and there's no SLA for when it completes.
- A **manual migration** (new account plus a copy with AzCopy) gives control over timing but can cause downtime.
## Example
`az storage account update -n contosodata -g rg-data --sku Standard_GRS`, then `az storage account migration start --account-name contosodata -g rg-data --sku Standard_GZRS`.
W: Add geo, then convert for zones: LRS to GZRS changes both aspects, so one step adds geo-redundancy through a SKU update and the other is a zone conversion. A conversion keeps the account online, which meets the read-and-write requirement.
X: B=One SKU update: a SKU update handles geo and read-access changes only. Adding zone-redundancy needs a conversion, so the change can't be done in one combined command.
C=Manual migration: a manual migration is supported, but it requires downtime when applications switch accounts. Standard general-purpose v2 accounts do support conversion, so the copy isn't necessary.
D=Planned failover: a failover swaps the primary and secondary regions for disaster recovery testing. It doesn't change the redundancy type, and the account must already be geo-redundant.
T: Geo and read-access changes are SKU updates; zone changes are conversions; LRS to GZRS takes both steps, done separately, with no downtime.
V: Azure Storage

@ AZ-104 D2 T2.2 advanced troubleshooting
S: An LRS general-purpose v2 account holds active blobs in the Hot tier plus several thousand older blobs in the Archive tier. The administrator tries to convert it to ZRS and the change can't proceed. What must be done first?
A: Move the archived blobs to an account whose redundancy supports the Archive tier, then convert the source account to ZRS
B: Enable a hierarchical namespace on the account, because ZRS conversion is supported only for Data Lake Storage accounts
C: Wait 24 hours after the last blob was archived, because conversions are blocked while new Archive tier writes are pending
D: Disable blob versioning on the account, because ZRS stores only current versions and can't hold earlier blob versions
K: A
G: ## Access tiers limit redundancy choices
The Archive tier isn't supported for **ZRS, GZRS or RA-GZRS** accounts. Before changing redundancy, Learn says to check that the target option supports the access tiers the account already uses.
- To convert an LRS, GRS or RA-GRS account to a zone-redundant option, first move the archived blobs to a storage account that supports the Archive tier, then convert.
- An LRS account with archived blobs can move to GRS or RA-GRS only after the archived blobs are rehydrated to Hot or Cool, or through a manual migration.
- Rehydration is costly and slow, so Learn recommends a manual migration that rehydrates only the data you need when such a change is unavoidable.
## Other conversion blockers worth knowing
- NFSv3 enabled for Blob Storage blocks conversions.
- An account used for VM boot diagnostics makes conversions that add zone-redundancy fail until boot diagnostics is disabled on it.
W: Move the archived blobs out: ZRS doesn't support the Archive tier, so the archived blobs must first go to an account whose redundancy supports Archive, after which the conversion can run.
X: B=Enable hierarchical namespace: standard general-purpose v2 accounts support conversion with or without a hierarchical namespace. The namespace has nothing to do with the Archive tier limitation.
C=Wait 24 hours: the 24-hour wait applies after a zone-redundancy conversion, before the next redundancy change. Archived blobs keep blocking ZRS no matter how long you wait.
D=Disable versioning: blob versioning isn't among the documented conversion blockers. The blocker is the access tier of the archived blobs, not their versions.
T: ZRS, GZRS and RA-GZRS don't support the Archive tier, so archived blobs must leave the account before a zone-redundancy conversion.
V: Azure Blob Storage

@ AZ-104 D2 T2.2 applied comparison
S: A company's GRS general-purpose v2 account serves an order system. Both regions are healthy, and auditors want a disaster recovery drill that makes the secondary region primary without expected data loss and keeps the account geo-redundant afterward. Which failover type fits?
A: Customer-managed planned failover, which swaps the primary and secondary regions while both endpoints stay available
B: Customer-managed unplanned failover, which promotes the secondary and keeps a geo-redundant copy in the old primary
C: Microsoft-managed failover requested through a support ticket for this one storage account during a planned window
D: A redundancy conversion from GRS to RA-GRS, which moves the primary endpoint to the secondary region for testing
K: A
G: ## Three failover types for geo-redundant accounts
Learn lists three kinds of failover for GRS, RA-GRS, GZRS and RA-GZRS accounts:
- **Customer-managed planned failover**: for disaster recovery testing or getting ahead of a large event. Both regions must be available. The regions swap roles, no data loss is expected, and geo-redundancy is retained (a GZRS account runs as GRS while failed over and returns to GZRS after failback).
- **Customer-managed (unplanned) failover**: for an outage of the primary endpoints. Data written after the last sync time can be lost, the copy in the original primary region is deleted, and the account becomes **LRS** in the new primary until you re-enable geo-redundancy (which incurs a replication charge).
- **Microsoft-managed failover**: initiated only for an entire region in extreme circumstances. It can't be started for an individual account, subscription or tenant, and Learn says not to rely on it for DR plans.
## Example
An auditor's drill: start a planned failover, validate the app in the new primary, then fail back; the account is GRS throughout.
W: Planned failover: built for drills while both regions are up; it swaps the regions, expects no data loss and keeps geo-redundancy, matching every audit requirement.
X: B=Unplanned failover: it's meant for a primary outage, can lose recent writes, deletes the copy in the original primary and leaves the account LRS, so geo-redundancy is lost.
C=Microsoft-managed failover: Microsoft initiates it only for a whole region in extreme cases, and it can't be requested for a single storage account.
D=Conversion to RA-GRS: adding read access only exposes a read-only secondary endpoint. It never makes the secondary region primary for writes.
T: For DR drills with both regions healthy, use customer-managed planned failover: no expected data loss and geo-redundancy is kept.

@ AZ-104 D2 T2.2 applied troubleshooting
S: A reporting app is configured to read from `contosodata-secondary.blob.core.windows.net` using the account's access key, so reports keep working during a primary outage. Requests to that host fail, while the primary endpoint works. The account's redundancy is GRS. What should the administrator change?
A: Change the account's redundancy to RA-GRS so the secondary endpoint accepts read requests with the existing access keys
B: Generate a separate access key for the secondary region, because the secondary endpoint doesn't accept the primary keys
C: Start a customer-managed failover so that the secondary region's endpoint becomes readable for the reporting app
D: Convert the account to GZRS, because the secondary endpoint is available only when the primary region uses zones
K: A
G: ## Geo-redundant is not the same as readable
With **GRS** or **GZRS**, data is copied asynchronously to the secondary region, but that copy isn't readable or writable unless a failover happens.
With **RA-GRS** or **RA-GZRS**, the secondary is always available for reads:
- The secondary endpoint adds `-secondary` to the account name, for example `contosodata-secondary.blob.core.windows.net`.
- The account access keys are the same for the primary and secondary endpoints.
- The secondary can lag behind the primary; the **Last Sync Time** property shows how current it is.
## Changing it
GRS to RA-GRS is a geo/read-access change, done in the portal's Redundancy page or with `az storage account update --sku Standard_RAGRS`; no conversion is needed. Azure Files doesn't support RA-GRS or RA-GZRS.
W: Enable read access: only RA-GRS or RA-GZRS exposes the `-secondary` endpoint for reads, and it accepts the same keys, so changing the SKU makes the app's configuration work as designed.
X: B=Separate secondary key: there's no secondary-only key. Learn states the access keys are the same for the primary and secondary endpoints.
C=Customer-managed failover: a failover makes the secondary the new primary through DNS updates. It's a disaster recovery action, not a way to enable read-only access, and an unplanned one would also drop geo-redundancy.
D=Convert to GZRS: GZRS still keeps the secondary unreadable without a failover. Read access comes from the RA- options, not from zones in the primary.
T: GRS and GZRS secondaries can't be read until a failover; RA-GRS and RA-GZRS expose a `-secondary` endpoint that uses the same keys.

@ AZ-104 D2 T2.2 applied definition
S: An administrator is setting up object replication of block blobs from a general-purpose v2 account in East US to one in West Europe. Before creating the replication policy, which TWO settings must be enabled? (Select TWO)
A: Blob versioning on both the source account and the destination account
B: Change feed on the source account so changes can be read for replication
C: A hierarchical namespace on the destination account to hold the replicas
D: Change feed on the destination account only, so it can request new blobs
E: Container soft delete on both accounts to protect the replicated blobs
K: A,B
G: ## How object replication works
Object replication asynchronously copies block blobs from a container in a source account to a container in a destination account. Azure Storage periodically reads the source account's **change feed** and replays writes and deletes to the destination.
## Prerequisites from Learn
- **Change feed**: enabled on the source account.
- **Blob versioning**: enabled on both the source and the destination accounts. While a policy is in effect, versioning can't be disabled.
- Both accounts must be general-purpose v2 or premium block blob accounts; only block blobs are replicated.
- Accounts with a hierarchical namespace aren't supported.
- Configuring a policy requires the Azure Resource Manager **Contributor** role at the account scope or higher.
## Policies and rules
The policy is created on the destination account (policy ID `default`, so Azure assigns one) and then associated with the source using that same policy ID. Each rule maps one source container to one destination container and can filter by prefix.
W: A=Versioning on both accounts: object replication requires blob versioning on the source and the destination so current and previous versions can be replicated.
B=Change feed on the source: the service reads the source account's change feed to find the writes and deletes it must replicate.
X: C=Hierarchical namespace: object replication isn't supported on accounts that have a hierarchical namespace, so enabling it would block the policy.
D=Change feed on the destination only: the change feed is required on the source, where the changes happen. Enabling it only on the destination doesn't satisfy the prerequisite.
E=Container soft delete: soft delete is a useful data protection feature but isn't a prerequisite for object replication.
T: Object replication needs blob versioning on both accounts and change feed on the source, and doesn't work with a hierarchical namespace.

@ AZ-104 D2 T2.2 advanced troubleshooting
S: An administrator created an object replication policy for the container `invoices`. Invoices uploaded after the policy appear in the destination within minutes, but about two million invoices uploaded last year, all in the Hot tier, never show up there. What should the administrator change?
A: Edit the replication rule's copy scope so it includes existing blobs, because by default a rule copies only new blobs
B: Enable change feed on the destination account, because older blobs are read from the destination's change feed
C: Set AllowCrossTenantReplication to true on both accounts, because older blobs are replicated as cross-tenant copies
D: Turn on blob versioning on the source account, because existing blobs need a version ID before they can be copied
K: A
G: ## What a new rule copies
A replication rule pairs one source container with one destination container. Learn states that after you create a rule, preexisting blobs are ignored: by default only block blobs added after the rule is created are copied.
You can change that per rule:
- copy both new and existing block blobs, or
- copy blobs created after a chosen time (a custom copy scope).
In a policy definition file this is the `minCreationTime` filter; Learn's example to replicate all blobs sets it to `1601-01-01T00:00:00Z`.
## Other replication behavior to remember
- The destination container is read-only for writes while the rule is active (writes fail with 409 Conflict).
- Blobs in the Archive tier, blobs written with a customer-provided key, and immutability policies on the destination can make replication fail.
W: Include existing blobs: the default scope copies only blobs created after the rule, which explains why last year's invoices are missing; widening the copy scope to existing blobs replicates them.
X: B=Change feed on destination: the change feed is read on the source account, and new invoices already replicate, so the prerequisites are in place.
C=Cross-tenant replication: that property only matters when the accounts are in different Microsoft Entra tenants. Nothing about a blob's age makes it a cross-tenant copy.
D=Versioning on the source: versioning is a prerequisite for creating the policy at all, so it's already enabled. New uploads replicating proves the prerequisites are met.
T: A new object replication rule ignores existing blobs by default; set its copy scope to include them (or an earlier `minCreationTime`).

@ AZ-104 D2 T2.2 advanced use-case
S: An administrator is creating a new storage account that must use a customer-managed key in an existing Azure Key Vault that uses the Azure RBAC permission model. Which TWO steps are required? (Select TWO)
A: Enable purge protection on the key vault, in addition to soft delete
B: Give a user-assigned managed identity Key Vault Crypto Service Encryption User on the vault
C: Use the new account's system-assigned identity, assigning it Key Vault Administrator first
D: Move the key vault into the same region and subscription as the new storage account
E: Generate an elliptic curve (EC) P-256 key in the vault and select it for encryption
K: A,B
G: ## How customer-managed keys work
Azure Storage always encrypts data at rest with 256-bit AES. By default the account key is protected by **Microsoft-managed keys**. With a **customer-managed key**, Azure Storage wraps the account's root encryption key with your key in Azure Key Vault (or Managed HSM), and calls the vault to unwrap it for reads and writes.
## Requirements from Learn
- The vault must have **soft delete** and **purge protection** enabled. Soft delete is on by default for new vaults; purge protection must be turned on.
- The key must be **RSA or RSA-HSM**, size 2048, 3072 or 4096.
- A managed identity needs at least `get`, `wrapkey` and `unwrapkey` on the key; with the RBAC model, assign **Key Vault Crypto Service Encryption User** scoped to the vault.
- At account creation you must use a **user-assigned** managed identity (the account doesn't exist yet, so it has no system-assigned identity). For an existing account, either type works.
- The vault and account can be in different regions, subscriptions and even Microsoft Entra tenants.
## Revoking access
Disabling the key makes data reads and writes fail with 403 for all users until access to the key is restored.
W: A=Purge protection: customer-managed keys for Azure Storage require both soft delete and purge protection on the vault, so a deleted key can't be purged while data depends on it.
B=User-assigned identity with the encryption role: a new account must use a user-assigned managed identity, and Key Vault Crypto Service Encryption User grants it the key permissions encryption needs.
X: C=System-assigned identity with Key Vault Administrator: a system-assigned identity can be used only for existing accounts, and Key Vault Administrator is a broad management role rather than the minimum key-use role.
D=Same region and subscription: Learn states the vault and the account can be in different regions, subscriptions and tenants.
E=EC P-256 key: customer-managed keys for Azure Storage must be RSA or RSA-HSM keys of 2048, 3072 or 4096 bits.
T: For customer-managed keys at account creation: vault with soft delete and purge protection, an RSA key, and a user-assigned identity holding Key Vault Crypto Service Encryption User.

@ AZ-104 D2 T2.2 applied use-case
S: A software vendor keeps each customer's documents in its own container in one shared storage account. Contracts now require each customer's data to be encrypted with a separate key that can be disabled independently, and uploads must never use another customer's key. What should the administrator configure?
A: An encryption scope per customer, set as the container's default scope with overrides blocked
B: Infrastructure encryption on the account, so each container gets its own layer of encryption
C: Customer-provided keys, with the administrator setting a different key on each container
D: One customer-managed key for the account, with a new key version for each container
K: A
G: ## Encryption scopes
By default a storage account is encrypted with one key scoped to the whole account. An **encryption scope** lets you manage encryption with a key scoped to a container or an individual blob, to create secure boundaries between data in the same account that belongs to different customers.
- Each scope uses a Microsoft-managed key or a customer-managed key in Key Vault; different scopes in one account can mix both.
- A container can get a **default encryption scope** when it's created. You choose whether clients may override it; with overrides prohibited, an upload with any other scope fails.
- Disabling a scope makes reads and writes that use it fail with 403 until it's re-enabled. A scope can't be deleted, and an enabled scope is billed for at least 30 days.
## Example
Scope `cust-fabrikam` with Fabrikam's customer-managed key is the default for container `fabrikam`, overrides prohibited; disabling the scope cuts off only Fabrikam's data.
W: Encryption scope per customer: each scope has its own key, a container default with overrides prohibited forces every upload into that customer's key, and each scope can be disabled on its own.
X: B=Infrastructure encryption: it adds a second, account-wide encryption layer that always uses Microsoft-managed keys. It doesn't give each customer a separate key that can be disabled.
C=Customer-provided keys: these keys are sent by the client on each read or write request and stored in the customer's own key store; they aren't set by the administrator on a container.
D=Key versions per container: an account's customer-managed key protects the whole account with its current version. Key versions are for rotation, not for separating containers.
T: Encryption scopes give containers or blobs their own keys in one account; a container default with overrides blocked enforces one customer, one key.

@ AZ-104 D2 T2.2 advanced tradeoff
S: A compliance audit requires double encryption at rest for all data in an existing general-purpose v2 account that holds blobs, queues and tables. The account was created without infrastructure encryption. What should the administrator do?
A: Create a general-purpose v2 account with infrastructure encryption enabled at creation, then move the data into it
B: Enable infrastructure encryption on the existing account's Encryption page; data written afterward is double encrypted
C: Switch the account to a customer-managed key, because combining it with service encryption counts as double encryption
D: Create an encryption scope with infrastructure encryption and make it the default scope for every blob container
K: A
G: ## Two layers of encryption
Azure Storage always encrypts data at the **service level** with 256-bit AES, using Microsoft-managed or customer-managed keys. **Infrastructure encryption** adds a second 256-bit AES layer at the infrastructure level, with a different algorithm and a separate Microsoft-managed key. This protects against one algorithm or key being compromised and is recommended mainly when compliance requires double encryption.
## When it can be set
- For an account: only when the account is created (portal Encryption tab, `--require-infrastructure-encryption` in the CLI, `-RequireInfrastructureEncryption` in PowerShell). It can't be enabled or disabled afterward. Supported for general-purpose v2, premium block blob and premium page blob accounts.
- For an encryption scope: at scope creation, even if the account doesn't use it. Encryption scopes apply to blob data only.
## Example
`az storage account create -n contosodbl -g rg-sec --kind StorageV2 --sku Standard_ZRS --require-infrastructure-encryption`, then move the blobs, queue messages and table entities.
W: New account with infrastructure encryption: the setting is fixed at account creation, and the account-wide layer covers blobs, queues and tables, so a new account plus a data move is what satisfies the audit.
X: B=Enable on existing account: Learn states infrastructure encryption can't be enabled or disabled after the account is created.
C=Customer-managed key: a customer-managed key changes who controls the service-level key; it's still one layer. Double encryption needs the separate infrastructure layer.
D=Encryption scope with infrastructure encryption: that gives double encryption only to blobs written with the scope. Queues and tables can't use encryption scopes, so they would stay single encrypted.
T: Account-level infrastructure encryption must be chosen when the account is created; for an existing account, create a new one and move the data.
V: Azure Storage

@ AZ-104 D2 T2.2 applied troubleshooting
S: An administrator holds the Owner role on a storage account. She runs `azcopy login`, signs in with her Microsoft Entra account, and runs `azcopy copy` to upload a folder to a container, but the upload fails with an authorization error. What is the most likely fix?
A: Assign her Storage Blob Data Contributor on the account or container and retry after a few minutes
B: Assign her Storage Account Contributor on the account, which adds the data upload permissions
C: Add `--recursive=true` to the command, because folder uploads without it are refused as unauthorized
D: Move the Owner assignment to the subscription scope, because AzCopy checks roles only at that scope
K: A
G: ## Management roles versus data roles
Azure RBAC separates **control-plane** roles (manage the resource: Owner, Contributor, Storage Account Contributor) from **data-plane** roles (read or write the data). Learn's AzCopy page states it directly: as an owner of a storage account, you aren't automatically assigned permissions to access data.
## Roles AzCopy needs with Microsoft Entra authorization
- Download: **Storage Blob Data Reader** (Blob Storage).
- Upload: **Storage Blob Data Contributor** or **Storage Blob Data Owner**.
- Role assignments can take up to five minutes to propagate.
- With a hierarchical namespace, ACL permissions on the target directory can be used instead of a role.
## Other ways to authorize AzCopy
- Append a **SAS token** to each source or destination URL.
- On an Azure VM, use a managed identity: `AZCOPY_AUTO_LOGIN_TYPE=MSI`, so no credentials are stored on the VM.
W: Data role for the upload: Owner only manages the resource. Storage Blob Data Contributor grants the write permissions AzCopy uses with Entra sign-in, and the new assignment can take up to five minutes to apply.
X: B=Storage Account Contributor: it's another management role for the account, not a data-plane role. It doesn't grant blob write permission to Entra-authorized requests.
C=Add recursive: `--recursive` controls whether subfolders are included. Leaving it out changes what's copied; it doesn't cause an authorization failure.
D=Owner at subscription scope: a broader scope doesn't change what Owner can do. It still lacks data actions, at any scope.
T: Owner and Contributor manage storage accounts but don't read or write data; AzCopy with Entra sign-in needs a Storage Blob Data role.
V: AzCopy, Azure Blob Storage
