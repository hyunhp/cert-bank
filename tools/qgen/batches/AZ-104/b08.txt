# AZ-104 D3 Deploy and manage Azure compute resources: T3.2 Create and configure virtual machines (18)

@ AZ-104 D3 T3.2 advanced comparison
S: An auditor requires that new Linux VMs at a logistics firm encrypt the temp disk and the OS and data disk caches at rest, and that disk data travel encrypted from the host to Azure Storage. Encryption must not use the VMs' own CPU. Which option should the administrator enable on the new VMs?
A: Encryption at host, so the VM host encrypts temp disks and caches and sends the data encrypted to storage
B: Azure Disk Encryption with a key encryption key, so DM-Crypt inside each VM encrypts every volume
C: Server-side encryption with a customer-managed key in a disk encryption set for each managed disk
D: Confidential disk encryption on a standard D-series size, so the OS disk key is bound to the VM's TPM
K: A
G: ## Four ways a managed disk can be encrypted
Azure offers several layers, and they protect different things:
- **Server-side encryption (SSE)** is always on. Azure Storage encrypts OS and data disks when it writes them to the storage clusters, with platform-managed keys or, through a **disk encryption set**, customer-managed keys. It does **not** cover the temp disk or the disk caches on the host, and data between the host and storage is not part of it.
- **Encryption at host** is a VM setting that extends SSE: the server hosting the VM encrypts the temp disk, the ephemeral OS disk and the OS/data disk caches, and the data flows encrypted to Azure Storage. It runs on the host, so it does not use the VM's CPU.
- **Azure Disk Encryption (ADE)** encrypts volumes inside the guest with BitLocker (Windows) or DM-Crypt (Linux). It uses the VM's CPU and does not work for custom Linux images. ADE is scheduled to retire on September 15, 2028, and Microsoft tells you to use encryption at host for new VMs.
- **Confidential disk encryption** binds the OS disk key to the VM's TPM and is available only on confidential VM sizes (such as DCasv5/ECasv5).
## Example
`vm-route-01` with encryption at host on: its `/dev/disk/azure/resource` temp disk and the read cache of its data disk are encrypted on the host, and writes leave the host already encrypted.
W: Encryption at host: it is the only listed option that encrypts temp disks and caches on the host, encrypts the data flow to storage and adds no load on the guest CPU; it is also Microsoft's recommended choice for new VMs.
X: B=Azure Disk Encryption: it covers temp disks and caches but encrypts inside the guest with DM-Crypt, which uses the VM's CPU, and it is scheduled for retirement in 2028.
C=Customer-managed SSE: a disk encryption set changes who controls the key for data at rest in storage, but SSE still leaves temp disks and host caches unencrypted.
D=Confidential disk encryption: it needs a confidential VM size such as DCasv5 or ECasv5 and protects the OS disk only; a standard D-series size cannot use it.
T: Temp disk and cache encryption plus encrypted data flow without guest CPU cost → encryption at host; ADE is retiring.
V: Azure Virtual Machines, Azure managed disks

@ AZ-104 D3 T3.2 advanced troubleshooting
S: An administrator deallocates a Windows VM to turn on encryption at host. The subscription already runs other VMs with encryption at host, and the VM size is on the supported list, but the change is rejected. Two years ago the VM's volumes were encrypted with BitLocker through Azure Disk Encryption and later decrypted. What is the cause?
A: Encryption at host can't be enabled on a VM that currently has, or ever had, Azure Disk Encryption enabled
B: Encryption at host requires a disk encryption set with a customer-managed key before it can be turned on
C: The EncryptionAtHost feature must be registered again for each VM before that VM can enable the setting
D: Encryption at host can be enabled only while the VM is running, because the host must read the disks
K: A
G: ## Prerequisites for encryption at host
Encryption at host is a property of the VM (`securityProfile.encryptionAtHost`). Before you can use it:
- The subscription must have the `EncryptionAtHost` feature registered for `Microsoft.Compute` (one registration per subscription, checked with `az feature show --name EncryptionAtHost --namespace Microsoft.Compute`).
- The VM size must be supported; some older sizes are not.
- An existing VM must be **deallocated** and started again to pick up the setting.
## The restriction that is easy to miss
Learn lists a hard limit: encryption at host **can't be enabled on VMs or scale sets that currently or ever had Azure Disk Encryption (ADE) enabled**, and ADE can't be enabled on disks that use encryption at host. Decrypting the volumes later does not reset that history. Microsoft publishes a separate migration procedure from ADE to encryption at host for such VMs.
## Example
`vm-fin-07`: ADE enabled in 2024, disabled in 2025 → enabling encryption at host in 2026 is still refused.
W: ADE history: the documented restriction blocks encryption at host on any VM that has ever had ADE, even after decryption, so this VM needs the ADE-to-encryption-at-host migration path instead.
X: B=Customer-managed key required: encryption at host works with platform-managed keys by default; a disk encryption set is optional and only needed when you want your own keys.
C=Per-VM feature registration: the feature is registered once per subscription, and other VMs in this subscription already use it, so registration is not the problem.
D=Must be running: it is the other way round; an existing VM must be deallocated and reallocated to be encrypted, which is exactly what the administrator did.
T: Encryption at host needs the subscription feature, a supported size and deallocation, and is blocked on any VM that ever used Azure Disk Encryption.

@ AZ-104 D3 T3.2 applied use-case
S: An administrator moves VM web01 with its NIC and managed disks from resource group rg-test to rg-prod in the same subscription. The move succeeds. Which TWO results should the administrator expect and handle? (Select TWO)
A: The resource ID of each moved resource changes, so scripts and dashboards that reference the old ID must be updated
B: A role assignment scoped to web01 doesn't move with it and must be created again at the new resource scope
C: web01 is restarted during the move, so the move must be scheduled inside an approved maintenance window
D: web01 is relocated to the region of rg-prod, so its private IP address changes after the move completes
E: The managed disks are copied, and the originals in rg-test keep incurring storage charges until deleted
K: A,B
G: ## What a resource move changes
Moving resources between resource groups (or subscriptions) changes only where the resource is **organized**, not where it runs:
- The **resource ID** contains the resource group name: `/subscriptions/{sub}/resourceGroups/rg-test/providers/Microsoft.Compute/virtualMachines/web01` becomes `.../resourceGroups/rg-prod/...`. Anything that stores the ID (dashboards, scripts, templates, alerts) must be updated.
- The **region does not change**. A resource group's location is only where its metadata lives.
- **Role assignments** on the moved resource do not move; they become orphaned and Azure later removes them. Re-create them at the new scope (Microsoft recommends removing them before the move).
- During the move both resource groups are **locked** for create, update and delete (up to four hours), but the VM keeps running with no downtime.
Child resources such as VM extensions move with their parent; you list only top-level resources in the move request.
W: A=Resource ID changes: the resource group is part of the resource ID, so every reference to the old ID breaks and must be updated after the move.
B=Role assignment left behind: Azure role assignments on a moved resource do not travel with it; the administrator must re-create them on the new resource ID.
X: C=Restart during move: the move only changes metadata; the VM keeps running and dependent services see no downtime, although its properties can't be changed until the move finishes.
D=Region change: moving a resource never changes its physical region, whatever the target resource group's location is, so networking stays the same.
E=Disks copied: the move transfers the same disk resources to the new group; nothing is duplicated and nothing is left behind in rg-test.
T: Moving a VM between resource groups keeps it running in the same region but changes its resource ID and drops its role assignments.
V: Azure Resource Manager, Azure Virtual Machines

@ AZ-104 D3 T3.2 advanced troubleshooting
S: An administrator tries to move VM app02 to another subscription in the same Microsoft Entra tenant. app02 is in rg-app, its managed disks are in rg-disks, and its virtual network is in rg-network. Validation fails. Which approach lets the move succeed?
A: Put the VM, disks, NIC and virtual network into one resource group, then move them to the new subscription together
B: Move each resource group to the new subscription separately, starting with rg-network, then rg-disks, then rg-app
C: Move only the VM, its disks and its NIC to the new subscription, then reach the old virtual network through peering
D: Create a new tenant link between the subscriptions, then retry the move of the VM alone from rg-app as before
K: A
G: ## Moving across subscriptions
A move to another subscription has extra rules on top of the resource-group move:
- Both subscriptions must be **active** and in the **same Microsoft Entra tenant**.
- The destination subscription must be registered for every resource provider being moved.
- **A resource and its dependent resources must be in the same resource group and move together.** For a VM, that means its managed disks, NICs and other dependents.
- For VMs specifically: a VM in an existing virtual network can move to a new subscription **only if the virtual network and all of its dependent resources move too**.
## The three-step pattern from Learn
1. If dependents are spread over several resource groups, move them into one resource group first (a move within the subscription).
2. Move the whole set to the target subscription in one operation.
3. Optionally redistribute them into separate resource groups in the target subscription.
## Example
`rg-app` (VM), `rg-disks` (disks), `rg-network` (VNet) → consolidate into `rg-app` → move `rg-app` contents to the new subscription → split again if wanted.
W: Consolidate, then move: Learn requires the VM, its disks and its virtual network to sit in one resource group and move in one operation, which is exactly the documented three-step pattern.
X: B=One group at a time: moving the groups separately splits the VM from its disks and network for each request, so validation fails for the same dependency reason.
C=VM only plus peering: a VM in an existing virtual network can't move to a new subscription unless the virtual network moves with it, so this move is rejected.
D=Tenant link: the subscriptions are already in the same tenant, and there is no "tenant link" setting; the failure comes from the dependents living in other resource groups.
T: For a cross-subscription VM move, put the VM, its disks, NICs and virtual network in one resource group and move them together.

@ AZ-104 D3 T3.2 advanced use-case
S: A company used Azure Resource Mover to move VM crm01 and its NIC, NSG, public IP address and virtual network from West Europe to Sweden Central, and has committed the move. crm01 ran the Azure Monitor agent extension, and partners reach it by its public IP address. Which TWO follow-up tasks are still needed? (Select TWO)
A: Install the VM extensions such as the Azure Monitor agent on the target VM, because extensions aren't copied
B: Give partners the target public IP address and update DNS, because the old public IP isn't kept across regions
C: Re-create the managed disks from snapshots in Sweden Central, because only the VM configuration is moved
D: Turn off the replication to Sweden Central manually, because it keeps running after the commit has finished
E: Run Commit a second time after deleting the source, because a commit is only final once the source is gone
K: A,B
G: ## How Resource Mover moves a VM between regions
Azure Resource Mover is a hub for moving resources across regions. For VMs it uses Azure Site Recovery replication under the covers. The flow is:
1. **Add** resources and **resolve dependencies** (NIC, virtual network, NSG and so on).
2. **Prepare**: the Site Recovery Mobility agent is installed and the VM's disks start replicating to the target region; ARM templates are generated for other resources.
3. **Initiate move**: replica VMs are created in the target; the source VM shuts down (usually minutes of downtime).
4. **Commit** (or **Discard** to roll back while testing). After commit, replication stops and the source is in *Delete source pending*.
5. Optionally **delete the source** resources.
## What does not come along
The support matrix lists settings that are not moved:
- **Extensions** are not copied; install them manually after the move.
- **Azure RBAC** assignments on the VM are not copied.
- **Public IP addresses** are region-specific and are not retained; the target gets a different address.
- The **temporary disk** is always excluded, and the boot diagnostics storage account must be re-enabled.
- The Mobility service stays installed until you remove it.
W: A=Reinstall extensions: Resource Mover does not copy VM extensions, so the Azure Monitor agent must be installed again on the target VM.
B=New public IP: a public IP address can't be carried to another region, so partners and DNS records must be switched to the target VM's new address.
X: C=Re-create disks: the Prepare step replicates the VM's disks to the target region, so the moved VM already has its OS and data disks.
D=Turn off replication: committing the move stops replication to the target region; only the Mobility service stays installed until you remove it.
E=Second commit: one commit completes the move; deleting the source afterwards is optional and is not a condition for the commit to take effect.
T: After a Resource Mover region move, reinstall extensions, re-create RBAC assignments and expect a new public IP address.
V: Azure Resource Mover, Azure Virtual Machines

@ AZ-104 D3 T3.2 advanced troubleshooting
S: A research team creates an Ubuntu VM on an NC-series GPU size with the portal defaults, which make it a Trusted launch VM with Secure Boot and vTPM enabled. Installing the NVIDIA GRID driver fails on that VM. What should the administrator change before installing the driver again?
A: Clear the Enable Secure Boot option in the VM's configuration, keeping vTPM, because the Linux GRID driver needs Secure Boot off
B: Change the security type to Confidential virtual machines, because Linux GPU drivers can load only in a confidential VM
C: Redeploy the VM from a Generation 1 image, because the GRID driver supports only BIOS-based Linux boot loaders
D: Enable encryption at host on the VM, because the GRID driver can't write to an unencrypted temp disk on Linux
K: A
G: ## Security type when you create a VM
On the **Basics** tab of the VM create page you choose the image, size, authentication and a **security type**. For Generation 2 images the portal, PowerShell and CLI create **Trusted launch** VMs by default. Trusted launch combines technologies you can turn on and off separately:
- **Secure Boot**: firmware only lets boot components (boot loader, kernel, kernel drivers) signed by trusted publishers load. Unsigned or untrusted drivers are blocked.
- **vTPM**: a virtual TPM 2.0 that stores keys and measures the boot chain for attestation.
## Where GPU drivers fit
Learn's Trusted launch article lists driver exceptions:
- CUDA and GRID drivers install on Secure Boot Windows VMs without extra steps.
- CUDA on Ubuntu needs extra steps; on other Linux distributions Secure Boot must be disabled.
- **The GRID driver requires Secure Boot to be disabled on Linux VMs.**
The Trusted launch FAQ says not to disable Secure Boot unless you use unsigned kernels or drivers, and that you do it by clearing **Enable Secure Boot** in the VM's configuration. vTPM can stay on.
W: Disable Secure Boot: Learn states the GRID driver needs Secure Boot off on Linux, and the setting is cleared in the VM configuration while the rest of Trusted launch stays in place.
X: B=Confidential VM: confidential VMs are a different security type for in-use data protection; they do not lift the Secure Boot requirement for unsigned drivers.
C=Generation 1 image: Trusted launch needs Generation 2, but the driver only needs Secure Boot off; dropping to Gen 1 loses vTPM and is not the documented fix.
D=Encryption at host: it encrypts temp disks and caches on the host and has no effect on whether a kernel driver is allowed to load.
T: On Linux Trusted launch VMs, the NVIDIA GRID driver needs Secure Boot turned off; keep vTPM and the rest of Trusted launch.

@ AZ-104 D3 T3.2 applied troubleshooting
S: A running VM must move from a D4s_v5 size to an E8s_v5 size for more memory. On the VM's Size page the E8s_v5 size doesn't appear in the list, although it is offered in that region for new VMs. What should the administrator do?
A: Stop (deallocate) the VM so that sizes from other hardware clusters in the region appear, then resize it
B: Delete the VM and create a new one, because a running VM can only move to a size of the same series
C: Move the running VM to another availability zone that has E-series hardware, then resize it there
D: Change the OS disk to Premium SSD v2 first, because memory-optimized sizes are listed only for that disk type
K: A
G: ## How resizing works
You can resize a VM whether it is running or deallocated, but:
- Resizing a **running** VM always **restarts** it, so treat it as a disruptive change.
- A running VM can only move to sizes that the **hardware cluster currently hosting it** supports. The portal's Size list for a running VM shows those sizes.
- If the size you want is not on that cluster, **stop (deallocate)** the VM. Deallocation releases the host, and the VM can then be placed on any cluster in the region that offers the new size. The portal notes that stopping the VM "may reveal more sizes".
Deallocation releases dynamic IP addresses; OS and data disks are not affected. PowerShell's `Get-AzVMSize -ResourceGroupName rg -VMName vm` lists the sizes available on the current cluster.
## Example
`vm-erp` on a cluster without E-series hardware: Size list shows only D-series → stop (deallocate) → E8s_v5 appears → resize → start.
W: Deallocate, then resize: the missing size is not available on the VM's current cluster; deallocating frees the VM from that cluster so any cluster in the region with E8s_v5 can host it.
X: B=Same series only: resizing across series is supported; there is no rule limiting a VM to its current series, and deleting it is unnecessary.
C=Change zone first: a zonal VM can't be moved to another availability zone, and the limit here is the VM's current hardware cluster, which deallocation releases.
D=Premium SSD v2 first: Premium SSD v2 can't even be an OS disk, and the disk type does not decide which memory-optimized sizes are listed.
T: If a size is missing for a running VM, deallocate it so it can land on a cluster that offers that size.

@ AZ-104 D3 T3.2 advanced troubleshooting
S: Four VMs run in availability set avset-sql. Resizing one of them to a newer size fails, and Get-AzVMSize on that VM doesn't list the new size, although the size is available in the region. What must the administrator do to resize the VM?
A: Stop (deallocate) all four VMs in the availability set, resize the VM, then start the VMs again
B: Stop (deallocate) only that VM and resize it, because the other members stay on their current cluster
C: Remove the VM from the availability set, resize it, then add it back to avset-sql when it is running
D: Increase the fault domain count of avset-sql to three, then retry the resize while the VM is running
K: A
G: ## Availability sets are tied to one cluster
An availability set spreads its VMs over fault domains (shared power and network switch) and update domains (groups restarted together during planned maintenance). To give those guarantees, all VMs of the set are allocated in the **hardware cluster that hosts the set**.
That has two consequences for resizing:
- A resize or a new VM in the set must be served by **that original cluster**. If it does not support the size or has no capacity, the request fails.
- Starting one VM after stopping only some of them is treated like adding a VM to the existing set, so it is still limited to that cluster.
## The documented fix
Stop (deallocate) **all** VMs in the availability set, resize, and start them again together. With every VM deallocated, the allocation can target any cluster in the region that supports the size. You might also need to update the other VMs' sizes.
## Other availability set rules
- A VM can join an availability set **only when it is created**; to change it, delete and re-create the VM.
- Fault and update domain counts can't be changed after the set is created.
W: Deallocate the whole set: only with every VM in the set deallocated can Azure allocate the set on a cluster that supports the new size, which is the procedure Learn gives for resizing in an availability set.
X: B=Deallocate one VM: starting one VM in a partly deallocated set still has to use the set's current cluster, which lacks the size, so the resize fails again.
C=Remove and re-add: a VM can join an availability set only at creation, so it can't be taken out and put back; that would mean deleting and re-creating it.
D=More fault domains: the fault domain count is fixed when the set is created and does not change which sizes the hosting cluster supports.
T: To resize a VM in an availability set to a size its cluster lacks, deallocate every VM in the set, resize, then start them together.

@ AZ-104 D3 T3.2 applied troubleshooting
S: An administrator expands a 512 GiB Premium SSD data disk on a running Windows Server VM to 1 TiB in the portal. The disk now shows 1 TiB in Azure, but File Explorer still shows the F: volume at 512 GiB after twenty minutes. What should the administrator do next?
A: Rescan the disks in the VM and extend the F: volume with Disk Management or DiskPart into the new space
B: Deallocate the VM and restart it, because Azure resizes the volume inside Windows only during a boot
C: Detach and reattach the data disk, because Windows reads a new disk size only when the disk is attached
D: Run the resize again with host caching set to None, because cached disks keep reporting their old size
K: A
G: ## Two layers of every disk expansion
Making a disk bigger always has two steps:
1. **Azure**: increase the managed disk size (portal **Size + performance**, `Update-AzDisk`, or `az disk update`). Shrinking is not supported.
2. **Guest OS**: extend the partition and file system into the new space. Azure never does this for you on Windows data disks.
## Expand without downtime
Eligible **data disks** can be expanded while the VM runs (portal, latest CLI/PowerShell, or ARM API 2021-04-01 or newer). Limits worth knowing:
- OS disks still need the VM deallocated.
- A Standard HDD, Standard SSD or Premium SSD of 4 TiB or less must be deallocated and detached to grow **beyond** 4 TiB.
- The host cache setting does not affect whether you can expand without deallocation.
After an online expansion the OS sees the new size only after a **rescan** (Windows Disk Management rescan, or a Linux device rescan), then you extend the volume.
## Example in Windows
`diskpart` → `list volume` → `select volume 3` → `extend`, or in Disk Management right-click F: → **Extend Volume**.
W: Rescan and extend the volume: the Azure step is done; Windows only uses the space once the disk is rescanned and the F: volume is extended into the unallocated area.
X: B=Reboot resizes the volume: deallocating is needed only for disks that can't be expanded online, and a restart never extends a Windows data volume by itself.
C=Detach and reattach: detaching is needed only to grow small disks beyond 4 TiB, and even after reattaching the F: volume stays 512 GiB until it is extended in Windows.
D=Host caching: Learn states the host cache setting does not change whether a data disk can be expanded online, and the Azure resize has already succeeded.
T: After growing a managed disk, rescan in the guest and extend the partition and file system; Azure only grows the disk itself.

@ AZ-104 D3 T3.2 applied troubleshooting
S: A build server runs on a Windows VM whose size includes a local temporary disk. A script wrote nightly build logs to drive D:. After the VM was stopped (deallocated) over the weekend and started on Monday, the logs are gone, but files on C: and the data disk E: are intact. What explains this and prevents it?
A: D: is the temporary disk, which isn't a managed disk and can lose data on deallocation; write the logs to a data disk
B: D: is a data disk with host caching set to Read/Write; set its caching to None so writes always reach the managed disk
C: D: is an ephemeral OS disk partition that resets on stop; convert the VM to a persistent OS disk to keep it
D: D: is a Standard HDD data disk that was trimmed on deallocation; convert it to Premium SSD to keep the files
K: A
G: ## The three disk roles on a VM
- **OS disk**: a managed disk with the operating system and boot volume (C: on Windows). Persistent.
- **Data disks**: managed disks you attach for applications and data, with drive letters you choose (E:, F:, ...). Persistent.
- **Temporary disk**: local storage on the physical host, **not a managed disk**. On Windows it is drive **D:** by default; on Linux it is typically `/dev/disk/azure/resource`. It is meant for page files, swap files or SQL Server `tempdb`.
## When temp disk data is lost
Data on the temporary disk can be lost during a maintenance event, when the VM is redeployed, or when it is stopped (deallocated), because the VM may come back on a different host. A normal restart keeps it. Some VM sizes have no local temp disk at all.
## The fix
Store anything you need to keep on the OS disk or, better, on a data disk, which gives backup, performance isolation and easier maintenance.
W: Temporary disk: D: is the host-local temp disk, so its contents can be lost when the VM is deallocated and reallocated, while managed OS and data disks persist; logs belong on a data disk.
X: B=Read/Write caching: host caching changes how reads and writes are cached on the host; a data disk is a persistent managed disk and is not wiped on deallocation, as E: shows.
C=Ephemeral OS disk: an ephemeral OS disk would hold the OS itself (C:), and such VMs can't be stop-deallocated at all, so it does not match this VM.
D=Standard HDD trimmed: managed disks of every type keep their data across deallocation; the disk type affects performance, not persistence.
T: Drive D: on most Windows VMs is the temporary disk; anything on it can disappear on deallocation, so keep data on managed disks.

@ AZ-104 D3 T3.2 applied comparison
S: Before a database upgrade, an administrator plans to take incremental snapshots of a VM's Premium SSD data disk every night. Which TWO statements about these snapshots are correct? (Select TWO)
A: The first incremental snapshot is a full copy, later ones store only changes, and each is billed for used size
B: Incremental snapshots use zone-redundant storage automatically when ZRS is available in the region
C: Incremental snapshots are stored on Premium SSD storage because the source disk is a Premium SSD
D: An incremental snapshot can be moved to another resource group or another subscription like a disk
E: A snapshot captures every disk attached to the VM in one coordinated, application-consistent copy
K: A,B
G: ## What a managed disk snapshot is
A snapshot is a **read-only, crash-consistent, point-in-time copy of one managed disk**. It exists independently of the disk, and you can create a new managed disk (or another snapshot) from it.
## Incremental snapshots
- The **first** incremental snapshot is a full copy; later ones contain only the **changes since the previous snapshot**. Restoring rebuilds the full disk for that point in time.
- They are billed for the **used size** only.
- They always use **Standard HDD storage**, whatever the source disk type (full snapshots can use Premium SSD).
- They use **ZRS automatically** if the region supports it, otherwise LRS.
- Snapshots of Premium SSD, Standard SSD and Standard HDD can be used right after creation.
## Restrictions
- They **can't be moved** between subscriptions or to another resource group; they can be **copied** to another resource group or region.
- Up to 500 incremental snapshots per disk at a time.
- A snapshot covers one disk; snapshots of several disks are **not coordinated**, so striped volumes need another method (for example restore points or Azure Backup).
W: A=Full then deltas, used-size billing: Learn describes the first incremental snapshot as a full copy, later ones as delta changes only, and billing on used size.
B=ZRS by default: if the region supports ZRS, incremental snapshots use it automatically, falling back to LRS where it is not available.
X: C=Premium storage: incremental snapshots always use Standard HDD storage regardless of the source disk's type; only full snapshots can be stored on Premium SSD.
D=Movable like a disk: incremental snapshots can't be moved between subscriptions or resource groups; they can only be copied to another resource group or region.
E=All disks together: a snapshot copies one managed disk and is crash-consistent; it does not coordinate several disks or guarantee application consistency.
T: Incremental snapshots: full first copy then deltas, billed by used size, Standard HDD with ZRS when available, copy rather than move.

S: VM report01 was created without an availability set. The team now wants it in the existing availability set avset-reports with two similar VMs, keeping its OS and data disks. What should the administrator do?
A: Delete report01 with its disks set to detach, then create a new VM in avset-reports that attaches the existing disks

G: ## Availability sets are chosen at creation
An availability set is a logical group that spreads VMs across **fault domains** (up to 3: shared power and network switch) and **update domains** (up to 20: groups restarted together during planned maintenance). The platform assigns these when the VM is created in the set.
Learn is explicit: **you can add a VM to an availability set only when you create it**. To add an existing VM, or to change its set, you delete and re-create the VM.
## How to do it without losing data
1. Make sure the VM's disks have **Detach** as the delete option, so deleting the VM keeps them.
2. Delete the VM.
3. Create a new VM in the availability set from the existing OS disk and attach the data disks (the Learn sample does this with PowerShell).
4. Re-add any load balancer configuration, extensions and Azure Hybrid Benefit setting as needed.
## Related limits
Fault and update domain counts are fixed once the set is created, and availability sets do not support Ultra Disks.

D=Resize into the set: resizing changes only the VM's hardware profile; maintenance events never add a VM to an availability set.

@ AZ-104 D3 T3.2 advanced troubleshooting
S: An administrator created VM vm-a in a new availability set, stopped (deallocated) it to change a setting, then created VM vm-b in the same set while vm-a was still deallocated. The availability set now shows both VMs in fault domain 0. What caused this, and how is it avoided?
A: vm-b's OS disk could be placed in vm-a's fault domain because vm-a was deallocated; don't stop VMs between deployments
B: The set was created with one fault domain by default; recreate it with three fault domains before adding VMs
C: The two VMs use different sizes, so they share one domain; use the same VM size for every VM in an availability set
D: The VMs use Standard SSD disks, which allow only one disk fault domain; convert both OS disks to Premium SSD first
K: A
G: ## Fault domains, update domains and disks
- A **fault domain** is a group of VMs that share a common power source and network switch. By default VMs in an availability set are spread across up to three fault domains.
- An **update domain** is a group restarted together during planned maintenance; only one update domain is restarted at a time, and it gets 30 minutes to recover before the next one.
- **Disk fault domains**: in a managed availability set, all managed disks of a VM are aligned with that VM's fault domain. Regions have two or three managed-disk fault domains.
## Shared fault domains
Learn describes one situation in which two VMs of a set land in the same fault domain:
1. Deploy the first VM.
2. Stop or deallocate it.
3. Deploy the second VM.
In that order, the second VM's OS disk might be created on the same fault domain as the first, so both VMs share it, and a single power or switch failure could take down both. The guidance is simple: **don't stop or deallocate VMs between deployments** into an availability set. You can check the assignment in the availability set's Fault Domain column.
W: Deallocated between deployments: this exact sequence is the documented cause of a shared fault domain, and the fix is to keep earlier VMs running while the next ones are deployed.
X: B=One fault domain by default: availability sets spread VMs across up to three fault domains by default, and the count can't be changed after creation anyway.
C=Different sizes: VM size does not decide fault domain placement; a set can contain different sizes that its cluster supports.
D=Standard SSD disk domains: the number of managed-disk fault domains depends on the region, not on the disk type, and both VMs use the same type.
T: Don't stop or deallocate VMs while you are still deploying others into an availability set, or they can end up sharing a fault domain.

@ AZ-104 D3 T3.2 advanced use-case
S: VM sql-02 was deployed as a zonal VM in availability zone 1 of a region. To balance a cluster, the team needs it in zone 2 with the same data. What is the supported approach?
A: Deploy a new VM in zone 2 from snapshots of sql-02's disks, then switch the workload over to the new VM
B: Stop (deallocate) sql-02, change its availability zone setting from 1 to 2, and start it again
C: Resize sql-02 to a size that zone 2 offers, which reallocates the VM into zone 2 automatically
D: Convert sql-02 to a nonzonal VM first, then pin the regional VM to zone 2 from its settings page
K: A
G: ## Zonal and nonzonal VMs
- A **zonal** VM is pinned to the one availability zone you choose at creation. By itself it is not resilient to that zone failing; you get zone resilience by running several VMs in different zones (or a scale set spanning zones).
- A **nonzonal (regional)** VM lets Azure place it in any zone of the region; if a zone fails, it might be in the failed zone.
There is no cost difference between the two.
## Changing the zone configuration later
The reliability guide for VMs lists what is and isn't possible:
- **Nonzonal → zonal**: supported by a move process that creates a new VM in the target zone (and a separate preview migration).
- **Zonal → a different zone**: **not supported**. Deploy a new zonal VM in the desired zone instead.
- **Zonal → nonzonal**: not supported; deploy a new nonzonal VM.
Disks follow the same logic: zonal LRS disks live in one zone, so you rebuild them in the new zone from snapshots (or use ZRS disks where supported).
W: New VM in zone 2: zonal VMs can't be moved to another availability zone, so the documented path is to deploy a new zonal VM in zone 2, here from snapshots of the existing disks, and cut over.
X: B=Edit the zone while deallocated: a zonal VM's zone can't be changed in place; Learn says to deploy a new VM in the desired zone.
C=Resize into zone 2: resizing changes the VM's size inside its current zone; it never moves a zonal VM to another zone.
D=Convert to nonzonal first: zonal VMs can't be converted to a nonzonal configuration either, so this path is unavailable.
T: A zonal VM stays in its zone for life; to change zones, deploy a new VM in the target zone (for example from disk snapshots).

@ AZ-104 D3 T3.2 applied comparison
S: A team is creating a scale set for a web tier. It wants to mix Spot and regular-priority instances, protect individual instances with Azure Backup, and manage each instance with the standard VM commands. Which configuration should it choose when creating the scale set?
A: Flexible orchestration mode, which manages standard Azure VMs and supports Spot plus regular mixes and Azure Backup
B: Uniform orchestration mode, which supports mixed Spot and regular instances in one set and Azure Backup per VM
C: Uniform mode now, switching to Flexible later once the instances need Backup and the standard VM commands
D: An availability set with autoscale, which spreads standard VMs over fault domains and backs up each member
K: A
G: ## Two orchestration modes
A Virtual Machine Scale Set is created in one of two **orchestration modes**, and **the mode can't be changed later**.
- **Flexible (recommended)**: instances are standard Azure VMs (`Microsoft.Compute/virtualMachines`). You manage them with the normal VM APIs, tags and RBAC; they support **Azure Backup** and (via PowerShell) Azure Site Recovery; you can mix Windows and Linux and **mix Spot and regular-priority instances**.
- **Uniform**: instances are scale set VMs (`virtualMachineScaleSets/virtualMachines`) built from one identical profile and managed through the scale set VM APIs. Spot instances must be all Spot or all regular; Azure Backup and Site Recovery are not supported. Uniform is still used for Service Fabric and AKS node pools.
## Where availability sets fit
Availability sets spread standard VMs across fault and update domains but offer **no autoscaling, no instance protection and no Spot instances** (regular priority only).
## Example
`vmss-web` in Flexible mode: two regular instances as a base and Spot instances for bursts, each VM backed up like any other VM.
W: Flexible orchestration: its instances are standard VMs, so standard VM commands and Azure Backup work, and Flexible is the mode that allows Spot and regular instances in the same scale set.
X: B=Uniform: in Uniform mode instances must be all Spot or all regular, and Uniform instances don't support Azure Backup.
C=Switch later: the orchestration mode is set when the scale set is created and can't be changed or updated afterwards.
D=Availability set: availability sets support neither autoscaling nor Spot instances, so they can't meet the scaling and pricing requirements.
T: Need standard VM management, Azure Backup or mixed Spot/regular instances in a scale set → Flexible orchestration, chosen at creation.

@ AZ-104 D3 T3.2 advanced use-case
S: In a scale set with CPU-based autoscale, instance vmss-batch_3 runs a six-hour data export. Autoscale must not remove that instance during the export, but it must still receive the model updates the team rolls out to all instances. What should the administrator set on vmss-batch_3?
A: Protect from scale-in on that instance, which blocks autoscale scale-in but still allows scale set upgrades
B: Protect from scale set actions on that instance, which blocks autoscale scale-in and all scale set upgrades
C: A NewestVM scale-in policy on the scale set model, which removes the newest VMs before any older instance
D: A CanNotDelete resource lock on the instance, which stops autoscale from deleting it during the export job
K: A
G: ## Instance protection
Scale sets offer two per-instance protection settings, applied on the **instance model** after the instance is created (never on the scale set model):
- **Protect from scale-in** (`protectFromScaleIn`): autoscale won't pick this instance when it scales in. Scale set operations such as upgrade, reimage or deallocate still apply, and a user can still delete the instance.
- **Protect from scale set actions** (`protectFromScaleSetActions`): also implies protection from scale-in, **and** shields the instance from scale set operations such as upgrade, reimage and deallocate. User-initiated instance operations and deleting the whole scale set are still allowed.
You set it in the portal (**Instances** → instance → **Protection Policy**), with `az vmss update --instance-id 3 --protect-from-scale-in true`, or with `Update-AzVmssVM -ProtectFromScaleIn $true`.
## Scale-in policy is different
A **scale-in policy** (Default, NewestVM, OldestVM) on the scale set model only decides the **order** in which instances are removed. It can't exempt one particular instance.
W: Protect from scale-in: it keeps autoscale from choosing vmss-batch_3 for scale-in while leaving scale set upgrades in effect, which is exactly the requirement.
X: B=Protect from scale set actions: it also blocks scale set operations such as upgrades and reimages, so the instance would miss the model updates.
C=NewestVM policy: a scale-in policy only sets the removal order for the whole set; it can't guarantee that one specific instance is never chosen.
D=Resource lock: Learn's mechanism for exempting one instance from autoscale scale-in is instance protection on the instance model; a resource lock is not the documented way to do it.
T: Keep one instance through scale-in but still upgrade it → protect from scale-in; also freeze it from upgrades → protect from scale set actions.

@ AZ-104 D3 T3.2 advanced troubleshooting
S: A scale set's autoscale profile (minimum 2, maximum 10) has four rules: scale out by 1 if CPU > 75% or memory > 75%; scale in by 1 if CPU < 30% or memory < 50%. At night CPU is 20% and memory is 60%, yet the set stays at six instances. Why?
A: A scale-in happens only when all scale-in rules are met, and memory at 60% doesn't meet the below-50% rule
B: A scale-in happens only after the scale-out rules have been inactive for 24 hours, so the set waits until then
C: The autoscale engine skips scale-in at night, unless a schedule-based profile is created for those hours
D: Memory metrics can't be used for autoscale, so the scale-in rule set is invalid and ignored by the engine
K: A
G: ## How autoscale combines several rules
An autoscale setting has a minimum, maximum and default instance count and one or more profiles with rules. When a profile has several rules:
- **Scale-out** runs if **any** scale-out rule is met.
- **Scale-in** runs only if **all** scale-in rules are met.
This is deliberate: removing capacity when only one signal is low could overload the remaining instances on the other dimension.
## Worked example from the Learn best-practices article
Rules: CPU < 30% scale in, memory < 50% scale in, CPU > 75% scale out, memory > 75% scale out.
- CPU 76%, memory 50% → scales out.
- CPU 25%, memory 51% → **no scale-in**; it needs CPU below 30% **and** memory below 50%.
## Other behavior to know
- Manual instance counts outside min/max are pushed back into the range on the next run.
- Autoscale avoids **flapping**: it defers a scale-in that would immediately trigger a scale-out. Keep a margin between thresholds and use the same metric for in and out.
W: All scale-in rules: the engine requires every scale-in condition to hold; CPU is low, but memory at 60% is above the 50% threshold, so no scale-in occurs.
X: B=24-hour wait: autoscale has no such rule; the engine runs every 30 to 60 seconds and compares each rule's metric over that rule's own time window.
C=Night-time skip: autoscale evaluates the active profile at all times; a schedule profile is optional and only needed for time-based instance counts.
D=Memory not supported: rules can use host metrics such as Percentage CPU, guest metrics through the diagnostics extension, or Application Insights metrics; the rules are valid.
T: With several autoscale rules, any scale-out rule can add instances, but all scale-in rules must be true before instances are removed.

@ AZ-104 D3 T3.2 applied troubleshooting
S: A production scale set uses the Manual upgrade policy. An administrator updated the scale set model to a newer image version. A day later, the eight existing instances still run the old image, while one instance added by autoscale overnight runs the new image. What explains this, and what should the administrator do?
A: Manual mode leaves existing instances on the old model; upgrade them from Instances > Upgrade or az vmss update-instances
B: Manual mode applies model changes only after each instance's weekly maintenance window; wait for the next window
C: The model update failed for existing instances; reapply it with the upgrade policy set to Automatic to retry it
D: Scale set image updates apply only to instances added later; delete the eight instances so autoscale replaces them
K: A
G: ## Upgrade policy modes
A scale set's **upgrade policy** decides how existing instances pick up changes to the **scale set model** (image reference, SKU, data disks, extensions, zones):
- **Automatic**: the scale set may update all instances at the same time, in no guaranteed order. Suited to dev/test.
- **Rolling**: updates in batches with settings such as batch size and max healthy percentage. Best for production. It needs application health monitoring: the Application Health extension (Flexible) or a health probe or the extension (Uniform).
- **Manual**: nothing happens to existing instances when the model changes; **new instances use the latest model**. You choose when to upgrade each instance.
## Upgrading instances under Manual
- Portal: scale set → **Instances** → select instances → **Upgrade**.
- CLI: `az vmss update-instances --resource-group rg --name vmss --instance-ids 0 1 2`
- PowerShell: `Update-AzVmssInstance`
Changes such as image reference, VM size, password/SSH key or custom data need a restart, reimage or redeploy of the instance, so upgrade in small groups for production.
W: Manual upgrade policy: model changes reach only new instances until the administrator upgrades existing ones, which is done from Instances > Upgrade or with az vmss update-instances.
X: B=Weekly maintenance window: Manual mode has no built-in schedule; existing instances stay on the old model until someone triggers the upgrade.
C=Update failed: the model update succeeded, as the new instance shows; Automatic mode could take every instance down at once, unsuitable for production.
D=Only new instances: other upgrade modes apply model changes to existing instances, and even under Manual you upgrade them in place instead of deleting them.
T: Under the Manual upgrade policy, new instances get the latest model but existing ones change only when you upgrade them; use Rolling for hands-off production updates.
