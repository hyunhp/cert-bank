# AZ-104 D2 T2.1 Configure access to storage (16 questions: firewall and network rules x5, SAS x3, stored access policies and revocation x3, access keys and Shared Key x2, Azure Files identity-based access x3)

@ AZ-104 D2 T2.1 advanced troubleshooting
S: Storage account `stfabdata` in West Europe allows public access only from selected virtual networks and IP addresses. VMs in subnet `app` of a West Europe virtual network reach the internet through a NAT gateway with public IP `20.50.10.4`. The admin added an IP network rule for `20.50.10.4`, but the VMs still get 403 errors on blob requests. What should the admin do?
A: Add a virtual network rule for subnet `app` and enable a service endpoint for Azure Storage on that subnet.
B: Replace the IP rule with one for the subnet's private range `10.20.1.0/24` so the firewall matches the VMs' real addresses.
C: Enable the exception that allows Azure services on the trusted services list to reach the storage account from the VMs.
D: Enter the NAT gateway address as the CIDR range `20.50.10.4/32` instead of a single address so outbound traffic matches.
K: A
G: ## How the storage firewall decides
When public network access is set to **Enabled from selected virtual networks and IP addresses**, only traffic from explicitly allowed sources reaches the account's public endpoint; everything else gets 403. Four kinds of rules exist:
- **Virtual network rules**: allow a subnet. The subnet also needs a service endpoint (`Microsoft.Storage` for the same region, or `Microsoft.Storage.Global` for any region). The portal creates the endpoint for you when you pick a subnet.
- **IP network rules**: allow public IPv4 addresses or ranges.
- **Resource instance rules**: allow a specific Azure resource instance.
- **Trusted service exceptions**: allow listed Azure services.
## The same-region catch
Requests from the **same Azure region** as the storage account travel over private Azure addresses, so IP network rules have no effect on them. Learn states this directly: use virtual network rules to allow same-region requests. Other IP rule limits:
- Private (RFC 1918) ranges such as `10.x`, `172.16-31.x` and `192.168.x` are not allowed.
- `/31` and `/32` prefixes are not supported; enter a single address instead.
- Only IPv4 is supported.
## Example
`az network vnet subnet update ... --service-endpoints Microsoft.Storage.Global` followed by `az storage account network-rule add ... --subnet <subnet-id>` lets the VMs in the subnet in.
W: Virtual network rule plus service endpoint: the VMs are in the same region as the account, so their traffic never shows up with the NAT gateway's public address. A subnet rule backed by a storage service endpoint is the supported way to admit same-region VMs.
X: B=Private IP range rule: IP network rules accept only public internet addresses; RFC 1918 ranges such as `10.20.1.0/24` are rejected.
C=Trusted services exception: the exception admits specific Azure services (Azure Monitor, Azure Backup and others) that run outside your network, not your own VMs.
D=/32 CIDR range: `/31` and `/32` prefixes are not supported in IP rules, and any IP rule is ignored for same-region traffic anyway.
T: IP network rules don't apply to same-region traffic; admit Azure VMs with a virtual network rule and a storage service endpoint on their subnet.
V: Azure Storage, Azure Virtual Network

@ AZ-104 D2 T2.1 applied use-case
S: A small accounting firm restricts its storage account to selected networks. Staff in its office must use Azure Storage Explorer against the account. The office LAN is `192.168.40.0/24` and all outbound traffic leaves through a firewall that translates it to `203.0.113.25`. What should the administrator configure?
A: An IP network rule for `192.168.40.0/24`, because the storage firewall evaluates the original LAN address of each client device.
B: An IP network rule for `203.0.113.25`, the public address that the office firewall uses for all of its outbound traffic.
C: A resource instance rule that names the office firewall appliance, so its translated traffic is matched by resource identity.
D: SAS tokens with `sip=192.168.40.0/24` for each user, because a SAS IP limit opens the storage firewall for those addresses.
K: B
G: ## Letting an on-premises network through the storage firewall
Clients outside Azure reach the storage account's public endpoint from whatever public address their network presents on the internet. To admit them you create an **IP network rule** for that public address or range.
- First identify the internet-facing addresses of the network (for ExpressRoute with Microsoft peering, the NAT addresses used for peering).
- Enter them as single IPv4 addresses or CIDR ranges such as `16.17.18.0/24`.
- Private RFC 1918 ranges (`10.x`, `172.16-31.x`, `192.168.x`) are not accepted, because the storage service never sees them.
## Rules versus SAS
A SAS can carry an IP restriction (`sip`), but that only narrows what the token holder can do. Learn notes that a SAS that grants access to a specific IP address does not grant new access beyond the configured network rules.
## Example
Office traffic leaves through NAT as `203.0.113.25`: add that single address as an IP rule, and every workstation behind the NAT can use Storage Explorer, subject to its own authorization.
W: Public NAT address rule: the storage service sees the office's translated public address, so an IP network rule for `203.0.113.25` is what admits the office's requests.
X: A=LAN range rule: private ranges such as `192.168.x` are not allowed in IP network rules, and the service never sees those source addresses.
C=Resource instance rule: resource instance rules admit Azure resource instances from the same tenant, not on-premises appliances.
D=SAS with sip: a SAS IP limit restricts the token holder; it never grants access beyond the network rules, so the firewall still blocks the office.
T: Admit on-premises clients by their public (NAT) address in an IP network rule; private LAN ranges and SAS IP limits don't open the firewall.
V: Azure Storage

@ AZ-104 D2 T2.1 applied troubleshooting
S: An admin creates a diagnostic setting that archives Microsoft Entra sign-in and audit logs to storage account `stauditlogs`. The account allows public access only from one virtual network, and no logs arrive. The admin must not open the account to the internet. What should the admin change on the storage account?
A: Add a resource instance rule for Azure Monitor and give that resource instance a data role on the account.
B: Add IP network rules for the Azure Monitor outbound address ranges in the same region as the storage account.
C: Enable the network exceptions for logging and metrics so that log files and metrics tables can be accessed.
D: Enable the exception that allows Azure services on the trusted services list to access this storage account.
K: D
G: ## Trusted service exceptions
Some Azure services run from networks that you can't add to a virtual network rule or IP rule. For them the storage firewall has a **network security exception**. In the portal it appears as **Allow Azure services on the trusted services list to access this storage account**; in the CLI it is `--bypass AzureServices`.
- Services in the tenant-registered list connect with strong authentication for specific operations.
- **Azure Monitor** (`Microsoft.Insights`) is on that list to write monitoring data to a secured account, including resource logs and Microsoft Entra sign-in and audit logs.
- Azure Backup, Azure Site Recovery, Event Grid and Azure File Sync are other examples.
## The other exception values
The same `bypass` setting also accepts `Logging` and `Metrics`. Those let services *read* log files and metrics tables in your account; they don't let a service write diagnostic exports into it.
## Example
`az storage account update -g rg-sec -n stauditlogs --bypass AzureServices` keeps the virtual network rule in place and lets Azure Monitor deliver the logs.
W: Trusted services exception: Azure Monitor is a trusted Azure service that writes resource logs and Entra sign-in and audit logs to firewall-protected accounts once this exception is on, without opening the account to the internet.
X: A=Resource instance rule for Azure Monitor: resource instance rules cover the resource types on the managed-identity list (Data Factory, AI Search and others); Azure Monitor diagnostic delivery uses the trusted services exception instead.
B=IP rules for Azure Monitor ranges: Azure services in the same region reach storage over private Azure addresses, so IP rules can't match them.
C=Logging and Metrics exceptions: these allow read access to log files and metrics tables in the account, not writes from Azure Monitor diagnostic settings.
T: Azure services that must reach a firewalled storage account, such as Azure Monitor log delivery, are admitted with the trusted services exception (`--bypass AzureServices`).
V: Azure Storage, Azure Monitor, Microsoft Entra ID

@ AZ-104 D2 T2.1 advanced use-case
S: An Azure AI Search service must index PDFs in a blob container. The storage account allows public access only from selected networks, and the search service isn't deployed in any virtual network. Both resources are in the same tenant, and the search service has a system-assigned managed identity. Which TWO actions give the search service access? (Select TWO)
A: Add a resource instance rule on the storage account for that specific Azure AI Search service.
B: Assign the Storage Blob Data Reader role on the storage account to the search service's managed identity.
C: Add an IP network rule for the outbound public address of the search service in the account's region.
D: Assign the Reader role on the storage account to the search service's managed identity at account scope.
E: Enable a storage service endpoint on the subnet that the search service uses to reach Azure Storage.
K: A,B
G: ## Resource instance rules
Some Azure resources can't be isolated with a virtual network rule or an IP rule because they don't run in your virtual network. A **resource instance rule** admits one specific resource (or all resources of a type in a tenant, subscription or resource group) through the storage firewall.
- The resource must be in the **same Microsoft Entra tenant** as the storage account; any subscription in the tenant is fine.
- Supported types include Azure AI Search, Data Factory, Synapse, Logic Apps and others with managed identities.
## Network access is not data access
Learn is explicit: a resource instance rule gives access to the public **endpoint**, not to the **data**. The resource's managed identity also needs an Azure role on the data plane, for example **Storage Blob Data Reader** to read blobs.
## Example
`az storage account network-rule add -g rg-docs --account-name stdocs --resource-id <search-service-id> --tenant-id <tenant-id>` admits the search service, and a Storage Blob Data Reader assignment for its managed identity lets the indexer read the PDFs.
W: A=Resource instance rule: admits that particular search service through the firewall even though it isn't in a virtual network.
B=Storage Blob Data Reader for the managed identity: the rule only opens the endpoint, so the identity also needs a data-plane role to read the blobs.
X: C=IP rule for the outbound address: services in the same region as the account reach it over private Azure addresses, so IP rules can't admit them.
D=Reader role: Reader is a control-plane role that shows the account's settings; it grants no access to blob data.
E=Service endpoint: the search service isn't deployed in a subnet you control, so there's no subnet to enable an endpoint on or to add as a rule.
T: A resource instance rule opens the firewall for one Azure resource; its managed identity still needs a data role to read the data.
V: Azure Storage, Azure AI Search

@ AZ-104 D2 T2.1 applied troubleshooting
S: A storage account allows public access only from the office's public IP. Working from home, an admin opens the account in the Azure portal: the list of blob containers appears, but opening a container to browse its blobs fails with an access error. She has the Owner role. What explains this?
A: The portal lists containers with her Entra token but browses blobs with Shared Key, and the firewall rejects only key-signed requests.
B: The container's anonymous access level is set to Private, which hides blob listings from anyone outside the allowed IP range.
C: The firewall filters only data plane requests; the container list can come through the control plane, but browsing blobs is a data request.
D: The portal caches the container list from the last session in the office, so the list appears even though no live request succeeded.
K: C
G: ## Control plane versus data plane
Azure Storage has two sets of operations:
- **Control plane** (Azure Resource Manager, the `Microsoft.Storage` resource provider): create the account, change its settings, list containers through the resource provider.
- **Data plane** (the storage service endpoints such as `blob.core.windows.net`): read, write and list blobs, queue messages, table entities and files.
## What the storage firewall covers
Learn states that firewall rules apply only to **data plane** operations; control plane operations aren't subject to them. Some operations, such as listing blob containers, exist in both planes, so listing containers in the portal succeeds unless something else blocks it. Opening a container to browse blobs is a data request from your browser, so you must be on a machine inside the trusted network boundary (or an allowed IP).
## Example
An admin in a hotel sees every container in the portal but gets an authorization error on each blob listing. Adding the hotel's IP temporarily, or connecting through the office VPN, fixes it.
W: Data plane only: the firewall blocks her browser's data requests from the home IP, while the container list comes through the control plane, which the firewall does not filter.
X: A=Firewall rejects only key-signed requests: network rules apply to every data plane request whatever its authorization, so blob browsing from her home IP would fail with Entra ID too.
B=Private access level: Private only means no anonymous access; it doesn't hide blob listings from authorized users on allowed networks.
D=Cached container list: listing containers is a control-plane operation that Learn says succeeds through the portal despite the firewall; no cache is involved.
T: The storage firewall filters data plane requests only, so a portal that lists containers can still fail to show blobs from a non-allowed network.
V: Azure Storage

@ AZ-104 D2 T2.1 applied use-case
S: A logistics partner must upload files to container `intake` for the next three days through a URL, without signing in. Security policy says no SAS may be signed with a storage account key, and every SAS must trace back to a Microsoft Entra identity. The admin has the Storage Blob Data Contributor role. What should the admin create?
A: A service SAS for the container that references a stored access policy with write permission and a three-day expiry.
B: An account SAS limited to the blob service and container and object resource types, with a three-day expiry time.
C: A user delegation SAS for the container, created with `--auth-mode login --as-user` and a three-day expiry time.
D: A service SAS on the container created from the portal's Shared access tokens page with the signing method set to key1.
K: C
G: ## Three kinds of SAS
- **User delegation SAS**: signed with a *user delegation key* that a Microsoft Entra security principal obtains. It works for Blob Storage (including Data Lake), and Learn now lists Queue, Table and Azure Files too. Microsoft recommends it whenever a SAS is needed.
- **Service SAS**: signed with the storage account key; delegates access to one service.
- **Account SAS**: signed with the storage account key; can span several services and include service-level operations.
## What a user delegation SAS needs
The creator needs a role that includes `Microsoft.Storage/storageAccounts/blobServices/generateUserDelegationKey`, such as **Storage Blob Data Contributor**, assigned at account, resource group or subscription scope. The key, and therefore the SAS, is valid for at most **7 days** from its start.
## Example
`az storage container generate-sas --account-name stlogi --name intake --permissions acw --expiry 2026-11-01T17:00Z --auth-mode login --as-user` returns a token whose `skoid` field holds the object ID of the Entra principal that requested the user delegation key.
W: User delegation SAS: it is signed with an Entra-issued user delegation key, not an account key, and the admin's Storage Blob Data Contributor role includes the action needed to get that key. Three days is within the 7-day limit.
X: A=Service SAS with stored access policy: a service SAS is always signed with the account key, which the policy forbids, even when a stored access policy controls its terms.
B=Account SAS: an account SAS is also signed with the storage account key and doesn't trace back to an Entra identity.
D=Portal SAS signed with key1: choosing key1 as the signing method makes it a key-signed service SAS, exactly what the policy bans.
T: When a SAS must not use the account key and must trace to an Entra identity, create a user delegation SAS (valid up to 7 days).

@ AZ-104 D2 T2.1 applied comparison
S: A third-party monitoring tool must call Get Service Properties and Get Service Stats on both the Blob and Queue services of one storage account, using a single token, without being given an access key. Which type of SAS should the admin issue?
A: A service SAS on each container and queue, with read permission and a short expiry for each token.
B: An account SAS with `ss=bq`, `srt=s` and read permission, signed with one of the account keys.
C: A user delegation SAS for the blob service, created by an admin who holds Storage Blob Data Reader.
D: A service SAS that references a stored access policy granting read access on every container.
K: B
G: ## What each SAS can reach
- **Service SAS**: one resource in one service (a container, blob, queue, table, share or file).
- **User delegation SAS**: the same container and object operations as a service SAS, secured with Entra credentials.
- **Account SAS**: everything a service or user delegation SAS can do, plus:
  - service-level operations such as **Get/Set Service Properties** and **Get Service Stats**,
  - more than one service in one token,
  - create and delete operations on containers, queues, tables and shares.
## Account SAS fields
- `ss` (signed services): `b` Blob, `q` Queue, `t` Table, `f` File, combined as needed, for example `ss=bq`.
- `srt` (signed resource types): `s` service, `c` container, `o` object.
- `sp` (permissions): for example `r` for read.
## Example
A token with `ss=bq&srt=s&sp=r` lets a tool read service properties and stats of the Blob and Queue services and nothing else.
W: Account SAS with service resource type: only an account SAS delegates service-level operations, and `ss=bq` covers both services in one token while `srt=s` and read keep it narrow.
X: A=Service SAS per container and queue: a service SAS can't delegate service-level operations, and the requirement asks for a single token.
C=User delegation SAS: it covers container and object operations; service-level calls such as Get Service Stats need an account SAS.
D=Service SAS with stored access policy: a stored access policy controls the terms of a service SAS but doesn't widen it to service-level operations or other services.
T: Service-level operations and multi-service access in one token require an account SAS (`ss` for services, `srt=s` for service-level APIs).
V: Azure Storage

@ AZ-104 D2 T2.1 applied use-case
S: An admin issues an account SAS to an outside auditor. The token must be usable only from the auditor's office range `198.51.100.16` to `198.51.100.31`, and it must never be accepted over plain HTTP. Which TWO settings should the admin include in the SAS? (Select TWO)
A: Set `sip=198.51.100.16-198.51.100.31` on the token.
B: Set `spr=https` so that only HTTPS requests are accepted.
C: Bind the token to a stored access policy that lists the range.
D: Leave `spr` at its default, which already allows HTTPS only.
E: Set `srt=s` so the token works only from the auditor's network.
K: A,B
G: ## Optional limits on a SAS
Besides permissions and expiry, a SAS can carry two network limits:
- **Signed IP (`sip`)**: a single public IPv4 address or an inclusive range, for example `sip=198.51.100.10-198.51.100.20`. A request from any other address isn't authorized. If the client goes through a proxy or gateway, use that device's public outbound address.
- **Signed protocol (`spr`)**: `https` (HTTPS only) or `https,http` (both). The **default is `https,http`**, and HTTP only isn't a permitted value.
## Caveats
- Don't put a public IP in `sip` for clients in the same Azure region as the account: their requests use private addresses and fail.
- A SAS IP limit narrows access; it doesn't open the storage firewall.
- Stored access policies can't be used with an account SAS, and they hold only start time, expiry and permissions.
## Example
`...&sip=198.51.100.16-198.51.100.31&spr=https&sig=...` works only over HTTPS from the auditor's range.
W: A=Signed IP range: `sip` with an inclusive range restricts the token to requests from the auditor's public addresses.
B=HTTPS-only protocol: `spr=https` makes the service refuse the token on plain HTTP requests.
X: C=Stored access policy with the range: stored access policies don't support account SAS and hold only start, expiry and permissions, not IP limits.
D=Default spr: the default is `https,http`, so leaving it unset would accept plain HTTP.
E=srt=s: `srt` picks resource types (service, container, object); it has nothing to do with where requests come from.
T: Use `sip` to limit a SAS to client IP addresses and `spr=https` to refuse HTTP; the protocol default allows both.

@ AZ-104 D2 T2.1 applied use-case
S: A team issued 40 service SAS URLs for container `reports`, all referencing the stored access policy `partner-read`. The partner contract ends today, and all 40 URLs must stop working. Internal apps use a connection string with key1 and must keep running. What should the admin do?
A: Regenerate key1 so that every SAS signed with it becomes invalid, then update the apps with the new key.
B: Run `az storage account revoke-delegation-keys` on the account to invalidate the partner's SAS tokens.
C: Configure a SAS expiration policy with an upper limit of one hour on the storage account that holds the container.
D: Delete the `partner-read` stored access policy, or set its expiry time to a value in the past, on the container.
K: D
G: ## Stored access policies
A **stored access policy** is defined on a container, file share, queue or table and holds start time, expiry time and permissions. A **service SAS** can reference it by its signed identifier and inherit those terms.
- Up to **five** stored access policies per container, share, queue or table.
- Only a service SAS can use one; account SAS and user delegation SAS can't.
- A new or changed policy can take up to 30 seconds to take effect.
## Revoking through the policy
To revoke every SAS tied to a policy, **delete** the policy, **rename** it (change the signed identifier), or set its **expiry to the past**. Deleting or modifying the policy affects all associated SAS immediately, and you don't touch the account keys.
## Example
The 40 URLs contain `si=partner-read`. Removing that signed identifier from the container's ACL makes every one of them fail with 403, while apps using key1 carry on.
W: Delete or expire the stored access policy: all 40 tokens depend on `partner-read`, so removing it or setting its expiry in the past revokes them together without touching the account keys.
X: A=Regenerate key1: this would revoke the SAS, but it also breaks every app on key1 until updated, which the requirement forbids.
B=Revoke delegation keys: this only invalidates user delegation SAS; service SAS are signed with the account key and aren't affected.
C=SAS expiration policy: it sets a recommended or enforced upper limit for SAS intervals, and its block action isn't supported for service SAS that use a stored access policy.
T: Revoke service SAS tied to a stored access policy by deleting, renaming or expiring that policy; the account keys stay untouched.
V: Azure Blob Storage

@ AZ-104 D2 T2.1 advanced troubleshooting
S: An ad hoc account SAS signed with key1 was posted in a public code repository. Production apps use a connection string with key1, and a few batch jobs already use key2. The admin must invalidate the leaked SAS with no app outage. Which sequence should the admin follow?
A: Regenerate key1 right away, then update the production apps to the new key1 value as quickly as possible afterwards.
B: Delete every stored access policy on the account's containers, then regenerate key2 to remove anything still valid.
C: Move the production apps to key2, confirm they work, then regenerate key1 to invalidate the leaked account SAS.
D: Run `az storage account revoke-delegation-keys`, then set a key expiration policy so both keys rotate in the future.
K: C
G: ## Two keys for rotation
Every storage account has two 512-bit access keys, **key1** (primary) and **key2** (secondary). Two keys exist so you can rotate without downtime:
1. Point apps to the key you are *not* regenerating.
2. Regenerate the other key (`az storage account keys renew --key primary`).
3. Move apps to the new key, and later regenerate the second key the same way.
## Keys and SAS
Learn notes that regenerating a key **revokes every SAS signed with it**, so account and service SAS created from that key must be reissued. User delegation SAS aren't affected by key rotation. An ad hoc account SAS has no stored access policy, so key regeneration is the way to revoke it.
## Example
Switch the production app settings to the key2 connection string, verify traffic, then run `az storage account keys renew -g rg-prod --account-name stprod --key primary`. The leaked token stops working; nothing goes down.
W: Move to key2, then regenerate key1: apps keep running on key2 while regenerating key1 revokes every SAS signed with it, including the leaked account SAS.
X: A=Regenerate key1 first: this does revoke the token, but the production apps fail from the moment the key changes until they're updated.
B=Delete policies and regenerate key2: account SAS can't use stored access policies, and the leaked token was signed with key1, so regenerating key2 leaves it valid and breaks the batch jobs.
D=Revoke delegation keys: that only invalidates user delegation SAS; a key expiration policy is a reminder and doesn't revoke anything.
T: To revoke an account or service SAS without stored access policy, switch apps to the other key and regenerate the key that signed it.

@ AZ-104 D2 T2.1 applied troubleshooting
S: A developer created a user delegation SAS with read and list access on container `designs`, valid for six days, and it was emailed to the wrong recipient. The storage account keys have never been used to sign anything. How can the admin invalidate this SAS?
A: Regenerate key1 and key2 on the storage account so that every outstanding SAS issued for the account is invalidated.
B: Run `az storage account revoke-delegation-keys` on the storage account so the key that signed the SAS is revoked.
C: Delete the stored access policy that the user delegation SAS references on container `designs` to end its access.
D: Set `AllowSharedKeyAccess` to false on the storage account so that SAS tokens are refused for every service.
K: B
G: ## How a user delegation SAS is secured
A user delegation SAS is signed with a **user delegation key** that a Microsoft Entra principal requests (the `generateUserDelegationKey` action). The key, and so the SAS, is valid for at most 7 days. Because it isn't signed with an account key:
- rotating key1 or key2 doesn't affect it,
- it can't use a stored access policy (it is always ad hoc),
- it keeps working when Shared Key authorization is disallowed.
## Revoking it
- `az storage account revoke-delegation-keys` revokes **all** user delegation keys on the account; every SAS signed with them is invalidated.
- Changing or removing the role assignments of the principal that created the SAS also invalidates it, because the SAS can never grant more than that principal's permissions.
- Learn notes a short delay: keys and role assignments are cached.
## Example
After `az storage account revoke-delegation-keys -g rg-design -n stdesign`, the leaked link returns 403 within the caching delay; other users simply generate new user delegation SAS.
W: Revoke user delegation keys: the SAS is signed with a user delegation key, so revoking the account's delegation keys invalidates it (and any other user delegation SAS on the account).
X: A=Regenerate both keys: Learn states user delegation SAS are secured with Entra credentials and aren't affected by account key rotation.
C=Delete the stored access policy: a user delegation SAS can't reference a stored access policy, so there's none to delete.
D=Disallow Shared Key: requests with a user delegation SAS are authorized through Microsoft Entra ID and are still permitted when Shared Key is disallowed.
T: Invalidate a user delegation SAS by revoking the account's user delegation keys; key rotation and stored access policies don't touch it.

@ AZ-104 D2 T2.1 advanced tradeoff
S: To meet an audit finding, an admin plans to set `AllowSharedKeyAccess` to false on a storage account that holds only blob containers. Which TWO kinds of client requests will keep working after the change? (Select TWO)
A: A web app that reads blobs with its managed identity, which holds the Storage Blob Data Reader role.
B: A partner script that uploads with a service SAS created on the container from the account's key1.
C: A reporting job that connects with a connection string that contains the account name and key2.
D: A mobile app that downloads blobs with a user delegation SAS issued by a back-end service.
E: A backup tool that uses an account SAS with blob and object access issued last week.
K: A,D
G: ## Disallowing Shared Key
By default a storage account accepts requests authorized with **Microsoft Entra ID** or with the account access key (**Shared Key**). The `AllowSharedKeyAccess` property is unset by default, which means Shared Key is allowed. Setting it to `false` makes the account reject every request authorized with the access keys.
## Effect on each kind of client
- Entra ID (OAuth) requests, for example from a managed identity with a data role: **permitted**.
- **User delegation SAS** (Blob Storage): authorized with Entra ID, **permitted**.
- **Service SAS** and **account SAS**: signed with the account key, **denied** for every service.
- Connection strings with an account key: **denied**.
## Before you flip it
Use Azure Monitor metrics (filter Transactions by Authentication = Account Key and SAS) and resource logs to find clients that still use keys. The built-in Azure Policy **Storage accounts should prevent shared key access** can audit accounts first. Disallowing Shared Key is also required before Microsoft Entra Conditional Access can protect a storage account.
W: A=Managed identity with a data role: this is Entra ID authorization, which is the only kind the account still accepts.
D=User delegation SAS: it is signed with an Entra-issued key, so Learn lists it as permitted when `AllowSharedKeyAccess` is false.
X: B=Service SAS from key1: a service SAS is signed with the account key, and such requests are denied for all services.
C=Connection string with key2: the connection string authorizes with Shared Key, which the account now rejects.
E=Account SAS: an account SAS is signed with the account key and is denied once Shared Key is disallowed.
T: With Shared Key disallowed, only Entra ID requests and user delegation SAS still work; service SAS, account SAS and key connection strings fail.

K: C
G: ## Key expiration policy
A **key expiration policy** (shown in the portal as a rotation reminder) displays a reminder when the set interval has passed and the keys haven't been rotated. Azure Policy's built-in definition **Storage account keys should not be expired** can then report accounts that are overdue.
## Why the button can be grayed out
The policy relies on the account's `keyCreationTime` property, which records when each key was created or last rotated. **Older accounts may have a null value** for one or both keys. Until both keys have been rotated at least once, you can't create a key expiration policy; the portal grays out **Set rotation reminder**, and PowerShell or CLI report that the creation time isn't set.
The same prerequisite applies to a SAS expiration policy, which also fails until the keys have been rotated.
## Example
Rotate safely (apps to key2, renew key1, apps back to key1, renew key2), then `az storage account update -g rg-old -n stlegacy --key-exp-days 60`.
W: Regenerate both keys once: rotating each key populates `keyCreationTime` for key1 and key2, which the key expiration policy needs before it can be set.
X: A=Store keys in Key Vault: Key Vault is the recommended way to manage keys, but it doesn't set the storage account's key creation times.
B=Key Operator role: that role lets a user list and regenerate keys, which Owner already includes; Learn ties the grayed-out button to keys that haven't been rotated, not to a missing role.
D=SAS expiration policy: the SAS policy is separate and has the same key-rotation prerequisite, so it can't be a fix.
T: A key expiration (rotation reminder) policy needs `keyCreationTime` for both keys, so rotate each key once on older accounts first.

@ AZ-104 D2 T2.1 applied use-case
S: A firm syncs its on-premises AD DS users to Microsoft Entra ID with Microsoft Entra Connect Sync. Staff laptops are Microsoft Entra hybrid joined and often work from home without VPN. Users must reach an SMB Azure file share with their own identities, and clients have no line of sight to domain controllers. Which identity source should the admin enable?
A: On-premises AD DS authentication, registering the storage account in the domain with the AzFilesHybrid module.
B: Microsoft Entra Domain Services authentication, with the laptops joined to the managed domain for Kerberos.
C: Microsoft Entra Kerberos authentication, with admin consent granted to the storage account's application.
D: No identity source; mount the share from a logon script that passes the storage account key as the password.
K: C
G: ## Identity sources for Azure Files over SMB
Azure Files uses Kerberos for identity-based access, and a storage account can use **only one** identity source for all its shares:
- **On-premises AD DS**: the storage account is registered in the domain (AzFilesHybrid `Join-AzStorageAccount`). Clients need unimpeded connectivity to domain controllers. Identities must be synced to Entra ID for share-level RBAC.
- **Microsoft Entra Domain Services**: a managed domain in Azure. Clients must join the managed domain (non-Azure clients can't) or reach its domain controllers.
- **Microsoft Entra Kerberos**: Entra ID issues the Kerberos tickets, so clients **don't need domain controller connectivity**. Clients must be Entra joined or Entra hybrid joined. Hybrid identities need AD DS synced with Connect Sync or Cloud Sync.
## Setup notes for Entra Kerberos
After enabling it, grant admin consent to the autogenerated application, and exclude that application from MFA policies. Then assign share-level roles and set NTFS permissions.
## Example
`az storage account update -g rg-files -n stfirmfiles --enable-files-aadkerb true` turns it on for every share in the account.
W: Microsoft Entra Kerberos: Entra ID issues the Kerberos tickets, so hybrid-joined laptops at home can authenticate with synced hybrid identities without reaching a domain controller.
X: A=On-premises AD DS: clients must have unimpeded network connectivity to the AD domain controllers, which home laptops without VPN lack.
B=Entra Domain Services: Kerberos with this source requires clients joined to the managed domain, and non-Azure clients such as laptops can't join it.
D=Storage account key: mounting with the key gives everyone full share access and isn't identity-based authentication at all.
T: When clients are Entra (hybrid) joined and can't reach domain controllers, use Microsoft Entra Kerberos for Azure Files.

@ AZ-104 D2 T2.1 applied troubleshooting
S: An Azure file share uses AD DS authentication. Hybrid user Mia has the Storage File Data SMB Share Reader role on the share and the NTFS Modify permission on folder `\Projects`. She can open files there but can't save changes. What should the admin do?
A: Give Mia the NTFS Full Control permission on `\Projects` so that her file-level rights are higher than the share-level role.
B: Assign Mia the Storage File Data SMB Share Contributor role on the file share, keeping her NTFS Modify permission.
C: Assign Mia the Storage Blob Data Contributor role on the storage account so that her write requests are authorized.
D: Assign Mia the Reader role on the storage account so her share-level and file-level permissions can be merged together.
K: B
G: ## Two layers of permission
Identity-based access to Azure Files checks two things:
- **Share-level permissions** (Azure RBAC roles on the share, or a default share-level permission): the gatekeeper for the whole share.
  - Storage File Data SMB Share Reader: read.
  - Storage File Data SMB Share Contributor: read, write, delete.
  - Storage File Data SMB Share Elevated Contributor: read, write, delete, modify ACLs.
- **Directory and file permissions** (Windows ACLs, also called NTFS permissions): fine-grained rights on folders and files.
## The most restrictive wins
When the layers differ, only the most restrictive applies. Learn's example: read/write at file level but read at share level means the user can only read. With SMB Share Reader, even NTFS Full Control yields Read only. With SMB Share Contributor and NTFS Modify, the user gets read, write and delete.
## Example
Share-level role changes usually take effect within 30 minutes, so Mia should reconnect after the new assignment propagates.
W: SMB Share Contributor role: her NTFS Modify already allows writing, and the share-level Reader role is the restrictive layer. Contributor at share level gives read, write and delete together with Modify.
X: A=NTFS Full Control: with the SMB Share Reader role, every NTFS level up to Full yields read access only, because the share level stays restrictive.
C=Storage Blob Data Contributor: that role covers blob data, not SMB access to Azure file shares.
D=Reader role: Reader is a control-plane role for viewing the account; it grants no data access and permissions are never merged upward.
T: Azure Files enforces the more restrictive of share-level RBAC and NTFS permissions; raise the share-level role when NTFS already allows the action.
V: Azure Files

@ AZ-104 D2 T2.1 advanced use-case
S: A storage account uses AD DS authentication for Azure Files. An on-premises service runs as a group Managed Service Account (gMSA) that isn't synced to Microsoft Entra ID, and it must write to a folder on one share. Other users already have role assignments. What should the admin configure at share level?
A: Assign the Storage File Data SMB Share Contributor role to the gMSA object directly on the file share.
B: Switch the account's identity source to Microsoft Entra Kerberos so that the gMSA gets an Entra identity.
C: Set a default share-level permission for all authenticated identities, then grant the gMSA NTFS rights.
D: Assign the Storage File Data SMB Admin role to the gMSA so it can take ownership of the target folder.
K: C
G: ## Share-level permission without an Entra identity
Share-level permissions are normally Azure RBAC role assignments to Microsoft Entra users, groups or service principals. That requires the AD DS identity to be **synced** to Entra ID. Some identities have no Entra counterpart:
- standalone and group Managed Service Accounts (sMSA, gMSA),
- computer accounts,
- identities from an AD DS synced to a different Entra tenant.
## Default share-level permission
For these, set a **default share-level permission** on the storage account. It applies to all authenticated identities (anyone who can authenticate against the AD DS the account is joined to) on every share in the account. It starts as `None`.
- Learn's PowerShell: `Set-AzStorageAccount ... -DefaultSharePermission StorageFileDataSmbShareContributor`.
- If a user also has a specific RBAC assignment, the higher of the two applies.
- Use Windows ACLs (NTFS) on folders and files to narrow what each identity can do.
## Example
Default share-level Contributor plus an NTFS Modify entry for the gMSA on `\Exports` lets the service write there, while ACLs keep other folders locked.
W: Default share-level permission: the gMSA has no Entra identity to receive an RBAC role, so a default share-level permission gives authenticated AD DS identities share access, and NTFS ACLs grant the gMSA its folder rights.
X: A=Role on the gMSA: Azure RBAC can only be assigned to Entra identities, and an unsynced gMSA has none.
B=Switch to Entra Kerberos: Entra Kerberos authenticates hybrid or cloud-only Entra identities; changing the source doesn't give an unsynced gMSA an Entra identity and interrupts access for every share.
D=SMB Admin role: it is still an RBAC role needing an Entra identity, and taking ownership is for admins managing ACLs, not for a service writing files.
T: For AD DS identities without an Entra counterpart (gMSA, computer accounts), use a default share-level permission and control detail with NTFS ACLs.
V: Azure Files
