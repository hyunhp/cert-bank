# AZ-104 D3 T3.1 Automate deployment of resources by using ARM templates or Bicep files (14 questions)

@ AZ-104 D3 T3.1 applied troubleshooting
S: An administrator manages resource group rg-web, which holds a web app, a storage account and a VM named vm-test that a developer created in the portal. She deploys a template that defines only the web app, the storage account and a new Key Vault, using `az deployment group create --mode Complete`. Afterwards vm-test is gone. Why?
A: Complete mode deletes resources in the target resource group that the template does not define, so the VM was removed.
B: Complete mode redeploys every resource from scratch, so the VM was rebuilt and then dropped when its build timed out.
C: The new Key Vault replaced the VM's managed disk encryption key, and Azure deletes a VM whose disk key becomes invalid.
D: Complete mode moves resources that are not in the template into a holding resource group named after the deployment.
K: A
G: ## Two deployment modes
When you deploy an ARM template or Bicep file to a resource group, Resource Manager runs in one of two modes. The difference is only about **existing resources that are not in the template**.
- **Incremental** (the default): resources in the template are created or updated; resources already in the group but missing from the template are left alone.
- **Complete**: resources in the template are created or updated, and resources in the group that the template does not define are **deleted**.
In both modes, a resource that already exists with unchanged settings is not touched, and a changed property is updated in place. Nothing is rebuilt from scratch.
## Example from the documentation
Resource group holds A, B, C; template holds A, B, D.
- Incremental result: A, B, C, D.
- Complete result: A, B, D (C is deleted).
## Guard rails
- Microsoft recommends incremental mode, calls complete mode not recommended and says it will be gradually deprecated; use **deployment stacks** when a deployment must delete resources.
- Always run **what-if** before a complete-mode deployment; it lists the resources that would be deleted.
- A resource lock on the group stops complete mode from deleting resources.
W: Complete-mode deletion: vm-test existed in rg-web but was not in the template, and complete mode deletes exactly those resources, so the VM was removed while the web app, storage account and Key Vault remained.
X: B=Rebuild from scratch: neither mode recreates resources; unchanged resources are left as they are and changed properties are updated in place, and the VM was never in the template at all.
C=Disk key replacement: creating a new Key Vault does not touch other resources' encryption settings, and Azure has no rule that deletes a VM because of a new vault.
D=Holding resource group: Resource Manager has no move-aside behaviour; resources outside the template are either left alone (incremental) or deleted (complete).
T: Complete mode deletes what the template does not list in the target resource group; run what-if first, or prefer incremental mode and deployment stacks.
V: Azure Resource Manager, Azure CLI

@ AZ-104 D3 T3.1 applied troubleshooting
S: A storage account was deployed from a Bicep file and later tagged CostCenter=4410 in the portal. An admin edits the Bicep file only to change the SKU to `Standard_ZRS` and redeploys in the default mode. The SKU changes, but the CostCenter tag disappears. What explains this?
A: Changing the SKU forces Resource Manager to delete and recreate the storage account, and a new account starts without any tags.
B: Tags added in the portal are stored separately from deployment data, and Resource Manager clears that store on every redeployment.
C: The redeployment reapplies the resource exactly as the file defines it, so properties the file leaves out, such as the tag, are reset.
D: The default deployment mode is complete mode, which removes every setting that the Bicep file does not list for the resource group.
K: C
G: ## Incremental does not mean "partial"
The default mode is **incremental**, which is about which *resources* are kept: resources missing from the template stay in the resource group. It says nothing about keeping *properties*.
When an existing resource is redeployed, **all of its properties are reapplied**. Microsoft's documentation warns that a common misunderstanding is to think unspecified properties are left unchanged: properties not in the template are reset to their default values. The resource definition in a template always describes the **final state** of the resource; it cannot express a partial update.
## Consequences for administrators
- Changes made outside the template (portal, CLI, policy remediation) can be undone by the next deployment if the template does not include them.
- Put every non-default value in the template, not just the one you are changing.
- Run `az deployment group what-if` first: in Microsoft's own example the what-if output shows a tag that is missing from the file as `- tags.Owner` (to be removed).
## Example
The file now says `sku: { name: 'Standard_ZRS' }` and has no `tags` block, so the account ends up with ZRS and no tags. Adding `tags: { CostCenter: '4410' }` to the file keeps it.
W: Final-state redeployment: an incremental redeployment reapplies all properties of the storage account from the Bicep file, and because the file has no tags, the tag added in the portal is reset.
X: A=Delete and recreate: an SKU change is applied as an update to the existing resource; Resource Manager does not delete and rebuild an existing resource because a property changed.
B=Separate tag store: tags are an ordinary property of the resource, not a separate store that deployments wipe; they disappear only because the file does not define them.
D=Complete as default: the default mode is incremental, and complete mode is about deleting whole resources missing from the template, not individual settings.
T: In incremental mode, unlisted resources survive but unlisted properties of a redeployed resource are reset, so keep every non-default setting in the template.

@ AZ-104 D3 T3.1 applied use-case
S: An ARM template creates storage accounts in a copy loop with `"copy": { "name": "stgLoop", "count": 3 }` and `"name": "[format('stgapp{0}', copyIndex())]"`. The naming standard needs stgapp1, stgapp2 and stgapp3. What is the smallest change?
A: Set the copy element's count to 4 so the loop runs from one up to four and the first instance is skipped automatically.
B: Change the name expression to use `copyIndex(1)`, which offsets the zero-based loop index so the names start at one.
C: Add `"mode": "serial"` and `"batchSize": 1` to the copy element so instances are created one at a time starting at one.
D: Replace `copyIndex()` with `length(variables('names'))` in the name expression so each instance gets its own number.
K: B
G: ## Copy loops in ARM templates
To create several instances of a resource, add a `copy` element to the resource:
- `name`: any name that identifies the loop (other resources can depend on it).
- `count`: number of iterations (up to 800).
- `mode` and `batchSize`: optional, to deploy in serial batches instead of in parallel (parallel is the default).
Inside the resource, `copyIndex()` returns the current iteration. It is **zero-based**, so `format('stgapp{0}', copyIndex())` with a count of 3 produces `stgapp0`, `stgapp1`, `stgapp2`.
## Offsetting the index
`copyIndex()` accepts an offset: `copyIndex(1)` returns 1, 2, 3 for the same three iterations. The number of instances is still set by `count`.
## Bicep equivalent
Bicep uses a `for` expression instead, for example `[for i in range(1, 3): { name: 'stgapp${i}' ... }]`, where `range(start, count)` gives 1, 2, 3.
W: Offset with copyIndex(1): the offset changes only the value returned in each iteration, so the same three-instance loop now yields stgapp1, stgapp2 and stgapp3.
X: A=Count of four: a count of 4 creates four accounts named stgapp0 to stgapp3; nothing skips the first iteration, so an extra wrong account appears.
C=Serial with batch size one: serial mode only controls how many instances deploy at a time; the index still starts at zero, so the names are unchanged.
D=length() in the name: `length()` returns the same total for every iteration, so every instance would get an identical name and the deployment would not create three distinct accounts.
T: copyIndex() is zero-based; use copyIndex(offset) to shift the numbering, while count alone decides how many instances are created.

@ AZ-104 D3 T3.1 applied use-case
S: A Bicep file declares `resource vnet 'Microsoft.Network/virtualNetworks@...'`, and a network interface sets its subnet ID to `vnet.properties.subnets[0].id`. A colleague wants to add `dependsOn: [ vnet ]` to the NIC "so the VNet is created first". What should the admin tell him?
A: It is required: Bicep deploys all resources in parallel unless dependsOn is listed, so the NIC could be created before the VNet.
B: It is required: references by symbolic name are resolved only after deployment, so they never control the order of resources.
C: It is not needed: the reference to the vnet symbolic name already creates an implicit dependency, so the NIC waits for the VNet.
D: It is not needed: Resource Manager always deploys resources in the order they appear in the Bicep file, from top to bottom.
K: C
G: ## How Resource Manager orders a deployment
Resource Manager reads the dependencies between resources, deploys dependent resources in order, and deploys **independent resources in parallel**. The order in which resources are written in the file does not matter.
## Implicit and explicit dependencies in Bicep
- **Implicit**: when one resource declaration references another resource's symbolic name (for example `vnet.properties.subnets[0].id` or `vnet.id`), Bicep makes the referencing resource depend on the referenced one. A nested child resource and a resource that sets `parent:` also depend on their parent implicitly.
- **Explicit**: `dependsOn: [ otherResource ]`, for the rare case where there is no property reference but an order is still required.
## Guidance from the documentation
When an implicit dependency exists, **don't add an explicit one**. Unnecessary dependencies slow deployments because they stop Resource Manager from deploying in parallel, and `dependsOn` is not a way to document relationships: deployed resources do not keep their deployment dependencies.
W: Implicit dependency: referencing `vnet` by symbolic name in the NIC's subnet property already tells Resource Manager the NIC depends on the VNet, so the explicit dependsOn adds nothing.
X: A=Parallel unless dependsOn: resources do deploy in parallel when independent, but this NIC is not independent; the symbolic-name reference already creates the dependency.
B=References resolved after deployment: the opposite is true; Bicep uses symbolic-name references to build the dependency graph that controls deployment order.
D=Top-to-bottom order: Resource Manager ignores the order of declarations in the file and orders resources only by their dependencies.
T: In Bicep, a symbolic-name reference creates an implicit dependency; add dependsOn only when there is no such reference.

K: C
G: ## Child resources in ARM JSON versus Bicep
In **Bicep**, a nested child resource or a resource with `parent:` gets an implicit dependency on its parent.
In **ARM JSON** templates this is different: Microsoft's documentation states that an implicit dependency **isn't automatically created** between a child resource and its parent. If the child must be deployed after the parent, set `dependsOn` yourself, even when the child is nested inside the parent's `resources` array.
## Ways to create a dependency in ARM JSON
- **Explicit**: `"dependsOn": [ "[resourceId('Microsoft.Sql/servers', parameters('serverName'))]" ]`.
- **Implicit**: the `reference()` and `list*()` functions create a dependency when you pass the resource **name**; passing a resource ID does not create one.
## Why order in the file does not help
Resource Manager deploys independent resources in parallel and does not use the order of the array, so a child without a dependency can race its parent.
W: Explicit dependsOn on the server: this is the documented fix for an ARM child resource; with the server's resource ID in dependsOn, the database is created only after the server deployment has finished.
X: A=Array order: Resource Manager does not deploy in the order resources are written; without a dependency the two still deploy in parallel.
B=Serial mode: `mode` and `batchSize` belong to a copy element and only stagger instances of the same loop; they do not make one resource wait for a different resource.
D=Matching API versions: API versions select the resource schema; they have no effect on deployment ordering.
T: In ARM JSON, nested child resources do not get an implicit dependency on their parent; add dependsOn (Bicep's parent property or nesting does this for you).

S: An admin decompiles a legacy template with `az bicep decompile --file main.json` and deploys main.bicep with the old JSON parameters file. It fails: parameter `Security.Tenant.Id` is not defined in the template. The ARM template had that parameter. What is the most likely cause?

G: ## Decompiling ARM JSON to Bicep
`az bicep decompile --file main.json` (or `bicep decompile main.json` without the Azure CLI) creates `main.bicep` in the same folder; add `--force` to overwrite an existing `main.bicep`. Visual Studio Code also offers **Decompile into Bicep** and **Paste JSON as Bicep**.
Decompilation is a starting point, not a guaranteed one-to-one translation:
- There is no guaranteed mapping from JSON to Bicep; you may need to fix warnings and errors, and some templates can't be converted.
- Converted files are functionally equivalent, but their syntax can differ from the original.
## Names with periods
Bicep identifiers, including parameter names, may contain only **letters, digits and underscores**. ARM JSON allows periods in parameter names, so the decompiler replaces them with underscores: Microsoft's example turns `Security.Authentication.AAD.Tenant` into `Security_Authentication_AAD_Tenant`. Any parameters file or pipeline that passes the old name must be updated.
## Typical workflow
`az group export --name rg-app > main.json`, then `az bicep decompile --file main.json`, then review names and parameters.
W: Periods replaced by underscores: the decompiled file now declares `Security_Tenant_Id`, so the parameters file still passing `Security.Tenant.Id` refers to a parameter that no longer exists.
X: A=Parameters without defaults dropped: the decompiler keeps parameters with or without defaults and converts their allowed values and descriptions into decorators.
C=JSON parameters files unsupported: Bicep deployments accept JSON parameters files as well as `.bicepparam` files; the failure is about one parameter name, not the file type.
D=Converted into variables: parameters stay parameters after decompiling; only the identifier is changed to a legal Bicep name.
T: After az bicep decompile, review the output: names with periods become underscores and other constructs may need manual fixes.

K: A
G: ## Deployment scopes
Every deployment targets a scope, and the scope decides which command you use:
- Resource group: `az deployment group create --resource-group <rg>` (PowerShell `New-AzResourceGroupDeployment`).
- Subscription: `az deployment sub create --location <location>` (PowerShell `New-AzSubscriptionDeployment`).
- Management group: `az deployment mg create --location <location>` (plus the target management group).
- Tenant: `az deployment tenant create --location <location>`.
For scopes above the resource group the command needs a **location**: it is where the deployment's own data is stored, not where the resources go.
## Setting the scope in Bicep
A Bicep file is resource-group scoped by default. `targetScope = 'subscription'` makes it a subscription deployment, which can declare `Microsoft.Resources/resourceGroups` resources and then deploy into them with a module whose `scope` is the resource group.
## Example
`targetScope = 'subscription'`, then `resource rg 'Microsoft.Resources/resourceGroups@...' = { name: 'rg-net' location: 'westeurope' }` and `module vnet 'vnet.bicep' = { name: 'vnetDeploy' scope: rg }`.
W: Subscription deployment: a file with `targetScope = 'subscription'` must be deployed with `az deployment sub create`, and subscription-level commands require `--location` for the deployment metadata.
X: B=Complete mode: complete mode only decides whether unlisted resources in the target group are deleted; it does not change the scope, and subscription-level deployments don't support complete mode anyway.
C=Management group scope: resource groups are child resources of a subscription, and the file declares subscription scope, so the management group command does not match the file.
D=Bicep can't create groups: Bicep can create resource groups from a subscription-scoped file; creating them by hand defeats the purpose and the scope mismatch would remain.
T: Match the command to the file's targetScope: subscription-scoped Bicep (for example, one that creates resource groups) uses az deployment sub create with --location.

@ AZ-104 D3 T3.1 applied use-case
S: An ARM template hard-codes `"sku": { "name": "Standard_LRS" }` for a storage account. The admin must let each deployment choose Standard_LRS or Standard_GRS, keeping LRS as the default and rejecting other values. Which TWO edits are required? (Select TWO)
A: In the parameters section, add storageSku of type string with defaultValue Standard_LRS and allowedValues listing Standard_LRS and Standard_GRS.

D: In the storage account resource, add a dependsOn entry for storageSku so the SKU value is resolved before the account is created.
E: In the outputs section, add an output named storageSku of type string whose value is the SKU name that the account was deployed with.

G: ## Template sections
An ARM JSON template has these main sections:
- `parameters`: values supplied at deployment time. A parameter can have a `type`, a `defaultValue`, `allowedValues` and `metadata`. A value outside `allowedValues` makes the deployment fail during validation.
- `variables`: values computed inside the template; they can't be set from outside and have no `allowedValues`.
- `resources`: what to deploy; values are read with `[parameters('name')]` and `[variables('name')]`.
- `outputs`: values returned after deployment.
## The edit
`"parameters": { "storageSku": { "type": "string", "defaultValue": "Standard_LRS", "allowedValues": [ "Standard_LRS", "Standard_GRS" ] } }`
and in the resource: `"sku": { "name": "[parameters('storageSku')]" }`.
## Bicep equivalent
`@allowed([ 'Standard_LRS', 'Standard_GRS' ])` on separate lines, then `param storageSku string = 'Standard_LRS'`, and `sku: { name: storageSku }` in the resource. This is exactly how `az bicep decompile` converts `allowedValues` and `defaultValue`.
W: A=Parameter with allowedValues: a parameter is the only section that accepts a value at deployment time, and defaultValue plus allowedValues give LRS as the default and reject anything else.
C=Reference the parameter: the hard-coded SKU must be replaced with `[parameters('storageSku')]`; otherwise the new parameter exists but the account still always gets Standard_LRS.
X: B=Variable with allowedValues: variables are computed inside the template, can't be supplied by the deployer and don't support allowedValues.
D=dependsOn for a parameter: dependsOn lists resources that must be deployed first; parameters are resolved before any resource deploys and can't be dependencies.
E=Output of the SKU: an output only reports a value after deployment; it does not let the deployer choose the SKU or restrict the allowed values.
T: To make a hard-coded value configurable, declare a parameter (with defaultValue and allowedValues as needed) and reference it in the resource.

G: ## Secure parameters
Parameters are recorded in the deployment, so a plain `string` parameter's value can be read later in the deployment history. To prevent that, Bicep marks parameters as sensitive with a decorator:
`@secure()`
`param adminPassword string`
With `@secure()`, Resource Manager treats the value as sensitive and does **not** log or display it in deployment history, the Azure portal or command-line output. In ARM JSON the same thing is the `secureString` or `secureObject` type. `@secure()` is valid only for `string` and `object` parameters.
## Other parameter decorators
- `@allowed([...])`: restricts values.
- `@minLength()` / `@maxLength()`: validates length; it does not hide anything.
- `@description()`: help text for whoever deploys the file.
## Better still
Instead of typing the password, the deployment can pull it from Azure Key Vault (the `getSecret` function in a `.bicepparam` file), and the parameter stays `@secure()`.
W: @secure() decorator: it is the documented way to mark a string parameter as sensitive, so Resource Manager keeps the password out of deployment history, the portal and command-line output while still accepting it at deploy time.
X: A=Move into a variable: a variable is set inside the file, so the password would be hard-coded in source and can no longer be passed at deploy time.
C=minLength: length decorators only validate the value; they don't change how it is logged or displayed.
D=Output with listKeys(): outputs are also stored in deployment history, so returning the password adds another exposure, and listKeys() reads a resource's access keys rather than masking a value.
T: Mark passwords and other secrets as @secure() parameters (secureString in ARM JSON) so they never appear in deployment history.

G: ## Outputs
The `output` keyword in Bicep (the `outputs` section in ARM JSON) returns values when a deployment finishes, for example an endpoint, a resource ID or a generated name. Outputs can also be loops, such as `[for i in range(0, storageCount): storageAcct[i].id]`.
## Reading outputs later
The values are stored with the deployment in the **deployment history** of the scope (here the resource group), so they can be read at any time without redeploying:
- Azure CLI: `az deployment group show -g rg-data -n stgDeploy --query properties.outputs.blobEndpoint.value`
- Azure PowerShell: `(Get-AzResourceGroupDeployment -ResourceGroupName rg-data -Name stgDeploy).Outputs.blobEndpoint.value`
## Things to keep in mind
- If you deploy again with the same deployment name, the earlier history entry is replaced.
- Each scope keeps up to 800 deployments; older ones are deleted automatically, which does not affect the resources.
- Don't return secrets as plain outputs; they are stored in the history too.
W: Deployment show with a query: outputs are stored with the named deployment, and `properties.outputs.<name>.value` returns the endpoint directly from the deployment history.
X: A=show-connection-string: this command builds a connection string for a storage account; it does not read the outputs stored with a deployment.
C=What-if: what-if predicts resource changes; it does not return the stored outputs of an earlier deployment.
D=Group export: an export generates a template from current resources; it contains no output values from earlier deployments.
T: Deployment outputs live in the deployment history; read them with az deployment group show --query properties.outputs.<name>.value or Get-AzResourceGroupDeployment.

@ AZ-104 D3 T3.1 advanced use-case
S: A Bicep file updates 10 web apps in a loop: `resource sites '...' = [for name in appNames: {...}]`. For a production change, the admin wants Resource Manager to update only two apps at a time and start the next pair after the previous pair finishes. Which TWO statements are correct? (Select TWO)
A: Adding the `@batchSize(2)` decorator directly above the resource loop makes Resource Manager deploy the instances in batches of two.
B: Without a decorator, the loop instances deploy one at a time in the array order, so the change only needs a smaller array per run.
C: Adding `dependsOn: [ sites ]` inside the loop body makes each app wait for the previous one and limits the run to two at a time.
D: With a batch size, Resource Manager creates a dependency on earlier instances, so it starts a batch only after the previous one ends.
E: Setting `--mode Complete` on the deployment command makes Resource Manager process loop instances in pairs instead of all at once.
K: A,D
G: ## Loops run in parallel by default
A Bicep `for` loop (or an ARM `copy` element) creates its instances **in parallel** by default, with no order guaranteed. That is fast but risky when updating production resources.
## Serial batches
- Bicep: put `@batchSize(n)` above the looped resource, for example `@batchSize(2)` and then `resource sites '...' = [for name in appNames: { ... }]`. For one-at-a-time deployment use `@batchSize(1)`.
- ARM JSON: in the `copy` element set `"mode": "serial"` and `"batchSize": 2`. The batch size can't exceed the loop's count.
With a batch size, Resource Manager creates a dependency on earlier instances, so a batch starts only after the previous batch completes. This staggers updates so only a few resources change at once.
## Example
Ten apps with `@batchSize(2)`: apps 1-2 deploy, then 3-4 after both finish, and so on, five rounds in total.
W: A=@batchSize(2): this decorator on a resource loop tells Resource Manager how many instances to deploy concurrently, which is two here.
D=Dependency on earlier instances: with a batch size set, Resource Manager adds dependencies so a batch begins only after the previous batch completes.
X: B=Serial by default: loop instances deploy in parallel by default and their order is not guaranteed; nothing limits them to one at a time.
C=dependsOn the loop: dependsOn orders a resource after other resources; it has no setting for how many loop instances run at once, so it can't express pairs of two.
E=Complete mode: the deployment mode only decides whether unlisted resources in the group are deleted; it has nothing to do with how loop instances are batched.
T: Loops deploy in parallel; use @batchSize(n) in Bicep (or mode serial with batchSize in ARM JSON) to roll out n instances at a time.
