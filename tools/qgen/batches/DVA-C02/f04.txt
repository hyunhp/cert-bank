S: A developer wants to find which API endpoint generated the most 5xx errors over the past 24 hours using CloudWatch Logs Insights on a log group where every request logs an endpoint field and a statusCode field. Which query fragment achieves this?
A: fields endpoint, statusCode | filter statusCode >= 500 | sort statusCode desc | limit 1
B: fields endpoint, statusCode | stats avg(statusCode) as avgStatus by endpoint | sort avgStatus desc
C: filter statusCode >= 500 | stats count(*) as errorCount by endpoint | sort errorCount desc
D: filter endpoint like /5/ | stats count(*) as errorCount by statusCode | sort errorCount desc
K: C
G: ## Finding the top error source with Logs Insights
Logs Insights processes events through a pipeline of commands separated by `|`:
- `filter statusCode >= 500` keeps only server errors (500 to 599).
- `stats count(*) as errorCount by endpoint` groups the remaining events by endpoint and counts each group, producing one row per endpoint.
- `sort errorCount desc` puts the endpoint with the most errors at the top; adding `limit 1` would return only that row.
The query runs over the time range you pick in the console or API, here the last 24 hours.
Example result:
- `/checkout` 412
- `/cart` 57
- `/search` 3
Because JSON fields such as `endpoint` and `statusCode` are discovered automatically, numeric comparisons like `>= 500` work directly.
W: Filter, count by endpoint, sort descending: filtering to status codes of 500 or above, counting per endpoint with `stats count(*) as errorCount by endpoint` and sorting descending ranks endpoints by number of 5xx errors, with the worst one first.
X: A=Filter, sort by statusCode, limit 1: the filter is right, but nothing is counted or grouped, so this returns one single event with the highest status code, not the endpoint with the most errors.
B=avg(statusCode) by endpoint: the average of status codes mixes successes and errors into a meaningless number; an endpoint with many 5xx errors among many 200s can average lower than one with a few 404s.
D=filter endpoint like /5/: this matches endpoints whose path contains the digit 5, not responses with 5xx status, and then counts by status code instead of by endpoint.
T: To rank sources of errors, filter to the error condition, `stats count(*) by` the grouping field, then sort the count descending.
V: CloudWatch Logs

S: A multi-tenant SaaS application stores all tenants' data in a single shared Amazon RDS PostgreSQL database and table. The development team wants to ensure a query executed under one tenant's context can never accidentally return another tenant's records, even if a query is missing a WHERE clause filter due to a bug. Which native PostgreSQL/RDS feature helps enforce this at the database level?
A: Row-level security policies enabled on the table
B: Automated backups with point-in-time recovery
C: IAM database authentication for each app user
D: A Multi-AZ deployment with a synchronous standby
K: A
G: ## PostgreSQL row-level security (RLS)
In a pooled multi-tenant table every row has a `tenant_id`. Relying on each query to include `WHERE tenant_id = ?` means one forgotten filter leaks data. **RLS** moves that filter into the database.
Example:
- `ALTER TABLE orders ENABLE ROW LEVEL SECURITY;`
- `CREATE POLICY tenant_isolation ON orders USING (tenant_id = current_setting('app.tenant_id'));`
- The app runs `SET app.tenant_id = 'tenant-42'` at the start of each request.
Now even `SELECT * FROM orders` returns only tenant-42's rows. RLS works on Amazon RDS for PostgreSQL and Aurora PostgreSQL. Note that the table owner bypasses RLS unless `FORCE ROW LEVEL SECURITY` is set, and superusers or roles with `BYPASSRLS` always bypass it, so the app should connect with a normal role.
W: Row-level security policies: the database applies the tenant filter from the policy to every query automatically, so a missing WHERE clause cannot expose another tenant's records.
X: B=Automated backups with point-in-time recovery: they allow recovery after data loss or corruption; they do nothing to restrict which rows a query returns.
C=IAM database authentication: it replaces passwords with IAM tokens to log in, but once connected the session can read every row the database role can.
D=Multi-AZ with a synchronous standby: it keeps a standby for failover and availability; queries see the same data regardless.
T: Authentication decides who connects; RLS decides which rows each tenant's session can see, even when the query forgets to filter.
V: Amazon RDS

@ DVA-C02 D3 T3.4 advanced use-case +DVA-C03:D3
S: A team runs a containerized application on Amazon ECS and wants to perform a blue/green deployment where a new task set is deployed alongside the old one, traffic is shifted via a load balancer, and the old task set is only terminated after validation succeeds. Which AWS service is designed to orchestrate this ECS blue/green deployment pattern?
A: AWS Config (conformance packs)
B: AWS Trusted Advisor (fault tolerance checks)
C: Amazon Inspector (ECR image scanning)
D: AWS CodeDeploy (ECS compute platform)
K: D
G: ## Blue/green on Amazon ECS with CodeDeploy
In an ECS blue/green deployment, the running tasks (blue) keep serving while a second set of tasks with the new task definition (green) starts next to them.
With the CodeDeploy ECS compute platform:
- The ECS service uses the `CODE_DEPLOY` deployment controller, and CodeDeploy creates a replacement task set.
- An Application or Network Load Balancer has two target groups and a production listener (optionally a test listener). Green tasks register in the second target group.
- Lifecycle hooks such as `AfterAllowTestTraffic` can run a Lambda function to validate green before production traffic moves.
- Traffic shifts all at once, in a canary or linearly, and CloudWatch alarms can trigger automatic rollback.
- After validation and an optional wait time, CodeDeploy terminates the original task set.
Amazon ECS also offers its own built-in blue/green deployment strategy, but among these choices only CodeDeploy is a deployment service.
W: CodeDeploy on the ECS compute platform: it is built to run ECS blue/green deployments, creating the replacement task set, shifting load balancer traffic between target groups, running validation hooks and terminating the old task set only after success.
X: A=AWS Config conformance packs: Config records resource configurations and evaluates them against rules for compliance; it never deploys tasks or shifts traffic.
B=Trusted Advisor fault tolerance checks: Trusted Advisor gives account-level best-practice checks for cost, security, limits and fault tolerance; it has no deployment or traffic-shifting features.
C=Inspector image scanning: Inspector scans EC2 instances, container images and Lambda functions for software vulnerabilities and network exposure; it does not orchestrate releases.
T: ECS blue/green with task sets, load balancer traffic shifting and validation hooks is a CodeDeploy job; Config, Trusted Advisor and Inspector audit resources rather than deploy them.
V: CodeDeploy, Amazon ECS

S: A team is rolling out a new feature-flag value using AWS AppConfig and wants to minimize the blast radius if the change causes errors, automatically halting the rollout if a specified CloudWatch alarm enters ALARM state. Which AppConfig capability provides this?
A: A deployment strategy (growth rate, bake time) with environment monitors
B: A Lambda alias with weighted routing between two function versions
C: An API Gateway stage variable that holds the flag value for each stage
D: A CodeDeploy AppSpec lifecycle hook that runs a validation function
K: A
G: ## AppConfig deployment strategies and monitors
AppConfig rolls out a new configuration version gradually according to a **deployment strategy**:
- **Deployment time**: how long the rollout takes in total.
- **Growth type and factor**: linear (e.g. 20% more targets per step) or exponential.
- **Final bake time**: how long AppConfig keeps watching after reaching 100%.
The environment has **monitors**, which are CloudWatch alarms. If a monitored alarm enters ALARM during the rollout or bake time, AppConfig stops and rolls back to the previous configuration. Predefined strategies such as `AppConfig.Linear50PercentEvery30Seconds` exist, or you define your own.
W: Deployment strategy with environment monitors: growth and bake time limit how many targets see the new flag value, and a monitor (the CloudWatch alarm) entering ALARM makes AppConfig stop and roll back automatically.
X: B=Lambda alias weighted routing: it shifts invocations between function versions, so it applies to code deployments, not to a flag value delivered by AppConfig.
C=API Gateway stage variable: it is a static per-stage value, with no gradual rollout, monitoring or rollback.
D=CodeDeploy AppSpec hook: hooks run scripts or functions during CodeDeploy application deployments; they are not part of AppConfig configuration rollouts.
T: For configuration and flags, AppConfig limits blast radius with a deployment strategy and rolls back on CloudWatch alarms.
V: AWS AppConfig, CloudWatch

S: A developer wants to test a Lambda function locally, simulating the Lambda execution environment and invoking it with sample event payloads, before deploying to AWS. Which AWS tool supports this?
A: AWS CloudTrail (Lake queries)
B: AWS Config (custom Lambda rules)
C: CloudWatch Synthetics (canaries)
D: AWS SAM CLI (sam local invoke)
K: D
G: ## Local testing with AWS SAM CLI
The **AWS Serverless Application Model (SAM) CLI** is a command-line tool for building, testing and deploying serverless applications.
`sam local invoke` runs a function locally inside a Docker container that emulates the Lambda runtime and execution environment for the chosen runtime and architecture.
- Pass a sample event with `-e event.json`; generate realistic payloads with `sam local generate-event`, for example `sam local generate-event s3 put`.
- `sam local start-api` runs API Gateway routes locally, and `sam local start-lambda` exposes a local Lambda endpoint for automated tests.
- Environment variables and the template's settings (memory, timeout, handler) are applied as in the cloud.
Example: `sam local invoke OrderFunction -e events/sqs.json` runs the handler with a sample SQS batch and prints the response and logs in seconds.
W: SAM CLI with `sam local invoke`: it emulates the Lambda environment in a container on the developer's machine and invokes the function with sample event payloads before any deployment.
X: A=CloudTrail Lake queries: CloudTrail records API calls made in an AWS account for auditing, and Lake queries that history; it cannot run code locally.
B=Config custom Lambda rules: these are deployed functions that Config calls to evaluate the configuration of AWS resources; they do not emulate Lambda for local testing.
C=CloudWatch Synthetics canaries: canaries run scripted checks against deployed endpoints on a schedule; they do not emulate Lambda locally.
T: Use the SAM CLI (`sam local invoke`, `sam local start-api`) to run Lambda functions locally with sample events before deploying.

S: An application connects to an Amazon RDS for MySQL instance, and the security team requires that all connections use SSL/TLS. Developers report that some client connections still succeed without SSL. What should be done to fully enforce encrypted connections?
A: Set require_secure_transport to ON in a custom DB parameter group
B: Turn on encryption at rest with a KMS key by restoring from a snapshot
C: Rotate the master user password regularly with Secrets Manager
D: Convert the instance to a Multi-AZ deployment with a standby
K: A
G: ## TLS on RDS for MySQL
RDS for MySQL instances have a server certificate, so clients can connect with TLS. By default, though, the server also accepts unencrypted connections; TLS is used only if the client asks for it.
To force it, set the DB parameter `require_secure_transport` to `1` (ON) in a **custom DB parameter group** attached to the instance. The server then rejects any connection that does not use TLS.
- You can also require it per user with `ALTER USER 'app'@'%' REQUIRE SSL;`.
- Clients should verify the server with the RDS CA bundle (for example `--ssl-mode=VERIFY_IDENTITY`).
## Example
Before the change, `mysql -h db... --ssl-mode=DISABLED` connects. After setting `require_secure_transport=1`, the same command fails with an error saying insecure transport is prohibited.
W: require_secure_transport in a custom parameter group: it makes the database server itself refuse any non-TLS connection, closing the gap left by clients that do not request TLS.
X: B=Encryption at rest with KMS: this encrypts data, logs, backups and snapshots on storage. It does not change whether client connections are encrypted.
C=Password rotation with Secrets Manager: rotation limits the damage of a leaked password but has nothing to do with the connection being encrypted.
D=Multi-AZ with a standby: Multi-AZ adds a standby for failover and availability. The standby uses the same settings, so plaintext connections would still be accepted.
T: Encryption at rest and credentials do not force TLS; on RDS for MySQL, set `require_secure_transport` in the parameter group.
V: Amazon RDS

S: A Lambda function must call a private RDS database in a VPC. What must be configured?
A: A public IP address on the function plus an inbound rule on the database
B: A Lambda layer that packages the database endpoint and its credentials
C: Function VPC settings that list VPC subnets and a security group
D: An internet gateway added to the route table of the database subnet
K: C
G: ## How Lambda reaches private resources
By default a Lambda function runs in a network owned by the Lambda service. It can reach public internet endpoints but not resources that only have private IPs inside your VPC, such as an RDS instance in private subnets.
To reach them, you add a **VPC configuration** to the function:
- **Subnets**: Lambda creates Hyperplane elastic network interfaces in these subnets, giving the function a private IP path into the VPC. Choose private subnets in at least two Availability Zones for resilience.
- **Security group**: attached to those interfaces. The database's security group then allows inbound on the DB port (for example `3306` for MySQL) from the function's security group.
- The execution role needs the EC2 network-interface permissions, which the managed policy `AWSLambdaVPCAccessExecutionRole` provides.
If the function in the VPC also needs the internet, route its subnets through a NAT gateway or use VPC endpoints for AWS services.
W: Function VPC settings with subnets and a security group: this places network interfaces for the function in the VPC so it can open connections to the database's private endpoint, with security groups controlling the traffic.
X: A=Public IP plus inbound rule: Lambda functions cannot be given public IPs, and a public IP would not help reach a database that only has a private address anyway.
B=Layer with endpoint and credentials: a layer only packages code or files; knowing the endpoint and credentials does not create a network path, and secrets belong in Secrets Manager rather than a layer.
D=Internet gateway on the database subnet: that would move the database toward public exposure, which is the opposite of the goal and still gives the function no private route into the VPC.
T: Private VPC resources require attaching the function to the VPC (subnets + security group); credentials or public networking do not create that path.
V: AWS Lambda

S: Running sam build from the repository root fails with 'Template file not found'. The template is at infra/app.yaml. What fixes it?
A: Commit infra/app.yaml to the repository before running sam build
B: Run sam build --template-file infra/app.yaml from the same folder
C: Rename the file to template.json and keep it in the infra/ folder
D: Copy infra/app.yaml into .aws-sam/build and run sam build again
K: B
G: ## How the SAM CLI finds a template
`sam build` looks for a template in the **current directory** by default, normally `template.yaml` (`template.yml` and `template.json` are also accepted). If you run it from a folder without one, it fails with "Template file not found".
Two fixes:
- Point at the file: `sam build --template-file infra/app.yaml` (short form `-t`).
- Or `cd` to the folder with the template before building.
The build result goes to `.aws-sam/build`, and later `sam deploy` uses the built template from there. Example: `sam build -t infra/app.yaml && sam deploy --guided`.
W: --template-file: it tells the SAM CLI exactly where the template is, so the build finds `infra/app.yaml` without moving or renaming anything.
X: A=Commit to the repository: `sam build` reads files from the local disk; source control does not affect how the CLI locates a template.
C=Rename to template.json in infra/: the default lookup is in the current directory (the repository root), so a renamed file in another folder is still not found.
D=Copy into .aws-sam/build: that directory is build output that `sam build` generates and overwrites; it is not where the CLI looks for the source template.
T: SAM looks for the template in the current directory; use `-t` / `--template-file` when it lives elsewhere.
V: AWS SAM
