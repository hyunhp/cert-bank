S: A Lambda function needs up to 10 minutes to process a file, and another team calls it synchronously through API Gateway. What is the issue?
A: Lambda's maximum timeout of five minutes is shorter than the job needs
B: API Gateway's integration timeout is shorter than the processing time
C: Long-running Lambda work has to be started by an S3 event notification
D: API Gateway must sit in a different Region from the function it calls
K: B
G: ## Two timeouts in one request path
When API Gateway calls Lambda synchronously, the client waits for both.
- **Lambda timeout**: up to 15 minutes (900 seconds), so a 10-minute job fits in Lambda itself.
- **API Gateway integration timeout**: 29 seconds by default for REST APIs, and at most 30 seconds for HTTP APIs. Regional and private REST APIs can request a higher limit, but holding an HTTP connection open for many minutes is still a poor design.
If the integration times out, the client receives a `504` while the function may still be running.
## The asynchronous pattern
Accept the request, start the work in the background, and return right away:
- API Gateway invokes Lambda asynchronously, or sends a message to SQS or starts a Step Functions execution.
- Return `202 Accepted` with a job ID.
- The client polls `GET /jobs/{id}` or is notified (webhook, WebSocket, SNS).
W: API Gateway integration timeout: the synchronous API call is limited to about 29 to 30 seconds by default, far shorter than 10 minutes of processing, so the caller times out even though Lambda could finish.
X: A=Five-minute Lambda limit: the maximum Lambda timeout is 15 minutes, so a 10-minute job is within Lambda's limits.
C=Started by S3 events: Lambda can be invoked asynchronously in many ways, including directly with the `Event` invocation type, via SQS, EventBridge or Step Functions; the invocation source is not the problem here.
D=Different Region: API Gateway invoking a Lambda function in the same Region is the most common serverless setup.
T: The bottleneck is API Gateway's short integration timeout, not Lambda's 15-minute limit; long work behind an API should be made asynchronous.

S: A cache-aside implementation returns stale data after database updates. Which change improves freshness?
A: Increase the cache TTL to several days so entries are reloaded less often
B: Retire the database and serve both reads and writes from the cache
C: Invalidate or update the cache entry when the database is written
D: Use the cache as a fallback that is read when the database is slow
K: C
G: ## Why cache-aside can serve stale data
In cache-aside (lazy loading), the app reads from the cache first and only loads from the database on a miss. If the database row changes later, the cache still holds the old copy until the entry expires. Users keep seeing old values for up to the full TTL.
## Keeping the cache fresh
Two common fixes, often used together:
- **Invalidate on write**: after updating the database, delete the key (`DEL user:42`). The next read misses and loads the new value.
- **Write-through**: after updating the database, also write the new value into the cache.
A modest TTL stays as a safety net, so any entry that was missed by the write logic still refreshes eventually.
Example: a profile update writes to RDS, then deletes `user:42`; the very next profile view fetches and caches the new name.
W: Invalidate or update on write: removing or replacing the cache entry whenever the database is written means the next read gets the latest value instead of an old copy.
X: A=TTL of several days: a longer TTL keeps old entries alive longer, so stale reads get worse, not better.
B=Retire the database: a cache is volatile, typically not the system of record, and may evict or lose data; it does not address consistency.
D=Cache as fallback: the cache is then read exactly when it is most likely stale, and the performance benefit is lost during normal operation.
T: Stale cache-aside data is fixed by invalidating or updating the cache on each database write, with a TTL as a backstop.

@ DVA-C02 D1 T1.1 advanced definition +DVA-C03:D1
S: A Lambda function calls a partner API that returns 429 and 503 errors during bursts. 500 concurrent invocations retry immediately, making things worse, and the function must finish within 10 seconds. Which approach fits BEST?
A: A fixed 2-second sleep between retries in each concurrent invocation
B: Immediate retries with the attempt count raised to 10 per invocation
C: Capped exponential backoff with jitter, limited attempts within the timeout
D: Raise the function timeout to 15 minutes to leave room for more retries
K: C
G: ## Why immediate retries make things worse
When a dependency returns `429 Too Many Requests` or `503 Service Unavailable`, it is overloaded. If 500 invocations all retry at once, the partner gets another wave of 500 requests at the same moment, which keeps it overloaded (a "retry storm").
## Exponential backoff with jitter
- **Exponential backoff**: wait longer after each failure, for example 100 ms, 200 ms, 400 ms, 800 ms.
- **Cap**: never wait more than a maximum, for example 2 seconds.
- **Jitter**: pick a random wait between 0 and the computed value, so callers spread out instead of retrying in sync. A common formula is `sleep = random(0, min(cap, base * 2^attempt))`.
- **Limited attempts**: stop after a few tries so the total time stays inside the budget, here the 10-second function timeout, and then fail or hand the work to a queue.
The AWS SDKs use the same idea for AWS API calls; for a partner API you implement it yourself or with a retry library.
W: Capped exponential backoff with jitter and limited attempts: randomized, growing waits spread the 500 callers over time so the partner can recover, and the attempt cap keeps each invocation within its 10-second limit.
X: A=Fixed 2-second sleep: the invocations still retry at the same moments, so the load arrives in synchronized waves, and a fixed interval does not back off as the partner stays overloaded.
B=Immediate retries, 10 attempts: this multiplies the burst up to ten times with no pause, deepening the overload that is causing the `429` and `503` errors.
D=15-minute timeout: the requirement is to finish within 10 seconds, and a longer timeout without backoff keeps hammering the partner longer while paying for idle compute.
T: Retry overloaded dependencies with capped exponential backoff plus jitter and a bounded number of attempts, not with fixed or immediate retries.
V: AWS Lambda

G: ## What encryption context is
Encryption context is a set of non-secret key-value pairs, such as `{"tenantId":"acme"}`, that you pass to KMS operations like `Encrypt` and `GenerateDataKey`.
- KMS binds it cryptographically to the ciphertext as **additional authenticated data**.
- `Decrypt` succeeds only if the caller supplies **exactly the same** context. Encrypting with `tenantId=acme` and decrypting with `tenantId=globex` fails.
- The context appears in CloudTrail logs, which helps auditing ("who decrypted data for which tenant").
## Using it for tenant isolation
Key policy or IAM conditions such as `kms:EncryptionContext:tenantId` can limit a tenant's role to decrypting only data encrypted for that tenant, even when all tenants share one KMS key.
Because the context is not secret, do not put sensitive values in it.
