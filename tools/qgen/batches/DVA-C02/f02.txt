# DVA-C02 fixes: Performance Insights reached end of life on 2026-07-31 (now CloudWatch Database Insights)

@ DVA-C02 D4 T4.3 advanced troubleshooting
S: An RDS-backed application has slow response times only during peak hours. A developer opens Amazon CloudWatch Database Insights (which replaced RDS Performance Insights) for the instance and sees that a small number of SQL queries account for the vast majority of database load during those periods. What should the developer do next to pinpoint the performance bottleneck?
A: Examine the top SQL wait events in Database Insights, then optimize or index those queries
B: Turn off Database Insights, since it reports only symptoms of the load and never the causes
C: Delete slow query log entries so that a lower baseline database load is calculated
D: Increase the instance size immediately so the peak-hour load fits on more vCPUs
K: A
G: ## From Performance Insights to Database Insights
Amazon RDS Performance Insights reached **end of life on July 31, 2026**, and AWS migrated its users to **Amazon CloudWatch Database Insights**. The **Standard mode** (the default) keeps the Performance Insights capabilities: DB load, top SQL and wait events. The **Advanced mode** adds longer included retention, per-query statistics, execution plan and lock analysis, and fleet-wide views.
## What the DB load view shows
Database Insights measures **database load** as average active sessions (AAS): how many sessions are running or waiting at each moment. The load chart can be sliced by:
- **Waits**: what sessions are waiting on, such as CPU, disk I/O, or row locks.
- **Top SQL**: which statements contribute most of the load, with their wait breakdown.
- Hosts, users and databases.
## Using it during peaks
Example: at 12:00 load jumps to 8 AAS on a 4-vCPU instance, and one `SELECT ... WHERE customer_id = ?` accounts for most of it, waiting on I/O. That points to a missing index or an inefficient plan: running `EXPLAIN` and adding an index on `customer_id` can remove the bottleneck without paying for a larger instance.
W: Examine top SQL waits and optimize: the DB load view already shows that a few statements cause most of the load; drilling into their wait events explains why they are slow (I/O, locks, CPU), and tuning or indexing those queries fixes the root cause.
X: B=Turn off Database Insights: its purpose is to connect load to specific SQL statements and wait events, which is the cause, not a symptom. Turning it off removes the best diagnostic data right when it is needed.
C=Delete slow query log entries: deleting log records does not change the queries or the load; it only destroys evidence. No metric becomes more accurate by hiding slow queries.
D=Increase instance size immediately: scaling up costs more and may only mask an inefficient query, for example a full table scan still grows with the data. Diagnose and fix the top statements before resizing.
T: When a few queries dominate database load in Database Insights (the successor of Performance Insights), fix those queries (waits, plans, indexes) before adding hardware.
