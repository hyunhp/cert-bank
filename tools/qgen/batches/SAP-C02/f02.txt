@ SAP-C02 D1 T1.3 applied use-case +DOP-C02:D3
S: A company running a fleet of on-premises VMware VMs needs to implement disaster recovery to AWS with continuous replication (an RPO of seconds) and the ability to fail over entire servers within minutes, without re-architecting the application. Which AWS service is purpose-built for this?
A: AWS Backup with hourly backup plans for the on-premises VMware VMs
B: AWS Transform MGN configured for a one-time server migration only
C: AWS DataSync tasks copying the VM file shares to Amazon S3
D: AWS Elastic Disaster Recovery (DRS) with continuous replication
K: D
G: ## AWS Elastic Disaster Recovery (DRS)
DRS protects physical servers, VMware VMs and cloud instances by replicating them to AWS.
- An **agent** on each source server sends **continuous block-level replication** to a low-cost staging area subnet in your AWS account, giving an RPO of seconds.
- On failover, DRS launches **recovery instances** on Amazon EC2 from the latest state or an earlier point in time, typically within minutes, with no application changes.
- You can run **drills** at any time without stopping replication, and **fail back** to the source environment after the outage.
## DR is not migration
**AWS Transform MGN (formerly AWS Application Migration Service)** uses a similar replication engine, but its workflow ends at a cutover: servers are moved once and the source is retired. DRS keeps replicating indefinitely, keeps point-in-time recovery snapshots, and supports repeated drills and failback.
## Example
A VMware SQL Server VM is replicated continuously; during a data center outage it is launched as an EC2 instance from the state a few seconds before the failure, and later failed back on premises.
W: Elastic Disaster Recovery: it continuously replicates whole servers at block level and launches them on EC2 within minutes, which is exactly lift-and-shift DR without re-architecting, with drills and failback built in.
X: A=AWS Backup: it takes scheduled backups, so the RPO is the backup interval (an hour here), and restoring VMs from backups does not give minute-level failover of entire servers.
B=AWS Transform MGN for one-time migration: AWS Transform MGN (formerly AWS Application Migration Service) is built to cut servers over once; it is not the service for ongoing DR with repeated drills, point-in-time recovery and failback.
C=DataSync to S3: it copies files and objects between storage systems; it does not replicate server disks or launch bootable recovery instances.
T: For continuous server replication to AWS with minutes of recovery time, use Elastic Disaster Recovery; backups, migration and file copy tools serve other goals.
V: AWS Elastic Disaster Recovery

S: A company with 80 accounts in 3 Regions must continuously measure compliance against CIS AWS Foundations and PCI DSS, view one consolidated score per standard, and automatically route new critical findings to a ticketing system. Which solution fits BEST?
A: AWS Artifact reports for CIS and PCI DSS downloaded monthly and reviewed by auditors
B: AWS Security Hub CSPM org-wide with cross-Region aggregation and EventBridge routing
C: Trusted Advisor security checks with organizational view and weekly email reports

K: B
G: ## Posture checks across an organization
**AWS Security Hub CSPM** (cloud security posture management) continuously evaluates resources against **security standards**, including the CIS AWS Foundations Benchmark and PCI DSS, using AWS Config rules underneath. Each standard gets a **security score**, the percentage of passed controls.
## Organization-wide setup
- A **delegated administrator** account in AWS Organizations enables Security Hub CSPM and the chosen standards in every member account, including new ones, through central configuration policies.
- **Cross-Region aggregation** pulls findings from linked Regions into one home Region, so 80 accounts across 3 Regions appear in one view with one score per standard.
- Every finding is sent to **Amazon EventBridge**. A rule matching, for example, severity `CRITICAL` with workflow status `NEW` can invoke a Lambda function or an API destination that opens a ticket.
## Example
The security account is the delegated administrator, `us-east-1` is the aggregation Region, and an EventBridge rule sends new critical PCI DSS findings to the ticketing system's API.
W: Security Hub CSPM org-wide with aggregation and EventBridge: it measures CIS and PCI DSS controls continuously in every account, shows one score per standard for the whole organization after aggregation, and EventBridge rules route new critical findings to ticketing automatically.
X: A=AWS Artifact reports: Artifact provides AWS's own compliance reports, such as AWS's PCI DSS attestation. They say nothing about how your accounts are configured, and a monthly download is not continuous monitoring.
C=Trusted Advisor security checks: Trusted Advisor has a limited set of security checks that are not organized as CIS or PCI DSS controls, gives no per-standard score, and weekly emails do not route individual findings to tickets.
D=Inspector CIS scans: Inspector's CIS scans assess operating-system settings inside EC2 instances. They do not check account-level controls such as CloudTrail, IAM or S3 settings, and do not produce a PCI DSS score.
T: Continuous, standards-based posture scoring across many accounts and Regions is AWS Security Hub CSPM with a delegated administrator and aggregation; EventBridge turns its findings into automated tickets.
V: AWS Security Hub CSPM, Amazon EventBridge

@ SAP-C02 D4 T4.1 advanced definition
S: A manufacturing execution system is tightly coupled to plant-floor controllers with millisecond latency needs, and its vendor supports only on-premises installation. The rest of the data center is moving to AWS. The company keeps the system on premises with Direct Connect to AWS and will revisit the decision in 3 years. Which strategy applies to this system?
A: Rehost: lift and shift it to EC2 with AWS Transform MGN
B: Retain: keep it on premises for now, with hybrid connectivity
C: Retire: decommission it and replace it with plant-floor scripts
D: Relocate: move it to VMware Cloud on AWS unchanged
K: B
G: ## Retain (revisit)
Not every application should move in the first wave. **Retain** means keeping an application in its current environment for now, usually for a concrete reason, and scheduling a later review.
Common reasons:
- Tight coupling to local hardware, such as plant-floor controllers needing millisecond response.
- Vendor support only for on-premises installation.
- Recent hardware investment or pending replacement decisions.
## Making retain work in a hybrid estate
A retained system still has to talk to the migrated workloads. Hybrid connectivity such as **AWS Direct Connect** or a Site-to-Site VPN links it to AWS, and the portfolio records a revisit date.
## Example
A manufacturing execution system stays next to the production line, exchanges data with analytics in AWS over Direct Connect, and is reassessed in three years.
W: Retain: the system stays on premises because of latency and vendor-support constraints, connected to AWS through Direct Connect, with a planned review in three years.
X: A=Rehost with AWS Transform MGN: AWS Transform MGN (formerly AWS Application Migration Service) would move the server into an AWS Region, which adds network distance to the controllers and breaks the vendor's on-premises-only support terms.
C=Retire: the system still runs the plant floor; retiring it and replacing it with scripts would remove a needed, vendor-supported production system.
D=Relocate to VMware Cloud on AWS: relocate still moves the workload into AWS, so it has the same latency and support problems as rehosting.
T: An application that must stay where it is for now, with hybrid links and a planned review, is retained; every move to AWS breaks the latency and vendor constraints.
V: AWS Direct Connect

@ SAP-C02 D4 T4.2 applied use-case
S: A company needs to migrate 150 physical and virtual on-premises servers to AWS with minimal application downtime during cutover, and wants to test the migrated instances in an isolated environment before finalizing the cutover. Which service and approach best satisfies these requirements?
A: AWS Database Migration Service in full-load-only mode for each server's data
B: AWS DataSync, running a nightly full copy of each server's disks to EBS snapshots
C: AWS Transform MGN with continuous block-level replication and test launches
D: AWS Snowball Edge devices to physically ship server images to AWS
K: C
G: ## How AWS Transform MGN works
**AWS Transform MGN (formerly AWS Application Migration Service)** is the main AWS service for rehosting physical, virtual and cloud servers onto Amazon EC2.
- A **replication agent** on each source server continuously copies its disks at the **block level** to a staging area subnet in the target AWS account.
- Replication keeps running while the source stays in production, so the copy stays nearly current.
- **Test launches** start instances from the replicated data in the subnets you choose, so you can validate them in isolation without affecting the source or the replication.
- **Cutover** launches the final instances after a short stop of the source, so downtime is minutes rather than hours.
## Example
Install agents on 150 servers, wait for initial sync, run test launches per wave, fix launch settings, then cut over each wave in a short window.
W: AWS Transform MGN with block-level replication and test launches: continuous replication keeps cutover downtime minimal, and test launches validate each server in an isolated subnet before the final cutover.
X: A=DMS full-load-only: DMS migrates database tables, not whole servers, and a full load without change data capture means downtime while data is copied.
B=DataSync nightly copies to EBS snapshots: DataSync copies files between storage services; it does not replicate server disks into bootable instances, and nightly copies lose up to a day of changes.
D=Snowball Edge server images: shipping devices takes days and the data is stale on arrival, which does not meet a minimal-downtime cutover or provide test launches. Snowball Edge is also closed to new customers.
T: Rehosting many servers with minimal downtime and pre-cutover testing is AWS Transform MGN; DMS and DataSync move data, not servers.
V: AWS Transform MGN

@ SAP-C02 D4 T4.2 advanced use-case
S: A company must move 80 TB from an on-premises NFS server to Amazon EFS over a 10 Gbps Direct Connect link. The source keeps changing until cutover, file permissions and timestamps must be preserved, and data integrity must be verified. Which service fits BEST?
A: AWS Transform MGN replicating the NFS server's volumes to EC2.
B: The aws s3 sync command run repeatedly to an S3 bucket.
C: AWS DataSync with incremental tasks and a final sync.
D: AWS Transfer Family, with the NFS data uploaded to EFS over SFTP.
K: C
G: ## What AWS DataSync does
AWS DataSync is a managed service for copying file and object data between on-premises storage and AWS storage services such as Amazon EFS, FSx and S3.
- A DataSync **agent** (a VM on premises) reads from the NFS share and sends data over the network, which can be a Direct Connect link.
- Each **task** compares source and destination and transfers only new or changed files after the first run.
- It preserves file metadata such as POSIX permissions, ownership and timestamps.
- It verifies integrity with checksums during transfer and can verify the destination afterwards.
- Bandwidth limits and schedules keep production traffic safe.
## Migration pattern
Example: an initial task copies the 80 TB over several days while users keep working. Incremental runs catch up on changes. At cutover, writes stop, one final short task copies the last changes, and clients remount the EFS file system.
W: DataSync with incremental tasks and a final sync: it moves NFS data directly into EFS over Direct Connect, preserves permissions and timestamps, verifies integrity, and the final incremental pass captures the last changes at cutover.
X: A=AWS Transform MGN: AWS Transform MGN (formerly AWS Application Migration Service) replicates whole servers block by block onto EC2 with EBS volumes; the result would be an NFS server on EC2, not data in Amazon EFS.
B=aws s3 sync: the command writes to an S3 bucket, not to EFS, and it does not preserve POSIX ownership and permissions or offer DataSync's task-level verification of the destination.
D=Transfer Family over SFTP: Transfer Family provides SFTP/FTPS/FTP endpoints for users and partners to exchange files; it is not a bulk migration tool with scheduled incremental sync and verification of 80 TB from an NFS share.
T: For large, changing NFS data sets going to EFS with metadata and verification, use DataSync; AWS Transform MGN moves servers, and s3 sync and Transfer Family are not migration tools for EFS.
V: AWS DataSync, Amazon EFS

@ SAP-C02 D4 T4.1 advanced use-case
S: Before migrating 300 on-premises servers, a company needs process-level information and network dependencies between servers to group applications into migration waves. Which approach provides this data?
A: Run AWS Trusted Advisor checks against the on-premises servers to report how they depend on each other.
B: Install discovery agents in each server's OS to record processes and connections, then group into waves.
C: Import a CMDB spreadsheet of server names, CPU and memory sizes, and owners as the wave plan.
D: Collect only hypervisor-level VM inventory and utilization from vCenter, without any in-guest data.
K: B
G: ## Discovery before migration
To group 300 servers into migration waves, you need to know which servers talk to each other; otherwise one wave might move an application while its database stays behind.
## What data you need and where it comes from
- **Inventory and sizing** (CPU, memory, disks, OS) can come from a CMDB export or from the hypervisor, for example vCenter.
- **Process-level data** (which program runs on the server and which program opened a connection) is visible only from **inside the operating system**, so it needs a lightweight agent or script installed on each server.
- **Network dependencies** come from recording inbound and outbound connections over a representative period, usually several weeks so that monthly batch jobs also show up.
## From dependency data to waves
Servers that communicate are grouped into an **application** (a dependency group), and each group is moved in the same wave so no application loses its database or its upstream service during the migration.
## Tooling note
AWS Application Discovery Service and AWS Migration Hub provided this agent-based collection, but both stopped onboarding new customers on 2025-11-07 (existing customers can keep using them). AWS now points new migrations to **AWS Transform**, and partner discovery tools collect the same kind of data. The design approach is the same whatever tool collects it.
## Example
The agent on `app-07` shows the `java` process opening connections to `db-12` on port `1521`, so both servers join the same dependency group and move in wave 2.
W: Agent-based discovery with dependency grouping: an agent inside each OS sees which processes run and which connections they open, which is exactly the process-level and dependency data needed to build dependency groups and plan the waves.
X: A=Trusted Advisor: Trusted Advisor inspects resources and settings in AWS accounts; it cannot examine on-premises servers or their connections.
C=CMDB spreadsheet as the wave plan: an import records names and sizes you already know, but it contains no process or connection data, so dependencies stay unknown and waves may split applications.
D=Hypervisor-level vCenter inventory only: it gives inventory and utilization of VMware VMs, but not the process-level detail that is only visible from inside each OS, and it does not cover physical servers at all.
T: Wave planning needs dependency groups, and process-level dependency data comes from agents inside each server's OS recording connections over time; inventories and hypervisor data alone do not show it.
V: AWS Transform

@ SAP-C02 D4 T4.2 advanced use-case
S: A company is migrating an on-premises Oracle database to Aurora PostgreSQL with minimal downtime. Which combination fits?
A: AWS Transform MGN replicating the Oracle server to EC2 only
B: A single DMS full-load task during a weekend with the application offline
C: Export Oracle tables to CSV, copy them to S3, and import them manually
D: AWS SCT to convert the schema and code, then AWS DMS with full load and CDC
K: D
G: ## Heterogeneous database migration
Moving from Oracle to Aurora PostgreSQL changes the engine, so two things must happen:
- **Schema and code conversion**: tables, indexes, views and PL/SQL procedures must become PostgreSQL equivalents. The AWS Schema Conversion Tool (or DMS Schema Conversion in the DMS console) converts most objects automatically and produces an assessment report listing items that need manual work.
- **Data movement with little downtime**: AWS DMS runs a **full load** of existing data and then **change data capture (CDC)**, reading Oracle's redo logs (with supplemental logging enabled) and applying ongoing changes to Aurora.
## Cutover
While CDC keeps the target in sync, you test against Aurora. At cutover you stop writes to Oracle, wait for DMS to apply the last changes, and switch the application's connection string, so downtime is minutes rather than hours.
## Example
A DMS task of type `full-load-and-cdc` with Oracle as the source endpoint and Aurora PostgreSQL as the target.
W: SCT plus DMS with full load and CDC: SCT converts the Oracle schema and code for PostgreSQL, and DMS copies the data then keeps it synchronized until a short cutover.
X: A=AWS Transform MGN to EC2: AWS Transform MGN (formerly AWS Application Migration Service) rehosts the Oracle server as-is on EC2, so the database is still Oracle and never becomes Aurora PostgreSQL.
B=One full-load task over a weekend: without CDC the application must stay offline for the whole copy, which is not minimal downtime, and the schema and code still are not converted.
C=CSV exports imported manually: exports capture only a point in time, lose constraints and procedural code, and need a long outage to avoid missing changes.
T: Oracle to Aurora PostgreSQL with minimal downtime means SCT for conversion plus DMS full load and CDC; rehosting keeps Oracle, and full load alone needs a long outage.
V: AWS DMS, AWS SCT

@ SAP-C02 D4 T4.4 applied use-case
S: A company wants to modernize a batch job that runs on an always-on EC2 instance for 20 minutes each hour. Which approach reduces cost and operations?
A: Run the job as an Amazon ECS task on AWS Fargate, started every hour by EventBridge Scheduler
B: Run the job manually each hour from an engineer's laptop instead of the EC2 instance
C: Keep the instance running all day and purchase a Reserved Instance to lower its hourly rate
D: Move the job to a larger EC2 instance type that is also kept running 24/7 for faster completion
K: A
G: ## Paying only while the job runs
A job that runs 20 minutes each hour on an always-on instance leaves the server idle about two thirds of the time, yet you pay for all 24 hours and must still patch the OS.
## Scheduled serverless containers
- Package the job as a container image in Amazon ECR and define an **Amazon ECS task definition** with the CPU and memory it needs.
- **AWS Fargate** runs the task without any EC2 instance to manage; capacity exists only while the task runs.
- **Amazon EventBridge Scheduler** starts the task on a schedule such as `rate(1 hour)` or a cron expression, using an ECS `RunTask` target with the cluster, subnets and security groups.
- You pay for vCPU and memory per second only while the task runs, there is no OS to patch, and logs go to CloudWatch Logs.
## Example
EventBridge Scheduler runs the task at minute 0 of every hour; each run takes about 20 minutes, so about 8 hours of compute per day are billed instead of 24.
W: Scheduled ECS task on Fargate: capacity exists only while the job runs, which removes idle cost and server management, and EventBridge Scheduler replaces the always-on host as the trigger.
X: B=Manual runs from a laptop: depends on a person being available every hour, has no retries or audit trail, and puts production execution on an unmanaged device.
C=Reserved Instance: a reservation lowers the hourly rate but still pays for the roughly 40 idle minutes each hour and keeps all server operations such as patching.
D=Larger always-on instance: a bigger instance costs more per hour and is still idle most of the time, so cost rises rather than falls.
T: For periodic jobs, remove the idle server with a scheduled ECS task on Fargate; discounts on an always-on instance still pay for idle time.
V: Amazon ECS, AWS Fargate, Amazon EventBridge Scheduler
