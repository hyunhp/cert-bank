@ Q001169 explain
G: ## Tracking a multi-tool migration
Large migrations rarely use one tool. Servers may move with AWS Application Migration Service (MGN), databases with AWS DMS, and some apps with partner tools. The program office needs one view of what has started, is in progress or is complete.
## AWS Migration Hub
- Provides a single place to group servers and databases into **applications** and see migration status per application.
- Receives status updates from integrated AWS migration services and from partner tools that integrate with it, so progress from different tools appears together.
- Can use discovery data (for example, from AWS Application Discovery Service or imports) to build the application inventory.
- Availability note: AWS closed Migration Hub to new customers in November 2025 and points new migrations to AWS Transform; existing customers can keep using it, and the tracking role described here is what the question tests.
- Example: an application "Billing" groups 6 servers moved by MGN and 1 database moved by DMS; the console shows it as in progress until all 7 finish.
Current name: AWS Application Migration Service (AWS MGN) is now documented as AWS Transform MGN. The exam guide and this question keep the older name.
W: AWS Migration Hub: it is designed to aggregate migration status from multiple AWS and partner migration tools into one console, so the office can track 200 applications without building custom reports.
X: A=AWS Config: it records resource configurations and evaluates compliance rules; it does not know the migration state of on-premises applications.
B=AWS Systems Manager: it manages and operates instances (patching, run commands, inventory), but it does not aggregate migration progress from MGN, DMS and partner tools.
D=AWS Organizations: it manages multiple accounts, consolidated billing and policies; it has no view of application migration status.
T: One console for migration progress across several tools is Migration Hub; Config, Systems Manager and Organizations manage resources and accounts, not migrations.

@ Q001175 explain
G: ## Relocate versus rehost
Both strategies move workloads without changing the applications, but they land on different platforms.
- **Relocate** moves VMs to a VMware environment running in AWS, classically **VMware Cloud on AWS**, a VMware software-defined data center (now sold by Broadcom) on dedicated bare-metal hosts in AWS. **Amazon Elastic VMware Service** (Amazon EVS) is a newer AWS option that runs VMware Cloud Foundation on EC2 bare-metal instances in your own VPC. vCenter, vSphere and the operations team's tooling stay the same, and VMs can move with vMotion or VMware HCX without being converted.
- **Rehost** with **AWS Application Migration Service** (MGN) replicates each server at block level and launches it as a native EC2 instance. After cutover the VMs are no longer VMware objects, so vCenter-based tooling and processes no longer apply.
## When relocate wins
Relocate is chosen when speed and continuity matter most: hundreds of VMs, a team that wants to keep VMware operations and licensing during a transition, and a plan to modernize later. Rehost is chosen when the goal is native EC2 and exit from the hypervisor stack.
Current name: AWS Application Migration Service (AWS MGN) is now documented as AWS Transform MGN. The exam guide and this question keep the older name.
W: Relocate with VMware Cloud on AWS: VMs move at the hypervisor level with existing vCenter, vMotion and VMware licensing, while MGN would convert each VM into a native EC2 instance and leave the VMware tooling behind.
X: B=Refactor: keeping VMware tooling requires no application change at all; refactoring means re-architecting code, which is slower and contradicts the "minimal changes" goal.
C=Relocate and rehost are identical: they end on different platforms, VMware SDDC hosts versus native EC2, with different tooling, operations and licensing.
D=Relocate supports only Windows: VMware Cloud on AWS runs the guest operating systems vSphere supports, including Linux; there is no Windows-only restriction.
T: Keep the VMware stack and move fast means relocate; convert to native EC2 means rehost with Application Migration Service.

@ Q001178 explain
G: ## What the Migration Hub home Region is
**AWS Migration Hub** is a single place to track discovery and migration progress across tools such as Application Migration Service and Database Migration Service. Each account chooses a **home Region**, and all discovery and tracking data for that account is stored and shown there.
- The home Region is only where tracking data lives; migrations can still target any Region.
- The console in the home Region shows the consolidated view. Data reported to a different home Region is not merged in.
- Availability note: Migration Hub stopped accepting new customers on November 7, 2025, and AWS recommends AWS Transform for new migration programs; existing customers can continue to use it.
## What happens with two home Regions
If one team reports to `us-east-1` and another to `eu-west-1`, the tracking data ends up in two separate places. Nothing syncs them, so a PMO watching `us-east-1` never sees the European work.
Example: the European team can keep replicating servers into `eu-west-1`, but its Migration Hub status must be reported to the same home Region the PMO uses.
Current name: AWS Application Migration Service (AWS MGN) is now documented as AWS Transform MGN. The exam guide and this question keep the older name.
W: One home Region for everyone: Migration Hub stores tracking data only in the configured home Region, so all teams must report to the same one, here `us-east-1`, to get a single consolidated view.
X: A=Automatic cross-Region sync: Migration Hub does not replicate tracking data between home Regions; that is exactly why the PMO cannot see the European status.
B=Delete and recreate migration jobs in us-east-1: the migration target Region is not the problem; replication can continue into `eu-west-1`. Only the tracking home Region needs to be aligned.
C=Unresolvable, separate hubs forever: unified visibility is the purpose of Migration Hub; it is achieved by standardizing on one home Region.
T: Migration Hub consolidates data in one home Region; migrations can go to any Region, but every team must report to the same home Region.

@ Q003050 explain
G: ## Tracking a large migration
A large migration uses many tools at once: discovery tools inventory servers, AWS Application Migration Service rehosts servers, AWS DMS moves databases, and partner tools may handle other workloads. Leaders need one place to see which applications are not started, in progress or completed.
## AWS Migration Hub
**AWS Migration Hub** is that central view.
- Servers and databases are grouped into **applications**.
- Integrated AWS and partner migration tools report status updates to the hub.
- The team sees progress per application in one dashboard, regardless of which tool performs the move.
- Availability note: since November 7, 2025, Migration Hub is no longer open to new customers; existing customers can keep using it, and AWS recommends AWS Transform for new migration and modernization projects.
Current name: AWS Application Migration Service (AWS MGN) is now documented as AWS Transform MGN. The exam guide and this question keep the older name.
W: Migration Hub: it aggregates status from AWS and partner migration tools and shows progress per application in one place, which is exactly the central view requested.
X: A=Control Tower: Control Tower builds and governs a multi-account landing zone with guardrails; it does not track the progress of individual application migrations.
C=Health Dashboard: the AWS Health Dashboard reports AWS service events and scheduled changes that affect your resources, not migration status.
D=Well-Architected Tool: it reviews workloads against best-practice pillars and records improvement plans; it has no view of migration waves or tool status.
T: Migration Hub is the single pane for migration progress across tools; Control Tower, Health and Well-Architected cover governance, service events and design reviews.

@ Q001069 explain
G: ## S3 Storage Lens
S3 Storage Lens gives organization-wide visibility into S3 usage and activity. From the management account or a delegated administrator, one **organization dashboard** can cover every account and Region.
- **Free metrics** include storage bytes and object counts, noncurrent version bytes, incomplete multipart upload bytes, and some encryption and replication status metrics, aggregated by organization, account, Region and bucket.
- **Advanced metrics and recommendations** (paid) add activity metrics, contextual recommendations, prefix-level detail and 15 months of history instead of 14 days.
- A **metrics export** writes the data daily to an S3 bucket in CSV or Apache Parquet format for analysis with Athena or QuickSight.
Example: the dashboard shows that 30% of bytes in one account are noncurrent versions, suggesting a lifecycle rule to expire them.
Current name: Amazon QuickSight is now documented as AWS Quick Sight, a feature of AWS Quick, with the same APIs and integrations. The exam guide and this question keep the older name.
W: Storage Lens organization dashboard with daily export: it aggregates all 900 buckets across the 70 accounts, shows growth, noncurrent versions and incomplete uploads, adds cost-saving recommendations with the advanced tier, and exports metrics daily.
X: A=CloudWatch storage metrics: the daily metrics cover bucket size and object count only, so there is no view of noncurrent versions or incomplete uploads, no recommendations, and dashboards must be stitched together across accounts.
B=Trusted Advisor S3 checks: they check bucket configuration such as permissions, logging, versioning or whether an abort-incomplete-multipart-upload lifecycle rule exists, but give no storage growth or noncurrent-version metrics and no daily metrics export.
D=S3 Inventory plus Athena and QuickSight: it can work, but you must configure inventory on 900 buckets and build every metric, aggregation and recommendation yourself, which is far more effort.
T: Organization-wide S3 usage metrics with recommendations and daily exports come built in with Storage Lens; inventory and CloudWatch need heavy custom work.

@ Q003116 explain
G: ## The most detailed billing data AWS offers
**AWS Cost and Usage Reports**, now delivered through **Data Exports** as **CUR 2.0**, contain line items for every service, usage type, resource ID, pricing and discount, and cost allocation tag.
- Granularity can be **hourly**, daily or monthly.
- Exports are delivered to an Amazon S3 bucket in `Parquet` or CSV format and refreshed several times a day.
- Created in the management (payer) account, they include usage for all member accounts.
- The data can be queried with **Amazon Athena** (for example by creating a table over the Parquet files) and visualized in Amazon QuickSight.
Example: an Athena query that sums `line_item_unblended_cost` grouped by `line_item_usage_account_id` for one billing period gives spend per account for that month.
Current name: Amazon QuickSight is now documented as AWS Quick Sight, a feature of AWS Quick, with the same APIs and integrations. The exam guide and this question keep the older name.
W: C=Cost and Usage Reports (CUR 2.0) to S3: it is the only option providing hourly, resource-level cost and usage for every account in a format Athena can query directly.
X: A=Health Dashboard event history: it lists service events and scheduled maintenance affecting your resources; it contains no cost or usage data.
B=Free Tier usage alerts: they only warn when free tier usage approaches its limit in one account; they give no detailed, organization-wide cost data.
D=Monthly invoice PDF: it is a summary for the whole month, not hourly line items, and a PDF cannot be queried with Athena.
T: For hourly, line-item cost analysis across accounts, export CUR 2.0 to S3 and query it with Athena; invoices and alerts are summaries.
