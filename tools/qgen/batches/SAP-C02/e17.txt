@ Q001118 explain
G: ## Why metrics hide slow calls
CloudWatch metrics are aggregates, such as average latency per service per minute. If 2 percent of requests are slow because one downstream call occasionally takes 3 seconds, averages barely move.
## Distributed tracing with X-Ray
AWS X-Ray follows single requests across services:
- Each request gets a **trace ID**, passed along in the `X-Amzn-Trace-Id` header.
- Each service records a **segment** with its timing, and **subsegments** for downstream calls such as a DynamoDB query or an HTTP call to another service.
- The **trace map** shows services and their latencies and errors; a single trace's timeline shows exactly which hop took the time.
Services are instrumented with OpenTelemetry (AWS Distro for OpenTelemetry, which AWS now recommends over the older X-Ray SDKs), and Lambda, API Gateway and others can enable tracing with a setting. CloudWatch Application Signals builds on the same trace data.
Note: the AWS X-Ray SDKs and the X-Ray daemon entered maintenance mode on 2026-02-25 (security fixes only), and AWS recommends OpenTelemetry (AWS Distro for OpenTelemetry) for new instrumentation. X-Ray itself, active tracing and the trace console are unchanged, and exam questions may still name the X-Ray SDK.
W: X-Ray tracing across the services: traces show each request's path and the time spent in every segment, so the specific slow service call can be identified even when aggregate metrics look normal.
X: A=More CPU alarms: CPU utilization says whether a host is busy, not which call in a request chain is slow. A slow downstream dependency often causes no CPU increase at all.
B=VPC Flow Logs with manual correlation: flow logs record IP connections and bytes, not application requests or their latency, and correlating timestamps by hand across services is slow and imprecise.
D=1-second high-resolution metrics: finer metrics are still aggregates per service. They show when latency rises but not which call inside a specific request was slow.
T: To find the slow hop in a distributed request, trace individual requests (X-Ray); metrics and alarms only show aggregates.

G: ## Building a migration business case
Before a large migration, leadership usually asks what the company spends today and what it would spend on AWS. The answer must come from real utilization, because on-premises servers are often heavily over-provisioned and a like-for-like price comparison overstates cloud cost.
## AWS Migration Evaluator
**AWS Migration Evaluator** (formerly TSO Logic) collects on-premises inventory and utilization data, for example with its agentless collector or from existing tool exports, then:
- Right-sizes each workload to a matching EC2 instance based on observed use.
- Models licensing options, such as bring-your-own versus license-included.
- Produces a report comparing current on-premises cost with projected AWS cost.
Example: 1,000 servers averaging 15% CPU are modeled on smaller instances, giving a TCO case built on measured usage rather than server nameplate capacity.
Note: AWS Transform assessments now also build the TCO business case from a server inventory, using agentic AI, and can import a Migration Evaluator Quick Insights file. SAP-C03 does not list Migration Evaluator as in scope, so for SAP-C03 expect AWS Transform for this job; this question follows the SAP-C02 guide.
W: AWS Migration Evaluator: it is purpose-built for pre-migration business cases, combining actual on-premises utilization with AWS pricing to produce a data-driven TCO comparison.
X: A=Cost Explorer forecasts: Cost Explorer analyzes and forecasts spend already incurred in AWS accounts; it has no data about on-premises servers.
C=Trusted Advisor cost checks: these checks find idle or underused resources already running in AWS; they cannot model a workload that has not migrated yet.
D=Pricing Calculator estimates: the calculator prices configurations you enter or import yourself; it does not collect on-premises utilization, right-size from it, or produce an on-premises versus AWS comparison.
T: For a pre-migration TCO case based on real on-premises utilization, use Migration Evaluator; Cost Explorer and Trusted Advisor only see what already runs in AWS.

@ Q001177 explain
G: ## Why TCO baselines go wrong
A TCO comparison has two sides. The AWS side is fairly easy to price. The on-premises side is where cases fail, because many costs never appear on a server invoice:
- **Facilities**: floor space, power, cooling, physical security.
- **Licensing**: support renewals and true-up fees.
- **Labor**: time spent patching, racking, backing up and troubleshooting.
Leave these out and the on-premises baseline looks cheaper than it is, so projected savings shrink.
## Quick view versus detailed assessment
Migration Evaluator's **Quick Insights** gives a fast, largely automated summary of projected AWS cost from the collected data. A more **detailed assessment and business case**, typically prepared with AWS migration specialists or a partner, lets you add the company's actual facility, licensing and staffing costs so the on-premises side reflects reality.
Example: adding power, space and patching hours to a 500-server estate can change the savings figure substantially.
Note: AWS Transform assessments now also build the TCO business case from a server inventory, using agentic AI, and can import a Migration Evaluator Quick Insights file. SAP-C03 does not list Migration Evaluator as in scope, so for SAP-C03 expect AWS Transform for this job; this question follows the SAP-C02 guide.
W: Detailed Migration Evaluator assessment: it lets the team add facilities, licensing true-ups and labor to the on-premises baseline, producing a complete TCO comparison before the budget decision.
X: A=Assume costs already included: the review showed those costs were missing from the baseline, so proceeding would knowingly present understated savings.
B=Cost Explorer after migration: Cost Explorer only reports AWS spend after the fact; it cannot supply the on-premises costs, and the case is needed before approval.
C=Pricing Calculator only: the calculator prices the AWS side from manual inputs; it drops the utilization-based analysis and still has no on-premises cost baseline.
T: A credible TCO needs the hidden on-premises costs (facilities, licensing, labor) in the baseline; enrich the Migration Evaluator assessment rather than switching tools.

G: ## Building a migration business case
A credible business case compares today's cost with the projected AWS cost for the same workloads. Using list prices for current server sizes overstates AWS cost, because many servers are overprovisioned and licensing options change the price.
## AWS Migration Evaluator
- It collects actual utilization with an agentless collector or imports data from existing tools and inventory exports.
- It models **right-sized** EC2 instances based on measured usage, compares purchase options, and models licensing, such as bring-your-own-license versus license-included Windows and SQL Server.
- The output is a directional business case (Quick Insights and a detailed report) that leaders can use before committing.
Example: 1,200 VMs averaging 15 percent CPU are mapped to smaller instances with Savings Plans pricing, showing a projected annual cost next to the current data center cost.
Note: AWS Transform assessments now also build the TCO business case from a server inventory, using agentic AI, and can import a Migration Evaluator Quick Insights file. SAP-C03 does not list Migration Evaluator as in scope, so for SAP-C03 expect AWS Transform for this job; this question follows the SAP-C02 guide.
W: Migration Evaluator with collected utilization: it produces a data-driven, right-sized cost projection and business case from how servers are actually used.
X: A=Free Tier calculator per server: the Free Tier is a limited allowance of free usage, not an estate-wide cost model, and pricing servers one by one ignores utilization and licensing.
B=Spreadsheet with list prices: sizing from current specs and list prices ignores real utilization and right-sizing, so the estimate is inaccurate and not data-driven.
D=Inspector security report: Inspector reports vulnerabilities on AWS resources. It produces no cost estimate and does not assess on-premises estates.
T: A right-sized, utilization-based migration cost case comes from Migration Evaluator, not from list-price spreadsheets or security tools.
