@ SAP-C02 D1 T1.4 advanced use-case
S: A central network account owns a Transit Gateway that must be used by 50 spoke accounts in an Organization to attach their VPCs, without granting those accounts any other permissions in the network account. Which approach meets these requirements?
A: Replace the transit gateway with VPC peering between each spoke VPC and a hub VPC
B: Create IAM users in the network account so each spoke team can manage its attachments
C: Have the network team create each attachment centrally after collecting spoke VPC IDs
D: Add the transit gateway to an AWS RAM resource share with the organization's accounts
K: D
G: ## Sharing a transit gateway with AWS RAM
A transit gateway lives in one account (the network account). With **AWS Resource Access Manager (RAM)** the owner creates a resource share containing the transit gateway and shares it with specific accounts, an OU or the whole organization.
- Spoke accounts see the shared transit gateway and call `CreateTransitGatewayVpcAttachment` for their own VPCs from their own accounts.
- If **auto accept shared attachments** is off, the network team accepts each attachment; either way the network team controls the transit gateway route tables.
- Spoke accounts get no IAM permissions in the network account and cannot change the transit gateway or other attachments.
Example: share `tgw-0abc` with the organization; a new account in any OU can attach its VPC the same day, and the network team associates the attachment with the right route table.
W: Resource share in AWS RAM: every account in the organization can see the transit gateway and create attachments for its own VPCs from its own account, without any IAM access to the network account, and accounts added later are covered by the same share.
X: A=VPC peering to a hub VPC: 50 peering connections are hard to manage, are not transitive, and abandon the transit gateway hub the design is built around.
B=IAM users in the network account: it hands spoke teams long-term credentials and permissions inside the network account, which the requirement forbids.
C=Network team creates each attachment: an attachment must be created from the account that owns the VPC, and funnelling every request through one team does not scale to 50 accounts.
T: Central network resources such as transit gateways are shared with RAM so owners keep control and other accounts get no extra permissions.
V: AWS Resource Access Manager (RAM), Transit Gateway, AWS Organizations

@ SAP-C02 D3 T3.3 applied use-case
S: A company runs a periodic large-scale batch processing job on Amazon EMR and wants to maximize throughput per dollar by drawing Spot capacity from many instance types and candidate Availability Zones, while keeping core nodes on On-Demand capacity for cluster stability. Which capability enables this provisioning strategy?
A: Dedicated Hosts reserved for the cluster's peak capacity in each Availability Zone
B: EMR instance groups that request one Spot instance type in a single subnet
C: EMR instance fleets with several instance types, subnets, and capacity targets
D: Reserved Instances purchased to cover the full cluster size for each periodic run
K: C
G: ## EMR instance groups versus instance fleets
An EMR cluster has primary, core and task nodes. Core nodes store HDFS data, so losing them hurts the cluster; task nodes only compute and are safe to run on Spot.
- **Instance groups** use one instance type per group and one purchasing option, so a Spot shortage for that type stalls the group.
- **Instance fleets** let each node type list many instance types (with weighted capacity), several subnets, and separate **On-Demand** and **Spot target capacities**.
## How fleets improve Spot success
At launch EMR evaluates the listed subnets and picks one Availability Zone (the cluster runs in a single AZ) with the best capacity for the requested types, then uses an allocation strategy (such as capacity-optimized for Spot) to draw from the deepest pools. A provisioning timeout can switch Spot requests to On-Demand if capacity is not found.
- Example: core fleet with an On-Demand target of 4 units; task fleet with a Spot target of 40 units across `m5`, `m6i`, `r5` and `c5` sizes.
W: EMR instance fleets: each node type can list several instance types and subnets with separate On-Demand and Spot target capacities, so Spot is drawn from the deepest pools at a good price while core nodes stay On-Demand, which is exactly the throughput-per-dollar plus stability goal.
X: A=Dedicated Hosts: they allocate whole physical servers for licensing or compliance needs and are billed per host whether or not instances fill it, which is the opposite of cheap, elastic Spot-based capacity for a periodic job.
B=Instance groups with one Spot type: an instance group uses one instance type and one purchasing option, so depending on a single Spot pool maximizes the chance of insufficient capacity and interruptions, and running the core nodes on that Spot request leaves no On-Demand capacity to keep the cluster stable.
D=Reserved Instances for each run: RIs are a 1- or 3-year billing commitment that is paid whether or not the periodic job is running, and they do nothing to diversify capacity or protect against Spot shortages.
T: Use instance fleets to spread Spot across many types and AZ choices while keeping core nodes On-Demand; a single Spot pool or long-term commitments do not fit periodic batch jobs.
V: EC2, EMR

@ SAP-C02 D1 T1.4 advanced use-case
S: A company must prevent all accounts in its organization from creating resources outside eu-west-1 and eu-central-1. Global services such as IAM, CloudFront, and Route 53 must keep working. Which SCP approach is correct?
A: A Deny SCP using NotAction to exempt global services, with an aws:RequestedRegion condition.
B: An allow-list SCP for actions in the two Regions, attached to the root in place of FullAWSAccess.
C: An IAM permissions boundary attached to each role and user that names the two approved Regions.
D: A Deny SCP for ec2:* and s3:* actions with an aws:RequestedRegion condition on the two Regions.
K: A
G: ## Restricting Regions with an SCP
Service control policies set the maximum permissions for accounts in an organization. Region restriction commonly uses a **Deny** statement with the `aws:RequestedRegion` condition key.
- Global services such as IAM, Organizations, CloudFront, Route 53 and Support send their API calls to a single Region endpoint, usually `us-east-1`. A plain "deny outside the approved Regions" would therefore also block them.
- The fix is `NotAction`: deny everything *except* the listed global actions when the requested Region is not approved.
- Because it is a Deny, it applies alongside `FullAWSAccess`, and applies to every principal in the accounts except the management account.
Example (abbreviated; AWS's published example exempts more global services): `"Effect":"Deny","NotAction":["iam:*","organizations:*","cloudfront:*","route53:*","support:*"],"Resource":"*","Condition":{"StringNotEquals":{"aws:RequestedRegion":["eu-west-1","eu-central-1"]}}`
W: Deny SCP with NotAction and aws:RequestedRegion: it blocks every action requested in other Regions while exempting the global services, so IAM, CloudFront and Route 53 keep working across every account.
X: B=Allow-list SCP replacing FullAWSAccess: allowing actions only in the two Regions would block global services whose calls are made to us-east-1, and allow-list maintenance is fragile.
C=Permissions boundaries on each principal: boundaries are set principal by principal, so any role created without one escapes, and they are not an organization-wide guardrail.
D=Deny ec2:* and s3:* outside the Regions: every other service, such as RDS or Lambda, could still create resources in unapproved Regions.
T: Organization-wide Region restriction is a Deny SCP on aws:RequestedRegion with NotAction exemptions for global services.
V: AWS Organizations, SCP

@ SAP-C02 D3 T3.4 advanced use-case
S: A company's critical application runs in one Region. The business now requires recovery within 30 minutes after a Regional outage with less than one minute of data loss, and the database is Aurora PostgreSQL. Which solution fits?
A: Aurora Global Database plus a scaled-down copy of the app running in a second Region
B: AWS Backup plans for the Aurora cluster that keep the backups in the primary Region
C: An Aurora Replica in another Availability Zone of the same Region with failover
D: Daily Aurora snapshots copied to a second Region and restored during a disaster
K: A
G: ## RTO and RPO
- **RTO** (recovery time objective): how long recovery may take, here 30 minutes.
- **RPO** (recovery point objective): how much data may be lost, here under one minute.
## Aurora Global Database
Aurora Global Database has a primary cluster in one Region and read-only secondary clusters in other Regions. Replication happens at the storage layer, so lag is typically under a second.
- In a Regional outage you can **fail over** to the secondary, which becomes the new primary within minutes. Data lost is only the small replication lag.
- For planned moves, a **switchover** changes Regions without data loss.
- For Aurora PostgreSQL, the `rds.global_db_rpo` parameter can enforce a maximum RPO.
## Warm standby
The database alone is not enough: the application tier must also run in the secondary Region. In a warm standby, a scaled-down but running copy of the application waits there and is scaled out during failover, with DNS (for example Route 53) moved to it.
W: Global Database plus a warm standby: sub-second storage-level replication keeps data loss well under one minute, and a running, scaled-down application copy plus database failover recovers within 30 minutes.
X: B=Backups in the primary Region: backups in the failed Region are unreachable during a Regional outage, and restoring from backups would not meet a one-minute RPO anyway.
C=Replica in another AZ of the same Region: a replica in the same Region protects against instance or AZ failure but fails together with the Region.
D=Daily cross-Region snapshots: up to 24 hours of data could be lost, and restoring a large snapshot plus rebuilding the stack is unlikely to fit 30 minutes.
T: Minutes of RTO and seconds of RPO across Regions for Aurora need Global Database plus a warm standby, not backups or same-Region replicas.
V: Amazon Aurora

@ SAP-C02 D2 T2.6 applied use-case
S: A new application stores large media files that are accessed frequently for 30 days and rarely afterward, but must be retrievable within milliseconds when needed. Which storage design minimizes cost?
A: S3 Standard, then a lifecycle transition to S3 Glacier Instant Retrieval at 30 days
B: S3 Glacier Deep Archive as the storage class at upload, restoring files on request
C: EBS gp3 volumes attached to the application servers to hold the media library
D: S3 Standard for the files throughout their life, with no lifecycle transitions
K: A
G: ## S3 storage classes by access pattern
- **S3 Standard**: highest storage price, no retrieval fee; right for frequently accessed data.
- **S3 Glacier Instant Retrieval**: much lower storage price, millisecond access like Standard, but a per-GB retrieval fee and a 90-day minimum storage duration. Designed for data accessed about once a quarter.
- **S3 Glacier Flexible Retrieval** and **Deep Archive**: cheaper still, but objects must be restored first, taking minutes to hours (up to 12 hours or more for Deep Archive).
## Lifecycle rules
A lifecycle rule moves objects automatically based on age, for example a `Transition` to `GLACIER_IR` after 30 days. Media files are large, so the 128 KB minimum billable object size of the infrequent-access classes does not matter here.
When access patterns are unknown, S3 Intelligent-Tiering is an alternative, but here the pattern is known.
W: Standard, then Glacier Instant Retrieval at 30 days: files are cheap to access while hot, much cheaper to store once they go cold, and still readable in milliseconds whenever needed.
X: B=Deep Archive at upload: the frequently accessed first 30 days would require restores taking hours, which breaks the millisecond requirement, and retrieval fees would pile up.
C=EBS gp3 volumes: EBS costs several times more per GB than S3, is tied to instances and AZs, and must be provisioned and grown manually for large media libraries.
D=S3 Standard for the whole life: access stays fast, but paying the Standard storage price for years of rarely accessed data is the most expensive S3 choice.
T: Known "hot then rarely read, but must be instant" data equals S3 Standard with a lifecycle transition to Glacier Instant Retrieval, not an archive class that needs restores.
V: Amazon S3

@ SAP-C02 D1 T1.2 advanced use-case
S: A company lets delegated administrators in member accounts create IAM roles for their teams, but the roles they create must stay within a permission ceiling defined by the security team. Which mechanism enforces this?
A: An iam:PermissionsBoundary condition that makes a boundary policy mandatory
B: A monthly access review of newly created roles by the central security team
C: A shared administrator login so that each role creation can be audited later
D: A tag policy that requires an owner tag on each new IAM role in member accounts
K: A
G: ## What a permissions boundary does
A permissions boundary is a managed policy attached to an IAM user or role that sets the **maximum** permissions it can have. The effective permissions are the intersection of the identity policies and the boundary: an action must be allowed by both.
## Using it for safe delegation
You let delegated administrators create roles, but only with the boundary attached:
- Allow `iam:CreateRole` and `iam:PutRolePolicy` only with the condition `iam:PermissionsBoundary` equal to the approved policy ARN, for example `arn:aws:iam::111122223333:policy/AppBoundary`.
- Deny `iam:DeleteRolePermissionsBoundary` and any change to the boundary policy itself.
Now even if an admin attaches `AdministratorAccess` to a new role, that role can still do only what `AppBoundary` allows, so privilege escalation is blocked at creation time.
W: Mandatory permissions boundary: allowing `iam:CreateRole` only when the `iam:PermissionsBoundary` condition names the approved boundary policy caps every role the delegated admins create, so they cannot grant more than the defined maximum, and IAM enforces the cap at request time.
X: B=Monthly access review: a review only finds excess permissions after they existed, possibly for weeks. It does not stop anyone from granting them.
C=Shared administrator login: shared credentials destroy accountability because you cannot tell which person acted, and they place no limit on what permissions are granted.
D=Tag policy requiring an owner tag: tag policies standardize tag keys and values. A role with a correct owner tag can still carry unlimited permissions.
T: To let others create roles without exceeding a ceiling, require a permissions boundary on every role they create; reviews and tags do not cap permissions.
V: AWS IAM

@ SAP-C02 D4 T4.1 applied use-case
S: A company has a VMware environment and wants to move VMs to AWS quickly while keeping VMware tooling and operational skills. Which strategy fits?
A: Retire the VMware workloads and rebuild them as new cloud-native services
B: Relocate the platform as-is to a vSphere environment hosted on AWS
C: Refactor the applications into AWS Lambda functions behind Amazon API Gateway
D: Repurchase SaaS products that replace the applications running on the VMs
K: B
G: ## Relocate: moving the platform, not the servers
The **relocate** strategy moves a whole virtualization platform to AWS without converting each VM. For VMware estates, options such as **Amazon Elastic VMware Service (Amazon EVS)**, generally available since August 2025, which runs VMware Cloud Foundation on EC2 bare-metal instances inside your own VPC, or **VMware Cloud on AWS**, now sold by Broadcom, run the VMware stack (vSphere, vSAN, NSX) on AWS infrastructure.
- VMs move with VMware tools such as vMotion or HCX, often without downtime or re-IP.
- Administrators keep using vCenter, runbooks and existing skills.
- Once there, workloads can later be modernized one at a time while sitting close to native AWS services.
## When it fits
Relocate is chosen when speed matters more than immediate optimization and the team wants to preserve VMware operating models during the move.
W: Relocate to VMware on AWS: the vSphere platform and tooling stay the same, so VMs move quickly and teams keep their operational skills.
X: A=Retire and rebuild: retiring working, needed workloads and rebuilding them is neither quick nor a way to keep VMware tooling.
C=Refactor to Lambda: re-architecting the applications into functions takes a long time and discards the VMware operating model entirely.
D=Repurchase SaaS: replacing the applications with SaaS products is a long procurement and data migration project and removes VMware tooling rather than keeping it.
T: When the goal is speed plus keeping VMware tools and skills, relocate the platform; the other Rs change the applications and take far longer.

@ SAP-C02 D2 T2.5 applied use-case
S: A new global application needs static IP addresses for customers to allow-list and fast failover between Regional endpoints. Which service fits?
A: Amazon CloudFront with an origin group
B: AWS Direct Connect with a hosted connection
C: Amazon Route 53 with failover routing records
D: AWS Global Accelerator with endpoint groups
K: D
G: ## AWS Global Accelerator
Global Accelerator gives an application **two static anycast IPv4 addresses** (dual-stack accelerators add IPv6) announced from AWS edge locations worldwide.
- Users connect to the nearest edge, and traffic travels over the AWS global network to **endpoint groups** in one or more Regions (ALBs, NLBs, EC2 instances or Elastic IPs).
- Health checks monitor endpoints; if a Regional endpoint becomes unhealthy, new traffic is sent to a healthy Region without any DNS change, so client DNS caching does not delay failover.
- **Traffic dials** and endpoint weights shift traffic between Regions for blue/green or maintenance.
Example: a customer's firewall allows only the accelerator's two static IPs; when `us-east-1` fails, traffic moves to `eu-west-1` behind the same two IPs.
W: Global Accelerator with endpoint groups: it provides fixed anycast IPs customers can allow-list and fails over quickly between the Regional endpoint groups using health checks, without relying on DNS changes.
X: A=CloudFront with an origin group: by default CloudFront serves from a large, changing set of edge IP addresses (static IP lists are an optional, special-purpose feature), and origin-group failover covers only GET, HEAD and OPTIONS requests of a caching CDN, not a static-IP entry point for any application traffic.
B=Direct Connect hosted connection: it provides a private network link from on premises to AWS through a partner; it does not give internet customers static IPs or failover between Regional endpoints.
C=Route 53 failover records: DNS failover returns different endpoint IPs, which breaks allow-lists, and clients may keep cached answers until the TTL expires, slowing failover.
T: Static IPs to allow-list plus fast Regional failover is Global Accelerator; Route 53 changes IPs through DNS and CloudFront is a caching CDN, not a static-IP front door.
V: AWS Global Accelerator

@ SAP-C02 D2 T2.6 applied use-case
S: A new application sends large volumes of data from EC2 to users worldwide. Which choice reduces data transfer costs?
A: Move to larger EC2 instance types that provide more network bandwidth per instance
B: Serve the content through a CloudFront distribution with the EC2 instances as origin
C: Deploy copies of the EC2 application in several Regions that are closer to the users
D: Keep serving the requests directly from the EC2 instances in a single Region
K: B
G: ## Where data transfer costs come from
AWS charges for data transferred **out to the internet**. Serving large files directly from EC2 incurs EC2 data-transfer-out rates for every byte sent to every user, and every request also uses instance capacity.
## How CloudFront changes the bill
- **Data transferred from AWS origins** (EC2, ALB, S3) **to CloudFront is not charged**.
- CloudFront has its own data-transfer-out pricing, which is generally lower than EC2 internet rates, especially at higher volume tiers.
- **Caching** at edge locations means repeated requests for the same object are served from the edge, so the origin sends it once instead of thousands of times.
Example: a 50 MB installer downloaded 100,000 times. From EC2, every download leaves the Region. Through CloudFront, the origin sends the file to each edge location a few times and the edges serve the rest, reducing origin load and transfer cost while also lowering latency for users.
W: CloudFront in front of EC2: origin-to-CloudFront transfer is free, CloudFront edge transfer rates are lower, and cached content is served without going back to EC2, which cuts both transfer cost and origin load.
X: A=Larger EC2 instances: more network bandwidth lets the instance send faster, but every byte is still billed at EC2 data-transfer-out rates and there is no caching, so cost goes up, not down.
C=Copies in several Regions: users get closer servers, but each Region still pays internet transfer for every byte, and running full fleets in several Regions adds large compute and replication costs.
D=Serve directly from one Region: this is the current costly pattern; every request pays EC2 transfer rates and far-away users also see high latency.
T: For large, repeated downloads, put CloudFront in front of the origin: free origin fetch plus edge caching lowers transfer cost, while bigger or more EC2 fleets only add cost.
V: Amazon CloudFront
