G: ## Finding single-AZ dependencies
An Availability Zone can have problems while others stay healthy. An architecture survives this only if **every layer** has capacity in more than one AZ.
## Two common hidden single points of failure
- **Single-AZ RDS**: the database runs in one AZ. With **Multi-AZ**, RDS keeps a synchronous standby in another AZ and fails over automatically, usually within a couple of minutes, and the DNS endpoint follows.
- **One zonal NAT gateway**: a zonal NAT gateway lives in one public subnet in one AZ. If private subnets in all AZs route `0.0.0.0/0` to it, an issue in that AZ breaks outbound internet access for the whole application. The classic fix is one zonal NAT gateway per AZ, with each AZ's private route table pointing to its local NAT gateway. AWS also offers a **regional NAT gateway** that automatically expands into each AZ where you have workloads, achieving the same per-AZ redundancy with one resource.
## Monitoring is not redundancy
Tools that show database load help you tune a database, but they add no standby. Note (2026-11-17): RDS Performance Insights reached end of life on July 31, 2026; its features now live in **Amazon CloudWatch Database Insights** (Standard mode), and it still adds no redundancy.
W: C=Convert the database to Multi-AZ: a synchronous standby in another AZ takes over automatically when the primary's AZ fails, removing the database as a single-AZ dependency.
E=NAT gateway in each AZ: each AZ routes outbound traffic through its own NAT gateway, so losing one AZ does not cut off egress for instances in the others.
X: A=Performance Insights: it analyzed database load and slow queries but adds no redundancy in another AZ. It reached end of life on July 31, 2026; its successor, CloudWatch Database Insights, is also a monitoring tool, not a failover mechanism.
B=Larger instance: more CPU and memory in the same AZ still fails when that AZ has problems.
D=More subnets in the same AZ: every new subnet shares the same AZ, so the failure domain does not change.
T: AZ resilience comes from redundancy in another AZ at every layer (Multi-AZ databases, per-AZ NAT gateways), not from monitoring tools such as Database Insights or bigger resources in one AZ.

G: ## What CloudWatch Logs charges for
CloudWatch Logs bills mainly for two things:
- **Ingestion**: every GB written to a log group. Verbose debug logging from every service multiplies this.
- **Storage (archival)**: every GB kept per month. By default a log group's retention is **Never expire**, so logs accumulate forever.
## The two levers
- **Retention settings** per log group (from 1 day up to 10 years) automatically delete older events. For example, `PutRetentionPolicy` with 30 days on application log groups; long-term copies, if needed, can be exported to S3 lifecycle tiers.
- **Log levels**: running production at `INFO` or `WARN` instead of `DEBUG` cuts the volume ingested at the source, which lowers both ingestion and storage costs.
## Log classes
For new log groups that are rarely queried, the **Essentials** log class (formerly named Infrequent Access; API value `ESSENTIALS`, `INFREQUENT_ACCESS` still accepted) has a lower ingestion price per GB. Storage and Logs Insights prices are the same as Standard, and a log group's class cannot be changed after creation, so it does not replace retention settings.
W: D=Retention periods: setting retention on each log group stops indefinite accumulation, so storage charges stop growing and old debug logs are deleted automatically.
E=Lower log levels: reducing production verbosity shrinks the amount of data ingested, which is usually the largest part of the bill.
X: A=More metric filters: metric filters turn log patterns into metrics; they do not delete or reduce log data, and custom metrics they publish can add cost.
B=Detailed monitoring: this sends EC2 metrics at 1-minute intervals and is charged extra; it has nothing to do with log volume or retention.
C=Second log group copy: duplicating logs into another log group doubles ingestion and storage rather than reducing them.
T: Log costs fall when you ingest less (lower log levels) and keep less (retention periods); filters, metrics and copies do not reduce stored logs.
