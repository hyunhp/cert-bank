@ SAP-C02 D1 T1.1 applied troubleshooting
S: Application teams report intermittent connectivity failures between an EC2 instance and an RDS database in the same VPC, but only during specific time windows. Which AWS capability should the architect enable to capture detailed IP-level traffic data for root-cause analysis?
A: AWS X-Ray tracing on the application to capture failed database calls and their latency
B: Amazon Inspector network reachability analysis of the paths between the two resources
C: AWS Config configuration history of the security groups and network ACLs involved
D: VPC Flow Logs on the relevant ENIs, recording which flows were accepted or rejected
K: D
G: ## What VPC Flow Logs capture
VPC Flow Logs record metadata about IP traffic on network interfaces (ENIs), subnets or whole VPCs. Each record includes source and destination IP and port, protocol, packets, bytes, start and end time and the **action**: `ACCEPT` or `REJECT`. Logs go to CloudWatch Logs, S3 or Amazon Data Firehose.
Example record: `10.0.1.15 10.0.2.40 49152 3306 6 ... REJECT` shows a MySQL connection from the app to the database that a security group or network ACL refused.
## Using them for intermittent failures
Enable flow logs on the EC2 and RDS network interfaces, then filter by time window: rejected flows point to a security group or NACL problem, while accepted flows with no reply suggest the database or application side.
Flow logs show packet metadata, not payloads; for full packet capture, VPC Traffic Mirroring is the tool.
W: Flow Logs on the ENIs: they record each flow's accept or reject decision with timestamps, so the team can see exactly what happened to the traffic during the failure windows.
X: A=X-Ray tracing: X-Ray follows requests through application code and shows that a database call failed or was slow, but not whether the network accepted or dropped the packets.
B=Inspector network reachability: Inspector analyzes configuration to show which ports could be reachable; it does not record what actually happened to traffic at a given moment.
C=Config history: Config shows when security group or network ACL rules changed, which may be a useful clue, but it does not log any traffic or its outcome.
T: To see what really happened to network traffic at a point in time, use VPC Flow Logs; configuration and tracing tools show settings or code, not packets.
V: VPC, VPC Flow Logs, CloudWatch

@ SAP-C02 D1 T1.1 applied use-case
S: A company needs to inspect all traffic between VPCs and to the internet with stateful rules and intrusion prevention, centrally. Which design fits?
A: An inspection VPC with AWS Network Firewall, routed through a transit gateway
B: A single EC2 proxy instance in a shared VPC that handles the traffic flows sent to it
C: Security groups on each instance in the VPCs, with rules that allow known CIDR ranges
D: Network ACLs on the subnets of each VPC, with explicit allow rules for expected ports
K: A
G: ## Centralized inspection with a transit gateway
In a hub-and-spoke network, every VPC attaches to a transit gateway. To inspect traffic in one place, you add an **inspection VPC** and use transit gateway route tables so that:
- Spoke VPC subnets route traffic to the transit gateway, and the transit gateway route table associated with the spoke attachments sends all traffic (`0.0.0.0/0` and other VPC CIDRs) to the inspection VPC attachment.
- The inspection VPC sends traffic through **AWS Network Firewall** endpoints, then back to the transit gateway or out through an egress NAT gateway.
## What AWS Network Firewall provides
- **Stateful rules** that track connections and match on domains, protocols and 5-tuples.
- **Intrusion prevention** using Suricata-compatible rules, including AWS managed threat signature rule groups.
- Central policy management across accounts with **AWS Firewall Manager**.
Enable **appliance mode** on the inspection VPC's transit gateway attachment so both directions of a flow go through the same AZ's firewall endpoint, keeping stateful inspection symmetric.
W: Inspection VPC with Network Firewall through a transit gateway: east-west and internet-bound traffic is routed through one managed, stateful, IPS-capable firewall that scales and can be deployed across AZs.
X: B=Single EC2 proxy: one instance is a single point of failure and a throughput bottleneck, and a proxy handles just the traffic explicitly sent to it, not VPC-to-VPC flows.
C=Security groups: they are stateful but allow traffic by port, protocol and source only; they have no intrusion prevention, and per-instance rules are the opposite of central control.
D=Network ACLs: NACLs are stateless allow and deny lists by IP and port with no payload inspection or IPS, and they are managed per subnet rather than centrally.
T: Central stateful inspection with IPS means routing traffic through Network Firewall in an inspection VPC; security groups and NACLs filter by address and port and are managed per resource.
V: AWS Network Firewall, AWS Transit Gateway

@ SAP-C02 D2 T2.6 advanced tradeoff
S: A new data lake must store 5 PB with most data rarely accessed after 90 days, but occasional audits need retrieval within 12 hours. Which storage plan minimizes cost?
A: EBS volumes attached to a fleet of EC2 instances that serve the data lake files to analysts
B: S3 Standard for the full 5 PB indefinitely, so that each audit retrieval stays instant
C: S3 Standard then lifecycle to Glacier Flexible Retrieval or Deep Archive after 90 days
D: S3 One Zone-IA for the data lake from the first day, with no lifecycle rules configured
K: C
G: ## S3 storage classes for a cold data lake
- **S3 Standard**: millisecond access, highest storage price; right for data read often.
- **S3 Glacier Flexible Retrieval**: much cheaper storage; retrieval in minutes (expedited), 3-5 hours (standard) or 5-12 hours (bulk); 90-day minimum storage duration.
- **S3 Glacier Deep Archive**: lowest storage price; standard retrieval within 12 hours, bulk within 48 hours; 180-day minimum storage duration.
## Lifecycle rules
A lifecycle configuration moves objects automatically, for example `Transition` to `GLACIER` or `DEEP_ARCHIVE` 90 days after creation. At 5 PB, the difference between Standard and archive pricing is very large every month.
Example: an audit needs 20 TB from last year; a standard or bulk restore from Glacier Flexible Retrieval, or a standard restore from Deep Archive, completes within the 12-hour window.
W: S3 Standard then lifecycle to Glacier after 90 days: recent data stays fast, rarely accessed data moves to archive classes that cost a fraction as much, and both archive classes can restore within 12 hours for audits.
X: A=EBS volumes on EC2: block storage is priced per provisioned GB and far more expensive than S3 at 5 PB, needs running instances, and is not a data lake storage layer.
B=S3 Standard indefinitely: it pays the top storage price for petabytes that are rarely read, even though a 12-hour retrieval window allows much cheaper archive classes.
D=S3 One Zone-IA without lifecycle: it stores data in a single AZ, so an AZ loss can destroy it, and without lifecycle rules it never moves to the far cheaper archive tiers.
T: When cold data only needs retrieval within hours, lifecycle it from S3 Standard to Glacier classes after the hot period instead of keeping it in costlier tiers.
V: Amazon S3

@ SAP-C02 D3 T3.5 advanced use-case
S: A company runs a steady ECS on EC2 cluster plus spiky batch tasks. It wants to lower cost without hurting the steady services. Which approach fits?
A: Run the cluster on On-Demand instances with no commitment, so that monthly costs stay predictable
B: Buy Reserved Instances sized for the highest batch peak, so that spikes are covered at a discount
C: Move the steady customer-facing services and the batch tasks to Spot Instances for the deepest discount
D: Cover the steady baseline with Savings Plans and run batch tasks on Fargate Spot or Spot capacity providers
K: D
G: ## Match the purchase model to the workload shape
- **Steady baseline**: capacity that runs all the time. Savings Plans (Compute Savings Plans cover EC2, Fargate and Lambda) or Reserved Instances give large discounts for a 1- or 3-year commitment to a steady amount of usage.
- **Spiky, interruptible work**: batch jobs that can retry. Spot capacity uses spare AWS capacity at a steep discount but can be reclaimed with a two-minute notice.
## ECS capacity providers
Amazon ECS lets each service or task choose a **capacity provider strategy**:
- An Auto Scaling group capacity provider backed by On-Demand instances for the steady services.
- `FARGATE_SPOT`, or an Auto Scaling group capacity provider using Spot Instances, for batch tasks.
Example: web services run on the On-Demand ASG covered by a Savings Plan, while nightly batch jobs use `FARGATE_SPOT` and simply retry if a task is interrupted.
W: Savings Plans plus Spot for batch: the commitment discounts the always-on baseline, and batch spikes run on cheap interruptible capacity that does not touch the steady services.
X: A=On-Demand with no commitment: it is predictable but the most expensive way to pay for capacity that runs all month, and it gives no discount on the batch spikes.
B=Reserved Instances sized for peak: the reservation is paid whether used or not, so capacity above the steady baseline sits idle between batch spikes.
C=Steady services on Spot: customer-facing services would be exposed to Spot interruptions, which risks outages for the workloads that must stay stable.
T: Commit (Savings Plans) for the baseline and use Spot for interruptible spikes; do not reserve for peaks or put steady services on Spot.
V: Amazon ECS, Savings Plans

@ SAP-C02 D3 T3.5 applied use-case
S: A company's CloudWatch Logs costs are growing because debug-level logs from all services are retained indefinitely. Which TWO actions reduce cost? (Select TWO)
A: Add metric filters that count debug messages
B: Enable detailed monitoring on EC2 instances
C: Export the logs to a second log group copy
D: Set retention periods on log groups
E: Lower log levels in production services
K: D,E
G: ## What CloudWatch Logs charges for
CloudWatch Logs bills mainly for two things:
- **Ingestion**: every GB written to a log group. Verbose debug logging from every service multiplies this.
- **Storage (archival)**: every GB kept per month. By default a log group's retention is **Never expire**, so logs accumulate forever.
## The two levers
- **Retention settings** per log group (from 1 day up to 10 years) automatically delete older events. For example, `PutRetentionPolicy` with 30 days on application log groups; long-term copies, if needed, can be exported to S3 lifecycle tiers.
- **Log levels**: running production at `INFO` or `WARN` instead of `DEBUG` cuts the volume ingested at the source, which lowers both ingestion and storage costs.
## Log classes
For new log groups that are rarely queried, the **Essentials** log class (formerly named Infrequent Access; API value `ESSENTIALS`, `INFREQUENT_ACCESS` still accepted) has a lower ingestion price per GB. Storage and Logs Insights prices are the same as Standard, and a log group's class cannot be changed after creation, so it does not replace retention settings.
W: D=Retention periods: setting retention on each log group stops indefinite accumulation, so storage charges stop growing and old debug logs are deleted automatically.
E=Lower log levels: reducing production verbosity shrinks the amount of data ingested, which is usually the largest part of the bill.
X: A=Metric filters: they turn log patterns into metrics; they do not delete or reduce log data, and the custom metrics they publish can add cost.
B=Detailed monitoring: this sends EC2 metrics at 1-minute intervals and is charged extra; it has nothing to do with log volume or retention.
C=Second log group copy: duplicating logs into another log group doubles ingestion and storage rather than reducing them.
T: Log costs fall when you ingest less (lower log levels) and keep less (retention periods); filters, metrics and copies do not reduce stored logs.
V: Amazon CloudWatch Logs

@ SAP-C02 D2 T2.3 applied use-case
S: A new web application must block common exploits and rate-limit abusive clients at the edge before traffic reaches the origin. Which design fits?
A: A security group on the ALB that allows inbound HTTPS from the company's office IP ranges
B: Network ACLs on the public subnets with deny rules for IP ranges seen in past attacks
C: An EC2 instance running a custom firewall script that inspects the incoming requests
D: CloudFront with an AWS WAF web ACL using managed rules and rate-based rules
K: D
G: ## Protecting at the edge
**Amazon CloudFront** serves traffic from edge locations worldwide. Attaching an **AWS WAF web ACL** to the distribution inspects every HTTP request at the edge, so blocked requests never reach the origin.
## What the web ACL contains
- **AWS Managed Rules** rule groups such as the Core rule set, Known bad inputs and SQL database rules block common exploits like SQL injection and cross-site scripting, and AWS keeps them updated.
- **Rate-based rules** count requests per client (by IP or other keys such as a header) over a time window and block or challenge clients that exceed a limit, for example 1,000 requests in 5 minutes.
- CloudFront also brings AWS Shield Standard for network-layer DDoS protection.
To stop attackers bypassing the edge, restrict the origin to CloudFront, for example with origin access control for S3 or a CloudFront-only prefix list on the ALB security group.
W: CloudFront with WAF managed and rate-based rules: requests are inspected at layer 7 at the edge, exploit patterns are blocked by managed rules and abusive clients are throttled before they consume origin capacity.
X: A=Security group for office IPs: it would lock out the real internet users of a public web app, and security groups cannot inspect HTTP content or rate-limit.
B=Network ACL deny rules: NACLs match IP ranges and ports, hold a small number of rules, act in the VPC rather than at the edge, and cannot see or count HTTP requests; new attacker addresses pass.
C=EC2 custom firewall: a self-managed box in the Region is a bottleneck and single point of failure, needs its own rule maintenance and does not stop traffic at the edge.
T: Layer-7 exploit blocking plus rate limiting before the origin equals AWS WAF on CloudFront; security groups and NACLs work at the IP and port level.
V: AWS WAF, Amazon CloudFront

@ SAP-C02 D1 T1.1 advanced use-case
S: A company has 60 VPCs across 25 accounts, all attached to a Transit Gateway, plus an on-premises data center connected by Direct Connect. On-premises servers must resolve records in private hosted zones owned by several accounts, and VPC workloads must resolve the on-premises domain corp.example.com. Which design has the LEAST operational overhead?
A: Run BIND DNS servers on EC2 in each VPC and configure zone transfers from the on-premises servers.
B: Create inbound and outbound Resolver endpoints in each VPC and replicate the forwarding rules by hand.
C: Convert the private hosted zones to public zones and restrict who can query them with security groups.
D: Central Resolver endpoints in a networking VPC with PHZs associated and forwarding rules shared via RAM.
K: D
G: ## Hybrid DNS with Route 53 Resolver
Every VPC has a built-in Route 53 Resolver at the VPC `+2` address. To connect it with on-premises DNS you use Resolver endpoints:
- An **inbound endpoint** gives on-premises DNS servers IP addresses in a VPC to forward queries to, so they can resolve private hosted zones associated with that VPC.
- An **outbound endpoint** plus **forwarding rules** sends queries for a domain such as `corp.example.com` to on-premises DNS servers.
**Centralized pattern:** put both endpoints in one networking VPC that is reachable over Transit Gateway and Direct Connect, associate all private hosted zones (cross-account association is allowed) with that VPC, and share the forwarding rules through **AWS RAM** so every account can associate them with its VPCs. Queries from those VPCs are then forwarded through the central outbound endpoint.
Example: on-premises servers forward `aws.example.internal` to the two inbound endpoint IPs; all 60 VPCs use one shared rule for `corp.example.com`.
W: Central Resolver endpoints with PHZs associated and rules shared via RAM: one pair of endpoints serves the 60 VPCs in both directions, and RAM sharing means new VPCs need a rule association, not new endpoints.
X: A=BIND on EC2 in each VPC: it means patching, scaling and making highly available dozens of DNS servers, and Route 53 private hosted zones do not support zone transfers to them.
B=Endpoints in each VPC with hand-replicated rules: it works but duplicates endpoint cost (each endpoint needs at least two IPs billed hourly) and rule management across 60 VPCs.
C=Public zones restricted by security groups: public zones answer anyone on the internet, and security groups cannot control who queries public DNS, so internal names are exposed.
T: For many accounts, centralize Resolver endpoints in one networking VPC and share forwarding rules with RAM instead of building DNS per VPC.
V: Amazon Route 53 Resolver, AWS RAM, AWS Direct Connect

@ SAP-C02 D2 T2.6 applied use-case
S: An S3 bucket stores millions of objects with highly unpredictable and changing access patterns; some objects are accessed frequently for weeks then never again, while others are accessed sporadically. The team wants automatic cost optimization without manual lifecycle rule tuning per object. Which storage approach fits?
A: S3 Intelligent-Tiering as the storage class for the objects
B: S3 Glacier Deep Archive as the storage class for new uploads
C: S3 Standard-IA as the default storage class for the bucket
D: A lifecycle rule moving objects to Glacier 30 days after creation
K: A
G: ## How S3 Intelligent-Tiering works
**S3 Intelligent-Tiering** monitors each object's access and moves it between tiers automatically:
- **Frequent Access** by default.
- **Infrequent Access** after 30 consecutive days without access.
- **Archive Instant Access** after 90 days without access.
- Optional **Archive Access** and **Deep Archive Access** tiers you can opt in to for asynchronous-retrieval savings.
When an object in an automatic tier is read again, it moves back to Frequent Access. There are **no retrieval fees**; you pay a small monthly monitoring fee per object (objects under 128 KB are not monitored and stay in the frequent tier).
Example: a video popular for three weeks drifts down to cheaper tiers once it goes quiet, and moves back up if it becomes popular again, with no rule to write.
W: S3 Intelligent-Tiering: it moves each object between tiers based on its real access, so unpredictable and changing usage is handled automatically without lifecycle tuning and without retrieval fees.
X: B=Deep Archive for new uploads: objects need a restore that takes up to 12 hours (48 for bulk) before they can be read, which breaks the frequently accessed objects, and it has a 180-day minimum storage charge.
C=Standard-IA as default: hot objects would pay per-GB retrieval fees on every read, and Standard-IA has a 30-day minimum and 128 KB minimum billable size, so frequently read data can cost more than in Standard.
D=30-day rule to Glacier: a single age-based rule ignores actual access; objects still hot after 30 days would be archived and need restores, which is the wrong fit for unpredictable patterns.
T: When access patterns are unknown or changing, let Intelligent-Tiering move objects per access; fixed classes or age-based rules fit predictable patterns.
V: S3

@ SAP-C02 D1 T1.2 applied use-case
S: A company with 50 AWS accounts wants employees to sign in once and access only the specific AWS accounts and roles relevant to their job function, without creating IAM users in each account. Which service should be used?
A: Amazon Cognito user pools federated to an IAM role in each of the 50 accounts
B: IAM users in each account, kept in sync by a scheduled replication script
C: Cross-account IAM roles that each account owner creates and maintains by hand
D: IAM Identity Center with permission sets assigned to groups per account

G: ## Workforce sign-in across many accounts
**AWS IAM Identity Center** is the central sign-in service for employees across an AWS Organization.
- Users and groups come from its own directory or from an external identity provider, such as Microsoft Entra ID or Okta, often synced with SCIM.
- A **permission set** is a template of policies, such as `ReadOnly` or `NetworkAdmin`.

C=Hand-built cross-account roles: each account owner builds roles and trust policies differently, there is no single sign-in portal, and permissions drift and are hard to audit.

@ SAP-C02 D3 T3.2 advanced use-case
S: A company wants temporary, just-in-time elevated access for production changes with approvals and automatic expiry. Which approach fits?
A: A shared break-glass password emailed to engineers when they request temporary elevated access
B: Identity Center permission sets assigned on request after review and removed when the window ends
C: Temporary IAM users created for each approved change and deleted manually after the change
D: Permanent administrator permissions for engineers, with approvals tracked in change tickets
K: B
G: ## Just-in-time access instead of standing admin rights
Standing administrator permissions mean every compromised engineer credential is a production admin credential. **Just-in-time (JIT) elevated access** grants higher permissions only when needed, only after approval, and removes them automatically.
## Building it on IAM Identity Center
- **IAM Identity Center** assigns **permission sets** (for example `ProdChangeAdmin`) to users or groups for specific accounts; these become short-lived role credentials.
- A JIT layer creates that assignment on request and deletes it after a set duration. AWS publishes the open-source **Temporary Elevated Access Management (TEAM)** solution for this, and AWS partner products offer the same pattern.
- Requests carry a justification, go to an approver, and the grant expires on time, for example after 2 hours. Activity is recorded in CloudTrail.
W: Approved, time-bound Identity Center assignments: engineers get production rights only for an approved window, credentials are short-lived role credentials, and removal happens automatically without anyone remembering to do it.
X: A=Emailed shared break-glass password: a shared password cannot be traced to one person, spreads through mailboxes, and has no approval or expiry built in.
C=Temporary IAM users deleted manually: IAM users have long-lived credentials, and manual deletion is easily forgotten, leaving elevated users behind.
D=Permanent admin with ticket approvals: tickets record intent, but the standing privilege remains between changes, the opposite of just-in-time, and maximizes the damage a leaked credential can do.
T: Just-in-time access means approved, time-limited Identity Center assignments that expire automatically, not shared passwords, leftover IAM users or permanent admin.

@ SAP-C02 D3 T3.3 advanced troubleshooting
S: An Aurora MySQL cluster shows high CPU on the writer during business hours. Analysis shows most load comes from read queries issued by a reporting tool. What is the most effective improvement?
A: Convert the Aurora cluster to a single-AZ deployment to remove the replication overhead on the writer
B: Move the writer to a larger instance class and keep the reporting tool on the cluster endpoint
C: Enable Backtrack so the writer can rewind long-running report queries when they slow it down
D: Point the reporting tool at the reader endpoint and add Aurora Replicas as needed
K: D
G: ## Aurora endpoints
An Aurora cluster has one **writer** and up to 15 **Aurora Replicas** that share the same storage volume. Aurora gives each cluster several DNS endpoints:
- the **cluster (writer) endpoint** always points to the current writer and handles reads and writes;
- the **reader endpoint** spreads connections across the available Aurora Replicas and is used for read-only work.
Because replicas read from the shared storage, adding them does not require copying data, and replica lag is typically low.
## Offloading reads
If a reporting tool connects to the writer endpoint, its heavy `SELECT` queries compete for CPU with the application's writes. Pointing the tool at the reader endpoint moves that load to replicas. Aurora Auto Scaling can add or remove replicas based on CPU or connections.
Example: the reporting tool's connection string changes from `mycluster.cluster-xxxx...` to `mycluster.cluster-ro-xxxx...`, and writer CPU drops.
W: Reader endpoint with more replicas: moving the reporting reads to Aurora Replicas removes that load from the writer, and read capacity can grow by adding replicas.
X: A=Single-AZ deployment: Aurora replicas share storage, so they add little replication overhead on the writer; removing them lowers availability and leaves all reads on the writer.
B=Larger writer: scaling up adds cost and still makes the reporting tool's queries and transactions compete on the same instance, instead of separating the workloads.
C=Backtrack: Backtrack rewinds the database to an earlier point in time to undo data changes; it cannot stop or rewind slow queries.
T: When reads overload the writer, send them to the reader endpoint and scale replicas, instead of scaling the writer up.
V: Amazon Aurora
