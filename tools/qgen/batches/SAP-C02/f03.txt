# SAP-C02 fixes: Performance Insights reached end of life on 2026-07-31 (now CloudWatch Database Insights)

@ SAP-C02 D3 T3.3 applied troubleshooting
S: An application's average API response time has degraded from 200 ms to 1.5 seconds over the past week. CloudWatch metrics show EC2 CPU utilization and Auto Scaling activity for the application tier remain healthy and stable. What should the team investigate next to identify the bottleneck?
A: Replace the Application Load Balancer with a Network Load Balancer to cut per-request overhead
B: Increase the Auto Scaling group's desired capacity so more instances share the API requests
C: Add CloudFront in front of the API so more requests are served from edge locations
D: Review CloudWatch Database Insights (formerly Performance Insights) for waits, locks, slow SQL
K: D
G: ## Follow the request path
A request goes through the load balancer, the application tier and its dependencies such as the database. If response time grows while EC2 CPU and Auto Scaling look normal, the application servers are mostly **waiting**, usually on a downstream dependency.
## CloudWatch Database Insights
Amazon RDS Performance Insights reached **end of life on July 31, 2026**; AWS migrated its users to **Amazon CloudWatch Database Insights**. The default **Standard mode** keeps the Performance Insights features, and the **Advanced mode** adds per-query statistics, execution plan and lock analysis, and fleet-wide views. Database Insights shows **database load** as average active sessions, broken down by:
- **Wait events**, such as lock waits, I/O waits or CPU.
- **Top SQL**, showing which statements consume the most load.
- Hosts and users.
Example: load rises steadily over a week, dominated by `io/table/sql/handler` waits from one query whose table has grown and lost its useful index plan, which matches a slow, gradual degradation.
W: Review Database Insights for waits, locks and slow SQL: with healthy app servers, the database is the most likely bottleneck, and the DB load view shows which wait events and SQL statements are slowing requests.
X: A=Replace the ALB with an NLB: load balancer overhead is in milliseconds and did not change this week; swapping it would not explain a 7x slowdown and would lose layer 7 features.
B=Increase desired capacity: the application tier is not saturated, so more instances would just wait on the same slow dependency and add cost.
C=Add CloudFront: API responses are generally dynamic and per-user, so little would be cached, and it does nothing about the backend delay.
T: When compute looks healthy but latency climbs, find the real bottleneck (often the database) in CloudWatch Database Insights, the successor of Performance Insights, before scaling or re-architecting.
V: Amazon CloudWatch Database Insights, Amazon RDS, Amazon EC2
