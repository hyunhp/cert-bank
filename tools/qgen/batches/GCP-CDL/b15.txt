@ GCP-CDL D1 T1.2 expert comparison
S: An engineering consultancy is moving three systems out of its server room. Its timesheet and expense process should use an off-the-shelf application because the firm has no developers for it. Its own project-pricing engine is custom code that developers update weekly, and they want to stop managing operating systems. Its structural-analysis package is licensed software whose installation guide requires a specific operating system release and a kernel driver on the machine. Leadership wants each system on the service model that removes the most operational work without breaking a requirement. Which assignment is BEST?
A: Timesheets on SaaS, pricing engine on PaaS or serverless, structural-analysis package on IaaS virtual machines
B: Timesheets on SaaS, pricing engine on IaaS virtual machines, structural-analysis package on a serverless container platform
C: Timesheets on IaaS virtual machines, pricing engine on SaaS, structural-analysis package on PaaS with a managed runtime
D: Timesheets on PaaS with custom code, pricing engine on serverless functions, structural-analysis package on a SaaS subscription
K: A
G: ## Service models and how much they remove
- **SaaS**: the provider runs the whole application; the customer manages users and data. Fits standard business processes when there is no need to write code.
- **PaaS / serverless** (for example Cloud Run or App Engine): the provider runs the platform, operating system and scaling; developers deploy their code. Fits custom applications whose team wants to stop managing servers.
- **IaaS** (Compute Engine): the provider runs hardware and virtualization; the customer controls the operating system and installed software. Needed when software requires a particular OS release, drivers or agents.
## The detail that decides
The structural-analysis package needs a specific OS release and a kernel driver. Only IaaS gives that control. Serverless and PaaS manage the operating system for you, so they cannot host it.
## Rule of thumb
Pick the highest level of service that still meets every requirement: it removes the most operational work.
W: SaaS, PaaS or serverless, IaaS: off-the-shelf timesheets need no code, the custom pricing engine runs without OS management, and only VMs allow the required OS release and kernel driver.
X: B=Pricing on IaaS, package on serverless: keeps OS management the developers want to drop, and a serverless platform cannot install a kernel driver.
C=Timesheets on IaaS, pricing on SaaS: running a standard process on VMs adds work, and SaaS cannot host the firm's own custom pricing code.
D=Package on SaaS: there is no SaaS version of a licensed package that must be installed on a chosen OS, and timesheets on PaaS would need developers the firm lacks.
T: Choose the highest service model each workload allows; any need for OS-level control, such as kernel drivers, keeps that workload on IaaS.
V: Compute Engine, Cloud Run

@ GCP-CDL D1 T1.1 expert tradeoff
S: A European payments company is adopting Google Cloud. Its financial regulator requires a documented, tested exit plan showing that critical workloads could move to another provider within a reasonable period. The company's platform team of six wants managed services rather than running infrastructure itself. While reviewing current tools, the architect notes that the data science team runs Apache Spark notebooks against the same transaction history that finance analysts will query in BigQuery, and both teams must work from one copy. Which strategy satisfies all three requirements BEST?
A: Run every workload on self-managed virtual machines with open-source software installed by the team, avoiding all managed services
B: Run applications as containers on GKE and keep transaction history in an open table format queried through BigLake tables
C: Use only proprietary serverless services for applications and data, and write the exit plan as a full rewrite on the other provider
D: Run every application in two public clouds at full capacity at all times, copying the transaction history to each cloud every hour
K: B
G: ## Openness as a business benefit
The exam guide highlights open source, open standards and interoperability as ways to avoid lock-in and silos.
- **Kubernetes** is open source. Applications packaged as containers and run on GKE (a managed Kubernetes service) use the same Kubernetes APIs available elsewhere, which keeps an exit plan realistic while Google manages the platform.
- **Open table formats** such as Apache Iceberg keep data readable by many engines. **BigLake tables** let BigQuery query data in Cloud Storage, and BigQuery connectors let engines such as Apache Spark read the same tables, so one copy serves both teams.
## Balancing the three requirements
- Exit plan: needs portable application packaging and data formats.
- Small team: needs managed services.
- Detail: Spark and BigQuery on one copy: needs an open format both engines can read.
Fully self-managed stacks satisfy portability but not the small team. Running everything twice satisfies resilience but costs double and still copies data.
W: GKE plus open table format with BigLake: managed Kubernetes keeps workloads portable, and one open-format copy of transaction history serves both Spark and BigQuery.
X: A=Self-managed VMs: portable, but six people would have to run all infrastructure, which the team explicitly wants to avoid.
C=Proprietary serverless with a rewrite plan: an exit that depends on a full rewrite is hard to test and slow, which weakens the regulator's exit plan.
D=Two clouds at full capacity: doubles cost and operations for a small team, and hourly copies break the one-copy requirement.
T: Managed services built on open source (GKE) and open data formats (BigLake over Iceberg) give a small team portability without running everything itself.
V: Google Kubernetes Engine, BigLake

@ GCP-CDL D1 T1.2 expert troubleshooting
S: A design-software company serves all customers from one Google Cloud region in the United States. Customers in Japan now make up a third of revenue and complain that each click in the editor feels slow. The office manager proposes buying a faster internet line for the Tokyo sales office. Measurements show each request is small, but the round trip from Japan to the region takes far longer than from US cities. The engineers add that editor clicks call an API whose responses are personalized and cannot be cached. Customer data may legally be stored in either country. Which action addresses the root cause BEST?
A: Upgrade the Tokyo office's internet line to a much higher bandwidth, so that each editor request transfers to the region faster
B: Put a content delivery network in front of the US region, so that edge locations in Japan answer the editor's API calls
C: Increase the machine size of the US servers, so that each API request is processed faster once it reaches the region
D: Deploy the API tier and the data it reads in a Google Cloud region in Japan, so requests travel a much shorter distance
K: D
G: ## Latency versus bandwidth
- **Bandwidth** is how much data can move per second. It matters for large transfers.
- **Latency** is the delay for one round trip. It depends mostly on physical distance and network path, and it dominates when many small requests are made.
## Edge caching versus regional deployment
- A **content delivery network** (Cloud CDN) caches responses at edge locations close to users. It helps for content that can be cached, such as images or static files.
- Responses that are **personalized and not cacheable** must be produced by the application itself, so the fix is to run the application, and the data it needs, in a region close to the users.
## Reading the evidence
Small requests plus long round trips point to latency, not bandwidth. Non-cacheable API calls rule out the CDN. There is no residency obstacle to a Japanese region.
W: API tier and data in a Japanese region: shorter physical distance cuts the round-trip time of every small, personalized request, which is the real cause of the slowness.
X: A=More office bandwidth: the requests are small, so the bottleneck is distance (latency), and customers outside the sales office would gain nothing.
B=CDN for the API: edge locations cache content; personalized responses that cannot be cached still travel to the US region.
C=Bigger US servers: processing time is not the problem; the round trip across the Pacific remains as long as before.
T: Many small, slow requests over long distances are a latency problem; move the application closer to users, because bandwidth and caching cannot fix non-cacheable round trips.
V: Google Cloud

@ GCP-CDL D2 T2.2 expert comparison
S: A concert-ticket marketplace sells seats for the same events to buyers in North America, Europe and Asia at the same moment when sales open. Its developers write relational SQL and want transactions across seats, orders and payments. The business requires the service to accept purchases in every region even during a regional outage, with the highest availability Google Cloud offers. A post-mortem from last year adds that two buyers on different continents were both sold the final seat of a show, which the company must never repeat. Which database fits BEST?
A: Cloud SQL with read replicas in other regions, so buyers on each continent read seat maps from a nearby copy
B: Bigtable with clusters replicated across three continents, so each region writes seats locally with low latency
C: Spanner in a multi-region configuration, giving relational transactions with strong consistency across regions
D: AlloyDB for PostgreSQL in one region with a columnar engine, so seat queries and purchase transactions run fast
K: C
G: ## Four databases, four strengths
- **Cloud SQL**: managed MySQL, PostgreSQL and SQL Server. Read replicas can be placed in other regions, but writes go to one primary instance.
- **AlloyDB for PostgreSQL**: high-performance PostgreSQL-compatible database with a columnar engine for analytics on live data; deployed in a region.
- **Bigtable**: NoSQL wide-column store for huge key-value workloads. Replication between clusters is **eventually consistent by default**: a write in one cluster is seen in the others only after it replicates.
- **Spanner**: relational database with horizontal read and write scalability and **strong consistency**, in single-region, dual-region or multi-region configurations, with up to 99.999% availability.
## The detail that decides
Selling the last seat twice is a consistency failure. Only a database that keeps transactions strongly consistent across regions prevents it while accepting writes everywhere.
W: Spanner multi-region: relational SQL transactions, strong consistency across continents so a seat is sold once, and the highest availability among these options.
X: A=Cloud SQL with replicas: replicas are for reads; every purchase still goes to one primary region, which fails the requirement to accept purchases during that region's outage.
B=Bigtable replicated: replication is eventually consistent by default and Bigtable is not a relational database, so two continents could sell the same seat.
D=AlloyDB in one region: excellent PostgreSQL performance, but a single-region database does not accept purchases everywhere during a regional outage.
T: For globally distributed writes that must never conflict, choose Spanner: relational transactions with strong consistency across regions.
V: Spanner

@ GCP-CDL D2 T2.2 expert tradeoff
S: A market-research firm stores two kinds of files in Cloud Storage and wants the LOWEST total cost for each. Raw survey uploads are read about once a month by analysts and are deleted 60 days after upload under the firm's privacy policy. Signed client reports must be kept for three years; auditors read a sample of them twice a year. The finance lead reminds the team that a class's minimum storage duration is charged even when an object is deleted earlier. Which TWO choices are correct? (Select TWO)
A: Raw survey uploads in Nearline storage, because monthly reads fit it and the 60-day life exceeds its 30-day minimum
B: Signed client reports in Coldline storage, because reads twice a year fit at most once a quarter over three years
C: Raw survey uploads in Coldline storage, because its lower at-rest price outweighs a 90-day minimum on 60-day files
D: Signed client reports in Archive storage, because any data kept longer than one year belongs in the coldest class
E: Raw survey uploads in Archive storage, because deleting the files early avoids paying for its 365-day minimum storage duration
K: A,B
G: ## Storage classes: price, access and minimum duration
- **Standard**: frequent access; no minimum storage duration.
- **Nearline**: about once a month or less; 30-day minimum.
- **Coldline**: at most once a quarter; 90-day minimum.
- **Archive**: less than once a year; 365-day minimum.
Colder classes have lower at-rest prices but higher access costs (retrieval fees), and an object deleted before the minimum duration is still charged as if stored for the full minimum.
## Worked reasoning
- **Survey uploads**: live 60 days, read monthly. Nearline's 30-day minimum is met. Coldline would bill each file for 90 days although it exists for 60, and monthly reads are more frequent than Coldline's pattern. Archive would bill 365 days.
- **Client reports**: kept three years, read twice a year. That is less often than once a quarter, so Coldline fits; Archive is meant for data read less than once a year, and its higher access costs apply to every audit read.
W: A=Nearline for surveys: monthly access matches Nearline, and the 60-day life is past its 30-day minimum, so no early-deletion charge.
B=Coldline for reports: two reads a year fits "at most once a quarter", and three years far exceeds the 90-day minimum.
X: C=Coldline for surveys: each 60-day file would be billed for the 90-day minimum, and monthly reads add retrieval costs.
D=Archive for reports: retention length alone does not decide; reads twice a year exceed Archive's less-than-once-a-year pattern, so access costs grow.
E=Archive for surveys: early deletion does not avoid the minimum; each file would be charged for 365 days.
T: Match the class to both access frequency and object lifetime; deleting before the minimum duration is still charged for the full minimum.
V: Cloud Storage

The inspection forms change often as regulators add questions, so the data structure must be flexible. The company has no database administrators and wants a fully managed, serverless database. The project brief also notes that many inspections happen in rural valleys with no mobile signal, and supervisors want to see completed inspections the moment a device reconnects. Which database fits BEST?
A: Cloud SQL for PostgreSQL, because relational tables with a fixed schema keep frequently changing inspection forms consistent everywhere
B: Bigtable, because a wide-column store handles flexible fields and synchronizes each inspector's phone while it is offline

- **Firestore**: fully managed, serverless **document** database. Documents can have different fields, which suits forms that change often. Built-in **real-time synchronization** and **offline support** let mobile apps keep working without a connection and sync when they reconnect.

X: A=Cloud SQL: a fixed relational schema fits changing forms poorly, and it has no built-in offline synchronization for mobile devices.
B=Bigtable: built for massive key-value throughput, not for syncing data to and from offline phones.
C=Spanner: strong consistency needs the database to be reachable; it does not let a disconnected phone store and later sync records.
T: Flexible documents plus offline mobile use and real-time sync point to Firestore.

@ GCP-CDL D3 T3.2 expert tradeoff
S: A biotech research group must fine-tune a language model on 16 GPUs for about four days. GPUs of that type are often scarce in its preferred region. The run can start any time in the next two weeks, the group will do this only twice this year, and its grant cannot fund long-term commitments. The group's lead engineer notes that the training code has no checkpointing yet, so if any machine is interrupted the whole run must start again from the beginning. Which way of obtaining the GPUs fits BEST?
A: Spot VMs, because their large discounts suit a tight grant and the run can simply be repeated after any preemption
B: A three-year resource-based committed use discount on 16 GPUs, because it gives the deepest discount for these machines
C: Flex-start VMs through Dynamic Workload Scheduler, which wait for capacity and then run uninterrupted for up to seven days
D: Standard on-demand VMs requested at a random time, hoping that all 16 GPUs are free in the zone whenever the team asks for them
K: C
G: ## Provisioning models for accelerators
Compute Engine offers several provisioning models; AI Hypercomputer groups them as flexible consumption options.
- **Standard**: create instances immediately if capacity is available; you control when they stop.
- **Spot**: excess capacity at much lower prices, but Compute Engine can **preempt** (stop or delete) the instances at any time. Ideal for fault-tolerant work that can resume.
- **Flex-start** (Dynamic Workload Scheduler): you request resources and Compute Engine provisions them when capacity becomes available within a waiting window or keeps trying for a managed instance group; instances then run for up to **seven days**. Suited to short training and fine-tuning runs that need stability.
- **Committed use discounts**: one-year or three-year commitments for predictable, steady usage.
## The detail that decides
No checkpointing means any preemption restarts four days of work, which rules out Spot. Two runs a year cannot justify a multi-year commitment. Flexible start time is exactly what Flex-start trades for obtaining scarce GPUs.
W: Flex-start with Dynamic Workload Scheduler: the group waits for capacity within its two-week window, then gets up to seven days of stable runtime for a four-day run, with no long-term commitment.
X: A=Spot VMs: cheap, but preemption can happen at any time and, without checkpoints, would restart the four-day run.
B=Three-year commitment: the grant cannot fund it, and two runs a year leave the committed GPUs idle most of the time.
D=On-demand at a random time: GPU capacity is not guaranteed when requested, and the team gets no help waiting for availability.
T: For short GPU runs that need stability and can wait to start, use Flex-start (Dynamic Workload Scheduler); use Spot only when work can resume after preemption.
V: Compute Engine, AI Hypercomputer

@ GCP-CDL D3 T3.1 expert troubleshooting
S: A national clinic network built a model to predict which patients will miss appointments, so staff can send reminders. It was trained on two years of data from city clinics and reached high overall accuracy. After a nationwide launch, rural clinics report that the model flags almost every patient, and a regulator asks the network to explain why individual patients are flagged. A data review notes that rural clinics joined the scheduling system only last month. Which TWO actions address these problems BEST? (Select TWO)
A: Retrain with data that represents rural clinics, and check accuracy separately for rural and city patients before relaunch
B: Use explainability methods that show which factors drove each prediction, so staff and the regulator see why a patient is flagged
C: Keep the model unchanged, because high overall accuracy on city data proves that the model works equally well for every clinic
D: Train a much larger model on the same city data, because larger models generalize to rural patients without needing new data
E: Remove human review of the reminders, so that the model's decisions are applied faster and are no longer questioned by clinic staff
K: A,B
G: ## Why a model fails for part of the population
A model learns the patterns in its training data. If a group is missing from that data, the model's predictions for that group can be poor or biased, even when **overall** accuracy looks high. Here the training data came from city clinics only, because rural clinics joined the system last month.
## Responsible and explainable AI practices
- **Representative data**: training data should cover the people the model will be used on; quality dimensions such as completeness apply to whole groups, not only to fields.
- **Evaluate by group**: measure performance for each relevant group, not only as one average.
- **Explainability**: show which factors drove a prediction, so decisions can be justified to regulators and checked by staff.
- **Human oversight**: keep people involved, especially when the model is new to a population.
W: A=Representative data and per-group evaluation: adding rural data fixes the gap the model learned from, and checking each group shows whether the fix worked.
B=Explainability: factor-level explanations answer the regulator and help staff spot unreasonable flags.
X: C=Keep the model: overall accuracy on city data hides the failure for rural patients that the clinics already report.
D=Larger model on the same data: size cannot teach patterns that are absent from the training data.
E=Remove human review: lowers oversight just when the model is known to misbehave, the opposite of responsible AI.
T: High overall accuracy can hide failure for an unrepresented group; retrain on representative data, evaluate per group and explain predictions.
V: Gemini Enterprise Agent Platform
