G: ## Openness and interoperability
The exam guide asks why openness matters for data: open formats and open standards let different tools read the same data, which removes silos and reduces vendor lock-in.
- **Open table formats** such as Apache Iceberg store data in files that many engines understand.
- **BigLake tables** let BigQuery query structured data in Cloud Storage (and in other clouds through BigQuery Omni), and BigQuery connectors let open-source engines such as Apache Spark read the same tables with the same access controls.
## This scenario
Two copies that disagree are a data silo problem. One copy in an open format, readable by both BigQuery and Spark, gives a single source of truth without tying the data to one engine.
Current name: Since April 2026 BigLake is documented as Lakehouse (BigLake metastore as Lakehouse runtime catalog), with API, CLI and IAM names unchanged. The exam guide and this question keep the older name.
W: Open table format plus BigLake: one copy in Cloud Storage serves both BigQuery and Spark, ending the disagreement and keeping the data in an open, portable format.
X: A=Proprietary format: increases lock-in, which leadership wants to avoid, and forces a team to abandon a tool it needs.
C=Nightly copies: keeps two copies and adds reconciliation work; the copies can still drift apart between comparisons.
D=Shared spreadsheet: unsuitable for large sales history and for programmatic analysis by either engine, and it lacks governance.
T: Keep one copy of data in an open format that several engines can read; this removes silos and reduces lock-in.

@ Q014761 explain
G: ## Openness as a business benefit
The exam guide highlights open source, open standards and interoperability as ways to avoid lock-in and silos.
- **Kubernetes** is open source. Applications packaged as containers and run on GKE (a managed Kubernetes service) use the same Kubernetes APIs available elsewhere, which keeps an exit plan realistic while Google manages the platform.
- **Open table formats** such as Apache Iceberg keep data readable by many engines. **BigLake tables** let BigQuery query data in Cloud Storage, and BigQuery connectors let engines such as Apache Spark read the same tables, so one copy serves both teams.
## Balancing the three requirements
- Exit plan: needs portable application packaging and data formats.
- Small team: needs managed services.
- Detail: Spark and BigQuery on one copy: needs an open format both engines can read.
Fully self-managed stacks satisfy portability but not the small team. Running everything twice satisfies resilience but costs double and still copies data.
Current name: Since April 2026 BigLake is documented as Lakehouse (BigLake metastore as Lakehouse runtime catalog), with API, CLI and IAM names unchanged. The exam guide and this question keep the older name.
W: GKE plus open table format with BigLake: managed Kubernetes keeps workloads portable, and one open-format copy of transaction history serves both Spark and BigQuery.
X: A=Two clouds at full capacity: doubles cost and operations for a small team, and hourly copies break the one-copy requirement.
B=Proprietary serverless with a rewrite plan: an exit that depends on a full rewrite is hard to test and slow, which weakens the regulator's exit plan.
C=Self-managed VMs: portable, but six people would have to run all infrastructure, which the team explicitly wants to avoid.
T: Managed services built on open source (GKE) and open data formats (BigLake over Iceberg) give a small team portability without running everything itself.

@ Q014772 explain
G: ## Analytics across clouds
- **BigQuery Omni** runs BigQuery analytics on data stored in Amazon S3 or Azure Blob Storage by using **BigLake tables**. Processing happens where the data sits, so raw data does not have to be copied, and query results can be moved into a BigQuery region (for example with `CREATE TABLE AS SELECT`).
- **BigLake tables** use access delegation: a connection retrieves the data, so users are granted access only to the table, not to the underlying store.
- **AlloyDB Omni** is downloadable PostgreSQL-compatible database software for environments you manage; it is a database, not a way to query object storage in place.
- **Storage Transfer Service** copies data between clouds.
## The details that decide
Raw records may not leave the other cloud (rules out copying), analysts know BigQuery, and access must be granted on Google Cloud tables, not on the other cloud's credentials (BigLake access delegation).
Current name: Since April 2026 BigLake is documented as Lakehouse (BigLake metastore as Lakehouse runtime catalog), with API, CLI and IAM names unchanged. The exam guide and this question keep the older name.
W: BigQuery Omni with BigLake tables: analysts query S3 in place with BigQuery, receive table-level access only, and move just aggregated results for the joins.
X: A=AlloyDB Omni in the other cloud: adds a database to run, copies data into it and hands out the other cloud's credentials, against the governance rule.
B=Storage Transfer Service copy: moves raw marketing records out of the other cloud, which the contract forbids.
C=Other cloud's query service: requires credentials for the other cloud and abandons the analysts' BigQuery skills and governed tables.
T: BigQuery Omni with BigLake tables analyzes data in other clouds in place, with access granted on tables rather than on the other cloud's credentials.
