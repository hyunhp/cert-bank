@ GCP-CDL D4 T4.1 applied definition
S: A hospital group is planning its move to the cloud. The project lead lists the patient-scheduling system, the billing database and the imaging archive as three separate items to be moved, assessed and sequenced independently. What is the common term for each of these items?
A: A workload, meaning an application or service together with the resources and data it needs to run
B: A region, meaning a geographic location where cloud resources are physically hosted
C: A tenant, meaning a separate customer account that Google creates inside the hospital's environment
D: A landing zone, meaning the one-time network that must exist before any application can be moved
K: A
G: ## Workload: the unit of migration
A **workload** is an application or service plus the resources and data it needs to run, such as servers, databases, storage and network connections. Migration teams plan, move and test in workloads, because each one has its own owners, dependencies, risks and best migration path.
## Why the term matters to a business leader
- Different workloads in the same company often need different migration approaches.
- Priorities and timelines are set per workload, for example moving a low-risk internal tool before a regulated patient system.
## Reading the scenario
Scheduling, billing and imaging are each a self-contained thing that is assessed and moved on its own.
W: Workload: each system is an application plus its data and supporting resources, and it is the unit that is assessed, sequenced and migrated.
X: B=Region: a region is a physical location in which resources run, not a name for an application being moved.
C=Tenant: a tenant is a customer or organizational boundary; the three systems all belong to the same hospital group.
D=Landing zone: this is the prepared target environment that receives workloads, so it is one shared foundation rather than the items being moved.
T: A workload is an application with its data and resources, and it is the unit you assess and migrate.

@ GCP-CDL D4 T4.1 applied use-case
S: A manufacturer has 400 applications in two data centers. Nobody has a complete list of which systems talk to which, who owns them, or how heavily they are used. The CIO wants to avoid surprises after the move starts. Which first phase of a migration addresses this?
A: Replatforming each application to a managed service, then documenting its dependencies afterward from the new environment
B: Discovery and assessment, which inventories the workloads and their dependencies and evaluates how each should be migrated
C: Rehosting every application in one weekend, so that the old data centers can be closed before the dependencies matter
D: Reimagining the business model first, because the list of applications changes entirely once new products are chosen
K: B
G: ## Start with what you have
Migration is a journey, and Google's migration guidance begins with **discovery and assessment**. You cannot choose a sensible path for a workload you do not know about.
- **Discovery** builds an inventory: which workloads exist, who owns them, what they depend on, how much they are used.
- **Assessment** evaluates each workload: how complex it is, what it would take to move, what the business gains, and which migration approach fits.
## What goes wrong without it
Hidden dependencies cause outages when one system moves and another that quietly relied on it does not. Unknown workloads can also be paid for long after nobody needs them.
## Reading the scenario
The CIO's problem is missing knowledge, so the fix is gathering it before moving anything.
W: Discovery and assessment: it produces the inventory and dependency picture and rates each workload, which is the information needed to avoid surprises.
X: A=Replatform first: changing applications before they are understood risks breaking hidden dependencies; the documentation is needed before the work, not after.
C=Rehost in one weekend: speed does nothing about unknown dependencies, and moving everything blind is what produces the surprises the CIO fears.
D=Reimagine first: new products may come later, but the immediate gap is knowledge of the existing estate, which a business-model exercise does not supply.
T: Discovery and assessment come first: inventory the workloads and dependencies, then pick a path per workload.

@ GCP-CDL D4 T4.1 applied use-case
S: During migration planning, a bank finds a reporting application that nobody has opened in two years. Its former users moved to a newer analytics tool. How should this workload be handled in the migration plan?
A: Retained on premises indefinitely, because applications that nobody uses are always the safest to leave untouched
B: Refactored into microservices so that, if the users ever return, the application is ready for a modern platform
C: Rehosted to virtual machines in the cloud so that its current appearance and data are preserved exactly
D: Retired, which means decommissioning it so that no money or effort is spent moving or running it
K: D
G: ## The cheapest migration is no migration
Assessment often reveals workloads that no longer deliver value. To **retire** a workload is to decommission it rather than move it (a generic migration term; Google's migration pages use "decommission" for this idea). It removes licences, hardware, support effort and security exposure, and it shrinks the scope of the migration project.
## When to retire
- Usage is negligible or the function has been replaced.
- No owner or business case exists to justify the cost of moving it.
Check data-retention rules first: sometimes data must be archived before the application is switched off.
## Reading the scenario
No users and a replacement tool exist, so moving the workload would only spend effort on something with no value.
W: Retire: the application has no users and has been replaced, so decommissioning it avoids all migration and running costs.
X: A=Retain: retaining means deliberately keeping a workload where it is because it still has a reason to stay; an unused workload has no such reason and just keeps costing money.
B=Refactor: re-engineering an application nobody uses spends the most effort of any approach on the least value.
C=Rehost: a lift and shift would reproduce the cost and risk in the cloud and pay for capacity with no users.
T: Retire = decommission workloads that no longer deliver value instead of migrating them.

@ GCP-CDL D4 T4.1 applied use-case
S: A defence supplier runs a control system tied to specialised on-site hardware. A regulator requires the equipment to stay inside the supplier's own facility for the next several years. The rest of its applications are moving to Google Cloud. What is the right migration decision for this control system?
A: Retire it now, because anything that cannot move to the cloud has no place in a modern organization
B: Reimagine it as a new cloud product, because only a complete redesign is allowed to leave the facility
C: Retain it where it is for now, and revisit the decision when the constraint changes
D: Rehost it in the cloud immediately, because the regulator's rule applies only to hardware that is out of warranty
K: C
G: ## Not every workload moves
To **retain** a workload is to decide, deliberately, to leave it in its current environment for now. Good reasons include regulatory or latency constraints, hardware that is tied to a physical process, a recent investment that has not paid off yet, or very high migration risk compared with the benefit.
## Retain is a decision, not neglect
A retained workload is documented and reviewed. It often connects to cloud workloads through a hybrid arrangement, and the decision is revisited when the constraint changes.
## Reading the scenario
The regulation and the tied-in hardware are a valid reason to keep this one workload on site while everything else moves.
W: Retain: the system still has value and a regulatory reason to stay, so it is kept on site by decision and reviewed later.
X: A=Retire: the control system is still needed, so decommissioning it would remove a function the business depends on.
B=Reimagine: a new cloud product does not satisfy a requirement that the equipment stay in the facility, and nothing in the rule asks for a redesign.
D=Rehost now: the regulation concerns where the equipment must be, not its warranty, so moving it would break the requirement.
T: Retain = knowingly keep a workload in place for now when constraints make moving it wrong.

@ GCP-CDL D4 T4.1 applied tradeoff
S: A retailer must leave its leased data center within three months. Its main order system runs on VMs, works well, and the vendor-supported software cannot be changed. The team accepts that the cloud benefits will be limited at first. Which approach fits, and what is the trade-off?
A: Rehost (lift and shift), which moves it fastest with the fewest changes, but it will not yet use cloud-native capabilities fully
B: Refactor, which rewrites the code for the cloud and gives the most benefit, but it takes the longest and needs changes to the code
C: Reimagine, which creates a new business model, but it requires that the vendor-supported software be modified first
D: Replatform onto serverless, which removes all servers, but it is the slowest approach because every VM is rebuilt by hand
K: A
G: ## Rehost: lift and shift
In a **rehost** (lift and shift) migration, a workload moves to the cloud with minor or no changes, for example moving VMs to virtual machines on Compute Engine.
## Strengths
- The fastest and least risky path, because the team keeps its tools and skills.
- Works for ready-made software that cannot be modified.
## Trade-off
The workload is not optimized for the cloud. It may not use autoscaling, managed services or other cloud-native features, so cost and agility improvements are limited until later modernization.
## Reading the scenario
A fixed deadline, working software the retailer may not change, and acceptance of limited benefits all point to rehost.
W: Rehost: it needs the fewest changes and moves fastest, which suits a deadline and unmodifiable vendor software, at the cost of fewer cloud benefits at first.
X: B=Refactor: rewriting code takes the longest of the approaches and the vendor software cannot be changed, so it cannot meet a three-month deadline.
C=Reimagine: new business models are a long-term ambition that does not solve moving a working system out of a lease in three months.
D=Replatform onto serverless: this changes how the workload runs and needs testing; it is not the quickest route, and the description of rebuilding every VM by hand is not how migrations are done.
T: Rehost is the fastest, lowest-risk move, but cloud benefits come only after later optimization.

@ GCP-CDL D4 T4.1 applied use-case
S: A publisher runs its content site on VMs with a self-managed database. The code is stable and staff do not want to rewrite it, but the team spends many hours on patching and backups. They move the site mostly as is, but switch the database to a managed Google Cloud database service. Which migration approach is this?
A: Rehost, because the site was moved to Google Cloud with no changes of any kind to its parts
B: Retire, because the self-managed database was switched off and the whole workload was decommissioned
C: Replatform, because one targeted improvement was made while the application code stayed the same
D: Reimagine, because using a managed database changes the publisher's business model
K: C
G: ## Replatform: move and improve
A **replatform** migration moves a workload and makes selective improvements so it benefits from the cloud, without redesigning the whole application. Swapping a self-managed database for a managed service, or moving to containers, are typical examples. (Labels differ between sources: the exam guide writes "replatform [move and improve]", while Google's migration guide calls replatform "lift and optimize" and uses "move and improve" for refactor. Judge by what is done, not by the label: here only a component is swapped and the code is not modified.)
## Why companies choose it
- Less operational work, such as patching and backups, moves to Google.
- Better reliability and performance than a plain rehost, for modest extra effort.
## Cost
It takes more testing than rehost because the platform under the application changed.
## Reading the scenario
The code is unchanged but one component was swapped for a managed service to cut operational work.
W: Replatform: a targeted optimization (managed database) is applied while the application code stays as it is, so the workload is moved and improved without being rewritten.
X: A=Rehost: a rehost applies the minimum change to run; here a component was deliberately upgraded to a managed service, which goes beyond that.
B=Retire: only the old self-managed database component was replaced; the site continues to serve readers, so no workload was decommissioned.
D=Reimagine: the publisher's business model is unchanged; this was an infrastructure improvement for lower operations effort.
T: Replatform = move with targeted improvements, such as a managed service, without rewriting the application.

@ GCP-CDL D4 T4.1 applied use-case
S: A ticketing company's monolithic application slows down every time a popular event goes on sale, and one change requires redeploying the whole system. Leadership approves a project to rewrite it as independent services that scale separately. Which migration approach is this?
A: Retain, because the company keeps the same application and only adds new tools to monitor it
B: Rehost, because the code is moved to Google Cloud and is run exactly as it ran in the data center
C: Replatform, because the existing application is moved to a managed database without any code changes
D: Refactor, because the application's code and architecture are modified to take advantage of cloud capabilities
K: D
G: ## Refactor: change the application itself
**Refactor** means modifying a workload's code and architecture to take advantage of cloud capabilities such as scalability and high availability, for example breaking a monolith into microservices.
## Trade-offs
- Benefits: independent scaling, faster and safer releases, resilience.
- Costs: more time, new skills, and higher risk than rehost or replatform.
## When to choose it
When the current design cannot meet business needs, or when a major update is needed anyway. Use it for workloads where the gain justifies the effort.
## Reading the scenario
Rewriting a monolith into independently scaled services changes the code and design, which is refactoring. (Google's migration guide also has a separate re-architect type for this kind of change; the exam guide folds it into refactor, and no option here is closer.)
W: Refactor: the code and architecture are being redesigned into independent services, which is the defining feature of this approach.
X: A=Retain: the company is not leaving the application alone; a project to rewrite it is the opposite of keeping it as is.
B=Rehost: running unchanged code in the cloud does not fix slow scaling or whole-system deployments.
C=Replatform: a managed database is a targeted improvement with no code changes, whereas the stem describes a rewrite of the application structure.
T: Refactor = change the code and architecture, for example monolith to microservices, to use cloud capabilities.

@ GCP-CDL D4 T4.1 applied use-case
S: A national insurer has moved its claims system to the cloud. It now wants to rethink the whole claims experience: customers submit photos, an AI agent drafts the assessment, and adjusters review exceptions, with new services built around the company's data. Which migration term describes this ambition?
A: Reimagine, which uses cloud and AI capabilities to rethink how the process and the business work
B: Rehost, which moves the existing claims process unchanged into virtual machines on Google Cloud
C: Retain, which keeps the existing process in place so that adjusters continue to do each step manually
D: Retire, which removes the claims system so that customers file claims without any insurer system
K: A
G: ## Reimagine: beyond moving
The other approaches ask how to move a workload. **Reimagine** asks what the business could do differently now that cloud, data and AI are available. It changes the process, product or experience, not only the technology under it.
The fetched Google migration pages do not define retire, retain or reimagine, so this description uses their generic industry meanings.
## Examples
- Replacing a manual review with an AI agent that handles routine cases and escalates exceptions.
- Launching new data-driven services on top of the consolidated data.
## Reading the scenario
Photos, an AI agent drafting assessments and adjusters handling exceptions is a new way of running claims, not a relocation of the old one.
W: Reimagine: the insurer is redesigning the claims process and customer experience around cloud data and AI, which goes beyond moving or tuning an application.
X: B=Rehost: a rehost keeps the process unchanged, whereas the stem describes a changed experience.
C=Retain: keeping every step manual is the status quo the insurer wants to leave behind.
D=Retire: the claims function is still essential; the goal is to improve it, not remove the system that supports it.
T: Reimagine = use cloud and AI to rethink the process or business, not just to move the technology.

@ GCP-CDL D4 T4.1 advanced comparison
S: Three workloads were assessed. Workload 1 is a vendor package that cannot be modified and must leave a data center next quarter. Workload 2 is a core customer app whose monolithic design blocks growth and that has a funded modernization budget. Workload 3 is an internal tool that duplicates a newer company system. Which assignment of approaches is the best fit?
A: Workload 1 refactor, workload 2 rehost, workload 3 replatform
B: Workload 1 retire, workload 2 retain, workload 3 refactor
C: Workload 1 rehost, workload 2 refactor, workload 3 retire
D: Workload 1 reimagine, workload 2 retire, workload 3 rehost
K: C
G: ## Match the approach to the workload
There is no single best strategy for a whole portfolio. Each workload is matched on three factors: business value, technical constraints and time and budget.
- **Retire**: the workload has no remaining value.
- **Retain**: a constraint says it must stay where it is.
- **Rehost**: speed matters and the workload cannot or need not change.
- **Replatform**: a few targeted improvements deliver real gains.
- **Refactor**: the design blocks the business and there is budget for a rewrite.
- **Reimagine**: cloud and AI could change the process or product.
## Applying it
An unmodifiable package under a deadline suits rehost. A blocked growth app with budget suits refactor. A duplicate tool is simply retired.
W: Rehost, refactor, retire: the unmodifiable, deadline-bound package is lifted and shifted, the blocked core app is modernized with the budget, and the duplicate tool is decommissioned.
X: A=Refactor, rehost, replatform: rewriting software that cannot be modified is impossible, and a simple lift of the app whose design blocks growth would leave that problem in place.
B=Retire, retain, refactor: the package is still needed and the core app would not be left unchanged, and a duplicate tool is not worth rewriting.
D=Reimagine, retire, rehost: a core app with a funded modernization need would not be switched off, and a duplicate tool should not be moved at all.
T: Choose retire, retain, rehost, replatform, refactor or reimagine per workload, based on value, constraints and time.

@ GCP-CDL D4 T4.1 applied use-case
S: Before approving a migration plan, a CFO asks what the assessment phase should deliver to make the plan reliable. Which TWO outputs are most useful? (Select TWO)
A: A list of every workload with its owner, its dependencies on other systems and its current usage
B: A guarantee that every workload will cost less in the cloud than it does today, whichever approach is used
C: A recommended migration approach per workload, based on its complexity, business value and constraints
D: A commitment to rewrite every application as microservices, so that the portfolio is consistent
E: A decision that no workload will be retired or retained, so that the scope is fully predictable
K: A,C
G: ## What assessment produces
Google's migration guidance has teams discover the workloads and then assess them: how complex they are, how much effort moving them takes, what depends on them, and what each is worth to the business.
- An **inventory** with owners, dependencies and usage.
- A **per-workload recommendation** (retire, retain, rehost, replatform, refactor, reimagine) and an order for moving them.
## What assessment cannot promise
It informs the plan; it does not guarantee savings, and it should not force one approach on every workload.
W: A=Inventory with dependencies: knowing owners, dependencies and usage is what lets the plan sequence moves without breaking hidden connections.
C=Recommended approach per workload: assessment ends with a fit-for-purpose path for each workload, which is the core input to the plan.
X: B=Guaranteed lower cost: costs depend on the approach chosen and later optimization, so an assessment cannot honestly promise savings for every workload.
D=Everything to microservices: a blanket rewrite ignores that some workloads should be rehosted, retained or retired.
E=No retire or retain: removing options in advance defeats the purpose of assessing, since retiring and retaining are often the cheapest outcomes.
T: Assessment delivers an inventory with dependencies and a fit-for-purpose approach for each workload.

@ GCP-CDL D4 T4.1 applied use-case
S: Two years after a lift and shift of its VMs, a logistics company says it has not seen the agility or cost gains it expected from the cloud. Which TWO explanations are the most likely? (Select TWO)
A: The workloads were moved with minimal change, so they do not yet use cloud-native features such as autoscaling or managed services
B: Google Cloud does not offer features that allow existing applications to be modernized after they are moved
C: The VMs are probably sized and run as they were in the data center, so capacity is still fixed rather than elastic
D: Rehost migrations always lose data, so the company has had to repeat its work several times
E: Lift and shift automatically converts every application to serverless, which then disables cost controls
K: A,C
G: ## Rehost is the start, not the end
A lift and shift gets workloads out of a data center quickly, but they keep their old design. They are still sized for peak demand, scale by buying bigger machines, and are patched by the team. The benefits of the cloud come mostly from **modernization after the move**.
## Typical next steps
- Right-size VMs and use autoscaling.
- Replace self-managed components with managed services.
- Containerize or refactor selected applications.
## Reading the scenario
Disappointing gains two years after a rehost point to workloads that were never optimized.
W: A=Minimal change: with no cloud-native features used, the workloads cannot yet use autoscaling or managed services, so agility gains are small.
C=Fixed capacity: VMs sized as before keep paying for peak capacity all day, which limits the cost gains.
X: B=No modernization path: Google Cloud supports modernizing after the move, including managed services and containers, so this is incorrect.
D=Always lose data: rehosts are routine and designed to preserve data, so this does not explain the result.
E=Automatic serverless: a rehost does not change an application's architecture, so nothing is converted.
T: A rehost delivers speed; agility and cost gains need follow-up optimization such as right-sizing, autoscaling and managed services.

@ GCP-CDL D4 T4.1 applied use-case
S: A software company wants developers to build an application once and run it in the same way on a laptop, in testing and in production, with less overhead than starting a full virtual machine per copy. Which technology addresses this?
A: Containers, which package an application with its dependencies and share the host operating system's kernel
B: Dedicated hardware, which gives each application its own physical server so that no two versions can conflict
C: Load balancers, which spread requests across servers but do not package software or its dependencies
D: Spot VMs, which are discounted machines that can be reclaimed and do not change how software is packaged
K: A
G: ## Containers
A **container** packages an application with its libraries and settings into one image that runs the same way anywhere a container runtime is available. Containers share the host operating system's kernel, so they start quickly and use fewer resources than VMs, which each carry a full guest operating system.
## Business value
- Consistent behaviour from developer laptop to production, with fewer "works on my machine" problems.
- Higher density, so more applications fit on the same hardware.
- Portability across clouds and data centers.
## Reading the scenario
Build once, run the same everywhere, with less overhead than a VM per copy: that is containerization.
W: Containers: the package carries the app with its dependencies and shares the host kernel, so it runs consistently and lightly in every environment.
X: B=Dedicated hardware: separate physical servers avoid conflicts at a great cost, and do not make the software portable or lightweight.
C=Load balancers: they distribute traffic among running copies, but have nothing to do with how the application is packaged.
D=Spot VMs: these are a pricing and availability option for VMs, not a way to package software consistently.
T: Containers package an app with its dependencies, run the same everywhere and are lighter than VMs.

@ GCP-CDL D4 T4.1 applied use-case
S: An online retailer's single large application handles search, cart, payments and recommendations. A defect in recommendations has forced a full redeployment of the whole system twice this quarter. The team wants each function to be developed, deployed and scaled by its own small team. Which architecture style addresses this?
A: A monolithic architecture, which keeps all functions in one deployable unit so that they can change together
B: A microservices architecture, in which an application is split into small, independently deployable services
C: A single bigger virtual machine, which adds capacity but leaves the one deployable unit unchanged
D: A backup and recovery architecture, which copies data to a second location to guard against outages
K: B
G: ## Monolith vs microservices
In a **monolith** every function is built and deployed together. It is simple at first, but one defect can force a full release, and the whole system must scale even if only one part is busy.
**Microservices** split an application into small services that each do one job, communicate through APIs, and are deployed and scaled independently.
## Business value
- Faster, safer releases because a change touches one service.
- Targeted scaling, such as more capacity for search during a sale.
- Teams own services end to end.
## Trade-off
More services mean more to coordinate and monitor, which is why containers, Kubernetes and managed services are often used alongside them.
W: Microservices: search, cart, payments and recommendations become separate services that teams can release and scale on their own, ending the whole-system redeployments.
X: A=Monolithic: this is the current design that causes full redeployments, so keeping it will not help.
C=Bigger VM: more capacity does nothing for the coupled release process, so a recommendations defect would still force a full redeploy.
D=Backup architecture: copying data supports recovery, but the problem is how the application is built and released.
T: Microservices split an application into independently deployable and scalable services, enabling faster releases and targeted scaling.

@ GCP-CDL D4 T4.1 applied use-case
S: A small team builds an app that processes photo uploads in occasional bursts: many in a few minutes and then none for hours. It wants to pay only while code is running and never manage servers. Which compute model fits?
A: Dedicated VMs left running around the clock, so capacity for the largest burst is always available
B: A self-managed Kubernetes cluster, so the team can tune the nodes that process each upload
C: Serverless computing, in which the provider allocates and scales resources on demand and bills for actual use
D: An on-premises server sized for the largest burst, to avoid any dependence on the cloud provider
K: C
G: ## Serverless computing
In **serverless computing** the cloud provider allocates and scales the machines automatically, and developers deploy code or containers without provisioning VMs. Servers still exist, but the customer does not see or manage them. Billing follows actual use, so idle time costs little or nothing.
## Good fit
- Spiky or unpredictable traffic.
- Event-driven work, such as reacting to an uploaded file.
- Small teams that want to focus on code rather than infrastructure.
## Limits
Less control over the environment, and long-running or specialised workloads may suit VMs or Kubernetes better.
## Reading the scenario
Bursts, long idle gaps, no server management and pay-per-use point to serverless.
W: Serverless: capacity follows the bursts automatically and falls to zero when idle, with no servers for the team to manage.
X: A=Always-on VMs: paying around the clock for peak capacity wastes money through the long idle periods.
B=Self-managed Kubernetes: this adds node and cluster operations, which the team wants to avoid, even though Kubernetes can scale.
D=On-premises server: sizing for the peak leaves hardware idle most of the time and gives up the on-demand scaling the cloud offers.
T: Serverless means no server management, automatic scaling (including to zero) and billing for actual use.

@ GCP-CDL D4 T4.1 applied tradeoff
S: A research institute runs a nightly genome-processing batch job. The job can be restarted from checkpoints, finishes within hours, and has no strict deadline. The institute wants the lowest compute cost. What is the trade-off of using Spot VMs?
A: They cost much less as they use spare capacity, but Google can reclaim them, so the job must tolerate it
B: They cost less because they are slower hardware, and they are guaranteed to run until a job completes
C: They cost the same as regular VMs, but they are the only type that can run batch jobs at night
D: They cost more than regular VMs, but they are never interrupted and so suit any deadline-bound job
K: A
G: ## Spot VMs
**Spot VMs** are Compute Engine virtual machines that use spare capacity at a significant discount. The trade-off is that Compute Engine may stop (preempt) them at any time to reclaim the capacity.
## Good fit
- Fault-tolerant, restartable work such as batch processing, rendering or analysis.
- Stateless workloads that can lose a machine without harm.
## Poor fit
- Applications that must stay up continuously or finish by a fixed deadline, such as a customer-facing payment service.
## Reading the scenario
Checkpointed, flexible-deadline batch work is the ideal tolerance for interruption in return for the lowest cost.
W: Lower cost in exchange for possible interruption: the checkpointed batch job can resume after a preemption, so the discount carries little risk.
X: B=Slower but guaranteed: Spot VMs are not slower hardware, and nothing guarantees they keep running to completion.
C=Same price, only batch option: Spot VMs are discounted, and batch jobs can run on any type of VM at any time.
D=More expensive and never interrupted: this reverses both the pricing and the interruption behaviour that define Spot VMs.
T: Spot VMs trade a deep discount for possible preemption, so use them for fault-tolerant, flexible work.

@ GCP-CDL D4 T4.1 applied use-case
S: A company has packaged dozens of services as containers. Operators now struggle to keep the right number of copies running, restart those that fail, roll out new versions without downtime and spread them over many machines. Which technology automates this container management?
A: Kubernetes, an open source system that orchestrates the deployment, scaling and management of containers
B: A relational database, which stores the records the services produce and can keep them consistent
C: A content delivery network, which caches static content near users to shorten page load times
D: A virtual private network, which encrypts traffic between the offices and the cloud
K: A
G: ## Kubernetes: orchestrating containers
Running a few containers by hand is easy. Running hundreds across many machines is not. **Kubernetes** is an open source system that automates deployment, scaling and management of containerized applications. It groups containers into pods and:
- Keeps the desired number of copies running and restarts failed ones.
- Rolls out updates gradually and can roll them back.
- Scales copies up or down with demand and balances traffic between them.
## Google connection
Google originally designed Kubernetes and it is open source, which supports portability. Google Kubernetes Engine (GKE) is Google's managed Kubernetes service, covered in a later task.
## Reading the scenario
Every pain point listed is something an orchestrator handles.
W: Kubernetes: it is built to keep containers running at the desired scale, restart failures, roll out updates and place workloads across machines.
X: B=Relational database: it stores records and does not place, restart or update application containers.
C=Content delivery network: caching static content speeds delivery to users but does not manage how services run.
D=VPN: encrypted connectivity is a network function, unrelated to running and scaling containers.
T: Kubernetes orchestrates containers: it keeps them running, scales and updates them, and spreads them across machines.
V: Google Kubernetes Engine

@ GCP-CDL D4 T4.1 applied use-case
S: A ticket-selling site sees traffic rise tenfold within minutes when sales open, then fall again. In the past it bought hardware for the peak and paid for it all year. Which feature lets the site match capacity to demand automatically in the cloud?
A: Autoscaling, which adds resources when demand rises and removes them when it drops
B: Rehosting, which moves the application to another data center before each sale
C: Data warehousing, which stores historical ticket sales so that they can be analyzed later
D: Retaining, which keeps a fixed amount of capacity running so that costs stay predictable
K: A
G: ## Autoscaling
**Autoscaling** automatically adjusts the number or size of resources, such as VMs or container copies, to match demand, based on measures such as load or traffic. Capacity grows when demand grows and shrinks when demand falls.
## Business value
- **Performance**: the site stays responsive during peaks.
- **Cost**: the company stops paying all year for capacity needed a few days.
- **Less manual work**: no one has to predict and order capacity.
## Reading the scenario
Short, large spikes and wasted peak hardware are the textbook case for elasticity.
W: Autoscaling: resources are added as sales open and removed afterwards, so the site is responsive at the peak without paying for it all year.
X: B=Rehosting: moving to another data center does not change capacity in response to demand.
C=Data warehousing: analyzing past sales may help forecasting, but it does not adjust running capacity.
D=Retaining fixed capacity: a constant amount either falls short at the peak or is wasted the rest of the time.
T: Autoscaling adds and removes capacity with demand, improving performance and avoiding paying for idle peak capacity.
V: Compute Engine, Google Kubernetes Engine

@ GCP-CDL D4 T4.1 applied use-case
S: A media company runs the same web application on many servers in several zones. Visitors sometimes get errors because one server is overloaded while others sit idle, and a failed server still receives traffic. What does a load balancer add?
A: It copies the application's data to a second region so that a backup exists if the first is lost
B: It converts the application into microservices so that each function runs on a different server
C: It distributes incoming requests across healthy servers, improving availability and use of capacity
D: It encrypts the data stored on every server so that a stolen disk cannot be read
K: C
G: ## Load balancing
A **load balancer** is the single front door for an application. It spreads incoming requests across many backend servers and checks their health, so traffic goes only to those that are working.
## Business value
- **Availability**: failed servers are skipped, so users do not see their failures.
- **Performance**: no single server is overwhelmed while others are idle.
- **Scalability**: when autoscaling adds servers, the load balancer begins using them.
## What it does not do
It does not back up data, restructure the application or encrypt storage.
## Reading the scenario
Uneven load plus traffic sent to a failed server is exactly what a load balancer corrects.
W: Distributes requests to healthy servers: overloaded and failed servers stop receiving all the traffic, so errors fall and capacity is used evenly.
X: A=Cross-region data copy: replication protects data, but it does not decide which server handles a request.
B=Microservices conversion: a load balancer routes requests and never changes how the application is built.
D=Disk encryption: protecting stored data is a security measure that does not affect where traffic is sent.
T: Load balancing spreads requests across healthy servers for availability and even use of capacity.
V: Cloud Load Balancing

@ GCP-CDL D4 T4.1 applied use-case
S: A mid-sized company runs its own databases, patching and backups, and its small IT team spends most of its week on this routine upkeep rather than on projects that serve customers. Which approach most directly frees that time?
A: Buying more powerful servers, so that the routine maintenance tasks finish more quickly each week
B: Using managed services, in which Google operates the underlying infrastructure and handles tasks such as patching and backups
C: Moving the same self-managed databases to larger virtual machines, to give them more headroom for growth
D: Hiring an additional team to take over the maintenance, so that the existing staff are not involved
K: B
G: ## Managed services
With a **managed service**, the cloud provider runs the underlying infrastructure and routine operations, such as provisioning, patching, backups, scaling and availability, while the customer uses the service and configures it for their needs. Examples include managed databases, managed Kubernetes and serverless platforms.
## Business value
- Staff move from upkeep to work that differentiates the business.
- Fewer errors and often better reliability, since the provider operates the service at scale.
- Faster delivery of new applications.
## Trade-off
Less low-level control than self-managing on VMs, and the customer still handles security of their own data and access.
## Reading the scenario
The scarce resource is IT staff time, and a managed service removes the routine work.
W: Managed services: Google handles patching, backups and infrastructure operations, so the team can spend its time on customer-facing projects.
X: A=Faster servers: better hardware may speed up some tasks, but the team still has all the maintenance to do.
C=Larger VMs: more capacity does not reduce patching and backups, which remain the team's responsibility on self-managed databases.
D=Extra team: hiring does shift the work but adds cost and still keeps the operation in-house, whereas a managed service removes it.
T: Managed services shift routine operations to the provider so that staff can focus on differentiating work.
V: Cloud SQL

@ GCP-CDL D4 T4.1 advanced tradeoff
S: A company is choosing among VMs, containers on Kubernetes and serverless for different applications. Which TWO statements describe the trade-offs correctly? (Select TWO)
A: Serverless gives the provider most of the operations, but offers less control over the underlying environment than VMs
B: VMs give the least control and the least operational effort, because Google patches the guest operating system
C: Kubernetes removes all operations work, because the applications scale and update themselves without any configuration
D: VMs give the most control over the operating system, but the company carries more work to patch, size and scale them
E: Serverless always costs the least, because it is cheaper than any other model for steady, constantly busy workloads
K: A,D
G: ## A spectrum of control and effort
Compute choices run from most control to most provider-managed:
- **VMs**: highest control (OS level), highest customer effort (patch, size, scale).
- **Containers on Kubernetes**: high control over the application, less over the machines; medium effort because orchestration still needs setup.
- **Serverless**: lowest control, lowest effort because the provider handles servers and scaling.
## No universal winner
Each application is placed according to its needs: custom OS requirements point to VMs, portable microservices to containers, and spiky event-driven work to serverless. A company often uses all three.
W: A=Serverless trade-off: the provider handles servers and scaling, at the cost of less control over the environment, so this is correct.
D=VMs trade-off: full OS control comes with the work of patching, sizing and scaling, so this is correct.
X: B=VMs least control: VMs give the most control and the most effort; the guest OS patching is generally the customer's task.
C=Kubernetes no operations: Kubernetes automates a lot, but it must still be configured, and someone must design and operate the workloads.
E=Serverless always cheapest: the pay-per-use model is best for variable demand, but a constantly busy workload may be cheaper on other models.
T: More control means more operations effort; serverless trades control for less work, VMs the reverse.
V: Compute Engine, Cloud Run, Google Kubernetes Engine
