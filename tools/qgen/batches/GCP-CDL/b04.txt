@ GCP-CDL D2 T2.2 applied use-case
S: An online fashion retailer sells in North America, Europe and Asia. Its order and inventory records must be updated by shoppers on every continent at the same time, and no shopper may ever see a stale stock count or an order that later disappears. The company also wants the database to stay available without planned downtime as it grows. Which Google Cloud product fits?
A: Cloud SQL, because it is a managed MySQL, PostgreSQL and SQL Server service that suits a single-region application
B: Spanner, because it is a relational database that offers strong consistency across regions and scales horizontally
C: Bigtable, because it is a wide-column store built for very high throughput on key-based reads and writes
D: BigQuery, because it is a serverless data warehouse that runs large analytical queries with SQL
K: B
G: ## Relational databases and consistency
A **relational database** keeps data in tables with defined relationships and uses **SQL**. Its key promise for business records is the **transaction**: a group of changes either all happen or none do, and every reader afterwards sees the same result. That promise is called **strong consistency**.
## Where Spanner fits
Spanner is Google Cloud's globally distributed relational database. It combines the SQL and transaction guarantees of a traditional database with the horizontal scale that used to belong to NoSQL systems, and it is built for always-on availability. That is the unusual combination a global retailer needs: many writers on several continents, one correct answer for everyone.
## Reading the scenario
The decisive phrases are "every continent at the same time", "never see a stale count" and "no planned downtime". They point to a globally consistent relational database, not to a regional managed database, a key-value store or a warehouse.
W: Spanner: it gives relational tables, SQL and strongly consistent transactions across regions, and it scales out without re-architecture, which matches global writers and a need for continuous availability.
X: A=Cloud SQL: a fine managed relational service for MySQL, PostgreSQL and SQL Server, but it is aimed at regional applications of moderate size and is not designed for strongly consistent writes from every continent.
C=Bigtable: it scales extremely well for key-based reads and writes, but it is not a relational database with multi-row transactions for orders and inventory.
D=BigQuery: it analyzes large datasets with SQL, but it is a data warehouse for reporting, not the system where shoppers place and update orders.
T: Global, strongly consistent, relational transactions at scale point to Spanner.
V: Spanner, Cloud SQL, Bigtable, BigQuery

@ GCP-CDL D2 T2.2 applied use-case
S: A streaming video company keeps a back catalog of millions of titles. Some old shows suddenly become popular after a social media trend, while thousands of others sit untouched for months, and nobody can predict which is which. The storage team does not want to review access reports and move objects between storage classes by hand. Which approach fits?
A: Leave every object in the Rapid storage class so that popular titles load quickly at any time
B: Enable Autoclass on the bucket so that Cloud Storage moves each object between classes based on how it is accessed
C: Move the entire catalog to Archive storage now, because older content is always the least valuable
D: Create a separate bucket for each show and ask the editors to pick a storage class for that bucket every quarter by hand
K: B
G: ## Storage classes follow access frequency
Cloud Storage is object storage, and its classes trade storage cost against access cost. The location-flexible classes are Standard (frequently accessed data), Nearline (about once a month or less), Coldline (about once a quarter or less) and Archive (once a year or less). A fifth class, Rapid, is only for zonal buckets that sit next to compute for I/O-intensive work.
Colder classes cost less to store but charge for access and carry a minimum storage duration, so putting a popular object in a cold class can cost more than it saves.
## Autoclass
When access patterns are unpredictable, **Autoclass** manages classes for you. It moves objects that are not accessed to colder classes and moves objects that are accessed back to Standard. The business gets the saving of cold storage without staff studying access logs.
W: Autoclass: it adjusts each object's class automatically from its access pattern, which fits a catalog where popularity is unpredictable and the team wants no manual reviews.
X: A=Rapid for everything: Rapid is a high-performance class for zonal buckets and I/O-intensive workloads; it is not meant as a cost-saving home for a mostly idle catalog.
C=Archive for everything: the assumption that old content is never read is exactly what the trend contradicts, and Archive charges for access and has a long minimum storage duration, so popular titles would be costly.
D=Manual per-show buckets: this recreates the manual class management the team wants to avoid, and a quarterly review cannot react to a sudden viral spike.
T: Unpredictable access patterns are the case for Autoclass.
V: Cloud Storage, Autoclass

@ GCP-CDL D2 T2.2 applied use-case
S: A manufacturer keeps quality-inspection images for every production batch. Engineers open them roughly once a quarter to prepare supplier reviews, and almost never in between. The data volume keeps growing, and the finance team wants lower storage cost while the images remain available within milliseconds when needed. Which Cloud Storage class is the best match?
A: Standard, because data that is opened at all should stay in the class meant for frequent access
B: Nearline, because it is designed for data read about once a month or less often
C: Coldline, because it is designed for data read about once a quarter or less often
D: Rapid, because it gives the lowest latency to workloads that read the images right next to compute
K: C
G: ## Matching class to access frequency
Cloud Storage classes are chosen by how often data is read. Rough guidance in the documentation:
- **Standard**: frequently accessed ("hot") data.
- **Nearline**: read or modified on average about once a month or less.
- **Coldline**: read or modified at most about once a quarter.
- **Archive**: data kept for backup, regulatory or disaster-recovery reasons and accessed less than once a year.
- **Rapid**: a zonal class for I/O-intensive workloads that need the lowest latency next to compute.
All of the first four keep data online and available in milliseconds, not hours; the colder the class, the lower the storage cost and the higher the access cost and the minimum storage duration.
## Reading the scenario
"Once a quarter", "growing volume", "lower cost" and "still available within milliseconds" together describe Coldline.
W: Coldline: its sweet spot is data touched about once a quarter, giving a much lower storage cost than Standard or Nearline while still serving objects within milliseconds.
X: A=Standard: it is the right home for hot data, but for images used four times a year it pays a higher storage cost for access speed the team does not need.
B=Nearline: it fits data read about once a month, so it would cost more to store than needed for quarterly access.
D=Rapid: it is a zonal class for latency-critical, I/O-heavy work; it does not fit a growing, rarely opened image archive.
T: Match the class to access frequency: monthly is Nearline, quarterly is Coldline, yearly or less is Archive.
V: Cloud Storage

@ GCP-CDL D2 T2.2 applied use-case
S: A regional chain of dental clinics runs a scheduling and billing application that was written for MySQL. The clinics have no database administrators and want to move off a single aging server. They need automated backups, patching and failover, but they have no need for global scale and do not want to rewrite the application. Which Google Cloud service should they choose?
A: Spanner, to rebuild the whole application around a globally distributed database with virtually unlimited scale and strong consistency
B: Bigtable, to store the appointments and invoices as wide-column rows spread across a large cluster
C: Cloud SQL for MySQL, a managed service running the same engine with backups, patching and failover handled
D: Firestore, to hold appointments as documents with flexible fields and mobile synchronization
K: C
G: ## Managed relational databases
Many business applications are built on a standard relational engine such as MySQL, PostgreSQL or SQL Server. **Cloud SQL** runs those engines as a fully managed service: Google handles backups, patching, replication and failover, and the application keeps talking to the same engine it already knows.
## Why it is the lowest-effort move
- No application rewrite, because the engine is unchanged.
- No database administrator is needed for routine operations.
- The scale matches a regional business; nothing here calls for a global database.
## Reading the scenario
"Written for MySQL", "no administrators" and "do not rewrite" all point to a managed version of the same engine.
W: Cloud SQL for MySQL: the application keeps its engine and SQL, while Google takes over backups, patching and failover that the clinics cannot staff themselves.
X: A=Spanner: it is powerful, but it targets global, massive-scale workloads and would mean re-engineering a small application for capacity the clinics will never use.
B=Bigtable: it is a NoSQL key-based store for high-throughput data, not a relational engine that a MySQL application can use without a rewrite.
D=Firestore: a document database is a different data model, so the billing logic would have to be redesigned around documents instead of tables.
T: A familiar relational engine with no administration burden is Cloud SQL.
V: Cloud SQL

As the business grew, the database became slow under heavy transactions, and analysts also want to run reports on fresh operational data without slowing customers down. Leadership wants to keep PostgreSQL compatibility so developers do not relearn anything. Which service best fits this goal?
A: AlloyDB for PostgreSQL, a PostgreSQL-compatible database built for demanding transactional workloads and analytics
B: Cloud Storage, an object store that keeps order data as files in buckets and answers application queries through SQL joins
C: Firestore, a document database that replaces PostgreSQL tables with collections of documents

Google Cloud has two managed ways to run PostgreSQL workloads:

The company is staying on PostgreSQL but has outgrown a general-purpose setup, and wants analytics on operational data. That is the profile of AlloyDB. A different data model would force developers to relearn and rewrite.
W: AlloyDB for PostgreSQL: it stays fully PostgreSQL-compatible, so developers keep their skills and tools, while giving the performance and scale for heavy transactions plus analytical queries on live data.

@ GCP-CDL D2 T2.2 applied use-case
S: A logistics company equips thousands of delivery trucks with sensors. Each truck reports location, speed and engine readings every second, so the company ingests millions of small timestamped records per minute. Dispatchers need to look up the recent history of a given truck in milliseconds. There are no joins or multi-table transactions. Which database fits this write-heavy, key-based pattern?
A: Spanner, because every single sensor record needs relational constraints and strongly consistent cross-table transactions
B: Cloud SQL, because a single managed MySQL instance is the simplest place for sensor data
C: Cloud Storage Archive, because sensor records are rarely read once they are written
D: Bigtable, because it handles very high read and write throughput at low latency for time-series data
K: D
G: ## NoSQL wide-column stores
Not all data needs tables with relationships. **NoSQL** (non-relational) databases trade some relational features for scale and speed on simple access patterns. **Bigtable** is Google Cloud's wide-column NoSQL database: rows are found by a single key, and it scales to billions of rows with high throughput and low latency.
## Typical uses
- Time-series data, such as server or sensor readings over time.
- Internet of Things data, such as meters and appliances.
- Large analytical or machine learning inputs that need fast key-based reads and writes.
## Reading the scenario
Millions of small timestamped records, lookups by truck, no joins or multi-table transactions: that is the Bigtable pattern. The word "milliseconds" also rules out a cold archive class.
W: Bigtable: it is built for huge write and read throughput on key-based data with low latency, which is how sensor and time-series workloads behave.
X: A=Spanner: it offers relational transactions, but the scenario needs none of that, and paying for a globally consistent relational design is unnecessary for simple keyed lookups.
B=Cloud SQL: a single managed relational instance would struggle with millions of records per minute and is not designed for that write volume.
C=Cloud Storage Archive: dispatchers need recent history in milliseconds, and Archive charges more for access, so it suits data kept for compliance and not live lookups.
T: High-throughput, key-based time-series and IoT data is the Bigtable use case.
V: Bigtable, Spanner, Cloud SQL, Cloud Storage

@ GCP-CDL D2 T2.2 applied use-case
S: A startup is building a mobile app that lets small teams share task lists. Users edit lists on their phones, sometimes without a connection, and expect changes to appear on teammates' devices as soon as they reconnect. Each task has different optional fields that the product team keeps changing. Which database fits best?
A: Firestore, a serverless document database with real-time synchronization and offline support for mobile and web apps
B: BigQuery, a data warehouse that stores each task update as a row for later analysis with SQL
C: Cloud SQL, a managed relational database that requires a fixed table design defined in advance for every task field and each change
D: Spanner, a globally consistent relational database for banking-style transactions across regions
K: A
G: ## Document databases
A **document database** stores each record as a flexible, JSON-like document, so different records can have different fields without a schema change. **Firestore** is Google Cloud's fully managed, serverless document database for mobile, web and server applications. It scales automatically and offers built-in real-time synchronization and offline handling, which are valuable for collaborative apps.
## Reading the scenario
Three signals: documents with changing optional fields, offline editing, and updates syncing to teammates. These are the Firestore strengths. Relational choices need a fixed schema and have no built-in device sync; a warehouse is for analysis, not for serving an app.
W: Firestore: flexible documents absorb the changing task fields, and built-in real-time sync with offline support lets phones edit offline and converge when they reconnect.
X: B=BigQuery: it is built for analyzing large datasets, not for serving an interactive app with per-user live updates.
C=Cloud SQL: a fixed relational design makes every new optional field a schema change, and it has no native device synchronization.

T: Flexible documents with real-time and offline sync for mobile apps point to Firestore.

@ GCP-CDL D2 T2.2 applied use-case
S: A national retailer has ten years of sales, loyalty and web-traffic history, many terabytes in total. Business analysts, who know SQL, want to run complex aggregate reports across all of it, such as revenue by region and product over time. The company does not want to size, tune or maintain database servers. Which service should hold and analyze this data?
A: Firestore, because documents can store each sales record with a flexible set of fields
B: BigQuery, because it is a serverless data warehouse that analyzes very large datasets with SQL and no servers to manage
C: Bigtable, because key-based lookups on a single sales row return in milliseconds
D: Cloud SQL, because analysts can query the whole ten-year history from one managed relational instance that the team sizes and tunes
K: B
G: ## Operational databases vs a data warehouse
Databases such as Cloud SQL, Spanner, Bigtable and Firestore serve **applications**: they handle many small reads and writes quickly. A **data warehouse** serves **analysis**: it answers big questions that scan and aggregate huge volumes of history.
**BigQuery** is Google Cloud's fully managed, serverless data warehouse. Analysts use SQL (and Python) and Google runs the infrastructure, so there are no servers to size or tune. BigQuery handles terabytes in seconds and petabytes in minutes for business intelligence and ad hoc analysis.
## Reading the scenario
Years of history, SQL-skilled analysts, large aggregations and no wish to manage servers all describe a warehouse.
W: BigQuery: serverless storage and SQL analysis at terabyte-to-petabyte scale lets analysts run big aggregate reports with no database administration.
X: A=Firestore: it serves mobile and web applications with document reads and writes, not large cross-history aggregations.
C=Bigtable: it excels at fast key-based access for operational data, but is not the place for ad hoc SQL reporting across all history.
D=Cloud SQL: a single relational instance is built for transactional applications and would need sizing and tuning for terabyte-scale scans, which the company wants to avoid.
T: Large-scale SQL analytics with no infrastructure is BigQuery.

@ GCP-CDL D2 T2.2 advanced definition
S: A new executive asks the data team to explain the difference between relational and non-relational databases in plain terms. Which TWO statements are accurate? (Select TWO)
A: A relational database stores data in tables with defined relationships and is queried with SQL
B: A non-relational (NoSQL) database cannot scale beyond one server and is used only for small applications
C: A non-relational database can store data as documents, key-value pairs or wide columns, often with a flexible schema
D: A relational database is a type of object storage that keeps each row as a separate file
E: A non-relational database requires the same fixed table design as a relational one, only with different software
K: A,C
G: ## Two families of databases
- **Relational databases** organize data into tables of rows and columns, with relationships between tables and a fixed schema. They are queried with **SQL** and are strong for transactions, where several changes must succeed together. Google Cloud examples: Cloud SQL, AlloyDB, Spanner.
- **Non-relational (NoSQL) databases** use other models, such as documents (Firestore), wide-column key-based stores (Bigtable) and key-value pairs. The schema is often flexible, and many designs scale out very widely for simple access patterns.
- **Object storage** (Cloud Storage) is a third idea: data kept as whole objects, such as images or backups, in buckets, not as rows.
## Reading the options
The correct statements describe tables plus SQL, and the variety and flexibility of NoSQL models.
W: A=Tables and SQL: this is the definition of a relational database, which is why it suits structured business records and transactions.
C=NoSQL models: non-relational databases cover documents, key-value and wide-column designs, and a flexible schema is a common reason to choose them.
X: B=Cannot scale: this is backwards, because several NoSQL databases, such as Bigtable, were designed to scale across many machines for very large workloads.
D=Rows as files: this confuses relational storage with object storage; relational databases store rows in tables, not as separate files in buckets.
E=Same fixed design: NoSQL databases are defined by not requiring the fixed table-and-relationship model, so this statement erases the real difference.
T: Relational means tables and SQL; non-relational covers documents, key-value and wide-column models with flexible schemas.
V: Cloud SQL, Spanner, Firestore, Bigtable

Files fetched by name, unlimited growth and no SQL: that is the profile of object storage. The other options each describe a different category of data service.

@ GCP-CDL D2 T2.2 advanced troubleshooting
S: A company moved last year's customer-support recordings to Archive storage to save money. This quarter the compliance team began reviewing the recordings every week, and the storage bill went up instead of down. What explains the result?
A: Archive storage cannot be read at all until the objects are first moved back to Standard storage
B: Archive storage costs more per stored gigabyte than Standard storage once data is a year old
C: Archive storage is a zonal class, so the weekly reviews are charged a cross-region transfer fee each time
D: Archive is meant for data read less than once a year, so frequent reads add access costs that outweigh savings
K: D
G: ## The trade-off behind colder classes
Each Cloud Storage class makes storage cheaper in exchange for more expensive access. Colder classes also have a **minimum storage duration** (longer for each colder class) and charge **retrieval fees** when data is read.
- Archive has the lowest storage cost and the highest access cost. It is meant for data kept for legal, regulatory or disaster-recovery reasons and read less than once a year.
- Data is still available in milliseconds, so nothing breaks, but the access charges add up fast when data is read often.
## Reading the scenario
A weekly review changed the access pattern from "rarely" to "frequently". The mismatch between pattern and class, not a malfunction, drives the higher bill. Moving the data to a warmer class, or using Autoclass for changing patterns, would fix it.
W: Access costs outweigh savings: Archive is priced for reads less than once a year, so weekly reviews pay retrieval charges that exceed the lower storage price.
X: A=Must restore first: Archive data is served within milliseconds like other classes; it does not need a restore step, so this is not the cause.
B=Always costs more: the opposite is true, because Archive has the lowest storage price of all the classes; its cost problem is access, not storage.
C=Zonal class: Archive is available in regions, dual-regions and multi-regions; the zonal-only class is Rapid, and no cross-region fee of this kind applies.
T: A cold class saves money only while data stays cold; frequent reads turn access fees into the main cost.
V: Cloud Storage

For AI training, idle accelerators are an expensive waste. Faster data delivery keeps them busy, so the team trains sooner for the same infrastructure.

The bottleneck is latency to storage, and the compute sits in one zone. Cost-saving classes and multi-location durability do not address that.

S: A mid-sized insurer runs several self-managed databases on virtual machines in its own data center. Its administrators spend most of their week on patching, backups and failover tests. Leadership wants to modernize by moving to managed database services. Which TWO benefits should leadership expect? (Select TWO)
A: Google takes over routine tasks such as backups, patching and failover so staff can focus on applications and data
B: The insurer is released from all responsibility for who can access its data and how it is classified

With a self-managed database, the company runs the servers and the operating system and does the maintenance itself. - Staff time moves from maintenance to work that differentiates the business.

T: Managed databases hand routine operations and capacity planning to Google, while data governance stays with the customer.

@ GCP-CDL D2 T2.2 advanced comparison
S: A small consultancy and a global payments company each need a new relational database. The consultancy's internal tool will serve a few hundred users in one region. The payments company must process transactions from customers on several continents with strong consistency and near-continuous availability. Which pairing of products is the most appropriate?
A: Spanner for the consultancy and Cloud SQL for the payments company
B: Bigtable for the consultancy and Firestore for the payments company
C: Cloud SQL for the consultancy and Spanner for the payments company
D: BigQuery for the consultancy and Cloud Storage for the payments company
K: C
G: ## Right-sizing a relational choice
Google Cloud offers several relational databases, and the right one depends on scale and consistency needs:
- **Cloud SQL**: managed MySQL, PostgreSQL and SQL Server; ideal for regional applications of moderate size and for teams that want a familiar engine.
- **AlloyDB**: PostgreSQL-compatible, for demanding performance.
- **Spanner**: globally distributed with strong consistency, horizontal scale and very high availability, for mission-critical workloads.

W: Cloud SQL for the consultancy and Spanner for the payments company: a simple managed engine fits a small regional tool, while multi-continent, strongly consistent, always-on transactions are Spanner's purpose.
X: A=Reversed pairing: it gives a global scale-out database to a small tool and a regional database to a global payment system, which is the wrong fit for both.

D=Warehouse and object storage: BigQuery analyzes data and Cloud Storage keeps files, so neither can serve as the transactional database either company asked for.
T: Pick the smallest product that meets the need: Cloud SQL for regional relational apps, Spanner for global strongly consistent ones.

@ GCP-CDL D2 T2.3 advanced use-case
S: A credit-card company reviews transactions for fraud in a nightly batch job. Fraudsters often make many purchases within minutes, so most losses happen before the next morning's review. Executives ask why the company should invest in real-time streaming analytics. Which TWO statements describe the value? (Select TWO)
A: Streaming analytics removes the need for any historical data, because only the latest event matters
B: Events are analyzed as they happen, so suspicious activity can be flagged and acted on within seconds instead of hours
C: Streaming analytics guarantees that no transaction will ever be fraudulent
D: Decisions and customer experiences can be based on current data, such as blocking a card or sending an alert immediately
E: Streaming analytics works only if the company copies all transaction data into a spreadsheet each night
K: B,D
G: ## Batch vs streaming
- **Batch analytics** collects data over a period and processes it later, for example nightly. Results describe the past.
- **Streaming (real-time) analytics** processes each event as it arrives, so results describe the present.
The business value of streaming is **timeliness**: when the value of an action falls quickly with time, such as stopping fraud, rerouting a delivery or adjusting a price, waiting for a batch means missed opportunity or avoidable loss.
## What streaming does not do
It does not replace historical analysis (models are often trained on history), and it does not make risk disappear. It shortens the time between an event and a response.
W: B=Analysis as events happen: acting within seconds rather than hours is the central benefit and addresses losses that happen in the minutes before a nightly review.
D=Decisions on current data: real-time insight enables immediate responses, such as blocking a card or alerting the customer.
X: A=No historical data needed: historical data is still valuable for trends and for training detection models; streaming adds current data to it.
C=Guarantees no fraud: analytics reduces and speeds up the response to fraud; no technology guarantees that fraud never happens.
E=Nightly spreadsheet: this is the opposite of streaming, since data is analyzed continuously and not once a night in a spreadsheet.
T: Streaming analytics turns data into action while it still matters, which cuts losses and improves customer experiences.
V: Pub/Sub, Dataflow, BigQuery

@ GCP-CDL D2 T2.3 applied definition
S: A smart-home company has millions of thermostats that send readings continuously. Several teams, such as billing, energy forecasting and device support, each need to consume these readings, and engineers do not want the thermostats to depend on any team's systems being online. Which service decouples the senders from the consumers?
A: Looker, a business intelligence platform that visualizes the readings in dashboards
B: Pub/Sub, a messaging service where publishers send events to a topic and subscribers receive them
C: Cloud SQL, a relational database that every team queries directly whenever it needs the latest thermostat reading
D: Cloud Storage Coldline, a low-cost class that keeps readings for long-term retention
K: B
G: ## Messaging that decouples systems
**Pub/Sub** is an asynchronous, scalable messaging service. Producers of events are **publishers**; they send messages to a **topic** without knowing who will read them. Consumers are **subscribers**; they receive messages at their own pace. Because neither side waits for the other, one slow or offline consumer does not stop the senders.
## Typical uses
- Ingesting user-interaction, server and IoT events.
- Distributing events to many applications (an enterprise event bus).
- Feeding stream-processing tools such as Dataflow, which write results to BigQuery and other stores.
## Reading the scenario
Millions of senders, many independent consumers and no dependency between them: this is a publish and subscribe pattern.
W: Pub/Sub: thermostats publish to a topic and each team subscribes on its own, so senders never depend on a consumer being online.
X: A=Looker: it presents and explores data, but it does not receive streams of events from devices or distribute them to systems.
C=Cloud SQL: having every team query one database couples all of them to it and is not designed for millions of continuous device events.
D=Coldline: it is a storage class for data read about once a quarter; it does not deliver events to consumers.
T: Pub/Sub decouples event producers from consumers and carries streaming data into pipelines.
V: Pub/Sub
