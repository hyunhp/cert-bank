@ GCP-PSE D4 T4.2 applied use-case
S: A company stores regulated customer documents in Cloud Storage buckets that live in projects under its `prod` folder. Auditors require a record of who reads and writes those objects. Other folders hold development workloads, and the security lead wants to limit log volume and cost. What should the security engineer configure?
A: Enable the DATA_READ and DATA_WRITE log types for the Cloud Storage service in the audit configuration of the `prod` folder
B: Enable every Data Access log type for all services in the organization-level audit configuration, then filter out development noise later
C: Enable only ADMIN_READ logging for Cloud Storage, because object contents are not touched by that log type and cost stays low
D: Rely on the Admin Activity audit logs of the buckets, which record every object read and write by default
K: A
G: ## Which audit logs exist and which are off
Cloud Audit Logs writes four kinds of entries. **Admin Activity** (configuration changes) and **System Event** entries are always written and cannot be disabled. **Policy Denied** entries are written by default and can only be kept out of storage with exclusion filters. **Data Access** logs, except for BigQuery, are disabled by default because the volume can be large.
## Data Access log types and where they are configured
- `ADMIN_READ` records reads of configuration or metadata, `DATA_READ` records reads of user-provided data, and `DATA_WRITE` records writes of user-provided data.
- The audit configuration is part of an IAM policy, so it can be set on an organization, a folder or a project, and it is inherited downward. You can also list exempted principals, whose accesses are then not recorded.
- Data Access logs are written to the project whose data is accessed and cost log storage, so scope is a security versus cost decision.
## Applying it
Regulated object access needs `DATA_READ` and `DATA_WRITE` for `storage.googleapis.com` only, set on the folder that holds the regulated buckets. Development folders stay quiet and cost nothing extra.
W: Folder-scoped Cloud Storage data types: the audit configuration is inherited by every project below `prod`, records exactly the object reads and writes auditors ask for, and leaves other folders and services unlogged.
X: B=All services at organization level: it would capture the evidence but also turn on high-volume Data Access logs for every service and every development project, which is the cost the lead wants to avoid; filtering afterwards still pays for generating the entries.
C=ADMIN_READ only: that type covers metadata and configuration reads, so object contents read or written by users would still go unrecorded.
D=Admin Activity logs: they record configuration changes such as bucket updates and IAM changes, not the reading or writing of objects, so they cannot answer who read a document.
T: Data Access logs (other than BigQuery) are off by default; enable only the needed types for the needed services at the narrowest level that covers the regulated data.

@ GCP-PSE D4 T4.2 applied troubleshooting
S: A platform team creates an intercepting aggregated sink at the organization level. Its filter matches all log entries that originate in projects under the `apps` folder, and it routes them to a central security project. Afterwards the application owners report that Logs Explorer in their own projects no longer shows application logs, although Admin Activity audit entries still appear. What explains this, and what is the fix?
A: The sink intercepts, so matching entries skip child sinks such as `_Default`; recreate it as a non-intercepting sink
B: The `_Required` bucket of each project now rejects writes from applications, so its retention must be set to a longer period
C: The destination project is in a different organization, so entries can only be read at the destination until a cross-organization trust is created
D: The sink's writer identity lacks the Logs Bucket Writer role, so it must be granted on every source project's `_Default` bucket
K: A
G: ## Intercepting versus non-intercepting aggregated sinks
An aggregated sink at a folder or organization routes entries from the resource and all its children. Each sink type behaves differently in the hierarchy:
- A **non-intercepting** aggregated sink copies matching entries to its destination and does not change what other sinks do. Child project sinks still evaluate the entry.
- An **intercepting** aggregated sink overrides routing: when an entry matches, it is *not* sent to the sinks in child resources. The one exception is the `_Required` sink, which always receives the entry in the project where it originated.
## Reading the symptom
Admin Activity entries still appear because they belong to the `_Required` bucket, which interception never blocks. Application logs normally land in `_Default`, a sink in the child project, so they disappeared there once intercepted.
## When interception is useful
Interception is the right tool when a central team wants to keep entries out of project buckets entirely (for example to avoid double storage). For a security copy, use a non-intercepting sink.
W: Switch to non-intercepting: matching entries then reach the central project and still flow to each project's own sinks, so owners regain their application logs.
X: B=Longer `_Required` retention: that bucket keeps the entries that still appear and is not affected by the sink; retention is unrelated to the missing application logs.
C=Cross-organization trust: an aggregated sink destination may be in any project and any organization, and no trust is needed; the missing local logs come from interception, not from the destination.
D=Bucket Writer on `_Default`: the writer identity writes to the sink's destination, not to the source projects' buckets, and the project's own `_Default` sink does not use it.
T: An intercepting aggregated sink stops matching entries from reaching child sinks except `_Required`; use non-intercepting sinks when you only want a security copy.

@ GCP-PSE D4 T4.2 advanced troubleshooting
S: An organization-level aggregated sink routes audit logs to a Cloud Storage bucket in a project that is inside a VPC Service Controls perimeter. The sink was created without errors, but no objects arrive in the bucket. Perimeter violation logs show denied writes from the sink's service account. How should the security engineer fix this?
A: Add an ingress rule to the perimeter that allows access from the sink's service account, using ANY_IDENTITY as the identity type for this destination
B: Add an egress rule so that the source projects, which are outside the perimeter, may call Cloud Storage in the destination project
C: Add an ingress rule with the identity type ANY_SERVICE_ACCOUNT, which covers the sink's service account because it is a Google-managed identity
D: Move the Cloud Storage bucket outside the perimeter permanently, because log sinks cannot write to any resource that a perimeter protects
K: A
G: ## Sinks writing into a perimeter
A sink delivers entries with a Google-managed service account, its writer identity, acting from outside the destination project. A VPC Service Controls perimeter around the destination therefore sees an external caller. Cloud Logging documents the requirement: routing log entries to a resource protected by a service perimeter needs an **ingress rule** that allows the sink's service account.
## Aggregated sinks have a special case
- For a non-aggregated sink, no ingress rule is needed.
- For an aggregated sink to a Cloud Storage bucket inside a perimeter, the documented identity type is `ANY_IDENTITY`. `ANY_SERVICE_ACCOUNT` and `ANY_USER_ACCOUNT` do not work for this destination.
## Diagnosis path
Violation logs naming the sink's service account confirm the cause. The fix is a narrowly scoped ingress rule (service `storage.googleapis.com`, the destination project) rather than weakening the perimeter.
W: Ingress rule with ANY_IDENTITY: it admits the writer identity of the aggregated sink to the destination project's Cloud Storage service only, which restores delivery without removing the perimeter.
X: B=Egress rule for source projects: the denied caller is the sink's service account entering the perimeter, which is ingress; egress rules govern calls leaving a perimeter.
C=ANY_SERVICE_ACCOUNT ingress: the documentation states that this identity type does not work for aggregated sinks to a Cloud Storage bucket in a perimeter, so the denials would continue.
D=Moving the bucket outside: sinks can write to protected resources once an ingress rule exists, and moving security logs out of the perimeter removes the protection the perimeter was meant to give.
T: Aggregated sinks into a perimeter need an ingress rule, and for a Cloud Storage destination the identity type must be ANY_IDENTITY.

@ GCP-PSE D4 T4.2 applied definition
S: A central security project stores logs from 12 workload projects in one custom log bucket. Each team lead must read only the entries of their own project, and nobody besides the security team may read the others. What is the most appropriate way to grant this access?
A: Create one log view per project on the bucket, then grant each team lead the Log View Accessor role on only their view
B: Grant each team lead the Log View Accessor role on the central security project, then remind them to filter by project in queries
C: Grant each team lead access to the bucket's `_AllLogs` view and attach an IAM condition on the project ID to the binding
D: Create twelve separate log buckets in the central project and give every team lead the Logs Viewer role on that project
K: A
G: ## Log views limit what a principal reads inside a bucket
Access to logs in a bucket is controlled with IAM. By default a principal with access to the bucket reads everything in it. A **log view** is a filtered subset of the bucket's entries, and it has its own IAM policy, so you can grant access to one view without exposing the rest.
- `_AllLogs` is created automatically and contains every entry in the bucket.
- Log View Accessor (`roles/logging.viewAccessor`) granted on a **project** gives access to views in every bucket of that project; granted on a **specific view** it covers only that view.
- A bucket can hold up to 30 views, enough for 12 projects.
## Why scope matters for security teams
Central storage simplifies analysis for security staff. Log views let the same bucket serve many consumers without splitting storage or duplicating entries.
W: One view per project, granted on the view: each lead reads only entries that match their view's filter, and IAM enforces the boundary instead of user discipline.
X: B=Accessor role on the project: roles granted at project level reach views in all buckets of that project, so each lead could open the all-logs view and read every team's entries; a query filter is not a control.
C=`_AllLogs` with a condition: the all-logs view returns every entry in the bucket, and a binding on the view cannot narrow the entries to one project through a project-ID condition, so the lead would read more than allowed.
D=Twelve buckets and Logs Viewer: Logs Viewer on the project reaches the `_Required` and `_Default` buckets, and the extra storage and sinks add operations without delivering the per-project restriction on shared buckets.
T: Use log views, with IAM granted on the view itself, to give consumers a subset of a bucket's entries; project-level grants reach all views.

@ GCP-PSE D4 T4.2 applied troubleshooting
S: An external auditor was granted the Logs Viewer role on a project. The auditor can see Admin Activity audit entries in the `_Default` bucket but cannot find any Data Access audit entries, although the security team confirmed that Data Access logs are enabled and flowing. Which change meets the auditor's need with least privilege?
A: Grant the auditor the Private Logs Viewer role on the project
B: Grant the auditor the Logs Viewer role on the organization instead of the project
C: Grant the auditor the Logs Configuration Writer role so the auditor can inspect the `_Default` sink
D: Grant the auditor the Logging Admin role on the project, which includes all log read permissions
K: A
G: ## Data Access logs need a separate read role
Logs Viewer (`roles/logging.viewer`) reads all log data in the `_Required` and `_Default` buckets **except** Data Access audit logs. Those entries can contain sensitive information about who read which data, so a distinct role guards them.
- Private Logs Viewer (`roles/logging.privateLogViewer`) adds read access to Data Access audit logs.
- Logs Configuration Writer manages sinks, buckets and exclusions; it is a configuration role, not a reading role.
- Logging Admin is a full administrative role, including changes to sinks and retention.
## Least privilege
An auditor reads evidence; the auditor does not change what is collected. The narrowest grant that adds the missing logs is Private Logs Viewer.
W: Private Logs Viewer: it is the role that adds Data Access audit logs to what the auditor already reads, with no ability to change sinks or retention.
X: B=Logs Viewer on the organization: widening the scope of a role that does not include Data Access logs gives the auditor access to more projects but still no Data Access entries.
C=Logs Configuration Writer: it lets the auditor create or change sinks and exclusions, which risks altering evidence collection, and it does not grant reading of Data Access entries.
D=Logging Admin: it would work, but it also lets the auditor modify sinks, exclusions and retention, which violates least privilege for an audit-only task.
T: Logs Viewer excludes Data Access audit logs; add Private Logs Viewer to read them without administrative rights.

@ GCP-PSE D4 T4.2 advanced use-case
S: Company policy requires that every new Cloud Logging bucket in any project of the organization is encrypted with a customer-managed key from the EU region. Security wants the rule to apply automatically, including to buckets that teams create later. What should the security engineer do?
A: Set organization default resource settings for Cloud Logging with an EU Cloud KMS key and create buckets in the matching location
B: Create a global key and reference it in default settings, since keys in the `global` location can protect log buckets in any region and satisfy residency
C: Ask each team to configure CMEK on its `_Default` bucket after it is created, then audit the buckets quarterly
D: Configure CMEK on the central destination bucket only, because entries routed there inherit the key of the source projects
K: A
G: ## CMEK for Cloud Logging at scale
By default Cloud Logging encrypts content at rest with Google default encryption. For compliance you can use customer-managed encryption keys (CMEK) from Cloud KMS.
- For organizations and folders you can set **default resource settings** for Cloud Logging, including a CMEK key. New `_Default` and `_Required` buckets created in child projects, folders or billing accounts use that key, and custom buckets also use it unless a different key is specified.
- A key can be from any region, but when you create a log bucket **its location must match the key's location**. EU data therefore needs an EU key and EU bucket location.
## Why defaults beat after-the-fact work
Settings inherited from the org apply to buckets that do not exist yet. Per-bucket manual steps leave a window where new resources use Google default encryption and rely on people remembering.
W: Organization default settings with an EU key: new buckets pick up the key automatically, and a matching EU location satisfies the rule that bucket and key regions agree.
X: B=Global key: a bucket's location must match its key's location, so a global key cannot protect an EU log bucket and would conflict with the region requirement.
C=Manual CMEK per `_Default`: it depends on each team, covers only that bucket and leaves new buckets unprotected between creation and the quarterly audit.
D=Destination bucket only: encryption is applied per bucket, not inherited from sources through routing, so source buckets would still use Google default encryption.
T: Use org or folder default resource settings for Cloud Logging to enforce CMEK on new buckets, and keep the bucket and key in the same location.

@ GCP-PSE D4 T4.2 advanced tradeoff
S: An investigation team must be able to show regulators that security logs in a central bucket were retained for seven years and could not be shortened or erased by administrators, including project owners. Which configuration provides this?
A: Set seven-year retention on the bucket and lock it, so retention cannot be reduced and the bucket cannot be deleted early
B: Set the retention period to seven years and rely on IAM to prevent anyone from holding the permission to change retention
C: Route the logs to the `_Required` bucket, whose fixed retention period is applied automatically to every entry routed there by a sink
D: Add an exclusion filter on the `_Default` sink that drops entries from the bucket before their retention period elapses
K: A
G: ## Retention and locking in Cloud Logging
Each log bucket has a retention period (configurable for custom buckets, between 1 and 3650 days; the default is 30 days). Retention alone can be edited by anyone holding the right permission, including a compromised administrator.
- **Locking** a bucket locks its retention policy as well. After locking, the retention period cannot be shortened, and the bucket cannot be deleted until every entry in it has fulfilled the retention period.
- Locking is permanent for the bucket's lifetime. Choose the retention value carefully, because you cannot undo the lock.
## Trade-off
Locking buys tamper resistance and meets evidence rules, but it prevents correcting a wrong value (for example too-long retention) and the storage cost accrues for the full period. Pair it with a project lien so the project hosting the bucket is not deleted.
W: Seven-year retention with a locked bucket: the lock makes the retention immutable and blocks early deletion, which is the guarantee regulators ask for even against owners.
X: B=Retention without a lock: IAM can change over time, and an owner or anyone granted configuration permissions could shorten the period, so the guarantee depends on trust.
C=`_Required`: this bucket holds system audit logs with a fixed retention that you cannot change and does not hold a custom seven-year period for logs routed there.
D=Exclusion filter: exclusions discard entries going into the bucket; they have no role in protecting stored entries and would reduce the evidence kept.
T: A locked log bucket makes retention immutable and prevents early deletion; unlocked retention is only a setting an administrator can change.

@ GCP-PSE D4 T4.2 applied comparison
S: Which TWO events are recorded in Cloud Audit Logs automatically, without any audit configuration being enabled, and cannot be switched off by the project's own audit configuration? (Select TWO)
A: The autoscaler adds a VM to a managed instance group in response to load
B: A user reads the contents of an object in a Cloud Storage bucket
C: A principal calls an API that only reads a resource's metadata
D: A service reads a Secret Manager secret value in a project
E: A user's request is blocked because it violates a VPC Service Controls perimeter
K: A,E
G: ## The four audit log types
- **Admin Activity**: configuration and metadata changes; always on, cannot be disabled.
- **System Event**: written by Google Cloud systems for changes not driven by a user (for example, a managed instance group autoscaling). Always written; you cannot configure, exclude or disable them.
- **Policy Denied**: written when a service denies access because of a security policy violation (for example, VPC Service Controls). On by default and cannot be disabled; you may keep them out of storage with exclusion filters, but you cannot disable generation.
- **Data Access**: reads and writes of data and metadata; disabled by default except for BigQuery, and must be enabled per service and type.
## Applying the types
Reading an object, reading a secret value or reading metadata is Data Access activity (`DATA_READ` or `ADMIN_READ`), which depends on audit configuration. Automatic infrastructure actions and policy denials are written regardless.
W: A=Autoscaler adding a VM: it is a System Event entry written by Google systems without user action, always present and impossible to disable.
E=VPC Service Controls denial: a request denied by a security policy produces a Policy Denied entry by default, and the audit configuration cannot turn that off.
X: B=Object read: reading user data is a `DATA_READ` Data Access entry, which Cloud Storage does not write until the type is enabled.
C=Metadata read: reading configuration or metadata is an `ADMIN_READ` Data Access entry, disabled by default for most services and controlled by audit configuration.
D=Secret value read: accessing a secret's contents is a Data Access event and is written only if the relevant Data Access types are enabled.
T: Admin Activity, System Event and Policy Denied logs are written by default and cannot be disabled; Data Access logs, except BigQuery, must be turned on.

@ GCP-PSE D4 T4.2 advanced tradeoff
S: A SIEM license is priced per ingested gigabyte. The security operations team needs near-real-time audit events from every project in the organization, including new ones, but cannot afford to send all logs. Full copies must remain searchable inside Google Cloud for investigations. Which TWO actions fit? (Select TWO)
A: Create an organization-level aggregated sink with an inclusion filter on audit logs that routes to a Pub/Sub topic read by the SIEM
B: Leave the default sinks in place so the full log set stays in log buckets, and do not add exclusions to them
C: Route all organization logs to Pub/Sub without a filter so the SIEM can apply its own drop rules at ingestion
D: Create a sink in each project that routes to Cloud Storage, and have the SIEM import the files from each bucket every hour
E: Disable Data Access logging organization-wide so fewer entries exist for the SIEM to receive
K: A,B
G: ## Separate the investigation copy from the SIEM feed
Every sink in a resource evaluates a log entry independently, so one entry can reach several destinations. That lets you shape each destination to its purpose.
- The SIEM feed carries a **narrow** selection: an inclusion filter on audit logs (and any other high-signal entries) keeps ingestion and licence costs in check.
- Pub/Sub delivers continuously, so an external SIEM can pull or receive entries in near real time through a subscription. Batch files in Cloud Storage add delay.
- Full copies stay in log buckets (the `_Default` bucket or a central bucket) with the retention you need. Not adding exclusion filters to those sinks keeps the data searchable for investigations.
## Aggregated sinks cover new projects
An organization-level aggregated sink with child inclusion applies to projects created later, so no per-project setup is needed.
W: A=Org aggregated sink with audit filter to Pub/Sub: it covers present and future projects, sends only the selected entries and delivers them continuously to the SIEM.
B=Default sinks without exclusions: log buckets keep the complete set for investigations, independent of what is sent to the SIEM, so cost control for the SIEM does not lose evidence.
X: C=Unfiltered org export: it moves every entry across the SIEM boundary, so the per-gigabyte licence cost the team wants to avoid is incurred before any drop rule applies.
D=Hourly Cloud Storage files: per-project sinks add work for new projects, and hourly batch import is not near real time.
E=Disabling Data Access logs: it lowers volume but removes evidence the security team may need, and it would not bring in entries of other kinds that the SIEM still wants.
T: Give each destination its own filter: a narrow Pub/Sub feed for the SIEM and unfiltered bucket storage for investigation.

@ GCP-PSE D4 T4.2 applied comparison
S: A team adds an exclusion filter to the `_Default` sink to drop verbose Data Access entries from the `_Default` bucket and cut storage. The next week, the security team asks whether the organization-level sink that feeds the SIEM will still receive those entries. What is true?
A: The SIEM feed is unaffected, because each sink applies its own filters independently and the exclusion belongs only to the `_Default` sink
B: The SIEM feed loses the entries, because an exclusion removes entries from the Log Router before any other sink processes them
C: The SIEM feed loses the entries, because exclusions in `_Default` apply to all sinks in the same project and to every aggregated sink above it
D: The SIEM feed is unaffected only if the exclusion filter is deleted, because a sink with exclusions always blocks routing to other destinations
K: A
G: ## How the Log Router evaluates sinks
When a resource receives a log entry, **every sink in that resource independently evaluates it**. A sink sends the entry to its destination when it matches the inclusion filter and does not match any of the sink's own exclusion filters. A matching exclusion affects only the sink that holds it.
- The `_Default` sink exists to fill the `_Default` bucket. Editing it changes what that bucket stores.
- Aggregated sinks higher in the hierarchy process entries before the project's sinks. A non-intercepting aggregated sink is not affected by a child's exclusions; an intercepting one blocks child sinks.
## Practical rule
Exclusions are per-sink cost controls. They do not remove entries from the stream other sinks see, and they do not stop generation of an entry. Stopping generation requires changing the audit configuration, which would also end ETD and SIEM visibility.
W: Independent sinks: the SIEM sink matches on its own inclusion filter and has its own exclusions, so the `_Default` exclusion has no effect on it.
X: B=Exclusion removes entries first: there is no global exclusion stage; each sink applies only its own filters, so entries remain available to other sinks.
C=Exclusions apply to the whole project: an exclusion belongs to one sink and does not propagate to other sinks in the project or to aggregated sinks above it.
D=Deleting the exclusion: a sink with an exclusion does not block other destinations, so there is nothing to delete for the SIEM feed to keep working.
T: Exclusion filters are scoped to the sink that owns them; other sinks still receive the entries unless interception or the audit configuration prevents it.

@ GCP-PSE D4 T4.2 advanced use-case
S: The security team must be notified within minutes whenever the break-glass account `breakglass-admin@example.com` performs any Google Cloud administrative action, in any project. The account is normally dormant. What is the best detection design?
A: Create a log-based alert on Admin Activity entries from that principal, notifying the on-call security team
B: Schedule a weekly query in Logs Explorer for the account's entries and review the results during the security meeting
C: Mute the account's findings in Security Command Center so analysts are not distracted, and review them monthly
D: Enable Data Access audit logs for the account only, since Admin Activity entries are not written when it acts
K: A
G: ## Detecting use of a dormant privileged identity
Break-glass accounts should produce no events day to day; any entry is a signal. Cloud Audit Logs gives the evidence, and Cloud Logging and Cloud Monitoring turn evidence into alerts.
- **Admin Activity** entries are always written, record configuration changes and carry the caller in `protoPayload.authenticationInfo.principalEmail`.
- A **log-based alerting policy** evaluates matching log entries and notifies a channel (email, chat, paging) without a metric dashboard.
- Alerting at organization scope requires the logs to be visible to the policy's scope; routing audit logs from all projects to a central project or using a log scope helps.
## What does not help
A periodic manual query is a review control, not detection. Muting hides findings rather than raising them.
W: Log-based alert on Admin Activity entries from the account: always-on audit entries are matched as they arrive and the on-call team is notified immediately.
X: B=Weekly manual query: a week's delay exceeds the minutes-level requirement, and it depends on someone running it.
C=Muting findings: mute rules hide findings from the default view, which removes attention from the account instead of drawing it.
D=Data Access logs only: Admin Activity entries are written for administrative actions without configuration, so enabling other types adds cost and misses the stated requirement.
T: Detect dormant privileged accounts with a log-based alert on always-on Admin Activity entries and route it to a monitored channel.

@ GCP-PSE D4 T4.2 applied comparison
S: A sandbox folder intentionally contains buckets with public demo data, approved by the CISO for 60 days. Security Health Analytics reports public-bucket findings for them every day and analysts are overwhelmed. The same findings must continue to appear for every other folder. What should the security engineer do?
A: Create a dynamic mute rule scoped to the sandbox folder's findings with an expiration of 60 days
B: Disable the public-bucket detector for the whole organization until the demo period has finished
C: Set each finding's state to INACTIVE manually, because inactive findings stay hidden until the 60 days expire
D: Delete the sandbox projects' findings from the list; the detector then skips resources it has scanned before
K: A
G: ## Mute rather than disable
Security Command Center detection services scan continuously, but some findings are acceptable (isolated assets, approved risk). **Muting** hides a finding from the default view and keeps the scanners running; the findings are still generated and remain hidden until someone views them.
- **Dynamic mute rules** apply to existing and new findings and can be temporary (an expiration time) or indefinite until the finding no longer matches. They are the recommended type.
- **Static mute rules** act indefinitely and take precedence over dynamic ones.
- Disabling a detector removes coverage for every resource it scans, which defeats the "other folders still reported" requirement.
## Muting and compliance
Compliance pages and reports compute percentages from active and muted findings, so muting does not hide the exposure from compliance evidence.
W: Dynamic mute rule with a 60-day expiry: it hides the findings for the approved period only, applies to existing findings, and unmutes automatically while other folders remain visible.
X: B=Disabling the detector: it removes the public-bucket check for every folder, so real exposures elsewhere would go undetected.
C=Manual INACTIVE state: the state follows the scanner's assessment, so findings for resources that are still public become active again, and manual changes do not scale.
D=Deleting findings: removing findings does not alter what the detector scans, so new findings reappear and the approval is not recorded anywhere.
T: To handle accepted risk, scope a dynamic mute rule with an expiry instead of disabling detectors or editing finding states.

@ GCP-PSE D4 T4.2 applied troubleshooting
S: A team has an old static mute rule hiding all open-firewall findings in project `lab-1`. Last month it added a dynamic mute rule for the same findings with a 30-day expiry. The 30 days have passed, but the findings are still muted. What is the explanation and the right fix?
A: The static rule takes precedence over the dynamic rule and keeps muting; remove the static rule and use dynamic mute rules only
B: Dynamic mute rules never expire for findings that were already muted once, so an analyst must unmute each finding by hand
C: The dynamic rule expired but Security Command Center caches the mute state for a year, so only re-enabling the detector clears it
D: Mute rules at project level cannot expire; the rule must be recreated at organization level for the expiry to take effect
K: A
G: ## Static and dynamic mute rules together
Static mute rules mute future findings indefinitely and, when created through the console, also mute existing ones. Dynamic mute rules apply to existing and new findings and can expire.
- When both apply to a finding, the **static rule has priority**, so the dynamic rule's expiry has no visible effect.
- Security Command Center recommends dynamic mute rules only, and documents a migration path from static to dynamic.
- Muted findings keep being generated; muting changes the `mute` property, not the scanning.
## Fix
Delete or migrate the static rule so the dynamic rule becomes the only authority; after the dynamic rule expires, findings that still match become visible.
W: Static precedence: the indefinite static rule continues to set the finding to muted, masking the dynamic rule's expiry; removing it leaves one rule that behaves as written.
X: B=Manual unmute only: dynamic rules do expire and unmute findings automatically when no other rule applies; hand work is the fallback for individual findings, not the mechanism.
C=One-year cache: no such cache exists; mute state follows rules and findings, and re-enabling a detector changes nothing about mute rules.
D=Project-level limitation: dynamic rules can be created at project, folder or organization scope with expiration; the scope is not what blocks expiry here.
T: A static mute rule overrides a dynamic one; use dynamic rules exclusively so expirations work.

B: Delete the service account and its project immediately so that no further access is possible, then restore everything from backup
