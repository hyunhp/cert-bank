@ GCP-PSE D1 T1.3 applied troubleshooting
S: After a company enables SAML single sign-on between Cloud Identity and its corporate IdP, a newly hired engineer authenticates successfully at the IdP but Google sign-in rejects the assertion. The IdP sends the engineer's employee number as the NameID, and a Cloud Identity user with the engineer's email address exists. What is the most likely cause and fix?
A: The NameID must match the user's primary email address in Cloud Identity, so the IdP must be configured to send that value
B: The engineer's Cloud Identity user must first be given a password, which Google compares with the one entered at the IdP
C: The IdP signing certificate has to be uploaded to the engineer's user profile instead of to the single sign-on profile
D: The engineer must be added to a super admin group, because only super admins can be matched to assertions from an IdP
K: A
G: ## How Google maps a SAML assertion to a user
With SAML federation, Google (the service provider) delegates authentication to the external IdP. The IdP sends a signed assertion; Google trusts it based on the IdP's certificate and then has to decide which Cloud Identity or Google Workspace user it describes.
- The mapping is done on the `NameID` claim of the assertion.
- The `NameID` value must equal the **primary email address** of an existing Cloud Identity user. The IdP is free to derive it with whatever logic it likes.
- Passwords are not part of the exchange: the IdP verifies credentials, Google never sees them.
## Why a mismatch fails
A NameID such as an employee number matches no user, so Google rejects the assertion even though the person authenticated correctly at the IdP. The fix is on the IdP side (map the NameID to the email), not in Google user records.
W: Primary email as NameID: Google matches the assertion's NameID to a user's primary email address; sending an employee number leaves nothing to match, so the IdP attribute mapping must be changed.
X: B=Password in Cloud Identity: with SSO the IdP verifies the credential and Google does not compare any password with the IdP's, so giving the user one fixes nothing.
C=Certificate in the user profile: the IdP's verification certificate belongs to the SSO configuration for the whole account and is not attached per user; the assertion is rejected at the identity-matching step, not the signature step.
D=Super admin group: super admins are actually exempt from the forced SSO redirect; being one is not required for assertions to be matched, and making a new hire a super admin would be a serious privilege error.
T: In SAML federation the IdP's NameID must equal the user's primary email address in Cloud Identity.

@ GCP-PSE D1 T1.3 applied comparison
S: A web application lets employees sign in with their Google identity. Its backend must learn which user is interacting with it, and it never calls a Google API on the user's behalf. Which token should the backend verify, and why?
A: The user ID token, a signed JWT issued to that client, which identifies the user but cannot call Google APIs
B: The user access token, because each access token carries a readable copy of the signed-in user's full profile
C: The refresh token, because it is the only token type that is tied to the identity of the user who authorized the client
D: A service account ID token, because identity tokens are always issued for workloads and never for human users
K: A
G: ## Three token families, three jobs
Google Cloud groups tokens by purpose:
- **Access tokens** let a client call Google Cloud APIs. They are short-lived and limited to OAuth scopes.
- **Token-granting tokens** (refresh tokens, authorization codes) let a client obtain other tokens later.
- **Identity (ID) tokens** let a client identify the user it is interacting with.
## What an ID token is
A user ID token is a JSON Web Token obtained through an OpenID Connect flow and signed with Google's keys.
- It is signed but not encrypted, so the client can decode and verify it.
- It is issued to one particular client and expires after at most one hour.
- It cannot be used to call Google APIs and cannot be used to obtain access tokens.
ID tokens exist for users, service accounts and agent identities, so the type must match the principal being identified.
W: User ID token: it is the token designed to tell a client who the user is, it can be verified from its signature, and it carries no power to call Google APIs.
X: B=Access token: access tokens authorize API calls and are limited to scopes; identifying the user is the purpose of identity tokens, not of access tokens.
C=Refresh token: it is a token-granting token that lets a client obtain further tokens; it is not meant to be read by the client to identify the user.
D=Service account ID token: that type identifies a service account; a human user is identified by a user ID token from the OIDC flow.
T: Use the user ID token (OIDC) to identify a user; access tokens call APIs and refresh tokens obtain new tokens.

@ GCP-PSE D1 T1.3 advanced comparison
S: A security team reviews what a stolen laptop exposes in an internal tool that uses OAuth. Employees who sign in as Cloud Identity users hold refresh tokens, and contractors who come through a workforce identity pool hold federated refresh tokens. Which statement about cutting off these tokens is accurate?
A: A refresh token can be revoked, but a federated refresh token cannot and stays valid until its workforce identity session expires
B: Both kinds are revoked in the same way, so one offboarding procedure for tokens covers employees and contractors
C: A federated refresh token can be used once, like an authorization code, so a stolen copy is worthless after one exchange
D: A refresh token expires within an hour, like an ID token, so a stolen laptop exposes the employee only briefly
K: A
G: ## Token-granting tokens
Refresh tokens and authorization codes let a client obtain access and ID tokens without asking the user again.
- A **refresh token** is tied to a specific client and works only with that client's credentials. It can be used many times and can be revoked. If the authorization includes Google Cloud OAuth scopes, its lifetime is subject to the Google Cloud session length control; otherwise it stays valid until the user revokes the authorization or another revoking event occurs.
- A **federated refresh token** is the equivalent for workforce identity pool principals. It can be used many times but **cannot be revoked**; its lifetime is linked to the workforce identity session that produced it and ends when that session expires.
- An **authorization code** is single-use, valid for 10 minutes and not revocable.
## What this means for offboarding
Plan differently for the two populations: revoke the refresh token for Cloud Identity users, and for workforce pool users rely on the workforce session ending (and on keeping that session short).
W: Revocable versus session-bound: a refresh token can be revoked, while a federated refresh token cannot and remains usable until the workforce identity session it came from expires.
X: B=Same procedure: federated refresh tokens are not revocable, so contractors need a different control than employees.
C=Single-use federated token: authorization codes are single-use; federated refresh tokens can be used many times.
D=Expires within an hour: one hour is the maximum lifetime of ID tokens; a refresh token can stay valid until it is revoked or its session control ends it.
T: Refresh tokens are revocable; federated refresh tokens are not and last as long as the workforce session.

@ GCP-PSE D1 T1.3 applied comparison
S: An enterprise syncs users from Active Directory into Cloud Identity and enables SAML SSO with AD FS. The security architect must decide where password complexity rules and MFA are managed for employees signing in to the Google Cloud console. Where does that responsibility sit?
A: With the on-premises identity system, because passwords are not synchronized and sign-in is delegated to it through SAML
B: With Cloud Identity, because synchronization copies password hashes to Google so that Google can validate them
C: With IAM, because allow policies define password length and MFA requirements per principal
D: With the Google Cloud console, because it applies its own MFA prompt to every federated sign-in regardless of the IdP
K: A
G: ## Provisioning versus authentication
In a federated setup two things happen separately:
- **Provisioning**: users and groups are synchronized periodically from Active Directory to Cloud Identity (one way). Synchronization does **not** include passwords.
- **Single sign-on**: when a user must authenticate, Google redirects to the IdP over SAML. The IdP verifies credentials and applies its own policies and MFA.
## Practical result
The identity system of record remains the only place that manages those credentials. Password rules, lockout, and the MFA method for employees are set there. Google-side password and 2-Step Verification settings still matter for accounts exempt from SSO, such as super admins.
W: On-premises identity system: AD remains the only system managing credentials; sign-in is delegated by SAML, so complexity rules and MFA are enforced where the credential is verified.
X: B=Hashes copied to Google: provisioning does not carry passwords, so Google never holds or validates the federated user's password.
C=IAM allow policies: IAM decides what an authenticated principal may do; it does not define how a person authenticates or what their password looks like.
D=Console MFA for every federated sign-in: Google delegates authentication to the IdP and does not add a console-wide prompt of its own for federated users.
T: With federation the IdP owns passwords and MFA; synchronization carries identities, not credentials.

@ GCP-PSE D1 T1.3 applied tradeoff
S: A holding company has two subsidiaries. The first needs mandatory SAML SSO through its own IdP; the second has no IdP and wants Google-managed passwords with 2-Step Verification. The architect prefers a single Cloud Identity account. What constraint must be weighed?
A: SSO is an account-wide setting for all users except super admins, so mixed models need scoping or separate accounts
B: SSO applies only to users holding an organization-level IAM role, so the second subsidiary is automatically excluded
C: SSO applies to Google Cloud console sign-in but not to the Admin console, so both subsidiaries can share one authentication model
D: SSO is applied per project, so each subsidiary can set its own policy simply by having its own project
K: A
G: ## One account or several
Google recommends as few Cloud Identity or Google Workspace accounts as possible, because settings such as password policies, SSO and 2-Step Verification are then applied consistently. The cost is flexibility: some settings are global.
- Enabling SSO is a **global setting** for the account; it applies to everyone other than super admins.
- Where two populations need incompatible authentication models, an architect either scopes the SSO configuration to the population that needs it, or uses separate accounts, accepting more administrative overhead.
## Decision rule
Use the smallest number of accounts that satisfies the requirements, and name the requirement (here, incompatible authentication models) that justifies each extra account.
W: Account-wide SSO: because SSO covers all non-super-admin users of an account, the mixed requirement must be solved by scoping or by splitting accounts, with the overhead that implies.
X: B=Tied to an IAM role: SSO is a Cloud Identity authentication setting and does not depend on IAM role holdings, so no automatic exclusion occurs.
C=Not for Admin console: SSO governs Google sign-in for the account as a whole, so the Admin console and Google Cloud console share the same model for non-super-admin users.
D=Per project: authentication is configured in Cloud Identity, which sits above projects in the organization, so project placement has no effect on SSO.
T: SSO is an account-level setting, so mixed authentication models force scoping or additional accounts.

@ GCP-PSE D1 T1.3 advanced use-case
S: A developer runs a script with a user access token. A colleague argues that because the user holds the Storage Admin role on a project, the token will always be able to list every bucket in it. A security engineer explains that this need not be true. Why?
A: A user access token is restricted to the OAuth scopes it was issued with, and IAM still decides which permissions apply
B: User access tokens never expire, so the role used at issue time is checked once and then cached indefinitely
C: OAuth scopes replace IAM roles, so a token without the storage scope removes the role from the user's allow policy
D: Access tokens are issued to the project rather than to a client, so they carry whichever role the project default has
K: A
G: ## Two layers: scopes and IAM
When a user authenticates through OAuth 2.0, the Google authorization server issues an **access token** with these properties:
- it authenticates one principal and is issued to one particular client;
- it is short-lived and expires after at most a few hours;
- it is restricted to certain OAuth scopes, endpoints or resources, so it typically does not grant access to everything the user could do.
## How this interacts with IAM
Scopes limit what the *client* may do on the user's behalf; IAM allow policies limit what the *user* may do. An API call succeeds only if both agree. A token issued with a narrow scope can therefore fail even when the user holds a powerful role.
W: Scope limits plus IAM: the token carries only the scopes granted to that client, so a narrow-scope token can be denied for a call the user's role would otherwise allow.
X: B=Never expire: access tokens are short-lived (a few hours at most), and IAM evaluates the allow policy on each request rather than once at issue time.
C=Scopes replace roles: scopes narrow what a client can call; they do not alter the user's allow policy bindings, and IAM remains the authorization decision.
D=Issued to the project: tokens authenticate a user or workload and are issued to one particular client, not to a project that supplies a default role.
T: An OAuth access token is short-lived and scope-limited; a request needs both a suitable scope and an IAM permission.

@ GCP-PSE D1 T1.3 applied definition
S: A security team wants to reduce the damage from a leaked access token that was captured from a developer laptop. Which property of Google Cloud tokens most directly limits the damage window?
A: Access tokens are short-lived and expire within hours, so a stolen one soon stops working
B: Access tokens are signed with the developer's SSH key, so they cannot be replayed elsewhere
C: Access tokens are stored in Cloud KMS and are automatically destroyed 90 days after issue
D: Access tokens are single-use and are rejected by the second API call that presents them
K: A
G: ## Bearer tokens and exposure
Most access tokens are **bearer tokens**: whoever holds one can use it until it expires. Therefore the main defenses are small lifetime, narrow scope and, where available, binding the token to a client.
- Google Cloud access tokens are short-lived, usually expiring within a few hours.
- They are restricted to certain scopes or resources.
- **Bound tokens** require the client to prove it is the rightful owner, which is more restrictive than a bearer token and reduces the risk of token theft.
## Contrast with long-lived secrets
A service account key has no expiry by default. Preferring short-lived tokens shrinks the attack window without extra revocation work.
W: Short lifetime: expiry within hours caps how long a captured token is useful, which is the property that bounds the damage window.
X: B=Signed with an SSH key: tokens are issued by Google's authorization server, not signed with a developer's SSH key, and bearer tokens can be replayed by any holder.
C=Stored in Cloud KMS for 90 days: KMS stores encryption keys, not access tokens, and tokens expire far sooner than 90 days.
D=Single-use: tokens are reusable until they expire; being usable more than once is exactly why theft is a concern.
T: Short-lived, scope-restricted access tokens (and bound tokens) limit what a stolen credential can do.

@ GCP-PSE D1 T1.3 applied tradeoff
S: Only 150 of 6,000 employees will ever use Google Cloud or other Google services, and the company federates Cloud Identity with its IdP. The architect wants an extra layer of defense in case an access rule is accidentally too lax. What should be done?
A: Create Cloud Identity users only for those 150 employees, and allow only them to sign in to Google through SSO at the IdP
B: Create Cloud Identity users for all 6,000 employees and rely on IAM roles to withhold access from everyone who does not need it
C: Create Cloud Identity users for all 6,000 employees and keep the other 5,850 only in a suspended group at the IdP
D: Create no Cloud Identity users and let the first SSO sign-in of any IdP user create a matching Google account
K: A
G: ## Shrink the set of identities that can authenticate
Google's federation guidance says that when only a subset of employees needs Google services, restrict authentication to that subset. The result is an extra layer of defense that helps if an access control rule is accidentally too lax.
- **Minimize the user accounts in Cloud Identity.** If an identity has no mapped Cloud Identity user, authentication fails even when the IdP is willing to let the person sign in with single sign-on.
- **Minimize who may use SSO to Google at the IdP.** Allow only the needed users to sign in to Cloud Identity.
Both measures work together: the IdP side and the provisioning side each narrow the population.
W: Provision and allow only the 150: no mapped user means a failed sign-in, and the IdP restriction is a second barrier, so a lax IAM rule can reach only a small population.
X: B=All 6,000 provisioned: every account is then a possible target of an over-broad role binding, and IAM roles become the only barrier.
C=Suspended group at the IdP: the accounts still exist in Cloud Identity and SSO can still map to them; a group at the IdP does not stop provisioning or authentication.
D=Create accounts at first sign-in: Google matches an assertion to an existing user and does not create users from an assertion.
T: Provision and allow SSO only for people who need Google services, so unmapped identities fail to authenticate.

@ GCP-PSE D1 T1.4 advanced use-case
S: A platform team grants broad roles to developers but must stop anyone, other than members of a project-admins group, from deleting projects tagged env=prod, without editing every role grant. Which control fits best?
A: A deny policy on the project-delete permission with a tag-based denial condition and the group as exception principal
B: An allow policy condition on each developer's role binding that checks the project tag
C: A custom role for developers that omits the project-delete permission, swapped into every existing role binding in every project
D: An organization policy constraint that lists the group as the only principal able to delete projects
K: A
G: ## Deny policies as guardrails
An IAM **deny policy** defines rules that stop principals from using certain permissions *regardless of the roles they hold*. It is attached to an organization, folder or project and inherited by everything below.
A deny rule has:
- denied principals and optional **exception principals**;
- denied permissions and optional exception permissions;
- an optional **denial condition**, which uses resource tag functions.
## Tag-based blocking
With a rule such as "deny `cloudresourcemanager.googleapis.com/projects.delete` to everyone except the `project-admins` group when the resource is tagged `env=prod`", principals can keep roles that contain the permission, and the guardrail applies only to tagged resources. No condition has to be added to every role grant.
W: Deny policy with tag condition and exception: one rule at the organization covers all grants, targets prod-tagged projects, and exempts the admin group.
X: B=Condition on each binding: this works in principle but must be repeated on every role binding of every developer and is easy to miss; a deny rule is a single central control.
C=Custom role without delete: this would remove deletion even for the cases that are allowed and would require changing every existing binding, which does not fit a tag-scoped exception.
D=Organization policy constraint: organization policy restricts resource configuration; it does not decide which principals hold a permission, so it cannot express this requirement.
T: Use a deny policy with a tag condition and exception principals to apply one central guardrail over many role grants.

@ GCP-PSE D1 T1.4 advanced use-case
S: To limit damage from phished credentials and data exfiltration, a company wants its employees and service accounts to be unable to use their roles on resources that belong to other organizations, even where those organizations' allow policies grant them access. Which control fits?
A: A Principal Access Boundary policy listing the company's organization as eligible resources, bound to its principals
B: A deny policy on the company's organization that names every external organization's projects as denied resources
C: An allow policy condition on every role binding that checks the parent organization of the requested resource
D: An organization policy constraint that lists the external organizations whose resources company users may not call
K: A
G: ## Policy types, by where they attach
- **Allow policies** and **deny policies** attach to resources (organization, folder, project) and describe who can or cannot use permissions on that resource and its descendants.
- **Principal Access Boundary (PAB) policies** attach to **principal sets** and define the resources those principals are *eligible* to access. If a principal is ineligible for a resource, access is blocked regardless of roles granted.
## Why PAB fits
By default principals are eligible to access any Google Cloud resource. A PAB policy that lists only your organization turns this around: once principals are subject to it, they can use permissions only on listed resources. The docs name this use case: preventing principals from accessing resources that you don't own. PAB can only block access; it never grants it.
W: PAB policy: attached to the company's principals, it limits eligible resources to the company's own organization, so roles granted by other organizations cannot be used.
X: B=Deny policy: deny policies attach to resources you administer and cannot be attached to other organizations' resources, so they cannot cover access to resources you do not own.
C=Conditions on allow bindings: bindings in your allow policies grant access to your resources; they do not govern what your principals do in someone else's organization.
D=Organization policy constraint: constraints configure how resources in your hierarchy behave; they do not restrict which external resources your principals may call.
T: Use a Principal Access Boundary policy on a principal set to keep principals within the resources they are eligible to access.
