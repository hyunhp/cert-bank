@ GCP-PSE D1 T1.4 expert troubleshooting
S: Project media-prod holds both prod-* and dev-* Cloud Storage buckets. To stop anyone except the storage-admins group from deleting production buckets, a platform team attached a deny policy to the project: denied principal principalSet://goog/public:all, exception principal the storage-admins group, denied permission storage.googleapis.com/buckets.delete, and the denial condition resource.name.startsWith("projects/_/buckets/prod-"). Since then, developers with Storage Admin cannot delete any bucket, including dev-* test buckets, while storage-admins members can still delete everything. C: Deny rules skip conditions when the denied principal is public:all, so name the developers group as the denied principal and keep the name-based condition

K: A
G: ## How deny policies evaluate conditions
- A deny rule applies when its denial condition evaluates to **true or cannot be evaluated**; it is skipped only when the condition is **false**.
- Denial conditions have the same CEL structure as IAM Conditions but **recognize only resource tag functions**, such as `resource.matchTag('ORG_ID/env', 'prod')`. Attributes such as `resource.name` are not usable there, so a name-based condition can never evaluate to false.
- Deny policies are attached to an **organization, folder or project** and inherited by everything below; they are checked before allow policies.
## Working the evidence
Developers are denied on dev-* buckets, so the rule is applying to buckets that the name expression should exclude. That matches "cannot be evaluated". Exception principals (storage-admins) are never denied, which is why they can still delete everything.
## Fix
Bind a tag such as `env=prod` to the prod-* buckets and use `resource.matchTag('ORG_ID/env', 'prod')` as the denial condition.
W: Tag-based denial condition: because a name condition cannot be evaluated in a deny rule, the rule always applies; a tag condition evaluates to false on dev-* buckets and true on tagged prod-* buckets.
X: B=Attach to each bucket: deny policies attach only to organizations, folders and projects, and the evaluation problem would remain with any name-based condition.
C=public:all skips conditions: conditions are evaluated for any denied principal set; renaming the principal does not make a name condition evaluable.
D=Add type and service clauses: those attributes are not recognized in denial conditions either, so the expression still cannot be evaluated.
T: Deny rule conditions understand only resource tags, and an unevaluable condition means the deny applies; scope deny rules with tags.

@ GCP-PSE D2 T2.1 expert troubleshooting
S: A logistics firm enforces mTLS on a global external Application Load Balancer for 20,000 telematics devices, using a ServerTLSPolicy in REJECT_INVALID mode and a trust config with the firm's root CA and intermediate. After rollout, 40 older devices fail. Their certificates chain correctly to the root, but each carries an Extended Key Usage extension that lists only serverAuth. Their firmware cannot be updated for six months. In a test with ALLOW_INVALID_OR_MISSING_CLIENT_CERT, the backend received client_cert_error set to client_cert_chain_invalid_eku for exactly those devices. Security requires full validation for every other device and no certificate checks written into the backend. What should the team do?
A: Switch to ALLOW_VALIDATION_RELAXATIONS with ALLOW_MISSING_EKU, so the load balancer ignores the wrong EKU purpose on the 40 device certificates
B: Keep REJECT_INVALID and add the 40 device certificates to the allowlistedCertificates field of the trust config until the firmware is replaced
C: Switch to ALLOW_INVALID_OR_MISSING_CLIENT_CERT and have the backend drop requests whenever the client_cert_error header names an EKU error
D: Keep REJECT_INVALID and add the device-issuing intermediate certificate as a second trust anchor, so chains for the 40 devices validate again
K: B
G: ## Client validation modes for load balancer mTLS
- `REJECT_INVALID`: no certificate or a failed validation terminates the connection.
- `ALLOW_VALIDATION_RELAXATIONS`: still validates, but relaxes listed checks. **`ALLOW_MISSING_EKU`** only accepts a certificate that has **no EKU extension at all**; if EKU is present it must include `clientAuth`, otherwise the connection is rejected.
- `ALLOW_INVALID_OR_MISSING_CLIENT_CERT`: forwards every request and passes the result in custom headers such as `client_cert_error`, leaving decisions to the backend.
## Allowlisted certificates
A trust config can hold **`allowlistedCertificates`**. An allowlisted certificate is **always considered valid** as long as it is parseable, proof of private key possession succeeds, and SAN constraints are met. This is meant for self-signed, expired or otherwise invalid certificates.
## Working the evidence
`client_cert_chain_invalid_eku` with an EKU that lists only `serverAuth` means the extension is present with the wrong purpose, which `ALLOW_MISSING_EKU` does not relax.
W: Allowlist the 40 certificates: they are treated as valid while every other device keeps full REJECT_INVALID validation, with no logic in the backend.
X: A=ALLOW_MISSING_EKU: it only tolerates certificates without any EKU extension; these certificates have an EKU that lacks clientAuth, so they would still be rejected.
C=Forward and check in the backend: it moves validation into application code, which security forbids, and accepts invalid certificates from everyone at the load balancer.
D=Intermediate as a trust anchor: the chain already validates; the failure is the EKU purpose, which a different anchor does not change.
T: ALLOW_MISSING_EKU covers only absent EKU; for a few certificates with a wrong EKU purpose, allowlist them in the trust config and keep REJECT_INVALID.
V: Cloud Load Balancing, Certificate Manager
