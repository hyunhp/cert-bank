@ GCP-PSE D1 T1.1 advanced use-case
S: A company federates 3,000 engineers into Google Cloud through a workforce identity pool backed by its SAML IdP; no user accounts exist in Cloud Identity. Access to the billing-analytics projects must follow two IdP facts automatically: membership in the IdP group finops-readers, and the HR attribute costcenter = 4711. A colleague proposes mapping google.display_name and google.email and writing IAM conditions on them. Which TWO configurations should the security engineer use instead? (Select TWO)
A: Map the IdP groups into google.groups and grant the role to the pool's principal set for the group finops-readers
B: Map google.email from the assertion and grant the role to that attribute in an IAM allow policy for each engineer who needs it
C: Map the cost center into a custom attribute.costcenter and grant the role to the principal set for attribute.costcenter value 4711
D: Map google.display_name to the cost center value and write an attribute condition on the provider that admits only display names of 4711
E: Map google.profile_photo to a group marker URL and grant roles to principals whose profile photo attribute matches that marker value
K: A,C
G: ## Which workforce attributes can drive authorization
- `google.subject` (required) identifies the user; `google.groups` carries the user's groups. Both **can be used for IAM authorization**: a group becomes `principalSet://iam.googleapis.com/locations/global/workforcePools/POOL/group/GROUP`.
- **Custom attributes** `attribute.KEY` can also be used in allow policies, for example `principalSet://iam.googleapis.com/locations/global/workforcePools/POOL/attribute.costcenter/4711`.
- `google.display_name`, `google.profile_photo`, `google.posix_username` and `google.email` **cannot be used in IAM allow policies or in the attribute condition**; they serve the console display, SSH user names or OAuth client integrations.
## Operational note
Anyone who can change membership of a mapped group in the IdP effectively grants Google Cloud access, so restrict who can edit those groups.
W: A=Groups as principal sets: google.groups is designed for authorization, so the finops-readers principal set follows IdP membership automatically.
C=Custom cost center attribute: a custom attribute mapped from the assertion can be granted as a principal set, so everyone with costcenter 4711 gets access.
X: B=google.email in allow policies: that attribute exists for OAuth client integrations and cannot be used in IAM allow policies; per-person grants would also not follow the HR attribute.
D=Display name in the attribute condition: google.display_name cannot be used in IAM allow policies or attribute conditions.
E=Profile photo marker: google.profile_photo is only a console picture and cannot be used for authorization.
T: Authorize workforce users with google.groups and custom attribute.KEY principal sets; display name, email, photo and POSIX attributes cannot be used in allow policies.
V: Workforce Identity Federation, IAM

@ GCP-PSE D1 T1.1 advanced use-case
S: A helpdesk of eight people resets passwords and edits memberships of the groups used in IAM bindings. Today they share one super admin account, and an audit flags that this account could also change SSO settings and grant Organization Administrator. The CISO wants least privilege, individual accountability, and the super admin kept only for emergencies. What should the security engineer recommend?
A: Keep the shared super admin but enforce a security key on it and log every sign-in, so actions stay traceable to the helpdesk team as a group
B: Give each helpdesk member a named account with a narrow Cloud Identity admin role for users and groups, and keep separate super admins for emergencies
C: Grant each helpdesk member the Organization Administrator IAM role on the organization, which covers password resets and all group membership changes in the directory
D: Make each helpdesk member a super admin with their own account, so actions are attributable, and require two-step verification for all of them
K: B
G: ## Super admin versus IAM roles versus admin roles
- The **super admin** of Cloud Identity or Google Workspace can do everything in the directory, including changing SSO and recovering any account, and can grant itself any IAM role on the organization.
- Google's best practices: do not use super admin for daily work, give super admins **separate accounts** (for example `alice-admin@example.com`), enforce MFA with security keys, and use the **less permissive Cloud Identity administrative roles** for managing users and groups.
- The **Organization Administrator** IAM role manages Google Cloud resources and policies; it does not manage directory users or passwords.
## Least privilege in practice
A custom or prebuilt admin role limited to user and group management, assigned to named accounts, gives each helpdesk action an individual audit trail and removes SSO and recovery powers from daily work.
W: Named accounts with a narrow admin role: each person gets only user and group management, actions are attributable per person, and the super admin is kept as a separate break-glass identity.
X: A=Shared super admin with a key: a security key protects the sign-in, but a shared account gives no individual accountability and keeps full directory power in daily use.
C=Organization Administrator role: it is an IAM role for Google Cloud resources and policies; it does not reset Cloud Identity passwords and is far broader than needed for the Cloud side.
D=Super admin per person: attribution improves, but eight people would now hold unrestricted directory power, the opposite of least privilege.
T: Use narrow Cloud Identity admin roles on named accounts for daily directory work and keep super admin accounts separate and reserved for emergencies.
V: Cloud Identity

What should the engineer do?
A: Keep the project-level grant and require engineers to request deploy-admin through a Privileged Access Manager entitlement with approval
B: Move deploy-admin to a new project, because Token Creator granted on a project never applies to accounts that were created after the grant
C: Remove the project-level grant and grant the group Service Account Token Creator on the etl-runner service account as a resource

D=Service Account User on the project: it also applies to every account in the project and lets the group attach deploy-admin to resources, which is another escalation path.

@ GCP-PSE D1 T1.2 advanced use-case
S: A vendor's data-migration tool runs on Compute Engine, reads one OAuth access token from a file at startup, and cannot refresh it. Migrations run up to six hours. Service account keys are banned by policy, and the tool must use the attached service account mig-sa with no added standing privilege. The documented default maximum lifetime of a service account access token is one hour. What should the security engineer do?
A: Create a key for mig-sa as a one-off exception and delete it after the run, because only key-based tokens can be issued with lifetimes beyond one hour
B: Add mig-sa to the organization policy that allows credential lifetime extension, then request a six-hour token from the IAM Credentials API
C: Set the token lifetime of mig-sa to six hours in the instance metadata, because the metadata server issues tokens with whatever lifetime the VM requests
D: Use Workload Identity Federation for the VM, because federated tokens exchanged through Security Token Service are valid for twelve hours by default
K: B
G: ## Short-lived credentials and their lifetime
- Service account access tokens created with `generateAccessToken` last **up to 1 hour (3,600 s) by default**.
- To allow up to **12 hours (43,200 s)**, add the service account to an organization policy that uses the list constraint `constraints/iam.allowServiceAccountCredentialLifetimeExtension`, then request a longer `lifetime`.
- The policy lists exactly which service accounts may receive long tokens, so the exception is narrow and auditable.
## Why not keys
A key is a long-lived secret that can be copied; Google recommends short-lived credentials instead. Here the problem is only the token lifetime, and the constraint addresses exactly that.
W: Lifetime extension constraint: listing mig-sa in the constraint allows a single six-hour token from the IAM Credentials API, with no key and no new role for the account.
X: A=Temporary key: it breaks the key ban, and a key is not needed to get a longer token once the lifetime extension policy is in place.
C=Lifetime in metadata: the metadata server does not accept a requested lifetime from the VM; the extension is controlled by the organization policy, not instance metadata.
D=Workload Identity Federation: it is meant for workloads outside Google Cloud; a VM already has an attached service account, and federation does not lift the one-hour limit.
T: For a non-refreshing client that needs a token longer than one hour, list the service account in iam.allowServiceAccountCredentialLifetimeExtension instead of creating a key.
V: IAM, Service accounts, Organization Policy

@ GCP-PSE D1 T1.2 advanced troubleshooting
S: The organization enforces the managed constraint that blocks service account key creation. A quarterly scan still finds a new user-managed key on a production service account. Logs show an engineer generated a key pair on a laptop and attached only the public key to the account. The security team wants to close this path organization-wide without breaking workloads that use attached service accounts. What should it do?
A: Grant the engineer's group a deny rule for all IAM permissions on service accounts, because uploading a key needs the same permission as creating one
B: Move every production service account into a single project protected by VPC Service Controls, which blocks external public keys from being attached
C: Shorten the key expiry constraint to one hour, so that uploaded public keys become invalid before they can be used to sign any request
D: Also enforce the managed constraint that disables service account key upload, since blocking creation does not stop attaching public keys

G: ## Two separate key paths
- **Key creation**: Google generates a key pair and returns the private key. Blocked by `constraints/iam.managed.disableServiceAccountKeyCreation` (legacy `iam.disableServiceAccountKeyCreation`).
- **Key upload**: you generate the pair yourself and attach only the public key to the account; the private key never leaves your machine. Blocked by a different constraint, `constraints/iam.managed.disableServiceAccountKeyUpload` (legacy `iam.disableServiceAccountKeyUpload`).
- Both legacy constraints are part of the Google Cloud security baseline for new organizations; enforcing both closes every user-managed key path.
## Effect on workloads
Workloads that use attached service accounts, impersonation or Workload Identity Federation need no keys, so both constraints can be enforced without breaking them.
W: Key upload constraint: uploading an external public key is governed separately from key creation, so the upload constraint must also be enforced to stop new user-managed keys.
X: A=Deny all service account permissions: it would break the engineers' legitimate use of service accounts and is far broader than closing one key path.
B=VPC Service Controls: perimeters restrict API data access by network and identity context; they do not stop the IAM API from attaching a public key to an account.
C=One-hour key expiry: an expiry setting limits key lifetime but still allows uploads, so a fresh key can be attached whenever it is needed.
T: Enforce both the key creation and the key upload constraints; blocking creation alone still allows externally generated keys.
V: IAM, Organization Policy

S: Employees and contractors both sign in through workforce identity pools. Policy requires that contractor console (federated) and gcloud sessions expire after 30 minutes, while employees keep 8-hour sessions to avoid repeated sign-ins. Both groups use the same Okta tenant, and the security team wants the setting enforced by Google Cloud rather than by Okta, so that an Okta change cannot weaken it. What configuration meets this requirement?
A: Put contractors in their own workforce identity pool with a 30-minute session duration, and keep employees in a pool set to 8 hours
B: Keep one pool and add a second provider for contractors whose provider-level session duration is set to 30 minutes in the provider config
C: Set the Google session length to 30 minutes in the Cloud Identity Admin console for a contractors organizational unit, and 8 hours for employees

D=Expiring IAM bindings: a time condition removes access at a fixed time; it does not end a sign-in session and requires constant rebinding by automation.

Where should the custom role be created and granted?
A: Create the custom role at the folder level on apps, then grant it on that folder so all 60 projects inherit the binding
B: Create the custom role in one project, then grant it on the apps folder so the role definition is reused by every project below
C: Create the custom role at the organization level, then grant it on the apps folder so every project in the folder inherits it

Which approach fits?

@ GCP-PSE D1 T1.4 advanced use-case
S: A shared project holds about 300 Secret Manager secrets for many teams, and new secrets appear daily. Team A must read only secrets whose names begin with team-a-, including secrets created later, without anyone editing IAM for each new secret. The security team prefers not to split the project or add tooling to maintain. Which configuration meets this with the LEAST ongoing administration?
A: Grant Team A the Secret Manager Secret Accessor role on the project with an IAM condition that matches only resource names with the team-a- prefix

@ GCP-PSE D1 T1.5 advanced use-case
S: The folder analytics grants the group data-eng the Storage Admin role, inherited by 25 projects. One new project under analytics, hr-exports, holds payroll files, and data-eng must not delete or change anything in its buckets. Other teams still need the folder structure unchanged, and the group must keep Storage Admin in the other 24 projects. What should the security engineer do?
A: Remove the Storage Admin binding for data-eng in the IAM policy of the hr-exports project, which overrides the binding inherited from the analytics folder
B: Attach an IAM deny policy to hr-exports that denies data-eng the Cloud Storage delete and update permissions, which overrides the inherited allow
C: Add an organization policy on hr-exports that enforces uniform bucket-level access, which stops roles inherited from folders from applying to its buckets
D: Grant data-eng the Storage Object Viewer role on hr-exports, because the narrower role replaces the inherited Storage Admin role inside that project
K: B

- Allow policies are **inherited down** the hierarchy and are **additive**: a child cannot remove or narrow a role granted on a parent. The effective policy is the union of all levels.
- To take a permission away below the point where it was granted, use an **IAM deny policy**. Deny policies attach to an organization, folder or project and are **checked before** allow policies, so a denied permission cannot be used whatever roles the principal holds.
## Example
On `projects/hr-exports`: denied principal `principalSet://goog/group/data-eng@example.com`, denied permissions such as `storage.googleapis.com/objects.delete` and `storage.googleapis.com/objects.update`. The folder binding keeps working in the other 24 projects.
W: Deny policy on the project: it subtracts the listed permissions for data-eng only in hr-exports, while the inherited allow keeps working everywhere else.
X: A=Remove the binding in the project: the binding lives on the folder; the project policy has nothing to remove, and inherited roles cannot be cancelled by a child.
C=Uniform bucket-level access: it disables object ACLs so that only IAM grants access; inherited IAM roles keep applying, including Storage Admin.
D=Narrower role in the project: allow policies are additive, so the extra viewer role is simply added to the inherited Storage Admin.
T: Inherited allow bindings cannot be narrowed below; use an IAM deny policy at the child to remove specific permissions.
V: IAM, Resource Manager

@ GCP-PSE D1 T1.5 advanced troubleshooting
S: Last month the security team enforced the managed constraint that restricts enabling serial port access on VMs at the organization. A scan today still finds 14 older VMs with serial port access enabled, and a network appliance vendor insists that its new VMs need the serial console for recovery. The team wants the appliance VMs as the only scoped exception. Which TWO actions should it take? (Select TWO)
A: Update the metadata of the 14 older VMs to turn serial port access off, because enforcement does not change VMs that already had it enabled
B: Re-enforce the constraint at each project level, because constraints set at the organization only apply to projects created after the policy
C: Bind a tag to the appliance VMs and add a conditional rule on that tag value that sets the constraint to not enforced for those VMs only
D: Add a dry-run policy for the same constraint at the organization, because dry-run mode turns off serial port access on VMs that already have it
E: Add the appliance vendor's support group to an IAM deny exception list, so the constraint no longer applies whenever those users change VM metadata
K: A,C
G: ## Managed constraints and existing VMs
- `constraints/compute.managed.disableSerialPortAccess` prevents the `serial-port-enable` metadata key from being set to true at the project, project-zonal or instance level where it is enforced.
- The documentation states that enforcing it **does not affect existing VMs** where the key is already true; they keep access until their metadata is updated. Existing exposure must be remediated separately.
- Managed constraints support **tags and conditional rules**: bind a tag to the VMs that need an exception, then add a rule with a condition on that tag that leaves the constraint unenforced for them.
## Why the scope matters
Conditional rules keep the exception tied to the resources, not to people, and the rest of the organization stays enforced.
W: A=Fix the existing VMs: enforcement only governs future metadata changes, so the 14 VMs that already have serial port enabled must be updated to turn it off.
C=Tag-conditioned exception: a conditional rule on a tag value exempts just the appliance VMs while the constraint stays enforced everywhere else.
X: B=Re-enforce per project: an organization policy is inherited by all existing and new projects; re-enforcing it lower changes nothing for the VMs already enabled.
D=Dry-run policy: dry-run mode only logs what the policy would block and changes no resource, so the 14 VMs keep serial port access.
E=Deny exception list: IAM deny exceptions affect IAM permissions, not organization policy evaluation, so they cannot scope an organization policy exception.
T: Managed Compute Engine constraints do not fix existing VMs and support tag-based conditional exceptions; remediate the old settings and scope exceptions with tags.
V: Organization Policy, Compute Engine

- Soft delete keeps deleted or overwritten objects recoverable for its retention duration: **7 to 90 days**, default 7, or **0 to disable**.
- `constraints/storage.softDeletePolicySeconds` defines the **allowable retention durations**. Any bucket insert, update or patch where it is enforced must have a soft delete duration that **matches** the constraint.
- When the policy is first enforced, **existing buckets keep their current soft delete policy**; they need a separate update.
## Why not retention policies or lifecycle
A retention policy prevents deletion for a period but is a different control with different side effects; lifecycle rules delete data and do not make deleted objects recoverable.
W: Soft delete retention constraint plus remediation: new and updated buckets must use 30 days, and the existing non-compliant buckets are fixed separately because enforcement is not retroactive.
X: A=Lifecycle template: lifecycle rules delete or transition objects; they do not keep deleted objects recoverable, and pipelines could skip the template.
B=Locked retention policy by job: it blocks deletion for 30 days rather than keeping deleted objects recoverable, and a nightly job leaves gaps.
D=Automatic update of existing buckets: existing buckets keep their soft delete policy when the constraint is enforced.
T: Use storage.softDeletePolicySeconds to require a soft delete duration on new or updated buckets, and remediate existing buckets separately.

@ GCP-PSE D5 T5.1 advanced use-case
S: A payments regulator requires that Google Cloud APIs used by the company's regulated workloads refuse connections negotiated with TLS 1.0 or 1.1, while TLS 1.2 and 1.3 clients keep working. The rule applies to every project in the regulated folder, and the security team wants a single preventive setting with no client inventory and no change to application code. What should it configure?
A: The Restrict TLS Versions constraint on the regulated folder, with TLS_VERSION_1 and TLS_VERSION_1_1 as denied values
B: The Restrict TLS Cipher Suites constraint on the folder, allowing only TLS 1.3 cipher suites for every Google Cloud API in the regulated projects
C: An SSL policy with the RESTRICTED profile and minimum TLS 1.2 attached to every Google Cloud API endpoint used by the regulated projects
D: A VPC Service Controls perimeter around the folder, because perimeter enforcement rejects any API request that uses TLS older than 1.2
K: A
G: ## gcp.restrictTLSVersion
- The constraint denies handshakes with **TLS 1.0 (`TLS_VERSION_1`) and TLS 1.1 (`TLS_VERSION_1_1`)** for Google Cloud resource APIs on the organization, folder or project where it is set, and on all children.
- It is a **deny list only**: trying to use an allow list is an error. To also block TLS 1.2, use the cipher suite constraint to allow only TLS 1.3 ciphers.
- It applies to APIs fronted by the Google Front End; the docs list exceptions such as App Engine, Cloud Run (`*.run.app`), Cloud Run functions (`*.cloudfunctions.net`), Apigee and Private Service Connect.
- A denied request fails with an error naming `constraints/gcp.restrictTLSVersion` and the violated TLS version.
## Contrast
SSL policies control TLS on your own load balancers, not on Google APIs.
W: Restrict TLS Versions on the folder: denying the two old versions blocks them for every in-scope Google API in all regulated projects while TLS 1.2 and 1.3 continue.
X: B=TLS 1.3 cipher allowlist: it would also reject TLS 1.2 clients, which the regulator still allows.
C=SSL policy: SSL policies attach to your load balancers' target proxies; you cannot attach them to Google Cloud API endpoints.
D=VPC Service Controls: perimeters evaluate identity, network and resources; they do not inspect the TLS version of a request.
T: Use gcp.restrictTLSVersion with TLS_VERSION_1 and TLS_VERSION_1_1 denied to keep old TLS off Google Cloud APIs; it is a deny list with documented exceptions.
