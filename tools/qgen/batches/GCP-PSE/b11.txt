@ GCP-PSE D1 T1.1 advanced use-case
S: A retailer's 2,000 store managers sign in with Microsoft Entra ID and need Google Cloud console and gcloud access to a few reporting projects. The privacy office forbids creating or synchronizing user accounts in any Google directory, and the identity team wants an Entra ID offboarding to end Google Cloud access with no second system to update. Which approach meets these requirements with the LEAST operational overhead?
A: Create a workforce identity pool with an Entra ID provider, map the IdP groups into attributes, and grant roles on the projects to the matching principal sets
B: Run Google Cloud Directory Sync to provision the managers into Cloud Identity, then configure SAML single sign-on with Entra ID as the external identity provider
C: Create a workload identity pool that trusts Entra ID as an OIDC issuer, and let the managers' tokens impersonate one shared reporting service account
D: Turn on Entra ID automatic user provisioning into Cloud Identity Free accounts, and have the provisioning job suspend each account when a manager leaves
K: A
G: ## Two ways to bring workforce identities to Google Cloud
- **Cloud Identity (or Google Workspace) accounts**: every user exists as a Google account, usually synchronized by Google Cloud Directory Sync or automatic provisioning, and signs in through SAML or OIDC single sign-on. The account lives in a Google directory and must be suspended or deleted when the person leaves.
- **Workforce Identity Federation**: a *workforce identity pool* trusts an external IdP (OIDC or SAML). Users sign in to the console (federated) and the gcloud CLI with their IdP identity; **no user is created or synchronized** in Cloud Identity. Attribute mappings turn IdP claims (for example groups) into attributes that IAM can reference as `principalSet://iam.googleapis.com/locations/global/workforcePools/POOL/group/GROUP`.
## Why it fits offboarding
Because each sign-in is checked against the IdP, disabling the user in Entra ID stops new sessions; access tokens then age out within the pool's session duration.
W: Workforce identity pool: it federates the IdP directly, keeps no user objects in a Google directory, gives console (federated) and gcloud access, and makes Entra ID the single place to revoke access.
X: B=GCDS plus SAML SSO: it works technically, but it creates a copy of every manager in Cloud Identity, which the privacy office forbids, and offboarding must reach two systems.
C=Workload identity pool: workload pools are for applications and machines, not people at a console; sharing one service account also destroys individual accountability in the audit logs.
D=Automatic provisioning to Cloud Identity Free: it still stores user accounts in a Google directory, breaking the privacy rule, and adds a provisioning job to operate.
T: When people need Google Cloud access but must not exist in a Google directory, use a workforce identity pool that federates the corporate IdP.
V: Workforce Identity Federation, Cloud Identity

@ GCP-PSE D1 T1.1 advanced use-case
S: A helpdesk of eight people resets passwords and edits memberships of the groups used in IAM bindings. Today they share one super admin account, and an audit flags that this account could also change SSO settings and grant Organization Administrator. The CISO wants least privilege, individual accountability, and the super admin kept only for emergencies. What should the security engineer recommend?
A: Keep the shared super admin but enforce a security key on it and log every sign-in, so actions stay traceable to the helpdesk team as a group
B: Give each helpdesk member their own account with a narrower Cloud Identity admin role for users and groups, and reserve separate super admin accounts for emergencies
C: Grant each helpdesk member the Organization Administrator IAM role on the organization, which covers password resets and group membership changes
D: Make each helpdesk member a super admin with their own account, so actions are attributable, and require two-step verification for all of them
K: B
G: ## Super admin versus IAM roles versus admin roles
- The **super admin** of Cloud Identity or Google Workspace can do everything in the directory, including changing SSO and recovering any account, and can grant itself any IAM role on the organization.
- Google's best practices: do not use super admin for daily work, give super admins **separate accounts** (for example `alice-admin@example.com`), enforce MFA with security keys, and use the **less permissive Cloud Identity administrative roles** for managing users and groups.
- The **Organization Administrator** IAM role manages Google Cloud resources and policies; it does not manage directory users or passwords.
## Least privilege in practice
A custom or prebuilt admin role limited to user and group management, assigned to named accounts, gives each helpdesk action an individual audit trail and removes SSO and recovery powers from daily work.
W: Named accounts with a narrow admin role: each person gets only user and group management, actions are attributable per person, and the super admin is kept as a separate break-glass identity.
X: A=Shared super admin with a key: a security key protects the sign-in, but a shared account gives no individual accountability and keeps full directory power in daily use.
C=Organization Administrator role: it is an IAM role for Google Cloud resources and policies; it does not reset Cloud Identity passwords and is far broader than needed for the Cloud side.
D=Super admin per person: attribution improves, but eight people would now hold unrestricted directory power, the opposite of least privilege.
T: Use narrow Cloud Identity admin roles on named accounts for daily directory work and keep super admin accounts separate and reserved for emergencies.
V: Cloud Identity

@ GCP-PSE D1 T1.2 advanced troubleshooting
S: Data engineers must impersonate the service account etl-runner to test pipelines, so an administrator granted their group the Service Account Token Creator role on project data-prod. A review now shows the same group can mint tokens for deploy-admin, a highly privileged service account in that project. The fix must keep the engineers' testing workflow and follow least privilege. What should the engineer do?
A: Keep the project-level grant and require engineers to request deploy-admin through a Privileged Access Manager entitlement with approval
B: Move deploy-admin to a new project, because Token Creator granted on a project never applies to accounts that were created after the grant
C: Remove the project-level grant and grant Service Account Token Creator to the group on the etl-runner service account itself, treating it as a resource
D: Replace Token Creator with the Service Account User role on the project, which allows impersonation for testing but not access token creation
K: C
G: ## A service account is both an identity and a resource
- Roles that let principals **impersonate** a service account (Service Account Token Creator, Service Account User) are granted on the service account as a resource, or on its project, folder or organization.
- A grant on the **project** applies to **every** service account in that project, existing and future, including privileged ones. That is a common privilege-escalation path.
- Google's guidance: grant impersonation roles on the **individual service account** that the principal needs.
## Example
`group:data-eng@example.com` with `roles/iam.serviceAccountTokenCreator` on `etl-runner@data-prod.iam.gserviceaccount.com` can create tokens for that account only; `deploy-admin` is no longer reachable.
W: Grant on the service account: binding the role on etl-runner limits token creation to that one identity, keeps the testing workflow, and closes the path to deploy-admin.
X: A=Privileged Access Manager on top: an entitlement adds a path for temporary access, but the standing project-level grant still lets the group mint deploy-admin tokens at any time.
B=New accounts excluded: project-level grants are inherited by all service accounts in the project, including ones created later, so moving accounts is not a reliable fix.
D=Service Account User on the project: it also applies to every account in the project and lets the group attach deploy-admin to resources, which is another escalation path.
T: Grant Token Creator and Service Account User on the specific service account, never on the project, when the project holds privileged identities.
V: IAM, Service accounts

@ GCP-PSE D1 T1.2 advanced use-case
S: A vendor's data-migration tool runs on Compute Engine, reads one OAuth access token from a file at startup, and cannot refresh it. Migrations run up to six hours. Service account keys are banned by policy, and the tool must use the attached service account mig-sa with no added standing privilege. The documented default maximum lifetime of a service account access token is one hour. What should the security engineer do?
A: Create a key for mig-sa as a one-off exception and delete it after the run, because only key-based tokens can be issued with lifetimes beyond one hour
B: Add mig-sa to the organization policy that allows credential lifetime extension, then generate a six-hour access token for it with the IAM Credentials API
C: Set the token lifetime of mig-sa to six hours in the instance metadata, because the metadata server issues tokens with whatever lifetime the VM requests
D: Use Workload Identity Federation for the VM, because federated tokens exchanged through Security Token Service are valid for twelve hours by default
K: B
G: ## Short-lived credentials and their lifetime
- Service account access tokens created with `generateAccessToken` last **up to 1 hour (3,600 s) by default**.
- To allow up to **12 hours (43,200 s)**, add the service account to an organization policy that uses the list constraint `constraints/iam.allowServiceAccountCredentialLifetimeExtension`, then request a longer `lifetime`.
- The policy lists exactly which service accounts may receive long tokens, so the exception is narrow and auditable.
## Why not keys
A key is a long-lived secret that can be copied; Google recommends short-lived credentials instead. Here the problem is only the token lifetime, and the constraint addresses exactly that.
W: Lifetime extension constraint: listing mig-sa in the constraint allows a single six-hour token from the IAM Credentials API, with no key and no new role for the account.
X: A=Temporary key: it breaks the key ban, and a key is not needed to get a longer token once the lifetime extension policy is in place.
C=Lifetime in metadata: the metadata server does not accept a requested lifetime from the VM; the extension is controlled by the organization policy, not instance metadata.
D=Workload Identity Federation: it is meant for workloads outside Google Cloud; a VM already has an attached service account, and federation does not lift the one-hour limit.
T: For a non-refreshing client that needs a token longer than one hour, list the service account in iam.allowServiceAccountCredentialLifetimeExtension instead of creating a key.
V: IAM, Service accounts, Organization Policy

@ GCP-PSE D1 T1.2 advanced troubleshooting
S: The organization enforces the managed constraint that blocks service account key creation. A quarterly scan still finds a new user-managed key on a production service account. Logs show an engineer generated a key pair on a laptop and attached only the public key to the account. The security team wants to close this path organization-wide without breaking workloads that use attached service accounts. What should it do?
A: Grant the engineer's group a deny rule for all IAM permissions on service accounts, because uploading a key needs the same permission as creating one
B: Move every production service account into a single project protected by VPC Service Controls, which blocks external public keys from being attached
C: Shorten the key expiry constraint to one hour, so that uploaded public keys become invalid before they can be used to sign any request
D: Also enforce the managed constraint that disables service account key upload, because blocking creation does not stop attaching an external public key
K: D
G: ## Two separate key paths
- **Key creation**: Google generates a key pair and returns the private key. Blocked by `constraints/iam.managed.disableServiceAccountKeyCreation` (legacy `iam.disableServiceAccountKeyCreation`).
- **Key upload**: you generate the pair yourself and attach only the public key to the account; the private key never leaves your machine. Blocked by a different constraint, `constraints/iam.managed.disableServiceAccountKeyUpload` (legacy `iam.disableServiceAccountKeyUpload`).
- Both legacy constraints are part of the Google Cloud security baseline for new organizations; enforcing both closes every user-managed key path.
## Effect on workloads
Workloads that use attached service accounts, impersonation or Workload Identity Federation need no keys, so both constraints can be enforced without breaking them.
W: Key upload constraint: uploading an external public key is governed separately from key creation, so the upload constraint must also be enforced to stop new user-managed keys.
X: A=Deny all service account permissions: it would break the engineers' legitimate use of service accounts and is far broader than closing one key path.
B=VPC Service Controls: perimeters restrict API data access by network and identity context; they do not stop the IAM API from attaching a public key to an account.
C=One-hour key expiry: an expiry setting limits key lifetime but still allows uploads, so a fresh key can be attached whenever it is needed.
T: Enforce both the key creation and the key upload constraints; blocking creation alone still allows externally generated keys.
V: IAM, Organization Policy

@ GCP-PSE D1 T1.3 advanced use-case
S: Employees and contractors both sign in through workforce identity pools. Policy requires that contractor console (federated) and gcloud sessions expire after 30 minutes, while employees keep 8-hour sessions to avoid repeated sign-ins. Both groups use the same Okta tenant, and the security team wants the setting enforced by Google Cloud rather than by Okta. What configuration meets this requirement?
A: Put contractors in their own workforce identity pool with a 30-minute session duration, and keep employees in a pool set to 8 hours
B: Keep one pool and add a second provider for contractors whose provider-level session duration is set to 30 minutes in the provider config
C: Set the Google session length to 30 minutes in the Cloud Identity Admin console for a contractors organizational unit, and 8 hours for employees
D: Grant contractor roles with an IAM condition on request.time that expires each binding 30 minutes after it is created by an automation job
K: A
G: ## Session duration belongs to the pool
- A workforce identity pool has a **session duration** that controls how long Google Cloud access tokens, **console (federated)** sign-in sessions and **gcloud** sign-in sessions from that pool remain valid.
- It defaults to **1 hour** and can be set from **15 minutes (900 s) to 12 hours (43,200 s)**.
- Because the setting is per pool, two populations that need different session lengths need **two pools** (they may trust the same IdP).
## Why not Cloud Identity session settings
Federated users from a workforce pool are not Cloud Identity users, so Admin console session controls for organizational units do not apply to them.
W: Separate pools: the session duration is configured on the pool, so a contractors pool at 30 minutes and an employees pool at 8 hours enforces both rules inside Google Cloud.
X: B=Provider-level duration: providers configure trust, attribute mapping and conditions; the session duration is a pool setting shared by all its providers.
C=Admin console session length: those controls apply to Cloud Identity or Workspace accounts, and workforce pool users are not accounts in that directory.
D=Expiring IAM bindings: a time condition removes access at a fixed time; it does not end a sign-in session and requires constant rebinding by automation.
T: Workforce pool session duration (15 minutes to 12 hours) is set per pool, so give populations with different session rules their own pools.
V: Workforce Identity Federation

@ GCP-PSE D1 T1.4 advanced use-case
S: Platform engineers in 60 projects under the folder apps need to view and restart Compute Engine instances, but nothing else. No predefined role matches, so the security team will build a custom role. It wants one role definition to maintain, granted only on the apps folder, and no one-off copies in each project. Where should the custom role be created and granted?
A: Create the custom role at the folder level on apps, then grant it on that folder so all 60 projects inherit the binding
B: Create the custom role in one project, then grant it on the apps folder so the role definition is reused by every project below
C: Create the custom role at the organization level, then grant it on the apps folder so every project in the folder inherits it
D: Create the custom role in each of the 60 projects with a script, and grant each copy on its own project from the same pipeline
K: C
G: ## Where custom roles live
- A custom role is created in an **organization** or in a **project**; there are no folder-level custom roles.
- A role can be **granted only within the organization or project where it was created**. A project-level custom role cannot be granted on a folder or on another project.
- An organization-level custom role can be granted on the organization, any folder, any project or any resource in it, and its definition is maintained once.
- Some permissions only make sense at folder or organization level and cannot be put in project-level custom roles.
## Example
Create `organizations/123/roles/vmRestarter` with `compute.instances.get`, `compute.instances.list` and `compute.instances.reset`, then grant it on `folders/apps` to the platform group.
W: Organization-level custom role: it is the only custom role scope that can be granted on a folder, and one definition serves all 60 projects through inheritance.
X: A=Folder-level custom role: custom roles cannot be created on folders; only organizations and projects can hold role definitions.
B=Project role granted on the folder: a project-level custom role can only be granted inside that project, so it cannot be bound on the apps folder.
D=Copies per project: it works but creates 60 definitions to keep in sync, which the team explicitly wants to avoid.
T: Create custom roles at the organization when they must be granted on folders or across projects; project roles stay inside their project.
V: IAM

@ GCP-PSE D1 T1.4 advanced use-case
S: After an incident, an auditor asks which principals could modify the IAM policy of project payments-prod, including people who could do so only indirectly by impersonating a service account that holds the permission. The organization has 900 projects and deep group nesting. The security engineer must produce an answer from current policies, not from past logs. Which approach fits?
A: Run Policy Troubleshooter for each employee against payments-prod, because it reports both direct and impersonation-based access for every principal
B: Export Admin Activity audit logs to BigQuery and list everyone who has called SetIamPolicy on payments-prod during the last 400 days
C: Use IAM recommender insights for payments-prod, because they list permissions each principal and service account used during the last 90 days
D: Run a Policy Analyzer query for the permission on payments-prod with service account impersonation analysis enabled, through the API or gcloud
K: D
G: ## Policy Analyzer answers "who can"
- **Policy Analyzer** evaluates allow policies across the organization, expanding groups (including nested groups) and inherited bindings, to answer questions such as "who can do X on resource Y".
- With the API or gcloud CLI it can also follow **service account impersonation**: for example "who can update project A by impersonating a service account".
- **Policy Troubleshooter** explains why one principal does or does not have one permission; it is for one principal at a time.
- **Audit logs** show what happened, not who could act. **Role recommendations** look at permission usage, not at potential access.
## Example
Query: resource `//cloudresourcemanager.googleapis.com/projects/payments-prod`, permission `resourcemanager.projects.setIamPolicy`, with the option to analyze service account impersonation.
W: Policy Analyzer with impersonation: it computes from current policies who holds the permission, expands nested groups, and adds principals who can reach it through a service account.
X: A=Policy Troubleshooter per employee: it checks a single principal and permission at a time, which does not scale to all identities and does not enumerate who can impersonate.
B=SetIamPolicy history: logs show who actually changed the policy, not everyone who could, and the auditor asked for current potential access.
C=Recommender insights: they describe permissions that were used, so principals who hold but never used the permission would be missed.
T: For "who can do this, directly or by impersonation" across an organization, use Policy Analyzer with service account impersonation analysis.
V: Policy Intelligence, Policy Analyzer

@ GCP-PSE D1 T1.4 advanced use-case
S: A shared project holds about 300 Secret Manager secrets for many teams, and new secrets appear daily. Team A must read only secrets whose names begin with team-a-, including secrets created later, without anyone editing IAM for each new secret. The security team prefers not to split the project. Which configuration meets this with the LEAST ongoing administration?
A: Grant Team A the Secret Manager Secret Accessor role on the project with an IAM condition that allows only resource names starting with the team-a- prefix
B: Attach a team=a tag to each team-a- secret when it is created, and grant Team A the Secret Accessor role on the project with a tag-based condition
C: Grant Team A the Secret Manager Viewer role on the project, which allows reading payloads only for secrets whose labels match the team's group name
D: Grant Team A the Secret Manager Secret Accessor role on each matching secret, and run a scheduled job that adds the binding to every new team-a- secret
K: A
G: ## IAM Conditions on resource names
- IAM Conditions add a CEL expression to a role binding; the binding applies only when the expression is true.
- **Secret Manager** supports the **resource name** and **resource type** attributes, so a project-level binding can be limited to secrets (and their versions) whose names start with a given prefix with `resource.name.startsWith(...)`.
- Because the condition is evaluated on each request, secrets created later with the same prefix are covered automatically.
## Contrast with tags and viewer roles
A tag-based condition also works, but each new secret must first be tagged; and the Secret Manager Viewer role reads metadata, not payloads.
W: Conditional project grant: one binding with a name-prefix condition gives access to every current and future team-a- secret and nothing else, with no per-secret work.
X: B=Tag-based condition: it scopes access correctly, but every new secret must be tagged by someone with tag permissions, which is the ongoing administration the team wants to avoid.
C=Secret Viewer by label: the Viewer role exposes secret metadata, not secret payloads, and roles are not filtered by labels.
D=Per-secret bindings by job: it meets least privilege but adds a job to operate and a gap between secret creation and the next run.
T: Use a project-level binding with an IAM condition on the resource name prefix when access must follow a naming convention for current and future secrets.
V: Secret Manager, IAM Conditions

@ GCP-PSE D1 T1.5 advanced use-case
S: The folder analytics grants the group data-eng the Storage Admin role, inherited by 25 projects. One new project under analytics, hr-exports, holds payroll files, and data-eng must not delete or change anything in its buckets. Other teams still need the folder structure unchanged, and the group must keep Storage Admin in the other 24 projects. What should the security engineer do?
A: Remove the Storage Admin binding for data-eng in the IAM policy of the hr-exports project, which overrides the binding inherited from the analytics folder
B: Attach an IAM deny policy to hr-exports that denies data-eng the Cloud Storage delete and update permissions, which overrides the inherited allow
C: Add an organization policy on hr-exports that enforces uniform bucket-level access, which stops roles inherited from folders from applying to its buckets
D: Grant data-eng the Storage Object Viewer role on hr-exports, because the narrower role replaces the inherited Storage Admin role inside that project
K: B
G: ## Allow policies only add
- Allow policies are **inherited down** the hierarchy and are **additive**: a child cannot remove or narrow a role granted on a parent. The effective policy is the union of all levels.
- To take a permission away below the point where it was granted, use an **IAM deny policy**. Deny policies attach to an organization, folder or project and are **checked before** allow policies, so a denied permission cannot be used whatever roles the principal holds.
## Example
On `projects/hr-exports`: denied principal `principalSet://goog/group/data-eng@example.com`, denied permissions such as `storage.googleapis.com/objects.delete` and `storage.googleapis.com/objects.update`. The folder binding keeps working in the other 24 projects.
W: Deny policy on the project: it subtracts the listed permissions for data-eng only in hr-exports, while the inherited allow keeps working everywhere else.
X: A=Remove the binding in the project: the binding lives on the folder; the project policy has nothing to remove, and inherited roles cannot be cancelled by a child.
C=Uniform bucket-level access: it disables object ACLs so that only IAM grants access; inherited IAM roles keep applying, including Storage Admin.
D=Narrower role in the project: allow policies are additive, so the extra viewer role is simply added to the inherited Storage Admin.
T: Inherited allow bindings cannot be narrowed below; use an IAM deny policy at the child to remove specific permissions.
V: IAM, Resource Manager
