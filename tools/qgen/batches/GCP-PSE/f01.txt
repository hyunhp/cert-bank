@ GCP-PSE D1 T1.5 applied use-case
S: A company with 300 projects will host regulated workloads (needing a tighter set of constraints) next to standard workloads. Developers must still manage their own projects. Platform engineers want organization policies and IAM grants to be applied once and automatically cover new projects. Which hierarchy design fits?
A: Folders keyed to billing accounts, with a policy set on each project because folders do not carry organization policies
B: A flat list of projects under the organization, with a pipeline that applies its own copy of each constraint and grant
C: A separate organization resource for each business unit, so that each unit's policies are set without any inheritance
D: Folder branches for the two workload types with environment subfolders, holding constraints and IAM grants that inherit
K: D
G: ## Folders as the unit of policy
Folders group projects and carry IAM allow and deny policies and organization policies. Everything set on a folder is inherited by every project and subfolder beneath it, including projects created later. This is what lets a platform team express a rule once.
## Designing the tree
- Separate branches for workloads with different control needs (for example regulated versus standard).
- Environment subfolders (non-prod, production) where constraints or access differ.
- Keep the tree shallow enough to reason about: each level adds another place where policy may be merged or overridden.
- Delegate day-to-day administration to teams at the folder or project level and keep guardrails at the top.
W: Folder branches with inherited policy: constraints and IAM set on the regulated and standard folders cover current and future projects, while teams keep project-level autonomy under those guardrails.
X: A=Folders by billing account: folders can carry organization policies, so per-project policies are unnecessary, and grouping by billing does not follow control requirements.
B=Per-project copies: each project needs its own pipeline-applied grant and constraint, which drifts, is easy to miss for new projects and removes the point of inheritance.
C=Many organizations: separate organization resources multiply identity, billing and policy administration and prevent shared central guardrails.
T: Model the hierarchy on control requirements and set guardrails once on folders so new projects inherit them.

@ GCP-PSE D1 T1.2 applied use-case
S: A project owner created a workload identity pool that trusts an AWS account the owner personally controls and gave it access to a bucket. Security wants to guarantee, for the whole organization and even for project owners, that only two company AWS accounts can ever be trusted by AWS providers. What should the security engineer enforce?
A: The service account key creation constraint at the organization, with exceptions granted to the AWS-facing projects
B: A deny rule that blocks granting Workload Identity User on service accounts anywhere in the organization
C: A provider URI constraint that lists the GitHub OIDC issuer as the allowed issuer for workload identity pools
D: The `iam.workloadIdentityPoolAwsAccounts` constraint set at the organization with the two approved accounts listed
K: D
G: ## Organization policy for federation
By default, workloads from **any** AWS account can be trusted by a provider if someone creates one. Two legacy managed constraints let central administrators set the boundary:
- `constraints/iam.workloadIdentityPoolAwsAccounts`: the list of AWS accounts that providers may trust.
- `constraints/iam.workloadIdentityPoolProviders`: the list of allowed identity provider URIs (for OIDC or SAML).
## Why this beats local checks
Project owners can configure pools in their own projects. An organization policy applies from the organization or folder down and cannot be lifted by a project owner who lacks the Organization Policy Administrator role.
W: AWS account constraint: it limits which AWS accounts any provider in scope can trust, so a personally controlled account cannot be configured, whoever owns the project.
X: A=Key creation constraint: it controls user-managed keys, not which external accounts a pool can trust.
B=Blocking Workload Identity User grants: this would break the legitimate federated deployments instead of limiting which accounts are trusted.
C=GitHub issuer in the provider URI constraint: the provider URI constraint governs OIDC and SAML issuers, so it would not narrow AWS accounts, and it would block legitimate non-GitHub issuers.
T: Use the workload identity pool organization policy constraints to restrict which AWS accounts and identity providers may be trusted.
V: IAM
