@ GCP-PSE D1 T1.4 applied use-case
S: After a data-handling incident, an auditor asks the security engineer: "Which principals, including members of nested groups, can read objects in the bucket that holds customer exports, and through which role bindings?" The bucket sits in one project of a large organization. Which Policy Intelligence tool answers this most directly?
A: Policy Analyzer for allow policies, with the bucket as the resource and the storage read permission as the access in the query
B: Policy Troubleshooter, run once for each user in the directory against the bucket and the read permission
C: IAM recommender, reviewing the role recommendations that were generated for the project that contains the bucket
D: Organization Policy dry-run mode, applied to a storage constraint on the folder that contains the project
K: A
G: ## Policy Intelligence tools answer different questions
Policy Intelligence is a suite. Each tool starts from a different side of the access question.
- **Policy Analyzer for allow policies** answers "who has what access to which resource". You build a query from principals, access (roles or permissions) and resources, and give it a scope (organization, folder or project). It reports the role bindings that match, including access obtained through group membership.
- **Policy Troubleshooter** answers "can this one principal use this permission on this resource, and why or why not". It evaluates allow policies, deny policies and Principal Access Boundary policies.
- **IAM recommender** answers "which granted roles contain permissions that were not used" using about 90 days of usage.
- **Organization Policy dry-run** tests constraints, not IAM access.
## Applying it
The auditor starts from a resource and a permission and wants the list of principals, so the query should fix the access and the resource and leave the principal open.
W: Policy Analyzer for allow policies: fixing the bucket and the read permission and leaving principals open returns every matching binding, with the principals (including group-derived access) and the policy it comes from.
X: B=Policy Troubleshooter per user: it explains one principal-permission-resource decision at a time, so looping it over a whole directory is slow and does not report the bindings that grant access.
C=IAM recommender: it suggests removing unused permissions from principals and never lists who can reach a given bucket today.
D=Organization Policy dry-run: it audit-logs would-be violations of a constraint and has nothing to say about which principals hold a role on a bucket.
T: Use Policy Analyzer for "who can access this resource" and Policy Troubleshooter for "why can or can't this principal".

@ GCP-PSE D1 T1.4 applied troubleshooting
S: A developer in a regulated project reports "permission denied" when reading a BigQuery table, although the group the developer belongs to appears in a project-level allow policy with a suitable role. The security engineer suspects another policy type is involved but cannot tell which. Which approach pinpoints the cause?
A: Run Policy Troubleshooter for that principal, the table and the permission, and read which allow, deny or Principal Access Boundary policy decides the result
B: Run Policy Analyzer for allow policies on the project, since its results also include deny policies and boundaries
C: Open the IAM recommender insights for the group, because an unused-permission insight explains why a specific request was rejected
D: Put the relevant organization policy constraint into dry-run mode, then retry the query to see which constraint rejected the table read
K: A
G: ## Why access can be denied despite an allow binding
IAM combines several policy types. An allow policy grants roles, but a deny policy can block specific permissions for specific principals, and a Principal Access Boundary policy can limit which resources a principal may use at all. A principal gets access only if an allow policy grants it and no deny or boundary blocks it.
## Which tool shows the decision
**Policy Troubleshooter** takes a principal, a resource and a permission and reports how each applicable policy affects the outcome. **Policy Analyzer for allow policies** only looks at allow policies, so it can show who is granted access but cannot explain a block caused by another policy type.
W: Policy Troubleshooter: it examines allow policies, deny policies and Principal Access Boundary policies for one principal, resource and permission, so it shows whether a deny or boundary overrides the project binding.
X: B=Policy Analyzer: it supports IAM allow policies only, so it would simply confirm the grant the developer already has and miss the deny or boundary.
C=IAM recommender insight: recommendations describe unused permissions over about 90 days and do not trace the reason for an individual rejected request.
D=Dry-run organization policy: it audits would-be violations of resource constraints and is not an IAM decision tool for a table read.
T: Use Policy Troubleshooter to explain a specific denial across allow, deny and boundary policies; Policy Analyzer is allow-policy only.

@ GCP-PSE D1 T1.4 advanced tradeoff
S: A security team applies IAM recommender suggestions to remove roles from engineers. Leadership asks how safe it is to apply them without review. A new on-call role was granted to a service team 3 weeks ago, and a quarterly disaster-recovery role is used only during the drill. What is the right way to handle the recommendations?
A: Review them before applying, since usage is measured over about 90 days, so a recently granted role has little history and a rarely used role may be flagged
B: Apply all of them at once, because the recommender only flags permissions that are proven by audit logs to be unneeded for any workload
C: Ignore any recommendation for roles granted below the project level, because the recommender only evaluates basic roles on single projects
D: Apply them only after the recommender converts every flagged role into a custom role, since it cannot suggest predefined role replacements
K: A
G: ## How the IAM recommender decides
The IAM recommender compares the permissions in a principal's roles with the permissions the principal used in roughly the last 90 days, and also uses machine learning to keep permissions the principal is likely to need. If a role was granted fewer than 90 days ago, the observation window is shorter.
## What that means operationally
- Rarely exercised duties (disaster recovery drills, quarterly close) may look unused and are flagged.
- Recently granted roles have little evidence either way.
- Recommendations should be reviewed by a person who knows the duty, and applied gradually with the ability to roll back.
W: Review before applying: the 90-day (or shorter) usage window means a three-week-old grant and a quarterly drill role are exactly the cases where an automatic removal could break a legitimate duty.
X: B=Apply everything: recommendations are based on observed usage over a window, not proof that a permission is unneeded by any workload, so rare duties can be flagged.
C=Ignore folder and organization roles: recommendations exist for projects, folders and organizations and are not limited to basic roles.
D=Convert to custom roles first: a recommendation may replace a role with a smaller predefined or custom role, and no conversion step is required before applying.
T: Treat IAM recommender output as evidence from a limited usage window; review rare-duty and new grants before applying.

@ GCP-PSE D1 T1.5 applied use-case
S: A company with 300 projects will host regulated workloads (needing a tighter set of constraints) next to standard workloads. Developers must still manage their own projects. Platform engineers want organization policies and IAM grants to be applied once and automatically cover new projects. Which hierarchy design fits?
A: Folders for regulated and standard workloads, each with environment subfolders, with constraints and IAM set on folders so that new projects inherit them
B: One flat organization where each project receives its own copy of every constraint and role grant through a deployment pipeline
C: A separate organization resource for each business unit, so that policies never need to be inherited by child resources at all
D: Folders organized only by billing account, with a policy set on each project because folders cannot carry organization policies
K: A
G: ## Folders as the unit of policy
Folders group projects and carry IAM allow and deny policies and organization policies. Everything set on a folder is inherited by every project and subfolder beneath it, including projects created later. This is what lets a platform team express a rule once.
## Designing the tree
- Separate branches for workloads with different control needs (for example regulated versus standard).
- Environment subfolders (non-prod, production) where constraints or access differ.
- Keep the tree shallow enough to reason about: each level adds another place where policy may be merged or overridden.
- Delegate day-to-day administration to teams at the folder or project level and keep guardrails at the top.
W: Folder branches with inherited policy: constraints and IAM set on the regulated and standard folders cover current and future projects, while teams keep project-level autonomy under those guardrails.
X: B=Per-project copies: every project needs its own pipeline-applied grant and constraint, which drifts, is easy to miss for new projects and removes the point of inheritance.
C=Many organizations: separate organization resources multiply identity, billing and policy administration and prevent shared central guardrails.
D=Folders by billing account: folders can carry organization policies, so per-project policies are unnecessary, and grouping by billing does not follow control requirements.
T: Model the hierarchy on control requirements and set guardrails once on folders so new projects inherit them.

@ GCP-PSE D1 T1.5 advanced use-case
S: The constraint policy for allowed external identity domains is set at the organization with a list of two approved partner domains. A folder for a new joint venture needs a third domain for its projects only, and the other two domains must remain allowed there. The policy is a list constraint. How should the policy at the folder be defined?
A: Set a folder policy that inherits from the parent and adds the third domain, so the effective allowed list is the union
B: Set a folder policy that does not inherit from the parent and lists only the third domain, because lists always merge anyway
C: Set the third domain on every project in the folder, because folder policies cannot add values to an inherited list
D: Edit the organization policy to add the third domain, because child policies can only narrow what the parent allowed
K: A
G: ## Merge versus replace for list constraints
For list constraints, a policy on a child resource either:
- **replaces** the inherited policy (inheritance from the parent is turned off), so the child alone decides; or
- **inherits from parent**, in which case the parent's effective policy is merged with the child's values.
## How merging works
When the child inherits, allowed values from parent and child combine, while denied values always win during reconciliation. So adding an allowed value in a child that inherits widens the allowed set only for that subtree.
## Applying it
The joint venture folder needs the two inherited domains plus one more, only in that folder. Inheritance with an added value does that without touching the organization policy.
W: Inherit and add: with inheritance from the parent turned on, the allowed domains from the organization merge with the folder's extra domain, producing the union for the joint venture subtree only.
X: B=Do not inherit: the folder policy would replace the parent's list, so only the third domain would be allowed there and the two approved partner domains would be lost; lists do not merge when inheritance is off.
C=Project by project: it is unnecessary because a folder policy can extend an inherited list and it would have to be repeated for every new project.
D=Change the organization: that would allow the third domain for the whole company, widening the policy where it is not needed, and child policies can add values when they inherit.
T: For list constraints, a child that inherits from its parent merges values (deny wins); a child that does not inherit replaces the parent's policy.

@ GCP-PSE D1 T1.5 applied definition
S: At the organization, a list-type constraint denies the value projects/123. A folder below it also denies projects/456, and a project in that folder sets an allowed value of projects/123 while inheriting from its parent. Which TWO statements about the effective policy at the project are correct? (Select TWO)
A: Both projects/123 and projects/456 remain denied there, because denied values take precedence during reconciliation
B: The project's own allow of projects/123 wins, because the most specific resource always has the final word on a value
C: The folder policy and the organization policy are merged for the project, since the project inherits from its parent
D: Only the project's own policy applies, since a policy set on a resource always discards every ancestor policy
E: Allow entries are merged across levels but deny entries are discarded when they come from an ancestor above the folder
K: A,C
G: ## Hierarchy evaluation
A policy on a resource supersedes policies of its ancestors unless the resource inherits from its parent. When it inherits, the parent's effective policy is merged with the resource's own values.
## Reconciliation rule
During merging, deny values take precedence over allow values. A folder that denies one value and an organization that denies another yield an effective policy that denies both. A child cannot re-allow a value that an inherited policy denies.
W: A=Deny wins: denied values from the organization and the folder both stay in force, and the project's attempt to allow projects/123 does not override the inherited deny.
C=Merge with the parent: because the project inherits from its parent, the folder's effective policy (itself merged with the organization's) is combined with the project's values.
X: B=Most specific wins: that is true only when the resource does not inherit; with inheritance, deny values from ancestors still apply.
D=Discard all ancestors: that happens only if inheritance from the parent is turned off for the project, which is not the case here.
E=Discard higher denies: ancestors' deny values are never dropped by merging, no matter how many levels up they were set.
T: With inheritance on, parent and child lists merge and any denied value stays denied.

@ GCP-PSE D1 T1.5 applied troubleshooting
S: A security engineer finds that a constraint (managed by Google with a default of DENY at the organization level) is not being enforced the way she expected. She sets a project under the organization to allow a specific service account, and the effective policy at that project allows it. A colleague claims it should stay DENY, because "deny always wins when policies are merged". What explains the result?
A: The default behavior of a constraint is never merged, so a policy set at the project replaces the default instead of being reconciled with it
B: The project is exempt from inherited constraints, since projects are the leaf nodes of the hierarchy and cannot receive enforcement
C: The organization policy service ignored the deny, because default values are written as policies at the organization and expire after a day
D: A deny only wins when the project and the organization are in different regions, so the allow takes precedence for a global resource
K: A
G: ## Defaults versus explicit policies
Some constraints have a Google-managed default behavior that applies when no organization policy is set. That default is not a policy on the organization node. It is never merged with a policy you set: when you set a policy on a descendant, the policy replaces the default for that resource.
## Contrast with an explicit policy
If someone explicitly sets DENY in an organization policy at the organization, then a descendant policy that inherits from its parent is merged with it, and the deny value takes precedence. The two situations look similar but differ: default is replaced, explicit deny is merged.
W: Defaults are replaced: because the DENY comes from the constraint default and not from an explicit policy, the project policy that allows the account simply replaces it. An explicit organization-level DENY would have prevailed.
X: B=Leaf exemption: projects receive organization policies by inheritance like any other resource, so there is no exemption.
C=Expiring defaults: defaults do not expire and are not stored as policies on the organization node.
D=Region dependence: reconciliation is based on the policy configuration and inheritance, not on regions or global versus regional resources.
T: A constraint's managed default is never merged; an explicit deny at the organization is, and deny wins.

@ GCP-PSE D1 T1.5 advanced tradeoff
S: A security team plans to enforce a new constraint across 40 production projects that blocks creation of resources in non-approved locations. Teams fear that automation might break. The team wants evidence of what would be blocked before enforcement, with no change to behavior. What should the engineer do?
A: Create the policy in dry-run mode, review the audit-logged violations, then enforce it
B: Enforce it only on a single test folder and wait for failures, then expand the scope gradually
C: Enforce it in production and rely on a project owner to remove the policy for any team that breaks
D: Use Policy Analyzer for allow policies to preview which creation requests the constraint will deny

G: ## Dry-run mode for organization policies
A dry-run organization policy is created like a normal one, but violating actions are only audit logged and are not denied. You then query the logs to see which principals and resources would have been blocked, adjust the policy or fix the automation, and finally enforce the policy.
## Why it beats the alternatives
- It provides evidence from real production traffic, not from a sample.
- It carries no risk of outage.

W: Dry-run mode: production automation keeps running while violations are recorded in the audit logs, giving a concrete list of requests that enforcement would break.
X: B=Enforce on a test folder: it proves nothing about the 40 production projects and causes real failures in whatever runs in the test folder.
C=Enforce and remove on complaint: it causes the outage the team wanted to avoid, and project owners cannot override an inherited organization policy.

@ GCP-PSE D1 T1.5 advanced use-case
S: Which TWO statements about custom organization policy constraints are correct? (Select TWO)
A: A condition is written as a CEL expression over fields of a supported resource type, such as a node pool setting
B: A constraint using the allow action permits only requests that match its condition, so every other request is blocked
C: Once a custom constraint is created, it retroactively blocks and deletes resources that already violate it
D: A custom constraint can be defined for any Google Cloud resource type, including those with no organization policy support
E: Custom constraints are enforced through the IAM deny policy engine, so no organization policy is created or needed
K: A,B
G: ## Custom constraints
Prebuilt (managed) constraints cover many common controls. When none expresses the control you need, a custom constraint lets you define it. A custom constraint is a YAML definition naming the resource type, the methods it applies to, a **CEL condition** over the resource's fields (for example `resource.management.autoUpgrade == false`) and an action, ALLOW or DENY.
## Behavior
- DENY: a request is blocked if the condition is true.
- ALLOW: a request is permitted only if the condition is true, so everything else is blocked.
- You create the constraint, then create an organization policy that enforces it at the organization, a folder or a project; it is evaluated like other constraints.
- Organization policy is not generally retroactive: existing violating resources are reported but not changed.
W: A=CEL condition: the condition is a CEL expression over fields of a supported service resource, so you can express controls such as requiring a node-pool setting.
B=ALLOW semantics: with the allow action, only the case listed in the condition passes, and everything else is blocked, which is why ALLOW needs care.
X: C=Retroactive deletion: new organization policies are generally not retroactive, and existing resources in violation are left alone for manual remediation.
D=Any resource type: only supported services and resource types can have custom constraints, with a limited number per resource type.
E=Deny policy engine: custom constraints are part of Organization Policy and are enforced by creating an organization policy, not by IAM deny.
T: Custom constraints use CEL over supported resource fields with ALLOW or DENY, and they are enforced through an organization policy that is not retroactive.

@ GCP-PSE D2 T2.1 advanced use-case
S: A security team wants Layer 7 threat inspection of east-west traffic between VMs in a VPC network in two zones of one region, by using Cloud NGFW. Which set of building blocks is required?
A: A threat-prevention profile in a profile group, an endpoint in each zone, and rules that apply the group
B: A Cloud Armor security policy attached to the backend service of each VM tier and set to the preconfigured threat rules
C: One firewall endpoint in a single zone that inspects the whole region, plus network tags on each VM to select what is scanned
D: Packet Mirroring to a collector, with the VPC firewall rules set to block when the collector reports a threat signature
K: A
G: ## How Cloud NGFW intrusion prevention works
Cloud NGFW intrusion detection and prevention uses **firewall endpoints**, Google-managed zonal resources that transparently inspect intercepted traffic (packet intercept). The flow:
1. A firewall policy rule matches the traffic and its action applies a **security profile group**.
2. Matched packets are sent to the firewall endpoint for Layer 7 inspection.
3. The endpoint scans for threat signatures configured in the `threat-prevention` security profile and performs the profile's action when it finds a threat.
## Zones
A firewall endpoint inspects traffic in the zone where it is created, and associates with VPC networks. Workloads in two zones therefore need an endpoint in each zone.
