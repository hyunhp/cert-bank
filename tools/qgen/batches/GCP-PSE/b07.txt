@ GCP-PSE D3 T3.2 applied troubleshooting
S: A regulated retailer serves its checkout site through an external Application Load Balancer. The compliance team requires that browsers can negotiate only TLS 1.2 or later with a reduced cipher set, and that traffic between the load balancer and the backend VMs is also encrypted with TLS. Which TWO actions meet both requirements? (Select TWO)
A: Attach an SSL policy to the target HTTPS proxy with minimum TLS version 1.2 and the RESTRICTED profile
B: Configure the backend service to use HTTPS and install a certificate on each backend VM
C: Attach the SSL policy to the backend service so that it also governs the load balancer to backend connection
D: Turn on Application Layer Transport Security (ALTS) on the backend VMs so the load balancer authenticates them
E: Add a Cloud Armor rule that drops requests that arrive without a TLS version header
K: A,B
G: ## Two separate TLS legs
A proxy-based Layer 7 load balancer terminates the client connection and opens a new connection to the backend. These are two legs with separate controls.
- **Client to load balancer**: governed by an **SSL policy** on the target HTTPS or SSL proxy. The policy sets the minimum TLS version and a profile (`COMPATIBLE`, `MODERN`, `RESTRICTED`, `FIPS_202205` or a custom cipher list). `RESTRICTED` offers a reduced cipher set for stricter compliance and effectively excludes TLS 1.0 and 1.1.
- **Load balancer to backend**: SSL policies do not affect this leg. Encryption here comes from the backend service protocol (HTTPS, HTTP/2) and certificates that the backends present.
## Why this matters to a security engineer
Google encrypts the client leg by default when the client supports TLS, but the version floor and the cipher set are your decisions, and the backend leg is only encrypted if you configure it.
W: A=SSL policy on the HTTPS proxy: the policy is the control that sets a TLS 1.2 floor and the RESTRICTED cipher profile for client connections.
B=HTTPS backend service: using an encrypted protocol on the backend service and a certificate on each backend is what encrypts the second leg.
X: C=SSL policy on the backend service: SSL policies attach to the target proxy and affect only the client leg, not the connection between the load balancer and the backends.
D=ALTS on backends: ALTS is Google's internal service-to-service mechanism that customers do not configure on their own VMs.
E=Cloud Armor header rule: Cloud Armor filters requests by attributes at the edge; it does not set TLS versions or ciphers, and clients do not send a TLS version header.
T: Use an SSL policy for the client leg and an HTTPS backend service for the load balancer to backend leg: the two are configured separately.

@ GCP-PSE D3 T3.2 applied troubleshooting
S: A security audit finds that two VMs, one in each of two peered VPC networks, exchange database traffic using their external IP addresses because of an old firewall design. The auditor states that this traffic is not covered by Google's automatic network-layer encryption between VMs. What is the most direct remediation?
A: Move the traffic to the VMs' internal IP addresses across the VPC peering, which Google encrypts with session keys
B: Put Cloud NAT in front of both VMs so that the connection is wrapped in a Google-managed tunnel
C: Enable customer-managed encryption keys on both VMs' boot disks so that data in motion uses the same keys
D: Apply a Cloud Armor edge policy to the external addresses so that Google authenticates the connection
K: A
G: ## Where Google encrypts VM traffic automatically
Google encrypts and integrity-protects VM-to-VM connections inside its production network, including connections within a VPC network and across peered VPC networks. Hosts that communicate establish session keys over a control channel protected by ALTS, and the session keys are rotated periodically.
## The condition that trips teams up
The automatic encryption is activated by the use of **internal IP addresses**. Connections between VMs that use external IP addresses are not automatically encrypted at the network layer, so such flows need application-level TLS or, better, a move to the internal path.
## Applying it here
Re-addressing the flow onto internal IPs over the peering restores the default protection and also removes the exposure of a public path.
W: Internal IPs over peering: the automatic network-layer encryption applies to internal-address traffic inside and across peered VPC networks, so moving the flow there is the direct fix.
X: B=Cloud NAT: NAT translates source addresses for egress; it does not create an encrypted tunnel or add authentication.
C=CMEK on boot disks: disk keys protect data at rest, not data moving between hosts.
D=Cloud Armor edge policy: Cloud Armor filters traffic that reaches external load balancers; it does not encrypt VM-to-VM flows.
T: Automatic VM-to-VM encryption keys off internal IP addresses; flows over external IPs need TLS or a move to the internal path.

@ GCP-PSE D3 T3.2 advanced tradeoff
S: A bank runs 40 microservices on GKE clusters in two projects. Auditors want every service-to-service call authenticated in both directions, encrypted in transit with certificates that the bank controls, and enforced without changing application code. Which approach fits best?
A: Use Cloud Service Mesh so that sidecar or mesh data planes enforce mutual TLS with bank-controlled certificates
B: Rely on ALTS between pods, since Google authenticates every service to service call in its production network
C: Attach an SSL policy with the RESTRICTED profile to an internal Application Load Balancer in front of each microservice
D: Ask each team to add TLS libraries and a certificate loader to its own code, then audit each repository quarterly
K: A
G: ## Layers of in-transit protection
Google's default protections (TLS at the front end, ALTS between Google services, network-layer encryption between VMs) secure Google's own infrastructure. Workloads on GKE and Compute Engine that need **mutual** authentication of both client and server, with certificates the customer manages, add **Cloud Service Mesh** to get mTLS.
## Why a mesh
- Policy is uniform and set centrally rather than per repository.
- Applications keep speaking plain protocols to their local proxy; no code changes are needed.
- Certificate issuance and rotation are handled by the mesh instead of by each team.
W: Cloud Service Mesh: it provides mTLS for mutual authentication and encryption with managed certificates, enforced by the data plane without application changes.
X: B=ALTS between pods: ALTS secures calls between Google's own production services; it is not a mechanism that customer pods use for their own mutual authentication.
C=SSL policy on an internal load balancer: an SSL policy tunes TLS versions and ciphers on one proxy; it does not give each service a workload identity or mutual authentication.
D=Per-team TLS code: this meets the goal only if every team implements it correctly, and it conflicts with the no-code-change requirement and creates inconsistent certificate handling.
T: For mutual TLS between workloads with customer-managed certificates and no code changes, use Cloud Service Mesh.

@ GCP-PSE D3 T3.2 applied comparison
S: An analytics team standardised on AMD-based machines for a regulated workload. The threat model includes a compromised hypervisor attempting data replay and memory remapping against guest memory, and the team wants attestation reports it can request at any time from the processor. Which Confidential VM technology matches?
A: AMD SEV-SNP, which adds hardware protections against replay and remapping and supports attestation reports on demand
B: AMD SEV on N2D machines, because it gives the best protection against hypervisor-based attacks of this type
C: Shielded VM with a virtual TPM, because measured boot also prevents a hypervisor from reading guest memory
D: Customer-managed encryption keys on the boot and data disks, which keep memory contents unreadable to a compromised host
K: A
G: ## Confidential VM technologies
Confidential VM protects **data in use** with hardware-based memory encryption inside a trusted execution environment (TEE), plus attestation to verify the VM's identity and state. The technology depends on the machine type and CPU platform.
- **AMD SEV**: memory encryption through the AMD Secure Processor, boot-time attestation through vTPM; minimal performance cost; live migration on N2D and C3D.
- **AMD SEV-SNP**: adds hardware protection against malicious hypervisor attacks such as data replay and memory remapping; attestation reports can be requested at any time from the AMD Secure Processor.
- **Intel TDX**: an isolated trust domain with memory encryption, which also defends against limited physical attacks on memory such as DRAM analysis.
## Reading the scenario
AMD plus replay/remapping plus on-demand attestation reports points to SEV-SNP.
W: AMD SEV-SNP: it extends SEV with protection against the replay and remapping attacks named in the threat model and offers attestation reports from the AMD Secure Processor.
X: B=SEV on N2D: SEV encrypts memory and supports live migration, but the hypervisor-attack hardening for replay and remapping is what SNP adds.
C=Shielded VM and vTPM: Shielded VM protects boot integrity; it does not encrypt guest memory against the host.
D=CMEK on disks: disk keys protect data at rest; memory is a separate exposure that only a TEE addresses.
T: For hypervisor replay and remapping threats on AMD, choose SEV-SNP; remember that memory encryption is separate from disk CMEK.

@ GCP-PSE D3 T3.2 advanced use-case
S: A payments company has one existing Standard GKE cluster. Only the tokenization pods need memory encryption, and the platform team wants to avoid taking the other 30 workloads onto confidential hardware or rebuilding the cluster. Which option fits?
A: Define a ComputeClass that uses Confidential GKE Nodes and select it only in the tokenization workloads
B: Enable Confidential GKE Nodes at the cluster level so every node in the existing cluster is converted in place
C: Create a Binary Authorization policy that requires tokenization images to be attested before they start
D: Enable Shielded GKE Nodes on the cluster, since secure boot also encrypts workload memory
K: A
G: ## Scoping Confidential GKE Nodes
Confidential GKE Nodes can be enabled at three scopes:
- **Cluster level**: applies to all nodes, is set when creating the cluster, cannot be overridden per pool or workload, and is irreversible.
- **Node pool level**: only the pool's nodes are confidential.
- **Workload level**: a ComputeClass carries the Confidential configuration, and pods that select it get confidential nodes. This works with AMD SEV, SEV-SNP or Intel TDX regardless of cluster mode.
## Reading the scenario
Selective protection of a few workloads in an existing cluster is the case for workload scope, which avoids confidential hardware for the rest.
W: ComputeClass at workload level: GKE creates confidential nodes only for pods that select the class, so the 30 other workloads stay as they are.
X: B=Cluster-level enablement: it is chosen at cluster creation, applies to every node and is irreversible, so it does not convert an existing cluster selectively.
C=Binary Authorization attestation: it controls which images may be deployed (supply chain), not how node memory is protected.
D=Shielded GKE Nodes: secure boot and integrity monitoring protect against boot-level tampering, not memory inspection by the host.
T: Confidential GKE Nodes can be scoped to a cluster, a node pool or a workload; use workload scope to protect only what needs it.

@ GCP-PSE D3 T3.2 advanced use-case
S: A bank and an insurer want to train a fraud model on the union of their customer records. Neither party will let the other see raw records, and neither trusts the cloud operator running the job. Each wants its data key released only to a workload image that both parties have approved. Which design fits?
A: Run the joint workload in Confidential Space, releasing each party's Cloud KMS key only to attested approved workloads
B: Copy both datasets into one Cloud Storage bucket in a neutral project, inside a VPC Service Controls perimeter
C: Have both parties de-identify their records with Sensitive Data Protection and email the files to a shared analyst
D: Run the job on a Confidential VM, with both parties granting the VM's service account access to their data
K: A
G: ## Multi-party computation with Confidential Space
Confidential Space is a TEE built on Confidential VM with a hardened OS image. A **workload** (container) runs on it, and an **attestation service** issues identity tokens describing the workload and its environment. Data owners set conditions on those tokens, so their keys or data are released only to a workload that matches an agreed image and runs in a genuine confidential environment.
## Why this meets the requirement
- Each party keeps control of its own data and key.
- The operator of the environment cannot read the data being processed.
- Release is tied to measurable workload properties, not to who owns the project.
W: Confidential Space with attested key release: the attestation token proves the approved workload is running in a TEE, so each owner releases its key only to that workload, and the operator cannot see the data.
X: B=Shared bucket in a perimeter: the perimeter limits where data can go, but whoever administers the shared project can read both datasets.
C=De-identify and email: this weakens the model by removing signal and moves data over an uncontrolled channel; it also does not address trust in the operator.
D=Plain Confidential VM with service account access: the VM protects memory, but access is based on an identity, not on attestation of an agreed workload, so either party's administrators could change the code that runs.
T: For multi-party analytics where nobody trusts the operator, use Confidential Space and release keys by attestation.

@ GCP-PSE D3 T3.2 applied definition
S: Which TWO statements about Confidential VM are accurate? (Select TWO)
A: It encrypts guest memory with hardware-based keys, so data in use is not readable by the hypervisor
B: It offers attestation, so a relying party can verify the identity and state of the VM before releasing secrets
C: It prevents the application running inside the VM from leaking data it is authorised to read
D: It makes encrypting disks with Cloud KMS unnecessary, because the whole VM boundary is encrypted
E: It supports live migration on every available Confidential Computing technology
K: A,B
G: ## What a TEE gives you
Confidential VM is a **trusted execution environment**: hardware-based memory encryption and isolation plus attestation. It addresses the exposure of data **in use** against the host, the hypervisor and the operator.
## What it does not do
- It does not change what the guest software itself may read or send; a flawed or malicious application inside the VM still has full access to its own memory.
- It does not replace encryption of data at rest or in transit, which are separate controls.
- Features differ per technology: live migration, for example, is available on AMD SEV with N2D and C3D machine types, unlike the other technologies.
W: A=Memory encryption: the hardware encrypts guest memory, which is the defining protection for data in use.
B=Attestation: verifying the VM's identity and state lets a relying party, such as a key service, decide whether to release secrets.
X: C=Leak by the application: a TEE protects against the platform, not against code inside the guest.
D=No need for disk keys: data at rest and data in use are separate exposures, so disk encryption and any CMEK requirement remain.
E=Live migration everywhere: live migration is limited to AMD SEV on N2D and C3D machines.
T: Confidential VM protects data in use and offers attestation, but it does not replace at-rest or transit encryption or protect against the guest's own code.

S: A healthcare AI team trains models on GPU instances and holds that the model weights and patient images processed on the GPU must not be visible to the hypervisor or to Google Cloud operators, not just the CPU memory. Which approach extends hardware isolation to the GPU?
A: Use NVIDIA Confidential Computing on a supported GPU machine series, paired with a CPU TEE such as Intel TDX or AMD SEV
B: Use CMEK-encrypted boot disks on the GPU instance, since data loaded onto the GPU is then encrypted in GPU memory too

Plain Confidential VM protects CPU-side memory. @ GCP-PSE D3 T3.2 advanced tradeoff
S: A trading firm moved its risk engine from N2D Confidential VMs running AMD SEV to newer machines using AMD SEV-SNP for stronger hypervisor-attack protection. Since the move, the operations team sees VMs restarting during host maintenance events, which broke long batch runs. What should the security engineer explain and recommend?
A: Live migration is available only on AMD SEV with N2D and C3D, so design the batch jobs to tolerate restarts or accept that trade-off
B: The restarts are a misconfiguration; turning on live migration for the SEV-SNP VMs removes them with no change in protection
C: Confidential VMs never experience host maintenance events, so a separate application bug must be causing the restarts
D: Replace the VMs with Shielded VM instances, which add the missing live migration while keeping memory encryption
K: A
G: ## Security features have operational costs
The Confidential VM documentation notes that AMD SEV on N2D and C3D machine types supports live migration, **unlike the other Confidential Computing technologies**. Where a technology cannot be live migrated, host maintenance events can stop and restart the VM.
## Making the trade-off
A security engineer weighs the stronger protection of SEV-SNP (replay and remapping defence, on-demand attestation reports) against the interruptions it brings, and then either:
- designs workloads to checkpoint and tolerate restarts (managed instance groups with autohealing, resumable jobs), or
- stays on SEV where the threat model allows it.
W: Tolerate restarts or keep SEV: live migration is limited to SEV on N2D and C3D, so the stronger protection of SNP comes with restarts that the batch design must handle.
X: B=Enable live migration on SEV-SNP: it is not offered for that technology, so there is no setting that removes the restarts.
C=No maintenance events: Confidential VMs are subject to host maintenance like other VMs; what differs is whether they can be live migrated.
D=Shielded VM: Shielded VM does not encrypt memory, so it would give up the confidentiality requirement without adding a migration capability.
T: Not every Confidential VM technology supports live migration; weigh the stronger protection against restart behaviour during maintenance.

@ GCP-PSE D3 T3.2 advanced troubleshooting
S: A bucket holds audit exports under a locked retention policy of seven years. A lifecycle rule deletes objects whose age exceeds one year. A security engineer is asked what the rule will do to a 13-month-old object.
A: The Delete action does not take effect until the retention policy is fulfilled, and then the rule deletes the object
B: The object is deleted at 13 months, because lifecycle actions override retention policies on the same bucket
C: The rule is rejected, because a bucket with a locked policy cannot also hold lifecycle rules
D: The object is moved to a colder storage class at 13 months, which satisfies the rule without deleting it
K: A
G: ## Retention policies beat lifecycle deletion
Object Lifecycle Management performs actions (`Delete`, `SetStorageClass`, `AbortIncompleteMultipartUpload`) when conditions are met. A `Delete` action does **not** take effect on an object that has an object hold or a retention policy that is not yet fulfilled. When the conditions remain satisfied, the deletion happens after the hold is removed or the retention period ends.
## Bucket Lock
Locking a retention policy makes it permanent: it cannot be removed or reduced, and the bucket cannot be deleted until every object has met the retention period. This is why retention is the right mechanism for immutability, while lifecycle rules are the right mechanism for cleanup after retention ends.
W: Delete waits for retention: the object survives until seven years have passed, and because the rule's condition still holds, the delete then occurs.
X: B=Lifecycle overrides retention: it does not; a retention policy blocks deletion regardless of who initiates it.
C=Rule rejected: lifecycle rules and locked retention policies coexist; this combination is a common pattern.
D=Move to colder class: the configured action is Delete, not SetStorageClass, so the class is unchanged.
T: A lifecycle Delete cannot remove an object under an unfulfilled retention policy or hold; it runs after the retention ends.

@ GCP-PSE D3 T3.2 applied comparison
S: A bucket has two lifecycle rules with the same age condition of 365 days: one deletes the object, the other changes the storage class to Archive. A new security analyst wants to know what happens to an object that reaches that age with no hold or retention policy.
A: The Delete action takes precedence, so the object is deleted
B: The object is changed to Archive first and deleted only after a second evaluation
C: Cloud Storage applies the rule that appears first in the configuration
D: Both actions run, so the object is first reclassified and then removed
K: A
G: ## Rule conflicts
When several lifecycle rules have their conditions satisfied at the same time, Cloud Storage performs only one action:
- `Delete` takes precedence over any `SetStorageClass`.
- Among `SetStorageClass` rules, the one that moves the object to the class with the lowest at-rest storage price wins; for example, with Nearline and Coldline rules on the same condition, the object ends up in Coldline.
## Why this matters for security
Overlapping rules are a common cause of accidental deletion. Test rules on a development bucket or on a subset selected with `matchesPrefix` or `matchesSuffix` before applying them to production data.
W: Delete takes precedence: when the same condition triggers both, the delete action is the one performed.
X: B=Reclassify then delete: only one action is performed per object when multiple rules match at once.
C=First rule wins: precedence is defined by action type and class price, not by position in the file.
D=Both actions: the documentation states that only one of the matching rules is acted on.
T: When lifecycle rules overlap, Delete beats SetStorageClass, and among class changes the cheapest class wins.

@ GCP-PSE D3 T3.2 advanced use-case
S: A financial firm must keep trade records unalterable for seven years, even against its own project owners, and then stop paying for the data. Which TWO configurations together meet this? (Select TWO)
A: Add a seven-year retention policy to the bucket and lock it
B: Add a lifecycle Delete rule that applies after the seven-year retention period ends
C: Add an IAM deny policy on object deletion for the project owners group only
D: Turn on Object Versioning and rely on noncurrent versions to preserve overwritten records
E: Add a lifecycle rule that sets the storage class to Archive after one year, which prevents modification
K: A,B
G: ## Immutability versus cleanup
- **Retention policy and Bucket Lock** define how long objects must be kept. Once locked, the policy cannot be removed or reduced, and objects cannot be deleted or overwritten before they reach the retention age, whoever has permissions.
- **Lifecycle Delete** removes objects once they satisfy the condition; with an unfulfilled retention policy the delete waits, so it can be configured once and takes effect only after retention is met.
## Why IAM and versioning are not equivalent
IAM controls can be changed by someone with sufficient permissions, and versioning preserves data only until noncurrent versions are deleted. Neither is a regulator-grade immutability guarantee.
W: A=Locked retention policy: it makes the seven-year minimum permanent, even for administrators.
B=Lifecycle Delete after retention: it removes expired data automatically, ending storage cost without manual work.
X: C=Deny policy for owners: IAM policies can be edited by those who administer the policy, so this is not immutability, and it leaves other principals unaffected.
D=Object Versioning: noncurrent versions can still be deleted by principals with permission, so records are not guaranteed to be retained.
E=Archive class: the storage class changes pricing and access cost, not whether objects can be modified or deleted.
T: Lock a retention policy for unalterable retention, and add a lifecycle Delete rule for automatic cleanup after it expires.

@ GCP-PSE D3 T3.2 applied troubleshooting
S: A privacy office must erase customer exports within seven days of a request. The data team deleted objects through a lifecycle rule and an auditor still found the data recoverable from the bucket days later. The bucket uses default soft delete settings. What is the best fix?
A: Set the bucket's soft delete retention period to match the erasure window, or disable soft delete where recovery is not needed
B: Add a second lifecycle Delete rule with a shorter age so the object is removed twice and cannot be restored
C: Enable Object Versioning so deleted objects are replaced by empty versions that cannot be read
D: Move the bucket to Autoclass so deleted data is automatically transferred to the Archive class before final removal occurs

G: ## Deletion is not always erasure
With default settings, when a live object is deleted in Cloud Storage it becomes **soft deleted** and is retained for seven days, during which it can be restored. A lifecycle `Delete` action behaves the same way. In buckets with Object Versioning, deleting a live version makes it noncurrent instead.
## Design for privacy requirements
- Align the **soft delete retention duration** with the deadline in the privacy commitment, or disable it where recovery is not needed.
- If versioning is enabled, also add rules for noncurrent versions.
- Record the behaviour in the erasure procedure so the deadline is defined from when data becomes unrecoverable.
W: Align or disable soft delete: the data remained restorable only because of the soft delete retention, so adjusting it removes the recovery window.
X: B=Second Delete rule: a second delete action on the same object does not change the soft delete retention; it is still restorable.
C=Object Versioning: versioning keeps older versions, which makes erasure harder, not easier.
D=Autoclass: Autoclass changes storage classes for cost, and does not remove data or shorten recovery windows.
T: A delete leaves data restorable through soft delete retention; align that period with privacy erasure deadlines.

@ GCP-PSE D3 T3.3 advanced use-case
S: Two teams share one project for custom training on Agent Platform. By default each training job runs with the project's Custom Code Service Agent. The security engineer finds that team A's jobs can read team B's bucket through that identity. What is the least-privilege fix?
A: Create a dedicated user-managed service account per team with only the roles it needs, and attach it to each of that team's training jobs
B: Grant the Custom Code Service Agent the storage admin role on both buckets so that access is consistent for everyone
C: Put each team's data in a separate folder and keep using the Custom Code Service Agent with a deny policy on the other team's folder
D: Ask the teams to export their own user credentials into the training container so that jobs run as each person
K: A
G: ## Default identity versus custom service account
Custom training containers run, by default, as the project's **Custom Code Service Agent**, a project-wide identity. Anything granted to it is available to every job. Agent Platform lets you **attach a user-managed service account** to a `CustomJob`, `HyperparameterTuningJob`, `TrainingPipeline` or deployed model, overriding the default for that resource.
## Why this is the least-privilege pattern
- Roles are scoped to what each team's jobs need.
- The identity is separate from the people who launch jobs.
- If the account lives in another project, the Agent Platform service agent needs the Service Account Token Creator role on it.
W: Per-team service accounts: each job runs with only its team's permissions, removing the shared broad identity.

- Scans are per digest; changing tags does not trigger a rescan.

C=No OS package detection: Artifact Analysis scans OS packages as well as language packages.
D=Only on-demand scans get new CVEs: automatic scanning includes continuous analysis for registry images.
