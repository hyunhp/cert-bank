@ GCP-PSE D2 T2.1 applied troubleshooting
S: A security team enforced the organization policy constraint that denies external IPv4 addresses on VM instances across the production folder. A later scan shows that a few VMs in dual-stack subnets are still reachable from the internet through external IPv6 addresses. What explains this, and what closes the gap?
A: The constraint governs only IPv4 external addresses, so keep private workloads on subnets with internal IPv6 access and deny ingress with firewall rules
B: The constraint takes effect only for VMs created after enforcement, so recreate the VMs and the external IPv6 addresses will be removed automatically
C: The constraint covers IPv6 only when the subnet is in custom mode, so convert every dual-stack subnet in the folder to custom mode and re-apply it
D: The constraint is overridden by default for any VM that has a service account attached, so remove the service accounts from the affected VMs
K: A
G: ## Public versus private addressing on Compute Engine
A VM is reachable from the internet only if it has an external address and a firewall rule that admits the traffic. Security engineers remove the first condition with organization policy and the second with firewall policy, so that one mistake does not expose a workload.
- The Restrict External IPs For VM instances constraint (`constraints/compute.managed.vmExternalIpAccess`) denies creating or updating VMs with **IPv4** external addresses. Google states that it does not restrict IPv6 external addresses.
- Dual-stack subnets can have an IPv6 access type of external or internal. Only the external type gives a VM a publicly routable IPv6 address.
- Implied deny ingress still blocks unsolicited inbound traffic, but an overly broad allow rule will admit it on any external address.
## Applying it here
The residual exposure is IPv6, which the constraint never touched. Private workloads belong in subnets with internal IPv6 access, and ingress deny rules in a firewall policy give a second layer.
W: Internal IPv6 plus ingress deny: the constraint is IPv4-only by design, so the fix is to stop handing out publicly routable IPv6 addresses to private workloads and to back that with firewall rules.
X: B=Recreate the VMs: the constraint does not remove IPv6 addresses at all, so recreated VMs in the same subnets would receive the same kind of external IPv6 address again.
C=Custom-mode subnets: the subnet mode does not change what the constraint covers; the constraint is IPv4-only whichever mode the subnet uses.
D=Remove service accounts: a service account has no effect on how the constraint evaluates a VM, so removing one would also break workload authentication without closing the exposure.
T: The external IP constraint covers IPv4 only; control IPv6 exposure with subnet IPv6 access type and firewall rules.

@ GCP-PSE D2 T2.1 advanced use-case
S: A bank's proxy team must let developers download packages from www.example.com/documentation but block www.example.com/uploads, for HTTPS traffic leaving private VMs through Secure Web Proxy. All VMs are managed by the bank. Which configuration meets the requirement?
A: Enable TLS inspection with a CA Service CA pool, install the root certificate on the managed VMs, and write path-based URL rules
B: Add a hostname-only rule for www.example.com and rely on the HTTPS server name to separate the documentation path from the uploads path
C: Switch the proxy to next hop mode, because that mode decrypts HTTPS traffic natively so that full URLs become visible to rules
D: Add a gateway security rule that matches the destination IP address of www.example.com, allowing one path and blocking the other path
K: A
G: ## What Secure Web Proxy can see in HTTPS
Secure Web Proxy (SWP) is a managed outbound proxy. It denies all outbound traffic by default until a rule allows it, and rules can match sources (IP addresses, service accounts, secure tags, verified client certificate identities) and destinations.
- Without decryption, an HTTPS request exposes only the host name. The path, query and headers are inside the encrypted stream.
- **TLS inspection** makes SWP terminate the client connection with a certificate it generates on the fly, inspect the request, then open a second TLS connection to the destination.
- SWP gets certificates from a private CA in **CA Service**. Clients accept them only if the organization's private root is trusted on the client, which is why inspection suits managed devices.
## Applying it here
Allowing one path and denying another needs the full URI, so TLS inspection is required. Managed VMs let the bank distribute the trust anchor.
W: TLS inspection with a CA pool: decryption exposes the full URL to the rules, and the managed VMs can be made to trust the bank's private root certificate.
X: B=Hostname-only rule: the server name identifies only the site, so a host-level rule would either allow both paths or block both; it cannot tell documentation from uploads.
C=Next hop mode: that mode decides how traffic reaches the proxy through routing, not whether HTTPS is decrypted; path rules still need TLS inspection.
D=Destination IP match: both paths are served from the same address, so an IP-based rule cannot separate them, and addresses behind CDNs change.
T: Path-level HTTPS control in Secure Web Proxy needs TLS inspection backed by a CA Service pool and client trust of the root.

@ GCP-PSE D2 T2.1 applied troubleshooting
S: After a bank enabled Secure Web Proxy TLS inspection for all outbound HTTPS from managed VMs, operating system and browser updates fail with certificate errors, while ordinary websites work. The applications are known to accept only specific public CA chains. What is the best fix?
A: Add the update hostnames to the session matcher as exclusions so those connections bypass decryption, and keep inspection for everything else
B: Turn off TLS inspection for the whole policy until the vendors of the update clients start accepting the proxy's private CA certificates
C: Install the proxy's private root CA on the update servers operated by the vendors, so that they trust the certificates the proxy issues
D: Move the VMs to a subnet that sends traffic to Cloud NAT directly, which restores update access but still lets the proxy log the sessions
K: A
G: ## Why some clients reject inspected connections
During TLS inspection the proxy presents a certificate signed by the organization's private CA. A client that has the private root installed accepts it. A client that uses **certificate pinning** is hard-coded to accept only a certain public key or public CA chain, so it ends the connection when the proxy's certificate does not match.
- Typical pinned clients include operating system updaters and browser updaters.
- Pinning cannot be fixed on the server side, because the pin is in the client.
## Narrow bypass instead of a global switch
The session matcher decides which traffic is decrypted. It can match or exclude by destination FQDN or by source attributes such as secure tags, service accounts or IP ranges, so pinned destinations are exempted while all other traffic keeps inspection.
W: Session matcher exclusions: bypassing decryption only for the pinned update destinations lets those clients complete their own TLS handshake, and everything else remains inspected.
X: B=Turn off inspection globally: this removes visibility into all encrypted traffic to solve a problem limited to a few pinned destinations, which is a much larger loss of control than necessary.
C=Install the root on vendor servers: the bank cannot change servers it does not operate, and the problem is on the client side pinning, not server trust.
D=Bypass the proxy via direct Cloud NAT: this skips the mandatory checkpoint for those VMs and loses the destination-level policy and logging that the proxy provides.
T: Exempt pinned destinations through the session matcher rather than disabling TLS inspection altogether.

@ GCP-PSE D2 T2.1 applied definition
S: A network security engineer reviews the properties of Secure Web Proxy before approving it for a Shared VPC environment. Which TWO statements are correct? (Select TWO)
A: Outbound traffic is denied by default until a gateway security rule explicitly allows it
B: Secure Web Proxy supports HTTP/3 and IPv6 traffic, so QUIC-based applications pass through the proxy unchanged
C: A proxy instance can be deployed only in the host project, not in a service project
D: TLS inspection works without any client configuration, even from unmanaged devices that lack the private root CA
E: Source-based rules can match only IP addresses, so identity-based rules require a separate identity-aware proxy product
K: A,C
G: ## Secure Web Proxy facts that drive design
Secure Web Proxy (SWP) is a managed, autoscaling outbound proxy for HTTP and HTTPS. These properties matter in a review:
- It has a default deny-all stance: nothing leaves until a rule allows it.
- Policies are separate from the proxy, so one set of gateway security rules or URL lists can be reused across proxies.
- Sources can be identified by IP address, service account, secure tag or a client certificate identity verified with frontend mTLS.
- Limitations: IPv4 only, HTTP up to version 2.0 (no HTTP/3), and deployment in a host project rather than a service project when Shared VPC is used.
- TLS inspection needs clients to trust the private CA, so it fits managed devices.
W: A=Default deny: SWP blocks all outbound web traffic until a rule allows it, so a missing rule fails safely.
C=Host project only: a proxy instance cannot be deployed in a service project; with Shared VPC the central team places it in the host project.
X: B=HTTP/3 and IPv6: SWP supports only IPv4 and HTTP versions up to 2.0, so QUIC and IPv6 clients are not supported.
D=No client configuration: inspected connections present certificates from the private CA, so unmanaged devices without that root get insecure-connection warnings.
E=IP-only sources: SWP rules can also match service accounts, secure tags and verified client certificate identities, so no separate product is needed for identity-based rules.
T: Secure Web Proxy is default-deny, identity-aware, IPv4 and HTTP/2 only, and lives in the host project under Shared VPC.

@ GCP-PSE D2 T2.1 applied troubleshooting
S: A company enabled DNSSEC on the Cloud DNS public zone for example.org and the console shows it as on. A security scan using a validating resolver still reports that the domain has no chain of trust. The registrar is a small reseller. What is the most likely cause?
A: No DS record was published at the registrar for the parent zone, so resolvers cannot link the signed zone to the registry
B: Cloud DNS signs only records of type A, so the NS and MX records in the zone are unsigned and break validation for the whole zone
C: DNSSEC works only for private zones, so enabling it on a public managed zone has no effect on public resolvers
D: The zone keys must be rotated manually before validating resolvers accept them, and no rotation has been performed yet
K: A
G: ## Three places DNSSEC must be configured
DNSSEC authenticates DNS answers so that an attacker cannot forge or poison them. It does not encrypt queries. For a public Cloud DNS zone, the chain of trust needs:
- **The zone**: with DNSSEC on, Cloud DNS creates and rotates the signing keys (DNSKEY) and signs the data (RRSIG records).
- **The registry**: the parent zone (for example `.org`) must hold a **DS record** that matches the zone's DNSKEY. You add it by activating DNSSEC at the domain registrar.
- **The resolver**: validation only protects clients whose resolver checks signatures.
If the registrar or registry does not support DNSSEC for the TLD, or no DS record is added, enabling it in Cloud DNS has no effect.
W: Missing DS record: without a DS record in the parent zone, validating resolvers have no trust link to the signed zone, which is exactly the symptom reported.
X: B=Signing only A records: Cloud DNS signs the whole zone's record sets with RRSIG records, so unsigned NS and MX records are not the cause.
C=Private zones only: public managed zones are the main use of DNSSEC in Cloud DNS, so this statement is wrong.
D=Manual key rotation: Cloud DNS manages creation and rotation of DNSSEC keys automatically for the zone.
T: DNSSEC on a public zone works only when the registrar publishes the DS record and clients use a validating resolver.

@ GCP-PSE D2 T2.1 advanced use-case
S: A security team wants every VM in a VPC network to receive a sinkhole address for any lookup of *.malware-campaign.test, while one required subdomain, updates.malware-campaign.test, must still resolve normally through the existing private zone. How should the team implement this with Cloud DNS?
A: Attach a response policy to the network with a wildcard rule returning the sinkhole address and a passthru rule for the one subdomain
B: Create a DNS routing policy on the wildcard record set with weighted round robin so that most answers resolve to the sinkhole address
C: Apply an inbound server policy on the network so that the sinkhole answers are served to every VM that uses the metadata server
D: Create a DNSSEC-signed public zone for the domain that contains the sinkhole records, so validating resolvers return those records
K: A
G: ## Three kinds of Cloud DNS policy
- **Server policies** configure how a VPC network resolves names: inbound forwarding so that on-premises hosts can query Google Cloud, outbound forwarding to alternative name servers, and query logging.
- **Response policies** hold rules that override answers for chosen query names (wildcards allowed) inside a network. A rule can return specific records, or use passthru to exempt names so the normal lookup continues. The effect is similar to the response policy zone (RPZ) concept used for blocking domains.
- **Routing policies** steer traffic on a record set (weighted round robin, geolocation, failover) and are not security controls.
Only one response policy can be attached to a network, but it may hold many rules.
## Applying it here
A wildcard rule redirects the campaign domain, and a passthru rule exempts the required subdomain so that the private zone continues to answer.
W: Response policy with passthru: a wildcard rule overrides the answers for the whole domain, while passthru lets the required subdomain resolve as if the wildcard rule did not exist.
X: B=Routing policy: weighted round robin only spreads answers between record values for one name and cannot override private-zone answers for a whole domain.
C=Inbound server policy: this exposes the network's resolver to on-premises clients; it does not change the answers that VMs receive.
D=DNSSEC-signed public zone: DNSSEC authenticates real answers, and a public zone does not override private resolution inside the VPC network.
T: Use a Cloud DNS response policy, with passthru exemptions, to override or block names for every VM in a network.

@ GCP-PSE D2 T2.1 applied use-case
S: A security operations team suspects that a compromised GKE workload uses DNS lookups of random-looking names to exfiltrate data, and queries are resolved by the VPC network's resolver. The team wants a record of every query the VPC resolves, kept in the project that owns the network. What should be configured?
A: Enable query logging in a Cloud DNS policy applied to the VPC network and analyze the records in Cloud Logging
B: Enable VPC Flow Logs on the subnets, because flow logs contain the names that VMs and containers queried
C: Create a log sink for Cloud Audit Logs Data Access in the project, because DNS queries are administrative API calls
D: Enable Packet Mirroring on the GKE nodes and store the mirrored traffic in a bucket, because Cloud DNS offers no logging
K: A
G: ## Monitoring DNS as a security signal
DNS tunnelling and domain-generation algorithms (DGA) show up as unusual query names. Cloud DNS logging records the queries that name servers resolve for VPC networks, as well as direct queries to a public zone.
- Logging is switched on through a DNS policy attached to the network.
- Logged queries can originate from VMs, GKE containers in the same network, peering zones, or on-premises clients using inbound forwarding.
- Records belong to the project that owns the network. With Shared VPC that is the host project.
- Logs go to Cloud Logging, where they can be routed to sinks, log-based metrics or SIEMs.
## Why other telemetry falls short
Flow logs record IP connections, not names, and audit logs record API calls, not DNS lookups.
W: DNS policy query logging: it records every query the VPC resolves, with results, in Cloud Logging under the project that owns the network.
X: B=VPC Flow Logs: flow records hold IP addresses and ports, and do not contain the query names, so the exfiltration pattern in names stays invisible.
C=Data Access audit logs: audit logs track API calls to Google Cloud services, and a DNS lookup from a workload is not such a call.
D=Packet Mirroring: it can capture DNS packets, but at much higher operational cost, and the claim that Cloud DNS offers no logging is false.
T: Turn on Cloud DNS query logging through a DNS policy to watch for tunnelling and DGA activity.

@ GCP-PSE D2 T2.1 advanced troubleshooting
S: A platform team sets the Restrict Resource Service Usage constraint on the sandbox folder with a denylist containing compute.googleapis.com, meaning to stop VM creation. Teams then report that GKE cluster operations in the folder also fail, and the team wants to understand and roll out changes safely. Which TWO statements are correct? (Select TWO)
A: Services with a direct dependency on a restricted service are restricted as well, so Google Kubernetes Engine fails when Compute Engine is denied
B: The constraint blocks runtime access for services such as IAM, Cloud Logging and Cloud Monitoring as well, because it covers every API
C: Applying the constraint with tags for conditional enforcement allows a staged rollout to selected projects before it is applied folder-wide
D: A policy can combine a denylist and an allowlist at the same level, so exceptions are written as allowed values within the denied list
E: Restricted services remain visible in the console, and only API calls to them fail
K: A,C
G: ## Restricting which APIs a hierarchy can use
The Restrict Resource Service Usage constraint (`constraints/gcp.restrictServiceUsage`) lets administrators allow or deny Google Cloud services for an organization, folder or project.
- It works either as a **denylist** (anything not denied is allowed) or as an **allowlist** (anything not allowed is denied); the two are mutually exclusive.
- It controls runtime access to resources of the services in scope, with eventual consistency, and also hides restricted services in the console.
- It does not apply to essential dependencies such as IAM, Cloud Logging and Cloud Monitoring.
- Services that depend directly on a restricted service are restricted too: restricting Compute Engine also restricts GKE.
## Safe rollout
Because the effect is immediate, Google suggests using tags to enforce the constraint conditionally and widening scope gradually.
W: A=Dependency effect: GKE manages Compute Engine resources, so denying Compute Engine also stops GKE operations, which explains the reports.
C=Tag-based staging: conditional enforcement by tag lets the team apply the constraint to a few projects first and widen it after checking for breakage.
X: B=Blocks IAM and Logging: the constraint excludes essential dependencies such as IAM, Cloud Logging and Cloud Monitoring, so they keep working.
D=Combined deny and allow: the two modes are mutually exclusive, so exceptions are expressed by choosing the mode that fits, not by mixing them.
E=Still visible in the console: restricted services disappear from navigation and search, and opening them shows an error.
T: Restricted service usage cascades to dependent services, so stage it with tags before enforcing folder-wide.

@ GCP-PSE D2 T2.1 applied use-case
S: A mobile team embeds an API key for the Places API in a published Android app. A security review notes the key could be extracted and abused to run other APIs and consume quota. Which TWO controls limit what a stolen key can do? (Select TWO)
A: Add an API restriction so the key can call only the Places API in the project
B: Add an application restriction to the Android package name and signing certificate fingerprint
C: Keep the key but store it in Secret Manager, which prevents the app from sending it to Google APIs in a request
D: Replace the key with an IAM role on the app's users, because API keys are checked by IAM and need no restriction
E: Apply an organization policy to the project that disables the Places API for all keys, then test usage
K: A,B
G: ## Restricting and containing API keys
A standard API key identifies a project for quota and billing, not a principal, so IAM cannot restrict who uses it. If the key is embedded in a client, assume that it will be extracted. Google recommends two kinds of restriction, used together:
- **API restrictions**: limit which APIs the key can call, for example only the Places API.
- **Application restrictions**: limit where the key is accepted, by websites (HTTP referrers), IP addresses, Android apps (package name plus SHA-1 signing certificate fingerprint) or iOS apps (bundle identifier).
A key without application restrictions can be used from anywhere.
## Monitoring side
Review API usage metrics and quota consumption per key so that unusual use of an unrestricted key is noticed.
W: A=API restriction: the key can then call only the listed API, so a stolen key cannot be used against other services in the project.
B=Application restriction: tying the key to the app's package name and signing fingerprint limits the clients Google accepts the key from.
X: C=Secret Manager: the app must still send the key with each request, and a secret held on the device is as extractable as one compiled in.
D=IAM roles replace the key: standard API keys carry no principal, so IAM does not evaluate them, and the claim that they need no restriction is wrong.
E=Disable the API for the project: this breaks the legitimate app and is not a per-key control, because organization policy cannot target a single key.
T: Restrict API keys by API and by application, because a standard key has no identity for IAM to check.

@ GCP-PSE D2 T2.2 advanced use-case
S: A company has an enforced VPC Service Controls perimeter around its analytics projects. The security team wants to add the Cloud KMS API as a restricted service and also loosen an access level that admits the corporate IP range. They want to see the effect on production traffic first, with no risk of new denials. Which approach is correct?
A: Edit the dry run configuration, create a new access level reflecting the loosening and apply it to the dry run spec, then review dry run audit log entries
B: Edit the enforced configuration directly, because access level changes take effect only after a one-hour review period that works as a built-in test
C: Edit the access level in place and use the dry run perimeter configuration to test it, because access levels have a dry run mode of their own
D: Clone the whole organization into a test organization and replay the production traffic there, because dry run cannot cover service changes
K: A
G: ## Dry run mode
A VPC Service Controls perimeter can have an enforced configuration and a dry run configuration. In dry run, requests that violate the perimeter are **logged but not denied**, with `metadata.dryRun` set to true in the audit log.
- The dry run configuration starts as a copy of the enforced one (inherited) and can then be changed freely, with no effect on enforcement.
- The enforced configuration is evaluated first. Only requests that the enforced configuration allows but the dry run denies are logged as dry run violations.
- **Access levels have no dry run mode.** To test a change to an access level, create a new access level with the intended change and attach it to the perimeter's dry run configuration.
- If problems cannot be resolved, a perimeter can stay dry run only and be used purely for monitoring.
W: Dry run with a new access level: the new restricted service and access level go into the dry run spec only, and any request they would block appears as a logged dry run violation.
X: B=Edit the enforced configuration: changes take effect on enforcement with no built-in review period, so any mistake immediately denies production traffic.
C=Access level dry run: access levels have no dry run equivalent, so an in-place edit would apply to every perimeter that uses the level.
D=Test organization: this is unnecessary effort, because dry run is designed to test new restricted services and access levels within the live environment.
T: Dry run tests perimeter changes without denials, and access level changes are tested by attaching a new level to the dry run spec.

@ GCP-PSE D2 T2.2 advanced use-case
S: A research partner's service account, which lives in the partner's own organization, must read one BigQuery dataset in a project protected by an enforced perimeter, running its query jobs in that same project, and nothing else. The partner's callers come from changing cloud IP addresses. What is the most precise configuration?
A: An ingress rule naming that service account, with BigQuery read methods and only the project that holds the dataset as its target
B: An access level for the partner's IP ranges attached to the perimeter, because IP-based admission is the finest control available
C: A perimeter bridge between the perimeters of the two organizations, because bridges are the supported way to share across organizations
D: A second perimeter for the partner containing the project, so both organizations share one security boundary and one policy
K: A
G: ## Ingress rules versus access levels
An **ingress rule** allows an API client outside the perimeter to reach resources inside it. Its `from` block names identities (or an identity type), sources (an access level, a project or VPC network, a Private Service Connect endpoint); its `to` block names services, methods or permissions, and target resources.
- Ingress rules can be narrowed by identity, method and target project, so they are far more granular than an access level, which mostly admits by IP range, device or geography.
- Troubleshooting guidance in the documentation favours ingress rules over access levels for the same reason.
- Ingress and egress rules replace many cases that previously needed perimeter bridges.
- Perimeter bridges cannot include projects from different organizations.
## Applying it here
Only one dataset is meant to be shared, so the rule should list the partner identity, the read methods, and the owning project.
W: Identity-based ingress rule: it grants that one service account only the BigQuery read operations against the one project, regardless of the source IP address.
X: B=IP access level: the partner's addresses change, and an IP-level admission would admit any identity and any operation from those addresses.
C=Perimeter bridge: bridges cannot span organizations, and they grant broad bidirectional access to the services in both projects.
D=Shared perimeter: it would put the partner's project under the company's boundary and does not limit access to one dataset or one identity.
T: For narrow cross-boundary access, write an ingress rule on identity, method and target project rather than an IP access level.

@ GCP-PSE D2 T2.2 advanced troubleshooting
S: An analyst in a project outside an enforced perimeter runs a BigQuery query job in that outside project against a dataset in a project inside the perimeter. An ingress rule for the analyst was added, yet the query is still denied. Which TWO changes are needed? (Select TWO)
A: Keep the ingress rule that lets the analyst's identity call BigQuery in the perimeter project
B: Add an egress rule that allows the BigQuery job project outside the perimeter to be used with the dataset inside it
C: Add the analyst's project as a service project of the perimeter project through a Shared VPC attachment
D: Replace the ingress rule with an access level on the analyst's device, because ingress rules cannot match user identities
E: Grant the analyst the BigQuery Admin role in the perimeter project, because IAM roles are evaluated before the perimeter

Direction in VPC Service Controls refers to the request, not to the data flow. A call that touches both a resource inside the perimeter and a resource outside it can need both rule types:
- An **ingress rule** admits the client that is outside the perimeter.
- An **egress rule** admits the use of the outside resource, because the request involves a resource inside the perimeter together with one outside it.
In the documentation's example, a BigQuery client outside the perimeter running a job in an outside project against an inside dataset needs both. The audit log shows both ingress and egress violations when only one is configured.
W: A=Ingress rule: the analyst is a client outside the perimeter, so an ingress rule for that identity and service is still required.
B=Egress rule: the query job lives in a project outside the perimeter while the dataset is inside, so an egress rule must allow that combination of resources.
X: C=Shared VPC attachment: Shared VPC attachment does not change which perimeter a project is in and is not involved in this API request.
D=Access level instead: ingress rules can match identities directly, and a device-based level does not remove the need for an egress rule.
E=BigQuery Admin: IAM grants permission, but VPC Service Controls is an independent layer, and the request is denied regardless of the role.
T: A request mixing an inside and an outside resource may need both an ingress rule and an egress rule.

@ GCP-PSE D2 T2.2 applied troubleshooting
S: A perimeter protects the service projects of a Shared VPC deployment. After enforcement, VMs in some service projects lose access to the Cloud Storage API, and requests show up as violations. The host project that owns the Shared VPC network sits outside every perimeter. What should the security engineer do?
A: Add the host project to the same perimeter as the service projects, so that the network and its workloads share one boundary
B: Remove the service projects from the perimeter and protect them only with firewall rules on the host project's network
C: Add each service project to its own perimeter, and connect the perimeters with bridges so that each pair can communicate
D: Create egress rules from the perimeter to the host project, since the host project is a Google-managed service project
K: A
G: ## Perimeters and Shared VPC
VPC Service Controls evaluates the network a request comes from as well as the resources it touches. In Shared VPC, the VPC network is owned by the **host project**, even though the VMs belong to service projects.
- Google recommends including the Shared VPC host project in the same perimeter as the service projects that use its network; some services fail when the two are separated.
- With the host project outside, requests from VMs on that network are attributed to a network that is outside the perimeter, which shows as a network violation.
- Rules such as ingress and egress can bridge gaps, but the clean design is one perimeter around the host and service projects.
W: Host and service projects in one perimeter: the VMs' requests originate from the host project's network, so putting it in the perimeter removes the cross-boundary violation.
X: B=Firewall rules only: firewall rules do not control access to Google API resources, so dropping the perimeter removes the exfiltration protection.
C=One perimeter per service project: this multiplies boundaries and the shared network is still outside them, so the violations remain.
D=Egress to a host project: the host project is a customer project, not Google-managed, and egress rules would open an exfiltration path rather than fix the design.
T: Keep a Shared VPC host project in the same perimeter as its service projects.

@ GCP-PSE D2 T2.2 applied troubleshooting
S: A developer's VM in project dev-sandbox, which is outside any perimeter, cannot read a bucket in the perimeter-protected project prod-data.
