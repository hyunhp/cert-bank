@ GCP-PSE D1 T1.1 advanced use-case
S: A company enabled SAML single sign-on between its identity provider (IdP) and Cloud Identity. The IdP enforces multi-factor authentication for every user. A review finds that the three super admin accounts still sign in with Cloud Identity passwords and are never challenged by the IdP. Which TWO changes best protect the super admin accounts? (Select TWO)
A: Enforce Google 2-step verification for all super admin users, preferably with security keys
B: Add a network mask to the single sign-on settings so that sign-ins from the office network are sent to the IdP
C: Move the super admin users into a dedicated organizational unit whose SSO profile has single sign-on turned off
D: Ask the IdP team to extend its multi-factor policy to the super admins, since Google redirects every user to the IdP
E: Turn off 2-step verification for the super admins so that it cannot conflict with the second factor of the IdP
K: A,C
G: ## How super admins behave under SSO
When single sign-on is enabled for a Cloud Identity account, service-provider-initiated sign-in sends every user to the IdP **except super admins**. Super admins are prompted for a Google password instead. They may still use SSO when the sign-in starts at the IdP (IdP-initiated sign-in).
## Consequences for security
- Any multi-factor policy configured at the IdP does not apply to a super admin who signs in with a password, so Google's own 2-step verification must protect these accounts.
- If you do not plan to use IdP-initiated sign-in for super admins, a dedicated organizational unit with an SSO profile that disables SSO removes that path. If you do use it, enforce additional (post-SSO) verification so that 2-step verification still applies.
- Network masks are not a control for this: they only decide which IP ranges are subject to SSO and let users sidestep the IdP's multi-factor authentication by changing location.
W: A=Google 2-step verification: super admins authenticate with Google passwords, so the second factor has to be enforced by Google itself; security keys resist phishing and keep the accounts safe even if the IdP is compromised.
C=Dedicated OU without SSO: assigning an SSO profile that disables single sign-on to an OU of super admins closes the IdP-initiated sign-in path, so the only way in is the password plus 2-step verification.
X: B=Network mask: a mask only chooses which source addresses are subject to SSO and does not change the super admin exemption; it also lets users bypass the IdP's multi-factor authentication by changing location or using a VPN.
D=Extending the IdP policy: Google never redirects super admins to the IdP for service-provider-initiated sign-in, so no IdP policy is evaluated for their password sign-ins.
E=Turning off 2-step verification: this removes the only second factor that applies to password sign-ins and makes the most powerful accounts weaker.
T: Super admins bypass the IdP, so protect them with Google 2-step verification and, where IdP-initiated sign-in is not needed, an OU whose SSO profile turns SSO off.

@ GCP-PSE D1 T1.1 advanced troubleshooting
S: A company uses IdP-initiated SSO. The super admin dana-admin@example.com exists only in Cloud Identity: the IdP has no matching user and the account has no 2-step verification. An IdP operator who can create users is suspected of creating an IdP user with the same email address and signing in as that super admin. Which remedy addresses the root cause?
A: Remove the password of the super admin account so that only the IdP can authenticate it from now on, including the break-glass case
B: Rename the super admin account every quarter and keep the new name secret from all of the IdP operators and their managers
C: Keep all Cloud Identity identities, admin accounts included, a subset of the IdP identities, and enforce post-SSO verification for super admins
D: Set a network mask on the SSO configuration so that sign-ins from the office network are always sent to the IdP
K: C
G: ## Name squatting against federated accounts
Federation trusts the **email address** in the SAML assertion. If a Cloud Identity user has no counterpart in the IdP, anyone able to create an IdP user with that address can sign in as the Cloud Identity user through IdP-initiated SSO. For a super admin this is a path to the organization.
## Mitigation
- Make the set of Cloud Identity identities a **subset** of IdP identities: create admin identities in the IdP too and let the IdP (or HRIS) provisioning flow manage the whole lifecycle.
- Turn on additional SSO verification and 2-step verification for super admins so a forged IdP sign-in is still challenged.
W: Subset of IdP identities plus post-SSO verification: when every Cloud Identity user is created, suspended and deleted by the IdP lifecycle, nobody can create an unrelated IdP user that collides with an admin, and the extra verification still challenges a sign-in that comes from the IdP.
X: A=Removing the password: this does not stop IdP-initiated SSO for a squatted identity and also removes the break-glass path if the IdP fails.
B=Renaming the account: obscurity does not fix the missing IdP counterpart, and the next IdP user with the new address can squat it again.
D=Network mask: a mask limits which users are subject to SSO and weakens multi-factor enforcement; it does not tie Cloud Identity users to IdP users.
T: Keep Cloud Identity identities a subset of IdP identities and require post-SSO verification for super admins to defeat name squatting.

@ GCP-PSE D1 T1.1 applied use-case
S: A company provisions Cloud Identity users from its IdP, but the offboarding process only disables the user in the IdP. Weeks after a departure, an audit finds that the former engineer's laptop still holds working gcloud credentials and that the account still receives budget alert emails. Which change fixes the process?
A: Suspend the matching Cloud Identity user whenever the IdP user is suspended, ending sessions and invalidating tokens
B: Shorten the IdP session to one hour so that the departed engineer's laptop reauthenticates more often
C: Have administrators remove the departed user's IAM role bindings in every project when HR announces a departure
D: Delete the Cloud Identity user in the same minute that the IdP user is disabled, before any retention period applies
K: A
G: ## Why disabling the IdP user is not enough
Suspending the user at the IdP stops new SSO sign-ins, but the Cloud Identity user still exists. An active browser session and OAuth tokens that were already issued keep working, notifications such as budget alerts keep arriving, and super admins or users outside a network mask can still sign in with a password.
## Suspension propagation
Suspending the Cloud Identity user terminates sessions, invalidates tokens and revokes access, and it is non-destructive: data, licenses and IAM role bindings stay in place until the account is reactivated or deleted. Automate this so the IdP is the source of truth for the whole lifecycle.
W: Propagating suspension: the provisioning integration mirrors every suspension and reactivation to Cloud Identity, so sessions end and tokens are invalidated at the same time as the IdP account is disabled.
X: B=Shorter IdP session: it only affects future SSO sign-ins and does not revoke sessions or tokens already issued by Google, or stop notifications.
C=Manual binding cleanup: roles are spread across many resources, the cleanup depends on human memory, and it leaves the live account and its tokens untouched.
D=Immediate deletion: deleting is destructive and may permanently remove associated data before compliance retention ends; suspension is the safe first step.
T: Mirror IdP suspensions into Cloud Identity automatically; suspension ends sessions and tokens without destroying data.

@ GCP-PSE D1 T1.1 applied use-case
S: HR deletes the IdP account when an employee leaves, but the Cloud Identity user is never removed. Months later, a new hire with the same name gets the same primary email in the IdP, signs in to Google, and inherits the former employee's group memberships and files. Compliance also requires keeping a leaver's data for 90 days. What should the lifecycle automation do when a user is deleted in the IdP?
A: Reset the password of the Cloud Identity user so that the next owner of the address must choose a new one on first login
B: Delete the Cloud Identity user immediately, accepting that Google may permanently remove its data
C: Leave the Cloud Identity user active but remove it from all groups so that nothing is inherited
D: Suspend the Cloud Identity user, rename its primary email to a unique obsolete name, and delete it after retention
K: D
G: ## Orphaned Cloud Identity users
Federation treats two users as the same person if they map to the same primary email address. A leaver whose IdP account is deleted but whose Cloud Identity user remains therefore becomes an orphan. If the IdP later reuses the name, the new user maps to the old account and inherits its data, settings and permissions.
## Safe deletion patterns
- Keep the user suspended in the IdP for the retention period and delete both after it ends.
- Or, when deleting in the IdP, suspend the Cloud Identity user and rename it (for example `obsolete-yyyymmdd-alice@example.com`) so the address is free, then delete it when the retention period has elapsed.
W: Suspend, rename and delete later: renaming frees the original address so a new hire cannot map to the old account, and suspension keeps the data for the 90-day requirement before the final deletion.
X: A=Password reset: with SSO the identity is matched by email address, so the new hire still maps to the old account and inherits it regardless of passwords.
B=Immediate deletion: it removes the collision but is destructive and can permanently delete data that the 90-day retention rule requires to keep.
C=Removing group memberships: the account, its files and its direct IAM bindings stay in place, and the collision on the email address remains.
T: Rename and suspend a leaver's Cloud Identity user for the retention period, then delete it, so a reused name never maps to the old account.

@ GCP-PSE D1 T1.1 advanced troubleshooting
S: A company syncs two Active Directory forests into one Cloud Identity account, using one Google Cloud Directory Sync (GCDS) instance per forest. After rollout, each instance suspends the users that the other instance created, and administrators fear that the user configured for GCDS could also be suspended. Which configuration fixes this?
A: Add exclusion rules for the other forest's users and groups to each instance, and keep domain admins protected from deletion
B: Set both instances to delete every Google user missing from their own directory, since the other recreates them next run
C: Enable two-way synchronization so that each instance reads the users that the other one created back into its own directory
D: Move both forests behind one LDAP query by merging their search bases, and remove the deletion policy so that nothing is ever suspended
K: A
G: ## What GCDS does
GCDS reads an LDAP directory such as Active Directory and uses the Directory API to **add, update, suspend or delete** users and groups in Cloud Identity. It is **one-way**: the directory is the source of truth and edits made in Cloud Identity are not copied back.
## Several instances, one account
- By default GCDS considers any Cloud Identity user it did not find in its own directory as deleted and applies the deletion or suspension policy.
- With several instances, each one needs **exclusion rules** (for example by OU path or by UPN domain) for the users and groups that another source manages.
- Keep the deletion/suspension policy option that protects Google domain admins not found in LDAP, so the account used to configure the tool is not suspended.
W: Exclusion rules plus admin protection: each instance then ignores the population owned by the other forest, while the admin safeguard stops the sync from suspending the configuration super admin.
X: B=Deleting everything missing: this causes a repeated delete and recreate cycle, loses user data and group memberships at every run, and risks deleting protected accounts.
C=Two-way synchronization: GCDS is one-way from the directory into Cloud Identity, so it cannot read users back into Active Directory.
D=Merging search bases and removing deletion: this changes the directory design to hide a configuration problem and stops departed users from ever being suspended.
T: With multiple GCDS instances, give each exclusion rules for users it does not own and keep domain admins protected from the deletion policy.

@ GCP-PSE D1 T1.1 applied use-case
S: Access to a documentation project must be granted to everyone whose HR job-role attribute is Technical Writer. Membership must follow the directory attribute automatically as people change role, and the platform team wants to manage the group through the Cloud Identity Groups API without maintaining member lists. Which group type fits?
A: A standard Google Group whose owners add and remove writers as roles change
B: A locked group, so that only administrators can edit the member list
C: A dynamic group whose membership is defined by a query on the job-role attribute
D: Individual IAM bindings for each writer, regenerated by a nightly export from the HR system
K: C
G: ## Group types in Cloud Identity
The Cloud Identity Groups API manages several kinds of groups:
- **Google Groups** (the default): a mailing-list style group that can also be used in IAM.
- **Dynamic groups**: membership is managed automatically from a query on user attributes such as job role or location.
- **Security groups**: a group used specifically to control access to organizational resources.
- **Locked groups**: a group that only administrators can edit, used to prevent drift from an external source or to protect sensitive groups.
## Choosing
When membership must follow a directory attribute with no manual list, a dynamic group is the type that does it. Granting roles to the group rather than to individual users keeps IAM policies short and auditable.
W: Dynamic group: the membership query on the job-role attribute adds and removes users automatically, so the IAM binding on the group always matches HR data without manual upkeep.
X: A=Standard Google Group: its owners must maintain membership by hand, which is the manual upkeep that the requirement wants to avoid.
B=Locked group: locking restricts who can edit attributes and members, but it does not compute membership from an attribute.
D=Individual bindings: per-user bindings multiply policy entries and go stale between exports, which is the opposite of group-based access.
T: Use a dynamic group when membership should follow a user attribute automatically, and grant IAM roles to the group.

@ GCP-PSE D1 T1.1 applied troubleshooting
S: The group gcp-network-admins is populated from the IdP, yet group owners also edit it directly in the Admin console. IdP and Cloud Identity memberships have drifted and some people hold network access that the IdP does not list. Which setting prevents this drift?
A: Lock the group, so that only authorized administrators can change its core attributes and memberships
B: Restrict who may post to the group so that owners can no longer send messages to its members
C: Replace the group with individual IAM bindings that an administrator reviews every quarter
D: Convert the group to a dynamic group whose query matches every user in the organizational unit
K: A
G: ## Keeping a synced group in step with its source
A group managed by an external source is only trustworthy if nobody can change it elsewhere. A **locked group** restricts edits to core attributes and memberships to authorized administrators, such as those holding a Groups Admin or Groups Editor role, while owners and managers can still adjust ordinary settings like moderation.
## Why other controls do not help
Posting permissions only control messages, not membership. Dynamic groups compute membership from a query rather than from the IdP. Direct bindings give up the group indirection altogether.
W: Locking the group: edits to membership are limited to authorized administrators, so manual changes by owners stop and the provisioning flow remains the only writer.
X: B=Posting restrictions: these control who can send messages and have no effect on who can add members.
C=Individual bindings: they remove the group abstraction, multiply policy entries, and a quarterly review still leaves long drift windows.
D=Dynamic group: membership would be calculated from an organizational query instead of the IdP list, which changes the source of truth rather than protecting it.
T: Lock groups that mirror an external source so that only administrators, and not owners, can edit their membership.

@ GCP-PSE D1 T1.1 advanced use-case
S: A company adds a workforce identity pool provider for a public SaaS identity provider that uses one issuer URL for all customer tenants, so that partner staff can sign in with their own accounts. A penetration test shows that a user from an unrelated customer tenant can present a token that the pool accepts. What fixes this?
A: Map google.subject to the email claim so that unrelated tenants produce a different subject
B: Add a provider attribute condition that accepts only tokens whose tenant or organization claim matches the company's tenant
C: Rely on the issuer URL check, since Google verifies that the token was issued by the provider
D: Create a second pool for the same provider and split users between the two pools to dilute the exposure of each pool
K: B
G: ## Multi-tenant IdPs and workforce pools
Workforce Identity Federation keeps no user directory; it uses claims-based identities. Two tokens from the same issuer that map to the same `google.subject` are treated as the same person, and the issuer URL is how Google decides which IdP signed the token.
## The multi-tenant trap
Some IdPs use one issuer URL for every customer. The issuer then identifies the whole provider, not your tenant, so a valid token from any tenant passes the issuer check. You must add an **attribute condition** (a CEL expression) that checks a tenant or organization claim and rejects everything else. The same technique also stops credentials meant for another platform from being replayed (confused deputy).
W: Tenant attribute condition: the condition is evaluated on every token, so a correctly signed token from a different tenant fails the condition and cannot sign in.
X: A=Mapping the subject to email: the subject only names the user; it does not test which tenant issued the token, and mutable emails make poor identifiers.
C=Trusting the issuer check: the issuer URL is shared by all tenants, which is the reason the foreign token passes.
D=Splitting into two pools: both pools would still trust the same shared issuer without a tenant check, and the split adds administration without adding restriction.
T: For IdPs with a shared issuer URL, always add an attribute condition that pins the tenant or organization.

@ GCP-PSE D1 T1.1 applied troubleshooting
S: A workforce pool maps google.subject to the IdP email attribute. During a rebrand, the IdP team changes every mailbox to a new domain. Afterwards, everyone can still sign in, but each user has lost all access that was granted with principal identifiers for the old addresses. What explains this and what is the lasting fix?
A: The provider was deleted in the rebrand, so engineers should recreate it with the same name
B: Users must reauthenticate once, after which Google rebuilds their old principal identifiers from the audit logs
C: Federated sessions cache the old subject for 24 hours, so the access returns once the cache expires
D: google.subject is the key in bindings and the mutable email changed it; map an immutable identifier and recreate the grants
K: D
G: ## google.subject is the identity key
In Workforce Identity Federation, `google.subject` is required, is written to Cloud Audit Logs as the principal, and appears in `principal://` bindings. Google stores no user object, so the binding only matches a token whose mapped subject is identical.
## Choosing the attribute
Map `google.subject` to a value that never changes (for example the stable `sub` claim or an immutable object ID), not to email or a name. If the mapped value changes, the user is effectively a new principal and loses every grant. For custom attributes, prefer stable values such as a role over a free-text title.
W: Mutable subject: a changed email creates a different principal, so old bindings no longer match; remapping to an immutable identifier and re-granting restores access and prevents repeat.
X: A=Deleted provider: sign-in still works, which shows the provider exists and trusts the IdP.
B=Rebuilding from logs: Google does not translate old principal identifiers; bindings are matched literally to the subject value.
C=Cache of 24 hours: there is no such subject cache; the grants never match the new value.
T: Map google.subject to an immutable IdP identifier, because bindings are matched to its literal value.

@ GCP-PSE D1 T1.1 applied troubleshooting
S: Users of a workforce pool sign in successfully, except a few who belong to a very large number of IdP groups. The provider maps google.groups to the full groups claim, and those users' sign-in attempts fail. How should the identity architect fix this?
A: Request a higher limit for groups per user before the next sign-in attempt
B: Map only the groups that are used in IAM bindings, with an expression that filters the claim
C: Switch the failing users to Google passwords by creating them manually in Cloud Identity
D: Map the same claim to google.subject so that the groups are carried in the user identifier
K: B
G: ## Groups in workforce federation
The optional `google.groups` attribute is built from a CEL expression that returns an array of strings. IAM `principalSet` bindings on a group grant access to every member of it.
## Practical limits
- A user who belongs to more than about 400 groups cannot sign in, so only groups used for access decisions should be mapped. Group names should also stay short.
- Because every member of a mapped group receives the access, only authorized administrators should be able to change the membership of those groups at the IdP.
W: Filtering the mapping: a CEL expression can keep only the groups used by IAM policies, which brings each user under the limit and also reduces the exposure of unrelated groups.
X: A=Requesting a higher limit: the number of mapped groups per sign-in is a fixed design limit that is handled by narrowing the mapping, not by a quota request.
C=Manual Cloud Identity users: this abandons federation, creates accounts to maintain, and still leaves the oversized mapping design in the pool.
D=Mapping groups to the subject: google.subject must be a single stable user identifier; stuffing groups into it breaks bindings and logs.
T: Map only the IdP groups used by IAM into google.groups, since users in too many mapped groups cannot sign in.

@ GCP-PSE D1 T1.1 applied troubleshooting
S: Security shortened the Google session length to 8 hours for SSO users, but employees report that they almost never see a login prompt after the session expires. The IdP keeps its own sessions for 30 days. How can security make the shorter session meaningful?
A: Lengthen the Google session to 30 days so that both sessions expire at the same moment
B: Add a network mask to the SSO settings so that expired sessions are verified against office addresses
C: Disable SSO for all users so that Google passwords decide when a prompt appears
D: Set the IdP session shorter than the Google session, so a new Google sign-in forces new IdP authentication

After SSO, the user has a **Google session** (by default 14 days for Google services; a shorter value is configurable, and a separate Google Cloud session length covers the console, gcloud and API clients) and usually also a session at the IdP.
## Silent re-authentication
When the Google session ends, the user is redirected to the IdP. If the IdP session is still alive, the IdP signs the user back in without a prompt, so shortening only the Google session achieves little. Make the IdP session shorter than the Google session so that expiry of Google forces a real authentication.
W: Shorter IdP session: when Google redirects an expired session to an IdP session that has already ended, the user must enter credentials and satisfy MFA again.
X: A=Equal 30-day sessions: this lengthens exposure and removes the intended 8-hour control.
B=Network mask: a mask decides which networks use SSO and can weaken MFA; it does not make the IdP prompt again.
C=Disabling SSO: it throws away centralized authentication and MFA at the IdP to solve a session configuration issue.
T: Keep the IdP session shorter than the Google session, or shortened Google sessions are renewed silently.

@ GCP-PSE D1 T1.2 advanced use-case
S: A company deploys from GitHub Actions to Google Cloud with Workload Identity Federation. Any workflow in the company's GitHub organization may deploy to the development project, but only the repository payments-infra may deploy to production. All workflows share one provider. Which design enforces this?
A: Restrict the provider by repository owner, map attribute.repository, and bind the production account to that repository's principal set only
B: Bind the production service account to the principal set for the whole organization and rely on developers to keep production workflows in the right repository
C: Create a service account key for payments-infra, store it as a repository secret, and use it only in the production workflow
D: Place the production service account in the development project so that its deployers can also be limited with the development permissions
K: A
G: ## Two layers of control
Workload Identity Federation controls access in two places:
- The **provider attribute condition** (a CEL expression on the incoming token) decides which external identities can authenticate to the pool at all. For GitHub, a multi-tenant issuer, you must at least restrict the organization (`assertion.repository_owner`).
- The **IAM binding** on a service account or resource decides what each accepted identity may do. A `principalSet://.../attribute.repository/<repo>` binding grants only workflows from that repository.
## Applying it
Map the attributes you need (such as `attribute.repository`) and grant `roles/iam.workloadIdentityUser` on the production service account to the repository's principal set only. A broader org-wide binding would allow any repository to deploy to production.
W: Condition plus narrow binding: the condition keeps other organizations out, and the principal set on one repository means no other repository in the organization can impersonate the production service account.
X: B=Organization-wide binding: any repository, including a new or compromised one, could obtain production credentials.
C=Key as a secret: this reintroduces a long-lived credential that can be copied and read from workflow logs, which federation is meant to remove.
D=Moving the account: project placement does not limit which GitHub workflows can impersonate it; the binding does.
T: Gate GitHub federation with a provider condition on the organization and per-repository principal set bindings on the target service account.

@ GCP-PSE D1 T1.2 advanced use-case
S: A regulated company hosts GitHub Enterprise Server inside its private network. Its OIDC discovery URL is unreachable from the internet and regulations forbid publishing it. Pipelines must deploy to Google Cloud without any service account keys. Which approach works?
A: Create a workload identity pool OIDC provider and upload the issuer's JSON Web Key Set directly to it
B: Publish the discovery document through a public load balancer and restrict it by source address
C: Store a service account key in Secret Manager and read it from the pipeline runner
D: Create a workforce identity pool so that pipelines sign in like employees using the console
K: A
G: ## Federating a private issuer
Workload Identity Federation normally verifies an OIDC token by fetching the issuer's public keys from its discovery endpoint. When the issuer has **no public OIDC endpoint** (typical for self-hosted GitHub Enterprise or Terraform), you can upload the **JSON Web Key Sets (JWKS)** directly to the provider. The pool then validates token signatures locally, so the issuer never has to be reachable from the internet.
## Operations
You must refresh the uploaded keys when the issuer rotates its signing keys.
