@ GCP-PSE D2 T2.3 advanced use-case
S: A insurer's on-premises batch servers upload files to Cloud Storage and query BigQuery over HA VPN tunnels, never over the internet. The security team also runs VPC Service Controls around the data projects and wants the servers to be unable to reach any Google API that VPC Service Controls cannot protect. Which design meets this?
A: Resolve all Google API names on premises to the restricted.googleapis.com addresses, and advertise that range from the Cloud Router
B: Resolve all Google API names on premises to the private.googleapis.com addresses, and advertise that range through the Cloud Router so every Google API stays reachable over the tunnels
C: Give each on-premises server a public route to Google APIs, then add VPC Service Controls ingress rules that deny any API request arriving from outside the perimeter
D: Enable Private Google Access on the VPC subnets that terminate the tunnels, because that setting also covers requests that originate in the on-premises network
K: A
G: ## Private Google Access for on-premises hosts
On-premises systems can reach Google APIs privately by sending the traffic to a special virtual IP range over Cloud VPN or a VLAN attachment. Two domains exist, and the one you point DNS at decides which APIs are reachable:
- `private.googleapis.com` (`199.36.153.8/30`) reaches most Google APIs, including ones that do not support VPC Service Controls.
- `restricted.googleapis.com` (`199.36.153.4/30`) reaches only the APIs that VPC Service Controls supports, so a client cannot fall back to an API outside the perimeter model.
## What is needed end to end
- On-premises DNS must resolve the API names (typically a `*.googleapis.com` CNAME) to the chosen domain, and on-premises routes must send that range into the tunnel.
- The VPC network needs routes for the range, and the Cloud Router advertises it back to on-premises as a custom advertised route.
## Applying it here
The requirement "cannot reach APIs that VPC Service Controls cannot protect" is exactly what the restricted VIP enforces, while keeping all traffic on the private tunnels.
W: Restricted VIP with DNS and route advertisement: the restricted range only serves VPC Service Controls-supported APIs, so unprotected APIs become unreachable, and the advertised route keeps the traffic inside the tunnels.
X: B=Private VIP: it reaches most Google APIs regardless of whether VPC Service Controls supports them, so it does not prevent use of APIs outside the protection model.
C=Public route plus ingress rules: sending traffic over the internet breaks the stated private-path requirement, and ingress rules only evaluate requests to protected services, not APIs outside the perimeter.
D=Subnet Private Google Access flag: that setting applies to VM clients inside the subnet; on-premises hosts need DNS and routes to a special VIP instead.
T: For on-premises hosts under VPC Service Controls, point DNS at restricted.googleapis.com and route its range over the hybrid link.

@ GCP-PSE D2 T2.3 applied troubleshooting
S: After a migration, on-premises clients that use Private Google Access for on-premises hosts show intermittent failures: some Cloud Storage calls succeed and others time out. Investigation shows the on-premises DNS zone for googleapis.com holds an A record for restricted.googleapis.com, but the CNAME and a manually added A record for storage.googleapis.com use addresses from the private.googleapis.com range. Routes and tunnels are healthy. What should the engineer do?
A: Point every record in the zone at one virtual IP range, either restricted or private, and do not mix addresses from both
B: Add a second Cloud Router in another region so that both address ranges are advertised over separate tunnels
C: Raise the TTL on the googleapis.com records so that clients cache one answer and always use the same address
D: Move the manual storage.googleapis.com record to a public DNS zone so that the resolver chooses the nearest address
K: A
G: ## One virtual IP range per resolution path
The `private.googleapis.com` and `restricted.googleapis.com` ranges serve different sets of services. When DNS hands a client addresses from both, the client's connections are served by whichever range the answer happened to contain, so a request for a service that the restricted range does not serve fails intermittently. Google's guidance is to configure DNS for exactly one of the two domains and not mix addresses.
## Diagnosing
- Healthy routes and tunnels with failures that vary by hostname or by lookup point to DNS content, not the network path.
- The fix is a single consistent zone: the `A` records for the chosen VIP and a `*.googleapis.com` CNAME to it.
W: One VIP range everywhere: removing the mixed answers makes every lookup land on the range that the security design chose, which ends the intermittent behaviour.
X: B=Second Cloud Router: more routers do not change which service set a destination range offers, and the tunnels are already healthy.
C=Higher TTL: caching only freezes whichever mixed answer a client received, so some clients stay broken for longer.
D=Public DNS record: a public answer would send the client over the internet, defeating the private-path purpose.
T: Configure DNS for either the private or the restricted VIP, never both, or lookups fail unpredictably.

@ GCP-PSE D2 T2.3 applied tradeoff
S: A media firm is allowed to use only Google APIs that VPC Service Controls supports in its regulated analytics environment, but its marketing environment, connected to the same data center, must also call Google Maps Platform APIs from on premises. Which approach respects both rules with the least duplication?
A: Use the restricted range for regulated resolvers and the private range for marketing resolvers, each in its own DNS scope
B: Use restricted.googleapis.com for all on-premises resolvers, since the stricter range also reaches the Google Maps Platform APIs
C: Use private.googleapis.com for all on-premises resolvers and rely on a VPC Service Controls perimeter to block unsupported services
D: Use public Google API addresses for marketing and the restricted range for analytics, since the private range excludes Maps APIs
K: A
G: ## Choosing the VIP per environment
The restricted range exists to keep clients inside the set of services that VPC Service Controls can protect. The private range serves a broader set, including Google Maps Platform, Google Ads and many other APIs, but offers no such guardrail. The choice is made by DNS, so it can differ per client population as long as each population resolves consistently to one range.
## Applying it here
The regulated environment gets the restricted range; the marketing environment gets the private range, using separate DNS scopes or resolvers for the two populations. Both stay on the private hybrid path.
W: Per-environment VIP choice: restricted for regulated clients enforces the supported-services-only rule, and private for marketing preserves Maps access, with no public path.
X: B=Restricted for everyone: the restricted range denies services that VPC Service Controls does not support, which includes the Maps Platform APIs, so marketing breaks.
C=Private for everyone with a perimeter: a perimeter only governs supported services, so analytics clients could still reach unsupported APIs through the broader range.
D=Public addresses for marketing: the private range does serve these APIs, so leaving the private path is unnecessary and weakens the stated design.
T: Select the private or restricted VIP per client population through DNS, based on whether unsupported APIs must be blocked.

@ GCP-PSE D2 T2.3 applied troubleshooting
S: To remove an exfiltration path, a network engineer deleted the default 0.0.0.0/0 route from a VPC network that hosts private VMs with no external IP addresses. Since then, those VMs can no longer call Google APIs, even though DNS already maps googleapis.com names to the restricted.googleapis.com addresses. What is the minimal change that keeps the internet closed while restoring API access?

B: Re-create the 0.0.0.0/0 route and add an egress deny firewall rule for everything except Google API names
C: Create a Cloud NAT gateway for the subnets so that the VMs can reach Google APIs through translated source addresses

K: A
G: ## Reaching the virtual IPs from a VPC network
The restricted and private API ranges are routed by Google's edge, but your VPC network still needs a route that matches the destination. VMs normally rely on the default route to the default internet gateway for this. If the default route is removed, a more specific route for the VIP range with the default internet gateway as next hop restores access to just that range.
## Why this keeps the internet closed
- The route covers only `199.36.153.4/30`, not the whole internet.
- Traffic to that range stays on Google's network and only reaches the services that VPC Service Controls supports.
W: Specific route to the VIP range: a custom static route with the default internet gateway as next hop gives the VMs a path to only the restricted range, so nothing else becomes reachable.
X: B=Default route back plus egress rules: this reopens a broad route that the engineer removed on purpose, and relies on firewall rules that cannot match Google API names by hostname.
C=Cloud NAT: the VMs have no external IPs and Cloud NAT needs a route to the internet anyway; it is also not how the restricted range is reached.
D=Peering to Google services: VPC Network Peering is not used for Google APIs, and no such peering exists for the restricted VIP.
T: With the default route removed, add a specific route for the restricted or private VIP range using the default internet gateway.

A Private Service Connect (PSC) endpoint is a forwarding rule with an internal IP address from your VPC network that maps to a bundle of Google APIs. You can create as many as you need, name them in the `p.googleapis.com` zone, and reach them from on-premises hosts over Cloud VPN or VLAN attachments.

- Compared with Private Google Access, you pick the IP address and get a per-endpoint resource, so routing and monitoring can differ by team.
W: PSC endpoints for Google APIs: each endpoint is a customer-owned internal IP, can be reached from on premises, and the vpc-sc bundle limits regulated units to protectable services.

@ GCP-PSE D2 T2.3 applied troubleshooting
S: A SaaS vendor publishes a managed service behind a Private Service Connect service attachment that explicitly accepts connections only from approved customer projects. A new customer creates an endpoint in its VPC network that targets the attachment, but the connection stays in the Pending state indefinitely. What should the vendor check first?
A: Whether the customer's project is on the accept list and whether connection capacity remains
B: Whether a VPC Network Peering connection exists between the two VPC networks
C: Whether the customer's subnet range overlaps with the vendor's NAT subnet and must be renumbered

G: ## Connection preference on a service attachment
A published service chooses either to accept all connections automatically or to accept only consumers on its accept list, which can name projects, VPC networks, or individual endpoints. A connection that is not permitted by the list, or that exceeds the attachment's connection limit, stays `Pending` until the cause is resolved. A consumer on the reject list, or a producer organization policy block, gives `Rejected` instead.
## Security view
- Explicit approval is the recommended setting because it limits who can reach the service.
- Changes to the lists affect new or pending connections; existing ones continue unless connection reconciliation is enabled.
W: Accept list and connection limit: a pending state means the service attachment has not approved the connection, which happens when the consumer is not listed or the limit is reached.
X: B=Peering connection: Private Service Connect does not rely on VPC Network Peering between the two networks, so its absence is irrelevant.
C=Overlapping ranges: Private Service Connect translates addresses through the producer's NAT subnet and is designed to work with overlapping consumer and producer ranges.
D=Service Directory namespace: namespaces matter for automatic DNS of Google API endpoints and do not govern approval of a published-service connection.
T: A Pending Private Service Connect connection means approval or capacity is missing on the producer's service attachment.

@ GCP-PSE D2 T2.3 advanced use-case
S: A healthcare company publishes records through a regional managed service that it accesses via Private Service Connect. The security team wants to terminate TLS on its own certificate and domain in front of the service, apply Cloud Armor and centralised logging to the traffic, and fail over between two regions under its own control. Which Private Service Connect type should it use?
A: Private Service Connect backends, using network endpoint groups behind an internal or external Application Load Balancer
B: Private Service Connect endpoints, because a forwarding rule gives the same control over certificates and fail over
C: Private Service Connect interfaces, because they let the consumer terminate certificates for the producer's service
D: Private services access, because its allocated range provides load balancer features for managed services
K: A
G: ## Endpoints, backends and interfaces
Private Service Connect has three consumer-side shapes:
- **Endpoints**: a forwarding rule with an internal IP that gives layer 4 connectivity to a service.
- **Backends**: a network endpoint group that lets a Google Cloud load balancer send traffic to a service attachment or a Google API. Because the load balancer is yours, you get custom domains and certificates, consumer-controlled failover between regions, and central security configuration.
- **Interfaces**: a network interface in the producer's service that lets the producer initiate connections into the consumer network.
## Applying it here
Needs such as owning the certificate, using Cloud Armor, and controlling failover are load balancer features, which only backends provide.
W: PSC backends with a load balancer: the consumer-side load balancer allows customer-owned domains and certificates, security policy attachment and regional failover control in front of the managed service.
X: B=Endpoints: they give layer 4 connectivity only, with no certificate termination, no Cloud Armor and no failover logic.
C=Interfaces: they exist so a producer can initiate connections to the consumer's network, not for terminating consumer certificates.
D=Private services access: it connects to producer services through VPC Network Peering and an allocated range, and offers no load balancer features.
T: Choose Private Service Connect backends when you need load balancer controls in front of a managed service.

@ GCP-PSE D2 T2.3 advanced use-case
S: A retailer connects its data center to Google Cloud with Dedicated Interconnect. A new policy says all traffic between on-premises networks and VPC networks must be encrypted at the network layer from end to end, not only on the physical link. Which design meets this?
A: HA VPN over Cloud Interconnect, with IPsec tunnels established over the VLAN attachments
B: MACsec on the Interconnect circuit alone, since it encrypts traffic between the two networks
C: A second Dedicated Interconnect connection in another metro, since redundant circuits encrypt each path
D: TLS on the application load balancers, since it encrypts all packets in the VPC network at layer 3
K: A
G: ## Encryption options on Cloud Interconnect
Cloud Interconnect traffic is private but not encrypted by default. Two mechanisms exist:
- **MACsec** (IEEE 802.1AE) encrypts at layer 2 between your on-premises router and Google's peering edge router. It does not provide encryption in transit within Google.
- **HA VPN over Cloud Interconnect** builds IPsec tunnels over VLAN attachments, which gives layer 3 encryption between on-premises networks and the VPC network, with internal IPs on the VPN gateways.
Google recommends layering these, plus TLS, for stronger protection.
## Applying it here
The policy asks for network-layer, end-to-end encryption, which is IPsec.
W: HA VPN over Cloud Interconnect: IPsec tunnels over the VLAN attachments encrypt traffic at layer 3 between the networks while using the private Interconnect path.
X: B=MACsec alone: it protects only the link between the customer's router and Google's edge, so traffic is not encrypted beyond that point.
C=Second circuit: redundancy improves availability, but each circuit carries traffic unencrypted unless an encryption method is enabled.
D=TLS on load balancers: it protects those application flows at the application layer and does not cover all traffic at the network layer.
T: IPsec through HA VPN over Cloud Interconnect gives network-layer encryption; MACsec covers only the hop to Google's edge.

@ GCP-PSE D2 T2.3 applied tradeoff
S: A company has private build VMs in a subnet and sensitive data-processing VMs in another, and none of the VMs has an external IP address. Only the build VMs may download packages from the internet, and the security team wants no other VM to be able to initiate internet connections. What is the best design?
A: Configure a Cloud NAT gateway serving only the build subnet, and give the sensitive subnet no NAT and no external IPs
B: Configure a Cloud NAT gateway that serves all subnets in the region, then add a firewall rule to block the sensitive VMs from using it
C: Give the build VMs external IP addresses, because Cloud NAT cannot be limited to a subset of a VPC network
D: Place a Cloud Router in the sensitive subnet, because it filters outbound connections by the source VM
K: A
G: ## Scoping Cloud NAT
Cloud NAT is a software-defined service that gives resources without external IPs outbound access to the internet. A gateway is attached to a Cloud Router and applies only to the subnets (or subnet ranges) you configure. It supports established inbound response packets but not unsolicited inbound connections.
## Least privilege for egress
- Limiting the gateway to the build subnet means VMs elsewhere have no source for internet connections at all.
- An organization policy that blocks external IPs on VMs prevents the sensitive subnet from getting one by mistake.
- Egress firewall rules can further limit destinations for the build subnet.
W: Gateway scoped to the build subnet: only that subnet gets translation, so the sensitive VMs have no external IP and no NAT and cannot start internet connections.
X: B=Gateway for all subnets with a block rule: it makes NAT available to sensitive VMs and depends on a rule staying correct, a weaker posture than not offering NAT at all.
C=External IPs on build VMs: Cloud NAT can be limited to selected subnets or ranges, and giving VMs public addresses increases exposure.
D=Cloud Router as a filter: a Cloud Router exchanges routes with BGP and does not filter connections.
T: Scope Cloud NAT to the subnets that need internet egress and give everything else no path.

Cloud NAT gives resources without external IP addresses outbound access to internet destinations. It is built into Google's Andromeda network virtualization, so there is no appliance or proxy VM to patch or scale. The control plane is a Cloud Router, but the Cloud Router does not carry the traffic.

G: ## Keys for cryptographic de-identification

D=Likelihood threshold: that setting filters findings during inspection and has nothing to do with key availability.
T: Reversible or cross-run consistent tokens need a persistent Cloud KMS wrapped key, never a transient key.

G: ## Choosing among crypto-based tokenization methods
- **Deterministic encryption (AES-SIV)**: no limit on the characters in the input, same input gives the same token (referential integrity), reversible with the key. It does not preserve length or alphabet.
- **Format preserving encryption (FPE-FFX)**: output has the same length and a chosen alphabet, for legacy systems that validate format. Input must be ASCII, at least two characters, and works best on short values of uniform length.

## Applying it here

W: AES-SIV with a KMS wrapped key: deterministic tokens allow joins, any character set and length is accepted, and the key allows authorised reversal.

C=Cryptographic hashing: it is one-way, so the privileged service could never reverse the tokens.
D=Redaction plus a copy: redaction removes the value so joins are impossible, and the copy recreates the exposure the project wanted to avoid.
T: Use AES-SIV for reversible, joinable tokens of variable-length values; use FPE only when format must be preserved.
