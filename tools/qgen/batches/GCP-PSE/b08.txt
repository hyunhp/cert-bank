@ GCP-PSE D4 T4.1 advanced use-case
S: A company requires that production GKE workloads run only images that were both functionally tested by the QA team and security reviewed by the application security team. Each team signs images with its own key. Which Binary Authorization rule enforces this?
A: Require attestations and list both the QA and the security attestor, so an image is admitted only when every listed attestor can verify an attestation
B: Set the rule to require attestations and list both attestors, so an image is admitted when any one of the listed attestors can verify an attestation for it
C: Create one attestor and have both teams share its single signing key, so that a single attestation represents both the QA and the security approval
D: Keep the rule on allow all images and rely on the QA team to delete untested images from Artifact Registry before each weekly release window
K: A
G: ## Attestors and attestations
Binary Authorization decides at deploy time whether an image may run. A policy has a default rule plus optional specific rules, and each rule has an evaluation mode and an enforcement mode.
- An **attestation** is a record, signed with a private key, that states a specific image digest completed a stage such as QA or security review.
- An **attestor** is the Binary Authorization resource that holds the matching public key and verifies those signatures at deploy time.
- A rule in the require-attestations mode lists one or more attestors.
## Modelling two independent approvals
When several attestors are listed in one rule, the image must have attestations that are verified by all of them. One attestor per approving team therefore gives a logical AND. Each team keeps its own key, so neither can forge the other's approval.
W: Require attestations with both attestors listed: the policy admits the image only when the QA attestor and the security attestor each verify an attestation, which enforces both approvals with separate keys.
X: B=At-least-one semantics: listing several attestors does not behave as OR, so this would be a wrong description of the rule and would not guarantee both reviews.
C=Single shared key: one signature cannot show that two independent teams approved, and either team could sign on behalf of the other, which destroys separation of duties.
D=Allow all images with manual cleanup: allow all images disables deploy-time enforcement, and deleting images after the fact is a slow detective step that lets untested images run first.
T: Several attestors in one require-attestations rule means every one of them must verify an attestation, which models independent approvals.

@ GCP-PSE D4 T4.1 advanced tradeoff
S: A regulated company wants to stop a compromised CI service account from approving its own malicious builds. The policy is enforced on production GKE clusters, and the security team wants separate ownership of the policy, the signing authority and the attestation records. Which setup achieves this?
A: Use a multi-project setup: the deployment project holds the policy, an attestor project holds attestors and Cloud KMS keys, and a third stores attestations, each with its own IAM
B: Place the policy, attestors, keys and attestations all in the production project and grant the CI service account the Owner role there so it can sign every build
C: Keep one project for everything but name the attestor after the CI pipeline, so that the pipeline identity is visible in each audit log entry it produces
D: Store the signing private key in a Cloud Storage bucket that only the CI service account can read, and load the key into the attestor at deploy time
K: A
G: ## One policy per project, resources elsewhere
Each Google Cloud project can have exactly one Binary Authorization policy, and it must be in the project where the deployment platform runs. Attestors and attestations are separate resources that can live in other projects.
## Separation of duties
In a single-project setup everything is together, so anyone with enough IAM in that project can change the policy and also create the approval. In a **multi-project setup**:
- the deployment project (for example the GKE project) holds only the policy;
- the attestor project holds attestors and the Cloud KMS keys that sign and verify;
- an attestation project holds the attestation records.
IAM is configured separately in each project, so no single role can both create an approval and relax the rule that demands it.
W: Multi-project configuration: the policy owner, signing authority and attestation store are different IAM boundaries, so a compromised pipeline identity cannot rewrite the policy or mint approvals outside the roles it was given.
X: B=Owner for CI in production: giving the pipeline broad ownership lets one identity edit the policy and sign any image, the opposite of separation of duties.
C=Naming the attestor: a label does not stop the same identity from signing and administering; it only improves readability of logs.
D=Key in a bucket: a private signing key kept in object storage is exposed to anyone who obtains the service account, whereas Cloud KMS keeps the private key non-exportable and signs on request.
T: Split policy, attestors and attestations into different projects so no single identity can both approve and relax enforcement.

@ GCP-PSE D4 T4.1 applied use-case
S: A security team plans to move a production GKE cluster from no Binary Authorization to a policy that requires attestations. Past releases suggest some teams deploy images that nobody has signed yet. The security team wants to measure impact for two weeks without breaking any deployment. What should it do?
A: Use the Dry Run: Audit Log Only enforcement mode, so non-conformant images still deploy but each violation is written to Cloud Audit Logs, then switch to blocking
B: Set the evaluation mode to disallow all images with Block and Audit Log, then relax the policy again for every team that raises a ticket during the period
C: Enable the policy on a new empty test cluster only and assume production results will be identical because the policy definition is the same
D: Leave the policy unchanged and review the GKE node logs of the production cluster for unsigned container image pulls over the two weeks
K: A
G: ## Evaluation mode versus enforcement mode
Each rule has two independent settings:
- The **evaluation mode** says what is checked: allow all images, disallow all images, or require attestations.
- The **enforcement mode** says what happens when an image fails: **Block and Audit Log**, or **Dry Run: Audit Log Only**.
## Using dry run to roll out safely
Dry run lets the policy be tested in the real environment before enforcement takes effect. Non-conformant images are allowed, but the deployment details are recorded in Cloud Audit Logs. The team reviews those entries, signs or fixes the offending pipelines, and only then switches to Block and Audit Log. Most production rules use blocking; dry run is for validation.
W: Dry Run: Audit Log Only: it tests the real policy against real deployments with no outage and produces the Cloud Audit Logs entries needed to find unsigned images.
X: B=Disallow everything first: blocking from day one stops all deployments except exempt images and turns the measurement into an outage.
C=Test only on an empty cluster: it exercises no real deployment pipelines, so it cannot reveal which production teams deploy unsigned images.
D=Reading node logs: node pull logs do not record policy decisions or attestation status, so they cannot show what the policy would have blocked.
T: Roll out a require-attestations rule in Dry Run: Audit Log Only first, read the audit log violations, then enforce with Block and Audit Log.

@ GCP-PSE D4 T4.1 advanced use-case
S: A site reliability team needs a way to deploy an urgent hotfix image to a GKE cluster when the attestation pipeline is down. The security team accepts this only if every use leaves an auditable trail. Which TWO statements about Binary Authorization break-glass are correct? (Select TWO)
A: Break-glass is requested by adding a break-glass label to the Pod specification, so who may use it follows who is allowed to create Pods
B: Every break-glass deployment is recorded in Cloud Audit Logs, so the security team can review it or trigger an alert on those entries
C: Break-glass is enabled by creating a second, permissive Binary Authorization policy that the cluster uses only on weekends
D: Using break-glass permanently removes the image from policy evaluation, so later deployments of the same digest never need a new attestation
E: Break-glass writes an audit entry only when the image would have violated the policy; compliant images deployed with the label are not recorded
K: A,B
G: ## Break-glass
Break-glass is an emergency escape hatch that lets a team deploy an image that Binary Authorization would block. It is consistent with the Kubernetes admission controller specification.
- It is requested per Pod by adding the break-glass label to the Pod specification.
- A **break-glass event** is automatically logged to Cloud Audit Logs, whether or not the image satisfied the policy.
## Governing the exception
Because the request is just a label on the Pod, Kubernetes RBAC on who may create Pods decides who can use it. The audit entries give the security team something to review or to wire to an alert.
W: A=Label on the Pod specification: break-glass is requested in the workload itself, so Pod creation rights govern who can invoke it.
B=Cloud Audit Logs entry: each use is logged automatically, and the entries can be audited or used to trigger alerts and downstream actions.
X: C=Second weekend policy: break-glass is a per-Pod override, not a second policy, and a project has exactly one policy.
D=Permanent exemption: the label affects only that deployment; it does not add the image to the exempt list or create attestations.
E=Logging only violations: the event is logged regardless of whether the image would have satisfied the policy.
T: Break-glass is a Pod label that overrides enforcement for one deployment and is always written to Cloud Audit Logs.

@ GCP-PSE D4 T4.1 applied troubleshooting
S: After a team set the default rule of a Binary Authorization policy to disallow all images with blocking enforcement, new GKE nodes fail to start system Pods such as the ones that provide networking. The team does not want to hand-maintain a list of Google image paths. What should it do?
A: Enable the setting that trusts Google-maintained system images so they are exempt from further policy evaluation, while the default rule keeps blocking other images
B: Change the default rule to allow all images and then use a cluster-specific rule to block application images in each namespace of every cluster
C: Set the default rule to Dry Run: Audit Log Only permanently, because Binary Authorization cannot evaluate system images created by the platform
D: Delete the policy and rely on GKE node auto-upgrade to reject untrusted container images at the node level before Pods are scheduled
K: A
G: ## Exempt images and system images
A policy's rules apply to every image that is not exempt. Two mechanisms keep a strict default rule from blocking the cluster itself:
- **Exempt images**: an allowlist of registry paths (`admissionWhitelistPatterns`) that Binary Authorization always allows. Paths such as `gcr.io/google_containers/*` and `k8s.gcr.io/**` are exempt by default because GKE needs them to start a cluster.
- **Trust Google-maintained system images**: set with `globalPolicyEvaluationMode`; a Google-managed system policy is evaluated before and in addition to the user policy, so images GKE requires are not blocked.
## Fix
Turn on the system-image trust and keep the strict default for everything else.
W: Trust Google-maintained system images: Google's list of required system images is exempted without the team maintaining paths, and the strict default rule still blocks any other image.
X: B=Allow all by default: this flips the model from deny-by-default to allow-by-default, so any unsigned application image would be admitted unless a rule catches it.
C=Permanent dry run: dry run stops all blocking, and the claim that system images cannot be evaluated is wrong; they are handled by exemption.
D=Deleting the policy: removing the policy disables enforcement entirely, and node auto-upgrade does not evaluate image provenance.
T: Pair a deny-by-default rule with the Google-maintained system images trust (or exempt paths) so GKE can start while everything else is blocked.

@ GCP-PSE D4 T4.1 applied definition
S: An organization must make sure every Cloud Run service in all of its projects is deployed under Binary Authorization policy, and that developers cannot turn it off per service. What is the correct mechanism?
A: Set the Cloud Run Binary Authorization organization policy constraint at the organization to allow only the value default, so each project uses its own policy

Cloud Run supports Binary Authorization policy for services and jobs. Differences from GKE:
- Only the **default rule** is supported; specific rules (cluster, namespace, service account) are not available for Cloud Run.
- The policy is read from the project where the service runs.

An organization policy constraint, `run.allowedBinaryAuthorizationPolicies`, can be set on an organization, folder or project to require enforcement. @ GCP-PSE D4 T4.1 advanced definition
S: A team promotes the same container image digest from a staging Artifact Registry repository to a production repository in another project and expects the production Binary Authorization policy to admit it. The pipeline created one attestation for the digest when the image was built. What is true?
A: One attestation can authorize identical images in different registries because it is bound to the digest, so the promoted copy needs no new signature
B: The attestation is bound to the repository path, so the promoted copy needs a fresh attestation from the attestor after every copy between repositories
C: Binary Authorization cannot evaluate images outside the repository where they were built, so the promoted copy must be rebuilt in the production project
D: The attestation expires automatically when the image is copied to another project, because attestations are kept in the source repository
K: A
G: ## What an attestation is bound to
An attestation is a signed record that contains the image's registry path and digest. The digest is the content hash of the image, so identical bytes have an identical digest wherever they are stored.
## Promoting between registries
Binary Authorization documentation states that a single attestation can authorize identical images stored in multiple locations or registries (Artifact Registry, Container Registry, or an external registry). A promotion pipeline that copies by digest can reuse the attestation, which also means the promoted image is provably the one that was approved. Deploying a rebuilt image would create a new digest and need a new attestation.
W: Digest-bound attestation: identical images in different registries share a digest, so one attestation covers the staging copy and the promoted copy.
X: B=Path-bound attestation: the signed content includes the digest, and the documentation says one attestation can authorize identical images across registries.
C=Only Artifact Registry images: images in Container Registry and external registries are supported, so no rebuild is needed.
D=Expiry on copy: attestations are stored in the attestation project as metadata, not in the repository, and are not removed when an image is copied.
T: Attestations bind to the image digest, so one attestation can cover the same image in several registries.

@ GCP-PSE D4 T4.1 applied comparison
S: After a deployment, the security team tightens the Binary Authorization policy and asks whether Pods that already run unsigned images will be flagged. An engineer describes Binary Authorization enforcement as the control that protects running workloads continuously. Which statement corrects this?
A: Enforcement validates an image once, at deploy time; checking Pods that already run for continued conformance needs the separate continuous validation feature
B: Enforcement re-evaluates every running Pod each time the policy changes and evicts those that no longer conform to the new rules

Binary Authorization has two roles in the overview documentation:
- **Enforce**: images being deployed to a supported platform are checked against policy, then allowed or blocked. The overview describes this as a one-time image validation at deploy time.
- **Monitor**: **continuous validation (CV)** periodically checks the metadata of images associated with running Pods for continued conformance and logs violations to Cloud Logging.
## Status to remember
The check-based platform policy form of CV is marked Preview in the current documentation, so a production design should not depend on it being generally available; combine deploy-time enforcement with vulnerability monitoring and posture findings.

@ GCP-PSE D4 T4.1 advanced tradeoff
S: A stateless web tier runs in a managed instance group. Every month the OS needs security updates. The security team wants every instance to be identical, tested before use, and free of configuration drift introduced by manual changes. Which approach fits best?
A: Build a hardened image in a pipeline, scan and test it, publish it to an image family, then roll it out with a new template and a rolling replace
B: Schedule VM Manager patch jobs each month on the running instances and let every VM reach its own update state through its package manager
C: Allow administrators to connect over SSH to the group's VMs and apply the updates by hand, recording each change in a ticket afterwards
D: Stop the group, patch one VM, and take a disk snapshot that is restored onto every other instance of the group when they restart
K: A
G: ## Immutable images versus in-place patching
There are two ways to keep a fleet current:
- **In-place patching** (VM Manager patch jobs) changes running machines. It fits stateful or long-lived VMs, but each machine ends up with its own history, and a failed patch leaves partial state.
- **Immutable images** are built, tested and published once, then instances are replaced from the new image. Instances that fail health checks are never put in service.
## Pipeline shape
A build pipeline (for example Packer or Cloud Build) produces the image with hardening applied, runs vulnerability and conformance checks, and publishes it to an image family in a central image project. A new instance template references the family and a rolling update replaces instances gradually. Every instance is identical because it came from the same tested artifact.
W: Hardened image pipeline with rolling replace: the tested artifact is promoted once, every instance is built from it, and drift disappears because machines are replaced rather than edited.
X: B=Monthly patch jobs: patch jobs are valuable for long-lived VMs, but each machine is patched separately, so drift and partial failures remain and the result is not a single tested artifact.
C=Manual SSH updates: hand edits are exactly the source of drift and cannot be tested or reproduced.
D=Snapshot restore: restoring one patched disk onto others is a manual, error-prone copy that skips scanning and testing and carries instance-specific state.
T: For stateless fleets, build, scan and publish a hardened image, then roll it out by replacement; reserve patch jobs for VMs you cannot replace.

@ GCP-PSE D4 T4.1 applied use-case
S: A company wants monthly patching for all production VMs labelled env=prod, including VMs created after the schedule is set up. No more than 10 percent of VMs in any zone may be patched at the same time, and a service check must run before patching starts on each VM. Which design meets this?
A: One recurring patch deployment with a label-based instance filter, a zone-by-zone rollout with a 10 percent disruption budget, and a pre-patch script

G: ## Patch deployment building blocks
A **patch deployment** schedules **patch jobs**, once or on a recurring schedule.
- **Instance filters**: labels, zones, name prefixes. They are applied to each patch job when it runs, so VMs created later with a matching label are included automatically.
- **Rollout options**: patch one zone at a time or concurrently, and set a **disruption budget**, the number or percentage of VMs in a zone that can be disrupted at once.

D=Concurrent zones without a budget: nothing then limits how many VMs are disrupted at once, and a pre-patch check does not cap concurrency.
T: Use recurring patch deployments with label filters (re-evaluated each run), zone rollout, a disruption budget and pre-patch scripts.

@ GCP-PSE D4 T4.1 applied use-case
S: A platform team wants to define a set of organization policy constraints and Security Health Analytics detectors, deploy them to the organization, apply stricter ones to the production folder, and be alerted when a resource drifts from the intended state. Which Google Cloud capability should it use?
A: The security posture service in Security Command Center, with a posture deployed at the organization and a stricter posture deployed at the production folder
B: Cloud Asset Inventory feeds exported to BigQuery, with scheduled queries that the team writes to compare resources with a sheet of expected values
C: Security Command Center Standard tier alone, since predefined detectors cover every resource and no posture needs to be defined or deployed
D: A Binary Authorization policy attached at the organization node, since its policies are inherited by every folder and project below it
K: A
G: ## Security posture service
Security Command Center includes a **security posture service** to define, deploy and monitor a security posture. It requires the Premium or Enterprise tier with SCC activated at the organization level.

C=Standard tier alone: the posture service is not available without Premium or Enterprise, and predefined detectors cannot enforce organization policy constraints.
D=Binary Authorization policy: it governs container image deployment on supported platforms, not general resource configuration or drift.
T: Use SCC security postures: bundle org policy constraints and SHA detectors, deploy hierarchically, and watch drift findings.

@ GCP-PSE D4 T4.1 advanced definition
S: Which TWO statements about the security posture service in Security Command Center are correct? (Select TWO)
A: A policy in a posture can be an organization policy constraint, including a custom constraint, or a Security Health Analytics detector, including a custom module
B: Drift from the deployed posture is reported as Security Command Center findings that can be reviewed and exported like other findings
C: Several postures can be deployed to the same folder at once, and for each resource the strictest definition among them wins

- **Policies** are either preventative (organization policy constraints) or detective (SHA detectors, including custom modules and custom constraints).
