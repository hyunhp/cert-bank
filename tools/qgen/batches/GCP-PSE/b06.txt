@ GCP-PSE D3 T3.2 advanced tradeoff
S: A bank protects a Cloud SQL and BigQuery estate with Cloud EKM keys that Google Cloud reaches over the internet. Operations see intermittent FAILED_PRECONDITION errors at peak load because the external key manager is slow to answer. Policy still requires the key material to stay in the bank's external key manager, and the data lives in one region. What should change?
A: Replace the external keys with Cloud HSM keys in a multi-region location, so the key manager stays out of the request path
B: Cache the external key material in Cloud KMS for a short period, so repeated requests stop leaving Google Cloud
C: Use Cloud EKM over a VPC connection in that region, so the key manager is reached over a private network path
D: Create the external keys in the global location, which is the closest location to every external key manager partner
K: C
G: ## How Cloud EKM works
With Cloud EKM the key material is created and kept in a supported external key manager (Fortanix, Futurex or Thales). A Cloud EKM key version holds only a reference (key URI or key path) plus extra internal key material that stays in Cloud KMS. For every cryptographic operation, Cloud EKM sends a request to the external manager, which wraps or unwraps a layer of encryption using the external key.
## Internet versus VPC
- `EXTERNAL`: Cloud EKM reaches the manager over the internet. It works in most locations, including multi-regions, but the path can add latency and failures.
- `EXTERNAL_VPC`: Cloud EKM reaches the manager over a Virtual Private Cloud network. The documentation positions it for better availability, so the keys and the resources they protect are less likely to become unavailable. It is available in most regional locations but not in multi-regional ones.
When the external key is unreachable, Cloud KMS returns `FAILED_PRECONDITION`, and the protected resource cannot be used until the key answers again.
W: Cloud EKM over a VPC: it keeps the key material in the external manager, as policy demands, and replaces the internet path with a private network path that improves availability. The single-region data fits because this option exists in regional locations.
X: A=Cloud HSM in a multi-region: this moves the key material into Google-managed hardware, which breaks the requirement to keep the key in the bank's external key manager.
B=Caching key material: Cloud EKM never caches or stores the external key material in Google Cloud; each request goes to the external manager, so there is nothing to cache.
D=Global location: `global` is one of the locations where Cloud EKM keys cannot be created, and a location name does not decide how close a partner is.
T: Cloud EKM over a VPC gives better availability than the internet path while keeping key material outside Google, but only in regional locations.

@ GCP-PSE D3 T3.2 applied troubleshooting
S: A security team sets a 90-day automatic rotation schedule on a Cloud EKM key that was created by entering the key URI of an existing key in the external manager. The schedule is rejected. What explains this, and what would allow scheduled rotation?
A: Cloud EKM keys can be rotated only by Google Cloud Support, who must be asked to rotate on the agreed date
B: Rotation schedules apply only to software keys, so the key has to be recreated as a software key and the external manager dropped
C: External keys need a rotation period above 365 days, so the schedule has to be lengthened and then rotated manually every quarter
D: Manually managed external keys cannot rotate automatically; use a coordinated key through an EKM-over-VPC connection managed from Cloud KMS
K: D
G: ## Manually managed versus coordinated external keys
- A **manually managed** external key is created in the external manager first, then referenced in Cloud KMS by URI or path. Rotation and destruction must be done in both systems by hand, and automatic rotation is not supported.
- A **coordinated** external key is created from Cloud KMS through an EKM connection over a VPC with "EKM key management from Cloud KMS" enabled. This needs an external key manager partner that supports the Cloud EKM control plane. Cloud EKM then asks the external manager to create, rotate and destroy key material, so a symmetric key can rotate on a schedule.
## Why it matters to a security engineer
Many standards require regular rotation. If the key must stay outside Google, the control plane decides whether rotation can be a schedule or a manual runbook.
W: Coordinated external key: the documentation states that automatic rotation is not supported for manually managed external keys, while coordinated keys over a VPC can rotate symmetric keys on a set schedule because Cloud EKM coordinates the new material with the external manager.
X: A=Support rotation: rotation is a customer operation in Cloud KMS and in the external manager; Google Support does not rotate keys on request.
B=Software keys only: automatic rotation also works for Cloud HSM keys and coordinated external keys; switching to software would give up the requirement for external custody.
C=Period above 365 days: no such minimum exists; the schedule fails because the key is manually managed, not because of the period chosen.
T: Scheduled rotation of external keys needs coordinated keys (EKM over a VPC with Cloud KMS key management and a supporting partner); manually managed ones rotate by runbook.

@ GCP-PSE D3 T3.2 advanced definition
S: A company evaluates Cloud EKM for regulated workloads. Which TWO statements about Cloud EKM are correct? (Select TWO)
A: The external key material is never cached or stored in Google Cloud, so an unreachable external key makes the protected operations fail
B: Revoking the project's access in the external manager stops use of the key, and lost keys mean unrecoverable data
C: Google Cloud Support can troubleshoot the external key manager directly, so no support contract with the partner is needed for it
D: Cloud EKM keys can be created in the global location, so a single key can protect resources in every region
E: Cloud EKM keeps a copy of the key in Cloud KMS to decrypt data when the partner is down, until access is restored
K: A,B
G: ## What Cloud EKM promises and what it costs
Cloud EKM gives key provenance (you decide where keys live), access control (the Google Cloud project can use a key only while the external manager allows it, and you can revoke that at any time), and central management of keys across cloud and on-premises data.
The price of that control is dependency. Google has no control over the availability of the external key, and cannot recover data if keys managed outside Google Cloud are lost.
## Practical consequences
- Every operation goes to the partner, so partner downtime becomes outage of the protected resource.
- You need a support contract with the partner; Google Cloud support covers Google Cloud services only.
- Some locations, including `global`, are not available for Cloud EKM.
W: A=Never cached: the external key material stays in the external manager and Cloud EKM contacts it for each request, so an unreachable key produces failures instead of a fallback.
B=Revocation and loss: access can be withdrawn in the external manager at any time, which makes the data unusable, and the flip side is that lost external keys mean unrecoverable data.
X: C=Support: Google Cloud support helps only with Google Cloud services; a support contract with the external key management partner is needed for issues on that side.
D=Global location: `global` and `nam-eur-asia1` are not available for Cloud EKM.
E=Backup copy: Cloud KMS holds only extra internal key material used as a layer of encryption, and the data cannot be decrypted without the external key.
T: Cloud EKM trades convenience for control: no copy of the key in Google Cloud, revocable access, and the partner's availability becomes your availability.

@ GCP-PSE D3 T3.2 applied tradeoff
S: A payment processor must show its auditor that the CMEK keys protecting cardholder data are generated and used inside FIPS 140-2 Level 3 validated hardware, with verifiable evidence for each key. It has no requirement to keep keys outside Google or to have exclusive hardware. Which key choice fits?
A: Software protection level keys, since the validated module is FIPS 140-3 and the newer standard satisfies the hardware requirement
B: Cloud HSM keys at the multi-tenant HSM protection level, with each key's attestation statement and certificate chains given to the auditor
C: Cloud EKM keys over the internet, so that an external hardware vendor supplies the compliance evidence for the keys
D: A Single-tenant Cloud HSM instance in every region, so that dedicated HSM partitions administered by the company carry the keys
K: B
G: ## Choosing a protection level
Cloud KMS keys have a protection level fixed at creation:
- `SOFTWARE`: operations in software with the BoringCrypto module, FIPS 140-3 Level 1 validated primitives. Cheapest, fine without a hardware requirement.
- `HSM`: Cloud HSM, multi-tenant, FIPS 140-2 Level 3 validated hardware, fully managed by Google.
- `HSM_SINGLE_TENANT`: dedicated partitions that the customer administers, giving cryptographic isolation from other customers at extra cost.
- `EXTERNAL` and `EXTERNAL_VPC`: keys held in the customer's external manager.
## Evidence
Each Cloud HSM key has an attestation statement, signed by the HSM hardware with certificates owned by Google and the HSM manufacturer. It can be downloaded with its certificate chains and verified to prove the key attributes and the hardware.
W: Multi-tenant Cloud HSM with attestation: it meets the FIPS 140-2 Level 3 hardware requirement with no HSM cluster to operate, and the attestation gives per-key proof, which is the evidence the auditor asks for.
X: A=Software keys: they are validated at Level 1; a newer standard number does not mean a higher level, and the requirement is Level 3 hardware.
C=Cloud EKM: this adds an external system and a dependency on its availability that nobody asked for, and attestation evidence for Cloud HSM keys does not come from it.
D=Single-tenant instance: it adds an instance the company must administer, plus cryptographic isolation and cost that the stem does not require.
T: Pick the lowest protection level that meets the stated requirement: hardware validation with per-key evidence is Cloud HSM with attestation, not EKM or dedicated HSM unless asked.

@ GCP-PSE D3 T3.2 applied troubleshooting
S: A bucket uses a software Cloud KMS key as its default key. Compliance now demands hardware-protected keys, and an engineer tries to change the protection level of the existing key. It is refused. What is the correct path?
A: Create a new HSM key in a location that supports Cloud HSM, make it the bucket default and rewrite existing objects
B: Add a new key version at the HSM protection level to the same key, then disable the old software version
C: Export the software key material, then re-import it into the same key as a version at the HSM protection level
D: Delete the key and create another with the same name at the HSM level, so that the bucket picks it up automatically on its next write
K: A
G: ## Properties fixed at creation
A key's protection level, purpose and type cannot be changed after creation, and all versions of a key share the protection level. Key material cannot move between storage environments (software, multi-tenant HSM, single-tenant HSM, external). A key and its key ring also cannot be moved to another location.
## What that means for a migration
Moving from software to hardware means a new key with the new protection level, followed by re-protecting what the old key protected. For Cloud Storage the default key of a bucket applies to new objects; existing objects keep their key until they are rewritten.
No principal, including Google, can view or export raw key material, so exporting is not an option.
W: New HSM key, new default, rewrite: it matches how Cloud KMS works, because the protection level cannot be edited and old objects are re-encrypted only when rewritten with the new key.
X: B=New HSM version on the same key: all versions of a key have the same protection level, so a hardware version cannot be added to a software key.
C=Export and re-import: Cloud KMS never exposes raw key material to any principal, and the target would still be a software key.
D=Delete and recreate by name: key resources cannot be deleted and recreated like that, and the bucket references a specific key, not a name pattern.
T: Protection level is permanent: change it by creating a new key and re-encrypting the data, never by editing the key.

@ GCP-PSE D3 T3.2 advanced troubleshooting
S: After suspecting that an old version of a symmetric Cloud KMS key was exposed, an administrator rotated the key. Weeks later a red team shows the exposed version can still decrypt stored data. Which step was missed?
A: Rotation also had to be applied to the key ring, which re-keys every key it holds and removes the exposed versions from use
B: The old version had to be left alone, because versions expire automatically once the rotation period has elapsed
C: Rotation only adds a primary version; data needed re-encrypting with it, and the old version disabling and then destruction
D: The key had to be deleted, because Cloud KMS then regenerates it and re-encrypts all protected data automatically
K: C
G: ## What rotation does and does not do
Rotating a symmetric key creates a new key version and makes it primary, so new encryption uses it. It does not re-encrypt existing data, and it does not disable or delete older versions. The ciphertext records which version encrypted it, so older versions stay enabled and keep decrypting.
## Responding to a suspected exposure
1. Rotate, so new data uses a fresh version.
2. Re-encrypt existing data under the new primary version.
3. Confirm nothing still depends on the old version, then disable it and schedule it for destruction. A disabled version can be re-enabled; a scheduled one can be restored during the destruction period; a destroyed one cannot be recovered.
W: Re-encrypt, then retire the old version: it is the only sequence that removes the exposed material from use, since rotation alone leaves the old version decrypting existing ciphertext.
X: A=Rotate the key ring: key rings are only containers; rotation happens per key, and nothing re-keys data inside a ring.
B=Versions expire: key versions stay enabled until someone disables or destroys them; the rotation period only decides when the next version is created.
D=Delete the key: keys and key rings cannot be deleted, and Cloud KMS never regenerates and re-encrypts data for you.
T: Rotation is only the first step of recovery; re-encrypt data and retire the old version to end its usefulness.

@ GCP-PSE D3 T3.2 advanced use-case
S: A release pipeline signs firmware with a Cloud KMS asymmetric signing key. Policy requires replacing signing keys every 180 days, and an attempt to set an automatic rotation schedule on this key fails. Which approach meets the policy with the least risk of breaking device verification?
A: Convert the key to a symmetric key, which supports automatic rotation, and verify firmware with the shared key
B: Create a new key version, publish its public key to verifiers, switch the pipeline to it, then disable the old version later
C: Schedule the current version for destruction on day 180 and let the pipeline fall back to the primary version of the key
D: Keep the key as it is, because the private part never leaves Cloud KMS and so asymmetric keys are exempt from rotation policies
K: B
G: ## Rotation is different for asymmetric keys
Cloud KMS does not support automatic rotation for asymmetric keys, because additional steps are required before a new version can be used:
- For signing keys, you must distribute the public key of the new version to verifiers, then call the signing method with the new version.
- Asymmetric keys have no primary version; every call names the version to use.
- The purpose and type of a key cannot be changed after creation.
## A safe procedure
Create the version, distribute its public key, switch signing to it, keep the old version enabled long enough for signatures that must still be verified, then disable it. This can be scripted in the pipeline on the required cadence.
W: New version with public key distribution: it follows the documented asymmetric procedure, allows a staged switch without invalidating devices, and keeps the policy cadence through a scheduled job.
X: A=Convert to symmetric: key purpose and type cannot be changed, and a shared symmetric key cannot provide public verification for devices.
C=Destroy and fall back: asymmetric keys have no primary version to fall back to, and destroying the only signing version stops signing.
D=Exempt from rotation: the policy says to replace keys, and the documentation recommends rotation including manual rotation for suspected compromise or algorithm changes.
T: Asymmetric keys rotate by procedure, not by schedule: create a version, distribute the public key, switch, then retire the old version.

@ GCP-PSE D3 T3.2 advanced use-case
S: A SaaS vendor gives every tenant its own Cloud KMS key. Contracts say that after offboarding a tenant's data must become permanently unreadable within 7 days, while the security team wants a short window to undo mistakes. The default scheduled-for-destruction period is 30 days. Which design satisfies both?
A: Create each tenant key with a destruction period of a few days, then schedule destruction of its versions at offboarding
B: Lower the destruction period on every existing tenant key at offboarding, because the setting can be changed at any time after creation
C: Disable the tenant key at offboarding, since disabled versions are destroyed automatically after seven days
D: Delete the tenant's key ring at offboarding, which destroys every key in it at once
K: A
G: ## Key version states
- `ENABLED` can be used. `DISABLED` cannot be used but can be re-enabled.
- `DESTROY_SCHEDULED` cannot be used; the version can be restored to disabled during the destruction period. By default this lasts 30 days.
- `DESTROYED`: key material is gone; ciphertext made with it is not recoverable.
## Tuning the window
The `destroy_scheduled_duration` of a key can be set only when the key is created and cannot be changed afterwards. It applies to all future versions. The range is 24 hours to 120 days, and Google recommends 30 days unless there is a specific requirement. Destroying all versions of a tenant key is a crypto-shredding way to delete that tenant's data.
W: Short duration set at creation: three or so days keeps a small recovery window and finishes inside the 7-day commitment, and per-tenant keys make shredding precise.
X: B=Change later: the duration is configurable only at creation and cannot be changed, so existing 30-day keys cannot be shortened.
C=Disable: a disabled version stays available for re-enabling and is never destroyed automatically.
D=Delete key ring: key rings and keys cannot be deleted, so there is no such shortcut; only versions are destroyed.
T: Set the destruction window when a key is created; crypto-shredding with a per-tenant key then has a predictable, short recovery period.

@ GCP-PSE D3 T3.2 applied troubleshooting

A: Cloud SQL suspended the instance as it cannot use the key; re-enabling the version lets the instance resume

With CMEK the service can operate only while it can use the key. For Cloud SQL, if the instance cannot access the key (for example the key version is disabled), Cloud SQL suspends the instance. When the key is accessible again, Cloud SQL resumes it automatically; the documentation says this can take up to ten minutes for internal validation.

- Destroying the key version makes data permanently unrecoverable, which is the deliberate "delete forever" route.

W: Suspend and automatic resume: the instance is suspended as designed when the key is unusable, and enabling the key version brings it back without data loss.

@ GCP-PSE D3 T3.2 advanced definition
S: A company generates AES keys in its on-premises HSM and must bring one into Cloud HSM. Which TWO statements about importing key material into Cloud KMS are correct? (Select TWO)
A: Once imported, the key material can be exported back to the on-premises HSM through a signed support request
B: The imported key becomes a new version of an existing target key, and importing into a key that already has a version is not allowed
C: Imported keys rotate automatically every 90 days, with new material generated on-premises through the import job
D: The key is wrapped locally with an import job's public key, and an import job expires after three days, so an expired one must be replaced
E: The protection level is set by the import job and key material cannot later be moved to a different storage environment
K: D,E
G: ## How key import works
1. Create a target key (a key ring and key whose location and protection level you choose). Skip creating an initial version if you want your material to be version 1.
2. Create an import job with a protection level and an import method (RSA 3072 or 4096-bit wrapping key). The job starts in `PENDING_GENERATION` and must be `ACTIVE` to be used.
3. Wrap your key locally with the import job's public key (automatically by tooling or manually) and send it. The key version is in `PENDING_IMPORT` until it becomes enabled, or `IMPORT_FAILED` if it fails.
## Properties to remember
- An import job expires after three days; create a new one if it lapses.
- Protection level can't be changed after import, and key material cannot be moved between software, HSM and external storage. Location is also fixed.
- Imported keys have automatic rotation disabled by default, and if you enable it, new versions are generated in Cloud KMS.
W: D=Wrapped with an import job: the key leaves the on-premises HSM protected by the job's wrapping key, and the three-day expiry means a replacement job is needed after that.
E=Fixed protection level: the import job decides software, HSM or single-tenant HSM, and material stays in that environment, so there is no return trip.
X: A=Export: no principal can view or export raw key material from Cloud KMS, including through support.
B=Existing version blocks import: importing adds a new version to the target key and has no effect on its existing versions.
C=Automatic 90-day rotation: automatic rotation is disabled for imported keys by default, and any new version generated by rotation would be created in Cloud KMS, not on-premises.
T: Import is a wrapped, time-limited transfer into a fixed protection level; it adds a version and never lets material come back out.

@ GCP-PSE D3 T3.2 advanced tradeoff
S: A SaaS vendor must be able to crypto-shred a single tenant's data and allow each tenant's support group to use only that tenant's data. Today it has one Cloud KMS key with a new key version per tenant and grants groups encrypt and decrypt on the key. The architect says this cannot meet both goals. Why, and what is the fix?
A: Each tenant key version can hold its own IAM policy only through IAM Conditions, so conditions on version names must be added
B: Access cannot be managed per key version, so a grant covers every enabled version; use one key per tenant in a shared key ring
C: The key needs to be asymmetric, because only asymmetric key versions can carry separate IAM policies for different groups
D: Disabling the whole key ring isolates a tenant, so the vendor should keep the single key and use a key ring per tenant
K: B
G: ## Where IAM and lifecycle attach in Cloud KMS
The hierarchy is project, location, key ring, key, key version. IAM can be set on the project, key ring and key, but not on a key version: granting access to a key grants access to all its enabled versions. Key versions are also what rotation creates over time, so they represent time, not tenants.
Cloud KMS resources can't be moved to a different location after creation, and keys and key rings cannot be deleted; lifecycle actions (disable, destroy) apply to versions or to the entire key.
## Design consequence
If tenants need independent access control and independent erasure, each needs its own key. A shared key ring is fine for grouping, because IAM on each key can differ.
W: One key per tenant: IAM on each key limits who can use that tenant's key, and destroying that key's versions shreds only that tenant's data.
X: A=IAM Conditions on versions: access to a key version cannot be managed independently, so there is nothing to attach the condition to.
C=Asymmetric keys: asymmetric versions also share the key's IAM, and the key type does not change who can be granted access.
D=Disable the key ring: key rings are containers without a state of their own, and the single key would still contain all tenants.
T: IAM and destruction scope to a key, not to a version, so isolate tenants with separate keys.
