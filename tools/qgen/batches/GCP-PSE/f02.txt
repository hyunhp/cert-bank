@ GCP-PSE D2 T2.1 advanced use-case
S: A media site serves images through a global external Application Load Balancer with Cloud CDN enabled. A backend security policy with WAF rules is already attached to the backend service. Requests from one abusive IP range must be rejected even when the response could be served from the cache. What should the engineer add?
A: Identity-Aware Proxy on the backend service, because IAP runs ahead of the cache and refuses unknown addresses
B: A Cloud Armor edge security policy whose deny rule matches the offending source addresses, next to the WAF policy
C: A further deny rule in the existing backend security policy, which sees every request before the cache answers it
D: A VPC firewall rule on the origin VMs that denies the range, which also stops the cache from serving that range
K: B
G: ## Edge versus backend security policies
Cloud Armor has several policy types. A **backend security policy** filters requests that reach the backend service. An **edge security policy** filters access to content that is stored in cache, such as Cloud CDN-enabled backend services and backend buckets, and is enforced near the outermost perimeter of Google's network, upstream of the Cloud CDN cache.
## Ordering
- Edge policies are evaluated before the cache and before Identity-Aware Proxy.
- When both policy types are attached to one backend service, the backend policy is enforced only for cache-miss requests that passed the edge policy.
- Edge policies support a subset of the parameters of backend policies, which suits simple controls such as IP ranges and regions.
W: Edge security policy: it is attached to the Cloud CDN-enabled backend service and enforced upstream of the cache, so the abusive range is denied even for objects that would have been served from cache.
X: A=IAP: edge security policies are evaluated before IAP, and IAP authenticates identities rather than refusing IP ranges.
C=Backend policy rule: backend policies run only for cache misses, so cache hits to the abusive range would still be served.
D=Origin firewall: the origin firewall sees only cache misses, and cached responses are served from Google's edge, so it cannot stop cache hits.
T: Use a Cloud Armor edge security policy to filter requests before the Cloud CDN cache; backend policies see only cache misses.
V: Cloud Armor, Cloud CDN

@ GCP-PSE D4 T4.2 applied use-case
S: A security team investigating a port scan finds that VPC Flow Logs show almost none of the short TCP probes that a scanning VM sent to other VMs, because each probe is only one or two packets. The team needs a record of every outbound TCP connection attempt. What should it enable?
A: A primary sampling rate of 1.0 on the subnet, so that every packet of every flow is sampled and logged
B: A 15-minute aggregation interval, so that all packets of each flow are combined into a single entry
C: Firewall Rules Logging on the implied allow egress rule, so that each outgoing connection is logged
D: TCP connection logging, an optional flow logs setting that logs connection setup (SYN) events
K: D
G: ## Why sampling misses short connections
VPC Flow Logs samples packets with a primary sampling rate that is dynamic and cannot be adjusted, then aggregates them over an aggregation interval and applies an optional secondary sampling rate. Short-lived or low-volume TCP connections can therefore be missed.
## TCP connection logging
This optional setting captures all outbound TCP connection attempts (the initial `SYN`) and all acknowledged inbound connections (the `SYN-ACK` reply) for VM instances and serverless endpoints. It can be set in a VPC Flow Logs configuration for a subnet, a VPC network or an organization. If data packets of the same 5-tuple are sampled in the same interval the event merges into that entry; otherwise it gets its own entry.
W: TCP connection logging: it records every outbound connection attempt from its initial `SYN`, independently of the packet sampling that misses one- or two-packet probes, so every probe is visible.
X: A=Primary sampling of 1.0: the primary sampling rate is dynamic and cannot be adjusted by the user.
B=Longer aggregation interval: the interval only controls how sampled packets are combined; it does not add packets that were not sampled.
C=Implied egress rule logging: implied rules cannot be logged, and rule logging records only TCP and UDP connections.
T: Enable TCP connection logging in flow logs to capture short TCP probes that packet sampling can miss.
V: VPC Flow Logs

@ GCP-PSE D1 T1.1 applied use-case
S: Access to a documentation project must be granted to everyone whose HR job-role attribute is Technical Writer. Membership must follow the directory attribute automatically as people change role, and the platform team wants to manage the group through the Cloud Identity Groups API without maintaining member lists. Which group type fits?
A: A dynamic group, whose members are computed from a query on user profile fields
B: A locked group, so that only administrators can edit the member list
C: A standard Google Group whose owners add and remove writers as roles change
D: Individual IAM bindings for each writer, regenerated by a nightly export from the HR system
K: A
G: ## Group types in Cloud Identity
The Cloud Identity Groups API manages several kinds of groups:
- **Google Groups** (the default): a mailing-list style group that can also be used in IAM.
- **Dynamic groups**: membership is managed automatically from a query on user attributes such as job role or location.
- **Security groups**: a group used specifically to control access to organizational resources.
- **Locked groups**: a group that only administrators can edit, used to prevent drift from an external source or to protect sensitive groups.
## Choosing
When membership must follow a directory attribute with no manual list, a dynamic group is the type that does it. Granting roles to the group rather than to individual users keeps IAM policies short and auditable.
W: Dynamic group: a membership query on the job-role attribute adds and removes users automatically, so the IAM binding on the group always matches HR data without manual upkeep.
X: B=Locked group: locking restricts who can edit attributes and members, but it does not compute membership from an attribute.
C=Standard Google Group: its owners must maintain membership by hand, which is the manual upkeep that the requirement wants to avoid.
D=Individual bindings: per-user bindings multiply policy entries and go stale between exports, which is the opposite of group-based access.
T: Use a dynamic group when membership should follow a user attribute automatically, and grant IAM roles to the group.
V: Cloud Identity
