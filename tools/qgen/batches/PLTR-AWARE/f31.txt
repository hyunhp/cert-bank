@ PLTR-AWARE D1 T1.3 applied comparison
S: A data science team already has a demand forecasting model trained in their own notebook environment outside Foundry. They want its predictions to support decisions on Ontology objects. Which statement about models in the platform is accurate?
A: The model has to be retrained inside Foundry with platform-native training code before its predictions can be written to Ontology objects
B: Externally built models can be imported as libraries, artifacts, containers or APIs, then governed, deployed and used with the Ontology
C: Logic on objects is meant to be LLM-driven, so the forecasting model should be replaced by an AIP Logic prompt that estimates demand
D: The model stays in the notebook, and each day the team exports Foundry data to it and pastes the predictions back into a dataset by hand
K: B
G: ## Logic sources
In the course's architecture view, logic sources sit next to data sources. The Ontology system page says the logic behind an action or object can be a simple business rule, a conventional machine learning model, an LLM-driven function or a multi-step orchestration.
## Models in Foundry
- A model is an artifact that holds machine learning logic.
- Models can be developed inside the platform or imported from outside: as libraries, artifacts, containers, or as externally hosted APIs.
- Once integrated, models get lineage, security, versioning and auditing, and Modeling Objectives help review, release and deploy them.
- A deployed model can be registered for use in the Ontology layer, so operational workflows can use it.
Example: a forecasting model from a notebook is imported as an artifact, released through a Modeling Objective and used to fill a predicted-demand value for each product.
W: Import as library, artifact, container or API: the model integration docs list exactly these routes for externally developed models, and an integrated model gains lineage, versioning and governance and can be used in the Ontology layer.
X: A=Retrain inside Foundry first: the docs support importing models built in external environments, so retraining the forecasting model on the platform is not a prerequisite.
C=Replace with an LLM prompt: the Ontology system page names conventional machine learning models as valid logic next to LLM-driven functions, so a working forecasting model does not need to be swapped for a prompt.
D=Manual daily export and paste back: this keeps the model outside the platform, so the predictions lose lineage, versioning and governance, and it ignores the supported import paths.
T: Logic sources include existing ML models, which can be imported into Foundry and used with the Ontology rather than rebuilt.
V: Model integration, Modeling Objectives

@ PLTR-AWARE D1 T1.5 applied tradeoff
S: A sponsor wants the team to integrate every table from all twelve logistics systems before building any application. The team expects that to take months. Which approach matches the platform's guidance on delivering a use case?
A: Finish integrating the twelve systems first, so the application is designed once against complete data and does not need rework later
B: Buy a second platform for the application layer and keep Foundry for storage, so each tool can be chosen separately later on
C: Build a set of dashboards for each department before choosing a decision, so users can later say which data they want integrated
D: Start from the decision to support, work back to the few sources it needs, ship a small working tool and extend it with feedback
K: D
G: ## Outcome first, then decompose
The "delivering a use case" page describes a use case as a time-bound effort to support a specific decision-making process. It advises thinking about the outcome rather than the method, decomposing the project into small logical steps, and working backwards from the outcome to identify the necessary data. It also notes a first prototype for feedback can be a good end point, and that tools can change as the project matures.
The Aware course's speedrun follows the same idea: get from zero to a working operational tool quickly, then iterate.
## Example
Decision: which late shipments to reassign today. Needed: shipments, warehouses, drivers. Three sources, one app, then expand.
W: Outcome first, minimal sources, iterate: this matches the documented approach of framing the outcome, decomposing the work, working backwards to the data that decision needs and using an early prototype to gather feedback.
X: A=Integrate the twelve systems first: months pass without value, and with no decision chosen there is nothing to tell the team which of the tables actually matter.
B=Second platform for apps: splitting the stack separates governance from the object layer that Foundry applications and Actions rely on, and it does not shorten the path to a first working tool.
C=Dashboards for each department first: this puts the method before the outcome, which the use-case guidance warns against, and it still leaves the decision undefined.
T: Start from the decision, bring in only the data it needs, deliver a small tool and iterate.

@ PLTR-AWARE D1 T1.5 applied troubleshooting
S: Main is protected so changes need a proposal and one approval. A builder asks a teammate who helped edit the branch to approve the proposal, but the teammate cannot approve it. Why?
A: Approving proposals into a protected branch needs the Owner role on the project, and an Editor who worked on the branch has too little access
B: The branch has to be archived before review starts, and archived branches are the ones reviewers can approve for merging into main
C: Approval is granted by the platform after a configured waiting period, and manual approvals stay blocked while that period runs
D: A valid approver needs Edit permission on the pipeline and must not have contributed to the proposed change, which the teammate did
K: D
G: ## Branch protection and approvals
The docs list two protection settings for branches:
- Require proposals: no direct changes to the protected branch; work happens on another branch and is merged by proposal.
- Require at least one approval: a further user must approve before merging.
Valid approvers are users with `Edit` permission on the pipeline who did not contribute to the proposed change. That keeps review independent.
## Example
Ana and Ben edited the branch together, so neither can approve; Chris, an editor who did not touch it, can.
W: Edit permission and no contribution: the branch protection docs define valid approvers as users with Edit permission on the pipeline who did not contribute to the proposed change, so a co-author cannot review their own work.
X: A=Owner role required: the documented requirement is Edit permission, not a higher role. The teammate is blocked because they contributed, and an Owner who had edited the branch would be blocked too.
B=Archive before review: archived branches cannot be edited or used until they are restored, so archiving the branch would stop the merge rather than enable an approval.
C=Waiting period: the docs describe no time-based approval; a qualifying user has to approve the proposal before it can be merged.
T: Protected branches need an approval from an editor who did not contribute to the change.

@ PLTR-AWARE D1 T1.5 applied tradeoff
S: After cleaning shipment and warehouse data in Pipeline Builder, a builder wants the Shipment and Warehouse object types and the link between them without switching tools. What does the documentation support?
A: Write the cleaned tables as dataset outputs and file a request so an administrator defines the object types and the link later on
B: Add a time series sync output for each table, since time series syncs are the Ontology output Pipeline Builder offers for entities
C: Add object type and link type outputs in the same pipeline, so the clean data defines the Ontology elements in one workflow
D: Export the cleaned data to a spreadsheet and upload it into Workshop, which turns an uploaded table into an object type with links
K: C
G: ## Ontology outputs from a pipeline
The docs list pipeline outputs as datasets, virtual tables, media sets, files and Ontology components: object types, link types and time series.
- Object type output: the schema definition of a real-world entity or event, usable in Workshop or Slate.
- Link type output: if two object type outputs exist in the pipeline, a link can define their relationship.
- Builders can add and edit object types, link types and time series "within one workflow interface rather than navigating back to Ontology Manager".
A dataset output remains a valid alternative when someone will build the Ontology in Ontology Manager later.
W: Object type and link type outputs: these are documented Ontology outputs of Pipeline Builder, and with two object type outputs in the pipeline a link type can define their relationship, so the builder goes from raw data to objects and links in one place.
X: A=Dataset outputs plus an administrator request: a dataset output works if someone builds the Ontology later, but it moves the work to another person and another tool, which the builder wanted to avoid; Pipeline Builder can create the object types itself.
B=Time series syncs for entities: a time series sync indexes timestamp and value pairs that back time series properties; it does not define Shipment or Warehouse as object types or link them.
D=Spreadsheet into Workshop: Workshop builds applications on top of existing objects; it does not create object types or links from an uploaded table.
T: Pipeline Builder can output object types and link types directly, not just datasets.

@ PLTR-AWARE D1 T1.5 applied troubleshooting
S: A builder combines two carrier files into one shipments table with a union in Pipeline Builder. One carrier names its column ship_id and the other shipment_id, and the union shows an error. What is the most direct fix?
A: Rename or cast columns in one input so both share the same schema before the union, since a union requires matching schemas
B: Build the pipeline anyway and let the object type output drop the unmatched column, since a schema mismatch is reported as a warning
C: Replace the union with a join on the carrier name column, since a join accepts inputs whose other column names differ
D: Write a Java user-defined function that appends the two files, because column renames need custom code in Pipeline Builder
K: A
G: ## Union versus join
- Union: stacks rows from inputs into one table. The docs state the union transform requires all inputs to have the same schema; if they differ it shows an error listing the missing columns.
- Join: combines two tables side by side on at least one matching column.
Harmonizing several sources usually means renaming and casting columns to a common shape first. Pipeline Builder's type-safe functions surface such errors while you build rather than after a long run.
## Example
Rename `ship_id` to `shipment_id` and cast both to string in one input path, then union: one table with every carrier's rows.
W: Align the schemas, then union: the error is the documented union rule (inputs must share a schema, and the error lists the missing columns), and renaming or casting columns with built-in transforms is the simple fix.
X: B=Build anyway and drop the column: the union error is not a warning to ignore; Pipeline Builder flags the schema problem before the build precisely so it is fixed, not passed downstream to the object type.
C=Join on carrier name: a join combines two tables side by side on matching columns; it does not stack the two carriers' shipments into one list of rows.
D=Java UDF to append: the docs suggest user-defined functions when existing transforms cannot do the job, and renaming and casting columns are built-in transforms.
T: A union needs identical schemas; rename and cast columns to a common shape first.
V: Pipeline Builder
