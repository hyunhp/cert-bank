@ PLTR-AWARE D2 T2.3 applied definition
S: A `Depot` dataset has a latitude column and a longitude column. The team wants each depot object to carry one location value that map features can use as a geographic point. Which property base type fits?
A: Geopoint, whose values are written as a comma-separated coordinate pair such as 57.64,10.40 in the backing data
B: Vector, because the base types reference describes vectors as the way to place objects on maps for spatial searches
C: Struct, because combining latitude and longitude as two fields of one property is how the Ontology represents a location
D: Geoshape, because it stores any geographic feature, and a single depot is best modeled as a polygon around its site
K: A
G: ## Base types set what a property can do
A property's base type defines what data it holds and which operations applications offer for it. Besides common types (String, Integer, Date ...), the base types page lists advanced types:
- **Geopoint**: geographic points, stored as `latitude,longitude` (for example `57.64911,10.40744`).
- **Geoshape**: geographic shapes such as areas.
- **Vector**: vectors for semantic search.
- **Struct**: schema-based properties with several fields.
## Building the value
In the backing pipeline, combine the two columns into one geopoint value, then map it to a Geopoint property. The docs also note Geopoint is valid as a title key but not as a primary key.
Example: depot `D-17` gets `52.37,4.90` as its location property.
W: Geopoint: it is the base type the docs define for geographic points, holding latitude and longitude together in one `latitude,longitude` value that map features can use.
X: B=Vector: the docs describe vectors for semantic search, not map locations.
C=Struct: a generic multi-field type; it does not give the property geographic meaning.
D=Geoshape: meant for shapes such as areas; a depot location is a single point.
T: Store a point location as one Geopoint property, built from latitude and longitude.

@ PLTR-AWARE D1 T1.3 applied comparison
S: An analyst must join two very large tables that are not mapped to the Ontology and save the joined result as a new dataset for other Foundry tools. Which point-and-click analysis application fits best?
A: Automate, because it checks conditions on a schedule and can run effects that combine large tables into a new output dataset
B: Contour, because its analysis paths run directly on rows and columns at scale, outside the object layer, and can be exported
C: Workshop, because it builds operational applications that read from the object layer and write back changes through actions
D: Quiver, because it is optimized for object and time series data from the Ontology and for dashboards embedded in Workshop
K: B
G: ## Analytics "north" of the Ontology
The Aware course groups analytics, workflows, automations and SDKs north of the Ontology: the things people use to look at and act on data. Foundry has several point-and-click analysis tools with different strengths.
## Contour
- Point-and-click analysis on tables at scale.
- A good fit when some data is not mapped in the Ontology, when the dataset is very large (the docs mention joins on over 100,000 objects or aggregations over 50,000 rows), or when results should be saved as a new dataset.
## Quiver
- Analysis on object and time series data from the Ontology, with links followed natively, dashboards embeddable in Workshop and writeback through actions.
Example: joining a 40-million-row sales table to a store table and saving the result for a pipeline is Contour work.
W: Contour: the docs list large tables, data not mapped to the Ontology and saving results as a dataset as the cases where Contour fits, which is exactly this analysis.
X: A=Automate: runs effects such as actions, functions and notifications when conditions are met; it is not a tool for joining tables.
C=Workshop: an application builder for operational users, not a table analysis tool.
D=Quiver: built for Ontology objects and time series; the tables here are not mapped to the Ontology.
T: Use Contour for large table analysis outside the Ontology, Quiver for object and time series analysis inside it.
V: Contour, Quiver

@ PLTR-AWARE D1 T1.3 applied comparison
S: Reliability engineers want to explore pump sensor readings over time for objects in the Ontology, follow links to each pump's site, embed the resulting dashboard in a Workshop app and record their conclusion through an action. Which application fits?
A: Contour, because it is the platform's tool for large tables and saves its analysis results as new datasets for downstream use
B: Data Connection, because sensor readings arrive from external systems and must be explored where the sync is configured
C: Quiver, because it is the object-aware analysis tool whose charts can live inside operational apps and drive writeback
D: Apollo, because it monitors the health of every environment and sends alerts to engineering teams through existing tools
K: C
G: ## Quiver
Quiver is a point-and-click analysis tool for object and time series data from the Ontology. The docs say it fits when:
- your data is mapped in the Ontology, so links replace manual joins;
- you work with time series data (it has a time series library and can be backed by a time series database);
- you want to embed findings in object-aware apps such as Workshop;
- you want to write analytical decisions back to the Ontology using an action.
## How it differs
Contour works on tables and is preferred for data not in the Ontology or for saving results as datasets.
Example: an engineer charts pressure and vibration for one pump, jumps to the linked site, embeds the chart in the maintenance app and applies a "flag for inspection" action.
W: Quiver: it combines object-aware analysis that follows links, time series support, Workshop embedding and action writeback, which are exactly the needs listed.
X: A=Contour: a table analysis tool, best when data is not mapped to the Ontology; it does not natively follow object links.
B=Data Connection: syncs data into Foundry; it is not where analysts explore or chart readings.
D=Apollo: Palantir's software delivery and deployment platform; its monitors cover software, not pump sensors.
T: Choose Quiver for analysis on Ontology objects and time series that should feed operational apps.
V: Quiver, Workshop
