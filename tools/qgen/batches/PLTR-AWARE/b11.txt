@ PLTR-AWARE D1 T1.4 expert troubleshooting
S: A retailer's enrollment runs a production AIP Logic automation that triages customer emails, owned by the service project. Since an innovation team started a project of Pipeline Builder experiments that run LLM transforms over millions of product reviews, the triage automation is often rate limited during the day. The CFO refuses to pay for a larger enrollment tier this year. The security office also wants the innovation project restricted to two approved models, because legal has reviewed only those. Which change addresses all three concerns?
A: Lower the user rate limits for the innovation team's members, so that each person's experiments consume less capacity per minute
B: Upgrade the enrollment from the medium tier to the large tier, so that both projects get enough capacity at the same time
C: Ask the innovation team to run its experiments only at weekends, and send the security office a list of the models it intends to use
D: Put the innovation project in its own project limit with a base of 0% and model overrides that allow only the two approved models
K: D
G: ## Three levels of LLM capacity
The AIP capacity page describes three levels:
- **Enrollment limits**: the overall ceiling per model (tokens and requests per minute), set by the enrollment tier.
- **Project rate limits**: the maximum share of enrollment capacity that all resources in a group of projects can use, per model.
- **User rate limits**: the maximum a single user can use, for traffic **not attributed to a project**.
## Who is limited by what
Project-attributed requests (Pipeline Builder, AIP Logic, Automate, Chatbot Studio, Workshop) fall under the enrollment and project limits; **per-user limits do not apply** to them. User-attributed requests (for example AIP Assist) fall under user limits.
## Model overrides
Within a project limit, **model overrides** set percentages per model. Setting the base limit to 0% and adding overrides creates a **model allowlist**.
## Example
Innovation project limit: base 0%, Model X 20%, Model Y 15%. Its pipelines can no longer saturate capacity, and no other model is usable there.
W: Project limit with 0% base and model overrides: it caps the pipelines' share so triage keeps capacity, costs nothing extra and allows only the two approved models.
X: A=Lower user rate limits: Pipeline Builder traffic is project-attributed, and per-user limits do not apply to it.
B=Larger enrollment tier: it would ease contention, but the CFO ruled out the cost, and it restricts no models.
C=Weekend runs plus a list: scheduling helps contention, but a list of intended models enforces nothing.
T: Use project rate limits, with model overrides as an allowlist, to stop experiments from starving production and to restrict models.
V: AIP, LLM capacity management

G: ## Read-time controls
Object and property security policies **filter what a user can read** in the Ontology. **Markings** are mandatory controls that **propagate** through transform logic: a dataset derived from marked data carries the marking unless someone with the right permission removes it. A user needs the marking to open any of those datasets.

@ PLTR-AWARE D1 T1.4 expert tradeoff
S: A builder plans a change on a global branch: add a new Pipeline Builder output dataset for cleaned returns, create a new `Return` object type backed by it, and delete an old returns dataset that nothing should need once the change ships. The team wants nothing to affect `main` until a reviewer approves the proposal. A dashboard owned by another team still reads the old dataset today and will only switch after the merge. Which plan meets all of these needs?
A: Do all three steps on the branch, because Global Branching isolates every resource change, including creations and deletions, until the merge
B: Create the dataset and object type on main first for reviewers to test, and delete the old dataset on the branch in the proposal
C: Do the pipeline and object type work on the branch, and delete the old dataset on main only after the merge and the dashboard's switch
D: Skip the branch and make all three changes on main during a quiet weekend, then ask the dashboard owner to repoint the dashboard on Monday
K: C
G: ## What a branch isolates
Global Branching lets you change resources on a branch without affecting `main`. The core concepts page adds a precise limit:
- **Creating or deleting Foundry resources on a branch affects `main`.**
- **Ontology resources are the exception**: you can create, modify or delete them on a branch without affecting `main`.
## Applying it
- Building the new output on the branch is the normal branched pipeline workflow.
- The `Return` object type is an Ontology resource, so it stays isolated until merge.
- Deleting the old dataset is a resource deletion, which would hit `main` at once and break the other team's dashboard.
## Safe ordering
Merge first, let the dashboard owner switch, then delete the old dataset.
W: Branch the pipeline and object type, delete later on main: the ontology work stays isolated, and the deletion waits until nothing depends on the old dataset.
X: A=Everything on the branch: resource deletions on a branch affect main immediately, so the dashboard would break before review.
B=Create on main first: it puts unreviewed resources on main, which the team wanted to avoid.
D=All changes on main at the weekend: it skips review entirely and breaks the dashboard until Monday.
T: Branches isolate edits and Ontology changes, but creating or deleting other Foundry resources on a branch reaches main, so delay deletions until after merge.
V: Global Branching

@ PLTR-AWARE D1 T1.3 expert use-case
S: When a buyer approves a purchase order in a Workshop app, the approval must be recorded in SAP before Foundry shows the order as approved, and the buyer must see SAP's error if SAP rejects it. The same approval should also notify a chat channel and update a supplier portal, but those two are best effort and must never block the buyer. All three systems already have REST API sources in Data Connection. How should the builder configure webhooks on the approval action?
A: Configure all three webhooks as writebacks, so that SAP, the chat channel and the supplier portal must all succeed before the order changes
B: Configure SAP as the writeback webhook, and add the chat channel and the supplier portal as two side-effect webhooks on the action
C: Configure SAP as a side-effect webhook too, together with the chat channel and supplier portal, so that none of them can block the buyer
D: Configure SAP as the writeback webhook, and call the chat channel and portal from an Automate automation on approved orders
K: B
G: ## Writeback versus side effect
A webhook in an action runs as one of two types:
- **Writeback**: runs **before** any other rules; if it fails, **no changes are made** and the user sees the error. Only **one** webhook per action can be a writeback.
- **Side effect**: runs **after** the object changes; failures are not shown to the user. An action can have **several** side effects, run in no particular order, and the docs recommend them for best-effort notifications or writing to multiple external systems.
## Mapping the requirements
- SAP must accept first, with errors shown: writeback.
- Chat and portal must never block: side effects.
## Why not an automation
An automation could call systems later, but the requirement is satisfied directly by the action, without a second component to own and monitor.
W: SAP writeback plus two side effects: SAP gates the change and reports errors, while the other two run after the edit without blocking.
X: A=Three writebacks: only one webhook per action can be a writeback, and the best-effort systems must not block.
C=All side effects: SAP would run after the order is already approved in Foundry, and its errors would not reach the buyer.
D=SAP writeback plus an automation: it works only with an extra automation to build and run, while side-effect webhooks on the action already fit.
T: One writeback webhook for the system that must accept first, side-effect webhooks for best-effort systems.
V: Action types, Data Connection webhooks

@ PLTR-AWARE D2 T2.1 expert troubleshooting
S: A supplier drops daily price files into an S3 bucket and, when it finds errors, overwrites a file with a corrected version under the same name; it refuses to change this habit. The pricing team needs the Foundry dataset to hold the latest version of every file ever delivered. The current sync uses APPEND transactions with Exclude files already synced, and corrections never arrive. The details add that a downstream team had planned to run its pipeline incrementally on this dataset. Which setup should replace the current one, and what follows from it?
A: Keep APPEND and add the Last modified date option to Exclude files already synced, which re-ingests corrected files while downstream stays incremental
B: Switch to SNAPSHOT with Exclude files already synced, which keeps the latest version of every file and lets downstream pipelines run incrementally
C: Switch to SNAPSHOT with no filters, which re-copies the whole bucket each day and lets the downstream pipeline stay incremental on top of it
D: Switch to UPDATE with Exclude files already synced on Last modified date, accepting that downstream pipelines can no longer run incrementally
K: D
G: ## File-based ingestion modes
The file-based syncs page lists known modes:
- **Batch mirror (SNAPSHOT, no filter)**: every run copies all files again.
- **Incremental mirror (APPEND + Exclude files already synced)**: new files only, keyed by **file path name**.
- **Incremental mirror (UPDATE + Exclude files already synced with Last modified date or File size)**: new **or changed** files; the dataset holds **the latest version of all files ever present**.
- **Trailing window (SNAPSHOT + Exclude files already synced)**: only files that are new since the last run.
## The documented traps
- With APPEND, adding Last modified date or File size "would attempt to incorrectly re-ingest existing files"; APPEND cannot modify existing files.
- UPDATE caveat: "downstream pipelines cannot run incrementally, as the output dataset ... is not append-only". Use it only when modifications to existing files are non-negotiable.
W: UPDATE with Last modified date: it picks up overwritten files and keeps the latest version of each, and the docs warn that downstream incremental processing is then impossible.
X: A=APPEND with Last modified date: the docs list it as contradictory, because APPEND cannot replace a file already ingested under that name.
B=SNAPSHOT with the filter: that is the trailing-window mode, which shows only files new since the last run, not every file.
C=SNAPSHOT with no filter: it does mirror the bucket, but a snapshot replaces the dataset each run, so downstream cannot run incrementally either.
T: When a source overwrites files that must be re-ingested, use UPDATE mode and accept that downstream pipelines lose incremental processing.
V: Data Connection
