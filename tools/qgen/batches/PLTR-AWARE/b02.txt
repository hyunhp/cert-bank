@ PLTR-AWARE D1 T1.3 applied tradeoff
S: An IT team plans to clean and reshape supplier files with scripts on an external server before loading them into Foundry, so that only tidy data arrives. What does Palantir's guidance on data ingestion favor instead?
A: Keep the external scripts, because data should arrive in Foundry already cleaned so that downstream pipelines remain short and simple
B: Ingest the data as-is from the raw source, then clean it in a versioned Foundry pipeline so every change to the data stays traceable
C: Ask each supplier to send pre-cleaned files, so that neither the IT team nor Foundry needs to transform the incoming data at all
D: Load only the cleaned columns that applications need today and drop the raw files, so storage and sync time stay as low as possible
K: B
G: ## Data sources sit "south" of the Ontology
The Aware course places data sources, logic sources and systems of action below ("south of") the Ontology. Data Connection is the application that syncs data from external systems into Foundry for the integration, modelling and Ontology layers.
## Ingest raw, transform inside
The Data Connection documentation describes a philosophy that data should be ingested "as-is" from its most raw source, with no external preprocessing. Then the branched and version-controlled Foundry pipeline becomes the single place where every change between raw data and the Ontology is recorded.
## Why it matters
- When a number looks wrong in an application, you can trace it back step by step to the raw file.
- Fixes happen in one governed pipeline instead of in scripts on a server nobody reviews.
Example: a supplier changes a date format. With raw ingest, the fix is a pipeline change on a branch; with external scripts, the bad rows may already be lost.
W: Ingest as-is, transform in Foundry: the docs recommend raw ingestion so the versioned pipeline is the single source of every change on the path to the Ontology.
X: A=Clean before loading: external preprocessing hides transformations outside the platform, which is exactly what the docs advise against.
C=Supplier pre-cleaning: moves the logic to systems you cannot see or version, so problems still cannot be traced inside Foundry.
D=Load only needed columns: throws away raw data that later use cases and audits may need, and the filtering again happens outside the pipeline.
T: Bring data in raw and do all cleaning in a versioned Foundry pipeline so every change stays traceable.
V: Data Connection, Pipeline Builder

@ PLTR-AWARE D1 T1.3 applied troubleshooting
S: An action that approves purchase orders also sends the approval to an external ERP through a webhook. Last week the ERP call failed, yet the order already showed "approved" in Foundry. The team wants Foundry unchanged whenever the ERP call fails. What should they change?
A: Keep the webhook as a side effect but add a second side effect webhook that repeats the same ERP call in case the first one fails
B: Remove the webhook and ask users to type every approval into the ERP by hand after they apply the action in Foundry
C: Schedule a nightly data sync from the ERP that overwrites the approval status in Foundry with whatever the ERP recorded that day
D: Configure the webhook as a writeback, which runs before the action's other rules so that a failed call stops the Ontology changes
K: D
G: ## Systems of action
Systems of action are the external systems where decisions finally take effect. An action type can call a webhook (a Data Connection concept) to send a request to systems such as SAP or Salesforce.
## Writeback versus side effect webhooks
- Writeback: runs before any other rules. If it fails, no other changes are made and the user sees an error. Only one webhook per action can be a writeback.
- Side effect: runs after the object changes. Failures are not shown to the user, and the user may see success before it runs. Several are allowed, in no particular order.
The docs add one caveat: with a writeback, the external call can still succeed while the Ontology change fails, so it gives "some degree" of transactionality, not a full guarantee.
Example: the ERP rejects an approval for a closed supplier; with a writeback webhook the order stays "pending" in Foundry and the user sees the error at once.
W: Writeback webhook: it executes first, and a failure stops the remaining rules, so Foundry is not changed when the ERP call fails.
X: A=Second side effect webhook: side effects run after the object edits, so the order is still approved in Foundry even if both calls fail.
B=Manual entry in the ERP: drops the integration and reintroduces the gap between the decision and the system of record.
C=Nightly overwrite sync: leaves Foundry wrong for most of a day and silently overwrites decisions instead of preventing the mismatch.
T: Use a writeback webhook when the external system must accept a change before Foundry records it.
V: Action types, Data Connection webhooks

@ PLTR-AWARE D1 T1.3 applied tradeoff
S: When a maintenance ticket is closed through an action, the team wants to notify a chat tool and update two separate reporting systems on a best-effort basis. A slow reporting system must not block the user. Which webhook setup fits?
A: Configure all three calls as side effect webhooks, which run after the object changes and do not hold up the user's success message
B: Configure all three calls as writeback webhooks, so that the action waits until every external system has confirmed the update
C: Configure the slowest reporting system as the writeback webhook, so the user waits only for that call and the others follow later
D: Skip webhooks and give each external system read access to the Foundry project so it can poll the ticket objects for changes
K: A
G: ## Two ways to reach external systems from an action
An action can call webhooks either as a writeback or as side effects. The choice is a tradeoff between consistency and user experience.
## When side effects win
- They run after the Foundry objects are modified, so the user sees success quickly.
- Several side effect webhooks can be configured in one action; they run in no particular order.
- Failures are not shown to the end user, so they suit notifications and best-effort updates.
The docs recommend side effect webhooks to send best-effort notifications or to write back to multiple external systems.
## When writebacks win
Only one webhook can be a writeback, and it blocks the action until it succeeds: right for a single critical system, wrong for three optional ones.
Example: a ticket closes instantly; the chat message and report updates follow a moment later.
W: Side effect webhooks: they suit best-effort updates to several systems and run after the edits, so a slow system does not block the user.
X: B=All writebacks: an action allows only one writeback webhook, and blocking on every system is what the team wants to avoid.
C=Slowest system as writeback: makes the user wait on the very system that is slow and lets a best-effort update fail the whole action.
D=Read access and polling: external systems would need Foundry access and custom polling, which is not the action-driven writeback the platform provides.
T: Side effect webhooks fit best-effort, multi-system notifications; a writeback fits one system that must succeed first.
V: Action types, Data Connection webhooks

@ PLTR-AWARE D1 T1.3 applied comparison
S: Three teams each built their own app to reassign field technicians, and each app edits the technician data in a slightly different way, with different checks. What does modelling the change as an Ontology action type provide?
A: A nightly reconciliation job that compares the three apps' edits and keeps whichever value was written most recently for each technician
B: A separate copy of the technician data for each app, so that each team's checks can stay different without affecting the other teams
C: One defined change with shared parameters, rules and validations that every application uses, so edits are applied the same way everywhere
D: A dashboard that shows which app changed each technician record, so that managers can correct inconsistent edits by hand afterwards
K: C
G: ## Actions are the "verbs" of the Ontology
Objects and properties describe the world; action types describe how people and AI may change it. An action is a single transaction that changes one or more objects based on defined logic.
## What an action type holds
- Parameters (the inputs a user fills in, often in a form).
- Rules that edit objects, properties and links.
- Validations, such as who may apply the action.
- Side effects, such as notifications or webhooks.
## Why one definition matters
The docs say the same action logic and validations can be made available across all user-facing applications, ensuring consistent edits. Changes are committed to the Ontology and reflected in every application.
Example: an Assign Technician action checks the technician's certification and region, then edits the link; every app calls the same action.
W: Shared action type: one definition of parameters, rules and validations is reused by every app, so the edit behaves the same everywhere.
X: A=Nightly reconciliation: accepts inconsistent edits and then guesses a winner, rather than preventing the inconsistency.
B=Separate copies per app: splits the truth into three versions, the opposite of a shared model that every app reads and writes.
D=Change-tracking dashboard: shows the problem but leaves fixing it to manual correction after the fact.
T: Define a change once as an action type so every application edits the Ontology the same way.
V: Ontology, Action types
