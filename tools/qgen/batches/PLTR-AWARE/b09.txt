@ PLTR-AWARE D3 T3.3 applied definition
S: A plant manager asks what an AIP Chatbot built in AIP Chatbot Studio (formerly AIP Agent Studio) actually is before agreeing to a pilot. Which description matches the documentation?
A: A private language model that Palantir fine-tunes on the plant's datasets, so that it answers questions without needing prompts, tools or Ontology access
B: A scheduled job that runs one prompt against every new object in a set and writes the model's answer into a property, without any conversation with users
C: An interactive assistant powered by an LLM, equipped with Ontology data, documents and tools, that can be used in apps such as Workshop or through APIs
D: A dashboard builder that turns plain-language questions into charts over datasets, without reading Ontology objects or calling any platform functions
K: C
G: ## What AIP Chatbot Studio builds
The documentation describes **AIP Chatbot Studio** as the place to build interactive assistants, called **AIP Chatbots**, that are equipped with enterprise-specific information and tools. The product was previously called AIP Agent Studio, and the chatbots were previously called AIP Agents, so older material uses "agent" for the same thing.
## What a chatbot is made of
- a **large language model** that does the reasoning,
- **instructions** that tell it its role,
- **retrieval context** from the Ontology, documents or functions,
- **tools** that let it query objects, run functions or apply actions.
## Where it runs
Chatbots can be deployed inside the platform, for example in a Workshop app through the AIP Chatbot widget, and outside it through the Ontology SDK and platform APIs. They support read and write workflows, so a user can ask a question and then have the chatbot carry out an Ontology edit through an action.
## Course framing
The Aware course calls this an "agentic AIP workflow": people and AI work on the same Ontology objects, with the platform's security model limiting what the model can reach.
W: Interactive assistant with Ontology, documents and tools: this is the documentation's definition, including deployment in Workshop and externally through the OSDK and APIs.
X: A=Fine-tuned private model: chatbots use models already enabled on the enrollment and are grounded through context and tools, not by training a new model.
B=Scheduled prompt job: running a function over new objects on a schedule is Automate's job; a chatbot is interactive and conversational.
D=Plain-language dashboard builder: chatbots read Ontology objects and call tools; they are not a chart builder over raw datasets.
T: An AIP Chatbot is an LLM-powered interactive assistant grounded in Ontology data, documents and tools and deployed into apps or through APIs.

@ PLTR-AWARE D3 T3.3 applied comparison
S: A team builds a chatbot that answers staff questions about a few hundred Safety Procedure objects. It never needs to change any data. Which way of giving it the procedures does the AIP Chatbot Studio documentation recommend for a case like this?
A: Retrieval context with Ontology context on the Safety Procedure objects, which fetches relevant objects with every message and is simple and fast
B: An Object query tool plus an Action tool on the Safety Procedure type, so the model can search the objects and also correct them when needed
C: A command tool that opens a separate Workshop app listing all procedures, so the chatbot can send each user to that app to look them up
D: Pasting the full text of every procedure into the instructions field, so that the model always holds all of the procedures in its system prompt
K: A
G: ## Two ways to give a chatbot information
AIP Chatbot Studio offers two families of building blocks:
- **Retrieval context** runs deterministically with every new user message: relevant Ontology objects, documents or function output are fetched and passed to the model along with the question.
- **Tools** are capabilities the model chooses to call, such as querying objects, running functions, applying actions or asking the user for clarification.
## Which to start with
The getting-started guide says retrieval context is **simple, fast and recommended for most use cases**, while tools are for **complex and action-taking** chatbots. A read-only question-answering assistant over one object type is the textbook case for retrieval context.
## Ontology context
Ontology context can pass a fixed set of objects or perform a semantic search for the most relevant ones, and you can choose which properties are printed for the model.
## Example
"What protective equipment is needed for tank cleaning?" retrieves the matching procedure objects and the model answers from them.
W: Ontology retrieval context: the documentation recommends retrieval context for most use cases and reserves tools for complex or action-taking chatbots; this one only reads procedures.
X: B=Object query plus Action tool: adding a write tool to a read-only assistant gives it power it does not need, and tools are the more complex option.
C=Command tool to another app: sending users elsewhere does not let the chatbot answer from the procedures at all.
D=Everything in the instructions: instructions describe the role and task; stuffing hundreds of documents into them wastes the context window and goes stale when procedures change.
T: For a read-only assistant over Ontology data, start with retrieval context; add tools only when the chatbot must do complex or action-taking work.

@ PLTR-AWARE D3 T3.3 applied troubleshooting
S: A builder wants a chatbot to pick the ten most relevant of 40,000 Incident objects for each question by semantic search. Ontology context on the Incident type can only be set to hand over a fixed set of objects. What is the most likely reason?
A: Semantic search in Ontology context only works for document context, so incidents must first be exported as PDF files and attached to the chatbot
B: Ontology context is limited to object sets of at most a few hundred objects, so the Incident type must be split into several smaller object types
C: The builder lacks the Owner role on the chatbot file, and only owners are allowed to switch Ontology context from a fixed set to a semantic search
D: The Incident object type has no vector embedding property, which Ontology context needs before it can search for the most relevant objects
K: D
G: ## Two modes of Ontology context
The retrieval context documentation says Ontology context can either:
- supply a **fixed set of N objects**, or
- perform a **semantic search** to find the **K most relevant objects** for the user's message, **provided that the object type has a vector embedding property**.
## What a vector embedding is
The core concepts page explains embeddings as numerical representations of text that capture its meaning. Similar texts get similar vectors, so a question can be matched to the incidents whose descriptions mean something close, even with different words.
## Fixing the gap
The data side must produce an embedding for each incident (for example from its description) and store it as a vector property on the object type. Then the chatbot can retrieve the top matches for each question instead of a fixed set.
## Why not the fixed set
Handing 40,000 incidents to the model would overflow the context window; semantic search exists so that only the relevant few are passed in.
W: Missing vector embedding property: the documentation makes semantic search in Ontology context conditional on the object type having a vector embedding property.
X: A=Export as PDFs: Ontology context supports semantic search on objects directly once embeddings exist; converting objects to documents throws away their structure.
B=Size limit, split the type: the docs state no such object-count limit; semantic search is how large object types are handled.
C=Owner role needed: the choice between fixed set and semantic search depends on the data, not on the builder holding a particular role.
T: Semantic search over objects in a chatbot needs a vector embedding property on the object type; without it only a fixed set can be passed.

@ PLTR-AWARE D3 T3.3 applied troubleshooting
S: A chatbot in a Workshop app told a planner that a spare part was out of stock, while the warehouse system shows plenty on hand. Before changing any configuration, the builder wants to see how the chatbot arrived at that particular answer. What does AIP Chatbot Studio provide for this?
A: View reasoning on that response, which lets the builder investigate the reasoning process the model went through to generate the answer
B: The Ontology edit history of the Part object type, which records every question users asked a chatbot and each answer that it gave them
C: Asking the chatbot in a brand-new session why it answered that way, because a new session carries over the earlier conversation's steps
D: Raising the temperature and asking the same question again, because comparing different answers shows which step returned bad stock data
K: A
G: ## Look before you change
When a chatbot gives a wrong answer, the cause can sit in several places: the instructions, the retrieval context, a tool that returned bad data, or the model's own reasoning. Changing settings at random hides the cause. The first step is to see what actually happened for that response.
## View reasoning
The tools documentation says that when a chatbot is deployed in edit mode, view mode, Workshop or AIP Threads, you can **view reasoning** below a response to **investigate the LLM reasoning process used to generate that response**. The getting-started guide adds that while testing in the editor you can expand the reasoning steps of each response.
## What to look for
- Did the chatbot call the stock tool at all, or did it guess?
- What input did it pass, for example the right part number?
- What did the tool return, and did the model read it correctly?
## Then fix the real cause
A missing tool call points to the tool description and instructions; a wrong input points to how the part is identified; a wrong tool result points to the function or data behind it.
W: View reasoning: the documentation offers it below a response in edit mode, view mode, Workshop and AIP Threads precisely to investigate how the model produced that answer.
X: B=Ontology edit history: it records edits to objects made through actions, not chat questions and answers, and a stock answer edits nothing.
C=New session: a new session starts without the earlier conversation's history, so the chatbot cannot reconstruct how it produced the old answer.
D=Higher temperature and retry: more randomness produces a different answer, not an explanation of the original one.
T: To debug a chatbot's wrong answer, view the reasoning behind that response before changing instructions, tools or models.

@ PLTR-AWARE D3 T3.3 applied use-case
S: Dispatchers often type requests such as "move the Hamburg shipment to Friday" when several shipments match. The chatbot currently guesses one and proceeds. Which tool lets the chatbot stop and ask the dispatcher which shipment is meant?
A: The Request clarification tool, which pauses the chatbot's execution and asks the user for clarification before it continues with the task

G: ## Tools beyond data and actions
The tools page lists six tool types: Action, Object query, Function, Update application variable, Command, and **Request clarification**. The last one lets the chatbot **pause its execution and request clarification from the user**.
## When to use it
Ambiguous requests are common in operational chat: several objects match, a parameter is missing, or two readings are possible. Asking is cheaper and safer than guessing, especially when the next step edits data.
## How it fits with instructions
The instructions can say when to ask, for example "if more than one shipment matches, ask which one before rescheduling". The tool gives the model a proper way to do so.
## Other tools in this scenario
- Object query finds the candidate shipments.
- Action applies the reschedule once the right shipment is known.
W: Request clarification tool: the docs describe it as the tool that pauses the chatbot and asks the user for clarification, which is exactly what ambiguous requests need.
X: B=Command tool: commands trigger operations in other Palantir applications; sending the dispatcher away does not resolve the question inside the conversation.
C=Update application variable: storing candidates in a variable does not ask the user anything; the chatbot would still choose alone.
D=Higher temperature: temperature makes answers more random, not more accurate, so guessing gets less predictable.
T: When a request is ambiguous, give the chatbot the Request clarification tool so it pauses and asks instead of guessing.

@ PLTR-AWARE D3 T3.3 applied troubleshooting
S: A chatbot calls a published Logic function as a Function tool. Last week a colleague published a new version of that function with a different output, and the chatbot's answers changed without anyone touching the chatbot. How can the builder stop this from happening again?
A: Copy the Logic function into the chatbot's instructions as plain text, so that the model follows the steps itself without calling any function
B: Ask the colleague to keep each new version unpublished, because chatbots can only ever call functions that are saved but have not been published
C: Delete the older versions of the Logic function, so that only one version exists and the chatbot always calls the same logic in the future
D: Configure the Function tool to use a specific published version of the Logic function instead of automatically using the latest version
K: D
G: ## Function tools and versions
The tools documentation says a **Function** tool lets the model call any Foundry function, including published AIP Logic functions. **The latest version of the function is used automatically**, but you can **specify a published version for more granular control**.
## Why answers changed
With the default, every new published version becomes the chatbot's behaviour at once. A changed output shape or meaning flows straight into the chat, without testing.
## A safer routine
- Pin the tool to a tested version.
- When a new version is published, test the chatbot against it (for example with an AIP Evals suite on the chatbot published as a function).
- Move the pin once the results are good.
This is the same change-management idea as testing on a branch before merging: deliberate upgrades instead of silent ones.
W: Pin a published version: the docs offer exactly this control in place of the automatic latest-version default, so upgrades become deliberate.
X: A=Copy into instructions: the model would have to imitate the function's logic in text, losing the tested, deterministic steps the function provides.
B=Keep versions unpublished: chatbots call published functions; this would block the colleague's work and is not how the tool works.
C=Delete older versions: removing history does not stop the next publish from changing behaviour, and it removes the version you may want to roll back to.
T: A chatbot's Function tool follows the latest version by default; pin a published version when behaviour must not change without testing.

@ PLTR-AWARE D3 T3.3 applied troubleshooting
S: After a long planning conversation, a chatbot suddenly returns an error and asks the user to start a new session. Its Ontology context passes all 60 properties of each retrieved object. What best explains the error?
A: The chatbot's session expired after a fixed time limit, and its sessions always end after thirty minutes whatever the length of the conversation
B: The context window was exceeded, because it holds the system prompt, the conversation history and the injected context such as retrieved objects
C: The user's access to the Ontology was revoked mid-session, which always appears as a new session request rather than as a permission error
D: The model's daily token budget for the whole enrollment ran out, so every user's chatbot sessions must be restarted on the following day
K: B
G: ## The context window
The core concepts page defines the **context window** as the amount of text (in tokens) an LLM can process at one time. In AIP Chatbot Studio it includes:
- the system prompt (instructions, tool and variable descriptions),
- the **conversation history**,
- injected information: **retrieval context**, application state and tools.
**Exceeding the context window results in an error, prompting users to create a new session.**
## Why this conversation hit it
Every turn adds history, and every message brings retrieved objects. Printing all 60 properties per object multiplies the size quickly.
## Making room
Ontology context lets you choose which properties are printed and passed to the model. Keeping only the properties the task needs keeps each turn small, lowers cost and often improves focus.
W: Context window exceeded: the documentation names this exact error and says the window holds the system prompt, history and injected context, which here grows fast with 60 properties per object.
X: A=Fixed session timeout: the docs tie the new-session prompt to exceeding the context window, not to a time limit.
C=Revoked access: losing access would show up as missing data or permission errors, not as a request to start a new session.
D=Daily enrollment budget: the documentation ties the request to start a new session to exceeding the context window, which a long conversation with 60 properties per object explains on its own.
T: Long conversations plus large retrieved context can overflow the context window; trim properties and context before blaming anything else.

@ PLTR-AWARE D3 T3.3 applied troubleshooting
S: A chatbot has a Function tool that checks spare-part stock, but it rarely calls it and instead guesses availability. The tool's description reads "tool 1" and the instructions do not mention it. Which change addresses the root cause?
A: Switch the chatbot to a larger model, because only the largest models are able to discover by themselves which tools exist and what they do

D: Add a second copy of the same tool under another name, so that the model sees the stock check twice and becomes more likely to call one of them

G: ## How a chatbot learns about its tools
The core concepts page says **instructions, tool descriptions and variable descriptions are compiled into the raw system prompt**. That text is how the model learns what it can do. The page adds: an LLM **only has access to the information you explicitly provide**.
## What good descriptions look like
- Instructions start with the most important information (the task), then cover data and how to use tools and state.
- Each tool description gives concrete steps on **how and when** to use it, for example: "Use this tool whenever the user asks whether a part is in stock. Input: the part number. Output: units on hand per warehouse."
- In the instructions, refer to the tool by name so the model knows how it fits the business logic.
## Why guessing happened
With "tool 1" and no mention in the instructions, the model has no reason to connect stock questions to the tool, so it falls back to plausible-sounding guesses.
W: Clear tool description and instructions: these texts are compiled into the system prompt, and the docs ask for concrete guidance on how and when to use each tool.
X: A=Larger model: no model can infer a tool's purpose from "tool 1"; the missing information is the problem, not model size.
B=Remove retrieval context: starving the model of useful context does not tell it what the tool is for and makes other answers worse.
D=Duplicate tool: two identically vague tools add confusion and tokens without explaining when to use either.
T: A chatbot uses tools well only when its instructions and tool descriptions say concretely what each tool does and when to call it.

@ PLTR-AWARE D3 T3.3 applied tradeoff
S: A chatbot is told in its instructions to put the sites it finds into the `selected_sites` variable using the Update application variable tool, but it sometimes forgets or fills it with the wrong set. The sites always come from its Object query tool. Which change does the documentation recommend?
A: Repeat the instruction three times in the system prompt, in capital letters, so that the model gives the variable update a higher priority

G: ## Two ways a variable can change
The application state documentation describes:
- **Automatic (deterministic) updates**: a variable is mapped to the output of the Object query tool, function-backed context or Ontology context. After each run the latest output is written to the variable when the model finishes streaming.
- **Model-driven (non-deterministic) updates** through the Update application variable tool, useful when the model must decide whether and what to update.
## The recommendation
The docs **recommend deterministic updates rather than non-deterministic updates to avoid LLM confusion**. When the value always comes from one tool's output, there is no decision for the model to make, so let the platform do it.
## Related settings
- **Value visibility**: only let the model read a variable's value when it needs it.
- **Deterministic tool inputs**: Action and Function tools can take inputs straight from variables instead of model-generated values, improving consistency and reducing tokens.
W: Automatic update from the tool output: the docs recommend deterministic updates over model-driven ones, and the value here always comes from the Object query tool.
X: A=Repeat in capitals: louder prompts may help a little but leave a mechanical step to a non-deterministic model.
B=Maximum temperature: more randomness makes the update step less reliable, not more.
C=Remove the variable: it gives up the integration with the app instead of fixing how the variable is filled.
T: When a variable's value always comes from a tool's output, map it deterministically instead of asking the model to update it.

@ PLTR-AWARE D3 T3.3 applied troubleshooting
S: A builder tests a chatbot published as a Function in an AIP Evals suite. Later test cases mention details from earlier test cases, as if the chatbot remembered them, and scores vary with the run order. Every test case passes the same `sessionRid`. What should the builder change?
A: Add more test cases after each existing one, so that the remembered details are spread over a larger number of cases and matter less to the score
B: Lower the chatbot's temperature to zero, because remembered details only appear when the model is allowed to produce more random answers
C: Move the evaluation suite to a different project from the chatbot, so that the suite's runs are kept separate from the chatbot's earlier sessions
D: Set `sessionRid` to null in the test cases, so that each test case starts a new session instead of continuing the same existing conversation
K: D
G: ## Sessions in a chatbot function
A chatbot published as a Function takes an optional `sessionRid`:
- **leave it out** to start a new session,
- **provide one** to continue an existing session, with its conversation history.
Each run returns a `sessionRid` so that a caller can continue the conversation on purpose.
## Testing advice in the docs
The chatbots-as-functions page warns that when setting up test cases in AIP Evals, `sessionRid` should be **null** to start a new session, because a provided session RID makes the chatbot **continue an existing session, which is likely not the intent during testing**. The same page notes that object set variables must be null or hold a real value.
## Where the suite lives
The page also says the evaluation suite **must be in the same project** as the chatbot.
## Why it matters
Independent test cases are the basis for meaningful scores. Shared history makes each result depend on the previous ones.
