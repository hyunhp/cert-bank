@ PLTR-AWARE D2 T2.1 applied definition
S: A new builder is following a guide to bring data from a company S3 bucket into Foundry. The guide asks them to create a source first and a sync afterwards. What is the difference between the two?
A: The source holds the connection to the external system, such as its location, credentials and network path, while a sync defines which data to read and which dataset receives it
B: The source is the dataset in Foundry that stores the imported files, while a sync is the network rule that lets Foundry reach the external bucket on a defined port and protocol
C: The source is a scheduled job that copies data from the bucket every night, while a sync is the encrypted credential record that the job uses to sign in to the external system
D: The source lists the users who may read the imported data, while a sync is the transform that cleans and joins the raw files before they are stored in the output dataset
K: A
G: ## Two building blocks in Data Connection
Data Connection is the Foundry application that synchronizes data from external systems into Foundry. Two of its core concepts are easy to mix up:
- A **source** represents a single connection to an external system: where it is (typically a URL), the credentials to authenticate, and the worker and networking used to reach it. A source is created from a connector (source type) such as S3, PostgreSQL or REST API.
- A **capability** runs over that connection. The most common one is a **batch sync**, which defines what data to read and which Foundry dataset to write it into.
## How they fit together
One source can have many syncs. Example: a source points at `s3://sales-bucket/` with its credentials and egress policy; one sync pulls the `orders/` folder into an `orders_raw` dataset, another pulls `returns/` into `returns_raw`.
The connection details are set up once; each sync only describes the data it moves.
W: Source = connection, sync = data movement: the docs define a source as the connection (location, credentials, worker/networking) and a batch sync as the definition of what to read and which dataset to write.
X: B=Source as dataset, sync as network rule: the dataset is the output of a sync, and the network rule is an egress policy, a separate resource attached to the source.
C=Source as job, sync as credential: credentials are stored as part of the source configuration; the scheduled run belongs to the sync, the reverse of what this says.
D=Source as reader list, sync as cleaning transform: access to the data comes from project permissions on the output location, and Data Connection deliberately offers minimal transformation; cleaning happens later in pipelines.
T: A source is the reusable connection to an external system; syncs run over it and write chosen data into Foundry datasets.

@ PLTR-AWARE D2 T2.1 applied comparison
S: A team on a cloud-hosted Foundry enrollment wants to connect to an S3 bucket that is reachable over the public Internet. Which kind of network egress policy fits this source?
A: An agent proxy policy, because every connection from Foundry to a storage bucket has to pass through an agent installed inside the customer's own network
B: No egress policy at all, because storage buckets are reached through the cloud provider's backbone and Foundry never applies firewall rules to that traffic
C: A direct connection policy, because the bucket is reachable from Foundry's network, which for a cloud-hosted Foundry instance means the public Internet
D: A private link policy, because the docs require private links for every cloud storage service so that no traffic between Foundry and AWS crosses the Internet
K: C
G: ## Egress policies describe the network path
Foundry blocks outbound traffic by default. A **network egress policy** allowlists a destination (domain, IP or CIDR, plus port) and the path used to reach it. A Foundry worker source needs a policy attached before it can connect.
## Picking the policy type
- **Direct connection policy**: for systems directly reachable from Foundry. On a cloud-hosted Foundry instance this means the public Internet; on a privately hosted Foundry, the network where Foundry is installed. The external system must accept inbound connections from Foundry.
- **Agent proxy policy**: for systems in a different network, typically on-premises, reached through a Data Connection agent.
- Other types (private link, bucket endpoint, secure tunnel) cover special network setups.
Example: the course's S3 exercise uses a direct-connection egress policy such as `bucket-name.s3.us-east-1.amazonaws.com` on port `443`. (If Foundry runs in AWS and the bucket is in the same region, the docs require extra bucket endpoint configuration.)
W: Direct connection policy: the bucket is reachable from Foundry's network over the Internet, which is exactly the case the docs give for direct connection policies on cloud-hosted Foundry.
X: A=Agent proxy policy: agents are for systems hosted in a separate network such as on-premises; an Internet-reachable bucket does not need one.
B=No egress policy: Foundry worker sources need egress policies to route traffic; without one the connection is blocked.
D=Private link for every cloud storage: private link policies exist for traffic over a configured private link, not as a requirement for all cloud storage.
T: Reachable from Foundry's network (the Internet, for cloud-hosted Foundry) means a direct connection egress policy.

@ PLTR-AWARE D2 T2.1 applied comparison
S: A company runs a cloud-hosted Foundry enrollment and wants to sync tables from a PostgreSQL database in its own data center. The database is not reachable from the Internet. Which setup fits the recommended architecture?
A: Open an inbound firewall rule from Foundry's egress IP ranges to the database and attach a direct connection policy, since direct is the only option for databases
B: Install a Data Connection agent inside the company network and use a Foundry worker source with an agent proxy egress policy, so compute runs in Foundry
C: Export the tables to CSV files every night with a script, upload them by hand into a Foundry dataset, and skip the source because databases cannot be connected
D: Install a Data Connection agent and configure it as an agent worker that runs every sync on the agent host, since this is the recommended mode for new sources
K: B
G: ## Reaching a system in another network
When the external system sits in a different network from Foundry, for a cloud-hosted Foundry usually an on-premises data center, Foundry cannot connect to it directly. The docs describe an **agent**: a downloadable program installed inside the organization's network and managed from Data Connection.
## Agent proxy vs agent worker
- **Foundry worker with an agent proxy policy** (recommended): the agent opens an outbound connection to Foundry and only proxies network traffic. The sync itself runs in Foundry's containerized, scalable compute.
- **Agent worker** (legacy): the agent host runs the sync itself. Still supported for existing sources, but the docs recommend migrating to Foundry worker.
Example: an agent on a VM in the data center can reach `pg01.corp.local:5432`; the source uses an agent proxy policy for that host and port, and syncs run in Foundry.
W: Agent plus agent proxy policy: the docs call Foundry worker with agent proxy the recommended architecture for systems on private networks; the agent acts as a network tunnel while capabilities run in Foundry.
X: A=Inbound rule plus direct connection: direct connection is for systems reachable from Foundry's network; opening a private database to the Internet is not what the docs recommend for on-premises systems.
C=Manual CSV export: Data Connection supports relational databases out of the box; manual uploads lose scheduling, robustness and an as-is raw source of truth.
D=Agent worker for new sources: agent worker is in the legacy phase; new sources run on a Foundry worker, and the agent is used only as a proxy.
T: On-premises system plus cloud Foundry: install an agent and give a Foundry worker source an agent proxy egress policy.

@ PLTR-AWARE D2 T2.1 applied definition
S: A manager asks why a builder had to request an egress policy before a new source could connect, even though the external system is a well-known public service. What is the purpose of an egress policy?
A: It encrypts the credentials of the source, so that passwords and tokens stored in Foundry cannot be read by users who only have viewer access to the project
B: It sets how often a sync may run against the external system, so that scheduled jobs do not overload the source with requests during business hours
C: It records which Foundry users have read the imported data, so that auditors can trace every dataset back to the person who first opened it in Foundry
D: It allowlists a specific destination and path that workloads may reach, since Foundry blocks outbound traffic unless a policy explicitly permits it
K: D
G: ## Network egress in Foundry
**Network egress** is any traffic that starts inside Foundry and connects to an external system. Foundry applies strict firewalls to it: a workload can only reach destinations that a network egress policy allows.
## What a policy contains and why it is controlled
- An address (domain, IP or CIDR), a port and, for direct connection policies, a protocol.
- Policies are **opt-in**: they must be explicitly attached to a workload such as a Data Connection source. The docs tie this to the principle of least privilege.
- Opening an egress route is always a security risk, because a workload that can connect out could also send data out. The docs therefore have Information Security Officers approve policies and limit who may use them.
Example: a source for `api.example.com` gets a policy for that domain on port `443`; it still cannot reach any other host.
W: Allowlisted destination: the docs describe egress policies as firewall rules that define how each target system can be reached and which destinations are permitted; without one the connection is blocked.
X: A=Encrypts credentials: credentials are encrypted and stored by the platform as part of the source; that is not what an egress policy does.
B=Limits sync frequency: run timing is set by schedules and build policies on the sync, not by the network policy.
C=Records readers: data access auditing is a separate concern; an egress policy controls outbound network paths.
T: An egress policy is a reviewed allowlist entry that lets a specific workload reach a specific external destination.

@ PLTR-AWARE D2 T2.1 applied troubleshooting
S: A builder proposed a direct connection egress policy for a partner API yesterday, attached it to a new source today, and the source still cannot connect. The policy's state shows Pending approval. What explains this, and what is the next step?
A: Workloads using a policy that is still pending approval fail to run, so an administrator with the egress management workflow must approve it first
B: The policy needs a day to replicate to every Foundry region, so the builder should wait and retry the connection without contacting anyone else
C: The source must be recreated whenever a policy changes state, so the builder should delete the source and build a new one with the same settings
D: A pending policy only allows read traffic, so the builder should switch the source to write mode until the policy finishes its review cycle
K: A
G: ## The life cycle of an egress policy
Any Foundry user may **propose** a network egress policy. New policies start in the state `Pending approval`.
- `Pending approval`: the policy can already be attached to a workload, but workloads that try to use it **fail to run**.
- `Active`: approved; importers can attach it and the workload may egress.
- `Paused`: blocked by Palantir's Information Security team.
- `Revoked`: revoked by the enrollment's Information Security Officers.
## Who approves
Approving or creating policies requires the `Manage network egress configuration` workflow, which by default comes with the Enrollment Administrator and Information Security Officer roles. Pending proposals appear in an approvals inbox in Control Panel. That is why the course lists "permission to create data egress policies" as a prerequisite.
W: Pending approval blocks the workload: the docs state that workloads using a pending policy fail; once an administrator with the egress workflow approves it, the attached source can connect.
X: B=Regional replication delay: there is no such waiting period in the docs; the state itself says the policy has not been approved.
C=Recreate the source: attaching the policy was already correct; the source does not need to be rebuilt, the policy needs approval.
D=Read-only pending mode: pending policies do not allow partial traffic; workloads using them fail entirely.
T: A proposed egress policy does nothing until it is approved; a pending policy makes the workload fail.

@ PLTR-AWARE D2 T2.1 applied troubleshooting
S: An Information Security Officer approved an egress policy for an internal API and shared it with a builder as a Viewer. The builder can see the policy but cannot attach it to a new source. What is missing?
A: The builder needs the Owner role on the Foundry project, because egress policies can only be attached to sources that live in a project the user owns
B: The builder needs Import permission on that policy, because viewers can see a policy exists but only importers may attach it to a workload
C: The builder needs the Information Security Officer role too, because only that role may attach any approved egress policy to a source
D: The builder needs to wait for the next platform release, because newly approved policies can only be attached after the following upgrade
K: B
G: ## Sharing an egress policy
When an Information Security Officer approves a policy, they decide which users or groups get **View** or **Import** on it:
- **View**: see that the policy exists, but not use it in any workload.
- **Import**: see the policy and attach it to workloads such as Data Connection sources, external transforms or functions.
The docs recommend making anyone who might ever need a policy a viewer, and limiting importers to trusted, trained developers, because an importer can run code in Foundry that talks to the destination.
## Why this matters
Attaching a policy to a source is what lets that source egress. Separating "can see" from "can use" keeps the number of people able to open a network path small.
W: Import permission: the docs require the Importer permission on the specific policy to assign it to a workload; View only shows that it exists.
X: A=Project Owner: project roles govern the source resource itself; using a policy is controlled on the policy, per user or group.
C=Information Security Officer role: that role approves and manages policies; ordinary builders attach them once they hold Import permission.
D=Wait for a release: an approved policy is active immediately; nothing in the docs ties attaching it to a platform upgrade.
T: Viewers can see an egress policy; only importers can attach it to a source.

@ PLTR-AWARE D2 T2.1 applied troubleshooting
S: A builder sets up a PostgreSQL source on a Foundry worker. The egress policy is active and correct, but the connection test fails with a PKIX path building error. The database uses a certificate issued by the company's internal certificate authority. What should the builder do?
A: Request a second egress policy for the same host on a different port, since PKIX errors mean the network route is too narrow for an encrypted session
B: Replace the database password with a personal user account, since PKIX errors appear when a service account lacks the privileges to read the tables
C: Add the internal certificate authority's certificate to the source as a server certificate, so Foundry can trust the certificate the database presents
D: Switch the source to a legacy agent worker, since Foundry worker sources cannot connect to any database that uses a non-public certificate authority
K: C
G: ## How Foundry trusts a server
When Foundry connects over TLS, the external system presents a **server certificate**. Foundry validates its chain up to a trusted root certificate authority (CA). Well-known public CAs are trusted by default.
If the system uses a self-signed certificate or one from a private or internal CA, Foundry cannot validate it, and the connection fails with `PKIX` or `SSLHandshakeException` errors.
## The fix
Add the missing certificate (the certificate only, never a private key) as a **server certificate** on the source. For Foundry worker sources, certificates are attached to the source itself; for legacy agent worker sources they go on the agent.
Example: the course's Postgres exercise includes a step to configure certificates; for Amazon RDS the PostgreSQL connector docs mention adding the RDS root CA as a server certificate.
W: Add a server certificate: a PKIX error with a certificate from an internal CA is the textbook case in the docs for adding that CA certificate to the source's truststore.
X: A=Second egress policy: the network path already works (the TLS handshake starts); PKIX is a trust problem, not a routing problem.
B=Personal account: a privilege problem shows up as an authentication or authorization error after the connection is established; using personal credentials also goes against the docs' advice to use a dedicated service account.
D=Switch to agent worker: Foundry worker sources support server certificates on the source; agent worker is legacy and not needed for this.
T: PKIX or SSL handshake errors mean Foundry does not trust the server's certificate: add the right server certificate to the source.

@ PLTR-AWARE D2 T2.1 applied comparison
S: A database team says their server requires mutual TLS: every client must prove its own identity with a certificate before any query is accepted. What does the Foundry source need in that case?
A: A server certificate only, provided as the certificate without a private key, because server certificates are how Foundry proves its own identity to the database
B: A second egress policy of the agent proxy type, because mutual TLS connections can only travel through an agent installed inside the database team's network
C: A personal user token in place of the service account password, because mutual TLS checks the identity of the human who triggers each sync run
D: A client certificate with its private key, because in mutual TLS the Foundry client presents its own certificate so the database can verify Foundry
K: D
G: ## Server certificates and client certificates
The Data Connection docs separate two cases:
- **Server certificate (TLS)**: the external system proves its identity to Foundry. You add one only when the system's certificate is not signed by a public CA. It is provided as the certificate only, never the private key.
- **Client certificate (mTLS)**: Foundry proves its identity to the external system. With mutual TLS, both sides verify each other. It is provided as a certificate and private key pair.
## Putting it together
A source can need both: a server certificate because the database uses an internal CA, and a client certificate because it demands mTLS. Both are attached to the source on a Foundry worker.
W: Client certificate and private key: mTLS means the client must prove its identity, and the docs say client certificates are provided as a certificate and private key pair.
X: A=Server certificate only: a server certificate lets Foundry verify the database, not the reverse; it cannot prove Foundry's identity.
B=Agent proxy policy: the network path type has nothing to do with TLS mode; mTLS works over direct connection policies too.
C=Personal user token: mTLS authenticates the client system with a certificate, not the person who runs the sync.
T: Server certificates let Foundry trust the system; client certificates (with private key) let the system trust Foundry in mTLS.

@ PLTR-AWARE D2 T2.1 applied use-case
S: A builder creates a batch sync from a new source and must choose an output location for the synced dataset. Which choice follows the documented best practice?

G: ## Output location decides who can read the data
Creating a batch sync also creates the Foundry dataset that receives the synced data. Its **output location** determines who can access the data, through **project-level permissions**. A default output folder can be set on the source and overridden per sync.
## The recommended pattern
- Keep each source in its own project in the datasource layer.
- Write each sync's output dataset into the **same project** as the source.
- Downstream teams import the datasets they need into their own projects.
This keeps all raw data from one connector under one set of permissions. The docs also warn that syncing into an existing dataset is supported but not recommended, because the sync may overwrite data already there.
Example: project `Datasource - Warehouse S3` holds the source, `orders_raw` and `returns_raw`; a logistics project imports `orders_raw` for its pipeline.
W: Same project as the source: the docs recommend saving sync datasets alongside the connector so that all data from a given connector is permissioned uniformly.
X: A=Personal folders: private copies scatter raw data and its permissions; the docs' pattern is one permission boundary per source.
C=Downstream application project: raw data would inherit the app team's permissions; downstream projects should import the dataset instead.
D=Existing curated dataset: syncing into an existing dataset is not recommended because the sync can overwrite what is already there.
T: Put a sync's output dataset in the same project as its source, then import it downstream.

@ PLTR-AWARE D2 T2.1 applied troubleshooting
S: A nightly batch sync failed halfway through copying files because of a network interruption. Users ask whether the output dataset now holds a mix of old and new files. What is the state of the dataset?
A: It holds every file copied before the failure, because each file is committed on its own as soon as it reaches Foundry
B: It is empty, because a failed run clears the output dataset so that no outdated data can be used downstream
C: It is unchanged from its state before the run, because the sync writes in one transaction that is aborted on failure
D: It is locked until an administrator repairs it by hand, because a failed run leaves the dataset in a broken state
K: C
G: ## Batch syncs are transactional
Each batch sync run writes its data within a **single transaction** on the output dataset. If the run fails at any point, the transaction is aborted and nothing from that run is committed.
- A partial failure does not produce partial data.
- The dataset stays exactly as it was before the failed run.
- The error message and stack trace for the failed run are available on the sync's run history.
## Practical consequence
Example: a sync of one million files fails after all but one were uploaded; none of them are committed. Downstream users keep seeing the last good version until a run succeeds. For very large file syncs, the docs suggest smaller incremental batches so a failure only affects the current batch.
W: Unchanged dataset: the docs state that a failed batch sync aborts its transaction, so the output dataset remains as it was before the run.
X: A=Partial commit: files are not committed one at a time; the whole run is one transaction.
B=Emptied dataset: a failure does not clear existing data; the previous committed version stays visible.
D=Locked dataset: no manual repair is needed; the next successful run commits normally.
T: A failed batch sync commits nothing: users keep the last good data, never a partial mix.

@ PLTR-AWARE D2 T2.1 applied comparison
S: A team connects two systems in the same week: an S3 bucket full of CSV and PDF files, and a PostgreSQL database with an orders table. Which kind of batch sync fits each one?
A: A table batch sync for the bucket, which infers one schema for all files, and a file batch sync for the database, which exports each table as a file
B: A file batch sync for the bucket, which copies files without a schema, and a table batch sync for the database, which reads rows through a query
C: A streaming sync for the bucket, because files arrive continuously, and a media sync for the database, because each row is stored as a media item
D: A file batch sync for both systems, because every batch sync stores raw files and the database rows are converted into CSV files afterwards
K: B
G: ## Two kinds of batch sync
The docs describe two main types:
- **File batch syncs** copy files **without a schema** into a Foundry dataset. Downstream transforms then read or parse those files. Typical systems: filesystems and blob stores such as S3, ABFS, Google Cloud Storage, SMB and SharePoint Online.
- **Table batch syncs** copy data **with a schema**. A query defines what is pulled, and the sync maps the external types to Foundry types. Typical systems: databases and SaaS systems such as PostgreSQL, SQL Server, SAP, Salesforce.
Most systems support one of the two; some support both.
## Related capabilities
Streaming syncs read from message queues (Kafka, Kinesis, Pub/Sub) into streams; media syncs load PDFs, images and video into media sets, which the docs recommend over datasets for media.
W: File sync for the bucket, table sync for the database: blob stores are the docs' standard example of file batch syncs, and databases of table batch syncs defined by a query.
X: A=Reversed types: a bucket of mixed CSV and PDF files has no single schema to infer, and database tables are synced as rows with a schema.
C=Streaming and media: streaming syncs need a low-latency message feed, not a bucket; media syncs are for media files, not database rows.

@ PLTR-AWARE D2 T2.1 applied tradeoff
S: A warehouse list of about 2,000 rows is maintained in a database, and rows are often edited or removed. A builder wants the Foundry dataset to always match the current list after each nightly sync. Which transaction type should the sync use?
A: SNAPSHOT, because each run replaces the previously ingested data with the current contents of the table
B: APPEND, because each run adds the new rows and also removes the rows that were deleted in the database
C: APPEND, because it is always faster and never needs to read the rows that already exist in the dataset
D: SNAPSHOT, because it keeps every earlier version of each row visible side by side in the current view
K: A
G: ## SNAPSHOT and APPEND in a batch sync
A batch sync's **transaction type** decides what each run does to the output dataset:
- `SNAPSHOT`: the run's data **overwrites** what was previously ingested. The current view shows exactly what the last run read.
- `APPEND`: the run's data is **added** to what is already there. Nothing previously ingested is changed or removed.
## Choosing for a small, changing table
For a small reference table where rows are edited and deleted, a nightly snapshot is simple and always correct: the dataset mirrors the table. Appending would keep the old versions and the deleted rows.
Append-style incremental syncs shine for large tables that only grow, where re-reading everything every night is too expensive. (Earlier versions remain available through the dataset's transaction history, not side by side in the current view.)
W: SNAPSHOT: each run overwrites the previous data, so the dataset always reflects the current table, including edits and deletions.
X: B=APPEND removes deleted rows: APPEND only adds data; deleted source rows stay in the dataset.
C=APPEND always faster: on 2,000 rows speed is not the concern, and appending would leave stale and deleted rows in the view.
D=SNAPSHOT keeps old versions in view: the current view of a snapshot shows only the latest run; old versions live in history, not side by side.
T: Use SNAPSHOT when the dataset must mirror a small, changing source; APPEND only adds data.

G: ## Network paths with an agent
With an agent proxy policy, the agent sits inside the organization's network and needs **two** network paths:
