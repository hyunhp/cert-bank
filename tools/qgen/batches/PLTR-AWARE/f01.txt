S: A platform lead asks whether Global Branching makes release management across development, test and production environments unnecessary. Which answer matches the documentation?
A: Yes, because merging a branch into main deploys the same change to the organization's other environments as well
B: Yes, because release management applies to code repositories and is not used for pipelines or Ontology resources
C: No, because Global Branching is limited to datasets, so release management is still needed for Ontology changes
D: No, the two solve different problems: one isolates work in progress, the other promotes versions between environments
K: D
G: ## Two different problems
- Global Branching: develop and test changes in isolation on a branch, merge into `main` when the feature is complete.
- Release management: manage multiple versions of resources across environments that serve different purposes (for example development, test, production).
## Using both
The docs say the two should not be seen as alternative solutions but as complementary solutions to different problems. Their example: build a large feature on a global branch, merge it into the development environment, then use release management to deploy to test and production.
Example: a three-week schema change lives on a branch, merges into dev, then is promoted to test and finally to production.
W: Complementary tools: the docs state that branching and release management solve different problems and work together; branching isolates development, release management moves versions across environments.
X: A=Merge deploys to other environments: merging updates `main` in that environment; moving versions between environments is release management.
B=Release management for code repositories: the docs present it as managing versions of resources across environments, not a code-only feature.
C=Branching limited to datasets: the docs' own example branches a pipeline and an object type definition.
T: Branch to develop safely; use release management to move finished work across environments.

@ PLTR-AWARE D2 T2.1 applied comparison
S: A team on a cloud-hosted Foundry enrollment wants to connect to an S3 bucket that is reachable over the public Internet. Which kind of network egress policy fits this source?
A: An agent proxy policy, because connections from Foundry to a storage bucket pass through an agent in the customer's network
B: No egress policy, because buckets are reached over the cloud provider's backbone, where Foundry applies no firewall rules
C: A direct connection policy, because the bucket can be reached straight from the network that the Foundry instance runs in
D: A private link policy, because the docs require private links for cloud storage so that the traffic stays off the Internet
K: C
G: ## Egress policies describe the network path
Foundry blocks outbound traffic by default. A **network egress policy** allowlists a destination (domain, IP or CIDR, plus port) and the path used to reach it. A Foundry worker source needs a policy attached before it can connect.
## Picking the policy type
- **Direct connection policy**: for systems directly reachable from Foundry. On a cloud-hosted Foundry instance this means the public Internet; on a privately hosted Foundry, the network where Foundry is installed. The external system must accept inbound connections from Foundry.
- **Agent proxy policy**: for systems in a different network, typically on-premises, reached through a Data Connection agent.
- Other types (private link, bucket endpoint, secure tunnel) cover special network setups.
Example: the course's S3 exercise uses a direct-connection egress policy such as `bucket-name.s3.us-east-1.amazonaws.com` on port `443`. (If Foundry runs in AWS and the bucket is in the same region, the docs require extra bucket endpoint configuration.)
W: Direct connection policy: the bucket is reachable from Foundry's network, which for cloud-hosted Foundry is the public Internet; that is exactly the case the docs give for direct connection policies.
X: A=Agent proxy policy: agents are for systems hosted in a separate network such as on-premises; an Internet-reachable bucket does not need one.
B=No egress policy: Foundry worker sources need egress policies to route traffic; without one the connection is blocked.
D=Private link for cloud storage: private link policies exist for traffic over a configured private link, not as a requirement for cloud storage.
T: Reachable from Foundry's network (the Internet, for cloud-hosted Foundry) means a direct connection egress policy.
V: Data Connection, Control Panel
