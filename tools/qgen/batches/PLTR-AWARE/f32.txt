@ PLTR-AWARE D3 T3.3 applied comparison
S: A team has two candidate implementations for classifying maintenance requests: an AIP Logic function and a function written in Code Repositories. They want both judged on exactly the same test cases with results side by side. What does AIP Evals offer for this?
A: Converting the code-authored function into a Logic function first, because the targets of one suite must share the same tool and input signature
B: Two separate suites, each holding a copy of the test cases, because a suite is tied to one target function and runs it against its own cases
C: Adding the second implementation as an additional target function in the same suite, then choosing which targets to include when running it
D: Unit tests in Code Repositories for the code-authored function, because AIP Evals suites accept Logic functions as their targets and not code
K: C
G: ## Target functions
In AIP Evals the **target function** is the function under test. The documentation lists AIP Logic functions, AIP Chatbot functions and **code-authored functions** as possible targets.
## More than one target
A suite **can be configured to test multiple target functions**. The create-suite page describes adding target functions to run different published functions or Logic functions on the **same test cases**, which is useful for comparing performance across implementations. Each target can have its own input and output signature, and evaluators are configured per target. When running the suite, you choose which targets to include.
## Why this beats copied suites
One set of test cases means a fair comparison: any difference in results comes from the implementations, not from different inputs.
W: Additional target function: the create-suite page describes adding target functions to one suite to run different published or Logic functions on the same test cases, which is meant for comparing implementations; when running, you pick the targets to include.
X: A=Convert to Logic first: the docs list code-authored functions as targets, and each target in a suite can have its own input and output signature.
B=Two suites with copies: a suite is not tied to one target; copied cases drift apart and make the comparison less fair than one shared set.
D=Unit tests instead: code-authored functions from Code Repositories are explicitly supported evaluation suite targets.
T: To compare implementations fairly, add them as target functions in one AIP Evals suite and run them on the same test cases.

@ PLTR-AWARE D3 T3.3 applied troubleshooting
S: An evaluation suite for a function that labels reviews as positive or negative runs every test case and shows each output, but gives no pass or fail results and no overall score. Each test case already holds the expected label. What is missing?
A: An evaluator, such as an exact string match, that compares the function's output with the expected label and has an objective for passing
B: A second target function, because a suite computes pass and fail results by comparing the outputs of two target functions with each other
C: A higher model temperature, because a suite skips scoring for test cases whose output stays identical across repeated runs of the function
D: A larger number of test cases, because aggregate metrics are calculated once a suite holds more than one hundred test cases in total
K: A
G: ## Suites with and without evaluators
The documentation explains that a suite **without evaluators** is useful for running a function over many scenarios and **reviewing each output by hand**, but it gives no aggregated metrics. **Evaluators** measure results at scale by producing comparable indicators.
## What an evaluator does
An evaluator compares an actual output with an expected value and returns a metric:
- Boolean, such as **Exact string match** (`positive` equals `positive`),
- numeric, such as a Levenshtein distance or a ROUGE score.
## Pass and fail
For each metric you set an **objective**: which Boolean value passes, or whether higher or lower numbers are better, with an optional threshold. A test case passes when all its metrics meet their objectives.
## For this function
Map the function output to the actual value and the expected label column to the expected value of an Exact string match evaluator. The next run shows pass or fail per case and an overall picture.
W: Add an evaluator: without evaluators a suite just shows raw outputs for review by hand; an evaluator such as Exact string match with an objective produces pass/fail results and aggregate metrics.
X: B=Second target function: extra targets compare implementations, but a single target is scored perfectly well by an evaluator.
C=Higher temperature: scoring does not depend on outputs varying, and more randomness makes a classifier worse.
D=More than one hundred cases: the docs set no such minimum; the missing piece is how outputs are judged.
T: Test cases alone show outputs; add an evaluator with an objective to get pass/fail results and metrics.
V: AIP Evals

@ PLTR-AWARE D3 T3.3 applied troubleshooting
S: After a long planning conversation, a chatbot suddenly returns an error and asks the user to start a new session. Its Ontology context passes all 60 properties of each retrieved object. What best explains the error?
A: The model's daily token budget for the enrollment ran out, so the user's chatbot sessions have to be restarted on the following day
B: The context window was exceeded, because it holds the system prompt, the conversation history and the injected context such as retrieved objects
C: The chatbot's session expired after a fixed time limit, since AIP Chatbot Studio sessions end thirty minutes after they are opened
D: The user's access to the Ontology was revoked mid-session, which appears as a request to start a new session rather than as a permission error
K: B
G: ## The context window
The core concepts page defines the **context window** as the amount of text (in tokens) an LLM can process at one time. In AIP Chatbot Studio it includes:
- the system prompt (instructions, tool and variable descriptions),
- the **conversation history**,
- injected information: **retrieval context**, application state and tools.
**Exceeding the context window results in an error, prompting users to create a new session.**
## Why this conversation hit it
Every turn adds history, and every message brings retrieved objects. Printing all 60 properties per object multiplies the size quickly.
## Making room
Ontology context lets you choose which properties are printed and passed to the model. Keeping only the properties the task needs keeps each turn small, lowers cost and often improves focus.
W: Context window exceeded: the documentation names this exact error and says the window holds the system prompt, history and injected context, which here grows fast with 60 properties per object.
X: A=Daily enrollment budget: the documentation ties the request to start a new session to exceeding the context window, which a long conversation with 60 properties per object explains on its own.
C=Fixed session timeout: the docs tie the new-session prompt to exceeding the context window, not to a time limit.
D=Revoked access: losing access shows up as missing data or permission errors, not as a request to start a new session.
T: Long conversations plus large retrieved context can overflow the context window; trim properties and context before blaming anything else.
V: AIP Chatbot Studio
