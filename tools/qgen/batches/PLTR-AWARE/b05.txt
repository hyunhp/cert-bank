@ PLTR-AWARE D2 T2.2 applied comparison
S: A team needs nightly data from a vendor's REST API in a Foundry dataset. They created a REST API source in Data Connection, but cannot find a way to add a batch sync to it. What does the documentation recommend?
A: Move the source to an agent worker, because batch syncs from REST API sources are only offered when the connection runs on an agent
B: Add a webhook to an action behind a Workshop button, and have a user press it each night so the API response is saved as dataset rows
C: Import the source into a Python transforms repository and write an external transform that calls the API and writes the output dataset
D: Ask the vendor for a nightly CSV export instead, because Foundry can bring REST API data in only when it arrives as uploaded files
K: C
G: ## Two jobs for a REST API source
The REST API connector page describes the REST API source for interactive HTTP calls from Foundry applications, for example an action webhook behind a Workshop button. The same page states that this source type does not support syncs or exports by itself.
## Syncs from REST APIs go through code
For syncs and exports that call REST APIs, the docs point to external transforms: you import the Data Connection source into a Python transforms repository and write the logic that queries the API and writes a dataset.
- The source keeps the connection details, credentials and egress policy.
- The transform holds the request logic (which endpoints, pages, fields).
- Building the transform produces the dataset, and a schedule can run it every night.
Example: a carrier tracking API is imported as a source; a transform requests yesterday's shipments and writes them to a `carrier_events` dataset.
W: External transform in a Python repository: the docs name external transforms as the way to sync data from REST APIs, with the source imported into code.
X: A=Agent worker: no batch sync appears on an agent either; external transforms even require a Foundry worker, so this change moves in the wrong direction.
B=Webhook on a button: webhooks make interactive calls when an action runs; they are not a scheduled ingestion path and depend on someone pressing a button.
D=Vendor CSV export: Foundry can call REST APIs from code, so changing the vendor's delivery format is unnecessary.
T: A REST API source alone does not sync; bring REST data in with an external transform that imports the source into code.

Creating a source in Data Connection does not by itself make it available to repositories. The external transforms guide lists a separate prerequisite:
- In the source's connection settings, open the code import configuration and allow the source to be imported into code repositories.
- Then, in the repository, add the source from the external systems panel. The source page lists every repository that imports it.
## Why it is a separate switch
A source holds credentials and network access to an outside system. Making code import an explicit choice lets the source owner decide whether custom code may use that connection at all.
Example: the `Weather API` source exists and its egress policy is active, yet a repository search returns nothing until the owner allows code import.

C=TypeScript only: the external transforms guide is written for Python transforms repositories; they are the documented place to import sources.
D=Re-create the egress policy: source-based external transforms take the egress policy from the imported source; per-repository egress settings belong to the legacy approach.

The docs describe two generations of external transforms.
- **Legacy**: credentials, egress policies and exportable markings are specified in the repository and its code.
- **Source-based (preferred)**: a Data Connection source holds the connection details, credentials and secrets; repositories import the source and the job picks up its settings automatically.

- Rotate or update credentials without code changes.
- Share one connection configuration across several repositories.
- Simpler governance and lineage that shows the external connection.

G: ## Commit, checks and build in Code Repositories
The batch pipeline tutorial separates three steps:
- **Commit**: labels your set of changes and runs automatic checks on the code.
- **Build**: also commits, runs the checks, and starts building the output dataset, creating it or updating it from the code on your branch.
- **Preview**: runs the code on sampled inputs without committing or materializing a dataset.
So a passing check proves the code is valid, not that any data was computed.
## Builds compute datasets
The builds page defines a build as the mechanism that computes new versions of datasets. Running a build is a one-time computation; schedules keep data flowing afterwards.
Example: after the commit, the builder runs a build for the transform file; the `vendor_orders` dataset appears and the build helper shows the job as completed.
W: Commit runs checks, build writes data: only a build computes and writes the output dataset.
X: A=Checks need the dataset: checks validate code and run before any build, so a pass says nothing about where data was written.
C=Commits expire: commits stay in the branch history; nothing discards them after an hour.
D=Needs an app reference: datasets are produced by builds regardless of whether any application uses them.
T: Committing runs checks; only a build creates or updates the output dataset.

The Code Repositories tutorial recommends creating a personal branch instead of editing master, and keeping master protected. ## The documented flow
1. Create a branch and edit the code.

3. Open a pull request; reviewers see changed files, impact analysis and a pipeline review.

D=Build on master and revert: users see the bad data first; revert is for mistakes that slip through, not a test plan.

@ PLTR-AWARE D2 T2.2 applied troubleshooting
S: A new external transform calls a REST API that returns results in pages. Every build writes exactly 100 rows, while the API holds about 40,000 records. Each response contains a field with a token for the next page. What is the most likely fix?
A: Run the build with more memory, because the transform stops writing rows once its default memory limit is reached at about 100 records
B: Ask for a higher API rate limit, because the API returns only one page per day until the account is upgraded to a paid tier
C: Change the dataset to an incremental output, because a full rebuild keeps only the last page that the API returned during the run
D: Make the transform loop through the pages, requesting the next page with the token until a response comes back without a token
K: D
G: ## Paginated APIs
Many REST APIs return large result sets in pages. The REST API connector page describes a common pattern: the response contains a next-page token while more results exist, and your transform should keep requesting pages until no token is returned.
## Why the dataset stops at one page
An external transform does exactly what its code says. If the code makes one request, it writes one page, whatever the API holds. Data Connection does not page through results for you here, because the request logic lives in your transform.
Example: page 1 returns 100 records and a token; the loop requests page 2 with that token, and so on, until the 400th response has no token; the build writes all 40,000 rows.
Related: access tokens can expire during long runs, so long paging loops may need to request a new token partway through.
W: Loop until no next-page token: the documented pattern for paginated REST APIs in external transforms.
X: A=More memory: a memory limit would fail the job, not cut the output at a neat page size of 100 rows.
B=Rate limit tier: the response already offers a next-page token, which shows more data is available now.
C=Incremental output: the transform never requested the other pages, so changing how the output is written cannot add them.
T: In code-based REST ingestion, your transform must follow the API's pagination itself.

@ PLTR-AWARE D2 T2.3 applied tradeoff
S: A builder creates a `Sensor Reading` object type from a dataset and proposes the reading's timestamp as the primary key, since "two readings never happen at the same time". Which choice fits the documented guidance?
A: Keep the timestamp, because time-based types are the recommended primary key wherever events happen in a steady order over time
B: Use a deterministic String key built from the sensor id and reading number, since time-based primary keys are discouraged in the docs
C: Use the measured value as a Double primary key, because a numeric key gives faster filtering than any text key in applications
D: Use a Boolean valid flag as the primary key, because it is the smallest base type and keeps each object as light as possible
K: B
G: ## What a primary key must do
Every object type needs a primary key: a property whose value uniquely identifies each object. For a dataset-backed type, each row must have a different value. The create object type guide adds that keys should be deterministic, so the same row gets the same key on every build; otherwise edits are lost and links disappear.
## Which base types fit
The properties overview lists which base types may serve as primary key:
- `String`, `Integer`, `Short`: valid and commonly used.
- `Date`, `Timestamp`: discouraged, because of unexpected collisions when the storage format differs from the display format. The docs recommend `String` in most cases.
- `Boolean`: discouraged; it limits the type to two objects.
- `Float`, `Double`, `Decimal`: not valid as primary keys.
Example: `S-104_000873` combines the sensor id and the sensor's own reading counter, and is stable across rebuilds.
W: Deterministic String key: matches the docs' advice to avoid time-based keys and prefer String built from stable columns.
X: A=Keep the timestamp: the docs say the opposite; time types are discouraged as primary keys because of collisions.
C=Double primary key: float-like types are listed as not valid for primary keys at all.
D=Boolean key: a Boolean allows only two distinct values, so only two objects could exist.
T: Pick a unique, deterministic primary key, usually a String from stable source columns, not a time or float value.

@ PLTR-AWARE D2 T2.3 applied comparison
S: Each row of the `Shipment` dataset has a carrier code that matches the primary key of the `Carrier` object type. Each shipment has one carrier; a carrier has many shipments. How should the link type be defined?
A: As a join table dataset link, because every link type in the Ontology needs its own dataset that lists each pair of linked objects
B: As a foreign key link: the shipment's carrier code property refers to the carrier's primary key, giving a one-to-many relationship
C: As an object-backed link, because a third object type is required whenever one side of a relationship can have many linked objects
D: Without a link type, by copying every carrier property into the shipment dataset, so applications never need to traverse a link
K: B
G: ## How link types are stored
The create link type guide offers three ways to back a link type:
- **Foreign keys**: one-to-one or one-to-many. A property on one object type stores the primary key of the other, like a foreign key column in a relational database.
- **Join table dataset**: many-to-many. A dataset lists the pairs of primary keys.
- **Backing object type**: an intermediary object type carries the link plus extra metadata.
## Matching the shape of the data
Here the carrier code already sits on each shipment and each shipment has exactly one carrier. That is the textbook foreign key case: Foundry creates a link wherever a shipment's carrier code equals a carrier's primary key.
Example: shipment `SH-9921` has carrier code `DHL-NL`; the link joins it to the `Carrier` object with that primary key, and from the carrier you can traverse to all its shipments.
W: Foreign key, one-to-many: the shipment property that holds the carrier's primary key backs the link directly.
X: A=Join table for every link: join tables are for many-to-many relationships; foreign key links need no extra dataset.
C=Object-backed link: an intermediary object is for links that need their own properties, not for every one-to-many case.
D=Copy carrier properties: duplicates data and gives up navigation from a carrier to its shipments.
T: A property that holds another type's primary key backs a one-to-many link type by foreign key.

A foreign key can only hold one value per object, so it suits one-to-one and one-to-many relationships. A link type is bidirectional: it has two sides and can be traversed from either object type, so there is no need for a second "reverse" link type.
Example: the join table holds rows such as `T-042, CERT-HV` and `T-042, CERT-GAS`; an action that adds a certification creates a new link row.

C=Two link types: a single link type already supports traversal in both directions; the docs say not to define a separate reverse link type.
D=One-to-one: the docs state one-to-one cardinality is an indicator and is not enforced, and the real relationship is many-to-many anyway.
