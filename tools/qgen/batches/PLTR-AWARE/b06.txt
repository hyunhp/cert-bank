@ PLTR-AWARE D2 T2.4 applied troubleshooting
S: When dispatchers open the inbox, the details panel beside the shipment table already shows the first shipment, and some act on it believing they picked it. The builder wants the panel empty until a dispatcher clicks a row. What should change?
A: Turn off the table's active object auto-selection, so the active object variable starts empty and the panel fills only after a row is clicked
B: Enable multi-select on the table, because the details panel then waits until a dispatcher has ticked at least one row before it shows data
C: Sort the table so the oldest late shipment comes first, because the panel then shows the shipment that dispatchers would pick anyway
D: Turn on auto-refresh for the module, because every refresh clears the active object and leaves the details panel empty once again
K: A
G: ## The Object Table's active object
The Object Table has two output variables, and other widgets (such as an Object View in a details panel) read them:
- Active object: the currently active (highlighted) row, as an object set.
- Selected objects: the checked rows, only populated when multi-select is enabled.
By default the first row is automatically set as the active object when the table loads. A details panel bound to the active object therefore shows a shipment before anyone has chosen one. The table has a setting to disable active object auto-selection, which leaves the active object empty at load time.
## Example
The panel's Object View reads `Object table 1 Active object`. With auto-selection disabled it stays empty until a dispatcher clicks a shipment.
W: A=Disable auto-selection: the documented default fills the active object with the first row; turning it off leaves the panel empty until a real choice.
X: B=Multi-select: it adds the Selected objects output for checked rows; the active object is still set to the first row at load time.
C=Sort the table: the first row is still auto-selected, so dispatchers still see a shipment they did not choose; sorting only changes which one.
D=Auto-refresh: it reloads module data when watched objects change; it does not clear the active object or stop auto-selection.
T: An Object Table makes its first row the active object at load unless auto-selection is disabled.

@ PLTR-AWARE D2 T2.4 applied definition
S: A builder sketches a dispatch app and wants to name the four Workshop core concepts correctly in the design notes. Which pairing of concept and job is correct?
A: Widgets store data between user sessions, variables decide the screen arrangement, events hold filter values, and layouts run the writeback Actions
B: Widgets display content, variables carry data between widgets, events trigger behavior when users act, and layouts organize the header, pages and sections

G: ## Four building blocks of a module
- Widgets: display content and are the core building blocks of the interface (Object Table, Filter List, Button Group, Metric Card).
- Variables: configure how data moves through a module. A widget has input variables (the data it shows) and output variables (what it produces, such as the selected object or a filter).
- Events: trigger specific behavior when a user acts, for example open an overlay, switch page or set a variable value.
- Layouts: organize the interface into the header, pages, sections and overlays.
## Example
A Filter List writes an object set filter variable, the Object Table reads an object set filtered by it, a Button Group button fires an event that opens a drawer, and the page layout puts the filter on the left and the table on the right.
W: B=Display, carry data, trigger, organize: each job matches the Workshop core concepts pages for widgets, variables, events and layouts.
X: A=Storage, arrangement, filters, Actions: saving values across sessions is state saving, screen arrangement is the layout, filters live in variables, and Actions run from widgets such as buttons.
C=Object types, access, refresh, aggregation: object types are defined in the Ontology, access comes from roles on the module and data, and aggregations are a variable definition type.
D=Builds, columns, audit, permissions: Workshop does not build pipelines, variables are not dataset columns, and module permissions come from roles, not layouts.
T: Widgets show, variables carry data, events react to users, layouts arrange the screen.

@ PLTR-AWARE D2 T2.4 applied troubleshooting
S: A builder adds a Filter List beside an Object Table of shipments. Users pick a status in the filter, but the table keeps showing every shipment. Both widgets use the Shipment object type. What is the most likely gap?
A: The object type needs a new pipeline build after each filter choice before the table is able to show the filtered set of shipments
B: Filter List widgets only affect chart widgets, so the table has to be replaced with a chart before any user filter can take effect
C: The Filter List's filter output was never applied to the object set that backs the table, so the table still reads the unfiltered set
D: Filters only take effect once a user saves a state of the module, so the table changes after the user saves and reopens that state
K: C
G: ## How a filter reaches a table
A Filter List does not change other widgets by itself. Its output is an object set filter variable: a set of property and value pairs that captures what the user picked.
- The filter output must be applied to the object set variable that backs the table (in the getting-started tutorial, the table's object set is defined as a filter "using a variable" that points to the Filter List output).
- Once applied, every change in the Filter List flows through the variable and the table updates.
- Many filtering widgets work the same way: they output a filter variable that can be applied to object sets or reused in widget configurations.
## Example
`Shipments (filtered)` = Shipment objects filtered by `Filter list 1 Filter output`; the Object Table reads `Shipments (filtered)`.
W: C=Filter output not applied: without wiring the filter variable into the table's object set, the table has no reason to change.
X: A=Rebuild per filter: filtering an object set happens at query time in the app; no pipeline build is involved.
B=Charts only: the Filter List output can filter any object set variable, and the docs' own tutorial applies it to an Object Table.
D=Saved state needed: state saving lets users store and share a view; it is not required for a filter to take effect.
T: A Filter List outputs a filter variable; apply it to the table's object set or nothing changes.

- Input: an object set variable that determines which filter options are available.

C=Second table and copying: adds clutter and manual work while the filter input stays wired to its own output.
D=One object type per status: status is a property value; splitting the model breaks the shared Ontology to fix an app configuration mistake.

@ PLTR-AWARE D2 T2.4 applied definition
S: A builder exposes a Reassign Shipment Action on a button and asks whether they now have to design the input form (fields, validation, submit) as a separate set of widgets. What do the docs say?
A: Yes, every field must be built as Text Input and Date Input widgets, and a Function then copies their values into the Ontology on submit
B: Yes, the form has to be built in a separate forms tool, and Workshop can only link to it from a button that opens a new browser tab
C: No, Workshop writes the user's edits directly into the backing dataset, so no form or Action is involved when a dispatcher saves a change
D: No, a form is generated automatically from the Action definition, and the builder only sets defaults and visibility for its parameters
K: D
G: ## Actions bring their own form
The docs describe Actions as user-friendly, secure building blocks for writeback, defined once as action types and reused in many apps.
- A form is generated automatically from the Action definition, so the writeback and its user interface are not defined separately.
- In Workshop, a Button Group (or the Inline Action widget) exposes the Action. The builder sets parameter defaults from module variables and chooses whether each parameter is visible, hidden or disabled in the form.
- Validation comes from the action type's submission criteria, so the same rules apply in every app.
## Example
The Reassign Shipment action type has parameters Shipment, New Driver and Comment. The button prefills Shipment from the table's active object; the form shows New Driver and Comment for the dispatcher to fill in.
W: D=Generated form: the form follows the action type's parameters, and Workshop only configures defaults and visibility.
X: A=Input widgets plus a Function: input widgets exist for other needs, but rebuilding the form duplicates what the Action already provides and loses its validation.
B=Separate forms tool: Workshop shows the Action form inside the module; no other tool or tab is needed.
C=Direct dataset edits: Workshop writes back through Actions on objects, not by editing the dataset behind them.
T: Expose an Action on a button and Workshop shows its generated form; you configure defaults, not fields.

@ PLTR-AWARE D2 T2.4 applied troubleshooting
S: A dispatcher fills in a Reassign form, but the submit control stays unavailable and the form flags one issue on the new depot code they typed. Other dispatchers submit the same Action without trouble. What is happening?

An action type can carry submission criteria: conditions on parameters (such as a code matching a pattern) or on the user (a user or group). In the Workshop form:
- Each failing condition shows up as an issue in the form.
- Submission becomes available only when all parameters pass validation.
- After a successful submit, a confirmation toast appears and the object is updated.

B=Unpublished module changes: publishing affects which version users see, not whether a valid form can be submitted.
D=Stale object type: a delayed build may leave data old, but it does not flag an issue on a value the user just typed.
T: An issue flagged in an Action form means a submission criterion failed; fix the input, not the app.

@ PLTR-AWARE D2 T2.4 applied troubleshooting
S: Two dispatchers from different regions open the same module at the same moment and see different shipments in the same table. The builder suspects a bug in the filter setup. What is the more likely explanation?
A: Each browser keeps its own cached copy of the data, and the copies drift apart until both dispatchers clear the cache and reload the module
B: Row-level controls such as object security policies filter what each user may read, and Workshop widgets never show data a user cannot read
C: The module interface variables differ between the two links, and module interface variables always restrict data by the user's region
D: Auto-refresh is off for one of the users, so that user sees an older set of shipments until a scheduled pipeline build runs again
K: B
G: ## Read-time enforcement in Workshop
The Workshop permissions page says row and column access controls (restricted views, object security policies, property security policies) filter what a user can see in a module:
- Widgets can never display data the user is not authorized to read.
- The same module therefore shows different rows to users with different access.
- These controls apply at read time; they do not extend to widget exports, Action writes or downstream functions, so the docs pair them with markings when data must stay protected downstream.
## Example
A policy lets EMEA dispatchers read only EMEA shipments; one module serves every region without a filter per region.
W: B=Row-level controls at read time: different users seeing different rows in one module is the expected effect of object-level security.
X: A=Drifting browser caches: objects are read from the shared Ontology, so two users do not see different data because of cached copies.
C=Interface variables restrict data: module interface variables pass values into a module; they are not a security control.
D=Auto-refresh off: auto-refresh reloads when data changes; turning it off cannot remove rows that the other user can see.
T: Different users can see different rows in one module because Ontology security filters every widget at read time.

G: ## Derived properties in Workshop
