@ PLTR-AWARE D1 T1.1 applied tradeoff
S: An insurer receives about 200,000 warranty claims a week. It wants an LLM to suggest a category and a priority for every new claim, and adjusters work through the suggestions the next morning in a Workshop queue. Nobody needs a suggestion within seconds of a claim arriving. Which pattern fits the platform overview's guidance?
A: Call an AIP Logic function live each time an adjuster opens a claim, so that the model output is computed at the moment of viewing
B: Run an LLM transform in Pipeline Builder over the new claims and write its suggestions as proposals that adjusters accept or reject
C: Train a custom classification model on past claims before using any LLM, so that categories come from a model the insurer owns
D: Give an AI agent permission to edit the claim objects directly, so the suggestions apply at once without a queue or extra storage
K: B
G: ## Two ways to bring a model into a decision
The platform overview describes AI agents that, "in most patterns", **create proposals** rather than make changes directly. Proposals reach people in two ways:
- **Synchronously**: an AIP Logic function integrated into a Workshop app runs when the user needs it.
- **Asynchronously**: through Automate, or through the **Use LLM** node in Pipeline Builder.
## Why pipelines suit high volume
Pipeline Builder offers point-and-click LLM transforms (classification, sentiment, summarization, entity extraction, translation). The overview says this "sets the stage for automatically creating proposals in the Ontology for operators to review and approve, **without the lag of always running a live request to a model**".
## Human in the loop
The proposal pattern keeps people deciding and creates metadata (accepted, edited, rejected) that feeds later improvement.
## Example
Nightly: new claims -> Use LLM transform -> suggested category and priority -> proposals on `Claim` objects -> adjusters accept or correct them in the morning queue.
W: B=Pipeline LLM transform writing proposals: the claims are processed in bulk ahead of time, adjusters see ready suggestions with no waiting, and they still decide on each one.
X: A=Live AIP Logic on open: it works, but every opened claim waits for a model call, which the stem says nobody needs; the docs describe the pipeline route for this.
C=Custom model first: the docs present pipeline LLM transforms for classification directly; training a new model delays value and is not required.
D=Agent edits directly: it removes the human review the insurer wants; the docs describe agents proposing changes for operators to approve.
T: When suggestions are not needed instantly, generate them in bulk with an LLM transform in Pipeline Builder and surface them as proposals for people to review.
V: Pipeline Builder, AIP Logic, Workshop

@ PLTR-AWARE D1 T1.2 applied troubleshooting
S: The `Building` object type is saved in project A, which uses project-based Ontology permissions. A new analyst gets the Viewer role on project A and can now see the object type's schema and contact details, but no `Building` objects appear for her. The object type has no object or property security policy. What is the most likely reason?
A: She needs the Editor role on project A, because listing the instances of an object type counts as an editing permission in a project
B: She has no access to the backing datasource, which she also needs to see objects when no security policy grants that access instead
C: Objects become visible to a user only after she applies an action on one of them, which records her as a participant of that type
D: The object type must implement an interface first, because project-based permissions show objects only through interface searches
K: B
G: ## Project-based Ontology permissions
With project-based permissions, an object type is a resource saved in a project, like a dataset. Your role in that project decides what you can do with the **type**:
- Viewer: see the type's schema and contact information.
- Editor: edit the type's definition.
## Type versus instances
Seeing the actual objects is a separate question. The docs use a `Building` example: to view specific objects you need **Viewer on the object type** and **either access to the backing datasource or access granted through object and property security policies**, depending on how security is configured. With only viewing rights on the type, "you can only see information such as schema and contact information, not the actual data".
The docs also note that migrating to projects "does not change who has access to the backing datasource".
## In this case
No security policy is set, so object visibility comes from the backing datasource, which she cannot read.
W: B=No backing datasource access: Viewer on the type shows its schema; without a policy, seeing the objects also requires access to the data behind them.
X: A=Editor needed to list objects: Editor lets her change the type's definition; it does not grant access to the backing data.
C=Apply an action first: actions change objects she can already see; they are not a way to unlock visibility.
D=Interface required: interfaces describe shared shapes of object types and play no part in permission to see objects.
T: Viewer on an object type shows its definition; seeing its objects also needs backing datasource access or a security policy that grants it.
V: Ontology permissions, Projects

@ PLTR-AWARE D2 T2.2 applied troubleshooting
S: A Python external transform in Code Repositories calls a supplier's REST API and has no Foundry dataset inputs. A nightly schedule was set on its output dataset, and a manual build ran correctly once. Since then, every scheduled run shows as ignored and the data never changes. What fixes this?
A: Re-enter the credentials stored on the REST API source, because expired credentials make a schedule skip its build without any error
B: Enable force build on a schedule that holds only this dataset, because unchanged inputs and logic mean the dataset never looks stale
C: Add the transform's own output dataset as an input, so that every successful build marks the dataset as changed for the next nightly run
D: Move the API call into a batch sync on the REST API source, because schedules can only build datasets that Data Connection syncs produce
K: B
G: ## Staleness decides what a build does
The builds page says an output is **fresh** when its inputs and its logic have not changed since it was last built, and a fresh dataset "will not be recomputed in subsequent builds". The schedules page lists an **Ignored** run: the run was attempted but no build was created, which "likely indicates that everything is up-to-date".
## Datasets that never go stale
A transform that only calls an API has no inputs that change. The abort-transactions page names this case: datasets that fetch data from API calls "require force building because [they do] not become stale".
## Force build, kept narrow
A **force build** recomputes datasets regardless of staleness. The scheduling best practices discourage force builds on multi-dataset schedules for derived data, because they are costly; put datasets that must be force-built **in their own schedule**. That page ties force builds to Data Connection syncs, which never go stale; an external transform that only calls an API is in the same position, which is why the abort-transactions page lists it as a dataset that needs force building.
W: B=Force build on its own schedule: it makes the API transform run every night even though nothing upstream changed, without force-building other datasets.
X: A=Re-enter credentials: bad credentials make the build fail with an error; an ignored run means no build was even created.
C=Own output as input: a dataset cannot feed itself in a normal build, and it would not be the documented way to mark API data as needing a rebuild.
D=Batch sync on the REST source: REST API sources are read through external transforms, and schedules build any dataset, not just sync outputs.
T: Transforms that only call external APIs never look stale, so schedule them with force build in a schedule of their own.
V: Code Repositories, Schedules, External transforms

@ PLTR-AWARE D2 T2.2 advanced tradeoff
S: A force-built Python external transform pulls a partner's order feed every hour. Most hours the feed has nothing new, yet each run commits a new transaction, and large downstream datasets rebuild every hour. The team wants to keep hourly checks, make quiet hours cheap downstream, and keep real failures easy to spot in the build history. What should the transform do?
A: Raise an error whenever the feed is empty, so the job fails and the downstream datasets keep their current versions until the next hour
B: Write an empty table in quiet hours, so downstream datasets still receive a transaction but have no new rows to process when they build
C: Abort its transaction when the feed has nothing new, so the job ends as successful without a commit and downstream stays up to date
D: Change the schedule from hourly to weekly, so the downstream datasets rebuild less often, including in weeks when new orders do arrive
K: C
G: ## Why downstream rebuilds
As soon as an output dataset gets a new transaction, the datasets built from it count as out of date (stale) and rebuild on their next scheduled or manual build. A force-built API transform commits every run, so downstream follows every hour.
## Aborting a transaction
Python transforms can **abort the job's transaction** when the output would be unchanged. The docs describe it as:
- a way to "prevent the output datasets and downstream datasets from updating under certain conditions";
- "an alternative to failing the build", which "makes it easier to identify when something is actually failing";
- shown as **grayed-out, successful jobs** in the transaction history, so you can see at a glance whether a successful build committed anything.
The docs list API-fetching datasets that need force building among the typical cases, and note it saves compute on downstream updates.
W: C=Abort when nothing is new: the hourly check still runs, downstream does not go stale in quiet hours, and failures stay distinct from empty hours.
X: A=Fail on empty feed: downstream is spared, but the history fills with failures that are not real problems, which hides the real ones.
B=Write an empty table: it is still a new transaction, so downstream goes stale and rebuilds anyway.
D=Weekly schedule: it cuts cost by giving up the hourly checks the team wants and delays real orders by up to a week.
T: When an always-built transform has nothing new, abort its transaction so the job succeeds without a commit and downstream is left alone.
V: Python transforms, External transforms, Builds

S: Auditors want every `Ticket` closed through the "Close Ticket" action to record who closed it and when, in the `closed_by` and `closed_at` properties. Users must not be able to type or change either value in the action form. How should the builder map these two properties in the action's rules?
A: Map both properties to static values, so the rules hold one fixed value that the form cannot change when users submit the action
B: Map both properties to parameters with default values, so the form opens prefilled with the user's name and the current time
C: Map `closed_by` to Current User and `closed_at` to Current Time, contextual values that the platform fills in at execution

K: C
G: ## Where rule values come from
When an Ontology rule creates or modifies an object, each mapped property takes its value from one of these sources:
- **From parameter**: a form field the user fills in (it may have a default, but users can change it).
- **Object parameter property**: a property of an object passed in as a parameter.
- **Static value**: one fixed value that exists only in the rules.
- **Current User / Time**: string and timestamp properties can take the action's current user or the time at the start of execution.
## Why the contextual values fit audits
Like static values, Current User and Current Time "cannot be interacted with when submitting the action". Unlike a static value, they differ for every submission. The docs note the time is fixed when execution starts and can differ slightly from the commit timestamp in the action log.

W: C=Current User and Current Time: each submission records the real user and moment, and users cannot see or edit these values in the form.
X: A=Static values: they are fixed in the rules, so every ticket would record the same person and time.
B=Parameters with defaults: a default is only a starting value; users can still change the parameter before submitting.
D=Selected ticket's properties: they copy who created the ticket and when, not who closed it.
T: Use Current User and Current Time values in action rules to record who made a change and when, without letting users edit them.

The IDEs inherit Foundry security (restricting a dataset restricts it in the workspace too), Git branching, build scheduling and resource management. Data scientists can create model assets tracked in modeling objectives.
## Its documented limit
The docs say Code Workspaces **runs on a single node**, while other Foundry applications use Spark. For large-scale data transformations they recommend **Pipeline Builder or Code Repositories** instead; for data connections and streaming, Data Connection and Foundry Streaming.
## Meeting teams where they are
This is a positioning point for the course: the team keeps its familiar tool for analysis and models, and heavy production pipelines go to the tools built for scale.

G: ## Roles in a use case
Palantir's "next steps by user role" page names common roles: data engineer, application builder, analyst, data scientist, **platform administrator** and data governance. It adds that boundaries shift: on a small team one person may cover several roles.
## What the platform administrator does
Administrators "typically set up **authentication** to connect to an organization's identity provider, configure **application access**, then set up Data Connection to enable data to flow into the platform". Later they manage resource consumption, Developer Console support and monitoring.
## Who builds the rest
- **Data engineers** build and maintain pipelines (Pipeline Builder, Code Repositories, Data Lineage).
- **Application builders** create Workshop apps on the Ontology and capture decisions through action types.
## Scoping takeaway
List the administrator's setup work as early prerequisites so the builders are not blocked in week one.

X: A=Pipelines and app centrally: these are the data engineer's and application builder's work, not administrative setup.
C=Identity provider and pipelines: logins are admin setup, but pipelines are data engineering, even though both touch outside systems.
D=Application access and the app: access configuration is admin work, but building the Workshop app is the application builder's job.
T: Platform administrators set up authentication and application access first; data engineers and application builders build pipelines and apps.
