@ PLTR-AWARE D3 T3.1 applied use-case
S: A manufacturer shortlists four candidate first use cases for Foundry & AIP. Which one shows the strongest fit for an operational, Ontology-driven solution?
A: Producing the statutory year-end financial statements, which the ERP already generates correctly once a year from its own ledger with a fixed report format
B: Archiving scanned delivery notes for ten years to meet a retention rule, where nobody needs to search, analyze or act on the documents once they are stored
C: Reallocating scarce raw material across plants each day, using supplier, stock and order data from several systems and pushing the chosen plan back to them
D: Replacing the payroll engine that calculates employee salaries, because it is old and the HR team would like to retire the vendor contract next year
K: C
G: ## What makes a strong fit
Palantir's documentation describes the platform as built for **operational decision-making**: it models each decision as data, logic, action and security, and stresses that "closing the action loop" is what separates an operational system from an analytical one. The docs' own examples of use cases are alerts that must be investigated and resolved, inventory optimized across a network of facilities, and sales staff allocated across regions.
## Signals to look for when scoping
- A **recurring decision** that people make often, not a one-off report.
- **Several sources** that must be combined to see the situation (ERP, MES, WMS, CRM, streams).
- **Interdependent teams** whose choices affect each other.
- A **decision that must flow back** into the systems that run the process (writeback).
The course's "Scoping Use Cases" lesson teaches the same checklist as good fit versus poor fit; the signals above are taken from the docs so they hold without the course text.
W: Daily material reallocation: it is a frequent operational decision, needs data from several systems, affects several teams, and ends in actions written back to the systems of record, which is the exact pattern the docs describe.
X: A=Year-end statements: the ERP already does this well, it happens once a year and no decision is taken in the tool, so there is little operational value to add.
B=Document archive: pure storage with no analysis or action is a records-management need; nothing in it uses the Ontology's links, logic or actions.
D=Payroll replacement: replacing a transactional system of record is not what the platform positions itself for; it integrates with such systems rather than becoming one.
T: The best first use cases are frequent, multi-source operational decisions whose outcome is written back to the systems that run the business.

@ PLTR-AWARE D3 T3.1 applied tradeoff
S: After a successful demo, a finance director proposes switching off the company's ERP and running orders, invoices and the general ledger in Foundry instead. How should the team position Foundry & AIP in this landscape?
A: Agree, because the Ontology stores objects with full history, so it can take over as the transactional system of record once all ERP tables are migrated
B: Keep the ERP as the system of record, and use Foundry & AIP to integrate it with other sources and write decisions back to it through governed actions
C: Agree only for invoices and the ledger, because those are analytical data, and keep orders in the ERP since they need to be processed in real time
D: Keep the ERP for now but freeze all changes to it, so that every new process is built only in Foundry until the ERP can be retired completely
K: B
G: ## Integrate, not rip and replace
The documentation positions the platform next to existing enterprise systems. The platform overview says the Ontology "facilitates deep, two-way interoperability with existing enterprise systems". The "Why create an Ontology?" page shows operational sources such as **ERPs, MES and WMS** being synchronized into the Ontology, and decisions being **written back to every enterprise substrate**, including transactional systems.
## Example from the docs
In the fictional Onyx manufacturer scenario, a reallocation decision is pushed to a warehouse management system through an API, to three ERP systems through Ontology-driven connectors "which abide by the safeguards in each system", and to a planning system as a flat file. The ERPs stay where they are; the Ontology connects them and orchestrates the decision.
## Why it matters for scoping
A use case that starts with "replace the ERP" spends its time re-implementing accounting controls instead of improving a decision. Keeping the system of record and adding the decision layer on top is faster and lower risk.
W: Keep the ERP and integrate: the docs describe two-way interoperability, with the ERP synchronized into the Ontology and decisions written back through actions that respect the ERP's own safeguards.
X: A=Ontology as system of record: object history and edits exist, but the docs never position the Ontology as a replacement for an ERP's transactional ledger; it is the decision layer that connects such systems.
C=Split by data type: invoices and the ledger are core transactional records, not analytical copies, and the split still means rebuilding accounting controls the ERP already provides.
D=Freeze the ERP: blocking all change to a working system of record creates risk without benefit; the platform is designed to work with systems that keep evolving.
T: Foundry & AIP sit on top of and alongside systems of record such as ERPs, integrating them and writing decisions back rather than replacing them.

@ PLTR-AWARE D3 T3.1 applied use-case
S: A maintenance manager asks the team to "build a dashboard of all machine sensor readings". Before choosing data or tools, what does Palantir's guidance on delivering a use case suggest the team do first?
A: Ingest every sensor stream available so that the dashboard can show any reading the manager might ask for later, then trim the unused ones
B: Pick the application that will host the dashboard first, because the tool choice decides which data formats and sources can be used at all
C: Ask an AI agent to generate a draft dashboard from the sensor tables, then let the manager refine the request by reacting to the draft
D: Find out which decisions the dashboard should support, such as when to schedule repairs, and frame the project around that outcome
K: D
G: ## Outcome before method
The "Delivering a use case" page says that as you break down a project, "it is more important to think about the outcome rather than the method". Its example: instead of starting with "build a sales dashboard", understand which decisions it should enable, such as how to allocate time and resources across sales regions.
## How the framing helps
- An outcome (fewer unplanned breakdowns, repairs scheduled before failure) tells you which **data** you need: you work backwards from it.
- It tells you which **tools** fit each step; the docs say the right tool may change as the project matures.
- It makes the project easy to **decompose** into small, logical steps.
The docs add that this takes more work at the start, especially when building for someone else, but leads to a realistic goal.
W: Frame around the decision: the docs explicitly tell builders to understand which decisions and outcomes the requested dashboard should enable before choosing data or methods.
X: A=Ingest everything first: it reverses the docs' order. Without an outcome there is no way to tell which streams matter, and the privacy guidance asks to minimize unnecessary data.
B=Tool first: the docs map steps to tools only after the outcome and data are understood, and note the right tool can change as the project matures.
C=AI-generated draft: a quick draft may help later, but it still skips the question of which decision the dashboard serves, which is the step the guidance puts first.
T: Scope a use case by the decision and outcome it should improve, then work backwards to the data and tools.

@ PLTR-AWARE D3 T3.1 applied troubleshooting
S: An "AI transformation" initiative has run for nine months with volunteers who work on it when they have time. It has no end date and no named group of users, and nothing has reached production. Which reframing matches how Palantir defines a use case?
A: A time-bound effort by a dedicated team that supports one specific decision-making process for a defined set of users
B: An open-ended platform program that keeps adding data sources until every department can find something useful in it
C: A catalog of all business processes in the company, ranked by data quality, which is completed before any building begins
D: A proof of concept that shows each Foundry and AIP application once, so that business teams can choose which ones to adopt
K: A
G: ## The docs' definition
The "Delivering a use case" page defines it directly: "A use case is a time-bound effort by a dedicated team to support a specific decision-making process." Use cases are how new capabilities are delivered to a set of users.
## What each part protects against
- **Time-bound**: a deadline forces a first version to reach users instead of drifting.
- **Dedicated team**: people whose job it is, not spare-time volunteers.
- **Specific decision-making process**: a narrow target, such as resolving alerts or allocating inventory, gives the work a clear finish line and a way to measure success.
- **A set of users**: someone who will actually use the result.
The initiative in the stem misses all four, which is why it produces activity without outcomes.
W: Time-bound, dedicated, specific decision: this is the docs' own definition of a use case, and each element addresses one of the gaps in the stalled initiative.
X: B=Open-ended program: adding sources without a target decision is the drift the initiative already suffers from; the docs tie a use case to a specific process.
C=Catalog first: a company-wide catalog delays any user value for months and is not a precondition in the docs; they start from one decision and work backwards to its data.
D=Showcase every application: a tour of tools has no decision or users behind it, so it cannot show operational value or reach production.
T: A Palantir use case is time-bound, staffed by a dedicated team and aimed at one specific decision-making process for real users.

@ PLTR-AWARE D3 T3.1 applied tradeoff
S: A retailer wants Foundry & AIP to improve store replenishment across 900 stores, 40,000 products and five source systems. The sponsor wants visible value within weeks. Which first scope fits that goal best?
A: All stores and products at once but read-only, so that every store manager sees the same replenishment view from day one and decisions come later
B: All stores and products, but only the data integration layer, so that the full Ontology is complete before any user-facing application is designed
C: One region's stores and one fast-moving category, covering the real reorder decision end to end with the planners who make it
D: A company-wide AI agent that answers any replenishment question, so that planners can discover by themselves which decisions they need help with
K: C
G: ## Start small, but end to end
Starting with a narrow, valuable slice is a central message of the course's scoping lesson (course framing). The docs support it from two directions:
- A use case targets **a specific decision-making process** and is **time-bound**, so it must deliver within a short window.
- The guidance tells builders to identify an outcome and **break the project into small, logical steps**.
## Thin slice versus broad layer
A thin slice covers the whole loop for a few users: data from the needed sources, logic, an application and an action that records the decision. It proves value and exposes real problems early. A broad layer (all data, or read-only views for everyone) touches every store but changes no decision, so it shows little value and hides integration issues until late.
## Growing from the slice
Because objects such as `Store` and `Product` live in the shared Ontology, the next region or category reuses them instead of starting again.
W: One region and category, end to end: it is small enough to ship in weeks, still covers the real decision with its actual users, and the objects it creates can be reused when the scope widens.
X: A=Everything, read-only: broad visibility without actions does not close the decision loop, so it shows little operational value and postpones the hard part.
B=Data layer first: completing the whole Ontology before any application delays user value by months; the docs work backwards from one outcome instead.
D=General agent: an agent with no defined decision has no outcome to measure and no clear actions to take; it skips the scoping step rather than doing it.
T: A good first scope is a narrow slice that covers one real decision end to end for a small set of users, then grows by reusing the same Ontology.

@ PLTR-AWARE D3 T3.1 applied use-case
S: A logistics team launches a tool to help dispatchers reassign delayed shipments. The sponsor asks how success should be measured after three months. Which measure fits an outcome-oriented use case best?
A: The number of datasets and object types created for the tool, since a larger Ontology shows that more of the business has been modelled
B: The number of weekly logins to the application, since frequent use proves that dispatchers find the new tool valuable in their daily work
C: The number of pipeline builds that succeeded each night, since reliable data refreshes show that the platform is healthy and trusted
D: The change in on-time delivery for reassigned shipments compared with a baseline, since that is the result the decision is meant to improve
K: D
G: ## Measure the outcome, not the activity
The "Delivering a use case" guidance asks teams to frame work around an **outcome** rather than a method. The natural success measure is therefore the business result the decision is supposed to change. Measuring outcomes is also a theme of the course's scoping lesson (course framing).
## Outputs versus outcomes
- **Outputs** (datasets, objects, builds, logins) show that work was done or that the tool is used.
- **Outcomes** (on-time delivery, stockouts avoided, hours to resolve an alert) show that decisions got better.
Healthy outputs are necessary but not sufficient: a tool can be used every day and still not improve the result.
## Baseline
Record the measure before the launch. Because actions capture each decision in the Ontology, the team can later pair decisions with what happened, which the docs describe as the basis for feedback loops.
W: Outcome versus baseline: it measures whether the reassignment decisions actually improved delivery, which is the outcome the use case was scoped around.
X: A=Ontology size: the number of objects is an output of building work; a bigger model says nothing about whether any decision improved.
B=Logins: usage is a useful health signal, but people can log in daily while delivery performance stays flat, so it does not show the outcome.
C=Build success: reliable pipelines are a precondition for trust, not evidence that dispatchers make better decisions.
T: Judge a use case by the change in the business outcome its decision targets, measured against a baseline, not by platform activity.

@ PLTR-AWARE D3 T3.1 applied troubleshooting
S: A procurement app shows supplier risk scores, but buyers decide on alternative suppliers by email and update the ERP by hand. After six months the team cannot show whether the scores led to better choices. What is the most likely gap?
A: The risk scores are refreshed only daily, so buyers do not trust them, and a streaming pipeline is needed before any value can be measured
B: The decisions are made outside the platform, so nothing links each choice to the score that prompted it or to what happened afterwards
C: The risk model is too simple, so a larger machine learning model must be trained before the effect of the scores becomes visible in the data
D: The app has too few users, so the team must roll it out to every buyer in the company before a measurable difference can appear at all
K: B
G: ## The decision loop
The documentation describes the platform as built to create data-driven loops: "use data to make a decision, capture the decision that was made, and then use data to assess the decision's impact over time." The platform overview adds that capturing decision outcomes in the Ontology "allows users to pair a particular decision with observations of the results in future data".
## What breaks the loop here
The buyers see the score in the app but act elsewhere: email and manual ERP entry. So:
- no record ties a supplier switch to the score shown at that moment;
- the ERP change cannot be matched to the analysis that led to it;
- outcomes (late deliveries, quality issues) cannot be compared between followed and ignored recommendations.
## The fix
Add an action in the app that records the choice and writes it back to the ERP. The decision becomes data, with its context, and the impact can be measured.
W: Decisions not captured: the docs make capturing the decision the step that lets teams assess impact, and here it happens in email and by hand, outside the loop.
X: A=Refresh speed: fresher data might help adoption, but even real-time scores cannot be evaluated if the choices made on them are never recorded.
C=Bigger model: model quality is not the problem shown; with no record of decisions, a better model's effect would be just as invisible.
D=More users: rolling out further multiplies untracked decisions; without capture there is still nothing to measure.
T: To measure value, capture decisions where they are made, through actions, so each one can be paired with its outcome.

@ PLTR-AWARE D3 T3.1 applied tradeoff
S: A bank keeps its curated customer tables in Snowflake, governed by a central data team. A new Foundry use case needs those tables, and the data team objects to maintaining a second full copy. Which approach fits Palantir's architecture?
A: Copy the tables into Foundry datasets every night anyway, since Ontology objects can only be backed by data that is physically stored inside Foundry
B: Ask the data team to move the tables out of Snowflake into Foundry for good, so that one platform holds the governed copy for every consumer
C: Register the Snowflake tables as virtual tables in Foundry, so the use case reads them in place under Foundry's permissions without a stored copy
D: Export Foundry's Ontology to Snowflake instead and build the use case there, so that the data team's existing warehouse stays the only platform
K: C
G: ## Virtual tables
Foundry's docs describe **virtual tables** as pointers to tables in supported data platforms, queried "without first storing the data in a Foundry dataset". Snowflake, BigQuery and Databricks are listed as generally available sources. Virtual tables are governed by Foundry's security and permissions model and can be combined with Foundry datasets, "where data need not be consolidated in one place".
## Positioning
The Architecture Center's Multimodal Data Plane page says Palantir supports mixed architectures, with Palantir as "one participant in a wider, more heterogeneous enterprise architecture", and that using data in the Ontology "never requires data to be duplicated". The interoperability page names virtual tables as the way to use assets in Databricks, Snowflake or BigQuery "without needless data duplication".
## Scoping takeaway
An existing warehouse is an asset to plug into, not an obstacle. The use case can start sooner and the data team keeps ownership.
W: Virtual tables: the docs present them as the way to use Snowflake tables in place, governed by Foundry permissions, without keeping a duplicate copy.
X: A=Nightly copy: the docs state the opposite; data can stay in the external platform and still feed workflows, so physical storage in Foundry is not required.
B=Move everything: migrating the warehouse is a large change the use case does not need, and it overrides the data team's ownership for no gain.
D=Build in Snowflake: there is no export of the Ontology's actions and applications to a warehouse; that would drop the operational layer the use case needs.
T: When the data already lives in a supported warehouse or lakehouse, use virtual tables to work with it in place rather than duplicating it.

@ PLTR-AWARE D3 T3.1 applied use-case
S: An insurer's analytics team works in its company data lake. A new Foundry use case produces cleaned claims data and fraud-model scores that the analytics team also wants to use in their own tools. How does this fit Palantir's positioning?
A: Use Data Connection exports to sync the cleaned data and model results to the data lake on a schedule, applying the needed access restrictions
B: Ask the analytics team to stop using the data lake and move to Foundry, since cleaned data can only be read inside the platform it was built in
C: Send the analytics team a weekly spreadsheet extract by email, since Foundry has no supported way to write data to other storage systems
D: Rebuild the cleaning logic separately in the data lake, so each platform keeps its own pipeline and neither depends on the other

Data Connection supports **exports** from Foundry to external systems. The docs list typical purposes:
- data cleaned and transformed in Foundry pipelines synced to systems such as data warehouses or data lakes;
- inference results of machine learning models exported to operationalize ML projects across the organization;
- operational data captured from users in the Ontology written to other systems for analysis.
Exports can be file, table or streaming, depending on the destination.

The docs remind builders that an export creates another place where data is held: confirm the purpose, minimize the fields and apply access restrictions before configuring it.
## Positioning
Foundry does not have to be the only consumer of what it produces. It can feed the wider data platform, which is part of the "open" architecture described in the Architecture Center.
W: Data Connection exports: the docs name exactly this pattern, cleaned data and model results synced to a warehouse or data lake, with access restrictions applied.
X: B=Move to Foundry: the docs describe open formats and exports precisely so other platforms can use Foundry's results; forcing a move is unnecessary.
C=Emailed spreadsheets: Foundry does support writing to external systems, and emailed extracts lose governance, lineage and scheduling.
D=Duplicate the logic: two independent pipelines drift apart and double maintenance, while an export reuses the single governed result.
T: Foundry can feed existing warehouses and data lakes through Data Connection exports, so its results serve the wider enterprise data platform.

@ PLTR-AWARE D3 T3.1 applied use-case
S: Account managers work in the company's CRM all day. A new Foundry app recommends which at-risk accounts to contact, and leaders want each accepted recommendation to appear as a task in the CRM right away. Which approach fits?
A: Ask account managers to copy accepted recommendations into the CRM by hand, since Foundry is designed only to read from operational systems
B: Configure an action that calls the CRM through a webhook when a manager accepts, so the decision is written back to the system they use
C: Replace the CRM with a Workshop application, so that account managers do all of their account work in Foundry and the CRM can be retired
D: Export the full accounts dataset to the CRM once a month, so that the CRM receives every recommendation together with the other changes
K: B
G: ## Writing back to operational systems
The action types docs describe **webhooks** as a Data Connection concept for sending a request to an external system, "such as Salesforce, SAP, or any configured HTTP server, typically to modify data in that external system". Configured in an action, a webhook sends data when a user applies the action, which "enables workflows in Foundry to connect directly with source systems and write back data and decisions into those systems".
## Two webhook modes (concept level)
- **Writeback**: runs before the Ontology changes; if it fails, nothing changes in Foundry and the user sees the error.
- **Side effect**: runs after; suited to best-effort notifications or several systems.
## Scoping takeaway
Meet users where they work. The CRM stays the system of record for tasks, and the Foundry decision reaches it as part of the action.
W: Action with a webhook: the docs describe webhooks in actions as the way to write decisions back to systems such as CRMs at the moment users act.
X: A=Manual copying: Foundry does write back to source systems; manual re-entry loses the link between decision and record and invites errors.
C=Replace the CRM: the platform positions itself alongside systems of record, and replacing a working CRM is far outside the scope of this use case.
D=Monthly export: a monthly batch misses the requirement that tasks appear right away, and pushing the full dataset is not how single decisions should flow.
T: Decisions made in Foundry reach CRMs and ERPs through actions with webhooks, so existing systems of record stay current.

@ PLTR-AWARE D3 T3.1 applied troubleshooting
S: Scoping a staff-scheduling use case, a team plans to sync the whole HR system, including health records and disciplinary notes, "in case they are useful later". What does Palantir's guidance on delivering a use case suggest?

W: Purpose first, minimal data: the docs tell teams to define purpose and stakeholders before selecting data so the use case avoids unnecessary data and sets appropriate access.

A: Start with a scheduled code pipeline and a custom application, since prototypes built in point-and-click tools cannot later be turned into production work
