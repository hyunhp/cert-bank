@ PLTR-AWARE D1 T1.1 advanced tradeoff
S: A retailer's pricing planners decide weekly markdowns in spreadsheets that they email to stores. Leadership wants to learn later which markdowns actually worked, so every decision must stay tied to the product and stock data the planner saw. Planners also refuse to learn a coding tool. Which approach BEST closes the decision loop the platform is built around?
A: Planners submit a markdown action in a Workshop app, and an action log object links each decision to the edited products
B: Planners keep their spreadsheets, and a nightly file sync loads each emailed workbook into a dataset that analysts later join to sales
C: Analysts build a Quiver dashboard of weekly sales by product so that planners can review the effect of last week's markdowns visually
D: Planners record each markdown in a Code Repositories transform that writes the decision and its inputs into a dedicated output dataset
K: A
G: ## The data-driven loop
Palantir's "Delivering a use case" page describes the loop the platform is built for: **use data to make a decision, capture the decision that was made, and then use data to assess the decision's impact over time**. The course calls systems built this way *decision-centric*; that is course vocabulary, but the loop itself is in the docs.
## Capturing a decision as data
- An **action type** is the governed way to change the Ontology. When a planner submits it from a **Workshop** app, the change is applied with the planner's identity and parameters.
- The **action log** turns every successful submission into an object of an action-log object type, automatically linked to every object the action edited. The docs say it answers "What decision was made, by whom, when, and in what context?"
## Example
A planner marks down 40 winter jackets. One action-log object is created, linked to those 40 products, so an analyst can later compare sell-through for products that received the decision with those that did not.
W: Workshop action plus action log: the decision is made inside a no-code app and stored as linked Ontology data, which is exactly the capture step of the loop.
X: B=Nightly sync of emailed workbooks: it copies the files but loses who decided, when and from which data, so the decision is not tied to what the planner saw.
C=Quiver sales dashboard: it shows outcomes but never captures the decision itself, so it covers only the assessment half of the loop.
D=Code Repositories transform per decision: it breaks the no-code constraint and turns each business decision into a code change.
T: Capture decisions through action types (with an action log) in an app, so later analysis can link outcomes to the exact decision and context.
V: Action types, Action log, Workshop

@ PLTR-AWARE D1 T1.1 advanced comparison
S: A manufacturer's data flows one way: ERP to warehouse to BI dashboards, after which planners phone suppliers and retype changes into the ERP. The new design must let an AI model propose purchase-order changes that planners approve in the same system, and an approved change must reach the ERP. Which design matches the decision-centric architecture the platform describes?
A: Export curated Foundry datasets to the warehouse every night so that the existing BI dashboards also show the AI model's proposals
B: Model purchase orders as Ontology objects, approve proposals through an action type, and send each approval to the ERP by webhook
C: Build Contour analyses on the synced ERP tables where planners filter the AI proposals and then copy the approved values into the ERP
D: Let an AIP Logic function write its proposals into a new dataset that planners download as a file and upload to the ERP each morning
K: B
G: ## From linear chains to decision-centric systems
The Aware course contrasts *linear* systems (data flows one way into reports, and people act elsewhere) with *decision-centric* systems; this is course framing. The docs express the same idea in the Architecture Center: the Ontology integrates an enterprise's **data, logic, action and security** into one representation that both humans and AI agents can use, with objects as "nouns" and actions as "verbs".
## The pieces in this scenario
- **Data**: purchase orders as Ontology objects synced from the ERP.
- **Logic**: an AI model or AIP Logic function that proposes changes.
- **Action**: an action type a planner submits to approve a proposal.
- **Writeback**: a Data Connection **webhook** configured in the action sends the approved change to the external system, for example SAP.
## Why the last step matters
Without writeback the decision stays in Foundry and someone retypes it, which is the linear pattern the company wants to leave.
W: Ontology, action type and webhook: proposal, human approval and ERP update all happen in one governed loop.
X: A=Nightly export to the warehouse: data still flows one way into reports, and nobody approves or writes anything back.
C=Contour analyses on ERP tables: Contour is for analysis; planners still copy decisions into the ERP by hand.
D=Logic output dataset downloaded as a file: the approval and ERP update stay manual file handling outside the platform.
T: A decision-centric design keeps proposal, human approval and writeback to the source system inside one Ontology loop of data, logic and actions.
V: Ontology, Action types, Data Connection webhooks

@ PLTR-AWARE D1 T1.2 advanced tradeoff
S: A company already has a "Reassign Technician" action type with submission criteria, used by dispatchers in Workshop. It now adds an AI chatbot that should reassign technicians too. An engineer proposes letting the chatbot update the backing dataset directly because it is faster to build. The security lead requires identical validation and an audit trail for humans and AI. Which choice BEST meets both requirements?
A: Give the chatbot an Action tool that uses the existing Reassign Technician action type, so the same submission criteria and logging apply
B: Grant the chatbot's project Editor on the technician dataset and repeat the submission criteria as rules inside the chatbot's instructions
C: Let the chatbot write proposals to a separate dataset that a scheduled Pipeline Builder job merges into the technician dataset every night
D: Give the chatbot an Object query tool on technicians, and ask dispatchers to retype its suggested reassignments into a Notepad document
K: A
G: ## One kinetic model for humans and AI
The Ontology's **action types** are the governed way to change objects. Their **submission criteria** decide who may apply them with which parameters, and they can generate action-log objects. The Architecture Center stresses that the same Ontology primitives are used by humans and AI agents, so guardrails apply equally.
## Chatbot tools
AIP Chatbot Studio offers an **Action** tool that gives a chatbot the ability to execute an Ontology edit through an action type, configured to run automatically or after the user confirms. An **Object query** tool only reads objects.
## Why not a shortcut
Writing to the backing dataset bypasses submission criteria and the action history. Rules written into a prompt are suggestions to the model, not enforced checks.
W: Action tool on the existing action type: the chatbot goes through the exact same validation and logging path as dispatchers, which satisfies both constraints.
X: B=Editor on the dataset plus prompt rules: prompt text is not an enforced validation, and dataset writes skip the action history.
C=Separate dataset merged nightly: the merge bypasses submission criteria and delays the change by up to a day.
D=Object query tool plus retyping: it reads safely but leaves the reassignment as manual retyping, so the AI never acts and nothing is logged.
T: Let AI act through the same action types humans use, so validation and audit are shared instead of rebuilt.
V: Action types, AIP Chatbot Studio

@ PLTR-AWARE D1 T1.2 advanced use-case
S: A plant models `Machine` objects. Every machine reports temperature every second, but only some machines also report flow rate. The plant has about 400 machines. The data team wants temperature available on every machine without adding properties full of nulls, and wants per-sensor metadata such as units kept in one place. Which time series setup does the documentation recommend?
A: A separate `Temperature Reading` object type with one object per second, linked to its machine through a one-to-many link type
B: Time series properties for both temperature and flow rate on `Machine`, leaving flow rate empty for machines without the sensor
C: A time series property for temperature on `Machine`, plus a linked sensor object type carrying flow rate where it exists
D: Two new object types, `Pump Machine` and `Plain Machine`, each with its own time series properties copied from the original `Machine` type
K: C
G: ## Two ways to store time series in the Ontology
The time series overview describes two setups:
- **Time series property (TSP) on the object type**: the most common option, used when **all** objects of the type have that series.
- **Sensor object type** linked to the root object type: each sensor object holds one series. It is recommended when only some objects have a series, and it keeps metadata such as **units or interpolation** for each sensor in one place.
## The docs' own example
Temperature exists for all machines, so it goes on `Machine` as a TSP. Flow rate exists only for some, so it belongs on a sensor object type, which "will help prevent numerous null entries" in the backing dataset.
## Why not one object per reading
A reading every second would create enormous numbers of objects; time series syncs index the values instead.
W: TSP plus sensor object type: temperature is universal, flow rate is partial, and sensor objects carry their own metadata, exactly as the overview recommends.
X: A=One object per reading: it floods the Ontology with billions of objects instead of using a time series property backed by a time series sync.
B=Both as TSPs on Machine: flow rate would be null for many machines, which the docs advise avoiding with a sensor object type.
D=Two copied object types: duplicating the type splits apps and analysis; the docs suggest one generic type with sensors instead.
T: Put a series on the object type when every object has it, and on a linked sensor object type when only some objects do.
V: Time series, Ontology

@ PLTR-AWARE D1 T1.2 advanced use-case
S: A hospital's `Patient` object type feeds a Workshop app, an AI chatbot and an OSDK portal. Nurses must see only patients on their own ward, and the diagnosis property must be visible to physicians alone. The architect wants one object type for all three consumers rather than copies that drift apart over time. Which control fits the Ontology BEST?
A: A restricted view on the patient dataset that filters rows by ward, used as the single backing datasource for the `Patient` object type
B: A separate `Patient` object type per ward, each backed by its own filtered dataset, with the diagnosis column removed for nurse groups
C: A PII marking on the entire patient dataset, granted only to physicians, so that nurses cannot open any patient record at all
D: An object security policy filtering patients by ward, plus a property security policy that limits the diagnosis property to physicians
K: D
G: ## Row, column and cell security in the Ontology
Object and property security policies are configured on the **object type**, independently of the backing datasource:
- an **object security policy** gives row-level security, for example matching a user's ward to the patient's ward;
- a **property security policy** guards selected properties and gives column-level security;
- together they give cell-level security.
## Restricted views
A restricted view filters **rows** of a dataset with a granular policy. It has no column-level policies, and Palantir's docs recommend object security policies over restricted views for most Ontology use cases.
## One model, many consumers
Because the policies sit on the object type, Workshop, chatbots and OSDK apps all read through the same rules. Users only ever see objects and property values they are authorized for.
W: Object plus property security policy: ward filtering is row-level and diagnosis hiding is column-level, on one shared object type.
X: A=Restricted view by ward: it handles the rows but cannot hide one column, so nurses would still see diagnoses.
B=One object type per ward: it multiplies object types and apps, which breaks the one-model requirement.
C=Marking on the whole dataset: markings are all-or-nothing per resource, so nurses would lose every patient record instead of only the diagnosis.
T: For row and column rules on one shared object type, combine an object security policy with a property security policy.
V: Object security policies, Property security policies, Restricted views

@ PLTR-AWARE D1 T1.3 advanced tradeoff
S: For three months, an AIP Logic function has proposed a category for each incoming invoice, and clerks approved or corrected every proposal in Workshop. Review data shows that utility invoices are accepted 99% of the time, while freight invoices are accepted only 70%. Leadership wants to cut clerk effort without raising the error cost. What is the BEST next step in progressive automation?
A: Apply every proposal automatically for both invoice types, and let the clerks spot-check a random sample of invoices once each month
B: Replace the Logic function with a larger model for both invoice types first, and keep full human review until freight reaches 99%
C: Automate the utility invoices with an Automate action effect, and keep human review in the Workshop app for freight invoices
D: Stop the AI proposals for freight invoices entirely, and send utility invoices to an external robotic process tool for faster entry
K: C
G: ## Progressive automation
The Aware course uses the term *progressive automation*: start with AI that proposes and humans who review, then hand over the parts where evidence shows the AI is reliable. The term is course framing; the building blocks are in the docs:
- **AIP Logic** produces the proposal.
- An **action type** applies an approved change, from **Workshop** for people or from **Automate** for automations.
- **AIP Evals** and review history give the evidence.
## Using the evidence
A 99% acceptance rate on one category is strong evidence for that category only. Freight at 70% still needs a person, so the safe step is to split by category, not to change everything at once.
## Example
An automation with an object set condition on new utility invoices runs an action effect that applies the proposed category, while freight invoices keep landing in the clerks' review queue.
W: Automate utilities, keep review for freight: effort drops where accuracy is proven, and the error-prone category keeps human review.
X: A=Automate everything with monthly spot checks: freight at 70% would apply many wrong categories before a sample caught them.
B=Larger model first: the guidance favors acting on evidence over reaching for a bigger model, and it delays any saving on utilities.
D=Drop freight AI and use an external tool: it throws away useful proposals and moves utilities outside the governed action path.
T: Progressive automation hands over only the slices where review evidence shows the AI is reliable, and keeps people on the rest.
V: AIP Logic, Automate, Workshop

Which tool fits BEST?
A: A Quiver dashboard per production line, with time series charts and filters that readers can adjust for each month themselves

Notepad is an **object-aware collaborative rich-text editor**. Its documented features include:

The docs say Notepad is less suited to dashboards, because it has no dynamic filtering; they point to Quiver dashboards (object or time series data), Contour dashboards (tabular data) or Workshop for that.

W: Notepad template: it embeds charts and objects from other tools, generates a report per line from a template and freezes it, without code.

@ PLTR-AWARE D1 T1.4 advanced use-case
S: An insurer's claims analysts often download sets of customer financial objects from Object Explorer and Workshop as files. Compliance now requires that each analyst state why they need the data before every such download, and that reviewers can read these reasons later. Analysts who have a valid reason must keep their current access. Around 200 analysts are affected. Which governance capability fits BEST?
A: A marking on the financial dataset that is granted only to analysts who have finished compliance training in the current year
B: An action log on every action type that edits customer objects, so reviewers can see who changed which financial records and when
C: Checkpoints configured on the sensitive interactions, prompting for a justification that is recorded for later review by administrators
D: A Sensitive Data Scanner schedule across the claims datasets, so that any newly found financial fields get flagged automatically for review
K: C
G: ## Purpose justification
**Checkpoints** is a data governance tool for **purpose justification and accountable records**. A checkpoint interrupts a potentially sensitive interaction with a prompt asking the user to justify it. The justification becomes a checkpoint record with context such as the timestamp, available to administrators in the Checkpoints application; users can review their own records too. Checkpoints is integrated into more than 60 platform interactions; each checkpoint type names one interaction, for example **Object set export** (downloading an object or object set from Object Explorer or Workshop), Object Explorer search or Submit action. Merely viewing an object is not in the list, so the governed moment is the export.
## Related but different controls
- **Markings** decide whether someone may access data at all; they never ask why.
- The **action log** records successful action submissions (decisions that edit objects), not reads.
- **Sensitive Data Scanner** finds sensitive patterns in datasets and can take automated actions; it does not involve the user's reason.
## Example
Before exporting a set of customer accounts, the analyst types "Claim C-2231 income verification"; compliance later reviews the checkpoint record, which also lists the objects involved.
W: Checkpoints: an Object set export checkpoint asks for a reason at each download and stores it for review, while people with a valid reason keep their access.
X: A=Training-based marking: it controls who can access, but never records why a specific download happened.
B=Action log: it captures edits made through actions, not the reason for downloading data.
D=Sensitive Data Scanner: it discovers sensitive fields in datasets, which does not capture an analyst's purpose.
T: When the reason for accessing sensitive data must be captured, use Checkpoints; markings and scanners answer different questions.
V: Checkpoints, Markings, Sensitive Data Scanner

@ PLTR-AWARE D1 T1.4 advanced troubleshooting
S: A proposal merges a branch that changes a Pipeline Builder pipeline and the object type it feeds. Two reviewers approved the pipeline, but a third reviewer rejected the object type change because of a property name. The team lead asks why the pipeline cannot merge on its own today. The deadline matters, but the changes must ship together. What explains the block and the fastest correct way forward?
A: Pipeline changes always wait for ontology changes, so the team should remove the object type from the branch and merge the pipeline alone
B: Proposals merge only once a day, so the team should wait for the next merge window and the rejection will expire automatically
C: The pipeline lacks its own approval policy, so the team should add one to the pipeline and then merge the proposal without the object type
D: A single rejection blocks the whole proposal, so the team should fix the property name and have that reviewer re-review and approve
K: D
G: ## Proposals in Global Branching
When a branch is ready, a **proposal** reviews and merges its changes into `main`. Checks run on each resource, and **all approval policies must be satisfied** before merging.
## Rejections
The core concepts page says that **a single rejection from any user causes that resource's changes to be Rejected, which prevents the entire proposal from merging**. The rejecting user must re-review and approve before the merge can go ahead.
## Removing a resource
Removing a resource from a branch returns it to its `main` version, but the docs warn this can break the branch if other branched resources rely on it. Here the pipeline output and the object type change together, so they must ship together.
W: Fix and re-review: the rejection blocks the whole proposal, and the quickest valid path is to address the comment and get the same reviewer's approval.
X: A=Remove the object type and merge the pipeline: the changes depend on each other and must ship together, and removing it does not follow from any rule that pipelines wait for ontology changes.
B=Daily merge window: there is no such window, and a rejection does not expire; the reviewer must re-review.
C=Add a pipeline approval policy: the pipeline is already approved; the block comes from the rejected object type change.
T: In a Global Branching proposal, one rejection blocks everything until the rejecting reviewer re-reviews and approves.
V: Global Branching

@ PLTR-AWARE D1 T1.5 advanced tradeoff
S: A carrier's files land through a Data Connection sync at unpredictable times between 02:00 and 06:00. The Pipeline Builder pipeline that feeds the Shipment objects must refresh as soon as new data arrives, and the platform team wants no builds on nights when the carrier sends nothing. The pipeline takes about ten minutes to build. Which schedule setup meets both goals?
A: A schedule that runs every 15 minutes from 02:00 to 06:00, so new files are picked up within a quarter of an hour
B: A schedule that runs once at 06:30, after the latest possible arrival time, so the pipeline always builds after the files are in place
C: A schedule triggered when input data has been updated, so the output builds only after the carrier sync writes new data
D: A schedule triggered when the pipeline logic has been updated, so the output rebuilds whenever a builder publishes a change to the pipeline
K: C
G: ## Pipeline Builder schedules
Schedules keep pipeline outputs up to date. The docs list the triggers a schedule can use:
- **at certain times**;
- **when data has been updated**;
- **when logic has been updated**;
- any combination of these.
They also choose the scope: a single dataset, a dataset and its dependencies, everything downstream, or everything between two datasets.
## Event triggers versus clocks
A time trigger runs whether or not anything changed. A data-updated trigger runs only when an input has new data, so it reacts quickly and does nothing on empty nights.
## Example
The carrier sync commits at 03:47; the schedule fires right after, and the Shipment objects refresh minutes later. On a night with no files, no build starts.
W: Data-updated trigger: it fires right after new data lands and stays idle when nothing arrives, meeting both goals.

B=Once at 06:30: no wasted builds most nights, but data arriving at 02:00 waits four and a half hours.
D=Logic-updated trigger: it reacts to pipeline edits, not to new carrier data, so nightly files would never be processed.
T: Trigger a pipeline on input data updates when arrival times vary and idle builds should be avoided.
V: Pipeline Builder

@ PLTR-AWARE D1 T1.5 advanced troubleshooting
S: A Pipeline Builder pipeline takes about 25 minutes to build, and its data-updated schedule fires each time a stream of small sensor files lands, roughly every 10 minutes.
