@ PLTR-AWARE D3 T3.2 applied use-case
S: A procurement director says invoices "take forever" between requisition and payment, but nobody can say where they wait. The steps already leave records in the ERP and in Foundry. Which Palantir capability is built for seeing how this purchase-to-pay process actually runs and where it gets stuck?
A: Machinery, which models the process as states and transitions of the invoice entity and can mine the real flow from historical state changes
B: Pipeline Builder, which joins the ERP tables into one clean dataset so that a weekly report can list every invoice that is older than thirty days
C: AIP Logic, which reads each invoice object with a language model and writes a short explanation of why that particular invoice has been delayed
D: Data Connection, which syncs the ERP approval tables into Foundry on a schedule so that the finance team can open them next to the invoice records
K: A
G: ## What Machinery is for
The Machinery documentation describes many real-world events as **processes**: entities such as documents, equipment or people change state over time. Machinery lets you understand and manage a process, identify unwanted behaviour and improve it toward a desired outcome.
The docs list purchase-to-pay ("from requisition to payment") as one of the example use cases, next to insurance claims, hospital operations and order-to-cash.
## How it sees the process
- The **process object** is the entity that moves through the process, here an `Invoice`, with a string property that holds its current state.
- **States** (created, approved, paid ...) are nodes; **transitions** between them are edges.
- **Process mining** derives the model automatically from historical observations, and metrics such as time in a state reveal bottlenecks.
## Where the other tools fit
Data integration and pipelines prepare the data Machinery reads; AIP Logic can act on single objects. Neither shows the flow of thousands of invoices through their states.
W: Machinery: it is the application the docs name for modelling a process as states and transitions, mining it from historical data and finding bottlenecks, and purchase-to-pay is one of its listed use cases.
X: B=Pipeline Builder: it can prepare the data, but a list of old invoices says nothing about which step they wait in or which paths they take.
C=AIP Logic: an LLM explaining one invoice at a time does not give a process-wide view of states, transitions and durations.
D=Data Connection: syncing the tables is a prerequisite, not the analysis. Raw tables next to each other do not show the flow.
T: When the question is "where does this process get stuck", Machinery models the entity's states and transitions and mines the real flow from history.
V: Machinery

@ PLTR-AWARE D3 T3.2 applied definition
S: A team wants to model its parcel delivery process in Machinery. The Parcel object type has these string properties: `name`, `status` (values such as received, sorted, out for delivery, delivered), `notes` and `driver_comment`. Which property should represent the process state?
A: `name`, because each parcel has its own unique name and Machinery needs one distinct value per parcel to follow it through the process
B: `notes`, because staff write the parcel's progress into it in their own words, which gives the richest description of each step taken
C: `driver_comment`, because drivers update it at every stop, so it changes most often and best reflects the parcel's movement over time
D: `status`, because it holds a small fixed set of values describing the parcel's current condition, which is what a state needs to be
K: D
G: ## What a state is in Machinery
The Machinery core concepts define a **state** as the current condition of an object, for example in progress or delivered for a parcel. Two rules follow:
- The process object type must have a **string property** that holds the state.
- The possible states must be **enumerable**. The docs give the counterexample directly: a `Name` property is not suitable because there are indefinitely many possible names.
Every object must be in exactly one of the possible states at any time, and transitions between states become the edges of the graph.
## Keeping states clean
The docs suggest backing the state property with an **enumeration value type**, so the Ontology data can only take predefined values and Machinery keeps its process states in sync with them.
## Identity is separate
Telling one parcel from another is the job of the object's primary key, not of the state property.
W: `status`: it is a string with a small, enumerable set of values describing the parcel's current condition, exactly what the docs require of a state property.
X: A=`name`: the docs use a name as the example of an unsuitable state, because there are indefinitely many values. Identifying a parcel is the primary key's role.
B=`notes`: free text written in each person's own words is not enumerable, so the graph would get one node per wording instead of a handful of states.
C=`driver_comment`: changing often does not make a property a state. Comments are free text with unlimited values, which cannot form a fixed set of nodes.
T: A Machinery state property is a string with an enumerable set of values, such as a status field, never a free-text or identifying field.
V: Machinery, Ontology

@ PLTR-AWARE D3 T3.2 applied troubleshooting
S: While modelling employee onboarding in Machinery, a builder finds that an employee can be "onboarded" and at the same time "awaiting payment" from payroll. Putting all of these values in one `state` property keeps breaking the graph. What does the Machinery documentation recommend?
A: Combine the two values into one compound state such as "onboarded and awaiting payment", so that each employee still has only one state at a time
B: Model onboarding and payment as separate processes, with a parent process that tracks whether the employee is ready to be paid
C: Let each employee hold a list of current states in one property, so that Machinery can place the same object on several nodes of the graph at once
D: Drop the payroll states from the model entirely, because Machinery is only able to track a single linear process for any one object type
K: B
G: ## One state at a time
Machinery's core concepts say that every object must be in exactly one of the possible states at any given time. When an entity is naturally in two conditions at once, that is a sign of two processes, not one.
## Process hierarchy
The docs use this very case: an employee can be new-hire or onboarded, and also paid or awaiting payment. These should be **separate processes**, with a **parent process** that tracks whether the employee is payable. In Machinery, process containers can be linked to each other and even nested, and an object type can carry more than one state property (for example a coarse and a granular state), each captured by its own container.
## Why not merge values
Compound states multiply quickly (every onboarding step times every payment step) and hide which part of the work is actually slow.
W: Separate processes with a parent: the documentation's answer to an object being in two conditions at once is a process hierarchy, not one overloaded state property.
X: A=Compound state: it technically keeps one value, but it multiplies the number of states and mixes two independent flows, which the docs avoid by splitting the processes.
C=List of states: the docs require one state value per object at a time, held in a string property; a list of simultaneous states is not how Machinery models a process.
D=Drop payroll: Machinery supports several linked and nested process containers and several state properties on one object type, so nothing needs to be thrown away.
T: If an entity is in two conditions at once, model two processes under a parent process instead of forcing both into one state.

@ PLTR-AWARE D3 T3.2 applied troubleshooting
S: A builder points Machinery at the Claim object type, which holds only each claim's current `state`. Mining shows the states, but the team cannot see which paths claims took or how long they spent in each state. What is missing?
A: A Workshop module with the Machinery widget, because transitions and durations are only calculated when the graph is shown inside an app
B: An enumeration value type on the state property, because Machinery only records transitions when the state values come from a fixed list
C: A log object type that records each state change of a claim with its old state, new state and timestamp, which Machinery uses to derive paths
D: A second process container nested inside the claim process, because transitions are stored on the child container and durations on the parent
K: C
G: ## Latest state versus history
The Machinery docs connect a process to two kinds of object data:
- **Process objects** such as `Claim` hold the **latest** state. The docs state that the process object type "cannot inform on state transitions and temporal patterns".
- **Log objects** record each individual change: a reference to the process object, the old state, the new state and the timestamp (with optional duration and path).
## Why the log matters
Patterns in paths and metrics such as average time in a state need the time dimension of each change. Machinery can install a standard solution that builds the log object type for you, from platform edit history or from an external changelog dataset. In mining, the docs say a log object type is recommended over mining only the latest state values.
Example: a log row `claim-17, submitted -> under review, 2026-05-03 09:14` is what lets Machinery count that transition and measure the wait.
W: Log object type: only a record of each change with old state, new state and timestamp lets Machinery derive transitions, paths and durations; the current-state object cannot.
X: A=Workshop widget: the widget displays metrics, but it reads them from the same process and log objects. Without a log, there is no history for it to show.
B=Enumeration value type: it keeps state values clean and in sync, but a clean current value is still only the latest state with no history behind it.
D=Nested container: containers model related or child processes, not storage for transitions. The history of one claim still needs a log.
T: Process objects give the current state; a log object type of timestamped state changes is what reveals paths and time in each state.

@ PLTR-AWARE D3 T3.2 applied use-case

A: A dataset in changelog format with one row per state change, giving the process id, the new state and the timestamp of the transition

G: ## Two sources of state changes
Machinery's log setup can track edits from two places:
- **Platform edits**: if the process object type is edited in Foundry, edit history can be enabled and included in the log.
- **External data**: if changes happen outside the platform, you provide a dataset in **standard changelog format**.
## The changelog format
The docs list its columns: `processId` (the entity), `state` (the new state entered), `timestamp` (when the transition occurred) and an optional `isDeleted` flag. Machinery then installs a product with a Pipeline Builder pipeline that turns these rows into the log object type, and computes derivations such as the previous state, the duration between states and the path taken.
## What not to do
The docs say the log object type is maintained automatically by Machinery, and you should not define actions on it yourself.
W: Changelog dataset: for processes outside the platform the docs require a dataset that records which object entered which state at what time, which Machinery turns into its log.
X: B=Overwriting snapshot: it keeps only the current ward, so any move between two snapshots is lost and timestamps of transitions are unknown.
C=Action on the log type: the docs say the log object type is maintained by Machinery and you should not define actions on it yourself.
D=Free-text export with an LLM: Machinery does not infer states from prose. It expects structured rows with an id, a state and a timestamp.
T: For external processes, give Machinery a changelog dataset of process id, new state and timestamp; it builds and maintains the log itself.

@ PLTR-AWARE D3 T3.2 applied comparison
S: Two teams start with Machinery. Team one has three years of state-change history for its insurance claims. Team two is designing a brand-new equipment inspection process that has no data yet. How should each team create its process model?
A: Both teams should draw the model by hand first, because process mining is only used later to monitor a process that has already been drawn and published
B: Both teams should wait to mine, because Machinery can only build a model from historical data and cannot represent a process that has never run
C: Team one should draw by hand to avoid noise in old data, while team two should mine because a new process has no errors in it to filter out
D: Team one can mine the model from its historical state changes, while team two draws its states and transitions by hand from the planned design
K: D
G: ## Two ways to build a process model
The Machinery docs give two routes:
- **Process mining** derives the model automatically from **historical observations**. Mining is a dedicated mode once a data connection exists, and shows the states and transitions found in the data.
- **Manual drawing** suits a process you have in mind (for example a physical process) or an existing model you want to modify. You start with a process container, add an initial state, the following states, and the actions and automations between them.
## They work together
Mining overlays what the data shows on the current definition, so a hand-drawn model can later be checked against real data. And linking concrete actions and automations to a drawn graph gradually turns the model into an implementation.
W: Mine where history exists, draw where it does not: years of state changes are what mining needs, and a process with no data can only be drawn from the planned design.
X: A=Draw first for everyone: mining can create the model from history on its own; it is not limited to monitoring an already drawn process.
B=Wait for data: the docs offer manual drawing precisely for processes you have in mind, so a new process does not have to run before it is modelled.
C=Swapped routes: mining needs data, so it cannot model a process with none. Noise in old data is handled by the mining filters, not by avoiding mining.
T: Mine a process model from historical state changes when you have them; draw it by hand when the process is new or you want to adjust a model.

@ PLTR-AWARE D3 T3.2 applied troubleshooting
S: A team mines its order-to-cash process in Machinery. The result shows dozens of rare transitions, including a few caused by a typo in an old status value, and the graph is too tangled to discuss. What is the intended way to get a usable model?
A: Delete the rows with rare transitions from the source dataset, so that the next mining run only sees the common paths and produces a cleaner graph
B: Apply the transition filter to keep the most frequent share of transitions, and list the typo values as excluded elements in the mining settings
C: Switch mining to read only the process objects instead of the log objects, because current states alone contain fewer unusual transitions
D: Accept the full mined graph as the process definition, because Machinery hides any transition that occurs in fewer than one percent of objects
K: B
G: ## Mining produces noise
The process mining docs warn that collected data often contains noise and errors, so raw mining output can be too complex or contain unexpected results. Machinery gives two filters:
- **Transition filter**: transitions are ranked by how often they occur, and only the top x % of the cumulative total are kept, cutting off the tail of infrequent transitions.
- **Excluded elements**: a list of erroneous state values or transitions that must not enter the process definition. The list is saved and can be managed over time.
## Why not fix it by deleting data
The source data is still the record of what happened. Filtering the mining result shapes the model without destroying evidence that rare paths exist, which may matter later when looking for deviations.
W: Transition filter and excluded elements: these are the mining filters the docs provide for cutting infrequent transitions and keeping erroneous values out of the definition.
X: A=Delete source rows: it destroys real history to tidy a picture, and the same problem returns with new data. The docs handle it with filters in mining instead.
C=Process objects only: the docs recommend a log object type for mining. Mining only latest values loses transitions instead of filtering the noisy ones.
D=Accept the full graph: the docs describe no automatic one-percent cut-off for mining; the builder sets the transition filter and exclusions.
T: Tame a noisy mined process with the transition filter and an excluded-elements list, not by deleting source data.

In mining mode, Machinery overlays the existing process definition with the states and transitions found in the data. The docs give three styles:

@ PLTR-AWARE D3 T3.2 applied troubleshooting
S: A builder renames the state "pending_qc" to "Waiting for quality check" in a Machinery graph. Afterwards, an action's submission criteria still check for "pending_qc", and the Ontology data still shows the old value. Why?
A: The rename failed to save, because states connected to actions are locked and can only be renamed after the actions are removed from the graph
B: Machinery is waiting for the next log pipeline build, after which the data and the action's submission criteria will both use the new value
C: The Ontology rejected the change, because a state can only be renamed by changing the enumeration value type that backs the state property

G: ## The graph describes, the data decides
Machinery's states are tied to data: the state ID in Machinery equals the string value of the object's state property. The docs are explicit about what editing the graph does not do:
- Changing the name of a state in Machinery **does not change values in your data**.
- Changing the state value in Machinery does **not update dependencies** such as action submission criteria or automations triggered by a state condition.
## Showing a friendlier label
To change the label shown on the graph, the docs say to **overwrite the display name** and keep the state ID equal to the data value. Backing the state property with an enumeration value type keeps Machinery's states in sync with the allowed values.
## Practical rule
Treat the graph as a model of the process. Changing what the process really does means changing the data, the actions and the automations themselves.
W: Model, not data: the docs state that renaming a state in Machinery changes neither the Ontology values nor dependencies such as submission criteria; a display name is the way to relabel it.
X: A=Locked states: the rename did take effect in the graph. What it does not do is reach the data and the action's criteria.
B=Wait for a build: the log pipeline computes log entries from data; it never rewrites the process object's state values or an action's criteria.
C=Ontology rejected it: nothing was sent to the Ontology. The graph edit simply does not touch the data.
T: Renaming a state in Machinery changes only the model; data values and action criteria stay as they are, so use a display name for labels.

@ PLTR-AWARE D3 T3.2 applied definition
S: A team has drawn its maintenance work-order process in Machinery. A planner asks what actually moves a work order from "scheduled" to "in progress" when that change happens inside Foundry, and how the graph reflects it. Which answer matches the Machinery documentation?
A: The log object type moves it: Machinery writes the new state into the work order each time a new log entry is created for that order

G: ## What causes a state change
The Machinery core concepts are direct: **actions are the cause of state transitions**. State changes that happen within the platform are defined by an action, and you can import those actions into the Machinery graph and describe their role in the process.
## How the graph shows it
- **Input states**: the states an object may be in before the action. For Foundry actions this can be enforced through submission criteria.
- **Output states**: the possible results, for example "extraction succeeded" or "extraction failed".
- **Automations**: an action that is triggered automatically when one of its input states is reached.
Linking concrete actions and automations to the drawn graph gradually turns the process model into a process implementation.
## What the other parts do
The log object type records changes after they happen, mining reads history to build a model, and the widget displays metrics and filters objects. None of them changes an object's state.
W: Action: the docs say actions cause state transitions inside the platform, and the graph shows each action between its input states and its output states.
X: A=Log object type: it records each change after the fact and is maintained by Machinery; it is a history, not the cause of the change.
C=Process mining: it derives a model of states and transitions from historical data; it never moves live objects to another state.
D=Machinery widget: selecting a node filters the widget's output object set by state; it does not edit the objects.
T: In Machinery, actions (and automations, which are triggered actions) cause state transitions; logs, mining and the widget only record, model or display them.

@ PLTR-AWARE D3 T3.3 applied definition
S: An operations lead asks what AIP Logic is before approving a pilot. Which description matches Palantir's documentation?
A: A code repository template where engineers write Python that calls an LLM provider's API with their own keys and deploy it as a scheduled transform

G: ## AIP Logic in one sentence
The documentation calls AIP Logic a **no-code development environment for building, testing and releasing functions powered by LLMs**. A Logic function:
- takes **inputs** such as Ontology objects, object sets or text strings,
- is composed of **blocks** (Use LLM, Apply action, Execute function, loops, conditionals, variables),
- returns an **output**: a value, an object, or edits to the Ontology.

Builders get AI-powered functions that use the Ontology without managing development environments and API calls themselves. Logic functions are then used like any other function: in Workshop, behind actions, or in automations.
## What it is not
It is not a model training tool; the Use LLM block uses models already available in the platform, following Palantir's multi-model approach.
W: No-code LLM function builder: this is the docs' own definition, with inputs like objects or strings and outputs that can be values or Ontology edits.
X: A=Code template with own keys: the docs stress that Logic avoids the complexity of development environments and API calls; models come from the platform.
C=Free-form chat: Logic builds and releases reusable functions; it is not a chat window over datasets.
D=Fine-tuning service: Logic writes prompts and uses available models; training a private model is not what it does.
T: AIP Logic is a no-code way to build, test and release LLM-powered functions that read from and act on the Ontology.

## The documented path
1. Give the function a way to edit: an Apply actions tool in a Use LLM block, or an Apply action block.
2. **Publish** the Logic function when you are done iterating.
3. **Create an action backed by** the published function.
4. Use that action in a **Workshop** module to power the workflow.
## Where Logic files live
A new Logic file must be saved in a project folder, not in a home folder, and permissions come from the platform's normal security model, not from a special grant to the function.
W: Publish, back an action, use it in Workshop: this is the sequence the docs give for turning a Logic function's proposed edits into real Ontology changes from an app.
X: B=Run it by hand: runs inside AIP Logic only propose edits, and copying results manually defeats the purpose of putting the decision in the app.
C=Edit permission on the function: there is no such grant; the docs require calling the function from an action for edits to be written.
D=Home folders: Logic files must be saved in a project folder, and copies per user would split one function into many unmanaged versions.
T: A Logic function changes the Ontology only when it is published and called from an action, which a Workshop app can then use.

@ PLTR-AWARE D3 T3.3 applied use-case
S: A Logic function drafts a quote for a customer and must include the total price, which comes from quantities, unit prices and a discount. In tests, the language model sometimes adds the numbers up wrongly. Which built-in option does AIP Logic offer for this?

G: ## Tools in a Use LLM block
A Use LLM block is made of a **prompt**, **tools** and an **output**. Tools let the model reach beyond its own text generation; the docs list:

@ PLTR-AWARE D3 T3.3 applied comparison
S: A Logic function always sets an incident's priority to "high" when its severity property is critical. The team wants this step to fill the action parameters the same way every time and run fast. Which building block fits best?
A: An Apply actions tool in a Use LLM block, with a prompt telling the model to set high priority whenever the incident looks critical
B: A Query objects tool that lets the model read the incident's severity and decide for itself whether the priority needs changing

K: D
G: ## Two ways to apply an action in Logic
- **Apply actions tool** (inside a Use LLM block): the model decides whether and how to call the action, guided by the prompt. Useful when judgement is needed.
- **Apply action block**: calls an action **deterministically**, without going through an LLM. The docs say it gives **precise control over how parameters are filled** and **speeds up execution**; their own example sets a priority status on an incident.
## Choosing
If a rule is fixed (critical means high), there is nothing for a model to judge. A deterministic block is faster, cheaper and predictable. Keep LLM blocks for the parts that need reading or reasoning over unstructured input. A conditional block can route different cases down different paths when the rule has branches.
Either way, the edit is written only when the Logic function runs from an action or automation.
W: Apply action block: it calls the action without an LLM, filling parameters exactly as configured, which the docs describe as precise and faster.
X: A=Apply actions tool: it leaves a fixed rule to the model's judgement, so the parameter could differ between runs and each run pays for an LLM call.
B=Query objects tool: it lets the model read data but not apply the edit, and it still makes a fixed rule depend on model judgement.
C=Call another Logic function: it adds a second model for a rule that needs no model at all, making the step slower and less predictable.
T: When an edit follows a fixed rule, use the deterministic Apply action block; keep LLM tools for steps that need judgement.
