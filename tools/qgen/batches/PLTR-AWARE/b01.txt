@ PLTR-AWARE D1 T1.1 applied definition
S: A planning team describes one of its weekly decisions: "We look at stock levels per warehouse, run our demand forecast model, and then reorder from a supplier." In Palantir's breakdown of a decision into data, logic and actions, where does the demand forecast model belong?
A: Data, because the forecast produces numbers that describe the world, so it counts as one more fact about stock levels next to the warehouse records
B: Actions, because the forecast directly triggers the supplier reorder, so it is part of how the decision takes effect in the operational systems
C: Logic, because a forecast is reasoning that evaluates the decision and enriches its context, alongside business rules and optimization models
D: None of the three, because models are managed in a separate data science workbench and stay outside the decision model of the platform itself
K: C
G: ## Data, logic and actions
Palantir's platform documentation breaks every decision into three components, and builds the platform around them:
- **Data**: the relevant facts about the world and the operations, the context of the decision. Here: stock levels per warehouse.
- **Logic**: the reasoning that evaluates the decision. Business rules, probabilities of outcomes, forecasts, optimization models and earlier similar cases all count as logic.
- **Actions**: the "kinetics", how the decision takes effect in the world, inside the Ontology or in external systems. Here: the reorder sent to a supplier.
## Why the split matters
The same model can feed many decisions, and the same action can be driven by different logic. Treating them as separate building blocks lets each one evolve on its own: the forecast model can be replaced without changing how reorders are written back. The "Why create an Ontology?" page adds a fourth element, security, which governs all three.
W: Logic: the documentation lists forecasting and optimization models under logic, the reasoning that enriches the context and evaluates options before anyone acts.
X: A=Data: the facts here are the warehouse stock records. A forecast is computed reasoning about what may happen, which the docs place under logic, not under the facts of the world.
B=Actions: the action is the reorder itself, the change that reaches the supplier. The forecast informs that action but does not carry it out.
D=Outside the model: the docs state the opposite. Models trained in the platform, uploaded or hosted elsewhere can be bound to the Ontology as logic.
T: In Palantir's decision model, facts are data, reasoning such as forecasts and rules is logic, and the change made in the world is the action.

@ PLTR-AWARE D1 T1.1 applied comparison
S: A logistics company already has dashboards that show late shipments every morning. A manager asks what would make a new solution "operational" rather than "analytical" in the sense Palantir uses. Which answer matches that distinction?
A: The operational solution refreshes its data in real time, while an analytical one refreshes on a schedule; the speed of the data is the defining difference
B: The operational solution lets users and agents act on what they see, and those decisions are written back to the Ontology or source systems
C: The operational solution is used by frontline staff, while an analytical one is used by managers; the audience of the screens is the defining difference
D: The operational solution replaces the existing dashboards entirely, while an analytical one runs next to them as a second reporting tool for managers
K: B
G: ## Closing the loop
The Palantir documentation draws the line clearly: "Closing the action loop as decisions are made in real-time is what distinguishes an operational system from an analytical system."
- An **analytical** system shows what happened. Someone reads the dashboard, then switches to another system (email, ERP, a phone call) to do something about it, and that decision is not recorded next to the data that prompted it.
- An **operational** system lets the person, or an AI agent, act from the same place: reassign the shipment, change its priority, notify the carrier. The action is captured in the Ontology and can be written back to the systems that run the process.
## Why it matters
Captured decisions become data themselves. Later, the team can pair each decision with its outcome, which feeds better rules, models and agents. The platform still supports conventional analytics; the operational layer is what it adds.
W: Act and write back: the docs define operational work by closing the action loop, so decisions made on the data are captured and pushed to the Ontology or the systems of record.
X: A=Data freshness: real-time data helps, but a real-time dashboard that nobody can act from is still analytical. The docs tie the difference to closing the action loop, not to refresh speed.
C=Audience: frontline staff can use read-only reports and managers can take operational decisions. Who looks at the screen does not decide whether the loop is closed.
D=Replace dashboards: the platform keeps analytics and BI workflows (it even offers connectors to BI tools). Operational use adds actions; it does not require removing existing reporting.
T: A solution is operational when people and agents can act from it and those decisions are captured and written back, not just viewed.

@ PLTR-AWARE D1 T1.1 applied tradeoff

A: The Ontology stores data more cheaply than a warehouse, so moving the tables into it lowers storage costs while keeping the same reports running
B: The Ontology replaces the warehouse's SQL with a visual query tool, so analysts no longer need to write joins when they build their weekly reports

D: The Ontology captures decisions, not only data: the logic and actions around them, so people and agents can act on operations, not just report

G: ## Data-centric versus decision-centric
The "Why create an Ontology?" page contrasts two architectures:
- Traditional data architectures store facts for reporting. They "do not capture the reasoning that goes into decision-making or the actions that follow", which limits learning and the use of AI.
- The Ontology "represents the decisions in an enterprise, not simply the data". It brings together data, logic, action and security in one model that both humans and agents use.
## What the warehouse keeps doing
A warehouse is not wasted: it can be one of the sources that feeds the Ontology. The difference is what sits on top. Objects and links give the business meaning, actions let users change things in a governed way, and every decision is recorded with its context ("decision data"), so the next decision and the next model can learn from it.
The course calls this "decision-centric"; the docs use the same phrase ("the decision-centric Ontology").
W: Decisions, not only data: the documentation's stated reason for the Ontology is that it models the decision, combining data with logic, actions and security, so humans and agents can act on operations.

B=Visual queries: point-and-click analysis exists in the platform, but replacing SQL for reports is not the reason given for the Ontology. A warehouse already serves reporting well.
C=Guaranteed quality: objects are backed by data and inherit its gaps. Data quality comes from pipelines and health checks, not from a guarantee built into the object model.
T: The Ontology's value over a warehouse is that it models decisions (data, logic, actions and security), so operations can be run, not only reported on.

B: Security, which ensures that the decision complies with operational policies for both the people and the agents involved in it

The platform overview speaks of data, logic and actions. The "Why create an Ontology?" page adds a fourth component and defines all four:
- **Data**: the information leveraged to make the decision.
- **Logic**: the heuristics and computations that evaluate it.
- **Action**: the orchestration and execution of the chosen decision.

## Why security is a component, not an add-on
Humans and AI agents work on the same Ontology. Security policies (markings, purpose- and role-based policies, row and column restrictions) are computed at runtime for every interaction, and tool use by agents is enforced through the same architecture. That is why the docs treat security as part of the decision itself: an agent should only see and do what its grants allow, exactly like a person.

C=Lineage: lineage is a real platform capability and supports security and learning, yet it is not the named fourth component of a decision.
D=Feedback: capturing outcomes to improve later decisions is described as a benefit of the Ontology, not as one of the four components.
T: Palantir models a decision as data, logic, action and security, with security ensuring compliance for humans and agents alike.

S: A maintenance team wants its AI workflows to work with three kinds of information beyond plain tables: thousands of repair manuals, photos of damaged parts, and part numbers that must follow a strict format. How does Palantir's platform overview describe the Ontology's support for this?
A: The Ontology handles only structured tables, so manuals and photos must stay in a separate document system that AI workflows query on their own, outside the model
B: The Ontology supports extended primitives such as semantic search for unstructured text, media references for images, and value types that add constraints to data

- **Semantic search** unlocks unstructured data, such as the text of repair manuals, so a workflow can find passages by meaning.

T: The Ontology handles unstructured text, media and constrained values through semantic search, media references and value types, not only tables.

@ PLTR-AWARE D1 T1.1 applied tradeoff
S: A supply chain analyst wants to substitute a raw material in one product line, but the same material feeds other products and the knock-on effects are unclear. Planners want to see the consequences before anything changes in production. Which approach matches the platform overview's guidance for this kind of what-if question?
A: Apply the substitution in the live Ontology during a quiet hour, watch the forecasts react, and roll it back afterwards if the results look worse than expected
B: Stage the substitution on a branch of the Ontology, and run forecasts and other analyses on top of that potential change before anyone commits it to production
C: Export the affected tables to a spreadsheet, edit the material there, and estimate the downstream effects by hand before entering the change in production
D: Describe the substitution to an AI agent in a long prompt, and accept its written summary of the likely effects as the basis for the production decision
K: B
G: ## The Scenario primitive
The platform overview notes that in tightly coupled environments such as a supply chain "a small change can cause cascading effects". The **Scenario** primitive makes changes to a branch of the Ontology, "effectively creating a sandbox universe" in which forecasts, business process models and other analyses run on top of, and downstream of, the potential change.
- The "Why create an Ontology?" example stages simulated material substitutions as Ontology scenarios, so teams can explore the implications "before committing to it".
- Agents use the same scenarios framework: an agent's proposed plan can be staged in a scenario and handed to a human for final review.
- Workshop natively supports scenarios for "What if..." workflows, and Vertex specializes in process visualization and scenario testing.
## The tradeoff
A scenario takes a little setup, but production data stays untouched until someone commits the decision. Trying the change live puts production at risk; estimating it outside the platform loses the connected models that reveal the knock-on effects.
W: Stage it in a scenario: a branch of the Ontology acts as a sandbox, so the connected models show the downstream effects before anything is committed.
X: A=Change live, roll back: production users and systems act on the change while it is being tested. The docs stage what-if changes instead of trying them in production.
C=Spreadsheet estimate: the copy loses the links to other products and the connected forecast and optimization models, which are what reveal the knock-on effects.
D=Prompt an agent: a summary written from a description is not a simulation on the connected models. In the docs, agents stage their proposals in the same scenarios for human review.
T: Stage a what-if change as a scenario on a branch of the Ontology to see its downstream effects before committing it.

@ PLTR-AWARE D1 T1.1 applied definition
S: The Architecture Center says the Ontology is not a thin semantic layer but a system made of a Language, an Engine and a Toolchain. Which part provides the read and write architecture, such as high-scale queries, subscriptions to changes and transactional updates?
A: The Language, because it defines the objects, links and actions, so it also executes every query and every write made against them
B: The Toolchain, because developers use it to build applications, so it is the part that stores data and runs every transactional update
C: The Workflow Services, because they run interactive compute, so they hold the read and write architecture of the Ontology system as well
D: The Engine, because it substantiates every component of the Language and is where queries and updates against the Ontology are executed
K: D
G: ## Language, Engine, Toolchain
The Architecture Center groups the Ontology's many components into three parts:
- **Language**: models the semantic objects, links and properties, the kinetic actions and automations, and the logic that defines how actions work and interact with other systems. It is *what* is modeled.
- **Engine**: "substantiates every component of the Language". On the read side: high-scale SQL queries, real-time subscriptions to state changes and the materializations humans and AI need. On the write side: atomic transactional updates, high-scale batch mutations, streams and change data capture.
- **Toolchain**: lets developers use the Ontology as a backend, through the Ontology SDK (OSDK) and DevOps tooling for governed production use cases.
## Why it is not a "semantic layer"
The docs state that the "fourfold integration and operationalization of data, logic, action, and security cannot be accomplished with a thin semantic layer". The Ontology also executes reads and writes at scale and is used to build applications, which is why the docs insist on the three-part description.
W: Engine: the docs assign the scalable read architecture (queries, subscriptions) and write architecture (transactional updates, batch mutations, streams) to the Engine.
X: A=Language: the Language defines what exists (objects, links, actions, logic). Running queries and writes against those definitions is the Engine's job.
B=Toolchain: the Toolchain is how developers build on the Ontology, through the OSDK and DevOps tooling. It uses the Engine; it is not where reads and writes are executed.
C=Workflow Services: these are a family of services around the Ontology (applications, automations), not one of the three parts of the Ontology system itself.
T: In the Ontology system, the Language defines, the Engine executes reads and writes, and the Toolchain lets developers build on it.

@ PLTR-AWARE D1 T1.2 applied definition
S: A new analyst who knows spreadsheets asks how Ontology concepts compare with a dataset. Which comparison matches Palantir's own description?
A: An object type is like a column, an object is like a dataset, a property is like a row, and a link type is like a filter applied to one dataset
B: An object type is like a row, an object is like a field value, a property is like a dataset, and a link type is like a sort order on two columns
C: An object type is like a dataset, an object is like a row, a property is like a column, and a link type is like a join between two datasets
D: An object type is like a join, an object is like a column, a property is like a filtered set of rows, and a link type is like a single field value
K: C
G: ## The dataset analogy
The Ontology core concepts page compares each Ontology idea with a familiar dataset structure:
- Dataset -> **object type** (for example `Employee`)
- Row -> **object** (one employee, "Melissa Chang")
- Column -> **property** (`role`, `start date`)
- Field (one cell) -> **property value** ("Product Manager")
- Join -> **link type** (`Employee` to `Company`)
## Where the analogy stops
The Ontology adds what a table does not have: business names and metadata, links that applications can follow, and action types that define how objects may change. A filtered set of rows has a counterpart too: an **object set**, such as "all tenured employees".
W: Dataset, row, column, join: the docs map object type to dataset, object to row, property to column and link type to join.
X: A=Column/dataset/row: this shuffles the mapping. Columns correspond to properties, and a filter corresponds to an object set, not to a link type.
B=Row/field/dataset: a row is one object, not the type, and a field value is a property value. A link type relates two object types, which a sort order does not.
D=Join/column/filter: a join corresponds to a link type, not to an object type, and a filtered set of rows is an object set, not a property.
T: Object type = dataset, object = row, property = column, property value = field, link type = join.

C: A link type, because the grounded aircraft are related to a maintenance status and that relationship defines the collection of aircraft
D: An action type, because a grounded aircraft is the result of a change in status and the action defines which aircraft belong together
K: A
G: ## Type, instance, set
The object types page uses three related terms:
- **Object type**: the schema of a real-world entity or event, for example `Aircraft` with its properties.
- **Object**: one instance, a single aircraft such as tail number N123.
- **Object set**: a collection of objects, a group of real-world entities. "All arrived flights" or "all tenured employees" are the docs' examples.
In dataset terms, an object set is like a filtered set of rows.
## Why the distinction matters
Groups change all the time: an aircraft is grounded today and flying tomorrow. A filter over one object type keeps the model stable, while a separate type for every group would multiply schemas and split the same aircraft across them.
W: Object set: a group of aircraft selected from the `Aircraft` object type is an object set, the Ontology counterpart of a filtered set of rows.
X: B=New object type: object types are schemas of entities. A grounded aircraft is still an aircraft; filtering does not need a new schema.
C=Link type: link types relate two object types (for example `Aircraft` to `Flight`). A status filter on one type is not a relationship.
D=Action type: an action type defines how objects can be changed, such as setting a status. It does not define a group used for viewing.
T: Object type is the schema, object is one instance, and an object set is a group of instances, like filtered rows.

G: ## What an interface is
An **interface** is an Ontology type that describes the shape of an object type and its capabilities. Object types that share a common shape implement it, which the docs describe as polymorphism.

G: ## Two kinetic building blocks
The core concepts page defines both:
- **Action type**: "the schema definition of a set of changes or edits to objects, property values, and links that a user can take at once", including the side effects that occur on submission. An **action** is one application of it, a single transaction.
- **Function**: "a piece of code-based logic that takes in input parameters and returns an output". Functions can take objects and object sets as input, read property values, and be used across action types and applications.
## How they work together
A function computes; an action type governs a change. A function can back an action type when the change needs complex logic (the platform overview mentions Function-backed Actions), and it can also feed an application directly, for example with a calculated value.
Example: a `Change Delivery Date` action type edits an order and notifies the customer team; a function could compute the earliest feasible date to suggest as its parameter.

X: A=Reversed: functions are code with inputs and outputs; action types define the edits a user makes, not the code itself.
C=Object set and link type: a saved group of objects is an object set, and a relationship between object types is a link type.
D=Interface and object type: a shape shared by several object types is an interface, and the schema of one kind of entity or event is an object type.
T: Action types define the governed changes users make to objects; functions are code-based logic that computes outputs and can power actions and apps.
