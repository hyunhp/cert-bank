@ PLTR-AWARE D1 T1.5 applied use-case

G: ## The path from raw data to an operational tool
The Foundry & AIP Aware course walks from zero to a working tool that harmonizes several sources. The docs describe the same layers:
- Data layer: data lands as datasets (usually synced from source systems) and is transformed in pipelines.
- Object layer (Ontology): clean datasets are mapped to object types, links and actions that anyone can understand.
- Applications: Workshop reads the object layer and uses Actions to write decisions back.
## Example
`carrier_shipments` and `warehouses` arrive as datasets, a Pipeline Builder pipeline cleans and joins them, the outputs back a Shipment object type linked to Warehouse, and a Workshop module lists late shipments with a reassign Action.
W: B=Datasets, pipeline, objects, app: each layer builds on the one below it, so the app reads clean, governed objects and the Action captures the dispatcher's decision.
X: A=Screens first: Workshop reads from the object layer, so screens have nothing to show until data is integrated and mapped to objects.
C=Raw tables as objects, cleaned in the app: the cleaning belongs in the pipeline once, not repeated by every user, and one object per system breaks the shared model.
D=Weekly spreadsheet merge: a manual, stale copy with no lineage and no writeback is exactly what the platform replaces with live data-driven loops.
T: The end-to-end path is sources to datasets, pipeline to clean outputs, outputs to objects, objects to an app with Actions.

The docs describe two places data lives:

- Object layer (the Ontology): objects represent real-world things (a vehicle, a customer), links represent relationships, and actions describe how people may change objects.

@ PLTR-AWARE D1 T1.5 applied troubleshooting
S: A builder combines two carrier files into one shipments table with a union in Pipeline Builder. One carrier names its column ship_id and the other shipment_id, and the union shows an error. What is the most direct fix?
A: Replace the union with a join on the carrier name, since a join accepts inputs whose column names do not match and keeps all rows
B: Rename or cast columns in one input so both share the same schema before the union, since a union requires matching schemas
C: Write a user-defined function in Java to append the files, since built-in transforms cannot handle tables from different carriers
D: Build the pipeline anyway and let the object type ignore the missing column, since schema errors are only warnings at build time
K: B
G: ## Union versus join
- Union: stacks rows from inputs into one table. The docs state the union transform requires all inputs to have the same schema; if they differ it shows an error listing the missing columns.
- Join: combines two tables side by side on at least one matching column.
Harmonizing several sources usually means renaming and casting columns to a common shape first. Pipeline Builder's type-safe functions surface such errors while you build rather than after a long run.
## Example
Rename `ship_id` to `shipment_id` and cast both to string in one input path, then union: one table with every carrier's rows.
W: B=Align the schemas, then union: the error is the documented union rule, and renaming or casting columns is the simple built-in fix.
X: A=Join on carrier name: a join matches rows side by side; it does not stack two carriers' shipments into one list of rows.
C=Java UDF: the docs recommend UDFs only when built-in transforms cannot do the job, and rename plus cast can.
D=Build anyway: Pipeline Builder flags schema problems before the build precisely so they are fixed, not ignored downstream.
T: A union needs identical schemas; rename and cast columns to a common shape first.

S: Each shipment row carries a warehouse_id, and a separate warehouse table holds the warehouse name and region for each id. The team wants every shipment row to show its warehouse name and region. Which Pipeline Builder transform fits?

G: ## Enrich rows with a join
The docs define a join as combining two datasets that share at least one matching column; depending on the join type, matching rows are combined and non-matching rows may be excluded.
- Union stacks rows (same schema required).
- Split partitions one input into a True and a False output by a condition.
- Filter removes rows from one table.
## Example
`shipments.warehouse_id = warehouses.warehouse_id` adds `warehouse_name` and `region` to every shipment. Choosing a join type that keeps all shipment rows avoids losing shipments whose warehouse is missing from the reference table.

X: A=Union: stacks shipments and warehouses as rows of one table, which does not attach a name to each shipment.
C=Split: divides one table into two outputs; it never brings in columns from another table.
D=Filter on warehouses: narrows the reference table but leaves shipment rows without the warehouse columns.
T: To add attributes from a reference table, join on the shared key; unions stack rows.

The docs describe Join, Union and Split as data-structuring transforms with their own configuration panes:
- Split: partitions a single input into two outputs by a condition. Rows satisfying it go to the True output, the rest to the False output.
- It is supported in standard batch and faster pipelines (not in streaming pipelines).
## Example
Condition `origin_country = destination_country` sends domestic shipments to the True output and international ones to the False output, each feeding its own dataset.

C=Join with unmatched rows written out: a join combines tables; it does not route unmatched rows to a second output.
D=Pivot: reshapes values into columns within one table, which is not routing rows to two outputs.

@ PLTR-AWARE D1 T1.5 applied troubleshooting
S: A pipeline build failed overnight and the app still shows yesterday's shipments. The job details show a row count expectation on the output failed because the input arrived nearly empty. What is the right first response?
A: Delete the row count expectation so tomorrow's build succeeds, since an app with fresh data is always better than an app with older data

Data expectations are requirements applied to outputs; the docs say that if any expectation fails, the build fails, and the job expectations pane shows which ones passed and failed. The goal is pipeline stability: a bad input should not silently overwrite good outputs.
## Reasoning
- The output and the objects keep the last successful data, which is why the app shows yesterday's shipments.
- The cause is upstream (a nearly empty delivery), so investigate the source, then rerun.
- Removing the guard would have pushed an almost empty table into the dispatchers' app.

C=Rebuild the object type: nothing is wrong with the Ontology definition; the failure is a data volume check.
D=Edit access for every dispatcher: broad access does not fix an incomplete input and weakens control of the pipeline.
T: When an expectation fails, fix the input that broke it; do not remove the guard.

- when data has been updated,
- when logic has been updated,

G: ## Version control gives a way back
The Pipeline Builder overview lists full version control among its features: users can draft a pipeline separately, collaborate on one pipeline, "or revert to previous versions". Branches let builders iterate without touching main and merge through proposals.
## Recovery pattern
1. Revert main to the last good version and rebuild, so the output and the objects are correct again.
2. Recreate the change on a branch, find why valid rows were dropped (for example, a filter condition that treats `null` as false), preview, and propose a fixed version.

X: A=Delete and rebuild: needless and slow, because the pipeline keeps its version history.
C=Manual entry by users: leaves the output wrong for weeks and pushes the fix onto every dispatcher.
D=Turn off every schedule: freezes all project data, including unaffected pipelines, without restoring the dropped rows.
T: When a merged pipeline change breaks outputs, revert to the previous version first, then fix on a branch.
