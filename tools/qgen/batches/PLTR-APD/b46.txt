# PLTR-APD batch 46: Domain 5 round 6 (OSDK, APIs, and External Applications), 8 questions

@ PLTR-APD D5 T5.3 applied use-case
S: An external mobile app lets drivers mark deliveries as completed and upload a photo. The completion must be validated (driver assigned, delivery not already completed). How should the app perform the update?
A: Write the completion status and photo link directly into the backing dataset from the phone, skipping the Ontology entirely
B: Invoke a Complete Delivery Action via the OSDK with the photo as a parameter, letting the Action validate assignment and status
C: Send an email to dispatch with the photo and ask them to mark the delivery as completed in Workshop by hand
D: Update the delivery through a scraped Workshop page loaded inside the mobile app's web view
K: B
G: ## Writes through Actions from external apps
The exam guide lists invoking Actions via the OSDK among external app skills.
## Design
- Action with parameters (delivery, photo).
- Criteria: driver assigned, status not completed.
- App shows specific validation messages.
Example: a driver completing someone else's delivery sees "You are not assigned to this delivery."
W: Invoking the governed Action from the app: validation, permissions and audit apply exactly as they do inside the platform.
X: A=Direct dataset write: bypasses validation, permissions and audit, and can overwrite concurrent changes made by dispatch.
C=Email to dispatch: adds a manual relay that delays updates and invites transcription mistakes.
D=Scraped web view: brittle, unsupported and breaks whenever the Workshop layout changes.
T: External apps should change Ontology state through Actions invoked via the OSDK.
V: OSDK, Action types

@ PLTR-APD D5 T5.4 applied troubleshooting
S: An external app's users suddenly cannot sign in; the error says the redirect URI does not match. Nothing changed in the app code, but the app was moved to a new domain yesterday. What is the fix?
A: Revert the app to the old domain permanently, since OAuth cannot work with domain changes
B: Register the new domain's redirect URI in the app's OAuth configuration
C: Disable OAuth and use a shared password for all users
D: Ask users to clear their browser cache repeatedly until sign-in works
K: B
G: ## Redirect URIs follow deployments
The exam guide lists deployment issues among OSDK diagnostics. OAuth only redirects users back to URIs registered for the application, so moving the app to a new domain without registering it breaks sign-in immediately.
## Fix
- Add the new redirect URI.
- Test sign-in; retire the old URI later.
Example: sign-in works on the new domain within minutes of the update.
W: Register the new redirect URI: OAuth refuses unregistered redirects, which is exactly the error after the domain move.
X: A=Revert permanently: unnecessary; OAuth works with any registered redirect URI.
C=Shared password: replaces individual sign-in with one shared secret, destroying identity, audit and security.
D=Clear cache: the mismatch is on the server's registration, not in browsers.
T: Update OAuth redirect URIs when moving external apps to new domains.
V: OSDK, Developer Console

@ PLTR-APD D5 T5.1 applied comparison
S: Which requirement most clearly justifies building with the OSDK rather than Workshop?
A: An internal team needs a table of its open tasks and a simple form for updating each task's status and owner
B: A customer-facing portal with custom branding and a tailored mobile experience
C: An internal dashboard with three charts and a filter
D: An internal approval queue with Approve and Reject buttons
K: B
G: ## When OSDK fits
The exam guide asks you to choose Workshop, OSDK or a hybrid and justify it.
- Internal tables, dashboards and approval queues: Workshop strengths.
- Customer-facing, branded, mobile-tailored experiences: OSDK.
Example: customers track orders in a branded mobile app powered by the OSDK.
W: External, branded, mobile-specific experiences need custom applications, which the OSDK supports.
X: A=Internal tasks table and form: Workshop meets this need with far less code.
C=Internal dashboard: native Workshop charts and filters fit well.
D=Internal approval queue: Workshop tables and Actions handle it directly.
T: Choose the OSDK for external or highly custom experiences and Workshop for internal standard ones.
V: OSDK, Workshop

@ PLTR-APD D5 T5.2 applied use-case
S: An internal app uses user-based OAuth. A new requirement adds a nightly job that recalculates scores for all customers. How should the job authenticate?
A: Reuse a particular employee's refresh token so that the job runs as that employee every night
B: A service client with only the permissions the job needs, run server-side
C: Ask an employee to stay logged in overnight so that the job can use their session
D: Skip authentication for the job since it runs internally
K: B
G: ## Headless jobs need service identities
The exam guide asks you to choose user-based or service-based authentication.
## Setup
- Service client with minimal scope.
- Server-side credentials; rotation; monitoring.
Example: the job runs at 02:00 regardless of who is logged in.
W: A dedicated service client: the job runs reliably without depending on an employee's session or rights.
X: A=Employee's token: tied to one person and their permissions; breaks when they leave.
C=Overnight login: breaks whenever the session expires and leaves a logged-in session unattended all night.
D=No authentication: platform calls require authentication, and running internally does not change that.
T: Use dedicated, least-privilege service clients for headless jobs.
V: OSDK

@ PLTR-APD D5 T5.3 applied troubleshooting
S: An external reporting app shows totals that differ from Workshop for the same filters. The app fetches objects page by page and sums them, while Workshop uses an aggregation. What is the likely cause and fix?
A: Workshop is wrong because aggregations are approximate, so the external app's numbers should be trusted instead
B: The app may miss pages or filter differently; use the same server-side aggregation
C: The OSDK rounds every number differently from Workshop, which cannot be fixed
D: The difference is caused by users looking at the two applications at different times of day
K: B
G: ## Consistent computation
The exam guide lists paginating and aggregating among OSDK skills.
## Fix
- Use an aggregation request with the same filters.
- If paging, follow all pages.
Example: the app switches to an aggregation and its totals match Workshop exactly.
W: Use the same server-side aggregation and filters: the totals match and the app avoids pagination errors.
X: A=Workshop wrong: server-side aggregations are not approximate in this sense.
C=Different rounding: a sum over the same values does not differ meaningfully.
D=Time of day: the difference persists for the same moment and filters.
T: Use server-side aggregations with identical filters for consistent totals across applications.
V: OSDK

@ PLTR-APD D5 T5.4 applied use-case
S: An external app depends on an OSDK package generated six months ago. The Ontology team plans changes. How can the app team avoid surprise breakages?
A: Never regenerate the package, so that Ontology changes can never affect the application at all
B: Pin the version, track Ontology changes, and regenerate and test on a branch
C: Regenerate automatically in production every night without testing
D: Copy Ontology definitions by hand into the app whenever they change
K: B
G: ## Managing SDK updates
The exam guide lists stale SDK packages and regeneration among OSDK concerns.
## Practice
- Pin versions.
- Track Ontology changes affecting scoped resources.
- Regenerate and test on a branch before release.
Example: a renamed property is caught in the branch build, not by users.
W: Pinned versions with deliberate, tested regeneration: Ontology changes are absorbed safely instead of breaking production.
X: A=Never regenerate: the app eventually breaks when resources change regardless.
C=Nightly untested regeneration: breakages reach users directly.
D=Hand-copied definitions: error-prone and drift from the real Ontology, losing the safety of generated types.
T: Pin OSDK versions and regenerate deliberately with testing.
V: OSDK

@ PLTR-APD D5 T5.1 applied troubleshooting
S: A developer added a new Action to an external app's code, but calls fail with an error that the Action is not available to the application, although the user can run it in Workshop. What should be done?
A: Ask the user to run the Action in Workshop instead, since external apps cannot invoke Actions
B: Add the Action to the application's scopes and regenerate the OSDK, then retest
C: Give the user administrator rights so that the Action becomes available everywhere
D: Copy the Action's logic into the external app's code
K: B
G: ## Scope intersection again
The exam guide lists scope intersections among OSDK diagnostics. The app can only invoke Actions in its scope.
## Fix
- Add the Action to the scope.
- Regenerate; retest.
Example: after updating the scope, the call succeeds for the same user.
W: The Action is outside the app's scope: adding it and regenerating makes it available to users who are permitted to run it.
X: A=Cannot invoke Actions: external apps invoke Actions routinely.
C=Administrator rights: unrelated to app scope and over-permissioning.
D=Copy logic: duplicates the Action's rules in the app and bypasses its validation, permissions and audit.
T: Add new Actions to an app's scope before calling them through the OSDK.
V: OSDK, Developer Console

@ PLTR-APD D5 T5.2 advanced tradeoff
S: A partner integration needs to read orders for one partner only. Options: a service client scoped to all orders with filtering in the integration code, or access restricted at the data level to that partner's orders. Which is better and why?
A: The service client with code filtering, since filtering in code is simpler and just as secure as any data restriction
B: Data-level restriction so the client can only read that partner's orders, with code filtering as a second layer
C: No restriction at all, since partners are trusted business relationships
D: Give the partner direct access to the full orders dataset
K: B
G: ## Enforce at the data layer
The exam guide asks you to apply least privilege and governance controls rather than rely on application code.
## Reasoning
- Code filtering can be bypassed by bugs or compromise.
- Data-level restriction limits what the credential can ever read.
Example: a bug in the integration's filter cannot expose other partners' orders because the client cannot read them.
W: Restrict at the data level: even a bug or leaked credential cannot reach other partners' data.
X: A=Code filtering only: one bug or leaked credential exposes all orders.
C=No restriction: trust in a partner is not a control; a mistake or compromise would expose every order.
D=Full dataset: gives the partner every other partner's orders, the maximum possible exposure.
T: Restrict external credentials at the data layer, not only in integration code.
V: OSDK, permissions
