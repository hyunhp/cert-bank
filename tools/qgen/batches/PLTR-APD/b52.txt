@ PLTR-APD D1 T1.2 advanced use-case
S: A field-service Ontology relates Technician and Site objects: each technician serves many sites and each site has many technicians. Dispatchers must record a certification level and a start date for every technician-site pairing and edit those values through Actions, and Workshop must show them when a user selects a link between a technician and a site. The ontology owner wants the relationship kept as a first-class Ontology resource rather than as columns duplicated on either object type. Which link design meets all of these requirements?
A: A many-to-many link type backed by a join table dataset that holds the technician and site primary keys, generated from the two object types
B: An Assignment object type with certification and start date, linked many-to-one to both sides, backing an object-backed link type
C: A foreign key property for the site on Technician with a one-to-many link type, storing the certification level and start date beside that key
D: Array properties on Technician for site IDs, certification levels and start dates, kept aligned by position and all edited by one Action
K: B
G: ## Three ways to back a link type
Ontology Manager offers three relationship types when you create a link type:
- **Object type foreign keys**: one-to-one or one-to-many. A property on one type stores the other type's primary key.
- **Join table dataset**: many-to-many. A dataset lists pairs of primary keys and nothing else, and it is required if users must edit the link.
- **Backing object type**: an object-backed link. An intermediary object type sits between the two sides, joined by many-to-one links to each, so the link can carry its own properties.
## Why the backing object matters here
Only the object-backed link lets a relationship carry metadata such as a certification level or a start date. The prerequisites are the two side object types, the backing object type, and the many-to-one link types from each side to the backing type. Object-backed links can be viewed in Object Explorer, Vertex and Workshop, where selecting the link shows the backing object's properties.
Example: an `Assignment` object with `certLevel = 3` and `startDate = 2026-03-01` backs the link between technician T-17 and site S-204, and an Update Assignment Action edits those two values.
W: Object-backed link through Assignment: the intermediary object type holds the pairing's own properties, each technician and each site can have many Assignment objects, and Workshop shows the backing object's values when the link is selected.
X: A=Join table link: a join table supports many-to-many and link edits, but it only stores the two primary keys, so the certification level and start date have nowhere to live.
C=Foreign key link: a foreign key gives one-to-one or one-to-many cardinality, so one technician could not be linked to many sites while each site also has many technicians.
D=Parallel arrays on Technician: there is no link resource at all, the values are duplicated columns on one side, and keeping three arrays aligned by position is fragile.
T: When a relationship needs its own attributes, back the link with an intermediary object type (object-backed link) instead of a join table or foreign key.
V: Ontology Manager, Workshop

@ PLTR-APD D1 T1.1 advanced comparison
S: An asset team models Pump, Compressor and Valve object types, each with type-specific properties plus a shared operating status and last-inspection date. They need one Ontology edit function that flags overdue equipment of any of these types, keeps working without code changes when a Turbine type is added next year, and keeps the three types distinct. The developers prefer Python but can also write TypeScript. Which approach meets these requirements?
A: Define an Equipment interface with the shared properties, implement it on all three types, and write the edit function in TypeScript v2 against it
B: Define an Equipment interface implemented by each type, and write the edit function in Python against that interface to match the team's preferred language
C: Write a Python edit function with three typed parameters, one per object type, and add a fourth parameter for Turbine when that type arrives next year
D: Merge the three types into one Equipment object type with a kind property, and write a Python edit function that edits that single object type
K: A
G: ## Interfaces describe a shared shape
An interface is an abstract Ontology type made of interface properties, link type constraints and action type constraints. Object types implement it, keep their own extra properties, and can implement several interfaces. Workflows written against the interface work with every implementing type, including types added later, without refactoring.
## Language support decides the build
The functions feature support table lists Ontology interfaces support as **Yes** only for TypeScript v2. AIP Logic, TypeScript v1 and Python show **No**, and the interfaces page lists TypeScript v1 and Python functions as not yet supported.
- Interface-based logic in a function therefore means TypeScript v2.
- A team preference for Python cannot override a missing platform capability.
Example: `flagOverdue(equipment: Osdk.Instance<Equipment>[])` in TypeScript v2 accepts Pumps, Valves and, next year, Turbines that implement `Equipment`.
W: TypeScript v2 against an Equipment interface: interfaces keep the three types distinct, new implementing types work without code changes, and TypeScript v2 is the function language that supports interfaces.
X: B=Python against the interface: the modelling is right, but Python functions do not support Ontology interfaces yet, so the function cannot be written this way today.
C=One parameter per type: it works for the three current types, but adding Turbine means changing the function signature and every caller, which the requirement rules out.
D=Merge into one type: one function then covers everything, but the types are no longer distinct and their type-specific properties end up as mostly empty columns.
T: For logic that must work across all types implementing an interface, use an interface plus a TypeScript v2 function.

@ PLTR-APD D1 T1.2 advanced troubleshooting
S: A fleet Ontology has a one-to-one link type between Vehicle and Telematics Unit, backed by a unit_id foreign key on Vehicle that installers set through an Install Unit Action. Dispatch now finds one telematics unit linked to two vehicles, which corrupts location tracking. A double install must be blocked at the moment it is submitted, the foreign key link must stay, and installers must keep using the same Action. What should the developer change?
A: Add a submission criterion to Install Unit that fails when the chosen unit is already linked to a vehicle, as one-to-one is not enforced
B: Keep the link and Action as they are, and add a nightly pipeline check that reports units linked to more than one vehicle to the fleet team
C: Replace the foreign key with a many-to-many join table link, so each install becomes its own row that the fleet team can review and delete
D: Make unit_id the primary key of the Vehicle object type, so that a unit can only ever appear on one vehicle object in the whole Ontology
K: A
G: ## Cardinality is a modelling statement
Foreign key link types support one-to-one and one-to-many cardinality. The link type documentation is explicit that **one-to-one cardinality is an indicator of the intended relationship and is not enforced**: nothing stops two Vehicle rows from carrying the same `unit_id`.
## Enforcing the rule where edits happen
If edits come through an Action, its **submission criteria** can encode the business rule. Criteria can use parameters, the objects they reference and their related objects, and they block the submission with a failure message when the rule is broken.
- Detecting duplicates later does not stop the bad edit.
- A primary key must identify the entity itself and stay stable; a replaceable device ID cannot do that for a vehicle.
Example: Install Unit fails with "Unit TU-0412 is already installed in vehicle V-118" when the chosen unit already has a linked vehicle.
W: Submission criterion on Install Unit: because one-to-one cardinality is not enforced, the Action must reject a unit that already has a vehicle, which blocks double installs at submission.
X: B=Nightly check: it finds duplicates after they exist, so double installs are not blocked when submitted.
C=Many-to-many join table: it removes the foreign key the team must keep and allows even more units per vehicle and vehicles per unit.
D=unit_id as Vehicle primary key: a vehicle's identity would change whenever its unit is replaced, breaking stable identity and the edits attached to it.
T: One-to-one link cardinality is not enforced by the platform; enforce it in the Action that writes the foreign key.

@ PLTR-APD D1 T1.3 advanced use-case
S: Every night a risk team must recompute a risk score for about 300,000 Supplier objects using an existing function-backed Action that accepts a set of suppliers. Applying the Action once to the whole set times out, the recompute must start without anyone pressing a button, and the team wants no new pipeline code to maintain. Which assembly meets these requirements with the LEAST additional build effort?
A: An automation with an Objects added to set condition on all Supplier objects, scheduled nightly, passing the added suppliers to the Action in one run
B: A Workshop button that applies the Action to the full Supplier object set, pressed each evening by an analyst on the night shift before leaving
C: An automation with a scheduled Run on all objects condition on Supplier, passing the suppliers to the Action effect in batches of a set size
D: A new Python transform that computes the scores into a dataset each night, replacing the Action, and scheduled to rebuild the backing dataset
K: C
G: ## Run on all objects
Automate's **Run on all objects** condition periodically runs effects on every object in a chosen object set. It is configured together with a schedule (or automation-dependent evaluation) and respects batch size and parallelization settings, so a large set is split into batches and the effect avoids function or Action timeouts.
## Matching the condition to the job
- Objects added to set fires only for objects that newly enter the set; with no filter it fires only for brand-new objects.
- A Workshop button needs a person.
- A transform is new pipeline code and bypasses the existing Action logic.
Example: a nightly schedule at 01:00 with batch size 500 turns 300,000 suppliers into 600 Action executions of 500 suppliers each.
W: Scheduled Run on all objects with batching: the schedule removes the manual step, batching avoids the timeout, and the existing Action is reused with no new pipeline.
X: A=Objects added to set: it only fires for suppliers newly added to the set, so the existing 300,000 suppliers are never recomputed, and one large run would still time out.
B=Workshop button: it reuses the Action, but it depends on a person pressing it every evening and still applies the Action to the whole set at once.
D=New Python transform: it avoids the timeout, but it is exactly the new pipeline code the team wants to avoid and duplicates the Action's logic.
T: For periodic work over a large object set, use Run on all objects with a schedule and a batch size.

@ PLTR-APD D2 T2.2 advanced tradeoff
S: When a planner applies a Release Order Action, Foundry must call a warehouse system, a transport system and a customer-messaging service, each through its own webhook. The order edit in Foundry must succeed even if any external call fails, the planner should not wait on the external systems, the calls need no particular order, and everything must be configured on the Action itself. How should the webhooks be configured?
A: Configure all three as side effect webhooks, which run after the Ontology edits in no set order and do not hold back the success message
B: Configure the warehouse call as a writeback webhook and the other two as side effects, so the warehouse confirms the release before the edit
C: Call the three systems from a separate automation that watches released orders and applies one webhook-backed Action per system shortly after
D: Configure one side effect webhook whose input function returns three payloads, so that single webhook is called three times after the edit
K: A
G: ## Writeback versus side effect webhooks
A webhook on an Action can run in one of two positions:
- **Writeback**: runs before any other rule. If it fails, no Ontology change is made and the user sees the error. Only one webhook per Action can be a writeback, and its output parameters can feed later rules.
- **Side effect**: runs after the Ontology edits. Several are allowed and they run in no particular order. The user sees success once objects are modified, possibly before the side effects finish, and a failure is not shown to the user.
## Choosing
Use writeback when the external system must accept first. Use side effects for best-effort calls or for writing to several external systems.
Example: Release Order sets `status = Released`, then side effects call the WMS, the TMS and the messaging service in parallel; a messaging outage does not undo the release.
W: Three side effect webhooks: the edit commits first and never depends on the external calls, the planner sees success immediately, order does not matter, and it is all Action configuration.
X: B=Warehouse as writeback: a warehouse failure would then block the order edit, which breaks the rule that the edit succeeds whatever the external calls do.
C=Separate automation: it decouples the calls, but it adds an automation and extra Actions outside the Action, which the team ruled out.
D=One webhook called three times: a list of payloads calls the same webhook repeatedly, so it cannot reach three different systems with their own webhooks.
T: Use side effect webhooks for best-effort calls to several systems; reserve the single writeback webhook for a system that must accept first.
V: Actions, Data Connection

@ PLTR-APD D2 T2.2 advanced use-case
S: A Create Purchase Request Action must register the request in an ERP that returns a requisition number. The new Foundry object must store that number in the same submission, no Purchase Request may be created in Foundry if the ERP rejects the call, and the requester must see the ERP's error when that happens. How should the developer configure the Action?
A: Configure the ERP call as a side effect webhook and map its output parameter into the Create object rule's requisition number property
B: Configure the ERP call as a side effect webhook and add an automation that copies the returned number onto the object a few minutes later
C: Configure the ERP call as a writeback webhook and map its output parameter into the Create object rule's requisition number property
D: Configure the ERP call as a writeback webhook and leave the number empty, asking requesters to enter it through a second Action later

G: ## Writeback webhooks give some transactionality
A writeback webhook runs before every other rule of the Action. If the external request fails, nothing is applied to the Ontology and the user sees an error describing the failure. (The reverse can still happen: the external call succeeds and the Ontology edit fails.)
## Output parameters
Only a writeback webhook's output parameters can be used in subsequent rules, because it has finished before those rules run. A side effect webhook runs after the edits, so its response cannot fill a property of the object being created.
Example: the ERP returns `REQ-55120`; the Create object rule maps the writeback response field `requisitionNumber` into the new Purchase Request's property in the same submission.

B=Side effect plus automation: the number arrives later rather than in the same submission, and the object exists even when the ERP rejects the request.
D=Writeback without the number: rejection handling is right, but the number is not stored in the same submission and depends on a second manual step.
T: When an external system must accept first and return data for the edit, use a writeback webhook and map its output parameters.

@ PLTR-APD D2 T2.3 advanced tradeoff
S: A Claims object type is backed by a dataset, and adjusters update claim status through an Update Claim Action. An integration team asks the developer to reopen the object type to Object Explorer edits, Foundry Forms and API calls for convenience. Security requires that adjusters gain no permission that lets them read more claim data than they already see through the Ontology, and the Action must keep working for them. Which configuration should the developer keep?
A: Allow edits through Actions, Object Explorer, Forms and APIs, and give Edit on the writeback dataset only to the integration team's service user
B: Allow edits through Actions, Object Explorer, Forms and APIs, and grant adjusters Edit on the writeback dataset so their submissions succeed
C: Keep edits allowed only through Actions and also grant adjusters the Editor role on the project that holds the backing dataset, to be safe
D: Keep edits allowed only through Actions, so adjusters submitting Update Claim need no Edit permission on the writeback dataset at all
K: D
G: ## Two writeback settings
Object types either allow edits **only via Actions** (the default for new object types) or allow edits via Actions, Foundry Forms, direct Object Explorer edits and API calls.
- Actions only: the submitter needs read access to the objects being edited; no dataset Edit permission is required.
- Reopened: for dataset-backed types, every Action submitter needs **Edit on the writeback dataset**, and a user with Edit there can view all of its data.
The docs therefore discourage reopening, since granting Edit just to make edits possible can expose more data than the workflow needs.
## Applying it
The decision is about the adjusters, not only the integration team: once the type is reopened, their Update Claim submissions also need writeback dataset Edit.
Example: an adjuster who sees 40 claims through a policy would, with dataset Edit, be able to read all 90,000 rows of the writeback dataset.
W: Actions-only edits: adjusters keep submitting Update Claim with read access to the objects, and no dataset permission widens what they can read.
X: A=Reopen with service-user Edit: once reopened, adjusters' Action submissions also need Edit on the writeback dataset, so without it their Update Claim submissions fail.
B=Reopen and grant adjusters Edit: submissions work, but dataset Edit lets adjusters read the whole writeback dataset, which security forbids.
C=Actions only plus project Editor: the Action already works without it, and a project Editor role gives adjusters broader data access than they need.
T: Keep object types editable only via Actions so submitters do not need Edit on the writeback dataset.

S: An Approve Payment Action has a submission criterion "current user's group IDs do not include External Contractors" so that contractors cannot approve payments. A security review flags that a request made with a scoped token, which carries only part of a user's permissions, could pass this check. The team must keep contractors blocked, keep employees able to approve, and avoid maintaining lists of individual users. What should the developer change?
A: Keep the negative group check and add a second NOT condition on the contractors' Organization, so a missing group attribute is still caught
B: Replace the negative check with a positive criterion that requires membership in a Payment Approvers group which excludes contractors

Submission criteria decide whether an Action can be submitted. The Current User template can check user IDs, group memberships (direct or inherited) and other user attributes. All criteria must pass, independently of who can edit the action type.

The docs warn against `NOT` conditions on group, marking or organization membership. Scoped tokens carry only a subset of a user's permissions; such a token may lack the very attribute the `NOT` condition checks, so the check passes and grants more access than intended.

T: Write membership-based submission criteria as positive checks; NOT conditions on groups, markings or organizations can be bypassed by scoped tokens.

@ PLTR-APD D2 T2.4 advanced troubleshooting
S: Planners edit delay minutes for flights in a Workshop table using an action-backed inline edit. The Delay Flight Action has two submission criteria: a flight may be delayed at most 20 minutes, and the total delay at an airport may not exceed 50 minutes. After a busy shift the airport's total reached 85 minutes, although every cell edit passed validation. The 50-minute cap must be enforced reliably. What explains this and what should change?
A: The Action's rules ran in a non-deterministic order, so the cap was checked before each edit; reorder the rules so the airport total check runs last
B: Submission criteria are skipped for inline edits in tables, so neither rule ran; move both rules into the table widget's column validation settings
C: The total criterion compared against an aggregation refreshed nightly, so it used stale sums; enable auto-refresh on the table's object set
D: Inline edits are checked against unedited values and submitted in bulk, so the total rule cannot hold; apply the Action per flight instead
K: D
G: ## How inline edits are validated
A single Action is validated and submitted on its own. Action-backed inline edits in a table are validated per edited object but **submitted in bulk**.
- Parameter and global submission criteria run for each edit, before any edit is applied.
- Criteria that depend on shared or linked objects, or on aggregates over the column, compare the new value with the **unedited** values of the other rows.
So a cap on a total across rows cannot hold: each cell passes against the old total, and all edits then land together.
## What to do
Actions whose criteria rely on aggregates, or that read data another edit may write, are not suitable for table editing. Apply them one object at a time (for example from a form), where each submission sees the result of the previous one.
Example: three cells of 20, 20 and 20 minutes each pass "total <= 50" against an old total of 25, then commit together for 85.
W: Bulk submission against unedited values: each cell passes the cap against the old total, so the aggregate rule cannot work in a table; per-flight submission makes each check see earlier edits.
X: A=Rule order: rule order affects how edits combine, not when submission criteria are evaluated, and the criteria already ran before any edit was applied.
B=Criteria skipped: inline edits do evaluate parameter and global criteria for each edited object; the problem is bulk submission, not skipped criteria.
C=Nightly aggregation: the criterion read the current unedited values, not a nightly aggregate, and auto-refresh does not change how inline edits are validated.
T: Do not use inline table edits for Actions whose submission criteria depend on totals across objects.

@ PLTR-APD D3 T3.2 advanced troubleshooting
