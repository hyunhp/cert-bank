@ PLTR-APD D3 T3.2 applied troubleshooting
S: A function that summarizes a customer's open orders works in testing but times out in production for large customers. The code traverses Customer → Orders → Line Items and loads every linked object before filtering by status in memory. What should change?
A: Increase the function's timeout so that the traversal of every linked object has enough time to complete for large customers
B: Filter and aggregate server-side (open orders only), page results, and bound the traversal
C: Cache the entire Ontology in the function's memory at startup so that later traversals are faster for every customer
D: Move the logic into a Workshop variable so that the browser performs the traversal instead of the function
K: B
G: ## Bounded, server-side queries
The exam guide lists querying, filtering, ordering, paginating and aggregating, and warns about unsafe or unbounded link traversal.
## Fix
- Filter the linked object set to open orders on the server.
- Aggregate counts and sums server-side instead of loading line items.
- Page when a list is genuinely needed; cap traversal depth.
Example: a customer with 40,000 orders returns a summary in 300 ms instead of timing out.
W: Server-side filtering, aggregation and bounded traversal: the function scales with the customer instead of loading everything into memory.
X: A=Longer timeout: the unbounded load still grows with customer size and will eventually exceed any timeout or memory limit.
C=Cache the whole Ontology: impossible at scale, stale immediately, and it ignores permissions per user.
D=Browser traversal: moves the same unbounded work to a slower, less capable place and still times out.
T: Avoid unbounded link traversal; filter, aggregate and page on the server.

@ PLTR-APD D3 T3.3 applied use-case
S: A function used by three Workshop modules and one Action needs a change to its return type. The developer wants to avoid breaking the existing consumers. What is the right approach?
A: Change the return type in place on the published version, since consumers always update automatically when a function changes
B: Publish a new function version with the new return type, migrate consumers deliberately, and keep the old version until all have moved
C: Delete the function and recreate it under the same name with the new return type so that consumers pick it up
D: Ask every consumer owner to stop using the function permanently and write their own logic instead
K: B
G: ## Versioning functions
The exam guide lists versioning and return types among function concepts. A return type change is breaking for any consumer that reads the result.
## Approach
- Publish a new version.
- Consumers move one by one; test each on a branch.
- Retire the old version after all have migrated.
Example: two modules move in week one, the Action and the third module in week two; the old version is then removed.
W: A new version with deliberate migration: consumers keep working on the old contract until each is updated and verified.
X: A=Change in place: consumers expecting the old type break at once with no fallback version available.
C=Delete and recreate: every consumer loses its reference and breaks, with no migration path.
D=Stop using it: discards shared logic and creates divergent copies across teams.
T: Publish breaking function changes as new versions and migrate consumers deliberately.

@ PLTR-APD D3 T3.1 applied comparison
S: Which requirement most clearly justifies writing a function in Python v2 rather than TypeScript v2?
A: The function only sets a status property on an object, which any language can do equally well
B: It needs a Python statistics library, and its maintainers are data scientists who work in Python
C: The function must be deterministic, since only Python functions can return the same result for the same input
D: The function must be called from Workshop, since Workshop can only call Python functions
K: B
G: ## Choosing Python v2
The exam guide asks you to choose a paradigm by runtime capabilities and maintainer audience. A required library and a Python-skilled team are concrete reasons.
- Library needs: available in the Python runtime.
- Maintainers: data scientists comfortable in Python.
- Determinism and Workshop integration are not language-specific.
Example: a forecast function uses a statistics library and is maintained by the analytics team.
W: A library requirement plus a Python-fluent team: the concrete runtime and audience reasons the guide names for choosing Python v2.
X: A=Status edit: no capability or audience reason favours one language; declarative Actions might suit it better still.
C=Only Python is deterministic: determinism depends on the logic, not on the language.
D=Workshop only calls Python: Workshop calls functions written in either language.
T: Choose function languages by required runtime capabilities and who will maintain the code.

@ PLTR-APD D3 T3.4 applied troubleshooting
S: A function-backed Action fails with an error indicating an invalid edit result. The function's code compiles and its unit test passes. What should the developer investigate?
A: Whether the Action's button label is too long for the Workshop form that displays it
B: Whether the edits violate Ontology constraints for the real objects (types, required values, links)
C: Whether the user's browser has enough memory to process the returned edits
D: Whether the function should be rewritten in a different language, since edit errors are specific to the language that produced them
K: B
G: ## Invalid edit results
The exam guide lists diagnosing invalid edit results among function failure modes. A unit test with mocks can pass while real objects violate constraints.
## Checks
- Property types and required values for the target object type.
- Links to objects that exist and are permitted.
- Edits on objects the execution identity may edit.
- Reproduce with the failing object and inputs.
Example: the function set `due_date` to a string in one branch of the code; the object type expects a date.
W: Check the edits against the object type's constraints with the real failing inputs: invalid edits come from values or links the Ontology rejects.
X: A=Button label: labels do not affect whether the returned edits are valid at execution.
C=Browser memory: edits are applied on the server; the browser does not process them.
D=Different language: the edit is invalid regardless of the language that produced it.
T: Diagnose invalid edit results by checking returned edits against object type constraints with real inputs.

@ PLTR-APD D3 T3.2 applied use-case
S: A function must return the top five suppliers by on-time delivery rate in the last 90 days from millions of Delivery objects. What implementation is appropriate?
A: Load all Delivery objects into the function's memory, compute rates per supplier in a loop, and sort the results in code
B: Use server-side filtering to the last 90 days and aggregations grouped by supplier, then order and take the top five
C: Ask the user to export the deliveries to a spreadsheet and compute the ranking there each week
D: Return all Delivery objects to Workshop and let a table widget sort them by supplier on the screen
K: B
G: ## Aggregate where the data lives
The exam guide asks you to query, filter and aggregate safely. Ranking across millions of objects is an aggregation problem.
## Implementation
- Filter: delivery date within 90 days.
- Aggregate: count on-time and total per supplier.
- Compute rate, order, limit to five.
Example: the function returns five suppliers with rates in under a second.
W: Server-side filter and aggregation: the ranking is computed efficiently without loading millions of objects.
X: A=Load everything: millions of objects exceed function limits and time out.
C=Spreadsheet: manual, weekly and outside the platform's governance.
D=Return everything to Workshop: moves millions of objects to the browser, which cannot handle them.
T: Use server-side filters and aggregations for rankings over large object sets.

@ PLTR-APD D3 T3.3 applied use-case
S: An external TypeScript application calls an Ontology function through the OSDK. After the function's signature changed, the application fails to compile. What should the developer do?
A: Edit the generated SDK files by hand so that they match the new function signature without regenerating anything
B: Regenerate the OSDK package for the new function version and update the application's calls to match
C: Downgrade the application's TypeScript compiler to an older version that ignores type errors
D: Remove all type checking from the application so that the mismatch no longer prevents compilation
K: B
G: ## Generated bindings follow the function
The exam guide lists generated SDK bindings among function concepts and stale SDK packages among OSDK failure modes.
## Steps
- Regenerate the SDK for the new function version.
- Update calls to the new signature; run the application's tests.
- Pin versions so future changes are deliberate.
Example: the regenerated package exposes `getRisk(customerId, asOfDate)`; the app adds the new parameter.
W: Regenerate the bindings and update the calls: type checking then protects the application against signature drift.
X: A=Hand-edit generated files: overwritten at the next generation and easy to get wrong.
C=Older compiler: hides a real mismatch that will fail at runtime instead.
D=Remove type checking: trades a compile error for production failures.
T: When function signatures change, regenerate the OSDK and update calls rather than suppressing type errors.

@ PLTR-APD D3 T3.1 applied tradeoff
S: A team must classify free-text maintenance notes into one of ten fault categories and then apply a deterministic routing rule by category. Which design is appropriate?
A: An AIP Logic function that both classifies the note and decides the route freely, with no structured output or rules
B: AIP Logic for the classification with a typed enum output and validation, then deterministic code that routes by category
C: A TypeScript function that uses keyword matching to classify notes and ignores any note without an exact keyword
D: Manual classification by a supervisor for every note before routing
K: B
G: ## Combine AI and deterministic logic
The exam guide asks when AI adds value over deterministic logic. Interpreting free text needs AI; routing by category is a rule.
## Design
- AIP Logic: classify into an enum of ten categories; validate; low confidence to review.
- Code: route by category deterministically.
Example: "pump vibrates at startup" → mechanical → maintenance team A, every time.
W: AI for the interpretation and code for the rule: each part uses the mechanism suited to it, and the output is constrained and testable.
X: A=Free-form AI decision: routing becomes nondeterministic and unvalidated.
C=Keyword matching: misses paraphrases and drops notes without exact keywords.
D=Manual classification: slow and the workload the feature was meant to remove.
T: Use AI for interpretation with typed outputs and deterministic code for the rules that follow.
V: AIP Logic, Functions

@ PLTR-APD D3 T3.4 advanced troubleshooting
S: A function returns correct results for most users but an empty list for some users who should see data. The function queries objects using the calling user's permissions. What should be checked?
A: Whether the function has an intermittent bug that only appears on certain days of the week and only for certain users
B: Whether those users lack access to the objects (markings, restricted views, roles), since queries run as the user
C: Whether the users' browsers are blocking the function's results with an extension
D: Whether the function should run as an administrator so that all users see every object
K: B
G: ## User-scoped results
The exam guide asks you to separate user-scoped and project-scoped execution. A function that queries as the user returns only that user's visible objects.
## Checks
- Access for an affected user to the object type and its backing data.
- Markings or restricted view policies that exclude them.
- Decide whether the empty result is correct or access should change.
Example: the users lack the region attribute required by the restricted view; HR updates their profiles.
W: User-scoped queries reflect each user's access: an empty list for some users points to their permissions, not to a code defect.
X: A=Day-of-week bug: the difference follows the users, not the date.
C=Browser extension: results are filtered on the server by permissions.
D=Run as administrator: returns objects the users are not permitted to see, solving an access question by bypassing access control.
T: When user-scoped functions return less for some users, check those users' access before changing code.
V: Functions, permissions
