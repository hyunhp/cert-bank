# PLTR-APD batch 41: Domain 8 round 5 (Application Security, Governance, and Operations), 8 questions

@ PLTR-APD D8 T8.1 applied use-case
S: A procurement application must let anyone in the company view approved suppliers, but only the procurement team may see supplier pricing agreements. Both live in the Ontology. How should access be designed?
A: Show pricing agreements in a hidden tab of the Workshop module and trust that non-procurement users will not find the tab
B: A separate pricing-agreement type restricted to procurement, with suppliers broadly visible
C: Put both suppliers and pricing agreements in a single object type visible to everyone, with pricing in a property named "internal"
D: Email pricing agreements to the procurement team each month instead of storing them in the Ontology
K: B
G: ## Separate sensitive data at the data layer
The exam guide lists governance controls and asks you to separate application access from data access.
## Design
- Supplier object type: broadly readable.
- PricingAgreement object type: restricted to procurement.
- Link between them; non-procurement users see no agreements through the link.
Example: an engineer sees supplier contact details; a procurement analyst also sees the pricing agreement.
W: A separately permissioned object type for sensitive data: broad visibility where intended and protection everywhere else, enforced by data permissions.
X: A=Hidden tab: the data remains readable through other tools and modules; hiding a tab is not access control.
C=Property named "internal": a name does not restrict who can read it.
D=Email: ungoverned copies outside the platform and no single source of truth.
T: Separate sensitive data into separately permissioned object types or properties.
V: permissions, Ontology Manager

@ PLTR-APD D8 T8.2 applied troubleshooting
S: A user reports that a newly shared application shows "no access" when they try to open it, while a colleague in the same department can open it. The application's data is not restricted. What should be checked first?
A: Whether the user's computer has the right fonts installed to render the application
B: Whether the user is in the group the app was shared with, compared with the colleague
C: Whether the data needs to be copied into a new project for this user
D: Whether the application needs to be rebuilt for each user who opens it
K: B
G: ## Resource access first
The exam guide asks you to separate application or resource access from data access.
## Checks
- Groups the application is shared with.
- The user's memberships versus the colleague's.
Example: the colleague is in "Ops-Managers", the user only in "Ops"; the app was shared with the former.
W: Opening the app is a resource-access question: compare group memberships against the app's sharing.
X: A=Fonts: missing fonts affect how text looks, not whether the platform grants access to open the app.
C=Copy data: the data is unrestricted; the user cannot open the application resource itself.
D=Rebuild per user: applications are shared resources; access is granted through sharing, not rebuilt per person.
T: Diagnose "cannot open" errors through resource sharing and group membership.
V: permissions

@ PLTR-APD D8 T8.3 applied use-case
S: A Function that generates monthly reports needs to read data from several projects that individual users cannot all access. Reports are written to a restricted reports project. How should execution be configured?
A: Run as each user who opens the report, so that each report contains whatever data that user happens to see
B: A project-scoped service identity reading the sources and writing only to reports
C: A personal account of the report's author, since they have access to everything
D: An administrator account to avoid any permission errors
K: B
G: ## Controlled service identities
The exam guide asks you to understand project-scoped execution and service identities.
## Configuration
- Service identity: read on specific sources, write on reports project.
- Report visibility controlled by the reports project's permissions.
Example: the monthly report includes cross-project figures but is readable only by finance leadership.
W: A least-privilege service identity: the Function can compile cross-project reports while reads and writes stay limited and auditable.
X: A=Run as each user: reports would differ by viewer and be incomplete.
C=Personal account: breaks when the author leaves and blurs accountability.
D=Administrator account: grants far more access than the reports need and widens the impact of any bug.
T: Use least-privilege service identities for cross-project reporting.
V: permissions, Functions

@ PLTR-APD D8 T8.4 applied use-case
S: An operations lead wants to know each morning whether the application's automations, Actions and AI features are healthy. What should be provided?
A: A daily email listing every single log line produced by the application in the last 24 hours
B: A health summary of Actions, automations, AI and indexing, with alerts on breaches
C: A message from a developer saying that everything looks fine
D: Nothing; problems will become obvious when users complain
K: B
G: ## Daily health summaries
The exam guide asks you to monitor application, Ontology, automation, indexing and AIP health.
## Summary
- Key metrics per component.
- Thresholds and alerts.
- Links to details and runbooks.
Example: the morning summary shows one automation with missed runs, already alerted at 03:10.
W: A concise health summary with alerts: the lead sees the state of every component and knows what needs attention.
X: A=Every log line: thousands of lines a day are unreadable and bury the few signals that matter.
C=Developer message: a subjective impression that cannot be verified and may miss overnight failures.
D=Wait for complaints: problems are found only after users are affected.
T: Provide component-level health summaries with alerts to operations leads.
V: monitoring

@ PLTR-APD D8 T8.1 applied comparison
S: Which control prevents a developer from merging an untested change to production Actions without another person's approval?
A: A team rule written in the wiki stating that all changes to production Actions should be reviewed first
B: Branch protection requiring an approving review before merge
C: A notification sent to the team after each merge
D: A monthly report of all merges
K: B
G: ## Enforced review
The exam guide lists branch protection among application governance controls.
- Branch protection blocks merges without approval.
- Rules, notifications and reports inform but do not prevent.
Example: an attempt to merge without approval is blocked by the platform.
W: Branch protection with required approval enforces review before production changes, which the other options only describe or report after the fact.
X: A=Wiki rule: a documented expectation that nothing enforces; an urgent merge can skip it.
C=Post-merge notification: arrives after the untested change is already in production.
D=Monthly report: shows the unreviewed merge weeks after users have been affected.
T: Use branch protection to enforce approval before production merges.
V: branches

@ PLTR-APD D8 T8.2 applied use-case
S: A dashboard module is shared with all managers. Some managers should see financial figures, others should not. The developer wants one module. How can this be done?
A: Create a separate copy of the dashboard module for each manager with the widgets they should not see removed
B: One module, with data permissions deciding who sees the financial values
C: Show financial figures to everyone and ask some managers not to look
D: Remove financial figures from the module entirely
K: B
G: ## One module, data-driven visibility
The exam guide asks you to separate application access from data access.
## Design
- Module shared with all managers.
- Financial data restricted by permissions.
- Empty states or conditional visibility explain missing figures.
Example: a regional manager sees operational charts; a finance manager also sees revenue figures.
W: One shared module governed by data permissions: each manager sees exactly what they may, without maintaining copies.
X: A=Copy per manager: unmaintainable and still not a data control.
C=Ask not to look: financial figures remain visible to everyone; a request enforces nothing.
D=Remove figures: managers who legitimately need financial data lose it to protect it from others.
T: Share one module and let data permissions determine what each user sees.
V: permissions, Workshop

@ PLTR-APD D8 T8.3 applied troubleshooting
S: After an automation was moved to run under a new service identity, it started failing with permission errors on writes. Reads work. What is the most likely cause and fix?
A: The new service identity is broken and must be deleted and then recreated under a different name before it will work
B: The new identity lacks write permission on the targets; grant just that
C: Automations cannot write data under service identities
D: Give the identity administrator rights so that permission errors never happen
K: B
G: ## Specific missing permissions
The exam guide asks you to separate user permissions from execution identity and to grant exact permissions.
## Fix
- Compare old and new identities' permissions.
- Grant write on the specific object types.
- Test.
Example: the new identity lacked edit on Task objects; granting it resolves the failures.
W: The new identity lacks the write permission the automation needs: granting exactly that restores it without over-permissioning.
X: A=Recreate the identity: a new identity would lack the same write permission, so the failures continue.
C=Cannot write: automations write under service identities routinely.
D=Administrator rights: grants everything to fix one missing permission, the opposite of least privilege.
T: When moving automations to new identities, grant exactly the permissions they need.
V: Automate, permissions

@ PLTR-APD D8 T8.4 advanced use-case
S: A team wants to detect quickly when an application's Ontology data becomes stale or its indexing falls behind, before users notice. Which approach fits?
A: Ask a team member to open the application every morning and look for anything that seems old
B: Monitor freshness and indexing lag against schedules, with alerts and runbooks
C: Rebuild every dataset hourly regardless of need so that data is never stale
D: Add a banner telling users that data might be stale
K: B
G: ## Freshness monitoring
The exam guide asks you to monitor Ontology and indexing health.
## Monitoring
- Expected update schedule per object type.
- Freshness and indexing lag metrics.
- Alerts and runbooks.
Example: an indexing stall at 04:00 alerts the on-call engineer, who resolves it before 07:00.
W: Freshness and indexing monitoring with alerts: staleness is caught early and handled with known steps.
X: A=Manual morning checks: depend on one person noticing subtle staleness every day, which they often will not.
C=Hourly rebuilds: wasteful and does not detect indexing problems.
D=Banner: a permanent warning informs users but neither detects staleness nor gets it fixed.
T: Monitor data freshness and indexing lag with alerts for key object types.
V: monitoring
