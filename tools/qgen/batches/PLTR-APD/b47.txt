@ PLTR-APD D6 T6.1 applied use-case
S: When a high-value Order (over 50,000) is created, a credit check must run immediately and the sales manager must be notified of the result. Smaller orders need no check. Which configuration fits?
A: A nightly schedule that runs credit checks on every order created that day, large or small, and emails all results to sales
B: An object-creation trigger with a condition on value over 50,000, running the credit check and notifying the sales manager
C: A trigger on any change to any order that runs a credit check every time a field is edited
D: Ask sales staff to run credit checks manually on large orders when they remember
K: B
G: ## Conditioned event triggers
The exam guide asks you to select triggers, conditions and effects that fit the requirement.
## Configuration
- Trigger: Order created.
- Condition: value > 50,000.
- Effects: credit check function; notification with result; idempotent.
Example: a 72,000 order triggers a check within a minute; a 3,000 order triggers nothing.
W: A creation trigger with a value condition: checks run immediately for exactly the orders that need them.
X: A=Nightly for all: delays large-order checks by up to a day and wastes checks on small orders.
C=Any change: reruns checks on every edit and floods the manager with notifications.
D=Manual: depends on memory and delays decisions on large orders.
T: Use conditioned creation triggers for immediate checks on qualifying objects.

@ PLTR-APD D6 T6.2 applied troubleshooting
S: An automation's notifications to managers stopped after the team moved its alerts to a new channel. The automation still runs. What should be checked?
A: Whether the automation should be deleted and recreated so that it picks up the new channel automatically
B: The notification destination: update it to the new channel and send a test
C: Whether managers have muted all notifications from the platform
D: Whether automations can only send notifications to the original channel they were created with
K: B
G: ## Notification routing
The exam guide lists notifications and service ownership among automation configuration.
## Fix
- Update the destination.
- Test notification.
- Document routing with ownership.
Example: the next run's notification arrives in the new channel.
W: Update and test the notification destination: the automation runs correctly; only its routing was out of date.
X: A=Delete and recreate: unnecessary; the destination is a configurable setting.
C=Managers muted: the notifications stopped exactly when the channel moved, which points to the destination setting.
D=Only original channel: notification destinations are configurable and can be pointed at the new channel.
T: Update and test notification routing when teams change channels.

@ PLTR-APD D6 T6.3 applied use-case
S: An automation updates a Customer's segment when their spending changes. Another automation sends a welcome-to-segment email when the segment changes. Occasionally a customer receives emails for a segment they were in only briefly. What design helps?
A: Disable the email automation entirely so that customers never receive segment emails
B: Debounce segment changes and re-check the current segment before sending
C: Send segment emails only once a year
D: Ask the marketing team to apologize to affected customers
K: B
G: ## Stabilizing chained automations
The exam guide asks you to account for live changes and races between automations.
## Design
- Wait for the segment to remain stable (for example one day).
- Re-check before sending; idempotent emails per segment change.
Example: a customer who briefly crosses a threshold and drops back receives no email.
W: Debounce and re-check before sending: only stable segment changes trigger emails.
X: A=Disable emails: removes a useful customer communication instead of fixing the timing that causes bad emails.
C=Yearly emails: welcome messages a year after a segment change are too late to be useful.
D=Apologize: treats the symptom each time while the automation keeps sending premature emails.
T: Debounce and re-check state in chained automations that trigger customer communications.
V: Automate

@ PLTR-APD D6 T6.4 applied troubleshooting
S: An automation runs and its effect reports success, but the expected object is not created. The effect calls an Action. What should be investigated?
A: Whether automations sometimes pretend to succeed for no reason, which cannot be investigated further
B: The Action's execution record for that run: parameters and which object it changed
C: Whether the automation should be disabled until next quarter
D: Whether the object type needs to be recreated
K: B
G: ## Follow the evidence
The exam guide lists diagnosing effect failures among automation skills.
## Steps
- Open the Action's execution record for the run.
- Compare parameters with expectations; inspect created objects.
Example: the automation passed a stale variable, creating the task on a different project.
W: Inspect the Action execution linked to the run: it shows what was actually done and why the expected object is missing.
X: A=Unexplainable: the Action's execution record shows exactly which parameters were used and what changed.
C=Disable: stops the automation's useful work without finding out what went wrong.
D=Recreate the object type: the object type is fine; the evidence points to what the Action was given.
T: Trace automation effects through the Action execution records they produce.

@ PLTR-APD D6 T6.1 applied comparison
S: A team is deciding which of several new notification requirements should use a scheduled automation rather than an event trigger. Which requirement is best met by a scheduled automation?
A: Send a reminder the moment a task is assigned
B: Generate a weekly summary of overdue tasks for each team every Monday
C: Notify the security team immediately whenever a user account is locked after repeated failed sign-in attempts
D: Create a follow-up as soon as an incident is closed
K: B
G: ## Schedules for periodic work
The exam guide asks you to select triggers by requirement. Summaries delivered on a calendar are driven by time, while reminders, alerts and follow-ups react to specific changes.
- Weekly summaries: scheduled.
- Immediate reactions to assignments, locks and closures: events.
Example: each team receives one summary every Monday morning.
W: A weekly summary is driven by the calendar rather than by any single change, so a scheduled automation that runs every Monday is the natural fit.
X: A=Reminder on assignment: an immediate reaction to an event, so an event trigger fits.
C=Security alert on lock: must fire immediately when the account state changes.
D=Follow-up on closure: an event on the incident's status change.
T: Use schedules for periodic summaries and events for immediate reactions.
V: Automate

@ PLTR-APD D6 T6.2 applied use-case
S: An automation calls an external API that enforces a strict rate limit. During busy periods the automation receives many rate-limit errors. What configuration helps most?
A: Disable retries so that rate-limit errors are logged once and ignored
B: Limit concurrency, back off on rate-limit errors, and batch where possible
C: Run the automation more often so that each run has fewer items
D: Ignore rate limits since the external API will eventually allow requests
K: B
G: ## Respecting rate limits
The exam guide lists retries, backoff and execution modes among automation configuration.
## Configuration
- Concurrency limit below the API's rate.
- Backoff on rate-limit responses.
- Batching where supported.
Example: errors drop to near zero and all items are processed within the hour.
W: Concurrency limits, backoff and batching: the automation works within the API's limits.
X: A=No retries: every item that hits the limit during busy periods fails permanently and must be redone.
C=Run more often: increases the number of calls per hour, which makes rate-limit errors more frequent.
D=Ignore limits: errors continue, and repeated violations can lead the provider to block the client.
T: Manage automation calls to rate-limited APIs with concurrency limits, backoff and batching.
V: Automate

@ PLTR-APD D6 T6.3 applied troubleshooting
S: An automation sometimes processes the same object twice within seconds because two updates arrived close together, leading to two identical notifications. What should be changed?
A: Accept duplicates, since customers rarely mind receiving two copies of a notification
B: Make the notification idempotent per change, keyed on object and new status
C: Turn off the automation during busy hours
D: Increase the automation's run time limit
K: B
G: ## Idempotent notifications
The exam guide states that automations must account for at-least-once execution and duplicate effects. Two updates seconds apart can each satisfy the trigger, so the effect itself must recognize work it has already done.
## Fix
- Notification key: object id + new status.
- Skip if already sent.
Example: two near-simultaneous updates produce one notification.
W: Idempotent notifications keyed on the change: duplicate processing no longer produces duplicate messages.
X: A=Accept duplicates: repeated messages confuse customers and erode trust in the notifications.
C=Off during busy hours: legitimate notifications are lost exactly when the most changes happen.
D=Longer run time: has nothing to do with two near-simultaneous triggers each sending a message.
T: Key automation notifications on the change so duplicates are skipped.
V: Automate

@ PLTR-APD D6 T6.4 advanced use-case
S: A team operates 40 automations across several projects. They want a reliable way to know which ones are failing, which are muted, and who owns each. What should they set up?
A: Rely on each automation's owner to remember to check its run history from time to time
B: An owned inventory with monitoring of failures, mutes and missed runs, and reviews
C: Disable all automations that have ever failed
D: Merge all 40 automations into one large automation
K: B
G: ## Operating automations at scale
The exam guide asks you to test and diagnose automations and assign service ownership.
## Setup
- Inventory: purpose, owner, project, schedule.
- Monitoring: failures, mute state, missed runs.
- Alerts to owners; quarterly review.
Example: a muted automation is spotted in the weekly report and re-enabled after its maintenance window ended.
W: An owned inventory with monitoring and reviews: failures and forgotten mutes are found quickly by the people responsible.
X: A=Rely on memory: owners check rarely, so failures and forgotten mutes go unnoticed for weeks.
C=Disable on any failure: removes useful automations because of transient or already-fixed problems.
D=One large automation: much harder to own, test and diagnose than separate, well-scoped ones.
T: Maintain an owned inventory of automations with monitoring and regular reviews.
V: Automate
