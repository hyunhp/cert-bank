@ PLTR-APD D3 T3.2 applied use-case
S: A function must list the ten most recent comments on a case for display in a side panel. Cases can have thousands of comments. What implementation is appropriate?
A: Load every comment linked to the case into memory, sort them by date in the function, and return the first ten from the sorted list
B: Query the case's linked comments with server-side ordering by date descending and a limit of ten
C: Return all comments to the Workshop panel and let the panel show only the first ten rows on screen
D: Ask users to scroll through the full comment history in a separate module to find the latest ones themselves
K: B
G: ## Ordering and limits on the server
The exam guide lists querying, ordering and paginating among function skills.
## Implementation
- Linked object set: comments of the case.
- Order by created date descending; limit 10.
Example: a case with 6,000 comments returns its latest ten in milliseconds.
W: Server-side ordering with a limit: only the ten needed comments are retrieved, regardless of how long the case's history grows.
X: A=Load and sort in memory: cost grows with every comment and the function slows or times out for long-running cases.
C=Return everything to the panel: transfers thousands of comments to the browser to display ten of them.
D=Scroll elsewhere: pushes the work onto users and defeats the purpose of the side panel.
T: Use server-side ordering and limits for "latest N" queries in functions.

@ PLTR-APD D3 T3.3 applied troubleshooting
S: After publishing a new version of a function, a Workshop module still behaves as if the old logic is running. Another module shows the new behaviour. What is the likely cause?
A: The platform caches function results forever, so the old module will never see the new version
B: The first module is pinned to the old function version; update its reference to the new version deliberately
C: The new version was not published correctly for one module only, which requires deleting the function
D: Workshop modules can only use the first version of any function ever published
K: B
G: ## Version references
The exam guide lists versioning among function concepts. Consumers reference specific versions; publishing a new one does not change pinned consumers.
## Fix
- Inspect the module's function reference.
- Upgrade to the new version after testing.
Example: the dispatch module referenced v4; upgrading to v5 applies the new routing logic.
W: The module is pinned to an older version: updating its reference applies the new logic, which is how versioning protects consumers from unplanned changes.
X: A=Permanent caching: results are not cached forever; the module is calling the version it references.
C=Delete the function: destroys the function for every consumer to fix one reference.
D=First version only: modules can reference any published version.
T: After publishing function versions, update each consumer's reference deliberately.

@ PLTR-APD D3 T3.1 applied use-case
S: A function must apply a sequence of tax rules depending on country, product category and customer type. The rules are precise and audited by finance. Which paradigm fits?
A: AIP Logic with the tax rules described in the prompt, so the model can interpret them for each order
B: A TypeScript or Python function implementing the rules deterministically, with tests that finance reviews
C: A Workshop formula duplicated in every module that displays prices
D: Manual tax calculation by the finance team for each order
K: B
G: ## Precise, audited rules belong in code
The exam guide asks you to choose a paradigm by determinism and maintainability.
## Implementation
- Deterministic function; rules as code or governed reference data.
- Tests reviewed by finance; versioned publishing.
Example: a German B2B order of category 3 always yields the documented rate.
W: A deterministic, tested function: exact tax results that finance can audit and that never vary between runs.
X: A=Rules in a prompt: nondeterministic application of precise rules that must be exact and auditable.
C=Formula per module: duplicates logic that drifts and cannot be reused by Actions.
D=Manual calculation: finance staff computing tax for each order is slow and error-prone at any realistic volume.
T: Implement precise, audited business rules as deterministic, tested functions.

@ PLTR-APD D3 T3.4 applied troubleshooting
S: A function fails in production with an error that a property is null, but tests pass. The tests use hand-made objects where the property is always set. What should change?
A: Delete the failing objects from production so that the function only sees objects like those in the tests
B: Handle nulls explicitly and add tests with missing or unusual values from real data
C: Mark the property as required in the Ontology without checking whether existing data has values
D: Wrap the whole function in a try/catch that returns an empty result on any error
K: B
G: ## Tests that reflect real data
The exam guide asks you to test functions and diagnose failures from real execution.
## Changes
- Explicit null handling with a clear behaviour (default, skip or validation message).
- Tests with nulls and edge values sampled from production.
Example: 3% of orders lack a shipping date; the function now treats them as "unscheduled" instead of crashing.
W: Explicit null handling with tests based on real data: the crash is fixed and similar gaps are caught before release.
X: A=Delete objects: destroys legitimate production data so that reality matches the tests, instead of the reverse.
C=Make required without checking: existing objects without values would immediately violate the constraint.
D=Silent empty result: hides the problem and returns wrong results.
T: Test functions with realistic data, including nulls, and handle missing values explicitly.

@ PLTR-APD D3 T3.2 applied comparison
S: Which function design safely updates the priority of every open ticket assigned to a team being disbanded?
A: Iterate over every ticket in the Ontology and check each one's team and status in memory
B: Query open tickets linked to that team server-side and return edits only for those tickets
C: Update all tickets in the Ontology to the new priority regardless of team or status
D: Ask agents to update their own tickets manually over the next week
K: B
G: ## Targeted edits
The exam guide lists querying, filtering and safe edits among function skills.
- Server-side filter: team = X and status = open.
- Edits only for those tickets.
Example: 230 open tickets are updated; closed tickets and other teams are untouched.
W: A filtered query with edits limited to matching tickets: only the intended objects change, efficiently.
X: A=Iterate everything: loads the whole ticket population to find a small subset.
C=Update all tickets: changes the priority of closed tickets and other teams' tickets that should not change at all.
D=Manual updates: agents update tickets over a week, slowly and incompletely, while the team is already disbanded.
T: Limit function edits to objects selected by server-side filters.

@ PLTR-APD D3 T3.3 applied use-case
S: A function computes a shipment ETA and is called from an Action. Customers later dispute ETAs. The team needs to explain any past ETA. What should be stored?
A: Only the final ETA timestamp on the shipment object, since recomputing it later will give the same answer
B: The ETA together with the function version and key inputs (distance, carrier, departure time) used to compute it
C: A screenshot of the shipment page taken each time the ETA changes
D: The name of the user who clicked the button that triggered the ETA calculation
K: B
G: ## Explainable computed values
The exam guide lists provenance among function concepts.
## Store
- Result, function version, key inputs.
- Old versions retained for reproduction.
Example: a disputed ETA of 14:00 is shown to have used carrier speed v2 and a departure at 09:30.
W: Result plus version plus inputs: any past ETA can be explained and reproduced even after logic and data change.
X: A=Final ETA only: recomputing later uses current data and logic, which may differ.
C=Screenshots: unstructured and not linked to inputs or versions.
D=User name: identifies who triggered it, not how it was computed.
T: Store version and inputs alongside computed values that may be disputed.

@ PLTR-APD D3 T3.4 applied use-case
S: Before publishing a function that edits many objects at once, the team wants to ensure it does not exceed limits or time out with real data volumes. What should they do?
A: Test with five objects and assume the function scales linearly to any number of objects in production
B: Run on a branch against the largest realistic set, measure, and bound or page the edits
C: Publish and monitor whether production calls time out
D: Remove the bulk capability and require users to edit objects one at a time
K: B
G: ## Testing at scale
The exam guide asks you to test functions and diagnose failures such as timeouts and unbounded operations.
## Approach
- Branch run with realistic maximum volumes.
- Measure time and edit counts.
- Bound or batch edits; document limits.
Example: the largest region has 12,000 objects; the function is changed to process in pages of 2,000.
W: Test at realistic maximum scale before publishing: limits and timeouts are discovered and designed for, not hit by users.
X: A=Five objects: small tests hide limits that only appear at scale.
C=Publish and monitor: real users hit the timeouts and partial edits first, and the team learns about limits from failures.
D=One at a time: removes a needed capability instead of making it safe.
T: Test bulk-editing functions at realistic maximum volumes before publishing.

@ PLTR-APD D3 T3.1 advanced use-case
S: A team must implement customer churn risk scoring in a function used by several apps. The logic is statistical (weights on features) and owned by data scientists who use Python. Explanations of scores are also requested in natural language. Which design fits?
A: One AIP Logic function that computes the score and writes the explanation from a long prompt describing the weights
B: Python v2 for the deterministic score, plus AIP Logic for explanations from its factors
C: A TypeScript function maintained by app developers who do not know the statistical model
D: Manual scoring by account managers using a spreadsheet template
K: B
G: ## Split deterministic scoring and language generation
The exam guide asks you to choose paradigms by determinism, LLM needs and maintainer audience.
## Design
- Python v2: score from features (deterministic, tested, owned by data scientists).
- AIP Logic: explanation from the score's top factors (typed input), on demand.
Example: score 0.82 with factors "usage down 40%, two support escalations" yields a short explanation for the account manager.
W: Deterministic Python scoring owned by its experts plus AI explanations from structured factors: each part uses the right paradigm and maintainers.
X: A=All in Logic: makes the score nondeterministic and hard to audit.
C=TypeScript by non-experts: maintainers would not understand the model they maintain.
D=Manual spreadsheet: account managers score customers inconsistently and cannot keep up as the customer base grows.
T: Separate deterministic scoring from AI explanations and assign each to the right paradigm and maintainers.
V: Functions, AIP Logic
